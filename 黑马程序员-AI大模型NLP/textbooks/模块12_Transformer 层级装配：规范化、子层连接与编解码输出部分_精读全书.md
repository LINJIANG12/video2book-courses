## 第 1 章：Day09-01.规范化层_代码实现(掌握)
> 对应分集：P126 | 原始标题：《Day09-01.规范化层_代码实现(掌握)》

这一节要把规范化层（Normalization Layer）讲透：它有什么用、怎么算、代码怎么写。在动手之前，先回答一个最直接的问题——**为什么要有它？**

### 为什么需要规范化层

其实很简单。**车开久了要干嘛？要保养。** 规范化层干的就是保养这件事。

再换一个更贴切的场景。你们家装修房子贴瓷砖，瓷砖下面要放砂浆，砂浆是材料加水混合出来的。水放多了会太稀，水放少了会太干，这两种效果都不行。所以你需要一个严格的**监理**（也就是监工）帮你盯着砂浆的调和情况：不管前面的工人把它调成什么样，监理都能让最终的砂浆落在一个合理区间——干了就加水，稀了就加沙子。

规范化层就是数据流里的这个监理。你前面有太多太多的组件在工作、在对数据做处理，为了防止数据跑偏，就要在这里规范一下，让数值处在合理的范围内再往下传递。就像车开一段时间就要保养一次，更换机油、冷却液、空调滤芯这些。

> **定义**：规范化层（Normalization Layer）是一种对输入数据进行归一化的重要组件，通常紧接在每个子层的**输出**之后。

#### 在子层结构里的位置

看子层结构就能看到它：每个子层的输出后面都跟一个 `Norm`，也就是规范化层。它旁边那个 `Add` 是**残差连接**，本质就是一个加法，把数据加到一起。

```text
        x  ------------------------------+
        |                                |
        v                                v
   +---------+                      +---------+
   | 子层计算 |                      |   Add   |  <-- 残差连接（加法）
   +---------+                      +---------+
        |                                |
        +--------------------------------+
                    |
                    v
              +-----------+
              |  Norm     |  <-- 规范化层
              +-----------+
                    |
                    v
                 输出到下一子层
```

读图说明：数据分两路，一路进子层做计算，一路作为残差直接跳过；两路在 `Add` 处相加，结果再送进 `Norm` 做规范化，然后才继续往下传。

#### 两个作用

规范化层要解决的问题，一个是**防止梯度消失或者梯度爆炸**。在深度网络中，随着梯度逐层传递会出现这类问题；对数据做了规范，就可以很大程度缓解。另一个是**加速训练过程**。

#### 与批量归一化的关系

这里会牵出深度学习阶段学过的另一个概念：批量归一化（Batch Normalization，BN）。

> **注意**：面试官极有可能会问你一个问题——BN（批量归一化）和 LN（层规范化）的区别是什么。这个扩展知识点后面单独展开，这里先记住规范化的计算方式，因为两者的公式其实是一样的。

### 计算方式

规范化层的计算方式是：**计算每个位置的所有特征维度的均值和方差，对该位置的所有特征维度做线性变换，保证均值为 0、方差为 1，再进行缩放和平移。**

这个流程熟不熟悉？先算均值和方差，再做缩放平移，**跟批量归一化的公式一模一样**。区别只在一个地方：**计算的方向不同——一个是横着算，一个是竖着算。**

先归一化，归一化之后会发现数据可能被压缩得太厉害，有可能会丢掉一些差异性，所以再用两个可调整的参数把信息找补回来一部分——缩放和平移就是干这个的。

用到的公式就是那个线性形式 $y = kx + b$：$k$ 是缩放因子，$b$ 是平移项。忘了就回去看深度学习那部分的具体公式。

### 规范化层的初始化

类名就叫 `LayerNorm`，它也是一个神经网络层，所以继承 `nn.Module`：

```python
class LayerNorm(nn.Module):
    """规范化层：用于对张量进行标准化处理，让模型训练更稳定"""

    def __init__(self, features, eps=1e-6):
        # 第一步：初始化父类
        super().__init__()
        # 第二步：定义可学习的缩放系数 a，形状与特征维度一致
        self.a = nn.Parameter(torch.ones(features))
        # 第三步：定义可学习的偏置 b（平移系数），形状与特征维度一致
        self.b = nn.Parameter(torch.zeros(features))
        # 第四步：定义小常数 eps，防止分母为 0
        self.eps = eps
```

初始化函数需要两个参数：

| 参数 | 取值 | 含义 |
| --- | --- | --- |
| `features` | `512` | 词嵌入维度，也就是词向量维度 |
| `eps` | `1e-6` | 一个小常数，目的是防止分母变为 0 |

`features` 这里写的是词向量维度，我们一直用的就是 512。`eps` 是一个非常非常小的数，它只做一件事：让分母不会变成 0。

四个动作落下来：

1. 初始化父类成员：`super().__init__()`；
2. 定义可学习的**缩放系数** `a`，初始化值为 1，形状为 `features`；
3. 定义可学习的**偏置** `b`，也就是所谓的平移系数，初始化值为 0，形状同样为 `features`；
4. 定义 `eps`。

`a` 和 `b` 都用了 `nn.Parameter` 包起来，因为它们是**可学习**的——训练过程中要跟着一起更新。

> **提示**：缩放系数初始化成 1、平移系数初始化成 0，这个组合是有讲究的：初始状态下这一层等价于“原样输出归一化结果”，不会一上来就打乱前面层已经学到的表示。平移项一般不需要额外考虑，默认 0 就行。

回顾一下线性公式：$y = kx + b$。这里把 $k$ 换成 $a$ 是同一个意思，$ax + b$ 和 $kx + b$ 在这儿完全一样。所以 `a` 负责缩放，`b` 负责平移，两者作用在**标准化之后**的数据上，一个缩放、一个平移。

### 前向传播

第二个动作是前向传播，它在实现的是对张量的标准化处理。

先把 `x` 扔进来，然后问一件事：**`x` 的形状现在长什么样？**

答案还是那个贯穿全程的形状：`batch_size, seq_len, d_model`，具体就是 `[2, 4, 512]`。

#### 计算最后一个维度的均值

在这三个维度里，要算的是**最后一个维度**——也就是词向量维度——的均值。

为什么只算最后一位？把三个数字翻译成人话：这是一批两个句子，每个句子有四个单词，每个单词用 512 个数字来表示。那么算均值的时候，算的是**每个单词自己的词向量的均值**，也就是对 512 个数求一个均值。

> **易错点**：算“四个单词的均值”没有意义，算“两个句子的所有单词的均值”同样没有意义。有意义的粒度是每个位置的词向量维度——一个位置一个均值。所以维度的选择必须落在最后一位上。

```python
def forward(self, x):
    # 1. 计算最后一个维度（词向量维度）的均值
    x_mean = x.mean(-1, keepdim=True)
```

第一个参数 `-1` 表示**最后一位**，最后一位就是词向量维度。第二个参数 `keepdim=True` 表示**保持维度不变**：算完之后维度还得是 `[2, 4, 512]` 的形状框架，不能把维度消掉。

#### 维度是怎么从 512 变成 1 的

接着算最后一个维度的标准差：

```python
    # 2. 计算最后一个维度（词向量维度）的标准差
    x_std = x.std(-1, keepdim=True)
```

形状的变化一目了然：`[2, 4, 512]` 变成 `[2, 4, 1]`。

为什么是 `1`？因为那 512 个数求出来只有**一个**均值和**一个**标准差。两个句子、每句四个单词，每个单词的词向量各得一个数，所以最后那一维就是 1。

```text
x 的形状演进

  (2, 4, 512)        (2, 4, 512)        (2, 4, 1)
  ┌──────────┐       ┌──────────┐       ┌────────┐
  │ 2 个句子  │  mean │ 2 个句子  │       │ 每个位置│
  │ 每句 4 词 │  /std │ 每句 4 词 │  -->  │ 各得一个│
  │ 每词 512  │  (-1) │ 每词 512  │       │ 统计量  │
  └──────────┘       └──────────┘       └────────┘
       沿最后一位 ->  压成 1          广播回去时自动对齐 512
```

读图说明：均值与标准差都只在最后一位上计算，`keepdim=True` 把这一位保留成 1 而不是直接删掉，这样后面做除法时才能自动广播回 512 维。

#### 标准化与缩放平移

第三个动作是标准化处理，还是回到那个线性公式 $y = kx + b$。这段代码写起来就是一行：

```python
    # 3. 标准化处理：归一化 + 缩放 + 平移
    return self.a * (x - x_mean) / (x_std + self.eps) + self.b
```

把这一行拆开看，正好对应公式的四个部件：

- $(x - x_{mean})$：当前值减去均值；
- $/(x_{std} + eps)$：除以标准差（也就是方差开平方根），分母加上小常数；
- $\times\, self.a$：乘上缩放系数，找回部分被压缩掉的信息；
- $+\; self.b$：最后加上平移。

| 数学符号 | 代码对象 | 作用 |
| --- | --- | --- |
| $\mu$ | `x_mean` | 该位置特征维度的均值 |
| $\sigma$ | `x_std` | 该位置特征维度的标准差 |
| $\gamma$ | `self.a` | 缩放系数，可学习 |
| $\beta$ | `self.b` | 平移系数，可学习 |
| $\epsilon$ | `self.eps` | 小常数，避免分母为 0 |

> **提示**：当前值减该位置的均值、再除以该位置的标准差，这个动作就是标准化处理。做完之后偏差有可能太大，所以前面要乘一个缩放、后面加一个平移，把部分信息找回来。

### 小常数为什么不能省

这一行里有个容易被忽略的“瑕疵”要单独说：分母里的 `x_std` 有可能是 **0**。

标准差一旦是 0，整个除法就废了——除以 0 直接出问题。所以分母必须加上一个小常数，让这个整体、让分母永远不会变成 0。

> **注意**：`eps` 不是可选项，是这个公式能稳定跑下去的前提。它必须加在分母上，且要让加完之后的值仍然足够小，才不会影响归一化的结果。

### 与批量归一化公式的对照

把这个公式和批量归一化的公式摆在一起看，会看到它们**完全一致**：

$$ \text{Norm}(x) = \gamma \cdot \frac{x - \mu}{\sigma + \epsilon} + \beta $$

批量归一化里 $\mu$ 表示均值，$\sigma$ 是标准差（方差开平方根就是标准差），$\epsilon$ 就是小常数，$\gamma$ 对应缩放、$\beta$ 对应平移。它和我们刚写的 `self.a * (x - x_mean) / (x_std + self.eps) + self.b` 是同一个式子。

两者在超参上的取值也很接近：批量归一化的 `eps` 常用 `1e-5`，我们这里写的是 `1e-6`。**其实都一样**，都是“足够小又不为 0”的量级。

> **结论**：规范化层和批量归一化用的是**同一个公式**，唯一不同的是**计算所沿的维度**——一个横着算，一个竖着算。这也是后面“BN 和 LN 的区别”那个扩展话题的真正落点。

## 第 2 章：Day09-02.规范化层_代码测试(理解)
> 对应分集：P127 | 原始标题：《Day09-02.规范化层_代码测试(理解)》

规范化层的类已经写好了，接下来把它跑起来看一眼。测试本身只有四个动作，但它逼着我们把前面几层的关系彻底理清：为什么这次不用自己去取多头注意力的结果，为什么输出形状"看都不用看"就必定是 `[2, 4, 512]`，以及为什么到这一步组件就算收工了。跑完这个测试，我们手上一共攒下五个零件，下一步就该把它们拼成子层。

### 测试链路的四个动作

测试的思路一句话能说完：**先把多头注意力的结果拿到手，再送进前馈全连接处理，处理完的结果交给规范化层，最后返回**。

数据是这样一路传下来的：

```text
词嵌入 + 位置编码
        |
        v
  多头注意力机制   ->  中间结果
        |
        v
  前馈全连接层     ->  处理结果
        |
        v
   规范化层        ->  最终结果（形状不变）
        |
        v
      返回
```

读图说明：规范化层不在链路的最前面，它是"下游的下游"——它的输入必须是前面组件处理完的产物，所以测试函数的第一件事是把上游结果取回来。

第一个动作就叫"获取前馈全连接层的结果"。这里的自然疑问是：思路里明明写着"先获取多头注意力的结果"，代码里为什么直接去拿前馈的结果？原因是前面写前馈全连接层测试的时候，那个函数内部**已经**替我们获取了多头注意力的结果，并且做完了一次前馈处理。既然它已经把活干完了，这里再写一遍取多头的代码就是重复劳动，直接调它就行。

> **提示**：如果你想按最初的思路走，把多头注意力单独取出来、再自己调前馈，也完全没问题。现在手上玩的是**组件**，你可以理解成在搭乐高：手里拿着一个个方块，愿意怎么拼就怎么拼，愿意怎么搭就怎么搭。等真正去实现 Transformer 架构的时候，顺序才必须照着架构图来。

四个动作连起来就是：

```python
def use_layernorm():
    # 动作一：获取前馈全连接层的结果（内部已包含多头注意力的处理）
    ff_x = use_ff()
    # 动作二：创建规范化层对象
    my_layernorm = LayerNorm(512)
    # 动作三：把前馈全连接的结果传给规范化层处理
    result = my_layernorm(ff_x)
    # 动作四：输出形状并返回结果
    print('规范化层', result.shape)
    return result
```

动作二里的 `512` 还是那个贯穿全程的词向量维度 `d_model`。`LayerNorm` 类定义的第一个参数是特征数量，也就是 `features`；`eps` 那个小常数在定义时已经给了默认值，调用的时候不用传。

### 形状不变性的三次验证

第四个动作可以顺带做两件事：打印形状、把结果返回出去。返回是为了让后面别的操作能接着用这份处理结果，不至于每次都要从头重算一遍。

真正值得留意的是形状。这个结果**看都不用看，必定是 `[2, 4, 512]`**。把三个数字翻译成人话：一批两个句子，每句四个单词，每个单词用 512 个数字表示。

前面每一层都承诺过同一件事：

| 环节 | 形状 | 说明 |
| --- | --- | --- |
| 多头注意力层 | `[2, 4, 512]` | 自注意力聚合后的结果 |
| 前馈全连接层 | `[2, 4, 512]` | 先升到 2048 再降回 512 |
| 规范化层 | `[2, 4, 512]` | 归一化不加不减维度 |

三次都是 `[2, 4, 512]`，一个数字都没变。

> **结论**：规范化层处理完以后，形状必定还是它，不能变——变了就没有意义了。整个 Transformer 之所以能一层一层往上叠，靠的正是这个形状不变性：每个组件都是"进去什么形状、出来什么形状"，前一个的输出可以直接当后一个的输入。

形状一样，内容不一样。想看内容变化，把数值全打印出来就行——归一化之后的数字肯定是变化的。这一步的检验点只有两个：形状对得上，数值确实变了。

### 规范化层的作用归纳

测试跑通，顺手把这一层讲过的内容收一下口。

它的定位可以用两个日常场景记住：**车开久了要保养，装修房子要有监工**。你的数值经过前面一系列处理，可能差异过大，也可能超出本身该有的阈值范围；那就得对数值做一次合理处理，把它压回一个合法区间。规范化层干的正是这件事。

> **定义**：规范化层（Normalization Layer）通常接在一个子层的后面，作用是确保网络在处理数据时保持**稳定的分布**，避免数值差异过大。

差异过大的后果很明确：容易出现**梯度消失**或者**梯度爆炸**。

那为什么公式里还要额外乘一个缩放因子、加一个偏置？因为上面的归一化动作可能把很多差异信息压掉了，需要靠两个**可调节的缩放与平移因子**把信息找补回来一部分。往深一层说，它是在学习不同批次之间的数据特征，让模型有更好的**泛化能力**。

> **提示**：这里说的可调节，指的是 `a` 和 `b` 都是 `nn.Parameter`——训练时跟着一起更新，不是写死的常数。这一点和批量归一化（Batch Normalization，BN）完全一致，两者的计算式本来就是同一个。

### 组件收尾：还差一个残差连接

规范化层测完，Transformer 的组件部分就算全都写完了。清点一下手里的零件：

| 组件 | 作用 |
| --- | --- |
| 词嵌入 | 把词映射成向量 |
| 位置编码 | 给词向量叠加位置信息 |
| 多头注意力机制 | 聚合上下文信息 |
| 前馈全连接 | 对每个位置的特征做强化 |
| 规范化层 | 稳住数值分布 |

这里还少一个东西：`Add`，也就是**残差连接**，它还没有单独实现过。

答案是它压根不需要单独实现——残差连接就是把**处理后的数据和原始数据用一个相加函数算在一起**，一行加法而已。所以前面一直没为它写一份组件代码。它的正式出场放在子层里，下一步写子层的时候顺手就把它写了。

组件齐了，接下来该学的就是**子层**：拿这些零件去拼装。多头注意力子层、前馈全连接子层、掩码的多头注意力子层，都是从这一步开始的。

## 第 3 章：Day09-03.扩展_BN和LN的区别(理解)
> 对应分集：P128 | 原始标题：《Day09-03.扩展_BN和LN的区别(理解)》

上一节写规范化层的时候，有个细节挺别扭：它的计算式跟深度学习阶段学过的批量归一化**几乎一模一样**。既然公式一样，那这两个东西到底差在哪儿？这就是一道很常见的面试题——BN 和 LN 的区别。被问到了，简单聊聊就行，但一定要聊对。

先把两个缩写展开，别在称呼上先把自己绕晕。

> **定义**：BN 是批量归一化（Batch Normalization）；LN 是层规范化（Layer Normalization），它就是我们刚写完的规范化层，叫层归一化、层规范化都行。

### 用一张三行三列的表格看差别

这两个东西从思路上讲**几乎是一样的处理**。所以要区分它们，不该从公式下手，而该从"算的是哪一摞数"下手。我在纸上画一张三行三列的表格，你们跟着看一遍就懂了。

横着看，一行就是一条数据（一个样本）：这是样本 1，这是样本 2，这是样本 3。竖着看，一列就是一个特征：这是特征 1，这是特征 2，这是特征 3，再往右还是同样的读法，一列一个特征。

```text
              特征1   特征2   特征3
            +-------+-------+-------+
   样本1    |   1   |   2   |   3   |   <- 横着一条 = 一个样本
            +-------+-------+-------+
   样本2    |   3   |   4   |   5   |   <- 横着一条 = 一个样本
            +-------+-------+-------+
   样本3    |   4   |   5   |   6   |   <- 横着一条 = 一个样本
            +-------+-------+-------+
               ^       ^       ^
               |       |       |
             竖着一列 = 同一个特征的三个样本取值
```

读图说明：同一张表，横着读得到样本，竖着读得到特征。里面填的 `1 2 3`、`3 4 5`、`4 5 6` 是随手写的，没有任何含义，也不用去纠结为什么填这几个数——重点是"横"和"竖"这两种读法。

看明白了这张表，两个名词一句话就分完了：

- **竖着一列一列地处理**：同一个特征、不同的样本放在一起算，这是 **BN**（批量归一化）；
- **横着一行一行地处理**：同一个样本、不同的特征放在一起算，这是 **LN**（层规范化）。

```text
      BN：竖着算                          LN：横着算
   特征1  特征2  特征3                特征1  特征2  特征3
  +-----+-----+-----+                +-----+-----+-----+
  |  1  |  2  |  3  |                | [1] | [2] | [3] |  <- 三个格子一起算
  +-----+-----+-----+                +-----+-----+-----+
  |  3  |  4  |  5  |                |  3  |  4  |  5  |
  +-----+-----+-----+                +-----+-----+-----+
  |  4  |  5  |  6  |                |  4  |  5  |  6  |
  +-----+-----+-----+                +-----+-----+-----+
     ^     ^     ^
     |     |     |
  每一列三个格子一起算（跨样本）
```

读图说明：BN 把同一列的三个格子归到一组做统计（跨样本、同一特征），LN 把同一行的三个格子归到一组做统计（同一样本、跨特征）。用同一批数字，两种归组的粒度不一样，算出来的统计量自然不一样。

> **结论**：公式一样，方向不一样。一个是横着算，一个是竖着算。记住这一条，这道题就不会答反。

#### 两种方向的数值对照

拿表里的数字各算一次，差别落得最实。**BN 处理特征 1 这一列**：三个样本的取值是 1、3、4，均值 $\mu=\frac{1+3+4}{3}=\frac{8}{3}\approx 2.67$，方差 $\sigma^2=\frac{(1-2.67)^2+(3-2.67)^2+(4-2.67)^2}{3}\approx 1.56$，标准差 $\sigma\approx 1.25$。三个数各自减去均值再除以标准差，得到 $[-1.33,\,0.27,\,1.07]$，和恒等于 0。

**LN 处理样本 1 这一行**：三个特征的取值是 1、2、3，均值 $\mu=\frac{1+2+3}{3}=2$，方差 $\sigma^2=\frac{(-1)^2+0^2+1^2}{3}=\frac{2}{3}\approx 0.67$，标准差 $\sigma\approx 0.82$。三个数算出来是 $[-1.22,\,0,\,1.22]$。

同一张表，BN 把"特征 1 上的三个样本"压成均值 0，LN 把"样本 1 上的三个特征"压成均值 0。**两边的归一化公式一模一样，只是参与统计的那一组数字换了对象。**

#### 为什么文本用 LN 而不是 BN

再看场景那一栏：BN 一般用于处理**图片**，LN 一般用于处理**文本**。这话怎么记才不容易忘？

图片的数据是固定的形状，每个通道、每个位置在所有样本上都有对齐的语义——所以沿样本维统计同一个特征是有意义的。文本换过来看：一批句子，句子长度参差不齐，序列长度是可变的，而且**不同句子的同一个"位置"之间本来也不算同一回事**。这时候再按 BN 那样统计"这个位置上跨样本的均值"，把不同句子不同内容的东西凑在一起算，就失去意义了。

LN 的统计范围**只在一个样本内部**：一句句子里所有位置、所有特征一起算，跟同一批里别的句子没有任何关系。样本之间互不牵连，长短句各算各的，这正是它更适合文本的原因。

### 面试话术的两句标准答法

横竖的说法自己心里清楚就行，面试场上不能这么讲——"一个横着一个竖着"肯定不合格。要把话组织成规范的技术表述。

**BN 的说法**：批量归一化是针对**同一个特征、不同的样本**进行规范化，一般用于处理**图片**。

**LN 的说法**：层规范化（也叫层归一化、规范化层）是针对**同一个样本的不同的特征**进行处理，一般用于处理**文本**。

对着上面的表格逐句核对一遍：BN 里"同一个特征"就是同一列，"不同样本"就是这一列的三个格子——它确实是在竖着的一条上做处理。LN 里"一个样本"就是同一行，"不同的特征"就是这一行的三个格子——它确实是在横着的一条上做处理。

| 对比项 | BN（批量归一化） | LN（层规范化） |
| --- | --- | --- |
| 统计方向 | 竖着算：同一列、跨样本 | 横着算：同一行、跨特征 |
| 规范化对象 | 同一个特征、不同的样本 | 同一个样本、不同的特征 |
| 典型场景 | 图像 | 文本 |
| 计算式 | 同一个式子 | 同一个式子 |

> **易错点**：这两句话极容易在面试现场说颠倒。判断办法只有一个——把"特征"和"样本"这两个词跟表格的列、行对上：跨样本必然是竖着，跨特征必然是横着。

### 回到我们写的 LN：横着算的就是那 512 维

前面实现规范化层的时候，前向传播里做的是 `x.mean(-1, keepdim=True)` 和 `x.std(-1, keepdim=True)`，最后一位就是词向量维度。现在能用这张表解释了：`x` 的形状是 `[2, 4, 512]`，也就是 2 个样本、每个样本 4 个位置（可以看成 4 个"词"这个维度上的位置）、每个位置 512 个特征。在最后一位上求均值和标准差，就是**在一个样本内部、跨 512 个特征做统计**——正是"横着算"。

所以每一个词向量各得一个均值、一个标准差，形状 `[2, 4, 512]` 的统计量压成 `[2, 4, 1]`，再广播回去。这也正是我们算出来的那个 512 维层面的结果。

> **提示**：BN 和 LN 的处理思路、计算公式完全相同，都是"减均值、除标准差，再乘缩放、加平移"，差异只在**统计量沿哪个维度求**：BN 沿样本维统计，LN 沿特征维统计。

面试问到你的时候，千万不要在这上面搞晕。一句话记住落点：**横着那个是层规范化，针对的就是你的 512 维**。

## 第 4 章：Day09-04.子层结构搭建_代码实现(掌握)
> 对应分集：P129 | 原始标题：《Day09-04.子层结构搭建_代码实现(掌握)》

组件全部写完了，那些零件一个个摆在桌面上：词嵌入、位置编码、多头注意力、前馈全连接、规范化层。接下来该干的就是把它们拼起来——这一步叫**子层**。你玩过乐高或者拼过机器人就知道，零件准备好之后才是真正的搭建阶段：拿哪块、往哪拼、先拼哪一边，从这一节开始才有讲究。

### 编码器与解码器的子层数量

先看架构图上这几个方框。按位置念一遍：编码器里头有几个子层？一个前馈全连接子层，一个多头注意力子层——**两个**。解码器呢？一个带掩码的多头注意力子层，一个不带掩码的多头注意力子层，再加一个前馈全连接子层——**三个**。

```text
   编码器层（2 个子层）              解码器层（3 个子层）
   +----------------------+        +----------------------+
   |  多头注意力子层       |        |  掩码多头注意力子层   |
   +----------------------+        +----------------------+
   |  前馈全连接子层       |        |  多头注意力子层       |
   +----------------------+        +----------------------+
                                   |  前馈全连接子层       |
                                   +----------------------+
```

读图说明：编码器层由两个子层堆叠而成，解码器层由三个子层堆叠而成；不管哪个位置的子层，内部装的都是同一个套路——一个组件、一个残差连接、一个规范化层，区别只在换来换去的那个组件是什么。

> **定义**：子层（Sublayer）就是用一个固定套路把组件**封装**起来的结构：多头注意力子层 = 多头注意力 + 残差连接（`Add`）+ 规范化层（`Norm`）；前馈全连接子层 = 前馈全连接 + 残差连接 + 规范化层。

看出来了吗？`Add` 和 `Norm` 是**固定的**，剩下那个位置看你这回传的是谁：传前馈全连接，它就是前馈全连接子层；传多头注意力，它就是多头注意力子层。这就是子层的设计思想——功能上实现的是

$$ x + x_2 $$

也就是"原始数据加上子层处理后的数据"。整个编码器层或者解码器层，说白了就是这样的子层跟堆积木一样叠起来的，这样写**好管理**。

这样做的实际好处，是组件级的测试代码可以完全复用。前面每个组件都留了一个 `use_xxx` 测试入口，到这里我们不重写任何计算，直接从组件文件里导进来拼装。

### 导包与前缀复用

第一步是建一个新的脚本，名字叫 `dm03_encoder_sublayer`，`sublayer` 就是子层。名字最好跟我保持一致，因为下一步要导包。

第二步是导包。子层的搭建既然只是"把之前写的组件拼起来"，那导入就非常简单——前面两个文件里的东西全都需要用：

```python
# 导入 dm02 里自己搭建的全部组件
from dm02_components import *
# 导入 dm01 里词嵌入与位置编码相关的内容

```

两个 `import *` 之后，前两个文件里写过的所有内容在这个新脚本里都能直接访问：`LayerNorm`、`MultiHead`、`PositionwiseFeedForward`，以及那几个 `use_xxx` 测试函数。**子层不生产任何新计算，它只负责组装**——这就是为什么这一节的导入这么粗暴还不出问题。

### 子层连接结构的初始化

接下来是 `TODO 1`：初始化子层连接结构。核心是残差连接加规范化层，让模型训练更稳定，避免梯度消失或者梯度爆炸。

类名写成 `SublayerConnection`。第一个动作肯定是初始化函数：

```python
class SublayerConnection(nn.Module):
    """子层连接结构：组件 + 残差连接 + 规范化层"""

    def __init__(self, d_model, dropout):
        # 1. 初始化父类成员
        super().__init__()
        # 2. 定义规范化层
        self.norm = LayerNorm(d_model)
        # 3. 定义随机失活层
        self.dropout = nn.Dropout(p=dropout)
```

初始化函数要两个参数：

| 参数 | 取值 | 含义 |
| --- | --- | --- |
| `d_model` | `512` | 输入的维度，即词向量维度 |
| `dropout` | `0.1` | 随机失活的概率 |

`d_model` 这个名字一看就知道是什么，我们一直写的就是 512。

定义规范化层这一行直接把前面写的 `LayerNorm` 调过来用：`self.norm = LayerNorm(d_model)`。按住 `Ctrl` 点进去看，跳转的就是 `dm02` 里我们自己的那个 `LayerNorm` 类，它需要的"特征数量"就是我们传过去的词向量维度；那个小常数在类定义里已经有默认值，这里不用传。这就是组件复用最直接的体现——规范化层写了一遍，到子层这一步是"拿过来"，不是"再写一遍"。

> **提示**：`dm02` 既然是自己写的文件，`LayerNorm` 就不是 `torch.nn` 里的那个；`Ctrl` 点击跳转到哪，就说明当前调用的是哪个。养成跳进去看一眼的习惯，能在报参数错误之前就发现问题。

### 前向传播：把子层对象当模板参数传进来

第二个动作是前向传播函数，完成具体的一个子层的计算动作。它要两个东西：

- `x`：输入张量，形状还是那个熟悉的 `batch_size, seq_len, d_model`，也就是 `[2, 4, 512]`；
- `sublayer`：**输入的子层对象**——例如多头注意力层对象 `MultiHead`，或者前馈全连接层对象 `PositionwiseFeedForward`。

`sublayer` 这个参数是整节代码的关键。它意味着这个类是一个**模板（框架）**：把多头注意力这个组件传进来，它就是多头注意力子层；把前馈全连接传进来，它就是前馈全连接子层。至于怎么调用那个组件、残差在哪加、规范化在哪做，全都由这个类统一负责——**变化的只是被传进来的组件，固定的流程写在这里一次**。

#### 核心逻辑的两种实现方式

子层的核心逻辑有两种常见的实现方式。

**方式一**：先子层处理，再残差连接，然后层规范化。大多数场景里用的都是这种。

```python
def forward(self, x, sublayer):
    # 子层处理 -> 残差连接 -> 随机失活 -> 层规范化
    my_result = self.norm(self.dropout(sublayer(x) + x))
    return my_result
```

这一行里的每个角色都对得上：`sublayer(x)` 是**子层处理**，`+ x` 是**残差连接**，`self.dropout` 是随机失活，`self.norm` 是层规范化。一层层拆开就是这个顺序：

1. 数据进子层（比如多头注意力）算出处理结果；
2. 处理结果跟原始数据 `x` 相加——这就是残差连接；
3. 相加的结果过一遍随机失活；
4. 最后过规范化层，作为这一层的输出返回。

**方式二**：处理顺序不同——先**规范化层**，再子层处理，最后残差连接。代码改法很简单，就是把包裹的次序换一下：先子层、再规范化、再拼接、再失活；或者先规范化、再子层、再拼接。感兴趣可以自己写一份对比，代码结构一样，**只是次序不同**。

> **结论**：实际开发里用得比较多的是方式一。你自己拼的时候怎么排都行，最后多测一测，看哪种效果更好；但面试或工程里被问到标准写法时，答方式一。

最后一个动作是 `return`，把 `my_result` 返回出去，这就是子层的输出。写完这一步，子层连接结构的初始化部分就完整了，`TODO 2` 测试子层连接结构是下一步的事。

### 残差连接的数据流

要想确信"残差连接就是一次加法"，得把数据流从头走一遍。先记住一个基准点：**经过词嵌入和位置编码处理后的原始结果，没有做任何额外处理**，我们就叫它绿点。

```text
绿点（词嵌入 + 位置编码的原始结果，未做处理）
  |
  +--> 复制三份，分别充当 Q、K、V
  |        |
  |        v
  |   多头注意力计算 ... ---------+
  |                               |
  |                               v
  |                          [处理结果]
  |                               |
  +-------------------------------+
                  |
                  v
              红点 = 多头注意力处理结果 + 原始数据（残差连接，加法）
                  |
                  +--> 红点再复制三份，充当 Q、K、V
                  |        |
                  |        v
                  |   前馈全连接处理 ... ----+
                  |                          |
                  |                          v
                  |                     [处理结果]
                  |                          |
                  +--------------------------+
                                  |
                                  v
                          黑点 = 前馈处理结果 + 红点（再一次残差连接）
```

读图说明：绿点是未经任何处理的原始数据；红点是"多头注意力那一整套处理的结果"与"绿点"相加得到的，所以红点其实是两条支路的和；黑点同理——是"前馈全连接处理的结果"与"红点"相加得到的。每一个残差连接都是**自身加上一个子层的处理结果**，中间那堆乘加运算不管多复杂，最后都要回到这条主干上来。

这就是"以前一直没有写代码模拟残差连接"的原因：它是纯粹的加法，不需要封装成组件，真正需要写的是**在哪里加、跟谁加**。

### 本讲提到的面试题

这一节末尾顺手记了一道要准备的问题。

**题干**：BN（批量归一化）和 LN（层规范化）有什么区别？

**解析**：两者在思路上几乎是同一个处理，计算公式也一致，区别落在**计算方向**上。画一张三行三列的表格：横着看，一行是一个样本；竖着看，一列是一个特征。**BN 是竖着一列一列地处理**，也就是针对同一个特征、不同的样本做规范化，一般用于处理**图片**；**LN 是横着一行一行地处理**，也就是针对同一个样本的不同的特征做规范化，一般用于处理**文本**。

**答案要点**：正面回答时不要讲"一个横着一个竖着"，要讲成"BN 面向同一特征、不同样本，常用于图像；LN 面向同一样本、不同特征，常用于文本"。再补一句印证：我们实现的 LN 是在 `[2, 4, 512]` 的**最后一位**上求均值和标准差，也就是在一个样本内部跨 512 个特征做统计——横着算的那个就是层规范化，针对的就是那 512 维。

解析依据就是本文前面《残差连接的数据流》那一节画的数据流：`[2, 4, 512]` 里的最后一位 512 就是特征维，LN 正是在这一位上求统计量。

## 第 5 章：Day09-05.子层结构搭建_代码测试(理解)
> 对应分集：P130 | 原始标题：《Day09-05.子层结构搭建_代码测试(理解)》

零件都备齐了，子层也搭好了，现在最该做的不是急着往上拼编码器，而是回头把子层这块先用数据跑一遍。原因很实在：越往上走，代码越简单，但越简单的东西一旦错在最底下，报错会追到最上面才暴露。所以这一节的活儿就是把 `SublayerConnection` 单独喂一次数据，确认它的形状对不对、残差连接和规范化有没有真的生效。

### 准备输入数据

测试函数的第一步永远是准备数据，而这里的数据不是随便造的张量，就是前面词嵌入加位置编码处理完的那个结果，也就是 `use_position` 的返回值。

```python
def use_sublayer():
    """测试子层连接结构的完整流程"""

    # 1. 准备输入数据：词嵌入 + 位置编码后的结果
    x = use_position()
```

> **提示**：`use_position()` 这一层是整个 Transformer 的入口，形状是 `[batch_size, seq_len, d_model]`，按我们一直用的例子就是 `[2, 4, 512]`。子层不改变形状，所以它的输入输出形状必须完全一致——这也是后面所有残差连接能成立的前提。

### 实例化子层连接结构

第二步是实例化子层连接结构对象，只传一个 `d_model`，随机失活概率不用写。

```python
    # 2. 创建子层连接结构
    sublayer_connection = SublayerConnection(d_model=512)
```

为什么不写 `dropout`？因为定义这个类的时候已经给了默认值，你不传它就用默认的。参数能少写一个就少写一个，这是读自己代码时最省心的做法。

`SublayerConnection` 内部只做三件事：拿一个层规范化对象、拿一个随机失活对象、在 `forward` 里把「规范化 + 失活 + 残差相加」这套动作串起来。它本身不含任何注意力或全连接的逻辑——它是个壳，是个模板。

### 定义子层对象并传入

第三步是这一节最需要动脑的地方。先把话说清楚：所谓「定义子层函数」，完整的意思是**定义一个子层对象，再把这个对象传进子层连接结构里，充当真正的子层处理**。

能当子层的东西有两个：多头注意力和前馈全连接。这里我拿多头注意力做示例，不是说前馈全连接不能测，而是因为稍后堆叠编码器层时这两个子层都要做，现在先做谁都无所谓。

传参的方式我用函数嵌套，也就是闭包写法：

```python
    # 3. 定义子层对象，充当子层处理（这里用多头注意力做示例）
    def sublayer_x(x):
        # 3.1 创建多头注意力层对象
        multi_attention = MultiHeadedAttention(d_model=512, head=8)
        # 3.2 计算注意力并返回：自注意力，所以 q = k = v = x
        return multi_attention(x, x, x)
```

这里的三个 `x` 就是 Q、K、V。自注意力的特点就是查询、键、值全部来自同一份输入，所以三个位置填同一个变量。`512` 是词向量维度，`8` 是头数，这两个参数必须传，因为它们是 `__init__` 的必填项。

现在关键认识来了：**`sublayer_x` 这个函数，对子层连接结构来说就是一个子层**。它可以被调用，接收 `x`，处理完返回结果——满足这三条就够了，子层连接结构并不关心它内部是多头还是全连接。

### 通过子层连接处理输入

把 `x` 和子层对象一起交给子层连接结构：

```python
    # 4. 通过子层连接处理输入，验证残差连接和规范化的效果
    result = sublayer_connection(x, sublayer_x)

    # 5. 打印处理结果
    print("子层处理结果:", result.shape)
```

`x` 是要被处理的值，`sublayer_x` 是处理它的对象，两个参数一对，子层连接结构内部就会执行「子层处理 → 层规范化 → 随机失活 → 与原始 `x` 相加」。

如果第三步里我不写多头，而是把那个函数体换成前馈全连接，这一整块就变成了前馈全连接子层。子层连接结构一行都不用改——这就是它作为模板的价值。

最后跑起来，结果必定是 `[2, 4, 512]`。子层只做变换不做压缩，形状从哪进就从哪出。

### 用匿名函数替代函数嵌套

上面那种写法虽然只有两行，但我嫌累：一个函数里先造对象、再 return 对象的处理结果，这本质上就是一行代码的活儿。一个函数、一行代码，那还能用什么写？用匿名函数，也就是 lambda 表达式。

两种写法是完全等价的替换关系，原来那个 `sublayer_x` 直接注释掉就行。区别只在 `sublayer` 这个位置填什么——把函数换成 lambda 表达式：

```python
    # 4. 通过子层连接处理输入（lambda 写法）
    result = sublayer_connection(x, lambda x: multi_attention(x, x, x))
```

注意这里为什么能直接写 `multi_attention`：因为这个对象是由外面的函数创建出来的，lambda 里可以直接引用它，不需要重新创建。如果 lambda 写在一个拿不到这个对象的位置，就会报未定义——那就把对象创建语句等价替换过来，直接内联进 lambda 里。这两种写法（先建对象再引用、直接内联）效果一样，内联版更紧凑：

```python
    result = sublayer_connection(
        x, lambda x: MultiHeadedAttention(d_model=512, head=8)(x, x, x)
    )
```

换成前馈全连接子层，写法一模一样，只是把中间那个对象换掉：

```python
    # 前馈全连接子层
    result = sublayer_connection(
        x, lambda x: FeedForward(d_model=512, d_ff=2048)(x)
    )
```

**为什么前馈全连接的 lambda 后面只跟一个 `x`，而多头注意力要跟三个？** 这是最容易写错的地方，我从两个方向说清楚：

- `__init__` 里传几个参数，取决于这个类的构造需要什么。`MultiHeadedAttention` 需要 `d_model` 和 `head`；`FeedForward` 需要 `d_model` 和 `d_ff`，这两个都是必填，少一个就报错。
- `forward` 里传几个参数，取决于它的前向逻辑需要几个输入。多头的 `forward` 要收 Q、K、V 三个，所以调用时给三家；前馈全连接的 `forward` 只处理一路特征，所以给一个 `x`。

换句话说：类名后面括号里的是「建对象要什么」，对象后面括号里的是「跑一次要什么」，两套参数不要混。

> **易错点**：`d_ff` 是升维的维度。前馈全连接的作用是强化特征，先把你从 `512` 升到一个更大的维度，再降回 `512`。忘了 `d_ff` 是多少，就点进 `FeedForward` 的源码看一眼——它的 `__init__` 里就是这两个参数。

### 参数名与 IDE 的检查手法

写这种嵌套调用时经常遇到一个「报黄」：IDE 给参数名标黄，提示你的参数名和人家定义的参数名对不上。参数名不匹配本身不影响运行（Python 的位置参数按顺序传），但看着很难受，而且以后改成关键字传参就会出错。

我给的建议是：不想纠结就别写参数名，只给位置参数，它一定不会错。但如果你确实记不清顺序，就用下面两个动作之一去确认：

- 把光标悬停在类名或对象上停一两秒，弹框会告诉你每个参数叫什么名、默认值是什么；
- 按住 `Ctrl` 不松手，用鼠标左键点进去，直接跳到源码里自己看。

这两个手法在这一节里会被反复用到：`FeedForward` 的参数名、`MultiHeadedAttention` 的参数顺序、`SublayerConnection` 的默认失活概率，都是靠它们确认的，不要凭记忆硬写。

### 子层测试的完整流程与结论

把这一节的逻辑画成一条线：

```text
   词嵌入 + 位置编码  ──►  x = use_position()         形状 [2, 4, 512]
                              │
                              ▼
                       sublayer_connection             只传 d_model=512
                              │
        ┌─────────────────────┴─────────────────────┐
        │  sublayer_connection(x, sublayer)         │
        │                                           │
        │   子层处理   sublayer(x)                  │  ← 多头注意力 / 前馈全连接
        │      │                                    │
        │      ▼                                    │
        │   层规范化   LayerNorm                    │
        │      │                                    │
        │      ▼                                    │
        │   随机失活   Dropout                      │
        │      │                                    │
        │      ▼                                    │
        │   残差相加   dropout(...) + x             │  ← 原始 x 直连过来
        └─────────────────────┬─────────────────────┘
                              │
                              ▼
                   result.shape == [2, 4, 512]
```

这张图说明一件事：`x` 走两条路，一条被子层加工过，另一条原封不动地绕过来做加法，最后汇合。因为形状全程不变，加法才能成立，规范化也才能在最后一个维度上正常统计。

> **结论**：子层这件事说穿了就三步——准备数据、把子层搭好、子层里传对象。`x` 是要处理的数，后面跟的是子层对象，至于这个对象是多头注意力还是前馈全连接，随你挑，等你往上拼编码器层的时候，两个都得用上。

到这里你会发现一个规律：代码越往后写越简单。零件准备阶段最麻烦、最耗时，零件齐了以后就是拼拼拼，一路拼上去。子层连接结构是最后一次需要动脑的封装，再往上就是组装了。

## 第 6 章：Day09-06.编码器层_代码实现(掌握)
> 对应分集：P131 | 原始标题：《Day09-06.编码器层_代码实现(掌握)》

子层搭完，再往上就该编码器层了。整个编码器由六个编码器层叠起来，而一个编码器层内部由两个子层组成——这句话就是这一节全部工作的地图。编码器层的角色是编码部分的组成单元，它完成一次对输入特征的提取，也就是一次编码过程：未经过编码处理的数据进来，经过这一层的处理再出去。

先把概念记成一句能复述的话：

> **定义**：编码器层（Encoder Layer）是编码器的组成单元，它内部由两个子层连接结构串联而成，负责完成一次对输入特征的提取。

因为是「两个子层连起来」，所以这一节的代码本质上是搭积木：词向量加位置编码是输入，接下来是多头注意力，注意力后面接残差连接加规范化层，再往下是前馈全连接，前馈全连接后面又是一套残差连接加规范化，最后输出——输出的下一步就该交给解码器那一套了。既然只是把现成的东西串起来，那么这一节要做的事只有三件：导包、初始化、前向传播。

### 导包与文件组织

先建一个新脚本。前面写过 `dm03` 是子层，那这个就叫 `dm04`：把 `sub` 去掉，留下 `layer` 就行。

```python
from dm01 import *
from dm02 import *
from dm03 import *
```

三个包各管一块：`dm01` 是位置编码，`dm02` 是输入部分，`dm03` 是子层。这里有个命名细节值得改一下：`dm02` 原来的名字是 `positional_encoding`，不合适，因为里面装的是词嵌入和位置编码这套输入环节，改叫 encoder element（输入部分）更贴切、更好检索。

再往下要说清 `dm03` 的定位：它里面装的多头注意力、前馈全连接这些组件，严格说不专属编码器——到解码器那边前馈全连接和多头注意力同样要用。所以这一层就叫「组件」，`dm03` 叫「子层」，`dm04` 才叫「编码器层」。

记住这条链，它决定了后面每一节该去哪里找东西：

```text
   组件（多头注意力 / 前馈全连接）
        │  被封装进
        ▼
   子层（SublayerConnection）
        │  被克隆两份并串联成
        ▼
   编码器层（EncoderLayer）
        │  被深拷贝六份并堆叠成
        ▼
   编码器（Encoder）
```

读图要点：每一级都是「拿到下一级的对象当参数」，一级一级嵌套上去。组件往上是子层，子层往上是编码器层。

### 初始化函数与参数

编码器层也是一个神经网络层，所以它同样只有两部分：`__init__` 和 `forward`。初始化函数要接四个参数：

```python
class EncoderLayer(nn.Module):
    """编码器层：把两个子层合二为一，串起来"""

    def __init__(self, d_model, self_attn, feed_forward, dropout=0.1):
        super().__init__()

        # 保存子层实例
        self.d_model = d_model
        self.self_attn = self_attn
        self.feed_forward = feed_forward

        # 克隆两个子层连接结构
        self.sublayer = clones(
            SublayerConnection(d_model, dropout), 2
        )
```

四个参数分别是：

| 参数 | 含义 | 我们用的值 |
| --- | --- | --- |
| `d_model` | 词嵌入维度 | `512` |
| `self_attn` | 多头注意力对象 | 外部传入的对象 |
| `feed_forward` | 前馈全连接对象 | 外部传入的对象 |
| `dropout` | 随机失活概率 | `0.1` |

注意 `self_attn` 和 `feed_forward` 传进来的是**对象**，不是类、也不是类名。这一点和后面测试时的传参方式直接相关：现在你把两个现成的对象扔给我，我就能拼出一个编码器层。

而 `d_model` 和 `dropout` 是配置量，用来构造子层。子层连接结构的构造本来就需要「词向量维度」和「随机失活概率」，正好由上一级保管、往下发。

### 克隆两个子层对象

编码器层里有几个子层对象？两个。所以要克隆两份子层连接结构：

```python
        self.sublayer = clones(SublayerConnection(d_model, dropout), 2)
```

`clones` 是前面写过的克隆函数，点进去看它的实现：返回一个 `nn.ModuleList`，里面装的是 `copy.deepcopy` 出来的副本。深拷贝意味着每个副本都是独立的，各自不相干，改一个不影响另一个——这就是「动态拷贝」的用处：两个子层结构一样但参数必须各算各的。

跑完这一行，`self.sublayer` 就是一个列表，里面有子层对象 1 和子层对象 2。后面写前向传播时，靠下标 `0` 和 `1` 把它们分别取出来。

### 前向传播：第一个子层（自注意力）

前向传播接收两个参数：

```python
    def forward(self, x, mask):
```

为什么编码器层也要 `mask`？因为编码器本身用不到掩码，但解码器要用，而这两个类是对称搭出来的。参数列表保持一致，解码器层那里就不用再改结构。

接着是第一个子层：

```python
        # 第一层子层连接：多头自注意力
        x = self.sublayer[0](
            x, lambda x: self.self_attn(x, x, x, mask)
        )
```

逐段拆开看：

- `self.sublayer[0]` 取出第一个子层连接结构对象。它等价于我们上一节测试时用的 `sublayer_connection` 那个变量，所以上一节测通的那行代码，这里可以直接照搬，只需要把 `sublayer_connection` 换成 `self.sublayer[0]`。
- 第一个参数 `x` 是待处理的值；第二个参数是子层对象，这里用 lambda 现场定义一个。
- 这个 lambda 干的事就是调用注意力对象：`self.self_attn(...)`。

**为什么是 `self.self_attn` 而不是 `MultiHeadedAttention`？** 因为注意力对象不是在这里创建的，而是 `__init__` 时由外面传进来存好的。`self.self_attn` 就是那个已经实例化好的多头注意力对象，等价于测试代码里那个 `multi_attention` 变量。既然对象已经存在，这里就不需要再构造一次，要做的事情只有一件：把参数丢进去。

那就是 `x, x, x, mask`——前三个是 Q、K、V，自注意力所以三个都填 `x`，第四个是掩码。写完这一行，第一个子层就通了。

### 前向传播：第二个子层（前馈全连接）

第二层和第一层结构完全一样，只换两处：取下标 `1`，以及把内部对象换成前馈全连接。

```python
        # 第二层子层连接：前馈全连接
        x = self.sublayer[1](
            x, lambda x: self.feed_forward(x)
        )

        return x
```

两处差异要盯住：

- `self.sublayer[1]` 取第二个子层对象；
- `self.feed_forward(x)` 只传一个 `x`，因为前馈全连接的 `forward` 只处理一路特征。

其余原封不动——同样用 lambda 把对象包一层当子层用，同样交给子层连接结构去做规范化、失活和残差相加。

写完 `x` 的接收，最后 `return x`。也可以不接收、直接返回，但分开写更清楚：你能一眼看出第一个子层的输出就是第二个子层的输入。

### 残差连接与规范化到哪去了

有人会问：编码器层里不是还该有残差连接和规范化层吗，代码里怎么没写？

答案在子层里。点进 `SublayerConnection` 的 `forward` 看一遍它的执行顺序：先做子层处理（也就是传进去的多头注意力或前馈全连接），做完做层规范化，规范化完做随机失活，失活完做残差相加。

```text
   SublayerConnection.forward(x, sublayer)
        │
        ├─► sublayer(x)              ← 多头注意力 或 前馈全连接
        │
        ├─► LayerNorm                 ← 规范化
        │
        ├─► Dropout                   ← 随机失活
        │
        └─► Dropout(...) + x          ← 残差连接
```

也就是说，这套「处理 → 规范化 → 失活 → 加原始输入」的动作在子层结构里已经做完了。编码器层要做的事情只有封装：把两个子层依次套上去。这也是为什么搭到编码器层会突然觉得简单——难的部分在零件和子层阶段已经吃掉，剩下的就是拼装。

### 编码器层的完整数据流

把这一节的实现整理成一张图：

```text
   输入 x  [batch_size, seq_len, d_model]
     │
     ├──────────────────────────────┐
     │                              │
     ▼                              │
   SublayerConnection #0            │
     ├─ self_attn(x, x, x, mask)     │
     ├─ LayerNorm                    │
     ├─ Dropout                      │
     └─ Dropout(...) + x  ◄──────────┘   残差：原始 x 直连过来
     │
     ▼   （形状仍是 [2, 4, 512]）
     ├──────────────────────────────┐
     │                              │
     ▼                              │
   SublayerConnection #1            │
     ├─ self.feed_forward(x)         │
     ├─ LayerNorm                    │
     ├─ Dropout                      │
     └─ Dropout(...) + x  ◄──────────┘   残差：第一个子层的输出直连
     │
     ▼
   输出 x  [batch_size, seq_len, d_model]
```

读图要点：两个子层严格串联，第一个子层处理完的结果既作为第二个子层的输入，也作为第二个子层残差连接的被加项；形状从头到尾不变，所以两次加法都能成立。

> **结论**：编码器层的实现就是给我一个词嵌入维度、一个多头注意力对象、一个前馈全连接对象，其余什么都不用管——第一个子层做自注意力，第二个子层做前馈全连接，中间那些规范化、失活、残差全部由子层内部完成。

到这儿编码器层就搭完了。这一步的搭建和搭积木是一个道理，一环套一环，而且越往后写越简单：这一节写完，接下来只要把数据喂进来，确认它进得去、出得来、形状没变，就可以继续往编码器整体推进了。

写这一行最容易卡在「里面参数叫什么名」。两种办法确认：一是把光标放到 `MultiHeadedAttention` 上按 `Ctrl+Q` 看建议，它会给出参数提示；二是鼠标悬停在类名上别动，等两秒左右弹框，里面就直接写着两个参数——`d_model` 和 `head`。词嵌入维度是 `512`，头数是 `8`。

`d_ff` 这个参数的意思是把特征升维升到多少。前馈全连接层干的活就是强化特征：从原始维度 `512` 升到一个更大的维度，`2048`、`1024` 等等都行，只要比 `d_model` 大就可以；升上去之后再降回 `512`。所以我们这里写 `512 → 2048`。

### 构建掩码张量

形状这里要看清楚：多头注意力是多头的，所以掩码要能对应到每个头上，写成 `[8, 4, 4]`——`8` 是头数，后面 `4, 4` 是句长乘句长。如果只写 `[2, 4, 4]` 就会和头数对不上，或者语义上落错位置。

```python

```

打出来的就是一整个嵌套结构，横着读下来，每一项都对得上我们写过的代码：

```text
EncoderLayer(
  (self_attn): MultiHeadedAttention(...)
  (feed_forward): FeedForward(...)
  (sublayer): ModuleList(
    (0-1): 2 x SublayerConnection(
      (norm): LayerNorm(...)
      (dropout): Dropout(p=0.1, inplace=False)
    )
  )
)
```

逐块对照一下：

- `self_attn` 是一个整体，就是多头注意力子层里的那个多头注意力组件，对应我们刚才传进去的 `multi_head`；
- `feed_forward` 也是一个整体，就是前馈全连接子层里的组件；
- `sublayer` 是一个 `ModuleList`，里面写着 `0-1`、`2 x SublayerConnection`——意思是这里有**两个子层对象**，因为 `2 × SublayerConnection`。每个子里装着 `norm`（层规范化）和 `dropout`（随机失活，连同概率 `0.1`）。

看这个对象的时候，先看大框架再看里面：`self_attn` 圈一个整体，`feed_forward` 圈一个整体，`sublayer` 那个 `ModuleList` 圈一个整体，三个大块各归各位，再去细看 `LayerNorm` 和 `Dropout` 这些零件。

### 从对象结构读出网络层数

再把注意力放到 `self_attn` 里面那一层：

```text
MultiHeadedAttention(
  (linears): ModuleList(
    (0-3): 4 x Linear(...)
  )
  (attn): Attention(...)
  (dropout): Dropout(p=0.1, inplace=False)
)
```

`0-3`、`4 x Linear` —— 多头注意力子层里有**四个线性层**。每个头做注意力时 Q、K、V 各需要一个线性层，这是三个；多头的多个头算完之后要把结果合并回一个，还需要一个线性层，加起来四个。你忘了就问自己一句：当时讲多头机制时那个「吃火锅」的比方，把特征切成细丝分给不同的头去处理，切之前要投影、切完要合并，投影和合并用的都是全连接层——三路投影加一路合并，四个。

再看前馈全连接：

```text
FeedForward(
  (linear1): Linear(in_features=512, out_features=2048, ...)
  (linear2): Linear(in_features=2048, out_features=512, ...)
  (dropout): Dropout(p=0.1, inplace=False)
)
```

**两个线性层**：一个是升维，从 `512` 升到 `2048`；另一个是降维，从 `2048` 降回 `512`。一升一降之间做非线性变换，特征就被强化了一遍——这就是前馈全连接在这一层里的全部职责。

汇总一下这一层里到底有几层网络：

| 子层 | 内部线性层数 | 作用 |
| --- | --- | --- |
| 多头注意力子层 | 4 | Q、K、V 三路投影 + 多头结果合并 |
| 前馈全连接子层 | 2 | `512 → 2048` 升维、`2048 → 512` 降维 |

> **结论**：一个编码器层 = 两个子层；多头注意力子层里有 4 个线性层，前馈全连接子层里有 2 个线性层。这些数字不需要背，把对象打印出来，结构自己会告诉你——而且打出来的每一项都能指回你亲手写过的代码，指针指到哪，哪就是它的定义。

把对象打印出来这件事，比单看形状有价值得多：形状只回答「通了没有」，对象结构回答的是「里面是什么」。以后往上拼编码器、解码器的时候，凡是怀疑某一层内部少装了东西，都可以用同样的办法先打印再判断。

### 2 编码器类的实现

#### 2.1 类定义与初始化参数

第一个 TODO 是定义编码器类。

```python
class Encoder(nn.Module):
    def __init__(self, layer, n):
        super().__init__()
```

参数只有两个，但都得说清楚：

- `layer`：单个编码器层，也就是我们上一个脚本里搭好的 `EncoderLayer` 对象；
- `n`：编码器层的数量。

**为什么不把 6 直接写死？** 因为经典的 BERT 底层默认确实是六个编码器层，但往后走就不一样了，BERT 有很多变体，有些模型的底层是 12 层。传一个 `n` 进来，这个编码器就能适配不同的深度，灵活。

> **提示**：`super().__init__()` 是初始化父类成员，这一步省不掉，漏了后面注册子模块时会报错。

#### 2.2 克隆 n 个编码器层对象

```python
        self.layers = clones(layer, n)
```

把传进来的编码器层克隆 `n` 份。这里要注意我讲的是编码器，但你们脑子里要同时做变形——一会儿把它改成解码器，解码器的写法是一模一样的。

#### 2.3 最终规范化层

第三个动作是定义最终的规范化层。

```python
        self.norm = LayerNorm(layer.d_model)
```

`LayerNorm` 我们在前面已经写过，这里传的维度是 `d_model`，也就是词向量的维度 512。

有人会问：`layer` 里面怎么会有 `d_model` 这个属性？翻回编码器层的定义就能看到，它初始化时就把 `d_model` 存成了自己的属性，所以这里能直接调出来。

**这一层为什么要额外加？** 看结构图：输入依次经过六个编码器层，六个都处理完之后，还要再做一次规范化，也就是拿最后一个编码器层的输出再过一遍层归一化。

> **注意**：这最后一次规范化在图里其实并没有画出来，你可以把它理解为额外加的，作用是提升模型的稳定性。

### 3 编码器前向传播

#### 3.1 输入与掩码的形状

```python
    def forward(self, x, mask):
```

- `x`：输入张量，形状 $(N, S, D) = (2, 4, 512)$，即 `batch_size`、`sequence_length`、`d_model`；
- `mask`：掩码张量，形状 $(8, 4, 4)$——八个头，所以是 $8 \times 4 \times 4$，写成具名维度就是 `batch_size × sequence_length × sequence_length`。

#### 3.2 依次经过 n 个编码器层

```python
        for layer in self.layers:
            x = layer(x, mask)
```

`self.layers` 里已经克隆出了六个编码器层对象，遍历就是把它们一个一个取出来，每个都做一次处理：第 1 个、第 2 个……一直到第 6 个。**x 是待处理的数据，也同时是每一层的输出**，所以直接把它覆盖回 `x`，逐层往下传。

#### 3.3 最终规范化与返回

```python
        return self.norm(x)
```

这一行就是把刚才定义的最终规范化作用在最后一层的结果上。

如果你不想做最终规范化，只想到第六层之后直接往后传，那只需要做一件事：把上面循环得到的 `x` 直接 `return`。这个不用纠结，跟搭积木一样，多一个少一个看你自己的需要。

### 4 编码器的测试与数据流转

写完类就要测。测试函数叫 `use_encoder`，注意它跟 `Encoder` 类之间是**并列关系**，不要写到类里面去（写到类里就得带 `self` 了）。

#### 4.1 测试步骤清单

测试函数的八个步骤，先列出来，再逐个落实：

1. 获取数据：词向量 + 位置编码；
2. 构建单个编码器层作为基础单元；
3. 实例化编码器并堆叠若干个编码器层；
4. 构建掩码张量；
5. 执行编码过程；
6. 打印结果；
7. （可选）观察输入与输出的变化；
8. 返回编码器处理后的结果。

#### 4.2 获取输入数据与构建基础单元

第一步的数据就是编码器之前的那份数据——词向量加位置编码，写法跟前面完全一样，直接调 `use_positional_encoding` 拿。

第二步是搭一个编码器层，这一段的代码跟 `use_encoder_layer` 几乎一样，你可以直接从那边整块挪过来，也可以照着注释重新写：

```python
def use_encoder():
    # 1. 获取数据
    x = use_positional_encoding()

    # 2. 构建单个编码器层作为基础单元
    # 2.1 创建多头注意力层对象
    multi_attn = MultiHeadedAttention(512, 8)
    # 2.2 创建前馈全连接层对象
    feed_forward = FeedForward(512, 2048)
    # 2.3 组合成编码器层对象
    encoder_layer = EncoderLayer(512, multi_attn, feed_forward)

    # 3. 实例化编码器并堆叠编码器层
    encoder = Encoder(encoder_layer, 3)

    # 4. 构建掩码张量
    mask = torch.zeros(8, 4, 4)

    # 5. 执行编码过程
    encoder_output = encoder(x, mask)

    # 6. 打印结果
    print("编码器的输出形状：", encoder_output.shape)
```

两个参数顺手记一下：多头注意力的 `(512, 8)` 是词向量维度与头数；前馈全连接层的 `(512, 2048)` 是先升维到 2048——**第一个是 512，第二个是 2048**，这就是升维。

> **提示**：参数记不熟的时候，把光标悬浮在类名上，或者按住 Ctrl 点击进去看底层源码，参数列表会直接列出来。很多时候照着提示传参都是 OK 的。用 `EncoderLayer` 举例，它要的第一个参数是 `d_model`（512），第二个是 `self_attn`（这里的多头注意力对象），第三个是 `feed_forward`（前馈全连接对象）。

#### 4.3 堆叠三个编码器层

```python
    encoder = Encoder(encoder_layer, 3)
```

这里有个必栽的坑，我先讲明白。看到"克隆"两个字，很多同学会顺手在前面再写一个 `clones`：

```python
    # 错误写法：重复克隆
    encoder = Encoder(clones(encoder_layer, 3), 3)
```

不行。`Encoder` 的 `__init__` 里面已经做过克隆了，你只管把一个编码器层对象给它、后面给个数字，它自己会克隆那些份。多克隆一次，等于把 `clones` 的结果当成一个 `layer` 再往里塞，语义全乱了。

那为什么这里堆叠的是 3 个而不是 6 个？**论文默认是 6 个**，我堆三个纯粹是运算量小，跑得快。你写 6 也行，随你。

#### 4.4 掩码与执行编码

掩码矩阵自己写一行就够了：

```python
    mask = torch.zeros(8, 4, 4)
    encoder_output = encoder(x, mask)
```

> **易错点**：这里传的是 $(8, 4, 4)$，不是 $(2, 4, 4)$。八个头的掩码要把头这一维展开，所以第一维是 8 而不是 batch 的 2。

#### 4.5 观察输入与输出的变化（可选）

跑起来之后，控制台会打印编码器输出形状 $(2, 4, 512)$，肯定没问题。这里我想再具体一点，加一段可选的动作——观察输入和输出结果：

```python
    # 7.（可选）观察输入与输出结果
    print(f"输入示例：\n{x[0, 0, :5]}")
    print(f"输出示例：\n{encoder_output[0, 0, :5]}")
```

`x[0, 0, :5]` 的意思是：第一个句子的第一个单词的前五个词向量的值。

整批数据的形状是"两个句子、每句四个词、每个词 512 维"，这里取的是第一个句子第一个词的前 5 维。

这段对比的意义在哪？输入是蓝色的那个点，输出是绿色的那个点。中间确实经历了一堆事——每步具体加了哪些动作、底层怎么实现的，我们不清楚，但你能看到的是：从蓝色到绿色，内容确实发生了变化，说明它在你给的数据基础上真的做了处理。

> **注意**：这两行是可选的，加不加都行。原因是——说实话，这些数我自己也看不懂。你能确认的只是"数不一样了"，具体的运算动作看不出来，流程我们是知道的。

#### 4.6 返回结果

```python
    # 8. 返回编码器处理后的结果，作为解码器的输入，继续往后执行
    return encoder_output
```

那有返回，为什么下面不接收它？因为这一段还没有接解码器，我打出来就行。等后面写解码器的时候，你就得去接收这个函数的执行结果了。

到这一步，数据已经从蓝色的点跑到了绿色的点。再往下写，就该写解码器的那一套动作了。

### 5 数据在层级之间的形状流转

把这一讲的数据流和形状用一张图收拢：

```text
输入数据
  x = 词嵌入 + 位置编码              形状 (2, 4, 512)
        │
        ▼
  Encoder(layer, n)  ──克隆──►  n 个 EncoderLayer
        │
        ├─ 第 1 个编码器层   layer(x, mask) ──► (2, 4, 512)
        ├─ 第 2 个编码器层   layer(x, mask) ──► (2, 4, 512)
        ├─ ...                               （形状一路不变）
        └─ 第 n 个编码器层   layer(x, mask) ──► (2, 4, 512)
        │
        ▼
  最终 LayerNorm(layer.d_model = 512)
        │
        ▼
  encoder_output                      形状 (2, 4, 512)  ──► 交给解码器

掩码：mask 形状 (8, 4, 4)  =  头数 × 序列长度 × 序列长度
```

读图要点：整条链路上张量形状始终是 $(2, 4, 512)$ 不变，编码器只改变内容、不改变形状——这也是为什么它能一层层往上传。唯一在形状上显眼的是掩码 $(8, 4, 4)$，把头维展开了。

### 6 层级关系的收束与子层连接的设计思想

#### 6.1 从输入到编码器：四个层级

这一节最后把这几个层次串一遍。从我给的数据一路往上：

```text
输入  ──►  组件  ──►  子层  ──►  编码器层  ──►  编码器
 1          2          3            4
```

看明白这个层级，下一讲就顺了。**接下来该写解码器了，那么解码器从哪开始写起？直接从解码器层写起。** 因为组件和子层是共通的，直接拿过来用就行，不需要再从头写一遍。这也是"越往后写越简单"的真正原因。

#### 6.2 子层连接结构的概念与思想

回到子层这个概念。子层分两个：多头注意力，以及前馈全连接（我一直叫它前馈全连接层）。

> **结论**：子层连接结构的本质是——**你传进来什么子层对象，它就是什么子层**。我搭建的其实只是一个结构：你给我一个子层对象，我在它后面接上残差连接和规范化层处理。

这个设计思想很值钱。正因为子层连接只描述"结构"、不描述"具体是哪个子层"，编码器层和解码器层才能复用同一套 `SublayerConnection`：解码器层有三个子层，就克隆三份结构，各塞一个不同的子层对象进去。

#### 6.3 三层结构的作用

把三个层级的作用连起来看：

- 编码器层：做**一次**特征抽取；
- 编码器：做 **n 次**特征抽取；
- 这么做的目的，是让结果更精准，让模型能更好地理解词义。

一句话记住这个递进：**编码器层是一次特征抽取，编码器是 n 次特征抽取。**

## 第 9 章：Day09-09.解码器层_代码实现(掌握)
> 对应分集：P134 | 原始标题：《Day09-09.解码器层_代码实现(掌握)》

解码器部分的实现比编码器简单得多，因为该玩的组件在前面基本都玩得差不多了。唯一需要重新想清楚的一件事是：解码器层有三个子层，而不是两个——多出来的那一个，恰恰是解码器区别于编码器的关键。

### 1 解码器层的结构定位

#### 1.1 本讲要建的东西与前置知识

先明确这一讲要拿下的两点：说得清解码器层的作用，说得清解码器层的实现流程；顺带把编码器部分的作用与实现流程也复述一遍——因为解码器要吃它的输出。

对照整体架构图，现在要写的是右边那一块：解码器。看进去就会发现，解码器层内部是由**三个子层**组成的，所以我们的路线是先把解码器层写出来，再把解码器构建起来。

#### 1.2 导入编码器的原因

新开一个脚本文件：

```text
DM06_decoder_layer.py     # 演示：解码器层的代码实现
```

导包这一步只导一个东西：

```python
from DM05 import *
```

`DM05` 就是编码器所在的脚本。**为什么解码器要导编码器？** 因为解码器要拿到编码器的输出结果——图里那条从编码器送过来的线，解码器的第二个子层就靠它工作。这条依赖关系决定了：解码器层必须能访问编码器，否则第二个子层没有 `K`、`V` 可用。

### 2 解码器层的三个子层

#### 2.1 三个子层的清单

先把三个子层写成文字，这是整个解码器层的骨架。

> **定义**：解码器层由三个子层组成。

- **子层一**：`masked_multi_head_attn`——掩码多头注意力机制层，后面接残差连接加规范化层；
- **子层二**：`multi_head_attn`——多头注意力机制层（注意，这里没有 `masked`），同样接残差连接加规范化层；
- **子层三**：`feed_forward`——前向传播层，也就是我们一直在说的前馈全连接层。

> **提示**：子层一和子层二长得几乎一样，区别只在一个词上——`masked`。少了这个 `masked`，注意力就不做遮挡，能看的范围完全不同。这是本讲最容易搞混的地方，记住一句话：**看自己用什么，要 `masked`；看编码器用什么，不用 `masked`。**

#### 2.2 类定义与前向传播骨架

```python
class DecoderLayer(nn.Module):
    def __init__(self, d_model, self_attn, src_attn, feed_forward, dropout=0.1):
        super().__init__()
```

第一个动作照旧是初始化函数，第二个动作是解码器层的前向传播。先把要传进来的参数逐个讲清楚：

- `d_model`：词向量维度；
- `self_attn`：注意力机制，处理**解码器输入序列内部关系**，也就是处理解码器自己的输入，对应掩码多头注意力；
- `src_attn`：另一路注意力机制，处理**源序列**——"源"是源头的源，三点水那个。它对应的就是编码器与解码器之间的那路注意力；
- `feed_forward`：前向传播层，作用是强化特征；
- `dropout`：随机失活，这里取失活概率 0.1。

**`self` 和 `src` 到底谁对应图里哪一块？** 这是必须钉死的一件事：

```text
                  ┌──────────────────────────────────┐
                  │  源序列侧（编码器）              │
                  │  encoder_output                  │
                  └───────────────┬──────────────────┘
                                  │  K, V
                                  ▼
  解码器输入 ──► 子层一（掩码多头自注意力）
                        │
                        ▼
                  子层二（多头注意力，跨编码器）  ◄── 用 src_attn
                        │
                        ▼
                  子层三（前馈全连接）
                        │
                        ▼
                   解码器层输出
```

读图要点：`self_attn` 玩的是下面这一套——解码器的 `outputs`、对应的 `embedding` 和 `positional encoding`；`src_attn` 玩的是上面这一套——从编码器过来的那一路。所以**一个 `self`、一个 `src`，解码器层需要两个注意力对象**，再加一个前馈全连接对象，一共三个。

#### 2.3 属性定义与三个子层结构

```python
        self.d_model = d_model
        self.self_attn = self_attn
        self.src_attn = src_attn
        self.feed_forward = feed_forward
        self.sublayer = clones(SublayerConnection(d_model, dropout), 3)
```

先初始化父类成员，再定义属性，最后定义**三个**子层连接结构——注意这里是 3，不是 2。数字和子层数量必须对上，写 2 的话第三个子层就没地方放了。

### 3 解码器层的前向传播

#### 3.1 四个参数的含义

```python
    def forward(self, x, encoder_output, source_mask, target_mask):
```

- `x`：解码器的输入序列，也就是图里那一路"法语"的输入，同样的词嵌入加位置编码；
- `encoder_output`：编码器的输出序列，即源序列经过编码之后的结果；
- `source_mask`：源序列的填充掩码，用在**编码器-解码器注意力**里；
- `target_mask`：目标序列的掩码，用在**自注意力**里。

> **易错点**：两个 mask 的作用对象不要串。`source_mask` 是给第二个子层（跨编码器那路注意力）用的，`target_mask` 是给第一个子层（解码器自己的自注意力）用的。串了之后跑不报错，但语义全错。

#### 3.2 依次经过三个子层

三个子层的调用写法完全对称，靠子层连接的**下标**区分：

```python
        x = self.sublayer[0](x, lambda x: self.self_attn(x, x, x, target_mask))
        x = self.sublayer[1](x, lambda x: self.src_attn(x, encoder_output, encoder_output, source_mask))
        x = self.sublayer[2](x, lambda x: self.feed_forward(x))
        return x
```

逐行看：

- **第一个子层**：多头自注意力机制层，走 `self.sublayer[0]`。注意力对象是 `self_attn`，因为它处理的是解码器自己下面的输入。按住 Ctrl 点进 `self_attn` 的实现，能看到它要四个参数：`q, k, v` 再加一个掩码——这里传进去的是 `x, x, x, target_mask`，自己查自己，所以叫自注意力。
- **第二个子层**：多头注意力机制层，没有"自"了，走 `self.sublayer[1]`。它是编码器-解码器那路注意力，调 `src_attn`，传参是 `x, encoder_output, encoder_output, source_mask`——注意 `K`、`V` 都来自 `encoder_output`，只有 `Q` 是解码器当前的 `x`。
- **第三个子层**：走 `self.sublayer[2]`，调 `feed_forward`，只把 `x` 传进去。

**为什么第一、二个子层的传参差这么多？** 因为它们的任务不同。第一个子层让解码器看清自己已经生成的内容，所以 `Q`、`K`、`V` 全来自 `x`；第二个子层让解码器去查询编码器给出的源序列信息，所以 `Q` 来自解码器、`K` 和 `V` 来自编码器。

写到这里，解码器层就完成了。下一讲再写测试——测试的部分稍微多一点。

### 4 三处必须记牢的对应关系

| 位置 | 子层名称 | 注意力对象 | 传参 | 掩码 |
| --- | --- | --- | --- | --- |
| 子层一 | 掩码多头自注意力机制层 | `self_attn` | `x, x, x` | `target_mask` |
| 子层二 | 多头注意力机制层（编码器-解码器） | `src_attn` | `x, encoder_output, encoder_output` | `source_mask` |
| 子层三 | 前馈全连接层 | `feed_forward` | `x` | 无 |

表里最值得盯的一列是传参：**只有第二个子层是"混合"的——`Q` 来自一边、`K`/`V` 来自另一边**，另外两个子层都是单一来源。看清这一点，解码器层就再也不会写错。

> **结论**：解码器层由三个子层组成，`self.sublayer` 克隆三份子层连接结构与之逐一对应；三个子层里唯一带跨序列信息交换的是第二个子层，它把 `encoder_output` 当作 `K`、`V` 接进来——这就是解码器层必须依赖编码器的原因。

## 第 10 章：Day09-10.解码器层_代码测试(理解)
> 对应分集：P135 | 原始标题：《Day09-10.解码器层_代码测试(理解)》

解码器层写完了，接下来跑通它。解码器层的测试比前面几讲都长，因为它要把整条数据链一次串起来：解码器自己的输入、位置编码、三个子层对象、掩码，还有从编码器那边取回来的输出——**一环套一环**，任何一环缺了，跑起来就报参数不匹配。

### 1 测试函数的定位

#### 1.1 并列的函数与缩进

测试函数叫 `use_decoder_layer`。

```python
def use_decoder_layer():
    ...
```

这里有一个必须当场纠正的位置问题：`use_decoder_layer` 和 `DecoderLayer` 类之间是**并列关系**，它应该和类平级，而不是缩进在类里面。刚才写前向传播时它缩在类内部，那只是写代码时的顺手位置；真正落到测试上，它得往前顶格，跟类对齐。

> **易错点**：因为 `use_decoder_layer` 不是类的方法，调用时**不能传 `self`**，直接 `use_decoder_layer()`。写了 `self` 就会报参数数量不对。判断标准很简单：这段代码写在类里面才加 `self`，跟类并列就不加。

#### 1.2 测试的十步流程

先列清单，再一步步行进：

1. 定义变量记录解码器的输入 `q`；
2. 构造 `y`，走词嵌入层；
3. 对 `y` 做位置编码，得到解码器侧的输入；
4. 创建多头注意力层；
5. 创建前馈全连接层；
6. 获取编码器的输出结果；

### 2 解码器输入的构造

#### 2.1 一个 LongTensor 与两份拷贝

第一步先定义变量记录解码器的输入，这个输入就是 `q`——你可以把它理解成解码器接下来要生成的那个内容的起点。

```python
    y = torch.LongTensor([[1, 2, 3, 4], [10, 11, 12, 13]])
```

这个张量的含义要看懂：**两个句子，每个句子四个词**。第二个句子加 10，是为了让两个句子的词索引完全不同，方便检查。类型上转成 `Long` 类型，因为词嵌入层要的是整数索引。

#### 2.2 词嵌入层与位置编码

```python
    embedding = nn.Embedding(vocab_size, d_model)
    y = embedding(y)
    my_position = PositionalEncoding(512, 0.1)
    position_y = my_position(y)
```

词嵌入层**不需要重新写一遍**，跟前面用的是同一个类，直接实例化来调就行。它要两个参数：`vocab_size` 是词表大小，另一个是词嵌入维度。

拿到词向量之后，把 `y` 传进位置编码。注意两个变量的区分——这一步容易写混：

- `my_position`：位置编码**对象**；
- `position_y`：把 `y` 丢进位置编码之后**得到的结果**。

真正被处理的是 `position_y`，形状是 $(2, 4, 512)$。到这里，解码器侧的输入就准备好了，数据已经走到了图里那一小块绿色区域。

### 3 三个子层对象的准备

#### 3.1 多头注意力层与深拷贝

```python
    multi_attn = MultiHeadedAttention(512, 8)
    self_attn = copy.deepcopy(multi_attn)
    src_attn = copy.deepcopy(multi_attn)
    ff = FeedForward(512, 2048)
```

先创建多头注意力层，参数是 $(512, 8)$，也就是词向量维度与头数。**但这里要创建的不是一个，而是需要在两份位置上各有一个。** 于是把刚建好的对象深拷贝两份，分别叫 `self_attn` 和 `src_attn`。

**为什么非得深拷贝？** 一句话：**深拷贝确保参数不会共享，各玩各的。** 这两个注意力层虽然结构完全一样，但一个负责解码器自己的内部关系，一个负责跨编码器的源序列关系，它们的权重必须独立训练、独立更新，不能指向同一块内存。

```python
import copy
import math
```

`copy` 这个包前面没导过，要补上。顺便把 `math` 也一起导了——一会儿如果有数学运算就直接用。

`self` 和 `src` 谁对应谁，再确认一次：`self` 是解码器自己那一路（对应图里下面那一块），`src` 是编码器过来的那一路（对应上面那一块）。虽然这俩对象此刻内容一致，**但一会儿执行的时候，它俩传进去的参数不一样**——这才是真正区分它们的地方。

#### 3.2 前馈全连接层

```python
    ff = FeedForward(512, 2048)
```

第二个参数 2048 是把 512 维升到 2048 维。三个对象（两路注意力 + 一个前馈全连接）凑齐，往三个子层连接结构里一扔，解码器层的骨架就搭完了。

### 4 编码器输出的接入

```python
    encoder_output = use_encoder()
```

第六个动作是获取编码器的输出结果。按住 Ctrl 点进 `use_encoder`，那就是上一个任务里"测试编码器对象"写下的函数——**最后一行返回了编码器的输出**。所以这里不是重新算一遍编码器，而是直接把那个函数的结果取回来用。

**这就是"一环套一环"的具体含义**：编码器测试函数当初写上 `return` 的那一行，作用就是让解码器这一讲能一行拿到整条链路处理好的数据，而不必把编码器的一大堆代码在这里再抄一遍。

```text
y ──► Embedding ──► PositionalEncoding ──► position_y  (2, 4, 512) ┐
                                                                    ├─► DecoderLayer 前向
源序列 ──► use_encoder() ──► encoder_output          (2, 4, 512) ─┘
                    │
                    └─ K, V 供第二个子层（src_attn）使用

掩码：source_mask (8, 4, 4)  ──► 第二个子层
      target_mask (8, 4, 4)  ──► 第一个子层
```

读图要点：解码器的两路输入在 `DecoderLayer.forward` 里汇合——`position_y` 当查询，`encoder_output` 当键和值；两个掩码各自送往对应的子层，互不交叉。

### 5 掩码的定义

```python
    source_mask = torch.zeros(8, 4, 4)
    target_mask = torch.zeros(8, 4, 4)
```

第七个动作是定义掩码。这两个掩码的**作用不同，要根据真正的业务来判断**——真实开发中你得按自己的尺寸来定哪些位置该掩、哪些不该掩，哪些填 0、哪些填 1，取决于你的填充策略和自注意力的可见范围。这里只是随手写一组示例值，两个都取 $(8, 4, 4)$。

> **注意**：形状里的 8 是头数，两个 4 分别是查询序列长度与被查询序列长度。别照着 batch 的 2 去写第一维。

### 6 实例化解码器层与执行

#### 6.1 按参数提示逐个传参

第八个动作是实例化解码器层对象。把光标停在 `DecoderLayer(` 后面等两秒，编辑器会把这个类需要的参数提示出来——**这些参数就是你自己写 `DecoderLayer.__init__` 时定义的那几个**，照着传就是：

| --- | --- | --- | --- |
| 1 | `d_model` | `512` | 词向量维度 |
| 2 | `self_attn` | `self_attn` | 掩码多头注意力对象，处理解码器输入序列内部关系 |
| 3 | `src_attn` | `src_attn` | 跨编码器的注意力对象 |

对着参数提示逐个填，其实很多时候照着传都是 OK 的。往下拉一眼就能看出：**现在拼出来的这个对象，跟架构图里那一块是一模一样的**。

#### 6.2 按前向传播的形参传数据

```python

```

第九个动作是把数据传给解码器层、取回输出。谁传谁不传，看 `DecoderLayer.forward` 的形参列表就能确定，对应关系是：

## 第 11 章：Day09-11.解码器_代码实现及测试(掌握)
> 对应分集：P136 | 原始标题：《Day09-11.解码器_代码实现及测试(掌握)》

编码器跑通之后，摆在我们面前的解码器其实只剩下一件事：把已经验证过的零件照原样再拼一遍。解码器层写完了，解码器就是把它复制 6 份再补一层规范化层，寥寥几行，快得让人怀疑是不是漏了什么。真正值得停下来想的是后面那个问题——解码器层之间自己连着好办，可它中间那个注意力子层要用的变量，是编码器送过来的，这个变量在 6 层之间到底怎么传？把这一条理清楚，解码器才算真的懂了。

### 1 解码器整体结构：6 层堆叠加一层规范化

先明确论文里的默认配置：编码器由 6 个编码器层组成，解码器同样由 6 个解码器层组成，最后再各加一层规范化层（Layer Normalization），让输出的数值分布更稳定。所以解码器的类结构和编码器是一一对应的，只是把「层」换成了 `DecoderLayer`。

新建 `demo07_decoder`，导包只写一行就够：

```python
from demo06 import *
```

接下来是 TODO 1，定义解码器：用 `clones` 把多个解码器层复制堆叠，最后接一层 `LayerNorm`。

```python
class Decoder(nn.Module):
    def __init__(self, layer, N):
        # 初始化参数：layer 是单个解码器层，N 是解码器层的堆叠数量
        super(Decoder, self).__init__()
        self.layers = clones(layer, N)
        self.norm = LayerNorm(layer.size)
```

`clones(layer, N)` 的写法在编码器里已经用过，含义就是把同一个解码器层深拷贝 N 份，避免 6 层共享同一组参数。`layer.size` 取的是单个解码器层的特征维度，也就是词嵌入维度 `d_model = 512`，规范化层要按这个维度来做归一化。

解码器层之间参数不共享，这是硬要求：6 层各自学习各自的一组权重，堆叠才有多层的意义。而 `my_embed = 1000` 那个 1000 是词表大小，和这里的 512 是两回事，容易在参数传递时看串。

### 2 前向传播的入参：从计算图反推需要什么

前向传播的函数签名是这一段最容易写漏的地方。`forward(self, x)` 只是开始，因为解码器的输入不止一个。

顺着图走一遍：`x` 先经过词嵌入、位置编码，然后一路走到解码器层；而解码器层里的第二个注意力子层，还要额外拿到编码器的输出。所以除了 `x`，必须有 `encoder_output`。再加上两个注意力子层都可能要用掩码，于是两个掩码矩阵也是入参。

```python
def forward(self, x, encoder_output, src_mask, tgt_mask):
    # x：解码器输入序列（词嵌入 + 位置编码）
    # encoder_output：编码器输出序列
    # src_mask：源序列填充掩码，用于编码器-解码器注意力
    # tgt_mask：目标序列填充掩码，用于自注意力
    for layer in self.layers:
        x = layer(x, encoder_output, src_mask, tgt_mask)
    return self.norm(x)
```

四个入参各自的角色要对上号，这里最容易搞混的是两个掩码的归属：

| 入参 | 含义 | 交给哪个子层 |
| --- | --- | --- |
| `x` | 解码器输入序列（词嵌入 + 位置编码） | 掩码多头自注意力 |
| `encoder_output` | 编码器输出序列 | 多头注意力（提供 K、V） |
| `src_mask` | 源序列的填充掩码 | 编码器-解码器注意力 |
| `tgt_mask` | 目标序列的填充掩码 | 自注意力 |

循环体里 `x = layer(x, encoder_output, src_mask, tgt_mask)` 表示第 i 层的输出直接成为第 i+1 层的输入，而 `encoder_output` 与两个掩码在每一层都是同一份。循环跑完 6 次之后，`return self.norm(x)` 把 6 层处理的结果做一次统一标准化再返回——不写这一句，扔出去的就是第 6 层未经规范化的原始输出，数值尺度会直接影响后面的输出部分。

### 3 解码器测试：从输入到输出走一遍

测试代码和之前测解码器层的代码几乎一模一样，可以直接复制过来改。TODO 2 的目标是：测试解码器从输入到输出走一遍完整流程，并验证每一层的维度是否正常。

第一步先定义解码器的输入。这里要认出哪个是 Q——解码器侧的输入位置就是 Q 所在的位置。

```python
import torch

# 1. 定义解码器输入
x = torch.LongTensor([[1, 2, 3, 4], [5, 6, 7, 8]])  # 2 个句子，每句 4 个词

# 2. 词嵌入
my_embed = Embeddings(1000, 512)
embed_x = my_embed(x)

# 3. 位置编码
my_pe = PositionalEncoding(512, 0.1)
pe_x = my_pe(embed_x)

# 4. 多头注意力：建两个，因为解码器层里有两个注意力子层
my_mha = MultiHeadedAttention(8, 512)
my_mha2 = MultiHeadedAttention(8, 512)

# 5. 前馈全连接
my_ff = PositionwiseFeedForward(512, 2048, 0.1)

# 6. 编码器的输出
use_encoder = Encoder(my_encoder_layer, 6)
encoder_output = use_encoder(input_x, src_mask)

# 7. 两个掩码矩阵
src_mask = torch.zeros(2, 1, 1, 4)
tgt_mask = torch.ones(2, 4, 4)

# 8. 实例化解码器层
my_decoder_layer = DecoderLayer(512, my_mha, my_mha2, my_ff, 0.1)
```

维度这一条线要一路盯住：`x` 是 `2 × 4`，经过词嵌入的 `(1000, 512)` 之后变成 `2 × 4 × 512`；位置编码给的是 `512` 维、失活率 `0.1`，处理完仍然是 `2 × 4 × 512`。左右两侧的输入——不管是编码器侧的 `input` 还是解码器侧的 `y`——拿到的形状都一样，都是 `2 × 4 × 512`。多头注意力建两个，是因为解码器层里有两个注意力子层：下面那个是自注意力，上面那个要接编码器的输出。

关键的一处变形在第九步。之前测的是解码器层，拿到 `my_decoder_layer` 就直接处理了；现在要测的是解码器，所以必须先把解码器层堆叠成解码器：

```python
# 9. 堆叠 6 层解码器层，组成解码器
my_decoder = Decoder(my_decoder_layer, 6)

# 10. 跑一遍解码流程：输入进 6 层解码器层，再到输出
result = my_decoder(pe_x, encoder_output, src_mask, tgt_mask)

print("解码器的形状:", result.shape)
print("解码器对象:", my_decoder)
```

第十一步是把 `my_decoder_layer` 换成 `my_decoder`，其余参数不动——内部会自动过 6 层。跑起来看到的结果是：词嵌入、位置编码、编码器输出都是 `2 × 4 × 512`，解码器输出形状 `2 × 4 × 512`，另外还会打印出解码器对象。

### 4 打印出来的解码器对象怎么读

控制台里那坨对象看着乱，其实逐个字段对图就能读懂：

```text
Decoder(
  (layers): ModuleList(
    (0): DecoderLayer(
      (self_attn): MultiHeadedAttention(...)   <- 掩码多头自注意力，用 tgt_mask
      (src_attn): MultiHeadedAttention(...)    <- 多头注意力，用 src_mask，吃 encoder_output
      (feed_forward): PositionwiseFeedForward(...)
      (sublayer): ModuleList(                  <- 3 个子层连接
        (0): SublayerConnection(...)
        (1): SublayerConnection(...)
        (2): SublayerConnection(...)
      )
    )
    ...
    (5): DecoderLayer(...)
  )
  (norm): LayerNorm(...)
)
```

- `self_attn` 对的是解码器层最下面那个自注意力子层；
- `src_attn` 对的是接编码器输出的那个注意力子层，名字里的 `src` 提示它跟源序列有关；
- `feed_forward` 是中间的前馈全连接；
- `layers` 里 `0` 到 `5` 一共 6 个 `DecoderLayer`，这就是论文默认的堆叠数量；
- `sublayer` 里是 3 个 `SublayerConnection`，注意这个 3 不是「6 层」的意思，而是说一个解码器层由 3 个子层组成：自注意力、编码器-解码器注意力、前馈全连接，每个子层外面都套了一层残差加规范化的连接。

> **易错点**：`sublayer` 里的 `(0)(1)(2)` 是子层序号，不是层数序号。把它当成「只有 3 层」是常见的误读，6 层的含义只体现在 `layers` 这个 `ModuleList` 的长度上。

最后把 `main` 里的函数名改过来：复制过来的测试函数原本叫 `use_decoder_layer`，测的既然是解码器，就要把后面的 `layer` 删掉，改成 `use_decoder`。名字不改，代码跑得通但语义全错。

### 5 结构关系的复盘：编码器与解码器的依赖差异

写到这里，编码器和解码器两边的代码都能读懂了。顺带说一句思路层面的判断：如果编码器已经写完，想极快地做出解码器，把编码器的代码整份复制过来、改掉差别的地方就行。这套代码里真正在做核心工作的是 `demo02`——各个组件的功能都在那里模拟实现；除它之外，剩下的工作本质上都是组合与拼接。

回到结构本身，先复习编码器层怎么走：

```text
编码器层（EncoderLayer）
  输入 x
   |
   +--> [ 子层1: 多头自注意力 ] --残差+规范化--> x
   |
   +--> [ 子层2: 前馈全连接   ] --残差+规范化--> 输出
```

编码器层之间就是顺序连接：上一个编码器层的输出接到下一个的输入，一直走 6 层。编码器除了词嵌入和位置编码之外不依赖任何外部输入——数据第一次传进来以后，就在 6 个编码器层里一路往下走。

解码器层内部也是这个模式，同样是顺序连接、逐层往后走。差异只有一处：解码器层中间那个注意力子层要用到编码器的输出。

### 6 编码器输出在解码器层间的共享

真正值得想清楚的是：这个由编码器送来的变量，在 6 个解码器层之间是怎么处理的？

答案是多层共享同一份。编码器最后一层的输出，同时喂给每一个解码器层的 `src_attn` 子层。

```text
                encoder_output（编码器最后一层的输出）
                        |
        +---------------+---------------+
        |               |               |
        v               v               v
  DecoderLayer 0  DecoderLayer 1  ...  DecoderLayer 5
        |               |               |
        +---- 顺序连接 --+---- 顺序连接 --+--> 输出
```

读图说明：解码器层之间是普通的顺序连接，上一层输出接下一层输入；而编码器输出是一条横向的共享线，被每一个解码器层各取用一次，不是逐层往后传递的。

> **结论**：多个解码器层共享编码器的输出结果。数据从编码器传过来一次，然后被所有解码器层共同使用。

对照编码器-解码器结构图里那个「中间语义张量 C」，它就是编码器的输出结果。图上三个子层的构成与刚才打印出来的解码器对象完全一致，解码器层之间互相连接这一点也没变；往上对接输出部分，往左对接的就是这份编码器输出。

### 7 三个注意力的 Q、K、V 来源与分工

把共享这件事放到注意力的公式里，会得到一个很干净的结论。缩放点积注意力需要 Q、K、V 三份张量，在解码器层里：

- 下方那个子层是自注意力，Q、K、V 都来自解码器侧的输入（也就是目标序列经过词嵌入与位置编码后的结果），三者是同一份数据；
- 上方那个子层里，K 和 V 来自编码器的输出，两者同样是同一份数据，而 Q 来自解码器侧。

$$K = V 
eq Q$$

Q 是什么？查询张量，说白了就是当前要生成哪一个词。要生成谁，谁就是 Q；解码器就是基于这个输入在不断地往前做预测。

拿英译法举例：输入 7 个英语单词，翻译出来是 9 个法语单词。如果现在要生成第 3 个法语单词，那 Q 代表的就是这第 3 个法语单词。

三个注意力看上去名字差不多，功能却完全不同：

| 位置 | 名称 | Q / K / V 来源 | 功能 |
| --- | --- | --- | --- |
| 解码器层下 | 掩码多头注意力（也叫多头自注意力） | Q、K、V 都来自解码器侧 | 屏蔽未来词，防止偷看 |
| 解码器层上 | 多头注意力 | K、V 来自编码器输出，Q 来自解码器侧 | 融合编码器与解码器的结果并算权重 |
| 编码器层内 | 多头自注意力 | Q、K、V 都来自编码器侧输入 | 找词与词之间的关联与概率分布 |

回到刚才那个例子：要生成第 3 个法语单词，掩码做的是什么？掩码矩阵大致是「1 1 0 0 …」这种形状——前两个法语单词允许你看，第 3 个以及后面的都不让看。这就是掩码注意力干的活：藏词，防止偷看未来的词，所以它才叫掩码。

> **提示**：命名上有两种习惯容易混。有人把解码器层下方那个叫「掩码多头注意力」，上方那个叫「多头注意力」；也有人把下方的叫「多头自注意力」，上方的叫「多头注意力」。名字怎么叫不重要，判断依据只有一条——看 Q、K、V 是不是同一份数据：三者同源就是自注意力，K、V 同源而 Q 另出就是编码器-解码器注意力。

上方那个注意力层算的是权重，看的是「我生成第 3 个词时，对这 7 个英语单词里谁的依赖最高」。而它的 Q、K、V 也不是凭空来的：K、V 来自编码器的输出，Q 来自解码器侧经过位置编码处理后的内容。

> **易错点**：解码器层里两个注意力的 Q 都来自解码器侧，但只有下面那个是自注意力。看到「注意力」三个字就默认 Q = K = V，是这一段最典型的错。

这也是为什么布置手绘 Transformer 结构图的作业有意义——把每一根箭头画一遍，才会注意到编码器输出那条线是横向拉出去共享的，而不是顺着解码器层往下流的。多个解码器层之间顺序连接，但它们共用编码器的输出，换言之，共享。

## 第 12 章：Day09-12.输出部分_代码实现(掌握)
> 对应分集：P137 | 原始标题：《Day09-12.输出部分_代码实现(掌握)》

组件层、编码器层、编码器、解码器层、解码器，一路拼到现在，只剩下最后一块积木——输出部分。这一块简单到有点不像话：一个线性层加一个激活函数，就这两下。可它偏偏是整张图里最实用的一个部件，因为它决定了模型到底「说出」哪个词。

### 1 输出部分的位置与两个动作

输出部分接在解码器的输出后面：先做一次线性层处理，再过一次激活函数，就结束了。两件事各自的任务很明确——线性层负责把上述结果做指定维度的变换，激活函数负责把分数转成概率。

先问一个该问的问题：解码器输出来的结果是什么形状？

答案是 `2 × 4 × 512`。解码器输出的张量是 2 个句子、每句 4 个词、每个词 512 维。那它经过线性层之后会变成什么？

不是 `2 × 4 × 512` 了，而是 `2 × 4 × 1000`。为什么是 1000？因为词表里一共 1000 个词。

这个 `2 × 4 × 1000` 的含义要读准：两个句子，每个句子 4 个词，每个词是这个词表中 1000 个词各自的概率——或者说得更拗口一点，每个词是词汇表中各个单词的概率分布。比如第一句话的第一个词，是这 1000 个里面哪一个？第一句话的第二个词，又是这 1000 个里面哪一个？输出部分做的就是这件事。

最后一步：把 1000 个概率里最高的那一个对应的词拿出来，作为预测结果。整个输出部分，到此结束。

```text
解码器输出 [2, 4, 512]
        |
        v
   Linear(512 -> 1000)
        |
        v
   log_softmax(dim=-1)
        |
        v
[2, 4, 1000]  两个句子 × 每句 4 个词 × 每个词对 1000 个词的（对数）概率
        |
        v
  取概率最高的词  -->  预测结果
```

读图说明：维度只在最后一步发生变化，句数和词数这两维自始至终不动，被替换掉的只有「512 维向量」这一维，它换成了「1000 个词的分布」。

### 2 参数设计：d_model 与 vocab_size

把这个变换写成线性层，两个参数就定下来了：

- `d_model`：词向量维度，例如 512；
- `vocab_size`：词汇表大小，也就是一共有多少个词，例如 1000。

也就是把一个 512 维的词向量映射成 1000 维的输出。数值上讲，这一步就是输入向量与形状为 `(1000, 512)` 的权重矩阵相乘、再加上 1000 维的偏置，得到 1000 个分数。

> **提示**：这里的 `d_model` 之所以写成 `d_model` 而不是写死 512，是因为线性层的输入维度必须跟着词嵌入维度走。词嵌入维度变了，输出部分不用改结构，只改参数。

### 3 为什么用 log_softmax

到激活这一步，写的是 `log_softmax`，不是 `softmax`。原因不在输出部分本身，而在后面算损失的时候——配合 `NLLLoss` 使用的就是对数概率。所以这里直接把分数转成对数概率分布。

`log_softmax` 做的事情，是把分数转成对数概率分布，也就是每个位置给出 $\log p$，而不是 $p$。

$$\text{log\_softmax}(z_i) = z_i - \log \sum_j \exp(z_j)$$

对数概率最要紧的性质一条：把它做指数运算就还原成普通概率，$e^{\log p} = p$。这一步在后面验证概率和的时候会直接用到。

### 4 Generator 类的实现

新建 `demo08_output`，导包同样只写一行，别的什么都不用导：

```python
from demo07 import *
```

TODO 1 的目标：把解码器的特征转成最终预测结果，也就是词汇表中每个词的概率。

```python
class Generator(nn.Module):
    def __init__(self, d_model, vocab_size):
        # d_model：词向量维度，例如 512
        # vocab_size：词汇表大小，例如 1000
        super(Generator, self).__init__()
        # 定义全连接层：把输入维度 512 转换成输出维度 1000
        self.project = nn.Linear(d_model, vocab_size)

    def forward(self, x):
        # 线性层处理阶段：2×4×512 -> 2×4×1000
        x = self.project(x)
        # 将分数转成对数概率分布，dim=-1 表示在最后一维上计算，确保概率和为 1
        return F.log_softmax(x, dim=-1)
```

`self.project` 这一行看着简单，参数别写反：`nn.Linear(d_model, vocab_size)`，先 512 后 1000，写反了维度对不上就会报错。

前向传播里的 `dim = -1` 要单独说清楚，因为它是初学者最容易含糊过去的参数。为什么是 `-1` 而不是别的数？

因为 `2 × 4 × 1000` 里，`2` 不能动，`4` 也不能动——这两个是句数和每句词数，是数据的组织方式；唯一要处理的是最后一维那个 1000，要基于它算出概率。所以 `dim = -1` 表示的是：对最后一维、也就是词汇表维度进行计算，把 1000 个分数归一化成概率，确保它们的和为 1。

### 5 导包的传递性

代码敲完只剩一个疑问：`F.log_softmax` 里的 `F` 是哪来的？明明没写 `import torch.nn.functional as F`。

顺着导包链往回找就明白了。`demo08` 导入的是 `demo07`，`demo07` 里同样没有这一句，但它导入了 `demo06`；`demo06` 没有，它导入了 `demo05`；再往上是 `demo04`、`demo03`，一直到最初的那个模块——`torch.nn.functional` 那句导入就写在最开始那一层里（`demo02` 或更前面）。于是整条链是这样的：

```text
demo02  里面写了 torch / torch.nn 相关的全部导包（含 functional as F）
   ^
demo03  from demo02 import *
   ^
demo04  from demo03 import *
   ^
demo05  from demo04 import *
   ^
demo06  from demo05 import *
   ^
demo07  from demo06 import *
   ^
demo08  from demo07 import *        <-- 这里直接用 F.log_softmax 也能用
```

读图说明：`from X import *` 会沿着链把上游模块里的可见名字一起带进来，所以最上游导入的那个 functional 模块在最下游依然可用。

> **结论**：导包具有传递性。`from demo02 import *` 之后，`demo02` 里导入的包以及它上游带进来的包，在后续所有模块里都能直接引用。

顺着这个性质，有个更省事的写法：把 `demo02` 到 `demo08` 里要用到的包，全部集中写进最前面的 `demo02`。往后每个模块只导前一个模块，里面那些包就随便用。这也是为什么在 `demo08` 里不写导包也能正常跑。

### 3 概率和验证：从对数概率到普通概率

#### 3.1 提取单个词的概率分布

#### 3.2 对数概率转成普通概率

第二个动作，把对数概率转成普通概率：


这一步用 `torch.exp` 就够了。为什么必须转？因为此时拿到的还是对数概率，直接求和肯定不是 1；只有做指数运算还原成普通概率，才谈得上「概率和为 1」这个验证。

打完这行，屏幕上会出现这一份分布里 1000 个词各自的概率，都是 `0.0000几几几` 这个量级。假设这 1000 个数里某一个最大，那个位置对应的词就是当前这个位置要预测的词。

要注意这份概率的归属：这 1000 个数是**第一个样本第一个词**的。整个输出里有几个词？`2 × 4 × 1000`，两个句子、每句 4 个词，一共 8 个词——所以这样的一份 1000 维分布，总共有 8 份。

#### 3.3 验证概率和为 1

第三个动作，把这份分布求和：

```python
# 5.3 验证概率和为 1
print(f"第一个词的概率和为: {torch.sum(probs)}")
```

跑出来是 `1.00000000`。后面那些位为什么不全准？因为单精度浮点算小数用的都是近似值，精度到某一位之后就不准了；如果只看前两位，它就是 1。

除了 `torch.sum(probs)`，还有另一种写法，直接调张量自己方法：

```python
print(f"第一个词的概率和为: {probs.sum()}")
```

两种写法结果一样。

> **易错点**：多跑几次会发现结果有时是 `1.0`，有时是 `0.99999`，有时是 `1.0000几几`。这不是代码写错了，也不是概率和真的不为 1。原因有两个：一是模型里有随机失活（Dropout），每次前向传播丢掉的神经元不同；二是每次运行的概率分布都是重新计算的，输入的数不同、随机性不同，结果就会有轻微变化。想要确认效果，得多跑几次，一次的结果说明不了问题。

### 4 概率分布的用途：取最大值作为预测结果

验证完之后，这套东西怎么用就很清楚了：把词在输出部分转成 1000 个词的概率，然后从这份概率里挑出最大的那个词，它就是要生成的结果。

再往深一层看，这里的「预测结果」随任务而变。假设输入是两个英语句子、每句 4 个词：

- 如果输入和输出是两种不同的语言——左边英语、右边法语——做的是**翻译**。法语句子是已知的，模型基于它一直预测下去。
- 如果输入和输出是同一种语言——左边两个英语句子，`output` 这边也是两个英语句子——做的是**生成**。

判断的依据就在注意力上。我们一直在用的这两个注意力，都是自注意力，也就是 $Q = K = V$，三者同为一份数据。语言不同就不是自注意力该干的翻译活，语言相同才是生成活。

这里还藏着一处关键差别，在两边「能看多远」上：

```text
编码器侧（源输入）           解码器侧（目标输入）
句子一: 词1 词2 词3 词4       预测 句一词二：
句子二: 词1 词2 词3 词4         可见: 词1
完全可见，谁跟谁都能看到         不可见: 词2 词3 词4（掩码置 0）
```

读图说明：左边编码器把整句 4 个词全看得到；右边解码器在预测某个位置时，只允许看到它前面的词。

举具体一例：现在要预测句子一的第二个词。这个位置就是 Q，它能看到什么？只能看到句子一的第一个词——词二本身、以及后面三个词，掩码位置上都是 0，全看不到。于是这个位置算出来的，就是「句子一的词一」对应的 1000 个词的概率。

因为输入是两个英语句子、每句 4 个词，输出这边也会给出两个英语句子、每句 4 个词，正好和原始输入逐位置对比，这也正是模型能训练起来的原因。

换成英译法的情形就不一样了：输入是两个英语句子、每句 4 个词，输出是两个法语句子，而法语句子每个句子的词数不一定相等——可以先把它的长度设成固定的 10，再往下处理。这种固定长度、不足补齐的做法，正是后面处理变长目标序列时要面对的问题。

### 5 已完成模块与整机拼接

把这一节做完，回头清点一下手里已经有了什么：

```text
输入部分（词嵌入 + 位置编码）
    |
    v
编码器（6 × 编码器层）  <----------------+
    |                                   |
    | 编码器输出（K、V）                  |
    v                                   |
解码器（6 × 解码器层）                   |
    |                                   |
    v                                   |
输出部分（Linear + log_softmax）         |
    |                                   |
    v                                   |
[2, 4, 1000] -> 取概率最高的词            |
                                        |
组件层（demo02：子层连接、多头注意力、前馈全连接、规范化层……）
```

读图说明：四大块各自独立完成，其中组件层是底座——所有组件的行为都在那里实现，上面几块只是把它们组合拼接起来。

四大块分别是：输入部分搞定了、编码器搞定了、解码器搞定了、输出部分也搞定了。那么最后一个动作是什么？

把它们四个拼起来。

这活跟拼积木一模一样：一块一块积木，先把这一层拼好，再把那一层拼好，最后往一块儿一组装，齐活。区别只在于拼的不是玩具——先拼发动机，再拼底盘，再拼变速箱，再拼车架，这几样一拼接，一辆完整的车就有了。把输入、编码器、解码器、输出四块拼起来，得到的就是 **Transformer 架构**。

### 6 全流程张量形状的贯通复盘

收尾时拿 `2 × 4 × 512` 把整条链路再走一遍，形状这条线一通到底，模型就跑通了。

一开始给进去的不是 `2 × 4 × 512`，而是 `2 × 4`——两个句子、每句 4 个词。经过词嵌入处理，它变成 `2 × 4 × 512`，从此一发不可收拾：

- 位置编码之后还是 `2 × 4 × 512`；
- 各个注意力子层处理之后还是 `2 × 4 × 512`；
- 前馈全连接会先把 512 升到高维（2048），再降回来，出来依然是 `2 × 4 × 512`；
- 从编码器传到解码器，一路还是 `2 × 4 × 512`；
- 因为是自注意力，K 和 V 同源，编码器侧是 `2 × 4 × 512`，解码器侧也是 `2 × 4 × 512`。

一路传到解码器输出，仍然是 `2 × 4 × 512`。直到往上走进 `Linear`，这一维才变成 1000：`2 × 4 × 1000`，再映射成概率，还是 `2 × 4 × 1000`。然后从这 1000 个概率里挑出概率最高的那个词，作为最终结果。

$$[2,4] \rightarrow [2,4,512] \rightarrow [2,4,512] \rightarrow [2,4,512] \rightarrow [2,4,1000] \rightarrow \text{概率分布}$$

其中第一段变换由词嵌入完成，中间两段分别由编码器、解码器完成，最后一段由 `Linear` 加 `log_softmax` 完成。

套路就是这么一条。说不难是真不难——思路理顺了，剩下的就是代码怎么写、以及怎么把这件事给别人讲明白。

## 第 14 章：Day09-14.完整的Transformer架构搭建_上(掌握)
> 对应分集：P139 | 原始标题：《Day09-14.完整的Transformer架构搭建_上(掌握)》

组件的活儿到这一讲算是全部干完了——输入部分、编码器、解码器、输出部分，四大块一个不剩，全都被我们实现过一遍了。所以现在该干的事情只有一件：把这四块融到一起，搭出一个能跑的 Transformer。说白了就是摘果子的时候到了。

这句话的意思很具体。之前我们是把架构拆成一颗一颗螺丝造的：多头注意力、前馈全连接、残差连接、规范化层、编码器层、解码器层，然后是编码器、解码器、输出层。拆着造的时候，你手里拿的都是一块一块的零件，谁也跑不起来。现在要把它们拧成一个整体，这个整体就叫编码解码模型，也就是我们的 Transformer。

### 1. 装配思路与命名

先看这次要交的东西有几个。

装配的成品分两件：一个是模型本体，也就是编码解码器 `EncoderDecoder`；另一个是给这个本体用的测试函数 `make_model`——造一个模型出来，跑一遍前向传播，看看形状对不对。一个是"造车"，一个是"点火试车"。

命名这件事我得多说一句，因为它直接反映你理解到不到家。

很多人上来就写一个 `MyTransformer`。这个写法在真项目里是很 low 的，一看就知道你没有把 Transformer 的定位搞清楚。为什么不能这么叫？回想我们做过的两个案例：全球人名分类，还有后面的机器翻译——英译法。英译法那个案例就是一个 sequence-to-sequence 架构。而 sequence-to-sequence 的核心就三块：编码、解码，中间夹一个中间语义张量 C。

Transformer 的底层，恰恰就是这个结构。它名字叫 Transformer，但骨子里是一个编码解码模型。

> **结论**：所以这个类我们叫 `EncoderDecoder`，不叫 `MyTransformer`。你写下 `EncoderDecoder` 这五个字，读代码的人立刻知道——哦，这是编码解码模型，那就是 Transformer 这一堆。名字本身就是一张说明书。

装配之前，先把图的骨架在脑子里过一遍。左边是源序列从下往上走，右边是目标序列从下往上走，两条路最后汇到顶上那个输出层：

```text
              ┌───────────────────────┐
              │      Generator        │   Linear(d_model -> vocab_size)
              └───────────▲───────────┘
                          │
              ┌───────────┴───────────┐
              │       Decoder         │
              └───────────▲───────────┘
                          │
              ┌───────────┴───────────┐
              │    tgt_embed + PE     │  <- target_y
              └───────────────────────┘

   ┌───────────────────┐
   │     Encoder       │
   └─────────▲─────────┘
             │
   ┌─────────┴─────────┐
   │  src_embed + PE   │              <- source_x
   └───────────────────┘
```

读图的关键在于：绿色那四个点是我要存下来的对象（源端词嵌入、目标端词嵌入、编码器、解码器），蓝色那一段是解码器的处理流，最后顶上的红色点由 `generator` 负责翻出来。你要什么，就照这张图存什么。

### 2. 模型初始化：五个核心组件

`__init__` 里到底要存哪几个东西？答案是五个，一个都不能少，也不用多。

第一个，源端的词嵌入加位置编码，存成 `self.src_embed`，它对应图上源序列最底下那一层。第二个，目标端的词嵌入加位置编码，存成 `self.tgt_embed`——注意图上是有**两个**词嵌入的，左边一个右边一个，很容易漏掉右边这个。第三个，编码器 `self.encoder`。第四个，解码器 `self.decoder`。第五个，输出层 `self.generator`。

`generator` 其实就是图上最上面那一对，也就是最后的 `linear`。它的职责只有一句话：把解码器的输出转换成词表上的概率分布。

```python
class EncoderDecoder(nn.Module):
    def __init__(self, encoder, decoder, source_embed, target_embed, generator):
        super().__init__()
        # 1. 编码器的输入嵌入层（词嵌入 + 位置编码）
        self.src_embed = source_embed
        # 2. 编码器模块
        self.encoder = encoder
        # 3. 解码器的输入嵌入层（词嵌入 + 位置编码）
        self.tgt_embed = target_embed
        # 4. 解码器模块
        self.decoder = decoder
        # 5. 输出层：把解码器输出映射到词表概率分布
        self.generator = generator
```

> **提示**：`src_embed` 和 `tgt_embed` 是同一个词嵌入类（`Embeddings`）配位置编码（`PositionalEncoding`）的两个**实例**，参数不共享。源语言和目标语言的词表各是各的，位置编码也各自跟着自己那一路序列走。

初始化写完了，回头看这五行，你会发现这件事本身毫无难度，难的是"我到底该存哪几个"。而"该存哪几个"这个问题的答案不在代码里，在图里——**对着那张架构图去数你要什么**，图上出现过的入口和模块，一个都不能丢。

### 3. 前向传播：四个参数与两类掩码

前向传播这一步，参数的个数才是这一讲真正要琢磨的地方。四个参数：`source_x`、`target_y`、`source_mask`、`target_mask`。

`source_x` 是编码器的输入，它的形状是 `(2, 4)`——`batch_size = 2`，`seq_len = 4`，这一批两个句子，每句四个词。`target_y` 是解码器的输入，形状同样是 `(2, 4)`：左边输入是 2 4，右边输出也是 2 4，因为右边走的是自注意力，序列自己对自己，长度和批大小都跟源端一致。

接着是这两个掩码。它们长得像，作用却完全不同，这里必须掰开。

`source_mask` 是填充掩码（padding mask）。填充（padding）就是补齐长度用的那些 pad 值，掩码要干的事是防止这些 pad 值影响注意力计算结果。它的形状是 `(8, 4, 4)`：`n_head = 8` 个头，`4 × 4` 是每个头上一份 `seq_len × seq_len` 的掩码矩阵。

> **定义**：填充掩码（padding mask）——把为了对齐长度而填进序列的 pad 位置在注意力计算中屏蔽掉，使这些位置不参与打分。它的形状是 `(n_head, seq_len, seq_len)`，本例为 `(8, 4, 4)`。

`target_mask` 是句子掩码（sentence mask）。顾名思义，是"跟句子有关"的掩码，作用是防止未来的信息被提前利用。说得直白一点，就是**防止偷看未来的词**。

> **易错点**：同样是掩码，掩的位置不一样。源端用 padding mask，掩的是填充位；目标端用 sentence mask，掩的是"还没轮到的未来位置"。写代码时可以同名传参，但语义千万不能混。

至于它具体怎么掩，我们对着 2 4 那一批来说：假设你要预测第一个句子的第一个词，那这个位置**什么都让你看不见**；要预测第一个句子的第三个词，那你只能看见第一个句子的前两个词，第三个、第四个都不许看。这就是目标端自注意力被掩码约束住的样子。

两个掩码的归属也要分清：`target_mask` 是给解码器**下面那个自注意力子层**用的；而编码器—解码器之间的注意力，用的是 `source_mask` 去算注意力。

前向传播本身的动作只有三步，先拿编码器的输出，再把解码器推进一遍，最后过输出层：

```python
    def forward(self, source_x, target_y, source_mask, target_mask):
        # 1. 编码器前向传播，拿到编码器的输出
        encoder_output = self.encode(source_x, source_mask)
        # 2. 解码器前向传播，把编码器输出作为源端信息喂进去
        decoder_output = self.decode(target_y, encoder_output, source_mask, target_mask)
        # 3. 经过输出层，得到词表概率分布
        output = self.generator(decoder_output)
        # 4. 返回结果
        return output
```

三个动作连起来看，数据的形状一路是这样的：编码器吃进 `(2, 4)`，吐出 `(2, 4, 512)`；解码器吃进 `(2, 4)` 的目标输入和 `(2, 4, 512)` 的编码器输出，吐出还是 `(2, 4, 512)`；最后 `generator` 把最后一维从 512 掰成词表大小 1000，输出 `(2, 4, 1000)`。

```text
source_x            (2, 4)
   │  src_embed + PE
   ▼
encode              (2, 4, 512)     <- encoder_output
   │
target_y (2, 4) ──► decode  ──►     (2, 4, 512)
   │
   ▼  generator (Linear 512 -> 1000)
output              (2, 4, 1000)    <- 词表上的概率分布
```

`return` 出来的就是模型预测的词表概率分布，形状 `(2, 4, 1000)`。到这里，前向传播这条链就通了。

### 4. 编码与解码动作的封装

写到这里其实还差一步：`forward` 里调了 `self.encode` 和 `self.decode`，但这两个动作本身还没写。光把 `encoder`、`decoder` 这几个对象存进 `self`，只是告诉模型"我要用谁"；编码、解码这两个动作得单独补上，才算真的把动作糅进去。

所以要补两个函数：一个是得到编码器输出结果的 `encode`，也就是编码器的前向传播；一个是得到解码器输出结果的 `decode`，也就是解码器的前向传播。

```python
    def encode(self, source_x, source_mask):
        # 1. 源序列词嵌入（含位置编码），转成向量
        source_embed = self.src_embed(source_x)
        # 2. 送入编码器处理嵌入后的数据
        return self.encoder(source_embed, source_mask)

    def decode(self, target_y, encoder_output, source_mask, target_mask):
        # 1. 目标序列词嵌入（含位置编码），转成向量
        target_embed = self.tgt_embed(target_y)
        # 2. 送入解码器处理嵌入后的数据
        return self.decoder(target_embed, encoder_output, source_mask, target_mask)
```

`encode` 收的是源序列和填充掩码。源序列先过词嵌入加位置编码变成向量，再交给编码器，编码器做的就是刚才说的那一堆处理，返回的那个结果就是编码器的输出，形状 `(2, 4, 512)`。

`decode` 收的参数多两个：目标序列 `target_y`、编码器输出 `encoder_output`，再加 `source_mask` 和 `target_mask`。目标序列同样先过自己的词嵌入加位置编码，然后连编码器输出和两个掩码一起交给解码器，返回解码器的输出，形状一样是 `(2, 4, 512)`。

这一步封完，整件事的性质就变了。以前那种写法是什么样？在外面先调一下编码器，哦这个输出还得再往解码器里塞，解码器调完了再挪到输出层——每一步都要在外面手动串一遍，`output`、`decoder` 来回折腾。现在不一样了：**你只需要调我这一层就够了**。外面拿到的就是一个 Transformer，编码和解码的动作都已经封在我的 `encode` / `decode` 里，谁用谁省事。

> **结论**：所谓"完整的 Transformer 架构"，完整在这两个动作上——既有对象，也有对象要干的事。只把模块存进 `__init__` 而不补 `encode` / `decode`，那只是个零件柜，不是模型。

### 5. 测试函数 make_model

最后收尾，把模型拼起来跑一遍，也就是前面说的摘果子。

装备测试用的函数是 `make_model`。它的意义在于：编码器和解码器里封装的就是编码动作和解码动作，也就是整个架构，所以造一个模型、跑一次前向，就能看出这一整套是不是真的接上了。

```python
def make_model(source_vocab, target_vocab, n=6,
               d_model=512, d_ff=2048, n_head=8, dropout=0.1):
    # 组装完整的一个 Transformer 模型
    transformer = EncoderDecoder(
        encoder=Encoder(EncoderLayer(d_model, deepcopy(attn), deepcopy(ff), dropout), n),
        decoder=Decoder(DecoderLayer(d_model, deepcopy(attn), deepcopy(attn),
                                     deepcopy(ff), dropout), n),
        source_embed=nn.Sequential(Embeddings(d_model, source_vocab),
                                   deepcopy(position_encoding)),
        target_embed=nn.Sequential(Embeddings(d_model, target_vocab),
                                   deepcopy(position_encoding)),
        generator=Generator(d_model, target_vocab)
    )
    return transformer
```

这个函数做的事就是纯粹的一层封装：开头的 `deepcopy` 是为了让每一层拿到自己独立的一份子层实例，不能让多头注意力和前馈全连接在编码器、解码器之间共享同一个对象；参数 `n` 是层的堆叠个数，`n = 6` 对应编码器和解码器各堆六层；`d_model = 512` 是模型维度，`d_ff = 2048` 是前馈全连接层的隐层维度，`n_head = 8` 是注意力头数，`dropout = 0.1` 是随机失活概率。

参数对上了，模型就能造出来，跑一次前向，输出就是对得上的 `(2, 4, 1000)`：源端 `(2, 4)` 进去，中间一路都是 `(2, 4, 512)`，最后落成 `(2, 4, 1000)`。

> **注意**：这一讲我们把整体的组装讲完了，但还差两个函数和一次完整的测试，收尾的部分留到后面继续，把这几个补齐，这件事就彻底结束了。整体上看其实不算难，难点只有两个——一是对着图数清楚 `__init__` 里要存哪五样，二是把编码、解码这两个动作封进模型自己身上。

## 第 15 章：Day09-15.完整的Transformer架构搭建_下(掌握)
> 对应分集：P140 | 原始标题：《Day09-15.完整的Transformer架构搭建_下(掌握)》

上一讲我们把 Transformer 的整体骨架立起来了：`__init__` 里存好了五样东西，`forward` 里写了三步走——编码器前向、解码器前向、过输出层。但前向传播里调的那两个动作，`encode` 和 `decode`，当时还是空的。

这一讲要干的事很明确：把编码器和解码器这两个动作真正写出来，补齐，做一次收口。补完这一步，上一讲那句"你只需要调我"才真正站得住——不然外面拿到的还是一个零件柜。

### 1. 编码器动作 encode

先写编码这一半。函数名就叫 `encode`，参数要两个：`src_x` 和 `src_mask`。它要做的事只有一件——得到编码器的输出结果，也就是编码器的前向传播过程。

`src_x` 就是编码器的输入。它的形状是 `(2, 4)`：`batch_size = 2`，`seq_len = 4`，两个句子、每句四个词。这个张量在图上的位置，就是左侧最底下的入口。

`src_mask` 是输入序列的掩码。这里要停一下——这个掩码我们前面是**分成几个头**来准备它的，还记得吧？所以它的形状是 `(n_head, seq_len, seq_len)`，也就是 `(8, 4, 4)`：`8` 个头，每个头一份 `4 × 4` 的打分屏蔽矩阵。

而这个掩码用的是哪一个？`padding_mask`，填充掩码。它的职责是把填充值挡在注意力计算之外——序列为了对齐长度补进去的 pad 值，不能让它们参与注意力的计算。

编码器动作的代码只有两小步：

```python
    def encode(self, src_x, src_mask):
        # 1. 对源序列进行词嵌入处理，转成向量
        embed_x = self.src_embed(src_x)
        # 2. 通过编码器处理嵌入后的数据
        return self.encoder(embed_x, src_mask)
```

第一步，`src_x` 交给 `self.src_embed`，这一步里面包含词嵌入和位置编码两件事，出来的 `embed_x` 就是图上那个绿点——源端已经带好位置信息的向量表示。

第二步，把 `embed_x` 和 `src_mask` 一起送进 `self.encoder`。掩码在这里的角色，是让编码器的注意力计算知道哪些位置该屏蔽。`return` 回来的就是编码器的输出，图上那个紫色的点。

> **结论**：编码器的输入是 `(2, 4)`，输出是 `(2, 4, 512)`。`d_model = 512` 就是序列每个位置被表示成的向量维度。

```text
src_x  (2, 4)
   │
   ▼  self.src_embed   （词嵌入 + 位置编码）
embed_x (2, 4, 512)
   │
   ▼  self.encoder(embed_x, src_mask)
encoder_output (2, 4, 512)
```

读这张图只要抓住一点：源端进来的是"词的编号"，出去的是"带上下文的向量"，长度和批大小一路上都没变，只有最后一维从 1 变成了 512。

### 2. 解码器动作 decode

解码器这边是同一个套路，只是参数变多了。函数名写 `decode`，它要收四样：`tgt`（也就是目标端的 `target_y`）、`encoder_result`（就是编码器的输出 `encoder_output`）、`src_mask`、`target_mask`。

四个参数对应四件事，一个一个对清楚：

`tgt` 是解码器的输入。例如它跟上面一样是 `(2, 4)`。左边那一路是 `src_x`，是 2 4；右边这一路是 `target_y`，也是 2 4——因为解码器下面那个子层走的是自注意力，序列对自己，长度和批大小跟源端一致，所以两边的形状看起来是一样的。

`encoder_output` 是编码器的输出结果，形状 `(2, 4, 512)`，也就是刚才 `encode` 返回的那个紫点。它是解码器这一侧唯一能看到源端信息的入口。

`src_mask` 和刚才一样，是填充掩码，防止填充的 pad 值影响注意力计算结果。它服务的是编码器—解码器之间那层注意力。

`target_mask` 是句子掩码（sentence mask）。虽然两个都叫掩码，但掩的东西不一样：它防的是未来的信息被提前利用。说白了，就是**防止偷看未来的词**。

```text
    padding_mask          句子掩码 sentence_mask
   （掩填充位，给编码器     （掩未来位置，只给解码器
     -解码器注意力用）        的自注意力子层用）
```

`target_mask` 归谁用，这一点必须记牢：它是给解码器**下面那个自注意力**用的。它怎么掩？拿 2 4 那批数据说，如果我要预测第一个句子的第一个词，那这个位置上我什么都不让你看；如果我要预测第一个句子的第三个词，那你只能看到第一个句子的前两个词，第三个、第四个不许看。而你算注意力（跨源端那一层）的时候，用的是 `src_mask`。

> **易错点**：`target_mask` 只管解码器的自注意力子层，不要顺手把它也传给编码器—解码器注意力；那一层用的是 `src_mask`。传错一层，模型不会报错，只会悄悄学会偷看。

解码器动作的代码也是两小步，跟编码器对得很齐：

```python
    def decode(self, target_y, encoder_output, src_mask, target_mask):
        # 1. 对目标序列进行词嵌入处理，转成向量
        embed_y = self.tgt_embed(target_y)
        # 2. 解码器处理嵌入后的数据
        return self.decoder(embed_y, encoder_output, src_mask, target_mask)
```

第一步，`target_y` 交给 `self.tgt_embed`——注意这是**目标端自己那一个**词嵌入加位置编码，跟源端的 `src_embed` 是两个独立实例。出来的 `embed_y` 是右边的绿点。

第二步，四样东西一起进 `self.decoder`：`embed_y`、`encoder_output`、`src_mask`、`target_mask`。注意传参的顺序和名字，`encoder_output` 夹在中间，两个掩码一前一后，参数名一定要对上，不然就是那种"跑得通但结果不对"的隐蔽 bug。

`return` 回来的是解码器的输出结果，形状 `(2, 4, 512)`。

### 3. 两处注意力的拷贝与传参对应

解码器层内部要的是两个注意力实例，不是一份。原因在于它们干的事不同：一个处理目标序列内部的关系，另一个处理目标序列和源序列之间的关系。

**第一个是解码器的自注意力。** 它处理的是目标序列内部关系。因为上一讲的 `self_attn` 那个名字已经被上面的编码器占掉了，所以这里得换个名字，写成 `self_attn1`。

写到这里顺便把一个概念性的特殊情形说清楚。我们以前讲自注意力的时候，说的是 `Q` 不等于 `K`、`Q = K = V` 这一种情况，那当然算自注意力。但其实还有一种特殊情形：`Q` 不等于 `K`，而 `K` 等于 `V`——这种严格意义上讲，它也属于自注意力机制。解码器这里用的就是这个情形，因为 `K` 和 `V` 是同一份东西。

**第二个是解码器的编码器—解码器注意力。** 它处理的是目标序列和源序列之间的关系。名字不要写成 `attn2`，写成 `src_attn` 更容易对上号：`src_attn = self_attn`——注意，它其实也是从上面那个 `self_attn` 拷贝来的。

拷贝这件事说明一个要点：解码器里这两个注意力，本质上都是基于同一个多头注意力类做出来的实例，**结构一模一样，区别只在于你把它放在哪个位置、传哪些参数进去**。放上面还是放下面，随便你，但有一件事要守规矩——固定死一套。你要是想这么写，就这么定下来，别一会儿放上一会儿放下，否则等一下传参的时候你自己就传蒙圈了。

所以对应关系一定要记清楚：

| 解码器层参数 | 传谁 | 作用 |
| --- | --- | --- |
| `self_attn` | `self_attn1` | 目标序列内部自注意力（`Q ≠ K`，`K = V`） |
| `src_attn` | `src_attn = self_attn` 的拷贝 | 目标序列与源序列之间的注意力 |

> **提示**：既然两个注意力都是同一份东西复制出来的，那么"谁生效"完全取决于你调函数时传的是谁。传参顺序和参数名，是这一步唯一的正确性来源。

### 4. 封装带来的调用变化

`encode` 和 `decode` 落下来之后，回过头看这一讲到底改变了什么。

以前是什么样？外面要自己走一遍流程：先手动调编码器拿到输出，再把输出往解码器里塞，解码器跑完再挪到生成器去，中间 `output`、`decoder` 来回倒手。现在不用了：**外面只需要调我这一层就够了**。因为编码和解码的动作已经封在模型自己身上，我的 Transformer 自己就有编码动作，也有解码动作。

换句话说，这一讲补的这两个函数，把"架构"从名词变成了动词。上一讲搭出来的是 Transformer 的静态结构，这一讲让它真的会干编码和解码这两件事。原因就在这儿。

```python
    def encode(self, src_x, src_mask):
        embed_x = self.src_embed(src_x)
        return self.encoder(embed_x, src_mask)

    def decode(self, target_y, encoder_output, src_mask, target_mask):
        embed_y = self.tgt_embed(target_y)
        return self.decoder(embed_y, encoder_output, src_mask, target_mask)
```

到这里，编码、解码这两个动作就封装完毕了。下一件事就是测试——把模型造出来，跑一遍前向传播，看那个 `(2, 4, 1000)` 是不是真的出来了。

## 第 16 章：Day09-16.Transformer架构测试_上(理解)
> 对应分集：P141 | 原始标题：《Day09-16.Transformer架构测试_上(理解)》

`make_model` 这个函数，我以前是把它当"测试函数"来讲的，但这一讲我要亲自把它从头写一遍。为什么？因为你回头看一眼就会发现：编码器和解码器里封装的，就是编码、解码这一整套内容，也就是整个架构。所以这个函数本身就是一次完整的拼装演示，写完它，再把模型造出来跑一次，输出会出现一个 `2 4 512`，那就代表 Transformer 整体走通了，最后落成的结果是我们之前反复说过的 `(2, 4, 1000)`。

中间这一路的形状，我先把话放在这儿：`2 4` 进去，中间一路全都是 `2 4 512`、`2 4 512`、`2 4 512`，最后落成 `2 4 1000`。写的过程中你拿这串数字对一下，哪一层跑偏了一眼就看出来。

### 1. 深拷贝工具函数与引用赋值

`make_model` 的第一步不是写层，是先准备一个工具：把深拷贝函数取个短名字。

```python
c = copy.deepcopy
```

就这一行，但里面藏着前面必须弄明白的一个语法点。`copy.deepcopy` 后面**加**小括号，那叫调用；**不加**小括号，那是赋值——把 `deepcopy` 这个函数对象本身起个名字叫 `c`。

这个写法我们早就见过，只是当时没往这儿想。比如：

```python
def get_sum(a, b):
    return a + b

hg = get_sum      # 函数名不加括号，是赋值
hg(10, 20)        # 等价于 get_sum(10, 20)，结果是 30
```

单独写一个函数名就是赋值，`hg` 在这里顶的角色跟 `get_sum` 完全一样。所以 `c` 的意思就是"我一会儿要写的那一堆 `copy.deepcopy`"，我不想每次都把那串长的写一遍，我就用 `c` 代它。

> **提示**：这类改名的写法，作用域只在当前函数里——`c` 是 `make_model` 内部的局部名字，出了这个函数就没了。

后面这一段编码器和解码器里，`deepcopy` 会被用上很多次：编码器层、解码器层、两处注意力、前馈全连接，还有编码端和解码端各自的词嵌入加位置编码，每一份都要是**独立的一份**。这是这一讲最容易被忽略、又最容易出事的地方——共用同一个实例，等于让编码器和解码器共享一份参数，结构看着对，语义已经错了。

> **易错点**：凡是"同一个类要用好几份"的地方，都要 `deepcopy` 出新实例，不能把同一个对象塞两处。

### 2. 编码器侧：七步搭建

编码器这一半要按数据流的箭头一步一步往上走。现在的路子很清楚：从 input 出发，先走词嵌入，再到位置编码，然后进多头注意力，再进前馈全连接。我们就照这个顺序，一个一个把实例造出来。

#### 2.1 词嵌入与位置编码

第一步，编码器的词嵌入层。上来先写这一层，因为它是入口。

```python
src_embed = Embedding(vocab, d_model)
```

参数对不上不用慌，正是它报红了你才知道该看它要什么。把光标放到类名上等一下，提示就出来了：它要的是 `vocab_size` 和 `d_model`。对照传进去——`vocab_size = 1000`，`d_model = 512`。意思是一共 1000 个词，每个词表示成 512 维的向量。

第二步，位置编码层。词嵌入之后紧接着就是它，参数同样是那一个模型维度。

```python
src_position = PositionalEncoding(512, dropout=0.1)
```

`d_model` 传 512，随机失活概率 `dropout = 0.1`。到这里，数据已经过了词嵌入和位置编码两层，走到图上那个位置了。

#### 2.2 多头注意力与前馈全连接

第三步，多头注意力机制的实例化。

```python
self_attn = MultiHeadedAttention(n_head, d_model)
```

这里有个真实的坑：这个类的第一个参数不是 `d_model`，而是头数。我们当时定义的参数名不是 `n`，是 `head`（也就是 `n_head`）。你要是不熟这个参数，就直接写数字 `8`，别硬写参数名；要么点进去看定义，要么把光标放到类名上等提示。

第四步，前馈全连接层。

```python
ff = FeedForward(512, 2048)
```

两个参数是 `d_model` 和 `d_ff`：512 是模型维度，2048 是前馈层内部的隐层维度——先升维再降回来，这是它一贯的形状。参数对不上就在类名上停一下鼠标，别自己飞半天猜。

#### 2.3 随机失活的独立定义

第五步，单独定义一个随机失活概率。

```python
dropout_p = 0.2
```

```python
self.dropout = nn.Dropout(dropout_p)
```

它的作用是防止过拟合。你会问：上面不都是 0.1 吗，怎么这里 0.2？是的，我就是想改一改。这个动作你不写也行，不写的话各层的失活概率都走默认的 0.1；我这里单独定一个 0.2，是为了等一下往里传参的时候让你看清楚——**这一层的失活概率是从外面传进去的**，不是一个写死的数。

#### 2.4 编码器层与堆叠

第六步，单个编码器层的实例化。它的组成是：多头注意力、前馈全连接、残差连接、规范化层。

```python
my_encoder_layer = EncoderLayer(512, self_attn, ff, dropout_p)
```

参数名一样对不上，光标放上去看：它要的叫 `feed_forward`，失活概率那个参数叫 `dropout`——**没有那个 `p`**。把 `dropout_p` 的值传进 `dropout` 这个形参，位置上不要串。

第七步，编码器的复制化，也就是堆叠。

```python
my_encoder = Encoder(my_encoder_layer, n=6)
```

把刚才那一个编码器层扔进去，再传一个堆叠个数。这里参数名写的是大写的 `n`，传 `n = 6`。

> **结论**：编码器 = 一个编码器层 × 6。层是模板，`n` 是复制份数，两份东西分开定义、分开实例化。

写到这里，左边这一路就搭完了。接下来箭头不能从老地方画了——你得从编码器输出那个位置重新起笔，往上继续捅。因为解码器是另一条独立的通路。

### 3. 解码器侧：七步搭建

解码器跟编码器是同样的套路，但**不是把编码器那段抄一遍就完了**——参数和实例对应关系上有几处必须分清。我一步一步来。

#### 3.1 词嵌入、位置编码与自注意力

第一步，解码器的词嵌入层。这里没有别的花样，它跟编码器那个词嵌入长得一模一样。既然是同一个东西，就有一个省事的写法：

```python
tgt_embed = copy.deepcopy(src_embed)
```

第二步，位置编码。跟上面一样，直接深拷贝过来：

```python
tgt_position = copy.deepcopy(src_position)
```

第三步，解码器的自注意力机制。它处理的是**目标序列内部的关系**。

```python
self_attn1 = copy.deepcopy(self_attn)
```

名字为什么带个 `1`？因为 `self_attn` 这个名字上面已经被编码器占住了，这里是第二个实例，所以写 `self_attn1`。

写到这里，顺手把一个概念难点讲清楚。我们以前说自注意力，只说过一种情况：`Q` 不等于 `K`，而 `Q = K = V`——那当然算自注意力。其实还有一种特殊情况：`Q` 不等于 `K`，但是 `K = V`。

> **提示**：`Q ≠ K` 且 `K = V` 这种情形，严格意义上也属于自注意力机制。解码器这里的自注意力用的就是它，因为键和值是同一份东西。

#### 3.2 编码器解码器注意力与传参对应

第四步，解码器的编码器—解码器注意力机制。它是用来处理**目标序列和源序列之间的关系**的。

```python
src_attn = copy.deepcopy(self_attn)
```

名字不要叫 `attn2`，叫 `src_attn`，这样一眼就知道它负责源端信息。你会发现，解码器里的两个注意力都是基于同一个多头注意力拷出来的，**本质上完全一样，区别只在于你把它放在上面还是下面**。放上放下都行，但传参的时候，你传谁就是谁生效。

> **易错点**：既然两个注意力是同一份东西复制出来的，那就固定死一套写法，别一会儿上、一会儿下——否则等一下传参你自己就传蒙了。虽然都是拷贝，但谁生效完全取决于你调函数时传的是哪一个。

第五步，前馈全连接层。

```python
ff1 = c(ff)
```

第六步，单个解码器层的实例化。它的组成是：多头注意力加前馈全连接、残差连接、规范化层。

```python
my_decoder_layer = DecoderLayer(512, self_attn1, src_attn, ff1, dropout_p)
```

传参这一节要格外慢。第一个 `512` 是模型维度；第二个参数是要目标端自注意力的位置，传 `self_attn1`；第三个位置是编码器—解码器注意力，传 `src_attn`；第四个是前馈全连接 `ff1`；最后一个是失活概率。

> **提示**：这里的参数名最好别硬写，写错了不报错但会传反。把光标点到类名上、鼠标别动，等一下提示就出来；或者光标点上去之后直接按 `Ctrl+Q`——`Q` 就是 query（查询）那个词。等提示出来了，参数名对上号再传。

第七步，解码器的堆叠。

```python
my_decoder = Decoder(my_decoder_layer, n=6)
```

把一个解码器层扔进去，再传 `6`。到这里，`my_decoder` 跟上面那个 `my_encoder` 的动作是完全一模一样的套路——一个编码、一个解码，记住这一点就够了。

### 4. 输出层与整体组装

编码写完了，解码也写完了，接下来该输出部分了。输出层其实只有一个东西，就是那个 `linear`，所以只有一步。

```python
generator = Generator(512, 1000)
```

`Generator` 是我们自己写的那个类，参数是模型维度 512 和词表大小 1000——把解码器输出的 512 维向量映射成 1000 个词上的分布。

到这一步，编码器、解码器、输出层这三个大件，全都在这个函数内部封装好了。接下来就是收尾，也就是摘果子的时候：把上面这些对象汇总到一起，组装成一个完整的 Transformer 模型。

```python
def make_model(source_vocab, target_vocab, n=6,
               d_model=512, d_ff=2048, n_head=8, dropout=0.1):
    # 深拷贝工具函数：用于复制模块
    c = copy.deepcopy

    attn = MultiHeadedAttention(n_head, d_model)
    ff = FeedForward(d_model, d_ff)
    position = PositionalEncoding(d_model, dropout)

    my_encoder_layer = EncoderLayer(d_model, c(attn), c(ff), dropout)
    my_encoder = Encoder(my_encoder_layer, n)

    my_decoder_layer = DecoderLayer(d_model, c(attn), c(attn), c(ff), dropout)
    my_decoder = Decoder(my_decoder_layer, n)

    model = EncoderDecoder(
        encoder=my_encoder,
        decoder=my_decoder,
        source_embed=nn.Sequential(Embeddings(d_model, source_vocab), c(position)),
        target_embed=nn.Sequential(Embeddings(d_model, target_vocab), c(position)),
        generator=Generator(d_model, target_vocab)
    )
    return model
```

这一大段里有几个地方值得对照前面的步骤看清：

`c = copy.deepcopy` 就是第一节说的那个改名，后面所有需要"来一份新的"的位置都写成 `c(某物)`，读起来短、看得清。

编码器层拿到的多头注意力和前馈全连接，都要先 `c(...)` 拷一份；解码器层要**两份注意力**——一份给目标序列内部的自注意力，一份给编码器—解码器注意力。这就是 3.1 和 3.2 里那两个实例在组装时的落点。

`EncoderDecoder` 那边一共有五个入参：编码器、解码器、源端嵌入、目标端嵌入、输出层。源端和目标端的嵌入都是「词嵌入 + 位置编码」组成的一个序列模块，参数不同（各自 1000 的词表）、位置编码各自一份拷贝。这就是上一讲"两个词嵌入一个都不能少"在代码里的样子。

至于组装这一段的最后一步代码，这一讲讲到这里就先停住了，剩下的收尾留到后面继续。

> **注意**：这一讲的主线不是"这几个类怎么用"，而是**装配的顺序**——先深拷贝工具，再按数据流箭头一层一层造编码器侧的子层，堆叠成编码器；再按同样的顺序造解码器侧的子层（两处注意力要分清），堆叠成解码器；最后拼输出层，汇总成完整模型。顺序乱了，参数就会串；参数一串，模型不报错但学不出东西。

## 第 17 章：Day09-17.Transformer架构组件介绍(理解)
> 对应分集：P142 | 原始标题：《Day09-17.Transformer架构组件介绍(理解)》

前面几讲我们是一块一块地敲零件——词嵌入、位置编码、多头注意力、前馈全连接、编码器、解码器、输出层，全都是散着的。这一讲要做的事情只有一件：把这些零件按正确的顺序塞进一个 `MyTransformer` 里，组装出一个能打印出完整结构的模型架构。

先说清楚这一讲在整条链上的位置。编码器的输入处理要做什么？词嵌入加上位置编码。解码器的输入处理呢？同样是这两件事。既然两边做的是同一套动作，那它们就该在同一个地方被描述清楚，而不是在模型里各写一遍。

```text
MyTransformer
   ├── src_embed   : 编码器输入处理链  = 词嵌入 + 位置编码
   ├── Encoder     : 编码器            = 6 × 编码器层（每层 2 个子层）
   ├── tgt_embed   : 解码器输入处理链  = 词嵌入 + 位置编码
   ├── Decoder     : 解码器            = 6 × 解码器层（每层 3 个子层）
   └── generator   : 输出层            = 512 维 → 词汇表大小的概率分布
```

读图说明：五块并列的组件就是这一讲要依次往里塞的东西，前两块与后两块在结构上刻意镜像，最后一块负责把隐藏维度翻译成词表上的概率。

---

### 1. 模型骨架与参数填充

上来先写这一行——我终于能把 `T-R-A-N-S-F-O-R-M-E-R` 这个单词完整地打出来了：

```python
class MyTransformer(nn.Module):
    def __init__(self, encoder, decoder, src_embed, tgt_embed, generator):
        super().__init__()
        self.encoder = encoder
        self.decoder = decoder
        self.src_embed = src_embed
        self.tgt_embed = tgt_embed
        self.generator = generator
```

这里的 `Encoder`、`Decoder` 是谁？就是我们自己写的这套模型架构里已经造好的那几个类。上面那一堆组件全都干出来了，现在这一步只是往里塞。

怎么知道构造函数要收几个参数？把光标点到名字上按 `Ctrl+Q` 看提示，它会把这几个参数都拉出来：`encoder`、`decoder`、`src_embed`、`tgt_embed`、`generator`。照着提示往里塞就行，塞的时候顺序别乱。

塞第一个参数之前先解决一个疑问：`src_embed` 这个位置到底该放什么？

如果把词嵌入层和位置编码对象直接拆成两个参数塞进去，那模型外面调用的时候每次都得自己写一遍相加。所以这里用 `nn.Sequential` 把它们包成一条链：

```python
self.src_embed = nn.Sequential(src_embed, src_position)
```

`Sequential` 是一条处理链，链的意思就是先走 A 再走 B，跟工厂流水线一模一样。编码器的输入处理，先走词嵌入拿到词的稠密向量，再走位置编码补上位置信息，两个动作合二为一。

> **易错点**：这个“拼接”动作在模型的测试代码里其实是写过的，但在模型类里没有。所以别以为重复劳动——不在模型里合成一条链，`MyTransformer` 的前向传播里就得自己手写这两步相加。既然是每次都要做的事，就归到模型里做一次。

那为什么只往 `Sequential` 里塞了一个 `src_embed`、一个 `src_position`，而不是把它们当成两个独立参数传？因为 `Sequential` 收的是“要按顺序执行的操作”，你把两个子模块丢进去，它自己就替你串起来；参数越多，构造的地方就越啰嗦。

同一条思路，解码器那一侧照抄一遍：

```python
self.tgt_embed = nn.Sequential(tgt_embed, tgt_position)
```

你们有没有发现，右边这俩 `tgt_embed`、`tgt_position` 跟左边那俩 `src_embed`、`src_position` 长得是一模一样的？对，就是复制过来改名的。所以这个模型真没那么难，很多地方都是同构的。

再把 `Encoder`、`Decoder` 塞进去，最后一个是输出层 `generator`。收尾那个逗号留不留都无所谓。然后打印模型结构调一下：

```python
if __name__ == '__main__':
    my_transformer = make_model()
    print(my_transformer)
```

打印出来“My Transformer”那一坨的时候别急着收工。这才刚把架构搭起来，还没干活——下面还得扔两句句子进前向传播里跑一跑。就像自己养了个孩子，零件是一个一个敲出来的，现在只是把这个孩子拼完整了。

> **提示**：模型组装完只是结构对了，参数维度对不对是另一件事。结构对了不等于能跑通，能不能跑通要等前向传播把维度全部对齐之后才算数（下一讲就是干这件事）。

结构打印出来之后，我们要拿它跟源码里那堆密密麻麻的组件名字一一对上。

```text
MyTransformer
 ├─ (encoder) MyEncoder
 │    ├─ (layers) ModuleList  0..5        → 6 个编码器层
 │    ├─ (src_embed) Sequential
 │    │    ├─ (0) Embedding(1000, 512)
 │    │    └─ (1) PositionalEncoding(512, dropout=0.1)
 │    └─ (norm) LayerNorm(512)
 ├─ (decoder) MyDecoder
 │    ├─ (layers) ModuleList  0..5        → 6 个解码器层
 │    ├─ (tgt_embed) Sequential
 │    │    ├─ (0) Embedding(1000, 512)
 │    │    └─ (1) PositionalEncoding(512, dropout=0.1)
 │    └─ (norm) LayerNorm(512)
 └─ (generator) Generator
      ├─ (linear) Linear(512, 1000)
      └─ (softmax) LogSoftmax(dim=-1)
```

读图说明：这张图是打印结果的自上而下复述，缩进层级就是对象的包含关系；`0..5` 那两处是模型规模的关键数字，`512` 与 `1000` 那两个数字决定后面所有维度能不能对齐。

---

### 2. 编码器输入处理链与词嵌入层

先看打印结果里的 `src_embed`，它是一个 `Sequential`，也就是编码器的输入部分处理链。链里面两件事：`0` 是 `Embedding` 词嵌入层，`1` 是 `PositionalEncoding` 位置编码。第一组解释完毕，就这一坨。

> **定义**：编码器输入处理链（source embedding pipeline）把“词 → 稠密向量”与“位置 → 位置向量”这两步固定地串在一起，对外只暴露一个可调用对象，保证任何输入都走完这两步再进编码器。

解码器那边 `tgt_embed` 是同样的结构，所以“解码器输入处理链”这四个字也只是把 source 换成了 target，其余一字不差。

词嵌入层这一层本身要交代两件事。第一，它把词表里每个词的索引映射成一个 512 维的稠密向量，因此两个关键参数是词表大小和嵌入维度：词表 1000 个词，就是 `1000 → 512`；第二，位置编码对象接在它后面，处理的是“同样这 512 维”，只是往里面注入词序信息。两颗零件的入口维度和出口维度必须一致，否则 `Sequential` 里第二颗零件吃不下第一颗的输出。

---

### 3. 编码器结构：6 层与两个子层

往下来看 `Encoder`，这一段是这一讲信息量最大的地方，得慢慢拆。

```text
MyEncoder
 ├─ (layers) ModuleList      → 6 × MyEncoderLayer
 │    └─ 单个 MyEncoderLayer
 │         ├─ (sublayer) ModuleList
 │         │    ├─ (0) MultiHeadedAttention   多头注意力子层
 │         │    └─ (1) PositionwiseFeedForward 前馈全连接子层
 │         └─ (2) ModuleList                  → 2 × SublayerConnection
 │              ├─ (0) SublayerConnection（包第一个子层）
 │              └─ (1) SublayerConnection（包第二个子层）
 └─ (src_embed) Sequential / (norm) LayerNorm
```

读图说明：编码器内部是三层嵌套——编码器包含 6 个编码器层，每个编码器层包含 2 个子层，每个子层外面再套一层连接结构；外层那个 `ModuleList` 的数字 6 就是编码器的深度。

第一层是 `ModuleList`，里面 0 到 5 一共 6 个元素。这就是编码器等于 6 个编码器层的意思。为什么用 `ModuleList`？因为这 6 层是同样的结构复制 6 份，用列表装起来，PyTorch 才认得这些子模块的参数需要一起管理。

进到单个编码器层，它由两个子层组成。

第一个子层是多头注意力子层，对应 `MultiHeadedAttention` 这个操作。再往里看它的内部结构，是 4 个全连接层。想想我们之前说的黄瓜切片、切段、下火锅那个图，脑子里把那张图翻出来就对了：4 个线性变换分别负责生成查询、键、值，以及把多个头拼回来之后再做一次输出投影。这个子层后面接的是 `Dropout` 随机失活，属于注意力内部的细节。

第二个子层是前馈全连接子层，对应 `PositionwiseFeedForward`。

> **定义**：前馈全连接子层（position-wise feed-forward）由两个全连接层构成，先升维、再降维，在两个线性层之间做非线性激活，作用是强化特征。

它为什么要先升维再降维？升维把 512 维投到更宽的空间里，让不同通道上的特征组合出非线性关系；降回来是为了让这一层的输出重新对齐 512 维，这样多个子层才能一层一层叠下去。所以这个位置的顺序一定是先升维、再降维，绝不能反。源码里前馈内部的特征维度是 2048，也就是 `512 → 2048 → 512`。

接下来这一句容易被看漏：`sublayer = ModuleList([SublayerConnection(...) for _ in range(2)])`。这里的 2 是什么？上面那个 6 是 6 个编码器层，这个 2 是每个编码器层有 2 个子层，把这句话贴到这儿就完全对上了。

> **提示**：这行代码原本的写法是 `2 * Sublayer(...)` 这种紧凑表达，读起来不直观。更好的写法是在注释里直接标出“第一个子层：注意力子层”“第二个子层：前馈全连接子层”，然后把这坨合起来看——`2` 这个数字的含义就在这一层被解释清楚了。

`ModuleList` 最后还有一个 `norm` 层，也就是 LayerNorm。它不参与子层计数，是编码器所有层处理完之后额外加的一次规范化。

---

### 4. 解码器结构：6 层与三个子层

`src_embed` 那一对括号到哪里结束？点到 `Encoder` 后面的括号，下面会出现一条红色的配对线，它连到对应的收尾括号。顺着红线确认边界，就能干净地断开编码器这一段——断开以后剩下来的，就是解码器的输入部分：`tgt_embed = Sequential(词嵌入层, 位置编码)`。

解码器里同样是 `ModuleList`，但这里的 6 换了一层含义：解码器等于 6 个解码器层。

进到单个解码器层的三个子层，第一个子层是多头注意力子层。这里的 `self` 参数与编码器那边的 `self` 看起来长得一样，但落在图上是不同的位置——解码器第一层的这个操作是掩码多头注意力子层，作用是防止偷看未来词。

```text
单个解码器层（3 个子层）
 ├─ 子层 1：掩码多头注意力子层   self-attn，带掩码，防止偷看未来词
 ├─ 子层 2：多头注意力子层       src-attn，不带掩码，算注意力权重
 └─ 子层 3：前馈全连接子层       升维降维，强化特征
```

读图说明：解码器层比编码器层多出来的就是中间那一层，它的查询来自解码器自身、键值来自编码器输出；三个子层的顺序不可交换，掩码自注意力必须在跨注意力之前。

第二个子层还是多头注意力子层，但它的 `src` 参数说明了一件事：这一层拿编码器的输出参与计算，作用是为解码器生成结果算出更合理的注意力权重。它不是做掩码的。

> **结论**：解码器里三个子层里只有第一个是掩码的，其余做注意力的地方都是在算权重，让你在生成结果时有侧重、更聚焦。

第三个子层是前馈全连接子层，同样是升维降维，细节与编码器一致就不重复了。

最后一句话也是用数字表达的：解码器层等于三个子层。于是 `3 × SublayerConnection` 这一堆就解释了——上面那个 6 是 6 个解码器层，这个 3 是每个解码器层有三个子层。跟编码器一样，这种紧凑写法不如在注释里把子层名字列出来看得明白。

同样地，解码器 `ModuleList` 外面也有一个 `norm`，也是所有层处理完之后再补的一次规范化。

---

### 5. 输出部分与概率预测

最后一个组件是输出部分，也就是 `generator`。

这一步在做什么？把词向量维度转成词汇表大小的概率分布。隐藏维度是 512，词汇表有 1000 个词，于是这里是一个 `512 → 1000` 的线性变换，接一个 `LogSoftmax` 得到概率分布。

有了这个分布，预测就变得很朴素：1000 个数里面，找最大的那个就行了，那个下标对应的词就是预测出的单词。

```text
最后一步的维度流向

  (2, 4, 512)  ──→  Linear(512 → 1000)  ──→  (2, 4, 1000)
   隐藏层输出          输出投影              每个位置上的词表概率
                                              ↓
                                      argmax(第 3 维) → 预测词
```

读图说明：最后一维从 512 变成 1000 之后，每个时间步上都有一份完整的词表打分，取最大值即得预测词；前两维（批大小、序列长度）在投影前后保持不变。

所以整条链是：输入 → 编码器 → 解码器 → 输出部分。这就是我们自己的 `MyTransformer` 组装出来的完整结构。

### 6. 调试时怎么查括号与维度

架构搭起来之后第一次跑，很可能是跑不通的，这一节把查错的路子留下。

第一件事是确认括号区间。IDE 里点到左括号，配对括号会被红线连起来，一眼就能看出这段代码覆盖到哪一行。编码器那段代码里有多个 `ModuleList`、多个 `SublayerConnection`，括号一多就很容易把解码器的组件写进编码器的括号里，靠配对提示比靠眼睛数括号可靠得多。

第二件事是顺着参数一个一个往下查。报错说维度不匹配的时候，不要盯着报错行发呆，从 `my_transformer` 往下捋：`make_model()` 里按顺序传了 `source_embedding`、`source_position`、`my_encoder`，然后是 `decoder` 和后面那几个。哪一环传错了、传漏了，都会在最后那次打印形状的时候暴露出来。

```text
自底向上的检查顺序

  组件层  →  每个组件自己的日志打印（张量形状 / 注意力权重形状）
  模型层  →  make_model() 里的参数顺序与个数
  前向层  →  forward 里调用的对象与方法名
```

读图说明：从最内层的组件往外查，先确认单个组件能独立跑出正确形状，再确认它们被组装时的顺序，最后确认前向传播调用的名字对不对——这三层里出错的概率是从低到高。

一旦某个地方写错，一路上的形状都会跟着错，最终打印不出来。所以“打印形状”不是可选的调试动作，是把错误逼到某一个具体位置的手段。

### 7. 组件规模与内部要求速查

把这一讲讲到的所有组件、嵌套层级和内部要求汇总到一张表里，扫一遍就能定位到某个组件在哪一层、要几个什么东西。

| 组件 | 嵌套位置 | 数量 | 内部要求 | 关键维度 |
| --- | --- | --- | --- | --- |
| 编码器输入处理链 `src_embed` | `MyTransformer` 直属 | 1 条链 | `Sequential`：先词嵌入，再位置编码 | 词表 1000 → 512 |
| 编码器 `Encoder` | `MyTransformer` 直属 | 1 个 | 内含 `ModuleList`，末尾补一次 `LayerNorm` | 6 个编码器层 |
| 编码器层 | 编码器 `ModuleList` 内 | 6 个 | 每层 2 个子层，配 2 组子层连接 | 子层内保持 512 |
| 多头注意力子层 | 编码器层内（第 1 个子层） | 1 个 | 内部 4 个全连接层 | 头数 8，`d_model` 512 |
| 前馈全连接子层 | 编码器层内（第 2 个子层） | 1 个 | 两个全连接层，先升维再降维 | 512 → 2048 → 512 |
| 解码器输入处理链 `tgt_embed` | `MyTransformer` 直属 | 1 条链 | 与 `src_embed` 结构一致 | 词表 1000 → 512 |
| 解码器 `Decoder` | `MyTransformer` 直属 | 1 个 | 内含 `ModuleList`，末尾补一次 `LayerNorm` | 6 个解码器层 |
| 解码器层 | 解码器 `ModuleList` 内 | 6 个 | 每层 3 个子层 | 子层内保持 512 |
| 掩码多头注意力子层 | 解码器层内（第 1 个子层） | 1 个 | 带掩码，防止偷看未来词 | 头数 8，`d_model` 512 |
| 跨注意力子层 | 解码器层内（第 2 个子层） | 1 个 | 用编码器输出算注意力权重，不掩码 | 头数 8，`d_model` 512 |
| 前馈全连接子层 | 解码器层内（第 3 个子层） | 1 个 | 升维降维，强化特征 | 512 → 2048 → 512 |
| 输出层 `generator` | `MyTransformer` 直属 | 1 个 | 线性变换 + `LogSoftmax` | 512 → 1000 |

### 8. 调试通过之后的一次复盘

跑通之后回到源码看一遍，有三件事值得盯住。

第一件是那份密密麻麻的注释。源码里每个组件旁边都标着数字——`1000`、`512`、`8`、`2048`，还有句子长度那个 `4`。这些数字不是装饰，它们共同决定了张量的形状能不能一路对齐。晚上回去把这一坨自己看明白，就等于把整个模型的数据流看明白了。

第二件是模型规模的对称性。编码器 6 层、解码器 6 层；编码器层 2 个子层、解码器层 3 个子层；两边各有一条输入处理链、各补一次规范化。记住这组对称关系，比死背打印结果有用得多——下次换模型规模，你知道哪些数字要成对改。

第三件是“自己写出来的”这件事本身的意义。这一讲的代码不是复制粘贴来的，是前面一讲一讲敲出来的零件拼起来的。写的时候顺畅，调试的时候也就知道该往哪儿找；如果一直是抄，报错的时候连自己都不知道组件之间是怎么连的。

### 9. 提示一处容易搞混的地方：掩码多头注意力与跨注意力

解码器两个注意力子层长得太像，名字里都带“多头注意力子层”，都传 `self` 和 `src`，很容易写成一样。它们的区别只有一条，但这条决定了模型能不能正确训练。

| 对比项 | 解码器第 1 个子层 | 解码器第 2 个子层 |
| --- | --- | --- |
| 是否加掩码 | 加，掩码掉未来位置 | 不加 |
| 目的 | 防止偷看未来词 | 计算注意力权重，让生成有侧重 |
| 查询来源 | 解码器自身输入 | 解码器自身状态 |
| 键值来源 | 解码器自身输入 | 编码器输出 |
| 位置上能不能省 | 不能，省了就是信息泄漏 | 不能，省了就没有对源句的聚焦 |

> **提示**：记忆办法是看“谁在算权重”。只有负责生成当前位置输出、又要防止看到未来词的那一层需要掩码；负责从编码器结果里挑重点的那一层只管算权重。编码器里那两个多头注意力子层都不需要掩码——编码器是同时看到整句的。

架构搭完、结构打印出来，模型还是一次都没跑过。这一讲只做一件事：把源序列和目标序列喂进去，把前向传播整条路走通，把输出形状打出来。

```text
本讲四步数据流
```

### 1. 构建输入数据

把上一讲的测试代码整段复制一份，向上挪一行，标题改成“Transformer 模型的前向测试”。

什么叫前向测试？就是从模型入口经过一路计算，一直到这里边算出结果。前向有了结果，往下是不是还能做别的事——比如“已经算出预测结果了，拿它跟真实值比一比、算损失，然后反向传播更新参数”，可不可以？可以。但再往下写就太多了，那部分留到后面聊——这一讲只带你把这套前向的东西整个模拟出来。

第一件事是构建测试输入数据，也就是源序列。我们前面反复说的那句假设今天不用再念了：两个句子，每个句子 4 个单词，这 4 个单词就是 4 个 token。

```python
src_x = torch.LongTensor([[1, 2, 3, 4],
                          [5, 6, 7, 8]])
```

`src_x` 是谁？它就是模型输入接口里收的那个源序列。`torch.long` 这个类型不是随便选的——词索引必须是整数，`LongTensor` 才能往词嵌入层里送。

想改数据完全可以，我把这句话提前说清楚：一改，你源码里标的那一套注释——`2`、`4`、`512`、`1000`——就都得跟着改。句子数变了、每句词数变了、掩码形状变了，全都要一起动。所以我这里就不再乱改了。

### 2. 构建目标序列

第二个动作是构建目标输入数据，也就是目标序列 `tgt_y`。

有可能俩句子都是 4 个单词，跟你源序列一样；也有可能不一样——比如源序列是 4 个词、目标序列换一组数。这里没有语义上的讲究，你自己想改成什么就改成什么。我这里是随手写的：

```python
tgt_y = torch.LongTensor([[3, 8, 6, 4],
                          [3, 8, 6, 2]])
```

> **提示**：源序列与目标序列的元素值本身在这个阶段不参与语义计算，它们只是词表下标。真正决定模型能不能跑通的是它们的形状——句子数、每句词数必须与掩码、与模型里的注释保持一致。

### 3. 掩码的初始化

第三个动作是初始化掩码。

```python
src_mask = torch.zeros((4, 4))
tgt_mask = src_mask
```

这里要记一句提醒：实际开发中掩码要根据序列长度动态生成。怎么动态？你 `len` 一下句子长度，是不是就知道那个数字是几了？把那个数扔进 `zeros` 里就行。语料里我们写死成 `(4, 4)` 只是为了方便，因为这一边 4 个词、那一边 4 个词；将来在项目里，就是把两个 `len` 的结果传进去，而不是写 `4`。

> **定义**：掩码（mask）是加在注意力打分上的一个同形状张量，用来屏蔽掉不该被看到的位置。全 0 的掩码表示不做任何屏蔽——这也是编码器侧掩码的常态。

`tgt_mask` 怎么来？跟上面一样，那还写什么——直接把 `src_mask` 赋给它就行。

听课的人当时就回答“复制一下”，这个反应是对的，但我要把话说完：**这一步只是学会了一个 `=`，别把它当成这一讲的全部收获。**真正的收获在后面——掩码为什么这么写、前向传播里谁在用它、以及那个多出来的字母。

### 4. 前向传播的调用与结果打印

第四个动作是执行前向传播。

先打一行华丽的分隔线，把输出跟上面打印的模型结构隔开：

```python
print('-' * 10, '前向传播的输入与输出', '-' * 10)

print('my_transformer 输出结果:', result)
print('输出结果的形状:', result.shape)
```

四样东西全扔进去：`src_x` 和 `tgt_y` 是数据，`src_mask` 和 `tgt_mask` 是给那两个注意力用的。

最后那两行打印里，最值得看的是形状。形状必然是一个三位张量，最后两维不早都已经写完了吗——`2 4 1000`：

```text
result.shape = (2, 4, 1000)
                │  │    └── 词表大小：每个位置对 1000 个词的打分
                │  └─────── 序列长度：每句 4 个 token
                └────────── 批大小：一次 2 句话
```

读图说明：三位分别是批大小、序列长度和词表规模；打印形状之所以能验证跑通，是因为这三个数字全都能从前面构造的数据和模型参数里推出来。

### 5. 维度不匹配与参数排查

第一次运行，跑挂了。报的是维度不匹配。

第一件事是别慌，也别改参——先确认传进去的东西对不对：`src_x`、`tgt_y`、`src_mask`、`tgt_mask` 四个都传了，`1 2 3 4` 那一组数据没错，两行句子的维度也是对的。

确定了输入没问题，就顺着模型往回捋。`my_transformer` 上面封装的是什么？就是 `Sequential(source_embedding, source_position)` 加上 `my_encoder`，然后是 `decoder`、输出层。往前传的时候，参数得一个一个去查：

```text
① 词嵌入：1000, 512
② 多头注意力：head = 8, d_model = 512
③ 解码器第一个注意力：与编码器同构，是拷贝
④ 解码器第二个注意力：同时用到解码器自身与编码器输出
⑤ 前馈：d_model = 512
⑥ 解码器整体与 generator 的输出维度
```

每一环都对得上，那就说明问题不在参数维度上。这类“参数全对却报维度不对”的情况，往往不是数值错，而是**在错误的地方取了值**——也就是下面那个字母的问题。

> **易错点**：维度不匹配有两种成因。一种是参数配错，一种是把某个对象、某个方法、某个张量搞混了。前者靠查参数、查注释解决，后者靠查“这行代码调用的到底是谁”解决。看到形状报错时，先分清属于哪一种，能省掉半小时。

### 6. forward 里的多一个字母

去类里看 `forward` 那一段。写的时候是这样：

```python
# 下面这种写法会调到编码器对象，而不是编码动作
enc_output = self.encoder(src_x, src_mask)
dec_output = self.decoder(tgt_y, enc_output, src_mask, tgt_mask)
```

问题在这里——我们前面定义的两个函数叫什么名字？叫 `encode` 和 `decode`。你在前向传播里做回调的时候，是不是也得写 `encode` 和 `decode`？写 `encoder` 的话，它去调的是那个编码器**对象**。

按住 `Ctrl` 点一下名字就能看出来它跳到哪儿：它跳到的是传进来的那个编码器对象，调的是对象自己的 `forward`；而这里需要的是回调我们自己写的处理函数、拿到编码器的**结果**往后传。所以要写的是 `self.encode`，不是 `self.encoder`。编码器处理动作里已经封装了编码器的动作，所以不能调编码器，得调“编码”这个动作。

> **结论**：`self.encode` 是我们自己写的前向接口方法，产出编码结果；`self.encoder` 是编码器组件，是个对象。名字只差一个 `r`，语义差一整层。这个 `r` 一删，`self.decode` 同样的处理，回调就通了——先调编码，再调解码。

改对之后的处理链路是这样的：

```text
my_transformer(src_x, tgt_y, src_mask, tgt_mask)
        │
        ├── self.encode()   ← 回调我们写的编码方法
        │       └── 内部走 src_embed（词嵌入 + 位置编码）→ 6 层编码器 → norm
        │
        └── self.decode(记忆向量)
                └── 内部走 tgt_embed → 6 层解码器 → norm → generator
```

读图说明：前向传播只负责把两个回调串起来，真正的组件堆叠都在 `encode` 与 `decode` 内部完成——这就是接口分层的作用。

### 7. AI 代写代码与接口分层

最后那句提醒我要重重说一遍：现在写代码，**你太相信 AI 给你生成的东西了**。它给你来一个 `self.encoder`，你看着名字顺眼就留下了，结果调的是组件而不是动作。

这属于最容易混的一类错误，因为它在语法上完全合法——`self.encoder` 存在，也能被调用，只是返回的东西不是你要的。运行时只用形状不匹配这一个信号告诉你。

> **注意**：凡是被调用的一方名字与被调用意图只差一个词（`encode` / `encoder`、`decode` / `decoder`），写完都要回头按 `Ctrl` 点一次确认跳转位置。这类错误编译器不会帮你抓。

反过来看，这也正好说明为什么接口要分层。我们的编码动作里封装了“输入处理链 + 6 层编码器 + 规范化”这一整套流程，外部只看到一个 `encode`。将来要换组件、换规模，改的是 `encode` 内部，外面那句调用一个字都不用动。这就是“每个组件分发的其实很细致”带来的好处。

### 9. Encoder-Decoder 的实现过程与一个拷问

把这一讲的动手过程往上收一层看，`Encoder-Decoder` 的实现过程就是：先把四部分构建出来，最后做一次拼接。所以真正的关键从来不在“拼”这一下，而在“四部分各自稳不稳”。

收尾的地方抛给我们一个问题，值得停下来想：

> **问题**：词嵌入层要不要深拷贝？为什么？

答案是要。因为编码器和解码器这两侧的词嵌入层是不一样的，不能共用一个对象。`Sequential` 那个位置不能图省事写成同一个对象；如果两侧共用一份参数，编码器与解码器的嵌入就会被互相牵动，这不是我们想要的结构。

所以这里要注意：两侧是各自独立的一份，不是深拷贝那种共享关系。

> **提示**：判断要不要独立一份的标准不是“长得一样不一样”，而是“将来要不要各自更新、各自变”。长得一样但需要各自演化，就必须分开。

### 10. 与论文的差异与代码组织原则

如果你去翻论文，会发现实现与论文在一些地方有出入。

最典型的一处：编码器 6 层，正常按论文的做法，编码器层输出的结果直接往后传就行了；我们的实现里在 6 层处理完之后**额外加了一次全局的规范化层**。解码器那边也是同样的处理。这就是与论文可能不一致的地方。

> **提示**：学术界与工业界的实现本来就会有一点点不一致，所以看论文的时候要活学活用。真纠结这一层，就把那一行代码删掉——其实就一行，删不删无所谓。

最后是一条写代码的长期原则：尽量做到高内聚、低耦合。

什么叫内聚？类自己独立处理问题的能力。什么叫耦合？类与类之间的关系。翻译成大白话就是：自己能完成的事就不要麻烦别人。高内聚，是尽量自己做；耦合，是有事就找别人。

耦合太强会怎样？父类一改动，子类就被动地跟着受影响。就像一个人身上背着案子，将来他的下一代考公、从政，是不是都会受到牵连——下一代还有选择吗？没有。这就是强耦合。

所以未来写代码一定是高内聚、低耦合。回头看这一讲写的这套模型：接口清晰，每个组件分发的职责很细，将来要扩展、要改造，无非是把这些组件重新组合和封装一次。
