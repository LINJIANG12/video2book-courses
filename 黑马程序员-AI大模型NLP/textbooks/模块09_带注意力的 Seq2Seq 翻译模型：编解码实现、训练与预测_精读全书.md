## Day06-09.英译法案例_构建基于GRU的编码器(掌握)
> 对应分集：P88 | 原始标题：《Day06-09.英译法案例_构建基于GRU的编码器(掌握)》

先把这一讲要落地的位置说清楚：我们现在啃的是 Seq2Seq（Sequence to Sequence，序列到序列）这个架构。既然是 Seq2Seq，那就意味着你不可能只做一半——左边的编码器要做，右边的解码器也得做，而且解码器还要做两个版本：一个不带注意力机制的，一个带注意力机制的。

所以光"构建模型"这件事，函数至少有三个。其实不是三个，是五个：编码器一个、无注意力解码器一个、带注意力解码器一个，写完还都得测——测试代码又是两个函数。我们一步一步来。

### 模型清单与本节任务

先把要交付的东西列出来，免得写着写着迷路。整个英译法案例里，模型侧一共五个函数：

| 序号 | 要写的东西 | 说明 |
| --- | --- | --- |
| 1 | 编码器 | 基于 GRU，本节要写的 |
| 2 | 无注意力（attention）解码器 | 注意力的第一个对照版本，只带一个上下文向量 $C$ |
| 3 | 带注意力解码器 | 对应 $C_1, C_2, C_3 \dots$ 逐位置变化的上下文向量 |
| 4 | 编码器测试 | 写完编码器立刻验证能不能跑通 |
| 5 | 解码器测试 | 同上 |

这一讲只做第 1 件：基于 GRU 的编码器。做完就先停，别急着往解码器冲——编码器能不能拼起来还没验过呢。

### 编码器的输入与输出

编码器这张图我不再另画一遍，因为我们前一天已经在桌面上画过了，重画一遍没有意义——把那张图打开，对着看就行。对着图，先用眼睛扫一遍：这里面应该有哪些东西？

- `input`：本次的输入。
- `previous_hidden`：上一时刻的隐藏状态。
- 中间是一个很眼熟的角色：词嵌入层（embedding层）。
- 然后是 GRU，它给出 `output`（本次的输出）和 `hidden`（本次的隐藏状态）。

设问一下：你本次输入的，肯定得是一个单词吧？把单词交给 GRU，GRU 就吐出一个输出。而这一套东西——`input` 进来、过一个词嵌入层、再进 RNN/GRU 出 `output` 和 `hidden`——跟我们前面讲 RNN 时玩的操作是不是一模一样？是。所以这一节真的不算难，`so easy`，不难受。

图里的颜色分工也要认准，它对应代码里的两类东西：

- 橙色（也就是黄色那一片）：张量。
- 蓝色：网络层。具体就是 `nn.Embedding` 和 `nn.GRU` 这两个。

```text
   input（单词索引）        previous_hidden
        |                        |
        v                        |
   +-------------+               |
   | nn.Embedding|  <- 蓝色：网络层
   +-------------+               |
        |                        |
        v                        v
   [ 词向量张量 ]  --------->  +-----------+
     橙色：张量                |  nn.GRU   |  <- 蓝色：网络层
                               +-----------+
                                 |       |
                                 v       v
                              output   hidden
                             （本次输出）（本次隐藏状态）
```

读图说明：橙色节点是数据（张量），蓝色方块是带有可学习参数的神经网络层；一行英文单词索引先被词嵌入层翻成词向量，再和上一时刻的隐藏状态一起送进 GRU，得到本次的输出与新的隐藏状态。

> **定义**：编码器（encoder）在这里就是一个"把整句源语言压成一个定长语义表示"的网络模块。在这个例子里，它的输出 `output` 是每个时间步的隐藏状态堆叠，`hidden` 是最后一个时间步的隐藏状态，也是后面要交给解码器的那个"中间语义向量"的载体。

#### EncoderRNN 类的三步骨架

按代码推进的顺序，先定类名：`EncoderRNN`，继承 `nn.Module`。这个类的骨架就三步：

1. `__init__`：初始化两个东西——词嵌入层和 GRU 层。
2. `forward`：前向传播。
3. 初始化隐藏状态（`initHidden`）。

> **易错点**：为什么是两层网络而不是四层五层？因为左边这个编码器里就只有两个层要实例化。看到"层"字先问一句"谁的层"，别条件反射地凑数。

#### init 里的两个层与三类参数

`__init__` 要接收 `input_size` 和 `hidden_size` 两个入参。

`input_size` 是编码器**词嵌入层的输入维度，也就是词汇表的大小**。这个词表大小我们前面已经算出来了——2803（英语侧词表）。别看到 2803 这个数字就以为是随便写的，它就是英文单词（严格说是词元）的总数。

`hidden_size` 是**隐藏层的维度**，128、256 都行，这里我们定 256。

> **提示**：`hidden_size` 和"层数"是两个东西。第 1 个参传 256，意思是"每个词用 256 个数字表示"；后面 GRU 的第 1 个参也传 256，意思是"输入特征维度是 256"；而层数是 `num_layers`，这里等于 1。数值一样，含义不一样——这是最容易混的地方。

`__init__` 里按顺序做四件事：

```python
import torch
import torch.nn as nn


class EncoderRNN(nn.Module):
    def __init__(self, input_size, hidden_size):
        # 初始化父类成员
        super(EncoderRNN, self).__init__()
        # 保存输入参数
        self.input_size = input_size   # 词嵌入层的输入维度，即词汇表的大小
        self.hidden_size = hidden_size  # 隐藏层维度 / 词嵌入维度

        # 词嵌入层：把单词索引转成词向量
        self.embedding = nn.Embedding(input_size, hidden_size)

        # GRU 层：输入特征维度 256，隐藏层维度 256
        self.gru = nn.GRU(hidden_size, hidden_size, batch_first=True)
```

四步分别是：`super()` 初始化父类成员；把 `input_size`、`hidden_size` 保存到 `self` 上；实例化 `nn.Embedding(input_size, hidden_size)`；实例化 `nn.GRU(hidden_size, hidden_size, batch_first=True)`。

`nn.Embedding` 的两个参数，意思完全不同：第 1 个是查表的总行数，也就是词汇表大小 2803；第 2 个是每一行有多少个数字，也就是词向量维度 256。查完表之后，一个编号就变成 256 个浮点数。

`nn.GRU` 的第 1 个参是输入的特征维度，我们喂进去的是 256 维词向量，所以传 `hidden_size`；第 2 个参是隐藏层维度，也传 `hidden_size`。这两个 256 数值相同但含义不同——前者描述"进来的东西有多宽"，后者描述"记住的状态有多宽"。

#### batch_first 与三维批数据格式

`batch_first=True` 的作用是**把批次维度设为第 1 个维度**，即数据格式为 `(batch_size, sequence_len, hidden_size)`。

不加 `batch_first=True` 时，PyTorch 默认的格式是 `(sequence_len, batch_size, hidden_size)`——句子长度在前、批次在后。加了之后，批次大小跑到最前面。

举个数就明白了：形状 `(2, 3, 256)` 的意思是"我给你两个句子，每个句子有三个单词，每个单词用 256 维词向量表示"。如果是 `(3, 5, 256)`，就是"三句话，每句话 5 个词，每词 256 维"。先批次、再句子、再词向量——顺序记住，后面所有形状推断都靠它。

#### forward 的两步与形状推算

`forward` 要传两个东西进来：本次输入和上一时刻的隐藏状态。参数名写成什么随你，`x` 也行，`input`/`hidden` 也行，但心里得清楚谁是谁——不会的话就把当初讲 RNN 时那张 12 个参数的图调出来，刻在脑子里，写代码时逐参对照。

- `input`：输入的单词索引序列，`(batch_size, sequence_len)`。比如之前见过的 `(1, 6)`：一个句子、句子里有 6 个单词。
- `hidden`：初始的隐藏状态，形状 `(num_layers, batch_size, hidden_size)`,这里就是 `(1, 1, 256)`：1 层、1 批、256 维。

第一步，过词嵌入层：

```python
    def forward(self, input, hidden):
        # 1. 词嵌入层：将单词索引序列转换为词向量
        output = self.embedding(input)   # (1, 6) -> (1, 6, 256)
        # 2. GRU 层处理，返回 GRU 层输出与最终隐藏状态
        output, hidden = self.gru(output, hidden)
        return output, hidden
```

`self.embedding(input)` 把 `(1, 6)` 的形状变成 `(1, 6, 256)`：6 个编号，每个编号换成 256 个数字。这是形状上唯一一次"升维"。

第二步交给 GRU。这里两个参数别搞混：`hidden` 是上面传进来的；`output` 要特别注意——它指的是上面 `embedding` 那个 `output`，也就是词向量张量，不是别的东西。所以 GRU 的两个入参是"本时刻的词向量"和"上一时刻的隐藏状态"。

出来之后把结果重新赋给 `output` 和 `hidden`，等于用旧 `output` 和旧 `hidden` 算出新的 `output` 和新的 `hidden`，省得外面再单独访问一次。这个写法跟前面讲 RNN 时完全一致。

**形状结算**（还是拿 `(1, 6)` 举例）：

| 张量 | 形状 | 含义 |
| --- | --- | --- |
| `input` | `(1, 6)` | 一个句子，6 个单词索引 |
| embedding 输出（即 GRU 的输入） | `(1, 6, 256)` | 6 个词向量，每个 256 维 |
| GRU 输出 `output` | `(1, 6, 256)` | 每个时间步一个 256 维输出 |
| GRU 隐藏状态 `hidden` | `(1, 1, 256)` | 1 层、1 批、256 维 |

> **结论**：`output` 的序列长度跟着输入句子的长度走，`hidden` 永远钉在 `(num_layers, batch_size, hidden_size)`。前面是"随句长变"，后面是"被参数定死"——记住这一条，后面看打印结果时就不会自己吓自己。

#### 初始化隐藏状态

第三个动作是初始化隐藏状态，也就是把一开始那个 $h_0$ 技术性地初始化一下。

要造的是全零张量，形状 `(num_layers, batch_size, hidden_size)`，这里即 `(1, 1, 256)`。另外还要处理设备问题：`device` 的意思是把你这个张量迁移到 CUDA 环境里去。如果整个模型在 CPU 上跑，这一步用默认设备就是对的；要用 GPU，初始隐藏状态也必须跟模型在同一块卡上。

```python
    def initHidden(self, batch_size, device):
        # 初始化隐藏状态 h0：形状 (num_layers, batch_size, hidden_size) = (1, 1, 256)
        return torch.zeros(1, batch_size, self.hidden_size, device=device)
```

> **易错点**：初始隐藏状态造在 CPU 上、模型搬到 GPU 上，是最典型的"形状全对但一跑就报设备不一致"的错误。谁造张量，谁负责指定 `device`。

到这里，编码器的三个动作齐了：初始化网络层、前向传播、初始化隐藏状态。图 6 这一步——"构建基于 GRU 的编码器"——交付完毕。

## Day06-10.英译法案例_测试基于GRU的编码器(理解)
> 对应分集：P89 | 原始标题：《Day06-10.英译法案例_测试基于GRU的编码器(理解)》

把编码器的代码写完，就放在那儿不管它，风险是很实在的：形状写错、批次维度搞反、隐藏状态没初始化，这些错误都不会在定义类的时候报出来，只会等到你真正喂进去一批数据才炸。所以写测试这件事不能省——这讲我们就给刚做好的编码器写一段测试代码，把"能不能拼得起来"这件事验掉。

思路其实不复杂，一行一行顺着往下写就行。

### 测试函数的前置准备

`Ctrl` 切进 PyCharm，先定义函数，名字就叫 `test_encoder`。这个函数负责"测试基于 GRU 的编码器"。

#### 第一步：获取数据集加载器对象

```python
    # 1. 获取数据集加载器对象
```

#### 第二步：编码器参数

```python
    # 2. 初始化编码器参数
    vocab_size = 2803   # 英文词汇表大小
    hidden_size = 256   # 隐藏层维度
```

`vocab_size = 2803` 就是英文词表的大小——2803 个英语单词（词元）。这个数和构建编码器时 `nn.Embedding` 的第 1 个参数是同一个东西。

名字里写 `RNN` 还是 `GRU` 都行，随你。叫 `encoder_gru` 更贴切一点，因为里面实例化的是 `nn.GRU`，不是 `nn.RNN`。


`x` 是英文侧输入，`y` 是法语侧目标。下面所有的 `5.x` 都写在这个循环体里面。

### 打印输入索引张量与形状

```python
        # 5.1 打印输入英文句子的索引张量和形状
        print("x.shape:", x.shape, "x:", x)
        break
```

跑起来之后打出来的东西大概是这个样子的：

```text
x.shape: torch.Size([1, 6]) x: tensor([[  14,   15,   42,   43,  139,  888,    1]])
```

`torch.Size([1, 6])` 是 1 批次、句长 6。后面那串数字是单词索引。

这里有个值得停一下的地方：**为什么最后一个数永远是 1？**

因为 1 就是 `EOS`（End of Sequence，序列结束标记）。还记得我们做数据处理时定的规矩吗——句子的开头是 0，结束是 1。所以无论前面的索引是多少、句子有多长，最后一个位置必定是 1，前面那些是什么我们不知道，得跑出来看。

实测也是这样：翻到任何一批，`(1, 6)` 的最后一个是 1，`(1, 9)` 的最后一个是 1，`(1, 3)`、`(1, 5)` 的最后一个是 1。前几个索引是正常的词，最后一个一定是结束标记。

> **提示**：`break` 只是让循环先跑一批、看一组结果，方便讲解。实际开发里千万不要这么写——遍历数据加载器时随手加 `break` 会把训练数据截断，这种代码进不了正式流程。

### 获取编码器的初始隐藏状态

```python
        # 5.2 获取编码器的初始隐藏状态
        h0 = my_encoder_gru.initHidden(x.size(0), device)
```

这里传进去的批次大小要从 `x` 上取，不能写死——换个批次大小形状就对不上了。同时设备也要按上一步的 `device` 指定，模型在哪块设备上，$h_0$ 就造在哪块设备上。

形状是 `(1, 1, 256)`：1 层、1 批、256 维。

### 执行前向传播

```python
        # 5.3 执行前向传播
        output, hidden = my_encoder_gru(x, h0)
```

编码器必须先算完，往后一步步算下去，才会得到中间语义向量 $c$。也就是说，编码器算完才能轮到解码器那一坨，顺序不能颠倒。

### 打印输出结果形状

```python
        # 5.4 打印输出结果形状
        print("output.shape:", output.shape)
```

这里只打形状，不打内容——内容肯定是一坨数字，看了也没用。

问题来了：`output` 应该是 `(1, 6, 256)` 吗？**不一定。**

你输入的是英文句子 `(1, 6)`，输出是 GRU 处理完之后对应的东西，所以句长那一位会跟着输入走。输入如果是 `(1, 9)`，输出就是 `(1, 9, 256)`；输入 `(1, 5)`，输出就是 `(1, 5, 256)`。所以这个位置的第二个数不固定。

但最后一位的 256 是钉死的——词向量/隐藏状态就是 256 维。

### 打印隐藏状态形状

```python
        # 5.5 打印隐藏状态形状
        print("hidden.shape:", hidden.shape)
```

这个形状一定能确定死：`torch.Size([1, 1, 256])`。因为隐藏状态就是 1 层、1 批、256 维。

```text
循环体内部的数据流向与形状变化：

  x (1, L)                    h0 (1, 1, 256)
     |                              |
     v                              |
  [ 编码器 EncoderRNN ]  <----------+
     |                              |
     +-- output (1, L, 256)         +-- hidden (1, 1, 256)
         句长随输入走                   形状恒定，被参数钉死
```

读图说明：批次维度恒为 1，`output` 的第二维等于输入句子的长度 $L$（可变），`hidden` 的第三维等于 `hidden_size`（恒为 256）；`hidden` 的三个维度由 `num_layers`、`batch_size`、`hidden_size` 共同决定，与句长无关。

### 输出长度与输入长度看似不一致的原因

前面留了一个坑，这里补上：有时候你会发现打印出来的 `x` 是 `(1, 6)`，但 `output` 却是 `(1, 7, 256)`；下一次跑又变成 `x` 是 `(1, 10)`、`output` 是 `(1, 8, 256)`。看起来像是编码器算错了。其实不是，原因在 `get_data_loader` 里面。

回头看那个函数，里面做了一件"仅显示一批"的事：它在创建加载器的过程中已经随机拿过一行数据并打印出来了。这个打印是随机的，取的是第一条。

现在回到测试函数：我们调 `get_data_loader()`，把它的返回值赋给 `my_dataloader`。也就是说，**函数内部那次随机取样消耗掉了一批，我们在 `for` 循环里遍历时再拿到的，是另一批随机的数据**。

于是上面那个 `x`（函数内部打印的那条）和我们循环里真正喂进编码器的 `x`，根本不是同一批。你把两个不同批次的形状放在一起比，当然对不上：

- 函数内部打印的 `x` 是 `(1, 9)`，循环里拿到的 `x` 是 `(1, 8)`，`output` 就是 `(1, 8, 256)`；
- 函数内部打印的 `x` 是 `(1, 6)`，循环里拿到的是 `(1, 7)`，`output` 就是 `(1, 7, 256)`。

所以结论很简单：**不应该看上面那条随机样本，应该看循环里实际喂进去的那一批。** 把函数内部那次打印注释掉，这个"干扰"就消失了——那时候你会看到 `x` 是 `(1, 6)`，`output` 就必定是 `(1, 6, 256)`；`x` 是 `(1, 9)`，`output` 就必定是 `(1, 9, 256)`。

> **易错点**：`x` 和 `y` 这一对也是同类陷阱。`x` 的句长是固定长度的**英语**句子长度，`y` 的句长是**法语**句子的长度，两者本来就可以不一样。所以别拿 `x` 的长度去要求 `y`，也别拿上一批的形状去要求这一批。

把上面那次随机打印注释掉之后，`for` 循环里其实就只剩一个 `break`，这个循环也就没有意义了——加载器每次只取一批，而且是随机取的一批。直接顺序执行一遍就行。

### 多批实测

把上面的干扰清掉之后，反复右键运行几次，看到的序列是稳定的：

| 输入 `x` 形状 | 输出 `output` 形状 | 隐藏状态 `hidden` 形状 |
| --- | --- | --- |
| `(1, 6)` | `(1, 6, 256)` | `(1, 1, 256)` |
| `(1, 9)` | `(1, 9, 256)` | `(1, 1, 256)` |
| `(1, 5)` | `(1, 5, 256)` | `(1, 1, 256)` |
| `(1, 8)` | `(1, 8, 256)` | `(1, 1, 256)` |

一眼看得出规律：给进去的是"1 批次、一句英语、$L$ 个单词"，拿回来的就是"1 批次、$L$ 个时间步、256 维"，最后那 256 就是一层隐藏状态的维度。

> **结论**：`output` 的第 2 维 100% 等于输入句子的长度，`hidden` 的三个维度恒为 `(1, 1, 256)`。只要这两条同时成立，编码器的实现就是自洽的。

### 测试的意义

这段代码能跑通，说明一件事：前面构建的那个基于 GRU 的编码器没有问题。

再往下说一句：**测试里那个字符长度、那个 `break`，其实都可以不写**。因为它们的作用只是验证第 6 步写出来的东西对不对。现在能正常出结果，而且和我们预想的形状完全一致，那就说明编码器这一层是通的。

> **提示**：这一讲没有留练习或课后作业，测试跑通的截图就是本讲的验收标准。到这里编码器的测试就结束了，下一步才是给它配上解码器。

## Day06-11.英译法案例_基于GRU的无Attention的解码器_思路分析(理解)
> 对应分集：P90 | 原始标题：《Day06-11.英译法案例_基于GRU的无Attention的解码器_思路分析(理解)》

编码器那一段收工之后，轮到右边了。这一节要拿下的，是解码器的第一个版本——不带注意力机制的那个。

先提醒一句：解码器这张图上并没有标出每个参数到底是谁对谁，所以别指望照抄，得我们自己把每个位置的名字、每个形状的含义写上去。后面才是具体的代码实现，这一节要做的就是把思路和形状推清楚。

### 图上的颜色约定与输入

先把颜色的约定捡回来，看图的时候靠它分辨"这是数据还是层"：

- 橙色（前面几讲里我一直说成黄色那一片）：向量，也就是张量；
- 蓝色：网络层，也就是神经网络层；
- 绿色：新出现的这一类，是运算/激活这些处理动作。

进图的入口有两个：

- `input`：本次的输入；
- `previous_hidden`：上一时刻的隐藏状态。这个隐藏状态是编码器那边传过来的，还是别的来源，都无所谓——它和 GRU 里的隐藏状态是同一种东西。

> **定义**：这里的"无注意力"指的是解码器只从编码器拿一个固定的中间语义向量 $C$（就是编码器最后一个时间步的隐藏状态），每生成一个法语词都看这同一个 $C$，不存在逐位置变化的 $C_1, C_2, C_3 \dots$。

### 本次输入的形状：为什么是 1×1

关键的问题来了：`input` 进来的时候应该是几个？

> **结论**：解码器的 `input` 是 `(1, 1)`——1 批次、1 个词。

为什么不是 `(1, 6)` 这种整句？因为解码器是**一次只处理一个时间步、只吃一个词**的：它拿"上一个词 + 上一时刻隐藏状态"算"下一个词"，然后把算出来的词当输入再算下一个，一个词一个词地滚下去。整句是一步一步喂进去的，不是一口气塞进去。

### 词嵌入层

`(1, 1)` 进来先过词嵌入层（embedding层）。这个层我们前面说过很多次了：它把索引转成词向量。

进去是 `(1, 1)`，出来必然带上词向量维度：`(1, 1, 256)`。词向量是 256 维，所以形状就在最后一维多出个 256——每个词用 256 个数字表示。

### ReLU 激活

词嵌入之后是一个 `ReLU`（Rectified Linear Unit，修正线性单元）激活函数。

设问一下：激活函数会不会改变形状？不会。`ReLU` 是逐元素做值的映射（把负数压成 0、正数原样保留），它改的是数值，不是结构。所以这里走到哪一步形状都不动：进 `(1, 1, 256)`，出还是 `(1, 1, 256)`。

### 与上一时刻隐藏状态的合并

另一条支路是 `previous_hidden`，形状 `(1, 1, 256)`——1 层、1 批、256 维。

它和当前这一步的表示一起送进 GRU。两个 `(1, 1, 256)` 合起来处理，出来的 `hidden` 依然是 `(1, 1, 256)`：编码器那边也一样，隐藏状态的三个维度由层数、批次、隐藏层维度决定，跟句长没关系，所以它恒定不变。

输出的 `out` 同样还是 `(1, 1, 256)`。

> **易错点**：`out` 是**本次的输出**，不是输入；上面那个 `input` 才是本次的输入。这两个名字在同一张图上，看错一个整条链就串了。

```text
无注意力解码器单步数据流（括号内为形状）：

  input (1, 1)                 previous_hidden (1, 1, 256)
      |                                  |
      v                                  |
  [ nn.Embedding ]  蓝色：网络层          |
      |                                  |
      v                                  |
  out (1, 1, 256)  橙色：向量             |
      |                                  |
      v                                  |
  [ ReLU ]          绿色：激活，形状不变   |
      |                                  |
      v                                  |
  out (1, 1, 256)                        |
      |                                  |
      +---------------> [ nn.GRU ] <------+
                            |
              +-------------+-------------+
              |                           |
              v                           v
        out (1, 1, 256)            hidden (1, 1, 256)
              |
              v
        [ softmax ]  映射成概率
              |
              v
        法语词表 4345 维上的概率分布 -> 取概率最高的那个词
```

读图说明：解码器一个时间步只吃一个词，词先过嵌入层升到 256 维，过激活函数保持形状不变，再和上一时刻的隐藏状态一起送进 GRU；GRU 输出的 256 维向量经 `softmax` 映射成法语词表上的概率分布，概率最高的那个词就是这一步生成的结果，同时新的隐藏状态往下传。

### softmax 与输出词表

最后一个问题是：`out` 是 `(1, 1, 256)`，经过 `softmax` 之后会变成多少？

`softmax` 的职责是**把数值映射成概率**。所以它把 256 维的表示投射到词表维度上，得到的是 4345 维——法语词表的大小。

> **易错点**：这里容易顺手写 2803。2803 是**英语**单词的数量，也就是编码器侧词表的规模；解码器要产出的是**法语**，法语词表是 4345。数字别背错，345 没有别的数——就是 4345。

于是这一步的含义就清楚了：把刚才那个 256 维的词表示，映射成"在 4345 个法语词里，每个词有多大概率"这样的分布。

最终 `output` 输出的是什么？**一个词**——4345 个词里的某一个。我们并不知道是哪一个，所以取的是这里面概率最高的那个词。概率最高的那一个，就是这一步生成的那个词。

### 这一版解码器的定位

把整条链串一遍：输入一个词 → 词嵌入层转成 256 维词向量 → `ReLU` 激活 → 与上一时刻隐藏状态一起进 GRU → 得到本次输出和新的隐藏状态 → `softmax` 映射到 4345 个法语词上的概率 → 取概率最高的词。

也就是说，解码器靠着 GRU 这一套处理，一步步把法语词生成出来。

> **结论**：这一版解码器记作"无 attention（无注意力）"版本。它和后面要做的注意力版本只差一件事——上下文向量的取法：无注意力版全程只用编码器传过来的那一个隐藏状态；注意力版则会逐位置拿到 $C_1, C_2, C_3 \dots$。

接下来写代码的时候，参数的流转和形状的变换就完全按这张图来：每个环节的输入形状、输出形状、谁是层谁是张量，图上都已经标死了。

## Day06-12.英译法案例_构建基于GRU解码器(无Attention)(掌握)
> 对应分集：P91 | 原始标题：《Day06-12.英译法案例_构建基于GRU解码器(无Attention)(掌握)》

上一步我们已经把无 Attention 解码器的思路捋完了，思路清楚了，接下来就是把它落到代码上。我先给结论：这个 `DecoderRNN` 里没有一行是新的——词嵌入、GRU、线性层、激活、LogSoftmax，全是我们前面反复用过的老面孔。真正要盯住的只有一件事：**每一个位置上的张量形状是多少，以及为什么必须是这个形状**。形状对了，代码就写完了；形状对不上，模型连跑都跑不起来。

---

### 类的命名与两个构造参数

类名叫 `DecoderRNN`。这里有个很容易被问到的地方：明明是 GRU，为什么名字里还是 `RNN`？因为 GRU 本身就是 RNN 的一类变体架构，构架形式是同一套——**沿着时间步递推、把信息压在隐藏状态里往下传**。所以 `DecoderRNN` 这个名字不算错，它说明的是"这是一个 RNN 家族的解码器"。

`__init__` 只收两个参数：

| 参数 | 含义 | 本案例取值 |
| --- | --- | --- |
| `output_size` | 解码器输出维度，即目标语言（法语）词汇表大小 | 4345 |
| `hidden_size` | 解码器隐藏层维度，即每个词向量的特征数 | 256 |

`hidden_size` 到底是多少，`__init__` 里根本不用猜——后面一定会传 256 进来，这一点和编码器完全一致。

剩下的层按顺序实例化：词嵌入层、GRU、输出线性层。GRU 的两个维度都写 `hidden_size`：

```python
self.gru = nn.GRU(hidden_size, hidden_size)
```

为什么输入 256、输出也 256？因为上一层（词嵌入）交出来的词向量就是 256 维，而这一层要交出去的隐藏状态同样是 256 维，**进来的和出去的维度一致，所以写两次 256**。

`self.out` 是那个负责降维/升维到词表大小的线性层，也就是结构图里标的 `out`；`self.embedding` 就是结构图里的 `embedding` 层。

---

### 各层维度与数据流

先看这张形状推导图。左侧是每一步的**输入**形状，右侧是**输出**形状：

```text
输入 (batch=1, seq_len)                  ← 一个批次一条数据，句子里若干词索引
        │
        ▼
   embedding(4345 → 256)
        │
输出 (1, seq_len, 256)                   ← seq_len 个词，每个词 256 维
        │
        ▼
   gru(256 → 256)  +  上一次隐藏状态 (1, 1, 256)
        │                    │
        ▼                    ▼
   output (1, seq_len, 256)   hidden (1, 1, 256)
        │
        ▼
   out: Linear(256 → 4345)
        │
输出 (1, seq_len, 4345)                  ← 每个位置对 4345 个法语词打分
        │
        ▼
   LogSoftmax(dim=-1) → 取概率最大的那个词 → 一个词
```

读图说明：输入是二维的词索引张量，词嵌入把它变成三维 `(batch, seq_len, hidden)`；GRU 吃这个三维张量，同时收下上一次的隐藏状态，吐出两个东西——每个时间步的输出和最后一步的隐藏状态；线性层把 256 维映射到 4345 维；Softmax 不改变形状，只把值变成概率分布，最后在这个分布里挑概率最高的一个词作为结果。

具体到数值：`seq_len=1` 时，`(1, 1)` → `(1, 1, 256)`；`seq_len=6` 时，`(1, 6)` → `(1, 6, 256)`；`seq_len=7` 时，`(1, 7)` → `(1, 7, 256)`。一句话有几个词，中间那一维就是几。为了讲解省事，后面统一用"一批一条、一条一个词"的 `(1, 1)` 举例。

#### out 线性层前后的形状标注

这里有一个必须较真的地方。结构图上把 `out` 线段的输入标成 `(1, 1, 256)`、输出也标成 `(1, 1, 256)`，其实标错了一半。

`(1, 1, 256)` 是 `out` 的**输入**：它是 GRU 处理完之后原样交出来的隐藏信息，形状没变。但 `out` 处理完之后的**输出**，绝对不再是 256——256 维根本映射不出一个词，**Softmax 也不会改变形状，它只管把值变成概率**。所以 `out` 的输出应该是 `(1, 1, 4345)`。

`(1, 1, 4345)` 才是它真正的输出形状，把它写在 `out` 线段的上方才对：上面一行是 `(1, 1, 256)`（输入），下面一行是 `(1, 1, 4345)`（输出）。这 4345 个值就是这个位置上对 4345 个法语单词的打分，进 Softmax 变成概率，挑最大的那个作为预测词。

> **易错点**：全连接层按理只能吃二维输入，但这里传进去的是 `(1, 1, 256)` 三维张量，为什么没报错？PyTorch 会**自动降维**——它把 `(1, 1, 256)` 内部处理成 `(1, 256)` 做矩阵乘法，算完再还原回去。所以你写代码时看到"输入 `(1, 1, 256)`、输出 `(1, 1, 4345)`"不必惊讶，这是框架替你兜住了。

#### GRU 的输入与双输出

GRU 那一步，左边是两个进项：本次输入 `(1, 1, 256)`（步内是 `(1, 256)`）和上次隐藏状态 `(1, 1, 256)`。出来也是两个：

- 本次输出（output）：`(1, 1, 256)`；
- 本次隐藏状态（hidden）：`(1, 1, 256)`。

`(1, 1, 256)` 和 `(1, 256)` 在这里其实是同一个东西的两种看法，别被这个区别绕晕。

---

### LogSoftmax 与损失函数的配对

走到线性层下面，会看到一个 `LogSoftmax`。第一反应通常是：为什么不直接 Softmax？

因为多分类交叉熵损失函数本身是拆开的两步：

$$\text{CrossEntropyLoss} = \text{LogSoftmax} + \text{NLLLoss}$$

**如果你的损失直接用 `CrossEntropyLoss`，网络里就根本不需要写这一层**——它内部已经把 log 对数算进去了。

> **结论**：网络里写了 `LogSoftmax`，后面的损失函数就只能用 `NLLLoss`；如果网络里不写、直接输出 logits，后面才用 `CrossEntropyLoss`。两者绝不能同时出现：LogSoftmax 已经求过一次对数，再用 CrossEntropyLoss 会让它**在内部再求一次对数**，结果就不准了。

本案例用的是 `LogSoftmax`，所以后面接 `NLLLoss`。

---

### 解码器代码的逐步实现

#### `__init__` 与父类初始化

第一步照旧初始化父类信息：

```python
super().__init__()
```

第二步保存输入参数：

```python
self.output_size = output_size
self.hidden_size = hidden_size
```

#### 词嵌入层

```python
self.embedding = nn.Embedding(output_size, hidden_size)
```

两个参数分别对应：第一个 `output_size`（4345）是词表大小，第二个 `hidden_size`（256）是每个词要转成的向量维度。

这里要重新过一遍输入的 `(1, 1)` 是什么意思：中间这个维度一直是 `batch_size, seq_len`。第一个 1 表示**一批一个句子**；第二个 1 表示**这个句子有一个单词**。写成 `(1, 6)` 就是"一批一个句子，句子六个单词"。所以：

- 给 `(1, 1)`，`embedding` 还给 `(1, 1, 256)`；
- 给 `(1, 6)`，还给 `(1, 6, 256)`。

数据在解码器里长什么样呢？因为翻译是一步吐一个词，解码器每次的输入就是一个词，所以典型形状就是 `(1, 1)` → `(1, 1, 256)`。

#### GRU 层与 `batch_first`

```python
self.gru = nn.GRU(hidden_size, hidden_size, batch_first=True)
```

`batch_first=True` 是把批次维度提到最前面的开关。默认情况下（`batch_first=False`），张量排布是"先序列长度、再批次大小、再词向量维度"；打开这个开关之后，批次放到最前面，变成"**批次大小 → 序列长度 → 词向量维度**"。

> **提示**：`(3, 5)` 在 `batch_first=True` 下的含义是"一批三个句子，每个句子长度 5"。这个开关开不开都行，但一旦开了，后面所有打印出来的形状都要按这个顺序读，不然很容易把 `batch` 和 `seq_len` 认反。

#### 线性层

```python
self.out = nn.Linear(hidden_size, output_size)
```

输入维度就是上面 GRU 的输出维度 `hidden_size`（256），输出维度就是 `output_size`（4345，从 `__init__` 的第一个参数来的）。这一层干的事，就是把 256 维的词向量映射成 4345 个法语词的打分。

#### LogSoftmax 层

```python
self.softmax = nn.LogSoftmax(dim=-1)
```

`dim=-1` 表示在**最后一维**（也就是 4345 那一维）上做归一化，把打分变成对数概率分布。

#### 前向传播

```python
def forward(self, input, hidden):
    # 1. 词向量处理
    output = self.embedding(input)

    # 2. ReLU 激活
    output = F.relu(output)

    # 3. GRU 层处理
    output, hidden = self.gru(output, hidden)

    # 4. 线性层与 LogSoftmax 处理
    output = self.softmax(self.out(output))

    # 5. 返回结果
    return output, hidden
```

逐段看。

**词向量处理**：`output = self.embedding(input)`，输入 `(1, 1)`，得到 `(1, 1, 256)`。

**ReLU 激活**：词嵌入后面接一个 ReLU，这一步只是把值过滤一遍，形状不变。

**GRU 处理**：`output, hidden = self.gru(output, hidden)`——这一行和写编码器时一模一样。GRU 输出仍然是三维的 `(1, seq_len, 256)`，隐藏状态还是 `(1, 1, 256)`。

**线性层与 Softmax**：注意这里的写法是 `self.softmax(self.out(output))`，**Softmax 在外面，线性层在里面先跑**。`self.out` 收下 GRU 交出来的三维张量，输出的仍是一个三维张量：

```text
output (1, seq_len, 256)  ─ Linear(256 → 4345) ─►  (1, seq_len, 4345)
```

读图说明：线性层只替换最后一维——把 256 换成 4345，前面两维原样不动。所以 `seq_len=1` 时输入是 `(1, 1, 256)`、出来是 `(1, 1, 4345)`。接着 `LogSoftmax(dim=-1)` 在 4345 这一维上做归一化，把这 4345 个打分变成对数概率，形状不变。

**返回**：`return output, hidden`，把输出和隐藏状态一起交出去。

#### 初始化隐藏状态

还差一个初始化隐藏状态的函数：

```python
def initHidden(self, device):
    return torch.zeros(1, 1, self.hidden_size, device=device)
```

`(1, 1, self.hidden_size)` 即 `(1, 1, 256)`，对应"一批一个句子 + 一层 GRU + 256 维隐藏状态"。

> **提示**：写到这儿你可以回头看一眼编码器的代码——把编码器复制下来稍作改动，就是解码器。这两套结构本来就是同一族。真正把它们区分开的，只在于编码器**不接输出层**、只把结果整体往后传；解码器要一层层把结果映射成词。

---

### 解码器写完之后的三步

到这儿模型部分已经攒齐两块：编码器（已经测过）与这个无注意力的 GRU 解码器。

接下来三步是顺着走的。先把刚写好的解码器跑一遍，确认它的形状和输出都对；再把同一个解码器**加上注意力机制**重写一遍；最后对带注意力的版本再做一次测试。

> **结论**：编码器不接输出层、只把 GRU 的结果原样往后交给解码器；解码器在 GRU 之上补一个 `Linear(256 → 4345)` 加 `LogSoftmax`，把隐藏信息变成词表上的概率分布。这就是无注意力编码器—解码器的全部分工。

### 测试函数的分步骨架

先给函数体一个骨架，剩下的都往里填：

```python
def demo_test_decoder():
    # 1. 获取数据集加载器
    mydataloader = get_dataloader()

    # 2. 初始化编码器模型，并移动到 GPU
    # 3. 初始化解码器模型，并移动到 GPU
    # 4. 打印模型结构
    # 5. 完整的编码与解码流程测试
```

> **易错点**：我这里测的是**解码器**，为什么第二步却要先初始化**编码器**？因为中间语义张量 `c` 是由编码器生成的——你得先把编码器那一趟跑完，才能拿着 `c` 走后边的解码器。测右边，就得先把左边造出来。

另外记住 `.to(device)` 的写法：不要先创建对象、下一行再写 `my_encoder = my_encoder.to(device)`。**在对象创建表达式的末尾直接接上 `.to(device)`** 就够了。

### 编码器与解码器的初始化

```python
input_size = English_words_n                  # 2803，英文词汇表大小

my_encoder_gru = EncoderRNN(input_size, hidden_size).to(device)

my_decoder_gru = DecoderRNN(French_words_n, hidden_size).to(device)
```

编码器吃的是英文词表大小 2803，因为英译法的**左边是英文**；解码器吃的是法语词汇表大小 4345，因为**右边是法语**。两个模型的隐藏层维度都是 256 —— 这一项必须对齐，否则 `c` 交到解码器手里形状就对不上。

> **提示**：如果换成 CPU 环境，`.to(device)` 这行可以不管；只要是 GPU 环境，这一行是必须写的。

---

### 打印模型结构：编码器为什么没有输出层

保险起见先把两个模型都 `print` 出来。编码器打印出来的三层是这样的：

| 层 | 维度 | 含义 |
| --- | --- | --- |
| `embedding` | 2803, 256 | 英文词汇表 2803 个词，每个词转成 256 维词向量 |
| `gru` | 256, 256 | 前一个 256 是输入维度（词向量维度），后一个 256 是输出维度（隐藏层维度） |

一眼就能看出：编码器**只有词嵌入和 GRU 两层，没有 `out` 那层**。这正是它和传统 RNN 用法不一样的地方——传统写法里 GRU 后面还要挂一个线性层做输出，这里**不挂**。

为什么不挂？因为编码器处理完的结果就是"中间语义张量 `c`"，它是往后**交给解码器继续干活**的，不是拿来做最终预测的。一旦挂上输出层，就直接出结果了，那 `c` 也就不再是原汁原味的隐藏信息了。

```text
编码器（EncoderRNN）
    输入 x (1, seq_len)
      │
      ▼
    embedding(2803 → 256)
      │
      ▼
    gru(256 → 256)          ← 到此为止，没有 out 层
      │
      ▼
    原样返回：c
```

读图说明：编码器只有词嵌入和 GRU 两个动作，中间不做任何降维或线性变换，GRU 算出来的结果原模原样交出去，这就是中间语义张量 `c`。

解码器打印出来是三层：

| 层 | 维度 | 含义 |
| --- | --- | --- |
| `embedding` | 4345, 256 | 法语词汇表 4345 个词，每个词转成 256 维 |
| `gru` | 256, 256 | 与编码器相同 |
| `out` | 256, 4345 | 把 256 维词向量映射成 4345 个法语词的概率 |

`out` 那句的含义是：**把预测到的那个词的 256 维词向量，映射成 4345 个词各自的概率**，然后从这个概率里挑最大的一个作为最终结果。

> **提示**：打印出来的维度里，`2803` 是英文单词总数（英文词汇表大小），`256` 是每个单词用多少维来表示，也就是词向量维度。GRU 那两个 `256` 分别对应"输入维度"和"输出维度"，后者其实就是隐藏层维度。如果你觉得 256 和 256 长得太像容易看晕，那就把隐藏层维度换成 512 或 128——两个数不一样了，后面往下写就清爽很多。

---

### 隐藏状态就是一切：解码器只用一层线性层的原因

看解码器结构时会撞上一个问题：GRU 后面为什么不接 `output` 输出那一步，直接上 `out` 线性层？

因为**隐藏状态里已经装着接下来要生成的那个词的全部信息**。回忆一下 RNN 的两步机理：

$$\text{本次隐藏状态} = \tanh(W \cdot [\text{上次隐藏状态}, \text{本次输入}] + b)$$

$$\text{本次输出} = \text{softmax}(W_o \cdot \text{本次隐藏状态} + b_o)$$

写公式的时候看着是一步到位、一口气全给你，但**底层其实是先算本次隐藏状态、再算本次输出这两个动作**。所以顺序永远是：

```text
s0（初始隐藏状态）
   │  + welcome（本次输入）
   ▼
  s1 ──────────► 输出 welcome
   │  + to（本次输入）
   ▼
  s2 ──────────► 输出 to
   │  + beijing（本次输入）
   ▼
  s3 ──────────► 输出 beijing
```

读图说明：先由上次隐藏状态和本次输入算出本次隐藏状态，再由本次隐藏状态算出本次输出。有了 `s1` 就能算 `welcome`，有了 `s2` 就能算 `to`，有了 `s3` 就能算 `beijing`——这就是"基于隐藏状态预测词"的来历。

> **注意**：真正调用这一层的时候，框架永远让你写成"把本次输入和上次隐藏状态一起传进去"，它一次把本次隐藏状态和本次输出都还给你。底层那两个动作是分开算的，但接口上它是合一的，这一点不用跟它较劲。

所以解码器的逻辑就顺下来了：GRU 交出的隐藏状态 → `out` 映射成 4345 维 → 4345 个法语单词的概率 → 挑概率最大的那一个，就是本次预测结果。这和结构图上"1×4345 转成概率、得到 一个词"完全对应。

---

### 完整的编码与解码流程

前面的模型只是"造出来了"，还没干活。接下来走一遍完整流程，分四步。

#### 从加载器里取一个批次

```python
for i, (x, y) in enumerate(mydataloader):
    print(f"输入的数据信息（英语句子）：{x.shape}")
    print(f"输入的数据信息（法语句子）：{y.shape}")
```

一个批次的样本就是一条数据——相当于从样本集里随机扒一条过来：**左边英文，右边法文**。这里只打印 `shape` 不打印内容，内容打出来信息量太大、看着难受；只看形状，一眼就能看出配对关系：

- `x.shape = (1, 6)`，`y.shape = (1, 7)`：六个英文词，生成七个法文词；
- `x.shape = (1, 9)`，`y.shape = (1, 10)`：九个英文词，生成十个法文词。

打印完记得 `break`，不然会把整个数据集刷满屏。

#### 编码过程：把英文句子压成中间语义张量 c

```python
h0 = my_encoder_gru.initHidden(x.size(0), device)

encoder_output, encoder_c = my_encoder_gru(x, h0)

print(f"编码器输出 c：{encoder_c.shape}")
```

先调 `initHidden()` 拿到初始隐藏状态 `h0`，再做编码器前向传播，得到的输出就是**中间语义张量 `c`**。

为什么编码器的输出可以直接当 `c` 用？因为它这一趟只做了词嵌入和 GRU，**没有 `out` 层做降维**，交出来的就是 GRU 处理后的原始信息，没有任何加工。

这一步的形状是可以直接推出来的。`x` 是 `(1, 6)`，所以：

```text
x (1, 6)  ──embedding──►  (1, 6, 256)  ──gru──►  (1, 6, 256)  ──►  c
```

读图说明：`(1, 6)` 经过词嵌入变成 `(1, 6, 256)`；GRU 保持形状不变，输出的 `c` 就是 `(1, 6, 256)`。如果 `x` 是 `(1, 9)`，`c` 就是 `(1, 9, 256)`；`(1, 7)` 对应 `(1, 7, 256)`。

这 6 个 256 维向量里装的是什么？**每个英文单词的词向量形式，以及 GRU 处理后的语义关联与隐藏状态信息，全都在里面**。这就是它被称为"语义张量"的原因。

#### 最后一个时间步的隐藏状态

真正交给解码器的，是 `c` 里面最后一个时间步的信息：

```python
print(encoder_c[0][-1].shape)
```

`encoder_c` 是 `(1, 6, 256)`，逐层剥：

- `[0]` 取第一个样本，形状变成 `(6, 256)`——六个时间步，每步 256 维；
- `[-1]` 取最后一个时间步，形状变成 `(256,)`。

> **结论**：这 `(6, 256)` 里记录的是 $h_0, h_1, h_2, \dots$ 依次递推的结果，而最后那一个 256 维向量就是最终的隐藏状态——**它已经包含了前面所有时间步的信息**。所以后面解码只需要这一个向量。

#### 逐词解码：把隐藏状态解成法语句子

解码是**逐个字符（逐词）生成**的，走不了捷径：

```python
for i in range(y.shape[1]):
    temp = y[0][i].view(1, -1)
    output, hidden = my_decoder_gru(temp, hidden)
    print(output.shape)
```

`range(y.shape[1])` 里的 `y.shape[1]`：`y` 的形状是 `(1, 7)`，取下标 1 就是 **7**，也就是目标句子的长度。所以 `i` 从 0 到 6 走一遍。

这一步为什么必须显式控制长度？因为如果没人告诉它"这句话一共七个词"，它可能会一路往下生成到 `(1, 10)`、`(1, 100)` 停不下来。**我把长度告诉它，它一个词一个词帮我生成**，就这么简单。

`y[0][i]` 是取出整批中第一个样本的第 `i` 个词的索引，比如第一次是 `y[0][0]`，第二次是 `y[0][1]`。取出来的东西是一个**标量**，形状是 `()`。而解码器要求输入至少是二维的，所以后面接 `.view(1, -1)`：`1` 是一行，`-1` 是列数由框架自己算——反正就一个数，转完就是 `(1, 1)`。

```text
y (1, 7)
   │  y[0][i]        取出第 i 个词的索引
   ▼
标量 123
   │  .view(1, -1)   匹配 embedding 的输入要求
   ▼
(1, 1)  ──►  [123]
```

读图说明：从 `(1, 7)` 里按下标取出一个词的索引，得到一个标量；再用 `view(1, -1)` 把它变成 `(1, 1)` 的二维张量，这个形状正是解码器 `embedding` 层要的输入。

于是循环就长这样：第一次把 `123` 送进去，算出第一个预测；第二次 `i` 变成 1，把 `297` 送进去，算出第二个预测；再下一次把 `126` 送进去……每一步都拿到那一时刻的输出，最后把整个句子的每个词都覆盖到。

#### 解码器前向传播与打印

```python
output, hidden = my_decoder_gru(temp, hidden)
print(output.shape)
```

前向传播为什么必须写？因为上面刚把词索引转成 `(1, 1)`，正处在结构图上"进入解码器"的位置，不算它等什么呢。

这里有个必须注意到的地方：**`hidden` 不是随便给的，它就是编码器的输出**。往上翻，这个 `hidden` 是编码器前向传播交出来的那一个——也就是上面的 `s0` 其实等于编码器算出的最终隐藏状态。这正是为什么要先用编码器初始化一遍：**解码器的起点，用的是编码器的终点**。

打印输出时，`output.size()` 和 `output.shape` 拿到的东西一模一样，两种写法没有区别。为了好读可以多打几个换行：

```python
print(f"预测第{i + 1}个法语单词的概率分布：{output.shape}\n\n")
```

注意下标写的是 `i + 1` 而不是 `i`，因为 `i` 是从 0 开始的，而我们要数的是"第几个法语词"。这样打出来的是形状，不是概率值本身——**单词量太大，只打形状就够看清结构了**。

---

### 跑出来的结果怎么读

随便找一组打印结果，比如英文 7 个词、法文 8 个词的那一组：

- `output` 的形状是 `(1, 1, 4345)`，也就是该时间步对所有 4345 个法语单词的一个概率分布；
- 循环跑了 8 次，就对应法语句子第 1 个词、第 2 个词……第 8 个词各自的概率分布；
- 在每一个 `(1, 4345)` 里挑概率最大的那个词，就是该位置的预测结果。

这就是完整的预测动作：**在这个概率分布里找到最大的那一个，再去 4345 个法语词汇表里把对应的词取出来，拼起来就是生成的句子**。

> **结论**：说明句子有几个单词，就让它生成几个单词——长度是我定的，不让它自己任性发挥。

---

### 这次测试真正验证了什么

到这里模型的训练和预测其实都通了：预测就是从概率分布里取最大、查词表、拼接句子。

但别忘了，**这才只是测试，还没训练**。只做这一步还不能叫人工智能——那叫人工智障。

不过测试本身已经完成了它的使命：**编码器和解码器这套代码能测通，说明两个模型的形状、接口与数据流全都没有问题**，可以放心进入下一步——在同一个解码器上加注意力机制，再重写一遍。唯一要记住的是：现在这一版，是**没有注意力**的解码器。

## Day06-14.英译法案例_基于GRU有Attention的解码器_思路分析(掌握)
> 对应分集：P93 | 原始标题：《Day06-14.英译法案例_基于GRU有Attention的解码器_思路分析(掌握)》

无注意力的解码器我们已经写完也测通了。现在把同一个解码器**加上注意力机制**重讲一遍。这一讲的落点还是思路：先把结构图上每条线、每个张量的形状都标注清楚，代码只是照图抄一遍。所以这一篇的重点不在"怎么写"，而在"**为什么每条线的形状必须长这样**"。

先把无注意力版和带注意力版的结构图并排放在一起看，你能一眼看出差别就在中间那几根新增的线上。

---

### 从无注意力版到带注意力版

无注意力版和带注意力版都是 sequence to sequence（序列到序列）架构，也就是"句子到句子"的架构。两者的编码器完全相同，差别全部落在解码器内部。

上图是无注意力版，下图是带注意力版。带注意力版多出来的动作是：把解码器的本次输入 `Q` 和编码器的输出 `K` 做拼接、算权重、再拿权重去乘 `V`，最后把结果和 `Q` 融合一遍。这就是注意力的全部。

顺带留个记录：前面测试无注意力解码器那一版的打印结果也值得留着，回头对着看会很省事——它给出了每一层的真实维度，是后面推形状的参照系。

---

### Q、K、V 各自是谁、形状多大

有注意力机制，就必然有 Q、K、V 三个角色。三者的分工是：

- **Q（Query，查询）**：查询的问题，就是解码器本次的输入；
- **K（Key，键）**：被查询的对象，来自编码器的输出；
- **V（Value，值）**：与 K 一一对应的内容，同样来自编码器的输出。

> **结论**：Q 一定是"你输入进来的那个东西"。你要拿一个查询去问别的位置，输入自然就是 Q。所以三个张量里第一个就是 Q。

形状方面：

| 角色 | 形状 | 含义 |
| --- | --- | --- |
| Q | `(1, 1)` → `(1, 256)` | 解码器本次输入的那一个词 |
| K | `(1, 10, 256)` | 编码器输出，10 个位置、每位置 256 维 |
| V | `(1, 10, 256)` | 与 K 同形状 |

`Q` 为什么是 `(1, 1)`？因为它就是从目标句子里取出的**一个标量**，再用 `view(1, -1)` 转成一行一列的形状。`K` 和 `V` 为什么中间的维度是 10 而不是 6、7、9 或 13？这是本讲最关键的一个坑，下面单独讲。

---

### 从词嵌入到注意力计算

带注意力版解码器的前半段，和无注意力版几乎一样：词嵌入层把输入的标量转成词向量，接着过一个 **dropout 层**做随机失活，然后进注意力计算。

```text
      Q (1, 1)                        K (1, 10, 256)
         │                                   │
         ▼                                   │
   embedding(4345 → 256)                     │
         │                                   │
         ▼                                   │
      dropout                                │
         │                                   │
         ▼                                   │
   embedded (1, 256)                         │
         │                                   │
         └───────────────┬───────────────────┘
                         ▼
                       attn
                         │
                         ▼
                    (1, 1, 10)      ← 权重分布
```

读图说明：Q 从 `(1, 1)` 出发，经词嵌入变成 `(1, 256)`，再经 dropout 排出过拟合；K 保持 `(1, 10, 256)` 原样进入注意力；两者在 `attn` 处汇合，算出一个长度 10 的权重分布。

#### 注意力计算的运算规则

注意力的运算顺序是固定的四步：

$$\text{attn\_weights} = \text{Softmax}\big(\text{Linear}([Q; K])\big)$$

$$\text{attn\_applied} = \mathbf{bmm}\big(\text{attn\_weights},\ V\big)$$

用文字说就是：**Q 和 K 先做拼接，外面套一个 Linear，最外层再套一个 Softmax，最后拿这个结果去乘 V**。所以只要看到拼接，就意味着形状要在这一维上翻倍：`(1, 256)` 和 `(1, 10, 256)` 拼起来，出现的是 `512`。

#### 拼接后的形状与 Linear 的转换

拼接动作落在 `attn` 这一步。它的本质是：**把 Q 和 K 拼接后的结果做一次全连接层变换**。

```text
 Q (1, 256)  ─┐
              ├─ 拼接 ─► (1, 10, 512) ─ Linear ─► (1, 10, 1) ─ Softmax ─► (1, 10)
 K (1, 10, 256)┘
```

读图说明：Q 在 10 个位置上被复制展开，和 K 逐位置拼接成 `(1, 10, 512)`；Linear 把 512 压成 1，得到每个位置的打分 `(1, 10, 1)`；Softmax 把打分归一化成权重 `(1, 10)`。

这里会看到 `(1, 1, 512)` 这样的中间形状——它出现的原因就是 Q 和 K 在拼接，说明这两条线并到了一起。

接着是 Softmax。Softmax 的作用是把值**压成概率**：这里就是要算出对每个词的注意力概率。概率分布在几个词上？本来是你的 6 个词，但这里写的是 10 个——**因为要统一长度**。

> **注意**：Softmax 之后还会经过一个激活函数，形状不变、只改变值，所以还是 `(1, 10)`；后面乘的那个权重是常量，算完形状也还是 `(1, 10)`。

这 10 个位置上的权重到底在表达什么？它表达的是：**生成这个 Q 的时候，我分别有多依赖编码器的第 1 个词、第 2 个词……第 10 个词**。是更依赖第一个，还是第二个，还是第三个——权重大的位置，就是这次生成主要参考的位置。

---

### 最大长度 10：补齐与截断

为什么是 10 而不是 6？因为**一开始就设定了句子的最大长度是 10**。这就是那个"定义了却一直没用"的变量，到这一步终于用上了。

```text
英文句子长度       进入注意力前统一为
     6      ──►        10
     7      ──►        10
     9      ──►        10
    13      ──►        10（截断）
```

读图说明：不管原始句子是 6 个词、7 个词还是 13 个词，到这里统统变成 10。不够的用 0 补齐，超出的截断——专业名称叫**截断和补齐**。

**为什么必须统一？** 因为如果它是 `(1, 6)`、`(1, 7)`、`(1, 9)` 这样一直变，下面那几层的矩阵乘法就没法与它配合，整个计算根本进行不下去。只有长度固定为 10，后面的运算才能统一算。

于是 Q 侧的中间表示也要跟着对齐：原来 `(1, 6, 256)` 的编码器输出，到这一步要变成 `(1, 10, 256)`。即使原始句子是 13 个词，到这里也还是 10。

> **易错点**：`(1, 6, 256)` 变 `(1, 10, 256)` 这一步**不经过任何线性层**，形状是直接改写出来的，得由你在代码里显式做到。不做这一步，`(1, 10)` 的权重就没法和 `(1, 6, 256)` 相乘。

---

### 注意力权重与 V 的相乘

`bmm` 是批量矩阵乘法。现在两边的形状是 `(1, 10, 256)`（V）和 `(1, 10)`（权重），这两个形状还不能直接乘，需要先把权重调整好——就是前面说的、把编码器输出的形状改成 `(1, 10, 256)`，让两者对齐。

对齐之后相乘：

$$\text{attn\_applied} = \mathbf{bmm}(\text{weights},\ V)$$

形状是 `(1, 1, 10)` 与 `(1, 10, 256)` 相乘 → `(1, 1, 256)`。

`(1, 1, 256)` 就是加权求和之后的结果——按注意力权重把 10 个位置的 256 维向量混合成一个 256 维向量。

---

### 注意力结果与 Q 的融合

`attn_applied` 拿到 `(1, 1, 256)` 之后，还有一步融合：**把第一步算出来的结果和 Q 再做一次拼接**。

为什么还要拼 Q？因为注意力算出来的是"从编码器那边取回来的信息"，而 Q 是"我现在要生成什么"的原始诉求。把两者拼在一起，模型才能同时看到"我问的什么"和"我取回了什么"。

```text
 attn_applied (1, 1, 256) ─┐
                            ├─ 拼接 ─► (1, 1, 512) ─ Linear ─► (1, 1, 256)
 Q (1, 1, 256) ─────────────┘
```

读图说明：`attn_applied` 和 Q 在最后一维上拼接成 `(1, 1, 512)`，再经过 `attn_combine` 的 Linear 重新换回 `(1, 1, 256)`。

拼接之后是 `(1, 1, 512)`，但这个 512 维**和后面的层没法接**——后面的 GRU 只吃 256 维。所以要用 `attn_combine` 把它换回 256 维。

> **提示**：只要是神经网络层，就能改变形状——它的本职就是"一个输入、一个输出"，形状变换本来就是它的工作。而激活函数（比如 ReLU）只改值、不改形状。这个区别在推算形状时非常有用：看到形状变了，往回找**一层神经网络**；看到形状没变，那多半是激活函数。

所以 `attn_combine` 这一步干的事很清楚：**按注意力计算步骤来看，第一步是拼接（Q 与 K 拼、算出 attn_weights），第二步则是把 Q 与第一步的计算结果拼接，再经历 Linear 做线性转换**，把 `(1, 1, 512)` 转成 `(1, 1, 256)`。

---

### 汇入 GRU 与输出层

融合之后的 `(1, 1, 256)` 进 GRU。GRU 那条线是从解码器的隐藏状态过来的，形状也是 `(1, 1, 256)`。

GRU 处理完会返回两个东西：**本次的隐藏状态和本次的输出**。这两者形状都是 `(1, 1, 256)`。

```text
 attn_combine (1, 1, 256) ──┐
                             ├──► gru(512 → 256) ──► output  (1, 1, 256)
 隐藏状态 (1, 1, 256) ───────┘                   └──► hidden  (1, 1, 256)
                                                          │
                                                          ▼
                                                 out: Linear(256 → 4345)
                                                          │
                                                          ▼
                                                    (1, 4345)
                                                          │
                                                          ▼
                                          代表预测每一个法文单词的概率
```

读图说明：`attn_combine` 的输出和隐藏状态一起进 GRU，GRU 同时返回本次输出和本次隐藏状态；输出经过 `out` 线性层从 256 维映射到 4345 维，这 4345 个值分别代表**预测每一个法文单词的概率**，取其中最大的那个就是本次预测出的词。

`out` 输出的形状是 `(1, 4345)`——这一步在无注意力版里也出现过，是同一个输出层。

---

### 整张结构图的完整数据流

把所有动作按代码执行顺序串起来，就是下面这一趟：

```text
 Q (1, 1)
    │
    ▼
 embedding(4345 → 256)
    │
    ▼
 dropout
    │
    ▼
 (1, 256)  ─────────────────────────┐   ← Q 侧
                                    │
 K (1, 10, 256) ─ 展成 (1, 10, 256) ┤
                                    ▼
                          attn：拼接 → Linear → Softmax
                                    │
                                    ▼
                              (1, 10) 权重
                                    │
                        bmm(权重, V (1, 10, 256))
                                    │
                                    ▼
                            (1, 1, 256)  attn_applied
                                    │
                     ┌──────────────┘
                     ▼
      与 Q (1, 256) 拼接 → (1, 1, 512)
                     │
                     ▼
       attn_combine：Linear(512 → 256)
                     │
                     ▼
              (1, 1, 256) ──┐
                             ├──► gru(512 → 256) ──► (1, 1, 256)
       隐藏状态 (1, 1, 256) ─┘
                             │
                             ▼
                  out: Linear(256 → 4345)
                             │
                             ▼
                        (1, 4345) 概率
                             │
                             ▼
                     取概率最大的一个词
```

读图说明：整条链路上，形状变换只发生在三个地方——注意力里的两次拼接加 Linear、`attn_combine` 的 Linear、`out` 的 Linear；其余位置（dropout、ReLU、Softmax）形状一律不变。

按代码顺序数，这条链路上有四个核心动作：

1. 词嵌入层：把标量形式的词索引转成 `(1, 256)` 的词向量；
2. 注意力计算：Q 与 K 拼接、Linear、Softmax，得到权重，再与 V 相乘；
3. `attn_combine`：第一步的计算结果与 Q 拼接，再经 Linear 换回 256 维；
4. GRU 后面的 `out`：把 256 维映射成 4345 个法文单词的概率。

> **结论**：`embedding` 做词嵌入，中间的 `attn` 与 `attn_combine` 把"编码器信息"按权重取回来并融合进本次输入，`out` 负责输出每个法文单词的概率——这三件事分工清楚，形状就一定是上面这样，不会变。

## Day06-15.英译法案例_基于GRU有Attention的解码器_代码实现_上(掌握)
> 对应分集：P94 | 原始标题：《Day06-15.英译法案例_基于GRU有Attention的解码器_代码实现_上(掌握)》

带注意力机制的解码器应该怎么搭？前面我们已经把它拆开分析完了，接下来就是把它用程序快速实现出来。切到 PyCharm，往下拉，代码正好停在 TODO 10 的位置——这个动作叫「构建基于 GRU 的解码器」，侧重点是有注意力机制。顺手把 TODO 11 也写上：测试基于 GRU 的带注意力机制的解码器。这两个干完，一条线就通了。

### 类的骨架与 TODO 规划

先声明类，名字叫 `AttnDecoderRNN`。之前那个不带注意力的解码器叫 `DecoderRNN`，这次只是在前缀上多加了 Attention，其余套路一模一样，继承 `nn.Module`。

```python
class AttnDecoderRNN(nn.Module):
    pass
```

> **提示**：命名上只加 `Attn` 前缀，是为了让两版解码器能放在同一个文件里对照着看。形状怎么变、层怎么接，一目了然。

紧接着就是初始化函数。这次 `__init__` 里的动作比不带注意力的版本要多，得一个一个数清楚。

### 构造参数与形状约定

先看入口的四个参数：`output_size`、`hidden_size`、`dropout_p`、`max_len`。

| 位置 | 参数名 | 含义 | 本项目取值 |
| --- | --- | --- | --- |
| 参 1 | `output_size` | 目标语言（法语）词汇表大小 | 4345 |
| 参 2 | `hidden_size` | 隐藏层维度 | 256 |
| 参 3 | `dropout_p` | 随机失活概率 | 由调用方传入 |
| 参 4 | `max_len` | 句子最大长度 | 10 |

参 1 是法语词汇表的大小，所以一会儿输出层的输出维度就是 4345。

参 2 这个隐藏层维度，我要专门说一句：**它必须和编码器一致**。为什么？因为在 seq2seq 架构里，编码器最后一个时间步吐出来的隐藏状态 $H_3$，就是解码器这边的 $S_0$。既然要拿它当起点，两边的隐藏状态维度就必须对齐，否则接不上。

参 3 是随机失活概率——这个位置本来就有 dropout 这件事。

参 4 是句子的最大长度：超过 10 就截到 10，不够 10 就硬补，统一成 10。这件事在后面的维度推导里会反复用到。

### `__init__` 的第一步：父类初始化与参数保存

先做 TODO 10.1。第一个动作是初始化父类成员：

```python
super().__init__()
```

第二个动作是把四个输入参数原样存到实例上：

```python
self.output_size = output_size
self.hidden_size = hidden_size
self.dropout_p = dropout_p
self.max_len = max_len
```

> **易错点**：这四个 `self.xxx` 后面在 `forward` 里都要被反查——建层的时候用它们，算维度的时候还要用它们。少存一个，后面就得硬写常量。

### 注意力权重的三段式：词嵌入层、注意力计算层、注意力融合层

第三到第五个动作，是注意力机制的三块核心。我们从下往上看，正好对应前面画的那张图。

#### 词嵌入层

第三个动作是创建词嵌入层。这里给的参数是 `self.output_size` 和 `self.hidden_size`——注意，用的是目标语言的词表大小，不是英文词表：

```python
self.embedding = nn.Embedding(self.output_size, self.hidden_size)
```

也就是说这一层做的事情是 $4345 \to 256$。为什么输入是法语词表？因为解码器每一步吃进去的是**已经生成的、上一步预测出来的法语词**，它自然要落在法语的编号空间里。

再看形状，这里必须说清楚，不然一会儿 `nn.Linear` 那块一定懵。

输入形状是 `[batch_size, seq_len]`，在本项目里就是 `[1, 1]`。为什么两个都是 1？

- 第一个 1 是批次大小，测试的时候一批就一条样本；
- 第二个 1 是序列长度——这里是**逐个时间步**解码的，一次只送一个词进来。

那个「1」是哪来的？就是编码器最后拿出来的那个隐藏状态，它带来的批次维继续沿用。

输出形状就是在后面接上 `hidden_size`，所以处理完变成 `[1, 1, 256]`。

#### 注意力计算层

第四个动作：注意力权重计算层。它要做的是计算查询向量和编码器输出之间的匹配程度——也就是匹配分。这一层对应图上的 `attn`：

```python
self.attn = nn.Linear(self.hidden_size * 2, self.max_len)
```

为什么是 `hidden_size * 2`？因为这一层的输入是「拼接后的查询向量」和「隐藏状态」两路合并的结果，所以维度得翻倍，在这里就是 `1 × 512`。

> **定义**：注意力权重分布张量的形状是 `[1, 1, 10]`，最后那个 10 来自 `max_len`——最多 10 个词，所以权重也正好是 10 份。

输出维度给 `self.max_len`，也就是 10，因为它输出的就是这个权重分布。

**这里一定会有人懵**：这不是 `nn.Linear` 吗？线性层不是只能处理二维吗？我这儿给的可是三维的东西。答案很简单——按 `[1, 512] → [1, 10]` 用就行，批次维在草稿阶段先不管，用它的时候再统一处理。为了跟前面对照一致，我不改成二维写法，能看懂就行。

#### 注意力融合层

第五个动作：注意力融合层。

它要做的事情是把词嵌入和注意力权重进行融合。名字沿用图上的 `attn_combine`：

```python
self.attn_combine = nn.Linear(self.hidden_size * 2, self.hidden_size)
```

还是同一个道理：输入是 `1 × 512` 的拼接结果，所以第一个参数是 `hidden_size * 2`；输出要回到 `1 × 256`，所以第二个参数就是 `self.hidden_size`。这一层的参数写法和上面 `attn` 层是完全一样的，就不再重复解释了。

### 第六到第九个动作：dropout、GRU、输出层、LogSoftmax

#### dropout 层的插桩位置

写完融合层，本来该轮到 GRU 了。但我在这个位置补一个动作：在 `attn_combine` 之后，给隐藏层也加一个 dropout。图上没有画它，但完全可以加。

于是第六步：dropout 层，随机丢弃部分神经元，防止过拟合。

```python
self.dropout = nn.Dropout(self.dropout_p)
```

为什么非要在这里补出来？因为最开始传进来的那个 dropout 概率，在建 `embedding`、`attn`、`attn_combine` 的时候**根本没被用上**——一层都没写。所以得给它建一个真正的层，把参数用起来；原本排在第六位的 GRU 顺势往后挪一位。

#### GRU 层

第七步：创建 GRU 层，处理序列数据、维持隐藏状态。

```python
self.gru = nn.GRU(self.hidden_size, self.hidden_size, batch_first=True)
```

往图上看，GRU 这一层进出的都是 `[1, 1, 256]`，所以输入维度和隐藏维度都写 `self.hidden_size`，两边一样。`batch_first=True` 让 `batch_size` 待在第一个维度上，读形状的时候更顺手。

#### 输出层

第八步：输出层。GRU 之后接输出，输出这一层负责把 GRU 的隐藏状态映射为目标词汇表（法语）的大小：

```python
self.out = nn.Linear(self.hidden_size, self.output_size)
```

也就是从 256 映射到 4345。

#### 对数 Softmax 层

第九步，也是最后一步：对数 Softmax（LogSoftmax）层。它把输出映射成对数 Softmax 的概率分布：

```python
self.softmax = nn.LogSoftmax(dim=-1)
```

`dim=-1` 表示在最后一个维度上做归一化。

> **提示**：如果你下游配的是 `CrossEntropyLoss`，这层其实可以不用写——`CrossEntropyLoss` 内部已经带了 `log_softmax`。写出来是为了让一步一算的过程更直观。

### `__init__` 全貌

九个动作按顺序落地下来，构造函数就是下面这个样子：

```python
class AttnDecoderRNN(nn.Module):
    def __init__(self, output_size, hidden_size, dropout_p, max_len):
        super().__init__()
        # 1. 保存输入参数
        self.output_size = output_size
        self.hidden_size = hidden_size
        self.dropout_p = dropout_p
        self.max_len = max_len
        # 2. 词嵌入层：4345 -> 256
        self.embedding = nn.Embedding(self.output_size, self.hidden_size)
        # 3. 注意力权重计算层：拼接后的 512 -> 10
        self.attn = nn.Linear(self.hidden_size * 2, self.max_len)
        # 4. 注意力融合层：拼接后的 512 -> 256
        self.attn_combine = nn.Linear(self.hidden_size * 2, self.hidden_size)
        # 5. dropout 层
        self.dropout = nn.Dropout(self.dropout_p)
        # 6. GRU 层
        self.gru = nn.GRU(self.hidden_size, self.hidden_size, batch_first=True)
        # 7. 输出层：256 -> 4345
        self.out = nn.Linear(self.hidden_size, self.output_size)
        # 8. 对数 Softmax 层
        self.softmax = nn.LogSoftmax(dim=-1)
```

### 维度流转速查

构造阶段把每一层的进出维度都定死了，把它们串起来看，整条链路是这样的：

```text
input(词索引)  [1, 1]
     |
     v
embedding      [1, 1, 256]
     |
     +---------------------------+
     |                           |
     v                           v
attn(拼接 Q 与 hidden -> 512)   attn_combine(拼接后 512)
     |                           |
     v                           v
权重分布        [1, 1, 10]       -> 256, 回到 [1, 1, 256]
                                 |
                                 v
                              dropout
                                 |
                                 v
                                GRU      [1, 1, 256]
                                 |
                                 v
                                out      256 -> 4345
                                 |
                                 v
                             LogSoftmax  [1, 1, 4345]
```

读图说明：左侧一路由词嵌入走向注意力权重分布，右侧一路把权重与词嵌入融合回 256 维，再经 dropout 进 GRU，最后由输出层映射到法语词表大小并做对数 Softmax 归一化。

> **结论**：`__init__` 里每一个 `nn.Linear` 的维度都不是拍出来的——`hidden_size * 2` 是拼接带来的，`max_len` 是权重个数带来的，`output_size` 是法语词表大小带来的，而 `hidden_size` 必须和编码器保持一致，因为解码器的初始隐藏状态就是编码器的最后一个输出。

到这里，基于 GRU 的带注意力机制解码器的 `__init__` 就做完了。构造函数只是把层摆好、把维度定死，真正把这些层串成一次前向计算，是下一步的事。先保存。

## Day06-16.英译法案例_基于GRU有Attention的解码器_代码实现_下(掌握)
> 对应分集：P95 | 原始标题：《Day06-16.英译法案例_基于GRU有Attention的解码器_代码实现_下(掌握)》

`__init__` 里的参数初始化已经全部做完了，接下来是 TODO 10.2——前向传播函数。这个动作比刚才那些建层要稍微花点心思，因为它要把九个步骤按顺序串起来，每一步的形状都得对上，错一个维度，后面就全崩。我要做的就是照着图一步一步走，中途随时把形状打出来看。

### `forward` 的入口参数与形状

先 `def forward`，然后问自己一句：前向传播里需要有谁？三个：`input`、`hidden`、`encoder_outputs`。为什么是这三个？因为这正好是要喂给注意力机制的 Q、K、V 那一路东西。

```python
def forward(self, input, hidden, encoder_outputs):
```

**参一 `input`**：当前时间步的输入词索引。形状是 `[batch_size, 1]`，一批一个，所以就是 `[1, 1]`。

**参二 `hidden`**：上一个时间步的隐藏状态。形状是 `[层数, batch_size, hidden_size]`——层数默认是 1，`batch_size` 也是 1，所以是 `[1, 1, 256]`。

**参三 `encoder_outputs`**：编码器的输出，写全一点叫「编码器所有时间步的输出」。形状是 `[batch_size, 句子长度, hidden_size]`。

> **易错点**：这里的「句子长度」不是真实句子长度，而是我们约定的 `max_len`，也就是 10。真实句子可能只有 6 个词、8 个词，但到了解码器手里一律是 10——因为编码器输出在传进来之前已经做过截断补齐，统一铺成了固定的 10 个位置。

### 第一步：词嵌入层

词嵌入层的输入形状就是 `[1, 1]`，也就是 `[batch_size, seq_len]`。这一层要把它转成 `[batch_size, seq_len, hidden_size]`，即 `[1, 1, 256]`。

```python
embedded = self.embedding(input)
```

变量名我特意沿用 `embedded`——一会儿要复现同样的名字，保持一致。`input` 是 `[1, 1]`，过完 `self.embedding` 就变成 `[1, 1, 256]`。

### 第二步：随机失活层

第二步是应用 dropout，也就是随机失活层：

```python
embedded = self.dropout(embedded)
```

把自己的 `embedded` 传进去随机失活一下，输出仍然叫 `embedded`。

> **注意**：这一步一定要在算注意力权重**之前**做。因为 `embedded` 是关键角色——它既要参与查询向量的拼接，又要参与后面的融合计算，先失活一次，后面两处用的就是同一份。

### 第三步：注意力权重计算

算完以后的结果就叫 `attn_weights`，所以变量名直接写成：

```python
attn_weights = F.softmax(self.attn(torch.cat((embedded[0], hidden[0]), 1)), dim=1)
```

这一行是整个 `forward` 里最绕的一句，我们拆成三层往里看——还记得注意力机制三大公式的第一条吗？外面是 softmax，里面是线性层，线性层里是 Q 和 K 做拼接。

#### 内层：`torch.cat` 的拼接

最里面是 `torch.cat`，把两个东西拼到一起：`embedded[0]` 和 `hidden[0]`。

为什么写 `[0]`？因为 `embedded` 现在的形状是 `[1, 1, 256]`，取 `[0]` 就把批次维摘掉，变成 `[1, 256]`；`hidden[0]` 同理，从 `[1, 1, 256]` 变成 `[1, 256]`。

为什么非要摘掉这一维？因为后面那个线性层处理的是二维张量，你拿三维的进去它不认。所以这里是**主动降维**，而不是被迫出错。

两个 `[1, 256]` 在 `dim=1` 上拼接，得到 `[1, 512]`。这就是「查询向量与隐藏状态拼接」这一步的真身：一份是当前时间步的输入信息（Q），一份是上一个时间步的隐藏状态（K），拼在一起就是相关性打分的原料。

> **提示**：`dim=1` 和 `dim=-1` 在这两个二维张量上是等价的，都是最后一个维度。写 `-1` 也可以，随你——但心里要清楚它加的是哪一维。

#### 中层：`self.attn` 做维度转换

拼接结果送进 `self.attn`。它就是一个神经网络层，神经网络层能做的事就是全连接和维度转换：把 `[1, 512]` 转成 `[1, 10]`。

这就是「通过线性层把长度转成 10」这个动作。转完的形状是 `[1, 10]`，10 对应 `max_len`——最多 10 个词，每个位置一个打分。

#### 外层：`F.softmax` 映射为概率

最外面套 `F.softmax`，把这些打分映射成概率分布。输入 `[1, 10]`，输出还是 `[1, 10]`，变的是数值的含义：从原始分数变成权重。

`dim=1` 的意思就是「用 `[1, 10]` 里那个 10 做归一化」——让这 10 个权重加起来等于 1。

```text
embedded[0]  [1, 256] ┐
                      ├─ torch.cat(dim=1) ─> [1, 512]
hidden[0]    [1, 256] ┘
                              |
                              v
                        self.attn(Linear)  ─> [1, 10]
                              |
                              v
                        F.softmax(dim=1)   ─> [1, 10]  权重分布
```

读图说明：两路 256 维向量在最后一维拼接成 512 维，经线性层压到 10 维打分，再经 softmax 归一化成 10 个注意力权重。

### 第四步：注意力上下文

权重有了，说明图已经走到「权重分布」那一步，接下来的绿箭头就是算上下文。变量名叫 `attn_applied`：

```python
attn_applied = torch.bmm(attn_weights.unsqueeze(0), encoder_outputs.unsqueeze(0))
```

`bmm` 是批量矩阵乘法，它处理的是三维张量。而我们现在手上的 `attn_weights` 是二维的 `[1, 10]`，所以得先升维：`unsqueeze(0)` 把它从 `[1, 10]` 变成 `[1, 1, 10]`。

`encoder_outputs` 原本是 `[10, 256]`，同样升一维变成 `[1, 10, 256]`。

两个三维张量做批量矩阵乘：`[1, 1, 10] × [1, 10, 256]`，中间的 10 对消，结果就是 `[1, 1, 256]`。

> **定义**：这一步算出来的就是注意力上下文（context），它的形状和隐藏状态一样是 `[1, 1, 256]`。它的含义是——按这 10 个权重，把编码器 10 个时间步的输出做加权求和，得到一个「当前该看哪里」的浓缩向量。

**为什么前面要升维？** 现在就能回答清楚了：`encoder_outputs` 从编码器出来时是 `[1, 6, 256]` 或者 `[1, 8, 256]`（按真实句子长度），而到了解码器这边它必须是 `[1, 10, 256]`（按 `max_len`）。这个统一的升维动作不在 `forward` 里，而是在测试代码准备 `encoder_outputs` 的时候做的。两处要上下联动着看，单看一处确实容易晕。

### 第五步：注意力融合层

上下文算出来，就该融合了——也就是 `attn_combine` 这一步：

```python
output = torch.cat((embedded[0], attn_applied[0]), 1)
output = self.attn_combine(output).unsqueeze(0)
```

还是 `torch.cat`。这次拼的是 `embedded[0]` 和 `attn_applied[0]`：一个是 `[1, 256]` 的当前输入特征，一个是 `[1, 256]` 的注意力上下文。同在 `dim=1` 上拼，得到 `[1, 512]`。

拼完丢给 `self.attn_combine` 处理。这一层把 512 压回 256，所以处理完变成 `[1, 256]`。

然后别忘了一件事：GRU 要的是三维输入，所以后面得补一个 `unsqueeze(0)` 把它升回 `[1, 1, 256]`。

> **结论**：二维和三维之间的来回转换，靠的就是 `unsqueeze` 和 `squeeze` 这两个函数。看到形状对不上，第一反应就是该升维还是该降维，而不是去改层的参数。

### 第六步：激活函数

拿到 `[1, 1, 256]` 之后，接一个激活：

```python
output = F.relu(output)
```

`F.relu` 把 `output` 送进去做非线性激活。形状不变，还是 `[1, 1, 256]`。

### 第七步：GRU 层

激活完就该 GRU 了。GRU 负责处理序列数据、维持隐藏状态：

```python
output, hidden = self.gru(output, hidden)
```

把 `output` 和 `hidden` 一起丢进 `self.gru`，返回更新后的 `output` 和 `hidden`。你会发现这四个张量的形状其实全都是 `[1, 1, 256]`——进 GRU 之前是 `[1, 1, 256]`，出来还是 `[1, 1, 256]`，因为隐藏层维度一直没变过。

### 第八步：输出层与对数 Softmax

最后一步是把 `[1, 1, 256]` 映射到法语词表大小上：

```python
output = self.softmax(self.out(output[0]))
```

`self.out` 把 256 映射成 4345。注意这里写的是 `output[0]` 而不是 `output`——**这样写才不会报错**。因为 `output` 现在的形状是 `[1, 1, 256]`，而 `self.out` 要的是 `[1, 256]`，所以用 `[0]` 把批次维摘掉。

维度这件事必须自己把控，不能指望框架替你兜底。处理完 `output` 的形状就是 `[1, 4345]`——这一步的输出概率分布。

### 第九步：返回值

前向传播算半天，当然得返回结果。返回三个：`output`、`hidden`、`attn_weights`。

```python
return output, hidden, attn_weights
```

**参一 `output`**：当前时间步的输出概率分布，形状 `[1, 4345]`。

**参二 `hidden`**：更新后的隐藏状态，也就是本次的隐藏状态，形状 `[1, 1, 256]`。

**参三 `attn_weights`**：注意力权重分布，形状 `[1, 10]`。

> **提示**：以前写前向传播是不是只返回 `output` 和 `hidden` 就够了？从来没返回过第三样东西。这里多返回一份权重，是为了后面画注意力权重分布图做可视化分析。如果不画图，这一项完全可以不返回。

### 前向传播全貌

九个动作串起来，`forward` 就是下面这个样子：

```python
def forward(self, input, hidden, encoder_outputs):
    # 1. 词嵌入层：[1, 1] -> [1, 1, 256]
    embedded = self.embedding(input)
    # 2. 随机失活
    embedded = self.dropout(embedded)
    # 3. 计算注意力权重：[1, 512] -> [1, 10]，再 softmax 归一化
    attn_weights = F.softmax(self.attn(torch.cat((embedded[0], hidden[0]), 1)), dim=1)
    # 4. 计算注意力上下文，bmm 需要三维，先升维
    attn_applied = torch.bmm(attn_weights.unsqueeze(0), encoder_outputs.unsqueeze(0))
    # 5. 融合层：拼接 256+256 -> 512，压回 256，再升回三维
    output = torch.cat((embedded[0], attn_applied[0]), 1)
    output = self.attn_combine(output).unsqueeze(0)
    # 6. 激活
    output = F.relu(output)
    # 7. GRU 层
    output, hidden = self.gru(output, hidden)
    # 8. 输出层 + 对数 Softmax：[1, 256] -> [1, 4345]
    output = self.softmax(self.out(output[0]))
    # 9. 返回结果
    return output, hidden, attn_weights
```

### TODO 10.3：初始化隐藏状态

还差最后一个动作——解码器起步时得有个初始隐藏状态。TODO 10.3 就是定义它：

```python
def initHidden(self):
    return torch.zeros(1, 1, self.hidden_size, device=device)
```

`torch.zeros(1, 1, self.hidden_size)` 造出 `[1, 1, 256]` 的全零张量，再 `device=device` 把它迁到指定设备上。就这一行，这个函数就完了。

### 形状流转速查

把 `forward` 里所有张量的形状变化按步排一遍，回头哪一步对不上，直接来这张表里查：

| 步骤 | 操作 | 输入形状 | 输出形状 |
| --- | --- | --- | --- |
| 1 | `embedding` | `[1, 1]` | `[1, 1, 256]` |
| 2 | `dropout` | `[1, 1, 256]` | `[1, 1, 256]` |
| 3 | `cat` + `attn` + `softmax` | `[1, 256]` 与 `[1, 256]` | `[1, 10]` |
| 4 | `bmm`（双方升维） | `[1, 1, 10]` 与 `[1, 10, 256]` | `[1, 1, 256]` |
| 5 | `cat` + `attn_combine` + `unsqueeze` | `[1, 256]` 与 `[1, 256]` | `[1, 1, 256]` |
| 6 | `relu` | `[1, 1, 256]` | `[1, 1, 256]` |
| 7 | `gru` | `[1, 1, 256]` 与 `[1, 1, 256]` | `[1, 1, 256]` |
| 8 | `out` + `softmax` | `[1, 1, 256]` 取 `[0]` | `[1, 4345]` |

## Day07-01.英译法案例_带注意力机制的解码器层_测试代码(理解)
> 对应分集：P96 | 原始标题：《Day07-01.英译法案例_带注意力机制的解码器层_测试代码(理解)》

到目前为止，带注意力机制的解码器已经搭出来了，接下来就是把它跑一遍、测一遍。写这个解码器的时候，建议大家一直对着那张图看，包括图里标的每一次维度转换——这样玩起来会清晰很多。测试代码的整体套路还是熟悉的四件事：封装数据集、建数据加载器，然后实例化编码模型，最后做测试。

这里面有个问题一定有人会问：**怎么又用上编码器了？** 原因很简单——解码器要用编码器的输出，才能拿到那个中间语义张量 $c$。所以测试流程里，编码器必须重新实例化一份，跟着一起跑。

测试代码最后会有一个 `break`，意思是只测一批就够了，不用把整个数据集跑完。

### 数据加载器与模型初始化

先定义测试函数：

```python
def dm_test_attn_decoder():
    # 1. 获取数据加载器对象
    my_dataloader = get_dataloader()
```

接下来是模型初始化阶段。既然是 seq2seq 架构，第一个动作一定是创建编码器对象：

```python
    # 2.1 创建编码器对象
    my_encoder = EncoderRNN(english_n, 256).to(device)
```

参 1 是英语词汇表大小——这个数字要背下来，是 **2803**；参 2 是隐藏层维度 256。

> **注意**：`.to(device)` 是把模型移动到指定设备上，这行代码**必须写**。如果你只是在下边把运行环境切成 GPU（比如 `nlp-base-2`），而模型没有 `.to(device)`，执行的时候是会报错的。切环境和搬模型是两件事，别混成一件。

2.2 创建解码器对象：

```python
    # 2.2 创建解码器对象
    my_decoder = AttnDecoderRNN(french_n, 256, dropout_p=0.1, max_len=10).to(device)
```

参 1 是法语句子词汇表大小 **4345**，参 2 是隐藏层维度 256——**两个模型的隐藏层维度必须一样**，因为编码器最后一个时间步的隐藏状态要直接当解码器的初始隐藏状态用。

### 取一个样本与编码过程

第三个动作是模型推理，其实就是走一遍前向。先从数据加载器里拿一个样本，用 `for i, (x, y) in enumerate(my_dataloader)` 来遍历——这个函数在数据加载里用得实在太多了。

拿到样本以后，先打印输入信息看看：

```python
    # 3.1 从数据加载器中获取一个样本
    for i, (x, y) in enumerate(my_dataloader):
        # 3.2 打印输入信息
        print(f'英语句子: {x}, shape: {x.shape}')
        print(f'法语句子: {y}, shape: {y.shape}')
```

句子最长也就十个单词，因为我们限定了句子长度，所以打出来不会特别长。但要注意：从加载器里拿出来的不是单词本身，而是**单词对应的编号**。

跑一下看结果，只关心最后两行。当前用的设备是 `cuda`，说明跑在 GPU 环境上；想切 CPU 就把环境换成 `nlp-base`，内容完全一样，无所谓。

打出来的英语句子形状是 `[1, 8]`——八个词，这些编号来自 2803 个英语单词表中每个单词的索引。法语句子也是 `[1, 8]`，而这些编号的范围是 4345，因为那是法语词表的长度。

接着做编码过程：

```python
        # 3.3 编码过程
        hidden = my_encoder.initHidden()
        encoder_output, hidden = my_encoder(x, hidden)
```

编码器底层就是一个 GRU：把本次的输入 `x` 和上一次的隐藏状态 `hidden` 丢进去，返回本次的隐藏状态和本次的输出。

两个返回值的含义分清楚：

- `encoder_output` 是**所有时间步**的输出，所以它保留了序列长度这一维，形状是 `[1, 8, 256]`；
- `hidden` 是**最后一个时间步**的隐藏状态，形状是 `[1, 1, 256]`。

这跟前面不带注意力的版本完全一样，没有新东西。

### 编码器输出的固定长度张量

3.4 是准备编码器的输出，供注意力机制使用：

```python
        # 3.4 准备编码器输出（后续用于注意力机制）
        encoder_output_c = torch.zeros(max_len, my_encoder.hidden_size, device=device)
```

先想清楚形状。刚才拿到的 `x` 是 `torch.Size([1, 8])`，法语句子是 `[1, 8]`。那有没有可能出现上面是 `[1, 6]`、下面是 `[1, 8]` 的情况？**有**，六个英语单词配八个法语单词，这很正常。既然真实长度不固定，那我们就要把它统一整成 `[1, 10]`——10 就是 `max_len`。

所以这里 `torch.zeros` 造的是一个形状为 `[10, 256]` 的固定大小张量：`max_len` 是 10，`my_encoder.hidden_size` 是 256，`device=device` 把它放到同一个设备上。

> **定义**：这个张量的作用是**存储编码器输出**，并且尺寸固定。它是全零的——这一点后面很关键，因为「零」正好可以当填充位。

#### 固定张量为什么不和图上的 `[1, 6, 256]` 冲突

有人会盯住形状不放：编码器输出明明是 `[1, 6, 256]`，这里怎么就成了 `[10, 256]`？不冲突。

编码器出来的是 `[1, 6, 256]`（假设我只说六个单词），这是**真实**的；而我们建的这个是 `[10, 256]`，这是**我们要的**。把真实的那一份填进这个固定容器里，容器就是 `[10, 256]`。

现在就能回答那个「为什么要升维」的问题了：正因为这个容器是二维的 `[10, 256]`，送到解码器那边去做 `bmm` 时必须是三维，所以前面代码里才会有一个升维动作，把它变成 `[1, 10, 256]`。这两个地方是上下联动的，单看一处确实容易晕。

#### 复制与截断补齐

3.5 把编码器的实际输出复制进这个固定张量：

```python
        # 3.5 将编码器实际输出复制到固定大小的张量中
        for index in range(encoder_output.shape[1]):
            encoder_output_c[index] = encoder_output[0, index]
```

`encoder_output.shape[1]` 拿到的就是这个 6（真实句子长度），`range(6)` 让 `index` 从 0 走到 5。往里填的时候，左边写 `encoder_output_c[index]`——取到的是第 `index` 行那 256 个位置；右边写 `encoder_output[0, index]`——先 `[0]` 摘掉批次维，再取第 `index` 个时间步的 256 维向量。

> **提示**：编码器的输出既要留着当容器里填的料，又要当后面解码器要用的 V，所以我把这两个名字分开写：`encoder_output_c` 是那个固定长度的容器，`encoder_output` 是编码器刚吐出来的真实输出。名字分开了，形状就不会看串。

这个动作的妙处在于，它一次把两件事都做完了：

- **截断**：真实长度超过 10，也只往前 10 个位置复制，多出来的直接不要；
- **补齐**：真实长度不到 10，后面那些位置保持着 `torch.zeros` 留下的 0，天然就是填充。

> **结论**：在上面创建一个固定长度 `[10, 256]` 的张量，其实等价于已经把截断和补齐一起做掉了——剩下的只是把你的数据复制进去。

那这个位置有没有用到之前讲的文本张量处理里那套截断补齐的思路和函数？其实并没有调用那个 `padding` 之类的函数。我想说的是：**思维有了，接下来就是做题的时候把这个技巧、这个思维用上去**。不一定非得用别人底层的源码，你自己把它模拟出来、达到想要的效果就行。学代码一定要灵活，千万不要死记硬背。

### 解码器过程与逐词翻译

3.6 是解码过程：把隐藏状态解码成法语句子。这里有一条硬要求——**必须逐词翻译**。

法语句子长度是 8，那就遍历八次，一个词一个词地让模型预测。它不可能一下子把整句吐出来；如果真让它一次预测整句，就会出现「真实长度是 8、预测出来是 6 或者 10」这种收不回来的情况。

#### 遍历目标句子的时间步

3.6.1 是遍历目标句子的每个时间步，说白了就是遍历它的长度：

```python
        # 3.6 解码器过程
        for i in range(y.shape[1]):
```

`y` 的形状是 `[1, 8]`，我要的不是 `[1, 8]`，而是那个 8，所以写 `y.shape[1]`，把 8 拿到手。

#### 提取当前时间步的目标词索引

3.6.2 提取当前时间步的目标词索引：

```python
            temp = y[0][i].view(1, -1)
```

`y[0]` 先摘掉批次维，拿到那八个词；再 `[i]` 取第 `i` 个。举例来说，如果这一句的编号序列是 `[1595, 992, ...]`，那么 `i=0` 拿到的就是 1595。但这时候它只是一个孤零零的 1595，没有用——所以要 `view` 一下把它转成规范的二维形状。

`view(1, -1)` 的意思是：转成一行，能排多少列就排多少列。这里就变成 `[1, 1]`。

> **易错点**：`view(1)` 和 `view(-1)` 出来的都是一维张量，只有写成 `view(1, -1)` 才是二维。解码器的输入要的是二维的 `[1, 1]`，别在这儿写漏一个参数。

#### 执行解码器前向传播

3.6.3 执行解码器的前向传播：

```python
            output, hidden, attn_weights = my_decoder(temp, hidden, encoder_output_c)
```

把三个输出一次接住。这里的三个实参正好对应前面说的 Q、K、V：

| 实参 | 传入内容 | 角色 | 形状 |
| --- | --- | --- | --- |
| `temp` | 当前时间步的输入词索引 | Q | `[1, 1]` |
| `hidden` | 上一个时间步的隐藏状态 | K | `[1, 1, 256]` |
| `encoder_output_c` | 编码器所有时间步的输出 | V | `[1, 10, 256]` |

`temp` 是「临时的」——这八个单词一个一个一直在变，这会儿是 1595，下次就变成 992，所以它是那个不断变化的查询。

`encoder_output_c` 虽然我们按真实长度讲它是 `[1, 6, 256]`，但它进到解码器里一定会变成 `[1, 10, 256]`，跟图里画的完全对上。

三个返回值也要逐个说清：

- `output`：当前时间步的输出概率分布，形状 `[1, 4345]`；
- `hidden`：当前时间步的隐藏状态，形状 `[1, 1, 256]`；
- `attn_weights`：当前时间步的注意力权重分布，形状 `[1, 10]`。

> **提示**：写注意力版解码器的时候我说过一句话——正常的前向传播返回 `output` 和 `hidden` 两个就够了，数据到这一步本来就是完整的。但因为我们后面要画注意力权重分布图，所以在 `forward` 里多返回了一份权重，这里接收的时候就得用三个变量来接。如果不做可视化，这一项可以不返回。

#### 打印结果

3.6.4 打印结果：

```python
            print(f'解码 output.shape: {output.shape}')
            print(f'解码 hidden.shape: {hidden.shape}')
            print(f'解码 attn_weights.shape: {attn_weights.shape}')
            # 只看一个词
            break
```

三个形状分别是什么其实早就标在图上了：`output` 是 `[1, 4345]`，`hidden` 是 `[1, 1, 256]`，`attn_weights` 是 `[1, 10]`。

那个 `break` 是加在最里面这个 `for` 里的，意思是只看一个词。但注意——**外面还有一层 `for`**，那层才是遍历每一个样本的。所以如果你把 `break` 放在内层，只是每个样本都只看第一个词；想让整个循环只跑一个样本，就得把这个 `break` 挪到外层去。

改完之后再跑一遍，就能看到「只看一个句子样本」的效果。打印的时候顺手加个换行分隔，看起来清楚些。

### 输出形状的含义

跑通以后盯着结果看，有一件事要解释清楚：我输入的是 `[1, 8]`，输出的也是 `[1, 8]`，那 `[1, 4345]` 是什么意思？

- `[1, 4345]` 是对**当前这一个词**在法语词表上的概率分布。真实的下一个词可能是 119，但预测的结果是在 4345 个编号里挑概率最大的那个；接下来要算损失，就是拿它和真实编号比。
- `[1, 10]` 是在生成**这一个词**的时候，对上面那 10 个源端词的权重考虑——也就是那八个英语单词（加上补齐位）各自占多少分量。

换个词再问一遍：这个 `[1, 4345]` 是预测哪个词的概率？假设是 297，那它就是在生成 297 这个词。那么生成 297 的时候，对上面那十个位置，权重分布又是另一份 `[1, 10]`——和生成 119 那份不一样。

往后每一个词都是这样：**每生成一个新词，就有一份新的 `[1, 10]` 权重**。注意力机制就是这样一步步加进去的。

把整段测试代码按步骤合起来：

```python
def dm_test_attn_decoder():

    my_dataloader = get_dataloader()
    # 2.1 创建编码器对象
    my_encoder = EncoderRNN(english_n, 256).to(device)
    # 2.2 创建解码器对象
    my_decoder = AttnDecoderRNN(french_n, 256, dropout_p=0.1, max_len=10).to(device)
    # 3. 模型推理
    for i, (x, y) in enumerate(my_dataloader):
        # 3.1 取一个样本并打印输入信息
        print(f'英语句子: {x}, shape: {x.shape}')
        print(f'法语句子: {y}, shape: {y.shape}')
        # 3.2 编码过程
        hidden = my_encoder.initHidden()
        output, hidden = my_encoder(x, hidden)
        # 3.3 准备固定大小的编码器输出张量
        encoder_output_c = torch.zeros(max_len, my_encoder.hidden_size, device=device)
        # 3.4 复制实际输出，顺带完成截断与补齐
        for index in range(encoder_output.shape[1]):
            encoder_output_c[index] = encoder_output[0, index]
        # 3.5 解码器过程：逐词翻译
        for i in range(y.shape[1]):
            temp = y[0][i].view(1, -1)
            output, hidden, attn_weights = my_decoder(temp, hidden, encoder_output_c)
            print(f'解码 output.shape: {output.shape}')
            print(f'解码 hidden.shape: {hidden.shape}')
            print(f'解码 attn_weights.shape: {attn_weights.shape}')
            break
        # 只看一个样本就退出外层循环

```

把整条测试链路上的形状变化排成一张图，对照着看，每一步的维度就有出处了：

```text
x                      [1, 8]        英语词索引
  |
  v
encoder_output         [1, 8, 256]   所有时间步的输出
encoder_hidden         [1, 1, 256]   最后一个时间步的隐藏状态
  |

encoder_output_c       [10, 256]     固定容器，多出的位置由 0 填充
  |

  |
  +------------------------+
  |                        |
temp  [1, 1]  ------------> Q
hidden [1, 1, 256] -------> K
encoder_output_c ---------> V
```

### 编码器的两个层与中间语义张量

编码器的编码过程，简单讲就是两层。

第一层是词嵌入层（embedding），把输入的英文单词序列换成稠密向量；第二层是 GRU（Gated Recurrent Unit，门控循环单元）层，按时间步扫过这个序列。这两层前后相接，一层做映射，一层做时序建模。

处理完之后得到的数据不是给分类器用的，也不是给损失函数用的，而是用来获取中间语义张量 $c$，它要传给解码器，供解码器做具体的生成工作。

```text
英文句子
   │
   ▼
[ 词嵌入层 Embedding ]       把词 ID 变成向量
   │
   ▼
[ GRU 层 ]                   按时间步扫描序列
   │
   ▼
中间语义张量 c  ──────────►  交给解码器，用于生成
```

读图说明：编码器对外只交出一个中间语义张量 $c$，它是解码器生成阶段的输入来源；后面带注意力的版本，会额外把 GRU 每一步的输出序列一起交出去参与注意力计算。

### 不带注意力的解码过程

解码的动作，本质是一次查询与一次取最大。

我需要结合 $Q$、$K$、$V$ 这三个值，把它们传给 GRU，最后得到一个 4345 维的输出——也就是 4345 个法语单词上的概率分布。然后在这个分布里找概率最高的那一个，作为本次的最终预测结果。

`4345` 这个数字就是法语词表的规模，不是随便写的常数：预测结果必须落在法语词表的索引范围里，所以输出维度必须等于词表大小。

这一版之所以叫“不带注意力”，是说它没有那套 $QKV$ 的加权运算：每次生成时，喂给 GRU 的语义信息是同一个 $c$，不随当前生成到哪个词而改变。

### 带注意力的解码：把普通 Q 升级成更强的 Q

带注意力机制的解码过程，就是在原来的动作上加了一整套 $QKV$ 操作。这一步到底在干什么？就是你通过 $QKV$ 运算，把你的普通 $Q$ 升级成一个更强大的 $Q$——这个更强的 $Q$ 其实就是那个中间语义张量 $c$，只不过它不是一份固定的 $c$，而是按当前这一步的需要，从编码器所有时间步里加权算出来的 $c$。

> **提示**：所谓“升级”，升级的是信息量而不是维度。普通 $Q$ 里只有“我上一步预测出了什么”这一条线索；经过 $QKV$ 之后，$Q$ 里装进了“源句子里哪几个词对我这一步最有用”这一层信息。维度照旧，内容变强。

加完这一层之后，后续动作都一样：拿这个 $c$ 当本次输入，结合上一时刻的隐藏状态喂给 GRU，再拿输出去和 4345 个法语单词比对概率。这就是两版解码器的全部差别所在。

### 图 1 与图 2 的差别：有没有注意力机制

练习里的图 1 和图 2，差别只有一个：有没有注意力机制。

图 1 没有注意力机制，图 2 有注意力机制。就这么一句，没有第二种区别，也不用往别处找。

> **易错点**：这张图上的 $K$ 不是“键（Key）”那个 $K$，而是 GRU 的隐藏状态。同一个字母在不同图里代表完全不同的东西，认图先认清它是哪张图的哪个角色，别把名字带错。

### 图 2 中 QKV 的形状变化

接着要能说出图 2 里 $Q$、$K$、$V$ 各自的形状，这一步容易答错，也容易被追问。

先看 $K$：它的形状是 `1, sequence_len`，也就是“句子原生有几个词，第二位就是几”。所以它并不一定是 `1, 10`——句子有 6 个词，它就是 `1, 6`。

再看变化：在做变换维度转置（transpose）之前这一步，它会把形状从 `1, sequence_len` 变成 `1, 10`。

> **易错点**：这个位置一定会变成 `1, 10`，但一开始的时候你是多少就多少，不要把它一开始就当成 `1, 10`。被追问的时候要分清“原始形状”和“转置前那一步的形状”，这两句话说的是两个时刻。

为什么必然是 `1, 10`？因为做注意力计算时，编码器的输出需要按统一的长度来参与运算，不足的部分由前面“复刻实际编码器输出”的做法补到固定长度，补完就是 10 个位置、每个位置 256 维。$Q$ 这边同理，`target_y` 经过 `view(1, -1)` 变成 `1, 1`，回到 $Q$ 该有的形状，才能和 $K$ 做匹配。

### 图 2 的完整工作流程

把图 2 用大白话说一遍，它干的事情是这几步。

$Q$ 和 $K$ 先算匹配分，得到一个注意力权重分布；然后这个注意力权重分布与 $V$ 相乘，得到的结果就是中间语义张量 $c$。

但这坨结果不能直接丢给 GRU，它还得往下走两层处理：先经过 combine 这一层，再做降维。降维完事以后再通过激活函数，这才能变回 GRU 要的参数类型。

用一句话压缩：$Q$ 和 $K$ 先算匹配分，匹配分再乘 $V$，得到中间语义张量 $c$；$c$ 做 combine、降维、激活，变成 GRU 能吃的输入。

```text
Q (1,1)  ──┐
           ├─► 匹配分 ──► 注意力权重分布 ──┐
K (1,10) ──┘                              │
                                          ▼
V (1,10,256) ───────────────────────► 相乘 ──► 中间语义张量 c
                                                    │
                                                    ▼
                                        combine ──► 降维 ──► 激活
                                                    │
                                                    ▼
                                        GRU 可以接受的输入
```

读图说明：$Q$ 与 $K$ 的匹配分负责决定“看哪儿”，乘上 $V$ 负责“取到什么”，combine 与降维负责把形状和数值性质调整到 GRU 能接收的样子。

### GRU 四个参数的读图法

到了图 2 的右半边，重点是中间语义张量 $c$ 充当本次的输入。那本次的输入除了它以外，是否还要上一时刻的隐藏状态？要。上一时刻的隐藏状态就是图上那个 $K$。

通过本次的输入和上一时刻的隐藏状态，就能得到本次的隐藏状态和本次的输出。GRU 就是靠这四个参数，把整张图描述完了。

所以这张图要分四块来理解：

- 第一块，GRU 本体——我们要调的那个函数；
- 第二块，充当上一次的隐藏状态；
- 第三块，充当本次的输入；
- 第四块，分别给出本次的隐藏状态和本次的输出。

> **提示**：图看不明白，往往不是数学不会，是没把它拆成这四块。按这四块去看，它就更好理解了——图上每个箭头的位置就对应一个参数的位置。

流程图里还有一些文字说明，具体流程之前介绍过，这里不再重复展开，细节按上面四块对照着认一遍就够了。模型搭建总结到此完成。

## Day07-03.Teacher Forcing_教师强制(理解)
> 对应分集：P98 | 原始标题：《Day07-03.Teacher Forcing_教师强制(理解)》

接下来要进入模型的训练了，目标是构建出训练函数并真正跑起来。但动手之前有个心理准备要先打：这个案例的训练时长会非常非常长，比之前写过的所有代码都长。所以运行的时候你得能等——或者干脆切到 GPU 环境上去跑。

那为什么不直接开跑？因为在跑之前要先扩展一个知识，叫教师强制（Teacher Forcing，教师强制）。它是什么、有什么作用，我们简单聊聊。顺便还有一个问题得先交代：不就是模型训练嘛，写一个函数就好了，为什么这里要写两个训练函数？

### 为什么要写两个训练函数

先回答第二个问题，因为它决定了后面代码怎么拆。

原先写训练，进去以后都是老一套：设置一下模型模式，上来就预测，预测完了算损失，损失完了三界客（反向传播），然后往下走——代码就那么五六行，所以训练和迭代一直是揉在一起写的。

现在不行了。单批次的训练动作代码挺多，大概二三十行。你要是把每批次的训练和整个模型的分轮分批次训练写在一起，起止结构加上代码会非常非常长，看起来阅读性很差。

所以这次要拆成两个：

- 上面那个函数是**单批次训练过程**——一批次怎么训；
- 下面那个函数才是分轮分批次，它只管骨骼和流程；
- 每一批具体怎么训，到点去调上面那个函数。

> **结论**：模型训练函数搭骨架与流程，具体的训练动作交给单批次函数完成。这么一拆，两个函数各自都在一行能看完的长度上。

### 教师强制的定义

先看它的定义。

> **定义**：教师强制（Teacher Forcing）是一种序列生成任务的训练技巧。在序列到序列（sequence-to-sequence，seq2seq）架构中，解码器每次使用真实结果作为输入的一部分，而不是上一个时间步的输出结果，这种训练方法叫教师强制。

把这句话再念一遍，重点只有两个：**每次**、**真实结果**。是每一次都用真实结果，而不是偶尔纠正一次。

翻译到我们这张图上，理解起来其实很快。先把一件事说清楚：上面那个英文句子是我们的特征，下面那个法语句子 $y$ 是我们要的目标，也就是标签。上面是特征，下面是标签，别晕。

### 一步错，步步错

正常的流程是什么？生成是一个词一个词往外蹦的。

先看第一个位置。这个标签是什么值？是真实值。第一位的真实值记作 119。你预测它的时候，第一步预测对了，输出 119。

好，接下来要预测第二位的 297。这一步你该用谁当输入？按正常流程，是接着用上一步生成的 119 往后做预测。那就把 119 填进去当本次输入，往后推。比如这一次也预测对了，出来 297。

但是你能保证每个词都预测对吗？假设再往后一位，真实值是 465，而这一步你预测出了 300——错了。

错就错了呗，会有什么问题？请你试想一下做数学公式推导的场景：只要一步错，后边步步都是错的，跟下棋差不多。

具体到这一步：如果没有教师强制，下一次要生成 25 的时候，你用的就是那个错的 300 作为本次输入，然后拿它去预测 25。输入本身是错的，你生成的 25 大概率也是错的。这就是一步错、步步错。

### 教师强制的纠正动作

那怎么办？

回到定义里那句话：解码器每次使用真实结果作为输入的一部分。翻译成动作就是——我生成下一个 25 的时候，不管你上一个预测出的是什么，我都把 465 当成已知的结果甩过去，用它来生成 25。

不管你在前一位预测成了什么，我都拿前一位的正确答案填进去，告诉你这几个位置的真实答案该是谁，然后让你去预测 25。**不会告诉你后边词的答案**，只把已经发生过的位置换成正解。这就是教师强制。

#### 用辅导孩子做作业来理解

这个机制其实像辅导小孩做数学题。

假设一道题一共要做八步。他的第三步算错了。你怎么处理？你自己是知道答案的，所以第三步错了，你就纠正他这一步的错误，告诉他正确答案是什么，然后后续的步骤让他自己继续推导——至于下一步他算出啥，你不参与，让他自己预测。等他下一步生成成功了，再生成第五步的时候，你还让他以正确的答案往下推。

要说绝对也不绝对。上初中的时候有没有经历过这种事：公式推导题中间流程全错了，但最后的答案让你算对了。有这种情况。所以这里不能说得太死，只能这么假设：一共八步，第三步算错了，后边步骤大概率全错。

所以教师强制的干预点是**出错的那一步已经被替换成正确答案，而不是替他做完整道题**。我改了第三步，第四步怎么算还是他自己来。

> **提示**：把教师强制理解成“训练时给模型开卷考试”并不准确。它不是把整份答案给它看，而是在它已经写错的那一行旁边写下正确的一行，然后继续让它往下写。

### 教师强制的两个作用

这样做的好处，第一个是避免一步错步步错；第二个是加快收敛。

> **结论**：教师强制能够极大地加快模型的收敛速度，并令模型训练过程更加稳定。

这两条要背下来，用大白话背也行。可以这么记：

- 第一条：矫正模型的预测，避免一步错步步错。换成大白话就是——纠正错误，避免越错越离谱。
- 第二条：大大地加快收敛速度。换成大白话就是——加速训练，让模型学得更快、更稳。

> **定义**：教师强制的本质，是在训练模型的时候用已知正确的答案去纠正模型的错误。

“越快越稳”“纠正错误、避免越错越离谱”——两条里总得记住一条，考的时候按哪个都行。

### 为什么必须“越错越离谱”也要防

“越错越离谱”这个说法是有来由的，它也解释了这个机制为什么重要。

小孩说话往往口无遮拦，不是因为他不在乎，而是因为他考虑得少，知道啥就讲啥。有一次教孩子背诗，背到“遥知兄弟登高处，遍插茱萸少一人”，我问他：茱萸是什么？他不假思索地告诉我：茱萸就是猪和鱼。

后来我告诉他，那是一种植物，如此等等。现在你问班上任何一个同学茱萸是什么，哪怕他没学过这篇课文，也不会说出“猪和鱼”来。差别在哪？在有没有人及时把错的答案纠正过来。模型的预测错误是同一个道理：它不会自己知道刚才那一步跑偏了，你不喂正解进去，它就会顺着错的方向一路推下去，越推越离谱。

所以整个机制收束成一句话：解码器每次使用真实结果作为输入的一部分，而不是使用上一步的运算结果——因为你的上一步运算结果是有可能出错的。不管你在这里生成了什么，我都拿真实结果来做下一次预测：第一个位置拿 119，生成 25 的时候用前面那个数，往后也一样。

## Day07-04.英译法案例_模型训练_单批次(掌握)
> 对应分集：P99 | 原始标题：《Day07-04.英译法案例_模型训练_单批次(掌握)》

教师强制这种训练技巧已经聊完了，一句话概括它的动作：强制干预。因为我们知道真实结果，所以解码器每次把真实结果当作输入的一部分，而不是拿模型自己的预测结果——预测一旦错了一步，基于错误答案往后接着预测，后面有可能全错。

接下来该看具体的训练过程了。真正动手之前，先看一眼这次和以往不一样的地方。

### 训练函数为什么要拆成两个

以往写代码，是把训练函数直接一遍全写下来。这次要分开，写两个。

- 第一个函数是**单批次的训练动作**，即一批次怎么训；
- 第二个函数才把整个分轮分批次训练写出来。

原因很实在：现在单批次训练的代码比较多，写完大概三四十行。你要是把这段代码揉进分轮分批次里，整个函数会非常长，一百多行，看起来就费劲了。所以拆开——**只做一批**。

而我们又知道，这份数据一批其实就一条数据。一个批次一条样本，这是后面所有形状推导的基准。

把上面的函数折叠起来看，它的位置是 `TODO 11`、`TODO 12` 这一段。

> **提示**：这一节里的代码只练真正有用的部分。凡是名字带 `demo`、`test` 的测试代码，你一个都不用练。能保证编码器没有任何问题，你测它干嘛？能保证解码器没有任何问题，你测它干嘛？所以那四个函数里，真正有用的是编码器和解码器这两个；剩下的都是测试，你如果不能保证自己写的代码没问题，那就一步一步测。

本轮要掌握的是：内部迭代训练函数、模型训练函数，以及损失曲线分析——也就是最后要画一下损失曲线。

### 单批次训练函数的参数

先把模型训练参数定义好，一共五个。

| 参数名 | 取值 | 含义 |
| --- | --- | --- |
| `my_lr` | `1e-4` | 学习率 |
| `epochs` | `5` | 训练轮数，至少也要跑三轮、五轮、十轮这个量级 |
| `teacher_forcing_ratio` | `0.5` | 教师强制的比例 |
| `print_interval` | `1000` | 打印信息的间隔，每训练 1000 条往控制台打印一次 |
| `plot_interval` | `100` | 绘图的间隔，每训练 100 条画一次图 |

`teacher_forcing_ratio` 这个值是 0.5 的含义要记准：一会儿会生成一个随机数，随机数比它小（小于这个阈值）就触发教师强制，比它大就不触发。所以 0.5 就是**有一半的概率会用上教师强制**。

> **易错点**：打印间隔和绘图间隔的作用域是分开的。打印是往控制台上打，1000 条一打印；绘图是画损失曲线时每 100 条画一次。两个数不要互相代入。

### 单批次训练函数的作用与入参

函数的任务范围，用一句话卡住：**完成一个样本从编码、到解码、到反向传播、到优化参数这一整条链路。**

函数签名收八个入参：

```python
def train_iterators(x, y, my_encoder_rnn, my_attn_decoder_rnn,
                    my_adam_encoder, my_adam_decoder, my_cross_entropy_loss):
    pass
```

逐个说清它们的身份：

- `x`：输入序列，形状为 `(batch_size, sequence_length)`。因为批次一直是 1，所以实际就是 `(1, 16)` 或 `(1, 18)` 这种——句子有多少个词，第二位就是多少。
- `y`：目标序列，即要翻译出来的法语句子，形状同样是 `(batch_size, sequence_length)`。
- `my_encoder_rnn`：编码器对象。
- `my_attn_decoder_rnn`：解码器对象，注意这里用的是**带注意力**的那个解码器。
- `my_adam_encoder` / `my_adam_decoder`：编码器优化器、解码器优化器。
- `my_cross_entropy_loss`：损失函数。

函数注释按这个口径写：实现单批次训练，完成一个样本从编码、解码到反向传播、再到优化参数的过程。

### 编码阶段

第一步，编码阶段：把输入的序列转换为上下文向量。

初始隐藏状态要先算出来：

```python
encoder_hidden = my_encoder_rnn.init_hidden()
```

然后做编码器的前向传播，把本次输入 `x` 和上一次的隐藏状态一起丢进去：

```python
encoder_outputs, encoder_hidden = my_encoder_rnn(x, encoder_hidden)
```

拿回来的两个东西：本次的隐藏状态和本次的输出。隐藏状态是一根链子末端的取值，输出是每个时间步的结果序列。

### 解码参数准备

解码这边的准备工作分四小步，一步都不能省，因为解码器的每次调用都要吃齐这几样东西。

#### 构建用于注意力计算的输出张量

```python
encoder_outputs_c = torch.zeros(max_length, my_encoder.hidden_size)
```

这一步是要拿到形状 `(10, 256)` 的张量。`10` 是参与注意力计算的固定长度，`256` 是隐藏层维度。

这里有个必须解释清楚的疑问：为什么这里是 10，而上一步算出来的 `encoder_outputs` 可能只有 6 个位置？

因为句子长度不固定。你上面的那个长度可能是 `(6, 256)`——只有 6 个单词，不够 10 个。那不够 10 个怎么办？把实际的编码器输出**复刻**进去，把长度固定成 10：

```python
for index in range(x.shape[1]):
    encoder_outputs_c[index] = encoder_outputs[0][index]
```

`x.shape[1]` 拿到的就是那个“6”。循环按实际词数把有效位置填进去，剩下的位置保持全零。

> **结论**：注意力计算需要的是一份长度固定的编码器输出，所以先造一个 `(10, 256)` 的全零张量，再把实际长度的那几步复刻进去——这就是“固定为固定长度的向量”这个动作的写法。

#### 解码器初始隐藏状态

```python
decoder_hidden = encoder_hidden
```

这行代码要读懂它背后的图，否则会觉得莫名其妙。跟着图走：编码器最后一步的隐藏状态，直接当成解码器的第一个隐藏状态。换句话说，解码器这边的 $s_0$ 就等于编码器那边的 $h_3$。

> **提示**：`encoder_hidden` 拿到的是编码器**最后一次**的隐藏状态，不是第一次。所以 `decoder_hidden = encoder_hidden` 这件事，含义是“编码器的最后一个隐藏状态，就是解码器的第一个隐藏状态”。做案例要上下通篇来回看，只看一段会懵。

它的形状是 `(1, 1, 256)`。

#### 解码器初始输入

```python
input_y = torch.tensor([[SOS_token]], device=device)
```

这是解码器的第一次输入。它不是 `welcome`，不是任何真实单词，而是起始标记。这里要特别注意：图上标的可能是 `GO`，但你不能真的写 `GO`。因为我们最开始约定的特殊标记是 `SOS` 和 `EOS`，所以这里的 `SOS_token` 就相当于图上那个 `GO`，它构成解码器第一次调用所需要的内容。

形状是 `(1, 1)`——`[[SOS_token]]` 两层中括号，本来就是二维。

> **易错点**：张量必须迁移到指定设备。这里要写 `device=device`。只要是张量就得迁到指定设备，这样张量才能在指定设备上玩；没迁移，一会儿运算的时候就会报错，告诉你这个张量没有移动上来，用不了。

#### 三样齐了，第一次解码就能发生

到这里，`decoder_hidden` 有了，说明 $s_0$ 有了；`input_y` 有了，说明那个 `GO` 有了。它俩往 GRU 里一传，第一次的输出就出来了。第一次的输出有了，下一次拿它当输入，再结合上一时刻的隐藏状态，就能得到第二次的结果，往后一环扣一环传下去。

### 目标序列长度与教师强制判定

解码循环开始前还有两件事。

```python
my_loss = 0.0
y_len = y.shape[1]
```

`y_len` 是要生成的法语句子的长度。不用去调 `len(y)`——形状里本来就有这个数，直接 `y.shape[1]` 取出来就行，能少调函数就少调函数。假设这句法语有 9 个词，那 `y_len` 就是 9，后面的循环就是 `range(9)`。

接着做教师强制的触发判定：

```python
use_teacher_forcing = True if random.random() < teacher_forcing_ratio else False
```

随机生成一个 0 到 1 之间的值，小于阈值就返回 `True`，大于等于阈值就返回 `False`。

这个判定有一个非常重要的性质，必须讲透：**它并不知道你这一步错没错**。它不是说“我精准地知道第三步错了，所以我就在第三步干预你”——它做不到这个。它只知道这次干不干预、下次干不干预，每一次都是独立按概率抽签。

那会不会出现这种情况：我这次预测错了，但这次没抽到干预？会。有没有可能第一次错没干预，第二次错立马就抽中干预？完全可能。所以这个机制防的是“越错越离谱”，不是“一次都不许错”。

> **提示**：阈值如果设成 1，因为随机数落在 0 到 1 之间，就意味着**永远都用**教师强制。真想把错误彻底堵住，就把它写成 1；反过来，你甚至可以不写这个随机判定，直接用与不用两条分支把代码摆出来。

### 教师强制分支

`if use_teacher_forcing` 走这里，说明使用教师强制：**用真实标签作为下一步的输入**。循环长度是 `y_len`。

```python
if use_teacher_forcing:
    for i in range(y_len):
        output_y, decoder_hidden, attention_weights = my_attn_decoder_rnn(
            input_y, decoder_hidden, encoder_outputs_c)

        target_y = y[0][i].view(1)
        my_loss += my_cross_entropy_loss(output_y, target_y)

        input_y = y[0][i].view(1, -1)
```

#### 解码器的前向传播与形状

解码器的前向传播，就是把入参按位对齐地扔进去：

```python
output_y, decoder_hidden, attention_weights = my_attn_decoder_rnn(
    input_y, decoder_hidden, encoder_outputs_c)
```

这一步的入参与出参形状必须张口就能报出来，因为它是整张网络形状表的核心：

- 输入 `input_y`：`(1, 1)`
- 输入 `decoder_hidden`：`(1, 1, 256)`
- 输入 `encoder_outputs_c`：`(10, 256)`
- 输出 `output_y`：`(1, 4345)`
- 输出 `decoder_hidden`：`(1, 1, 256)`
- 输出 `attention_weights`：`(1, 10)`

`4345` 是法语词表大小，注意力权重压成 `(1, 10)`，正好对应 10 个被看的源位置。

#### 当前时间步的真实标签

```python
target_y = y[0][i].view(1)
```

`y` 是二维的，`y[0]` 拿到里面那个一维列表，再传一个 `i`，就取到一维列表里的第 `i` 个元素——假设取到的是 119。

但直接拿 119 不行，它是一个标量值，后面没法参与运算。要把它转成张量，用 `view(1)` 转成一维，形状就是 `[119]` 这种。

#### 累加损失

```python
my_loss += my_cross_entropy_loss(output_y, target_y)
```

`my_cross_entropy_loss` 就是函数外面传进来的那个损失函数参数，这里直接当交叉熵来用。扔进去的两个东西：`output_y` 是刚才前向传播返回的结果，`target_y` 是这一步的真实标签。

> **提示**：`target_y` 用 `view(1)` 而不是 `view(1, -1)`，是因为这里要的是一维形状 `[119]`，好和 `output_y` 那二维的一批概率做比对。到了下一小步要用它当输入时，才需要再升成二维——同一个标签，在两个不同的用途下要摆成两种形状，这是最容易写错的地方。

#### 下一个时间步的输入

```python
input_y = y[0][i].view(1, -1)
```

走教师强制分支，下一个时间步的输入直接使用真实标签。注意这里取的是 `y[0][i]`，也就是 119 本身，不是 `i + 1`——因为本次要预测的是下一位，而喂进去的是这一位已经发生过的真值。

`view(1, -1)` 把它变成 `(1, 1)` 这种形状，形状一回到 `(1, 1)`，就正好对上图上 $Q$ 的位置。

> **易错点**：`view(1)` 是一维，`view(1, -1)` 是二维，这两个千万不能混。前者用于算损失，后者用于当前馈输入，写反了形状就对不上。

### 非教师强制分支

`else` 与 `if use_teacher_forcing` 对应，走这里说明不使用教师强制：**使用上一步的预测结果作为下一步的输入**。

```python
else:
    for i in range(y_len):
        output_y, decoder_hidden, attention_weights = my_attn_decoder_rnn(
            input_y, decoder_hidden, encoder_outputs_c)

        target_y = y[0][i].view(1)
        my_loss += my_cross_entropy_loss(output_y, target_y)

        top_v, top_i = output_y.topk(1)
        if top_i.squeeze().item() == EOS_token:
            break
        input_y = top_i.detach()
```

前两小步和教师强制分支完全一样：解码器前向传播，取当前时间步的真实标签（损失照样要用真实标签来算，只是输入换了来源），累加损失。

不一样的是后面这两步。

#### 取概率最高的词

```python
top_v, top_i = output_y.topk(1)
```

获取预测的下一个词，也就是概率最高的那个词的索引和概率。`topk(1)` 拿到的就是第一名的值和它的索引。

#### 遇到结束标记就停止

```python
if top_i.squeeze().item() == EOS_token:
    break
```

如果预测到了句子的结束标记，就停止预测，不再往后生成了。`squeeze()` 把多余维度去掉，`item()` 取出那个标量值，再和 `EOS_token` 比对。

#### 把预测词接成下一次输入

```python
input_y = top_i.detach()
```

走到这里才说明：没有预测到结束标记，那就把预测出来的词作为下一个时间步的输入。

> **易错点**：这里必须加 `detach()`。因为要反向传播，而这一步的输入来自模型自己的预测，不能让这条“预测接预测”的链条把梯度一路往回穿，所以要把它从计算图上摘下来。形状和上面的 `input_y` 一样，都是 `(1, 1)`——区别只在于一个是真实值，一个是预测值。

### 反向传播与参数更新

两条分支的 `if / else` 折叠起来，里面的东西只做了一件事：把下一次时间步的输入准备好。分支之外，就是第五步——反向传播和参数更新。

```python
my_adam_encoder.zero_grad()
my_adam_decoder.zero_grad()

my_loss.backward()

my_adam_encoder.step()
my_adam_decoder.step()
```

梯度清零要清两个：编码器的优化器和解码器的优化器，一个都不能漏。然后 `my_loss.backward()` 做反向传播。最后两步是参数更新：`encoder` 更新一次，`decoder` 再更新一次，因为这两个子网络各自有自己的优化器。

> **提示**：清零、反向、更新这三件事的顺序不能颠倒。梯度是累加的，不清零就会把上一步的残留带进来。

### 返回平均损失

第六步，返回平均损失：

```python
return my_loss.item() / y_len
```

`my_loss` 里累加的是这条样本在这个批次里的全部损失，`.item()` 把它取成标量，再除以 `y_len` 得到每个时间步的平均损失。

到这里，单批次训练就写完了。下一个函数要做的才是分轮分批次——写两层 `for`，外层控制轮数、内层控制每轮的批次数，然后把这个函数调进去就结束了。

> **结论**：单批次的训练就已经这么麻烦，所以更要把它单独抽成函数；跟多轮多批次写在一起，函数就没法看了。

### 单批次训练的整体流程

把六个步骤串起来，一次单批次训练从入参到返回值走的就是这条路：

```text
x, y, 编码器, 带注意力解码器, 两个优化器, 交叉熵损失
        │
        ▼
[1] 编码阶段
    encoder_hidden = 编码器.init_hidden()
    encoder_outputs, encoder_hidden = 编码器(x, encoder_hidden)
        │
        ▼
[2] 解码参数准备
    2.1 构建注意力用的输出张量 (10, 256)，复刻实际长度
    2.2 encoder_outputs_c 填实际步
    2.3 decoder_hidden = encoder_hidden          -> s0
    2.4 input_y = [[SOS_token]]，device=device    -> GO
        │
        ▼
[3] my_loss = 0.0 ; y_len = y.shape[1]
        │
        ▼
[4] use_teacher_forcing = 随机数 < ratio
        │
        ├── True  ──► 每个时间步：前向传播 -> 取真实标签 -> 累加损失
        │              -> input_y = 真实标签(view(1,-1))
        │
        └── False ──► 每个时间步：前向传播 -> 取真实标签 -> 累加损失
                       -> topk(1) 取最高概率词
                       -> 命中 EOS 则 break
                       -> 否则 input_y = 预测词.detach()
        │
        ▼
[5] 两个优化器 zero_grad -> loss.backward -> 两个优化器 step
        │
        ▼
[6] return my_loss.item() / y_len
```

读图说明：第 1、2 步只做一次，把解码器需要的隐藏状态、起始输入和源端张量准备齐；第 4 步是每个时间步都要重复的核心循环，两条分支只在“下一步输入从哪来”上不同；第 5、6 步在整条样本跑完后执行一次。

## Day07-05.扩展_view()函数演示(理解)
> 对应分集：P100 | 原始标题：《Day07-05.扩展_view()函数演示(理解)》

我们前面写英译法（seq2seq）训练代码的时候，你可能已经被一行代码卡住过：`y0_i.view(1, -1)`。它出现在 teacher forcing 的输入构造里，也出现在解码器拿上一步真实标签当下一步输入的地方。这行代码本身没有任何算法含量，可它偏偏长得可疑——里面那个 `1` 是什么意思，`-1` 又是什么意思，为什么括号里有的时候是一个数、有的时候是两个数？

这一节我们就专门花几分钟，把 `view()` 这个动作拆开看一遍。方法特别土：新建一个脚本，只留数据准备和打印两件事，把那一行代码单独拉出来做一次实验。

> **提示**：遇到看不懂的函数，别在原地死磕那一行。先把它的数据源模拟出来，单独跑一次，看输入是什么形状、输出是什么形状、括号里的数各自负责什么。这是本文真正想留给你的一条工作方法。

---

### 实验脚本：一维视图与二维视图

新开一个脚本 `demo02`，主题就写「view 函数测试」。我们要对照两种写法：

```python
import torch

# 1. 准备数据：模拟前面法语句子的那份 y
y = torch.randint(0, 4345, size=(1, 7))

# 2. 打印结果
print(y)
print(y.shape)
```

先看数据准备这一步。`torch.randint(0, 4345, size=(1, 7))` 的意思是：在 $[0, 4345)$ 这个左闭右开区间里随机取整数，取够 `size=(1, 7)` 这么多——也就是 1 行 7 列，共 7 个数。

`4345` 不是随手写的数字，它是法语词汇表的大小。所以这一行 `y` 模拟的正是前面那份法语句子对应的标签张量：形状是 `(1, 7)`，代表 1 个句子、句子编码后长度 7 个词元（token）。打印 `y.shape`，得到的应该是：

```text
torch.Size([1, 7])
```

> **定义**：`view()` 是 PyTorch 张量（`Tensor`）的对象方法，用来在不复制数据的前提下重新解释这块内存的形状，返回一个共享底层存储的新张量。

现在把注意力移到第二件事——打印。前面代码里出现的 `y0`、`y0_i`，很多同学在这里会顿一下：`y0` 是什么？

`y0` 就是 `y[0]`，也就是 `y` 里第 0 行。而 `y` 的形状是 `(1, 7)`，只有一行，所以 `y0` 拿到的就是里面那唯一一个句子——**它本身还是一个张量**，形状是 `(7,)`。`y0` 是句子，`y0[3]` 才是句子里的第 4 个词元。这就是我们前面写的 `y0_i` 那个 i 的含义：句子 `y[0]` 里索引为 `i` 的那个位置。

接着看 `y0[3]`。索引 3 取的是第 4 个数（索引从 0 数起：0、1、2、3）。跑一次可能是 94，再跑一次可能变成 2442——**这个数字会变**。

> **注意**：`torch.randint` 是随机取数，你每右键重跑一次，里面的数都不一样。不要因为数字变了就以为自己写错了。变的只是数值，形状永远不变，这才是我们要盯住的东西。

---

### 同一份数据的三种 view 写法

把 `y0[3]` 这一个标量拿出来，分别接上三种 `view`：

```python
# 打印结果：连形状一起打出来
print(y, y.shape)
print(y[0], y[0].shape)              # 句子本身
print(y[0][3])                       # 标量：tensor(94)

print(y[0][3].view(1))               # 一维
print(y[0][3].view(-1))              # 一维
print(y[0][3].view(1, -1))           # 二维
```

`y0[3]` 是一个 0 维张量（标量，`dim() == 0`），类似 `tensor(94)`。它后面接三个不同的 `view`，结果分成两类：

| 表达式 | 输出形状 | 维度 | 说明 |
| --- | --- | --- | --- |
| `y0[3]` | `()` | 0 维 | 裸标量，`tensor(94)` |
| `y0[3].view(1)` | `(1,)` | 1 维 | 外层加一层中括号，`tensor([94])` |
| `y0[3].view(-1)` | `(1,)` | 1 维 | 与 `view(1)` 等价 |
| `y0[3].view(1, -1)` | `(1, 1)` | 2 维 | 再加一层中括号，`tensor([[94]])` |

看打印出来的样子最直观：`tensor(94)` 外面没有中括号；`view(1)` 之后变成 `tensor([94])`；`view(1, -1)` 之后变成 `tensor([[94]])`。**每多一层中括号，就多一个维度。**

`view(1)` 和 `view(-1)` 输出完全一样，因为这里总共只有 1 个元素，`-1` 让 PyTorch 自己算出这一维该填几，算出来就是 1。

---

### -1 的语义：占位符与推断

`view()` 括号里的每一个数都是一维的长度，正常情况下个数必须和原张量的维数对得上——三维张量就得写三个数。

`-1` 是唯一的例外，它是一个占位符：**这一维的长度我不写，由 PyTorch 根据元素总数和其余几维推出来。**

推导的约束很简单，就是元素个数守恒：

$$ \prod_{k} d_k = N $$

其中 $d_k$ 是 `view` 之后各维的长度，$N$ 是原张量的元素总数。只有一维写 `-1` 时，这一维的长度由 $N$ 除以其余维度的乘积唯一确定。

回到英译法训练代码里的那行 `y0_i.view(1, -1)`：`y0_i` 是一个标量，总共只有 1 个元素，`(1, -1)` 告诉 PyTorch「第 0 维长度是 1，第 1 维你自己算」。$1 \times d_1 = 1$，于是 $d_1 = 1$，结果是形状 `(1, 1)` 的二维张量。

为什么非要升到二维？因为解码器的一次前向计算处理的是一个时间步的输入，模型内部按批次处理，期望进来的输入永远是「批大小 × 特征长度」这种二维形式，哪怕批大小就是 1、特征长度也是 1。`view(1, -1)` 做的就是把裸标量补成符合接口要求的形状。

> **易错点**：`view()` 只在元素总数能整除目标形状时才成立，而且各维长度的乘积必须严格等于原来的元素总数。`view` 过程中不能改变元素个数，也不能跨内存跳着取数——它只是重新解释形状。若需要改变元素个数，那属于切片、拼接或索引，不是 `view` 的职责。

---

### 数据流：从句子张量到模型输入

把上面的动作连起来看，就是一条完整的形状变化链：

```text
y                       torch.randint(0, 4345, size=(1, 7))
   shape = (1, 7)       1 个句子, 句子长度 7

   |  y[0]  取第 0 个句子（外层降一维）
   v
y0                      tensor([...])
   shape = (7,)         句子本身，仍是一维张量

   |  y0[i]  取句子里第 i 个词元
   v
y0_i                    tensor(94)
   shape = ()           0 维标量，单个数

   |  .view(1, -1)  补成模型要的二维形式
   v
y0_i.view(1, -1)        tensor([[94]])
   shape = (1, 1)       批大小 1, 特征长度 1
```

读图：`view(1, -1)` 与它上面的区别只有一件事——把标量 `tensor(94)` 加上一层中括号变成 `tensor([[94]])`，容器形状从「什么都没有」变成「批大小 1、特征长度 1」。数值自始至终没动过。

> **结论**：`view(1, -1)` 的作用就是「封装成二维张量」。它不计算，不查找，不改变数据，只改变数据的形状描述。至于为什么在训练里要这么封装，答案在模型的接口约定上，而不是在这个函数本身。

### 编码器、解码器与优化器初始化

接下来把网络部件按前面定好的参数搭起来。

```python
    # 2.1 编码器：输入维度 = 英文词汇表大小 2803，隐藏层维度 256
    my_encoder_rnn = EncoderRNN(2803, 256).to(device)

    # 2.2 解码器：输入维度 = 法语词汇表大小 4345，隐藏层维度 256
    my_attention_decoder_rnn = AttentionDecoderRNN(
        4345, 256, dropout_p=0.1, max_length=10
    ).to(device)

    # 3. 优化器：Adam，学习率 my_lr = 1e-4
    my_adam_encoder = optim.Adam(my_encoder_rnn.parameters(), lr=my_lr)
    my_adam_decoder = optim.Adam(
        my_attention_decoder_rnn.parameters(), lr=my_lr
    )
```

编码器只有两个参数：输入维度等于**英文词汇表大小 2803**，隐藏层维度是 256。它没有「输出维度」这一项，因为输出维度就是隐藏层维度。

解码器则是两个不同的数：输入维度等于**法语词汇表大小 4345**（因为它要看的是目标语言在这个时间步的输入），输出维度是隐藏层维度 256。

> **易错点**：解码器的输入维度是法语词汇表大小，不是隐藏层维度。这两个数千万别串了——一个是「词表里有多少个词」，一个是「每个词被表示成多长的向量」。

至于 `dropout_p=0.1` 和 `max_length=10` 这两个参数，因为后面都有默认值，所以**不写也能跑**。我在这里给你写上，是为了让你知道有这么两个东西存在；实际开发的时候，人家都有默认参数了，写它干什么，不写。

优化器用 Adam，编码器和解码器各一个，学习率用上面已经定义好的 `my_lr`，也就是 `1e-4`。参数直接用 `.parameters()` 从模型里取，一行一个，不需要你手工列。

### 损失函数的选择

这里有一个必须停下来讲的坑。

我猜你第一反应肯定是 `CrossEntropyLoss`。你说得对，但**这个场景下不能用它**。

原因在解码器里：`AttentionDecoderRNN` 在最后一步已经做过 `log_softmax` 了。而 `nn.CrossEntropyLoss` 内部自己做的是 `log_softmax` + `NLLLoss` 两步。解码器已经吐出了对数概率，你再套一层 `CrossEntropyLoss`，等于**把 softmax 算了两次**——分布被压了两遍，训练结果自然不对。

有两条路可选：

1. 把解码器里那行 `log_softmax` 删掉，然后用 `CrossEntropyLoss`；
2. 保留 `log_softmax`，损失函数换成 `nn.NLLLoss()`。

我们不动解码器，走第二条路：

```python
    # 4. 损失函数初始化
    my_cross_entropy = nn.NLLLoss()
```

> **结论**：`log_softmax` 与 `NLLLoss` 是一对；`CrossEntropyLoss` 内部自带 `log_softmax`，配的是未经 softmax 的原始 logits。配对关系弄混，就是「多算一回」，是这类代码里最常见的一类静默错误。

### 多轮多批次训练主循环

现在是核心部分。两层循环，各管一件事。

#### 外层循环：控制训练的轮数

```python
    # 6.1 外层循环：控制训练的轮数
    for epoch_index in range(1, epochs + 1):
        # 6.1.1 初始化本轮的两个损失累加器
        print_loss_total = 0.0
        plot_loss_total = 0.0

        # 6.1.2 记录本轮开始训练的时间
        start_time = time.time()
```

`range(1, epochs + 1)` 展开就是 1 到 5。为什么不写 `range(epochs)`？因为我想让轮次从 1 开始编号，这样后面保存模型文件时文件名里直接就是这个轮次，好认、好看。要是从 0 开始，你在存文件名的时候还得再写个 `+1`。

两个累加器都是本轮专属的：`print_loss_total` 累计给控制台打印用的损失，`plot_loss_total` 累计给绘图用的损失。它们**在本轮开始时清零**，这一点很关键，后面会看到为什么。

#### 内层循环：遍历每个批次

```python
        # 6.2 内层循环：遍历数据集的每个批次
        for item, (x, y) in enumerate(tqdm(my_dataloader), start=1):
            # 6.2.1 调用内部训练函数，完成单批次（单样本）训练
            my_loss = train_iters(  # 单批次的训练函数
                x, y,
                my_encoder_rnn, my_attention_decoder_rnn,
                my_adam_encoder, my_adam_decoder,
                my_cross_entropy,
                device,
            )

            # 6.2.2 累加损失
            print_loss_total += my_loss
            plot_loss_total += my_loss
```

有三处值得单独说。

**第一，`enumerate(..., start=1)`。** `enumerate` 会给序列里的每个元素在前面加一个索引，默认从 0 开始编号。加上 `start=1`，索引就从 1 开始。写 `for item, (x, y) in enumerate(...)` 是因为数据加载器每一次吐出来的就是一个 `(x, y)` 元组；在它外面套一层 `enumerate`，就能同时拿到「第几个批次」这个编号，也就是 `item`。

**第二，`tqdm`。** 我本来只想写最朴素的 `enumerate`，但那样看不到进度。把数据加载器用 `tqdm(...)` 包起来，就能以进度条的形式显示训练进度。这是最终要的写法：

```python
for item, (x, y) in enumerate(tqdm(my_dataloader), start=1):
```

> **提示**：进度条不是一开始就动的。刚开始它还停在 1%、2% 的位置，别以为程序卡死了。等它走过一小段，进度条才会动起来。

**第三，`train_iters` 的参数为什么能原样复制过来。** 因为我在这两个函数里定义的参数名完全一样，`Ctrl+C`、`Ctrl+V` 就完了，一个字都不用改。参数名一样是我照着上面那函数抄的，当然不会写错。

**函数调用时，形参名和实参名不一样也可以**，位置对上就行。但位置一旦错了，模型和优化器就可能传反，这种错误不会报错，只会让你训练半天发现不收敛——所以不如干脆把名字写成一样。

#### 损失累加

有一个细节：`train_iters` 返回的这批损失，是**这一批的平均损失**，不是总和。因为单批次训练函数最后除以了句子长度 `len`，所以它给出来的是按词元平均后的值。

既然它是平均值，多批累加之后就还需要再除一次批次数量，才能得到区间平均值——这一点下面立刻就用上。

两个累加器都要加同一个损失值，因为它们是两个用途：一个负责往控制台打印，一个负责画图。用途不同，数据来源是同一个。

---

### 日志打印与累加器重置

```python
        # 6.3 打印训练日志：每 1000 个样本打印一次
        if item % print_interval_num == 0:
            print_loss_avg = print_loss_total / print_interval_num
            print_loss_total = 0.0
            print(
                f'轮次: {epoch_index}, '
                f'平均损失: {print_loss_avg:.6f}, '
                f'耗时: {time.time() - start_time:.0f}s'
            )
```

`item` 每 1000 的倍数就触发一次。平均损失用 `print_loss_total / print_interval_num` 算——这里累加器里装的是这 1000 个句子的损失和，除以 1000，就是这 1000 个句子的平均损失。

耗时用 `time.time() - start_time`，单位是秒，所以后面标一个 `s`。它是**从本轮开始到现在**的累计耗时，所以你会看到这个数字一条比一条大。

打印完立刻做一件事：**把 `print_loss_total` 重置为 0。**

> **易错点**：这一步如果漏了，累加器永远不会清零。那么第一条日志是前 1000 条的平均，第二条就变成了前 2000 条的平均，第三条是前 3000 条——你算的是不断拉长的累计平均，根本看不出最近这 1000 条的实际效果。加上重置，每一条日志都是干干净净的「刚刚这 1000 条」。

---

### 损失曲线数据的记录与重置

```python
        # 6.4 每 100 个样本记录一次损失，用于绘图
        if item % plot_interval_num == 0:
            plot_loss_avg = plot_loss_total / plot_interval_num
            plot_losses_list.append(plot_loss_avg)
            plot_loss_total = 0.0
```

逻辑和上一节一模一样，只是换了间隔和去向：间隔是 100，算出来的是这 100 条的区间平均损失，然后 `append` 进 `plot_losses_list`。最后画折线图时，横轴就是这些点的顺序，纵轴就是损失值。

`plot_loss_total` 同样要在记录完之后清零。

到这里你大概能看出规律了：**累计 → 到点算平均 → 入账 → 清零**，这四个动作在打印和绘图两条线上各出现一次。

### 逐轮保存模型

```python
        # 6.3 一轮训练完毕：保存模型
        if item > 3000:
            break

        torch.save(
            my_encoder_rnn.state_dict(),
            f'./model/my_encoder_rnn_{epoch_index}.pth'
        )
        torch.save(
            my_attention_decoder_rnn.state_dict(),
            f'./model/my_attention_decoder_rnn_{epoch_index}.pth'
        )
```

先说缩进。这一段写在 `for epoch_index` 里面、`for item` 外面——**能走到这里，说明这一轮的所有批次都跑完了**。

保存什么呢？`state_dict()`，也就是模型的参数。路径写到 `./model/` 下面，文件名带上 `epoch_index`。

**为什么文件名要带 `epoch_index`？** 因为不带的话，第二轮保存时会直接覆盖第一轮的结果。带上轮次编号，每轮一个文件，历史全留着——这也是我把 `epoch_index` 从 1 开始编号的第二个理由。

> **提示**：`.pth` 这类文件的常见后缀还有 `.ptl`、`.pkl`、`.pickle`，用哪个都可以，它们本质上都是 pickle 序列化出来的文件。但你不能什么后缀都不写，也不能随便乱起个扩展名。

#### 为什么一轮一保存

这才是我最想让你记住的一段。

一轮训练要 50 分钟。如果 5 轮一起跑完再统一保存，那意味着你要在一个多小时的窗口里一动不动地等着：中间你去点了终止、机器崩了、服务器宕机了、停电了、被人攻击了——**你什么都不会剩下。**眼睁睁看着好不容易跑到只差最后 10 分钟，结果前功尽弃。

所以正确做法是：**一轮一做，一轮一存。**或者做得再细一点，永远只保留最近 3 个模型——训练到第 4 轮生成成功了就把第 1 个删掉，第 5 轮成功了就删第 2 个，滚动地留着最后三个。

大模型训练没有任何一家公司会把 100 轮跑完才存一次。跑一轮要 7 天，指望最后那一下保存，等于把两个月的成本押在一次不断电上。

### 实测：CPU 与 GPU 的对比

把上面那个多轮多批次训练函数注释掉，改调 `train_sequence()` 跑起来，5 轮、每轮 3000 条。

先看 CPU 环境。进度条一开始几乎不动，因为 3000 条里跑到 1%、2% 才会动一下。第一批 1000 条打印出来：**35 秒**。按 6.3 万条算，是 63 个打印批次：

$$ 63 \times 35 = 2205 \ \text{s} \approx 36.75 \ \text{分钟} $$

跟我估计的 50 分钟同量级，这次 CPU 状态还不错——正常应该在 45 秒左右一批。按 45 秒算，$63 \times 45 = 2835 \ \text{s}$，差不多 47 分钟，剩下的一点凑到 50 分钟。5 轮就是 250 分钟左右，用我原来的估算是 3 个小时往上。

再看一件很有意思的现象：进度条才走到 5% 左右，程序就跳到第二轮了。**不是因为它没跑完 6 万条，而是因为我们自己写了每轮只训 3000 条。**你写的代码，你自己看。

然后在第一轮跑到一半的时候，我在界面上点了终止：

```text
KeyboardInterrupt / 人为终止导致的报错
```

一停，程序就报错了。但**第一轮的模型已经存下来了**——这就是分轮保存的价值。要是以前那种「所有轮跑完最后存一次」的写法，这一停就是彻底归零。以前为什么可以那样写？因为数据量小，瞬间就跑完了，根本来不及出意外。

换成 GPU（`LS-base` 之类的 GPU 运行配置，我这台是 2060）再跑：

| 批次 | CPU 每 1000 条 | GPU 每 1000 条 | 提升 |
| --- | --- | --- | --- |
| 第 1 批 | 35 秒 | 23 秒 | 约 1.5 倍 |
| 第 2 批 | — | 23 秒 | 稳定 |

23 秒对 35 秒，提升接近一半，而且两批之间非常稳定。要是按 CPU 正常值 45 秒算，那提升就接近一倍了。当然，我这只是 2060，换更好的卡只会更快。

## Day07-07.英译法案例_模型训练_总结(理解)
> 对应分集：P102 | 原始标题：《Day07-07.英译法案例_模型训练_总结(理解)》

程序跑完了。5 轮，每轮大概 1 分钟——这是因为我每轮只训了 3000 条。现在该做两件事：看一眼它到底产出了什么，然后把整个训练流程从头到尾捋一遍。

---

### 训练产物的核对

先看控制台。5 轮的日志一条一条往下走：第 1 轮、第 2 轮、第 3 轮、第 4 轮、第 5 轮，每轮里面每 1000 条打一次，这个节奏跟我前面设的 `print_interval_num` 对得上。

因为现在用的是 CUDA，也就是**显卡**在跑，一批 1000 条数据大概 20 秒左右。这个数字你可以拿来估自己的时间：1000 条 20 秒，那 6.3 万条一轮就是 63 批，$63 \times 20 = 1260$ 秒，二十来分钟一轮。

> **注意**：日志里出现的耗时是从本轮开始累计的，不是单批耗时。想算单批速度，就盯住相邻两条日志之间的差值。

再数模型文件。跑去 `model` 目录里看一眼，里面一共是 **10 个**文件。为什么是 10？**5 轮，每轮存一个编码器加一个解码器**，$5 \times 2 = 10$。我们前面在每一轮结束的时候各存了两个 `state_dict()`，编号是靠文件名里的 `epoch_index` 区分开的，所以这 5 组模型一组都没被覆盖。

同目录下还有一张图片，就是训练过程里画出来的损失曲线，长成一条一路向下的样子。不想在这儿看也没关系——我们前面用 `plt.savefig` 把它存到 `image` 文件夹下了，双击打开一样看。

打开 `image` 里的那张图，跟我笔记里画的曲线形状基本一致。横轴是样本区间的顺序，纵轴是每 100 个样本的平均损失。

> **提示**：想让曲线更细，就把绘图间隔调小。现在是 100 个样本记一个点，改成 10 个、甚至 1 个样本记一个点都行，代价是点变密、保存的图变大而已。

曲线整体一直在往下走，这件事本身就说明问题：**模型在收敛。**不是「看起来还行」，而是损失单调下降，训练没有跑偏。

---

### 单批次训练的内部实现

现在把整个训练流程复述一遍，方便你自查有没有哪一步漏掉。

内部迭代，也就是单批次（单样本）训练，顺序是这样的：

```text
1. 编码：把源语言句子送进编码器
2. 解码：把编码结果送进解码器，得到输出
3. 训练策略：决定这一步要不要用 teacher forcing
     - 用 teacher forcing：拿上一步的【真实值】作为下一步的输入
     - 不用 teacher forcing：拿本次的【预测值】作为下一次的输入
4. 梯度清零
5. 反向传播
6. 梯度更新
```

第 4、5、6 步就是那套「三剑客」——梯度清零、反向传播、梯度更新，顺序不能乱，也不用多解释。

> **易错点**：第 3 步的二选一里，用 teacher forcing 时喂进去的是**上一步的真实标签**，不用时喂进去的是**本次的预测结果**。这两个说法很容易记串，但它们是同一个分岔口的正反两面。

`train_iters` 这个名字里的 iters 指的是一次迭代，也就是一条数据走完上面六步。

---

### 多轮多批次训练的外层结构

单批次解决的是「一条数据」，再往上一层就是多轮多批次：定义优化器、定义损失函数，然后两层循环跑起来。这些前面都写过了，这里只把骨架摆出来对比：

```text
train_sequence()
├── 获取 DataLoader
├── 初始化编码器 / 解码器 / 两个 Adam 优化器 / NLLLoss
├── for epoch in 1..5                  <- 外层：轮数
│      ├── 清零 print_loss_total / plot_loss_total
│      ├── 记录 start_time
│      └── for item, (x, y) in enumerate(tqdm(loader)):
│             ├── train_iters(...)     <- 单批次训练
│             ├── 累加损失
│             ├── 每 1000 条：算平均、打印、清零
│             ├── 每 100 条：算平均、入列表、清零
│             └── （调试用）item > 3000 就 break
│      └── 保存本轮模型
└── 画损失曲线、保存图片、返回损失列表
```

读图：内层那个 `train_iters(...)` 调用就是整个结构里最关键的一行，它把上一节那六步整个包住了。

**为什么要拆成两个函数？**这是这节课我最想强调的一个工程判断。如果把单批次训练的代码直接摊在多轮多批次的循环里，那个函数会变得非常非常臃肿——四五十行起步，加上两层循环、日志、绘图、保存，一眼看过去根本不知道哪段在干正事。

拆开之后：`train_iters` 只负责「一条数据怎么训」，`train_sequence` 只负责「训多少轮、多少批、什么时候记账、什么时候存档」。各自的职责单一，读起来、改起来都清爽。**分开写会更好看一些**，这不是审美问题，是能不能维护的问题。

### 本讲提到的题目

**第 1 题（单选）**：什么是 teacher forcing？它在 NLP 里的作用是什么？

- A. 一种处理缺失值的机制
- B. 一种生成模型的训练策略，每个时间步接收真实序列作为输入
- C. 一种降低过拟合的手段

**答案：B。**

解析：teacher forcing 是训练阶段的一种输入策略——把上一步的**真实值**作为当前时间步的输入喂给解码器，让生成模型能沿着真实序列往前走，避免早期的预测偏差被一路放大。它不处理缺失值，也不是正则化手段，所以 A、C 都不成立。它的判断依据在单批次训练的第 3 步：用 teacher forcing 就喂真实值，不用就喂自己的预测值。

**第 2 题（单选）**：关于 teacher forcing 的使用，下面哪个描述是正确的？

- A. 能保证模型在训练时产出准确的输出
- B. 可能导致模型在推理阶段出现不稳定的情况
- C. 只适用于 RNN 模型

**答案：B。**

解析：A 混淆了训练阶段和推理阶段。**训练本身并不产生最终输出**，它做的是前向计算加参数更新，所以谈不上「保证训练时输出准确」。C 不成立，teacher forcing 是序列生成任务的通用训练策略，并不限于 RNN。真正要防的是 B：训练时每一步都能拿到真实值，模型没经历过「顺着自己出错的预测往下走」这种情况；到了推理阶段，输入只能来自自己的预测，前面一偏后面就滚雪球，表现出来就是不稳定的生成结果。

> **提示**：这就是为什么 teacher forcing 的概率不要设大。我们这个案例里写的是 0.5，保持这个量级就好。设成 1 相当于每一步都用真实值，训练阶段的损失会很漂亮，推理阶段的稳定性反而更差。

## Day07-08.英译法案例_模型预测_代码实现(掌握)
> 对应分集：P103 | 原始标题：《Day07-08.英译法案例_模型预测_代码实现(掌握)》

模型训练完了，参数就那样了，接下来该拿它去干活了。这一讲我们要写的，是整个英译法案例里最后一块拼图的前半截：**模型评估函数**，也就是真正让训练好的 Seq2Seq 去翻译一句话的那个函数。

先说清楚它的定位。我们写的这个函数叫 `evaluate_seq2seq`，它做三件事：把一句英文喂进编码器，然后一个词一个词地把法语吐出来，最后连注意力权重一起交回去。它不训练、不更新参数，只负责"用"。

### 函数签名与推理开关

签名里我要三个东西：输入 `X`、一个编码器 `my_encoder_rnn`、一个解码器 `my_attn_decoder_rnn`。

```python
def evaluate_seq2seq(X, my_encoder_rnn, my_attn_decoder_rnn):
    # 1. 关闭梯度计算
    with torch.no_grad():

        # 2. 编码阶段
        encoder_hidden = my_encoder_rnn.init_hidden()
        encoder_output, encoder_hidden = my_encoder_rnn(X, encoder_hidden)
```

为什么参数要外部传进来？因为在写评估函数的时候，我方还没有编码器和解码器这两个对象——它们是在后面测试函数里才被创建、才被加载参数进来的。所以这里先留三个口子，等测试函数把对象造好了再喂进来。

第一行就是 `with torch.no_grad()`。这一步你以前没见过很正常，梯度这个概念我们之前只在训练里用：$w_{new} = w_{old} - lr \times grad$。那问题来了——既然梯度是用来更新参数的，我为什么在这儿主动把它关掉？

> **结论**：因为模型已经训练完毕，参数固定死了，这里做的是预测而不是训练。就算中间算出了梯度，我也不会去走"清空梯度 → 反向传播 → 更新参数"这一套，算了也是白算，白算还占内存。所以直接禁掉梯度计算，省内存、加速推理。

> **提示**：`torch.no_grad()` 只适用于模型的**预测**过程，训练里绝不能这么写——写了就等于模型永远学不到东西。

### 编码阶段：一句话变成隐藏状态

编码阶段的活是：把输入的英文句子转成隐藏状态。

```python
        # 2. 编码阶段
        encoder_hidden = my_encoder_rnn.init_hidden()
        encoder_output, encoder_hidden = my_encoder_rnn(X, encoder_hidden)
```

要先把编码器的初始隐藏状态要出来（`init_hidden`），再拿它和英文句子的索引张量 `X` 一起送进编码器。

回来的是两个东西，名字我按它们的含义记：

- `encoder_output`：本次的输出，也就是编码器在每个时间步产出的那串状态，后面进注意力时它就是 **V**；
- `encoder_hidden`：本次往后传的隐藏状态，也就是常说的上一时间步隐藏状态，它进注意力时是 **K**。

`encoder_hidden` 这个名字在这里同时承担了两个角色：它既是我这次循环的初始状态，也是解码器第一时刻要用的 `decoder_hidden`，后面直接赋值过去就行。

### 解码器参数准备：把句子长度钉死

进入解码之前，有四件准备工作必须做完。这一段的思路就是"不管来多长的句子，我都按最长的那一档准备空间"。

#### 固定长度输出张量

```python
        # 3.1 构建固定长度的编码器输出张量
        encoder_output_c = torch.zeros(MAX_LENGTH, my_encoder_rnn.hidden_size, device=device)
        for index in range(X.shape[1]):
            encoder_output_c[index] = encoder_output[0, index]
```

形状是 `(10, 256)`：`MAX_LENGTH` 是 10，`hidden_size` 是 256。

`X.shape[1]` 拿到的是"你这句英文里有几个词"。不管它是 6 个还是 3 个，我都只在 `encoder_output_c` 的前几行写真实数据，没写到的位置保持全 0——这一步就是补零对齐。

这么做的原因很直白：每句话长度都不一样，张量必须形状统一才能往下算，所以我把长度截齐到 10。

#### 解码器隐藏状态与起始输入

```python
        # 3.2 解码器的隐藏状态
        decoder_hidden = encoder_hidden

        # 3.3 解码器的初始输入：句子的开始标记
        input_y = torch.tensor([[SOS_token]], device=device)
```

编码器最后吐出来的那个隐藏状态，就是解码器的起点。这就是"中间语义向量 $C$"在这个架构里的落点。

`input_y` 要给的不是随便一个词，而是句子的开始标记 `SOS`（Start Of Sentence）。**必须从开始标记出发**，因为解码器第一个时间步得先有个输入，而这个输入在我们还没有生成任何法语词的时候，只能是"开始"这个符号本身。

#### 记录容器：预测词列表与注意力矩阵

```python
        # 3.4 自回归解码过程
        decoder_words = []                              # 存储解码后的法语单词
        decoder_attentions = torch.zeros(MAX_LENGTH, MAX_LENGTH)   # 初始化注意力矩阵
```

`decoder_words` 装的是我自己预测出来的法语词，一个词一个位置地往后 append。

注意力矩阵这边：`attentions` 是解码器在带注意力的情况下会回来的第三个返回值，是一个权重分布矩阵。

> **结论**：这个矩阵的形状是 $10 \times 10$。

为什么是 $10 \times 10$？第一个 10 是我假设的法语句子最大长度——每生成一个法语词，就是矩阵里的一行；第二个 10 是被我拉长过的英语句子——每个法语词都要对上面那 10 个英语词算一遍注意力概率。

换个说法：生成法语词 1 的时候，我拿它当 Q，对 10 个英语词算出一行"$1 \times 10$"的权重；生成法语词 2 的时候，又是一行 $1 \times 10$。一共生成 10 个法语词，就是 10 行，所以是 $10 \times 10$。就算你的英文只有 6 个词，我也已经把它拉成 10 个了，所以列永远是 10。

### 自回归解码循环

```python
        for idx in range(MAX_LENGTH):
```

为什么循环也是 10 次？因为前面已经假定生成的法语最长也是 10 个词。**编码器和解码器两边的长度假设必须一致**，否则矩阵对不上。

#### 解码器前向传播与 QKV 对应

```python
            output_y, decoder_hidden, attn_weights = my_attn_decoder_rnn(
                input_y, decoder_hidden, encoder_output_c
            )
```

解码器的前向传播要三个输入、返回三个输出。三个输入进来，正好对上 Q、K、V：

| 传进去的参数 | 对应角色 | 是什么 |
| --- | --- | --- |
| `input_y` | **Q** | 当前输入词的索引 |
| `decoder_hidden` | **K** | 上一时间步的解码隐藏状态 |
| `encoder_output_c` | **V** | 编码器输出张量（拉长后的） |

回来的三个输出：

- `output_y`：下一个词的概率分布；
- `decoder_hidden`：更新后的隐藏状态，接着往下一时刻传；
- `attn_weights`：这一步的注意力权重分布。

> **易错点**：`Q` 是"我要生成的那个词"，`K` 是"我上次记着的东西"，`V` 是"英文句子被编码出来的全部信息"。中间那个 `decoder_hidden` 而不是 `encoder_output` 当 K，这个搭配是带注意力的解码器定下来的，别按直觉想成"K、V 都来自编码器"——V 才来自编码器。

#### 记录注意力矩阵

```python
            decoder_attentions[idx] = attn_weights
```

刚才拿到的那一行 $1 \times 10$ 的权重，填进大矩阵的第 `idx` 行。第一次循环填第 0 行，第二次填第 1 行，一直到填满 10 行，矩阵就完整了。这是一个"逐行落位"的动作。

#### 用 topk 预测下一个词

```python
            topv, topi = output_y.topk(1)
```

`output_y` 是概率分布，我只要概率最大的那一个：

- `topv` 是那个最大的概率值；
- `topi` 是它对应的索引。

这个思路跟 `argmax` 像，但比 `argmax` 好用：`argmax` 只给你索引，`topk` 索引和值一起给你。

#### 终止条件：撞上 EOS 就停

生成的这个词**不一定**能当下一时刻的输入——万一它预测出来的就是结束标记呢？

```python
            if topi.squeeze().item() == EOS_token:
                break
            else:
                decoder_words.append(index2word[topi.squeeze().item()])
```

如果当前预测词是 `EOS`（End Of Sentence，句末标记），说明这句法语已经说完了，**立刻跳出循环，不再往下生成**。

否则就把这个词记进结果列表。要注意往 `decoder_words` 里加的不是张量，而是词本身：拿 `topi.squeeze().item()` 得到那个整数索引，再用 `index2word` 把索引翻回单词。`index2word` 的键是索引、值是具体单词，正好干这活。

> **提示**：`.item()` 是从标量张量里取出那个具体数值、变成 Python 的 `int`。`torch.tensor([18])` 整体是个张量，但把里面的 `18` 拿出来，它就是普通的整数。这个函数后面用得非常多。

#### 更新输入：把预测词当下一个输入

```python
            input_y = topi.detach()
```

拿刚才预测出来的词，当作下一时间步的输入——这就是**自回归**：自己生成的输出，回头变成自己的输入。

一定有人会问：这里要不要触发一下 teacher forcing？万一是错的呢？

> **易错点**：teacher forcing 是**训练**阶段的做法。训练时我像教小孩做作业，他写错了我就纠正他，把正确的前一个词喂给他。但现在是**考试**，错了就错了，你不能再提示他。所以这一步只能是"把当前预测词作为下一时间步的输入"，没有纠错的机会。

`detach()` 的作用也不需要更多解释：这个词只用来做输入，不需要再跟计算图挂钩。不用加 `squeeze`，直接 `topi.detach()` 就够了。

### 返回值：注意力矩阵为什么要切片

循环跑完，返回两样东西：

```python
        return decoder_words, decoder_attentions[:idx + 1]
```

`decoder_words` 是预测出来的词列表，没有争议。真正需要解释一下的是后面那个 `[:idx + 1]`——这个 `+1` 是从哪来的？

想想循环是怎么结束的。`idx` 从 0 走到 9，正常情况下会走满 10 次。但如果中途撞上 `EOS` 就 `break` 了，循环会**提前结束**，而注意力矩阵是我们初始化好的 $10 \times 10$，后面那些没写过行仍然是全 0。

举个具体例子：假设 `idx = 5` 的时候生成了 `EOS`，触发了 break。

- 此时真实生成的法语词是 5 个吗？不是，是 **6 个**——索引 0、1、2、3、4、5 这两步之前都已经写过结果了，第 5 次也生成了东西（生成了 EOS 才 break 的）；
- 所以我要保留的是前 $5 + 1 = 6$ 行，写成切片就是 `[:idx + 1]`；
- 拿到的注意力矩阵就是 $6 \times 10$。

```text
idx = 5 时触发 EOS 的注意力矩阵裁剪：

  decoder_attentions  (10 x 10，初始全 0)
  +---- 行索引 ----+
  | 0  | <- 已写入，保留
  | 1  | <- 已写入，保留
  | 2  | <- 已写入，保留
  | 3  | <- 已写入，保留
  | 4  | <- 已写入，保留
  | 5  | <- 已写入（这一步生成 EOS，随后 break），保留
  | 6  | <- 全 0，丢弃
  | 7  | <- 全 0，丢弃
  | 8  | <- 全 0，丢弃
  | 9  | <- 全 0，丢弃
  +----------------+

  decoder_attentions[:idx + 1]  ->  (6 x 10)
  后 4 行为什么不要？因为全是 0，不是真实的注意力。
```

读图说明：`idx + 1` 的含义是"实际写了几个词"，切片把后面那些没被写过的全零行一起**割掉**，返回的才是这一步真实的注意力分布。

反过来看那个上界：如果生成的法语长度真按假设跑满 10 个、全 10 行都写了，那 `idx + 1` 就等于 10，切出来还是 $10 \times 10$，一样对得上。这个写法在两种情况下都成立，这也是为什么循环要走满 10 次、矩阵要开 $10 \times 10$，而不是开个刚刚好的尺寸。

> **结论**：注意力矩阵开足 $10 \times 10$ 是"预留空间"，`[:idx + 1]` 是"按实际用量交货"。前面叫假设长度，这里叫实际长度，两者只在提前遇到 `EOS` 时才不相等。

### 这一讲的代码骨架

把上面那些片段合起来，评估函数的完整结构如下：

```python
def evaluate_seq2seq(X, my_encoder_rnn, my_attn_decoder_rnn):
    with torch.no_grad():                      # 关闭梯度计算，只做预测
        # 1. 编码阶段：英文句子 -> 隐藏状态
        encoder_hidden = my_encoder_rnn.init_hidden()
        encoder_output, encoder_hidden = my_encoder_rnn(X, encoder_hidden)

        # 2. 解码器参数准备
        encoder_output_c = torch.zeros(MAX_LENGTH, my_encoder_rnn.hidden_size, device=device)
        for index in range(X.shape[1]):
            encoder_output_c[index] = encoder_output[0, index]

        decoder_hidden = encoder_hidden
        input_y = torch.tensor([[SOS_token]], device=device)

        decoder_words = []
        decoder_attentions = torch.zeros(MAX_LENGTH, MAX_LENGTH)

        # 3. 自回归解码
        for idx in range(MAX_LENGTH):
            output_y, decoder_hidden, attn_weights = my_attn_decoder_rnn(
                input_y, decoder_hidden, encoder_output_c
            )
            decoder_attentions[idx] = attn_weights

            topv, topi = output_y.topk(1)
            if topi.squeeze().item() == EOS_token:
                break
            else:
                decoder_words.append(index2word[topi.squeeze().item()])

            input_y = topi.detach()

        # 4. 返回解码结果与裁剪后的注意力矩阵
        return decoder_words, decoder_attentions[:idx + 1]
```

到这儿评估函数就写完了，但**现在还调不动它**：手里没有编码器和解码器的对象，也就没有参数可喂。下一步得写测试函数，把训练好的编码器、解码器参数从磁盘上读回来，再调这个 `evaluate_seq2seq` 把结果生成出来。

### 模型路径与迁移学习的由来

第一个动作是把两个模型的文件路径定下来。

```python
# 1. 模型路径：model 目录下训练时保存的参数文件（编码器 + 带注意力的解码器）
path1 = "./model/my_encoder_rnn.pth"
path2 = "./model/my_attention_decoder_rnn_5.pth"
```

`path1` 是编码器：选 `my_encoder_rnn`。`path2` 是解码器：选带 `_5` 的那个，也就是**第 5 轮训练结束时保存的参数**。为什么挑最后一轮？因为轮数越往后，效果一般越好。当然这里有个前提——我们的训练数据里一共 6 万多条句子，每一轮却只训练了 3000 条，所以第 5 轮的 `_5` 也只是"在这 3000 条上练了 5 遍"的成果。

顺着这个路径，讲一件很多人好奇的事。

假设有个 `.pth` 文件，是我跑了 6 个小时、把 6 万条句子跑满 10 轮（一共 60 万次）训出来的。我把这个文件直接拷给你，你那儿能不能拿来就用？

能。**这就叫迁移学习**——拿着别人已经训练好的模型直接拿过来用，简单到就这一个动作。这也是后面章节要专门讲的内容，等我们讲完 Transformer 那个框架，接着学的就是迁移学习。

### 测试函数与两个模型的加载

函数名就叫 `demo_test_seq2seq_evaluate`，表示"Seq2Seq 模型的演示测试"。

```python
def demo_test_seq2seq_evaluate():
    # 1. 获取数据加载器对象
    my_dataloader = get_data_loader()

    # 2. 加载编码器模型
    my_encoder_rnn = EncoderRNN(input_size=english_word_n, hidden_size=256).to(device)
    my_encoder_rnn.load_state_dict(
        torch.load(path1, map_location=device, weights_only=True)
    )
    print("编码器模型架构：", my_encoder_rnn)

    # 3. 加载解码器模型
    my_attn_decoder_rnn = AttnDecoderRNN(

    my_attn_decoder_rnn.load_state_dict(

    print("解码器模型架构：", my_attn_decoder_rnn)
```

加载这件事分两小步，顺序不能反：**先造一个结构相同的空对象，再把参数灌进去**。

先 `.to(device)` 把对象搬到 GPU，再 `load_state_dict` 把参数读进来。解码器这边写的 `french_word_n` 就是法语词表大小——4345 个法语词，这是解码器每个时间步要从中挑一个的那个类别数。

#### map_location 与 weights_only

`torch.load(path1, map_location=device, weights_only=True)` 这一行里，第一次见到的人基本都会一脸懵。分开说。

> **定义**：`map_location` 决定读回来的参数放到哪个设备上。

正常配对应该是"用 GPU 训练就用 GPU 预测、用 CPU 训练就用 CPU 预测"。麻烦在于：**如果训练时用的是 GPU，你现在想用 CPU 加载它去跑，是会报错的**。代码看起来一样，但底层不一样——底层怎么不一样就得去问写框架架构师了。要跨设备，就靠 `map_location`。

所以加了 `map_location=device` 之后，设备**不挑**，方向也可以是反的：GPU 训练 → CPU 预测可以，CPU 训练 → GPU 预测也可以。不加就得老老实实设备配对，否则报错。

> **提示**：`weights_only=True` 表示只加载模型的**权重参数**，忽略保存文件里其他那些东西。这样一来读的是参数本身，不去执行任何附带内容，加载更安全、也更快。

两个 `print` 也不是摆设。打印出来的就是模型的层级结构：

```text
编码器 EncoderRNN：
  embedding      <- 词嵌入层
  gru            <- GRU 层

带注意力的解码器 AttnDecoderRNN：
  embedding      <- 词嵌入层
  attn           <- 注意力层
  bmm / attention_bmm   <- 注意力里的矩阵乘法
  dropout        <- 随机失活
  gru            <- GRU 层
  out            <- 输出层
  softmax        <- 输出概率
```

读图说明：这两段打印结果就是后面那张整体流程图的"骨架"，每一层都在里面挂着。脑子里装不下这张结构图，代码里那些维度转换就根本没法推——光流程本身就已经够绕，何况还有各种维度变换。

### 实测结果与误差归因

跑出来什么效果？说实话，别抱太大希望——原因只有一个：**训练太少了**。

先看几个对得上的：

| 原始英语 | 模型生成的法语 | 参考含义 | 评价 |
| --- | --- | --- | --- |
| `I am the spokesman of this organization` | 关于机构发言人的那句 | 我是这个机构的发言人 | 意思接近 |
| `I am thinking of buying a new umbrella` | `Je pense acheter un nouveau parasol` | 我正在考虑买把遮阳伞 | 基本正确 |
| `he swims very fast` | `Il nage très` | 他游泳的速度很快 | 相当准 |

也有彻底跑偏的。有一条生成出了"我正在洗澡"这种和原句毫不相干的内容，还有一条生成出"我是纳尔维克的一个儿子"这样莫名其妙的句子——这就是**完全废了**。

为什么？回到训练那一步。训练函数里写了这么一句：

```python
if i > 3000:
    break
```

也就是说，6 万多条句子，**只训练了 3000 条**，比例大概是 $\frac{3000}{63000} \approx \frac{1}{21}$。才跑了这么点数据，结果不准是正常的。

想让效果变好，操作也很简单：

1. 把训练函数里那个 `if i > 3000: break` 判断**注释掉或删掉**，这样每一轮都能吃满 6 万条数据；
2. 把训练轮数从 5 改成 10——其实 10 轮都算少，改成 100 也行；
3. 但轮数一上去，算力就顶不住了，跑起来要很久很久。

时间上是这么一笔账：CPU 上训完一轮大概 **50 分钟**，10 轮就是 **500 分钟**，差不多 **9 个小时左右**。所以最实际的做法是——**晚上睡觉前把训练这个函数跑起来，第二天早上模型就跑完了**，拿它再做预测，结果会比现在准很多很多。误差依然会有，但比现在这个效果好得多得多。

### 数据、算法与算力

为什么这事儿最后卡在机器上？因为人工智能就是三样东西：

```text
人工智能 = 数据 + 算法 + 算力
              |        |        |
              |        |        +-- 显卡：A100 80G / H100 80G，一张就 20 万
              |        +----------- 代码逻辑：编码器 + 带注意力的解码器，已经写完
              +-------------------- 6 万多条英法句子对，已经有了
```

读图说明：数据我们手上有 6 万多条英法句子对，算法这套编码解码的代码逻辑也写完了，**差的就只有算力这一项**。给我一块 A100 80G 或者 H100 80G，动不动就跑一轮，结果自然精准得多。

现实里为什么普通人不做这件事，就在这个"20 万一张"上。有些公司、科研机构，包括证券类机构，会配两块甚至三块这种显卡给团队用。也见过这样的团队：需要什么就跟公司说，别给公司省钱，要开会员、要买设备都批——那这种情况下，直接跟公司提一块 H100 80G 就完了。

不过在练手阶段，我们没必要纠结这个。**先把 3000 条改掉、把轮数加上去、让它通宵跑一遍**，看到效果变好，这个案例的教学目的就已经达到了。

### 图上的两个坐标轴

先看结果图长什么样：纵轴是英语句子，横轴是法语句子，格子的颜色表示两者之间的关联强度。

```text
注意力热力图（示意）：

   横轴 -> 生成的 法 语 词 序 列
   +----+----+----+----+----+----+----+
英 |    |    |    |    |    |    |    |
语 |    | 深 |    |    |    |    |    |
词 |----+----+----+----+----+----+----+
序 |    |    | 深 |    |    |    |    |
列 |----+----+----+----+----+----+----+
   |    |    |    | 深 |    |    |    |
   |----+----+----+----+----+----+----+
   |    |    |    |    | 深 | 浅 |    |
   +----+----+----+----+----+----+----+

   颜色越浅  ->  依赖越深、关联越大
   颜色越深  ->  依赖越弱、关联越小
```

读图说明：竖着的 y 轴是英语句子，横着的 x 轴是生成出来的法语句子；每个格子的颜色深浅表示"生成这个法语词的时候，对那个英语词投入了多少注意力"。**颜色越浅，说明这个英语单词越重要、影响越大**。

看的时候有两个现象值得留意：

- **越往后越重要**——生成越靠后的法语词时，权重往往落在越靠后的英语词上，整体呈现逐级匹配的趋势；
- **一个法语词会同时用到好几个英语词**——不是一对一，而是"主要依赖某一个、顺带依赖它周围几个"，那个颜色最浅的格子就是它最依赖的那个词。

### 绘图函数与模型实例化

函数名叫 `demo_test_attention`。

```python
def demo_test_attention():

    my_dataloader = get_data_loader()

    # 2.1 实例化编码器模型

    my_encoder_rnn.load_state_dict(

```

第一件事永远是拿数据加载器，跟前面每一段代码一样。

`hidden_size` 就是**隐藏维度**，写 256。这里有个小技巧：如果你只是想看看图、不追求效果，可以把这个 256 调小一点，跑起来更快，也不会影响你对整条链路形状的理解。

编码器这边两个参数就是词表大小和隐藏维度，写的时候可以直接用变量传（`input_size` 接 2803，`hidden_size` 接 256），也可以把 2803 和 256 直接写死。用变量传的好处是这个数只出现一次，改的时候不用满篇找。传完 `.to(device)` 搬到设备上，再把参数 `load_state_dict` 进来。

解码器这边同理：第一个位置接**法语**词表 `french_word_n`，第二个接 `hidden_size`。注意别把英语的 2803 塞进解码器的输出维度——解码器要产出的是法语，它面对的类别数是那 4345 个法语词。

> **易错点**：`2803` 是英语词表、`4345` 是法语词表。编码器进的是英语词表，解码器出的是法语词表，两个数分别是各自那一侧的规模。

### 形状 7×10 的来历

打印结果是 `(7, 10)`。逐个数清楚。

#### 行数 7：法语侧的实际长度

生成的法语一共 6 个词。但形状的行数是 **7**，多出来的那一行是**结束标记 `EOS`**——它也在矩阵里占了一行，只是在图上没被专门显示出来。

那再往前推一步：如果连最开头的开始标记 `SOS` 也算进来，是不是就变成 8 了？对。不过这个矩阵里**只有结束标记、没有开始标记**，所以是 7 行。

`7` 这个数不是固定死的，它等于"这次实际生成了几个词再加一个 `EOS`"。生成长度不同的句子，行数就不同。

#### 列数 10：英语侧被拉长的长度

`7` 能解释，`10` 就奇怪了：英语句子 `we are both teachers` 一共才 4 个词，加上句末的结束标记是 5 个，再加上开始标记也才 6 个，怎么都凑不到 10。哪来的 10？

> **结论**：为了统一，英文句子不够 10 个词的，一律**补成 10 个**。

所以这个 10 就是前面反复见到的 `MAX_LENGTH = 10`。它跟这句话实际有几个词没关系，是一个恒定值。

把两边的算法合起来看：

```text
英语侧（列，恒为 10）：
  we / are / both / teachers  ->  4 个真实词
  + EOS                       ->  5 个
  + 补零对齐到 MAX_LENGTH=10   -> 10 个（后 5 个是占位）

法语侧（行，随实际生成变化）：
  生成 6 个法语词
  + 第 7 个位置是 EOS
  -> 7 行

  于是：attentions.size() = (7, 10)
```

读图说明：列数 10 是"英语句子被拉长后的固定长度"，行数 7 是"这次实际生成到哪里"。生成第 1 个法语词时算出来的权重是一行 $1 \times 10$，生成第 2 个时又是一行 $1 \times 10$……一共生成 7 行，所以整体是 $7 \times 10$。第 8 个词的权重从哪来？没有第 8 个词了，所以不要。

这也正好解释了上一讲那个 `[:idx + 1]` 切片——**它是这套"假设长度 10、实际长度按 EOS 截断"约定的直接后果**。矩阵开足 $10 \times 10$，实际生成 7 行就返回 7 行。

#### 图上索引为什么是 0 到 6

图上的刻度是 0 到 6，不是 1 到 7。索引从 0 开始，7 行就是 0 到 6，对得上。至于"我的英语句子有这么长吗"这个疑问——把句子切一遍就清楚了：`we are both teachers` 是 5 个（含那个句点），加上结束标记是 6 个，加上开始标记是 7 个，索引正好落到 0 到 6。而英文这一侧被统一拉到了 10，所以列方向的索引是 0 到 9。

### 视觉匹配与逐级依赖

对着图上颜色看，结论挺清楚：

- 法语前面几个词，主要跟英语前面几个词相关；
- 生成法语**最后一个词**的时候，它**不依赖英语前面那几个词**，而是明显偏向英语句子的**最后那一段**——顺着一条线下来，这个匹配是相当合理的；
- 有些格子颜色特别浅（比如生成某个法语词时对某一个英语词的那一格），意思是**生成这个词时我更依赖那个英语单词，对后面的英语词依赖没那么高**——有依赖，但没那么高。

> **定义**：颜色越浅，说明影响越大、关联越大。图上横向看是"某一步生成时对整句英语的关注分布"，纵向看是"某个英语词在整段生成的哪些位置被用到"。

这段可视化的官方说明也就两句：图像的纵坐标（y 轴）代表英语词汇，横坐标（x 轴）代表生成的目标语言，也就是法语句子；颜色越浅，说明影响越大、关联越大。

### 案例复盘：注意力机制到底是什么

整个英译法案例到此写完。有两处难：一是代码量比较多，二是里面维度转换特别多。

> **结论**：维度的难点是有解的——**把每个张量的形状打印出来**，你是啥形状、我是啥形状，一个个标到整体流程图上，对着图走一遍流程。这么做会简单很多。

另外要有心理准备：这个案例需要几天时间消化，指望一天写完不太现实。多敲几遍、多理解几遍里面到底在干什么，等真看明白了注意力机制怎么玩，那就是真的懂了。

回头看，讲了这么多，注意力机制就两句话：

1. **把人的注意力机制迁移给计算机**，让计算机也像人一样有侧重点地学习；
2. **注意力权重的计算公式**——Q 和 K 先算匹配分，拿到匹配分就是注意力概率，再拿概率去乘 V。

这套公式我们一共写了三个：前面两个是一般注意力，最后一个"点积并做缩放"的那个，就是**自注意力**（self-attention）。

最后是整个案例的架构定位，还有一处必须点明的小瑕疵：

> **易错点**：我们用的是 Seq2Seq 架构，而在这个架构里，**注意力只加到了解码器上，编码器并没有加注意力**。

正是这个"只在解码器加注意力"的版本，让很多人得到了一个结论：注意力机制确实好用。于是自然有人接着想——既然加在解码器上管用，**能不能也把注意力加到编码器里**？顺着这个思路优化再优化，就到了下一个要学的架构：**Transformer**。
