## 1. 案例需求与整体设计

> **一句话主旨**：交代英译法案例的需求、数据规模与词向量选型，确定编码器与解码器的分工及注意力的接入位置。

* **序列到序列（Sequence to Sequence，Seq2Seq）**
    * > 定义：把一条输入序列映射成一条输出序列的架构，本案例即"英文句子到法文句子"。
    * 由三部分组成：编码、解码、中间语义张量 $c$；编码器主"理解"，解码器主"生成"。
    * 属于 RNN 分类里的 n vs m 结构——输入句与输出句长度不同，区别于 n vs 1、n vs n。
    * 编码按时间步推进：本步输入 $x_t$ 与上一步隐藏状态 $h_{t-1}$ 一起算得本步隐藏状态 $h_t$，最后把前面所有词的信息汇总成 $c$。
    * 解码末尾用全连接加 `Softmax` 完成分类，从 4345 个法语词里挑概率最大的那个。
    * 无注意力机制时解码器每个时刻用的 $c$ 完全相同；加注意力后每个时刻的 $c$ 都不一样。
    * > 来源: P80

* **注意力机制（Attention）的接入位置**
    * 本案例把注意力计算加在解码器内部，编码器不加。
    * 加入注意力后计算 `to` 这个词，既要依赖源端第三个词，也要依赖前面已经生成的那个词。
    * > 易错点：注意力并非只能用在解码器层；Transformer 里编码器层与解码器层都有注意力，还分多头自注意力与掩码多头自注意力，本案例只是先在解码器上用。
    * > 来源: P80

* **特殊标记（Special Token）**
    * > 定义：人为加进词表、不对应任何真实单词的保留索引，用来标记句子的开始与结束。
    * `SOS_TOKEN = 0`、`EOS_TOKEN = 1`；`SOS` 是 start of sequence，不是"求救"。
    * 预测时从哪个标记开始、到哪个标记结束，全靠这两个值定义。
    * 编码器造出的实际输出末尾也要补 `EOS`，它是句子的真正边界。
    * > 来源: P80, P81, P86

* **词向量的选型**
    * 本案例选词嵌入层 `nn.Embedding`，不选 `one-hot`、`word2vec`、`fasttext`。
    * 处理路线是：分词 → 建立 `word2index` 映射 → 用 `nn.Embedding` 构建词向量。
    * 选它的理由是 `nn.Embedding` 一行代码即可完成索引到稠密向量的映射，并与 RNN／GRU／LSTM 的输入要求天然契合；用 fasttext 会绕很大一圈。
    * > 来源: P80

* **案例的学习目标与实现步骤**
    * 目标三条：了解需求并掌握数据集特点；确定数据文本数值化方案；了解效果展示。
    * 实现顺序：任务识别 → 数据处理 → 构建编码器与两个解码器 → 加入注意力机制 → 模型训练与评估。
    * 完整代码加注释在 800 行以上，且重复代码很少，需要按"图路"分批推进。
    * > 来源: P80

## 2. CUDA 环境配置与设备选择

> **一句话主旨**：判断机器能否用 GPU、正确读出 CUDA 版本并挑选安装命令，在沙箱中装好环境并与 PyCharm 关联。

* **硬件与操作系统的前提条件**
    * Windows 有独立显卡可以用 GPU；Windows 无独显不行。
    * Linux 可以；macOS 必须是 M 芯片（M1 即可），Intel 芯片不行。
    * 不行的两类出在硬件本身，换版本、装驱动都改变不了结果。
    * 独显查法：任务栏右键 → 任务栏设置 → 任务管理器 → 性能页拉到最下面看有几个 GPU，独立显卡会标明英伟达与型号。
    * 性能页里没有 GPU 选项通常是刷过系统又没装显卡驱动所致。
    * > 来源: P81, P82, P83

* **CUDA 版本的读取与安装命令的选择**
    * 读版本：Windows 按 `Win + R` 输入 `cmd`，或在 PyCharm 的 Terminal 里执行 `nvidia-smi`，记下输出里的 CUDA Version。
    * 正常机器的 CUDA 版本应落在 12.x 或 13.x；读到 11 开头说明驱动太旧，先更新驱动再读一次。
    * 装哪一档的规则只有一条：所装 PyTorch 对应的 CUDA 版本**不能低于**本机 `nvidia-smi` 报出的版本；示例是 13.1 只能挑 13.0 及以上，官网最高到哪就装到哪。
    * 官网 `pytorch.org` 会自动识别操作系统；macOS 上 CUDA 一栏标注 `Not available on macOS`，直接用默认的 `pip install torch torchvision`。
    * 驱动是 11.x 时有两条路：翻 `Previous Versions of PyTorch` 找老版本（不推荐），或直接把驱动升到最新再装最新版 PyTorch。
    * > 来源: P81, P82

* **设备选择代码**
    * Windows／Linux 写法：`device = torch.device("cuda" if torch.cuda.is_available() else "cpu")`，支持则返回 `cuda`，不支持返回 `cpu`。
    * Mac 写法只要一句 `device = "mps"`，不需要判断。
    * 张量必须显式指定设备：`torch.tensor(x, dtype=torch.long, device=device)`；不指定即使机器有 GPU 也留在 CPU。
    * `device` 的取值只能是 `cuda` 或 `cpu` 这两个字符串，改成中文会直接报错；模型搬了设备，喂进去的数据和初始隐藏状态也必须跟着搬。
    * > 来源: P81, P86, P88

* **沙箱的创建、切换与删除**
    * 建环境与切环境：
    ```bash
    conda create -n nlp_base python=3.8
    conda activate nlp_base
    pip install <官网生成的那条命令>
    ```
    * GPU 版与 CPU 版不能共存于同一个沙箱；已有的 `nlp_base` 是 CPU 环境，装进 GPU 版命令后 CPU 版就用不了了，所以建议单独建一个 `nlp_base2`。
    * 新建沙箱会缺 `jieba` 这类常用包，需要重新 `pip install` 装一遍。
    * 删除沙箱：`conda remove -n <沙箱名> --all`；**当前激活的沙箱删不掉**，要先 `conda activate base` 再删。
    * > 易错点：删除命令不要在 base 沙箱里直接运行，也不要在 base 里试错——base 崩盘要卸载重装 Anaconda，试错成本最高。
    * > 来源: P81, P82, P83

* **PyCharm 关联沙箱**
    * 入口：右下角解释器选择处（或 `Settings` 左上角），往下拉到最底部的 `Add New Interpreter`。
    * 步骤：`Add Local` → 选 `Conda` → 选 `Use` 使用之前的 conda 路径 → 加载完成后点路径下拉箭头，列出本机所有沙箱。
    * 同一份脚本靠切解释器换硬件：切到 `nlp_base2` 输出 `cuda`，切到 `nlp_base` 输出 `cpu`，代码不必改。
    * 切沙箱后第一次运行会有一段时间在改包、更新依赖，之后切换很快。
    * > 来源: P81, P82

* **驱动更新与影响配置结果的四个变量**
    * 变量是 Anaconda 版本、Windows 操作系统版本、显卡型号、显卡驱动版本，四者乘在一起决定哪一组参数能装成，别人的命令未必能过。
    * 排查顺序建议：先看驱动（升级最容易、见效最快），再换 Python 版本，最后才怀疑 Anaconda 与操作系统。
    * 更新驱动的入口是 NVIDIA 面板左侧的"驱动程序"；选项里 Game Ready 为游戏优化不要选，**务必选 Studio**，它面向创意应用与开发者。
    * > 易错点：面板提示"升级到最新版"升级的是面板软件本身，不是显卡驱动；面板升级与驱动不相关。
    * 官方声明要求 Python 至少 3.10，但实测 3.8 也能装成、能跑，所以版本号只做参考，不要完全照抄。
    * 版本换法：3.8 不行就换 3.10，再不行换 3.11，换一次装一次；每轮固定成本只有"删、建、装"三条命令。
    * 成功的判据只有一条：**出现 CUDA 就 OK**；没出现也不影响，先用 CPU 环境把代码跑通，等网络空闲时再配。
    * > 来源: P81, P82, P83

## 3. 语料工程与数据管道

> **一句话主旨**：用正则把原始文本规范化，切出双语句子对并建好双向词表，再封装成 Dataset 与 DataLoader。

### 3.1 数据清洗函数

* **字符串规范化（Normalization）**
    * > 定义：把写法千差万别的原始文本映射到统一、可预测的形式，本案例统一到两条硬约束——整行必须是小写字母，且除英文字母外只允许出现 `.` `!` `?`。
    * 函数 `normalize_string(s)` 四步走完：`s.lower().strip()`、`re.sub(r"([.!?])", r" \1", s)`、`re.sub(r"[^a-zA-Z.!?]+", r" ", s)`、`return s`。
    * `strip()` 只处理首尾空白，句子中间的空格与制表符一个都不动，那些交给第三步的过滤规则。
    * 处理后的保证只有两条：整行一定是小写；整行除英文字母外只有点号、叹号、问号。
    * > 来源: P84

* **正则替换 `re.sub()` 与捕获组（Capturing Group）**
    * `re.sub()` 三个参数依次是：要被替换的正则、用来替换的内容、要操作的字符串；参三一定是 `s`，参一参二需要设计。
    * 中括号 `[.!?]` 表示"里面任意一个都行"；外面加小括号构成捕获组，它不改变匹配范围，只改变"这段匹配能不能被引用"。
    * 编号规则：整条正则自身是组 0（不写括号也存在），自己写的第一对小括号是组 1，往后依次递增。
    * `\1` 是反向引用（Backreference），指代第 1 个捕获组实际匹配到的文本；参二必须写成原始字符串 `r" \1"`，避免反斜杠被提前转义。
    * 替换效果就是"你匹配到点号就还你点号、匹配到叹号就还你叹号"，区别只在前面多加一个空格。
    * > 来源: P84

* **过滤非标准字符与标点前补空格的动因**
    * `[^a-zA-Z.!?]` 中中括号里的 `^` 表示取反，含义是"除了小写字母、大写字母、点号、叹号、问号以外的任意一个字符"。
    * 紧跟的 `+` 是数量词，表示前面的单元至少出现一次、至多无数次；连续的非法字符整体被当成一个匹配块替换成一个空格。
    * 结果是把 `#`、制表符、中文等全部清掉，字符串里只剩字母和 `.` `!` `?`。
    * 第二步补空格的唯一目的是切分：`I love you!` 里叹号紧贴 `you`，不拆开就会把 `you!` 当成一个记号；补空格后一定是 `you` 一个、`!` 一个。
    * > 易错点：`+` 少了也能跑，但没有 `+` 时连续的多个非法字符会被逐个替换，中间的空白结果不一样。
    * > 来源: P84

* **处理前后的对照**

    | 位置 | 处理前 | 处理后 | 原因 |
    | :--- | :--- | :--- | :--- |
    | 首部 | 有前导空格 | 前导空格消失 | `strip()` 移除首尾空白 |
    | 大小写 | `I` 是大写 | 全为小写 | `lower()` 统一小写 |
    | 标点 | `you!` 紧贴 | `you !` 之间有一个空格 | 捕获组 + `\1` 补空格 |
    | 制表符 | 含 `\t` | 被替换为空格 | `[^a-zA-Z.!?]+` 命中 |
    | 中文与 `#` | `#爱你` | 被替换为空格 | 同上 |

    * > 易错点：输出里看似"两个空格"的地方，其中一个来自 `print` 输出语句本身带的空格，与字符串内容无关。
    * > 来源: P84

### 3.2 双语预处理与词表构建

* **数据预处理函数 `my_get_data()`**
    * > 定义：一次性完成"清洗文本"与"构建文本字典"两件事，产出七样东西交给后面的环节。
    * 读取用 `with open(data_dir + 'eng-fra.txt', 'r', encoding='utf-8') as src:`，再 `lines = src.readlines()` 一次性取出所有行。
    * 句子对用嵌套推导式构建：`my_pairs = [[normalize_string(s) for s in line.split('\t')] for line in lines]`。
    * 内层不是嵌套循环，而是"每行按 `\t` 切一刀"：`\t` 左边是英文、右边是法文，所以内层长度恒为 2，索引 0 是英文、索引 1 是法文。
    * 句子对总数 `len(my_pairs)` 为 **63594**，与原始数据的行数一致，没有漏也没有多。
    * 返回值共七项：英语词到索引映射、英语索引到词反向映射、英语词表大小、法语词到索引映射、法语索引到词反向映射、法语词表大小、双语句子对。
    * > 来源: P85

* **词表初始化与索引分配**
    * 英语侧初始字典为 `{SOS_token: 0, EOS_token: 1}`，计数器 `english_word_n` 初值为 2，因为里面已经躺着两个人为加入的特殊标记。
    * 法语侧同样初始化，只把 `english` 换成 `french`，`french_word_n` 初值也是 2。
    * 分配新索引的规则是 `if word not in xxx_word_to_index:` 成立时 `xxx_word_to_index[word] = 计数器`，随后计数器加 1。
    * 之所以新索引可以直接取当前计数器值，是因为**新索引 = 字典当前长度**：字典 2 个元素时新词该拿 2，5 个元素时新词该拿 5，一处不差。
    * > 易错点：`if` 判断绝对不能省；键唯一，重复登记会把老索引覆盖掉，同一个词拿到两个编号，词表与索引的对应关系就崩了。
    * > 来源: P85

* **反向映射表与词表统计**
    * 反向映射写法：`english_index_to_word = {v: k for k, v in english_word_to_index.items()}`，法语的 `french_index_to_word` 同理。
    * 反向表的用途是"将来模型算出来的是编号，得有办法拿编号把原词找回来"。
    * 统计结果：英语词表 **2803** 个不同词，法语词表 **4345** 个不同词；用计数器与用 `len(字典)` 得到的值一样，两者必须一致，否则说明加词时漏了加一。
    * 用字典去重的必要性：六万多句里同一个词若不去重会被登记无数次。
    * 数据探查两个动作：前 5 条看格式，另外跳着抽第 7000 条检查中间段有没有坏；`7000` 这个数字没有任何特殊含义。
    * > 易错点：`my_pairs[7000]` 拿到的是整条句子对，要再跟一个中括号，`[0]` 取英文、`[1]` 取法文，少写这一层看到的就是个长度 2 的列表。
    * > 来源: P85

### 3.3 数据集对象

* **自定义数据集类 `MyPairsDataset`**
    * > 定义：继承 `Dataset` 并实现 `__init__`、`__len__`、`__getitem__` 三个魔法方法的容器，把句子对加工成模型可吃的张量。
    * 选择自定义而非 `TensorDataset`，是因为本案例的数据是一对一对的句子，还得自己查词表转索引。
    * `__init__(self, my_pairs)` 做两件事：保存 `self.my_pairs`，计算 `self.sample_len = len(my_pairs)`；一个句子对算一个样本。
    * `__len__(self)` 只返回 `self.sample_len`，`DataLoader` 靠它知道一共多少样本、一个 epoch 迭代多少批。
    * `__getitem__` 在被 `对象[索引]` 调用时触发；`__len__` 在被 `len(对象)` 调用时触发。
    * 取数据的调用要写在类外面，其他函数才能复用同一批数据；写进 `class` 里就只有这一个数据集类能用了。
    * > 来源: P86

* **索引修正与句子对取出**
    * 修正写法：`index = min(max(index, 0), self.sample_len - 1)`；内层 `max` 兜住下界 0，外层 `min` 兜住上界 `sample_len - 1`。
    * 上界是"样本总数 - 1"，十个样本不能大于 9。
    * `x = self.my_pairs[index][0]` 是英语句子，`y = self.my_pairs[index][1]` 是法语句子。
    * > 易错点：`min` 和 `max` 的顺序不能反；写成 `max(min(index, self.sample_len - 1), 0)` 效果看着一样，但谁管哪一头容易说不清、参数就容易写错。
    * > 来源: P86

* **文本转数值与张量设备**
    * 英文侧：`x = [english_word_to_index[word] for word in x.split(' ')]`，把整句字符串变成一串编号；随后 `x.append(EOS_token)` 在末尾补结束标记。
    * 法语侧套路完全一样：按空格切、查法语词表转编号、补 `EOS_token`、转张量并带 `device`。
    * 转张量写法：`tensor_x = torch.tensor(x, dtype=torch.long, device=device)`；返回 `tensor_x, tensor_y` 两个张量。
    * > 易错点：`x.append(EOS_token)` 不能写成 `x.append('EOS')`，列表里全是整数编号，塞字符串进去就成了混合类型，转张量直接报错。
    * > 来源: P86

### 3.4 数据加载器与批次形状

* **数据加载器对象的三个参数**
    * `my_dataset = MyPairsDataset(my_pairs)` 先实例化数据集，再 `DataLoader(my_dataset, batch_size=1, shuffle=True)`。
    * 参一 `dataset` 传数据集对象；参二 `batch_size` 批次大小，本案例先给 1，实际开发一般是 8、16、32；参三 `shuffle` 是否打乱。
    * 打乱规则只有一条：**训练集打乱，测试集不打乱**。
    * 测试时用 `for i, (x, y) in enumerate(my_dataloader):` 取一批来看形状和内容，看完 `break`。
    * 因为 `shuffle=True`，第一批不一定是第一条，是随便抽的一条。
    * > 来源: P87

* **批次数据的形状与长度对齐**
    * 加载器交出来的是编号不是单词：`Say something .` 会变成 `tensor([[13, 9, 105, 1]])`，最后那个 1 是补上的 `EOS`。
    * `batch_size=1` 时形状是 `[1, len]`，实测出现过 `torch.Size([1, 6])` 与 `torch.Size([1, 6])`，也出现过 `1 7` 与 `1 8`。
    * 英文与法文长度对不齐是常态，不是数据坏了；`x` 的长度是英语句长，`y` 的长度是法语句长，本来就可以不一样。
    * `batch_size` 调大后同一批里长度不一的句子拼不成规整二维张量，那时才需要 `collate_fn` 之类的补齐手段。
    * > 来源: P87, P89

* **单词转索引的原因与 Embedding 的输入约束**
    * > 定义：`nn.Embedding`（词嵌入层）只能根据整数索引取出对应的词向量，接受不了字符串，所以喂给模型之前所有文本都必须先查表变成索引。
    * 它本质上是一张形状为 $(\text{num\_embeddings}, \text{embedding\_dim})$ 的可学习查找表，输入索引 $i$ 返回第 $i$ 行：$E \in \mathbb{R}^{V \times d},\ \text{Embedding}(i) = E[i]$，其中 $V$ 是词表大小（英语 2803、法语 4345），$d$ 是词向量维度。
    * 有了词表与反向词表的双射，既能拿编号取词向量，将来也能把模型输出的编号还原成原始的词。
    * 数据处理三部曲：**读取数据到内存、构建 `dataset`、构建 `dataloader`**。
    * > 来源: P87

## 4. 编解码器搭建与维度推导

> **一句话主旨**：逐个搭建 GRU 编码器与两版解码器，把每一层的进出维度、张量形状和衔接关系钉死。

### 4.1 基于 GRU 的编码器

* **编码器 `EncoderRNN` 的类骨架**
    * > 定义：把整句源语言压成一个定长语义表示的网络模块；它的输出 `output` 是每个时间步的隐藏状态堆叠，`hidden` 是最后一个时间步的隐藏状态。
    * 继承 `nn.Module`，骨架三步：`__init__` 初始化词嵌入层与 GRU 层、`forward` 前向传播、`initHidden` 初始化隐藏状态。
    * 数据流：`input` 单词索引 → 词嵌入层 → 词向量张量 → 与上一时刻隐藏状态一起进 GRU → 得到本次 `output` 与 `hidden`。
    * `__init__` 按顺序做四件事：`super()` 初始化父类成员、把 `input_size` 与 `hidden_size` 存到 `self`、实例化 `nn.Embedding(input_size, hidden_size)`、实例化 `nn.GRU(hidden_size, hidden_size, batch_first=True)`。
    * > 来源: P88

* **编码器的三类参数与含义**
    * `input_size` 是编码器词嵌入层的输入维度，即词汇表大小，本案例传 **2803**（英语侧词表）。
    * `hidden_size` 是隐藏层维度，也是词向量维度，128、256 都行，本案例定 **256**。
    * `nn.Embedding` 两个参数含义不同：第 1 个是查表总行数（词表大小 2803），第 2 个是每行有多少个数字（词向量维度 256）。
    * `nn.GRU` 两个参数含义不同：第 1 个是输入的特征维度（喂进去的是 256 维词向量），第 2 个是隐藏层维度，两者数值相同但含义分别是"进来的东西有多宽"和"记住的状态有多宽"。
    * 层数是 `num_layers`，这里等于 1；它与 `hidden_size` 是两个东西。
    * > 易错点：编码器里只有两个层要实例化，看到"层"字先问一句"谁的层"，别条件反射地凑数。
    * > 来源: P88

* **`batch_first` 与三维批数据格式**
    * `batch_first=True` 把批次维度设为第 1 个维度，数据格式为 `(batch_size, sequence_len, hidden_size)`。
    * 不加这个开关时 PyTorch 默认是 `(sequence_len, batch_size, hidden_size)`，句子长度在前、批次在后。
    * 形状 `(2, 3, 256)` 表示"两个句子、每句三个词、每词 256 维词向量"；`(3, 5, 256)` 表示"三句话、每句 5 个词、每词 256 维"。
    * 开关一开，后面所有打印出来的形状都要按"批次 → 句子 → 词向量"的顺序读，否则很容易把 `batch` 和 `seq_len` 认反。
    * > 来源: P88, P91

* **前向传播与形状结算**
    * `forward` 收两个东西：`input` 是单词索引序列，形状 `(batch_size, sequence_len)`（如 `(1, 6)`）；`hidden` 是初始隐藏状态，形状 `(num_layers, batch_size, hidden_size)`，即 `(1, 1, 256)`。
    * 前两步代码：`output = self.embedding(input)` 把 `(1, 6)` 变成 `(1, 6, 256)`；`output, hidden = self.gru(output, hidden)`。
    * GRU 的两个入参是"本时刻的词向量"和"上一时刻的隐藏状态"，返回后重新赋给 `output` 与 `hidden`。
    * 形状结算（以 `(1, 6)` 为例）：`input` `(1, 6)` → embedding 输出（即 GRU 输入）`(1, 6, 256)` → GRU 输出 `(1, 6, 256)` → GRU 隐藏状态 `(1, 1, 256)`。
    * `output` 的序列长度跟着输入句子长度走，`hidden` 永远钉在 `(num_layers, batch_size, hidden_size)`：前者随句长变，后者被参数定死。
    * > 来源: P88

* **初始化隐藏状态**
    * 写法：`return torch.zeros(1, batch_size, self.hidden_size, device=device)`，这里即 `(1, 1, 256)` 的全零张量。
    * 传进去的批次大小要从输入张量上取（`x.size(0)`），不能写死，否则换个批次大小形状就对不上。
    * > 易错点：初始隐藏状态造在 CPU 上、模型搬到 GPU 上，是最典型的"形状全对但一跑就报设备不一致"的错误；谁造张量，谁负责指定 `device`。
    * > 来源: P88, P89

* **编码器测试与形状验证**
    * 测试函数 `test_encoder` 五个动作：拿数据加载器、初始化 `vocab_size = 2803` 与 `hidden_size = 256`、创建 `EncoderRNN(input_size=vocab_size, hidden_size=hidden_size)`、可选地 `.to(device)`、遍历加载器取一批做前向。
    * 实测输入最后一维**永远是 1**：`(1, 6)`、`(1, 9)`、`(1, 3)`、`(1, 5)` 的最后一位都是 1，因为那就是 `EOS`。
    * 多批实测：输入 `(1, 6)` 输出 `(1, 6, 256)`、`(1, 9)` 对 `(1, 9, 256)`、`(1, 5)` 对 `(1, 5, 256)`、`(1, 8)` 对 `(1, 8, 256)`，隐藏状态恒为 `(1, 1, 256)`。
    * 判据两条：`output` 的第 2 维 100% 等于输入句子长度，`hidden` 的三个维度恒为 `(1, 1, 256)`；同时成立就说明实现自洽。
    * > 易错点：`get_data_loader()` 内部随机取过一行并打印，循环里再拿到的又是另一批随机数据，把两个不同批次的形状放在一起比当然对不上；应该看循环里实际喂进去的那一批。
    * > 来源: P89

### 4.2 无注意力解码器

* **无注意力版本 `DecoderRNN` 的定位**
    * > 定义：解码器只从编码器拿一个固定的中间语义向量 $C$（编码器最后一个时间步的隐藏状态），每生成一个法语词都看这同一个 $C$，不存在逐位置变化的 $C_1, C_2, C_3 \dots$。
    * 解码器一次只处理一个时间步、只吃一个词：拿"上一个词 + 上一时刻隐藏状态"算下一个词，再把算出的词当输入继续滚。
    * 所以解码器的 `input` 形状是 `(1, 1)`——1 批次、1 个词，不是 `(1, 6)` 这种整句。
    * 无注意力版与带注意力版的差别只落在解码器内部，两者的编码器完全相同。
    * > 来源: P90, P93

* **构造参数与各层**
    * 类名 `DecoderRNN`；GRU 本身就是 RNN 的一类变体架构，沿时间步递推、把信息压在隐藏状态里往下传，所以名字里带 `RNN` 不算错。
    * `__init__` 只收两个参数：`output_size` 是目标语言（法语）词汇表大小 **4345**，`hidden_size` 是隐藏层维度 **256**。
    * 各层写法：`self.embedding = nn.Embedding(output_size, hidden_size)`、`self.gru = nn.GRU(hidden_size, hidden_size, batch_first=True)`、`self.out = nn.Linear(hidden_size, output_size)`、`self.softmax = nn.LogSoftmax(dim=-1)`。
    * GRU 两个维度都写 `hidden_size`，因为进来的词向量是 256 维、要交出去的隐藏状态也是 256 维。
    * `initHidden` 写法：`return torch.zeros(1, 1, self.hidden_size, device=device)`，对应"一批一个句子 + 一层 GRU + 256 维隐藏状态"。
    * > 来源: P91

* **前向传播与形状流转**
    * `forward` 五步：`output = self.embedding(input)` → `output = F.relu(output)` → `output, hidden = self.gru(output, hidden)` → `output = self.softmax(self.out(output))` → `return output, hidden`。
    * 词嵌入：`(1, 1)` → `(1, 1, 256)`；`ReLU` 逐元素映射，只改值不改形状；GRU 之后 `output` 仍是三维 `(1, seq_len, 256)`、`hidden` 仍是 `(1, 1, 256)`。
    * 线性层只替换最后一维：`(1, seq_len, 256)` 经 `Linear(256 → 4345)` 变成 `(1, seq_len, 4345)`，前面两维原样不动。
    * `LogSoftmax(dim=-1)` 在 4345 那一维上做归一化，把打分变成对数概率分布，形状不变。
    * > 易错点：结构图把 `out` 的输出也标成 `(1, 1, 256)` 是错的，256 维映射不出一个词；`out` 的输出应为 `(1, 1, 4345)`，Softmax 也不会改变形状。
    * > 来源: P91

* **LogSoftmax 与损失函数的配对**
    * 多分类交叉熵本身是拆开的两步：$\text{CrossEntropyLoss} = \text{LogSoftmax} + \text{NLLLoss}$。
    * 损失直接用 `CrossEntropyLoss` 时，网络里根本不需要写 `LogSoftmax` 这一层，它内部已经把对数算进去了。
    * 网络里写了 `LogSoftmax`，后面的损失函数就只能用 `NLLLoss`；本案例走的就是这条路。
    * > 易错点：两者绝不能同时出现——`LogSoftmax` 已经求过一次对数，再用 `CrossEntropyLoss` 会让它内部再求一次对数，结果就不准了。
    * > 来源: P91

* **解码器测试：逐词解码与长度钉死**
    * 测试函数要测解码器却必须先 `EncoderRNN` 初始化编码器，因为中间语义张量 $c$ 由编码器生成，测右边就得先把左边造出来。
    * 初始化写法在创建表达式末尾直接接上 `.to(device)`，不要先建对象再单起一行搬移；编码器吃 2803、解码器吃 4345，两个模型的隐藏层维度都必须是 256，否则 $c$ 交到解码器手里形状对不上。
    * 打印模型结构：编码器只有 `embedding(2803, 256)` 与 `gru(256, 256)` 两层，**没有 `out` 层**；解码器有 `embedding(4345, 256)`、`gru(256, 256)`、`out(256, 4345)` 三层。
    * $c$ 的来历：`x` 是 `(1, 6)` 时 `(1, 6) → embedding → (1, 6, 256) → gru → (1, 6, 256)`，这 6 个 256 维向量里装着每个英文单词的词向量以及 GRU 处理后的语义关联与隐藏状态信息。
    * 真正交给解码器的是最后一个时间步：`encoder_c[0][-1]` 把 `(1, 6, 256)` 逐层剥成 `(256,)`，它已经包含前面所有时间步的信息。
    * 逐词解码：`for i in range(y.shape[1])` 里的 `y.shape[1]` 即目标句长；`temp = y[0][i].view(1, -1)` 把标量索引补成 `(1, 1)`，再 `output, hidden = my_decoder_gru(temp, hidden)`。
    * 必须显式控制长度的原因：不告诉它"这句话一共几个词"，它可能一路生成到 `(1, 100)` 停不下来；长度是我定的，不让它自己任性发挥。
    * 解码器的起点是编码器的终点：传进去的 `hidden` 就是编码器前向传播交出来的那个最终隐藏状态。
    * > 易错点：`view(1)` 和 `view(-1)` 出来的都是一维张量，只有 `view(1, -1)` 才是二维 `(1, 1)`，解码器输入要的就是二维。
    * > 来源: P92, P96

### 4.3 带注意力的解码器

* **Q、K、V 的角色与形状**
    * > 定义：Q（Query，查询）是查询的问题（解码器本次的输入），K（Key，键）是被查询的对象（来自编码器输出），V（Value，值）是与 K 一一对应的内容（同样来自编码器输出）。
    * Q 一定是"你输入进来的那个东西"：从目标句子里取出一个标量，再用 `view(1, -1)` 转成一行一列，形状 `(1, 1)` → 词嵌入后 `(1, 256)`。
    * K 是编码器输出，形状 `(1, 10, 256)`；V 与 K 同形状 `(1, 10, 256)`。
    * > 易错点：本案例里 K 取的是解码器的 `decoder_hidden`（上一时间步隐藏状态）而不是 `encoder_output`；只有 V 来自编码器，别按直觉想成"K、V 都来自编码器"。
    * > 来源: P93, P96, P103

* **注意力计算的四步与形状**
    * 运算规则：$\text{attn\_weights} = \text{Softmax}(\text{Linear}([Q; K]))$，$\text{attn\_applied} = \mathbf{bmm}(\text{attn\_weights}, V)$。
    * 用文字说就是：Q 和 K 先做拼接，外面套一个 Linear，最外层再套一个 Softmax，最后拿这个结果去乘 V。
    * 拼接意味着形状在这一维翻倍：`(1, 256)` 与 `(1, 10, 256)` 拼起来出现 512，得到 `(1, 10, 512)`。
    * Linear 把 512 压成 1，得到每个位置的打分 `(1, 10, 1)`；Softmax 把打分归一化成权重 `(1, 10)`。
    * 10 个位置上的权重表达的是：生成这个 Q 时分别有多依赖编码器的第 1 个词、第 2 个词……第 10 个词；权重大的位置就是这次生成主要参考的位置。
    * 注意力结果与 Q 再拼一次得 `(1, 1, 512)`，经 `attn_combine` 的 Linear 换回 `(1, 1, 256)`，因为后面的 GRU 只吃 256 维。
    * > 来源: P93, P97

* **注意力融合与汇入 GRU**
    * 为什么还要拼 Q：注意力算出来的是"从编码器那边取回来的信息"，而 Q 是"我现在要生成什么"的原始诉求，拼在一起模型才能同时看到"我问的什么"和"我取回了什么"。
    * 融合结果 `(1, 1, 256)` 与隐藏状态 `(1, 1, 256)` 一起进 GRU，返回的本次隐藏状态与本次输出形状都是 `(1, 1, 256)`。
    * `out` 是 `Linear(256 → 4345)`，输出的 `(1, 4345)` 分别代表预测每一个法文单词的概率，取最大的那个就是本次预测出的词。
    * 整条链路上形状变换只发生在三处：注意力里的两次拼接加 Linear、`attn_combine` 的 Linear、`out` 的 Linear；其余位置（dropout、ReLU、Softmax）形状一律不变。
    * 判断技巧：看到形状变了，往回找**一层神经网络**；看到形状没变，那多半是激活函数。
    * > 来源: P93

* **类 `AttnDecoderRNN` 的构造**
    * 类名只在 `DecoderRNN` 前多加 `Attn` 前缀，两版解码器放在同一个文件里对照着看。
    * `__init__` 收四个参数：`output_size` 法语词表 **4345**、`hidden_size` 隐藏层维度 **256**、`dropout_p` 随机失活概率、`max_len` 句子最大长度 **10**。
    * `hidden_size` 必须和编码器一致，因为 seq2seq 里编码器最后一个时间步吐出的隐藏状态就是解码器这边的 $S_0$，两边维度不对齐就接不上。
    * 九个动作依次落地：保存四个参数、`nn.Embedding(self.output_size, self.hidden_size)`、`self.attn = nn.Linear(self.hidden_size * 2, self.max_len)`、`self.attn_combine = nn.Linear(self.hidden_size * 2, self.hidden_size)`、`nn.Dropout(self.dropout_p)`、`nn.GRU(hidden_size, hidden_size, batch_first=True)`、`nn.Linear(hidden_size, output_size)`、`nn.LogSoftmax(dim=-1)`。
    * `attn` 输入维度写 `hidden_size * 2` 是因为输入是两路合并的拼接结果（$1 \times 512$），输出维度给 `max_len` 因为它输出的就是这个权重分布，权重分布张量形状是 `[1, 1, 10]`。
    * dropout 层的插桩位置在 `attn_combine` 之后：最初传进来的 dropout 概率在建 `embedding`、`attn`、`attn_combine` 时根本没被用上，得给它建一个真正的层把参数用起来。
    * 词嵌入层用的是法语词表大小，因为解码器每一步吃进去的是已经生成的、上一步预测出来的法语词，它落在法语的编号空间里。
    * > 易错点：四个 `self.xxx` 后面在 `forward` 里都要被反查，少存一个后面就得硬写常量。
    * > 来源: P94

* **带注意力解码器的前向传播**
    * `forward` 收三个参数，正好对上 Q、K、V 那一路东西：`input` 形状 `[1, 1]`、`hidden` 形状 `[1, 1, 256]`、`encoder_outputs` 形状 `[batch_size, 句子长度, hidden_size]`。
    * 九个动作：`embedded = self.embedding(input)` → `embedded = self.dropout(embedded)` → `attn_weights = F.softmax(self.attn(torch.cat((embedded[0], hidden[0]), 1)), dim=1)` → `attn_applied = torch.bmm(attn_weights.unsqueeze(0), encoder_outputs.unsqueeze(0))` → `torch.cat((embedded[0], attn_applied[0]), 1)` 后 `self.attn_combine(output).unsqueeze(0)` → `F.relu(output)` → `self.gru(output, hidden)` → `self.softmax(self.out(output[0]))` → 返回三元组。
    * 写 `[0]` 是主动降维：`embedded` 是 `[1, 1, 256]`，取 `[0]` 摘掉批次维变成 `[1, 256]`，因为后面那个线性层处理的是二维张量，拿三维进去它不认。
    * `bmm` 处理三维张量，所以 `attn_weights` 要 `unsqueeze(0)` 从 `[1, 10]` 变成 `[1, 1, 10]`，`encoder_outputs` 要 `unsqueeze(0)` 从 `[10, 256]` 变成 `[1, 10, 256]`。
    * 第五步拼完是 `[1, 512]`，`attn_combine` 压回 `[1, 256]`，再 `unsqueeze(0)` 升回 `[1, 1, 256]` 给 GRU 用。
    * 二维与三维之间的来回转换靠 `unsqueeze` 和 `squeeze`：看到形状对不上，第一反应是该升维还是该降维，而不是去改层的参数。
    * 第八步写 `self.out(output[0])` 而不是 `self.out(output)`，因为 `output` 是 `[1, 1, 256]` 而 `self.out` 要的是 `[1, 256]`。
    * 返回三个值：`output` 形状 `[1, 4345]`、`hidden` 形状 `[1, 1, 256]`、`attn_weights` 形状 `[1, 10]`；第三个返回值是为后面画注意力权重分布图做可视化分析用，不画图可以不返回。
    * `initHidden` 写法：`return torch.zeros(1, 1, self.hidden_size, device=device)`。
    * > 来源: P95

* **前向传播的形状流转速查**

    | 步骤 | 操作 | 输入形状 | 输出形状 |
    | :--- | :--- | :--- | :--- |
    | 1 | `embedding` | `[1, 1]` | `[1, 1, 256]` |
    | 2 | `dropout` | `[1, 1, 256]` | `[1, 1, 256]` |
    | 3 | `cat` + `attn` + `softmax` | `[1, 256]` 与 `[1, 256]` | `[1, 10]` |
    | 4 | `bmm`（双方升维） | `[1, 1, 10]` 与 `[1, 10, 256]` | `[1, 1, 256]` |
    | 5 | `cat` + `attn_combine` + `unsqueeze` | `[1, 256]` 与 `[1, 256]` | `[1, 1, 256]` |
    | 6 | `relu` | `[1, 1, 256]` | `[1, 1, 256]` |
    | 7 | `gru` | `[1, 1, 256]` 与 `[1, 1, 256]` | `[1, 1, 256]` |
    | 8 | `out` + `softmax` | `[1, 1, 256]` 取 `[0]` | `[1, 4345]` |

    * 逐词翻译时每一份输出的含义：`[1, 4345]` 是当前这一个词在法语词表上的概率分布，`[1, 10]` 是生成这一个词时对上面那 10 个源端位置各占多少分量。
    * 每生成一个新词，就有一份新的 `[1, 10]` 权重，注意力机制就是这样一步步加进去的。
    * > 来源: P95, P96

### 4.4 最大长度 10 的补齐与截断

* **固定长度容器 `encoder_output_c`**
    * 写法：`encoder_output_c = torch.zeros(max_len, my_encoder.hidden_size, device=device)`，造出形状 `[10, 256]` 的固定大小张量。
    * 复制动作：`for index in range(encoder_output.shape[1]): encoder_output_c[index] = encoder_output[0, index]`，先 `[0]` 摘掉批次维，再取第 `index` 个时间步的 256 维向量。
    * 编码器出来的是 `[1, 6, 256]`（真实），容器是 `[10, 256]`（我们要的），把真实的那一份填进固定容器，两者不冲突。
    * > 定义：这个张量的作用是存储编码器输出并且尺寸固定，它是全零的，"零"正好可以当填充位。
    * 两个名字要分开：`encoder_output_c` 是固定长度的容器，`encoder_output` 是编码器刚吐出来的真实输出，分开了形状就不会看串。
    * > 来源: P96, P99

* **补齐与截断一次做完**
    * 截断：真实长度超过 10，只往前 10 个位置复制，多出来的直接不要。
    * 补齐：真实长度不到 10，后面那些位置保持 `torch.zeros` 留下的 0，天然就是填充。
    * 统一长度的原因是每句话长度都不一样，张量必须形状统一才能往下算；不够的用 0 补齐、超出的截断，专业名称叫**截断和补齐**。
    * 统一长度才有可算性：如果一直是 `(1, 6)`、`(1, 7)`、`(1, 9)` 这样变，下面几层的矩阵乘法没法配合，整个计算进行不下去。
    * > 易错点：`(1, 6, 256)` 变 `(1, 10, 256)` 这一步**不经过任何线性层**，形状是直接改写出来的，得由代码显式做到；不做这一步，`(1, 10)` 的权重就没法和 `(1, 6, 256)` 相乘。
    * 本案例没有调用 `padding` 之类的现成函数，而是用容器加复刻把这个效果自己模拟出来。
    * > 来源: P93, P96, P99

* **解码器侧的 Q 与长度基准**
    * `MAX_LENGTH = 10` 是截断与补齐用的最大句子长度，包括标点；定 10 是因为统计下来左边那些句子的长度一般不超过 10。
    * `Q` 为什么是 `(1, 1)`：它是从目标句子里取出的一个标量，再用 `view(1, -1)` 转成一行一列。
    * `K` 与 `V` 中间维度是 10 而不是 6、7、9 或 13，就是因为统一长度到 10：不管原始句子是 6 个词、7 个词还是 13 个词，到这里统统变成 10。
    * > 来源: P81, P93

### 4.5 模型搭建的动作与形状速查

* **两版解码器的判别与动作骨架**
    * 两版都是序列到序列架构，编码器完全相同，差别全部落在解码器内部；带注意力版多出来的动作是把解码器的本次输入 Q 和编码器的输出 K 做拼接、算权重、再拿权重去乘 V，最后把结果和 Q 融合一遍。
    * 无注意力版的解码动作本质是"一次查询与一次取最大"：把 Q、K、V 传给 GRU，得到 4345 维输出，再在分布里取概率最高的那一个。
    * 带注意力版是把普通 Q 升级成更强的 Q——升级的是信息量不是维度：普通 Q 里只有"我上一步预测出了什么"一条线索，经过 QKV 之后 Q 里装进了"源句子里哪几个词对我这一步最有用"这一层信息，维度照旧。
    * > 易错点：练习图上的 K 不是"键（Key）"那个 K，而是 GRU 的隐藏状态；同一个字母在不同图里代表完全不同的东西。
    * > 来源: P97

* **Q、K、V 形状的答法与 GRU 四参数读图法**
    * 回答形状要分清"原始形状"和"转置前那一步的形状"：$Q$ 是 `1, 1`；$K$ 原始形状是 `1, sequence_len`（句子原生有几个词第二位就是几），在做变换维度转置之前这一步会变成 `1, 10`；$V$ 是编码器输出张量，形状 `10, 256`。
    * 为什么必然变成 `1, 10`：做注意力计算时编码器输出要按统一长度参与运算，不足的部分由复刻实际编码器输出的做法补到固定长度。
    * 图 2 的流程一句话：Q 和 K 先算匹配分得到注意力权重分布，权重分布与 V 相乘得到中间语义张量 $c$；$c$ 做 combine、降维、激活，变成 GRU 能吃的输入。
    * GRU 那段分四块看：GRU 本体、充当上一次的隐藏状态、充当本次的输入、分别给出本次的隐藏状态和本次的输出。
    * > 来源: P97

* **编码器与解码器的分工**
    * 编码器两层：第一层词嵌入层把英文单词序列换成稠密向量，第二层 GRU 按时间步扫过这个序列；处理结果不交给分类器、也不交给损失函数，只用来获取中间语义张量 $c$。
    * 编码器**不接输出层**，只把 GRU 的结果原样往后交给解码器；一旦挂上输出层就直接出结果了，$c$ 也不再是原汁原味的隐藏信息。
    * 解码器在 GRU 之上补一个 `Linear(256 → 4345)` 加 `LogSoftmax`，把隐藏信息变成词表上的概率分布。
    * 隐藏状态里已经装着接下来要生成的那个词的全部信息，所以解码器的 GRU 后面直接上 `out` 线性层，不再接一步"计算本次输出"。
    * 底层顺序永远是先算本次隐藏状态、再算本次输出：有了 $s_1$ 就能算 `welcome`，有了 $s_2$ 就能算 `to`，有了 $s_3$ 就能算 `beijing`；框架的接口上仍然写成"把本次输入和上次隐藏状态一起传进去"，一次把两者都还给你。
    * > 来源: P92, P97

## 5. 训练设计与单批次训练

> **一句话主旨**：拆分单批次与多轮多批次两个训练函数，用教师强制纠正早期预测偏差，跑通一次完整的迭代链路。

### 5.1 教师强制（Teacher Forcing）

* **定义与纠正动作**
    * > 定义：教师强制（Teacher Forcing）是一种序列生成任务的训练技巧；在 seq2seq 架构中，解码器每次使用真实结果作为输入的一部分，而不是上一个时间步的输出结果。
    * 定义里重点是"**每次**"和"**真实结果**"两个词：是每一次都用真实结果，不是偶尔纠正一次。
    * 对应到图上：上面那个英文句子是特征，下面那个法语句子 $y$ 是目标也就是标签。
    * 纠正动作是——生成下一个 25 的时候，不管你上一个预测出的是什么，我都把 465 当成已知结果甩过去，用它来生成 25；**不会告诉你后边词的答案**，只把已经发生过的位置换成正解。
    * 干预点是"出错的那一步已经被替换成正确答案"，而不是替模型做完整道题。
    * > 易错点：把它理解成"训练时给模型开卷考试"并不准确——不是把整份答案给它看，而是在它已经写错的那一行旁边写下正确的一行，然后继续让它往下写。
    * > 来源: P98

* **要防的问题与两个作用**
    * 正常的生成是一个词一个词往外蹦：第一位真实值 119，预测对了就输出 119；接着拿 119 当输入预测第二位 297；再往后一位真实值是 465 却预测成了 300，就错了。
    * 一步错步步错的具体后果：下一次要生成 25 时用的是那个错的 300 作为本次输入，输入本身就是错的，生成的 25 大概率也是错的。
    * 第一个作用是矫正模型的预测，避免一步错步步错；第二个作用是加快收敛。
    * > 结论：教师强制能够极大地加快模型的收敛速度，并令模型训练过程更加稳定。
    * 本质是在训练模型的时候用已知正确的答案去纠正模型的错误；模型不会自己知道刚才那一步跑偏了，不喂正解进去它就会顺着错的方向一路推下去。
    * > 来源: P98

* **概率判定与设定量级**
    * 判定写法：`use_teacher_forcing = True if random.random() < teacher_forcing_ratio else False`；随机生成一个 0 到 1 之间的值，小于阈值返回 `True`，大于等于阈值返回 `False`。
    * `teacher_forcing_ratio = 0.5` 的含义是**有一半的概率会用上教师强制**。
    * 这个判定有一个重要性质：**它并不知道你这一步错没错**，只知道这次干不干预、下次干不干预，每一次都是独立按概率抽签。
    * 阈值设成 1 因为随机数落在 0 到 1 之间，就意味着永远都用教师强制；也可以不写随机判定，直接用与不用两条分支把代码摆出来。
    * > 易错点：概率不要往上调——设成 1 等于每一步都用真实标签当输入，训练阶段的损失会很漂亮，推理阶段的稳定性反而更差。
    * > 来源: P98, P99, P101, P102

### 5.2 单批次训练流程

* **训练函数拆成两个的理由**
    * 单批次的训练动作写出来大概二三十行（写完三四十行），要是和整个模型的分轮分批次训练揉在一起，起止结构加上代码会非常长、一百多行，阅读性很差。
    * 拆法：上面的函数是**单批次训练过程**，只管"一批次怎么训"；下面的函数负责分轮分批次，只管骨骼和流程，每批具体怎么训就到点去调上面那个函数。
    * 函数任务范围用一句话卡住：完成一个样本从编码、到解码、到反向传播、到优化参数这一整条链路。
    * > 提示：凡是名字带 `demo`、`test` 的测试代码一个都不用练，真正有用的是编码器和解码器这两个函数。
    * > 来源: P99, P102

* **训练超参数与函数入参**

    | 参数名 | 取值 | 含义 |
    | :--- | :--- | :--- |
    | `my_lr` | `1e-4` | 学习率 |
    | `epochs` | `5` | 训练轮数，至少也要跑三轮、五轮、十轮这个量级 |
    | `teacher_forcing_ratio` | `0.5` | 教师强制的比例 |
    | `print_interval` | `1000` | 每训练 1000 条往控制台打印一次 |
    | `plot_interval` | `100` | 每训练 100 条画一次图 |

    * 函数签名收八个入参：`x` 输入序列形状 `(batch_size, sequence_length)`（批次一直是 1，实际是 `(1, 16)` 或 `(1, 18)` 这种）、`y` 目标序列同形状、编码器对象、带注意力的解码器对象、编码器优化器、解码器优化器、损失函数。
    * > 易错点：打印间隔与绘图间隔的作用域是分开的，打印是 1000 条一次、绘图是 100 条一次，两个数不要互相代入。
    * > 来源: P99, P101

* **编码阶段与解码参数准备**
    * 编码：`encoder_hidden = my_encoder_rnn.init_hidden()` 拿到初始隐藏状态，再 `encoder_outputs, encoder_hidden = my_encoder_rnn(x, encoder_hidden)`，拿回本次的隐藏状态与本次的输出。
    * 解码准备四小步：造 `encoder_outputs_c = torch.zeros(max_length, my_encoder.hidden_size)` 的 `(10, 256)` 张量并复刻实际长度、`decoder_hidden = encoder_hidden` 即 $s_0$ 等于编码器的 $h_3$、`input_y = torch.tensor([[SOS_token]], device=device)` 的起始输入、把三样备齐。
    * 复刻写法 `for index in range(x.shape[1]): encoder_outputs_c[index] = encoder_outputs[0][index]`，循环按实际词数把有效位置填进去，剩下的位置保持全零。
    * 解码器第一次输入不是 `welcome` 也不是任何真实单词，而是起始标记；图上标的可能是 `GO`，但不能真的写 `GO`，约定的特殊标记是 `SOS`。
    * > 易错点：张量必须迁移到指定设备，`input_y = torch.tensor([[SOS_token]], device=device)` 里的 `device=device` 不能漏，没迁移一会儿运算就会报错。
    * > 来源: P99

* **两条分支：教师强制与非教师强制**
    * 分支前先准备 `my_loss = 0.0` 与 `y_len = y.shape[1]`；目标长度直接从形状里取，不用去调 `len(y)`。
    * 两条分支的前三小步完全一样：解码器前向传播 → `target_y = y[0][i].view(1)` 取当前时间步真实标签 → `my_loss += my_cross_entropy_loss(output_y, target_y)` 累加损失。
    * 教师强制分支的第四步：`input_y = y[0][i].view(1, -1)`，下一个时间步的输入直接使用真实标签，取的是 `y[0][i]` 而不是 `i + 1`，因为喂进去的是这一位已经发生过的真值。
    * 非教师强制分支的第四步：`top_v, top_i = output_y.topk(1)` 取概率最高的词的索引与概率，命中 `EOS_token` 就 `break` 停止生成，否则 `input_y = top_i.detach()` 把预测词接成下一次输入。
    * 解码器前向传播的入参出参必须张口就能报：输入 `input_y` `(1, 1)`、`decoder_hidden` `(1, 1, 256)`、`encoder_outputs_c` `(10, 256)`；输出 `output_y` `(1, 4345)`、`decoder_hidden` `(1, 1, 256)`、`attention_weights` `(1, 10)`。
    * > 易错点：`view(1)` 是一维、用于算损失（形状 `[119]`，好和 `output_y` 那二维的一批概率做比对），`view(1, -1)` 是二维、用于当前馈输入，写反了形状就对不上。
    * > 易错点：非教师强制分支必须加 `detach()`，因为这一步的输入来自模型自己的预测，不能让"预测接预测"的链条把梯度一路往回穿。
    * > 来源: P99

* **反向传播、参数更新与返回值**
    * 分支之外做第五步：`my_adam_encoder.zero_grad()` 与 `my_adam_decoder.zero_grad()` 清两个优化器的梯度，然后 `my_loss.backward()` 反向传播，最后 `my_adam_encoder.step()` 与 `my_adam_decoder.step()` 各更新一次。
    * 梯度清零要清两个，编码器与解码器各有一个优化器，一个都不能漏。
    * > 提示：清零、反向、更新这三件事的顺序不能颠倒；梯度是累加的，不清零就会把上一步的残留带进来。
    * 第六步返回平均损失：`return my_loss.item() / y_len`，`.item()` 把累加的总损失取成标量，再除以 `y_len` 得到每个时间步的平均损失。
    * 一整个单批次训练只有第 4 步是每个时间步都重复的核心循环，第 1、2 步只做一次，第 5、6 步在整条样本跑完后执行一次。
    * > 来源: P99

### 5.3 view 函数与张量形状

* **三种写法的维度差别**
    * > 定义：`view()` 是 PyTorch 张量（`Tensor`）的对象方法，用来在不复制数据的前提下重新解释这块内存的形状，返回一个共享底层存储的新张量。
    * 实验数据源：`y = torch.randint(0, 4345, size=(1, 7))`，在 $[0, 4345)$ 左闭右开区间随机取整数，取 1 行 7 列；`4345` 正是法语词汇表的大小。
    * 三种写法的输出形状：`y0[3]` 是 `()` 的 0 维裸标量 `tensor(94)`；`view(1)` 与 `view(-1)` 都是 `(1,)` 的 1 维 `tensor([94])`；`view(1, -1)` 是 `(1, 1)` 的 2 维 `tensor([[94]])`。
    * 直观规律：**每多一层中括号，就多一个维度**。
    * `y0` 是 `y[0]`，形状 `(7,)` 仍是张量；`y0[3]` 才是句子里的第 4 个词元，形状 `()`。
    * > 易错点：`torch.randint` 是随机取数，每次重跑数值都不一样；变的只是数值，形状永远不变。
    * > 来源: P100

* **`-1` 的语义与元素个数守恒**
    * `view()` 括号里的每一个数都是一维的长度，正常情况下个数必须和原张量的维数对得上——三维张量就得写三个数。
    * `-1` 是唯一的例外，它是占位符：这一维的长度不写，由 PyTorch 根据元素总数和其余几维推出来。
    * 推导约束是元素个数守恒 $\prod_{k} d_k = N$；只有一维写 `-1` 时，这一维长度由 $N$ 除以其余维度的乘积唯一确定。
    * 回到 `y0_i.view(1, -1)`：`y0_i` 是标量共 1 个元素，`(1, -1)` 告诉 PyTorch"第 0 维长度是 1，第 1 维你自己算"，$1 \times d_1 = 1$ 于是得到 `(1, 1)`。
    * 非要升到二维，是因为解码器一次前向计算处理的是一个时间步的输入，模型内部按批次处理，期望的输入永远是"批大小 × 特征长度"这种二维形式，哪怕两者都是 1。
    * > 易错点：`view()` 只在元素总数能整除目标形状时才成立，各维长度的乘积必须严格等于原来的元素总数；它不能改变元素个数，也不能跨内存跳着取数——改变个数属于切片、拼接或索引，不是 `view` 的职责。
    * > 结论：`view(1, -1)` 的作用就是"封装成二维张量"，它不计算、不查找、不改变数据，只改变数据的形状描述。
    * > 来源: P100

## 6. 多轮多批次训练与损失曲线

> **一句话主旨**：用两层循环把 6 万多条数据来回训 5 遍，记好日志与绘图两套账，逐轮保存模型并画出损失曲线。

### 6.1 训练规模与时间预算

* **训练量级与耗时估算**
    * 外层轮数设成 5，数据集一共 63594 条（按 6 万算），$60000 \times 5 = 300000$，即 30 万个句子要过一遍模型。
    * 这个量级在这台 2060 显卡的机器上跑完要一个多小时；策略是先跑几批让它出结果把模型跑通，等午饭功夫再让它自己跑。
    * 为什么这么慢：批大小是 1，**每一个句子**进来都要走词嵌入、经过 RNN 处理、做注意力计算，一整套都得来一遍，不是每一批做一遍。

    | 环境 | 每 1000 条打印一次的耗时 | 跑完一整轮（6 万条）的估算 |
    | :--- | :--- | :--- |
    | CPU | 约 45 秒（本次实测 35 秒） | 约 50 分钟（同比例推算约 36 分钟） |
    | GPU | 约 23 秒 | 约 20 分钟出头 |

    * CPU 按 6.3 万算共 63 个打印批次：$63 \times 35 = 2205\ \text{s} \approx 36.75$ 分钟；按 45 秒算 $63 \times 45 = 2835\ \text{s}$ 约 47 分钟，5 轮就是 250 分钟左右。
    * > 结论：CPU 一轮 6 万条约 35 到 50 分钟，GPU 一轮约 20 分钟出头；这个差距不是写代码能补的，模型规模一上来设备就是硬门槛。
    * > 来源: P101

* **模型、优化器与损失函数的初始化**
    * 编码器 `EncoderRNN(2803, 256).to(device)`：输入维度等于英文词汇表大小 2803，隐藏层维度 256；它没有"输出维度"这一项，因为输出维度就是隐藏层维度。
    * 解码器 `AttentionDecoderRNN(4345, 256, dropout_p=0.1, max_length=10).to(device)`：输入维度等于法语词汇表大小 4345，隐藏层维度 256。
    * 优化器用 Adam，编码器与解码器各一个，学习率用 `my_lr = 1e-4`，参数直接用 `.parameters()` 从模型里取。
    * 损失函数初始化成 `my_cross_entropy = nn.NLLLoss()`：因为解码器最后一步已经做过 `log_softmax`，而 `nn.CrossEntropyLoss` 内部自己做的是 `log_softmax` + `NLLLoss` 两步，再套一层等于把 softmax 算了两次。
    * > 结论：`log_softmax` 与 `NLLLoss` 是一对；`CrossEntropyLoss` 内部自带 `log_softmax`，配的是未经 softmax 的原始 logits。配对关系弄混就是"多算一回"，是这类代码里最常见的静默错误。
    * > 易错点：解码器的输入维度是法语词汇表大小而不是隐藏层维度，一个是"词表里有多少个词"、一个是"每个词被表示成多长的向量"，千万别串。
    * > 来源: P101

### 6.2 两层循环与损失记账

* **外层循环与内层循环的分工**
    * 外层写法 `for epoch_index in range(1, epochs + 1)` 展开是 1 到 5；从 1 开始编号是为了后面保存模型文件时文件名里直接就是轮次，不用再写 `+1`。
    * 外层开头初始化两个本轮专属累加器 `print_loss_total = 0.0` 与 `plot_loss_total = 0.0`，并记录 `start_time = time.time()`；累加器在本轮开始时清零。
    * 内层写法 `for item, (x, y) in enumerate(tqdm(my_dataloader), start=1):`，调用 `my_loss = train_iters(x, y, 编码器, 解码器, 两个优化器, 损失函数, device)` 完成单批次训练。
    * `enumerate` 会给序列里的每个元素在前面加一个索引，默认从 0 开始，加 `start=1` 就从 1 开始；数据加载器每次吐出来的是一个 `(x, y)` 元组，套一层 `enumerate` 就能同时拿到批次编号 `item`。
    * 用 `tqdm(...)` 把加载器包起来就能显示进度条；进度条不是一开始就动，停在 1%、2% 时别以为程序卡死了。
    * > 易错点：两个函数的参数名写成完全一样是为了 Ctrl+C、Ctrl+V 不出错；形参名和实参名不一样也可以，位置对上就行，但位置一旦错了模型和优化器可能传反，这种错误不报错，只会让你训练半天发现不收敛。
    * > 来源: P101, P102

* **累计到清零的四步动作**
    * 单批次函数返回的是**这一批的平均损失**，因为它最后除以了句子长度；既然它是平均值，多批累加之后还要再除一次批次数量才能得到区间平均值。
    * 两个累加器加的是同一个损失值：`print_loss_total += my_loss` 与 `plot_loss_total += my_loss`，用途不同、数据来源是同一个。
    * 打印：`if item % print_interval_num == 0:` 成立时算 `print_loss_avg = print_loss_total / print_interval_num`，打印轮次、平均损失与耗时，然后把 `print_loss_total` 重置为 0。
    * 绘图：`if item % plot_interval_num == 0:` 成立时算 `plot_loss_avg = plot_loss_total / plot_interval_num`，`plot_losses_list.append(plot_loss_avg)`，然后把 `plot_loss_total` 重置为 0。
    * 耗时用 `time.time() - start_time`，单位是秒，它是**从本轮开始到现在**的累计耗时，所以数字一条比一条大。
    * > 易错点：打印完不重置累加器，第一条日志是前 1000 条的平均、第二条就变成前 2000 条的平均、第三条是前 3000 条，算的是不断拉长的累计平均，根本看不出最近这 1000 条的实际效果。
    * `print_interval_num = 1000` 配控制台日志、`plot_interval_num = 100` 配损失曲线，日志疏、曲线密；想看更细的曲线就把 100 改小，想看更少的日志就把 1000 改大。
    * 规律：**累计 → 到点算平均 → 入账 → 清零**，这四个动作在打印和绘图两条线上各出现一次。
    * > 来源: P101, P102

### 6.3 分轮保存与损失曲线

* **逐轮保存模型**
    * 保存代码写在外层 `for epoch_index` 里面、内层 `for item` 外面——能走到这里说明这一轮的所有批次都跑完了。
    * 保存的对象是 `state_dict()` 也就是模型参数：`torch.save(my_encoder_rnn.state_dict(), f'./model/my_encoder_rnn_{epoch_index}.pth')`，解码器同样存一份带轮次编号的文件。
    * 文件名必须带 `epoch_index`，不带的话第二轮保存时会直接覆盖第一轮的结果；带上轮次编号每轮一个文件，历史全留着。
    * `.pth` 之类的常见后缀还有 `.ptl`、`.pkl`、`.pickle`，用哪个都行，本质都是 pickle 序列化出来的文件，但不能什么后缀都不写。
    * 一轮训练要 50 分钟，5 轮一起跑完再统一保存意味着一个多小时里不能出任何意外：中途点终止、机器崩了、停电了，什么都剩不下。
    * > 结论：正确做法是**一轮一做、一轮一存**；做得再细一点可以永远只保留最近 3 个模型，训练到第 4 轮成功就删第 1 个，滚动地留着最后三个。
    * > 来源: P101

* **损失曲线的绘制与目录准备**
    * 绘制代码：`plt.figure()` → `plt.plot(plot_losses_list)` → `plt.savefig('./image/seq2seq_loss.png')` → `plt.show()`；只有一条折线，横轴是样本区间的顺序、纵轴是列表里存的那一串平均损失。
    * **`savefig` 必须放在 `show` 之前**，顺序反了存下来的就是一张空白图。
    * 最后 `return plot_losses_list` 把损失列表交出去，后面别的地方还要用。
    * > 易错点：`plt.savefig('./image/seq2seq_loss.png')` 里的 `image` 目录必须提前存在，`plt.savefig` 不会替你创建目录树；保存模型要往 `./model/` 写，这两个文件夹要先手动建好，否则程序跑完一轮最后一步写文件失败，那才真叫白跑。
    * > 来源: P101

* **每轮 3000 条的测试开关与实测对照**
    * 调试写法是在内层循环里塞一段 `if item > 3000: break`，`break` 一出内层循环就结束，于是每轮只训练 3000 条，5 轮共 1.5 万条，几分钟就能看到完整效果。
    * > 易错点：这段代码实际开发中万万不能写——正式训练必须把 6 万多条全部跑完，留着这个 `break` 等于模型永远只见过 5% 的数据。
    * 实测现象：进度条才走到 5% 左右程序就跳到第二轮，不是因为它没跑完 6 万条，而是因为我们自己写了每轮只训 3000 条。
    * 实测对照：

    | 批次 | CPU 每 1000 条 | GPU 每 1000 条 | 提升 |
    | :--- | :--- | :--- | :--- |
    | 第 1 批 | 35 秒 | 23 秒 | 约 1.5 倍 |
    | 第 2 批 | — | 23 秒 | 稳定 |

    * 在第一轮跑到一半时人为终止会报 `KeyboardInterrupt`，但**第一轮的模型已经存下来了**，这就是分轮保存的价值。
    * > 来源: P101

* **训练产物的核对与流程复述**
    * 5 轮跑完后 `model` 目录里一共 **10 个**文件，因为 5 轮每轮存一个编码器加一个解码器，$5 \times 2 = 10$，5 组模型一组都没被覆盖。
    * 控制台 5 轮日志每轮每 1000 条打一次，与 `print_interval_num` 对得上；CUDA 环境下一批 1000 条约 20 秒，6.3 万条一轮 63 批即 $63 \times 20 = 1260$ 秒，二十来分钟一轮。
    * 日志里出现的耗时是从本轮开始累计的，不是单批耗时；想算单批速度就盯住相邻两条日志之间的差值。
    * 单批次训练顺序复述：编码 → 解码 → 决定这一步要不要用 teacher forcing → 梯度清零 → 反向传播 → 梯度更新；`train_iters` 里的 iters 指的是一次迭代，也就是一条数据走完这六步。
    * 曲线整体一路向下说明**模型在收敛**：不是"看起来还行"，而是损失单调下降、训练没有跑偏；想让曲线更细就把绘图间隔调小，代价是点变密、保存的图变大。
    * > 易错点：第 3 步的二选一里，用 teacher forcing 时喂进去的是**上一步的真实标签**，不用时喂进去的是**本次的预测结果**，这两个说法容易记串。
    * > 来源: P102

## 7. 模型预测与结果评估

> **一句话主旨**：关闭梯度做自回归解码，逐步挑出概率最大的法语词，按实际用量裁剪注意力矩阵并把结果拼回句子。

### 7.1 自回归解码与注意力矩阵裁剪

* **评估函数 `evaluate_seq2seq` 的定位与推理开关**
    * > 定义：评估函数只负责"用"——把一句英文喂进编码器，一个词一个词地把法语吐出来，最后连注意力权重一起交回去；它不训练、不更新参数。
    * 签名收三个东西：输入 `X`、编码器 `my_encoder_rnn`、解码器 `my_attn_decoder_rnn`；参数外部传进来是因为写评估函数时还没有这两个对象，它们是在后面的测试函数里才被创建、才被加载参数的。
    * 第一行就是 `with torch.no_grad()`；模型已经训练完毕、参数固定死了，这里做的是预测不是训练，就算算出梯度也不会走"清空梯度 → 反向传播 → 更新参数"那一套，算了也是白算，白算还占内存。
    * > 易错点：`torch.no_grad()` 只适用于模型的**预测**过程，训练里绝不能这么写——写了就等于模型永远学不到东西。
    * > 来源: P103

* **编码阶段与解码器参数准备**
    * 编码阶段：`encoder_hidden = my_encoder_rnn.init_hidden()`，再 `encoder_output, encoder_hidden = my_encoder_rnn(X, encoder_hidden)`。
    * 两个返回值的角色：`encoder_output` 是编码器在每个时间步产出的那串状态，后面进注意力时它是 **V**；`encoder_hidden` 是往后传的隐藏状态，既当本次循环的初始状态，也是解码器第一时刻要用的 `decoder_hidden`。
    * 固定长度输出张量：`encoder_output_c = torch.zeros(MAX_LENGTH, my_encoder_rnn.hidden_size, device=device)` 再按 `for index in range(X.shape[1])` 复刻实际输出；形状 `(10, 256)`，`MAX_LENGTH` 是 10、`hidden_size` 是 256。
    * 起始输入：`input_y = torch.tensor([[SOS_token]], device=device)`；解码器第一个时间步必须先有个输入，而在还没有生成任何法语词的时候，这个输入只能是"开始"这个符号本身。
    * 记录容器：`decoder_words = []` 装自己预测出来的法语词，`decoder_attentions = torch.zeros(MAX_LENGTH, MAX_LENGTH)` 初始化注意力矩阵。
    * > 结论：注意力矩阵的形状是 $10 \times 10$——第一个 10 是假设的法语句子最大长度（每生成一个法语词就是一行），第二个 10 是被拉长过的英语句子（每个法语词都要对上面那 10 个英语词算一遍注意力概率）。
    * 就算英文只有 6 个词，也已经把它拉成 10 个了，所以列永远是 10。
    * > 来源: P103

* **自回归解码循环与 QKV 对应**
    * 循环写法 `for idx in range(MAX_LENGTH):`，走 10 次，因为前面已经假定生成的法语最长也是 10 个词；编码器与解码器两边的长度假设必须一致，否则矩阵对不上。
    * 前向传播三进三出：`output_y, decoder_hidden, attn_weights = my_attn_decoder_rnn(input_y, decoder_hidden, encoder_output_c)`。

    | 传进去的参数 | 对应角色 | 是什么 |
    | :--- | :--- | :--- |
    | `input_y` | **Q** | 当前输入词的索引 |
    | `decoder_hidden` | **K** | 上一时间步的解码隐藏状态 |
    | `encoder_output_c` | **V** | 编码器输出张量（拉长后的） |

    * 回来的三个输出：`output_y` 是下一个词的概率分布，`decoder_hidden` 是更新后的隐藏状态接着往下一时刻传，`attn_weights` 是这一步的注意力权重分布。
    * 逐行落位：`decoder_attentions[idx] = attn_weights`，第一次循环填第 0 行、第二次填第 1 行，直到填满 10 行。
    * 选词用 `topv, topi = output_y.topk(1)`，`topv` 是最大的概率值、`topi` 是对应索引；这个思路像 `argmax` 但比它好用——`argmax` 只给索引，`topk` 索引和值一起给。
    * 终止与接续：`if topi.squeeze().item() == EOS_token:` 就 `break`，否则 `decoder_words.append(index2word[topi.squeeze().item()])`；最后 `input_y = topi.detach()` 把预测词当下一个输入。
    * > 易错点：teacher forcing 是**训练**阶段的做法，预测这一步没有纠错的机会，只能是"把当前预测词作为下一时间步的输入"。
    * > 来源: P103

* **注意力矩阵的裁剪**
    * 返回写法：`return decoder_words, decoder_attentions[:idx + 1]`。
    * `idx` 从 0 走到 9 正常会走满 10 次，但中途撞上 `EOS` 就 `break`，循环提前结束，而注意力矩阵是初始化好的 $10 \times 10$，后面没写过的行仍然是全 0。
    * 举例：`idx = 5` 时生成了 `EOS` 触发 break，真实生成的法语词是 **6 个**（索引 0 到 5 都写过结果，第 5 次也生成了东西），所以要保留前 $5 + 1 = 6$ 行，拿到的矩阵是 $6 \times 10$。
    * 如果真按假设跑满 10 个词、全 10 行都写了，`idx + 1` 就等于 10，切出来还是 $10 \times 10$，两种情况下写法都成立。
    * > 结论：注意力矩阵开足 $10 \times 10$ 是"预留空间"，`[:idx + 1]` 是"按实际用量交货"；前面叫假设长度、这里叫实际长度，两者只在提前遇到 `EOS` 时才不相等。
    * > 来源: P103

### 7.2 模型加载与设备映射

* **加载的两个动作与路径选择**
    * 路径定义：`path1 = "./model/my_encoder_rnn.pth"` 是编码器，`path2 = "./model/my_attention_decoder_rnn_5.pth"` 是解码器，选带 `_5` 的那个也就是第 5 轮训练结束时保存的参数，因为轮数越往后效果一般越好。
    * 加载分两小步且顺序不能反：**先造一个结构相同的空对象，再把参数灌进去**。
    * 编码器写法：`my_encoder_rnn = EncoderRNN(input_size=english_word_n, hidden_size=256).to(device)`，随后 `my_encoder_rnn.load_state_dict(torch.load(path1, map_location=device, weights_only=True))`。
    * 解码器写法：`AttnDecoderRNN(output_size=french_word_n, hidden_size=256).to(device)`，`french_word_n` 就是 4345 个法语词，这是解码器每个时间步要从中挑一个的类别数。
    * 先 `.to(device)` 把对象搬到 GPU，再 `load_state_dict` 把参数读进来。
    * > 来源: P104

* **`map_location` 与 `weights_only`**
    * > 定义：`map_location` 决定读回来的参数放到哪个设备上。
    * 正常配对是"用 GPU 训练就用 GPU 预测、用 CPU 训练就用 CPU 预测"；麻烦在于训练时用 GPU、现在想用 CPU 加载去跑会报错。
    * 加了 `map_location=device` 之后设备不挑，方向也可以是反的：GPU 训练 → CPU 预测可以，CPU 训练 → GPU 预测也可以；不加就得老老实实设备配对，否则报错。
    * `weights_only=True` 表示只加载模型的**权重参数**，忽略保存文件里其他内容，读的是参数本身、不去执行任何附带内容，加载更安全也更快。
    * 两个 `print` 打印的是模型层级结构：编码器是 `embedding` 加 `gru` 两层；带注意力的解码器是 `embedding`、`attn`、`bmm`／`attention_bmm`、`dropout`、`gru`、`out`、`softmax`。
    * 迁移学习的由来：别人跑了 6 小时、把 6 万条句子跑满 10 轮训出来的 `.pth` 文件，直接拷过来就能用——这就是迁移学习，简单到就这一个动作。
    * > 来源: P104

### 7.3 文本数值化与结果还原

* **测试样本的格式与硬约束**
    * 样本格式是"英文句子 + `\t` + 法语句子"，一对一行；测试里准备三组就差不多了。
    * 硬约束：自己写的英文句子，里面每个词都必须在那 2803 个英语词里存在，否则词表里查不到，模型也不认识它。
    * 从原始数据里抠样本时，原始形式是"英文 TAB 法语"连成一整串，从 TAB 那儿切一下，左边是英语句子、右边是真实法语句子。
    * 切完每一对都要用单引号包成两个字符串、逗号隔开，凑成一行一对的两元素列表，格式才对得上后面 `pair[0]`、`pair[1]` 的取法。
    * 遍历用 `for index, pair in enumerate(my_sample_pairs):`，`pair[0]` 是英语句子、`pair[1]` 是真实法语句子。
    * > 来源: P104

* **数值化、预测与文本化**
    * 数值化：`temp_x = [english_word2index[word] for word in pair[0].split(" ")]` 按空格切并查词表，随后 `temp_x.append(EOS_token)` 补结束标记，再 `torch.tensor(temp_x, dtype=torch.long, device=device).view(1, -1)`。
    * 这里用的是 `word2index` 而不是 `index2word`，因为现在要的是"从词找索引"，方向不能反。
    * 预测：`decoded_words, attentions = evaluate_seq2seq(tensor_x, my_encoder_rnn, my_attn_decoder_rnn)`。
    * 结果还原：`output_sentence = " ".join(decoded_words)`，因为 `decoded_words` 是一个词一个词的列表，用空格 `join` 连起来才算是能读的句子。
    * 打印三行对照：原始英文句子、真实法语句子、预测法语句子，再加一行 `"=" * 10` 与 `\n` 做样本之间的分隔。
    * > 提示：`view(1, -1)` 是在外面又加一层维度，把原来的一维索引列表变成"$1 \times N$"的二维张量，加完这一层才是模型能吃的批次形式。
    * > 来源: P104

* **实测效果与误差归因**
    * 好的一面：`I am thinking of buying a new umbrella` 生成 `Je pense acheter un nouveau parasol`，基本正确；`he swims very fast` 生成 `Il nage très`，相当准；机构发言人那句意思接近。
    * 也有彻底跑偏的：一条生成出"我正在洗澡"这种和原句毫不相干的内容，还有一条生成出"我是纳尔维克的一个儿子"这样莫名其妙的句子，这就是完全废了。
    * 原因只有一个：**训练太少了**。训练函数里那句 `if i > 3000: break` 让 6 万多条句子只训练了 3000 条，比例大概是 $\frac{3000}{63000} \approx \frac{1}{21}$。
    * 改进三步：把 `if i > 3000: break` 注释掉或删掉，让每轮吃满 6 万条；把轮数从 5 改成 10（10 轮都算少，改成 100 也行）；但轮数一上去算力就顶不住了。
    * 时间账：CPU 上训完一轮大概 50 分钟，10 轮就是 500 分钟、差不多 9 个小时；最实际的做法是晚上睡觉前把训练跑起来，第二天早上模型就跑完了。
    * > 来源: P104

## 8. 注意力可视化与案例复盘

> **一句话主旨**：把注意力权重矩阵画成热力图并读懂两个坐标轴的含义，收束整个案例的架构定位与维度难点解法。

* **注意力热力图的坐标轴与视觉结论**
    * 绘图函数 `demo_test_attention`：先拿数据加载器，再实例化编码器 `EncoderRNN(input_size, hidden_size).to(device)` 与解码器 `AttnDecoderRNN(french_word_n, hidden_size).to(device)`，然后加载参数。
    * 样本句子用 `we are both teachers`，按空格一切是 4 个词；数值化那几步与测试函数完全一样，直接照搬。
    * 关键一行是 `plt.matshow(attentions.numpy())`：用的是 `matshow` 而不是 `imshow`，`mat` 就是 matrix，作用是把一个矩阵直接以矩阵、列表的形式显示出来；张量必须先转成 `numpy` 数组才能交给绘图函数。
    * 存盘路径是 `./img/s2s_attn.png`，最后 `plt.show()` 显示；`print(attentions.numpy())` 与 `print(attentions.size())` 用来解惑，后面的推理都是从这两行打印出来的数出发的。
    * > 定义：纵坐标（y 轴）代表英语词汇，横坐标（x 轴）代表生成的目标语言也就是法语句子；颜色越浅，说明影响越大、关联越大。
    * 两个现象：越往后越重要——生成越靠后的法语词时权重往往落在越靠后的英语词上，整体呈现逐级匹配的趋势；一个法语词会同时用到好几个英语词，不是一对一，而是主要依赖某一个、顺带依赖它周围几个。
    * 横向看是"某一步生成时对整句英语的关注分布"，纵向看是"某个英语词在整段生成的哪些位置被用到"。
    * > 易错点：`2803` 是英语词表、`4345` 是法语词表；编码器进的是英语词表，解码器出的是法语词表，别把 2803 塞进解码器的输出维度。
    * > 来源: P105

* **张量形状 7×10 的来历**
    * 打印结果是 `(7, 10)`；行数 7 是法语侧的实际长度：生成的法语一共 6 个词，多出来的那一行是结束标记 `EOS`，它也在矩阵里占一行。
    * 如果连最开头的开始标记 `SOS` 也算进来就变成 8 了，但这个矩阵里只有结束标记、没有开始标记，所以是 7 行。
    * 列数 10 是英语侧被拉长的长度：`we are both teachers` 一共才 4 个词，加上句末结束标记是 5 个，再加开始标记也才 6 个，凑不到 10——为了统一，英文句子不够 10 个词的一律补成 10 个。
    * `7` 不是固定死的，它等于"这次实际生成了几个词再加一个 `EOS`"，生成长度不同的句子行数就不同；`10` 就是此前反复见到的 `MAX_LENGTH = 10`，与这句话实际有几个词无关，是一个恒定值。
    * 图上的刻度是 0 到 6 不是 1 到 7，因为索引从 0 开始；英文这一侧被统一拉到 10，所以列方向索引是 0 到 9。
    * `[:idx + 1]` 的切片正是这套"假设长度 10、实际长度按 EOS 截断"约定的直接后果：矩阵开足 $10 \times 10$，实际生成 7 行就返回 7 行。
    * > 来源: P105

* **案例复盘与架构定位**
    * 整个绘图流程：加载器 → 编码器解码器 → 预测结果 → 打印 → 画注意力图；绘制注意力图的代码只需要做到两个字——**了解**，不需要自己写，看懂图是怎么来的就够了。
    * 这个案例有两处难：代码量比较多，以及里面维度转换特别多。
    * > 结论：维度的难点是有解的——**把每个张量的形状打印出来**，你是啥形状、我是啥形状，一个个标到整体流程图上，对着图走一遍流程。
    * 注意力机制就两句话：把人的注意力机制迁移给计算机，让计算机也像人一样有侧重点地学习；注意力权重的计算公式是 Q 和 K 先算匹配分，拿到匹配分就是注意力概率，再拿概率去乘 V。
    * 这套公式一共写了三个：前面两个是一般注意力，最后一个"点积并做缩放"的就是**自注意力（Self-Attention）**。
    * > 易错点：本案例用的是 Seq2Seq 架构，而在这个架构里**注意力只加到了解码器上，编码器并没有加注意力**。
    * 顺着"既然加在解码器上管用，能不能也把注意力加到编码器里"这个思路优化再优化，就到了下一个要学的架构：**Transformer**。
    * > 来源: P105
