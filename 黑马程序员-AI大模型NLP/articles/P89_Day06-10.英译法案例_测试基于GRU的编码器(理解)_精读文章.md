# GRU 编码器的测试与形状验证

把编码器的代码写完，就放在那儿不管它，风险是很实在的：形状写错、批次维度搞反、隐藏状态没初始化，这些错误都不会在定义类的时候报出来，只会等到你真正喂进去一批数据才炸。所以写测试这件事不能省——这讲我们就给刚做好的编码器写一段测试代码，把"能不能拼得起来"这件事验掉。

思路其实不复杂，一行一行顺着往下写就行。

## 测试函数的前置准备

`Ctrl` 切进 PyCharm，先定义函数，名字就叫 `test_encoder`。这个函数负责"测试基于 GRU 的编码器"。

按顺序有五个准备动作，前四个都是准备，第五个才进正题。

### 第一步：获取数据集加载器对象

```python
def test_encoder():
    # 1. 获取数据集加载器对象
    my_dataloader = get_data_loader()
```

`get_data_loader` 是前面已经写好的函数，直接调用它的返回值就行。

> **注意**：这里拿到的是同一个 `DataLoader` 对象，不是新造的。这一点在下面看形状时会引出一个把人绕进去的现象，先记住。

### 第二步：编码器参数

```python
    # 2. 初始化编码器参数
    vocab_size = 2803   # 英文词汇表大小
    hidden_size = 256   # 隐藏层维度
```

`vocab_size = 2803` 就是英文词表的大小——2803 个英语单词（词元）。这个数和构建编码器时 `nn.Embedding` 的第 1 个参数是同一个东西。

`hidden_size = 256` 是隐藏层维度，也是词向量维度。写 256 是我们自己定的，想写大一点或小一点都可以，只要模型侧和测试侧保持一致就没事。

### 第三步：创建编码器模型对象

要测它，你得先有一个模型实例。

```python
    # 3. 创建编码器模型对象
    my_encoder_gru = EncoderRNN(input_size=vocab_size, hidden_size=hidden_size)
```

构造时只传两个参数，因为 `EncoderRNN` 的 `__init__` 就要这两个：第 1 个 `input_size` 是编码器词嵌入层的输入维度，也就是词表大小，传 `vocab_size`（2803）；第 2 个是编码器隐藏层的维度，传 `hidden_size`（256）。观察一下，2803 和上面算出来的数对得上。

名字里写 `RNN` 还是 `GRU` 都行，随你。叫 `encoder_gru` 更贴切一点，因为里面实例化的是 `nn.GRU`，不是 `nn.RNN`。

### 第四步（选做）：移动到指定设备

```python
    device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
    my_encoder_gru = my_encoder_gru.to(device)
```

这一步是选做的。PyTorch 默认就在 CPU 上跑，如果你的机器只用 CPU，这行不用写。

但如果要用 GPU，这行必须写：`.to(device)` 把整个编码器的参数搬到你指定的设备上。模型搬了，后面喂进去的数据和初始隐藏状态也得跟着搬，否则就是设备不一致。

### 第五步：遍历数据加载器，进行测试

```python
    # 5. 遍历数据集加载器，截取数据，进行测试
    for i, (x, y) in enumerate(my_dataloader):
```

`x` 是英文侧输入，`y` 是法语侧目标。下面所有的 `5.x` 都写在这个循环体里面。

## 5.1 打印输入索引张量与形状

```python
        # 5.1 打印输入英文句子的索引张量和形状
        print("x.shape:", x.shape, "x:", x)
        break
```

跑起来之后打出来的东西大概是这个样子的：

```text
x.shape: torch.Size([1, 6]) x: tensor([[  14,   15,   42,   43,  139,  888,    1]])
```

`torch.Size([1, 6])` 是 1 批次、句长 6。后面那串数字是单词索引。

这里有个值得停一下的地方：**为什么最后一个数永远是 1？**

因为 1 就是 `EOS`（End of Sequence，序列结束标记）。还记得我们做数据处理时定的规矩吗——句子的开头是 0，结束是 1。所以无论前面的索引是多少、句子有多长，最后一个位置必定是 1，前面那些是什么我们不知道，得跑出来看。

实测也是这样：翻到任何一批，`(1, 6)` 的最后一个是 1，`(1, 9)` 的最后一个是 1，`(1, 3)`、`(1, 5)` 的最后一个是 1。前几个索引是正常的词，最后一个一定是结束标记。

> **提示**：`break` 只是让循环先跑一批、看一组结果，方便讲解。实际开发里千万不要这么写——遍历数据加载器时随手加 `break` 会把训练数据截断，这种代码进不了正式流程。

## 5.2 获取编码器的初始隐藏状态

```python
        # 5.2 获取编码器的初始隐藏状态
        h0 = my_encoder_gru.initHidden(x.size(0), device)
```

这里传进去的批次大小要从 `x` 上取，不能写死——换个批次大小形状就对不上了。同时设备也要按上一步的 `device` 指定，模型在哪块设备上，$h_0$ 就造在哪块设备上。

形状是 `(1, 1, 256)`：1 层、1 批、256 维。

## 5.3 执行前向传播

```python
        # 5.3 执行前向传播
        output, hidden = my_encoder_gru(x, h0)
```

编码器必须先算完，往后一步步算下去，才会得到中间语义向量 $c$。也就是说，编码器算完才能轮到解码器那一坨，顺序不能颠倒。

## 5.4 打印输出结果形状

```python
        # 5.4 打印输出结果形状
        print("output.shape:", output.shape)
```

这里只打形状，不打内容——内容肯定是一坨数字，看了也没用。

问题来了：`output` 应该是 `(1, 6, 256)` 吗？**不一定。**

你输入的是英文句子 `(1, 6)`，输出是 GRU 处理完之后对应的东西，所以句长那一位会跟着输入走。输入如果是 `(1, 9)`，输出就是 `(1, 9, 256)`；输入 `(1, 5)`，输出就是 `(1, 5, 256)`。所以这个位置的第二个数不固定。

但最后一位的 256 是钉死的——词向量/隐藏状态就是 256 维。

## 5.5 打印隐藏状态形状

```python
        # 5.5 打印隐藏状态形状
        print("hidden.shape:", hidden.shape)
```

这个形状一定能确定死：`torch.Size([1, 1, 256])`。因为隐藏状态就是 1 层、1 批、256 维。

```text
循环体内部的数据流向与形状变化：

  x (1, L)                    h0 (1, 1, 256)
     |                              |
     v                              |
  [ 编码器 EncoderRNN ]  <----------+
     |                              |
     +-- output (1, L, 256)         +-- hidden (1, 1, 256)
         句长随输入走                   形状恒定，被参数钉死
```

读图说明：批次维度恒为 1，`output` 的第二维等于输入句子的长度 $L$（可变），`hidden` 的第三维等于 `hidden_size`（恒为 256）；`hidden` 的三个维度由 `num_layers`、`batch_size`、`hidden_size` 共同决定，与句长无关。

## 输出长度与输入长度看似不一致的原因

前面留了一个坑，这里补上：有时候你会发现打印出来的 `x` 是 `(1, 6)`，但 `output` 却是 `(1, 7, 256)`；下一次跑又变成 `x` 是 `(1, 10)`、`output` 是 `(1, 8, 256)`。看起来像是编码器算错了。其实不是，原因在 `get_data_loader` 里面。

回头看那个函数，里面做了一件"仅显示一批"的事：它在创建加载器的过程中已经随机拿过一行数据并打印出来了。这个打印是随机的，取的是第一条。

现在回到测试函数：我们调 `get_data_loader()`，把它的返回值赋给 `my_dataloader`。也就是说，**函数内部那次随机取样消耗掉了一批，我们在 `for` 循环里遍历时再拿到的，是另一批随机的数据**。

于是上面那个 `x`（函数内部打印的那条）和我们循环里真正喂进编码器的 `x`，根本不是同一批。你把两个不同批次的形状放在一起比，当然对不上：

- 函数内部打印的 `x` 是 `(1, 9)`，循环里拿到的 `x` 是 `(1, 8)`，`output` 就是 `(1, 8, 256)`；
- 函数内部打印的 `x` 是 `(1, 6)`，循环里拿到的是 `(1, 7)`，`output` 就是 `(1, 7, 256)`。

所以结论很简单：**不应该看上面那条随机样本，应该看循环里实际喂进去的那一批。** 把函数内部那次打印注释掉，这个"干扰"就消失了——那时候你会看到 `x` 是 `(1, 6)`，`output` 就必定是 `(1, 6, 256)`；`x` 是 `(1, 9)`，`output` 就必定是 `(1, 9, 256)`。

> **易错点**：`x` 和 `y` 这一对也是同类陷阱。`x` 的句长是固定长度的**英语**句子长度，`y` 的句长是**法语**句子的长度，两者本来就可以不一样。所以别拿 `x` 的长度去要求 `y`，也别拿上一批的形状去要求这一批。

把上面那次随机打印注释掉之后，`for` 循环里其实就只剩一个 `break`，这个循环也就没有意义了——加载器每次只取一批，而且是随机取的一批。直接顺序执行一遍就行。

## 多批实测

把上面的干扰清掉之后，反复右键运行几次，看到的序列是稳定的：

| 输入 `x` 形状 | 输出 `output` 形状 | 隐藏状态 `hidden` 形状 |
| --- | --- | --- |
| `(1, 6)` | `(1, 6, 256)` | `(1, 1, 256)` |
| `(1, 9)` | `(1, 9, 256)` | `(1, 1, 256)` |
| `(1, 5)` | `(1, 5, 256)` | `(1, 1, 256)` |
| `(1, 8)` | `(1, 8, 256)` | `(1, 1, 256)` |

一眼看得出规律：给进去的是"1 批次、一句英语、$L$ 个单词"，拿回来的就是"1 批次、$L$ 个时间步、256 维"，最后那 256 就是一层隐藏状态的维度。

> **结论**：`output` 的第 2 维 100% 等于输入句子的长度，`hidden` 的三个维度恒为 `(1, 1, 256)`。只要这两条同时成立，编码器的实现就是自洽的。

## 测试的意义

这段代码能跑通，说明一件事：前面构建的那个基于 GRU 的编码器没有问题。

再往下说一句：**测试里那个字符长度、那个 `break`，其实都可以不写**。因为它们的作用只是验证第 6 步写出来的东西对不对。现在能正常出结果，而且和我们预想的形状完全一致，那就说明编码器这一层是通的。
