# 用 AutoModelForQuestionAnswering 做中文抽取式问答：从输入拼接格式到答案区间还原

阅读理解这个任务和前面几个差不太多，真正需要改的地方只有一处：加载模型时换类。上一节用的是 `AutoModel`，这一节要换成 `AutoModelForQuestionAnswering`。也就是说，Hugging Face 这套接口里，不同任务对应的加载入口不一样，你换了任务却忘了换入口，跑起来就会报错。

这件事在班里确实有人踩过：六个任务的代码和模型都一模一样，人家能跑，自己一跑就报错。原因通常是 Anaconda 版本、驱动版本这些环境差异。有两条路可以走：一条是降版本、把环境往回调，另一条是换一个模型。做阅读理解的模型不止一个，你可以去 Hugging Face 上找：页面上方有个 `models` 入口，点进去，从左边挑 `tasks`，找到和你当前任务相关的那一类模型，可以在网页上先试试效果，觉得能用，再把模型下载到本地。

这一节我们就用本地那个中文 MRC 模型走完抽取式问答的全流程。

## 1 抽取式问答的任务形态与模型加载

先给任务下个定义。

> **定义**：抽取式问答（Extractive Question Answering）给定一段文本和一个问题，让模型从这段文本里**找出**答案所在的那一段，而不是自己生成一句话。

模型加载部分和老套路一致，只有类名变了：

```python
from transformers import AutoTokenizer, AutoModelForQuestionAnswering
import torch

# 第 0 步：定义变量记录模型名
model_name = r"C:\software\develop\src\talk\chinese-bert-wwm-mrc"

# 第 1 步：加载分词器对象
my_tokenizer = AutoTokenizer.from_pretrained(model_name)

# 第 2 步：加载模型
my_model = AutoModelForQuestionAnswering.from_pretrained(model_name)
```

> **易错点**：这里不是直接 `AutoModel`。直接用它加载，模型顶部没有问答头，取不到我们要的 `start_logits` 和 `end_logits`。选 `AutoModelForQuestionAnswering`。

## 2 上下文与问题的构造

第三步准备文本。这里有一个细节，讲之前先想清楚：**上下文里最好不要写空格**。

原因不在"好看不好看"，而在"模型能不能定位"。空格会被分词器删掉，你肉眼看到的"我叫 张三"和模型实际拿到的"我叫张三"长度不一样，后面靠位置索引去切答案就会差位。

> **易错点**：做分隔时优先用逗号或其他标点，尽量不要用空格。空格不统计。

所以我们的上下文故意用空格分隔，就是要让这件事露出来：

```python
# 第 3 步：准备文本
context = "我叫 张三 我是一个程序员 我的喜好是 PPQ"   # 故意用空格分隔，观察被忽略的后果
questions = ["我是谁？", "我是做什么的？", "我的爱好是什么？"]
```

三个问题写在一个列表里。模型是**逐个问题**做推理的：一个问题进去，一段答案出来；下一个问题再进去，再出一段答案。所以这里必须用 `for` 循环驱动。

## 3 逐问题编码：encode_plus 的参数

第四步开始循环。循环体第一件事，是把当前问题转成模型可接受的输入格式 —— 也就是把"我是谁"按词表转成编号。

```python
for question in questions:
    # 4.1 把问题与上下文一起编码成模型输入
    inputs = my_tokenizer.encode_plus(
        question,                      # 参 1：当前问题
        context,                       # 参 2：包含答案的上下文文本
        return_tensors="pt"            # 参 3：返回张量形式
    )
    print("inputs:", inputs)
```

三个参数各自的含义：参 1 是当前问题；参 2 是包含答案的上下文文本；参 3 指定返回张量。

跑出来会打印三组 `inputs`，因为问题一共三个。第一眼看不出问题，但把 `input_ids` 逐个数下去就会卡住：

- 开头 `101` 是 `[CLS]`，这个没问题；
- 接着是问题"我是谁？"，到 `102` 结束 —— 这是 `[SEP]`；
- 然后应该接上下文"我叫张三 我是一个程序员 我的喜好是 PPQ"；
- 再往后走完全部内容，**再也没有出现过第二个 `102`**。

按我们的直觉，上下文结束处应该还有一个 `[SEP]`，可它就是不出现。这也是最容易让人怀疑"是不是我转错了"的地方。

> **结论**：`encode_plus` 收到"问题 + 上下文"两个字符串时，不是各转各的，而是把它们**拼成一条序列**再编码。所以打印出来的三个 `input_ids` 长度相同、内容不同，不同的只是中间那一段问题。

## 4 输入格式：input_ids 的拼接顺序与 token_type_ids 分工

那这条拼好的序列到底长什么样？第一个键 `input_ids` 的格式是：

$$[\text{CLS}] + \text{问题} + [\text{SEP}] + \text{上下文} + [\text{SEP}]$$

第二句 `[SEP]` 确实存在，只是它在整条序列的最后，被中间那一大段上下文推远了，所以第一眼看容易觉得"中间缺一个"。

**空格不统计**。你写"我叫 张三"，进到 `input_ids` 里的只有"我叫张三"四个 token，中间那个空格不在其中。这就是前面为什么反复强调别用空格做分隔。

第二个键是 `token_type_ids`，它负责区分"这一段是问题"还是"这一段是上下文"：

| 键名 | 取值规律 | 含义 |
| --- | --- | --- |
| `input_ids` | `[CLS]` + 问题 + `[SEP]` + 上下文 + `[SEP]` | 拼接后的索引序列 |
| `token_type_ids` | 问题段为 `0`，上下文段为 `1` | 归属标记：`0` 表示问题，`1` 表示上下文 |
| `attention_mask` | 本讲全为 `1` | `1` 表示真实位置，`0` 表示填充位 |

第三个键是 `attention_mask`。这条序列里全是真实 token，没有任何填充，所以它全是 `1`。`0` 留给填充位。

把第一个问题"我是谁？"的序列逐位摊开，和前面的格式表对齐看：

```text
位置     内容                       说明
------------------------------------------------------
  0      [CLS] = 101                序列开头
  1      我       ┐
  2      是       │  问题："我是谁？"
  3      谁       │  共 4 个 token
  4      ？       ┘
  5      [SEP] = 102                问题与上下文的分界
  6      我       ┐
  7      叫       │
  8      张       │
  9      三       │  上下文："我叫张三"
 10      我       │  我是一个程序员 我的喜好是乒乓球
 11      是       │  （原文用空格分隔，空格不统计）
 12      一       │
 13      个       │
 14      程       │
 15      序       │
 16      员       │
 17      我       │
 18      的       │
 19      喜       │
 20      好       │
 21      是       │
 22      乒       │
 23      乓       │
 24      球       ┘
 25      [SEP] = 102                序列结尾
```

读图说明：`[CLS]` 与 `[SEP]` 把整条序列框住，中间被一个 `[SEP]` 切成"问题区"和"上下文区"，`token_type_ids` 也就照着这条分界线取值。三个句子共用同一个上下文区，变的只有问题区。

顺便验一下词表映射，确认这条序列没有错位。从上下文里随便抠一个 token，比如索引 `1962`：去 MRC 模型目录下的 `vocab` 里按"索引 + 1"的行号找，第 1963 行是"好"字 —— 对应"我的喜好是乒乓球"里的那个"好"。位次也对得上。

到这里，三个问题跑出来会是三组结构完全相同、只有问题段内容不同的序列。固定的部分：`[CLS]`、`[SEP]`、上下文、`[SEP]`。变化的部分：问题。

## 5 模型推理与 start_logits、end_logits 的形状

内容处理完，接下来喂给模型取输出。

```python
    # 4.2 切到评估模式并做推理
    my_model.eval()
    output = my_model(**inputs)

    # 4.3 获取结果
    print("output:\n", output, "\n" * 3)
```

`\n` 乘 3 是每个结果后面空三行，把三组输入输出隔开，方便肉眼对比。

`output` 里 `loss` 先不管。第一个要看的键是 `start_logits`，第二个是 `end_logits`。数一下它的长度：`0` 到 `25`，一共 26 个 —— 正好等于上面那条序列的长度，也就是 `[CLS] + 问题 + [SEP] + 上下文 + [SEP]` 合起来的 token 数。

```python
    print(output.start_logits.shape)
    print(output.end_logits.shape)
```

两个形状一样，都是 `1 × 26`。

> **定义**：`start_logits` 表示**答案起始位置**的分数分布，`end_logits` 表示**答案结束位置**的分数分布。两者的长度都等于输入序列长度，因为每一个 token 位置都可能是答案的起点，也都可能是终点。

说白了，这 26 个位置里，模型对"哪一位最像答案的开头"给一套分，对"哪一位最像答案的结尾"再给一套分。我们要做的就是从这两套分布里各取一个位置，中间那段就是答案。

## 6 答案区间的计算与切片

第五步计算预测答案，也就是开头的位置索引和结束的位置索引。

```python
    # 4.4 计算答案的起始、结束位置索引
    start = torch.argmax(output.start_logits)
    end = torch.argmax(output.end_logits) + 1
    print(f"start: {start}, end: {end}")
```

`torch.argmax` 就是在 26 个分数里找最大值所在的位置。

这里有一个必须解释清楚的动作：**`end` 为什么要加 1**。因为我们后面靠切片把答案取出来，而切片是包左不包右的。假设模型认为答案是第 2 到第 5 个 token，如果切片写成 `[2:5]`，第 5 个 token 拿不到，答案会少一个字。所以结束索引要加 1。

> **易错点**：`end` 不加 1，取出来的答案永远缺最后一个字。这不是模型预测错了，是切片边界的问题。

第一个问题跑出来是 `start = 8`、`end = 10`（原值 9 加 1）。也就是说答案落在第 8 位到第 9 位，不含第 10 位。

## 7 答案还原：张量取值与 token 转换

最后一步，把这两个位置索引对应的 token 从 `input_ids` 里切出来，再翻译成文字。

```python
    # 4.5 截取答案区间并还原成字符串
    answer = my_tokenizer.convert_tokens_to_string(
        my_tokenizer.convert_ids_to_tokens(
            inputs["input_ids"][0][start:end]
        )
    )
    print(question, answer)
```

这段代码是层层剥开的，从里往外看：

1. `inputs["input_ids"]` 是一个嵌套的张量，形状是 `1 × 26`，外面还包着一个批次维度；
2. `[0]` 把最外面那层批次框拆掉，拿到具体的元素列表；
3. `[start:end]` 按区间切片，拿出答案位置上的那几个 token 索引；
4. `convert_ids_to_tokens` 把索引转成 token 文本；
5. `convert_tokens_to_string` 把若干 token 拼成一句可读的字符串。

> **易错点**：不要用 `convert_tokens_to_string` 去接索引，它接的是 token；把索引转 token 的那一步是 `convert_ids_to_tokens`，顺序反了会直接报错。

第一个问题的答案对一下位：第 8 位是 `2476`，第 9 位是 `676`。去词表里查：`2476` 对应行号 2477，是"张"；`676` 对应行号 677，是"三"。拼起来就是"张三"。

接下来循环继续往下走，从列表里取出第二个问题"我是做什么的？"，上下文不变，同样一套编码、推理、取位、还原，答案"程序员"就出来了。第三个问题"我的爱好是什么？"，答案是"乒乓球"。

```text
我是谁？        → 张三
我是做什么的？   → 程序员
我的爱好是什么？ → 乒乓球
```

## 8 整条链路的推进顺序

把这一节的流程按顺序摆开：

```text
model_name（变量记录模型名）
   ├─ AutoTokenizer.from_pretrained            → my_tokenizer
   └─ AutoModelForQuestionAnswering.from_pretrained → my_model
                     │
        context 一段 + questions 三条
                     │
        for question in questions：逐个问题推理
                     │
        encode_plus(question, context, return_tensors="pt")
                     │
   inputs → input_ids（CLS+问题+SEP+上下文+SEP）
            token_type_ids（问题 0 / 上下文 1）
            attention_mask（全 1）
                     │
        my_model.eval() → output = my_model(**inputs)
                     │
   start_logits（1×26） → argmax → start = 8
   end_logits  （1×26） → argmax + 1 → end = 10
                     │
   input_ids[0][8:10] → convert_ids_to_tokens → convert_tokens_to_string
                     │
                  "张三"
```

读图说明：整条链路只有一个循环，循环里每一步都重来一遍：编码、推理、取分布、定位区间、还原文本；上下文和模型始终不变，变的只有循环变量 `question`。

真正要记住的是三件事：

1. 抽取式问答的输入是**一条拼接序列**，格式为 `[CLS] + 问题 + [SEP] + 上下文 + [SEP]`，空格不参与统计；
2. 模型给的是 `start_logits` 与 `end_logits` 两套位置分布，长度等于序列长度；
3. 结束位置要加 1 再切片，因为切片包左不包右。
