# 具体模型方式做中文完形填空：把 Auto 换成 BERT

接下来讲 Transformers 的最后一个方式：**具体模型方式**。你会发现它跟自动模型的方式思路几乎一样，只是 API 不同。所以这一节用 BERT 做分词器的文本数值化，做完形填空（fill-mask）就行了。

你可能会问：为什么那六个任务不都写一遍，偏偏只做完形填空？原因特别简单——其他五个一模一样。既然一模一样，写第二遍就只是把同一份代码抄到另一个标题底下，这种活没有意义。

先把思路摆出来：加载 Tokenizer、加载模型、文本转张量、喂数据得结果、打印结果。跟自动模型的思路一样不一样？一模一样。

---

## 1 自动模型与具体模型的关系

### 1.1 唯一的区别在 API 名字

先看不一样的地方在哪。加载的是 `BertTokenizer`，这个名字说明你用的是 **BERT 系列**的模型；以前加载的那个叫 `Auto`，也就是自动模型。区别就这么点——**只差 API**。

```text
自动模型方式                      具体模型方式
-----------                      -----------
AutoTokenizer.from_pretrained    BertTokenizer.from_pretrained
AutoModelForMaskedLM             BertForMaskedLM
```

读图说明：左边一列与右边一列逐行对应，函数名里的动作完全相同，变的只是类名里的前缀——一个是 `Auto`，一个是 `Bert`。

那剩下的代码呢？`encode_plus` 还叫 `encode_plus`，模型还是往里一传。除了前面那个类名不一样，思路跟函数都是一模一样的。所以说穿了，**这就是一个换类名的问题**。

### 1.2 为什么功能更全

换个 API 就只是为了改个名字吗？不是。这些具体模型类**底层支持的比 `Auto` 更细致、更深入**。

> **结论**：`Auto` 是"我帮你挑一个够用的"，`Bert` 是"你自己挑，我把更多口子开放给你"。

要理解这件事，举个跟 NLP 无关的例子：现在我要把 10、20、30 这三个数存下来。用 `list` 行不行？用集合行不行？用元组行不行？都能存。用 NumPy 的 `ndarray` 行不行？也能。用 `tensor`（张量）行不行？还是能。

就"把 10、20、30 存下来"这一个需求而言，它们之间有区别吗？没有，都是存。但要说有区别——肯定有，因为 `tensor` 的 API 比 `ndarray` 的 API、比列表的 API 更多更全。仅此而已，没别的。

这个类比搬回来看就清楚了：想玩得更细致，就用 `Bert` 这一队把 `Auto` 替掉；想深入比较，按住 `Ctrl` 点进类定义里去翻——`BertTokenizer` 里有哪些动作，`AutoTokenizer` 里又有哪些动作，两边对着看，你会发现右边的 API 更多一点、更全一点、功能稍微强大一点。

> **提示**：具体模型的输入输出格式各厂商可能有细微差异，这是灵活性的代价。基础功能上它们的用法完全一致，所以其余的就不再演示了，没有多大意义。

## 2 代码落地

新建一个操作，文件命名 `DM03`，意思是具体（special）模型。这一节的定位写在注释里就够了：具体模型方式完成 NLP 任务，其方式与自动模型几乎一致，只是在加载模型和分词器的 API 上稍有不同；因此这里只演示一个案例。细节记在笔记本上——**除了类名不一样，调用方式稍有不同，其他都一模一样**。

导包这一步不用手写，直接把任务文件里现成的三行拉过来取舍：`AutoConfig` 不用，`AutoModel` 不用，`AutoTokenizer` 要用；模型那边只留一个 `AutoModelForMaskedLM`，其余删掉。整理完，跑起来：

```python
from transformers import AutoTokenizer, AutoModelForMaskedLM

model_name = r''

my_tokenizer = AutoTokenizer.from_pretrained(model_name)
my_model = AutoModelForMaskedLM.from_pretrained(model_name)

inputs = my_tokenizer.encode_plus('测试具体模型方式演示完形填空，', return_tensors='pt')
outputs = my_model(**inputs)
print(outputs)
```

先看清楚：这段代码**跑的是自动模型，不是具体模型**，因为里面写的还是 `Auto`，预测出来的最大概率也是自动模型的。它跑通了，我们才开始动手改。

改法分两种心态。想偷懒，直接 `Ctrl+R` 全局替换，把所有 `Auto` 换成 `Bert`，点一下 `Replace all` 完事。想一步到位也是一回事：

```python
from transformers import BertTokenizer, BertForMaskedLM

model_name = r''

my_tokenizer = BertTokenizer.from_pretrained(model_name)
my_model = BertForMaskedLM.from_pretrained(model_name)

inputs = my_tokenizer.encode_plus('测试具体模型方式演示完形填空，', return_tensors='pt')
outputs = my_model(**inputs)
print(outputs)
```

注意类名不是机械替换：`AutoModelForMaskedLM` 换过去叫 `BertForMaskedLM`，中间那个 `Model` 是不要的。换完剩下的一堆代码全都不用动，右键跑一遍，结果一样。

有一处现象值得留意：换完以后打印的日志比刚才少很多。原因就是——如果只做基础的、简单的这些活，写法跟刚才是一样的，只是把 `BertTokenizer`、`BertForMaskedLM` 这两行换一下而已。

## 3 两者区别与联系的完整说明

收回来，具体模型方式的实现流程是：第一步加载分词器，第二步加载模型，第三步文本转张量，第四步把张量数据丢给模型获取结果，第五步打印。如果第五步的结果不一定能满足要求，还得对结果稍微做点处理——需要处理时再处理。

真正要掌握的是这两条路的**区别和联系**。

- 相同点：两者都能做 NLP 任务。
- 自动模型：通过任务类型让 Transformers 统一管理各个厂商的预训练模型，由它统一定义与管理。
- 具体模型：开发者自己调用具体的预训练模型，输入输出格式自己把控，更灵活，但难度也更大。

### 3.1 作业与规则：Hugging Face 的角色

"通过任务类型让 Transformers 管理各个厂商"这句话很抽象，得翻译一下。

设想我今晚给全班布置一份作业：定义一个函数，实现模拟计算器，加减乘除都要有，正弦、余弦、开根、指数也都要有。函数名就叫 `my_calc`。规则我定好，写清楚。

现在问一个问题：张三同学来写这份实现，李四同学也来写这份实现，他们俩的代码思路会完全一样吗？肯定不会一样。但**最终完成的效果一定是我要的那个效果**。

把角色对上：

```text
Hugging Face   -->  布置作业、制定规则的人（规则 = 接口）
各个厂商 A/B/C -->  交作业的人（按规则把模型做出来）
我们（调用者）  -->  只管看最终效果，不管底层怎么实现
```

读图说明：规则由一方统一制定，实现由多方分别完成，调用者只跟定规则的那一方打交道。

Hugging Face 就是把规则写好——分词器叫什么、模型的接口长什么样、具体用谁，都定死。它再去找各个厂商，把它们的模型功能拿过来用。作为调用者，我们不需要关心底层怎么做的，只需要把这套规则拿来用。这就是自动模型。

> **结论**：自动模型是你直接找 Hugging Face，让 Hugging Face 去适配底层；底层变量名怎么起、函数怎么命名，都得照规则来，不能乱变。代价是你被管着，好处是更固定、更通用。

### 3.2 具体模型的角色变化

具体模型有点像"你不走 Hugging Face 那一套了，直接跟厂商对接"。

`BertForMaskedLM` 就不是 `Auto` 了——它只能下载 BERT 系列的模型。你要是想玩 GPT，用这套就走不通了。

> **易错点**：具体模型方式要求开发者自己把控各厂商的输入输出。有可能同一个功能，参数名有个细微差异——比如分词器在自动模型这边叫 `Tokenizer`，到了某个具体实现里叫 `tokenizers`，多一个字母，就是这种情况。

功能更全也是同一个原因：你是直接跟模型对接的，拿到的口子更全；而自动模型那边，有些"我觉得不需要开放给你"的内容，Hugging Face 在中间就帮你屏蔽掉了。

对普通用法来说，两者没什么太大区别，用谁都可以。

```text
                自动模型                     具体模型
调用路径     我 ──> Hugging Face ──> 厂商    我 ──> 具体模型
可换模型     按任务类型全厂商可选            锁定该系列（BERT 就是 BERT）
参数命名     统一规范，不能乱变              各厂商自行把控，可能有差异
功能开放     中间层做了屏蔽，够用为主         直接对接，更全更灵活
使用难度     低                             高
```

读图说明：两条路径的分叉点在中间那一层——有它，换来的是统一和通用；没有它，换来的是灵活和功能完整。

那么需要掌握哪一个？**自动模型其实就足够你玩了。** 具体模型作为了解，感兴趣可以自己去试试。

## 4 本讲提到的题目

### 题目一：自动模型与具体模型方式的区别和联系

**题干**：在 Transformers 库中，说明自动模型和具体模型方式两者之间的区别和联系。

**答案与解析**：

- **相同点**：两者都能做 NLP 任务，且核心实现流程完全一致——加载分词器、加载模型、文本转张量、喂数据得结果、打印结果，五步一个不多一个不少。
- **自动模型**：通过任务类型让 Transformers 管理各个厂商的预训练模型，由 Hugging Face 写好规则并统一定义管理。调用者不关心底层实现，只按统一接口使用，因此更固定、更通用。
- **具体模型**：开发者自己调用具体的预训练模型。各厂商的输入输出可能有差异，需要开发者自己把控。因此指定模型方式更灵活，但难度也更大，同时开放的 API 更全。
- **落地判断**：日常使用自动模型就够了；想更细致地玩，把 `Auto` 换成对应系列的类名（如 `Bert`）即可，剩下的代码一模一样。

### 题目二：三组输入字段的含义

**题干**：`input_ids`、`token_type_ids` 和 `attention_mask` 分别代表什么？

**答案与解析**：

- `input_ids`：句子在词表中对应的序号，也就是把文本转成词表编号的结果。
- `token_type_ids`：句子分段的标记，表示这是第几个句子。如果只有一个句子，可能全是 0；如果是两个句子，就是 0 和 1。三个句子时可能是 0、1、2，也可能是 0、1、0、1、0、1 这种交替排布——具体要看实际打印出来的结果。
- `attention_mask`：字面翻译是注意力掩码，本质含义是**真实还是填充**。1 代表真实数据，0 代表填充（padding）出来的位置。

### 题目三：找出下面句子错误的一项

**题干**：下面句子（把模型的输入传给模型的写法）中错误的一项是哪一个？

**答案与解析**：

答案是 **D**。D 项直接把字典传了进去，没有解包，正确写法应该是 `**inputs`。

> **提示**：`**` 是解包运算符。`inputs` 是一个字典，模型接收的是关键字参数，所以必须写成 `my_model(**inputs)`；写成 `my_model(inputs)` 就是把整个字典当成一个位置参数塞进去，直接报错。

这三个字段和这个解包写法，前面已经强调过很多次了。一眼看不出来，说白了还是一句话——练得少。多敲敲、多练练就好了。
