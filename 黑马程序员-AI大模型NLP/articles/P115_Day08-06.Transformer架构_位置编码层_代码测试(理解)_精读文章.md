# 位置编码层的测试代码：从 2×4 到 1×60×512 的形状追踪

位置编码层的代码刚才已经写完了，接下来就是把它跑起来看看。这一步不能省——不是"证明代码没写错"这么简单，而是**位置编码这一层到底对词向量做了什么**，只有打印出来才能看明白。我以前讲 Torch 的时候就说过，很多同学看不懂 Transformer 的代码，不是因为逻辑难，是因为脑子里没有"这一步的形状是多少、下一步的形状是多少"这张图。这张图画不出来，代码就只能靠背。

所以这一篇我们就用一段测试代码，从 `(2, 4)` 的输入一路打到 `(2, 4, 512)` 的输出，中间每一个张量的形状都亲手打一遍。

---

## 1. 测试代码的七步骨架

整个测试函数的写法和前面 demo 的套路一样，就是多了"位置编码"这一步。先定义配置，再实例化两层，再喂输入，最后相加返回。

### 1.1 词汇表大小与词嵌入维度

第一步还是老样子，定义**词汇表大小（vocabulary size）**和**词嵌入维度（d_model）**：

```python
vocab, d_model = 1000, 512
```

`vocab = 1000` 表示词表里一共 1000 个词，`d_model = 512` 表示每个词用 512 维向量表示。这两个数字后面每一步的形状都能对得上：词嵌入层的权重矩阵就是 `(1000, 512)`，查表查出来的每个词就是一个 512 维的向量。

### 1.2 实例化词嵌入层与构造输入张量

第二步实例化**词嵌入层（embedding layer）**，第三步造输入：

```python
# 1) 实例化词嵌入层
my_embed = nn.Embedding(vocab, d_model)

# 2) 构造输入张量
x = torch.LongTensor([[1, 2, 3, 4], [5, 6, 7, 8]])   # shape: (2, 4)
```

输入张量的形状是 `(batch_size, sequence_length)`，也就是 `(2, 4)`。这两个数字的意思很直白：**两个句子，每个句子四个词**。这一步和前面那个输入层 demo 里的写法一模一样，因为本来就是同一个输入。

### 1.3 计算词向量

第四步，把输入丢进词嵌入层，拿到**词向量**：

```python
embed_x = my_embed(x)
print(embed_x.shape)   # torch.Size([2, 4, 512])
```

形状从 `(2, 4)` 变成 `(2, 4, 512)`——一个词一个 512 维向量，那么两个句子、每句四个词，自然就是 `2 × 4 = 8` 个 512 维向量。到这里为止，流程还是老样子。

### 1.4 创建位置编码层对象

关键的多出来一步在这里。以前拿到词向量，是不是就直接往后传、算结果了？现在不行。拿到词向量以后，还得先把它送进**位置编码层（positional encoding layer）**，加上位置信息，得到结果之后才能往下传。

```python
my_position = PositionalEncoding(d_model, dropout=0.1)
```

这里 `max_len` 不用传，因为类里默认长度就是 60，你不写它就拿默认值。有人问为什么是 60？想改成 6 也无所谓，这个数不影响你现在要做的事。

### 1.5 计算位置编码结果

第五步，把词向量丢进位置编码层：

```python
position_x = my_position(embed_x)
print(position_x.shape)   # torch.Size([2, 4, 512])
```

算位置编码的时候，塞进去的 `x` 就是刚才那个词向量，形状 `(2, 4, 512)`。处理完以后出来的，还是 `(2, 4, 512)`。然后返回：

```python
return position_x
```

在 `main` 里接住它，打印结果，顺便打印形状：

```python
if __name__ == '__main__':
    demo1()                       # 输入层那套测试
    result = demo2()              # 位置编码层测试
    print(result)
    print(result.shape)
```

打出来就是 `(2, 4, 512)`：两个句子、每句四个词、每个词 512 维。也就是说，这个 `(2, 4, 512)` 里既装了**词向量**，又装了**位置编码信息**，它是两者结合之后的最终结果。而这一层再往下，就是把这个 `(2, 4, 512)` 交给编码器（encoder）。

> **结论**：文本嵌入层的作用是把词变成向量、带上一层语义信息；位置编码层的作用是在这个向量上再叠加位置信息。叠加前后**形状完全不变**，变的只是内容。

## 2. 逐层打印：中间到底发生了什么

到这里有人会不服气：`(2, 4, 512)` 进来，`(2, 4, 512)` 出去，那这一层到底干了啥？光看输入输出看不出名堂，那我们就把中间量一个一个打出来。这也是我一直在教的一个笨办法——**哪一步看不懂，就把哪一步打出来**。

### 2.1 词向量与最终结果的对比

先打印一下 `embed_x`：

```python
print(embed_x)          # 内容是一堆小数，看不懂也正常
print(embed_x.shape)    # torch.Size([2, 4, 512])  <- 词向量结果
```

有意思的是打印顺序：`embed_x` 的内容会出现在 `position_x` 的上面，因为词嵌入是前面的步骤，先算先打印。两行形状都是 `(2, 4, 512)`，一个是词向量结果，一个是词向量加位置编码的结果。**形状一样、数值不同**——那就必须把中间过程拆开看。

### 2.2 position：0 到 59 的位置编号

进到位置编码层内部，第一个要看的是 `position`：

```python
position = torch.arange(0, max_len).unsqueeze(1)
print(position)          # 0, 1, 2, ... 一直到 59
print(position.shape)    # torch.Size([60, 1])
```

`position` 从 0 一直走到 59，一共 60 个数。这里要理清一件事：句子明明只有 4 个词，为什么编号有 60 个？因为 60 是**假设的每个句子的最大长度**，底层按最大长度把位置编号预先备好，至于你实际传几个词进来，那是你自己的事——传 4 个就 4 个，但底层处理时最多按 60 个准备。所以编号从 0 开始、到 59 结束，形状 `(60, 1)`。

### 2.3 div_term：为什么是 256 个数

第二个要看的是 `div_term`，形状是 256：

```python
div_term = torch.exp(torch.arange(0, d_model, 2).float() * (-math.log(10000.0) / d_model))
print(div_term.shape)    # torch.Size([256])
```

为什么必须是 256？回头看公式：

$$PE_{(pos, 2i)} = \sin\left(\frac{pos}{10000^{2i/d_{model}}}\right), \qquad PE_{(pos, 2i+1)} = \cos\left(\frac{pos}{10000^{2i/d_{model}}}\right)$$

`div_term` 算的就是 $1 / 10000^{2i/d_{model}}$ 这一坨，$i$ 从 0 取到 255，一共 256 个不同的缩放因子。而 $2i$ 配上偶奇两路——$2 \times 256 = 512$，正好等于 `d_model`。位置编码矩阵的列数要凑够 512，一半给 sin、一半给 cos，所以缩放因子就得是 256 个。

> **易错点**：`div_term` 的长度是 `d_model / 2`，不是 `d_model`。因为 512 列里偶数下标和奇数下标各占 256 列，共用同一组缩放因子。

### 2.4 position 与 div_term 相乘：维度自匹配

接下来是相乘：

```python
pe = position * div_term
print(pe.shape)          # torch.Size([60, 256])
```

等一下——`position` 是 `(60, 1)`，`div_term` 是 `(256,)`，一个二维一个一维，这能乘吗？按矩阵乘法的规矩是乘不了的。但 PyTorch 底层会自动做**维度自匹配（broadcasting）**：一维的 `(256,)` 会被自动补成 `(1, 256)`，于是 `(60, 1)` 与 `(1, 256)` 逐元素相乘，得到 `(60, 256)`。

> **提示**：讲解 PyTorch 的时候我就强调过维度自匹配这件事。遇到"一个一维一个二维乘不了"的情况，别急着怀疑自己算错了，先看底层会不会自动把维度补上——`(60, 1)` 配 `(1, 256)` 出 `(60, 256)`，这是规则允许的。

### 2.5 pe 升维：拼接、赋值、unsqueeze

拿到 `(60, 256)` 的数值以后，要把 sin 和 cos 拼成完整的 512 列：

```python
pe[:, 0::2] = torch.sin(pe)     # 偶数列放 sin
pe[:, 1::2] = torch.cos(pe)     # 奇数列放 cos
print(pe.shape)                 # torch.Size([60, 512])

pe = pe.unsqueeze(0)
print(pe.shape)                 # torch.Size([1, 60, 512])
```

`0::2` 是"从第 0 列开始每隔一列取一个"，`1::2` 是"从第 1 列开始每隔一列取一个"，两路正好把 512 列铺满。最后 `unsqueeze(0)` 在最前面升一维，把 `(60, 512)` 变成 `(1, 60, 512)`——多出来的这一维是给 batch 留的位置。

到这里位置编码就算完了，形状 `(1, 60, 512)`。**这个形状我在写代码的时候就标在注释里了**，不是看结果才知道的。为什么能提前标？因为在写每一步的时候，脑子里清楚这一步的形状是几乘几、维度是几维，直接写上去就行，不用运行。你前期不熟怎么办？多打几次——就像现在这样，一个不熟就打一个，照着自己打出来的形状去推理，推起来就轻松了。练到能凭记忆标形状，玩起来才会有"很轻松"的感觉。

### 2.6 缓冲区：self.pe 从哪来

写完 `pe` 之后执行这一句：

```python
self.register_buffer('pe', pe)
```

然后在 `forward` 里能用 `self.pe`，是因为 `pe` 已经**注册到缓冲区（buffer）**里了。上面代码里我写的是 `self.pe` 吗？不是，我写的就是 `pe`。那为什么下面能直接写 `self.pe`？因为注册缓冲区这个动作，相当于把这个张量挂到了模块上，`self.pe` 就是从缓冲区里把它取出来。**不会随梯度更新的张量，用缓冲区存**，这样它既能跟着模型走（`to(device)` 的时候一起搬），又不参与优化。

### 2.7 相加时的形状对不上：切片解决

真正的相加发生在最后：

```python
x = x + self.pe[:, :x.size(1)]
print(x.shape)      # torch.Size([2, 4, 512])
```

看仔细，`self.pe` 是 `(1, 60, 512)`，而传进来的 `x` 是 `(2, 4, 512)`——`60` 和 `4` 对不上，怎么加？

答案就在那个切片里。`self.pe[:, :x.size(1)]` 一步一步拆：

- 第一个 `:` 是**第一维不变**，`1` 还是 `1`；
- 第二个 `:x.size(1)` 是在**长度为 60 的那一维上动手脚**——`x.size(1)` 就是 `x` 的第 1 维长度，也就是句子长度 `4`；
- `:4` 表示从 0 号索引取到 4 号索引，**包左不包右**，所以是 `0, 1, 2, 3`，一共 4 个元素；
- 第三维 512 不动。

于是 `(1, 60, 512)` 被切成 `(1, 4, 512)`，再和 `(2, 4, 512)` 相加，broadcasting 把第一维的 `1` 扩到 `2`，形状仍然是 `(2, 4, 512)`。

打印出来验证一下：

```python
print(x.shape)                              # torch.Size([2, 4, 512])
print(self.pe[:, :x.size(1)].shape)         # torch.Size([1, 4, 512])
```

一个 `(2, 4, 512)`，一个 `(1, 4, 512)`，相加没问题。

> **结论**：位置编码矩阵是按最大长度 60 预先生成的，但真正用的时候**只取前 `sequence_length` 行**。生成 60 行是我的事，用几行是你的句子长度决定的——你只要前四个，我就从 60 个里挑前四个给你。

### 2.8 数据流全景

把这一整条链路画出来是这样的：

```text
输入索引 (2, 4)
      |
      v
词嵌入层 nn.Embedding(1000, 512)
      |
      v
词向量 embed_x (2, 4, 512) ------------------+
      |                                      |
      v                                      |
位置编码层 PositionalEncoding                |
   position  (60, 1)                         |
   div_term  (256,)                          |
   position * div_term  ->  (60, 256)        |
   sin/cos 填充         ->  (60, 512)        |
   unsqueeze(0)         ->  (1, 60, 512)     |
   切片 [: , :4]        ->  (1, 4, 512)      |
      |                                      |
      +------------------ 相加 <-------------+
      |
      v
最终结果 (2, 4, 512)  = 词向量 + 位置编码
      |
      v
交给编码器
```

读图要点：整条链路里形状只在词嵌入那一步从二维升到三维，位置编码这一层**不改变形状**，它只往同一形状的张量里注入位置信息；真正需要动脑子的地方是 `60` 与 `4` 之间的那次切片取齐。

## 3. 两个坑：缓冲区调用与设备一致

写完测试代码还有两件小事值得记住。

**第一件，缓冲区要在 `forward` 里取。** 上面那段代码里 `self.pe` 之所以能用，前提是构造阶段已经 `register_buffer('pe', pe)`。如果你在构造之后又赋了一个全新的 `self.pe = 别的张量`，缓冲区里的那份和新的这份就是两回事，后面跑起来很容易对不上——所以注册完就别再拿普通属性去覆盖它。

**第二件，位置编码层实例化的时候 `dropout` 也要给。** `PositionalEncoding(d_model, dropout)` 里的 dropout 用的是同一个比例，它跟后面各个子层里的 dropout 是一个思路：训练时随机丢一点，防止过拟合；推理时 `model.eval()` 下自动失效，不需要你手动关。

> **提示**：这是位置编码这一层与输入层在工程上的差别——输入层里就一个 `nn.Embedding`，没有别的可配；位置编码层除了那个 PE 矩阵，还多了一个 dropout。所以实例化的时候参数别少传。

到此为止，输入部分全部收工：文本嵌入层的实现很简单，里面只有一个 `nn.Embedding`，剩下的往里传就完事；位置编码层的作用就是给词向量**加上位置信息**——你的词向量有几个数，我就生成几个数，这样才对得上、才能相加。搞的还是一个 PE 矩阵，由偶数和奇数两路分别算 sin 和 cos。

## 4. 输入处理完之后，接下来去哪

现在回头看整张架构图。输入处理完了，代码走到"往上一层"的入口，`(2, 4, 512)` 就该传给**编码器（encoder）**了。

编码器里要做的东西比输入层多得多：多头注意力（multi-head attention）、前馈全连接（feed forward）、残差连接（residual connection）、规范化层（layer normalization），一个都跑不掉。而且这四个概念是有**层级关系**的，写代码的顺序也照这个顺序来：

1. **组件（component）**——多头注意力、前馈全连接、残差连接、规范化层，都是独立的零件；
2. **子层（sublayer）**——"多头注意力 + 残差 + 规范化"是一个子层，"前馈全连接 + 残差 + 规范化"是第二个子层；
3. **编码器层（encoder layer）**——把两个子层拼在一起；
4. **编码器（encoder）**——把编码器层叠 6 层。

这个顺序千万别搞混，不然后面写代码的时候文件都不知道怎么建。下一段我们就要从最底下的组件开始写。

## 本讲提到的题目

课上留了一道选择题，给了 A、B、C、D 四个选项，问哪个是错的。题干里的关键信息是：词表大小 `vocab = 1000`，代码里出现了一个用 `1001` 作为索引去取词向量的写法。

**答案：选 A。**

**解析**：词表里有 1000 个词，对应到 `nn.Embedding(1000, 512)` 的权重矩阵就是 1000 行，**合法索引是 0 到 999**。索引 `1001` 已经超出了这个范围，属于越界访问，运行时会报索引越界的错误。所以"用 1001 作为索引去查表"这个写法是错的，选 A。

选项 B 里那个多出来的 `s`（`embeddings` 的拼写）不构成错误——按 `embeddings` 理解即可。

> **易错点**：`nn.Embedding(vocab, d_model)` 的可取索引区间是 `[0, vocab - 1]`。词表大小是"有多少个词"，不是"最大索引是多少"，差一（off-by-one）的问题在词表上特别常见。
