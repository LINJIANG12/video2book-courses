# 结巴分词处理繁体中文

先看一句话：**烦恼即是菩提，我暂且不提**。

这句话里的字，你一个个念下来都认识，可它跟前面我们练的那些简体句子长得不太一样——它是繁体。港澳台的文本资料里，繁体字出现得相当多，所以做中文分词迟早要碰它。那结巴碰上繁体字会怎么办？要不要先做繁简转换？要不要另配一套词表？

答案比你想的省事：**不用，直接切就行**。整个过程只多了一个 `lcut`，写完 `lcut` 就结束了。

## 三种模式回顾与本次的落点

分词这个工具，前面我们已经把它的三种切分模式过了一遍：精确模式切词、全模式切词、搜索引擎模式切词。这三种模式管的是「怎么切」，解决的是切分粒度的问题。

这一次要解决的是另一个维度的问题：**切的对象换成了繁体中文，结巴还认不认**。这件事跟前面三种模式并不冲突——你选的仍然是精确模式，只不过句子的字符集换成了繁体。

我们先写出 `demo04` 这个函数，同时把调用也先写好，免得后面忘了调用，跑起来什么都没有。

```python
# 4. 定义函数：演示结巴分词之繁体字
def demo04():
    # 定义、记录要被分词的内容
    content = '烦恼即是菩提，我暂且不提'

    # 使用结巴进行分词
    print(jieba.lcut(content))

demo04()  # 测试结巴繁体字
```

三行就是全部。第一行定义句子，第二行切，第三行打印——这已经是最简单的操作了。

## `lcut` 返回列表：`l` 前缀的含义

注意 `lcut` 里面那个 `l`。它是 `list` 的意思：我想让结巴直接帮我切出来，并且给我一个列表，所以我在 `cut` 前面加一个 `l`。

> **提示**：`jieba.cut()` 返回的是一个生成器，要自己做遍历或封装才能用；`jieba.lcut()` 返回的是列表，拿来就能打印、能索引、能参与后面的流程。两者的切分规则完全一致，差别只在返回值形态。

那什么时候才需要生成器？如果处理的语料很大、词量很多，一次性构造一个完整列表会明显占内存，这时候用 `cut` 返回的生成器，配合 `next` 逐个取、或者用 `for` 逐个遍历，是更省内存的写法。

```python
for word in jieba.cut(content):
    print(word)

print(list(jieba.cut(content)))   # 也可以用 list 再封装回来
```

这三种写法学一种就够了。日常开发里，最顺手的还是 `lcut` 一把出结果。

## 三种模式在 `lcut` 上的调用式

前面讲模式的时候我们是在 `cut` 上演示的，换成 `lcut` 只是把函数名改写，参数一字不动。

| 切分模式 | 调用式 | 关键参数含义 |
| --- | --- | --- |
| 精确模式（默认） | `jieba.lcut(content)` | `cut_all=False`，最常用，默认即此 |
| 全模式 | `jieba.lcut(content, cut_all=True)` | 把成词可能全部切出，速度快、有冗余 |
| 搜索引擎模式 | `jieba.lcut_for_search(content)` | 在精确模式基础上对长词再切，用于检索 |

`cut_all=False` 就是精确模式。要换成全模式，把这个 `False` 改成 `True` 即可；要搜索引擎模式，则换用 `lcut_for_search`。

> **易错点**：搜索引擎模式的函数名是 `lcut_for_search`，不是往 `lcut` 里塞某个参数——它是独立函数。而 `cut_all` 只区分精确与全模式两种情况，写不出「搜索引擎模式」。

## 返回值：一个可用列表

拿上面那句繁体句去跑，你会得到一个列表：逗号之前的部分切出来是「烦恼」「即是」「菩提」这些词，全角逗号自己单独占一个元素，之后接着是「我」「暂且」「不提」。

这一点是可以预期的：标点在分词器眼里不成词，但它不能凭空消失，否则把分词结果拼回原句时，位置和信息就对不上了，所以它老老实实留在结果里当一个 token。

> **结论**：结巴对繁体中文可以直接分词，不需要预先繁简转换，也不需要另配词表——这也正是它在预处理阶段省事的原因。

如果下游只关心词、不关心标点，就在拿到列表之后自己过滤一道，这一步不是结巴的职责：

```python
import jieba

content = '烦恼即是菩提，我暂且不提'
words = jieba.lcut(content)

# 只要中文词，把标点和空白去掉
words = [w for w in words if w.strip() and not all(not ch.isalnum() for ch in w)]
print(words)
```

列表一拿到手，你就能对它做任何事：统计词频、查词表、丢给后面的向量化流程。分词这一步的输出形态是不是列表，直接决定了后面写起来顺不顺，这也是我们一直用 `lcut` 的原因。

## 繁体字分词的意义

一句话能直接切，说明结巴的词表与切分逻辑对繁体是兼容的。这带来两个现实好处。

一是处理港澳台语料时不必先跑一遍繁简转换，少一个环节就少一处信息损耗；二是繁体句子切出来的词仍然是有语义的单位，`烦恼`、`菩提` 这类词没有被拆成单字，后面对它们做词性标注、命名实体识别、向量化，全都能接得上。

不过这里要提醒一句：**能切不等于切得和简体一模一样**。同一个词，简体写法与繁体写法在结巴眼里是两个不同的字符串，落在词典里也是两条不同的记录。所以如果你手上的语料里，「传智教育」既有简体写法又有繁体写法，而你又通过用户自定义词典把简体那个词固化成了一个整体，那么繁体写法并不会自动跟着变成整体——它得在词典里另占一行。

> **提示**：当同一批语料里繁简混排，而某些专业词必须整体切出时，最稳的做法是把该词的繁、简两种写法都在词典里各写一条；如果你的业务只在意语义、不在意字符形态，也可以先用繁简转换统一到简体再做后续处理。两条路都通，选哪条取决于你下游要不要保留原文形态。

## 分词能力在文本预处理中的位置

把这一讲放回整条预处理链路上看，分词是第一个真正动手的环节，它后面还有词性标注、命名实体识别这些动作。而这些后续动作能不能做对，前提就是分词切得准不准。

```text
原始文本（简体 / 繁体 / 港澳台语料）
            |
            v
     jieba 分词（选模式：精确 / 全 / 搜索引擎）
            |
            +--> 常见的通用词汇：结巴自带词典已经处理得不错
            |
            +--> 专业词、生僻词、公司名：结巴会切开，需要外部干预
                        |
                        v
                用户自定义词典（下一讲）
```

读图说明：繁体语料跟简体语料走的是同一条流水线，不需要在入口处加一道转码。真正需要外部干预的位置在下游——当结巴把某个你希望整体保留的词切开了（比如公司名被切成两段），那才是要引入用户自定义词典的场景。

> **结论**：结巴这个分词工具是相当强大的。模式上它给了你精确、全模式、搜索引擎三种粒度选择；字符集上它直接支持繁体中文；剩下的少数特殊情况，它另外给了一条用户自定义词典的路。到目前为止，繁体字这一项是最省事的——一个 `lcut` 就结束了。
