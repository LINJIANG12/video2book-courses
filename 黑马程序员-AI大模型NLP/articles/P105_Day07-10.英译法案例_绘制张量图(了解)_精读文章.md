但"看一眼"不等于走马观花。这张图里藏着整条链路上最容易搞混的东西：哪个轴是英语、哪个轴是法语、为什么行数不是 7 就是 8、为什么列数明明英文只有 4 个词却写成了 10。搞清楚这些，那些绕人的维度转换才算真的过了一遍。

## 图上的两个坐标轴

先看结果图长什么样：纵轴是英语句子，横轴是法语句子，格子的颜色表示两者之间的关联强度。

```text
注意力热力图（示意）：

   横轴 -> 生成的 法 语 词 序 列
   +----+----+----+----+----+----+----+
英 |    |    |    |    |    |    |    |
语 |    | 深 |    |    |    |    |    |
词 |----+----+----+----+----+----+----+
序 |    |    | 深 |    |    |    |    |
列 |----+----+----+----+----+----+----+
   |    |    |    | 深 |    |    |    |
   |----+----+----+----+----+----+----+
   |    |    |    |    | 深 | 浅 |    |
   +----+----+----+----+----+----+----+

   颜色越浅  ->  依赖越深、关联越大
   颜色越深  ->  依赖越弱、关联越小
```

读图说明：竖着的 y 轴是英语句子，横着的 x 轴是生成出来的法语句子；每个格子的颜色深浅表示"生成这个法语词的时候，对那个英语词投入了多少注意力"。**颜色越浅，说明这个英语单词越重要、影响越大**。

看的时候有两个现象值得留意：

- **越往后越重要**——生成越靠后的法语词时，权重往往落在越靠后的英语词上，整体呈现逐级匹配的趋势；
- **一个法语词会同时用到好几个英语词**——不是一对一，而是"主要依赖某一个、顺带依赖它周围几个"，那个颜色最浅的格子就是它最依赖的那个词。

## 绘图函数与模型实例化

函数名叫 `demo_test_attention`。

```python
def demo_test_attention():
    # 1. 获取数据加载器对象
    my_dataloader = get_data_loader()

    # 2.1 实例化编码器模型
    input_size = english_word_n        # 2803
    hidden_size = 256
    my_encoder_rnn = EncoderRNN(input_size, hidden_size).to(device)
    my_encoder_rnn.load_state_dict(
        torch.load(path1, map_location=device, weights_only=True)
    )

    # 2.2 实例化解码器模型
    my_attn_decoder_rnn = AttnDecoderRNN(french_word_n, hidden_size).to(device)
    my_attn_decoder_rnn.load_state_dict(
        torch.load(path2, map_location=device, weights_only=True)
    )
```

第一件事永远是拿数据加载器，跟前面每一段代码一样。

`hidden_size` 就是**隐藏维度**，写 256。这里有个小技巧：如果你只是想看看图、不追求效果，可以把这个 256 调小一点，跑起来更快，也不会影响你对整条链路形状的理解。

编码器这边两个参数就是词表大小和隐藏维度，写的时候可以直接用变量传（`input_size` 接 2803，`hidden_size` 接 256），也可以把 2803 和 256 直接写死。用变量传的好处是这个数只出现一次，改的时候不用满篇找。传完 `.to(device)` 搬到设备上，再把参数 `load_state_dict` 进来。

解码器这边同理：第一个位置接**法语**词表 `french_word_n`，第二个接 `hidden_size`。注意别把英语的 2803 塞进解码器的输出维度——解码器要产出的是法语，它面对的类别数是那 4345 个法语词。

> **易错点**：`2803` 是英语词表、`4345` 是法语词表。编码器进的是英语词表，解码器出的是法语词表，两个数分别是各自那一侧的规模。

## 形状 7×10 的来历

打印结果是 `(7, 10)`。逐个数清楚。

### 行数 7：法语侧的实际长度

生成的法语一共 6 个词。但形状的行数是 **7**，多出来的那一行是**结束标记 `EOS`**——它也在矩阵里占了一行，只是在图上没被专门显示出来。

那再往前推一步：如果连最开头的开始标记 `SOS` 也算进来，是不是就变成 8 了？对。不过这个矩阵里**只有结束标记、没有开始标记**，所以是 7 行。

`7` 这个数不是固定死的，它等于"这次实际生成了几个词再加一个 `EOS`"。生成长度不同的句子，行数就不同。

### 列数 10：英语侧被拉长的长度

`7` 能解释，`10` 就奇怪了：英语句子 `we are both teachers` 一共才 4 个词，加上句末的结束标记是 5 个，再加上开始标记也才 6 个，怎么都凑不到 10。哪来的 10？

> **结论**：为了统一，英文句子不够 10 个词的，一律**补成 10 个**。

所以这个 10 就是前面反复见到的 `MAX_LENGTH = 10`。它跟这句话实际有几个词没关系，是一个恒定值。

把两边的算法合起来看：

```text
英语侧（列，恒为 10）：
  we / are / both / teachers  ->  4 个真实词
  + EOS                       ->  5 个
  + 补零对齐到 MAX_LENGTH=10   -> 10 个（后 5 个是占位）

法语侧（行，随实际生成变化）：
  生成 6 个法语词
  + 第 7 个位置是 EOS
  -> 7 行

  于是：attentions.size() = (7, 10)
```

读图说明：列数 10 是"英语句子被拉长后的固定长度"，行数 7 是"这次实际生成到哪里"。生成第 1 个法语词时算出来的权重是一行 $1 \times 10$，生成第 2 个时又是一行 $1 \times 10$……一共生成 7 行，所以整体是 $7 \times 10$。第 8 个词的权重从哪来？没有第 8 个词了，所以不要。

这也正好解释了上一讲那个 `[:idx + 1]` 切片——**它是这套"假设长度 10、实际长度按 EOS 截断"约定的直接后果**。矩阵开足 $10 \times 10$，实际生成 7 行就返回 7 行。

### 图上索引为什么是 0 到 6

图上的刻度是 0 到 6，不是 1 到 7。索引从 0 开始，7 行就是 0 到 6，对得上。至于"我的英语句子有这么长吗"这个疑问——把句子切一遍就清楚了：`we are both teachers` 是 5 个（含那个句点），加上结束标记是 6 个，加上开始标记是 7 个，索引正好落到 0 到 6。而英文这一侧被统一拉到了 10，所以列方向的索引是 0 到 9。

## 视觉匹配与逐级依赖

对着图上颜色看，结论挺清楚：

- 法语前面几个词，主要跟英语前面几个词相关；
- 生成法语**最后一个词**的时候，它**不依赖英语前面那几个词**，而是明显偏向英语句子的**最后那一段**——顺着一条线下来，这个匹配是相当合理的；
- 有些格子颜色特别浅（比如生成某个法语词时对某一个英语词的那一格），意思是**生成这个词时我更依赖那个英语单词，对后面的英语词依赖没那么高**——有依赖，但没那么高。

> **定义**：颜色越浅，说明影响越大、关联越大。图上横向看是"某一步生成时对整句英语的关注分布"，纵向看是"某个英语词在整段生成的哪些位置被用到"。

这段可视化的官方说明也就两句：图像的纵坐标（y 轴）代表英语词汇，横坐标（x 轴）代表生成的目标语言，也就是法语句子；颜色越浅，说明影响越大、关联越大。

## 案例复盘：注意力机制到底是什么

整个英译法案例到此写完。有两处难：一是代码量比较多，二是里面维度转换特别多。

> **结论**：维度的难点是有解的——**把每个张量的形状打印出来**，你是啥形状、我是啥形状，一个个标到整体流程图上，对着图走一遍流程。这么做会简单很多。

另外要有心理准备：这个案例需要几天时间消化，指望一天写完不太现实。多敲几遍、多理解几遍里面到底在干什么，等真看明白了注意力机制怎么玩，那就是真的懂了。

回头看，讲了这么多，注意力机制就两句话：

1. **把人的注意力机制迁移给计算机**，让计算机也像人一样有侧重点地学习；
2. **注意力权重的计算公式**——Q 和 K 先算匹配分，拿到匹配分就是注意力概率，再拿概率去乘 V。

这套公式我们一共写了三个：前面两个是一般注意力，最后一个"点积并做缩放"的那个，就是**自注意力**（self-attention）。

最后是整个案例的架构定位，还有一处必须点明的小瑕疵：

> **易错点**：我们用的是 Seq2Seq 架构，而在这个架构里，**注意力只加到了解码器上，编码器并没有加注意力**。

正是这个"只在解码器加注意力"的版本，让很多人得到了一个结论：注意力机制确实好用。于是自然有人接着想——既然加在解码器上管用，**能不能也把注意力加到编码器里**？顺着这个思路优化再优化，就到了下一个要学的架构：**Transformer**。
