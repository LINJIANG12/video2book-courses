# 自动模型方式完成命名实体识别：从管道走向 Token 级分类

我们用自动模型（AutoModel）来完成一个命名实体识别（Named Entity Recognition，NER）任务，相对来讲还是比较简单的。跟之前的套路差不多，就是把加载的动作换一个——换成自动模型这条路。这里唯一需要额外留神的地方是：一旦涉及中文，就绕不开编码这一步，其余的都还好。

---

## 1 命名实体识别的任务定位

在 `ToDo` 里新建一条操作，编号六，名字就叫 NER 任务。它的全称是 Named Entity Recognition，中文叫**命名实体识别**。

> **定义**：命名实体识别本质上是一个分类任务，更准确地说，是一个**序列标注任务**（sequence labeling）——给句子里的每一个 token 打一个标签。

它干的事是揪出句子里的实体词：人名是哪些、地名是哪些、公司名是哪些。这件事听起来像是个加分项，实际上它是入口：**实体词识别是句法分析的基础**。你连"这句话里有谁"都分不清楚，后面句法结构怎么往下做？而句法分析又是 NLP 任务的核心。

所以这一节的链条是：

```text
实体词识别  -->  句法分析的基础
句法分析    -->  NLP 任务的核心
结论        -->  命名实体识别是必须打牢的一环
```

一句话读图：NER 不是可有可无的边角任务，它是句法分析的地基，而句法分析坐在 NLP 任务的核心位置。

正因为如此，这一节不能只当作"再写一个 demo"，它的价值在于看清底层怎么做的。

---

## 2 分词器、模型与配置文件的加载

### 2.1 模型名与分词器

先定义变量记录模型名：

```python
model_name = r''
```

引号里放 RoBERTa 模型的名字。第一步动作还是下载分词器：

```python
my_tokenizer = AutoTokenizer.from_pretrained(model_name)
```

> **提示**：分词器（Tokenizer）可以理解成**秘书**。它的职责是"按你这个模型要的数据格式，把文本处理成它能吸收的样子"。一个领导一个习惯，秘书是最了解领导习惯的那个人——所以**每个分词器对应一个模型**，换来换去一定会出问题。

### 2.2 自动模型与 TokenClassification

第二步下载模型，但这次不能随手挑一个：

```python
my_model = AutoModelForTokenClassification.from_pretrained(model_name)
```

选谁？选 `TokenClassification`。为什么是它？因为 NER 的本质是分类任务，`classification` 这个词已经说明了问题——只不过它分的是 **token 级**的类，不是整句一个类。

> **易错点**：文本分类用 `AutoModelForSequenceClassification`，NER 用 `AutoModelForTokenClassification`。一个是给整个句子一个标签，一个是给每个 token 一个标签，选错任务头，形状对不上，后面全错。

### 2.3 配置文件里的标签映射表

自动模型这条路比管道方式多一个动作：加载配置文件。

```python
config = AutoConfig.from_pretrained(model_name)
```

配置文件是谁？就是模型目录下的 `config.json`。打开它看一眼，里面写着 `id2label` 这张表——**把 ID 转成对应的标签**。

这张表的用法很直白：如果我告诉你识别出来的 ID 是 1，你就把它标成 `B-address`；如果我告诉你是 12，那就是 `I-movie`。命名实体识别到底识别哪些类别，答案全在这张表里：address（地址）、book（书名）、company（公司）、game（游戏），等等。

沿着标签往下看，还能看到它用的标注体系：

```text
O          非实体
B-xxx      某类实体的第一个 token（Begin）
I-xxx      某类实体的后续 token（Inside）
```

读图说明：句子里的每一个 token 最终都会落到这三类之一，`B-` 和 `I-` 配对使用才能拼出完整的实体跨度。

后面我们还会用到这张表把数字 ID 翻译回人看得懂的标签——现在只需要记住它从哪来。

## 3 文本张量化与三组字段

### 3.1 编码与二维张量

第四步是数据张量化，也就是把输入文本转换成模型能接受的格式：

```python
inputs = my_tokenizer.encode_plus('我爱北京天安门，天安门上太阳升！',
                                  return_tensors='pt')
```

参数不用写那么多，但 `return_tensors='pt'` 这个一定要有。

> **结论**：写了 `return_tensors='pt'`，返回的直接是二维张量；不写，返回的是一维列表，后面还得自己手动封装一遍。那还不如直接写。

### 3.2 三组字段的含义

跑起来打印 `inputs`，返回的是三组字段。

- `input_ids`：文本的序列，也就是把每个字照着模型的词汇表翻译成对应的索引。词汇表是从 0 开始数的，所以这一步相当于在"行号"上减 1。
- `token_type_ids`：分段的标记。整句话是一个句子，所以这里全是 0。如果输入是句子对，第二句就会用 1 标出来。
- `attention_mask`：字面翻译是注意力掩码，但在这里它的实际含义是**是否是真实数据**。1 代表真实，0 代表填充（padding）。

顺便注意一个细节：句子里我们硬打的那个空格会被忽略掉。首尾也不在白名单之外——`101` 开头，`102` 结尾，这两个是 BERT 家族拿来包裹句子的特殊标记。

```text
[CLS]  我  爱  北  京  天  安  门  ，  天  安  门  上  太  阳  升  ！  [SEP]
 101   ...                                                        102
```

读图说明：`[CLS]`（101）负责提供句子级表示，`[SEP]`（102）标记句子结束，中间才是真正的文本内容。

## 4 前向计算与输出对象

第五步把数据喂给模型、拿结果。先切到推理模式：

```python
my_model.eval()

logits = my_model(inputs['input_ids']).logits
```

只把 `input_ids` 传过去就够了——模型只需要你文本对应的序号。取出来的属性叫 `.logits`。

> **提示**：模型返回的完整结果其实应该叫 `output`，它是一个 `TokenClassifierOutput` 对象，里面装着 `loss`、`logits` 等一堆字段。我们只需要 `logits`，所以顺手取出来就行。

打印 `logits.shape`，得到：

```text
torch.Size([1, 18, 32])
```

三个维度的含义必须掰清楚：

- 第一个 `1`：一个句子，也就是一批里只有一条数据；
- 第二个 `18`：句子的长度，也就是 token 数；
- 第三个 `32`：类别数。

为什么是 18？把 `我爱北京天安门，天安门上太阳升！` 数字数——不算空格是 16 个字符，加上末位的标点就是 17，再加上首尾的 `[CLS]` 和 `[SEP]`，正好 18。

为什么是 32？回头翻 `config.json` 里的标签表：从 0 到 31，一共 32 个类别。所以模型对**每一个字**都会给出一个 32 维的分数向量，表示它属于这 32 个标签各自的得分。

把这层对应关系画出来：

```text
输入 token :  [CLS]  我   爱   北   京  ...  [SEP]
              |     |    |    |    |         |
logits     :  32维  32维 32维 32维 32维 ...  32维
              \___________________________/
                    形状 = [1, 18, 32]
```

读图说明：张量的第二维跟着 token 走，第三维跟着标签表走。`[CLS]` 位置也有自己的 32 个分数，它代表的是"这个特殊符号该被标成什么"，一般都会被过滤掉。

> **易错点**：`logits` 里的数**不是概率**，是未归一化的分数。想拿"概率"得自己走 softmax；但做预测只看谁大谁小，直接取 argmax 就够，不必多此一举。

## 5 结果处理：从 ID 回到标签

光有数字张量没用，任何人翻开 `[[...32个数...], ...]` 都是一脸懵。所以第六、第七步做结果处理与显示。

### 5.1 ID 转回 token

先做可视化 6.1：把输入 ID 转回 token 形式。

```python
input_tokens = my_tokenizer.convert_ids_to_tokens(inputs['input_ids'][0])
```

为什么需要这一步？如果直接打印 `logits[0][0]`，你会拿到 32 个分数；再想把这些分数映射成概率、找最大值、再回头匹配字符——太麻烦了，而且没必要。

`convert_ids_to_tokens` 一次就把 18 个 ID 全翻译回来：

```text
['[CLS]', '我', '爱', '北', '京', '天', '安', '门', '，',
 '天', '安', '门', '上', '太', '阳', '升', '！', '[SEP]']
```

这正是我们原始输入的那串字符。分词器和模型是一对一绑定的，它翻译出来的 token 和模型内部的词表完全对齐——这就是为什么第一步必须先把分词器配对。

### 5.2 逐 token 取最大概率标签

6.2 用 `zip` 把 token 和它的预测标签概率分布组合在一起：

```python
outputs = []
for token, value in zip(input_tokens, logits[0]):
    if token in my_tokenizer.all_special_tokens:
        continue
    index = torch.argmax(value).item()
    outputs.append((token, config.id2label[index]))
```

逐段拆开看：

- `logits[0]`：`logits` 的形状是 `[1, 18, 32]`，取下标的 0 就把批次那一维去掉，得到 `[18, 32]`——18 个 token，每个配一个 32 维分布。
- `zip(input_tokens, logits[0])`：每轮循环拿到一个 token 和它对应的那个 32 维向量。
- 过滤特殊字符：`token in my_tokenizer.all_special_tokens` 命中就 `continue`。凡是特殊 token 一律跳过，走到这一行之后还在处理的，都是真文本。
- `torch.argmax(value).item()`：在那个 32 维分布里找最大值的下标，`.item()` 把单元素张量取成 Python 整数。这样 18 个 token 就各自得到了自己的标签 ID。
- `config.id2label[index]`：拿着 ID 去配置文件那张映射表里查字符串标签。

> **提示**：`config.id2label` 这个键名值得记住。它是标准的反查表，`id2label[2]` 就会告诉你 2 对应的是 `I-address`。同一份配置里还有 `hidden_size` 之类的字段，需要什么从这里取什么。

中间先打印一次 `token_index` 能把过程看清：`我` 是 0，`爱` 是 0，`北京天安门` 得到 1、2、2。0 对应 `O`，1 对应 `B-address`，2 对应 `I-address`。到这里就和之前用管道方式做出来的东西完全对上了——**管道的底层就是这么做的**。

数字当然不能直接给人看。别人问你 `天安门` 是啥，你回答"2 2"，那谁都听不懂。所以才有 `id2label` 这一跳。

### 5.3 最终输出

第七步打印最终结果，格式是列表套元组：

```text
[('我', 'O'), ('爱', 'O'), ('北京', 'B-address'), ('京', 'I-address'),
 ('天', 'I-address'), ('安', 'I-address'), ('门', 'I-address'), ...]
```

这就是最终形态。当时我举例时写过 `local`、`location` 之类的，那只是随手示范格式，真正的内容必须以 `config.json` 里那 32 个标签为准——不同模型这张表不一样，别把示例当结论。

> **结论**：自动模型的输出形态是「token → 标签」的配对列表，和管道方式的输出在外观上是一致的。看懂这一层，你就知道管道不是魔法，它只是把这一整套动作封进了一个函数。

## 6 NER 任务划分与两类方式的对比

到这里，关于管道的部分以及自动模型这条路就算做完了。回头看整条主线，我们在管道方式旁边又多出了一个 `AutoModel`。

管道方式怎么做？三步，不用代码也能说清：

1. `pipeline` 里丢任务、丢模型，拿到一个管道对象；
2. 把数据往里一丢——截断、补齐、张量转换全都不用你管；
3. 打印结果。

真的就三行代码。

自动模型方式怎么做？把每一步摊开：

1. 加载分词器 `my_tokenizer`（秘书，按模型的习惯处理文本）；
2. 加载模型 `my_model`（对应任务的 `AutoModelForXxx`）；
3. 用分词器把文本转成张量，`return_tensors='pt'`；
4. 把张量喂给模型，拿到结果；
5. 输出——如果拿到的是形状或分数而不是可直接展示的内容，还得自己动手找最大值、做转换。

```text
管道方式                              自动模型方式
--------                              ------------
pipeline(任务, 模型)                   1. AutoTokenizer 加载分词器
      |                                2. AutoModelForXxx 加载模型
      v                                3. encode_plus 文本转张量
数据直接丢进去                          4. model(...) 前向获取结果
      |                                5. 手动处理并输出
      v                                      |
   结果打印                                   v
  (3 行)                                结果打印 (5 步)
```

读图说明：左边把细节全部封进了 `pipeline`，右边把细节摊在你面前。右边多出来的第 5 步，正是自动模型"更透明但更啰嗦"的代价。

即将要讲的具体模型方式，思路跟自动模型一模一样：加载分词、加载模型、文本张量、输入获取结果、第五步打印。唯一变的是 API 的名字，其余全同。

### 6.1 任务头与 API 对照

以文本分类任务为例，自动模型这条路要用到的 API 各管什么，值得一次记住：

| 类名 | 任务类型 | 用途 |
| --- | --- | --- |
| `AutoTokenizer` | 全任务通用 | 分词器，文本 ←→ ID |
| `AutoModel` | 全任务通用 | 只出隐层表示，不带任务头 |
| `AutoModelForSequenceClassification` | 文本分类 | 整句一个标签 |
| `AutoModelForMaskedLM` | 掩码语言模型 | 完形填空 |
| `AutoModelForQuestionAnswering` | 抽取式问答 | 给一段话、给一个问题，去上下文里找答案 |
| `AutoModelForSequenceToSequenceLM` | 序列到序列 | 文本理解与生成（如翻译） |
| `AutoModelForTokenClassification` | Token 级分类 | 命名实体识别 |

> **结论**：`TokenClassification` 就是 NER 在 Transformers 里的名字。名字里带 `For` 的部分是任务头，选任务头等于选任务；选错了，输出形状和标签表都对不上。

至此，自动模型这条路走通了：先拿分词器，再拿模型，文本转张量，模型处理数据获取结果，最后打印结果。剩下的只是往这个骨架里填代码。
