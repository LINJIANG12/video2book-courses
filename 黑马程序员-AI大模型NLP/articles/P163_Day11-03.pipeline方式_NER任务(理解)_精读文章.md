# pipeline 方式做命名实体识别：BIO 标注与结果解读

六个 NLP 任务我们已经写完五个，就剩最后一个没用上了。之前做文本分类的时候，倒数第二个模型是 RoBERTa-base，一直没让它干活——现在轮到它了。这个任务叫 NER，也就是命名实体识别。

## 1 NER 在做什么

NER 的全称是命名实体识别（Named Entity Recognition，NER），它是 NLP 里的一个基础任务，主要用来识别文本中的人名、地名、组织机构名以及其他实体。

举个例子，`王小明在办公室` 这句话里，模型要告诉我们：哪个片段是实体、是什么类型的实体。产出形式就是给每个字打上一个标记：

- `O`：不是实体。比如 `在` 这个字，它就是 `O`。
- `B`：实体的开始（Begin）。
- `I`：实体的内部（Inside）。

`王小明` 会被标成 `B-PER I-PER I-PER`。这里的 `PER` 就是 person，人名；`LOC` 是 location，地名；再往下还有组织机构名，以及 `MISC` 这一类其他实体。

> **定义**：同一实体内部的字，第一个打 `B`，其余全部打 `I`。所以一个实体就是“一个 B 加一串 I”的连续区间；遇到下一个 `B`，或者遇到 `O`，这一段就断了。

把 `王小明` 的标记按顺序读出来，`B` 开头、后面全跟 `I`，中间没有断开，三个字属于同一组，拼起来就是 `王小明`。这就是 BIO 标注方案的全部逻辑。

> **易错点**：`B` 和 `I` 本身不携带实体类型，类型写在后面的后缀上（`PER`／`LOC`／`ORG`／`MISC`）。判断“是不是同一组”只看 `B` 与 `I` 的断点，不看类型后缀。

## 2 pipeline 的三步套路

任务六叫命名实体识别，做的时候还是老三步，这一步一步已经重复六遍了。

第一步，创建 pipeline 对象，只要两个参数：任务名和模型路径。任务名写 `"ner"`，模型路径就用之前一直没用上的那一个。

```python
from transformers import pipeline

my_model = pipeline("ner", model=r"模型路径")
```

第二步，把文本交给模型，拿回预测结果：

```python
output = my_model("我叫浩哥，我是一名教师")
```

第三步，打印结果：

```python
print(output)
```

就这三步。管道方式里我们从头到尾没有做过任何“把文本转成张量”的操作，因为数据丢进 pipeline 之后，底层会替我们把它转好、喂给模型、再把输出整理成可读形式。这也是它省事的地方。

> **提示**：`pipeline` 的第一个参数是任务名，第二个参数才是模型。任务名写成 `"ner"` 之后，pipeline 就知道该按哪种任务的方式去组织输入和输出。模型路径必须指向与该任务匹配的模型（这里用 `RoBERTa-base` 这个路径）；用了别的任务的模型，行为不会是你想要的。

## 3 两个例子的输出对比

### 3.1 教师身份没被识别出来

第一个例子是 `我叫浩哥，我是一名教师`。跑完之后，结果里能抽出来的实体是“教师”，它对应的标注是一段 `BI`。

有意思的地方在这里：名字（浩哥）没有被抽出来，`我`、`是`、`一`、`名` 这些字也没有被抽出来。原因是这类词对模型来说比较小众——训练数据里没见过、或者出现得很少的用法，模型就不会把它认成实体。

### 3.2 换一段更常规的文本

把文本换成人名地名更典型的句子：`我爱北京天安门`。输出立刻就多了很多。

这段输出里出现了 `B I I I I I` 这样的连续标记，从 `B` 打头、后面一路 `I`，说明它是一整组——抽出来的实体是“北京天安门”，类型是地址。这正是我们前面讲的人名、地名之类的实体。

再做第三个例子：把文本换成 `我爱武汉黄鹤楼` 这样的句子，输出里就轮到“武汉黄鹤楼”“黄鹤楼”这一串被抽出来，而且是按新的实体分组走的。同一个模型，换一段文本，抽出来的实体数量和分组都跟着变。

两个例子的输出情况：

| 输入文本 | 抽出的实体片段 | 类型档位 |
| --- | --- | --- |
| 我叫浩哥，我是一名教师 | 教师 | 人名/职业类实体（`PER` 档） |
| 我爱北京天安门 | 北京天安门 | 地址实体（`address`） |

同一套三步流程，换掉文本就换了一种抽取结果。到这里，NER 会做、怎么用，就到手了。

## 4 输出的数据形状

pipeline 返回的是一个“一条实体一个字典”的列表，每个字典里带着抽出来的词、它属于哪一组、以及它在输入里的位置下标。真实结构大致长这样：

```python
[
    {"entity": "B-xxx", "score": 0.99, "index": 1, "word": "北", "start": 1, "end": 2},
    {"entity": "I-xxx", "score": 0.99, "index": 2, "word": "京", "start": 2, "end": 3},
    # ... 同组的后续 token
]
```

读的时候按组读，不要一条一条孤立地看：

- `entity`：这一条 token 的 BIO 标记，带类型后缀。`B-` 开头就是这一组的第一个 token。
- `word`：这一条覆盖到的原文片段。
- `index`／`start`／`end`：它在分词结果里的位置与区间下标，用来把结果对回原文。
- `score`：模型对这一条标记的置信度。

```text
输入文本
   |
   v
pipeline 内部：分词 -> 转张量 -> 模型前向 -> 标记解码
   |
   v
逐 token 的 BIO 标记序列
   B-PER   I-PER   I-PER   O
     |       |       |      |
     +-------+-------+      +--> 非实体，丢弃
             |
             v
     同一组（B 开头 + 后续 I）拼回原词 = 王小明
```

读图说明：pipeline 对外只暴露“文本进、实体列表出”，中间的分词、张量转换、标记解码全都封在里面；我们能看到的产物就是带 BIO 标记的逐 token 结果。

> **提示**：`B` 标记既代表“新实体开始”，也隐含“上一个实体到此为止”。所以拿到结果先扫 `B`，每一个 `B` 就是一次实体切分的边界。

## 5 六个任务收口

到目前为止，六个 NLP 任务全部写完了。回头看一遍，管道方式的套路惊人地统一：第一步生成（加载）模型，第二步把数据丢给它，第三步打印结果。

| 任务名 | 对应任务 |
| --- | --- |
| 情感分析 | 情感分类 |
| 特征抽取 | 特征提取 |
| 完形填空 | 掩码语言建模 |
| 阅读理解／问答 | 问答 |
| 文本摘要 | 摘要生成 |
| NER | 命名实体识别 |

以文本分类为例，管道方式的写法就是：导包，第一步获取一个 pipeline 对象（该下载就下载），第二步把文本送给模型拿回数据，完事。

> **结论**：管道方式的价值是“简单、高效地把各种自然语言任务跑起来”，它把分词、张量封装、输出整理这些活全包了。代价是中间的细节你控制不了，想微调、想改句子长度都插不上手。

除了管道方式，Transformers 还有两种写法：自动模型方式和具体模型方式。接下来我们就换成这两种方式，把同样的六个任务再做一遍——到时候你会发现，管道方式帮我们省掉的那些活，会一件一件自己写出来。

## 本讲提到的题目

题目（单选）：管道方式（pipeline）的作用是什么？

- A. 提供一种简单高效的方式去执行各种自然语言处理任务
- B. 用于自定义模型的训练
- C. 用于特定模型的训练

答案：A。

解析：管道方式把分词、输入封装与输出整理都放在底层完成，我们只交代“任务名 + 模型路径”，把文本丢进去就能拿到结果，因此它解决的是“简单高效地跑各种 NLP 任务”。自定义模型训练、特定模型训练属于另一条路线，不是管道方式承担的事（见第 2 节的三步流程与第 5 节的任务名单）。
