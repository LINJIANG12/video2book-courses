## 1. Web应用属性与工程框架

> **一句话主旨**：界定 WebApp 区别于传统软件的核心属性，并给出分层工程框架与增量式过程模型。

### 1.1 核心属性

* **Web 应用（Web-based Application，WebApp）**
    * 教材首次作为独立主题单列，因其属性会一路渗透到后续的分析、设计、测试。
    * > 来源: P21

* **强网络依赖**
    * 全部能力建立在与服务器的连接之上，「断网即失效」是天然风险。
    * 网络延迟、带宽、链路质量直接转化为用户体验。
    * > 来源: P21

* **浏览器差异与外观敏感**
    * 运行在浏览器中，不同浏览器渲染不一致，同一布局可能错位，必须照顾浏览器兼容性。
    * 视觉呈现本身就是功能的一部分，美观度是硬要求。
    * > 来源: P21

* **本地存储少、性能敏感**
    * 本地存储有限，大量内容要从服务器取回，「快」是硬指标。
    * 性能不是优化项，而是用户留存的前提。
    * > 来源: P21

* **极短的迭代周期**
    * 常见工期「三周已算长，最好一周做完」，无法承受瀑布式冗长节奏。
    * > 来源: P21

* **用户未知、交互性强**
    * 上网后不知道谁在用，行为不可预测，交互必须极其周到并容忍异常操作。
    * 与传统内部系统（用户固定、可培训、可监控）形成最本质的区别。
    * > 来源: P21

* **持续演化与无缝更新**
    * 迭代以周计甚至更短，极端情况无「发版日」，后台持续部署、前端无感切换。
    * > 来源: P21

* **服务端存储与安全**
    * 数据托管在服务器数据库而非用户本机，安全（Security）成为头等大事。
    * 直接决定人员构成：除编码强的人外，还须有一批真正懂安全的人。
    * > 来源: P21

* **并发与不可预测负载**
    * 并发性（Concurrency）：可能产生大规模并发，须有强大并发处理能力。
    * 不可预测负载（Unpredictable load）：负载呈季节性、脉冲式波动，不同小时、不同天压力不同。
    * > 来源: P21

* **高可用性**
    * 公众默认挂网系统应 `7×24×365` 在线，宕机时间应极少，背后需强大维护团队。
    * > 来源: P21

* **奥运抢票崩溃案例**
    * 引入的抢票软件并发能力约每秒 `5` 个，开放瞬间即被挤爆。
    * 根因是严重低估负载规模；按小人口量级设计容量，在真实访问洪流下必然失效。
    * > 来源: P21

### 1.2 层次化工程框架

* **Web 工程的 layered technology（层次化技术）**，自上而下四层。
* **质量焦点（Quality Focus）**
    * 最底层，永远以质量为中心；再匆忙也不能松质量管控。
    * > 来源: P21
* **过程模型（Process Model）**
    * 通常选敏捷型（agile），核心精神是「快」。
    * > 来源: P21
* **方法（Methods）**
    * 仍是 communication、requirements、requirements analysis、design、testing，一样不少，仅为「快」做裁剪加速。
    * > 来源: P21
* **工具（Tools）**
    * 针对性更强，典型如 HTML 等 Web 专用工具链。
    * > 来源: P21

### 1.3 增量式过程模型

* **渐增式交付（incremental delivery）**
    * 由「为了快」与「持续演化（continuous evolution）」两个驱动力决定。
    * 绝不能一步到位；变更频繁、时间线极短（short timeline）。
    * > 来源: P21
* **过程形态**
    * 沟通（Communication）→ 需求分析（Requirements Analysis，轻量、场景驱动）→ 设计（Design）→ 构建（Construction）+ 测试（Testing）→ 产出增量（increment）→ 回到沟通做下一个增量。
    * 每圈迭代输出一个 increment。
    * > 来源: P21
* **重构（refactoring）**
    * 在构建阶段同时进行，不断优化内部结构、追加新功能。
    * > 易错点：重构是「大坑」，动手前须想清楚、想周全，不能盲目下手。
    * > 来源: P21

### 1.4 澄清清单与分类

* **动手前七问**
    1. 重要性/内容敏感度：主页多重要、内容多敏感（国防部、全国高校公开访问、课程内部自娱，敏感度天差地别）。
    2. 页面布局套路（page layout）：顶部横排 Menu + 下方内容，还是一横栏加一竖栏；竖栏放左或放右。
    3. 媒介选择：纯文字，还是视频、音频、Flash 等。
    4. 用户目标与耐心：访问想干什么、最多愿意几步操作完成。
    5. 目标用户画像：老人、大学老师、幼儿园小朋友，风格各不相同。
    6. 复杂度与导航：内容多则做 Search 或导航图（navigation map）；注册表单字段越多越易流失用户。
    7. 无障碍与可访问性（accessibility）：是否照顾残疾人，搜索要多强大。
    * > 来源: P21
* **WebApp 分类**
    * 教材列约十种类型，含信息型（informational）、可定制型（customizable）、事务型（transaction-oriented）、门户类（portal）、交互类（interaction）等。
    * 归类练习：支付宝归属何类并讲理由；自负责模块是否具 WebApp 特征；从十类中挑两种举著名网站说明归类。
    * 归类目的：先能准确归类，才知道该用哪套工程手法应对。
    * > 来源: P21

## 2. Web项目启动、规划与团队组织

> **一句话主旨**：讲清 Web 项目从 formulation 到计划、团队角色与外包/自制的管理要点。

### 2.1 启动与规划

* **启动（initiating）**
    * 项目第一步。
    * > 来源: P22
* **formulation（无贴切中文对应）**
    * 意为「先大概规划一下」，做到拿到一个「大致的需求」为止。
    * 由应征者提问、与需求方沟通，直至需求初定；提问的先后顺序本身就是能力。
    * > 来源: P22
* **三问（必须覆盖）**
    1. 用户为什么要做这件事（动机/business need）。
    2. 他想要做成哪些事（目标与功能）。
    3. 做好了以后谁来用（最终用户）。
    * > 来源: P22
* **两类目标（从回答中抽取）**
    * 信息目标（information goals）：网站要提供哪些内容、数据，以什么形式展现（数据侧）。
    * 义务/功能目标（obligative goals）：有哪些任务可通过网站完成（功能侧）。
    * > 来源: P22
* **少问「给谁用」的反面教材**
    * 单用户假设导致系统只支持一位用户，后期改多用户时设计极难改。
    * 结论：主要功能（major features and functions）、目标用户、使用范围，必须在 formulation 阶段用一句话对齐。
    * > 易错点：双方各自觉得「显然」却不点破，是返工起点的常见根源。
    * > 来源: P22

### 2.2 用户类别与需求收集

* **用户类别（user categories）**
    * 对 Web 应用比对传统软件重要得多，是 Web 项目的命门。
    * 每类用户须写详细描述：背景（background，教育程度、识字与否）、习惯（年龄段、熟悉的网络环境）、使用场合与情境、特别喜欢与特别讨厌什么。
    * > 来源: P22
* **风格匹配人群**
    * 面向幼儿园用户应是花花绿绿、文字极少、动画图片多、可点戳；同一风格搬到银行网站则荒谬。
    * > 来源: P22
* **沟通手段**
    * 开会面对面、邮件（email）、调查问卷（survey）。
    * 全新构想须靠问卷采集足够数据，看清用户心中该 service 应有的样子。
    * > 来源: P22
* **沟通产出**
    * 场景构建（scenario-building）→ 抽取内容对象（content objects）与操作（operations）→ 得到用例（use cases）。
    * > 来源: P22

### 2.3 项目计划对照

* 教材对照三类项目：传统项目（Traditional Projects）、小型 Web 应用（Small e-Projects）、大型复杂 Web 应用（Major e-Projects）。

| 对比维度 | 传统项目 | 小型 Web 应用 | 大型复杂 Web 应用 |
| :--- | :--- | :--- | :--- |
| 流程严格度 | 严格、按部就班 | 周期极短，一切求快 | 接近传统，同样严格按部就班 |
| 需求收集 | 多轮会议、详尽规格说明书 | 简要描述性概述（descriptive overview） | 接近传统 |
| 客户反馈 | 面向封闭固定人群，可针对性获取 | 用户为全球网民，须自动获取或公开问卷 | 唯一显著差异：反馈须自动化/公开化 |
| 质量与风险 | 完备质量监控 | 速度与质量间权衡，重点 risk control | 接近传统 |

* **大型复杂 Web 应用的唯一显著差异**
    * 差异在客户反馈（customer feedback）：传统项目面向封闭固定人群可针对性获取；Web 应用用户是全世界网民，须设计自动获取反馈机制或公开问卷。
    * > 来源: P22
* **小型轻量 Web 应用的计划要点**
    * 周期极短，各项工作都求快。
    * 需求只需简要描述性概述，不必厚重多轮会议与详尽规格说明书。
    * 重点在风险控制（risk control）：团队须对所用技术非常熟练，且每天跟踪进度（如仅 7 天工期，绝不能花 2 天准备后放任 5 天）。
    * 质量权衡：既强调速度又不能完全放弃质量，做不到极完备的质量监控。
    * > 来源: P22

### 2.4 团队角色构成

* 团队不止开发组，还包括开发及后续运营中紧密协作的利益相关者（Stakeholders）。

| 角色 | 英文 | 职责 |
| :--- | :--- | :--- |
| 管理与运营人员 | Administrator / Admin | 系统日常管理与配置 |
| 技术支持团队 | Support Team | 上线后响应、排查故障与数据异常（通常与初始开发团队分开） |
| 内容提供与维护者 | Content Developer / Provider | 提供、审核、发布内容；明确哪些来源信息可被接收 |
| 内容发布者 | Web Publisher | 后台把授权内容发布到正确位置（需稍懂技术） |
| 开发工程师 | Web Engineers | 核心开发力量 |
| 业务领域专家 | Business Domain Experts | 掌握业务规矩与流程 |
| 技术支持 | Support | 系统坏、不好用时有人响应 |
| 站点管理员 | Webmaster / Administrator | 系统总管（常从用户中找，而非开发方自己人） |

* **业务领域专家（Business Domain Experts）**
    * 最容易被忽视却最关键，与赚钱/市场无关。
    * 计算机学院网站：办公室主任须入队——他清楚办公流程、各部门职责、内容边界。
    * 选课网站（含成绩管理、退学警告）：教务处长、学籍管理处长（或其代表）为 domain expert，政策与规矩须先搞清。
    * > 来源: P22

### 2.5 外包与自制

* **外包（Outsourcing）沟通结构**
    * 核心内容封在承包商（Outsourcing Vendor）内部，改动或讨论须经联络员（Liaison）机制收集意见再传入。
    * > 来源: P22
* **自制（In-house）沟通结构**
    * 所有角色（含外部利益相关者代表）直接坐在同一张桌上讨论，对大家全透明。
    * > 来源: P22
* **外包前甲方必须自做的六项功课**
    1. 自行收集需求（gather requirements），弄明白到底要做什么。
    2. 有粗略设计（rough design），大模样得知道。
    3. 有进度表（schedule），谈条件谈价钱才不离谱。
    4. 定义增量（increments）边界，每次交到什么程度先定好。
    5. 划清责任，自家人负责哪些、外包商负责哪些。
    6. 定义联络员机制。
    * > 来源: P22
* **选外包商与管控**
    * 多找几家，别盯死一家；考察报价可靠性、以往声誉、大项目经验。
    * 确认把事包出后你对 project 的掌控程度与管理方式。
    * 外包商一般不容你插手细致进度，但范围（scope）与大体进度必须管。
    * > 来源: P22
* **自制（In-house）要点**
    * 知道 scope、哪些地方最易频繁改变、有什么限制条件；若做 incremental，定义每个 increment。
    * 风险分析（risk analysis）最重要；有宏观估算（estimation）；定义任务集（task set）。
    * 控制进度常见做法：数用例（count use cases），看走完多少即知完成百分比。
    * 最后有变更管理（change management）。
    * 与传统开发唯一明显区别就是「快一点」。
    * > 来源: P22

### 2.6 最佳实践与最坏实践

* **最佳实践（Best Practices）**
    1. 先花时间搞清楚业务需求与产品目标，大方向的时间不能省。
    2. 采用场景驱动（scenario-based）方法，做一系列 user scenarios / use cases 再据此开发。
    3. 仍要有轻量级计划（plan），不能完全没计划直接动手。
    4. 动手前做一点建模（modeling），为长期维护留文档与模型（ZOJ 例：2001 投用、2008 上 2.0 版，团队早已换人）。
    5. 把控内容、模型整体设计的一致性与质量（consistency、quality）。
    6. 靠重用来提速（专注某领域沉淀共性构件，越做越快）——快的根本在重用，不在加班。
    7. 上线前充分自测，绝不能把测试留给用户。
    * > 来源: P21
* **最坏实践（Worst Practices）**
    1. 「有伟大想法就开干」——先想清钱在哪、是否有人用、能否赚钱再开始。
    2. 「需求总在变，所以不用搞太清楚」——会带来更多不必要的变更（unnecessary changes）。
    3. 「传统软件高手直接能做 Web」——教材认为不经新培训不太可能（讲师对此存疑）。
    4. 官僚式管理轻型项目——开发小型轻量 Web 应用时领导应靠边，以快为准。
    5. 「testing why bother」——内部测试做不好就交给用户测，可能是大悲剧。
    * > 来源: P22

## 3. Web需求分析建模

> **一句话主旨**：把「快」与用户分层、用例、五维建模拧在一起，形成轻量但完整的分析骨架。

### 3.1 用户分层

* **轻量化的分析模型**
    * Web 应用的分析模型不必像传统项目那样严肃、正式、严谨，「有就可以」。
    * 骨架一致：formulation（快速弄清要做什么）→ requirements gathering（所有人坐到一起对齐目标）→ 给出 analysis model。
    * > 来源: P23
* **formulation 的目标与新增物**
    * 主要目标仍是 goals（大目标，为什么做）与 objectives（具体目标，做成哪些事）。
    * Web 额外必须做用户分类（categories of users），并画一张用户层级（user hierarchy）图。
    * > 来源: P23
* **用户层级图示例（SafeHome）**
    * 顶层为「网站用户」，分三类：访客（guest，权限最低）、注册用户（registered user）、客服（customer service）。
    * 注册用户可再分新客户（new customer）与老用户（old user）——服务要做细致才分，界面与权限相同则不必分。
    * 划分得干不干净、界限清不清楚，直接决定后续开发顺畅度。
    * > 来源: P23

### 3.2 use case 与模块划分三原则

* **用例（use cases）的核心地位**
    * 每一类 user 都要设计一套对应 use case；后面大量工作都依赖它。
    * 写需求：至少四大类分析模型都从 use case 提取信息。
    * 做设计：照着它设计。
    * 做测试：黑盒测试就是一个 use case 一个 use case 地走。
    * > 来源: P23
* **进度度量：数用例（count use cases）**
    * 走完数/总数即完成百分比（如 100 个走完 60 个为 60%）。
    * 不绝对准确（简单注册与复杂购买差别大），但总体可用；「完成」指测过没问题、好用。
    * > 来源: P23
* **用例示例（new customer）**
    * 登录（login）、查看商品描述性内容、建立/保存配置（configuration）、召回已保存配置（recall saved configuration）、定制（customize SafeHome）、购买配置（purchase configuration）。
    * 画法：复杂 actor 的动作可塞进包（package），介绍时再打开看细节。
    * > 来源: P23
* **划分模块三原则**
    * 可理解（comprehensible）：图不能太乱太复杂，命名不含糊。
    * 高内聚（cohesive）与松耦合（loosely coupled）：包内目标集中，包与包之间关系松散。
    * 层次浅（hierarchically shallow）：层次太深则用户点太多链接、等得太久，测试也痛苦。
    * > 来源: P23

### 3.3 五维分析模型

* 在 use case 基础上建 analysis models，大致分五个方面：内容（Content）、交互（Interaction）、功能（Functional）、配置（Configuration）、导航（Navigation）。

* **内容模型（Content Model）**
    * 确定什么东西作为系统的 class 或 object 存在，从 use case 抽取并理清关系（relationship）。
    * 除 ER 图（ER diagram）外，用数据树（data tree）：类似结构体定义，如定义 struct `component`，白框为简单类型（`part number` 数字、`part name` 字符串、`part time` 整型或字符串、`Price` 数字），黑底如 `description` 为真正 data object。
    * 复杂系统可写词法分析器（parser）把 use case 整体过一遍抽名词，滤掉只需简单数字/字符串的，剩下设计为 data objects。
    * > 来源: P23
* **交互模型（Interaction Model）的四要素**
    * 用例（use case）：必备。
    * 时序图（sequence diagrams）：随时间从上往下，几个 actors 之间动作由谁做、产生什么、如何往下走。
    * 状态图（state diagrams）：系统在状态间转换；对 WebApp 即页面间跳转。
    * 用户界面原型（User Interface prototype）：最直观，交互长什么样一目了然。
    * > 来源: P23
* **功能模型（Functional Model）**
    * 分两层：用户可见功能（user-observable functionality）与背后支撑的内部操作层（contain within operations）。
    * 通常用活动图（activity diagram）描述。
    * > 来源: P23
* **配置模型（Configuration Model）**
    * 传统软件环境固定、事先知道即可；网站不知客户端 OS、浏览器，却要保证各种人打开都好用。
    * 服务端（Server side）：硬件要求与服务器性能、操作系统、所用应用/数据库及版本、通信协议。
    * 客户端（Client side）：列清单照顾哪些浏览器（如 ZOJ 拒绝 IE6 并提示安装新浏览器）、操作系统、插件（如 Flash）及如何检测与补救。
    * 配置模型里必须含一个测试计划，把要照顾的所有环境全部测一遍。
    * > 来源: P23
* **导航模型（Navigation Model / RNA）**
    * 网站无法训练用户，故必须「充分傻瓜」：极易找到目标，且能退回、知道自己在哪。
    * RNA 五步：
        1. 分析所有利益相关者（即用户分类）。
        2. 分析有哪些数据、哪些功能。
        3. 分析关系（relationships）：网页间如何跳转，不同类用户交互是否互相影响。
        4. 决定浏览复杂程度：是否需要网站地图（site map）等导航辅助（树形适合程序员，幼儿网站要画成地图配链接）。
        5. 评估分析（evaluation analysis）：权衡友好度与工作量/投入产出比，决定导航做到什么程度。
    * > 来源: P23

## 4. Web应用设计模型

> **一句话主旨**：从设计前置约束与设计目标出发，逐层落到界面、美学、内容架构、导航与构件级设计。

### 4.1 设计前置约束与设计目标

* **设计阶段就要盯死的前置属性**
    * 安全（Security）：如跑考试/竞赛不能让考前扒题，须事先设计防攻击与黑客。
    * 可用性（Availability）：不能三天两头挂；频繁宕机用户就不来。
    * 可扩展性（Scalability）：要能应对访问量大幅波动，一两个人能玩、一两百人就挂掉不行。
    * 上市时间（Time to market）：工期极短，设计别想太复杂，尽量简单、先完成主要功能。
    * > 来源: P24
* **设计目标（design goals）**
    * 简单（simplicity）：第一条，尽量简单，不把事情搞复杂。
    * 健壮性（Robustness）：用户不可控，须应付各种人、各种「变态」操作，让各种水平的人进出自如。
    * 兼容性（Compatibility）：用户群不可控，规划照顾哪些平台、OS、浏览器（连 IE6 都可能）。
    * > 来源: P24
* **设计金字塔**
    * 越往上越靠近用户（界面、美工），越往下越靠近工程师（技术实现）。

```text
              [ Users 用户 ]            <-- 顶端，目标
                   |
        [ Interface Design 界面/美工 ]
                   |
         [ Content Design 内容设计 ]
                   |
        [ Navigation Design 导航设计 ]
                   |
         [ Technology 工程师 ]         <-- 底端，干活
```

### 4.2 界面设计

* **三个必答问题**
    * Where am I?（我在哪）：如行政办公网顶部「当前位置：首页 → 学术机构」，既告知位置又给出路径。
    * What can I do now?（我现在能干吗）：可点的东西清楚展示；本质是「把按钮做成按钮、把链接做成链接、把下拉框做成下拉框」，符合用户习惯预期。
    * Where have I been? / Where am I going?（去过哪、能去哪）：如点过的链接变紫、未点的蓝色；复杂网站可提供 site map。
    * > 来源: P24
* **有效界面的特征**
    * 视觉清晰且宽容（visually apparent and forgiving）：给用户掌控感，并允许点错（把用户当白痴，白痴都会用）。
    * 不暴露系统内部运作：并不弹窗询问是否保存，而是默认替用户存下且任何时刻可撤销。
    * 以最小信息完成最多工作（perform a maximum of work while requiring a minimum of information）：网上多一步既依赖服务器又依赖网络，用户不可容忍多余操作。
    * > 来源: P24
* **界面设计流程**
    1. 回顾并精化分析模型（review analysis model + refinement）。
    2. 画界面布局草图（rough sketch of the interface layout）：banner、功能带、竖栏左右、中间放什么。
    3. 把用户目标映射为具体界面动作（map user objectives into specific interface actions）。
    4. 列出点击后的后续动作序列（如 buy a component → 查看、选择、购物车、结账、填银行卡与地址）。
    5. 画分镜头（storyboards），描述每个界面动作下屏幕出现的状态。
    6. 抽取界面对象（interface objects）。
    7. 建立交互流程与动态行为（状态迁移）模型。
    8. 不断精化、评审、细化。
    * > 来源: P24
* **控制机制（Control Mechanisms）**
    * 最简单的是导航菜单（navigation menus）；另有图形图标（graphic icons）、图形图像（graphic images）等可作跳转与控制。
    * > 来源: P24

### 4.3 美学设计

* **合理留白（Don't be afraid of white space）**：不必把屏幕边角全填满，全填满有密集恐惧症的人看着难受。
    * > 来源: P24
* **突出内容（Emphasize content）**：一页重点展示什么要清楚，切忌喧宾夺主（如文字被 fancy 的 Flash banner 盖过）。
    * > 来源: P24
* **自左上至右下排布（Organize layout elements from top-left to bottom-right）**：绝大多数人习惯从左上往右下看。
    * > 来源: P24
* **区域一致性（Group navigation, content and function geographically within the page）**：同一功能（如「下一页」）在各页位置要一致，跳来跳去会让用户满屏找链接。
    * > 来源: P24
* **别靠滚动条掩盖重点（Don't extend your real estate with the scrolling bar）**：重点应出现在最上面、最醒目处；真要放下面，前面给提示性链接直达。
    * > 来源: P24
* **适配分辨率与视窗（Consider resolution and browser window size）**：不同浏览器、不同分辨率都要在美工时考虑。
    * > 来源: P24

### 4.4 内容与架构设计

* **内容设计（Content Design）**
    * 基本用 UML，把内容相关东西抽取为 Class 或 Object，定义好关系，与 Content Model 一脉相承。
    * > 来源: P24
* **内容架构（Content Architecture）**
    * 一个 content object 约等于一个 web page；网页与网页之间的整体结构有四种典型形态。

```text
Linear（线性）       Grid（网格）        Hierarchical（层次）      Network（网状）
 A→B→C→D          A──B──C                 A                     A↔B
                  │──│──│               / │ \                 ↕ ↕ ↕
                  D──E──F              B  C  D                B↔C↔D
```

    * 线性（Linear）：顺序串联；网格（Grid）：行列节点；层次（Hierarchical）：树状层次；网状（Network）：关系复杂。
    * > 来源: P24
* **应用架构（Application Architecture）：MVC（Model-View-Controller）**
    * 把系统分层，至少三层：View 前台/界面、Model 后台/业务逻辑与数据、Controller 控制器。
    * Controller 衔接前后台：接受用户从前台输入的需求，调用后台程序、从后台取数据，再传回前台展示。
    * 区别于普通软件从数据流图翻译成 call-and-return 结构。

```text
[ 用户 ]
   |
[ View 前台 / 界面 ]
   |  (输入需求)
   v
[ Controller 控制器 ]  <-- 衔接前后台
   |  (调用后台程序 / 取数据)
   v
[ Model 后台 / 业务逻辑与数据 ]
   |
   +---> 获取数据后回传前台展示给用户
```

    * > 来源: P24

### 4.5 导航设计

* **语义层面：导航语义单元（Navigation Semantic Units，NSU）**
    * 定义：A set of information and related navigation structures——一套描述信息与信息间导航关系的图。
    * 每个 use case、每个 actor 的行为对应一套 NSU。
    * SafeHome 例：actor → 首页 Home → link: Select Room → Room 页面 → link: Recommend Components → Product Component 网页。
    * > 来源: P24
* **语法层面：实现机制**
    * 单个导航链接（individual navigation link）：文字、icon、按钮等。
    * 导航条（navigation bar，水平）：放最重要几大类功能，不要超过七个（约四到七个）。
    * 导航栏（navigation column，垂直）：放左或放右皆可，可放几乎所有 major content objects 与重要链接。
    * 选项卡（tabs）：一般三到五个页面。
    * 网站地图（site map）：帮用户随时知道自己在哪。
    * > 来源: P24
* **横向 ≤ 7、纵向不限的原因**
    * 横向导航条须在同一屏宽内解决；纵向可借竖向滚轮滚动延展。
    * 尊重用户既有交互习惯——竖向滚轮对应竖向滚动，不让动作方向与页面移动方向冲突。
    * > 来源: P24

### 4.6 构件级设计

* **构件级设计（Component-Level Design）**
    * 与普通软件差别不大，WebApp 大致把功能分成四大类 component。
    * > 来源: P24
* **动态生成内容的构件**
    * 运行时动态产出页面内容。
    * > 来源: P24
* **提供计算功能的构件**
    * 承担系统的计算逻辑。
    * > 来源: P24
* **数据库查询功能的构件**
    * 负责对数据库的查询访问。
    * > 来源: P24
* **与外部系统沟通的构件**
    * 与外部系统做交互通信。
    * > 来源: P24

## 5. Web测试总纲

> **一句话主旨**：从质量维度与固有困难出发，给出与设计模型一一对应的分层测试策略。

### 5.1 质量维度

* Web 应用的质量考察维度（Dimensions of Quality）：

| 维度 | 含义与 Web 特殊性 |
| :--- | :--- |
| 内容（Content） | 内容要好 |
| 功能（Function） | 功能齐全、稳定 |
| 结构（Structure） | 整体组织架构合理，可扩展性（extensibility）强 |
| 可用性（Usability） | 强调每个 actor 都能学会并应用界面所需的所有导航语法与语义（用户分散、无法统一培训） |
| 可导航性（Navigability） | 用户不能迷路 |
| 性能（Performance） | 效率重要，打不开就流失用户 |
| 兼容性（Compatibility） | 客户端 OS、浏览器、屏幕分辨率千奇百怪都要较好兼容 |
| 可交互性（Interoperability） | 与其他软件、应用软件、数据库的可交互能力 |
| 安全（Security） | 挂到网上怕丢钱、被攻击，是重中之重 |

* **与传统软件的区别**
    * 普通软件 usability 常与 availability 挂钩（一年宕机不超过多少分钟）；Web 的 usability 强调用户能自学并走通导航。
    * 结构测试还须检验应用能否准确展现内容、是否可扩展、能否支持新内容随时更新。
    * > 来源: P25, P27

### 5.2 固有困难

* **症状位置与根因位置分离**
    * 客户端表现出的症状未必是客户端自身问题（如页面加载不出可能是网络下线、带宽不足），须穿透表层找根因。
    * > 来源: P27
* **环境不可复现**
    * 某错误只在某种配置或某种浏览器下出现，环境信息极难还原，测试在技术上不可重复、不可复制。
    * 典型：错误只在那台机器上那样，几乎无法在环境外重现（almost impossible to reproduce the error outside the environment）。
    * > 来源: P25, P27
* **错误常由配置引起**
    * 与传统软件多由代码逻辑出错不同，Web 应用许多错误来自不同配置；同一份代码在不同配置下表现迥异。
    * > 来源: P27
* **错误跨越三个层面**
    * 错误可能发生在客户端、服务器端、网络通信端三者之一，定位时须判断落在哪一层。
    * 来源还分静态的（与配置相关）与动态操作环境的（如瞬时资源负载量、《中国好声音》开播瞬间访问、退选时段负载骤增）。
    * > 来源: P27

### 5.3 测试策略与设计—测试映射

* **测试总体流程**
    1. 内容模型 → 内容测试。
    2. 界面模型 → 界面测试（需界面设计与美学设计）。
    3. 设计模型 → 导航测试（需导航设计与整体架构概念）。
    4. 用户界面 → 整体测试，找内容展示、排版、导航机制错误。
    5. 构件 → 单元测试（Unit Testing）。
    6. 整体架构/系统框架 → 完整系统测试。
    7. 配置（Configuration）与兼容性（Compatibility）→ 专门测试。
    8. 安全（Security）、性能（Performance）。
    9. 终端用户可用性测试（先培训再控制执行）。
    10. 上线前内部公测：可控环境挑选部分 End Users 做整体黑盒测试（如 ZOJ 正式上线前让集训队先「虐」）。
    * > 来源: P25, P27
* **测试活动与设计活动严格对应**

```text
内容测试        ──对应──► 内容设计
界面测试        ──对应──► 界面设计 + 美学设计
导航测试        ──对应──► 导航设计 + 体系框架设计
构件测试        ──对应──► 构件设计
配置/性能/安全测试 ──横跨──► 上述全部（综合性维度）
```

    * > 来源: P27

## 6. 内容测试与数据库测试

> **一句话主旨**：内容测试分语法、语义、结构三层，最复杂处是数据库的分层交互测试。

### 6.1 内容三类错误

* **语法错误（Grammar）**
    * 排版/拼写错误（typo）、句子不通顺等，依文本、文法、图表及其他表示形式检查。
    * > 来源: P25, P27
* **语义错误（Semantics）**
    * 语法拼写都没问题，但信息是否准确、清晰、完整；须精确表达，不出现二义、模棱两可或语义混淆（如挂十年前的学院介绍）。
    * 还包括政治等敏感因素是否恰当、无恶意。
    * > 来源: P25, P27
* **结构错误**
    * 内容最终展现给用户时，结构是否能合理反映内容；哪些内容放一起、哪些先出现，组织、顺序、结构是否正确。
    * > 来源: P25, P27

### 6.2 数据库分层交互

* **以数据库为中心的架构**
    * 绝大多数 Web 应用以数据库为中心，数据库操作必须测，且比普通软件复杂，因为与数据库的交互层数多。
    * > 来源: P25
* **五层交互链路**
    * 以「填查询词 → 点查询按钮 → 返回结果」为例：读网页 HTML 代码 → 解析出用户要查询的字段 → 判断是何种数据库操作并转换成相应数据库语言（如 SQL）→ 传给数据库执行并返回原始数据（raw data）→ 转换成用户可理解、可展示的格式显示。
    * 客户端请求一般不是 MySQL/SQL 语句，要做翻译；数据库可能不在你的 server 上，涉及 server 间 communication；raw data 回传后还要 proper format for display。

```text
[用户界面层]        获取 HTML scripts
      |
[WebApp Server 层]  从 scripts 中抽取 user data
      |
[WebApp Server 层]  转换成 SQL/格式, 与数据库交互
      |
[数据库]            执行操作, 返回 raw data
      |
[回传]              获得 raw data 向上传
      |
[用户界面层]        转换成可展示 format, display
```

    * 教材建议分五层（layers of interaction），每层都要有 testing plan。
    * > 来源: P25, P27
* **数据库测试复杂的四个原因**
    1. 客户端很少直接暴露 SQL（结构化查询语言），需在数据库管理系统（DBMS）间做跨平台翻译。
    2. 数据库可能位于远端，Web 应用服务器需跨服务器存取。
    3. 原始数据须尽快到达 Web 应用服务器再呈现给客户端，往往要做格式转换；动态内容对象亦需适当格式化以适合展示。
    4. 逻辑上要与客户端交互。
    * > 来源: P27

## 7. 界面测试与可用性测试

> **一句话主旨**：界面测试逐机制做单元、整合、验证三步，可用性测试由终端用户执行。

### 7.1 界面机制与测试步骤

* **界面机制（interface mechanism）**
    * 链接（links）、按钮（button）、表格（form）、弹出框（pop-up windows）、cookie 等。
    * 还包括客户端脚本、动态 HTML、CGI 脚本（Common Gateway Interface，运行在 Web 服务器上的应用程序）、流动的动态内容。
    * 特殊机制要专门测，如电商购物车：最小/最大容量、一件未选就点结算是否显示金额为零、超出最大容量会怎样。
    * 机制的目的是实现导航、功能与内容展示，要测其是否在语义上正确实现了目标（objectives）。
    * > 来源: P25, P27
* **测试策略四步**
    1. 整体界面特征（Interface Features）初测：对照界面设计原则看违背了哪些，再从美工角度检视（table size、行间距、边角留空）。
    2. 单元测试（Unit Testing）：对每一种 mechanism 做局部测试（如每种表格都要测）。
    3. 整合测试（Integration Testing）：把每一个 use case 或对应 NSU 整体串一遍 interface mechanism（NSU 比 use case 更管用）。
    4. 验证测试（Validation Testing）：把若干 use cases / NSUs / 模型组合起来整体走一遍界面，检查语义是否实现正确。
    * > 来源: P25
* **兼容性与人工验证**
    * 要对各种不同环境（客户端 OS、浏览器、分辨率）做兼容性测试。
    * 需引入人的测试以验证界面语义性，类似确认测试；在不同浏览器下测访问服务器、后台数据库的兼容性，类似配置测试目标。
    * > 来源: P25, P27

### 7.2 可用性测试

* **执行分工**
    * 测试由 Web 工程团队设计，由终端用户（end users）执行；不能自己人测自己人，须招募有代表性的用户群真实操作。
    * 核心问题：这批不可控用户能否自己学会并使用你的界面。
    * > 来源: P26
* **步骤一：界定目标（identify goals of each）**
    * usability 是一组「ability」的统称，实际包含：可交互性（interactivity）、布局（layout）、可读性（readability）、美工（aesthetics）、展示特性（display characteristics）、时间敏感性（time sensitivity）、个性化（personalization）、无障碍（accessibility）。
    * 选择哪些目标取决于产品本身与最看重的体验。
    * > 来源: P26
* **步骤二：为每项目标设计可量化评估方法**
    * 最难、最见功力：不能「用一下感觉不咋地打 60 分」，每个维度都要有可操作的评判指标。
    * 手势交互示例：找若干被试 → 先讲任务、用传统鼠标点击完成并掐表 → 再教手势完成相同任务并掐表 → 观察学习曲线（各自重复多少次后耗时趋于稳定）→ 辅以主观问卷。
    * 结论：客观计时 + 主观问卷，才是对「可交互性好坏」有依据的判断。
    * > 来源: P26
* **步骤三：选择并观察用户群**
    * 招募代表性用户完成测试，团队人员在旁观察、给予必要帮助与指导，并记录其接受程度。
    * > 来源: P26

## 8. 导航测试与构件测试

> **一句话主旨**：导航测试分语法与语义两线，构件测试以功能为基准并与数据库测试合并。

### 8.1 导航测试语法与语义

* **目标分两层**
    * 语法：检查导航机制是否正确；语义：导航是否准确。
    * 重点防止死连接（死导航、点不进的死链接）。
    * > 来源: P26, P27
* **语法层检查对象**
    * 链接（links）、重定向（redirects）、书签（bookmark）、框架与框架集（frame / frame sets）、站点地图（site map，若有）、站内搜索引擎（internal search engine，若有）。
    * 设计用例时，应确保每个用例能覆盖并正确回答教材所列测试问题（20.6.2 节 / 23.6.2 节）。
    * > 来源: P26, P27
* **重定向（redirect）的处理**
    * 当网页地址被删除、更新或取消时，应给用户恰当提示（如「网页已不存在或已删除」）。
    * 并建议「按某键返回主页」——非常规但必要的处理。
    * > 来源: P27

### 8.2 构件级测试

* **构件级测试（component level testing）**
    * 与普通软件测试差异不大，主要以功能为基准；黑盒测试、白盒测试等经典方法均适用。
    * > 来源: P26
* **与数据库测试合并**
    * Web 应用通常以数据库为中心，数据库测试一般与功能测试合并进行，共同验证功能点。
    * > 来源: P26

## 9. 配置测试

> **一句话主旨**：配置测试最头痛，分服务端与客户端两端，逐项检查环境适配。

### 9.1 配置测试难点

* **环境复杂、查错改错困难**
    * 配置测试是测试维护团队最头痛的一块，根源在环境复杂、查错改错困难。
    * > 来源: P25, P26
* **错误现象不等于错误本身**
    * 你在客户端发现的错误现象往往不是错误本身，很可能是用户系统的配置引起。
    * 用户说「在我机器上做某操作就出错」，但你在自己机器上几乎无法重现。
    * > 来源: P25
* **三层结构导致难定位**
    * Web 应用是客户端（client）+ 网络（network）+ 服务端（server）三层结构，debug 时很难定位 bug 发生在哪一层。
    * 分静态配置（static configuration）错误与动态（dynamic）错误（瞬时流量特别大时产生诡异错误）。
    * > 来源: P25

### 9.2 服务端配置

* **典型检查项**
    * 操作系统版本；依赖与依赖版本；安装位置；系统文件运行时能否正确生成。
    * 安全：防火墙是否安装；防火墙与加密（encryption）提高安全度的同时可能降低性能，须评估是否明显降速。
    * 分布式环境部署方案；数据库版本与应用是否存在版本不匹配；跨平台/软件版本的敏感性异常。
    * 服务端脚本（server-side scripts）必须测试；代理（Proxy Server）配置与不用代理时的差异。
    * 与数据库软件的良好整合，与服务器的兼容性。
    * > 来源: P26, P27
* **管理员角色（administrator）**
    * 最易被忽略：管理员通常是友好用户，团队安全设防更弱、权限更大。
    * 必须假设其可能误操作，并评估误操作（而非恶意攻击）对系统造成的后果。
    * > 来源: P26, P27

### 9.3 客户端配置

* **硬件与操作系统**
    * 硬件：CPU、显卡 GPU、内存、打印设备等（网游对显卡有最低要求）。
    * 操作系统：Windows、Linux、Mac OS X、手机端 Android 等都要实测。
    * > 来源: P26, P27
* **浏览器与界面组件**
    * 浏览器：IE（份额最大）、Mozilla Firefox、昔日流行的 Netscape（份额已极低）、Safari（苹果平板等），不能只测 IE。
    * 界面构件：ActiveX、Java Applets 等；动态插件 QuickTime、RealPlayer 等，缺失时能否提供安装文件。
    * > 来源: P26, P27
* **网络连接与传输设备**
    * 网络连接（connectivity）在网络环境下的表现。
    * 传输设备：Cable、DSL、调制解调器（Modem，带宽约 `56K`）、T1 等。
    * DSL 含 HDSL、SDSL、ADSL、VDSL；T1 美国制式 `1.544 Mbps`、欧洲 `2.048 Mbps`；T3 约为 T1 的 28 倍，达 `44 Mbps` 级别。
    * > 来源: P27

## 10. 安全测试

> **一句话主旨**：安全脆弱性分布在客户端、服务端、网络三个层面，须在交付前发现并弥补。

### 10.1 三层面脆弱性

* **客户端**
    * 最容易出错的是浏览器本身存在缺陷（这也是「不要用旧版 IE」的原因）。
    * 邮件系统、即时通信软件（如 QQ、MSN）带来安全隐患；既存 Bug 需跟踪找出并弥补。
    * > 来源: P26, P27
* **服务端**
    * 最易遭受拒绝访问攻击（DoS）与恶意脚本（malicious script）攻击，需评估防御能力。
    * 恶意脚本由客户端传入，可使服务器操作瘫痪，产生大量隐患。
    * > 来源: P26, P27
* **网络**
    * 传输链路的脆弱性。
    * > 来源: P26

### 10.2 客户端示例与攻防要点

* **客户端脆弱性示例（学生举证）**
    * 木马注入客户端，监听并截获输入的账号密码——测试时应验证防监听机制，看能否截获刚输入的账号密码。
    * 用 GET 传输指令或获取内容时，变量名显现在 URL 上，有经验的黑客可修改参数获取受限文件或他人隐私，进而影响服务器端（亦关联缓冲区溢出角度）。
    * > 来源: P27
* **攻防做法与性能权衡**
    * 课堂通过模拟黑客手段发现弱点；「一击即破」好过在运行中出事，可及时补救，否则给用户造成大损失。
    * 安全性测试须尽早找出弱点/易攻击性（vulnerability），在交付后被攻击前弥补。
    * 防火墙、加密提高安全度的同时可能降低性能，须评估是否会大幅明显降速。
    * > 来源: P27

## 11. 性能测试与负载模型

> **一句话主旨**：性能测试以总吞吐量模型 P=N×T×D 量化，分负载测试与压力测试两段。

### 11.1 性能测试要回答的问题

* **核心问题**
    1. 服务器响应时间会不会退化到「明显且不可接受」的程度（Does the server response time degrade to a point where it is noticeable and unacceptable）？
    2. 在什么并发量、什么数据流量下，性能变得不可接受（At what point does performance become unacceptable）？
    3. 接近崩溃时，哪些模块是瓶颈？
    4. 高流量下系统的安全性是否会受影响？
    5. 高并发时部分功能的可靠性、数据精确性是否受影响？
    * > 来源: P26, P27
* **Online Judge 案例**
    * 考试或比赛接近崩溃边缘会出现：运行时间测不准、内存使用测不准。
    * PAT 考试规则常注明：最后 10 分钟系统崩溃不补时，以崩溃时刻排名为准——高负载下数据准确性本身就是要测的对象。
    * > 来源: P26
* **超容量行为**
    * 超过最大容量（如支付系统设定一万，测一万零一、一万零二）会发生什么：直接瘫痪、不瘫痪还是性能死掉。
    * 性能衰竭要追到与哪个部件相关（服务器过少可增服，带宽不足可升级）。
    * > 来源: P27

### 11.2 吞吐量模型

* **总吞吐量（overall throughput）**

$$P = N \times T \times D$$

* $N$：并发用户数（the number of concurrent users）。
* $T$：单位时间内每个用户完成的在线事务数（online transaction per user per unit time）。
* $D$：每个事务所产生的数据量（data volume per transaction）。
* 以秒为单位时 $P$ 即每秒涌入服务器的总数据量；测试时不断改变 $P$，对三个要素做多种排列组合（极大并发+简单操作小数据量，或中等并发+复杂操作），不同组合暴露的瓶颈不同。
    * > 来源: P26, P27
* **NBA 直播页算例**
    * 假定 2000 人观看（$N=2000$），每人每两分钟递交一次评论（$T=1/120$ 次/秒），每次评论平均 3K（$D=3\text{K}$）：

$$P = 2000 \times \frac{1}{120} \times 3\text{K} \approx 500\text{KB/s}$$

    * 即该体育网站必须达到约 `500KB/s` 的吞吐能力。
    * > 来源: P27

### 11.3 负载测试与压力测试

* **负载测试（load testing）**
    * 在「正常值范围内」改变加载条件，观察 Web 应用及服务端环境对不同流量、访问量的反应。
    * > 来源: P26, P27
* **压力测试（stress testing）**
    * 负载测试的延续：找到系统的临界点并将其推过去（不断加压直至满载甚至超限），观察整体表现与是否瘫痪。
    * > 来源: P26, P27
* **真实流量不可控**
    * 真实世界流量（real-world loading）完全无法控制；玉米是服务器最好的测试员——每到抢票季，谁家服务器扛不扛得住一试便知。
    * > 来源: P26

### 11.4 支付系统并发证明

* **场景约束（类支付宝在线支付系统 Online Payment System）**
    * 至少支持 `100 万` 在线用户。
    * 每天并发量约 `10 万` 人次的分钟级并发访问。
    * 每天产生约 `1TB` 级数据。
    * 需同时考虑并发、存储、数据库对 100 万用户数据的支持。
    * > 来源: P26
* **证明要求**
    * 不谈用户界面与导航测试，聚焦性能。
    * 不能只测 10 个并发就宣称「大规模并发无压力」；须设计对照吞吐量模型 $P = N \times T \times D$ 的负载与压力测试方案，给出可量化证据。
    * 任何「优秀的特性」都不是嘴上两个形容词就能成立，每个形容词都要有根据、可证明。
    * > 来源: P26
