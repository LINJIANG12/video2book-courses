## 1. Web 应用工程：属性、分层与过程模型

> **一句话主旨**：列出 Web 应用的十项属性与十类应用分类，给出 Web 工程的四层技术栈、增量加敏捷的过程模型、动手前五问与最佳实践。

### 1.1 十项属性及其工程后果

* **严重依赖网络**
    * 属性本身即 Web 应用的定义性约束：它是基于 Web 的、基于网络的。
    * 后续的配置分析、配置测试、兼容性测试都由这一条派生。
    * > 来源: P21

* **跨浏览器兼容性与外观**
    * 不同的浏览器打开同一个页面，显示出来的东西可能不一样，因此必须照顾浏览器。
    * 也正因为是给人看的，外观与美观被提到与功能并列的位置。
    * > 来源: P21

* **本地存储少、性能压力大**
    * 本地存储比较少，其直接后果是它必须快，`performance` 很重要。
    * 用户打开半天还在 loading，就可能不耐烦走掉；想吸引访问量的站点做不好性能就没人气。
    * > 来源: P21

* **开发要敏捷、迭代周期极短**
    * 一般接到 Web 应用任务时不会给出很长周期，给三个星期就已经很长，最好是一个星期交付。
    * 周期决定了过程模型必须是非常敏捷、非常快的模型。
    * > 来源: P21

* **更新与迭代连续进行**
    * 传统软件可能两星期或一两个月更新一次，Web 应用可能两三个星期就更新一次，对维护团队管理能力要求很高。
    * 进一步可能是无缝衔接的：没有固定上线节奏，版本一直不停地在变、连续地在变。
    * > 来源: P21

* **用户交互性强，而用户群体不可知**
    * 交互性要照顾得周到，最麻烦的是不知道是什么用户。
    * 对照：给一个小银行做只给员工用的系统，用户群固定，可以训练他们、监控他们的行为；上网之后谁在用完全不可知。
    * > 来源: P21

* **数据存在服务器上，安全成为核心**
    * 数据从用户本地电脑转移到服务器的数据库里，安全（`security`）成为非常重要的因素。
    * 它还决定挑人标准：除了编码强的人，还需要一帮对 security 很懂行的人。
    * > 易错点：课程大作业对 security 不做特别高的要求，具体到什么程度要去跟助教、跟客户谈；真正的支付系统 security 要求完全不同，不能拿作业标准类推。
    * > 来源: P21

* **大规模并发与不可预测的负载**
    * 放到网上给大家用的软件必须考虑工作负载（`workload`）与并发性（`concurrency`），要有很强的并发处理能力。
    * 实例量级：奥运抢票网站引进的国外软件实测并发是**每秒钟五个**；每秒钟 500 个还不一定够，每秒钟 5 个并发必然瞬间崩溃。
    * 不可预测的负载：使用量可能季节性爆发，每天不同、每个时段也不同。
    * > 来源: P21

* **全天候可用性**
    * 挂上网的东西被默认应当每天 24 小时、一星期 7 天、一年 365 天 available，不应有太多挂掉的时间。
    * 这要求一个非常强大的维护团队。
    * > 来源: P21

* **数据驱动、内容质量与美观**
    * 大多数网站主要是 `data-driven` 的，共同的基本功能是向用户展示某一类数据（视频、音频、文本等）。
    * 靠内容吸引访问时，对内容质量的要求比一般软件高得多；只给内部员工用的软件里，措辞与美观是次要的，能支持工作流程即可。
    * 美观是吸引人的一部分，需要有一个强大的美工；美工难找，且 UI 与美工可以是两个人。
    * > 来源: P21

* **连续演化与即时性**
    * 连续演化（`continuous evolution`）意味着团队组好之后不是开发一个星期就散伙，团队结构不是一次性的。
    * 即时性（`immediacy`）要求今天说最好明天做出来，最多给一个星期，不可能规划三年后交付，整个过程模型的设计要以快为主。
    * > 来源: P21

### 1.2 十类应用分类

* **十种类型与典型代表**

    | 类型 | 含义与特征 | 典型例子 |
    | :--- | :--- | :--- |
    | `informational` | 基本上是静态网站，发通知、发新闻，`read-only`，没有互动，只是发布消息用的 | 各类信息发布站点 |
    | `download` | 专门给你提供资源下载的 | 源网那类提供高清电影下载的站点 |
    | `customizable` | 允许你根据自己的个性做定制的 | 博客（非常典型） |
    | `interaction` | 交互用的 | CC98、飘渺水云间、QQ |
    | `user input` | 让你在网上填表用的 | 各类在线表单 |
    | `transaction-oriented` | 事务类型的：你提一个请求，它按你这个请求走一个处理流程；不同的请求走不同的流程，处理不同的事务，起的是一个事务中心的作用 | 各类在线业务办理系统 |
    | `service-oriented` | 提供某种服务的 | 学校里的服务类系统 |
    | `portal` | 门户网站，起一个门户作用的 | 各类门户 |
    | `database access` | 提供数据库访问的 | 各类数据查询站点 |
    | `data warehouse` | 再大一点的数据库的集合，即数据仓库 | 见下文辨析 |

    * > 来源: P21

* **数据仓库与数据库的区别**
    * `data warehouse` 基本上可以理解成**数据库的集合**，而且是好多不同数据库的数据的集合。
    * 它不是简单的拼凑：要把不同数据库里面的数据整理一下，重新归类、再组织，规模比 `database` 大很多。
    * > 来源: P21

* **分类框架的课堂三问**
    * 问一：整个支付宝 project 属于哪一类，用它的特点说明理由。
    * 问二：自己负责的模块是否具有 Web 应用特征、属于哪一类；不属的要用特征逐条否定——**不是每个模块都具备**。
    * 问三：挑两种类型，每种举一两个著名网站，不许只报网站名，要讲清这个网站做什么、有什么特点、所以归哪一类。
    * > 来源: P21
    * `data warehouse` 基本上可以理解成**数据库的集合**，而且是好多不同数据库的数据的集合。
    * 它不是简单的拼凑：要把不同数据库里面的数据整理一下，重新归类、再组织，规模比 `database` 大很多。
    * > 来源: P21

* **分类框架的课堂三问**
    * 问一：整个支付宝 project 属于哪一类，用它的特点说明理由。
    * 问二：自己负责的模块是否具有 Web 应用特征、属于哪一类；不属的要用特征逐条否定——**不是每个模块都具备**。
    * 问三：挑两种类型，每种举一两个著名网站，不许只报网站名，要讲清这个网站做什么、有什么特点、所以归哪一类。
    * > 来源: P21

### 1.3 层次结构、过程模型与动手前五问

* **四层技术栈**
    * Web 工程与普通软件工程一样是层次化技术（`layered technology`），层次自下而上是质量焦点、过程模型、方法与工具，与普通软件工程同构。
    * 区别在于每一层的内容都向「快」和「连续演化」倾斜。
    * 各层内容：`quality focus` 以质量为中心且始终在最底层；`process model` 通常是 `agile`（特点就是快）；`methods` 仍要注重 `communication`、`requirements and analysis`、`design`、`testing`，但有一套自己的方法；`tools` 是 HTML 等常用工具，针对性更强一点。
    * > 注意：很匆忙不代表就不做质量，仍然要注意控制 quality。
    * > 来源: P21

    ```text
    +---------------------------------------------------+
    |  tools      常用工具：HTML 等（针对性更强一点）    |
    +---------------------------------------------------+
    |  methods    注重 communication、requirements and   |
    |             analysis、design、testing，都要做      |
    +---------------------------------------------------+
    |  process model   agile / incremental（特点：快）   |
    +---------------------------------------------------+
    |  quality focus    以质量为中心，始终在最底层       |
    +---------------------------------------------------+
    ```

* **过程模型：增量交付 + 敏捷**
    * 过程模型要照顾两点——为了快，以及连续演化（随时随地都在更新版本，不是三五个月推一个新版本）。
    * 因为不要指望「一步到位」，所以一般是渐增交付（`incremental delivery`），一点一点交出来；加上改变经常发生、时间线非常短，因此要选 **incremental process model**，同时大多数情况下是 **agile process model**。
    * 迭代的每一圈转出去一个 `increment`；中间的 `construction` 部分同时伴随重构（`refactoring`），不断优化内部结构、同时添加新功能，从而产出新增量。
    * > 易错点：做重构之前一定要想好、要小心——课上把它称为一个大坑。
    * > 来源: P21

* **动手之前要搞清楚的五个问题**
    * 网站内容的重要程度：决定内容敏感（`content-sensitive`）到什么程度，是给国防部做的还是本课程给大伙儿用的，是内部学生自己用还是要放到外面给全国高校学生看。
    * 页面布局的最有效套路：上面横着一条 menu 下面放内容，还是横着一栏、竖着一栏（竖栏放左或放右），先想清楚。
    * 内容用什么媒体形式呈现：简单文字、视频、音频还是 Flash，哪一种效果最好。
    * 用户想做什么、他有多大的耐心：他最多愿意做几步操作，取决于面向的是老年人、大学老师还是幼儿园小朋友。
    * 导航、检索与表单填写量：网站复杂度决定要不要做 search 或导航图；注册表能指望用户填完吗——商家希望填得越多越好，填太多用户直接不注册走掉。
    * 另有一条独立决策项：要不要照顾残疾人、要不要做到无障碍访问，有没有可能做到。
    * > 易错点：表单信息量与用户耐心的平衡非常微妙，而且它跟导航连在一起——网站很复杂、内容非常多时，search 功能需要强大到什么程度也要一并定。
    * > 来源: P21

* **最佳实践七条**
    * 花时间搞清楚业务需求与产品目标（`take the time to understand the business needs and product objectives`）：大方向不能省，有一些时间是不能省的。
    * 采用基于场景的方法（`scenario-based approach`）：做一系列用户场景（`user scenarios`）与一套一套用例（`use cases`），据以规划和开发。
    * 仍然要先有一个计划：不是传统软件工程那种严格到同一数量级的 plan，而是**轻量级的 plan**，但不能没有 plan 就动手。
    * 动手之前先做一点建模（`modeling`）：为长期的维护过程留文档——ZOJ 系统 2001 年投入使用、2.0 版本 2008 年上线，开发团队早已换过好几拨人；这个 modeling 可以写得比较简单，但一定是要有的。
    * 对一致性与质量做检查：把握系统的一致性以及内容、模型的整体设计质量。
    * 尽可能重用已经做好的模块：这是「快」的根本——专门做教育领域网站的人会把共性保留下来，后面越做越快。
    * 上线之前内部一定要做充分测试：不能把测试留给用户，否则用户一用就挂掉，后面至少一大半的人不会再来；Web 测试比普通软件测试还要更困难一点。
    * > 来源: P21

## 2. 项目管理：立项、团队与外包

> **一句话主旨**：讲清 formulation 阶段的终点与必问的三类问题、两类目标抽取、三类项目的计划差异、六种团队角色，以及外包与自研的界线。

### 2.1 formulation 阶段与需求获取

* **formulation（构想、规划）**
    * > 定义：`formulation` 阶段从最初听到一句模糊的想法开始，到拿到一个大致的需求为止。
    * 项目启动第一步叫 `initiating`，其第一件事就是 `formulation`，字面勉强解释为「大概规划一下」，但它的终点非常清楚。
    * > 易错点：越「理所当然」的目标越容易漏问——双方各自的预设都很显然，而两个「很显然」不相等，这类分歧不会在会上爆发，只会在交付之后爆发。
    * > 来源: P22

* **提问的覆盖面与顺序**
    * 列给客户的问题必须覆盖三个方面：用户**为什么**要做这件事；他想要**做成哪些事**；**谁来用**。
    * 顺序有讲究：同样一组问题，顺序不一样，得到的效果不一样；很多人的第一反应是问「有钱没的」，这么问不好听，而且真正决定预算的是他为什么要做这件事，所以第一问应落在动机上，预算从动机里推。
    * > 来源: P22

* **business need：识别业务需求**
    * `identification of business need` 问的是你为什么要做这个网站：为了申请报奖、申请教育部的项目、学校要求的，还是自己想做。
    * 问这个问题的同时还在摸另一件事——做这件事能带来什么好处、愿意付多少代价，这个预期必须有。
    * > 结论：先搞清楚「到底为什么要做这件事情」，才谈得上后面所有的问题。
    * > 来源: P22

* **objectives 与 major features and functions**
    * `objectives` 问的是这个网站到底干嘛用：只把课件放上去方便学生下载，还是另有课外 reference 供下载，要不要组织论坛、要不要布置作业、原来带的打分功能还要不要保留。
    * 问完用途要落到 `major features and functions` 上，明确到底需要哪些功能——这是后面所有设计工作的输入。
    * > 来源: P22

* **谁来用：单用户还是整个课程组**
    * 第三个问题是最要命的：是给我一个人用的，还是要给整个课程组五六个老师一起用。
    * 反面实例：给课程组做的网站只有一个用户，其他老师都不能用；原因是双方都认为目标很显然，谁都没说那句话，后来要改成多用户，才发现原设计很不好、改起来非常麻烦。
    * > 来源: P22

* **requirements gathering 与共同目标**
    * `formulation` 收尾要有 `requirements gathering`：用一种方式把需求收集、整理起来，并做一个 `analysis model`。
    * 最后所有 `stakeholders` 与开发人员要坐到一起，达成 `common set of goals and objectives`——要做什么、达到什么总体目标、完成哪些功能，都是大家同意要做的。
    * 为什么必须有「都同意」这一步：时间线这么短、钱只有这么一点，胃口很大地说要做什么什么，所以最后要达成一个协议。
    * > 来源: P22

* **两类目标的抽取**
    * `information goals`（信息目标）：这个网站要提供哪些内容、哪些数据，以什么形式展现。
    * `obligative goals`（功能目标）：有哪些功能、有哪些任务可以通过这个网站来完成。
    * 一类是数据、一类是功能，两方面都要抽出来，这是 `formulation` 阶段必须完成的抽取工作。
    * > 来源: P22

* **用户类别与每类用户的描述**
    * `user categories` 做别的软件时也要做但没那么重要；做 Web 应用时显得非常重要——有哪些人要用这个网站。
    * 对每一类用户都要给详细描述，除了他要干什么、他的 objectives，还包括：background（教育背景、识不识字、是哪一类人）、习惯（年龄段，比如面对 90 后就要想他们喜欢的网络环境什么样，这直接决定界面风格）、在什么情况下什么场合会来用、特别喜欢什么和特别不喜欢什么。
    * 风格对照：给幼儿园小朋友做要花花绿绿、少文字、多动画图片、点点戳戳就能用；把这种风格弄到银行网站上去就很奇怪。
    * > 来源: P22

* **沟通、前期调研与场景构建**
    * `communicate` 的手法：对传统人士用开会、面对面谈，还可以用 `email`，或者做 `survey` 发到特定用户群。
    * 特别需要前期调研的情形：做的是以前没人做过的东西、有一个 `great idea`，那么很重要的一项工作就是设计调查问卷到合适人群里去发，采集充分多的数据，才看得到在人家心目中这类 service 应该是什么样子。
    * `scenario building`（场景构建、用户脚本）：慢慢在脑子里成形——这一群人用你这个东西时是怎么一个用法，对他来说怎么用最有吸引力、最好用。
    * > 来源: P22

* **从 content object 到 use cases**
    * 分析这一步要从各种信息里抽取出 `content object`（内容对象：数据、输入输出、要展示的东西）与 `operations`（操作：要完成哪些功能），最后得到一套一套 `use cases`。
    * > 结论：做网站基本上都是以 `use cases` 为核心的；后面从建模、设计到测试，`use case` 都是非常重要的依据。
    * > 来源: P22

### 2.2 三类项目的计划对照

* **三类项目对照表**

    | 项目类型 | 流程与规范 | 反馈与风险 |
    | :--- | :--- | :--- |
    | `traditional project` | 面向比较封闭的环境、公司内部比较固定的人群，流程严格、按部就班 | 可以直接去获得用户反馈 |
    | `major e-project` | 基本流程跟传统软件工程差不多，要求一样严格，也要按部就班 | 唯一区别在 `customer feedback`：用户是全世界所有可以上网的人，没办法在特定范围内获得反馈 |
    | `small e-project` | 什么都要求快，时间周期非常非常短；`requirements gathering` 不需要严格过程，但总要有一个 `descriptive overview` | `testing`、`QA`、`risk management` 的重点都在 `risk control` 上 |

    * 表里列出的就是 planning 阶段要计划的那几件事：`requirements gathering`、`technical specifications`、到底有多长时间做、`testing` 与 `QA`、`risk management` 等。
    * > 来源: P22

* **大型 Web 应用与传统项目的唯一差别**
    * 规模比较大、功能比较多的复杂大系统，基本流程跟传统软件工程差不多，要求一样严格，唯一区别在最后使用的 `customer feedback` 方向上。
    * 传统项目在比较封闭的环境下、面向比较固定的人群，可以直接获得用户反馈；Web 应用的用户是全世界所有可以上网的人，所以反馈收集过程要尽量设计成自动获取反馈的机制，或者用调查问卷到处丢。
    * > 结论：大型 Web 应用跟传统项目在流程上不用另起一套，真正要单独设计的是「谁来告诉你它好不好用、你怎么拿到这个信息」。
    * > 来源: P22

* **小型 Web 应用：快与 risk control**
    * 基本特点就是快，时间短所以什么都要求快。
    * `requirements gathering` 不需要传统那套严格过程（一步步做、仔细设计问什么、开好几次会、写需求规格说明书），但你还是大概需要一个 `descriptive overview`，三言两语说一下。
    * `testing`、`QA`、`risk management` 的重点都强调 `risk control`；团队的人要对要用的技术非常熟练，并随时关注到底做不做得完。
    * 全部时间只有 7 天时，不能说用两天做准备、剩下 5 天大家加油干、中间什么都不管——那样 5 天以后多半得到「我没做完」；要保证做完，其实每天都要 track、每天都要盯牢。
    * > 结论：小型 Web 项目的 plan 要强调快，但又不能放松质量，而你又不可能做一个很好的质量监控，要在中间做一个平衡。
    * > 来源: P22

### 2.3 团队构成与 stakeholder 角色

* **team 与 stakeholder**
    * > 定义：这里的 `team` 不只是指开发团队，而是开发过程中需要紧密沟通的那一群人，也就是 `stakeholder`（利益相关者）。
    * `web engineer` 绝对是团队里的重要人物；除他们之外还需要别的角色，而且这个 team 不一定都包括自己人。
    * 课程网站场景：客户既给钱又提需求，一个人身上可以集中好几个角色；换到办公网场景，角色就必须拆开。
    * > 来源: P22

* **开发团队与 support team**
    * 网站做好后团队撤了、接着没人管，网站会迅速死掉；要让网站一直活着，需要开发的与维护的两类人，所以要有一个 `support team`。
    * 办公网里数据库乱掉、怎么弄都进不去时，办公室的人要打电话找人，因此总有一个联系人始终守在电话那边、随叫随到。
    * > 结论：`support team` 是一定要的，且不一定是开发的那拨人，通常是两拨人。
    * > 来源: P22

* **content provider 与 web publisher**
    * `content developer`／`content provider`（内容开发者／内容提供者）负责给网站提供内容，例如办公网上的通知由谁写好、准备好往上挂。
    * 范围要划死：网站只接受哪些人提供过来的信息，不是随便什么人打个电话就能挂东西上去；要明确谁有权提供这个内容。
    * 提供内容的人不一定是把内容挂出去的人，所以还有 `web publisher`（Web 发布者）：学校里有稍微懂点技术的人在后台操作，把内容发布到相对应的正确位置上。
    * > 来源: P22

* **business domain expert 与 administrator**
    * `business domain experts` 不等于 marketing，他掌握整个 domain 相关的知识：做计算机学院网站时，学院办公室主任一定是 team 里的一员，因为他知道办公流程、什么部门管什么事情、哪部分内容该放哪里、什么可以放什么不可以放。
    * 做选课与成绩管理（含退学警告）网站时，对应的 domain expert 就是教务处处长、学籍管理处处长或他们派的代表；`content provider` 只负责把某门课挂上去、把学生导进去，不一定知道整个流程的规矩。
    * `administrator`（以前叫 `web master`）：自己的开发团队里大概只有 `web engineer` 和 `support specialist`，不会有 administrator，得在用户里面找一个来做这个事情。
    * > 来源: P22

### 2.4 外包、自研与最佳／最差实践

* **outsourcing 与 in-house 的唯一区别**
    * `in-house`（自己做）：开发团队 + 全部 stakeholder 代表坐在同一张圆桌上直接讨论软件的核心问题，对所有参与方全透明。
    * `outsourcing`（外包）：软件的核心内容由外包承包商封在里面，任何改动与讨论都要经过他提供的 `liaison`（联络员）这一中间机制，由联络员收集各方意见再传到里面去。
    * > 来源: P22

    ```text
    in-house（自己做）
      开发团队 + 全部 stakeholder 代表
          |
          +---> 同一张圆桌，直接讨论软件的核心问题
                （对所有参与方全透明）

    outsourcing（外包）
      开发方与各 stakeholder 代表
          |
          +---> liaison（联络员） --收集大家的意见--> [ vendor：软件的核心内容被封在里面 ]
          |                                                    |
          +------------------ 改动与答复 <----------------------+
    ```

* **外包前的六项准备**
    * 自己先 `gather requirements`：要知道到底要做的是个什么东西。
    * 自己先有一个 `rough design`：虽然 rough，但它也是一个 design，大模样得知道。
    * 自己先有一个 `schedule`：出去谈条件谈价钱时才不至于太离谱。
    * 定义 `increment` 到什么程度：Web 应用不是一次性交付就完事，每一次要给一个增量，每次到什么程度自己要有定义。
    * 划清责任：自己人负责哪些、外包商团队负责哪些，否则最后就会打起来。
    * 定义双方的联络机制（联络员机制）。
    * > 来源: P22

* **外包商的考察要点**
    * 多找几个，别盯死一家。
    * 看他报的价钱，以及这个价钱到底有多可靠——报得很低、时间很短，就要考察他的资质、报价、团队以前的声誉：他做得了吗、做得完吗。
    * 想清楚包出去以后自己在多大程度上还可以掌控这个 project：是一交给他就什么都不许碰，还是仍能做一定程度的 management。
    * 核对你的 `schedule` 是否合理——前提是你自己知道一个真正合理的 `schedule` 是什么样子。
    * 外包商一般不会让你把手伸到他公司里面去管细致进度，但 `scope`（范围）要管，大致的进度也要管一下。
    * > 来源: P22

* **in-house 要盯的几件事**
    * 知道 `scope` 是什么、大概范围是什么、什么地方最经常要改变、有什么限制条件。
    * `incremental` 化：每一个 `increment` 怎么定义。
    * `risk analysis` 是最重要的一点。
    * 宏观的 `estimation`：大概是什么规模、大概需要多少人力物力，毛估估就可以。
    * 定义 `task set`，把工作分解成若干任务并控制任务进度；判断完成了百分之多少最常见的做法是 `count use cases`，看有多少个 use cases 已经走完——当然这取决于开发策略，不一定按 use cases 的线索开发。
    * 还有 `change management`（变更管理）。
    * > 结论：`in-house` 要注意的东西跟传统开发差不多，一个特点就是快一点。
    * > 来源: P22

* **best practices 中被点名的三种做法**
    * 「`we have a great idea`，所以我们就开始干吧」：要先想好钱在哪、做出来有没有人用、能不能赚到钱，然后才开始做。
    * 「反正它总是要变的」：因为需求总在变就不把需求搞清楚，后果是 `unnecessary changes`（不必要的改变）更多。
    * 「做传统软件开发做得好的人直接拿过来做 Web 开发，不需要任何新培训」：书上认为这两种东西 `they are different`；讲师自述对这一条没有特别深刻的感受，只是把它作为书上的一个建议列出。
    * > 来源: P22

* **worst practices 中的两种做法**
    * 官僚式管理：什么都要走固定流程，在大公司里或许可以，但开发轻型小型 Web 应用时应鼓励大伙加油、自己靠边不捣乱，一切以快为准。
    * `testing web bother`：自己内部测试不好，拿出去让用户去测试，可能是一个很大的悲剧。
    * > 来源: P22

## 3. 需求分析：用户、用例与分析模型

> **一句话主旨**：说明 WebApp 需求分析在任务不变的前提下如何降低正式程度，并给出用户层次、用例四原则、四类分析模型与导航分析 RNA。

### 3.1 用户层次、用例与划分原则

* **WebApp 分析模型的正式程度**
    * WebApp 一般要求做得快，所以它的 `analysis model` 不要求特别严肃、正式，也不要求特别详细、严谨——有就可以。
    * 做需求分析的 `tasks` 本身跟普通 project 没有两样，变的只是要求的程度：一上去先要有一个 `formulation`（很快），接着 `requirements gathering`（所有人坐到一起说清做成的到底是什么东西），最后交出一个 `analysis model`。
    * > 来源: P23

* **formulation 的两个交付物**
    * `formulation` 的主目标跟普通项目一样是搞清楚 `goals and objectives`：`goals` 是大目标（为什么要做这件事），`objectives` 具体一点（要做成哪些事）。
    * 不一样的是要特别做 `categories of users`（用户分类），并在 goals and objectives 之外再给出一张 `user hierarchy`（用户层次、用户分类）图。
    * 到这里 formulation 需要的两样东西就齐了：一份 `goals and objectives`，一张用户层次图。
    * > 来源: P23

* **user hierarchy 的划法与细分依据**
    * 书上用 `SafeHome` 家居保安系统的网上商店举例：顶层是 `SafeHomeAssure.com user`，往下第一层分三大类，`registered user` 再往下细分一层，`guest` 与 `customer service` 不再分。
    * 三大类的划分依据是权限：`guest`（游客，打酱油的）、`registered user`（注册用户，正经想买东西的）、`customer service`（网上商场的服务人员）。
    * `registered user` 还可再分成新手还是老用户，给他们提供的 `service` 也可以略有不同。
    * > 提示：要不要分这一层由网站决定——如果新手与老用户进去看到的界面、拥有的权限都一样，就没有必要再分；只有当你要给这两类人提供不一样的 service 时，这个细分才有意义。
    * > 来源: P23

    ```text
                        SafeHomeAssure.com user
                                  |
            +---------------------+---------------------+
            |                     |                     |
       +---------+        +----------------+     +------------------+
       |  guest  |        | registered user|     | customer service |
       +---------+        +--------+-------+     +------------------+
                                   |
                        +----------+----------+
                        |                     |
                  +----------+          +----------+
                  |  新手    |          |  老用户  |
                  +----------+          +----------+
    ```

* **use cases 的三个去处**
    * 设计的时候要用到它。
    * analysis 阶段也要用到它：写需求时里面有好几种模型，至少四大类，每一类模型都跟它有关系、都能从它里面得到很多信息。
    * 测试的时候用它测：黑盒测试肯定是一个 `use case` 一个 `use case` 地走。
    * > 易错点：用「数 use case」当进度指标并不非常准确，因为每个 use case 的难度不一样——注册一个新账号很简单，进去做一大堆事、最后买完东西再走这一串就复杂得多；但它起码是一个可以拿来说事的指标。
    * > 来源: P23

* **用例图的画法：actor、圆饼与 package**
    * 以 `new customer`（新手用户）为例，他要做的事有先后的讲究：首先要 `log in`，然后看要买的商品的描述性内容，接着 `建立 configuration`（挑哪几个模块并保存），保存后可能还要 `recall saved configuration`（调出已保存的配置）。
    * 两个比较复杂的业务功能是 `customize SafeHome`（自己定制一套个性化系统、决定要哪些东西）与 `purchase configuration`（配置定好后购买，购买过程也比较复杂）；画不下就各装进一个 `package`（包）里，在图上直接展示这两个 package。
    * > 提示：`recall saved configuration` 对新手不是最要紧的一步，因为他还没存过东西；真正必需的顺序是先建立 configuration、再存，才能谈调出。
    * > 来源: P23

* **用例划分的四个原则**
    * `comprehensible`（可理解）：图要让人看得懂，别画得太乱太复杂，也别把名字取得很含糊。
    * `cohesive`（内聚性要强）：一个 package 里的东西都比较集中，都为完成同一个任务、目标比较集中。
    * `loosely coupled`（耦合要松）：package 与 package 之间、功能模块与功能模块之间最好不要有太紧密的关系，这样分工会分得比较干净。
    * `hierarchically shallow`（层次要浅）：用例本身是分层次的（前面那张图基本分两层），但最好不要有太深层次——太深对用户不好（完成一件事要点很多环节）、对 WebApp 尤其重要（还受网络带宽影响，点一个链接等半天还要点 10 个链接就没人用了）、对测试也不好（一条线索设计太深，测起来很痛苦很麻烦）。
    * > 易错点：内聚与耦合说的是两个方向上的事——包**内部**要抱成一团，包**之间**要尽量少牵连；把一堆互不相关的目标塞进同一个包，不叫高内聚，那只是把东西堆在了一起。
    * > 来源: P23

### 3.2 四类分析模型：内容、交互、功能、配置

* **分析模型的四个方面**
    * **内容**（content）：网站要展示什么东西，包括文本、图片、视频、音频，都要分类，弄清哪些是要做的 `data objects`。
    * **交互**（interaction）：用户交互方面的分析。
    * **功能**（functional）：要完成哪些功能，比较传统。
    * **配置**（configuration）：WebApp 比较注重、比较特殊的一项。
    * > 来源: P23

* **为什么必须有配置分析**
    * `configuration analysis` 在普通传统软件里不太讲：传统软件就是给这个公司做的，公司环境固定，事先知道就可以了。
    * 网站不一样：你不知道客户端是什么样子——不知道有什么样的客户，也不知道他用了什么操作系统、什么浏览器，所以要保证各种人打开都好用。
    * > 易错点：这不是容易做到的事情，其实是一个很痛苦的事情；配置分析不能像做传统软件那样跳过。
    * > 来源: P23

* **内容模型与 data tree**
    * `content objects` 要解决的问题是什么东西作为你的 `class`、什么作为系统里的 `objects` 存在：来源是去看 use case 抽取，然后把它们之间的 `relationship` 搞清楚。
    * 描述关系除了数据库用的 `ER diagram`，书上还介绍了 `data tree`（数据树）：定义一个 `struct` 叫 `component`（家具系统里的一个模块），它要展示 `part no.`（数字）、`part name`（字符串）、`part time`（整型／字符串）、`price`（数字）与 `description`。
    * 前四项画在白框里表示只是简单数据、不是复杂 object；黑底的 `description` 才是要花笔墨去描写的东西，是一个真正的 `data object`。
    * 画 data tree 的目的是让人一目了然地知道最后要设计的 `data object` 都有哪些。
    * > 提示：系统比较复杂、想弄得比较全时，有一个笨而有效的办法——写一个 `parser` 把 use case 整个过一遍，把里面相应的名词抽出来，筛掉简单的，再考虑那些不是一个数字或字符串能解决的是否该设计成要在系统里处理的 data object。
    * > 来源: P23

    ```text
                             component
                                 |
           +-------+-------+-----+-----+-------+
           |       |       |           |       |
       part no. part name part time  price  description
       数字     字符串    整型/字符串 数字    data object
       [白底:简单数据]                    [黑底:真正的对象]
    ```

* **交互模型的四个元素**
    * `use cases`——必须有。
    * `sequence diagrams`（顺序图）：随着时间迁移从上往下走，每个动作涉及哪几个元素，像泳道一样摆成几个 `actors`，一路往下走。
    * `state diagrams`（状态图）：就是状态迁移。
    * `user interface` prototype（用户界面原型）：做一个 prototype 出来，就知道 interaction 是什么样子，这是最直观的一个东西。
    * > 易错点：`data flow`（数据流）不算描述交互的图——数据流是内部功能与功能之间的转换、数据怎么变，说的不是用户跟你这个东西怎么沟通；真正跟「交互」对得上的是 `control flow`，而对 WebApp 来说状态转换直接落在页面上，也就是**页面之间的跳转**。
    * > 提示：四个元素不一定全都要画——给那位老先生做的东西虽然不典型，但 interaction 部分比较复杂，图都画了，`use case` 却没写，做了一个很有用的 `interface prototype` 问题就都解决了。
    * > 来源: P23

* **功能模型的两个层次**
    * `functional` 比较传统，但有一处要特别注意：需求收集阶段基本上收集到的是 `user observable functionality`（用户可观察的功能）——用户看得到、他说「我要这些功能」的那些。
    * 系统要真的做到这些事情，后台还有一些动作要做，后台那些动作也要准备好；所以要准备两个层次的 functional：一个用户可见的，一个背后支持的（`contain within` 系统内部的 `operations`）。
    * 描述 functional model 一般用 `activity diagram`（活动图）就够了。
    * > 提示：说 WebApp 时所有这些 model 都没有要求得那么严格；大概画个草图、小团队大家能互相看懂就可以。
    * > 来源: P23

* **配置模型：服务端与客户端**
    * 服务端（`server side`）在需求分析阶段不用特别具体，但要大概说清：硬件要求是不是特别高、服务器性能要到什么程度；在什么操作系统上跑；是否还要用别的应用、别的数据库、版本是什么；之间的通信协议是不是网络的通信协议。
    * 客户端（`client side`）有一条对所有人都适用的清单。

    | 客户端环境 | 要做的判断 |
    | :--- | :--- |
    | 浏览器 | 先列一个清单：要照顾到哪些浏览器，不照顾哪些 |
    | 操作系统 | Windows 是一套解决方案；用 Unix 或 Linux 打开会不会有影响 |
    | 必需的运行环境 | 例如要展示的东西需要 Flash，本地没装 Flash 就显示不出来，怎么办 |
    | 测试计划 | 把你要照顾到的所有环境全部都要测一遍 |

    * 前三条决定「要照顾谁」，第四条决定「怎么把这套照顾落到实处」。
    * 浏览器不可能照顾得很周全，只能声明照顾哪几类，比如 `IE6` 就不管了：用 IE6 打开会看到一行提示说检测到版本是 IE6、建议重装新浏览器并给一个链接。
    * 归拢起来客户端要回答三件事：要正常显示与使用需要一个什么样的配置；如果没有这样的配置，怎么检测出来；如果没有，怎么给他解决。
    * > 提示：你做的网站用的浏览器早晚也会过时，照顾哪些、不照顾哪些要做一个规划，而不是等出了问题再说。
    * > 来源: P23

### 3.3 导航分析与评估分析

* **navigation analysis（RNA）要做的四部分活**
    * 分析所有的 `stakeholders`，也就是分类。
    * 分析大概有哪些**数据**、哪些**功能**，这些东西都准备好。
    * 分析它们的 `relationships`（关系）：简单说就是网页跟网页之间怎么跳转、不同种类用户的交互之间有没有互相影响——这一环比较重要。
    * 决定网站浏览的复杂程度，到底有没有必要做什么特别的工具来给导航做辅助。
    * > 来源: P23

* **导航的动机：网站没法训练用户**
    * 非常复杂的普通软件也有导航问题但没这么明显，因为它是给某个固定单位做的，可以训练员工：告诉他你这个角色要做什么、要点哪几个键，训练熟练就好。
    * 网站没办法训练任何人，所以得做得充分傻：要让人随时在里面跑来跑去而不会跑丢——非常容易找到想找的东西；找了一圈想起「我要前面那个」时不至于退不回去、不知道自己在哪、退回首页后死也找不到原来那个东西。
    * > 来源: P23

* **要不要做 map**
    * `navigation` 设计本身后面讲用户界面设计时会专门讲，它有一些特别的技巧；除技巧之外还要决定需不需要一样东西：一个 `map`（地图）。
    * 同一份关系数据，树形结构（首页 → A/B/C → A1/B1）是程序员比较喜欢看的；普通用户、尤其给幼儿园小朋友看的网站要画得像一张真地图（游乐园大门 → 小火车／旋转木马／糖果屋），再在上面准备各种链接跳到想去的地方。
    * 有些 BBS、有些网站做得比较好，可以直接把整个地图调出来，所有分支一目了然。
    * > 来源: P23

    ```text
        树形结构的站点地图                  给小朋友的站点地图

             [首页]                        +------------------+
               |                           |   游乐园大门      |
        +------+------+                    +--------+---------+
        |      |      |                             |
      [A]    [B]    [C]                    +--------+--------+--------+
        |      |                            |        |        |
      [A1]   [B1]                       [小火车]  [旋转木马] [糖果屋]
    ```

* **evaluation analysis 与交付尺度**
    * `evaluation analysis`（评估分析）算的是一笔账：网站做得越友好，说明照顾到的人群越多；但照顾到越多人群，工作量就越大、给自己找的事越多。时间与人力都有限，要估算投入与产出比合算不合算——也就意味着 navigation 做到什么程度就差不多了。
    * > 结论：这些事情在这个 analysis 阶段你最好都做，但没有要求你一定要写一个 100 页的文档出来，通常没有人这么干；但这些事你都要考虑过。
    * > 来源: P23

## 4. 应用设计：目标、分层与设计工具

> **一句话主旨**：给出 Web 应用六条设计目标、四层设计分层，并逐层展开接口、美工、内容与架构、导航、组件级设计的具体规则与工具。

### 4.1 设计目标与设计分层

* **六条设计目标**

    | 目标 | 含义 |
    | :--- | :--- |
    | `simplicity` 简洁 | 尽量简单，不要把事情搞得很复杂 |
    | `consistency` 一致 | 内容、美工、整体架构、界面、导航等各项设计可能交给不同的人、不同的组去做，但从始至终要保持一致 |
    | `identity` 形象认同 | 软件呈现出来的风格要符合这个领域的 `domain image`，符合这个领域给人家固有的形象 |
    | `robustness` 健壮性 | 用户群不可控，容错要求高 |
    | `navigability` 可导航性 | 不需要有人教，用户自己就能在你的系统里跑来跑去，还不会迷路 |
    | `visual appeal` 视觉吸引力 | 网站要做得漂亮，这没什么好说的 |

    * `identity` 的判据：不能弄一个五彩斑斓的银行系统网站；把银行网站做得像幼儿园网站，人家会觉得这个银行靠谱吗。
    * `simplicity` 要接着 `time to market` 一起看：时间很短，所以设计上要尽量简单，把主要的功能完成。
    * > 来源: P24

* **设计时要特别强调的几项特性**
    * `security` 肯定很重要：要在上面跑考试、跑竞赛，就不能被人考试之前进把题目直接拿出来，所以防各种攻击、防黑客是很看重的因素。
    * 大规模并发：做在线评测这类网站，必须考虑好几百人疯狂提交时怎么处理。
    * `availability`：偶尔挂掉可以容忍，三天两头挂掉大家就不来了；`scalability`：一两个人可以弄、一两百人就挂掉，那这个网站不行，你要知道访问量的变化范围。
    * `time to market`：网站一般要求得比较急，只有很短时间，这也意味着设计时要尽量简单、把主要功能完成。
    * > 来源: P24

* **robustness 与 navigability 在 Web 上格外重要的原因**
    * 做 robustness 是要花钱的——要花人力去做，做到什么程度是一个投入的取舍：支付宝那种放到网上给所有人用的系统，与银行内部给柜员用的系统，两者都要 robustness，但要求显然不一样，花的时间也不一样。
    * 银行内部系统可以不用那么 robust：用户群可控，就那么几个人，做完了给内部人员做 `training`，手把手教、告诉他什么键一定不能点错、什么东西在哪里，培训材料还能留给新员工用——所以 robustness 差一点不要紧，navigability 差一点也不要紧，找不到的东西告诉他在哪儿就行。
    * > 结论：`robustness` 跟 `navigability` 在 Web 应用上特别重要，是因为你的用户群不可控。
    * `compatibility` 出于同一道理：用户群不可控，用什么操作系统、什么平台、甚至 IE6 的都可能存在，设计时要照顾到哪些层面的人必须特别注意。
    * > 来源: P24

* **四层设计分层**
    * 越往上的层级越靠近用户，越往下的层级越靠近工程师；顶端是用户，底端是技术（干活的工程师），四层依次是 `interface design`（界面设计／美工设计）、`content design`（内容设计）、`navigation design`（导航设计）、`technology`。
    * > 来源: P24

    ```text
                    用户 (user)
            +---------------------+
            |   interface design   |  界面设计 / 美工设计
            +---------------------+
            |   content design     |  内容设计
            +---------------------+
            |   navigation design  |  导航设计
            +---------------------+
            |     technology       |  (工程师)
            +---------------------+
               工程师 (engineer)
    ```

* **上一环节的教训：先看清要你做的是什么事**
    * 反面实例：用 UML 在 60 多页文档里详细描述了一个 `use case`，把一个用例的流程写得非常详尽，然后就没有然后了——`use case` 在中间只占 8 分左右，加上前面的 `introduction`，后面的分都没有了，因为后面都没做。
    * 需求规格说明书相当于订合同时一份很重要的参考文档，合同里很重要的一点是验收指标：在什么情况下客户会付钱、客户付了钱你要拿出什么东西，一项一项指标要写得非常明确具体；这一项没有，最后赔定了。
    * > 结论：学软件工程不仅是学怎么画图，最重要的是做事情的套路——写需求规格说明书之前，也要先去看这门课对它的要求，这是你这个 project 的需求。
    * > 来源: P24

### 4.2 接口设计

* **页面必须随时能回答的三个问题**
    * `Where am I?` 我现在在哪儿：要让别人很容易知道他不迷路，随时告诉他他在整个系统里处于什么位置；常见做法是页面上有一行「当前位置」式的小字，例如「首页 → 学术机构」，既说明你是通过点「学术机构」打开的，也说明它是首页下面的链接。
    * `What can I do now?` 我在这儿能干嘛：在页面上提供可以点击的东西，并清楚展示有哪些功能可用、哪些链接是活的、哪些内容相关——本质是把每个东西做得像它应该有的样子：按钮像按钮、链接像链接、下拉框像下拉框。
    * `Where have I been? Where am I going?` 我已访问过哪些地方、还可以去哪些地方：最简单的机制是点过的链接变紫色、没点过的蓝色；网站太复杂时能提供一个 `map`（站点地图）更好，而在用这个最有效的办法是：开发网站之前先去找很多相似的网站，看人家是怎么做的。
    * > 来源: P24

* **有效接口的三个特点**
    * 视觉上一目了然而且宽容（`visually apparent and forgiving`），给用户一种掌控感：用户很快看到他有多少选择余地，抓住怎么达到目标、怎么把事做完；同时还要允许他点错、允许他犯错误。设计原则是**把用户当成白痴**——如果白痴都会用，不白痴的用户会用得更舒服；整个设计不能让人猜、不能让人想。
    * `effective interfaces do not concern the user with the inner workings of the system.`：普通软件可以随时提醒「你要不要保存你的修改」，而网站有更高的要求——根本不要提醒他，默默替他存了，而且还得让他在任何时刻可以反悔。
    * `perform a maximum of work while requiring a minimum of information from users.`：让用户做的事情越少越好，用最小的精力完成尽可能多的工作。这条对普通软件也适用，但对 Web 应用特别重要——内部软件让人多点一下是忍一忍就算了，在 internet 上让人多点一下，人家会非常不爽，因为这一下不仅依赖服务器反应速度，还依赖网络速度。
    * > 结论：internet 上的用户起码在计算机专业方面可以想象得多白痴就多白痴，但他也有权利使用——因为你是发布在全世界公开的；如果他很容易就犯了错误，那是你设计得不好；你不想让他破坏的东西，绝对不要给他破坏的机会，根本不要让它出现在你的页面上。
    * 更细的 `design principles and guidelines` 书上有；`control mechanisms` 里最简单的是 `navigation menus`（菜单），此外 `graphic icons`、`graphic images` 也可以作为跳转控制的界面。
    * > 来源: P24

* **接口设计的九步流程**
    * `review analysis model`，然后做 `refinement`。
    * 动手画一个 `rough sketch of the interface layout`：粗略画一下界面整体布局——要不要 `banner`、横着要不要一条功能带、竖着放左还是放右、中间放什么。
    * `Map user objectives into specific interface actions.`：做一一对应，网站给用户提供哪几件事可以完成，每件事对应网页上哪一个链接或按钮。
    * 把点进去之后的那一串动作理出来：例如「我要买东西」，后面还要查看、选择、放到购物车、结账、填信息与银行卡与邮寄地址等，一条一条理出来。
    * 画 `storyboards of screen images for each interface action`（如同拍电影画分镜头），说明界面跟用户交互时屏幕上会出现什么状态。
    * 再 `refine`：这次的精化是根据美工的设计来的。
    * 开始抽取 `interface objects`，然后开始做模型。
    * 画什么图取决于你，因为时间很紧、不要求画非常正式的图；但总要用一种方式描述用户跟 interface 交互的流程，还要有一种东西描述它的行为，即界面使用的动态模型（相当于 `state transition` 状态迁移图之类）。
    * 每一种状态界面长什么样、是什么布局要有一个描述，然后 `refine`、`review`，不断细化。
    * > 来源: P24

### 4.3 美工设计与内容、架构设计

* **美工设计六条规则**
    * `don't be afraid of white space.`：不需要把屏幕所有边边角角填满，留白不是坏事，留白是一种品味；留多少可以商量，但不能全填满。
    * `emphasize content`：不要喧宾夺主——本来要展示一段文字，却做了一个特别 fancy、带 flash 的 banner，结果所有人只记住了那个 flash，网站干嘛的没印象。
    * `Organize layout elements from top-left to bottom-right.`：绝大多数人的阅读习惯是从左上角往右下角看，所以放东西的顺序也从左上往右下分布；存心从右下往左上堆以吸引眼球是另外一说。
    * `Group navigation, content and function geographically within the page.`：跟 navigation 相关、跟内容相关、以及功能按钮，第一页放在什么位置，后面几百个页面里相同功能的东西最好都放在差不多的位置。反面实例是「下一页」按钮在屏幕上来回跳，用户满屏找链接，访问起来很累；页面分给不同人做、风格没统一时尤其容易出现，这是不专业的表现。
    * `don't extend real estate with the scrolling bar.`：特别想炫耀、觉得特别重要的东西最好不要让人一直拉滚动条才看到——不是所有人都有耐心等到最后；哪怕它的位置适合在下面，也可以在前面先放一个提示性的东西和链接让人跳下去。
    * `consider resolution and browser window size` 等等：不同的浏览器、不同的分辨率，做美工设计时都要考虑到。
    * > 来源: P24

* **内容设计与内容架构**
    * `content design` 没有太多好说的：基本上就是用 UML 把跟内容相关的东西抽取出来，设计成一个类（`class`）或一个对象（`object`），然后定义好它们之间的关系。
    * `content architecture`：一个 `content object` 差不多相当于一个 web page，整个网页与网页之间的整体结构有四大种。
    * `linear` 是一条直线往下走；`grid` 是节点按网格排布、横竖都能连；`hierarchical` 层次感非常强、是一棵树；`network` 是结构关系比较复杂的那种。
    * > 来源: P24

    ```text
    linear（线性）          grid（网格）

    [A] -> [B] -> [C]        [A] [B] [C]
                             [D] [E] [F]

    hierarchical（层次）      network（网络）

            [A]                  [A] --- [B]
           /   \                 | \    / |
         [B]   [C]               |   \/   |
         / \     \               |   /\   |
       [D] [E]   [F]            [C] --- [D]
    ```

* **应用架构：MVC**
    * 整体架构（`application architecture`）不像普通软件设计那样从一个数据流图翻译成 `call and return structure`；比较流行的一种设计网站的架构风格叫 `MVC`。
    * `MVC` = `Model View Controller`：把整个系统分层来设计，至少分三层——一个前台、一个后台，中间有一个中转的 `controller`。
    * `Controller` 衔接前台与后台：接受用户从前台输进去的需求，去调用后台的程序、从后台获取数据，再传到前台展示给用户。
    * > 来源: P24

### 4.4 导航设计与组件级设计

* **navigation semantic units（NSU）**
    * 导航有语义与语法两个层面；语义方面的工具叫 `navigation semantic units`（简称 `NSU`，不是 NUS），官方定义是 `a set of information and related navigation structures`。
    * 实操口径：对每一个 `use case`、每一个 `actor` 的行为，去对应一套 NSU。
    * 以网上购买 SafeHome 为例：`actor`（购买者）在首页点 `select room` 这个 navigation link 进入 `room` 页面，在 room 页面上点 `recommend components` 进入推荐的模块，打开 `product component` 产品说明页。
    * > 结论：这张图说明的是用户完成一个目标时要涉及哪几类页面——不是哪几个页面，因为 room 有好多种、不会给每一种都画一张图，room 就是抽象出来的 `content object`，图里说的是涉及哪几个 content object、以及它们之间用什么链接跳转。
    * > 来源: P24

* **可用的导航机制**
    * `individual navigation link` 是最简单普通的机制：做一个链接，文字的、icon 的、按钮的都可以。
    * 水平 `navigation bar` 上放比较重要的几大类功能，建议不要超过 7 个、大概是 4 到 7 个；垂直方向还可以有一个 `navigation column`，不管放左边还是右边，里面可以放基本上所有的 `major content objects`。
    * 为什么横的建议不超过 7 个而竖的可以随便放：关键在于鼠标的滚轮是竖着的，横向一般要在一个屏幕宽度里解决，纵向可以上下滚；即使硬让竖着滚产生横向移动，用户的动作跟看到的东西不一致，感觉也很不好。
    * `tabs` 实际上像很多卡片摞在一起、上面看到卡片的标识，一般不超过 5 个、3 到 5 个页面；此外还有 `site map`，帮助大家随时知道你在哪里。
    * > 来源: P24

    ```text
        +------------------------------------------------+
        | [logo]  A  |  B  |  C  |  D  |  E  |  （4~7 个）  | <- 水平 navigation bar
        +----------+-------------------------------------+
        | F        |                                     |
        | G        |                                     |
        | H        |               内容区                |
        | ...      |                                     |
        | （任意多） |                                     |
        +----------+-------------------------------------+
            ^
            |
            垂直 navigation column：放几乎所有 major content objects
    ```

* **组件级设计的四类模块**
    * `component-level design` 跟普通的组件级设计差不多，只不过对 Web 应用大概把模块分成四大类。
    * 四类分别是：动态生成内容的模块；提供计算功能的模块；做数据库查询功能的模块；跟外部的一些系统做沟通的模块。
    * > 来源: P24

## 5. 质量维度与测试策略

> **一句话主旨**：给出 Web 应用质量度量的九条维度与度量口径、测试的三个特殊难点、设计模型到测试对象的对应关系与先表层后底层的执行顺序。

### 5.1 九条质量维度

* **九条质量维度总表**

    | 维度 | 考察什么 | 在 Web 应用里为什么特殊 |
    | :--- | :--- | :--- |
    | 内容（content） | 信息是否准确、组织是否合理 | 内容本身就是产品的一部分，且更新频繁 |
    | 功能（function） | 功能齐全、稳定 | 与传统软件一致，但依赖网络与远端服务 |
    | 结构（structure） | 整体组织架构、可扩展性 | 站点会长大，架构必须撑得住 |
    | 可用性（usability） | 界面能否被自主学习、自主走通 | 用户分散，没有统一培训的机会 |
    | 可导航性（navigability） | 用户能否凭想象走通路径 | 页面之间靠链接导航，路径不唯一 |
    | 性能（performance） | 响应效率 | 受网络与并发流量直接影响 |
    | 兼容性（compatibility） | 对不同客户端环境的适配 | 客户端环境千奇百怪，不可控 |
    | 互操作性（interoperability） | 与其它软件、数据库的交互 | Web 应用天然是集成体 |
    | 安全性（security） | 数据与资金安全 | 开放网络，攻击面大 |

    * > 来源: P25

* **可用性的定义与度量口径**
    * > 定义：Web 应用的可用性强调的是 *each actor can learn and apply all required navigation syntax and semantics of the interface*——每一个参与者都能自己学会、并且用上界面所要求的全部导航语法与语义。
    * 与传统软件的含义并不一样：传统软件里说可用性常常讲「在多大程度上能用」，跟 `availability` 那种意思连在一起，比如一年不许宕机超过多少分钟、多少小时。
    * 为什么要紧：用户群是分散的，没有机会把他们集中起来做统一培训；走不通就是可用性问题，不是用户笨。
    * > 来源: P25

* **功能与结构两条的测试口径**
    * 功能测试既要管「正确」，也要管「稳定」，还要管「合规」：看它的不稳定程度有多大，是否符合业内标准——用 Java、用 JSP 写，就要拿这些技术自己的标准去衡量。
    * 结构测试关心能否把内容准确地表达出来、能不能扩展，以及在推出新内容的时候能不能顺畅地推进去——结构不只是摆得下今天的内容，还要摆得下以后的内容。
    * > 来源: P25, P27

* **性能与兼容性两条的测试口径**
    * 性能测试测的是**规定条件**下系统的表现：服务器端、客户端的各种配置、硬件配置、浏览器配置都是「规定条件」的一部分；此外还要验证它在特殊和突发情况下的反应速度，比如访问量一下子变得很大还能不能撑住。
    * 兼容性测试各个端、各种情况都要测：客户端和服务器端都要测，看它们彼此兼容不兼容；最突出的问题是**浏览器**——IE、火狐、Netscape 都要验证一遍。
    * > 来源: P25, P27

* **互操作性与安全性两条的测试口径**
    * 互操作性测试针对 Web 应用的另一面：它除了访问界面，往往还要跟大型数据库打交道、去访问里面的数据——界面之外还有界面，访问其他应用、访问数据库的这个界面有没有问题就属于互操作性。
    * 安全性测试找的是系统可能存在的弱点、或者叫它的**易攻性**，防范的对象是黑客；设计的时候就得先把「哪里容易被攻击」找出来，尽早处理掉，安全隐患要消灭在前端。
    * > 来源: P25, P27

* **九条中真正需要盯住的是哪几条**
    * 内容要好、功能要齐全稳定、结构要有充分可扩展性，这些凭直觉就能列出来；真正需要盯住的是后面几条：可用性、可导航性、兼容性、互操作性——它们是 Web 应用**特有**的考核点，也是测试策略要专门安排步骤的地方。
    * > 提示：这九条是写在 slide 上的 `dimensions of quality`；仔细说的话每一条都有 Web 应用特别的地方，所以最难的那道讨论题从九条里挑任何一条来答都不会错题——关键不在选题，在于能不能把「为什么这条特别难」讲到细节上。
    * > 来源: P25

### 5.2 测试的三个难点

* **配置测试：错误现象不等于错误本身**
    * 测试和维护团队最头痛的是 `configuration` 这一块：在客户端发现一个错误，它表现出来的**现象并不一定是那个错误本身**，很大可能是用户那边的系统配置引起的。
    * 用户说「我在我的机器上做了某个操作，然后就出现了某个现象」，而你回到自己的机器上重现不了。
    * > 结论：error 几乎不可能脱离它所在的运行环境被重现——*it's almost impossible to reproduce the error outside the environment*；那台机器以外，任何一台别的机器都不行，这事就只在他那台机器上是这样。
    * 手里没有可复现的最小环境，于是 `configuration testing` 成了整个测试里最费劲、最难做的一块。
    * > 来源: P25

* **症状出现的地方不一定是问题所在的地方**
    * 用户进入某个页面出来很慢，很可能不是服务器算得慢，而是他这一端自己在算、在帮自己做别的事情，问题根本不在服务器上。
    * 测试里最基本的判断纪律是先分清「哪里痛」和「哪里病」——症状在客户端，根因可能在服务器端，也可能在网络通信上。
    * > 来源: P27

* **三层结构下的定位困难**
    * 设计的时候分了层，有客户端、有服务端，中间还有网络，所以 debug 时非常难找：这个 bug 到底发生在哪一层。
    * 错误有可能出在客户端、服务器端、网络通信端这三层中的任何一层，出了问题要仔细甄别究竟在哪一层。
    * > 结论：`environment` 在 Web 应用测试里扮演一个非常重要的角色，这也是为什么质量维度里兼容性、性能、安全性会被单独拎出来。
    * > 来源: P25, P27

* **静态与动态两种操作环境**
    * 再往细分还要看错误跟哪一类操作环境有关：静态的操作环境（比如跟配置有关的那些），以及动态的操作环境（比如瞬时的资源超载）。
    * 动态环境的典型例子：中国好声音刚开播那会儿，很多人同时去访问某些网站，访问量一下子上去就超载了；在这种时候出现的错误就属于动态操作环境带来的错误。
    * 配置本身也分两种：静态配置可能直接引起错误；动态配置在瞬间流量特别大时也会产生一些很诡异的错误。
    * 传统软件测试的条件是完全可以控制的；Web 应用即使完全再现原来的操作，要把当时的环境也精确复原是非常难的。很多错误往往由配置引起，不同的配置会引出不同的错误信息。
    * > 来源: P25, P27

### 5.3 设计模型到测试对象的对应与执行顺序

* **测试对着设计模型走**
    * 内容方面的问题要用 `content model` 来查，也就是说 `content model` 肯定是要用的。
    * `interface model` 也是要用的，用它检查是不是所有的 use case 都能按这个界面模型走通；`design model` 主要用来检查**导航**方面的问题。
    * 用户界面要做一次整体的测试；功能模块 `functional components` 要做单元测试（`unit testing`）；整个系统架构的导航要很仔细地测过。
    * > 来源: P25

* **做一层测试往往不只取一个 model**
    * 测 interface 不能只要一个 `interface design model`：`interface design` 和 `aesthetic design` 这两件事是一起做的，测的时候起码这两个是一个整体。
    * 测 navigation 时 `navigation design` 肯定要，但要做真正好的 navigation testing，还必须知道整个系统的架构——手里得先有一个整体的架构观念，才谈得上去做导航测试；所以 navigation model 之外，架构那一层也要拿过来。
    * 再往下是 component testing，这个肯定是取 `component design` 这个 model。
    * > 来源: P25

* **先表层、后底层**
    * 内容测试 → 界面测试 → 构件级测试这一路测的是**表层**的东西；表层测完才进入底层特性的测试——那些跟 `technology` 直接相关的部分，包括 `configuration`、`performance`、`security`。
    * 测试的顺序是从上往下测的，也就是从最接近用户的那一层，逐步走向最接近底层技术的那一层。
    * > 来源: P25

* **Web 应用特有的测试步骤**
    * 有几个 Web 应用基本上**特有**的测试步骤要专门测：一是 `configuration`，二是 `compatibility`，然后还有 `security`、`performance`。
    * > 来源: P25

* **上线之前的内部公测**
    * 做完技术测试不能直接挂到网上——真的一挂上去就 crash 掉，大家就再也不回来找你了。
    * 正式上线之前还要有一次**内部公测**：在一个人数可控的环境里，选一部分最终用户（`end user`），对整个系统做一次黑盒测试。
    * 三件事的全部就是：选用户、控环境、整体黑盒；网游、ZOJ 这类在线评测系统正式上线之前都会先叫集训队的人去虐一下。
    * > 来源: P25

* **一句话总策略：你说的每一个形容词都要有根据**
    * 性能测试的产出不是一个形容词，而是一组能指到具体数字的证据——在多大的并发、多大的数据流量、什么样的操作复杂度下，测出的响应时间是多少；越过哪个点以后，系统的表现开始不能忍。
    * > 易错点：号称可以支持很大的并发量，最后一章测试却只测了 10 个并发，这不叫测完了并发——你凭什么证明你说你号称可以什么什么。
    * > 来源: P26

* **整体测试策略的九步**
    * 对**内容模型**进行检查，看 Web 应用的内容本身，找出内容错误。
    * 对**模型**仔细审查，看是不是所有的用例都能完成——如果全部用例都能完成，基本上问题就不大了。
    * 对**体系模型**仔细审查，找出导航方面的错误；对**用户界面**进行测试，找出展示方面的错误与导航机制上的问题。
    * 对我们选拔出来的一系列**功能构件**做单元测试（导航语义单元 NSU 就是这样的构件），对子系统做操作性测试——这一层跟平常说的单元测试类似。
    * 让 Web 应用在**不同的环境配置**下跑一遍，测它对每种配置的兼容性；再做**安全测试**（在每种环境下找出容易受攻击的地方和攻击点，把隐患消灭在前端）与**性能测试**（看它在不同负载下、在很多用户登录的情况下，性能有没有受到严重影响）。
    * 除了这些技术性的测试，还有一个最好用的办法：把**最终用户**直接请进来，找志愿者过来真的去用、去体验，先做这样一轮测试——技术上测得再细，也替代不了真实用户的这一次体验。
    * > 来源: P27

* **测试项挂在设计产物上的金字塔**
    * 从技术层面看，这整套测试是个**金字塔**：最底下是我们具体的实现技术，最顶上是最终用户。
    * 内容测试对内容设计；界面测试对界面设计加美工设计；导航测试对导航设计加系统构架设计；构件测试对构件设计（含单元测试）。上面再综合出三类测试：**配置测试、性能测试、安全测试**。
    * > 来源: P27

    ```text
                最终用户（直接可用的方式：志愿者试用）
                  ▲
       内容设计 ──► 内容测试
       界面设计 ──► 界面测试        （界面测试与界面设计、美工设计息息相关）
       美工设计 ──┘
       导航设计 ──► 导航测试
       系统构架设计 ►              （导航测试与导航设计、系统构架设计紧密相关）
       构件设计 ──► 构件测试（含单元测试）
                  ▲
            具体实现技术
    ```

## 6. 逐层测试流程

> **一句话主旨**：按先表层后底层的顺序拆开内容测试、数据库交互分层、界面测试、构件级测试与可用性测试的具体对象、策略与评判口径。

### 6.1 内容测试与数据库交互分层

* **内容测试的三个目标**
    * 发现**语法上的错误**：最典型的就是 `typo`（打字打错、拼写拼错），围绕文档、图的表示以及其它各种表示都要看有没有语法错误。
    * 发现**语义上的错误**：语义错通常表现为精细度不够、信息完整程度不够；语义准确了，用户导航时才能精确导航，不会出现模棱两可的说法，也不会引起误导、引起误解。
    * 发现**结构上的错误**：结构对了，内容才能井井有条地展现给最终用户，看起来才合理。
    * > 来源: P27

* **语义准确，尤其是政治上的准确**
    * 内容测试分语法与语义两块：语法这一层问「你写对了没有」——拼写有没有错、链接有没有错；语义这一层问「你表达准确了没有」，这两个不是一回事，拼写全对的一段话照样可以把意思说反。
    * 语义上最要紧的一类，是**政治上**的准确：同样一件事情的表述，哪怕只是一点细微的差别，都可能造成不允许的后果；所以内容在政治上必须没有歧义，别人一看就知道你要表达的意思，不能有第二种理解。
    * 另一个语义实例：给学院做的网站上有学院介绍，而你拿的是**十年前的介绍**——这段文字每个字都对，但它是错的。
    * > 来源: P25, P27

* **内容的组织与结构**
    * 除了语法与语义，还有一层是内容的**组织和结构**：哪些内容跟哪些内容放在一起出现、哪些先出现、哪些后出现，这种组织顺序、结构是不是正确，也是要测的内容。
    * > 来源: P25

* **数据库测试为什么最复杂、最难测**
    * 第一，客户端那边的原始需求很少会被直接展示出来：用的是 `SQL（Structured Query Language，结构化查询语言）`，从 `数据库管理系统（Database Management System，DBMS）` 开始往往还要做相应的转化和翻译。
    * 第二，数据库有时候是很遥远的、是**远端**的：对 Web 应用的服务器来说，这就需要由服务器之间来进行查询。
    * 第三，绝大多数数据必须先到 Web 应用的服务器上才能展现给客户端；到了这一步，原始数据往往还要做排版转换、格式化和格式化展现。
    * 第四，**动态内容**还要跨对象做格式转换，转换完才适合展现，这里就牵涉到格式化和兼容性的问题。
    * > 易错点：不要以为「测数据库」就是拿 SQL 去打一遍库——用户的一次查询在到达数据库之前和离开数据库之后，还有好几道转换要过，每一道都在你负责的范围里。
    * > 来源: P25, P27

* **数据库交互的五层转换与返回路径**
    * 请求侧：第一层 interface layer 取得界面上提交的 HTML scripts；第二层 web app server layer 从 scripts 中把 user data 抽取出来；第三层 format layer 把抽取出的数据转换成规定的 format；第四层转换成 SQL 语句；第五层 database 交互层对数据库执行操作、取回 raw data。
    * 补充环节：这个 database 可能并不在你这个 server 上，所以 server 和 server 之间还有一个 `communication` 的问题。
    * 返回路径：`raw data` → Web 应用服务器 → `proper format for display`（转换成可展示的格式）→ 用户 interface（转换成用户可以理解的方式）→ 显示在屏幕上。
    * 做法上就对 database interaction 做**分层**处理（`layers of interaction`），把交互拆成层，然后**对每一层去设计相应的测试方法**；按书上的建议可以分成五层，每一层做每一层的处理。
    * > 结论：我们需要为每一层各写一份 testing plan，这是 `content testing` 里比较麻烦的部分。
    * > 来源: P25

    ```text
    第一层  interface layer
            取得界面上提交的 HTML scripts
       |
       v
    第二层  web app server layer
            从 scripts 中把 user data 抽取出来
       |
       v
    第三层  format layer
            把抽取出的数据转换成规定的 format
       |
       v
    第四层  SQL 转换
            转换成 SQL 语句
       |
       v
    第五层  database 交互层
            对数据库执行操作，取回 raw data
       |
       v
    返回路径   raw data -> Web 应用服务器 -> proper format for display
              -> 用户 interface -> 显示在屏幕上（两层之间含 server 间 communication）
    ```

* **数据库测试的六层结构**
    * 自下而上：数据库（底层数据存储）→ 数据存取层（数据的存取访问）→ SQL 访问层（通过 SQL 访问元数据）→ 服务器层（数据管理与转换）→ 服务器层（Web Apps + HTML／脚本）→ 客户端（用户界面最终展现）。
    * 数据从底层的数据库出发，先经过存取访问，再用 SQL 访问元数据，到服务器层做数据管理与转换，最后由 Web 应用通过 HTML 和脚本送到客户端界面上展现出来。
    * > 提示：数据库测试一般不单独进行，而是跟单元测试合在一起做。
    * > 来源: P27

    ```text
    +--------------------------------------------+
    |  客户端：用户界面最终展现                  |
    +--------------------------------------------+
    |  服务器层：Web Apps + HTML / 脚本          |
    +--------------------------------------------+
    |  服务器层：数据管理与转换                  |
    +--------------------------------------------+
    |  SQL 访问层：通过 SQL 访问元数据           |
    +--------------------------------------------+
    |  数据存取层：数据的存取访问                |
    +--------------------------------------------+
    |  数据库：底层数据存储                      |
    +--------------------------------------------+
    ```

### 6.2 界面测试

* **界面测试的对象与目标**
    * 界面测试的重点是先测**每一个不同的 `interface mechanism`**：界面上各种不同种类的东西——链接、按钮、表单（`form`）、表格、弹出窗口（`pop-up window`）等，每一个这样的东西叫做一个 interface mechanism。
    * 要针对每一种不同的机制设计与之相对应的、不同的测试；因为这些机制存在的目的是实现导航、实现某些功能、实现某些内容的展示。
    * > 结论：测试的目标是这些机制是不是**正确**地实现了它应该实现的功能，在**语义**上是不是正确。
    * > 来源: P25

* **界面机制清单**
    * 链接、表格、按钮、表单（`form`）、`pop-up window`（弹出框）、`cookie`（如果用了 cookie 的话），以及其它七七八八的东西。
    * 服务端和客户端的脚本、动态 HTML、`CGI` 脚本（`Common Gateway Interface`，公共网关接口，是 Web 上应用的一个程序）、动态的链路（流动的链路）也在测试范围内。
    * 这些东西承担的目的各不相同——有的为实现导航，有的为实现功能，有的为实现内容的 display；目的不同，**测法就不同**，不能拿一套测链接的办法去测表单。
    * > 来源: P25, P27

* **购物车是典型的特殊界面机制**
    * 购物车能装的最小数量是多少、最大是多少要测。
    * 一件东西都没选就直接去打结账，它会不会给你算出一个金额——如果算出来了，那显然是错的。
    * 超过它最大的容量会怎么样，也要测。
    * > 来源: P27

* **界面测试的三件策略**
    * 第一件，先看整体的 `interface features`：是不是符合讲 interface design 时讲过的一系列界面设计原则、有没有违背其中哪几条；再从美工角度整体看——表格的 `table size`、行间距是否合适、边框边距留出的空白距离是否好看、整体看上去是否舒服。这是**第一眼**的测试。
    * 第二件，`unit testing`：把每一种 mechanism 做一个局部的测试，比如要交表格，那每一种表格都得测一遍；这一层跟普通测试里的单元测试类似。
    * 第三件，整合测试：相当于把每一个 use case、或者 use case 所对应的那套 `NSU` 整体走一遍——这里实际上是 **NSU 更管用一点**。
    * `validation testing`：把某些 use case 或者 NSU、或者把一些模型组合在一起，把整个 interface 走一遍，看它是不是正确的，有点像最后的黑盒测试、功能验证性的测试；这时检查的是整个 interface 的语义，也就是它的意义是不是被正确地实现了。
    * 最后还有一项 Web 应用特有的：必须对各种不同的环境做 `compatibility` 测试。
    * > 来源: P25

* **NSU 与 use case 的差别**
    * > 定义：`NSU` = `Navigation Semantic Unit`，导航语义单元；`N` 是 navigation，`S` 是 semantic，`U` 是 unit。
    * 它长得和 use case 很像：旁边也有一个小人、有一个 actor；它描述的是这个 actor 根据一个 use case 要完成一件事情，过程中间要经历哪些页面——点哪个链接进入什么页面，再点哪个链接进入什么页面，最后在那个页面上做什么操作。
    * 差别在于：use case 只说明 actor 要完成的一件事（描述「要做什么」），NSU 把它展开成一串页面与链接构成的走法（描述「要一个页面一个页面地怎么走」），一个 use case 对应一套 NSU。
    * 界面这一层的测试是把前面讲过的那些单元拉过来用：单元测试界面机制（NSU 就是一个完整的机制，比如一个购物流程、一个订单流程，就按这个单元去测）；模仿用户的操作，看每种机制是不是都对；测试特殊的用户种类（有点像整合测试）；对整体界面做测试，测界面的一致性，这时不能再只挑一些用例或只看语义单元（有点像确认测试）。
    * 界面还要在不同环境下测：不同的浏览器（以前用得最多的是 IE，现在浏览器越来越多）、服务器端和数据库那边也要看兼容性——这其实就相当于配置测试。
    * > 来源: P25, P27

    ```text
            use case                      NSU
         +-----------+          +---------------------------------------+
         |  (actor)  |          | (actor) --页面1--链接--> 页面2         |
         |   ~~~~~   |          |            --链接--> 页面3            |
         +-----------+          |            --在页面3上做某个操作-->   |
                                +---------------------------------------+
           描述"要做什么"           描述"要一个页面一个页面地怎么走"
    ```

* **界面测试为什么必须认真做**
    * 界面测试的目的是在界面的层面上发现**显示上的错误**；要保证界面在实现上、在语义上、在导航和功能上、在内容展现上都不出错。
    * 还要测界面的**特征**：设计的美感、媒介上的讲究，以及相关的设计内容——Web 应用跟传统软件不一样的地方就在这里：它主要以展示内容为主，而视觉的东西一定要有**吸引力**。
    * > 结论：视觉上没有吸引力，用户很快就走掉了，不愿意再来浏览；这就是界面测试要认真做的原因。
    * > 来源: P27

### 6.3 构件级测试

* **构件级测试**
    * `component-level testing` 跟普通软件没有太大的区别，主要是基于功能的；基于功能点的测试有黑盒测试、白盒测试，这些都是有的。
    * 有一点要特别记住：`Web app` 一般都是以数据库为中心的，所以 `database testing` 通常跟功能是在一起测的。
    * 构件水平的测试，注意力集中在发现功能方面的错误和漏洞上；传统软件测试方法在这里可以用——黑盒法和白盒法都可以，设计得好的测试用例同样能拿来用。
    * > 来源: P26, P27

* **整体策略中构件测试的位置**
    * 对我们选拔出来的一系列**功能构件**做单元测试（`unit testing`）；前面讲过的**导航语义单元（Navigation Semantic Unit，NSU）**就是这样的构件，对子系统做操作性测试，看有没有错误——这一层跟我们平常说的单元测试类似。
    * 这一层测完就进入底层特性的测试，也就是跟 `technology` 直接相关的配置、性能与安全测试。
    * > 来源: P27

* **可用性测试的执行者是谁**
    * > 定义：`usability test` 是 `designed by you, the web engineering team`（由你和你的 Web 工程团队设计），而执行（`executed`）是由 `end users`（最终用户）来完成的——设计的责任在你，操作的责任在用户。
    * 它跟一般说的可用性定义稍微有点不同，差别在执行者：主要测的是你**不认识的这帮人、你不可控制的这些人**，能不能自己就会用你这个 interface。
    * 所以执行过程基本上不是由你这个团队自己人来做的：要找一个用户群，或者从各种用户群里找几个有代表性的，让他们过来用一下。
    * > 来源: P26

* **可用性测试的三步执行**
    * 第一步，定义清楚具体要测的东西：`usability` 只是一个词，它其实代表了很多词、很多 abilities，不能拿着这一个词去测，得先划分这次打算测哪几个目标（`identify goals of each`）。
    * 第二步，对每一种要测的目标设计 `test cases`，并且设计一种测试方式使得它能够被 `evaluated`；后面每一个特性都要设计一个指标来证明它是好还是不好——什么叫好、什么叫不好，必须有一个很明确的测试方法。
    * 第三步，选择相应的用户群来做测试，他们做的时候你还要在旁边看着：做一些帮助、做一些指导，同时看他们接受的程度怎么样。
    * > 易错点：不能说「我就把它用了一下，觉得不是很好，要打分的话我给你打 60 分」——你凭什么打的 60 分、这个 60 分是哪儿来的、有人说 61 分不可以吗；这种没有指标的打分站不住脚。
    * > 来源: P26

* **可用性目标清单**
    * 交互性（`interactivity`）：交互做得好还是坏，你怎么判断。
    * 布局（`layout`）：所有东西展示出来，人家是不是好理解。可读性（`readability`）：字体（`font`）、大小、颜色，别人能不能看清——这一条很容易被忽略，字色与背景色几乎混为一谈时，屏幕稍微不够亮大家就看不到了。
    * 美工：整个看上去够不够舒服。展示特性（`display characteristics`）：展示的时候它的一些特性。
    * 时间敏感性（`time sensitivity`）：有什么东西响应很慢、有什么东西对响应速度特别敏感——点一下多久有反应，时间太长用户肯定不满意。
    * 个性化（`personalization`）：对不同用户人群有没有特别的定制。可访问性（`accessibility`）：有没有考虑到残疾人、各种有障碍的人怎么用你这个软件。
    * 到底看重哪几个取决于你开发的是个什么东西，所以要先制定一个目标。
    * > 来源: P26

* **把「可交互性」变成可评判的测试**
    * 例：一套鼠标单点手势交互的毕业论文，写完实现之后要证明「我这个手势要比普通的鼠标点菜单更好用」，所以要设计一系列测试。
    * 设计口径：找几位同学过来，先把任务讲清楚；让他用传统鼠标点选方式完成这些任务，你在旁边掐表记时间；再教他这套手势、用同样任务再做一遍，再掐表看时间。
    * 一次还不行，还得有一个**学习曲线**：让他把任务重复做多少次，然后看时间的变化。
    * 除此之外还有调查问卷：用完以后让他主观描述哪些方面好用、哪些不好用——这就是一个主观的评判。
    * > 来源: P26

* **可用性测试的补充要求**
    * 可用性不是「看起来还行」，它要求每个目标都能被评估，评估结果才能拿去改进——这条最容易被忽略。
    * 可用性测试还必须支持**参与者测试**：参与测试的人是可控的，但你要先教会他们怎么跟这个 Web 应用交互、怎么走完测试过程。
    * 最好再开发一套**自动化的评估机制**，去评估 Web 应用的这个「流」，做**定量评估**。
    * > 来源: P27

## 7. 配置、安全与性能测试

> **一句话主旨**：拆开配置测试的服务端与客户端清单、安全测试的三层弱点，并给出负载与压力测试的分界、吞吐量公式与容纳上限的边界测法。

### 7.1 配置测试

* **配置测试要测两个方面**
    * `configuration testing` 是比较头痛的一件事情，通常要测两个方面：一个是 `server-side`（服务端），一个是 `client-side`（客户端）。
    * 两边要检查的东西完全不同；客户端这边的配置组合是乘法关系——几种操作系统 × 几种浏览器 × 有没有插件，很快就爆炸，所以要先想清楚哪几种组合是你的用户群里真正有代表性、真正需要保证的。
    * > 来源: P26

    ```text
    服务器端配置测试
    ├─ 与服务器操作系统的兼容性
    ├─ 文件 / 目录 / 系统数据库能否正常创建
    ├─ 安全：防火墙与加密（安全性 vs 性能）
    ├─ 分布式服务器部署的全盘考虑
    ├─ 与数据库软件的整合、数据库版本与平台差异
    ├─ 服务器端脚本能否正确运行
    ├─ 管理员误操作的影响
    └─ 代理服务器（Proxy Server）配置差异

    客户端配置测试
    ├─ 硬件：CPU / 显卡 GPU / 内存 / 媒体播放器 / 打印机
    ├─ 操作系统：Microsoft Windows / Linux / Mac OS / Android
    ├─ 浏览器：IE / Mozilla / Netscape / iPad 等各种屏幕
    ├─ 界面构件：ActiveX / Java applet
    ├─ 插件：QuickTime / RealPlayer
    └─ 网络接入设备：cable / DSL / 调制解调器 / T1
    ```

* **服务端要操心的内容**
    * 操作系统的**版本**一定是要看一下的，这里版本问题很多；`database` 也是版本问题——你跟你的数据库有没有版本问题。
    * **依赖项**：装完了不是就能用了，你在依赖上有没有问题；系统的**文件、目录**以及相关的系统数据库，在运行的时候能不能被正常、适当地创建出来，这是最基本的问题。
    * `security`：防火墙有没有配错、装的防火墙会不会影响响应速度、对系统的使用到底会有多大的影响；上了防火墙、做了加密安全性当然提高了，但要同时看**性能会不会明显降低**。
    * 如果涉及**分布式系统**，那个分布式的环境要测过——Web 应用往往跑在分布式服务器上，大的 Web 应用更是如此，这时配置有没有全盘考虑过。
    * 有没有跟**数据库软件**很好地整合在一起，因为数据访问本身就是个问题；面对不同的数据库版本和平台会不会出现奇奇怪怪的情况——对某个版本支持得很好，换个平台就出状况。
    * 你服务端的 `server-side scripts`（服务器端脚本）肯定也是要测一下的，看它能不能正确运行。
    * 还有一点很容易被忽略：如果有一个 `administrator`（管理员）这个角色，他通常权限比较多、比较高，可以干很多事，那么他干了坏事以后会怎么样。
    * 用到了代理的话，代理的 `configuration` 也要相应地做一个测试；用了 `Proxy Server` 和不用代理服务器，在同一个站点上的配置有没有区别也要看。
    * > 提示：必须假设这个 administrator 是友好用户，所以在安全防范方面对他会弱很多、他的权限会大很多；但正因为如此，他一旦误操作会对系统产生什么样的后果，这是要考虑的——他不见得是恶意干坏事。
    * > 来源: P26, P27

* **客户端要操心的内容**
    * 硬件方面：不同的客户群用的硬件可能不一样——`CPU`、`memory`（还有现在常说的图形显卡 GPU）、媒体播放器；网游里很直观，要能玩我这个网游，他的显卡得是什么以上的，显卡不够就是玩不了。
    * 容易出差错的是 `printing devices`（打印设备）：如果需要有打印功能，是不是能够正确地设置这个打印，也是一个要操心的问题。
    * 软件环境：客户端的操作系统（`Microsoft Windows`、开源的 `Linux`、苹果的 `Mac OS`、手机上的 `Android` 等）各种都最好去试一下；各种浏览器（`browser`）；`user interface components`（用户界面构件），比如 `ActiveX`、`Java applet`。
    * 如果你的 Web 应用做得比较 `fancy`（花哨），是不是还用到**插件**（比如 `QuickTime`、`RealPlayer` 这些播放器）：还需要什么样的插件、如果他没有你是不是还要给他一个安装文件。
    * 还有 `connectivity`：要测试一下网络连接的问题，也就是**网络接入设备**这一路——cable、DSL、调制解调器（常说的「猫」）、T1 等。
    * > 易错点：不能只在 IE 上、只在一块屏幕上试过就说过关了——IE 能行不代表别的浏览器能行，桌面能行不代表别的屏幕能行（加上移动端的 iPad 这类设备，屏幕种类越来越多）。
    * > 来源: P26, P27

* **网络接入设备的几个具体数字**
    * 调制解调器：传输速率大概 **56K**。
    * T1：在美国它的标准是 **1.544 兆**，在欧洲是 **2.048 兆**。
    * 更大的还有 T2、T3：T3 能承担的带宽是 T1 的 **44.28 倍**，可以达到 **42 兆**左右。
    * `DSL` 的全称是**数字用户线（Digital Subscriber Line，DSL）**，它下面还有 HDSL、SDSL、ADSL、VDSL 等等，这些都是电信和各种运营商提供的，属于电信网。
    * > 来源: P27

### 7.2 安全测试

* **安全测试的三个环节**
    * `security testing` 基本上就关心三个环节的 `vulnerability`（脆弱点）——它的弱点了，它在哪些方面最薄弱、最薄弱环节在哪里：客户端、服务器端，还有网络。
    * 三个环节就是安全测试的三个落点：客户端这一列是最容易出错的地方，服务器端那一列则是攻击最集中的地方，中间的网络环节本身也是要单独测的一段。
    * 做 Web 应用时得先看清它可能的**攻击性**——哪些地方会被人下手。
    * > 来源: P26, P27

    ```text
        +-------------+        +-------------+        +-------------+
        | client-side | -----> |   network   | -----> | server-side |
        |  (客户端)   |        |   (网络)    |        | (服务器端)  |
        +-------------+        +-------------+        +-------------+
         浏览器缺陷              链路与传输             DoS 攻击
         邮件系统                  安全                  恶意脚本攻击
         QQ / MSN 等
         communication software
    ```

* **客户端与服务器端的攻击面**
    * 客户端的攻击通常是**预先存在于**浏览器、e-mail 等程序或者通信程序（QQ、MSN 这类 `communication software`）当中的那些欺诈程序；办法是把它们查找出来，看是不是真的存在这种跟踪，一旦查出来有漏洞就得想办法弥补。
    * 在客户端最容易出错的就是它用的浏览器——大家说不要用 `IE6` 了，因为它本身有很多缺陷，有一些是致命的缺陷。
    * 服务器端面临的攻击包括：**拒绝访问的攻击**（`DoS`，让你访问不了）；**恶意脚本（`malicious script`）**，从客户端传过去，用来让我们服务器上的操作泄露出来，甚至让它任意运行。
    * 要测的是：你在多大程度上可以防御这些对服务器端的攻击。
    * > 提示：这些漏洞一旦落到真实环境里，Web 应用可能出现非常大的隐患，给用户造成非常大的损失；所以做安全测试，就是自己先模拟黑客的手段去攻一攻。
    * > 来源: P26, P27

* **两类具体攻击情形**
    * 移动终端被植入木马，木马能够监听、截获，甚至调用虚拟键盘上的信息——用户输入的账号密码就这样被截走了；所以终端上应该做**反监听**机制，测试时要做的事就是看能不能截获到那个输入的账号密码。
    * 客户端与服务器之间用 `GET` 传指令、取信息：`GET` 的内容会显示在 URL 上，上面的变量名是能看到的；有经验的黑客会去修改上面的参数，从而拿到本来受限的文件，包括其他用户的隐私，这就会危害服务器的安全；这类问题从缓冲区溢出的角度也能解释。
    * > 来源: P27

### 7.3 性能测试：负载、压力与吞吐量

* **性能测试为什么最头痛**
    * Web 应用最头痛的其实就两件事情：一件是**配置环境**（查错、改错什么都很麻烦）；另一件就是 `performance`——你的 `real-world loading`（真实负载），就是你真实使用起来那个流量，你是没法控制的。
    * 既然控制不了，就要对各种流量给系统带来的影响做各种各样的测试；性能测试主要看的就是**负载**：用仿真的办法去模拟真实情况下的负载，特别是负载非常大的那种情况。
    * > 来源: P26, P27

* **性能测试要回答的五个问题**
    * 第一，`Does the server response time degrade to a point where it is noticeable and unacceptable?` 会不会出现在某种情况下服务器的响应速度变得不能忍。
    * 第二，`At what point does performance become unacceptable?` 在什么并发程度、什么数据流量之下服务器的表现就不能忍了——这种时候往往就是并发量上来了，大概上百、上千个请求压过来，系统反应就变得很迟钝。
    * 第三，到底哪些模块是瓶颈，这是要测出来的；还要判断**性能衰竭到底出在哪一部分**，好对症下药——如果是服务器台数太少就增加服务器数量，如果是带宽的原因就去申请带宽更高的服务。
    * 第四，在不同的 `loading conditions`（负载条件）下，测一下大概平均响应时间是什么样子；比如 100 个人访问响应速度怎么样、1 万人呢、100 万人同时访问呢。
    * 第五，如果流量非常大、系统接近崩溃的时候，系统的**安全性**会不会受到影响（这种混乱局面里容易被人混水摸鱼）；同样在这个临界点上，某一部分功能的**可靠性**、或者它产生的**数据的精确性、准确性**，是不是会受到影响。
    * 性能下降还会连带来两件事：安全性可能受影响，以及 Web 应用的**可信度和信任度**可能受影响——负载增加得非常快的时候，用户还信不信它。
    * > 来源: P26, P27

* **在线评测系统上的具体体现**
    * 考场规则最后一条：**如果在最后 10 分钟系统崩溃，我们就不补时，按系统崩溃那个时候它的排名为准**。
    * 系统接近崩溃边缘时会出现两种情况：那个 `time`（运行时间）可能就测不准；最难测的是那个 `memory`，内存使用也是测不准的，会出现各种问题。
    * 崩溃**以后**会怎么办、会怎么样，这就是压力测试要做的事情。
    * > 来源: P26

* **负载测试与压力测试是连续的两步**
    * `load testing`（负载测试）：在正常值的范围内改变 `loading conditions`，看这个 Web 应用以及它的 `server-side environment`（服务器端环境）对不同的流量、访问量是怎么样的反应。
    * `stress testing`（压力测试）：实际上是 load testing 的一个继续——看它的临界点在哪里，然后把它 `push` 过去，看整个系统会怎么样；具体做法是**不停地**加压，持续增加负载量，让系统跑满负荷甚至超过它的极限，看它会不会瘫痪。
    * 两步是连续的：左半段是在正常范围内的 load testing，右半段是越过临界点的 stress testing。
    * > 来源: P26, P27

    ```text
    响应时间
      ^
      |                                          .
      |                                        .
      |                                     ..      <- 接近崩溃
      |                              ......            （time / memory 测不准）
      |                    ........
      |        ..........
      |......
      +--------------------------------------------------> 负载 P
       |<---- load testing ---->|<---- stress testing ---->|
            在正常值范围内                 越过临界点
            改变 loading conditions         把它 push 过去
    ```

* **吞吐量：P = N × T × D**
    * `load testing` 里有一个术语叫 `overall throughput`（总吞吐量），就是 $P$；它由三个元素乘在一起得到，也就暗示了测试时要调控的就是这三个元素：

    $$P = N \times T \times D$$

    * $N$ 是 `the number of concurrent users`（并发量：有多少个用户并发）；$T$ 是每个用户在单位时间里要做的 `transaction`（`online transaction`，在线事务）；$D$ 是每件事情要产生的数据量、数据流量。
    * > 定义：每秒钟有这么多个并发，然后每个并发事件他有这么多个操作，每个操作会产生这么大的数据量，你把它乘到一起，就是每秒钟产生的总的数据量，就是一个 `overall throughput`。
    * 测试时要做的事就是不断改变 $P$ 的值，看系统的响应；$P$ 里有三个因素，就把这三个因素的各种不同排列组合都测一下：可以是非常大的并发量但每个人操作都很简单、产生数据量比较少；也可以是中等规模的并发但其中操作很复杂。
    * 这两种情况下 $P$ 可能差不多，但系统承受的压力完全不同——这就是为什么三个因素要分别调控，而不是只看乘出来的那个总数。
    * > 提示：有一句笑话是，玉米是服务器的最好测试员——你什么时候要抢票的时候你就知道了，谁家的服务器好不好，拿它放到抢票的时候用一下。
    * > 来源: P26

* **另一种吞吐量口径及其算例**
    * 性能测试里的负载测试有一个计算公式，把 $N$ 记为**并发用户的数量**、$T$ 记为**单位用户、单位时间的提交量**（每个用户多久提交一次）、$D$ 记为**每次提交的数据量**，$P$ 是总算下来要扛住的量：

    $$P = \frac{N \times T}{D}$$

    * > 易错点：这一口径与上文 `P = N × T × D` 的写法不一致（一处 $D$ 在分子、一处 $D$ 在分母，且 $T$ 的定义也不同），两处都出自精读长文，备考时按各自出处分别记，不要互相代入。
    * 算例：假设总访问人数按 2 万算，有 2000 个人在提交评论，每个人大概每两分钟提交一次，每次提交的平均数据量是 3K。
    * > 结论：按这个口径算下来，负载量每秒可以达到 500K 以上；如果你的网站做的是体育这一类内容，基本上就必须达到这个标准，达不到用户来一次就不会再来。
    * > 来源: P27

* **容纳上限的边界测试**
    * 如果服务器的容量上限是 1 万个用户，那么同时来 1 万零 1 个、1 万零 2 个，超过这个最大数会怎么样——是直接瘫痪，还是只是变慢，这一定要在交付之前弄清楚。
    * > 来源: P27

* **被低估的三项测试**
    * 导航测试检查导航的语法和语义，其中一项重点工作是**防止死链接**这一类问题：点进去没反应、点进去是空的，都要在这一步抓出来。
    * 互操作性测试针对 Web 应用的另一面：它除了那个访问界面，往往还要跟大型数据库打交道、去访问里面的数据，界面之外的访问界面有没有问题就属于互操作性。
    * 安全性测试找的是系统可能存在的弱点或者易攻性，防范的对象是黑客。
    * > 来源: P27

## 8. 导航测试与可用性测试

> **一句话主旨**：补齐导航测试的语法元件、重定向的定义与处理办法，以及可用性测试由谁执行、测哪些目标、指标怎么设计。

### 8.1 导航测试

* **导航测试的两个方向**
    * `navigation testing` 主要测两个方面：一个是导航的**语法**，一个是导航的**语义**，是不是正确。
    * 语法要测的有六样：`links`（链接）、`redirects`（重定向）、`bookmarks`（书签）、`frame` 与 `frame sets`（框架与框架集）、`site map`（站点地图，如果有的话）、`internal search engines`（内部搜索引擎，如果有的话）——每一个都有它要测的几个点。
    * 语义方面也有一系列要测的东西：书上 20.6.2 节列了一系列 `testing questions`，设计 `test cases` 时要确保你的 case 能够覆盖、能够正确回答这一系列问题。
    * > 来源: P26, P27

* **重定向必须会处理**
    * > 定义：重定向是指网页原来的地址被删掉了、不再更新了，或者已经取消掉了，这时要给它一个去处。
    * 处理办法一般是给用户一个明确的指示：告诉他这个网页已经不存在、已经拆除，然后建议他按任意键回到主页——这是最常见的做法。
    * 除了断链和重定向，书签、框架或者框架集这一类结构也容易出错；网站地图（导航地图）和站内搜索引擎同样在测试范围里。
    * > 来源: P27

* **导航测试在整体策略中的位置**
    * 对**体系模型**仔细审查，找出导航方面的错误——比如有没有死档、有没有点不进去的死链接；对**用户界面**进行测试，找出展示方面的错误、内容展示方面的错误，以及导航机制上的问题。
    * 通过系统架构的**导航系统**也要测试一遍。
    * 导航测试与导航设计、系统构架设计紧密相关：测试项都挂在它对应的设计产物上。
    * > 来源: P27

### 8.2 可用性测试的设计与执行

* **可用性测试由谁设计、由谁执行**
    * > 定义：`usability test` 是 `designed by you, the web engineering team`（由你和你的 Web 工程团队设计），而执行（`executed`）是由 `end users`（最终用户）来完成的——设计的责任在你，操作的责任在用户。
    * 它跟一般说的可用性定义稍微有点不同，差别在执行者：主要测的是你**不认识的这帮人、你不可控制的这些人**，能不能自己就会用你这个 interface。
    * 所以执行过程基本上不是由你这个团队自己人来做的：要找一个用户群，或者从各种用户群里找几个有代表性的，让他们过来用一下。
    * > 来源: P26

* **可用性测试的三步执行**
    * 第一步，定义清楚具体要测的东西：`usability` 只是一个词，它其实代表了很多词、很多 abilities，不能拿着这一个词去测，得先划分这次打算测哪几个目标（`identify goals of each`）。
    * 第二步，对每一种要测的目标设计 `test cases`，并且设计一种测试方式使得它能够被 `evaluated`；后面每一个特性都要设计一个指标来证明它是好还是不好——什么叫好、什么叫不好，必须有一个很明确的测试方法。
    * 第三步，选择相应的用户群来做测试，他们做的时候你还要在旁边看着：做一些帮助、做一些指导，同时看他们接受的程度怎么样。
    * > 易错点：不能说「我就把它用了一下，觉得不是很好，要打分的话我给你打 60 分」——你凭什么打的 60 分、这个 60 分是哪儿来的、有人说 61 分不可以吗；这种没有指标的打分站不住脚。
    * > 来源: P26

* **可用性目标清单（P26 口径）**
    * 交互性（`interactivity`）：交互做得好还是坏，你怎么判断。
    * 布局（`layout`）：所有东西展示出来，人家是不是好理解。可读性（`readability`）：字体（`font`）、大小、颜色，别人能不能看清——这一条很容易被忽略，字色与背景色几乎混为一谈时，屏幕稍微不够亮大家就看不到了。
    * 美工：整个看上去够不够舒服。展示特性（`display characteristics`）：展示的时候它的一些特性。
    * 时间敏感性（`time sensitivity`）：有什么东西响应很慢、有什么东西对响应速度特别敏感——点一下多久有反应，时间太长用户肯定不满意。
    * 个性化（`personalization`）：对不同用户人群有没有特别的定制。可访问性（`accessibility`）：有没有考虑到残疾人、各种有障碍的人怎么用你这个软件。
    * 到底看重哪几个取决于你开发的是个什么东西，所以要先制定一个目标。
    * > 来源: P26

* **把「可交互性」变成可评判的测试**
    * 例：一套鼠标单点手势交互的毕业论文，写完实现之后要证明「我这个手势要比普通的鼠标点菜单更好用」，所以要设计一系列测试。
    * 设计口径：找几位同学过来，先把任务讲清楚；让他用传统鼠标点选方式完成这些任务，你在旁边掐表记时间；再教他这套手势、用同样任务再做一遍，再掐表看时间。
    * 一次还不行，还得有一个**学习曲线**：让他把任务重复做多少次，然后看时间的变化。
    * 除此之外还有调查问卷：用完以后让他主观描述哪些方面好用、哪些不好用——这就是一个主观的评判。
    * > 来源: P26

* **可用性目标清单（P27 口径）**
    * 做的时候有几件事必须落实：定义好一系列可用性测试的**种类**；每一次测试之前都要先把这一次的**目标**确定下来；让每个目标都容易测、容易评估，这样行不行、要不要改进才有依据。
    * 要看的具体方面可以列成一张表。

    | 方面 | 要检查什么 |
    | :--- | :--- |
    | 交互性 | 用户与界面的操作交互是否顺畅 |
    | 布局 | `layout` 是否合理 |
    | 可读性 | 内容是否容易读 |
    | 美学 | 美工与美感，能否吸引用户 |
    | 展示的特点 | 内容的呈现方式 |
    | 时间敏感性 | 点一下多久有反应，时间太长用户肯定不满意 |
    | 个性化 | 能否按用户个性化 |
    | 可访问性 | 用户总希望一年 365 天、每周 7 天、每天 24 小时都能访问 |
    | 可评估性 | 每个目标是否容易测试和评估 |

    * > 易错点：这张表里最容易被忽略的是最后一行——可用性不是「看起来还行」，它要求每个目标都能被评估，评估结果才能拿去改进。
    * > 来源: P27

* **参与者测试与定量评估**
    * 可用性测试必须支持**参与者测试**：参与测试的人是可控的，但你要先教会他们怎么跟这个 Web 应用交互、怎么走完测试过程。
    * 最好再开发一套**自动化的评估机制**，去评估 Web 应用的这个「流」，做**定量评估**。
    * > 来源: P27
