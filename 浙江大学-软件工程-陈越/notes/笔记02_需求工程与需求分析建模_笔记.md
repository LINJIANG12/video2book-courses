## 1. 需求失效的代价与需求失真的传导

> **一句话主旨**：用事故与行业调查数据说明需求做不好的代价，并指出需求失真在交付链上的传导机制。

### 1.1 需求失效的三类证据

* **Ariane 5 火箭事故**
    * > 定义：1996 年 6 月 4 日 Ariane 5 升空后姿态失稳、被遥控引爆，火箭与搭载的 4 颗卫星同时损毁，总损失 5 亿美元。
    * 直接原因：`requirements documents` 里少写了一句话——Ariane 5 的轨迹倾角会比 Ariane 4 的倾角大。
    * 失效链：倾角越过旧公式的取值上限 → 计算溢出 → 出错模块既不检测也不停机 → 继续用溢出后的垃圾数据往下算 → 轨道结果错误 → 火箭在空中摇摆 → 遥控引爆。
    * 边界：链条起点不在代码里，而在需求文档里一句没有写下来的约束；中间每个环节都只是忠实地执行了别人给它的错误前提。
    * > 来源: P07

* **Standish Group 的行业调查**
    * > 定义：1994 年 Standish Group 对 350 家企业约 8000 多个 software projects 的调查，用来度量项目实际成败比例。
    * 未完成即被取消的项目占 31%（8000 多个项目的全样本）。
    * 按时、按预算、保质保量交付的比例：规模较大的公司只有 9%，规模较小的公司为 16%。
    * 小公司比例更高的解释：人少，可以出错的环节就少；公司一大，人都认不全。
    * > 来源: P07

* **失败原因的排序（1995 年后续调查）**
    * 第一位是 `incomplete requirements`（需求不完整）。
    * 第二位是 `lack of user involvement`（用户参与不足）。
    * 这两条几乎是同一个原因：`communication`（沟通）出了问题——没跟 user 沟通好，才会得到 incomplete requirements。
    * > 来源: P07

* **需求失真的传递链**
    * 转手顺序：客户如此描述需求 → 项目经理的理解 → 分析员的设计 → 程序员的编码 → 交付与安装 → 项目文档 → 技术支持 → 实际做出来的东西。
    * 机理：需求在每一个转手环节都被重新解释一次，每解释一次就偏一点，一路偏到最终交付物与客户真实意图完全不是一回事。
    * Brooks 的判断：`The hardest single part of building a software system is deciding what to build.`——搞清楚到底要干嘛是最难的那一部分，真的搞清楚以后开始做反倒不难。
    * > 来源: P07

### 1.2 跨专业沟通的三个已知坑

* **双方的兴奋点不在一个地方**
    * > 定义：做软件的一方关心的是执行流程与输入输出，非本专业的用户关心的是他自己那套专业内容。
    * 用户是研究者时，他会花大量时间讲算法原理（各种政策组合进来以后逐年推算人口怎么变），而这套原理对软件构造没有意义。
    * 软件方真正需要的是另一头：算出来的结果要怎么显示，要哪几种图、哪几种表；以及整个执行流程是什么样。
    * 双方心里都觉得"这有什么好说的"，于是该说的都没说。
    * > 来源: P07

* **用原型逼出真实需求**
    * 做法：先做一个 `prototype` 拿去给客户看，客户看见东西之后才说得出来"没有这么简单"。
    * 一轮只多露出一部分：数据导入远不是"都准备好了，导进来就好"，导入之前还有一整套要选的选项（一个很复杂的选项卡）。
    * 结论：需求不是一次问出来的，是一轮一轮被原型逼出来的，而且只有在他看见东西之后才说得出来。
    * > 来源: P07

* **缺少文档带来的接手代价**
    * 现象：需求随沟通一点一点增加，程序被一路推着长出来，事后再补文档。
    * 后果：接手的人看不懂，会误判成"怎么可以把程序写得这么乱"；真实成因是需求一点点来、程序被推着长出来的，并不是先有完整需求再做好设计与架构。
    * 前提提醒：必须假设客户不是你这个专业的，沟通要用他的术语，否则就是两个平行世界各说各话。
    * > 来源: P07

## 2. 需求工程的七个环节

> **一句话主旨**：给出需求工程从起手到写定文档的环节顺序，以及压在整条链上的变更管理。

* **需求工程（requirements engineering，RE）的环节链**
    * > 定义：把"要做什么"从模糊意图推进到写定文档的一整套活动，回答的是 what to do。
    * 环节顺序：`inception` → `elicitation` → `elaboration` → `negotiation` → `specification` → `validation`。
    * `management` 不是链条上的某一站，而是压在整条链上的一层控制，核心是变更管理。
    * 边界：how to do it 不属于本阶段，那是设计阶段的事。
    ```text
      inception --> elicitation --> elaboration --> negotiation --> specification --> validation
          |             |               |              |                |               |
          +-------------+---------------+---------------+----------------+---------------+
                                              |
                                         management
                                  （压在整条链上，核心是变更管理）
    ```
    * > 来源: P07

* **inception（起始）**
    * > 定义：起手式——先问一系列问题，把基本情况搞清楚。
    * 要搞清的四件事：你要做的到底是什么东西；是谁要这个 solution（项目干系人都有谁）；这个 solution 属于什么类型；customer 与 developer 之间可以期待的那种沟通方便程度。
    * > 来源: P07

* **elicitation（需求导出、需求获取）**
    * > 定义：把所有相关的人问一圈，主动地导出、诱导出他真正想要的那个东西。
    * 起点只是一份很简单的 requirements 概述，不能当成结论。
    * 客户常常自己说不清他想要什么，也不清楚计算机到底能帮到他什么程度；聊着聊着他的胃口会越来越大。
    * > 来源: P07

* **elaboration（细化）**
    * > 定义：把导出的需求真的落到纸面上，做成一个 `analysis model`（分析模型）。
    * 模型要描述三块：怎么描述它的 data structure（数据结构）、怎么描述功能、以及系统动态的 `behavioral requirements`（行为需求）。
    * 模型与 prototype 的作用都是帮助你跟客户更好地沟通；只把他说话记成一份很长的纪要再让他审查"我记得有没有错"很容易出错，99% 的客户没有耐心仔细读纯文字。
    * > 来源: P07

* **negotiation（谈判）**
    * > 定义：确认要做这件事之后，谈成本底线与 deadline。
    * 谈的是：我的成本在哪里、底线在哪里，你至少要给我多少钱；deadline 怎么设（人手就这么多，不可能下周交活）。
    * > 来源: P07

* **specification（需求规格说明）**
    * > 定义：把所有内容写成一个详细的文件，即 `requirements specification`（需求规格说明）。
    * 三重作用：后面做设计的主要依据与基础；作为跟用户沟通的文档；更主要的是最后验收的依据。
    * 验收要求：最后一节要写清验收的条件与验收 `criteria`（验收标准）——哪些指标达到了什么要求，达到要求就一手交钱一手交货。
    * > 易错点：没有明确的 specification，交付后客户可以说"这不是我要的"，或者"90% 的功能可以，但有一项关键功能做错了所以不能用、不能用我为什么付钱"；你这边说当初是这么讲的，可证据、文档什么都没有，最后辛苦做出来的东西没法交付。
    * > 来源: P07

* **validation（验证）**
    * > 定义：对写好的 specification 做审核、复审。
    * 审核四件事：有没有问题、有没有错；有没有漏掉什么东西；整个需求里面有没有前后矛盾的地方；不同部门之间的需求有没有互相掐起来、撞车的地方。
    * > 来源: P07, P08

* **management（需求管理）**
    * > 定义：压在整条链上的管理活动，最主要的一个功能是 `change`（变更）。
    * 公司里必须有一套严格的流程来决定要不要 change：你可以 change，change 要加钱。
    * 边界：熟人关系下的"用户说有什么 change 我们就 change"等于没有 change management。
    * > 来源: P07

## 3. 起始阶段要摸清的三组问题

> **一句话主旨**：起始阶段先找齐干系人，再依次问清项目上下文、客户心目中的方案与沟通机制。

### 3.1 干系人与协作关系

* **stakeholder（项目干系人）**
    * > 定义：与这个项目有关系的所有人，不只是直接使用这个软件的人。
    * 找齐的问法：`Who else do you think I should talk to?`——除了你，还有谁要用这个软件、还有谁需要再去谈一谈。
    * > 来源: P07

* **多方观点与协作关系**
    * `recognize multiple points of view`：多找几个人，从不同的角度了解你要做的是一个什么样的东西——**不是从技术细节上讲**。
    * `working toward collaboration`：尽可能地营造出一种合作的关系，本质是判断客户在多大程度上愿意配合你。
    * 必须让客户搞明白：他的工作跟这件事随时有关系，不是把需求丢过墙就可以不管。
    * > 来源: P07

### 3.2 三组问题的内容与用途

* **第一组：项目所处的上下文**
    * `Who's behind the request for this work?`——幕后是什么人提出要做这件事的（是上级部门，还是别的什么人）。
    * `Who will use the solution?`——做出来以后谁用这个东西。
    * `What will be the economic benefit of a successful solution?`——做成之后会给客户从经济上带来多大的效益。
    * `Is there another source for the solution that you need?`——做这个东西是不是只找了我这一家，还有别家可以找吗。
    * 这组问题跟要做的软件内容没有直接关系，目的是判断客户在多大程度上愿意配合，并顺带决定后面的谈判策略。
    * > 来源: P07

* **第一组问题的推断用法**
    * 这第一套问题是要把前后左右的那个关系、这个大环境先搞搞清楚，跟你要做的具体内容还不着急问。
    * 四个问题的答案合起来，判断的是客户在多大程度上愿意配合，也顺带决定了你后面的谈判策略。
    * 三种典型处境各自对应一套不同的后续做法：
    * > 来源: P07

| 客户的处境 | 你能预期的配合与后续做法 |
| :--- | :--- |
| 做成了能给他带来巨大的经济效益，而且你们家技术力量强到别人家都不找、他就认定你了 | 后面是一整套相应的处理办法，你在关系里是主动的一方 |
| 对他们家只是锦上添花、可有可无，做成做不成关系不大，联系人可能只是为了什么政治任务才要做 | 他后期跟你配合就是另外一个态度 |
| 他其实还有好几家在联系中 | 你还没开始谈判，只是了解一下要做什么，但你的谈判策略后面全都会不一样 |

* **第二组：客户心目中的解决方案（customer's perceptions about the solution）**
    * 问的是：在你的 customer 脑海里，他想要的大概是一个什么样子东西。
    * 获取方式基本上就是去**做一个 prototype**；嫌麻烦时可以在黑板现场画界面——画出下拉菜单、解释上面是什么，再擦掉、改成文本框，问一句"你觉得是不是这样的"。
    * 演示到中间他就会觉得这步不对、这步不是这样的，然后又是那句话"没有那么简单"。
    * > 来源: P07

* **第三组：沟通机制本身的效果（effectiveness of the communication activity itself）**
    * 要问清：以后我想了解细节的时候可以找谁；你那边公司里是不是有一个专门的联系人，我随时可以找他、他忙不忙、是不是老要出差。
    * 要问清：这个人来参加我们的组会，算不算他工作的一部分、他拿不拿工资——否则对方领导会很不高兴（我付你工资，你是给我干活还是给他们干活）。
    * 拿到答案就能判断在什么程度上这个客户会跟你配合（例如"可以，但要提前一星期来跟我预约"）。
    * > 来源: P07

## 4. 需求会议的组织

> **一句话主旨**：把需求会议当成一项工程来安排，先定人与规矩和日程，再靠主持人控场并留下记录。

* **会议要达成的四件事**
    * `identify the problem`：先把要解决的问题认出来。
    * `propose elements of the solution`：这个解决方案都有哪几部分，大家来凑一下。
    * `negotiate different approaches`：解决可能有好几种途径，谈判一下大家都 prefer 哪一种。
    * 最后给出 `a preliminary set of solution requirements`：大概导出一个初步的需求，这时候还没有去细化它。
    * > 来源: P07

* **该请谁到场**
    * 自己组的人。
    * **客户（customer）**：需求会议的核心对象，客户不到场这个会基本白开。
    * **与这个模块关系最密切的其他组的骨干技术人员**：你做的是系统里的一个模块，你的模块要跟别人的模块对接，接口那头的人不来，讨论出来的东西落地时就会撞墙。
    * 开会前先坐下来想清楚这个会到底要找谁；想不清就别急着发通知。
    * > 来源: P08

* **会议规矩（rules）**
    * 核心问题：**谁必须到，以及你怎么保证他一定到。**
    * 最难保证的是客户：对方是银行里的工作人员，"我这边要开个会您必须来"凭什么成立；这一条不解决，会议通知发出去也就是个建议。
    * 另一类规矩是会议的频度：组会是定期的还是不定期的；如果定期（比如一星期碰一次头），就要跟人家协商，让"我开会的时候你们都要到"变成对方的承诺。
    * > 来源: P08

* **会议日程（agenda）**
    * 必须写清：几点钟开会；本次会议有几个议题、第一第二第三分别是什么；每个议题大概讨论多少分钟；整场会大概几个小时。
    * 作用一：大家不会跑题。
    * 作用二：每个人都有"我做事很有效率"的感觉——说好从几点到几点开会，这段时间给我空出来，剩下的时间他可以安排自己的事。
    * 边界：日程不是形式主义，它是替所有参会人的时间负责。
    * > 来源: P08

* **会议主持人（facilitator）**
    * 身份可以灵活：交给客户主持、自己主持，或者专门请一个第三方来当仲裁都可以，但功能是明确的。
    * 功能一：按会议日程掐时间——这个议题说好多少分钟，时间到了就切换到下一个议题，**不管你讨论出结果没有**；这个议题下次再找时间讨论。
    * 功能二：时间快到时给提醒（30 分钟的议题过了 20 分钟还没头绪，就让大家拢一拢，剩下 10 分钟赶紧商量出一个结论）。
    * 功能三：有人啰里啰嗦说不到点子上，主持人要过去打断一下，请他简短一点。
    * 边界：如果时间真的不够用，那说明 agenda 本身就排错了、会议组织人事先没有做好充分准备。
    * > 来源: P08

* **讨论工具与记录工具（definition mechanism）**
    * > 定义：让大家在讨论的时候把东西记下来、看得见的工具。
    * 常规配置：给每个参会的人一张纸、一支笔，随时记。
    * 更好的配置：有一块投影或者一块黑板，某个共同的见解要发表出来的时候在黑板上写两句——大家都同意吗？这样它同时是讨论工具和记录工具。
    * > 来源: P08

* **不专业的开法与会后底线**
    * 不专业的开法：发邮件、群发短信通知什么时候到哪个寝室开会；会前要说啥谁也不知道，也没跟人打招呼；组长想到哪说到哪，大伙想到什么议到哪，歪歪一通。
    * 底线：最后必须产生一份**会议纪要**——把刚才讨论过的事情记下来，否则回头就忘掉了；会开得再散，纪要留下来需求线索就没断。
    * > 来源: P08

## 5. QFD 与需求的三类价值

> **一句话主旨**：把客户想要的东西翻译成技术需求，并按功能价值打分分成三类来决定开发取舍。

* **QFD（Quality Function Deployment，质量功能部署）**
    * > 定义：一种策略，作用是把客户想要的东西转换成技术员可以理解的 requirement（需求），以 maximize customer satisfaction（客户满意度最大化）为目标去做所有事情。
    * 三步：`function deployment`（功能部署，逐功能搞清楚并打分）→ 常规建模（确定数据、确定输入输出、确定整个系统的 `behavior`）→ `value analysis`（价值分析，按分数分类）。
    * 边界：中间那一步（数据、输入输出、行为）是平常做需求都会做的普通工作，前后两步才是 QFD 特殊的地方。
    * > 来源: P08

* **function deployment（功能部署）**
    * 把每一个要做的功能搞清楚。
    * 同时给每一个功能一个 `value`（价值）——这个功能对客户来说有多少价值，打个分，它有多重要；换个角度说，就是这个功能做好以后客户的满意度会变成什么样子。
    * > 来源: P08

* **value analysis（价值分析）**
    * 把所有需求想做的事情归拢到一起，每个功能上都已经打了一个分，然后按分数给这些功能分个类。
    * 分完之后，需求里要做的事情就落到 `normal`、`expected`、`exciting` 三大类里。
    * 这一步是 QFD 真正起作用的地方。
    * > 来源: P08

| 类别 | 含义 | 开发时的处置 |
| :--- | :--- | :--- |
| `normal` | 基本功能，用户理所当然认为该有的东西 | 有限的人力、有限的时间之内**最先要保证**的，必须给人做好 |
| `expected` | 用户期待有、但没有也不至于没法用的功能 | 也应该做好——作为一个 `professional` 的软件，这一档属于专业底线 |
| `exciting` | 用户没指望、有了会惊喜的功能 | 看你有没有余力，当然也要看他给的钱够不够 |

* **本末倒置的取舍**
    * `expected` 与 `normal` 的差别不在"想不想做"，而在"缺了会不会死掉"——`expected` 缺了系统不会死，但它决定你这个软件是业余水平还是专业水平。
    * 反例：你要做的是个手机，结果地图、导航、照片、音乐每一样都做得很漂亮，就是电话不好使、打电话用的通讯簿做得笨得要命。
    * 边界：至于它卖得好不好是另外一回事；作为一个软件产品来看，只能说它的 QFD 做得很不到位。
    * > 来源: P08

## 6. 需求导出阶段的交付物

> **一句话主旨**：列出需求导出阶段结束时必须齐备的文档与产物，作为这一阶段做完了的判据。

* **交付物清单（八项）**
    * `statement of need and feasibility`（需求说明与可行性分析报告）：这件事情是不是可行的。
    * 系统的 `scope`（范围）：这个系统大概涵盖哪些东西。
    * **stakeholders 通讯录**：所有利益相关者的联系方式——人找得到，需求才追得下去。
    * `technical environment`（技术环境）。
    * `a list of requirements`（需求列表）：用功能来描述，说明这个系统要求完成哪几个功能。
    * 特殊的 `constraints`（约束）：有哪些特别的限制条件。
    * 一套 `scenario`（使用场景）——注意，**不是一个，是一套**。
    * 最好有一个 `prototype`（原型）。
    * > 来源: P08

* **为什么 scenario 是一套**
    * 系统足够复杂时你不可能一个脚本走到底：中间有好多分支——在这个地方做这个选择，它就这么表演一套；在那个地方做另一个选择，它就走另外一条路。
    * 所以场景是一整套，要覆盖各条分支。
    * > 来源: P08

## 7. 基于场景的建模：用例、活动图与泳道图

> **一句话主旨**：以参与者为核心把使用过程写成剧本，先用例核对需求，再用活动图与泳道图摊开分支。

### 7.1 用例的定义、用途与写法

* **用例（use case）**
    * > 定义：描述一个用户、一个 `actor`（参与者、角色）去使用你这个系统的那一个剧本、那一个过程。
    * 需求阶段的作用：跟用户核对——将来你来用这个系统就是这样用的，你先做这个后做这个、发生了某件事的时候你做这个选择，然后问他这是不是你印象中使用系统的方法。
    * 测试阶段的作用：需求分析阶段写的用例都要好好留着；测试的时候至少先拿来自己内部按那个剧本演一遍，把所有剧本全演一遍，没问题你才好去见人。
    * 本阶段主要帮助定义：哪些东西在系统之外、要接触你这个系统（即哪些是你的 actors），以及这些 actors 要做哪几件事情、做这些事情时 system 本身应该怎么反应才能让他达成目标。
    * > 来源: P10

* **写用例的三个步骤**
    * 先把所有 actor 列出来：有哪些人、哪些角色要用你这个系统。
    * 针对每一个 actor，列出他要做哪几件事情（functions）。
    * 根据这些 functions 列出 `primary scenarios`（主场景，最初等、最简单的那些），画出用例图；再考虑使用过程中有没有特殊情况、有没有分支岔路可走，细化出 `secondary scenarios`（辅场景）。
    * 边界：需求这一层的描述比较粗、比较粗放，后面才会越来越细。
    * > 来源: P10

* **SafeHome 的三个 primary 场景（例）**
    * `homeowner`（家里的主人）在面板上至少可以完成三件事：初始化（把参数设置好）；出门时按 `set alarm` 把警报器开起来；人在外面时通过 internet 看 `camera surveillance`（监控镜头）。
    * 三者性质不同：前两件在保安系统的面板上直接按按钮就能完成；看监控要通过 internet，而且要通过它去启动硬件设备 cameras，这里头有一条线去调用那个镜头。
    * 精细到"有这么一条线调用摄像头"这个程度，就已经是一个 primary。
    * 每一项功能还可以再往下走一层（如 `configuration` 要设置哪些参数、先点哪个再点哪个），那是另一串细化的用例。
    * > 来源: P10

### 7.2 用例脚本的检查清单

* **actor 定义本身就是一份检查清单**
    * 每一个 use case 首先要定义一个 `actor`（参与者）——谁是这场戏里的演员，他是什么角色。
    * 定了角色之后，根据这个角色为他设计一系列的行为、一系列的操作。
    * 好处：**你这一套 scenario 不会漏掉什么东西**。
    * > 来源: P08

* **清单的用法**
    * 定完 actor 还要回过头逐个脚本检查：每一个脚本是不是都很清楚地回答了清单上那一系列问题。
    * 作用是把"这套脚本写全了没有"变成一条条可核对的项。
    * 书上的例子是 `SafeHome`——相当于一个装在墙上的家居保安监控器，离家出门时打开、回家以后关掉，人出去了它就监控整个房间有没有异常的动作；书里给出的是一个 `high-level use case`（高层用例）。
    * > 来源: P08

| 检查项 | 要回答的问题 |
| :--- | :--- |
| 角色配置 | 谁是主角？谁是配角？有没有配角？ |
| 目的 | 在这个剧本里，这个 actor 最终想达到的目的是什么？ |
| 前置条件 | 他要在什么前提下做这件事，也就是做这个操作的 `pre-condition` 是什么？ |
| 主要功能 | 主要的 `function` 有哪一些？ |
| 异常 | 有没有 `exceptions`？有没有会出错的状况？ |
| 分支 | 这个 `interaction` 有什么 `variations`？不沿着这条线走的时候，他还有没有别的选择？ |
| 数据 | 他要处理哪些数据：读哪些数据，操作产生哪些数据，改变了哪些数据？ |
| 外部环境 | 外部环境有改变的时候，这个 actor 需不需要告诉系统？他跟控制面板有没有要沟通的地方？ |
| 期望输出 | 他要从系统这里得到的输出信息是什么？ |
| 意外响应 | 有意料之外的情况发生时，有没有必要让这个 actor 知道，进而做出反应？ |

### 7.3 活动图与泳道图

* **活动图（activity diagram）**
    * > 定义：用例的另外一种形式，不是脚本式的，而是把所有的分叉全放在一张图里表示出来。
    * 走到某一步有两种可能、两种选择，选这一边就是这么一串行为，选那一边就是那么一串行为，各种岔路都摊在同一张图上。
    * 不足：看上去没有用例那么好理解。
    * > 来源: P10

* **泳道图（swimlane diagram）**
    * > 定义：在活动图基础上再细化一点——它是游泳池的那个泳道，额外说明每个动作**是谁来做的**。
    * 主体还是活动图的那些 activity、action，只是按角色分道；示例中分成三个角色：homeowner、camera、控制面板的 interface。
    * 分工：homeowner 负责 initialize、set alarm、view image、deactivate；camera 负责把镜头画面 deliver 出来；control panel 负责 start camera 与 show image。
    * 读法：横向三条泳道是三个角色，纵向自上而下是动作发生的时间顺序，列与列之间的衔接就是这个系统真正走完的那一连串动作。
    ```text
      homeowner   |   camera   |   control panel
      ------------+------------+------------------
       initialize |            |
       set alarm  |            |
       -----------+------------+------------------
                  |  <camera>  |   start camera
                  |  deliver   |   show image
       -----------+------------+------------------
       view image |            |
       deactivate |            |
    ```
    * 读一遍就大概清楚这个系统有哪几块、整个是由哪一连串动作做出来的、哪个角色负责哪些动作。
    * > 来源: P10

* **两张图共同的用途**
    * 泳道图和用例图都是帮助用户和你自己充分沟通、确认"我用这个过程、用这个系统的方式是不是就是这个样子"的辅助图。
    * 要回答的是：我是用哪几个操作去把这个系统走完的。
    * > 来源: P10

## 8. 分析模型的三大目标与流程位置

> **一句话主旨**：分析模型夹在客户给的系统描述与自己人要交的设计模型之间，必须同时对上两头。

* **分析模型的三大目标**
    * 把 `customer requirements`（客户需求）描述清楚——这个阶段的描述不仅是给技术人员看的，它主要是给 customer 看的、给非专业人士看的。
    * `define a set of requirements that can be validated`：定义出一套可以被验证的需求；落到钱上就是写清什么情况下客户要给你钱，验收的标准要写清楚。
    * 给你自己人用：内部人员应该能够通过这个 model 得到更细化的 user scenarios，然后是 function、class，然后是 behavior。
    * 缺一不可：三个目标都很重要，缺一个都不成立；每次拿起笔来画图都可以拿这三条回头对一遍。
    * 顾此失彼是这一阶段最常走偏的地方——同一个模型既要客户看得懂，又要给下一阶段的 software design model 做基础（establish a basis），所以还得在技术层面足够清楚。
    * > 来源: P09

* **分析模型在流程中的位置**
    * 上游：customer 给的、也就是讲师给的一个非常简单的 `system description`。
    * 本阶段：`analysis model`，是夹在两者中间的一座桥梁。
    * 下游：你的技术人员要交出来的 `design model`，人家是在你这个 model 的基础上去细化，来完成整个系统的 design。
    * 两头都要顾：客户看得懂（这个阶段的主要读者是客户、是非专业人士）＋技术人员能接着往下做 design（所以还要有技术性）。
    * 重点回答的还是 what to do，是 what，不涉及技术细节；技术细节在 design model 里才会涉及。
    ```text
      customer 给的            本阶段                 下一阶段
      system description  ──▶  analysis model  ──▶  design model
      （极简）                  （中间的桥梁）          （细化到实现）
    ```
    * > 来源: P09

## 9. 分析建模的六条经验法则与领域分析

> **一句话主旨**：六条经验法则定下建模的取舍方向，领域分析则是为将来的重用攒下领域知识。

* **rules of thumb（经验法则）**
    * > 定义：前辈们提醒大家做 requirements 的时候一定要注意的那几条经验教条。
    * `focus on business domain, do not get bogged down in details`：不要想太多的细节。技术人员看到问题就不由自主想到"这个地方我要怎么处理、这里可能有什么 exception、我该用哪种语言去做"，这些是本能，但做 analysis 时就是要忽略很多细节。
    * `add to an overall understanding`：每一张图都要增进大家对系统的整体理解；写出来只会把大家搞得更糊涂的就不要写，前面一张图已经说清楚的也不要再用后面的工具重复一遍。
    * `delay consideration of infrastructure and other non-functional models and pure design`：非功能性的考虑、细节性的考虑都先放到后面；这个阶段主要还是面向 customer——他要的什么功能，你把它搞清楚。
    * `minimize coupling`：在划分这个系统的时候，尽可能让块与块之间不要有太多的关联。
    * `be certain that the analysis model provides value to all stakeholders`：你写出来的东西要对所有的人（主要还是包括你的客户）都是有价值的。
    * `keep it as simple as possible`：尽可能简单，不要把事情搞得太复杂，不要弄得很 fancy、华而不实。
    * 边界：判断标准不是"这个东西我能不能画"，而是"画出来以后有没有人变得更清楚"。
    * > 来源: P09

* **领域分析（domain analysis）**
    * > 定义：把你这一个 project 涉及的领域的相关知识保留下来，供以后在该领域开发其他软件时重用。
    * 立论：做完支付宝之后，对银行内部的转账流程、规矩就比较清楚了，这些就叫做 `domain knowledge`（领域知识）。
    * 主要目标是未来的 `reuse`（重用）；附带好处是有一个 group 对该领域非常熟悉，很容易得到该领域的各种项目、做起来也会比别人更有经验。
    * 做法：从各种渠道去获得领域知识——读技术文件、把现在有的软件拿来用一用、customer survey、专家建议，综合一下做一个 domain analysis 出来。
    * 结果上要抽取的是：有哪些 `class` 是你以后可以用的、整个领域的东西都可以用的。
    * 产出物：重用标准（reuse standards）、功能模型（functional models）、领域语言（domain languages），以及这个领域相关的 `analysis patterns`（分析模式）。
    * > 来源: P09

## 10. 分析建模的两大流派与四类模型

> **一句话主旨**：分析建模分结构化分析与面向对象分析两大流派，工具归为四大类，都是规格说明的内容。

* **两大流派**
    * 传统的 `structured analysis`（结构化分析）。
    * `object-oriented analysis`（面向对象分析，OOA），也就是平常说的 OO。
    * 本教材这一版把两者基本上融合在一起讲；老版本会专门出一章讲 OO，再专门一章讲 structured analysis。
    * > 来源: P09

* **四类分析模型**
    * `scenario-based`（基于场景的）：就是 use case。
    * `activity`（活动）图：描述活动，这是另外一种图。
    * `class-based`（基于类的）：如果你是 OO，这就是你的数据、数据结构的设计。
    * `behavioral elements`（行为元素）：描述系统的动态表现——使用系统的过程中系统会不会处于几种不同的状态、状态与状态之间用什么触发事件让它转换，用 `state diagram`（状态转换图）描述。
    * `flow-oriented elements`（面向数据流的元素）：描述数据流；这是软件工程里面非常古老但有效、也非常重要的一个工具，基本要求是任何时候第一件事 `data flow diagram`（数据流图，DFD）你要能画对。
    * 这些图都不是白画的，它们都是最后要交的那份 `requirements specification`（需求规格说明）里面的内容。
    * > 来源: P09, P10

* **分析阶段也有 patterns（模式）**
    * 模式不展开讲，只要知道有这个东西；将来做 `reuse`（复用）的时候会很有用。
    * > 来源: P08

## 11. 数据建模：数据对象、属性与关系

> **一句话主旨**：在客户的抽象层次上描述数据，从名词里筛出数据对象，再补上关系与基数模态。

### 11.1 在客户的抽象层次上抽取数据对象

* **抽象层次的纪律（create a model at the customer's level of abstraction）**
    * 做法：告诉客户"我这个系统里有一个 object 叫做账户"，账户里头包含姓名、密码、电话号码、通讯地址，他能看懂就够了。
    * 不要写：这个电话号码是用 `int`、`long long` 还是用一个字符串去表示的——这是实现细节，客户看不懂，在需求分析这个阶段写没有意义。
    * 本阶段回答的都是 what to do、都是 what，这里没有 how；到 design 那个阶段才真正涉及 how to do it。
    * > 易错点：需求建模和设计建模的粒度不一样；常见错误是需求文档里做的模型，到 design 做报告、做演讲时几乎原封不动又搬来一遍。需求这部分是给 customer 看的（技术人员也要看懂，看懂了才去作他的 design），design 是给自己人看的，目标不一样。
    * > 来源: P09

* **data object（数据对象）的抽取流程**
    * 前提：真做大型系统时需求可能是几千字、从十几个到二十个部门汇总过来的报告，从这么厚一本书里抽 data objects 是一件很恐怖的事情。
    * 第一步不做人肉：写个程序，先写一个 `parser` 把所有名词抽出来，动词、形容词先扔掉。
    * 中文的难点：你很可能断词、断句断错了。
    ```text
      需求文档（几百页，从十几个、二十个部门汇总过来）
          │
          │  第一步不做人肉：写个 parser 把名词抽出来
          │  （动词、形容词先扔掉）
          ▼
      一堆名词
          │
          │  两道筛子：① 能不能被一组属性唯一定义出来
          │            ② 跟这个系统有没有关系
          ▼
      候选的 data object（没过的，落到属性、功能或约束里去）
    ```
    * > 来源: P09

* **三类词各自的归属**
    * 动词通常是跟系统的功能相关的。
    * 形容词一般来说跟 `attributes`（属性）有关系，或者跟你的 `performance`（性能）、也就是 `constraint`（约束）这类限定性的要求有关系。
    * 名词比较复杂：它可能是 object 本身，也可能是它的 attribute。
    * > 来源: P09

* **data object 的三个判据**
    * 每一个 instance（实例）都有唯一的、确定的标识——跟数据库里一样，要有一个 keyword 唯一标识它。
    * 每一个在你的系统里面都是有意义的——跟系统没关系的就不考虑在内。
    * 每一个都是由一系列的 attributes、一系列的属性来刻画的。
    * ATM 举例：需求里出现"重点分布在几个街区""每隔多少个红绿灯要有一台 ATM"，其中红绿灯不是 data object（只跟安装布置、部署有关，跟系统没关系）；街区不一定——要看系统里需不需要记录客户操作的地点、这台机器的 location 是不是要记录，而且街区自己本身不一定是一个 object，它可能是某一个 object 的 attribute。
    * > 来源: P09

* **attributes（属性）的界定**
    * attributes 很难界定：有的时候 attribute 本身是一个 object，同时又是另外一个 object 的 attributes。
    * 筛选依据：看哪些词是在刻画一个东西的特点、刻画它的质量、描述它的特色或存在状态（颜色、大小），这些一般是某个东西的 attributes。
    * 书上的例子：定义一个 `automobile`（汽车）的 attributes，大概有它的出厂、model、body type、price、options code 等等，用这些去刻画这个 automobile；这些一个一个给定了，就刻画出这么一个东西，程序里就应该认识这是要处理的一个什么。
    * 这件事没有捷径，只能在具体实践过程中慢慢积累抽取 data objects 的经验。
    * > 来源: P09

### 11.2 关系、基数与模态

* **relationship（关系）**
    * > 定义：推不出来、也算不出来的那种联系——你只能够明确地告诉这个系统它是有这个关系、它要记住的。
    * 抽取来源同样是需求文档；区别在于：通过算法计算出来的、通过什么东西推导出来的、逻辑推理推出来的，那些都不能算作 relation。
    * > 来源: P09

* **关系的两个维度**
    * 关系里面有两类：一类叫 cardinality，另一类叫 modality，"就这么两种"。
    * 一般来讲，`ER diagram`（ER 图）是传统上描述这个数据模型的工具；E 是 Entity（实体），R 是 Relation（关系）——数据建模要搞清楚的就是 entities 跟它们之间的 relation。
    * > 来源: P09

| 维度 | 问的是什么 | 取值 |
| :--- | :--- | :--- |
| `cardinality`（基数） | 两个实体之间的数量对应关系 | 一对一、一对多、多对多 |
| `modality`（模态） | 这个关系是不是必须存在 | 必须有、可有可无 |

* **关系的记法**
    * ER 图是传统工具；有了 OOA 之后，`Unified Modeling Language`（统一建模语言，UML）提供了 `class diagram`（类图），还有 `class hierarchy`（类层次，即那个结构层次图）。
    * > 来源: P09

## 12. 面向对象基础：绑定、封装与继承

> **一句话主旨**：从 C 与 C++ 的写法差异讲清 class 把数据与操作绑在一起，换来封装、信息隐藏与安全重用。

### 12.1 C 的 struct 与 C++ 的 class

* **OO 语言至少具备的机制**
    * 它对于数据的包装，是用一个 `class` 的形式来包装的——`class` 这个东西跟 C 里面的 `struct` 是对着看的。
    * 有继承，`inheritance`（继承）——这是 object-oriented 里面一个非常重要的机制。
    * 有私有成员，有 `private` 和 `public` 的概念——用一个词形容它，这实际上就是一种封装，包装，`encapsulation`。
    * C 语言肯定不是 object-oriented，就是因为它缺少这几个特点；C++ 和 Java 是。
    * > 来源: P09

* **一百个学生的成绩单：C 与 C++ 的两种写法**
    * 任务：有 100 个学生，每个学生有学号、姓名、成绩，要把这 100 个学生的成绩全部打出来。
    * C 的写法：定义一个 `student` 的 `struct`，里面放姓名、学号、成绩；再用这个 `struct` 定义一个数组（比如 `s100`）；把所有信息读进来；打印时另写一个 `print_student` 函数，把数组作为参数传进去，在函数里写 `for` 循环用 `printf` 一个个打出来。
    * C++ 的写法：把原来的 `struct` 定义成一个 `student` 的 `class`，原来 `struct` 那一部分的内容成为这个 class 的 `private` 属性；`print` 是这个学生自己有的功能，方法体里没有 `for` 循环、只有一行——打印这个实例的内部属性；调用写成 `student[i].print`。
    * 关键区别：C 里面数据归数据、操作归操作，两个东西是分开的（数据结构定义可以写在一个 `.h` 文件，其它操作写在另一个 `.h` 文件，可以完全拆开、分别拿给不同的人用）；C++ 的 class 把这两件事情绑在了一起。
    * > 来源: P09

| 方面 | C 的写法 | C++ 的写法 |
| :--- | :--- | :--- |
| 数据放在哪 | 定义一个 `student` 的 `struct`，里面有姓名、学号、成绩；再定义一个 `struct` 数组，比如 `s100` | 把原来那个 `struct` 定义成一个 `student` 的 class，原来 `struct` 里的内容成为这个 class 的 `private` 属性 |
| 打印怎么做 | 另写一个函数 `print_student`，把数组当参数传进去，函数里写一个 `for` 循环，用 `printf` 一个个打出来 | `print` 是这个学生自己有的功能，方法体里没有 `for` 循环，只有一行——打印这个实例的内部属性；调用写成 `student[i].print` |
| 数据与操作的关系 | 数据归数据、操作归操作，两者是分开的：所有数据结构的定义可以写在一个 `.h` 文件，其它操作写在另一个 `.h` 文件，可以完全拆开，文件分别拿给不同的人用 | 这两件事情是绑在一起的，绑在同一个 class 里面 |
| 由此多出来的机制 | 没有继承，也没有 private／public 的概念 | 有 `inheritance`（继承），有 `private`／`public` 之分，也就是 `encapsulation`（封装） |

### 12.2 OO 的关键概念与 OOA 的任务过程

* **OO 的关键概念**
    * 有 `class`，有 class objects，也就是对象。
    * 每一个 object 有它的 `attributes`（属性），还有它的 `operations`（操作）。
    * 最关键的、刻画 OO 属性的东西，除了上面这些，就是封装（`encapsulation`）以及继承（`inheritance`）这两件事。
    * > 来源: P09

* **OOA（面向对象分析）的任务过程**
    * 通过 communication、沟通获得一个 `basic requirements` 基本需求描述。
    * 从这个需求描述里头刻画你的数据，在这个做法里就是要把 `class` 抽取出来。
    * 定义这个数据之间的关系，那就是一个 `class hierarchy`（结构层次图），relationship 要刻画清楚。
    * 做行为模型（`behavior model`）——刻画一个系统动态属性的；不仅是 OO 要做，其它普通的做法也要做。
    * 反复地做，一直做到所有的东西都搞清楚为止，这也是一个迭代的过程。
    * 边界：这个任务过程跟"普通青年"的做法差不多，只是稍微文艺一点。
    * > 来源: P09

### 12.3 封装与信息隐藏

* **封装（encapsulation）**
    * > 定义：把数据和专门处理这些数据的那些操作绑在同一个 class 里；内部属性被留在墙以内，外部只能通过约定的接口提出请求。
    * 场景：给 `post office` 这个 object send 一个 message，说我想做这件事；它就用某种方法（sent by method）把花按时、按量送到指定地点。
    * 调用者不关心内部怎么实现：是傻傻地在杭州找一个人买花坐飞机送过去，还是在北京有个点、发个信息让当地人买了花按时送过去，是找美女送还是找帅哥送，都不影响你把这件事做成。
    * 外部改不了内部：想把邮局搬到自家门口、想多加几个邮递员、想 24 小时开门都做不到——没有对外接口让你动这些东西，你就没有权利动，碰不到里面。
    * 能做的只是调用 `post office.send`：按约定填一张 request form（送到哪里、什么时间、要什么类型的花），再给 payment，它读进去发现输入符合要求就去完成功能。
    ```text
      post office（对象）
      ├─ private attributes（墙以内，外部碰不到）
      │   ├─ location：邮局建在哪里
      │   ├─ employee：有哪些员工、多少员工
      │   └─ open hours：开门关门的时间
      └─ public services（对外接口，用户只能从这里进来）
          ├─ send(message)：送信、送花、送电报
          ├─ sell：信封、邮票
          └─ store：存储
    ```
    * > 来源: P09

* **Taylor 记法（Taylor's notation）**
    * > 定义：一种描述 class、或者说描述 data object 的符号，实际用的时候不大有人真的这么用，因为太难画，但它的寓意很好。
    * 画法：整个是一个圈——class name 写在上面，attributes 写在圆圈里面，外边一圈写那些 methods 的名字。
    * 最外那一圈用砖头墙的形式画在那儿，意思就是"这就是墙，而且这个墙没有缝"；里面的 attributes 被保护在里面，没有门让你进去。
    * 唯一的通道是某一面墙上留出的那只手——外部只能通过它发一个请求去改对应的属性；如果有些 attributes 哪一面墙都没有提供修改功能，你就根本没有渠道碰到它。
    ```text
      Taylor 记法（由外向内看）
        最外一圈    methods 的名字，画成砖头墙：这就是墙，而且没有缝
        里面一圈    attributes，被保护在墙以内，外面进不去
        最上面      class name
        唯一的通道  某一面墙上留出的那只手——外部只能通过它发请求去改属性
    ```
    * 实际最常用的还是 UML 那种描述方式：上面是 class name，然后 attributes、operations 这样列一下。
    * > 来源: P09

* **为什么需要封装**
    * 内部实现对调用者不可见，调用者只依赖接口：送花只需按约定填一张 request form 再付钱，调用 `post office.send` 就够了；邮局内部那套做法怎么换，外边调用的人不受影响。
    * 内部状态被保护起来，外部没有渠道乱改：location、员工多少、open hours 都是 private 属性，只有某一面墙上留了那只手，外部才可能通过它发请求去改对应的属性。
    * 数据与操作绑在同一个单位里，可以整体交给一组人维护、整体拿走：C 的写法把数据结构定义放在一个 `.h`、把其它操作放在另一个 `.h`，两件事拆开，谁要用就得记住拿了哪些、还要 include 哪些；class 把这两件事绑在一起。
    * > 来源: P09

* **信息隐藏（information hiding）与其收益**
    * > 定义：一个模块把内部的实现细节藏起来，只对外暴露稳定的接口；只要对外的接口不变，内部实现随你怎么换。
    * 收益一：今天高兴用这个算法把这件事解了一下，后天觉得有更好的算法就把里头的东西改掉——只要对外的接口没有变，藏起来的那些东西爱怎么改就怎么改；即使改出了错误，影响面也不会那么大，不会因为动了某一块整个系统跟着塌掉。
    * 收益二：模块之间都通过 `message`（消息）来互相沟通，所以模块化会做得比较好，模块与模块之间那种耦合、牵来扯去的关系会变得比较简单。
    * 收益三：`reuse`（重用）方便得多——用 C 的时候常见习惯是把所有 `data structures`（数据结构）塞进一个 `.h`，把所有别的操作塞进另一个 `.h`，下次重用时得记住当初 `copy` 了哪些、哪些 `.h` 要 `include`，它们分散在很多地方，漏掉一个这段代码就用不起来；类把数据结构和跟它相关的东西绑在一起，重用时整体重用这一个类就行。
    * > 来源: P10

### 12.4 继承与多继承

* **继承（inheritance）**
    * > 定义：子类把父类的公共属性与操作继承下来（相当于 copy 一份），再戴上自己特有的属性，就成了另一个类。
    * 类图结构：上面的 `furniture` 是 `superclass`（父类、超类），它提取了下面所有 `subclasses`（子类）共同的属性——出厂（厂家）、价格、颜色、材质（木头、塑料、铁，还是 whatever）。
    * 子类 `table`、`chair`、`desk`、`chable` 各自只保留自己的特点。
    * `chable` 的来历：据说以前老浙大是有 chable 的——它又是 chair 又是 table，是一把椅子、当然有扶手，而那个扶手翻过来就是一个小桌子，可以在上面写东西，所以它既有 chair 的功能又有 table 的功能；这些东西买的时候都在家具馆那一片能买到。
    ```text
                        +-------------+
                        |  furniture  |
                        |  price      |
                        |  color      |
                        |  material   |
                        +------+------+
                               |
              +--------+-------+--------+---------+
              |        |                |         |
         +---------+ +--------+   +---------+ +---------+
         |  table  | | chair  |   |  desk   | | chable  |
         +---------+ +--------+   +---------+ +---------+
    ```
    * 被称为**非常安全的重用模式**：想重用一个类的时候，不需要把那个类拿出来、把人家类里面的代码直接改掉；只要继承一下，然后在自己继承出来的子类里去改你想改的、添你想添的，不影响原始父类的内容；那个父类别人还可以接着拿去用，不会因为你改完人家就没法用了。
    * > 来源: P10

* **多继承（multiple inheritance）**
    * > 定义：一个子类可以从多个父类继承——C++ 本来就允许，前面那张图恰好每个子类上面只有一个父类而已。
    * 好处很直接：这个人开发了这一块、那个人开发了那一块，我发现都能用在我这里。
    * 冲突场景：要开发一个 `graphical deck`（有图形界面的纸牌游戏）。恰好有两个现成的类可以用——古老的 `card deck`（封装了所有纸牌游戏的规则：什么情况下谁比谁大、怎么抽牌、怎么出牌）和另一拨人为别的目的写的 `graphical object`（操纵界面上一个图形化的物体：先把它画出来，然后移动它，三维的话还要旋转、缩放）；于是很自然把这两个都作为父类派生出一个 `graphical deck`。
    * 冲突根源：两个类的 `method`（方法）里有重名的功能，都叫 `draw`——英文单词 draw 一词多义：打牌时 draw a card 是"抓了一张牌"（take a card from a deck）；graphical object 里面 draw 的含义是"画"，是把一个图形化的物体在屏幕上显示出来。拿到一个 instance 去点 `draw`，它到底该抓牌还是该画图，就打起来了。
    ```text
          +-----------+          +------------------+
          | card deck |          | graphical object |
          | draw(card)|          | draw(object)     |
          +-----+-----+          +---------+--------+
                |                          |
                +-----------+--------------+
                            |
                     +------+-------+
                     | graphical    |
                     | deck         |
                     | draw(?)      |
                     +------+-------+
    ```
    * 解决：可以用 `overriding`（重写、覆盖）的办法，但那不是唯一的解决方案；有好多种办法，区别只在于解决得聪明还是不聪明。
    * > 易错点：多继承真正的危险不只是方法重名。一旦出现这类冲突，继承的 `transitive`（可传递性）就没有了——如果都是单父类一路继承下去，A 派生了 B、B 派生了 C，那么 C 同时继承了 A 的所有属性，这个可传递性是成立的；而多继承的情况下，这个可传递性很可能被破坏掉。
    * > 来源: P10

## 13. 面向数据流的建模：数据流图

> **一句话主旨**：把系统看成输入处理输出，用有向图描述数据经过一个个功能如何从输入变成输出。

### 13.1 IPO 视角与图元约定

* **数据流图（data flow diagram，DFD）**
    * > 定义：`flow-oriented modeling`（基于流线的建模）里最最古老的一个图；它把系统看成由**数据和功能**构成的整体，想描述的就是数据到底是怎么从输入变成输出的。
    * 理念：把计算机系统看成一个 IPO 的系统（`input`、`process`、`output`）——系统不管它是怎么做的，总是读了一堆输入进来，然后在里面弄了一下，变成一个输出就出去了。
    * 过程：数据从输入的地方流进来，经过一个功能以后变成了这个样子，又经过下一个功能变成下一个样子，经过一系列功能以后转变成最后的输出出去。
    ```text
       +--------+        +--------+        +--------+
       | 外部   |=====>  | 处理   |=====>  | 外部   |
       | 实体   |        | (圆饼) |        | 实体   |
       +--------+        +---+----+        +--------+
                             ||
                        +----++----+
                        || 数据库  ||
                        +----------+
    ```
    * > 来源: P10

* **图元与画法约定**
    * 方块表示外面的 `external entity`（外部实体），一个输入操作、一个输出操作都放在方框里；有的书上输入输出全用一个方块表示，有的书区分一下（输入用方块、输出用另外那么一个东西），都没有关系。
    * 功能画在一个圆饼里面，圆饼里写上这个功能、这个动作。
    * 外部实体与功能之间有很多流线，这些流线跟数据结构里画的 `graph`（图）一样是一个**有向图**，边的上面要标出这条边上流动的数据是什么、有哪些数据。
    * 如果中间涉及到数据库，数据库画在两条线之间——数据库有各种画法，本书采用的是上下两条线、中间写上数据库的名称和它存放什么数据。
    * 边界：画的规矩很简单，讲起来讲完了都知道了，但是会不会画是另外一回事——就像花五分钟能把出牌的规矩讲清楚，打得好不好是另外一回事。
    * > 来源: P10

### 13.2 例题：简化公共图书馆

* **题目（information system of a public library，简化到只有两个功能）**
    * `get a book`：用户输入书的 `title`、`author`，还有借书人自己的名字；调用这个功能以后应该把书找到给他，同时记一下这个人把这本书借走了，数据库要更新。
    * `search by topics`：不借书，只查一下有没有这个书；search by 有好多好多，这里简单地说它只是 search by topics——你应当列出所有这个 topic 的书，包括这些书的 titles 就可以了。
    * > 来源: P10

* **参考画法与数据库划分**
    * `user` 这个外部实体分别送出 book request（线上带 title、author、name of user）和 topic request。
    * `get a book` 一路把 book 交回前台（book reception），另一路把借走的这本书的 title 与 user name 写进 `list of books borrowed` 这个借书数据库。
    * 要得到这本书，search 时至少需要 `author catalog`、`title catalog` 两个数据库加上一个 `bookshelf`：从 author catalog 里找 author、从 title catalog 里找 title，找到它们的公共交集以后，从 bookshelf 上找到那本书的位置，把书得到，然后产生输出。
    * `search by topics` 更简单：输入 topic request，传进去的是一个 topic——不需要告诉你他是谁，你不关心是谁要 search，反正他只是 search、他不借书；产出一个 `list of titles referring to the topic` 在屏幕上显示出来，再加上一个 topic 的数据库，从里面按 topic 找 title，中间处理一下。
    * 边界：这也不一定是标准答案，你可以有别的画法。
    ```text
                         title, author, name of user
       +--------+  ------------------------------->  +==============+
       |  user  |                                      |  get a      |
       +--------+  <-------------------------------    |  book       |
           ^              book  ------------------+    +======+=======+
           |                                       |           |
           |                                       |     title, name of user
           |                                       |           v
           |                                       |   +-------------------+
           |                                       |   || list of books   ||
           |                                       |   || borrowed        ||
           |                                       |   +-------------------+
           |                                       |
           |                                       |     title, author
           |                                       |           v
           |             +==============+      +-------------------+
           |             |  search by   | <--- || author catalog    ||
           |             |  topics      |      +-------------------+
           |             +======+=======+      +-------------------+
           |                    |              || title catalog     ||
           |     list of titles |              +-------------------+
           +--------------------+                      ^
                                                        | book position
                                  +-------------------+
                                  ||  bookshelf        ||
                                  +-------------------+
    ```
    * > 来源: P10

* **这项技能的分量**
    * 画数据流图是软件工程的重要技术技能之一，这几乎是每年必考的。
    * 期末卷子前面 50 分是基本概念题，后面 50 分是临场发挥的题——给你一个小 project，看清这个需求描述，先把数据流图画出来。
    * 边界：没有标准答案，你只要可以自圆其说、不犯明显系统错误就行。
    * > 来源: P10

### 13.3 两个典型错误

* **断流**
    * 现象：某一个功能只有输入没有输出。
    * 判定：这个功能就是有问题的，你肯定画错了什么——数据流流到它这儿就停住了，跟后面再没有关系，那这个功能其实没有存在的必要，它到底在干嘛。
    * > 来源: P10

* **莫名其妙自启动（"灵异事件"）**
    * 现象：一个功能放在那儿，凡是只向它的箭头都是从数据库来的，再没有别的指向它的箭头，然后它就直接开始往外产生输出了。
    * 原理：一个功能在系统里面就是一段程序，肯定要有一个东西去启动它一下，它才能起作用——肯定得有指向它的箭头，它才可能产生出去的箭头、才能产生输出；即使它是根据一个 `timer` 定点定时启动，那也得有一个 timer 去启动它。
    * 病因：数据库是被动的、等着被读的，它不会主动发送数据给这个功能去启动它；得是先启动这个功能，它才去读数据库，所以这种从数据库指向功能的箭头是不算的。
    * 正确形态：只有像 `book request` 这样真正启动了它、调用它、传给它一些数据把它启动起来，它才开始工作，才去调用这些数据库，然后产生输出。
    * > 易错点：断流和灵异事件明显是搞错了，因为这个系统是不可能的，属于明显的系统错误，是要扣分的。
    * > 来源: P10

### 13.4 细化与分层展示

* **refinement（细化）的判据**
    * `get a book` 这个函数其实不太好——它产生了两个不同的输出：它送了输出去，同时它又写了数据库，说明它干了两件事。
    * 目标：把系统拆成"一个圆饼就干一件事情"，最好是这样；如果不是，说明它干了两件事，这两件事就可以拆成两个圆饼来描述。
    * 拆法示例：`book request` 可以分解成 `find book position` 和 `get a book` 两件事（名字是不是这么取还可以再商榷）。
    * 流程：用户说我要借一本书 → 先 `find book position`，从数据库这边找到那本书在哪里、书是存在的 → 把书在哪里传给下一个功能，同时就可以完成第一个功能（表示这本书已经借出去了，去写数据库）→ 下一个功能才去从书架上拿书，给到前台。
    * 边界：这是一个不停地 refine 的过程。
    ```text
       book request        find book position      get a book
       ------------>  (1)  ------------------>  (2)  ---------->  book
                            |                       ^
                            | book position         |
                            v                       |
                      +-------------------+         |
                      || title/author     ||        |
                      || catalogs         ||        |
                      +-------------------+         |
                                                    |
                      +-------------------+         |
                      || bookshelf         ||-------+
                      +-------------------+
    ```
    * > 来源: P10

* **level 0 / level 1 / level 2**
    * level 0 是最起码的：读一个什么东西进去，中间就是**一个 process、一个系统、一个大黑盒子**，然后产生数据给到什么输出。
    * level 1：把中间那个 process 细化，发现它里面原来还有好几个子功能，看数据在这些子功能之间怎么流动。
    * level 2：如果某一个功能还不够细，就再细化一层，这个功能又可以拆成几个功能——它是这么读处理两个输入、最后产生一个输出。
    * 比喻：像拿一个天文望远镜去看，然后走近一点用肉眼看，再拿放大镜看，再拿显微镜去看——你看到的细节越来越多，而这些细节一定是要**逐渐**展示的。
    ```text
      level 0        +--------+      +=========+      +--------+
       book request  |  user  |----->|  系统   |----->|  前台  |
                     +--------+      +=========+      +--------+

      level 1        +--------+   +=========+   +=========+   +--------+
                     |  user  |-->| get a   |-->| find    |-->| book   |
                     +--------+   | book    |   | position|   | shelf  |
                                  +=========+   +=========+   +========+

      level 2        get a book 内部再拆：读两个输入，处理，产生一个输出
    ```
    * > 来源: P10

* **最忌讳的画法与最终目的**
    * 最忌讳：在一页纸、一张 A4 纸里面啪地打出一个巨复杂的数据流图——一堆小圆饼、上面细细小小的字、好多数据在上面流来流去，人家一眼看上去就晕掉了。
    * 目的：你写的需求文档不是给你自己看的，是给别人看的；要照顾别人怎么能在很短的时间里面看懂。
    * 一级一级地展示系统各个细节就是其中一种技巧；书上 SafeHome 还有一个 example 讲了怎么画这个 data flow。
    * > 来源: P10

## 14. 面向控制流的建模：状态图

> **一句话主旨**：从控制流角度看系统运行中有哪几个状态，以及状态之间被什么事件驱动完成转换。

* **控制流与状态图（state diagram）**
    * > 定义：从"我的系统在整个执行过程中有哪几个不同的状态，发生了什么事情、它做了一个处理，就从一个状态转移到另一个状态"这个角度去理解系统。
    * 每种图都从某一个角度理解系统：`user scenario` 是说我这个用户、这个 actor 是怎么做动作的；`activity` 也是说你怎么做动作；`data flow` 是说功能是怎么改变数据的；`control flow` 就是状态图。
    * 事件就是发生或者不发生，其实有两种情况；对应到代码里，看那些标出来的重点词：某个地方发生中断了，`interrupt`；然后 `switch cases`、`if else`——凡是有这种转折的、有几种可能性的，都叫做 control 的节点、控制节点。
    * 描述你这个 control 过程的图就是 control flow diagram；它描述的就是系统有几个不同的 `states`（状态），以及这些状态是通过什么东西、被什么事件驱动完成转换的。
    * 边界：把 control flow 放到 flow-oriented 里面不知道是不是合适，这也是一种大家一定要画的图。
    * > 来源: P10

* **家居保安系统的四个状态**
    * `resetting`（重置）：系统刚被 `switch on` 打开时进入。系统当前的状态是 `inactive`（没启动、没有在做监控）；面板上显示 `starting system`（正在启动，please wait）；那个小灯很慢地一下一下跳着闪，表示系统内部正在做事情；系统内部在做的事情是 `run diagnostics`（自己检测、系统初始化，看看启动起来有没有什么问题）。
    * 启动失败：启动不起来、坏掉了，面板上就显示一个 `contact vendor`（去联系经销商），然后就结束、终止（`terminate`）。
    * `idle`（待机）：顺利启动起来 `system OK` 后进入，什么都不做。这时候 status 还是 inactive、还是没启动；面板上显示的是 `ready`；灯不闪了、一直亮着；然后等待你按下面一个键去做下一步。
    * `monitoring`（监控）：按一下 `activate`（比如要出门）进入。系统现在的状态是 monitoring；面板上显示的是 `armed`（武装起来了）；灯也是不闪的、亮着的；系统内部在做的事情叫 `monitor and control system`。
    * `monitor and alarm`（监控并报警）：进来贼时 `sensor triggered`、`start timer` 开计时，然后它就开始哇哇地叫。面板上显示的是 `alarm`（在报警）、显示 `triggering sensor`，那个灯在很快很快地闪；这时候除了原来那个功能还在执行以外，还要有一个 `sound alarm`（报警器开叫），同时应该有一个动作自动去 `notify alarm responders`（比如自动拨通警察局的电话，再自动拨通住户的电话），同时面板还在等待着下一步的输入。
    * 边界：至于它怎么完成 `monitor and control system`、怎么完成 `run diagnostics`，你都不去管它——**这是给用户看的**；你跟用户描述的是"我这个系统现在是这么一个状态，然后我等着有人再来碰这个面板"。
    * > 来源: P10

* **状态之间的转换条件**
    * `idle` 下的三种按键可能：有人按 `reset`，它又回到 `resetting`，好了以后又进入 `idle`；有人按 `power off`，直接关了就关了；有人按 `activate`，就进入监控阶段。
    * `monitoring` 下的退出：人回来了要把它关掉，关掉不是随便关，你得有一个 `password`（`deactivate password`），成功了它就进入 `idle` 状态。
    * 报警之后的几种去向：贼出现了一下就不见了、后面不再动，它有一个 timer，叫了一段时间之后差不多行了就不叫了；发现是报错警了，可以用某种方法把它掐掉，或者警察进来把事情处理掉后 `deactivate`；否则如果监控器持续地发现有人在里面跑来跑去，它就会 `restart timer`，一直叫。
    ```text
                     power off
            +-----------------------------------------------+
            |                                               |
            v                                               |
       +---------+  switch on   +-----------+  system OK  +--------+
       | initial |------------->| resetting |------------>|  idle  |
       +---------+              +-----+-----+             +----+---+
                                      |                        |
                              启动失败 |                  activate
                                      v                        v
                                +-----------+          +--------------+
                                | terminate |          |  monitoring  |
                                +-----------+          +-------+------+
                                                               |
                                            sensor triggered   |
                                            start timer        v
                                                       +--------------+
                                                       | monitor and  |
                                            deactivate | alarm        |
                                                       +--------------+
    ```
    * 结论：家居保安系统一目了然地说明这个系统有**四个状态**；描述这四种状态之间是怎么转换的图，就叫状态图。
    * > 来源: P10

## 15. 基于类的建模与 UML 记法

> **一句话主旨**：用 UML 的类图、CRC 卡片与 package 把类、职责、协作者和依赖关系摆清楚。

* **从需求文字里找类、属性与操作**
    * 做法：用一个 `grammar`（文法）的 `parser`（分析器）去抽一下名词，然后看哪些名词是 `attributes`（属性）——哪些词定义了某一个 object 的东西，它就叫 attributes；再找动词，动词是哪些动作去 `manipulate`（操纵、处理）attributes。
    * tricky 的地方：所有的动词抽出来之后要把它抽成一个个 `operation`、一个个要完成的函数，那么哪些功能跟哪些 attributes 是绑在一起、属于同一个 class 的？这其实是一件很复杂的事情。
    * 技巧方向：看数据流图以什么为中心，以及画一个什么样的图来分析哪些功能改变了哪些 attributes——一般来说功能应该跟它改变的 attributes 绑在一起。
    * 难点：有些功能改变了好几个 class 的 attributes，这个时候怎么辨有具体的技巧，本课程不介绍。
    * > 来源: P10

* **类图（class diagram）**
    * 一种画法：把一个 class 画好，然后把它们之间的组成关系画出来，在连线上稍微写一句话说明这个关系就可以了。
    * UML 具体怎么用要自己下去学；前面提到的 `class hierarchy`（类层次、结构层次图）就是用来刻画 class 之间 relationship 的。
    * > 来源: P09, P10

* **CRC 卡片（CRC cards）**
    * 第一个 C 是 `class`（类）；R 不是 relationship，是 `responsibility`（职责）；第三个 C 不是 cards，是 `collaborators`（协作者）。
    * class 与 responsibility 这两栏就是那个 class 的描述——它的 private attributes 和 public operations 都写在一起，所以这半栏不是什么新鲜的东西。
    * **重要的是 collaboration 这一栏**：你要写你每一项东西还调用了谁，或者你被哪个其他的 class 调用。
    * 为什么关键：做完就什么都不改那倒无所谓，但改的时候就要小心你改了哪一块——比如电话号码本来定义成整数，现在改成字符串，它可能在另外一个 class 里面被当成一个 hash key 来用，本来认为你是一个 integer hash key，现在变成字符串，人家就挂了。
    * 追查方式：通过 collaborator 去找，把相应的卡片再揪出来，看这些卡片里你影响了哪一部分；而你影响的这一部分可能还有另外的 collaborator，那就牵一发动全身。
    * > 结论：拎出来的卡片越少，说明你的设计越好；设计不好的话，一不小心就拎出来一坨，改的时候就要特别小心。
    * > 来源: P10

* **组成、依赖与 package**
    * 黑色实心菱形表示**组成**关系：一个 `player`，由他的头、身子、胳膊、腿这些东西来组成一个 player。
    * 这些符号还表示一对一、一对多，以及 `mandatory`（强制、必须有一个）还是可以有可以没有。
    * `dependencies`（依赖）：你在 internet 上要给它做一个界面，有一个 `display window`，而它是要去动那个 camera 的，并且要附加一个 `password` 你才能够去动这个 camera。
    * `package`（包）：好多的 classes、好复杂，画成一张很大的图很恐怖，就把它们归归类、放在几个不同的信封里面。比如描述一个足球游戏：所有描述运动场上那个环境相关的类放在一个口袋里，关于这个游戏规则的那些类放在一个口袋里，游戏里面的人物再放一个。
    * > 来源: P10

| 符号 | 含义 | 说明 |
| :--- | :--- | :--- |
| `+` | public | 所有人都可以用 |
| `-` | private | 内部的，就是藏起来的 |
| `#` | protected | 指明这个东西只有某几个 package 才可以同（共享） |

## 16. 行为模型：系统状态、类状态与顺序图

> **一句话主旨**：行为模型描述系统使用中的动态，要同时画系统状态与类状态，最终落在一张顺序图上。

* **behavior model（行为模型）**
    * > 定义：描述这个系统在使用过程中的动态；简单地说就是这样——刚才说的状态图也是行为模型的一部分，就是描述你整个的系统处于哪几种状态。
    * 对于每一个 class，你要仔细分析一下这个 class 是不是动态的、是不是存在几种不同的状态。
    * 除了 state diagram for the system 以外，还要仔细分析 use case，看哪一些 objects 它自己是不是也有一个 state transition（状态转换）的特性；如果有，你要对这个 class、这个 object 做它的状态转换图。
    * > 结论：总的来说你要画两种 state transition——一个是 the state of the system，一个是 the state of each class。也不是 each class，是每一个**有必要画**的 class；如果这个 class 一直是静态的，那就没有必要画。
    * > 来源: P10

* **两类 state（状态）**
    * `passive`（被动的）state：只是它那个 attribute 的值、它的属性值发生了改变。
    * 主动的 state：是它整个的那个 process 在改变。
    * 书上给的例子是 `control panel`（控制面板）——把家居系统里面的控制面板定义成一个类的话，这个类的转换图大概有这么四种状态；但**这个不是你最终要画的那个图**。
    * > 来源: P10

* **顺序图（sequence diagram）**
    * > 定义：把状态图里的每一个 state 按**时间轴从上到下**排列，然后看状态转换过程中涉及到哪几个因素。
    * 与状态转换图的关系，就好像一开始那个 activity diagram 和 swimlane（游泳池那个泳道）图的关系是一样的。
    * 画法：把各种牵连到的系统元素都放在一个图里面——有 homeowner 去启动它，进入一个状态；然后他要跟 system 交互去转换状态；然后还要跟 sensor 交互去做状态转换。
    * 读法：三条竖线是三个系统元素，横向箭头是消息与事件的传递，纵向自上而下是时间推进；这样一眼就能看出在哪个阶段、由谁的动作或哪个传感器事件触发了状态转换。
    ```text
      homeowner        system          sensor
          |              |               |
          |  switch on   |               |
          |------------->|               |
          |              |  resetting    |
          |              |  -> idle      |
          |  activate    |               |
          |------------->|               |
          |              |  monitoring   |
          |              |               |
          |              |<--------------|  sensor triggered
          |              |  start timer  |
          |              |  monitor and  |
          |              |  alarm        |
          |<-------------|               |
          |  sound alarm |               |
          |  notify      |               |
          |  responders  |               |
    ```
    * > 结论：这个顺序图才是你们最终要画的、要解释的那个东西。
    * > 来源: P10

## 17. 需求文档的写作与交付要求

> **一句话主旨**：需求必须落到纸面，写作要分层、统一名词、缩写给全称、带目录索引，并站在第三者立场自查。

* **Everyone knew exactly what had to be done until someone wrote it down.**
    * > 定义：一定要落到纸面上，你才确保说大家都搞得很清楚了；嘴上说说是不算的。
    * > 来源: P10

* **写作的六条规矩**
    * 不要一次性把所有细节展示出来，一定要分层次地去展示。
    * 上百页的需求文档通常由好几个人合作组成，大家要**统一名词用语**：不能这个人管这个东西叫这个名字、在另外一个人写的东西里它又叫另外一个名字，否则读的人会分不清这两个词是不是同一个东西。
    * 所有的缩写，不管这个缩写有多么常见，**第一次出现的时候必须给出全称**，然后说明这个东西的简称是什么，以后你才可以直接用简称去称呼它——这是写论文、写任何正式文件的规矩。
    * 你肯定要有一个目录（`table of contents`）；如果做得再友好一点，后面应该有个 `index`（索引），比较容易找。
    * 写作风格要清楚、简单，不要啰嗦。
    * > 来源: P10

* **站在第三者的立场审视**
    * 总原则：你是很清楚你想做什么的，别人不是很清楚你想做什么；所以写完了这一段、在审视的时候，要站在第三者的立场上去看你写的东西。
    * 自查标准：你给 TA 看，你觉得他在 10 分钟以内能读懂你这块东西吗？就你这个文档，他能读得完吗、他能读得明白吗？
    * 时间投入：留三个星期是因为它**真的需要花三个星期**，不是最后三天就可以赶出来的，更不要指望最后一个晚上把它赶出来。
    * > 来源: P10
