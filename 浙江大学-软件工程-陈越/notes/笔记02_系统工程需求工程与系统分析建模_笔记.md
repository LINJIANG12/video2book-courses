## 1. 系统工程与层次观

> **一句话主旨**：本节先立工程活动的五步骨架与四条原则，再用层次化观念把软件放进企业从战略到代码的坐标。

### 1.1 工程实践的五步骨架

* **工程实践五步（Five Steps）**
    * > 定义：任何工程活动通用的心智模型，也是软件过程的骨架。
    * 第一步 理解问题（Understand the problem）：对应 Communication 与 Analysis，搞清要做什么、为谁做、做到什么程度。
    * 第二步 制定计划（Plan）：对应 Modeling 与 Design，想清怎么做、系统长什么样、模块怎么切分。
    * 第三步 执行计划（Carry out the plan）：进入构造阶段。
    * 第四步 验证结果（Verify）：对应 Testing 与 Quality Assurance。
    * 第五步 交付部署（Deployment）：把成果交给用户使用。
    * > 来源: P06

* **五步的两段划分**
    * 前三步（理解、计划、执行）是从无到有地定义与构造。
    * 后两步（验证、交付部署）是确认与交付。
    * > 来源: P06

### 1.2 四条核心原则

* **为顾客与用户创造价值（Customer & User Value）**
    * 推动任何变更前必须先回答：它对 customer 和 user 有什么价值。
    * 判据是用户可感知的收益：性能从 3 秒压到 0.3 秒有意义；从 1 毫秒压到 0.1 毫秒用户感知不到，客户不会为此多花钱。
    * 以"技术流行、内部结构漂亮、便于维护"说服客户无效。
    * > 来源: P06

* **KISS 原则（Keep It Simple, Stupid）**
    * 结论：不要追求 fancy、smart 的解法，先把"傻一点"的方案想出来，越简单越好。
    * > 来源: P06

* **随时校准方向（Vision）**
    * Vision 指大方向；方向反了，做得越卖力错得越狠、毁得越彻底。
    * 即"Be open to the future"：站在战略高度才能看清未来。
    * > 来源: P06

* **产物必被他人消费（What you produce, others will consume）**
    * 交付的不只是软件系统；需求文档是给别人读的，设计方案是要让别人看懂的。
    * > 来源: P06

### 1.3 系统工程的层次结构

* **业务流程工程（Business Process Engineering）**
    * > 定义：系统工程最顶层，关注企业的业务目标。
    * 信息战略规划（Information Strategy Planning）：站在最顶端，考虑企业未来三年、五年的战略目标与信息化应达到的水平。
    * 企业建模（Enterprise Modeling）：把企业组织结构、业务流程、数据流建为模型。
    * 业务领域分析（Business Area Analysis）：落到财务、人力资源、生产制造等具体领域。
    * > 来源: P06

* **产品工程（Product Engineering）**
    * > 定义：面向具体系统或产品，包含软件工程、硬件工程及其他相关工程，最终交付一个具体产品或系统。
    * 产品由不同 component 构成，因而有构件工程（Component Engineering），涵盖构件的分析、设计、构造、测试。
    * 最底层是 element，如一行代码或一张数据表。
    * 自顶向下的归属链：代码属于 component，component 属于 product，product 支撑 business area，business area 服务于 enterprise 的 information strategy。
    * > 来源: P06

### 1.4 组织视角的分层视图

* **企业角色与视图粒度对应**
    * 老板（顶层）：World View，回答"要在哪几个方面改变世界"。
    * 产品领域负责人：Domain view，面对 Domain of interest，如 Office 是一组 products（Word、PowerPoint、Excel）。
    * 产品经理 / 系统负责人：System view，关注 software、hardware、people、timeline。
    * 项目经理：Element view，对应 product 之下的 management。
    * 基层团队：Detailed view。
    * 结论：看所有事情都按这种层次化方式拆解。
    * > 来源: P06

* **顶层视角关心的三类架构**
    * product architecture：整个公司的产品架构，需要定义架构。
    * data architecture：打算处理哪些领域的数据（注意不是 data structure）。
    * technology：公司最擅长哪几项技术、重点发展哪个方向。
    * 顶层关心 business analysis → business 的 system design → construction 的业务视野，而非程序架构与机器结构。
    * > 来源: P06

## 2. 系统构成与建模框架

> **一句话主旨**：本节给出基于计算机系统的六大要素与系统层次，并落到 input-process-output 的通用建模框架与常用 UML 图印象。

### 2.1 基于计算机系统的六大要素

* **基于计算机的系统（Computer-based System）**
    * > 定义：做系统分析与系统工程时考察的对象，由六类要素共同构成，绝不能只盯着代码。
    * 结论：六类要素必须综合起来考虑。
    * > 来源: P06

* **六大要素（Six Elements）**
    * 软件（Software）：计算机程序、数据结构以及相关的文档。
    * 硬件（Hardware）：运行软件的计算机设备、网络设备、各种外设、传感器等。
    * 人（People）：系统的用户、操作者、维护人员等。
    * 数据库（Database）：存储系统所需的各种结构化与非结构化数据。
    * 文档（Documentation）：用户手册、操作指南、开发与维护文档等纸质或电子资料。
    * 规程（Procedures）：定义人如何在不同情况下使用该系统的步骤与规范。
    * 结论：软件只是其中一块，硬件、人、数据库、文档、规程同样决定系统能否真正运转。
    * > 来源: P06

### 2.2 系统层次与两种工程方向

* **系统层次结构（System Hierarchy）**
    * 自宏观到微观：World View（全局视图）→ Domain（领域）→ System（系统）→ Component（构件）→ Element（元素）。
    * > 来源: P06

* **两种工程方向**
    * 自顶向下（Top-down）：分析问题时从宏观逐层分解，把大问题拆成小问题。
    * 自底向上（Bottom-up）：工程实现与构造时先把底层 element 做好，组装成 component，再集成到 system，最终解决特定 domain 的业务问题。
    * 大型企业数字化转型先做流程梳理与企业架构设计（Enterprise Architecture），理清脉络后才立项进入 Product Engineering。
    * > 来源: P06

### 2.3 系统建模的通用框架

* **input-process-output 框架**
    * > 定义：绝大部分系统都可理解为 input-process-output 结构——有输入，中间处理一下，最后产生输出。
    * 几乎所有系统都能被装进这个框架。
    * > 来源: P06

* **架构流程图（Architecture Flow Diagram）布局约定**
    * 顶层画 interface，即最前端的用户界面。
    * 底层画后端的 management / maintenance 以及 self-test / diagnostic（系统自我检测模块）。
    * 左侧放把 input 数据转化为内部可处理类型的数据的模块。
    * 右侧放处理 output 的模块。
    * 中间放核心处理模块，所有 process 功能集中在这里。
    * 前提：图不能太复杂；不复杂时把不同模块放不同位置、用箭头连线表示关联即可。
    * 表达技巧：presentation 时不要一次性甩出整幅图，先出空框架，随讲解让模块逐个浮现、箭头按演讲顺序依次展现。
    * > 来源: P06

* **实例：传送带分拣系统（Conveyor Line Sorting System）**
    * Scanner 读取条形码，同时 Sensor 读取传送带速度。
    * Decoder 解码器解出该箱子应归属哪个 bin；查 Database 得到 bin location。
    * 结合传送带速度估算箱子到达时间。
    * Shunt 分送机械臂在正确时机把箱子送入对应的第 N 号大箱，并写入 Database 生成 Report。
    * 架构要点：前端有 interface，底层有 self-test，左侧是 barcode 读取与 sensor 速度信号处理，右侧是机械臂送物，中间是处理模块及其彼此通信。
    * > 来源: P06

### 2.4 建模工具速览

* **部署图（Deployment Diagram）**
    * 专门描述硬件块；用处理器（processor）表示实物机器，处理器内分模块（如管 sorting 与管控制 display）。
    * > 来源: P06

* **活动图（Activity Diagram）**
    * 描述动态执行过程（动作序列）。
    * 开始点为实心黑圆饼；结束为黑圆饼外套一个圆圈。
    * 每个动作写在框里，用箭头表示发生顺序；粗黑线表示时间线（时间点上两件事同时开始）；菱形表示"或"的关系（分流）。
    * 多个分支在某点汇齐后再进入下一步。
    * > 来源: P06

* **类图（Class Diagram）**
    * 三块：上面是名字，中间是 attributes，下面是 methods / operations。
    * > 来源: P06

* **用例图（Use Case Diagram）**
    * 前身叫 user scenarios（用户脚本），类似导演写的电影分镜头剧本，描述用户从启动到分步操作的完整流程。
    * 脚本可以有分支：执行到某步有三个选项就对应三个子脚本，纯文字描述痛苦且少有人认真看，后简化成半图形、半文字形式。
    * 图可以有好几层，从粗到细逐层深化。
    * > 来源: P06

## 3. 需求工程的代价与需求失真

> **一句话主旨**：本节用火箭事故与行业调查说明需求缺陷的代价，再刻画需求在逐层传递与跨专业沟通中的失真机理。

### 3.1 需求缺陷的两类证据

* **阿丽亚娜 5 号（Ariane 5）发射失败**
    * 时间与结果：1996 年 6 月 4 日升空后像"喝醉了酒"一样摇晃，最终遥控引爆，火箭连同四颗卫星一起炸毁。
    * 直接经济损失达 5 亿美元（500 million US dollars）；另有 ESA（欧洲空间局）声誉损失。
    * 根因：需求文档少写一句话——阿丽亚娜 5 号的轨迹倾角会比阿丽亚娜 4 号更大。
    * 后果链：计算轨迹的公式未相应修改，升空后倾角超过阿丽亚娜 4 号倾角的最大值，计算发生溢出（overflow）；模块未在溢出时停止计算，继续算出一堆垃圾数据，火箭失控。
    * > 来源: P07

* **Standish Group 行业调查**
    * 1994 年调查 350 家企业、约 8000 多个软件项目。
    * 31% 的项目在完工前被取消（canceled before completion）。
    * 在保质保量、按预算、按时交付的维度上，大公司只有 9% 较成功，小公司为 16%。
    * 1995 年追查原因，高居榜首的两位是 Incomplete requirements（需求不完整）与 Lack of user involvement（用户参与度不足），二者本质同源，都是 communication 出了问题。
    * > 来源: P07

### 3.2 需求逐层失真

* **需求失真的传递链（tree swing）**
    * 客户描述 → 项目经理理解 → 分析员设计 → 程序员编码 → 商业顾问认知 → 项目文档 → 安装程序呈现 → 技术支持，每一层都在偏离，最终交付物与客户本意天差地别。
    * > 来源: P07

* **Brooks 论断**
    * "The hardest single part of building a software system is deciding what to build."——建造软件系统最难的那一部分，是搞清楚到底要造什么。
    * 真的把"要做什么"搞清楚之后，动手去做反而不是最难的事。
    * > 来源: P07

### 3.3 非专业用户沟通案例

* **兴趣错位**
    * 人口仿真项目中，用户是非本专业的研究者，兴奋点在算法本身：算法原理、政策组合怎么推算、放开二胎后 100 年内人口怎么变。
    * 开发方的兴奋点在执行流程：数据怎么导入、要哪几种图、哪几种表、界面上按个按钮就开始算、结果怎么图形化显示。
    * 用户不关心流程，只草草一句"流程很简单，数据导进来算一下显示一下就好了"。
    * > 来源: P07

* **需求逐步浮现与原型的作用**
    * 开发方先做一个 prototype（原型）给用户看，用户一看"没这么简单"，数据导入前其实有一堆复杂选项卡。
    * 每星期去一次、每星期都冒出不一样的需求，需求循环为：用户的描述 → 你的理解 → 他否定 → 他给出新描述 → 你再改。
    * 教训一：原型（prototyping）救了场；幸好选了原型过程模型。
    * > 来源: P07

* **无文档的后果与术语错位**
    * 该项目没有需求文档，学生每次沟通到新需求就记一下、在原型里实现，接手者无从知晓全貌。
    * 认知错位：客户不是你专业的，你以为至关重要的专业细节他根本不 care；跟非专业人士沟通不能用自己的术语，必须用他的术语。
    * > 来源: P07

## 4. 需求工程的七个环节

> **一句话主旨**：本节按先后顺序给出需求工程七环节各自的职责与产物，说明从摸清情况到变更控制的完整闭环。

### 4.1 起始与导出

* **Inception（起始阶段）**
    * > 定义：需求工程的起手式，问一系列问题把基本情况摸清。
    * 要做的三件事：找齐干系人（stakeholders）、识别多种观点（recognize multiple points of view）、营造合作关系（working toward collaboration）。
    * 找干系人的典型问题："Who else do you think I should talk to?"——把相关的人全部找齐。
    * 合作关系要点：让客户明白他的工作随时与你相关，不是把需求"丢过墙"就可以不管。
    * > 来源: P07

* **Inception 的三组问题**
    * 第一组 上下文（Context）：谁在幕后推动、做出来谁用、成功交付的经济效益、是否还有别家可选；这组直接决定后续谈判策略。
    * 第二组 客户感知（customer's perceptions）：在客户脑海里他想要的到底大概是什么样，最好做个 prototype 或在黑板上边画界面边演示来确认。
    * 第三组 沟通活动有效性（effectiveness of the communication activity itself）：以后能期待什么程度的配合，如联系人忙不忙、要提前多久预约、参加组会算不算工作。
    * > 来源: P07

* **Elicitation（导出 / 诱导阶段）**
    * > 定义：把所有可能相关的人问一圈，主动诱导用户说出他真正想要、或对他有帮助的东西。
    * 难点：客户自己常常说不清想要什么；因不专业，他最初不清楚计算机到底能帮到什么程度。
    * 导出需求离不开开会，会议四个目的：Identify the problem、Propose elements of the solution、Negotiate different approaches、给出一份 preliminary set of solution requirements。
    * > 来源: P07

### 4.2 细化、谈判与规约

* **Elaboration（细化阶段）**
    * > 定义：把导出的需求真正落到纸面，建立 analysis model（分析模型）。
    * 分析模型要覆盖 data structure、功能、系统的动态行为（behavioral requirements）。
    * 纪律：纯文字不受欢迎，99% 的客户没耐心细读长篇纪要，要用一堆图形（包括 prototype）去沟通确认。
    * > 来源: P07

* **Negotiation（谈判阶段）**
    * 围绕两件事：成本与底线（至少得给多少钱，否则做不来）、Deadline（交货时间是否可行）。
    * > 来源: P07

* **Specification（规约阶段）**
    * > 定义：谈判谈定后，把所有东西写成详细文件 Requirement Specification（需求规格说明书）。
    * 三个功能：作为后续设计的主要根据与基础；作为与用户沟通的文档；最重要的——验收依据。
    * 必须写清验收准则（acceptance criterion）：哪些指标达到什么要求就付钱，一手交钱一手交货。
    * > 来源: P07

### 4.3 验证与管理

* **Validation（验证阶段）**
    * > 定义：对 specification 的审核、复审过程。
    * Consistency（一致性）：前后有没有矛盾，不同部门的需求有没有互相掐架（撞车）。
    * Completeness（完整性）：有没有漏掉什么东西。
    * Clarity（清晰性）：有没有描述不清楚、让人看不懂的地方。
    * > 来源: P07, P08

* **Management（管理阶段）**
    * > 定义：核心功能是 change（变更控制）。
    * 公司里需求变更有一套严格流程，决定要不要改、甚至要加钱。
    * > 来源: P07

## 5. 需求导出会与 QFD

> **一句话主旨**：本节给出组织专业需求导出会的六个要素，以及用 QFD 把客户语言翻译成技术需求并排定开发优先级的方法。

### 5.1 需求导出会的组织要素

* **参会人（Participants）**
    * 绝不只是本组的人参加，TA（customer）必须参加。
    * 因你做的不是整个系统、而是系统里的一个模块，跟你有最强关联的其他几个组的主要技术人员最好也拉来参加。
    * > 来源: P08

* **会议规矩（Rules）**
    * 不能"想来就来、想不来就不来"；哪些人必须到要想办法保证，尤其是 customer。
    * 规矩要提前协商好，如组会固定每周一次、事先与对方商量好开会时都要到。
    * > 来源: P08

* **会议日程（Agenda）**
    * 专业通知要写清：几点开会、本次会议有几个议题（第一、第二、第三）、每个议题讨论多少分钟、总共几小时。
    * 作用：每个人心里有数（哪段时间空出来给你），既不跑题，又给人做事有效率的感觉。
    * > 来源: P08

* **主持人（Facilitator）**
    * 可以由你、customer 或专门请的仲裁来当，形式随意。
    * 最重要功能是按日程控时：议题说好讨论 30 分钟，到点无论有没有结论都切换到下一议题，剩下的下次再找时间。
    * 时间不够只能说明 agenda 排错了、会前准备没做好；主持人还要管发言，啰嗦说不到点子的要打断。
    * > 来源: P08

* **记录机制（Definition Mechanism）**
    * 让大家能把讨论的东西记下来的工具：通常至少给每人一张纸、一支笔。
    * 最好有投影或黑板，要发表共同见解让人看见时就在黑板上写两句、大家确认；既要有讨论工具，也要有记录工具。
    * > 来源: P08

* **会议纪要（Meeting minutes）**
    * 最后一定要产出会议纪要；讨论过的事不记下来，回头就忘。
    * > 来源: P08

### 5.2 QFD：功能展开与价值分析

* **QFD（Quality Function Deployment，质量功能展开）**
    * > 定义：把 customer 想要的东西转换成技术人员能理解的 requirement 的策略。
    * 核心特征：以客户满意度最大化为目标（maximize customer satisfaction）。
    * 确定数据输入输出、确定系统 behavior、建 model 是普通环节；Function Deployment 与 Value Analysis 是关键。
    * > 来源: P08

* **Function Deployment（功能展开）**
    * 把每一个要做的功能搞清楚，同时给每个功能一个 value（价值分）——该功能对客户有多重要、做好了能带来多少满意度。
    * > 来源: P08

* **Value Analysis（价值分析）与需求分类**
    * 把所有需求归拢，在每项功能上打分，然后按分数把需求分成三大类并据此定优先级。

    | 类别 | 含义 | 开发策略 |
    | :--- | :--- | :--- |
    | Normal | 必备项 | 有限资源下最先保证做好 |
    | Expected | 期待有但缺了也不会死 | 作为专业软件也应该做好 |
    | Exciting | 惊喜型功能 | 看余力、看钱够不够再做 |

    * 纪律：绝不能本末倒置；若 Normal 的功能没保住，项目就做不成。
    * > 来源: P08

## 6. 需求谈判的原则

> **一句话主旨**：本节把"做不做、以什么条件做"的谈判收敛为双赢前提与七条原则，界定妥协的度与承诺的边界。

### 6.1 双赢前提

* **双赢局面（Win-Win Condition）**
    * > 定义：谈判达成的前提——双方都能从这件事中获得好处。
    * 沟通合作时不要只想"对我们有什么好处"，还要想"人家这么做对他有什么好处"。
    * > 来源: P08

* **双赢的达成逻辑**
    * 以出国交流项目为例：学院派学生出去，一方面锻炼学生，另一方面要创国际声誉、派优秀学生去创牌子而不是砸牌子。
    * 结论：达不到 win-win，事情就不可能达成。
    * > 来源: P08

### 6.2 七条谈判原则

* **It is not a competition（这不是竞赛）**
    * 你在谈判，不是在辩论赛；辩论中赢了对你未必有好处。
    * 谈判是妥协的艺术：妥协过了你傻，push 太过了也未必聪明，是一个"度"。
    * > 来源: P08

* **Map out a strategy（要有策略）**
    * 忌一竿子插到底"我的底线就在这，要么同意要么拉倒"，结果一上来就谈崩。
    * 要先迂回营造出"他最后不得不接受、或非常愿意接受"的情境。
    * 事先做好功课：充分了解对手的需求、长处、弱点，最好摸清他的底线，再设计"先说什么、后说什么、把哪件事谈到什么程度"的全套计划。
    * > 来源: P08

* **Listen（听）**
    * 不要急于表达自己、人家刚说个开头就打断；哪怕对方说得啰嗦、慢，也要仔细听。
    * 人家常有弦外之音，也会在不经意间透露出本来没打算透露的信息；会听就比不会听的人多得到很多。
    * 你说得越多犯错机会越多，没必要 volunteer（主动暴露）太多信息。
    * > 来源: P08

* **Focus on the other party's interest（聚焦对方利益）**
    * 最忌"做这事对我有什么好处"；最高明的技巧是站在对方立场说"如果这样做，对你有什么好处"。
    * 例：不能说"把学生送过去对我的学生很有好处"，而要说"把我最优秀的学生送给你，对你有什么好处"。
    * > 来源: P08

* **Don't let it get personal（对事不对人）**
    * 技术问题、项目分歧可以拍桌子吵架，但不要人身攻击、不涉及人品。
    * 尤其忌讳翻老账（"上次那项目你就是那样，这次又来了"）。
    * > 来源: P08

* **Be creative（有创意）**
    * 卡死时不要认定是不可协调的矛盾，其实一定有办法。
    * 聪明人在大家陷入死胡同时 jump out of the box（跳出框框），想一个不一样的办法。
    * > 来源: P08

* **Be ready to commit（说到做到）**
    * 说出去的话泼出去的水，是要兑现的；你说的每个条件都要准备好被对方画线承接下来。
    * 忌抢着说"我一个星期就能做完"（其实一个月都悬），对方说"好，给你钱"就傻了。
    * > 来源: P08

## 7. 分析模型的目标与戒律

> **一句话主旨**：本节界定分析模型在客户描述与设计模型之间的桥梁地位，给出三大目标、经验戒律与领域分析的复用定位。

### 7.1 分析模型的三大目标与定位

* **分析模型的三大目标**
    * 把 customer requirements 描述清楚——这一阶段的模型主要是给 customer（非专业人士）看的。
    * 为下一阶段的 software design model 打基础（establish a basis）——需足够技术性，让内部人员觉得可以把它转化成软件系统。
    * 定义一组可以被验证的需求（define a set of requirements that can be validated）——写清验收标准，什么情况下客户要给你钱。
    * > 来源: P09

* **桥梁定位与粒度**
    * 位置：Customer 给出的极简 System Description → Analysis Model → Design Model（内部人员细化）。
    * 分析模型重点回答 what to do，不涉及技术细节；技术细节（用什么算法、什么数据结构）要到 design model 才展开。
    * > 易错点：把需求文档里的模型原封不动搬到设计报告里——需求照顾 customer 看懂"要实现什么"，设计给自家人看"怎么实现"，二者目标与粒度不同。
    * > 来源: P09

### 7.2 分析模型的经验戒律

* **面向客户与业务的三条戒律**
    * Focus on business domain, do not get bogged down in details：聚焦业务领域，刻意忽略 exception、用哪种语言等细节。
    * Delay consideration of infrastructure and non-functional models until design：非功能性、细节性的考虑先放到设计阶段。
    * Be certain that the analysis model provides value to all stakeholders：模型对所有干系人（尤其客户）都要有价值。
    * > 来源: P09

* **面向清晰与简单的三条戒律**
    * 每个图都要 add to an overall understanding：只画能帮助大家更好理解的图，前一张图已讲清就不必用另一个工具重复。
    * Minimize coupling：切分系统时，尽量让块与块之间不要有太多关联（coupling）。
    * Keep it as simple as possible：尽可能简单，不要华而不实、不要 fancy。
    * > 来源: P09

### 7.3 领域分析与两大流派

* **领域分析（Domain Analysis）**
    * > 定义：把本项目涉及的领域知识（domain knowledge）保留下来，主要目标是未来的 reuse（复用）。
    * 例：做完支付宝后对银行内部的转账流程、规矩已比较清楚，这些就是领域知识；下次开发同领域软件时可大量复用。
    * 做法：从技术文件、试用现有软件、customer survey、请教专家等渠道获取领域知识，抽取哪些 class 以后可用、定出 reuse standards（重用标准），配合 functional models、domain languages，总结出 domain 相关的 analysis patterns（分析模式）。
    * > 来源: P09

* **分析模型的两大流派与四大类**
    * 两大流派：传统的 structured analysis（结构化分析）与 object-oriented analysis（面向对象分析，OOA）；本版教材把二者融合在一起讲。
    * 分析模型有四大类工具，每一大类里有若干具体 diagram，都是最终要交的 Requirement Specification 里的内容。
    * 描述需求至少包括：基于 use case 的模型、数据模型（data modeling）等。
    * > 来源: P09

## 8. 数据建模

> **一句话主旨**：本节在客户的抽象层次上描述数据，明确数据对象与联系的抽取方法、判定标准以及基数与模数两个维度。

### 8.1 抽象层次与两项任务

* **在客户的抽象层次上建模（customer's level of abstraction）**
    * 数据模型要让客户看得懂，是在他的层面描述数据；只说"有什么"，不说"怎么实现"。
    * 例：描述账户（account）包含姓名、密码、电话号码、通讯地址即可，不写电话号码用 int、long long 还是字符串表示。
    * > 易错点：需求文档里出现设计阶段的模型（具体算法、数据结构）。
    * > 来源: P09

* **数据建模的两项任务**
    * 除摘出有哪些 data objects，更重要的是搞清楚它们之间的 relationship（关系）。
    * ER diagram（实体-联系图）：E 是 Entity（实体），R 是 Relation（联系）。
    * 传统用 ER 图描述数据模型；OO 里 UML 提供 class diagram 与 class hierarchy（结构层次图）。
    * > 来源: P09

### 8.2 从需求文档抽取数据对象

* **名词 / 形容词 / 动词的映射**
    * 面对几千字、从十几个部门汇总来的厚报告，可写一个 parser（解析器）先抽出所有名词候选（英文易抽，中文断词易错）。

    | 词性 | 通常映射 |
    | :--- | :--- |
    | 名词 | 可能是 object 本身，也可能是某 object 的 attribute |
    | 形容词 | 多为 attributes，或与 performance / constraint（限定性要求）有关 |
    | 动词 | 与系统要完成的 function（功能）有关 |

    * 筛选方式：名词归一堆、形容词归一堆、动词归一堆，再判断谁是 object、谁是 attribute。
    * > 来源: P09

* **ATM 实例辨析**
    * 需求："希望 ATM 分布在每几个街区，每隔多少红绿灯至少有一台 ATM。"候选名词为 ATM 机、街区、红绿灯。
    * ATM 机：显然是要做的东西，是 data object。
    * 红绿灯：肯定是 object，但不是你的 data object——你的系统跟它没关系，那是部署（deployment）时才考虑的事。
    * 街区：不一定；若系统需要记录客户操作地点、机器的 location 需记录则可能相关，但街区本身往往只是某个 object 的 attribute。
    * > 来源: P09

### 8.3 数据对象的判定标准

* **Data Object 的三条判定标准**
    * 它的每个实例（instance）有唯一确定的标识（类似数据库的主键 keyword）。
    * 在系统中有意义（无关的东西排除）。
    * 由一系列 attributes（属性）刻画。
    * > 来源: P09

* **Attributes 的边界**
    * attributes 本身有时也是一个 object，同时又是另一个 object 的 attribute，这种情况会发生。
    * 例：automobile（汽车）的 attributes 有出厂信息、model、body type、price、options code 等，给定后就能刻画一辆具体的车。
    * > 来源: P09

### 8.4 联系与基数、模数

* **Relationship（联系）的抽取边界**
    * 凡能通过算法计算、通过逻辑推导出来的，都不算 relation。
    * Relation 是指推不出来也算不出来、只能明确告诉系统"它俩有关系"且要记住的东西。
    * > 来源: P09

* **关系的两个维度**
    * Cardinality（基数）：一对一（1:1）、一对多（1:N）还是多对多（M:N）。
    * Modality（模数）：必须有的（mandatory）还是可有可无的（optional）。
    * > 来源: P09

## 9. 面向对象分析基础

> **一句话主旨**：本节回顾面向对象的核心机制与 C/C++ 的本质差别，给出 OOA 迭代流程，并用封装与消息刻画对象的外部边界。

### 9.1 面向对象的关键概念

* **面向对象的四项核心机制**
    * class / objects（类与对象）。
    * 每个 object 有 attributes（属性）与 operations（操作）。
    * encapsulation（封装）。
    * inheritance（继承）。
    * > 来源: P09

* **语言是否 OO 的判据**
    * 一门语言被称为 Object-Oriented，至少要有上述机制。
    * C 语言因缺了关键特点不是 OO；C++ 和 Java 是。
    * > 来源: P09

### 9.2 C 与 C++ 的本质区别

* **C 的写法：数据与操作分离**
    * 数据归数据（struct student 写在 .h），操作归操作（print_students 函数写在另一个 .h），二者可完全分开。
    * > 来源: P09

* **C++ 的写法：数据与操作绑定**
    * class 把数据与操作绑在一起，print 不再是独立的外部函数，而是对象自己的方法。
    * 调用方式为 `S[i].print()`，print 内部无需 for 循环。
    * 结论：面向结构语言里数据与操作分开，class 里二者绑在一起，这是最大区别。
    * > 来源: P09

### 9.3 OOA 的任务流程

* **OOA（面向对象分析）的迭代流程**
    * basic requirements（沟通获得基本需求描述）→ 抽取 class（刻画数据）→ 定义 class hierarchy（类层次）与 relationship → 建立 behavior model（行为模型，刻画动态属性）→ 反复迭代，直到一切清楚。
    * > 来源: P09

* **behavior model 的适用范围**
    * behavior model 不仅 OO 要做，普通（结构化）分析也要做。
    * > 来源: P09

### 9.4 对象与消息

* **对象、消息与方法**
    * 给一个 object **send a message**，object 用它的某种 method 完成功能。
    * 调用者只关心 object 提供的接口，不关心内部怎么实现。
    * 例：调用 post office（邮局）object，发"我要送花到某地某时"的消息，邮局用 send by method 把花按时按量送达。
    * > 来源: P09

* **私有属性与对外接口的边界**
    * private attributes（私有属性）：如邮局的 location、employees、open hours，外部不能动。
    * public interface（对外接口/服务）：如邮局的 send（送信送花送电报）、sell（卖信封邮票）。
    * 边界：外部只能通过接口发请求（按约定填 request form 并付 payment）间接驱动内部，无权直接触碰内部属性。
    * > 来源: P09

### 9.5 封装的图示

* **Taylor's Notation（Taylor 记号）**
    * 用于描述一个 class / data object；因太难画，实际少用。
    * 画法：Class Name 写在方框顶部；attributes 写在圆圈里；methods 写在外圈；外圈用砖墙表示，墙没有缝、没有门。
    * 含义：唯一的出入口是某一面墙上的"手"（接口）；若某 attribute 任何一面墙都没提供修改功能，你就根本碰不到它。
    * > 来源: P09

* **记号的现实替代**
    * 现实中大家还是用最常见的方式——UML 类图：上面 class name，下面列 attributes 与 operations。
    * > 来源: P09

## 10. 封装与继承

> **一句话主旨**：本节说明封装实现信息隐藏与复用便利的机理，以及单继承与多重继承在复用收益与命名冲突、传递性上的边界。

### 10.1 封装与信息隐藏

* **封装（Encapsulation）与信息隐藏（Information Hiding）**
    * > 定义：把数据和操作这些数据的函数绑在同一个 class 里；与 C 的根本区别就在这里。
    * 信息隐藏：只要对外的接口（Interface）没变，今天用算法 A、明天换成算法 B，把里头的东西改掉，外部完全不受影响。
    * 内部出错影响范围也有限；因大家都通过 message 互相沟通，模块化（Modularization）更好，模块间的耦合（coupling）关系更简单。
    * > 来源: P10, P09

* **复用上的便利**
    * 用 C 时，有人习惯把所有 data structures 放一个 .h、所有操作放另一个 .h，复用时要记住 copy 哪些、include 哪些，分散多处、容易漏。
    * class 把数据结构与相关内容绑在一起，只要重用这个 class 即可。
    * > 来源: P10

### 10.2 单继承与父类

* **superclass 提取公共属性**
    * 用一个 superclass 提取所有 subclass 的公共属性。
    * 例：Furniture（家具）作为父类，下含 table、chair、desk 以及兼具 chair 与 table 功能的老浙大特有 chable。
    * 公共属性（出厂、价格、颜色、材质：木 / 塑料 / 铁）放到父类；子类继承下来再叠加自己的属性，成为新 class。
    * > 来源: P10

* **继承作为安全的重用模式**
    * 想重用某个 class 时，不需要把人家的代码改掉，只需继承一下。
    * 在自己的 subclass 里改想改的、加想加的，且不影响原始 superclass——别人还能继续用父类。
    * > 来源: P10

### 10.3 多重继承与其危险

* **多重继承（Multiple Inheritance）**
    * > 定义：一个子类可以从多个父类继承，C++ 支持。
    * 好处：能结合多家的东西。
    * > 来源: P10

* **多重继承的两类危险**
    * 危险一 命名冲突：GraphicalDeck 同时继承 CardDeck（draw=抓一张牌）与 GraphicalObject（draw=在屏幕上画出来），两父类都有同名方法 `draw`，调用时二者打架、产生冲突；可用 overriding（方法重写）等化解。
    * 危险二 破坏传递性：单继承链 A 派生 B、B 派生 C 时 C 同时继承 A 的全部属性（transitive 可传递），多重继承下这种可传递性很可能失效。
    * > 来源: P10

## 11. 用例建模

> **一句话主旨**：本节用 actor 与剧本刻画人机交互，给出用例构建三步与需求、测试两个使用阶段，以及泳道图对活动图的细化。

### 11.1 用例的作用与构建步骤

* **Use Case（用例）**
    * > 定义：描述一个 actor（参与者）使用系统的剧本（过程）。
    * 需求阶段价值：跟用户核对"将来你就是这么用系统的——先做、后做、遇到这事做选择"，作为确认工具。
    * 测试阶段价值：内部先按剧本把所有场景演一遍，没问题了才去见人。
    * > 来源: P10

* **构建 use case 的三步（需求阶段不必写太细）**
    * 列出所有 actor（哪些人、哪些角色要用系统）。
    * 对每个 actor，列出他要做的几件事。
    * 根据 functions 列出 primary scenarios（初级 / 最简单剧本），画一张粗的 use case 图；再考虑使用中有无特殊情况、分支岔路，细化出 secondary scenarios。
    * > 来源: P10

### 11.2 SafeHome 案例与泳道图

* **SafeHome 家居保安系统用例**
    * 系统装好后，homeowner（主人）在面板上至少能完成三件事：初始化（Configuration）设置参数、Set Alarm 出门时按按钮开启警报、通过 Internet 看 camera surveillance（监控镜头）。
    * 前两者直接在保安系统面板上按键完成；第三者要走 Internet，启动硬件 cameras、调用镜头。
    * 每项功能再向下细化（如 Configuration 要设哪些参数、先点哪再点哪），形成一串更细的 use case。
    * > 来源: P10

* **Swimlane Diagram（泳道图）**
    * > 定义：在 Activity Diagram（活动图）基础上细化，把每个 action 归到负责它的角色泳道里。
    * 相对活动图：活动图在一张图里把所有分叉都画出来，不如 use case 好理解。
    * SafeHome 分三道：Homeowner 负责一堆积动作、Camera 负责镜头动作、Interface（控制面板）负责两个动作。
    * 作用：一目了然看出系统由哪几块构成、整体由哪串动作完成、哪个角色负责哪些动作。
    * > 来源: P10

## 12. 面向流的建模：数据流图

> **一句话主旨**：本节以 IPO 视角描述数据从输入经功能变换为输出的路径，给出符号约定、画图错误与分层细化纪律。

### 12.1 核心理念与符号

* **Data Flow Diagram（数据流图，DFD）**
    * > 定义：Flow-oriented modeling 的工具，把系统看成由"数据"和"功能"构成的整体。
    * 根本理念：把计算机系统看作一个 IPO 系统（Input - Process - Output）。
    * DFD 要描述的是数据到底怎么从输入变成输出——数据从输入处流进，经过功能变成另一副模样，再经下一个功能继续变，经一系列功能后转成最终输出。
    * 整个图是一个有向图。
    * > 来源: P10

* **DFD 符号约定**

    | 符号 | 含义 |
    | :--- | :--- |
    | 方块（□） | External Entity（外部实体）：输入操作、输出操作 |
    | 圆饼（○） | Process（功能 / 加工），圆饼内写功能 |
    | 有向边 | 数据流，边上标注流动的数据是什么 |
    | 两条平行线 | 数据库，中间写数据库名称 |

    * > 来源: P10

### 12.2 图书馆实例

* **公共图书馆信息系统的两个功能（简化版）**
    * Get a book：用户给 title、author、借书人姓名（Name of user），系统找到书给人，并更新"已借书"数据库。
    * Search by topics：按主题查书，列出所有相关书的 titles。
    * > 来源: P10

* **Get a book 的数据流路径**
    * 先画功能进程（圆饼）作为黑盒子，需求阶段不要细化内部。
    * 输入数据流：User 给一个 Book request，流线上带 title、author、Name of user 三个数据，传给 Get a book。
    * Get a book 查 author、title 对应的书架位置（至少涉及"书架"数据库与"已借书清单"数据库）。
    * 输出：产生一本 book 交给前台 Book reception，并把借走书的 title 与 username 写入 list of books borrowed 数据库。
    * > 来源: P10

* **Search by topics 的数据流路径**
    * 输入一个 topic，从 title / topic 数据库查。
    * 屏幕显示 list of titles referring to the topic，无需知道是谁在查。
    * > 来源: P10

### 12.3 两大典型错误

* **断流**
    * 某个功能只有输入、没有输出；数据流到这就停住、跟后面无关联，那这个功能毫无存在必要。
    * > 来源: P10

* **灵异事件（莫名其妙自启动）**
    * 功能必须有东西启动它才能产生输出；若所有指向它的箭头都从数据库来、没有真正的触发源，就是它"自己跳起来读数据库"。
    * 原因：数据库是被动的、等着被读，不会主动发数据去启动功能。
    * 正确情况：有 book request 这类外部输入真正调用、启动功能，功能再去读数据库、产生输出。
    * 结论：只要不犯断流与灵异两类系统级错误，能自圆其说即可得分（无标准答案）。
    * > 来源: P10

### 12.4 细化与分层

* **Refinement（逐步细化）**
    * 若 get a book 产生两个不同的输出（既送书到前台、又写数据库），说明它干了两件事，应拆成两个圆饼：先 `find book position`（找到书在哪），再 `get a book`（从书架取书给前台），同时并行去写借书数据库。
    * > 来源: P10

* **分层（Level 0 / 1 / 2）**
    * Level 0：最简，读输入 → 一个大黑盒子 process → 产生输出去哪。
    * Level 1：把中间 process 细化，露出几个子功能及数据如何在子功能间流动。
    * Level 2：若某子功能还不够细，再拆。
    * 纪律：忌在一页 A4 上"唰"地甩出巨复杂 DFD；细节要逐渐展示，让忙得要命的 TA 在很短时间内看懂。
    * > 来源: P10

## 13. 状态建模与行为建模

> **一句话主旨**：本节从控制流视角刻画系统的状态与转换，并给出行为模型对状态、时序以及主被动状态的建模范围。

### 13.1 控制流与状态图

* **Control flow（控制流）与 State Diagram（状态图）**
    * > 定义：从"系统在执行过程中有哪几个不同状态、发生何事、如何处理，从而从一个状态转移到另一个状态"来理解系统。
    * 对应代码里的中断（interrupt）、switch-case、if-else 等所有有转折、有多种可能性的控制节点。
    * > 来源: P10

* **SafeHome 的四个状态**
    * RESETTING（自检）：由 switch on 触发，run diagnostics、面板显示 starting system；启动失败则面板显示 contact vendor 并终止，启动成功则进入 SYSTEM OK。
    * IDLE（待机）：面板 ready、灯常亮、status=inactive；按 reset 键回到 RESETTING，按 power off 关机，出门按 activate 键转下一状态。
    * MONITORING（监控中）：面板 armed、灯常亮、status=monitoring；人回来加 deactivate password 回到 IDLE；进贼则 sensor triggered → START TIMER 转下一状态。
    * MONITOR AND ALARM（报警）：面板 alarm、灯急闪，sound alarm 叫、notify alarm responders（自动拨警局 / 住户电话）；贼消失加 timer 超时或 deactivate 回到 IDLE（或 restart timer 持续叫）。
    * 边界：run diagnostics、monitor and control system 等内部怎么实现用户不需要管，这张图是给用户看的。
    * > 来源: P10

### 13.2 行为模型

* **Behavior Model（行为模型）**
    * > 定义：描述系统使用过程中的动态，state diagram 是其中一部分。
    * 既要画 state of the system，也要分析每个有必要的 class 自己的 state transition diagram；一直静态的 class 不必画。
    * 状态分两类：passive（被动）——仅 attribute 值改变；active（主动）——整个 process 在改变。
    * > 来源: P10

* **Sequence Diagram（时序图）与状态转换图的关系**
    * 类似 activity diagram 与 swimlane 的关系：把每个 state 按时间轴从上到下排列。
    * 标出状态转换过程中牵涉哪些系统元素：如 Control panel 由 home owner 启动进入某状态、与 system 交互转换、与 sensor 交互转换，把所有牵连元素放进一张图。
    * > 来源: P10

## 14. 类建模与需求文档写作

> **一句话主旨**：本节给出 OOA 抽取类与操作的方法、CRC 卡与 UML 类图符号，并落到需求文档的分层、命名与换位审视纪律。

### 14.1 类建模与 CRC 卡

* **Class-based Modeling（类建模）**
    * 抽取方法：写个 parser 抽名词，区分哪些是 attributes、哪些词定义了某 object 的属性；抽动词，动词是 manipulate（操纵）哪些 attributes 的动作，应抽成 operation。
    * 归属判定：某些功能改变了好几个 class 的 attributes 时，一般应与被操纵的 attributes 绑在一起；具体技巧可结合 DFD 分析"哪些功能改变哪些 attributes"。
    * > 来源: P10

* **CRC 卡（CRC Cards）**
    * C = Class（类）；R = Responsibility（责任，即 class 的 attributes + public operations，等于 class 描述）；C = Collaborators（协作者）。
    * 关键是 Collaborator 栏：写下你这项还调用了谁、或被谁调用。
    * 用途：改动影响分析（impact analysis）——如把"电话号码"从整数改成字符串，若另一 class 把它当 integer hash key，一改它就挂；通过 Collaborator 把相关卡片揪出来看影响范围。
    * 判据：受影响卡片越少说明设计越好；一改就牵出一大坨，就是差设计。
    * > 来源: P10

### 14.2 UML 类图符号

* **关系与基数符号**
    * 黑色实心菱形 = Composition（组成关系），如 player 由头、身、四肢组成。
    * 连线上的标注表示基数与模数：一对一、一对多、mandatory（必须有）或 optional（可有可无）。
    * > 来源: P10

* **Package 与可见性符号**
    * Package（包）：复杂系统把 class 归类装进"信封"，如足球游戏分环境相关类一包、规则类一包、人物类一包。
    * 可见性符号：`+` public（所有人可用）、`-` 内部私有（藏起来）、`#` 仅限某几个 package 可用。
    * > 来源: P10

### 14.3 需求文档写作纪律

* **面向读者的六条纪律**
    * 分层展示：不要一次性抖出所有细节，务必逐级展开。
    * 统一名词：上百页文档由多人合作，同一东西不能在这叫"名字"、在那叫"另一个名"。
    * 缩写首次给全称：任何缩写第一次出现必须给出全称并说明简称，之后才可用简称。
    * 要有目录（table of contents），友好一点再加 index（索引）。
    * 文风清楚、简单、不啰嗦。
    * 站在第三者立场审视：问自己 TA 哥能否在十分钟内读懂这块。
    * > 来源: P10

* **落纸与规模纪律**
    * 一句话点题："Everyone knew exactly what had to be done until someone wrote it down."——不落到纸面就不算数。
    * 工期：项目 due date 留了三个星期是有道理的，它真需要三周；以往有 TA 要求"需求文档写不到 100 页好意思交？"。
    * > 来源: P10
