## 1. 测试的目的、立场与组织方式

> **一句话主旨**：测试的目的是发现问题而非证明正确，本节定交付物、定介入时机、定人员分工与误区边界。

### 1.1 测试的根本目的

* **测试的目的（Testing Purpose）**
    * > 定义：测试的根本目的是发现问题（`for finding errors`），不是证明软件没有问题。
    * 测试员的立场是站在程序员的对立面想方设法破坏它，而不是保护程序员（`protect the programmer`）。
    * 公司按找到错误的多少给测试员发奖金：找到越多奖金越多，而不是因为"证明了程序是对的"拿奖金。
    * > 易错点：什么都没测出来可能是测试太弱，不能说明软件没有错。
    * > 来源: P17

* **一致性测试（Consistency Testing）**
    * > 定义：一致性测试是检查软件与用户既有使用习惯是否对齐的那一类测试。
    * 缺失的后果：卡利空难共 163 人、仅 4 人幸存；机长按旧航图（`charts`）的字符习惯输入 Cali，系统里该字符对应反方向的 Bogota，飞机撞山。
    * 做法前提是先做用户画像分析：分析飞行员在不用该软件时怎么工作，设计的字符集与旧航图保持一致。
    * 这一问题应当由测试人员提出，同时设计用户界面时也该考虑到。
    * > 来源: P17

* **测试计划的启动时机（Test Plan Timing）**
    * 测试计划不依赖已经存在的代码：拿到 `design` 就能写"测哪几个环节、重点测哪些部分"。
    * 代码尚未开始写时，`test plan` 就可以做，因为计划描述的是"打算怎么测"。
    * > 来源: P17

### 1.2 测试团队的交付物

* **五类交付物（Testing Deliverables）**
    * `errors`：bug 清单；`test cases`：测试用例清单，按 `test case` / `expected output` / `actual output` / `status` 四栏列表。
    * > 定义：`status` 记录该用例的实际输出与预期是否相符，不相符即为一个 bug，并标注已改、`pending` 或 `corrected`。
    * `requirements conformance`：在多大程度上遵守了需求；`performance`：效率、安全性等指标逐条对照。
    * `an indication of quality`：总体评价被测软件质量的指标。
    * 易错点：每个功能都正确，合在一起未必是需求描述的那个软件，功能正确不能替代 `requirements conformance` 的检查。
    * > 来源: P17

| 交付物 | 内容 |
| :--- | :--- |
| `errors` | bug 清单，最直接的一项 |
| `test cases` | `test case` / `expected output` / `actual output` / `status` 四栏的表 |
| `requirements conformance` | 在多大程度上遵守了 `requirements` 的要求 |
| `performance` | 效率、安全性等指标逐条对照 |
| `an indication of quality` | 总体评价被测软件质量的指标 |

### 1.3 测试的推进顺序与参与者

* **由小到大的测试顺序（Test Approach）**
    * 从 `component level` 出发，向 `integration`、再向整个 `system` 一点一点完成。
    * 技术分工：`unit testing` 一般用白盒测试，`integration`、`system testing` 用黑盒测试。
    * > 来源: P17

    ```text
      一件一件做出来的 component
              |
              |  unit testing（写它的人自己做，一般用白盒）
              v
         component level
              |
              |  integration testing（黑盒）
              v
          integration
              |
              |  system testing（黑盒）
              v
            整个 system
    ```

* **测试组的介入时点（Team Involvement）**
    * 从 `analysis` 阶段就旁观，了解系统整个成型过程，才能知道最薄弱、最容易出错的环节在哪里。
    * 拿到 `design` 就开始写测试计划；`integration` 阶段 `ITG` 进来与开发者密切合作，`system testing` 起逐步由独立测试组接手。
    * 参与者至少两种人：写程序的人自己，以及不写这个程序的独立测试人员。
    * > 来源: P17

* **测试与调试（Testing vs. Debugging）**
    * `Testing` 是发现错误并给出 `report`，指出这个地方错了、这个模块有错。
    * `Debugging` 是改正错误的过程。
    * 两者是两种不一样的 `strategy`，要分别对待。
    * > 来源: P17

### 1.4 验证与确认

* **验证（Verification）**
    * > 定义：`Verification` 回答 `Are we building the product right?`，检查每一个模块的功能是不是都正确。
    * 检查对象是模块级、功能级的正确性。
    * > 来源: P17

* **确认（Validation）**
    * > 定义：`Validation` 回答 `Are we building the right product?`，检查全部功能合在一起是不是需求要的那个软件。
    * > 易错点：模块功能全对不代表整软件对——五官每个都画成美人形状，放到一起未必是一张人脸。
    * 这是 `SQA team` 最关注的两个环节。
    * > 来源: P17

| 对照项 | `verification`（验证） | `validation`（确认） |
| :--- | :--- | :--- |
| 回答的问题 | `Are we building the product right?` | `Are we building the right product?` |
| 检查什么 | 每一个模块、每一个功能是否都正确 | 全部功能合在一起是不是需求要的那个软件 |
| 画画的类比 | 每一个器官画得漂不漂亮 | 放到一起是不是一张人脸 |

* **测试与 SQA 的关系（Testing in SQA）**
    * `software testing is only one element of SQA`；`SQA` 即 `Software Quality Assurance`，软件质量保证，需要专门有一拨人做。
    * `Quality must be built into the development process, one cannot use testing to add quality after the fact.`
    * > 结论：质量取决于开发过程的严格程度，把质量责任全推给 `testing team` 是 `blame the testing team, that's not fair.`
    * > 来源: P17

### 1.5 测试团队的组成与三个误区

* **开发者自测（Developer Testing）**
    * 优势：熟悉内部结构，不必花时间重新理解程序，能较快设计出有针对性的 `test cases`。
    * 问题一："我已经测过了"的骄傲，交了就觉得肯定没问题。
    * 问题二：个人利益驱使——测试不过就要改，过 `deadline` 改不完要罚、奖金没有了，因而不会非常严格地测。
    * 问题三：每个人都有盲点，自己死都看不出来的东西换一个人看特别容易；两人盲点重合在一点上的可能性比较小。
    * > 来源: P17

* **独立测试组（Independent Test Group, ITG）**
    * 与开发方利益对立：抓到多少 bug 给多少奖金，因而会全力以赴多抓 bug，质量保证效果更好。
    * 代价是要多花时间，也就意味着要多花钱，要付人家这一段时间的工资。
    * > 来源: P17

| 谁来做测试 | 好处 | 问题 |
| :--- | :--- | :--- |
| 开发者自测 | 熟悉内部结构，不必花时间重新理解程序，能较快设计出有针对性的 `test cases` | "我已经测过了"的骄傲；改不完就过 `deadline`、丢奖金，受个人利益驱使；人人有盲点 |
| 独立测试组（`ITG`） | 与开发方利益对立，抓到多少 bug 给多少奖金，会全力以赴多抓 bug，质量保证效果好 | 要多花时间，也就意味着要多花钱，得付人家这段时间的工资 |

* **三个需要避免的误区（Three Misconceptions）**
    * `developers do no testing at all` 不成立：前期的 `unit testing` 与初期的 `integration`，`developer` 都要参与。
    * `tossed over the wall` 不成立：交出去不等于没责任，`testing team` 一般不做 `debugging`，改错还是要开发者来改。
    * `Testers are not involved with the project until it's time for it to be tested` 不成立：`testing team` 从 `analysis` 阶段就在旁观。
    * > 来源: P17

* **测试策略中强调的六条做法（Testing Strategy Requirements）**
    * `Specify product requirements in a quantifiable manner before testing starts.`：需求规格最后的 `validation criteria` 要尽可能量化为一系列指标。
    * 测试之前把 `testing objectives` 清楚明白地写进测试计划：要测可用性的哪几个功能、测 `performance` 的哪几个点、测到什么指标。
    * `Identify categories of users and develop a profile for each.`：用户群分几类，每一类的 `profile` 都写出来，测试时按用户习惯去用软件。
    * `test plan` 最好是 `rapid cycle`：一个功能加进来测一下、快速迭代，而不是一次性想测得很完整再总结。
    * `Build robust software that is designed to test itself.`：软件设计时要考虑各种异常、自己做异常处理、抛出有用的异常信息，动不动就"蓝屏"的软件没法测下去。
    * `formal reviews as a filter`：正式测试之前先做 `formal review`，不运行代码、由作者从上到下讲有几个分支怎么走、一帮人听，相当于一群人在做抽象的 `testing`，能滤掉大部分关键错误。
    * > 来源: P17

* **进度量化的植入错误法（Error Seeding）**
    * 需求量化要解决"已找到 90% 的 bug"这类说法：全部 bug 总数未知，比例就没有分母。
    * 做法：按以往经验设计 N 个错误悄悄植入软件，再交给测试人员去测；每周从错误清单里统计植入错误被找回多少，找回 90% 就说测试完成了 90%。
    * 机理是给自己人造一个已知的分母——植入的错误已知存在，其找回比例才是个算得出来的量。
    * > 易错点：植入错误成本相当高，而且植入的错误本身是否"干净"、会对软件产生什么影响，并没有十足把握。
    * 另一条路是从公司第一个 `project` 开始就随时度量、随时收集数据，供后面估计还剩多少错没被找出来。
    * > 来源: P17

### 1.6 结构化与面向对象软件的测试策略

* **结构化软件的测试策略（Traditional Testing Strategy）**
    * `unit testing`：一个 `component` 一个 `component`，一个 `component` 基本属于一个 `team`。
    * `integration testing`：一点一点集成，每一次集成都做一次 `verification`——集成的功能是否正确、集成进来后这块功能是否还正确。
    * `validation testing`：按需求规格说明书最后那部分 `validation criteria`（功能、性能及其他标准）一条一条对照验收。
    * `system testing`：安装调试，装到实际使用的大环境系统下面测。
    * > 来源: P17

    ```text
      unit testing
      一个 component 一个 component，做完就测
            |
            v
      integration testing
      一点一点集成；每集成一步都做一次 verification
            |
            v
      validation testing
      对着需求规格说明里的 validation criteria 一条一条验收
            |
            v
      system testing
      安装调试，装进实际使用的大环境
    ```

* **面向对象软件的测试策略（OO Testing Strategy）**
    * `unit testing` 测一个一个 `class`：一个 `class` 就是一个 `unit`、一个 `component`；测一个 `class` 与测一个功能模块复杂程度不是一个量级。
    * `integration testing` 尤其复杂：要覆盖 `class` 与 `class` 之间的关系，做全排列式的完全测试根本测不完，只能在有限时间精力下把主要东西测到。
    * `system testing`：按一种方式把整体效果与 `requirements` 对照起来测。
    * > 来源: P17

* **测试的结束判据（When Are We Done）**
    * 理想答案是 `never`：充分复杂的系统做穷尽测试不可能，不能做穷尽测试就永远不敢说里面没有 bug。
    * 实际判据是 `when you run out of time, or you run out of money.`
    * > 结论：测试只是发现错误的过程，永远不能证明软件没有错误；一个错误都没测出来也只能说明测试可能太弱。
    * > 来源: P17

## 2. 单元测试的驱动模块与存根模块

> **一句话主旨**：单元测试围绕模块灌用例、出结果，靠驱动与存根两类辅助模块把错误来源锁在被测模块自身。

### 2.1 驱动模块

* **被测对象与用例覆盖面（Unit Testing Scope）**
    * 输入是一个模块（`module`）加一堆 `test case`，输出是结果（`results`），也就是一份 bug 清单。
    * `test case` 要覆盖的五个方面：接口（`interface`）、数据结构（`data structures`）、边界条件（`boundary conditions`）、独立路径（`independent paths`）、出错处理路径（`error handling paths`）。
    * > 来源: P18

* **驱动模块（Driver）**
    * > 定义：驱动模块是包围在被测模块外面的那层"壳"，负责供数据、调模块、收结果、做比对。
    * 三件事：接收所有 `test case` 并一个一个喂给模块、把模块产生的结果打出来、检查结果是不是有问题。
    * 类比：Online Judge（ZOJ、PAT）的判题软件就是 `driver`，提交的代码就是 `module`；数值分析课只交一个函数而 `main` 由老师写，那个 `main` 就是 driver。
    * 被测模块本身不需要知道自己在被谁调用。
    * > 来源: P18

    ```text
             +-----------------------+
             |        driver         |
             |  读入 input（测试用例） |
             +-----------+-----------+
                         |  逐个取出 test case
                         v
             +-----------------------+
             |   module（被测模块）    |
             +-----------+-----------+
                         |  返回 result
                         v
             +-----------------------+
             |  输出 result 并检查     |
             +-----------------------+
    ```

### 2.2 存根模块

* **存根模块（Stub）**
    * > 定义：存根模块是一个假的子模块（`sub-module`），接口与真实 `sub-module` 一模一样，但内容是空的、假的。
    * 存在理由：被测模块内部还调用子模块时，结果错了就说不清是当前模块的错还是下层的错。
    * 两步做法：先把传进来的参数打出来确认调用方传参正确；再写一个类似 `switch-case` 的结构，直接返回该用例**已知正确**的值。
    * 之所以能这么做：事先知道 `test case` 有哪些，也就知道这些用例下正确的返回值应该是什么。
    * > 易错点：stub 的返回值是照着自己的 `test case` 事先写死的，它只能证明"在下层完全正确的前提下这个模块对不对"，不能替代对下层的真实测试。
    * 效果：被调用的 `sub-module` 保证不产生任何错误，driver 输出不对就只能是这个模块自己的问题。
    * > 来源: P18

    ```text
      参数进来
         |
         v
     [打印/记录参数]  ---------> 确认调用方传参正确
         |
         v
     [switch-case 匹配测试用例]
         |
         +-- case 1  --> 直接返回该用例的正确返回值
         +-- case 2  --> 直接返回该用例的正确返回值
         +-- ...    --> ...
         |
         v
      返回值出去（不做任何真实计算）
    ```

* **辅助模块的工作量（Stub Cost）**
    * 模块越复杂、调用的底层模块越多，每个底层模块都要写一个相应的 stub，并针对每一个 `test case` 返回它的正确值。
    * 由此牵出策略取舍：自底向上要写很多 driver，自顶向下要写很多 stub，都得花工作量。
    * > 来源: P18

### 2.3 组装策略

* **大爆炸式集成（Big-bang Testing）**
    * 做法：每个模块分头去测，然后"啪"一下全部合到一起。
    * > 结论：big-bang 最大的问题是 `isolation of causes is complicated`——原因没有办法隔离，系统不正常时不知道是谁的错。
    * 后果是大家互相 finger-pointing："这肯定是他的""我都测过了"，每个人都认为自己的东西没问题。
    * 反例佐证：数据结构课允许三人一组各负责一个模块的最小生成树题（涉及最小堆、union-find、树与图结构维护），凡去挑战组合的组没有一个组合成。
    * 它只适合作为最终验收测试：五个组各自验收都对，再合成一个系统整体测一次。
    * > 来源: P18

* **自顶向下（Top-down）**
    * 做法：从最顶端的控制模块开始测，先写两个 stub 顶上去返回数据，再用真实模块一层一层往下替，直到测到底层模块。
    * 优点：主要的控制点、决策点（`major control or decision points`）最早被测到——大方向若错，底下越努力错得越厉害。
    * 缺点：从下面流上来的数据一直是假的，真实数据的复杂性要到最后才暴露。
    * > 来源: P18

* **自底向上（Bottom-up）**
    * 做法：把底层模块分成堆，一堆一堆测好，每测一个都要写不同的 driver；再用真实模块替代 driver，继续写上层的 driver，一层层往上走到顶端。
    * 优点：下面传上来的是真实数据，而且不用写 stub——stub 其实是比较难写的。
    * 缺点：最主要的、领导层面的控制模块最后才测到，万一最后发现它错了，下面全白干。
    * > 来源: P18

* **三明治集成（Sandwich Testing）**
    * 做法：一部分人从上往下测，一部分人从下往上测，大家在中间某一层汇合。
    * > 易错点：汇合层的协调成本高，是这种策略的主要风险。
    * > 来源: P18

| 策略 | 主要依赖的辅助模块 | 最早测到的部分 | 主要风险 |
| :--- | :--- | :--- | :--- |
| 自顶向下（top-down） | 大量 stub | 主要控制点与决策点 | 上层长期只见理想数据，底层真实数据的复杂性暴露太晚 |
| 自底向上（bottom-up） | 大量 driver | 底层工作模块 | 顶层控制模块最后才测，一旦错了下面全白干 |
| 三明治（sandwich） | 两者混合 | 上下两端 | 需要在中间某一层完成汇合，汇合层的协调成本高 |

### 2.4 回归测试、冒烟测试与测试准则

* **回归测试（Regression Testing）**
    * 场景：已经测过一遍，发现一个 bug 并改掉它之后，以前 pass 过的 case 要再重复执行一遍，因为改动可能影响别的模块。
    * > 易错点：回归测试不等于把以前所有测过的 case 全部重跑一遍，那太耗钱、太耗时间；要选比较重要、比较相关的部分重新测。
    * 失效案例：电话局系统升级后没做完整回归测试，把加州州内不同区号之间的 local 通话判成长途（`long distance`），账单从长途出口出，客户在 local 与长途两家公司之间被踢皮球。
    * 判据是"不可能做完全的回归测试，但那些比较重要的回归测试该做的没做就会出这样的问题"。
    * > 来源: P18

* **冒烟测试（Smoke Testing）**
    * 名字来自硬件测试：新零件插上板子没事则零件是好的，一插进来板子冒烟、炸了、短路，通常说明新插进来的这个零件是坏的。
    * 软件里的"板子"是一个 `build`：一个**已经测过的、可信的东西的集合**，包括源代码、数据库以及其它已测过的相关东西。
    * 日常做法是往 `build` 里加一个 component 就全部运行一遍，加进去后走不通通常就是新加进来的这个 component 有问题；每天把不同的 build 都测好后再集成并再测一遍。
    * > 易错点：策略关键是**怎么划分 build**——build 不能规模很大，把整个软件当成一个 build 则每天测一遍非常费劲，要划分到合适的 size。
    * 通常用在 `time-critical projects`（时间特别紧的项目）上。
    * > 来源: P18

* **测试准则的几个方面（Test Criteria）**
    * 接口完整性（`interface integrity`）：要有一类测试专门去测接口。
    * 功能正确性：要有一类测试去测功能是不是对。
    * 数据结构：测局部与全局的数据结构（`local` / `global data structure`）定义得是否正确。
    * 性能：还需要测 `performance`。
    * 写 `test specification` 的具体建议在书上占两页，就是下一次要交的 report。
    * > 来源: P18

## 3. 面向对象测试与系统测试

> **一句话主旨**：OO 的类测试基于状态行为而非数据流图，系统测试把恢复、安全、压力、性能四类测到边界。

### 3.1 面向对象测试的三个层次

* **类作为测试单元（Class as Unit）**
    * 传统的一个 unit 基本只完成一个功能，测它这个功能正确与否就够；一个 `class` 可不止一个功能，它是一个对象，要干好多事情，相当于一个小软件。
    * > 易错点：即使每一个功能单独都是正确的，也不代表这个 `class` 的实现就是正确的。
    * > 结论：类的测试不是基于数据流图的，而是基于状态行为（`state behavior`）来测的——要测的是操作（`operations`），更是对象的状态迁移。
    * 状态转换图（`state transition diagram`）有两种，一种是整个系统运行中的状态与转换，一种是针对每一个 `class` 的：一个 object 有哪几个状态、由哪几个动作触发迁移，这些就是测试的点。
    * > 来源: P18

* **基于线索的测试（Thread-based Testing）**
    * > 定义：线索（`thread`）是从给系统一个输入、到系统内各对象互相协作完成一系列动作、最后给出输出的那一条执行线。
    * 测的是这条线索执行过程中每一个 `class`、每一个 `object` 的表现是不是都对，一条线一条线地测过来。
    * > 提示：这其实就是 use case——针对需求，一个 use case 一个 use case 地测过来。
    * > 来源: P18

* **基于使用的测试（Use-based Testing）**
    * 做法：先找基本上不怎么用到别人、比较独立、被别人调用的 `class` 测好，再去测调用它们的 `class`，一圈一圈往外扩，类似传统自底向上。
    * > 易错点：传统架构是层次结构往上走，面向对象不是——它是一个图，互相乱七八糟地调用，所以更复杂。
    * > 来源: P18

* **簇测试（Cluster Testing）**
    * 依据是 `CRC cards` 里最重要的第二个 C——`collaborators`：一张 CRC card 描述一个 `class` 及与它相关的那些 `class`。
    * 做法是一拎拎起一串而不是拎起一个：把所有与它相关的卡片全抓出来，抓出来一坨就是一个 `cluster`，然后论墩地测、一堆一堆地测。
    * 测的是它们之间的协作（`collaboration`）。
    * > 来源: P18

### 3.2 确认测试与验收方式

* **确认测试（Validation Testing）**
    * 依据是 `requirement specification` 最后的 `validation criteria`，用里面的 `use case`、行为（状态）、`event flow diagram` 跑一遍。
    * 除功能之外还要检查配置（`configuration`）：文档、数据库等各种东西是不是都配齐了。
    * > 来源: P18

* **Alpha 测试（Alpha Testing）**
    * 做法：把 TA 叫到你那儿去，但不许 TA 碰你的机器；他在后面看着，你操作软件并讲解每个功能怎么用，然后问他觉得可不可以。
    * > 来源: P18

* **Beta 测试（Beta Testing）**
    * 做法：你靠边站，TA 坐下来用这个软件，你在后面看着；他不再受你约束，想怎么动就怎么动。
    * 对应场景是 beta 版已经放到玩家或用户手里，管不到他们怎么操作。
    * > 易错点：无论 alpha 还是 beta，都一定要有一个文档人员在旁边记录 `deficiency list`（错误清单）。
    * > 来源: P18

### 3.3 系统测试的四种类型

* **恢复测试（Recovery Testing）**
    * > 定义：恢复测试是先让系统垮掉、再让它恢复，看恢复的程度如何。
    * 做法来自 95 年浙大主办的 ACM-ICPC 亚洲区赛：一百多台机器各装一个机器人，一声令下所有志愿者启动机器人疯狂提交，系统被冲垮，随后启动备用系统并迁移服务器数据。
    * 目标是崩溃时立刻切到备用系统且不丢任何东西，原来的 submission 全部都在、可以直接继续比赛。
    * 当时一直弄到半夜快 12 点才搞定，根因是服务器上的 Linux 版本与开发者笔记本上的版本差了一点点。
    * > 来源: P18

* **安全性测试（Security Testing）**
    * 要试各种黑客攻击，看系统的防御能力。
    * > 来源: P18

* **压力测试（Stress Testing）**
    * 回答的问题是"到底多大的冲击量是这个系统可以承受的"，即所有机器人一起攻时到什么程度服务器就挂了。
    * 与恢复测试通常是合在一起做的。
    * 数据用途：比赛要设"一秒钟之内不能提交超过多少次"的门槛，这个次数根据 `stress testing` 的数据算出来，用来做事先防范。
    * > 来源: P18

* **性能测试（Performance Testing）**
    * 测系统的效率。
    * > 来源: P18

### 3.4 调试过程与技巧

* **调试流程（Debugging Process）**
    * 闭环是：执行 `test case` → 发现错误 → 猜测/估计错误由什么造成 → 加 `additional test` 验证 → 证明的确是这里错 → 改正错误 → 做一定的回归测试。
    * > 易错点：少了"加用例验证"这一步，改的很可能不是真正的病根。
    * 调试是 `the art of debugging`，是一门艺术。
    * > 来源: P18

    ```text
      执行 test case
            |
            v
         发现错误
            |
            v
      猜测/估计错误是由什么造成的
            |
            v
      加一些 additional test（新的 test case）去验证
            |
            +---- 没证明 --> 回到"重新猜测"
            |
            v
       证明的确是这里错
            |
            v
          改正错误
            |
            v
       做一定的回归测试
    ```

* **蛮力法（Brute-force Testing）**
    * 最牛的做法是 `memory dump`：把程序出错那一瞬间的内存全部打印出来，八进制的 code，从里面读、从里面找错误。
    * 另一种是 `spy points`。
    * > 来源: P18

* **回溯法（Backtracking）**
    * 程序不太大时，在程序中间插一个断点看这时候是对的还是错的。
    * 判断规则：这时候已经错了说明错误在上面；这时候数据是对的说明错误在下面。
    * > 提示：可以把它理解为一个二分的过程。
    * > 来源: P18

* **归纳法（Induction）**
    * 在很多公司里用的方法：每天领一张表按给定输入、给定输出逐项做测试，跑出输出后记录对与不对。
    * 不对时填一张表，写清三个 W 一个 H——`What`、`Where`、`When`、`How`，描述这个错误。
    * 三个 W 的填法：`What` 有哪些、有什么、没什么；`Where` 在哪里有、在哪里没有；`When` 什么时间发生了、什么时间没发生——凡"有的"放一栏、"没有的"放另一栏。
    * 交表后程序员据此猜、分析大概会有哪些 causes。
    * > 来源: P18

* **演绎法（Deduction）**
    * 就是侦探的演绎过程：先有很多怀疑对象、嫌疑人，调查中一个一个排除，最后剩下的那个就是真正的 cause。
    * > 来源: P18

* **改 bug 的三点注意（Bug Removal Consideration）**
    * 产生这个 bug 的原因，是不是在程序的其它地方也出现了、会不会在别处也有类似的错。
    * 把这个错误改过来之后，下一个 bug 有可能是什么。
    * 总结一下经验教训：为什么会犯这样的错误、下次怎么才能不重复犯。
    * > 来源: P18

## 4. 白盒测试：控制流图、环形复杂度与逻辑覆盖

> **一句话主旨**：白盒测试只对小段代码做，靠控制流图算环形复杂度，再按覆盖强度逐级加强用例。

### 4.1 测试用例的判定标准与可测试性

* **好测试用例的判定标准（Good Test Criteria）**
    * 覆盖要全面：一套 case 强不强，看它有没有把被测模块"应该有的性质"都覆盖掉。
    * 每个 case 要有充分代表性、不能冗余（`redundant`）：输入范围 1 到 100 的整数里测 `n = 5`、`10`、`18`、`86` 没有意义。
    * 完备测试（`exhaustive testing`）是 1 到 100 全部测一遍，把 100 个 case 塞给 PAT 会因每 case 单开虚拟空间把系统搞挂。
    * 用例必须有很大可能找到错误：很多错误能溜过去的 case，通过了也一点用都没有。
    * 用例要 `best of breed`：有 deadline、只够"咬一口"时，选最有代表性的那几个。
    * 用例复杂度要适中：一个 case 只查一个错误时 `debug` 最省事，但那样需要很多很多 case、很多人执行，不合算；太复杂则十几个测试点里错一个也不知道是哪一个。
    * > 结论：设计 `test case` 时随时放着三件事——目的（`uncover errors`）、方式（`in a complete manner`）、约束（`with a minimum of effort and time`）。
    * > 来源: P19

* **案例难度对照（Sample Engineering）**
    * 竞赛题特别是国际竞赛题的 `sample` 给得很少、很傻：过了它什么都不表示，程序可能 80% 是错的也能过。
    * PAT 的 sample 有技术含量：一般 cover 掉一半以上的测试点，sample 过了起码有 60% 的可能是对的，剩下 40% 边边角角的点再用其它点测。
    * 比较合算的做法是一个 case cover 掉 50% 到 60% 的测试点，攻克它说明这一堆东西都过掉了。
    * > 来源: P19

* **可测试性的七个组成指标（Testability）**
    * `testability` 不像可靠性（`reliability`）或可用性（`availability`）那样能用一个公式算出百分比，它由很多个 `ability` 共同决定。
    * `operability` 可操作性：软件好不好操作、操作的方便性决定测试难易。
    * `observability` 可观察性：执行时能看到多少；整个软件是一个黑盒（只有一个接口、一个按钮，中间完全碰不到）对测试团队来说非常恐怖。
    * `controllability` 可控制性：测试人员在多大程度上能控制软件，权限足够大才可能设计自动化测试，如 PAT、ACM 的 judge 程序。
    * `decomposability` 可分解性：能拆成多小的块，块小就好测。
    * `simplicity` 简单性：被测软件本身有多复杂，越简单越好测。
    * `stability` 稳定性：开发过程稳不稳；刚测完一块需求就变、版本还没测完下一个版本又来了，所有人都会抓狂。
    * `understandability` 可理解性：设计文档与代码有多好懂；需求有了黑盒测试策略基本能出来，设计有了部分白盒测试策略也可以出来。
    * > 来源: P19

    ```text
     testability
       |-- operability        可操作性：这个软件好不好操作
       |-- observability      可观察性：执行过程你能够看到多少
       |-- controllability    可控制性：测试人员能控制它到什么程度
       |-- decomposability    可分解性：能拆成多小的块
       |-- simplicity         简单性：被测软件本身有多复杂
       |-- stability          稳定性：开发过程稳不稳
       |-- understandability  可理解性：设计文档与代码有多好懂
    ```

### 4.2 白盒测试要回答的四个问题与独立路径

* **穷尽测试的组合规模（Why Not Exhaustive Testing）**
    * 书上算例：流程图里只有 5 个 `if-else` 分支，其中有一个循环执行 20 次，每次 5 种走法，完备用例数是 $5^{20}$。
    * $5^{20}$ 是十多万亿量级的组合数，按书上估算要花差不多 3000 多年才能把这么小的程序做完备测试。
    * > 结论：`testing cannot show the absence of errors and defects`；只要不是穷尽测试，就永远不能说"可以保证这个软件里面是没有 bug 的"。
    * 只能说：有 bug 你没查出来、以你现在的能力和经验查不出来了、在有限时间范围内能测的就这些。
    * > 来源: P19

* **白盒测试的范围（White-box / Glass-box Testing）**
    * 也叫 `glass-box testing`：看得见程序内部，非常清楚地知道那个程序流程图。
    * 只能用于 `testing in the small`——对小段的代码做测试，即单元测试、调试阶段做的事。
    * 强调重点是每一个 `path`，希望达到尽可能好的对路径的逻辑覆盖。
    * > 来源: P19, P20

* **必须回答的四个问题（Four Questions）**
    * `can you guarantee that all independent paths within a module will be executed at least once?`——保证所有独立路径至少执行一次，也就是图中每条边至少走一遍，这是非常弱的要求。
    * `can you exercise all logical decisions on their true and false branches?`——凡 `if-else`、`switch-case` 这类控制节点的 yes 和 no 两种可能都测到。
    * `will all loops execute at their boundaries and within their operational bounds?`——循环的边界是一进一出那两个点；循环 1 到 100 时，1 和 100 就是边界，要设计只循环一次就跳出的 case，也要设计循环满 100 次才跳出的 case。
    * `can you exercise internal data structures to ensure their validity?`——如数组要设计用到最大极限的 case 看会不会溢出、`run-time error`、跑到中间就崩溃。
    * 前两个问题关于逻辑覆盖，后两个关于数据与边界。
    * > 来源: P19

* **独立路径（Independent Path）**
    * > 定义：独立路径是不可能由其它路径组合出来的路径，它一定至少有一条边是别的路径没有覆盖到的。
    * 对应线性代数里线性无关组的概念：任何一个向量都不能被其它向量组合出来，总有自己独特的、别人 cover 不了的一点。
    * > 来源: P19

### 4.3 控制流图与环形复杂度

* **控制流图（Flow Graph）**
    * 画法：凡是顺序执行的语句都缩成一个点，看成图里面的节点并编号，把流程图简化成一个平面上的、二维的有向图。
    * 分支节点要细看：`do while` 的条件 `total < 1000 and a != 0` 里含一个 `and`、测的是两方面，这个节点最好拆成两个节点。
    * 拆开后边也跟着细化，相当于这里是两次判断。
    * > 来源: P19

    ```text
     拆之前（一个节点里藏着两次判断）
         ... ---> < total < 1000  and  a != 0 > ---> ...

     拆之后（串成两个条件节点，边也跟着细化）
         ... ---> < total < 1000 > --T--> < a != 0 > --T--> ...
                        |                       |
                        F                       F
                        |                       |
                        +-----------+-----------+
                                    |
                                    v
                           （循环出口 / 后继语句）
    ```

* **环形复杂度的三个等价定义（Cyclomatic Complexity）**
    * 连通域的个数：图是画在平面上的，它把整个平面切成几个连通域，环形复杂度就是几。
    * 边数减节点数加 2：$E - N + 2$。
    * 分支节点数加 1：$P + 1$，$P$ 是谓词节点（`predicate node`）的个数。
    * > 定义：分支节点就是出去的箭头不止一个的节点。
    * 课上第一个算例：图上有三个分支点，$3 + 1 = 4$，同时整个平面也被分成四个连通域，所以那个程序的环形复杂度等于 4。
    * 下面示意图的三个定义对照：连通域 3 个；$7 - 6 + 2 = 3$；$2 + 1 = 3$。
    * > 来源: P19

$$CC = E - N + 2 = P + 1$$

| 等价定义 | 内容 | 用下面那张示意图核对 |
| :--- | :--- | :--- |
| 连通域的个数 | 图是画在平面上的，它把整个平面切成了几个连通域，环形复杂度就是几 | 3 个 |
| 边数减节点数加 2 | $E - N + 2$ | $7 - 6 + 2 = 3$ |
| 分支节点数加 1 | $P + 1$，$P$ 是谓词节点（predicate node）的个数 | $2 + 1 = 3$ |

    ```text
       +------+                N = 6  （节点数）
       |  s1  |                E = 7  （边数）
       +------+                P = 2  （分支节点数）
          |
          v
      < cond A > --T--> +------+
          |             |  s2  |
          F             +------+
          |                |
          |                v
          +----------> < cond B > --T--> +------+
                         |              |  s3  |
                         F              +------+
                         |                 |
                         v                 v
                      +------+ <-----------+
                      |  s4  |
                      +------+
    ```

* **环形复杂度给出的用例数上限（Upper Bound of Test Cases）**
    * 书上说法：`the number of independent paths in the basis set of a program, and provides us with an upper bound for the number of test cases that must be conducted`。
    * > 结论：算出 4 就表示**最多**只需要设计 4 个 case 就能做到"每个 statement 至少执行一次"，当然也可以设计得更少；它是上限而不是下限或恰好值。
    * $P + 1$ 这个定义最有用，因为它直接与分支节点个数相关：分支越多这个数越大，每多一个分支就多出来一条路要走。
    * 分支节点的个数决定了这个程序测试的难度，它表示有多少个 `independent path` 要测。
    * > 来源: P19

### 4.4 逻辑覆盖强度的逐级加强

* **语句覆盖（Statement Coverage）**
    * 要求 `execute every statement at least once`：保证没有哪一段是没意义的、冗余的、直接被跳过去的语句。
    * 复合条件程序要先拆点再画图，算得环形复杂度是 5，即最多需要 5 个 case 就能让每个 statement 至少执行一次。
    * 但达到语句覆盖**最少一个 case 就够了**：条件覆盖非常弱，只保证每句被执行一遍，不要求每个分支都被执行一遍；课上当场设计的输入是 `a = 3`、`b = 0`，算得 `x` 为 $4/3$ 大于 1，拐到另一支上去，每个语句都被执行了一遍。
    * > 易错点：语句覆盖查不出复合条件的逻辑运算符错误——本该写 `and` 的地方写成 `or`，这个 case 还是对的，程序却是错的；查不出来的原因是有个分支从未被测到。
    * > 来源: P19

* **条件测试的最少用例数（Condition Testing）**
    * 目标是把整句话测完备：**这一句话里面所有可能的 `true` 和 `false` 都要被至少测到一次**。
    * 系统化做法：先把两个分支当成整个一句话看（`Branch 1`、`Branch 2`，中间是 `and`），让整个语句既出 `true` 也出 `false`，同时两个分支各自也要取到 `true` 和 `false`，**至少三个用例**就够。
    * 三个用例的分工：一个让两者都取 `true`、整个语句为 `true`；一个让一假一真、整个语句为 `false`；一个让一真一假、整个语句为 `false`。
    * > 易错点：不要图省事写 `(T,T)` 加 `(F,F)`——那样两个分支的取值被绑在一起同时真、同时假；用 `(T,T)`、`(F,T)`、`(T,F)` 才能在一个分支取值变化时观察另一个分支。
    * > 来源: P20

* **从分支取值展开到关系表达式（Relation Expansion）**
    * 抽象 `T`/`F` 要再细化：`B1` 为 `T` 意味着让 `E1` 和 `E2` 相等；`B1` 为 `F` 意味着设计两个用例，一个大于、一个小于。
    * 于是 `B1` 位置上的 `T` 拆成"等于"，`F` 拆成一个"小于"加一个"大于"，用例数变成四个。
    * 再把 `B1` 换成真正要测的 `E1 > E2`：`T` 直接翻译成"大于"，`F` 要翻译成"小于"加"等于"；`B2`（`E3 < E4`）同样处理。
    * 合并四次翻译的结果得到五组数据。
    * > 易错点：五组不都是"新增覆盖"——C1 是最初的 `(T,T)`；C2 是 `B2` 的 `T` 拆出的那一组的第一个；C3 是 `B1` 的 `T` 拆出的那一组的第二个；C4、C5 是 `B1` 的 `F` 拆出的"小于/等于"两组。
    * 分支覆盖的下限是三组，要做到每个条件都取到每个取值就得把 `T`/`F` 拆成关系取值，用例数自然涨到五组。
    * 考试常出这类题：给一个比较复杂的复合语句（`compound statement`），要求**用最少的测试用例**把它测完备，并保证每一个 `true` 和 `false` 都被执行过。
    * > 来源: P20

| 编号 | `E1 > E2` | `E3 < E4` | 这一组要覆盖的取值 |
| :--- | :--- | :--- | :--- |
| C1 | `E1 > E2` 成立 | `E3 < E4` 成立 | 两分支同真 |
| C2 | `E1 < E2` | `E3 < E4` 成立 | 第一分支假（小于）、第二分支真 |
| C3 | `E1 > E2` 成立 | `E3 > E4` | 第一分支真、第二分支假（大于） |
| C4 | `E1 = E2` | `E3 = E4` | 第一分支假（等于）、第二分支假（等于） |
| C5 | `E1 > E2` 成立 | `E3 = E4` | 第一分支真、第二分支假（等于） |

### 4.5 数据流测试与循环测试

* **数据流测试（Data Flow Testing）**
    * 关注数据在程序里的变化：一个变量取值在程序里怎么变，就像调试时一步一步执行下来看它取到多少。
    * 做法是把程序拆解，对**每一个变量**去找它在哪些地方被定义、在哪些地方被用到。
    * > 定义：对一条语句 `S`，`def of S` 是所有在这条语句里被定义的变量的集合；`use` 是这句话用到了哪些变量——它在读取这些变量的值，虽然并没有改变这些值。
    * > 定义：DU 链（`definition-use chain`，定义-使用链）是一个 `D` 加一个 `U`，看变量在哪几条语句里被定义、在哪几条语句里被使用，而且要顺序地往下走——中间没有被改动过，用到时用的确实是上面给的那个定义；串起来就是 `the flow of X`。
    * 覆盖标准是 `every DU chain is covered once`：以 DU 链为单位，一条链一条链地测过来。
    * > 提示："定义"和"使用"之间只要被中途改写过就断开成两条链，所以同一对语句中间有没有别的赋值，测试负担完全不同。
    * > 来源: P20

* **简单循环的边界用例（Simple Loop）**
    * 若从 1 到 n 循环，循环 1 次、循环 n 次肯定要测。
    * 还要测非法的循环——直接跳过的 0 次循环；以及有没有可能让它循环 n+1 次，会怎么样。
    * 还有正好卡在边界上的 n-1 次循环，循环最容易出错的地方就是边界附近。
    * 最后在中间随便取一个数让它循环一下。
    * > 易错点：这里的 n 不是事先定好、你让它循环多少次就行，n 指的是**输入数据的规模**：输入数据的 `size` 可能是 1 也可能是 100，1 要测、100 要测；这组边界用例的落地形式就是取一组最小规模、一组最大规模、一组中间规模的数据。
    * > 来源: P20

* **嵌套循环与串接循环（Nested / Concatenated Loops）**
    * 嵌套循环（`nested loops`）：先让外循环不执行或者只执行一次，然后先把内循环测完备；内循环测完就当成一个已经完整测过的模块不再去管，再用普通策略去测外循环。
    * 串接循环（`concatenated loops`）：一个一个顺着循环往下测。
    * 还有一类循环碰到就只有一个办法：直接踢回去、说我不测——程序不能这么写，把程序直接退回给程序员、拒绝测。
    * > 来源: P20

## 5. 黑盒测试：等价类划分与边界值分析

> **一句话主旨**：黑盒测试只看外部表现、用于集成之后，落地靠等价类划分定类、边界值分析在接缝上布点。

### 5.1 黑盒测试用例设计要考虑的因素

* **黑盒测试的范围（Black-box Testing）**
    * 也叫 `testing in the large`：不关心程序内部结构，只关心外部表现是不是正常；基本上用在集成测试之后。
    * 设计用例时脑子里要有七个问题：功能点一个个都要测到；行为（`behavior`）的各个状态过渡是否正常；性能（`performance`）若有要求要测。
    * 输入的分类（`classes of input`）：输入怎么分类、哪些类比较有代表性，这就是等价类划分。
    * 对什么输入特别敏感：系统对什么样的 `input` 特别敏感（`sensitive`）要非常小心地测到——这种数据有错时系统是整个崩溃还是怎么样。
    * 数据类的边界：`how the boundaries of a data class are isolated`，怎么确定每一类数据的边界。
    * 数据速率与数据量：`what data rates and data volume can the system tolerate`，意味着应该做压力测试（`stress testing`）。
    * 再往外一层是各种输入数据的排列组合对整个系统表现的影响，怎么设计这些组合也是策略里要考虑的。
    * > 来源: P20

### 5.2 四种黑盒测试技术

* **基于图的测试（Graph-based Testing）**
    * 思路与白盒测试一致：白盒把一段程序变成一张图、通过分析图的复杂性判断测试与代码的复杂性；对整个系统也有办法把系统映射到一张图。
    * 不展开，属于研究生的更高级内容。
    * > 来源: P20

* **正交数组测试（Orthogonal Array Testing）**
    * 针对的问题：输入是三个不同种类、不同参数，每个都有自己的取值范围，不仅要测每个参数的取值范围，还要把排列组合有效测到。
    * 为难之处：穷尽排列组合工作量太大，选择性测又一定会漏掉一些组合，关键是确定哪几种组合比较有代表性。
    * 属于专门技术，不展开。
    * > 来源: P20

* **两类必用技术的连带关系（Equivalence Partitioning and Boundary Value Analysis）**
    * 等价类划分与边界值分析是所有软件测试里都必须有的两类技术。
    * 两件事连在一起：先划分等价类，类一划分好它的边界就有了，然后有效地在边界上做重点测试。
    * > 来源: P20

| 技术 | 关注的问题 | 本篇取舍 |
| :--- | :--- | :--- |
| `graph-based testing`（基于图的测试） | 先把系统映射成一张图，再分析这张图的复杂性 | 不展开，属于研究生的更高级内容 |
| `equivalence partitioning`（等价类划分） | 输入应该分成哪几类才等价 | **重点** |
| `boundary value analysis`（边界值分析） | 每一类的边界上该怎么布用例 | **重点** |
| `orthogonal array testing`（正交数组测试） | 多个参数取值范围的排列组合，怎么挑出有代表性的 | 不展开，属于专门技术 |

### 5.3 等价类划分

* **等价类（Equivalence Class）**
    * > 定义：等价类是这样一类元素的集合——`There is no particular reason to choose one element over another as a class representative`，在这个集合里面随便挑哪一个效果都是一样的。
    * 例：1 到 100 这个整数范围里挑 18、39 还是 97 没有区别，这些整数在测试方面是等价的。
    * 判定一个类划得对不对，就看"类里任意两个元素互换，测试结论会不会变"。
    * > 来源: P20

* **按输入形式划分的指南（Partitioning Guidelines）**
    * 一个范围：一个合法类加两个非法类，至少三类——合法是 1 到 100 时，类内取一个数、小于 1 的整数一类、大于 100 的整数一类。
    * 一个确定的值：等于它一类、大于它一类、小于它一类，共三类。
    * 一个集合：属于这个集合的一类、不属于的一类——说"教师"是一个集合时，所有教师是一个等价类、所有非教师人员是另一个等价类。
    * 布尔条件：`yes` 一类、`no` 一类。
    * > 来源: P20

| 合法输入的形式 | 等价类怎么划 | 举例 |
| :--- | :--- | :--- |
| 一个范围 | 一个合法类 + 两个非法类，至少三类 | 合法是 1 到 100：类内取一个数；小于 1 的整数一类；大于 100 的整数一类 |
| 一个确定的值 | 等于它一类；大于它一类；小于它一类，共三类 | 合法值是 `X`：`X`、`> X`、`< X` |
| 一个集合 | 属于这个集合的一类；不属于的一类 | 开发一个系统说"教师"是一个集合：所有教师是一个等价类，所有非教师人员是另一个等价类 |
| 布尔条件 | `yes` 一类、`no` 一类 | 条件成立与不成立 |

### 5.4 边界值分析

* **边界值分析（Boundary Value Analysis）**
    * 边界值分析是几乎所有测试里面都必须用到的。
    * 现象支撑：第一次去 PAT 或竞赛网站做题的人常哭诉 sample 都过为什么还有错，去看程序错在哪儿，绝大部分的程序都错在边界上。
    * 真实例子：校赛一道简单题，十行不到的程序一交就 WA，看不出错；设计一个 `boundary` 用例直接取到最大值，取到最大值转一下就崩溃——因为答案超出长整型了。
    * > 结论：这种 bug 喜欢在墙角呆着，边边角角的地方是最容易出错的地方。
    * > 来源: P20

* **区间取值的布点规则（Range Guidelines）**
    * 给的是一个 range、`a` 到 `b` 时：两个端点 `a`、`b` 要取，端点本身合法、必须落在合法类里。
    * 下端点外侧：正好大于 `a`、正好小于 `a`——这是合法类与下方非法类的接缝，最容易误判。
    * 上端点外侧：正好大于 `b`、正好小于 `b`——这是合法类与上方非法类的接缝。
    * > 来源: P20

| 用例位置 | 取值 | 为什么要有它 |
| :--- | :--- | :--- |
| 两个端点 | `a`、`b` | 端点本身合法，必须落在合法类里 |
| 下端点外侧 | 正好大于 `a`、正好小于 `a` | 合法类与下方非法类的接缝，最容易误判 |
| 上端点外侧 | 正好大于 `b`、正好小于 `b` | 合法类与上方非法类的接缝 |

## 6. 面向对象用例设计与裁判数据设计

> **一句话主旨**：OO 用例是一组动作序列而非一组输入，裁判数据则把等价类与边界值落到具体测试点上。

### 6.1 OO 测试用例的构成与设计方法

* **OO 用例与传统用例的区别（OO Test Case Design）**
    * 传统用例就是一个用例、一套输入、一个测试目的、一个输出；OO 的一个 `test case` 不是一组数据的输入，而是**一组动作的执行过程**。
    * 传统用例设计由软件的输入-处理-输出（`IPO`）视图或单个模块的算法细节驱动，OO 测试关注的是设计合适的操作序列去走类所处的状态。
    * 用例要包含的要素：给一个单独的 ID 与名字；写清楚测**哪个 class**（类名）；写清楚测试目的是什么；最关键的是一份 `a list of testing steps`（测试步骤）。
    * 每个用例还要交代：这个 class 有哪几个状态、是不是所有状态都测到了；过程中哪些 `message`、接口、`operations`（也叫 `functions` 或 `methods`）被执行到；要做哪些步骤；测试的外部条件与准备条件；需要用到其它 `classes` 时它们该怎么配合。
    * > 来源: P20

* **基于故障的测试（Fault-based Testing）**
    * 有经验的老测试员有一套做好的 `test case`，闭着眼睛执行一遍，如果这一套都过了则绝大多数问题就没有了。
    * 做法是先想清楚软件最常会出错的地方有哪些，针对这些错误设计 `test case`，过一个就说明这方面的错误肯定没有了。
    * > 来源: P20

* **类测试与类层次（Class Testing and Class Hierarchy）**
    * 继承（`inheritance`）让编程时非常容易扩展、裁剪与修改，但测的时候就惨了。
    * 测完父类，子类那些来自父类的功能照样要测，因为它会变；把所有的子类都测完了，父类也照样要测。
    * > 结论：编程的时候继承给你省了事，测试的时候它只会让你变得更复杂。
    * > 来源: P20

* **基于场景的测试（Scenario-based Testing）**
    * 做法是把 `use case` 一个一个走一遍。
    * 重点是**用户的使用过程**而不是软件内部逻辑的执行过程；使用过程正常，内部逻辑仍然有可能是错的。
    * > 提示：这几种方法都站在不同角度看同一个软件，最好结合起来用。
    * > 来源: P20

* **分类测试的三种等价类定义（Classification Testing）**
    * 分类测试与传统软件工程的等价类划分是同一个道理，只不过在 OO 里等价类不像传统那样容易看出来。
    * 基于状态（`state-based`）：哪些功能让这个 class 从一个 state 换到另一个 state，这一类功能放在一起测。
    * 基于属性（`attribute-based`）：哪些功能集中在改这个 class 内部的某一个 attribute，与某一个 attribute 相关的所有操作放在一类。
    * 基于范畴（`category-based`）：按功能分类，根据这个 class 要完成的几大功能把相应操作绑在一起测试。
    * > 来源: P20

* **类间测试（Inter-class Testing）**
    * 把 class 理解成 `client` 与 `server` 的关系：一个是使用的、一个是被使用的。
    * 基本做法是先把几个 class 之间的关系划分成 client 和 server，再把它们之间交互的 `message` 和 `operator` 关系测好，以及与 `collaborator class` 之间的协作（`collaboration`）。
    * 具体方法不展开，基本上也是基于 `random` 的，没有什么特别好的办法去测它。
    * > 易错点：随机测试（`random testing`）能做到的第一步是定一个**最小的测试集合**——最低限度得把这些 cover 了，剩下的分支扩展再用随机组合去碰；随机不是不做底线覆盖。
    * > 来源: P20

* **基于状态转换图的测试（State Transition Diagram Testing）**
    * 前提是有非常清楚的行为（`behavioral`）描述、状态转换图画得清楚：图里面画的是 state，箭头上画的是"做了一个什么动作、导致它变成了这个状态"。
    * 用例设计方式是沿这条线把动作排列组合：什么都不做直接做下一个动作然后结束是一个 case；走到某处把这个动作做一下再往下走结束是一个 case；把两个动作组合做一下再往下走结束又是一个 case。
    * > 易错点：基于状态转换图设计用例用的是"动作序列"而不是"输入值"来标记覆盖，判断两个用例是否重复看的是动作序列是否等价，不是看输入数据是否相同。
    * > 来源: P20

    ```text
    (动作 a1)         (动作 a2)         (动作 a3)
    [初始状态]───► [中间状态一]───► [中间状态二]───► [结束状态]
          │              │                │
          │(什么都不做)  │(动作 b1)       │(动作 b2)
          ▼              ▼                ▼
    直接结束        另一条分支        另一条分支
    ```

* **其余测试内容与测试模式（Other Testing Types）**
    * 还要做图形用户界面测试（`graphical user interface testing`）、`client-server` 测试，以及 `help` 的测试。
    * 如果是实时系统（`real-time systems`），`performance` 也是必不可少的测试内容。
    * 测试过程中如果找到规律，可以抽象出一些 `testing patterns` 供以后 `reuse`。
    * `testing never ends`：即使把活儿交出去了测试也没完，只不过测试从你手里交到了客户手里，他会继续替你测试。
    * > 来源: P20

### 6.2 二分查找裁判数据的设计

* **题目与要交的东西（Problem Statement）**
    * 题目：在一串**有序**的整数里找一个给定的整数；心目中要用二分查找，用线性查找从头到尾扫描的实现必须在某个 case 上卡住。
    * 输入三行：第一行正整数 `n` 不超过 10 万；第二行 `n` 个整数，每个不超过长整型，用 `int` 即可；第三行整数 `X`；这 `n` 个整数保证按从小到大的顺序给出。
    * 输出：`X` 在这 `n` 个整数里回答 `yes`，否则回答 `no`。
    * 要交的不是程序而是裁判数据：case 无论如何不要超过 10 个、越少越好；要设计 `sample in` 与 `sample out`；每个 case 都要写清楚测试目的；最好把每个 case 的分值也写上。
    * 给分原则：`sample` 过了给一半的分——20 分的题 `sample` 占 10 分，剩下 10 分分布给其他 case。
    * > 结论：设计测试数据的原则，一是尽可能多地 cover 错误、能够找出错误，二是测得尽可能全面但用最少的时间和精力——用最少的 case 测到最多的事情。
    * > 来源: P20

* **课堂上澄清的两处条件（Clarified Conditions）**
    * "从小到大是不减吗"——不减；不是一定严格递增，也就意味着允许重复的数字出现。
    * 允许重复却不影响判题，是因为只回答 `yes` 或 `no`、不要求回答位置；如果要回答位置，这就有点不对了。
    * `sample` 应该给两组：一个 `yes` 的 case、一个 `no` 的 case。
    * > 来源: P20

* **等价类划分（Equivalence Classes）**
    * 真正需要分的是"`X` 与序列的位置关系"而不是 `X` 的取值范围，因为查找结果只可能是 `yes` 或 `no`。
    * 命中：`X` 等于序列中的某个元素，由各类 `yes` 用例覆盖。
    * 未命中（落在序列内部）：`X` 在 `a[1]` 与 `a[n]` 之间但没有出现，由落在区间内的 `no` 用例覆盖。
    * 未命中（落在序列两端之外）：`X < a[1]` 或 `X > a[n]`，由两个越界的 `no` 用例覆盖。
    * 类内取值：同一等价类里挑哪一个都行，上面的用例每一组都只需要一个代表值，不需要重复布点。
    * > 来源: P20

| 等价类 | 含义 | 覆盖它的用例 |
| :--- | :--- | :--- |
| 命中 | `X` 等于序列中的某个元素 | 各类 `yes` 用例 |
| 未命中（落在序列内部） | `X` 在 `a[1]` 与 `a[n]` 之间，但没有出现 | 落在区间内的 `no` 用例 |
| 未命中（落在序列两端之外） | `X < a[1]` 或 `X > a[n]` | 两个越界的 `no` 用例 |

* **边界值布点与分值分配（Boundary Values and Score Allocation）**
    * `n = 1`：序列只有一个元素的退化情况，查找的下界。
    * `X = a[1]`、`X = a[n]`：查找区间的两个端点，二分过程里最先被切到的位置。
    * `X < a[1]`、`X > a[n]`：两个端点的外侧。
    * `n = 10^5`：`n` 的上限，同时这也是"程序是不是真的二分"的性能判据——用线性扫描的实现在这一组数据上必然超时，正好把该卡的人卡住。
    * 分值分配：题目 20 分，`sample` 两组（一个 `yes`、一个 `no`）占 10 分，剩下 10 分分给其他用例，并按"测试目的"标明每一组分多少。
    * 大数据用例要专门写一个 `generator` 生成，10 万个整数手抄不现实——用例设计不只是"想几个数据"，还包括把数据造出来的工具。
    * > 来源: P20
