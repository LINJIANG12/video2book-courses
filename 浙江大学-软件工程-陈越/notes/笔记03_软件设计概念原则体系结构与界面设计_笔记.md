## 1. 设计与分析模型的对应与追溯

> **一句话主旨**：给出分析模型四类模型与各设计分块的对应关系，并说明设计为什么必须能回溯到分析模型。

* **设计分块与各自该看分析模型的哪一部分**
    * 做设计的人分好几拨：有做数据设计的、有做整体架构设计的、有做界面设计（`interface design`）的；这些设计做完之后，我们在每个 `component` 上再做详细设计。
    * 各组不需要通读一百多页文档，只重点看与自己直接相关的那几块：拿做数据类设计（`data class design`）的那个 group 来说，他重点看的是 `class based` 那一块，`behavior model` 不是他关心的事。
    * 反向也要问：`class based` 这部分跟哪几个 team 有关系——设计数据的人要看它，整体架构设计的人也要看它；重点看的是 `CRC model` 里的 collaboration，也就是类和类之间是怎么关联的。
    * > 来源: P11

* **分析模型四类模型与设计分块的对应关系**
    * `class based`（CRC/collaboration）：服务数据设计、整体架构设计、详细设计三个分块；它对架构设计的作用是——类和类之间怎么关联，直接决定了系统的架构要搭成一个什么样子。
    * `flow-oriented`（流模型）：重点是给界面设计提供依据，对做 `interface` 的那个 team 特别重要；架构设计也需要它，详细设计也需要它；做数据库设计的人不一定需要管这个模型。
    * `behavior model`（`state diagram`、`sequence diagram`）：重点也是管界面的——基本上都是那些看得见的状态转换，所以它跟界面相关，详细设计也会用到它。场景（`scenario`）也肯定会影响界面。
    * `scenario`（`use case`）：主要描述的是交互，所以重点还是服务界面设计，对界面设计来说它是最重要的；至于场景跟架构有多大关系，架构只要有了 flow、再看一下那个 CRC 就可以做出来，倒不一定非需要 use case。
    * > 来源: P11

| 分析模型 | 服务的设计分块 | 备注 |
| :--- | :--- | :--- |
| `class based`（CRC/collaboration） | 数据设计、整体架构设计、详细设计 | 架构设计重点看 collaboration |
| `flow-oriented` | 界面设计（依据来源）、架构设计、详细设计 | 数据库设计不一定需要 |
| `behavior model`（state/sequence） | 界面设计、详细设计 | 描述的是看得见的状态转换 |
| `scenario`（use case） | 界面设计 | 对界面设计来说最重要 |

* **设计的可追溯性（trace back）**
    * 用法：哪一部分出了问题——比如架构设计做坏了——就回去看分析模型里相关的那一部分：我为什么会这么设计，是因为你分析模型里哪一块这样误导了我。
    * 结论：这是能够 `trace back`、能够回溯的，这才是一个比较 professional 的做法；它对应的就是「设计必须能追溯到分析模型」这条原则。
    * > 来源: P11

## 2. 好设计的评判标准与设计质量

> **一句话主旨**：列出好设计的三条最低要求，以及设计质量必须在设计过程中同步评估这一时间维度上的要求。

* **显式需求与隐式需求（explicit requirements / implicit requirements）**
    * > 定义：显式需求是分析模型里被明确写出来的要求；隐式需求是客户默认人尽皆知、因而没有写出来的要求。好的设计两者都要满足。
    * 原文：`The design must implement all of the explicit requirements contained in the analysis model and it must accommodate all of the implicit requirements desired by the customer.`
    * 隐式需求的典型项：一个给公司用的小型数据库只实现插入、删除、查询三个功能是不够的——至少要能 `exit`；还要有 `save`，否则第二天开机数据全没了；还要有 `load`，说明这次要 load 哪一个数据库；做得更好一点，`exit` 之前还要检查一下有没有什么东西没有 `save`。
    * 判据：用户不一定把所有东西都明明白白写在纸上，但根据行业的习惯肯定要有的，你就要考虑到，这就是好设计要求的设计者考虑周全。
    * > 易错点：只实现明写出来的功能、界面上就只有对应的那几个键，用户插进去一百多个人的信息，下班没有退出的余地、第二天也没有 load 的动作，一个不能 save 的数据库没有用——需求文档没写不等于设计可以不做。
    * > 来源: P11

* **面向技术人员的可读性**
    * 原文要求：这个设计一定要是 `readable`、`understandable` 的，是给别人看的。
    * 读者是谁：给程序员看——人家编程的时候看你的设计要能看得懂；还有后续做测试的人、做维护的人，都应该很容易看懂你的设计。
    * 边界：客户看 `analysis model`，我们自己人看 `design model`；这意味着设计主要是给内部技术人员看的，它要有充分多的细节。
    * > 来源: P11

* **完整的实现视角**
    * 原文要求：设计要尽可能全面地 `provide a complete picture of the software`，而且你的描述是 `from an implementation perspective`。
    * 细化程度的例子：分析模型里只说"我这个数据里面有电话号码"；到了设计模型里就要很明确地说这个电话号码是一个 `int`、一个 `string` 还是一个 `long long`，用什么类型去实现它。
    * > 提示：这个细化不是一步到位的，它是慢慢一层一层细下去的。
    * > 来源: P11

* **设计质量的过程性**
    * 原文：`design should be assessed for quality as it is being created, not after the fact.`
    * 落法：检查设计质量的时候，`quality assurance team` 是要跟踪在整个过程里面的，而不是等一个完整的设计做完了再告诉你"这个从一开始就错了"。
    * 与迭代的关系：这其实就是在鼓励设计过程应当是迭代的——每次给出的抽象程度从高到低，从最抽象的慢慢具体化，反复不断细化，质量评估必须跟着这个过程一直进行。
    * > 来源: P11

* **书上的 quality guidelines**
    * 书本另给了一系列 `quality guidelines`，课上没有时间一条一条过。
    * 讲师的建议：这些 guidelines 还是挺有道理的，在做自己的 design 之前自己去读一下。
    * > 来源: P11

## 3. 九条设计原则与评审顺序

> **一句话主旨**：逐条给出九条设计原则各自约束的对象，并指出评审要先看整体架构的方向性错误。

| 原则（书上的原文） | 约束什么 | 要点 |
| :--- | :--- | :--- |
| `Design process should not suffer from tunnel vision.` | 视野 | 中文对应"一孔之见"；做的是支付宝里的一个小模块，也不能只看到你自己那一个小模块，要随时注意看到全貌 |
| `The design should be traceable to the analysis model.` | 与分析模型的关系 | 设计跟分析模型是要有关系的，不能是没关系的 |
| `The design should not reinvent the wheel.` | 复用 | 充分借鉴前人的经验，能重用的要充分重用；`framework` 的抽取、`design pattern` 都是在帮我们做到这一句 |
| `The design should minimize the intellectual distance between the software and the problem in the real world.` | 可懂性 | 在人的脑子跟机器之间充分靠近人脑的理解 |
| `The design should exhibit uniformity and integration.` | 整体性 | 设计可能是很多人合作完成的，但整体上要有整体的感觉，不能看上去是七拼八凑、各种风格不一样的东西拼起来的 |
| `The design should be structured to accommodate change.` | 应变 | 设计要灵活、要面向未来可能发生的改变；架构水平不够，稍微改一点东西程序就要推翻重写，这是很傻的设计 |
| `The design should be structured to degrade gently.` | 异常处理 | 不要动不动就蓝屏；用户总会犯各种各样的错误，即使出了异常也要比较优雅地处理，不能甩一句 `fatal error occurred at` 加一个看不懂的地址 |
| `Design is not coding, coding is not design.` | 抽象程度 | 设计的一个特点就是它要充分的抽象，跟具体代码之间还是有一定距离的 |
| `Design should be reviewed to minimize conceptual errors, semantic errors` | 评审 | 最最重要的做法是先看整体架构有没有方向性的错误 |

* **评审的顺序**
    * 最最重要的做法是：你先不要看很多细节，先看一下它的整体架构有没有方向性的错误。
    * 机理：大方向性的错误是最重要的；如果一开始大家就一头扎到细节里去看，所有细节都很完美，最后放到一块儿却不是我要的那个东西，那个时候就惨了。
    * > 来源: P11

## 4. 抽象与逐步精化

> **一句话主旨**：说明设计过程就是抽象加不断细化，抽象的对象是数据与操作，而精化的产物并不是代码。

* **抽象（abstraction）**
    * > 定义：整个设计的过程就是一个抽象加不断细化的过程；需要抽象的有两样——一个是数据，一个是 procedure（或者说 `operations`、操作）。
    * 第一级描述：刚开始的时候是从需求文档里直接 copy 下来的，非常粗略。
    * 精化方向：是一个 `top-down` 自顶向下的 `refinement`，会给 structure 里面那几个 data 加上更细的描述。
    * 边界：它始终不是代码——并不依赖于某一种编程语言，用 Java 去实现、用 C 去实现、用 whatever 去实现都可以，它描述的只是一个方法；描述算法跟写 code 加上 comments 是两回事。
    * > 来源: P11

* **逐层细化是什么样子（以 `open` 为例）**
    * 第一层：`open` 这个操作其实就是"进门"这么一个动作。
    * 第二层：走到门前，抓住门把手把门打开，走进去，再把门关上——这个过程是我定义的 open。
    * 第三层（什么叫"把门打开"）：拽一下那个门把手，顺时针拽一下；如果拽不动，要掏出钥匙，找到正确的那把钥匙插进去，朝 clockwise 转一下，转动了就把门打开、人闪开。
    * 再往下一层：how to find the correct key——如果你有很多很多钥匙，要用一个什么样的算法，才能最快地找到你要的那把 key。
    * > 来源: P11

## 5. 模块化与信息隐藏

> **一句话主旨**：给出模块化的工程收益、划分粒度上开发与集成成本的取舍，以及信息隐藏与受控接口的落法。

* **模块化（modularity）**
    * 典型例子：家庭音响就是特别典型的模块化设计——它由放唱片的、放磁带的、喇叭、放 DVD 的好几个机器组成，每一个都是一个模块。
    * 收益一（好做）：每个模块都比较容易做出来，一个工人只要会做这个喇叭就可以，不需要会做 DVD 那个机；每个模块需要一个专长，大家要求的技术层次不一样。
    * 收益二（好改）：换喇叭只要接口是一样的，把这个喇叭拔下来扔掉、换一个插上去，它同样起的是喇叭的功能；改完了不会影响别的地方。
    * 收益三（好修）：喇叭坏了不会说其他地方都不能用了；拔下来可以修，修它的时候不会把别的地方一起烧了。
    * > 来源: P11

* **模块划分粒度与成本**
    * 开发成本：开发一个模块要花的成本随着模块数增加而下降——不分模块、就一个模块，那开发这一个模块肯定累得要死。
    * 集成成本：把很多模块最后合并起来的工作量（`integration` 成本）随着模块数增加而上升。
    * 总成本：两条曲线叠加出的总成本在中间某个位置最低。
    * 边界：模块分得很细、每个人只干一点活，每一个模块开发的劳动力要求就比较低，但要把这么多个模块合起来就无比痛苦。
    ```text
      cost
        ^
        |  \                                    /
        |   \  开发成本（模块少 -> 每个都累）  /  集成成本（模块多 -> 合并痛苦）
        |    \                                /
        |     \                              /
        |      \                            /
        |       \__________________________/
        |                  ^
        |              总成本最低点（靠经验找）
        +-----------------------------------------------> 模块数
         少                                          多
    ```
    * > 易错点：没有一个公式告诉你，拿这个公式一算就知道我这个体量的软件分成 10 个模块最好；没有这个公式，这要靠你自己的经验。
    * > 来源: P11

* **信息隐藏（information hiding）与受控接口**
    * 定义：模块划分的时候，对每一个模块的设计就是要设计一个合理的接口，并且要能充分地保护你内部的数据。
    * 前提假设：如果你有一些东西不想让用户破坏、不想让用户犯错误，你先要假设用户不可能不犯错误，他肯定要犯错误；你如果不想让他破坏什么东西，你就不要给他破坏这个东西的机会。
    * 落法：把你不想让他破坏的东西充分藏好，你甚至可以让他根本不知道这个东西的存在；你给他的那个接口里面，让他根本碰不到你不想让他碰的东西。所以一个 `controlled interface`（受控接口）是非常重要的。
    * C++ 里那个 `class` 的机制就充分体现了 information hiding 这个特点，保证封装性会比较好；封装的好处就是 information hiding。
    * > 来源: P11

* **模块化时要权衡的两个问题**
    * 一个问题是我都往这个模块里面放什么东西。
    * 另一个是你这个模块的规模不要太大。
    * > 来源: P11

## 6. 耦合与内聚的等级

> **一句话主旨**：把耦合四级与内聚六级排成从最差到最理想的序列，并给出模块划分时可直接使用的判断依据。

* **耦合（coupling）**
    * > 定义：耦合就是两个模块之间到底在多大程度上关联，也就是这两个模块之间的交互性到底有多强。
    * 目标：耦合要 `as loose as possible`（尽可能低耦合），也就意味着 `as independent as possible`（每个模块尽可能独立）。
    * 边界：最好这两个模块干干净净、谁都不管谁，但这一点其实很难做到，你能做成这个样子就已经很不错了。
    * 四级序列（从最差到最理想）：`content` > `common` > `control` > `data`。
    * > 来源: P11

| 耦合等级 | 传递或共享什么 | 评价 |
| :--- | :--- | :--- |
| `content coupling`（内容耦合） | 直接跳到对方模块中间的某一句往下执行（如 A 里写一行 `go to C1`） | 最差；不只是 the least desirable，而是根本 forbidden，不允许这么写程序 |
| `common coupling`（公共耦合） | 全局变量 | 不好、不鼓励；如果是一个只管写、一个只管读那还好，两个都又写又读就会有麻烦 |
| `control coupling`（控制耦合） | 传一个 `flag`；这个 flag 的值直接决定对方走哪一条路径、执行哪一个分支 | 接口简单（只要传一个数字进去）但不够好，可以接受 |
| `data coupling`（数据耦合） | 传进去的是纯数据 | 最理想的状态 |

* **content 与 common 两级的边界**
    * `content coupling` 的结构样子：明明 A 在这里、C 在这里，它们俩应该是不搭的，结果 A 里面有一行语句叫 `go to C1`，一下子跳到 C 那个模块中间的某一句开始往下执行；也就是别人调用你这个模块时可以不从自顶向下的地方调用，而是从中间某一句直接跳进来。
    * `content coupling` 的成因：汇编时代的老程序员设计的东西经常能看到这种情况——两个模块可以共享一段代码，你这一改完了以后都不知道会发生什么，这是很恐怖的事情。
    * `common coupling` 的机理：全局变量设很多就有很大的危险；为了处理两个模块都又写又读带来的问题，要设计好多机制去解决。
    * > 来源: P11

* **data coupling 的实例（MATLAB 解方程组）**
    * 接口：把方程组的系数矩阵，还有那边那个常向量输进去，然后它就把解给你输出来；两边传来传去的都是纯数据。
    * 机理：我传的这个矩阵是什么样并不影响它——不管传什么矩阵，它里面解题的步骤都是一样的；我传进去的不是一个信号，它就是一个纯的数据。
    * 边界：它里面解方程组有很多很多算法，今天用算法 A、明天用算法 B、后天把 A 和 B 结合一下再优化，那是它的事情，我根本就不管，也不知道它变了没有；反正我给你数据，你返回给我要的数据就可以。
    * > 提示：我们说最好是什么都不用传，但那个不太容易做到。
    * > 来源: P11

* **内聚（cohesion）**
    * > 定义：内聚的意思是说，这个模块里的东西有多大程度都在做同一件事；内聚当然是越强越好。
    * 六级序列（从最差到最强）：`coincidental` < `logical` < `temporal` < `procedural` < `communicational` < `functional`。
    * > 来源: P11

| 内聚等级 | 划分依据 | 课上配的例子 |
| :--- | :--- | :--- |
| `coincidental cohesion`（偶然内聚） | 好多东西是常用的工具，只是因为大家比较常用就放在一起，逻辑上没关系 | 工具箱 |
| `logical cohesion`（逻辑内聚） | 逻辑上来讲稍微相关的东西放在一起 | 这个系统所有读输入的功能全都分给一个组去做 |
| `temporal cohesion`（时间内聚） | 根据时间来划分：在某个时间段发生的事情交由一个组去做 | 初始化——系统启动要做的很多动作全包给一个组 |
| `procedural cohesion`（过程内聚） | 按事务性流程或按 use case 来分工 | 某一个流程或某一个 use case 包给一个组去做 |
| `communicational cohesion`（通信内聚） | 以数据库为核心：大家都在一个数据库里读取、维护同一个数据库 | 维护这个数据库相关的全部包给一个组去做 |
| `functional cohesion`（功能内聚） | 一个组就做一件事，一个模块就完成一个功能 | 内聚性最强的分工方法 |

* **模块划分的判断依据（可用的范围到此为止）**
    * 耦合里，最糟糕的 `content coupling` 是不能要的；`common coupling`（全局变量）也是不鼓励的；最好是 `control` 或者 `data coupling`。
    * 内聚里，工具箱（偶然内聚）是最差的；`logical`、`temporal` 也不是很强；比较好的是后面那三种（`procedural`、`communicational`、`functional`）。
    * 论证要求：提出来的新分工方案，必须能说明它把原来某一级较低的耦合降到了 `control` 或 `data`，并把内聚提升到了功能级；只说"这样分工更好"而不指出耦合与内聚等级的具体变化，是不满足要求的。
    * > 来源: P11

## 7. 重构、设计阶段的类与抽象层次

> **一句话主旨**：说明重构的触发与代价、设计阶段要新增哪几类类，以及分析模型到设计模型的四类对应元素。

* **重构（refactoring）**
    * > 定义：在不改变外部表现的情况下，把内部结构变一变；用户是看不见你里面做了什么东西的，他觉得你那软件没变，但其实你的内部结构变了。
    * 两种触发情形：一种叫忍无可忍型的；一种叫处处追求完美的——你总在进步，特别是作为学生总学到新的东西、新的技术，回头看原来写的东西总会觉得它不完美。
    * 要检查的东西：有没有什么多余的、冗余的、没用的东西，或者那个结构性很差的东西。
    * > 注意：重构是一个大坑，一定要谨慎，重构需谨慎——自信满满准备好要去重构的时候，通常会发现情况跟想的不一样。
    * > 来源: P11

* **设计阶段的类（design classes）**
    * 做法：把需求阶段已经抽取的一系列 classes 做一个细化，细化到你的程序员可以理解、可以去执行的程度。
    * 需求阶段抽取、设计阶段只做细化的两类：`user interface classes`（用户界面类）、`business domain classes`（这个领域共用的一些类）。
    * 设计阶段可能要新增的三类：`process classes`（管理用的类，支持上面两类）、数据库相关类（底下那层留的数据库）、系统级底层 `classes`（更底层的类）。
    * 新增的原因：不仅要看需求阶段给你的那些 classes，还要看到它背后——要真的去处理、管理这些 classes 的时候，系统内部可能还需要一些底层的模块去做这些事情。
    ```text
      需求阶段抽取、设计阶段细化
      ├── user interface classes      用户界面类
      └── business domain classes     这个领域共用的一些类

      设计阶段可能要新增
      ├── process classes             管理用的类，支持上面两类
      ├── 数据库相关类                底下那层留的数据库
      └── 系统级底层 classes          更底层的类
    ```
    * > 来源: P11

* **分析模型与设计模型之间的抽象层次**
    * 四个方面的元素在两个模型里一一对应，design model 里都是 analysis model 中相应元素的细化：系统架构级 elements、与 interface 相关的所有元素、`component level` 详细设计的元素、`deployment` 部署阶段的元素。
    * 纵轴是 abstraction dimension：上面抽象程度比较高，是你的客户还能看得懂的；下面的抽象程度比较低，是技术人员看得懂、客户就不一定看得懂了，因为大量的术语进来了。
    ```text
      抽象程度高
      （客户看得懂）
        ^   +----------------------+   +----------------------+
        |   |  分析模型里的元素      |   |  设计模型里的元素      |
        |   +----------------------+   +----------------------+
        |   系统架构级 elements      --->  相应细化
        |   与 interface 相关的      --->  相应细化
        |   component level 详细设计 --->  相应细化
        |   deployment 部署级        --->  相应细化
        v
      抽象程度低
      （术语多，技术人员才看得懂，客户不一定看得懂）
    ```
    * > 来源: P11

## 8. 设计模式与框架

> **一句话主旨**：说明设计模式的动因是非功能需求、模式按抽象程度分三类，以及设计模式与框架的区别。

* **设计模式（design patterns）与设计动因（design forces）**
    * > 定义：`design forces` 是一些 non-functional 的描述，也就是非功能性的需求——比如我需要它后期比较容易维护，或者我需要它比较容易在不同的系统、不同的版本之间做迁移。
    * 规则：这个 design forces 是你一定要想清楚的；套用的时候要根据你这个 non-functional requirements 去挑相应合适的设计 pattern 来用。
    * 三大类（抽象程度从高到低）：系统架构的模式（`architectural patterns`）、设计元素级的 patterns、编程的模式（`coding patterns`）。
    ```text
      抽象程度高
      ├── 系统架构的模式（architectural patterns）
      ├── 设计元素级的 patterns
      └── 编程的模式（coding patterns）
      抽象程度低
    ```
    * > 来源: P11

* **框架（framework）与设计模式的区别**
    * framework 更具体一点，它是依赖于你的问题域的：针对某一个问题的领域，抽象出它公共的那一部分骨架——凡是这个领域的软件，它的骨架都是这个样子。
    * 复用方式：做下一个同领域的东西时，可以直接把这个 framework 搬过来，它是不动的，然后把你自己的东西填进去。
    * 抽象程度：设计模式要更抽象一点，而且它不依赖于某一个定义的问题域；architectural 的那个系统框架的模式，也是不依赖于某一个领域的。
    * 规模：真正的 design patterns 通常来说比 framework 要小——framework 是一个大的框架、一个骨架，design pattern 是某一个元素它的设计模式；pattern 没有 framework 那么具体，也没有它那么特指。
    * > 来源: P11

## 9. 架构设计的概念与重要性

> **一句话主旨**：给出软件架构的定义与只关注外部可见性质的边界，并说明架构设计的三重意义与要建立的五类模型。

* **软件架构（software architecture）**
    * > 定义：软件架构是对系统的结构描述。这个结构由组件（components）构成，描述内容包含组件本身、组件的性质（properties）与组件之间的关系（relationships），并且只关心外部可见的性质，不涉及内部实现细节。
    * 描述对象：它认为整个系统是一个一个组件组装起来的；在 architecture design 里面，除了描述清楚组件有什么东西，还要描述清楚它有什么样的 properties、以及它们中间的 relationships。
    * 边界：讲到架构设计的时候，我们更多关注的是 `externally visible properties`（外部可见的那些性质）；我们不是详细设计，所以不设计内部那些很 tricky 的东西，只说外面的结构。
    * > 来源: P12

* **架构设计为什么重要（三个理由）**
    * 它是一个 `communication` 的工具：是大家用来沟通的，这个沟通是 `between all stakeholders interested in the development of the system`——基本上就是内部人员，你的同行、其它几个组的人；首要目的是让别人听懂。
    * 通过 architectural design 可以看到 `early design decisions`：早期的设计决策如果有错误，后面弥补起来是很困难的。
    * 它给了我们一个 `relatively small, intellectually graspable model`：一个相对来说比较小、大家比较容易懂、比较抽象到可以看懂的架构，而不是由很多细节堆起来的复杂庞大的东西；目的还是让所有开发人员能够比较容易地沟通。
    * 建筑类比：需求是"我有一个 150 平米的房子，要把它设计成三室一厅、一厨、两卫"；如果一开始就决策成三个居室都围着厨房建、两个卫生间放在一块放在客厅的一个角落里，那不管后期再怎么装修、用什么高级的吊顶豪华的地板，人家进去以后还是觉得这不像一个正常的人家，而且通风、油烟、煤气这些东西全都会出问题。
    * > 来源: P12

* **架构需要建立的五类模型**
    * `structural models`：把系统分成几个模块，以及模块之间怎么关联。
    * `framework models`：这个领域里所有软件共有的框架性东西（要做的支付宝属于金融领域，那金融领域所有的软件大概都是一个什么框架的东西）。
    * `dynamic models`：描述系统的动态状况。
    * `process models`：软件提供给人家用的时候，人家的使用过程。
    * `functional models`：功能模型。
    * `structural`、`framework`、`dynamic`、`process` 这四类是重点区分的对象，`functional` 只是顺带列上。
    ```text
      architecture 需要的 models
      ├── structural models    把系统分成几个模块，以及模块之间怎么关联
      ├── framework models     这个领域里所有软件共有的框架性东西
      ├── dynamic models       描述系统的动态状况
      ├── process models       软件提供给人家用的时候，人家的使用过程
      └── functional models    功能模型，就不用说了
    ```
    * > 易错点：`process models` 不是指我们软件开发团队工作的 process model，那两回事；这里说的是你做的这个软件提供给人家用、人家要用的时候那个使用的过程。
    * > 来源: P11

## 10. 数据设计的两层

> **一句话主旨**：把数据设计分成定框架的架构级与落到类的组件级两层，并给出数据、界面、接口三面对齐的检查办法。

* **架构级数据设计**
    * 层面定位：宏观层面——一上来不是想每一件事情的数据结构、每一个 `class`，而是先设计好大的数据框架，然后再去细化。
    * 第一件要做的事是想数据库：你要建几个数据库？你需要建什么样的数据库？它整个的数据结构是什么样子的？
    * 数据形态：复杂一点的系统涉及的数据有很多种、很多类型，是异构的——有视频、有音频、有文字、有图片，各种各样乱七八糟的东西。
    * `data mining` 机制：这些数据不仅要有有效的组织，而且你希望在你获取的时候——如果系统能获取海量数据，就是现在特别时髦叫的"大数据"——你得考虑一下这个 mining 的机制，就是从里面获取有效信息的机制。
    * 两种情形：如果不是太复杂，就是几个比较简单的数据库，那要想要的是怎么样能够有效地从数据库里面提取一些你这个领域相关的 `business-level information`；如果有多种不同的、一致的数据库集合在一起，你要想做很有效的 mining，还涉及到 `data warehouse`（数据仓库）的设计问题——要从不同的数据库里面抽象、抽取一些东西，集成到一个 data warehouse 里面。
    ```text
      架构级 data design（宏观，只定框架）
      ├── 建几个数据库、建什么样的数据库、整体数据结构
      └── 数据挖掘机制
          ├── 简单情形：从几个数据库里提取领域相关的 business-level information
          └── 复杂情形：从多个异构数据库抽象、抽取、集成到 data warehouse
    ```
    * > 来源: P12

* **组件级数据设计**
    * 起点：需求阶段得到很多的 `data objects`，它们是比较抽象的、抽象程度比较高，只描述了是什么东西。
    * 细化链：在这个地方要 `refine`、要细化到怎么实现——把它定义成哪几个 `class`；每一个 `attributes` 具体怎么实现（某个 attribute 可能还会被细化成另外一个数据结构）；最后要把 data class 跟 class 之间的 `relationship` 定义清楚。
    * 收尾动作：再看一下这个庞大繁杂的关系图，看看有没有什么可以简化的地方——比如可以在顶层抽象出一个父类，再下面是不是有些子类可以合并一下，诸如此类地做一些调整。
    ```text
      组件级 data design（微观，落到实现）
      data object（需求阶段，抽象，只说是什么）
         └── refine ──> 定义成哪几个 class
                           ├── 每个 attribute 怎么实现（可能再细化成另一个数据结构）
                           └── class 与 class 之间的 relationship
                                    └── 通看关系图，做简化：顶层抽父类、合并子类
    ```
    * > 来源: P12

* **关系与键的约定（在线预订系统的数据库）**
    * 表里的 `ID` 要区分两种身份：一个是数据库自己管理用的主键，一个是业务上真实的编号（航班号、酒店编号）；混在一起，后面跟别的组交换数据时最容易出错。
    * 航班、酒店两张表各有一个自建的 `ID`——这个 ID 是为了数据库管理方便造出来的，不是它们在现实里的真实编号。
    * 用户这张表借用了别的组提供的用户，把用户 ID 当外键（`foreign key`）用。
    * 用户与航班、用户与酒店之间的关系，是以**下订单的日期**加上**用户 ID** 共同做主键（`primary key`）来承载关系属性的。
    * 管理员操作日志表独立存在，记录的是管理员的日常操作：管理员 ID、操作对象与操作内容、操作的日期时间。
    * > 提示：表里的 `ID` 要区分两种身份——一个是数据库自己管理用的主键，一个是业务上真实的编号；混在一起，后面跟别的组交换数据时最容易出错。
    * > 来源: P14

* **数据、界面与接口三面对齐**
    * 判据：表上的字段要和前面讲的功能、和界面呈现的内容对得上——界面上有的东西，数据里就得有。
    * 缺字段的典型：界面要显示照片，数据里就要有图片的 `URL`（图片本身用文件存、表里存地址）；航班表里要有起飞时间；别的组的航班信息里可能还要有航空公司的信息，这部分也要写出来。
    * 检查办法：拿界面上的每一处展示，回去问它在哪张表的哪个字段；四张表要能立刻答上来是哪四张、分别是什么，不能等一项一项被逼问。
    * > 易错点：数据设计和界面设计、和别的组的接口是同一套东西的三个面；表字段少了，界面上的功能就是空的；跟对方交换的字段没定，接口就是假的。
    * > 来源: P14

## 11. 架构风格与四个结构度量

> **一句话主旨**：区分架构风格与架构模式，梳理几种常见风格，并给出 call-and-return 的四个结构度量与过大的代价。

* **架构风格（architectural styles）**
    * 作用：说到一个名字的时候，就大概会想到它是一个什么样子——尽管每一个建筑可能有它具体细节上的不同，内部的装修细节也会有不同。
    * 要描述清楚的四件事：有一系列的 `components`，由这些组件构成你的系统；关键的是这些 components 是怎么连在一起的，即 `a set of connectors`（做沟通的那些连接者）；它们是以什么样的 `constraints`（约束条件）放到一起的；最后你要提供一个语义模型。
    * 名字与画面（软件与建筑两组对照）：说"面向对象式"，马上想到一个 `class` 一个 class 加关联线（封装）；说"以数据为中心"，马上想到一个大数据库、所有的应用都围着它转；说"哥特式"，想到尖房顶；说"徽派"，想到黑顶白墙。
    * > 来源: P12

* **架构模式（pattern）**
    * > 定义：架构模式说的是"你希望它具有某一种特点，具有某一种特点的东西就应该怎么设计"。
    * 例子：设计一个房子，只要是人住的房子，一般来说它应该有卫生间、应该有厨房；一说到设计一个厨房，它就有固定的设计模式——只要是个厨房，必定要考虑通风、煤气管道，它得有个水池子、得接水管、要有下水的地方。这些基本的东西是必须有的，这才叫设计模式。
    * 边界：模式不是唤起画面，而是规定"具备某种特点的东西应该怎么设计"。
    * > 来源: P12

* **几种常见架构风格**
    * `data-centered`（以数据为中心）：以某一个大的数据库为中心，其他所有的功能你都可以认为是一个小型应用，围绕着这个数据库来建；所有应用都通过这个中心交换数据。
    * `data flow`（数据流）：数据在你这个系统里呈现非常明显的朝一个方向流动的特性；它中间的每一个模块就好像一个 `filter`（过滤器），数据流的线就是 `pipes`（像水管）；水沿着水管通过一个又一个的过滤器、过滤系统，朝着一个方向去流动。
    * `object-oriented`：组织单元不是那个共享的中心数据库，而是一个个自带数据和操作的封装体，重要的特性就是 `encapsulation`（封装），一个一个封装好的 class；它是数据为中心的架构的对照面。
    * `call-and-return`：最常见、最经典的结构化设计模型；顶端是我们整个这个大系统，它下面分成三大模块，模块下面再分更细的模块；上面的层在做决策，下面的层是真的在工作、在提供数据、提供底层支持，供上面的模块去调用。凡是结构化的设计，都会想到这么一个非常经典的结构。
    * `layered architecture`（层次化架构）：把系统看成有非常明显的层次感，自内而外是 core layer（最底层、最核心的支持）→ utility layer（做基础设施用的那一类工具的模块）→ application layer（各种应用层）→ user interface layer（面向用户，各应用的接口）。
    ```text
        +---------------+        +---------------+
        |    app  A     |        |    app  B     |
        +-------+-------+        +-------+-------+
                |                        |
                +-----------+------------+
                            |
                    +-------v--------+
                    |    大数据库    |   <-- 中心
                    +-------+--------+
                            |
                +-----------+------------+
                |                        |
        +-------v-------+        +-------+-------+
        |    app  C     |        |    app  D     |
        +---------------+        +---------------+
    ```
    ```text
      +--------+          +--------+          +--------+          +--------+
      | source |          | filter |          | filter |          |  sink  |
      +---+----+          +---+----+          +---+----+          +---+----+
          |     pipe          |     pipe          |     pipe          |
          +---------->        +---------->        +---------->        v
                                                                   输出
      数据源              过滤器              过滤器                输出
    ```
    * > 提示：`layered architecture` 真正来讲只能给你起一个"系统全貌"的风格展示；真正去做系统设计的时候，好像这也不是很容易画，还是 `call-and-return` 那种比较容易画。
    * > 来源: P12

* **call-and-return 的四个结构度量**
    * 宽度：同一层有多少个模块。
    * 深度：一共往下分了多少层。
    * `fan-in`：有多少条边指进来，即上层有多少个模块同时调用它。
    * `fan-out`：有多少条边从它这里出去，即它向下调用多少个模块。
    * 结构性质：这可以理解成一棵树，其实也不对——不是一棵标准的树；这个图里每个模块头上只有一个 `parent`，但是一个模块下面可以有好多个。宽度和深度都要恰当，不可以太多；四个指标都不能太大。
    ```text
                     +-------------------+
                     |      系统          |   深度 = 一共往下分了多少层
                     +---------+---------+
                               |               <-- 同一层有多少个模块 = 宽度
              +----------------+----------------+
              |                |                |
         +----v----+      +----v----+      +----v----+
         |    M1   |      |    M2   |      |    M3   |
         +----+----+      +---------+      +----+----+
              |                                  |
         +----v----+                        +----v----+
         |    r    | <-- fan-in = 4     |    c    | --> fan-out = 2
         +---------+                        +---------+
         有多少条边指进来                     有多少条边出去
    ```
    * 四个指标过大的代价：

| 指标 | 过大的代价 |
| :--- | :--- |
| 宽度 | 同一层次要同时铺开很多模块，要看这家公司的人手够不够——极端的例子是整个系统唰一下铺开就一层，那你得有这么多人 |
| 深度 | `call-and-return` 意味着从底下开始开发、底下开发完了再做上面的，测试也是底下测完了测上面；深度太深，将来测试的时候就需要测太多的环节 |
| `fan-in` | 一个模块被很多的模块调用，就是一种很脆弱的结构，叫牵一发动全身：它一错，调用它的很多模块都傻了；它下面改掉了，上面的各种模块说不定都要跟着它改 |
| `fan-out` | 说明这个模块功能的内聚性不是特别强——它怎么会分出那么多分支出来；将来合并的时候、做集成测试的时候就会很麻烦，要凑在你这一个模块这边来测的东西太多 |

    * > 来源: P12

* **架构层面设计模式的三类划分**
    * 划分依据是系统最突出的运行特征。
    * 并发类：系统有强烈的大规模并发，比如操作系统的 `process management`、任务调度的模式。
    * 驻留数据类：`persistence`，基本上说起来就是数据库管理系统，数据库管理系统有它固定的设计模式。
    * 分布式类：系统具有非常明显的分布式特征，分布式系统有它自己的设计模式。
    * 每一大类里面又有很多不同的设计模式。
    * > 来源: P12

* **一个系统可以套用多个模式**
    * 整个系统的设计不一定只用一个模式，里面不同的功能可以套用不同的设计模式。
    * 报告要求：联系自己组做的那个模块、那个子系统，说明一种什么样的设计模式是可以拿过来套用的；最主要的那个套用要最详细地说明，然后再想一下是不是有其它设计模式也可以用到。
    * > 来源: P12

## 12. 架构上下文图（ACD）

> **一句话主旨**：说明上下文是对外部环境的描述，并给出 ACD 四类外部实体的画法与一处最容易画错的边界。

* **架构上下文（context）**
    * > 定义：架构上下文指的是目标系统所处的外部环境，即哪些系统、模块或角色与它相邻、与它通信；所以 context 实质上是一个环境的描述，是一个外部环境的描述。
    * 目的：把你要做的这个系统放在一个大环境里面，去考虑它在大环境里面是什么位置的——它前、上、下、左、右都是什么模块在跟它沟通、起作用。
    * > 来源: P12

* **ACD（architectural context diagram）**
    * 描述的对象：`target system`——你要做的这个系统，`interacts with entities external to its boundaries`，即这个系统跟它以外的东西是什么关系。
    * 要描述清楚的四种东西：一个 `superordinate system`（上级）——有哪些系统要调用你这个系统、要用到你；一个下级——你的底层模块，你要用到哪些模块、哪些模块给你提供支持、你从它那里获取数据；一个 `peer-level`（同级）——你跟哪些模块是 peer-to-peer 的关系，你们两个互相调用，或者你读它的、你提供信息给它、它提供信息给你；还有画在边上的 `actors`（角色）——哪些模块扮演 actor 的角色，他来使用你、用你去完成一个什么事情。
    * 画法：中间是你这个 target system，写上系统的名字；上面画有哪些模块是调用你的（`The target system is used by the superordinate systems`）；下面画你这个系统调用、`it depends on` 的一些 subordinate systems；同级画一边，actors 画另一边。
    ```text
                         +-------------------------------------------+
                         |        superordinate system（上级）       |
                         |        哪些系统要调用你、要用到你         |
                         +---------------------+---------------------+
                                               |
                        +------------------+   +------------------+   +--------------------+
                        |peer-level（同级）|   |  target system   |   |   actors（角色）   |
                        |     互相调用     |   |   写上系统名字   |   |     它来使用你     |
                        |   互相提供信息   |   |    完成某件事    |   |     去完成事情     |
                        +------------------+   +--------+---------+   +--------------------+
                                               |
                         +---------------------v---------------------+
                         |        subordinate system（下级）         |
                         |        你要用到哪些模块、从它取数据       |
                         +-------------------------------------------+
    ```
    * > 提示：ACD 不是照抄一张图，画出来什么样取决于你怎么定义这个系统的边界与接口；一个角色既通过中间层间接调用你、又有自己的直连入口，就得两条线都画上。
    * > 来源: P12, P13

* **一处最容易画错的边界（家居保安系统实例）**
    * 被描述的核心模块：`Security function`（安保相关功能的处理）。
    * 上级：`SafeHome product` 的 `Internet-based system`（远程联网操作系统）调用它。
    * 下级：它直接调用的 `sensors`（探头／传感器）。
    * 同级：`surveillance function`（监控），做行为处理的监控功能与它 peer to peer 互相调用。
    * 两个 actor：`control panel` 与 `homeowner`；`homeowner` 一般是**通过** control panel 去操纵这个模块的，可图上又把 homeowner 画成了一个直接的 actor——意思是它还有一个接口，让 homeowner 可以不经过 control panel 就直接操作 `Security function`。
    * > 来源: P13

## 13. 从数据流图映射到系统结构

> **一句话主旨**：区分变换流与事务流两种数据流，给出它们各自映射成调用返回结构的方法与初步结果的缺陷。

* **两种数据流：变换流与事务流**
    * `transform flow`（变换流）：基本上所有的数据流图，你都可以把它认为是变换流——把系统理解为一部分处理 input、一部分处理 output，中间这一部分是 process，这就是一个 IPO 的结构。
    * `transaction flow`（事务流）：当数据流图里面有某一个点有特别明显的 `transaction center` 的特点时，就是它了。
    * `transaction center` 的样子：长途汽车站、火车站、机场都是非常典型的——大家从四面八方汇聚到这个点，然后这个点把人按照不同的目标分到不同的路径上，送到不同的地方去。
    * 结构性质：它相当于一个 `switch-case`，有这么个结构就是一个典型的 transaction flow 的结构。
    * 两种模式经常套在一起：一个大的、复杂的系统里面，会有好几种具有不同特点的局部。
    * > 来源: P13

* **变换流的映射**
    * 第一层：我这个系统分成 IPO 三大块——那个 `I` 对应这一块，`P` 对应中间这一块，`O` 对应这一块。
    * input 的映射：以 `boundary` 为界，从朝它来的方向、从上往下的顺序画；也就是 `I` 这个模块调用 B 和 C，B 和 C 共同调用 A（A 是数据流最上游的输入加工）。
    * process 的映射：随便你怎么弄，一个最简单的初步方法就是把它们全都当成并列的——可以分成三个组，也可以把某一个挂在某一个下面，这是后期调整的。
    * output 的映射：同样是从 `boundary` 往外去画，朝数据流的终点方向逐个挂上去。
    ```text
                [ I ]  input 控制模块
                       |
            +----------+----------+
            |                     |
          [ B ]                 [ C ]
            |                     |
            +----------+----------+
                       |
                     [ A ]     （数据流最上游的输入加工）

                [ P ]  process：把中间那几个加工先当成并列的
                     P1    P2    P3

                [ O ]  output 控制模块
                       |
            +----------+----------+
            |                     |
          [ D ]                 [ E ]     （朝数据流的终点方向逐个挂上去）
    ```
    * > 提示：这张图画的是模块之间的**调用关系**，所以方向跟数据流的方向是反的——数据从 A 流到 B、C，调用就从 I 出发往下走到 B、C、再走到 A；同一张图用"数据往哪流"和"调用从哪发起"两种方向来读都成立，真正落地成模块结构图时用的是后者。
    * > 来源: P13

* **事务流的映射**
    * 局部展开的样子：有一个 input 的流，中间放着 `transaction center`，下面有三条路径对着它，每条路径上再排着 P1、P2、P3。
    * 嵌套关系：它的每一条路径，其实又是一个小的 IPO——每一条路径本身又是一个 IPO 的模式。
    * 初步结果的缺陷：这么画出来的架构一点都不好，首先它太宽了，这一层实在太宽，而且还没对齐；这只是一个可以机械操作出来的初步结果。
    * 后续动作：拿到这个图以后还要人工去做很多调整，把它调得更合理一点，包括宽度、深度等等。
    * 自动化的边界：如果你能直接用某种方式去表示你的数据流图，甚至可以写一个程序把数据流图自动转换成一个 call and return 的结构，但那只是初步的东西。
    ```text
                        [ input flow ]
                              |
                              v
                     [ transaction center ]        （相当于 switch-case）
                      |        |        |
             +---------+        |        +---------+
             |                  |                  |
        [ path 1 ]         [ path 2 ]         [ path 3 ]
        input->P->output   input->P->output   input->P->output
    ```
    * > 来源: P13

## 14. archetype 与领域实体

> **一句话主旨**：说明 archetype 是域里最核心的少数抽象，并给出判断一份设计有没有落到面向对象上的判据。

* **archetype（领域原型）**
    * > 定义：用面向对象的眼光看，archetype 就是一个 class，一个封装的 class；面向对象建模里有一块内容叫 `Archetype`，它说的就是你那个域里面最核心的抽象。
    * 抽取范围：你整个系统从详细设计的角度细化下去会有很多很多 class，能被叫做 archetype 的，是其中非常核心、非常 critical、至关重要的那几大类；抽几个最有代表性、最关键的那些出来就行，不是把几十个 class 一股脑都摆上去。
    * 要报告的内容：抽出来之后要描述清楚它们之间怎么关联。
    * 细化关系：architecture 层面是少数、抽象的[几个核心 archetype]，不断细化到 design 层面的一批 class，再细化／实例化到实现层面的具体的类与对象——archetype 不是另一套东西，它就是这些 class 里最要紧的那几个。
    ```text
      archetype 的抽取与细化

        architecture 层面   [ 几个核心 archetype ]        少数、抽象
                                    |
                                    | 不断细化
                                    v
        design 层面         [ 一批 class ]                多、具体
                                    |
                                    | 再细化／实例化
                                    v
        实现层面            [ 具体的类与对象 ]
    ```
    * 书上例子：家居保安系统的 `Security function`；书上给了非常好的例子，如果不知道怎么定义 archetype，自己去看 `Figure 10.8` 和 `10.9`——从一个大的 archetype 怎么抽出来、怎么不断细化、怎么再实例化，整个过程的图都在那儿。
    * > 来源: P13, P14

* **判定设计有没有落到面向对象上**
    * 前提：既然全程都在强调自己要用面向对象（Object-Oriented，OO），那么报告里就必须强调一件事——这个系统所要解决问题的核心、也就是应用域（领域）里的那个实体是什么。
    * 判断路径：以在线预订为例，酒店是不是一个实体？航班是不是一个实体？如果是，那么它们就在实现的时候成为一个实体类；针对这个实体类，它和它的历史信息之间的关联、在它上面能做的那些操作，是不是应该封装到类里面去？
    * 订单交易的例子：订单交易里面最重要的是订单；每一笔订单交易，你甚至可以把这一笔交易看成一个 `Transaction`（事务），它也可以作为一个类。
    * 反面现象：讲了那么多体系结构上的类，在讲述里很难看得到；讲的很多东西都偏过程式了——都是"这是一个流程""那是一个流程"。
    * > 易错点：流程当然要讲，但 `Archetype` 不是额外多做的一份作业，它是你整个域的骨架；流程图画得再顺，只要说不出域里的实体有哪几个、操作封在谁身上，这份设计就还没有落到面向对象上。
    * > 来源: P14

## 15. 架构评估与质量属性

> **一句话主旨**：给出折中分析的步骤、质量属性要落成可度量值的要求，以及选方案必须讲出为什么的论证纪律。

* **trade-off analysis（折中分析）**
    * 前提：设计的时候千万不要一根筋，不能只有 `tunnel vision`（一孔之见）；你要考虑很多种可能性，然后从里面选一个对你这个系统、对你要达成的目标最有效、最合适的架构。
    * 名字的含义：trade-off 大概就是有得必有失、有失必有得，得失之间你怎么平衡；从这个名字也能看出来，实际上是要提出几种不一样的 architectural design、几种不同风格的设计，然后大家来评估。
    * 前几步：从 `scenarios`、`requirements` 开始，最后给出几个不同的 architectural styles 和 patterns；真正重要的是第四步和第五步。
    * 第四步：针对每一个 quality attribute，对每一种 style 单独做一次评估。
    * 第五步：看你这个系统设计的 `sensitivity`（敏感度）——每一个 quality attribute 的敏感度。
    * > 来源: P13

* **quality attribute 与敏感度**
    * quality attributes 取决于你要做的东西里什么比较重要：`reliability`、`performance`、`security`、`portability`，还有好多好多种性质。
    * 敏感度的读法：如果你选了这个风格，那么在某个地方稍微起一点变动，你的安全性就会极大降低——那你对于安全性就是非常敏感的；或者什么地方稍微有点不稳定，另外一个属性就会变得非常厉害。
    * 要找的：自己最 sensitive 的那些点在哪里。
    * 结果用法：架构给出来以后，逐个 quality attribute 去评估，然后就能看出来你这个架构哪方面比较强、哪方面比较弱。
    * > 来源: P13

* **质量属性要落成可度量的东西**
    * 要求：`reliability`（可靠性）听上去是一个很抽象、很虚的词，最后是要得到一个数的——可靠性大概 80%，还是 95%？这东西不是拍脑袋拍出来的。
    * 度量存在性：每一个 quality attribute 背后都有一系列的度量。
    * 课程安排：这些度量具体怎么做，这门课在这学期的最后才大概给大家介绍；现在要知道的是这个方向——架构给出来以后要逐个 quality attribute 去评估。
    * > 结论：它看起来是一个很虚的形容词，实际上都应该努力把它落地成非常实的、可度量的东西。
    * > 来源: P13

* **选择方案要讲出道理**
    * 通病：毕业设计只写"我做了什么"——我的需求是这些，于是我是这样设计系统的，然后我是这样实现的，然后我是这样测试的；做了什么、做了什么、做了什么，每一件事都写得很清楚，但这是不够的，这种写法是不对的。
    * 必须补上的那条线：你要写你做了什么，你还要写你为什么这么做——你凭什么这么设计？有没有其它方法可以实现同样的功能？我们有很多现成的设计风格、设计模式，为什么你选择这一种？为什么这一种是最合适的？
    * 答辩的底线：老师问"你为什么这么做"，回答"我也不知道，老板让我这么设计，于是我就这么干了"，这就是典型的码农风格，也是最差的回答。
    ```text
      毕业设计／毕业论文里两条线的分量

        我做了什么   —— 需求、设计、实现、测试的流水账      必须写，但没有技术含量
        我为什么这么做 —— 为什么选这种风格、为什么它最合适    最有技术含量的部分
    ```
    * > 来源: P13

## 16. 分工方式与架构设计的目标

> **一句话主旨**：对比横向与纵向两种分工方式，并列出架构设计必须照顾到的测试、维护与灵活性目标。

* **横向分工（horizontal）**
    * 适用条件：如果你的系统非常明确地有几个比较独立的功能。
    * 做法：基本上一个功能对应一个分支，分工的时候就是一个功能归一个组（竖着切、横着分）；按每个功能模块对应一个分支画下来的系统架构图，就是横向分工的样子。
    * > 来源: P13

* **纵向分工（vertical）**
    * 适用条件：系统具有特别明显的"底层是支持的、上层是决策的"——下面是干活的、上面是领导，有特别明显的这种决策层的层次感。
    * 做法：横着切、竖着分——先按层次横着切开，再在同一层里按功能分给不同的人。
    * > 来源: P13

* **复杂系统两种切法混用**
    * 在一个充分庞大、充分复杂的系统里，不可能每次只用一种风格去分工。
    * 通常先竖着切，把一个一个分支分给各组；各组自己下面再分工的时候，可以竖着切，也可以横着切，大家都是纵横交错的。
    ```text
      横向分工：一个功能一个分支（竖着切、横着分）

                              [ 系统 ]
       +--------+--------+--------+--------+--------+
     [ F1 ]   [ F2 ]   [ F3 ]   [ F4 ]   [ F5 ]
      组1      组2      组3      组4      组5

      纵向分工：底层支持、上层决策（横着切、竖着分）

                         [ 决策层 ]
                              |
                         [ 协调层 ]
                              |
                         [ 支持层 ]      同一层里再按功能分给不同的人
    ```
    * > 来源: P13

* **架构设计要照顾到的几件事**
    * 你希望测试会比较容易——要方便测试。
    * 你希望方便维护；你怎么测的，其实跟你后面维护的那个队伍是直接相关的。
    * 方便测试、方便维护，实际上就意味着 `fan-out` 不要太多。
    * 你希望 `side effects` 的 `propagation` 不要太广——什么地方错了、一个模块错掉的话，它的副作用不要传播得太开；那就意味着一个模块的 `fan-in` 不要太多，否则你就牵一发动全身。
    * 你希望整个系统架构还是比较灵活的：如果我要扩展功能，希望它是比较容易扩展的。
    * 落点：做 architectural design 总的目的，是希望你的分工和模块划分能照顾到这几点——你脑子里要有这些概念，设计是给人用的。
    * > 来源: P13

## 17. 设计汇报的内容、顺序与评审

> **一句话主旨**：给出设计汇报的四块内容、先外部接口后内部结构的顺序，以及接口边界与打分评审的规矩。

* **汇报与报告书的分工**
    * 两件事：报告书是交上来给老师看的；汇报是把里面最精彩的东西讲出来。
    * 五分钟的时间，讲什么、按什么顺序讲，本身就是一次设计。
    * > 来源: P14

* **汇报内容的四块**

| 汇报内容 | 要求 |
| :--- | :--- |
| 项目背景与各组的关系 | 简单交代，让别的组知道你在整个系统的什么位置 |
| 体系结构设计 | 汇报的重点，相当于总体设计；含数据的体系结构与系统的体系结构两部分，系统体系结构里采用的 pattern 或 style 要重点介绍 |
| 用户接口设计 | 界面设计本来就在同步进行，一并讲 |
| 报告整体效果与表达 | 打分表上有这一项，PPT 做得用不用心、讲得清不清楚都算分 |

    * 边界：可行性、立项那一套报告书里有，设计汇报里不用讲。
    * > 来源: P14

* **汇报的推进顺序**
    * 第一顺位：一上来先把你的系统和别的组之间是什么关系、接口是什么讲清楚，讲完了再讲你内部怎么设计；先从外部整体的接口和关系讲起，再讲内部不同模块之间的结构，这个顺序不要反。
    * 需求不念就等于没讲：功能性与非功能性需求必须口头交代清楚，翻页过去不算汇报（实例：功能性需求是用户能查询酒店和航班信息、并且通过界面把结果比较好地反馈给用户；非功能性需求是界面的设计要好看之类）。
    * 整体感：逐条讲细节之前，先把你这块有哪几大功能说清楚，听众才有地方挂后面的细节。
    * 界面的那一节要讲得快、讲得直接：讲的是页面之间的关系、每一页承担什么功能，别的不用讲。
    * 数据归属要主动讲：酒店信息的维护、航班信息的维护归谁，这种"数据归谁维护"的归属必须主动讲出来，不要等别人问。
    * 图要让人一眼看出是哪一层：业务功能的划分、模块之间的调用关系、体系结构，回答的是不同的问题，不能挑字眼混着画。
    * > 易错点：架构图里把别人的接口都放进去了、大量箭头都是别人的东西，自己真正核心的那一块反而没体现出来；把用户评价、用户推荐这些从别人那儿借来的模块摆进自己的功能图，看上去内容更丰富，实际上把你的核心稀释掉了。
    * > 来源: P14

* **接口边界要谈清的三件事**
    * 三件事：谁能改订单的字段、谁能改订单的状态、退款之后订单归谁管；这三条不在接口里讲清楚，两边各写各的代码，联调的时候一定对不上。
    * `改信息` 与 `改状态` 是两件事，谈接口的时候要分开谈：订单有唯一标识，按它定位到原来那条订单、在原订单上改，而不是重新生成一张；需要改状态时，就调用对方提供的那个改状态接口。
    * 对方的接口能力要写清：对方对接过来只提供了改订单状态的接口，没有提供修改订单信息的接口，因此修改信息放在自己这边做。
    * 一条链上的三方分工（在线预订实例）：第三组负责查询与生成订单、把订单号传给第二组；第二组生成一个新的订单条目并马上进入支付流程，与第四组（个人账户管理）通信完成支付；支付结果先回到第二组，再由第三组调管理接口把订单改成"支付成功"，一单支付才算完成。
    ```text
      在线预订系统（第三组）与相邻子系统的接口链

         用户
          |  1. 按出发地／目的地查询酒店、航班
          v
       +------------------+   2. 选酒店、填表单，生成订单，存入自己的库
       | 第三组：在线预订 |-------------------------------------------+
       | 查询／订单／后台 |   3. 把订单信息（订单号）传给第二组        |
       +------------------+                                          v
              ^                                            +-------------------+
              |  6. 调管理接口，把订单改成"支付成功"          | 第二组：交易／支付 |
              +--------------------------------------------| 生成新的订单条目   |
                                                           +-------------------+
                                                                    |
                                                  4. 与第四组通信，完成支付
                                                                    v
                                                           +-------------------+
                                                           | 第四组：个人账户   |
                                                           | 管理              |
                                                           +-------------------+
                                                  5. 返回支付成功状态
    ```
    * > 提示：订单存在谁的库里、订单条目由谁生成、状态由谁改，这三件事各说一套，就是接口没谈清楚；一条链上跨了三个组，任何一端把"谁存、谁改"说错，编码阶段就要返工。
    * > 来源: P14

* **五分钟汇报的时间规划**
    * 难度：5 分钟的 presentation 比 50 分钟的难做——45 分钟有很充分的弹性去掌握伸缩度，5 分钟什么弹性都没有，还要在 5 分钟里把一件事情讲清楚，这是很有挑战的任务。
    * 听众与目的：不是讲给自己组里的人听，而是讲给其它组、不熟悉你这个模块的人听；不仅是为了打分，还是大家沟通、全班互相协调的机会——这份设计如果明显的接口有问题，人家还要说不对。
    * 两种规划方法：一种是按时间点分——把要讲的东西先铺好，每一分钟要讲到哪，一共五个点，每个点讲到什么位置；另一种是按内容重要程度分——哪几块重要、哪几块不重要，重要的花两分钟、不够就两分半，不重要的半分钟略过或 10 秒以内三言两语带过。
    * 时间点控制：给自己设几个时间点，一般做得好的组是上下配合的——台上一个人讲，台下好多人在到点时就给个信号。
    * 总时长约束：一共十个组、一共 90 分钟，还要开 PPT、还要有 Q&A（一分钟实际上肯定不够，总要两三分钟），一点多余的时间都不能有；超时就扣分，扣在打分表的 `style` 那一项上（那个 style 是指演讲人的演讲风格，不是你的 architectural style）。
    * > 易错点：5 分钟的第一顺位是把打分表上的每一项都讲到，而不是把你最有心得的那个部分讲痛快；讲完必备项之后还有余力，才是加分内容的场合。
    * > 来源: P13

* **打分与评审的规矩**
    * 打分表自己打印：给其它九个组各准备一张，还要做个记录。
    * 除分数外必须写理由：表上有"它的优点是什么、它的缺点是什么"；给人家扣分，扣的每一分都要写出理由来；如果给他满分，也要好好地夸他一下、说清他有什么样的优点。
    * 算分：九个组给你打的分数去掉一个最高分、去掉一个最低分算一个平均分；老师作为教师打一个分占 50% 的权重；两者加起来除以二得到最后的成绩。
    * 最终成绩由 TA 给：TA 要看一下你给其他组的评判是不是很认真，这就意味着你对同行劳动的尊重程度。
    * 算错分的代价：给别人多算或少算多少分，就从你最后得分里面扣多少分——你给这个组少了 2 分，你的总分里就扣 2 分；给那个组多了 2 分，你的总分里还是扣 2 分。
    * 同行评语：每组最后拿到一张很详细的打分表，除了分数分布还有所有同行给的评价；有时候会看到大家的意见可以有多么不同——有的组认为是很大的优点的地方，被另外的组认为是很大的缺点。
    * > 来源: P13

* **出错处理设计**
    * 用处两层：一是作为最终验收的一个标准，二是后面真正写代码时的参考。
    * 要列出的出错场景（在线预订实例）：搜索酒店时没有填目的地点或者酒店名；查机票时没有填出发地或者目的地；查询结果不存在时，在搜索结果区用文字提示"查询不存在"；真正预订的时候信息填写不完整；给酒店评分的时候星级没有选全；管理员在做搜索、审核、修改的时候信息填写不完全。
    * 边界处理：数据库故障这一项没有具体写进设计里，理由是要等后期写代码的时候才发现得出来、真出现了再修改；同时把联系方式留给用户，真出问题让用户可以联系到他们。
    * > 来源: P14

## 18. 构件与面向对象设计原则

> **一句话主旨**：给出构件的定义与两类开发风格中的指代，并逐条给出面向对象构件与打包的设计原则。

### 18.1 构件的定义与两类开发风格中的指代

* **构件（component）**
    * > 定义：构件是模块化的、可以被发布的、可替换的系统组成部分；它的实现封装在内部，对外只暴露一组接口。
    * 原文（OMG 给过的正式说明）：`a modular, deployable, and replaceable part of a system that encapsulates implementation and exposes a set of interfaces`。
    * 三个形容词都落到实处：它是模块化的，因为它本身就是一个模块；它是可以被发布的，所以它能作为发布单位独立交出去；它是可替换的，因为只要对外接口不变，内部被封装起来的实现就可以换掉——比如后来有了更好的算法，把实现换成新算法，只要外部接口不动，整个系统都不受影响。
    * > 来源: P15

* **两个缩写**
    * OMG 不是 oh my god：O 是 object，M 是 management，G 是 group，`Object Management Group`；UML 就是它发布的。
    * UML = `Unified Modeling Language`（统一建模语言）。
    * > 来源: P15

* **两类开发风格里构件的指代**
    * 结构化设计：一个构件代表你那个层次结构图里的一个方块；一个方块通常对应数据流图里的一个圆饼，也就是一个功能——它是**以功能为核心**划分出来的构件，是完成某一个功能的单位。
    * 面向对象（Object Oriented，OO）：一个 `class` 就是一个构件；但也不一定总是一个 class，这取决于这个 class 的复杂程度——有时候它可能是一群 classes，按某种规则分成一堆，然后这一堆打包交给某一个组去做，这一堆就是你的一个构件。
    * 两类构件需要的工具和设计原则不一样。

| 开发风格 | 一个构件指的是 | 划分依据 |
| :--- | :--- | :--- |
| 结构化设计 | 层次结构图里的一个方块 | 数据流图里的一个圆饼，即一个功能 |
| 面向对象设计（OO） | 一个 `class`，或按规则打包的一群 classes | 这个 class 的复杂程度，以及准备交给哪个组 |

### 18.2 面向对象构件的四条设计原则

* **开闭原则（open-closed principle，OCP）**
    * > 定义：`a module or a component should be open for extension but closed for modification`——一个模块、一个构件，对扩充应该是开放的，对改动应该是封闭的。
    * 违背的写法：`detector` 这个类的作用是收集各种 sensor 的状态、看有没有异常；最直观的一种写法是在里面加一堆 `if-else`（或者简单一点用 `switch-case`）——进来的是这种 sensor 就做这种处理，是那种 sensor 就做那种处理。
    * 什么时候需要 extension：以后技术进步，人家又发明出一种新 sensor，跟原来那些都不一样，那个时候你就得去改 `detector` 的源代码——去改核心源代码，这是一件很不受欢迎的事情；这就叫没有 close for modification。
    * 建议做法：专门设计一层接口——定义一个 interface 的 class，叫 `sensor`，新的 sensor 类型进来，就从它派生一个子类。
    * 类比：核心代码是墙上那个电源插座，接口就是插在上面的接线板；有了新的 sensor 类型就往接线板上插一个，接线板的口不够用再拿一个接线板从这个接线板插出去，可以无限扩展；而墙上那个插座的口是不用拆来拆去的。
    ```text
        核心部分（不动）
        [ detector 的核心算法 ]
                  |
        [ interface sensor ]   <==== 专门负责往外扩展的那一层
           /       |       \
      [ 烟传感器 ] [ 温度传感器 ] [ 震动传感器 ] ...   （都是派生出来的子类）
    ```
    * > 来源: P15

* **里氏替换原则（Liskov Substitution Principle，LSP）**
    * > 定义：`subclasses should be substitutable for their base classes`——子类应该能够替换掉它们的基类。
    * 命名来源：Liskov 是位女士，这条原则是用她的名字命名的，是她提出来的。
    * 实质：说白了就是向下兼容——你的新版本总是应该兼容老版本，所谓 base class 就是它的老版本。
    * 契约：派生出一个子类之后，要保证别人用你的时候虽然没用那个 base class，但他默认你反正是这一类的东西；基类有的那些默认行为你都应该有，那个 contract 你得尊重、得把它继承下来。
    * > 来源: P15

* **依赖倒置原则（Dependency Inversion Principle，DIP）**
    * > 定义：`Depend on abstractions, do not depend on concretions.`——依赖抽象，不要依赖具体。
    * 争取方向：让你的核心部分尽量依赖抽象的东西；比如核心部分依赖某一个算法，这是没问题的——算法不依赖于具体的实现，不依赖于你用哪种语言实现，也不依赖于你在哪台机器上、哪种类型的操作系统上实现。
    * 反例：如果你的代码过分依赖底层的某个具体东西，比如某个操作系统的版本，那你改起来就会有非常大的麻烦。
    * 边界：专门负责底层接口的那一层是没有办法的，它必然贴着具体平台；你能做的是尽可能把这种东西跟核心代码拆分开。
    * > 来源: P15

* **接口隔离原则（Interface Segregation Principle，ISP）**
    * > 定义：`many client-specific interfaces are better than one general-purpose interface.`
    * 适用场景：针对有明显 `client-server` 特征的那种划分——一个 class 充当 server 的角色，有很多 classes 来用它、做它的 clients。
    * 做法：把你这几种主要的 client 划出来，给每一个 client 设计属于它自己的那套 interface；即使有些功能是重复的，你宁可重复两遍——给它提供一套，再给它提供一套。
    * 不该做的：不要因为它们 share 了一部分功能，你就弄一个大的 interface 让它们两家分别去用。
    * > 来源: P15

### 18.3 构件是一堆类时的分堆原则

* **重用发布等价原则（Release Reuse Equivalency Principle，REP）**
    * > 定义：`the granule of reuse is the granule of release.`——重用的粒度就是发布的粒度。
    * 做法：对那些一开始做设计时就准备日后重用的模块，你最好把它们抽出来放在一堆，升级的时候大家一起升级。
    * 边界：你要重用的规模有多大，一批新版本 release 的规模就应该有多大；要是七零八落地升级，最后别人重用的时候版本不统一，就会乱掉。
    * > 来源: P15

* **共同封闭原则（Common Closure Principle，CCP）**
    * > 定义：`classes that change together belong together.`——要一起改变的东西，就放到一起。
    * 需要再分情况："一起改变"本身还要分是一起**被**改变，还是一起**去**改变某个东西；这两种情形对应的策略是不一样的。
    * > 来源: P15

* **共同重用原则（Common Reuse Principle，CRP）**
    * > 定义：`classes that aren't reused together should not be grouped together.`——不总在一起被重用的类，就不要打在一个包里。
    * 与 REP 的关系：它是补充关系——REP 说的是你想做 reuse 的东西最好都打成一个包；CRP 说的是你要 reuse 的东西还得再分一分类，如果它们不是总在一起 reuse，就最好不要打在一个包里；要一起用、要一起重用的，才打在一个包里。
    * > 来源: P15

* **分堆的落地技巧**
    * 你要看着类图，按某种方式左一分、右一分，把你的 components 划分出来——这就像看着数据流图左一分右一分、分出一个系统的层次架构图一样。
    * 边界：这些技巧等你真正用到的时候再去学。
    * > 来源: P15

### 18.4 面向对象详细设计的步骤与 OCL

* **详细设计的步骤**
    * 先把 classes 分类：属于问题域的、跟你面对的那个现实问题直接相关的那些类分出来；跟后台的基础设施（`infrastructure`）这些底层东西有关的那些类也分出来。
    * 然后细化，先细化那些不需要重用的部分；细化的是四样东西——你要传递的 `message`、抽取出来的 `interface`、`attributes`，以及每一个 process 或者说 method 内部的算法。
    * 再往下是设计数据库以及数据库的管理。
    * 再考虑动态，也就是它的 `behavioral model`（行为模型）。
    * 再细化一个 `deployment diagram`（部署结构图）。
    * 收尾迭代：这个设计过程从来不是一次成形的，一定是一个迭代的、不断改善的过程，所以中间有一个 `refactor`（重构）的过程；重构的过程中始终要记住 `be open to the alternatives`——总是要想一想，还有没有别的、更好的解决方案。
    ```text
      classes 分类
        |-- 问题域类（与现实问题直接相关）
        |-- infrastructure 类（后台底层）
                 |
           细化（先做不需要重用的部分）
                 |
        +--------+--------+-------------+
      message  interface  attributes   每个 method 内部算法
                 |
        设计数据库及数据库的管理
                 |
        考虑 behavioral model
                 |
        细化 deployment diagram
                 |
        refactor：迭代改善，be open to the alternatives
    ```
    * > 来源: P15

* **OCL（Object Constraint Language，对象约束语言）**
    * > 定义：OCL 是 UML 的一个补充（`complements UML`），用接近伪代码的形式，为一个对象或它的某个操作写明前置条件（pre-condition）与后置条件（post-condition）。
    * 形式：它有点像伪代码，有自己正式的文法和语法（`formal grammar and syntax`）；它是用程序员比较容易理解的那种方式，去描述 design model elements 里面的 object constraint，也就是一个对象所受到的约束是什么。
    * 描述内容：它想把一个对象的使用条件写清楚——一个 class 有一个 method，你要能正常使用它，前提条件是什么（在使用它之前你的系统、或者说你传进去的参数应该处于一个什么状态）；而用完了这个东西之后，系统会处于什么状态，或者某些变量会变成什么状态。
    * 四个要素：`context`（你到底要描述的是什么东西，不一定是一个 class，也可能是 class 里面的某一个功能、某样东西，或者是整个 class）、`property`（这个对象的属性，如果对象是一个 class 那就是它的 attribute）、`operation`（这个对象上的操作）、`keywords`（`if`、`then`、`else`、`and`、`or`、`not` 这些像程序里面关键字的东西）。
    * 例子（有一个 `print job` 类，是给 printer 的一个任务，里面有一个函数叫 `validate`，作用是把某一个状态从 no 改成 yes）：`context` = print job 这个类里的 `validate`；`property` = job authorization（当前处于 no 状态）；前置条件 = 传进去的两个整型参数都为正、job authorization 处于 no 状态；后置条件 = 这两个条件满足时 job authorization 从 no 改成 yes。
    ```text
      context      print job 这个类里的 validate
      property     job authorization（当前处于 no 状态）
      operation    validate
      keyword      if / then / else / and / or / not

      pre-condition    传进去的两个整型参数都为正；job authorization 处于 no 状态
      post-condition   这两个条件满足时，job authorization 从 no 改成 yes
    ```
    * > 易错点：它描述的不是输入输出，而是"用之前的状态"和"用之后的状态"。
    * > 来源: P15

## 19. 算法设计及其表达工具

> **一句话主旨**：说明传统构件的算法设计过程，并对比流程图、盒图、判定表与伪代码这几种表达工具。

### 19.1 算法设计的过程

* **构件以功能为核心，详细设计的核心落在算法设计上**
    * 传统软件工程里构件的划分是以功能为核心的：一个构件就是完成某一个功能的单位。
    * 那么实现这个功能的详细设计，核心就落在 `algorithm design`（算法设计）上。
    * > 来源: P15

* **算法设计的过程**
    * 你去看那份 design 的 `description`，明确你在这一个构件里要完成的是什么功能。
    * 然后做 `refinement`，把算法层层细化下去。
    * 写程序的时候要用 `structured programming`（结构化程序设计）。
    * 最后还有 `formal methods`（形式化方法），用形式化的方法做一个正规的检查。
    * > 来源: P15

### 19.2 程序流程图与盒图

* **程序流程图（flow chart）**
    * 定位：最常用最常用的工具；不管你第一门语言课学的是 C、Java 还是 C++，老师给你讲的第一件工具大概都是它，几种符号是什么意思你们也都看得懂。
    * 历史：作为描述算法和程序流程的工具，它是最古老的一个，后来也经历了非常多批评。
    * 最大的批评：太容易改了；容易出错，而且错误不容易被识别出来——说到底是，一个改动对你整个程序结构的破坏程度，你是不容易体会到的。
    * 典型改法：在流程中间加一个需求、加一个条件，加一个 `condition Z`，`if true exit the program`，满足就直接从这个程序里跳出去、跳到别的地方去；在黑板上做这件事更随意，哗哗哗把这块擦掉、加一个菱形、掐一根线扯到哪儿去都行，箭头可以满处乱飞。
    ```text
              [ 原来的处理流程 ]
                     |
              [ 顺序执行的若干步 ]
                     |
               < condition Z >  ---- true ---->  [ exit the program ]
                     |                              （掐一根线，直接扯出去）
                   false
                     |
              [ 后面的处理 ]
    ```
    * > 提示：工具还是那个工具，脑子里得有 `structured` 这个概念；改流程图的时候自己管好自己，不要做那种在嵌套结构里飞来飞去、指针乱飞的事情。
    * > 来源: P15

* **盒图**
    * 画法：它把整个程序画在一个盒子里；顺序执行的语句，就是每一行语句一个长方形，一条一条顺序往下执行。
    * `if-else` 的画法：上面写一个 if 条件，下面分成两块，这边是 true、那边是 false。
    * 循环：它又有另外一种画法；再有嵌套，就往里再套一层框。
    * 好处一（看复杂度）：你去数那个盒子里面套了多少层——有很多逻辑嵌套的话，你会看到它一层一层套进去，套了多少层，你大概就知道这个程序的复杂程度是多少。
    * 好处二（看改动代价）：像跳转式的那种改动，在盒图里就不容易改了，为了做这个改动你要在盒子里面擦掉很多东西、再把什么重新画过；而你要擦掉的那一部分，正好就是整个程序直接受影响的部分——影响范围有多大、改起来有多难，从你改这张图有多难就看得出来。
    * 推广情况：除了盒图，还有很多七七八八、稀奇古怪的各种工具被人推荐出来，最后都不了了之；习惯是一个很强大的势力——基本上每个程序员一开始写程序老师教的都是 flow chart，等你已经习惯了一种工具再强行让你换一种，不管这工具有多好都很难推广，所以到这一版书上最后还是只剩下一个 flow chart。
    ```text
        盒图的基本画法

        +-----------------------------+
        |  语句 1                      |   顺序：一行语句一个长方形，
        +-----------------------------+   一条一条往下排
        |  语句 2                      |
        +-----------------------------+
        |  if <condition>             |   if-else：条件写在顶上，
        +--------------+--------------+   下面分成 true / false 两块
        |   true 块     |   false 块    |
        |              |              |
        +--------------+--------------+
    ```
    * > 来源: P15

* **两种工具的四点对比**

| 对比点 | 程序流程图（flow chart） | 盒图 |
| :--- | :--- | :--- |
| 表达方式 | 方框、菱形用箭头连成流程 | 整个程序装在一个外框里，按嵌套分层 |
| 复杂度的可见性 | 箭头可以满处乱飞，嵌套关系不容易看出来 | 数盒子套了多少层，就知道程序有多复杂 |
| 改动的代价 | 擦一块、加个菱形、扯一根线，破坏程度体会不到 | 要擦掉重画的那一部分，就是直接受影响的范围 |
| 推广情况 | 最古老也最普及，习惯势力把它保住了 | 命不长，最后没有留下来 |

### 19.3 判定表与伪代码

* **判定表（decision table）**
    * 适用条件：如果你遇到各种条件的排列组合，不同的情况要对应不同的处理方式，那么一般来说有这么一张 `decision table` 可以帮上忙。
    * > 来源: P15

* **伪代码（PDL，Program Design Language）**
    * > 定义：PDL 就是常说的 pseudo-code（程序设计语言）；它的特点是基本上长得很像一个程序，但关键的、比较复杂的地方是用自然语言来描述的。
    * 优势一：非常容易跟真正的 `source code` 结合，非常容易被翻译成真正的代码。
    * 优势二：`machine readable, no need for graphics input`——要输入一个程序结构，画一张程序流程图是很麻烦的事情，而伪代码敲进去很简单；对机器来说，你给它伪代码、它替你自动生成一张程序流程图，这是可以做到的，写一个转换的程序就行。
    * 反向的边界：你给它一张程序流程图、让它给你生成源代码，那件事非常难。
    * 对维护的意义：对 `maintenance team`（维护的团队）来说，PDL 也是比较容易接受的一种表达，总归比直接读源代码要好理解。
    * > 来源: P15

## 20. 用户界面设计的三条黄金原则

> **一句话主旨**：把三条黄金原则展开成各自的机制，逐条给出可落在界面上的做法与典型反例。

### 20.1 界面设计者的知识背景与三条原则

* **界面（user interface，UI）的定位**
    * 你的客户用得爽不爽，账最后都算在界面上：他有什么地方用得不顺，都是由这个 `interface` 引起的，界面上首当其冲要挨骂；要是他脾气再不好一点，还会殃及无辜，连机器硬件也跟着倒霉。
    * UI 不等于美工：`web app` 的美观确实占了很重要的位置，但 UI 更重要的地方，还是偏重技术。
    * > 来源: P16

* **做好界面所需的知识背景**
    * 对人机交互（human-computer interaction，HCI）要有比较好的理解。
    * 要知道一点用户心理学——这一点非常重要。
    * 要懂人机交互的基本技术。
    * 要能理解程序员的世界，还要能理解整个系统的架构。
    * 另外还要有一点点美工的概念，也就是审美观。
    * 选人取向：不会专门去找一个人做美工，还是希望找一个技术人员、同时他又有一点美感、有点审美观；现在的工具也很好，你不需要真的会画画，只要找得到足够好的元素，也能做出一个比较清爽漂亮的界面来。
    * > 提示：这几条摆在一起，界面设计的重心就很清楚了——技术是底子，心理学和审美是加成；中间那条"理解整个系统的架构"最容易被忽略，界面是长在系统上面的，你不理解底下的结构，就设计不出跟它相配的交互。
    * > 来源: P16

* **三条黄金原则（the golden rules）**
    * `place the user in control`（把用户放在掌控位置）。
    * `reduce the user's memory load`（减轻用户的记忆负担）。
    * `make the interface consistent`（保持界面一致）。
    * 三根主干下面挂的是实现这条原则的具体机制，每一条机制都是一个可以落在界面上的做法。
    ```text
      user interface design 的三条 golden rules
      |
      +-- place the user in control
      |   +-- 交互流程中的多余步骤与误操作
      |   +-- 交互方式的灵活性
      |   +-- 交互的可中断与可撤销
      |   +-- 交互随熟练程度的精简与用户定制
      |   +-- 普通用户与技术内部细节的隔离
      |   +-- 直接操作屏幕上出现的对象
      |
      +-- reduce the user's memory load
      |   +-- 不让用户记住任何东西（尤其不要在短时间内记）
      |   +-- 建立有意义的默认值
      |   +-- 界面布局的真实世界隐喻
      |   +-- 信息渐进披露
      |
      +-- make the interface consistent
          +-- 单个软件内部风格统一
          +-- 当前任务所处的上下文
          +-- 产品家族跨产品的一致性
    ```
    * > 来源: P16

* **三个常见机制各归哪一条**
    * `undo`：归第一条，属于"宽容"那一块——你允许用户后悔、允许他反悔。
    * 导航条：导航条要做得充分有导航性，用户就不需要努力去记"我刚才访问了哪里、哪里、哪里"，还能随时知道自己现在在哪儿——这是减轻记忆负担的典型。
    * 帮助文档：你给他提供一些有用的提示，提醒他"你想做的那个功能可以在哪儿用"，同样是在替他记事。
    * > 来源: P16

### 20.2 把用户放在掌控位置（place the user in control）

* **原则本身的含义**
    * 字面意思是"把用户放到掌控的位置上"。
    * 讲师的另一种说法：设计界面记住的第一条原则，就是要把你的用户牢牢地掌握在你的魔爪之下。
    * 落法：他要点的那个东西，你要保证就是他该点的东西——他点下去的结果，跟我们想要他得到的结果是一致的；换句话说，我不想让他搞乱的地方，我一定让他搞不乱。
    * 性质：它不是一个动作，是一组机制。
    * > 来源: P16

* **机制一：交互流程中的多余步骤与误操作**
    * 原文：`define interaction modes in a way that does not force a user into unnecessary or undesired actions.`
    * 一句话：你如果不想让他犯错误，你就不要给他犯错误的机会。
    * 环节一（多余的步骤）：他要完成这件事，你要用最少的操作让他做到他想做的事，不能让他中间做一步对他毫无意义的动作；有的多余步骤纯粹是因为你程序设计的缘故（"不好意思，你只能在这儿多点一下，才能进到下一页"），偶尔让他点一次无所谓，天天让他用这个东西、天天让他多点一次，他就要爆发了。
    * 环节二（误操作 `undesired actions`）：一个普通用户一不小心点了什么东西就把你整个系统搞崩溃了——那不是他的错，那是软件工程师的错，而且最主要的是 UI 的错。
    * > 来源: P16

* **机制二：交互方式的灵活性（provide for flexible interaction）**
    * 与前一条的关系：这一条跟前一条是互补的——你应该把用户放在掌控的位置，不想让他犯错误就不要给他机会犯；但是不能太过分，你要给他多种可行的输入方式。
    * 反例（炒外汇软件）：原来要做交易时界面上有一个交易的输入框、数字都从键盘输进去；升级以后大键盘不能用了，屏幕上弹出一个虚拟的小键盘、只有数字和小数点。
    * 反例的两个过分之处：第一，只能用鼠标去点那些数字，用鼠标点着输肯定不如手敲键盘来得爽；第二，为了那个键盘不占屏幕太大的地方把它做得非常小，上了年纪的人手不稳，要眯着眼睛看那个小东西、拿鼠标哆哆嗦嗦地对上去，一点就点错了。
    * 出发点与错处：堵住非法输入的思路本身没错，错在过头——你把一个老年人本来可以用的东西，变成了一个他根本就没法用的东西。
    * > 易错点：你不想让用户输错，不等于只能让他用你给的那一种输入方式。
    * > 结论："不许出错"要求的是适度的约束；把输入方式收窄到只剩一种、而且那一种还很难用，就等于把"不许出错"变成了"不许用"。
    * > 来源: P16

* **机制三：交互的可中断与可撤销**
    * 原文：`allow the user interaction to be interruptable and undoable.`
    * 落法：说白了就是要仁慈（`have mercy`）——你一定得给人家改错、反悔的机会，得有一个 `undo` 的功能。
    * 现状边界：现在大家已经被从微软开始的那批产品宠坏了；你做出来的东西里头居然没有 `undo`，人家手一滑干了什么事情、没有反悔的余地，就会骂死你"这个软件太土了"。
    * > 提示：`undo` 也可以理解成"用户退回去的时候，你替他记住了上一步"，那就属于下一条"减轻用户的记忆负担"；它放在这里，重点在宽容——你允许用户后悔。
    * > 来源: P16

* **机制四：随熟练程度精简交互并允许定制**
    * 原文：`streamline interaction as skill levels advance and allow the interaction to be customized.`
    * 定位：这是一个更高的要求——允许用户按自己喜欢的方式去定制他的界面。
    * 普及程度：五六年前这还是相当高的要求，现在用得比较普遍了——微博、BBS，各种各样的地方都会提供这方面的功能。
    * > 来源: P16

* **机制五：隔离普通用户与技术内部细节**
    * 原文：`hide technical internals from the casual user.`
    * 做法：把你的用户分一分级别——除了 `admin` 可以接触到所有底层的东西之外，那些不该让普通用户碰到的东西，你要很小心地把它藏好。
    * 时机：这件事必须在设计的时候一起做——这条界限一定要划得很清楚。
    * > 来源: P16

* **机制六：直接操作屏幕上出现的对象**
    * 原文：`Design for direct interaction with objects that appear on the screen.`
    * 例子：用操作系统的时候桌面上都有一个垃圾箱；想把什么东西扔掉，可以拿鼠标拖着它、直接拖到垃圾箱里去，一松手就扔掉了——这是一种非常直观的交互。
    * 效果：这一类的直接交互会给用户非常好的体验，会给他一种"我是 `in control`"的感觉——觉得你给我的这个软件是为我服务的，我可以控制它，我在控制局面。
    * > 提示：至于实际上 `who's in control`，用户感觉自己说了算，和他真正被允许做什么，是两件事。
    * > 来源: P16

### 20.3 减轻用户的记忆负担（reduce the user's memory load）

* **原则核心**
    * 这一条的核心只有一句话：一定不要让用户记住什么东西，尤其是不要让他在短时间内记住点什么，再去做下一步。
    * > 来源: P16

* **说明书编写的用户假设**
    * 一条做产品的原则：你设计产品说明书的时候，要把你的客户当成白痴和弱智——前提是他还得会读。
    * 推论：如果白痴和弱智看了以后都能很容易上手、会用，那我们普通人都会用、都会觉得好用；那么弱智和白痴肯定记性很不好，所以你不可以让他记住什么东西，再去作下一步的内容。
    * > 来源: P16

* **反例：查询与修改被拆成两个人的工作**
    * 场景：想要修改某个人的信息，正常想法是先把他查出来、然后点修改；对方要求你必须先点查询，把人找出来之后，把组长的 ID 号抄下来——而且还是 `case sensitive` 的，大小写有区别，得照着抄；点修改的时候会弹出一个框，要你把他的 ID 输进去。
    * 成因：修改是另外一个人做的，两个组任务的边界划分得不清楚。
    * 后果：现场两拨人开始 `finger-pointing`（互相指着对方说这是你的事），谁也说不清该谁改；边界本身模糊时，每个人都觉得自己那一块完成了，界面上的窟窿还是得用户来填。
    * > 易错点：已经查出来的对象，还要用户自己抄下来、再手工输回去，中间这一环不产生任何信息，纯粹是让用户替系统搬数据；这是最典型的一种违背"减轻记忆负担"的设计。
    * > 来源: P16

* **建立有意义的默认值（establish meaningful defaults）**
    * 反例（炒外汇软件）：登录方式从一个输入框改成用一个下拉框选账号；问题是这个下拉框做得不好——它没有一个 `default`，默认是空的，而那个空着的样子看上去跟升级以前那个输入框是一样的。
    * 更糟的地方：一般的下拉框光标一点上去就应该自动出现，它偏不是，光标点上去就在那儿闪，旁边有一个很小的向下的箭头，点一下那个箭头下拉框才出来。
    * 改进方向：既然允许很多人在同一台机器上用、有好几个账号，又不涉及保密不保密的问题，那起码可以统计一下使用次数，把使用次数最多的那个人当作默认账号；如果这台机器上只有一个人用，那他的账号自动就是默认，连一次操作都给用户省下来了。
    * 补充：这类细节还有一堆——你能提供快捷键、快捷方式，那也会更好。
    * > 结论：默认值不是"随便填一个"，它是替用户先做一个合理的判断；空默认值加上一个看起来像输入框的外观，等于给用户设了一个陷阱。
    * > 来源: P16

* **界面布局的真实世界隐喻**
    * 原文：`the visual layout of the interface should be based on a real-world metaphor.`
    * 适用条件：软件系统存在之前，人家用人肉的、用纸做的那些表格本来就在工作——没有你这个系统人家照样干活——而你是要用你的系统去取代它，比如无纸办公就是要把那张纸去掉、变成你系统里的一个电子表格让他填。
    * 原则：你这个电子表格，最好跟他原来那张纸上的表格是一样的。
    * 事故实例：有一个人去银行办存款业务，回去一查账上多了天文数字那么一大笔钱；查下来的结果是那个银行职员在输身份证号码的时候，把身份证号码敲到了存款金额上面。
    * 机理：很大的可能是这个电子表格让他填的时候跟他以前填的那张单子的位置略有不同——他本来习惯于在这个地方填身份证号码，结果你把存款金额的那个空放在了他习惯看到的那个位置上；全神贯注应该不会错，但他只要有点疲劳、稍微一走神，那个强大的习惯就会回来。
    * 做法：先调查一下他在用你这个系统之前是怎么工作的；你做出来的这一套电子流程，要跟他以前那套人工流程最大限度地符合他的习惯，不要让他重新记一遍表格的位置。
    * > 来源: P16

* **信息渐进披露**
    * 原文：`Disclose information in a progressive fashion.`
    * 底线：你不可以一次性把所有的细节唰地全弄在一个界面上摆出来给人看。
    * 讲究的地方：一个界面一次要展示多少条、宽度有多宽、每一个下拉菜单的深度有多深，这都是很有讲究的事情。
    * > 来源: P16

### 20.4 界面一致性与界面用词的理解一致

* **一致性的两种概念**
    * 第一种是说：在我这一个软件内部，我希望它整体的风格是一致的。
    * 第二种是当前任务所处的上下文，以及产品家族跨产品的一致性。
    * > 来源: P16

* **单个软件内部的整体风格**
    * 要求：你的整个软件可能是好几个组分工做出来的，但最后做出来的东西不能让人一看就是一个七拼八凑的结果。
    * 反面实例（假的 interface）：前面做一个统一的界面、一个壳，你点这个按钮，它就去把那个组的 `.exe` 文件运行起来、打开那个组自己的一个界面；点另一个按钮，起的又是另一个组的一个界面，这几个界面谁跟谁都不挨着。
    * 为什么是假的：后台的数据库没有和起来——用这个组输进去的东西、想用那个组的界面调出来查，查不到。
    ```text
      统一的外壳（前端）
        |
        +-- [按钮 A] --> 启动 A 组的 .exe --> A 组自己的界面
        +-- [按钮 B] --> 启动 B 组的 .exe --> B 组自己的界面
        +-- [按钮 C] --> 启动 C 组的 .exe --> C 组自己的界面

      后台数据库：A 组输进去的东西，用 B 组的界面调不出来（数据没有汇到一起）
    ```
    * > 结论：正经做一个软件，这种事情是不允许的；你的软件不管有多少人合起来做，它都要有一个整体的形象。
    * > 来源: P16

* **当前任务所处的上下文**
    * 原文：`allow the user to put the current task into a meaningful context.`
    * 场景：一边在上网、一边在聊 QQ、一边在写论文，同时还要做 presentation，于是 PPT 也开着、Word 也开着、Excel 也开着；正干着这个的时候突然想打开另一个东西，那么多窗口，要用最快的速度把它找出来。
    * 机制：屏幕下面那条工具栏——你每打开一个窗口，底下就多一个图标；这个图标的设计也是有学问的，你一看图标就知道是哪个东西。
    * 对照点：`Word` 通常是一个蓝色的，`PowerPoint` 是橘红色的，`Excel` 是绿色的。
    * 目的：这就是让用户随时知道自己在哪儿、想要的东西在哪儿，属于 `consistent` 里的一个环节——容易找到。
    * > 来源: P16

* **产品家族跨产品的一致性**
    * 原文：`Maintain consistency across a family of applications.`
    * 范围：这一条说的不是某一个软件产品内部一致的问题，而是说你这个产品——这一系列的产品、这个家族——它的风格都要一致。
    * 判据（凭什么说它一致）：同一家族的几个产品，在界面布局、操作方式、术语命名、图标与视觉风格上彼此呼应；用户在这个产品上学到的操作习惯，搬到同族的另一个产品上大体仍然成立——`Word`、`PowerPoint`、`Excel` 三个图标的颜色对应关系就是一个现成的对照点，你在其中一个上形成的识别习惯，在另外两个上照样管用。
    * 好处：家族一致最直接的作用是减轻用户的记忆负担——他不需要为每一个新产品重新学一套操作方式；一致的布局与合理的默认值还能降低出错概率（用户靠的是习惯，习惯一旦养成，他一走神就会顺着旧习惯动手）。
    * 另一条理由：多人分工做出来的东西要有一个整体形象，这条要求在一个软件内部成立，在一个产品家族上同样成立。
    * > 来源: P16

* **界面用词与用户理解的一致性**
    * 场景：一个人打电话来说 `my computer doesn't work. The hard drive crashed, what do I do?`（我的硬盘驱动器坏掉了，我怎么办？），这边的人回他一句 `did you back up?`
    * 错位点：`back up` 这个词在英语里是"什么东西要爆炸的时候，叫你往后退、赶快撤"；那边一听就笑了，说"听着像要炸了吗？"
    * 边界：界面上写的术语，客户的理解跟你自己的理解很容易是不一致的。
    * > 结论：你在界面上写任何你以为是那个意思的东西的时候，你要确信你的客户和你的理解是一致的——很容易是不一致的。
    * > 来源: P16

### 20.5 页面关系与各页功能

* **用户端与管理端分开**
    * 普通用户的界面和管理员的页面是分开的。
    * 管理员那一侧单独提供一个链接关联，正常访问的路径上看不到——也就是客户不能直接访问管理员的那些操作。
    * 访问流：进站以后是预订酒店的查询和用户登录；登录之后就进入个人账户界面，看他以前预订过的历史信息。
    * 管理端逻辑更简单：它跟用户端是两个入口，管理员按酒店 ID 把已经登录上去的信息查出来，在表单里改完提交。
    * > 来源: P14

* **各页承担的功能**

| 页面 | 承担的功能 |
| :--- | :--- |
| 主查询页 | 按目的地和日期搜索；展示商家提供的打折酒店信息与推荐酒店；管理员入口链接藏在这一块 |
| 查询结果页 | 输入目的地后展示结果列表；可按标准排序筛选；显示价格与用户评价（星级或百分比）；右侧是广告性质的推荐位 |
| 酒店详情页 | 酒店星级、地址、内部照片；在这里下单，选房型、选住几天；同时展示其他住客的评价 |
| 航班列表页 | 按时间或价格排序；分页显示；右侧推荐用户可能要去的那座城市的酒店 |
| 登录后的个人页 | 查看历史预订信息，修改入口也在这里 |
| 管理端页面 | 管理员按酒店 ID 查询已录入的信息，在对应表单里修改、提交 |

    * 两处取舍：主查询页上的搜索框只接受目的地和日期这一类条件；打折与推荐的酒店直接铺在首页，用户点一下就能进详情；结果页右侧那一栏是广告性质的推荐位，酒店和门票、机票都能往上放——这是界面设计里的一处取舍，不是随手摆的。
    * > 来源: P14

* **界面汇报的边界**
    * 界面这一节要讲得快、讲得直接：讲的是页面之间的关系、每一页承担什么功能，别的不用讲。
    * 补充要求：界面做得接近现成的网站不是坏事，但光是页面像还不够——后台是怎么样的、各个端分别是什么样的系统，这些都要在报告里说清楚。
    * > 来源: P14
