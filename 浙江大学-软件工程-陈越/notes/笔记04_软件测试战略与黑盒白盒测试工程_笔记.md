## 1. 测试的根本立场与交付物

> **一句话主旨**：确立测试的立场是站到程序员对立面去找错，并厘清测试团队最终必须交付的五类产物。

* **测试的根本目的（purpose of testing）**
    * > 定义：测试是为了发现问题（for finding errors），而不是为了证明软件正确。
    * 正确立场：站到程序员的对立面，想方设法去破坏程序；想尽办法破坏不了，才是对开发者最大的帮助。
    * 公司里测试员按「找到更多错误」发奖金，而非按「证明程序没错」发放。
    * 什么错误都没测出来，只说明测试太弱，并不说明软件没有错。
    * > 易错点：列几个极简单 case、全部通过就宣布「程序是对的」——立场站到了程序员一边去「保护」他。
    * > 来源: P17
* **测试计划（Test Plan）的启动时点**
    * 设计尚未通过最终验收、代码还没写时，测试计划就可以同步启动。
    * 启动先看战略：整体策略、如何分层、自顶向下还是自底向上、有哪些测试类型。
    * > 来源: P17, P18
* **测试交付物（Test Deliverables）**
    * **Bug 清单**：列出发现的所有缺陷。
    * **测试用例表（Test Cases）**：每行含用例、期望输出（expected output）、实际输出（actual output）、状态（status：相符 / pending / corrected 等）；不相符即是一个 bug。
    * **需求符合度（Requirements conformance）**：每个功能单独看都对，合到一起未必是需求规格描述的软件，须逐项对照需求检查。
    * **性能指标（Performance）**：对安全性、效率等有要求的逐一核对。
    * **质量指标（Indication of quality）**：综合以上给出总体质量评价。
    * > 来源: P17
* **两个历史事故**
    * 1963 年火星火箭：Fortran 转录时把 `DO 5 I = 1, 3` 的逗号模糊成小数点，敲成 `DO 5 I = 1.3`，循环被当作赋值语句 `I = 1.3`，编译器诊断不出，损失 1000 万美元；根因是测试时没核对循环体结构。
    * 飞机导航：地图上用字母 `Cali` 代表目的地 Cali，而导航系统中该字母对应反方向的 `Bogota`，飞机撞山、159 人遇难（163 减 4）；根因是少做了一项**一致性测试（consistency test）**，未分析**用户画像（user profile）**。
    * > 来源: P17

## 2. 验证与确认（V&V）与 SQA

> **一句话主旨**：区分验证管「单个模块是否正确」、确认管「拼起来是否是想要的软件」，并明确测试只是 SQA 的一个要素。

* **验证与确认（Verification & Validation）**
    * > 定义：二者中文字典都译作「验证」，但关注点不同——验证管模块，确认管整体。
    * 验证回答 *Are we building the product **right**?*，检查每个模块是否以正确方式实现、功能是否正确。
    * 确认回答 *Are we building the **right** product?*，检查所有正确模块组装后整体是否就是需求想要的软件。
    * 「每一个功能都正确、放在一起却不是你要的软件」这类问题由确认阶段把关。
    * > 来源: P17

    | 概念 | 英文问题 | 关注点 |
    | :--- | :--- | :--- |
    | 验证（Verification） | Are we building the product **right**? | 每个模块是否以正确方式实现、功能是否正确 |
    | 确认（Validation） | Are we building the **right** product? | 各模块拼起来是否就是需求想要的那个软件 |

* **软件质量保证（Software Quality Assurance, SQA）**
    * 软件测试只是 SQA 的一个要素（Software testing is only one element of SQA），测试不等于 SQA 全部。
    * 质量必须内建于开发过程之中：*Quality must be built into the development process. One cannot use testing to add quality after the fact.*
    * 过程本身不合规，软件质量从一开始就被注定高不了；指望最后靠测试团队兜底既不公平也不现实。
    * 验证与确认是 SQA 团队最关注的两个环节。
    * > 来源: P17

## 3. 测试与调试的区别

> **一句话主旨**：测试只负责发现并定位错误，调试负责改正错误，两者是不同策略、通常由不同角色承担。

* **测试（Testing）与调试（Debugging）**
    * > 定义：测试 = 发现错误、给出「哪里有错」的报告；调试 = 改正错误的过程。
    * 测试只负责定位错误，调试负责把错误改掉。
    * 调试一般不由测试团队做，改错仍由开发者完成。
    * > 来源: P17, P18

## 4. 分层测试战略

> **一句话主旨**：测试从构件开始沿单元、集成、确认、系统四层由小到大展开，各层配以不同技术与配套程序。

### 4.1 四层测试的四部曲

* **测试的展开方向与技术分配**
    * 真正执行测试从 component（构件）开始：程序员先对自己做的 component 做单元测试（unit testing），提交后从 component 层向 integration（集成）、再向 system（系统）逐级完成。
    * 单元测试一般用**白盒测试**，集成与系统测试一般用**黑盒测试**。
    * > 来源: P17
* **传统结构化架构的四部曲**
    * **单元测试（Unit Testing）**：一个 component 一个 component 地测，每个 component 下更小的 component 各自完成单元测试。
    * **集成测试（Integration Testing）**：把 component 逐步集成，每集成一步都要做一次验证——新集成功能是否正确、集成后整块功能是否仍正确。
    * **确认测试 / 验收测试（Validation Testing）**：所有东西做好后，对照需求规格说明书里的**验收标准（Validation Criteria）**，功能、性能及其他标准逐条测；标准写明「达到即付钱」。
    * **系统测试（System Testing）**：安装、调试到目标大环境下，做整体系统测试。
    * 顺序链：单元测试 → 集成测试（每步验证）→ 确认测试（对照验收标准）→ 系统测试（装入真实环境）。
    * > 来源: P17

### 4.2 单元测试的配套程序：Driver 与 Stub

* **单元测试的覆盖方面与测试目的**
    * 单元测试把一个 module 拿过来，喂入一堆 test cases，产出 bug 清单与结果。
    * 每个 test case 必须有明确的**测试目的（testing purpose）**，在正式技术评审（formal technical review）环节核查以提升后续效率。
    * 需覆盖：接口（interface）、数据结构（data structures）、边界条件（boundary conditions）、独立路径（independent paths）、错误处理路径（error-handling paths）。
    * > 来源: P18
* **Driver（驱动）**
    * > 定义：相当于在线评测系统（ZOJ、PAT）里的 judge 程序，为只提交 module / 函数的被测者补写 main。
    * 职责：接收所有 test cases，调用被测模块、把模块产生的结果打印出来并检查。
    * 典型模板：读入 inputs → 循环 { 读入一个 test case → 调用被测模块 → 输出结果 }。
    * > 来源: P18
* **Stub（桩）**
    * > 定义：一个接口与原 sub-module 完全相同、内容为空壳的「假模块」，只按预先知道的正确值返回。
    * 用途：隔离错误来源。被测模块内部调用下层 sub-module 时，一旦结果出错，无法判断是被测模块自己错了还是 sub-module 错了。
    * 做法类似 switch-case：事先知道有哪些 test case 及各 case 下 sub-module 若正确应返回什么值，在 stub 里直接返回该正确值，不做真实计算。
    * 这样所有下层调用都返回正确值，若 driver 最终结果仍不对，只能是被测模块自身的问题。
    * > 来源: P18
* **Driver 与 Stub 的成本权衡**
    * 模块复杂、调用很多底层模块时，要为每个底层模块写对应 stub 并针对每个 case 返回正确值，是实打实的工作量。
    * 策略选择：**自顶向下测要写很多 stub，自底向上测要写很多 driver**，两种方式都有成本。
    * > 来源: P18

### 4.3 集成测试策略

* **Big-bang testing（一次性组装）**
    * > 定义：每个模块分头测完，最后一次性合到一起测，是最省事的策略。
    * 缺陷根因是 **isolation of causes is complicated（原因隔离复杂）**：合起来发现系统不正常，却说不清是谁的错，各组互相甩锅。
    * 本门课期末验收近似此模式：五个组分别验收都「对」，再在 72 小时内拼成系统统一测；真敢全程 big-bang 必定悲剧。
    * > 来源: P18
* **Top-down（自顶向下）**
    * 从最顶端控制模块开始测，先写 stub 返回假数据，再用真实模块一层层往下替代，直到测到底层。
    * 优点：**major control / decision points 最早被测到**，大方向先测对。
    * 缺点：从下往上流的数据一直是假的，直到最后才接触真实底层数据，可能到最后一天才发现真实数据远比理想复杂。
    * > 来源: P18
* **Bottom-up（自底向上）**
    * 先把底层模块分堆测好（每个底层都要写 driver），再用真实模块替代 driver、继续写上层的 driver，一层层往上走，最后测顶端。
    * 优点：底层都是真实数据往上传，且不用写难写的 stub。
    * 缺点：最高层的控制模块最后才测到，若最后发现它错，下面可能全白干。
    * 实践中很少极端只用一种，一般综合使用。
    * > 来源: P18
* **Sandwich testing（三明治测试）**
    * 一部分人从上往下测，一部分人从下往上测，在中间某层汇合，因「三明治」夹心结构而得名。
    * > 来源: P18
* **Regression testing（回归测试）**
    * > 定义：已测过一遍、发现 bug 并改完后，把「改动可能影响的模块」中虽已 pass 但仍相关的旧 case 重新跑一遍。
    * 不是全部重跑（太耗钱耗时），而是挑重要、相关的重测。
    * 反面教材：某电话局系统升级后回归测试没做全，把加州州内的 local 通话误按长途出账单，用户被 local 与 long distance 公司两头踢皮球。
    * > 来源: P18
* **Smoke testing（冒烟测试）**
    * 名字来自硬件测试：新零件插上板子一插就冒烟，多半是新零件坏了。
    * 软件里「板子」叫一个 **build**——一个已测过的集合，含源代码、数据库等相关东西；每天把不同 component 往 build 里插，加一个就全跑一遍，跑不通通常就是新加的有问题。
    * 关键是巧妙划分 build 的大小，不能把整个软件当成一个 build；常用于 time-critical（时间紧）的项目。
    * > 来源: P18
* **通用测试准则（Test Criteria）**
    * 无论何种策略都要考虑：接口完整性（interface integrity）、功能正确性、局部与全局数据结构定义正确（local/global data structure）、性能（performance）。
    * > 来源: P18

### 4.4 系统测试的类型

* **系统测试（System Testing）总定位**
    * 在真实大环境下做，常见 recovery、security、stress、performance 四类。
    * > 来源: P18
* **Recovery testing（恢复测试）**
    * 测系统崩溃后能否恢复、恢复程度。
    * 实例：1995 年学校主办 ACM-ICPC 亚洲区赛，赛前必做 recovery testing——怕比赛中系统崩溃，需立刻切到备用系统且不丢任何 submission；现场一百多台机器每台装机器人狂交，服务器冲垮后启动备用系统做数据迁移，结果折腾到快半夜 12 点才成。
    * > 来源: P18
* **Security testing（安全测试）**：试各种黑客攻击，验防御能力。
* **Stress testing（压力测试）**
    * 常与 recovery testing 合做，回答「系统能承受多大冲击量、最大冲击量是多少」。
    * 如机器人一起攻时看服务器到什么程度挂掉，据此算出门禁（如一秒提交不超过多少次）以防挂掉。
    * > 来源: P18
* **Performance testing（性能测试）**：测效率。

## 5. 面向对象架构的测试挑战

> **一句话主旨**：OO 把系统看成对象及其相互作用，单元变成类、集成要覆盖对象关系，确认测试分 Alpha 与 Beta 两种。

### 5.1 OO 的单元与集成测试

* **单元测试 = 测一个类（Class）**
    * OO 里一个 class 就是一个 unit / component，但测一个 class 与测一个功能模块复杂度不在一个量级。
    * 一个 class 干很多事、像个小软件：即使每个功能单独正确，也不代表 class 实现正确。
    * 测 class 不只测 operations，更要依据它的**状态行为（state behavior）**测：每个 class/object 在系统运行中处于哪几个状态、由哪些动作触发迁移，这些才是测点。
    * > 来源: P17, P18
* **集成测试尤其复杂**
    * 要把 class 与 class 之间的关系尽可能覆盖清楚；想做完全测试、穷举所有排列组合会「测死」，根本测不完，必须在有限时间内用技巧抓住主要关系。
    * OO 集成的三类策略：
        * **Thread-based testing（基于线索）**：给一个输入，各对象协作、做一系列动作、给出输出，从输入到输出加中间动作就是一条 thread（即一个 use case），一条线一条线测。
        * **Use-based testing（基于使用）**：类似自底向上，先测基本不调用别人、只被别人调用的独立 class，再测上层 class，一圈圈往外扩。
        * **Cluster testing（基于簇）**：拎一张 CRC card，它链接到其他卡片，把所有相关卡片抓出来成一坨 cluster，论「堆」测它们之间的 collaboration（协作者）。
    * > 来源: P17, P18

### 5.2 确认测试：Alpha testing 与 Beta testing

* **确认测试（Validation Testing）的依据与检查项**
    * 依据需求规格的 validation criteria，用 use case、状态行为、事件流图（event flow diagram）跑一遍。
    * 同时检查配置（configuration：文档、数据库等）是否配齐。
    * > 来源: P18
* **Alpha testing 与 Beta testing**
    * **Alpha testing**：把 TA 叫到你这儿，但不许 TA 碰机器，你操作给他看、讲解功能，他在后面看、问「可不可以」。
    * **Beta testing**：你靠边站，TA 坐下来自己用，你在后面看但不能拦；如同游戏放出 beta 版放到网上，玩家怎么动你管不着。
    * 两种都要有文档员在旁记录 **deficiency list（错误清单）**。
    * > 来源: P18

## 6. 测试团队的组织、终止与量化计划

> **一句话主旨**：厘清开发者与独立测试组的职责合作，明确测试只在时间或预算耗尽时停止，并把目标量化进测试计划。

### 6.1 测试团队的组织与三个误区

* **参与测试的两类人**
    * **开发者自测**：优点是对内部结构极清楚，不花时间理解就能针对性快速设计用例；缺点是程序员一旦 submit 就默认「我测过了、没问题」，且测试不过要改、超 deadline 扣奖金，受利益驱使不太会严格测自己的东西。
    * **独立测试组（ITG，Independent Test Group）**：缺点是多花时间、多花钱（付人家工时）；因其 independent，利益与开发者对立，若「抓到多少 bug 给多少奖金」便会全力找 bug，质量保障效果更好。
    * > 来源: P17
* **盲点与结对编程（pair programming）**
    * 每个人都有盲点，自己死活看不出的错换个人一眼就见。
    * 建议找另一个人结对编程一起查：两人坐一起，写的人讲「这块在干什么」，共同往下看；两人盲点完全重合的概率很小。
    * > 来源: P17
* **三个必须避免的误区**
    * 误区一「Developer should do no testing at all」：错。起码前期的单元测试和初期集成开发者必须参与，进入集成阶段 ITG 进来后双方密切合作，到系统测试才逐步由 ITG 接手。
    * 误区二「Software 可以 tossed over the wall（丢过墙就不管）」：错。发现错误仍要开发者来改，不能 submit 后就撒手。
    * 误区三「Testers are not involved until it is time to be tested」：错。测试团队从需求分析（Analysis）阶段就该旁观，拿到设计（Design）即可针对设计做测试计划。
    * > 来源: P17

### 6.2 测试的终止、量化目标与计划要素

* **测试的终止条件**
    * 理想主义答案：**Never（永远没头）**——充分复杂的系统穷尽测试（exhaustive testing）不可能，既然不能穷尽，就永远不敢说软件里没有 bug。
    * 现实角度：**When you run out of time, or you run out of money**——没时间或没钱就不测了。
    * 测试只是发现错误的过程，永远不能证明软件没有错误。
    * > 来源: P17
* **以可量化的方式（quantifiable manner）定义目标**
    * 原则：*Specify product requirements in a quantifiable manner before testing starts.*
    * 需求规格里的验收标准尽可能量化成一系列指标，达到指标即如何；测试过程本身也要量化。
    * 量化「测试完成 90%」的方法不唯一，例如一家日本公司根据经验预先**植入 N 个错误**，若植入错误 90% 被找到，就说测试完成了 90%；这办法成本高、也有风险（植入错误是否「干净」、会不会影响软件未必有把握）。
    * > 来源: P17
* **测试计划五要素**
    * **明确测试目标（testing objectives）**：要测什么逐个写清，如测可用性就列清包含哪几个功能，测性能就列清是哪几个点、测到什么指标。
    * **识别用户类别与画像**：用户群分几类，每类写 profile，目的是测试时模拟用户习惯去用软件。
    * **快速迭代（rapid cycle）**：采用「功能加进来就测一下」的递增、迭代式流程，而非一次性想测完整再总结。
    * **构建可自测的健壮软件（Build robust software that is designed to test itself）**：软件设计时考虑各种异常、自带异常处理、抛出有用异常信息。
    * **用正式评审作过滤器（formal reviews as a filter）**：正式跑代码前，先让开发者讲一遍程序怎么走、几个分支怎么走，一帮人听，相当于在抽象层面过滤掉大部分关键错误。
    * > 来源: P17

## 7. 调试过程与技巧

> **一句话主旨**：调试是在测试报错后猜测、验证、改正并回归的过程，含暴力、回溯、归纳、演绎四类技巧与三条改错注意。

* **调试过程（art of debugging）**
    * 执行 test case → 发现错误 → 猜测原因 → 加 additional tests 验证的确是这里错 → 改过来 → 做一定回归测试。
    * > 来源: P18
* **四类调试技巧**
    * **Brute Force（暴力法）**：最老派程序员用 **memory dump**——把出错瞬间内存全部以八进制打印出来读找错误；年轻一辈最多用 spy points（观察点）。
    * **Backtracking（回溯法）**：程序不大时在中间插断点看数据对错——此处已错则错误在上面，此处对则错误在下面，可理解为二分过程。
    * **Induction（归纳法）**：如微软实习生每天领表做测试填对错，不对时填一张 **3W1H** 表描述现象——What（有什么/没什么）、Where（在哪有/在哪没有）、When（何时发生/何时没发生）、How，交给程序员据现象分析可能原因。
    * **Deduction（演绎法）**：像侦探，先列一堆嫌疑人，调查中一个个排除，最后剩下真正的 cause。
    * > 来源: P18
* **改 bug 的三点注意（Bug removal considerations）**
    * 产生这个 bug 的原因在程序其他地方是否也出现。
    * 把错误改过来以后，下一个 bug 可能是什么。
    * 总结经验教训：为什么会犯这种错、怎么才能不重复犯。
    * > 来源: P18

## 8. 好测试的评判基准

> **一句话主旨**：用覆盖全面、有代表性无冗余、代价最小三条基准判断一套测试用例的强弱，弱测试会拖垮系统。

* **好测试的三条准则**
    * **覆盖全面**：被测模块该有的性质都要被 case 触达。
    * **有代表性、无冗余**：每个 case 要有充分代表性，不能互相重复。
    * **代价最小**：用最少的时间和精力达到最好效果；软件测试是工程，要有代价意识，不能不计成本只求完美。
    * 弱测试要么覆盖不全，要么用几十个冗余 case 把系统拖垮（如 PAT 每 case 开虚拟空间，case 太多系统会挂）。
    * 出题最花时间、技术含量最高处不在想 idea，而在 **test case 的设计**。
    * > 来源: P19

## 9. 可测试性的七个能力

> **一句话主旨**：可测试性由操作、观察、控制、分解、简单、稳定、理解七个 ability 组成，衡量软件「好不好测」。

* **可测试性（Testability）**
    * > 定义：它不像 reliability / availability 能套公式算百分比，而由多个 ability 组成，评价软件「好不好测」。
    * **Operability（可操作性）**：软件本身可被操作，操作的方便性直接影响测试难易。
    * **Observability（可观察性）**：运行时能在多大程度看到执行情况，越能看越好测。反例：某系统为版权保护做成完全黑盒子，只有一个接口、一根网线、一个按钮，出错有 N 多处可能却不知内部结构，observability 极低。
    * **Controllability（可控制性）**：测试人员在多大程度能控制软件，如 PAT / ACM 竞赛中裁判直接控制提交代码、写 judge 程序自动跑。
    * **Decomposability（可分解性）**：能在多大程度分块，块越小越好测。
    * **Simplicity（简单性）**：被测软件越简单越好测。
    * **Stability（稳定性）**：开发过程稳定，若刚测完一块需求就变、版本未测完下一个又来，测试无法进行。
    * **Understandability（可理解性）**：设计文档、代码在多大程度可读可理解；test plan 与设计并行，需求有了可出黑盒策略，设计有了可出部分白盒策略。
    * > 来源: P19

## 10. 穷尽测试不可行

> **一句话主旨**：用 $5^{20}$ 约需 3000 多年的例子说明穷尽测试不可能，故只要不是穷尽测试就不能保证软件无 bug。

* **穷尽测试（exhaustive testing）不可行的量化依据**
    * 书上一例：一个程序流程图有 5 个 if-else 分支，其中还有一个循环执行 20 次，每次循环有 5 种走法，覆盖所有可能性需 $5^{20}$，约等于要花 3000 多年才能把这幺小的程序完备测完。
    * 因此必须忽略部分情况、选最有代表性的情况去走，这正是测试技术的价值所在。
    * 结论：**Testing cannot show the absence of errors and defects**——只要不是穷尽测试，就永远不能说「保证软件没有 bug」。
    * > 来源: P19

## 11. 黑盒测试与等价类划分

> **一句话主旨**：黑盒只依据功能规格设计用例，最基础的方法是等价类划分，把输入划成有效与无效两类各取代表。

### 11.1 两类测试技术总览

* **黑盒测试（Black-box testing）**
    * > 定义：程序对你是一个黑盒子，看不到实现细节、看不到代码，只知道 specification（要实现什么功能、输入输出大概什么样）。
    * 用例只能从功能 specification 出发设计。
    * > 来源: P19
* **白盒测试（White-box / Glass-box testing）**
    * > 定义：盒子透明，看得见内部，清楚知道程序流程图，可针对每一条执行路径细测。
    * 不同阶段用不同技术：单元测试多用白盒，集成与系统测试多用黑盒。
    * > 来源: P19

### 11.2 等价类划分的思想与准则

* **等价类划分（equivalence partitioning）**
    * > 定义：把所有可能输入划分为若干等价类，假设同一等价类里任一输入程序处理都类似，每类只挑一个代表做 test case。
    * 依据：一个等价类里其中一个暴露错误，其他大概率也暴露；一个没暴露，其他大概率也不暴露；用最少 case 覆盖最大可能。
    * 它是黑盒技术中最基础、最重要的思想，大量测试都基于它；其他黑盒技术还有边界值分析、错误推测、因果图。
    * > 来源: P19
* **有效等价类与无效等价类**
    * **有效等价类（valid equivalence class）**：符合 specification 的、合理的输入，如输入 1~100 的整数时 5、10、50 属此类。
    * **无效等价类（invalid equivalence class）**：不符合 specification 的、不合理的输入，如小于 1 的数（0、负数）、大于 100 的数（101、1000）、非整数（浮点、字符、空输入）。
    * 程序要在非法输入下能合理处理——不崩溃、给出合理错误提示，故无效等价类在安全测试、健壮性测试中往往更重要。
    * > 易错点：只测有效等价类，合法输入都过了就以为程序没问题。
    * > 来源: P19

    | 输入条件类型 | 有效等价类 | 无效等价类 |
    | :--- | :--- | :--- |
    | 规定取值范围（如 1~100） | 1~100 之间的数（1 个） | 小于 1（1 个）、大于 100（1 个） |
    | 规定个数（如 1~3 个参数） | 1~3 个参数（1 个） | 0 个、4 个及以上 |
    | 规定值的集合（如红/黄/蓝之一） | 红、黄、蓝（各 1 个） | 不属于集合的值（绿、黑等） |
    | 规定布尔量 | true（1 个）、false（1 个） | 非布尔值 |

### 11.3 等价类用例设计步骤

* **三步设计流程**
    * 给每个等价类规定唯一编号（1, 2, 3, …）。
    * 设计新 case，尽可能多地覆盖尚未覆盖的有效等价类，直到所有有效等价类都被覆盖（有效类希望一个 case 多覆盖几个，减少 case 数）。
    * 对每个无效等价类单独设计一个 case，一次只覆盖一个未覆盖的无效等价类。
    * > 来源: P19
* **无效类「一次只测一个」的原因**
    * 若一个 case 含多个无效输入，可能被第一个无效输入拦截，后面的错误被掩盖、测不到后续无效处理。
    * > 来源: P19

## 12. 边界值分析与其他黑盒技术

> **一句话主旨**：错误多藏在边界上，边界值分析围绕取值范围端点及两侧邻点取 case，并辅以错误推测与因果图。

### 12.1 边界值分析

* **边界值分析（boundary value analysis）**
    * > 定义：大量经验表明，程序出错往往不在规矩的中间值，而在边界上，如 `>=` 写成 `>`、off-by-one error（循环多/少一次）。
    * 选 case 要特别关注：边界上取一个、刚越过边界取一个、刚进入边界取一个。
    * 教材边界准则：若取值范围是 A 到 B，则 case 必须包含 A、B，以及紧贴两侧的「刚好大于 A」「刚好小于 A」「刚好大于 B」「刚好小于 B」。
    * > 来源: P19, P20
* **溢出教训（实例）**
    * 三位老师组队参加校赛，不到十行的小程序一提交却 Wrong Answer；取边界最大值一跑，程序崩溃——答案超出长整型（long long 溢出）。
    * 结论：bug 喜欢躲在墙角，边角最易出错。
    * > 来源: P20

### 12.2 错误推测与因果图

* **错误推测（error guessing）**
    * 凭经验直觉，针对程序员易错处专门设计 case。
    * > 来源: P19
* **因果图**
    * 从输入（因）与输出（果）之间的逻辑关系出发设计用例，具体展开未说明。
    * > 来源: P19

## 13. 白盒测试：独立路径与环形复杂度

> **一句话主旨**：白盒针对小段代码追求逻辑覆盖，用流图标出独立路径，并以环形复杂度给出覆盖所需用例数的上界。

### 13.1 白盒的定位与独立路径

* **白盒的定位与四个必答问题**
    * 白盒（Glass-box）看得见程序内部、清楚流程图，所以只能是 **testing in the small**——针对小段代码。
    * 重点：关注每一个 path，追求尽可能好的**逻辑覆盖（logic coverage）**。
    * 设计时要回答四个问题：
        * 所有独立路径是否至少执行一遍？（Can you guarantee that all independent paths within a module will be executed at least once?）
        * 所有逻辑判断的 true 与 false 分支是否都走到？
        * 所有循环是否在其边界与运行范围内执行？
        * 内部数据结构是否有效？
    * > 来源: P19
* **独立路径（Independent Path）**
    * > 定义：类比线性代数的线性无关向量——一个独立路径不可能由其他路径组合出来，它至少有一条边是别人没覆盖的。
    * 最低要求：设计的 case 走一遍时所有独立路径至少被执行一次，即图里每条边至少被走一遍（很弱的要求）。
    * > 来源: P19

### 13.2 流图与环形复杂度

* **流图与复合条件**
    * 最弱覆盖是 execute every statement at least once（每条语句至少执行一次），做法是把顺序执行语句缩成一个节点、编号，简化成平面有向图（flow graph）。
    * 判断节点处理：复合条件（如 `total < 1000 && A != 0` 含 AND）实际包含两次判断，最好拆成两个节点、把边细化——compound conditions 要拆开。
    * > 来源: P19
* **环形复杂度（Cyclomatic Complexity, CC）**
    * > 定义：图论里有三个等价定义——平面图被切成连通域（region）的个数；边数 − 节点数 + 2（$E - V + 2$）；谓词节点数 + 1（$P + 1$，谓词节点即出去箭头不止一个的分支节点）。
    * 三者可证相等；某图有 3 个分支点则 $P+1 = 4$，平面也被切成 4 个连通域，CC = 4。
    * CC 与分支节点个数成正比，代表程序中独立路径的条数，并给出测试 case 数的上界（upper bound）：CC = 4 时最多只需设计 4 个 case，就一定能做到每条语句至少执行一次。
    * 另一例：含复合条件需拆成两个节点后再画图，算得 CC = 5，即最多需 5 个 case。
    * > 来源: P19

## 14. 逻辑覆盖

> **一句话主旨**：从最弱的语句覆盖讲到条件覆盖，复合条件按「分支组合 → 细化 T/F → 翻译回表达式」逐层展开。

### 14.1 从语句覆盖到条件覆盖

* **语句覆盖（statement coverage）**
    * 目标：每条语句至少执行一次，是最弱的逻辑覆盖。
    * 以 CC = 5 的程序为例，实际只需 1 个 case 就能从头走到尾，例如输入 A = 3, B = 0, X = 4/3（且 X > 1）。
    * > 易错点：把程序里的 `AND` 错写成 `OR`，该 case 仍「正确」、错误查不出；原因是还有分支没测到。
    * 更强覆盖应是 execution of each path（每条路径执行），而非 each statement。
    * > 来源: P19
* **条件覆盖（condition testing）**
    * > 定义：每个条件（condition）的 True 与 False 都至少测到一次（test every condition at least once）。
    * 条件常是复合的，需系统化、不遗漏地设计用例。
    * > 来源: P20

### 14.2 复合条件的展开步骤

* **复合条件 `B1 AND B2` 的三步展开**
    * 第一步（分支层，最少 3 个 case）：把 B1、B2 当作整体，取三种组合，使整句有 T 有 F、B1 有 T 有 F、B2 有 T 有 F。
    * 第二步（细化 T/F 含义，展开到 4 个 case）：`T` 意味着「两者相等」，`F` 意味着「不相等」，不相等再分 `<` 与 `>` 两个子 case。
    * 第三步（翻译回具体表达式，得 5 个 case）：将 B1 换成具体比较 `E1 > E2`，则 B1 的 T 翻译为 `>`，B1 的 F 翻译为一个 `<`、一个 `=`。
    * 诀窍：先按分支组合、再逐层把 T/F 翻译成具体关系值。
    * > 来源: P20

    | case | B1 | B2 | 整句 |
    | :--- | :--- | :--- | :--- |
    | 1 | T | T | T |
    | 2 | F | T | F |
    | 3 | T | F | F |

* **只取两种极端的错误**
    * 只取（T,T）与（F,F）会漏掉「一个 F 一个 T」的组合，无法保证 B1、B2 各自都取到 T 与 F。
    * > 来源: P20

## 15. 数据流测试

> **一句话主旨**：数据流测试不看路径本身，而以变量的定义-使用链为单位，要求每条 du-chain 至少覆盖一次。

* **数据流测试（Data Flow Testing）**
    * > 定义：关注的不是路径本身，而是一个变量在程序里取值的变化过程。
    * 对程序语句做拆解：
        * **DEF of S**：语句 S 中在这句话里被定义（赋初值、被给值）的所有变量。
        * **USE of S**：语句 S 用到了哪些变量的值（未改变，只读取）。
        * **du-chain（定义-使用链）**：对每个变量，顺着执行顺序找它的链——上面的定义在中间未被改变、到下面某语句被使用。
    * 测试目标：**every du-chain covered once**（每条 du-chain 至少覆盖一次），以 du-chain 为单位逐链去测。
    * > 来源: P20

## 16. 循环测试

> **一句话主旨**：循环是易错点，按简单、嵌套、串接三种形态分别取边界次数，简单循环须覆盖 0 到 n+1 次。

* **Simple loop（简单循环，1 到 n）**
    * 至少覆盖以下边界与邻近点：0 次（直接跳过，看非法循环是否发生）、1 次、2 次、n-1 次、n 次（边界）、n+1 次（越界会怎样），再取一个中间值随便跑一下。
    * 这里的 n 由输入规模决定（例如输入 size 可能是 1 也可能是 100，则 1 和 100 都要测）。
    * > 来源: P20
* **Nested loops（嵌套循环）**
    * 技巧：先让外循环不执行或只执行一次，把内循环测完备；内循环测完当作已测过的模块不再管它，再用普通策略测外循环。
    * > 来源: P20
* **Concatenated loops（串接循环）**：没什么特殊，顺着往下逐环测即可。

## 17. 面向对象测试方法

> **一句话主旨**：OO 的一个 test case 是一组动作而非一组数据，测试方法围绕类层次、场景、分类与类间交互展开。

* **OO test case 的结构：从 IPO 到「一组动作」**
    * 传统测试把软件看成 input-process-output（IPO），给一组输入、检查输出即可。
    * OO 一个 test case 不是一组数据输入，而是一组动作的执行过程（a list of testing steps）；*OO testing focuses on designing appropriate sequences of operations to exercise the states of a class*。
    * 一个 OO test case 通常包含：唯一 ID / 名字、要测的 class 名、测试目的、测试步骤清单、覆盖了哪些 state、执行了哪些 message / operation（方法）、外部准备条件、若用到其他 class 它们如何配合。
    * > 来源: P20
* **Fault-based testing（基于故障）**
    * 资深老测试员有一套针对「软件最常出错处」预制的 case，闭眼执行一遍全过，绝大多数问题就没了；思路是先想软件所有易错点，针对它们设计 case。
    * > 来源: P20
* **Class testing 与 class hierarchy（类与类层次）**
    * OO 有继承（inheritance），编程时易扩展、易裁剪，测试时却麻烦：测完父类不等于父类功能不用测（子类会「变」），测完所有子类也不等于父类不用测。
    * > 来源: P20
* **Scenario-based（基于场景）**
    * 拿 use case 逐个走，关注用户使用过程是否正常，不关注内部逻辑执行；但用户过程正常不代表内部逻辑没错，不同角度最好结合用。
    * > 来源: P20
* **Random testing（随机测试）**：先定最小必测集合，其余做随机组合「瞎猫碰死耗子」，不够好。
* **Partition testing（分类测试）**
    * 本质同传统等价类划分，但等价类定义方式不同：
        * *state-based*：把让 class 在状态间迁移的功能归一类。
        * *attribute-based*：把集中修改某一内部 attribute 的所有 operation 归一类。
        * *category-based*：按 class 要完成的几大功能把相关操作绑一起。
    * > 来源: P20
* **Inter-class testing（类间测试）**
    * 把 class 理解为 client-server 关系，测试它们之间交互的 message / operator 以及 collaborator class 的配合。
    * 基本原理：先划分 client 与 server，再测交互；多基于 random，无特别好办法。
    * > 来源: P20
* **State-transition-diagram based（基于状态转换图）**
    * 若行为状态图清楚，就沿图设计 case——每个动作（箭头）都要做一下，动作可排列组合（什么都不做直接跳到下一动作，或走两步再结束等）。
    * > 来源: P20
* **补充方向与收尾结论**
    * 此外还有 GUI 测试、client-server 测试；实时系统里 performance 测试很重要。
    * 建议测试中发现规律就抽象出 **testing patterns** 以便复用。
    * 结论：**testing never ends**——活交出去后测试只是从你手里交到客户手里，他替你继续测。
    * > 来源: P20

## 18. 实战：PAT 二分查找裁判用例设计

> **一句话主旨**：以二分查找题为例，用不超过 10 个、越少越好的用例覆盖错误点，示范等价类划分与边界值分析的综合运用。

* **题目与设计规则**
    * 题目：在一串整数中查找给定整数。第一行正整数 $N$（$N \le 10^5$）；第二行 $N$ 个整数（均可用 int、不超长整型），按从小到大**非减序**（允许重复）；第三行待查整数 $X$；$X$ 在序列中回答 `YES`，否则 `NO`。
    * 总 case 不超过 10 个，越少越好；目标是于最少 case 覆盖最多错误点。
    * **Sample 占 10 分（总分 20）**：sample 须包含一组 `YES` 与一组 `NO`，过了至少得一半分；其余 10 分分布给其他 case，每个 case 写明「测哪个点、占几分」。
    * > 来源: P20
* **示例用例设计**

    | case | 输入要点 | 测试目的 | 期望输出 | 分值 |
    | :--- | :--- | :--- | :--- | :--- |
    | sample-1 | 小 N、X 存在 | 基本命中（YES 样例） | YES | 5（sample） |
    | sample-2 | 小 N、X 不存在 | 基本未命中（NO 样例） | NO | 5（sample） |
    | 3 | $N = 1$ | 最小规模、单元素边界 | 视 X | 2 |
    | 4 | $N = 10^5$ | 最大规模、线性查找会被卡（逼二分） | 视 X | 2 |
    | 5 | 含大量重复值、X 为重复值 | 非严格递增、重复边界 | YES | 2 |
    | 6 | X 恰为序列首元素 | 左边界 | YES | 1 |
    | 7 | X 恰为序列末元素 | 右边界 | YES | 1 |
    | 8 | X 小于最小元素 | 下溢边界 | NO | 1 |
    | 9 | X 大于最大元素 | 上溢边界 | NO | 1 |

* **设计要点**
    * 用 sample 保证基本功能（10 分）。
    * 用 $N=1$ 与 $N=10^5$ 卡住「不用二分查找（线性扫描）必超时」的实现。
    * 用重复值验证「非减序」假设，用首尾与越界值覆盖边界。
    * 更难的题还需写 generator 生成大数据。
    * > 来源: P20
