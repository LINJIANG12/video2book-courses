# 第18讲 测试策略（二）：驱动/桩、集成策略与系统级测试

## 一、单元测试的机制：Driver 与 Stub

单元测试（Unit Testing）把一个 module 拿过来，喂入一堆 test cases，产出 bug 清单与结果。一个 test case 必须有明确的**测试目的（testing purpose）**——要测哪一块，这要在正式技术评审（formal technical review）环节核查，以提升后续效率。单元测试要覆盖的方面包括：接口（interface）、数据结构（data structures）、边界条件（boundary conditions）、独立路径（independent paths）、错误处理路径（error-handling paths）。

为了让"被测模块"能独立运行并被评判，需要两种配套程序，这也是单元测试真正的工作量所在。

### 1.1 Driver（驱动）

Driver 相当于在线评测系统（如 ZOJ、PAT）里的 judge 程序：你只提交一个 module / 一个函数，main 函数由 driver 来写。它的职责是接收所有 test cases，调用被测模块、把模块产生的结果打印出来并检查。一个 driver 的典型模板是：

```
读入 inputs
循环：
    读入一个 test case
    调用被测模块（把 test case 喂进去）
    输出结果
```

若在数值分析类课程中，老师写 driver、学生只交内部一个函数，就是这种关系。

### 1.2 Stub（桩）

麻烦在于：被测模块内部往往还会调用下层 sub-module。一旦结果出错，你无法判断是"被测模块自己错了"还是"它调用的 sub-module 错了"。为隔离错误来源，需要写 **stub**——一个接口与原 sub-module 完全相同的"假模块"，内容是个空壳，只做一件事：按预先知道的正确值返回。

做法类似 switch-case：你事先知道有哪些 test case，也知道每个 case 下 sub-module 若正确应当返回什么值；于是在 stub 里判断"进来的 data 等于某值，就直接返回那个正确值"，不做任何真实计算。这样，所有下层调用都返回正确值，若 driver 最终结果仍不对，**只能是被测模块自身的问题，而非 sub-module 引起**。

```
stub(case):
    switch(case):
        case A: return 正确值_A
        case B: return 正确值_B
        ...
```

若模块复杂、调用很多底层模块，就要为每个底层模块写对应 stub、针对每个 case 返回正确值——这是实打实的工作量。于是引出策略选择：**自顶向下测要写很多 stub，自底向上测要写很多 driver**，两种方式都有成本。

## 二、集成测试：从 big-bang 到三明治

### 2.1 Big-bang 的混乱

最省事的策略叫 **big-bang testing**：每个模块分头测完，最后一次性合到一起测。本门课期末验收近似这种——五个组分别验收都"对"，然后 72 小时内拼成系统统一测。但真敢全程 big-bang，必定悲剧。

原因是 **isolation of causes is complicated（原因隔离复杂）**：最后啪一下合起来发现系统不正常，却说不清是谁的错，几个人互相 finger-pointing（甩锅）："这肯定是他的""我都测过了"。一个真实前车之鉴是当年数据结构大作业——让三人各负责一个模块，合起来做一个最小生成树程序（涉及最小堆取最便宜边、Union-Find 并查集判环、维护图结构）。每个人都号称自己那块是好的，凑一起却各种乱，最后一分钟没人搞定。集成测试就是这么"讨厌"。

### 2.2 Top-down（自顶向下）

从最顶端控制模块开始测，先写 stub 返回假数据，再用真实模块一层层往下替代，直到测到底层。

- **优点**：**major control / decision points 最早被测到**。关键控制模块若方向错，底下员工再努力也错得越厉害——大方向先测对；
- **缺点**：从下往上流的数据一直都是假的，直到最后才接触真实底层数据；而真实数据可能远比理想复杂，可能到最后一天才发现"下面数据原来如此复杂"。

### 2.3 Bottom-up（自底向上）

先把底层模块分堆测好（每个底层都要写 driver），再用真实模块替代 driver、继续写上层的 driver，一层往上走，最后测顶端。

- **优点缺点与 top-down 正好相反**：底层都是真实数据往上传，且不用写难写的 stub；但最高层的控制模块最后才测到，若最后发现它错，下面可能全白干。

实践中很少极端只用一种，一般综合使用。

### 2.4 Sandwich testing（三明治测试）

一部分人从上往下测，一部分人从下往上测，在中间某层汇合。因"三明治"是夹心结构而得名。

### 2.5 Regression testing（回归测试）

已测过一遍、发现 bug 并改完后，不只测改的那块，而要把"改动可能影响的模块"中那些**虽已 pass 但仍相关的旧 case 重新跑一遍**——不是全部重跑（太耗钱耗时），而是挑重要、相关的重测。

反面教材：某电话局系统升级后没做完整回归测试，区号搞错。美国各州有区号（如杭州 0571、上海 021），跨区一般算长途（long distance），转给长途公司出账单；但加州很大、州内就有多个区号，州内互打应算 local。local 公司升级时把逻辑搞错，把加州州内的 local 通话按长途账单出了。用户拿着长途账单去找 local 公司，local 推给 long distance，long distance 查完说"是你们 local 的错"，用户被两头踢皮球。根因就是升级后回归测试没做全——不可能做完全回归，但重要的回归没做就会出这种事。

### 2.6 Smoke testing（冒烟测试）

名字来自硬件测试：把新零件往板子上插，若一插"砰"地冒烟炸了短路，说明多半是新零件坏了。软件里"板子"叫一个 **build**——一个已测过的集合，含源代码、数据库等相关东西。每天把不同 component 往 build 里插，加一个就全部运行一遍；哪个 component 加进去后整体跑不通，通常就是新加的有问题。每天把各 build 测好再集成。关键是**巧妙划分 build 的大小**（不能把整个软件当一个 build，否则每天测太费劲），常用于 time-critical（时间紧）的项目。

### 2.7 通用测试准则（Test Criteria）

无论何种策略，都要考虑：接口完整性（interface integrity）、功能正确性、局部与全局数据结构定义正确（local/global data structure）、性能（performance）。教材另有两页专门讲如何写 test specification（即下次要交的报告），需细看。

## 三、面向对象测试的复杂性

### 3.1 单元 = 类，基于状态行为

OO 里 unit 相当于一个 class。但普通 module 基本完成一个功能、测功能正确即可；一个 class 是对象，干很多事，像个小软件——即使每个功能单独正确，也不代表 class 实现正确。所以测 class 不只是测 operations，更要依据它的**状态行为（state behavior）**测：回忆状态转换图，每个 class/object 在系统运行中处于哪几个状态、由哪些动作触发迁移，这些才是测点。它基于状态行为而非数据流图。

### 3.2 集成的三类策略

- **Thread-based testing（基于线索）**：给一个输入，系统各对象开始协作、做一系列动作、给出输出，从输入到输出加中间动作就是一条 thread（即一个 use case）。一条线一条线测过来，保证 thread 中每个 object 表现正确；
- **Use-based testing（基于使用）**：类似自底向上。先找那些基本不调用别人、只被别人调用的独立 class 测好，再测用它的上层 class，一圈圈往外扩；
- **Cluster testing（基于簇）**：回忆 CRC cards，重点是第二个 C——collaborators（协作者）。拎一张卡片，它链接到其他卡片，把所有相关卡片抓出来就是一坨 cluster，论"堆"测它们之间的 collaboration。

### 3.3 确认测试（Validation Testing）

依据需求规格的 validation criteria，用 use case、状态行为、事件流图（event flow diagram）跑一遍；同时检查配置（configuration：文档、数据库等）是否配齐。分两种：

- **Alpha testing**：把 TA 叫到你这儿，但**不许 TA 碰机器**，你操作给他看、讲解功能，他在后面看、问"可不可以"；
- **Beta testing**：你靠边站，**TA 坐下来自己用**，你在后面看但不能拦（"这地方你不能碰！"不行）。如同游戏放出 beta 版放到网上，玩家怎么动你管不着。

两种都要有文档员在旁记录 **deficiency list（错误清单）**。

## 四、系统测试的类型

系统测试（System Testing）在真实大环境下做，常见几类：

- **Recovery testing（恢复测试）**：测系统崩溃后能否恢复、恢复程度。实例：1995 年学校主办 ACM-ICPC 亚洲区赛，赛前必做 recovery testing——怕比赛中系统崩溃，需立刻切到备用系统且不丢任何 submission。总裁苟同学（吴家植）亲自做备用系统，现场一百多台机器每台装机器人，一声令下狂交，服务器冲垮后启动备用系统做数据迁移。结果折腾到快半夜 12 点才成：他笔记本上 Linux 一点问题没有，赛场服务器 Linux 版本差了一点，就死不对。这就是 recovery testing；
- **Security testing（安全测试）**：试各种黑客攻击，验防御能力；
- **Stress testing（压力测试）**：常与 recovery testing 合做，回答"系统能承受多大冲击量、最大冲击量是多少"。如机器人一起攻时看服务器到什么程度挂掉，据此算出门禁（如一秒提交不超过多少次）以防挂掉；
- **Performance testing（性能测试）**：测效率。

## 五、调试的艺术（Debugging）

### 5.1 调试过程

执行 test case → 发现错误 → 猜测原因 → 加 additional tests 验证的确是这里错 → 改过来 → 做一定回归测试。调试被称为 "art of debugging"（调试的艺术）。

### 5.2 调试技巧

- **Brute Force（暴力法）**：最老派程序员用 **memory dump**——把出错瞬间内存全部以八进制打印出来，从里面读找错误；年轻一辈最多用 spy points（观察点）；
- **Backtracking（回溯法）**：程序不大时，在中间插断点看数据对错——若此处已错，错误在上面；若此处对，错误在下面。可理解为二分过程；
- **Induction（归纳法）**：如微软实习生每天领表做测试、填对错，不对时填一张 **3W1H** 表描述现象——What（有什么 / 没什么）、Where（在哪有 / 在哪没有）、When（何时发生 / 何时没发生）、How。把表交给程序员，由他据现象分析可能原因；
- **Deduction（演绎法）**：像侦探，先列一堆嫌疑人，调查中一个个排除，最后剩下真正的 cause。

### 5.3 改 bug 的三点注意（Bug removal considerations）

1. 你产生这个 bug 的原因，**在程序其他地方是否也出现**？会不会别处有类似错；
2. 把错误改过来以后，**下一个 bug 可能是什么**；
3. 总结**经验教训**：为什么会犯这种错、怎么才能不重复犯。

## 六、随堂自测

**题 1：** 单元测试里 driver 与 stub 分别解决什么问题？为什么"被测模块调用下层 sub-module"时必须写 stub？

> **解析与答案：** driver 负责接收 test cases、调用被测模块并输出结果，让只提交一个函数的模块能运行；stub 是接口相同、只返回正确值的假 sub-module。因为被测模块内部会调用下层 sub-module，一旦结果出错无法判断是模块自身还是 sub-module 之错，写 stub 让所有下层调用都返回正确值，从而把错误隔离到被测模块本身。依据见第一节。

**题 2：** 回归测试（regression testing）为什么不能把"所有旧 case 全重跑"？电话局案例说明了什么后果？

> **解析与答案：** 全部重跑太耗钱耗时，故只挑重要、相关的旧 case 重测。电话局升级后回归没做全，把加州州内 local 通话误按长途出账单，用户被 local 与 long distance 公司互相踢皮球——说明重要回归遗漏会直接造成计费错误与用户体验灾难。依据见第二节 2.5。

**题 3：** Alpha testing 与 beta testing 在操作权限上的根本区别是什么？调试技巧中的 backtracking 如何理解？

> **解析与答案：** alpha 中 TA 不碰机器、由开发者操作演示给他看；beta 中 TA 自己用、开发者不能干预。backtracking 是在程序中间插断点：若断点处数据已错，错误在上方；若正确，错误在下方，相当于二分定位。依据见第三节 3.3 与第五节 5.2。
