# 第19讲 测试方法（一）：测试审美、黑盒等价类与白盒路径覆盖

## 一、什么是好的测试：先立审美观

讲具体战术前，先建立"什么是好测试"的审美观。出题（设计题目）最花时间、技术含量最高的地方不在想一个 idea——知识点那么多，拍脑袋就能编个故事；真正难在 **test case 的设计**。一套 case 被称为"出得好、出得强"，至少要满足三点：

1. **覆盖全面（cover 得比较全面）**：被测模块该有的性质都要被 case 触达；
2. **有代表性、无冗余**：每个 case 要有充分代表性，不能互相重复；
3. **代价最小**：用最少的时间和精力达到最好效果。软件测试是工程，要有代价意识，不能像象牙塔科研那样不计成本只求完美。

这三点就是评判一套测试用例强弱的基准：弱测试要么覆盖不全，要么用几十个冗余 case 把系统拖垮（如 PAT 每 case 开虚拟空间，case 太多系统会挂）。

## 二、两类测试技术总览

常用软件测试分两大类：

- **黑盒测试（Black-box testing）**：程序对你是一个黑盒子，看不到实现细节、看不到代码，只知道 specification（它要实现什么功能、输入输出大概什么样）。用例只能从功能 specification 出发设计；
- **白盒测试（White-box / Glass-box testing）**：盒子透明，看得见内部，清楚知道程序流程图，可针对每一条执行路径细测。

不同阶段用不同技术：单元测试多用白盒，集成与系统测试多用黑盒。

## 三、黑盒测试与等价类划分

### 3.1 等价类划分的思想

黑盒技术里有几大类：等价类划分、边界值分析、错误推测、因果图等。其中**等价类划分（equivalence partitioning）**是最基础、最重要的思想——大量测试都基于它。

输入数据往往有极多种可能（例如 1 到 100 之间就有 100 种可能）。把所有可能输入划分为若干**等价类**：假设同一等价类里任一输入，程序对它的处理都类似——其中一个暴露错误，其他大概率也暴露；一个没暴露，其他大概率也不暴露。于是每类只挑一个代表做 test case，用最少 case 覆盖最大可能。

### 3.2 有效等价类与无效等价类

划分时要分两种：

- **有效等价类（valid equivalence class）**：符合 specification 的、合理的输入。例如输入 1~100 的整数，则 5、10、50 属此类；
- **无效等价类（invalid equivalence class）**：不符合 specification 的、不合理的输入。例如小于 1 的数（0、负数）、大于 100 的数（101、1000）、非整数（浮点、字符、空输入）。

**千万不要只测有效等价类。** 常见毛病是只测合法输入、都过了就以为程序没问题。一个健壮（robust）的程序，不仅要在合法输入下正确工作，还要在非法输入下能合理处理——不崩溃、给出合理错误提示。因此无效等价类同样重要，在安全测试、健壮性测试中往往更重要。

### 3.3 等价类划分准则

| 输入条件类型 | 有效等价类 | 无效等价类 |
| --- | --- | --- |
| 规定取值范围（如 1~100） | 1~100 之间的数（1 个） | 小于 1（1 个）、大于 100（1 个） |
| 规定个数（如 1~3 个参数） | 1~3 个参数（1 个） | 0 个、4 个及以上 |
| 规定值的集合（如红/黄/蓝之一） | 红、黄、蓝（各 1 个） | 不属于集合的值（绿、黑等） |
| 规定布尔量 | true（1 个）、false（1 个） | 非布尔值 |

### 3.4 用例设计步骤

1. 给每个等价类规定唯一编号（1, 2, 3, …）；
2. 设计新 case，**尽可能多地覆盖尚未覆盖的有效等价类**，直到所有有效等价类都被覆盖（有效类希望一个 case 多覆盖几个，减少 case 数）；
3. 对**每个无效等价类**，单独设计一个 case，**一次只覆盖一个**未覆盖的无效等价类。

第三步为何"一次只测一个"？若一个 case 含多个无效输入，可能被第一个无效输入拦截，后面的错误就被掩盖，测不到后续无效处理。无效等价类必须一次一个。

### 3.5 其他黑盒技术预告

- **边界值分析（boundary value analysis）**：大量经验表明，程序出错往往不在规矩的中间值，而在边界上——如 `>=` 写成 `>`，off-by-one error（循环多/少一次）。选 case 要特别关注：边界上取一个、刚越过边界取一个、刚进入边界取一个；
- **错误推测（error guessing）**：凭经验直觉，针对程序员易错处专门设计 case；
- **因果图**：后续详讲。

## 四、可测试性（Testability）：七个 ability

Testability 不像 reliability / availability 能套公式算百分比，它由多个 ability 组成，评价软件"好不好测"：

- **Operability（可操作性）**：软件本身可被操作，操作的方便性直接影响测试难易；
- **Observability（可观察性）**：运行时能在多大程度看到执行情况。越能看，越好测。一个反例：与医学院合作某系统，美方为版权保护做成完全黑盒子——只有一个接口、一根网线、一个按钮，点一下出结果，中间全碰不到。测试团队痛苦：出错有 N 多处可能，却不知内部结构、算法、流程，只知"按按钮出结果"，observability 极低；
- **Controllability（可控制性）**：测试人员在多大程度能控制软件。如 PAT / ACM 竞赛，裁判直接控制提交代码、写 judge 程序自动跑，可控性强；
- **Decomposability（可分解性）**：能在多大程度分块。块越小越好测；
- **Simplicity（简单性）**：被测软件越简单越好测；
- **Stability（稳定性）**：开发过程稳定。若刚测完一块需求就变、设计开发乱改又丢回来，版本未测完下一个又来，所有人抓狂（"让程序员发疯：改三次需求他就疯了"）；
- **Understandability（可理解性）**：设计文档、代码在多大程度可读可理解。Test plan 与设计并行，需求有了黑盒策略可出，设计有了部分白盒策略可出，先充分理解才能测好。

每个指标自身如何量化都是一门学问，这里只列举"有什么"，不展开"怎么做"。

## 五、为何不做穷尽测试

既然 case 设计有技术，为何不直接做穷尽测试？书上一个例子：一个程序流程图有 5 个 if-else 分支，其中还有一个循环执行 20 次。每次循环有 5 种走法，要覆盖所有可能性需：

$$5^{20}$$

约等于要花 **3000 多年**才能把这么小的程序完备测完。一个几行、看似毫不复杂的程序，穷尽测试都不可能，复杂系统更不必想。因此必须忽略部分情况、选最有代表性的情况去走——这正是测试技术的价值所在。**只要不是穷尽测试，就永远不能说"保证软件没有 bug"**（Testing cannot show the absence of errors and defects）。

## 六、白盒测试与路径覆盖

### 6.1 白盒的基本定位

白盒（Glass-box）看得见程序内部、清楚流程图，所以只能是 **testing in the small**——针对小段代码。重点是关注每一个 path，追求尽可能好的**逻辑覆盖（logic coverage）**。设计白盒测试时，脑子里要回答四个问题：

1. **所有独立路径是否至少执行一遍？**（Can you guarantee that all independent paths within a module will be executed at least once?）
2. **所有逻辑判断的 true 与 false 分支是否都走到？**（exercise all logical decisions on their true and false branches）
3. **所有循环是否在其边界与运行范围内执行？**（all loops execute at their boundaries and within their operational bounds）
4. **内部数据结构是否有效？**（exercise internal data structures to ensure their validity）

### 6.2 独立路径（Independent Path）

Independent path 类比线性代数里的**线性无关向量**：无关组里任一向量都不能被其余向量组合出来，总有别人 cover 不到的独特点。独立路径同理——流程图里某些路径可相互组合出第三条；一个独立路径不可能由其他路径组合出来，它至少有一条边是别人没覆盖的。最低要求：设计的 case 走一遍时，所有独立路径至少被执行一次，即图里每条边至少被走一遍（很弱的要求）。

### 6.3 最弱覆盖：语句覆盖与流图

最弱覆盖是 **execute every statement at least once（每条语句至少执行一次）**。做法是把顺序执行语句缩成一个节点、编号，简化成平面有向图（flow graph）。注意判断节点：复合条件（如 `total < 1000 && A != 0` 含 AND）实际包含两次判断，最好拆成两个节点，把边细化——compound conditions 要拆开。

### 6.4 环形复杂度（Cyclomatic Complexity）

做 Basis Path Testing 时要算一个量：**环形复杂度（Cyclomatic Complexity, CC）**。图论里有三个等价定义：

1. 平面图把平面切成的**连通域（region）个数**；
2. **边数 − 节点数 + 2**，即 $E - V + 2$；
3. **$P + 1$**，其中 $P$ 是谓词节点（predicate node，即出去箭头不止一个的**分支节点**）的个数。

三者可证相等。例如某图有 3 个分支点，则 $P+1 = 4$，平面也被切成 4 个连通域，CC = 4。

**CC = 4 告诉我们什么？** 它与分支节点个数成正比，代表程序里**独立路径的条数**，也给出测试 case 数的**上界（upper bound）**：最多只需设计 4 个 case，就一定能做到"execute every statement at least once"、把所有路径走一遍。可以设计得更少。

另一个例子：一段程序含复合条件，需拆成两个节点后再画图，算得 CC = 5，即最多需 5 个 case 即可让每条语句至少执行一次。

### 6.5 覆盖强度演示：语句覆盖远远不够

以 CC = 5 的程序为例，目标"每句话至少执行一次"，实际只需 **1 个 case** 就能从头走到尾。例如设计：

```
输入：A = 3, B = 0, X = 4/3（且 X > 1）
```

程序沿一条路走完，每一语句都被执行，达到了最基本要求。但**覆盖非常弱**——若把程序里的 `AND` 错写成 `OR`，这个 case 仍"正确"，错误查不出来。原因是有分支没测到；只有去走分支（走不同 path），才可能发现写错。因此更强覆盖应是 **execution of each path**，而非 each statement。

## 七、随堂自测

**题 1：** 等价类划分中，为何无效等价类必须"一次只测一个"？有效等价类为何鼓励一个 case 多覆盖？

> **解析与答案：** 无效类一次只测一个，是因为若一个 case 含多个无效输入，会被第一个无效输入拦截，后面的无效处理被掩盖、测不到；有效类鼓励多覆盖是为了用最少 case 覆盖全部有效等价类、减少冗余与代价。依据见第三节 3.4。

**题 2：** 程序环形复杂度 CC = 4 的含义是什么？它给出测试 case 数的上界还是下界？

> **解析与答案：** CC = $P+1$（$P$ 为分支节点数），表示程序中独立路径的条数，并给出"让每条语句至少执行一次"所需测试 case 数的**上界**——最多设计 4 个 case 就一定够。依据见第六节 6.4。

**题 3：** 为什么说"语句覆盖"是最弱的逻辑覆盖？用一个能暴露其缺陷的场景说明。

> **解析与答案：** 语句覆盖只要求每条语句至少执行一次，一个 case 即可走完整段程序；但若程序中把 `AND` 误写为 `OR`，该 case 仍能通过、错误查不出，因为还有分支未走到。只有覆盖每个 path（路径覆盖）才可能发现此类逻辑错。依据见第六节 6.5。
