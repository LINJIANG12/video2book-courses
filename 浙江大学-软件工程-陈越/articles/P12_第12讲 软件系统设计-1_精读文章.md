# 软件系统设计（一）：体系结构风格与架构语境建模

上一讲建立了设计的若干基本概念与原则，其中模块独立性的两个衡量指标必须牢记：**内聚（cohesion）**——模块在多大程度上只做一件事，越强越好；**耦合（coupling）**——两个模块之间的关联程度，越轻（越没关系）越好。本讲进入"怎么干活"的实操层面：设计完成后要给出一个设计模型，而设计模型是如何导出的，重点是**体系结构设计（Creating an Architectural Design）**。

## 一、体系结构设计：要交付什么、为何重要

用建筑打比方最直观：用户提出需求——要四个卧室、三个卫生间、房间多用玻璃和窗；设计师把这些需求拆解成具体的组件（一个房间是一个组件），决定每个组件放在哪、组件之间如何联系，最后画成图纸。体系结构设计做的正是这件事：把需求拆成组件，排布它们的位置与联系。

教材给的书面定义包含几个关键词：软件体系结构（software architecture）总体而言是一种**结构（structure）**，是对结构的描述；这个结构由**组件（components）**构成，即把整个系统看作由组件组装起来。在体系结构设计中，除了描述有哪些组件，还要描述每个组件的**性质（properties）**，以及组件之间的**关系（relationships）**。特别要注意：体系结构设计关注的是**外部可见的性质（externally visible properties）**——它是架构设计而非详细设计，不刻画内部那些 trick 的东西，只画外部结构。

为什么做软件之前一定先要有架构设计？教材引用一篇论文的三个观点，其中两点最为关键：

1. **沟通工具（Communication Tool）**：架构设计是给所有对开发感兴趣的人（stakeholders，基本是内部同行、其他组的成员）用来沟通的工具，首要目的是让别人听懂。后续课程会让每个组上台讲自己子系统的架构设计，上台前必须明确——你讲的一切都是为了沟通。常见误区是：有的组把上台当成"把准备好的 PPT 闭卷念完"，完全不在乎台下听懂没有。要时刻记得，这件事是为 communication 服务的。

2. **暴露早期设计决策（Early Design Decisions）**：如果早期设计决策错了，后面弥补极难。再以盖房为例：用户说"150 平米，三室一厅一厨两卫"，这是需求；架构设计要先想这 150 平米怎么布局。若一开始决策"三个居室都围着厨房建、两个卫生间堆在客厅角落"，那这房子怎么看都不像正常人住的——一家都是吃货才为厨房近。更糟的是，后期无论用多高级的吊顶、多豪华的地板去装修每个房间，一进门还是觉得不对劲；而且三居室围着厨房会带来通风、油烟、煤气等一系列问题，绝不是把每个模块仔细改善就能解决的。**布局先错，后面一系列问题随之而来**——这正是架构设计 highlight（凸显）早期决策的原因。

## 二、体系结构风格（Architectural Styles）

体系结构风格描述系统"长什么样"。一个规范的风格定义通常要讲清四件事：

- 一系列**组件（components）**构成系统；
- 组件之间是**如何连通的（a set of connectors）**；
- 在什么样的**约束条件（constraints）**下把它们放到一起；
- 提供一个**语义模型（semantic model）**。

常见的几种风格如下。

### 2.1 以数据为中心的架构（Data-centered Architecture）

一听到 "data-centered"，脑海里应立刻出现这样一幅画面：

```
            ┌──────────────┐
            │   应用 A      │
            └──────┬───────┘
                   │ 读写
            ┌──────▼───────┐
            │   应用 B      │
            └──────┬───────┘
                   │ 读写
        ┌──────────▼──────────┐
        │   中央大数据库        │  ← 系统围绕它转
        │  (Repository)        │
        └──────────▲──────────┘
                   │ 读写
            ┌──────┴───────┐
            │   应用 C      │
            └──────────────┘
```

把系统理解为**围绕着一个数据库**，所有功能都被视为围绕它构建的小型应用，统一在该数据库上读写。

### 2.2 数据流架构（Data-flow Architecture）

当数据在系统中呈现非常明显的**单向流动**特征时适用。中间的每个模块像一个**过滤器（filter）**，数据流线像**管道（pipes）**，水沿管道通过一个又一个过滤器、朝一个方向流动：

```
 输入 → [filter1] → [filter2] → [filter3] → ... → 输出
        (pipe)      (pipe)      (pipe)
```

这就是经典的**管道-过滤器（Pipes and Filters）**风格。最简单的是单线流水线。

### 2.3 面向对象架构（Object-oriented Style）

把整个世界看成由对象和对象间的关联构成：一个一个封装好的 `class`，彼此之间有某种关联性。其核心特征是**封装（encapsulation）**——对象把数据与操作捆绑在一起，组件间通过消息传递/方法调用协作。

### 2.4 调用-返回架构（Call-and-Return Architecture）

这是最常见的结构化设计模型：

```
                    ┌─────────────────┐
                    │   整个大系统       │
                    └────────┬────────┘
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         ┌─────────┐   ┌─────────┐   ┌─────────┐
         │ 模块 A  │   │ 模块 B  │   │ 模块 C  │
         └────┬────┘   └────┬────┘   └────┬────┘
              ▼              ▼              ▼
         ┌─────────┐   ┌─────────┐   ┌─────────┐
         │ 子模块  │   │ 子模块  │   │ 子模块  │
         └─────────┘   └─────────┘   └─────────┘
```

顶端是整个大系统，下面分三大块/三大模块，模块之下再分更细的模块；也可理解为上层调用底层模块——上层做决策，下层真正工作、提供数据与底层支持，供上层调用。这种结构适用于绝大多数结构化软件设计，是极其经典的形式。

### 2.5 层次化架构（Layered Architecture）

更"文艺"的画法，体现系统明显的层次感（由内向外、由底向上）：

```
  ┌─────────────────────────────────────┐
  │  User Interface Layer  (用户界面层)    │   ← 最上：面向用户，各应用接口
  ├─────────────────────────────────────┤
  │  Application Layer      (应用层)        │
  ├─────────────────────────────────────┤
  │  Utility Layer         (工具层)        │   ← 基础设计用的工具模块
  ├─────────────────────────────────────┤
  │  Core Layer             (核心层)        │   ← 最底：最核心的支持
  └─────────────────────────────────────┘
```

核心层（Core Layer）在最内/最底，提供最核心支持；其上构建工具层（Utility Layer），放基础工具模块；再上是应用层（Application Layer）；最上是用户界面层（User Interface Layer）。这种画法主要起"展示系统全貌风格"的作用，真正动手设计时，调用-返回那种结构反而更容易画，所以后续重点介绍它。

## 三、宽度、深度与扇入扇出：结构指标辨析

调用-返回结构可理解为一棵树：同一层有多少个模块，称为**宽度（width）**；往下一共分多少层，称为**深度（depth）**。宽度和深度都要恰当，不可太大。

还有两个关键指标：**扇入（fan-in）**与**扇出（fan-out）**。

```
              ┌─── M1 ───┐
              │          │
        ┌─────▼──┐    ┌──▼─────┐
        │ 模块 R  │◄───┤ 模块 R  │      fan-in(R) = 4
        └─────▲──┘    └──▲─────┘
              │          │
        ┌─────┘          └─────┐
        │                     │
    ┌───▼───┐             ┌───▼───┐
    │ 模块 A │             │ 模块 B │
    └───────┘             └───────┘

        模块 C
        ├──► 子模块 X      fan-out(C) = 2
        └──► 子模块 Y
```

- **fan-in**：模块 R 的 fan-in = 4，表示有 4 个上层模块同时调用它（有 4 条边指进来）；
- **fan-out**：模块 C 的 fan-out = 2，表示它向下调用 2 个模块（有 2 条边指出去）。

教材明确：宽度别太宽、深度别太深、fan-in 和 fan-out 都不能太大。课堂给出一个开放性问题（书上没写、需凭常识判断）：若这些指标太大，为什么不好？

讨论结论如下：

- **fan-in 太大**（一个模块被很多模块调用）：这是"牵一发动全身"的脆弱结构。该模块一旦出错，调用它的许多模块都傻了；它下面一改，上面各种模块说不定都要跟着改。所以 fan-in 不宜过多。
- **fan-out 太大**（一个模块向下调用很多）：一方面说明该模块**功能内聚性不强**（否则怎会分出那么多分支）；另一方面将来合并、做集成测试时会很麻烦——大量东西要凑在这个模块这边测，它与太多模块相关联，问题很大。
- **宽度太宽**：通常对应分工——同一时间层次铺开太多模块，你公司有那么多人手吗？若极端地整个系统只铺一层、唰一下排开十几二十个模块，那得有那么多人力才撑得住。宽度要根据公司规模、人手来定。
- **深度太深**：调用-返回结构的开发是从底层往上做的（底层开发完做上层，测试也是底测完测上），深度太深意味着将来要测太多环节，不是好事。

总之，这些指标没有"标准答案公式"，靠常识与经验权衡。

## 四、架构模式与设计风格的区别

**风格（Style）** 是宏观骨架——比如一提到房子，人住的房子一般该有卫生间、有厨房；**模式（Pattern）** 则是"你希望它具有某特点，就该怎么设计"。以厨房为例：只要设计厨房，必有固定的设计模式——通风、煤气管道、水池子接水管、下水处，这些基本东西必须有。凡厨房都得考虑这几件事，这就是设计模式。

在架构层面，教材把架构设计模式（Architectural Design Patterns）分为三类：

| 类别 | 适用场景 | 典型模式 |
| --- | --- | --- |
| **并发（Concurrency）** | 系统有强烈、大规模的并发 | 操作系统的进程管理（Process Management）、任务调度（Task Scheduling）模式 |
| **驻留数据 / 持久化（Persistence）** | 涉及数据库 | 数据库管理系统（DBMS）的固定设计模式 |
| **分布式（Distributed）** | 明显的分布式系统 | 分布式设计模式 |

每一大类下又含许多不同的设计模式。一个系统的整体设计未必只用一种模式——内部不同功能可套用不同模式。课程要求学员联系自己组的项目/子系统，撰写一份研究性报告（类似但不完全是文献综述）：先读若干近期论文，再说明自己的项目可以套用哪种设计模式、为何套用，并思考还有哪些模式也可用。

## 五、Context Design：体系结构语境图（ACD）

描述一个架构，第一步是做 **Context Design（语境设计）**。Context 不是写文章里的"上下文"，而是指：把你设计的系统放在一个大环境里，考虑它在环境中处于什么位置——它的上下左右都是哪些模块在跟它沟通、起作用。这本质是一个**外部环境的描述**。

要掌握的图是 **Architectural Context Diagram（ACD，体系结构语境图）**。ACD 描述的是目标系统（Target System）"与边界之外的实体如何交互（interacts with entities external to its boundaries）"。通常要画清四件事：

1. **上级系统（Superordinate Systems）**：画在目标系统上方，是调用你系统、要用到你系统的那些系统；
2. **下级模块（Subordinate Systems）**：画在下方，是你系统依赖、从中获取支持与数据的底层模块；
3. **同级系统（Peer Level）**：与你平级的模块，彼此是 peer-to-peer 关系，互相调用或互供信息；
4. **参与者（Actors）**：画在旁边，扮演"使用者"角色的模块——它来用你的系统完成某件事（联想到用户脚本里的角色）。

画法：中间写目标系统的名字（Target System）；上方标 "Target System is used by the superordinate systems"；下方标 "it depends on some subordinate systems"；两侧与旁侧标同级与 Actor 关系。

```
          [Superordinate A]      [Superordinate B]
                 │                      │
                 │ used by              │ used by
                 └──────┐       ┌───────┘
                        ▼       ▼
                   ┌─────────────────┐
                   │  Target System  │
                   └────────┬────────┘
            depends on      │      peers with / actors
                   ┌────────┴────────┐
                   ▼                 ▼
          [Subordinate X]     [Peer / Actor Y]
```

## 六、随堂自测

**1. 为什么说体系结构设计是"暴露早期设计决策"的关键？用盖房比喻说明。**

**解析**：教材强调早期决策错误后期极难弥补。以 150 平米"三室一厅一厨两卫"为例，若架构决策把三居室全围厨房、卫生间堆客厅角落，后期再豪华装修也救不回来，且会引发通风、油烟、煤气等连锁问题。布局一旦错了，不是把每个模块改善就能解决的——架构凸显的正是这种早期、全局性的决策。
**答案**：架构决定系统整体布局，早期错误会沿生一系列结构性问题且后期难改；如户型布局错了，装修再好也无效。

**2. 一个模块的 fan-in = 8、fan-out = 7，从结构健壮性角度分别说明隐患。**

**解析**：fan-in = 8 表示 8 个上层模块调用它，属于"牵一发动全身"的脆弱结构——它出错则 8 个调用者全受影响，它一改上面诸多模块可能跟着改。fan-out = 7 表示它向下调用 7 个模块，一方面暗示功能内聚不强，另一方面集成测试时要凑大量东西在该模块侧测，合并痛苦。
**答案**：高 fan-in 导致脆弱、改动波及面广；高 fan-out 暗示低内聚且集成测试困难。

**3. 绘制 ACD 时，Superordinate、Subordinate、Peer、Actor 四者各描述目标系统与外部怎样的关联？**

**解析**：ACD 描述目标系统与边界外实体的交互。Superordinate 是调用/使用目标系统的上级；Subordinate 是目标系统所依赖、从中取数据的下级；Peer 是与目标系统平级、互相调用/互供信息的同级；Actor 是扮演使用者、用目标系统完成某事的旁侧角色。
**答案**：上级=被其调用；下级=依赖其支持；同级=对等互调；Actor=使用系统的角色。
