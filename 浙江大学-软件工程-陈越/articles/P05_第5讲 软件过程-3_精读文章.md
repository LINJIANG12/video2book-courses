# 软件过程（三）：规范模型家族总览——瀑布、增量、RAD、演化与统一过程

## 一、规范模型的适用边界：为何"有序"仍主导、又为何需要敏捷补位

本章所讲的全部 process models 都属于 **prescriptive process model（规范/描述性过程模型）**——事先规定任务与次序，强调有序的软件工程方法。在软件过程的早期，这类模型确实带来很大好处：它为开发规定了明确的任务与要求，使混乱可控。

但随着软件发展、用户对交付时间和变化响应要求越来越高（尤其大量 Web 应用），纯规范模型暴露出诸多问题。因此**第四章将专门引入敏捷软件过程（agile）来应对**。本章先夯实规范模型家族本身——它们至今仍有作用，是理解后续一切模型的基础。

需要明确一个判据：课程的大 project（简化版支付宝）**不适合 RAD 模型**。原因有二：其需求在立项时基本已确定（大作业性质），且课程项目**没有那么多资源**。RAD 与增量模型的最大区别，正在于它依赖**大量组间并行开发、需要大量资源**——这是课程情境不具备的。

## 二、瀑布模型及其 V 模型变体

**Waterfall Model（瀑布模型）** 是过程模型中最基础的一个，也是"经典生命周期"的代名词。其命名源于瀑布**永远从上往下流、难从下往上流**的线性特征。

### 2.1 五个阶段

最基础的瀑布模型抽取出软件开发必备的五个要素，自上而下推进：

| 阶段 | 内容 |
|---|---|
| **沟通（Communication）** | 项目启动前调查需求，与项目提供方充分沟通 |
| **策划（Planning）** | 将口头沟通落实为书面文件：项目估算（时间/成本/人力）、进度计划（全局观，何时做何事）、项目跟踪（tracking） |
| **建模（Modeling）** | 用模型工具把复杂问题形象化，便于在更抽象层面分析与设计（非直接代码） |
| **构建（Construction）** | 编码与测试——本科生当前主要学习内容 |
| **部署（Deployment）** | 交付、支持与反馈；程序做完不是终点，要获取新需求、改进意见 |

水从顶端一直滑下，正如箭头依次推进，故曰瀑布。

### 2.2 V 模型变体

瀑布还有一个重要变体 **V-Model**：左侧自上而下是**开发**流向（需求分析 → 概要设计 → 详细设计 → 编码），右侧自下而上是**测试**流向，且一一对应：

```text
需求分析 ─┐
概要设计 ─┤
详细设计 ─┤        单元测试
  编码  ─┼─ 对应 ─ 集成测试
          │        系统测试
          │        验收测试
```

左侧每个开发环节，都在右侧有对应层面的测试验证。V 模型与经典瀑布本质相同，都符合"顺序原则"。

### 2.3 现实困境

瀑布最符合人们最初的直觉，但现实应用问题显著：

1. **真实工程很少严格顺序进行**。线性模型不强调迭代，要用间接方式实现变动都极其困难。
2. **用户需求无法在一开始就清晰、准确、完整**。瀑布的前提（需求一开始就提得非常清晰完整）在操作中很难实现；需求随开发过程不断变化。
3. 一旦后期变更，线性结构使回头成本极高。

## 三、增量模型：以 iOS 的版本迭代为证

**Incremental Model（增量模型）** 在实践中用得较多、也较好。其核心是：先交付一个**功能较弱但可运行的雏形**，再不断加入功能、逐步逼近完美。

以 **iOS 操作系统** 为例极具说服力：

- **2007 年第一版**：功能极欠缺——无彩信、无复制粘贴，仅具打电话、发短信能力；
- **第二版起**：加入中文字符支持、手写输入法、App Store 与开发者 SDK，系统开始流行；
- **2009 年**：推送通知、拷贝粘贴（发布两年后才补上）、彩信（推出两年后加入）、蓝牙、语音控制；
- 之后持续迭代：多任务、文件夹等；
- **2011 年 iPhone 4S**：iCloud 云端功能；
- 再后来：智能助手 Siri。

五年间 iOS 不断功能迭代、向"完美"迈进——这正是增量模型的典型应用。需澄清一个常见误解：iOS 3 与 iOS 2 并非推翻重来（无重构式重置），而是在原有基础上**持续加入新功能**，因此符合"在一个项目内部做增量"的定义（每个版本不是独立项目，而是同一操作系统项目的迭代）。

增量模型的优点：

1. 人力不足时，短时间开发雏形，**快速交由客户获得支持、缓解团队人力压力**；功能需快速迭代时可投入更多人力做"功能试点"。
2. **化解风险**：若某功能点市场反响差，早期发现比漫长开发后才发现浪费更小——避免人力、时间、精力成本打水漂。

## 四、RAD 快速应用开发：与增量的同与异

**RAD（Rapid Application Development，快速应用开发）** 同样使用瀑布五过程，本质是把这五过程**快速融合、高速重复**，相当于"高速瀑布模型"。

### 4.1 机制与适用

- 尽可能**利用现有程序构件（component）**，并为以后重复开发类似构件做好准备（可重用构件）；
- 适用场景：小型团队用已有构件创建工程；时间紧迫时大团队快速迭代；学生团队用开源构件快速完成 construction 环节。

### 4.2 与增量模型的区别

增量也能"开发得比较快"，但 RAD 的最大特征是**大量组间并行开发**——需要大量资源协调。例如 A 组开发某功能模块、B 组开发另一模块，初期就要大量人力资源去协调匹配。

### 4.3 缺点与不适用情形

1. 初期可能需要大量人力资源协调多组并行；
2. 客户与程序员都须**适应** RAD 节奏——若客户提要求但程序员未适应，无法在时限内交付；
3. **高性能项目不适合**：如为移动终端开发接口，若重用原本给 PC 浏览器的接口，对低带宽移动环境不合理；
4. 若需大量**新技术**，开发风险极高，等开发完才发现不符合要求，重构的时间成本更高。

正因如此，课程项目（资源有限、需求既定）不适用 RAD。

## 五、演化式过程模型

演化式模型的现实背景有三点：业务与软件需求**不断变化**；开发时间紧、须有限时间内推出有限版本应对商业竞争；开始时系统细节不明确，须通过演化不断完善。它是**不断迭代**的过程。

### 5.1 原型开发（Prototyping）：循环逼近含糊需求

**Prototyping** 是一种循环过程，不断完善软件版本直到客户满意接受。适用于：

- 客户定义了总体要求，但**未定义详尽的输出、输入与过程细节**，且客户自己也不太清楚；
- 不确定**算法有效性、操作系统能力、人机交互形式**等情形。

其循环如下：

```text
  沟通(明确需求)
      │
      ▼
  快速策划 + 设计原型 → 交付客户试用
      ▲                    │
      │                    ▼
  客户反馈(再沟通) ←── 调整版本
      │
   （循环直至客户接受）
```

**优点**：客户能立刻看到软件初步长什么样，观点直观；能快速推出、不浪费其他资源。

**缺点**：

1. 开发者为快速推出，**未考虑长期维护**，后期维护困难、质量不高；
2. 为快速实现，可能沿用自己熟悉但**未必适合**的语言/架构，导致性能下降。

**关键纪律**：一开始就要定好规则，让客户明白——原型开发是**为后续正式系统服务**的，而非推出一个产品就再也不改。换言之，原型绝不能当最终产品。

### 5.2 螺旋模型（Spiral）：Boehm 的风险驱动迭代

**Spiral Model** 由 **Boehm 教授**提出，核心目标是**减少软件开发风险**。它把原型开发的迭代过程，与瀑布模型的**可控性、系统性**结合在一起。

可理解为"在原型开发中加入了风险分析"。其形态是**顺时针不断扩大的圆圈**（每圈代表一次迭代，圆圈随软件完善而扩大）：从沟通开始 → 策划 → 项目设计 → 编码测试 → 产品发布。早期几次迭代可能只是"产品说明书"阶段；随着迭代加深，开发出较像样的原型；原型再经多次迭代演化出不同版本，适应不同需求。

特征与适用：

- 适合开发**大型软件系统**；
- 难点：常需反复修改，**可控性不确定**，难说服客户（"已有这么好的了为何还要一直改"）；
- 必须配备**大量风险评估专家**——若风险未被检测到，产品可能失败。

## 六、统一过程（UP / RUP）：用例驱动、架构中心、迭代增量

**UP（Unified Process，统一过程）**，早期称 **RUP**——因其出自 Rational 公司（即开发画 UML 的 Rational Rose 软件的公司，后被 IBM 收购，遂改叫 UP）。它像螺旋模型，也是**迭代 + 增量**，试图把前面"一大堆乱七八糟的模型"统一起来，故称"统一过程"。

### 6.1 三大特点

1. **use-case driven（用例驱动）**：用例即 UML 中的 use case diagram——给用户看的图，画出有哪些角色、各自要做什么，以及系统给什么输出；多用户时描绘其相互关系，无需文字描述。
2. **architecture-centric（以架构为中心）**：在 **elaboration（细化）** 阶段就要把软件架构定好，此后若无问题架构不动；后续迭代都围绕该架构展开。
3. **iterative + incremental（迭代 + 增量）**：切分很小阶段，每阶段都出成果以控制风险。

### 6.2 四个阶段与迭代

UP 分四阶段，对应传统步骤：

| UP 阶段 | 含义 | 主要产出（Artifact） |
|---|---|---|
| **Inception（初始）** | 项目开始 | 用例图（标示用户需求）、领域模型、术语表 |
| **Elaboration（细化）** | 粗了解后细化 | 画出系统模块与子模块图；做出**可执行的**（模块间可互动）原型；架构用 UML 表达 |
| **Construction（构建）** | 进入编码 | 大部分编码完成，产出可运行系统 |
| **Transition（过渡/交付）** | 转交用户 | 交付、修复 bug |

四个阶段构成一个完整生命周期，但**每个阶段可切分为多个迭代**（较小时间段），每次迭代结束都要出一个成果——如同课程中"第一周、第二周都要完成一件东西"，避免全部堆到最后。每迭代有目标，每大阶段也有目标；目标未完成则前期工作视为未完，须重做。

每个迭代内含 **5 个 workflow（工作流）**，类似瀑布：沟通需求 → 分析 → 设计架构 → 编码实现 → 测试（课本还提 4 个支持性工作流）。各阶段这五项工作量不同：前期用例建模多，后期实现多——并非"某阶段绝对做或不做"，而是"做多或做少"。

### 6.3 与迭代模型的不同：强调 Artifact

UP 特别强调整个过程中要产出 **Artifact（制品/人造物）**——每个阶段结束要生成什么。例如 Inception 完成的最重要判据：**把成果拿给客户看、客户认可即可**；细化阶段须做出模块间可互动的原型（不同于纯静态界面样机）。

现实映射：Windows Vista 的 Beta 1、Beta 2、候选版（Release Candidate）、零售版，正是迭代产出；Win7、Win8 也都实行迭代开发。

## 七、软件生命周期视角：从立项到消亡的全过程

跳出单个模型，须从**软件生命周期**整体理解：软件从**立项 → 开发 → 维护 → 消亡**，是完整生命周期。前述各模型（尤其演化模型）描述的正是这一发展过程——软件一个版本接一个版本，最初功能很弱，后不断增加、演化，直到消亡，过程才结束。

演化过程**包含维护过程**。UP 与 UML 紧密对应：UML 从 80 年代面向对象思潮中诞生，是 OO 开发最流行、最成功的环境与工具；UP 则是与 UML 配对、面向对象的**过程模型**。尽管 UP 表现形式与前几类模型差异明显，但其**核心内容基本一致**，只是表达不同。

## 随堂自测

**1. 瀑布模型与 V 模型的关系是什么？V 模型右侧的测试层级自下而上如何对应左侧开发环节？**

解析：V 模型是瀑布模型的变体，本质都符合顺序原则。左侧自上而下为需求分析→概要设计→详细设计→编码；右侧自下而上对应单元测试→集成测试→系统测试→验收测试，每个开发层都有对应测试验证。

答案：V 模型是瀑布的顺序变体；右侧测试自下而上（单元/集成/系统/验收）一一对应左侧（编码/详细设计/概要设计/需求分析）。

**2. 增量模型与 RAD 在"快"的机制上根本区别何在？为何课程项目判定不适用 RAD？**

解析：增量之快来自"先交功能较弱雏形 + 持续迭代加功能"；RAD 之快来自"大量组间并行开发、高速重复瀑布五过程"，需大量资源协调。课程项目需求立项时基本已确定、且缺乏大量并行资源，故不适用 RAD。

答案：增量靠雏形先行与迭代；RAD 靠多组并行 + 大量资源。课程项目资源有限、需求既定，故不适 RAD。

**3. 螺旋模型由谁提出？它试图把哪两类思想结合起来？它最主要的风险控制前提是什么？**

解析：螺旋模型由 Boehm 提出，把原型开发的迭代过程与瀑布模型的可控性、系统性结合，目标是减少风险。其落地前提是必须配备大量风险评估专家，否则风险未被检测会导致产品失败；且因频繁修改难说服客户。

答案：Boehm 提出；结合原型迭代 + 瀑布可控性/系统性；前提是需大量风险评估专家且难说服客户接受持续修改。
