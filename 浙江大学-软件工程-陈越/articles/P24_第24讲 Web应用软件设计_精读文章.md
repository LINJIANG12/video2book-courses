# 第24讲 Web 应用软件设计：从界面美学到 MVC 与导航的设计分层

设计之前先记住一个方法论教训：做任何事都从需求分析开始。写需求规格说明书，要先去读课程对它的要求——它相当于签合同的重要参考文档，而合同里最关键的是验收指标（什么情况下客户付钱、要拿出什么东西）。曾有组交了 60 多页文档，却只对其中一个 use case 做了详尽描述，其余打分项的活一点没干，TA 无从打分。无论画多漂亮的 UML，先搞清楚"要你做的是什么事"再动手——这是软件工程交给你的"做事情的套路"。本讲进入 Web 应用的设计模型（design model），看它作为"文艺青年"有哪些特殊讲究。

## 一、Web 设计为何特殊：要在设计中前置的属性

设计方面的特殊，必然与它那十几条特点里"在设计阶段就要盯死"的几条相关。回想做 online judge（如 ZOJ、PAT）这类网站，设计时必须先想清楚：

- **Security（安全）**：跑考试、跑竞赛，不能让人轻易在考前进去把题扒出来，必须事先设计好如何防范各种攻击与黑客。
- **Availability（可用性）**：网站不能三天两头挂。偶发宕机可容忍，频繁挂掉用户就不来了。
- **Scalability（可扩展性）**：一两个人能玩、一两百人就有挂掉，不行。要能应对访问量大幅波动。
- **Time to market（上市时间）**：工期极短，意味着设计时别想太复杂，尽量简单、先完成主要功能。

由此引出 **design goals** 的第一条：**simplicity（简单）**。尽量简单，不把事情搞复杂。

随后被强调的还有两条，根因同样是"用户不可控"：

- **Robustness（健壮性）**：你根本不知道坐在电脑前的是美女还是抠脚大汉，甚至不知道是一个人还是一条狗，不知道他会按什么键、什么搜索习惯。所以要能应付各种各样的人、各种"变态"操作，让各种水平的人都能进出自如、找得到东西。
- **Compatibility（兼容性）**：用户群不可控，用什么平台、什么操作系统、什么浏览器（连 IE6 这种老古董都可能）都有。设计时要规划照顾哪些、不照顾哪些。

## 二、设计金字塔：越往上越靠近用户

教材把 Web 设计画成一座金字塔：

```
                      [ Users 用户 ]            <-- 顶端，目标
                          |
                  [ Interface Design 界面/美工 ]
                          |
               [ Content Design 内容设计 ]
                          |
             [ Navigation Design 导航设计 ]
                          |
                  [ Technology 工程师 ]         <-- 底端，干活
```

越往上越靠近用户（界面、美工），越往下越靠近工程师（技术实现）。下面把各层逐一过一遍。

## 三、界面设计（Interface Design）

对 Web 应用，界面设计的核心要求是：用户在任何页面、任何停留点，都能轻松回答三个问题。

### 3.1 三个必答问题

1. **Where am I?（我在哪？）**：随时清楚自己没迷路。常见做法如行政办公网，页面顶部一行小字"当前位置：首页 → 学术机构"，既告诉你在哪、又告诉你路径。最有效的方法是先去研究同类网站人家怎么做的，学习风格。
2. **What can I do now?（我现在能干吗？）**：页面要把可点的东西清楚展示——哪些功能可用、哪些链接有效、哪些内容相关。本质是"把按钮做成按钮、把链接做成链接、把下拉框做成下拉框"，符合用户在互联网上养成的习惯预期。现实中奇葩设计很多：看上去不是链接一点却是链接；写着"点按钮"却找不到按钮，原来那坨东西就是按钮；看着像文本框，点上去没反应，仔细看旁边小箭头才发现是下拉框。所以必须让元素"长成它该有的样子"。
3. **Where have I been? / Where am I going?（我去过哪、能去哪？）**：最简单的机制是浏览器默认的"点过的链接变紫、没点过的是蓝色"，告诉你走过哪、还能去哪。复杂网站还可提供 site map。

### 3.2 有效界面的特征

- **visually apparent and forgiving（视觉清晰且宽容）**：给用户掌控感（a sense of control），让他迅速看到选择余地、明白如何达成目标；并且**允许他点错**——设计原则之一是把用户当成白痴，白痴都会用，不白痴的用户自然更舒服。
- **不暴露系统内部运作**：普通内部系统会弹窗问"Do you want to save your change?"，网站则要求更高——**根本不提醒，默替他存了**，且让他在任何时刻都能反悔（撤销）。这是很高的要求。
- **perform a maximum of work while requiring a minimum of information**：让用户做的事越少越好、用最小精力完成最多工作。对内部软件，多点一下用户虽不爽但勉强忍了；在网上则不可忍——多一步不仅依赖服务器，还依赖网络，赶上网络抽风，用户绝不能容忍多余操作。所以完成目标所需动作必须尽可能少。

补充一句：互联网用户你尽可以想象得多白痴就多白痴，哪怕是计算机小白也有权使用你公开发布的系统；若他轻易犯错，那是你设计得不好。不想让他破坏的东西，根本别出现在页面上。

### 3.3 界面设计流程

1. **review analysis model**，做 refinement（回顾需求分析模型并精化）；
2. 画 **rough sketch of the interface layout**（界面布局草图）：要不要 banner？横着要不要一条功能带？竖栏放左还是放右？中间放什么？因工期短，只粗略画；
3. **map user objectives into specific interface actions**（关键步骤一）：把网站给用户提供的几件事，与页面上对应的链接/按钮一一映射——他点哪个完成哪个目标；
4. **列出点击后的后续动作序列**（关键步骤二）：比如点"buy a component"进去后，还要查看、选择、放进购物车、结账、填银行卡与邮寄地址……把这一系列动作一条条理出来；
5. 画 **storyboards（分镜头）**：像导演画分镜，描述每个界面动作下屏幕出现的状态，再据美工设计 refine；
6. 抽取 **interface objects**（面向对象开发时抽相关对象）；
7. 建立模型：因时间紧不要求正式图，但要有一种方式描述**交互流程**，还要有描述**动态行为**的模型（即状态迁移图 state transition），每个状态下界面长什么样、布局如何，都要有描述；
8. 不断 refine、review、细化。

### 3.4 控制机制（Control Mechanisms）

最简单的是 **navigation menus（导航菜单）**；此外还有更花哨的 **graphic icons、graphic images** 等可作为跳转与控制界面。

## 四、美学设计（Aesthetic / 美工设计）

工科学生普遍缺乏审美——写论文排版不知丑、画结构图把字写到方框外面还觉得"还好"。本节不指望短时间培养审美，只给几条必须遵守的基本品位：

- **Don't be afraid of white space（合理留白）**：不必把屏幕边角全填满。留白不是坏事，是品味；全填满有密集恐惧症的人看着难受。
- **Emphasize content（突出内容，切忌喧宾夺主）**：一页重点展示什么要清楚。若本要展示一段文字，却做了特别 fancy 的 Flash banner，结果访客只记住 banner、不知网站干嘛，就是喧宾夺主。
- **Organize layout elements from top-left to bottom-right（自左上至右下的阅读动线）**：绝大多数人习惯从左上往右下看，元素按此顺序排布。除非故意反着吸引眼球，正常网页应如此。
- **Group navigation, content and function geographically within the page（区域一致性）**：同一功能（如"下一页"按钮）在第 1 页放什么位置，后面几百页最好都放差不多位置。若"下一页"在每页跳来跳去（这页底下、下页上面、再下页左边），用户会满屏找链接、用得很累，这是不分工作、风格不统一的不专业表现。
- **Don't extend your real estate with the scrolling bar（别靠滚动条掩盖重点）**：特别想炫耀的重点最好出现在最上面、最醒目处。虽流行"亮点总在最后"，但不是所有人有耐心拉到最后。真要放在下面，前面先给个提示性链接可直达。
- **Consider resolution and browser window size（适配分辨率与视窗）**：不同浏览器、不同分辨率都要在美工设计时考虑。

## 五、内容设计（Content Design）

内容设计本身没太多新花样：基本就是用 UML，把内容相关东西抽取成 Class 或 Object，定义好它们之间的关系。这与前面的 Content Model 一脉相承。

## 六、架构设计（Architecture Design）

架构设计分两大类。

### 6.1 内容架构（Content Architecture）

一个 content object 差不多就相当于一个 web page。网页与网页之间的整体结构有几种典型形态：

```
Linear（线性）       Grid（网格）        Hierarchical（层次）      Network（网状）
 A→B→C→D          A──B──C            A                      A↔B
                  │──│──│           / │ \                  ↕ ↕ ↕
                  D──E──F          B  C  D                 B↔C↔D
```

- **Linear structure（线性结构）**：顺序串联；
- **Grid structure（网格结构）**：行列节点；
- **Hierarchical（层次结构）**：树状、层次感强；
- **Network structure（网状结构）**：关系复杂。

### 6.2 整体应用架构（Application Architecture）：MVC

整体架构不像普通软件那样从数据流图翻译成 call-and-return 结构。网站流行一种架构风格叫 **MVC（Model-View-Controller）**——常听人说"我网站是 MVC 架构的"。核心是把系统分层设计，至少分三层：前台、后台，中间一个中转的 Controller。

```
        [ 用户 ]
           |
        [ View 前台 / 界面 ]
           |  (输入需求)
           v
        [ Controller 控制器 ]  <-- 衔接前后台
           |  (调用后台程序 / 取数据)
           v
        [ Model 后台 / 业务逻辑与数据 ]
           |
           +---> 获取数据后回传前台展示给用户
```

Controller 接受用户从前台输入的需求，调用后台程序、从后台取数据，再传回前台展示。系统搭成"后台 + 前台 + 中间 Controller"的结构，这就是 MVC 风格。

## 七、导航设计（Navigation Design）

导航设计有两个层面：**语义层面**与**语法层面**。

### 7.1 语义层面：NSU（Navigation Semantic Units）

工具叫 **NSU（Navigation Semantic Units）**，官方定义是"A set of information and related navigation structures"——一套描述信息与信息间导航关系的图。要对每个 use case、每个 actor 的行为，对应一套 NSU。

教材例子是 SafeHome 网上购物的流程：actor 在首页有一个链接，点进去要完成"选房间（Select Room）"；进入某 Room 页面后，页面上有多个链接，点其中一个"Recommend Components（推荐模块）"；再点进入被推荐的模块，打开描述该 Product Component 的网页。全程通过链接完成功能、跳转到对应网页。

```
[ actor ] --link--> [ 首页 Home ]
                       | link: Select Room
                       v
                   [ Room 页面 ]
                       | link: Recommend Components
                       v
              [ Product Component 网页 ]
```

通过图能清楚看到：用户完成一个 objective 时涉及哪几类页面（Room 是抽象出的 Content Object，不会给每个 room 各画一张图），这些 objects 之间用什么链接跳转——这便是导航设计的重要工具。

### 7.2 语法层面：实现机制

- **individual navigation link**：文字、icon、按钮等各种链接；
- **navigation bar（水平导航条）**：放最重要的几大类功能，**不要超过七个**（约四到七个）；
- **navigation column（垂直导航栏）**：放左或放右皆可，里面可放几乎所有 major content objects 和重要链接。为何横向建议不超七个、纵向随便放？因为鼠标滚轮是竖的——纵向可上下滚，横向应在同一屏宽内解决。若硬让竖向滚轮产生横向移动效果，动作与所见不一致，用户很难受；
- **tabs（选项卡）**：像多张卡片叠在一起，露出标识，一般三到五个页面；
- **site map（网站地图）**：帮用户随时知道自己在哪。

### 7.3 为何横向≤7、纵向不限

横向导航条塞在同一屏幕宽度内，所以数量受限（四到七个）；纵向导航栏可借助滚动条上下延展，故可放更多。这背后的道理是尊重用户既有的交互习惯（竖向滚轮对应竖向滚动），不让动作方向与页面移动方向冲突。

## 八、构件级设计（Component-Level Design）

构件级设计与普通软件差别不大，只是 WebApp 大致把功能分成四大类 component：

1. **动态生成内容的构件**：运行时动态产出页面内容；
2. **提供计算功能的构件**；
3. **数据库查询功能的构件**；
4. **与外部系统做沟通的构件**。

详细设计留到后面专门讲。至此，Web 应用的设计模型基本介绍完毕。

## 九、小结

Web 设计因用户不可控而前置了安全、可用性、可扩展性、上市时间等约束，design goals 首推 simplicity，并要强化 robustness（容忍任何用户与异常操作）与 compatibility（兼容多样客户端）。设计金字塔从用户的界面/美工，经内容、导航，落到工程师的技术实现。界面设计用"我在哪 / 能干什么 / 去过哪能去哪"三问锚定，要求视觉清晰宽容、默存可撤、动作最少；美学六原则守住基本品位与区域一致性。内容用 UML 类与关系建模；架构分内容架构（线性/网格/层次/网状）与应用架构（MVC 三层）；导航分语义（NSU 描述页面跳转关系）与语法（水平条≤7、垂直栏、tabs、site map）两层；构件级则归为动态内容、计算、数据库查询、外部沟通四类。

## 随堂自测

**1. Web 应用的界面设计为什么要求"把用户当成白痴"、且"默替他存、随时可撤"？**

解析：因网站用户完全不可控、无法培训，各种水平甚至误操作都可能发生（robustness 要求高）。有效界面要 visually apparent and forgiving，给用户掌控感并允许点错；相比内部软件弹窗问"是否保存"，网站更高要求是根本不提醒、自动保存且任意时刻可反悔，不想让用户破坏的东西干脆不出现在页面上。

答案：用户不可控且无法培训，必须让任何人（含计算机小白）都能顺畅、容错地使用；故界面要宽容、自动保存可撤销，把误操作风险在设计层面消弭。

**2. MVC 架构中 Controller 的职责是什么？它与普通软件的整体架构思路有何不同？**

解析：普通软件整体架构常从数据流图翻译成 call-and-return 结构；网站流行 MVC，分前台（View）、后台（Model）、中间 Controller。Controller 衔接前后台：接受用户从前台输入的需求，调用后台程序、从后台取数据，再传回前台展示。

答案：Controller 是前后台的中转层，负责接收前台请求、调度后台逻辑与数据并回传展示；区别于普通软件的数据流/调用返回式整体架构，网站以"前台—Controller—后台"三层分离为典型。

**3. 导航设计的语义层面（NSU）与语法层面分别解决什么问题？为何水平导航条建议不超过七个？**

解析：语义层面用 NSU 描述"信息及信息间导航关系"，即一个 use case 涉及哪些 Content Objects、它们之间用什么链接跳转；语法层面是具体实现机制（链接、水平/垂直导航栏、tabs、site map）。水平条限四到七个，是因为它要在同一屏宽内解决问题，而纵向可借竖向滚轮滚动延展，且动作方向须与页面移动一致，横向塞太多会破坏一致性与可读性。

答案：NSU 解决"页面间跳转关系怎么描述"，语法层解决"用什么控件实现"；水平条受屏宽限制且须与竖向滚轮习惯一致，故建议≤7，纵向则可滚动延展。
