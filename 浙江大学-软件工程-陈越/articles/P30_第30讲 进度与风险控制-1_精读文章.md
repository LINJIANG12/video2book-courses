# 第30讲 进度与风险控制（一）：项目进度计划、追踪与挣值分析

软件研发项目的成败，往往不取决于算法是否精妙、代码是否优雅，而取决于计划是否可行、进度是否可控。需求分析、设计、测试这些工程活动在前面的课程中已经逐一拆解，但把所有这些活动按时、按质、按预算串起来的，是项目管理中的进度计划（project scheduling）与进度追踪（tracking）。这一讲聚焦两个核心问题：项目为什么会delay，以及用什么工具和量化模型把"大概完成了一半"这种模糊感觉变成可度量、可纠偏的客观结论。

## 一、进度失控的根源：项目为什么会delay

几乎每一个做过真实项目的人，都对"项目延期"有切肤之痛。延期不是偶然，而是若干结构性原因反复作用的结果。把常见诱因逐条列出，几乎每一条都能在真实团队里找到共鸣：

1. **不切实际的deadline（unrealistic deadline）**。制定进度计划时，常常受到用户方或软件项目之外其他干系人的干扰。例如客户强硬要求"六月底、七月底必须上线"，于是进度表从一开始就不是基于工作量估算出来的，而是被外部压力"倒推"出来的。这种 deadline 违背工程规律，注定难以守住。

2. **需求变化没有反映到进度计划中**。用户需求频繁变化是常态，从正常流程看，变化应当体现为进度计划的相应调整。但实际操作中，除非是很大的变更，小的变化很难及时回填到 schedule 里，于是计划与实际之间的偏差被悄悄累积。

3. **工作量（effort）估计过低**。实际操作中的工作量远超预期，导致原先排定的时间点根本完不成。这是估计能力不足与乐观偏差叠加的结果。

4. **未预见的技术风险**。例如某些关键技术没有事先做技术攻关（技术预研），等到实现阶段才暴露困难，直接拖垮进度。

5. **人力安排困难**。人员到位、技能匹配、协作摩擦等人力因素，同样会转化为进度损失。

以上五类原因，在课堂大作业和实验室真实项目中反复出现。理解它们的共性，是做好进度管理的第一步：进度问题不是执行力问题，而是计划与风险识别的问题。

## 二、制定进度计划的基本原则

project scheduling 不是简单地把任务排进日历，它有一组必须同时满足的原则。任何一个原则缺失，都会埋下延期的隐患：

- **compartmentalization（任务分舱/任务分解）**：先把项目拆成明确的 task 列表。没有清晰的 task 清单，就谈不上排程。
- **interdependency（任务依赖识别）**：识别 task 之间的先后顺序约束。有些任务必须先做、做完后另一些才能开始；如果把有依赖的任务排成并行，就会出错。
- **effort validation（工作量与资源校验）**：确认资源确实可用，且资源能够完成这些 effort。资源可以是开发工程师、QA 工程师或其他研发人员。
- **responsibility（责任到人）**：在 schedule 里明确定义"具体哪个人做哪个 task"。
- **deliverables（交付物定义）**：每个 task 需要产出什么。例如需求分析阶段要产出若干分析模型；设计阶段要有概要设计、详细设计，乃至接口设计。
- **milestone / checkpoint（里程碑与检查点）**：若要严谨地跟踪和控制项目，必须设定里程碑。例如"需求分析做完""编码阶段做完"就是大的里程碑。一旦里程碑比计划时间点延后，项目极可能整体 delay，必须及时采取措施。

这六条原则共同回答了计划的三件事：做什么、谁来做、做到什么程度算完成。

## 三、工作量与交付时间的权衡曲线

一个反直觉但必须正视的事实是：项目并非"投入越多人力、越快完成"。研发过程中，由于 task 之间存在依赖、资源（人）的效用（utility）有上限，effort（投入）与 delivery time（交付时间）之间是一条有折中区的曲线，而非单调递减直线：

```
effort (投入)
  ^
  |   impossible 区
  |  |\            （再怎么加人也无法更早）
  |  | \___ 最短时间/最高代价
  |  |      \___
  |  |          \____
  |  |               \________ 折中区（实务取此）
  |  |                        \________
  |  |                                 \____ 最低代价/最长时间
  +-----------------------------------------------> delivery time
```

- 曲线最左端代表"用最短时间完成"，此时 effort 惊人地高；再往前就是 impossible 区——即便不计代价也无法再提前。若要求提前 25% 完成，成本已经非常高昂。
- 曲线最右端代表"代价最低"，但此时大量 task 无法并行，交付时间被拉得很长。
- 实务中通常取一条折中方案，在 effort cost 与 delivery time 之间 balance。

这条曲线对 Web 应用尤其有现实意义：Web APP 的实效性敏感，常常要求三个月或六个月的短期交付。若客户既要极短工期又要极低投入，这种要求在工程上"不切合实际"。项目经理的价值之一，就是向干系人说清楚这条曲线的存在，把不现实的期望拉回折中区。

## 四、各阶段工作量的真实分布

初学者容易把"软件研发"等同于"写代码"，但真实项目里编码阶段在总工作量中占比其实很小。一个典型分布如下：

| 项目阶段 | 工作量占比 | 主要活动 |
|---------|-----------|---------|
| 前端活动（front end） | 40% – 50% | 与客户的沟通（customer communication）、需求分析（analysis）、设计评审（design review）、与用户确认（confirm） |
| 构建/编码（coding） | 15% – 20% | 真正的程序编写 |
| 测试与安装（testing / installation） | 30% – 40% | 单元测试、集成、安装部署，其中集成（integration）代价尤其大 |

这个分布带来一个重要提醒：很多团队在第一次展示（demo）前的集成阶段异常挣扎（struggling），因为各小组之间要做大量集成、事先定义的接口也会暴露许多问题。把 30%–40% 的测试/安装 effort 提前规划进去，而不是到了后期才临时补救，是避免延期的关键。

## 五、任务集定义与工作分解结构（WBS）

定义 task set（任务集），需要根据项目类型（project type）的严格程度，确定项目里到底要完成哪些 task。以编码阶段为例：若质量要求很高，则应当安排一人编码、另一人做 peer review（同行评审），召开评审会（review meeting），并做单元测试、做 class 之间的协作测试。task set 要求尽可能详细——项目执行中真正要做的所有 activity 列得越全越好；若漏掉较多 activity，就容易引起 delay。

当一个项目以上述"层层分解"的形式列出，即大方面 → 要点 → 小点（如 review、derive a list 等），就形成了 **Work Breakdown Structure（WBS，工作分解结构）**。把整个 structure 完整列出来，task set 也就基本识别完成了。WBS 是后续排程、估算、责任分配的基础。

## 六、任务依赖与网络图

task 之间的 dependency 必须显式识别，否则就无法判断项目在研发阶段的并行度有多高。用 task network（任务网络图）可以把各 task 的完成先后顺序和依赖关系定义清楚。典型例子如下：

```
               ┌─ 1.3a ─┐
1.2 ───────────┼─ 1.3b ─┼──→ 1.4
               └─ 1.3c ─┘
```

含义：只有当 1.3a、1.3b、1.3c 三个 task 全部做完，才能进入 1.4。识别清楚这种 dependency 后，在安排 resource 做真实 task 时，才能正确排定先后顺序，避免把本应串行的任务错误地并行化。

## 七、甘特图与工期规划

把任务落到时间轴上，用的是 timeline chart，也就是**甘特图（Gantt chart）**。它表达每个 task 从什么时间到什么时间、由谁来做：

```
任务    第1周   第2周   第3周   第4周   第5周
T1     ████████████████
T2              ████████████████
T6                            ████████████████
                                  ↑ T6 起点必须在 T1 完成后
```

对于有依赖关系的 task，甘特图必须表达出依赖含义：例如 task 6 依赖于 task 1（task 1 做完才能做 task 6），那么 task 6 的起始时间一定在 task 1 完成时间之后。把所有 task 的时间轴画完后，最后一个任务的完成时间就是整个项目的 duration（历时）。

业界普遍使用自动化工具来画甘特图，例如微软的 Project（如 Project 2000 及其后续版本）。使用这类工具，只需把任务列出来、填好时间、设好 milestone/checkpoint、设好任务间依赖性，工具会自动规划出项目的整体历时。这张时间表是软件产业中项目计划的必备文档。

## 八、项目追踪与里程碑评估

进度计划做完后，必须靠 tracking（追踪）来检验真实项目状态是否偏离计划。tracking 的主要做法是：

- 召开周期性的项目状态会议（periodic project status meeting），由团队成员汇报进展与问题；
- 通过评审（review）结论来判断，例如编码阶段评审的结论是什么；
- 对照正式的里程碑（formal project milestone）：编码阶段结束了吗？测试阶段、部署阶段、集成阶段结束了吗？

里程碑通常设有明确时间点。例如某项目设"demo 1 完成"的里程碑为 6 月 19 号，当天下午/晚上助教 review 第一个 demo 后，就能确认该里程碑是否真正 close（关闭）。若有偏差，则比较 actual start date（实际开始日期）与 planned start date（计划开始日期）的差异。

对于采用面向对象分析与设计（OOAD）的项目，技术里程碑通常可归为四类：

1. **分析完成（analysis milestone）**：分析模型已建立，模型间关系清晰，可重用的类已被识别——分析阶段结束。
2. **设计完成（design milestone）**：设计了多少个类、类之间如何协作、类的属性与操作（operation）均已设计完成。
3. **编码完成（coding milestone）**：编码结束。
4. **测试完成（OO testing milestone）**：包括类本身的测试、类间协作测试、模块内集成测试、功能/系统级测试均完成，该里程碑即可 close。

无论课堂项目还是工业项目，只要采用 OO 方法，都绕不开"需求分析→设计→编码→测试/集成"这几大里程碑。

## 九、挣值分析（EVA）：把进度变成可量化数字

仅靠"感觉项目完成了一半"来评估进度极不精确。要在项目早期（甚至进度仅 15% 时）就获得可靠的绩效读数，需借助量化的**挣值分析（Earned Value Analysis, EVA）**模型。EVA 的核心术语如下：

| 缩写 | 全称 | 含义 |
|------|------|------|
| BCWS | Budgeted Cost of Work Scheduled | 计划中应完成工作的预算成本（按人天计） |
| BAC | Budget at Completion | 所有 task 的 BCWS 之和，即整个项目的预算总成本 |
| BCWP | Budgeted Cost of Work Performed | 已经完成工作的预算成本 |
| ACWP | Actual Cost of Work Performed | 已完成工作的实际成本 |

其中 BCWS 与 BAC 是预先在项目计划中定义好的，供后续计算分析指数使用。

**进度相关指标：**

- 计划完成百分比（percent scheduled for completion）：
  $$P_{sch} = \frac{BCWS}{BAC}$$
  表示按计划在此时点"应该"完成的比例。

- 实际完成百分比（percent complete）：
  $$P_{act} = \frac{BCWP}{BAC}$$
  表示实际已经挣得（完成）的比例。

- 进度绩效指数（Schedule Performance Index）：
  $$SPI = \frac{BCWP}{BCWS}$$
  反映项目利用计划资源的效率。

- 进度偏差（Schedule Variance）：
  $$SV = BCWP - BCWS$$

**成本相关指标：**

- 成本绩效指数（Cost Performance Index）：
  $$CPI = \frac{BCWP}{ACWP}$$
  反映成本控制的效率。

- 成本偏差（Cost Variance）：
  $$CV = BCWP - ACWP$$

**算例理解**：若某 task 计划预算是 5 个人天（即 BCWP 的预算基准为 5），而实际执行花费了 6 个人天（ACWP = 6），则
$$CPI = \frac{5}{6} < 1$$
说明成本控制效率低于计划，实际比预算超支。同理，若 BCWP < BCWS，则 $SPI < 1$，表示进度落后；若 BCWP > BCWS，则进度超前。

这些指标直观但关键：它们把"项目完成度""进度快慢""花钱效率"统一到同一套预算基准上，使项目经理能在偏差刚出现时就量化问题、定位是进度偏差还是成本偏差，从而采取针对性纠偏措施。

## 十、从进度管理走向风险管理

进度控制之外，项目管理另一个同等重要的方面是 **risk management（风险管理）**。一个合格的项目经理，一定是合格的风险评测与风险预测人员；否则项目会频繁暴露在风险之中。本节只引出这一主题——风险的定义、识别、评估、缓解与监控，将在后续章节系统展开。需要提前建立的认识是：绝大多数进度延期，追根溯源都能在风险识别阶段找到预警信号；把风险管住，进度自然更可控。

## 随堂自测

**1. 某项目 BAC = 100 人天。到第 8 周计划应完成 BCWS = 40 人天的工作，实际已完成工作的预算成本 BCWP = 32 人天，实际花费 ACWP = 38 人天。求：计划完成百分比、实际完成百分比、SPI、SV、CPI、CV，并判断进度与成本状态。**

解析与答案：
- 计划完成百分比 $P_{sch} = BCWS/BAC = 40/100 = 40\%$；
- 实际完成百分比 $P_{act} = BCWP/BAC = 32/100 = 32\%$；
- $SPI = BCWP/BCWS = 32/40 = 0.8 < 1$，进度落后；
- $SV = BCWP - BCWS = 32 - 40 = -8$ 人天（负值表示落后）；
- $CPI = BCWP/ACWP = 32/38 \approx 0.84 < 1$，成本超支；
- $CV = BCWP - ACWP = 32 - 38 = -6$ 人天（负值表示超支）。
结论：进度与成本双双偏离计划，且都劣于基准。

**2. 为什么"客户要求六月底必须上线"这类外部 deadline 容易导致项目延期？它与工作量—交付时间权衡曲线有何关系？**

解析与答案：这类 deadline 往往不是基于工作量估算，而是被外部压力倒推出来的 unrealistic deadline，违背了工程规律。结合权衡曲线，要把交付时间压到极短，必须付出惊人高的 effort（进入"最短时间/最高代价"区），而现实中资源有限、并行度受 task 依赖限制；若强行按不现实工期排程，就会落入 impossible 区或导致质量与进度双双失控。因此项目经理应把期望拉回 effort 与 delivery time 的折中区。

**3. 面向对象的软件项目，其技术里程碑通常包含哪四个？WBS 在排程中起到什么作用？**

解析与答案：四个技术里程碑为——分析完成（分析模型建立、可重用类识别）、设计完成（类的数量、协作、属性与操作设计完）、编码完成、测试完成（含类测试、类间协作测试、集成与系统测试）。WBS（工作分解结构）是把项目层层分解为 task set 的结果，它使 task 清单完整、依赖可识别、effort 可估算、责任可分配，是后续甘特图排程与挣值分析的基础。
