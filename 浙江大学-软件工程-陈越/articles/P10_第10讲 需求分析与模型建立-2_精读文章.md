# 需求分析与模型建立（二）：封装继承、用例、数据流图与状态建模

## 一、封装的本质是信息隐藏

封装（Encapsulation）把数据和操作这些数据的函数绑在同一个 class 里，与 C 的根本区别就在这里。这样做最大的好处是实现了 **Information Hiding（信息隐藏）**：只要对外的接口（Interface）没变，你今天高兴用算法 A 实现、明天换成更好的算法 B，把里头的东西改掉，外部完全不受影响。即使内部出了错，影响范围也有限——因为大家都通过 message 互相沟通，模块化（Modularization）更好，模块间的耦合（coupling）关系更简单。

另一个直接好处是 **reuse（复用）更方便**。用 C 时，有人习惯把所有 data structures 放一个 `.h`、所有操作放另一个 `.h`，复用时要记住 copy 哪些、include 哪些，分散多处、容易漏。class 把数据结构与相关内容绑在一起，只要重用这个 class 即可，机制非常顺手。

## 二、继承：一种安全的复用模式

### 2.1 单继承与 superclass

Inheritance（继承）是 OO 的重要特性。用一个 superclass 提取所有 subclass 的公共属性。例如 **Furniture（家具）** 作为父类，下面有 table、chair、desk，以及一种老浙大特有的 **chable**——既是椅子又有扶手、扶手翻过来就是小桌板，兼具 chair 与 table 的功能。它们都属于"家具"，公共属性（出厂、价格、颜色、材质：木/塑料/铁）放到父类 Furniture 里；子类继承下来（相当于 copy 一份），再叠加自己的属性，成为新 class。

继承被形容为**一种非常安全的重用模式**：想重用某个 class 时，不需要把人家的代码改掉，只需继承一下，在自己的 subclass 里改想改的、加想加的，且**不影响原始 superclass**——别人还能继续用父类。

### 2.2 多重继承（Multiple Inheritance）及其危险

一个子类可以从多个父类继承（C++ 支持 multiple inheritance）。好处是能结合多家的东西。但它可能引发危险。

**案例：GraphicalDeck（图形化纸牌游戏）。** 要做一个有图形界面的纸牌游戏，可复用两类现成 class：

- `CardDeck`：包含纸牌游戏规则——谁比谁大、怎么抽牌怎么出牌。
- `GraphicalObject`：操纵界面上图形物体的功能——画出来、移动、三维旋转缩放等。

让 `GraphicalDeck` 同时继承这两个父类，看似完美，却撞上一个坑：两个 class 里都有一个同名方法 `draw`，但英文 "draw" 是多义词——在 `CardDeck` 里是"抓一张牌（take a card from a deck）"，在 `GraphicalObject` 里是"在屏幕上画出来"。调用 `GraphicalDeck` 实例的 `.draw` 时，二者打架、产生冲突。解决办法之一是用 **overriding（方法重写）**，但聪明与否取决于具体手法。核心提醒是：**Multiple inheritance 可能有这种命名冲突的危险**。

更严重的是，一旦出现这种问题，**inheritance 的 transitive（可传递性）会被破坏**。如果 A 派生 B、B 派生 C，那么 C 同时继承 A 的全部属性——这是可传递的。但多重继承下，这种可传递性很可能失效。

## 三、基于用例的建模（Use Case）

Use case 描述一个 actor（参与者）使用系统的剧本（过程）。它在两个开发阶段极有价值：

1. **需求阶段**：跟用户核对"将来你就是这么用系统的——先做、后做、遇到这事做选择"，作为确认工具。
2. **测试阶段**：use case 是极可爱的资产。内部先按剧本把所有场景演一遍，没问题了才去见人。

**构建 use case 的三步（需求阶段不必写太细）：**

1. 列出所有 **actor**（哪些人、哪些角色要用系统）。
2. 对每个 actor，列出他要做的几件事。
3. 根据 functions 列出 **primary scenarios（初级/最简单剧本）**，画一张粗的 use case 图；再考虑"使用中有无特殊情况、分支岔路"，细化出 **secondary scenarios**。

### 3.1 案例：SafeHome 家居保安系统

书上的 SafeHome 例子很粗：家装好系统后，homeowner（主人）在面板上至少能完成三件事：

1. **初始化（Configuration）**：设置参数。
2. **Set Alarm**：出门时按按钮开启警报。
3. **通过 Internet 看 camera surveillance（监控镜头）**：在外网上查看房间是否异常。

前两者直接在保安系统面板上按键完成；第三者要走 Internet，启动硬件 cameras，调用镜头。每项功能再向下细化（如 Configuration 要设哪些参数、先点哪再点哪），形成一串更细的 use case。

### 3.2 Activity Diagram → Swimlane Diagram（泳道图）

前面讲过 **Activity Diagram（活动图）**：它不是脚本式，而在一张图里把所有分叉（走这步有两种可能、选 A 是一串行为、选 B 是另一串）都画出来，不如 use case 好理解。在活动图基础上可细化成 **Swimlane Diagram（泳道图）**——游泳池分道的概念，把每个 action 归到负责它的角色泳道里。SafeHome 的泳道分三道：

- **Homeowner**：负责一堆积动作。
- **Camera**：负责镜头动作。
- **Interface（控制面板）**：负责两个动作。

泳道图一目了然：系统由哪几块构成、整体由哪串动作完成、哪个角色负责哪些动作。它与 use case 都是辅助用户沟通的图，帮助理解"我怎么一步步把系统走完"。

## 四、面向流的建模：数据流图（DFD）

**Flow-oriented modeling** 把系统看成由"数据"和"功能"构成的整体。最古老的就是 **Data Flow Diagram（数据流图，DFD）**。它的根本理念是把计算机系统看作一个 **IPO 系统（Input - Process - Output）**：系统读一堆输入进来，在里面处理一下，变成输出出去。DFD 要描述的就是：**数据到底怎么从输入变成输出**——数据从输入处流进，经过功能变成另一副模样，再经下一个功能继续变，经一系列功能后转成最终输出。

**DFD 的符号约定：**

| 符号 | 含义 |
|------|------|
| 方块（□） | External Entity（外部实体）：输入操作、输出操作 |
| 圆饼（○） | Process（功能/加工），圆饼内写功能 |
| 有向边 | 数据流，边上标注流动的数据是什么 |
| 两条平行线 | 数据库，中间写数据库名称 |

整个图是一个**有向图**。

### 4.1 实例：公共图书馆信息系统

需求（简化版，只有两个功能）：

- **Get a book**：用户给 title、author、借书人姓名（Name of user），系统找到书给人，并更新"已借书"数据库。
- **Search by topics**：按主题查书，列出所有相关书的 titles。

画法要点（黑盒子原则）：

1. **先画功能进程（圆饼）**：`Get a book`、`Search by topics` 两个黑盒子，需求阶段不要细化内部。
2. **确定输入数据流**：User 给一个 Book request，流线上带 `title`、`author`、`Name of user` 三个数据，传给 `Get a book`。
3. **处理与输出**：`Get a book` 需要查 author、title 对应的书架位置（至少涉及"书架"数据库与"已借书清单"数据库），最终产生一本 book 交给前台 Book reception，并把借走书的 title 与 username 写入 list of books borrowed 数据库。`Search by topics` 则输入一个 topic，从 title/topic 数据库查，屏幕显示 list of titles referring to the topic，无需知道是谁在查。

### 4.2 初学者两大典型错误

1. **数据流断流**：某个功能只有输入、没有输出。数据流到这就停住、跟后面无关联，那这功能毫无存在必要——说明你画错了。
2. **莫名其妙自启动（灵异事件）**：功能是一段程序，必须有东西启动它才能产生输出。若所有指向它的箭头都从数据库来、没有真正的触发源，那它"自己跳起来读数据库"——不可能，因为**数据库是被动的，等着被读**，不会主动发数据去启动功能。正确情况是：有 book request 这类外部输入真正调用、启动功能，功能再去读数据库、产生输出。

只要不犯断流与灵异这两类系统级错误，能自圆其说即可得分（无标准答案）。

### 4.3 细化（Refinement）与分层（Level 0/1/2）

若 `get a book` 产生两个不同的输出（既送书到前台、又写数据库），说明它干了两件事，应拆成两个圆饼：先 `find book position`（找到书在哪），再 `get a book`（从书架取书给前台），同时并行去写借书数据库。这是 refinement（逐步细化）。

画图最忌在一页 A4 上"唰"地甩出巨复杂的 DFD——一堆小圆饼、细小字、数据乱流，谁看都晕。正确做法是**分层次**：

- **Level 0**：最简。读输入 → 一个大黑盒子 process → 产生输出去哪。
- **Level 1**：把中间 process 细化，露出几个子功能及数据如何在子功能间流动。
- **Level 2**：若某子功能还不够细，再拆。

就像拿天文望远镜→肉眼→放大镜→显微镜，细节要**逐渐展示**。记住：你写的需求文档是给别人看的（尤其忙得要命的 TA），要让人在很短时间内看懂。分级展示是一种关键技巧。

## 五、控制流与状态图（State Diagram）

除了数据怎么被功能改变（Data flow），系统还有另一维度：**Control flow（控制流）**，也叫 **State Diagram（状态图）**。它从"系统在执行过程中有哪几个不同状态、发生何事、如何处理，从而从一个状态转移到另一个状态"来理解系统。对应代码里就是中断（interrupt）、switch-case、if-else 等所有有转折、有多种可能性的**控制节点**。

以 SafeHome 为例，系统有四个状态，转换由事件驱动：

```
[switch on] → RESETTING（自检 run diagnostics, 面板显示 starting system）
    │  启动失败 → 面板显示 contact vendor（联系经销商）→ 终止
    │  启动成功 → SYSTEM OK
    ▼
  IDLE（待机, 面板 ready, 灯常亮, status=inactive）
    │  reset键 → 回到 RESETTING
    │  power off → 关机
    │  activate键（出门） →
    ▼
  MONITORING（监控中, 面板 armed, 灯常亮, status=monitoring）
    │  人回来 + deactivate password → 回到 IDLE
    │  进贼 → sensor triggered → START TIMER →
    ▼
  MONITOR AND ALARM（报警, 面板 alarm, 灯急闪）
    │  sound alarm 叫；notify alarm responders（自动拨警局/住户电话）
    │  贼消失 + timer 超时 / deactivate → 回到 IDLE（或 restart timer 持续叫）
```

这张图让用户一目了然：系统有四种状态，状态之间如何转换。注意 `run diagnostics`、`monitor and control system` 等内部怎么实现，用户不需要管——这是给用户看的。

## 六、类建模（Class-based Modeling）与 CRC 卡

OOA 抽取 class 的方法：写个 parser 抽名词，区分哪些是 attributes、哪些词定义了某 object 的属性；抽动词，动词是 manipulate（操纵）哪些 attributes 的动作，应抽成 operation。麻烦在于：某些功能改变了好几个 class 的 attributes，该跟谁绑？一般应与被操纵的 attributes 绑在一起；具体技巧结合 DFD 分析"哪些功能改变哪些 attributes"。

### 6.1 CRC Cards

早期真的用卡片（cards）做 **CRC**：

- **C** = Class（类）
- **R** = Responsibility（责任，即 class 的 attributes + public operations，等于 class 描述）
- **C** = Collaborators（协作者）

前两项（Class Responsibility）并非新东西。关键是红色的 **Collaborator 栏**：写下你这项还调用了谁、或被谁调用。它最重要的用途是**改动影响分析（impact analysis）**。例如你把"电话号码"从整数改成字符串——若另一 class 把它当 integer hash key，你一改它就挂。通过 Collaborator 把相关卡片揪出来，看影响了哪部分；若受影响卡片越少，说明设计越好；一改就牵出一大坨，就是差设计（牵一发而动全身）。

### 6.2 UML 类图符号速记

- 黑色实心菱形 = **Composition（组成关系）**，如 player 由头、身、四肢组成。
- 连线上的标注表示基数与模数：一对一、一对多、mandatory（必须有）或 optional（可有可无）。
- **Package（包）**：复杂系统把 class 归类装进"信封"。如足球游戏：环境相关类一包、规则类一包、人物类一包。
- 可见性符号：`+` public（所有人可用）、`-` 内部私有（藏起来）、`#` 仅限某几个 package 可用。

## 七、行为建模（Behavior Model）

Behavior model 描述系统使用过程中的动态。前面讲的 state diagram 就是其中一部分。要点：

- 既要画 **state of the system**，也要分析每个有必要的 class 自己的 **state transition diagram**（一直静态的 class 不必画）。
- 状态分两类：**passive（被动）**——仅 attribute 值改变；**active（主动）**——整个 process 在改变。
- **Sequence Diagram（时序图）** 与 state transition diagram 的关系，类似 activity diagram 与 swimlane 的关系：把每个 state 按时间轴从上到下排列，标出状态转换过程中牵涉哪些系统元素（如 Control panel 由 home owner 启动进入某状态、与 system 交互转换、与 sensor 交互转换），把所有牵连元素放进一张图。

## 八、写需求文档的六条纪律

最后落到"把模型写成文档"。一句话点题：**"Everyone knew exactly what had to be done until someone wrote it down."** 不落到纸面就不算数。写文档注意：

1. **分层展示**：不要一次性抖出所有细节，务必逐级展开。
2. **统一名词**：上百页文档由多人合作，不能同一东西在这叫"名字"、那叫"另一个名"。
3. **缩写首次给全称**：任何缩写，无论多常见，第一次出现必须给出全称并说明简称，之后才可用简称——写论文、写正式文件的通用规矩。
4. **要有目录（table of contents）**，友好一点再加 index（索引）。
5. **文风清楚、简单、不啰嗦**。
6. **站在第三者立场审视**：你清楚自己想做什么，别人不一定。问自己：TA 哥能在十分钟内读懂这块吗？

另外提醒：项目 due date 是 24 号，留了三个星期是有道理的——它真需要三周，别指望最后一晚或三天赶出来；以往有 TA 要求"需求文档写不到 100 页好意思交？"。

## 随堂自测

**1. 封装（Encapsulation）如何实现信息隐藏？为什么它让"改内部实现"变得安全，并便于复用？**

解析：封装把数据和相关操作绑进 class，只暴露对外接口（interface）。只要接口不变，内部算法/实现怎么改都不影响外部（Information Hiding），因此改内部安全；同时因数据+操作绑在一起，复用时只需重用整个 class，不必像 C 那样分散记住多个 `.h` 文件，故复用方便。模块化更好、耦合更简单。（依据：第一节）

**2. 画 DFD 时，"断流"和"灵异事件"两种典型错误分别指什么？为什么"数据库主动发数据启动功能"不可能？**

解析：断流=某功能只有输入无输出，数据到此停住、功能无意义；灵异事件=某功能没有真正的外部触发（所有入边都来自数据库）却自行产生输出。数据库是被动的、等着被读，不会主动发数据去启动功能；必须由 book request 这类外部输入真正调用、启动功能，功能才去读库、产输出。（依据：第四节 4.2）

**3. 多重继承（Multiple Inheritance）可能带来哪两类问题？用 GraphicalDeck 的 draw 冲突说明。**

解析：① 命名冲突——父类 `CardDeck`（draw=抓牌）与 `GraphicalObject`（draw=画出来）都有 `draw()`，派生类调用时语义打架，可用 overriding 等化解；② 破坏继承的 transitive（可传递性）——单继承链 A→B→C 时 C 继承 A 全部属性，多重继承下该传递性可能失效。（依据：第二节 2.2）
