# 第21讲 Web工程概述：把 Web 应用当作一类特殊软件来工程化

在需求工程之后、正式进入软件设计之前，需要先单独处理一类软件——Web 应用（WebApp）。之所以把它从普通应用软件中拎出来单独成章，是因为这一版的教材第一次把 WebApp 当作一个独立主题来讲解，根本原因在于它具备一组与普通应用软件明显不同的属性（attributes）。这些属性会一路渗透到后续的分析、设计、测试工作中，使得针对 WebApp 的工程活动与针对传统 App 的工程活动存在系统性差异。本讲先界定 WebApp 究竟"特殊"在哪里，再给出它的工程化框架、过程模型，以及动手之前必须澄清的需求清单与行业最佳实践。

## 一、为什么 WebApp 需要单独对待

传统的软件工程把软件当作一个"交付给明确用户的、有固定发布节奏的产物"。但 WebApp 从诞生起就带着互联网的基因：它跑在网络上、被陌生的人访问、随时在变、永不关机。教材把 WebApp 单列，正是提醒工程师——你面对的不是一台装好就完事的机器，而是一个持续在线、持续演化、受众不可控的系统。

理解"特殊"的标准不是背诵定义，而是把它变成工程决策的约束条件：凡是做 WebApp，都要在每一个环节**照顾到这些特点**。下面先把课上归纳出的核心属性逐条拆开。

## 二、WebApp 的核心属性

### 2.1 强网络依赖

WebApp 严重依赖网络。它不是本地运行的程序，所有能力都建立在与服务器的连接之上。这意味着"断网即失效"是天然风险，也意味着网络延迟、带宽、链路质量都会直接转化为用户体验。

### 2.2 浏览器差异与外观敏感

WebApp 运行在浏览器里，而不同浏览器对页面元素的渲染并不完全一致。一个在 Chrome 上美观的布局，在另一个浏览器上可能错位。因此 WebApp 必须**照顾浏览器兼容性**，并且要高度重视外表的美观度——视觉呈现本身就是功能的一部分，而不是锦上添花。

### 2.3 本地存储少、性能敏感

与把数据存在本机磁盘的传统软件不同，WebApp 的本地存储很有限，大量内容要从服务器取回。于是"快"成为硬指标：performance 不行，用户等不及加载就走了。性能不是优化项，而是留存的前提。

### 2.4 极短的迭代周期与敏捷要求

做 WebApp 极少有人给你三年工期。常见的现实是"给你三个星期已经算长，最好一个星期把网站弄出来"。这注定了 WebApp 的过程模型必须非常敏捷、非常快，无法承受传统软件那种冗长的瀑布式节奏。

### 2.5 用户未知、交互性强

这是 WebApp 与普通内部系统最本质的区别之一。给一家小银行做只给员工用的系统时，用户群固定、可被培训、行为可监控；但 WebApp 一上网，你不知道谁在用、什么人都有，各种稀奇古怪的操作都会出现。因此用户交互必须设计得极其周到，且要容忍"不可预测的人的行为"。

### 2.6 持续演化与无缝更新

传统软件可能两个月更新一次，WebApp 往往两个星期甚至更短就迭代一轮。更极端的是，它可能是**无缝衔接**的——没有"发版日"，版本一直在连续地变，后台持续部署、前端无感知切换。这对维护团队的管理能力提出了很高要求。

### 2.7 服务端存储与安全问题

WebApp 的数据通常存在服务器的数据库里，而非用户本机。用户把数据交给你托管，你就必须特别保证其安全。Security 因此成为头等大事，也直接决定了团队的人员构成：除了编码强的人，还必须有一批真正懂安全的人。

### 2.8 并发与不可预测的负载

把系统挂到网络上，就要直面两个孪生难题：

- **Concurrency（并发性）**：可能产生大规模并发，必须有强大的并发处理能力。
- **Unpredictable load（不可预测负载）**：负载是季节性的、脉冲式的——一阵子疯抢，过后没人用；一天之中不同小时、一周之中不同天的压力都不同。

### 2.9 高可用性

挂上网的东西，公众默认它应当 **7×24×365** 永远在线，不应有太多宕机时间。这就要求背后有一支强大的维护团队在支撑。

### 2.10 一个真实教训：奥运抢票网站的崩溃

这些属性不是抽象教条。课上举了一个鲜活的例子：北京奥运会抢票网站开放瞬间就崩溃了。讲师的表弟恰好在技术组，被调侃"做的什么破网站"。表弟的辩解是：领导坚持引进美国人当年办奥运会用的抢票软件。讲师算了笔账——那套软件能处理的并发大约是**每秒 5 个**。每秒 5 个并发！哪怕每秒 500 个都未必够，结果瞬间被挤爆，崩溃完全正常。问题出在严重低估了负载规模（"严重低估我们中国人民的热情"）。这个案例把"并发"和"不可预测负载"两个属性一下子钉进了工程现实：你按美国人口量级设计的容量，放到中国式访问洪流里就是纸糊的。

## 三、WebApp 的工程化分层框架

软件工程本身被描述为一个 layered technology（层次化技术），Web 工程也一样。它的分层自上而下是：

1. **质量焦点（Quality Focus）**：最底层永远是以质量为中心。虽然 WebApp 一切都做得匆忙，但匆忙不等于不做质量管控。再快，质量这根弦不能松。
2. **过程模型（Process Model）**：通常选 **agile（敏捷型）**。敏捷开发的详细过程留到最后一节课讲，但其核心精神就是"快"。
3. **方法（Methods）**：大面上仍是普通软件工程那一套——要做 communication（沟通）、requirements（需求）、requirements analysis（需求分析）、design（设计）、testing（测试），一样都不能少，区别只在于为了"快"而做裁剪与加速。
4. **工具（Tools）**：针对性更强，典型如 HTML 等 Web 专用工具链。

也就是说，Web 工程不是另起炉灶，而是在传统软件工程的骨架上，套了一层"快、持续、在线、不可控"的约束皮肤。

## 四、WebApp 的过程模型：增量式、持续演化、短周期

WebApp 的过程模型由两个驱动力决定：一是"为了快"，二是"持续演化（continuous evolution）"。网站不会说三五个月给你推一个新版本，它随时随地都在更新。因此**绝不能想着一步到位**，而必然采用 **incremental delivery（渐增式交付）**——一点一点交出来，变更是家常便饭，时间线（timeline）极短（short timeline）。

大多数情况下适用的就是 **incremental / agile process model**。其形态与之前讲过的迭代式过程模型一脉相承：

```
                 +-----------------------------+
                 |      Communication           |
                 |  (与用户/干系人持续沟通)      |
                 +-------------+---------------+
                               |
                               v
                 +-------------+---------------+
                 |   Requirements Analysis     |
                 |   需求分析(轻量、场景驱动)    |
                 +-------------+---------------+
                               |
                               v
                 +-------------+---------------+
                 |        Design               |
                 |   设计(布局/导航/内容建模)    |
                 +-------------+---------------+
                               |
                               v
        +-------------+  +-----+---------------+  +-------------+
        |  下一圈迭代   |  |   Construction        |  |   Testing   |
        | (回到沟通做   |  |  (构建 + 持续 Refactoring|  |  测试(上线前 |
        |  下一个增量)  |  |    重构内部结构,        |  |   充分自测) |
        +------+------+  |    追加新功能)          |  +-----+-------+
               ^         +-----------+-----------+        |
               |                     | 产出               v
               +---------------------+ 一个 increment(增量)
                                     (交付并立即投入演化)
```

每一圈迭代输出一个 increment（增量）；在 construction 阶段，还同时进行 **refactoring（重构）**——不断优化内部结构、追加新功能，新的增量就这样生长出来。需要特别警惕的是：重构是个"大坑"，动重构之前一定要想清楚、想周全，不能盲目下手（这点后续会再展开）。

## 五、动手之前的澄清清单：七问

团队在真正干活之前，最起码要把下面这些问题搞清楚。它们是把模糊的"做个网站"翻译成工程约束的关键：

1. **重要性 / 内容敏感度**：这个网站主页到底有多重要？内容敏感程度如何？给国防部做的、给全国高校学生公开访问的、还是只是课程内部自娱自乐的，敏感度天差地别。
2. **页面布局套路**：Page layout 最有效的大概是什么套路？是顶部横排 Menu、下方内容，还是一横栏加一竖栏？竖栏有人喜欢在左、有人喜欢在右。整体怎么排布要提前定。
3. **媒介选择**：用纯文字展示，还是用视频、音频、Flash 或其他形式？哪一种对目标效果最好？
4. **用户目标与耐心**：用户访问网站想干什么？他最多愿意几步操作完成？不同人群的容忍度完全不同。
5. **目标用户画像**：网站给谁做？给老年人做是一种风格，给大学老师做的是一种风格，给幼儿园小朋友做的是另一种风格。你能指望用户做到什么程度的操作？
6. **复杂度与导航**：网站有多复杂？页面导航（navigation）极其重要。内容多就要做 Search（搜索）或导航图（navigation map）。注册表单是典型矛盾：商家希望填的字段越多越好（多收集信息），但太多用户就没耐心填完、直接走人。measurement（度量）在这里非常微妙，要找到平衡点——别把人烦跑。
7. **无障碍与可访问性**：要不要照顾残疾人、做到无障碍访问（accessibility）？有没有可能做到？搜索功能要强大到什么程度？

这些问题不必在文档里写满，但团队脑子里必须清楚，否则做出来的东西会在真实使用中被打回。

## 六、WebApp 的分类练习：先会归类，才能设计

教材里给 WebApp 列了约十种类型（informational 信息型、customizable 可定制型、transaction-oriented 事务型等），课上用一道三问练习把"分类"变成一种工程直觉：

1. 整个支付宝项目属于哪一类？讲理由。
2. 你自己负责的模块具有 WebApp 特征吗？若是，属于哪一类；若不是，也要讲清为什么它不具有 WebApp 特点。
3. 从十种类型里挑两种，举出一两个著名网站，说明它干什么、有什么特点，所以它归到哪一类（比如 portal 门户类可举大量门户网站，interaction 交互类可举出更多实例）。

这道练习的用意在于：做这一行的人要多见多识广，先能准确归类，才知道该用哪套工程手法去应对。归类本身不是目的，而是让"特殊性"落到具体对象上。

## 七、最佳实践（Best Practices）

即便时间极紧，做得好的团队依然遵循一套被验证有效的做法：

- **先花时间搞清楚业务需求与产品目标**。大方向的时间不能省，细节可以慢来。方向错了，后面再快也是白做。
- **采用 scenario-based（基于场景）的方法**。很多网站开发的核心技巧，就是做一系列 user scenarios / use cases（用户场景、用例），再依据这一套用例去规划和开发。
- **仍然要有轻量级计划**。这里的 plan 与传统软件工程那种极其严格的计划不在一个数量级，是轻量级的，但你不能"完全没计划直接动手"，那会出大麻烦。
- **动手前稍微做一点建模（modeling）**。哪怕团队小、周期短，也要想到后期是**长期维护**的过程。讲师举了 ZOJ（Online Judge，ACM 竞赛同学熟悉的系统）的例子：系统最早 2001 年投入使用，2.0 版本 2008 年上线，到如今换了好几波学生，当年的开发团队早走光了。长期存活的系统（你当然不希望它只活几个月或两三年）必须有留给人看的文档与模型，可以写得简单，但必须有。
- **把控一致性与质量**。对内容、模型整体设计的一致性（consistency）和质量（quality）要有检查、有把握。
- **靠重用提速**。怎么做到快？尽可能找已经做好、可重用的模块。有学长毕业后开公司专门给老师做各种课程网站，因为专注教育这一个领域，沉淀出大量共性构件，后面越做越快——**快的根本在重用**，不在加班。
- **上线前充分自测**。绝不能把测试留给用户：心想"反正要上网，挂出去让这帮人一用 bug 就出来了"。一旦你把它交给用户、一上线哗一下崩了，至少一大半人不会再回来。所以上线前内部必须做好、做充分的测试。

需要点明的是：WebApp 的测试比普通软件测试**更难、更困难**，难点后续会专门讲。本讲先把"必须自测、且自测不简单"这条纪律立住。

## 八、小结

WebApp 之所以被单列成章，是因为它在网络依赖、浏览器差异、性能敏感、极短迭代、用户未知、持续演化、服务端安全、并发与不可预测负载、高可用这九个方面，系统性地不同于传统软件。工程化应对的框架仍是"质量焦点→敏捷过程→标准方法→Web 工具"的分层，过程模型必然走向增量式、持续演化、短周期、边构建边重构。动手前用七问清单澄清需求，遵循"先定方向、场景驱动、轻量计划、少量建模、重用提速、上线前自测"的最佳实践，才能把"快"和"好"同时拿到手。

## 随堂自测

**1. 为什么说 WebApp 的"并发 / 不可预测负载"属性在工程中极为致命？结合课上案例说明。**

解析：WebApp 上网后受众不可控，负载呈脉冲式、季节性波动（unpredictable load），且可能瞬间爆发大规模并发（concurrency）。课上奥运抢票案例：引进的国外软件仅能处理约每秒 5 个并发，而真实访问洪流远超此量级，开放瞬间即崩溃。这证明若按小规模人口量级设计容量，面对中国式访问热情会直接失效，因此并发与负载必须作为架构级约束来对待。

答案：因为 WebApp 受众不可控、负载脉冲化且可能瞬时海量并发，容量设计一旦低估就会在峰值直接崩溃（如奥运抢票网每秒 5 并发的设计被挤爆），所以必须把并发与负载当作架构级问题而非优化项。

**2. WebApp 的过程模型为什么必然采用 incremental / agile，而不是一步到位的瀑布模型？**

解析：两个驱动力——（1）为了快：WebApp 工期常以周计，无法承受冗长节奏；（2）持续演化：网站随时在更新，没有固定发版日，版本连续变化。因此绝不能一步到位，只能渐增式交付（incremental delivery），变更频繁、时间线极短，对应增量式 / 敏捷过程模型，每圈迭代产出一个 increment，构建中持续 refactoring。

答案：WebApp 工期极短且持续演化、无固定发版，注定要渐增式交付、频繁变更、短周期迭代，故采用 incremental/agile 过程模型而非一步到位的瀑布。

**3. 上线前充分自测对 WebApp 为何特别关键？它与"靠用户发现 bug"的思路差在哪里？**

解析：WebApp 用户未知且耐心有限（性能/体验差就走人）。若把测试留给用户、上线即崩溃，至少一大半人不会再回来，损失不可逆。而传统软件用户相对固定、可培训可监控，容错空间更大。因此 WebApp 必须在上线前做充分内部测试，且 WebApp 测试本身比普通软件更难。

答案：WebApp 用户陌生且易流失，上线即崩会永久失去大半用户；把测试推给用户等于用口碑赌运气。故必须上线前充分自测，且须正视 WebApp 测试比普通软件更难的客观事实。
