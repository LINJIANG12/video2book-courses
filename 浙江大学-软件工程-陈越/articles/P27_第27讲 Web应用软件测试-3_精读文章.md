# 第27讲 Web应用软件测试（三）：测试维度、固有困难与综合策略

Web 应用的测试同样是从质量度量维度出发，用以达成 Web 应用的质量目标。本讲在前两讲逐维度展开的基础上，回到整体视角：先列出测试覆盖的全部质量维度，再剖析 Web 测试相比传统软件测试的固有困难，之后给出一套"设计模型—测试活动"层层对应的策略，最后对内容/数据库、界面机制、导航语义、配置两端、安全攻防、性能负载等维度做纵深补充，其中不少细节是前两讲未及的。

## 一、质量维度总览：测试要覆盖什么

从质量度量出发，Web 应用测试至少应覆盖以下维度：

- **内容测试**：分语法与语义两层。语法关注拼写、连接等是否正确；语义关注表达是否准确，包括政治等敏感因素是否恰当、无恶意。
- **功能测试**：验证内容与需求一致，考察稳定性（有多少不稳定），并符合既定标准（如 Java、JSP 等规范）。
- **结构测试**：检验设计出的应用能否准确展现内容，是否可扩展，能否支持新内容随时更新。
- **可用性测试**：不同用户是否都能使用，能否借助导航的语法/语义快速学会并上手。
- **导航测试**：检查导航的语法与语义，重点防止死连接。
- **性能测试**：在各种配置（服务器端、客户端、硬件、浏览器）下的执行条件；以及在访问量突增等特殊情况下的反应速度。
- **兼容性测试**：各种客户端、各种终端、服务端都要测，突出问题是不同浏览器（IE 与其他浏览器）表现差异。
- **互操作性（interoperability）**：现代 Web 应用除访问页面外，常与大型数据库交互，需测其访问其他应用、数据库的界面是否有问题。
- **安全性**：找出弱点/易攻击性（vulnerability），尽早弥补，避免交付后被黑客攻击。

## 二、Web 测试的固有困难

Web 测试之所以比传统软件测试更难，根源于运行环境的开放与不可控，具体表现为四类困难：

1. **症状位置与根因位置分离**。客户端表现出的症状，未必是客户端自身的问题。例如用户页面加载不出来，很可能不是网页本身的错，而是网络下线、带宽不足。这正如人感冒发烧流鼻涕——流鼻涕看似鼻子的问题，实则深层原因是身体遭受病菌侵染。诊断时必须穿透表层症状找根因。

2. **环境不可复现**。传统软件测试的条件完全可控、可复现；而 Web 应用中，某错误只在某种配置或某种浏览器下出现，即便想原样复现，环境信息也极难还原，测试在技术上"不可重复、不可复制"。

3. **错误常由配置引起**。与传统软件由代码逻辑出错不同，Web 应用的许多错误来自不同配置。同一份代码在不同配置下表现迥异。

4. **错误跨越三个层面**。错误可能发生在客户端、服务器端、网络通信端三者之一，定位时须判断究竟落在哪一层。此外，错误来源还分静态的（与配置相关）与动态操作环境的（如瞬时资源负载量）。例如《中国好声音》开播瞬间大量用户同时访问，或退选时段负载骤增，都会引发错误。环境在 Web 架构中扮演极重要的角色，诊断错误时须高度重视。

## 三、分层测试策略与设计—测试映射

完整的 Web 测试策略按以下顺序推进：

1. 对**内容模型**严格检查，发现内容错误；
2. 对**界面模型**审查，确认所有用例均可完成——若全部用例能走通，基本问题不大；
3. 对**设计模型**审查，发现导航类错误（如死导航、点不进的死链接）；
4. 对**用户界面**测试，找内容展示、排版、导航机制的错误；
5. 选**构件**做单元测试（如导航单元的整体操作测试，类似传统功能测试）；
6. 对**整体架构/系统框架**做完整系统测试；
7. 在**不同环境、配置**下测兼容性；
8. **安全性测试**，找出易受攻击点，把隐患消灭在交付前；
9. **性能测试**，保证多用户登录下性能不受严重影响；
10. 最终由**终端用户**做可用性测试（先培训再控制执行）。

测试活动与各设计活动严格对应，这是本讲的核心脉络：

```
内容测试  ──对应──► 内容设计
界面测试  ──对应──► 界面设计 + 美学设计
导航测试  ──对应──► 导航设计 + 体系框架设计
构件测试  ──对应──► 构件设计
配置/性能/安全测试 ──横跨──► 上述全部（综合性维度）
```

内容测试与内容设计密不可分，界面测试与界面设计、美学设计紧密相关，导航测试与导航设计、体系框架设计相关，构件测试与构件设计密不可分。

## 四、内容测试与数据库测试的复杂性

内容测试要发现三类错误：

- **语法错误**：typo（排版/拼写错误），依据文本、文法、图表及其他表示形式检查；
- **语义错误**：信息的清晰度、完整程度，须精确表达，不出现二义、模棱两可或语义混淆；
- **结构错误**：内容最终展现给用户时，结构是否能合理反映内容。

**数据库测试**是内容测试中最复杂的部分。原因有四：

1. 客户端很少直接暴露 SQL（结构化查询语言），需在数据库管理系统（DBMS）间做跨平台翻译；
2. 数据库可能位于远端，Web 应用服务器需跨服务器存取；
3. 原始数据须尽快到达 Web 应用服务器再呈现给客户端，往往要做格式转换/格式化，动态内容对象亦需适当格式化以适合展示；
4. 逻辑上要与客户端交互。

其数据流动可用下图表示：

```
客户端(用户界面)
   ▲  HTML 脚本
   │
WebApp 服务器层  ──转换──► 用户数据
   ▲  SQL
   │
数据存储层(DBMS) ──原始数据访问──► 原始数据
```

因此每种数据都需单独测试并综合测试，复杂度正源于此。

## 五、界面机制测试

界面测试旨在发现形式错误，使界面特征满足设计原则与关键点。Web 应用以展示内容为主，视觉内容必须有吸引力，否则用户会迅速离开。

测试覆盖的界面机制包括：链接（Link）、表格、客户端脚本、动态 HTML、弹出窗口（弹出位置、大小、展示形式）、CGI 脚本（Common Gateway Interface，运行在 Web 服务器上的应用程序）、流动的动态内容、Cookie 等。特殊机制要专门测，例如电商购物车：最小装多少、最大装多少、一件未选就点结算是否显示金额为零、超出最大容量会怎样。

测试手法上：

- 对**导航语义单元（NSU，Navigation Semantic Unit）**做单元测试，如"购物""下订单"这类完整机制；
- 通过模仿用户操作设计用例；
- 测试特殊用户种类，类似第13章的集成测试；
- 测试整个界面，需引入人的测试以验证界面语义性，部分类似确认测试；
- 在不同环境（不同浏览器）下测访问服务器、后台数据库时的兼容性，类似配置测试目标。

## 六、导航测试的语法与语义

导航测试目标分语法与语义两层：

- **语法**：检查导航链接、重定向（redirect）、书签、框架（Frames）/框架集（Framesets）、网站地图、内部搜索引擎。
- **语义**：导航是否准确。

关于**重定向**：当网页地址被删除、更新或取消时，应给用户恰当提示，例如"网页已不存在或已删除"，并建议"按某键返回主页"，这属非常规但必要的处理。具体测试问题参见教材 23.6.2 节。

## 七、配置测试的两端细节

### 服务端

- 与服务器的兼容性；
- 系统文件、目录、相关系统数据库能否在运行时以标准方式正常创建；
- 安全测试：防火墙、加密（encryption）提高安全度的同时，**可能降低性能**，须评估是否会大幅明显降速；
- 分布式服务器上的配置方案；
- 与数据库软件的良好整合，注意不同数据库版本/平台/软件版本的敏感性异常；
- 服务端脚本能否正确运行；
- 系统管理员误操作是否影响运行；
- 代理服务器（Proxy Server）配置与不用代理时的差异。

### 客户端

- **硬件**：CPU、显卡 GPU、内存、打印设备等；
- **操作系统**：Windows、Linux、Mac OS X、手机端 Android 等都要实测；
- **浏览器**：IE（份额最大）、Mozilla Firefox、昔日流行的 Netscape（份额已极低）、Safari（苹果平板等）等，不能只测 IE；
- **界面构件**：ActiveX、Java Applets 等；
- **动态插件**：QuickTime、RealPlayer 等播放器及其他插件，须全面测试；
- **网络传输设备**：Cable、DSL、调制解调器（Modem，带宽约 56K）、T1 等。其中 DSL 含 HDSL、SDSL、ADSL、VDSL 等类型；T1 在美国制式为 1.544 Mbps，欧洲为 2.048 Mbps；更大的 T2、T3 中，T3 带宽约为 T1 的 28 倍，达 44 Mbps 级别。

## 八、安全测试：三个层面的攻防

安全脆弱性分布在三个层面：服务器管理层面、网络通信层面、客户端层面。课堂中通过模拟黑客手段来发现弱点——"一击即破"好过在运行中出事，因为可及时补救，否则给用户造成大损失。

**客户端脆弱性示例**（学生举证）：

- 木马注入客户端，监听并截获输入的账号密码——测试时应验证防监听机制，看能否截获刚输入的账号密码；
- 用 GET 传输指令或获取内容时，变量名显现在 URL 上，有经验的黑客可修改参数获取受限文件或他人隐私，进而影响服务器端（亦关联缓冲区溢出角度）。

客户端脆弱性常源于浏览器、email、通信软件上既存的 Bug，需跟踪找出并弥补。

**服务器端脆弱性**包括：拒绝访问攻击（DoS）、恶意脚本（malicious script）——恶意脚本由客户端传入，可使服务器操作瘫痪，产生大量隐患。

## 九、性能测试与负载模型

性能测试模拟现实复杂情况，核心是观察：服务器响应时间在何种并发/数据量下退化到不可接受；访问量猛增（如春运订票系统）时性能是否明显下降、让用户焦虑甚至愤怒；在某一 $N$ 值下，递交的交易数或数据负载何时变得不可接受；性能衰竭与哪个部件相关（如是服务器过少可增服，是带宽可升级）。

还要注意：高负载下系统安全性是否受影响；可靠性/可信度是否受影响；超过最大容量（如支付系统设定一万，测一万零一、一万零二）会发生什么——是直接瘫痪、不瘫痪还是性能死掉。

性能测试含**负载测试**（观察服务端环境应对不同负载的反应）与**压力测试**（不断加压直至满载甚至超限，看是否瘫痪）。

总负载量公式：

$$P = N \times T \times D$$

- $N$：并发用户数量；
- $T$：单位用户、单位时间递交的事务数量；
- $D$：每次递交的数据容量。

举例：某 NBA 东部决赛（热火队）直播页面，假定 2000 人观看，每人每两分钟递交一次评论（即每秒约 1/120），每次评论平均 3K，则：

$$P = 2000 \times \frac{1}{120} \times 3\text{K} \approx 500\text{KB/s}$$

意味着该体育网站必须达到约 500KB/s 的吞吐能力。类似地，网上支付系统（支付宝、天猫）在大促时订单与请求暴增，需分别评估 100 人、1 万人、100 万人下的平均反应时间。压力测试的具体问题见教材相关章节。

## 随堂自测

**1. Web 测试相比传统软件测试有哪四类固有困难？**

解析：①症状位置与根因位置分离（如页面加载不出可能是网络而非网页本身，类比感冒流鼻涕根因在病菌）；②环境不可复现（错误依赖特定配置/浏览器，难原样还原）；③错误常由配置引起（非纯代码逻辑）；④错误跨越客户端、服务器端、网络通信三个层面，且分静态配置与动态负载两类来源。

**2. 导航测试中关于"重定向（redirect）"应如何处理？其语法层还要检查哪些对象？**

解析：当网页地址被删除/更新/取消时，应给用户恰当提示（如"网页已不存在或已删除"并建议返回主页）。语法层还需检查：导航链接、书签、框架/框架集、网站地图、内部搜索引擎。

**3. 总负载量 $P = N \times T \times D$ 中三要素分别是什么？用 NBA 直播页案例说明其代入方式。**

解析：$N$ 为并发用户数，$T$ 为单位用户单位时间递交的事务数，$D$ 为每次事务数据量。案例中 $N=2000$ 人，每人每 2 分钟评论一次即 $T=1/120$ 次/秒，每次 $D=3K$，得 $P\approx 500\text{KB/s}$，即网站需具备该吞吐能力。
