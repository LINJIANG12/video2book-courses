# 软件系统设计（三）：体系结构设计报告的五个评审焦点

体系结构设计报告的价值，不在于给出某个标准答案，而在于通过真实案例暴露设计中**最典型的错误**并给出纠正方向。以下以一个"在线酒店／航班预订系统"的体系结构设计为实例，剖析架构评审中最常出现的五类问题。

## 一、架构设计报告应当怎么讲

报告与写文档不同：不是把 doc 文件从头念一遍，而是把最精华的东西讲出来。要点如下：

1. **背景与其他子系统关系**：简明介绍项目背景，以及本组在整个大系统里与其他组的关系；
2. **重点在体系结构设计（总体设计）**，包含两大部分：
   - **数据的体系结构**；
   - **系统的体系结构**；
   - 采用的 **pattern 或 style** 要重点介绍；
3. **用户界面设计**同步进行，也要讲；
4. 整体汇报效果（PPT 制作、演讲人表达）也在评分之列；
5. 评审方要打分并**提交评价**：哪些方面做得好值得借鉴、哪些是弱点。

最关键的呈现纪律：**先讲清本系统与其他子系统的关系和接口，再讲内部具体结构**。一上来就扎进内部细节，听众根本不知道你在哪。

## 二、案例背景：在线预订系统的子系统与接口

本例要设计的系统：用户在网页上流畅地查询、预订酒店和航班，并能反馈评价与评分。其内部划分为四个子模块：

| 模块 | 职责 |
| --- | --- |
| 查询模块 | 酒店/航班信息查询 |
| 订单处理模块 | 生成订单、改单、退单 |
| 登录模块 | 用户登录 |
| 后台管理模块 | 酒店/航班信息的增删改查、日志 |

跨组接口是设计中最易纠缠之处，厘清后如下：

```
   [用户浏览器]
        │
        ▼
   ┌──────────────┐   生成订单(表单)    ┌──────────────┐
   │ 第一组:订单   │ ─────────────────► │ 第二组:交易/  │
   │ 处理模块      │                     │ 订单管理      │
   └──────┬───────┘ ◄───────────────── └──────┬───────┘
          │   返回支付状态           新建订单条目│
          │                                      │ 需与
          │                                      ▼
          │                            ┌──────────────────┐
          │                            │ 第四组:用户账户   │
          │                            │ 管理(支付通信)    │
          ▼                            └──────────────────┘
   [第一组自己的数据库: 订单/评价]
```

流程：用户查到某酒店 → 选合适项生成订单 → 点"确认支付"跳转第二组交易模块 → 第二组新建订单条目 → 需与第四组（个人账户管理）通信完成支付 → 支付成功后调第二组管理接口把订单状态置为"已支付"。订单信息存放在第一组数据库，仅把订单号传给第二组。

此外：酒店/航班信息的维护（增删改查）由第一组后台管理模块负责；订单完成后用户对交易评价，反馈信息与评价文字存进第一组自己的数据库；用户信息与航班记录关联，需借用其他组提供的用户作为外键。

## 三、评审焦点一：先讲接口与边界，再讲内部

常见的错误是汇报时一上来就讲"订单处理模块调用第二组接口"，却没有先说清：本系统与交易处理平台到底是什么关系？需要对方提供什么？正确做法是先建立全局位置感：

> 先讲本系统与其他子系统之间的关系是什么、接口是什么；讲完大关系与大概情况，再讲内部结构如何组合。

这是架构呈现的黄金顺序：**边界优先，内部其次**。听众若不知道你在整个系统里的位置，听内部细节毫无意义。同理，讲到订单修改时必须确认"修改"究竟是"改变订单状态"还是"在原订单上改姓名/目的地"——因为第二组只提供了"改状态"接口，原订单内容修改其实是第一组自己做。接口职责若不厘清，跨组协作必然混乱。

## 四、评审焦点二：用 Archetype 找回面向对象

这是最常见也最严重的问题：需求分析阶段明明抽过类，但一进入架构设计就退化成 **流程（procedural）** 描述——"这里调一下、那里跳一下"，把面向对象整个抛掉了。

纠正方向：

- 系统对付的是**问题域的核心实体**，要搞清楚应用域（领域）内的实体是什么，它在实现中对应哪个 **Class** 来展现；
- 例如**酒店（Hotel）**、**航班（Flight）**，本身就应该是一个 Class；Class 除了属性信息，**还应有针对它的操作**，二者都要放进设计；
- 订单交易里最重要的就是**订单（Order）**——每个订单交易可看作一个 **Transaction（事务）**，也完全可以建模为一个 Class；
- 这些最核心的抽象，就是 **Archetypes**。需求分析时分析过的东西不能扔掉，要在架构里呈现。

一句话：**架构不是流程图，而是领域核心实体（类）及其关系图**。把"酒店、航班、订单"当作带属性与操作的类来设计，而不是只描述"用户点了查询 → 出结果"的过程。

## 五、评审焦点三：数据架构要自洽

数据体系结构是总体设计的两大组成部分之一。本系统的数据库分三张 SQL 表：航班/酒店一张、用户一张、后台管理员一张。E-R 图分航空模块、酒店模块、用户模块，关系为"航班与用户以下单日期为主键、用户 ID 共同作主键"。但此类设计常暴露几处不自洽：

1. **E-R 图未对齐 UI 呈现的信息**：界面上航班展示了航空公司、起飞等信息，但 ER 图的航班信息里**缺"航空公司（航班名字）"**这一项——图里有、表里没贴出来，必须对上；
2. **图片也是数据**：界面展示酒店内部照片，图片用文件存储、库里存 **URL**。这是数据的一部分，E-R 与表中应体现，不能"没体现出来"；
3. **后台操作日志表**要记管理员 ID（主键）、流水号、操作内容、操作日期时间，用于防止误操作、便于日后核查——这一块做到了；
4. **功能对应的数据要齐**：用户评价模块、用户推荐模块必然由本组完成，其数据也要落到自己的库里，不能只画"别人的接口箭头"而漏掉自己核心功能的数据。

核心原则：**界面上呈现的每一条信息，数据架构里都要有对应字段；反之，数据架构的每一项都要能在系统功能里找到落点**。

## 六、评审焦点四：核心内部模块必须凸显

常见缺陷是：结构图里大量箭头指向别的组（订单 → 第二组、支付 → 第四组），但**自己内部最核心的那条线却不清楚**：

> 大量箭头都是别人的东西在做，本组内部核心的这块反而不清楚、表达不出来。

真正应当被凸显的内部核心是**出错数据收集模块**。它把四种用户身份在查询时可能出现的各种出错信息汇总成一个列表，作为最后复核验收的标准，也供写代码时参考。具体涵盖：

- 搜索酒店无目的地或酒店名；
- 机票无指定目的地/出发地，或出发地目的地重合；
- 预订时搜索结果显示"查询结果不存在"；
- 真正预订时信息填写不完整；
- 给酒店评分时出现负数星格；
- 管理员搜索/修改时信息不完整；
- 以及留作后续发现的故障，记入故障日志。

这条核心线必须在一张架构图里被一眼看到，而不是淹没在对外接口中。

## 七、评审焦点五：B/S 架构要交代端侧与通信

既然系统基于 B/S（浏览器/服务器）模式，界面本身就是 B 端、C 端的系统。架构图里至少要交代：

- **后台 server 端**是怎样的；
- **B 端**是什么、**移动端**是什么系统；
- 它们之间**通信机制**如何存在。

本系统做得对的一点：管理员页面和主查询页**分开**——管理员页是单独链接、客户不能直接访问，只有管理员知道地址；主查询页面向客户。但仅有"页面长什么样"不够，架构层面必须说明各端归属与互通方式。

补充的界面事实（作为数据/界面设计的落点）：全站共 8 个界面，用 CSS 样式；主查询页含日历酒店、机票、按目的地+日期搜索框、打折酒店推荐、banner 广告区；酒店查询页支持按标准筛选排序、显示价格与用户评价（星级）、右侧广告；机票页按起飞时间/价格排序、显示准点率与目的地热门酒店推荐；详情页展示星级、地址、照片、下单与评价；后台按酒店 ID 查询并表格内修改提交。

## 八、随堂自测

**1. 架构汇报时，为什么必须先讲"系统与其他子系统的关系和接口"，再讲内部结构？**

**解析**：听众（其他组）不熟悉你的模块，只有先知道你在整个大系统里的位置、与谁交互、接口是什么，才能理解后续内部细节。先扎进内部细节，听众会完全迷失。这也是 ACD（语境图）必须先做的原因。
**答案**：边界与接口是理解内部的前提；先建立全局位置感，内部细节才有意义，否则听众无法定位。

**2. 把订单系统讲成"查询 → 出结果 → 支付"的流程，属于抛掉了面向对象。正确的做法应如何在架构中呈现"订单"？**

**解析**：订单是问题域核心实体，应建模为一个 Class（或 Archetype）——订单（Order）除属性（订单号、状态、目的地等）外还带有操作（生成、改状态、改内容）。每个订单交易也可视为一个 Transaction 事务类。架构应呈现这些核心类及其关系，而非仅描述过程流程。
**答案**：把订单作为带属性与操作的类（Archetype）呈现，体现领域核心实体及其关系，而非只画流程。

**3. 某设计的 E-R 图被判为"未对齐 UI 信息"，具体漏了什么？这违反了数据架构的哪条原则？**

**解析**：界面航班展示了航空公司/航班名，但 ER 图航班信息缺"航空公司"项；另外图片存为 URL 也应在表中体现却没体现。这违反了"界面呈现的每条信息，数据架构都要有对应字段；数据每一项也要在功能里找到落点"的自洽原则。
**答案**：漏了航空公司（航班名）字段与图片 URL 字段；违反"E-R/表结构必须与 UI 呈现信息一一对齐"的自洽原则。
