# 软件系统设计（二）：体系结构映射、构件分工与设计评审

上一讲收尾于体系结构语境图（ACD）的画法。本讲先用一个完整实例把 ACD 与 archetype（原型类）讲透，再讨论如何避免"一孔之见"、如何用权衡分析（trade-off analysis）从多个候选架构中选出最合适的，继而给出从数据流图到调用-返回结构的映射方法（Transform / Transaction mapping），最后落到分工策略与架构评审的实战要求。

## 一、语境图实例：SafeHome 保安系统

教材以家居保安系统 **SafeHome security** 为例。其核心模块被抽取为 **security function**——专门负责安全保卫相关功能处理的核心组件。把它的 ACD 画出来：

```
        [SafeHome product]   [Internet-based system]
              │ used by            │ used by
              └─────────┬──────────┘
                        ▼
                 ┌──────────────────┐
                 │ security function│  ← Target System
                 └───┬──────────┬───┘
        depends on   │          │ peers with
              ┌──────▼──┐   ┌────▼─────────┐
              │ sensors │   │ surveillance │
              │ (探头)  │   │ function(监控)│
              └─────────┘   └──────────────┘
       actors: [control panel]   [homeowner]
```

- **上级（Superordinate）**：整个 SafeHome 产品（product 模块）要调用它；基于 Internet 的远程操控系统（Internet-based system）也要调用它；
- **下级（Subordinate）**：security 模块直接调用 **sensors（传感器/探头）**，从中获取信息；
- **同级（Peer）**：**surveillance function（监控功能）**——一个做行为处理、一个做监控，二者互相调用，是 peer-to-peer 关系；
- **参与者（Actors）**：**control panel（控制面板）**与 **homeowner（房主）**。这里有个细节值得玩味：房主一般通过控制面板来操纵 security function，因此画了 control panel 作 actor；但 homeowner 又被画成一个**直接**的 actor，意味着 security function 还留有一个接口，允许房主**不经过控制面板**直接操控它。

做 presentation 时第一件事就必须讲清这种上下文：你的系统在支付宝大系统里处于什么位置？你们组和其他四个组是什么关系？

## 二、抽取 Archetype（原型类）

做完 ACD，第二件事是抽取 **archetype**。用面向对象眼光看，archetype 本质上就是一个 `class`——但系统细化后会有几十个 class，能被称为 archetype 的，是那些**最核心、最关键、至关重要**的几大类。要抽取的是最有代表性、最重要的少数 class，并描述清楚它们之间的关系，而非把几十个 class 全堆上来。之后再把 archetype 逐层细化。

教材以 SafeHome 为例给出极好的示范（Figure 10.8 与 10.9）：展示如何从一个大的抽象 archetype（如 safe）出发，不断细化、再实例化。archetype 也是架构报告必须包含的内容之一。

## 三、避免一孔之见：权衡分析（Trade-off Analysis）

设计最忌"一根筋"、患上隧道视野（tunnel vision）。好设计不应只有一种视角——要考虑多种可能性，再选一个对达成目标最有效、最合适的架构。怎么评判"有效"？教材给出的方法是 **trade-off analysis（权衡分析）**。"trade-off"难译，大约是"有得必有失"——把得与失如何平衡分析清楚。

方法流程：

1. 从 scenarios、requirements 等出发；
2. 提出**几种不同风格**的架构设计方案（如同盖楼，是先评估"江南风""摩天大楼"还是别的风格）；
3. 给出几种不同的 architectural styles / patterns；
4. **对每一个 quality attribute，单独评估每种风格**（关键步骤）；
5. 综合权衡，选定方案。

**第 4 步是核心**。quality attributes 取决于你要做的东西什么最重要——例如支付宝，**reliability（可靠性）**与 **security（安全性）**必然重要，此外还有 **performance（性能）**、**portability（可移植性）**等。针对每个性质，仔细分析某一种 architectural style / pattern 在该性质上表现如何。像"可靠性"听上去是个虚词，但必须落到具体评估上。

## 四、从数据流到结构：Transform 与 Transaction 映射

当需求以数据流图（DFD）形式给出时，可把它**机械地**映射成调用-返回结构。两种典型映射：

### 4.1 Transform Mapping（变换映射）

系统呈现"输入流 → 变换中心 → 输出流"的形态：

```
     输入流            变换中心            输出流
  [输入A]→[输入B] → [Transform Center] → [输出C]→[输出D]
```

映射为调用-返回结构时，主模块下辖输入处理、变换中心、输出处理等分支。

### 4.2 Transaction Mapping（事务映射）

系统呈现"一个入口，按事务类型分发到不同处理路径"的形态，中间有一个 **Transaction Center（事务中心）**，每条路径本身又是一个小的 **IPO（输入-处理-输出）**模式：

```
           输入
            │
     ┌──────▼─────────┐
     │ Transaction    │
     │ Center         │
     └──┬─────┬──────┬┘
       ▼     ▼      ▼
      P1     P2     P3      ← 每条路径各是一个 IPO 子结构
    (IPO)  (IPO)   (IPO)
```

两种模式常**套在一起**：一个大型复杂系统的不同局部具有不同特点，局部展开时往往"外层事务、内层变换"或反之。拿到机械生成的初版结构后，还必须**人工调整**——让它宽度、深度更合理。机械映射常得出"太宽"的结构（一层排开几十个模块、未对齐），需要人为优化。

## 五、分工策略：水平切分与垂直切分

架构定下后，要把模块分给不同小组。两种基本分工风格：

- **水平切分（Horizontal）**：若系统有明确、相对独立的功能，则"一个功能对应一个分支，一个功能归一个组"。这是本课程主要的分工方式——把系统面上分成五大功能模块，按功能横着分。
- **垂直切分（Vertical）**：若系统层次感极强——底层是支持、上层是决策，下面干活、上面领导做决策——则可竖着分，把一个分支整体分给一组。

在充分庞大复杂的系统里，不可能只用一个风格。通常**纵横交错**：先竖切把分支分给各组，各组内部再自行横切或竖切。

无论怎么分工，架构设计的总目标要落到几点：

- **方便测试、方便维护**：测试方式直接关联后续维护队伍；
- 要方便测试、维护，意味着 **fan-out 不要太多**（避免低内聚、集成测试痛苦）；
- 要限制**副作用传播（side effects propagation）**——一个模块出错不要波及太广，意味着 **fan-in 不要太多**（否则牵一发而动全身）；
- 系统要**灵活、易扩展**：将来加功能应尽量容易。

这些具体如何做到，有一门"软件系统架构"选修课专门讲解。此刻要建立起的概念是：**设计是给人用的，不是只交给你 TA 看的**。

## 六、架构评审实战：5 分钟 Presentation

架构设计最终要在 22 号的 presentation 上展示，每组 **5 分钟**。一个常见误区是以为"5 分钟很容易"——恰好相反。**50 分钟比 5 分钟容易做**：长报告时间弹性大，可多讲可少讲、语速可调；5 分钟毫无弹性，还要把一件事讲清楚，是极有挑战的任务。

你面对的不是本组人（他们已很熟），而是**其他组、不熟悉你模块的人**。要在 5 分钟内让另外 4 个组都听懂你打算怎么做，并能提出意见——若接口设计明显有误，别人还要当场指出。presentation 不仅是打分，更是全班协调沟通的契机。

**时间规划经验**：

- 把要讲的内容先铺好，按时间点规划——共 5 个点，每点讲到什么位置要清楚；
- 按重要程度分配时间：重要的花 2 分钟细讲，不重要的 10 秒内三言两语带过；不够则两分半；
- 给自己设几个时间点，台上台下配合——到某页 PPT 时台下"咚"一下提示；
- 全场共 10 组、90 分钟，分秒必争，超时即扣分。讲者会带小铃铛，4 分钟时"叮当"提醒"最后一分钟"，超时开打扣分。

**打分表（grading table）与常见误区**：

- 打分表里有一条叫 "style"，指**演讲风格**（不是 architectural style）；超时扣分落在该项；
- 学长学姐最常犯的错误：**没看打分表里有哪些打分项就开讲**。打分项即"我要求看到的内容"，是最基本的。常见惨剧：刚做完 architectural style 论文、特别兴奋，讲了三分半还在讲 style，结果该打分的 ACD 没做、archetype 不知道，草草讲完 architecture 就下台——这些项全零分；
- 必须先讲清打分表要求的**（1）ACD、（2）archetype、（3）architecture** 等基础项，有余力再讲额外内容。

**同行评审规则与做人道理**：

- 每组自带 9 张 grading table 给其他 9 组；除打分外**必须写清理由**——优点写清好在哪，扣分写清凭什么扣、扣在何处几分，满分也要写足理由；
- TA 算分时：9 个组打分去掉最高最低取平均；老师打分占 **50% 权重**，与同行平均分合计得初分；最终成绩由 TA 给；
- TA 还会看你对同行评审是否认真——这反映你对同行劳动的尊重程度。你充分尊重别人，别人未必尊重你；你不尊重别人，别人肯定不尊重你；
- 分数不能算错。若你给别人少算 2 分或多算 2 分，都从**你自己的总分里扣 2 分**。你希望别人严肃对待你，也要严肃对待别人。

## 七、随堂自测

**1. 在 SafeHome 的 ACD 中，homeowner 被同时画为 actor，且 security function 还留有一个"不经控制面板直接操控"的接口。这反映了 ACD 中 actor 描述的什么含义？**

**解析**：Actor 指"扮演使用者角色、用目标系统完成某任务的实体"。房主通常经 control panel 调用 security function（control panel 作 actor），但系统另留直控接口，使 homeowner 也可不经面板直接操控，故 homeowner 也被画为 actor。这说明 actor 描述的是"谁在使用系统"，且同一使用者可能通过多条路径（不同接口）成为 actor。
**答案**：actor 表示使用目标系统的角色；homeowner 既可经面板、也可经直控接口使用系统，故被列为 actor，体现使用路径的多样性。

**2. 用 trade-off analysis 评估架构时，为什么说"对每种 quality attribute 单独评估每种风格"是关键步骤？以支付宝为例说明。**

**解析**：trade-off 是有得有失的权衡。流程先提数种风格，再对 reliability、security、performance、portability 等 quality attributes 逐一评估每种风格的表现。支付宝最看重 reliability 与 security，若某风格安全性好但可移植性差，需就具体属性逐项打分比较，才能选出最契合目标的架构，而非凭整体印象拍脑袋。
**答案**：因不同架构在各质量属性上优劣不同，必须按属性逐项评估（如支付宝重可靠性与安全性），才能量化权衡、选出最合适方案。

**3. Transaction mapping 与 Transform mapping 在结构形态上有何区别？为何说二者常套在一起？**

**解析**：Transform mapping 是"输入流→变换中心→输出流"的线性变换形态；Transaction mapping 是入口经 Transaction Center 按类型分发到多条 IPO 路径。大型复杂系统的不同局部常具不同特点——外层可能是事务分发、内层各路径又是变换处理，或反之，故两种模式常嵌套使用。
**答案**：Transform 为线性变换中心结构，Transaction 为事务中心分发多路径；复杂系统局部特征不同，故二者常嵌套组合。
