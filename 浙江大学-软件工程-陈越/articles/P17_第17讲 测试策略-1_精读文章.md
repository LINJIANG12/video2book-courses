# 第17讲 测试策略（一）：从验证/确认到分层测试战略

## 一、为什么测试至关重要：两个历史教训

测试不是收尾才想起的环节。即便设计尚未通过最终验收，测试计划（Test Plan）就该同步启动——先看战略（整体策略、分层、自顶向下还是自底向上、有哪些测试类型），再在下一讲看每个阶段具体用什么技术。两个著名事故足以说明"测试不完备"的代价。

**事故一：1963 年火星火箭，1000 万美元的逗号。** 一段 Fortran 程序中本应是一个循环：

```fortran
      DO 5 I = 1, 3
C        ...循环体...
   5  CONTINUE
```

Fortran 用标号区（语句前若干字符）标识循环结束行，标号为 `5` 表示循环体到此结束；C 语言里等价写法是 `for (i = 1; i <= 3; i++)`。问题出在转录环节：程序员写好之后，复印件上那个逗号（`,`）模糊得像小数点（`.`），敲代码的人把它敲成了：

```fortran
      DO 5 I = 1.3
```

于是 `DO 5 I = 1.3` 不再是一个循环，而被编译器理解为一个赋值语句 `I = 1.3`。当年的 Fortran 编译器诊断不出这个语义偏差，程序"正确"地执行了，火箭随之失败，损失 1000 万美元（1963 年的 1000 万）。根因正是测试时没仔细核对循环体的结构。

**事故二：飞机导航，159 条人命毁于"一致性测试"缺失。** 一架装有自动导航系统的飞机，机长过去用纸质地图飞行，地图上用字母 `Cali` 代表目的地 Cali。他习惯性地把字符输进导航系统，却不知道在该系统里这个字母对应的是反方向的 `Bogota`。飞机直接撞山，159 人遇难（163 减 4）。地面导航员虽发现方向不对，却用了一句委婉的话："我建议你以比较直接的方式飞向你的目的地"，机组没听懂，等反应过来山已在眼前。

这起悲剧给测试留下明确教训：少做了一项**一致性测试（consistency test）**。设计自动导航系统时本该分析用户画像（user profile）——飞行员在没用你系统前怎么工作、习惯用什么符号。若把字符约定设计得与旧地图一致，错误可避免。该测的没测，正是测试人员的责任。

## 二、测试的根本立场与目的

一个必须刻进骨子里的认知：**测试是为了发现问题（for finding errors），而不是为了证明软件正确。**

这绝非废话。初学者写测试报告时常犯的典型错误是：列几个极简单的 case，然后宣布"这些 case 都过了，所以程序是对的"。这种测试的立场站错了——你站到了程序员同一阵营，去"保护"他。正确立场是**站到程序员的对立面，想方设法去破坏它**。想尽一切办法都破坏不了，才是对开发者最大的帮助。公司里测试员的奖金也按"找到更多错误"发放，而非按"证明程序没错"发放。什么错误都没测出来，只说明你的测试太弱，并不说明软件没有错。

## 三、测试团队的交付物（Test Deliverables）

测试团队最终必须交付的东西，远不止一份 bug 清单：

1. **Bug 清单**：列出发现的所有缺陷；
2. **测试用例表（Test Cases）**：每一行包含用例、期望输出（expected output）、实际输出（actual output）、状态（status：相符 / pending / corrected 等）。不相符合即是一个 bug；
3. **需求符合度（Requirements conformance）**：每个功能单独看都对，合到一起未必是需求规格里描述的软件，必须对照需求逐项检查；
4. **性能指标（Performance）**：对安全性、效率等有要求的，逐一核对；
5. **质量指标（Indication of quality）**：综合以上给出总体质量评价。

换言之，测试团队交付的是"错误清单 + 用例与结果 + 需求符合度 + 性能 + 质量总评"，而不是单单一纸 bug 列表。

## 四、验证与确认（Verification & Validation）

验证与确认是测试团队要完成的两件事，字典里中文都译作"验证"，但二者有微妙差别：

| 概念 | 英文问题 | 关注点 |
| --- | --- | --- |
| 验证 | Are we building the product **right**? | 每个模块是否以正确的方式实现、功能是否正确 |
| 确认 | Are we building the **right** product? | 各模块拼起来，是否就是需求想要的那个软件 |

验证（Verification）检查每一个模块功能的正确性；确认（Validation）检查所有正确模块组装后，整体是否就是你要的软件——"每一个功能都正确，放在一起却不是你要的软件"这类问题，由确认阶段把关。一幅漫画很传神：一个人画的眉毛、眼睛、鼻子、嘴，单看每一个都是美人的形状，放一起却不是一张人脸，因为位置全错了。验证保证每个器官都漂亮，确认保证它们拼成一张人脸。这两步是 SQA（Software Quality Assurance，软件质量保证）团队最关注的两个环节。

需要澄清一个观念：**软件测试只是 SQA 的一个要素（Software testing is only one element of SQA）**，测试不是 SQA 的全部。质量必须内建于开发过程之中（*Quality must be built into the development process. One cannot use testing to add quality after the fact.*）。若管理流程的每一环都没有质量监控，却指望最后靠测试团队兜底，既不公平也不现实——过程本身不合规，软件质量从一开始就被注定高不了。

## 五、测试与调试的区别

- **测试（Testing）**：发现错误，给出"哪里有错"的报告；
- **调试（Debugging）**：改正错误的过程。

两者是不同策略：测试只负责定位错误，调试负责把错误改掉。一般不是测试团队来做调试，改错仍由开发者完成。

## 六、分层测试策略

### 6.1 测试从小到大地展开

真正执行测试从 component（构件）开始：程序员先对自己做的 component 做单元测试（unit testing），提交后从 component 层向 integration（集成）、再向 system（系统）逐级完成。不同时间点采用的技术不同——单元测试一般用**白盒测试**，集成与系统测试一般用**黑盒测试**。白盒要细到什么程度、有哪几种逻辑覆盖，留待下一讲。

### 6.2 传统软件架构的四部曲

传统结构化架构的测试，思路清晰，分四步：

1. **单元测试（Unit Testing）**：一个 component 一个 component 地测。每个 component 下又分更小的 component，各自完成单元测试；
2. **集成测试（Integration Testing）**：把 component 逐步集成。每集成一步都要做一次验证——新集成进来的功能是否正确，集成后整块功能是否仍正确；
3. **确认测试 / 验收测试（Validation Testing）**：所有东西做好后，对照需求规格说明书里的**验收标准（Validation Criteria）**——功能、性能及其他标准逐条测。标准写明"达到即付钱"；
4. **系统测试（System Testing）**：安装、调试到目标大环境下，做整体系统测试。

```
单元测试 → 集成测试(每步验证) → 确认测试(对照验收标准) → 系统测试(装入真实环境)
```

### 6.3 面向对象（OO）架构带来的测试挑战

OO 刚流行时被捧得"什么都好"，但它绝不完美，最麻烦的正是测试。OO 把系统理解为对象及其相互作用，不是结构化的东西，关系网极难测全。

- **单元测试 = 测一个类（Class）**：一个 class 就是一个 unit / component，但测一个 class 与测一个功能模块复杂度不在一个量级；
- **集成测试尤其复杂**：要把 class 与 class 之间的关系尽可能覆盖清楚。若想做完全测试、穷举所有排列组合，会"测死"——根本测不完，必须在有限时间内用技巧抓住主要关系；
- **系统测试**：按某种方式整体对照 Requirements 测效果。

## 七、谁来测：测试团队的组织与误区

参与测试至少有两种人：写程序的人自己，以及不写你程序的独立测试人员。两类各有优劣。

**开发者自测。** 优点：程序是自己写的，对内部结构极清楚，不需花时间理解就能针对性地快速设计用例。局限同样明显：程序员多少有点骄傲，一旦 submit 就默认"我测过了、没问题"；且测试不过要改、超 deadline 会扣奖金，受利益驱使，他不太会严格测自己的东西。

**盲点与结对编程。** 每个人都有盲点——自己死活看不出的错，换个人一眼就见。一个真实例子：有位同学信心满满重构，结果掉进坑里，bug 查到想放弃、要给自己放一周假。建议是找另一个人**结对编程（pair programming）**一起查：两人坐一起，写的人讲"这块在干什么"，共同往下看。一周后两人都兴奋——各种错误被揪出。因为两人盲点完全重合的概率很小。卡住时代价最小的解法：请朋友吃顿饭，两人坐一起看，什么都看得出来。

**独立测试组（ITG，Independent Test Group）。** 缺点是要多花时间、多花钱（付人家工时）。但因其 independent，利益与开发者对立；若"抓到多少 bug 给多少奖金"，便会全力找 bug，质量保障效果更好。

需避免三个误区：

- **误区一："Developer should do no testing at all"（开发者根本不该测）**——错。起码前期的单元测试和初期集成，开发者必须参与；进入集成阶段 ITG 进来后双方密切合作，到系统测试才逐步由 ITG 接手；
- **误区二："Software 可以 tossed over the wall（丢过墙就不管）"**——错。开发者 submit 后就说"是测试团队的事、没我事了"不成立。发现错误仍要开发者来改，调试一般不由测试团队做；
- **误区三："Testers are not involved until it is time to be tested（代码没写出来测试员就闲着）"**——错。理论上设计尚未验收、代码还没写，但**测试计划今天就能做**。测试团队从需求分析（Analysis）阶段就该旁观，了解成型的全过程，才能摸清最薄弱、最易错的环节；拿到设计（Design）即可针对设计做测试计划：测哪几个环节、重点测哪些部分。

## 八、何时结束测试（When are we done?）

理想主义答案：**Never（永远没头）**。对于充分复杂的系统，穷尽测试（exhaustive testing）不可能；既然不能穷尽，就永远不敢说软件里没有 bug。越牛的程序员越爱说"我做的东西不会坏"——这是很不成熟的表现，因为你没做过完备测试，凭什么打包票？一个错误都没测出来，只能说明可能程序质量真强，也可能说明你测得太弱。

现实角度：**When you run out of time, or you run out of money**——要么没时间，要么没钱，大家就不测了、交出去"先用着吧"。必须记住最根本的观念：测试只是发现错误的过程，永远不能证明软件没有错误。

## 九、可量化的测试过程与测试计划要素

### 9.1 以可量化的方式（quantifiable manner）定义目标

*Specify product requirements in a quantifiable manner before testing starts.* 需求规格里的验收标准尽可能量化成一系列指标，达到指标即如何。测试过程本身也要量化。

一个讨论题：老板想知道"测试进行到什么程度"，有公司报告"已找到 90% 的 bug"——可 90% 怎么来？你都不知道 bug 总数，凭什么算出 90%？必然是毛估，但毛估也要有依据，不能说拍脑门"我已测完 90%"。量化"测试完成 90%"的方法不唯一，例如一家日本公司的做法：根据经验预先**植入 N 个错误**到软件，交给测试人员测；每周错误清单里看植入错误被找出多少。若植入错误 90% 被找到，就说测试完成了 90%。这法子有趣，但成本高、也有风险——植入的错误是否"干净"、会不会影响软件，你未必有把握。总之方法很多，关键在量化的思路。

### 9.2 测试计划的其他要素

- **明确测试目标（testing objectives）**：要测什么逐个写清。例如测可用性，就列清可用性包含哪几个功能；测性能，列清是哪几个点、测到什么指标；
- **识别用户类别与画像（Identify categories of users and develop a profile for each）**：用户群分几类，每类写 profile，目的是测试时模拟用户习惯去用软件。前文飞机导航悲剧，正是没认真做这件事；
- **快速迭代（rapid cycle）**：采用"功能加进来就测一下"的递增、迭代式流程，而非一次性想测完整再总结；
- **构建可自测的健壮软件（Build robust software that is designed to test itself）**：软件设计时要考虑各种异常、自带异常处理、抛出有用异常信息，让他人看到信息就知道走了哪条路。动不动就"蓝屏"的软件没法测下去；
- **用正式评审作过滤器（formal reviews as a filter）**：正式跑代码前，先让开发者讲一遍程序从上怎么走、几个分支怎么走，一帮人听，相当于在抽象层面帮你测、过滤掉大部分关键错误，大面过了再去看实现细节。

## 十、随堂自测

**题 1：** 验证（Verification）与确认（Validation）的区别是什么？请用本讲的两个英文问句概括，并说明飞机导航事故主要缺了哪一类测试。

> **解析与答案：** 验证回答 "Are we building the product right?"，关注每个模块功能是否正确；确认回答 "Are we building the right product?"，关注拼起来是否就是需求想要的软件。飞机事故根因是缺了**一致性测试（属于验证/确认中对用户习惯与符号约定一致性的核对）**——导航系统字符约定与飞行员旧地图不一致却没测出，导致输入被误解。依据见第一、四节。

**题 2：** "开发者根本不该做测试"与"软件写完直接丢过墙给测试团队"这两种说法分别错在哪里？

> **解析与答案：** 前者错在：起码单元测试和初期集成开发者必须参与，进入集成后 ITG 才逐步接手；后者错在：发现错误后仍由开发者改（调试一般不由测试团队做），开发者不能 submit 后就撒手。两者都违背了"开发者与测试团队协作"的原则。依据见第七节三个误区。

**题 3：** 为什么说"测试永远不能证明软件没有错误"？实践中测试在何时终止？

> **解析与答案：** 因为对复杂系统做穷尽测试不可能，既然不能穷尽，就永远不敢断言内部无 bug；一个错误都没测出，只可能说明程序强或测试弱，而非软件无错。实践终止条件是 **run out of time, or run out of money**（没时间或没钱）。依据见第八节。
