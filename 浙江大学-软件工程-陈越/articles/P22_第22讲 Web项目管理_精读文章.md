# 第22讲 Web 项目管理：从启动一个 Web 项目到组建团队与管控风险

把 Web 应用当成一个 project 来运转时，要考虑的事情与传统软件项目管理同源，但节奏、角色与风险点都有 Web 自己的特征。本讲先讲项目如何"启动"（initiating）与"规划"（formulation），再讲需求澄清必须覆盖的三问与两类目标，接着落到团队角色构成、计划对照表、外包与自制的差异，最后给出最坏实践清单。具体怎么做需求建模、怎么做设计，留到后面几次课。

## 一、启动与规划：formulation 阶段到底要做什么

项目第一步叫 **initiating（启动）**，随后进入 **formulation**——词典里没有特别贴切的中文对应词，大体意思是"先大概规划一下"，一直做到你拿到一个"大致的需求"为止。

课上用一个应征场景把这个过程具象化：老师说"我要给软件工程课重做一个课程网站"，在"酒吧里贴帖征人做网站"，你来应征。你找到我、跟我谈、向我提问，直到把需求大致搞清楚——这个从应征者上门到需求初定的过程，就是 formulation。

### 1.1 提问的顺序就是能力

应征者要列一串问题，而且问题有先后。先问什么、再问什么，得到的答案和效果完全不同。"问"本身是一门技术：信息只有"做课程网站"这一句话时，千头万绪要先排好序。有人第一冲动就想问"有钱没得"，但这句话不好听，而且你本应能自己推导出来对方出不出钱。

### 1.2 第一问：identification of business need

最先要搞清楚的是 **business need（业务需求）**：你为什么要做这个网站？

- 是为了申请报奖？
- 是为了申请教育部的项目？
- 是学校硬性要求？
- 还是自己吃饱撑了想做一个？

这直接决定了你愿意为它付多少代价。如果是"自己玩玩"，就别指望对方掏十万二十万；如果是申报项目，预算与严肃程度完全不同。紧接着要弄明白 **objectives（目标）**：网站到底干嘛用？一门课程网站形态很多——只是把课件放上去方便下载？还是专门放课外参考资料供下载？要不要组织论坛？要不要布置作业？要不要保留原来的打分功能？

### 1.3 一个真实的反面教材：少问一句"给谁用"

老师讲了自己课程网站的血泪教训：当年做网站的学长（同时是老师的 TA）默认网站是"给老师一个人用的"，于是系统里只有单一用户，其他老师都用不了。老师以为"用课程组的钱请人做，显然给整个课程组五六个老师用"；学长以为"给 TA 提供方便的打分、收集、统计工具，显然给自己做"。双方都觉得"显然"，谁都没说破那句话，结果做成了单人版。等后来要改成多用户时，原设计极难改、非常麻烦。

教训很清楚：**major features and functions（主要功能）、目标用户、使用范围，必须在 formulation 阶段用一句话对齐，否则后期返工成本极高。**

### 1.4 必须覆盖的三问与抽取的两类目标

无论你怎么问，最终问题清单必须覆盖三个最关键方面：

1. **用户为什么要做这件事**（动机 / business need）；
2. **他想要做成哪些事**（目标与功能）；
3. **做好了以后谁来用**（最终用户是谁）。

漏掉任何一个，问题都不全面。

从用户的回答里，要抽取出两大类信息：

- **information goals（信息目标）**：网站要提供哪些内容、数据，以什么形式展现——这是与"数据"相关的；
- **obligative goals（义务/功能目标）**：有哪些任务可以通过网站完成——这是与"功能"相关的。

一类是数据，一类是功能，formulation 阶段就要把这两者剥出来。

## 二、需求收集：user categories 是 Web 项目的命门

需求收集（requirements gathering）里，有一件事对 Web 应用特别重要、比对传统软件重要得多——**user categories（用户类别）**。

你要给每类用户写详细描述，描述不只包括"他用网站干什么"（objectives），还要包括：

- 他的 **background（背景）**：教育程度、识字还是不识字、属于哪类人；
- 他的 **习惯**：年龄段（如面对 90 后年轻人），平时熟悉的网络环境是什么样，由此决定界面风格；
- 他在 **什么场合、什么情况下** 来用你的软件；
- 这群人 **特别喜欢什么、特别讨厌什么**。

风格必须匹配人群：给幼儿园小朋友做的东西，用蓝黑稳重色调会让他们觉得没劲，应该是花花绿绿、文字极少、动画图片多、拿手去点去戳就能用；而把这种风格搬到一个银行网站上就荒谬了。所以"面向什么人群"必须先做分析。

沟通（communication）有多种手段：

- 对传统人群：开会、面对面谈；
- 邮件（email）；
- 发调查问卷（survey）到特定用户群。

如果你有一个 great idea、要做没人做过的网站，前期关键工作是设计问卷去校园里拦截"同学打扰两分钟帮我填一下"，采集足够多数据，才能看清在用户心目中这类 service 应该是什么样子。

沟通的核心产出是 **scenario-building（用户脚本）**：在脑子里成形"这群人怎么用你的东西最有吸引力、最好用"。随后做分析，从五花八门的信息里抽取出：

- **content objects（内容对象）**：数据、输入输出、要展示的东西；
- **operations（操作）**：有哪些操作要做、要完成哪些功能。

最终得到一套 **use cases（用例）**。做网站基本都以 use case 为核心——先把"人家怎么用你的网站"搞清楚，后面的建模、设计、测试，use case 都是重要依据。

## 三、计划：三类项目的对照表

formulation 大致清楚后，仍要做一个 plan。它非常不正式、非常短、比较草，但必须有。教材给了一张对照表，比较三种项目在 planning 阶段的特点：传统项目（Traditional Projects）、小型 Web 应用（Small e-Projects）、大型复杂 Web 应用（Major e-Projects），对比维度包括需求收集、技术规格说明书、开发工期、测试与质量保证、风险管理等。

要点在于看"红色"——红色表示与传统软件工程差异较大的地方：

- **大型复杂 Web 应用**：如果基于 Web 但规模大、功能多、系统极复杂，基本流程与传统软件工程差不多，同样严格、按部就班。唯一显著差异在 **customer feedback（客户反馈）** 环节：
  - 传统软件项目：面向相对封闭环境、公司内部固定人群，可直接、有针对性地获取反馈；
  - Web 应用：用户是全世界所有能上网的人，无法在预先划定的小范围内逐一获取反馈。因此要设计**自动获取反馈的机制**（automatically 收集），或采用公开问卷（如"是否知道该网站""体验如何""哪些功能不好用"）。
- **小型轻量级 Web 应用**：表格里几乎全红，核心就是"快"：
  1. 周期极短，各项工作都求快；
  2. 需求收集不需要厚重的多轮会议和详尽规格说明书，通常只要一个**简要的描述性概述（descriptive overview）**，三言两语交代清楚；
  3. 测试与风险管理重点放在 **risk control（风险控制）**——团队成员必须对所用技术非常熟练，且随时盯"到底能不能按期做完"。比如总共只有 7 天，绝不能花 2 天准备、剩下 5 天放任不管；不做日常 track（跟踪），5 天后大概率做不完，必须每天盯进度；
  4. **质量权衡**：既强调速度又不能完全放弃质量，但时间有限做不到极其完备的质量监控，必须在速度与质量间取得平衡。

## 四、团队角色：不只是开发工程师

组建团队（team）时，团队不止是开发组，还包括开发及后续运营中需紧密协作的 **Stakeholders（利益相关者）**。角色至少包含：

| 角色 | 英文 | 职责 |
|------|------|------|
| 管理与运营人员 | Administrator / Admin | 系统日常管理与配置 |
| 技术支持团队 | Support Team | 上线后响应排查故障/数据异常（通常与初始开发团队是分开的两拨人） |
| 内容提供与维护者 | Content Developer / Provider | 提供、审核、发布内容；明确哪些来源的信息可被接收 |
| 内容发布者 | Web Publisher | 在后台把授权内容发布到正确位置（需稍懂技术的人） |
| 开发工程师 | Web Engineers | 核心开发力量 |
| 业务领域专家 | Business Domain Experts | 掌握业务规矩与流程的人 |
| 技术支持 | Support | 系统坏了、不好用时有人响应 |
| 站点管理员 | Webmaster / Administrator | 系统总管（常从用户中找，而非开发方自己人） |

**Business Domain Experts 最容易被忽视却最关键**。不要一看到 business 就联想到赚钱/市场。举例：

- 给计算机学院做网站，计算机学院**办公室主任**必须是团队成员——他清楚办公流程、各部门职责、内容该放哪、什么能放什么不能放，他是 domain 知识的拥有者；
- 做选课网站（含成绩管理、退学警告等），相应的 domain expert 是**教务处长、学籍管理处长**（或其代表）——选课流程、成绩控制流程、通知发布流程，他们最清楚，政策与规矩要先搞清。

Content Providers 可能只负责"把这门课挂上去、把学生导进去"，未必知道整体流程规矩，所以 domain expert 必须请到。

自家人大概只有 Web Engineer 和 Support Specialist；Administrator 通常得从用户里找。整个开发过程中，团队要含上述多类角色。

## 五、管理策略：外包（Outsourcing）与自制（In-house）

### 5.1 两种模式的沟通结构差异

- **In-house（自制）**：所有角色（含外部 stakeholder 代表）直接坐在一张圆桌上讨论软件核心问题，对大家全透明。
- **Outsourcing（外包）**：核心内容封在承包商（Outsourcing Vendor）内部，任何改动或讨论都要通过他提供的 **Liaison（联络员）** 机制，由联络员收集意见再传进去。

### 5.2 一个理发外包的讽刺故事

老师讲了自己剪头发的经历来类比外包：每年剪一次，前年换了一家店，对理发师小帅哥说"把马尾巴剪成羊尾巴"（意指长发剪短些）。理发师没多问"好嘞"就动手；老师摘掉眼镜闭目养神，结果戴上眼镜一看——"你管这叫羊尾巴？这是兔子尾巴！"太短了。理发师辩称是"小羊的尾巴"。悲剧收场，以至于现在头发都不用剪。

这就是一个外包过程：我想把头发剪短点，嫌自己剪麻烦，外包给专业理发师；双方都犯了错，导致悲剧。课堂据此让大家写：作为外包方、作为承包商，分别犯了什么错？这类错误本是软件外包中也会重演的。

### 5.3 外包方（甲方）必须自己先做透的功课

最关键的一点：**千万不要以为 outsourcing 你就没事了**。外包前，自己内部必须先搞清楚：

1. **自行 gather requirements**：自己先弄明白到底要做的是什么；
2. **有一个 rough design（粗略设计）**：大模样得知道，哪怕粗糙也是 design；
3. **有一个 schedule（进度表）**：这样跟外包商谈条件、谈价钱时才不会太离谱；
4. **定义 increments**：Web 应用不是一次交付就完事，每次给一个 increment，每次到什么程度自己先定义好；
5. **划清责任**：自家人负责哪些、外包商负责哪些，责任必须划清楚，否则最后会"打起来"；
6. **定义联络机制**：联络员机制要先定好。

准备好这些，才出去找外包商。找的时候注意：

- 多找几家，别盯死一家；
- 关注报价及其可靠性——报极低价格、极快时间时，要考察其团队以往声誉、做过大项目没有、做不做得了；
- 搞清楚把事包给他后，你在多大程度上还能掌控 project、能以什么方式做 management；
- 看 schedule 是否合理（前提是自己先知道什么是真正合理的 schedule）。

外包商一般不会让你把手伸进他公司管细致进度，但 **scope（范围）你要管**，大体进度要管——这就是外包的管理要点。

### 5.4 自制（In-house）的要点

In-house 与传统开发差不多：

- 知道 **scope** 是什么、哪些地方最可能频繁改变、有什么限制条件；
- 若做 incremental，每个 increment 如何定义；
- **risk analysis（风险分析）最重要**；
- 有一个宏观 **estimation（估算）**：软件什么规模、需多少人力物力，毛估即可；
- 定义 **task set（任务集）**，分解成若干任务并控制进度；
- 控制进度的常见做法：**count use cases（数用例）**——做了几套 use case，看走完了多少个就知道完成百分比（取决于开发策略，未必都按 use case 线索）；
- 最后有 **change management（变更管理）**，后续专讲。

In-house 与传统开发唯一明显区别就是"快一点"。

## 六、最坏实践（Worst Practices）：别犯这些错

教材在讲完 best practices 后，专门列了最差实践，作为反面清单：

1. **"We have a great idea, 所以就开始干吧"**：有伟大想法就开干。先想清楚钱在哪、做出来有人用没人用、能不能赚到钱，再开始。想法总会变，但盲目开干是错。
2. **"需求总在变，所以不用搞太清楚"**：网站需求确实不停变，但你若太不清楚，后面会产生更多 **unnecessary changes（不必要的变更）**。适度澄清仍必要。
3. **"传统软件高手直接能来做 Web"**（此条讲师存疑）：教材认为传统软件做得好的人，不经过新培训直接做 Web 开发不太可能，因为"they are different"。讲师本人表示没特别深感受，留作参考。
4. **官僚式管理轻型项目**：你是 manager/领导就什么都官僚、走固定流程——这在 IBM 那样的大公司可行，但开发轻型小型 Web 应用时，最好鼓励大家加油、领导靠边别捣乱，以快为准。
5. **"testing why bother"**：前面已强调，内部测试做不好就交给用户测，可能是大悲剧。

## 七、小结

Web 项目管理始于 formulation：用"为什么做、想做成什么、谁会用"三问覆盖业务需求，抽取信息目标与功能目标；需求收集中 user categories 是命门，靠沟通产出 use cases。计划上，大型 Web 项目接近传统工程、重在自动反馈机制，小型项目核心就是"快+风险控制+质量权衡"。团队不止工程师，domain expert、content/publisher、support、admin 缺一不可。外包不是甩手掌柜——甲方须先自定需求、粗略设计、进度与增量边界、责任与联络机制；自制则重在范围、风险分析、估算、任务集与变更管理。最后，伟大想法不能直接开干，需求不能因"总在变"就放任，轻型项目别用官僚流程，测试绝不能省。

## 随堂自测

**1. formulation 阶段必须覆盖的"三问"是什么？从用户回答中应抽取出哪两类目标？**

解析：无论用什么顺序提问，问题清单必须覆盖——（1）用户为什么做这件事（business need）；（2）他想要做成哪些事（目标/功能）；（3）做好了谁会用（最终用户）。从回答中抽取两类目标：information goals（网站要提供哪些内容数据、以何形式展现，属"数据"侧）与 obligative goals（哪些任务可通过网站完成，属"功能"侧）。

答案：三问是"为什么做 / 想做成什么 / 谁会用"；抽取的两类目标是信息目标（数据内容）与义务（功能）目标。

**2. 小型 Web 应用与大型复杂 Web 应用，在计划与反馈上最关键的差异是什么？**

解析：大型复杂 Web 应用流程接近传统软件工程，唯一显著差异在 customer feedback——传统项目面向封闭固定人群可针对性获取反馈，而 Web 应用用户是全世界网民，须设计自动反馈机制或公开问卷。小型轻量 Web 应用核心则是"快"：需求只要 descriptive overview，重点在 risk control（每天盯进度、技术熟练），并在速度与质量间权衡。

答案：大型 Web 项目反馈须自动化/公开化（因用户不可控），小型项目核心是快+风险控制+质量权衡，不可套用厚重传统流程。

**3. 把 Web 项目外包出去，甲方（外包方）在交给承包商之前自己必须先做哪些功课？**

解析：绝不能"外包后就没事"。甲方外包前须：自行 gather requirements 弄清要做什么；有 rough design（大模样）；有 schedule 以便谈价；定义 increments 边界；划清自家人/外包商的责任；定义联络员机制。之后再多找几家比价与资质，且外包后 scope 与大体进度仍要管。

答案：甲方须先自定需求、粗略设计、进度表、增量定义、责任划分与联络机制，并多比选外包商、保留对范围与进度的管控，而非甩手等待。
