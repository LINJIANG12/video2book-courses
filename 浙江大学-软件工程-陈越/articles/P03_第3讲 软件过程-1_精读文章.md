# 软件过程（一）：层次化技术、过程框架与成熟度模型

## 一、软件工程是"层次化技术"：从质量焦点到工具的四层

上一讲是"站在月球上看地球"，俯瞰软件工程全貌、知道它"做什么"；从本讲起，要"举起天文望远镜看地球"，看到更多细节。第一个细节就是 **process（过程）**。

教材的写作风格本身就体现了一种核心思想：**layered technology（层次化技术）**。这本书任何一大块知识都"由浅到深、一层一层深入"——开头必是 generic view（概览），想快速了解只要看每章开头，想深入再看下一层、再下一层。本课程贯穿始终要培养的习惯，正是这种**由宏观到微观、逐层深入的看问题方式**。

一个类比能说明"层次"为何重要：你跟建筑工程师说"我要建一座桥"，他第一反应绝不会是"买几号螺丝钉、去哪家厂订"——那是显微镜级别的事。同理，学期大 project 布置下来，很多学生脑子里第一个冒出的念头是"我该用什么语言开发"，这**远还没到那个层次**。正确顺序是：先从最宏观角度看清全貌，确认看清了，再拿天文望远镜、普通望远镜、放大镜、显微镜，逐级看到越来越多细节。

这套思想方法可落地为四层结构：

```text
┌─────────────────────────────────────┐
│  Tools（工具）                        │  ← 显微镜：用什么语言/测试工具/版本控制
│  Methods（方法）                      │  ← 放大镜：每阶段具体 how to do
│  Process Models（过程模型）           │  ← 望远镜：what to do，走哪条路
│  Quality Focus（质量焦点）★最底层     │  ← 全貌：一切为了高质量软件
└─────────────────────────────────────┘
```

最底层是 **quality focus（质量焦点）**。上节课讲过的 myths vs reality 里，有人质疑"写文档是官僚负担、专门捣乱"，而 reality 是：规定你"先这么做、再那么做"、写大量文档、做详细 report，目的只有一个——**若不如此，你极易陷入困境、做出不好用的软件**。可维护性、可用性、少 bug，都属于软件质量。所做的**一切**规章制度，若伤害了"做出高质量软件"这个总目标，无论 process 多 fancy、多花哨，都没有意义。将来你管理团队、设计制度时，也要以"是否有助于质量"为唯一标尺。

## 二、过程模型：通往高质量产品的地图

在质量焦点之上，人们设计了一系列 **process models（过程模型）**。它的本质是**一张地图（a road map that helps you create a timely high-quality result）**：从起点（拿到项目）到终点（按时、高质量地生产出软件产品），要经过哪些地方？先干什么、再干什么、每一步分几步、每步干什么——把路线理清，就是 process model。

从起点到终点有很多条路，不同公司选不同道路，取决于：**主营软件的类型**、**手底下员工所处的层次（人力资源特点）** 等。选定一个模型后，才进入 **methods（方法）** 层——过程模型回答"what to do（干点什么）"，方法层回答"在每个阶段具体 how to do（怎么干）"。方法清楚了，才到最顶层的 **tools（工具）**：用什么编程语言、测试工具、版本控制工具。整个过程正是"天文望远镜 → 望远镜 → 放大镜 → 显微镜"的逐级下沉。

## 三、通用过程框架：Framework Activities 与 Umbrella Activities

下一章会看到五花八门的 process models，但**万变不离其宗**。无论设计何种模型，都要先做几件共同的事，称为 **framework activities（框架活动）**；此外还有一组**笼罩全程**的活动，称为 **umbrella activities（伞形活动）**。

### 3.1 框架活动五件套

任何 process model 最少都要包含：

1. **任务分解**：把要做的分成几个任务（大 project 的宏观分工已由课程定好）。
2. **work products（工作产品）**：每个任务总要产出点什么——交一份文档也是阶段性 product，不一定是最终产品。
3. **milestones（里程碑）与时间控制**：怎么定义里程碑是有学问的。
4. **deliverables（交付物）**：每个 milestone 要能交出来什么东西。
5. **QA checkpoints（质量保证检查点）**：QA = Quality Assurance（非 Question Answer）。课程已替大家做好了粗框架的 QA checkpoints——需求文档里写了学期要做 **7 件事**，每件 TA 如何打分、需求文档至少含哪几部分、各部分占多少分，都已在其中。但这是"guideline 级"的粗框架；组长把需求文档拆给组员后，对**每个人的子任务**还要有更详细的 checkpoints，才能评估其工作。

### 3.2 伞形活动：贯穿始终的八件事

**umbrella（雨伞）** 得名于它的形态——把整个过程"笼罩"在下面。以下活动**贯穿 project 始终**，做任何一件小事时都要考虑：

| 伞形活动 | 含义 |
|---|---|
| Project Management | 任何小事都可视为一个小 project，都要有管理、有规矩 |
| Quality Assurance | 如何保证做的事是好的 |
| Product Production | 产品生产 |
| Measurement | 度量 |
| Formal Technical Review | 正式技术评审 |
| Configuration Management | 配置管理 |
| Reusability Management | 重用管理 |
| Risk Management | 风险管理 |

其精髓在于"大中有小、小中有大"：宏观有这几大活动，微观每个细节也贯穿着同样的逻辑。

## 四、五步本质流程：communication → planning → modeling → construction → deployment

无论具体模型长什么样，大体都绕不开这五个环节，不同公司只是对这五步做了**不同的排列与执行策略**：

```text
  ① Communication        ② Planning          ③ Modeling
  （沟通/需求收集）      （计划）            （建模/写文档）
        │                    │                   │
        └────────────────────┼───────────────────┘
                              ▼
                  ④ Construction（编码）+ Testing（测试）
                              │
                              ▼
                  ⑤ Deployment（部署）→ 接受用户反馈
```

1. **Communication（沟通）**：拿到 project 的第一件事**不是**需求分析，而是先跟客户谈——即课程里的 TA（扮演啥也不懂的客户）。要先"知己知彼"：摸清他懂什么语言、你该用什么程度的话跟他交流。真实世界里你通常不是给自家人做软件，客户非计算机出身、听不懂术语，必须用语他能懂的方式沟通。这是 requirement gathering（需求收集）过程。
2. **Planning（计划）**：摸清需求后才做计划。看手头有多少人、多少机器，大家对工具/技术的风险与人手熟练度如何，做分工，定 schedule 与各种 deadline。大面上的 plan 课程已定，但每个小组对自己小 project 还要另做 plan。
3. **Modeling（建模）**：计划完还**不能写代码**。建模要写文档，但文档**不是给你自己看的**（除非两三年后你忘了、要改 bug 时感谢当年的自己）。建模的重点是**跟别人沟通**——用图、表、统一格式描述你将搭建的系统的结构，目的是确认"我做的跟你要的是否一致"，让 customer 易看懂，也让组间、工程师间能在短时间内互相理解系统样貌、定位问题。统一图形语言是沟通效率的关键。
4. **Construction + Testing（构建与测试）**：当 customer 看了模型说"差不多就是我要的"，才真正开始写代码，写完测试。
5. **Deployment（部署）**：交第一版，接受用户反馈……事情并未结束（呼应上节课"90% 魔咒"与"交付后花 60%~80% 精力"）。

## 五、CMMI 能力成熟度模型：0~5 级全解

**CMMI = Capability Maturity Model Integration（能力成熟度模型集成）**。最早是 SEI（CMU 软件工程研究所）推出的 CMM，后来模型太多太庞杂，便做了 Integration 推出 CMMI，内容大致相同。独立评估机构会给软件公司打 **0~5 分**的成熟度等级，级别高（如 4 级、5 级）的公司可把认证书挂墙上拉生意，让人放心其有成熟管理机制。

各等级含义：

| 等级 | 名称 | 特征 |
|---|---|---|
| **Level 0** | Incomplete（不完整） | 基本不能算公司。创业草台班子：拿到活就做，无 process、无分工、无进程管理概念 |
| **Level 1** | Performed（已执行） | 开始有**分工**概念，知道每个任务要产生 work product，但**无管理**概念。典型如"组长分完工就撒手，deadline 前夜才收东西" |
| **Level 2** | Managed（已管理） | 有**管理**概念，有专人在管；所有 **stakeholders（项目干系人，即对项目有发言权的人）** 能有效沟通；过程被 monitored（监控）、reviewed（评审）、evaluated（评价）。**课程希望每组至少达到 Level 2** |
| **Level 3** | Defined（已定义） | 真像一个公司。规章制度**固化下来、写进文件、上墙**，成为贯穿任何 team、任何 process 的行为标准/行业规范，一代代传下去 |
| **Level 4** | Quantitatively Managed（量化管理） | 较大且历史长的公司才能做好。有意识地**采集数据**（每人每天产多少行源码、经手多大规模软件、查出多少 bug、月均查 bug 百分比等），分析后支撑管理决策。如向客户承诺"有 85% 把握达某质量标准"——这 85% 不能拍脑袋，要有算法从数据中得出 |
| **Level 5** | Optimizing（优化中） | 最高级。不仅守规矩、用某 process model，还**持续改进甚至创新**模型，用更好方法/技术保证质量、控制进程 |

评分方式值得注意：评估**重点看过程而非结果**——不是"看你最终交的软件市场评价好就打 5 分"，而是检查你做事情有没有规矩、管理严格到什么程度、员工多大程度把 manager 当回事。课程小团队多半连 Level 2 都未必稳达，但重在体验。

## 六、模式（Pattern）：可重用的过程模板

**Pattern（模式）** 更像 C++ 里的 **template（模板）**。前辈工程师把成熟的做事方式总结成模板，下次做相似事直接套用，最大好处是**重用（reusability）**。模式不仅 Process 有，每个环节都有。

教材定义：pattern "defines a set of activities, actions, work tasks, products, or related behaviors"。若自己定义一个 Pattern，至少应包含以下部分（结构极像一个 C++ 类定义）：

| 组成项 | 含义 | 类比 OJ 题目 |
|---|---|---|
| **Pattern Name** | 模式名称 | 题目名称 |
| **目的/类别** | 它管 process 哪一段（更有效测试？管理？设计？） | — |
| **Initial Context** | 在什么情况下可用此模式（输入前提） | 输入格式 |
| **Solution** | 如何解决（核心，相当于代码主程序） | 解题核心（由你写） |
| **Resulting Context** | 用成功后产生什么结果（输出） | 输出格式 |
| **Related Patterns** | 还需调用哪些其他模式 | 关联题目 |
| **例子** | 应用实例 | Sample In / Sample Out |

Process 模式分三大类：**Task Pattern**（与具体任务相关）、**Stage Pattern**（与 Framework Activity / 各单步过程相关）、**Phase Pattern**（如何把这些步骤串起来）。课程鼓励学期末总结出一个有用 Pattern 写成小 essay，可有加分。

## 七、过程评估、PSP/TSP 与个人复盘

**Process Assessment（过程评估）**：定义 process 后请独立机构评估，不仅给分数，还会出一份 **Report**——告诉你当前过程的能力成熟度、哪些方面不足、有哪些风险；据此组建团队改进，改进结果反馈回 process，形成闭环。书上列了几个独立评估机构，了解即可。

**PSP / TSP（Personal and Team Process Models，个人与团队过程模型）**：这是**建议而非规定**。个人做事建议有五个框架性环节：

1. **Planning（计划）**：任何活先计划。
2. **High-Level Design（高层设计）**：打算怎么做、做成什么样。
3. **High-Level Design Review（高层设计评审）**：去跟对方确认"我没理解错吧"。**切勿自动脑补**——常见错误是听了任务上半句就自行补完下半句去做，结果做错白干。务必确认沟通一致再动手。
4. （构建/执行阶段）
5. **Postmortem（事后复盘）**

**Postmortem（验尸报告）** 字面意为"验尸"，实际指**教训总结**：事情"死"了不要白死，要分析"怎么死的、为什么"。课程中一位实验室毕业、先后在国内与日本企业工作过的学长，对两国企业管理水平的差异感触极深——这正呼应了 postmortem 所代表的"从经历中萃取经验"的文化。

## 随堂自测

**1. 软件工程"层次化技术"的四层从底到顶分别是什么？最底层存在的根本理由是什么？**

解析：四层由底至顶为 Quality Focus（质量焦点）→ Process Models（过程模型）→ Methods（方法）→ Tools（工具）。最底层是 quality focus，其上一切过程模型、方法、工具的存在理由只有一个——保证做出高质量（可维护、可用、少 bug）的软件；任何不服务于该总目标的 process 都无意义。

答案：底层质量焦点、过程模型、方法、工具（顶）；最底层为质量焦点，一切制度皆为保证软件质量而存在。

**2. 拿到项目后的第一步为什么是 Communication 而非需求分析？建模（Modeling）产出的文档主要是给谁看的？**

解析：客户（课程中的 TA）扮演不懂技术的角色，必须先沟通、收集需求（requirement gathering）、知己知彼，才能正确分析。Modeling 文档重点不是给自己看，而是与客户确认"做的与要的一致"、与组间/工程师间统一描述系统结构，故首要给 customer 及协作者看。

答案：先沟通才能摸清客户真实需求；建模文档主要用于与客户及协作者沟通，确认一致性、统一系统描述。

**3. CMMI 中 Level 1 与 Level 2 的关键区别是什么？课程对小组的最低期望是哪一级？**

解析：Level 1（Performed）仅有分工概念、知每个任务产出 work product，但无管理；Level 2（Managed）加入管理概念，有专人在管、stakeholders 有效沟通、过程被监控/评审/评价。课程希望每组至少达到 Level 2。

答案：Level 1 有分工无管理，Level 2 有管理且过程受监控评审；期望至少 Level 2。
