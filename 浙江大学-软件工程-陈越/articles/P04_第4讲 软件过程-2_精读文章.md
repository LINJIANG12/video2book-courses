# 软件过程（二）：规范模型谱系与瀑布、增量、RAD、原型、螺旋

## 一、个人复盘（Postmortem）：从"结果"挖到"根源原因"

上节末尾提到的 **Postmortem（验尸报告）**，字面意为"验尸"，实际指**教训总结**：事情"死"了不要白死，要分析"怎么死的、为什么"。一位先后在国内与日本企业工作过的学长，对两国管理水平差距感触极深，他讲的故事正是 Postmortem 的范本。

他在日本公司由一位 mentor（师傅）带。有一次调程序卡死很久，最终发现原因是一段代码本可重用，他 copy-paste 时**手滑漏了一个字母**；偏偏漏字母后的变量名恰好是另一个**合法变量名**，编译通过、肉眼难辨，于是耗了极长时间才定位。

mentor 问他"原因"，他答"copy 漏了一个字母，所以错了"；mentor 打断："你告诉我的叫**结果（result）**，我问的是**原因（cause）**。"mentor 要的原因是：是鼠标不好用？日式键盘不习惯？工作时间太长精神难集中？家里有事心不在焉？——要分析到**根源**。

Postmortem 的目的正在于此：避免重蹈覆辙。会学习的人不是不犯错，而是**不重复犯同一种错误**——错一次就记住，不在同一坑里摔第二次；不会学习的人反复摔在同一坑里。核心是 **understand the types of errors（理解错误属于哪一类）**，从而规避再犯。这是个人做事的基本 process。

## 二、团队自驱与度量

对组长而言，每件任务须定义清楚、有执行"脚本"，然后团队应**自驱（teams are self-directed）**——像演电影，先有剧本大家照演，自己有效率地往前走，而不是每人都像机器人等顶端 manager 发话（"往东就往东、往西就往西、停就停"）。课程不需要这种被动团队。

关于 **measurement（度量）**：在真实公司可有意识地收集数据、分析并改进 team process。但本课程的 project 是特殊的训练项目，收集的数据对未来无用，故做度量的必要性不强。

## 三、规范模型（Prescriptive Models）的边界之辩：orderly approach 真的好吗？

接下来介绍的著名 process models，全部属于 **prescriptive models（规范模型）**。其反义词是"美国大片里的英雄"——遭遇计划外突发事件、事先没想好应对、见招拆招。这种英雄气概**最好别在软件开发中展示**。

Prescriptive 意为**事先规划好、按规矩做事**，强调 *orderly approach to software engineering（有序的软件工程方法）*。

由此引出第一个课堂讨论题：**Is orderly approach really that good?（有序方法真的那么好？）** 可从两方自圆其说：

- **强调 order 的弊端**：人类社会与人是最复杂的，需求变化是本质特征。过分强调规矩会**死板、不易适应变化**。
- **另一极端的弊端**：若完全抛弃 prescriptive，走到哪算哪、客户说改就马上改，会导致**一盘散沙、没头苍蝇**的状态。

结论预设在两类讨论里：order 与灵活都不可极端，关键在于权衡。学生需将观点写在纸上并签名提交。

## 四、瀑布模型：定义传统生命周期，也定义其死板

第一个、也是最古老的模型是 **Waterfall Model（瀑布模型）**。前述五个阶段正是由它总结而来，它定义了**传统的软件生命周期**。

### 4.1 为什么叫"瀑布"

水从上往下流很顺，但**原则上不许返工**——想把下面的水倒抽上去，得动用抽水机、挑上去，极累。严格规则是：前一阶段彻底做完、通过评审后"关门"，原则上下一阶段不许回头。必须从上往下顺做。

### 4.2 致命缺点

1. **太死板、不真实**。真实 project 不可能"前面做完后面不许返工"。常在 construction 甚至 testing 阶段，客户说"我要改个需求"——客户是上帝，不能不给他改。需区分：本课程的 customer（TA）是**存心捣乱**；真实 customer 并非故意，因为他也是人不是神，不能指望外行一次性把需求讲清。常见情形是"大概知道要做什么"，磨合中才发现有好几件事，一开始很难讲清。
2. **客户见到可用产品太晚**。直到 deployment 阶段才看到能用的东西。此前一直看文档、钱早给了却久不见成果，客户心理越来越没底、发毛不耐烦。更糟的是：给他 100 页需求文档让他找错，**他根本没耐心看完**——除非错得离谱，否则说不出哪里不对。等真看到可用产品才惊呼"不是我要的"，问答往往是：
   > "你怎么不早说？" —— "早我不知道。" —— "不是写在文档里了吗？" —— "没看懂。"

   此时双方都没脾气。

### 4.3 现实地位

现在几乎**没有公司用纯瀑布**，但**所有公司的模型都是它的变形**——瀑布的五步贯穿在每一个模型里。

## 五、增量模型：先交 core product 占领市场（微软范式）

使用最广的渐增式开发是 **Incremental Model（增量模型）**，传说即微软做法。

```text
features
  ^
  |          ●(Increment 3)
  |       ●(Increment 2)
  |    ●(Increment 1)
  | ●(core product)
  +------------------→ time
```

- 横轴是时间，纵轴是完成的 features 数量。
- 以很短时间、很快速度先提交 **core product（核心产品）**——不完美但包含主要功能（如 Windows 最基本的操作界面），先**占领市场**。
- 此后不断升级，每次加 more features，逐步逼近完美系统。
- 每个 Increment 内部仍遵循瀑布五阶段。

其聪明之处在于：在 timeline 上以最短时间先站稳脚跟。人力资源上也极合算——设计工程师做完 Increment 1 的分析设计后，coder 进驻写程序测试；coder 做第一产品时，设计工程师已着手第二产品，无缝衔接，**没人闲着**。即 *makes a better use of resources（更充分利用资源）*。

## 六、RAD 快速应用开发：并行模块的快与适用边界

**RAD（Rapid Application Development，快速应用开发）**：communication、planning 做好后，在 **60~90 天（2~3 个月）** 周期内把东西做出来。其快源于**并行**——将问题拆成 N 个模块，N 个 team 同时开工，最后合并。这套模式与课程 project 的做法高度相似，于是引出第二个讨论题：**简化版支付宝适合选 RAD 吗？**

RAD 要"快"起来的前提条件：

1. **充分人手**：N 个 team 同时铺开。本课程闲人多，此条不是问题。
2. **客户得着急**：客户不急就快不起来。需建立与客户**救火式、快速反应**的沟通机制。但真实客户心态往往是："钱给你了，开发就是你自己的事"，不愿被频繁打扰，出差、度假、觉得"没必要替你找人"。若你没及时反应导致 deadline 交不了活，客户会认定"那是你的错"。所以课程强调要跟 TA（客户）拉好关系。
3. **系统能有效拆成 N 个较独立模块**：若模块间千丝万缕、接口始终定不下来，最后必一团乱麻。
4. **技术风险低、团队对技术熟悉**：若技术风险高，别急着上 RAD，中途必乱。

若以上条件不满足，RAD 未必是最佳选择——回答"好/不好"皆可，关键自圆其说。

## 七、演化式过程模型

### 7.1 原型法（Prototyping）：用样机撬开含糊需求

**Prototyping** 是最受欢迎的演化式模型，前述"学长自创的 process model"总结的其实就是它。其流程极快：快速了解需求 → 快速计划 → 做 modeling design → 产出 **prototype（原型系统 / 样机）**。

样机是什么？一个有界面、按钮、菜单的**空壳**——按钮背后的功能可能尚未实现，先不做。把它给用户点一点、看一看，描述"点这个会发生什么"，借此收集反馈（如"菜单位置我不习惯、找半天没找着"）。人读图形普遍比读文字易懂，这是极有效的沟通方式：写上百页需求文档让用户评判满意度，他说不出；给一个可点的 prototype，他立刻告诉你哪要哪不要。故 prototype 是**沟通需求的好第一步**。

关键纪律：**prototype 最终不能作为正式产品交付，必须扔掉**。因为它以"快"为准，内部结构可能乱七八糟，后期改得面目全非，目的是借此得到正式需求后**另造系统**。但现实中很多团队没扔——授课者自己的项目组就没扔，一直在 prototype 上改，改到无比痛苦（后文再述）。

### 7.2 螺旋模型（Spiral Model）：漂亮的图，少用的现实

**Spiral Model（螺旋模型）** 能写漂亮 paper、画漂亮图，但**没什么人用**。其轴表示花销（可理解为时间，时间即金钱），一条分割线是任务分割线，每次穿线都要测试/验证/审核；在**四个象限**里螺旋前进，每象限代表一类阶段工作：

```text
        需求/计划 ←─── ② 开发阶段(定功能)
          ↑                │
   ① 定目标/风险分析/原型  ③ 计划下一步
          ↑                │
          └─── ④ 测试验证/运行 ─┘
        （每转一圈 = 一个迭代周期）
```

- 第一象限：定 objective 总目标、做风险分析、给 prototype；
- 第二象限：开发阶段，把功能定下来；
- 第三象限：计划下一步（Requirement Plan、Life-cycle Plan）；
- 第四象限：测试、运行、验证，再计划下一圈。

过程太复杂，少有公司用，了解即可。它要表达的是软件有**演化 / 进化**的过程。

### 7.3 并发开发模型（Concurrent Development）

**Concurrent Development Model（并发开发模型）** 适合 **client-server applications**。与前几种"流水线式"不同，它是一个**网络（network）**而非一条线——回想数据结构里的 AOE network、AOV network：算关键路径、最长周期、关键任务。它用网络描述过程而非线性序列。

## 八、特殊模型与统一过程（Unified Process）

其余特殊模型简述：

- **Component-based Development（基于构件开发）**：强调**重用**。模块化要好，抽象出模块使类似产品可直接拿来用。
- **Formal Methods（形式化方法）**：给庞大非 IT 企业做办公管理系统时，多部门需求可能矛盾（一份五六千字需求文档中，部门间要求互相冲突）。靠人脑发现冲突既难又不靠谱，故用**数学 / 形式化语言表述需求，自动查逻辑冲突**。
- **Aspect-Oriented（面向方面）**：近年流行，译法五花八门，不展开。
- **Unified Process（统一过程）**：与"面向对象"同期产生，重要工具是 **UML（Unified Modeling Language，统一建模语言）**，以设计软件 **architecture（架构）** 为核心，用 **use case（用户脚本，描述用户如何使用软件）** 驱动。它是 **iterative（迭代）、incremental（增量）** 的，特点是以 UML 为重要工具。其 phases 与传统五步对应：

| Unified Process 阶段 | 对应传统步骤 | 含义 |
|---|---|---|
| **Inception（初始）** | communication + planning | 正式表示"开始" |
| **Elaboration（细化）** | planning + modeling | 粗了解后再细化 |
| **Construction（构建）** | construction | 进入编码构建 |
| **Transition（过渡）** | deployment + construction 后期 | 产品从专业人员转到用户手中，release 一个版本 |

随后反复迭代，一个 increment 一个 increment 地交付，进入 production 阶段。各阶段 work products 详见教材。

## 九、一条贯穿线：所有模型都是瀑布的变型，质量是不可让步的终点

增量、演化等模型，本质上**都是 Waterfall Model 的变型**——没人再用纯瀑布，但瀑布五步贯穿每个模型内部。它们共同强调的是 **flexibility（灵活性）** 与"快"。

但必须时刻提醒：**无论用哪种 model，最终目的都是保证 high quality（高质量）**。若"快"要伤害"质量"，必须做权衡。模型是手段，质量才是终点。

## 随堂自测

**1. Waterfall Model 为何被称为"瀑布"？它最不真实的两点表现是什么？**

解析：因前一阶段做完原则不许返工，如水流只能自上向下、倒抽极难，故称瀑布。最不真实处：①真实项目不可能"前面做完后面不许改"，客户（上帝）常在 construction / testing 阶段改需求；②客户到 deployment 才见可用产品，且给百页文档他也看不出错，等见到成品才发现不符预期。

答案：水只能向下流、不可倒抽喻不可返工；不真实在"客户中途必改需求"与"客户太晚见可用产品、文档难校验"。

**2. Incremental Model 与 RAD 在"快"的机制上有何根本不同？RAD 适用的前提条件有哪些？**

解析：Incremental 的快来自"先交 core product 占领市场 + 设计/编码人员无缝接力"；RAD 的快来自"N 个 team 并行开发 N 个模块、最后合并"。RAD 前提：充分人手、客户愿意急、系统可拆成独立模块、技术风险低。

答案：增量靠核心产品先行与人员接力；RAD 靠并行模块合并。RAD 需人手足、客户急、模块独立、技术熟。

**3. 原型法（Prototyping）中"prototype 必须扔掉"的理由是什么？若舍不得扔会发生什么？**

解析：prototype 以"快"为唯一准则，内部结构乱、功能多为空壳，仅用于撬开含糊需求、确认用户真实意图，故不能作为正式产品。若在其上持续修改，会改到"无比痛苦"——授课者项目组即因未扔掉 prototype 而深陷其中。

答案：原型仅为快速沟通需求、内部混乱不可作正货；不扔则在其上反复修补、痛苦不堪。
