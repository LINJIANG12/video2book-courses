## 第 1 章：第23讲 Web需求分析
> 对应分集：P23 | 原始标题：《第23讲 Web需求分析》

Web 应用要求快，因此它的 analysis model 不必像传统项目那样严肃、正式、严谨——"有就可以"，要求的程度低一些。但任务骨架与普通项目一致：先 formulation（快速弄清要做什么），再 requirements gathering（所有人坐到一起对齐目标），然后给出 analysis model。差别只在"要求的程度"。本讲的重点，是 Web 需求分析**独有什么、要补哪些传统软件不怎么讲的东西**。

### 一、formulation：目标之外，必须建用户分层

formulation 阶段的主要目标仍是 **goals and objectives**——goals 是大目标（为什么做这件事），objectives 是具体一点的目标（要做成哪些事）。但 Web 应用多了一件必须做的事：**categories of users（用户分类）**。

因为系统上网后你不知道谁会来用，但心里要有数，要把 Web App 的用户大致分一分类。所以除目标外，还要画一张 **user hierarchy（用户层级）图**。

教材沿用 SafeHome（家居保安系统）的例子：给它做了一个可网上定制、购买的网店 safehomeassured.com，顶层用户是"网站用户"，再分成三大类：

- **guest（打酱油的访客）**：权限最低的一类；
- **registered user（正经注册想买东西的用户）**；
- **customer service（后台商场服务人员）**。

其中 registered user 还可再细分：新手（new customer）与老用户（old user），给他们提供的 service 可以略有不同。如果你的网站很简单，新手老用户看到的界面和权限都一样，那就没必要再分；要把服务做细致，才给两类人不同的 service。

这一原则对支付宝这类大系统同样适用：一个系统被按某种原则分成多个组，划分得干不干净、界限清不清楚，直接决定后续开发的顺畅度。

### 二、use case 是一切的基础

对 Web App 而言，最重要的东西是 **use cases（用例）**。后面大量工作都依赖这一套用例设计。每一类 user（前面分好的类）都要设计一套对应的 use case。

#### 2.1 use case 用在哪

闭着眼睛先把 use case 准备好，它会在这些地方被反复用到：

- **写需求时**：各种分析模型（至少四大类）都跟它相关，都要从 use case 里提取信息；
- **做设计时**：照着它设计；
- **做测试时**：黑盒测试就是一个 use case 一个 use case 地走。

进度也靠它度量。最简单粗暴的指标是**数 use case（count use cases）**：设计了 100 个、走完 60 个，进度就是 60%。当然不绝对准确——有的 case 只是"注册一个新账号"很简单，有的 case 是"进去做一堆事最后买走"很复杂。但总体它是个可用指标：所谓"完成"，就是测过没问题、好用。

#### 2.2 用例设计示例与画法

教材给了一个 new customer（新手注册用户）的例子，他要做的几件事：

- **login**：点击登录功能；
- **查看商品描述性内容**：浏览要买的物品展示；
- **建立/保存配置（configuration）**：新手要先建立自己想要的 SafeHome 配置、挑好模块、存一下；
- **recall saved configuration**：回头查看刚才存的东西；
- **customize SafeHome**：定制个性化系统（较复杂功能）；
- **purchase configuration**：把配置买下来（较复杂的过程）。

画法上：如果一个 actor 要做的事情比较复杂、画不下，就把复杂功能塞进一个 **package（信封/包）**，介绍时再打开包看里面详细内容。总之 use case 大致这么画，但要做到全面、不漏，是个复杂过程——课上只告诉大家"有什么"，具体怎么做自己去摸索。

#### 2.3 划分模块的三条原则

每个圆饼（用例/包）对应一个要实现的模块操作，可视为一个模块。划分遵循三原则：

1. **comprehensible（可理解）**：图不能太乱太复杂，命名不能含糊，要让别人看得懂。
2. **cohesive（高内聚）与 loosely coupled（松耦合）**：
   - 内聚性强 = 一个 package 里的东西目标集中、彼此相关，而不是把八竿子打不着的好几个目标零碎塞进一个包；
   - 松耦合 = package 与 package 之间、功能模块之间最好不要有太紧密的关系。包内紧、包间松，分工才干净。
3. **hierarchically shallow（层次浅）**：use case 最好不要分太深。太深意味着用户为完成一件事要点好多环节——受网络带宽影响，点一个链接等半天、点十个链接才办成事，没人会用。层次浅还因为测试会轻松些；太深测起来痛苦。Web App 尤其不能让用户觉得烦。

### 三、五维分析模型

在 use case 基础上，开始建 analysis models，大致分五个方面：

1. **内容（Content）**：网站要展示什么（文本、图片、视频、音频……），并分类出 data objects；
2. **交互（Interaction）**：用户与网站如何交互；
3. **功能（Functional）**：要完成哪些功能；
4. **配置（Configuration）**：传统软件不太讲，但 Web 必须讲——你不知道客户端是什么样；
5. **导航（Navigation）**：Web 特有且极重要。

下面逐维拆解。

#### 3.1 内容模型（Content Model）

**Content Objects**：确定什么东西作为系统的 class 或 object 存在，去 use case 里抽，并把它们之间的 relationship 搞清楚。

除数据库用的 **ER diagram（实体-关系图）** 外，教材介绍一种 **data tree（数据树）**。它类似结构体定义：定义一个 struct 叫 `component`（家居系统里的一个模块），展示时需要哪些字段。白框里的表示不是复杂 object，只是简单类型——`part number` 是数字，`part name` 是字符串，`part time` 用整型或字符串定义，`Price` 是数字。黑底（黑颜色）的如 `description` 表示是真正的 data object。把 data tree 画出来，就能让人一目了然知道最终要设计哪些 data object。

若系统复杂、想弄得全，data object 从哪来？可以写一个 **parser（词法分析器）** 把 use case 整体过一遍，抽出相应名词，再滤掉那些只需一个简单数字/字符串就能解决的，剩下的设计成要处理的 data objects。

#### 3.2 交互模型（Interaction Model）

描述用户与网站之间的交互，共有 **four elements（四个要素）**：

1. **use case**：必备；
2. **sequence diagrams（时序图）**：随时间从上往下，像泳道一样，几个 actors 之间动作由谁做、产生什么、如何往下走；
3. **state diagrams（状态图）**：系统在不同状态间转换，用户做一个动作就从一状态转到另一状态；对 WebApp，做一个动作就从一页面跳到另一页面，这正是页面间跳转；
4. **User Interface prototype（界面原型）**：最直观——做好 prototype，交互长什么样就知道了。

讲师以给老先生做的系统为例：虽不是典型 WebApp，但 interaction 复杂。结果图没画、use case 没写，而是做了一个很有用的 interface prototype，直接解决了所有问题。这说明原型在交互分析里常常四两拨千斤。

#### 3.3 功能模型（Functional Model）

这部分比较传统，但要注意一个 Web 特有的点：需求收集时，你收集到的是 **user-observable functionality（用户可见功能）**——用户跟你说"我要这些功能"。但系统真正跑起来，后台还有一批动作要做。因此功能要准备**两个层次**：

- 用户可见的功能层；
- 背后支撑的 contain within operations（内部操作层）。

通常用 **activity diagram（活动图）** 描述功能模型。

再次强调：WebApp 所有这些 model 都不要求那么严格，因为要快。画个草图，小团队彼此能看懂即可。

#### 3.4 配置模型（Configuration Model）

这是与传统软件明显不同的地方。传统软件给固定公司做、环境固定，事先知道就行，不必专门详细分类；网站则不知道客户端什么样、有什么操作系统、什么浏览器，全不知道，却要保证各种人打开都好用——"这是一个很痛苦的事情"。因此 configuration analysis 对 WebApp 很重要，分两端：

**Server side（服务端）**：需求分析阶段虽不具体到实现，但要大致说清：

- 对硬件要求多高？服务器性能要到什么程度？
- 在什么操作系统上？
- 用到别的什么应用、数据库、版本？
- 之间的通信协议、网络通信协议等。

**Client side（客户端）**：要列清单照顾哪些浏览器。你不可能照顾周全，只能规划"肯定照顾哪几类"。例如开发 ZOJ 最新版时，负责同学直接说 IE6 太讨厌不要了——用 IE6 打开会显示一行字："检测到你用的版本居然是 IE6，建议安装新浏览器"，并附链接。很多地方已开始"鄙视 IE6"。你做新网站，用的浏览器早晚也会过时，所以要规划照顾哪些、不照顾哪些。

还要考虑操作系统：Windows 是一种方案，Unix/Linux 或别的操作系统打开会不会有影响？取决于要展示的东西。比如需要 Flash，本地没装 Flash 不仅显示不出，还要想怎么解决。总之要弄清：网站正常显示使用，客户端需要什么配置？怎么检测客户端有没有这配置？没有的话怎么解决？browser configuration 相关的所有东西都要考虑到。

此外，**configuration model 里还要有一个测试计划**：把你要照顾到的所有环境全部测一遍。

#### 3.5 导航模型（Navigation Model / RNA）

普通复杂软件也有导航问题，但不那么明显，因为可训练固定单位的员工"点哪几个键"。网站没法训练任何人，所以必须做得**充分傻瓜（傻）**——navigation 的意思是：让用户在网站里跑来跑去不能跑丢。两个要求：

- 非常容易找到想找的东西；
- 找一圈后想"退回前面"，能退得回去、知道自己现在在哪。若退回首页却死活找不到原来要找的东西，就很恶心。

因此要做专门的 **navigation analysis**。教材建议的 RNA（Navigation Analysis）大致包含几步：

1. **分析所有 stakeholders（即用户分类）**；
2. **分析有哪些数据、哪些功能**，这些先准备好；
3. **分析 relationships（关系）**：网页与网页之间怎么跳转，不同类用户的交互之间有没有互相影响——这是 relationship 分析；
4. **决定浏览复杂程度**：到底要不要做特别的导航辅助工具。导航设计后面讲用户界面时会专讲技巧，但此处要先判断：需不需要一个 map（网站地图）？有些 BBS/网站做得好，有 map 可一键看全部分支。形式各异：树形结构程序员喜欢看，但给幼儿园小朋友看的网站要用另一种画法——画得真像个地图，配各种链接跳到想去的地方；
5. **evaluation analysis（评估分析）**：想做到越友好，照顾到的人群越多，工作量就越大。时间人力有限，做完要估算投入产出比合不合算，从而决定 navigation 做到什么程度"差不多了"。

所有这些事在 analysis 阶段最好都做，但不要求写 100 页文档（通常没人这么干）。只是这些都要考虑过。至于用什么图描述 relationship、怎么设计 navigation，到 design 阶段再细讲——本阶段只需分析"我要不要做这些事"。

### 四、小结：需求分析的收口

Web 需求分析因"快"而轻量，但骨架完整：formulation 除了 goals/objectives，必须补一张 user hierarchy 把用户分层（SafeHome 的三类用户及其再分是范本）；use case 是所有工作的基石——设计靠它、测试靠它、进度也靠数它，划分模块遵循可理解、高内聚低耦合、层次浅三原则。随后展开五维建模：内容（data tree / parser 抽名词）、交互（use case + 时序图 + 状态图 + 界面原型四要素）、功能（用户可见层 + 后台支撑层，活动图）、配置（服务端 + 客户端浏览器/OS/Flash 清单 + 全环境测试计划）、导航（RNA 五步：分类、数据功能、关系、地图决策、评估）。这些都想清楚，就可以动手写需求报告了。

### 随堂自测

**1. 为什么说 use case 是 Web 应用需求分析的"基础"？它至少支撑哪些后续活动？**

解析：每一类 user 都设计一套 use case。它用于写需求（各类分析模型都从 use case 提取信息）、做设计（照着设计）、做测试（黑盒测试逐个用例走）；进度也靠 count use cases（走完数/总数）来度量。因此它是设计、分析、测试、度量四方面的共同依据。

答案：use case 是后续设计、需求建模、测试（黑盒按用例走）、进度度量（数用例）的共同基础，缺了它后面各环节都无据可依。

**2. Web 应用为什么要做 configuration analysis，而传统软件通常不重点讲？配置模型分哪两端、各关注什么？**

解析：传统软件给固定公司、环境已知，不必专门分类；网站不知客户端操作系统/浏览器，却要保证各种人都好用，故必做。分 server side（硬件性能、操作系统、数据库/应用、通信协议）与 client side（照顾哪些浏览器/OS、Flash 等插件、如何检测与补救，及全环境测试计划）。

答案：因 Web 客户端不可控、须保证跨环境好用；配置模型分服务端（性能/OS/协议等）与客户端（浏览器/OS/插件清单 + 全环境测试）。

**3. 导航分析（RNA）里的 evaluation analysis 在权衡什么？为什么 navigation 不能无限制做复杂？**

解析：RNA 第五步 evaluation analysis：网站越友好、照顾人群越多，工作量越大；时间人力有限，要估算投入产出比，决定导航做到什么程度"差不多"。导航不能无限复杂，因为网站无法训练用户，必须"充分傻瓜"；层次太深会让用户为办成一件事点太多链接、等太久，且测试也痛苦。

答案：evaluation analysis 权衡"友好度（覆盖人群）"与"工作量/投入产出比"，决定导航做到适可而止；导航须傻瓜化、层次浅，否则用户易迷失、体验差且测试难。

## 第 2 章：第24讲 Web应用软件设计
> 对应分集：P24 | 原始标题：《第24讲 Web应用软件设计》

设计之前先记住一个方法论教训：做任何事都从需求分析开始。写需求规格说明书，要先去读课程对它的要求——它相当于签合同的重要参考文档，而合同里最关键的是验收指标（什么情况下客户付钱、要拿出什么东西）。曾有组交了 60 多页文档，却只对其中一个 use case 做了详尽描述，其余打分项的活一点没干，TA 无从打分。无论画多漂亮的 UML，先搞清楚"要你做的是什么事"再动手——这是软件工程交给你的"做事情的套路"。本讲进入 Web 应用的设计模型（design model），看它作为"文艺青年"有哪些特殊讲究。

### 一、Web 设计为何特殊：要在设计中前置的属性

设计方面的特殊，必然与它那十几条特点里"在设计阶段就要盯死"的几条相关。回想做 online judge（如 ZOJ、PAT）这类网站，设计时必须先想清楚：

- **Security（安全）**：跑考试、跑竞赛，不能让人轻易在考前进去把题扒出来，必须事先设计好如何防范各种攻击与黑客。
- **Availability（可用性）**：网站不能三天两头挂。偶发宕机可容忍，频繁挂掉用户就不来了。
- **Scalability（可扩展性）**：一两个人能玩、一两百人就有挂掉，不行。要能应对访问量大幅波动。
- **Time to market（上市时间）**：工期极短，意味着设计时别想太复杂，尽量简单、先完成主要功能。

由此引出 **design goals** 的第一条：**simplicity（简单）**。尽量简单，不把事情搞复杂。

随后被强调的还有两条，根因同样是"用户不可控"：

- **Robustness（健壮性）**：你根本不知道坐在电脑前的是美女还是抠脚大汉，甚至不知道是一个人还是一条狗，不知道他会按什么键、什么搜索习惯。所以要能应付各种各样的人、各种"变态"操作，让各种水平的人都能进出自如、找得到东西。
- **Compatibility（兼容性）**：用户群不可控，用什么平台、什么操作系统、什么浏览器（连 IE6 这种老古董都可能）都有。设计时要规划照顾哪些、不照顾哪些。

### 二、设计金字塔：越往上越靠近用户

教材把 Web 设计画成一座金字塔：

```
                      [ Users 用户 ]            <-- 顶端，目标
                          |
                  [ Interface Design 界面/美工 ]
                          |
               [ Content Design 内容设计 ]
                          |
             [ Navigation Design 导航设计 ]
                          |
                  [ Technology 工程师 ]         <-- 底端，干活
```

越往上越靠近用户（界面、美工），越往下越靠近工程师（技术实现）。下面把各层逐一过一遍。

### 三、界面设计（Interface Design）

对 Web 应用，界面设计的核心要求是：用户在任何页面、任何停留点，都能轻松回答三个问题。

#### 3.1 三个必答问题

1. **Where am I?（我在哪？）**：随时清楚自己没迷路。常见做法如行政办公网，页面顶部一行小字"当前位置：首页 → 学术机构"，既告诉你在哪、又告诉你路径。最有效的方法是先去研究同类网站人家怎么做的，学习风格。
2. **What can I do now?（我现在能干吗？）**：页面要把可点的东西清楚展示——哪些功能可用、哪些链接有效、哪些内容相关。本质是"把按钮做成按钮、把链接做成链接、把下拉框做成下拉框"，符合用户在互联网上养成的习惯预期。现实中奇葩设计很多：看上去不是链接一点却是链接；写着"点按钮"却找不到按钮，原来那坨东西就是按钮；看着像文本框，点上去没反应，仔细看旁边小箭头才发现是下拉框。所以必须让元素"长成它该有的样子"。
3. **Where have I been? / Where am I going?（我去过哪、能去哪？）**：最简单的机制是浏览器默认的"点过的链接变紫、没点过的是蓝色"，告诉你走过哪、还能去哪。复杂网站还可提供 site map。

#### 3.2 有效界面的特征

- **visually apparent and forgiving（视觉清晰且宽容）**：给用户掌控感（a sense of control），让他迅速看到选择余地、明白如何达成目标；并且**允许他点错**——设计原则之一是把用户当成白痴，白痴都会用，不白痴的用户自然更舒服。
- **不暴露系统内部运作**：普通内部系统会弹窗问"Do you want to save your change?"，网站则要求更高——**根本不提醒，默替他存了**，且让他在任何时刻都能反悔（撤销）。这是很高的要求。
- **perform a maximum of work while requiring a minimum of information**：让用户做的事越少越好、用最小精力完成最多工作。对内部软件，多点一下用户虽不爽但勉强忍了；在网上则不可忍——多一步不仅依赖服务器，还依赖网络，赶上网络抽风，用户绝不能容忍多余操作。所以完成目标所需动作必须尽可能少。

补充一句：互联网用户你尽可以想象得多白痴就多白痴，哪怕是计算机小白也有权使用你公开发布的系统；若他轻易犯错，那是你设计得不好。不想让他破坏的东西，根本别出现在页面上。

#### 3.3 界面设计流程

1. **review analysis model**，做 refinement（回顾需求分析模型并精化）；
2. 画 **rough sketch of the interface layout**（界面布局草图）：要不要 banner？横着要不要一条功能带？竖栏放左还是放右？中间放什么？因工期短，只粗略画；
3. **map user objectives into specific interface actions**（关键步骤一）：把网站给用户提供的几件事，与页面上对应的链接/按钮一一映射——他点哪个完成哪个目标；
4. **列出点击后的后续动作序列**（关键步骤二）：比如点"buy a component"进去后，还要查看、选择、放进购物车、结账、填银行卡与邮寄地址……把这一系列动作一条条理出来；
5. 画 **storyboards（分镜头）**：像导演画分镜，描述每个界面动作下屏幕出现的状态，再据美工设计 refine；
6. 抽取 **interface objects**（面向对象开发时抽相关对象）；
7. 建立模型：因时间紧不要求正式图，但要有一种方式描述**交互流程**，还要有描述**动态行为**的模型（即状态迁移图 state transition），每个状态下界面长什么样、布局如何，都要有描述；
8. 不断 refine、review、细化。

#### 3.4 控制机制（Control Mechanisms）

最简单的是 **navigation menus（导航菜单）**；此外还有更花哨的 **graphic icons、graphic images** 等可作为跳转与控制界面。

### 四、美学设计（Aesthetic / 美工设计）

工科学生普遍缺乏审美——写论文排版不知丑、画结构图把字写到方框外面还觉得"还好"。本节不指望短时间培养审美，只给几条必须遵守的基本品位：

- **Don't be afraid of white space（合理留白）**：不必把屏幕边角全填满。留白不是坏事，是品味；全填满有密集恐惧症的人看着难受。
- **Emphasize content（突出内容，切忌喧宾夺主）**：一页重点展示什么要清楚。若本要展示一段文字，却做了特别 fancy 的 Flash banner，结果访客只记住 banner、不知网站干嘛，就是喧宾夺主。
- **Organize layout elements from top-left to bottom-right（自左上至右下的阅读动线）**：绝大多数人习惯从左上往右下看，元素按此顺序排布。除非故意反着吸引眼球，正常网页应如此。
- **Group navigation, content and function geographically within the page（区域一致性）**：同一功能（如"下一页"按钮）在第 1 页放什么位置，后面几百页最好都放差不多位置。若"下一页"在每页跳来跳去（这页底下、下页上面、再下页左边），用户会满屏找链接、用得很累，这是不分工作、风格不统一的不专业表现。
- **Don't extend your real estate with the scrolling bar（别靠滚动条掩盖重点）**：特别想炫耀的重点最好出现在最上面、最醒目处。虽流行"亮点总在最后"，但不是所有人有耐心拉到最后。真要放在下面，前面先给个提示性链接可直达。
- **Consider resolution and browser window size（适配分辨率与视窗）**：不同浏览器、不同分辨率都要在美工设计时考虑。

### 五、内容设计（Content Design）

内容设计本身没太多新花样：基本就是用 UML，把内容相关东西抽取成 Class 或 Object，定义好它们之间的关系。这与前面的 Content Model 一脉相承。

### 六、架构设计（Architecture Design）

架构设计分两大类。

#### 6.1 内容架构（Content Architecture）

一个 content object 差不多就相当于一个 web page。网页与网页之间的整体结构有几种典型形态：

```
Linear（线性）       Grid（网格）        Hierarchical（层次）      Network（网状）
 A→B→C→D          A──B──C            A                      A↔B
                  │──│──│           / │ \                  ↕ ↕ ↕
                  D──E──F          B  C  D                 B↔C↔D
```

- **Linear structure（线性结构）**：顺序串联；
- **Grid structure（网格结构）**：行列节点；
- **Hierarchical（层次结构）**：树状、层次感强；
- **Network structure（网状结构）**：关系复杂。

#### 6.2 整体应用架构（Application Architecture）：MVC

整体架构不像普通软件那样从数据流图翻译成 call-and-return 结构。网站流行一种架构风格叫 **MVC（Model-View-Controller）**——常听人说"我网站是 MVC 架构的"。核心是把系统分层设计，至少分三层：前台、后台，中间一个中转的 Controller。

```
        [ 用户 ]
           |
        [ View 前台 / 界面 ]
           |  (输入需求)
           v
        [ Controller 控制器 ]  <-- 衔接前后台
           |  (调用后台程序 / 取数据)
           v
        [ Model 后台 / 业务逻辑与数据 ]
           |
           +---> 获取数据后回传前台展示给用户
```

Controller 接受用户从前台输入的需求，调用后台程序、从后台取数据，再传回前台展示。系统搭成"后台 + 前台 + 中间 Controller"的结构，这就是 MVC 风格。

### 七、导航设计（Navigation Design）

导航设计有两个层面：**语义层面**与**语法层面**。

#### 7.1 语义层面：NSU（Navigation Semantic Units）

工具叫 **NSU（Navigation Semantic Units）**，官方定义是"A set of information and related navigation structures"——一套描述信息与信息间导航关系的图。要对每个 use case、每个 actor 的行为，对应一套 NSU。

教材例子是 SafeHome 网上购物的流程：actor 在首页有一个链接，点进去要完成"选房间（Select Room）"；进入某 Room 页面后，页面上有多个链接，点其中一个"Recommend Components（推荐模块）"；再点进入被推荐的模块，打开描述该 Product Component 的网页。全程通过链接完成功能、跳转到对应网页。

```
[ actor ] --link--> [ 首页 Home ]
                       | link: Select Room
                       v
                   [ Room 页面 ]
                       | link: Recommend Components
                       v
              [ Product Component 网页 ]
```

通过图能清楚看到：用户完成一个 objective 时涉及哪几类页面（Room 是抽象出的 Content Object，不会给每个 room 各画一张图），这些 objects 之间用什么链接跳转——这便是导航设计的重要工具。

#### 7.2 语法层面：实现机制

- **individual navigation link**：文字、icon、按钮等各种链接；
- **navigation bar（水平导航条）**：放最重要的几大类功能，**不要超过七个**（约四到七个）；
- **navigation column（垂直导航栏）**：放左或放右皆可，里面可放几乎所有 major content objects 和重要链接。为何横向建议不超七个、纵向随便放？因为鼠标滚轮是竖的——纵向可上下滚，横向应在同一屏宽内解决。若硬让竖向滚轮产生横向移动效果，动作与所见不一致，用户很难受；
- **tabs（选项卡）**：像多张卡片叠在一起，露出标识，一般三到五个页面；
- **site map（网站地图）**：帮用户随时知道自己在哪。

#### 7.3 为何横向≤7、纵向不限

横向导航条塞在同一屏幕宽度内，所以数量受限（四到七个）；纵向导航栏可借助滚动条上下延展，故可放更多。这背后的道理是尊重用户既有的交互习惯（竖向滚轮对应竖向滚动），不让动作方向与页面移动方向冲突。

### 八、构件级设计（Component-Level Design）

构件级设计与普通软件差别不大，只是 WebApp 大致把功能分成四大类 component：

1. **动态生成内容的构件**：运行时动态产出页面内容；
2. **提供计算功能的构件**；
3. **数据库查询功能的构件**；
4. **与外部系统做沟通的构件**。

详细设计留到后面专门讲。至此，Web 应用的设计模型基本介绍完毕。

### 九、小结

Web 设计因用户不可控而前置了安全、可用性、可扩展性、上市时间等约束，design goals 首推 simplicity，并要强化 robustness（容忍任何用户与异常操作）与 compatibility（兼容多样客户端）。设计金字塔从用户的界面/美工，经内容、导航，落到工程师的技术实现。界面设计用"我在哪 / 能干什么 / 去过哪能去哪"三问锚定，要求视觉清晰宽容、默存可撤、动作最少；美学六原则守住基本品位与区域一致性。内容用 UML 类与关系建模；架构分内容架构（线性/网格/层次/网状）与应用架构（MVC 三层）；导航分语义（NSU 描述页面跳转关系）与语法（水平条≤7、垂直栏、tabs、site map）两层；构件级则归为动态内容、计算、数据库查询、外部沟通四类。

### 随堂自测

**1. Web 应用的界面设计为什么要求"把用户当成白痴"、且"默替他存、随时可撤"？**

解析：因网站用户完全不可控、无法培训，各种水平甚至误操作都可能发生（robustness 要求高）。有效界面要 visually apparent and forgiving，给用户掌控感并允许点错；相比内部软件弹窗问"是否保存"，网站更高要求是根本不提醒、自动保存且任意时刻可反悔，不想让用户破坏的东西干脆不出现在页面上。

答案：用户不可控且无法培训，必须让任何人（含计算机小白）都能顺畅、容错地使用；故界面要宽容、自动保存可撤销，把误操作风险在设计层面消弭。

**2. MVC 架构中 Controller 的职责是什么？它与普通软件的整体架构思路有何不同？**

解析：普通软件整体架构常从数据流图翻译成 call-and-return 结构；网站流行 MVC，分前台（View）、后台（Model）、中间 Controller。Controller 衔接前后台：接受用户从前台输入的需求，调用后台程序、从后台取数据，再传回前台展示。

答案：Controller 是前后台的中转层，负责接收前台请求、调度后台逻辑与数据并回传展示；区别于普通软件的数据流/调用返回式整体架构，网站以"前台—Controller—后台"三层分离为典型。

**3. 导航设计的语义层面（NSU）与语法层面分别解决什么问题？为何水平导航条建议不超过七个？**

解析：语义层面用 NSU 描述"信息及信息间导航关系"，即一个 use case 涉及哪些 Content Objects、它们之间用什么链接跳转；语法层面是具体实现机制（链接、水平/垂直导航栏、tabs、site map）。水平条限四到七个，是因为它要在同一屏宽内解决问题，而纵向可借竖向滚轮滚动延展，且动作方向须与页面移动一致，横向塞太多会破坏一致性与可读性。

答案：NSU 解决"页面间跳转关系怎么描述"，语法层解决"用什么控件实现"；水平条受屏宽限制且须与竖向滚轮习惯一致，故建议≤7，纵向则可滚动延展。
