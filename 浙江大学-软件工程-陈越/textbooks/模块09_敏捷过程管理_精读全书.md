## 敏捷开发
> 对应分集：P33 | 原始标题：《第33讲 敏捷开发》

最后一课，我们讲敏捷过程管理。

到这个时候，你们的大作业已经做了一段时间，对软件工程也算有了一个简单的了解：知道软件要按流程走，知道要写文档，这比没学过软件工程肯定是有提升的。但做的过程中，很多人心里已经冒出问题了——软件工程带来那么多文档，过程又那么复杂，这反而把效率降低了很多。

我要说，这个抱怨不是没有道理。确实，对某些项目来讲，传统的软件过程管理就是存在这些问题。

所以到了 2001 年，Kent Beck 和一些比较知名的软件工程专家成立了一个敏捷开发的联盟，提出了下面这些观点，也就是敏捷开发的整个宣言。这一讲就是把这份宣言展开：它凭什么这么说，敏捷到底是什么，以及它落到工程上是哪几套具体的过程模型。

### 敏捷宣言的四条价值观

#### 个人能力与交互重于过程与工具

软件开发过程中，个人的能力和交互，要比整个的过程和工具更加重要。

这一条不是把过程和工具否定掉。工具和过程是要有的，只是到了具体的项目上，真正决定成败的是坐在那里的人，以及他们之间怎么交互。

#### 可运行的软件重于复杂的文档

工作的交付物、也就是可运行的软件产品，要比各种复杂的文档更加重要。

道理很直白：最终用户看到的是软件，而不是这些文档。你交出一摞写得再漂亮的文档，用户拿不到能跑的东西，对他就没有意义。

#### 与客户的持续交流协作

和客户持续的交流和协作，要比跟用户谈判、然后确定明确的需求信息更重要。

为什么？因为在很多软件项目里，需求实际上并不是太明确的——用户一下提不出非常明确的需求，需要靠我们和用户持续交互，才能把问题搞清楚。

现在的很多大型软件项目，特别是互联网这个行业，还有一层变化：客户可能根本不是甲方乙方的关系，开发的部门和市场部门本来就是在一起的。如果按过去那种方式来做，整个交互过程反而更长；还不如把用户拉进来，持续的交流比先去确认和谈判一份明确的需求更管用。

#### 对变化的快速反应

要对变化做出快速的反应。软件开发过程是不可能不变的：需求在变、人员在变、开发的环境也可能都在变。你要能够对这种变化及时反应。

这种对更改的反应和反馈，可能要比按照一个计划按部就班地做更有效果。因为一直按着计划走，做的却是用户已经不需要的东西，这才是最冤的。

> **提示**：这四条不是把两边对立起来做取舍，不是说过程、工具、文档、明确的需求、计划就不重要了。这些依然很重要；但针对不同的项目来讲，前面那一组——人的能力与交互、可运行的软件、与客户的持续协作、对变化的快速反应——是非常非常重要的。判断一个项目该往哪边偏，才是这一讲后面所有模型的前提。

### 敏捷的含义

什么叫敏捷？它有四层。

- **快速适应更改**：用户的需求改动之后，我们能快速做出相应的调整，整个开发、整个人员都能跟着调整，也就是快速响应用户的更改。
- **高效交流沟通**：能和项目的利益相关者进行非常高效的交流，大家都是同一个团队里面的人，可以充分地交流。
- **把客户拉进团队**：不再是跟客户隔离开、分成甲方乙方，而是把用户和客户做成你团队的一部分。
- **项目组织自主掌控**：整个项目组能够按自己的想法、按自己的判断来组织项目的活动。

敏捷最终的结果是：能够快速地、增量地提交软件交付物，让用户快速看到结果，而不是等了很久很久才看到东西。一开始就让他看到最核心的成果，然后不断改进、不断增长，让用户持续不断地有一些惊喜。

关于敏捷的原则，书上讲得比较细，比如要求整个系统保持比较简单、强调面对面的交流等等。这里不重复，有时间可以回去看那几页。

### 敏捷开发过程的五项特征

敏捷开发现在很热，这几年大家听得也多。敏捷开发的过程和模型有一大堆：极限编程（Extreme Programming，XP）、Scrum、DSDM 等等。但不管它怎么变，总的来看都符合以下几个公共特征。

#### 用户需求驱动

第一个特征，基本上都是用户的需求来驱动。

首先要对用户的需求做一个很全面的分析，用户需求分析这一块是肯定不可避免、不可缺少的。而且我认为，这一块的要求实际上比过去还要更高：你要把用户的需求分析得非常清晰，还要把它 1、2、3、4、5 列得很清楚，并对用户的需求做一个排序。

#### 短周期的计划

第二个特征，敏捷并不是说就不要计划了，它也要强调计划。

区别在于计划的大小。过去的计划可能列得很详细、很宏大，一个大项目一列就是几个月、一年、两年、三年；敏捷的计划是比较短期的，基本上可能就是三周、一个月这样一个计划。

#### 编码与测试的受关注度

第三个特征，整个开发过程重在构造——也就是编码和测试这个环节，它是更加受关注的。

而设计这一块，希望做得到越简单越好。这个“简单”是后面讲 XP 时的一个核心要求。

#### 交付物不断增量

第四个特征，交付物是一个不断增量的过程：不是一次性交付，而是用各种增量开发模型不断演化，持续不断地把软件产品交付给用户。

#### 对更改的适应性要求

第五个特征，比较强调对更改的适应性要求——根据各种变化做出快速反应。

> **易错点**：很多人以为敏捷就是“没有过程”，好像跟 CMM 的 0 级一样，大家没有任何过程约束。**敏捷过程并不是没有过程，它是有过程的**。它只是把软件工程里很多比较繁琐的过程简化下来，保留一些最核心的东西，然后加上增量开发的模型，让用户能够快速看到成果。

所以有人觉得“敏捷开发就是我自己想怎么干都可以”，这不是这么回事。敏捷开发实际上还是有很多模型，待会儿我们看的时候你会发现，这些模型和我们过去的大致也差不多，只是在一些小的地方、在具体过程和方法上做了一些改进。

### 对开发人员素质的要求

要达到敏捷，对软件开发人员的素质要求还是蛮高的。并不是说把一帮新手凑在一起就可以做敏捷开发，这个还是蛮难的。主要有这么几个方面。

- **要有能力**：对软件开发的工具要比较熟悉，对软件开发技术要比较熟悉，而不是都靠新手从头开始培训。培训本身就要几个月，怎么可能在培训期内把一个月的事情做好？所以敏捷团队的成员一定是在技术上、在各方面都非常有经验的人。
- **要精诚合作**：敏捷开发过程中不像过去的软件开发过程纪律那么严格——当然有很多纪律，但不像过去那么严格。所以特别强调大家要精诚合作，不能相互扯皮，因为我们要的是提高效率。
- **要有共同的目标**：后面你们会看到，我们可能就希望在三周之内、四周之内出一个版本。所以大家要有共同的理念、共同的目标，全力以赴把这几周里该做出来的东西做出来。
- **要有决策能力**：遇到更改之后，我们能够自己判断该怎么适应这个更改，快速对人员、对开发计划、对需求做出相应的调整。
- **要能对付模糊问题**：软件开发过程中经常遇到一些悬而未决、模糊的问题，可能包含技术难点——对技术难点，要能快速组织团队把它攻克。还有一类模糊问题更磨人：今天看它是有意义的，明天再看可能根本就没意义。这样的过程多了以后，很多人就会垂头丧气。一开始反反复复还好，到最后天天这么折腾，很多人就觉得没劲了。所以要对付这方面不利因素、对付这些悬而未决的问题，要有一定的解决能力，不至于因为天天在更改就垂头丧气。
- **要相互信任和尊重**：团队要有合作的精神。
- **要有自主组织的能力**：能够自己来把控整个项目组。

> **结论**：我们在组织团队的时候，也要考查一下自己的团队是否符合这几方面的原则。有哪一方面有欠缺，就要做相应的改动、改进。

顺便说一下现状。敏捷开发目前用得非常多，很多公司在用。很多互联网公司、很多小公司，基本上都是采用敏捷开发来做的。但很多传统行业，比方说军方的那些大型工程，因为时间周期比较长、质量要求比较高，这类传统的软件企业里，传统的软件过程管理用得还是蛮多的，敏捷开发用得稍微少一点。总的来看，对中小企业和大型互联网企业来讲，敏捷开发现在用得非常多。

模型也是蛮多的，我们重点讲目前用得最多的两个：一个是极限编程，也就是 XP；第二类叫 Scrum。其他的模型我们了解它的思想就可以了——那些模型有的思想还是不错的，但真正用得不是太多。

### 极限编程 XP

XP 编程最近用得非常多，它是 1999 年由 Kent Beck 提出来的。而且目前很多软件开发工具都支持它：Borland 公司有一个 Together，就直接支持极限编程；Eclipse 上也有很多插件，你下载下来安装好，它就可以直接支持极限编程的一些工作。

XP 的思想基本上是采用了面向对象软件开发过程的一个大致框架，只是在每一个步骤上提出一些新的概念、做一些改进。所以它的阶段划分和过去一样，还是规划、设计、编码、测试这几个阶段，我们一个阶段一个阶段看它改了什么。

#### 规划阶段：功能列表、验收准则与排序

第一步也是规划，也是计划这个阶段。和过去不太一样的地方是：过去的计划可能比较繁琐，要对用户需求做分析，还要制定各种比较详细的计划；XP 这一块第一步同样要对用户的需求做一定理解，但需求理解完之后，要做的是三件事。

**第一件，把需求拆成小的功能项。** 对用户的需求每一项都给它拆分，拆分成很多小的功能，每个功能希望能够顶多三周之内完成。拆成很多小的 `function list`。

**第二件，给每个功能项确定验收准则。** 也就是要回答“我什么时候算做完了”。因为可能三周就要做完，做完之后要看这个东西有没有完成，因此要确定整个功能完成的一个确认准则。

**第三件，对功能进行排序。** 功能很多，所以要排：哪个先做、哪个后做，哪一个重要、哪一个非重要，哪一个是用户最需要的、哪一个是最不需要的，把这些功能做成一个排序，得到这样一个 `function list`。

同时还要制定一些小的、迭代型的计划。这个计划可能不宏大，但一开始最近一个月要干什么，先制定这样一个计划。

#### 设计阶段：简单设计、CRC 卡片与攻关原型

第二个阶段是设计。XP 的设计和过去不太一样：它不像我们过去那样，要对整个体系结构做设计、要做构件级的设计、要做整个 UI 的很详细的设计。它希望的是**简单设计**。

简单设计里，体系结构设计肯定还是要做的——我们前面讲过，体系结构的差异非常非常大，如果体系结构错了，后面就很难改。high level 的设计，也就是概要设计这一块，一般来讲还是要做的。但 detailed 这种设计，也就是详细设计这一块，一般来讲是不做的：详细设计很繁琐、很繁复，要做大量的文档工作，花的时间太多，对我们 XP 来讲，可以逐步来补。

> **定义**：XP 的“简单设计”有两层意思。一层是**设计过程**要简化，把详细设计这类繁琐的文档工作先放掉、逐步补；另一层是**设计结果**也要简化——整个架构尽量做得简单一点，为了解决问题就可以了，不需要把东西搞得很复杂。刻意把东西搞得很复杂没必要，只要把问题解决掉就可以。

设计过程中，XP 比较推崇 **CRC 卡片**（Class-Responsibility-Collaborator，类-职责-协作者），也就是这种表示协作关系的卡片，希望用这种卡片做一个简单的设计。

如果在设计过程中遇到比较难的问题——比方说某个关键技术我们现在还不知道怎么做——那就快速地成立一个攻关组，由攻关组做一个简单的原型，用原型来对这些关键技术、比较困难的问题做突破。先做原型。

#### 编码阶段：结对编程

编码这个阶段，XP 提出两个概念，我觉得非常不错，也很有特色。第一个叫**结对编程**（pair programming）。

结对编程是什么意思？在编码过程中，对同一个功能模块，**两个人坐在一起，对着同一块屏幕进行编程**。过去我们编程一般是这样：大家一分，每个人做一个不同的功能点，做完之后最后再集成在一起。结对编程是两个人一起来做。

两个人一起来做，主要基于什么考量？是希望质量比一个人做要好，因为两个人同时在思考同一个问题。

但两个人同时思考同一个问题，并不是说两个人都做同样的重复工作。它希望两个人在做的时候侧重点不太一样：比如一个人关注整个架构，另一个人关注实现这个角度，也就是两个不同的角色划分。

> **易错点**：结对编程的缺点也是很明显的。软件开发过程中经常是人不够的，很难让两个人同时来做同一个功能模块。对大公司来讲可能是有这个条件的；但对一般小公司来讲不太可能——对小公司来说，一个人恨不得能做两个模块，而不是两个人做同一个模块。对大多数中小型企业来讲，这个成本根本负担不起，经常是赶时间，一个人白加黑、五加二，一个人做两个模块然后交付。

对大公司来讲，它不仅做结对编程。像 IBM，我们过去也讲过，它经常是两个团队来做：对同一个比较重要的项目成立两个团队，这两个团队采用完全不同的技术路线——比方说一个团队用 Java 来做，一个团队用 C 来做——最终让用户来判断哪个东西做得好，就把哪个交付给用户。

当然这也是因为它能拿到大的订单。同样一个订单，IBM 可以签到一千万，国内的一些中小企业签不到一千万，可能只能签三百万。一千万有一千万的做法，可以这么干；对中小企业来讲，完全不可能做这个事。

#### 编码阶段：测试驱动

第二个概念是**测试驱动**（test-driven development，测试驱动开发），这也是非常流行的一个观点。

过去我们讲软件工程，做法都是先写代码，代码写完之后，单元测试是由开发人员再写单元测试的脚本、测试类。这种方式实际上效率不高：因为你在编码的过程中，经常想看看这个结果对不对，为此要写很多辅助程序。

测试驱动主张反过来：**先把单元测试的用例写好，然后再做编码。**

> **结论**：单元测试是省不掉的，一定要做。那与其后面做，不如前面做——前面做的效率可能更高。

所以测试驱动就是把单元测试和编码的次序提前：先生成测试用例、撰写测试用例，然后做后面的开发工作。

#### 编码阶段：重构

这一块还有一个非常重要的概念，就是**重构**（refactoring）。

因为 XP 的周期都比较短，一个周期可能就是三周、一个月，就要出一个东西。时间短，整个设计就可能没那么完善，所以在后续的开发过程中、在后续的整理过程中，即使已经交付给用户之后，我们也经常要做代码的重构工作。

> **定义**：重构就是**保证用户接口、用户的交互行为不变，只做内部结构的调整**。用户看得见的接口一律不改，改的是里面的结构。

#### 测试阶段：确认测试与版本发布

第四个阶段是测试。测试实际上和过去也差不多，只是刚才讲的单元测试这一块会和开发做融合——开发和测试做了融合。

其他方面，过去该做的测试还是要做，特别要重点做一个**确认测试**：功能做完之后，看有没有满足用户的功能需求，性能需求有没有达到指标。

做完之后，下一步就是 release，出一个软件版本、一个软件的增量。这个版本包含一开始这个周期所设定的各个功能。这些功能做完之后，就开启下一个循环：又把一些新的功能拉过来，重复这样一个循环，直到用户所有的功能需求都满足、都完成，整个开发过程才结束。

整个 XP 的开发过程大致就是这样：

```text
XP 的单次迭代循环

plan                    需求 -> 拆成小功能项 -> 定验收准则 -> 排序 -> 短期迭代计划
    |                   简单设计：概要设计做，详细设计不做
    |                   用 CRC 卡片做简单设计
    |                   关键技术难点 -> 攻关组做简单原型
    v                   简单设计完成
code                    结对编程 / 测试驱动 / 重构
    |                   先写单元测试用例，再编码
    v                   编码完成
test                    单元测试与开发融合
    |                   确认测试：功能需求 + 性能指标
    v                   测试通过
release                 交付本周期设定的各个功能

    把新的功能拉过来
    <-------------------------------- 回到 plan，开始下一轮循环
```

读图说明：横向是一次迭代的推进次序，从规划一路走到版本发布，然后带着新功能回到规划，一轮一轮重复，直到用户所有功能需求都被满足。

从这个过程可以看到前面讲的几点：**XP 是有过程模型的**，不是说极限编程就是大家凑在一起发挥个人能力、爱干嘛干嘛，那是一个误解。它同样有整个开发过程，只是每个环节做了一些调整——尽量把繁琐的工作去掉，设计做得更简单，开发周期控制在不超过一个月（三周、一个月一个周期），让用户能够持续不断地看到结果。

### Scrum

第二个用得比较多的、最近几年也用得比较多的是 Scrum。它也是一个比较常用的软件开发过程模型，而且这个过程模型也比较简单。

#### 产品功能列表

一开始是一样的，也要对整个软件产品做分析，得到一个软件产品的功能列表。Scrum 里它不叫 `function list`，叫**确认项**（product backlog），实际上就是一个 `function list`。得到之后，对它做一个排序，重要的先做。

#### 冲刺与冲刺目标

排完序之后，第一步就是从 `function list` 里面拿出一些功能，这些功能形成一个功能集合，对这个功能集合做一个研制的周期。这个周期称为一个**冲刺**（sprint）。

Scrum 这个概念本来就是从橄榄球球赛来的。它是橄榄球的一个专用术语，指大家围成一个圈，中间一个球，把球按住；冲刺也是橄榄球里一个很重要的术语——抱着球从这边跑到那边去。用到软件开发上比较形象：一次冲刺，就是我们抱了一系列软件功能项，在这次冲刺里面要把这些功能项的功能全部实现、全部完成。所以所谓的确认项，实际上就是确定一部分的 to do list。

#### 冲刺内的工作细分

冲刺的目标确定好之后，下一步就开始做。第一步要对这次冲刺的功能做一个细分——因为这几件事可能有多个人在做，所以要把功能拆分，确定每个人干什么事，把它再细化一下。

细化完之后，就是三十天一个冲刺（三周或者三十天，你可以自己确定是三个礼拜还是四个礼拜，一般一个周期），然后每个人按照自己的工作做下去。

#### 每日 15 分钟站会

在这个做的过程中，有一个小周期，这是 Scrum 一个很有特色的东西：**每 24 小时、也就是每天有一个小会**。

很多公司现在每天都在这么干：开发团队每天早上一来，开一个 15 分钟的短会。这个短会一般来讲站着开，大家站在一起交流。

这 15 分钟主要讲三个方面的问题。

1. **昨天你做了什么事，这些工作有没有完成。**
2. **昨天做事的过程中有没有什么问题**——有没有没做完的，或者碰到什么技术问题，提出来。
3. **今天要干什么事。**

每天 15 分钟，团队成员站在一起把这些事讨论一遍，简单开个短会，把昨天的事总结一下，把今天的事安排一下。

> **提示**：这个短会非常重要。因为大会解决不了问题——大会上讲的事都比较宏观，但真正解决问题的是小会。每天大家站在一起一起谈这几件事，对整个进度的了解会比较清晰；对每个人也是一个促进作用：有的人可能想偷懒，但每天都要讲、每天都要汇报，这个时候你就很难偷懒——真偷懒了，你在那里就没法讲。所以每天 15 分钟的这个会，会对每个人形成很大的压力和促进作用。

#### 版本交付与支撑工具

然后一个周期出来一个版本，给用户展示，让用户来看。整个 Scrum 的大致过程就是这样，过程很简单。

Scrum 这一块有很多工具来支撑。有一个工具大家可以去下载一下，叫 **ScrumWorks**，过去我们一直在用，挺好的。它有开源版本、免费版本，你可以下载下来用。

ScrumWorks 实际上是一套工具：主界面上有很多的 `function list`，你可以确定指派——这个功能谁来做，直接指派给人；然后每个人整个工作的进展都可以进行跟踪。这是它的相关支撑工具，用的还蛮多的。课后可以去下载用一下，这个工具比较实用，以后为了工作可能都用得到。

### 其他敏捷过程模型

除了 XP 和 Scrum，还有其他一些过程模型。

#### DSDM：动态系统开发方法与二八原则

**DSDM** 就是动态系统开发方法。这个方法实际上和我们过去的方法比较类似，整个有点像我们过去快速开发的框架。

它前面有两个阶段：一个是**可行性研究**阶段，主要研究这个项目是否适合用这个模型来做；第二个是**需求分析**阶段。这两个阶段做完之后，后面跟了三个大的循环。

三个循环的编排如下：

```text
DSDM 的阶段与循环

可行性研究        判断项目是否适合用本模型
      |
      v
需求分析          需求的分析
      |
      v
  +-----------------------------------------------------------------+
  | 大循环 1：功能模型构架阶段                                      |
  |   对需求做详细分析                                              |
  |   内部由很多小循环组成，不停地循环                              |
  |   直至把所有东西都做好                                          |
  +-----------------------------------------------------------------+
      |
      v
  +-----------------------------------------------------------------+
  | 大循环 2：设计的构建环节                                        |
  |   每个环节都：制定计划 -> 开发原型 -> 评估原型                  |
  |               -> 确定下一步的计划                               |
  +-----------------------------------------------------------------+
      |
      v
  +-----------------------------------------------------------------+
  | 大循环 3：最终构建阶段                                          |
  |   原型已经设计好，移植到可运行的环境下                          |
  |   也要经过一些循环来完成                                        |
  +-----------------------------------------------------------------+

  每个环节都可以返回过去：
  在最终实现环节发现问题 -> 回到构建阶段
```

读图说明：纵向是两个前置阶段接三个大循环，每个大循环内部又套着“制定计划—开发原型—评估原型—定下一步计划”的小循环；图下方的箭头表示每个环节都可以往回走，在最终实现时发现问题就回到构建阶段。

DSDM 在安排任务的过程中，主要强调一个**二八开的原则**，也就是帕累托原则（Pareto principle）：我们用 20% 的精力就可以完成 80% 的工作、80% 的功能。所以每次制定开发计划的时候，我们希望每个循环都按这个原则去安排任务——只做那 80% 的工作，花 20% 的精力。

#### FDD：特征驱动开发

**FDD** 是特征驱动开发（Feature Driven Development）。它比较适合中型的项目：保留了很多传统软件开发过程的思想，同时又加入了敏捷开发过程的一些理念。

整个模型有点像我们过去那个快速开发模型：前面走系统分析，后面分成很多组来做。首先一样，要建立整个需求模型，然后对整个需求做一个 list，对每个模型做一个评估。他们对功能模型的称呼叫**特征**（feature）——一个特征就是一个功能。对这些特征进行计划，然后分成很多组，这些组同时来做。这个很像我们过去快速开发的模型。

#### ASD：适应性软件开发

**ASD** 是适应性的软件开发过程（Adaptive Software Development）。这个理念挺好，但实际上用的并不多，很少有人用。

它认为整个软件开发过程最关键的地方是**人**，因而要考虑怎么保证人的主动性能够发挥出来，并据此提出一个过程模型。这个过程分三个阶段：**思考**阶段、**协作**阶段、**学习**阶段。学习这个阶段就是要对整个软件过程做一个验尸报告，做总结，总结不足。

这个过程用的不是太多，了解一下就可以了。

#### 水晶过程模型

还有**水晶**（Crystal）这种过程模型，用的也不多。它的核心思想就是主要强调面对面的交流。

#### 系统模型的取舍与改造原则

最后还有一个叫**敏捷模型**。它是什么概念呢？

我们知道在软件开发过程中会经常用到各种过程模型：我们有 CRC 卡片、有 DFD 图、有状态图、有泳道图，有各种各样的图形、各种各样的模型。这些模型对用户来讲感觉到很庞大，不知道用哪个好。

敏捷过程就是基于这样一些理念，提出使用这些模型的一些观点。

- **可以用多种模型来表达、刻画同一个系统**：从不同的方面来刻画系统，把系统刻画得很清晰。
- **保留有价值的模型**：整个开发过程中，希望能保留一些有价值的模型；一些比较繁琐、没有价值的模型，在分析阶段可能还有，后面没有了，我们就可以把它删掉、摒弃掉。
- **内容比表现形式更重要**：有很多过程模型、很多需求分析的模型，这些图形这些方法不一定全部采用，可以采用一部分，以内容表达清楚为主。整个的符号也可以不规范，都没关系。比方说状态图，有人可能画得很规范、很漂亮，有人可能画得很简单，没关系——只要能把问题表达清楚、刻画清楚就可以，不一定画得非常规范。
- **允许适应性改造**：每个模型都规定了很多条条框框，我们在用的过程中不一定全部搬来，可以做一些适应性改造：有用的保留下来，没用的摒弃掉，而且可以加入我们自己公司的、自己团队里有特色的东西。

这个叫敏捷模型。它主要是提出一些原则，让你来判断该怎么样来使用这些需求分析模型。
