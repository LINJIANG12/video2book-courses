## Web工程概述
> 对应分集：P21 | 原始标题：《第21讲 Web工程概述》

需求分析讲完之后，本来应该接着讲设计了。但今天我们中间先停一下，专门来介绍一类软件：Web 应用（web app），以及针对它的 Web 工程（web engineering）。

为什么要单开一讲？因为这一类软件在这一版教科书里，**第一次被当成一个额外的、专门的主题提出来**。教科书肯为它单列一章，说明它有一批与众不同的属性（attributes）——它有自己的一些特点。而这些特点的后果很实际：后面我们做分析、做设计、做测试，针对 Web 应用的做法和针对普通应用的做法，是**有点不一样**的。

那么，要知道在什么地方做得不一样，前提是先弄清楚：Web 应用到底在哪些方面和普通应用典型地不同。这一讲的主线就是这条——先把特点讲清楚，再看工程的各个环节怎么去照顾这些特点。

### Web 应用的特点

我在课上先让大家自己说，你们来数一数 Web 应用有什么与众不同的地方。要理解"特点"这两个字的用意：**以后你做任何事情的时候，都要记住照顾到它这些特点**。特点不是拿来背的名词，是拿来指导决策的约束条件。

#### 严重依赖网络

第一条我先说了：它是基于 Web 的，是基于网络的。**它严重依赖于网络。**

#### 跨浏览器兼容性与外观

有人做过 Web 应用吗？我本来觉得你们中间应该有人做过。都上到三年级了，还没做过？——有人说：跨浏览器。对，兼容性。

**要照顾浏览器。** 不同的浏览器，同一个页面显示出来的东西可能不一样。也正因为是给人看的，你就得特别注意它的外表、它的美观。

#### 本地存储少、性能压力大

本地存储比较少。本地存储少的意思是什么？**是它要快。** 它的性能（performance）很重要。

#### 开发要敏捷、迭代周期极短

因为这类需求通常来得很快，所以它的开发应该做得很敏捷。而且 Web 应用上线之后，可以用一个很短的周期来迭代。

一般你接到 Web 应用这种任务的时候，人家不会说"我给你三年，你把这个东西做出来"——那不可能。**一般来说给你三个星期就已经很长了**。最好就是"做个网站吧，给你一个星期，赶紧把这东西给我弄出来"。这就注定了你的过程模型（process model）肯定是一种非常敏捷、非常快的模型。

#### 更新与迭代是连续进行的

它的更新要求极高。对传统软件来说，可能两个星期更新一次，也可能一两个月更新一次，差不多就这样；但对 Web 应用，可能两三个星期就更新一次。这对维护团队的管理能力要求很高。

更进一步：它甚至可能是**无缝衔接**的。它没有"我两个星期上一个新版本"这种固定节奏，它那个版本**一直在不停地变，连续地在变**。这一点要求非常高。

#### 用户交互性强，而用户群体不可知

用户的交互性要考虑得很周到。而最麻烦的地方在于：**你不知道是什么用户。** 各种稀奇古怪的人都有，因为它是在网上的。

这里有个对比。支付宝很大程度上也是一个基于 Web 的应用。你和普通的银行系统不一样——如果你给一个小银行做一个只给它员工用的系统，那你的用户群是固定的：你可以训练他们，让他们不要犯错误，他们有什么行为都在监控之下。但支付宝一上网，你都不知道谁在用你这个东西，什么人都有。

#### 数据存在服务器上，安全成为核心

传统软件的数据存在本地，存在用户自己的电脑里；而现在的 Web 应用，数据通常存在**服务器的数据库**里面。这带来两个后果：

- 用户的数据存在你的服务器里，你就需要特别保证它的安全。**安全性（security）是一个非常重要的因素。**
- 它还决定了你在组建团队时挑什么人：除了编码要强的人，**你还需要一帮对 security 很懂行的人**。

#### 大规模并发与不可预测的负载

如果这是一个放到网上让大家用的软件，你还要特别考虑工作负载（workload）的问题，或者说并发性（concurrency）——你得有很强的并发处理能力。

这件事我有亲身体会。当年北京办奥运会的时候，抢奥运会门票那个网站，开放的一瞬间就崩溃了，就死掉了。正好我有一个表弟在那个技术组里。过年的时候我看见他，嘲笑他，我说你们做的是什么土网站。他说不是我的错——我们本来要自己开发，领导说不要，领导说我们要引进美国当年办奥运会时用的那套软件，美国人当年就是用那个东西来抢票的。我说：美国才多少人呢？**你严重低估我们中国人民的热情。** 然后我替他算了一下大概的那些参数，最后算下来：那套软件可以处理的并发是**每秒钟五个**。

每秒钟五个——这不可思议。每秒钟 500 个还不一定够，每秒钟 5 个并发，那不是瞬间就崩溃？所以它崩溃是很正常的。

紧接着两件事是挨着的：

- **不可预测的负载（unpredictable load）**：你不知道你这个软件的使用量会是多少。它可能是季节性的——有一阵子疯抢，过了以后就没人用了。所以那个 workload 每天跟每天不一样，哪个小时到哪个小时的时间段也不一样。
- **性能（performance）**：对访问效率一定要特别注意。如果人家打开半天都打不开你这个网站，半天还在 loading，人家可能不耐烦就走了。尤其是你想要吸引别人来访问的网站——性能做不好，你就没有人气了，人家半天打不开就走掉了。

#### 全天候可用性

**可用性（availability）** 意味着你必须有一个非常强大的维护团队。通常来说，你挂上网的东西，大家都默认你应该是每天 24 小时、一星期 7 天、一年 365 天都 available 的，不应该有太多挂掉的时间。

#### 数据驱动、内容质量与美观

大多数网站主要是**数据驱动（data-driven）** 的。它们有一个共同的基本功能：向用户展示某一种类型的数据——不管是视频、音频、文本还是别的什么，它有一个展示的功能。所以你在设计的时候要意识到，这是一个以数据驱动为主的网站类型。

如果你靠网站的内容来吸引人访问，那么它对内容质量的要求，要比一般软件**高得多**。反过来看：如果这个软件只是给一个公司内部的员工用，那么措辞好不好、网站美观不美观，这些都是次要的——它能支持工作流程就可以了。但挂出去给不知道什么人看、你想吸引尽可能多的人眼球的东西，内容质量以及美观程度就相当重要了。

还有两个特征需要点出来：

- **连续演化（continuous evolution）**：这是 Web 应用一个非常重要的特征。它意味着你把团队组好之后，**不是**说给你一个星期把网站开发出来，开发了一个星期大家就散伙——肯定不是这样一种团队结构。
- **即时性（immediacy）**：要求很快。通常人家要做个网站，今天跟你说，最好你明天就能做出来；如果不可能，最多给你一个星期。我不能说我今天规划了一个网站，然后三年以后你再交付——那是想都不要想。这是他跟传统软件一个很重要的不同点，也就决定了我们整个过程模型的设计要**以快为主**。

#### 安全与美观在工程实践中的位置

Security 在 Web 应用里扮演了一个非常非常重要的角色。

不过要说清楚：因为你们现在学的知识内容有限，所以我们做支付宝这个课堂大作业的时候，**对 security 就不做特别高的要求**。到底要求到什么程度，那你们去跟助教谈，跟你们的客户去谈——我跟他们讲的是不做特别高的要求。但真正的支付宝，security 肯定是不用说的。

最后一个是**美观**。美观可能是其他软件不太看重、没那么看重的。但一个网站漂亮不漂亮，是它吸引人的一部分，你要有一个很漂亮的包装。也就是说，你在团队里拉人的时候，**必须有一个强大的美工**。

美工其实很难找。做界面的人和做美工的人是两种人。像我们自己的学生里，做开发、做功能开发的人有很多很多，但做 UI 的人就很少。而我们其实默认了"UI 就包括了美工"——这是不对的，UI 跟美工可以是两个人。这个后面专门讲 UI 的时候还会再提到。总之，美工在 Web 应用里通常占了一个很重要的位置。尤其是你开发一些网络游戏之类的东西，美工也是一个非常要紧的角色。

> **结论**：以上就是 Web 应用几个重要的特点。了解这些特点之后，才可以去关注它的各个环节里，我们是怎么照顾到这些特点的。

### 教科书的分类框架与课堂练习

在讲各个环节之前，先看一下书上大概把 Web 应用分了几大类。

对这个分类，**你可以同意，也可以不同意**。它不一定就特别有道理，但它有它的道理。你看完了以后如果觉得"这么分类是不是有点别扭"，那你就可以保留你的看法。如果你有不同的意见，有兴趣的话可以写一个小小的 essay 去论述你自己的观点——这种新的观点我都是很欢迎看到的。我这里只负责介绍书上是怎么分类的。

#### 十种类型与典型代表

| 类型 | 含义与特征 | 典型例子 |
| --- | --- | --- |
| `informational` | 基本上是静态网站，发通知、发新闻，`read-only`，没有互动，只是发布消息用的 | 各类信息发布站点 |
| `download` | 专门给你提供资源下载的 | 源网那类提供高清电影下载的站点 |
| `customizable` | 允许你根据自己的个性做定制的 | 博客（非常典型） |
| `interaction` | 交互用的 | CC98、飘渺水云间、QQ |
| `user input` | 让你在网上填表用的 | 各类在线表单 |
| `transaction-oriented` | 事务类型的：你提一个请求，它按你这个请求走一个处理流程；不同的请求走不同的流程，处理不同的事务，起的是一个事务中心的作用 | 各类在线业务办理系统 |
| `service-oriented` | 提供某种服务的 | 自己想一想，我们学校有什么东西是这种类型的 |
| `portal` | 门户网站，起一个门户作用的 | 各类门户 |
| `database access` | 提供数据库访问的 | 各类数据查询站点 |
| `data warehouse` | 再大一点的数据库的集合，即数据仓库 | 见下文辨析 |

#### 数据仓库（data warehouse）与数据库的区别

听过 data warehouse 这个词吗？知道 warehouse 是什么东西吗？

我们国内好像没有类似于美国那种 warehouse 商店。Warehouse 就是像仓库一样的商店，它卖什么东西都是跟批发差不多的。

打个比方：你去买饼干，到普通的商店里面——也就是到普通的 database 里面——你就买这一种饼干，买一小盒。你去 warehouse 里面买东西，人家不卖你一小盒，要么就是一打一包的，你要买就这么一大箱扛走。

所以 data warehouse 基本上你可以理解成**数据库的集合**，而且是好多不同数据库的数据的集合。当然它**不是一个简单的拼凑**：它要把不同数据库里面的数据整理一下，然后重新归类，再组织一下。总之它比 database 的规模要大很多。

#### 课堂练习：三个问题

今天第一个要讨论的问题是这样的，其实是**三个问题**：

1. 我们整个的支付宝这个 project，它是属于哪一类的？你要简单说一下理由——它有什么特点，所以它属于哪一类。
2. 你自己负责的那个模块，是不是具有 Web 应用的特征？如果是，它属于哪一类？如果不是，你要说个理由：为什么它显然不具有 Web 应用的特点。注意——**不是每个模块都具备**。
3. 你挑两种类型（书上列了 10 种，你挑自己知道比较多的两种），每种举一个或者两个非常著名的网站。**不能只给我列一个网站名字**，你要讲一下道理：这个网站是干嘛的、它具有什么特点，所以它应该属于哪一类。

课堂时间有限，所以只挑两种；否则我应该让你们把十类每类都举几个例子出来。**作为做我们这一行的人，要多知道一点。**

### Web 工程的层次结构与过程模型

Web 应用作为一类需要被特殊处理的软件，我们需要知道它的特点；至于它的整个流程，其实**都是围绕这些特点来设计的**。

我们说普通软件的时候，说软件工程是一个层次化技术（layered technology）。Web 工程也是一样。

```text
+---------------------------------------------------+
|  tools      常用工具：HTML 等（针对性更强一点）    |
+---------------------------------------------------+
|  methods    注重 communication、requirements and   |
|             analysis、design、testing，都要做      |
+---------------------------------------------------+
|  process model   agile / incremental（特点：快）   |
+---------------------------------------------------+
|  quality focus    以质量为中心，始终在最底层       |
+---------------------------------------------------+
```

读图说明：层次自下而上依次是质量焦点、过程模型、方法与工具，与普通软件工程的层次划分同构，区别在于每一层的内容都向"快"和"连续演化"倾斜。

- **最底层是质量焦点（quality focus）**。我们做什么都还是要以 quality 为中心。虽然 Web 应用要求你什么事情都做得非常匆忙，但**很匆忙不代表就不做**，所以你还是要注意控制这个 quality。
- **在此之上，我们选择的过程模型通常是敏捷型（agile）**。敏捷开发这个 process 我们放在最后一节课才给大家介绍，为什么放最后一节课，到时候再说。总的来讲它的特点就是快——做什么事情都要快。
- **为了达到快这个目的，它要做的一些方法**，大面上看其实还都是我们普通软件工程里一样的那些方法：要注重沟通（communication），要做需求与分析（requirements and analysis），要做设计（design），要做测试（testing），都要做。只是它**有自己的一套方法**。
- **它用的工具**，是一些常用的工具，比如 HTML 等。跟普通的软件开发相比，**它的针对性更强一点**。

#### 连续演化与渐增交付

它的过程模型，我们说了，一定要注意两点：一个是**为了快**，一个就是那种**连续演化**——连续持续更新、不断推进的特点。它不会说过三五个月给你推出一个新版本，一般网站不这么干，它随时随地都在更新它的版本。

所以你做的时候，根本就不要想到"一步到位"。它一般来说是一个**渐增交付（incremental delivery）**，是一个渐增的模型，肯定是一点一点一点一点交出来的。再加上改变（change）这件事情是经常发生的，它有一个非常短的时间线（short timeline）。这就决定了：我们要选择一个 **incremental process model**，同时它在大多数情况下是一个 **agile process model**。

```text
                    .-'''''''-.
                 .-'           '-.
               .'    .-''''-.     \
              /    .'        '.    \
             |    /            \    |
             |   |   .-''-.     |   |
             |   |  /      \    |   |
             |   | |  core  |   |   |
             |   |  \      /    |   |
             |   |   '-..-'     |   |
             |    \            /    |
              \    '.        .'    /
               '.    '-....-'    .'
                 '-.           .-'
                    '-.......-'
```

读图说明：这是过程模型的示意图，你们看上去应该很眼熟了——我们之前在讲过程模型的时候，很多迭代式的、渐增的模型都是这种类型。它是一圈一圈的：有人喜欢顺时针画，有人喜欢逆时针画，这里是逆时针画的。

每转一圈，迭代出去一个增量（increment），再转一圈又出去一个增量，总之都是这么一个类型。而在中间，**construction 这个部分同时还伴随着重构（refactoring）**，不停地做重构。重构是什么？——就是重构。那是一个大坑：你要做重构之前一定要想好，要小心，这个我们后面再说。它实际上是在不断重构、优化它的内部结构，同时不断添加新的功能，这样就出来一个新的增量。这是它的过程模型的基本形式。

### 动手之前的五个问题

在开始做事情之前，你们这个 team 一定要搞清楚下面几个问题。这是最起码要搞清楚的。

#### 网站内容的重要程度

你要做的这个 website home page 到底有多重要？这决定了它内容敏感（content-sensitive）到什么程度：**你是给国防部做的呢，还是我们这门课要做一个网站给大伙儿用？**

再往下细分：我这门课要做一个网站，是给我内部的学生、我们自己用着玩玩的，还是我要放到外面去，让全国的学生、全国高校的学生都可以看到？内容的敏感程度是不一样的。

#### 页面布局的最有效套路

你这个特定的 Web 应用，page layout 最有效的大概是一个什么套路？

- 是上面横着一条 menu，然后下面放内容？
- 还是横着一栏、竖着一栏，而竖着的那一栏有人喜欢放左边、有人喜欢放右边？

整个页面要怎么布局，先想清楚。

#### 内容用什么媒体形式呈现

你是就用简单的文字去展示内容，还是用视频？用音频？用 Flash？还是用别的什么？哪一种效果最好？

#### 用户想做什么，以及他有多大的耐心

用户在访问你这个网站的时候，他想要做成什么事情？他要做成这件事，**有多大的耐心**？他最多愿意做几步操作？

这就取决于你这个网站是给谁做的，你主要面向的用户群是什么人：

- 给老年人做，是一个风格；
- 给大学老师做，是一种风格；
- 给幼儿园小朋友做，又是另外一种风格。

你能指望你的用户做成什么程度的操作，去达到他想要达到的目的？

#### 导航、检索与表单填写量

- 你这个网站到底有多复杂？页面导航这件事情是不是非常重要？这就决定了你是不是要做 search，或者要做一个导航图之类的东西。
- 如果你有提交表格的话（一般来说都有了，**起码得注册一个账户**），那你注册账户的时候，你能指望用户把这个注册表填完吗？一般来说，商家希望这个表填的东西越多越好，我希望了解的内容越多越好；但是要填的太多，用户根本就没有耐心填完——"这么烦呢，我不注册了，算了，我走了"。**你要不要把人家烦得跑掉？**

> **易错点**：这个平衡是非常微妙的（delicate），你要找到那个平衡点。而且它其实跟导航是连在一起的：网站如果很复杂、内容非常多，你是不是需要一个 search 功能？这个 search 功能需要强大到什么程度？

最后还有一条：**你的网站要不要照顾残疾人？** 要不要做到无障碍访问，你有没有可能做到这一点？

以上这些，基本上就是你准备动手开始干活之前，要大概搞清楚的几个问题。

### 最佳实践

在这一讲的最后，列举一些 best practices——做得比较好的那些 team，他们是怎么做的，你想把事情做好，最佳的做法有哪些。

前提要摆在前面：**大家时间都很紧。** 时间很短促，然后要在很短的时间里面做很多事情。在这个前提下：

1. **花时间搞清楚业务需求与产品目标（take the time to understand the business needs and product objectives）**。大方向先要搞清楚，这个时间是不能省的——**有一些时间是不能省的**。你要花时间把大方向先搞清楚，细节问题可以慢慢来。
2. **采用基于场景的方法（scenario-based approach）**。很多网站开发的技巧就是做一系列的用户场景（user scenarios），做一套一套的用例（use cases），然后根据这一套一套的 use cases 来做你整个的规划和开发。
3. **仍然要先有一个计划**。虽然时间很短促，你还是要先有一个 plan。这个 plan 跟传统软件工程里要求的那个非常严格的 plan **不是一个数量级**的——它是轻量级的 plan，但你仍然要有。不能说没有 plan 直接就动手开始干，这是要麻烦的。
4. **动手干之前，先稍微做一下建模（modeling）**。这是为了方便后期。尽管你可能是一个很轻巧、很小巧、人很少的开发团队，但你要想到后期是一个**长期的维护过程**——它不是说你开发一个星期，然后大家就散伙了。你开发用了一个星期，这个网站的存活期你不希望它只是几个月吧？你也不希望它只是两三年吧？

   举个例子：你们如果都知道我们的 ZOJ 系统，那个 online judge，玩 ACM 竞赛的同学都很熟悉那个系统。那个系统最早是 2001 年投入使用的，现在多少年过去了？它不可能还是原来那个团队在维护。它也换了好几个版本了——2.0 这个版本是 2008 年上线，到现在又是多少拨学生毕业了。当年开发团队的人早都走得干干净净了。所以后期维护你还是需要留一定的文档，留一定的东西给后面的人来看。**这个 modeling 不能完全没有**：你可以写得比较简单，但一定是要有的。

5. **对一致性与质量做检查**。你还需要有一个大概的检查，在 consistency 和 quality 这方面——它的一致性，以及它的内容、模型的整体设计质量，要有一个把握。

6. **尽可能重用已经做好的模块，这是"快"的根本**。怎么能做到快？就是尽可能找已经做好的、可以重用的模块。如果你是一个专门做网站的——我们就有你们的学长毕业以后自己开公司，专门给老师们做各种课程网站——那他就有很多可以重用的东西。因为我是专门做这一个领域的网站的，专门做教育领域网站的，它有一些共性，那么他要注意把这些共性保留下来，后面就会做得越来越快。**这是快的根本在这里。**

7. **上线之前内部一定要做充分测试**。不能够把测试留给用户。不能抱着"反正我是要上线的嘛，我直接把它挂出去，然后这帮人一用我就知道了，有什么 bug 都出来了"这种想法。你要想一想：你就把这件事情交给你的用户，他们上线哗一用，然后你就挂掉了，**瞬间挂掉了**，那么后面至少一大半的人不会再来用了，走掉了。这是很大可能的。

   所以上线之前你自己是要做一个充分测试的。而这个测试跟普通软件的测试**不太一样**。不一样在什么地方？它其实挺难的，比普通的软件测试还要更困难一点。难在什么地方，大家再去考虑，后面我们专门还会再讲。

题干：

2. 你自己负责的那个模块，是不是具有 Web 应用的特征？如果是，它属于哪一类？如果不是，说明理由——为什么它显然不具有 Web 应用的特点。

解析与答题依据：

- 第 1 问的落点不在类型名称本身，而在**用特点去论证类型**。正文中已经给出了判断所需的特点：支付宝是严重依赖网络的、用户群体不可知的（"你都不知道谁在用你这个东西，什么人都有"）、数据存在服务器的数据库里因而安全要求极高、面临大规模并发与不可预测负载、要求接近 24×7 的可用性。把这些特点摆出来，再对照十种类型的定义去归位，理由才立得住。

## Web项目管理
> 对应分集：P22 | 原始标题：《第22讲 Web项目管理》

接下来这一章，我要大面上讲一件事：你把一个 `web application`（Web 应用）当成一个 `project` 开始运行的时候，大概要考虑哪几方面的事情。注意是"大面上"——具体的需求怎么做、设计怎么做，那是下一次课再仔细讲的事情。

这第一步有个名字，叫 `initiating`，也就是先把一个 Web 应用项目启动起来。

### formulation 阶段的终点与一次提问练习

第一步是 `formulation`。这个词你去查字典，查不到一个很合适的词来描述它，勉强说就是"大概规划一下"。放在项目里，它的终点非常清楚。

> **定义**：`formulation` 阶段从你最初听到一句模糊的想法开始，到你拿到一个大致的需求为止。

我举一个例子。我说我要给我们这门课程做一个课程网站——我现在这个网站做得不太满意，所以我要换一个，重新做一个。我把这个消息发布出去了，在 BBS 上挂了个帖说征人做网站。然后你来应征。

你来应征，你打算怎么办？你找到我，你要跟我谈。你得问我一些问题，你得从我这儿了解一些东西——一直到大概把一个需求搞清楚。这个过程就是 `formulation`。

那么问题来了：假如你今天过来应征，你要怎么准备？你打算问我什么？

这个问题我当场丢给过班上的同学：你来列一组问题，给你三分钟到五分钟，写完签上名字交。而且我加了两个条件。

第一，这些问题列出来是要有学问的。第二，它得有个顺序：你要先问什么，再问什么；先搞清楚什么，再搞清楚什么。同样的一组问题，顺序不一样，你得到的效果就是不一样的。

你们交上来之后我还得把顺序调来调去，说明你们还是挣扎了一下——我到底先问什么。很多人第一口就想问"有钱没的"。这么问多不好听啊，对不对？你要自己能推导出来到底有钱没有。

> **提示**：把"他有多少钱"当成第一个问题，问法上难看，答案上也不可靠。真正决定预算的是他为什么要做这件事，所以第一问应该落在动机上，预算从动机里推。

### 需求必须覆盖的三个问题

不管你怎么设计问题清单，总体来说有三个方面的内容你必须覆盖到：

1. 用户为什么要做这件事；
2. 他想要做成哪些事；
3. 谁来用——做好了以后到底是谁来用。

这三个方面漏掉任何一个，你的问题就是不全面的。

#### business need：为什么要做这个网站

第一问是 `identification of business need`，识别业务需求。什么叫 `business need`？就是你为什么要做这个网站。你是老师，你做这个网站干嘛用的？是为了申请报奖？还是要申请教育部的什么项目？还是学校要求的？还是说没什么事，自己吃饱了撑的想做一个？

> **结论**：先搞清楚"到底为什么要做这件事情"，你才谈得上后面所有的问题。

在问这个问题的同时，你其实还在隐约地摸另外一件事：做这件事情对我来说能带来什么好处，我愿意付多少代价去做。这个预期你要有。

我是自己做着玩的，你就不要指望我给你十万二十万去建一个网站——我自己吃饱了撑的，对吧？你心里得有这么一个预期。

#### objectives 与 major features and functions

第二问是 objectives：我做这个网站到底是干嘛用。

一个网站、一个课程网站，它有很多种。我是只为了把我的课件放上去、方便学生下载？或者我有些课外的 reference（参考资料）要给大家放上去，专门供你们下载？我要不要专门组织一个论坛？我要不要布置作业？还是像我们现在这个网站——它原来是有打分功能的——我还要不要打分？

问完用途，你还得落到 `major features and functions` 上：到底我们需要的功能有哪些。这是后面所有设计工作的输入。

#### 谁来用：单用户还是整个课程组

第三个问题是最要命的一个：它是给谁用的？

是给我一个人用的——你们就下载——还是要给我整个课程组五六个老师大家一起来用？

做我们现在在用的这个网站，当时做网站的你们那位学长就犯了一个很严重的错误，少问了这么一句话。而我也少说了这么一句话。他默认这个网站就是给我一个人做的，所以里头只有一个用户，其他老师都不能用。

我跟他说，我觉得这个事情很显然：我是用课程组的钱出来请你做这个网站的，那肯定是给整个课程组用的。他呢，他当时是我的 TA（助教），所以他的目标是给 TA 提供一个非常方便的打分、收集、最后统计的东西，他就给他自己做了一个。所以他认为这个目标也很显然，我认为这个目标也很显然。问题是我们俩都觉得很显然，所以谁都没说那句话。

于是就做成了这么一个局面。他后面再要改成多用户的，就发现自己的设计很不好，改成多用户是一件很麻烦的事情。

> **易错点**：越是"理所当然"的目标越容易漏问。双方各自的预设都很显然，而两个"很显然"并不相等——这类分歧不会在会议上爆发，只会在交付之后爆发。

到 `formulation` 阶段收尾，还要有 `requirements gathering`：得有一种方式把需求收集、整理起来，稍微还要做一个 `analysis model`（分析模型）。最后所有的 `stakeholders`（利益相关者）和开发人员要坐到一起，达成一个 `common set of goals and objectives`——我要做的这个东西到底要干嘛、要达到什么样的总体目标、要完成哪些功能。这些是大家都同意要做的。

为什么非要有"都同意"这一步？因为在这么短的 timeline 里，你又只给这么一点钱，然后你胃口很大地说我要做什么什么什么，你觉得可能吗？所以大家最后要达成一个协议：我到底要做什么。

### 从用户回答中抽取的两类目标

通过用户对问题的回答，你要从中抽取两大类信息：

- `information goals`（信息目标）：这个网站要提供哪些内容、哪些数据，以什么形式展现；
- `obligative goals`（功能目标）：有哪些功能、有哪些任务可以通过这个网站来完成。

一类是数据，一类是功能。

> **结论**：数据与功能这两方面的信息都要抽出来，这是 `formulation` 阶段必须完成的抽取工作。

### requirements gathering 中要关注的事情

到 `requirements gathering` 这一步，有几件事情要关注。

#### 用户类别与每类用户的描述

第一件是 `user categories`（用户类别）。这件事你做别的软件的时候也要做，但没有那么重要；可是你要做一个 Web 应用，`user categories` 就显得非常重要——有哪些人要用你这个网站？

对每一个类型的用户，你都要给一个详细的描述。这个描述不只包括这个用户用你的网站要干什么事情、他的 objectives，还包括：

- 这一类型用户的 background：他的教育背景是什么样，他识字还是不识字，他是哪一种类型的人；
- 他的习惯：这一类用户通常是什么年龄段。比如我们面对的是年轻人，是 90 后，那么这一类年轻人平时喜欢的那个网络环境是什么样子的？这直接决定了你给他设计的时候，界面风格应该大概是一个什么样子的；
- 他在什么情况下、什么场合下会到达这个地方来用你这个软件；
- 这一群人特别喜欢什么、特别不喜欢什么。

给很新潮的人设计是一种设计方法，给很传统的人设计是另外一种设计方法。

比如你设计的东西是给幼儿园小朋友用的，而你用的基本上是蓝黑那种比较稳重的色调，小朋友会觉得这个很没劲。给小朋友做，我肯定要花花绿绿的，很吸引人；他觉得最好是没有多少文字，各种动画图片，他拿手过去点点戳戳就能用——这是给小朋友做的。你要把这个风格弄到一个银行的网站上去，那就是很奇怪的一件事了。

所以你要做的这个东西面向的是什么样的人群，你必须先做一个分析。

#### 需求沟通与前期调研

接着是 communicate：通过沟通，尽可能充分地拿到你想要的需求。

对传统人士，你要用传统的方法——开会、面对面地去谈，这是一种；还可以通过 `email`（电子邮件）；或者你可以做一些 `survey`（调查表），发到特定的用户群。就是想办法用各种办法去做这件事。

有一种情况特别需要前期调研：你要做的是一个以前没人做过的东西，你有一个 `great idea`，一个特别好的想法。我要是做了这么一个网站——问题是你确定有人会感兴趣、会用吗？

那前期工作里很重要的一项，就是设计一个调查问卷，然后到你认为合适的人群里去发。比如你面对的是学生，你就到各个校园里去：同学，打扰你两分钟，帮我填一下这个东西。然后你要采集充分多的数据，你才可以看得到，在人家心目中，如果是这种类型的 service（服务），它应该是什么样子。

沟通里还有一个关键的东西：`scenario building`（场景构建），也就是用户脚本。你要慢慢在脑子里成形——这一群人要你这个东西的时候，他是怎么一个用法；对他来说，怎么用是最有吸引力、最好用的。

#### 从 content object 到 use cases

分析这一步，你要从各种各样的信息里面抽取出来：

- `content object`（内容对象）：你的数据、输入输出，以及你要展示的什么东西；
- `operations`（操作）：有哪些操作是需要做的，你要完成哪些功能。

最后你得到一套一套的 `use cases`（用例）。

> **结论**：做网站基本上都是以 `use cases` 为核心的。你先把 use case 一个一个搞清楚——人家要怎么做你的网站、怎么用你的网站；后面从建模、设计到测试，`use case` 都是非常重要的一个依据。

到这里，`formulation` 大概就了解完了。

### plan：三类项目的对照

然后你还是要做一个 `plan`。这个 `plan` 非常不正式、非常短、比较草，但它还是要做的。

书里给了一个表，把 `traditional projects`（传统项目）、小型的 `e-projects`（小型 Web 应用）和 `major e-projects`（大型复杂 Web 应用）这三种项目的特点列在一起对照。表里列出来的就是 planning 阶段你要计划的那几件事情：`requirements gathering`、`technical specifications`（技术规格说明）、到底有多长时间做、`testing` 与 `QA`（质量保证）、`risk management`（风险管理），等等。

看这个表，你不需要仔细去看里面的内容，你只要看一下颜色——红色标记的，就是跟传统软件工程不太一样的地方。

| 项目类型 | 流程与规范 | 反馈与风险 |
| --- | --- | --- |
| `traditional project` | 面向比较封闭的环境、公司内部比较固定的人群，流程严格、按部就班 | 可以直接去获得用户反馈 |
| `major e-project` | 基本流程跟传统软件工程差不多，要求一样严格，也要按部就班 | 唯一的区别在 `customer feedback`：用户是全世界所有可以上网的人，没办法在特定范围内获得反馈 |
| `small e-project` | 什么都要求快，时间周期非常非常短；`requirements gathering` 不需要严格过程，但总要有一个 `descriptive overview` | `testing`、`QA`、`risk management` 的重点都在 `risk control` 上 |

读表说明：三行从上到下依次是传统项目、大型 Web 应用与小型 Web 应用；大型 Web 应用跟传统项目只在"反馈与风险"这一列上分岔，小型 Web 应用则是整行都跟传统不一样。

#### 大型 Web 应用与传统项目的唯一差别

虽然这是一个基于 Web 的 project，如果它的规模比较大、功能比较多，是一个非常复杂的大系统，那么它基本的流程跟传统的软件工程是差不多的，要求一样严格，要按部就班。唯一的区别在最后使用的那个 `customer feedback` 这个方向上。

传统的软件项目，我们说过，是在比较封闭的环境下面、面向比较固定的一个公司内部人群，所以你可以直接就去获得用户反馈。

但如果你做的是一个 Web 应用，你的用户是全世界所有可以上网的人。你没办法在特定的一个范围内去获得用户反馈。所以一定程度上，你反馈收集的过程要尽可能地设计成一种自动获取反馈的机制；或者你要有一种收集 feedback 的形式，比如发调查问卷，到处丢：你知道我这个网站吗？你用过它吗？它什么地方好用、什么地方不好用？

> **结论**：大型 Web 应用跟传统项目在流程上不用另起一套，真正要单独设计的是"谁来告诉你它好不好用、你怎么拿到这个信息"。

#### 小型 Web 应用：快与 risk control

小型的、轻量级的 Web 应用就完全不一样了，全都是红色的。它基本的特点就是快——时间短，所以什么都要求快。

比如 `requirements gathering`，如果是传统的软件工程，我们讲过，它有一个很严格的过程：一步一步做过来，仔细地设计要问什么问题，要得到什么东西，要开好几次会，最后写一个需求规格说明书出来。这在做小型 Web 应用的时候全都不需要。但是你还是大概需要一个 `descriptive overview`，三言两语要说一下——只是不需要说得那么严格、那么仔细。

它的时间周期要求非常非常短。然后它整个 `testing`、`QA` 和 `risk management` 这个过程，重点强调的是 `risk control`。

它希望这个团队的人对要用的技术是非常熟练的，然后随时要关注的是：到底做不做得完？

你一共只有 7 天时间。你不可能说我用两天时间做了一下准备工作，剩下 5 天大家加油干，然后我就不管了；5 天以后再来看，告诉你没做完。你如果中间什么都不管，5 天以后多半告诉你的是：我没做完。你要想保证 5 天把东西做完，其实你每天都要 track，每天都要盯牢——这就是一个 risk control 的过程。

> **结论**：小型 Web 项目的 `plan`，特点就是要强调快，但你又不能够放松质量；而你又不可能做一个很好的质量监控。你要在中间做一个平衡。

### 团队构成与 stakeholder 角色

接下来是 `team`。你要组一个队来做这件事，那么什么人要放在你的 team 里面？

> **定义**：这里的 `team` 不只是指开发团队，而是开发过程中需要紧密沟通的那一群人——也就是 `stakeholder`（利益相关者）。

`web engineer`（Web 工程师）绝对是这个团队里面的重要人物，但除了他们之外，你还需要哪几种角色？这个 team 不一定都包括你自己人。

以课程网站为例：我肯定得是你们 team 里面的一员，要紧密地参与你们 team 的工作。我是个什么角色呢？我是给钱的——但你真以为我只要给钱就行了、别的都不用管了？不是，我还要提出需求，你现在已经进入开发阶段了，需求还是从我这儿来的。

我这个例子举得可能不太好，因为我这一个人身上集中了好多角色，好几件活都是我干的。换一个例子就清楚了。

#### 开发团队与 support team

比如我们计算机学院的办公网，或者说我们学校的办公网。网站做好了，然后你这个 team 就可以撤了，接着就没人管了？那个网站不是迅速就死掉了吗？

那个网站要一直活着，它需要几种人？一类开发的，一类维护的。所以你还要有一个 `support team`（支持团队）。

办公网这边，办公室的人发现它死掉了，或者什么地方数据库好像乱掉了，他也不知道是什么，反正是怎么弄都进不去了，他就要打电话找谁？你总有一个联系人始终守在电话那边，随叫随到：这个东西坏了，你就要派人过来把它搞定。

> **结论**：一个 `support team` 是一定要的。`support team` 不一定是开发的那拨人，通常是两拨人。

#### 内容提供者与 Web 发布者

再往外看，用户这边其实也得有一个 team。

先是 `content developer` 或者 `content provider`（内容开发者／内容提供者）：到底是有什么人负责给你这个网站提供内容？比如办公网，我要挂的通知都是哪里来的？什么人负责把这个通知写好、准备好往上挂？这就是一个 provider。

同时你要把范围划死：我这个网站只接受哪些人给我提供过来的信息。我不能说这个办公网随便什么人都去打个电话说"哎你给我挂个东西在哪里"，然后他就给你挂上去了——这是不可能的。它只接受哪些来源的信息，谁有权提供这个内容。

提供内容的人，不一定是把内容挂出去的人。所以还有一个 `web publisher`（Web 发布者）：谁负责把这些信息发布出去？

学校里面有一个稍微懂点技术的人，他负责在后台操作，然后把这个东西发布到相对应的正确的位置上。

#### 业务领域专家与管理员

然后是 `business domain experts`（业务领域专家）。这个人是干嘛的？

你不要一看见 business 就想到赚钱、想到跟市场有关系，不一定是 marketing。他其实是这样的：你要给计算机学院做个网站，那计算机学院的办公室主任一定是你这个 team 里面的一员。因为他知道你整个的办公流程，知道什么部门是管什么事情的，哪一部分内容应该放在哪里，这些规矩，什么东西是可以放的、什么东西是不可以放的。他知道所有这个 domain 相关的知识。

再来一个例子。如果你开发的网站是给我们学校做一个选课网站，选课用的，还包括学生的成绩管理，包括他有没有什么退学警告之类的事情——那么什么人是这个网站相对应的 `business domain expert`？教务处处长、学籍管理处处长。这两位领导，或者说他们派的代表，肯定是你这个开发过程中的一员。你要随时去把政策搞清楚、把规矩搞清楚。

为什么非得是他们？`content provider` 只负责把某门课挂上去、把选课的学生导进去，这些人不一定知道整个流程的规矩。整个的选课流程、整个成绩控制的流程、各种通知发布的流程，你要找这些处长们，他们最清楚。所以这些人是你要请进来的。

最后你要有一个 `administrator`（管理员），或者以前我们叫 `web master`。

> **结论**：你自己的开发团队里大概就是 `web engineer` 和 `support specialist`；你自己人里不会有 `administrator`，你得在你的用户里面找一个 `administrator` 来做这个事情。

### outsourcing 与 in-house 的差别

开发管理的策略，你可以做 `outsourcing`（外包），也可以做 `in-house`（自己做）。

这两者唯一的区别在这里：

```text
in-house（自己做）
  开发团队 + 全部 stakeholder 代表
      |
      +---> 同一张圆桌，直接讨论软件的核心问题
            （对所有参与方全透明）

outsourcing（外包）
  开发方与各 stakeholder 代表
      |
      +---> liaison（联络员） --收集大家的意见--> [ vendor：软件的核心内容被封在里面 ]
      |                                                    |
      +------------------ 改动与答复 <----------------------+
```

读图说明：`in-house` 的时候，你有这么多的角色，包括 `stakeholders` 这些外部人员的代表，他们都是直接坐在一张圆桌上去讨论这个软件的核心问题的，全透明；`outsourcing` 就不一样了，你的软件的核心内容是给你的外包承包商，他把它封在里面，你要想改任何东西、做任何讨论，都要通过他给你提供的 `liaison`（联络员）这个中间机制，把大家的意见收集起来，再传到里面去。

### 一次外包失败案例中双方的责任

我前不久在微博上看到一个比较搞笑的事情。美国哪个公司里头有一个中国职员，他每次就是把老板给他的活直接外包到国内的一家企业。然后这个人每天就上上网、喝喝咖啡、玩玩游戏，到点了从那个外包企业把东西拿过来去交差。他只要把他那个工资的一部分付过去就可以了。

外包好像是这么轻松愉快的一件事情——你觉得可能吗？

这种事情是有可能发生的。但是，如果说他直接就把任务拿过来丢过墙，然后自己什么都不用管，你觉得这件事情就能做得很好——我觉得这个肯定有夸张之处。`outsourcing` 不是那么简单的事情。不是说你大概知道一下要做什么，然后把你大概知道的东西丢给那个外包的承包商，你就等着他把好东西拿出来给你。

我再举一个比较搞笑的例子。你们看我这个头发，现在长得这么长了。我本来是每年剪一次头发：夏天的时候头发长长了就把它盘上去，夏天结束了就把它剪短，到第二年它又可以再盘上去，所以每年剪一次，每次都去同一个地方。

前年我去剪头发的时候换了一个地方。进去跟那个理发师，那个小帅哥，坐下说：你给我把马尾巴剪成羊尾巴。我的意思是，马尾巴这么长嘛，你给我剪成羊尾巴，你起码得有羊尾巴那么长——你见过羊的尾巴，它起码得有这么长吧。我说你把马尾巴给我剪成羊尾巴。

他也没有什么疑问，"好嘞"，就开始动手做。我呢，把眼镜一摘——近视眼理发的痛苦——闭着眼睛闭目养神。等一会儿他说理好了，我戴上眼镜一看：你管这个叫羊尾巴？这不是兔子尾巴吧？太短了，这给我剪没了嘛。他如果说这是小羊的尾巴呢？我们没说那个羊有多大。于是就悲剧了。

搞到我一直到现在这个头发都不用剪，夏天盘上去正好——你就说当时他给我剪得有多短。

这其实就是一次 `outsourcing` 的过程。我的任务是想把头发剪短一点，我自己也可以剪，但嫌麻烦、剪不好，所以就把它外包给一个专业的理发师。在这个过程里，我犯了一些错误，理发师也犯了一些错误，导致最后一个悲剧的结果。

我把这个问题也给过班上的同学：作为我这个外包的人和那个外包的承包商，我们分别犯了什么错误？这种类型的错误本来可以怎么样去避免？

可以不限于剪头发这件事情。如果我做的是一个软件而不是剪头发，我把它外包给一个外包商，我就给了他一个非常简短的说明——就相当于说"你把马尾巴给我剪成羊尾巴"；然后对方什么也没问，说"好嘞"就开始做了；我中间呢就闭上眼睛什么也没管，等着他出来一个结果，结果是个兔子尾巴。这个过程，双方都犯了哪些错误？

> **结论**：最关键的一点——千万不要以为 `outsourcing` 然后你就没事干了。

### 外包的准备与外包商的选择

#### 外包前自己必须完成的工作

你在 outsourcing 之前，一定要自己内部先把这么多事情搞清楚。

第一，你自己还是要 `gather requirements`。你自己要知道到底要做的是个什么东西，自己先把这件事情搞清楚。

第二，你自己要大概有一个 `rough design`。虽然 rough，但它也是一个 design——大模样你得知道。

第三，你要大概有一个 `schedule`。这样你出去外包的时候，跟人家谈条件、谈价钱，才不能太离谱。

第四，你自己对所有的事情都要有一个大概的把握。因为 Web 应用又不是一个一次性交付就没事了的东西，你每一次要给一个 `increment`（增量），这个 `increment` 每一次到什么程度，你自己大概要有一个定义。

第五，责任要划清楚：我自己人要负责哪些事情，外包商那个团队要负责哪些事情。这个责任一定要划清楚，否则的话最后你就打起来了。

第六，双方要有一个联系的机制，这个联络员的机制要定义好。

你大概准备好了以后，你才开始出去找外包商。

#### 外包商的考察要点

找外包商你要注意：多找几个，别盯死一家。

然后你要关注的是这么几件事：

- 他报的价钱；
- 他报的价钱到底有多可靠。他报了一个很低的价格、很短的时间，然后你考察一下他这个团队以前的声誉——他做得了吗？他做得完吗？这些你都要先搞清楚：他的资质，他的报价；
- 你把这个事情包给他以后，你在多大的程度上还可以掌控这个 project。是一交给他你就什么都不许碰了？那也是一回事。在什么程度上我还可以对它有什么样的 management？这一点你是要了解的；
- 最后看一下你那个 `schedule` 是不是合理——前提是你自己知道一个真正合理的 `schedule` 是什么样子的。

最后你要有 management，但是外包商一般不会让你把手伸得那么长、伸到他公司里面去管那个细致的进度。但是你那个 `scope`（范围）是要管的，大致的进度你要管一下。

### in-house 开发要盯的几件事

`in-house` 其实跟传统的是差不多的。

- 你要知道 `scope` 是什么，大概的范围是什么，什么地方是最经常要改变的，它有什么限制条件；
- 你要 `incremental` 化，每一个 `increment` 你是怎么定义的；
- `risk analysis` 是最重要的一点；
- 有一个宏观上面的 `estimation`：大概你这个软件是什么规模的，大概需要多少人力、物力。这些东西毛估估的就可以了；
- 你要定义一个 `task set`，就是把它分解成若干个任务，然后你要控制这个任务的进度。

控制任务的进度，你通常来说怎么知道他完成了百分之多少？最常见的一个做法是 `count use cases`：你不是做了好多套 `use cases`？那你要了解做到哪儿了，就看有多少个 `use cases` 已经走完了。

当然这也不一定，取决于你那个开发的策略是什么样的——你不一定是按照 `use cases` 的线索来开发的。

最后还有一个 `change management`（变更管理），这个后面还会专门再讲。

> **结论**：`in-house` 要注意的东西跟我们传统的开发是差不多的，一个特点就是快一点。

### web engineering 的最佳实践与最差实践

最后我来说 Web 工程的 `best practices`：最好的实践是什么样的，同时告诉你最差的实践是什么样的——这些错误你不要犯。

#### best practices 中被点名的三种做法

第一种："`we have a great idea`，所以我们就开始干吧。"你有一个很伟大的想法，然后你就开始干。你得先想好钱在哪。你有没有想好，你这东西做出来以后有人用没人用？你能不能赚到钱？这些事情先想清楚，然后才开始做。

第二种："反正它总是要变的。"它的说法是，这个网站的需求总是不停在变，所以你没有必要把那个需求搞得特别清楚。问题在于：你如果太不清楚的话，你后面可能是 `unnecessary changes`——不必要的改变会更多。

第三种，这一条我觉得有待商榷，起码我自己没有特别深刻的感受。它的意思是：你这个团队的人是在传统软件开发上做得很好的一批人，他直接就可以拿过来做 Web 软件的开发，不需要经过任何新的培训——它认为这个不太可能，说这两种东西 `they are different`，他们是不一样的。但是我起码没有这个感觉。anyway，这是它的一个建议。

#### worst practices 中的两种做法

第一种：你是 manager，你是个领导，于是什么都要官僚一点，要走固定的流程。那你可能是在 IBM 那样的大公司里面是可以的；但是如果开发的是轻型的小型的这种 Web 应用，你最好就是鼓励大伙加油，然后你就靠边儿，不要捣乱——这是以快为准的。

第二种是 `testing web bother`。如果自己内部测试不好的话，拿出去就让你的用户去测试，那可能是一个很大的悲剧。

### 本讲提到的题目

**题目一：向客户提出的问题清单**

题干：我在 BBS 上发了一个帖子，说我要征人做软件工程的课程网站。除此之外，你只知道一句话——我要做一个软件工程课程的网站，信息量太少：我没说我是要招一个人，还是要招一个团队。现在请你列出一组你打算问我的问题，并排好顺序：先问什么、后问什么，先搞清楚什么、再搞清楚什么。要求是给三五分钟写出来，写完签名字交。

解析：这道题的判分点不在问题数量，而在覆盖面和顺序。

第一是覆盖面。不管你怎么问，下面三个方面必须覆盖掉，否则问题就是不全面的：用户为什么要做这件事（`identification of business need`）；他想要做成哪些事（objectives，以及由此展开的 `major features and functions`）；谁来用——做好了以后到底是谁来用。

第二个方面在课程网站这个具体场景下可以问得很实：课件放上去方便学生下载？课外的参考资料要不要？要不要专门组织一个论坛？要不要布置作业？像现在这个网站原来带的打分功能还要不要保留？

第三方面的问法要特别小心，它是三个问题里最容易漏的。要问清楚这个网站是给一个人用的，还是给整个课程组五六个老师一起用的——正文里那位学长就是漏了这句话，照着"单用户"把系统做出来，后来要改成多用户，才发现自己的设计很不好，改起来非常麻烦。

第二是顺序。顺序不一样，效果不一样：先问"为什么要做"而不是先问"你有多少钱"，一是问法上不难看，二是预算这件事可以从动机里推出来——我自己做着玩的，就不可能给你十万二十万。问完这三方面，你还要把回答里的信息抽成两类：一类是 `information goals`（网站要提供哪些内容与数据、以什么形式展现），一类是 `obligative goals`（有哪些功能、哪些任务可以通过网站完成）。这两类抽全了，`formulation` 阶段才算交付到位。

**题目二：一次外包中双方各自的错误**

题干：把"你把马尾巴给我剪成羊尾巴"这件事当成一次外包——作为我这个发包的人和那个承包的外包商，双方分别犯了哪些错误？这些类型的错误本来可以怎么样去避免？可以不限于剪头发这件事：如果做的是一个软件，我把它外包给一个外包商，只给了他一个非常简短的说明，就相当于说"你把马尾巴给我剪成羊尾巴"；对方什么也没问，说"好嘞"就开始做了；我中间闭上眼睛什么也没管，就等着他出来一个结果，结果是个兔子尾巴。这个过程里双方都犯了哪些错误？

解析：这道题分两栏答，落点都要回到"外包不等于甩手"。

发包方的错误：需求没有在自己内部先搞清楚（没有 `gather requirements`），不知道到底要做的是个什么东西；没有 `rough design`，连大模样都没有定；没有 `schedule`，所以谈条件、谈价钱时没有底；没有定义 `increment` 是什么程度，而 Web 应用本来就不是一次性交付就完事的东西；责任没有划清楚——哪些事自己人负责、哪些事外包商团队负责；没有约定双方的联络机制；找外包商时也没有多找几家、没有考察对方的资质、报价与以前的声誉；更没有想清楚包出去以后自己在多大程度上还能掌控这个 project。至于"中间闭上眼睛什么也没管"，等于连大致的进度和 scope 都不管了。

承包方的错误：接到"把马尾巴剪成羊尾巴"就动手，没有把关键量纲问清楚——"羊有多大"没人说过，最后得到一个"兔子尾巴"；过程中也没有设置阶段性的确认与中间交付检查，一直做到最后才让发包方看到结果。

避免的方式，就是正文里列的那一串准备工作：自己先 `gather requirements`、先有 `rough design` 与 `schedule`、先定义好 `increment`、先把责任和联络员机制划清楚，再出去找外包商并且多找几家；接手的一方则在动手之前把范围与量纲确认掉，在过程中留出确认点。这样即便结果有偏差，也是在中间就被发现的，不会一路做到"夏天盘上去正好"才发现剪短了。

## Web需求分析
> 对应分集：P23 | 原始标题：《第23讲 Web需求分析》

### 需求分析在 WebApp 上是怎么做减法与加法的

上一讲我们把 `WebApp`（Web 应用）分析了一圈，看它有哪些特别的特点；接下来做需求分析、做设计、做测试，都要照着这些不一样的特点来做。这一讲专门看它的 `analysis`（需求分析）这一块做成什么样子。

头一件事是把要求降下来。WebApp 的一个特点就是一般要求做得快，所以它的 `analysis model`（分析模型）不要求特别严肃、正式，也不要求特别详细、严谨——有就可以。

那这一讲的重点在哪里？在于它跟普通项目不一样的地方。

> **结论**：做需求分析的 `tasks`（任务）本身跟普通 project 没有两样，变的只是要求的程度。一上去先要有一个 `formulation`（构想、规划），大概了解一下要做点什么，这一步很快；接着要有 `requirements gathering`（需求获取），所有人坐到一起，说清楚我们到底要做成一个什么样的东西；最后要交出一个 `analysis model`。任务是一样的，不一样的是这个模型做到什么火候。

### 构想阶段的用户分类：`user hierarchy`

`formulation` 的主目标跟普通项目一样，是搞清楚 `goals and objectives`（目标与子目标）：`goals` 是大目标——我们为什么要做这件事；`objectives` 具体一点——我们要做成哪些事。

不一样的地方是，它要特别做一件事：`categories of users`（用户分类）。原因很直白——它是一个上网的东西，上网以后你不知道会有什么人来用。不知道会有什么人来用，但你心里必须有数，所以要把用你这个 WebApp 的用户大概分一分类，在 `goals and objectives` 之外再给出一张 `user hierarchy`（用户层次、用户分类）图。

书上继续用那个 `SafeHome` 家居保安系统举例：给这套家居保安系统在网上做了一个商店，你可以到网上去定制、购买。这个网上商店的用户层次是这样画的：

```text
                    SafeHomeAssure.com user
                              |
        +---------------------+---------------------+
        |                     |                     |
   +---------+        +----------------+     +------------------+
   |  guest  |        | registered user|     | customer service |
   +---------+        +--------+-------+     +------------------+
                               |
                    +----------+----------+
                    |                     |
              +----------+          +----------+
              |  新手    |          |  老用户  |
              +----------+          +----------+
```

读图：顶层是这个网站的用户，往下第一层分成三大类，`registered user` 这一类再往下细分一层，`guest` 与 `customer service` 不再分。

这三大类的划分依据是权限：

- `guest`（游客）——打酱油的，他有什么权限，这是一类人；
- `registered user`（注册用户）——正经想买东西的，这是第二类；
- `customer service`（客户服务人员）——网上商场的服务人员，这是第三类。

对于 `registered user` 还可以再往下分细一点：分成新手还是老用户，给他们提供的 `service` 也可以略有不同。

> **提示**：要不要分这一层由你的网站决定。如果我这个网站做得很简单，管他是新手还是老用户，进去看到的界面、拥有的权限都一样，那就没有必要再分；只有当你要给这两类人提供不一样的 service 时，这个细分才有意义。

到这里 `formulation` 阶段需要的两样东西就齐了：一份 `goals and objectives`，一张用户层次图。

### 用例是所有事情的基础

对 WebApp 来说最重要的事情是 `use cases`（用例）。WebApp 后面很多东西都依赖于你这一套 use cases 的设计。做法是：对于前面分出来的每一种、每一类 user，各设计一套它的 use cases。

先回答一个设问：既然先把一套 use cases 准备好，那它到底用在什么地方？写程序的时候就照着它写，是吗？肯定不是。它至少有三个去处——

- 设计的时候要用到它；
- 现在的 analysis 这部分也要用到它。你建好多个模型，写需求的时候里面有好几种模型，至少四大类，其实每一类模型都跟它有关系，都能从它里面得到很多信息；
- 测试的时候也是用它测的。黑盒测试肯定是一个 `use case` 一个 `use case` 地走。

顺着测试这条线还有一个指标问题：你怎么知道我这个模块到底完成了百分之多少？所谓完成，就是我测过了、没问题、好用。最简单的办法就是**数 use case**：一共设计了 100 个，现在走完 60 个，那就说进度是 60%。

> **易错点**：这个指标并不非常准确，因为每一个 use case 的难度不一样。注册一个新账号就非常简单；而进去以后在里面做一大堆乱七八糟的事、最后买了个什么东西再走，这一串测起来就复杂得多。但它起码是一个可以拿来说事的指标。

无论如何，`use case` 是所有事情的一个基础。

### 用例图怎么画：以 SafeHome 网上商店为例

书上给了一个设计 use cases 的例子，角色是一个 `new customer`（新手用户）——他刚注册进来，大概要做这么几件事情。要注意这里有一个顺序上的讲究：他首先要 `log in`（登录），要有一个让他点的 log in 功能；然后他可以去看他要买的东西的那种描述性内容，这种显示部分是他要看的；接着他首先要建立自己的 `configuration`，也就是他打算怎么配置他那套 SafeHome、要挑哪几个模块，挑好以后存一下；存完一会儿他又回头想看一下自己刚才存的东西，所以 `recall saved configuration`（调出已保存的配置）这个功能也是需要的。

> **提示**：`recall saved configuration` 对新手来说其实不是最要紧的那一步，因为他还没有存过东西；真正必需的顺序是先建立 `configuration`、再存、才能谈调出。

比较复杂的业务功能有两个：一个是 `customize SafeHome`——我自己定制一套个性化的 SafeHome 系统，决定我到底要哪些东西；另一个是 `purchase configuration`——配置定好以后我要来买，购买的过程也是比较复杂的一个过程。

这两个功能在图上画不下，就把每一个装进一个信封口袋里，也就是一个 `package`（包），在图上直接把这两个 package 展示出来。

```text
                    +--------------------------+
                    |    SafeHome 网上商店     |
                    |                          |
   +---------+      |    ( log in )            |
   |  new    |----->|    ( view product        |
   | customer|      |        description )     |
   +---------+      |                          |
                    |   +------------------+   |
                    |   |    package:      |   |
                    |   | customize        |   |
                    |   | SafeHome         |   |
                    |   +------------------+   |
                    |   +------------------+   |
                    |   |    package:      |   |
                    |   | purchase         |   |
                    |   | configuration    |   |
                    |   +------------------+   |
                    +--------------------------+
```

读图：左边是这个 `actor`（参与者），方框里每一个圆饼是一个 use case；圆饼上的名字就是他登录之后能做的那几件事；两个画不下的大功能各自缩成一个 `package`，讲解的时候再把口袋一个一个打开，说清里面详细是什么内容。

所以设计 use case 的办法就是：`actor` 要做的事情如果比较复杂，你可能在一张图上画不下那么多东西，那就把比较复杂的那些功能放进一个一个 `package` 里，需要的时候再展开。

> **提示**：`use case` 大概就是这么个画法。真正难的是把它考虑得非常全面、保证没有漏掉什么东西，那是一个比较复杂的过程。这一门课只告诉大家有什么、长什么样，具体怎么做要自己先去摸索。

### 用例划分的四个原则

原则上，你画的**每一个圆饼对应的都是一个模块**——要实现它的一个操作，你就可以认为这是一个模块。往前走一步：这个模块的划分要遵循哪些原则？

- `comprehensible`（可理解）。你这张图得让人看得懂，别画得太乱、太复杂，也别把名字取得很含糊，搞得大家看不懂；
- `cohesive`（内聚性要强）。一个 package 里面的东西基本上都比较集中，都为了完成同一个任务、目标比较集中；而不是一个 package 里放了好几个目标，这几个目标之间也没什么联系，反正零七八碎地就塞进一个 package 里；
- `loosely coupled`（耦合要松）。`package` 与 `package` 之间，要操作的功能模块与功能模块之间，最好不要有太紧密的关系。在一个 package 里面关系应该紧密，package 跟 package 之间不要有太多千丝万缕的关系，这样大家的分工会分得比较干净。

> **易错点**：内聚与耦合说的是两个方向上的事——包**内部**要抱成一团，包**之间**要尽量少牵连。把一堆互不相关的目标塞进同一个包，并不叫高内聚，那只是把东西堆在了一起。

这三条之后，设计包的时候还有一个原则是 `hierarchically shallow`（层次要浅）。用例本身是分层次的，前面那张图基本上就分了两层：第一层是 `actor` 直接触发的，第二层是下面细化的。use cases 最好不要有太深的层次。太深意味着什么不好的地方？

- 对用户不好。用户真的去做的时候，是一条线索一条线索走下来，表示他要完成一件事情。如果你的层次非常多，就意味着他想完成这件事情，中间要点点点点点走好几个环节，才终于把要做的事情做成，这是很烦人的；
- 对 WebApp 尤其重要。你不能让你的用户觉得很烦，何况你还受到网络带宽的影响：如果访问还很慢，我点了一个链接要等半天，而且我要点 10 个链接才能做成一件事，那大家就不要用你这个东西了，这就做得太差了；
- 对测试不好。一条线索设计得太深，到时候测起来会很痛苦、很麻烦。

层次浅这一条讲完了，紧接着就是这一讲现场留下的一个思考题：我们现在这个支付宝，为了这门课我把一个系统分成了五个组（按照某一种原则分的五个组），这个分得是不是很干净？这个界限、这个划分是不是有很大的问题？这个要自己去考虑一下。它问的其实正是下面第一条原则——`package` 与 `package` 之间要 `loosely coupled`：如果分出来的界限是干净的，那说明划分合理；如果几个组之间牵来扯去、谁也离不开谁，那就是界限出了问题。

> **提示**：这几个原则在做设计的时候还会再详细展开，现在先记住有这几条，顾名思义地体会一下。

### 分析模型的四个方面

有了 `use cases` 做基础，接下来就在它的基础上开始做 `analysis models`（分析模型）。要做的大概是这几个方面的东西：

- **内容**（content）：这个网站要展示什么东西，包括文本的、图片的、视频、音频，所有东西都要来分分类，弄清楚哪些是我要做的 `data objects`（数据对象）；
- **交互**（interaction）：用户交互的这么一种分析；
- **功能**（functional）：我要完成哪些功能，这比较传统；
- **配置**（configuration）：这是 WebApp 比较注重的、比较特殊的一项。

`configuration analysis`（配置分析）在普通的一般的传统软件里面不太讲。为什么？因为传统软件就是给你这个公司做的，你这个公司的环境是固定的，我事先知道了就可以了，不需要专门做特别详细的分类。网站不一样：你不知道你的客户端是什么样子的——你都不知道你有什么样的客户，你也不知道他用了什么操作系统、用了什么浏览器、用了什么东西，你都不知道。所以你要保证你这个东西**各种人打开都好用**。

> **易错点**：这不是一个很容易做到的事情，其实是一个很痛苦的事情。所以对 WebApp 来说，配置分析也是一个比较重要的部分，不能像做传统软件那样把它跳过。

### 内容模型与数据树

`content objects`（内容对象）要解决的问题是：什么东西作为你的 `class`、什么东西作为你系统里面的 `objects` 而存在。

来源很直接——去看 use case，从里头抽一下你觉得是什么东西；然后把它们之间的 `relationship`（关系）搞清楚。描述这些关系，除了做数据库用的 `ER diagram`（实体-关系图）之外，书上还介绍了一种叫 `data tree`（数据树）的东西。

它其实也很简单，跟一个 `structure`（结构）差不多：你定义一个 `struct`，就叫 `component`（部件），也就是你那个家具系统里面的一个模块。这个 `component` 要展示给人家看的时候，需要展示哪些东西？看这棵树：

```text
                         component
                             |
       +-------+-------+-----+-----+-------+
       |       |       |           |       |
   part no. part name part time  price  description
   数字     字符串    整型/字符串 数字    data object
   [白底:简单数据]                    [黑底:真正的对象]
```

读图：`component` 下面挂的是这个部件要展示出来的各项。白底的这几项——`part number`、`part name`、`part time`、`price`——都画在白框里面，表示它们其实不是复杂的 object，只是一个数字或者一个字符串；`part time` 不管你用整型、用字符串还是用 whatever 去定义它都行，`price` 也就是一个数字。黑底的那个 `description` 才是要花笔墨去描写、描述这个 `component` 的东西，它有好多内容，表示一个真正的 `data object`。

把 `data tree` 画出来，就希望一目了然地让人知道最后你要设计的 `data object` 都有哪些。

> **提示**：如果你的系统比较复杂、想要弄得比较全，还有一个笨而有效的办法——写一个 `parser`（词法分析器），把那个 use case 整个过一遍，把里面相应的名词抽出来；抽出来以后再把其中比较简单的东西筛掉，然后考虑那些不是简单的一个数字、一个字符串就能解决的，是不是可以设计成一个要在你系统里面处理的 `data object`。

### 交互模型的四个元素

`interaction model`（交互模型）要描述的是用户跟你这个网站之间交互的东西。它一共有 `four elements`（四个元素），需要哪些工具来描述？前面学过的 analysis model 里有好多图，但哪些图真的能用来描述交互？

先数一数这四个：

- `use cases`——必须有；
- `sequence diagrams`（顺序图）——随着时间迁移从上往下走，每一个动作涉及哪几个元素，像游泳的泳道一样一道一道地摆成几个 `actors`，往下走的时候在这些 actors 之间，是哪个角色做哪个动作、产生了什么，一路往下；
- `state diagrams`（状态图）——就是状态迁移；
- `user interface` prototype（用户界面原型）——做一个 prototype 出来，做好这个 prototype 你就知道这个 interaction 是什么样子的了，这是最直观的一个东西。

这里有一个很容易混的地方：`data flow`（数据流）算不算描述交互的图？不算。数据流是你**内部**功能与功能之间的转换、它的数据是怎么变的，那叫数据流；它说的不是用户跟你这个东西是怎么沟通的。真正跟"交互"对得上的是 `control flow`（控制流）：我这个系统有几种状态，你做了一个什么动作，它就从一个状态转到另外一个状态。对于 WebApp 来说，这个"状态转换"就直接落在页面上——你做了一个什么动作，它就从一个页面转到另外一个页面去了，也就是**页面之间的跳转**。

> **提示**：这四个元素不一定全都要画。我们给那位老先生做的那个东西，虽然不是一个很典型的 WebApp，但它的 interaction 这一部分还是比较复杂的：那些图其实都画了，`use case` 却没写，我们做了一个很有用的 `interface prototype`，问题就都解决了。

### 功能模型：用户可见的操作与背后的支撑操作

`functional`（功能）这一块比较传统，但有一处要特别注意：对 WebApp 来说，你在做**需求收集**的时候，基本上收集到的是 `user observable functionality`（用户可观察的功能）——用户看得到的功能，他说"我要这些功能"，那是他要的功能。

但你整个系统要真的做到这些事情的时候，后台还有一些动作要做；后台那些动作你也要准备好。所以这里你要准备**两个层次的 functional**：一个层次是用户可见的，一个层次是背后支持的，也就是那些 `contain within`（内含在系统内部）的 `operations`（操作），它们同样要准备好。

描述这个 functional model，一般用个 `activity diagram`（活动图）就够了。

> **提示**：说 WebApp 的时候，所有这些 model 都没有要求得那么严格，因为你要快。大概地画一个草图，差不多就行——一个小团队大家沟通一下，你能看懂、我能看懂就可以了。

### 配置模型：服务端与客户端两端

`configuration model`（配置模型）跟传统软件最不一样。配置要分两个端来讲。

**服务端（server side）**你打算怎么配置，这个要讲清楚。在需求分析这个阶段，还没到特别具体，但你大概要说清楚：

- 硬件——你对硬件的要求是不是特别高，那个服务器的性能要到什么程度；
- 你是在什么操作系统上面跑的；
- 你是不是还要用到别的什么应用，然后还有别的什么数据库，版本是什么；
- 它们之间的通信协议，是不是网络的通信协议，等等。

**客户端（client side）**的 configuration，你大概需要做哪些事情？这里有一条对所有人都适用的清单：

| 客户端环境 | 要做的判断 |
| --- | --- |
| 浏览器 | 先列一个清单：要照顾到哪些浏览器，不照顾哪些 |
| 操作系统 | Windows 是一套解决方案；用 Unix 或 Linux 打开会不会有影响 |
| 必需的运行环境 | 例如要展示的东西需要 Flash，本地没装 Flash 就显示不出来，怎么办 |
| 测试计划 | 把你要照顾到的所有环境全部都要测一遍 |

读表：前三条决定"要照顾谁"，第四条决定"怎么把这套照顾落到实处"。

先说浏览器。你肯定不能够照顾得很周全，所以你只能说我肯定会照顾到哪几类。比如说 `IE6` 我就不管了。我们现在开发那个 OJ 新版本，夸克同学就直接说：IE6 太讨厌了，我不要它了。所以如果是用 IE6 打开，你会在上面看到一行字，说检测到你用的版本居然是 IE6，建议你重新安装一个新的浏览器，下面还给你提供一个链接。好多地方都已经开始鄙视 IE6 了。

> **提示**：反过来说，你要做一个新网站，你现在用的浏览器早晚也会过时的。所以照顾哪些、不照顾哪些，这个你要做一个规划，而不是等它出了问题再说。

然后是操作系统和对本地环境的依赖：Windows 上是一种解决方案，如果他是用 Unix 或者 Linux 打开、或者用别的操作系统打开，会不会有影响？这还取决于你要展示的这个东西——比如你需要 Flash，他本地如果没装 Flash，那不就显示不出来了？那个时候你要怎么解决？

把这些问题归拢起来，客户端要回答的就是这么几件事：想要你的网站能够正常显示、正常使用，客户端需要是一个什么样的配置；如果它没有这样的配置，我怎么检测出它有没有；如果它没有，我要怎么给他解决。

另外，`browser configuration` 相关的东西考虑完，你基本上还要有一个测试计划在里面：你怎么样测，把**所有你要照顾到的这些环境全部都要测一遍**。

### 导航分析（RNA）

最后比较特殊的，是 WebApp 有一个 `navigation`（导航）的问题。

一个非常复杂的普通软件也存在导航问题，但没有这么明显，因为你不需要做得很傻瓜：一般的软件都是给某一个固定的单位做的，你可以训练他的员工——告诉他你这个角色要做的工作、你要点哪几个键，训练他熟练了就好了。**网站的话，你没办法训练任何人，所以你得做得充分傻。**

导航是什么意思？就是得随时让人家在你这个网站里面跑来跑去的时候不会跑丢：

- 他要非常容易地能够找到他想找的东西；
- 他找了一圈东西以后想起来"哎，我要前面那个"，结果退不回去了，不知道我现在在哪里；他刚才见过的、记得在哪里见过的东西，到底在哪里？然后他退回去、退回退到首页，然后死都找不着他原来要找的那个东西了——这就很恶心。

所以这方面需要一个特殊的 `navigation analysis`（导航分析），书上把它叫 `RNA`。大概有这么几部分活要做：

- 分析你所有的 `stakeholders`（利益相关者），也就是分类；
- 分析你这个大概有哪些**数据**、大概有哪些**功能**，这些东西都准备好；
- 分析它们的 `relationships`（关系）——简单来说就是网页跟网页之间是怎么跳转的；不同的种类用户的交互之间有没有互相影响的。这个 relationship 的分析是比较重要的一环；
- 决定我这个网站浏览的复杂程度，到底有没有必要做什么特别的工具来给导航做辅助。

导航设计本身后面讲用户界面设计的时候会专门讲，它有一些特别的技巧。除了那些技巧之外，还要决定需不需要一样东西：一个 `map`（地图）。

```text
   树形结构的站点地图                  给小朋友的站点地图

        [首页]                        +------------------+
          |                           |   游乐园大门      |
   +------+------+                    +--------+---------+
   |      |      |                             |
 [A]    [B]    [C]                    +--------+--------+--------+
   |      |                            |        |        |
 [A1]   [B1]                       [小火车]  [旋转木马] [糖果屋]
```

读图：同一份关系数据，树形结构是程序员比较喜欢看的；普通用户、尤其是给幼儿园小朋友看的网站，要画得像一张真地图一样，再在上面准备各种链接跳到他想去的地方。有些 BBS、有些网站做得比较好，它是有 map 的：你可以直接把整个地图调出来，所有分支一目了然地给你画出来。

那么需不需要这种 map？是在分析这个阶段、分析完各种 relationship 之后，看一下它的复杂程度，然后做一个决定：要不要做。

### 评估分析与这一阶段的交付尺度

最后还有一个 `evaluation analysis`（评估分析）。它要算的是一笔账：我想把这个网站做得友好，越友好就说明你照顾到了越多的人群；但你要照顾到越多的人群，你的工作量就会越大，你会给自己找好多事。而你时间有限、人力有限，做完了以后到底要投入多少人手去做这些事情？把自己的投入跟产出比估算一下，合算不合算——也就意味着你这个 navigation 要做到什么程度就差不多了。

> **结论**：所有这些事情在这个 analysis 阶段你最好都做，但**没有说要求你一定要写一个 100 页的文档出来**，通常没有人会这么干。但这些东西你都要考虑过。

至于用什么样的图去描述这个 relationship、你要怎么设计这个 navigation，那是到设计阶段再讲得更详细一点的事情；在这个阶段，大概分析一下我要不要做这些事情就可以了。需求分析就到这里告一段落，接下来就要进入 `design`（设计）的阶段。

所以今天回去以后，确实可以开始动手写需求报告了。有的组已经写得差不多了，我也看到写得非常漂亮的组；其他组我没看到，你们自己考虑这个压力的大小。

## Web应用软件设计
> 对应分集：P24 | 原始标题：《第24讲 Web应用软件设计》

### Web应用与普通软件在设计上的差别

上一次我提醒过，这一次会有一个组悲剧。我先不说哪个组悲剧。你们可能去学了某种画图的工具，比如说 UML，然后用得很爽，于是就在那份 60 多页的文档里面，详细地描述了一个 `use case`——把一个用例的流程写得非常详尽，然后，就没有然后了。

所以我前面一直强调的是：做事情之前，一定要先看清楚要你做的是什么事，看清楚了以后再开始做事。你不能想当然地觉得，反正我要写一份组里看得懂的需求说明，我用一个 `use case` 就可以表述了，然后就交上去不管了，搞得 TA 不知道怎么打分好。因为 `use case` 在中间只占几分——8 分还是多少——加上你前面的 `introduction`，后面的分都没有了，因为你后面都没做。

需求规格说明书，其实相当于你要订合同时的一份很重要的参考文档。合同里面很重要的一点就是验收指标：在什么情况下客户会付给你钱。客户付了钱，你要拿出什么东西来，一项一项的指标要写得非常明确、具体。如果这一项没有，那你最后开一个小公司这样做生意，就赔定了——你做好了，我可以不给你钱，我说你什么东西没做好；你说当初没告诉我，那我说需求里头你也没说。这就是需求这一步的分量。这一次算是给大家一次弥补的机会；到下一次做总体设计报告的时候，我还会再提醒一次，千万看清楚总体设计报告的要求是什么，哪几项是打分项。我为什么要把那几项设成打分项，肯定是有理由的——你先想清楚你为什么要做这个东西，再想你该怎么做这个东西。

> **结论**：学软件工程，不仅仅是学怎么画那个图，最重要的是做事情的一个套路。为什么做软件要先从需求分析开始？你做任何一件小事情也都是从需求分析开始的。让你写一份需求规格说明书，你也要先去看一下这门课对需求规格说明书的要求——这是你这个 project 的需求。搞清楚需求，然后才动手去做，否则就不知道做了些什么，写了 60 多页，只完成了其中一项。

今天正经的内容大概有两块。上一次我们介绍了普通青年的架构设计是怎么做的；而我们这本书始终把 `Web application`（Web 应用）当成一个文艺青年来特殊对待，所以今天要花一节课的时间讨论：对于 Web 应用，有什么特殊的事情要注意，它的设计模型（design model）是怎么建立的。之后我们会稍微停下来，讲一点项目管理（project management）相关的问题。

### Web应用在设计中要被特别强调的特性

先想一个更基本的问题：Web 应用为什么这么特殊？它在设计这个方面，肯定是跟它一些特殊的性质相关联的。我们前面讲过 Web 应用有好多好多特点，有十几条。那么做设计的时候，要特别强调、重视它的哪几个特点？

十几条你不需要背出来，但特别重要的，你随便一想能列一两条出来吗？Web 应用有什么特性，是你在设计的时候要特别小心的？如果我要做一个 `online judge`（在线评测）的网站，我特别要紧的是哪几件事情？

`security`（安全性）肯定很重要。我要在上面跑考试、跑竞赛，就不能很轻易地被人考试之前进去把题目直接拿出来，所以防各种攻击、防各种黑客攻击，这是我非常看重的一个因素。

考过 PAT 的同学应该记得，我在考场最后宣布考场纪律的时候，有一句话说：按照国际惯例，最后 10 分钟系统崩溃我们是不补时的。你做这样的网站，就必须考虑到好几百人疯狂提交的时候，你怎么样处理这种大规模的并发。

还有 `availability`（可用性）。基于网站的东西，大家一般的说法是你不能三天两头地挂掉——偶尔挂掉可以容忍，三天两头挂掉大家就不来做你这个了，太麻烦了。还有 `scalability`（可伸缩性）：一两个人你可以弄，一两百人你就挂掉了，那这个网站是不行的。所以你要知道访问量的变化范围，你是不是可以应付多大范围的变化。

还有一条 `time to market`（上市时间）：网站一般都要求得比较急，你只有很短的时间。这也意味着，你在设计的时候需要想得很多吗？尽量简单，把主要的功能完成。

在设计阶段就要事先考虑好怎么防范攻击、怎么扛住提交高峰、怎么把访问量变化接住，这些都属于设计目标层面的事。接下来我们就来看这个设计模型。

### Web应用的设计目标

Web 应用的设计目标有这么几点：

| 目标 | 含义 |
| --- | --- |
| `simplicity` 简洁 | 尽量简单，不要把事情搞得很复杂 |
| `consistency` 一致 | 内容、美工、整体架构、界面、导航等各项设计可能交给不同的人、不同的组去做，但从始至终要保持一致 |
| `identity` 形象认同 | 软件呈现出来的风格要符合这个领域的 `domain image`，符合这个领域给人家固有的形象 |
| `robustness` 健壮性 | 用户群不可控，容错要求高 |
| `navigability` 可导航性 | 不需要有人教，用户自己就能在你的系统里跑来跑去，还不会迷路 |
| `visual appeal` 视觉吸引力 | 网站要做得漂亮，这没什么好说的 |

`identity` 那一条我上次课也讲过：你不能弄一个五彩斑斓的银行系统网站，看上去它就不像一个银行。你把一个银行系统的网站做得像幼儿园的网站一样，人家会觉得这个银行靠谱吗？你要给什么行业的人做它的网站，你做的这个网站的形象就要符合这个行业的形象。

`simplicity` 是第一条。这里要接着 `time to market` 一起看：你时间很短，所以设计上就要尽量简单，把主要的功能完成。

### 健壮性与可导航性为什么在Web上格外重要

`robustness` 和 `navigability` 在普通青年的软件里面也是要的，但是它们的重要性没有在 Web 应用里面那么重要。Web 应用把这两个特点看得特别重。

我把这件事当作今天的第一个讨论题：`robustness` 跟 `navigability` 对于 Web 应用来说是特别重要、特别困难的，为什么？跟普通的软件相比。

先说 `robustness`：要做到这一个点，你是要花钱的。也就是说你要花人力去做这个事情，你要做到什么程度，这是一个投入的取舍。如果我们现在做的是支付宝，那是可以放到网上给所有人用的；如果我让你做的是另一套系统——银行内部的系统，就是给柜台前面那些小姑娘、小伙子，给柜员用的那套系统——两个都要 `robustness`，但对这两个东西的 `robustness` 要求显然是不一样的，你在上面花的时间也是不一样的。

> **结论**：`robustness` 跟 `navigability` 在 Web 应用上特别重要，是因为你的用户群不可控。

给银行内部职员做的系统，我可以不用那么 `robust`：等做完了以后，我给系统内部的人员做一个 `training`，这相对来说简单多了。我手把手教你怎么用，告诉你什么键一定不能点错，什么东西在哪里，因为我的用户群是可控的，就这么几个人。这套培训的东西也可以留下来，以后来了新员工，照着这个去培训他就行。所以 `robustness` 差一点不要紧，`navigability` 差一点也不要紧——你说什么东西不太找得着，我告诉他在哪儿。

但是支付宝这样的网站，你根本不知道有谁在用。你不知道坐在电脑前面的是个美女还是个抠脚大汉；你甚至不知道在前面坐的是一个人还是一条狗。所以你不知道他会按什么键，你也不知道他是什么样的搜索习惯。于是你在 `robustness` 方面的要求就特别高：你要应付各种各样的人，各种各样变态的人；同时你还得让各种各样的白痴都能在你的网站里面进出自如，找来找去能很容易找到他要找的东西。

`compatibility`（兼容性）也是同一个道理：因为用户群不可控，他用什么的都有，用什么操作系统、什么平台的都有，用 IE6 的人都有，什么样的老古董都可能有。你设计的东西要照顾到哪些层面的人，这些都是要特别注意、特别考虑的。

### Web设计的分层

Web 设计有这么多东西要设计，这是一张金字塔：

```text
                用户 (user)
        +---------------------+
        |   interface design   |  界面设计 / 美工设计
        +---------------------+
        |   content design     |  内容设计
        +---------------------+
        |   navigation design  |  导航设计
        +---------------------+
        |     technology       |  (工程师)
        +---------------------+
           工程师 (engineer)
```

读图说明：顶端是用户，底端是技术，也就是干活的工程师；越往上的层级越靠近用户，越往下的层级越靠近工程师。往下我们把它一个一个大致过一遍。

### 接口设计

#### 页面必须随时回答的三个问题

`interface design`（接口设计）对 Web 应用来说特别重要的是：你设计的整个系统所有的页面——只要它是基于一个页面一个页面的——都要能让你的用户在任何一点停下来的时候，都很清楚、很轻易地回答三个问题。

第一个问题是 `Where am I?`——我现在在哪儿？你得让别人很容易地知道他不迷路，你要给人家一种方式，随时告诉他他在整个系统里面处于什么位置。常见的解决办法你看行政办公网：你随便点一个链接进去，它上面有一行小字，叫"当前位置"。比如我点了一个学术机构，上面就写：当前位置——首页，然后一个箭头，学术机构。它不仅告诉你，你是通过点"学术机构"打开这个页面的，同时还告诉你学术机构是放在首页下面的一个链接，这个路径也告诉清楚了。这是一种方法，还有很多种解决办法。这里我觉得最有效的办法是：你要开发一个网站的时候，先去找这么多跟你相似的网站，看人家是怎么做的，学习一下人家的风格。

第二个问题是 `What can I do now?`——我在这个位置，我现在能干嘛？你要在这个页面提供给他可以点击的东西，并且很清楚地展示出来：有哪些功能可用、哪些链接是活的、哪些内容是相关的。你回想一下，这不就是废话吗？其实它要做的就是：你要把一个按钮做得像按钮，把一个链接做得像链接，把一个下拉框做得像下拉框——把每个东西做得像它应该有的那个样子。

有人不这么做吗？如果你觉得这是一句废话，我只能说你肯定是 internet 上面逛得不够多。多逛一些地方，你会发现各种很奇葩的设计：你看上去明明不是一个链接，一点，它居然是一个链接，有人是故意藏起来的；他告诉你点一个什么按钮，然后你找哪儿都找不着那个按钮，最后发现原来这坨东西是个按钮——这是他理解的按钮。我还看过更奇葩的：我看到一个文本框，那意思就是应该我往里面输账号；鼠标点上去以后没反应，光标在那儿闪啊闪，敲什么东西都没反应；仔细一看，它旁边有个很小的箭头，一按——原来是个下拉框，它根本就不是文本框。

所以这不是一件很显然的事情。你要回答这个问题，要做的就是：把它应该是什么、或者说大多数人在互联网上逛习惯了之后习惯性认为它应该是什么样子的东西，做成那个样子。

第三个问题是 `Where have I been? Where am I going?`——我已经访问过哪些地方，我还可以去哪些地方？一个最简单的机制：现在你不管用什么工具做网页，它都默认点过的链接变成紫色，没点过的链接是蓝色——这就是一种机制，告诉你你已经访问过哪些地方，还有哪些地方可以去。如果网站太复杂，你能提供一个 `map`（站点地图）那就更好。当然 map 也不是人人都喜欢的，而且 map 的设计其实也是一件很有学问的事情。

> **结论**：接口设计的总体原则是，让每一个页面在用户访问到这儿的时候，都有一些很清楚的指示，告诉他我在哪儿、我在这页面可以做哪些事情、哪些是我已经走过的地方、我还可以去哪些地方。这三个问题是最重要的问题。

#### 有效接口的特点

跟普通青年的 `interface` 相比，Web 应用的界面设计有几个很重要的特点要注意。

第一个是 `effective interface`：界面在视觉上一目了然，而且宽容（`visually apparent and forgiving`），它给用户一种掌控感。用户很快就能看到他有多少选择的余地，抓住怎么去达到他的目标、怎么把他的事情做完——所有的事情都要很清楚明白，而且你还得允许他点错，允许他犯错误。

有一条设计原则就是：你要把你的用户当成白痴。如果白痴都会用，那不白痴的用户应该用得比较舒服，感觉也会比较好。你把用户当成白痴，所以你的整个设计不能让人猜，不能让人想。这里顺便说一句，iPhone 其实不是一个 Web 应用，所以我先不在这儿批判它——它实际上违反了很多设计原则。

第二个特点：`effective interfaces do not concern the user with the inner workings of the system.` 一个最重要的、跟普通青年的系统不一样的地方是——对于普通青年的软件，你可以随时提醒他说你要存一下，弹出一个窗口问他"你要不要保存你的修改"；而在网站来说，一个更高的要求是：你根本就不要提醒他，你默默就替他存了。而且你还得让他在任何时刻可以反悔。这是一个非常高的要求。

> **结论**：用户尤其是 internet 上面的用户，你可以把他想象得要多白痴就多白痴，起码在计算机专业这个方面。他可能是完全彻底的电脑小白，但是他也要能用你这个系统，他也有权利去用你这个系统——因为你是发布在全世界公开的，所有人都可以用，所以人家有权利去用，你不要说他是故意捣乱。如果他很容易就犯了错误，那是你设计得不好。也就是说，你不想让他破坏的东西，绝对不要给他破坏的机会，那就根本不要让它出现在你的页面上。

第三个特点：`perform a maximum of work while requiring a minimum of information from users.` 让用户做的事情越少越好，用他最小的精力完成尽可能多的工作。

这一条普通的软件最好也这样做，但对于 Web 应用来说又显得特别重要。为什么？如果你给普通青年设计的是在 local 用的、在一个单位内部用的软件，人家用着用着会觉得不太爽：你为什么这个地方让我多点一下？但你就算设计的流程不太合理，让他多点了一下，那就多点一下而已，算了也就忍了，虽然时间长了还是会不爽。可是在 internet 上面，你让他多点一下，人家可能非常不爽——因为你多点这一下不仅依赖于你服务器的反应速度，还依赖于网络的速度。赶上哪天网络抽风，本来他点开一个链接就很慢，然后你还要他多做一步他完全不需要做的东西，人家就会觉得不能容忍。

所以整个设计的原则是：用户完成他的一个目标，要做的动作一定尽可能少。这一点对于 Web 应用特别重要。

更多的 `design principles and guidelines` 书上有，这里不过细地过了，自己下去好好看一下。`control mechanisms` 里面，最简单的当然是 `navigation menus`，就是有一个菜单；除了菜单以外，还有更 fancy 的东西，`graphic icons`、`graphic images` 都可以作为跳转控制的界面。

#### 接口设计的流程

做接口设计，大概的流程是这样的：

1. `review analysis model`，然后做 `refinement`。你大概看一下你的需求分析。
2. 动手画一个 `rough sketch of the interface layout`——界面的粗略草图。为什么叫 rough？因为你没时间，开发的时间很短。你大概粗略地画一下那个界面整体的布局：要不要一个 `banner`？横着要不要一条功能带？竖着放左边还是放在右边？中间到底要放什么东西？
3. `Map user objectives into specific interface actions.` 即做一个一一对应：这个网站给用户提供哪几件事情他是可以完成的，每一件事情在你这个网页上对应的是哪一个链接或按钮，他通过点哪一个可以完成他那个目标。
4. 点进去之后的那一串动作也要理出来。比如这个按钮是"我要买东西"，他点进去以后，为了完成 `buy a component` 这件事，后面还要做好几件事：他要查看，要选择，要放到购物车，最后要结账，要填各种信息、银行卡的信息、邮寄地址等等。他点了一个功能键进去以后，后面要完成一系列的动作，这一系列的动作是什么，一条一条给理出来。
5. 画 `storyboards of screen images for each interface action`。`storyboard` 是什么？拍电影的导演一般都会画分镜头，大概画一下。不同的导演画分镜头的风格很不一样，有的人画得很草，有的人画得很精致。这里就是大概说一下，你的界面跟用户交互的时候，屏幕上会出现什么样的状态。
6. 再 `refine`。这个精化是根据美工的设计来的，你要再做一个细化。
7. 开始抽取 `interface objects`。如果是面向对象的开发，通常就是这样：有哪些对象是跟接口相关的，把它抽出来，然后开始做模型。
8. 要画什么图取决于你。因为时间很紧，所以不要求你画非常正式的图。但不管你画什么图，你总要用一种方式去描述用户跟你的 interface 做交互的流程是什么样的，还要有一种东西描述它的行为，也就是这个界面使用的动态模型——相当于我们以前说的 `state transition`，状态迁移图之类的东西。
9. 每一种状态，界面长什么样、是什么样的布局，要有一个描述。然后就是 `refine`、`review`，不断地把它细化。

前两步是最重要的：目标与界面动作的对应，以及一个功能键点进去之后的动作序列。

### 美工设计

美工听上去好像跟我们没什么关系——我们一想美工设计，想的应该是工业设计专业的同学帮我们干的事，或者是艺术类的学生帮我们做的事。工科的学生呢，我不得不说，在我接触的大多数工科学生里面，实在是非常的没有审美观。没有到什么程度？不是说设计一个网站的审美观的问题，是你写一篇论文的时候看看排版，不知道什么叫丑。你在里面画了一个结构图，画了一个方框，然后那文字就写到方框外面去了，一直冲破那个方框写在那儿。我看得忍无可忍，把一个学生叫到我办公室来，把那个论文放在我电脑上，我说你看看这一页，你不觉得它有什么问题吗？我们可怜的孩子瞪着屏幕看了半天，没看出来：哪里错了？我说你把那个字写到方框外头，你不觉得难受吗？他不觉得，还好啊。那我说，你画那个框子干什么呢？你要不干脆不要画那个框子也好一点，是不是？你画了一个方框，又把文字画到外面去。

这一节不是要在短短一两分钟里培养你什么样的好审美观，只是一些必须注意的事情：你要有一点最起码的品味。

`don't be afraid of white space.` 不需要把整个屏幕所有的边边角角全部都填得满满的。留点白，留白不是坏事，留白是一种品味。留多少是可以商量的，但反正不能把所有的边边角角全都填满——有密集恐惧症的人看上去很难受。

`emphasize content`，不要喧宾夺主。你要知道你这一页重点要展示的是什么。你本来要展示的是一段文字，然后你做了一个特别 fancy 的 banner，那个 banner 上面有一个 flash，哇，人家访问完你的网站之后，所有人都记住了那个 flash，然后那个网站到底干嘛的？好像没什么印象。那就叫喧宾夺主。

`Organize layout elements from top-left to bottom-right.` 绝大多数人的阅读习惯是从左上角往右下角去看东西，所以你放东西的顺序也是从左上角往右下角去分布的。当然，如果你存心就要把所有东西从右下角开始堆、往左上角放，想以这种方式吸引眼球，那是另外一说。大多数情况下，一个正常的普通青年设计的网页，它应该是从左上角往右下角看的。

`Group navigation, content and function geographically within the page.` 这句怎么讲？"在地理上"——凡是跟 navigation 相关的、跟内容相关的，还有一些功能的按钮，你在第一页放在什么位置，后面你可能还有几百个页面，在所有的页面里头，相同功能的东西最好都放在差不多的位置上。

我举一个极端点的例子。比如说我有一个内容一页显示不够，它有一个"下一页"的按钮。通常来说"下一页"的按钮都在你从上往下读、读到下面的时候发现它在那儿，然后你点"下一页"。结果进到下一页以后发现，这一页的"下一页"跑到上面去了；再点完了以后发现，再下一页它跑到左边去了。那个"下一页"的按钮在屏幕上来回地跳，你的第一反应是这个设计师好萌，他在跟我玩捉迷藏——让我满屏幕去找那个"下一页"的链接在哪里。如果你的整个设计都是这种风格，你会让人觉得好乱，访问起来觉得好累。我记不住他那个东西在哪儿——反正都是"下一页"这个功能键，你如果都放在一个固定的位置，那我自然就会到那个地方去找那个链接，我就不需要找，我就知道它会在那儿。

你如果每次把同样的一个东西放在不同的位置，这是很有可能出现的，如果你做的不小心的话。特别是如果你需要设计一个有几百个页面甚至几千个页面的网站，然后你是分工把它分给不同人去做，风格没有统一，就会造成这种后果。大家点点点，点到这一页是另外一个人做的，然后发现他整个布局又变掉了。人家在用你这个网站的过程中，风格不断在变，位置不断在变，这就用得很累。这是不专业的一个表现。

`don't extend real estate with the scrolling bar.` 你一页如果显示得太长，不是得用那个下拉框吗？你特别想炫耀一下、你觉得特别重要的东西，最好不要让它一直拉下拉框拉到后面。虽然说我们现在有一句时髦的词叫"亮点总在最后"，但不是所有人都有耐心等到最后去看你那个亮点的。所以你要注意：你特别想要表现的东西，你要想办法让它出现在最上面、最醒目的位置。哪怕它的位置适合出现在下面，你也可以在前面先有一个提示性的东西，然后有一个链接连到下面去，人家很关注的话可以直接跳到下面去看。总的来说，你最好要在一上来就给人家看到你最想让他看到的东西。

还有一条是 `consider resolution and browser window size` 等等：不同的浏览器、不同的分辨率，做美工设计的时候都要考虑到。

### 内容设计

`content design` 其实没有太多好说的。基本上我们就是用 UML，把跟内容相关的东西抽取出来，设计成一个类（class）或者一个对象（object），然后去定义好它们之间的关系。

### 内容架构与应用架构

`architecture design` 有两大类。

一类是 `content architecture`：你的一个 `content object`（内容对象）差不多相当于一个 web page，差不多相当于一个网页；然后你整个网页跟网页之间的这个整体结构有这么几大种：

```text
linear（线性）          grid（网格）

[A] -> [B] -> [C]        [A] [B] [C]
                         [D] [E] [F]

hierarchical（层次）      network（网络）

        [A]                  [A] --- [B]
       /   \                 | \    / |
     [B]   [C]               |   \/   |
     / \     \               |   /\   |
   [D] [E]   [F]            [C] --- [D]
```

读图说明：`linear` 是一条直线往下走；`grid` 是节点按网格排布，横竖都能连；`hierarchical` 层次感非常强，是一棵树；还有一种是结构关系比较复杂的，就是 `network`。

除此之外，还有整体的架构，就是 `application architecture`。整体架构这里，不像我们普通青年的软件设计讲整体架构时那样，从一个数据流图把它翻译成一个 `call and return structure` 什么的，这个不是这样子的。比较流行的一种设计网站的架构风格叫 `MVC`。

经常听人家说"我这个网站是 MVC 架构的"。`MVC` 架构是什么东西？`Model View Controller`。大概的意思是：你把整个系统一定要分层来设计——至少你要分三层，一个前台、一个后台，然后有一个中转的 `controller`。`Controller` 是在衔接前台跟后台的：它接受用户从前台输进去的需求，由前台传给它；然后它去调用后台的程序，从后台获取数据，再传到前台，再展示给用户。这是 `controller` 做的事情。所以整个系统搭架构的时候，搭成一个后台、一个前台，中间一个 `controller`，这是一种风格的结构。

### 导航设计

#### 语义层面：导航语义单元

`navigation` 也是 Web 应用比较重要的一个特点。它大概有两个层面的东西要考虑：一个是语义方面的，一个是语法方面的。

语义方面有一个工具叫 `navigation semantic units`，简称 `NSU`——不是 NUS，是 NSU。它主要描述的是什么东西呢？官方的定义是 `a set of information and related navigation structures`，主要就是这么一套东西：跟信息以及信息之间的导航关系，把它画出来。实际上，你是要对每一个 `use case`、每一个 `actor` 的行为，去对应一套 NSU。

书上给了一个例子，那个字比较小，其实你不需要看清楚那些字，大概看一下这个图的结构就知道是怎么回事了。它对应的是你的一个 `use case` 里面的描述：用户要到网上去购买 SafeHome 那个家居保安系统，到网上买几个模块，是这么一个购物的流程。

```text
        [actor]（购买者）
           |
           | select room           <- navigation link，首页上的链接
           v
     [room 页面]（某一类房间）
           |
           | recommend components   <- room 页面上的一条链接
           v
   [product component 页面]         <- 推荐模块的产品说明页
```

读图说明：actor 在这里就是购物的人；箭头表示这是一条 `navigation link`——你在主页、首页上面点了某个链接，这个链接是要完成什么事情。第一步是先选一个房间 `select room`，点完了以后就进入了 `room` 这个页面；在 room 界面上我有好多的链接，点了其中某一个，那个链接的名字是 `recommend components`——意思是说，在这个房间里，比如卧室里、客厅里，在这一类房间里我推荐你装哪几个模块；然后点了其中一条链接，就进了它推荐的一个模块，打开的网页叫 `product component`，是描述这个 product component 的网页。上面这全部都是通过链接去完成一个功能，然后跳转到某一个网页，描述的是这么一个动作的过程。

> **结论**：通过这张图你可以很清楚地看到，用户要完成一个目标（一个 objective）的时候，他要涉及到哪几类页面——不是哪几个页面。因为 room 有好多种，我不会给每一个 room 都画一个这样的图；room 是抽象出来的，它就是你的 `content object`。图里说的是涉及到哪几个 content object，以及在这些 object 之间用什么样的链接来做跳转。这就是导航设计里面一个很重要的工具。

#### 语法层面：可用的导航机制

语法方面，就是你有什么机制可以去实现这些。

最简单的、最普通的就是 `individual navigation link`：你做一个链接，不管这个链接是文字的、icon 的、按钮的还是 whatever。一般来说你会有水平的一个 `navigation bar`，它建议你在水平的 bar 上面放比较重要的几大类的功能，不要超过 7 个，大概是 4 到 7 个，把最主要的列在上面。垂直方向你还可以有一个 `navigation column`，不管你习惯放在左边还是右边，这个垂直的 column 里面可以放你基本上所有的 `major content objects`，所有重要的链接、功能都可以放在这儿。

这里有一个问题：为什么水平的就建议最好不要超过 7 个，而竖着你想放多少都可以？竖着有那个 scrolling bar 是吧，横着也可以有。关键在于鼠标的滚轮是竖着的。你要什么时候设计一个横着动的鼠标滚轮？那你可能是横向的任务比较多。你说即使鼠标滚轮是竖着的，我也可以让它竖着滚的时候是横着动的——可以是可以，但是用户就会感觉很不好：我的动作是垂直的，结果你给我产生了一个横向移动的水平移动的效果，他的动作跟他看到的东西不一致，这也是觉得很难受的。所以横向一般要在一个屏幕宽度里面解决，纵向你可以上下滚。

```text
    +------------------------------------------------+
    | [logo]  A  |  B  |  C  |  D  |  E  |  （4~7 个）  | <- 水平 navigation bar
    +----------+-------------------------------------+
    | F        |                                     |
    | G        |                                     |
    | H        |               内容区                |
    | ...      |                                     |
    | （任意多） |                                     |
    +----------+-------------------------------------+
        ^
        |
        垂直 navigation column：放几乎所有 major content objects
```

读图说明：横向的导航栏受屏幕宽度与滚轮方向限制，只放几大类最主要的功能；纵向的导航列可以借助上下滚动容纳几乎所有重要的内容对象链接。

还有一些别的机制，比如 `tabs`。什么是 tabs 知道的吧？我们在做各种配置的时候其实都可以看到，它实际上就好像很多卡片摞在一起：你在上面看到那个卡片的一个标识、一个标识。一般来说也不是很多，不超过 5 个吧，3 到 5 个页面。你看上去就好像是叠在一起，这是 tabs 的风格。

然后包括 `site map`。`site map` 也是帮助大家随时知道你在哪里的。这些就是语法方面可以实现的机制。

### 组件级设计

`component-level design` 我们其实没有太多要说的，它在后面基本上跟普通青年的 `component-level design` 是差不多的。只不过对于 web app，它大概把模块分成了四大类：

- 动态生成内容的模块；
- 提供计算功能的模块；
- 做数据库查询功能的模块；
- 跟外部的一些系统做沟通的模块。

详细设计的问题我们在后面专门再去讲。
