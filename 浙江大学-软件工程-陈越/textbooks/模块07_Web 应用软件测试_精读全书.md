## Web应用软件测试-1
> 对应分集：P25 | 原始标题：《第25讲 Web应用软件测试-1》

前面我们把普通软件的测试讲完了。今天我们回到 testing，但换一个对象：**Web 应用软件测试（testing for Web apps）**。

如果前面那一套算"普通青年"的测试，今天这一套可以算"文艺青年"的测试。它到底哪里不一样？答案不神秘——不一样的地方，取决于 Web 应用相对于普通软件那些特别的性质。测试里真正需要另眼相看的，永远只是那些性质本身。

所以这一讲我不急着给方法，我们先把对象看清楚。

### Web 应用的质量维度

我先问你们一个问题：一个 Web 应用，它的质量考察要考察哪几个方面？随便说。

你们答得其实挺全：内容重要、功能重要，结构和布局重要，性能肯定重要，可靠性、可扩展性也要。更关键的一条是——你们打网游的都知道——你放在网上的东西，用户是**看不见摸不着对面是谁**的。如果这个东西是要上网做支付的，你不怕丢钱吗？所以 `security` 是必须的。还有一条容易被忽略：你放到网上去的东西，你**不知道谁来用**，所以你一定要非常注意界面。那个 N 开头的词叫什么？对，`Navigation`，导航。

把这些整理一下，就是 Web 应用的质量维度。

| 维度 | 考察什么 | 在 Web 应用里为什么特殊 |
| --- | --- | --- |
| 内容（content） | 信息是否准确、组织是否合理 | 内容本身就是产品的一部分，且更新频繁 |
| 功能（function） | 功能齐全、稳定 | 与传统软件一致，但依赖网络与远端服务 |
| 结构（structure） | 整体组织架构、可扩展性 | 站点会长大，架构必须撑得住 |
| 可用性（usability） | 界面能否被自主学习、自主走通 | 用户分散，没有统一培训的机会 |
| 可导航性（navigability） | 用户能否凭想象走通路径 | 页面之间靠链接导航，路径不唯一 |
| 性能（performance） | 响应效率 | 受网络与并发流量直接影响 |
| 兼容性（compatibility） | 对不同客户端环境的适配 | 客户端环境千奇百怪，不可控 |
| 互操作性（interoperability） | 与其它软件、数据库的交互 | Web 应用天然是集成体 |
| 安全性（security） | 数据与资金安全 | 开放网络，攻击面大 |

其中 `usability` 这一条，在 Web 应用里的含义和传统软件**并不一样**，度量方式也不同。传统软件里说可用性，常常讲的是"在多大程度上能用"，跟 `availability` 那种意思连在一起：一年不许宕机超过多少分钟、多少小时。

> **定义**：Web 应用的可用性强调的是 *each actor can learn and apply all required navigation syntax and semantics of the interface*——每一个参与者都能自己学会、并且用上界面所要求的全部导航语法与语义。

为什么这条对 Web 应用这么要紧？因为你的用户群是分散的，你**没有机会把他们集中起来做统一培训**。所以界面必须做到：用户自己很容易上手，并且能按照他自己的想象把路走通。走不通，就是可用性问题，不是用户笨。

`compatibility` 也是 Web 应用比较特别的地方。客户端的操作系统、用的浏览器、屏幕分辨率，什么都可能不一样，甚至千奇百怪。你的东西是不是都能跟这些环境友好相处？这就是兼容性要回答的。

再往下两条是 `interoperability`（互操作性）和 `security`。互操作性指的是你的 Web 应用跟其它的软件、其它的应用软件、跟数据库之间的可交互性——它天生不是一座孤岛。安全性则是 Web 应用非常重要的一方面，理由前面说过了：东西放在网上，你不知道谁来用。

这张表里，内容要好，功能要齐全、要稳定，结构要有充分的可扩展性，这些你们凭直觉就能列出来。真正需要盯住的是后面几条：可用性、可导航性、兼容性、互操作性——它们是 Web 应用**特有**的考核点，也是后面测试策略要专门安排步骤的地方。

> **提示**：这九条是我写在 slide 上的 `dimensions of quality`。你要仔细说的话，**每一条都有 Web 应用特别的地方**；所以后面最难的那道讨论题，你从九条里挑任何一条来答都不会错题。关键不在选题，在于你能不能把"为什么这条特别难"讲到细节上。

### Web 应用测试难在哪里

看完了这些质量维度，第二个问题就自然冒出来：如果让你去测这样的东西，你觉得跟普通软件测试相比，最大不同的、最难测的、最让你头痛的是哪几个方面？头痛到什么程度呢——头痛到要专门把 testing for Web app 拎出一章来讲。

我给你们一道讨论题，五分钟，商量一下。

题目是这样的：你现在开发的这个（简化版的）支付宝，是在线支付的；另外一个是给银行做的、专门给银行内部用的银行系统操作软件。这两种软件，你测起来有哪些不一样？哪些地方是最困难的？讨论时你举一个方面就可以，但要说得稍微详细一点：你为什么觉得这个地方特别困难、会出现什么情况——**你要站在一个测试员的角度去想这件事**。

这个题没有唯一答案，九条质量维度里每一条都有 Web 应用特别的地方，怎么写都有道理。不过真有经验的人，答案往往会集中在几个地方。

#### 配置测试：错误现象不等于错误本身

测试和维护团队最头痛的事情，是 `configuration` 这一块。

你在客户端发现一个错误，它表现出来的**现象并不一定是那个错误本身**。很大可能，它是用户那边的系统配置引起的。于是他来跟你说：我在我的机器上做了某个操作，然后就出现了某个现象。可你回到自己的机器上，**重现不了**。

> **结论**：error 几乎不可能脱离它所在的运行环境被重现——*it's almost impossible to reproduce the error outside the environment*。那台机器以外，任何一台别的机器都不行，这事就只在他那台机器上是这样。

这就是配置引起的错误为什么难办：你手里没有可复现的最小环境。于是 `configuration testing` 成了整个测试里最费劲、最难做的一块。

#### 三层结构下的定位困难

第二类困难来自架构。我们设计的时候分了层，有客户端、有服务端，中间还有网络。所以 debug 的时候非常难找：这个 bug 到底发生在哪一层？

配置本身又分两种。一种是静态的配置，静态配置就可能直接引起错误；另一种是 `dynamic`（动态的）——瞬间流量特别大的时候，也会产生一些很诡异的错误。这些东西都跟你的运行环境有关。

> **结论**：`environment` 在 Web 应用测试里扮演一个非常重要的角色。这也是为什么前面那些质量维度里，兼容性、性能、安全性会被单独拎出来。

### 设计模型到测试对象的对应

把话题收回来，我说一下 Web 应用的测试总体策略。

你们还记得我们在讲 Web 应用设计的时候，有一个设计模型的金字塔吧？不要金字塔——是**一个三角形**，上面有很多的 model，越往上越接近用户，越往下越接近底层技术。那时候我们分了几大块：`interface design`、`aesthetic design`、`content design`、`navigation design`、`architecture design`、`component design` 等等。

测试就是**对着这些 design model 走**：设计阶段产出哪些 model，测试阶段就从对应的 model 里取测试依据。

- 内容方面的问题，要用 `content model` 来查，也就是说 `content model` 肯定是要用的；
- `interface model` 也是要用的，用它来检查是不是所有的 use case 都能按这个界面模型走通；
- `design model` 主要用来检查**导航**方面的问题；
- 用户界面要做一次整体的测试；
- 功能模块 `functional components` 要做单元测试（`unit testing`）；
- 整个系统架构的导航要很仔细地测过。

这里有件事要特别提醒：**做一层测试，往往不只取一个 model。**

我让你去测 interface，你就只要一个 `interface design model`，别的都不要了？美工起码是要的——`interface design` 和 `aesthetic design` 这两件事是一起做的，测的时候**起码这两个是一个整体**。

接下来要走 navigation。测 navigation，`navigation design` 肯定要，但除了它以外，你要做真正好的 navigation testing，还必须知道**整个系统的架构**：你手里得先有一个整体的架构观念，然后才谈得上去做导航测试。所以 `navigation model` 之外，架构那一层也要拿过来。

Navigation 测完是 component testing，这个就肯定是取 `component design` 这个 model。

再往上还有一层对应关系要记牢：这一路测的是**表层**的东西；表层测完，才进入底层特性的测试——那些跟 `technology` 直接相关的部分，包括 `configuration`、`performance`、`security`。整个流程是**先表层、后底层**。

除了这些，还有几个 Web 应用基本上**特有**的测试步骤，要专门测：一是 `configuration`，二是 `compatibility`，然后当然还有 `security`、`performance`。

最后还剩一步。你的 Web 应用做完技术测试，是不是直接挂到网上就完了？一般来说不敢这样——真的一挂上去就 crash 掉，大家就再也不回来找你了。所以正式上线之前还要有一次**内部公测**：在一个人数可控的环境里，选一部分最终用户（end user），对整个系统做一次黑盒测试。

网游不就是这么干的吗？我们自己的 `ZOJ`，还有那几个 online judge 系统，正式上线之前都会叫我们集训队的这帮家伙先去虐一下，先去虐一下。选用户、控环境、整体黑盒——这三件事就是这一步的全部。

### 逐层测试的推进顺序

测试的顺序是**从上往下**测的，也就是从最接近用户的那一层，逐步走向最接近底层技术的那一层。每一层从哪个 model 里取依据，是有讲究的，我们一层一层看。

#### 内容测试：语法、语义与组织

第一件事是先测内容。`Content testing`，从 `content model` 这个地方拿过来，然后做测试计划。

内容要检查的，起码有两个方面：一个是**语法**方面的，一个是**语义**方面的。

语法方面基本就是 `typos`——拼写错误、错别字，还有语法错误、句子不通顺等等。

语义方面的问题更麻烦一点：语法拼写都没有问题，但你提供的信息是不是**准确**、是不是**正确**？举个例子，你给学院做个网站，上面有学院介绍，而你拿的是**十年前的介绍**。这段文字每个字都对，但它是错的。

除此之外还有一层：内容的**组织和结构**。哪些内容跟哪些内容放在一起出现、哪些先出现、哪些后出现——这种组织顺序、结构是不是正确，也是要测的内容。

而 `content testing` 里面最复杂、最难测的一个方面，是 `database testing`。绝大多数的 Web 应用都是以数据库为中心的架构，所以数据库的操作必须测。为什么它对 Web 应用来说格外复杂？因为**层数多**。

> **易错点**：不要以为"测数据库"就是拿 SQL 去打一遍库。用户的一次查询，在到达数据库之前和离开数据库之后，还有好几道转换要过，每一道都在你负责的范围里。

#### 数据库交互的分层

我们跟着用户的一次操作，把它从头走一遍。

用户在网页上要查个东西，页面上有个文本框，他输进去一个词，然后点了查询按钮。从他输词、点按钮，到把搜索结果返回给他，中间经过了多少环节？

先看请求这一侧：

1. 第一步，你读到的是网页的 HTML 代码，你要从这段代码里面解析出来**哪个字段是用户输进来要查询的东西**；
2. 然后你得知道这是对数据库做一个什么样的操作——是查询还是写入，还是别的什么；
3. 然后你得把它转换成相应的数据库语言，比如 SQL 语句，也就是要做一次 `translate`；
4. 然后才传给数据库。这里还有一件事我差点忘说：这个 database 可能并不在你这个 server 上，所以 server 和 server 之间还有一个 `communication` 的问题。

数据库做完相应的操作，把数据返回给你，这事就完了吗？

没有。你从数据库获取了 `raw data`，接下来还要把它返回给用户——而且不能直接把原始数据丢回去。你要先返回到 Web 应用服务器，做成一种 `proper format for display`，也就是转换成可展示的格式，再送到用户那一层的 interface，转换成用户可以理解的方式，最后显示在屏幕上。

```text
第一层  interface layer
        取得界面上提交的 HTML scripts
   |
   v
第二层  web app server layer
        从 scripts 中把 user data 抽取出来
   |
   v
第三层  format layer
        把抽取出的数据转换成规定的 format
   |
   v
第四层  SQL 转换
        转换成 SQL 语句
   |
   v
第五层  database 交互层
        对数据库执行操作，取回 raw data
   |
   v
返回路径   raw data -> Web 应用服务器 -> proper format for display
          -> 用户 interface -> 显示在屏幕上（两层之间含 server 间 communication）
```

读图说明：请求沿着箭头自上而下逐层转换，最后落到数据库；数据库返回的 `raw data` 再沿原路向上，被重新格式化后才呈现给用户。往返路径上的每一步都是独立的转换环节。

既然分了这么多层，做法就很清楚了：对 database interaction 做一个**分层**的处理，把交互拆成层，然后**对每一层去设计相应的测试方法**。这就是所谓 `layers of interaction`。按书上的建议，可以分成五层，每一层做每一层的处理：第一层从 interface 获得 HTML scripts，在 Web 应用服务器层把 scripts 里的 user data 抽取出来；第二层把它转换成规定的 format；接下来再向 SQL 语句做转换；最后与数据库做交互。取回的 `raw data` 再往上传回 user interface 这一层。

所以我们需要**为每一层各写一份 testing plan**。这是 `content testing` 里比较麻烦的部分。

#### 界面测试：机制、目标与三级策略

内容测完，下一步测 `interface`。

界面测试的重点，是先测**每一个不同的 interface mechanism**。什么是 interface mechanism？就是界面上的各种机制、各种不同种类的东西：链接、按钮、表单（form）、表格、弹出窗口（`pop-up window`）等等。每一个这样的东西，叫做一个 interface mechanism。

所以你要针对每一种不同的机制，设计与之相对应的、不同的测试。

这些机制存在的目的是为了实现导航、实现某些功能、实现某些内容的展示。因此测试的目标就是：

> **结论**：这些机制是不是**正确**地实现了它应该实现的功能，在**语义**上是不是正确。

对应的测试策略有三件事，顺序和普通软件测试是一一对应的。

第一件，先看整体的 `interface features`。这指的是你是不是符合一些设计原则——我们在讲 interface design 的时候讲过一系列界面设计原则，那它是不是违背了其中的哪几条？然后从美工的角度整体看一下：表格的 `table size` 怎么样？行间距是不是合适？边框边距留出的空白距离是不是好看？整体看上去是不是让人觉得舒服？这是**第一眼**的测试。

第二件，`unit testing`，相当于普通测试里的单元测试：把每一种 mechanism、每一种界面机制做一个局部的测试。比如你要交表格，那每一种表格你都得测一遍。

第三件，整合测试。单元测试完了之后就应该做整合测试——这是普通测试里我们反复强调的顺序。在这里，整合测试相当于把每一个 use case、或者 use case 所对应的那套 `NSU` 整体走一遍。这里实际上是 **NSU 更管用一点**。

`NSU` 是什么？我们在讲 navigation 的时候讲过它，它是做 `navigation model` 的时候提出来的东西，是对着你的 use case 来的：每一个 use case 要对应着一套 `NSU`。

> **定义**：`NSU` = `Navigation Semantic Unit`，导航语义单元。`N` 是 navigation，`S` 是 semantic，`U` 是 unit。

它长得和 use case 很像：旁边也有一个小人，有一个 actor。它描述的是——这个 actor 根据一个 use case 要完成一件事情，而在完成这件事情的过程中间，他要经历哪些页面：他点哪个链接进入什么页面，再点哪个链接进入什么页面，最后在那个页面上他做什么操作。

```text
        use case                      NSU
     +-----------+          +---------------------------------------+
     |  (actor)  |          | (actor) --页面1--链接--> 页面2         |
     |   ~~~~~   |          |            --链接--> 页面3            |
     +-----------+          |            --在页面3上做某个操作-->   |
                            +---------------------------------------+
       描述"要做什么"           描述"要一个页面一个页面地怎么走"
```

读图说明：use case 只说明 actor 要完成的一件事，NSU 把它展开成一串页面与链接构成的走法，一个 use case 对应一套 NSU。

所以整合测试就是：根据每一个 NSU 或者每一个 use case，把这一串页面上的 interface mechanism 整体地走一遍、串一遍——这相当于普通测试里的 integration test。

整合完了之后，我们还有一个 `validation testing`：把某些 use case 或者 NSU，或者把一些模型组合在一起，把整个 interface 走一遍，看它是不是正确的。这有点像最后的黑盒测试、功能验证性的测试。**这时你检查的是整个 interface 的语义**，也就是它的意义是不是被正确地实现了。

最后还有一项 Web 应用特有的：你必须对各种不同的环境做 `compatibility` 测试。各种不同的环境是什么，你们自己想一想——前面讲兼容性维度时那些答案，就是这里要覆盖的清单。

至于界面机制具体有哪些，这里只简单列一下：

- `links`，链接；
- 表格；
- 一个按钮；
- 一个表单（`form`）；
- `pop-up window`，弹出框；
- 还有其它七七八八的；
- 还有 `cookie`——对，`cookie` 也是要测的，如果你用了 cookie 的话。

把它们并排列出来，你就能看清一件事：这些东西承担的目的各不相同——有的为了实现导航，有的为了实现某些功能，有的为了实现内容的 display。目的不同，**测法就不同**，不能拿一套测链接的办法去测表单。这些东西每一条都有它自己的测试原则，我们下一次课接着讲。

## Web应用软件测试-2
> 对应分集：P26 | 原始标题：《第26讲 Web应用软件测试-2》

上一次我们把 Web 应用的测试从上到下走了一遍，最上面是 `content testing`（内容测试），往下一层是 `interface testing`（界面测试），再往下是 `component-level testing`（构件级测试）。剩下几条——`usability testing`、`navigation testing`、`configuration testing`、`security testing`、`performance testing`——还没过完，这一讲把它们接上。教科书里关于这些测试的原则和基本策略，书上写得很清楚，你可以自己看；我要花时间的是那些书上写不出结论的地方，尤其是最后一个：一个系统号称能扛住一百万在线用户，你拿什么来证明这句话。

### 可用性测试：谁来执行，测哪些方面

`usability test`（可用性测试）跟一般说的可用性定义稍微有点不同。差别在执行者：它主要测的是**你不认识的这帮人、你不可控制的这些人**，能不能自己就会用你这个 `interface`（界面）。

所以基本上，这个测试的执行过程不是由你这个团队自己人来做的。你要找一个用户群，或者从各种用户群里找几个有代表性的，让他们过来用一下。

> **定义**：`usability test` 是 `designed by you, the web engineering team`（由你和你的 Web 工程团队设计），而执行（`executed`）是由 `end users`（最终用户）来完成的。设计的责任在你，操作的责任在用户。

它的执行步骤大概是这么几步。

#### 先定义要测的可用性目标

第一步，你要定义清楚具体要测的东西。`usability` 只是一个词而已，它其实代表了很多词、很多 abilities。你不能拿着这一个词去测，得先划分一下：这次打算测哪几个目标（`identify goals of each`）。

我们列一些参考目标。

| 目标 | 含义与要操心的问题 |
| --- | --- |
| `interactivity` 可交互性 | 交互做得好还是坏，你怎么判断 |
| `layout` 布局 | 所有东西展示出来，人家是不是好理解 |
| `readability` 可读性 | 字体（`font`）、大小、颜色，别人能不能看清 |
| `美工` | 整个看上去够不够舒服 |
| `display characteristics` 展示特性 | 展示的时候它的一些特性 |
| `time sensitivity` 时间敏感性 | 有什么东西响应很慢，有什么东西对响应速度特别敏感 |
| `personalization` 个性化 | 对不同用户人群有没有特别的定制 |
| `accessibility` 可访问性 | 有没有考虑到残疾人、各种有障碍的人怎么用你这个软件 |

`readability` 这一条很容易被忽略，但很容易出问题：你那个字的颜色跟你背景的颜色几乎混为一谈，屏幕稍微不够亮，大家就看不到了。

这些目标里到底看重哪几个，取决于你开发的是个什么东西。于是你要先制定一个目标——这次打算测哪几个方面。

#### 为每个目标设计测试用例与评判方法

第二步，对每一种你要测的目标设计 `test cases`（测试用例），并且要设计一种测试方式，使得它能够被 `evaluated`（评判）。这一点其实挺难做的。

难在哪儿？拿 `interactivity` 来说：这个交互性，你怎么说它是好还是坏？你要测一个交互性好还是坏，你打算怎么个证明法？

我们那个给人做人口学研究的人文社科系统就是个例子。你们的一位师姐在里面做过一个鼠标单点的手势：因为没钱买触摸屏，就先用鼠标单点的手势来做——希望将来如果有触摸屏的话，起码我一个手指头可以把它拖来拖去，可以新建一个什么东西，打个叉叉就把它删掉，等等，就这么设计了一系列手势交互。这是她毕业论文里一个很重要的内容。

但是你在毕业论文里只写"我按照某个原则设计了一套手势，然后我实现了这个手势"——你要写程序去实现"我怎么判断是哪个手势，然后完成什么操作"——写完这个就完了吗？你毕业论文最后一章一定要写的是：你做这个手势，意思肯定是说**我这个手势要比普通的拿鼠标点点点点那些菜单要好用**，这才有意义。你肯定是觉得，我划一下新建，比我先去找文件、再点下拉框、再选新建要方便。那你怎么证明它是方便的？你用什么指标来证明你的 `interactivity` 是比较好的？

所以这个就是你要设计的一系列测试。比如这样的测试可以这么设计：

- 找几位帮忙的同学过来，先给每个人把任务讲清楚——我给你列几个任务，你要完成这几个任务，每个任务的意思是什么，先介绍清楚；
- 让他自己用鼠标点点点点，用传统的交互方式完成这些任务，你在旁边掐表，记下用了多少时间；
- 然后你再教他这套手势，让他用这些手势去完成同样的任务，再掐表，看用了多少时间。

一次还不行。一次还不行，你得有一个**学习曲线**：他多快能够上手。你教他用鼠标，让他把这个任务做多少次，然后你看他时间的变化；你教他用这个手势，让他重复多少次以后，你再看他的时间变化。

这是用客观的评判标准去评判哪个比较好用。除此之外还有调查问卷：用完了以后，让他主观地描述一下哪些方面好用、哪些方面不好用。这就是一个主观的评判。

后面每一个特性，你都要设计一个指标来证明它是好还是不好。什么叫好，什么叫不好，你必须有一个很明确的测试方法。

> **易错点**：你不能说"我就把它用了一下，觉得不是很好，要打分的话我给你打 60 分"。那你凭什么打的 60 分？你这个 60 分是哪儿来的？有人说 61 分不可以吗？这种没有指标的打分，站不住脚。

#### 选用户群并在旁边观察

然后你当然需要选择相应的用户群来给你做这个测试，找一帮同学来帮你做。他们做的时候，你还要在旁边看着：做一些帮助、做一些指导，同时看他们接受的程度怎么样。

所以 `usability` 涉及的每一种机制，你都要设计一种评审的机制，最后才能很有根据地说出 `usability` 是什么样子的。

### 构件级测试：基于功能，与数据库绑在一起

回到测试类型的主线上。`component-level testing`（构件级测试）跟普通软件没有太大的区别，我们所谓的构件级测试主要是基于功能的。基于功能点的测试呢，就是我们有黑盒测试、白盒测试，这些都是有的。

有一点要特别记住：`Web app` 一般都是以数据库为中心的，所以 `database testing`（数据库测试）通常跟功能是在一起测的。

### 导航测试：语法的六个元件与语义的正确性

`navigation testing`（导航测试）主要测两个方面：一个是导航的**语法**，一个是导航的**语义**，是不是正确。

语法要测的有这么几样东西：

- `links` 链接；
- `redirects` 重定向；
- `bookmarks` 书签；
- `frame`、`frame sets` 框架与框架集；
- `site map` 站点地图（如果有的话）；
- `internal search engines` 内部搜索引擎（如果有的话）。

这些每一个都有它要测的几个点。语义方面也有一系列要测的东西。书上给你列了一系列问题——自己去看一下书上 20.6.2 节，它有一系列 `testing questions`：你在设计 `test cases` 的时候，要确保你的 case 能够覆盖、能够正确回答这一系列问题。这里就不细讲了。

### 配置测试：服务端与客户端各自要操心什么

`configuration testing`（配置测试）是比较头痛的一件事情。通常来说，我们要测两个方面：一个是 `server-side`（服务端），一个是 `client-side`（客户端）。

#### 服务端要关注的内容

我先问一个问题：你要做服务端的 `configuration testing`，装服务器的时候你要关注哪些内容？

- **操作系统的版本**一定是要看一下的，这里版本问题很多；
- **依赖项**：装完了不是就能用了，你在依赖上有没有问题；
- 你的**系统文件**是不是能在运行的时候被正确地生成；
- `security`：你的**防火墙**有没有配错，你装的防火墙会不会影响你的响应速度，对你这个系统的使用到底会有多大的影响；
- 如果涉及**分布式系统**，那个分布式的环境要测过；
- `database` 也是**版本问题**——你跟你的数据库有没有版本问题；
- 你服务端的 `server-side scripts`（服务器端脚本）肯定也是要测一下的；
- 还有一点很容易被忽略：如果你有一个 `administrator`（管理员）这个角色，他通常权限比较多、比较高，他可以干很多事。那么他干了坏事以后会怎么样？

最后这一条值得单独说：他不见得是恶意干坏事。你**必须假设这个 administrator 是友好用户**，所以在安全防范方面对他会弱很多，他的权限会大很多。但正因为如此，他一旦误操作，会对系统产生什么样的后果，这是要考虑的。

当然，如果你还用到了代理，那么代理的 `configuration` 也要相应地做一个测试。这就是服务端你要操心的这么多问题。

#### 客户端要关注的内容

客户端这边要操心的事情，同样不少。你把它挂出去，就是默认了别人用什么环境在访问。

先说硬件方面：你要考虑不同的客户群，他用的硬件可能是不一样的——`CPU`、`memory`。对于网游来说很直观：你要能玩我这个网游，他的显卡得是什么以上的，显卡不够就是玩不了。还有容易出差错的是 `printing devices`（打印设备）：如果你需要有打印功能，是不是能够正确地设置这个打印，也是一个要操心的问题。

然后是软件环境：

- **客户端的操作系统**，各种操作系统最好你都去试一下，看能不能好用；
- **各种浏览器**（`browser`）；
- `user interface components`（用户界面构件），比如 `ActiveX` 等等这些东西；
- 如果你的 Web 应用做得比较 `fancy`（花哨），是不是还用到**插件**？你还需要什么样的插件？如果他没有，你是不是还要给他一个安装文件。

还有 `connectivity`：要测试一下网络连接的问题。

> **提示**：客户端这边的配置组合是乘法关系——几种操作系统 × 几种浏览器 × 有没有插件，很快就爆炸。这也正是配置测试"头痛"的来源，所以你要先想清楚哪几种组合是你的用户群里真正有代表性、真正需要保证的。

### 安全测试：客户端、服务端、网络三个环节的薄弱点

`security testing`（安全测试）我们基本上就关心三个环节的 `vulnerability`（脆弱点）。`vulnerability` 是什么意思？我也不知道中文确切的翻译应该是什么，就它的弱点了——它在哪些方面最薄弱，它的最薄弱环节在哪里。要测的就是这三个环节：客户端、服务器端，还有网络。

```text
        +-------------+        +-------------+        +-------------+
        | client-side | -----> |   network   | -----> | server-side |
        |  (客户端)   |        |   (网络)    |        | (服务器端)  |
        +-------------+        +-------------+        +-------------+
         浏览器缺陷              链路与传输             DoS 攻击
         邮件系统                  安全                  恶意脚本攻击
         QQ / MSN 等
         communication software
```

读图说明：三个环节就是安全测试的三个落点，客户端这一列是最容易出错的地方，服务器端那一列则是攻击最集中的地方，中间的网络环节本身也是要单独测的一段。

在客户端，最容易出错的就是它用的浏览器。为什么大家说不要用 `IE6` 了？因为它这个浏览器本身有很多缺陷，有一些是致命的缺陷。然后它的邮件系统，以及还用了些其他的 `communication software`（通信软件），比如你的 QQ、比如 MSN 这些东西，是不是有一些安全隐患？

服务器端呢，保护服务器最容易受到的攻击就是 `DoS`（拒绝服务）攻击，还有一些恶意脚本攻击。要测的是：你在多大程度上可以防御这些对服务器端的攻击。

### 性能测试：为什么它最头痛

`performance testing`（性能测试）也是 `Web app` 比较头痛的。Web 应用最头痛的其实就两件事情。

一件是你那个**配置环境**：让你查错、改错什么都很麻烦——这一条刚才在配置测试里已经领教过了。

另一件就是 `performance`：你的 `real-world loading`（真实负载），就是你真实使用起来那个流量，你是没法控制的。既然控制不了，你就要对各种流量给你的系统带来的影响做各种各样的测试。

#### 性能测试要回答的五个问题

基本上来说，性能测试要回答这么几个问题。

**第一，`Does the server response time degrade to a point where it is noticeable and unacceptable?`** 会不会出现在某种情况下，你这个服务器的响应速度就变得不能忍？通常来说是会有这种情况的。

**第二，`At what point does performance become unacceptable?`** 在什么情况下——你的用户并发到什么程度，它的数据流量到什么程度的时候——你这个服务器的表现就不能忍了？

**第三，到底哪些模块是瓶颈？** 什么东西是瓶颈，这是你要测出来的。

**第四，在不同的 `loading conditions`（负载条件）下，你要测一下大概平均响应时间是什么样子。**

**第五，也相当重要**：如果流量非常大、你的系统接近崩溃的时候，你的系统**安全性**会不会受到影响？如果你学过一点信息安全原理，应该知道这是意味着什么。

同样在这个临界点上，你某一部分功能的**可靠性**，或者说它产生的**数据的精确性、准确性**，是不是会受到影响？

这一条在我们自己的 `online judge`（在线评测系统）上体现得特别具体。你们大家如果去玩 `PAT` 或者 `ZOJ` 的话，`online judge` 很多方面就是有这个问题：当比赛——不管是比赛还是考试——PAT 的考试我通常宣布的考场规则，最后一条总是说，**如果在最后 10 分钟系统崩溃，我们就不补时，按系统崩溃那个时候它的排名为准**。

意思是，当你系统接近崩溃边缘的时候，会出现两种情况：

- 那个 `time`，就是你的运行时间，可能就测不准；
- 最难测的是那个 `memory`，你的内存使用也是测不准的，会出现各种问题。

还有就是崩溃**以后**会怎么办、会怎么样——这就是压力测试要做的事情，测一下你崩溃以后会是一个什么样的情况。

#### 负载测试与压力测试是连续的两步

`performance testing` 基本上分两大块：一个叫 `load testing`（负载测试），一个叫 `stress testing`（压力测试），这么两步。这两步其实是连续的。

```text
响应时间
  ^
  |                                          .
  |                                        .
  |                                     ..      <- 接近崩溃
  |                              ......            （time / memory 测不准）
  |                    ........
  |        ..........
  |......
  +--------------------------------------------------> 负载 P
   |<---- load testing ---->|<---- stress testing ---->|
        在正常值范围内                 越过临界点
        改变 loading conditions         把它 push 过去
```

读图说明：横轴是负载 $P$，纵轴是响应时间。左半段是在正常范围内的 `load testing`，你在这里改变负载、观察系统的反应；右半段是越过临界点的 `stress testing`，要看的是它被推过头以后整个系统会怎么样。

`load testing` 的意思是：你是在正常值的范围内，改变那个 `loading conditions`，看这个 Web 应用以及它的 `server-side environment`（服务器端环境）对不同的流量、访问量是怎么样的反应。

`stress testing` 实际上是 `load testing` 的一个继续。`load testing` 是在一个正常的范围内给它做测试，`stress testing` 就是看它的临界点在哪里，然后把它 `push` 过去，看一下你整个的系统会怎么样。

关于这两步要注意的问题，书上列出来了，这里也不细讲，大家自己回去要看。

#### 吞吐量 P = N × T × D

`load testing` 这里头有一个术语，叫做 `overall throughput`（总吞吐量），就是 $P$ 这个东西。它是由三个元素乘在一起得到的。它其实也就暗示了：你测试的时候，大概要调控的就是这三个元素。

$$P = N \times T \times D$$

- $N$ 是 `the number of concurrent users`，就是并发量：你有多少个用户并发；
- $T$ 是每个用户在单位时间里面他要做的 `transaction`（`online transaction`，在线事务），就是他要完成的事情有多少；
- $D$ 是每件事情要产生的数据量、数据流量。

把这三个东西乘在一起得到的是什么？单位时间是以秒为单位，$N$ 乘以 $T$ 乘以 $D$ 乘出来就是每秒钟冲进你这个 `server` 的**总的数据量**。

> **定义**：每秒钟有这么多个并发，然后每个并发事件他有这么多个操作，每个操作会产生这么大的数据量，你把它乘到一起，就是每秒钟产生的总的数据量，就是一个 `overall throughput`。

所以你在测试的时候要做的事情，就是不断地改变 $P$ 的值，然后看一下你系统的响应。那 $P$ 这个值里面有三个因素，你就把这三个因素的各种不同的排列组合都测一下：

- 可以是**非常大的并发量**，但是每个人的操作都很简单，就做一件事，产生的数据量比较少；
- 也可以是**中等规模的并发**，但其中它的操作很复杂。

这两种情况下 $P$ 可能差不多，但系统承受的压力完全不同——这就是为什么三个因素要分别调控，而不是只看乘出来的那个总数。

> **提示**：有一句笑话是，玉米是服务器的最好测试员。你什么时候要抢票的时候你就知道了，谁家的服务器好不好，你就拿它放到那个抢票的时候用一下。

#### 怎么证明"我能支持大规模并发"

前面这些内容合起来是为了一件事：**你说的每一个形容词，都要有根据、都要有证明**。

我关心的是 `performance`。你号称你开发好了这么一个系统，号称可以做到支持多大的并发量，那你就得拿出东西来证明。

学生毕业论文答辩的时候就很搞笑：开发了一个在线系统，号称可以支持什么什么多大的并发量，然后最后一章写他的测试——他测试就测了 10 个并发。我说，你这叫测完你的并发了？你凭什么证明你说你号称你可以什么什么？

有些同学做系统，它有很优秀的特性，但那些优秀的特性不是一个抽象的几个形容词，放在那儿上嘴皮一碰下嘴皮说出来就完了。你要证明说你可以毫无困难地支持大规模并发，那你那个大规模并发你测试出来就 10 个人，然后这叫你的大规模并发？那什么叫不大规模的并发？

> **结论**：性能测试的产出不是一个形容词，而是一组能指到具体数字的证据——在多大的并发、多大的数据流量、什么样的操作复杂度下，测出的响应时间是多少；越过哪个点以后，系统的表现开始不能忍。

### 本讲提到的题目

课上的最后一个讨论题，也就是今天的第二个讨论题。题干如下：你要开发一个 `online payment system`（在线支付系统，也就是支付宝），面对一个接近真实的情况——

- 需要支持至少 **100 万**的在线用户；
- 每天你的并发量大概是 **10 万**，10 万用户并发访问，**分分钟并发访问 10 万人次**；
- 每天你要产生 **1 TB** 级的数据。

你要考虑并发，考虑存储，然后考虑你的数据库对这 100 万用户数据的支持。

现在，这个支付宝系统的测试任务交给你：**你要用什么方法去证明这个系统可以做到这一点？**

解析要点：

- 讨论"怎么测"，不要跑题去谈界面、导航性那一类测试。看到这个题目的条件就应该知道我关心点在哪里——我关心的是 `performance`。所以答案的骨架应当落在性能测试上；
- 把上面五个问题当作答题清单：响应时间会不会变得不能忍；在多大的并发与数据流量下变得不能忍；瓶颈模块是哪些；不同负载条件下的平均响应时间是多少；系统接近崩溃时，安全性与数据的精确性是否还保得住；
- 用 $P = N \times T \times D$ 来说明你打算怎么调配负载：$N$ 取到 10 万并发的量级，$T$ 和 $D$ 按支付这个场景（每笔事务的数据量与频率）分别推向不同的组合，而不是只把并发数拉大就完事；
- 光说"我能支持 100 万在线用户"不是一个证明。证明必须给出具体的测试设计，测出来的数字要对得上你号称的那个规模——测了 10 个并发就宣称支持大规模并发，那是站不住的。

时间安排：这个问题我在后面给大家留了很长的时间，大概 15 分钟左右慢慢讨论；商量好了、做完了就交上来，下课以前交都可以。

## Web应用软件测试-3
> 对应分集：P27 | 原始标题：《第27讲 Web应用软件测试-3》

这一讲我们回到 Web 应用软件测试。前面已经讲过内容模型、导航语义单元这些设计上的东西，现在要把它们放到测试这一头来用。

先说清楚为什么要测。我们的目标是把软件的质量提上去，而质量不是一个可以拍脑袋说的东西，它要**从度量的维度上来度量**：你测的是哪一维，这一维上的合格标准是什么，测出来才算数。所以这一讲的主线是——Web 应用要从哪些维度去度量它的质量，每个维度上具体测什么、怎么测。

### 质量度量的十个测试维度

#### 内容、功能与结构测试

**内容测试**分两块：一块是**语法**，一块是**语义**。语法这一层问的是"你写对了没有"——拼写有没有错，链接有没有错。语义这一层问的是"你表达准确了没有"。这两个不是一回事，拼写全对的一段话照样可以把意思说反。

语义上最要紧的一类，是**政治上**的准确。同样一件事情的表述，哪怕只是一点细微的差别，都可能造成不允许的后果。所以内容在政治上必须没有歧义，别人一看就知道你要表达的意思，不能有第二种理解。

**功能测试**的任务是验证内容对不对、准不准，看它的不稳定程度有多大，另外还要看它是否符合业内标准。比如你用 Java 写、用 JSP 写，就要拿这些技术自己的标准去衡量，还有别的相关标准也一样。一句话，功能测试既要管"正确"，也要管"稳定"，还要管"合规"。

**结构测试**关心的是你这个应用能不能把内容准确地表达出来、能不能扩展，以及在推出新内容的时候能不能顺畅地推进去。也就是说，结构不只是摆得下今天的内容，还要摆得下以后的内容。

#### 可用性、导航、性能、兼容性、互操作性与安全性

**可用性测试**问的是：各个用户是不是都能用？你提供的语法、语义，界面上导航用的那套语言，用户能不能理解？能不能快速上手就用起来？可用性不合格的典型表现，就是用户看得见却不会用。

**导航测试**检查导航的语法和语义，其中一项重点工作是**防止死链接**这一类问题——点进去没反应、点进去是空的，都要在这一步抓出来。

**性能测试**测的是在规定条件下系统的表现：服务器端、客户端的各种配置，硬件的配置，浏览器的配置，都是"规定条件"的一部分。此外还要验证它在特殊和突发情况下的反应速度，比如访问量一下子变得很大，系统还能不能撑住。

**兼容性测试**是各个端、各种情况都要测：客户端和服务器端都要测，看它们彼此兼容不兼容。最突出的问题是**浏览器**——IE、火狐、Netscape，都要验证一遍，看看系统在这些浏览器上能不能跑起来。

**互操作性测试**针对的是 Web 应用的另一面：它除了那个访问界面，往往还要跟大型数据库打交道、去访问里面的数据。这时候界面之外还有界面——访问其他应用、访问数据库的这个界面有没有问题，就属于互操作性。

**安全性测试**找的是系统可能存在的弱点，或者叫它的**易攻性**，防范的对象是黑客。设计的时候就得先把"哪里容易被攻击"找出来，尽早处理掉。

> **结论**：安全隐患要消灭在前端，而不是等交付以后再去补。交付之后再出事，损失就大了。

把这十个维度并排放在一起，可以看出它们其实是成对的：内容、功能、结构属于"里面"的东西；可用性、导航、性能、兼容性、互操作性属于"用起来"的东西；安全则是横在中间、面向攻击者的那一维。

```text
内容测试 ── 语法（拼写/链接）      语义（准确/无歧义，尤其政治上）
功能测试 ── 内容与准确性   不稳定度   符合业内标准（Java、JSP 等）
结构测试 ── 内容能否准确表达   可扩展性   新内容能否推进
可用性   ── 各用户都能用？界面与导航语言能理解？能快速上手？
导航测试 ── 导航语法与语义，重点防死链接
性能测试 ── 规定配置（服务器/客户端/硬件/浏览器）+ 突发高访问下的反应速度
兼容性   ── 各端都要测：客户端与服务器端，IE / 火狐 / Netscape
互操作性 ── 与其他应用、与大型数据库之间的访问界面
安全性   ── 找易攻点，防黑客；隐患消灭在前端
```

读图说明：左边是每个维度的名字，右边是它在测试时真正要检查的对象。注意"性能"一栏里"规定条件"这四个字不能省——脱离配置谈性能是没有意义的。

### Web 应用测试的特殊困难

#### 客户端看到的症状不等于病根

Web 应用测试的第一个困难，是**症状出现的地方不一定是问题所在的地方**。

我上课提过这个问题，也请同学举过例子。同学讲得很到位：我作为一个用户进入某个页面，出来很慢；这时候很可能不是服务器算得慢，而是我这一端自己在算、在帮我做别的事情，问题根本不在服务器上。

> **提示**：这个例子说明的是测试里最基本的一条判断纪律——先分清"哪里痛"和"哪里病"，再去动手。症状在客户端，根因可能在服务器端，也可能在网络通信上。

身体上的例子更好懂：感冒发烧了，我们看得见的是流鼻涕，一眼看去好像是鼻子有问题。但深层原因并不是鼻子，是身体遭了各种病菌的侵扰，鼻子只是它表现出来的地方。

#### 环境与配置的作用

第二个困难是**环境**。因为运行环境复杂，我们发现的某种错误，很可能只在某种配置下、某种浏览器下才出现。

这一点跟传统的软件测试很不一样。传统软件测试的条件是完全可以控制的；而 Web 应用，即使你完全再现了原来的操作，要把当时的环境也精确复原，是非常难的。

还有一层：很多错误往往是由**配置**引起的。不同的配置会引出不同的错误信息。这跟传统软件测试里"错误就是代码错了"的直觉也不一样。

#### 错误出现在哪一层

发生错误的时候，要判断它落在哪一层。Web 应用有三个层面：

- **客户端**；
- **服务器端**；
- **网络通信端**。

错误有可能出在这三层中的任何一层，所以出了问题就要仔细甄别，究竟在哪一层。

再往细里分，还要看它跟哪一类操作环境有关：

- **静态的操作环境**，比如跟配置有关的那些；
- **动态的操作环境**，比如瞬时的资源超载。

动态环境的例子特别典型：中国好声音刚开播那会儿，很多人同时去访问某些网站，访问量一下子就上去了，这时候就超载了。在这种时候出现的错误，就属于动态操作环境带来的错误。

> **结论**：环境在 Web 应用当中有非常重要的作用，它在诊断错误的时候起很大作用。这又是它跟传统软件测试的一大不同。

### 测试策略：从内容模型到构件测试

有了这些困难打底，我们再来看测试该怎么安排。这一套策略是顺着前面设计的产物一路走下来的：

1. 对**内容模型**进行检查，看 Web 应用的内容本身，找出内容错误；
2. 对**模型**仔细审查，看是不是所有的用例都能完成；如果全部用例都能完成，基本上问题就不大了；
3. 对**体系模型**仔细审查，找出导航方面的错误——比如有没有死档、有没有点不进去的死链接；
4. 对**用户界面**进行测试，找出展示方面的错误、内容展示方面的错误，以及导航机制上的问题；
5. 对我们选拔出来的一系列**功能构件**做单元测试。前面讲过的**导航语义单元（Navigation Semantic Unit，NSU）**就是这样的构件，对子系统做操作性测试，看有没有错误——这一层跟我们平常说的单元测试类似；
6. 通过系统架构的**导航系统**也要测试一遍；
7. 让 Web 应用在**不同的环境配置**下跑一遍，测它对每种配置的兼容性；
8. **安全测试**：在每种环境下找出容易受攻击的地方和攻击点，把隐患消灭在前端；
9. **性能测试**：看它在不同负载下、在很多用户登录的情况下，性能有没有受到严重影响。

除了这些技术性的测试，还有一个我认为最好用的办法：把**最终用户**直接请进来。找志愿者过来，让他真的去用、去体验，先做这样一轮测试。技术上测得再细，也替代不了真实用户的这一次体验。

从技术层面看，这整套测试是个**金字塔**：最底下是我们具体的实现技术，最顶上是最终用户。

```text
            最终用户（直接可用的方式：志愿者试用）
              ▲
  内容设计 ──► 内容测试
  界面设计 ──► 界面测试        （界面测试与界面设计、美工设计息息相关）
  美工设计 ──┘
  导航设计 ──► 导航测试
  系统构架设计 ►              （导航测试与导航设计、系统构架设计紧密相关）
  构件设计 ──► 构件测试（含单元测试）
              ▲
        具体实现技术
```

读图说明：测试项都挂在它对应的设计产物上——内容测试对内容设计，界面测试对界面设计加美工设计，导航测试对导航设计加系统构架设计，构件测试对构件设计。上面再综合出三类测试：**配置测试、性能测试、安全测试**。

### Web 应用的内容测试与数据库测试

#### 内容测试的三个目标

内容测试的目标可以列成三条：

1. 发现**语法上的错误**。最典型的就是 `typo`，也就是打字打错、拼写拼错。围绕文档、图的表示以及其它各种表示，都要看有没有语法错误。
2. 发现**语义上的错误**。语义错通常表现为精细度不够、信息完整程度不够。语义准确了，用户在导航的时候才能精确地导航，不会出现模棱两可的说法，也不会出现引起误导、引起误解的情况。
3. 发现**结构上的错误**。结构对了，内容才能井井有条地展现给最终用户，看起来才合理。

#### 数据库测试的复杂性来自多层转换

内容测试里面还有一个重要的部分：**数据库测试**。数据库测试是非常复杂的问题，复杂在哪？我把它拆成几条来讲。

第一，客户端那边的原始需求很少会被直接展示出来。我们用的是 **SQL（Structured Query Language，结构化查询语言）**，从**数据库管理系统（Database Management System，DBMS）**开始，往往还要做相应的转化和翻译。

第二，数据库有时候是很遥远的，是**远端**的。对 Web 应用的服务器来说，这就需要由服务器之间来进行查询。

第三，绝大多数数据必须先到 Web 应用的服务器上，才能展现给客户端。到了这一步，原始数据往往还要做排版转换、格式化和格式化展现。

第四，**动态内容**还要跨对象做格式转换，转换完才适合展现。这里就牵涉到格式化和兼容性的问题。

正因为要经过这么多形式的交互，数据库这一块才这么复杂。我们可以用多层结构把它表示出来：

```text
+--------------------------------------------+
|  客户端：用户界面最终展现                  |
+--------------------------------------------+
|  服务器层：Web Apps + HTML / 脚本          |
+--------------------------------------------+
|  服务器层：数据管理与转换                  |
+--------------------------------------------+
|  SQL 访问层：通过 SQL 访问元数据           |
+--------------------------------------------+
|  数据存取层：数据的存取访问                |
+--------------------------------------------+
|  数据库：底层数据存储                      |
+--------------------------------------------+
```

读图说明：数据从底层的数据库出发，先经过存取访问，再用 SQL 访问元数据，到服务器层做数据管理与转换，最后由 Web 应用通过 HTML 和脚本送到客户端界面上展现出来。层次清楚以后，测试的思路也就清楚了——每个层面都要单独测，还要做综合测试。

> **提示**：数据库测试一般不单独进行，而是跟单元测试合在一起做。

### 界面测试

#### 界面测试的目标与界面机制

界面测试的目的，是在界面的层面上发现**显示上的错误**。测试界面往往跟特殊的界面机制相关，我们要保证界面在实现上、在语义上、在导航和功能上、在内容展现上都不出错。它还要测界面的**特征**：设计的美感、媒介上的讲究，以及相关的设计内容。

Web 应用跟传统软件不一样的地方就在这里：它主要以展示内容为主，而视觉的东西一定要有**吸引力**。

> **结论**：视觉上没有吸引力，用户很快就走掉了，不愿意再来浏览。这就是界面测试要认真做的原因。

界面的机制很多，测试时要一个个过：

- 链接；
- 表格；
- 服务端和客户端的脚本；
- 动态 HTML；
- 弹出窗口——页面弹到哪里、大小怎么样，都要看；
- `CGI` 脚本，全称是 **公共网关接口（Common Gateway Interface，CGI）**，是 Web 上应用的一个程序；
- 动态的链路，也就是流动的链路；
- `cookie`。

举个电商里最常见的例子：**购物车**。大家用得挺多，但真正测起来问题不少。购物车能装的最小数量是多少、最大是多少，要测；一件东西都没选就直接去打结账，它会不会给你算出一个金额？如果算出来了，那显然是错的；还有，超过它最大的容量会怎么样？这些都是特殊的界面机制，都要测。

#### 界面测试怎么组织

界面这一层的测试，是把前面讲过的那些单元拉过来用：

- **单元测试界面机制**。前面讲过的**导航语义单元（NSU）**就是一个完整的机制，比如一个购物流程、一个订单流程，就按这个单元去测。
- **模仿用户的操作**。让应用程序去模仿用户是怎么操作的，看每种机制是不是都对。
- **测试特殊的用户种类**。这一条有点像前面第 13 章讲的**整合测试**。
- **对整体界面做测试**。这时不能再像前面那样只挑一些用例或者只看语义单元，而要整体来测，测界面的一致性。这一条有点像**确认测试**。

界面还要在不同环境下测：不同的浏览器，以前用得最多的是 IE，现在浏览器越来越多；服务器端和数据库那边也要看兼容性。这其实就相当于前面说的**配置测试**。

### 可用性测试

可用性测试有个特殊之处：它的**设计**是我们这些 Web 应用工程师、由团队来做的，但**执行**是交给最终用户的。

做的时候有几件事必须落实：

- 定义好一系列可用性测试的**种类**；
- 每一次测试之前，都要先把这一次的**目标**确定下来；
- 让每个目标都容易测、容易评估，这样行不行、要不要改进，才有依据。

可用性要看的具体方面，我一条条数给你：

| 方面 | 要检查什么 |
| --- | --- |
| 交互性 | 用户与界面的操作交互是否顺畅 |
| 布局 | `layout` 是否合理 |
| 可读性 | 内容是否容易读 |
| 美学 | 美工与美感，能否吸引用户 |
| 展示的特点 | 内容的呈现方式 |
| 时间敏感性 | 点一下多久有反应，时间太长用户肯定不满意 |
| 个性化 | 能否按用户个性化 |
| 可访问性 | 用户总希望一年 365 天、每周 7 天、每天 24 小时都能访问 |
| 可评估性 | 每个目标是否容易测试和评估 |

这张表里最容易被忽略的是最后一行。可用性不是"看起来还行"，它要求每个目标都能被评估，评估结果才能拿去改进。

另外，可用性测试还必须支持**参与者测试**：参与测试的人是可控的，但你要先教会他们怎么跟这个 Web 应用交互、怎么走完测试过程。最好再开发一套**自动化的评估机制**，去评估 Web 应用的这个"流"，做**定量评估**。

可用性之外，还有针对**构件**的测试：构件水平的测试，注意力集中在发现功能方面的错误和漏洞上。传统的软件测试方法在这里可以用——**黑盒法**和**白盒法**都可以，设计得好的测试用例同样能拿来用。

### 导航测试

导航测试的目标分两类：一类是**语法**方面，一类是**语义**方面。

语法方面，先看导航的链接是不是断了。然后有一个东西必须会处理：`redirect`，也就是**重定向**。

> **定义**：重定向是指网页原来的地址被删掉了、不再更新了，或者已经取消掉了，这时要给它一个去处。

处理办法一般是给用户一个明确的指示：告诉他这个网页已经不存在、已经拆除，然后建议他按任意键回到主页。这是最常见的做法。

除了断链和重定向，书签、框架或者框架集这一类结构也容易出错；网站地图（导航地图）和站内搜索引擎同样在测试范围里。

语义方面怎么测，书上有一节讲得很细，就在 20 章 6.2 节，那里列了测试中一些很常用的问题。这一块我不在课上展开了，时间的关系，大家自己下来好好看一遍。

### 配置测试

配置测试要把**服务器端**和**客户端**分开看，两边要检查的东西完全不同。

服务器端要逐条落实的问题是：

- Web 应用跟服务器的**操作系统**是不是完全兼容；
- 系统的**文件、目录**以及相关的系统数据库，在运行的时候能不能被正常、适当地创建出来——这是最基本的问题；
- 系统的**安全**配置，比如**防火墙**和**加密（encrypt）**；
- 上了防火墙、做了加密，安全性当然提高了，但要同时看**性能会不会明显降低**；
- Web 应用往往跑在**分布式服务器**上，大的 Web 应用更是如此，这时配置有没有全盘考虑过；
- 有没有跟**数据库软件**很好地整合在一起，因为数据访问本身就是个问题；
- 面对不同的**数据库版本和平台**，会不会出现一些奇奇怪怪的情况——对某个版本支持得很好，换个平台就出状况；
- 服务器端的**脚本**能不能正确运行；
- 系统**管理员误操作**了，会不会影响 Web 应用的运行；
- 用了**代理服务器（Proxy Server）**和不用代理服务器，在同一个站点上的配置有没有区别。代理服务器这个东西大家不陌生，有些同学查资料就得靠它。

```text
服务器端配置测试
├─ 与服务器操作系统的兼容性
├─ 文件 / 目录 / 系统数据库能否正常创建
├─ 安全：防火墙与加密（安全性 vs 性能）
├─ 分布式服务器部署的全盘考虑
├─ 与数据库软件的整合、数据库版本与平台差异
├─ 服务器端脚本能否正确运行
├─ 管理员误操作的影响
└─ 代理服务器（Proxy Server）配置差异

客户端配置测试
├─ 硬件：CPU / 显卡 GPU / 内存 / 媒体播放器 / 打印机
├─ 操作系统：Microsoft Windows / Linux / Mac OS / Android
├─ 浏览器：IE / Mozilla / Netscape / iPad 等各种屏幕
├─ 界面构件：ActiveX / Java applet
├─ 插件：QuickTime / RealPlayer
└─ 网络接入设备：cable / DSL / 调制解调器 / T1
```

读图说明：左边一组是服务器端要逐项验证的配置，右边一组是客户端要覆盖的配置范围。两边的共同点是——**没有"测过一遍就够了"这一说，每一种组合都算一种被测配置**。

客户端这边，**硬件的配置**要熟悉：CPU、现在常说的图形显卡 GPU、内存，还有媒体播放器、打印机这些设备。

**操作系统**也有很多种：我们用得比较多的是 Microsoft Windows，开源的 Linux，苹果的 Mac OS，手机上是 Android，等等。

**浏览器**方面，IE 现在用得最多；Mozilla 也是一大类；大概十年前，Netscape 非常流行。加上移动端的 iPad 这类设备，屏幕种类越来越多。

> **易错点**：不能只在 IE 上、只在一块屏幕上试过就说过关了。IE 能行，不代表别的浏览器能行；桌面能行，不代表别的屏幕能行。

客户端界面的**构件**也要测，比如 `ActiveX`、`Java applet`。**插件**同样要测，比如 QuickTime、RealPlayer 这些播放器，还有其它插件，都要做全面的测试。

最后一个是**网络接入设备**，也就是有线电视设备、网络电视设备这一路，包括 cable、DSL、调制解调器（大家常说的"猫"）、T1 等。这里面有几个具体数字要记住：

- 调制解调器：传输速率大概 **56K**；
- T1：在美国它的标准是 **1.544 兆**，在欧洲是 **2.048 兆**；
- 更大的还有 T2、T3，T3 能承担的带宽是 T1 的 **44.28 倍**，可以达到 **42 兆**左右；
- DSL 的全称是 **数字用户线（Digital Subscriber Line，DSL）**，它下面还有 HDSL、SDSL、ADSL、VDSL 等等，这些都是电信和各种运营商提供的，属于电信网。

### 安全性测试

安全性测试也是分三个层面来看：服务器这个**管理层面**、**网络通信层面**，还有客户端那一层。做 Web 应用时，我们得先看清它可能的**攻击性**——哪些地方会被人下手。

先说客户端。客户端的攻击，通常是**预先存在于**浏览器、e-mail 等程序或者通信程序当中的那些欺诈程序。办法是把它们查找出来，看是不是真的存在这种跟踪；一旦查出来有漏洞，就得想办法弥补。

再说服务器端，它面临的攻击包括：

- **拒绝访问的攻击**，让你访问不了；
- **恶意脚本（malicious script）**，从客户端传过去，用来让我们服务器上的操作泄露出来，甚至让它任意运行。

> **提示**：这些漏洞一旦落到真实环境里，Web 应用可能出现非常大的隐患，给用户造成非常大的损失。所以做安全测试，就是自己先模拟黑客的手段去攻一攻。

课上我请同学举了几个具体情形，都举得很实在。一个是移动终端：终端可能被植入木马，木马能够监听、截获，甚至调用虚拟键盘上的信息——用户输入的账号密码就这样被截走了。所以终端上应该做**反监听**机制，测试的时候就去看看能不能截获到那个输入的账号密码，这就是终端上的一种漏洞。

另一个是**客户端与服务器之间用 `GET` 传指令、取信息**：`GET` 的内容会显示在 URL 上，上面的变量名是能看到的。有经验的黑客会去修改上面的参数，从而拿到本来受限的文件，包括其他用户的隐私，这就会危害服务器的安全。这类问题从缓冲区溢出的角度也能解释。

### 性能测试

性能测试主要看的是**负载**：用仿真的办法去模拟真实情况下的负载，特别是负载非常大的那种情况。

要观察的第一件事，是服务器端的**响应时间**在什么时候突然变得很差、反应变得很慢，以及这种情况下是不是还可以接受。这不只是技术指标问题——如果用户等了好几分钟都没有反应，他会非常焦虑，甚至愤怒。

第二件事，是找出**临界点**：在哪个点上，交易提交的速度或者输出负载的速度突然变得不可接受了。这种时候往往就是并发量上来了，大概上百、上千个请求压过来，系统反应就变得很迟钝。

第三件事，是判断**性能衰竭到底出在哪一部分**，好对症下药：

- 如果是服务器台数太少，那就增加服务器数量；
- 如果是带宽的原因，那就去申请带宽更高的服务。

第四件事，是把**不同负载下的平均响应速度**都测出来——每一种负载情况对应多少响应时间。比如我们现在做的大型网上支付系统，像阿里巴巴的支付宝、天猫，在某些情况下订单请求量是非常大的：100 个人访问，响应速度怎么样？1 万人呢？100 万人同时访问呢？

订票系统是个更贴近生活的例子。每到提前放假的时候，订票系统的订购量会一下子上去，访问量明显上升，这时候性能的下降幅度有多大、会不会变得不可接受，就必须测。

性能下降还会带来两个连带影响：一是**安全性**可能受影响，因为这种混乱的局面里容易被人混水摸鱼，产生安全隐患；二是 Web 应用的**可信度和信任度**可能受影响——负载增加得非常快的时候，用户还信不信它。

还有一个边界要测：如果服务器的容量上限是 1 万个用户，那么同时来 1 万零 1 个、1 万零 2 个，超过这个最大数会怎么样？是直接瘫痪，还是只是变慢？这一定要在交付之前弄清楚。

#### 负载测试与一个吞吐量计算公式

性能测试里包含**负载测试**：看客户端环境下的这个系统，怎么去应对不同的负载。这里有一个计算公式：

$$P = \frac{N \times T}{D}$$

其中：

- $N$ 是**并发用户的数量**；
- $T$ 是**单位用户、单位时间的提交量**，也就是每个用户多久提交一次；
- $D$ 是**每次提交的数据量**；
- $P$ 就是总算下来要扛住的量。

我用一个例子把这套算一遍。假设昨天正好是 NBA 东部决赛，比如热火、篮网这些队，大家都很关心，总访问的人数按 2 万算。看比赛的时候人很激动，还要往上提交评论：有的说热火好、三巨头好，有的说不行，这是草根球队，应该逆袭，打败那个抱团的队。假设有 2000 个人在提交评论，每个人大概每两分钟提交一次，而每次提交的平均数据量是 3K。

> **结论**：按上面这个口径算下来，负载量每秒可以达到 500K 以上。

这意味着什么？如果你的网站做的是 NBA、体育这一类内容，基本上就必须达到这个标准。达不到，用户来一次就不会再来。当然不只是篮球，还有法网、网球公开赛，李娜的淘汰赛，都是同样的道理——大型赛事一来，访问量就是这样往上冲的。

#### 压力测试

**压力测试**跟负载测试的区别在于，它是**不停地**加压：持续增加负载量，让系统跑满负荷，甚至超过它的极限，看它会发生什么——会不会瘫痪。

具体做法就是不断提高负载，达到甚至超过它那个最大负载量，然后观察状况。关于测试的一些具体问题，书上还有一节讲得很细，就是本书的 9.3 节，大家可以自己看一遍。

第一类，移动终端被植入木马，木马能够监听、截获甚至调用虚拟键盘上的信息，用户输入的账号密码就被截走了。对应的防范思路是在终端上做**反监听**机制；测试时要做的事，就是看能不能截获到那个输入的账号密码。这是终端上的一种漏洞。
