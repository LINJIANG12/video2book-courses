## 第 1 章：第19讲 测试方法-1
> 对应分集：P19 | 原始标题：《第19讲 测试方法-1》

### 一、什么是好的测试：先立审美观

讲具体战术前，先建立"什么是好测试"的审美观。出题（设计题目）最花时间、技术含量最高的地方不在想一个 idea——知识点那么多，拍脑袋就能编个故事；真正难在 **test case 的设计**。一套 case 被称为"出得好、出得强"，至少要满足三点：

1. **覆盖全面（cover 得比较全面）**：被测模块该有的性质都要被 case 触达；
2. **有代表性、无冗余**：每个 case 要有充分代表性，不能互相重复；
3. **代价最小**：用最少的时间和精力达到最好效果。软件测试是工程，要有代价意识，不能像象牙塔科研那样不计成本只求完美。

这三点就是评判一套测试用例强弱的基准：弱测试要么覆盖不全，要么用几十个冗余 case 把系统拖垮（如 PAT 每 case 开虚拟空间，case 太多系统会挂）。

### 二、两类测试技术总览

常用软件测试分两大类：

- **黑盒测试（Black-box testing）**：程序对你是一个黑盒子，看不到实现细节、看不到代码，只知道 specification（它要实现什么功能、输入输出大概什么样）。用例只能从功能 specification 出发设计；
- **白盒测试（White-box / Glass-box testing）**：盒子透明，看得见内部，清楚知道程序流程图，可针对每一条执行路径细测。

不同阶段用不同技术：单元测试多用白盒，集成与系统测试多用黑盒。

### 三、黑盒测试与等价类划分

#### 3.1 等价类划分的思想

黑盒技术里有几大类：等价类划分、边界值分析、错误推测、因果图等。其中**等价类划分（equivalence partitioning）**是最基础、最重要的思想——大量测试都基于它。

输入数据往往有极多种可能（例如 1 到 100 之间就有 100 种可能）。把所有可能输入划分为若干**等价类**：假设同一等价类里任一输入，程序对它的处理都类似——其中一个暴露错误，其他大概率也暴露；一个没暴露，其他大概率也不暴露。于是每类只挑一个代表做 test case，用最少 case 覆盖最大可能。

#### 3.2 有效等价类与无效等价类

划分时要分两种：

- **有效等价类（valid equivalence class）**：符合 specification 的、合理的输入。例如输入 1~100 的整数，则 5、10、50 属此类；
- **无效等价类（invalid equivalence class）**：不符合 specification 的、不合理的输入。例如小于 1 的数（0、负数）、大于 100 的数（101、1000）、非整数（浮点、字符、空输入）。

**千万不要只测有效等价类。** 常见毛病是只测合法输入、都过了就以为程序没问题。一个健壮（robust）的程序，不仅要在合法输入下正确工作，还要在非法输入下能合理处理——不崩溃、给出合理错误提示。因此无效等价类同样重要，在安全测试、健壮性测试中往往更重要。

#### 3.3 等价类划分准则

| 输入条件类型 | 有效等价类 | 无效等价类 |
| --- | --- | --- |
| 规定取值范围（如 1~100） | 1~100 之间的数（1 个） | 小于 1（1 个）、大于 100（1 个） |
| 规定个数（如 1~3 个参数） | 1~3 个参数（1 个） | 0 个、4 个及以上 |
| 规定值的集合（如红/黄/蓝之一） | 红、黄、蓝（各 1 个） | 不属于集合的值（绿、黑等） |
| 规定布尔量 | true（1 个）、false（1 个） | 非布尔值 |

#### 3.4 用例设计步骤

1. 给每个等价类规定唯一编号（1, 2, 3, …）；
2. 设计新 case，**尽可能多地覆盖尚未覆盖的有效等价类**，直到所有有效等价类都被覆盖（有效类希望一个 case 多覆盖几个，减少 case 数）；
3. 对**每个无效等价类**，单独设计一个 case，**一次只覆盖一个**未覆盖的无效等价类。

第三步为何"一次只测一个"？若一个 case 含多个无效输入，可能被第一个无效输入拦截，后面的错误就被掩盖，测不到后续无效处理。无效等价类必须一次一个。

#### 3.5 其他黑盒技术预告

- **边界值分析（boundary value analysis）**：大量经验表明，程序出错往往不在规矩的中间值，而在边界上——如 `>=` 写成 `>`，off-by-one error（循环多/少一次）。选 case 要特别关注：边界上取一个、刚越过边界取一个、刚进入边界取一个；
- **错误推测（error guessing）**：凭经验直觉，针对程序员易错处专门设计 case；
- **因果图**：后续详讲。

### 四、可测试性（Testability）：七个 ability

Testability 不像 reliability / availability 能套公式算百分比，它由多个 ability 组成，评价软件"好不好测"：

- **Operability（可操作性）**：软件本身可被操作，操作的方便性直接影响测试难易；
- **Observability（可观察性）**：运行时能在多大程度看到执行情况。越能看，越好测。一个反例：与医学院合作某系统，美方为版权保护做成完全黑盒子——只有一个接口、一根网线、一个按钮，点一下出结果，中间全碰不到。测试团队痛苦：出错有 N 多处可能，却不知内部结构、算法、流程，只知"按按钮出结果"，observability 极低；
- **Controllability（可控制性）**：测试人员在多大程度能控制软件。如 PAT / ACM 竞赛，裁判直接控制提交代码、写 judge 程序自动跑，可控性强；
- **Decomposability（可分解性）**：能在多大程度分块。块越小越好测；
- **Simplicity（简单性）**：被测软件越简单越好测；
- **Stability（稳定性）**：开发过程稳定。若刚测完一块需求就变、设计开发乱改又丢回来，版本未测完下一个又来，所有人抓狂（"让程序员发疯：改三次需求他就疯了"）；
- **Understandability（可理解性）**：设计文档、代码在多大程度可读可理解。Test plan 与设计并行，需求有了黑盒策略可出，设计有了部分白盒策略可出，先充分理解才能测好。

每个指标自身如何量化都是一门学问，这里只列举"有什么"，不展开"怎么做"。

### 五、为何不做穷尽测试

既然 case 设计有技术，为何不直接做穷尽测试？书上一个例子：一个程序流程图有 5 个 if-else 分支，其中还有一个循环执行 20 次。每次循环有 5 种走法，要覆盖所有可能性需：

$$5^{20}$$

约等于要花 **3000 多年**才能把这么小的程序完备测完。一个几行、看似毫不复杂的程序，穷尽测试都不可能，复杂系统更不必想。因此必须忽略部分情况、选最有代表性的情况去走——这正是测试技术的价值所在。**只要不是穷尽测试，就永远不能说"保证软件没有 bug"**（Testing cannot show the absence of errors and defects）。

### 六、白盒测试与路径覆盖

#### 6.1 白盒的基本定位

白盒（Glass-box）看得见程序内部、清楚流程图，所以只能是 **testing in the small**——针对小段代码。重点是关注每一个 path，追求尽可能好的**逻辑覆盖（logic coverage）**。设计白盒测试时，脑子里要回答四个问题：

1. **所有独立路径是否至少执行一遍？**（Can you guarantee that all independent paths within a module will be executed at least once?）
2. **所有逻辑判断的 true 与 false 分支是否都走到？**（exercise all logical decisions on their true and false branches）
3. **所有循环是否在其边界与运行范围内执行？**（all loops execute at their boundaries and within their operational bounds）
4. **内部数据结构是否有效？**（exercise internal data structures to ensure their validity）

#### 6.2 独立路径（Independent Path）

Independent path 类比线性代数里的**线性无关向量**：无关组里任一向量都不能被其余向量组合出来，总有别人 cover 不到的独特点。独立路径同理——流程图里某些路径可相互组合出第三条；一个独立路径不可能由其他路径组合出来，它至少有一条边是别人没覆盖的。最低要求：设计的 case 走一遍时，所有独立路径至少被执行一次，即图里每条边至少被走一遍（很弱的要求）。

#### 6.3 最弱覆盖：语句覆盖与流图

最弱覆盖是 **execute every statement at least once（每条语句至少执行一次）**。做法是把顺序执行语句缩成一个节点、编号，简化成平面有向图（flow graph）。注意判断节点：复合条件（如 `total < 1000 && A != 0` 含 AND）实际包含两次判断，最好拆成两个节点，把边细化——compound conditions 要拆开。

#### 6.4 环形复杂度（Cyclomatic Complexity）

做 Basis Path Testing 时要算一个量：**环形复杂度（Cyclomatic Complexity, CC）**。图论里有三个等价定义：

1. 平面图把平面切成的**连通域（region）个数**；
2. **边数 − 节点数 + 2**，即 $E - V + 2$；
3. **$P + 1$**，其中 $P$ 是谓词节点（predicate node，即出去箭头不止一个的**分支节点**）的个数。

三者可证相等。例如某图有 3 个分支点，则 $P+1 = 4$，平面也被切成 4 个连通域，CC = 4。

**CC = 4 告诉我们什么？** 它与分支节点个数成正比，代表程序里**独立路径的条数**，也给出测试 case 数的**上界（upper bound）**：最多只需设计 4 个 case，就一定能做到"execute every statement at least once"、把所有路径走一遍。可以设计得更少。

另一个例子：一段程序含复合条件，需拆成两个节点后再画图，算得 CC = 5，即最多需 5 个 case 即可让每条语句至少执行一次。

#### 6.5 覆盖强度演示：语句覆盖远远不够

以 CC = 5 的程序为例，目标"每句话至少执行一次"，实际只需 **1 个 case** 就能从头走到尾。例如设计：

```
输入：A = 3, B = 0, X = 4/3（且 X > 1）
```

程序沿一条路走完，每一语句都被执行，达到了最基本要求。但**覆盖非常弱**——若把程序里的 `AND` 错写成 `OR`，这个 case 仍"正确"，错误查不出来。原因是有分支没测到；只有去走分支（走不同 path），才可能发现写错。因此更强覆盖应是 **execution of each path**，而非 each statement。

### 七、随堂自测

**题 1：** 等价类划分中，为何无效等价类必须"一次只测一个"？有效等价类为何鼓励一个 case 多覆盖？

> **解析与答案：** 无效类一次只测一个，是因为若一个 case 含多个无效输入，会被第一个无效输入拦截，后面的无效处理被掩盖、测不到；有效类鼓励多覆盖是为了用最少 case 覆盖全部有效等价类、减少冗余与代价。依据见第三节 3.4。

**题 2：** 程序环形复杂度 CC = 4 的含义是什么？它给出测试 case 数的上界还是下界？

> **解析与答案：** CC = $P+1$（$P$ 为分支节点数），表示程序中独立路径的条数，并给出"让每条语句至少执行一次"所需测试 case 数的**上界**——最多设计 4 个 case 就一定够。依据见第六节 6.4。

**题 3：** 为什么说"语句覆盖"是最弱的逻辑覆盖？用一个能暴露其缺陷的场景说明。

> **解析与答案：** 语句覆盖只要求每条语句至少执行一次，一个 case 即可走完整段程序；但若程序中把 `AND` 误写为 `OR`，该 case 仍能通过、错误查不出，因为还有分支未走到。只有覆盖每个 path（路径覆盖）才可能发现此类逻辑错。依据见第六节 6.5。

## 第 2 章：第20讲 测试方法-2
> 对应分集：P20 | 原始标题：《第20讲 测试方法-2》

### 一、从语句覆盖到条件覆盖：复合条件的系统化展开

上一讲说到，只让每条语句执行一次的语句覆盖太弱——把 `AND` 错写成 `OR` 也查不出。更强的要求是**条件覆盖（condition testing）**：每个条件（condition）的 True 与 False 都至少测到一次（test every condition at least once）。若条件本身就是单个简单判断，事情很简单；麻烦在于条件常是复合的。

如何系统化、不遗漏地设计复合语句的 case？以一个含两个分支、且为 `AND` 关系的语句为例（设两个分支为 B1、B2）。目标是：整句结果既有 True 也有 False，且 B1 取到 T/F、B2 也取到 T/F。

**第一步（分支层，最少 3 个 case）：** 把 B1、B2 当作整体看，不写"两个都 T、两个都 F"（那样会漏掉组合细节），而是取三种组合：

| case | B1 | B2 | 整句 |
| --- | --- | --- | --- |
| 1 | T | T | T |
| 2 | F | T | F |
| 3 | T | F | F |

这样整句有 T 有 F，B1 有 T 有 F，B2 有 T 有 F，满足"每个条件至少一次"。

**第二步（细化 T/F 含义，展开到 4 个 case）：** `T` 意味着"两者相等"，`F` 意味着"不相等"——不相等要分两种情况（一个小于、一个大于）。于是把 `F` 拆成 `<` 与 `>` 两个子 case。

**第三步（翻译回具体表达式，得 5 个 case）：** 将 B1 换成具体比较 `E1 > E2`。则 B1 的 T 翻译为 `>`；B1 的 F 翻译为"一个 `<`、一个 `=`"。逐层翻译下来，整句所有 True/False 组合都被覆盖，达成"test every condition at least once"。

这类题考试常出：给一段复杂复合语句，要求用**最少 test cases** 保证每个 True/False 都被执行，并写出设计思路。诀窍就是"先按分支组合、再逐层把 T/F 翻译成具体关系值"。

### 二、数据流测试（Data Flow Testing）

数据流测试关注的不是路径本身，而是一个**变量在程序里取值的变化过程**（debug 时一步步看值怎么变，正是这个思路）。做法是对程序语句做拆解：

- **DEF of S**：语句 S 的 def 集合，指在这句话里被定义（赋初值、被给值）的所有变量；
- **USE of S**：语句 S 用到了哪些变量的值（未改变它，只是读取）；
- **du-chain（定义-使用链）**：对每个变量，顺着执行顺序找它的链——上面的定义在中间未被改变、到下面某语句被使用，用的就是上面给的定义。链刻画了"X 在哪被改、在哪被用、顺序如何"。

测试目标：**every du-chain covered once（每条 du-chain 至少覆盖一次）**，即以 du-chain 为单位逐链去测。

### 三、循环测试（Loop Testing）

循环是另一个易错点，按循环形态分策略。

#### 3.1 Simple loop（简单循环，1 到 n）

至少覆盖以下边界与邻近点：

- **0 次**（直接跳过，非法循环是否发生）、**1 次**、**2 次**；
- **n-1 次**、**n 次**（边界）、**n+1 次**（越界会怎样）；
- 再取一个**中间值**随便跑一下。

这里的 n 由输入规模决定（例如输入 size 可能是 1，也可能是 100，则 1 和 100 都要测）。

#### 3.2 Nested loops（嵌套循环）

技巧：先让**外循环不执行或只执行一次**，把内循环测完备；内循环测完当作已测过的模块、不再管它，再用普通策略测外循环。

#### 3.3 Concatenated loops（串接循环）

没什么特殊，顺着往下逐环测即可。

### 四、边界值实战：二分查找溢出教训

边界值分析在工程中极其实用。一个真实教训：三位老师组队参加校赛，何老师瞬间写了不到十行的小程序，一提交却 "Wrong Answer"。这么简单的程序能有错？看不出来的时候，就设计一个 case 让它跑——取**边界最大值**一跑，程序崩溃：答案超出了长整型（long long 溢出）。

所谓"bug 喜欢躲在墙角"，边角最易出错。教材给的边界准则：若取值范围是 A 到 B，则 case 必须包含 A、B，以及紧贴两侧的 `刚好大于 A`、`刚好小于 A`、`刚好大于 B`、`刚好小于 B`。其余具体边界设计规则自行参照。

### 五、面向对象测试的复杂性

#### 5.1 测试单元从"数据"变成"动作"

传统测试把软件看成 input-process-output（IPO）：给一组输入、检查输出即可。OO 则完全不同——一个 test case **不是一组数据输入，而是一组动作的执行过程**（a list of testing steps）。正如书中表述：*OO testing focuses on designing appropriate sequences of operations to exercise the states of a class*。即测的是一个 class，定义一系列动作去覆盖该 class 所处的不同状态。

一个 OO test case 通常包含：唯一 ID / 名字、要测的 class 名、测试目的、测试步骤清单（list of testing steps）、覆盖了哪些 state、执行了哪些 message / operation（方法）、外部准备条件、若用到其他 class 它们如何配合。

#### 5.2 主要测试方法

- **Fault-based testing（基于故障）**：公司里资深老测试员有一套针对"软件最常出错处"预制的 case，闭眼执行一遍全过，绝大多数问题就没了。思路是先想软件所有易错点，针对它们设计 case；
- **Class testing 与 class hierarchy（类与类层次）**：OO 有继承（inheritance），编程时易扩展、易裁剪，测试时却惨——测完父类不等于子类父类功能不用测（子类会"变"）；测完所有子类也不等于父类不用测。测试时省不了事；
- **Scenario-based（基于场景）**：拿 use case 逐个走，关注用户使用过程是否正常，不关注内部逻辑执行。但用户过程正常不代表内部逻辑没错，故不同角度最好结合用；
- **Random testing（随机测试）**：先定最小必测集合，其余做随机组合"瞎猫碰死耗子"，不够好；
- **Partition testing（分类测试）**：本质同传统等价类划分，但等价类定义方式不同：
  - *state-based*：把让 class 在状态间迁移的功能归一类；
  - *attribute-based*：把集中修改某一内部 attribute 的所有 operation 归一类；
  - *category-based*：按 class 要完成的几大功能把相关操作绑一起；
- **Inter-class testing（类间测试）**：把 class 理解为 client-server 关系，测试它们之间交互的 message / operator，以及 collaborator class 的配合。基本原理是先划分 client 与 server，再测交互；多基于 random，无特别好办法；
- **State-transition-diagram based**：若行为状态图清楚，就沿图设计 case——每个动作（箭头）都要做一下，动作可排列组合（什么都不做直接跳到下一动作；或走两步再结束等）。

此外还有 GUI 测试、client-server 测试；实时系统里 performance 测试很重要。建议测试中发现规律就抽象出 **testing patterns** 以便复用。最后提醒：**testing never ends**——活交出去后测试只是从你手里交到客户手里，他替你继续测。

### 六、实战演练：为二分查找设计 PAT 裁判用例

课堂给出一道 PAT 风格题，要求据此设计裁判测试数据（case 不超过 10 个，越少越好，且每个 case 须写明测试目的与分值）。

**题目：** 在一串整数中查找给定整数。输入三行——第一行正整数 $N$（$N \le 10^5$）；第二行 $N$ 个整数（均可用 int，不超长整型），**按从小到大非减序**（允许重复）；第三行待查整数 $X$。输出：若 $X$ 在序列中回答 `YES`，否则 `NO`。

**设计规则（课堂给定）：**
- 总 case 不超过 10 个，越少越好；
- 目标：用最少 case 覆盖最多错误点；
- **Sample 占 10 分（总分 20）**：sample 须包含一组 `YES` 与一组 `NO`，过了至少得一半分；
- 其余 10 分分布给其他 case，每个 case 写明"测哪个点、占几分"。

**一套符合规则的示例设计（应用等价类 + 边界值）：**

| case | 输入要点 | 测试目的 | 期望输出 | 分值 |
| --- | --- | --- | --- | --- |
| sample-1 | 小 N、X 存在 | 基本命中（YES 样例） | YES | 5（sample） |
| sample-2 | 小 N、X 不存在 | 基本未命中（NO 样例） | NO | 5（sample） |
| 3 | $N = 1$ | 最小规模、单元素边界 | 视 X | 2 |
| 4 | $N = 10^5$ | 最大规模、线性查找会被卡（逼二分） | 视 X | 2 |
| 5 | 含大量重复值、X 为重复值 | 非严格递增、重复边界 | YES | 2 |
| 6 | X 恰为序列首元素 | 左边界 | YES | 1 |
| 7 | X 恰为序列末元素 | 右边界 | YES | 1 |
| 8 | X 小于最小元素 | 下溢边界 | NO | 1 |
| 9 | X 大于最大元素 | 上溢边界 | NO | 1 |

设计要点：用 sample 保证基本功能（10 分），用 $N=1$ 与 $N=10^5$ 卡住"不用二分查找（线性扫描）必超时"的实现，用重复值验证"非减序"假设，用首尾与越界值覆盖边界——正是等价类划分（有效/无效）与边界值分析的综合运用。更难的题还需写 generator 生成大数据。

### 七、随堂自测

**题 1：** 复合条件 `B1 AND B2` 做条件覆盖，为何"两个都 T、两个都 F"两种 case 不够？最少应取哪几种组合？

> **解析与答案：** 只取（T,T）与（F,F）会漏掉"一个 F 一个 T"的组合，无法保证 B1、B2 各自都取到 T 与 F（且整句同时有 T 有 F）。最少应取三种：（T,T）、（F,T）、（T,F），使 B1、B2 均得 T/F，整句亦得 T/F。依据见第一节。

**题 2：** 简单循环（1 到 n）的循环测试，至少要覆盖哪些"次数"？为何要测 0 次与 n+1 次？

> **解析与答案：** 至少覆盖 0、1、2、n-1、n、n+1 次以及一中间值。测 0 次看能否直接跳过（非法循环），测 n+1 次看越界会怎样——边界附近最易出错（如 off-by-one）。依据见第三节 3.1。

**题 3：** OO 测试与传统 IPO 测试的根本区别是什么？为何继承（inheritance）让测试更麻烦？

> **解析与答案：** 传统测试是 input-process-output，给输入查输出；OO 测试设计的是一组动作序列去覆盖 class 的状态（state-driven），case 是一组动作而非一组数据。继承让测试麻烦：测完父类不代表子类父类功能无错（子类会变），测完子类也不免测父类，测试无法省事。依据见第五节。
