### 一、工程实践的五步骨架

在动手写代码之前，先把"软件工程到底要做什么"这件事重新理顺。前面讲过程模型时已经点明：任何软件过程都绕不开五个最关键的步骤。换一个更贴近个人经验的角度来表述，每个人做一件事，本质上也是这五步循环：

1. **理解问题（Understand the problem）**：对应工程中的 Communication 与 Analysis。先搞清楚要做什么、为谁做、做到什么程度。
2. **制定计划（Plan）**：对应 Modeling 与 Design。想清楚打算怎么做、系统长什么样、模块怎么切分。
3. **执行计划（Carry out the plan）**：真正开始"干活"，进入构造阶段。
4. **验证结果（Verify）**：对应 Testing 与 Quality Assurance，确认做出来的是对的、是合格的。
5. **交付部署（Deployment）**：把成果交给用户使用。

这五步中，前三步是"从无到有地定义与构造"，后两步是"确认与交付"。它们既是软件过程的骨架，也是任何工程活动通用的心智模型。软件工程课程后续所有内容，都可以挂回这五步之中。

### 二、四条不可违背的核心原则

原则不要求死记硬背，只需判断它有没有道理。

#### 2.1 始终为顾客与用户创造价值

你提出任何建议、推动任何改动，第一反应应当是：这件事给 customer 和 user 带来了什么价值？最笨的一种说服方式是这样的——你跑去跟客户说："现在这项技术最流行，我把它用上，系统内部结构会非常漂亮，以后便于维护、便于扩展……"客户的真实反应是："So what？跟我有关系吗？"

举个计算性能的例子。原来的程序算一次要 3 秒，你能压到 0.3 秒，这对用户是有意义的，可以说服人。但如果原来的计算 1 毫秒就完成了，你优化到 0.1 毫秒，用户根本感知不到差异，却要为此多花钱——那客户当然选择维持原状。技术宅自我陶醉式的"内部很漂亮"，对用户毫无意义。

因此，凡是打算推动的变更，必须先想清楚：**它对客户而言意义何在**。说不清楚价值，事情就谈不下来。

#### 2.2 KISS 原则：Keep it simple, stupid

不要追求 fancy、smart 的解法，越简单越好。两个流传甚广的笑话恰好说明问题。

**太空笔的故事。** 宇航员进入太空后发现圆珠笔写不出字——失重状态下不出水。美国人花重金组建研究团队，研制出一支在失重状况下照常出水的"太空笔"。俄国人碰到同样的问题，解决方案是：用铅笔。

**空肥皂盒的故事。** 一家企业引进了自动生产肥皂的生产线，肥皂自动装盒、流水线产出。但偶尔会出故障：肥皂没进盒，出来的就是空盒子，表面上看和普通盒子一模一样，难辨真伪。大企业请了一位博士，申请到国家自然科学基金资助，立项研究，花大钱设计了一套精密仪器架在流水线上，用传感器精确判断哪个盒子是空的。另一家乡镇小厂买的是同一条线，也遇到同样问题。老板请不起博士，找了个小工。小工抱了一台电风扇，放在流水线旁对着盒子吹——空的肥皂盒轻，直接被吹跑了；有肥皂的盒子重，顺着线走下去。问题就这么解决了。

两个故事共同揭示一件事：先想"傻一点"的方案，别把事情想复杂。**Keep it simple, stupid** 往往是最优解。

#### 2.3 随时校准方向（Vision）

Vision 指的是大方向。无论你埋头处理多细的细节，都要确保自己朝着正确的方向走。方向如果反了，做得越卖力，错得越狠、毁得越彻底。所以要随时把自己抽离出来，抬头看一眼："我还在正确的方向上吗？"这一步极其重要，也是前面讲过的"Be open to the future"——站在战略高度才能看清未来。

#### 2.4 你生产的东西，是给别人消费的

What you produce, others will consume。你做的不仅仅是最终交付的软件系统，你写的需求文档是给别人读的，做的设计方案是要让别人看懂的。这门课教的不仅是"怎么做事"，更是"怎么为人"——做事时随时替别人着想。你不是为了自我陶醉、自我满足才做事情的，你做出来的每一份产物都有下游的消费者。

### 三、系统工程的层次观

软件工程是系统工程的一种。系统工程最大的特点是看问题有鲜明的**层次化观念**。从最顶层到最底层，可以清晰地分为以下几级：

```
Business Process Engineering（业务流程工程）
 ├─ Information Strategy Planning（信息战略规划）
 ├─ Enterprise Modeling（企业建模）
 └─ Business Area Analysis（业务领域分析：财务/人力/制造…）
        │
        ▼
Product Engineering（产品工程：软件工程 + 硬件工程 + 其他）
 ├─ Component Engineering（构件工程 / 组件工程）
 │   └─ 构件的 分析 / 设计 / 构造 / 测试
 │        └─ Element（元素：一行代码 / 一张数据表）
```

**业务流程工程（Business Process Engineering）**这一层关注企业的业务目标。其中：

- **信息战略规划（Information Strategy Planning）**站在最顶端，考虑整个企业未来三年、五年的战略目标，信息化要达到什么水平、去支撑什么样的业务。
- **企业建模（Enterprise Modeling）**在规划基础上，把企业的组织结构、业务流程、数据流等建立成相应模型。
- **业务领域分析（Business Area Analysis）**落到具体领域，如财务、人力资源、生产制造等。

再往下，进入具体的系统（某业务领域的系统或某个具体产品），就到了 **Product Engineering（产品工程）**。它包含软件工程、硬件工程及其他相关工程，最终交付一个具体产品或系统。产品由不同 component 构成，于是有 **Component Engineering（构件工程）**，涵盖构件的分析、设计、构造、测试。最底层是具体的 element，比如一行代码或一张数据表。

学软件工程一定要明白：**你不是孤立地在写代码**。你写的代码属于某个 component，component 属于某个 product，product 是为了支撑某个 business area，而 business area 又是整个 enterprise 的一部分，服务于企业的 information strategy。有了这种宏观视野和自顶向下的层次感，做软件设计、软件架构时的格局会完全不同——你会明白需求为何这样提、系统为何这样架构、为何要考虑扩展性以及未来的变化。

### 四、一个计算机系统的六大要素

做系统分析与系统工程时，绝不能只盯着代码。一个完整的基于计算机的系统（Computer-based System）由六个要素共同构成：

| 要素 | 英文 | 含义 |
|------|------|------|
| 软件 | Software | 计算机程序、数据结构以及相关的文档 |
| 硬件 | Hardware | 运行软件的计算机设备、网络设备、各种外设、传感器等 |
| 人 | People | 系统的用户、操作者、维护人员等 |
| 数据库 | Database | 存储系统所需的各种结构化与非结构化数据 |
| 文档 | Documentation | 用户手册、操作指南、开发与维护文档等纸质或电子资料 |
| 规程 | Procedures | 定义人如何在不同情况下使用该系统的步骤与规范 |

这六类要素必须综合起来考虑。软件只是其中一块，硬件、人、数据库、文档、规程同样决定系统能否真正运转。

### 五、系统层次结构与两种工程方向

从最宏观到最微观，系统的层次是：

```
World View（全局视图）
   └─ Domain（领域）
        └─ System（系统）
             └─ Component（构件）
                  └─ Element（元素）
```

工程方法上通常有两个方向：

- **自顶向下（Top-down）**：分析问题时，从宏观逐层分解，把大问题拆成小问题。
- **自底向上（Bottom-up）**：工程实现与构造时，先把底层 element 做好，组装成 component，再集成到 system，最终解决特定 domain 的业务问题。

做 Business Process Engineering 时，核心目标是明确企业业务目标、梳理核心业务流程、规划相应的信息系统来支撑。这也是大型企业数字化转型时先做流程梳理与企业架构设计（Enterprise Architecture），理清脉络后才立项进入具体 Product Engineering 的原因。而 Product Engineering 阶段，软件工程是非常核心的组成部分，涵盖需求分析、设计、编码、测试、维护等一整套规范的方法、工具与过程。

### 六、组织视角下的分层视图

把层次观映射到一家真实公司，会看到不同层级的人关心不同的粒度：

- **老板（顶层）**：脑子里是一个 World View。他要回答"我们要在哪几个方面改变世界"——做互联网、做操作系统、做硬件还是做别的。这是 World View 层面。
- **产品领域负责人**：每个 product domain 有一位负责人，面对 Domain of interest。例如 Office 不是一个 product，而是一组 products（Word、PowerPoint、Excel……），这就构成 Domain view。
- **产品经理 / 系统负责人**：Domain view 里每个 product 都有自己的 System element，涉及 software、hardware、people、timeline 等做产品必须关心的因素。
- **项目经理（Element view）**：每个 product 之下有对应的 management。
- **基层团队（Detailed view）**：项目经理之下，由具体团队去干活的 detailed view。

公司里不同层次的人，每人关心自己的一摊活，但关注到的细节程度不一样。应当养成习惯：看所有事情都按这种层次化方式去拆解。

站在老板的层面，他也有一层层加细的考虑，但那是业务视野：先有 information strategy planning（处理哪些领域的信息），每个领域有 business analysis，再到 business 的 system design，越来越细，最后到 construction 阶段。他关心的不是程序架构、机器结构，而是**整个公司的产品架构（product architecture）**——需要定义架构；他要考虑 data architecture（打算处理哪些领域的数据，注意这不是 data structure）、要做哪些应用、这些应用在公司产品架构里如何架设；还要考虑 technology——公司最擅长哪几项技术、重点发展哪个方向。这是非常宏观的考量。

Product 层则是把老板想做的几件事归拢成一个产品，即 product engineering。做事情时，脑海里应自动浮现这样的层次化架构。

### 七、系统建模的通用框架

给系统建模型时，有一个通用模板：**绝大部分系统都可以理解为 input-process-output 的结构**——有输入，中间处理一下，最后产生输出。几乎所有系统都能被装进这个框架。

用 Architecture Flow Diagram（架构流程图）来表达时，通行的画法如下：

```
          ┌─────────────────────────────────────────┐
          │               System Boundary             │
          │                                           │
  输入 ──▶│  输入处理模块 (Input→Internal)             │
          │        │                                  │
          │        ▼                                  │
          │  核心处理模块 (Core Process Functions)     │
          │        │                                  │
          │        ▼                                  │
  输出 ◀──│  输出处理模块 (Output)                     │
          │                                           │
  前端 ──▶│  Interface (用户界面 / 最前端)             │
          │                                           │
          │  Management / Maintenance (后端管理维护)   │
          │  Self-Test / Diagnostic (自我诊断，底层)   │
          └─────────────────────────────────────────┘
```

布局约定：

- 顶层画的是 **interface**，即最前端的用户界面。
- 底层画的是后端的 **management / maintenance** 以及 **self-test / diagnostic**（系统自我检测模块）。
- 左侧放把 input 数据转化为内部可处理类型的数据的模块。
- 右侧放处理 output 的模块。
- 中间放核心处理模块，所有 process 功能都集中在这里。

前提是该图不能太复杂；不太复杂时，把不同模块放在不同位置，用箭头连线表示它们如何关联即可。以后做毕业设计，若只做了大系统里的某个模块，也可以画这么一张图，说明你的模块在大系统架构中的位置和上下关系。

#### 7.1 实例：传送带分拣系统（Conveyor Line Sorting System）

书中以传送带上的集装箱分拣为例。一堆集装箱从传送带过来，每个箱子上贴有条形码。系统的工作流程如下：

```
[Scanner] 读取条形码
    │
    ├─ 同时读取传送带速度 (Sensor)
    ▼
[Decoder] 解码器：解出该箱子应归属的哪个大箱 (bin)
    │
    ├─ 查 Database → 得到 bin location (应放入的仓位)
    │
    ├─ 结合传送带速度估算箱子到达时间
    ▼
[Shunt] 分送机械臂：在正确时机把箱子送入对应的第 N 号大箱
    │
    └─ 写入 Database，生成 Report 记录
```

描述这个系统时，无需细抠小字，只需看架构：前端有 interface 让人看到结果；底层有 self-test 模块检测系统是否出错；左侧是 barcode 读取与 sensor 速度信号处理；右侧是机械臂把物品送往何处；中间是真正的处理模块，以及它们彼此如何通信。这就是一份非常粗的 Architecture Flow Diagram。

**画图的表达技巧：** 若做 presentation 要解释清楚系统，绝不能像"哗"一下把整幅图同时甩出来——那样听众只会晕。正确做法是先出一个空框架，然后随讲解进度，动态地让对应模块逐个浮现，流水线箭头按演讲顺序依次展现。这样读者才能在短时间内理解你的系统。

### 八、后续将用到的建模工具速览

后面正式收集、整理需求之前，先快速认识几类 UML（Unified Modeling Language）图。UML 本身足以单独开一门课，这里只建立初步印象。

**1. 部署图（Deployment Diagram）**
专门描述硬件块。例如上面的分拣系统交付时，用一个处理器（processor）表示实物机器，处理器内大体分两块模块：一块管 sorting，一块管控制 display。其中 sorting 那块又分读取 sensor 的、控制分转机械臂的。部署图用来讲清硬件由几块组成。

**2. 活动图（Activity Diagram）**
描述动态执行过程（动作序列）。规矩是：开始点是一个实心黑圆饼；结束是黑圆饼外头套一个圆圈；每个动作写在框里，用箭头表示发生顺序；**粗黑线表示时间线**——在时间点上两件事同时开始；菱形表示"或"的关系（例如 barcode 读对、或读错 invalid，两种情况分流）。多个分支在某点汇齐后，再进入下一步。

**3. 类图（Class Diagram）**
描述一个 class（学过 C++ 会很容易理解）。基本分三块：上面是名字，中间是 attributes，下面是 methods / operations。

**4. 用例图（Use Case Diagram）**
它早先叫 user scenarios（用户脚本），翻译过来即"用户脚本"——像导演写电影分镜头剧本，描述用户从启动、进入情景、第一步做什么、第二步做什么的完整流程。脚本可以有分支，执行到某步有三个选项，就对应三个子脚本，因此纯文字描述会很痛苦、也少有人认真看。后来把它简化成半图形、半文字的形式。

仍以分拣系统为例，第一层 use case 非常简单：operator 进入系统后，可直接在面板上做几件明确的事。到更细的分析与设计阶段，图可以有好几层——例如 request barcode 之后还要调用哪些功能完成，被调用的功能再调用其他功能，一层层深化下去。UML 给出的就是这样一个工具，让你用图形把整个执行流程画清楚，而不必完全依赖文字。

### 随堂自测

**1. 为什么直接以"技术新颖、内部结构漂亮、便于维护"作为说服客户的理由往往是无效的？正确的出发点应该是什么？**

解析：客户关心的是自身价值而非技术宅的自我满足。若优化带来的性能提升（如从 1ms 到 0.1ms）用户根本感知不到，却要为此多花钱，客户自然拒绝。正确出发点是"我这么做会给客户带来什么好处"，即始终为 customer 和 user 创造价值。（依据：第二节 2.1）

**2. 一个基于计算机的系统由哪六大要素构成？为什么做系统工程不能只盯着代码？**

解析：六大要素是 Software（软件）、Hardware（硬件）、People（人）、Database（数据库）、Documentation（文档）、Procedures（规程）。软件只是其中之一，硬件、人、数据库、文档、规程同样决定系统能否真正运转，因此做系统分析必须综合六要素考虑。（依据：第四节）

**3. 自顶向下与自底向上分别在什么阶段使用？请结合系统层次结构说明。**

解析：系统层次为 World View → Domain → System → Component → Element。分析问题时通常自顶向下逐层分解（把大问题拆小）；工程实现与构造时通常自底向上，先把底层 element 做好，组装成 component，再集成到 system，最终解决特定 domain 的业务问题。（依据：第五节）

## 第 2 章：第7讲 需求工程-1
> 对应分集：P07 | 原始标题：《第7讲 需求工程-1》

### 一、为什么需求工程值得单独开一章

前面三周都在讲宏观概念，现在终于要干第一件实事——Requirements Engineering（需求工程），也就是你们要交的第一个 project 对应的工作内容。但按本书的写作习惯，讲任何方法之前先要回答 **what to do**（做什么），然后才讲 **how to do it**（怎么做）。所以这一讲不急着教画图，先说清楚：需求工程大概干哪几件事、为什么非做不可、做的过程中有哪些环节。

### 二、需求没做好的代价

在讲环节之前，先看两个触目惊心的反例，体会"需求错了会怎样"。

#### 2.1 阿丽亚娜 5 号（Ariane 5）发射失败

1996 年 6 月 4 日，阿丽亚娜 5 号火箭带着四颗卫星升空后，像"喝醉了酒"一样开始摇晃，最终只能遥控引爆，火箭连同四颗卫星一起炸毁。事故的直接经济损失达 **5 亿美元（500 million US dollars）**，这还只是看得见的部分；看不见的损失是 ESA（欧洲空间局）的声誉一落千丈——当年反倒让别国赚了一笔卫星发射的生意。

事故调查追踪到的根因，竟是需求文档里**少写了一句话**：阿丽亚娜 5 号的轨迹倾角会比阿丽亚娜 4 号更大。就这一点区别没说清，导致计算轨迹的公式没有相应修改。火箭升空后，倾角超过了阿丽亚娜 4 号倾角的最大值，计算发生**溢出（overflow）**；而模块没有在溢出时停止计算，继续算出一堆垃圾数据，于是火箭在天上东摇西摆、轨道全乱，最终自毁。

一句话的缺失，葬送了 5 亿美元和四颗卫星。这就是需求缺陷的代价。

#### 2.2 Standish Group 的行业调查报告

1994 年，Standish Group 对 350 家企业、约 8000 多个软件项目做了调查，结果发人深省：

- **31%** 的项目在完工前就被取消（canceled before completion），中途夭折。
- 在保质保量、按预算、按时交付的维度上，大公司只有 **9%** 较成功，小公司稍好，为 **16%**（人少麻烦事少）。

1995 年继续追查原因，高居榜首的两位是：

1. **Incomplete requirements**（需求不完整）
2. **Lack of user involvement**（用户参与度不足）

这两件事本质上同源，都是 **communication（沟通）** 出了问题——正因为没有跟用户充分沟通，才导致需求残缺不全。这足以说明：获取需求是一件多么重要、又多么容易翻车的事。

### 三、需求是如何一层层失真的

网上有一张流传很广的"树上秋千（tree swing）"讽刺图，把需求失真画得淋漓尽致：

- 客户描述："我要这么个东西"（一个秋千）
- 项目经理理解成了：另一个样子
- 分析员设计成：又一个样子
- 程序员编码：又一个样子
- 商业顾问眼里的：豪华沙发
- 项目文档里写的：极简
- 安装程序呈现的：如此简洁
- 客户投资：如此巨大
- 技术支持：另一样
- 解密后的实际需求：其实他就要那么个玩意儿

每一层都在偏离，最后交付物与客户本意天差地别。

《人月神话》的作者 **Brooks** 有一句名言：

> "The hardest single part of building a software system is deciding what to build."
> 建造软件系统最难的那一部分，是搞清楚到底要造什么。

真的把"要做什么"搞清楚之后，动手去做反而不是最难的事。

#### 3.1 一个真实的非专业用户沟通案例

讲一个人口仿真计算项目的经历。用户是一位非本专业的研究者（老先生），他要做一个人口仿真系统。沟通中暴露出典型的"兴趣不一致"问题：

- **用户的兴奋点**在算法本身：他花大量时间讲算法原理、政策组合怎么推算、放开二胎后 100 年内人口怎么变。
- **开发方的兴奋点**在执行流程：数据怎么导入、要哪几种图、哪几种表、界面上按个按钮就开始算、结果怎么图形化显示。

原理对做软件的人来说意义不大——那不过是一段写好运行的程序，重点在界面按钮和图形显示。但用户不关心流程，只关心算法，于是草草一句"流程很简单，数据导进来算一下显示一下就好了"。

开发方最初的理解是：你要么有数据库、要么有文件，导进来即可。于是先做了个 prototype（原型）去给用户看。用户一看："没这么简单！"——数据导入前其实有一堆复杂选项卡。改好选项卡，一周后再去沟通，用户又说"没这么简单"。每个星期去一次，每个星期都冒出不一样的需求。

这个案例带来三点深刻教训：

1. **原型（prototyping）救了场。** 幸好选了原型过程模型，否则麻烦更大。
2. **需求是逐步浮现的。** 用户的描述 → 你的理解 → 他否定 → 他给出新描述 → 你再改……如此循环。
3. **没有文档的后果很严重。** 这个项目没有需求文档，学生每次沟通到新需求就记一下、在原型里实现。后来前面的学长去香港交流，接手的人崩溃了："这是什么乱七八糟的东西！"程序写得乱是有原因的——需求是"一点一点"来的，不是先有完整设计再编码。接手者无从知晓全貌。

更关键的是认知错位：**客户不是你专业的**。你以为至关重要的专业细节，他根本不 care、根本没想到有问题。跟非专业人士沟通时，你不能用自己的术语，必须**用他的术语跟他讲**，否则就是"鸡同鸭讲"，两人各说各话、谁也没听懂谁，后面极可能跳进一个大坑。

### 四、需求工程的七个环节

基于常识想想：拿到一个项目，要开始做需求，第一件事干什么？你们的 project 现在大概自以为需求清楚了——但其实第一件事应该是 inception（起始、起手式）。

需求工程（Requirements Engineering）整体包含以下环节，下面逐一展开：

```
Inception（起始）
   │  摸清情况、找干系人
   ▼
Elicitation（导出 / 诱导）
   │  问一圈所有人：你到底想要什么
   ▼
Elaboration（细化）
   │  落到纸面，建 analysis model
   ▼
Negotiation（谈判）
   │  成本、底线、deadline
   ▼
Specification（规约）
   │  写成详细文件：Requirement Specification
   ▼
Validation（验证）
   │  复审：有没有错、漏、矛盾
   ▼
Management（管理）
      控制需求变更
```

#### 4.1 Inception（起始阶段）

太极拳或任何拳法都有"起手式"，inception 就是需求工程的起手式：问一系列问题，把基本情况摸清。

**要做的三件事：**

1. **找齐干系人（stakeholders）。** 一个典型问题是："Who else do you think I should talk to?"（你觉得我还应该跟谁谈？）你获取了某个人的需求，但他是唯一相关的人吗？还有谁要用软件？还有谁需要再谈？把相关的人全部找齐。
2. **识别多种观点（recognize multiple points of view）。** 不同角度的人看法不同，要多找几个人、从不同侧面了解。
3. **营造合作关系（working toward collaboration）。** 让客户明白：他的工作随时与你相关，不是把需求"丢过墙"就可以不管了。客户应当有义务帮你把事情理解清楚。

本书像工作手册，连"该问什么问题"都列好了。问题分三组，逐组细化：

**第一组：上下文（Context）——先不问技术细节，先摸清大环境**

- *"Who's behind the request for this work?"* —— 谁在幕后推动？比如支付宝项目，你直接对接的是 TA，但"垂帘听政"的另有其人。
- *"Who will use the solution?"* —— 做出来谁用？
- *"What will be the economic benefit of a successful solution?"* —— 成功交付能带来多大经济效益？这一点决定了后续一系列措施都不同。
- *"Is there another source for the solution that you need?"* —— 我是你唯一找的人吗？你还找了别家吗？

为什么要问"还有没有别家"？因为它直接影响谈判策略。如果这事能给他带来巨大经济效益、且你技术力量强到他非你不可，那后续是一套处理方式；如果对他只是锦上添花、可有可无（比如为了某个政治任务），他配合态度就完全不同；如果他同时在联系好几家，那你在 inception 阶段（还只是了解情况、没开始谈判）就要意识到：后面的谈判策略全都会不一样。所以第一套问题，是把前后左右的关系、大环境先搞清楚，具体内容反而不急。

**第二组：客户的感知（customer's perceptions about the solution）**

才开始问稍微沾边的事——在客户脑海里，他想要的到底大概是什么样？获取这种感知，最好做个 prototype。若嫌改原型麻烦，可以像跟老先生沟通那样，直接在黑板上画界面："你点一下，出现一个下拉菜单（画出来）；最上面是什么；你再点，上面出现一个文本框，里面是什么内容，你觉得这样？"边画边演示。演示到中途他往往会说："这步不对，没那么简单。"——这正是你想要的：看清客户脑海里真正想要的东西。

**第三组：沟通活动本身的有效性（effectiveness of the communication activity itself）**

要问清以后能期待什么程度的配合。例如在支付宝这种跟金融、银行规矩强相关的项目里，你可以问："我很多规矩不懂，以后想了解细节时，我可以找谁？"对方公司里有没有专门的联系人、他忙不忙、出不出差、来参加组会算不算他工作的一部分（拿不拿工资）？如果银行领导发现自己的员工整天跑去你们组开会，会很不高兴："我付你工资是给我干活还是给他们干活？"这些——你的 TA 有多忙、要提前多久预约、能在多大程度上随叫随到——都必须在 **Inception** 阶段问清楚。

#### 4.2 Elicitation（导出 / 诱导阶段）

Elicitation 一词本意是"诱导、导出"。你初步了解"要做支付宝"后，不能只停留在一个简单概述，必须主动去导出——把所有可能相关的人问一圈：你到底想要什么。

难点在于：**客户自己常常说不清想要什么**（比如那位人口学老先生，不觉得有什么好说，认为"很显然"）。而且因为不专业，他最初不清楚计算机到底能帮到什么程度。聊着聊着他会发现："哎，你还能干这个？那能不能给我加个功能？"胃口越来越大，甚至想"像苹果一样在屏幕上拖来拖去、用手势打开新项目"——这些需求在第一次接触时他全想不到，最初他只想做个"算法最亮眼的人口仿真平台"。

所以 elicitation 是要**主动诱导**用户说出他真正想要、或对他有帮助的东西。

**导出需求离不开开会。** 会议的目的有四：

1. **Identify the problem** —— 搞清楚我们要解决的是一个什么样的问题。
2. **Propose elements of the solution** —— 解决方案大致由哪几部分构成，大家来凑。
3. **Negotiate different approaches** —— 解决途径往往不止一种，谈判一下大家更偏好哪一种。
4. **A preliminary set of solution requirements** —— 给出一个初步的、尚未细化的需求集合。

开好这个会本身就是学问：要找哪些人、设置哪些环节、做哪些准备、最后要得到什么，都需提前设计。

#### 4.3 Elaboration（细化阶段）

Elaboration 即细化：把导出的需求真正落到纸面，建立 **analysis model**（分析模型）——也就是下一讲要教的内容：如何描述 data structure、描述功能、描述系统的动态行为（behavioral requirements）。

这里有个重要经验：**纯文字不受欢迎**。如果你只把用户的话记成长篇日记或纪要，让他审查"我记错没"，可以担保 99% 的客户没耐心细读。所以要用一堆图形（包括 prototype）这种更容易理解的方式去沟通，确认"你确实想做这件事"。

#### 4.4 Negotiation（谈判阶段）

确认了要做的是什么，就进入谈判：我要不要做这件事、以什么条件做。谈判主要围绕：

- **成本与底线**：你至少得给我多少钱，否则我做不来。
- **Deadline**：你跟我说下星期交货，我两颗人实在做不出来，不可能。

就是这些条件的博弈过程。

#### 4.5 Specification（规约阶段）

谈判谈定后，才真正把所有东西写成详细文件——**Requirement Specification（需求规格说明书）**。这份文件有三个关键功能：

1. 作为后续设计的主要根据与基础；
2. 作为与用户沟通的文档；
3. **最重要的——验收依据**：写清楚哪些指标达到了，就要付钱。

很多项目做得不愉快，根子就在没有 specification。口头说定，交付时客户说"这不是我要的"，或"90% 功能可以，但一项关键功能做错了，软件不能用，我不付钱"——你拿不出证据、没有文档，辛苦做出来的东西无法交付。所以 specification 必须写清验收准则（acceptance criterion）：哪些指标达到什么要求，一手交钱一手交货。

#### 4.6 Validation（验证阶段）

写好的 specification 必须有一个审核、复审过程：看有没有错误、有没有漏掉东西、前后是否矛盾、不同部门的需求有没有互相掐架（撞车）。

#### 4.7 Management（管理阶段）

最后必须有 management，核心功能是 **change（变更控制）**。课题组做得差，基本没有 change management——因为是熟人，老先生说要改就改了。但在公司里绝不能这样：需求变更有一套严格流程决定要不要改、甚至要加钱。这些控制过程就是 management 要管的。

### 随堂自测

**1. 阿丽亚娜 5 号事故的根因是什么？它说明了需求文档的哪一项功能不可或缺？**

解析：根因是需求文档中少写了一句话——阿丽亚娜 5 号轨迹倾角比 4 号更大，导致计算轨迹的公式未改，升空后倾角超出旧最大值发生溢出，模块未停止计算而输出垃圾数据，火箭失控自毁。这说明需求文档必须精确无遗漏，尤其是像规格说明（specification）那样写清每一项指标与约束，否则后续一切推导都可能建立在错误前提上。（依据：第二节 2.1）

**2. 与"非专业用户"沟通需求时，为什么容易出现偏差？正确的沟通策略是什么？**

解析：因为客户不是本专业的，他对自己专业至关重要的事不 care、也想不到计算机能帮到什么程度；而开发方习惯用自己的术语，双方兴奋点不一致（用户关心算法原理、开发方关心执行流程），于是"鸡同鸭讲"。正确策略是：用客户的术语而不是自己的术语跟他讲，并通过原型（prototype）或黑板画界面等方式让他直观确认，主动诱导（elicitation）他说出真实需求。（依据：第三节、第四节 4.2）

**3. 需求工程的七个环节中，Inception（起始）阶段要问的三组问题分别解决什么？**

解析：第一组问上下文（Context），摸清大环境——谁在幕后推动、谁使用、成功带来的经济效益、是否还有别家可选，这决定了后续谈判策略；第二组问客户感知（customer's perceptions），弄清客户脑海里想要的东西长什么样（用原型/草图确认）；第三组问沟通有效性（communication effectiveness），弄清以后能在多大程度上期待客户配合（联系人忙不忙、能否参加组会等）。（依据：第四节 4.1）

## 第 3 章：第8讲 需求工程-2
> 对应分集：P08 | 原始标题：《第8讲 需求工程-2》

### 一、需求导出会怎么开才专业

需求导出（Elicitation）离不开开会。会开得专不专业，直接决定你能不能把需求问清楚。上一讲提过会议有四个目的：identify the problem、propose elements of the solution、negotiate different approaches、给出一份 preliminary set of solution requirements。这一讲落到"怎么组织这场会"的操作细节。

#### 1.1 把对的人请到

开会首先要想清楚**请谁**。绝不只是你们组的人要参加——TA（customer）必须参加。但这够了吗？不够。因为你做的不是整个系统，而是系统里的一个模块，所以跟你有最强关联的其他几个组的主要技术人员，最好也拉来参加。先把"要找谁"想明白，再去准备开会。

#### 1.2 立规矩，确保人到

会议要有 rules，不能"想来就来、想不来就不来"。哪些人是必须到的，要想办法保证。尤其是 customer——比如银行那边的工作人员，你说"我开个会您必须来"，拿什么措施保证他一定到？规矩要提前协商好。例如组会固定每周一次，大家碰头，那你得事先跟人家商量好：开会时你们都要到。

#### 1.3 必有的会议日程（Agenda）

**agenda（会议日程）极其重要。** 很多人发会议通知只写"几点大概开个会、商量哪几件事"，这不够。专业的通知要写清：几点开会、本次会议有几个议题（第一、第二、第三）、每个议题讨论多少分钟、总共几小时。这样每个人心里有数——"从几点到几点这段时间我空出来给你，其余时间我安排自己的事"，既不跑题，又给人"做事很有效率"的感觉。

#### 1.4 主持人（Facilitator）

有了 agenda，就必须有 **facilitator（会议主持人）**。主持人可以是你、可以是 customer、也可以专门请一个仲裁来当，形式随意。主持人最重要的功能是**按日程控时**：议题说好讨论 30 分钟，20 分钟过去还漫无边际没头绪，就要提醒"聚拢一下，还有 10 分钟赶紧商量出结论"；时间一到，无论有没有结论，切换到下一议题，剩下的下次再找时间。因为每个人的时间都宝贵——说好 45 分钟下课就 45 分钟下课，拖堂会耽误别人下节课。时间不够只能说明 agenda 排错了、会前准备没做好。

主持人还要管发言：某人啰哩啰嗦说不到点子上，主持人要打断"简短一下，时间有限"。

#### 1.5 记录机制（Definition Mechanism）

开会要有一个 **definition mechanism**——让大家能把讨论的东西记下来的工具。通常至少给每人一张纸、一支笔；最好有投影或黑板——要发表一个共同见解让人看见时，就在黑板上写两句，大家确认。也就是既要有讨论工具，也要有记录工具。

#### 1.6 会议纪要

最后一定要产出 **会议纪要（meeting minutes）**。讨论过的事不记下来，回头就忘。这点怎么强调都不过分。

反面典型是：发个邮件、群发短信说"啥时候开个会、到哪个寝室去"，大家来了，之前要说啥没打过招呼，组长想到哪说到哪，大伙歪一通——这种会开得不专业。

### 二、用 QFD 把客户语言翻译成技术需求

需求导出后，要把 customer 想要的东西转换成技术人员能理解的 requirement。这里介绍一种策略：**QFD（Quality Function Deployment，质量功能展开）**。

QFD 的核心特征是**以客户满意度最大化为目标（maximize customer satisfaction）**去做所有事情。因此第一步必须搞清楚：什么叫 customer satisfaction（客户满意度）？它的做法里，中间那几件（确定数据输入输出、确定系统 behavior，建 model）是普通的，但有两件事是关键：

#### 2.1 Function Deployment（功能展开）

要把每一个要做的功能搞清楚，同时给每个功能一个 **value（价值分）**——这个功能对客户有多重要、做好了能带来多少满意度，打个分。

#### 2.2 Value Analysis（价值分析）

把所有需求归拢，在每项功能上打分，然后按分数把需求分成三大类：

| 类别 | 含义 | 开发策略 |
|------|------|----------|
| **Normal** | 普通青年要的功能，必备项 | 有限资源下**最先保证**做好 |
| **Expected** | 文艺青年要的功能，期待有但缺了也不会死 | 作为专业软件**也应该做好** |
| **Exciting** | 惊喜型功能 | 看余力、看钱够不够再做 |

这个分类决定了开发优先级：**绝不能本末倒置**。举个手机的例子——你做了地图、导航、照片、音乐，全都很好，唯独电话不好使，那公司的人会说"事情根本没法做，你怎么会答应下来的"，项目就做不成了。Normal 的功能（打电话）必须先保住，Expected 应该做好，Exciting 有余力再加。

### 三、谈判是一门妥协的艺术

谈判（negotiation）阶段，要把"做不做、以什么条件做"谈定。这里面的道理，其实不止用于软件项目，做人也一样。

#### 3.1 双赢（Win-Win）是前提

跟人沟通合作时，不要只想着"对我们有什么好处"，还要想"人家这么做对他有什么好处"。以面试出国交流项目为例：学生都强调"我特别希望得到机会"，这没错但不够。面试官（代表学院）会想"我为什么要让你去？"——学院派学生出去，一方面锻炼学生，另一方面要创国际声誉、派优秀学生去**创牌子而不是砸牌子**。所以必须是一个 **win-win condition（双赢局面）**，达不到双赢，事情就不可能达成。

#### 3.2 七条谈判原则

**原则一：It is not a competition（这不是竞赛）。**
你在谈判，不是在辩论赛。辩论中赢了，对你未必有好处。政治是妥协的艺术，谈判也是——妥协到什么程度是学问：妥协过了你傻，push 太过了也未必聪明，是一个"度"。

**原则二：Map out a strategy（要有策略）。**
没经验的谈判者常犯傻：一竿子插到底"我的底线就在这，要么同意要么拉倒"，结果一上来就谈崩。要想让对方接受你的条件，要先迂回营造出一个"他最后不得不接受、或非常愿意接受"的情境。事先做好功课：充分了解对手，了解他的需求、长处、弱点，**最好能摸清他的底线**，才能设计出"先说什么、后说什么、把哪件事谈到什么程度"的全套计划。

**原则三：Listen（听）。**
年轻人最容易犯的错，是沟通时急于表达自己——"我有个 idea 赶紧让你知道"，人家刚说个开头就打断"我知道你想说什么，听我说"。这很傻。不要急，哪怕他说得啰嗦、慢，也要仔细听。人家常有弦外之音，也会在不经意间透露出本来没打算透露的信息——**你会听，就比不会听的人多得到很多**。你说得越多，犯错机会越多；没必要 volunteer（主动暴露）太多信息，尽可能从人家只言片语里挖更多信息。Listen 不仅是礼貌，更是策略。

**原则四：Focus on the other party's interest（聚焦对方利益）。**
谈判最忌"做这事对我有什么好处"。对方想的是"我关心对我有什么好处"。所以最高明的技巧，是**站在对方立场说"如果这样做，对你有什么好处"**。例如谈国际交流，不能说"把学生送过去对我的学生很有好处"，而要说"把我最优秀的学生送给你，对你有什么好处"——他心动了，事就成。

**原则五：Don't let it get personal（对事不对人）。**
这是 be professional 的基本原则。技术问题、项目上有分歧，可以拍桌子吵架，但**不要人身攻击、不涉及人品**，尤其忌讳翻老账（"上次那项目你就是那样，这次又来了"）。就事论事，一件事是一件事。

**原则六：Be creative（有创意）。**
如果卡死了，好像是不可协调的矛盾——其实没有不可协调的矛盾，一定有办法。聪明人会在大家陷入死胡同时 **jump out of the box（跳出框框）**，想一个不一样的办法。

**原则七：Be ready to commit（说到做到）。**
说出去的话泼出去的水，是要兑现的，不能忽悠。谈判时小心：你说的每个条件，都要准备好——如果对方说"好的"，这条线画下来，你是真做得到的。别抢着说"我一个星期就能做完"（其实你一个月都悬），对方说"好，给你钱"，你就傻了。随时准备好你说出去的每条线会被画下来，然后你必须 commit。

### 四、验证需求（Validation）

需求做好后要做 validation（验证/复审）。主要检查三件事：

- **Consistency（一致性）**：前后有没有矛盾，不同部门的需求有没有互相掐架（撞车）。
- **Completeness（完整性）**：有没有漏掉什么东西。
- **Clarity（清晰性）**：有没有描述不清楚、让人看不懂的地方。

这就是需求工程收尾时该做好的质量把关。

### 随堂自测

**1. 一场专业的需求导出会，为什么必须有 agenda 和 facilitator？二者各自解决什么问题？**

解析：agenda（会议日程）要解决"跑题"和"参与者无法安排时间"的问题——它写清几点开会、几个议题、每议题多少分钟、总时长，让每个人心里有数、会议不偏题。facilitator（主持人）要解决"控时失控"的问题——按日程在议题时间到时强制切换下一议题，并打断啰嗦发言、提醒大家聚拢出结论，保障每个人的时间不被浪费。（依据：第一节 1.3、1.4）

**2. QFD 的 Value Analysis 把需求分为哪三类？为什么"手机地图导航照片都好、唯独电话不好使"是失败的设计？**

解析：三类是 Normal（必备功能，最先保证）、Expected（期待功能，应该做好）、Exciting（惊喜功能，有余力再做）。手机的核心 Normal 功能是"打电话"，若把资源全花在地图、导航、照片、音乐等上面而电话不好使，就是本末倒置——Normal 没保住，项目会被判"没法做"，必然失败。（依据：第二节 2.2）

**3. 谈判原则中说"It is not a competition"并且要"Focus on the other party's interest"，请结合双赢（win-win）说明其内在逻辑。**

解析：谈判不是辩论赛，目的不是"赢过对方"而是达成交易，所以它是妥协的艺术。要让对方接受条件，必须站在对方立场讲"这样做对你有什么好处"，而非只讲对自己好处——因为只有形成 win-win（双方都获益）局面，事情才可能达成；若只顾己方利益，对方无动力配合，谈判必崩。同时配合 Listen（多听摸清对方底线）、Map out a strategy（设计迂回策略）等原则。（依据：第三节 3.1、3.2）
