## 第 1 章：第9讲 需求分析与模型建立-1
> 对应分集：P09 | 原始标题：《第9讲 需求分析与模型建立-1》

### 一、分析模型的三大目标与定位

我们建立各种模型，归根结底要服务于三个目标，任何时候都不能忘：

1. **把 customer requirements 描述清楚。** 这一阶段的模型主要是给 customer（非专业人士）看的，不是给技术人员炫技的。
2. **为下一阶段的 software design model 打基础（establish a basis）。** 设计人员是在你的模型上进一步细化，完成整个系统的 design，所以模型要有足够的技术性，让内部人员觉得"我可以把它转化成一个软件系统了"。
3. **定义一组可以被验证的需求（define a set of requirements that can be validated）。** 也就是写清验收标准——什么情况下客户要给你钱。

从流程地位看，分析模型处在中间，是一座桥梁：

```
Customer 给出的极简 System Description
            │
            ▼
   ★ Analysis Model（分析模型）★
   给客户能看懂 + 给技术人员够清楚
            │
            ▼
   Design Model（设计模型，内部人员细化）
```

它重点回答的还是 **what to do**，不涉及技术细节——技术细节（用什么算法、什么数据结构）要到 design model 才展开。需求阶段的粒度与设计的粒度不同：需求照顾 customer 情绪，让他看懂"你要实现什么"；设计才是给自家人看的"怎么实现"。学生常犯的错误是：需求文档里的模型原封不动搬到设计报告里——那是没搞清楚"什么东西给谁看"。

### 二、建立分析模型的经验戒律（Rules of Thumb）

前辈们总结了几条做需求分析时必须守住的规矩：

1. **Focus on business domain, do not get bogged down in details.** 聚焦业务领域，不要陷进细节。技术人员本能地会想"这里怎么处理、有什么 exception、用哪种语言"——但在 analysis 阶段要刻意忽略这些。
2. **每个图都要 add to an overall understanding.** 你画的每一张图都必须是帮助大家更好理解的，而不是把人搞糊涂。如果写出来只会增加混乱，或者前一张图已经讲清了、没必要用另一个工具重复一遍，那就不要写。
3. **Delay consideration of infrastructure and non-functional models until design.** 非功能性、细节性的考虑先放到后面，这一阶段面向 customer，把"他要什么功能"搞清楚。
4. **Minimize coupling.** 切分系统时，尽量让块与块之间不要有太多关联（coupling 后面会专门讲）。
5. **Be certain that the analysis model provides value to all stakeholders.** 模型对所有干系人（尤其客户）都要有价值。
6. **Keep it as simple as possible.** 尽可能简单，不要华而不实、不要 fancy。

### 三、领域分析（Domain Analysis）：为复用而建

什么叫 domain analysis？以支付宝为例，它和银行系统密切相关；做完支付宝，你对银行内部的转账流程、规矩已经比较清楚。这些就是**领域知识（domain knowledge）**。把本项目涉及的领域知识保留下来，下次开发同领域的其他软件时就能大量复用。

Domain analysis 的主要目标就是**未来的 reuse（复用）**。具体做法：从各种渠道获取领域知识（读技术文件、试用现有软件、customer survey、请教专家），综合后做 domain analysis，抽取出哪些 class 以后可用、定出 reuse standards（重用标准），再配套 functional models、domain languages，总结出 domain 相关的 analysis patterns（分析模式）。这样公司以后做同领域项目效率更高、更有经验优势。

### 四、分析模型的两大流派与四大类

分析模型分两大类：**传统的 structured analysis（结构化分析）** 与 **时髦的 object-oriented analysis（面向对象分析，OOA）**。本版教材把二者融合在一起讲（老版本是分两章）。下节课要介绍分析模型的**四大类工具**，每一大类里有若干具体 diagram，这些都是最终要交的 Requirement Specification 里的内容。

回顾一下：上次讲完开会准备，提到建模型有四大类。要描述一个需求、让客户看懂也让技术人员看懂，需要写清哪几方面？至少包括：基于 use case 的模型、数据模型（data modeling）等。

### 五、数据建模（Data Modeling）

#### 5.1 在客户的抽象层次上建模

第一件要紧事是 data modeling（数据建模）。关键是 **create a model at the customer's level of abstraction**——数据模型要让客户看得懂，是在他的层面描述数据。

例如描述系统里有个"账户（account）"对象，账户包含姓名、密码、电话号码、通讯地址等。你只要告诉客户"账户里包含哪几项内容"，**不要写**"电话号码我用 int 还是 long long 还是字符串表示"——具体在程序里怎么实现，客户看不懂也没意义。需求阶段只说"有什么"，不说"怎么实现"；到了 design 阶段才真正涉及 how。

需求文档里出现设计阶段的模型（如具体算法、数据结构），是常见错误。

#### 5.2 数据建模的两项任务与 ER 图

描述数据时，除摘出有哪些 **data objects**，更重要的是搞清楚它们之间的 **relationship（关系）**。若学过数据库，就会知道古老的 **ER diagram（实体-联系图）**：E 是 Entity（实体），R 是 Relation（联系）。这就是 data modeling 要搞清楚的两件事。

#### 5.3 如何从需求文档抽取 Data Object

面对大型系统，需求可能是几千字、从十几个部门汇总来的厚报告。人肉逐句读不现实，得"偷懒"——写个 parser（解析器）先把所有**名词**抽出来（英文易抽，中文断词易错）。过滤掉动词、形容词，留下名词候选。

各类词性的去向：

| 词性 | 通常映射 |
|------|----------|
| 名词 | 可能是 object 本身，也可能是某 object 的 attribute |
| 形容词 | 多为 attributes，或与 performance / constraint（限定性要求）有关 |
| 动词 | 与系统要完成的 function（功能）有关 |

**Data Object 的判定标准：**

- 它的每个实例（instance）有**唯一确定的标识**（类似数据库的主键 keyword）；
- 在系统中**有意义**（无关的东西排除，如红绿灯）；
- 由**一系列 attributes（属性）**刻画。

**ATM 实例辨析。** 需求报告写："希望 ATM 分布在每几个街区，每隔多少红绿灯至少有一台 ATM。" 候选名词：ATM 机、街区、红绿灯。

- **ATM 机**：显然是要做的东西，是 data object。
- **红绿灯**：肯定是 object，但**不是你的 data object**——你的系统跟红绿灯没关系，那是部署（deployment）时才考虑的事。
- **街区**：不一定。若系统需要记录客户操作地点（在哪台机器上操作），机器的 location 需记录，则街区可能相关；但街区本身往往只是某个 object 的 **attribute**，而非独立 object。

所以抽出名词后要分类筛选：名词归一堆、形容词归一堆、动词归一堆，再判断谁是 object、谁是 attribute。

**Attributes 的微妙之处：** attributes 本身有时也是一个 object，同时又是另一个 object 的 attribute，这种情况会发生。书上举例：automobile（汽车）的 attributes 有出厂信息、model、body type、price、options code 等，给定后就能刻画一辆具体的车。

#### 5.4 Relationship 的要点

Relationship 也要从需求文档抽取，但要注意：**凡能通过算法计算、通过逻辑推导出来的，都不算 relation**。Relation 是指"推不出来也算不出来、只能明确告诉系统'它俩有关系'且要记住"的东西。

关系的两个维度：

- **Cardinality（基数）**：一对一（1:1）、一对多（1:N）还是多对多（M:N）。
- **Modality（模数）**：必须有的（mandatory）还是可有可无的（optional）。

传统用 ER 图描述数据模型；OO 里 UML 提供 class diagram 与 class hierarchy（结构层次图）。

### 六、面向对象（OO）基础回顾

#### 6.1 OO 的关键概念

一门语言被称为 Object-Oriented，至少要有这些机制。C 语言不是 OO，因为它缺了关键特点；C++ 和 Java 是。核心刻画 OO 的属性：

- **class / objects（类与对象）**
- 每个 object 有 **attributes（属性）** 与 **operations（操作）**
- **encapsulation（封装）**
- **inheritance（继承）**

#### 6.2 C 与 C++ 的本质区别（一个教学例子）

教授讲 C++ 时的经典例子：有 100 个学生，每人有学号、姓名、成绩，要全部打印出来。

**C 语言写法（面向结构）：**

```c
struct student {
    char name[20];
    int id;
    float score;
};
struct student S[100];   // 定义数组
// 读入所有信息后：
void print_students(struct student arr[], int n) {
    for (int i = 0; i < n; i++)
        printf("%s %d %f\n", arr[i].name, arr[i].id, arr[i].score);
}
```

数据归数据（struct 写在 .h），操作归操作（print 函数写在另一个 .h），二者可完全分开。

**C++ 写法（面向对象）：**

```cpp
class student {
private:
    char name[20];
    int id;
    float score;
public:
    void print() {   // print 是对象自己的方法，无 for 循环
        printf("%s %d %f\n", name, id, score);
    }
};
student S[100];
// 调用：
S[i].print();
```

最大区别：在 C 这类面向结构的语言里，**数据归数据、操作归操作，两件事分开**；在 C++ 的 class 里，**数据与操作绑在一起**。print 不再是独立的外部函数，而是对象自己的方法，调用 `student[i].print()` 即可。

#### 6.3 OOA 的任务流程

用 OO 观点做需求分析（OOA），任务和普通需求分析差不多，也是迭代过程：

```
basic requirements（沟通获得基本需求描述）
   → 抽取 class（刻画数据）
   → 定义 class hierarchy（类层次）与 relationship
   → 建立 behavior model（行为模型，刻画动态属性）
   → 反复迭代，直到一切清楚
```

behavior model 不仅 OO 要做，普通（结构化）分析也要做，后面再讲。

#### 6.4 对象与消息：邮局实例

以"给老外婆送花"为例。本人在杭州上课，外婆在北京过九十大寿，于是调用一个 object——**post office（邮局）**：

- 我作为用户，给邮局 **send a message**："我要送花到某地某时"。
- 邮局用它的某种 **method（send by method）** 把花按时按量送达。
- post office 相当于程序里一个 class，交给某个开发小组维护（"你们来管邮局"）；我作为调用者，只关心它提供的接口，不关心内部怎么实现——是傻傻地在杭州买花坐飞机送，还是在北京当地买花送，找美女还是帅哥送，那是维护 class 的团队关心的事。

**邮局的内部与外部：**

- **private attributes（私有属性）**：location（建在哪）、employees（多少员工）、open hours（开关门时间）——外部不能动。
- **public interface（对外接口/服务）**：send（送信送花送电报）、sell（卖信封邮票）等。

作为用户，我最想"把邮局搬家门口、多加邮递员、24 小时开门"——这是企图直接改邮局内部的 attributes（location、employee、open hours）。但邮局说："本邮局不提供此类服务"，即没有对外接口让你动这些内部属性，你无权碰。

我能做的，只是调用 `PostOffice.send`，按约定填一张 **request form**（送到哪、什么时间、买什么花），再付 **payment**。邮局读入发现输入合规，就完成功能。这种"外部只能通过接口发请求来改内部属性、无法直接触碰内部"的特性，就叫 **encapsulation（封装）**。

#### 6.5 封装的形式化图示：Taylor's Notation

有人发明了 Taylor 记号描述一个 class / data object（因太难画，实际少用，但寓意极好）：

```
        ┌─────────────────────────┐
        │       Class Name         │
        │  ┌───────────────────┐  │
        │  │  (attr) (attr)    │  │  ← attributes 写在圆圈里
        │  └───────────────────┘  │
        │  [method] [method]      │  ← methods 写在外圈
        │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │  ← 砖墙，无缝无门
        └─────────────────────────┘
```

外圈用**砖墙**表示，墙没有缝、没有门，里面的 attributes 被保护起来，外面的人进不去。作为调用者，只有通过某一面墙上的"手"（接口）发请求，才能由它去改相应 attributes；若某 attribute 任何一面墙都没提供修改功能，你就根本碰不到它。这就是封装的概念图。现实中大家还是用最常见的方式——UML 类图：上面 class name、下面列 attributes 与 operations。

### 随堂自测

**1. 分析模型（Analysis Model）在开发流程中处于什么位置？它回答"what"还是"how"？为什么需求阶段的模型不能直接原样搬到设计报告里？**

解析：分析模型是 customer 极简系统描述与内部 design model 之间的桥梁，重点回答 **what to do（要做什么）**，不涉及技术细节（how 留到设计阶段）。需求模型主要给客户看懂（照顾客户抽象层次、不写实现），设计模型给内部人员看（讲怎么实现），二者目标与粒度不同，所以原样照搬是错误的。（依据：第一节、第二节、第五节 5.1）

**2. 从一份大型需求文档抽取 Data Object 时，为什么"红绿灯"可能不是 data object，而"街区"可能只是某 object 的 attribute？判定 data object 的标准是什么？**

解析：红绿灯虽是名词、看似 object，但系统本身与红绿灯无业务逻辑关联（那是部署时才考虑），故不是 data object；街区是否相关要看需求——若系统需记录机器 location，则街区可能作为某 object 的 attribute 而非独立 object。判定 data object 的标准：① 实例有唯一标识（类似主键）；② 在系统中有意义；③ 由一系列 attributes 刻画。（依据：第五节 5.3）

**3. 用邮局实例说明"封装（encapsulation）"的含义，并对比 C 语言 struct 与 C++ class 在数据与操作关系上的根本差异。**

解析：邮局把 location、employees、open hours 等设为 private attributes，外部用户无法直接修改，只能通过 `PostOffice.send` 这类 public 接口、填 request form 来间接驱动内部行为——这就是封装：内部被"砖墙"保护，外部只能通过接口交互。对比上，C 的 struct 把数据（struct）与操作（如 print_students 函数）分开定义、可分离；C++ 的 class 把数据与操作（如 student 的 print 方法）**绑在一起**，调用 `S[i].print()`。（依据：第六节 6.2、6.4、6.5）

## 第 2 章：第10讲 需求分析与模型建立-2
> 对应分集：P10 | 原始标题：《第10讲 需求分析与模型建立-2》

### 一、封装的本质是信息隐藏

封装（Encapsulation）把数据和操作这些数据的函数绑在同一个 class 里，与 C 的根本区别就在这里。这样做最大的好处是实现了 **Information Hiding（信息隐藏）**：只要对外的接口（Interface）没变，你今天高兴用算法 A 实现、明天换成更好的算法 B，把里头的东西改掉，外部完全不受影响。即使内部出了错，影响范围也有限——因为大家都通过 message 互相沟通，模块化（Modularization）更好，模块间的耦合（coupling）关系更简单。

另一个直接好处是 **reuse（复用）更方便**。用 C 时，有人习惯把所有 data structures 放一个 `.h`、所有操作放另一个 `.h`，复用时要记住 copy 哪些、include 哪些，分散多处、容易漏。class 把数据结构与相关内容绑在一起，只要重用这个 class 即可，机制非常顺手。

### 二、继承：一种安全的复用模式

#### 2.1 单继承与 superclass

Inheritance（继承）是 OO 的重要特性。用一个 superclass 提取所有 subclass 的公共属性。例如 **Furniture（家具）** 作为父类，下面有 table、chair、desk，以及一种老浙大特有的 **chable**——既是椅子又有扶手、扶手翻过来就是小桌板，兼具 chair 与 table 的功能。它们都属于"家具"，公共属性（出厂、价格、颜色、材质：木/塑料/铁）放到父类 Furniture 里；子类继承下来（相当于 copy 一份），再叠加自己的属性，成为新 class。

继承被形容为**一种非常安全的重用模式**：想重用某个 class 时，不需要把人家的代码改掉，只需继承一下，在自己的 subclass 里改想改的、加想加的，且**不影响原始 superclass**——别人还能继续用父类。

#### 2.2 多重继承（Multiple Inheritance）及其危险

一个子类可以从多个父类继承（C++ 支持 multiple inheritance）。好处是能结合多家的东西。但它可能引发危险。

**案例：GraphicalDeck（图形化纸牌游戏）。** 要做一个有图形界面的纸牌游戏，可复用两类现成 class：

- `CardDeck`：包含纸牌游戏规则——谁比谁大、怎么抽牌怎么出牌。
- `GraphicalObject`：操纵界面上图形物体的功能——画出来、移动、三维旋转缩放等。

让 `GraphicalDeck` 同时继承这两个父类，看似完美，却撞上一个坑：两个 class 里都有一个同名方法 `draw`，但英文 "draw" 是多义词——在 `CardDeck` 里是"抓一张牌（take a card from a deck）"，在 `GraphicalObject` 里是"在屏幕上画出来"。调用 `GraphicalDeck` 实例的 `.draw` 时，二者打架、产生冲突。解决办法之一是用 **overriding（方法重写）**，但聪明与否取决于具体手法。核心提醒是：**Multiple inheritance 可能有这种命名冲突的危险**。

更严重的是，一旦出现这种问题，**inheritance 的 transitive（可传递性）会被破坏**。如果 A 派生 B、B 派生 C，那么 C 同时继承 A 的全部属性——这是可传递的。但多重继承下，这种可传递性很可能失效。

### 三、基于用例的建模（Use Case）

Use case 描述一个 actor（参与者）使用系统的剧本（过程）。它在两个开发阶段极有价值：

1. **需求阶段**：跟用户核对"将来你就是这么用系统的——先做、后做、遇到这事做选择"，作为确认工具。
2. **测试阶段**：use case 是极可爱的资产。内部先按剧本把所有场景演一遍，没问题了才去见人。

**构建 use case 的三步（需求阶段不必写太细）：**

1. 列出所有 **actor**（哪些人、哪些角色要用系统）。
2. 对每个 actor，列出他要做的几件事。
3. 根据 functions 列出 **primary scenarios（初级/最简单剧本）**，画一张粗的 use case 图；再考虑"使用中有无特殊情况、分支岔路"，细化出 **secondary scenarios**。

#### 3.1 案例：SafeHome 家居保安系统

书上的 SafeHome 例子很粗：家装好系统后，homeowner（主人）在面板上至少能完成三件事：

1. **初始化（Configuration）**：设置参数。
2. **Set Alarm**：出门时按按钮开启警报。
3. **通过 Internet 看 camera surveillance（监控镜头）**：在外网上查看房间是否异常。

前两者直接在保安系统面板上按键完成；第三者要走 Internet，启动硬件 cameras，调用镜头。每项功能再向下细化（如 Configuration 要设哪些参数、先点哪再点哪），形成一串更细的 use case。

#### 3.2 Activity Diagram → Swimlane Diagram（泳道图）

前面讲过 **Activity Diagram（活动图）**：它不是脚本式，而在一张图里把所有分叉（走这步有两种可能、选 A 是一串行为、选 B 是另一串）都画出来，不如 use case 好理解。在活动图基础上可细化成 **Swimlane Diagram（泳道图）**——游泳池分道的概念，把每个 action 归到负责它的角色泳道里。SafeHome 的泳道分三道：

- **Homeowner**：负责一堆积动作。
- **Camera**：负责镜头动作。
- **Interface（控制面板）**：负责两个动作。

泳道图一目了然：系统由哪几块构成、整体由哪串动作完成、哪个角色负责哪些动作。它与 use case 都是辅助用户沟通的图，帮助理解"我怎么一步步把系统走完"。

### 四、面向流的建模：数据流图（DFD）

**Flow-oriented modeling** 把系统看成由"数据"和"功能"构成的整体。最古老的就是 **Data Flow Diagram（数据流图，DFD）**。它的根本理念是把计算机系统看作一个 **IPO 系统（Input - Process - Output）**：系统读一堆输入进来，在里面处理一下，变成输出出去。DFD 要描述的就是：**数据到底怎么从输入变成输出**——数据从输入处流进，经过功能变成另一副模样，再经下一个功能继续变，经一系列功能后转成最终输出。

**DFD 的符号约定：**

| 符号 | 含义 |
|------|------|
| 方块（□） | External Entity（外部实体）：输入操作、输出操作 |
| 圆饼（○） | Process（功能/加工），圆饼内写功能 |
| 有向边 | 数据流，边上标注流动的数据是什么 |
| 两条平行线 | 数据库，中间写数据库名称 |

整个图是一个**有向图**。

#### 4.1 实例：公共图书馆信息系统

需求（简化版，只有两个功能）：

- **Get a book**：用户给 title、author、借书人姓名（Name of user），系统找到书给人，并更新"已借书"数据库。
- **Search by topics**：按主题查书，列出所有相关书的 titles。

画法要点（黑盒子原则）：

1. **先画功能进程（圆饼）**：`Get a book`、`Search by topics` 两个黑盒子，需求阶段不要细化内部。
2. **确定输入数据流**：User 给一个 Book request，流线上带 `title`、`author`、`Name of user` 三个数据，传给 `Get a book`。
3. **处理与输出**：`Get a book` 需要查 author、title 对应的书架位置（至少涉及"书架"数据库与"已借书清单"数据库），最终产生一本 book 交给前台 Book reception，并把借走书的 title 与 username 写入 list of books borrowed 数据库。`Search by topics` 则输入一个 topic，从 title/topic 数据库查，屏幕显示 list of titles referring to the topic，无需知道是谁在查。

#### 4.2 初学者两大典型错误

1. **数据流断流**：某个功能只有输入、没有输出。数据流到这就停住、跟后面无关联，那这功能毫无存在必要——说明你画错了。
2. **莫名其妙自启动（灵异事件）**：功能是一段程序，必须有东西启动它才能产生输出。若所有指向它的箭头都从数据库来、没有真正的触发源，那它"自己跳起来读数据库"——不可能，因为**数据库是被动的，等着被读**，不会主动发数据去启动功能。正确情况是：有 book request 这类外部输入真正调用、启动功能，功能再去读数据库、产生输出。

只要不犯断流与灵异这两类系统级错误，能自圆其说即可得分（无标准答案）。

#### 4.3 细化（Refinement）与分层（Level 0/1/2）

若 `get a book` 产生两个不同的输出（既送书到前台、又写数据库），说明它干了两件事，应拆成两个圆饼：先 `find book position`（找到书在哪），再 `get a book`（从书架取书给前台），同时并行去写借书数据库。这是 refinement（逐步细化）。

画图最忌在一页 A4 上"唰"地甩出巨复杂的 DFD——一堆小圆饼、细小字、数据乱流，谁看都晕。正确做法是**分层次**：

- **Level 0**：最简。读输入 → 一个大黑盒子 process → 产生输出去哪。
- **Level 1**：把中间 process 细化，露出几个子功能及数据如何在子功能间流动。
- **Level 2**：若某子功能还不够细，再拆。

就像拿天文望远镜→肉眼→放大镜→显微镜，细节要**逐渐展示**。记住：你写的需求文档是给别人看的（尤其忙得要命的 TA），要让人在很短时间内看懂。分级展示是一种关键技巧。

### 五、控制流与状态图（State Diagram）

除了数据怎么被功能改变（Data flow），系统还有另一维度：**Control flow（控制流）**，也叫 **State Diagram（状态图）**。它从"系统在执行过程中有哪几个不同状态、发生何事、如何处理，从而从一个状态转移到另一个状态"来理解系统。对应代码里就是中断（interrupt）、switch-case、if-else 等所有有转折、有多种可能性的**控制节点**。

以 SafeHome 为例，系统有四个状态，转换由事件驱动：

```
[switch on] → RESETTING（自检 run diagnostics, 面板显示 starting system）
    │  启动失败 → 面板显示 contact vendor（联系经销商）→ 终止
    │  启动成功 → SYSTEM OK
    ▼
  IDLE（待机, 面板 ready, 灯常亮, status=inactive）
    │  reset键 → 回到 RESETTING
    │  power off → 关机
    │  activate键（出门） →
    ▼
  MONITORING（监控中, 面板 armed, 灯常亮, status=monitoring）
    │  人回来 + deactivate password → 回到 IDLE
    │  进贼 → sensor triggered → START TIMER →
    ▼
  MONITOR AND ALARM（报警, 面板 alarm, 灯急闪）
    │  sound alarm 叫；notify alarm responders（自动拨警局/住户电话）
    │  贼消失 + timer 超时 / deactivate → 回到 IDLE（或 restart timer 持续叫）
```

这张图让用户一目了然：系统有四种状态，状态之间如何转换。注意 `run diagnostics`、`monitor and control system` 等内部怎么实现，用户不需要管——这是给用户看的。

### 六、类建模（Class-based Modeling）与 CRC 卡

OOA 抽取 class 的方法：写个 parser 抽名词，区分哪些是 attributes、哪些词定义了某 object 的属性；抽动词，动词是 manipulate（操纵）哪些 attributes 的动作，应抽成 operation。麻烦在于：某些功能改变了好几个 class 的 attributes，该跟谁绑？一般应与被操纵的 attributes 绑在一起；具体技巧结合 DFD 分析"哪些功能改变哪些 attributes"。

#### 6.1 CRC Cards

早期真的用卡片（cards）做 **CRC**：

- **C** = Class（类）
- **R** = Responsibility（责任，即 class 的 attributes + public operations，等于 class 描述）
- **C** = Collaborators（协作者）

前两项（Class Responsibility）并非新东西。关键是红色的 **Collaborator 栏**：写下你这项还调用了谁、或被谁调用。它最重要的用途是**改动影响分析（impact analysis）**。例如你把"电话号码"从整数改成字符串——若另一 class 把它当 integer hash key，你一改它就挂。通过 Collaborator 把相关卡片揪出来，看影响了哪部分；若受影响卡片越少，说明设计越好；一改就牵出一大坨，就是差设计（牵一发而动全身）。

#### 6.2 UML 类图符号速记

- 黑色实心菱形 = **Composition（组成关系）**，如 player 由头、身、四肢组成。
- 连线上的标注表示基数与模数：一对一、一对多、mandatory（必须有）或 optional（可有可无）。
- **Package（包）**：复杂系统把 class 归类装进"信封"。如足球游戏：环境相关类一包、规则类一包、人物类一包。
- 可见性符号：`+` public（所有人可用）、`-` 内部私有（藏起来）、`#` 仅限某几个 package 可用。

### 七、行为建模（Behavior Model）

Behavior model 描述系统使用过程中的动态。前面讲的 state diagram 就是其中一部分。要点：

- 既要画 **state of the system**，也要分析每个有必要的 class 自己的 **state transition diagram**（一直静态的 class 不必画）。
- 状态分两类：**passive（被动）**——仅 attribute 值改变；**active（主动）**——整个 process 在改变。
- **Sequence Diagram（时序图）** 与 state transition diagram 的关系，类似 activity diagram 与 swimlane 的关系：把每个 state 按时间轴从上到下排列，标出状态转换过程中牵涉哪些系统元素（如 Control panel 由 home owner 启动进入某状态、与 system 交互转换、与 sensor 交互转换），把所有牵连元素放进一张图。

### 八、写需求文档的六条纪律

最后落到"把模型写成文档"。一句话点题：**"Everyone knew exactly what had to be done until someone wrote it down."** 不落到纸面就不算数。写文档注意：

1. **分层展示**：不要一次性抖出所有细节，务必逐级展开。
2. **统一名词**：上百页文档由多人合作，不能同一东西在这叫"名字"、那叫"另一个名"。
3. **缩写首次给全称**：任何缩写，无论多常见，第一次出现必须给出全称并说明简称，之后才可用简称——写论文、写正式文件的通用规矩。
4. **要有目录（table of contents）**，友好一点再加 index（索引）。
5. **文风清楚、简单、不啰嗦**。
6. **站在第三者立场审视**：你清楚自己想做什么，别人不一定。问自己：TA 哥能在十分钟内读懂这块吗？

另外提醒：项目 due date 是 24 号，留了三个星期是有道理的——它真需要三周，别指望最后一晚或三天赶出来；以往有 TA 要求"需求文档写不到 100 页好意思交？"。

### 随堂自测

**1. 封装（Encapsulation）如何实现信息隐藏？为什么它让"改内部实现"变得安全，并便于复用？**

解析：封装把数据和相关操作绑进 class，只暴露对外接口（interface）。只要接口不变，内部算法/实现怎么改都不影响外部（Information Hiding），因此改内部安全；同时因数据+操作绑在一起，复用时只需重用整个 class，不必像 C 那样分散记住多个 `.h` 文件，故复用方便。模块化更好、耦合更简单。（依据：第一节）

**2. 画 DFD 时，"断流"和"灵异事件"两种典型错误分别指什么？为什么"数据库主动发数据启动功能"不可能？**

解析：断流=某功能只有输入无输出，数据到此停住、功能无意义；灵异事件=某功能没有真正的外部触发（所有入边都来自数据库）却自行产生输出。数据库是被动的、等着被读，不会主动发数据去启动功能；必须由 book request 这类外部输入真正调用、启动功能，功能才去读库、产输出。（依据：第四节 4.2）

**3. 多重继承（Multiple Inheritance）可能带来哪两类问题？用 GraphicalDeck 的 draw 冲突说明。**

解析：① 命名冲突——父类 `CardDeck`（draw=抓牌）与 `GraphicalObject`（draw=画出来）都有 `draw()`，派生类调用时语义打架，可用 overriding 等化解；② 破坏继承的 transitive（可传递性）——单继承链 A→B→C 时 C 继承 A 全部属性，多重继承下该传递性可能失效。（依据：第二节 2.2）
