## 第 1 章：第25讲 Web应用软件测试-1
> 对应分集：P25 | 原始标题：《第25讲 Web应用软件测试-1》

回到 testing 主题。普通软件（"普通青年"）的测试已讲过，现在看 Web 应用（"文艺青年"）的测试有何不同。差异的根源在于 Web 应用那些需要特别强调的特性——测试最难、最头疼的地方，恰恰就是这些特性所在。本讲先列出 Web 应用的质量维度，指出最棘手的配置与环境测试，再把测试策略与前面的设计模型一一对应，最后落到内容测试（含最复杂的数据库分层测试）与界面测试的具体做法。

### 一、Web 应用的质量维度（Dimensions of Quality）

评判一个"好的 Web 应用"，要考察哪些质量维度？除了传统软件都看重的内容、功能之外，Web 应用还有一组自己的维度。综合课上归纳，主要有：

| 维度 | 含义与 Web 特殊性 |
|------|------|
| **Content（内容）** | 内容要好 |
| **Function（功能）** | 功能齐全、稳定 |
| **Structure（结构/架构）** | 整体组织架构合理，可扩展性（extensibility）强 |
| **Usability（可用性）** | 与普通软件略有不同：普通软件的 usability 常与 availability 挂钩（一年宕机不超过多少分钟）；Web 应用的 usability 强调"每个 actor 都能学会并应用界面所需的所有导航语法与语义"——因用户分散、无法统一培训，界面必须让用户自己能轻松上手、按想象走通 |
| **Navigability（可导航性）** | 很重要，用户不能迷路 |
| **Performance（效率/性能）** | 很重要，打不开就流失用户 |
| **Compatibility（兼容性）** | Web 特有：客户端操作系统、浏览器、屏幕分辨率千奇百怪，都要较好兼容 |
| **Interoperability（可交互性）** | 与其他软件、应用软件、数据库的可交互能力 |
| **Security（安全）** | 挂到网上怕丢钱、被攻击，是重中之重 |

这九条基本覆盖了 Web 应用的质量考察面。每一条相对普通软件都有特别之处，测试时都要重新考量。

### 二、最头痛的测试：配置与环境

若问 Web 应用测试哪方面特别难、以至于要单独拎出一章，经验告诉我们：测试维护团队最头痛的其实是 **configuration（配置）** 这一块。

典型现象是：你在客户端发现的错误现象，往往**不是错误本身**。很可能是因为用户系统的 configuration（系统配置）引起的。用户说"在我的机器上做了某操作就出错了"，但你在自己机器上**几乎无法重现（almost impossible to reproduce the error outside the environment）**——错误只在他那台机器上是那样的。

根因在于 Web 应用是三层结构：**客户端（client）+ 网络（network）+ 服务端（server）**。Debug 时很难定位 bug 到底发生在哪一层：

- **静态配置（static configuration）**错误：由固定环境配置差异引起；
- **动态（dynamic）**错误：瞬时流量特别大时也会产生诡异错误。

这些都和**运行环境（environment）**强相关。环境在 Web 测试里扮演极重要的角色，配置测试因此是最费劲、最难做的一块。

### 三、测试策略：与设计模型对应

测试不是凭空设计用例，而是回顾设计阶段那座"设计模型的三角形/金字塔"——里面有 content model、interface model、design model、component design 等。测试总体策略大致是：

1. **Content Model**：检查内容方面的问题；
2. **Interface Model**：检查所有 use case 能否依据界面模型走通；
3. **Design Model**：主要检查 Navigation（导航）问题；
4. **User Interface**：整体测试；
5. **Functional Components（功能模块）**：单元测试（Unit Testing）；
6. 整个系统架构的 Navigation 也要仔细测过；
7. Web 特有步骤：**Configuration（配置）** 与 **Compatibility（兼容性）** 需专门测；
8. **Security、Performance**；
9. 最后一步：不能技术员测完直接挂网上。通常要先做**内部公测**——在可控环境里挑选一部分 End Users 做整体黑盒测试。例子：ZOJ、各类 Online Judge 正式上线前，会让集训队那帮人先去"虐一下"，在可控范围内先暴露问题。

#### 3.1 自顶向下的测试流程

测试流程与 Design Models 自顶向下对应（最上层最接近 User，最下层最接近底层技术；设计分过 Interface、Aesthetic、Content、Navigation、Architecture、Component 等块）：

```
设计模型(顶→底)              对应测试
─────────────────────────────────────────
Content Model          →  Content Testing（内容测试）
Interface Design       →  Interface Testing（界面测试）
Aesthetic Design       ↗    （与界面测试一体）
Navigation Design      →  Navigation Testing（导航测试）
(整体架构概念)          ↗
Component Design       →  Component Testing（构件测试）
                            ↓ 进入底层技术特性
Configuration / Performance / Security Testing
```

- **Content Testing** 取自 Content Model 做测试计划；
- **Interface Testing** 需要 Interface Design **和** Aesthetic Design——两者是一体的，测界面不能脱离美工；
- **Navigation Testing** 需要 Navigation Design，**还需要整体架构概念**，才能做好；
- **Component Testing** 取自 Component Design Model，表层东西测完后进入底层、与技术直接相关的 Configuration、Performance、Security 测试。

### 四、内容测试（Content Testing）

内容测试主要检查内容，至少两方面：

1. **语法方面（Grammar）**：Typos（拼写错误/错别字）、句子不通顺等；
2. **语义方面（Semantics）**：语法拼写都没问题，但提供的信息是否准确正确。例如给学院做网站，挂的是十年前的学院介绍，就不对。要检查展现出来的 content 意思正确。

此外，还要测内容的**组织与结构**：哪些内容跟哪些内容放在一起、哪些先出现哪些后出现，这种组织、顺序、结构是否正确。

#### 4.1 最复杂的部分：数据库测试（Database Testing）

绝大多数 Web 应用是以数据库为中心的架构，数据库操作必须测，且比普通软件复杂——因为与数据库的交互**层数多**。

以"用户在网页上填查询词、点查询按钮、返回结果"为例，从输入到返回经过多少环节？

1. 读到网页 **HTML 代码**；
2. 从代码里**解析出用户要查询的字段**（哪段是用户输入）；
3. 判断这是对数据库的什么操作（查询/写入/……），**转换成相应的数据库语言（如 SQL 指令）**——做翻译；
4. 传给数据库，数据库操作并返回**原始数据（raw data）**；
5. 拿到 raw data 不能直接丢回给用户，要**转换成用户可理解、可展示的格式**显示在屏幕上。

还没完：客户端给的原始请求一般不是 MySQL/SQL 语句，要做 translation；数据库可能不在你的 server 上，**server 与 server 之间还有 communication 问题**；raw data 返回到 Web app server 后还要 **proper format for display** 转换。

因此要对 database interaction 做**分层（layers of interaction）**处理，对每一层设计相应的测试方法。教材建议分五层：

```
[用户界面层]  第1层: 获取 HTML scripts
     |
[Web App Server 层] 第1层: 从 scripts 中抽取 user data
     |
[Web App Server 层] 第2层: 转换成 SQL/格式, 与数据库交互
     |
[数据库] 执行操作, 返回 raw data
     |
[回传] 获得 raw data 向上传
     |
[用户界面层] 转换成可展示 format, display
```

每层都要有 testing plan。这就是内容测试里最麻烦的部分。

### 五、界面测试（Interface Testing）

内容测完测界面。界面测试重点：

#### 5.1 测每一种 interface mechanism（界面机制）

**interface mechanism** 指界面上的各种机制/控件：链接（links）、按钮（button）、表格（form）、弹出框（pop-up windows）、cookie 等。每一种机制都要针对性设计不同的测试。这些机制存在的目的是实现导航、功能与内容展示，要测它们在语义上是否正确实现了该实现的功能与目标（objectives）。

#### 5.2 测试策略三步

1. **整体界面特征（Interface Features）初测**：对照界面设计原则，看违背了哪些；再从美工角度检视——table 的 table size、行间距、边角留空距离是否好看、整体是否舒服。这是第一眼测试。
2. **单元测试（Unit Testing）**：对每一种 mechanism 做局部测试。例如交表格，每一种表格都要测。
3. **整合测试（Integration Testing）**：单元测试完后做整合。这里对应**把每一个 use case 或对应的 NSU 整体串一遍 interface mechanism**——NSU 比单纯 use case 更管用。
4. **验证测试（Validation Testing）**：把若干 use cases / NSUs / 模型组合起来，整体走一遍界面，检查整个 interface 的语义（意义）是否实现正确，类似最后的黑盒功能验证测试。

#### 5.3 复习：NSU 是什么

课上特意重申 NSU = **Navigation Semantic Units**：

- **N** = Navigation（导航）
- **S** = Semantic（语义）
- **U** = Unit（单元）

它是讲 navigation design 时做的导航模型，对着 use case 来——每个 use case 对应一套 NSU。图形上像 use case：一边有个小人儿（actor），描述 actor 按一个 use case 完成一件事的过程中，经历哪些页面、点哪个链接进什么页面、再点哪个链接进什么页面、最后在页面做什么操作，由网页串起来。整合测试时按每个 NSU/use case 把 interface mechanism 整体串一遍，相当于普通测试里的 integration test；最后整体走一遍则相当于 validation testing。

#### 5.4 Web 特有的兼容性测试

界面测试还要对各种不同环境做 **compatibility 测试**（各种客户端操作系统、浏览器、分辨率等），这正是 Web 应用区别于普通软件的关键之一。

### 六、小结

Web 测试之难，源于质量维度在普通软件之外多了 usability（用户自学导航）、navigability、compatibility、interoperability、security 等维度；而最棘手的配置/环境测试，因 client-network-server 三层结构导致错误现象多源于用户环境、难以在外部重现，debug 难定位层。测试策略与设计模型严格对应、自顶向下：Content Model→内容测试、Interface+Aesthetic→界面测试、Navigation+架构→导航测试、Component→构件测试，再下沉到配置/性能/安全，最后以可控环境内的用户内部公测收口。内容测试含语法、语义、组织结构，最复杂的是数据库分层交互测试（HTML抽取→SQL转换→DB操作→原数据→展示格式，五层）；界面测试逐机制（链接/按钮/表格/弹窗/cookie）做单元、整合（按 NSU 串）、验证三步，并补兼容性测试。下一讲继续展开导航、构件、配置等后续测试。

### 随堂自测

**1. 为什么说 Web 应用的配置测试（configuration testing）最难？它和系统的什么结构有关？**

解析：客户端出现的错误现象往往不是错误本身，而由用户系统的配置引起，且几乎无法在环境外重现（almost impossible to reproduce outside the environment），错误只在他机器上那样。根因是 Web 应用有 client + network + server 三层，debug 难定位 bug 在哪一层；静态配置错误与动态（流量峰值）错误都和 environment 强相关。

答案：因 Web 是客户端-网络-服务端三层结构，错误常源于用户本地配置且无法在别处重现，难以定位故障层，故配置/环境测试最棘手。

**2. Web 应用的内容测试中，数据库测试为何比普通软件复杂？请描述其分层交互流程。**

解析：绝大多数 Web 应用以数据库为中心，但与 DB 交互层数多：客户端请求不是 SQL，要经 HTML 解析抽取用户数据→翻译成 SQL→DB 操作返回 raw data→再转换成可展示格式；DB 还可能在另一 server，涉及 server 间通信。故要对 database interaction 做 layers of interaction 分层（约五层），每层单独设计测试。

答案：因请求需经"HTML抽取→SQL转换→DB操作→原数据回传→展示格式转换"多层且跨 server 通信，须按五层交互逐层测试，比普通软件单层直接访问 DB 复杂得多。

**3. 界面测试的"整合测试"为什么强调用 NSU 而不是只用 use case？NSU 三个字母分别代表什么？**

解析：整合测试要把 interface mechanism 整体串一遍。NSU（Navigation Semantic Units，导航语义单元）比 use case 更管用，因为它直接描述 actor 按某 use case 完成事情时经历的页面跳转链（点哪个链接进哪页、再点哪链接），正是导航与界面机制的串联图。N=Navigation，S=Semantic，U=Unit。

答案：NSU 描述"按用例走完所需页面跳转链"，比 use case 更贴合界面机制串联，故整合测试以 NSU 为线索；NSU 即 Navigation（导航）-Semantic（语义）-Unit（单元）。

## 第 2 章：第26讲 Web应用软件测试-2
> 对应分集：P26 | 原始标题：《第26讲 Web应用软件测试-2》

Web 应用的测试与传统软件测试在底层方法上相通，但因运行环境开放、用户不可控、流量不可预知，其测试维度有明显扩展。本讲在内容测试、界面测试之后，继续展开五个关键维度：可用性测试（usability test）、组件级测试、导航测试、配置测试、安全测试，最后以最棘手且最易被忽视的性能测试收尾，并引出以在线支付系统为对象的并发能力证明问题。

### 一、可用性测试：让真实用户来验收"好不好用"

可用性（usability）在 Web 语境下的含义与普通软件略有不同。普通软件的目标用户相对确定、可控，而 Web 应用的用户是一群"你不认识、也控制不了"的人，可用性测试的核心问题就是：这批不可控的用户，能不能自己学会并使用你的界面？

因此可用性测试的执行存在一个本质分野：测试由 Web 工程团队**设计**，但由**终端用户（end users）执行**。团队不能自己人测自己人，必须招募有代表性的用户群来真实操作。其执行步骤可归纳为：

1. **界定目标（identify goals of each）**。usability 只是一个统称，它实际包含一组不同的"ability"。测试前要先选定本次到底测哪些方面。常见目标包括：
   - **可交互性（interactivity）**：用户能否顺畅地完成交互；
   - **布局（layout）**：信息展示是否易于理解；
   - **可读性（readability）**：字体、字号、颜色搭配是否清晰，例如文字颜色与背景颜色几乎混淆、屏幕稍暗就看不清，都是可读性缺陷；
   - **美工（aesthetics）**：整体观感是否舒适；
   - **展示特性（display characteristics）**：呈现时的显示特性；
   - **时间敏感性（time sensitivity）**：是否存在对响应速度特别敏感的部分；
   - **个性化（personalization）**：是否针对不同类型用户提供了定制能力；
   - **无障碍（accessibility）**：是否顾及残障或能力受限人群如何使用软件。

   具体选择哪些目标，取决于你开发的产品本身是什么、你最看重哪些体验。

2. **为每一项目标设计测试用例与可量化评估方法**。这一步是整个可用性测试中最难、也最见功力的地方。难点在于：你凭什么说某个特性"好"还是"不好"？不能"用了一下，感觉不咋地，打分 60 分"——那 60 分从何而来？凭什么不是 61 分？每一个 usability 维度都必须有可操作的评判指标。

   以"可交互性"为例。某个人文社科人口学研究的系统中，曾设计过一套鼠标单点手势交互（为将来触摸屏做准备）：一个手指拖拽移动对象、划一下新建、打叉删除等。手势的实现本身只是毕业论文章节里的"设计与编码"，但论文最后一章必须回答：为什么手势比传统"点菜单—找文件—下拉框—选新建"更好用？这就需要一个客观的、有说服力的证明方案。一种可行设计是：

   - 找若干名被试同学；
   - 先讲解一组任务及其含义，让其用传统鼠标点击方式完成，掐表记录耗时；
   - 再教其手势操作，让其用手势完成相同任务，掐表记录耗时；
   - 单次不够，还需要观察"学习曲线"：传统方式重复做多少次后耗时趋于稳定、手势方式重复做多少次后趋于稳定，对比上手速度；
   - 辅以主观问卷，让其描述哪些方面好用、哪些方面不好用。

   客观计时 + 主观问卷，这才是对"可交互性好坏"有依据的判断。其余每一项 usability 特性都应力求设计这样一种评审机制，最后才能"很有根据"地说清楚系统的可用性究竟如何。

3. **选择并观察用户群**。招募代表性用户来完成上述测试，团队人员需在旁观察、给予必要帮助与指导，并记录其接受程度。

### 二、组件级测试与导航测试

#### 组件级测试（component level testing）

组件级测试与普通软件测试差异不大，主要以功能为基准。黑盒测试、白盒测试等经典方法都适用。由于 Web 应用通常以数据库为中心，数据库测试一般与功能测试合并进行，共同验证功能点。

#### 导航测试（navigation testing）

导航测试主要测两个方面：**语法**与**语义**的正确性。

**语法层面**需要覆盖以下几类对象，各自有其待测要点：

- 链接（links）
- 重定向（redirects）
- 书签（bookmark）
- 框架与框架集（frame / frame sets）
- 站点地图（site map，若有）
- 站内搜索引擎（internal search engine，若有）

设计导航测试用例时，应确保每一个用例都能覆盖并正确回答教材第 20.6.2 节所列的一系列测试问题（testing questions），以此保证语法与语义两条线都得到充分验证。

### 三、配置测试：最头痛的环境适配

配置测试（configuration testing）让测试人员头疼，根源在于环境复杂、查错改错困难。它分两端进行。

#### 服务端配置（server-side）

部署 Web 应用时要关注服务端哪些配置？典型检查项包括：

| 检查维度 | 关注点 |
| --- | --- |
| 操作系统版本 | 不同版本带来的兼容性与行为差异 |
| 依赖与依赖版本 | 依赖版本过高或过低都会导致问题 |
| 安装位置 | 不同架构/管理要求下安装路径可能不同 |
| 系统文件 | 运行时能否正确生成所需系统文件 |
| 安全 | 防火墙是否安装、是否影响响应速度 |
| 分布式环境 | 若涉及分布式部署，需专门测试 |
| 数据库版本 | 与应用是否存在版本不匹配 |
| 服务端脚本 | server-side scripts 必须测试 |
| 管理员角色 | administrator 误操作可能造成的后果 |
| 代理 | 若使用代理，相应配置也要测试 |

其中"管理员角色"最易被忽略：管理员通常是友好用户，团队在安全防护上对其假设更弱、权限更大；但必须假设其**可能误操作**，并评估误操作对系统造成的后果。

#### 客户端配置（client-side）

不能默认所有用户都用同一分辨率、同一浏览器。客户端要考虑：

- **硬件**：不同客户群硬件差异大，CPU、内存乃至显卡（例如网游对显卡有最低要求）；
- **打印设备**：若需打印功能，能否正确设置并打印；
- **操作系统**：尽量覆盖各种客户端操作系统；
- **浏览器**：各种浏览器均宜实测；
- **界面组件**：ActiveX 等控件；
- **插件**：若 Web 应用用到插件，缺失时能否提供安装文件；
- **网络连接（connectivity）**：网络环境下的表现。

### 四、安全测试：三个环节的脆弱性

安全测试关注三个环节的脆弱性（vulnerability，即最薄弱的环节在哪里）：

- **客户端**：最容易出错的是浏览器本身存在缺陷（这也是"不要用旧版 IE"的原因），以及邮件系统、即时通信软件（如 QQ、MSN 等）带来的安全隐患；
- **服务端**：服务器最易遭受 DoS 攻击、恶意脚本攻击，需评估防御能力；
- **网络**：传输链路的脆弱性。

### 五、性能测试：真实流量不可控下的压力验证

性能测试是 Web 应用最头痛的事之一——配置环境本就难查错，而真实世界流量（real-world loading）是你完全无法控制的。它要回答的核心问题包括：

1. 服务器响应时间会不会退化到"明显且不可接受"的程度（Does the server response time degrade to a point where it is noticeable and unacceptable）？
2. 在什么并发量、什么数据流量下，性能变得不可接受（At what point does performance become unacceptable）？
3. 接近崩溃时，哪些模块是瓶颈？
4. 高流量下系统的安全性是否会受影响（学过信息安全原理应知此意味）？
5. 高并发时部分功能的可靠性、数据精确性是否受影响？

一个真实教训来自在线评测系统（Online Judge，如 PAT、ZOJ）。考试或比赛时，接近崩溃边缘会出现：运行时间测不准、内存使用测不准等。因此 PAT 考试规则中常注明：最后 10 分钟系统崩溃不补时，以崩溃时刻排名为准。这说明高负载下数据准确性本身就是要测的对象。压力测试还要考察：崩溃之后系统会怎样。

性能测试分为连续的两大块：**负载测试（load testing）**与**压力测试（stress testing）**。

#### 吞吐量模型

负载测试在"正常值范围内"改变加载条件，观察 Web 应用及服务端环境对不同流量、访问量的反应。有一个核心术语——总吞吐量（overall throughput），记为 $P$，它由三个要素相乘得到：

$$P = N \times T \times D$$

其中：

- $N$：并发用户数（the number of concurrent users）；
- $T$：单位时间内每个用户完成的在线事务数（online transaction per user per unit time）；
- $D$：每个事务所产生的数据量（data volume per transaction）。

以秒为单位时，$N \times T \times D$ 即"每秒涌入服务器的总数据量"。测试时要不断改变 $P$ 的值，观察系统响应。注意 $P$ 由三个独立因素构成，需做多种排列组合：例如极大并发但每人的操作都很简单、数据量小；或中等并发但操作很复杂。不同组合暴露的瓶颈不同。

一句话类比：**玉米是服务器最好的测试员**——每到抢票季，谁家服务器扛不扛得住，放到抢票场景一试便知。

#### 压力测试

压力测试是负载测试的延续：负载测试在正常范围内做，压力测试则要找到系统的临界点并将其推过去，观察整体表现。两者注意事项详见教材，此处不展开。

### 六、讨论：如何证明一个支付系统能扛住百万并发

性能测试不能停留在形容词。曾有学生的毕业论文开发了一个在线系统，号称支持"多大并发量"，但测试章只测了 10 个并发——这根本无法证明其宣称的能力。任何"优秀的特性"都不是嘴上两个形容词就能成立的，每个形容词都要有根据、可证明。

因此设一讨论题：开发一个类支付宝的在线支付系统（Online Payment System），面对接近真实的约束——

- 至少支持 **100 万**在线用户；
- 每天并发量约 **10 万**人次的分钟级并发访问；
- 每天产生约 **1TB** 级数据；
- 需同时考虑并发、存储、数据库对 100 万用户数据的支持。

要求：不谈用户界面与导航测试，聚焦**性能**。若你声称系统能做到上述指标，要用什么方法**证明**它确实能做到？不能只测 10 个并发就宣称"大规模并发无压力"，必须设计对照吞吐量模型 $P = N \times T \times D$ 的负载与压力测试方案，给出可量化的证据。

### 随堂自测

**1. Web 应用的可用性测试为何必须由终端用户而非团队自身执行？其核心步骤包含哪三项关键活动？**

解析：Web 应用的用户是"不可控、不认识"的人群，只有让真实代表性用户操作，才能验证他们能否自主使用界面。团队只能设计测试、不能替代执行。三项关键活动：①界定本次要测的 usability 目标（interactivity、layout、readability、aesthetics、personalization、accessibility 等）；②为每项目标设计可量化的测试用例与评估指标（如用手势交互案例中的客观计时 + 学习曲线 + 主观问卷）；③选择并观察用户群完成测试。

**2. 性能测试中的总吞吐量 $P$ 由哪三个要素构成？它们分别含义为何？**

解析：$P = N \times T \times D$。$N$ 为并发用户数；$T$ 为单位时间内每用户完成的在线事务数；$D$ 为每个事务所产生的数据量。三者乘积即单位时间（如每秒）涌入服务器的总数据量，测试时通过改变三者的排列组合来观察系统响应。

**3. 服务器配置测试中，为何"管理员角色"是容易被忽略却必须测的环节？**

解析：管理员通常被假设为友好用户，团队对其安全设防较弱、权限较大；但必须假设其可能发生误操作，并评估误操作（而非恶意攻击）对系统造成的后果。只测外部攻击、不测高权限误操作，配置测试就不完整。

## 第 3 章：第27讲 Web应用软件测试-3
> 对应分集：P27 | 原始标题：《第27讲 Web应用软件测试-3》

Web 应用的测试同样是从质量度量维度出发，用以达成 Web 应用的质量目标。本讲在前两讲逐维度展开的基础上，回到整体视角：先列出测试覆盖的全部质量维度，再剖析 Web 测试相比传统软件测试的固有困难，之后给出一套"设计模型—测试活动"层层对应的策略，最后对内容/数据库、界面机制、导航语义、配置两端、安全攻防、性能负载等维度做纵深补充，其中不少细节是前两讲未及的。

### 一、质量维度总览：测试要覆盖什么

从质量度量出发，Web 应用测试至少应覆盖以下维度：

- **内容测试**：分语法与语义两层。语法关注拼写、连接等是否正确；语义关注表达是否准确，包括政治等敏感因素是否恰当、无恶意。
- **功能测试**：验证内容与需求一致，考察稳定性（有多少不稳定），并符合既定标准（如 Java、JSP 等规范）。
- **结构测试**：检验设计出的应用能否准确展现内容，是否可扩展，能否支持新内容随时更新。
- **可用性测试**：不同用户是否都能使用，能否借助导航的语法/语义快速学会并上手。
- **导航测试**：检查导航的语法与语义，重点防止死连接。
- **性能测试**：在各种配置（服务器端、客户端、硬件、浏览器）下的执行条件；以及在访问量突增等特殊情况下的反应速度。
- **兼容性测试**：各种客户端、各种终端、服务端都要测，突出问题是不同浏览器（IE 与其他浏览器）表现差异。
- **互操作性（interoperability）**：现代 Web 应用除访问页面外，常与大型数据库交互，需测其访问其他应用、数据库的界面是否有问题。
- **安全性**：找出弱点/易攻击性（vulnerability），尽早弥补，避免交付后被黑客攻击。

### 二、Web 测试的固有困难

Web 测试之所以比传统软件测试更难，根源于运行环境的开放与不可控，具体表现为四类困难：

1. **症状位置与根因位置分离**。客户端表现出的症状，未必是客户端自身的问题。例如用户页面加载不出来，很可能不是网页本身的错，而是网络下线、带宽不足。这正如人感冒发烧流鼻涕——流鼻涕看似鼻子的问题，实则深层原因是身体遭受病菌侵染。诊断时必须穿透表层症状找根因。

2. **环境不可复现**。传统软件测试的条件完全可控、可复现；而 Web 应用中，某错误只在某种配置或某种浏览器下出现，即便想原样复现，环境信息也极难还原，测试在技术上"不可重复、不可复制"。

3. **错误常由配置引起**。与传统软件由代码逻辑出错不同，Web 应用的许多错误来自不同配置。同一份代码在不同配置下表现迥异。

4. **错误跨越三个层面**。错误可能发生在客户端、服务器端、网络通信端三者之一，定位时须判断究竟落在哪一层。此外，错误来源还分静态的（与配置相关）与动态操作环境的（如瞬时资源负载量）。例如《中国好声音》开播瞬间大量用户同时访问，或退选时段负载骤增，都会引发错误。环境在 Web 架构中扮演极重要的角色，诊断错误时须高度重视。

### 三、分层测试策略与设计—测试映射

完整的 Web 测试策略按以下顺序推进：

1. 对**内容模型**严格检查，发现内容错误；
2. 对**界面模型**审查，确认所有用例均可完成——若全部用例能走通，基本问题不大；
3. 对**设计模型**审查，发现导航类错误（如死导航、点不进的死链接）；
4. 对**用户界面**测试，找内容展示、排版、导航机制的错误；
5. 选**构件**做单元测试（如导航单元的整体操作测试，类似传统功能测试）；
6. 对**整体架构/系统框架**做完整系统测试；
7. 在**不同环境、配置**下测兼容性；
8. **安全性测试**，找出易受攻击点，把隐患消灭在交付前；
9. **性能测试**，保证多用户登录下性能不受严重影响；
10. 最终由**终端用户**做可用性测试（先培训再控制执行）。

测试活动与各设计活动严格对应，这是本讲的核心脉络：

```
内容测试  ──对应──► 内容设计
界面测试  ──对应──► 界面设计 + 美学设计
导航测试  ──对应──► 导航设计 + 体系框架设计
构件测试  ──对应──► 构件设计
配置/性能/安全测试 ──横跨──► 上述全部（综合性维度）
```

内容测试与内容设计密不可分，界面测试与界面设计、美学设计紧密相关，导航测试与导航设计、体系框架设计相关，构件测试与构件设计密不可分。

### 四、内容测试与数据库测试的复杂性

内容测试要发现三类错误：

- **语法错误**：typo（排版/拼写错误），依据文本、文法、图表及其他表示形式检查；
- **语义错误**：信息的清晰度、完整程度，须精确表达，不出现二义、模棱两可或语义混淆；
- **结构错误**：内容最终展现给用户时，结构是否能合理反映内容。

**数据库测试**是内容测试中最复杂的部分。原因有四：

1. 客户端很少直接暴露 SQL（结构化查询语言），需在数据库管理系统（DBMS）间做跨平台翻译；
2. 数据库可能位于远端，Web 应用服务器需跨服务器存取；
3. 原始数据须尽快到达 Web 应用服务器再呈现给客户端，往往要做格式转换/格式化，动态内容对象亦需适当格式化以适合展示；
4. 逻辑上要与客户端交互。

其数据流动可用下图表示：

```
客户端(用户界面)
   ▲  HTML 脚本
   │
WebApp 服务器层  ──转换──► 用户数据
   ▲  SQL
   │
数据存储层(DBMS) ──原始数据访问──► 原始数据
```

因此每种数据都需单独测试并综合测试，复杂度正源于此。

### 五、界面机制测试

界面测试旨在发现形式错误，使界面特征满足设计原则与关键点。Web 应用以展示内容为主，视觉内容必须有吸引力，否则用户会迅速离开。

测试覆盖的界面机制包括：链接（Link）、表格、客户端脚本、动态 HTML、弹出窗口（弹出位置、大小、展示形式）、CGI 脚本（Common Gateway Interface，运行在 Web 服务器上的应用程序）、流动的动态内容、Cookie 等。特殊机制要专门测，例如电商购物车：最小装多少、最大装多少、一件未选就点结算是否显示金额为零、超出最大容量会怎样。

测试手法上：

- 对**导航语义单元（NSU，Navigation Semantic Unit）**做单元测试，如"购物""下订单"这类完整机制；
- 通过模仿用户操作设计用例；
- 测试特殊用户种类，类似第13章的集成测试；
- 测试整个界面，需引入人的测试以验证界面语义性，部分类似确认测试；
- 在不同环境（不同浏览器）下测访问服务器、后台数据库时的兼容性，类似配置测试目标。

### 六、导航测试的语法与语义

导航测试目标分语法与语义两层：

- **语法**：检查导航链接、重定向（redirect）、书签、框架（Frames）/框架集（Framesets）、网站地图、内部搜索引擎。
- **语义**：导航是否准确。

关于**重定向**：当网页地址被删除、更新或取消时，应给用户恰当提示，例如"网页已不存在或已删除"，并建议"按某键返回主页"，这属非常规但必要的处理。具体测试问题参见教材 23.6.2 节。

### 七、配置测试的两端细节

#### 服务端

- 与服务器的兼容性；
- 系统文件、目录、相关系统数据库能否在运行时以标准方式正常创建；
- 安全测试：防火墙、加密（encryption）提高安全度的同时，**可能降低性能**，须评估是否会大幅明显降速；
- 分布式服务器上的配置方案；
- 与数据库软件的良好整合，注意不同数据库版本/平台/软件版本的敏感性异常；
- 服务端脚本能否正确运行；
- 系统管理员误操作是否影响运行；
- 代理服务器（Proxy Server）配置与不用代理时的差异。

#### 客户端

- **硬件**：CPU、显卡 GPU、内存、打印设备等；
- **操作系统**：Windows、Linux、Mac OS X、手机端 Android 等都要实测；
- **浏览器**：IE（份额最大）、Mozilla Firefox、昔日流行的 Netscape（份额已极低）、Safari（苹果平板等）等，不能只测 IE；
- **界面构件**：ActiveX、Java Applets 等；
- **动态插件**：QuickTime、RealPlayer 等播放器及其他插件，须全面测试；
- **网络传输设备**：Cable、DSL、调制解调器（Modem，带宽约 56K）、T1 等。其中 DSL 含 HDSL、SDSL、ADSL、VDSL 等类型；T1 在美国制式为 1.544 Mbps，欧洲为 2.048 Mbps；更大的 T2、T3 中，T3 带宽约为 T1 的 28 倍，达 44 Mbps 级别。

### 八、安全测试：三个层面的攻防

安全脆弱性分布在三个层面：服务器管理层面、网络通信层面、客户端层面。课堂中通过模拟黑客手段来发现弱点——"一击即破"好过在运行中出事，因为可及时补救，否则给用户造成大损失。

**客户端脆弱性示例**（学生举证）：

- 木马注入客户端，监听并截获输入的账号密码——测试时应验证防监听机制，看能否截获刚输入的账号密码；
- 用 GET 传输指令或获取内容时，变量名显现在 URL 上，有经验的黑客可修改参数获取受限文件或他人隐私，进而影响服务器端（亦关联缓冲区溢出角度）。

客户端脆弱性常源于浏览器、email、通信软件上既存的 Bug，需跟踪找出并弥补。

**服务器端脆弱性**包括：拒绝访问攻击（DoS）、恶意脚本（malicious script）——恶意脚本由客户端传入，可使服务器操作瘫痪，产生大量隐患。

### 九、性能测试与负载模型

性能测试模拟现实复杂情况，核心是观察：服务器响应时间在何种并发/数据量下退化到不可接受；访问量猛增（如春运订票系统）时性能是否明显下降、让用户焦虑甚至愤怒；在某一 $N$ 值下，递交的交易数或数据负载何时变得不可接受；性能衰竭与哪个部件相关（如是服务器过少可增服，是带宽可升级）。

还要注意：高负载下系统安全性是否受影响；可靠性/可信度是否受影响；超过最大容量（如支付系统设定一万，测一万零一、一万零二）会发生什么——是直接瘫痪、不瘫痪还是性能死掉。

性能测试含**负载测试**（观察服务端环境应对不同负载的反应）与**压力测试**（不断加压直至满载甚至超限，看是否瘫痪）。

总负载量公式：

$$P = N \times T \times D$$

- $N$：并发用户数量；
- $T$：单位用户、单位时间递交的事务数量；
- $D$：每次递交的数据容量。

举例：某 NBA 东部决赛（热火队）直播页面，假定 2000 人观看，每人每两分钟递交一次评论（即每秒约 1/120），每次评论平均 3K，则：

$$P = 2000 \times \frac{1}{120} \times 3\text{K} \approx 500\text{KB/s}$$

意味着该体育网站必须达到约 500KB/s 的吞吐能力。类似地，网上支付系统（支付宝、天猫）在大促时订单与请求暴增，需分别评估 100 人、1 万人、100 万人下的平均反应时间。压力测试的具体问题见教材相关章节。

### 随堂自测

**1. Web 测试相比传统软件测试有哪四类固有困难？**

解析：①症状位置与根因位置分离（如页面加载不出可能是网络而非网页本身，类比感冒流鼻涕根因在病菌）；②环境不可复现（错误依赖特定配置/浏览器，难原样还原）；③错误常由配置引起（非纯代码逻辑）；④错误跨越客户端、服务器端、网络通信三个层面，且分静态配置与动态负载两类来源。

**2. 导航测试中关于"重定向（redirect）"应如何处理？其语法层还要检查哪些对象？**

解析：当网页地址被删除/更新/取消时，应给用户恰当提示（如"网页已不存在或已删除"并建议返回主页）。语法层还需检查：导航链接、书签、框架/框架集、网站地图、内部搜索引擎。

**3. 总负载量 $P = N \times T \times D$ 中三要素分别是什么？用 NBA 直播页案例说明其代入方式。**

解析：$N$ 为并发用户数，$T$ 为单位用户单位时间递交的事务数，$D$ 为每次事务数据量。案例中 $N=2000$ 人，每人每 2 分钟评论一次即 $T=1/120$ 次/秒，每次 $D=3K$，得 $P\approx 500\text{KB/s}$，即网站需具备该吞吐能力。
