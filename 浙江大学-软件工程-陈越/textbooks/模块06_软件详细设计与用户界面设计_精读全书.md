## 第 1 章：第15讲 详细设计
> 对应分集：P15 | 原始标题：《第15讲 详细设计》

总体设计与测试方法讲过之后，就可以真正开工了。本讲用两节课粗略介绍两个 design 中的**构件级设计（component-level design，即详细设计）**。详细设计内容极多，单独开一门课都不为过，这里只过其大类与要点。构件（component）有两大类视角，对应的工具与设计原则也分两大支。

### 一、什么是构件（Component）

OMG（Object Management Group，对象管理集团——UML 即由它发布，UML = Unified Modeling Language，统一建模语言）给出的正式定义是：

> 构件是一个**模块化的（modular）、可发布的（deployable）、可替换的（replaceable）**系统部件，它**封装了实现（encapsulates implementation）**，并**暴露一组接口（exposes a set of interfaces）**。

要点在于：只要对外接口不变，内部实现可随意替换——比如你有更好的算法，用新算法换掉旧实现，只要外部接口不变就毫无问题。

"构件"指代的对象随开发风格而变：

- **传统结构化设计**：构件 = 层次结构图里的一个方块；该方块通常对应数据流图里的一个圆（一项功能）。即以**功能为核心**划分构件，一个构件是完成某一功能的单元。
- **面向对象设计（OO）**：构件基本就是 **一个 `class`**；但当类很复杂时，也可能是一**堆 classes**——按某种规则打包成一组，交给某个小组去做，这一包就是一个构件。

因此构件设计大体分**类级（class-based）**与**传统/结构化**两支。

### 二、类级构件的设计原则

OO 世界里，软件由一堆 objects 构成，详细设计就是对这些 objects 的设计。四条著名原则必须掌握。

#### 2.1 开闭原则 OCP（Open-Closed Principle）

> A module or component should be **open for extension but closed for modification**.
> 对扩展开放，对修改封闭。

教材以家居保安系统为例：系统中有 `Detector` 类，作用是收集各类 **sensor（传感器）**的状态，发现异常就发出 `detected` 信号。家中 sensor 不止一种——有监测烟的、温度、震动、图像等。

**违背 OCP 的写法**是在 `Detector` 里堆 `if-else` / `switch`：

```java
class Detector {
    void detect(Sensor s) {
        switch (s.type) {
            case SMOKE:    ... ; break;
            case TEMP:     ... ; break;
            case VIBRATION:... ; break;
            // 将来发明新 sensor，必须回来改这里的核心代码
        }
    }
}
```

一旦技术进步、出现新型 sensor，就得改 `Detector` 的核心源码——这正违反"对修改封闭"。

**符合 OCP 的写法**是引入一层接口，把扩展点隔离出去：

```java
abstract class Sensor { abstract void read(); }
class SmokeSensor    extends Sensor { void read() { ... } }
class TempSensor     extends Sensor { void read() { ... } }
class VibrationSensor extends Sensor { void read() { ... } }

class Detector {
    void detect(Sensor s) { s.read(); /* 核心算法不动 */ }
}
// 新增 sensor → 新增一个子类，Detector 核心一行不改
```

用一个生活比喻：核心代码是**墙上的电源插座**，不要每多一个电器就拆开插座重分数个口；而是接一个**接线板（power strip）**往外扩，接满了再接一个接线板，可无限扩展，而插座本身永不拆动。讲师做医学院系统时也用此思路：换一家医院的器械厂商，核心源码受保护不动，只改一层接口。

#### 2.2 里氏替换原则 LSP（Liskov Substitution Principle）

> Subclasses should be **substitutable for their base classes**.
> 子类应当能替换掉它们的基类。

即向下兼容：派生出子类后，应保证别人用你的子类时，默认它继承并尊重了基类的契约（contract）。基类（老版本）该有的默认行为，子类都应继承下来。

#### 2.3 依赖倒置原则 DIP（Dependency Inversion Principle）

> **Depend on abstractions, do not depend on concretions.**
> 依赖抽象，不要依赖具体实现。

核心部分尽量依赖抽象的东西（如"某个算法"），不依赖具体实现——不依赖实现语言、运行机器、操作系统版本。若代码过分依赖底层具体物（如某 OS 版本），改动将极麻烦。当然，专门负责底层接口的模块无法避免依赖具体，但应**尽可能把这类东西与核心代码拆分开**。

#### 2.4 接口隔离原则 ISP（Interface Segregation Principle）

> **Many client-specific interfaces are better than one general-purpose interface.**
> 多个针对客户端的专用接口，优于一个通用大接口。

若一个 class 扮演 server 角色、有多个 client 来调用它，即便某些 client 有共同需求，也**宁可把功能重复两遍**，给每个主要 client 设计各自的接口；而不要因为功能有共享就做一个大而全的接口让大家都用。原因留作思考：通用大接口会把这些 client 不必要地绑死在一起。

#### 2.5 构件打包原则（当构件=一堆 classes 时）

当构件是若干类的集合，如何"分堆"有几条建议性原则：

- **REP（Release/Reuse Equivalency Principle，发布/重用等价原则）**：*"The granule of reuse is the granule of release."* 你要重用的规模多大，一批发布（release）的规模就多大。打算以后重用的模块应提前抽出放一堆，**要重用的东西一起升级**，否则七零八落升级会导致版本不统一、复用混乱。
- **CCP（Common Closure Principle，共同闭包原则）**：*"Classes that change together, belong together."* 会一起改变的类放到一起（"一起改变"也分"被一起改"还是"一起去改某物"，策略不同，此处不展开）。
- **CRP（Common Reuse Principle，共同重用原则）**：*"Classes that aren't reused together should not be grouped together."* 不与 REP 矛盾，而是其补充——总是一起被重用的类才打一包，不总一起重用的不要打在一起。

### 三、面向对象细化设计的步骤

具体做法分几步：

1. **类分类（Class 分类）**：先把类分成两类——直接对应自然界/问题域的类，与对应后台、基础设施（infrastructure）等底层的类；
2. **细化类内部细节**：先细化不需要重用的部分。细化四样东西：
   - 细化要传递的 **message**；
   - 细化 **interface**（抽取接口）；
   - 细化 **attributes**；
   - 把每个 process / method 内部的**算法**细化出来；
3. **数据与动态行为设计**：设计数据库及其管理；考虑动态行为，即 behavioral model；
4. **部署图与重构**：细化 **Deployment Diagram（部署图，发布结构图）**。

始终记住：设计从不是一次成型，必是**迭代、不断改善**的过程，期间要 **refactor（重构）**，并在重构中 **be open to the alternatives**——总要想"还有没有更好的解法"。

### 四、OCL：对象约束语言

教材介绍一种补充 UML 的工具 **OCL（Object Constraint Language，对象约束语言）**。它 complement UML，有 formal grammar and syntax（形式化语法），长得像伪代码，用程序员易理解的方式描述 design model elements 里的 **object constraint（对象约束）**。

本质上它描述：一个 class 的某 method 要能正常使用，**前提状态（precondition）**是什么（使用前应处于什么状态、传入参数应是什么样），**用完后（postcondition）**系统或某些变量应处于什么状态。即描述每个对象/功能的 pre 与 post 状态。

最简单的 OCL 含四要素：

| 要素 | 含义 |
| --- | --- |
| **Context** | 描述对象是谁——可以是整个 class、class 内某功能、或某属性 |
| **Property** | 对象的属性（若是 class，即其 attribute） |
| **Operation** | 要描述的操作/方法 |
| **Keywords** | 关键字，如 `if-then-else`、`and`、`or`、`not` 等类程序关键字 |

教材示例：`PrintJob` 类给打印机一个任务，其中函数 `validate` 要把某状态从 `no` 改为 `yes`。其 OCL 大致为：

- **Context**：`validate`，传入两个 integer 参数；
- **Precondition**：两个传入参数都应为正数；且 `job authorization` 变量应处于 `no` 状态；
- **Postcondition**：若上述条件满足，则该变量从 `no` 变为 `yes`。

注意它描述的不是"输入输出"，而是"用前状态 / 用后状态"。OCL 细节可查专门参考书。

### 五、传统构件：算法设计与表示工具

传统软件工程的构件以功能为核心，实现一个功能最重要的详细设计就是**算法设计（algorithm design）**。过程是常识性的：看清要完成什么功能 → 做 refinement（自顶向下逐层细化）→ 用 structured programming（结构化程序设计）→ 最后用 formal methods（形式化方法）做正规检查。

描述算法有几种常用工具。

#### 5.1 程序流程图（Flowchart）

最古老、最常见，每个程序员初学语言都学过。但它饱受批评：**太容易改**反而成了大缺点——加个需求 `if Z true then exit program`，在黑板上擦掉一块、加个菱形、随手扯一根线飞出去，箭头满处乱飞。你画起来轻松，却**体会不到这次改动对整个程序结构的破坏程度**。

#### 5.2 盒图（Box Diagram / Nassi-Shneiderman）

为克服流程图缺陷而发明。把整个程序画在一个盒子里：顺序语句是一条条长方形自上而下；`if-else` 在中央划开，左 true 右 false；循环另有画法。**好处**有二：

- 嵌套多少层一目了然，程序的复杂程度直接可见；
- 改动不轻松——要在盒里擦掉一大片重画，你擦掉的范围就是程序直接受影响的范围，改图多难就知道改程序多难，从而克制随意改动。

可惜盒图"命也不长"，最终没普及。

#### 5.3 判定表（Decision Table）

当有多种条件的排列组合、不同情况对应不同处理方式时，用 decision table 理清很合适。

#### 5.4 伪代码 / PDL

**PDL（Program Design Language）** 即常说的 **pseudocode（伪码）**。特点：长得像程序，但关键、复杂处用**自然语言**描述；非常容易与真正的 source code 结合、翻译成代码。它还有一大优势：**machine-readable, no need for graphics input**——敲伪代码比画流程图省事得多，且可由程序自动从伪代码生成流程图（反向从流程图生成源代码则极难）。对维护团队而言，它也比源码易理解。

#### 5.5 习惯的力量

盒图及其他稀奇工具最终都不了了之，到本书这一版只剩流程图。原因很现实：**习惯是强大的势力**——程序员从第一节课就被教流程图，强制换工具再好也难推广。因此提醒：改流程图时脑子里要绷一根"structured"的弦，**自己管好自己**，别在嵌套结构里指针乱飞、箭头乱扯。

### 六、随堂自测

**1. 用 OCP 分析：Detector 类用 switch 按 sensor 类型分支，为何违反"对修改封闭"？正确的隔离手段是什么？**

**解析**：OCP 要求核心代码对修改封闭、对扩展开放。switch 分支把"识别 sensor 类型"硬编码进 Detector 核心；一旦新增一种 sensor，就必须回改 Detector 源码——核心被动。正确做法是定义抽象 `Sensor` 接口/基类，各类 sensor 各自派生子类，Detector 只依赖 `Sensor` 接口调用 `read()`，新 sensor 只需新增子类，核心零改动（即"插座不动、接线板外扩"）。
**答案**：switch 把扩展点钉死在核心，新增类型必改核心源码；应抽接口、用子类扩展，核心保持封闭。

**2. ISP 主张"多个客户端专用接口优于一个通用大接口"。若把 server 对所有 client 合成一个接口，会有什么问题？**

**解析**：ISP 指出当某 class 作为 server 被多 client 调用时，即便 client 间有共享功能，也应给各 client 各自的接口。若合为大接口，则 client 被不必要地绑死在一起——任一 client 的需求变动都可能牵动整个大接口，增加耦合与改动面。
**答案**：通用大接口会把各 client 不必要地耦合在一起，任一变动波及全体，违背接口隔离初衷。

**3. 为何说 PDL/伪代码比流程图更适合作为详细设计的"机器可读"载体？**

**解析**：PDL 形如程序但复杂处用自然语言，易翻译成源码；且为文本输入（no need for graphics input），机器可读。可由程序从伪代码自动生成流程图，而反向从流程图生成源码极难。维护团队也更易接受文本化的 PDL。
**答案**：PDL 是文本、机器可读、易转代码，可自动生成流程图而无法逆向；相比图形化的流程图更利于自动化与维护。

## 第 2 章：第16讲 界面设计
> 对应分集：P16 | 原始标题：《第16讲 界面设计》

### 一、交互本质与用户认知

用户界面（User Interface，UI）是用户接触软件的窗口，也是一切用户怨气的出口。当用户用得不顺手、用得不舒服，骂名绝大多数都指向界面，甚至因为界面太糟而牵连硬件一起挨骂。界面之所以"首当其冲"，是因为它处在用户与系统之间唯一的交界处——用户能感知到的软件，就是界面本身。

#### 1.1 UI 不是美工

很多人把界面设计等同于"美工"，这是一个根本性的误解。在 Web 应用等场景里，美观确实占很大比重，但 UI 的本质偏技术而非艺术。一个值得追求的界面，首先要在功能与交互上正确、高效、不易出错，美观只是锦上添花。

什么样的人能成为好的界面设计者？需要兼具以下几类知识背景：

- **人机交互（HCI）的基本技术**：理解交互的原理与手段；
- **用户心理学**：知道用户如何感知、记忆、形成习惯、在何时犯错；
- **理解程序员的世界与系统架构**：能看懂程序如何组织，知道哪些限制是真实的、哪些限制只是实现偷懒；
- **一点美工与审美**：不需要亲自会画，但要有品味、会挑元素，借助现成工具也能拼出清爽漂亮的界面。

实际选型上，与其找一个纯美工，再配一个纯技术，不如找一个"懂技术又有美感"的人。技术素养保证他不至于因为自己的实现方便而强迫用户多点一步，审美素养保证结果不丑。

#### 1.2 用户习惯是一种下意识的本能

界面设计有一条底层事实必须时刻记住：用户在用你的系统之前，早就在用别的方式工作——纸质的表格、人工的流程、旧的系统。人的操作习惯一旦形成，就变成下意识动作。只要稍微疲劳、稍微走神，强大的旧习惯就会回来。这意味着界面设计不是"教用户新习惯"，而是"尽量贴合他已经有的习惯"，从而降低出错概率。

### 二、三大黄金设计原则（The Golden Rules）

界面设计有三条放之四海皆准的黄金法则，所有具体机制都从它们派生。

| 原则 | 英文 | 核心意图 |
| --- | --- | --- |
| 把用户置于掌控之中 | Place the user in control | 用户能按意图操作，且不会被设计坑去犯错 |
| 降低用户的记忆负担 | Reduce the user's memory load | 用户不必死记路径与状态，系统替他记 |
| 保持界面一致 | Make the interface consistent | 操作方式、视觉风格遵循习惯与整体统一 |

#### 2.1 原则一：把用户置于掌控之中（Place the user in control）

这一原则的字面翻译虽是"把用户牢牢掌握在控制中"，但其准确含义是：用户所点的东西，应当与他想点的东西一致；你不想让他搞乱的东西，就根本不给他搞乱的机会。它包含若干互相支撑的机制。

**（1）定义交互模式，不强迫用户做无意义或不期望的动作**

要点是两句话：*不要给他犯错误的机会*，以及*用最少的步骤做到他想做的事*。

- 设计交互时，不能因为程序实现的原因，逼用户多走一步无意义的操作。例如"只能让你在这多点一下才能进下一页"——偶尔一次用户可忍，天天让用户多点一次，他会爆发，因为那明显是软件的愚蠢。
- 更要防止"不小心点一下就闯大祸"。如果一个普通用户随手一点就把整个系统弄崩溃，错不在用户，而在软件工程师、在 UI 设计。好的设计应当从交互上消灭这类灾难路径。

**（2）提供灵活的交互方式（Provide for flexible interaction）**

这一条与第一点互补：既要防止用户犯错、不给他多余动作，又不能走到另一个极端——剥夺他习惯的输入方式。

一个真实的反面教材：一款外汇交易软件升级后，原本用键盘大键盘输入交易数字，升级后大键盘失效，屏幕上只弹出一个仅含数字和小数点的小键盘。原因在于旧版客户经常往输入框里乱敲无关字符，设计者一怒之下封死了键盘。结果是老用户（如长辈）完全不会用了——因为他们习惯敲键盘，新界面却逼他用鼠标点小键盘。灵活交互意味着应当保留多种可行输入途径，而不是用"防错"的名义砍掉用户已有的能力。

**（3）建立有意义的默认值（Establish meaningful defaults）**

同样是那款外汇软件，账号选择用了下拉框，但默认值竟然是空。问题在于：如果有多个账号，本可以统计使用频次、把最常用的账号设为默认；如果只有一个人用，账号就应当自动成为默认。这样至少省掉用户一次操作。默认值空着，等于把本可代劳的事推回给用户，是细节上的懒政。

**（4）视觉布局基于真实世界隐喻（The visual layout should be based on a real-world metaphor）**

如果你的软件替代了原本用纸、用人完成的流程，电子界面应当尽量复刻原有实物。比如"无纸办公"把纸质表格变成电子表格，电子表格的字段位置、顺序最好和原纸张表格一致。

这条原则的分量，由一起真实事故可见：某人去银行存钱，事后查账发现多出一笔天文数字般的金额，他老实上报，银行一查，是柜员把身份证号码敲进了"存款金额"栏。可能的原因就是——电子表单里"存款金额"框的位置，被放在了柜员习惯填身份证号码的地方。工作时全神贯注不会错，但只要一疲劳、一走神，强大的旧习惯就回来，字段错位便酿成差错。所以做电子流程前，应先调查用户在没有你系统之前怎么工作，让新流程最大限度贴合其手工习惯。

**（5）渐进式披露信息（Disclose information in a progressive fashion）**

不要把所有细节"唰"一下全摊在一个界面上吓晕用户，而应分层展开。真正做到位很有学问：一个界面一次展示多少条目（宽度）、每个菜单下拉多深（深度），都是需要权衡的设计参数。信息要随用户深入操作而逐步呈现。

#### 2.2 原则二：降低用户的记忆负担（Reduce the user's memory load）

用户不应被迫记住"我刚才访问了哪里""我现在在哪""下一步去哪"。支撑这一原则的机制包括：

- **导航条**：做得充分有导航性，让用户随时知道自己身处何处、能去哪里；
- **帮助文档/提示**：在他想用某功能时，提示他可以在哪里用；
- **撤销（Undo）**：虽常被归入"宽容用户、允许后悔"，本质上也是系统在替用户记住上一步状态，便于回退。

核心思路是：凡是可以由系统代记的上下文，就不要压给用户的大脑。

#### 2.3 原则三：保持界面一致（Make the interface consistent）

"一致"至少有三层含义，由内到外。

**（1）软件内部整体风格一致**

一个软件可能由多个小组分头开发，但最终成品不能是七拼八凑。一个验收中的反面案例：几个小组的模块始终合不到一起，便做了一个"假的界面外壳"应付——前台统一壳子，点按钮就拉起某个组的 .exe，打开该组自己的界面；点另一个按钮又起另一组的界面，彼此风格、布局毫无关联。更致命的是后台数据库没合并：在 A 组界面录入的数据，用 B 组界面查不出来。这种"壳一致、里不一致"的东西，在正经软件里绝不允许。无论多少人协作，软件必须呈现统一的整体形象。

**（2）让当前任务处于有意义的情境中（Allow the user to put the current task into a meaningful context）**

用户在 Windows 下常同时开很多窗口：上网、聊 QQ、写论文、做 PPT、开 Word、开 Excel。要在数十个窗口里快速找回目标，依赖底部任务栏——每开一个窗口就有一个图标。图标设计本身有学问：靠视觉即可辨识归属。例如 Word 图标通常是蓝色、PowerPoint 是橘红色、Excel 是绿色，用户扫一眼就能定位要找的窗口。一致性在这里表现为"随时可定位、可回到情境"。

**（3）跨产品家族保持一致（Maintain consistency across a family of applications）**

不止单个软件内部要一致，一个厂商的一系列产品（产品家族）风格也要一致。为何要强调这一点？不一致又怎样？这是本讲的讨论题，见下文。

### 三、设计评估与一致性的价值讨论

关于"跨产品家族一致性"，可分解为三项思考任务：

1. 举出一个**具体的产品系列**例子；
2. 分析它的哪些特征体现了 consistency（一致的风格、一致的操作逻辑、一致的视觉语言）；
3. 说明这么做有什么**好处**、为什么需要这条原则。

论证方向（基于前述原理推导）：家族一致降低用户的学习迁移成本——在一个产品里学会的操作，到同家族另一产品可直接复用；统一的视觉与交互语言建立品牌识别与信任感；一致的报错、一致的导引减少跨产品时的认知错乱。反之，家族内风格割裂，等于让用户每换一个产品都从零学起，既增加出错率，也稀释品牌。

界面设计的"评估"并不只是上线后看，而应贯穿设计：是否把用户置于掌控中？是否减少了记忆负担？是否从内到外保持一致？可用前文那些机制逐条对照，像"外汇软件封死键盘""银行字段错位""假界面外壳"这类事故，都是违背原则后付出的真实代价。

### 四、收尾警示：你以为的意思，未必是客户的意思

用一则漫画收束，它点出一个常被忽视的界面风险：用户对你写的词，理解可能和你完全不同。

漫画里有人打电话："My computer doesn't work. The hard drive crashed. What do I do?"（电脑坏了，硬盘崩了，怎么办？）对方问："Did you back up?" 英语里 back up 原意是"往后退、撤"（像要爆炸时喊 Back up），于是电话那头"哗"地一退："要炸了吗？"

back up 在软件语境是"备份"，但用户的日常词汇里它是"后退/撤离"。这则笑话的严肃教训是：你在界面上写的任何你"以为"是某意思的词，必须确认客户的理解和你是同一回事。词汇歧义、隐喻错位，都会让精心设计的界面在对的地点、对的按钮上，触发完全错的理解。

### 五、随堂自测

**题 1：** 某软件为防用户误填，在升级后取消了键盘输入，只允许鼠标点屏幕小键盘。这违反了哪条黄金原则下的哪一机制？为什么？

> **解析与答案：** 违反了"把用户置于掌控之中（Place the user in control）"下的"提供灵活的交互方式（Provide for flexible interaction）"。该机制要求保留多种可行的输入途径，与第一点"不强迫用户做不期望的动作"互补；用"防错"为名砍掉用户既有的键盘输入能力，走向了过度限制，剥夺了习惯性操作，反而让用户（尤其老用户）无法正常使用。依据见 2.1 节机制（2）。

**题 2：** 银行柜员把身份证号码敲进"存款金额"栏，源于电子表单字段位置与原纸质单据不同。这主要说明哪条设计原则没被遵守？应如何避免？

> **解析与答案：** 违反了"视觉布局基于真实世界隐喻（real-world metaphor）"——电子流程应最大限度贴合用户此前手工作业/纸质流程的习惯与字段位置。避免方法：设计前先调查用户在没有系统前如何工作，使电子表单的字段布局、顺序与原实物一致，从而在其疲劳走神时旧习惯仍指向正确字段。依据见 2.1 节机制（4）。

**题 3：** 一个软件由三个小组分头开发，验收时用一个统一外壳包住，点按钮分别拉起各组自己的 .exe 与界面，且后台数据库未合并。这种做法违背了"一致性"的哪一层含义？危害性是什么？

> **解析与答案：** 违背了"软件内部整体风格一致"这一层（Make the interface consistent 的第一层含义）。它是"假界面外壳"：视觉上统一、实则各组界面互不相干，且后台数据未合并——在 A 组界面录入的数据无法用 B 组界面查出。危害是数据割裂、体验破碎、无法作为统一产品交付。依据见 2.3 节（1）。
