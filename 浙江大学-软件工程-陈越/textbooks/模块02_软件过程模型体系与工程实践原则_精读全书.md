## 软件过程-1
> 对应分集：P03 | 原始标题：《第3讲 软件过程-1》

上一讲我们人是站在月球上看地球，看的差不多是"做什么"这件事的全貌。这一讲我们还站在月球上，不过手里多了一台天文望远镜，能多看一点细节了。今天讲的第一个题目是过程（process）。过程要分两章讲，第一章是过程的一般性视图（generic view），今天先把"过程"这件事的总体样子看清楚。

### 层次化的看问题方法（layered technology）

#### 教材由浅入深的写法与 generic view

你要是有兴趣去翻一翻我们这本教材的目录，会发现一个很有意思的写作风格。这本书很多人都可以用：本科生的教材可以用它，研究生的教材也可以用它；已经工作的人还能把它当成一本手册，想查什么就翻进去查。不同的人看到不同的层次就可以。

它的特点就是——每一大块知识都是由浅到深、一层一层往里深入的，一开始必定是一个 generic view。所以如果你只想用很短的时间大致知道软件工程的方方面面，你只要看每一章开头那个 generic view，view 过去，就差不多知道到哪个层次了。你要是还想知道更多细节，就再往下看下一节、再下一节，它会越讲越细。

这种"由浅入深地分层"也是我想贯穿这门课始终的东西。这门课最重要的目的，不是让你们背下来多少定义，而是让你们养成这么一个看问题的习惯。

#### 层次化技术的推进：从望远镜到显微镜

我们有一句话说：software engineering is a layered technology，软件工程是一门层次化的技术。什么叫 layered？layer 是什么？是"层"。什么叫层次化？就是我们看问题的时候，一定不要一下子看到所有的细节。

打个比方。我跟建筑工程师说，我要建一座桥。他第一件想到的事情，难道是"我要买多少号的螺丝钉、我应该去哪个厂家定"？可能吗？不可能。再换个说法：我说这学期我们大家要做一个大的 project，你们各位脑子里第一件冒出来的事情是什么？——"我应该用什么语言开发？"我想你们好多人第一件冒出来的就是这个。远还没到那儿呢，远远还没到那儿呢。

我们考虑任何事情都有一个公共的方法：先从最宏观的角度看整个事情的全貌，看清楚了，确认自己确实看清楚了，然后再拿一台天文望远镜，再拿一个普通望远镜，再拿一个放大镜，最后拿一台显微镜，看到越来越多的细节。

> **提示**：这个道理不只在软件工程里成立。你们以后毕业设计答辩、做 PPT，都是同一个道理。这学期我们还有一次机会让大家上来做 presentation，你要特别注意这一点——你要充分体现你对 layered technology 这个词的理解。

### 软件工程的最底层：质量焦点（quality focus）

那么 software engineering 最底层应该是哪一层？我们先回忆上一讲讲的 myths and reality。

有一个 myth 是这么说的：我们为什么要写文档呢？软件工程就是让我们写一大堆没用的文档，设立一堆官僚机构，总而言之是专门捣乱的。那 reality 告诉我们的是什么？我们为什么要写文档？或者说不只是写文档——我们有了软件工程这个学科，研究这么方方面面一大堆乱七八糟的事情，最终的目的是要干什么？

不用怕说错，就算全国人民都看见你说错了又怎么样呢？拍出来的也只是你的后脑勺而已。

我们做所有的事情，是为了展示我们的文档可以编辑得有多漂亮吗？本质上是要写出一个有用的软件——对，这是我们的终极目标，是要写出一个软件。但是给一个软件就够了吗？不够，我们需要它是可维护的。这是一个关键。还有呢？还希望它是一个好用的软件。再然后呢？你们不想要一个 bug 少一点的软件吗？

这就是我们最底层的那一层，叫质量焦点（quality focus），就是为了保证质量。

我们做的所有一切规定——你要先这么做，再这么做，再这么做，每一次要写很多文档，要有详细的 report，各种各样罗里吧嗦的事情——目的都是同一个：你如果不这么做，你很可能陷入困境，很可能做出来的软件是不好用的。其实可维护性、可用性都是软件质量的一部分。软件的质量很难定义，它包括很多方面，也包括刚才有同学说的那几个方面。我们做所有的事情，都是为了让我们有一个质量很好的软件。

> **结论**：你们将来应该不会一辈子做程序员。你将来如果去管理一个公司、管理一个团队做事，你也要设计一些规章制度。那时候你要想清楚：你设计的这些规章制度到底是为了什么？我们有一个总的目标，如果你设计的东西伤害了这个总目标，它就是没有意义的；或者说，如果对保证软件质量没有帮助，那么不管这个 process 看上去多么 fancy、多么花里胡哨，它都是没有用的。我们所做的一切，只要它有一样意义——保证我们能做出高质量的软件。

### 逐层细化：过程模型、方法与工具

#### 过程模型（process model）：回答 what to do

在这个层次之上，我们就看到更多的细节。为了达到"保证质量"这个目标，人们设计了一系列的过程模型（process model）。

过程是什么东西？它是一种地图，a road map that helps you create a timely, high-quality result，一张帮助你按时做出高质量成果的路线图。打个比方：我现在站在这个位置，我的终极目标是拿到一个很高质量、又能按时完成的软件产品。于是从这儿走到那儿，我要经过哪些地方？我要先干什么、再干什么、再干什么？每一步应该分成多少步、每一步要干什么？把这件事情搞清楚，它对应出来的就是一个过程模型。

当然，从这里走到目的地有很多条路可以走。不同的公司选择不同的道路，这要根据它主营的软件是什么类型、手底下这些员工是什么层次、它的人力资源有什么特点等等来决定它的策略。所以过程模型回答的是同一个问题：我从这儿到软件生产出来，要做哪些事情？这些事情又是怎么连贯起来的？

#### 方法（method）：回答 how to do

选好过程模型之后，你就要在上面做方法（method）的设计，也就是每一步到底要怎么做。过程模型回答的是 what to do——我们要干点什么才能把这个东西做出来；讨论到方法这个层面的时候，就是具体到每一个阶段你要怎么干，这就是 how to do。

#### 工具（tool）：回答用什么做

每一个方法你知道怎么做了，接下来才轮到"你要用什么工具做"：你应该用什么编程语言，用什么测试工具，用什么版本控制工具，等等等等。这才细到"你要选择什么工具来做事情"的问题。

```text
工具 Tools
  用什么编程语言、什么测试工具、什么版本控制工具
        ↑
方法 Methods
  每一个阶段具体怎么做（how to do）
        ↑
过程模型 Process Model
  先做什么、再做什么、怎么连贯起来（what to do）
        ↑
质量焦点 Quality Focus
  一切活动的总目标：保证软件的质量
```

读图时从下往上看：最底下是总目标，每往上一层就比下一层更具体一点，越往上越接近"到底该用什么工具"这种细节。这一层层往下钻的顺序，正好就是天文望远镜、望远镜、放大镜那套办法。整套课程的过程都贯穿这种思想方法，希望大家学完一个学期之后能把它养成个人习惯。

### 通用过程框架（common process framework）与框架活动

不管最后是哪些公司、设计出什么样的过程模型，大家的模型都差不多有一些共同点。基本上所有的过程模型都要做这么几件事情，这些东西叫框架活动（framework activities）。

- **先分工**：把你要做的事情分成几个任务。就我们这个 project 来说，大面上这件事我已经做了——大概要分这么几个阶段。
- **每个阶段的工作产品（work products）**：任务交给你以后，你总得做出个东西来，才叫完成任务。你交出一份文档来，它也是你这个阶段的 product。它不一定是最终的那个产品，而是你阶段性的一个产出。
- **里程碑（milestones）**：我怎么控制时间？怎么定义里程碑？这也是有学问的。
- **交付物（deliverables）**：在每一个里程碑，我要能交出什么东西来。
- **QA 检查点（QA check points）**：最后我一定要设计一些质量保证的检查点。QA 是什么？Question & Answer 吗？不是。是 quality assurance，质量保证。

就我们这门课的这个 project，大面上的 QA check points 我已经替大家做了。它对应的是哪一块内容？就在 requirement 那个文档里面——我有写我们整个学期要做七件事情，以及每一件事情 TA 应该怎么打分。比方说需求文档你至少要包括哪几个内容，每一部分内容大概占多少分。这个就叫 QA check points。

但这只是一个很粗的、框架性的 QA check points，它相当于一个 guideline，是大面上的。

轮到你自己做事情的时候，你要做得比这细得多。就说需求文档，最后你可能要写好几十页、厚厚的一本。那么如果组长一个人做的话，是注定悲剧的——已经有人悲剧过了。所以你一定会把任务拆解给整个组，大家分头去做。那每个人交上来，你怎么评估他的工作？你要有更详细的检查点：对于每一个分工，你要有自己的 check points；你之后要做 QA 的时候，打算怎么检查？

> **结论**：不管我们采用哪一种过程模型、或者说你自己设计哪一种过程模型，上面这几件事情都得做，这是最最少的。

### 伞活动（umbrella activities）

除了框架活动，还有一类叫伞活动（umbrella activities）。umbrella 是什么？就是今天我们下雨嘛，大家都用的——雨伞。为什么叫伞活动？伞的特点是什么？伞的特点是它把你笼罩在下面。所以它实际上是一类笼罩性的活动。

下面列出来的这些活动：项目管理（project management）、质量保证（quality assurance）、文档编制与产出、测量（measurement）、正式技术评审（formal technical review）、配置管理（configuration management）、可重用性管理（reusability management）、风险管理（risk management）。

它"笼罩性"的意思是：这些活动是贯穿你这个 project 整个始终的。你在做任何一件小事情的时候——你在做分工的时候，你在检查你的工作产品的时候，你在做任何一件事情的时候——都有这么几件事情是你要考虑的。

你肯定要有一个 management，要有一个管理。这里的 project 不是只指我们整个一个大的 project：你做任何一件事情，都可以认为是一个小的 project；做任何一个小 project 的时候，都要有一定的管理，都要有个规矩。然后，你做的这件事情你怎么保证它做得好？所以你要有 quality assurance。这个 quality assurance 不只是一个大的概念——你看，大的和小的、再细的细节，其实有相似的地方；在每一个细节上，都有这些活动贯穿始终。这些活动的意义，我们在后面差不多每一章里都会再讲到。

```text
伞活动 Umbrella Activities（笼罩在整个项目的始终）
  项目管理 · 质量保证 · 文档编制与产出 · 测量 · 正式技术评审
  配置管理 · 可重用性管理 · 风险管理
        |
        +--> 笼罩在做任何一件小事之上：
             分工的时候   检查工作产品的时候   做任何一件事情的时候
        |
框架活动 Framework Activities（每个项目至少要做的那几件事）
  任务分解 · 工作产品 · 里程碑 · 交付物 · QA 检查点
```

读图时注意两者的分工：框架活动是"每个项目至少要做的那几件事"，伞活动是"每一件事里都要同时考虑的几件事"，它是盖在上面、贯穿全程的。

### 所有过程模型共有的五个环节

下一章会让大家看到五花八门的过程模型。但万变不离其宗：不管它怎么变、形式上怎么变，基本上都会分这么五大步骤来做。

**第一件事：沟通（communication）**。我给了大家这个 project，你拿到之后要做的第一件事情不是"需求分析"，你还没到需求分析那个阶段。你要先把需求搞清楚，然后才谈得上分析——先有一个沟通的过程。这就是我为什么问大家：有人打电话跟 TA、跟你们的客户约谈了吗？你总得先跟客户谈一谈，摸一摸底。他要扮演一个啥也不懂的客户，那么他啥也不懂到什么程度、他能装傻充愣到什么程度，你就知道你以后跟他交谈要用什么程度的语言。真实世界就是这样：你通常不会给自己人做软件，你的客户不是计算机出身的，你跟他讲术语他听不懂，那么他能听懂的是什么样的话？你要怎么样跟他沟通？第一个要做的就是知己知彼。这个过程一定要有，否则后头你会很恼火。这一步同时是一个需求收集（requirement gathering）的过程：他想要什么、能收集的东西，先都收集一下。

**第二件事：计划（planning）**。你要有 plan。看看你手里有多少人、有多少台机器；对于要使用的工具和技术方面有没有什么风险，这些人熟不熟；然后分工一下，确定一个 schedule，把各种 deadline 设好。大面上的 plan 也是我替大家做的，但这是远远不够的：做每一个小的 project 的时候，你们组要做自己的 plan，回头我们再讲怎么做。

**第三件事：建模（modeling）**。计划完了，是不是就可以开始写代码了呢？还不行。你猜肯定是不行的——我这么问的话。后面要做的一件事情就是建模：你还要写文档。这个文档到底干嘛用的？这个文档不是给你自己看的。当然，也可能有一天是给你自己看的：两三年以后你已经把这茬忘了，人家跟你说里头有个 bug 要你去改一下，那时候你可能需要翻一翻自己当年写的文档——如果当年文档做得好，你会感谢你自己；如果做得不好，不知道你是不是想掐死自己。

但建模的重点是为了跟别人沟通，而这个"别人"包括很多人。所以你要想清楚，你那个文档到底是给谁看的。起码在需求这个方面，建模的意思就是用图、用表、用各种方式去描述你将要搭建的这个系统，它的结构是什么样子的。你的目的是什么？目的是"我有没有做错"——我要做的跟你要做的是不是一个东西。所以你做的所有东西，都要保证你的 customer 能比较容易地看懂，你主要是为了跟他交流。

组和组之间、工程师和工程师之间也是一样。两个组要互相沟通接口的时候，最好也用同一种方式去描述。因为你对自己要做的系统很清楚，人家并不清楚；你怎么在很短的时间里面让别人迅速知道你这个系统是什么样子的、你们讨论的问题在哪里？这就需要大家都用统一标准的那种图、用同一种格式去描述这件事情，沟通起来才方便。而且这种格式、这种模型，你要设计得让你的 customer 也能容易懂。这才是我们做这件事情的整个目的，不是没事让大家练练写文档。

**第四件事：构建（construction）**。这个时候是真的该写代码了。所有一切准备就绪，你的 customer 看了一下你的模型，觉得"嗯，差不多，我要的东西就是这样"，那你就开始做。做完之后要测试。

**第五件事：部署（deployment）**。写代码、测试，然后是部署。也不要以为交出版本就完了：你先交一个版本，然后要接受用户的反馈，等等等等。

```text
沟通 Communication（需求收集：先摸清客户的底）
        ↓
计划 Planning（人力、机器、工具风险、分工、schedule 与 deadline）
        ↓
建模 Modeling（用图、用表描述将要搭建的系统）
        ↓
构建 Construction（准备就绪，开始写代码，然后测试）
        ↓
部署 Deployment（交付一个版本，接受用户的反馈）
```

读图时注意这是"五个环节"而不是"五条死板的顺序"：不管具体的 process model 是什么样子，它大概都有这五方面的内容；不同的公司采用不同的模型，无非是把它做了不同的排列——不能叫排列组合——用不同的策略去执行这五个步骤罢了。

### 能力成熟度模型（CMMI）

#### 名称、来历与用途

这里头还有一个很有趣的东西，叫 CMMI，全称是 Capability Maturity Model Integration，能力成熟度模型集成。那个 integration 是后来加上去的：最早推出来的时候就是 CMM，Capability Maturity Model，能力成熟度模型。之所以后面多了一个 I，是因为 CMM 后来弄得有点太多了、太庞杂了，所以又做了一个集成式的 integration，推出一个新的就是 CMMI，内容大致差不多。

它是谁推出来的？CMU（卡内基梅隆大学）的软件工程研究所，也就是 SEI（Software Engineering Institute）。

这个东西一定要知道。学完软件工程以后出去，人家跟你谈到 CMM 或者 CMMI，你说"啊？"，那人家就会说："哎？你学过吗？"所以至少要清楚它是能力成熟度模型、大概在做什么事情。

它做的事情是：有独立的评估机构去评估一个软件公司是 CMMI 几级，也就是给这个公司打分，0 到 5 分，说你是第几级。级别比较高，你就可以很骄傲地把认证证书挂在墙上；以后出去拉生意的时候说"我这个公司是 CMMI 几级的"，四级的、五级的，人家觉得好厉害——意思就是说，把任务交给这个公司去做会比较让人放心，因为它有一个成熟的管理机制。

CMMI 光是它自己就可以开一门课专门讲，我们这里只是大概介绍一下它都有什么内容。

#### 从 0 级到 5 级

| 等级 | 名称 | 这个等级是什么状态 |
| :--- | :--- | :--- |
| 0 级 | 不完整（Incomplete） | 基本上不及格。很多校友毕业出去拉三五个好朋友一起创业，创业之初这个草台班子就肯定是 incomplete：大家拿了活就去做，没有 process 的概念，不太有分工的概念，也不太有进度管理的概念，反正大家去做、做完就交。很难称为一个公司。 |
| 1 级 | 已执行（Performed） | 开始有分工的概念了：做一个软件的时候，大家知道有一个明确的分工，每一个任务要产生什么样的工作产品，开始有这个概念。但还没有管理的概念。就像上次说的那个组长：你写哪块、他写哪块，分工分下去之后中间不管了，等到 deadline 前一天把东西收上来——这就属于 1 级。 |
| 2 级 | 已管理（Managed） | 不仅有分工，而且有人在管，至少有一个人在管；各种相关的项目干系人之间有有效、充分的沟通机制；对过程和产品要 monitored、reviewed and evaluated（监控、评审、评价）。每一个组至少应该做到这一级。 |
| 3 级 | 已定义（Defined） | 它真的像一个公司了：有规章制度，有一些东西固化下来、写进文件——我们叫规章制度上墙。这套行为标准贯穿任何一个 team、任何一个 process、开发任何一个产品的过程，也就是行业规范、行业标准；固化的东西留下来，一代一代往下传。大多数软件公司努力一下能做到 3 级，也得做到，否则待不下去。至于你们，每一个人的小 team 实在太小，一般还到不了那个份上。 |
| 4 级 | 量化管理（Quantitatively Managed） | 一般小公司不太做，规模比较大、历史比较长的公司这点做得比较好。办法是想一个办法去采集跟你这个开发有关的数据：比如你看他每天能产生多少行源代码，这是一种；比如你做过多大规模的软件、曾经查出过多少个 bug、平均每个月能查出那个 bug 的百分之多少。采集数据，然后分析这些数据，帮助你的 manager 随时大概知道开发进度——"我这个软件开发了百分之多少"；也让你跟客户保证"我这个团队软件开发质量都是很高的""要达到某一个质量标准我有 85% 的把握"的时候，这个 85% 不是拍脑袋说出来的，而是有一种算法作支撑。 |
| 5 级 | 优化（Optimizing） | 最高一级。你不仅有做事情的规矩、不仅知道采用某一种过程模型去做事情，而且会改进这个模型，不断改进自己的开发过程，甚至可以创新：有更好的开发方法、更好的技术来帮你实现质量保证，帮你控制整个进度。这里面有一个创新的概念。 |

> **易错点**：4 级那一层有个反面。你在微博上会看到有员工从某公司退出以后去抨击这个公司，那往往是量化管理过度了——只看重某一个指标，最后管理会走到人性涣散的地步。量化管理本身是有弊端的，这一点要一起看到。

关于 2 级的"项目干系人"（stakeholder），这个英文词本来是"参加会议的人"：为了让大伙不吵架，拿一根棍子，谁手里拿着那根棍子谁发言——有权利拿到那根棍子的人，就是 stakeholders。也就是说，在你这个整个项目里面有发言权的人。所有有发言权的人，我们叫项目干系人、有关系的人。你要有一个机制，让所有这些人都能有充分、有效的沟通。

我还想补一句：我希望你们每一个组至少要做到 2 级。起码要有 management 这个概念，不能只是把活分下去就完事。

#### 评估看的是过程，不是结果

那这个分数到底怎么打出来？它肯定有一张打分表，上面有很多要考察的点。但它不是这样运作的：我要考察这个点，于是派一个人到你公司里转一圈，根据印象给你打个一分、两分、三分——肯定不是这么干的。它有一个很详细、比较复杂的评估过程，每一个点都要检查具体哪些东西。

> **结论**：它检查的重点不是结果。不是"你当前接了个任务，最后交出来的软件产品市场评估很好，我就给你打个五分"。它要看的是过程——过程考核非常重要。它要看你整个做事情有没有规矩，你做事情的管理严格到什么程度，你的员工在多大程度上拿你这个 manager 当回事。

说到这里我得实话实说：我们这个班就是一家小公司，你们多半是不会太拿我这个 manager 当回事的。我让你交一份 requirement specification、交个需求文档，你交来给我看看就算了；至于这份需求文档是不是真的那个后面的主程序员要用的，那是另外一回事。通常大家不太拿这个当一回事。所以要是真去做一次评估，我们能到几级？不知道——3 级其实到不了的，2 级能不能到都不知道。不过无所谓，幸好我们不是一个真实的项目，这主要是让大家体验一下，知道有这些事情。

### 模式（patterns）

#### 模式就是可重用的模板

还有一个很有趣的东西叫模式（pattern）。pattern 翻译成"模式"，这两个字大家都认识，它到底什么意思？书上是这么写的：defines a set of activities, actions, work tasks, products, or related behaviors，定义一组活动、动作、工作任务、产品或相关的行为——这好像什么也没说嘛。

更容易理解的说法是：它实际上就像 C++ 里面的 `template`，它像一个模板。基本上就是以前我们的前辈工程师们把做这件事情比较成熟的做法总结出来——大家就是这么做的——然后把它总结成一个模板；下次你在做相似的事情的时候，直接把这个模板拿过来套用一下。

它最大、最好的好处是什么？是重用，也就是可重用性：你要能把它抽象出来。我也希望这一个学期做下来之后，你如果有心，可以考虑一下你能不能抽象出个什么模式出来。模式不只是过程有模式，什么都有模式，每个环节都有模式。

我们这门课其中一项 project 内容，就是让大家在做设计（design）的时候考虑一下设计模式（design pattern）：有哪些现成的模式是你可以用的。这会省掉你很多力气。你要设计某一个功能，自己从头去想，还不一定想得好；如果你发现人家前面已经做得很好——这个"红楼梦"都有人写过了——人家碰到这种问题就是这么一种设计模式，你直接套进去，做得又漂亮，又省力。这就是你要会找这个模式。

#### 过程模式的三类

在 process 里面，模式大概分成三大类：

- **任务模式（task pattern）**：跟具体的任务相关；
- **阶段模式（stage pattern）**：跟 stage 相关，也就是你的框架活动——你的过程中间要做什么，这些单独的模式；
- **相位模式（phase pattern）**：怎么把它们串起来，也就是串起来的方式。

#### 一个模式必须写清的内容

如果你自己有本事定义一个模式出来，你要怎么写？通常一个模式至少要包含这么几项内容。看上去它其实很像一个程序、一个类——很像 C++ 里面一个类的定义：

- `pattern name`：模式的名字；
- 这个模式到底是干嘛用的：它是为了管理过程的某一个阶段？是为了让你更有效地测试？还是让你更有效地做 management？还是让你更有效地设计一个什么样的东西？也就是——你为什么做这个模式；
- 这个模式属于哪一类；
- `initial context`：问题的输入。我要用你这个模式，我在什么情况下可以用？
- `solution`：你怎么去解决这个问题。这是你的核心，相当于代码的那一部分——你写的那个主程序；
- 输出：用了这个模式之后，如果你用得成功，最后会有什么样的结果；
- `related patterns`：我这个模式还要用到哪几个其他的模式；
- 最后，最好再给一些例子——应用过的实例。

这就好像大家去 OJ 上做题，在 ZOJ 或者 PAT 上，你看那个题目描述基本上就是这个风格：首先有一个题目的名称，然后描述这个是干什么的，然后具体的输入是什么样的，我要产生什么样的输出——当然中间那个 solution 由你自己去做，related patterns 也是由你自己去做——但最后会给你一组 sample in、sample out。差不多就是这样一种描述方式。

> **提示**：如果你有兴趣，这个学期末你要是能写一篇不错的小 essay，也是有加分的。可以考虑一下：有没有可能你总结出一个有用的模式出来。

### 过程评估（process assessment）

再说一下过程评估。你定义了一个过程，然后去请独立的机构来评估一下，它主要评估的就是你这个做软件的过程。assessment 就是评估。

```text
定义自己的软件过程（process）
        ↓
请一个独立的评估团队来做 assessment（评估）
        ↓
评估团队来看你的过程
        ↓
给你一个结果：一份报告，而不只是三分、四分、五分
        ↓
报告告诉你当前这个过程的能力成熟度、哪方面不足、哪方面有风险
        ↓
组织一个团队去做过程改进
        ↓
改进的结果反馈回这个过程本身，形成闭环
```

读图时抓住最后一步：评估不是花一笔钱换一个分数就结束了。你花钱请人家过来，人家不会最后给你个三分、四分、五分就走人，他有一份 report；这份 report 会帮助你改进你的 software process。你从报告里既知道当前过程的能力成熟度、不足和风险在哪里，又据此组织一个团队去做改进，改进的结果再反馈回过程。到这儿，评估这件事才算完成了它该起的作用。

书上还稍微列出了几个独立的评估机构。这些略微知道一下就好了——记也是记不住的，等你要用的时候你就知道了。

### 个人与团队过程模型

#### 个人过程的五件框架性工作

最后简单说一下个人与团队过程模型（personal and team process models）：一个管个人怎么做事情，一个管 team 怎么做事。这是一点建议，不是规定。

交给任何一个人任何一个活，不管大小，你最好有这么五件框架性的工作：

1. **计划（planning）**：接手任何一件事，先做一下计划。
2. **高层设计（high-level design）**：确定你的理解跟派活给你那个人的理解是一致的。我打算怎么做、我打算把它做成什么样。
3. **高层设计评审（high-level design review）**：拿着它去跟人家沟通、确认——你是不是确定我就是要做这些事情？我没搞错吧？
4. **开发（development）**：按确认过的设计把事情做出来。
5. **事后复盘（postmortem）**：很重要的最后一件事，你要有 postmortem 这个习惯。

这里我特别要强调第 3 件，你们不要嫌它啰嗦。很多人犯错误就犯在这上面：包括我布置作业、布置任务的时候，有人听完上半句就觉得下半句他知道了，然后自动脑补了一些内容，直接去做；做出来我说"我那天不是这么说的，我那句话是这个意思，不是那个意思"，他就惨了，前面全白干了。你一定不能自动脑补很多东西，一定要确认地沟通"我要做的事情是对的"，然后才开始干。

#### postmortem：事后复盘

postmortem 这个词认识吗？post 是"事后"，mortem 是"验尸"——字面上的意思就是验尸报告，很恐怖的一个词。那它实际上说的是什么？其实就是教训：你要学会吸取教训。不是这件事情死了就死了，而是要分析一下——它是怎么死的？为什么？

说到吸取教训，有一个故事。从我实验室毕业出去的一位学长回来跟我说，他特别有感触。他之前在国内的企业里面工作过一段时间，后来到了日本，在日本的企业里面工作，现在还在日本。他说有一件事情让他感触特别深——就是这两个国家的企业在管理水准上的差别。

## 软件过程-2
> 对应分集：P04 | 原始标题：《第4讲 软件过程-2》

从过程的大面上讲起：一件事情做砸了、让你痛苦了一下，你会怎么对待它？你以为你分析过了，你分析到位了吗？

### 一、post-mortem：追到根源的原因分析

我们实验室毕业出去的一个学长，现在还在日本工作。他先在国内的企业待过一段时间，后来去了日本的企业，回来跟我说了一件事，感触特别深。他说两个国家的企业在管理水平上，我们真的是有差距。差距在哪？他讲了一个故事，这个故事的名字叫 post-mortem。

他刚进公司的时候，公司给他派了一个 `mentor`，就是一个师傅带他。有一次他调一个程序调了很长时间，卡死了，死活找不到错误，最后终于找出来了。怎么错的呢？他发现程序里有一段其实是可以重用的，可以直接 copy-paste 到下面来用，就 copy-paste 了一下。关键是手一滑，copy 的时候漏了一个字母。

恶心的地方在这里：这个变量名少了一个字母以后，**它刚好是另外一个合法的变量名**——代码里本来就有一个变量，跟前面那个变量就差一个字母。于是编译是通过的，编译器一点问题都不报。变量名本身又挺长，人眼一扫，差一个字母根本看不出来，就这样一直调到死。

师傅过来问他：你给我说一下这个事情的原因。

他说：我 copy 的时候漏了一个字母，所以后面就错了，导致卡了很长时间。

师傅说：我不是问你这个。你告诉我的这个东西叫**结果**，我问的是**原因**。

他当时就傻了，什么意思？你到底要什么原因？

师傅就给他打比方：原因可能是什么呢？

- 你是说这个鼠标不好用？
- 还是说日式键盘你不习惯？
- 还是说你最近工作时间太长，导致精神很难集中？
- 还是说你家里发生了什么事情，导致你有点心不在焉？

师傅说，这个才叫原因；你跟我说 copy 的时候少了一个字母，这是结果。

> **定义**：post-mortem 就是追原因要追到那个很根源的原因上，而不是停在"我哪一步手滑了"这样的直接结果上。

之所以要这么做，是为了让你下一次不要犯同样的错误。人都会犯错——我们是人类，人类都会犯错。那会学习的人跟不会学习的人区别在哪？会学习的人不是不犯错，他是**不会重复犯同一种错误**：这个错误犯过一次，我就记住了，下次不会在同一个坑里再摔一次。不会学习的人，就一次一次地摔在同一个坑里。

所以 post-mortem 这件事的判断标准很简单：任何一件事情你没做好、让你痛苦了一下，你一定要想到根源，为什么？做这件事的目的，就是避免你把同样的错误再犯一次。最重要的是 `understand the types of errors`——搞清楚这是**哪一类**错误，然后避免重犯。这是个人做事情的 process。

个人如此，team 层面大概要做这么几件事。

第一，**每件事情要有分工，任务要定义好**。你们现在组长要做的事情就是这个：先把任务切清楚、定义清楚。

第二，**要有一个怎么执行这些任务的脚本**。就跟演电影一样：先有一个剧本，然后大家照着这个剧本去演。

第三，`teams are self-directed`——每一个小的 team 自己应该有一种管理的模式，自己驱动着往前走，而不是每个人都像机器人一样等着顶端的 manager 发话：manager 说做这个就往东，说往西就往西，说停就停，中间自己没有任何脑子。这样的 team 我们是不需要的，team 应该能自己有效地往前走。

第四，**如果可能的话，做一些 measurement（度量）**。

> **提示**：对你们手上这个 project 来说，做 measurement 的必要性不是很强，因为这是一个很 special 的 training project，它不具备那个条件——你收集的那些数据对你未来可能没有什么用。收集数据的目的，是为了让你以后能够做得更好更快；在公司里面，你才应该有这样的意识去收集一些数据、分析一下，看我们这个 team process 怎么能够有所改进。

关于 process，大面上要做的事就是这些。

### 二、prescriptive models 与 orderly approach

接下来介绍几个比较著名的 process model，每一个都是有一些公司在用的。首先要说清楚一点：我们介绍的**所有** process model，都叫做 prescriptive models（规约式模型）。

什么叫 prescriptive？就是事先规划好的，规规矩矩地去做事情。跟它相对的另一种做法，就像美国那些大片里的英雄：他总会遭遇到各种突发事件，计划之外的，他事先也没想好要怎么应对，事情发生了就去把它解决掉，见招拆招。

> **提示**：这种情况你最好希望在软件开发过程中不要碰到，不要给你展示英雄气概的机会。

这一章介绍的所有 model 都是 prescriptive 这种类型，它强调的是 `orderly approach to software engineering`。

这就引出今天的第一个讨论题：

> `Is orderly approach really that good?` —— orderly approach 是不是真的那么好？

你可以回答 yes，也可以回答 no，不管回答什么都要给我理由。**那个 yes or no 不是主要的，理由是主要的。**没有标准答案，你能自圆其说就可以。

这个问题可以从两个方向去回答。

- 一方面，如果你很强调 order：我们现实社会、包括软件的需求，其实是经常在变的，**变化是它的本质，是它一个很重要的特征**。你很强调规矩的话，它是不是就比较死板？是不是就不太容易适应变化？
- 另一方面，如果走到另一个极端，完全不要这种 prescriptive model，做到哪算哪："我快啊，我反应迅速啊，你说怎么改我就怎么改，我马上给你改"——那是不是会导致你最后一盘散沙，变成盲头苍蝇那个状态？是不是有这个可能？

> **结论**：两种极端都有各自的代价——强调秩序要付出适应变化的代价，放弃秩序要付出去失控的代价。这道题考的是你能不能把理由讲圆，而不是让你选边站。

### 三、瀑布模型：传统软件生命周期的定义者

进入正题，看第一个 model，也是最古老的，叫 waterfall model（瀑布模型）。

#### 五个阶段的单向推进与「关门」约定

它基本上就是我们前面说的那 5 个阶段它都有——**这 5 个阶段其实也就是根据瀑布模型总结出来的**。

它为什么叫瀑布？你前面一个阶段做完了，原则上不允许再回去返工。水是从上往下流的，从上往下流下来很顺；你想把水从下面往上倒抽上去，不是不可能，那你要动用抽水机之类的东西往上挑，总之很困难。所以严格来说，原则上你应该遵守这个规矩：前面一件事彻底做完了、通过了评审，说 OK，我这把门关上，原则上不许再回去，就要从上往下顺着做下来。

它是最古老的，也定义了传统的软件工程的生命周期——**一个软件的生命周期就是根据它来的**。

#### 瀑布模型的三个明显缺点

它的缺点是非常明显的。

**第一，太死板，不真实。**真实世界的 project 没有这么做的，不可能说我前面做完了后面不许返工。你经常会到了 construction 阶段，甚至都到了 testing 阶段了，客户跟你说："哎，不好意思，我改了，我要改一个需求。"你不能不给他改，他是你的客户，客户是上帝。

而且你不能觉得 customer 是存心给你捣乱——当然我们这门课的 customer 是存心给大家捣乱的，但通常真实的 customer 他不是故意要给你捣乱，那是因为**他是人，他不是神**。你不能指望一个外行的 customer 在一次性的、一开始就把他想要的所有东西都给你很清楚地讲出来。你最经常碰到的情况是：他大概觉得"我大概知道我想要你帮我做这么一个东西、帮我干这件事情"；只有跟你仔细去磨合的时候，你才会发现他中间其实要做很多件事情，不是他一开始说得那么简单。他一开始很难把事情讲清楚。

**第二，客户见到可用产品的时间太后。**如果你真的严格按照这个流程来做，最后客户能够见到一个可用的产品的样子，是在很后期——到 deployment 这个阶段，他才真的看到一个可以用的东西。对客户来说，一个是心理上会越来越没底：你一直都在给我看文档，我一笔钱给了你，过了这么长时间我都没看到一个能用的东西，心里很发毛，等得很不耐烦。

**第三，文档根本替代不了产品。**还有一种很大的原因：你给他看文档的时候，他找不出错来。如果这个软件系统充分复杂，你给他看一个 100 页的需求文档，你说这里面有什么地方没写对，你觉得他能告诉你什么地方没写对吗？除非你错得太离谱，他能告诉你；一般情况下他看都没有耐心看。所以等他真的看到一个可用的东西的时候才发现：不是，这不是我想象中的样子，我不是要这副样子。你问他怎么不早说，他说早我不知道；你说我不是写在某个文档里了吗，他说那个文档我没看懂。你一点脾气都没有。

> **易错点**：瀑布模型"不允许返工"是**原则上**的约定，不是技术上做不到。它的真正问题不在"能不能回去"，而在于它把需求当成一次性可以问清楚的东西，而真实的客户做不到这一点。

`waterfall model` 实际上现在不太有人用了，说起来是没有公司在用它；但事实是，**所有公司的 process model 其实也都在用它**，都是它的变形而已，在它的基础上产生了各种各样的变形。

### 四、渐增式过程模型：incremental model 与 RAD

大家用得比较多的其实是 `incremental process models`，渐增式的这种开发过程。它里面最有名的就是 incremental model。

#### incremental model：先交一个 core product 占领市场

传说这个就是微软公司做事情的过程。它的图是这样画的：横轴是时间轴，纵轴是你完成了多少个 features、完成了多少功能。

它的做法是：找一批人，先用很短的时间、很快的速度，先提交一个 `core product`，把最核心想要的功能先开发出来。然后 incremental 1 的开发也遵循前面瀑布模型里那 5 个阶段，也是这么来的。它不是个完美的产品，但是它包含了主要的功能——比方说它是一个操作系统，作为一个操作系统最起码要有的功能要有；作为一个 Windows 操作系统，那些比较方便你操作的界面、最基本的东西它要有。但它不完美。

然后它先要有一个 core product 去占领市场。市场站住了以后，我再给你升级，再慢慢升级，每一次都给你 more features——当然你说到底是 more features 还是 more bugs，那就另说了。每一次都升级、升级、不断升级，然后提供一个越来越完美的系统出来。

```text
features
   ^
   |                                        .
   |                                   .  '
   |                             .   '
   |                       .  '
   |                 .  '
   |           .  '
   |      .'
   |   .'
   | .'  core product
   +----------------------------------------------> time
     inc1   inc2   inc3   inc4   inc5   ...
     (每个 increment 内部仍走瀑布的 5 个阶段)
```

读图说明：纵轴是已完成的功能数，横轴是时间。起步阶段用一个短的周期先把 core product 交出来，之后每一个 increment 都在前一个的基础上叠加更多功能，台阶式往上走。

这个策略聪明的地方在哪？**在 timeline 上面，在尽可能短的时间先能站住脚，先能占领市场。**

#### incremental model 的人力资源账

在人力资源方面，这其实是一个非常合算的策略。

设想有一批人是专门做前期分析一直到设计的，就是设计工程师这一批人。他设计完第一个 increment 1 以后，开发团队（coder）进来开发、写程序、开始测试，这是一波人。这波人做完了第一个产品，第二波人进驻的时候，他们就开始做第二个产品。设计那边设计好了，开发这边正好干完活了，接着往下做。

**每个人都没有闲着的时候。**大家就不停地升级、升级、升级，但实际上总共就这么几个人——就这么一个有效的人力资源的使用。

> **结论**：incremental model 的一个很大的好处是 `makes a better use of resources`，资源的利用效率非常高。

#### RAD：n 个 team 并行，60 到 90 天出一个东西

另外还有一种叫 `RAD`，Rapid Application Development model（快速应用开发模型）。

它前期其实没有什么：`communication`、`planning` 这些做好以后，它会在一个很短的两到三个月的时间周期里面，就把东西差不多做出来。

它为什么能做到快？基本上就是这么一个模式：**我有 n 个 team 同时并行，把问题分成 n 个模块，n 个 team 同时开始做，做到最后的时候大家合并一下**，完成一个产品。这个周期差不多是 60 到 90 天。

```text
             communication + planning
                       |
        +--------------+--------------+
        |              |              |
     team 1         team 2   ...   team n
     模块 1         模块 2          模块 n
    (并行开发)     (并行开发)      (并行开发)
        |              |              |
        +--------------+--------------+
                       |
                    合并集成
                       |
                   一个产品
             （周期约 60 - 90 天）
```

读图说明：上面是简短的前期沟通与计划，中间是 n 个 team 按模块切分后并行推进，最后汇总合并成一个产品，整个周期控制在 60 至 90 天。

这个模型看着很眼熟——这好像我们就是这么干的，我们就是这么干的。问题是我们这个要做的产品适合这么干吗？

#### 讨论题：简化版支付宝适不适合用 RAD

这是我们下一个讨论的问题：

> 考虑一下我们现在手头要做的这个**简化版支付宝**，它到底适不适合我们选择 RAD 这个 model？它适不适合作为一个最佳的选择？你有没有更好的选择？你要觉得它很好，它好在哪里——因为这个项目有什么特点，因为我们的人员有什么特点，所以采取这个模型是好的；或者说是是不好的，不好在哪里？把你的道理讲出来。回答好或者不好都可以，只要能自圆其说。

#### RAD 能够成立的前提条件

在什么情况下不适用 RAD？RAD 看上去很好，又能够很快地交一个东西出来，但它能够很快的前提条件是这些。

**第一，得有充分多的人手。**你一下子 n 个 team 扑开，你得有这么多人。这个对我们来说不是问题——我们是嫌人多，不是嫌人少的。

**第二，得跟客户保持良好沟通。**你想快，你的客户不着急，那是快不起来的。你得跟客户有一个良好的沟通，所以说，你有没有跟你的 TA 拉好关系？你着急的时候他不着急。

你会想，真实开发的过程中 customer 怎么会不着急呢？他要做软件，他都不着急，我在那儿着急，皇帝不急。但你要站在客户的角度去理解这件事：**他不是不着急，他只是觉得他没有着急的必要。**大多数客户都会觉得，我把钱给你了，我说好了让你替我做这个软件，剩下都是你的事了，你干嘛一天到晚来烦我，问东问西的怎么这么烦？我没有时间啊，我不太清楚这个事情，知道这个事情的人他出差去了、度假去了。他总觉得开发软件这个事情丢给你了就是你的事情，不是他的事情。所以最后因为我没有及时跟你反应、导致 deadline 到了我交不了活，那是你的事情——交不了活、你没按照合同做完，那是你的错，**他不认为他有任何的责任**。这是普遍的一种理解。

所以你跟 customer 有没有一种有效的、救火式的、很快速的反应机制，这也决定了你 RAD 能不能够有用。

**第三，系统真的要能有效地分成 n 个模块，而且最好这 n 个模块是比较独立的。**如果模块与模块之间、两个 team 之间有千丝万缕的关系，这个事情最后肯定是要搞乱掉的。这其实也就是刚才那句话：team 跟 team 之间的 `interface`（接口）如果你还要调来调去、始终定不下来，那最后你肯定是一团乱麻，几个 team 就搅在一起了。

**第四，技术风险不能太高。**如果大家对你将要采用的这个技术不是很熟悉，技术风险比较高的话，你最好也不要那么着急地去做这件事情——RAD 到中间肯定会乱掉的。

这就是你大概要考虑的因素：RAD 到底适不适用你现在做的这个 project。

### 五、prototyping：用样机替代需求文档去沟通

前面是 incremental，接下来还有一大类叫做 `evolutionary process models`，演化式的 model。里面最受欢迎的、最多被采用的就是 `prototyping`（原型化）。

Prototyping 是什么呢？就是**快**。首先我很快的速度大概去了解一下需求，然后用非常快的时间大概做一个计划，然后做一个 modeling、做一个设计。这个设计最重要的是：**我做了一个 prototype 出来。**

> **定义**：prototype 我们叫原型系统，其实就是一个**样机**。

样机是个什么东西呢？他大概有你这个产品的那个界面，界面上面有各种按钮、菜单什么的，但是每一个按钮后面的那个功能你可能没时间实现——你先不用去实现，它是个空壳。

你这个壳先给你的用户去看一下，你告诉他：你点了这个按钮它就会做什么事情，你点这个它会发生什么，你大概跟他描述一下，然后你就收集他的反馈。

他会说：这个东西是不是我想要的？或者说，这个东西放在菜单的这个位置我不太习惯，我想找那个功能找了半天没找着——你说被你藏在这儿了——不好，我要放到这里来。

这个效果，跟你写了一个上百页的需求文档去给他看、让他说他满不满意，完全是两回事：**他说不出来。**但是你给了他一个 prototype，让他去点一下、看一下，他会很容易地告诉你哪个是他要的、哪个是他不要的。然后你再帮他想：你还有没有想要的、我没有写在里面的？这个沟通就顺了——人读图形，比读文字要更容易懂一点。这是一种非常有效的沟通的模式。

所以 prototyping 一般来说是一个 `good first step`：你一开始跟 customer 沟通的时候，他需求一开始说得很含糊，大概是"我想要这么个东西"，然后你给他做一个 prototype，这是非常有效的一种沟通方式。

> **易错点**：prototype 这个东西最后**不能作为正式的产品交给人家，你最后一定是要扔掉的**。

为什么一定要扔掉？因为你的 prototype 是**以快为准**的：你用非常快的速度，一轮一轮去跟他反复地沟通，这是一个循环迭代的过程。那么这个东西的质量肯定是有问题的，它内部的结构可能是乱七八糟的——因为你就是要以快为准。后期又有各种修改，里头改得乱七八糟。做 prototype 的目的是为了得到一个很正式的需求，**真正的系统你要另外造一个**。

当然，在实际工作中，你觉得有多少 team 会把它的 prototype 真的扔掉呢？反正我知道我那个项目组就没扔掉，然后一直在那个 prototype 上头改来改去，改到他们无比痛苦——这个我后面还会再说。我们的开发团队人员就在这儿，没准你们可以去问问他们做得有多痛苦。

### 六、spiral model：四个象限一圈一圈转

另外一个是 `spiral model`，我们翻译成螺旋模型。这个东西说实在的，**没什么人用**——这是可以写一篇很漂亮的 paper、画一个很漂亮的图，但无论如何还是给大家很快地看一下。

```text
                    |
        Q1          |          Q2
   确定 objective   |     (开发阶段)
   风险分析          |   把要做的功能全部定下来
   给出 prototype    |   做出来并验证
                    |
  ------------------+------------------  <- 分割线(任务的分割线)
                    |      每次穿线:
                    |      测试 / 验证 / 审核
        Q4          |          Q3
    计划下一步       |
    requirement plan|
    lifecycle plan  |
                    |
           轴: 花销(可理解为时间, 时间就是金钱)
           运动方向: 一圈一圈向外螺旋推进
```

读图说明：从中心向外是一圈圈的螺旋，轴表示花销（可以理解为时间）；那条线是任务的分割线，每次穿过这条线的时候你总是要测试、要验证、要审核；四个象限各代表一个阶段的工作，一圈转完就往外推进一层。

它做事情是在四个象限里面，每个象限代表一个阶段的工作。最开始是它的第一象限：第一象限总是在大概地知道一下我要做什么，有一个 `objective`，有一个大总目标定下来，然后做风险分析，然后给出一个 prototype 去跟人家说，然后做一些测试、运行，然后有些 model 就提出来；如果可以了，那么这个象限是开发阶段——首先把我要做什么功能在这个阶段全部定下来。这个象限是**计划下一步**：开始做 `requirement plan`、`lifecycle plan`。做好计划以后你开始——每一次都是说大概是这个 requirement 要做点什么事情，然后分析一下风险，给一个 prototype，然后在这一阶段把它做出来，然后验证一下可以了，然后做下一步的计划。

就是这么一圈一圈一圈做出来的。

> **结论**：螺旋模型确实是一个很漂亮的图，但实际上过程太复杂，也不太有公司用，大家看一下就好了。它总的就是要表示一个 evolutionary——这个软件它有一个演化的过程、有一个进化的过程。

### 七、并发式模型与其他几类特殊模型

#### concurrent development model：从一条线变成一张网

另外还有一些叫 `concurrent development model`，并发式的。

它跟我们前面那些 model 的区别在于：前面那些基本上都是一个**流水线式**的工作——就算微软的 incremental，它也是一步一步来的，1、2、3、4、5 五步，然后再 1、2、3、4、5，它都是一条线的运动。

而这个 concurrent development，据说比较适合于 `client/server applications`。它的特点是：**它是一个 network，它是一个网，不是简单的一条线。**

```text
前面那些 model（一条线）:     1 -> 2 -> 3 -> 4 -> 5 -> 1 -> 2 -> ...

concurrent development（一张网）:

        +-------+        +-------+
        | 活动A |<------>| 活动B |
        +---+---+        +---+---+
            ^  \        /  ^
            |   \      /   |
            |    v    v    |
        +---+-------------+---+
        |      活动C        |
        +---+-------------+---+
            ^                ^
            |                |
        +---+---+        +---+---+
        | 活动D |<------>| 活动E |
        +-------+        +-------+
```

读图说明：上面是流水线式的模型，推进顺序是一条单向的线；下面是并发式模型，各个活动之间是双向连通的网络结构，可以互相触发与反馈。

这个后面我们还会再提到。其实我们在学数据结构的时候见过这样的网络——刚讲图的时候有讲过 `AOE network`、`AOV network`，还记得吗？怎么计算关键路径，你那个最长的那个周期，什么关键任务这些东西。就是那样的 network，这也是一种 process model。

#### 所有演化式模型的共同点：waterfall 的变形

总的来说，我们前面说的 evolutionary process、包括 incremental 等等，他们强调的都是：**这些 model 其实都是 waterfall model 的变形。**说起来没有人再用 waterfall，但是 waterfall 是贯穿在每一个 model 里面的。

大家强调的都是 `flexibility`：我这样很快地一个周期一个周期往前走，我会比较灵活，而且主要是比较快。

> **提示**：不管你用哪一种 model，你要记住，我们做这些 model 的**最终目的是要保证一个 high quality**。如果你的快会伤害到你的 quality，你就要做一个权衡。

#### component-based development 与 formal methods

最后稍微说一下几个比较特殊的 process model。最特殊的一个我们会留到这个学期的最后一次课才讲；今天讲到这里，接下来是 component-based development。

- **component-based development（基于构件的开发）**：这种 development 的特点就是特别强调**重用**。你开发的时候模块化要非常地好，最好能够抽象出这个模块，使得它在以后开发类似产品的时候可以直接拿来用。它的侧重点就在这里。

- **formal methods（形式化方法）**：还有一批人是专门研究 formal methods 的。我们这个（简化版）支付宝还是比较简单的；你如果给一个比较庞大的、非 IT 的企业，给它做一个比方说办公管理的系统，那它有很多的部门，每个部门有自己的需求，你最后整理出来的可能是一个五六千字的很厚的需求文档。这里面综合了各个部门的需求，但是部门与部门之间的需求**可能是矛盾的**：这个部门认为我这个功能要求一定要特别到位，其它那些都可以不要；另外一个部门可能正好跟它说的相反。如果它是一个很庞大的需求文档，你要靠人的脑力去发现这中间的冲突，就比较难了，也不靠谱。所以专门有一批人研究：**你用形式化方法、用数学的方法、用形式化语言去表述这个需求，然后用数学的方法自动地查出来它中间有没有逻辑冲突。**

- **aspect-oriented（面向方面的）**：另外比较现在、最近几年流行起来的就是 aspect-oriented。什么是 `aspect`？很难翻译，我去网上还专门查了一下，译法五花八门什么都有，"面向方面的"算是一种。这个时间有限，就不多说了，大家有兴趣自己去看一下。

### 八、统一过程（Unified Process）

最后是 Unified Process（统一过程）。它其实跟 OO 差不多同一时间产生，就是在面向对象这个概念流行的时候，有一批人做的，它的**重要工具是 `UML`，Unified Modeling Language（统一建模语言）**。他们开发了这么一套工具来帮大家做设计。

里面的这些词像 `use case`，后面我们也会讲到：就是用户脚本——用户怎么使用你这个软件，它有一个剧本；**根据这个剧本，以设计这个软件的 architecture、设计它的架构为核心**。它总的这个模式的特点就是 `iterative, incremental`，它其实是一种 incremental 的。

> **提示**：UML 的使用如果要讲的话又是一门课，要花一个学期一门课来慢慢讲。我们这里面后面会给大家有一个简单的介绍。

它与我们前面讲的阶段是对应的，只是换了一套名字。它的 process、它的 phases 大概就是这样：

| 统一过程的阶段 | 对应的阶段 | 做什么 |
| --- | --- | --- |
| `inception` | communication、planning | 初始阶段，一个很正式的表示开始 |
| `elaboration` | planning、modeling | 细化：粗粗地了解一下，然后把它细化 |
| `construction` | construction | 构建（阶段名称不变） |
| `transition` | deployment + construction 后期 | 把产品从专业人员手里转到用户手里，产生一个 `release` |

- `inception`：我们原来定义的 communication、planning 这个阶段，它有另外一个名字叫 inception。inception 就是一个很正式的表示开始，这是一个开始、初始阶段。
- `elaboration`：planning、modeling 这个阶段它叫 elaboration，叫**细化**，就粗粗地了解一下，然后我再来把它细化。
- `construction`：然后大家都进入 construction，它也叫做 construction，进入这个阶段。
- `transition`：deployment 跟 construction 的后期合起来，它叫一个 transition——**把一个产品从你的专业人员的手里转到用户的手里**，这么一个过程。然后它会产生一个 `release`，release 一个版本，这就是一个 software increment，就给一个版本。然后你继续反复地迭代，一个 increment 一个 increment 地给出来，大概是这么一个 model。

后面就是 production 的阶段，再后面列出了一些它在每一个阶段的 work products。这个书上有，大家有时间自己下去了解一下就好了。

process model 今天就介绍到这里。下一次会先介绍管理，不急着进入需求分析——先提醒一下各个小组，你们在管理方面要注意哪些内容。

#### 题 1：orderly approach 是不是真的那么好？

**题干（课上给出的英文表述）**：`Is orderly approach really that good?` 请判断 orderly approach（有秩序的方法）是否真的那么好，回答 yes 或 no 都可以，但必须给出理由。

**当场给的提示与评分口径**：

- 那个 yes 或 no 不是主要的，**理由是主要的**；没有标准答案，能自圆其说就可以。
- 可以从两个方面回答：一方面，现实社会包括软件的需求经常在变，**变化是它的本质**，很强调规矩就比较死板，不容易适应变化；另一方面，如果完全不要 prescriptive model、做到哪算哪，虽然快、反应迅速，但可能导致最后一盘散沙、变成盲头苍蝇的状态。
- 写在纸上，到场的人签名字（学号不用写），5 分钟后收；没到的人不要替他签名。

**解析**：这道题的落点在 prescriptive models 的适用范围上。本讲介绍的瀑布、incremental、RAD、prototyping、spiral、concurrent 等全都是 prescriptive models，它们都强调 `orderly approach to software engineering`。所以答题的两个方向要落在同一组权衡上：秩序换来的可预测、可评审、可分工，与需求变化带来的适应性代价之间如何取舍——而不是简单地在"规矩好"与"灵活好"之间站队。

#### 题 2：简化版支付宝适不适合选 RAD？

**题干**：考虑现在手头要做的这个简化版支付宝，它到底适不适合我们选择 RAD 这个 model？它适不适合一个最佳的选择？有没有更好的选择？要觉得它很好，好在哪里（因为项目有什么特点、人员有什么特点，所以采取这个模型是好的）？或者是不好的，不好在哪里？回答好或者不好都可以，只要能自圆其说。

**解析**：判断依据就是 RAD 能够成立的那几个前提——人手是否充分（n 个 team 能不能真的扑开）、跟客户（本项目里是 TA）有没有良好的沟通与有效的、救火式的快速反应机制、系统能不能有效地分成 n 个**比较独立**的模块且模块间 `interface` 能定得下来、所采用的技术是否熟悉（技术风险是否足够低）。对照这几条逐条检查本项目的实际情况，理由就立住了。我最后也明说了：人手对我们是够的（"我们是嫌人多，不是嫌人少"），难点在客户沟通与模块独立性上。

## 软件过程-3
> 对应分集：P05 | 原始标题：《第5讲 软件过程-3》

上一讲我们把软件过程的一般性框架过了一遍——过程里有哪些活动、这些活动凭什么组织成一个骨架。这一讲开始看**具体的**过程模型，也就是把那个框架落成一套有名有姓、能照着走的做法。

这一讲讲到的模型，都属于**描述性过程模型（descriptive process model）**：它们负责把软件开发的步骤和顺序描述清楚。至于这类模型在现实中暴露出来的问题该怎么解决，第四章我们再讲**敏捷的过程模型**。

---

### 过程模型要解决的问题与合适性判断

软件工程的过程本来就是一件容易乱的事情。方法或者模型选得不合适，软件开发过程就会带来很多混乱：谁先做、谁后做、做到什么程度算完，全凭临场发挥。

> **结论**：过程模型最根本的作用，是给软件工程**规定一个规矩**，让我们在这个范围里面排出一定的顺序。

那么这样一个过程模型，它是不是合适？这个问题得分时间看。

在软件工程的早期，这类过程模型确实给我们带来很多好处：它给软件开发规定了要求，一步一步该做什么、每一步要交出什么，都写清楚了，所以它是合适的。可是现在情况变了——软件发展了，人们对软件的要求越来越高，特别是我们做很多 web 应用的时候，用户对软件交付的时间有很高的要求，这个要求本身还一直在变。于是老一套的过程模型暴露出挺多问题。

> **提示**：这一章要讲的模型，有的时间已经比较长了，但它的机制到现在仍然有作用，所以不能因为"老"就跳过。后面几个模型，几乎都是站在最基础的那个模型肩膀上改出来的。

下面我们一个一个看：**瀑布模型**、**增量过程模型**、**演化过程模型**（原型开发和螺旋模型），最后是**统一过程**。

---

### 瀑布模型

#### 名称由来与线性特征

过程模型一般第一个就讲瀑布模型，因为它最早，也最基础。

为什么叫瀑布模型？看一眼瀑布就知道了。瀑布有什么特点？我们把它的特点提取出来，有这么两条：瀑布永远是从上往下流的，你很难看到它从下往上流；它是一个带有线性逻辑的东西。所以瀑布模型也就是一个**线性的过程模型**。

我们再换一个角度把这个模型推出来。假设所有的条件都非常非常简单，整个软件开发过程当中没有任何复杂的逻辑，那么最基本的一个过程模型，需要拥有哪些要素？把这些要素按它最原始的状态列出来，就得到一个非常清晰的过程模型——这就是瀑布模型。

#### 五个基本阶段

瀑布模型有五个阶段，一个走完才能开始下一个。

```text
┌──────────┐
│ 1 沟通   │  和客户、和给你项目的人充分沟通，把需求调查清楚
└────┬─────┘
     │
     ▼
┌──────────┐
│ 2 策划   │  项目估算（多少时间、多少成本、多少人力）＋进度计划＋项目跟踪
└────┬─────┘
     │
     ▼
┌──────────┐
│ 3 建模   │  用模型工具在更高的抽象层次上分析和设计，还不是代码
└────┬─────┘
     │
     ▼
┌──────────┐
│ 4 构件   │  编码与测试
└────┬─────┘
     │
     ▼
┌──────────┐
│ 5 部署   │  交付、支持、反馈
└──────────┘
```

图中五步自上而下依次进行，箭头只有一个方向：前一步不完成，后一步不开始。

**第一步，沟通。** 这非常符合现实过程当中的认识：在项目启动之前，你需要把需求究竟是怎么样的调查出来；项目启动的过程中，要提前和不同的人做充分的沟通——包括和给你提供这个项目的人。这就是瀑布模型的第一步。

**第二步，策划。** 有了妥当的沟通，你要把它落实成可以操作、可以执行的书面文件，需要有一个非常具体的、详细的规划。策划里面有项目的估算——这个项目需要花多少时间、需要花多少成本、大致要投入多少人力；还有一个是进度计划，每个过程需要花多少步都要写出来。做过 SITP、做过毕业设计的同学都清楚，进度计划里非常重要的一部分，是它会给你一个非常全局观的思想：告诉你什么时候应该做什么样的事情。接下来还有项目的跟踪，不断地 tracking，不断了解你这个项目进行到了什么样的程度。

**第三步，建模。** 我们通过一系列的模型工具，把很复杂的这个问题更加形象地表示出来。但是它又不是直接的代码，它便于我们在一个更高的抽象层面上去进行分析和设计。

**第四步，构件。** 这就是大家很熟悉的 construction：编码和测试。我们本科生现在主要在学的就是这个环节；以后进一家 IT 企业，一开始做的很可能也是编码测试。等这些做得比较熟练了，才慢慢能看到整个过程，并且参与得更多一些。

**第五步，部署。** 它包含交付、支持和反馈。程序不是做完了就算了：还要交出去，看看有没有一些新的需求，及时获得一些支持，还要有反馈——有没有需要改进的地方。

把五步连起来看，水从最上面的位置一直这样划下来，就像那个箭头一样，所以它叫瀑布模型。瀑布模型也被人叫做经典的生命周期模型：它把一个生命周期分拆开来，再按一个非常顺序的方式展示下来。

#### V 模型变体

瀑布模型除了这种最原始的形式，还有一个变体：**V 模型**。

```text
需求分析 ─────────────▶ 验收测试
概要设计 ─────────────▶ 系统测试
详细设计 ─────────────▶ 集成测试
编码     ─────────────▶ 单元测试
```

左列是开发流程，自上而下走：需求分析、概要设计、详细设计、编码；右列是测试流程，自下而上回：单元测试、集成测试、系统测试、验收测试。两列按行一一对应，左边从上到下把 V 的左腿走完，右边再从下到上把 V 的右腿走回来，合起来就是一个 V 字。

V 模型把前面的环节和后面的环节一一对应起来，本质上和瀑布模型是一样的，都符合顺序原则。

#### 现实工程中暴露的问题

瀑布模型是最早的、凭直觉对软件工程产生的一批想法。它在现实过程当中运用起来，会带来很多问题。

**第一，现实工程很少按这个顺序模型进行。** 虽然在过程当中线性模型也被加以迭代，但是它是用一些间接的方式来实现的，你在过程当中面对这些东西，大家都会觉得非常非常困难。

**第二，用户不是都把需求说得很清楚。** 瀑布模型有一个前提：用户的需求在刚一开始就提得非常清晰、非常准确、也非常完整。这个在实际操作过程中非常难实现。而且用户的需求本身是不断变化的——你们自己做着做着，也会发现一些更好的需求，这个时候再加进来，就可能破坏它原本的一系列设计和框架，带来很大的混乱，可能耗费很多不必要的时间。

**第三，客户必须等待。** 在项目接近尾声的时候，他才能拿到这个可执行的程序。我们假设这个程序当中出现了一个非常大的漏洞，而在可执行程序评审之前都没有被发现，那就会造成极其惨痛的损失。你只有做到最后一步才知道这个东西是什么样的，中间出了错误，可能整个过程都是白费的。

除了这三条，还有这些：

- **变化**：无论是需求上的变化、制作上的变化，还是人员上的变化，一遇到变化，传统的模式就显得非常僵化，难于调整；
- **不断进化的系统**：不断在改建、不断在进化的这种系统，可能也不会存在于这个框架里；
- **有限的时间**：一步一步这样走下来，对于我们制作一些很简单的东西而言，会非常耗费时间。

#### 评价与适用条件

给瀑布模型做一个评价，要分成两句话说。

**它告诉了我们软件开发过程当中都需要有哪一些步骤。** 刚才那五步——沟通、策划、建模、构件、部署——其实都是非常必要的，它把大致的蓝图给描绘了出来。

**它又非常不现实。** 因为我们现实的环境不像前面假设的那么简单，它有很多更现实、更复杂的东西，所以它并不实用。

那它是不是就没有意义了？不是。它是后面做一系列改建的基础，接下来几个模型都是从这个最基础的模型出发，再根据实际情况的一些特殊条件进化出来的。可能它就不叫瀑布模型了，但瀑布模型的原理和基石在这里。

> **结论**：需求清楚的时候，瀑布模型还是不错的：可以用它来进行软件工程项目的开发，一步一步走，它是一个非常结构化的方法，规定了每一步做什么事情。它是描述性过程模型里面比较经典的、也是最早提出来的一种方法，是我们学习其他过程模型的一个基础；但在实践中，我们很少会直接去用它。

---

### 增量过程模型

增量过程模型是站在瀑布模型的基础上构建出来的一种新方法，用来应对瀑布模型所产生的那些问题，它由两部分组成：一个是**增量模型**，一个是**快速应用开发**。这个模型在实际当中用得比较多，也比较好。

#### 五个阶段的反复迭代

瀑布模型的五个步骤是以后软件开发过程中的五个基本步骤，增量模型也是以这五个步骤为基础，不断地重复、不断地迭代，使得软件的功能一个比一个强：功能一个一个增加进去，特性一步步加强，整个软件一点一点获得功能上的提升。

画一张图来说明：横坐标是项目开发的一个日程，纵坐标是这个软件所具备的功能。

```text
功能
 ▲
 │                                  ┌─────┐
 │                        ┌─────┐   │     │
 │              ┌─────┐   │     │   │     │
 │    ┌─────┐   │     │   │     │   │     │
 │    │     │   │     │   │     │   │     │
 └────┴─────┴───┴─────┴───┴─────┴───┴─────┴──▶ 日程
      第1次迭代 第2次迭代 第3次迭代 第4次迭代
```

每一级台阶，都是五个步骤走完的一轮：**沟通**，先跟客户沟通、获知客户的需求；**策划**，协调团队怎么来开展工作；**建模**，把这个需求转化成我们的软件开发需要哪些模型；**构件**，进入 coding 的过程；**部署**，把初级的这个软件部署给客户，向他展示——这已经有了一个雏形，或者说这是第一个版本。

于是一轮走完，在项目开发的初期，我们就已经有了一个初步功能的软件。接下来就是不断地迭代这个过程，开发出更高特性级别的软件，再往下推进，最后拿到一个功能比较全面、达到客户最终要求的软件。

> **结论**：增量模型解决了瀑布模型身上两个最要命的缺点——**客户需求不定**和**客户等待时间过长**。随着项目开发过程的推进，我们能看见软件一点一点成长起来，同时还能根据客户的各种需求加以迭代。

#### iOS 系统的版本迭代

一个很具体的例子是苹果的 iOS 系统。

最早随着苹果发布 iPhone，它在 2007 年推出了第一个版本。现在很多人都在用 iPhone 系统，但是很少有人知道它的第一个版本功能是非常欠缺的：没有方向感应的功能，也没有复制或者粘贴的功能，可以说它作为一部智能机，仅仅具备了打电话和发短信的功能。

| 版本节点 | 这一次加进来的能力 |
| --- | --- |
| 第一版（2007 年，随 iPhone 首发） | 功能非常欠缺：没有方向感应，没有复制粘贴，作为智能机只有打电话和发短信 |
| 第二版 | 中文语言支持、手写输入法支持，更重要的是 App Store 和给开发人员用的 SDK |
| 2009 年 | 推送通知（可以随时随地在状态栏上直接回复）、拷贝粘贴（推出两年之后才补上）、蓝牙、语音控制 |
| 之后的版本 | 多任务、分文件夹等等 |
| 2011 年，iPhone 4S 发布 | 苹果云端的一些功能特性 |

第二版之后加入的这些特性，特别是 App Store 和 SDK，使得苹果的操作系统特别地流行起来。拷贝粘贴这个功能，是在它推出两年之后才加进去的。到最近的版本，它也还是先放出测试版系统、再转正式版。

> **结论**：苹果在这五年多的开发过程当中，手机操作系统不断地加以功能的迭代，一点一点向着它认为完美的这一步迈进——它非常合理地应用了增量过程模型这样一个软件开发方法。

#### 增量模型解决的问题

增量模型的优点，可以从人力与风险两个角度来讲。

**第一，在最初人力成本不够的时候，它可以帮助人们在短时间内开发出一个软件的雏形**，这样快速交予客户，得到客户的支持，也缓解了团队人力资源的问题。以后如果还有功能需要快速迭代开发，再投入更多的人力，可以做一个功能试点。

**第二，它可以解决软件开发过程中的一些风险问题。** 随着开发过程的推进，可能有些功能点其实不是特别需要的，可你已经投入了人力；一旦经过了漫长的时间、没有得到市场很好的反响，那么这个功能点相当于白白浪费掉了人力成本、时间成本、金钱成本。分批交付的做法，能很好地解决这个冲突——先把一部分功能放到客户和市场面前试一下，再决定后面的投入。

#### 跨版本迭代与项目边界

讲到这里，课堂上有一个追问值得记下来，因为它问到了增量模型的适用边界。

有同学提出：苹果每一个版本应该是一个统一的系统吧？可是你拿增量模型来说，增量模型应该是在**一个项目**中的吧？如果 iOS 这个项目随着版本一直加下去、几百年继续改下去，那这个项目不就没完没了了？他又进一步追问：它开发 iOS 3 和 iOS 2 的时候，有经历过重构吗？或者说整个项目有推倒重来吗？

回答是：没有推倒重来。它在原有的基础上面继续加入了这些新的功能，所以它符合增量过程模型的概念和定义。至于重构，可能到了后世的版本迭代的时候，对于原先的代码也有重构的过程，但它先前的几个版本肯定是符合增量过程模型的定义的。

最后落到的点是：这个争论真正的问题在于，**增量模型是用在一个项目中的**。各人的理解方式不一样，不必强求一致，但这条边界要清楚。

> **提示**：区分两个层次——增量模型讲的是一个项目内部把功能分批交付，一次迭代交一个可用版本；而一个产品跨好几个大版本、持续若干年的演化，是另一个尺度上的事情。把两者混在一起，就会掉进"这个项目到底什么时候算完"的绕圈里。

#### 快速应用开发模型

增量过程模型的第二部分是 **RAD（Rapid Application Development，快速应用开发）**。

RAD 也用了瀑布模型中的五个过程，它本质上就是把这五个过程快速地融合在一起，实现整个过程的非常快速的一个重复。它对开发方式有一个要求：尽可能利用现有的程序构件；同时必要的话，要为以后重复开发类似的构件做好准备，准备好可以重复重用的程序构件。

**它适合用在这些地方：**

- 小型的团队，可以利用已有的一些构件来创建我们的软件；
- 项目对时间的要求非常迫切的时候，一个大的团队也可以用这种方法来快速迭代；
- 我们软件工程的同学、学生团队，也可以利用一些开源构件，快速地完成五个过程当中的 construction 这个中间环节。

**它也有几个缺点：**

- **初期就需要大量的人力资源来协调。** A 小组开发某一个功能模块，B 小组开发另一个功能模块，这个过程需要大量的人力资源去协调、去匹配；
- **要求客户和程序开发人员都适应这个开发过程。** 客户一旦提出某种要求，他想到的可能是 RAD 这个模型，但程序员那边没有适应，就无法在必要的时间内给客户一个合理的软件成品；
- **对需要高性能的项目不适合。** 比如开发移动互联网络的程序：你为移动终端开发接口，假如用了以前给 PC 浏览器的一些接口去重用，这样开发出来的接口，对于移动互联网这种带宽比较低的环境是不符合要求的，这样做不科学、不合理；
- **需要大量新的开发技术的项目，开发风险非常高。** 也可能等你开发完成了，才发现这个项目不符合要求，那么重构的时间成本会更高。

> **易错点**：RAD 不是"把增量模型用得更快"。它和增量模型最大的区别在于，**它需要大量的资源来做这件事情**——这一点直接决定了它能不能用在某个项目上。

### 演化过程模型

#### 演化模型的现实背景

演化过程模型有它的实际背景，主要有三条。

**第一，软件开发过程中，它的业务和软件的需求是在不断变化当中的。**

**第二，开发的时间非常紧。** 它不可能给你一个非常非常长的时间让你去开发，你必须在有限的时间内拿出一个有限的版本，迅速地推出来，去应对一个非常严肃的商业竞争环境。

**第三，刚开始的时候并没有明确软件系统的一些细节。** 在开始不明确的情况之下，我们必须通过这样一个软件演化过程模型，来不断地完善它的版本。

> **结论**：所以演化过程模型是一个不断迭代的过程。

#### 原型开发

原型开发就是一种循环的过程：在这个过程当中，它把软件的版本不断地进行改善，直到它能够让客户满意、能够接受为止。

它主要适用于这些情况：客户定义了一些目标要求，但是并没有定义非常详细的输入、输出和过程当中的那些细节，有时候客户自己本身也不太清楚；在开发程序、不清楚这些情况的时候，就必须和客户进行沟通，而沟通的开始又是不清楚的，所以必须先进行一个原型的开发。第二种情况是，不确定算法的有效性、不确定操作系统的能力，还有比如类似交流的形式——这些情况都不清楚的时候，原型开发就是更好的方法。

```text
   1 沟通 ─▶ 2 快速策划 ─▶ 3 设计原型 ─▶ 4 交付客户试用 ─▶ 5 客户反馈
     ▲                                                         │
     └──────────────────◀ 提高版本，再走一圈 ──────────────────┘
```

一轮循环是这样的：先沟通，客户和开发人员沟通清楚这个软件究竟需要做什么；开发人员知道了客户的需求以后，就进行快速的策划，并且设计出一个原型来；做成一个原型以后把它交付给客户去测试；客户反馈之后，把他所需要的一些需求再和开发人员进行沟通；知道了反馈的效果以后，再不断提高这个版本。就这样一圈一圈循环下去。

> **提示**：原型不仅仅是一种开发模型，它有时候也经常作为一种技术手段来利用。

**优点**：客户能够马上看到这个软件初期的版本是长什么样的，有一个非常直接的观感；能够快速地推出一个产品来，而不需要浪费很多其他的东西。

**缺点**：正因为要快，一开始开发的时候并没有考虑以后的长期维护过程，所以到后期它的维护是非常困难的，软件的质量也不是非常高。第二点是它为了快速实现软件，采用一种折中的手段：因为本身经验有限，它会使用自己熟悉的一些语言，而这种语言不一定适合这个软件，还可能用上一些不太适合的架构，这样就会导致整个性能的下降。

所以用原型开发，有一条前提必须在一开始就讲清楚：**要让客户明白，这个原型是为后面的演化服务的，而不是"产品推出来以后就不再改"的最终东西。**

#### 螺旋模型

螺旋模型是由波姆（Boehm）教授提出来的，它主要是为了减少软件开发过程中的风险问题——软件开发其实是有很多风险的，你推出来以后不一定能够成功。

它由几样东西拼起来：

- 原型开发当中的**迭代**的过程；
- 瀑布模型当中的**控制型和系统性**；
- 以及一句话就能记住的理解：它就是在原型开发当中**加入了一个风险分析**的过程。

```text
   1 沟通 ──▶ 2 策划 ──▶ 3 设计、构建与测试 ──▶ 4 交付（新版本）
     ▲                                                 │
     │  每一圈都插入一次风险分析                       │
     └──────────◀ 半径扩大，从里往外转下一圈 ──────────┘
```

典型图示上，它以一个顺时针的方式一圈一圈地转，并且圈在不断地扩大。每一圈里面的步骤和前面模型是一样的：从沟通开始，再进行策划，然后进行设计，并且编码、测试，最后是产品的发展。因为软件在不断地完善，所以这个圆圈是在不断地扩大当中的。

随着迭代不断加深，它的产物也在变样：前期几次迭代可能只是一个产品的说明书这个阶段；再往下迭代，可能会开发出一个比较像样的原型来；这个原型经过多次迭代以后，又会不断地演化出各种各样的版本来。我们实际的软件开发过程也是这样，它会在原有的基础上开发出不同的版本，以适应不同的需求。

螺旋模型和前面几个模型不一样的地方在于：**它是贯穿于整个软件生命周期当中的。** 前面几次迭代可能还是一个概念的发展项目，随着多次迭代以后，它可能转换到新项目发展阶段，再经过多次迭代，就一步一步地往上走。

对它的分析有两条：

- **它比较适合我们开发大型的软件系统**，因为它是迭代的过程；
- **它比较难说服客户**：因为它要经常改，可控性有时候是不确定的，客户很难接受这个现实——"我已经有这么好的了，你还要一直改一直改"，他可能就不愿意这样做。而且风险如果没有被检测到，会产生非常大的问题，所以软件开发的时候需要大量的风险评估专家来给它进行评测；没有做到这一步，有时候这个产品就会失败。

---

### 软件的生命周期与演化过程的位置

讲完前面这几个模型，我们把软件的生命周期摆一下位置。

软件的生命周期，是从我开始立项这个软件，到开发，到维护，到最后消亡——这是它的整个生命周期。前面讲的过程，包括刚讲的演化的过程，实际上讲的都是软件发展的这个过程，只是从**演化**的这个角度看。

从演化的角度看，软件的发展是一个版本、一个版本地走：最初的版本可能功能很弱，后面不断地增加功能、不断地演化，一直到它消亡为止——到了这个时候，这个过程才算结束，才算完成了我们这个软件。

所以演化的过程实际上也把整个维护的过程包含在内了。这就是为什么我们讲过程模型的时候，讲到最后总要回到"版本"这个词上来：模型讲的是怎么组织开发活动，而它组织的对象，就是一个一个要走完自己生命周期的软件版本。

---

### 统一过程

#### 名称来源与三个核心特点

统一过程（Unified Process，UP）有时候也被叫做 RUP。它原来出自 Rational 公司——就是做 UML 建模软件 Rational Rose 的那批人搞出来的；后来 RUP 随着公司被 IBM 收购，厂商的名字就去掉了，改叫 UP。

这个过程跟前面讲的螺旋过程其实有点像：它也分成这么几个阶段，也是可以迭代的——一个生命周期那样迭代一次，每一次搞出来一个 increment。它也包含了前面的增量模型。它为什么叫 UP？因为它力图把前面那一大堆乱七八糟的、很多个模型，都合在一起，所以叫统一的过程。

它定义的时候有这么几个特点：

- **用例驱动（use-case driven）。** UML 里面有一个东西叫**用例图（use-case diagram）**，是给用户看的一张图：用户画出来说我这里有哪几个人、哪几个角色，他要做什么事情。比如我画一个人在这里，中间是一个系统，我要给它什么输入，这个系统要给我什么输出；可能有多个用户，就描绘出他们与中间这个系统之间的关系。这个东西不一定要用图形画出来，也可以用文字描述——这样一份东西就叫一个 use-case。统一过程就是靠用例来驱动的。
- **以架构为中心（architecture-centric）。** 在这四个阶段的过程当中，前面那些模型没有说过这一条：比如迭代模型有好几个原型、迭代好几轮，但每一次考虑的都是一个软件的整体；而统一过程要求在**细化阶段就把软件的架构定好**，后面如果没出什么问题，这个架构就一直不动它。就像做电脑一样，上面的东西都已经定好了，接下来就是往它细化。
- **迭代与增量（iterative and incremental）。** 像前面迭代模型的好处一样，把它切分成很小的阶段，每个阶段我们都要搞出成果，用这种方式控制风险。

```text
  角色 1 ──┐                ┌── 用例 A
           ├──▶┌────────┐───┤
  角色 2 ──┤   │  系统  │   ├── 用例 B
           ├──▶└────────┘───┤
  角色 3 ──┘                └── 用例 C
```

图上左边是参与的角色，中间是被使用的系统，右边是这个系统对外提供的用例；角色与系统之间、系统与用例之间用连线表示关系，这张图就叫用例图。

#### 四个阶段与两层迭代结构

统一过程分成四个阶段：**初始（inception）**、**细化（elaboration）**、**构造（construction）**、**转交（transition）**。最后出来的是一个产品。

```text
┌────────────┬────────────┬────────────┬────────────┐
│   初始     │   细化     │   构造     │   转交     │
│ inception  │elaboration │construction│ transition │
├────────────┼────────────┼────────────┼────────────┤
│  迭代 1    │  迭代 1    │  迭代 1    │  迭代 1    │
│  迭代 2    │  迭代 2    │  迭代 2    │  迭代 2    │
│  迭代 n    │  迭代 n    │  迭代 n    │  迭代 n    │
└────────────┴────────────┴────────────┴────────────┘
```

这张图上有两层：四个阶段构成一个版本的生命周期，这是外面那一层；每个阶段里面又可以切分成多个迭代，也就是把它缩成较小的时间段，这是里面那一层。两层叠在一起，我们也可以把它看成两层螺旋。每个迭代结束的时候我们都要出来点成果：比如一个学期要完成整个课程，那可以说第一周、第二周，每一周都要完成一点东西，这样可以控制住，不要说都堆到最后——那样子不行。

每个迭代都要有一个目标，我们要看能不能完成；每个大的阶段也有它的目标。如果这个目标没完成，前面做的事情没搞好，那你要继续回去把它做好。

> **结论**：四个阶段迭代下来，每一个生命周期结束的时候，就是一个可交付的软件。比如 Windows Vista：先是 beta、再是 beta，最后是零售版，到零售版这个时候才算——前面拿到的那些其实不是正式交付。而且这种开发是连着往前走的，整个过程并不是一个版本彻底结束、再从头开始下一个版本的连续过程。

#### 迭代内的工作流与投入差别

每个迭代里面有一种东西叫**工作流（workflow）**。它跟前面的 waterfall 是一样的：先跟用户沟通需求，然后分析，再设计这个架构，然后编码实现，最后测试。这五个步骤，在每一个迭代里头都要做一次。迭代很多次就构成了一个阶段，四个阶段在一起构成一个生命周期，所以它实际上是分成两层的。

需要说明一点：一次迭代里其实不只五个步骤。IBM 对它有一个正式的约定，比这里讲的还多了四个稍微小一点的支持性的工作流，那个是它原来的版本。

而且，虽然说每个阶段都是这几条工作流、每个阶段要做什么事情——建模、需求分析、设计、实现——都差不多，但**每个阶段做这些事情的量是不一样的**：比如前面设计的时候偏于模型要多一点，后面做的时候就是实现，差别很大，它用"幅度"把这个差别表示出来——哪个阶段在哪条工作流上投入多，画出来就更宽一些。

也正因为后面有可能要稍微改动一下前面的模型，或者前面做模型的时候要为实现一些原型做准备，所以前面阶段也会有编码或者测试的工作。也就是说，并不是每个阶段绝对"做"或者"不做"某件事，而是这件事做得有多有少，是一个活动量的问题。

#### 各阶段的制品与完成标准

统一过程想要强调的、跟前面那些迭代方法不同的东西，是它一定要强调**制品（artifact）**：每一个阶段完了，我们要产生人造的东西，要出成果，最后要生成出什么东西来。它给了一个约定，说清楚每个阶段要什么。

| 阶段 | 这一阶段的制品 | 具体做什么 |
| --- | --- | --- |
| 初始（inception） | 蓝图、用例模型、术语 | 蓝图是用语言描绘的；用例模型跟 UML 结合得很紧密，可以用用例图让用户把需求画出来；术语是因为这是一个 domain specific、跟用户那个特定领域有关的工程，要把该领域的术语描述清楚 |
| 细化（elaboration） | 一个可执行的架构原型 | 把整个系统的图（架构）画出来：主要分成哪几个模块，用 UML 画；做出来的原型要可以执行、模块之间要能够互动，看起来还不一定像最终的用户界面，但它不是一个不能动的东西；同时要有一个可评估的目标 |
| 构造（construction） | 各模块的构件与测试结果 | 这是最重要的阶段，大部分的编码要在这里做完；一个个模块的构件——比如登录——把它写出来，然后测试，测试完之后就可以交付，如果有 bug 再改 |
| 转交（transition） | 可交付的软件 | 走完这个生命周期，交出去的是一个可交付的软件版本 |

> **定义**：制品（artifact）指的就是每一个阶段做完以后要产生出来的那份人造的产物——文档、模型、原型、构件、测试结果都算。统一过程要求每个阶段都有明确的制品，而不只是"做了很多事"。

做出来这些制品以后还要判断：这些制品是不是成功？这个阶段我们到底完成了没有？这要有一个标准。最要紧的一条说穿了很实在：**拿给客户看，看客户满意不满意。** 从初始阶段开始，UML 图就都用得上，因为它可以很方便地告诉别人：我已经做到哪一步了，后面还有多少。

#### UML 与统一过程的配对关系

从 80 年代开始，面向对象的方法流行起来，当时就出来了 UML。面向对象的软件开发有一个最常用、最流行的做法，也有相应的环境和工具来支持它，就是 UML。到现在很多地方一直在用，它是面向对象里面到目前为止比较成功的一种开发方法。

UML 是从**开发技术**这个角度讲的——我怎么去建模。那么问题就来了：跟 UML 相配对的过程模型，应该是什么样的？于是后面就提出了统一过程 UP。所以 **UP 跟 UML 是最近的**：它就是面向对象的软件开发所采用的那个过程模型。

我们也能看到，UP 在表现形式上跟前面讲的几个模型有很大的差别，但它的内容核心跟前面是互相重叠的，也有些相似，有些只是表达上的不一样。

---

### 模型之间的继承与重叠

把这一讲讲过的模型摞在一起看，关系其实很简单：

```text
瀑布模型（描述性过程模型的基础）
  五个基本步骤：沟通 → 策划 → 建模 → 构件 → 部署
        │
        ├── 增量模型：把五个步骤反复迭代，功能一批一批加进去
        ├── 快速应用开发 RAD：把五个步骤快速融合、高速重复，靠复用构件
        ├── 原型开发：快速做出原型交客户试用，循环改进版本
        ├── 螺旋模型：原型开发的迭代 ＋ 风险分析，一圈一圈向外扩大
        └── 统一过程 UP：用例驱动、以架构为中心、迭代与增量，把上述模型统一起来
```

| 模型 | 基本做法 | 主要解决的问题 |
| --- | --- | --- |
| 瀑布模型（Waterfall Model） | 沟通、策划、建模、构件、部署，一步做完再走下一步 | 把开发步骤和顺序固定下来，需求清楚的时候非常结构化 |
| 增量模型（Incremental Model） | 把五个步骤反复迭代，功能一批一批加进去 | 客户需求说不清、客户等待时间过长 |
| 快速应用开发（RAD） | 把五个步骤快速融合、高速重复，尽可能复用现有构件 | 时间要求迫切的项目，小型团队用已有构件起步 |
| 原型开发（Prototyping） | 快速策划并做出原型交客户试用，循环改进版本 | 需求细节、算法有效性、平台能力都不清楚 |
| 螺旋模型（Spiral Model） | 原型开发的迭代加上风险分析，一圈一圈向外扩大 | 降低软件开发过程中的风险 |
| 统一过程（UP） | 用例驱动、以架构为中心、迭代与增量，四阶段两层结构 | 把前面这些模型统一到一套过程里，逐步交付、控制风险 |

> **提示**：这一章讲的都是描述性过程模型——它们描述的是"应该按什么顺序做什么"。第四章我们再看另一路：针对这些模型在实际中暴露的问题，敏捷的过程模型是怎么做的。

### 本讲提到的题目

**题目**：在我们这个课程后面要做的课程项目里面，我们合不合适用 RAD 模型？为什么？

**解析**：不合适。更主要的原因在于，我们这个课程项目**没有那么多资源**——RAD 跟增量模型最大的区别就在这里：它需要大量的资源来做这件事情。RAD 在初期就需要大量的人力资源去协调、去匹配（一个小组开发一个功能模块、另一个小组开发另一个功能模块，都要人去协调），而课程项目的人力、时间都有限。

当时有同学给出的理由是：课程作业的需求应该是一开始就完全确定、设定好的，不需要去寻找。这条理由站得住；但把落点放在资源上更直接——资源不够，就撑不起 RAD 要求的"快速融合、高速重复"。

> **提示**：判断能不能用一个过程模型，不要只看它的步骤好不好看，要先看它需要什么前提条件。RAD 的前提条件就是资源，尤其是初期协调的人力。

## 系统工程概述
> 对应分集：P06 | 原始标题：《第6讲 系统工程概述》

### 复习：所有软件过程共同的那几个步骤

开始干活之前，先把前面讲过的东西复习一遍：`software engineering` 我们到底有哪些事情要做？也就是所谓 `essence of practice`，实践中最基本的几件事。

前面讲过程模型（`process model`）时其实已经点过：不管哪一种 `process`，都有这么五个最关键的步骤。

第一步是沟通（`communication`）——先跟人沟通，搞清楚要他做什么。第二步是建模（`modeling`）——沟通完先建个模型，分析一下，把设计建出来。第三步是施工（`construction`）——真正动手，把东西做出来。第四步是测试（`testing`），还要维护。第五步是部署（`deployment`），交付出去给人使用。

> **定义**：这五步不是某种过程模型专有的流程，而是所有软件过程模型都要覆盖的公共骨架。瀑布、原型、增量、螺旋讲的是这些步骤怎么排、怎么迭代，而不是换掉这些步骤。

为什么是这几步？因为把软件工程换成"人做事"，每个人每天都这么干，一点都不抽象：

| 人做事的一般顺序 | 对应的软件工程步骤 |
| --- | --- |
| 先弄明白我要做什么东西（`understand the problem`） | `communication` 与 `analysis` |
| 我要做个计划，打算怎么做 | `modeling and design` |
| 把计划执行出来（`carry out the plan`） | 干活，写代码、做出来 |
| 看我做出来的结果对不对 | `testing`、质量保证（`quality assurance`） |
| 交出去用 | `deployment` |

> **结论**：这五步、以及上面对应的两张面孔，就是整个学期最该关注的基本东西。后面每一章，都在给其中某一格补充细节。

```text
communication ──▶ modeling ──▶ construction ──▶ testing ──▶ deployment
   沟通            分析/设计        编码实现        测试        交付使用
     │                │               │             │            │
     └────────────────┴───────────────┴─────────────┴────────────┘
                后续课程逐个展开，但骨架始终是这五步
```

读图说明：从左到右是推进顺序，下一行标出每一步在课程里的常用叫法；这五步之上的各类过程模型只是给这条链加上回退与迭代。

#### 后面章节与这五个步骤的对应关系

这套框架不只是复习，它同时是后面整门课的路线图，每一个方面都会专门讲：

- `communication`：需求获取与需求整理，专门有需求工程的部分；
- `planning`：做计划、排进度、估工作量的部分；
- `modeling`：分成分析与设计两块；
- `construction`：编码与测试，代码写出来不等于做完，测试要跟上；
- `deployment`：交付与部署，同样会单独展开介绍。

### 核心原则：不用背，但要听听有没有道理

`core principles` 这一组原则，你不需要背，你只要听听它有没有道理。但每一条都值得记在心里，因为它们决定了你做出来的东西是被人接受还是被人退回来。

#### 对客户和用户产生价值

第一条：不管你做什么，你始终要记得，你的任何建议、任何方案，都要 `provide value to the customer and the user`——对客户和用户做有价值的事情。

说服人家掏钱让你做什么东西的时候，最傻的一种说法是："这个技术现在是最流行的。"接着说："我做好了以后，你这个系统的内部结构会非常漂亮，以后便于维护，便于什么，有什么什么好处。"客户心里只会冒出一个词：`So what`？跟我有关系吗？

你自己是技术宅，你自己歪歪一下，觉得这个技术很新、想用一下，内部结构很漂亮——可这对我有什么影响？比如说我要做这个计算，原来要 3 秒钟算出一个结果，你能给我缩短到 0.3 秒吗？如果不能，那你再跟我说什么？它跟我有什么关系？

反过来说，你说这个计算速度的确可以大幅提高，我可以提高 10 倍，听上去很好。OK，原来这个计算 1 毫秒就完成了，你现在 0.1 毫秒完成。这对客户有意义吗？1 毫秒我也感觉不到，0.1 毫秒我也感觉不到。为了这 0.1 毫秒，你要我多花多少钱？那算了吧，我还是保持原样就可以了。

> **易错点**：技术指标提升的百分比，和用户能感知到的收益，是两回事。"快了 10 倍"是技术语言，"这 0.1 毫秒对我不值这个钱"是客户语言——讲方案时你要说第二句。跟人谈项目，态度始终是：我这么做会给你带来什么好处？这一点你先想清楚。如果要做的事情对客户来说没有什么意义，那你是谈不下来的。

#### KISS 原则：先想傻一点的解决方案

第二条是 `KISS` 原则——`Keep it simple, stupid!` 你不需要有很 `fancy`、很 `smart` 的解决方案，越简单越好。这一条最好是用两个笑话记住。

**太空笔**。宇航员到了太空，发现圆珠笔写不出来字：因为没有重力，油墨不出水。美国人怎么解决？花重金请研究团队，最后研制出"太空笔"——在失重状况下能够照常出水，很神奇，也很花钱。俄国人碰到同一个问题，解决方案是：用铅笔。当然，如果你看过印度那部《三傻大闹宝莱坞》，"用铅笔"这个办法后面还有后话，没看过的自己去看。

**空肥皂盒**。有个企业买了一条自动生产线，肥皂做好以后自动装盒，从流水线另一头产出。但它有时出问题：肥皂没进盒子，空盒子照样流出去，这就算事故了。麻烦在于，从表面看一堆盒子完全一样，你怎么知道哪个是空的？于是这家大企业请了一位博士，博士立了一个项目，还申请到国家自然科学基金的资助，弄了一个很大的项目，花了好多钱设计出一套精密仪器，装在生产线上精确判断哪个肥皂盒是空的。

另外一个乡镇企业的小厂子买了同一套流水线，碰到同样的问题。老板找不到博士，也请不起博士，就找了一个小工说：你想想办法。这小工想了个什么办法呢？他抱了一台电扇放在生产线旁边，照着上面吹。肥皂盒里没有肥皂就是空的，空盒子直接被吹出去了；有肥皂的，就顺着往下走。

> **结论**：这叫非常典型的 KISS 原则。先想傻一点的解决方案，不要一上来就想得很花哨，不要把事情想得很复杂。`Keep it simple, stupid!` 是最好的原则。

#### 保持大方向正确

第三条：随时注意保持你的 `vision` 是正确的。`vision` 是什么？大方向。

你要确保，不管你正在做多细的细节，你先得确认自己是朝着一个正确的方向在走。方向走反了是很悲剧的，你做得越卖力，错得越厉害，毁得越厉害。所以要随时把自己从细节里抽离出来看一眼：我是不是还在正确的方向上。

> **提示**：这一条在项目里最直观的体现是：越到后期，方向错误的代价越大。抽离出来看方向的频率，应该跟你在细节上下沉的深度成正比。

#### 你做的东西是给别人消费的

第四条：`What you produce, others will consume.` 你做的东西是给别人用的。

不只是说你最后做出来的系统是给别人用的。你做的需求文档是给别人读的，你做的设计方案是要让别人看懂的。随时注意这一点。

> **结论**：这门课其实也不只是教大家怎么做事，更重要的是怎么做人——做事的时候随时替别人着想。你到底为什么做事情？不是为了自己歪歪一下，或者自己爽一下，体验一下。你做出来的东西是要给别人用的，随时记住这一点。

#### 对未来保持开放：课堂练习

第五条：`Be open to the future`。这一条我们现场做了个练习。给大家三五分钟，自己来补充这句话是什么意思，把"future"细化一下：`future` 指的是哪些地方需要你 `be open`？做软件的时候，哪些方面需要注意 `be open to the future`？随便写，写至少两条，两条以上更好。

大家交上来的答案虽然不多，但方向基本对，可以顺着往下列几条：

- 硬件系统可能要升级——你现在选的硬件配置、接口余量，撑不撑得住几年后的升级；
- 软件系统可能要升级——版本要不要留扩展点，能不能平滑替换某一层；
- 技术发展这么快，人们的生活习惯会不会因此改变、在多大程度上会改变——用户几年后的使用方式，可能和今天不一样；
- 如果你做的是 `web application`，就要想到是不是有大数据（`big data`）可以用，现在很时髦，那你打算怎么弄。

> **提示**：这几条不是让你预留一堆没人用的扩展点。它要求的是：在设计时把"未来会变的那部分"识别出来，并且清楚它会从哪儿变、你留的余地在哪一层。

#### 为重用做计划，先动脑再动手

第六条：`Plan ahead for reuse`——注意重用。这一点在我们讲模块化的时候会再展开，是很重要的一条。

最后一条最重要：先动脑再动手，`Think!` 多想想是值得的。不要很着急就开始，慌手忙脚地动手干活。

### 系统工程的层次化视角

剩下一点时间，看一下所谓的系统工程。这部分内容前面稍微有点重复，这里是要强化一下大家的层次感。

> **定义**：软件工程是系统工程的一种。系统工程一个很重要的特点，就是看问题时有非常明确的层次化观念。

一个公司就是这种层次最好的例子。它最顶层的老板脑子里有一个整体的战略想法：我们公司要"改变世界"——很多公司都有这句口号，说"跟着我做，我可以叫你改变世界"。但你要改变的是世界的哪几个方面？要在哪个方面改变人们的生活？你是要做互联网的，那么这一波人去做互联网，这一波人去做操作系统，这一波人去做硬件，这一波人去做别的什么。有很多事情可以做，你到底要在哪几个方面改变世界，这就是你的 `world view`，是顶层老板要关心的事。

```text
世界/战略层   world view           老板：我们要改变世界的哪几个方面
     │
领域层        domain of interest   每个 product domain 一个负责人
     │
要素层        element view         每个 product 的 software / hardware
     │                             people / timeline …
     ▼
细节层        detailed view        项目组内部真正干活的那一摊
```

读图说明：上面一层给方向与边界，下面一层在自己那一摊里把方向落成具体决策；层数越往下，关注的范围越小、细节越细。

#### 领域视图：一个领域不是一个产品

战略决策做好以后，每一个 `product domain` 就会有一个负责人去做下面的事情，这就是 `domain of interest`。比如操作系统，Windows 操作系统丢给一个队去弄。

关于软件产品领域，`Office` 是更好的例子：它不是一个 `product`，而是一堆 `products`——有 Word，有 PowerPoint，有 Excel，等等。文件处理这一整套，是由好几个产品组成的，这是一个领域视图（`domain view`）。

#### 要素视图：一个产品由哪些东西构成

`domain view` 里面，每一个产品有它自己的 `system element`。所谓要素，包括设计时要考虑的软件（`software`）、硬件（`hardware`）、人（`people`），还有时间线（`timeline`）等等，很多因素它都要关心——这些都是把一个产品做出来必须关心的因素。这些要素下面各有相应的管理（`management`），这就是要素视图（`element view`）。

#### 细节视图：项目组里的具体执行

每一个要素下面，就是项目经理（`project manager`）带着一个团队去干活，这里有细节视图（`detailed view`）。

> **结论**：一个公司里有好多不同层次的人。每个层次的人只关心自己的一摊活儿，各人关心的事情不一样，关注到的细节程度也不一样。要始终养成这么一个习惯：看所有事情都用这个层次化的方式去看——后面内容可以过得很快，因为你已经能看到每一层各自的关注点了。

```text
层次          谁在看            在看什么
────────────────────────────────────────────────────────────────
world view    顶层老板          业务总目标、要改变世界的哪几个方面
                               定义整体产品架构 architecture
                               关心 data architecture：处理什么类型、
                               哪些领域的数据（不是 data structure）
                               关心 technology：最擅长、要重点发展哪几项
────────────────────────────────────────────────────────────────
domain view   领域负责人        本领域有哪几个 products
                               它们之间怎么划分、怎么协同
────────────────────────────────────────────────────────────────
element view  产品/要素管理     software、hardware、people、timeline …
────────────────────────────────────────────────────────────────
detailed view 项目经理与团队    具体一摊活儿的执行细节
```

读图说明：从上到下是同一件事被逐层展开的四个视角，每一层都有自己的一份"要搞清楚的问题清单"。

#### 从老板的视角看业务：几条逐步细化的线

站在老板的层面上，他要关心的事情也可以看到一层一层加细的过程。他从业务（`business`）的角度看问题时，大致是这样的：

- 我有一个总的目标，我要 `define architecture`。注意这个 `architecture` 不是程序的、不是机器的体系结构，不是机器的结构，也不是软件的体系结构，而是你整个公司、整个产品的架构。
- 要搞清楚 `data architecture`——这个不是 `data structure`，不是数据结构。它问的是：你打算处理什么类型的数据？打算处理哪些领域的数据？
- 为了处理这些数据，你要做什么样的应用？这些应用在你整个公司的产品架构里是怎么架起来的？这是很宏观的考虑。
- 还包括 `technology`：我这个公司最擅长的是哪几项技术，希望能重点发展的是哪一个方面的技术。

这些就是老板要关心的事情。再往下，它就是一条一层比一层细的链条：先是信息处理的策略计划（`information strategy planning`）——我要处理哪些方面、哪些领域的东西；然后每一个领域有一个业务分析（`business analysis`），再往下是业务层面的系统设计（`business system design`），越来越细，最后一直落到施工（`construction`）阶段。这就是业务的视野。

再往下到产品层面，其实不用多说：`product` 就是把你想要做的事情归拢一下，做成一个产品，这就是产品工程（`product engineering`）。

> **提示**：这几张层次图里的字通常很小，你不需要看清那些字，只要看到这个架构就够了。以后你要很习惯地看到这个架构——做事情的时候，脑子里自动产生这样一个架构，那就对了。所有的动作都是这种层次化的，非常明显。

### 输入-处理-输出框架与架构流图

系统建模时，一般有一个通用的模板。通常我们大家都把一个系统理解为"输入-处理-输出"（`input-process-output`）这么一个过程：有输入，中间处理一下，最后产生一个输出。

> **定义**：绝大部分系统都可以被装进这个框架。所以你会看到，几乎所有的系统都能用同一套版式画出来。

#### 系统架构的一般版式

按这个框架画图的时候，有一条固定的摆法：

- 顶层画的是你的接口（`interface`），也就是用户界面，是整个系统最前端的那部分；
- 最底下画后端（后台）的东西，包括管理（`management`）、维护（`maintenance`），还有系统的自我检测（`self-test`），也叫诊断（`diagnostic`）；
- 一边摆放所有处理输入数据、把外部数据转换成内部要处理类型的那部分东西；
- 另一边摆放所有处理输出的东西；
- 中间是你的核心模块，所有真正的处理（`process`）功能都放在这里面。

```text
+-------------------------------------------------------------------+
|                    interface  （用户界面 / 最前端）                |
+----------------+--------------------------------+-----------------+
| 输入侧         |        核心处理模块            | 输出侧          |
| 输入数据的     |   所有 process 功能放在这里    | 所有处理输出    |
| 转换与预处理   |                                | 的模块          |
+----------------+--------------------------------+-----------------+
|      management / maintenance  /  self-test（diagnostic）         |
+-------------------------------------------------------------------+
```

读图说明：横向是"输入 → 处理 → 输出"的数据走向，纵向是前端界面与底层管理诊断；这只是总框架，具体模块按项目往里填。

这个版式的用处很实际。比如你以后做毕业设计，你说我做了某个大系统里面的一个模块，那就要讲清楚：你这个模块放在大系统里是什么架构、处在哪个位置——用这么一张图就可以画清楚。前提是整个系统图不能太复杂。不太复杂的情况下，你把不同的模块放在不同的地方，再用一些箭头连线表示它们之间是怎么关联的。

#### 传送带分拣系统：一个书上例子

书上给了一个例子讲这套画法：传送带分拣系统（`conveyor line sorting system`）。一堆集装箱从传送带过来，每个箱子上有一个条形码。系统要做的事情是这样一条链：

1. 这边的扫描器（`scanner`）读到条形码，同时还要读传送带的速度；
2. 有一个解码器，解码器解完以后就知道这个箱子应该属于哪一个、应该放到哪个大箱子里去；
3. 到数据库（`database`）里查一下，知道它的箱位（`bin location`）在哪里；
4. 因为它一直在计算传送带的速度，所以能估计出这个箱子什么时候到；
5. 到时候就通知那个分送装置（`shunt`）——可以理解成一个分送的机器手臂——把箱子送到对应的第几号大箱子里。

怎么描述这个系统？乍一看很复杂，但你还是看那个框架就够了。前端得有一个界面让人看见结果；底层要有自我诊断的模块，用来对付系统出错；输入这一侧是条形码的读取，以及速度传感器（`sensor`）信号的处理；输出这一侧是最后的结果——机器手要把它送到哪里去，同时记录要写进数据库，有一份报告（`report`）；真正处理这些事情的模块放在中间，再加上它们之间怎么沟通。

```text
+-------------------------------------------------------------------+
|                      用户界面（结果可见）                         |
+------------------+---------------------------+--------------------+
| 输入侧           |        核心处理           | 输出侧             |
| 条形码读取       |  解码器：判定属于哪个箱   | 分送装置 shunt：   |
| 传送带速度 sensor|  查 database 得 bin       | 机器手送进第几号   |
| 信号处理         |  location；结合速度估计   | 大箱子             |
|                  |  到达时刻 → 通知 shunt    | 记录写入数据库     |
+------------------+---------------------------+--------------------+
|        management / maintenance / self-test（故障诊断）           |
+-------------------------------------------------------------------+
```

读图说明：这是那个分拣系统落到通用版式上的粗架构，箭头在真实图上表示模块间的调用与数据传递；输入侧解决"读得准不准"，输出侧解决"放得对不对"，中间解决"送到哪里去"。

> **定义**：这种图叫架构流图（`architecture flow diagram`）。它有个约束：里面不能有很多模块，模块一多，图看上去就很乱。

#### 讲架构图的做法：一次不要全出来

刚才那张图，如果我一点鼠标整幅就出现在大家眼前，其实这不是一个很好的介绍方式。原因是我本来也没打算把这个系统讲清楚——我的重点不是介绍清楚这个系统，而是让大家看一眼这张图大概是怎么用的。

但如果是做报告（`presentation`），你要跟大家解释清楚你这个系统的时候，肯定不能这么干。你应该怎么干？

> **结论**：先出来一个空的框架，然后动态地放——你讲到哪个地方，哪个地方的系统模块才出来；那些连线（流水线）要根据你演讲的顺序一点一点出来展现给大家。这样读者才能在短时间内理解你要讲的话。

不可以像我刚才那样哗一下什么东西都出来，大家会觉得很晕，是不可能看懂的。

### UML：描述系统的几类图

后面要用到的一些工具里，最重要的一个是 `UML`（`Unified Modeling Language`，统一建模语言）。

关于 `UML`，真正讲它怎么用其实可以专门开一门课——软工原来就专门有一门课教大家怎么用。在这里只是很快地看一下它有哪些东西。

| 图的种类 | 描述的对象 | 本讲看到的要点 |
| --- | --- | --- |
| 部署图（`deployment diagram`） | 硬件 | 最后交出去的机器由哪几块组成 |
| 活动图（`activity diagram`） | 动作/活动 | 起止记号、动作框、时间线、分支与汇合 |
| 类图（`class diagram`） | 类 | 名字、属性、方法三块 |
| 用例图（`use case diagram`） | 用户与软件的交互流程 | 由用户脚本演化而来的图形表达，可分层细化 |

#### 部署图：描述硬件组成

有一种图叫 `deployment diagram`，专门用来描述硬件块。

还是拿刚才那个流水线系统为例。你最后交给对方的是一台机器，这一台机器是一个处理器（`processor`）。这个 `processor` 里面大体分成两块：一块专门管分拣（`sorting`），一块专门管显示控制（`display`）。分拣的这一块又分成两个：一个读传感器（`sensor`），一个控制手臂——也就是控制那个分送装置。

这就是一张专门描述硬件的结构图，用来说明我这个硬件是由几块组成的。

#### 活动图：描述动态执行过程的记号规矩

还有一个图叫 `activity diagram`，描述的是动作、活动。这个图的特点就是"规矩"，记号系统很固定：

- 开始点是一个黑疙瘩，一个黑色圆饼，表示开始；
- 这个圆饼外面套一个圆圈，表示结束；
- 每一个动作都写在这么一个框框里面；
- 用箭头表示它们发生的顺序；
- 粗的黑线表示时间线：走到这个时间点，这两件事情同时开始。

那一条粗黑线是怎么用的？它表示在这个时间点上，下面这两件事情同时开始。还有一种表示"或"的关系：比如这个条形码，或者是对的，或者是读错了、无效（`invalid`），会有两种情况，于是从这里分出去两条路。

反过来也有汇合：这几件事情在这一个点上都等齐了，然后才开始执行下一步。

```text
  ●  开始（黑色圆饼）
  |
  v
  +------------------+
  | 动作：读条形码   |
  +------------------+
     |
     +-------------- 或 --------------+
     |  正确                          |  读错 invalid
     v                                v
  +------------------+          +------------------+
  | 动作：查 bin     |          | 动作：报无效     |
  | location         |          |                  |
  +------------------+          +------------------+
     |                                |
     +--------- 多条分支等齐 --------+
     |
     ========== 粗黑线 ==========     达到这个时间点，线下活动同时开始
     |
     v
  +------------------+
  | 动作：通知 shunt |
  +------------------+
     |
     v
  ◉  结束（圆饼外面套一个圆圈）
```

读图说明：`●` 与 `◉` 分别是开始与结束的记号，方框里写动作，箭头表示发生的顺序；`或` 标出从一条路分出多条路径的分支，多条路径汇到同一点表示等齐后才往下走，`═══` 那条粗黑线表示达到该时间点时线下的活动同时开始。

这就是活动图大致的规矩，它用来描述你那个系统动态执行的过程。

#### 类图：一个类的三块内容

类图用来描述一个类（`class`），如果你正在学 C++，理解起来会很容易。一个类基本上就三块：最上面是名字，中间是属性（`attributes`），下面是它的方法（`methods`），也叫操作（`operations`）。

```text
+-----------------------------------+
|            类名 Class             |
+-----------------------------------+
|  attributes：属性                 |
|    - 属性1 : 类型                 |
|    - 属性2 : 类型                 |
+-----------------------------------+
|  operations / methods：方法       |
|    + 操作1(参数) : 返回类型       |
|    + 操作2(参数) : 返回类型       |
+-----------------------------------+
```

读图说明：三个横格从上到下依次是类名、属性、方法/操作——记住这三格，画类图时先把格子画出来再往里填。

#### 用例图：由用户脚本演化而来的画法

还有一个是 `use case`。`Use case` 在很早以前叫 `user scenarios`，翻译过来叫用户脚本。

用户脚本是什么？就像你当导演写电影剧本一样，每一个分镜头是怎么走的。用户从一开始启动，进入一个什么样的情境，我就开始用这个软件；然后他第一步做什么，第二步做什么，这就是他怎么用的一个流程。

当然，这个脚本可以很复杂，因为中间是有判断的，行动会有分支。你要把所有的分支都描述清楚的话，那就有好多个脚本，不是一个脚本能写完的：他执行到这一步的时候，我可以有三个选项，那么对应每一条选项，你都要往下再写一个脚本。

以前这些都是用文字描述的。而对大多数人来说，看一大篇文字是很痛苦的，而且也不会很认真地看。所以后来就把它简化一下，做成图形的方式——大家看图会稍微容易一点，理解起来容易一点。基本思路是：用图、半图形半文字的形式，把整个执行的流程画清楚，而不是像以前完全用文字去描述。

那这个例子的图呢，还是刚才那个流水线的例子，这是非常简单的第一层次的 `use case diagram`：系统的操作员（`operator`）进来以后，他可以直接在面板上做哪几件事情——对着这个图，就是他有这么几件事情是直接做的。

要更细化地分析和设计的时候，这个图可以有好几层。比如 `request barcode`，它后面还需要调用哪些功能去完成这个功能？它后面调用的功能是不是还要调用其他的功能？它就可以一层一层地伸下去。

```text
                        ┌────────────────────────────┐
    ┌──────────┐        │  直接可在面板上完成的操作  │
    │ operator │───────▶│    （第一层用例）           │
    │  操作员  │        └────────────┬───────────────┘
    └──────────┘                     │
                                     ▼
                          ┌────────────────────┐
                          │ request barcode    │
                          └─────────┬──────────┘
                                    │ 需要调用的功能
                                    ▼
                          ┌────────────────────┐
                          │ 更下一层的功能 …   │
                          └────────────────────┘
```

读图说明：左边的小人（`actor`）是外部参与者，右边第一层矩形是操作员可直接完成的操作，箭头往右下方逐层展开，表示某个用例还要调用哪些功能来完成它，以及那些功能是否还要继续往下调用。
