## 第 1 章：第30讲 进度与风险控制-1
> 对应分集：P30 | 原始标题：《第30讲 进度与风险控制-1》

软件研发项目的成败，往往不取决于算法是否精妙、代码是否优雅，而取决于计划是否可行、进度是否可控。需求分析、设计、测试这些工程活动在前面的课程中已经逐一拆解，但把所有这些活动按时、按质、按预算串起来的，是项目管理中的进度计划（project scheduling）与进度追踪（tracking）。这一讲聚焦两个核心问题：项目为什么会delay，以及用什么工具和量化模型把"大概完成了一半"这种模糊感觉变成可度量、可纠偏的客观结论。

### 一、进度失控的根源：项目为什么会delay

几乎每一个做过真实项目的人，都对"项目延期"有切肤之痛。延期不是偶然，而是若干结构性原因反复作用的结果。把常见诱因逐条列出，几乎每一条都能在真实团队里找到共鸣：

1. **不切实际的deadline（unrealistic deadline）**。制定进度计划时，常常受到用户方或软件项目之外其他干系人的干扰。例如客户强硬要求"六月底、七月底必须上线"，于是进度表从一开始就不是基于工作量估算出来的，而是被外部压力"倒推"出来的。这种 deadline 违背工程规律，注定难以守住。

2. **需求变化没有反映到进度计划中**。用户需求频繁变化是常态，从正常流程看，变化应当体现为进度计划的相应调整。但实际操作中，除非是很大的变更，小的变化很难及时回填到 schedule 里，于是计划与实际之间的偏差被悄悄累积。

3. **工作量（effort）估计过低**。实际操作中的工作量远超预期，导致原先排定的时间点根本完不成。这是估计能力不足与乐观偏差叠加的结果。

4. **未预见的技术风险**。例如某些关键技术没有事先做技术攻关（技术预研），等到实现阶段才暴露困难，直接拖垮进度。

5. **人力安排困难**。人员到位、技能匹配、协作摩擦等人力因素，同样会转化为进度损失。

以上五类原因，在课堂大作业和实验室真实项目中反复出现。理解它们的共性，是做好进度管理的第一步：进度问题不是执行力问题，而是计划与风险识别的问题。

### 二、制定进度计划的基本原则

project scheduling 不是简单地把任务排进日历，它有一组必须同时满足的原则。任何一个原则缺失，都会埋下延期的隐患：

- **compartmentalization（任务分舱/任务分解）**：先把项目拆成明确的 task 列表。没有清晰的 task 清单，就谈不上排程。
- **interdependency（任务依赖识别）**：识别 task 之间的先后顺序约束。有些任务必须先做、做完后另一些才能开始；如果把有依赖的任务排成并行，就会出错。
- **effort validation（工作量与资源校验）**：确认资源确实可用，且资源能够完成这些 effort。资源可以是开发工程师、QA 工程师或其他研发人员。
- **responsibility（责任到人）**：在 schedule 里明确定义"具体哪个人做哪个 task"。
- **deliverables（交付物定义）**：每个 task 需要产出什么。例如需求分析阶段要产出若干分析模型；设计阶段要有概要设计、详细设计，乃至接口设计。
- **milestone / checkpoint（里程碑与检查点）**：若要严谨地跟踪和控制项目，必须设定里程碑。例如"需求分析做完""编码阶段做完"就是大的里程碑。一旦里程碑比计划时间点延后，项目极可能整体 delay，必须及时采取措施。

这六条原则共同回答了计划的三件事：做什么、谁来做、做到什么程度算完成。

### 三、工作量与交付时间的权衡曲线

一个反直觉但必须正视的事实是：项目并非"投入越多人力、越快完成"。研发过程中，由于 task 之间存在依赖、资源（人）的效用（utility）有上限，effort（投入）与 delivery time（交付时间）之间是一条有折中区的曲线，而非单调递减直线：

```
effort (投入)
  ^
  |   impossible 区
  |  |\            （再怎么加人也无法更早）
  |  | \___ 最短时间/最高代价
  |  |      \___
  |  |          \____
  |  |               \________ 折中区（实务取此）
  |  |                        \________
  |  |                                 \____ 最低代价/最长时间
  +-----------------------------------------------> delivery time
```

- 曲线最左端代表"用最短时间完成"，此时 effort 惊人地高；再往前就是 impossible 区——即便不计代价也无法再提前。若要求提前 25% 完成，成本已经非常高昂。
- 曲线最右端代表"代价最低"，但此时大量 task 无法并行，交付时间被拉得很长。
- 实务中通常取一条折中方案，在 effort cost 与 delivery time 之间 balance。

这条曲线对 Web 应用尤其有现实意义：Web APP 的实效性敏感，常常要求三个月或六个月的短期交付。若客户既要极短工期又要极低投入，这种要求在工程上"不切合实际"。项目经理的价值之一，就是向干系人说清楚这条曲线的存在，把不现实的期望拉回折中区。

### 四、各阶段工作量的真实分布

初学者容易把"软件研发"等同于"写代码"，但真实项目里编码阶段在总工作量中占比其实很小。一个典型分布如下：

| 项目阶段 | 工作量占比 | 主要活动 |
|---------|-----------|---------|
| 前端活动（front end） | 40% – 50% | 与客户的沟通（customer communication）、需求分析（analysis）、设计评审（design review）、与用户确认（confirm） |
| 构建/编码（coding） | 15% – 20% | 真正的程序编写 |
| 测试与安装（testing / installation） | 30% – 40% | 单元测试、集成、安装部署，其中集成（integration）代价尤其大 |

这个分布带来一个重要提醒：很多团队在第一次展示（demo）前的集成阶段异常挣扎（struggling），因为各小组之间要做大量集成、事先定义的接口也会暴露许多问题。把 30%–40% 的测试/安装 effort 提前规划进去，而不是到了后期才临时补救，是避免延期的关键。

### 五、任务集定义与工作分解结构（WBS）

定义 task set（任务集），需要根据项目类型（project type）的严格程度，确定项目里到底要完成哪些 task。以编码阶段为例：若质量要求很高，则应当安排一人编码、另一人做 peer review（同行评审），召开评审会（review meeting），并做单元测试、做 class 之间的协作测试。task set 要求尽可能详细——项目执行中真正要做的所有 activity 列得越全越好；若漏掉较多 activity，就容易引起 delay。

当一个项目以上述"层层分解"的形式列出，即大方面 → 要点 → 小点（如 review、derive a list 等），就形成了 **Work Breakdown Structure（WBS，工作分解结构）**。把整个 structure 完整列出来，task set 也就基本识别完成了。WBS 是后续排程、估算、责任分配的基础。

### 六、任务依赖与网络图

task 之间的 dependency 必须显式识别，否则就无法判断项目在研发阶段的并行度有多高。用 task network（任务网络图）可以把各 task 的完成先后顺序和依赖关系定义清楚。典型例子如下：

```
               ┌─ 1.3a ─┐
1.2 ───────────┼─ 1.3b ─┼──→ 1.4
               └─ 1.3c ─┘
```

含义：只有当 1.3a、1.3b、1.3c 三个 task 全部做完，才能进入 1.4。识别清楚这种 dependency 后，在安排 resource 做真实 task 时，才能正确排定先后顺序，避免把本应串行的任务错误地并行化。

### 七、甘特图与工期规划

把任务落到时间轴上，用的是 timeline chart，也就是**甘特图（Gantt chart）**。它表达每个 task 从什么时间到什么时间、由谁来做：

```
任务    第1周   第2周   第3周   第4周   第5周
T1     ████████████████
T2              ████████████████
T6                            ████████████████
                                  ↑ T6 起点必须在 T1 完成后
```

对于有依赖关系的 task，甘特图必须表达出依赖含义：例如 task 6 依赖于 task 1（task 1 做完才能做 task 6），那么 task 6 的起始时间一定在 task 1 完成时间之后。把所有 task 的时间轴画完后，最后一个任务的完成时间就是整个项目的 duration（历时）。

业界普遍使用自动化工具来画甘特图，例如微软的 Project（如 Project 2000 及其后续版本）。使用这类工具，只需把任务列出来、填好时间、设好 milestone/checkpoint、设好任务间依赖性，工具会自动规划出项目的整体历时。这张时间表是软件产业中项目计划的必备文档。

### 八、项目追踪与里程碑评估

进度计划做完后，必须靠 tracking（追踪）来检验真实项目状态是否偏离计划。tracking 的主要做法是：

- 召开周期性的项目状态会议（periodic project status meeting），由团队成员汇报进展与问题；
- 通过评审（review）结论来判断，例如编码阶段评审的结论是什么；
- 对照正式的里程碑（formal project milestone）：编码阶段结束了吗？测试阶段、部署阶段、集成阶段结束了吗？

里程碑通常设有明确时间点。例如某项目设"demo 1 完成"的里程碑为 6 月 19 号，当天下午/晚上助教 review 第一个 demo 后，就能确认该里程碑是否真正 close（关闭）。若有偏差，则比较 actual start date（实际开始日期）与 planned start date（计划开始日期）的差异。

对于采用面向对象分析与设计（OOAD）的项目，技术里程碑通常可归为四类：

1. **分析完成（analysis milestone）**：分析模型已建立，模型间关系清晰，可重用的类已被识别——分析阶段结束。
2. **设计完成（design milestone）**：设计了多少个类、类之间如何协作、类的属性与操作（operation）均已设计完成。
3. **编码完成（coding milestone）**：编码结束。
4. **测试完成（OO testing milestone）**：包括类本身的测试、类间协作测试、模块内集成测试、功能/系统级测试均完成，该里程碑即可 close。

无论课堂项目还是工业项目，只要采用 OO 方法，都绕不开"需求分析→设计→编码→测试/集成"这几大里程碑。

### 九、挣值分析（EVA）：把进度变成可量化数字

仅靠"感觉项目完成了一半"来评估进度极不精确。要在项目早期（甚至进度仅 15% 时）就获得可靠的绩效读数，需借助量化的**挣值分析（Earned Value Analysis, EVA）**模型。EVA 的核心术语如下：

| 缩写 | 全称 | 含义 |
|------|------|------|
| BCWS | Budgeted Cost of Work Scheduled | 计划中应完成工作的预算成本（按人天计） |
| BAC | Budget at Completion | 所有 task 的 BCWS 之和，即整个项目的预算总成本 |
| BCWP | Budgeted Cost of Work Performed | 已经完成工作的预算成本 |
| ACWP | Actual Cost of Work Performed | 已完成工作的实际成本 |

其中 BCWS 与 BAC 是预先在项目计划中定义好的，供后续计算分析指数使用。

**进度相关指标：**

- 计划完成百分比（percent scheduled for completion）：
  $$P_{sch} = \frac{BCWS}{BAC}$$
  表示按计划在此时点"应该"完成的比例。

- 实际完成百分比（percent complete）：
  $$P_{act} = \frac{BCWP}{BAC}$$
  表示实际已经挣得（完成）的比例。

- 进度绩效指数（Schedule Performance Index）：
  $$SPI = \frac{BCWP}{BCWS}$$
  反映项目利用计划资源的效率。

- 进度偏差（Schedule Variance）：
  $$SV = BCWP - BCWS$$

**成本相关指标：**

- 成本绩效指数（Cost Performance Index）：
  $$CPI = \frac{BCWP}{ACWP}$$
  反映成本控制的效率。

- 成本偏差（Cost Variance）：
  $$CV = BCWP - ACWP$$

**算例理解**：若某 task 计划预算是 5 个人天（即 BCWP 的预算基准为 5），而实际执行花费了 6 个人天（ACWP = 6），则
$$CPI = \frac{5}{6} < 1$$
说明成本控制效率低于计划，实际比预算超支。同理，若 BCWP < BCWS，则 $SPI < 1$，表示进度落后；若 BCWP > BCWS，则进度超前。

这些指标直观但关键：它们把"项目完成度""进度快慢""花钱效率"统一到同一套预算基准上，使项目经理能在偏差刚出现时就量化问题、定位是进度偏差还是成本偏差，从而采取针对性纠偏措施。

### 十、从进度管理走向风险管理

进度控制之外，项目管理另一个同等重要的方面是 **risk management（风险管理）**。一个合格的项目经理，一定是合格的风险评测与风险预测人员；否则项目会频繁暴露在风险之中。本节只引出这一主题——风险的定义、识别、评估、缓解与监控，将在后续章节系统展开。需要提前建立的认识是：绝大多数进度延期，追根溯源都能在风险识别阶段找到预警信号；把风险管住，进度自然更可控。

### 随堂自测

**1. 某项目 BAC = 100 人天。到第 8 周计划应完成 BCWS = 40 人天的工作，实际已完成工作的预算成本 BCWP = 32 人天，实际花费 ACWP = 38 人天。求：计划完成百分比、实际完成百分比、SPI、SV、CPI、CV，并判断进度与成本状态。**

解析与答案：
- 计划完成百分比 $P_{sch} = BCWS/BAC = 40/100 = 40\%$；
- 实际完成百分比 $P_{act} = BCWP/BAC = 32/100 = 32\%$；
- $SPI = BCWP/BCWS = 32/40 = 0.8 < 1$，进度落后；
- $SV = BCWP - BCWS = 32 - 40 = -8$ 人天（负值表示落后）；
- $CPI = BCWP/ACWP = 32/38 \approx 0.84 < 1$，成本超支；
- $CV = BCWP - ACWP = 32 - 38 = -6$ 人天（负值表示超支）。
结论：进度与成本双双偏离计划，且都劣于基准。

**2. 为什么"客户要求六月底必须上线"这类外部 deadline 容易导致项目延期？它与工作量—交付时间权衡曲线有何关系？**

解析与答案：这类 deadline 往往不是基于工作量估算，而是被外部压力倒推出来的 unrealistic deadline，违背了工程规律。结合权衡曲线，要把交付时间压到极短，必须付出惊人高的 effort（进入"最短时间/最高代价"区），而现实中资源有限、并行度受 task 依赖限制；若强行按不现实工期排程，就会落入 impossible 区或导致质量与进度双双失控。因此项目经理应把期望拉回 effort 与 delivery time 的折中区。

**3. 面向对象的软件项目，其技术里程碑通常包含哪四个？WBS 在排程中起到什么作用？**

解析与答案：四个技术里程碑为——分析完成（分析模型建立、可重用类识别）、设计完成（类的数量、协作、属性与操作设计完）、编码完成、测试完成（含类测试、类间协作测试、集成与系统测试）。WBS（工作分解结构）是把项目层层分解为 task set 的结果，它使 task 清单完整、依赖可识别、effort 可估算、责任可分配，是后续甘特图排程与挣值分析的基础。

## 第 2 章：第31讲 进度与风险控制-2
> 对应分集：P31 | 原始标题：《第31讲 进度与风险控制-2》

合格的项目经理，本质上必须是一个合格的风险评测与风险预测人员。进度失控几乎都能在风险识别阶段找到预警信号；把风险管住，进度与成本才谈得上可控。这一讲系统展开风险管理（risk management）：先界定风险的本质，再给出识别与评估的方法，最后落到缓解、监控与应对。

### 一、风险的本质：四个必须回答的问题

项目风险（project risk）管理的起点，是把"风险"从模糊的担忧变成可讨论的对象。任何风险都要能回答四个问题：

1. **What can go wrong？（什么会出错）**——有哪些事情不按预先设想的预期发展，从而给项目带来风险。例如关键技术岗位人员离职、不成熟的技术攻关、对硬件/软件采购的时间依赖（采购不到位项目就无法继续）。
2. **What's the likelihood？（可能性有多大）**——风险发生的概率。概率越高，越容易发生，越需要优先处置。概率需要项目管理人员或团队详细评估。
3. **What's the damage？（损害有多大）**——一旦发生后造成的损失。例如地震在非地震区概率低，但一旦发生 damage 极大；而关键岗位人员因不确定性因素离职的概率较高，若事先做好规避或控制，则可以把 damage 缩得很小。
4. **What can we do about it？（我们能做什么）**——识别风险与可能性之后，在发生前或发生时如何避免、监控或规避。这是针对风险采取手段的依据。

这四个问题构成了风险管理的思维骨架：先问"会不会出事"，再问"多大概率、多大损失"，最后问"怎么办"。

### 二、两种管理思路：应对式与预见式

风险管理在实践上有两条基本路线。

#### 2.1 Reactive（应对式）风险管理

应对式是"发生了再积极应对"。一旦风险出现，项目团队投入去 react、去解决。它包含三个层次：

- **mitigation（缓解/救火预案）**：预先 plan for additional resource， anticipating the firefighting——万一某风险发生，谁来救火、哪些资源可用于解决，要事先规划。
- **fix（修复）**：一旦出现 failure，及时去 fix。资源要在事前就规划好。
- **crisis management（危机管理）**：若当前可支配的资源也解决不了遇到的 risk，相当于项目出现较大危机，仍需有一套危机管理预案。

应对式的局限在于它总是滞后于风险发生，补救成本最高。

#### 2.2 Proactive（预见式）风险管理

预见式强调预见性，把风险消灭在萌芽或大幅降低其冲击：

- **formal risk analysis（正式风险分析）**：把风险分析作为项目管理中必须执行（must perform）的任务，且不只是项目经理一人做，整个研发团队都应参与识别风险，做得正式、完善。
- **organization corrects the root cause（从根因上纠正）**：引入全局的 Total Quality Management（TQM，全面质量管理）理念与 statistic SQA（统计化软件质量保证），在硬件体系、系统层体系、软件层体系下审视哪里存在风险。
- **examining risk sources beyond the bounds of the software（审视软件边界之外的风险源）**：对可能产生风险的来源做详细分析，不局限于代码层面。
- **developing the skill to manage the change（培养管理变化的能力）**：很多 risk 由变化引起，必须事先设好应对变化的手段与措施。

### 三、风险管理的七条原则

要把风险管理真正落地，需遵循七条原则：

1. **Maintain a global perspective（保持全局视野）**：从 business problem 到 system context 都要纳入视野。缺乏全局视野，识别出的只是片面的、局部的风险，而非全局重要的风险。
2. **Take a forward-looking view（向前看）**：思考未来环节可能浮现的风险，并建立 contingency plan（应急计划）。
3. **Encourage open communication（鼓励开放沟通）**：每个成员都可能在某个环节发现项目经理未意识到的 risk，必须在开放环境下让所有人参与识别，而非只有 manager 负责。
4. **Integrate（集成进过程）**：对风险的考虑必须有机集成进软件研发过程——项目启动前要有正规 risk analysis，过程中新风险要加入，已识别风险要有效跟踪。
5. **Emphasize a continuous process（强调持续过程）**：随着信息增多，不断修改已识别风险、添加新洞察出的风险。
6. **Develop a shared product vision（建立一致的产品愿景）**：包括 stakeholder 在内，对软件愿景保持一致。若研发团队理解的"未来软件"与终端用户、customer 理解的不一致，风险最大——即便 customer 内部，不同部门对目标软件的期望也可能冲突，若 everyone is not on the same page，项目 risk 就高。
7. **Encourage teamwork（鼓励团队协作）**：stakeholder 作为一支团队作战，才可能对风险有效规避。

### 四、风险管理的循环步骤

风险管理不是一次性动作，而是一个循环：

```
identify（识别） → analysis（分析） → plan（计划应对）
                                       ↑
                    track & control（跟踪与控制）────┘
```

识别出 risk 后，要分析它、制定应对 plan，一旦发生则及时控制；控制过程中产生的新信息又回流到识别与分析，形成持续闭环。

### 五、风险识别的维度

风险识别要从多个维度扫描项目，主要考虑以下方面：

- **Product size（产品规模）**：项目规模大小直接关联风险量级。
- **Business impact（业务影响）**：风险对业务带来的冲击面。
- **Customer characteristics（客户特征）**：客户方的特点与成熟度。
- **Process maturity（过程成熟度）**：项目流程是否成熟带来的风险。
- **Development environment（开发环境）**：工具、平台、环境稳定性。
- **Technology to be built（待建技术的复杂度）**：所用技术是否复杂、是否成熟。
- **Staff size and experience（人员规模与经验）**：参与者的技能与经验。

### 六、评估项目风险的关键问题

具体评估一个项目的风险时，需要逐项确认：

- 高层软件/客户经理是否正式承诺支持项目？
- 终端用户是否已认可要构建的系统？
- 整个工程团队是否完全理解了需求？
- 客户是否充分参与了需求定义？
- 客户是否抱有 realistic expectation（合理预期）？曾遇到建设单位提出"半年才能完成的活要求两个月上线"这类非常 aggressive 的要求，若完全照办则必然 miss deadline 或 out of budget；若完全不顾客户意见，又在 client engagement（客户参与）上出问题。项目经理与团队需在此间取得平衡。
- **Project scope 是否稳定**？若仅发一封 email 就要求进入研发，变化会随过程不断涌出，给研发带来很大风险。

### 七、风险构成类别

风险可按受冲击的方面归为几类：

- **Performance risk（性能风险）**：开发出的系统与需求不符，尤其是性能层面不达标。
- **Cost risk（成本风险）**：例如原本 200 万的项目，最后实际花了 300 万——在商业环境里绝对不允许。
- **Support risk（支持风险）**：投产后遇到问题或提供支持时的风险。
- **Schedule risk（进度风险）**：对进度 deadly 敏感的风险。

**进度风险实例**：曾开发一套在北美市场运行的股票交易系统。美国证券交易委员会（SEC）因监管规则、交易规则变化，要求一个月内把变化反映到交易系统中，否则系统无法参与日常交易——schedule 极紧，绝不允许 miss deadline。当时把 schedule 评估为较高风险：规则变化不是程序员改完代码就能上线，而要做大量回归测试，需要制定专门的 plan 在一个月内控制进度。若 6 月 15 日前新版本无法上线，对方公司每天损失数百万美金佣金（broker 不能运行、trader 无法交易就没有 commission）。这个例子说明 schedule risk 的后果常以金钱损失直接计量。

### 八、风险预测（估算）：概率与后果

风险预测（risk projection，也称 risk estimation）在风险管理中极为重要。识别出 risk 后，要评估其发生的可能性（是 schedule 类还是 cost 类、概率多大），以及一旦发生引起的 consequence（后果）。后果要可量化，如上述股票系统"每天数百万美金损失"。

### 九、风险表（Risk Table）与风险暴露（Risk Exposure）

风险管理的标配文档是 **risk table（风险表）**，记录：风险是什么、probability（概率）、priority（优先级）、impact（影响）、以及 mitigation/monitoring/management（缓解与监控手段）。整个项目过程中这张表要持续维护。

**影响程度分级**：可分成一级到五级。风险的量化规划一般用 **risk exposure（风险暴露）**：

$$RiskExposure = Probability \times Cost_{if\_occur}$$

即"发生概率"乘以"一旦发生所需的代价"，乘积即为风险暴露值。

**算例**：开发软件时约 70% 的 component 可重用，则 30% 不可重用。若有 60 个 component，需新开发的数量为：

$$60 \times 30\% = 18 \text{ 个 component}$$

每个 component 平均 100 行代码，每行代码成本约 14 美金，则一旦发生（需全部新开发）的代价为：

$$18 \times 100 \times 14 = 25200 \text{ USD}$$

评估该风险发生概率约 80%，则风险暴露为：

$$RiskExposure = 0.8 \times 25200 = 20160 \text{ USD}$$

这个值就是该风险的 risk impact。风险暴露越大，越应优先排程资源去缓解。

另一个简单的应对计划例子：识别出"关键软件设计人员可能离开团队"这一风险，可指定两名技术设计人员互为 backup——万一一人变动，另一人能顶上。复杂风险则需要多步骤的应对计划。

### 十、影响风险级别的属性

以下属性会直接影响风险的级别，识别时需逐一回答：

- **Project Size（项目规模）**：评估规模主要有两种方式——看代码行（LOC）或看功能点（function point）。
- **Business Impact（业务影响）**：对业务哪些方面带来风险。
- **Customer（客户因素）**：由 customer 带来的风险。
- **Process Maturity（过程成熟度）**：流程成熟度带来的风险。
- **Technical Risk（技术风险）**：采用不成熟技术会带来风险。曾做股票撮合系统时采用分布式集群方式，当时某些著名厂商的平台还只是 trial version（试用版）、并不成熟，因此在技术上遇到不少风险，导致项目 delay 了好几个月。这类风险本应在执行前或执行中被预测出来。
- **Staff / People Risk（人员风险）**：例如人员 skill、availability（是否可用）；有些人是 part-time 参与项目，其时间如何保证也是风险点。

### 十一、风险信息的记录

业界用 **risk table** 记录 risk information，比课程所讲更复杂，通常包含：risk 名、risk type、priority、对业务的影响、发生概率、规避手段等。风险管理的闭环——识别、分析、计划、跟踪、控制——最终都要沉淀到这张不断维护的表里。

（课堂实践：以在线支付网络系统 Online Payment Network 为背景，各小组从本模块与项目全局两个角度，在 risk table 中记录不少于两到三条风险：可能存在哪些风险、发生可能性、对整体项目的影响、以及 mitigation/monitoring/management 手段。）

### 随堂自测

**1. 风险的本质要求回答哪四个问题？应对式（reactive）与预见式（proactive）风险管理的主要区别是什么？**

解析与答案：四个问题是——What can go wrong（什么会出错）、What's the likelihood（可能性多大）、What's the damage（损害多大）、What can we do about it（能做什么）。区别在于：reactive 是风险发生后才积极应对（含 mitigation 救火预案、fix 修复、crisis management 危机管理），成本最高且滞后；proactive 强调预见性，通过正式风险分析、从根因纠正（TQM 与统计 SQA）、审视软件边界外的风险源、培养管理变化的能力，把风险消灭在萌芽或降低冲击。

**2. 某项目有 50 个组件，预计 64% 可重用，不可重用部分需新开发，每个组件平均 120 行代码，每行成本 12 美金，该风险发生概率为 75%。计算其 risk exposure。**

解析与答案：不可重用比例 = 1 − 64% = 36%，需新开发组件数 = 50 × 36% = 18 个；一旦发生代价 = 18 × 120 × 12 = 25920 USD；Risk Exposure = 0.75 × 25920 = 19440 USD。该值越大说明风险越需优先缓解。

**3. 为什么"stakeholder 对目标软件的理解不一致"会构成高风险？它与七条原则中的哪几条直接相关？**

解析与答案：若研发团队、终端用户、客户内部各部门对"未来软件该是什么样"理解不同（如两部门期望冲突、无人统一），需求与范围就无法稳定，项目极易返工与范围蔓延，因此风险最高。它直接对应原则六 Develop a shared product vision（建立一致产品愿景），也依赖原则三 encourage open communication（开放沟通以暴露分歧）与原则一 maintain a global perspective（全局视野识别冲突）。

## 第 3 章：第32讲 进度与风险控制-3
> 对应分集：P32 | 原始标题：《第32讲 进度与风险控制-3》

进度与风险控制在前两讲分别铺开了计划工具（WBS、网络图、甘特图、挣值）与风险管理框架。这一讲换一个更贴近项目经理日常决策的视角：当 deadline 明显不现实时怎么办、工作量与开发时间之间到底遵循什么规律、以及把风险落到 RMMM 这一可执行模型上。

### 一、项目为什么会 late：根因复核

交付期到了却无法交付，根因可以逐条归并：

- **不合理的 deadline**：用户以商业运作施压，例如本需一年多，用户要求九个月，承接方咬牙答应，留下外部业务因素导致的隐患。
- **需求频繁变更未进 schedule**：变更本身合理，但若日程安排没把变更因素考虑进去，就会迟。
- **低估（underestimate）**：低估 effort（工作量）或资源。例如实际需要 20 个人月，却算成 15 个；或本需两人，却只按一人估算。
- **未考虑可预见/不可预见风险**：新技术成熟度不够、预先不可见的技术困难（如穿戴式设备测步数/呼吸/血压/血糖，谷歌眼镜这类全新方向，技术难度不可预期）。
- **不可预见的人力因素**：关键人员跳槽、生病。应对是培养后备人员随时掌握项目情况以便顶上；也可通过制度（按时发薪、文化建设增强归属感与认同度）降低流失。小公司更要靠团队看到前景、齐力奋斗。
- **沟通不畅**：组员不能及时沟通导致延误。例如大作业 19 号验收，组长须及时沟通、落实责任，才能保证整体功能（而非单点功能）可演示。
- **管理失职**：管理人员没意识到项目已滞后，或即使发现也缺乏改进途径——这是项目管理上的严重失职。

### 二、当 deadline 不现实时：用增量模型协商

面对"不现实 deadline"，最危险的做法是默默咬牙接下。正确流程以医疗实时知识诊断系统控制器为例：计划需 9 个月交付，但细致评估后判定至少需 14 个月。

1. **细致评估**：依据历史数据与经验，确定真实工作量与所需时间（得出 14 个月）。
2. **选择增量模式（incremental model）**：既然需 14 个月而对方要 9 个月，把最关键功能作为第一批在 9 个月交付，其余次要功能、文档、附加功能推迟，并把计划文档化。
3. **沟通协商**：向客户解释为何细致评估后 9 个月全交付不合理，提议 9 个月出第一增量版本满足基本需求，再经 11 个月出第二版、14 个月出第三版。客户通常能接受"陆续交付"，因为看到了可执行的计划与质量保证策略。

核心原则：用增量开发把"全或无"的僵局，转化为"先交核心、再补外围"的可执行承诺，并通过沟通让客户理解为何需要 12~14 个月而非 9 个月。

### 三、进度安排的关键点

排程时要落实七件事：

- **任务划分**：明确任务清单（需求分析、coding、测试、整合）。
- **相互依赖性**：大部分可并行分开发，但强依赖任务必须前者完成后者才能开始，须显式证明依赖关系。
- **时间分配**：每个任务明确起止时间。
- **工作量评估**：保证所有资源充足——需 5 人不能只给 3 人，测试资源、网络资源同样关键。
- **责任到人**：谁做、何时做完，必须明确，不能模糊。
- **交付物（改进定义）**：每个任务须有交付物。例如 11 号交 V2 版本及其改进说明，17/18 号前完成测试，19 号整合演示。
- **里程碑**：里程碑是质量审查的标志。上一版本必须完成（如 V2 程序整包交付），否则无效。一切要有白纸黑字明确约定。

### 四、工作量—成本曲线：E = M·(T_D/T_A)^8 与四分之三原则

工作量成本与开发时间之间并非线性，而是一条陡降后回升的曲线：

```
工作量成本 E
  ^                               _
  |  T_A 极短 → E 极高(不可能区)
  |   \___
  |       \___
  |           \_____ T_0 最佳(成本最低)
  |                 \________
  |                          \____ T_A 很长 → E 回升
  +------------------------------------> 开发时间 T_A
```

曲线表达为：

$$E = M \cdot \left(\frac{T_D}{T_A}\right)^8$$

其中 $M$ 为常数系数，$T_D$ 为合同规定/评估应交付的时间（如 12 个月），$T_A$ 为实际开发时间（可短可长于 $T_D$）。由于是 8 次方，一旦 $T_A$ 短于 $T_D$，成本 $E$ 会急剧攀升；稍长一点则成本下降。

两个重要结论：

- **四分之三原则（0.75 原则）**：若项目正常需 12 个月，则 9 个月（0.75 倍）已是极限；想要低于 9 个月（8 或 7 个月）基本是不可能完成的任务，大量实验都证实此点不可突破。紧急时可通过加班或追加人力逼近 9 个月，但绝不能碰更短的线。
- **最佳开发时间 $T_0$**：用成本衡量，最佳开发时间约为原定交付时间的两倍多（约 2×）。这看似反直觉，原因有二：① 开发时间越长，人员越熟练（如 3 个月交付需 10 人，6 个月交付因熟练只需 3~4 人）；② 时间充裕能在发布前发现并修复 Bug，而错误发现越晚修改成本越高，可达原有设计的数十倍。因此"时间长一点"反而质量高、开发成本相对低。该曲线即 PR 曲线（Putnam/软件方程相关）。

### 五、40-20-40 工作量分布

把整个开发周期分为前、中、后三段，工作量大致遵循 40-20-40 原则（或称 4-2-4）：

| 阶段 | 占比 | 主要活动 |
|------|------|---------|
| 前期（front-end） | 40% – 50% | 与用户沟通 10%–20%；分析+设计 20%–25%；审查修改 |
| 开发期（build） | 15% – 20% | 编码/coding 等构建活动（大型项目尤其如此） |
| 后期（post） | 40% | 单元测试、集成测试、白盒/黑盒测试、回归测试、架构测试、安装 |

这再次印证：编码只是小头，沟通、分析、设计与测试才是工时主体。

### 六、任务集类型与严格度（Degree of Rigor）

没有一种任务集适合所有项目。按项目类型区分：

- **新技术/新概念开发**：如穿戴式计算设备、谷歌眼镜类，前景好但把握不大、存在技术风险，须重点评估。
- **新应用开发**：成熟技术应用于新领域，把握相对较大。
- **再工程（Re-engineering）**：旧软件因运行环境变化而移植，如 Windows 下软件移植到 iPad 或改为手机游戏。

团队还要评估工作的**严格度（Degree of Rigor）**：市场规模多大、潜在用户多少、客户沟通难易（有的客户固执）。据此定义自适应标准，选择匹配的软件工程任务集。具体任务集类型可参考教材第 24 章 24.3.1、24.3.2 节。

**新概念开发任务集案例**（石窟壁画在线复原穿戴设备）：
1. 定义概念范围；
2. 概念策划——含三部分：透视眼镜（类谷歌眼镜）、手持基带操作设备、软硬件如何连接；
3. 对三个任务集分别进行技术风险评估；
4. 概念可行性证明，证明可行后再分别实现；
5. 系统整合与用户反馈。

这条通路走通并被证明可行，项目才能继续推进，称之为"关键路径分析"。

### 七、进度表与里程碑的画法

进度表：纵向列一系列 task set，横向表示时间周期（如 5 周）。每个任务集节点通常打**菱形标记**表示里程碑（Milestone）。项目经理严格控制各节点应完成的任务；对独立性强的任务与有先后依赖/协作的任务分别对待。到了既定节点未完成，就要调整——这涉及前期策划与分析的质量。

### 八、进度的跟踪与控制

日程表制定后必须严格跟踪，手段包括：

- **周期性会议**：常一周一次，紧张时周一、周四各一次，成员汇报进展与问题。
- **评估阶段成果**：评估迄今所有软件工程过程，检查是否按 Schedule 进行。
- **核对里程碑**：对照里程碑表检查第 1、2 周任务是否如期达成。
- **比对计划与实际**：比较 actual start date 与 planned start date，在资源分配表上确认后续任务能否按期启动、资源是否足够。
- **非正式交流**：与开发人员非正式沟通，听取实际意见。例如原定两周工作量，一周后询问若人员反映不够，经理须及时调整或追加人员。
- **讨论潜在问题**：共同分析可能出现的风险。定了日程表不跟踪执行，极易延期。

### 九、挣值分析（EVA/EVM）：用量化替代直觉

挣值分析是一种经典定量化项目监控方法，核心是用统计精确的方法**代替凭直觉（gut feeling，西方俚语"用肠子思维"）**，尤其能在项目完成约 40% 时给出可靠预测。关键术语：

- **BCWS**（Budgeted Cost of Work Scheduled）：按预算/时间安排，每个任务集的工作量（人月/人日或金额）。
- **BAC**（Budget at Completion）：全部任务完成时总工作量之和。
- **BCWP**（Budgeted Cost of Work Performed）：实际已完成工作的预算代价（P = performance）。

推导出的指标：

- 进度绩效指数 $SPI = BCWP / BCWS$：≥1 超前，<1 滞后，接近 1 正常。
- 进度偏差 $SV = BCWP - BCWS$：>0 超前，<0 滞后需补救。
- 计划完成百分比 $= BCWS / BAC$；实际完成百分比 $= BCWP / BAC$。
- 成本绩效指数 $CPI = BCWP / ACWP$：≈1 正常，>1 说明花钱效率高，<1 超支。
- 成本偏差 $CV = BCWP - ACWP$。

**算例**：总工作量 100 人月，单价 1 万元/月即预算 100 万。到 6 月（半年）计划应完成 50%（即 50 人月/50 万）。若实际只完成 40%（落后）；若实际投入了 120 人月（120 万）才把活干完，则：

$$CPI = \frac{BCWP}{ACWP} = \frac{100}{120} < 1$$

说明任务虽完成，但代价超支——为赶进度 4 月发现问题后追加人力，最终成本超出。SPI 与 CPI 共同把"凭感觉"变成可比对的数字。

### 十、风险管理：被动、主动与 RMMM

风险分被动与主动两类，主动优于被动。

**被动（reactive）管理**，风险发生后才处理：① 尽量避免，计划增加资源参与"救火"（firefighting），人员不够则加人、加班（如 7 点下班改 9 点）；② repair（修补）出错之处；③ 若修复不起作用、资源已用仍不行，则进入危机状态（crisis management）——这是不得已的被动局面。

**主动（proactive）管理**，如中医"治未病"：高明的医生在病发前就防范。做法包括：建立正式风险分析机制预防；从根因上根除风险（用统计 SQA 方法检查风险根源）；审视软件以外的风险（硬件、不成熟新技术）；主动管理变动，事先做好应对而非事后补救。

**风险的特征**：① 不确定性——可能发生也可能不发生；② 损失——一旦变现实产生不情愿的结果。评估时综合可能性（80% 几乎等于发生须重视；40%、20% 次之）与损失严重度（客户抱怨可忍，投诉/停用则厉害）。

**风险类型**：项目风险（预算/代价）、技术风险（质量、交付时间）、商业风险（缺人手、市场战略，如 iPhone 5 配件突然停产导致货不能按期交付）、管理风险等。

**影响度分级**：可忽略（negligible）、边缘（marginal，较严重）、危机（critical，相当严重）、灾难（catastrophic，最高）。后两级须严重量化。

**风险评估步骤**：① 建立评估机制，看发生概率（20% 还是 80%）；② 推断后果严重度；③ 评估对整个项目/产品的影响；④ 注意精度，使结论无二义性、人人明白。再按"概率 × 后果"排优先级，先解决排前的。

**RMMM 模型**（Risk Mitigation, Monitoring, Management）：
- **Mitigation（规避）**：如何让风险不发生；
- **Monitoring（监控）**：判定风险变得可能性更高还是更低，识别主因（人力因素则加更资深开发者；技术因素则更落实技术）；
- **Management（管理）**：制定应急预案，一旦风险变现实如何应对。

### 随堂自测

**1. 四分之三原则与最佳开发时间 T_0 分别是什么含义？结合 E = M·(T_D/T_A)^8 说明为何"压缩工期"代价极高。**

解析与答案：四分之三原则指若项目正常需 12 个月，9 个月（0.75 倍）已是交付极限，低于此基本不可能。T_0 指最佳开发时间约为原定交付时间的 2 倍多，此时成本最低。由公式 E = M·(T_D/T_A)^8 可知，工作量成本与实际工期成 8 次方反比：当 T_A 短于 T_D（压缩工期），分母变小使 E 急剧飙升；加之时间短导致人员不熟练、Bug 发现晚修改成本可达数十倍，故压缩工期代价极高。

**2. 某项目总预算 BAC = 200 人月。到第 6 月计划应完成 BCWS = 100 人月（SPI 基准），实际 BCWP = 80 人月，实际投入 ACWP = 110 人月。求 SPI、SV、CPI、CV，并判断状态。**

解析与答案：SPI = 80/100 = 0.8 < 1，进度落后；SV = 80 − 100 = −20 人月（滞后）；CPI = 80/110 ≈ 0.73 < 1，成本超支；CV = 80 − 110 = −30 人月（超支）。结论：进度与成本双双偏离，且成本偏差更大，需同时追加纠偏资源并审查超支根因。

**3. 面对"客户要求 9 个月交付但评估需 14 个月"的局面，应如何处置？RMMM 中 Mitigation 与 Management 有何区别？**

解析与答案：先细致评估得出真实工作量（14 个月），再选增量模型——9 个月交付最关键功能的第一增量版本，其余推迟，并把计划文档化；随后向客户解释全交付不合理，用"陆续交付+质量保证策略"达成可执行承诺。Mitigation 是在风险发生前采取措施使其尽量不发生（如培养后备人员避免关键人离职）；Management 是制定应急预案，一旦风险变现实如何补救（如危机时的救火与加班），二者前者前置预防、后者后置应对。
