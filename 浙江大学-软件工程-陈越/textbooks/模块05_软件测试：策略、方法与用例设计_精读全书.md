## 第 1 章：第17讲 测试策略-1
> 对应分集：P17 | 原始标题：《第17讲 测试策略-1》

我们今天开始讲 `testing`。先说一件可能让你们有点意外的事：虽然你们那个 `design` 还没有通过最后的验收，但你们现在就要开始准备做 `testing plan`，做测试计划了。

为什么？因为测试在整个开发过程中是很重要的一个环节，所以我们要专门分两次课讲。第一次课从战略的方面讲：整个测试的策略大体是什么样子，大概要分哪几块，你是自顶向下测还是自底向上测，有哪几种类型的测试。下一次课再给大家具体讲，每一个不同的测试阶段你具体要用的测试技术是什么。先看大的，再看细节。

### 测试计划的启动时机

这一讲讲的就是"大的策略"，下次讲"测试的细节"。而这两次课的分工本身就说明了一件事：测试计划不必等到代码写完、甚至不必等到设计定稿才开始写。

理论上来讲，你们的 `design` 还没有经过验收，所以代码应该还没开始写；但是 `test plan` 今天回去就可以做了——因为它是一份计划，它描述的是"我打算怎么测"，不依赖已经存在的代码。前提是你手上要有 `design`：拿到了设计，你就能针对这个设计写出"我要测哪几个环节、重点测哪些部分"。

这个结论不是凭直觉下的，后面讲测试团队的误区时我们还会回到它：测试组恰恰应该从很早的阶段就参与进来。

### 测试不完备的两个历史案例

先给大家看几个历史上非常有名的例子，都是由测试不完备引起的。

#### 1963 年火星火箭：一句 Fortran 循环语句的录入错误

第一个是 1963 年一个非常著名的案例。那一年美国人向火星发射了一颗火箭，然后挂掉了。损失是多少？`10 million`，一千万美元。这是一九六三年的一千万美元，你先把它按今天的币值折算一下，再来体会这个数字。

错误就错在一段 `Fortran` 程序被敲错了一点。出错的语句，是 `Fortran` 里相当于 C 里面 `for` 循环的那个语句。用 C 写，就是 `i` 等于 1、`i` 小于等于 3、`i++` 这么一行。

那语句里的 `5` 是什么东西？它指的是循环体结束那行语句前面的标号。`Fortran` 在前面有一个标号区域，行首若干个字符是可以写标号的：你在循环体最后一行前面写了个 `5`，就表示执行到这一句的时候，这个循环体结束。C 是用一对大括号把循环体括起来，`Fortran` 靠的是行首那个标号。

```text
C 的写法（相当于这里的 for 循环）
for (i = 1; i <= 3; i++) { ... }

Fortran 的写法：循环体结束的那一行，行首带一个标号
        DO 5 I = 1, 3      <- 逗号：I 从 1 走到 3
    5   ... 循环体最后一行 ...

录入时那个逗号被看成了点，于是被敲成这样
        DO 5 I = 1.3       <- 不再是循环语句，而是一条赋值语句
```

读图说明：`Fortran` 用行首标号（这里是 `5`）标出循环体的最后一行，C 用大括号划定边界；逗号被看成点之后，`DO 5 I = 1, 3` 变成了 `DO 5 I = 1.3`，整个循环语句就退化成一条赋值语句。

据说是这样的：程序员先把程序写好，然后大概是复印了一下，交给另外一个人去敲进去。结果在复制的过程中，那个逗号看上去就不清楚了，看上去很像一个点，敲程序的人就把它敲成了 `i = 1.3`，这一句就变成了一个赋值语句。而当年 `Fortran` 的编译器是诊断不出来的——它没有报错，于是这个程序被认为是"对的"，就这么执行了。一千万美元就没有了。

> **易错点**：这类错误的可怕之处在于它不触发任何编译报错，程序照常运行，看起来一切正常。测试的时候没有仔细检查到那个循环体，代价就是一千万美元。

#### 卡利空难：导航字符与飞行员旧习惯的不一致

第二个例子的开头是一行红色小字：`crash killed all but 4`。一共死了多少人？163 减 4，159 个人直接挂掉了。

事故是怎么发生的？飞机上装了自动导航系统。但是在没有这套导航系统以前，那位机长用的是地图。在那张地图上，他要飞的 Cali 这个地方有一个字母来代表它。他很熟悉自己以前用的那张地图，认为 Cali 对应的就是这个字符，就把这个字符输了进去。哪知道在这套自动导航系统里面，这个字母对应的不是 Cali，而是 Bogota，而且正好是反方向的。他输完了以后，他们就直接撞到山上去了。

地面导航也有责任。事后把黑盒子翻出来的时候就听到：地面其实已经发现他方向不对了——他怎么在向反方向飞——但他没有很直接了当地告诉机长"你飞错方向了"，而是用一种比较幽默的办法跟他说："我建议你以比较直接的方式飞向你的目的地。"机组成员没听懂这句话是什么意思；等他们听懂的时候，那座山已经在眼前了，已经撞上去了。

所以这里有几个教训。民航系统的人后来也建议所有飞行员：你不能够完全相信 `computer`，不要完全相信那个自动导航系统，不要完全相信计算机软件，你还是要根据自己的飞行经验去判断你到底应该往哪个方向飞。地面导航人员也有不可推卸的责任：你有发出直接警告的责任，但是你没有——提醒是提醒了，可你说了半天人家没听懂的话。这个悲剧是很严重的，一百五十多条人命，就毁在一个软件手里。

> **结论**：这个软件本身没有问题，但是测试软件的人是有责任的——因为你少了一个测试：一致性测试（`consistency testing`）。

### 一致性测试：与用户既有习惯的对齐

这个案例真正缺的那一环，为什么叫一致性问题？回到我们前面讲过的东西：你设计软件的时候，为什么要分析你的用户的 `profile`？为什么要分析用户的背景——他受教育的背景、他的特点、他平时习惯用的东西？

特别是像自动导航系统这种软件，你当然要分析一下那些飞行员在没用你这个系统的时候是怎么工作的。然后你设计的这一套字符，肯定要跟它以前用的那个 `charts`（航图）是一致的，才会避免这种错误。

道理很直白：人家默认的是"我原来只不过看着纸质的地图，现在有一个键盘让我去按一下，那我原来怎么按的，现在还怎么按喽"。你让他专门再去记住另外一套，他很可能就记错了。

> **提示**：这个一致性问题是应该由测试人员提出来的。当然，设计本身就有问题——设计的时候你就应该考虑到这一点，设计用户界面的时候也应该考虑到这一点。你没有考虑，然后测试也没有去想这个事情，大家整个地把一致性这个问题给放过去了，就导致这样一系列悲剧。

所以测试要有很有很多东西要测。这也正好引出第一个根本问题。

### 测试的目的：发现问题而非证明正确

第一个问题是 `What is testing for?` 我们测试的根本目的是什么？——为了发现问题。

我们测试的目的是为了证明这个软件是对的吗？我们不是为了证明它没有问题，我们是为了发现问题的，是 `for finding errors`，是为了找错误。

你不要以为这是一句废话。我知道大家都学过数据结构，最初等的测试训练在教数据结构的时候就已经做过了：让大家写 `report`，那个 `project report` 里面专门有一节是让你写测试的。作为第一次做测试这件事的小朋友，当年的你们很多人写的那份测试，现在回头看看得过去吗？实在看不过去——写了几个特别简单的 `case`，然后就证明这些 `case` 都过了，所以这个程序是对的。

> **结论**：如果这就是你的测试，那么你这个测试员的根本目的就错了，你的立场站错了。你要站在程序员的对立面，不是站在他同一阵营里面。你要做的是想方设法去破坏它；如果你想尽了所有的办法都不能破坏它，那你其实对它是一个很大的帮助。

公司里面给测试员的奖金也是这么给的：你找到更多的错误，我会给你更多的奖金；而不是你测完了证明"这个程序是对的，我保护了它"，然后你拿到奖金。反过来说，如果你什么都没测出来，那可能是你的测试太弱了，并不能说明它没有错。

所以作为一个 `testing team`，你一定要明白你的立场在哪儿：你的立场是要 `finding errors`，你不是为了 `protect the programmer`，你不是为了保护程序员而去做测试的。这是一点非常重要的。

### 测试团队的交付物

明白了立场，接下来是产出：`testing team` 最后要给什么东西出来？我先把最容易的说出来——一个 bug 清单你总要给出来吧。

- `errors`：bug 清单，这一项最直接。
- `test cases`：测试用例清单。讲数据结构的时候我们要求大家列一个表：一栏里列了你所有的 `test cases`，然后一栏是 `expected output`（应该有什么输出），再一栏是 `actual output`（你实际获得的是什么输出），最后一栏是一个 `status`——如果不相符，它就是一个 bug，而它的状态是已经改过来了，还是 `pending`，还是 `corrected`，还是别的什么。
- `requirements conformance`：与需求的一致性。你完成的东西，有可能每一个功能都是对的，合在一起却不是你要的那个软件。你要检查的是，它最后做出来的是不是你 `requirement` 里头描述的那个软件。
- 各项指标的逐条对照：比如如果我对安全性有要求，如果我对 `performance`、对它的效率有要求，这些指标要一个一个指标都去对一下。
- 最后还要给出一个总体指标：`an indication of quality`，用来总体评价一下你测的这个东西质量如何。

| 交付物 | 内容 |
| --- | --- |
| `errors` | bug 清单，最直接的一项 |
| `test cases` | `test case` / `expected output` / `actual output` / `status` 四栏的表 |
| `requirements conformance` | 在多大程度上遵守了 `requirements` 的要求 |
| `performance` | 效率、安全性等指标逐条对照 |
| `an indication of quality` | 总体评价被测软件质量的指标 |

> **结论**：`errors`、`requirements conformance`、`performance`、`an indication of quality`——这是 `testing team` 要做的事情；也就是说，你们的 `test plan` 里要写点什么东西、你打算怎么测，这些都得提前准备好。

### 测试的推进顺序与参与者

接下来看大概的 `approach`：从什么时候开始真正执行测试呢？是从那个 `component` 开始的。

`component` 做完了以后，那个程序员自己肯定要做 `unit testing`，先测一下自己的工作，然后交上来。交来以后，我们就是从 `component level` 出发，向着 `integration`，然后向整个的 `system`，一点一点完成。那个测试是从小到大进行的。

在不同的时间点，你采用的测试技术是不一样的。比如 `unit testing` 的时候，一般我们用白盒测试；然后到 `integration`、`system testing` 的时候，我们会用黑盒测试。什么是白盒测试、什么是黑盒测试，白盒要测到细到什么程度，有哪几种不同的逻辑覆盖，等等等等，这些下一次课再给大家介绍。

```text
  一件一件做出来的 component
          |
          |  unit testing（写它的人自己做，一般用白盒）
          v
     component level
          |
          |  integration testing（黑盒）
          v
      integration
          |
          |  system testing（黑盒）
          v
        整个 system
```

读图说明：测试的推进方向是从小到大、自底向上的；每一段用的技术不一样，白盒在前、黑盒在后，具体技术下一讲再展开。

什么人来参与测试？一般来说至少有两种人：写程序的人自己肯定要参与测试；然后最好还有不是写你这个程序的、独立的测试人员来帮你一起测试。为什么最好要有独立的人？这个问题等讲到测试团队的组成时再回答。

### 测试与调试、验证与确认

#### 测试与调试的区别

再提醒大家一遍：`testing` 和 `debugging` 是不一样的。

- `Testing` 是发现错误。我发现这里有一个错误，然后给你一个 `report`：这个地方错了，显然这个模块有错。
- `Debugging` 是改正错误的过程。

翻译过来就是测试与调试：测试只是发现哪里有错误，调试是想办法把错误改过来。这是两种不一样的 `strategy`，后面我们要分别介绍。

#### 验证与确认的区别

另外有两个概念，一个是 `verification`，一个是 `validation`，这是测试团队要做的两件事情。这两个词如果你去查字典，它的翻译好像都是一样的，都是"验证"。有区别吗？

中文翻译的教科书里是这么翻的：`verification` 是验证，`validation` 是确认。看上去就是两个时间顺序不一样的工作。实际上它们都有"检验一下、确认一下"的概念，但有一点微妙的不同。书上有两句话特别清楚地阐述了这种不同。

`Verification` 回答的是这个问题：`Are we building the product right?` 就是我们是不是在以正确的方式来做这个 `product`？也就是说，它要检查一下每一个模块——你号称这个模块是做这个的、那个模块是做那个的——每一个模块的功能是不是都是正确的。检查每一个模块功能的正确性，这是 `verification` 做的事情。

做完了以后，`validation` 来回答这个问题：`Are we building the right product?` 你可以说每一个功能都是正确的，可是放在一起好像不是我要的这个软件。这个问题就是在 `validation` 这个阶段去检查的。

我以前看过一幅漫画，说的就是这件事：一个人画画，你看他的眉毛、眼睛、鼻子、嘴，每一个细节都是一个美人的形状，然后放在一起就不是一张人脸——因为他都没放对地方，全部放错位了；你把其他东西遮住，单看那一个器官，都是很漂亮的。

`Verification` 就是检查你画的每一个器官是不是都很漂亮，`validation` 就是说放到一起是不是一张人脸。这两个步骤是 `SQA team` 里面最重要的、他们最关注的两个环节。

| 对照项 | `verification`（验证） | `validation`（确认） |
| --- | --- | --- |
| 回答的问题 | `Are we building the product right?` | `Are we building the right product?` |
| 检查什么 | 每一个模块、每一个功能是否都正确 | 全部功能合在一起是不是需求要的那个软件 |
| 画画的类比 | 每一个器官画得漂不漂亮 | 放到一起是不是一张人脸 |

### 测试只是 SQA 的一个环节

这里头要澄清一个观点：`software testing is only one element of SQA.` 测试不是 `SQA` 的全部工作。顺便说一句，`SQA` 是什么来着？`Software Quality Assurance`，软件质量保证——`SQA team` 是要专门有一拨人做这件事情的。

你不能够把最后软件质量的责任全部都推到 `testing team` 身上去。`Quality must be built into the development process, one cannot use testing to add quality after the fact.` 你整个软件的质量，取决于你开发软件的这个过程管理、执行的严格程度。

你如果在管理的每一个环节都没有质量监控，然后你就指望着到最后一关说"`testing team` 全靠你们了"；如果这个软件质量一塌糊涂，就说那都是你 `testing team` 的责任——"你这么多 bug 当时没揪出来，所以都是你的错"——`blame the testing team, that's not fair.` 这是不公平的。

> **提示**：持这种观点是不太成熟的表现。如果你整个公司的管理流程就不符合质量保证的要求，那么从一开始就注定了你这个软件的质量高不了；它已经做成这个烂样子了，然后你指望着最后全靠 `testing team` 给你解决问题，是不现实的。

### 测试团队的组成

那么 `software testing team` 应该由什么样的人组成比较好？两类人，各有各的好处。

#### 开发者自测的优势与问题

第一类是交给 `developer`，写程序的这个人让他自己去做测试。

好处是什么？因为这个程序是他自己写的，所以他自己对这个内部结构特别清楚，他不需要花很多时间再去理解这个程序，只要直接去测就好了；所以他可能比较有针对性，很快能设计出一些 `test cases`，然后直接去测一下就好了。

但是，它的问题显然也是有的。

第一个问题是程序员都有自己的那一点骄傲。我们大家都是程序员：我这个程序，要么就是我没调好的时候我不会交出去；我一旦 `submit`、一旦上交出去了，我总是觉得我已经测过了呀，单元测试我测过了，没有问题的，所以我交出去的程序肯定是没问题的。然后你再叫我做一个 `formal test`，那我就 `test` 一下呗，怎么会有问题呢？

第二个问题是个人利益的驱使。你如果测试不过的话你要改，在一定时间里你改不了的话，你过了 `deadline` 你要被罚的，奖金没有了。所以他会受到种种个人利益的驱使，不太会非常严格地去测他自己做出来的东西。

第三个问题就是每个人都有盲点。你自己死都看不出来的东西，你换一个人看就特别容易。

这件事我给过一个现成的例子。我们组里有一个同学，信心满满地说要重构，然后"砰"就跳到那个坑里去了。重构完当然就有 N 多的 bug，然后他自己很痛苦地查了半天查不出来，查到最后都要放弃了，说"我要给我自己放一个礼拜的假，什么都不干，我要去干点别的，我实在受不了了"。

我给他出的主意是：找另外一个人，你们两个人 `pair programming`，两个人坐到一起，来查这个程序。为什么我要他们两个人坐在一起呢？是为了避免另外一个极端。当然，我如果直接把他的程序丢给另外一个人去看，也可以的；但是缺点是他得从头去学一下这整个系统、整个架构是什么样，他要花相当多的时间去了解、要先看懂，然后再去查错。两个人坐在一起做，就可以避免这个麻烦：写的人给他讲我这块是在干什么，然后大家一起往下看。一周下来两个人都很兴奋，说结果非常好、收获大大的，N 多的错误、各种错误都找出来了。

就是因为你换了一个人看，就完全不一样的感觉。两个人都有各自的盲点，但是两个人盲点重合在一点上的可能性比较小。

> **提示**：如果你自己的代码卡死在什么地方，我的建议是找一个好朋友，请人家吃顿饭，你们大家坐在一起看一下——什么东西都能看出来。

#### 独立测试组的引入与代价

第二类是：作为一个公司来讲，你给一个独立的测试组，叫 `independent test group`，`ITG`，去做 `testing` 这件事情。

缺点呢，就是他们要花时间——要多花点时间，就意味着你要多花点钱，你要付人家这个时间段的工资。

但是，因为他们是 `independent`，他们两个的利益是有点对立的：`testing team` 那边，你抓到多少 bug 我给你多少奖金，那么他就会全力以赴地要去抓尽可能多的 bug 出来。所以在质量保证这个意义上，这个效果会好一点。

| 谁来做测试 | 好处 | 问题 |
| --- | --- | --- |
| 开发者自测 | 熟悉内部结构，不必花时间重新理解程序，能较快设计出有针对性的 `test cases` | "我已经测过了"的骄傲；改不完就过 `deadline`、丢奖金，受个人利益驱使；人人有盲点 |
| 独立测试组（`ITG`） | 与开发方利益对立，抓到多少 bug 给多少奖金，会全力以赴多抓 bug，质量保证效果好 | 要多花时间，也就意味着要多花钱，得付人家这段时间的工资 |

#### 三个需要避免的误区

这里头有几个误区，大家要避免。

第一个是 `developers do no testing at all`：既然 `developer` 倾向于保护自己的程序，他是不是根本就不应该碰这个 `testing`？这也不对的。起码前期的 `unit testing` 和初期的 `integration`，`developer` 都要参与在其中。然后他有一个过渡：在 `integration` 阶段，那个 `ITG` 进来以后，就是两方要密切地合作；然后在后面 `system testing` 什么什么，慢慢才由独立测试组把那个事情接过去。

第二个是：software 是不是就可以 `tossed over the wall`？这个说法很形象，就是说我直接把它丢过墙，我就不管了，这不是我的事情了——我写完了，`submit` 以后就是 `testing team` 的事情，我直接丢过去，没我的事了。这也是不对的。最起码的一件事情：人家发现有错误，还是得你来改。一般不是 `testing team` 来做 `debugging` 的，改错这种事情还是要你来改。

第三个是 `Testers are not involved with the project until it's time for it to be tested`：是不是说代码都没写出来，我 `testing team` 就闲着没事干？肯定不是这样。事实上，你的 `testing team` 是要从 `analysis` 阶段就在旁观，然后你要了解他整个成型的过程，你才能够充分地了解他最薄弱的环节、最容易出错的环节在哪里。然后这个时候，你只要拿到了他的 `design`，你就可以开始针对他这个 `design` 去做这个测试计划了：我要测哪几个环节，重点测哪些部分。这些都是可以事先就已经开始做的。

> **结论**：你们的 `design` 还没有经过验收，代码应该还没开始写，但是 `test plan` 今天回去就可以做了。我相信你们的 `design` 应该做得差不多了。

```text
  需求分析（analysis）      测试组从这里就开始旁观，了解系统是怎么成型的
        |
        v
  设计（design）            拿到 design 就写 test plan：测哪几个环节、重点测哪些部分
        |
        v
  unit testing             开发者自己做（一般白盒）
        |
        v
  integration testing      开发者与 ITG 密切合作，ITG 从这个阶段进来（黑盒）
        |
        v
  system testing           ITG 逐步把测试接过去（黑盒）
```

读图说明：测试组的介入远早于代码——从 `analysis` 阶段就开始旁观，`design` 一到手就能写测试计划；越往后走，测试越由独立测试组接手。

### 结构化软件的测试策略

在测试策略方面，我们大概分成两种。一种是 `traditional software architecture`，就是我们传统的、结构化的这种软件架构。

这种架构最基本的几条，其实就是四步走。

1. `unit testing`：一个 `component` 一个 `component`。我们前面不是做过任务拆解吗？基本上一个 `component` 属于一个 `team`，然后你们自己去做 `unit testing`。你们这个 `component` 自己下面肯定又分了很多小的 `component`，那就做一个一个的 `unit testing`。
2. `integration testing`：把它一点一点地集成起来。这一步在每一次集成的时候，你都有一个 `verification`：我集成的这个功能是不是正确的？是正确的、集成进来以后，这块功能是不是还是正确的？
3. `validation testing`：才开始要看——所有东西都做好了，我照着我需求说明书、需求规格说明书最后那个非常重要的 `validation criteria` 来看。你当时是怎么写的？并且写清楚。就我验收的时候，你达到这些标准我就给钱，就是那些标准：一个是有功能，然后性能，然后还有一些其他的标准，一条一条都写出来，然后照着这个 `validation criteria` 去测。
4. `system testing`：最后呢就有一个安装调试，把它装到你要用的那个大环境系统下面，做一个 `system testing`。

传统的软件测试，其实思路是比较清楚的。

```text
  unit testing
  一个 component 一个 component，做完就测
        |
        v
  integration testing
  一点一点集成；每集成一步都做一次 verification
        |
        v
  validation testing
  对着需求规格说明里的 validation criteria 一条一条验收
        |
        v
  system testing
  安装调试，装进实际使用的大环境
```

读图说明：四步顺着"越做越大"的顺序往下排；前两步问的是"每一步做得对不对"，到第三步才换一个问题——整套东西是不是客户要的那个。

### 面向对象软件的测试策略

另外一种就是 `OO`，`object-oriented`。

`Object-oriented` 这种 `approach` 在它刚推出来的时候，是一个非常时髦的概念，大家都说特别好特别好，什么都好，好像它什么都好。肯定不可能什么都好的嘛，它肯定有它的弱点。那最麻烦的地方在于什么呢？你测试起来很麻烦。这就是 `OO` 比较痛苦的一个地方。

#### 面向对象方法的测试难点

`OO` 的理想是什么？它是说你理解这个软件比较容易：我按照正常人、普通人的观点去理解这个软件，我就认为这个世界就是由一个一个对象、它们互相之间的作用在运转的。于是我这个系统也理解为一个一个的对象，然后它们之间互相作用来运转。

那问题就来了：你要怎么样的测试，才能够把他们所有的关系测试清楚，然后保证它运转是正确的？它不是一个结构化的东西。所以你测试这一点的时候是非常、非常痛苦的。

#### 面向对象的三个测试层次

总的来说，它大概也可以分成这么几种。

- `unit testing`：那就是测一个一个 `class`。一个 `class` 就是一个 `unit`，一个 `component`。但是你这个 `class` 的测试方法，跟我们传统的那个一个 `module`、一个模块的测试方法是很不一样的——你测一个功能模块跟你测一个 `class` 那是两回事，复杂不是一个程度的。
- `integration testing`：尤其复杂。你要那个 `class` 跟 `class` 之间的那个关系，你要怎么样能够把它尽可能覆盖清楚。你如果想用全排列——就是你做完全测试、你试它全部的排列组合的话——你会测死的，你就不可能测得完了。那你要在有限的时间精力下面把主要东西测到，这是需要一些技巧的。
- `system testing`：那这个也就没什么好说的，就是整体的，你按照一种方式去跟你的 `requirements` 对照起来，然后测一下它整体的效果。

### 测试的结束判据

最后以一个问题来收：`When are we done?` 什么时候测试是个头呢？你测到什么时候就可以宣布说"OK，我不测了，可以交了"？

理想主义地告诉你，是 `never`。对于一个充分复杂的软件系统来说，首先你做穷尽测试是不可能的；你既然不能够做穷尽测试，你就永远不敢说这个软件里面是没有 bug 的，它总是会有出错的地方。

但是虽然大家都明白这个道理，具体到某个人他做出来的东西的时候，他总是说"你你这个事情要给我有一个备份，万一你这个坏了，我怎么办"，他说"不会坏的"。程序员都是这样的，越牛的程序员越是这样的："不会坏的，我做的东西不会坏的。"其实这么说就是很不成熟的表现：你不可能做过完备的测试，然后你凭什么说这句话呢？源于你强大的自信。你只能说，你这个 bug 最好希望有生之年它不会出现就好了。

从一个实际的角度来讲，`when you run out of time, or you run out of money.` 你要没时间了、要没钱了，那也就不测了，就好交出去了，大家先用着吧。只能是这样一个过程。

> **结论**：一定要记住一个最基本的观点——`testing` 你只是发现错误的过程，你永远不能够证明这个软件没有错误。即使你一个错误都没测出来，也不能说明这个软件没有错误，只能说可能你的测试太弱了。当然，也可能这个程序写得质量的确不错、它很强，另外也可能是说明你很弱。都是有可能的。

### 测试策略中强调的几条做法

这里面有几个从策略方面要跟大家强调的概念。

#### 需求的量化描述

第一个是：`Specify product requirements in a quantifiable manner before testing starts.` `Quantifiable manner` 是什么意思？就是可量化的。

所以就是你需求规格说明书最后那个 `validation criteria`，你要尽可能地把什么东西都量化，最后都要设计成一系列的指标：我达到这个指标我就怎么样。那么测试的过程呢，其实你也是要有一个量化的过程。

这里有一个讨论题目。比如说我这个老板，我希望能够知道你这个测试大概进行到什么程度了。有的公司他可以在 `report` 里面说：我们目前已经找到了 90% 的 bug。你不觉得好奇吗？这个 90% 是怎么得到的？你怎么知道全部的 bug 有多少？你既然不知道的话，你怎么能把这 90% 算出来？你凭什么算出来？它肯定是一个毛估估的数据。但毛估估你也要有一个根据，你不能说一拍脑袋说"我觉得已经测完 90% 了"。

这个过程的量化有什么方法？有很多种办法，答案绝对不唯一，你们自己去想一下；但是你都给我讲出个道理来——我首先打算怎么算？我打算怎么获得数据？然后为什么我这么算是比较合理的？

日本有一家公司想了一个辙，我觉得比较好玩。他根据以往的经验，会设计 N 个错误，然后悄悄地把它植入到那个软件里面，然后就丢给测试人员去测。然后在他每周一报、每周一报报上来的那个错误清单里头，他看有多少是他植入的错误被找出来了。如果他所有自己加进去的错误都被找出来了，他就认为差不多了，该查的错都差不多查出来了。他所谓"90% 找出来了"的意思是：他植入的错误 90% 被找到了，他就说我的测试完成了 90%。

> **提示**：这个办法的机理是给自己人造一个已知的分母。你不知道全部 bug 有多少，"90%" 就无从算起；植入的错误是你已知存在的，它的找回比例才是一个算得出来的量。但这个成本也是相当高的，而且也是有相当风险的：你植入的错误会很干净吗？它会对软件产生什么样的影响，你其实很有把握吗？

不管怎么说，这是一种方法，有很多很多的方法可以去做这个事情。要注意的是：从你公司开始做的第一个 `project` 开始，你就要随时度量、随时收集这些数据，给你后面用。

#### 测试目标的明确写出

第二，你在做 `testing` 之前，一定要把那个 `testing objectives` 非常清楚明白地写出来，写在你的测试计划里面。

比如我要测这个软件的可用性：这个软件的可用性包含了哪几个功能、哪几方面的可用性？我要测它的 `performance`、它的效率：它是哪几个方面的效率、我要测哪几个点的效率、测到什么指标？就是我到底要测什么东西，每一个测试的目标你都要非常清楚地写出来。

#### 用户类别与用户画像

第三，你还是要分析一下、了解一下你的用户，然后要很清楚地写出来，这一条叫 `Identify categories of users and develop a profile for each.` 你的用户群大概分几类，每一类它的 `profile` 你都要写出来。

其目的是：你去测试的时候，最后你要模拟你这个用户的习惯去用这个软件。前面那个飞机的自动导航软件，如果他很有认真地去做了这件事情的话，他就不会出那个悲剧——就是这件事情没做好。

#### 快速迭代的测试流程

第四，你的 `test plan` 最好是一种 `rapid cycle`。`Rapid cycle` 是什么意思？就是快速的、渐增迭代式的这种风格的测试流程比较好。

而不是那种一次性想把它测得很完整，然后才来总结一下看看。它一般是一个功能加进来测一下，一个功能加进来测一下，然后很快地迭代——是这么一种风格。

#### 软件自身的可测性

第五，希望你们开发团队开发出来的这个软件本身是比较 `robust` 的：`Build robust software that is designed to test itself.`

简单来说，你不要动不动就"蓝屏"。你们这个年纪没有经历过蓝屏吧？用过那种蓝屏的 `Windows` 吗？看来你们还有点年纪，还不能算太小——再后面的小孩子可能都不知道蓝屏是什么东西了。当年那个 `Windows` 真是动不动不知道按了哪儿，然后它"砰"就蓝屏了。

那如果你的软件本身就是做得动不动就蓝屏的那种，那就测不了，没法测下去。所以你的软件系统在设计的时候，你最好就考虑到各种异常，然后你自己有异常处理，然后你会抛出那种比较有用的异常信息，让别人知道：我出现这个信息的时候，我知道你走的是哪条路、这条路走得对不对。这就是 `robust software` 的意思。

#### 正式评审作为过滤器

最后一条，你最好用一下 `formal reviews as a filter`。

在你正式地去测那个代码之前，可以先有一种 `formal review` 的机制。`Formal review` 的意思就是：我不是去运行你的代码——你就给我讲一下，大家就过一下。你大概把你这个程序打算怎么从上到下走、有几个分支是怎么走的讲一遍，然后有一帮人在那儿听；实际上就相当于有一帮人在那儿帮你做 `testing`，在做抽象的 `testing`。

它作为一个过滤，可以帮你过滤掉大部分的错误、关键的错误。把这些东西过完了以后，你起码大面上都是对的了，然后剩下的就是你实现细节的问题了。

### 本讲提到的题目

**讨论题：把"已经找到了 90% 的 bug"这句话量化出来**

题干：老板希望知道测试大概进行到什么程度了。有的公司会在报告里写"我们目前已经找到了 90% 的 bug"。问题是：你并不知道全部的 bug 一共有多少个，那么这个 90% 是怎么算出来的、你凭什么算出来？请给出一种把测试进度量化的方法，并把三件事讲清楚——你打算怎么算、你打算怎么获得数据、为什么这么算是比较合理的。

解析：

- 这道题的落点在"分母从哪儿来"。全部 bug 的总数是未知的，比例就直接算不出来；所以关键不是把数字算得更准，而是给自己造一个**已知**的参照量，让比例有分母。随便拍一个"我觉得测完 90% 了"，缺的正是这个分母——文章正文里那句"毛估估你也要有一个根据"，要的就是这一步。
- 正文给过一种现成的做法：按以往经验设计 N 个错误，悄悄植入软件，再交给测试人员去测；每周从报上来的错误清单里统计植入的那些错误被找出来多少。植入的错误 90% 被找到，就说测试完成了 90%。它站得住的原因就是分母（植入的 N 个错误）是自己造的、完全已知的。
- 用这个办法答题，还要把它的代价一并说清楚，这也是正文点到的：植入错误成本相当高；而且你植入的错误本身是否"干净"、对软件会产生什么样的影响，你并没有十足把握。
- 另一条思路在正文收尾处：从公司的第一个 `project` 开始就随时度量、随时收集数据，用这些积累下来的数据去估计"这类模块通常还会剩多少错没被找出来"。这一条的根据是历史积累，不是当场拍脑袋。
- 这一题没有任何唯一答案——课上明确说了答案绝对不唯一，有很多种办法。判断好坏看的是那三句话本身是否自洽：算的方法、数据来源、以及这么算为什么合理。

## 第 2 章：第18讲 测试策略-2
> 对应分集：P18 | 原始标题：《第18讲 测试策略-2》

上一讲我们把测试的组织方式和技术评审讲完了：你打算怎么测、你设计的每一个 `test case` 都要写清楚测试目的，这些东西要经过一轮正式的技术评审（formal technical review）让大家帮你检查一遍，后面的工作才会更有效率；最后还要对测试过程建立一个持续改进的路子——不断积累经验、随时采集数据，让以后做其它项目时测试做得越来越有效。

这些是"大面上"的策略。接下来就该落到具体的测试类型上了：`unit testing`、`integration testing` 等等，一个一个过。

### 1. 单元测试：驱动模块与存根模块

对传统的软件工程来说，**第一步要做的就是单元测试**。

它要做的事情很朴素：你给我一个模块（module），这就是要测的对象；我准备一堆 `test case` 灌进去；最后输出一份结果（results）——一份 bug 清单。

`test case` 要覆盖哪些方面，是下一次课要仔细讲的具体内容：接口（interface）、数据结构（data structures）、边界条件（boundary conditions）、独立路径（independent paths）、出错处理路径（error handling paths）。你针对这些方面设计好 `test case`，再拿它们去做这个模块的测试。

而在单元测试这一环，有**两个地方是要实实在在花工作量的**，也就是你要动手写两种东西：`driver` 和 `stub`。

#### 1.1 驱动模块（driver）

`driver` 是什么？如果你做过任何一个 Online Judge——ZOJ、PAT 都行——那它就很像那个 Judge 软件：Judge 软件就是 driver，你写的东西就是 module。你交上去一份 solution，它得想办法让你的代码跑起来。

要说更准确的例子，是我那门数值分析（Numerical Analysis）课：你只交里面的一个函数，`main` 函数是我写的。因为我只让你写其中一个函数，而我得测这个函数的功能，所以我必须写一个能让这个函数跑起来的东西——这就是 driver。

driver 要做的事：接收所有的 `test case`，把它们一个一个喂给模块，把模块产生的结果打出来，再检查结果是不是有问题。所以一个 driver 的模板通常就是这个流程：

```text
         +-----------------------+
         |        driver         |
         |  读入 input（测试用例） |
         +-----------+-----------+
                     |  逐个取出 test case
                     v
         +-----------------------+
         |   module（被测模块）    |
         +-----------+-----------+
                     |  返回 result
                     v
         +-----------------------+
         |  输出 result 并检查     |
         +-----------------------+
```

读图说明：driver 是包围在被测模块外面的那层"壳"，它负责供数据、调模块、收结果、做比对，被测模块本身不需要知道自己在被谁调用。

#### 1.2 存根模块（stub）

但有时候事情没那么简单。driver 调用这个模块时，会发现**模块里面还调了一个子模块（sub-module）**。这时候如果结果错了，你就说不清是谁的错：是你正在测的这个模块错了，还是它下面调用的那个模块错了？

为了保证错误清清楚楚地来自这个模块、而不是来自它的 sub-module，你就得再写一个东西，叫 `stub`，中文翻译成"存根"。stub 是一个**假的 sub-module**：它的接口跟真实 sub-module 一模一样，但内容是空的、是假的。

真实的 sub-module 里会拿你传进去的参数做一堆计算再返回一个值，而 stub 的做法是：

1. 先把传进来的参数打出来看一眼——确认我调用它的时候传进去的参数是对的；
2. 然后写一个类似 `switch-case` 的结构，直接返回那个**已知正确的值**。

为什么能这么做？因为你事先就知道自己的 `test case` 有哪些，也就知道：对这些 `test case`，这个 sub-module 如果执行正确，正确的返回值应该是什么。

```text
  参数进来
     |
     v
 [打印/记录参数]  ---------> 确认调用方传参正确
     |
     v
 [switch-case 匹配测试用例]
     |
     +-- case 1  --> 直接返回该用例的正确返回值
     +-- case 2  --> 直接返回该用例的正确返回值
     +-- ...    --> ...
     |
     v
  返回值出去（不做任何真实计算）
```

读图说明：stub 只做"认用例、返正确值"两件事，不做计算，于是它把下层的影响人为地清零。

这样一来，所有被这个模块调用的 sub-module 都保证没有产生任何错误、返回的都是正确值。那么如果 driver 最后输出的结果不对，就只能是**这个模块自己的问题**，不会是 sub-module 引起的。

> **易错点**：stub 的返回值是照着你自己的 `test case` 事先写死的，它只能证明"在下层完全正确的前提下这个模块对不对"，不能替代对下层的真实测试。

这件事在足够复杂的系统里工作量相当大：如果一个模块比较复杂、调用了很多底层模块，那你每个底层模块都要写一个相应的 stub，并且针对每一个 `test case` 去返回它的正确值。

所以这也就牵出了策略问题：**你到底是自底向上测，还是自顶向下测**？一种做法要写很多 stub，另一种做法要写很多 driver，都得花工作量。

### 2. 集成测试与大爆炸式集成的问题

集成测试有一种策略叫 `big-bang testing`：每个模块分头去测，然后"啪"一下全部合到一起。

我们这门课的测试策略就有点像 big-bang：要求大家提交的 Version 1、Version 2，都是五个组各自验收、各自都是对的；到期末考试结束以后 72 小时之内，你们得把这五个组"啪"地合成一个系统，我来测一下。这就是 big-bang testing，也是我的最终验收测试。

但这是**最后的验收**。至于你们五个组合成系统之后，内部自己怎么测——你觉得 big-bang testing 好用吗？你真敢这么干，肯定要悲剧的。

这个词念 `chaos`，不要念成"靠死"，就是"一团混乱"。为什么会一团混乱？因为你最后啪一下合到一起，发现整个系统运行不正常，而**你不知道是谁的错**。好几个人、好几份工作合在一起，谁都说不清楚，于是大家开始互相 finger-pointing："这肯定是他的"、"这显然是他的"、"这一定不是我的，我都测过了"。每个人都测过，每个人都认为自己的东西一点问题都没有。

> **结论**：big-bang 最大的问题是 `isolation of causes is complicated`——原因没有办法隔离，你不知道到底是谁的错。

**十几年前的一个真实教训。** 当年我留数据结构的 project，允许三个人一组，说最后一个 project 稍微复杂一点，建议你们三个人每人负责一个模块、各负责一个小功能，最后三个人合起来；合得成的组，打分的起评分可以高一点。于是有几个组胆子很大，去 challenge 了一下。

结果：**凡是去 challenge 这个的，就没有一个组合成的。**

那个题其实就是一个**最小生成树的算法**。最小生成树大家记得怎么做吗？里面要牵扯好几样东西：你每次要拿一条最便宜的边出来，所以要用**最小堆**；你要判断新加进去的边会不会构成环，所以要用 **union-find（并查集）**；你还要维护一个树、维护一个图的结构，最后输出整棵最小生成树。

三个人分一下工，每人负责一块，每个人都号称自己这一块是好的。等他们把三块凑成一个最小生成树程序的时候，就各种乱七八糟，最后一分钟还搞不定，**没有一个组搞定**。

所以你就知道了：集成测试其实是件非常讨厌的事情。

### 3. 组装策略：自顶向下、自底向上与三明治

改进的方法有两种典型策略。

#### 3.1 自顶向下（top-down）

`top-down`（自顶向下）意味着你要写**很多 stub**：从最顶端的模块开始，也就是最面上那个控制模块先测，先写两个 stub 顶上去返回数据；然后用真实模块去替代那个 stub，一层一层往下替，直到最后测到底层模块。

它的好处是：**主要的控制点、决策点（major control or decision points）是最早被测到的**。道理不难懂——如果大方向有错误，底下工作的人再努力也没有用，你可能越努力就错得越厉害。大方向先要测对，所以 top-down 就是先测大方向，再测底下具体的工作情况。

它的缺点是：**从下面流上来的数据一直是假的**。你要到最后才会接触到真实底层数据往上流的情况，而真实的数据可能比你想象的要复杂得多。从上往下看，每个环节给你的都是理想数据；到最后一天你才发现，下面的数据原来如此。

#### 3.2 自底向上（bottom-up）

与它相对的策略是 `bottom-up`（自底向上）：先把底层测了。大体把底层模块分成堆，一堆一堆都测好；每测一个底层模块，当然都要给它写 driver，而且写的是不同的 driver。然后用真实模块去替代 driver，继续写上层的 driver，一层一层往上走，最后把顶端的模块测掉。

它的优点和缺点跟 top-down 正好**反过来**：

- 优点：下面工作模块传上来的都是**真实数据**，你不用写 stub——stub 其实是比较难写的；
- 缺点：最主要的、领导层面的控制模块是最后才测到的，万一最后发现它错了，下面全白干了。

#### 3.3 三明治集成（sandwich testing）

实际测试时很少这么极端，说我只用 top-down 或我只用 bottom-up，一般是综合着用。还有一种策略叫 `sandwich testing`：sandwich 就是三明治、夹心的面包——一部分人从上往下测，一部分人从下往上测，大家在**中间某一层汇合**。

三种策略的取舍，可以并排放在一起看：

| 策略 | 主要依赖的辅助模块 | 最早测到的部分 | 主要风险 |
| --- | --- | --- | --- |
| 自顶向下（top-down） | 大量 stub | 主要控制点与决策点 | 上层长期只见理想数据，底层真实数据的复杂性暴露太晚 |
| 自底向上（bottom-up） | 大量 driver | 底层工作模块 | 顶层控制模块最后才测，一旦错了下面全白干 |
| 三明治（sandwich） | 两者混合 | 上下两端 | 需要在中间某一层完成汇合，汇合层的协调成本高 |

读表说明：三种策略的差别，本质上是"你先相信哪一头的正确性"，代价则体现在辅助模块的编写量上。

### 4. 回归测试（regression testing）

`regression testing` 中文叫**回归测试**。它发生的场景是：我已经测过一遍了，然后发现一个 bug，改了它。改完之后**不是只测我改的这一块**，因为我的改动有可能会影响到别的模块，所以要把以前虽然已经 pass 过的那些 case 再重复执行一遍。

> **提示**：回归测试不等于把以前所有测过的 case 全部重跑一遍——那太耗钱、太耗时间。你要选一些比较重要的、比较相关的部分重新测一遍，这就叫回归测试。

**回归测试没做好会出大事，有这么个例子。** 一个电话局的系统升级，升级以后没做回归测试，结果**区号搞错了**。

美国的电话是按州设区号的，就像杭州是 0571 开头一样，每个州有自己的区号。但有的州非常大，比如加州，它不止一个区号——一个州内不同地区有几个不一样的区号。通常我们认为：从一个区号打到另一个区号，就是长途电话（long distance）。比如我从杭州 0571 拨到上海 021，这就算长途，这笔单子会被转给长途电话公司；长途和本地（local）是两个不同的部门，账单从两个不同的出口出来。

但如果你是在加州以内，虽然区号不同，**都还在加州以内，那就应该算 local**。这个系统升级是给 local company 做的，结果它把这件事搞错了：本来人家打的是加州以内的 local 电话，出来的却成了长途电话的账单。

于是客户去找 local 电话局 complain，local phone company 说这是长途电话局搞错了，你应该去找长途电话公司；他再去找长途电话公司，long distance 查了半天说不是我们的错，是你们 local 的错。客户就在两种公司之间被踢皮球，这个感觉非常差。

顺便说一段当年的事：美国那时候有好几家不一样的长途电话公司，至少三家同时在打仗——当年我在美国的时候，AT&T 和另外几家（还有 Sprint，还有一家我现在都忘了名字）互相抢着降价，后来不仅降价，还贴钱给你："你这个月转到我这儿来，我送你多少钱。"打到这个程度，最后好像几败俱伤，还是财力最雄厚的那家站住了，另外两家小的全被它灭了。灭了以后 customer 就开始倒霉了——打仗的时候你到处占便宜，只剩一家老大的时候，你就任他宰割了。不过我运气好：他们打仗的时候我在美国，他们尘埃落定的时候我已经在中国了，所以我是便宜占够了回来的。

回到这个例子：**问题就在于你升级之后，回归测试没有测完整**。你不可能做完全的回归测试，但那些比较重要的回归测试该做的没做，就会出这样的问题。

### 5. 冒烟测试（smoke testing）

传统软件工程里还有一个叫 `smoke testing`，冒烟测试。你知道它为什么叫"冒烟"吗？这个名字是从**硬件测试**来的。

硬件测试是这样：我弄一块板子，把做好的一个零件往上面一插。新插进来的零件插进去没事、都好的，那这个零件是好的；如果它一插进来"砰"一下，板子冒烟了、炸了、短路了，那就通常说明**很大可能是你新插进来的这个零件是坏的**。这就叫冒烟测试。

在软件测试里，"板子"是什么呢？它叫一个 `build`：一个**已经测过的、可信的东西的集合**，里面包括源代码，也包括数据库，以及其它相关的、都已经测过的东西，全部放进一个小的集合里，这个集合就叫一个 build。

然后你每天做的事情就是：往里面加一个 component，全部运行一遍；再加一个 component，再全部运行一遍。如果加进去某个 component 之后全部运行发现走不通了，那通常就是**你新加进来的这个 component 有问题**。每一天把不同的 build 都测好之后，再把它集成一下、再测一遍——每天迅速地去测。

> **易错点**：这里的策略关键是**怎么划分 build**。build 不能是一个很大规模的东西；你要是把整个软件当成一个 build，那每天测一遍就非常费劲。你要很巧妙地把它划分到合适的 size。

这种策略通常用在 **time-critical projects**（时间特别紧的项目）上：事情要得特别急，你需要很迅速地测一些东西，那这是一个可用的策略。

### 6. 测试准则（test criteria）的几个方面

一般的测试准则有这么几类，很快过一下：

- **接口完整性（interface integrity）**：要有一类测试专门去测接口；
- **功能正确性**：要有一类测试去测功能是不是对；
- **数据结构**：测局部与全局的数据结构（local / global data structure）定义得是否正确；
- **性能**：当然还需要测 performance。

书上有两页内容专门教大家怎么写 `test specification`，里面给了不少建议——那就是你们下一次要交的 report，一定要仔细去看一下。

### 7. 面向对象（OO）的测试

OO 的测试相对来说复杂一点。

#### 7.1 类作为测试单元

单元测试在 OO 里，一个 unit 相当于一个 `class`。但类测试跟我们普通的单元测试**不同**：普通的一个 unit 基本上就完成一个功能，它就是一个功能模块，你只要测它这个功能完成得正确不正确就可以了；而**一个 class 可不止一个功能**，它是一个对象，这个对象要干好多事情。

麻烦就在这里：你不太可能把一个功能一个功能单独拎出来测——**即使它每一个功能单独都是正确的，也不代表你这个 class 的实现就是正确的**。一个 class 相当于一个小软件。所以你要测的不只是它的操作（operations），而是要根据它的**状态行为（state behavior）**去测这个 class。

回过头看我们前面讲的 `state transition diagram`，它有两种：一种是大的，讲整个系统在运行过程中处于哪几个不同的状态、怎么转换；一种是针对每一个 class 的，一个 object 在系统运行过程中有哪几个不同的状态、这个状态由哪几个动作来完成迁移、来触发它做状态迁移。**这些就是你要测的点**，而不仅仅是要测功能本身它的算法是不是正确。

> **结论**：类的测试不是基于数据流图的，它是基于状态行为来测的。

集成测试在 OO 里就更复杂了。为了尽可能测全面，书上建议了三大类策略。

#### 7.2 基于线索的测试（thread-based testing）

什么叫基于线索？我给了系统一个输入，输入以后系统里各个对象就开始**互相协作**，去做一系列动作，最后完成一个任务、给出一个输出。从输入到输出，加上中间这一系列动作，就是一个线索——一个 `thread`。

那我要测的就是：这个 thread 的执行过程中间，每一个 class、每一个 object 的表现是不是都是对的。`thread-based testing` 就是一条线一条线一条线地测过来。

> **提示**：说白了，这其实就是 **use case**——针对你那个需求，一个 use case 一个 use case 地测过来。

#### 7.3 基于使用的测试（use-based testing）

`use-based testing` 有点像传统的自底向上测试：先找一些**基本上不怎么用到别人**的 class——它们比较独立，做自己的事情，是被别人调用的，不太调用别人。先把这些 class 测好，然后再去测调用它们的那些 class，再一圈一圈地往外扩。

这就像传统软件工程自底向上：最下面是自己干活的模块，然后是上层谁调用了它，再上层又是谁调用了它，一层一层往上走。

但要注意差别：**传统架构是层次往上走的，而 object-oriented 不是这么一个结构**——它是一个图，互相乱七八糟地调用，所以它更复杂。不过这也是一种策略。

#### 7.4 簇测试（cluster testing）

还有一种策略叫 `cluster testing`。还记得前面讲过的 `CRC cards` 吗？CRC cards 最重要的是什么？是它那个**第二个 C——collaborators**。

一张 CRC card 描述了一个 class，同时还描述了跟它相关的那些 class 都有哪些。于是你要做的，就是**一拎拎起一串，而不是拎起一个**：你拎起一张卡片，这张卡片链接到其它卡片，你把所有跟它相关的卡片全抓出来，抓出来一坨——这就叫一个 `cluster`。然后你就论墩地测，一堆一堆地测，把它们之间的协作（collaboration）都测清楚。

### 8. 确认测试（validation testing）与验收方式

确认测试要看的，是你那份 `requirement specification` 最后的 **validation criteria**，然后用里面的 `use case`、行为（状态）、`event flow diagram` 来跑一遍。也就是说，最后 TA 会照着你们这份需求来跑一遍。

除了跑功能，它还要检查**配置（configuration）**：文档、数据库等等各种东西是不是都配齐了。

确认测试有两种方式：`alpha testing` 和 `beta testing`。你们经常在网上看到人家推出的试用版叫 beta 几点几——那些的 alpha testing 已经过了。

#### 8.1 Alpha 测试

`alpha testing` 是：你把 TA 叫到你那儿去，但是**你不许 TA 碰你的机器**。他在后面看着，你来操作给他看：你操作这个软件，说"这个功能是这么用的"、"那个功能是那么用的"，给他做一遍，然后问他觉得可不可以。

#### 8.2 Beta 测试

`beta testing` 是：**你靠边站**，TA 坐下来，他来用这个软件，你在后面看着。这时候你不能抓住他的手说"这个地方你不能乱动"——不可以了，他想怎么动就怎么动。

这就好像一个游戏推出 beta 测试版放到网上去，你还管得到那些玩家吗？你说这个地方不能碰、那个地方不能碰？那时软件已经在玩家手里了。这就是 beta testing。

> **易错点**：无论哪一种，都**一定要有一个文档人员在旁边记录 `deficiency list`**，也就是错误清单。

### 9. 系统测试（system testing）的几种类型

#### 9.1 恢复测试（recovery testing）

**95 年的时候，我们学校主办了 ACM-ICPC 国际大学生程序设计竞赛亚洲区赛**，就在我们学校办，当时搞得我们很紧张。比赛之前我们要做的一件很重要的事情，就是恢复测试——因为你要想到：比赛中间如果系统崩溃了怎么办？

如果系统崩溃，我们有一个备用系统，你要**立刻切换到备用系统，而且保证不丢任何东西**：原来所有的 submission 全部都在，立刻迁移到备用系统，然后大家可以继续比赛。

当时我们的"狗狗同学"吴家智是场地主裁判、总裁判，备用系统是他自己亲自做的。做完了要到赛场去测一下，怎么测呢？就是做恢复测试：

- 现场一百多台机器，每台机器上装一个机器人；
- 一声令下，所有志愿者启动机器人，这些机器人就疯狂提交；
- 哗一下，系统当然马上就被冲垮了，服务器挂了；
- 挂了以后马上启动备用系统，把服务器的数据做迁移。

这就是一个 recovery testing：**我先让它垮掉，再让它恢复，我看恢复的程度如何。**

结果很悲剧：一直弄到半夜快 12 点才搞定。狗狗同学在他自己的笔记本上做那个系统一点问题都没有，放到赛场的服务器上就不对了。你知道最后的错误在哪吗？**在于服务器上装的 Linux 版本跟他笔记本上那个 Linux 版本就差了一点点**——版本问题，差那么一点，然后就不对，死都不对。

#### 9.2 安全性测试（security testing）

`security testing` 比较好理解：就是要试各种黑客攻击，看你那个系统的防御能力。

#### 9.3 压力测试（stress testing）

`stress testing` 跟 recovery testing 通常是**合在一起做**的。压力测试要回答的问题是：**到底多大的冲击量是这个系统可以承受的**，它能承受的最大冲击量是多少。也就是说，所有机器人一起攻的时候，你要看它到什么程度服务器就挂了。

这在实际比赛里是有用的：比赛中间你要设一个门槛，比如说"一秒钟之内不能提交超过多少次"，这个次数我要**根据 stress testing 的数据算出来**，然后做事先的防范——我当然不希望它挂掉。

#### 9.4 性能测试（performance testing）

`performance testing` 比较好理解：测一下这个效率。

### 10. 调试（debugging）的过程与技巧

时间不多了，调试大概说一下。`debugging` 就是这么一个过程：

```text
  执行 test case
        |
        v
     发现错误
        |
        v
  猜测/估计错误是由什么造成的
        |
        v
  加一些 additional test（新的 test case）去验证
        |
        +---- 没证明 --> 回到"重新猜测"
        |
        v
   证明的确是这里错
        |
        v
      改正错误
        |
        v
   做一定的回归测试
```

读图说明：调试不是"看一眼就改"，而是"猜原因—补用例验证—再改—改完回归"的闭环；少了补用例验证这一步，改的很可能不是真正的病根。

调试有很多技巧，它是 **the art of debugging**——调试的艺术，它是一门艺术。

#### 10.1 蛮力法（brute-force testing）

`brute-force testing` 是很古老的、程序员很牛的一种做法。最牛的是 **memory dump**。我还老到不了那个程度，我最多就用过 **spy points**。

老一辈程序员做 memory dump 是什么意思？他把程序出错的那一瞬间的内存**全部打印出来**，八进制的 code，然后从里面读、从里面找错误。

所以你们想想，跟老一辈程序员比起来，你们现在真是弱爆了——现在有那么多好的调试工具。

#### 10.2 回溯法（backtracking）

如果你的程序不是很大，backtracking 的策略是：最后结果不是错了吗？你在程序中间插一个断点看一下，这个时候它是对的还是错的。如果这个时候就已经错了，说明**错误在上面**；如果这个时候的数据是对的，说明**错误在下面**。

> **提示**：你可以把它理解为一个二分的过程。

#### 10.3 归纳法（induction）

**归纳法是在很多公司里用的。** 我以前教的学生里有人说，美国学生暑假去微软打工，干什么呢？每天领一张表做测试：表上告诉你这些输入、然后应该得到这些输出，你就一项一项去做——体力活。

把输出跑出来，然后你就写记录，对的还是不对的。如果是不对的，你要填这么一张表：**三个 W 一个 H**——What、Where、When、How，描述一下你这个错误。

- What：有哪些、有什么、没什么；
- Where：在哪里有、在哪里没有；
- When：什么时间发生了、什么时间没发生。

凡是"有的"东西放在这一栏，"没有的"东西放在那一栏，就填这么一张表。你把这张表交给程序员以后，他就根据你描述的这个现象来猜、来分析大概会有哪些 causes。

#### 10.4 演绎法（deduction）

`deduction` 就是侦探的演绎过程：我先有很多怀疑对象、嫌疑人，然后在调查过程中一个一个地排除，**最后排除剩下的那个就是真正的 cause**。

#### 10.5 改 bug 时的三点注意（bug removal consideration）

最后提醒一下，你在改 bug 的时候要注意三点：

1. 产生这个 bug 的原因，**是不是在程序的其它地方也出现**了？你会不会在其它地方也有类似的错？
2. 如果我把这个错误改过来了，**下一个 bug 有可能是什么**？
3. **总结一下经验教训**：我为什么会犯这样的错误？下次不要再重复犯，怎么才能不重复犯这个错？

### 好测试用例的判定标准

按这本书写作的习惯，讲战术之前先要把审美观建立起来：什么是好的战术、什么是坏的战术。`what is a good test?` 什么是好的测试？先用你们的 common sense 想一想。

#### 测试用例设计的技术含量

出题这件事，有一个 idea 是非常简单的：编程、数据结构有那么多知识点，有那么多算法，我拍着脑子随便就能想一个故事出来。出题真正花时间的地方在 test case 的设计上，最大的技术含量就在那里。你们考过 PAT、玩过竞赛的都知道，题目本身是想得出来的，难的是配那一套测试数据。

> **结论**：一套 case 出得强不强，看它有没有把你所测模块"应该有的性质"都覆盖掉——覆盖得足够全面。

课上我问过这个问题，有同学答的就是这个意思：cover 得比较全面。但如果一个模块可以测的点特别多，你想一个一个测完，大概需要好几十个 case，这在 PAT 那种系统上是很麻烦的：PAT 是分 case 给分的，每个 case 都要单独 run 一遍；每 run 一个 case，系统出于安全性要开一块虚拟空间，把你的程序包在里面转。你要是出了好几十个 case，那个系统就挂掉了。

所以每个 case 还得有充分的代表性，不能有冗余。

#### 冗余与完备测试的分界

什么叫冗余（redundant）？假设我说这个输入数据的测试范围是 1 到 100 之间的整数，然后我测了 `n = 5`、`n = 10`、`n = 18`、`n = 86`——有用吗？有意思吗？我完全可以把 1 到 100 全部测一遍，这个叫**完备测试**（exhaustive testing）：所有可能的输入我都测了一遍，至少对输入来说，是测完备了。那有意思吗？为此设计 100 个 test case，系统就挂掉了，没有必要。那这 100 个 case 里大概有多少个是冗余的？不好说，一会儿我们再看。

#### 最有可能发现错误的用例

一个测试首先必须有很大的可能找到错误。你给了一个 case，如果很多错误都能从它底下溜过去，那它通过了也一点用都没有——错误还是被掩盖着，这个 case 就不好。

就像你们去参加竞赛，题目上面总会印一组 sample input、sample output，为的是让你把输入输出格式的描述看明白。作为竞赛题，特别是国际竞赛题，它那个 sample 给得很少，给得特别傻：你过了这个 sample 其实什么都不表示，你的程序可能 80% 是错的，也能过这个 case。它那个 case 的意思只是——你连这个 sample 都过不了，就不要提交了，提交上去肯定不过。

它是为了提高竞赛的难度，所以先给你看的那个测试很愚蠢，什么意思都没有。PAT 考试不一样，PAT 的 sample 是有技术含量的：一般来说它会 cover 掉一半以上的测试点，你的程序如果 sample 过了，起码有 60% 的可能是对的，剩下 40% 边边角角的测试点再用其它点去测一下。这就是两种不同的策略。

#### 冗余带来的测试成本

`good test is not redundant`，不能浪费时间。你要知道，你是在一个公司里面工作，你的分分钟老板都是要付钱的——他付你工资。你要是做了很多没有意义的劳动，就意味着你老板的很多钱花在了没有意义的事情上面，这是不能接受的。

#### 用例的代表性（best of breed）

还有一条：`a good test should be best of breed`。这个词组听过吗？它原来的意思好像是说，狗有一个全类的比赛，那狗有好多品种，每个品种里头决出一个最好的来，就是 best of breed。

用在测试上：你不可能像刚才说的 1 到 100 全部都测一遍。都测一遍是可以的，那就测完备了，但你的很多时间就浪费了；你要选几个有代表性的，要选最好的、最有代表性的。

打个比方：给你一个很大的面包，然后告诉你只有时间吃一口。这么大一个面包，剩下的时间只够你咬一口，你咬哪？你肯定咬你最好吃、最想吃的那一块，咬一口就走了。测试很多时候就是这个样子。

你做一个 testing team，是有 deadline 的：我只想花这么多时间、这么多精力、就这么多人去做这个测试，但要测的东西非常多。所以你就要精打细算地想好，我要测哪些东西，才能保证这个软件拿出去不至于太丢人；同时把预算控制在这个范围以内，尽可能多地发现错误。

#### 复杂度适中的用例

`a good test should be neither too simple nor too complex`。too simple、sometimes naive，那不行。

什么叫 too simple？一个 case 最好是只为了检查一个错误而设计的：这个 case 对了，说明程序里头肯定没有这个错误；它错了，那一定是这个地方错了。目标特别明确，一个 case 对一个目标来，debug 的时候就很省事——发现它错了，我就知道是这里错，去看这个问题就好了。

但真做到一个 case 只查一个问题，你就要好多好多 case，好多好多 case 就要好多好多人去执行，不合算。所以比较合算的做法是像 PAT 的 sample 那样：一个 case cover 掉 50% 到 60% 的测试点，你把这个 case 攻克掉了，就说明这一堆东西肯定都过掉了，问题不大。

那也不要走到另一个极端。too complex 的意思是：一个 case cover 了太多测试点，结果这个 case 老也过不了——要过它很困难；更糟的是你发现它错了，里面十几个测试点，就有十几种出错的可能，到底是哪里错了？于是 debug 就很困难，你还得再补充其它 case 去定位、去改错。

所以好的 case 是适中的：你尽可能想节省精力，所以一个 case 要多 cover 几个点；但不要 cover 太多，太多了它又没用了——它只能告诉你"这十几个点里有一个是错的"，你还是不知道是哪一个。

#### 设计用例时的三个目标

> **结论**：设计 test case 的时候，脑子里随时要放着三件事——目的（`uncover errors`）、方式（`in a complete manner`）、约束（`with a minimum of effort and time`）。

我们的目标是 uncover errors，是要去找错的。我们希望设计的 case 在方式上尽可能完备（`in a complete manner`）——完备其实说不上，只能说覆盖得尽可能全面，想测到的方向比较全面。约束是 `with a minimum of effort and time`：最少的时间、最少的人力物力，达到最好的效果。

这里有一个反过来说的道理：如果真能做到完备测试，那测试就没有技术含量了——我全全覆盖，就不可能有 bug。但事实上，绝大多数情况下完备测试是不可能的，一会儿我们看一个非常简单的例子就知道。正因为它不可能，设计 test case 才是一门很有趣的技术。

### 可测试性的七个组成指标

另一个概念顺便介绍一下：一个软件设计出来以后，它的可测试性（testability）怎么样？

testability 不像我们前面讲的可靠性（reliability）或者可用性（availability），我没法给你一个公式，让你算出一个百分比来。testability 是由很多个 ability 组成的。大致列一下是这么几个：

```text
 testability
   |-- operability        可操作性：这个软件好不好操作
   |-- observability      可观察性：执行过程你能够看到多少
   |-- controllability    可控制性：测试人员能控制它到什么程度
   |-- decomposability    可分解性：能拆成多小的块
   |-- simplicity         简单性：被测软件本身有多复杂
   |-- stability          稳定性：开发过程稳不稳
   |-- understandability  可理解性：设计文档与代码有多好懂
```

读图说明：可测试性不是一个单一的指标，而是由这一组 ability 共同决定的，其中每一个都会从不同方向影响测试的难易程度。

`operability` 指的是你肯定得能用这个软件、它得是可操作的；如果不可操作，你都不知道怎么测才好。操作的方便性同样决定了测试的难易程度。

`observability` 是你在多大程度上能看到这个程序：看到得越多，就越好测。如果一个软件整个就是一个黑盒子，你就比较没法测。举个例子，我们现在另一个组在跟浙二医院做医学方面的合作，要做一个系统。这个系统以前美国人是做过的——我不说具体是哪个机构做的——他大概是为了版权保护，把它做成了一个完全的黑盒：只有一个接口，就一根网线，卖给你的是一台小型服务器。你有一个界面，上面就一个按钮，要用的时候点一下那个按钮，它把结果给你，中间的东西你完全碰不到。如果这个盒子让你测，你就痛苦了：可能有 N 多地方有问题，但你根本不知道它内部结构是什么样子，也不知道它执行的算法、流程是什么样子，你只知道按一下按钮它出一个结果——这对测试团队来说是一件非常恐怖的事情。所以 `observability` 指的是软件在执行的时候，你能够多大程度看到它的执行情况。

`controllability` 指的是测试人员在多大程度上可以控制这个软件。你有足够大的权限去控制它，就有可能比较好地设计那种自动化的测试。像 PAT、像 ACM 竞赛，人家说的是：我这个裁判直接控制你提交上来的代码，所以我写一个 judge 程序，自动地跑一下，什么都搞定了——这就是 development team 允许你在多大程度上动他的软件。

`decomposability` 比较好理解，就是你在多大程度上可以把它分块：块分得小一点，你测起来就容易一点；如果块很大，里面又很复杂，难度当然就增大了。

`simplicity` 是说，你要测的这个软件到底有多复杂——越简单当然越好测。

`stability` 是说整个软件开发的过程是不是 stable。这个稳定性指的是什么？你不能说我刚把这一块测完，需求就变了；需求一变，设计团队、开发团队哗啦一通乱改，然后又丢给你："你接着测吧。"我这个版本还没测完，他下一个版本又来了，又变过了——那所有人都会很抓狂。所以说让一个程序员发疯是很容易的，你只要改三次需求他就疯了。

`understandability` 也很显然：你看他的设计文档——我们的 test plan 是跟设计几乎同步进行的，需求有了以后，基本上黑盒测试的那些策略都要出来；设计有了以后，部分白盒测试的策略也可以出来了——他的设计、他写的程序代码在多大程度上是可读的、可理解的。你当然要先充分理解，然后测起来才能够效果比较好。

所以我们评价一个软件的 testability 怎么样，就是这么一堆指标去评价它。每一个指标都是一门学问：如果你想把 `observability` 给出一个确切的指标来，你要怎么设计？——这里我只告诉大家有什么，不告诉你怎么做，我只告诉你 testability 是由这么多 ability 组成的。

### 穷尽测试的组合规模

接下来进入具体的策略。上次也说过，在软件测试的不同阶段我们有不同的策略，有的时候用白盒，有的时候用黑盒，这是两大最常见的测试技术。先说一个更根本的问题：`why not try exhaustive testing?` 我们干嘛不干脆做一个穷尽测试呢？

书上给的例子是这样的：一个程序流程图，里面有好多个 `if-else` 分支——数一下，一个、两个、三个、四个，最后是五个，一共只有 5 个分支。然后它告诉你，这个地方是一个循环，这个循环 20 次。每一次循环都有几种可能的走法，一共有 20 次循环，那要设计完备的 test case，需要设计多少个？你要把所有的可能性都测到，这就是排列组合：每次循环 5 种可能，20 次就是

$$5^{20}$$

这是一个十多万亿量级的组合数，按书上的估算，要花差不多 3000 多年，才能把这么小的一个程序做完备测试。

你要知道，这么简单的一个程序、看上去一点都不复杂、几行就写好了、这么短，做穷尽测试都是不可能的，更不要说一个复杂的系统——想都不要想。所以你一定要有一些策略：忽略掉一些情况，然后选最有代表性的情况去走。这就是那两大策略——`white-box testing`（白盒测试）和 `black-box testing`（黑盒测试）。从我画的示意图也能看出来，白盒测试是看得到盒子里面，它是透明的；黑盒是不透明的。

> **结论**：不管你怎么测，只要不是穷尽测试，你就永远不能够说"我可以保证这个软件里面是没有 bug 的"。这句话你说不出来：`testing cannot show the absence of errors and defects`。

你不能说"它通过了我所有的 test case、通过了我非常严格的测试，所以这个软件就是正确的、没有 bug 的"。你只能说：有 bug 你没查出来；以你现在的能力和经验，你查不出来了；在有限的时间范围内，你能测的就这些。

### 白盒测试要回答的四个问题

`white-box` 也叫 `glass-box testing`。顾名思义，你是看得见程序的：你看得见程序内部，非常清楚地知道那个程序流程图。所以这个技术只能用于 `testing in the small`——对小段的代码来做测试。

白盒测试强调的重点是每一个 path，就是程序执行的路径，希望达到尽可能好的对路径的逻辑覆盖。逻辑覆盖是什么意思？一会儿看几个方法你就知道了，它们的逻辑覆盖强度是不一样的。

至少在设计白盒测试的时候，你脑子里有这么几个问题是必须回答的。

**第一个问题：`can you guarantee that all independent paths within a module will be executed at least once?`** 什么是 independent path？

> **定义**：独立路径（independent path）是不可能由其它路径组合出来的路径——它一定至少有一条边是别的路径没有覆盖到的。

你们学过线性代数的话，什么叫 independent vector？线性无关组里面的任何一个向量，都不可以被其它向量组合出来，它总有自己独特的一个点是别人 cover 不了的。independent path 是一样的道理：流程图里可能有好多的路径在走，这些路径是可以组合的——我这两条路径组合一下，组合出第三条路径来是有可能的。一个 independent path，就是不可能由其它路径组合出来的，它一定有至少一条边是别人没有 cover 的。

所以一个最低要求是：你设计的 test case 让它进去走一遍的时候，是不是可以保证它所有的 independent path 都至少被执行了一遍，也就是图里面的每一条边至少被走了一遍。这是一个非常弱的要求。

**第二个问题更强一点：`can you exercise all logical decisions on their true and false branches?`** 凡是有 `if-else` 判断、`switch-case` 判断，有这种控制节点的地方，它是不是 yes 和 no 两种可能都测到了。

**第三个问题：`will all loops execute at their boundaries and within their operational bounds?`** 什么是 loop boundary？循环的边界，就是进去跟跳出来的、一进一出那两个点。比如我这个循环从 1 到 100，那么 1 和 100 就是它的边界。你要设计一个 case 让它只循环一次就跳出来，再设计一个 case 让它必须循环满 100 次然后跳出来——这种就叫 boundaries。

**第四个问题：`can you exercise internal data structures to ensure their validity?`** 比如你定义了一个数组，数组有固定的大小，你就要设计一个 case 让它用到最大的极限，看它会不会溢出、会不会 run-time error、会不会跑到中间就崩溃了。如果你很清楚它的数据结构定义——比如定义了一个 `struct`，里面有字符串、有数组、有指针——你要测的就是这些数据结构内部在程序执行的过程中会不会出现什么诡异的情况。

这四个方面是你在设计 case 的时候随时要想到的：前面两个是关于逻辑覆盖的——每一条边、每一条路都要走一下（independent path），每一个 `if-else` 的 yes 和 no 两个分支都要走一遍；后面两个是关于数据和边界的——一个测数据结构定义，一个测程序的 boundary，boundary 后面我们还会再说，有很多 boundary 要测。

### 控制流图与节点覆盖

白盒测试里头最重要的就是路径覆盖；有路径覆盖，也有节点覆盖。

最弱的一个是 `execute every statement at least once`——每一个语句至少要执行一遍。它要保证的是：你没有哪一段是没意义的、冗余的、直接被跳过去的，也就是说没有这样的语句存在。所以要问：一个 case 能不能把每一句话都执行一遍？

这里有一个技巧。给你一个程序的流程图，看着也比较简单，你要注意：凡是顺序执行的语句，我们都把它缩成一个点，把它看成图里面的节点，编号，然后把它简化成一个 flow graph，一个有向图——一个平面上的、二维平面上的有向图。

有的时候还要仔细看：像那种判断的分支节点，比如它是一个 `do while`，条件是 `total < 1000 and a != 0`，看不清楚的话就过去了。这个条件里面实际上包含的是两个逻辑关系——它有一个 `and`，测的是两方面的东西。所以这个节点最好把它拆成两个节点。

```text
 拆之前（一个节点里藏着两次判断）
     ... ---> < total < 1000  and  a != 0 > ---> ...

 拆之后（串成两个条件节点，边也跟着细化）
     ... ---> < total < 1000 > --T--> < a != 0 > --T--> ...
                    |                       |
                    F                       F
                    |                       |
                    +-----------+-----------+
                                |
                                v
                       （循环出口 / 后继语句）
```

读图说明：复合条件（compound conditions）不能当成一个节点来看，把一个节点拆成两个串起来的条件节点之后，图上的边也跟着细化，相当于这里是两次判断。

### 环形复杂度的三个等价定义

图做好以后，做 `basis path testing`（基本路径测试）的时候有一个数据是要你去算的，叫 `cyclomatic complexity`，环形复杂度。学过图论的同学应该见过这个概念。环形复杂度有三个等价的定义。

| 等价定义 | 内容 | 用下面那张示意图核对 |
| --- | --- | --- |
| 连通域的个数 | 图是画在平面上的，它把整个平面切成了几个连通域，环形复杂度就是几 | 3 个 |
| 边数减节点数加 2 | $E - N + 2$ | $7 - 6 + 2 = 3$ |
| 分支节点数加 1 | $P + 1$，$P$ 是谓词节点（predicate node）的个数 | $2 + 1 = 3$ |

所谓分支节点，就是出去的箭头不止一个的节点——出去有两个箭头的那种。

$$CC = E - N + 2 = P + 1$$

```text
   +------+                N = 6  （节点数）
   |  s1  |                E = 7  （边数）
   +------+                P = 2  （分支节点数）
      |
      v
  < cond A > --T--> +------+
      |             |  s2  |
      F             +------+
      |                |
      |                v
      +----------> < cond B > --T--> +------+
                     |              |  s3  |
                     F              +------+
                     |                 |
                     v                 v
                  +------+ <-----------+
                  |  s4  |
                  +------+
```

读图说明：T 表示判断为真、F 表示判断为假；这张示意图只是拿来核对环形复杂度的三个定义——6 个节点、7 条边、2 个分支节点，用三个定义一路算下来都是 3，平面也确实被它切成 3 个连通域。

课上算的第一个算例是：图上有一个、两个、三个分支点，所以 $3 + 1 = 4$；它的 region 也被整个平面分成四个连通域。所以那个程序的环形复杂度就等于 4。

### 环形复杂度给出的用例数上限

那我的问题是：这个 4 表示什么意思？这个 4 给了我们一个什么样的信息？

我给你一段程序要测，测试目标是每一个 statement 至少要执行一次。我说：大家先把这个图画出来，算一下它的环形复杂度等于 4。于是你就知道了一件事——4 是什么意思？对你来说有什么意义？设计四个 case，这是最少要设计四个、最多设计四个，还是正好设计四个？

> **结论**：这个 4 是**上限**。最多只需要设计 4 个 case，你就肯定可以做到"每个 statement 至少执行一次"，把那些路径都走一遍；当然你也可以设计得更少。

书上给的说法是：`the number of independent paths in the basis set of a program, and provides us with an upper bound for the number of test cases that must be conducted`。

为什么最后那个定义比较有用？因为它是 $P + 1$，说明它跟分支节点的个数直接相关：分支节点的个数越多，这个数就越大。分支节点的个数决定了你这个程序测试的难度——它表示有多少个 independent path 要测：每多一个分支，就多出来一条路要走，所以它算出来的是"最多有多少条不同的路要走"。

### 语句覆盖的强度

前面说的那个最弱的覆盖——`execute every statement at least once`——到底有多弱，我们看一个例子：一个带复合条件的程序，先算它的环形复杂度是多少。有 compound 的你要拆一下，把复合条件拆成两个点，再把图画出来，得到 5。也就是说，我们最多需要设计 5 个 case，就应该可以让每个 statement 至少执行一次。

那么反过来问：真的要设计 test case 的时候，**最少**需要几个 case，才能做到程序里面的每一句话都被至少执行一次？你自己去设计一下——实际上你要设计的就是 `a` 等于几、`b` 等于几，给三个数进去让它跑一遍，看它对不对。

#### 达到语句覆盖所需的最少用例数

答案是一个 case 就够了。这里要注意：条件覆盖是非常弱的，我只是说保证每个语句被执行一遍，我没有说每个分支要被执行一遍。所以一个 case 就可以让它从头走到尾。

我当场设计的那组输入是 `a = 3`、`b = 0`，走下来 `x` 得到 4/3、大于 1，于是又拐到另一支上去，每一个语句都被我执行了一遍——达到了最基本的要求。答案不唯一，你也可以设计其它的输入。

#### 语句覆盖查不出复合条件的运算符错误

但这个覆盖弱在哪儿？假如我在程序里头把逻辑运算符写错了：本来应该写 `and` 的地方，我把它写成了 `or`——你查得出错来吗？查不出来，你这个 case 还是对的，可你的程序有可能是错的。

查不出来的原因，就在于你其实还有一个分支没有测试到。你要是测着走一下那个分支，你就会发现这个地方写错了。

所以更强一点的覆盖应该是：`force execution of each path`，而不是 each statement——`each statement` 这是一个太弱的覆盖。要覆盖每一个 path，用例该怎么设计，就还是要回到前面那套审美观上来：目标明确，覆盖要全，要有代表性，不能冗余，也不能复杂到让你定位不了错误。

## 第 4 章：第20讲 测试方法-2
> 对应分集：P20 | 原始标题：《第20讲 测试方法-2》

上一讲我们把白盒测试的框架搭了起来，说到语句、分支、路径这些覆盖标准。可一落到真话上，事情就变得微妙了：`path` 覆盖说到底是要求每一个分支节点在 `true` 和 `false` 两种情况下都被走到过——`test every condition at least once`。如果你的 `condition` 非常简单，就一个条件，这事当然很简单。问题它经常不是这样的。

### 1. 条件测试：把一个复合条件拆到能设计用例为止

#### 1.1 复合条件的覆盖要求与最少用例数

假定测试代码里有这么一句话，你要把这句话测完备，该设计几组用例？设计目标是明确的：**这一句话里面所有可能的 `true` 和 `false` 都要被至少测到一次**。

难点在于不能漏。所以我要一个系统化的、有规则的测试用例设计方法，保证你不会漏掉。窍门是：先把两个分支当成**整个一句话**来看——一个 `Branch 1`、一个 `Branch 2`，中间是 `and` 的关系。要让整个语句既执行出 `true` 也执行出 `false`，同时两个分支各自也要取到 `true` 和 `false`，那么**至少设计三个用例**就够了：

- 一个用例让它们俩都取 `true`，整个语句为 `true`；
- 一个用例让一个是 `false`、一个是 `true`，整个语句为 `false`；
- 一个用例让一个是 `true`、一个是 `false`，整个语句为 `false`。

第 1 组保证了语句结果为 `true` 的场合，后两组保证了语句结果为 `false` 的场合，同时 `B1` 有 `true` 有 `false`，`B2` 也有 `true` 有 `false`，两边都做到了。

> **提示**：那为什么不干脆写两个 `T` 加两个 `F`（`(T,T)` 和 `(F,F)`）？可以是可以，但不好。`(T,T)` 里两个分支同时为真、`(F,F)` 里两个分支同时为假，两个分支的取值被绑在一起了。用 `(T,T)`、`(F,T)`、`(T,F)` 这一组，才能在一个分支取值变化时观察另一个分支，测的是"这个分支真的影响结果"，而不是"它俩总是一起动"。

#### 1.2 从分支取值到关系表达式的展开

上面用的还是抽象的 `T` 和 `F`，必须再细化一步：**这个 `T` 到底意味着什么**。把原来要测的那句话解开就清楚了。

先说 `B1`：`T` 意味着设计一个用例让 `E1` 和 `E2` 相等；`F` 意味着设计两个用例，一个大于、一个小于，反正两者不等——两种"不等"的情况都要测一下。于是 `B1` 位置上的 `T` 拆成了"等于"，`F` 拆成了一个"小于"加一个"大于"，用例数变成四个。

然后再把 `B1` 换成真正要测的 `E1 > E2`，接着翻译：

- `T` 比较好翻译，直接就翻译成"大于"；
- `F` 要翻译成"小于"加"等于"。

同样的动作在 `B2`（`E3 < E4`）上再做一遍，把四次翻译的结果合起来，就得到下面五组数据。

| 编号 | `E1 > E2` | `E3 < E4` | 这一组要覆盖的取值 |
| --- | --- | --- | --- |
| C1 | `E1 > E2` 成立 | `E3 < E4` 成立 | 两分支同真 |
| C2 | `E1 < E2` | `E3 < E4` 成立 | 第一分支假（小于）、第二分支真 |
| C3 | `E1 > E2` 成立 | `E3 > E4` | 第一分支真、第二分支假（大于） |
| C4 | `E1 = E2` | `E3 = E4` | 第一分支假（等于）、第二分支假（等于） |
| C5 | `E1 > E2` 成立 | `E3 = E4` | 第一分支真、第二分支假（等于） |

> **易错点**：五组用例不都是"新增覆盖"。C1 是最初的 `(T,T)`；C2 是 `B2` 的 `T` 拆出的那一组的第一个；C3 是 `B1` 的 `T` 拆出的那一组的第二个；C4、C5 是 `B1` 的 `F` 拆出的"小于 / 等于"两组。所以分支覆盖的下限是三组，而要做到每个条件都取到每个取值，就得把 T/F 拆开成关系取值，用例数自然涨到五组。哪些是第一遍要的、哪些是拆开之后才冒出来的，看住这条链就不会记错。

一步一步展开完，这句话就满足了 `test every condition at least once`。考试里也常出这种题：给一个比较复杂的复合语句（`compound statement`），要求把它测完备——前提是**用最少的测试用例**，同时保证每一个 `true` 和 `false` 都被执行过，然后看你怎么设计。

#### 1.3 数据流测试：def 集合、use 集合与 DU 链

另一种白盒测试叫**数据流测试（data flow testing）**。它关注的是数据在程序里的变化：一个变量实际上在程序里取值是怎么变的。就像调试的时候，你要一步一步执行下来，看它那个值取到多少、又取到多少——它关注的是一个 `variable` 的变化过程。

做法是把程序拆解，对**每一个变量**去找它在哪些地方被定义、在哪些地方被用到。由此有两个概念：

> **定义**：对一条语句 `S`，`def of S` 是**所有在这条语句里被定义的变量的集合**——有哪些变量是在这句话里被赋予了初值、拿到了一个值，它就是在这句话里被定义的。`use` 则是**这句话用到了哪些变量**：它在读取这些变量的值，虽然并没有改变这些值。

把语句这样拆解之后，就可以为每个变量找它的 **DU 链（definition-use chain，定义-使用链）**：一个 `D`、一个 `U`，一个是定义，一个是使用。它要看的是这个变量在哪几条语句里被定义、在哪几条语句里被使用，而且**要顺序地往下走**——上面那个定义在中间没有被改动过，下面某条语句用到它时，用的确实是上面给的那个定义。这样串起来的一条链，就是 `the flow of X`，也就是变量 `X` 的值在程序里的变化路径。

对应的覆盖标准是 `every DU chain is covered once`：**以 DU 链为单位，一条链一条链地测过来。**

> **提示**：数据流测试比条件测试更细的地方在于，"定义"和"使用"之间只要被中途改写过，就断开成两条链。所以同一对语句，中间有没有别的赋值，测试的负担完全不同。

#### 1.4 简单循环的边界用例

测试技巧还有很多，除了控制结构，还有**循环测试（loop testing）**。循环有好几种，策略各不相同。

先说**简单循环（simple loop）**。一个循环，你至少要做到**边界测试**：如果是从 1 到 n 去循环，那么循环 1 次、循环 n 次肯定要测。同时还要测：**非法的循环——直接跳过的 0 次循环**；以及有没有可能让它循环 **n+1 次**，会怎么样。然后还有正好卡在边界上的 **n-1 次循环**：循环最容易出错的地方就是边界附近。最后在中间随便取一个数让它循环一下。

> **易错点**：这里的 n 不是事先定好、你让它循环多少次就行。n 指的是**输入数据的规模**。我输入数据的 `size` 有可能是 1，有可能是 100，那么 1 要测一下、100 要测一下，诸如此类。所以简单循环的这组边界用例，落地形式就是"取一组最小规模的数据、一组最大规模的数据、一组中间规模的数据"。

#### 1.5 嵌套循环与串接循环

**嵌套循环（nested loops）**的技巧比较特别：**先让外循环不执行或者只执行一次，然后先把内循环测完备**。内循环测完之后，就把它当成一个已经完整测过的模块，不再去管它，再用普通策略去测外循环。

**串接循环（concatenated loops）**就没什么好说的，一个一个顺着循环往下测就好了。

最后还有一类循环，你碰到就只有一个办法：**直接踢回去，说我不测**。程序不能这么写，不允许这么写程序——把程序直接退回给程序员，拒绝测。

### 2. 黑盒测试：从 testing in the small 到 testing in the large

前面讲的白盒测试（white-box testing）也叫**玻璃盒测试（glass-box testing）**，我们说它叫 `testing in the small`：基本上是在**单元测试**阶段用的，程序还没交出去，就是你自己的这一段程序要做测试，再或者是在调试那个阶段做的事。

**黑盒测试（black-box testing）**呢，基本上是在**集成测试之后**的事情，集成的时候要用到。它顾名思义：我不关心你程序内部的结构，我只关心它的外部表现，我要测的是它的外部表现是不是正常。这是 `testing in the large`。

#### 2.1 黑盒测试用例设计要考虑的因素

设计黑盒测试用例的时候，脑子里要有这么几个关键问题：

1. **功能点**：你这个模块所有应该有的功能，一个个都要测到。
2. **行为（behavior）**：它的表现、它的几个状态，是不是很正常地达到了那几个状态，这要测到。
3. **性能（performance）**：它的效率，如果有要求的话。
4. **输入的分类（classes of input）**：你的输入怎么分类，哪些类比较有代表性——这就是后面要讲的等价类划分。
5. **对什么输入特别敏感**：这一点经常不太有人想到。你的系统对什么样的 `input` 特别敏感（`sensitive`），那个地方要非常小心地测到——如果这个数据有错，你的系统是会整个崩溃，还是会怎么样，那里要测得特别小心。
6. **数据类的边界**：`how the boundaries of a data class are isolated`，你怎么确定每一类数据的边界。
7. **数据速率与数据量**：`what data rates and data volume can the system tolerate`，这意味着你应该做**压力测试（stress testing）**，看你的系统到底能扛多久。

再往外一层，还有**各种输入数据的排列组合**对整个系统表现的影响。要怎么设计这些组合，也是设计策略里要考虑的。

#### 2.2 四种黑盒测试技术

书上大概介绍了四种技术：

| 技术 | 关注的问题 | 本讲的取舍 |
| --- | --- | --- |
| `graph-based testing`（基于图的测试） | 先把系统映射成一张图，再分析这张图的复杂性 | 不展开，属于研究生的更高级内容 |
| `equivalence partitioning`（等价类划分） | 输入应该分成哪几类才等价 | **重点** |
| `boundary value analysis`（边界值分析） | 每一类的边界上该怎么布用例 | **重点** |
| `orthogonal array testing`（正交数组测试） | 多个参数取值范围的排列组合，怎么挑出有代表性的 | 不展开，属于专门技术 |

`graph-based testing` 的思路，其实跟我们讲白盒测试时是一致的：白盒的时候我们把一段程序变成一张图，通过分析图的复杂性来判断测试用例的复杂性、判断测这段代码的复杂性；对整个系统来说，也有办法把系统映射到一张图，再通过分析图的复杂性决定后面怎么做。`orthogonal array testing` 针对的是另一类麻烦：输入进去是三个不同种类的数据、参数，每个都有自己的取值范围，你不仅要测每个参数的取值范围，还要把它们的排列组合有效地测到。穷尽排列组合工作量太大，选择性地测又一定会漏掉一些组合——那怎么确定哪几种组合比较有代表性？这套技术有专门的方法，我们也不讲了。

**实际重点是这两个，所有软件测试里都必须要有：等价类划分和边界值分析。** 而且这两件事是连在一起的：你先划分了等价类，类一划分好，它的边界就有了；然后你再去有效地在边界上做一些重点测试。所以下面重点讲这两类。

#### 2.3 等价类划分

> **定义**：**等价类（equivalence class）**是这样一类元素的集合——`There is no particular reason to choose one element over another as a class representative`。在这个集合里面随便挑哪一个，效果都是一样的。

比如从 1 到 100 这个整数范围里，你挑 18、挑 39、还是挑 97，没有区别。既然如此，那么这一个范围里随便拿一个整数出来都可以，这些整数的集合就叫一个等价类——**因为它们在测试方面是等价的**。

写出来的定义每个单词都看得懂，放到一起的关键就是最后那一句"没有特别的理由挑这一个而不挑另一个"。判定一个类划得对不对，就看这句：类里任意两个元素互换，测试结论会不会变。

书上给的划分指南，按输入的形式分成几种：

| 合法输入的形式 | 等价类怎么划 | 举例 |
| --- | --- | --- |
| 一个范围 | 一个合法类 + 两个非法类，至少三类 | 合法是 1 到 100：类内取一个数；小于 1 的整数一类；大于 100 的整数一类 |
| 一个确定的值 | 等于它一类；大于它一类；小于它一类，共三类 | 合法值是 `X`：`X`、`> X`、`< X` |
| 一个集合 | 属于这个集合的一类；不属于的一类 | 开发一个系统说"教师"是一个集合：所有教师是一个等价类，所有非教师人员是另一个等价类 |
| 布尔条件 | `yes` 一类、`no` 一类 | 条件成立与不成立 |

这就是等价类划分。

#### 2.4 边界值分析

等价类划分好了以后，紧接着就是**边界值分析（boundary value analysis）**。

> **结论**：边界值分析是几乎所有测试里面都必须用到的。

为什么它这么要紧？我们看一个现象：没有考过 PAT、也没有玩过竞赛的人，第一次入门去那个网站上做题，总会有各种哭诉——"怎么会说我这个 `sample` 都是过的，为什么我的程序还有错？"这时候你去看他程序错在哪儿，**绝大部分的程序都错在边界上**。

举个上个月底的真实例子。我们三个老师组队去参加了一下我们的校赛，有一道简单题，多简单呢——何老师瞬间就写了一个十行不到的、这么小的一个程序，结果一交上去就 WA（`Wrong Answer`）。然后我们瞪着眼睛看半天：这么简单的程序怎么可能有错呢？错在哪儿呢？

看不出来错在哪儿的时候，有一个技巧：**设计一个 test case 让它去跑一下**。我就设计了一个用例，这个用例是 `boundary`，直接取到它的最大值——取到最大值转一下，它就崩溃了。为什么呢？因为它的答案超出长整型了。一道简单题，它居然出了一个 `long long` 型的这么个东西，我说这个太恶劣了。可是程序你看不出来错，看着是对的，你怎么知道边界数据一进去它就超过整型呢？

这种 bug 就是喜欢在墙角呆着。**边边角角的地方是最容易出错的地方。**

书上也给了 guideline。如果给的是一个 range，是 `a` 到 `b`，那么：

| 用例位置 | 取值 | 为什么要有它 |
| --- | --- | --- |
| 两个端点 | `a`、`b` | 端点本身合法，必须落在合法类里 |
| 下端点外侧 | 正好大于 `a`、正好小于 `a` | 合法类与下方非法类的接缝，最容易误判 |
| 上端点外侧 | 正好大于 `b`、正好小于 `b` | 合法类与上方非法类的接缝 |

剩下的用法，大家自己去看一下边界测试应该怎么设计。

### 3. 面向对象测试

#### 3.1 OO 测试用例与传统测试用例的区别

接着看**面向对象测试（object-oriented testing，OO testing）**。上一讲我说过，OO 对测试来说是个很大的麻烦，它其实挺难做的。它的一个 `test case design` 跟传统的 `test case design` 是**两个概念**。

传统的测试用例：一个用例就是一个用例，一套输入，我有一个测试目的，然后对着一个输出，仅此而已。但是对 OO 来说，**我设计的不是一个 case，它是一套动作**——我设计的一个 test case 不是一组数据的输入，而是一组动作的执行过程。这是 OO 比较复杂的地方。

那么一个 OO 的测试用例包括什么？

- 首先它得有一个名字，给一个单独的 ID；
- 然后一定要写清楚，它是要测**哪个 class** 的，把类名写在那儿；
- 当然要写清楚**测试目的是什么**；
- 最关键的是一份 **`a list of testing steps`**，也就是测试的步骤。

对每一个用例，你还要交代：这个 class 有哪几个状态，是不是所有的状态都测到了；测状态的过程中，哪些 `message`、哪些接口、哪些 `operations`（也可以叫 `functions` 或者 `methods`）被执行到了；执行过程中要做哪些步骤；测试的外部条件、准备条件是什么；如果它还需要用到其他的 classes，其他的 classes 应该怎么配合。这都是很复杂的事情。

差别根本在哪里？

> `Unlike conventional test case design which is driven by an IPO view of software or the algorithm detail of individual modules.`

传统的测试是把软件看成一个 **input、process、output**（输入-处理-输出）的结构：我只要给一个 input，然后检查它的 output，就知道它的 process 对不对。这是传统测试的观点。但是 OO 呢：

> `OO testing focuses on designing appropriate sequences of operations to exercise the states of a class.`

首先它测的是一个 class，其次它定义的是一系列的动作，这一系列的动作应该 cover 你这个 class 所处的不同状态。所以它整个对测试的理解是完全不一样的角度，也就意味着这个测试很复杂，一个 test case 很复杂。

#### 3.2 OO 测试的几种方法

**基于故障的测试（fault-based testing）**。如果公司里有一个非常有经验的老测试员，他基本上有一套做好的 test case——你把他这套用例不管什么东西拿过来，闭着眼睛执行一遍，如果这一套都过了，那么绝大多数问题就没有了。他的做法就是：先把软件最常会出错的地方都有哪些想清楚，针对这些错误设计 test case。过了一个，就说明**这方面的错误肯定是没有了**。

**类测试与类层次（class testing and class hierarchy）**，这是最让人痛苦的地方。OO 的程序一般都有**继承（inheritance）**这个特征，继承让你在编程的时候非常容易扩展、非常容易裁剪和修改，有好多好多的好处。**测的时候你就惨了。**

你以为你测完了父类，子类那些来自父类的功能就不需要测了吗？不是的，它会变的。你以为你把所有的子类都测完了，父类就不用测了吗？也不是的。这个你其实省不了事，起码不能省事。

> **结论**：编程的时候继承给你省了事，测试的时候它只会让你变得更复杂。

**基于场景的测试（scenario-based）**，就是把 `use case` 拿出来，按照 use case 一个一个地走一遍。这种测试的重点不是软件内部的执行过程——我不关注软件内部逻辑的执行过程，我关心的是**用户的使用过程**，我要保证用户的使用过程是正常的。它的使用过程正常，你内部逻辑仍然有可能是错的。

> **提示**：这几个方法都是站在不同角度看同一个软件，所以最好结合起来用。

**类级别的测试**。除了随机测试，最好还是做事情稍微有点规律——有几种划分方法，就是**分类测试**。分类测试其实跟传统软件工程里面的等价类划分是同一个道理，**只不过你怎么定义等价类**：它不像传统等价类那么容易看出来。你可以这样定义：

- **基于状态（state-based）**：哪些功能让这个 class 从一个 state 换到另一个 state，那么这一类功能放在一起测。
- **基于属性（attribute-based）**：哪些功能集中在改这个 class 内部的某一个 attribute，跟某一个 attribute 相关的所有操作放在一类。
- **基于范畴（category-based）**：就按功能分类——根据这个 class 要完成的几大功能，把它们相应的操作绑在一起做测试。

**类间测试（inter-class testing）**更麻烦：class 跟 class 之间的测试。你大概把那个 class 理解成 `client` 跟 `server` 的关系——一个是使用的，一个是被使用的，`client-server` 的关系。基本的原理是：几个 class 之间的关系先划分成 client 和 server，然后它们之间交互的 `message` 和 `operator` 这个关系也要测试好，还有就是 **collaboration**——它们之间的那种 `collaborator class` 要做相应的测试。具体的不讲了，大家自己回去看一下。但是基本上也是基于 `random` 的，没有什么特别好的办法去测它。

> **易错点**：随机测试（random testing）能做到的第一步是定一个**最小的测试集合**——最低限度我得把这些 cover 了，剩下的分支扩展再用随机组合去碰，"瞎猫抓死耗子"。随机不是不做底线覆盖。

**基于状态转换图的测试**。如果你有非常清楚的**行为（behavioral）**描述，状态转换图画得清楚，那么设计 test case 的时候就可以基于这个 **state transition diagram** 来设计。图里面画的是 state，箭头上画的是"你做了一个什么动作、导致它变成了这个状态"。

```text
        (动作 a1)            (动作 a2)            (动作 a3)
[初始状态] ──────► [中间状态一] ──────► [中间状态二] ──────► [结束状态]
     │                   │                    │
     │(什么都不做)        │(动作 b1)            │(动作 b2)
     ▼                   ▼                    ▼
  直接结束             另一条分支            另一条分支
```

读图说明：实线箭头上的标注是触发状态迁移的动作，纵向箭头表示"在这一步什么都不做、直接往下走"的另一条路径；每条从初始状态到结束状态的走法，就是一个 OO 测试用例——用例的内容是**这一串动作**，而不是一组输入数据。

那用例怎么设计呢？沿着这条线，某些动作肯定要做一下，然后这些动作就可以排列组合：

- 什么都不做，直接做下一个动作，然后结束——这是一个 case；
- 走到这儿，把这个动作做了一下，往下走，结束；
- 或者把这两个组合做了一下，往下走，结束。

随时要记住：OO 的 testing 不是一个 case，它是一组动作，**一个 case 描述的是一组动作**，你就对着这张图去设计你的动作集合。

> **易错点**：基于状态转换图设计用例，用的是"动作序列"而不是"输入值"来标记覆盖。所以判断两个用例是否重复，看的是动作序列是否等价，不是看输入数据是否相同。

除了这些，还有其他一些，像**图形用户界面测试（graphical user interface testing）**、`client-server`，当然你还要测试一下你的 `help`；如果是**实时系统（real-time systems）**，那么 `performance` 也是非常重要的测试内容。

最后建议大家：在测试的过程中如果找到规律，可以抽象出一些 **testing patterns**，以后做 `reuse`。

还有一句提醒：**`testing never ends`**。你即使把活儿交出去了，你的测试也没完，只不过这个测试从你的手里交到了你的客户手里，他会继续替你测试的。

### 4. 本讲提到的题目

#### 4.1 题目：有序整数序列的查找与裁判数据设计

最后一节课留了十来分钟做一道题，出的是一道 PAT 考试的考题。

**题目描述**

在一串整数里面找一个给定的整数。给定的是**有序**的整数，所以我心目中想的是：你总应该用一下**二分查找**吧。如果你不用二分查找，我肯定不能让你过，肯定在一个 case 上要把你卡住。如果有人用比较蠢的办法，比如线性查找，从头到尾扫描一遍找那个东西在不在——这么实现的人，你得把他卡住。

**输入格式**

输入分三行：

- 第一行给一个正整数 `n`，这个正整数不超过 10 万，上限是 10 万；
- 第二行给出 `n` 个整数，每一个整数都不超过长整型——我不要用 `long long`，不要那么变态，用 `int` 就可以了；
- 第三行给出一个整数 `X`。

这 `n` 个整数是按从小到大的顺序给的，并且**保证**是按这个顺序给的。

**输出格式**

如果 `X` 在这 `n` 个整数里面，回答 `yes`，否则回答 `no`。

**要交的东西**

不是写程序，而是**帮这道题出裁判数据**：把测试数据给出来。

- PAT 这个系统不能够测太多的 case，你的 case 无论如何**不要超过 10 个**；10 个太多了，越少越好；
- 同时要设计 `sample in` 和 `sample out`；
- 每一个 case 都要写清楚**测试目的**——你到底要测哪个点，才把这个 case 放在这儿，这个要写清楚；
- 最好把分数也写上，这样更省事：给分原则是 `sample` 过了给一半的分。这道题 20 分，`sample` 过了就给 10 分；那么 `sample` 占 10 分，剩下 10 分分布给其他的 case。也就是说你要给出**每一个 case 占多少分**。

**设计原则**

> **结论**：设计测试数据的原则，一是要尽可能多地 cover 错误、能够找出错误；二是要测得尽可能全面，但要用最少的时间和精力——**用最少的 case 测到最多的事情**。

**课堂讨论中澄清的两处条件**

- 学生问："从小到大是不减吗？"——**不减**。我只是说不减，**不是一定严格递增**，也就意味着可以允许重复的数字出现。
- 为什么允许重复却不影响判题？因为我只回答一个 `yes` 或 `no`，我不让他回答它的位置。如果要回答位置，这就有点不对了。
- `sample` 给几组？有同学问"`sample` 是不是给 `yes` 就一组啊"，那是 `yes` 和 `no` 的问题——`sample` 应该给人家**两组**：一个 `yes` 的 case，一个 `no` 的 case。给两个就好了，你还打算给多少？

**一点补充**

不要看二分查找这么简单的一个东西，你要把它的 test case 做出来，是不是还得**专门写一个 generator**，去生成大数据？我要再出稍微复杂一点的题，这个 case 就要写半天了。

#### 4.2 解析：二分查找的测试点与用例分配

这道题的用例设计，逐条对应上面讲过的规则：

**（1）先把等价类划出来**。这里真正需要分的是"`X` 与序列的位置关系"，而不是 `X` 的取值范围——因为查找的结果只可能是 `yes` 或 `no`：

| 等价类 | 含义 | 覆盖它的用例 |
| --- | --- | --- |
| 命中 | `X` 等于序列中的某个元素 | 各类 `yes` 用例 |
| 未命中（落在序列内部） | `X` 在 `a[1]` 与 `a[n]` 之间，但没有出现 | 落在区间内的 `no` 用例 |
| 未命中（落在序列两端之外） | `X < a[1]` 或 `X > a[n]` | 两个越界的 `no` 用例 |

**（2）边界值分析**。序列的"边界"和 `n` 的规模边界各来一遍：

- `n = 1`：序列只有一个元素的退化情况，查找的下界；
- `X = a[1]`、`X = a[n]`：查找区间的两个端点，二分过程里最先被切到的位置；
- `X < a[1]`、`X > a[n]`：两个端点的外侧；
- `n = 10^5`：`n` 的上限，同时这也是"程序是不是真的二分"的性能判据——用线性扫描的实现在这一组数据上必然超时，正好把该卡的人卡住。

**（3）按等价类的类内取值**。同一等价类里挑哪一个都行，不需要重复布点；上面的用例每一组都只需要一个代表值。

**（4）分值分配**。题目 20 分，`sample` 两组（一个 `yes`、一个 `no`）占 10 分，剩下 10 分分给其他用例，并按"测试目的"标明每一组分多少。

**（5）生成大数据的准备**。10 万个整数的用例，手抄不现实，得写一个 generator 生成，这也说明用例设计不只是"想几个数据"，还包括把数据造出来的工具。
