## 第 1 章：第7讲 需求工程-1
> 对应分集：P07 | 原始标题：《第7讲 需求工程-1》

前面三周都在讲宏观的概念，今天终于开始看上去好像需要干活的样子了。要干的第一件事情就是**需求工程（requirements engineering，RE）**——跟你们要交的第一个 project 直接相关的那件事。不过按这本书的写作习惯，轮到讲需求工程的时候，先讲的肯定不是那些图怎么画。这一讲要说清楚的是三件事：需求工程大概都干点什么事情，它为什么有必要做，以及在做这件事的过程中它有哪些环节、我们都要做哪些事情。仍然是在回答 **what to do**——做任何事情之前先搞清楚 what to do，然后才谈得上 **how to do it**，而 how to do it 是下一节课的内容。

### 1 需求没做好的后果

在讲环节之前，先看一个反面案例：需求没做好，后果是什么。

#### 1.1 Ariane 5：需求文档里少写的一句话

对，1996 年 6 月 4 日。那年你们刚出生吧？那个年纪大概还不记事——记得那个时候的事情吗？那个时候我也刚回国不久，然后就发生了这么一件事情。

Ariane 5 火箭带着几颗卫星升上去以后，就开始像喝醉了酒一样晃，摇来摆去，最后被遥控引爆了。报废的不只是 Ariane 5 这颗火箭：它带了四颗卫星，四颗卫星一起炸掉了。所以 the total cost of the disaster was 500 million US dollars，5 个亿——是美元，5 亿美元。

这是你看得见的损失，它还有看不见的损失。当年这个事故让我们国家赚了一笔：ESA 的 reputation 就没有了，声誉掉下来了，结果你要发射卫星吧，你就来找我们了。所以那一次，我们国家是因为这件事情赚了一笔的。

事情到底是因为什么？后来有一个事故调查，追踪下来发现：**在 requirements documents 里面少了那么一句话**。少了一句什么话呢？就是 Ariane 5 它的轨迹的那个倾角，会比 Ariane 4 的那个倾角要大。就这一点区别没有说清楚，于是它计算轨迹的那个公式就没有改。结果 Ariane 5 升空以后，它的倾角超过了 Ariane 4 的那个倾角的最大值，计算的时候就溢出了。溢出了呢，但是它那个模块没有停止计算，它继续计算，然后算了一堆垃圾数据出来——所以你才会看到 Ariane 5 在天上像喝醉了酒一样摇来摆去，它计算出来的轨道就不对了。

```text
需求文档里少一句约束：Ariane 5 的轨迹倾角 > Ariane 4 的倾角上限
                |
                v
计算轨迹的公式没有随之修改，仍按 Ariane 4 的倾角取值范围设定
                |
                v
实际倾角越过旧公式的取值上限  -->  计算溢出
                |
                v
出错模块既不检测也不停机，继续用溢出后的垃圾数据往下算
                |
                v
轨道结果错误  -->  火箭在空中摇摆  -->  遥控引爆
                |
                v
火箭报废，搭载的 4 颗卫星同时损毁，总损失 5 亿美元
```

读图说明：这条链的起点不在代码里，而在需求文档里一句没有写下来的约束；从少一句话到炸掉五亿美元，中间每一个环节都只是忠实地执行了别人给它的错误前提。

#### 1.2 Standish Group 的调查数据

一两个案例可能是偶然，那么整个行业的情况怎么样？1994 年有一个 Standish Group，对 350 家企业大概 8000 多个 software projects 做了一个调查，看看他们做得怎么样。结果是这样的：31% 的 projects were cancelled before they were completed——还没做完就直接 cancel 掉了，中途夭折的占了 31%。8000 个的 31% 是多少？所以说要开个企业不容易。

再看那些做完的。按照时间、在预算范围内、保质保量 deliver 出来的，在大一点的 company 里面只有 9%；小一点的 company 这个比例稍微高一点，16%。

| 调查指标 | 数值 | 口径 |
| --- | --- | --- |
| 未完成即被取消的项目 | 31% | 8000 多个项目的全样本 |
| 按时、按预算、保质保量交付 | 9% | 规模较大的公司 |
| 按时、按预算、保质保量交付 | 16% | 规模较小的公司 |

为什么小的反而好？小的人少。人少麻烦事就少；公司一大，人都认不全，可以出错的环节就有很多。

1995 年 Standish 继续做 survey，这一次是看原因是什么。高居榜首第一位的是 **incomplete requirements**（需求不完整），第二位是 **lack of user involvement**（用户参与不足）。其实这两件事情差不多是同样的原因，就是 communication 的原因——都是人跟人的沟通方面出了问题。你肯定跟你的 user 没有沟通好，才会有 incomplete requirements 这么一个结果。

#### 1.3 一张讲需求失真的图与 Brooks 的判断

我从网上当下来一张讲需求失真的图，觉得挺好玩的。它画的是这样一条链：**客户如此描述需求**——这是客户描述的，我要这么一个东西；然后项目经理把它理解成这么一个东西；分析员设计的时候把它设计成了另外一个样子；这是程序员的编码；这是商业顾问——商业顾问拿到的是一个豪华的沙发；然后这是项目文档；这是安装程序如此简捷；这是客户投资如此巨大；然后这是技术支持；最后解密——实际的需求其实就是这么个玩意儿。这种事情是经常发生的。

```text
客户的原话  -->  项目经理的理解  -->  分析员的设计  -->  程序员的编码
                                                              |
                                                              v
实际要做的东西  <--  技术支持  <--  项目文档  <--  交付与安装
```

读图说明：需求在每一个转手环节都被重新解释了一次，每解释一次就偏一点，一路偏到最终交付物与客户的真实意图完全不是一回事。

然后我们这位老先生，认得他是谁吗？第一次课给大家讲 IBM 360 的时候提到过，《人月神话》的作者——Brooks，这就是 Brooks 年轻的时候。他说过一句话：

> The hardest single part of building a software system is deciding what to build.

你到底想干嘛？这件事情就是 the hardest single part，是**最难的那一部分**：搞清楚你到底要干嘛。真的搞清楚以后开始做，那反倒不是很难的事情。

### 2 一个人口仿真项目里的需求沟通

上面讲的都是别人家的事故和统计。我说说我们那个**人口学的项目**——它到现在我们还没有完全搞清楚到底要干嘛，这件事已经做了一年多了。最初的沟通是你们的学长去做的，所以现在的 DS 不太清楚当年的情形。当年的情形跟刚才那张图描述的路径还不太一样，但它更典型。

#### 2.1 两位当事人的兴奋点不在一个地方

你要跟一个非本专业的用户去沟通，说我可以帮你做一个系统，会出现一个非常常见的沟通问题：**两家的兴趣是不一致的**。

我说我要来帮你做这个系统，那是帮老先生做一个人口仿真计算。他给我的描述大概是这样的：我有一堆基础数据，这些数据都是准备好的，你只要把它读进来，然后我有一个程序去算那个仿真的结果。

作为一个研究者、一个学者，他特别兴奋，他的兴奋点在于**他那个算法本身**。所以他花了很多时间跟我们介绍这个算法的原理是什么，是怎么仿真的、怎么推算的：你各种政策组合进来以后，我怎么样从一年一年推算——现在允许生二胎，然后 100 年以内，我们国家的人口是怎么变的，等等等等。他花了很长时间给我们描述这个原理。

但是其实这个原理对我们做软件的来说是没有意义的。因为对我们来说只是：你一个程序写好了在那儿，我只要在界面上给你弄一个按钮，你一按那个它就开始算。真正让我们关心的是另一头——算出来的结果他要有一个图形的显示，他需要有哪几种图、哪几种表要给人家看，这个是我们关心的。

他讲的时候，他的兴奋点跟你的兴奋点不在一个地方。我关注的是**你整个执行的流程是什么样的**，他没有太大的兴趣给你描述那个流程，他说流程很简单的：数据导进来算一下，然后这边显示一下，就好了。好简单的一个东西。这相当于他给我描述的是这么一个需求。

> **提示**：这就是需求获取里最要命的一层。你认为对你这个专业至关重要的事情，对他来说他根本不 care，他根本没想到有这个问题；反过来，他兴致勃勃讲的那套算法细节，对你的软件构造又完全没有用。双方都觉得"这有什么好说的"。

#### 2.2 用原型逼出真实需求

我理解了一下之后，就叫学生先去做一个 prototype。**我当初最明智的选择，就是选择了 prototyping 这个 process model**——否则这件事情就麻烦大了。

做了个 prototype 拿去给老先生看，他一看说："没这么简单。"

原来数据导入根本不是他说的"都准备好了，导进来就好"。我当时的理解是：你要么有个数据库，要么有个文件，要么有个什么东西，我导进来就好了——不是的。你在导数据之前还有好多要选的选项，是一个很复杂的选项卡，说了半天才说出来。于是我们把这个选项卡做好，过了个把星期又去跟他沟通：您看看是不是这样子？他说："没有这么简单。"

然后我们就崩溃掉了。每个星期去跟他沟通一次，每个星期你都会发现不一样的需求，他总是会跟你说"没有这么简单"。我们的情形就是：客户做了这么一个描述，我把它做成了一个理解，随后他说不是的，然后下次他告诉你说是这样的，再下次他告诉你说又是那样的。

```text
客户的口头描述  -->  我们的理解  -->  原型 v1
                                        |
                          客户："没有这么简单"
                                        v
                          补出数据导入的选项卡  -->  原型 v2
                                        |
                          客户："没有这么简单"
                                        v
                                     原型 v3  ...
```

读图说明：需求不是一次问出来的，是一轮一轮被原型逼出来的——每一轮都只多露出一点，而且只有在他看见东西之后才说得出来。

#### 2.3 缺少文档带来的接手代价

这个项目我们是没有项目文档的。学生有什么需求，就去记一下，下次在 prototype 里面给他实现一下，看了再改；文档就是没有的。

文档没有，有一个什么后果呢？前一个做这个项目的学长出国，跑到香港交流去了，于是这件事要交给后面的人，包括这小家伙去做。接手的人就崩溃了，说这是一个什么乱七八糟的东西，然后鄙视一下他的学长：怎么可以把程序写得这么乱。

我跟他说，他把程序写得这么乱是有原因的。这个程序不是说"我把所有的需求都搞清楚了，然后我有一个很好的设计、我有一个很好的架构"——根本不是这样的。因为他的需求是一点一点来的，你每一次跟他沟通他就多一点东西，程序是被这样一路推着长出来的。

> **结论**：需求获取可能远比你想象中要复杂得多。特别是你要假设**你的客户不是你这个专业的**。跟他们沟通你会觉得特别吃力，讲话特别费劲：你不能用你的术语，你要用他的术语去跟他讲。否则你就会发现一种鸡同鸭讲的感觉——两个平行的世界里面，你说你的我说我的，谁也没听懂对方在说什么。这个时候你就有大麻烦了，后面就很可能跳到一个坑里。

### 3 需求工程包含的七个环节

在看书上的介绍之前，你先自己用 common sense 说一下：大概都有哪几件事情要做？我现在给你一个项目，你要开始做需求了，你打算怎么做呢？第一件事要干嘛？

就你们现在这个 project，第一件事做了什么？应该已经把第一件事做过了，你们现在应该自以为需求都已经清楚了——第一件事是先看看那个文档的描述，然后要给 TA 打个电话。打过了吗？问过他了吗？还没问过的话，你们后面肯定要悲剧的。

按书上的体系，需求工程大概要做这么几件事情：

```text
  inception --> elicitation --> elaboration --> negotiation --> specification --> validation
      |             |               |              |                |               |
      +-------------+---------------+---------------+----------------+---------------+
                                          |
                                     management
                              （压在整条链上，核心是变更管理）
```

读图说明：横向那一排是需求从无到有、从模糊到写定的推进顺序；management 不是其中某一站，而是压在这条链上的一层控制，因为需求随时会变。

#### 3.1 起始与需求导出

**inception** 就是起手。就像太极拳，或者任何一种拳法，它都有一个起手式，这个起手式就是 inception。它要做的事情是**问一系列问题，把一些事情搞清楚**：

- 你大概要知道你要做的是什么东西；
- 这些是谁要你这个 solution——也就是项目干系人都有谁；
- 你这个 solution 到底是一种什么类型的，你要做的是一个什么类型的东西；
- 你跟 customer 之间、customer 跟 developer 之间，可以期待的那种能够沟通的方便程度。

这是 inception，大概就是了解情况、摸清情况。

**elicitation** 这个词是什么意思？查字典——诱导，也可以说导出。我已经先给了你一个很简单的需求 requirements，但那只是一个非常简单的概述。你要**导出**：把所有相关的人问一圈，你到底想要一个什么样的东西。

客户有的时候自己是说不清楚他想要什么东西的。比如人口学这位老先生，因为他不是这个专业的，所以对于你要做一个软件系统这件事，他觉得没什么好说的——这不是很显然吗？我很显然要这些功能啊。但是你不知道啊，对你来说不显然。

而且他也不太清楚计算机到底能帮到他什么程度。你跟他聊，聊着聊着他发现："哎，你还可以干这个？原来还可以干这个？那你可以不可以给我做这么一个功能？那你能不能再给我做那个功能？"聊着聊着，他的胃口就越来越大，他就越来越兴奋：计算机既然这么有用的话，你还可不可以帮我做成这个样子？像苹果那样在那个屏幕上头，把它拖过来拖过去，我不要拿鼠标去点一个很傻的菜单，看上去好死板的样子；那我怎么打开一个新项目——我手做一个手势就打开一个新项目，等等等等。

这些需求在他一开始第一次接触的时候，他全都想不到。第一次你去跟他接触的时候，他就想着我要做一个人口仿真的这么一个平台，这个平台最亮的地方是我这个算法——他还花了一个晚上给我们讲他的算法。所以 elicitation 的意思就是：你要**主动地**去导出、去诱导，让他说出来他真正想要的那个东西是什么，或者对他有帮助的东西是什么。

#### 3.2 细化、谈判与规格说明

得到了以后回来做 **elaboration**。elaboration 是什么意思？就是**细化**。真的要把它落到纸面上，做成一个 analysis model（分析模型）——下一节课要跟大家说的，你怎么去描述它的 data structure，怎么描述它的功能，还有系统动态的 behavioral requirements（行为需求）。

这个模型的作用是**帮助你跟客户更好地沟通**，prototype 也是。反过来看：如果你只是把他说话记下来，写了一个很长的日记或者纪要，然后让他审查一下"我记得有没有错"，这是很容易出错的。我可以保证，99% 的客户没有耐心仔细地去读你那些文字——纯文字是很不受欢迎的。你要用一堆图形、用大家比较容易理解的方式去跟他沟通，确认你是想做这件事情。

好，确认要做这件事了，那我们就来谈判——**negotiation**，我要不要做这件事情。谈判主要谈的是：既然搞清楚了他要做什么，那**我的成本在哪里，我的底线在哪里**，你至少要给我多少钱，否则我做不来；然后是 **deadline** 怎么设。我就这么两颗人，你跟我说下个星期就要交活，我实在是做不出来，这实在是不可能。这些就是谈判的过程。

谈判完了以后才到 **specification**，就是你真的要把所有的东西写成一个详细的文件，requirements specification（需求规格说明）。这个文件的功能有几层：

- 它是你后面设计的一个主要的依据、基础；
- 它是作为跟用户沟通的一个文档；
- **更主要的是最后的验收**：你要写清楚哪些指标达到了，他就要付钱。这件事情一定要写清楚。

之前很多项目做得很不愉快，也就是这个地方这个文档没有。大家口头上说说。包括其实我们学院里我听过有些老师的故事：做得很不愉快，最后钱没拿到。原因就是你当初说的时候，没有一个很明确的 specification 放在这里。你觉得你把软件做好了交付出去，人家说这不是我要的；或者说 90% 的功能是可以的，但是有一项关键的功能你做错了，所以这个软件我不能用，我不能用我为什么付钱？你这边说你当初是这么跟我说的——那证据呢？证据也没有，文档也没有，什么都没有。最后辛辛苦苦做了半天，做出来的东西没法交付。

> **结论**：specification 在这里面一个很重要的功能，就是它的最后一节要写清楚你那个**验收的条件、验收的 criteria（验收标准）**：哪些指标达到了什么要求，那么达到这些要求，你就一手交钱一手交货。

#### 3.3 需求验证与需求管理

**validation** 是验证。你写好的 specification 肯定要有一个审核、复审的这么一个过程：看看有没有问题、有没有错；有没有漏掉什么东西；你整个的需求里面有没有什么前后矛盾的地方；不同的部门之间的需求有没有互相掐起来、撞车的地方。这些都是审核过程要盯的。

最后，我们还必须有一个 **management**，有一个管理。它要管哪些事情，后面再说；它最主要的一个功能是 **change**。我这里得承认：我这个组做得比较差，基本上没有什么 change management——因为大家都是那个熟人的关系，老先生说有什么 change，我们就 change 了。在公司里头肯定不能是这样的。你有一个 requirement change 的时候，是有一套严格的流程来说要不要 change：你可以 change，change 要加钱。这些控制的过程是要有一个 management 的。

到这里，我们先用望远镜看了一下：需求工程大概要做这么几件事情。接下来就换成裸眼，看一下每一件事情大概又要做哪些，才算完成了。

### 4 起始阶段（inception）要摸清的情况

inception 这个阶段要做哪几件事情呢？

#### 4.1 找齐项目干系人

第一件事情，先搞清楚**这个事情都跟谁有关系**。

一个典型的问题是：**"Who else do you think I should talk to?"** 你跟这个人去沟通、获取了他的需求，那你是唯一跟这个项目有关系的人吗？你是直接用这个软件的人吗？还有谁要用这个软件呢？还有什么人我需要再去谈一谈？

你要把相关的 **stakeholder（项目干系人）** 找齐。

#### 4.2 多方观点与协作关系

接下来要注意的是 **recognize multiple points of view**：各种可能的观点、不同的角度。简单来说就是多找几个人问问，从不同的角度去了解一下你要做的是一个什么样的东西——**不是从技术细节上来讲**。

然后要 **working toward collaboration**，尽可能地营造出一种合作的关系。什么叫营造成合作关系？就是在**多大程度上你的客户愿意配合你**：他是觉得他有义务帮你理解清楚要做的事情，还是他觉得整件事情都是你的，跟我没关系？

你一定要让你的客户搞明白一点：你的工作跟他是随时有关系的，不是说他把这个需求丢过墙去，他就可以不管了。

#### 4.3 第一组问题：项目所处的上下文

书上这本书有点像一本工作手册，里面连要问什么问题，它都给你建议性地列出来。这里只是大概看一下：你上来先问的第一组问题，跟你要做这个软件的内容没有直接关系——你是要了解一下上下文，也就是大概了解一下你的大环境。这一组有四个问题：

1. **Who's behind the request for this work?** 你幕后有没有什么人——是你的上级部门，还是到底是什么人？像你们这个支付宝，你直接接触的人是你们的 TA，对不对？但是 who's behind？是我。我是那个垂帘听政的。
2. **Who will use the solution?** 做出来以后，谁用你这个东西？
3. **What will be the economic benefit of a successful solution?** 这一点非常重要：你这个东西做出来以后，会给你的客户从经济上来讲带来多大的效益。这其实也就决定了你后面一系列的措施都会不一样。
4. **Is there another source for the solution that you need?** 做这个东西你是只找了我这一家吗？你还有别家可以找吗？

这四个问题合起来，就是在判断**客户在多大程度上愿意配合**，也顺带决定了你后面的谈判策略：

| 客户的处境 | 你能预期的配合与后续做法 |
| --- | --- |
| 做成了能给他带来巨大的经济效益，而且你们家的技术力量强到别人家都不找、他就认定你了 | 后面是一整套相应的处理办法，你在关系里是主动的一方 |
| 对他们家只是一个锦上添花的、可有可无的东西，做成做不成反正关系不大，联系你的人觉得花头不大，可能只是为了什么政治任务才要做 | 他后期跟你配合就是另外一个态度 |
| 他其实还有好几家在联系中 | 你还没开始谈判，只是了解一下要做什么，但你的谈判策略后面全都会不一样 |

所以这第一套问题，是要把前后左右的那个关系、这个大环境先搞搞清楚，跟你要做的具体内容还不着急问。

#### 4.4 第二组问题：客户心目中的解决方案

第二套问题才开始问稍微有一点实质的东西：**customer's perceptions about the solution**——在你的 customer 的脑海里，他想要的**大概是一个什么样子**的东西。

要获取这个，基本上就是去**做个 prototype**。如果嫌太麻烦——我有的时候去跟老先生沟通，现场去改那个 prototype 比较麻烦，那我就直接找块黑板，在上面给你画一个界面：你点了这个以后它有一个下拉菜单，把下拉菜单给它画出来，然后这上面是什么东西；然后你点了这个以后——把下拉菜单擦掉——这个上面会出现一个什么样的文本框，它里面是什么内容，你觉得是不是这样的？

就这样给他演示一遍。演示到中间他就会觉得这步不对、这步不是这样的，然后又是那句话：**没有那么简单**。这是我最怕听到的一句话。

#### 4.5 第三组问题：沟通机制本身

最后要问清楚的一点是 **effectiveness of the communication activity itself**：以后你可以期待什么。

比如说你做的是支付宝，它跟金融行业有关系，银行系统的很多规矩在里面。那你告诉我：我不是这个系统的人，我有很多规矩什么都不懂，包括你们的操作流程。那我以后想要了解这些细节的时候，我可以找谁？你那边公司里面、或者银行里面，是不是有一个专门的联系人，我随时可以找他？他忙不忙？他是不是老要出差的？

接着还有一件很实际的事情：这个人来参加我们的组会，有时候我可能会请他来参加我们的组会，那么这些工作算不算他工作的一部分？他拿不拿工资？否则的话，银行里那位领导可能会很不高兴：我付你工资，你是给我干活还是给他们干活？然后你一整天跑去那边开会。我银行里面其实有好多事情要做，我人手都不够，你说你要调他到那儿去开一整天的会——这一天的工资谁付给他？

把这些问题问清楚，你就能够期望在什么程度上这个客户会跟你配合。

这一点有没有问过 TA？你们的 TA 哥哥说他还要上课，然后他还要给我做项目，他也很忙。那么他在多大程度上能够出来，你开组会随时就能叫到他吗？他可能跟你说：可以是可以，提前一星期来跟我预约一下。那你心里也有数了。

inception 这个阶段要搞清楚的，就是这些事情。你想想你前面做了什么、没搞清楚什么，到现在应该知道了。

### 5 需求导出（elicitation）与需求会议

#### 5.1 会议要达成的四件事

导出 requirements 里面很重要的一件事情就是**开会**。必须要坐到一起来开会。

开会的目的是搞清楚我们要解决的是一个什么样的问题，具体有四件事：

- **identify the problem**：先把这个要解决的问题认出来；
- **propose elements of the solution**：这个解决方案都有哪几部分，大家来凑一下；
- **negotiate different approaches**：解决可能有好几种途径，谈判一下大家都 prefer 哪一种、喜欢哪一种；
- 最后给出 **a preliminary set of solution requirements**：大概导出一个初步的需求，这时候你还没有去细化它。

会开完，你手上应该就有这么一份初步的需求了。

#### 5.2 组会组织方式的课堂讨论

这里我把今天的一个问题丢给大家：**你们开过组会了吗？**开过的，描述一下你那个会是怎么开的；没开过的，说一下一个组会应该怎么开。

要具体到这几件事：你要做这个需求导出、要开这个会，它应该怎么一个开法？你应该找哪些人？设置哪些环节？做哪些准备工作？最后你要得到什么？

这个问题的答案没有标准答案，我要看的就是你上路不上路、你会不会开会。**开会也是学问。**

这一讲把需求工程的架子搭了起来：先看清需求不做好的代价，再记住它包含的七个环节，然后把 inception 该问的三组问题问明白，最后把需求会议开起来。会议到底怎么组织、用什么方法把客户嘴里的"想要"翻译成技术员能动手的需求、需求又怎么谈、怎么验，都是下一讲的事。

## 第 2 章：第8讲 需求工程-2
> 对应分集：P08 | 原始标题：《第8讲 需求工程-2》

上一讲把需求工程的框架搭起来了，这一讲接着往下走。一上来先问一句：**你们会不会开会？** 这不是随口一问。需求是从人嘴里挖出来的，而挖需求最常发生的场合就是会议——你跟客户开会、跟 TA 开会、跟自己组里开会。会开得不像话，需求就是一堆糊的东西。所以这一讲的前半段，讲的是一件看起来不像软件工程的事：怎么组织一场有效的需求会议。后半段才回到正题：用什么方法把客户嘴里的"想要"翻译成技术员能动手的"需求"，怎么把需求写成文档，怎么跟各方谈判，最后怎么验收自己写出来的需求。

### 会议的组织：人、规矩、日程、主持、记录

#### 该请谁到场

开会第一件事是把人找对。自己组的人当然要到，此外还有两类人必须请：

- **客户（customer）**：需求会议的核心对象，客户不到场，这个会基本白开；
- **与这个模块关系最密切的其他组的骨干技术人员**：这一点最容易被忽略。你不是在做整个系统，你做的是系统里的一个模块；你的模块要跟别人的模块对接，接口那头的人不来，你讨论出来的东西落地时就会撞墙。

所以开会前先坐下来想清楚：这个会到底要找谁。想不清，就别急着发通知。

#### 会议规矩

人找齐了还要有**规矩（rules）**。会不能是想来就来、想不来就不来的。规矩要解决的核心问题是：**谁必须到，以及你怎么保证他一定到。**

最难保证的就是客户。对方是银行里的工作人员，你说我这边要开个会您必须来——凭什么？你手上有什么措施能让这件事成立？这一条不解决，会议通知发出去也就是个建议。

另一类规矩是会议的频度：组会是定期的还是不定期的？如果是定期的，比如一星期碰一次头，那你要怎么跟人家协商，让"我开会的时候你们都要到"这句话变成对方的承诺。

> **提示**：这里问的不是会议内容，而是会议的组织。内容当然重要，内容是主要部分；但在内容之前，先得把"人齐不齐、到不到、多久碰一次"这几件组织层面的事情定下来。

#### 会议日程（agenda）

会议必须有一份 **agenda，也就是会议日程**。

平时见到的会议通知大多是这么写的：几点钟大家开个会，大概要商量哪几件事。这就算通知了。但真正专业的写法里头要带时间点：

- 几点钟开会；
- 本次会议有几个议题，第一、第二、第三；
- 第一个议题大概讨论多少分钟，第二个议题多少分钟；
- 每个议题多少分钟，整场会大概几个小时。

这样写，是让每个人心里有数：这一天你还有别的事情要安排，如果你从几点到几点来参加这个会，那这段时间给我空出来，剩下的时间你可以安排自己的事。

> **结论**：agenda 的价值有两层——一是大家不会跑题，二是每个人都有一个"我做事很有效率"的感觉。日程不是形式主义，它是替所有参会人的时间负责。

#### 会议主持人（facilitator）

有了 agenda，就一定要有一个 **facilitator，也就是会议主持人**。

主持人的身份可以很灵活：交给客户主持，你自己主持，或者专门请一个第三方来当仲裁，都可以，形式很多。但主持人的功能是明确的——**按会议日程掐时间、管发言**：

- 这个议题说好讨论多少分钟，时间到了就切换到下一个议题，**不管你讨论出结果没有**；
- 时间快到时给个提醒：这个议题一共打算讨论 30 分钟，现在 20 分钟过去了，好像还漫无边际没有头绪，这不行的，大家拢一拢，剩下 10 分钟赶紧商量出一个结论；
- 某个人啰里啰嗦半天说不到点子上，一直在那儿绕，主持人要过去打断一下：请您简短一点，我们时间有限。

如果时间真的不够用，那说明 **agenda 本身就排错了，会议组织人事先没有做好充分准备**。即便如此，时间到了照样要切到下一个议题，这个议题下次再找时间讨论。

道理很简单：每个人的时间都很宝贵。你说好这个时间结束，就一定要在这个时间结束——就像说好了 45 分钟下课，45 分钟一定要下课；你一拖堂，同学们后面那节课就赶不上了。

#### 讨论工具与记录工具

还有一样东西叫 **definition mechanism**：让大家在讨论的时候把东西记下来、看得见的工具。

常规配置是给每个参会的人一张纸、一支笔，随时记；更好的配置是有一块投影或者一块黑板，某个共同的见解要发表出来的时候，在黑板上写两句——大家都同意吗？这样就有了一个讨论的工具，同时也是一个记录的工具。

#### 常见的不专业开法

反过来说，不专业的会是这样的：发个邮件、群发个短信，说我们什么时候开个会，到哪个寝室来，大伙就来了。会前要说啥谁也不知道，也没跟人打招呼，反正就是关于这个 project 的事情。组长想到哪说到哪，大伙想到什么议到哪，歪歪一通。

有一件事做得还不错：最后总算产生了一份**会议纪要**。这一点很重要——把刚才讨论过的事情记下来，要不然回头就忘掉了。会开得再散，纪要留下来，需求线索就没断。

### QFD：从客户满意度出发做功能取舍

会议解决的是"信息怎么进来"，接下来要解决"进来之后怎么用"。这一讲给出的方法叫 **QFD（Quality Function Deployment，质量功能部署）**。

> **定义**：QFD 是一种策略，作用是把客户想要的东西，转换成技术员可以理解的 requirement（需求）。它的特点很明确：主要关注 maximize customer satisfaction，也就是**以客户满意度最大化为目标**去做所有事情。

既然目标定在客户满意度上，第一件事就得搞清楚什么叫 **customer satisfaction（客户满意度）**。QFD 的做法里面有几件事情，中间那两件是大家平常都在做的，前后两件才是它特殊的地方。

#### 功能部署与功能价值打分

第一步是 **function deployment（功能部署）**：

- 把每一个要做的功能搞清楚；
- 同时给每一个功能一个 **value（价值）**——这个功能对客户来说有多少价值，打个分，它有多重要。换个角度说，就是这个功能做好以后，客户的满意度会变成什么样子。

第二步是中间那部分常规工作：确定数据、确定输入输出、确定整个系统的 **behavior（行为）**。这些模型都是普通的，做需求都会做。

#### 价值分析：把需求分成三类

最后一步是 **value analysis（价值分析）**，这是 QFD 真正起作用的地方：把所有需求想做的事情归拢到一起，每个功能上都已经打了一个分，然后**按分数给这些分个类**。分完之后，需求里要做的事情就落到三大类里：

| 类别 | 含义 | 开发时的处置 |
| --- | --- | --- |
| `normal` | 基本功能，用户理所当然认为该有的东西 | 有限的人力、有限的时间之内**最先要保证**的，必须给人做好 |
| `expected` | 用户期待有、但没有也不至于没法用的功能 | 也应该做好——作为一个 `professional` 的软件，这一档属于专业底线 |
| `exciting` | 用户没指望、有了会惊喜的功能 | 看你有没有余力，当然也要看他给的钱够不够 |

> **提示**：这三类里的 `expected` 值得多说一句。它跟 `normal` 的差别不在"想不想做"，而在"缺了会不会死掉"——`expected` 缺了系统不会死，但它决定你这个软件是业余水平还是专业水平。

拿到这个分类，开发时的取舍就有了判据。**最要防的是本末倒置**：你要做的是个手机，结果地图、导航、照片、音乐每一样都做得很漂亮，就是电话不好使，打电话用的通讯簿做得笨得要命。那你说我买的是个手机，还是买的是个什么玩意儿？

这就是 QFD 没做好。至于它卖得好不好是另外一回事；作为一个软件产品、作为一个产品来看，只能说它的 QFD 做得很不到位。

### 需求导出阶段的交付物

方法讲完，回到流程本身：在 **eliciting（需求获取）** 这个阶段，除了要拿到 **user scenarios（用户使用脚本）**，还要产出一批文档。判断"我这个阶段的工作完成了"的依据，就是这些东西齐了没有：

- **statement of need and feasibility（需求说明与可行性分析报告）**：这件事情是不是可行的；
- **系统的 scope（范围）**：这个系统大概涵盖哪些东西；
- **stakeholders 通讯录**：所有利益相关者的联系方式，人找得到，需求才追得下去；
- **technical environment（技术环境）**：这一项不用多说，要写一下；
- **a list of requirements（需求列表）**：用功能来描述，说明这个系统要求完成哪几个功能；
- **特殊的 constraints（约束）**：有哪些特别的限制条件；
- **一套 scenario（使用场景）**——注意，**不是一个，是一套**；
- **最好有一个 prototype（原型）**：原型的好处前面已经交代过了。

关于"一套 scenario"这一点要讲透：如果系统足够复杂，你不可能一个脚本走到底。中间有好多分支——在这个地方做这个选择，它就这么表演一套；在那个地方做另一个选择，它就走另外一条路。所以场景是一整套，覆盖各条分支。

### 用例（use case）的检查清单

用例的具体做法要详细讲时间就太长了，这里说个大概：书上有专门的建议，**每一个 use case 首先定义一个 actor（参与者）**——谁是这场戏里的演员，他是什么角色。定了角色之后，根据这个角色为他设计一系列的行为、一系列的操作。这样做的好处是：**你这一套 scenario 不会漏掉什么东西**——这个 actor 定义本身就是一份检查清单。

定完 actor，还要回过头逐个脚本检查：每一个脚本是不是都很清楚地回答了下面这一系列问题。

| 检查项 | 要回答的问题 |
| --- | --- |
| 角色配置 | 谁是主角？谁是配角？有没有配角？ |
| 目的 | 在这个剧本里，这个 actor 最终想达到的目的是什么？ |
| 前置条件 | 他要在什么前提下做这件事，也就是做这个操作的 `pre-condition` 是什么？ |
| 主要功能 | 主要的 `function` 有哪一些？ |
| 异常 | 有没有 `exceptions`？有没有会出错的状况？ |
| 分支 | 这个 `interaction` 有什么 `variations`？不沿着这条线走的时候，他还有没有别的选择？ |
| 数据 | 他要处理哪些数据：读哪些数据，操作产生哪些数据，改变了哪些数据？ |
| 外部环境 | 外部环境有改变的时候，这个 actor 需不需要告诉系统？他跟控制面板有没有要沟通的地方？ |
| 期望输出 | 他要从系统这里得到的输出信息是什么？ |
| 意外响应 | 有意料之外的情况发生时，有没有必要让这个 actor 知道，进而做出反应？ |

这份清单就是书上给的 check list，作用是把"这套脚本写全了没有"变成一条条可核对的项。

书上还给了一个很好的例子：**SafeHome**。

> **例子**：SafeHome 相当于一个家居保安监控器，装在墙上。你离家出门的时候把它打开，回家以后把它关掉。出门之前打开，人出去了，它就监控你整个房间有没有什么异常的动作。书里给出的是一个 **high-level use case**——高层用例，可以自己去仔细分析那个案例是怎么写出来的。

### 下一课要展开的分析模型

需求有了，接下来要建 **analysis model（分析模型）**。它包含几类模型，下一节课专门讲：

- **scenario-based（基于场景的）**：就是 use case；
- **activity（活动）图**：描述活动，这是另外一种图；
- **class-based（基于类的）**：如果你是 OO（面向对象），这就是你的数据、数据结构的设计；
- **behavioral elements（行为元素）**：描述系统的动态表现——使用系统的过程中，系统会不会处于几种不同的状态？状态与状态之间用什么触发事件让它转换？描述这个东西要画 **state diagram（状态转换图）**；
- **flow-oriented elements（面向数据流的元素）**：描述数据流。这是软件工程里面非常古老但有效、也非常重要的一个工具。基本要求是：任何时候，第一件事 **data flow diagram（数据流图，DFD）** 你要能画对。具体怎么画，也是下次课介绍。

另外，在 analysis 这个阶段也有 **patterns（模式）**。模式不展开讲，你只要知道有这个东西，将来做 reuse（复用）的时候会很有用。

### 谈判：把双赢找出来

需求工程绕不开谈判（negotiation），而谈判是很要技巧的一件事情。有三点最要紧：

1. **知道你的对手都有谁，谁要参加这场谈判**——知道得越多越好；
2. **determine each of the stakeholders' win conditions**：搞清楚每一个利益相关方在什么情况下算赢；
3. **最终目标是一个 win-win situation，也就是双赢**。

对自己的 win 在哪儿，一般人都很清楚；难点在于**搞清楚对方在什么时候算 win，而有的时候这一点并不那么明显**。比如 TA 是一个很微妙的身份，你要去分析这个微妙的身份，判断谈判的时候可以把他 push 到什么程度，既对你最有利，又是他能够接受的。

> **易错点**：如果不同的 customer 或 user 不能在这个双赢的局面上达成一致，有一方占不到便宜，那这个项目失败的风险是非常大的。所以不能光想着自己占便宜。

自己当前占到最大便宜，有可能只是对方谈判的时候有点傻，让你占到了；但他事后一旦意识到是让你占了便宜，事情就会有很大麻烦。反过来也一样：如果客户很强势，导致你答应下来的条件拿回公司一看——这事情根本没法做，你怎么会答应下来？同样是大麻烦，通常这个项目就做不成了。

这个道理跟做人一样：跟人沟通、跟人合作的时候，不要只想着对我有什么好处，还要想到人家这么做对人家有什么好处。一个很常见的场景是三年级申请出国交流项目的面试——所有学生都强调自己特别希望得到这个机会。充分表达意愿没错，但这不够：**你有没有想到我为什么要让你去？** 如果功课挂得一塌糊涂、各种不及格，然后说我特别想要这个机会来提高自己——我理解你很想要，但我为什么要让你去？我要让你去是出去砸我牌子的吗？

我代表的是学院，不是我个人。从学院的角度讲，派这个学生出去，一方面要锻炼学生，另一方面也要为学院的国际声誉考虑——我希望派很优秀的学生出去为学院创牌子，不是砸牌子。**所以一定要是一个 win-win condition。现在的情况达不到双赢，这个事情就是不可能达成的。** 这就是谈判里很重要的一点：站在对方的角度想他为什么要做这件事；如果他自己不清楚，你要跟他讲清楚。

#### 谈判的几条具体原则

第一，**it is not a competition**。你在谈判，不是在辩论赛、不是演讲比赛，你不是要赢谁。在辩论里赢了，对你不见得是好事。政治是一门妥协的艺术，谈判也一样，它是一门妥协的艺术——就看你要妥协到什么程度。**妥协得过了，你就傻了；push 得太过，也未必聪明。** 关键在这一个度。

第二，**map out a strategy**：谈判要有策略。没有经验的谈判者往往很"直爽"，一竿子插到底：我的底线就在这儿，要么同意要么不同意，没什么好谈的——于是一上来就谈崩，事情谈不成。你想要对方接受你的条件，就得先迂回，营造一个让他最后不得不接受、或者非常愿意接受的情境。这需要技巧，也需要事先做好充分功课：充分了解你的对手，了解他的需求、他的长处、他的弱点，最好能知道他的底线在哪儿。然后你才能设计出来先说什么、后说什么，哪件事情谈到哪个程度——**这些全部都要事先计划好**。

第三，也是最重要的一条，**listen，听**。少说，多听。

年轻人最容易犯的错误，就是在沟通中特别急于表达自己：我有一个 idea 赶快说出来让你知道；我有一个观点想表达，来不及听你说完。甚至人家刚开了个头，你就说"我知道你后面想说什么，我想说的是你先听我说"。这是很傻的一种策略。

> **提示**：不要着急，哪怕他说话很啰嗦、说得很慢，也仔细听。人说话有的时候有弦外之音；有的时候他会透露出一些自己本来没打算透露的信息，就看你会不会听。会听的人比不会听的人多得到很多信息。不要急着表达自己——**你说得越多，犯错的机会就越多**；也没有必要主动 volunteer 给别人太多信息，而要从人家的只言片语里面尽可能多拿信息。

听这一点非常重要，它不只是一个礼貌问题（不要打断人家讲话）。很多人把它理解成礼貌，其实不完全是：**把人家的话听全、听清楚，对你自己是有好处的。**

第四，**focus on the other party's interest**：把焦点放在对方的利益上。跟人谈判最忌讳的一句话是"做这件事情对我有什么好处"——人家会说，我管对你有什么好处，我关心的是对我有什么好处。所以最重要的技巧一定是站在对方的立场上讲：**如果这样做的话，对你有什么好处。**

谈国际交流项目就是这样。去跟合作高校谈的时候，我不能说我把学生送过去对我的学生很有好处——人家的回答是"那对我有什么好处"；我要说的是：如果我把最优秀的学生送给你，对你是有什么好处的。看看这个好处他能不能心动。他动心了，事情就达成了。**要站在对方的立场上去讲对他有什么好处。**

第五，**don't let it get personal**：这是 be professional 的一条基本原则——职业一点，做事情专业一点。技术问题、项目上有分歧，你可以拍桌子、可以吵架，但不要人身攻击，不要涉及人品。**特别忌讳的是翻老账**："上次那个项目你就是这个样子的，结果我们怎么怎么样，这次你又来了"——这种话最要不得。就事论事，一件事是一件事，一定要**对事不对人**。不管做事还是做人，其实都是这个原则。

第六，**be creative**。如果大家都卡死了，看起来像是不可协调的矛盾——**没有什么不可协调的矛盾，肯定有一种方法可以协调**。这种时候特别需要聪明人：什么叫聪明人？就是当大家陷入死胡同的时候，他会 jump out of the box，从这个框子里跳出来，想一个不一样的办法。肯定是有办法的。

第七，**be ready to commit**：说出去的话，泼出去的水，你是要兑现的，不能随便忽悠。

> **例子**：赵本山有个小品，两个人客气着抢着付钱，"哎我付钱我付钱"，另一个也说"我付钱我付钱"，最后来一句"好吧，你付钱"——那个就傻掉了，原来只是客气一下。

谈判的时候你要小心：你说出去的每一个条件都要准备好，如果对方说"好的"，那**你画的这条线你是真的做得到的**。不要在前面抢着说，本来要一个月做完的东西，你跟人家说我一个星期就能做完，你给我这么多钱我一个星期就能做完——人家说好的，我给你这么多钱。然后你傻了，发现自己其实做不出来。所以说话要小心：谈判的时候随时随地准备好，你说出去的那条线会被画下来，那个时候你就要 commit。

### 需求的验证（validating）

最后一步是 validating。需求做好以后要检查：

- **consistency**：各处的描述是不是一致的；
- 有没有漏掉什么东西；
- 有没有什么描述不清楚的地方。

到这儿，需求阶段要做的事情大致就是这些：把人聚齐、把会开好、用 QFD 把客户的"想要"翻译成有优先级的"需求"、按清单把用例和场景写全、把该出的文档出齐，再用谈判把各方的利益摆平，最后自己验收一遍。

## 第 3 章：第9讲 需求分析与模型建立-1
> 对应分集：P09 | 原始标题：《第9讲 需求分析与模型建立-1》

先把总目标摆到桌面上。我们在这个阶段要建的 model 很多、要画的图也很多，但一定要确保自己不要忘掉总目标，一共就三个，三个都很重要，缺一个都不成立。把它们记牢，后面每一次拿起笔来画图，都可以拿这三条回头对一遍。

### 1 分析模型的三大目标与它在流程中的位置

第一件，当然是要把客户需求（customer requirements）描述清楚。这里"清楚"有一层特别的含义：这个阶段的描述不仅是给你的技术人员看的，它主要是给 customer 看的，是给非专业人士看的。

但同一个模型，同时还要给下一阶段的 software design model 做一个基础，establish a basis——人家是在你这个 model 的基础上去细化，来完成整个系统的 design 的。既然下游要拿它当底子，你就得有一定的技术性，在技术层面上要足够清楚。这两头是同时要顾的，顾此失彼是这一阶段最常走偏的地方。

第二件，define a set of requirements that can be validated：定义出一套可以被验证的需求。这话听起来抽象，落到钱上就很具体——什么情况下你的客户要给你钱？最后验收的标准你要写清楚。没有可验证的需求，验收的时候就是一笔扯不清的账。

第三件，是给你自己人用的：你的内部人员应该能够通过你这个 model，得到更细化的 user scenarios，然后是 function、class，然后是 behavior，等等等等。

把这三件事放到整个流程里看，位置就清楚了。你前面有一个其实是 customer 给你的、也就是我给你的东西——一个非常简单的 system description；最后你的技术人员要交出来的是一个 design model；而你现在要写的这个 analysis model，就夹在这两者中间，是一座桥梁。

```text
  customer 给的            本阶段                 下一阶段
  system description  ──▶  analysis model  ──▶  design model
  （极简）                  （中间的桥梁）          （细化到实现）

  analysis model 要同时满足两头：
    ├─ customer 看得懂（这个阶段的主要读者是客户，是非专业人士）
    └─ 技术人员能接着往下做 design（所以还要有技术性）
```

读图说明：上游是客户那份极简的 system description，下游是自己人要交的 design model，analysis model 站在中间，两头都得对上。

> **结论**：这一阶段要把它细化，但是你的 customer 也要能看得懂，你的技术人员也要觉得"充分清楚，我可以把它转化成一个软件系统了"。它重点回答的还是 what to do 的问题，是 what，不涉及技术细节——技术细节在 design model 里才会涉及。

### 2 分析建模的六条经验法则

这里头有几条经验法则（rules of thumb）。rules of thumb 是什么？就是经验教条——前辈们提醒大家，做 requirements 的时候一定要注意的那么几条。

**第一，focus on business domain，do not get bogged down in details**：不要想太多的细节。这其实是技术人员不可避免的毛病：你想到一个问题的时候，不由自主地就会想到细节——这个地方我要怎么处理？这里可能有什么 exception？那我该怎么办？上来就想我应该用哪种语言去做它。这些都是本能，可以理解，但你在做这个 analysis 的时候，就是要忽略，要忽略很多细节。

**第二，每一张图都要 add to an overall understanding**。在建立 analysis model 的过程中，我们要画很多的图、各种各样的图，每一张图都是要增进大家对系统的整体理解的，是帮助大家理解得更好，而不是想把大家搞糊涂的——这一点要搞清楚。你如果觉得这个东西写出来只会把大家搞得更混乱，那就不要写；或者这个东西其实前面一张图已经很清楚了，我没有必要再用后面的工具把它重复一遍，那你后面那个工具也是不要写。要确信你写的东西是有意义的，这个意义就在于帮助每一个人更好地理解你的系统。

**第三，delay consideration of infrastructure and other non-functional models and pure design**。一些非功能性的考虑、一些细节性的考虑，这些东西都先放到后面去。在这个阶段，你主要还是面向 customer 的：他要的什么功能，你把它搞清楚。

**第四，在划分这个系统的时候，minimize coupling**。你要把系统切分成几块的时候，尽可能让块与块之间不要有太多的关联——coupling 这个词后面还会专门讲。

说到这一条，我得顺便交代一句：我实际上给你们的那份任务划分，根本就没有考虑什么 coupling 不 coupling 的问题。我知道它绝对不是一个很好的划分，但是我就这么分了。一个目的是给你们留下吐槽的机会，另一个目的你们都懂——给你们制造充分多的混乱。你们真觉得我这么分有问题，可以专门写一篇小 essay，写得有道理、有充分的技术含量，最后是可以加分的。但注意，一句话的吐槽那叫喷子，是要被无视的：又不具体，纯粹发泄一下情感，这种就免了吧。

**第五，be certain that the analysis model provides value to all stakeholders**。all stakeholders 这个词要强调一下，它主要还是包括你的客户——你写出来的东西要对所有的人都是有价值的。

**第六，keep it as simple as possible**。尽可能简单，不要把事情搞得太复杂，不要弄得很 fancy，不要华而不实，主要就是这个原因。

> **提示**：这六条讲的都不是什么技术，而是取舍的方向。多画一张图、多记一笔，代价是让读者更糊涂；所以判断标准不是"这个东西我能不能画"，而是"画出来以后有没有人变得更清楚"。

### 3 领域分析与领域知识的复用

最后还要提一个概念，叫做领域分析（domain analysis）。

打个比方：我们现在做的这个支付宝，它是跟银行系统比较密切相关的。那其实呢，你做完这个支付宝以后，我如果再让你做一个银行系统呢？你是不是觉得有很多东西其实可以重用？最起码，你做完支付宝以后，应该对银行内部的什么转账啊、什么这些流程、规矩比较清楚了。这些就叫做领域知识（domain knowledge）。

所以你要尽可能地把你这一个 project 涉及的领域的相关知识保留下来。下一次你在这个领域里开发其他的软件的时候，你有很多东西、很多知识是可以重用的。做 domain analysis 这件事，它的主要目标就是为了你未来的重用（reuse）。附带还有个好处：你有一个 group 对这个领域非常熟悉，你就很容易得到这个领域的各种项目，做起来也会比别人更有经验。

具体怎么做？所谓领域分析，具体的其实没有什么好说的：你需要从各种渠道去获得领域知识。比如说你去读一些技术文件，把现在有的软件拿来用一用，然后有 customer survey，有一些专家的建议，等等等等。所有这些相关的领域知识你综合一下，做一个 domain analysis 出来，结果上你要抽取的是——有哪些 class 是你以后可以用的、整个领域的东西都可以用的？

我让你写个股票交易系统，还是一个银行操作员的系统，还是网银，还是什么东西，只要差不多是这个领域的东西，你肯定有一些 class 是可以重用的。你把那些可能重用的东西抽出来，然后你有一个重用标准（reuse standards）；还有相应的功能模型（functional models）、领域语言（domain languages）等等等等。把所有这些东西弄起来，其实这里面还会产生这个领域相关的分析模式（analysis patterns），都是你可以总结出来的。总结所有这些东西，是为了让你的公司以后能够有更高的效率去做事情。

### 4 分析模型的两大流派与待建的四类模型

分析模型其实分两大类：一类是传统的结构化分析（structured analysis）；另一类是后面时髦一点的面向对象分析（object-oriented analysis，OOA），也就是平常说的 OO。

我们这本书里头，在这一版里，它是把两个基本上融合在一起讲的。在老的版本里面，它会专门出一章来讲 OO，然后专门有一章去讲 structured analysis。

下次课要给大家介绍的是 analysis model 的四大类工具，每一大类里面又有好多具体的 diagrams。我们会通过各种例子来介绍你怎么做这些 diagrams。这些图都不是白画的——它们都是你们最后要交的那份需求规格说明（requirements specification）里面的内容。

### 5 数据建模：在客户的抽象层次上描述数据

上一节我们把模型的目标、经验和流派都过了一遍，这一节回到最要紧的第一件事：数据建模（data modeling）。

进正题之前先对一遍账。要建模型，最后一张图说的是我们有四大类的模型要建，还记得是哪四大类吗？基于什么的模型？比如说，基于 use case 的，有一大类模型要建；然后呢？你要描述一个需求，既要给你的客户看懂，也要给你的技术人员看懂，你需要描述哪几方面的事情？use case 又是干嘛用的？——看我今天要是来一个测验的话，你们不是全挂了。那就从头顺一遍。

第一件你要搞清楚的事情是：输入输出是什么？你要处理哪些数据？所以第一件要紧的事情就是数据建模，你要把数据模型先建起来。

什么叫数据模型？这里有一条纪律要特别注意：create a model at the customer's level of abstraction。你这个数据模型建起来是要你客户能够看得懂的，是在他那个层面上、去描述数据的。这是什么意思？举个例子。

比如说，你要跟他描述：我这个系统里面有一个东西叫做账户，有一个 object 叫做账户。那么这个账户里头包含哪些内容呢？当然包括这个人的名字，包括他的密码，然后包括他的电话号码，然后他的通讯地址，等等等等。你要描述的就是"我这个账户里面包含哪几项内容"，然后他能看懂，就可以了。

不要写成什么？不要告诉他，我这个电话号码是用一个 `int` 去表示的，还是用一个 `long long` 去表示的，还是用一个字符串去表示的。这个电话号码在你的程序里面具体是怎么实现的，这个细节不要给你的客户看，他也看不懂，你在需求分析这个阶段写这个是没有意义的。你只要告诉他有什么、有什么、有什么，就可以了。

> **易错点**：需求建模和设计建模的粒度是不一样的。需求这一个阶段，基本上你要照顾到你 customer 的情绪，他要能看得懂，所以你不要有很细很技术的说法，说我具体要去怎么实现这个东西、你用什么算法去实现——who cares？对你的客户来说，他才不管你用什么算法、什么数据结构去实现它，你只告诉他我要实现什么东西。

所以在这个阶段，你回答的都是 what to do，都是 what，一定要记住，都是 what，这里没有 how。到了 design 那个阶段，你才真正要涉及到 how to do it，那些细节才会展现出来。

这也是以前学生常犯的错误：我在他的需求文档里面看到他做的模型是这个样子的，然后到了他 design 来做报告、做演讲的时候，我发现其实没怎么改，差不多原封不动地就又搬来了，然后 presentation 就给你展示一遍。这就是没搞清楚什么东西是给谁看的。需求这部分内容是给 customer 看的——当然你的技术人员也要看懂，他看懂了，他才去作他的 design；而 design 是给自己人看的。目标是不一样的，大目标一定要搞清楚。

### 6 数据对象与属性的抽取

在描述 data 的时候，除了你要摘出来说"我有哪些东西是我的数据对象（data object）"之外，很重要的一点是你要搞清楚它们之间的 relationship。你们这个学期之前学数据库的时候，都见过那个很古老的图，叫做 ER diagram，对吧？E 是什么？Entity，实体。R 呢？Relation，关系。那其实就是你要描述清楚 entities 跟它们之间的 relation。这就是数据建模这一部分你要搞清楚的两件事情。

先看第一件：what is a data object？这其实是一个很复杂的问题，我们没有那么多时间具体地去讲你怎么抽取。为什么说它复杂？因为你现在的需求其实还蛮简单的——我给你的那个需求的描述一共才多少页？你们五个组加在一起才这么几个字。但你真正要去做一个比较复杂、比较大型的系统的时候，你的需求可能是几千字的一个文档，是一个几千字的报告告诉你我们要做这个东西，而且它是从各个不同的部门汇总过来的需求。你要从这么厚厚的一本书里面去抽"我这个系统里面哪些东西是我的 data objects"，这就是一件很恐怖的事情。

那怎么办？你搞计算机的，这么大的工作量，第一步肯定不能人肉去做，那得有点偷懒的办法：写个程序。先弄个什么？写个 parser，先把所有的名词抽出来。

```text
  需求文档（几百页，从十几个、二十个部门汇总过来）
      │
      │  第一步不做人肉：写个 parser 把名词抽出来
      │  （动词、形容词先扔掉）
      ▼
  一堆名词
      │
      │  两道筛子：① 能不能被一组属性唯一定义出来
      │            ② 跟这个系统有没有关系
      ▼
  候选的 data object（没过的，落到属性、功能或约束里去）
```

读图说明：抽取的着力点不在"把名词抄下来"，而在后面那两道筛子——能不能被一组属性唯一定义出来，以及跟这个系统有没有关系。

英文比较容易，中文比较复杂：你很可能断词、断句断错了。anyway，你可以先写一个比较简单的东西，起码把动词、形容词都扔掉，先把名词留下来，然后我再去看看这堆名词。

那这堆名词应该有什么特点？两大特点：一个特点呢，是它有一个明确的定义，它是可以被其他一些东西把它刻画出来的——有一些属性可以刻画它，唯一定义出这么一个东西；那它就有可能是你的 data objects。另外一个呢，就是它得跟你这个系统相关。

举个例子。我要做这个 ATM，自动提款机。那我在需求报告里头可能有这样的话：我希望它重点分布在几个街区；然后我希望它的数量呢，是每隔多少个红绿灯它要有一个 ATM。

这里面 ATM 不用说，就是你要做的东西。还有些什么名词？比如说街区，你拎出来是一个东西；红绿灯，也是一个东西。你看上去他们都是 objects 的那些可能的候选人。他们是吗？

红绿灯肯定是一个 object，但是它应该不是你的 data object。你想想看，你做这个系统，不可能跟红绿灯有什么关系——那是在你安装、布置这个系统的时候，你说每隔多少个红绿灯至少要有一台；那是安装布置的时候、部署的时候才有这个问题，在你的系统里面好像跟红绿灯没什么关系。

那街区呢？不一定。街区有没有关系，那要看它再细一点的需求：在你的系统里头，当客户做操作的时候，你需不需要记录他这个操作的地点？他是在哪台机器上做的？那这台机器的 location、这台机器的位置，是不是也是你这个系统要记录的？如果是的话，那街区可能是有意义的。但是街区自己本身不一定是一个 object，它可能是某一个 object 的属性，attributes。

所以你抽出来一堆名词以后，分一下：名词归一堆，形容词归一堆，动词归一堆。动词通常是跟系统的功能相关的；形容词一般来说跟 attributes 有关系，或者跟你的 performance，也就是 constraint——你这个系统的一些限定性的要求——有关系；名词呢就比较复杂，它可能是 object 本身，也可能是它的 attribute。

具体判断的时候，一般有这么几个注意的地方：

- 你这个 object 的每一个 instance，也就是它的一个实例，应该是有唯一的、确定的标识的——这跟数据库里面一样，你要有一个 keyword 是唯一标识它的；
- 每一个在你的系统里面都是要有意义的——跟你系统没关系的，比如红绿灯之类的，就不考虑在内；
- 每一个都是由一系列的 attributes、一系列的属性来刻画的。

那么这样东西才叫做一个 data object。

attributes 其实很难界定。有的时候 attributes 本身它自己是一个 object，然后它同时又是另外一个 object 的 attributes，这种事情也是有可能发生的。所以你基本上在筛选这些名词的时候，要看哪些是在刻画一个东西的特点、刻画它的质量，描述它的什么特色，或者是描述它的存在状态——颜色啊、大小啊——这些东西一般是某个东西的 attributes。

经验性地给大家举一个书上举过的例子：automobile，汽车。你定义一个汽车的 attributes 的时候，大概它有它的出厂，它的 model、body type、price、options code 等等等等，用这些去刻画这个 automobile。这里面的东西一个一个给定了以后，就会刻画出这么一个东西出来，你的程序里头就应该认识：这是我要处理的一个什么东西。

这件事没有捷径，就是在具体的实践过程中，慢慢去积累你的经验：在看一个复杂的系统描述的时候，怎么抽取出你适当的 data objects。

### 7 实体间的关系：基数与模态

第二件事是关系（relationship）。什么是 relationship？那也是要你从需求文档里面去抽取的。抽取的时候要注意区别的是：有些东西是可以推导出来的——通过算法计算出来的，通过什么东西推导出来的，逻辑推理推出来的——那些东西都不能算作 relation。

> **定义**：relationship 的意思是说，推不出来、也算不出来，你只能够明确地告诉这个系统它是有这个关系、它要记住的。

关系里面有两类。一类呢，叫 cardinality，基数，就是到底是一对一的、一对多的，还是多对多的。另外呢，modality，模态，它的意思是说：这个是必须有的，还是可有可无的。就这么两种。

| 维度 | 问的是什么 | 取值 |
| --- | --- | --- |
| `cardinality`（基数） | 两个实体之间的数量对应关系 | 一对一、一对多、多对多 |
| `modality`（模态） | 这个关系是不是必须存在 | 必须有、可有可无 |

一般来讲，ER diagram 是传统的描述这个数据模型的工具。当然我们后面有了 OO，也就是面向对象分析，那里面统一建模语言（Unified Modeling Language，UML）提供了类图（class diagram），还有类层次（class hierarchy），那个结构层次图，这些我们后面再看。

### 8 面向对象的基本概念与 C/C++ 的差异

#### 8.1 C 的 struct 与 C++ 的 class

先问一个问题：什么叫 OO？一个编程语言它被称为是 object-oriented，那么它至少有哪几个特点？它有哪几个机制？C 语言肯定不是 object-oriented，为什么？就是因为它缺少那几个特点，所以它不是。C++ 和 Java 是，那它们两个有什么共同点？

这个问题别不当回事。我们有学生要出国去美国的时候去签证，签证官一看，是 computer science 的学生，那我问你：什么叫做 object-oriented programming？你要是像今天这样沉默的话，签证就通不过了——连签证官都知道的事。

那首先，它对于数据的包装，是用一个 class 的形式来包装的。class 这个东西跟 C 里面的 struct 是对着看的：C 里面描述一个比较复杂的数据的时候，它用 struct；在 C++ 里面用一个 class。这两个有什么区别？

有继承，inheritance（继承）——这是一个非常重要的特点，object-oriented 里面继承是个非常重要的机制。还有呢？有私有成员，它有一个 private 和一个 public 的概念——那你用一个词去形容它，这实际上就是一种封装，包装，encapsulation。

#### 8.2 一百个学生的成绩单：C 与 C++ 的两种实现

说到 C 和 C++，我是怎么学 C++ 的？C++ 刚出来的时候，我那个时候还在美国念书，大概是 94 年左右的样子。那个时候就听到 C++ 这个词、object-oriented 这个词特别流行、特别时髦，然后就很好奇想去学。去查了我们 UConn 计算机系的课程，没有一门是教 C++ 的。好不容易看到一门，它叫做 Software Engineering in C++，我想好歹它教 C++，然后就选进去了。选进去以后发现上当了：它是教 software engineering，它是在教软件工程；in C++ 的意思呢，是这个大 project 要你用 C++ 来做。但是它上课完全没有一节课去讲 C++，然后它直接大程布置下来了，说必须用 C++ 去做。

当时我们全班同学都很傻眼，看着教授说：但是你没讲啊。教授说：这还需要我讲吗？我不是参考书告诉你们了吗？——他列出来的 C++ 的参考书是哪一本，自己去看啊。

然后就有一个同学很那个什么地说：Professor，你能不能花很短的时间给我们简单地说一下，我用 C 跟我用 C++ 到底有什么区别？

那个教授显然也没什么准备，拍着脑袋想了几秒钟，然后他说：好吧，我给你举个例子。举个什么例子呢？就是说我有 100 个学生，每个学生当然有他的学号、有姓名，还有他的成绩，我要把这 100 个学生的成绩全部打出来。

C 的写法是这样的：你先定义一个 `struct`，一个 `student` 的 `struct`，`struct` 里头有他的姓名、学号和成绩；然后我这个 `struct` 定义一个数组，比如说 `s100`，有 100 个学生，把这个数组定义好；然后我有一个地方把他们的所有信息读进来；到要 print 的时候怎么 print 呢？我写一个 `print_student` 这个函数，然后我把这个数组作为一个参数传进去，然后在这个函数里面写一个 `for` 循环，就把这 100 个学生给 print 出来了，用 `printf` 把它给打出来。

C++ 的写法是：原来的那个 `struct`，你要定义一个 `student` 的 class；你原来 `struct` 那一部分的内容，是这个 class 的 `private` 属性，它的私有属性。然后 print 这个功能怎么实现？`.print`——print 是这个学生他有一个要 print 他内部属性的这么一个功能。写一个 print 函数，这个 print 函数里头没有 `for` 循环，它就是一行，就 print 这个 class instance 它的内部属性，就可以了。调用的时候写成 `student[i].print`，就把它给打出来了。

| 方面 | C 的写法 | C++ 的写法 |
| --- | --- | --- |
| 数据放在哪 | 定义一个 `student` 的 `struct`，里面有姓名、学号、成绩；再定义一个 `struct` 数组，比如 `s100` | 把原来那个 `struct` 定义成一个 `student` 的 class，原来 `struct` 里的内容成为这个 class 的 `private` 属性 |
| 打印怎么做 | 另写一个函数 `print_student`，把数组当参数传进去，函数里写一个 `for` 循环，用 `printf` 一个个打出来 | `print` 是这个学生自己有的功能，方法体里没有 `for` 循环，只有一行——打印这个实例的内部属性；调用写成 `student[i].print` |
| 数据与操作的关系 | 数据归数据、操作归操作，两者是分开的：所有数据结构的定义可以写在一个 `.h` 文件，其它操作写在另一个 `.h` 文件，可以完全拆开，文件分别拿给不同的人用 | 这两件事情是绑在一起的，绑在同一个 class 里面 |
| 由此多出来的机制 | 没有继承，也没有 private／public 的概念 | 有 `inheritance`（继承），有 `private`／`public` 之分，也就是 `encapsulation`（封装） |

这就是区别。这个例子其实也说出了一个很关键的问题：在 C 里面，在面向结构的语言里面，数据归数据，操作归操作，两个东西是分开的。但是在 C++ 的 class 里面，这两件事情是绑在一起的。

那绑在一起有什么好处呢？先把封装到底是什么意思讲清楚，这笔账才好算。

#### 8.3 OO 的关键概念与 OOA 的任务过程

把 OO 的 key concepts 回忆一下，它最关键的、刻画 OO 属性的东西是：它有 class，有 class objects，也就是对象；每一个 object 有它的属性（attributes），还有它的操作（operations）；然后很重要的两件事是封装（encapsulation）以及继承（inheritance）——这两件事情非常重要。

至于说 OOA，用 OO 的观点去做这个需求分析，你要包含哪些任务？那其实这个任务过程跟"普通青年"的做法差不多，它稍微文艺一点：你总要有一个 basic requirements，通过 communication、通过沟通，获得一个基本的需求描述；然后从这个需求描述里头，你要刻画你的数据，在这个里面就是要把 class 抽取出来；然后呢，你要定义这个数据之间的关系，那它就是一个 class hierarchy，它的这么一个结构层次图，relationship 要刻画清楚；这里面还有一个就是行为模型（behavior model）——不仅是 OO 要做行为模型，其它普通的做法也要做行为模型，它是刻画一个系统动态属性的，我们后面还会再说到。然后就是你反反复复地做，一直做到说所有的东西都搞清楚为止，这也是一个迭代的过程。

### 9 封装：以 post office 对象为例

#### 9.1 邮局的对外接口与内部状态

什么是封装？用一个从游戏里面抠出来的角色讲个故事。就说年轻时候的我：我人在杭州，我的老外婆在北京，她要过九十大寿了。我想在她做生日这天给她送一束花过去，这就是我的目的。

但是我要给你们上课，所以我没办法自己飞过去。于是我要求助，我要调用一个 object，就叫做 post office——调用一下邮局。我给这个邮局 send 一个 message，说我想要做这件事情；然后这个邮局呢，就应该用它某种方法，sent by method，把花给我按时、按量送到指定的地点。

那么 post office 就相当于是程序里面一个 object 的概念。这个 object，或者说这个 class，交给某一个程序员的小组去维护，你们负责开发，也就相当于你们来管这个邮局。那我作为用户来说，我是调用你的人。调用你的人其实不关心你内部是怎么实现 sent by method 的、是什么 method，我其实不管：至于你这边是傻傻地在杭州找一个人买了一束花，然后坐飞机替我送过去；还是我在北京有个点，我给北京那边的人发一个信息，然后他在当地买了花，到那个时间给你送过去；然后是找一个美女送过去，还是找一个帅哥送过去——这些具体的怎么去实现，那是你维护这个 class、你这个团队关心的事情。

我根本不关心你里面做了什么。我只要知道你有这个功能，然后你给我定义了一个接口，我按照接口把东西给你，你就可以替我做成这件事。这就够了。

```text
post office（对象）
├─ private attributes（墙以内，外部碰不到）
│   ├─ location：邮局建在哪里
│   ├─ employee：有哪些员工、多少员工
│   └─ open hours：开门关门的时间
└─ public services（对外接口，用户只能从这里进来）
    ├─ send(message)：送信、送花、送电报
    ├─ sell：信封、邮票
    └─ store：存储
```

读图说明：邮局内部那些 private 属性——建在哪里、有几个员工、几点开门——外部是碰不到的；用户能走的只有下面那一组对外接口。

那 post office 里面呢，它有它自己内部的一个属性、private 属性：它的 location，它这邮局建在哪里的；它有哪些员工、多少员工；它开门关门的时间是什么。这些是外部不能动的。然后它提供了一个外部的接口，就是对外提供的服务、功能：比如说它可以帮你送信、送花、送电报，然后它还有一个卖东西的功能，卖给你信封、卖给你邮票，卖给你什么什么东西；邮局现在有的还有存储的功能，等等等等，它有一些给你提供的、对外你可以用的东西。

反过来看。如果我作为这个 post office 的用户，我最好想把邮局搬到我们家门口，然后你最好多加几个邮递员，最好 24 小时什么时候我去它都开门——我可以这么做吗？我是不可能这么做的。为什么？因为我想改的是什么东西？我作为一个外部的用户，我企图直接去改动它内部的 attributes：我想改掉它的 location，我想改掉它的 employee，我想改掉它的 open hours。这个呢，就是"对不起，本邮局不提供此类服务"——就我没有一个对外的接口让你动这些东西，你就没有权利动，你是不能碰到里面的。

那我能做的是什么事情呢？我能做的只能是：耐心送一束花吧。送一束花，我调用的是 `post office.send`，因为它提供了 send 这个功能，然后它提供了 message 这个接口。那我要想达到我的目的，根据约定，我需要给它填一个 request form——我需要填个表：你要送到哪里啊，什么时间啊，我要买什么类型的花啊，等等等等；最后呢当然不能忘了还得给人家 payment，得给钱。这些都弄好了以后，它读进去发现你的输入是符合要求的，然后它就会把东西送过去，完成它这个功能。

整个这个特点，就叫做 encapsulation，叫做封装。

> **定义**：封装（encapsulation）是把数据、和专门处理这些数据的那些操作绑在同一个 class 里；内部属性被留在墙以内，外部只能通过约定的接口提出请求。

#### 9.2 描述一个类的两种记法

再说得绝对一点，有一个 Taylor's notation：有人发明了这么一个符号去描述一个 class，或者说描述一个 data object。它其实是比较极端的，实际上用的时候不大有人真的这么用，因为太难画了。

它是怎么画的呢？整个这个东西是一个圈：你把那个 class name 写在上面；然后 attributes 写在这个圆圈里面；外边一圈写你的那些 methods 的名字。你要真画个图的话，这个太难画了。所以不大有人用，但是它的寓意很好。

```text
Taylor 记法（由外向内看）
  最外一圈    methods 的名字，画成砖头墙：这就是墙，而且没有缝
  里面一圈    attributes，被保护在墙以内，外面进不去
  最上面      class name
  唯一的通道  某一面墙上留出的那只手——外部只能通过它发请求去改属性
```

读图说明：最外那一圈是用砖头墙的形式画在那儿的，意思是里面的 attributes 被保护着，没有门让你进去；哪一面墙上留了手，外部才能通过它发请求。

你如果真去看这个记法的图，要注意到这一圈是用砖头墙的那个形式画在这儿的，就告诉你这就是墙，而且这个墙没有缝。里面的 attributes 是被保护在里面的，没有门让你进去，你进不去的。外面的人——作为我调用你这个 object 的这个用户——只能通过某一面墙：如果这面墙它有一只手可以进去动里面的 attributes 的话，你只能通过它来发一个请求，然后它来给你改相应的 attributes。如果有些 attributes 就是哪一面墙都没有提供你修改的功能，那你就根本没有渠道碰到它。

这就是封装的这么一个概念性的图。当然，实际上大家用的、最常见的还是 UML 那种描述方式：上面是 class name，然后 attributes、operations 这样列一下。

至于从需求文档里——从一个巨大的、复杂的需求文档里面——去抽哪些应该是属于你的 class，那是给你的各种建议，大概什么东西都可能是你的候选对象。

**题目**：写两三条，说明为什么需要 encapsulation（封装）——封装有什么好处？它可以避免什么问题、可以加强什么优势？（当时的要求是：不用抄书，能写几条写几条，三分钟。）

**解析**：答案就在邮局那个对象上，顺着它想就很清楚。

1. **内部实现对调用者不可见，调用者只依赖接口。** 我送花只需要按约定填一张 request form——送到哪里、什么时间、什么类型的花——再付钱，调用 `post office.send` 就够了。至于邮局内部是傻傻地在杭州买花坐飞机送过去，还是在北京设个点让人在当地买了花送过去，是找美女送还是找帅哥送，我一概不管，也不影响我把这件事做成。里面那套做法怎么换，外边调用的人不受影响。
2. **内部状态被保护起来，外部没有渠道乱改。** location、员工多少、open hours 这些都是邮局的 private 属性；我作为用户想把邮局搬到我家门口、想多要几个邮递员、想让它 24 小时开门，都做不到——没有对外接口让我动，我就没有权利动，碰不到里面。只有某一面墙上留了那只手，外部才可能通过它发请求去改对应的属性。
3. **数据与操作绑在同一个单位里，可以整体交给一组人维护、整体拿走。** C 的写法把数据结构的定义放在一个 `.h` 文件、把其它操作放在另一个 `.h` 文件，两件事是拆开的，谁要用就得记住拿了哪些、还要 include 哪些；class 把这两件事绑在一起，邮局这个 object 整个交给一个小组负责开发维护，用户只管按接口调用。

### 封装、信息隐藏与继承

#### 数据与函数的绑定，以及它换来的三件事

C 和 C++ 最大的区别在哪里？就在 `encapsulation`（封装）这一个词上：它把数据，和专门处理这些数据的那些函数，绑在同一个 `class`（类）里面。绑起来之后换来的第一样东西，是 `information hiding`（信息隐藏）：你在里面改来改去，其实不大影响外面。

> **定义**：信息隐藏指一个模块把内部的实现细节藏起来，只对外暴露稳定的接口；只要对外的接口不变，内部实现随你怎么换。

这个好处具体到什么程度？我今天高兴，用这个算法把这件事解了一下；后天我觉得有更好的算法可以做这件事，就把里头的东西改掉了——只要对外的接口没有变，你藏起来的那些东西爱怎么改就怎么改。即使改出了错误，影响面也不会那么大，不会因为你动了某一块，整个系统跟着塌掉。

第二样好处来自沟通方式：模块之间都通过 `message`（消息）来互相沟通，所以模块化会做得比较好，模块与模块之间的耦合、那种牵来扯去的关系，会变得比较简单。

第三样是 `reuse`（重用）会方便得多。用 C 的时候有一种很常见的编程习惯：把所有 `data structures`（数据结构）塞进一个 `.h` 头文件，把所有别的操作塞进另一个 `.h` 文件里。这种写法下次要重用的时候就麻烦了——你得记住当初 `copy` 了哪些东西、哪些 `.h` 要 `include`，它们分散在很多地方，只要你漏掉一个，这段代码就用不起来。类的好处正在这里：把数据结构和跟它相关的东西绑在一起，你要重用时整体重用这一个类就行，这是一个非常方便的机制。

#### 继承：一种"安全地重用"的模式

除了封装，另一个重要的特性是 `inheritance`（继承）。继承的结构可以从一张类图上看清楚：

```text
                  +-------------+
                  |  furniture  |
                  |  price      |
                  |  color      |
                  |  material   |
                  +------+------+
                         |
        +--------+-------+--------+---------+
        |        |                |         |
   +---------+ +--------+   +---------+ +---------+
   |  table  | | chair  |   |  desk   | | chable  |
   +---------+ +--------+   +---------+ +---------+
```

读图：上面的 `furniture` 是 `superclass`（父类、超类），它提取了下面所有 `subclasses`（子类）共同的属性；table、chair、desk、chable 各自只保留自己的特点。

父类里放的是公共属性：出厂（厂家）、价格、颜色、材质——是木头的、塑料的、铁的，还是 whatever。子类只要继承下来，相当于把父类这些东西 copy 一份，再戴上自己特有的属性，就成了另一个类。

中间那个 `chable` 是什么东西？据说以前老浙大是有 chable 的：它又是 chair 又是 table，是一把椅子，当然有扶手，而那个扶手翻过来就是一个小桌子，你可以在上面写东西。所以它既有 chair 的功能，又有 table 的功能，才叫 chable。无论如何，这些东西都是家具的某一种，去买的时候都在家具馆那一片能买到它们。

继承被形容为一种**非常安全的重用模式**。为什么安全？因为你想重用一个类的时候，不需要把那个类拿出来，把人家类里面的代码直接改掉。你只要继承一下，然后在自己继承出来的子类里去改你想改的东西、添你想添的东西，不影响原始父类的内容；那个父类别人还可以接着拿去用，不会因为你改完人家就没法用了。

#### 多继承的危险：draw 一词多义与可传递性的丢失

既然 chable 同时有 table 和 chair 的双重属性，为什么不干脆让它从 table 和 chair 共同衍生出来？这也可以，没什么不可以——C++ 本来就允许 `multiple inheritance`（多继承），一个子类可以从多个父类继承，只是前面画的那张图恰好每个子类上面只有一个父类而已。

多继承的好处很直接：这个人开发了这一块，那个人开发了那一块，我发现都能用在我这里。但它也可能产生很危险的问题。看这么一个任务：需要开发一个 `graphical deck`，就是有图形界面的纸牌游戏。为什么要强调 graphical？因为几十年前也有计算机纸牌游戏，但那是文字形式的、没有图形界面——那个年代你用 TC 去画图形界面，不是要累死吗？所以老程序只有游戏规则，没有界面。

现在恰好有两个现成的类可以用：一个是古老的 `card deck`，它封装了所有纸牌游戏的规则——什么情况下谁比谁大、应该怎么抽牌、怎么出牌；另一个是另一拨人为别的目的写的 `graphical object`，它的功能是操纵界面上一个图形化的物体：先把它画出来，然后移动它，三维的话还要移动、旋转、缩放，拖来拖去，这一堆处理都放在这个类里。但它不是专门对纸牌的。

于是很自然：把这两个都作为父类，派生出一个 `graphical deck`。

```text
      +-----------+          +------------------+
      | card deck |          | graphical object |
      | draw(card)|          | draw(object)     |
      +-----+-----+          +---------+--------+
            |                          |
            +-----------+--------------+
                        |
                 +------+-------+
                 | graphical    |
                 | deck         |
                 | draw(?)      |
                 +--------------+
```

读图：`graphical deck` 同时继承了两个父类，而两个父类里都有一个叫 `draw` 的方法，名字撞在一起。

麻烦就出在这里：两个类的 `method`（方法）里有重名的功能，都叫 `draw`。这是因为英文单词 draw 一词多义——在打牌的时候，draw a card 是"抓了一张牌"，take a card from a deck，这是 draw 这个动作；在 graphical object 里面，draw 的含义是"画"，是把一个图形化的物体在屏幕上显示出来。那么你在派生出来的类里，拿到 graphical deck 的一个 instance（实例）去点 `draw`，它到底该抓牌还是该画图？它就打起来了，就产生冲突了。

怎么解决？可以用 `overriding`（重写、覆盖）的办法，但那不是唯一的解决方案。C++ 学过了，有兴趣的话可以自己下去琢磨，有好多种办法解决这个问题，区别只在于解决得聪明还是不聪明。

> **易错点**：多继承真正的危险不只是方法重名。一旦出现这类冲突，继承的 `transitive`（可传递性）就没有了。如果都是单父类一路继承下去，A 派生了 B、B 派生了 C，那么 C 同时继承了 A 的所有属性，这个可传递性是成立的；而多继承的情况下，这个可传递性很可能被破坏掉。

### 基于场景的建模：用例

#### 用例的两种用途

后面几种方法其实都是在刻画系统的使用和系统运行的过程。第一种是 `scenario-based`，也就是基于 `use case`（用例）的。用例描述的是一个用户、一个 `actor`（参与者、角色），去使用你这个系统的那一个剧本、那一个过程。

用例在需求阶段有两大重要功能——其实它在另一个阶段同样重要。在需求阶段它的作用很容易想象：你要跟用户描述一下，将来你来用这个系统的时候就是这样用的——你先做这个，后做这个，发生了某件事的时候你做这个选择，等等，给他看一遍，问他这是不是你印象中使用系统的方法。这是拿来核对的。

另一个阶段是哪里？想出来了吗？你在需求分析阶段写的用例都要好好地留着，后面有用的。**测试**的时候你就会发现用例是多么可爱的一个东西：至少你先拿来，自己内部按那个剧本先演一遍，把所有的剧本全演一遍，没问题你才好去见人。

在这个阶段，用例主要帮助大家定义：哪些东西是这个系统之外、要接触你这个系统的——也就是哪些是你的 actors；然后这些 actors 要做哪几件事情，做这些事情的时候你这个 system 本身应该怎么反应，才能让他把目标达成。

#### 用例的写法：actor、primary 与 secondary 场景

做用例的技巧就是三个步骤，而且需求这一段不用写得很仔细：

- 先把所有 actor 列出来：有哪些人、哪些角色要用你这个系统；
- 针对每一个 actor，列出他要做哪几件事情（functions）；
- 根据这些 functions，列出 `primary scenarios`（主场景，最初等的、最简单的那些），画出用例图；然后考虑使用过程中有没有特殊情况、有没有分支岔路可走，把用例再细化一下，形成 `secondary scenarios`（辅场景）。

> **结论**：这一层的描述是比较粗、比较粗放的，后面才会越来越细。

书上的例子是 `SafeHome`，一个家居保安系统。之所以说它粗，因为它只告诉你：你先把这个家居系统装好，一个 homeowner（家里的主人）在面板上至少可以完成三件事。一是初始化，把它的参数设置好；二是出门的时候按一个按钮 `set alarm`，把警报器开起来；三是人在外面的时候，可以通过 internet 去看 camera surveillance（监控镜头），看看房间里有没有什么问题。

这三件事的性质并不一样：前两件都是在保安系统的面板上直接按按钮就能完成的；看监控要通过 internet，而且要通过它去启动硬件设备 cameras，这里头有一条线去调用那个镜头。用例精细到"有这么一条线调用摄像头"这个程度，就已经是一个 primary 了。

当然，描述每一项功能的时候还可以再往下走一层：`configuration` 我怎么做？系统初始化的时候我要设置哪些参数？设置参数的时候先设哪个、再设哪个，先点哪个、再点哪个？这些就是每一个功能下面那个细化的用例，是另一串。用例本身还是比较简单的。

#### 活动图与泳道图

在初步沟通、要描述一个系统的时候，我们前面讲过可以画 `activity diagram`（活动图）。活动图其实也是用例的另外一种形式，只是它看上去没有用例那么好理解：它不是脚本式的，而是把所有的分叉全放在一张图里表示出来。你走到某一步有两种可能、两种选择，选这一边就是这么一串行为，选那一边就是那么一串行为，各种岔路都摊在同一张图上。

在这个图的基础上可以再细化一点，画成 `swimlane diagram`（泳道图）。Swimlane 就是游泳池的那个泳道。看这张图里的主体，它还是刚才那个活动图，每一个 activity、每一个 action 还是那些；但它额外说明了每个动作**是谁来做的**，分成了三个角色：homeowner 负责这一堆动作，camera 负责这个动作，控制面板的 interface 负责这两个动作。

```text
  homeowner   |   camera   |   control panel
  ------------+------------+------------------
   initialize |            |
   set alarm  |            |
   -----------+------------+------------------
              |  <camera>  |   start camera
              |  deliver   |   show image
  ------------+------------+------------------
   view image |            |
   deactivate |            |
```

读图：横向三条泳道分别是三个角色，纵向自上而下是动作发生的时间顺序，列与列之间的衔接就是这个系统真正走完的那一连串动作。

这样一来就一目了然：你把这个图读一遍，就大概清楚了到底这个系统有哪几块、整个是由哪一连串动作做出来的、哪一部分、哪个角色负责哪些动作。

> **提示**：泳道图和用例图，这两个图都是帮助用户和你自己充分沟通、确认"我用这个过程、用这个系统的方式是不是就是这个样子"的辅助图——我是用哪几个操作去把这个系统走完的。

### 面向数据流的建模：数据流图

#### 系统的 IPO 视角与图元约定

另一种方法是 `flow-oriented modeling`，基于流线的建模。最最古老的一个图叫做 `data flow diagram`（数据流图，DFD）。它的整个理念是把计算机系统看成一个 IPO 的系统：`input`、`process`、`output`。系统不管它是怎么做的，它总是读了一堆输入进来，然后在里面乱七八糟弄了一下，变成一个输出就出去了。

数据流图把系统看成是由**数据和功能**构成的整体，它想描述的就是数据到底是怎么从输入变成输出的：数据从输入的地方流进来，经过一个功能以后变成了这个样子，又经过下一个功能变成下一个样子，经过一系列功能以后转变成最后的输出出去。

```text
   +--------+        +--------+        +--------+
   | 外部   |=====>  | 处理   |=====>  | 外部   |
   | 实体   |        | (圆饼) |        | 实体   |
   +--------+        +---+----+        +--------+
                         ||
                    +----++----+
                    || 数据库  ||
                    +----------+
```

读图：方框是 external entity（外部实体），一个输入操作、一个输出操作都放在方框里；圆饼是 process（处理、功能），里面写上这个功能、这个动作；`=` 是流线；两条横线中间夹一个名称是数据库。

数据流图常用的符号就是这样：方块表示外面的 `external entity`；功能画在一个圆饼里面，圆饼里写上这个功能、这个动作；外部实体与功能之间有很多流线，这些流线跟数据结构里画的 `graph`（图）一样，是一个**有向图**，边的上面要标出这条边上流动的数据是什么、有哪些数据；如果中间涉及到数据库，数据库画在两条线之间——数据库有各种画法，我们这本书采用的是上下两条线、中间写上数据库的名称和它存放什么数据。

画的规矩很简单，讲起来讲完了你们都知道了。但是会不会画是另外一回事。这就跟你说"你们都会打牌"，不会打牌的人我花五分钟就能把出牌的规矩讲清楚，可是打得好不好是另外一回事。

#### 例题：简化公共图书馆的数据流图

现在给一个具体问题，给五分钟，把这个数据流图画出来。这是 `information system of a public library`，一个公共图书馆，而且简化到只有两个功能。

- 一个功能是 `get a book`：用户输入书的 `title`、`author`，还有借书人自己的名字；调用这个功能以后你应该把书找到给他，同时记一下这个人把这本书借走了，数据库要更新。
- 另一个功能是 `search by topics`：我不借书，只查一下有没有这个书。search by 有好多好多，这里简单地说它只是 search by topics；你应当列出所有这个 topic 的书，包括这些书的 titles 就可以了。

五分钟到了，还可以再给一分钟写名字。这个 discussion 不收——我预感到收上来会悲剧，所以不收，我们直接看答案。这也不一定是标准答案，你可以有别的画法。

所以你知道规则是一回事，真的会用这个东西去干活是另外一回事，给你个活干你就知道了。怎么画呢？知道它的 trick 就很简单。

```text
                     title, author, name of user
   +--------+  ------------------------------->  +==============+
   |  user  |                                      |  get a      |
   +--------+  <-------------------------------    |  book       |
       ^              book  ------------------+    +======+=======+
       |                                       |           |
       |                                       |     title, name of user
       |                                       |           v
       |                                       |   +-------------------+
       |                                       |   || list of books   ||
       |                                       |   || borrowed        ||
       |                                       |   +-------------------+
       |                                       |
       |                                       |     title, author
       |                                       |           v
       |             +==============+      +-------------------+
       |             |  search by   | <--- || author catalog    ||
       |             |  topics      |      +-------------------+
       |             +======+=======+      +-------------------+
       |                    |              || title catalog     ||
       |     list of titles |              +-------------------+
       +--------------------+                      ^
                                                    | book position
                              +-------------------+
                              ||  bookshelf        ||
                              +-------------------+
```

读图：两个圆饼就是需求描述里要的两个功能；`user` 这个外部实体分别送出 book request（线上带 title、author、name of user）和 topic request；`get a book` 一路把 book 交回前台、另一路把借走的 title 与 user name 写进借书数据库；`search by topics` 只吃一个 topic，产出一份书目清单。

先说 `get a book`。因为你涉及 title、涉及 author，所以肯定要去查数据库；最后产生的是一个 book，给到前台的 book reception。有的书上输入输出全用一个方块表示，有的书区分一下——输入用方块，输出用另外那么一个东西，whatever，这都没关系。另外你要写数据库：借走的这本书的 title，还有 user name，要写到 `list of books borrowed` 这个借书数据库里面去。

而要得到这个 book，在 search 的时候你至少需要这么两个数据库加上一个书架：从 author catalog 里找 author，从 title catalog 里找 title，找到它们的公共交集以后，从`bookshelf` 上找到那本书的位置，把书得到，然后产生输出。这么设计以后，`search by topics` 就更简单了：先有一个输入 topic request，传进去的是一个 topic——他可不需要告诉你他是谁，你不关心是谁要 search，反正他只是 search、他不借书。既然是 topic，那么他肯定要有一个给出去的东西：在屏幕上把书目清单显示出来，也就是 `list of titles referring to the topic`；再加上一个 topic 的数据库，从里面按 topic 找 title，中间处理一下，就给出这么一个东西。

> **结论**：画数据流图是软件工程的重要技术技能之一，这几乎是每年必考的。期末卷子前面 50 分是基本概念题，后面 50 分就是你临场发挥的题——给你一个小 project，说你看清楚这个需求描述，先把数据流图画出来。画法就是这么一个画法。

#### 两个典型错误：断流与"灵异事件"

初学者最容易犯的错误有两个。

一个是**断流**的问题：你会发现某一个功能只有输入没有输出。那这个功能就是有问题的，你肯定画错了什么——数据流流到它这儿就停住了，跟后面再没有关系，那这个功能其实没有存在的必要，它到底在干嘛？

另一个是莫名其妙**自启动**的问题，我们叫灵异事件：一个功能在系统里面就是一段程序，肯定要有一个东西去启动它一下，它才能起作用，也就是说肯定得有指向它的箭头，它才可能产生出去的箭头、才能产生输出。即使它是根据一个 timer、根据时间到一个定点定时启动，那也得有一个 timer 去启动它。

> **易错点**：经常有人画成这样——一个功能放在那儿，凡是只向它的箭头都是从数据库来的，再没有别的指向它的箭头，然后它就直接开始往外产生输出了。这段程序好神奇，它自己就跳起来去读数据库了？数据库是被动的，等着被读的，它不会主动发送数据给这个功能去启动它。得是先启动这个功能，它才去读数据库，所以这种指向的箭头是不算的。只有像 `book request` 这样真正启动了它、调用它、传给它一些数据把它启动起来，它才开始工作，才去调用这些数据库，然后产生输出。

期末给一个 project 让你做的时候，我们没有标准答案。你只要可以自圆其说、只要不犯这种错误就行。断流、灵异事件这种明显是搞错了，因为这个系统是不可能的，属于明显的系统错误，是要扣分的；其他情况下，只要你能自圆其说，我们觉得按照你的方法，不管聪明还是笨，你是可以做出一个系统来的，这样就可以。

#### 一次细化：把一个圆饼拆成两件事

回头看 `get a book` 这个函数，它其实不太好。所谓不太好是什么意思？就是它这一个功能产生了两个不同的输出：它送了输出去，同时它又写了数据库，说明它干了两件事。我们希望最后把系统拆成"一个圆饼就干一件事情"，最好是这样；如果不是，就说明它干了两件事，这两件事就可以拆成两个圆饼来描述，也就是你可以继续做 `refinement`（细化）。

比如 `book request` 可以分解成 `find book position` 和 `get a book` 两件事。名字是不是这么取还可以再商榷。总的来说：用户说我要借一本书，先 `find book position`，从数据库这边找到那本书在哪里、书是存在的；把书在哪里传给下一个功能，同时就可以完成第一个功能——表示这本书已经借出去了，去写数据库；然后下一个功能才去从书架上拿书，给到前台。就这么拆分一下，是不停地 refine 的一个过程。

```text
   book request        find book position      get a book
   ------------>  (1)  ------------------>  (2)  ---------->  book
                        |                       ^
                        | book position         |
                        v                       |
                  +-------------------+         |
                  || title/author     ||        |
                  || catalogs         ||        |
                  +-------------------+         |
                                                |
                  +-------------------+         |
                  || bookshelf         ||-------+
                  +-------------------+
```

读图：第一个圆饼只负责"定位"，顺带把借阅记录写进数据库；第二个圆饼只负责"取书"，从书架把书拿出来交给前台。一个圆饼一件事。

#### 分层展示：level 0、level 1、level 2

真正写需求的时候最忌讳的一件事，是在一页纸、一张 A4 纸里面啪地打出一个巨复杂的数据流图：一堆小圆饼，上面细细小小的字，好多数据在上面流来流去，人家一眼看上去就晕掉了。不可以这么画图。

要怎么画？要分层次地画：

```text
  level 0        +--------+      +=========+      +--------+
   book request  |  user  |----->|  系统   |----->|  前台  |
                 +--------+      +=========+      +--------+

  level 1        +--------+   +=========+   +=========+   +--------+
                 |  user  |-->| get a   |-->| find    |-->| book   |
                 +--------+   | book    |   | position|   | shelf  |
                              +=========+   +=========+   +========+

  level 2        get a book 内部再拆：读两个输入，处理，产生一个输出
```

读图：level 0 是最起码的——读一个什么东西进去，中间就是**一个 process、一个系统、一个大黑盒子**，然后产生数据给到什么输出；level 1 把中间那个 process 细化，发现它里面原来还有好几个子功能，看数据在这些子功能之间怎么流动；如果某一个功能还不够细，就再细化一层，也就是 level 2，这个功能又可以拆成几个功能，它是这么读处理两个输入、最后产生一个输出。

这就像拿一个天文望远镜去看，然后走近一点用肉眼看，再拿放大镜看，再拿显微镜去看——你看到的细节越来越多，而这些细节一定是要**逐渐**展示的。

> **提示**：你要想到，你写的这个需求文档不是给你自己看的，是给别人看的。要照顾别人怎么能在很短的时间里面看懂。尤其你们的 TA 哥哥，他本身要帮我做他的 research project，本身就很忙，自己还要上课，有很多事情，他还要谈女朋友，还要做别的。在这种情况下，他有多少时间仔仔细细读你的文档呢？如果你的文档写得一团糟，你能指望他有很大的耐心从头看到尾吗？所以想让 TA 有耐心欣赏一下你做的东西，你要做的就是让它比较方便阅读，让他很短的时间可以理解你在做什么——这是最终极的目的。至于怎么达到，有很多技巧，一级一级地展示系统各个细节就是其中一种。书上 SafeHome 还有一个 example，大家课后自己去看怎么画这个 data flow。

### 面向控制流的建模：状态图

#### 从事件到状态转移

另外还有一种 flow，叫 `control flow`（控制流）。说实话，把 control flow 放到 flow-oriented 里面不知道是不是合适，我个人不一定同意这种分类方法，but anyway，这也是一种大家一定要画的图。

每一种图都是从某一个角度去理解系统：user scenario 是说我这个用户、这个 actor 是怎么做动作的；activity 也是说你怎么做动作的；data flow 是说功能是怎么改变数据的；而 control flow 其实也叫做 `state diagram`（状态图），它理解系统的角度是——我的系统在整个执行过程中有哪几个不同的状态，发生了什么事情、它做了一个处理，就从一个状态转移到另一个状态，也就是 event（事件）发生了什么、系统怎么 `process`（处理）这个事件。

事件就是发生或者不发生，其实有两种情况。对应到你的代码里，看那些标出来的重点词：某个地方发生中断了，`interrupt`；然后 `switch cases`、`if else`。凡是有这种转折的、有几种可能性的，都叫做 control 的节点、控制节点；描述你这个 control 过程的就是 control flow diagram。它描述的就是系统有几个不同的 states（状态），以及这些状态是通过什么东西、被什么事件驱动完成转换的。

#### 家居保安系统的状态图

看一个具体的例子，还是那个家居保安系统。这个字很小，在书上 199 页——我的书跟你们的书不太一样，所以页码自己找一下。我在黑板上用不同的颜色区分系统内部的不同层次。

```text
                 power off
        +-----------------------------------------------+
        |                                               |
        v                                               |
   +---------+  switch on   +-----------+  system OK  +--------+
   | initial |------------->| resetting |------------>|  idle  |
   +---------+              +-----+-----+             +----+---+
                                  |                        |
                          启动失败 |                  activate
                                  v                        v
                            +-----------+          +--------------+
                            | terminate |          |  monitoring  |
                            +-----------+          +-------+------+
                                                           |
                                        sensor triggered   |
                                        start timer        v
                                                   +--------------+
                                                   | monitor and  |
                                        deactivate | alarm        |
                                                   +--------------+
```

读图：系统先有人按了一下 switch on 把它开起来，开起来以后系统进入 `resetting` 状态；如果启动不起来就终止，顺利启动就进 `idle` 待机，再按 activate 进入 monitoring 监控，监控中一旦 sensor triggered 就进入报警状态。

把这张图上的信息一层一层说清楚。系统刚被 `switch on` 打开时进入 `resetting`（重置）状态：

- 系统当前的状态是 `inactive`——没启动，没有在做监控；
- 面板上显示的信息是 `starting system`，它正在启动，please wait；
- 那个小灯很慢地一下一下跳着闪，表示系统内部正在做事情；
- 系统内部在做的事情是 `run diagnostics`，在自己检测、在系统初始化，看看启动起来有没有什么问题。

如果启动的结果是启动不起来、坏掉了，那面板上就显示一个 `contact vendor`（去联系经销商），你这个东西坏掉了，然后就结束、终止了。如果顺利启动起来了，`system OK`，它就进入 `idle` 状态，一个待机状态，什么都不做。这时候它的 status 还是 inactive，还是没启动，是待机；面板上显示的是 `ready`；灯不闪了，一直亮着。然后它要等待你按下面一个键去做下一步。

那下面这个键有几种可能？

- 有人按了一下 `reset`，重置，它又回到 `resetting` 状态，好了以后又进入 `idle`；
- 有人按了 `power off`，直接关了，它就关了；
- 有人按了 `activate`，比如要出门了，出门之前让保安系统启动起来，它就进入监控阶段。

进入监控以后：系统现在的状态是 `monitoring`；面板上显示的是 `armed`（武装起来了）；灯也是不闪的、亮着的；系统内部在做的事情叫 `monitor and control system`，整个处于监控状态。至于它怎么完成 monitor and control system 这个功能、怎么完成 `run diagnostics`，你都不去管它——**这是给用户看的**，你要搞清楚这一点。你跟用户描述的是：我这个系统现在是这么一个状态，然后我等着有人再来碰这个面板。

接下来发生的事情分几种：

- 如果人回来了，没有必要再开着，就要把它关掉。关掉不是随便关，你得有一个 `password`，有一个 `deactivate password`，成功了它就进入 `idle` 状态；
- 如果进来贼了，那么 `sensor triggered`、`start timer`，就开计时，然后它就开始哇哇地叫。系统进入 `monitor and alarm` 状态：面板上显示的是 `alarm`，在报警；显示 `triggering sensor`；那个灯在很快很快地闪。这时候除了你原来那个功能还在执行以外，还要有一个 `sound alarm`——报警器开叫；同时应该有一个动作自动去 `notify alarm responders`，比如自动拨通警察局的电话，再自动拨通住户的电话，告诉你家里进来贼了。同时面板还在等待着下一步的输入；
- 如果这个贼出现了一下就不见了、后面不再动，它有一个 timer，叫了一段时间之后差不多行了，它就不叫了；
- 或者发现是报错警了，你用某种方法也可以把它掐掉，或者 deactivate——警察进来了，把事情处理掉了，deactivate；
- 否则，如果监控器持续地发现有人在里面跑来跑去，它就会 `restart timer`，它会一直叫。

> **结论**：家居保安系统一目了然地说明，这个系统有**四个状态**；描述这四种状态之间是怎么转换的图，就叫状态图。

### 基于类的建模与 UML 记法

#### 从需求文字里找类：名词、属性与操作

`Class-based`（基于类的建模）就不再展开了，其实前面已经说得差不多了。`class-based modeling` 就是像 C++ 里面那样去抽象出那些 class：用一个 `grammar`（文法）的 `parser`（分析器）去抽一下名词，然后看哪些名词是 `attributes`（属性）——哪些词定义了某一个 object 的东西，它就叫 attributes；再找动词，动词是哪些动作去 `manipulate`（操纵、处理）attributes。

这里头有一个 tricky 的东西：所有的动词抽出来之后，你把它抽成一个个 `operation`、一个个要完成的函数，那么哪些功能跟哪些 attributes 是绑在一起、属于同一个 class 的？这其实是一件很复杂的事情。具体有很多技巧，比如看数据流图以什么为中心，以及你要画一个什么样的图来分析哪些功能改变了哪些 attributes——一般来说功能应该跟它改变的 attributes 绑在一起。麻烦的是，有些功能改变了好几个 class 的 attributes，这个时候你怎么辨？这些都有具体的技巧，这堂课就不介绍了，告诉你有这么件事情就好。

`class diagram`（类图）有几种，大家自己去学一下 UML 怎么用。一种画法就是：一个 class 画好，然后把它们之间的组成关系画出来，在连线上稍微写一句话说明这个关系，就可以了。

#### CRC 卡片：协作者是关键

以前比较重要、现在我不知道，UML 里也有 `CRC cards`（CRC 卡片）这个工具可以用。在很早很早以前它真的就是一张一张卡片，在卡片上把东西写好的。

- 第一个 C 是 `class`（类）；
- R 不是 relationship，是 `responsibility`（职责）；
- 第三个 C 不是 cards，是 `collaborators`（协作者）。

其实第一个 C 和 R，class 和 responsibility，就是那个 class 的描述——它的 private attributes 和 public operations 都写在一起，所以这半栏不是什么新鲜的东西，你就描述了一下那个 class。**重要的是 collaboration 这一栏**：你要写你每一项东西还调用了谁，或者你被什么东西调用，你被哪个其他的 class 调用、或者你调用了其他的 class。

这部分实际上是最关键、最重要的。为什么？如果你做完了就什么都不改，那倒也无所谓；但你要改的时候就要小心：你改了哪一块？

> **提示**：打个比方，就说电话号码，我本来把它定义成整数的，现在改成字符串。改成字符串以后它会影响谁？你这个电话号码可能在另外一个 class 里面是把它当成一个 hash key 来用的，本来它认为你是一个 integer hash key，现在你把它变成字符串，人家就挂了。

所以你影响了谁，就要通过 collaborator 去找：把相应的那些卡片再揪出来，看这些卡片里你影响了哪一部分；而你影响的这一部分可能它还有另外的 collaborator，那就牵一发动全身，就是比较差的设计了——你要改一张卡片，结果相当于拎出来一大堆卡片都会受到影响。

> **结论**：拎出来的卡片越少，说明你的设计越好；设计不好的话，一不小心就拎出来一坨，那个时候你就麻烦大了，改的时候要特别小心。这就是 CRC 卡片基本的作用。

#### 组成、依赖与 package

还有几种图形的方法。比如一个黑色的实心菱形表示**组成**关系：一个 player，由他的头、身子、胳膊、腿这些东西来组成一个 player。这些符号还表示一对一、一对多，以及 `mandatory`（强制、必须有一个）还是可以有可以没有的。这是一种图形的表示方法，大家知道一下就可以了。

`dependencies`（依赖）呢，就是说：你在 internet 上要给它做一个界面，有一个 `display window`，而它是要去动那个 camera 的；并且要附加一个 password，你才能够去动这个 camera，这是一种描述的方式，就符号而已。

如果好多的 classes、好复杂，你要画成一个很大的图那是很恐怖的一件事情，那就把它们归归类，放在几个不同的信封里面，叫 `package`（包）。比如这是在描述一个足球游戏：所有描述运动场上那个环境相关的类都放在这里面、一个口袋里；关于这个游戏规则的那些类放在这里面；游戏里面的人物放在这里面。

package 名称前面的符号是有讲究的：

| 符号 | 含义 | 说明 |
| --- | --- | --- |
| `+` | public | 所有人都可以用 |
| `-` | private | 内部的，就是藏起来的 |
| `#` | protected | 指明这个东西只有某几个 package 才可以同（共享） |

这是一些符号的问题，anyway 你们自己下去自学一下就好了。

### 行为模型

#### 系统状态与类状态

最后还有一个 `behavior model`（行为模型）。它的特点，简单地说，就是描述这个系统在使用过程中的动态。其实刚才说的状态图也是行为模型的一部分，就是描述你整个的系统处于哪几种状态。

更细一点说：对于每一个 class，你要仔细分析一下这个 class 是不是动态的，它是不是存在几种不同的状态。所以除了这个 state diagram for the system 以外，你还是要仔细分析 use case，看哪一些 objects 它自己是不是也有一个 state transition 的特性；如果有，你要对这个 class、这个 object 做它的状态转换图。

> **结论**：总的来说你要画两种 state transition，一个是 the state of the system，一个是 the state of each class。也不是 each class——是每一个**有必要画**的 class；如果这个 class 一直是静态的，那就没有必要画。

介绍 state 的时候它有分两种：

- `passive`（被动的）state：只是它那个 attribute 的值、它的属性值发生了改变；
- 主动的 state：是它整个的那个 process 在改变。

书上给了一个例子，就是 `control panel`。Control panel 就是刚才家居系统里面如果我把控制面板定义成一个类的话，这个类的转换图——你要看到这个类大概有这么四种状态。但**这个不是你最终要画的那个图**。

#### 顺序图

建议你最终要画的那个图是下一个图：在图画好的基础上，画出来这么一个 `sequence diagram`（顺序图）。

顺序图和前面那个状态转换图的关系，就好像一开始那个 activity diagram 和 swimlane（游泳池那个泳道）图的关系是一样的：它把状态图里的每一个 state 按**时间轴从上到下**排列，然后看状态转换过程中涉及到哪几个因素。

```text
  homeowner        system          sensor
      |              |               |
      |  switch on   |               |
      |------------->|               |
      |              |  resetting    |
      |              |  -> idle      |
      |  activate    |               |
      |------------->|               |
      |              |  monitoring   |
      |              |               |
      |              |<--------------|  sensor triggered
      |              |  start timer  |
      |              |  monitor and  |
      |              |  alarm        |
      |<-------------|               |
      |  sound alarm |               |
      |  notify      |               |
      |  responders  |               |
```

读图：三条竖线是三个系统元素，横向箭头是消息与事件的传递，纵向自上而下是时间推进；这样一眼就能看出在哪个阶段、由谁的动作或哪个传感器事件触发了状态转换。

有 homeowner 去启动它，进入一个状态；然后他要跟 system 交互去转换状态；然后还要跟 sensor 交互去做状态转换。把各种牵连到的系统元素都放在一个图里面，就完成这个顺序图。

> **结论**：这个顺序图才是你们最终要画的、要解释的那个东西。

### 需求文档的写作与交付要求

#### 一定要落到纸面上

> **Everyone knew exactly what had to be done until someone wrote it down.**

一定要落到纸面上，你才确保说大家都搞得很清楚了。嘴上说说是不算的。

写的时候注意这么几条：

- 不要一次性把所有细节展示出来，一定要分层次地去展示——前面已经说过了；
- 通常你这个上百页的需求文档是由好几个人合作组成的，大家要**统一名词用语**。不能这个人管这个东西叫这个名字，在另外一个人写的东西里它叫另外一个名字，那就很讨厌了：大家读起来的时候，这两个词是不是同一个东西？
- 所有的缩写，不管这个缩写有多么常见，**第一次出现的时候必须给出全称**，然后说明这个东西的简称是什么，以后你才可以直接用简称去称呼它。这是写论文、写任何正式文件的规矩，记住一下；
- 你肯定要有一个目录（table of contents）；如果做得再友好一点，后面应该有个 `index`（索引）。我们的英文书后面都是有 index 的，比较友好，大家比较容易找；
- 写作风格要清楚、简单，不要啰嗦。

#### 站在第三者的立场审视

总的原则是：你写完了这一段、在审视的时候，要**站在第三者的立场上去看你写的东西**。你是很清楚你想做什么的，别人不是很清楚你想做什么。你给 TA 哥哥看，你觉得他在 10 分钟以内能读懂你这块东西吗？就你这个文档，他能读得完吗？他能读得明白吗？其实要想清楚这一点。

我们的 due date 还很早，24 号才交，你们有三个星期的时间去做这件事情。之所以留三个星期，是因为它**真的需要花三个星期**，不是说你最后只要三天就可以赶出来的，千万不要指望最后一个晚上把它赶出来。

> **提示**：今年你们的 TA 哥哥其实是比较 nice 的一个人。以往有的 TA 是这样的：需求文档写不到 100 页，你好意思交给我看吗？所以这个东西你是不能指望一个晚上赶出来的，三天也是不够的。我为什么给你三个星期，是有道理的，在这里就友情提醒一下。
