## 第 1 章：第3讲 软件过程-1
> 对应分集：P03 | 原始标题：《第3讲 软件过程-1》

### 一、软件工程是"层次化技术"：从质量焦点到工具的四层

上一讲是"站在月球上看地球"，俯瞰软件工程全貌、知道它"做什么"；从本讲起，要"举起天文望远镜看地球"，看到更多细节。第一个细节就是 **process（过程）**。

教材的写作风格本身就体现了一种核心思想：**layered technology（层次化技术）**。这本书任何一大块知识都"由浅到深、一层一层深入"——开头必是 generic view（概览），想快速了解只要看每章开头，想深入再看下一层、再下一层。本课程贯穿始终要培养的习惯，正是这种**由宏观到微观、逐层深入的看问题方式**。

一个类比能说明"层次"为何重要：你跟建筑工程师说"我要建一座桥"，他第一反应绝不会是"买几号螺丝钉、去哪家厂订"——那是显微镜级别的事。同理，学期大 project 布置下来，很多学生脑子里第一个冒出的念头是"我该用什么语言开发"，这**远还没到那个层次**。正确顺序是：先从最宏观角度看清全貌，确认看清了，再拿天文望远镜、普通望远镜、放大镜、显微镜，逐级看到越来越多细节。

这套思想方法可落地为四层结构：

```text
┌─────────────────────────────────────┐
│  Tools（工具）                        │  ← 显微镜：用什么语言/测试工具/版本控制
│  Methods（方法）                      │  ← 放大镜：每阶段具体 how to do
│  Process Models（过程模型）           │  ← 望远镜：what to do，走哪条路
│  Quality Focus（质量焦点）★最底层     │  ← 全貌：一切为了高质量软件
└─────────────────────────────────────┘
```

最底层是 **quality focus（质量焦点）**。上节课讲过的 myths vs reality 里，有人质疑"写文档是官僚负担、专门捣乱"，而 reality 是：规定你"先这么做、再那么做"、写大量文档、做详细 report，目的只有一个——**若不如此，你极易陷入困境、做出不好用的软件**。可维护性、可用性、少 bug，都属于软件质量。所做的**一切**规章制度，若伤害了"做出高质量软件"这个总目标，无论 process 多 fancy、多花哨，都没有意义。将来你管理团队、设计制度时，也要以"是否有助于质量"为唯一标尺。

### 二、过程模型：通往高质量产品的地图

在质量焦点之上，人们设计了一系列 **process models（过程模型）**。它的本质是**一张地图（a road map that helps you create a timely high-quality result）**：从起点（拿到项目）到终点（按时、高质量地生产出软件产品），要经过哪些地方？先干什么、再干什么、每一步分几步、每步干什么——把路线理清，就是 process model。

从起点到终点有很多条路，不同公司选不同道路，取决于：**主营软件的类型**、**手底下员工所处的层次（人力资源特点）** 等。选定一个模型后，才进入 **methods（方法）** 层——过程模型回答"what to do（干点什么）"，方法层回答"在每个阶段具体 how to do（怎么干）"。方法清楚了，才到最顶层的 **tools（工具）**：用什么编程语言、测试工具、版本控制工具。整个过程正是"天文望远镜 → 望远镜 → 放大镜 → 显微镜"的逐级下沉。

### 三、通用过程框架：Framework Activities 与 Umbrella Activities

下一章会看到五花八门的 process models，但**万变不离其宗**。无论设计何种模型，都要先做几件共同的事，称为 **framework activities（框架活动）**；此外还有一组**笼罩全程**的活动，称为 **umbrella activities（伞形活动）**。

#### 3.1 框架活动五件套

任何 process model 最少都要包含：

1. **任务分解**：把要做的分成几个任务（大 project 的宏观分工已由课程定好）。
2. **work products（工作产品）**：每个任务总要产出点什么——交一份文档也是阶段性 product，不一定是最终产品。
3. **milestones（里程碑）与时间控制**：怎么定义里程碑是有学问的。
4. **deliverables（交付物）**：每个 milestone 要能交出来什么东西。
5. **QA checkpoints（质量保证检查点）**：QA = Quality Assurance（非 Question Answer）。课程已替大家做好了粗框架的 QA checkpoints——需求文档里写了学期要做 **7 件事**，每件 TA 如何打分、需求文档至少含哪几部分、各部分占多少分，都已在其中。但这是"guideline 级"的粗框架；组长把需求文档拆给组员后，对**每个人的子任务**还要有更详细的 checkpoints，才能评估其工作。

#### 3.2 伞形活动：贯穿始终的八件事

**umbrella（雨伞）** 得名于它的形态——把整个过程"笼罩"在下面。以下活动**贯穿 project 始终**，做任何一件小事时都要考虑：

| 伞形活动 | 含义 |
|---|---|
| Project Management | 任何小事都可视为一个小 project，都要有管理、有规矩 |
| Quality Assurance | 如何保证做的事是好的 |
| Product Production | 产品生产 |
| Measurement | 度量 |
| Formal Technical Review | 正式技术评审 |
| Configuration Management | 配置管理 |
| Reusability Management | 重用管理 |
| Risk Management | 风险管理 |

其精髓在于"大中有小、小中有大"：宏观有这几大活动，微观每个细节也贯穿着同样的逻辑。

### 四、五步本质流程：communication → planning → modeling → construction → deployment

无论具体模型长什么样，大体都绕不开这五个环节，不同公司只是对这五步做了**不同的排列与执行策略**：

```text
  ① Communication        ② Planning          ③ Modeling
  （沟通/需求收集）      （计划）            （建模/写文档）
        │                    │                   │
        └────────────────────┼───────────────────┘
                              ▼
                  ④ Construction（编码）+ Testing（测试）
                              │
                              ▼
                  ⑤ Deployment（部署）→ 接受用户反馈
```

1. **Communication（沟通）**：拿到 project 的第一件事**不是**需求分析，而是先跟客户谈——即课程里的 TA（扮演啥也不懂的客户）。要先"知己知彼"：摸清他懂什么语言、你该用什么程度的话跟他交流。真实世界里你通常不是给自家人做软件，客户非计算机出身、听不懂术语，必须用语他能懂的方式沟通。这是 requirement gathering（需求收集）过程。
2. **Planning（计划）**：摸清需求后才做计划。看手头有多少人、多少机器，大家对工具/技术的风险与人手熟练度如何，做分工，定 schedule 与各种 deadline。大面上的 plan 课程已定，但每个小组对自己小 project 还要另做 plan。
3. **Modeling（建模）**：计划完还**不能写代码**。建模要写文档，但文档**不是给你自己看的**（除非两三年后你忘了、要改 bug 时感谢当年的自己）。建模的重点是**跟别人沟通**——用图、表、统一格式描述你将搭建的系统的结构，目的是确认"我做的跟你要的是否一致"，让 customer 易看懂，也让组间、工程师间能在短时间内互相理解系统样貌、定位问题。统一图形语言是沟通效率的关键。
4. **Construction + Testing（构建与测试）**：当 customer 看了模型说"差不多就是我要的"，才真正开始写代码，写完测试。
5. **Deployment（部署）**：交第一版，接受用户反馈……事情并未结束（呼应上节课"90% 魔咒"与"交付后花 60%~80% 精力"）。

### 五、CMMI 能力成熟度模型：0~5 级全解

**CMMI = Capability Maturity Model Integration（能力成熟度模型集成）**。最早是 SEI（CMU 软件工程研究所）推出的 CMM，后来模型太多太庞杂，便做了 Integration 推出 CMMI，内容大致相同。独立评估机构会给软件公司打 **0~5 分**的成熟度等级，级别高（如 4 级、5 级）的公司可把认证书挂墙上拉生意，让人放心其有成熟管理机制。

各等级含义：

| 等级 | 名称 | 特征 |
|---|---|---|
| **Level 0** | Incomplete（不完整） | 基本不能算公司。创业草台班子：拿到活就做，无 process、无分工、无进程管理概念 |
| **Level 1** | Performed（已执行） | 开始有**分工**概念，知道每个任务要产生 work product，但**无管理**概念。典型如"组长分完工就撒手，deadline 前夜才收东西" |
| **Level 2** | Managed（已管理） | 有**管理**概念，有专人在管；所有 **stakeholders（项目干系人，即对项目有发言权的人）** 能有效沟通；过程被 monitored（监控）、reviewed（评审）、evaluated（评价）。**课程希望每组至少达到 Level 2** |
| **Level 3** | Defined（已定义） | 真像一个公司。规章制度**固化下来、写进文件、上墙**，成为贯穿任何 team、任何 process 的行为标准/行业规范，一代代传下去 |
| **Level 4** | Quantitatively Managed（量化管理） | 较大且历史长的公司才能做好。有意识地**采集数据**（每人每天产多少行源码、经手多大规模软件、查出多少 bug、月均查 bug 百分比等），分析后支撑管理决策。如向客户承诺"有 85% 把握达某质量标准"——这 85% 不能拍脑袋，要有算法从数据中得出 |
| **Level 5** | Optimizing（优化中） | 最高级。不仅守规矩、用某 process model，还**持续改进甚至创新**模型，用更好方法/技术保证质量、控制进程 |

评分方式值得注意：评估**重点看过程而非结果**——不是"看你最终交的软件市场评价好就打 5 分"，而是检查你做事情有没有规矩、管理严格到什么程度、员工多大程度把 manager 当回事。课程小团队多半连 Level 2 都未必稳达，但重在体验。

### 六、模式（Pattern）：可重用的过程模板

**Pattern（模式）** 更像 C++ 里的 **template（模板）**。前辈工程师把成熟的做事方式总结成模板，下次做相似事直接套用，最大好处是**重用（reusability）**。模式不仅 Process 有，每个环节都有。

教材定义：pattern "defines a set of activities, actions, work tasks, products, or related behaviors"。若自己定义一个 Pattern，至少应包含以下部分（结构极像一个 C++ 类定义）：

| 组成项 | 含义 | 类比 OJ 题目 |
|---|---|---|
| **Pattern Name** | 模式名称 | 题目名称 |
| **目的/类别** | 它管 process 哪一段（更有效测试？管理？设计？） | — |
| **Initial Context** | 在什么情况下可用此模式（输入前提） | 输入格式 |
| **Solution** | 如何解决（核心，相当于代码主程序） | 解题核心（由你写） |
| **Resulting Context** | 用成功后产生什么结果（输出） | 输出格式 |
| **Related Patterns** | 还需调用哪些其他模式 | 关联题目 |
| **例子** | 应用实例 | Sample In / Sample Out |

Process 模式分三大类：**Task Pattern**（与具体任务相关）、**Stage Pattern**（与 Framework Activity / 各单步过程相关）、**Phase Pattern**（如何把这些步骤串起来）。课程鼓励学期末总结出一个有用 Pattern 写成小 essay，可有加分。

### 七、过程评估、PSP/TSP 与个人复盘

**Process Assessment（过程评估）**：定义 process 后请独立机构评估，不仅给分数，还会出一份 **Report**——告诉你当前过程的能力成熟度、哪些方面不足、有哪些风险；据此组建团队改进，改进结果反馈回 process，形成闭环。书上列了几个独立评估机构，了解即可。

**PSP / TSP（Personal and Team Process Models，个人与团队过程模型）**：这是**建议而非规定**。个人做事建议有五个框架性环节：

1. **Planning（计划）**：任何活先计划。
2. **High-Level Design（高层设计）**：打算怎么做、做成什么样。
3. **High-Level Design Review（高层设计评审）**：去跟对方确认"我没理解错吧"。**切勿自动脑补**——常见错误是听了任务上半句就自行补完下半句去做，结果做错白干。务必确认沟通一致再动手。
4. （构建/执行阶段）
5. **Postmortem（事后复盘）**

**Postmortem（验尸报告）** 字面意为"验尸"，实际指**教训总结**：事情"死"了不要白死，要分析"怎么死的、为什么"。课程中一位实验室毕业、先后在国内与日本企业工作过的学长，对两国企业管理水平的差异感触极深——这正呼应了 postmortem 所代表的"从经历中萃取经验"的文化。

### 随堂自测

**1. 软件工程"层次化技术"的四层从底到顶分别是什么？最底层存在的根本理由是什么？**

解析：四层由底至顶为 Quality Focus（质量焦点）→ Process Models（过程模型）→ Methods（方法）→ Tools（工具）。最底层是 quality focus，其上一切过程模型、方法、工具的存在理由只有一个——保证做出高质量（可维护、可用、少 bug）的软件；任何不服务于该总目标的 process 都无意义。

答案：底层质量焦点、过程模型、方法、工具（顶）；最底层为质量焦点，一切制度皆为保证软件质量而存在。

**2. 拿到项目后的第一步为什么是 Communication 而非需求分析？建模（Modeling）产出的文档主要是给谁看的？**

解析：客户（课程中的 TA）扮演不懂技术的角色，必须先沟通、收集需求（requirement gathering）、知己知彼，才能正确分析。Modeling 文档重点不是给自己看，而是与客户确认"做的与要的一致"、与组间/工程师间统一描述系统结构，故首要给 customer 及协作者看。

答案：先沟通才能摸清客户真实需求；建模文档主要用于与客户及协作者沟通，确认一致性、统一系统描述。

**3. CMMI 中 Level 1 与 Level 2 的关键区别是什么？课程对小组的最低期望是哪一级？**

解析：Level 1（Performed）仅有分工概念、知每个任务产出 work product，但无管理；Level 2（Managed）加入管理概念，有专人在管、stakeholders 有效沟通、过程被监控/评审/评价。课程希望每组至少达到 Level 2。

答案：Level 1 有分工无管理，Level 2 有管理且过程受监控评审；期望至少 Level 2。

## 第 2 章：第4讲 软件过程-2

### 一、个人复盘（Postmortem）：从"结果"挖到"根源原因"

上节末尾提到的 **Postmortem（验尸报告）**，字面意为"验尸"，实际指**教训总结**：事情"死"了不要白死，要分析"怎么死的、为什么"。一位先后在国内与日本企业工作过的学长，对两国管理水平差距感触极深，他讲的故事正是 Postmortem 的范本。

他在日本公司由一位 mentor（师傅）带。有一次调程序卡死很久，最终发现原因是一段代码本可重用，他 copy-paste 时**手滑漏了一个字母**；偏偏漏字母后的变量名恰好是另一个**合法变量名**，编译通过、肉眼难辨，于是耗了极长时间才定位。

mentor 问他"原因"，他答"copy 漏了一个字母，所以错了"；mentor 打断："你告诉我的叫**结果（result）**，我问的是**原因（cause）**。"mentor 要的原因是：是鼠标不好用？日式键盘不习惯？工作时间太长精神难集中？家里有事心不在焉？——要分析到**根源**。

Postmortem 的目的正在于此：避免重蹈覆辙。会学习的人不是不犯错，而是**不重复犯同一种错误**——错一次就记住，不在同一坑里摔第二次；不会学习的人反复摔在同一坑里。核心是 **understand the types of errors（理解错误属于哪一类）**，从而规避再犯。这是个人做事的基本 process。

### 二、团队自驱与度量

对组长而言，每件任务须定义清楚、有执行"脚本"，然后团队应**自驱（teams are self-directed）**——像演电影，先有剧本大家照演，自己有效率地往前走，而不是每人都像机器人等顶端 manager 发话（"往东就往东、往西就往西、停就停"）。课程不需要这种被动团队。

关于 **measurement（度量）**：在真实公司可有意识地收集数据、分析并改进 team process。但本课程的 project 是特殊的训练项目，收集的数据对未来无用，故做度量的必要性不强。

### 三、规范模型（Prescriptive Models）的边界之辩：orderly approach 真的好吗？

接下来介绍的著名 process models，全部属于 **prescriptive models（规范模型）**。其反义词是"美国大片里的英雄"——遭遇计划外突发事件、事先没想好应对、见招拆招。这种英雄气概**最好别在软件开发中展示**。

Prescriptive 意为**事先规划好、按规矩做事**，强调 *orderly approach to software engineering（有序的软件工程方法）*。

由此引出第一个课堂讨论题：**Is orderly approach really that good?（有序方法真的那么好？）** 可从两方自圆其说：

- **强调 order 的弊端**：人类社会与人是最复杂的，需求变化是本质特征。过分强调规矩会**死板、不易适应变化**。
- **另一极端的弊端**：若完全抛弃 prescriptive，走到哪算哪、客户说改就马上改，会导致**一盘散沙、没头苍蝇**的状态。

结论预设在两类讨论里：order 与灵活都不可极端，关键在于权衡。学生需将观点写在纸上并签名提交。

### 四、瀑布模型：定义传统生命周期，也定义其死板

第一个、也是最古老的模型是 **Waterfall Model（瀑布模型）**。前述五个阶段正是由它总结而来，它定义了**传统的软件生命周期**。

#### 4.1 为什么叫"瀑布"

水从上往下流很顺，但**原则上不许返工**——想把下面的水倒抽上去，得动用抽水机、挑上去，极累。严格规则是：前一阶段彻底做完、通过评审后"关门"，原则上下一阶段不许回头。必须从上往下顺做。

#### 4.2 致命缺点

1. **太死板、不真实**。真实 project 不可能"前面做完后面不许返工"。常在 construction 甚至 testing 阶段，客户说"我要改个需求"——客户是上帝，不能不给他改。需区分：本课程的 customer（TA）是**存心捣乱**；真实 customer 并非故意，因为他也是人不是神，不能指望外行一次性把需求讲清。常见情形是"大概知道要做什么"，磨合中才发现有好几件事，一开始很难讲清。
2. **客户见到可用产品太晚**。直到 deployment 阶段才看到能用的东西。此前一直看文档、钱早给了却久不见成果，客户心理越来越没底、发毛不耐烦。更糟的是：给他 100 页需求文档让他找错，**他根本没耐心看完**——除非错得离谱，否则说不出哪里不对。等真看到可用产品才惊呼"不是我要的"，问答往往是：
   > "你怎么不早说？" —— "早我不知道。" —— "不是写在文档里了吗？" —— "没看懂。"

   此时双方都没脾气。

#### 4.3 现实地位

现在几乎**没有公司用纯瀑布**，但**所有公司的模型都是它的变形**——瀑布的五步贯穿在每一个模型里。

### 五、增量模型：先交 core product 占领市场（微软范式）

使用最广的渐增式开发是 **Incremental Model（增量模型）**，传说即微软做法。

```text
features
  ^
  |          ●(Increment 3)
  |       ●(Increment 2)
  |    ●(Increment 1)
  | ●(core product)
  +------------------→ time
```

- 横轴是时间，纵轴是完成的 features 数量。
- 以很短时间、很快速度先提交 **core product（核心产品）**——不完美但包含主要功能（如 Windows 最基本的操作界面），先**占领市场**。
- 此后不断升级，每次加 more features，逐步逼近完美系统。
- 每个 Increment 内部仍遵循瀑布五阶段。

其聪明之处在于：在 timeline 上以最短时间先站稳脚跟。人力资源上也极合算——设计工程师做完 Increment 1 的分析设计后，coder 进驻写程序测试；coder 做第一产品时，设计工程师已着手第二产品，无缝衔接，**没人闲着**。即 *makes a better use of resources（更充分利用资源）*。

### 六、RAD 快速应用开发：并行模块的快与适用边界

**RAD（Rapid Application Development，快速应用开发）**：communication、planning 做好后，在 **60~90 天（2~3 个月）** 周期内把东西做出来。其快源于**并行**——将问题拆成 N 个模块，N 个 team 同时开工，最后合并。这套模式与课程 project 的做法高度相似，于是引出第二个讨论题：**简化版支付宝适合选 RAD 吗？**

RAD 要"快"起来的前提条件：

1. **充分人手**：N 个 team 同时铺开。本课程闲人多，此条不是问题。
2. **客户得着急**：客户不急就快不起来。需建立与客户**救火式、快速反应**的沟通机制。但真实客户心态往往是："钱给你了，开发就是你自己的事"，不愿被频繁打扰，出差、度假、觉得"没必要替你找人"。若你没及时反应导致 deadline 交不了活，客户会认定"那是你的错"。所以课程强调要跟 TA（客户）拉好关系。
3. **系统能有效拆成 N 个较独立模块**：若模块间千丝万缕、接口始终定不下来，最后必一团乱麻。
4. **技术风险低、团队对技术熟悉**：若技术风险高，别急着上 RAD，中途必乱。

若以上条件不满足，RAD 未必是最佳选择——回答"好/不好"皆可，关键自圆其说。

### 七、演化式过程模型

#### 7.1 原型法（Prototyping）：用样机撬开含糊需求

**Prototyping** 是最受欢迎的演化式模型，前述"学长自创的 process model"总结的其实就是它。其流程极快：快速了解需求 → 快速计划 → 做 modeling design → 产出 **prototype（原型系统 / 样机）**。

样机是什么？一个有界面、按钮、菜单的**空壳**——按钮背后的功能可能尚未实现，先不做。把它给用户点一点、看一看，描述"点这个会发生什么"，借此收集反馈（如"菜单位置我不习惯、找半天没找着"）。人读图形普遍比读文字易懂，这是极有效的沟通方式：写上百页需求文档让用户评判满意度，他说不出；给一个可点的 prototype，他立刻告诉你哪要哪不要。故 prototype 是**沟通需求的好第一步**。

关键纪律：**prototype 最终不能作为正式产品交付，必须扔掉**。因为它以"快"为准，内部结构可能乱七八糟，后期改得面目全非，目的是借此得到正式需求后**另造系统**。但现实中很多团队没扔——授课者自己的项目组就没扔，一直在 prototype 上改，改到无比痛苦（后文再述）。

#### 7.2 螺旋模型（Spiral Model）：漂亮的图，少用的现实

**Spiral Model（螺旋模型）** 能写漂亮 paper、画漂亮图，但**没什么人用**。其轴表示花销（可理解为时间，时间即金钱），一条分割线是任务分割线，每次穿线都要测试/验证/审核；在**四个象限**里螺旋前进，每象限代表一类阶段工作：

```text
        需求/计划 ←─── ② 开发阶段(定功能)
          ↑                │
   ① 定目标/风险分析/原型  ③ 计划下一步
          ↑                │
          └─── ④ 测试验证/运行 ─┘
        （每转一圈 = 一个迭代周期）
```

- 第一象限：定 objective 总目标、做风险分析、给 prototype；
- 第二象限：开发阶段，把功能定下来；
- 第三象限：计划下一步（Requirement Plan、Life-cycle Plan）；
- 第四象限：测试、运行、验证，再计划下一圈。

过程太复杂，少有公司用，了解即可。它要表达的是软件有**演化 / 进化**的过程。

#### 7.3 并发开发模型（Concurrent Development）

**Concurrent Development Model（并发开发模型）** 适合 **client-server applications**。与前几种"流水线式"不同，它是一个**网络（network）**而非一条线——回想数据结构里的 AOE network、AOV network：算关键路径、最长周期、关键任务。它用网络描述过程而非线性序列。

### 八、特殊模型与统一过程（Unified Process）

其余特殊模型简述：

- **Component-based Development（基于构件开发）**：强调**重用**。模块化要好，抽象出模块使类似产品可直接拿来用。
- **Formal Methods（形式化方法）**：给庞大非 IT 企业做办公管理系统时，多部门需求可能矛盾（一份五六千字需求文档中，部门间要求互相冲突）。靠人脑发现冲突既难又不靠谱，故用**数学 / 形式化语言表述需求，自动查逻辑冲突**。
- **Aspect-Oriented（面向方面）**：近年流行，译法五花八门，不展开。
- **Unified Process（统一过程）**：与"面向对象"同期产生，重要工具是 **UML（Unified Modeling Language，统一建模语言）**，以设计软件 **architecture（架构）** 为核心，用 **use case（用户脚本，描述用户如何使用软件）** 驱动。它是 **iterative（迭代）、incremental（增量）** 的，特点是以 UML 为重要工具。其 phases 与传统五步对应：

| Unified Process 阶段 | 对应传统步骤 | 含义 |
|---|---|---|
| **Inception（初始）** | communication + planning | 正式表示"开始" |
| **Elaboration（细化）** | planning + modeling | 粗了解后再细化 |
| **Construction（构建）** | construction | 进入编码构建 |
| **Transition（过渡）** | deployment + construction 后期 | 产品从专业人员转到用户手中，release 一个版本 |

随后反复迭代，一个 increment 一个 increment 地交付，进入 production 阶段。各阶段 work products 详见教材。

### 九、一条贯穿线：所有模型都是瀑布的变型，质量是不可让步的终点

增量、演化等模型，本质上**都是 Waterfall Model 的变型**——没人再用纯瀑布，但瀑布五步贯穿每个模型内部。它们共同强调的是 **flexibility（灵活性）** 与"快"。

但必须时刻提醒：**无论用哪种 model，最终目的都是保证 high quality（高质量）**。若"快"要伤害"质量"，必须做权衡。模型是手段，质量才是终点。

### 随堂自测

**1. Waterfall Model 为何被称为"瀑布"？它最不真实的两点表现是什么？**

解析：因前一阶段做完原则不许返工，如水流只能自上向下、倒抽极难，故称瀑布。最不真实处：①真实项目不可能"前面做完后面不许改"，客户（上帝）常在 construction / testing 阶段改需求；②客户到 deployment 才见可用产品，且给百页文档他也看不出错，等见到成品才发现不符预期。

答案：水只能向下流、不可倒抽喻不可返工；不真实在"客户中途必改需求"与"客户太晚见可用产品、文档难校验"。

**2. Incremental Model 与 RAD 在"快"的机制上有何根本不同？RAD 适用的前提条件有哪些？**

解析：Incremental 的快来自"先交 core product 占领市场 + 设计/编码人员无缝接力"；RAD 的快来自"N 个 team 并行开发 N 个模块、最后合并"。RAD 前提：充分人手、客户愿意急、系统可拆成独立模块、技术风险低。

答案：增量靠核心产品先行与人员接力；RAD 靠并行模块合并。RAD 需人手足、客户急、模块独立、技术熟。

**3. 原型法（Prototyping）中"prototype 必须扔掉"的理由是什么？若舍不得扔会发生什么？**

解析：prototype 以"快"为唯一准则，内部结构乱、功能多为空壳，仅用于撬开含糊需求、确认用户真实意图，故不能作为正式产品。若在其上持续修改，会改到"无比痛苦"——授课者项目组即因未扔掉 prototype 而深陷其中。

答案：原型仅为快速沟通需求、内部混乱不可作正货；不扔则在其上反复修补、痛苦不堪。

## 第 3 章：第5讲 软件过程-3
> 对应分集：P05 | 原始标题：《第5讲 软件过程-3》

### 一、规范模型的适用边界：为何"有序"仍主导、又为何需要敏捷补位

本章所讲的全部 process models 都属于 **prescriptive process model（规范/描述性过程模型）**——事先规定任务与次序，强调有序的软件工程方法。在软件过程的早期，这类模型确实带来很大好处：它为开发规定了明确的任务与要求，使混乱可控。

但随着软件发展、用户对交付时间和变化响应要求越来越高（尤其大量 Web 应用），纯规范模型暴露出诸多问题。因此**第四章将专门引入敏捷软件过程（agile）来应对**。本章先夯实规范模型家族本身——它们至今仍有作用，是理解后续一切模型的基础。

需要明确一个判据：课程的大 project（简化版支付宝）**不适合 RAD 模型**。原因有二：其需求在立项时基本已确定（大作业性质），且课程项目**没有那么多资源**。RAD 与增量模型的最大区别，正在于它依赖**大量组间并行开发、需要大量资源**——这是课程情境不具备的。

### 二、瀑布模型及其 V 模型变体

**Waterfall Model（瀑布模型）** 是过程模型中最基础的一个，也是"经典生命周期"的代名词。其命名源于瀑布**永远从上往下流、难从下往上流**的线性特征。

#### 2.1 五个阶段

最基础的瀑布模型抽取出软件开发必备的五个要素，自上而下推进：

| 阶段 | 内容 |
|---|---|
| **沟通（Communication）** | 项目启动前调查需求，与项目提供方充分沟通 |
| **策划（Planning）** | 将口头沟通落实为书面文件：项目估算（时间/成本/人力）、进度计划（全局观，何时做何事）、项目跟踪（tracking） |
| **建模（Modeling）** | 用模型工具把复杂问题形象化，便于在更抽象层面分析与设计（非直接代码） |
| **构建（Construction）** | 编码与测试——本科生当前主要学习内容 |
| **部署（Deployment）** | 交付、支持与反馈；程序做完不是终点，要获取新需求、改进意见 |

水从顶端一直滑下，正如箭头依次推进，故曰瀑布。

#### 2.2 V 模型变体

瀑布还有一个重要变体 **V-Model**：左侧自上而下是**开发**流向（需求分析 → 概要设计 → 详细设计 → 编码），右侧自下而上是**测试**流向，且一一对应：

```text
需求分析 ─┐
概要设计 ─┤
详细设计 ─┤        单元测试
  编码  ─┼─ 对应 ─ 集成测试
          │        系统测试
          │        验收测试
```

左侧每个开发环节，都在右侧有对应层面的测试验证。V 模型与经典瀑布本质相同，都符合"顺序原则"。

#### 2.3 现实困境

瀑布最符合人们最初的直觉，但现实应用问题显著：

1. **真实工程很少严格顺序进行**。线性模型不强调迭代，要用间接方式实现变动都极其困难。
2. **用户需求无法在一开始就清晰、准确、完整**。瀑布的前提（需求一开始就提得非常清晰完整）在操作中很难实现；需求随开发过程不断变化。
3. 一旦后期变更，线性结构使回头成本极高。

### 三、增量模型：以 iOS 的版本迭代为证

**Incremental Model（增量模型）** 在实践中用得较多、也较好。其核心是：先交付一个**功能较弱但可运行的雏形**，再不断加入功能、逐步逼近完美。

以 **iOS 操作系统** 为例极具说服力：

- **2007 年第一版**：功能极欠缺——无彩信、无复制粘贴，仅具打电话、发短信能力；
- **第二版起**：加入中文字符支持、手写输入法、App Store 与开发者 SDK，系统开始流行；
- **2009 年**：推送通知、拷贝粘贴（发布两年后才补上）、彩信（推出两年后加入）、蓝牙、语音控制；
- 之后持续迭代：多任务、文件夹等；
- **2011 年 iPhone 4S**：iCloud 云端功能；
- 再后来：智能助手 Siri。

五年间 iOS 不断功能迭代、向"完美"迈进——这正是增量模型的典型应用。需澄清一个常见误解：iOS 3 与 iOS 2 并非推翻重来（无重构式重置），而是在原有基础上**持续加入新功能**，因此符合"在一个项目内部做增量"的定义（每个版本不是独立项目，而是同一操作系统项目的迭代）。

增量模型的优点：

1. 人力不足时，短时间开发雏形，**快速交由客户获得支持、缓解团队人力压力**；功能需快速迭代时可投入更多人力做"功能试点"。
2. **化解风险**：若某功能点市场反响差，早期发现比漫长开发后才发现浪费更小——避免人力、时间、精力成本打水漂。

### 四、RAD 快速应用开发：与增量的同与异

**RAD（Rapid Application Development，快速应用开发）** 同样使用瀑布五过程，本质是把这五过程**快速融合、高速重复**，相当于"高速瀑布模型"。

#### 4.1 机制与适用

- 尽可能**利用现有程序构件（component）**，并为以后重复开发类似构件做好准备（可重用构件）；
- 适用场景：小型团队用已有构件创建工程；时间紧迫时大团队快速迭代；学生团队用开源构件快速完成 construction 环节。

#### 4.2 与增量模型的区别

增量也能"开发得比较快"，但 RAD 的最大特征是**大量组间并行开发**——需要大量资源协调。例如 A 组开发某功能模块、B 组开发另一模块，初期就要大量人力资源去协调匹配。

#### 4.3 缺点与不适用情形

1. 初期可能需要大量人力资源协调多组并行；
2. 客户与程序员都须**适应** RAD 节奏——若客户提要求但程序员未适应，无法在时限内交付；
3. **高性能项目不适合**：如为移动终端开发接口，若重用原本给 PC 浏览器的接口，对低带宽移动环境不合理；
4. 若需大量**新技术**，开发风险极高，等开发完才发现不符合要求，重构的时间成本更高。

正因如此，课程项目（资源有限、需求既定）不适用 RAD。

### 五、演化式过程模型

演化式模型的现实背景有三点：业务与软件需求**不断变化**；开发时间紧、须有限时间内推出有限版本应对商业竞争；开始时系统细节不明确，须通过演化不断完善。它是**不断迭代**的过程。

#### 5.1 原型开发（Prototyping）：循环逼近含糊需求

**Prototyping** 是一种循环过程，不断完善软件版本直到客户满意接受。适用于：

- 客户定义了总体要求，但**未定义详尽的输出、输入与过程细节**，且客户自己也不太清楚；
- 不确定**算法有效性、操作系统能力、人机交互形式**等情形。

其循环如下：

```text
  沟通(明确需求)
      │
      ▼
  快速策划 + 设计原型 → 交付客户试用
      ▲                    │
      │                    ▼
  客户反馈(再沟通) ←── 调整版本
      │
   （循环直至客户接受）
```

**优点**：客户能立刻看到软件初步长什么样，观点直观；能快速推出、不浪费其他资源。

**缺点**：

1. 开发者为快速推出，**未考虑长期维护**，后期维护困难、质量不高；
2. 为快速实现，可能沿用自己熟悉但**未必适合**的语言/架构，导致性能下降。

**关键纪律**：一开始就要定好规则，让客户明白——原型开发是**为后续正式系统服务**的，而非推出一个产品就再也不改。换言之，原型绝不能当最终产品。

#### 5.2 螺旋模型（Spiral）：Boehm 的风险驱动迭代

**Spiral Model** 由 **Boehm 教授**提出，核心目标是**减少软件开发风险**。它把原型开发的迭代过程，与瀑布模型的**可控性、系统性**结合在一起。

可理解为"在原型开发中加入了风险分析"。其形态是**顺时针不断扩大的圆圈**（每圈代表一次迭代，圆圈随软件完善而扩大）：从沟通开始 → 策划 → 项目设计 → 编码测试 → 产品发布。早期几次迭代可能只是"产品说明书"阶段；随着迭代加深，开发出较像样的原型；原型再经多次迭代演化出不同版本，适应不同需求。

特征与适用：

- 适合开发**大型软件系统**；
- 难点：常需反复修改，**可控性不确定**，难说服客户（"已有这么好的了为何还要一直改"）；
- 必须配备**大量风险评估专家**——若风险未被检测到，产品可能失败。

### 六、统一过程（UP / RUP）：用例驱动、架构中心、迭代增量

**UP（Unified Process，统一过程）**，早期称 **RUP**——因其出自 Rational 公司（即开发画 UML 的 Rational Rose 软件的公司，后被 IBM 收购，遂改叫 UP）。它像螺旋模型，也是**迭代 + 增量**，试图把前面"一大堆乱七八糟的模型"统一起来，故称"统一过程"。

#### 6.1 三大特点

1. **use-case driven（用例驱动）**：用例即 UML 中的 use case diagram——给用户看的图，画出有哪些角色、各自要做什么，以及系统给什么输出；多用户时描绘其相互关系，无需文字描述。
2. **architecture-centric（以架构为中心）**：在 **elaboration（细化）** 阶段就要把软件架构定好，此后若无问题架构不动；后续迭代都围绕该架构展开。
3. **iterative + incremental（迭代 + 增量）**：切分很小阶段，每阶段都出成果以控制风险。

#### 6.2 四个阶段与迭代

UP 分四阶段，对应传统步骤：

| UP 阶段 | 含义 | 主要产出（Artifact） |
|---|---|---|
| **Inception（初始）** | 项目开始 | 用例图（标示用户需求）、领域模型、术语表 |
| **Elaboration（细化）** | 粗了解后细化 | 画出系统模块与子模块图；做出**可执行的**（模块间可互动）原型；架构用 UML 表达 |
| **Construction（构建）** | 进入编码 | 大部分编码完成，产出可运行系统 |
| **Transition（过渡/交付）** | 转交用户 | 交付、修复 bug |

四个阶段构成一个完整生命周期，但**每个阶段可切分为多个迭代**（较小时间段），每次迭代结束都要出一个成果——如同课程中"第一周、第二周都要完成一件东西"，避免全部堆到最后。每迭代有目标，每大阶段也有目标；目标未完成则前期工作视为未完，须重做。

每个迭代内含 **5 个 workflow（工作流）**，类似瀑布：沟通需求 → 分析 → 设计架构 → 编码实现 → 测试（课本还提 4 个支持性工作流）。各阶段这五项工作量不同：前期用例建模多，后期实现多——并非"某阶段绝对做或不做"，而是"做多或做少"。

#### 6.3 与迭代模型的不同：强调 Artifact

UP 特别强调整个过程中要产出 **Artifact（制品/人造物）**——每个阶段结束要生成什么。例如 Inception 完成的最重要判据：**把成果拿给客户看、客户认可即可**；细化阶段须做出模块间可互动的原型（不同于纯静态界面样机）。

现实映射：Windows Vista 的 Beta 1、Beta 2、候选版（Release Candidate）、零售版，正是迭代产出；Win7、Win8 也都实行迭代开发。

### 七、软件生命周期视角：从立项到消亡的全过程

跳出单个模型，须从**软件生命周期**整体理解：软件从**立项 → 开发 → 维护 → 消亡**，是完整生命周期。前述各模型（尤其演化模型）描述的正是这一发展过程——软件一个版本接一个版本，最初功能很弱，后不断增加、演化，直到消亡，过程才结束。

演化过程**包含维护过程**。UP 与 UML 紧密对应：UML 从 80 年代面向对象思潮中诞生，是 OO 开发最流行、最成功的环境与工具；UP 则是与 UML 配对、面向对象的**过程模型**。尽管 UP 表现形式与前几类模型差异明显，但其**核心内容基本一致**，只是表达不同。

### 随堂自测

**1. 瀑布模型与 V 模型的关系是什么？V 模型右侧的测试层级自下而上如何对应左侧开发环节？**

解析：V 模型是瀑布模型的变体，本质都符合顺序原则。左侧自上而下为需求分析→概要设计→详细设计→编码；右侧自下而上对应单元测试→集成测试→系统测试→验收测试，每个开发层都有对应测试验证。

答案：V 模型是瀑布的顺序变体；右侧测试自下而上（单元/集成/系统/验收）一一对应左侧（编码/详细设计/概要设计/需求分析）。

**2. 增量模型与 RAD 在"快"的机制上根本区别何在？为何课程项目判定不适用 RAD？**

解析：增量之快来自"先交功能较弱雏形 + 持续迭代加功能"；RAD 之快来自"大量组间并行开发、高速重复瀑布五过程"，需大量资源协调。课程项目需求立项时基本已确定、且缺乏大量并行资源，故不适用 RAD。

答案：增量靠雏形先行与迭代；RAD 靠多组并行 + 大量资源。课程项目资源有限、需求既定，故不适 RAD。

**3. 螺旋模型由谁提出？它试图把哪两类思想结合起来？它最主要的风险控制前提是什么？**

解析：螺旋模型由 Boehm 提出，把原型开发的迭代过程与瀑布模型的可控性、系统性结合，目标是减少风险。其落地前提是必须配备大量风险评估专家，否则风险未被检测会导致产品失败；且因频繁修改难说服客户。

答案：Boehm 提出；结合原型迭代 + 瀑布可控性/系统性；前提是需大量风险评估专家且难说服客户接受持续修改。
