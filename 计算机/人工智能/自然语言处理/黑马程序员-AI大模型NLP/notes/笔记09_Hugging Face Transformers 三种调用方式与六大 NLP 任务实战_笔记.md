# Hugging Face Transformers 三种调用方式与六大 NLP 任务实战
## 三种调用方式的定位与选型


### 三种调用结构各自替谁做决定

* **pipeline（管道方式）**
    * > **定义**：transformers 库提供的高级接口，作用是快速调用预训练模型完成常见 NLP 任务；函数名是 `pipeline`，没有 `s`，写成 `pipelines` 不可用。
    * 只需两个参数：参一是任务类型，参二是模型路径；任务类型写错就找不到任务，与模型无关。
    * 分词、张量封装、输出整理全部在底层完成，开发者只交代「任务名 + 模型路径」并把文本丢进去。
    * 代价是中间过程不可控：截断、补齐、句子长度这些活都插不上手，想 DIY 也做不了。
* **自动模型（Auto）**
    * > **定义**：所有以 `auto` 开头的 API 组成的调用方式，定位是比管道方式更具体——多出来的「加功」的活由开发者自己干。
    * 步骤为：先加载分词器，再加载模型，然后自己把文本转成张量，最后喂给模型并自己解析输出。
    * 换任务时要同步换 `AutoModelForXxx` 任务头，头选错则输出形状与标签表都对不上。
* **具体模型（具体模型方式）**
    * 类名从 `Auto` 换成系列名：`AutoTokenizer` → `BertTokenizer`、`AutoModelForMaskedLM` → `BertForMaskedLM`，中间那个 `Model` 不要。
    * `BertForMaskedLM` 只能下载 BERT 系列模型，想玩 GPT 用这套走不通。
    * 流程与自动模型完全一致，剩下的代码一个字都不用动。

### 三种方式的横向对比

| 对比项 | 管道方式（pipeline） | 自动模型方式（Auto） | 具体模型方式（Bert 等） |
| :--- | :--- | :--- | :--- |
| 加载分词器 | 底层自动完成 | 第一步，自己写 | 第一步，换成系列分词器类 |
| 加载模型 | `pipeline()` 一次搞定 | 第二步，`AutoModelForXxx` | 第二步，`BertForXxx` |
| 文本转张量 | 底层自动完成 | 第三步，自己写（两种思路） | 第三步，写法相同 |
| 推理与输出 | 底层整理成可读结果 | 第四步自己调，输出自己解析 | 第四步同自动模型 |
| 中间层 | Hugging Face 全包 | 经 Hugging Face 适配底层 | 不经过中间层，直接对接厂商 |
| 换模型范围 | 由任务名与模型路径决定 | 按任务类型全厂商可选 | 锁定该系列，BERT 就是 BERT |
| 参数命名 | 无 | 统一规范，不能乱变 | 各厂商自行把控，可能有差异 |
| 功能开放度 | 全部屏蔽 | 中间层做了屏蔽，够用为主 | 直接对接，API 更全更灵活 |
| 使用难度 | 低 | 低 | 高 |

* 读表的落点只有两处：管道方式与自动模型方式的可换模型范围，以及具体模型方式被锁定的系列范围（BERT 就只能是 BERT）。
* 三种方式的差距全部落在中间那一层上：有它换来的是统一与通用，没有它换来的是灵活与功能完整。

### 选型结论

* 管道方式给初学者用，几行代码出结果；自动模型给「既想换不同模型、又不想太操心」的人用；具体模型自由度拉满，什么都能改也什么都得自己管。
* 三条路不是「哪条更高级」的关系，而是「谁来做决定」的关系：找不对模型，等于把选择权交出去而已。
* 六个任务的代码骨架高度统一，会一个就会六个：换任务名、换模型、换句子，输出写法照抄。
* 六个任务乘三种写法本来是 18 个案例，因具体模型与自动模型几乎一样，课程按 6、6、1 共讲 13 个；掌握文本分类、特征提取、完形填空，了解阅读理解、文本摘要、NER。
* 日常使用自动模型就够了；具体模型作为了解，需要更细致地玩时再把 `Auto` 换成对应系列的类名。

## 六个任务的定位与产出形态


### 任务头：成品与半成品的分界

* **任务头（Task Head）**
    * > **定义**：`AutoModelForXxx` 里 `For` 后面那个单词，指模型顶部针对具体任务的那一层；任务决定了要哪个头，名字里带 `For` 的部分就是任务头。
    * **带头任务头输出**：输出针对具体任务的结果，是成品，拿到就能直接用。
    * **不带任务头输出**：输出文本的原始特征（中间结果，类似词向量），是半成品，必须结合后续模型继续处理。
    * 不带头只给原材料，适合自己后续开发新任务；带头能落地，文本分类、情感分析、翻译全部属于带头。
    * 记法只有一句：带头就是有结果，不带头就是没结果。
* **六个任务按任务头的归类**
    * 带头任务头：情感分类、完形填空、阅读理解、文本摘要、命名实体识别。
    * 不带任务头：特征提取，它属于预训练任务的范畴，输出结果要和其他模型一起用。
    * `AutoModel` 不带任务头，输出的是文本的隐层表示，也就是一个矩阵。

### 六个任务的任务名与产出

| 任务 | 任务名 | 要求 | 有任务头 | 输出长什么样 |
| :--- | :--- | :--- | :--- | :--- |
| 文本分类（情感分类） | `sentiment_analysis` | 掌握 | 是 | 带 `label` 与 `score` 的字典列表，`label` 取概率最高的那一档 |
| 特征提取（特征抽取） | `feature-extraction` | 掌握 | 否 | 类似词向量的特征，类型是 `list` |
| 完形填空（掩码语言建模） | `fill-mask` | 掌握 | 是 | 每个候选带 `token_str`、`token` 等字段 |
| 阅读理解（抽取式问答） | `question-answering` | 了解 | 是 | `{'score', 'start', 'end', 'answer'}` |
| 文本摘要 | `summarization` | 了解 | 是 | `[{'summary_text': ...}]` |
| 命名实体识别（NER） | `ner` | 了解 | 是 | 一条实体一个字典的列表，带 `entity`、`word`、`index`、`start`、`end`、`score` |

* 情感分类覆盖的场景不止一种：情绪分类（「今天开心极了」是积极、「今天很难过」是消极）、商品分类（手机壳与数码配件分到一起，连衣裙归到服饰）、好评差评判断。
* 命名实体识别找的是人名、地名、组织机构名以及其他实体；它与词性标注（POS）标的对象不一样——POS 标名词、动词这一类词性，NER 标实体类别。

### 任务与模型的配对与替换

* 六个模型对应六个任务，每个任务使用与自己匹配的模型：情感分析用 `chinese_sentiment`，特征提取用 `bert-base-chinese`，完形填空用 `chinese-bert-wwm`，摘要用 `distilbart-cnn-6-6`，NER 用 `RoBERTa-base`。
* 模型路径必须指向与该任务匹配的模型，用了别的任务的模型，行为不会是你想要的。
* 不知道某个任务该配哪个模型时，去模型社区的任务导航里查：打开首页，左侧按大类列好热门任务、多模态、自然语言处理、语音，点进对应任务，右边列出的就是属于这个任务的模型。
* 同一个任务可以换别的模型来解决，只要能出效果就都行；不改代码，只改模型路径这一行。

## 运行环境与本地模型准备


### 依赖包与运行环境

* 两条安装命令一条都不能少：`pip install transformers` 和 `pip install datasets`；`transformers` 负责加载模型，`datasets` 负责把数据弄进来。
* 导入写法是 `from transformers import pipeline`，注意没有 `s`。
* GPU 环境和 CPU 环境都要各装一遍，只装一个时解释器会直接报找不到模块，跟模型无关。
* 环境里没配好对应算力时，运行时会自动兜底到 CPU，控制台刷出「没检索到 GPU、实际走 CPU」的信息——那是日志，不是警告更不是报错，只是跑得慢。
* > **易错点**：资料里可能还写了 `git clone` 那一套，那是 Linux 环境下的部署方式，与本套流程无关，直接跳过。

### 本地模型的数量与存放

* 共享资料里的预训练模型要先同步下载并解压，一共六个模型，对应六个任务，解压后大约九个 G。
* 模型不贴进项目目录，放在项目外（例如 C 盘 `software` 目录下），原因是每天都可能新建一个 day 目录，九个 G 的模型塞进项目等于每天重新搬一遍。
* > **易错点**：模型路径必须合法，不能出现中文、空格、特殊符号；一旦落在这种路径下，加载时会出问题，而报错信息通常不会直接告诉你「是中文路径的锅」。
* 用 `BertTokenizer` 等具体模型类时同样要写绝对路径或相对路径，但必须真实合法。

### 路径写法与绝对路径的获取

* 绝对路径的取法：选中文件夹右键 → 属性 → 安全 → 对象名称，从那里把路径拷出来；`Ctrl+C`、`Ctrl+V` 也可以。
* Windows 路径分隔符是反斜杠，直接粘进 Python 字符串会被当成转义字符，所以前面加 `r` 写成原始字符串：`model_path = r"C:\software\chinese_sentiment"`。
* 也可以写相对路径，比如 `./model/chinese_sentiment`，前提还是路径合法。
* 模型目录的取法：对着模型文件夹右键选「打开文件所在位置」，往上一级，选中模型目录，把整条路径拉过来填进 `model` 参数。

## 模型检索与目录构成


### 按任务检索与在线测试

* Hugging Face 的检索路径：进网站点 `Models`，在左侧选任务（如文本分类 `text classification`），搜索框里输入 `chinese` 就会把做中文文本分类的模型筛出来。
* 直接下载的弊端是先下载才能用，万一下完发现不是想要的效果，时间就白花了。
* 在线测试：点进模型页面后有输入文本的地方，填进去点 `Compute`，下面立刻出结果；旁边的 `Use in Transformers` 可以查看该预训练模型的下载地址。
* > **提示**：先在线测试，确认是你要的效果再下载；不是你要的效果就不下，这个顺序能省掉大量无用的下载时间。
* 魔搭社区（ModelScope）同样可用：点模型库，在自然语言这一栏里点文本分类，搜索 `chinese`，`bert-base-chinese` 等中文模型直接筛出来。
* > **易错点**：魔搭有自己类似 transformers 的库，在线体验的导包导的是 `from modelscope.pipelines`；本套代码用的是 Hugging Face 的 Transformers，导包和下载来源必须配套，混着用一定跑不通。

### 配置文件与标签映射表

* **config.json（模型配置文件）**
    * > **定义**：模型目录里记载该模型各项配置参数的文件，用 `AutoConfig.from_pretrained(model_name)` 加载，`AutoConfig` 的作用就是自动配置模型参数。
    * 情感分析模型的配置里写着一共 5 星，0 到 4 分别代表五星好评里的每一档，本质上是一个 5 分类问题。
    * 自动模型方式比管道方式多一个动作，就是加载配置文件；它不是每个任务都要做，NER 需要它来把数字 ID 翻译成标签。
* **`id2label`（标签映射表）**
    * 作用是把 ID 转成对应的标签：告诉你 ID 是 1 就标成 `B-address`，是 12 就是 `I-movie`。
    * 用法是 `config.id2label[index]`，这个键名是标准的反查表；同一份配置里还有 `hidden_size` 之类的字段，需要什么从这里取什么。
    * NER 到底识别哪些类别，答案全在这张表里：address（地址）、book（书名）、company（公司）、game（游戏）等等；不同模型这张表不一样，不能把示例当结论。

### 词表与特殊标记索引

* 词表文件是模型目录下的 `vocab.txt`（或 `vocab.json`），每一行一个 token，行号与 ID 一一对应；`vocab_size` 表示训练这个模型一共用了多少个词，量级在两万多个。
* `[CLS]` 与 `[SEP]` 也有各自的索引，分别是 101 和 102，都可以在词表里直接查到。
* > **易错点**：词表里的行号从 1 数，而 token 索引从 0 开始数，所以关系是「行号 = ID + 1」；要找 ID 101 的 token 去看第 102 行得到 `[CLS]`，要找 ID 102 去看第 103 行得到 `[SEP]`，差 1 不是 bug，是数数方式不同。
* 模型目录里一般还有 `README`，写着你想用我该做哪些事、版本、用法（usage）等等，翻一翻就知道它支不支持某种语言。
* 判断一个模型支不支持手上的语言，直接双击进模型目录看 `vocab.json`，里面标着这个模型认识哪些字符；不支持就换个模型，思路全都一样，换的只是模型那一行。
* > **易错点**：模型目录里的文件是整个模型的一部分，别乱删；误删了重新解压一遍即可，但压缩包别动它，解压出来的目录随便点。

### 结构参数与词表的语言覆盖

* `bert-base-chinese` 是 12 层、12 个注意力头，每个头 64 维，$12 \times 64$ 正好合起来 768 维，对应配置里的 `hidden_size` 是 768、`num_hidden_layers` 是 12、每层 `num_attention_heads` 是 12。
* 配置写在文件里、形状体现在输出上，两边是同一件事的两种呈现，而且这些参数都是可以改的。
* 中文模型的词表里同时收了中文、日文和特殊符号，所以完形填空的候选里可能冒出片假名 `スノー`（雪）或 `しています`（正在做某事）这类非汉字 token，它们是词表里检索出来的合法 token，不用慌。
* > **易错点**：`bert-base-chinese` 是原生 BERT 的变体，与「原生的 BERT」不是一回事，别搞混。

## 分词器输入构造


### 三组字段的含义与取值

* **input_ids（文本 ID 序列）**
    * > **定义**：文本按词表切好并映射成索引后得到的序列，对应模型目录下的词表文件。
    * 头部 `101` 是 `[CLS]`，尾部 `102` 是 `[SEP]`，中间是我们写的每一个字按词表查出来的索引。
    * 「我想明天去 `[MASK]` 家吃饭」编码后是 `101, 2769, 2682, 2523, 1217, 103, 1716, 1391, 1928, 102`，共 10 个位置。
* **token_type_ids（段落标记）**
    * 用来区分输入里的不同文本段：属于第一句的位置标 `0`，属于第二句的位置标 `1`。
    * 只有一个句子时整条都是 `0`；出现 `0`、`1` 交替时才是第三句、第四句的段落标记。
    * > **易错点**：第二句比较短、被填充到固定长度时，第二句的 `token_type_ids` 又会全是 `0`，这些 `0` 是填充位而不是第二个句子。
* **attention_mask（注意力掩码）**
    * 字面翻译是注意力掩码，实际含义是「是否真实数据」：`1` 代表真实值（这个位置真的有内容），`0` 代表填充值（为了凑长度补出来的）。
    * 掩码里连续的 `1` 有几位，就说明这一条样本的真实 token 有几位；后面成片的 `0` 就是补位留下的空位。
    * 模型靠这个掩码知道哪些位置该看、哪些位置可以忽略，句子真实长度是几就靠它告诉模型；没有填充时它就全是 `1`。

### 特殊标记与序列长度

* **`[CLS]` 与 `[SEP]`（BERT 系列特殊标记）**
    * > **定义**：开头标记 `[CLS]` 与结尾标记 `[SEP]`；只要用 `bert-base-chinese`，它就会自动给你加一个开头、加一个结尾，中文模型和英文模型都有。
    * 别记成 `SOS`、`EOS` 那一套，那是别的模型的写法。
    * `[CLS]` 负责提供句子级表示、`[SEP]` 标记句子结束；`[CLS]` 的向量表示同时也是整个序列的聚合表示，所以做分类时很多做法直接取 `[CLS]` 那一个位置来用。
    * > **易错点**：判断一个句子的 `sequence_length` 不能只数汉字个数，必须把首尾两个特殊标记一起算进去。
* **`[MASK]`（掩码占位符）**
    * 占位符不是下划线之类的东西，就是方括号包起来的大写单词 `[MASK]`，而且区分大小写。
    * `[MASK]` 是词表里的一个独立特殊符号，对应索引 103，只会被切成一个 token，不会被拆成六个字符。
* **序列长度算例**
    * 「人生该如何起头」共 7 个汉字，加上 `[CLS]` 与 `[SEP]` 两个位置，位置总数 $7 + 2 = 9$，所以输出的 `sequence_length` 是 9。
    * 「我爱北京天安门，天安门上太阳升！」不算空格是 16 个字符加末位标点共 17，再加首尾的 `[CLS]` 与 `[SEP]` 正好 18。
    * 「我想明天去 `[MASK]` 家吃饭」是 `[CLS]`、八个字、`[MASK]`、`[SEP]`，一共 11 个位置。

### 文本对的拼接格式

* **`encode_plus` 的拼接规则**
    * > **定义**：`encode_plus` 收到「问题 + 上下文」两个字符串时不是各转各的，而是把它们拼成一条序列再编码。
    * 拼接格式是 $[\text{CLS}] + \text{问题} + [\text{SEP}] + \text{上下文} + [\text{SEP}]$。
    * 上下文结束处那个 `[SEP]` 确实存在，只是它在整条序列的最后，被中间一大段上下文推远了，所以第一眼看容易觉得「中间缺一个」。
    * 三个问题跑出来是三组结构完全相同、只有问题段内容不同的序列：固定的部分是 `[CLS]`、`[SEP]`、上下文、`[SEP]`，变化的部分是问题。
    * 第二个 `[SEP]` 已经承担了分隔作用，所以第二句前不必再加一个开头标记。
* **文本对里的字段取值**
    * 问答式输入里 `token_type_ids` 按段取值：问题段为 `0`，上下文段为 `1`。
    * 这条序列全是真实 token、没有任何填充，所以 `attention_mask` 全为 `1`，`0` 留给填充位。
    * 拼接后序列的长度直接决定问答输出里 `start_logits` 与 `end_logits` 的长度。
    * > **易错点**：上下文里最好不要写空格，做分隔优先用逗号或其他标点——空格会被分词器删掉，你肉眼看到的「我叫 张三」和模型实际拿到的「我叫张三」长度不一样，后面靠位置索引切答案就会差位。

### 词表与索引的核对方法

* 拿到索引后按「索引 + 1」的行号去词表里核对：索引 872 对应第 873 行，那是一个「你」字；索引 1962 对应第 1963 行，是「好」字。
* 索引 2476 对应行号 2477 是「张」，索引 676 对应行号 677 是「三」。
* > **易错点**：看索引和词表对不上号时，先数长度再数位置；你按人的习惯从 1 开始数，而词表索引从 0 开始，所以要找的那个字在词表文件里的行号永远比索引大 1，这一步最容易让人怀疑「是不是模型加载错了」。
* 索引是给模型用的、字是给人看的，中间那一步转换必须交给分词器，不要凭索引去猜对应哪个字。

## 批量长度与张量转换


### return_tensors 与两种转张量思路

* **`return_tensors`（返回张量类型）**
    * > **定义**：指定分词器返回什么类型的张量，默认 `None`；可选值有 `pt`（PyTorch 张量）、`tf`、`np`（NumPy）。
    * 写 `pt` 返回的直接就是二维张量（外层带批次维度），一步到位；不写就要自己把一列整数包装成张量。
    * 不写 `return_tensors` 但补上 `encode` 动作时，打印出来是纯粹的一串编号，没有字典包装，但类型是列表；`encode` 与 `encode_plus` 本质上是同一件事的简写与完整版，`encode_plus` 是增强编码、参数给得更全。
    * 摘要任务里对纯英文文本可以直接写 `my_tokenizer(text, return_tensors="pt")`，不需要额外做编码那一步。
* **两种思路的对比与取舍**

| 思路 | 写法 | 返回物 | 后续动作 |
| :--- | :--- | :--- | :--- |
| 思路一 | 带 `return_tensors="pt"` | 二维张量（带字典包装） | 直接可用 |
| 思路二 | 不加 `pt`（用 `encode`） | 一维列表（纯编号，无字典包装） | 需 `torch.tensor([...])` 手动升维 |

* 两种写法打印结果上下对齐看，内容完全一样——同样的一串编号、同样的形状；既然结果一样，就用带 `pt` 的那种，省一步手写。
* > **易错点**：只要用 PyTorch 框架，底层流转的东西就都得是张量；模型要的是二维张量，用一个列表直接传进模型是处理不了的，得用中括号包一层升成二维：`tensor2 = torch.tensor([message_list])`。

### padding、truncation 与 max_length

* `padding="max_length"` 是填充方式，可以理解为「是否填充」，写 `max_length` 就是一律补到指定长度——最大长度是 50 时，不够 50 的就直接补到 50。
* `truncation=True` 是是否截断，`max_length` 指定输入的最大长度；填充和截断这一对在这里全都有了。
* 输入「人生该如何起步」七个字，在 `max_length=5` 加 `truncation=True` 下结果里只剩 5 个 token，超出的部分被截掉。
* > **提示**：`padding="max_length"` 会把每一条都补到 `max_length`，所以不同句子的张量长度一致；批量送入模型时长度必须对齐，这正是管道方式里控制不了、而现在能自己控制的那一环。
* 特征提取用 `max_length=30` 是为了让输出里的填充位看得清楚，真实长度不足 30 的部分会被补上，正好用来解释 `attention_mask` 里的 `0`。

## 前向推理与输出形状


### 评估模式与字典拆包

* **`eval()`（评估模式）**
    * > **定义**：`eval` 在这里是 evaluate，做预测、进入评估模式（也叫推理模式）的意思。
    * 作用是在预测时关闭 `Dropout`、随机失活这些只在训练时使用的层。
    * 跑推理之前必须调用它，同一句输入每次跑出来的结果才是稳定的。
* **`**inputs`（字典拆包传参）**
    * 作用是把字典里的每个键当成关键字参数传进去：`input_ids` 传给 `input_ids`，`token_type_ids` 传给 `token_type_ids`，`attention_mask` 传给 `attention_mask`。
    * 直接写 `my_model(inputs)` 是把整个字典当成一个位置参数塞进去，模型并不知道该拿它怎么办，直接报错；正确写法必须是 `my_model(**inputs)`。
    * 理解方式：把字典的花括号摘掉，键当参数名、值当实参；不写 `**` 就得手动逐个传 `my_model(input_ids=..., token_type_ids=..., attention_mask=...)`，两者等价。
* **只传 `input_ids` 的场景**
    * NER 只把 `inputs['input_ids']` 传过去就够了——模型只需要文本对应的序号。
    * 摘要用 `my_model.generate(inputs["input_ids"])`，刻意只取 `input_ids` 一个键，不把整个 `inputs` 铺开传进去。

### 返回结构与同名的 from_pretrained

* 默认返回包含模型输出的字典对象，不同类型各有一个名字：分类任务是 `SequenceClassifierOutput`（里面是 `loss=...`、`logits=...` 这样一排键值对），NER 是 `TokenClassifierOutput`，特征提取是 `BaseModelOutputWithPoolingAndCrossAttentions`。
* 加上 `return_dict=False` 返回元组，元组里当前只有一个张量对象，写成小括号加逗号的形式。
* 两种写法拿到的东西对不上：字典键值分明但一眼不太好懂，元组拎出来就是裸数据、当列表读也行但对不上字段名，想弄清楚里面装了什么两种都要打出来看看。
* `AutoModel` 与各个 `AutoModelForXxx` 提供了同名的函数（比如都叫 `from_pretrained`），`AutoTokenizer` 与 `AutoModel` 之间也是如此；这是为了调用方便刻意设计的，用的时候要清楚自己调的是分词器的还是模型的，名字一样、对象不同。
* 每个分词器对应一个模型，换来换去一定会出问题；`convert_ids_to_tokens` 翻译出来的 token 与模型内部的词表完全对齐，所以第一步必须先把分词器配对。

### 各任务输出张量的维度分解

* **`last_hidden_state` 与 `pooler_output`**
    * `last_hidden_state` 是最后一个隐藏状态的输出，形状是 `(batch_size, seq_len, hidden_size)`，也就是常说的 BTC 三维；`bert-base-chinese` 下 `seq_len` 由 `max_length` 决定、`hidden_size` 是 768。
    * `pooler_output` 是池化层的输出，形状是 `(batch_size, hidden_size)` 二维；做法是对最后一层隐藏层先做一次线性变换，再取平均池化。
    * > 结论：池化层把 `(1, 30, 768)` 压成 `(1, 768)`，作用是忽略「句子长度」这一维，只在 batch 与 hidden 两个维度上留结果；出现「平均池化」这个词基本说明它服务的场景是分类。
    * 输出对象里还装着 `past_key_values`、`attentions`、`cross_attentions` 等等，都不需要全关心。
* **logits 的三维读法**
    * 完形填空里 `logits` 的形状是 `torch.Size([1, 11, 21128])`：第一个 `1` 是批大小，中间 `11` 是句子长度，最后 `21128` 是词表大小；读成一句话就是「11 个位置，每个位置都给出词表里两万多个词各自的分数」。
    * NER 里 `logits` 的形状是 `torch.Size([1, 18, 32])`：第一个 `1` 是一个句子里只有一条数据，`18` 是 token 数，`32` 是类别数，来自 `config.json` 里 0 到 31 的标签表；张量的第二维跟着 token 走，第三维跟着标签表走。
    * 序列分类里 `logits` 的形状是 `(1, num_labels)`，也就是一条样本、每个类别一个分数。
    * > **易错点**：`logits` 里的数不是概率，是未归一化的分数；想拿概率得自己走 softmax，但做预测只看谁大谁小，直接取 argmax 就够，不必多此一举。
    * 掩码语言建模虽然只留了一个空，模型其实把 11 个位置全部预测了一遍，每个位置都有自己那 21128 个分数，我们只是去里面挑掩码那一位。
* **问答任务的两套位置分布**
    * `start_logits` 表示答案起始位置的分数分布，`end_logits` 表示答案结束位置的分数分布。
    * 两个形状一样，都是 $1 \times 26$，长度等于输入序列长度，因为每一个 token 位置都可能是答案的起点，也都可能是终点。

## 任务结果的还原


### 分类与掩码任务的取数

* **文本分类取类别下标**
    * 模型吐出的是 `logits`，取最大值对应的下标即可：`pred_id = torch.argmax(logits, dim=-1).item()`。
    * 类别下标与「好评/差评」这类标签文字的对应关系取决于该模型自己的配置，所以先看下标、再按模型说明把它翻译成标签是最稳的做法。
* **完形填空定位掩码那一行**
    * 定位分两步：先在掩码位置取最大分数的索引，再把索引翻译回字。
    * 索引位置可以数出来：索引 `0` 是 `[CLS]`，`1` 到 `5` 依次是「我 想 明 天 去」，第 `6` 位正是 `[MASK]`。
    * 取数写法是 `torch.argmax(output.logits[0, 6], dim=-1).item()`：取第 0 个批次、第 6 个位置那一行，在第 21128 个分数里找最大值所在的位置，再用 `.item()` 把张量里的标量取成 Python 数字。
    * 这一步得到索引 872，再用 `my_tokenizer.convert_ids_to_tokens(872)` 还原成「你」。

### 抽取式问答的区间定位

* **`start_logits` 与 `end_logits` 的取数**
    * 取数写法是 `start = torch.argmax(output.start_logits)`、`end = torch.argmax(output.end_logits) + 1`，`torch.argmax` 就是在 26 个分数里找最大值所在的位置。
    * 加 1 的原因是后面靠切片把答案取出来，而切片包左不包右：模型认为答案是第 2 到第 5 个 token 时，写成 `[2:5]` 会拿不到第 5 个 token，答案少一个字。
    * 第一个问题跑出来是 `start = 8`、`end = 10`（原值 9 加 1），答案落在第 8 位到第 9 位，不含第 10 位。
    * > **易错点**：`end` 不加 1，取出来的答案永远缺最后一个字；这不是模型预测错了，是切片边界的问题。
* **切片与逐层还原**
    * 还原写法是 `my_tokenizer.convert_tokens_to_string(my_tokenizer.convert_ids_to_tokens(inputs["input_ids"][0][start:end]))`。
    * 从里往外读：`inputs["input_ids"]` 是形状 $1 \times 26$ 的嵌套张量，`[0]` 拆掉最外面的批次框，`[start:end]` 按区间切片，`convert_ids_to_tokens` 把索引转成 token 文本，`convert_tokens_to_string` 把若干 token 拼成可读字符串。
    * > **易错点**：不要用 `convert_tokens_to_string` 去接索引，它接的是 token；把索引转 token 的那一步是 `convert_ids_to_tokens`，顺序反了会直接报错。
    * 三问三答：`我是谁？` → 张三；`我是做什么的？` → 程序员；`我的爱好是什么？` → 乒乓球；抽取式问答从不生成新句子，它只输出 $[start, end)$ 这一刀切下来的原文片段，所以只要下标没错，答案一定在原文里逐字找得到。
* **候选与置信度**
    * `score` 是模型对这个答案的置信度；模型返回的候选在 pipeline 里默认只给最优的一条，想看更多候选可以调 `top_k` 参数取前 k 条，再横向比较它们的 `score` 和下标区间。
    * 近义词替换是抽取式问答里常见的语义坑：原文写「我的喜好是」而问题问「我的爱好是什么」时，模型会给出一个低分候选（`乒乓球`、`台球` 这类，概率大概 7%），分差正是判断「模型到底有没有读懂」最直接的观察点。

### 摘要任务的生成与解码

* **`generate`（生成式推理）**
    * 摘要属于序列到序列的任务，输入一条序列、输出另一条序列，所以加载模型要选 `AutoModelForSeq2SeqLM` 这一支。
    * 推理写法是 `my_model.generate(inputs["input_ids"])`，这里刻意只传 `input_ids` 一个键；写成 `my_model.generate(**inputs)` 会把 `input_ids`、`attention_mask` 全都传进去，对这次要演示的东西来说多传的参数是不需要的。
    * `outputs` 是一个二维张量，外层是批次，`outputs[0]` 取的就是里面那一行编号，也就是模型生成的答案的编号序列。
* **`decode` 与它的三个布尔参数**

| 参数 | 取值 | 含义 |
| :--- | :--- | :--- |
| `skip_special_tokens` | `True` | 跳过特殊标记，即去掉 token 前后的特殊字符 |
| `clean_up_tokenization_spaces` | `True` | 是否清理分词遗留的空格 |
| `tokenization_spaces` | `True` | 是否保留原始分词的空格 |

* 写法是 `"".join([my_tokenizer.decode(g, skip_special_tokens=True, clean_up_tokenization_spaces=True, tokenization_spaces=True) for g in outputs])`，`g` 就是 `outputs` 里的每一个数值序列，逐个 `decode` 再拼起来。
* 把 `skip_special_tokens` 从 `True` 改成 `False`，输出里立刻会多出 `<s>` 这样的标记，这正说明这个参数在干什么。
* > **易错点**：`convert_ids_to_tokens` 出来的是 token（还带着特殊标记），不是给人读的句子，到这一步必须再走一次 `decode`，否则打印出来的永远是那串编号。

### 命名实体识别的标签反查

* **逐 token 取最大概率标签**
    * 取数写法：`for token, value in zip(input_tokens, logits[0])`，命中 `token in my_tokenizer.all_special_tokens` 就 `continue` 跳过，再 `index = torch.argmax(value).item()`，最后 `outputs.append((token, config.id2label[index]))`。
    * `logits[0]` 把批次那一维去掉得到 `[18, 32]`——18 个 token、每个配一个 32 维分布；`torch.argmax(value).item()` 在那个 32 维分布里找最大值下标，`.item()` 把单元素张量取成 Python 整数。
    * 先做一步 `my_tokenizer.convert_ids_to_tokens(inputs['input_ids'][0])` 把 18 个 ID 全翻译回 token，才方便和标签一一对齐；这样 18 个 token 就各自得到了自己的标签 ID。
    * 中间先打印一次标签下标能看清过程：「我」是 0、「爱」是 0、「北京天安门」得到 1、2、2；0 对应 `O`，1 对应 `B-address`，2 对应 `I-address`。
    * 最终形态是列表套元组：`[('我', 'O'), ('爱', 'O'), ('北京', 'B-address'), ('京', 'I-address'), ...]`；`[CLS]` 位置的 32 个分数代表「这个特殊符号该被标成什么」，一般都会被过滤掉。
* **BIO 标注方案**
    * > **定义**：NER 本质上是分类任务，更准确地说是一个序列标注任务（sequence labeling）——给句子里的每一个 token 打一个标签。
    * 标注体系只有三类：`O` 是非实体，`B-xxx` 是某类实体的第一个 token（Begin），`I-xxx` 是某类实体的后续 token（Inside）。
    * 同一实体内部的字第一个打 `B`、其余全部打 `I`，所以一个实体就是「一个 B 加一串 I」的连续区间；遇到下一个 `B` 或遇到 `O` 这一段就断了。
    * `B` 标记既代表「新实体开始」，也隐含「上一个实体到此为止」；拿到结果先扫 `B`，每一个 `B` 就是一次实体切分的边界。
    * > **易错点**：`B` 和 `I` 本身不携带实体类型，类型写在后面的后缀上（`PER` 人名／`LOC` 地名／`ORG` 组织机构名／`MISC` 其他实体）；判断「是不是同一组」只看 `B` 与 `I` 的断点，不看类型后缀。
    * NER 不是可有可无的边角任务：实体词识别是句法分析的基础，而句法分析坐在 NLP 任务的核心位置。

### 管道方式的结果解读

* 情感分类输出里 `label` 是标签（`STAR_5` 就是五星好评），`score` 是分数；这个分数可以直接理解成概率，最后选概率最高的那一个返回给你。
* 完形填空默认返回概率最高的前五个结果，不是一个；把「我想明天去 `[MASK]` 家吃饭」丢进去，前五名依次是「她」「你」「他」「我」「您」，五个字全部来自模型的词表，词表里没有的字绝不会输出。
* 完形填空结果里的 `token` 字段是整数，去 `vocab.txt` 里按「索引 + 1」的行号即可核对位置：排第二的「你」token 是 872，在第 873 行。
* 摘要任务的返回值是 `[{'summary_text': '...'}]`，`summary_text` 就是模型提炼出来的那段简短内容；摘要每一句都能在原文里找到出处，它是针对原文的提取，不是另起一段自由发挥。
* 特征提取的返回值类型是 `list`，而 `list` 没有 `shape` 属性，得先用 `np.array(output)` 转成 `ndarray` 才能取形状，得到 `(1, 9, 768)`。

## 自动模型方式的类族与调用链


### 三个 Auto 基类与分组导包

* `AutoConfig`：自动配置模型参数，每个模型都有自己的 `config`，这个类负责把配置自动读出来。
* `AutoModel`：自动加载模型，可以理解成一个通用的模型加载类，专门帮你加载 Hugging Face 里各种模型；它不带任务头，输出的是文本的隐层表示即一个矩阵。
* `AutoTokenizer`：自动加载「和模型匹配的」分词器，也就是一个通用的分词器加载类；模型没法直接处理一大坨长文本，需要先切词，而不同语种的切词习惯不一样，中文怎么切、英文怎么切都有各自的规则。
* 只导这三个类还不够——它们能把模型加载进来，却没法让模型去完成具体任务，所以还要再导一组带任务头的类：`AutoModelForSequenceClassification`、`AutoModelForMaskedLM`、`AutoModelForQuestionAnswering`、`AutoModelForSeq2SeqLM`、`AutoModelForTokenClassification`。
* > **提示**：这三个类的记法很简单，写 `auto` 敲下去，编辑器提示里全是它们。
* 分词器（Tokenizer）可以类比成以前用的结巴分词器（类比可以，但别把它当成同一件事），它的本职就是分词。

### 任务与任务头的对应表

| 任务 | 模型类 | 说明 |
| :--- | :--- | :--- |
| 文本分类 | `AutoModelForSequenceClassification` | sequence 指文段，这里的分类就是在文段上做分类 |
| 特征提取 | `AutoModel` | 不带任务头，输出隐层表示 |
| 完形填空 | `AutoModelForMaskedLM` | 即掩码语言建模，掩码语言指的就是 `mask` 的位置 |
| 问答 | `AutoModelForQuestionAnswering` | question + answering，问答 |
| 文本摘要 | `AutoModelForSeq2SeqLM` | 序列到序列建模，摘要就是典型的序列到序列 |
| 命名实体识别 | `AutoModelForTokenClassification` | token 级别的分类，具体到字 |
| 全任务通用 | `AutoTokenizer` | 分词器，文本与 ID 之间互转 |

* 误用完形填空的任务头：不能再写 `AutoModel`，用它加载，模型顶部没有那个「输出到词表维度」的预测头，跑起来会直接告诉你拿不到 `logits`；`AutoModelForMaskedLM` 与 `AutoModel` 的唯一区别就是多了顶上那一层按词表打分的预测头。
* 误用问答的任务头：不能直接 `AutoModel`，直接用它加载，模型顶部没有问答头，取不到我们要的 `start_logits` 和 `end_logits`。
* 文本分类用 `AutoModelForSequenceClassification`，NER 用 `AutoModelForTokenClassification`；一个是给整个句子一个标签，一个是给每个 token 一个标签。
* NER 归到 `TokenClassification` 是因为它的标注能拆到每一个字上——像「北京天安门」会被标成 `B I I I I`，粒度是 token，比整句分类细得多。

### 五个任务的链路共性

* 自动模型方式一共五步（含打印输出）：找分词器、找模型、准备数据、送进去推理、处理并输出。
* 步骤一 `AutoTokenizer.from_pretrained(...)`，步骤二 `AutoModelForXxx.from_pretrained(...)`，步骤三用分词器分词并补/截、转张量，步骤四 `my_model.eval()` 后前向推理，步骤五解析返回值。
* 模型是「老大」、分词器是「秘书」：直接去找老大，老大不认识我们、不接见，所以第一步就是把模型配套的秘书找过来，由秘书把我们的问题翻译成老大能吸收的方式；所以必须先有秘书，再请出老大。
* 以后所有任务都按这个骨架走，换的只是 `AutoModelForXxx` 那一个任务头，以及各任务对输出的解读方式。
* 具体模型方式的思路跟自动模型一模一样，唯一变的是 API 的名字，其余全同。

### 减少重复与批量循环

* 模型路径要写两遍（加载分词器一次、加载模型一次），哪天换模型漏改一处就报错，所以把模型名提成一个变量，在文件最上面记一次，下面都用它。
* 阅读理解用 `for question in questions` 驱动：模型是逐个问题做推理的，一个问题进去一段答案出来，下一个问题再进去再出一段答案；上下文和模型始终不变，变的只有循环变量。
* 抽取式问答用关键字传参，`question` 与 `context` 谁写在前面都无所谓，两种写法等价。
* 上下文里可以故意用空格分隔来做观察实验，比如 `context = "我叫 张三 我是一个程序员 我的喜好是 PPQ"`，用来暴露空格被忽略的后果。
* 六个任务的代码和模型都一样却「别人能跑、自己报错」时，通常是 Anaconda 版本、驱动版本这类环境差异，两条路可走：降版本把环境往回调，或者换一个模型。
* `from rich import print` 只是让打印格式更好看一点，处理超长文本或特殊格式时才会做自动换行之类的处理，写不写都行。

### 管道方式与自动模型方式的步骤对照

```text
管道方式                              自动模型方式
--------                              ------------
pipeline(任务, 模型)                   1. AutoTokenizer 加载分词器
      |                                2. AutoModelForXxx 加载模型
      v                                3. encode_plus 文本转张量
数据直接丢进去                          4. model(...) 前向获取结果
      |                                5. 手动处理并输出
      v                                      |
   结果打印                                   v
  (3 行)                                结果打印 (5 步)
```

* 管道方式把分词、输入封装与输出整理全部封在底层，只交代「任务名 + 模型路径」就能拿到结果，所以代码只有 3 行。
* 自动模型方式把同一套动作摊开成 5 步，多出来的第 5 步正是它「更透明但更啰嗦」的代价：拿到的是形状或分数而不是可直接展示的内容时，还得自己动手找最大值、做转换。
* 管道方式的价值是简单、高效地把各种自然语言任务跑起来，代价是中间的细节你控制不了——想微调、想改句子长度都插不上手。

## 具体模型方式


### 类名替换与全局替换改法

* 改动只有两处：`AutoTokenizer.from_pretrained` → `BertTokenizer.from_pretrained`，`AutoModelForMaskedLM` → `BertForMaskedLM`。
* 注意类名不是机械替换：`AutoModelForMaskedLM` 换过去叫 `BertForMaskedLM`，中间那个 `Model` 是不要的。
* 想偷懒就直接 `Ctrl+R` 全局替换，把所有 `Auto` 换成 `Bert`，点 `Replace all` 完事；`encode_plus` 还叫 `encode_plus`，模型还是往里一传，换完剩下的一堆代码全都不用动，右键跑一遍结果一样。
* 换完以后打印的日志比之前少很多，因为只做基础的、简单的活时写法就是一样的，只是把 `BertTokenizer`、`BertForMaskedLM` 这两行换一下。
* > **易错点**：先跑通 `Auto` 那一版再动手改——如果代码里写的还是 `Auto`，它跑的就是自动模型而不是具体模型，预测出来的最大概率也是自动模型的。

### 功能更全的原因与代价

* `Auto` 是「我帮你挑一个够用的」，`Bert` 是「你自己挑，我把更多口子开放给你」；这些具体模型类底层支持的比 `Auto` 更细致、更深入。
* 具体模型类提供的 API 比自动模型对应的类更多、更全——按住 `Ctrl` 点进类定义里去翻，把 `BertTokenizer` 与 `AutoTokenizer` 两边对着看就能看出差别。
* 直接跟模型对接，拿到的口子更全；自动模型那边有些「我觉得不需要开放给你」的内容，Hugging Face 在中间就帮你屏蔽掉了。
* 具体模型的输入输出格式各厂商可能有细微差异，这是灵活性的代价；基础功能上它们的用法完全一致。
* > **易错点**：具体模型方式要求开发者自己把控各厂商的输入输出，有可能同一个功能参数名有细微差异——比如分词器在自动模型这边叫 `Tokenizer`，到某个具体实现里叫 `tokenizers`，多一个字母就是这种情况。

### 两条调用路径的分工与选用

* Hugging Face 扮演的是「布置作业、制定规则的人」：把分词器叫什么、模型的接口长什么样、具体用谁全都定死，再去找各个厂商，把它们的模型功能拿过来用；规则就是接口。
* 各个厂商是「交作业的人」，按规则把模型做出来，实现思路可以各不相同，但最终完成的效果一定是规则要的那个效果；我们作为调用者只管看最终效果，不管底层怎么实现。
* 自动模型的代价是被管着——底层变量名怎么起、函数名怎么命名都得照规则来，不能乱变；好处是更固定、更通用。
* 具体模型有点像「不走 Hugging Face 那一套了，直接跟厂商对接」，更灵活但难度也更大。
* 落地判断：日常使用自动模型就够了，具体模型作为了解；想更细致地玩，把 `Auto` 换成对应系列的类名（如 `Bert`）即可，剩下的代码一模一样。

```text
                自动模型                     具体模型
调用路径     我 ──> Hugging Face ──> 厂商    我 ──> 具体模型
可换模型     按任务类型全厂商可选            锁定该系列（BERT 就是 BERT）
参数命名     统一规范，不能乱变              各厂商自行把控，可能有差异
功能开放     中间层做了屏蔽，够用为主         直接对接，更全更灵活
使用难度     低                             高
```

* 六个任务只演示一个完形填空的原因：其他五个一模一样，再写一遍只是把同一份代码抄到另一个标题底下。
