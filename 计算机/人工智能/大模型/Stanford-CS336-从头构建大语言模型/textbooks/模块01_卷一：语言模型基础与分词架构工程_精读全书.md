在今天这样一个编码智能体凭借零样本提示就能编写出完整程序的时代，我们为什么还要大费周章地从零去构建一个大语言模型？

如果你只是想利用现有的模型开发应用，通过提示词（Prompting）确实能解决许多实际问题。提升抽象层级本是一件好事，然而抽象层从来都不是完美的，它们往往存在“漏洞”（Leaky Abstractions）。当你给模型编写提示词却无论如何都无法达成目标、陷入无计可施的境地时，你就会意识到，仅仅停留在提示层极大地限制了你所能探索的方案空间。如果你想从事基础研究，或者渴望对系统的底层机理拥有绝对的控制力，唯一的途径就是把整个技术栈推倒重来，通过亲手构建每一个模块，彻底搞懂它们是如何运转的。

### 大语言模型研究方法论与扩展思维

从零开始构建语言模型，首先需要建立一整套适应现代规模化计算的研究方法论。我们需要明确小规模实验的边界，区分不同层级的知识属性，并正确理解算法效率在规模扩展中的决定性作用。

#### 抽象层漏洞与推倒重来的必要性

回顾人工智能研究的演进历程，技术栈的抽象层级一直在不断上移：
- 大约十年前，做 AI 研究必须自己亲手实现网络架构，并从头编写训练循环；
- 到了八年前，研究范式转变为下载 BERT 等预训练模型的开源权重，在其基础上针对特定下游任务进行微调；
- 如今，许多工作已经被简化为直接向闭源前沿模型发送提示词。

提示工程虽然能快速交付成果，但在基础研究中，它将研究者局限在一个高度受限的黑盒接口内。面对模型能力失效、长上下文退化或推理瓶颈等深层缺陷时，上层提示往往无能为力。要打破这种局限，必须深入底层，重建从分词、架构、分布式系统、数据清洗到对齐微调的完整流水线。

#### 小模型与前沿大模型的扩展差异

构建大语言模型在当下已经高度工业化。训练前沿模型的资金投入极其巨大：三年前训练 GPT-4 据传耗资约 1 亿美元，如今前沿模型的训练成本已攀升至 10 亿美元量级，依赖数以万计的 GPU 集群协同运算。更严峻的是，前沿模型的系统细节几乎完全闭源，正如 2023 年 GPT-4 技术报告所陈述，出于竞争格局与安全的考量，模型架构、硬件配置、算力规模和训练细节均未公开。

在学术界或普通算力条件下，我们只能构建小型语言模型。然而必须时刻警惕：**小规模实验观察到的规律，往往无法直接代表前沿大模型的行为**。造成这种鸿沟的核心原因有两个：

```text
+-----------------------------------------------------------------------+
| 差异维度一：计算浮点运算分配（FLOPs Distribution）                   |
|                                                                       |
| 小规模模型 (Small-scale)       前沿规模模型 (~15B+ Parameters)        |
| +-----------------+            +------------------------------------+ |
| | MLP: ~44%       |            | MLP: ~80%                          | |
| +-----------------+            +------------------------------------+ |
| | Attention & Other: ~56%      | Attention & Other: ~20%            | |
| +------------------------------+------------------------------------+ |
|                                                                       |
| 差异维度二：涌现能力（Emergent Abilities）                            |
|                                                                       |
| 模型性能 (Accuracy)                                                   |
|      ^                                                                |
|      |                                            * * * (性能跃升)   |
|      |                                          *                     |
|      |                                         *                      |
|      |                                        *                       |
|      | --------------------------------------*                        |
|      | (小规模/少样本学习基本处于随机基线)    |                       |
|      +----------------------------------------+------------------->   |
|      0                                   临界规模 (Scale)             |
+-----------------------------------------------------------------------+
```

*图：小规模模型与前沿模型在计算瓶颈及涌现能力上的本质断裂示意图。*

1. **计算瓶颈随规模发生结构性偏移**：在小模型中，多层感知机（MLP）层消耗的浮点运算次数（FLOPs）仅占总量的约 44%，其余开销主要分布在注意力机制等结构中；但当模型参数规模扩展至 150 亿（15B）以上时，MLP 层消耗的浮点运算比例飙升至 80%。这意味着，如果在小规模下花费大量精力优化注意力计算，在大模型场景下所获得的全局加速收益将被急剧摊薄。
2. **行为涌现现象的非线性跃迁**：小模型在少样本（Few-shot）或零样本（Zero-shot）任务上通常表现得几乎毫无效果，指标长期贴近随机基线；只有当参数和数据跨过特定临界规模后，模型才会突然展现出解决复杂推理任务的涌现能力。在小规模下做消融实验，很可能会误判某些关键技术的真实价值。

#### 可迁移知识的三层分类架构

面对这种规模鸿沟，我们应当从小规模构建中汲取哪些能够真正迁移到前沿规模的知识？必须将其划分为三个层次：

```text
+-----------------------------------------------------------------------+
| 可迁移性分级架构                                                      |
|                                                                       |
| 1. 机制 (Mechanisms)      -> 完全可迁移                               |
|    - Transformer 内部张量流动、自注意力与 MLP 运算机理                |
|    - 模型并行、张量分片、分布式通信与底层内核加速原理                 |
|                                                                       |
| 2. 思维模式 (Mindset)     -> 完全可迁移                               |
|    - 对每一个模块进行严谨的基准测试 (Benchmarking) 与性能分析 (Profiling)|
|    - 追求系统与硬件效率的最大化，以扩展配方指导全局决策               |
|                                                                       |
| 3. 直觉 (Intuitions)      -> 高度不可靠 / 难以跨规模迁移              |
|    - 具体的超参数选择、数据混合配比、微小架构变体在特定规模下的优劣   |
|    - 往往属于纯实证试错产物，不可在缺乏大规模验证下随意推断           |
+-----------------------------------------------------------------------+
```

*图：从模型构建实践中提炼的三层知识架构及其可迁移性界限。*

机制层与思维模式能够跨越规模持续生效。你可以完全通过数学与代码理解通信拓扑、内存搬运与并行切分；你也会始终坚持用严苛的基准测试（Benchmarking）与性能分析（Profiling）数据指导优化。

> **易错点**：切忌将小模型上总结出的“架构直觉”盲目套用到大模型上。许多架构改动的成功并不遵循纯粹的理论美感，而是工程试错的实证结果。正如 Noam Shazeer 在提出 SwiGLU 激活函数的经典论文中所坦陈的结语：“我们不做任何解释，我们把这些架构的成功，一如其他一切，都归于上天的恩典。”

#### 可扩展算法与资源效率乘数定律

业内常提及由 Rich Sutton 提出的“苦涩的教训”（The Bitter Lesson），但这一概念在当下常被粗暴地误解为“算法毫无用处，规模堆叠一切”。

> **结论**：正确的解读是：**唯有能够伴随算力扩展而持续释放收益的可扩展算法，才是制胜的关键**。规模本身并不排斥算法，规模恰恰极度渴求高效率的算法。

可以用一个直观的关系式来审视模型性能与系统的关系：

$$\text{Accuracy} \approx \text{Efficiency} \times \text{Resources}$$

其中输入的是计算与数据等硬件资源（$\text{Resources}$），而算法与系统则决定了资源转化效率（$\text{Efficiency} = \frac{\text{Output}}{\text{Input}}$）。规模越大，效率提升的经济价值就越巨大：
- 在一次耗资数千美元的小规模调试中，计算效率下降一倍，你或许只需多等待一倍的时间；
- 但在总预算高达数亿美元的前沿集群上，即便是 5% 的算法与系统效率提升，也直接对应着数千万美元的资金节省与训练周期的成倍缩短。

从实证历史上看，OpenAI 在 2020 年的分析指出，在 2012 至 2019 年间，ImageNet 任务上达到相同分类精度所需的算法计算量缩减了整整 44 倍。正是算法效率的持续改良与硬件算力爆发发生相乘效应，才造就了现代大语言模型的突破。因此，整个预训练阶段的核心问题可以提炼为：**在给定的计算预算与数据约束下，我们能构建出的最优模型究竟是什么？**

### 语言模型技术演进与开放生态

为了深入技术细节，我们需要建立关于语言模型技术源流与生态环境的历史纵深。语言模型并非近年骤然诞生的产物，其核心概念与范式经历了长达数十年的迭代演进。

#### 神经架构与预训练范式演进

从概率统计到神经网络，语言模型的历史脉络清晰可寻：
- **统计建模起源**：早在 1950 年代，Claude Shannon 便利用 n-gram 统计模型测算英语文本的信息熵。在长达数十年的时间里，n-gram 模型一直是机器翻译与语音识别系统中保证文本流利度的标配组件。
- **神经架构探索**：1990 年代长短期记忆网络（LSTM, Long Short-Term Memory）问世；2003 年 Yoshua Bengio 发表了第一篇基于前馈神经网络的神经语言模型论文；随后序列到序列（Seq2Seq, Sequence-to-Sequence）框架提出，确立了将非定长序列压缩为隐空间向量的范式。
- **Transformer 与系统基石**：为了解决神经机器翻译问题，业界相继发明了 Adam 优化器、自注意力机制，并最终于 2017 年催生了 Transformer 架构。随后，混合专家网络（MoE, Mixture of Experts）与模型并行切分技术也相继萌芽。
- **自监督预训练的爆发**：2010 年代末，ELMo 与 BERT 确立了在大规模无标注文本上进行自监督预训练、随后在下游任务进行参数微调（Fine-tuning）的标准路径。

#### 计算最优扩展定律与开源模型发展

真正通过坚定拥抱规模化扩展打开新局面的机构是 OpenAI。从 GPT 到 GPT-2，团队逐步确认了模型的扩展能力；在充分接纳扩展定律（Scaling Laws）的指引后，他们训练出了参数量剧增 10 倍以上的 GPT-3，首次在业界展现出令人惊叹的上下文学习（In-Context Learning）能力。

这一突破引发了全球实验室的军备竞赛：
1. **扩展定律的确立**：Google 初期训练了一个庞大的密集模型，但事后证明该模型处于严重的训练不足（Under-trained）状态；与此同时，DeepMind 在 Chinchilla 论文中提出了计算最优扩展定律，修正了参数规模与训练数据量之间的最优平衡点。
2. **早期草根探索与挫折**：为了打破前沿技术封锁，EleutherAI 成立并发布了早期开源数据集与模型；Meta 尝试复刻推出了约 1750 亿参数的 OPT-175B，但由于训练过程中遭遇了大量硬件故障与训练不稳定性，模型表现并不理想；BigScience 项目则集合全球算力推出了 BLOOM 模型。
3. **开源生态的成熟**：近三年来，以 Meta 的 Llama 系列（Llama 1、2、3）为代表，开源模型生态发生了质的跃迁。随后 Mistral，以及以 DeepSeek、Qwen（阿里通义）、字节跳动和腾讯等为代表的模型集群全面崛起。这些开放权重模型在主流基准上的表现正在迅速逼近顶级闭源模型。
4. **全开放路线的探索**：除仅开放权重的做法外，AI2、Nvidia 以及开源研究项目 Marron 等进一步推进了“全要素开源”，将模型权重、训练数据、清洗管线、训练代码与技术报告完全公开，使学术界能够真正透视前沿系统的工程实现细节。

#### 模型交互形态演化与底层不变性

在过去十年中，语言模型的角色定位经历了四次形态跃迁：

```text
+-----------------------------------------------------------------------+
| 语言模型交互范式的演化轨迹                                            |
|                                                                       |
| 1. 微调对象 (Fine-tuning Era)     -> 2018: 抽取特征，下游任务微调     |
|         |                                                             |
|         v                                                             |
| 2. 提示对象 (Prompting Era)       -> 2020: 给定前缀指令，续写补全     |
|         |                                                             |
|         v                                                             |
| 3. 对话助手 (Chatbot Era)         -> 2022: 多轮人机对齐交互 (ChatGPT) |
|         |                                                             |
|         v                                                             |
| 4. 智能体执行者 (Agent Era)       -> 当前: 规划、工具调用、长轨迹环境编码|
+-----------------------------------------------------------------------+
```

*图：从下游微调基座到长程自主智能体的角色演进。*

尽管上层能力要求已经从简单的短句补全演进到执行长达数千行的自主编码与系统调用任务，但**支撑整个技术体系的底层根基并未发生根本性动摇**：
- 底层硬件基础设施依然由 GPU、张量加速核心与高速互联网络主导；
- 优化算法依然以随机梯度下降（SGD）及其自适应变体为核心；
- 主干架构依然建立在自注意力机制与 Transformer 的变体之上。

理解了这些底层不变性，我们就能以不变应万变，自如应对未来的技术演进。

#### 语言模型基础与训练稳定性

第一阶段的核心是在本地从零编写出所有的核心组件，包括分词器、模型架构、损失函数与优化算法。
- **分词实现**：实现字节级 BPE（Byte-Pair Encoding）分词器，建立词表并实现编码与解码循环；
- **现代架构演进**：放弃早期的传统 Transformer 设计，融入近年来沉淀的关键工程改进：采用旋转位置编码（RoPE, Rotary Position Embedding）、均方根归一化（RMSNorm, Root Mean Square Normalization）、SwiGLU 门控激活函数，以及在注意力层与 MLP 层之间设置更稳定的数值防溢出连接；
- **长上下文与高效注意力**：标准自注意力机制的计算开销与显存占用随序列长度 $n$ 呈平方级增长（$\mathcal{O}(n^2)$）。为了应对长上下文挑战，除引入轻量化注意力设计外，现代模型正逐步融合状态空间模型（SSM, State-Space Models）与门控线性注意力架构（如 Mamba 和 Gated DeltaNet），通过与标准自注意力的混合设计兼顾捕获能力与线性计算复杂度；
- **混合专家网络（MoE）**：以稀疏激活的 MoE 替代传统稠密 MLP 层，在不显著增加单 Token 计算开销的前提下成倍扩充模型总参数量；
- **训练超参数与稳定性工程**：在优化器层面，从传统的 Adam 逐步向近期展现出优异收敛特性的 Muon 优化器演进。仔细设置学习率退火策略、权重初始化、批量大小（Batch Size）以及数值稳定性边界。

> **提示**：训练大语言模型本质上是一场对抗数值崩溃的博弈。如果参数范数与梯度范数失控，就会发生毁灭性的损失爆炸（Loss Explosion）。工程实现的核心是在**模型表达能力**、**数值稳定性**与**硬件吞吐效率**三者之间寻找黄金平衡点。

#### 硬件系统架构与算子内核优化

第二阶段全面下沉到底层硬件与系统层面，目标是榨干 GPU 的每一丝算力。

##### 计算复杂度核算（FLOPs Accounting）
在训练大型模型时，需要时刻清楚每一个浮点运算发生在哪里。一个贯穿全流程的经典核算法则是：
对于包含 $N$ 个参数的稠密 Transformer 模型，在包含 $D$ 个 Token 的数据集上完成一次自监督预训练，总计消耗的浮点运算次数约为：

$$\text{FLOPs} \approx 6 \times N \times D$$

该公式的物理推导在于：每个 Token 在前向传播时每个参数约参与 2 次浮点运算（一次乘法、一次加法），即 $2ND$；而在反向传播计算梯度时，开销约为前向传播的两倍，即 $4ND$。两者相加即为 $6ND$。

##### 内存墙与屋顶线分析（Roofline Analysis）
计算核心与高带宽内存（HBM, High Bandwidth Memory）物理分离，所有张量必须从 HBM 经由总线搬运至芯片内部 SRAM/寄存器才能被运算核心处理，计算完成后再写回 HBM。

以 Blackwell 架构的 NVIDIA DGX B200 为例：
- BF16 精度下的理论峰值算力高达 $2.25\text{ PFLOPS}$；
- 内存带宽为 $8\text{ TB/s}$。

```text
+-----------------------------------------------------------------------+
| 传统无融合算子执行流 (高开销数据搬运)                                 |
|                                                                       |
| HBM 内存                GPU 运算核心                                  |
| +--------+  1. 读取 A   +----------------+                            |
| | 张量 A | -----------> | 执行计算 A     |                            |
| +--------+              +----------------+                            |
| +--------+  2. 写回中间值      |                                      |
| | 中间值 | <-------------------+                                      |
| +--------+                                                            |
| +--------+  3. 读取中间值+B                                           |
| | 张量 B | -----------> +----------------+                            |
| +--------+              | 执行计算 B     |                            |
|                         +----------------+                            |
| +--------+  4. 写回结果        |                                      |
| | 最终值 | <-------------------+                                      |
| +--------+                                                            |
|                                                                       |
| 算子融合执行流 (Operator Fusion, 单次读写)                            |
|                                                                       |
| HBM 内存                GPU 运算核心 (SRAM / Registers)               |
| +--------+  1. 一次性读取 +------------------------------------+      |
| | 输入张量| -----------> | 寄存器常驻: 连续完成计算 A 与计算 B  |      |
| +--------+              +------------------------------------+      |
| +--------+  2. 一次性写回      |                                      |
| | 最终结果| <-------------------+                                     |
| +--------+                                                            |
+-----------------------------------------------------------------------+
```

*图：高带宽内存（HBM）与计算核心之间的数据搬运瓶颈及算子融合消除数据搬运的原理对比。*

通过屋顶线模型（Roofline Model）分析可以清晰看出，许多常见的逐元素操作（如 LayerNorm、GELU/SiLU 激活）并非受限于算力瓶颈（Compute-bound），而是严重受限于内存带宽瓶颈（Memory-bound）。

##### 算子融合与内核编程
为了消除不必要的内存往返传输，我们使用 Triton 语言编写针对特定操作的高性能 GPU 自定义内核（Kernel）。其核心手段包括：
- **算子融合（Operator Fusion）**：将多个连续的计算步骤（如 Bias Add + Activation + Dropout）合并进同一个内核，数据只需从 HBM 加载一次至片上缓存，运算完毕后一次性写回；
- **分块计算（Tiling）**：将超大矩阵切分成适配 SRAM 容量的小块进行流水线搬运与计算，FlashAttention 便是这一思想在注意力机制上的终极体现。

#### 分布式训练通信与推理加速

##### 大规模分布式并行切分
当模型参数和上下文超出一张显卡的承载极限时，必须将计算在数千张 GPU 间进行分片（Sharding）。需要分片的对象包括模型参数、激活值、梯度以及优化器状态：
- **经典集合通信（Collective Operations）**：深入理解 `Gather`、`Reduce`、`All-Reduce` 等底层的通信拓扑与带宽代价；
- **多维切分策略**：权衡数据并行（Data Parallelism）、张量模型并行（Tensor Parallelism）、流水线并行（Pipeline Parallelism）、序列并行（Sequence Parallelism）以及专家并行（Expert Parallelism）在不同网络拓扑下的延迟与显存开销。

##### 推理双阶段与加速技术
在生产环境中，推理不仅用于用户交互，还大量消耗在强化学习采样生成（Rollouts）、合成数据生成与自我验证上。推理包含两个计算特征截然不同的阶段：
1. **预填充阶段（Prefill）**：输入完整 Prompt，一次性完成前向传播计算并构建键值缓存（KV Cache），计算模式高度密集（Compute-bound）；
2. **解码阶段（Decoding）**：自回归逐 Token 生成，每次前向仅生成一个 Token，但需读取整个序列的庞大 KV Cache，呈现极其严重的内存带宽受限（Memory-bound）。

优化推理的手段包括：
- **模型压缩**：权重量化（Quantization）、剪枝与知识蒸馏；
- **投机解码（Speculative Decoding）**：利用参数量极小的辅助小模型快速生成多个候选 Token，随后由完整主模型进行单次并行前向验证，若全部猜中则一次性接收整个 Token 块，成倍提升解码吞吐；
- **动态批处理（Dynamic Batching）**：针对并发请求到达时间随机的特点，在服务层将不同长度的请求动态打包进连续批次中处理。

#### 扩展配方制定与超参数迁移

面对极其昂贵的训练预算（例如 $10^{24}$ FLOPs，等价于数千万美元成本），工程师没有任何试错机会，不可能在目标规模上盲目进行网格搜索。

> **定义**：**扩展配方（Scaling Recipe）**是一个数学映射系统，它接收给定的 FLOPs 预算输入，输出一套确定性的超参数配置组合（包含隐藏维度、层数、头数、学习率、批量大小及衰减曲线等）。

扩展配方必须具备可向外预测的外推能力（Extrapolation）。为此，必须引入**超参数迁移（Hyperparameter Transfer）**参数化设计：保证在小规模下表现优异的超参数，在向大规模扩展时要么保持恒定，要么是关于算力规模的严格单调且可预测的函数。在规模化设计中，**可预测性（Predictability）的权重绝不亚于局部最优性（Optimality）**。

```text
+-----------------------------------------------------------------------+
| 计算最优扩展法则 (Chinchilla Scaling Law) 核心边界                    |
|                                                                       |
| 经验法则是：训练数据 Token 总量约为模型参数量的 20 倍                  |
|                                                                       |
|                 模型参数规模 (N)  x  20  =  训练 Token 规模 (D)       |
|                                                                       |
| 典型示例：                                                            |
| +---------------------+-----------------------+---------------------+ |
| | 模型参数量 (N)      | 计算最优数据量 (D)    | 计算预算 (FLOPs)    | |
| +---------------------+-----------------------+---------------------+ |
| | 70 亿 (7B)          | 约 1.4 万亿 (1.4T)    | ~ 6 x 7B x 1.4T     | |
| | 700 亿 (70B)        | 约 14 万亿 (14T)      | ~ 6 x 70B x 14T     | |
| +---------------------+-----------------------+---------------------+ |
|                                                                       |
| 注：现代推理优先场景通常会打破该最优配比，选择“过训练”（Over-training） |
| 即采用 10x 甚至 20x 以上の超额 Token 训练小模型，以压低部署推理成本。 |
+-----------------------------------------------------------------------+
```

*图：计算最优法则在预训练中的基准比例及面向推理优化的工程异化。*

在计算最优的预训练中，Kaplan 与 Chinchilla 扩展定律给出了基准：参数量为 $N$ 的模型，计算最优的训练 Token 数约为 $20 \times N$（例如 7B 模型应搭配约 1.4T Token 训练）。但在当前工业界，由于需要摊薄极其高昂的线上推理部署成本，业界普遍倾向于采用“过训练”（Over-training）策略——在较小的参数骨架上喂入远超计算最优比例的数倍 Token 进行极限压缩。

#### 数据清洗处理管线与评估体系

数据质量从根本上决定了模型能力的上限。

##### 评估指标的生态效度与内在平滑性
构建数据流水线前必须先确定评估准则：
- **内部评估指标（困惑度，Perplexity）**：在保留测试集上计算的困惑度具有极高的统计平滑性，能够在模型规模扩张过程中展现出极其稳健的单调下降规律，是研发过程中最可靠的“测向仪”，且不会轻易出现为刷高分数而导致的过拟合伪优化；
- **外部任务基准（External Benchmarks）**：用于向最终用户或客户证明综合应用能力，必须高度重视生态效度（Ecological Validity），并严防互联网评估集遭训练语料污染（Data Contamination）。

##### 端到端数据处理流水线
原始互联网语料本质上并非结构化文本，而是混杂着各类标记的复杂对象。数据工程包含严密的清洗流水线：

```text
+-----------------------------------------------------------------------+
| 数据清洗处理管线架构                                                  |
|                                                                       |
| [ 原始输入数据源 ] -> 网页抓取 (Common Crawl)、电子书、论文、代码库   |
|         |                                                             |
|         v                                                             |
| [ 文本抽取转换 ]   -> 解析 HTML、提取 PDF、剥离目录结构转纯文本       |
|         |                                                             |
|         v                                                             |
| [ 启发/统计过滤 ] -> 规则过滤低质广告、毒性文本与垃圾数据             |
|         |                                                             |
|         v                                                             |
| [ 全局数据去重 ]   -> MinHash / LSH 算法消除长文本跨文档高频复读      |
|         |                                                             |
|         v                                                             |
| [ 语料分期配比 ]   -> 基础预训练 -> 中期长文退火 -> 智能体合成后训练  |
+-----------------------------------------------------------------------+
```

*图：从多源异构原始语料到高质量训练集的分级过滤与去重管线。*

1. **格式转换**：从 HTML、PDF 以及树状代码仓库中抽取纯净文本，剔除网页模版代码与乱码；
2. **启发式过滤**：设计统计规则（如符号密度、行长分布、停用词比例）剔除低质网页与机器生成垃圾文本；
3. **精准去重（Deduplication）**：利用 MinHash 等局部敏感哈希（LSH）算法在海量数据中消除重复文档。在有限计算预算下，把梯度更新浪费在重复文本上不仅会损害泛化能力，更会白白消耗极其昂贵的有效算力；
4. **语料分期演化**：基础预训练完成后，在预训练尾期引入包含大代码库、长篇学术文献的高质量数据进行**中期训练（Mid-training）**，将上下文窗口平稳拉伸；最后注入包含工具调用与智能体轨迹数据的**后训练（Post-training）**语料。

#### 强化学习弱监督与系统解耦

预训练赋予了模型强大的通用表征能力，但要使模型表现出可靠的行为准则，必须依赖对齐技术。

> **结论**：采用弱监督（Weak Supervision）的核心逻辑在于：**在许多复杂任务中，验证回答的正确性与优劣，要远比直接人工编写出完美的标准答案容易得多**。

对齐技术的实现路径包括：
- **强化学习框架**：借助人类反馈、环境执行验证器（如代码沙箱运行结果）或更高级的语言模型裁判（LLM-as-a-Judge）对生成结果进行即时打分，运用近端策略优化（PPO, Proximal Policy Optimization）或组相对策略优化（GRPO, Group Relative Policy Optimization）动态调整模型策略分布；
- **直接偏好优化（DPO）**：在仅具备静态偏好数据对时，绕过独立的奖励模型建模，直接在闭式解下微调模型权重。

大规模强化学习面临严重的系统工程挑战：在大规模分布式运行并追求吞吐量最大化时，系统必须拆分为**执行 Rollouts 生成的推理服务器集群**与**执行梯度反传更新的训练服务器集群**。当环境交互耗时出现波动、部分工作节点滞后时，系统极易滑向严重的离策略（Off-policy）漂移。如何在保持近同策略（Near On-policy）算法稳定性与最大化硬件吞吐量之间求得平衡，是目前极其前沿的系统挑战。

### 文本表示与分词器设计缺陷

正式进入分词器（Tokenizer）的核心算法实现前，我们首先需要从数学与工程的角度，剖析为什么需要分词，以及为什么分词器既不可或缺却又充满妥协。

#### 字符与标记之间的双向转换

对于人类而言，文本是具有连续语义的自然语言，在计算机中以 Unicode 编码的字符串形式存在；但对于大语言模型而言，其数学本质是在离散的离散标记（Token）整数索引序列上构建的条件自回归概率分布：

$$P(x_1, x_2, \dots, x_T) = \prod_{t=1}^T P(x_t \mid x_{<t})$$

分词器的核心职责，就是在原始 Unicode 字符串与模型操作的整数索引之间建立可逆转换桥梁：

```text
+-----------------------------------------------------------------------+
| 分词器双向往返映射 (Round-trip Integrity)                             |
|                                                                       |
|                encode(text)                                           |
|  Unicode 字符串 ------------> 整数索引序列 [id_1, id_2, ..., id_k]    |
|       ^                                    |                          |
|       |                                    |                          |
|       +------------------------------------+                          |
|                decode(tokens)                                         |
+-----------------------------------------------------------------------+
```

*图：分词器编码与解码无损往返转换流程示意。*

> **注意**：分词器必须保证**无损往返性（Round-trip Losslessness）**，即对任意合法输入字符串 $S$，必须恒满足：
>
> $$\text{decode}(\text{encode}(S)) = S$$
>
> 如果一个分词器在经历编码再解码后改变了原始文本（哪怕只是改变了一个空格或不可见字符），该分词器便存在不可接受的致命缺陷。

然而，现代分词器表现出许多令人生疑且反直觉的边缘特性：
- **前导空格敏感性**：在绝大多数分词器中，`"Hello"` 与带前导空格的 `" Hello"` 会被映射为两个数值截然不同、在词表中完全独立的 Token ID。对于模型而言，这两个 Token 在进入嵌入层（Embedding Layer）之初彼此毫无关联；
- **数字切分的不稳定性**：部分分词器会将一个长数字每若干位聚合成一个 Token，有时按固定步长切分，有时则根据语料统计频次呈现无规律碎裂，这直接对大语言模型的四则运算与算术推理能力构成了人为的严重干扰。

#### 压缩比定义与词表稀疏性权衡

引入分词的一个最直接动力在于**大幅削减输入序列长度，以此缓解自注意力计算的二次方开销**。

> **定义**：**压缩比（Compression Ratio）**衡量了分词器将连续字节流抽象聚合的能力，其计算公式为：
>
> $$\text{Compression Ratio} = \frac{\text{输入文本的总字节数 (Bytes)}}{\text{分词后生成的标记总数 (Tokens)}}$$

假设一段文本转换成 UTF-8 编码占用 20 个字节，经由分词器处理后映射为 8 个 Token，则其压缩比为 $\frac{20}{8} = 2.5\text{ Bytes/Token}$。压缩比数值越大，意味着同一段语义所需的 Token 数量越少，模型在长文本注意力运算中的开销就越低。

然而，压缩比不能通过无限扩充词表大小来单向换取。这里存在严格的工程权衡：
1. **词表扩大的收益**：更大的词表（现代多语言大模型通常采用 10 万到 20 万即 100k~200k 词表大小）能显著提高对非英语语种以及专业代码的压缩比；
2. **参数与稀疏性代价**：嵌入层矩阵与输出解嵌入层（Unembedding Layer）的尺寸为 $V \times d_{\text{model}}$。词表 $V$ 过大会直接占用数以亿计的模型参数；更严重的是，长尾罕见词在训练集中的曝光频次过低，导致这部分词向量在梯度更新中遭遇严重的**稀疏性问题（Sparsity）**，难以得到充分训练。

#### 传统分词方案的边界与局限

在现代方法成熟之前，自然语言处理领域尝试过三种主流的分词方案，但它们各自都在极端情况下暴露出不可调和的缺陷。

| 分词方案 | 词表规模 ($|V|$) | 压缩比表现 | 核心缺陷与工程瓶颈 |
| :--- | :--- | :--- | :--- |
| **字符级分词 (Character-level)** | 约 15 万 (Unicode 码点) | 较差 (单字符多 Token) | 词表中绝大部分 Unicode 字符极度罕见，词表利用率极低；多字节字符映射碎片化。 |
| **纯字节级分词 (Pure Byte-level)** | 恒定 256 (单字节 $0\sim 255$) | 最差 ($\text{Ratio} \equiv 1.0$) | 序列长度被拉伸至极大，直接引爆自注意力机制 $\mathcal{O}(n^2)$ 的显存与计算灾难。 |
| **单词级分词 (Word-level)** | 无界/极度庞大 ($>10^6$) | 优秀 (单词单 Token) | 遭遇未登录词（OOV）时必须引入特殊标记 `[UNK]`，破坏无损往返性，极大扰乱困惑度评估。 |

在字符级分词方案中，通过 Python 的 `ord()` 函数获取 Unicode 码点。然而 Unicode 拥有超过 15 万个字符，海量字符在真实场景中极少出现；而在纯字节方案中，词表虽然被极度压缩在 $0\sim 255$ 的固定空间内，但文本序列被极度拉长，使得 Transformer 处理万级上下文的成本高不可攀；传统单词级切分则因语言创造新词的无界性，在遇到未登录词时被迫抛出 `[UNK]`，彻底摧毁了从索引还原原始文本的可能。

### 字节对编码算法原理与工程实现

为了彻底破除上述三种方案的固有困境，字节对编码（BPE, Byte-Pair Encoding）成为了当前大模型分词机制的绝对通用标准。

BPE 最初由 Philip Gage 于 1994 年提出作为一种通用的无损数据压缩算法。Sennrich 等人于 2015 年首次将其引入神经机器翻译任务以处理开放词汇问题，随后 OpenAI 在 GPT-2 中正式确立了在字节流上运行 BPE 的标准范式。

> **结论**：BPE 是一种数据驱动的自适应贪心算法。其核心优势在于：**以 256 个基础字节作为词表保底，天生绝不存在未登录词（No UNK）；同时通过高频子串合并规则，对常见文本实现了极高的压缩比**。

#### 词表构建与相邻标记贪心合并

BPE 词表的训练构建过程是一个纯粹基于统计频次的自底向上贪心迭代过程：

```text
+-----------------------------------------------------------------------+
| BPE 词表训练与迭代合并流水线                                          |
|                                                                       |
| 1. 初始化基础词表:                                                    |
|    Vocab = {0: b'\x00', 1: b'\x01', ..., 255: b'\xff'} (大小 256)    |
|                                                                       |
| 2. 将输入语料编码为初始字节流:                                        |
|    Text -> [byte_0, byte_1, byte_2, ...]                              |
|                                                                       |
| 3. 循环迭代直至达到目标词表大小 |V|:                                  |
|    a. 全局扫描当前序列，统计所有相邻标记对 (Bigram) 出现的绝对频次    |
|    b. 选取共现频次最高的标记对 (Pair_A, Pair_B)                       |
|    c. 分配新 Token ID = 256 + 当前合并轮数                            |
|    d. 记录合并规则: (Pair_A, Pair_B) -> New_ID                        |
|    e. 全局遍历序列，将所有连续的 (Pair_A, Pair_B) 替换为 New_ID      |
+-----------------------------------------------------------------------+
```

*图：BPE 词表从 256 个底层字节逐步贪心合并至预设容量的训练循环。*

##### 演进实例演算
假设我们的训练语料中频繁出现短语 `"the"`，文本被转换为 UTF-8 字节序列：
- 字符 `'t'` 对应 ASCII 码值 `116`；
- 字符 `'h'` 对应 ASCII 码值 `104`；
- 字符 `'e'` 对应 ASCII 码值 `101`。

在初始状态下，语料中的片段呈现为连续的单字节 Token：`[..., 116, 104, 101, ...]`。

```text
+-----------------------------------------------------------------------+
| BPE 合并实例演算流程                                                  |
|                                                                       |
| [ 初始状态: 单字节序列 ]                                              |
| 序列片段:     ... [ 116 ] [ 104 ] [ 101 ] ...                        |
| 语义映射:     ...    t       h       e    ...                         |
|                                                                       |
| [ 第一轮合并: (116, 104) 频次最高 -> 生成 Token 256 ]                 |
| 新建规则:     (116, 104) -> 256 (代表 b'th')                          |
| 替换后序列:   ...   [   256   ]   [ 101 ] ...                         |
| 语义映射:     ...       th           e    ...                         |
|                                                                       |
| [ 第二轮合并: (256, 101) 频次最高 -> 生成 Token 257 ]                 |
| 新建规则:     (256, 101) -> 257 (代表 b'the')                         |
| 替换后序列:   ...        [     257     ]  ...                         |
| 语义映射:     ...              the        ...                         |
+-----------------------------------------------------------------------+
```

*图：高频字符对 `'t'` 和 `'h'` 合并为 `'th'`，再与 `'e'` 合并为完整单词 `'the'` 的状态转移图。*

1. **第一轮统计与合并**：统计发现 `(116, 104)` 在语料中出现频次最高。算法开辟新 Token ID `256` 代表字节组合 `b"th"`，记录规则 `(116, 104) -> 256`。全语料扫描，将所有相邻的 `116, 104` 替换为 `256`。序列长度缩短；
2. **第二轮统计与合并**：继续统计，发现新生成的 Token `256` 与其后续的 `101`（即字符 `'e'`）构成的 Bigram `(256, 101)` 频次攀升至第一。算法开辟新 Token ID `257` 代表字节组合 `b"the"`，记录规则 `(256, 101) -> 257`。全语料再次替换；
3. 伴随迭代深入，常见前缀、词根以至整个高频词均被收录进词表，输入序列的长度呈阶梯式下降，压缩比迅速提升。

#### 编码推理流程与算法复杂度瓶颈

在完成词表与合并规则库的训练后，当系统接收一段全新的推理文本时，分词器执行的是一个自洽的重写流水线：

```text
新输入字符串 S
  -> 转换为 UTF-8 基础字节 Token 列表 (值均在 0~255)
  -> 按照训练阶段记录的合并规则优先级（按生成先后或频次降序）
  -> 贪心地对序列中匹配的相邻对进行迭代替换
  -> 最终收敛输出 Token ID 序列
```

> **易错点**：**朴素 BPE 编码实现的性能灾难**。如果在编写推理 `encode()` 函数时，机械地遍历全部合并规则（规则总数等于 $|V| - 256$，通常达数万甚至十几万条），对每一条规则在整个文档中做一次全局搜索与替换，算法的时间复杂度将高达 $\mathcal{O}(|V| \times L)$（其中 $L$ 为文本序列长度）。对于长文档，这种朴素实现在生产环境下完全不可接受。

为了实现高效的编码算法，必须重构搜索逻辑：
- 在当前文本序列上维护相邻 Token 对的有向图或双向链表；
- 利用优先队列（Min-Heap）建立局部倒排索引，仅针对当前文本中**真实存在且在规则库中排位靠前**的候选合并对进行局部常数级替换；
- 避免全量循环，将复杂度大幅压缩至接近线性时间。

#### 块级预分词与系统级加速设计

在现代工业级分词器（如 GPT-4 等前沿模型采用的实现）中，纯粹的全局 BPE 会引发不符合人类常识的跨词合并（例如将标点符号与后续单词前缀合为一个 Token，导致语义解析破碎）。

为此，必须在应用 BPE 之前增加一层**块级预分词（Pre-tokenization / Regex Chunking）**机制：

```text
+-----------------------------------------------------------------------+
| 块级预分词与并行 BPE 处理管线                                         |
|                                                                       |
| 原始连续输入文本: "Hello world! How are you?"                         |
|         |                                                             |
|         v 正则表达式分块 (Regex Splitting)                            |
| 分割为独立文本块:                                                     |
| [ "Hello" ]  [ " world" ]  [ "!" ]  [ " How" ]  [ " are" ]  [ " you?" ]|
|         |           |        |           |           |           |    |
|         +-----------+--------+-----------+-----------+-----------+    |
|         |                                                             |
|         v 多线程并发分发                                              |
| 并行独立执行 BPE 编码 (块与块之间严格隔离，不可跨边界合并)            |
|         |                                                             |
|         v                                                             |
| 拼接所有子块的 Token ID 列表，产出全局最终序列                        |
+-----------------------------------------------------------------------+
```

*图：基于正则表达式的块级预分词与多线程并行 BPE 加速流程。*

1. **语义边界隔离**：利用精心设计的正则表达式，预先将完整文本切分成包含标点、单词前导空格、连续数字的独立文本块。BPE 合并规则严格限定在各个切分块内部生效，严禁发生跨越单词或标点边界的非自然合并；
2. **多核并行加速**：将全局文本切散为海量独立子块后，分词任务天然退化为一个令人愉悦的并行问题（Embarrassingly Parallel Problem）。我们可以将不同文本块分发给多线程或多进程并发处理，彻底破除单线程锁的束缚；
3. **系统级重构（Python 到 Rust）**：由于分词器涉及高密度的循环迭代、指针跳转与字符串切片操作，动态类型解释型语言（如 Python）在这类微观密集型计算上往往成为严重的端到端瓶颈。在真实工业界落地时，通常会完全使用系统级语言（如 Rust）重写底层内核，再通过 FFI 绑定暴露给 Python 训练管线调用。

#### 无分词架构的必要演进约束

尽管我们花费了大量精力设计与优化 BPE 分词器，但学术界与工业界的终极理想，始终是构建出一种纯粹的**端到端全无分词（Tokenizer-free / Byte-level）模型**，直接以二进制字节流作为输入。近年来诸如 MegaByte 等工作展示了直接建模字节的前景，但迄今为止，这类端到端方案依然未能在前沿规模上全面替代分词器。

任何试图在未来彻底取代分词器的下一代架构，都必须在本质上满足以下两大硬性设计约束：

```text
+-----------------------------------------------------------------------+
| 取代分词器方案必须具备的两大核心属性                                  |
|                                                                       |
| 1. 层次化序列抽象 (Hierarchical Sequence Abstraction)                 |
|    - 单个原始字节 (如文本字节、视频像素、DNA 碱基) 的局部信噪比极低   |
|    - 必须具备某种架构机制，将低级字节聚合为高级语义单元以供计算      |
|                                                                       |
| 2. 自适应计算分配 (Adaptive Computation)                              |
|    - 输入序列不同区间的复杂度天差地别 (高频冗余 vs 罕见复杂)          |
|    - 聚合后的块大小必须是动态可变的，保证算力向信息密集区域倾斜      |
+-----------------------------------------------------------------------+
```

*图：未来端到端字节级模型取代分词器必须攻克的核心架构约束。*

- **层次化序列抽象（Hierarchical Sequence Abstraction）**：无论是文本、高清视频还是 DNA 测序数据，单个原始字节或基础单元的信噪比极低。Transformer 无法在缺乏抽象的低阶细粒度网格上直接构建宏观注意力依赖。系统必须具备自动将原始字节流提升至高阶语义表征的局部层次结构；
- **自适应计算（Adaptive Computation）**：自然界的信息并非匀质分布。简单、高频的冗余数据应当以极少的算力预算快速略过，而对于深奥、罕见且信息密集的语义断裂点，系统必须能够动态自适应地分配更多的计算资源与上下文容量。静态、等长切分的纯字节处理方式在信息论与计算经济学上均属于次优选择。

### 张量基础与数值精度体系

深度学习系统中的一切实体——模型参数、反向梯度、优化器动量状态、输入数据、中间激活值，底层无一例外都是张量（Tensor）。哪怕像 DeepSeek 这种复杂的前沿混合专家（MoE）模型，剖开底层代码，本质上也是由成百上千个具有特定形状、排布与精度的张量所构成的集合。

张量可以被视为标量、向量与矩阵在任意高维空间的广义推广。衡量张量首先要衡量它在物理介质中占用的内存字节数。

#### 单精度浮点数表示与内存占用

在科学计算早期，32 位单精度浮点数（Float32，FP32）是默认的通用基准。如果没有显式声明，PyTorch 创建的浮点张量默认类型就是 Float32。

一个 Float32 数值在内存中严格占用 32 位（即 4 字节），其底层位布局由三部分构成：

```text
+-----------------------------------------------------------------------+
| IEEE 754 Float32 (32-bit 单精度浮点数结构)                           |
|                                                                       |
|  1 位           8 位                            23 位                 |
| +----+------------------------+-------------------------------------+ |
| | S  |    Exponent (指数位)   |          Mantissa / Fraction        | |
| +----+------------------------+-------------------------------------+ |
|  符号        表示动态范围                  表示有效数字精度 / 分辨率   |
+-----------------------------------------------------------------------+
```

*图：标准 IEEE 754 Float32 内部比特位排布拓扑图。*

- **1 位符号位（Sign）**：指示数值的正负极性；
- **8 位指数位（Exponent）**：决定数值的尺度阶数，直接定义了数值能够表达的动态范围（Dynamic Range）；
- **23 位尾数位（Mantissa / Fraction）**：表征有效数字的小数部分，决定了数值的分辨率与测量精度。

若在 PyTorch 中构建一个形状为 $4 \times 8$ 的矩阵，其占用的基础存储空间计算如下：

$$\text{Memory} = \text{元素总数} \times \text{单元素字节数} = (4 \times 8) \times 4\ \text{Bytes} = 128\ \text{Bytes}$$

在早期大模型如 GPT-3 中，前馈神经网络（FFN）内部单层权重矩阵的规模就已经达到千兆字节（GB）级别。对于当下的千亿模型，若全量使用 Float32 存储与运算，显存容量与内存搬运带宽都将迅速崩溃。

#### 低精度演进与动态范围权衡

既然降低精度能够成倍压缩内存，同时在硬件层面让单条指令处理更多数据（理论吞吐提升），工业界的直觉往往是直接对折位宽——使用 16 位半精度浮点数（Float16，FP16）。

Float16 采用 1 位符号位、5 位指数位与 10 位尾数位。然而在大语言模型训练的早期实践中，FP16 带来了灾难性的数值不稳定性：
- 5 位指数位所能表示的动态范围极为狭窄；
- 当梯度值衰减至小于 $10^{-5}$ 量级时，在 FP16 体系下会直接遭遇阶下溢（Underflow），数值瞬间截断为绝对零；
- 而一旦层数加深或注意力未缩放，中间激活值又极易发生阶上溢（Overflow），导致产生不可逆的 `NaN`（Not a Number），使整批次训练彻底报废。

为了拯救训练稳定性，Google 在 2018 年推出了专为深度学习设计的 **Bfloat16（Brain Floating Point 16）**。

```text
+-----------------------------------------------------------------------+
| FP32、FP16 与 BF16 比特排布对比                                       |
|                                                                       |
| 格式             符号位        指数位 (范围)        尾数位 (精度)     |
| Float32 (32位)   [1]          [8 位]               [23 位]            |
| Float16 (16位)   [1]          [5 位] (易下溢)      [10 位]            |
| Bfloat16 (16位)  [1]          [8 位] (等同FP32)    [7 位]             |
+-----------------------------------------------------------------------+
```

*图：FP32、FP16 与 BF16 的比特位分配与设计权衡对比。*

Bfloat16 的设计哲学极具启发性：它放弃在位数上妥协，总长度同样保持为 16 位（2 字节），但断然削减了尾数位（从 10 位砍到 7 位），将节省出来的 3 位全部补给指数位，保持与 Float32 完全一致的 8 位指数宽度。

> **结论**：**动态范围远比分辨率重要**。大语言模型训练内部本身蕴含着巨大的随机噪声（Dropout、数据抖动、批次采样），神经网络对微观有效数字截断表现出极强的鲁棒性，但对动态范围越界造成的下溢归零和溢出 `NaN` 极其脆弱。BF16 在保留了与 FP32 相同动态范围的同时，将内存需求硬生生砍掉了一半，成为现代大模型预训练的标准基准。

#### 混合精度训练机制

即便使用 BF16，某些数值敏感的操作（如 Softmax 内部的指数计算、层归一化中的方差统计以及优化器内部的二阶动量累加）若直接在 16 位下运算，仍然可能累积灾难性的截断误差。

当今工业界的标准做法是**混合精度训练（Mixed Precision Training）**：
- **权重参数、输入激活值、反向传播梯度**：统一使用 BF16 存储与执行矩阵乘法（GEMM）；
- **优化器内部状态、敏感标量统计、损失缩放**：强制保持在 Float32 高精度空间。

在 PyTorch 中，这套管线被封装在自动混合精度模块（AMP, `torch.cuda.amp`）中。它在底层构建了上下文调度器，在保证安全的操作上自动将张量降采样至 BF16，并在高危数值计算中自动提升回 FP32，开发者几乎无需手动进行类型转换。

#### 极低精度格式与量化边界

硬件厂商正将精度推向更极限的低位宽：

1. **FP8（8 位浮点格式）**：目前已在 NVIDIA Hopper（H100）及 Ada Lovelace 架构中完全标准化。FP8 包含两种子格式：
   - **E4M3**（1 符号 + 4 指数 + 3 尾数）：精度更高，常用于前向传播与激活值；
   - **E5M2**（1 符号 + 5 指数 + 2 尾数）：范围更广，常用于反向传播梯度。
   NVIDIA 的 Transformer Engine 软件栈能够动态在这两种格式间自动切换。
2. **NVFP4（4 位微缩放格式）**：每个元素仅占 4 位，在无缩放状态下只能表示从 -6 到 +6 极其有限的离散点。为了让其能够支撑深层模型训练，NVIDIA 采用了**分块缩放（Block-scaling）**技术：
   - 连续的张量子向量（例如每 16 或 32 个元素）被组织为一个 Block；
   - 每个 Block 绑定一个更高精度的共享缩放系数（Scaling Factor）；
   - 单个元素在其微观 4 位空间内变化，而宏观绝对尺度由共享系数放大或缩小，使得张量子集内部的相对比例精确锁定，整体覆盖超越 4 位的有效动态范围。NVIDIA 发布的 Nemotron-3-Super 已经成功展示了使用 FP4 预训练大模型的实证可行性。
3. **1-bit（极限二值化）**：将模型压缩至 1 位（0/1 符号）在推理后量化（Post-Training Quantization）中已有广泛研究，但**从零预训练一个高水准的 1-bit 大语言模型**在当下的学术界与工业界依然处于前沿探索阶段，尚未出现具备普遍工业可信度的成熟落地成果。

#### 张量设备放置与内存迁移

PyTorch 在初始化张量时，默认将其分配在宿主机的系统主存（CPU Memory）上。对于大模型训练而言，CPU 计算能力与总线带宽过于孱弱。在执行任何高性能张量计算前，必须显式地调用 `.to('cuda')` 或 `.cuda()` 将张量转移至 GPU 专有的高带宽显存（HBM）中。

> **易错点**：如果在训练循环中不小心遗留了一个处于 CPU 上的张量并参与 GPU 计算，PyTorch 将被迫在 PCIe 总线上进行隐式同步阻塞与数据拷贝，使得整个 GPU 流水线陷入停顿（Pipeline Stall），瞬间拖垮训练吞吐量。

### 声明式多维张量操作体系

在深入硬件算力核算前，我们需要解决一个长期困扰深度学习代码可读性与正确性的系统工程难题：多维张量操作的抽象泄漏。

#### 原生操作缺陷与维度命名抽象

回顾传统的 PyTorch 原生张量代码，开发者常常写出如下形式的算子组合：

```python
# 传统原生操作：充满负数索引与隐式广播，可读性极差
x = x.transpose(-2, -1)
out = torch.bmm(x, y.unsqueeze(1)).squeeze(1)
```

这类代码的缺陷在于：
- **位置依赖**：维度的语义完全绑定在数字索引上。一旦模型架构调整导致张量增加了一个批次维度（如从 `[B, S, D]` 变成 `[B, H, S, d]`），所有的负数索引（如 `-2`, `-1`）对应的物理含义将彻底错位；
- **调试黑盒**：他人阅读代码时，必须时刻在草稿纸上记录每个步骤的形状演变，极难一眼看出其数学本意。

为了彻底消除这一心智负担，我们需要采用**声明式张量操作库 `einops`**。其核心哲学是：**用强语义的变量名称，全面替代脆弱的位置数字索引**，这一思想源自爱因斯坦求和约定（Einstein Summation Convention）。

#### 通用张量乘法与隐式求和

`einsum` 可以被理解为一种附带绝对清晰索引管理的通用矩阵乘法与张量积算子。

以两个最基础的矩阵乘法为例，假设我们要将一个形状为 $3 \times 4$ 的矩阵 $X$ 与一个 $4 \times 3$ 的矩阵 $Y$ 相乘：

```python
from einops import einsum

# 显式声明：维度名称完全对应物理语义
# X: [seq_1, hidden], Y: [hidden, seq_2]
# 输出张量仅包含 seq_1 与 seq_2，未在输出中声明的 hidden 维度自动求和消除
z = einsum(x, y, 'seq_1 hidden, hidden seq_2 -> seq_1 seq_2')
```

其底层计算执行机制为：遍历所有在输入模式中出现的符号集合（`seq_1`、`hidden`、`seq_2`），根据输入张量取对应元素相乘，并在输出缺失的轴上执行归约累加：

$$Z[\text{seq\_1}, \text{seq\_2}] = \sum_{\text{hidden}} X[\text{seq\_1}, \text{hidden}] \times Y[\text{hidden}, \text{seq\_2}]$$

当引入多批次与转置时，`einsum` 的优势更加显著。假设我们需要执行一个附带批次维度的矩阵乘法，且要求在相乘时对第二项的最后两个轴进行转置：

```python
# 原生 PyTorch 做法：
# z = torch.bmm(x, y.transpose(-2, -1))

# einops 做法：通过命名直接表达数学意图，无需任何显式转置调用
z = einsum(x, y, 'b seq_1 hidden, b seq_2 hidden -> b seq_1 seq_2')
```

在这里，`y` 的输入描述符直接写为 `b seq_2 hidden`。因为右侧输出要求沿着 `hidden` 轴聚合，系统自动完成了转置与批次矩阵乘法的逻辑编排。

在构建通用大语言模型层时，输入张量可能附带不确定的前导批次维度（例如 `batch`、`beam_width`、`num_heads` 等）。我们无需逐一硬编码这些维度，只需使用省略号 `...` 进行通配声明：

```python
# 无论前面嵌套了多少个前导维度，始终只对最后两个物理轴执行收缩
z = einsum(x, y, '... seq_1 hidden, ... hidden seq_2 -> ... seq_1 seq_2')
```

#### 统计聚合操作与语义归约

在 PyTorch 原生代码中，开发者频繁调用 `torch.sum(x, dim=-1)`、`torch.mean(x, dim=1)` 等算子。`einops.reduce` 为这一过程提供了统一的声明式接口：

```python
from einops import reduce

# 将张量沿着 hidden 轴进行求和聚合（输出右侧未声明 hidden）
out_sum = reduce(x, 'b s hidden -> b s', 'sum')

# 支持在聚合槽位无缝替换统计原语：mean、max、min
out_mean = reduce(x, 'b s hidden -> b s', 'mean')
```

> **提示**：`reduce` 并没有创造新的底层汇编算子，它在底层被直接解析为对应维度的原生聚合内核。它属于纯粹的**工程语法糖**，但它消除了硬编码数字维度带来的重构脆弱性。

#### 维度拆分合并与内存排布

在实现 Transformer 的多头自注意力（Multi-Head Attention, MHA）时，我们必须频繁在“全局隐藏层维度”与“头数 $\times$ 单头维度”之间进行拆解与合并。

例如，输入张量形状为 `[3, 8]`（批次为 3，隐藏维度为 8）。如果每个注意力头占用 4 个特征通道，则隐藏维度必须被显式拆解为 2 个头。原生做法需要使用 `x.view(3, 2, 4)` 或 `reshape`，稍有不慎就会因维度错配导致隐蔽的语义崩溃。

使用 `einops.rearrange` 可以使用括号表达维度的合成与解耦：

```python
from einops import rearrange

# 拆分：明确声明隐藏维度 8 是由 h=2 个头和 d=4 个特征通道复合而成
# 形状变换：[b, 8] -> [b, 2, 4]
x_heads = rearrange(x, 'b (h d) -> b h d', h=2, d=4)

# 变换完成后，重新打包合并回单一特征维度：
# 形状变换：[b, 2, 4] -> [b, 8]
x_merged = rearrange(x_heads, 'b h d -> b (h d)')
```

在执行多维张量展平与重构时，物理内存存在**行优先（Row-major / C-contiguous）**与**列优先（Column-major / Fortran-contiguous）**的区别。`einops` 默认按照声明的逻辑顺序从左至右组织物理排布，保证重构前后的元素在底层内存中的连续性，避免非连续跨步（Strided Memory Access）导致的显存带宽惩罚。

### 算力计量与硬件性能指标

建立了对数据结构（张量）的控制后，我们必须对算法执行的“计算成本”建立严格的物理度量。

#### 运算次数与吞吐速率辨析

在文献与日常讨论中，`flops` 经常引起巨大的混淆。我们必须在符号体系上严格划清界限：

```text
+-----------------------------------------------------------------------+
| 算力计量符号硬性约定                                                  |
|                                                                       |
| 1. FLOPs (小写 s)  -> 浮点运算次数 (Floating-point Operations)        |
|    - 属性：纯数学标量，与硬件物理特性无关                             |
|    - 作用：度量特定模型执行前向/反向传播所必须完成的绝对计算工作总量  |
|    - 示例：GPT-3 训练总计算量约为 3.14e23 FLOPs                       |
|                                                                       |
| 2. FLOP/s (或 FLOPS，大写 S) -> 每秒浮点运算次数 (吞吐速率)           |
|    - 属性：硬件物理速率，衡量算力引擎的处理速度                       |
|    - 作用：度量加速器芯片在单位时间内能吞吐的最大浮点运算次数         |
|    - 示例：NVIDIA H100 SXM5 标称 BF16 稠密算力约为 989 TFLOP/s        |
+-----------------------------------------------------------------------+
```

#### 硬件标称算力与稀疏性修正

当你翻开 NVIDIA 官方关于 H100 Tensor Core GPU 的技术规格白皮书时，你会看到在 BF16 精度下一栏极其显眼的数字：**1979 TFLOP/s**（即 $1.979 \times 10^{15}\ \text{FLOP/s}$）。

如果你直接拿这个数字代入公式去计算训练时间，你的算力集群排期将直接面临严重的延期风险。

> **易错点**：**必须时刻警惕厂商宣传的稀疏性算力**。仔细阅读规格表最底部的脚注细则，你会发现 1979 TFLOP/s 是在开启了 **2:4 结构化稀疏性（Structured Sparsity）** 条件下测得的理论峰值。在前沿大语言模型的全参数预训练中，权重与激活值都是稠密矩阵（Dense Matrix），完全不满足结构化稀疏前提。
> 
> 因此，**对于稠密矩阵计算，标称算力必须无条件除以 2**：
> 
> $$\text{H100 BF16 稠密峰值算力} = \frac{1979\ \text{TFLOP/s}}{2} \approx 989\ \text{TFLOP/s}$$

为了建立硬件算力产出的物理直觉，我们可以计算一台标准的 8 卡 H100 单节点服务器，在全功率运行一周时间内所能供给的理论最大浮点运算次数：

$$\begin{aligned}
\text{单节点周理论算力} &= 8\ \text{GPUs} \times 989 \times 10^{12}\ \text{FLOP/s} \times (7 \times 24 \times 3600\ \text{Seconds}) \\
&\approx 8 \times (9.89 \times 10^{14}) \times (6.048 \times 10^5) \\
&\approx 4.78 \times 10^{21}\ \text{FLOPs} \approx 5 \times 10^{21}\ \text{FLOPs}
\end{aligned}$$

这一量级告诉你：仅凭单台 8 卡服务器连续跑上一整周，也只能支撑约 $5 \times 10^{21}$ FLOPs 的计算。这对于探索小模型的缩放定律足够，但对于需要 $10^{24}$ 乃至 $10^{25}$ FLOPs 的工业级大模型而言，只是沧海一粟。

#### 矩阵乘法浮点运算量推导

在现代神经网络中，超过 95% 以上的计算开销集中于矩阵乘法。我们需要严格推导一次线性映射的 FLOPs。

设输入数据批次为 $X \in \mathbb{R}^{B \times d}$（$B$ 个数据样本，输入维度为 $d$），线性层权重矩阵为 $W \in \mathbb{R}^{d \times k}$（输出维度为 $k$），前向输出为 $Y = XW \in \mathbb{R}^{B \times k}$：

```text
+-----------------------------------------------------------------------+
| 矩阵乘法算力推导结构                                                  |
|                                                                       |
|      X [B x d]          *        W [d x k]       =       Y [B x k]    |
| +-----------------+            +-----------+           +-----------+  |
| |                 |            |           |           |           |  |
| | d 维输入向量    |            | k 列权重  |           | B x k     |  |
| | (共 B 行)       |            | (每列 d 维|           | 个输出元素|  |
| +-----------------+            +-----------+           +-----------+  |
+-----------------------------------------------------------------------+
```

*图：标准线性矩阵乘法的维度映射拓扑。*

计算输出矩阵 $Y$ 中的每一个标量元素 $Y_{i, j}$，都需要执行输入第 $i$ 行与权重第 $j$ 列的内积：

$$Y_{i, j} = \sum_{m=1}^{d} X_{i, m} W_{m, j}$$

- 每次内积包含 $d$ 次乘法；
- 包含 $d - 1$ 次加法；
- 输出矩阵一共有 $B \times k$ 个独立元素。

因此，严格的浮点运算总次数为 $(B \times k) \times (d + d - 1) = B k (2d - 1)$。在大模型工程中，$d$ 通常为数千（如 4096、8192），$-1$ 可以忽略不计。

> **结论**：**通用矩阵乘法（GEMM）标准计算法则**：
> 
> $$\text{FLOPs}_{\text{GEMM}} = 2 \times B \times d \times k$$
> 
> 这一公式的物理本质非常直观：**总计算量等于数据点总数（Token 数 $B$）乘以参数总量（$d \times k$）的 2 倍**。每一次乘加复合操作（Fused Multiply-Add, FMA）贡献了 2 次浮点运算。

至于其他的逐元素操作（Element-wise Operations，如向量加法、LayerNorm、激活函数）：一个大小为 $N$ 的向量做逐元素操作仅消耗 $\mathcal{O}(N)$ 级别的浮点运算。在面对大矩阵 $\mathcal{O}(N^3)$ 的立方级算力扩张时，逐元素算子的算力占比微乎其微。硬件架构师之所以不把加法算子作为算力扩充的主要目标，正是因为加法与乘法在 Tensor Core 硬件电路上是高度融合的，而系统的真正颈椎并不在此。

#### 异步执行机制与基准测试屏障

在测量 GPU 上某段算子运行所需的时间时，初学者极易踩入一个严重的评测陷阱：

```python
import time
import torch

# 错误的基准测试写法：
start = time.time()
y = torch.matmul(x, w)
elapsed = time.time() - start  # 测出来的耗时往往极其微小（接近0）！
```

> **易错点**：**GPU 调用的非阻塞与异步性**。在 PyTorch 中，当你在 Python 端调用 `torch.matmul` 时，CPU 只是迅速向 GPU 的执行队列（CUDA Stream）中提交了一个计算指令指针，随后立即非阻塞地返回。如果此时直接读取 CPU 时钟，你测量的仅仅是指令下发的时间，而非 GPU 物理内核真实执行计算的时间。

必须在计时起点和终点前后，显式插入**同步屏障（Synchronization Barrier）**：

```python
# 正确的 GPU 基准测试标准写法：
torch.cuda.synchronize()  # 清空此前所有未决指令
start = time.time()

y = torch.matmul(x, w)

torch.cuda.synchronize()  # 阻塞 CPU 直至 GPU 彻底完成计算
elapsed = time.time() - start
```

在严格的测试基准中，通常还需要预先进行多次“热身运行”（Warm-up Runs）以使 GPU 频率锁定并初始化 CUDA 驱动缓存，随后对正式测试循环进行数十次迭代并计算统计均值。

#### 模型浮点运算利用率

有了确切的算法逻辑 FLOPs 和硬件真实耗时 $t$，我们就能计算系统在真实运行中所达到的有效吞吐速率：

$$\text{实际每秒浮点运算次数} = \frac{\text{算法总 FLOPs}}{t\ (\text{秒})}$$

进而定义系统工程中最核心的效率评估指标——**模型浮点运算利用率（Model FLOPs Utilization, MFU）**：

$$\text{MFU} = \frac{\text{实际有效每秒浮点运算次数}}{\text{硬件标称理论稠密峰值算力 (FLOP/s)}}$$

工业界基准表现如下：
- **现代大模型端到端训练**：MFU 若能达到 **0.5（即 50%）** 左右，就已经说明分布式系统、内核与显存流水线设计得相当优秀；
- **单卡孤立大矩阵乘法**：MFU 可以冲高至 **0.8（80%）** 甚至更高；
- **系统出现病态瓶颈**：如果你的 MFU 跌至 **0.1（10%）** 附近，则意味着硬件的昂贵计算核心绝大部分时间处于空闲挂起状态，必须立即对数据加载、通信带宽或内存调度进行排查。

### 算术强度与屋顶线模型

为什么即使在最顶级的集群上训练大模型，我们通常也只能拿到 50% 左右的 MFU？为什么昂贵的计算核心会被大面积闲置？

要回答这个问题，必须引入计算机体系结构中最核心的分析框架：**算术强度（Arithmetic Intensity）与屋顶线模型（Roofline Model）**。

#### 硬件架构抽象与临界强度

任何深度学习加速器芯片（如 GPU、TPU）的硬件拓扑都可以高度抽象为两个分离的核心实体：
1. **高带宽片外显存（High Bandwidth Memory, HBM）**：负责存放模型的大规模参数、中间激活值与数据，容量相对较大（如 80GB），但传输速度受限于物理总线引脚；
2. **片上计算核心（Compute Engine / Tensor Cores）**：负责在极短时钟周期内完成庞大的加法与乘法运算，速度极快，但内部缓存（SRAM）容量极度狭小。

```text
+-----------------------------------------------------------------------+
| 加速器物理数据流抽象模型                                              |
|                                                                       |
|  +-----------------------------------------------------------------+  |
|  |              高带宽片外显存 (HBM, 如 80GB)                       |  |
|  +-----------------------------------------------------------------+  |
|             | 读取输入张量 (Bytes)        ^ 写回结果张量 (Bytes)      |
|             | 内存总线带宽: 3.34 TB/s     |                           |
|             v                             |                           |
|  +-----------------------------------------------------------------+  |
|  |              片上计算引擎 (Tensor Cores 计算核心)                |  |
|  |              峰值算力: 989 TFLOP/s (BF16 稠密)                   |  |
|  +-----------------------------------------------------------------+  |
+-----------------------------------------------------------------------+
```

*图：片外显存（HBM）与片上计算引擎之间的数据流转与速率差异拓扑。*

以 NVIDIA H100 SXM5 硬件规格为例：
- **片上峰值稠密算力**：$P_{\text{peak}} = 989 \times 10^{12}\ \text{FLOP/s}$（BF16）；
- **片外内存物理带宽**：$B_{\text{mem}} = 3.34\ \text{TB/s} = 3.34 \times 10^{12}\ \text{Bytes/s}$。

据此，我们可以计算出该硬件本身的**物理临界强度（Machine Balance / Critical Intensity）**：

$$I_{\text{critical}} = \frac{P_{\text{peak}}}{B_{\text{mem}}} = \frac{989 \times 10^{12}\ \text{FLOP/s}}{3.34 \times 10^{12}\ \text{Bytes/s}} \approx 295\ \text{FLOP/Byte}$$

> **定义**：**加速器临界强度（Machine Balance）**：该数值代表**硬件每从片外显存（HBM）中读入或写出 1 个字节的数据，片上计算核心必须对该字节反复执行至少 295 次浮点运算，才能让计算引擎不陷入断流饥饿**。这是一个极为严苛的物理门槛（约 300 FLOP/Byte）。

#### 算术强度定义与瓶颈判据

对应于硬件特性，特定算法或算子的计算特征由其**算术强度（Arithmetic Intensity）**决定：

$$I_{\text{algo}} = \frac{\text{算法总浮点运算量 (FLOPs)}}{\text{算法往返片外显存搬运的总数据量 (Bytes)}}$$

在理想状态下，现代硬件通过多流与流水线机制实现通信与计算的完全重叠掩盖（Overlapping）。执行算子的理论最短时间由两者的最大值决定：

$$T = \max\left(T_{\text{comp}}, T_{\text{comm}}\right) = \max\left(\frac{\text{FLOPs}}{P_{\text{peak}}}, \frac{\text{Bytes}}{B_{\text{mem}}}\right)$$

由此产生两类截然不同的性能受限状态：

```text
+-----------------------------------------------------------------------+
| 算法性能受限状态双向判据                                              |
|                                                                       |
| 状态一：内存带宽受限 (Memory-bound)                                   |
|   - 判据：I_algo < I_critical (算术强度 < 295 FLOP/Byte)              |
|   - 表现：T_comm > T_comp                                             |
|   - 本质：搬运数据的时间远超计算时间，计算核心大部分时间在等待数据传输|
|                                                                       |
| 状态二：计算能力受限 (Compute-bound)                                  |
|   - 判据：I_algo >= I_critical (算术强度 >= 295 FLOP/Byte)            |
|   - 表现：T_comp >= T_comm                                            |
|   - 本质：数据搬运被计算时间完全掩盖，加速器计算单元进入饱和满载状态  |
+-----------------------------------------------------------------------+
```

#### 典型算子算术强度推导与推理瓶颈

我们以 BF16 精度（每个数值 2 字节）在 H100 上的表现，逐一推演常见算子的物理瓶颈。

**逐元素激活函数（ReLU 与 GELU）**：
- **ReLU（$N = 10^6$ 向量）**：从 HBM 读取输入向量 $X$（$2N$ 字节）；计算完成后向 HBM 写入结果向量 $Y$（$2N$ 字节），总搬运量为 $4N$ 字节。计算量为 $N$ 次比较（$N$ FLOPs）。算术强度为 $I_{\text{ReLU}} = \frac{N}{4N} = 0.25\ \text{FLOP/Byte}$。在 H100 上，搬运数据耗时约 $1.2\ \mu\text{s}$，而计算仅需 $1\ \text{ns}$。**ReLU 属于极度内存带宽受限算子**，计算核心 99.9% 的时间都在等待显存总线把数据送过来。
- **GELU（$N = 10^6$ 向量）**：搬运数据量同样是读取加写入共 $4N$ 字节。浮点运算包含立方、乘法、加法、开方系数及超越函数近似，单元素约需 20 次浮点运算，总计 $20N$ FLOPs。算术强度为 $I_{\text{GELU}} = \frac{20N}{4N} = 5\ \text{FLOP/Byte}$。
> **提示**：**直觉悖论：复杂的 GELU 并不比简易的 ReLU 更慢**。初学者直觉上会认为 GELU 计算开销必定远超 `max(0, x)`。但在真实 GPU 上，GELU 的算术强度（5 FLOP/Byte）依然远远低于硬件临界点 295。两者的物理耗时都完全由搬运 $4N$ 字节的显存带宽决定。在没有做算子融合的前提下，两者在硬件上的实际耗时几乎完全一致。

**向量内积（Dot Product）**：
两个长度为 $N$ 的向量 $x, w$ 计算内积 $y = x^T w$。读取 $x$（$2N$ 字节）+ 读取 $w$（$2N$ 字节）+ 写入标量 $y$（2 字节，可忽略）$\approx 4N$ 字节。浮点运算量为 $N$ 次乘法与 $N-1$ 次加法 $\approx 2N$ FLOPs。算术强度为 $I_{\text{dot}} \approx \frac{2N}{4N} = 0.5\ \text{FLOP/Byte}$，同样属于重度内存受限操作。

**矩阵-向量乘法（GEMV 与自回归推理瓶颈）**：
设权重矩阵为 $W \in \mathbb{R}^{N \times N}$，输入为向量 $x \in \mathbb{R}^N$，输出向量 $y = Wx \in \mathbb{R}^N$。
- **数据搬运量**：读取向量 $x$（$2N$ 字节）+ 读取全量矩阵 $W$（$2N^2$ 字节）+ 写入向量 $y$（$2N$ 字节）$\approx 2N^2 + 4N \approx 2N^2\ \text{Bytes}$；
- **浮点运算量**：相当于执行 $N$ 次长度为 $N$ 的向量内积，总计 $2N^2$ FLOPs；
- **算术强度**：$I_{\text{GEMV}} \approx \frac{2N^2\ \text{FLOPs}}{2N^2\ \text{Bytes}} \approx 1\ \text{FLOP/Byte}$。
> **结论**：**自回归单 Token 推理瓶颈的本质根源**。大语言模型在生成阶段（Generation / Decode Phase）是逐个 Token 自回归产出的。每生成一个新 Token，都需要将全网数十亿参数的大矩阵从 HBM 中完整读取一次，仅仅为了和一个单独的最新 Token 向量做乘法。这正是 GEMV 操作，其算术强度仅为 1 FLOP/Byte，使得大模型单批次推理被死死锚定在内存带宽瓶颈上。

#### 矩阵乘法计算饱和与架构设计

设两个大矩阵相乘：$A \in \mathbb{R}^{N \times N}$ 与 $B \in \mathbb{R}^{N \times N}$，输出 $C \in \mathbb{R}^{N \times N}$：
- **数据搬运量**：读取 $A$（$2N^2$ 字节）+ 读取 $B$（$2N^2$ 字节）+ 写入 $C$（$2N^2$ 字节）$\approx 6N^2\ \text{Bytes}$；
- **浮点运算量**：每个元素需要 $2N$ 次操作，共有 $N^2$ 个元素，总计 $2N^3$ FLOPs；
- **算术强度**：$I_{\text{GEMM}} \approx \frac{2N^3}{6N^2} = \frac{1}{3} N\ \text{FLOP/Byte}$。

随着矩阵尺度 $N$ 的扩张，算术强度呈线性增长 $\mathcal{O}(N)$：
- 当 $N = 1000$ 时，$I_{\text{GEMM}} \approx 333 > 295$，正式跨越硬件临界线进入计算受限区；
- 当 $N = 4096$ 或 $8192$ 时，$I_{\text{GEMM}}$ 超过 1000，计算核心被完全填满，硬件发挥出真正的标称峰值算力。

> **结论**：**Transformer 架构的本质设计哲学**。Transformer 之所以在所有深度学习模型中脱颖而出成为大一统底座，绝非历史偶然，而是硬件协同设计的必然产物。它的主体结构被刻意设计为由一系列巨型矩阵乘法组合而成，赋予了整个训练过程极高的算术强度。在预训练阶段，我们把成千上万个 Token 打包成超大批次同时输入，正是为了将计算强行推进至计算受限的高效区。

#### 屋顶线模型分析与硬件启示

将上述关系绘制在坐标系中，即为经典的**屋顶线图**：

```text
+-----------------------------------------------------------------------+
```

### 训练过程的算力与显存核算

明确了硬件与单算子的物理规律后，我们现在把视角提升到完整的模型训练循环，严格解构端到端训练阶段的算力与显存账本。

#### 深度神经网络基准模型

为了使推导具备严密的数学确定性，我们定义一个通用的多层前向网络基准：
- **输入数据**：批大小为 $B$，特征维度为 $D$，即输入矩阵 $X \in \mathbb{R}^{B \times D}$；
- **网络结构**：包含 $L$ 个完全相同的隐藏层；
- **层间变换**：每一层包含一个参数矩阵 $W_l \in \mathbb{R}^{D \times D}$，后接一个逐点激活函数（如 ReLU）；
- **总参数量**：每个隐藏层包含 $D^2$ 个浮点参数，网络总参数量为：

$$P = L \times D^2$$

#### 反向传播计算量推导

考虑网络中的某一特定层（例如第 2 层）：
- **前向计算**：接收前一层的激活输出 $H_1 \in \mathbb{R}^{B \times D}$，乘以权重矩阵 $W_2 \in \mathbb{R}^{D \times D}$，产出预激活输出 $H_2 \in \mathbb{R}^{B \times D}$（暂时略去激活函数）：

$$H_2 = H_1 W_2$$

前向 GEMM 计算量按照规则：

$$\text{FLOPs}_{\text{forward}} = 2 \times B \times D \times D = 2BD^2$$

- **反向传播过程**：根据微积分多元链式法则，当上游回传了损失函数对输出的梯度 $\frac{\partial \mathcal{L}}{\partial H_2} \in \mathbb{R}^{B \times D}$ 时，该层必须计算出两个独立的梯度信号：

```text
+-----------------------------------------------------------------------+
| 反向传播梯度分离流动模型                                              |
|                                                                       |
|                          上游反向信号 dH_2                            |
|                            [B x D]                                    |
|                               |                                       |
|               +---------------+---------------+                       |
|               |                               |                       |
|               v                               v                       |
|       计算对输入的激活梯度            计算对参数的权重梯度            |
|       dH_1 = dH_2 * W_2^T             dW_2 = H_1^T * dH_2             |
|       [B x D] * [D x D]^T             [D x B]^T * [B x D]             |
|       输出形状: [B x D]               输出形状: [D x D]               |
|       收缩轴: 输出特征轴 D            收缩轴: 批次样本轴 B            |
|       算力开销: 2 B D^2 FLOPs         算力开销: 2 B D^2 FLOPs         |
|               |                               |                       |
|               v                               v                       |
|       继续向浅层传递                  留存在显存中供优化器更新        |
+-----------------------------------------------------------------------+
```

*图：反向传播过程中激活梯度与参数梯度的并行流动与算力开销。*

用爱因斯坦求和标记能够极其清晰地展现这一过程：
1. **计算损失对前级输入激活的导数（向后传播信号）**：

   $$\frac{\partial \mathcal{L}}{\partial H_1} = \frac{\partial \mathcal{L}}{\partial H_2} W_2^T$$

   对应 `einsum` 语法为：`'b d_out, d_in d_out -> b d_in'`。这里对输出特征维度 `d_out` 遍历累加，总计算量为 $2 \times B \times D \times D = 2BD^2$。
2. **计算损失对本层参数权重的导数（权重更新信号）**：

   $$\frac{\partial \mathcal{L}}{\partial W_2} = H_1^T \frac{\partial \mathcal{L}}{\partial H_2}$$

   对应 `einsum` 语法为：`'b d_in, b d_out -> d_in d_out'`。这里对批次维度 `b` 遍历累加，总计算量同样严格为 $2 \times B \times D \times D = 2BD^2$。

> **结论**：**反向传播计算量严格等于前向传播的 2 倍**：
> 
> $$\text{FLOPs}_{\text{backward}} = \text{FLOPs}_{
abla_H} + \text{FLOPs}_{
abla_W} = 2BD^2 + 2BD^2 = 4BD^2 = 2 \times \text{FLOPs}_{\text{forward}}$$

#### 训练算力经验法则

将单步前向传播与反向传播的开销汇总，得到整个 $L$ 层深度网络处理单批次数据所需的总浮点运算量：

$$\begin{aligned}
\text{单步训练总 FLOPs} &= \text{FLOPs}_{\text{forward}} + \text{FLOPs}_{\text{backward}} \\
&= (2BD^2 \times L) + (4BD^2 \times L) \\
&= 2 B (L D^2) + 4 B (L D^2) \\
&= 2 B P + 4 B P \\
&= 6 \times B \times P
\end{aligned}$$

如果将批次样本 $B$ 推广至全局训练消耗的 Token 总数 $D_{\text{data}}$，将模型参数量记为 $N_{\text{param}}$，就得到了深度学习领域最著名的经验公式：

$$\text{Total Training FLOPs} \approx 6 \times N_{\text{param}} \times D_{\text{data}}$$

> **提示**：**6ND 的有效假设前提与长序列修正**。6ND 定律成立的前提是：模型的计算主体为线性投影矩阵乘法（MLP 与自注意力投影 QKV/Out）。对于标准 Transformer，只要上下文序列长度保持在常规区间（如 2048、4096），该公式极为精准。但如果序列长度 $S$ 极度拉长（如 32K、128K），自注意力机制中两两 Token 点积形成的 $S \times S$ 注意力矩阵乘法所带来的 $\mathcal{O}(S^2)$ 二次项开销将不可忽略，此时总算力将显著超出 6ND 的预测值。

#### 训练显存开销解构

在进行显存容量预算时，我们必须将显存划分为四大正交的组成部分（假设模型全量采用 BF16 混合精度训练）：

```text
+-----------------------------------------------------------------------+
| 训练期显存四大开销构成 (以全量参数 P、BF16 混合精度为例)              |
|                                                                       |
| 1. 模型参数 (Parameters, BF16)                                        |
|    - 占用: 2 * P 字节                                                 |
|                                                                       |
| 2. 梯度张量 (Gradients, BF16)                                         |
|    - 占用: 2 * P 字节                                                 |
|                                                                       |
| 3. 优化器状态 (Optimizer States, 必须 FP32)                            |
|    - AdaGrad: 4 * P 字节 (仅保存累加二阶矩 g^2)                       |
|    - AdamW:   8 * P 字节 (保存一阶动量 m 4P + 二阶动量 v 4P)          |
|                                                                       |
| 4. 中间激活值 (Activations, BF16)                                     |
|    - 占用: O(B * S * D * L) 字节 (随批次与序列长度动态线性激增)       |
+-----------------------------------------------------------------------+
```

*图：大语言模型训练期静态状态与动态激活值的显存切片模型。*

1. **模型参数（Parameters）**：总共 $P$ 个参数。以 BF16 存储，单参数占用 2 字节，总显存开销为 $2P$ 字节。
2. **反向梯度（Gradients）**：每个可学习参数在反向传播中都需要一个与之形状完全相同的梯度张量，以 BF16 存储，总显存开销为 $2P$ 字节。
3. **优化器状态（Optimizer States）**：
   - **历史渊源：为什么要在 Adam 前面看 AdaGrad？**
     AdaGrad 诞生于 2011 年，是自适应学习率算法的先驱。它在朴素随机梯度下降（SGD）的基础上引入了梯度二阶矩（梯度平方和）的累加跟踪，使得高频特征的学习率自动衰减；动量法（Momentum）则跟踪梯度的一阶矩（滑动平均速度）；而如今统治大模型训练的 Adam/AdamW，本质上就是一阶矩与二阶矩的集大成者。
   - **数值稳定性硬约束**：
     优化器状态**必须强制使用 Float32（单参数 4 字节）存储**。工业界曾多次尝试将优化器状态直接降格为 BF16 以节省显存，但由于优化器涉及跨成千上万步的微小梯度方差平方累加，16 位宽的精度损失会导致截断误差持续发散，使得模型训练在后期不可避免地下溢或无法收敛。
   - **显存消耗对比**：
     - 若使用 **AdaGrad**：仅需记录历史梯度平方和 $g^2$，每个参数需要 1 个 FP32 状态，占用 $4P$ 字节；
     - 若使用 **AdamW**：必须同时维护一阶偏差动量 $m_t$（4 字节）与二阶未中心化方差 $v_t$（4 字节），每个参数需要 2 个 FP32 状态，占用整整 **$8P$ 字节**。
     加上参数本身的副本，仅优化器相关的静态显存开销就高达 $8P$ 至 $12P$ 字节。
4. **前向中间激活值（Activations）**：
   为了在反向传播中执行链式法则乘法，前向传播每一层产生的输入特征、线性层输出以及激活函数前的张量，都必须保存在显存中等待反向传播消费。
   对于一个 $L$ 层的网络，激活值显存占用大致为：

   $$\text{Memory}_{\text{act}} \approx 2 \times B \times D \times L\ \text{Bytes}$$

> **结论**：**静态显存与动态显存的分立**。参数、梯度与优化器状态是静态常驻显存，大小仅由模型参数量 $P$ 决定，与输入数据大小无关；而激活值是动态显存，其体积直接与批大小 $B$ 及上下文长度成正比。当上下文或批次极大时，激活值将瞬间反客为主，成为引发显存溢出（OOM）的头号元凶。

### 显存优化技术

当面对有限的单卡或单节点物理显存，而算法又要求极大的批次规模时，我们该如何打破显存天花板？

#### 梯度累积机制

在大语言模型预训练中，为了降低梯度随机方差并提升优化步的稳定性，模型往往需要在一个巨大的**临界批次大小（Critical Batch Size）**下运行（例如数百万 Token）。然而，如果直接将如此庞大的批次送入 GPU，爆炸的中间激活值会瞬间导致显存崩溃。

梯度累积利用反向传播的线性可加性，通过时间维度的串行调度巧妙化解了这一矛盾：

```text
+-----------------------------------------------------------------------+
| 梯度累积时序执行逻辑                                                  |
|                                                                       |
| 目标大批次 (Batch Size = 4 * Micro-batch)                             |
|                                                                       |
| 微批次 1: 前向 -> 反向 -> 梯度累加到 w.grad (不清零)                 |
| 微批次 2: 前向 -> 反向 -> 梯度累加到 w.grad (不清零)                 |
| 微批次 3: 前向 -> 反向 -> 梯度累加到 w.grad (不清零)                 |
| 微批次 4: 前向 -> 反向 -> 梯度累加到 w.grad (不清零)                 |
|                                                                       |
| 触发更新:                                                             |
|   1. optimizer.step()  (利用累加的完整梯度更新一次参数)               |
|   2. optimizer.zero_grad() (清零梯度，准备下一轮循环)                 |
+-----------------------------------------------------------------------+
```

*图：将宏观批次拆分为微批次并进行就地梯度累加的时间线展开。*

- **实现机制**：将逻辑批次 $B$ 切分为 $K$ 个微批次（Micro-batches，大小为 $B/K$）。在处理前 $K-1$ 个微批次时，前向反向正常执行，梯度被累加存储在 `param.grad` 张量中，**既不执行 `optimizer.step()`，也不调用 `optimizer.zero_grad()`**。直到第 $K$ 个微批次反向完成后，统一执行一次参数更新并清空梯度。
- **系统代价**：**计算量完全零增加**，纯粹是调度顺序的改变，却将峰值激活显存直接压缩至原来的 $1/K$。

#### 激活检查点与局部重计算

即使缩减了微批次大小，当网络层数 $L$ 达到数十乃至上百层时，全网累加的静态激活值依然占据过半显存。

在推理过程中，我们不需要反向传播，因此计算完当前层后可以立即丢弃前一层的激活值，显存常驻仅需 $\mathcal{O}(1)$；但在标准训练中，为了反向传播能拿到激活值，我们被迫将 $L$ 层的中间状态全部死锁在显存中，开销为 $\mathcal{O}(L)$。

**激活检查点（Activation Checkpointing / 梯度检查点 Gradient Checkpointing / 重计算 Rematerialization）**的核心思想是：**用重计算的时间，换取显存的物理空间**。

在前向传播时，系统丢弃大部分中间层的激活值，仅在关键边界点（Checkpoints）保留少量的快照；当反向传播回溯到该区间时，系统利用最近的检查点快照，**重新执行一次局部的局部前向计算**，就地恢复出反向传播所需的激活张量。

```text
+-----------------------------------------------------------------------+
| 标准前向反向 vs 激活检查点重计算机制                                  |
|                                                                       |
| 模式一：标准全量存储 (激活显存 O(L))                                  |
| 前向: Layer 1 -> Layer 2 -> Layer 3 -> ... -> Layer L (全量保存在显存) |
| 反向: Layer L <- Layer 3 <- Layer 2 <- ... <- Layer 1 (直接读取激活值)|
|                                                                       |
| 模式二：激活检查点局部重计算                                          |
| 前向: [Check 1] -> (丢弃) -> [Check 2] -> (丢弃) -> [Check 3]         |
| 反向:                                                                 |
|   1. 回溯到 Check 2 ~ Check 3 区间时发现激活值丢失                    |
|   2. 从 [Check 2] 重新跑一次局部前向，重构出中间激活值                |
|   3. 立即执行反向计算，用完后彻底释放                                 |
+-----------------------------------------------------------------------+
```

*图：激活检查点在前向丢弃与反向即时重计算的执行逻辑对比。*

在由线性层和 ReLU 构成的深度模块中，每个模块内部包含线性层的输出（预激活值）与经过 ReLU 后的输出（激活值）。最粗粒度的做法是不存储线性层与激活函数之间的中间张量：
- 前向仅保留每一层的最终输出 $H_l$；
- 丢弃未激活的临时张量；
- 反向传播需要时，直接由输入顺手做一次极速计算重构；
- **收益**：几乎不付出可感知的计算延迟，直接节省接近一半的激活值显存。

#### 检查点粒度权衡与最优划分

我们可以将检查点的保留程度推向两个极端：
- **极端一：全量保留（无检查点）**：显存开销为 $\mathcal{O}(L)$，额外计算量为 0。
- **极端二：全量不保留（只留输入）**：前向传播只存最原始的数据输入，显存占用暴跌至 $\mathcal{O}(1)$。
  > **易错点**：**完全不存激活值的二次方计算灾难**。如果层与层之间完全不设检查点，当反向传播计算第 $l$ 层时，必须从第 1 层一路重新前向推演到第 $l$ 层；计算第 $l-1$ 层时，又必须从第 1 层推演到 $l-1$ 层。整网反向传播的总重计算量将膨胀为：
  > 
  > $$\sum_{l=1}^{L} l = \frac{L(L+1)}{2} = \mathcal{O}(L^2)$$
  > 
  > 这会导致训练速度断崖式下跌，完全丧失实用价值。

- **最优数学折中：$\sqrt{L}$ 策略**：
  我们在网络中每隔 $\sqrt{L}$ 层设置一个保存检查点。
  - **显存开销**：仅需存储 $\sqrt{L}$ 个快照，显存从 $\mathcal{O}(L)$ 大幅下降至 $\mathcal{O}(\sqrt{L})$；
  - **计算开销**：反向传播期间，每个区间内部局部的重计算步数最大不超过 $\sqrt{L}$，全网额外付出的重计算代价严格被压制在 $\mathcal{O}(\sqrt{L})$。

在实际大模型工程中，通常只对完整的 Transformer 块（Transformer Block）施加检查点。这仅仅需要多付出约 20% 到 33% 的前向计算时间，却能将绝大部分显存空间彻底腾出，使得系统能够塞下两倍以上的模型规模或大幅扩充上下文长度。

#### 集群训练周期估算题

> **题干**：
> 现有由 1024 张 NVIDIA H100 80GB GPU 构成的计算集群，计划在 15 万亿（$15 \times 10^{12}$）个 Token 的数据集上，从头预训练一个参数量为 700 亿（70B）的大语言模型。假设集群在实际训练中的模型浮点运算利用率（MFU）稳定在 0.5。请估算完成该预训练任务所需的端到端实际运行天数。

**推导与解析**：

1. **计算预训练所需的总浮点运算次数（FLOPs）**：
   根据单步训练的 6ND 算力法则，在常规上下文长度下，每个 Token 对应每个参数约消耗 6 次浮点运算：
   
   $$\begin{aligned}
   \text{Total FLOPs} &= 6 \times N_{\text{param}} \times D_{\text{tokens}} \\
   &= 6 \times (70 \times 10^9) \times (15 \times 10^{12}) \\
   &= 420 \times 10^9 \times 15 \times 10^{12} \\
   &= 6.3 \times 10^{24}\ \text{FLOPs}
   \end{aligned}$$

2. **计算单张 H100 的有效稠密算力供给**：
   查阅规格表，H100 在 BF16 下标称稀疏算力为 1979 TFLOP/s。针对大模型稠密矩阵训练，必须先除以 2 得到真实稠密硬件理论算力：
   
   $$\text{稠密峰值算力} = \frac{1979}{2} \approx 989\ \text{TFLOP/s} = 9.89 \times 10^{14}\ \text{FLOP/s}$$
   
   集群设定 MFU 为 0.5，故单卡实际有效算力输出为：
   
   $$P_{\text{eff}} = 9.89 \times 10^{14}\ \text{FLOP/s} \times 0.5 \approx 4.945 \times 10^{14}\ \text{FLOP/s}$$

3. **计算 1024 卡集群每天（24 小时）所能供给的有效 FLOPs**：
   
   $$\begin{aligned}
   \text{Daily Effective FLOPs} &= 1024\ \text{GPUs} \times (4.945 \times 10^{14}\ \text{FLOP/s}) \times 86400\ \text{s/day} \\
   &\approx 5.0637 \times 10^{17} \times 86400 \\
   &\approx 4.375 \times 10^{22}\ \text{FLOPs/day}
   \end{aligned}$$

4. **计算最终所需的连续训练天数**：
   
   $$\text{Days} = \frac{\text{Total FLOPs}}{\text{Daily Effective FLOPs}} = \frac{6.3 \times 10^{24}}{4.375 \times 10^{22}} \approx 144\ \text{天}$$
   
   > **提示**：如果集群 MFU 能在超大规模下进一步优化，或者硬件主频更高，天数会有所浮动；在课堂最初给出的粗略口算中，假定日算力更高时天数约为数十天（约 40 天量级）。在系统设计时，核心在于掌握这条清晰的从 FLOPs 到集群吞吐除法的核算链路。

#### 单节点显存承载容量估算题

> **题干**：
> 现有单台标准的 8 卡 NVIDIA H100 服务器，每张 GPU 配备 80 GB 的 HBM3 显存。若采用 BF16 混合精度与标准 AdamW 优化器进行全参数训练，在暂不计算动态激活值显存（假设通过极端微批次结合重计算压制到极低）的前提下，这台服务器的纯显存物理上限能容纳的最大模型参数量约为多少？

**推导与解析**：

1. **计算单节点总物理显存容量**：
   
   $$\text{Total HBM} = 8\ \text{GPUs} \times 80\ \text{GB} = 640\ \text{GB} = 640 \times 10^9\ \text{Bytes}$$

2. **拆解每个参数在训练状态下必须常驻的字节数**：
   采用 BF16 混合精度与 AdamW 优化器时，状态显存包含：
   - 模型参数（BF16）：2 字节 / 参数；
   - 反向梯度（BF16）：2 字节 / 参数；
   - 优化器状态（必须 FP32）：
     - 一阶动量 $m_t$：4 字节 / 参数；
     - 二阶动量 $v_t$：4 字节 / 参数；
     优化器状态合计为 $4 + 4 = 8$ 字节 / 参数。
   
   每个参数消耗的纯状态显存总和为：
   
   $$\text{Bytes per Parameter} = 2 + 2 + 4 + 4 = 12\ \text{Bytes/param}$$

3. **计算理论承载的最大模型参数上限**：
   
   $$N_{\text{max}} = \frac{640 \times 10^9\ \text{Bytes}}{12\ \text{Bytes/param}} \approx 53.33 \times 10^9\ \text{params} \approx 533\ \text{亿参数 (53.3B)}$$

**结论**：在不考虑激活值显存的前提下，单台 8 卡 H100 80GB 服务器最多能够硬塞下约 **530 亿参数（53B）** 的模型状态。一旦计入真实的动态激活值与通信缓冲区，实际能稳定训练的模型通常在 30B 到 40B 之间，更大的模型必须跨多节点进行模型并行或 ZeRO/FSDP 显存分片切分。

### 训练资源核算与核心度量体系

#### 计算量与吞吐率的指标定义

在评估模型计算成本时，核心度量基准是浮点运算次数。在大多数深度学习负载中，非线性激活、归一化等辅助运算的计算量在数量级上远小于矩阵运算，因此在建立直觉模型时，我们默认关注最基础的浮点乘法与加法。

工程讨论中极易混淆两组发音相同但物理意义迥异的缩写术语：
- **浮点运算次数（FLOPs）**：末尾为小写 `s`，代表 Floating Point Operations。它度量的是一项计算任务本身所包含的绝对运算量，是一个与硬件架构无关的纯算法量纲。例如训练一个 GPT-3 模型大约需要消耗 $3 \times 10^{25}$ FLOPs 的计算量。
- **每秒浮点运算次数（FLOP/s）**：通常写作大写 `FLOPS` 或带斜杠的 `FLOP/s`，代表 Floating Point Operations Per Second。它度量的是硬件计算核心在单位时间内执行浮点运算的物理速率，属于硬件吞吐能力的量纲。例如 NVIDIA H100 SXM 在半精度下的理论峰值通常以 TFLOP/s（$10^{12}$ FLOP/s）或 PFLOP/s（$10^{15}$ FLOP/s）来标定。

在查阅厂商提供的硬件规格说明书（Datasheet）时，必须格外警惕标称数值背后的细则陷阱。例如翻看 NVIDIA 官方手册，H100 GPU 标称的 BF16 Tensor Core 峰值算力高达 1979 TFLOP/s。如果直接拿着这个数字去做基准测试和容量规划，实测数据一定会让你大失所望。因为翻到手册最下方的细则脚注会发现，该标称值是基于结构化稀疏矩阵（2:4 Structured Sparsity）计算出来的。但在通用大语言模型预训练中，权重和激活值都是稠密矩阵（Dense Matrix），并不满足结构化稀疏的硬性假设。

> **结论**：对于稠密矩阵运算，规格书上的标称半精度峰值必须无条件除以 2。H100 SXM 真实的 BF16 稠密物理算力上限约为 989.5 TFLOP/s（工程估算通常取 989 TFLOP/s）。

建立起正确的物理量纲后，我们就可以快速推演特定算力集群的绝对生产力上限。例如一个拥有 8 张 H100 的单节点服务器，连续满载运行一周（7 天，即 604,800 秒），它所能提供的稠密 BF16 浮点运算总量上限为：

$$8 \times 604,800 \text{ s} \times (989 \times 10^{12} \text{ FLOP/s}) \approx 4.78 \times 10^{21} \text{ FLOPs} \approx 5 \times 10^{21} \text{ FLOPs}$$

这个粗略的量级估算，构成了后续所有训练进度规划与资源分配的锚点。

#### 硬件利用率与基准测试规范

计算量独立于硬件，但将计算量映射到具体物理芯片上实际跑完需要多久，则必须依靠严格的基准测试（Benchmarking）。

在 GPU 上进行耗时测定时，新手极易踩入一个经典的测量陷阱：代码执行完毕并打印耗时，结果显示只用了微秒级别，似乎速度飞快。这实际上是由于 PyTorch 的 CUDA 调用是完全异步（Asynchronous）的。当你在 Python 层调用一个张量运算时，主机端（CPU）仅仅是把该计算内核（Kernel）发射到 GPU 的执行队列（CUDA Stream）中，随后函数立即非阻塞返回。此时 GPU 芯片上甚至还没有真正开始调度线程执行该内核。

> **易错点**：进行 GPU 基准测定时，必须在被测代码段的起始点与结束点显式调用 `torch.cuda.synchronize()` 建立硬件同步屏障，强行等待 GPU 核心排空流水线并执行完毕，否则测得的只是 CPU 发射指令的微小延迟。此外，测定前必须先运行若干轮预热迭代（Warm-up），并在正式计时中重复多次取平均值，以消除动态升频、驱动初始化和缓存冷启动带来的扰动。

标准计时范式如下所示：

```python
import torch

# 预热 GPU
for _ in range(10):
    _ = torch.matmul(x, w)
torch.cuda.synchronize()

# 正式测定
start_event = torch.cuda.Event(enable_timing=True)
end_event = torch.cuda.Event(enable_timing=True)

start_event.record()
for _ in range(num_iters):
    _ = torch.matmul(x, w)
end_event.record()

torch.cuda.synchronize()
elapsed_time_ms = start_event.elapsed_time(end_event)
avg_time_sec = (elapsed_time_ms / num_iters) / 1000.0
```

基于实测的真实耗时与算法本身的理论逻辑运算量，我们引入评估系统工程效率最核心的黄金指标——模型浮点利用率（Model FLOPs Utilization, MFU）：

> **定义**：模型浮点利用率（MFU）是指硬件在单位时间内实际完成的模型有效逻辑浮点运算次数，与硬件理论标称稠密峰值算力（除以 2 后的真实物理峰值）之比：
> $$\text{MFU} = \frac{\text{实际有效 FLOP/s}}{\text{硬件标称峰值 FLOP/s}}$$

由于计算过程中必然夹杂显存搬运、内核启动开销、层间同步以及分布式通信延迟，系统的实际吞吐绝不可能超越物理标称极限（即 MFU 恒小于 1.0）。在现代大模型分布式预训练工程中：
- 如果能够把端到端的全流程 MFU 维持在 50%（0.5）左右，系统实现就已经达到了工业级的高度优化水平；
- 若只跑单一孤立的纯超大矩阵乘法（GEMM），硬件利用率可能冲到 80%（0.8）甚至更高；
- 若实测 MFU 跌落到 10%（0.1）附近，则意味着硬件计算单元绝大部分时间处于饥饿闲置状态，系统必然遭遇了严重的通信阻塞或显存带宽瓶颈，必须立刻进行性能剖析。

### 张量存储机理与数值精度选型

#### 浮点数位结构与数值动态范围

在大语言模型系统的物理世界中，张量（Tensor）是承载万物的基础单元。模型参数（Weights）、反向梯度（Gradients）、优化器动量与方差（Optimizer States）、训练语料（Tokens）以及前向传播生成的中间激活值（Activations），在物理内存中无一例外都是多维张量。解构像 DeepSeek 这样的超大规模模型，其本质就是一张由海量具备不同形状与数值精度的张量构成的计算图。

张量在内存中占用的物理空间，严格等于其包含的元素总数乘以单个数值类型的字节大小。以标准的单精度浮点数 `float32`（FP32）为例，每个元素占据 32 位（Bit），即 4 字节（Byte）。一个维度为 $4 \times 8$ 的张量总共包含 32 个元素，在内存中占据 $32 \times 4 = 128$ 字节。当维度上升到大模型前馈网络（FFN）中常见的中间投影矩阵时，例如尺寸为 $20,000 \times 16,000$ 的单个权重矩阵，其占用的显存为：

$$20,000 \times 16,000 \times 4 \text{ Bytes} = 1,280,000,000 \text{ Bytes} \approx 1.28 \text{ GB}$$

这还仅仅是某一层的一个单精度权重矩阵。由于模型总参数量动辄达到数十亿乃至数千亿，无脑使用全量 FP32 训练会导致显存需求瞬间爆炸。

为了压缩存储并加速运算，我们必须深入剖析 IEEE 754 浮点数的二进制构成。一个典型的浮点数由三个字段拼接而成：
1. **符号位（Sign）**：1 位，标定数值的正负；
2. **指数位（Exponent）**：决定数值的缩放阶数，直接限定了该数据类型能够覆盖的**动态范围（Dynamic Range）**；
3. **尾数位（Mantissa / Fraction）**：记录有效数值信息，直接决定了该数据类型的**数值精度与分辨率（Precision / Resolution）**。

| 数据格式 | 总位数 (Bits) | 符号位 | 指数位 | 尾数位 | 指数偏置 | 最小正正规数 | 动态范围对比 | 字节数 (Bytes) | 典型应用场景 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :--- |
| **FP32** | 32 | 1 | 8 | 23 | 127 | $\approx 1.18 \times 10^{-38}$ | 基准标准（极宽） | 4 | 优化器主状态、高精度累加 |
| **FP16** | 16 | 1 | 5 | 10 | 15 | $\approx 6.10 \times 10^{-5}$ | 极窄（易下溢） | 2 | 早期混合精度（需损失缩放） |
| **BF16** | 16 | 1 | 8 | 7 | 127 | $\approx 1.18 \times 10^{-38}$ | 等同于 FP32 | 2 | 现代大模型训练黄金标准 |
| **FP8 (E4M3)** | 8 | 1 | 4 | 3 | 7 | $\approx 1.95 \times 10^{-3}$ | 偏向高精度 | 1 | 前向激活与权重的极低开销计算 |
| **FP8 (E5M2)** | 8 | 1 | 5 | 2 | 15 | $\approx 6.10 \times 10^{-5}$ | 偏向大动态范围 | 1 | 反向梯度回传计算 |

早期深度学习试图直接将数据位宽斩半切换为半精度 `float16`（FP16）。FP16 仅有 5 位指数，其能够表示的非零正规数下限仅约为 $6.1 \times 10^{-5}$。在大模型深层网络的反向传播中，梯度经过多层连续矩阵相乘后往往会衰减到 $10^{-7}$ 或更小。在 FP16 体系下，这类微小数值会直接遭遇下溢（Underflow）被强制截断为 0，导致网络权重无法更新；或者在数值剧烈变化时触发上溢（Overflow）变成 `Inf`，进而在后续计算中引发灾难性的 `NaN`（Not a Number）数值崩溃。

为了克服 FP16 的动态范围缺陷，Google 于 2018 年推出了专为深度学习定制的 Brain Floating Point 16（BF16）。BF16 的设计极为精巧：它在总位宽同样压缩至 16 位的前提下，拒绝牺牲动态范围，保留了与 FP32 完全相同的 8 位指数位，仅仅将尾数位由 23 位大幅截短至 7 位。

> **提示**：天下没有免费的午餐，BF16 维持大动态范围的代价是数值分辨率的显著下降。然而深度学习反向传播本质上是一个带有随机噪声的随机梯度下降（SGD）过程，梯度和激活值本身包含环境噪声，对尾数有效精度的微小损失具有极强的容忍度，但对梯度下溢清零或上溢崩溃却脆弱不堪。因此，BF16 完美契合了大语言模型预训练对动态范围的刚性需求，成为了当前大模型训练的绝对事实标准。

#### 混合精度训练机制

即便 BF16 表现优异，单纯采用纯 BF16（Pure BF16）进行端到端全流程训练依然暗藏巨大的数值不稳定风险。特别是在优化器内部，涉及梯度平方的一阶矩与二阶矩累积，以及参数更新步长的极其微小的更新量叠加。如果直接把微小的更新量加到较大的 BF16 权重上，会因为尾数位数不足直接发生严重的精度损失甚至更新停滞。

因此，工业界通行的解决方案是**自动混合精度训练（Automatic Mixed Precision, AMP）**。其核心调度逻辑为：
- **模型参数、梯度与前向激活值**：统一采用 **BF16** 存储与计算。这不仅直接削减了 50% 的参数与激活显存占用，更让计算核心能够跑在低精度 Tensor Core 的峰值吞吐速率上；
- **优化器内部状态与主权重副本**：必须强制保留为 **FP32**。优化器维护高精度的参数母本，梯度以 BF16 传回后，在 FP32 空间完成动量衰减、方差平方平均和参数更新，最后再将更新后的参数投射回 BF16 供下一轮前向传播使用；
- **数值敏感操作**：涉及大幅度非线性映射的算子（如计算大范围指数和的 Softmax、损失函数计算），由框架自动回退到 FP32 精度执行，避免发生指数溢出。

PyTorch 通过 `torch.cuda.amp` 原生支持该调度机制：

```python
import torch

scaler = torch.cuda.amp.GradScaler(enabled=False) # BF16 通常不需要损失缩放器

for input_tokens, targets in dataloader:
    optimizer.zero_grad()
    
    # 将前向传播包裹在 autocast 上下文中
    with torch.cuda.amp.autocast(dtype=torch.bfloat16):
        # 内部的大型矩阵乘法自动使用 BF16 执行
        logits = model(input_tokens)
        loss = criterion(logits, targets)
        
    # 反向传播计算梯度（以 BF16 产出）
    loss.backward()
    
    # 优化器在内部以 FP32 更新状态和参数副本
    optimizer.step()
```

#### 超低精度量化与块缩放机制

在混合精度之外，业界正在向更激进的 8 位（FP8）甚至 4 位（FP4）浮点演化：
- **FP8 格式**：已进入标准化阶段，主要分化为两大流派：`E4M3`（4 位指数、3 位尾数，侧重保留更高精度）常用于前向传播中的激活值与权重矩阵；`E5M2`（5 位指数、2 位尾数，侧重维系更大的动态范围）常用于误差梯度反向传播。现代 GPU（如 Hopper 及后续架构）的 Transformer Engine 已能在底层实现 FP8 算子的无缝转换；
- **FP4 格式（如 NVFP4）**：每个数值仅占据微不足道的 4 个比特位。仅凭 4 位甚至无法在一条连续数轴上表达几十个离散数值（例如仅仅覆盖 $-6$ 到 $+6$ 之间的离散整数）。若直接进行机械式的截断量化，神经网络训练必定彻底发散。工程上的破局手段是**分块缩放（Block Scaling）**：将张量在空间上划分为若干紧凑的连续小块（例如每 16 或 32 个元素为一个 Block），整个块内的数值共享一个更高精度（如 FP8 或 FP32）的全局缩放因子（Scale Factor）。块内数值仅表示局部的相对比例，通过动态缩放因子在宏观上撑开整体张量的动态范围；
- **极低位量化与 1-Bit 误区**：在更极端的单比特（1-bit）或双比特（2-bit）领域，必须清晰划定**训练（Training）**与**推理（Inference）**的鸿沟。模型训练完毕后，通过训练后量化（PTQ）将权重压制到极低位宽是工业可行的成熟技术；但直接从零使用 1-bit 精度端到端训练出具备可用性能的大语言模型，目前在学术界与工业界尚无经得起验证的突破性先例。

### 维度变换语义与 Einops 原语

#### Einsum 的求和消去与转置规避

在底层计算中，算术逻辑最终落地为张量沿各个维度的乘加运算。原生 PyTorch API 在处理多维张量变换时，严重依赖无语义的轴序号与负数索引（如 `dim=-1, -2`）以及无休无止的 `transpose` 和 `permute`。面对像下面这种典型的原生操作代码：

```python
# 原生 PyTorch 写法: 轴语义极其隐晦，代码可读性极差
out = torch.matmul(x.transpose(-1, -2), y).squeeze(1)
```

读者根本无法直观判断 `-1` 和 `-2` 轴究竟对应序列长度、隐藏维度还是多头数量，极易引发维度隐式对齐失误的静默缺陷。

为了彻底消除这种心智负担，我们引入基于爱因斯坦求和约定的 `einops` 与 `einsum`。其核心设计哲学为：**彻底废除抽象轴索引，以命名变量显式绑定各个维度的几何语义**。

> **定义**：Einsum 是一种高度规范化的广义矩阵乘法语法糖。其运转规则为：在箭头左侧分别声明输入张量的各个命名轴，在箭头右侧声明输出张量保留的命名轴。**凡是在输入中出现、但在输出端被隐去的命名轴，系统将自动对该轴上的所有元素执行遍历相乘与累加求和（求和消去）**。

以基础矩阵乘法为例，设有输入矩阵 $X \in \mathbb{R}^{3 \times 4}$ 与 $Y \in \mathbb{R}^{4 \times 3}$：

```python
import einops

# 显式声明轴语义: seq1 为行, hidden 为内积收缩维度, seq2 为输出列
# hidden 轴未在右侧出现，系统自动对其执行乘加求和消去
z = einops.einsum(x, y, 'seq1 hidden, hidden seq2 -> seq1 seq2')
```

当场景复杂化为高阶批量矩阵乘法时，Einsum 的优势更加显著。假设有两个三维张量 $X, Y \in \mathbb{R}^{2 \times 3 \times 4}$，若要将它们按最后两个维度相乘并输出 $(2, 3, 3)$ 的张量：

```python
# 原生 PyTorch: 必须强制执行最后两轴转置，依赖转置抵消内积轴
z_native = torch.matmul(x, y.transpose(-1, -2))

# Einops: 无需调用任何 transpose，直接通过命名轴的位置排列隐式完成转置
z_einops = einops.einsum(x, y, 'batch seq1 hidden, batch seq2 hidden -> batch seq1 seq2')
```

在这段代码中，根本不需要在脑海中旋转张量维度——输入张量 $Y$ 的第二个轴与第三个轴分别被赋予了 `seq2` 和 `hidden` 标签，输出端直接指定由 `batch seq1 seq2` 承接，系统自然知道该沿着 `hidden` 轴完成缩并。

为了让模块化代码兼容任意维度的批处理结构，Einsum 原生支持省略号（Ellipsis `...`）语法。当张量包含诸如样本批次、流水线阶段、多头分组等复合前导轴时，只需用 `...` 一揽子指代，无需关心张量的具体秩数（Rank）：

```python
# 无论前面嵌套了多少层前导维度，始终只关注末尾两维的几何变换
out = einops.einsum(q, k, '... seq1 hidden, ... seq2 hidden -> ... seq1 seq2')
```

#### 张量归约与空间重排

除矩阵乘法外，`einops` 提供了两组极具表现力的核心空间变换基元：`reduce` 与 `rearrange`。

##### 通用归约操作（Reduce）

`reduce` 是沿特定轴聚合求和（`sum`）、均值（`mean`）、最大值（`max`）或最小值（`min`）的通用泛化接口：

```python
# 原生写法: 语义与负索引强耦合
sum_native = x.sum(dim=-1)

# Einops 写法: 显式声明 hidden 轴在聚合后消失
sum_einops = einops.reduce(x, 'batch seq hidden -> batch seq', 'sum')
```

> **提示**：在计算性能层面，`einops.reduce` 与原生 PyTorch 操作毫无二致。它完全编译为底层的相同 CUDA 内核，纯属提供高级语义保障的零成本抽象（Zero-cost Abstraction）。

##### 维度结构重排（Rearrange）

在多头自注意力机制（MHA）等经典结构中，张量经常需要在“宽隐藏层”与“多头分割层”之间来回折叠与展开。例如输入张量形状为 `(3, 8)`，其中第二维的 8 并非单一物理量，而是由 2 个注意头（`heads=2`）和每个头 4 个通道（`dim=4`）复合交织而成。原生 PyTorch 必须通过繁杂的 `view(3, 2, 4)` 伴随连续性校验 `contiguous()` 来完成变换。而在 `einops` 中，括号语法被赋予了复合轴解包与打包的严格语义：

```python
from einops import rearrange

# 输入 x 形状为 (3, 8)
# 使用括号 (h d) 声明将复合轴拆解为 head 数量 2 与单头维度 4
x_heads = rearrange(x, 'b (h d) -> b h d', h=2) # 结果形状: (3, 2, 4)

# 经过单头矩阵运算后，可以毫无歧义地重新打包压缩回展平维度
x_merged = rearrange(x_heads, 'b h d -> b (h d)') # 结果形状还原为: (3, 8)
```

这种语法不仅可以在行优先与列优先次序间清晰传达数据排布，而且当底层张量发生隐蔽的轴错位时会立即抛出断言异常，彻底防范了深层大模型中最难排查的维度混淆隐患。

### 访存墙瓶颈与屋顶线模型分析

#### 加速器硬件架构与临界算术强度

很多初学者容易产生一种朴素的误解：只要使用顶级 GPU，所有运算都能获得成百上千倍的算力加速。但现实中，现代神经网络中相当一部分算子在高端硬件上的实际执行速度慢得惊人。要洞察这一现象，必须穿透加速器的物理硬件拓扑。

```text
+-------------------------------------------------------+
|                高带宽显存 (HBM, ~3.35 TB/s)            |
|     存储对象: 模型参数、优化器状态、输入数据、前向激活值   |
+-------------------------------------------------------+
                           |   ^
           读取输入与权重   |   | 写回输出与激活值
              (Load Data)  |   | (Store Data)
                           v   |
+-------------------------------------------------------+
|                片上计算引擎 (Tensor Cores / SRAM)      |
|    执行运算: 矩阵乘加 (MAC)、逐元素激活、归约求和       |
|    BF16 稠密物理峰值: ~989 TFLOP/s (H100 SXM)          |
+-------------------------------------------------------+
```

加速器硬件内部计算引擎与高带宽显存（HBM）处于物理分离状态，所有张量计算都必须经历从 HBM 加载到片上寄存器、计算、再写回 HBM 的完整数据传输回路。

衡量该硬件传输与计算性能的两个核心技术指标为：
- **稠密半精度计算算力峰值（$P_{\text{peak}}$）**：对于 H100 SXM，稠密 BF16 算力峰值约为 $989 \times 10^{12} \text{ FLOP/s}$（即 989 TFLOP/s）；
- **显存带宽（$BW$）**：片上核心与 HBM 之间的数据搬运带宽上限，H100 SXM 约为 $3.35 \times 10^{12} \text{ Bytes/s}$（即 3.35 TB/s）。

我们将两者相除，即可推导出硬件的物理本质属性——**临界算术强度（Critical Arithmetic Intensity）**：

> **定义**：硬件加速器的临界算术强度（$I_{\text{crit}}$）定义为理论计算峰值算力与显存带宽的比值：
> $$I_{\text{crit}} = \frac{P_{\text{peak}}}{BW} = \frac{989 \times 10^{12} \text{ FLOP/s}}{3.35 \times 10^{12} \text{ Bytes/s}} \approx 295 \text{ FLOP/Byte}$$

这个数值拥有极其震撼且残酷的物理意义：**在 H100 GPU 上，硬件每从 HBM 显存中读取或写入 1 个字节的数据，片上计算引擎必须至少完成 295 次浮点运算，才能让计算单元彻底吃饱而不陷入停工等待！**

对应地，我们给出算法端自身的指标——**算法算术强度（Arithmetic Intensity）**：

$$I_{\text{alg}} = \frac{\text{算法总浮点运算次数 (FLOPs)}}{\text{算法引发的总显存搬运字节数 (Bytes)}}$$

基于现代计算硬件的双缓冲重叠机制（Overlap），数据传输与核心计算可以流水线并行，因此算法在芯片上的端到端理论执行总时间受制于木桶的最短板：

$$T_{\text{mem}} = \frac{\text{Bytes}}{BW}, \quad T_{\text{comp}} = \frac{\text{FLOPs}}{P_{\text{peak}}}$$
$$T_{\text{total}} \approx \max(T_{\text{mem}}, T_{\text{comp}})$$

由此将算法严格划分为两大阵营：
1. **内存受限（Memory-bound）**：当 $I_{\text{alg}} < I_{\text{crit}}$ 时，$T_{\text{mem}} > T_{\text{comp}}$。搬运数据的时间远超计算时间，计算核心长期处于饥饿等待状态，系统吞吐受制于显存总线带宽；
2. **计算受限（Compute-bound）**：当 $I_{\text{alg}} > I_{\text{crit}}$ 时，$T_{\text{comp}} > T_{\text{mem}}$。计算时间压倒传输时间，硬件计算核心处于全负荷满载运转，系统吞吐受制于计算单元的绝对主频与数量。

#### 经典运算算子的算术强度剖析

我们以 BF16 精度（每个浮点数占 2 字节）为例，对深度学习中几类核心算子进行严格的算术强度与瓶颈推演。

##### 逐元素激活函数（ReLU）

设输入张量为包含 $N$ 个元素的向量 $x$：
- **显存搬运量**：从 HBM 读取输入向量 $x$ 消耗 $2N$ 字节；计算完毕将输出向量 $y$ 写回 HBM 消耗 $2N$ 字节。总搬运量为 $4N$ 字节；
- **浮点计算量**：对每个元素执行一次与 0 的最大值比较（$\max(0, x_i)$），计为 $N$ FLOPs；
- **算术强度**：
  $$I_{\text{ReLU}} = \frac{N \text{ FLOPs}}{4N \text{ Bytes}} = 0.25 \text{ FLOP/Byte}$$

对于需要 295 FLOP/Byte 才能喂饱的 H100 而言，0.25 意味着灾难性的资源闲置。计算单元只需要花 1 纳秒就能搞定的运算，显存搬运却需要花上微秒级别去等待。ReLU 属于极端典型的显存受限算子。

##### 复杂激活函数（GELU）

GELU 激活包含一系列复杂的多项式乘加与双曲正切超越函数逼近：
- **显存搬运量**：依然是读入 $x$（$2N$ 字节）并写回 $y$（$2N$ 字节），总共 $4N$ 字节；
- **浮点计算量**：展开后的多项式逼近在每个元素上通常需要消耗约 20 次浮点运算，总计 $20N$ FLOPs；
- **算术强度**：
  $$I_{\text{GELU}} = \frac{20N \text{ FLOPs}}{4N \text{ Bytes}} = 5 \text{ FLOP/Byte}$$

> **提示**：初学者看到 GELU 的数学公式比 ReLU 复杂数十倍，常直觉性地认为 GELU 的延迟开销一定远高于 ReLU。但在硬件底层，5 FLOP/Byte 依然被死死锁在 295 的临界线之下（$5 \ll 295$）。在 GPU 物理世界中，两者耗费的端到端执行时间几乎完全相同！因为耗时的主导权完全由那 $4N$ 字节在显存总线上的搬运时间决定，片上核心多做的这十几步算术指令完全被掩盖在漫长的显存读取延迟之中。

##### 向量内积（Vector Dot Product）

计算两个长度均为 $N$ 的向量 $x, w$ 的点积 $y = x \cdot w$：
- **显存搬运量**：读取 $x$（$2N$ 字节），读取 $w$（$2N$ 字节），写回单一标量标量 $y$（2 字节），总计约 $4N$ 字节；
- **浮点计算量**：$N$ 次乘法与 $N-1$ 次加法，总计约 $2N$ FLOPs；
- **算术强度**：
  $$I_{\text{Dot}} \approx \frac{2N \text{ FLOPs}}{4N \text{ Bytes}} = 0.5 \text{ FLOP/Byte}$$
  同样属于严重的显存受限操作。

##### 矩阵-向量乘法（GEMV）

输入向量 $x \in \mathbb{R}^N$，权重矩阵 $W \in \mathbb{R}^{N \times N}$，执行 $y = xW$：
- **显存搬运量**：读取向量 $x$（$2N$ 字节），读取整个权重矩阵 $W$（$2N^2$ 字节），写回输出向量 $y$（$2N$ 字节），总计约 $2N^2 + 4N \approx 2N^2$ 字节；
- **浮点计算量**：相当于执行 $N$ 次长度为 $N$ 的向量点积，总计 $2N^2$ FLOPs；
- **算术强度**：
  $$I_{\text{GEMV}} \approx \frac{2N^2 \text{ FLOPs}}{2N^2 \text{ Bytes}} \approx 1 \text{ FLOP/Byte}$$

> **重要结论**：大语言模型在进行自回归解码（Inference / Generation）时，每次只输入一个刚刚生成的单 token 向量，与模型全量权重矩阵做乘法，本质上执行的就是纯粹的 GEMV 操作。其算术强度仅为 1 左右，这意味着大模型单批次文本生成是极度显存带宽受限的负载，硬件计算核心处于巨大的闲置状态，生成速度完全被 HBM 的读出带宽卡死。

##### 矩阵-矩阵乘法（GEMM）

输入矩阵 $X \in \mathbb{R}^{N \times N}$ 与权重矩阵 $W \in \mathbb{R}^{N \times N}$ 相乘，生成 $Y = XW \in \mathbb{R}^{N \times N}$：
- **显存搬运量**：读取 $X$（$2N^2$ 字节），读取 $W$（$2N^2$ 字节），写回 $Y$（$2N^2$ 字节），总计为 $6N^2$ 字节；
- **浮点计算量**：输出矩阵中包含 $N^2$ 个元素，每个元素对应长度为 $N$ 的行与列的内积，计算量为 $2N \times N^2 = 2N^3$ FLOPs；
- **算术强度**：
  $$I_{\text{GEMM}} = \frac{2N^3 \text{ FLOPs}}{6N^2 \text{ Bytes}} = \frac{N}{3} \text{ FLOP/Byte}$$

数据搬运量随尺寸呈平方级增长（$O(N^2)$），而计算量却呈立方级爆发（$O(N^3)$）！当矩阵维度 $N$ 足够大时，算术强度随着 $N$ 呈线性扩张：
- 当 $N = 300$ 时，$I \approx 100 \text{ FLOP/Byte}$；
- 当 $N = 900$ 时，$I \approx 300 \text{ FLOP/Byte} > 295$，系统正式跨过临界阈值，迈入神圣的**计算受限区**！

| 算子类别 | 输入张量维度 | BF16 显存搬运量 (Bytes) | 理论计算量 (FLOPs) | 算术强度 (FLOP/Byte) | H100 上的性能受限形态 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **ReLU** | $N$ | $4N$ | $N$ | $0.25$ | 极端内存受限（Memory-Bound） |
| **GELU** | $N$ | $4N$ | $20N$ | $5.0$ | 严重内存受限（Memory-Bound） |
| **Dot Product** | $N$ 与 $N$ | $4N$ | $2N$ | $0.5$ | 严重内存受限（Memory-Bound） |
| **GEMV** | $N$ 与 $N \times N$ | $\approx 2N^2$ | $2N^2$ | $1.0$ | 严重内存受限（解码推理典型） |
| **GEMM** | $N \times N$ 与 $N \times N$ | $6N^2$ | $2N^3$ | $N / 3$ | 计算受限（当 $N > 900$，训练典型） |

Transformer 架构之所以横扫整个现代人工智能领域，其最深层的系统原因正在于此：它的骨干网络被刻意设计为完全由超大规模的 GEMM 堆叠而成（前馈层双投影矩阵、自注意力 QKV 投影与输出投影），将运算强行推入计算受限的高算术强度区间，从而最大化榨取 GPU Tensor Core 的巅峰效能。

#### 屋顶线模型与性能饱和区判定

将上述访存与计算的动态权衡抽象提炼，即构成了著名的屋顶线模型（Roofline Model）。

```text
性能 (FLOP/s, 对数刻度)
  ^
  |                     计算受限区 (Compute-Bound)
  |                  +----------------------------- 理论峰值算力 P_peak (~989 TFLOP/s)
  |                 /
  |                /
  |               /   拐点: 临界算术强度 I_crit (~295 FLOP/Byte)
  |              /
  |             /
  |            /
  |           /
  |          / 访存受限区 (Memory-Bound)
  |         /  斜率 = 内存带宽 BW (~3.35 TB/s)
  |        /
  +-------+---------------------------------------->
  0      I_crit                                     算术强度 I (FLOP/Byte, 对数刻度)
```

屋顶线模型以算术强度为横轴、达成计算吞吐为纵轴，以硬件显存带宽为上升斜率、硬件理论峰值算力为平顶天花板，明确划定访存受限与计算受限的物理分界。

图中的物理分界线清晰地解释了为什么大模型系统的端到端 MFU 通常只有 50%：
1. **网络并非纯粹由矩阵乘法组成**：在宏伟的大矩阵乘法之间，不可避免地穿插着层归一化（LayerNorm/RMSNorm）、Softmax、残差加法和位置编码。这些算子处于左侧倾斜的显存受限上升区，强行拖慢了整机的平均吞吐；
2. **小微批次导致的利用率跌落**：如果在前向计算中设置的 Batch Size 过小，导致有效矩阵乘法的 $N$ 尺寸无法跨越临界拐点，GEMM 算子自身也会滑落到倾斜的访存受限区，使得算力核心大面积闲置。增大微批次（Micro-batch Size）或扩大隐藏层宽度，本质就是在把算子强行推上屋顶线的水平平台。

### 深度网络训练算力与显存占用建模

#### 前向与反向传播的计算量推导

脱离具体模型的工程估算都是空中楼阁。我们来考察一个拥有 $L$ 层深度的网络结构，输入数据批次为 $B$，网络特征隐藏维度为 $D$。为了清晰呈现推导链条，暂时略去激活函数的非线性开销，每层严格执行尺寸为 $D \times D$ 的全连接投影。每一层的参数权重矩阵为 $W \in \mathbb{R}^{D \times D}$（单层参数量为 $D^2$，全网总参数量为 $P = L \cdot D^2$）。

我们聚焦于网络中任意的第 2 层变换：该层接收上一层的激活值 $H_1 \in \mathbb{R}^{B \times D}$，乘以权重矩阵 $W_2 \in \mathbb{R}^{D \times D}$，生成输出激活值 $H_2 \in \mathbb{R}^{B \times D}$。

##### 前向传播（Forward Pass）

前向矩阵乘法的维度变换为：

$$H_2 = H_1 W_2, \quad (B \times D) \times (D \times D) \to (B \times D)$$

输出张量共包含 $B \cdot D$ 个元素，每个元素对应一个长度为 $D$ 的内积。因此前向传播的单层浮点计算量为：

$$\text{FLOPs}_{\text{fwd\_layer}} = 2 \times B \times D \times D = 2 B D^2$$

遍历全网 $L$ 个层，全网前向传播总算力消耗严格为：

$$\text{FLOPs}_{\text{fwd\_total}} = L \times 2 B D^2 = 2 B \cdot (L D^2) = 2 B P$$

其计算量严格等同于两倍的输入样本数乘以模型参数量。

##### 反向传播（Backward Pass）

在反向传播中，基于微积分链式法则，当损失函数 $\mathcal{L}$ 的误差信号沿着计算图反向传递到 $H_2$ 处时，反向传播引擎必须强制完成两个独立方向的矩阵求导计算：

```text
               前向传播 (Forward Pass, 2BD^2 FLOPs)
         H1 ----------------( 乘以 W2 )----------------> H2 ---> 损失 L
         |                                               |
         |                                               | 反向传播
         v                                               v
   dH1 = dH2 * W2^T                             dW2 = H1^T * dH2
(输入梯度回传, 2BD^2 FLOPs)                   (参数梯度更新, 2BD^2 FLOPs)
         \                                               /
          +---------------------------------------------+
               反向传播总计: 2BD^2 + 2BD^2 = 4BD^2 FLOPs
```

单层线性变换在反向传播中必须沿计算图向左输出激活信号梯度以维持链式法则，同时向下输出参数权重梯度以供优化器更新，因而反向计算量严格为前向计算量的两倍。

我们用 Einsum 记法来展现这两步求导的数学本质与开销：
1. **关于输入的梯度（Activation Gradients）**：将误差信号继续向浅层传递，以供上一层进行链式求导：
   $$\frac{\partial \mathcal{L}}{\partial H_1} = \frac{\partial \mathcal{L}}{\partial H_2} W_2^T$$
   对应的 Einsum 操作为：
   ```python
   # dH2 形状 (B, D), W2 形状 (D_in, D_out)
   dH1 = einops.einsum(dH2, W2, 'batch d_out, d_in d_out -> batch d_in')
   ```
   该计算同样是一次标准的矩阵乘法，其维度规模为 $(B \times D) \times (D \times D) \to (B \times D)$。计算量为 $2 B D^2$ FLOPs。
2. **关于权重参数的梯度（Weight Gradients）**：计算损失关于当前层参数矩阵的导数，供优化器更新权重：
   $$\frac{\partial \mathcal{L}}{\partial W_2} = H_1^T \frac{\partial \mathcal{L}}{\partial H_2}$$
   对应的 Einsum 操作为：
   ```python
   # H1 形状 (B, D_in), dH2 形状 (B, D_out)
   # 沿 batch 轴求和累加
   dW2 = einops.einsum(H1, dH2, 'batch d_in, batch d_out -> d_in d_out')
   ```
   其维度规模为 $(D \times B) \times (B \times D) \to (D \times D)$。计算量同样严格为 $2 B D^2$ FLOPs。

> **结论**：单层的反向传播计算量为 $2 B D^2 + 2 B D^2 = 4 B D^2$ FLOPs。**在深度神经网络中，反向传播的算力开销严格为前向传播的 2 倍！**

##### 6ND 缩放法则的物理本源

将单步训练迭代（一次前向 + 一次反向）的计算量求和：

$$\text{FLOPs}_{\text{step}} = \text{FLOPs}_{\text{fwd}} + \text{FLOPs}_{\text{bwd}} = 2 B P + 4 B P = 6 B P$$

如果将批次大小 $B$ 推广到训练全流程中消耗的 Token 总数量 $N$，整个大模型预训练过程所需的理论总浮点运算量即为著名的：

$$C \approx 6 N P$$

这就是在所有大模型缩放定律文献中作为公理引用的 $6ND$（在部分文献中用 $D$ 代表 Data Tokens，等同于此处的 $N$）法则的底层推导全貌。在基于自注意力机制的 Transformer 中，只要上下文序列长度 $S$ 处于常规区间（没有达到数十万超长上下文导致自注意力点积项 $S^2$ 压倒前馈投影层），由于全连接投影占据了绝对算力主导，$6NP$ 都是误差极小的精准估算模型。

#### 静态显存开销与优化器状态解构

明确了算力开销后，我们来精确核算显存（Memory Footprint）的静态消耗。在基于 BF16 混合精度与 AdamW 优化器的工业预训练中，显存开销主要由四部分构成：

1. **模型参数（Weights）**：以 BF16 格式存储，每个模型参数占用 **2 字节**；
2. **模型梯度（Gradients）**：以 BF16 格式存储，反向传播产出的梯度与参数维度完全同构，每个参数占用 **2 字节**；
3. **优化器状态（Optimizer States）**：
   - 优化器状态绝不能为了省显存而采用 BF16 存储，必须严格使用 **FP32**。因为动量累积和梯度的平方滑动平均涉及极小量的平滑更新，低精度舍入误差会导致优化方向产生严重漂移甚至发散；
   - 若采用老旧的 AdaGrad 优化器，它仅需要存储历史梯度的平方累加和（二阶动量），每个参数维护 1 个 FP32 状态，占用 $1 \times 4 = 4$ 字节；
   - 若采用标准的 **AdamW** 优化器，针对每一个权重参数，必须独立维护两个历史统计量：
     - 一阶动量（动量均值 $m$）：FP32 存储，占用 **4 字节**；
     - 二阶动量（方差平方均值 $v$）：FP32 存储，占用 **4 字节**；
     - 优化器状态总计占用：$4 + 4 = 8$ 字节/参数；
4. **动态前向激活值（Activations）**：每一层前向传播保存的中间张量，用于在反向传播时根据链式法则回算梯度。激活值大小与 Batch Size $B$、序列长度 $S$ 以及层数 $L$ 严格线性成正比。

> **结论**：在 AdamW 混合精度训练体系下，即使 Batch Size 压缩为 0，模型自身所占据的静态基础显存开销即达到：
> $$\text{静态显存} = 2 \text{ (参数)} + 2 \text{ (梯度)} + 4 \text{ (动量 } m) + 4 \text{ (方差 } v) = 12 \text{ 字节/参数}$$
> （若系统实现中包含一份显式同步的 FP32 主权重副本，则总静态显存为 $16$ 字节/参数；在讲师口述的核算模型中，按经典的 $2 + 2 + 4 + 4 = 12$ 字节/参数基准执行）。

#### 显存优化技术方案

在实际训练中，静态显存往往直接决定了硬件能容纳的最大模型尺寸，而动态激活显存则限制了训练能采用的最大 Batch Size。为了突破物理硬件的显存墙，必须引入两项关键的工程优化技术：梯度累积与激活检查点。

##### 梯度累积（Gradient Accumulation）

在大模型优化理论中，为了确保 SGD 或 AdamW 能够稳定收敛，必须让总批次大小（Total Batch Size）达到特定的**临界批次大小（Critical Batch Size）**。若批次太小，梯度的方差噪声过大，优化轨迹会剧烈震荡。然而，激活值显存随批次大小线性爆发，直接开大 Batch Size 会瞬间引发显存溢出（Out of Memory, OOM）。

梯度累积的破局思路极其简明：**在时间维度上切分批次**。
- 将一个庞大的全局批次在物理上切分成 $K$ 个微批次（Micro-batch）；
- 每次只将一个微批次送入 GPU 执行前向传播和反向传播，将计算得出的梯度原位累加到 `.grad` 张量中，期间**绝不调用** `optimizer.zero_grad()`；
- 当连续累加 $K$ 个微批次后，统一触发一次 `optimizer.step()` 更新权重，随后清零梯度。

这种方法使得峰值激活显存仅仅取决于微批次的大小，以多轮微批次串行计算的时间开销为代价，在有限显存上完美模拟了任意宏观大批次的优化稳定性。

##### 激活检查点（Activation Checkpointing / 梯度检查点）

在标准训练流程中，网络必须将所有层的全部前向激活值完整驻留在 HBM 显存中，直到反向传播执行到该层并完成求导后才能释放。对于深达数十层乃至上百层的大模型，激活值显存往往会数倍于模型参数自身。

激活检查点的底层思想是经典的**空间换时间（Rematerialization）**：在前向传播中，主动丢弃绝大部分中间激活值，仅在关键节点保留极少量的“检查点”激活值；在反向传播需要用到某层的激活值时，从最近的检查点出发，重新向前做一次局部的轻量前向计算来复现该激活值。

```text
全量存储 (标准训练):
  Layer 1 ----> Layer 2 ----> Layer 3 ----> Layer 4 ... (保存全部激活值, 显存 O(L), 重算 O(0))

无检查点 (极端重算):
  Layer 1       Layer 2       Layer 3       Layer 4 ... (仅存当前层, 显存 O(1), 重算 O(L^2))

根号 L 检查点 (平衡折中):
  [Check 1] ----> x ----> [Check 2] ----> x ----> [Check 3] (显存 O(√L), 重算 O(√L))
```

激活检查点通过在前向传播中周期性保留关键锚点层激活值、反向传播时局部重构中间值，在额外耗费少量计算的前提下大幅压低峰值激活显存。

PyTorch 提供了开箱即用的工具包装器 `torch.utils.checkpoint.checkpoint`。在微观层面，最典型的应用是线性层与 ReLU 组成的单元块：
- 在标准前向中，线性变换的输出（即 ReLU 前的预激活值）以及 ReLU 后的激活值都需要保存；
- 开启激活检查点后，彻底丢弃线性变换的中间输出，仅保留输入；反向传播抵达时，顺手重新执行一次极快的前向线性投影，就能立刻恢复中间信号。这一简单改动就能直接在激活层面上节省近 50% 的显存。

在宏观架构层面，存在三种权衡策略：
1. **全量存储（No Checkpointing）**：激活显存开销为 $O(L)$，无任何额外计算；
2. **极端重算（Zero Checkpointing）**：完全不保留任何中间层，每次求导都从第一层从头重算，激活显存降至 $O(1)$，但全局计算量退化为灾难性的 $O(L^2)$；
3. **理论最优划分（$\sqrt{L}$ Checkpointing）**：每隔 $\sqrt{L}$ 层设置一个保存锚点。此时激活值占用的显存规模被压缩至 $O(\sqrt{L})$，而为了重构激活值所付出的额外前向计算代价同样仅仅为 $O(\sqrt{L})$（在整网全流程中通常仅带来约 20%~30% 的额外前向计算开销），达成了计算时间与物理显存之间极佳的工业平衡。

### 经典系统容量估算推导演练

现在我们调集前文推导出的全部理论工具——$6ND$ 浮点核算、稠密硬件真实物理峰值、MFU 利用率系数以及 AdamW 静态显存模型，完整解答讲师在开篇抛出的两道标志性工程容量估算题。

#### 集群训练周期估算推导

> **思考题目**：使用配备 1024 张 NVIDIA H100 SXM GPU 的计算集群，在 15 万亿（$15 \times 10^{12}$）个 Token 的海量语料上，全量预训练一个包含 700 亿（$70 \times 10^9$）参数的稠密自回归大语言模型，预计需要耗费多少天？

##### 算法所需总浮点运算量推算

根据 $6NP$ 缩放法则：
- 模型参数量 $P = 70 \times 10^9$；
- 训练 Token 总量 $N = 15 \times 10^{12}$；
- 训练所需理论总算力：
  $$C = 6 N P = 6 \times (15 \times 10^{12}) \times (70 \times 10^9) = 6.3 \times 10^{24} \text{ FLOPs}$$

##### 集群硬件有效算力供给推算

- 单张 H100 SXM 的标称 BF16 半精度稠密物理算力峰值（除去稀疏水分后）：
  $$P_{\text{single}} = 989 \text{ TFLOP/s} = 989 \times 10^{12} \text{ FLOP/s}$$
- 集群拥有 1024 张 GPU，取当前大规模分布式系统优良的基准利用率 $\text{MFU} = 0.5$；
- 集群实际对外输出的有效算力为：
  $$P_{\text{cluster}} = 1024 \times (989 \times 10^{12} \text{ FLOP/s}) \times 0.5 = 5.06368 \times 10^{17} \text{ FLOP/s}$$
- 该集群持续运行一天（86,400 秒）所能交付的有效算力配额为：
  $$\text{FLOPs/Day} = 5.06368 \times 10^{17} \text{ FLOP/s} \times 86,400 \text{ s} \approx 4.375 \times 10^{22} \text{ FLOPs/天}$$

##### 最终训练天数结算

将总计算需求除以单日有效产出：

$$T = \frac{6.3 \times 10^{24} \text{ FLOPs}}{4.375 \times 10^{22} \text{ FLOPs/天}} \approx 144 \text{ 天}$$

推导出的 144 天与讲师课上口算给出的约 143 天完全吻合。这正是各大前沿大模型实验室在启动超万卡集群预训练任务前，进行预算申报与排期规划的精确底层推演逻辑。

#### 节点显存承载模型容量推导

> **思考题目**：如果手头只有一个单机节点，内插 8 块配备 80GB HBM3 高带宽显存的 H100 GPU（节点显存总计 640GB），配合 AdamW 优化器进行全参数训练。在通过梯度累积与充分的激活检查点将动态激活显存压制到忽略不计的前提下，该节点物理上能塞下的最大模型参数极限是多少？

##### 节点物理显存池汇总

- 单卡物理显存为 80 GB；
- 8 卡节点聚合的总物理显存池为：
  $$\text{Mem}_{\text{total}} = 8 \times 80 \text{ GB} = 640 \text{ GB} = 640 \times 10^9 \text{ Bytes}$$

##### 单参数静态显存消耗核算

在标准的 AdamW 混合精度训练配置下：
- 参数本身（BF16 存储）：2 字节/参数；
- 反向梯度（BF16 存储）：2 字节/参数；
- AdamW 一阶动量（FP32 存储）：4 字节/参数；
- AdamW 二阶方差（FP32 存储）：4 字节/参数；
- 每个模型参数对应的静态物理显存开销严格为：
  $$\text{Bytes/Param} = 2 + 2 + 4 + 4 = 12 \text{ 字节/参数}$$

##### 极限参数容量求解

设物理显存能容纳的最大参数总量为 $P_{\max}$：

$$P_{\max} \times 12 \text{ Bytes} \le 640 \times 10^9 \text{ Bytes}$$
$$P_{\max} \le \frac{640 \times 10^9}{12} \approx 5.333 \times 10^{10} \approx 530 \text{ 亿参数（53B）}$$

推导结果显示，在不借助跨节点模型并行（如张量并行 TP 或 ZeRO-3 状态分片）的纯静态极限下，单台 8 卡 H100 节点能够承载的模型参数上限约为 530 亿。这一推演直接印证了讲师课上提出的 53B 估算，让复杂的显存约束化为简明的算术确定性。
