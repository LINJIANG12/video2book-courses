# Agent 代理与会话式 RAG 问答

## 绑定工具的模型与调用指令

* **携带工具的模型（model_with_tools）**

    * > **定义**：`model.bind_tools(tools)` 的返回值，本质仍是一个携带了工具的 Runnable 对象，可以直接 invoke。

    * invoke 里只传一个用户的提问，写法与普通调用一致。

    * 绑定工具之后，模型会自动推理：这个问题是它能直接回答的，还是它没办法知道答案、要交给工具去处理的。

    * 返回值有两块：`resp.content` 是模型直接返回的内容；`resp.tool_calls` 是工具调用回调，可以理解为工具将要返回的内容。

    * 工具调用指令是一个 JSON 格式的字符串：通过 Tavily 这个搜索工具搜天气，里面写着要搜索的关键词，还有这条调用的 id。

| 对比项 | 问题一：中国的首都是哪个城市 | 问题二：北京的天气怎么样 |
| :--- | :--- | :--- |
| `resp.content` | 中国的首都是北京 | 空 |
| `resp.tool_calls` | 空 | 一条调用 Tavily 搜索天气的指令 |

* **模型只下指令，不执行**

    * > **注意**：`tool_calls` 只是一条"该去搜索"的指令，模型其实并没有真正去搜索。

    * 模型能根据用户的问题自动推理要不要调用工具，但只会给出调用工具的指令；真正把工具调起来，要靠代理（Agent）。

```text
用户提问
   │
   ▼
绑定了工具的模型（model_with_tools）
   │
   ├── 模型自己能答 ──► content 有答案，tool_calls 为空
   │
   └── 模型答不了 ───► content 为空，tool_calls 里出现
                        一条工具调用指令（JSON）
```

## 代理执行器与消息对象

* **代理执行器（agent_executor）**

    * > **定义**：由 langgraph 的 `create_react_agent(model, tools)` 创建的"工具调用器"，补上真正执行工具调用这一步。

    * 两个参数：模型和 tools；tools 本身是一个序列，即一组工具执行器的集合，最好的做法是把定义好的 tools 整体传入，不用重新造。

    * 走代理这条路后，`model.bind_tools` 那一行就不需要了，模型和工具都交给 `create_react_agent` 统一安排。

* **代理的调用方式**

    * invoke 的参数是一个字典：键固定叫 `messages`，值是 `("user", 问题)` 这样的元组；元组前加的 key 不是固定的，主要是为了后面取值方便。

    * 返回值也是字典：传进去的是什么键，就根据这个键去取返回值。

* **两种返回的消息对象**

| 对比项 | 模型自己能答的问题 | 需要动用工具的问题 |
| :--- | :--- | :--- |
| 返回对象个数 | 2 个 | 3 个 |
| HumanMessage（用户提示） | 用户的问题 | 用户的问题 |
| AIMessage | content 是答案，附带 token 用量信息 | content 为空 |
| ToolMessage（工具返回） | 没有 | 有，位于数组下标 2 |

* **取结果与企业判断**

    * 取工具结果用 `resp["messages"][2].content`：数组下标从 0 数起，第三个对象的 content 就是搜索引擎搜出来的真正答案。

    * 结果包含两部分：定义工具时指定了 `max_results=2`，每条结果带着来源 URL，是网页上搜到的英文描述。

    * 企业项目里只要加一个判断：AIMessage 的 content 为空，就去取 ToolMessage 里那个值；不为空，直接把 AIMessage 里面的 content 拿出来用。

    * > ⚠️ **易错点**：括号一定要配对，而且绝不能混进中文括号——一个中文括号、少一个中括号都会编译不过，检查半天才能找出来。

## RAG 的动机与整体流程

* **检索增强生成（Retrieval-Augmented Generation，RAG）**

    * > **定义**：一种增强型大语言模型的方法，通过引入额外的数据来实现。

    * 动机：大语言模型的数据来自互联网，尤其是谷歌、微软这些公司拿到的非常高质量、专门用来训练大语言模型的数据；公司内部的数据一般不会拿去训练大语言模型，模型压根没见过，所以单独一个大语言模型做不了公司内部数据的 AI 问答。

    * 引入额外数据的一种通用做法：用一个工具（本质是爬虫）自动去网络上把相关内容拿下来，比如某人写的博客、发布的论文；这不叫"爬"叫"加载"，由文档加载器（document loaders）完成。

* **五步思路**

    * 构建流程五步：加载数据、分割、存储、检索、整合生成——前四步是"知识入库"，最后两步是"问答"。

    * 问答的含义：用户提问先过检索器，把相关内容找出来，再把检索内容和提示一起交给大模型，答案基于引入的额外数据生成。

```text
加载文档（互联网上的 / 本地文本文档 / 关系型数据库）
        |
        v
切分：长文章切成一个个片段（每片最多 1000 字符）
        |
        v
向量化：用 Embedding 把每个片段变成向量
        |
        v
存储：向量存进向量数据库（向量空间）
        |
        v
检索器：用户提问先检索出相关片段
        |
        v
检索结果 + 提示模板 --> 大语言模型 --> 给出答案
```

* **要不要切割**

    * 看文章体量：一篇文章本来也就一两万字，不用切；十万字以上的大文章，才有必要切成一个一个的片段。

## 文档加载器 WebBaseLoader

* **网页加载器（WebBaseLoader）**

    * > **定义**：langchain_community 里现成的加载工具，负责把网页内容加载成文档；community 是一大堆工具的集合，网络搜索工具也出自这个包。

    * 数据的来路有很多种：本地数据库、本地的 word 文档或 PDF 文档、互联网上的一篇博客或论文；案例加载的是互联网上一篇讲大语言模型与 Agent 交互整合的英文长博客——不用在乎是英文，换成中文博客也一样。

    * 案例的动机：博客很长，里面有代码、图形，还引用了很多其他博客和论文，人从头看完要花特别多时间；交给 AI 之后，通过问问题直接找到想看的内容，效率大大提高。

### 参数 web_paths 与 bs_kwargs

* **web_paths：爬哪里**

    * 传一个字符串或序列化的字符串：允许一次爬一个网页，也可以爬多个网页——多个就放在一个列表或元组里，逗号隔开接着写。

* **bs_kwargs：怎么解析**

    * `header_template` 可以不传，真正要传的是 `bs_kwargs`：它接一个字典，透传给 BeautifulSoup（简称 BS4）——爬虫里专门解析 HTML 标签内容的解析器；安装 langchain_community 时会自动安装，导入 bs4 就能用。

    * 网页里是一个一个的标签，做 RAG 问答其实只需要文本：标题的文本、发布日期与作者的文本、正文的内容，所以要用解析器只解析需要的部分。

```python
loader = WebBaseLoader(
    web_paths=("https://…",),  # 要爬取的网页地址，多个网页用列表/元组
    bs_kwargs=dict(
        parse_only=bs4.SoupStrainer(
            class_=("post-header", "post-title", "post-content"),
        )
    ),
)
```

    * `parse_only` 表示"仅仅解析哪些内容"，解析器用 `bs4.SoupStrainer`；SoupStrainer 里按标签名筛的参数不用传，只要传 `class_`——类选择器。

    * 类选择器怎么找：在页面源代码里搜标题文字，看要取的内容藏在哪个标签里；BeautifulSoup 解析文本一般根据 id 或类选择器定位，这里没有 id，就用类选择器；怕单词写错，直接从源代码里复制那一段。

    * 标题在 h1 标签里，外层的类选择器是 post-header，标题本身是 post-title；只写 post-title 只会解析出标题，写 post-header 还能把标题下面装着发布日期、作者的 div 包进去——单独写 post-meta 去取那个 div 也行，两种写法都可以。

    * 正文被一个大 div 整个包起来，类选择器叫 post-content；它的结束标签在源代码里不好找，选中那一行用浏览器的"检查"，页面上立刻高亮定位，一眼看出这个 div 从头到尾包含了所有文章内容。

### 加载结果 Document

* `docs = loader.load()` 返回一个数组，长度只有 1——整篇博客就是一个文档。

* `metadata`：原数据，里面的 `source` 就是这篇文档的来源，即网址。

* `page_content`：文档内容，开头是标题，接着是作者、发布时间这些原数据信息，再往后是长长的正文，几万字肯定有。

* 文章这么大，不可能直接拿它去建向量空间，所以加载完紧接着做切割。

## 文本切割器 RecursiveCharacterTextSplitter

### 为什么切与分隔符

* **切割的必要性**

    * 切割对索引数据、以及把内容传递给模型很有用：不能把几万字的文章直接丢给模型，大块的数据很难搜索，而且不适合模型有限的上下文窗口。

    * 一篇 10 万字的论文，不可能把整个 10 万字作为一个整体放进向量空间；切成小块，针对小块建立索引、构建向量空间，再传递给大模型才有意义。

* **分隔符参数**

    * 构造切割器时第一个参数其实是分隔符，但没必要传：大部分情况下文本没有固定分隔符，按行切割也不合适——一行不一定是一句话；智能切割靠 chunk_size 和 chunk_overlap 两个参数。

### chunk_size 与 chunk_overlap

* `chunk_size`：每一个片段最多包含多少个字符；演示阶段故意设小到 20，正式使用调成 1000。

* `chunk_overlap`：允许相邻片段重复的字符数，为的是保证每一句话的完整性；演示设 4，正式调到 200 这个量级（100 也可以）。

* 重复值要跟着单词长度调：hello world 不够 20 个字符，切割器会把后面的 how 拉进来凑；下一片又从 how 开头，这个 how 就是重复的 4 个字符。写成 2 的话，how 这种三个字母的短词没法整体重复，只能拿两个字母做重复，就没有意义——要以单词为单位。

* 输出里一行不一定是一句话，它是一个片段：片段上限 20 个字符，一句话超过 20 也只能被切成两段；但切割器不会把一个单词从中间切开，thanks I'm fine、machine learning class 这样的完整句子都能保持完整。

### split_text 与 split_documents

* `split_text(text)`：传入字符串，切完得到一个数组——适合拿一小段文本先把切割器试明白再放进正式代码。

* `split_documents(docs)`：切割 Document 对象的列表，得到一个一个的片段——正式切割加载出来的文档用它。

* > ⚠️ **易错点**：手里是 Document 对象却调用 `split_text`，会报"预期是字符串或者字节数据，实际传入的不是"的错；切文本用 `split_text`，切文档对象用 `split_documents`。

## 向量存储与检索器

* **向量存储（Chroma）**

    * 存储调用 `Chroma.from_documents(splits, OpenAIEmbeddings())`：函数叫 from_documents，因为切割后的每一个片段就是一个 document，把它们传进去；第二个参数是做向量化的 embedding，采用 OpenAI 的。

    * > ⚠️ **易错点**：`OpenAIEmbeddings` 是一个类，要创建对象使用，后面一定要加括号。

* **检索器（Retriever）**

    * `retriever = vector_store.as_retriever()`：把向量存储变成检索器，以便后面根据用户的问题做检索。

## 提示模板与两条基础链

* **提示模板（ChatPromptTemplate）**

    * > **定义**：用 `ChatPromptTemplate.from_messages` 组装的消息模板：一部分通过 system 角色传给 AI，一部分通过 human 角色（用户角色）传入。

    * system 这段话给 AI 一个定位：你是一个专门做问答任务的助手；使用检索器检索出来的内容去回答问题；不知道答案就直接说你不知道；知道就最多用三句话回答，并保持答案简洁。

    * `MessagesPlaceholder("chat_history")` 用来记录提问和回答的历史：问答系统不可能只问一个问题；这个键名是自定义的，用别的字符串都可以，但要跟后面传参的地方保持一致。

    * 每一次的提问都从 human 的 `input` 变量传进去；invoke 时传一个字典，键写 `input`——模板里定义的变量名。

    * 文本内容都是英文的，提问时最好也用英文去问。

* **提问链（create_stuff_documents_chain）**

    * `chain1 = create_stuff_documents_chain(model, prompt)`：创建一个作用于多个文档的链，把多个文本整合进一条问答链；参数一是大语言模型 LLM，参数二是提示模板。

    * 它只是把模型和提示整合起来的"提问的链"，没办法帮我们做检索；链本身也可以理解为一个组件。

* **检索链（create_retrieval_chain）**

    * `chain2 = create_retrieval_chain(retriever, chain1)`：参数一传检索器，参数二把 chain1 传进去；chain1 负责问答，chain2 在问答的基础上增加了检索器——先检索，再做问答。

    * invoke 传的字典键是 `input`，值是问题；问 "What is task decomposition?" 最合适，因为这个问题正来自博客里的相关内容。

    * 打印出来的结果非常多：有 input、有 context、还有 answer；只要答案就按键取值 `resp["answer"]`。

## 首次运行的排错与答案验证

* **三个坑**

    * 坑一：报错"预期是字符串或者字节数据，实际传入的不是"——切割时把 `split_documents` 调成了 `split_text`，改过来就好；运行之前还要先把 OpenAI 的 API key 配好。

    * 坑二：一条提示说缺少某个环境变量——这不是报错，只是提示，而且那个环境变量根本不用，不用管它。

    * 坑三：报错说缺少 history——模板里写了 `chat_history`，但历史记录还没有去保存；先把涉及历史记录的部分注释掉，等历史功能补上再跑，问题就能先被回答。

* **答案是否真来自文档**

    * AI 的答案直接复制到原文里是搜不到的——它不可能照着原文给你回答；把答案放进翻译器翻译一下，对照着看即可验证。

    * 博客原文关于任务分解：思维链（CoT）已经成为在复杂任务中增强性能的标准提示技术——让模型一步一步地思考，利用更多的测试时计算，把困难的任务分解成更小、更简单的任务；可以把任务分成多个可管理的子任务，并对模型的思维过程做出解释。

    * AI 给出的答案：任务分解是将一个复杂的任务分解成更小的、更易于管理的部分或步骤的过程；思维链（CoT）和思维树（Tree of Thoughts）这样的技术被用于增强这一过程，分别允许详细的逐步推理和探索多种推理可能性，有助于管理复杂性并提高规划和解决问题的执行阶段的清晰度。

    * 这个答案比网页的中文直译更准确、更看得懂，而且紧跟着博客的内容；假设没有这篇博客，直接去问 OpenAI 同样的问题，得到的答案一定不是这样。

## 历史感知检索器

### 检索器的上下文难题

* 对人写好的博客提问，注定是答疑式、聊天式的，所以一定要有提问的历史记录；一般做法是构建链时用 `MessagesPlaceholder` 把问答记录传进去关联上下文，模型理解了历史，上下文就接上了——一般情况下这样做就够了。

* 但在这个场景里，光让模型理解上下文不够：查询检索器也需要上下文才能被理解，否则检索器自己就会出问题。

* 例子：张三先问"任务的分解是什么"，接着问"他有哪些方法可以做到"——人能理解"他"就是任务分解；大语言模型也一样，把聊天或问答的历史记录给它，它就能理解上下文。问题出在检索上：检索是由大模型生成一个检索指令去执行的，总不能拿"他有哪些方法"这句话当关键词直接扔进检索器做相似搜索——匹配不到，或者很难搜到想要的结果。

* **历史感知的检索器（history-aware retriever）**

    * > **定义**：能结合对话上下文，把引用了历史的问题改写成独立表述之后再去检索的检索器。

    * 解决方法：添加一个子链，拿最新用户的问题和历史聊天记录，在问题引用历史信息的地方重新进行表述——"他有哪些方法"要重新表述成"任务分解有哪些方法"；第一个问题的时候可能没有聊天记录，问到第二、第三个问题之后历史就攒起来了。

    * 子链的目的就一句话：让检索过程融入对话的上下文。

### 子链的指令与组装

* **system 指令（contextualize_q_system_prompt）**

    * 指令内容：给我聊天历史，以及最新的用户问题——这个问题可能会引用聊天历史中的上下文；请你改写出一个"独立的问题"，一个不依赖聊天历史也能被理解的问题；不要回答它！需要改写就转述改写，不需要就原样返回。

    * 这句话是给 system 的，是告诉 AI 大模型的。

* **组装三步**

    * 提示模板三件套：system 放 AI 的定位（上面的指令）；`MessagesPlaceholder("chat_history")` 放历史记录——键爱填什么填什么，但要跟传参的地方保持一致；`("human", "{input}")` 放用户最新的问题。

    * `history_chain = create_history_aware_retriever(model, retriever, retrieval_history_template)`：参数依次是大语言模型 model、检索器 retriever、提示模板；这就是一个子链。

    * 这个子链不直接用，后面要合并到一个大的链里；检索器已经加进子链，所以原来的 chain2 连同相关测试注释掉，只留 chain1——里面是模型，加上让模型理解上下文的那个模板。

## 会话历史与父链组装

* **会话历史的存取（get_session_history）**

    * `store` 是一个字典：以每一个会话的 id 作为键，以该会话所有的历史记录对象作为值。

    * `get_session_history` 按会话 id 取历史：这个 id 已经在 store 里，就直接返回对应的记录；不在，就新建一个 `ChatMessageHistory` 存进去再返回。

    * `ChatMessageHistory` 来自 langchain 的 community 包。

* **父链（chain）**

    * `chain = create_retrieval_chain(history_chain, chain1)`：`create_retrieval_chain` 的第一个参数除了检索器，也可以是一个 Runnable——这里传子链，因为子链本来就是干检索的；第二个参数是 chain1。

```text
用户提问 input
    |
    v
父链 chain（create_retrieval_chain）
    |
    +--- 子链 history_chain（历史感知检索器）
    |        输入：聊天历史 chat_history + 最新问题 input
    |            |
    |            v
    |        模型把问题改写成"独立问题"
    |            |
    |            v
    |        检索器 retriever --> 相关片段
    |
    +--- chain1（问答链）
             输入：检索到的片段 + 提示模板
                 |
                 v
             模型 --> answer（最多三句话的简洁答案）

最外层再包一个 RunnableWithMessageHistory：
按 session_id 存取会话历史，自动接上 chat_history
```

* **会话化包装（RunnableWithMessageHistory）**

    * > **定义**：包在整条链最外层的会话历史包装器：先创建一个可调用的 Runnable 对象，之后用它去 invoke，得到一个真正意义上完整的、包括传参的链。

    * 它按 session_id 存取会话历史，自动接上 chat_history。

| 参数 | 传什么 | 要注意什么 |
| :--- | :--- | :--- |
| 第一个参数 | 要包装的链（上面的父链 chain） | 接的是一个 Runnable，也就是一条链 |
| `get_session_history` | 按会话取历史记录的函数 | 千万不要加括号——传函数本身，不是在这里调用它 |
| `input_messages_key="input"` | 用户输入问题的键 | 要跟模板里 human 的变量名保持一致 |
| `history_messages_key="chat_history"` | 保存历史记录的键 | 要跟模板里 `MessagesPlaceholder` 的键保持一致 |
| `output_messages_key="answer"` | 返回结果的键 | 之后取答案就按这个键来取 |

    * > ⚠️ **易错点**：`get_session_history` 只传函数名，不要加括号；加了括号就成了在这里把函数调掉，而不是把"按会话取历史"这个能力交给包装器。

## 两轮会话实测与上下文边界

* **调用方式**

    * invoke 要传两个东西：第一个是字典，键 `input`、值是用户的问题；第二个是 config——不用提前创建，直接写在调用里：`configurable` 键后面跟一个字典，字典里定义 `session_id`，会话 id 随便写。

* **两轮提问的正例**

    * 第一轮问 "What is task decomposition?"：答案与最初单轮提问时一致，把任务分解的定义讲清楚了，没问题。

    * 第二轮问 "What are common ways of doing it?"：这个 it 代表什么？人知道它指的就是任务分解，整句是"任务分解有哪些常用的方法"；如果它没有上下文，答案肯定乱七八糟。

    * 第二轮的答案第一句就是"执行任务分解常用的方法包括"；对照博客，三种方法都在：任务分解可以通过 LLM 完成，配一个简单的提示（比如"实现某件事有哪些步骤"）；可以通过特定于任务的指令（比如"写一个故事大纲"）；还可以结合人工输入来指导分解过程。

    * > ⚠️ **易错点**：两轮提问的 `session_id` 必须一致——必须在同一个会话之内，它才能识别"它"指的是什么；把 id 改了就根本识别不到。

* **反例：换一个会话 id**

    * 把第二个问题换到另一个会话（只改 session_id 这一处）：AI 给的答案是"我不知道，根据你提供的上下文，无法得到这个问题的答案"——新会话里没有前面那段聊天历史，它理解不了"它"指什么。

    * 第一个问题不受影响：它不依赖历史，照样答得出来。

    * 历史记录是绑定在会话 id 上的：id 一换，上下文就丢了。

* **应用场景**

    * 例：专门分析学校里每个学生写的论文——论文交给 AI 处理完之后，问一些非常核心的问题；如果答案是错的，大概率是论文本身有问题，再去细看论文到底错在哪；这是非常快速、高效地帮我们解析论文、解析文章的方式。
