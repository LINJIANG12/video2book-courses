# Harness 工程总论：起源、定义与六层架构

## 驾驭工程：定义与词源

   * **驾驭工程（Harness Engineering）**

       * > **定义**：一种以智能体可靠执行为目的的系统工程方法，是智能体开发的一种新工程范式、一种新的智能体架构。

       * 词源：harness 直译为马具、缰绳——缰绳控制奔跑中千里马的方向与速度，马具负责负载、提供拉力；用在这里就是控制智能体给出正确回答、让它稳定地长周期执行。engineering 与 prompt engineering（提示词工程）、context engineering（上下文工程）是同一构词法。

       * 定位：不是一门技术，也不是一种智能体的架构方案，而是智能体开发过程中的一种工程方法；"你会不会 Harness engineering"这种问法本身就不对。

       * 实现手段：通过设计模型外部的上下文、工具、运行时、权限、约束、验证、反馈、持久状态，把大模型那种带不确定性的内容生成能力，转换成可操作、可控制、可恢复、可审计、可持续改进的任务执行能力。

       * 必要性：大模型最底层是概率计算，回答与生成天然带不确定性；企业落地交付时，领导、客户、消费者都不接受"因为大模型有不确定性，所以智能体不准确"这种甩锅，必须靠这套工程方法把"碰运气"变成可控的执行能力。

## 智能体构成等式：Agent = Model + Harness

   * **等式含义**

       * > **定义**：在智能体工程里，除了模型之外的其他所有内容，统称为 Harness。

       * 出处：这个等式流行于 DeepSeek Harness 在 GitHub 上的项目首页和 LangChain 官网。

       * 范围：怎么控制模型、怎么操作模型、怎么让任务可恢复、可审计、可持续改进、可持续稳定执行，统统属于 Harness；通俗地说，智能体工程系统里除了模型本身之外，几乎所有决定它能不能稳定交付的东西都是 Harness。

   * **概念的宽度**

       * Harness 是很宽泛的、广义上的概念，同一个 Harness 各家有各家的技术实现：LangChain 团队用 LangGraph、LangChain 加 DeepAgents 来实现；OpenAI 有 Agent SDK；Claude 有 Claude Agent SDK；阿里巴巴有 AgentScope 这个框架；DeepSeek 用插件的方式实现；腾讯 CodeBuddy 也有自己的一套技术。

       * > **易错点**：Harness 工程不代表某一个技术——它只是智能体一种新的开发方式、一套工程化方案与工程化架构的名字。

## 概念命名时间线

```text
2025 年及以前   agent loop、eval harness、上下文工程、提示词工程已在用，
                但没人给这种新的智能体架构统一命名
2026-02-05     Mitchell Hashimoto 的博客第五章出现 Harness 一词
2026-02-11     OpenAI 发博客跟进，把概念扩展到整个智能体架构
2026-03-24     Anthropic 博客：Harness Design for Long-Running
               Application Development（长周期任务开发中 Harness 如何设计）
2026-04-08     Anthropic manager agent 博客：会话管理、智能体管理、
               子智能体，以及解决工具执行环境的 sandbox
2026 年中后期   Harness Engineering 成为全行业智能体工程的共同方法论
```

   * **命名节点**

       * Harness 一词正式出现于 2026 年 2 月 5 日 Mitchell Hashimoto 博客的第五章；六天后的 2 月 11 日，OpenAI 发博客跟进，标题里就是 Harness Engineering，把这个词扩展到整个智能体架构。

       * Anthropic 两度跟进：3 月 24 日发文谈开发长周期任务时 Harness 如何设计；4 月 8 日在 manager agent 一文里重点谈 Harness 的详细设计——会话如何管理、智能体如何管理、子智能体，以及 sandbox；sandbox 是 Harness Engineering 里解决工具执行环境的重要东西。

       * 到 2026 年 5 月份之后，几乎全球所有的公司都统一认为：最新的智能体开发应该优先采用 Harness Engineering。

   * **概念前身**

       * 2025 年及以前，agent loop、eval harness、上下文工程、提示词工程这些词都已经在用，只是这种新智能体架构没有统一命名。

       * > **易错点**：不要误以为 Harness 工程是 2026 年 2 月之后才有的——2025 年下半年或年底，OpenAI、Anthropic 以及国内的 DeepSeek、千问、腾讯就已在不断探讨、改进自己的智能体与 RAG 项目，只是当时还没被命名为 Harness。

   * **趋同而非同源**

       * Claude Code、Codex、OpenClaw、Hermes Agent、DeepSeek 的 Harness（DSH）都是体现 Harness Engineering 思想的产品，但它们并非由 Mitchell 的博客启发，也不是建立在同一个 Harness 技术或框架上。

       * 实际过程：每家公司在内部自行探索、采用不同技术，在模型工具化、长任务、长上下文上逐渐形成趋同的架构——这个趋同架构到 2026 年 2 月之后才有了统一的名字。

## 代表产品的 Harness 化节奏

   * **质变窗口**

       * 全球热门智能体发生质的飞跃集中在 2026 年 1 月到 3 月；各家底层技术不一样，但都往 Harness 工程一个方向趋同，此后企业在开发定制化智能体时一般也优先采用 Harness 工程方式。

   * **产品节点**

       * Claude Code：2025 年 2 月就真正出来，但当时普遍觉得不好用；2026 年 2 月左右的新版本多了 `hooks`、`Skills`、`sandbox` 等，明显好用起来，采用的就是 Harness Engineering 工程方式。

       * Codex：同样在 2026 年 2 月左右突然特别好用，底层基于 OpenAI 自家的 Agents SDK 框架。

       * OpenClaw：最早成熟起来的 Harness 产品之一，2025 年年底就开始火，2026 年 1 月火得一塌糊涂，2 月更新、3 月继续更新后越来越好用。

       * Hermes Agent：2026 年 4 月出现，有后发优势，有人认为比 OpenClaw 还好用，各有所长。

       * DeepSeek Harness：2026 年 4 月中旬左右决定启动，8 月开始公测，历时四个月，采用的技术与前面产品完全不一样。

## 大模型就业的两个方向

   * **方向划分**

       * 从 2026 年 1 月起，大模型就业市场只分两个方向：大模型工程化落地方向、大模型算法研究方向；不管从事什么大模型岗位都在这两者之内，两个方向对学历、论文的要求不一样。

| 对比项 | 工程化落地方向 | 算法研究方向 |
| :--- | :--- | :--- |
| 做什么 | 对已有基座模型做二次开发、二次训练，与业务结合完成落地：智能体、RAG、微调，还包括知识图谱结合大模型、GraphRAG、调用 YOLO 这类模型做图像处理 | 大模型算法底层研究：写算子，优化大模型及其训练过程，优化大模型的推理过程 |
| 学历门槛 | 最低本科就可以 | 最低 985 硕士起步，且必须科班——计算机、数学两个大专业里的才算，其他不算；论文只看顶刊，花一两千块找人写的论文没用 |
| 典型岗位 | 大模型应用工程师、大模型应用算法工程师、AIGC 工程师、大模型工程师 | 大模型算法工程师、大模型算法专家、多模态算法工程师等 |
| 供需情况 | 岗位数量最多，但找工作的人数也会越来越多 | 急缺人，到现在为止最好找工作的方向——能满足要求的人太少 |

   * > **易错点**：不要认为大模型工程化落地方向不需要学任何算法——这个说法是错的。

   * 用 YOLO、卷积神经网络做图像处理的岗位不属于大模型算法研究岗位，而是属于大模型工程化落地方向。

   * **趋势与持续学习**

       * 工程化落地方向的岗位数量肯定最多、会越来越多，但找工作的人也会越来越多，这个行业一定会出现内卷；开始时间无法预测——2027 年、2028 年还是 2030 年之后开始，说不准。

       * 程序员工作到什么时候就要学到什么时候：中断学习大概 3 年左右就会被淘汰；这是整个 IT 行业的现实所决定的，去做网络安全等其他方向同样要不断学习。

       * 算法研究方向未来有可能转向具身智能、世界模型等新热点；但十几二十年来，底层的机器学习、深度学习算法（神经网络那一套）没有变，变的是网络拓扑架构——YOLO 最早 2017 年左右出现、2018 年之后才慢慢好用，用的仍是神经网络。

       * 做算法研究绕不开数学：重要的机器学习、深度学习算法的数学推导都可能用到求导；梯度下降必用，尤其线性模型的推导都用梯度下降来做。

       * 找工作这件事有时候也确实看运气。

## 求职实操：关键词、城市与薪资

   * **岗位检索方法**

       * 招聘平台（Boss 直聘、智联、拉勾等）上的岗位名字由 HR 各写各的，没有国家或行业标准，不能按岗位名字去搜。

       * 典型误导例：岗位名叫"大模型算法工程师"，点进去写的却是"基于 LangChain、LlamaIndex 框架开发 RAG 智能体"——真算法工程师要进公司做模型预训练、算法优化。

       * 正确做法：一律用"大模型"三个字作关键词去搜，看岗位描述和任职要求是否符合所学，符合就投，不用在乎岗位叫什么名字。

   * **城市分档**（按大模型找到工作的数量排，不是城市大小）

       * 一线（岗位数量非常多）：北京最多，其次上海，然后深圳，然后杭州。

       * 二线：重庆、成都、南京、广州、苏州，以及武汉、长沙、西安等；广州的岗位数量还没有重庆、成都多，与成都差不多（佛山并入广州算）；此外青岛、贵阳、天津、郑州等省会与内地城市也有岗位。

   * **薪资看中位数**

       * 一线城市：低于 25K 的大模型相关岗位非常少，大部分 30K 以上，中位数 30K–40K；40K 以上、80K 的都只出现在北京、上海、深圳、杭州。

       * 二线城市：中位数大概 18K–25K；也有 12K、15K、20K 的——12K 实例在西安，26K 实例在南京（34 岁、专升本、多年 Java 背景）。

       * 评价薪资只看正态分布与概率（中位数），不盯最高也不盯最低；Boss 上只看到 15K 左右属正常——Java 里还有 6K、7K 的，要学会去谈薪资。

## 智能体架构的四阶段演进

   * **阶段一：调 API（2022–2023）**

       * 背景：GPT-3 与 3.5 刚出，调用其 API 并执行一些外部代码，完成比较简单的智能化操作。

       * 边界：这个阶段智能体还没有真正出现。

   * **阶段二：单一 ReAct 智能体（2023–2024）**

       * 机理：推理 → 工具调用 → 观察 → 再次推理的循环递归，用递归循环自主行动，是智能体的第一版雏形。

       * 地位与框架：ReAct 是该时期主流架构（Plan 这类方案不是主流）；框架以 LangChain 为主，或用 LlamaIndex。

       * 局限：单个智能体难以承担长周期的复杂任务——做翻译、答简单问题可以，财务分析、造价预算这类长流程复杂任务不行；当时产品普遍功能不强、体验一般。

   * **阶段三：工作流（Workflow）+ 多智能体（Multi-Agent）（2024–2025）**

       * 特征：流程编排、状态持久化、角色分工与委派。

       * 代表：平台是 Dify、扣子（Coze）——本质是基于 Workflow 架构的智能体平台；开发框架典型是 LangGraph，其中多智能体有两个库——LangGraph Supervisor（主从结构）、LangGraph Swarm（网络结构）；2023 年最早火的多智能体框架是 AutoGen。

       * 局限：编排能力仍不足以保证安全、正确、可恢复的长周期运行；该时期只有上下文工程（上下文压缩也有），没有考虑安全边界、工具执行环境、沙箱问题，没有 Skills，上下文断层也没有解法。

   * **阶段四：Harness Agent 架构（2025 年底–2026）**

       * 组成：Agent Runtime（智能体运行时）+ 上下文工程 + 工具 + 会话 + memory + Skills + sandbox + 人工介入 + 评估。

       * 目标：让智能体长周期、稳定、可靠、准确地完成所有指令。

   * **演进关系：进化与包含，不是淘汰**

       * 四个阶段不是淘汰关系，而是进化关系、包含关系，一次达尔文式演化：workflow 加多智能体进化到了 Harness 里面去，但 Harness 里照样用 workflow、一定有多智能体，最早期的 ReAct 也没被替代。

       * 每个阶段都是在补上一阶段的短板；节奏记法：2025 年智能体的重心是流程编排和多智能体，2026 年的重心就是 Harness engineering。

       * 两个要点：大模型编程方向技术更新迭代快，不能拿去年学的东西直接应付今年的面试；2026 年要搞懂智能体核心一共分几层、每一层怎么做，理论与实战都要会。

```text
Harness Agent：不丢弃旧模式，全部纳入统一运行环境
├── ReAct              作为循环基础
├── Workflow           控制确定性流程
├── Multi-Agent        完成任务分工与并行执行
├── Session 会话       以会话为单位保存历史与上下文
├── Memory / Skill     长期记忆与技能
├── Sandbox            限制执行环境
├── Approve            控制高风险操作
└── 评估评测 + 日志轨迹  支持审计与持续改进
```

## 三大工程的包含关系

```text
驾驭工程（Harness Engineering）—— 对整个智能体系统做工程化
└── 上下文工程（Context Engineering）—— 对整个输入环境做工程化
    └── 提示词工程（Prompt Engineering）—— 对指令做工程化
```

   * **包含而非并列**

       * 智能体项目最重要的三大工程——提示词工程、上下文工程、驾驭工程——不是替代关系、不是并列关系，而是典型的包含关系：驾驭工程天然包含上下文工程，上下文工程包含提示词工程。

       * 验证逻辑：系统提示词和用户输入的提示词都属于上下文的一部分，所以提示词工程属于上下文工程的其中一部分；驾驭工程要保证智能体长周期稳定执行，就必须做上下文的摘要、剪裁、压缩，所以上下文工程是驾驭工程里必做的其中一小部分。

       * 驾驭工程除上下文工程外还要做：约束、权限控制、反馈回路、沙箱隔离、可持续的评估。

       * 提示词工程的内容：把提示词按标准化结构写好，加 few-shot、案例演示、思维链引导——最终写出来的提示词仍然属于上下文。

| 工程 | 工程化的对象 | 要解决的问题 |
| :--- | :--- | :--- |
| 提示词工程 | 指令 | 怎么给智能体合适的指令：标准结构、few-shot、案例、思维链 |
| 上下文工程 | 整个输入环境 | 组织指令、工具执行结果、模型决策结果等；防上下文爆炸，保长周期稳定运行 |
| 驾驭工程 | 整个智能体系统 | 约束、权限、验证、反馈、恢复、评估等系统级问题 |

   * 三者最大的区别：针对的目标对象不一样——提示词对指令做工程化，上下文对输入环境做工程化，Harness 对整个智能体系统做工程化。

## 六层核心架构

```text
第六层  约束与恢复    出错不崩、越权可约束、失败可恢复
第五层  评估与观测    不只看最终输出，更要看中间过程
第四层  记忆与状态    记忆不断层，无需每轮全量检索历史
第三层  执行编排      动态拆解复杂任务，边执行边做决策
第二层  广义工具系统  工具、Skill、MCP 的整体工程化
第一层  上下文精细化  每轮看什么、不看什么、如何压缩
```

   * **结构来源**

       * OpenAI、Anthropic、LangChain、DeepSeek 等顶流团队的产品形态、技术栈、服务对象各不相同，拆开看里面的组件却惊人相似——"让一个智能体在真实世界里稳定地工作"这个命题，天然推着所有人往同一个方向收敛。

       * 一个成熟的 Harness 大致分为六个核心组件，称六层（六层、六个组件的说法都可以）；六层自下而上环环相扣，整个智能体具备这六层，才能说采用了 Harness engineering 的技术架构与工程化方案。

### 上下文精细化

   * 任务：对上下文进行精细化的过滤和总结。

   * 解决的问题：模型每一轮到底应该看到什么信息、不应该看到什么信息——每轮调用模型时传什么、不让模型看什么，这就叫精细化；以及历史信息太长了怎么压缩、怎么检索。

### 广义工具系统

   * > **定义**：围绕工具的一整套工程化体系，不是简单地给智能体加几个工具函数。

   * 覆盖的工程问题：工具列表如何分配、工具如何执行、执行环境是什么、执行过程中会不会报错、报的错有没有统一的解决方式——都要给出统一的工程化解决方案。

   * "广义"的含义：归入这层的不只是工具，还有 Skill——网上别人写好的 Skill 可能用 Java、Python、Go 等不同语言，智能体必须为所有这些 Skill 提供运行环境。

   * 参数风险：工具参数可能而且大概率由模型基于上下文推理生成（少部分参数可直接从上下文提取），生成值不保证正确，直接拿去调工具就有可能报错。

   * 解法：在模型生成工具参数之后、调用工具之前加一道判断；连接 MCP 也一样——模型生成调用参数这一步完全可能出错，同样需要工程化处理。

### 执行编排

   * > **易错点**：执行编排不等于 workflow——不能把 workflow 那种固定流程当成 Harness 工程里的编排。

   * 要求：把任意复杂任务动态地拆解成可执行的流程，既不能流程想一步做一步，也不能把流程固定成死的。

   * 不能写死的原因：流程一旦固定是死的，智能体的功能边界、能力边界就被限定死——比如规定一个审批流程，它就只能做审批，其他都不能做，能力无法通用化。

   * 执行中动态决策的内容：先做什么、后做什么，什么时候做转交、什么时候调工具、什么时候等待用户确认、什么时候结束任务。

### 记忆与状态

   * > **定义**：保证智能体的记忆不出现断层，同时不需要每一轮都重复加载、查询整个完整的历史记录。

   * 必须记住的信息：当前规划执行到哪里了、用户上一轮做了什么、这个代码仓库原来做过什么——智能体不能每一轮都像第一次见到用户和代码仓库一样重新开始。

   * > **易错点**：每条指令都对长期记忆做一次全文检索、语义检索，不是不行，而是缺点很大——每条指令先耗时一秒到两秒去检索，智能体还没开始运行，用户每问一句先等两秒，体验极差，直接违反可交付要求。

   * 应对面试提问"为什么没对长期记忆做完整的语义检索和全文检索"的正确答案：可以检索，但应该只在极个别问题、极个别任务上检索，大部分情况不用检索；因为用户不但要准确率高，还要快。

### 评估与观测

   * 要求：智能体不能只看最后有没有输出，还要观察它中间做了什么、为什么这样做。

   * 验证：结果是不是对的、有没有验证过。

### 约束与恢复

   * 前提：智能体不可能永远是对的——可能调工具调错、传错参数，可能访问的路径或数据越权，可能陷入死循环，可能工具执行失败（比如网络断了），可能测试不通过，甚至可能遇到沙箱不可用。

   * 原则：遇到这些问题不能让整个智能体直接崩掉；智能体报错是正常现象，要确保它报错了可以让它恢复、访问权限越界了可以及时对它进行约束。

   * 外部依赖背景：智能体往往要和外面很多系统打交道——通过 MCP 和 Java 系统对接、通过 A2A 协议和另一个智能体对接、调 Skill 访问远程服务；程序写得再好也可能网络出错，工具写得再好参数也可能出错。

## 可交付：六层的共同落点

   * 六个核心全部围绕智能体项目的长周期稳定执行；"落地"的意思就是可交付，可交付的标准是领导满意、消费者满意、大家都满意。

   * **面试考察方式**

       * 面试官不单独问概念，而是盯着项目细节问：工具调用报错了如何解决？数据安全如何解决？高并发的问题如何解决？用户和租户的隔离应该怎么解决？智能体中出现记忆断层应该怎么解决？

       * 项目里有这些体现，才说明是可以落地和交付的项目，而不是一个 demo 级别的项目。

   * **用户体验三条**

       * 时间不能太慢，但必须有信息不断输出——执行一秒、两秒、三秒可以接受，但不能干等着：Claude Code 写代码 30 秒甚至一分钟能接受，前提是过程中不断提示写到哪一块代码、写了哪些代码、做了什么事情。

       * 写错了要能自己恢复——代码写错了或某个地方写错了，它自己能找到错误在哪里，然后解决这个错误。

       * 复杂业务要能看到执行步骤——先做哪一步、再做哪一步，每一步的顺序和步骤都看得到。

   * 背后的技术细节：权限控制、数据的安全边界、用户的隔离。

## 架构思想与框架选型

   * **思想属性**

       * Harness engineering 是一种架构思想、一种工程思维，不等同于任何一个智能体开发框架。

       * 基于 Harness engineering 架构的开源框架：DeepSeek Harness、Claude Agent SDK、OpenAI 的 Agent SDK、LangChain 团队的 DeepAgents、阿里巴巴的 AgentScope-Harness——它们不是普通的智能体框架。

   * **两条实现路径**

       * 用大厂现成开源框架：代码写得少；大厂框架经过很多个版本的迭代，稳定性也比较高，不用担心开发的智能体总是报错。

       * 从零自研、不用任何框架也可以，但要先掂量两个条件：一是团队人要多、技术要非常强——完整实现 Harness engineering 的代码量少则三四万行，多则十万行以上；二是真正上线交付的时间要比较长——DeepSeek 团队 2026 年 4 月中旬启动、8 月公测，历时四个月，且砸了很多钱、投入很多人。

   * **vibe coding 的边界**

       * 过于复杂的代码用 vibe coding 交付的可能性、可交付的概率越来越低：技术方案是它随机设计的、代码看不懂、是否重复也不知道；它经常重复造轮子——五天前写好的公共模块，今天写代码时再重新写一遍。

       * vibe coding 最适合程序员去用，效率大大提高；非程序员用它一次性生成整个项目（十万行、二十万行代码），不做规范、不做代码审查、不做测试，结果各种 bug、交付不了。

   * **开源协议**

       * 上述框架全部开源，协议为 Apache 2.0 或 MIT；符合这两种协议的在国企也可以用，除非负责人特意说某个不让用，那可以选阿里 AgentScope-Harness 或 LangChain 团队的 DeepAgents。

       * > **易错点**：LangChain 这个框架本身不是 Harness engineering 的，LangGraph 也不是——别把"用了 LangChain"等同于"做了 Harness"。

## 多智能体辨析与七条判断标准

   * **多智能体不等于 Harness**

       * Harness engineering 不等于多智能体：多智能体实际上是 Harness 的其中一种能力。

       * 单智能体系统只要有高质量的工具系统、自动验证、安全约束、会话恢复、完整的评测，即使没有采用多智能体也属于 Harness engineering 架构。

       * 反例：简单启动十个智能体，但没有任务边界、没有权限隔离、没有结果验证、没有状态一致性、没有冲突处理——即使用它们完成很复杂的项目，也不能称之为 Harness engineering。

       * 大部分情况下，基于 Harness 架构的智能体往往都是多智能体。

       * > **易错点**：别把"堆了几个 Agent"当成"做了 Harness"——判断的锚点是约束、验证、恢复、评测这些工程能力，不是智能体的数量。

   * **七条判断标准**

       1. 智能体是否自主获取了必要的上下文；
       2. 是否有结构化的工具；
       3. 系统是否机械地验证结果；
       4. 高风险操作是否有权限控制；
       5. 长周期任务是否持久化，且可以恢复、可以继续、还可以自动动态规划；
       6. 失败是否能够被记录下来，同时可以恢复，还可以加入回归测试；
       7. 更换模型之后，系统能力是否大部分仍然成立。

       * 第七条最容易露馅：换一个好一点的模型性能突然变好、换一个差一点的模型性能就变得非常差，那就要怀疑——真采用了 Harness engineering，只要模型属于中上水平，效果其实都大差不差。

   * > **提示**：不少中小公司的智能体团队、AI 团队负责人自己都不知道什么叫 Harness engineering，也不知道如何判断自己的项目符不符合——这套判断方法要学扎实。
