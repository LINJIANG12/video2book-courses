# 工具系统、执行编排、记忆状态与约束恢复

## 沙箱与执行环境

### 沙箱的分类与实现

   * **沙箱（Sandbox）**

       * > **定义**：给工具调用提供隔离执行环境的文件后端，把宿主机器隔离在工具的活动范围之外。

       * 没有沙箱后端时，工具调用会变成模型直接操作宿主机器，风险很高；所谓宿主，就是运行智能体的那台服务器。

       * 沙箱解决五类问题：文件越权、命令越权、环境污染、依赖混乱、故障不可恢复，最终目的是让智能体长周期稳定运行。

       * 沙箱都被实现为文件后端（Backend）：这是 LangChain 团队的方案，backends 有很多种，沙箱是其中在 Harness Engineering 中用得最多的一种。

       * 自定义套路：写一个类继承 `BaseSandbox` 父类并重写函数，代码里凡带 `@override` 标记的函数都是在重写父类。

       * > **注意**：企业项目大概率用自建远程沙箱；第三方公司提供的远程沙箱服务被认为不安全、有风险，国内公司一般宁可自己在服务器上用 Docker 搭。

   * **远程沙箱**

       * 基于自己服务器上的 Docker 容器构建，实现类 `OpenSandboxBackend` 继承 `BaseSandbox`。

       * 需要重写的函数：`id`（每个沙箱的唯一标识，用于管理沙箱）、`execute`（执行脚本和命令）、`download_files`（文件下载）。

   * **本地沙箱**

       * 实现类 `LocalShellBackend` 继承同一个父类 `BaseSandbox`，重写的函数更多：`id`、`execute`，外加文件列表 `list`、读 `read`、写 `write`。

       * 仅这一个本地沙箱后端的代码量就有六七百行、接近上千行，实现并不简单。

| 对比项 | 本地沙箱 | 远程沙箱 |
| :--- | :--- | :--- |
| 隔离对象 | 本地某个目录 | 自己服务器上的 Docker 容器 |
| 安全性 | 一定比不过远程沙箱 | 更高，企业大概率用它 |
| 使用占比 | 约 20% 的场景 | 大部分场景 |

   * 个人电脑上的编码工具（如 Codex、Claude Code）用的就是本地沙箱；本地沙箱仍约占两成场景，并非没有用武之地。

### 沙箱内的边界控制

   * **命令黑名单与白名单**

       * 黑名单列出绝对不允许执行的命令；白名单划定允许执行的范围，只有列在里面的命令才可以用；两者都定义为列表。

       * 命令在执行前要做安全性检查；白名单、黑名单当时写死在代码里、未配置化，更好的做法是放进配置文件、运行时加载。

   * **工作目录边界**

       * 智能体只能在规定的工作目录内活动，超出 `self.root` 目录之外绝对不允许访问；工作目录内的 skill、policies 等目录可以访问、写文件、操作。

   * **路径映射与虚拟路径**

       * > **易错点**：路径映射这一步容易搞错——智能体操作的 `/project/skills` 这类路径，不会真的去宿主根目录下找，而是到沙箱规定的根目录中找；做完限制后必须提供映射，否则智能体根本找不到真正的文件。

       * 虚拟路径就是以沙箱为根目录的路径：既可以用一个 Docker 容器当沙箱，也可以把服务器上的一个目录（或 Windows 本地目录）当作虚拟沙箱、虚拟路径来用。

       * 参数或命令中一旦匹配到绝对路径即拒绝访问，必须采用虚拟路径。

   * **本地沙箱后端的覆盖面**

       * 工作区隔离、文件路径映射、文件相关操作、命令执行、安全、跨平台，这些能力在本地沙箱后端里全部落地。

## 工具调用链路与中间件治理

### 完整调用链路

```text
模型决策要调某个工具
   │
   ▼
选择工具 ──► 模型生成参数
   │
   ▼
参数校验（中间件清洗）
   │
   ▼
权限判断（这个智能体能不能执行这个工具）
   │
   ▼
真正执行（进入文件后端 / 相关工具）
   │
   ▼
对结果进行结构化
   │
   ▼
返回模型上下文，继续推理
```

   * 结构化的不一定是真实成功的结果：工具没调成功，同样会得到一个结果并被结构化，前置还有各种权限控制和参数校验把关。

   * 无论成功还是异常，结果最后都必须返回模型上下文——智能体内部的 ReAct 循环一直保留，工具执行完回到上下文继续推理。

### 工具治理组件

   * **工具不能裸奔**

       * > **定义**：工程价值较高的工具都必须通过中间件（Middleware）治理，覆盖参数、错误、权限与限制，不允许不加治理直接调用。

   * **四个中间件加一个追踪器**

       * 工具执行之前的参数清洗中间件。

       * 工具报错之后，把错误信息转换成结构化 ToolMessage 的中间件。

       * 工具异常的统一捕获，外加一个异常 ToolMessage 的清理中间件。

       * `model call limit`：模型调用次数的限制。

       * 自定义的 `TrackAgentRunLimit`：限制工具调用次数和运行时间。

   * **错误要转成 ToolMessage 的原因**

       * 工具偶尔报错是正常现象，只有一直报错才不正常；模型会根据错误描述重新选择工具或调整参数重试，所以错误描述必须结构化、详细地返回给模型上下文。

       * > **易错点**：不能报一个错误就直接抛给智能体、让整个智能体崩溃——错误必须被捕获、被结构化，再喂回上下文。

### 参数清洗的拦截规则

   * **参数清洗中间件**

       * 自定义类继承 `AgentMiddleware`，构造函数重写父类，通过钩子函数在工具调用之前做判断、做拦截。

   * **拦截清单**

       * 拒绝 Windows / Linux 绝对路径：把宿主机器的绝对路径传给工具，意味着可以读取宿主上的其他文件，是巨大的安全风险。

       * 拒绝 `../`（点点杠）：使用它就意味着可以跳出工作区。

       * 拒绝访问敏感目录：存放 token、API key 的目录绝不允许访问，敏感内容要放到敏感文件或敏感目录中并做参数上的判断。

       * 拒绝 git url 格式错误、PR 编号类型错误以及其他非法参数。

### 重试上限与死循环

   * **死循环的产生机理**

       * 这里的死循环不是参数不变地反复调用同一个工具，而是：工具报错 → 智能体自动重试 → 重试构成循环；重试次数要设上限，例如重试五次或十次之后就不能再重试，要开始做限制。

   * **重试耗尽后的处理**

       * 重试到上限仍不成功时，智能体拿不到完整结论，本轮交付应当停止，并给用户一个提示结论，说明可能缺少了什么。

       * 用户自己也会犯错：指令里有错别字、错误的数据会造成多次尝试失败，智能体要反馈是哪个数据、哪个点、哪个环境造成的报错——例如网络断了造成的报错，就需要汇报给运维人员，或让用户重新修改输入参数。

### 工具系统与业务工具的分界

   * **工具系统**

       * 治理三件事：工具的执行环境；执行过程中的各种错误（参数的错误、权限的错误、工具本身报错）；工具可能重试很多遍、不能无限制重试的限制处理。

       * 它不教某个具体工具怎么写——具体工具怎么写属于业务。

   * **业务工具**

       * 真正干活的是加了 `@tool` 装饰器的函数，集中放在 tools 目录，例如与 git 打交道的工具（解析 git 仓库地址、获取 git token）；工具与业务相关，后期可以再定义、再增加。

## 执行编排

   * **执行编排**

       * > **定义**：整个智能体从如何接收用户输入，到得到一个完整结论的全过程执行方式；分多少层、采用固定流程编排（workflow）还是动态方式，由需求和项目决定。

       * 正规的 Harness 智能体一定有执行编排；Harness 架构里可以保留流程编排——这说的是整个智能体的编排，而不是某一条业务线选流程编排还是开放式，后者可以自主决定。

```text
用户输入
   │
   ▼
输入意图分类 ──► 小模型语义分类 + 规则兜底（此时还没有智能体）
   │
   ▼
主控智能体转交判断 ──► 决定委派给哪个子智能体
   │
   ▼
拆解并生成任务计划 ──► 分几步、每步干什么、跟踪与回退（agent loop 在这里）
   │
   ▼
步骤级意图决策 ──► 调工具 / 调 skill / 等待 / 确认（ReAct）
```

### 输入意图分类

   * **任务分类函数**

       * `classify_task` 接收一个 prompt（用户在客户端输入的内容，连同之前输入的内容），分析用户想干什么、归入哪个类别，再把分类结果交给智能体调度。

       * 六个类别：analysis（分析）、plan（方案生成与修改）、QA（普通问答）、inspect（代码解析）、review（代码审查）、coding（写代码）。

       * 六类任务分为只读任务和可写任务：可写任务只有 coding，只有 coding 才允许改代码——任务类别直接与权限挂钩。

   * **分类的作用**

       * 避免用户只是问个问题时触发代码修改；保证写代码必须先走方案确认，用户确认技术方案之后才动手写代码。

   * **分类的实现：小模型语义分类 + 规则兜底**

       * 代码先做一小段规则判断，再调小规模大模型做语义分类，模型调完之后还再通过规则判断做兜底。

       * 不用纯规则的原因：用户输入非常灵活（“帮我增加一个功能”“这个模块缺一个查询接口”不一定有明确关键词），纯规则等于关键词匹配，会出现大量 if-else、维护成本非常高；轻量模型负责理解自然语言。

       * > **易错点**：第一层分类直接决定后面的执行链路——模型把普通问答误判成 coding，就可能触发代码修改，造成很大的安全隐患，所以调完模型后不能完全相信它，规则兜底不能省。

### 主控智能体转交

   * **主控智能体（组织智能体）**

       * 在意图分类之后做任务的转交、委派判断，决定把业务交给哪个子智能体执行。

       * 例：用户输入“刚刚写的代码，帮我做一下代码审查”，第一层分类知道要做代码审查之后，主控智能体通过第二层意图判断，委派 code review 子智能体执行代码审查。

### 任务计划拆解

   * **任务计划**

       * 委派到子智能体后先拆解：分几步、每一步干什么、先干什么再干什么；写代码与代码审查一样，每一步都有任务计划生成。

   * **跟踪与回退：agent loop 所在**

       * 每一步都要跟踪：做完了没有、做的过程中是否报错，报错了可能回到原来的某一步。

       * 例：任务计划第九步运行 pytest 验证，没通过就回退到第五步的代码修复，修复完再跳回第九步做校验——Harness 架构里天然就有 agent loop。

### 步骤级意图决策

   * **步骤级意图决策**

       * 完成一个具体步骤时，决定调哪些工具、调哪些 skill，或者等待、确认，这一层采用 ReAct。

   * **四层的组合**

       * 这四层用户意图识别，组成了整个智能体完整的执行编排。

### 固定流程作为子智能体

   * **workflow 融入执行编排**

       * 某条业务线想用固定流程完全可以，例如代码审批流程是固定的，就搞一个 workflow 融入当前智能体，融入之后它作为一个子智能体存在。

       * workflow 本质上也是一个智能体（流程编排式的智能体），百分之百可以当成子智能体看待，但必须暴露给主控智能体——告诉主控它这个子智能体能干什么，主控按意图分类和子智能体交接，把业务交过去执行里面写死的固定流程。

   * **装配步骤**

       * 用 LangGraph 的 `StateGraph` 定义节点、定义边得到 graph，再通过 `compile` 得到一个可运行的工作流。

       * 挂入主控：先把工作流预编译，再调用框架提供的封装类，把工作流的名字、描述、工作流本体一起包装成子智能体，传入主控智能体的子智能体列表——主控里是个列表，还可以接其他子智能体。

## 非单例与动态装配

### 智能体按次创建

   * **非单例模式**

       * > **定义**：智能体不是全局单例，每一次任务运行都会根据当前的 config 创建并配置一个新的 agent。

       * 任何用户、不管在不在同一个会话，只要输入提示词一点击发送，代码里就重新调一遍 `get_agent`，创建一个新的智能体。

   * **第一层分类时智能体还不存在**

       * `classify_task` 只返回一个分类（kind），交给智能体调度；调度函数 `run_agent_task` 一上来先做意图分类，分类完才调用 `get_agent` 创建主控智能体，连它里面的子智能体也一起创建。

       * 由此实现提示词动态加载：先得到任务分类，按不同类别加载不同的提示词，再拿着提示词去创建智能体。

   * **动态装配的好处**

       * 执行流程不写死，可以根据不同仓库、不同任务类型、不同用户会话动态装配，里面的子智能体也可以动态装配。

       * 单例 agent 容易把提示词、工具、记忆、用户数据全部混在一起，不适合工程化；非单例模式百分之百支持动态创建提示词、动态 sub-agent、动态 skill 的弹性装配。

### 上下文连续的保障

   * **上下文不断的三重保障**

       * 非单例不代表上下文会断掉：上下文的持续由 thread id + checkpoint + 三层上下文结构来保证。

       * store 和 checkpoint 是单例的——因为要保证上下文是连续的。

   * **配套工程手段**

       * 会话连续性保持；使用仓库记忆，保证仓库级的上下文连续；使用统一的 Agent 工厂，保证上下文注入方式的一致性。

       * 各设计环环相扣：不采用非单例模式，四层意图识别与动态装配这套方案就做不到。

## 记忆与状态分层

### 三层记忆的分工

| 记忆层 | 保存什么 | 存在哪里 |
| :--- | :--- | :--- |
| 会话短期状态 | 当前会话的全部历史消息（system message、human message、tool message、AI message），外加图的状态 | checkpoint |
| 仓库长期记忆 | git 仓库的长期工程信息，即仓库的记忆 | 专门的 store backend，里面有路由 |
| 业务运行状态 | 任务摘要、运行事件、PR、审查结果 findings、会话列表 | 业务表（业务 store） |

   * 三层解决的是不同的问题，不能混在一起。

   * 仓库长期记忆按仓库区分：问一句“当前仓库的记忆是什么”，它会把哪一天干了什么、最近干了什么全部列出，不同的仓库有不同的记忆。

   * 业务运行状态里的运行事件，是智能体运行过程中产生的事件，未来做日志追踪用的就是它；审查结果 findings 也属于业务数据。

### 三条数据通路

```text
会话短期状态：用户输入 ─► 会话 id 记录本会话全部聊天记录 ─► 序列化存入 checkpoint ─► 恢复出上下文传给智能体运行
仓库长期记忆：仓库 URL ─► 解析出拥有者 + 仓库名（以此判断唯一）─► 存入带路由的 store backend ─► 中间件读取后注入当前上下文
业务运行状态：运行过程 ─► 记录做到哪一步 / 提交的 PR 地址 / 审查出的问题 ─► 单独存入业务 store ─► findings 会被读回
```

   * 仓库长期记忆与仓库 URL 绑定，用拥有者加仓库名判断唯一；不同项目用什么判定记忆唯一性可以不同——记什么、和什么绑定、以什么判断唯一性，要根据业务动态调整。

   * 仓库记忆的注入不是单打独斗，也要通过中间件读取再注入当前上下文。

   * 业务 store 会写也会读，findings 是必须要读的。

### 可选的检索层

   * **检索层做法**

       * 可以在三层之上再加一层专门做检索：针对业务数据做全文检索或语义检索，再做多次重排（去掉不相关内容、做精细化细粒度重排），最后把剩下的内容注入智能体上下文。

   * **当前项目不做的两个原因**

       * 每次用户输入提示词后，要等整个搜索过程完成智能体才开始执行，明显耗时。

       * 仓库长期记忆文件已经把非常重要的核心信息都记在里头；当前项目只读取了 review findings（审查问题清单），运行事件一直保存但没有做检索。

## 约束边界

   * **约束与恢复**

       * > **定义**：约束就是限定智能体的权限——它能做什么、不能做什么；恢复就是智能体报了错，仍保证它能继续往下执行。

       * 模型到目前为止天然带有不可确定性，agent 不可能永远正确：调错工具、参数传错、访问越权、路径越权、陷入循环、执行失败、测试不通过、甚至遇到沙箱不可用都可能出现；工程上要做的，是设置边界并保证出错后可以恢复。

       * 约束落在三个地方：操作权限、沙箱、工具参数。

### 子智能体级操作权限

   * **权限动态装配**

       * 权限细化到每一个 subagent（子智能体）头上；subagent 和权限 scope 可以一起动态装配——不同的 subagent 绑定不同的提示词、不同的工具、不同的权限。

   * **review 子智能体的权限**

       * 对代码默认只读，但可以写文件——因为它最终要生成一份代码审查报告，即“代码可以看，但不能动”。

       * 可写目录只有两个：reviews（放审查报告）和 tmp（临时目录，审查报告比较长时先临时生成中间文件、最后再汇总）。

       * 专门写代码的智能体就应有写的权限，每一个子智能体的权限各不相同、各干各的事。

   * **权限的代码配置**

       * `get_agent` 创建智能体时就把权限分配进去：`create_agent` 创建主智能体时传入 `permissions` 参数，子智能体的定义中同样有各自的 `permissions`。

       * 权限围绕文件操作定义：哪些目录可读、哪些目录可写、哪些目录不允许（denied）。

       * > **提示**：这些路径的根是沙箱的根路径，而不是服务器的本地磁盘路径；用远程沙箱同理——都以沙箱的根目录为根，出了这个边界就不行。

### 子智能体架构的价值

   * **解决角色职责混乱**

       * 就像一个人既是运动员又是裁判员；子智能体若既能写代码又做代码审查，代码审查根本审不出东西——代码都是它自己写的，它认为自己的代码没有错。

   * **专业能力隔离**

       * 一个业务、一个专业就用一个 subagent 做专门的业务能力隔离，本质是防止大模型的注意力机制分散——注意力分散时回答出错的概率会大大提高，隔离后可以提高模型意图决策的准确率。

### 沙箱层约束

   * **两类沙箱都要有的约束**

       * 不管本地沙箱还是远程沙箱，都要有沙箱本身的约束：一是网络约束，限定只能访问哪几个网络；二是命令约束，git 命令也是命令，有些可以执行、有些不可以，要有命令白名单加黑名单。

       * 本地沙箱通过白名单机制、正则表达式、黑名单机制做各种约束：正则匹配到 Windows 绝对路径就拒绝访问，必须采用以沙箱为根的虚拟路径。

```text
沙箱安全边界
├── 网络约束：限定可访问的网络范围
├── 命令约束：白名单 + 黑名单，命令执行前做安全性检查
├── 路径约束：必须使用以沙箱为根的虚拟目录
│     ├── 真实目录的映射
│     ├── 路径解析，防止通过绝对路径绕过
│     └── 敏感路径的拒绝
├── 读写权限：逐目录判定可读 / 可写
└── 敏感信息：token 脱敏
```

### 工具参数拦截

   * **参数拦截器**

       * > **定义**：`ToolInputMiddleware` 是在调用工具之前检查参数是否传错的中间件。

       * 必须拦参数的原因：参数是由模型本身生成的，里面有可能带 `..`、带绝对路径，甚至带 token、API key 之类的东西。

   * **拦截清单**

       * Linux / Windows 的绝对路径，拒绝。

       * 通过 `..` 做路径穿越，拒绝。

       * 敏感目录：除规定的那几个目录之外，其他目录不允许访问。

       * git url 格式错误、PR 编号类型错误以及其他非法参数，也拒绝。

   * **约束的设计原则**

       * Harness 工程并没有规定必须加哪几种约束，开发人员要根据智能体的业务需求灵活设计，完全可以加第四个、第五个约束，没有标准答案。

## 恢复机制

### 工具调用失败的兜底

   * **兜底流程**

       * 适用于所有子智能体。

```text
模型发起一次工具调用
   │
   ▼
ToolErrorMiddleware：先拿到工具名字 → try 真正执行工具 → except 捕获所有异常
   │ 调用失败
   ▼
错误信息脱敏 ──► 构造 ToolMessage（status = error）
   │
   ├── 记录文件日志
   ├── record_error 写一条数据库错误日志
   └── 记录 run event（存入业务 store，支撑日志追踪）
   │
   ▼
ToolMessage 返回给 agent ──► agent 根据错误描述修正 ──► 进行下一轮推理
```

   * **中间件实现**

       * 类 `ToolErrorMiddleware` 继承 `AgentMiddleware`，实现钩子函数 `wrap_tool_call`：既能在工具调用之前拦截，也能在调用之后拦截，这里主要用于调用之后拦异常；try 块里才是真正执行工具的地方，套路非常类似 Java 后端开发里的拦截器。

   * **捕获异常后的三件事**

       * 先记录一条文件日志。

       * 再通过 `record_error` 往数据库里写一条错误日志——文件里一份、数据库里一份。

       * 然后调用脱敏函数，把错误信息脱敏之后构造出 ToolMessage，返回给 agent。

   * **效果**

       * agent 能看到错误的原因，但看不到原始的错误（已脱敏）；前端可以看到哪个工具失败了。

       * 工具失败并不会打断智能体——异常在中间件里被消化成一条普通的 ToolMessage，agent 拿到的只是一个错误提示而不是一次崩溃，可能换一个方案继续执行，整个过程就像智能体没有报错一样；run event 保证整个过程可追踪。

### 循环保护

   * **两层闸门**

| 层 | 机制 | 盯什么 |
| :--- | :--- | :--- |
| 第一层 | `model_call_limit` 中间件 | 模型调用次数 |
| 第二层 | `AgentRunLimitTracker`（观察者） | 工具调用次数与运行时间 |

       * 要第二层的原因：工具就算报错了也没关系、会恢复，但一恢复就有可能进入工具调用的死循环，所以还要统计和跟踪工具调用的次数以及运行时间。

   * **AgentRunLimitTracker 的机理**

       * 可以理解为普通的观察者对象；工具函数检查工具调用，一旦发现超过指定的最大调用次数，就抛出自定义异常，异常里带描述信息——本轮工具调用超过了多少次保护上限、任务类型是什么，并提示如果是特别复杂的开发任务，这个上限可以稍微提高。

       * 挂载位置：智能体由任务调度用 runtime 来跑，runtime 调度真正调的是 streaming runtime 里的 `run_agent_with_event_stream`——以事件流方式执行智能体，底层用 LangChain 团队 2026 年 6 月之后提出的 V3 版本事件流（流式输出），主要函数 `astream_events` 返回一个 stream。

       * 用法：函数一进来就创建一个 `AgentRunLimitTracker` 实例，通过 `observe_event` 以观察者设计模式监听运行过程中产生的一个个 event——调一次模型是一个 event，调一次工具也是一个 event；函数外面有一行代码专门捕获 tracker 抛出的自定义异常，捕获之后记录日志 `record_event`（一条 run event）。

   * **超限后的行为**

       * 只要超出次数和时间，tracker 抛异常被捕获后，本轮智能体就结束；返回给用户的是一个普通的提示（可以理解成警告提示），而不是错误提示——循环很多次仍未达成目标时再继续运行已没有意义，但要告诉用户是因为什么原因没拿到最终结果。

       * 智能体不可能百分之百给出正确回答：用户输入五花八门且不受限制，拿 AI coding 智能体问天气、做旅游规划就给不出结果，此时必须给用户一个提示。

       * > **提示**：面试高频点——不要说靠模型自己判断何时停止，而是在运行时设置硬限制：模型调用次数、工具调用次数、单轮执行时间都有上限；这样即使 agent 的策略异常，也不会把服务器资源耗尽、造成整个系统崩溃。

### 用户确认机制

   * **确认点清单**

       * 确认方案、确认 PR、确认提交、确认评论、确认代码审查，以及代码审查的修改方案（整改方案），都需要用户确认。

   * **作用与合理性**

       * 每生成一个技术方案、每个修改方案都要确认，对用户来说不算特别友好，但它能最大限度地保证 AI coding 智能体写出的代码是可靠的。

       * Claude Code、Codex 在执行某些命令之前，也要先向用户申请权限才能继续执行——让用户介入确认，在智能体中并不是绝对不能用的。

## 观测与评估闭环

### 追踪到评估的顺序

   * **顺序链**

```text
日志追踪（事件结构化入库）
   │
   ▼
观测（token / 费用 / 次数 / 耗时的统计与趋势）
   │
   ▼
评估（对智能体行为做质量判断）
   │
   ▼
工程化闭环
```

   * 追踪是地基，观测是在追踪之上做统计呈现，评估是最后的判断；三者自下而上依赖，顺序不能颠倒——首先得有观测，才有评估。

   * **追踪记录什么**

       * 智能体整个运行过程中某些关键环节的内容，保存到文件或数据库中，便于做运行追踪：调了多少次模型、多少次工具，调模型一共花多少 token、输入 token 是多少、输出 token 是多少。

   * **观测统计什么**

       * 每一轮对话消耗多少 token、消耗多少钱、调用多少次模型、耗多长时间以及时间的变化趋势；最近一个小时内智能体的平均响应时间、平均消耗 token 的数量。

### 结构化日志追踪

   * > **易错点**：日志追踪 ≠ 打日志文件——日志文件一行行平铺，第七行的对话开始与第四十四行的工具调用肉眼看不出关联，建立不起「一轮对话 ↔ 多次模型/工具调用」的一对多关联；追踪要求每个事件结构化入库、能按对话串起来。

   * **关联与字段设计**

       * 通过 `run_id` 和 `thread_id` 两个 id 建立关联；类型字段标记这条事件是调了工具还是调了模型——`think` 是模型调完之后产生的 AI message，此外还有 `todo`、`other` 等很多类型。

       * 每条记录还有标题、详细内容、状态以及时间。

   * **当前项目现状**

       * 有日志追踪，但没有做观测页面；本地运行用 SQLite 图个方便，能用 SQLite 就一样可以用 MySQL、SQL Server、DB2，没有什么区别。

       * 最关键的数据库里，每一轮、每一轮对话产生的任何一条事件、任何一条消息都有记录，数据量特别大；不想自建，可以采用第三方服务帮做日志追踪、可观测和评估。

### 编码智能体的评估闭环

   * **闭环全流程**

```text
写代码需求 ─► 生成技术方案（用户可多轮修改）─► 用户确认实施
   │
   ▼
写代码 ─► 自动运行 pytest ──不通过──► 重新写代码
   │ 全部通过
   ▼
创建 PR 提交（进入远程仓库）─► review 子智能体代码审查 ─► 生成审查报告
   │
   ▼
针对报告生成整改方案（用户可修改）─► 确认后修改代码 / 生成新代码
   │
   ▼
回到单元测试 ─► 提交 ─► 第二轮代码审查 ─► 以此类推，循环闭环
```

   * **关键细节**

       * 每写完任何一小段代码，智能体都自动执行单元测试，全部是 pytest 做的；日志里可以看到所有写的代码都有单元测试。

       * 单元测试里有不通过的就会重新写，一定全部通过之后才创建 PR 进行提交。

       * 只要一生成新的代码，就触发新一轮「单元测试—提交—代码审查」，如此往复形成内部闭环。

   * **普适性**

       * 不是写代码的智能体（例如做财务分析或其他事情的传统智能体），同样要搞这样一个评估闭环。

### 外置观测服务

   * **Langfuse**

       * > **定义**：在智能体外部单独构建的一个服务，专门承接日志追踪、观测与评估的闭环。

       * 放到外部的三个好处：可以并行；可以异步；就算评估有问题或日志最终有问题，也不会影响智能体本身的运行。

       * 适用场景：企业中比较大型的智能体项目、服务器资源比较丰富时，推荐使用第三方 Langfuse 来专门做日志追踪、评估、观测的闭环。
