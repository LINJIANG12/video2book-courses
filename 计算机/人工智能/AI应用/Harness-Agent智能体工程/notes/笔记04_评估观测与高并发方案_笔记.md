# 评估观测与高并发方案

## 评测与测试的分野

* **确定性**

    * > **定义**：传统软件测试成立的前提——相同输入必然得到相同输出。

    * 结果一旦不确定，直接判为测试不通过。

    * 传统软件测试主要测两样：功能是否合理、是否成功；性能能否扛住并发（例如 Web 后端逐个接口测，再做压测看接口能承受多少并发）。

* **评测**

    * > **定义**：智能体质量保障的正确形态，关键字在「评」——对一组客观指标做评估，而非验证确定性输出。

    * 判定方式：智能体输入相同参数，最终结论不一定相同——可能语义相同但内容不完全一样，这不算是运行错误。

    * 评估对象是整组指标：正确率、召回率、token 消耗、延迟、某个工具调用出现循环的概率、意图决策的准确率、最终结果的准确率。

    * 智能体对外无非一个聊天界面甚至只有一个 API 接口，功能有测的必要但过于单一，撑不起「测试」这个概念。

    * > **易错点**：把这件事叫「智能体测试」「大模型测试」是误区——主要工作不在「测」这个字上，而在「评」这个字上。

    * 岗位形态：正规企业、了解技术底层的企业招聘的岗位名就是「模型评测工程师」「智能体评测工程师」，不是测试工程师；现在和未来会出现海量的模型与智能体评测工程师。

| 对比维度 | 传统软件测试 | 智能体评测 |
| :--- | :--- | :--- |
| 关注点 | 接口功能对不对、性能扛不扛得住 | 正确率、召回率、token 消耗、延迟、工具调用循环概率、意图决策与最终结果准确率 |
| 隐含前提 | 相同输入必然得到相同输出 | 相同输入结论可以不同，语义相同就不算错 |
| 关键字 | 测 | 评 |

## Langfuse 与 LangSmith 选型

* **Langfuse**

    * > **定义**：面向大模型、RAG、智能体这类应用的开源 AI engineering 平台，专门用来搭评估观测闭环，从一出生就干评测这件事。

    * 能力清单：追踪运行过程、分析 token 成本和延迟、管理提示词、收集反馈、执行自动与人工评估，再通过 Datasets 和 Experiments 做持续改进。

    * 开源成色：真正做到 MIT 开源协议且全部开源——包括 server、PostgreSQL 组件、日志分析组件等每一处；国内内网服务器可以随便部署、随便改代码、随便做配置。

    * 版本选择：建议用 V4.5，即 V4 以后的版本；该版本 2026 年 8 月 6 日发布。

    * 真正意义上开源的评测平台只有两个，其中 Langfuse 历史渊源最长久；智能体评测工程师必须掌握它。

* **LangSmith**

    * > **定义**：LangChain 生态里的评测平台。

    * 开源成色：核心并没有真正开源，必须注册 LangChain 的 API key 才能用；私有化部署到本地同样需要 API key，而且动不动就需要联网。

    * 后果：内网部署非常不方便，国内企业一般不会采用。

    * > **易错点**：以为掌握 LangSmith 就能胜任大模型/智能体评测岗位——选型重心应放到全开源的 Langfuse 上，而不是这类并非正经全部开源的平台。

## 智能体并发瓶颈

* **并发能力量级**

    * 普通服务器节点跑普通 Web 项目：并发约 200 到 500，程序写得好坏影响不大，上下浮动不超过 50。

    * Agent 的单个 worker 节点：并发数非常低，一般可能就几十——与 Web 差好几倍，差不多差了一个数量级。

* **长周期任务**

    * > **定义**：Harness engineering 架构智能体执行的任务形态——复杂且执行周期长，这是并发能力弱的根源。

    * 典型例子：AI Coding 那样写代码；ERP 智能采购助手——做采购对比、供应商对比，生成采购方案，甚至真的下采购单，下完还要跟原有数据做验证。

    * 单轮任务耗时：少则一二十秒，长的可能一两分钟。

* **流式长连接**

    * Web 服务器一般是毫秒级响应（150 毫秒、200 毫秒），请求即结束连接。

    * Agent 的每次请求要通过服务器的 SSE 或 WebSocket 不断把流式输出给客户端，持续差不多几十秒甚至几分钟；一条连接被长期挂住，单节点能同时伺服的请求数自然少一个数量级。

* **高并发必要性判定**

    * 企业内部只有 50 到 150 人使用的智能体也要做高并发；只要同时使用人数超过几十人到几百人以上，并发就是必须考虑的问题。

    * 面向 C 端普通消费者的智能体，高并发必做，毋庸置疑。

* **高并发核心两条**

    * 服务的分离。

    * 消息队列的隔离。

## 服务分离

* **服务分离**

    * > **定义**：智能体项目必须把 Web 服务器和智能体本身拆开——智能体部署到服务器端必然有对外发布的接口，有接口就必然有 Web 服务器，二者必须分离；分离后架构即 Web 服务器 + Agent Worker（智能体服务器）。

    * 好处一：Web 服务器技术栈任选。智能体代码用 Python 写，Web 服务器用 Java、Go、.NET 都可以，因为分离后两者没有任何直接联系、不存在依赖关系。

    * 好处二：两者之间靠中间件衔接，可以理解为消息队列——Redis、Kafka、RabbitMQ 都可以。

* **ASGI**

    * > **定义**：Python 里服务器通信协议的名字，不是什么特殊组件。

    * > **提示**：看到「ASGI 的 Web 服务器」，按「网站服务器」理解即可，相当于一个网站的服务器；Java 里对应的角色是 Tomcat 容器。

    * 架构里取名为 ASGI 仅仅是示例项目为了方便讲解直接采用了 Python 的 Web 服务器——Python 这边现在常用的就是 ASGI 的 Web 服务器。

## 请求队列与响应队列

* **请求队列**

    * > **定义**：Web 服务器把用户提示词连同各种 id 一同写入的消息队列，负责把任务从 Web 服务器交给 Agent Worker。

    * thread id、run id 等各种 id 全部由 Web 服务器生成：前端没传会话 id 就创建会话 id，没产生 run id 就创建 run id。

* **响应队列**

    * > **定义**：Agent Worker 运行中流式吐出的 token 以生产者身份写入的另一条队列，与请求队列同在一个消息中间件里。

    * Web 服务器作为消费者从响应队列取数：只拿属于当前会话 id 和 run id 的数据，拿到后就通过 SSE 流式响应给客户端。

    * > **易错点**：从响应队列取数据必须用 Web 服务器自己生成并塞进请求里的 thread id、run id 做匹配，只取本会话的数据，不能见数据就拿。

* **Agent Worker 的运行形态**

    * 不需要开启服务：它不直接和客户端打交道，也不直接和 Web 容器打交道。

    * 只开启轮询：通过线程池或进程池轮询中间件的队列——作为消费者从请求队列拿数据，作为生产者把 token 数据写入响应队列，一拿一写都是轮询方式。

    * 「智能体分离出来」的确切含义：把跑智能体的这段代码从 Web 服务器的进程里拿出来，放到独立的 Worker 节点上去跑，两边只靠队列通信。

* **整条链路**

```text
客户端
  │ ① HTTP 请求
  ▼
Web 服务器
  │ ② 未传会话 id / run id 就代为生成，再把提示词连同 id 写入
  ▼
请求队列（消息中间件内：Redis / Kafka / RabbitMQ 任选）
  │ ③ Agent Worker 用进程池或线程池轮询消费
  ▼
Agent Worker
  │ ④ 运行中流式输出 token，以生产者身份写入
  ▼
响应队列（同在这一消息中间件里）
  │ ⑤ Web 服务器按自己发出的 thread id / run id 只取本会话数据
  ▼
Web 服务器
  │ ⑥ 经 SSE 流式响应
  ▼
客户端
```

## 集群部署方案

* **负载均衡与 Web 接入层**

    * 最上层一个负载均衡器，下面挂多个 Web 服务器节点（示例技术栈为 FastAPI + uvicorn，即 ASGI 的 Web 服务器节点），节点可以有多个。

    * Web 节点收到用户请求后，把请求数据插入队列；插入的时候可以搞个分布式锁。

    * 队列用 Redis、Kafka 还是 RabbitMQ，由自己决定。

* **Worker 集群与分布式锁**

    * Agent Worker 节点也是多个，节点内有多线程或多进程，执行 run——即执行一个 Python 命令把整个 Agent 的代码跑起来，用多线程或多进程轮询消费请求队列。

    * 消费时采用分布式锁：保证同一条用户请求只能被一个 Agent Worker 拿走，它拿走了其他 Worker 就不能再拿。

* **上下文记忆服务器**

    * 单独搞一套上下文记忆服务器，承接每个 Agent Worker 的上下文恢复以及长期记忆；本质都是数据库服务器。

    * 选型：采用 PostgreSQL 作上下文存储，或采用 Redis，或两个都用——典型分工是短期记忆用 Redis，长期记忆用 PostgreSQL。

    * > **注意**：这套存储全集群只有一套，所有 Agent Worker 都拿同一个，这样才能保证上下文是一致的。

* **部署全貌**

```text
                        负载均衡器
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
      Web 节点 1        Web 节点 2        Web 节点 3
   （FastAPI + uvicorn，即 ASGI Web 服务器，可有多个）
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼  插入请求数据（可配分布式锁）
             请求队列（Redis / Kafka / RabbitMQ 任选）
                            │
                            │  多个 Agent Worker 节点轮询消费
                            │  （分布式锁：一条请求只能被一个 Worker 拿走）
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
      Worker 节点 1     Worker 节点 2     Worker 节点 3
   （节点内多线程/多进程执行 run，跑起 Agent 代码）
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼  流式 token 以生产者身份写入
                    响应队列（同一个中间件）

   所有 Worker 共用同一套上下文记忆服务器（保证上下文一致）：
       短期记忆 → Redis　　长期记忆 → PostgreSQL（或两者都用）
```

## 大模型 API 单独用的局限

* **训练数据边界**

    * 大语言模型的数据来自训练时投喂的数据，而训练数据来自互联网——例如 OpenAI 用的是全球数据，尤其是来自谷歌的高质量数据。

    * 互联网不包含公司内部数据：京东、阿里巴巴、腾讯这类企业的内部数据不可能暴露到互联网上，百度、谷歌都拿不到，现在数据安全做得很好。

    * 结论：基于 OpenAI 或国内 GLM 等大语言模型 API 开发的聊天机器人，不能根据自己公司内部的数据库或文件来回答问题。

* **动作执行边界**

    * 纯 API 调用无法根据聊天指令执行动作：让它「请帮我发一封邮件给某某邮件地址」，现在的大语言模型完成不了。

* **LangChain 的诞生动机**

    * 投喂 100 篇某个行业、某个主题的专业论文，连续针对论文提问，最后一句「把我刚问的这些问题作为历史记录发邮件给我」——写好的 AI 程序真能把问题与答案发到指定邮箱。

    * 把 Django 官方文档地址交给程序，请它把文档看一遍、搜索一遍，之后所有问题都基于文档回答，例如「用 Django 开发连接 Redis 数据库的程序，配置文件应该怎么写、代码怎么写」。

    * 先通过某个工具去百度搜索信息，把搜到的信息交给大语言模型，接下来的提问都基于收到的这些信息——让 AI 不局限于大语言模型本身，还能自动执行动作。

## LangChain 框架

* **LangChain**

    * > **定义**：一个开源框架，用于开发由语言模型驱动的应用程序——把大语言模型与外部的计算和数据源结合起来。

    * 模型不限于 GPT-4：谷歌的模型、微软的大语言模型、国内百度的模型都行。

    * 兼容能力在 2024 年 3 月升级到 0.2 之后又扩大了一倍，国内外常用的大语言模型都支持。

    * 职责：为应用开发做抽象的封装、获取外部数据、数据存储、搜索和访问向量数据库。

    * 类比 Java 生态：类似 Spring Boot、Spring 或 JDBC 这样的框架——把大语言模型变成真正跟用户直接交互的产品、软件程序。

* **组件（Components）**

    * > **定义**：为大语言模型提供接口封装的部件。

    * 机理：像 JDBC 的 driver 一样提供一套抽象的通用驱动，OpenAI 的 LLM、谷歌的大语言模型、国内 GLM 都可以去调。

    * 价值：直接基于这套抽象封装开发代码，代码几乎不变的情况下就能更换大语言模型——国内好用用国内的、国外好用用国外的；没有这套框架之前做不到。

* **链（Chains）**

    * > **定义**：将不同的组件组合起来、解决特定任务的连接层。

    * 开发一个 AI 产品可能同时需要语言模型、存储数据库、向量数据库以及向量化或嵌入；专门把这些组件整合、连接起来的东西就是 chain。

    * 这个框架统称叫 LangChain，名字的来历就在这。

* **代理（Agents）**

    * > **定义**：使大语言模型能够与外部环境进行交互的机制。

    * 机理：先指定一个代理的工具帮我们把外部数据获取到（例如抓取 Django 官方文档里的各种信息），拿到之后再交给我们的大语言模型。

    * 「外部」的范围：Django 官网是外部，自己的数据库也是外部——例如把京东的商品数据交给 AI，就能基于这些商品信息做智能化客服、营销代理、销售代理。
