# 上下文精细化与工程落地实战

## 沙箱与 OpenSandbox

   * **沙箱（Sandbox）**

       * > **定义**：Harness Engineering 的必备组件，提供安全边界——用户隔离、权限控制（网络控制、文件操作权限控制），同时充当工具与 skill 的执行环境。

       * Claude Code、Codex 也自带沙箱，但装在个人本地电脑上，不方便采用远程，实际上也不支持远程沙箱。

       * 企业开发一律采用远程沙箱：本地沙箱会把沙箱和智能体混在一起，没有实现解耦。

       * 沙箱本质上就是一个 docker 容器，专门运行智能体里的工具与 skill，并承担用户隔离、数据安全边界与网络权限控制。

   * **OpenSandbox**

       * 阿里巴巴开源的通用 AI 应用沙箱平台，支持 docker、K8s 等多种形态，专门给智能体提供远程的、基于 docker 容器的沙箱。

       * 沙箱服务器启动后监听 `0.0.0.0:8080`，这个接口地址暴露给智能体并配置进智能体的配置里，由智能体请求它创建和管理沙箱。

       * 服务器刚启动时还没有任何沙箱容器，用 `docker ps` 看到的数据库容器不算；沙箱要等智能体启动之后才被创建，创建后还要上传初始化信息、安装依赖库。

       * 容器内预置 Python 3.11、Java 21、Node.js v22、Go 1.25 四套执行环境；镜像可以自定义，往镜像里加入一套 C++ 执行环境，基于该镜像启动的沙箱就能多支持 C++。

       * 沙箱正被占用时要重做热备、已被回收时要重新创建，这两种情况都会拉长耗时。

   * **沙箱获取：先取后建**

       * 已有 sandbox id 时走 connect：按 id 连接既有沙箱复用，不会重新创建。

       * 没有 sandbox id（第一次启动智能体）时走 create：基于镜像创建 docker 容器沙箱，有多个镜像时还可以选择。

       * 创建参数：资源占用 2 核 CPU、4G 内存；网络默认拒绝所有网络，只放行指定的几个网站。

       * > **易错点** ⚠️：最容易忽略的是网络控制——skill 拿到执行环境后不能放任它访问整个互联网，默认全拒绝、白名单放行才是安全边界。

   * **依赖项目的启动顺序**

       * 固定三步，顺序不能乱：先启动沙箱服务器，再启动 MCP 服务端（基于 FastMCP，专门对接 Java ERP），最后启动智能体本身。

       ```text
       沙箱服务器启动，监听 0.0.0.0:8080（此刻还没有任何沙箱容器）
              │
              ▼
       MCP 服务端启动（FastMCP，对接 Java ERP）
              │
              ▼
       智能体启动 ──► 创建专属沙箱容器 ──► 上传初始化信息、安装依赖库，沙箱就绪
       ```

## 两个落地项目

   * **智能采购助手**

       * 基于 Java ERP 系统的智能采购助手：从一份采购政策入手，接收指令后生成零配件的采购综合对比分析报告。

       * 运行依赖三件套：远程沙箱、对接 Java ERP 的 MCP 服务端、智能体本身，三者按固定顺序启动。

   * **服务端 AI coding**

       * > **定义**：不是简单的聊天智能体，而是围绕企业内部 git 仓库构建的工程化 agent harness。

       * 立项理由是本地工具的四个痛点，对比如下表。

       * 技术构成：多层意图识别控制任务入口；非单例的 agent 动态装配提示词、sub-agent 与 skill；checkpoint 与仓库记忆保证上下文连续；自定义的文件后端和沙箱保证安全边界；DeepSeek V3 加 SSE 实现过程可观测、流式输出；worker 集群加 Redis 加 PostgreSQL 支持高并发扩展。

       * 业务能力：先与用户多次确认技术方案、方案不合适还要修改；然后代码实施、代码审查、生成审查报告、基于审查报告继续修改代码、做单元测试；最后与 git 仓库交互——提交代码、创建分支、提交 PR、回复 PR 评论。

       * 部署形态：前后端分离，代码原封不动即可部署到服务器；以点开头的环境文件存放多个模型的 API key，在 Linux 中自动隐藏。

| 对比维度 | 本地 AI coding（Claude Code、Codex） | 服务端自建 AI coding |
| :--- | :--- | :--- |
| 安装与配置 | 每个程序员各装一遍、各配一套 API key | 统一服务，一次部署全员使用 |
| 规则与习惯 | skill 与代码审查规则各电脑各自配置，同一项目五花八门 | 统一的代码审查规则与统一的编程习惯 |
| 使用入口 | 必须打开客户端或 IDE 插件，出差路上远程操作很麻烦 | 微信小程序、聊天窗口里就可以写代码 |
| 内网 git 安全 | 直连企业内网 git，代码可能被全部拉走再上传到外部大模型 | 统一对接企业内部 git 平台 |

   * 正因这些安全顾虑，不少国企和中大型企业为了代码与数据安全，一般不太让员工使用 Claude Code、Codex 这类本地工具。

## 上下文精细化

   * **上下文精细化（context refinement）**

       * > **定义**：不是简单地把历史消息拼接进一个提示词里，而是一个完整的上下文治理过程。

       * 治理过程包含七件事：上下文过滤（只保留和当前任务相关的信息）、上下文剪裁、上下文压缩、长期记忆、记忆的检索、状态恢复、上下文注入（模型调用之前把必要的背景动态注入进去）。

       * 做这七件事之前，得先有上下文分层的地基。

## 上下文三层存储

   * **上下文的三层**

       * 分几层由设计者自己决定，分两层、三层都行，该项目分了三层。

       * > **易错点** ⚠️：这里是「三种数据」，不是「三个」——每一种里面还分很多个数据；叫「上下文的三层」，不能叫「记忆的三层」。

| 上下文层 | 存的数据 | 谁来维护 |
| :--- | :--- | :--- |
| 业务 store | run event 运行日志、review findings 问题清单、线程运行数据、仓库与工作目录映射 | 自己创建、自己写入 |
| checkpoint | 以会话为单位的聊天历史（短期记忆） | 创建智能体时配置即可，框架维护 |
| LangGraph store | 项目/仓库记忆文件（长期记忆） | 自己维护存储后端 |

### 业务 store

   * **运行事件（run event）**

       * > **定义**：把智能体每一步的运行都当成一个事件，触发即写入单独的业务数据库；事件是自定义的数据格式，每一步存什么由自己定义。

       * 只拿聊天记录当日志不完整：智能体什么时候创建、什么时候注入了新提示词、什么时候做了一次提示词剪裁缩减，这些在聊天记录里可能看不到。

       * 落库由自己的函数完成，本质是一条 insert into 插入语句，插入逻辑自己写。

   * **审查问题清单（review findings）**

       * > **定义**：代码审查之后得到的代码问题清单，分高风险、低风险、一般风险几档。

       * 必须永久保存：程序员本人要看，项目经理也要回看团队上周的代码经第一轮审查暴露了哪些问题。

       * 它属于上下文的理由：隔几天回来修问题时，要把清单从数据库取出来注入正在运行的智能体上下文，而不是重新做一次代码审查。

   * **映射与线程数据**

       * 一个仓库就是一个项目，仓库地址要跟项目绑定，这个映射关系要保存；线程运行数据同样存入业务 store。

### checkpoint

   * **检查点（checkpoint）**

       * > **定义**：短期记忆层，以会话为单位存聊天历史。

       * 创建智能体时配置一下即可，存储和恢复都由框架维护，不用自己操心；大部分智能体项目都有这一层。

   * **会话的保存与恢复**

       * 以会话为单位的聊天历史由 checkpoint 保存，会话的恢复也由 checkpoint 决定。

### LangGraph store

   * **LangGraph store（长期记忆）**

       * > **定义**：长期记忆层，存项目/仓库记忆文件。

       * 记忆文件跟仓库绑定、不跟用户关联，对所有有该仓库代码操作权限的开发者共享。

       * 共享与长期保存的理由：张三要知道李四写了什么；人自己会忘上周写到哪、智能体也可能会忘，所以必须有一份长期记忆文件。

   * **存储后端**

       * 长期记忆的存储后端由自己维护：store 本质是一个数据库连接，地址、端口号在连接里指定，用什么数据库都可以。

## 仓库记忆

   * **仓库记忆**

       * > **定义**：一个仓库一份、对所有有代码操作权限的开发者共享的长期记忆文件，记录项目从创建到不断开发的全过程。

       * 内容字段：代码仓库地址（与 git 服务器关联）、本地仓库目录、初始化时间、技术栈、启动命令、测试命令、关键文件、已知约定、按日期一条条列出的最近结论。

       * 只要有仓库操作权限就能查看；第一次使用稍慢，要先构建缓存；回答是流式输出，内容大概十几二十行。

       * 文件太长会自动截断：前几条是完整记录，中后部大量历史交互痕迹做了多段截断；需要针对某一项展开说明也可以。

       * 写新代码时把记忆内容注入上下文，智能体才知道仓库已经写了哪些代码、用了什么技术、完成了哪些测试，从而不出现上下文的记忆断层。

       * > **易错点** ⚠️：记忆里展示的本地目录是沙箱内的仓库地址，不是宿主机的真实路径——宿主机根目录下根本不存在那个目录，真实位置在沙箱对应的 workspace 里。

   * **记忆文件后端与 /memories 路由**

       * 仓库记忆用一个专门的文件后端存储，完整路径以 `/memories` 开头，这是一个虚拟路径，靠路由做分配。

       * 路由规则：文件路径以 `/memories` 开头即命中 store backend，最终落到 LangGraph store 背后的数据库。

       * 需要路由的原因是有好几个 store，每个文件按路径规则各查各的库。

   * **长期记忆的本质**

       * > **定义**：长期记忆是对整个代码仓库进行操作所产生摘要的索引，类似大模型的 wiki——wiki 最重要的是建立索引。

       * 记录的是操作摘要（某月某日修复了什么代码、做了什么事），不是把每一步操作的完整信息原原本本保存下来。

       * 确实缺细节时，借助语义搜索或全文检索去日志追踪数据里查：完整的智能体运行日志和历史记录日志各存了一份。

       * 大部分情况没必要每次检索细节：每写一次代码都要把之前几周的所有代码细节拿到手，智能体就太傻了；通常拿到操作痕迹和影响干活的核心内容即可——已知约定、技术栈、关键文件、测试命令、入口。

       * 长期记忆自动更新：每做一步操作就更新一下，实现上是智能体运行结束之后做异步更新。

   * **记忆注入流水线**

       ```text
       智能体启动，按任务与仓库地址查询仓库记忆
              │
              ▼
       解析仓库地址 ──► 得到记忆文件的完整路径
              │
              ▼
       按文件路径路由分配 ──► 定位长期记忆 store
              │
              ▼
       读取记忆 ──► 做摘要
              │
              ▼
       注入中间件 ──► 截取不超过 6000 字符 ──► 注入智能体上下文
       ```

## 提示词动态加载

   * **用户意图识别（第一层）**

       * 用户输入先分类再干活：写代码、生成技术方案、代码审查、回答问题几个大类，大类里面还有很多小类。

       * 输入内容不同，智能体就执行不同的任务和操作；分类结果决定了后面加载哪一套提示词。

   * **提示词动态化**

       * > **定义**：上下文中包含提示词，所以上下文精细化的第一件事就是提示词的动态化——提示词不是固定的，由用户需要做什么来决定。

       * 实现：创建主智能体时，system_prompt 不是写死的，而是调函数动态获取，调用时传入任务类别参数 `cat_id`；类别是默认的 coding 就拿 coding 相关提示词，不是 coding 就拿其他类别对应的提示词。

       * 多套提示词并存：当前代码分析、项目分析的提示词，coding 的提示词，普通对话用的提示词，代码审查的提示词。

       * 与常见做法的区别：很多智能体的提示词是固定的，最多加一点变量替换，那跟固定没什么区别；这里是提前判断任务后按任务完全动态拼接，不是简单变量替换。

## 仓库记忆注入

   * **注入时机**

       * 只有写代码和生成技术方案（任务规划）这两类任务才注入仓库记忆；回答问题不注入。

       * 只要是写代码或生成技术方案，就必须把仓库长期记忆加载出来注入提示词，这样才不会出现记忆断层——「什么时候注」本身就是精细化的一部分。

   * **加载流程**

       * 根据仓库 URL 定位仓库记忆：先由仓库 URL 找到记忆路径，然后加载目录、构建记忆的 namespace、提取内容，再通过 store 读取，最后做记忆是否存在、是否要初始化等判断。

   * **注入方式**

       * 由专门的仓库上下文注入中间件执行注入，注入不是完整的：做字符串截取，最多注入 6000 个字符。

       * 截取的理由：记忆文件随着写代码越来越多、越来越大——文件大是好事，说明记得更完整；但注入不需要整个文件，只拿最近的、跟当前任务相关的部分。

   * **注入的周边配套**

       * 清洗历史消息：把原来一些不要的消息干掉。

       * checkpoint 做短期记忆的会话保持，维持会话状态。

       * 任务成功后做沉淀：把这次操作做成摘要——什么时间、修改了什么代码、主要修改了什么功能——存起来更新到数据库，长期记忆因此不断变化。

## 上下文压缩

   * **压缩的构成**

       * > **定义**：压缩是自动摘要和上下文剪裁的合称，两部分都包括，由两个重要中间件分别负责自动压缩与主动压缩。

   * **上下文剪裁**

       * 有工具读了一个很大的文件时，不能把完整内容一次性放进上下文：应该把文件的摘要内容放进上下文，把完整内容剪掉。

       * 剪裁和摘要是合在一起做的：先把该工具的输出内容做摘要，再把这段工具输出从历史里剪裁掉。

       * > **易错点** ⚠️：做摘要的只是这一个工具的输出内容，不是把整个历史记录做摘要；对整个历史做自动摘要是另一个机制干的事，两码事。

### 自动摘要

   * **自动摘要（`SUMMARIZATION_MIDDLEWARE`）**

       * > **定义**：框架侧的摘要中间件，上下文太长时自动触发压缩，定位是兜底机制。

       * 配置要给四样东西：摘要用哪个模型、摘要时读写文件用的文件后端，以及 `trigger`、`keep` 两个参数。

   * **触发与保留参数**

       * `trigger` 取 0.85：达到大模型总体上下文的 85% 就自动触发——模型是百万 token 上下文时，到 85 万 token 就触发。

       * `keep` 取 6：触发时保留最近 6 条聊天消息，真正被摘要的是这 6 条之前的历史聊天记录；最近的记录跟本次对话密切相关，所以要保留。

       * 0.85 是默认值：觉得多了可以设小一点，觉得少了可以设大一点，自己定。

### 主动摘要

   * **主动摘要工具（`compact_convert_conversation`）**

       * > **定义**：注册进智能体的一个摘要工具，由智能体自主决定什么时候调用，定位是日常压缩的主力。

       * 由工厂函数创建：返回一个工具，基于 LangChain 的 `StructuredTool` 定义——工具的名字、工具的描述、具体调哪个函数；创建时可以传一个摘要专用的系统提示词，不传就采用默认的。

       * 默认摘要提示词的含义：通过访问 `compact_convert_conversation` 工具，主动调用它来完成上下文的摘要。

   * **两个语义触发条件**

       * 条件一：当前用户请求转向了一个全新的任务，之前的上下文可能已经不相关——比如刚写完代码，现在开始做代码审查，之前的一些上下文就可以摘要掉。

       * 条件二：已经完成了结果的提取，或者已经生成了最终的回复结果，之前处理的上下文已经不需要了。

       * 两个条件任意满足一个，智能体就可以自主触发摘要；这个「主动」是站在智能体角度——靠语义理解、意图识别、逻辑推理自主决策，没有硬性条件，条件本身也可以自己改。

### 自动与主动的分工

   * **机制对比**

| | 自动压缩 | 主动压缩 |
| :--- | :--- | :--- |
| 触发方 | 框架（摘要中间件） | 智能体自己 |
| 触发条件 | 上下文达到模型上限的 85% | 两个语义条件之一满足 |
| 看上下文占比吗 | 看，到了就压 | 不看，只占 50% 也压 |
| 形态 | `SUMMARIZATION_MIDDLEWARE` 中间件 | 智能体工具 `compact_convert_conversation` |
| 定位 | 兜底机制 | 日常主力 |

   * **兜底与日常**

       * 自动摘要兜住的场景：智能体一直没主动触发、上下文不断累积，达到模型上下文的 85% 时自动压缩马上启动。

       * 日常情况下智能体按任务分配、任务交接或特殊情况自己调主动工具压缩，不用管占比——可能上下文只占 50%，照样压。

### 采购助手的主动压缩

   * **采购对比分析任务**

       * 场景：从一份采购政策入手，分析两款摩托车火花塞（其中一款是博世的）的原材料，对两个零配件做采购综合对比，生成长报告。

       * 过程调用量极大：通过 MCP 协议调 Java ERP 对外接口查关系型数据库、查不到换方式去供应商官网查数据、查历史订单价格与库存预警、调远程 MCP 生成数据分析图表，中间还有子智能体委派。

   * **为什么靠主动压缩**

       * 报告已写到文件里、业务要转入下一阶段（做其他分析或真正开始生成采购单）时，就应该主动摘要——这时可能远没到 85% 的上下文占比。

       * 不压缩的代价：旧上下文一直被占着，大模型做决策时可能注意力分散，整个决策失败的概率提高。

---

## 精细化解决的问题

   * **避免上下文过大**

       * 上下文压缩与剪裁两种机制结合，存储做三层分层。

   * **避免每一轮重复分析仓库**

       * 有了长期记忆文件，不需要每一轮都把整个仓库拉取一遍、把代码扫一遍——每次全仓库扫描效率太低。

   * **避免历史消息污染模型**

       * 把多余的对话提前主动摘要掉：上一个任务的关键信息已经存下、上下文对前端展示可能还有价值，接下来做另一个任务时没必要保留上一个任务的历史记录。

   * **避免工具消息破坏上下文**

       * 专门有一个中间件对工具执行后的消息做验证和判断：无效的 tool call、不成对的 tool message、报错信息或非法信息，清洗掉。

## 按业务设计的精细化

   * **没有标准方案**

       * 上下文精细化不是标准化的，不是所有智能体都统一这样做：完全可以不搞长期记忆，改成对整个历史信息做全文检索或语义检索。

       * 长期记忆到底是对完整历史聊天记录做检索，还是用记忆文件存关键重要信息，由开发者按业务动态决定。

   * **仓库记忆记什么**

       * 技术栈必须记：写新代码不能脱离既有技术另搞一套，要在既有技术栈内部写。

       * 已完成的功能与模块要记：新代码可能要跟之前的模块关联，得知道要不要关联、怎么关联。

       * 换业务就换内容：做工程造价预算，就应该把造价预算的经验性结论总结进长期记忆——每个项目业务不同，长期记忆存的内容一定略有不同。
