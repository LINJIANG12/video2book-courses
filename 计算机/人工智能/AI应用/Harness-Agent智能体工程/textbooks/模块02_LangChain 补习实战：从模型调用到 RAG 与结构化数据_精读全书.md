## LangChain 补习：连接大模型的桥梁与第一次实战调用
> 对应块：BLK08 | 覆盖分集：P23-P26 | 块标题（分集名）：《【补习篇】Langchain的核心》

如果你是 Java 程序员，JDBC 这个词一定不陌生；如果你写 Python，那边也有对应的东西，比如 PyMySQL，里面装的就是连接数据库的驱动。LangChain 在 AI 领域里扮演的就是 JDBC 这样的角色——两者有类似之处，特别是它们都作为**连接和集成不同系统的桥梁**。

所以 LangChain 本质上就是一座桥：它把大语言模型和你未来要开发的 AI 产品连起来。而且这座桥不一定只通向大模型，它还会和各种外部的东西建立连接——LangChain 扮演的是一种中介的角色，允许开发者利用特定的技术（比如 AI 或者数据库技术）与其他系统、其他应用进行交互。这种结构设计带来的直接好处是：大语言模型不仅能够处理文本，还能在更加广泛的环境中操作和响应，大大扩展了它的使用范围和有效性。

相信我一句话：未来如果真要把大语言模型应用在各行各业，你一定会用到 LangChain。为什么这么说？目前国内特别喜欢往应用方向开发，所以对国内的各种程序员来说，LangChain 很重要；国外关注的更多是怎么优化底层模型、优化算法。但说实话，优化算法需要大量的硬件设备——英伟达 H100、H200 这种高端显卡，一块卖几十万，40 万到 60 万美金甚至更高，这种卡我们不光是钱的问题，国内根本拿不到。所以国内的大公司想做算法调参和升级，不是完全做不到，但肯定有点难。那我们完全可以另辟蹊径：先往"大语言模型落地"这个方向做一些开发。再等个五年十年，模型本身已经很牛叉了，但再牛叉最后还是要落地。什么叫落地？就是要把大模型和人、和普通消费者使用的产品连起来，那你就得开发各种各样的功能性软件；要开发软件，就需要框架。LangChain 干的就是这个事情。

### 为什么要用它：两个理由

**第一个理由，数据连接。** LangChain 允许你把大语言模型链接到你自己的数据源——比如你自己的数据库、你自己公司内部的 PDF 文件或者 Word 文档。这意味着你可以使用模型从私有数据库中提取数据：和大模型交互、问答的时候，其中有一些回答的数据就来自我们私有数据库里提取的内容。这其实更加符合真实的业务场景。

**第二个理由，行动执行。** 它不仅仅可以提取你的私有数据，还可以帮助你根据这些信息执行一些特定的操作，比如发邮件——我们说一句话，LangChain 写好的程序就能帮我们做一些特定的事情。有人会问：没有 LangChain，普通的 OpenAI 能不能做？不能做，除非你在 OpenAI 的基础上再加一些代码，而且这个代码要加的比较多了；用 LangChain 这个框架，你的代码就写得少一些。这就是用它最重要的两个理由。

### 六个核心组件

LangChain 里面到底有哪些东西？核心是六件：模型、提示模板、链、代理、嵌入与向量数据库、索引。

| 组件 | 英文叫法 | 干什么用 |
| :--- | :--- | :--- |
| 模型封装 | Models | 包装各大厂的大模型，提供统一调用入口 |
| 提示模板 | Prompt Template | 避免硬编码文本，动态插入用户输入 |
| 链 | Chains | 把多个组件组合起来，解决特定任务 |
| 代理 | Agents | 让语言模型与外部 API 交互 |
| 嵌入与向量数据库 | Embeddings / Vector Store | 文本向量化与向量存储检索 |
| 索引 | Indexes | 搜索之前先对资料建立索引 |

**模型封装**是一个模型的包装器，允许你连接到各种大语言模型：GPT-4、GPT-3 这些 OpenAI 的模型都可以用，Hugging Face 的可以，GLM 提供的各式各样的模型也可以。0.2 版本之后，LangChain 支持的大模型至少有几十种，几乎涵盖市面上所有大公司比较著名的大模型，全都支持。它最牛的地方在于：写代码的时候想切换到另外一个模型，代码不用变。比如我一开始开发用的是 GPT-4，后来觉得国产的更好、更便宜，想切换成 GLM，代码一行不动，配置上改一下就行了。

**提示模板**让你避免用硬编码的文本来进行输入：可以动态地把用户的输入插入到模板中，形成一条完整的提示信息，再交给我们的大语言模型。模板还可以自己去定义。如果你真正用过 OpenAI 这样的大模型就知道，提问时这个 prompt（提示）是非常重要的——刚好 LangChain 里面专门有一个管理提示的东西，就是提示模板。

**链**将多个组件结合在一起，来解决一些特定的任务，并构建完整的语言模型应用程序。说白了，链就是把各个组件联合在一起，到底要联合哪些？你自己看着办，后面会讲。

**代理**允许我们的语言模型与外部的 API 进行交互。这个东西说实话非常重要。当然，这些都重要，没有一个是不重要的。

**嵌入与向量数据库**：现成的、稳定的向量数据库产品现在有很多；如果你们公司有向量数据库，LangChain 在开发的时候也可以直接连你公司的向量数据库。

**索引**：帮我们做搜索索引。比如想把一个官网文档里的内容交给 LangChain 来做搜索，那就要先基于指定的这些内容建立索引，然后才能在里面做搜索——做搜索之前，首先是要建立索引的。

### 底层原理：一个智能客服的完整链路

底层原理通过一个例子来讲：一个智能问答系统的工作流程。你可以把它理解成一个智能的销售客服——它接收用户的各种提问。

假设用户问了一个问题 question。注意，这个问题很可能跟我们公司的产品、服务，或者公司提供的数据有关系。所以第一步别急，先不要直接进入大模型：要先通过**相似性搜索**，在一个大型数据库或向量空间中找到与之相关的信息。这个相似性搜索，其实就是向量之间的相似度——原理之前讲过，就是拿两个向量的夹角，用余弦距离来做这个事情。

拿到相关信息之后，把它与原始问题相结合——这时得到的信息就多多了——最后封装成一个非常复杂的 prompt（提示），再传给我们的 AI 大模型。大模型处理后得到一个 answer（答案）。这个答案有两种去向：

- 它可能就是一段回答，直接传给普通消费者、传给用户；
- 它也可能需要**执行某个动作**。比如模型判断，对这个用户问题最好的处理，是去找一位非常专业的技术服务人员来和当前消费者直接交互，那么就需要拨号，或者把我们的信息流转给另外一个人——通过拨号、发邮件、或者消息转发的方式发出去。这就调用了 AI 系统外部的 API，由之前讲过的 Agent（代理）来执行：可能会执行一个 API 的调用，或者与外部系统进行交互，最终完成任务。

```text
用户提问 Question
   |
   v
相似性搜索（余弦距离度量向量相似度）
   |
   v
在向量数据库 / 向量空间中检索公司相关资料
   |
   v
检索结果 + 原始问题 --> 封装成一条完整的复杂 Prompt
   |
   v
大语言模型（LLM）
   |
   v
答案 Answer
   |
   +--> 只是一段回答 ----------------------> 直接交给用户
   |
   +--> 需要执行动作 --> Agent（代理）-----> 调用外部 API
                                          （拨号 / 发邮件 / 转发信息）
```

读图：问题先进检索、再进模型；答案出来后分岔——要么是纯回答直接返回，要么经代理落到外部动作上。

整个流程反映的是一个**数据驱动的决策过程**，其中包含了从信息检索、到处理、到最终行动的自动化步骤。记住一点：这个 answer 可能造成最终的行动，也可能直接就是一句回答——到底是行动还是回答，不确定，要根据用户问的是什么来决定。所以这种智能问答系统已经不是那种简简单单的人机交互对话了：它不单包括对话，还包括 AI 自动执行的一些动作——由用户提问，通过 AI 的决策去执行相关的动作。另外补一句，用户问题背后的数据，还可以来自我们自己公司内部，比如自己存的大型关系数据库或者向量数据库，都可以。

### 应用场景：会做事的 AI 才叫智能

LangChain 的应用场景非常广泛，包括但不限于下面三类。

**个人助手**：可以帮助你预订航班，还有自动转账、缴税等等。注意，预订航班就是我前面讲的"动作"——普通消费者问了一句话，AI 接收这个信息之后做出了决策，这个决策不是只给你回答一个答案，而是要自动地帮你实现航班的预订、自动地帮你实现转账缴税。这种 AI 助手就不是那种只会人机对话的助手了，那种助手太简单，是完全没有任何动作的；不单有人机对话、还能帮你执行动作的 AI 软件或功能，才更加的智能。

**学习辅助**：可以参考你提供的整个课程大纲，帮助你更快地学习材料。举个例子，最近我需要阅读国外某一个主题下的十篇或者一百篇论文——一百篇论文自己去看，要花多长时间？我可以把这 100 篇论文告诉 AI：你先去指定的地方搜索这 100 篇论文；搜完之后我去问一些问题，它根据论文里的信息来帮我们做回答；甚至还可以帮我们摘取论文里的内容，自动保存到一个 Word 文档中，或者自动生成一个 PDF 给我。后面这几步就是在执行动作了。这样的学习辅助，比只能人机对话的那种牛逼得多。

**数据分析和数据科学**：公司的数据、客户的数据、市场的数据，都能极大地促进数据分析的进展。

从这几个应用场景，大家应该已经发现了，LangChain 未来的应用是非常广泛的。作为一个 AI 大模型的开发人员，你是必须要掌握它的。

### 装环境：pip 两个库与 0.2 版本

安装是通过 pip 直接安装，我建议大家直接这样做。首先安装 LangChain 本身；如果你要用到 OpenAI 的模型的话，还需要安装 `langchain-openai`，它里面包括了 OpenAI 所有的模型。

```bash
pip install langchain
pip install langchain-openai
```

不指定版本的话，这两个命令默认只安装最新的版本，也就是 0.2。我建议大家也跟我一样使用最新的版本——你看我都用最新的了，你为啥不用？

版本的事可以打开 LangChain 官网的官方文档看（注意不是官网首页，是官方文档）。目前它只支持两种语言：JS 和 Python，我相信大家主流应该是 Python。文档里的版本是 0.2，想看 0.1 的话可以点版本切换。0.2 是 5 月 20 号才正式发布的，其实三四月份的时候 beta 测试版就已经出来了；到我录这节课为止，正式版才发布十多天的样子。

0.2 相比 0.1 改了多少？我把 0.2 的英文文档用心读了一遍，几乎每一个链接都点进去看了。从代码上讲主体差不多，大概改了 10% 到 15%。注意，它的升级不是功能上的——功能上还是那些功能——主要是往两个方向做升级：一个是**稳定性**（也就是安全性），避免了一些容易被拿去做 DoS 攻击的东西；还有一个是**兼容性**，兼容更多的大模型了。这两点对我们程序员来说是最好的。企业里面未来一定用的是 0.2，所以我们不用去管 0.1 到底是啥，只需要学会 0.2 其实就够了。

安装的时候会连带装上很多东西：SQLAlchemy——因为 LangChain 可以帮我们访问各种各样的东西，包括本地的数据库，尤其是关系数据库，会用到它；BeautifulSoup4——LangChain 还可以帮我们去做爬虫、爬数据，所以这个包也有；还有 JSON 的一些解析工具；以及 langchain-core、langchain-openai 这些核心的包。langchain-community 当时要是没看到也没关系，后面用到的时候发现缺了，我们再装。

### LangSmith：免费的监控与跟踪

在实操过程中，还会用到 LangChain 的一个监控工具：LangSmith。它是 LangChain 内部的一个项目，专门做监听、数据分析、日志分析。

为什么需要它？大模型都是根据 token 来计费的，这点之前课程中讲过。问题来了：我到底花了多少钱？我想统计一下，只能去大模型官网里面做统计。可我今天用这个大模型、明天用那个大模型，最后想看总共用了多长时间、总共花了多少钱，两个平台都得去看，太麻烦了。LangSmith 可以直接帮我们跟踪调用大模型 API 的次数、以及总共的 token 数量，帮我们做统计、做跟踪，非常爽。而且它是**免费**的，各位不用去纠结这个事情是不是要交费。

要拿到它的 API key，需要进入到 LangSmith 去注册。注意，这个 key 不是 LangChain 的 API key，是 LangChain 里面内部项目 LangSmith 的 API key，它的作用是帮我们做监控、做跟踪、做代码的跟踪、做 token 的统计等等。国内不翻墙就能访问，就是网速稍微慢了点。登录方式有三种：可以使用 GitHub 账号登录，可以使用谷歌账号登录，或者通过你的邮箱地址来进行注册登录，都可以，任选一种。

登录之后拿 key 的路径是：界面左下角点 Settings，第一项就是 API Keys。一开始这里是没有的，你要点 Create API Key 这个按钮，然后会进入一个窗口，需要填写一个描述信息——随便写，比如 `test`，写 `my test` 之类的都可以，个人用的就可以了——然后点击 Create，这样就能生成一个 API key。生成之后我建议大家立刻复制，保存到你自己的电脑上的记事本里面：这个 key 复制过一次之后，列表里就看不到了，要点进去才能再看到；不想要的话旁边也有删除，可以把它删掉。

> **易错点**：刚刚这个操作不做也行，不做就是没有代码的跟踪、没有提示数据的存储、也没有监控和大模型的数据分析。反正是免费的，我建议大家还是最好配上。

免费额度方面：LangSmith 针对单个用户来说是免费的，每个月 5000 次 trace（追踪）也是免费的，实际上我们做测试的话根本用不到。当然，如果你在公司里真的把它作为一个产品、用户量非常多的话，可能会超过每月 5000 次，超过就要收费了，页面上有收费标准。但不用它也完全可以——从来不存在"不用 LangSmith 就不能学 LangChain"这回事。

> **定义**：LangSmith 是一个构建生产级大语言应用程序的平台，提供调试、测试、评估、监控的能力，覆盖基于任何大模型框架构建的链和智能代理，并且可以与 LangChain 无缝集成——因为它本身就是 LangChain 的一个子项目。

它的主要作用逐条说：**调试与测试**——通过记录 LangChain 构建的大模型应用的中间过程，开发者可以更好地调整提示词等中间环节，来优化模型的响应；然后是**评估效果**、**监控性能**；还有**数据管理**——我们每次调用大模型的时候一定要提供输入，就是那个提示，LangSmith 会自动帮我们把它存起来，存好之后还可以帮我们做分析，以便于开发者更好地理解模型的提示、优化大模型的输入；再有就是**团队协作**、**可扩展性与维护性**。它作为一个子产品，核心提供的就是调试、测试、评估和监控这四件事。

### 第一次调用：环境搭好，裸调大模型

了解了 LangSmith 之后，接下来才正式开始开发。用 PyCharm 新建一个项目，名字随意（比如 langchain demo），解释器还是选之前已经创建好的虚拟解释器——不用再创建；如果列表里一时没有提示，自己手动找到那个已有的虚拟环境，选上点 OK 就可以了。这一步只是把环境搭好，两个核心的库前面已经装好了。

> **提示**：调 OpenAI 的模型需要网络可达（翻墙），而且要把 OpenAI 的 API key 配置到运行环境里。第一次运行就报错了，提示 OpenAI 的 API key 没有，在运行配置里加上才跑通——这个坑提前说在前面。

新建一个 Python 文件 `demo1.py`，演示怎么使用 LangChain 来调大模型。先把 LangSmith 的监控配置复制进来，其中有两行非常核心的代码：一行指定我们接下来的代码需要用到 LangSmith 来做代码的追踪；另一行是 API key，从你自己生成的 key 那里复制粘贴过来就可以了。追踪开关一定要写 `true`——不写的话它会用 V1 的版本，而我们当前安装的环境不可能是 V1，所以这里面一定要写 `true`，表示用的是 V2 版本。

```python
import os

os.environ["LANGCHAIN_TRACING_V2"] = "true"        # 必须写 true：使用 V2 追踪
os.environ["LANGCHAIN_API_KEY"] = "你的 LangSmith API Key"
```

然后就可以开始调大语言模型了。

**第一件事，创建模型。** 直接使用 OpenAI 的模型类，包从 `langchain_openai` 里面导：

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4-turbo")
```

`model` 参数就是模型的名字，比如 `gpt-4-turbo`，或者 `gpt-3.5-turbo`，都可以这样写；模型的名字从 OpenAI 官网上去看。所以你现在明白了吗？未来我要换不同的模型，只需要把这个字符串——这个模型的名字——改一下就可以了。

**第二件事，准备提示。** prompt 其实你可以理解为就是传 message，是一个中括号列表——为什么是中括号呢？因为我们可以传不同的角色。角色分为三种，之前讲过：系统、用户、AI。示例里先用了两种：

```python
from langchain_core.messages import SystemMessage, HumanMessage

messages = [
    SystemMessage(content="请将以下内容翻译成意大利语"),
    HumanMessage(content="请问你要去哪里"),
]
```

`SystemMessage` 给出任务设定（把下面的内容翻译成意大利语），`HumanMessage` 是普通用户说的话，也就是要被翻译的那句内容。

有了模型和提示，调用就非常简单，直接使用 `model.invoke`，里面传的参数是 messages，返回一个 result，打印出来：

```python
result = model.invoke(messages)
print(result)
```

运行之后，结果很快就出来了。控制台里输出的内容就是最后的意大利语译文，大概是"你要去哪里"的意思——意大利语我是真不会读，懂意大利语的同学可以自己看看这个 AI 的回答是不是对的，应该是对的。重点是这个 result：它是一个**非常复杂的对象**，里面除了 `content`，还包含了响应的元数据——返回的 token 数量，以及具体用的哪个模型，比如 2024 年 4 月 9 号快照的 gpt-4-turbo。

还可以切到 LangSmith 里看代码的追踪，里面就有一个统计。进到默认的项目里点进去，就能看到这一次调用：用的什么时间发的 input、OpenAI 返回的数据是什么样子、花了多少钱、一共多少 token——演示这一次是 46 个。这些监控、数据统计的工具就是 LangSmith；它之所以能监控，是因为我们用上了开头的那两行配置，尤其是需要那个 LangSmith 的 API key。

### 解析响应与链式写法：未来代码的标准形态

这种非常简单的方法返回的 result 对象太复杂了。我能不能把对象里的内容直接解析出来，只看那句话的内容，input token、返回的 token 数量这些都不想看？有办法，这就是**解析响应数据**：给 OpenAI 返回的响应数据配一个 parser（解析器）。

最简单的是字符串解析器 `StrOutputParser`，包来自 `langchain_core` 的 `output_parsers` 模块——output parser 就是输出（响应）的解析，把我们的响应数据解析出来：

```python
from langchain_core.output_parsers import StrOutputParser

parser = StrOutputParser()          # 空构造函数直接创建
result_str = parser.invoke(result)  # 同样用 invoke，传的是响应对象
print(result_str)
```

解析器也是调用 `invoke`，里面传的是 result 这个响应对象，返回解析之后的字符串。再运行一下，这时候你看到的是不是只有那句话了？这次和上一次的译文略有差异——估计在意大利语里"请问你要去哪里"和"你要去哪里"的语气、敬语差不太多，这个我确实不太熟，大家了解一下就好。总之 `StrOutputParser` 干的事，就是把 AI 返回的那句话给你拉出来，其他的全不要。

其实我们还有一种更加简单的写法，也是未来真正要写代码的形态。调大模型一共就这么几件事：

1. 创建模型；
2. 准备提示（prompt）；
3. 创建返回数据的解析器——它的好处就是把返回的数据变成你想要的类型的数据。一般来说未来我们要解析：可能需要把 OpenAI 返回的数据解析成字符串，也有可能解析成 JSON 格式，比如之前做过的自动书籍翻译案例，就是把 OpenAI 返回的数据解析成了 JSON；解析器还有其他好几种，未来还要学，这只是其中一个最简单的解释器；
4. 得到链（chain）：把模型和解析器连起来；
5. 直接使用 chain 来调用。

```python
chain = model | parser
print(chain.invoke(messages))
```

链里的竖线就是把各个组件连起来：这是解析器的组件，这是模型的组件，把它们连起来得到一个 chain，然后链自己去 `invoke`，message 传进去，结果直接打印。再运行，结果直接出来了，这样就比较简短。还记得理论部分讲的吗——链允许你将多个组件组合在一起，来解决特定的任务。我这个特定任务比较简单：就是调用一下 OpenAI，问一个问题，给我一个返回的答案。那么是哪些组件呢？这里用到了模型组件，其实我们还用了一个解析器的组件——这个解析器组件，前面列六个核心的时候我还没把它写进 PPT 里去。解析器有很多种：JSON 格式的解析器，还有可能要把数据解析成我们自己定义的 Python 类型——类似 Java 里 POJO 那种对象类型——也是可以的。

未来的代码都是这样子的，前面那种裸调的写法我们很少会采用了。这一讲写了一个最简单、最基本的案例，我们就从这个简单的案例开始入手，慢慢地一步一步把整个 LangChain 学会。

## LangChain 组件实战：提示模板、LangServe 部署与带记忆的聊天机器人
> 对应块：BLK09 | 覆盖分集：P27-P29 | 块标题（分集名）：《【补习篇】Langchain的提示模板》

各位小伙伴们，大家好。上一课我们用 LangChain 写了一个非常小的应用：调用大语言模型，帮我们做翻译——"请把下面这句话翻译成什么什么"。模型一调、结果一拿，案例是跑通了，但你要是接着往下用就会发现别扭的地方：提示词是写死的，一点也不灵活。这一讲我们就顺着这个案例，把 LangChain 里最要紧的几块知识补齐：它支持哪些模型、提示模板怎么把写死的提示词变活、怎么把写好的程序部署成服务让别人调，最后再做一个能"记住你"的聊天机器人。知识点不少，老规矩——全部通过案例来讲。

### 先把上节课的账算清：模型、解析器与追踪

第一个知识点：LangChain 支持哪些模型？官网上你可以看到，它支持了大概二三十种模型。比如要用 OpenAI 的模型，代码是一套写法；要用 Anthropic 的模型，是另一套写法——当然你得先安装一下，装的是一个叫 `langchain-anthropic` 的包；接下来你还可以用谷歌的模型，以此类推。官方文档里列得很详细，常用的模型就有十几种，这十几种的代码全都给你写好了，直接复制粘贴过来就能用。说实话，我现在 PPT 这一页的代码，就是从官网上原样复制粘贴过来的。

然后回到上节课的案例，盘点一下我们用到了什么。第一，怎么调用大语言模型，这个讲过了。第二，怎么使用输出解析器（OutputParser）。它是干嘛的？大语言模型返回的响应数据是一个非常复杂的对象，但我们只要那个最重要的核心结果，其他都不要，所以需要一个东西帮我们解析：解析成字符串、解析成 JSON 对象、解析成我们自己定义的 Python 类，都可以。上节课的案例里只用了最简单的"解析成字符串"，后面会专门开一个小章节、一个小案例，讲输出解析器的其他用法。

第三，使用 LangSmith 帮我们追踪应用程序。这个上节课提过：只要配好 LangSmith 的 API key，代码一跑，你整个项目用到了多少 token，都有非常明确的历史记录。这里大家可以再去看一眼：找到我们的 project，点进去，就能看到那次调用的完整输入——"请将以下内容翻译成意大利语……"——包括你的输入以及输出，还包括时间，一共有多少个 token，里面都告诉你了，而且连一共花了多少钱都帮你算出来了，清清楚楚。

### 提示模板：把写死的提示词变成活的

好，接下来就到本讲的重头戏——提示模板。未来在 LangChain 里，提示模板是一个非常重要的组件。

回到上节课的代码。你看前面这句话："请将以下内容翻译成意大利语"——之前的案例没有使用模板。没有模板，用起来肯定不爽，未来肯定不爽。为什么不爽？不灵活嘛。大家想想：今天翻意大利语，明天想翻英语，你是不是得改代码？所以接下来我们干脆还在这个翻译例子上做处理，把它改造成模板。

> **定义**：提示模板，其实就是我们输入给大语言模型的模板。

模板有专门的类，我们通过这个类的一个函数帮我们做这件事——`from_messages`，从一个消息列表里构建模板（这个类在 `langchain_core` 里，要导一下包）：

```python
from langchain_core.prompts import ChatPromptTemplate

# 定义提示模板
prompt_template = ChatPromptTemplate.from_messages([
    ("system", "请将下面的内容翻译成{language}"),
    ("user", "{text}"),
])
```

`from_messages` 接收一个消息数组，数组里一个一个元组括起来。里面传什么？不同的角色说不同的话嘛。我们有两个角色：一个是 system，一个是 user。system 里放那句固定的话——"请将下面的内容翻译成"，那到底翻译成意大利语、英语还是中文？这里我们用一个变量来替换。变量在模板里怎么写？就是大括号，大括号里面写上名字，名字你随便取，我们叫 `language`。未来我们就根据 `language` 这个参数名传参，传进去之后，你可以把句子翻译成任何语言——意大利语、英语，包括阿拉伯语，都 OK。

第二个元组是用户 user，逗号隔开。用户的整个输入我们都当成一个变量，这个变量叫 `text`——名字还是那句话，随你定义。定义好之后，未来就通过这个变量名把参数传进去。各位，这就是一个模板，已经有一份模板了。

模板有了，接下来要把模板、模型、输出解析器这三个组件，通过链把它们合在一起。模板一般放在前面，所以一样加个竖线，前面加上 `prompt_template`——`prompt_template | model | output_parser`，这样得到一个完整的链。`model` 和 `output_parser` 就是上节课案例里定义好的那两个对象，不用动。

有了完整的链，接下来就用它来调用——`chain.invoke`。调用的时候肯定要把参数传进去，但这里不能像以前那么干了：传参要用大括号括起来，因为它实际上是用字典的方式来进行传参。先写参数名 `language`——比如传 `"italian"`，翻成意大利语；你要翻成英语，就写 `"english"`，以此类推，这个参数是可以动态传的。然后是 `text`，随便写一句话，比如"下午还有一节课，不能去打球了"：

```python
# 模板 + 模型 + 输出解析器，串成一条完整的链
chain = prompt_template | model | output_parser

# 字典方式传参：参数名就是模板大括号里的名字
response = chain.invoke({
    "language": "italian",
    "text": "下午还有一节课，不能去打球了",
})
```

直接运行，走——结果直接出来了。"下午还有一节课"，so"不能去打球了"，这句话被翻成了意大利语。有个小细节挺有意思：这个"打球"，它给理解成打篮球了。那你要想翻别的语言呢？只要把 `language` 的值换一下就可以了。

```text
chain.invoke({"language": "italian", "text": "..."})
        |
        v
[提示模板] 把参数填进 system / user 消息里的 {language} 和 {text}
        |
        v
[模型] 收到完整的提示词，返回复杂的响应对象
        |
        v
[输出解析器] 从响应对象里抽出我们要的核心结果
```

读图：模板、模型、解析器用竖线串成一条链，参数从链头进去，干净的结果从链尾出来。

### 把程序部署成服务：LangServe 登场

这是这个翻译案例的最后一个知识点：使用 LangChain 里的 LangServe，把你的应用程序部署出去。什么意思？我不是写好了一个能翻译各种语句的应用程序嘛，那我还想让别人去调——让公司里其他人去调，或者让别的程序来调我的：别的 API、别的应用，比如别人的安卓程序、iOS 程序。那我就得把我这个程序部署成一个服务器，别人通过发 HTTP 请求来调它。学过 Java 后端或者 Python 后端的同学，一定明白我在说什么；没学过也没关系，照着做就行。

要干这件事，先安装 langserve。注意，装的是它的所有东西，后面加了个 `[all]`：

```bash
pip install "langserve[all]"
```

这里有个当场踩的坑给大家提个醒：我第一次装，死活装不上，为什么？其实就是翻墙——把代理去掉，马上就装好了。不过等会儿真正要调模型跑程序的时候，代理又得开回来，这是两码事，别搞混。

这套东西底下用到 WebSocket，还用到了一个叫 FastAPI 的东西。记住啊，FastAPI 是目前为止 Python 里性能最好的 Web 框架，它可以把我们的任何服务都部署成一个一个的接口。FastAPI 本身的具体用法，这节课没办法给大家展开讲，不过大家可以去 Python 课程里找，里面有非常详细的 FastAPI 教学。

好，先写个注释——把我们的程序部署成服务，以服务的方式让别人就可以调了。首先，创建 FastAPI 的应用，名字就叫 `app`：

```python
from fastapi import FastAPI

app = FastAPI(
    title="我的LangChain服务",
    version="v1.0",
    description="使用LangChain翻译任何语句的服务器",
)
```

`title` 传一个标题，值随你写。它是什么意思？就是我们到时候打开接口文档的时候，能看到整个应用程序的名称，你可以理解为部署之后的应用名字。`version` 是版本，表示你部署的这个服务的版本，由你决定，比如 v1.0，你也可以写别的。`description` 是描述，随便写。（写到这里的时候，PyCharm 里导包可能还报红——因为包还没安装完，没关系，代码先写完，等会再说导包的事。）

到这一步，其实只是创建了一个 FastAPI 的应用。接下来要添加路由以及启动。这部分我就不一个一个带着敲了，直接把我写好的代码复制粘贴过来，重点给大家讲一讲。添加路由是一个函数（要导包），关键是后面这个 `path`：

```python
from langserve import add_routes

add_routes(app, chain, path="/chain_demo")
```

`path` 表示请求路径，可以随便改——默认叫 chain，我们改名叫 chain_demo。未来别人要请求我们这个接口，就按照这个 `path` 来请求。顺便把文件里之前直接调用测试的几行去掉，那只是上节课的测试代码，启动服务的时候不需要它再跑一遍打印。

然后运行，直接右键运行就可以。启动起来之后，你发现它监听在 localhost 上——localhost 就是 Windows 的本地；写 localhost，就表示只监听 `127.0.0.1` 上，端口是 8000，日志里写得清清楚楚。

> **提示**：真要给别人调，监听地址写具体的服务器 IP 最合适；只写 localhost 的话，就只监听在 127.0.0.1 上，外面访问不到。

### 用 HTTP 客户端调你的服务

这是一个服务了，记住吧？是服务，就要像模像样地测。两种方式，第一种：模拟发送一个 API 请求，用工具。可以用 ApiPost，也可能你用过别的，比如 Postman——Postman 用的人可能多一点，我用的是国产软件 ApiPost，其实无所谓，到底用哪个都可以，网上随便下一个都行。

先说地址怎么拼。服务器监听在 localhost 上，所以地址写 `127.0.0.1`；启动时监听的端口号是 8000，这个地方也写着了，所以端口写 8000；然后是我们定义的路由，还记得吧——就是请求路径，路由名字叫 chain_demo，所以路径写 `/chain_demo`；chain_demo 后面还有一个 `/invoke`——这个是固定死的，就是表示"调用"的意思，要注意。

还有一件差点忘了说的事：一定是 POST 请求。传参也有规则：首先要设置传参类型是 JSON 格式（`Content-Type` 用 `application/json`），不能是表单提交的方式，这里要注意一下。参数方面，首先 `input` 是固定死的，这是整个参数的名字；那 `input` 里面传什么？这就跟我们的提示模板有关了——模板里定义了 `language` 和 `text` 两个变量，那就传这两个。

| 请求要素 | 值 | 说明 |
| :--- | :--- | :--- |
| 请求方法 | POST | 一定是 POST 请求 |
| 服务器地址 | `127.0.0.1` | 服务监听在 localhost，就是本机回环地址 |
| 端口 | `8000` | 启动日志里写着的监听端口 |
| 路由路径 | `/chain_demo` | `add_routes` 里 path 参数定义的 |
| 调用后缀 | `/invoke` | 固定死的，表示"调用" |
| 传参类型 | `application/json` | JSON 格式，不能是表单提交 |
| 参数结构 | 外层 `input`，内层放模板变量 | `input` 固定，内层由提示模板决定 |

所以请求体就这么写——请把"我要去上课了，不能和你聊天了"翻译成英语：

```json
{
  "input": {
    "language": "english",
    "text": "我要去上课了，不能和你聊天了"
  }
}
```

点击发送请求，稍等，返回结果里有个 `output` 字段，装的就是翻译之后的结果——"我得去上课了，没法再跟你聊了"的英文。你看，这个客户端模拟的就是别人来调我们写好的翻译程序。把你的 AI 服务"部署"出去，就是这个意思。

这段要是有些人听不懂，没关系，你就照着我这个做就行了；或者这个客户端你干脆不用，直接用 Python 代码来请求我们的服务——这就引出第二种方式。

### 换成 Python 代码当客户端

你要问了：如果我是真正通过别的代码去调，怎么办？OK，也可以，写一个客户端的代码，通过 Python 来调。新建 client.py，写个 main 函数，代码非常简单。

首先，要得到一个远程调用的客户端，它是一个类，叫 `RemoteRunnable`，从 langserve 里导包。构造的时候接一个地址——地址就是我们刚刚写的路由地址，但你注意，要把 `/invoke` 去掉！因为接下来我们真正调用的是它的 invoke 函数，等于说你在调 invoke 函数的时候，它会自动在后面给你加一个 `/invoke`：

```python
from langserve import RemoteRunnable

client = RemoteRunnable("http://localhost:8000/chain_demo")

# 传参：HTTP 里叫 JSON，Python 里叫字典，一回事
response = client.invoke({
    "language": "italian",
    "text": "你好",
})
print(response)
```

传参的话，HTTP 客户端里叫 JSON，Python 里就不叫 JSON 了，叫字典，一样的。`language` 传 italian——请帮我把"你好"这句话翻译成意大利语，就这意思。

你看整个客户端代码，我们自己实现了 AI 的功能吗？没有。但是服务器实现了，我们调服务器就行。

直接运行，走。注意啊，服务端得先跑起来——你看我这个服务一直没动；你跑起来之后就不要关了，你关了之后，别人肯定是访问不了的。客户端一跑，诶，没有打印？其实已经成功了，加一个 print 输出一下——这不就出来了吗，这就是翻译之后的结果，你看非常灵活。

所以现在明白了：未来我们写出一个真正的、切合消费者需求和实际的大语言模型产品，就可以把它部署成服务的方式，再给我们的其他应用程序、或者其他人去调。这种玩法，以后在企业开发过程中也是会用到的。

### 存历史的架子：store 字典与回调函数

保存聊天历史，我通过一个叫 `store` 的字典来保存。这个字典是什么意思？我们做的这个 AI 聊天，它是针对很多用户的——真的很多用户，所有用户的会话聊天记录，都保存到 store 里面。那以什么为 key？我用 session_id，每一个用户的 session_id 来作为 key；session id 肯定是可以自己去定义的。value 呢？就是我们的聊天记录——历史聊天记录对象。注意了：我们写的这个程序，不可能只针对一个用户，我要针对所有用户，而每一个用户每一次会话，都会有一个新的 session_id。

```python
# 保存聊天历史：session_id -> 历史聊天记录对象
store = {}
```

接下来定义一个函数，从 store 里找到当前某一个会话的聊天历史记录。函数起名叫 `get_session_history`，参数就是 session_id，字符串类型。这个函数实际上是一个回调函数——等会我们真正发送聊天的时候，要把它作为参数传进去。

这个函数里面的代码非常简单：你给我一个 session_id，我从 store 里给你返回当前这个会话的聊天历史。所以其实只需要做一个判断：看这个 session_id 是不是不在 store 里；如果不在，我就往里面放一个新的。放的这个历史聊天记录对象，就要用到 community 里面的一个类——`ChatMessageHistory`（聊天 message、history，聊天信息历史记录），先把它导进来：

```python
from langchain_community.chat_message_histories import ChatMessageHistory

def get_session_history(session_id: str) -> ChatMessageHistory:
    if session_id not in store:
        # 第一次聊：新建一份聊天记录放进 store
        store[session_id] = ChatMessageHistory()
    return store[session_id]
```

其他情况其实不用写 else——其他情况下都是直接从 store 里返回就可以了，所以最后一句 `return store[session_id]`。你看，这函数非常简单。

### RunnableWithMessageHistory：把记忆挂到链上

定义了这个回调函数之后，接下来我们就需要一个叫 `RunnableWithMessageHistory` 的对象——等会专门靠它来帮我们做聊天。名字里的 with message history，意思就是携带：每次运行聊天的时候，携带这个聊天历史记录。

```python
from langchain_core.runnables.history import RunnableWithMessageHistory

with_message_history = RunnableWithMessageHistory(
    chain,                    # 没有 chain 的话，传模型也行
    get_session_history,      # 回调函数：千万不要加括号！
    input_messages_key="my_msg",
)
```

它传的参数比较多，所以换行写。第一个参数传 chain——如果你没有 chain，传模型也可以。第二个参数，就是我们刚写的回调函数 `get_session_history`。

> **易错点**：这个回调函数千万注意，不要加括号！写 `get_session_history`，不要写 `get_session_history()`——因为这个函数是由 RunnableWithMessageHistory 这个类负责帮我们去调用的，不是你在这里手动调的。

还有一个参数：我们每次聊天输入消息的时候的一个键。因为接下来每次聊天，你都得给它一个键——定义一个键，就是输入我们聊天信息的键，所以叫 `input_messages_key`。这个键的名字随你定，爱叫什么叫什么，我就叫 `my_msg`。这个参数比较特殊——它是每次聊天时发送消息的键，所以必须在这里定义好。

到这里，架子就全部搭好了。前面架子搭好之后，后面写代码就非常方便了。来看一眼这套架子的全貌：

```text
用户调用 with_message_history.invoke(输入, config)
        |
        v
RunnableWithMessageHistory（负责每次携带历史记录）
        |
        |-- 从 config 里取出 session_id（如 "张三123"）
        |        |
        |        v
        |   get_session_history("张三123")   <-- 回调，由它自动调用
        |        |
        |        v
        |   store 字典：{"张三123": ChatMessageHistory}
        |   （没有这份记录就新建，有就直接取）
        |
        v
chain（模板 + 模型）拿着 [历史记录 + 本轮消息] 生成回答
```

读图：真正干活的是 chain，但每次运行都由 RunnableWithMessageHistory 按 session_id 从 store 里取（或建）对应的历史记录，带着一起跑。

## 从流式输出到搜索工具：LangChain 补习实战
> 对应块：BLK10 | 覆盖分集：P30-P33 | 块标题（分集名）：《【补习篇】流式输出的处理》

上节课的聊天代码我们写好了，今天一运行就发现问题：总体上看看没有毛病——会话的 id 都有了，每次聊天也都带着配置发过去——但还有个地方写得有问题：每次聊天除了发这句话，还应该把历史的聊天记录一起发，而我们恰恰没有留这个口子，历史记录根本没送出去。这很重要，我们就从这里补起。

### 先补一个洞：提示模板里少了历史消息的占位符

为什么历史记录发不出去？因为我们的提示模板中，根本没有"要发送的历史记录"这一项。这里少了一句话，少了一个占位符。

这个占位符是特殊写法，叫 `MessagesPlaceholder`，里面要定义一个 `variable_name`。说白了就是声明：你要发送的、真正的所有历史消息，它的键是什么。这个键你在哪儿定义了呢？就在前面定义历史消息的地方，我们这里叫 `messages`——两边必须保持一致。

```python
from langchain_core.prompts import MessagesPlaceholder

# 提示模板里补上历史消息占位符：variable_name 要与存放历史消息的键保持一致
MessagesPlaceholder(variable_name="messages")
```

这样消息模板里除了 `system`，还有你的所有历史聊天记录。要是没有这一句呢？那每次对话都是单独的，AI 完全不记得你前面说过什么。你们可以自己动手把这行注释掉，对比一下注释和不注释时回答的差别——一试就明白。

> **易错点**：`MessagesPlaceholder` 的 `variable_name` 必须和后面真正存放历史消息的那个键保持一致，两边名字对不上，历史记录就接不进来。

补好之后再运行。第一问打招呼，AI 回："你好，老肖，很高兴见到你，有什么可以帮助你的吗？"这是第一个问题的答案。第二问我问"请问我的名字是什么"，它答："你刚才已经告诉我你是老肖，如果你还有其他的名字或昵称，随时告诉我。"看到没？从 AI 大模型的这个回答，你就可以明确知道：它是根据上下文的历史记录来回答我的信息的。

### 流式输出：一个 token 一个 token 地返回

接下来讲另一个知识点：流式输出，就是一个 token 一个 token 地输出。

我们写第三轮对话，还是老办法，把上一轮的代码复制一份，这次要做特殊处理：返回的数据是流式的。关键改动就一处——调用的函数不再是 `invoke`，而是 `stream`。在 LangChain 里，如果你想要 AI 返回的数据是流式的，就必须用 `stream`。

| 对比项 | `invoke` | `stream` |
| :--- | :--- | :--- |
| 调用方式 | 一次调用，等完整结果 | 调用后拿到一个可循环的对象 |
| 每次得到什么 | 一个完整的响应 | 循环里的每一次响应都是一个 token |

`stream` 返回来的东西是一个循环，所以代码不能再像 `invoke` 那样一次接住，要换成 `for` 循环，一次拿一个结果。传参跟之前的 `invoke` 完全一样，只是还要传一个 `config`；这一整串太长，我们把它写成一行再断行格式化一下。

```python
# 第三轮对话：返回流式数据；问题参数跟前面 invoke 时一模一样，只是多了 config
resp3 = chain.stream(
    {"question": "请给我讲一个笑话，请使用英文回答"},
    config=config3,
)

for resp in resp3:
    # 循环里的每一次响应 resp 都是一个 token
    print(resp.content + "-")
```

注意这个 `print` 是写在 `for` 循环里面的——前面几轮的 `print` 在外面，打的是整段结果；这里每来一个 token 就打印一个，我在每个 token 后面加了一个 `-` 分隔符，这样你在屏幕上能清楚地看到 token 的边界，一个一个蹦出来。

这里还有个会话的小故事，值得你们记一下。第三轮最开始我用的还是前面那轮的 config，让它"用英文讲个笑话"，结果它确实一个 token 一个 token、用分隔符隔开地返回了——机制是对的——但回答却是中文的。我怀疑就是因为这个会话里前面聊的都是中文，它不可能突然改用英文给我回答。那怎么办？把之前的 config 复制一份，给第三轮一个全新的会话，里面定义一个新的 session id，我乱写了一个"李四"。其他地方都不变，就是换了一个 config。

```python
# 第三轮换一个全新的会话：复制一份 config，session id 换成新的
config3 = {"configurable": {"session_id": "李四"}}
```

再运行，返回的就是英文结果了，生效了。顺带一提：如果第三轮你换一个 session，那名字就找不到了——因为历史记录是按 session id 存的，换了会话就是一张白纸。

> **提示**：历史记录跟着 session id 走。想让一段对话"重新开始"，给它换一个新的 session id 就行。

回过头来把聊天案例复习一下。整个聊天案例其实就讲了两个知识点：一个是怎么保存历史记录——我们有一个专门保存历史记录的对象，叫 `ChatMessageHistory`；这个历史会话记录不但能存进去，还可以从它里面拿出来，都存在 store 里。大家可以把这个 store 打印一下，看看里面有什么东西，我这里就不打印了，你们自己去调试一下。

### 案例三总纲：四步走向检索增强

案例三：用 LangChain 帮我们构建向量数据库和检索器。这个东西我相信你们在未来的增强型生成 AI——也就是 RAG——里面肯定会用到；还不只 RAG，做智能化的搜索、智能化的检索，也需要用到向量数据库。

这个案例支持从向量数据库和其他来源检索数据，以便与大语言模型的工作流集成。这对应用程序来说是非常重要的——这些应用程序需要获取数据，作为模型推理的一部分来进行推理。说白了，大语言模型确实可以帮我们做推理，但我们想基于自己的数据：自己指定的一款数据、从自己数据库里拿出来的数据、或者指定某个网页里的数据。这个案例就有点类似检索增强（RAG）的大语言模型，后面我们会专门去讲。

"其他来源"在这个案例里其实并没有真的用上——数据源是我们自己设置的一组定死的数据。当然，未来数据从数据库里来，或者从其他地方来，也完全可以；比如下一个案例，数据源就要从网络上某一个网页里爬下来。

这个案例要用到一个新工具：LangChain 里面的 Chroma。它帮我们做什么？专门帮我们存储向量数据库用的东西。你可以理解为 Chroma 就是 LangChain 内置的一个向量数据库；当然，外面也有一些公司提供的向量数据库服务器，那些同样可以用。

我们拷贝一份原来的代码叫 demo3，聊天那些部分全部删掉，模型留着后面用。整个案例分四步，骨架先立起来：

```text
准备数据（一个个 Document 文档）
        │
        ▼
向量化，存进向量数据库（得到向量空间）
        │
        ▼
根据向量空间得到检索器（一个 Runnable 对象）
        │
        ▼
检索器与大语言模型结合，用 chain 串起来
```

先把数据准备成一个个文档；再把数据向量化、存到向量数据库里，得到一个向量存储；然后根据向量空间得到一个检索器；最后，检索器还要和我们的大语言模型结合在一起用。

### 把数据装进 Document

第一步，准备数据。这节课的数据不从别处获取，就是定死的测试数据。在 LangChain 里，数据最好都是一个一个的 `Document`，它来自 LangChain 的核心库（core）。

每一个 `Document` 代表一个文档数据——其实就是文本数据嘛，我们大语言处理的就是文本，不是关系型数据库那种结构化数据（当然，关系型数据库某个字段里存着大段文本，也一样可以拿来处理）。

`Document` 有两个属性：

- `page_content`：文本内容。每一个文档里的文本都放到这个属性里。比如未来我们要针对某一篇论文做向量数据库的检索，就可以把这篇论文里的所有文字——假设两千多字——全都放进 `page_content`。
- `metadata`：元数据，是一个字典。你可以理解为这个文档的摘要、文章的作者、文档的来源——键随你设置，爱填多少填多少。比如设个 `author` 表示这篇文章是谁写的，甚至设个日期表示它是什么时间发布的。

> **定义**：元数据——除了这篇文章核心内容之外的数据，都叫元数据。

我准备了五篇文档：狗、猫、金鱼、鹦鹉、兔子，组成一个文档数组。内容非常少，模拟一下而已：

```python
from langchain_core.documents import Document

documents = [
    Document(
        page_content="猫是独立的宠物，通常喜欢自己的空间。",
        metadata={"author": "老肖"},    # 元数据：字典，键随意设置
    ),
    Document(
        page_content="金鱼是初学者的流行宠物。",
        metadata={"author": "老肖"},
    ),
    # 另外三篇是狗、鹦鹉、兔子，写法完全相同
]
```

### 用 Chroma 把文档变成向量空间

第二步，实例化一个向量数据库。通过刚才说的 Chroma 来做，它需要自己先安装一下：

```bash
pip install langchain-chroma
```

```python
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

vector_store = Chroma.from_documents(
    documents,              # 第一个参数：文档列表，所有文档都放这里
    OpenAIEmbeddings(),     # 第二个参数：采用哪种技术来帮我向量化
)
```

`from_documents` 就是基于我们的文档来创建向量数据库。第一个参数是文档的列表；第二个参数是 embedding——你采用哪一种技术来帮我向量化。之前讲过，OpenAI 里面有一个专门做嵌入向量化的东西，就叫 embedding；LangChain 整合的这个类叫 `OpenAIEmbeddings`，它是一个类，所以要把实例创建出来再传进去。这句话的意思就是：使用 OpenAI 的向量化工具，帮我们把所有文档变成一个向量空间——其实准确来说，叫向量空间是最合适的。

有了向量空间有什么好处？之前讲 embedding 的时候也提过：有了向量空间，我们就可以计算每一个向量之间夹角的余弦值，根据余弦值就知道每个向量的相似度。接下来，就可以做相似度搜索了。

### 相似度搜索：分数越低，越相似

相似度搜索怎么做？调一个函数 `similarity_search`，它的参数是 query——就是你需要查什么东西。我们随便给它一个，比如搜索"咖啡猫"：去向量空间里查询，哪一个向量和"咖啡猫"这个向量相似度最高。

不过我把函数换了一下，用 `similarity_search_with_score`。不加 `with_score`，它就是帮你查指定的一个向量，在向量空间里有哪一个向量离它最相似；加了 `with_score`，我不但要查出结果，还要把相似度的分值也一起返回。

```python
results = vector_store.similarity_search_with_score("咖啡猫")
print(results)
```

跑之前别忘了 OpenAI 的 key，embedding 是要调 OpenAI 接口的，还是一样在运行配置里把它配好。

来看结果。搜"咖啡猫"，排第一的是猫那篇——"猫是独立的宠物，通常喜欢自己的空间"，分值 0.27。后面依次往下：

| 命中的文档 | 距离分值 |
| :--- | ---: |
| 猫是独立的宠物…… | 0.27 |
| 兔子 | 0.41 |
| 狗 | 0.413 |
| 金鱼 | 0.43 |

猫毕竟也是一个动物，所以它和兔子、狗都有一定相似度，但你很明显看到分值被拉大了：第一是 0.27，下一个就跳到 0.41，再到 0.413、0.43。

你看到的这个 0.几，其实就是我们所谓的距离。距离越大，越不相似；距离越小，相似度越高。所以在 Chroma 这个向量空间里，相似分数是这样子的：分数越低，相似度越高。

> **结论**：`similarity_search_with_score` 返回的分值是距离：距离越小，相似度越高；文档排得靠不靠前，看的就是这个分值。

如果你不想看到这个分数，直接调 `similarity_search` 就可以了。

### 检索器：把向量空间包装成 Runnable

到这里我们只是用向量空间做了搜索。但为了后面把它和 LangChain 里的聊天模型链接起来，还要把它变成一个 Runnable 对象。

这里补一个前面忘了强调的点：之所以我们能用 chain 把这些对象通过竖线 `|` 隔开、链接起来，是因为这些对象必须都是一个 Runnable 对象。你可以随便追踪一下，比如我们的 model——创建的是 `ChatOpenAI`，一个个往上追它的父类，最终实现的就是一个 Runnable。所有的 Runnable 对象，才能通过链串起来。

还记得 chain 是干嘛的吗？它就像链一样，把多个组件结合、整合在一起。但组件必须是 Runnable——而我们刚刚创建的 `vector_store` 不是一个 Runnable 对象，所以未来不方便用 chain 把它链接起来。

怎么办？根据向量空间来得到一个检索器——这个检索器就是一个 Runnable 对象：

```python
from langchain_core.runnables import RunnableLambda

retriever = RunnableLambda(vector_store.similarity_search).bind(k=1)
```

`RunnableLambda` 里面传一个函数——lambda 你可以理解为就是一个匿名函数。我们就把 `similarity_search` 这个函数传进去。注意我们不需要看分值，所以只调不带 score 的 `similarity_search` 就可以了。

> **易错点**：函数后面千万千万记住，不要加括号！你不是在这里直接调用它，而是把它封装到一个 Runnable 对象中，后面运行的时候，它会自动帮我们调用。

然后还可以再设置一下。前面演示搜索的时候，它会把所有有一定相似度的结果全部输出出来；其实我们不需要输出那么多，只要相似度最高的那个就行了。所以再调用 `bind`，里面设定 `k=1`——意思就是选取相似度最高的第一个返回。

这个 `retriever` 现在就是一个 Runnable 对象了，后面用起来就非常方便。而且它除了通过链来组合，还可以自己单独调。你看它有 `invoke`——各位，一看到 `invoke` 其实你就知道了：它也是一个 Runnable 对象。这里我们不调 `invoke`，调 `batch`，可以理解为匹配或者批处理：一次性检索多个。

```python
results = retriever.batch(["咖啡猫", "鲨鱼"])
print(results)
```

效果跟上面的搜索差不多，无非 `batch` 可以一次性帮我们检索多个向量的相似度。返回的是一个数组：第一个"咖啡猫"，跟它最相似的就是猫那篇文档——"猫是独立的宠物，通常喜欢自己的空间"；第二个"鲨鱼"，跟它最相似的就是鱼类那篇——金鱼是初学者流行的宠物什么的。很明显是对的，符合我们人类的语义。

> **提示**：检索器做的不是像百度那样的全文检索，本质上是一个相似度搜索。

当然这一步只是测试一下。我们最终是要把这个向量空间、这个检索器，和我们的 AI 大语言模型结合起来——刚刚讲的只是一些基本知识点，接下来就把它们接上。

### 检索器和模型结合：把上下文接进提示模板

为什么要结合起来？因为我们接下来写的这些应用程序，要把给定的问题与检索到的上下文结合起来——这样未来大语言模型给你的结果才相对准确，符合我们的一些特殊需求。

首先定义提示模板。这个 message 比较复杂，我们单独先定一下，为了方便采用三引号多行字符串。我们接下来的提问，是要结合当前向量空间里的向量数据来进行的，所以这样写：使用提供的上下文，仅回答这个问题。那这个问题到底是什么问题？用花括号定义一个变量 `question`——在模板里定义参数，这个之前讲过。上下文呢？也通过一个变量传进去，叫 `context`。

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough

message = """
使用提供的上下文仅回答这个问题：

{question}

上下文：{context}
"""

prompt_template = ChatPromptTemplate.from_messages([("human", message)])
```

这个模板最重要的就是里面要传两个变量：一个是你要回答的问题是什么，第二个是你的上下文是什么——上下文其实就是我们的向量空间，你可以理解为就是检索器。

`from_messages` 的传参是一个 sequence（序列）。那 Python 中什么是序列？元组是序列，列表是序列，字符串是序列；LangChain 里面还有 BaseMessage、提示模板这些也算。对 Python 的基础类型来说，元组、字符串、列表这三个东西是序列。我们用列表，列表里面放一个个提示文本；因为还要设置角色，所以我们用二元组——`("human", message)`。就这么简单，别搞那么复杂。

接下来通过链把各个组件连起来。你看是这样连的：第一个组件是参数字典；第二个组件是模板；第三个组件是模型——model 之前注释掉了，把它打开。

```python
chain = (
    {"question": RunnablePassthrough(), "context": retriever}
    | prompt_template
    | model
)

resp = chain.invoke("请介绍一下猫")
print(resp.content)
```

为什么模板不能直接放在最前面？因为一开始你应该先把模板里面的参数准备好，然后才是模板。参数里 `question` 用 `RunnablePassthrough` 来构建——这是一个"假问题"，等会儿再去传。它的意思是：允许我们将用户的提问，之后再传递给提示模板和模型。构建 chain 的时候，我其实并不知道要提的问题是啥；这个问题是动态传过来的，真正把问题提出来、传进去，是在调用 `invoke` 的时候。所以这里先用 `RunnablePassthrough` 占个位，运行时再把真正具体的问题传过来。

那 `context` 呢？上下文已经确定了，只需要把检索器给它就可以了——在组件组成这个链的时候，就已经把上下文传过去了。所以调用 `chain.invoke` 时只传问题，`context` 不用传。

来看效果。问题就一个非常简单的："请介绍一下猫"。你想想，如果我就问这么一个问题，直接问 OpenAI 的模型，它的介绍一定是非常笼统、非常一般的一个介绍——就是在百度里搜索能搜到的那种关于猫的介绍。但现在我们传了上下文，它的回答是："猫是独立的宠物，通常喜欢自己的空间。"你看这句话来自哪？很明显，来自我们提供的数据。答案和我们的上下文紧密结合在一起：它是根据我们提供的上下文文本数据，来回答我们提的问题的。当然，如果你提的问题跟上下文一点关系都没有，那它可能就直接通过 OpenAI 回答了。

这个案例最重要的就是两件事：学会怎么样去构建一个向量空间；以及构建好的向量空间，怎么样通过我们的 chain 和其他组件组合起来。这才是最重要的。

### 代理：让只会输出文本的大模型执行动作

案例四：用 LangChain 构建代理。代理前面讲过，英语单词叫 Agent。代理是干嘛的？执行一些动作的。

为什么大模型需要代理？因为我们的大语言模型本身是无法执行动作的，它只能输出文本。你可以问它问题，它可能会给你回答，但事实上有一些问题的答案它回答不了。比如我想问一下"北京最近的天气怎么样"——它回答不了。为什么？因为这是实时的数据，而大语言模型训练用的数据可能是几个月前的、甚至是几年前的，它根本没办法知道最近北京的天气怎么样。它想真正给出正确答案，就必须要执行相关的动作，比如实时搜索一下天气网站的数据——这就是动作。而大模型本身是无法执行这个动作的。

所以，代理就是使用大语言模型来作为推理引擎，确定要执行的操作、以及这些操作的输入应该是什么。

> **定义**：代理（Agent）——用大语言模型作为推理引擎，由它来确定要执行什么操作、以及操作的输入是什么。

这里注意顺序。用户问一个问题，问题叫 Q 吧，问给谁？肯定问给我们的大语言模型。大语言模型回答的时候，有时候没办法直接回答，需要执行一些动作，这时它就会得到一个推理结果——让你去执行一些动作——于是自动去调用我们的代理，让代理去执行相关的动作；代理进行处理、得到一些信息之后，再交给我们的大语言模型，由大语言模型最终返回给用户。当然也有可能大模型根据你问的问题直接给了答案，那就直接返回了。

```text
用户提问 Q
   │
   ▼
大语言模型 LLM（推理引擎）
   │
   ├─ 能直接回答 ──► 直接把答案返回给用户
   │
   └─ 答不了（需要实时信息 / 要执行动作）
          │
          ▼
     得到推理结果：去执行相关动作
          │
          ▼
     自动调用代理，代理执行动作拿到信息
          │
          ▼
     信息交回大语言模型，整合后返回最终答案
```

图上这条链路就是代理的全部：能不能直接答，由大模型这个推理引擎来判断；要动手，就交给代理去执行，结果再回流给大模型。

在 LangChain 里要创建代理，还需要一个新的包，叫 langgraph，我们原来没装过，先安装一下，把这条安装命令在你的环境里执行就可以了：

```bash
pip install langgraph
```

我们先看没有代理的情况下，模型会怎么回答。直接调用 `model.invoke`——它的输入可以是一个字符串，也可以是一个序列，类型可以很多，因为提示模板的输入确实可以非常丰富。我们传一个 `HumanMessage` 的列表，问题是"北京最近天气怎么样"：

```python
from langchain_core.messages import HumanMessage

result = model.invoke([HumanMessage(content="北京最近天气怎么样")])
print(result)
```

答案出来了："很抱歉，我无法提供实时数据，包括当前的天气。我建议查看可靠的天气预报网站，或者使用天气应用程序来获取北京的天气更新。"这就是大语言模型的小缺陷——说白了一句话，它没办法针对这个问题给出相应的答案，意思就是：你自己去查。

可是问题是，我就要这个答案，我不想自己去查天气网站。怎么办？这种情况下就需要代理。

### Tavily 搜索工具：先单独用起来

要用代理，得先把工具创建出来——实际上就是一个搜索引擎的工具。LangChain 里面内置了工具，可以轻松地使用 Tavily API 帮我们做搜索引擎、搜索一些数据。

```python
from langchain_community.tools import TavilySearchResults

search = TavilySearchResults(max_results=2)
result = search.invoke("北京的天气")
print(result)
```

这个类来自 `langchain_community`——这个库里有很多工具，其中有一个专门的 `tools` 库，里面就有 `TavilySearchResults`。

> **易错点**：类名结尾有个 s——`TavilySearchResults`。少写了这个 s，自动导入都出不来。

初始化的时候要传一个参数 `max_results`。这个搜索引擎工具会帮我们去搜索互联网中的数据——记住，它不是说去百度里搜，它里面存了一些元数据，具体的一些常用的公共网站它都有。以天气为例，它会搜很多很多跟天气有关的网站，每个网站都会搜回一些相关数据；但我们最终只想让它返回两个，所以加 `max_results=2`，表示返回的结果只有两个值。你写三个也行。

先直接试这个工具——现在它还没有和大语言模型进行整合。调用 `search.invoke`。各位，一看到 `invoke` 其实你就知道了：这个 search 也是一个 Runnable 对象。它会自动去做文本匹配、向量匹配，匹配之后就知道你要查的是天气、而且是北京的天气，然后给你返回两个不同网站上的结果。

第一次运行会报缺 `TAVILY_API_KEY`。这个工具可以免费用，不过需要你先得到一个 API key。很简单：到它的官网搜 API key（课程资料里的网址就是它），页面上有个获取 API key 的按钮，点击它需要先登录——可以用谷歌或者其他网站的用户来登录，我是直接用谷歌的用户名登录的。登录之后就能看到自己的 API key，复制下来，放到运行配置的环境变量里，名字是大写的 `TAVILY_API_KEY`，值就是你刚刚复制的那个。你们自己的话也需要去注册登录一下，很简单，免费的；一个月用量到了之后它才会收费。企业里开发要看情况，如果你的访问量一天有几十次甚至几千次，可能才需要考虑收费——具体怎么个收费法我还没找到，大家可以自己去找一下。

配好之后再运行。它返回的是一个数组——为什么是数组？因为它最多返回两个结果，放到一个数组里。每一个结果都有一个 `url`，就是它去哪个网址上搜到的；还有一个 `content`，搜到的内容是什么；另外还有 `name`。不过内容是英文的，为什么？因为它优先去国外的网站上搜索——其实国外的网站也有关于北京的天气预报。如果搜的是国内网站，返回的数据里面肯定就是中文了。

### 绑定工具：迈向代理的第一步

现在把这个搜索工具变成代理的工具。做法是：调用 model 的 `bind_tools`，把工具绑定到我们的模型上。

```python
llm_with_tools = model.bind_tools([search])
```

`bind_tools` 接的参数是一个 sequence 序列——要么是列表，要么是元组，要么是字符串。为了方便，我们直接用中括号把 `search` 括起来再传进去。你要是直接放 `search`，它不是序列，所以代码应该这么写，这一点要能快速地看出来。

这句话的主要目的就是让模型绑定工具。绑定之后，我们的大语言模型就会自动根据模型里的工具来做一些选择。那选择之后的效果是什么样子的？实际上到这里我们还没用到代理——现在只是在模型里面去绑定工具，因为它有很多种灵活的用法。怎么样在模型里面使用代理，下一节我们再继续详细地聊。

## 让模型学会自己动手：Agent 代理的使用与 RAG 开篇
> 对应块：BLK11 | 覆盖分集：P34-P35 | 块标题（分集名）：《【补习篇】Agent代理的使用》

接着上一节讲。现在我们已经把工具绑定到模型上了，那绑完是不是就能直接用了？我现在就可以拿它去问大语言模型问题了。不过这一讲你会看到一件有意思的事：模型"知道"该调工具，跟工具真的被调起来，中间还差一个角色——代理（Agent）。把这件事讲透之后，我们再顺势开一个新案例：用 LangChain 构建 RAG 对话应用。

### 绑了工具的模型，先问它两个问题

先补一个小尾巴。上一节演示的时候，`bind_tools` 我没有做赋值，其实它是会返回一个值的——把这个值接住，取名叫 `model_with_tools`，顾名思义，这个模型是携带了工具的：

```python
model_with_tools = model.bind_tools(tools)
```

它照样是一个 Runnable 对象，所以可以直接 invoke。invoke 里面传什么？就传一个用户的提问，跟之前的写法一样。我本来随手打了个招呼当输入，后来想想那不算个问题，干脆换成正经问题，方便对比。接下来把结果打印出来——打印这里有意思的地方来了：结果会有两个。为什么会有两个？因为这个模型绑定了工具，绑定工具之后，模型会自动推理：你问的这个问题，它是不是可以直接通过模型返回给你？第二种情况，就是模型没办法知道答案，于是把你这个问题交给工具去处理。所以返回值里有两块东西：`resp.content` 是模型直接返回的内容，`resp.tool_calls` 是工具的回调——你可以理解为工具（将要）返回的内容。

```python
# 第一个问题：与工具无关
resp = model_with_tools.invoke([("user", "中国的首都是哪个城市")])
print(f"Model Result: {resp.content}")
print(f"Tool Calls: {resp.tool_calls}")

# 第二个问题：模型答不了，需要借助工具
resp2 = model_with_tools.invoke([("user", "北京的天气怎么样")])
print(f"Model Result: {resp2.content}")
print(f"Tool Calls: {resp2.tool_calls}")
```

问了两个问题，我们看看打印出来有什么不同，运行：

| 对比项 | 问题一：中国的首都是哪个城市 | 问题二：北京的天气怎么样 |
| :--- | :--- | :--- |
| `resp.content` | 中国的首都是北京 | 空 |
| `resp.tool_calls` | 空 | 一条调用 Tavily 搜索天气的指令 |

前面两行是第一个问题的结果。这个问题不需要借助工具，模型直接就把"中国的首都是北京"答出来了，`tool_calls` 那里是空的，什么都没有。第二个问题"北京的天气怎么样"，模型是回答不了的，于是反过来了：模型返回的内容是空的，同时给你一个工具的回调。打开看，它得到的是一条去专门搜索天气的指令——一个 JSON 格式的字符串，通过 Tavily 这个搜索工具来帮你搜天气，里面写着要搜索的关键词（北京的天气），还有这条调用的 id。

> **注意**：记住，这只是一个搜索的指令。模型其实并没有真正去搜索，只是得到了一个"该去搜索"的指令而已。

通过这几行代码你就可以发现，我们的大语言模型是非常智能的：它能根据用户问的问题，判断到底要不要去调它的工具。要调，就返回一条调用工具的指令。但这里面它真的把工具调了吗？还没有，其实没有真正调工具。真正要想把工具调起来，是要代理去帮我们调的。所以上面讲了那么多，还没讲到代理——现在把这四行打印注释掉，留下两行注释，把刚才的知识点钉住：

```python
# 模型可以自动推理：是否需要调用工具，去完成用户的回答
# 但它只会给出调用指令，真正执行要靠代理（Agent）
```

整个判断过程长这样：

```text
用户提问
   │
   ▼
绑定了工具的模型（model_with_tools）
   │
   ├── 模型自己能答 ──► content 有答案，tool_calls 为空
   │
   └── 模型答不了 ───► content 为空，tool_calls 里出现
                        一条工具调用指令（JSON）
```

读图：同一个绑定工具的模型，对两类问题给出两种截然不同的返回；但无论哪种，它都停留在"判断 + 下指令"这一步。

### 创建代理：真正把工具调起来

创建代理，用到的是前面我们新安装的那个包（langgraph）里的一个函数：`create_react_agent`。你可以把它理解为"创建一个工具的调用器"——因为前面绑定工具的模型并没有真正调用工具，给出的只是一个调用工具的指令，这一步就是来补上执行的。

```python
from langgraph.prebuilt import create_react_agent

agent_executor = create_react_agent(model, tools)
```

两个参数：把模型传进去，再把 tools 传进去。tools 本身就是一个序列——一组工具执行器的集合，最好的做法就是直接把前面定义好的 tools 整个传进来，不用重新造。这里还有个细节别忘了：走了代理这条路，上面 `model.bind_tools` 那一行就不需要了，绑定这一步可以划掉了，模型和工具都交给 `create_react_agent` 统一安排。变量名我起作 `agent_executor`——准确来说，它是"代理的执行器"。

接下来用代理帮我们去回答用户的提问。还是 invoke，但传参变了：这次的参数是一个字典。字典里的键是固定死的，叫 `messages`；冒号后面把用户的提问放进去。列表里每一项我写成 `("user", 问题)` 的元组——这个 key 不是固定的，给它加个 key，主要是为了后面取值的时候方便。因为 invoke 返回的值也是一个字典，我们传进去的是什么键，就根据这个键去取它的返回值：

```python
resp = agent_executor.invoke(
    {"messages": [("user", "中国的首都是哪个城市")]}
)
print(resp["messages"])
```

第一个问题实际上是不需要用到代理的，不过我照样问一遍，看看不用工具的时候，AI 是不是也能智能地帮我们分辨出来。运行，答案出来了：中国的首都是北京。再看它返回的数据长什么样——是一个消息对象组成的数组，这里只有两个对象：第一个叫 HumanMessage，就是你的问题本身，仅仅是用户的一个提示；第二个叫 AIMessage，你可以理解为就是大语言模型给你返回的问题的答案，content 是"中国的首都是北京"，后面还跟着一堆关于 token 用量的信息。到这就结束了，没有第三个对象了。

第二个问题就有意思了，它会返回一个非常特殊的对象：

```python
resp2 = agent_executor.invoke(
    {"messages": [("user", "北京的天气怎么样")]}
)
print(resp2["messages"])
```

同样是先返回一个 HumanMessage，就是你的问题、用户的提示；第二个对象也是 AIMessage——不过它的 content 是空的，没有东西。往下翻，还有第三个：ToolMessage，工具返回的 message。两种返回放在一起看：

| 对比项 | 问题一（模型自己能答） | 问题二（需要动用工具） |
| :--- | :--- | :--- |
| 返回对象个数 | 2 个 | 3 个 |
| HumanMessage | 用户的问题 | 用户的问题 |
| AIMessage | content：中国的首都是北京 | content：空 |
| ToolMessage | 没有 | 有，排在下标 2 |

所以你要真正拿到想要的内容，就得取第三个对象。数组下标从 0 数起，第三个对象下标是 2，它里面有个 content，内容就是搜索结果：

```python
print(resp2["messages"][2].content)
```

运行，最后这一行打印出来的，就是搜索引擎帮我们搜出来的真正的答案。回想一下：这个答案之前是我们自己手动调用工具拿到的；现在交给代理，它自动推理、自动执行，把结果原样带回来了。内容里包含两部分结果——因为定义工具的时候指定了 `max_results=2`——每条结果带着来源 URL，是网页上搜到的英文描述，说的就是北京的天气怎么样；第二条来自另一个网页。英文的自己翻译一下就行，反正内容我们已经拿到了，就是从 AI 的返回里取出来的。

那如果未来你真正在企业里面做项目，其实只要加一个判断就可以了：看第二个对象 AIMessage 的 content 是不是为空。为空，就去取 ToolMessage 里那个值；不为空，直接把 AIMessage 里面的 content 拿出来用就行。

> **易错点**：写这段代码时括号一定要配对，而且绝不能混进中文括号——现场我就因为一个中文括号、少一个中括号编译不过，检查了半天才找出来。

把这一讲关于代理的主干串起来：AI 与代理整合之后，AI 会自动进行推断和推理，根据用户的问题决定是否调用相关的工具；需要调用时，由代理执行器去把工具真正调起来，执行完把结果返回。返回的数组里是三种消息对象：HumanMessage（用户的提示）、AIMessage、ToolMessage（工具的信息）。整条链路画出来就是：

```text
invoke({"messages": [("user", 问题)]})
        │
        ▼
  模型推理：要不要用工具？
        │
        ├─ 不用 ──► [HumanMessage, AIMessage]（AIMessage 直接给答案）
        │
        └─ 要用 ──► 代理真正执行工具调用
                      └─► [HumanMessage, AIMessage(content 为空), ToolMessage]
```

读图：需要工具的问题之所以返回三个对象，中间多出来的那一步，正是代理替你执行了工具调用。

### 换个场景：为什么需要 RAG

接下来进入案例五：通过 LangChain 构建一个 RAG 的对话应用。先说句实在话：未来你在实际生产环境中，大概率做的就是这种 RAG 对话应用。

RAG 是啥意思？它是一种增强型的大语言模型的方法，通过引入额外的数据来实现。为什么需要引入额外的数据？我们都知道，大语言模型的数据来自互联网上的一些数据——尤其是谷歌、微软这些公司，它们拿到了非常高质量的、专门用来训练大语言模型的数据。但实际上在某个公司内部，公司内部的数据一般是不会拿去训练大语言模型的。所以你想对公司内部的数据做 AI 问答，单独一个大语言模型是做不到的——它压根没见过这些数据。解决办法，就是引入额外的数据。

引入额外数据的方法有很多种，这一讲讲一种比较通用的：用一个工具，或者说一个爬虫，自动去网络上帮我们把相关的内容拿下来，比如某人写的一篇博客、某人发布的一篇论文。我们不叫"爬"，叫"加载"——其实本质就是把它爬下来，这件事由 document loaders（文档加载器）来完成。

这个案例用的是网上一篇文章——一篇专门讲大语言模型与 Agent 交互、整合的英文博客。你其实不用在乎它是英文的，换成中文博客也一样。这篇博客很长很长，里面还有代码、图形，引用了很多其他的博客和论文，总而言之是一篇包含很多内容的博客。要让一个人从头到尾看完，肯定得花特别多的时间。那我能不能先把它交给 AI，然后再问这个 AI 一些问题——我的问题，答案就从这篇博客里面帮我去找？这样人的效率就会大大提高：我们看博客不再是漫无目的地从头扫到尾，而是通过问问题，直接找到想看的内容。

### 实现思路：五个步骤

构建这个 AI 对话应用，思路是五个步骤：

```text
加载数据 ──► 分割 ──► 存储 ──► 检索 ──► 整合生成
```

读图：先把博客数据加载下来；然后做分割——一篇博客可能有 10 万字，比如一篇 10 万字的论文，你不可能把这整个 10 万字作为一个整体放进向量空间，那可能不合适，所以要把它切割成比较小的一块一块，针对这些小块来建立索引、构建向量空间，这样再传递给大模型才有意义；存储就是用向量空间帮我们存；检索是用户提问时把相关的内容找出来；最后一步，把我们的模型和检索器进行整合，得到我们想要的答案——这个答案，就是基于我们引入的额外数据生成的答案。

大概就是这么一个思路。接下来一步一步来，先从加载数据说起。

### 加载数据：把一篇博客装进来

回到 PyCharm。我在原来代码的基础上直接复制一份，叫 demo5，把用不上的东西清一清：第 15 行注释掉就可以了（其实留着它也不报错），其他的全部干掉，只留一个 model——model 暂时其实用不上，等后面用到的时候再把它打开。

要加载的数据有很多种来路：可能来自你本地的数据库，可能来自公司本地的一篇 word 文档、一篇 PDF 文档，也可能本地没有，是互联网上的一篇博客、一篇论文。我们这个案例以互联网上的一篇博客为例，所以第一步"加载数据"，加载的就是这篇博客的内容数据。

LangChain 里有个现成的工具帮我们完成这件事，叫 `WebBaseLoader`，来自 `langchain_community`——community 就是一大堆工具的集合，上节课用的那个网络搜索工具，其实也在里面。

#### 两个参数：爬哪里、怎么解析

先看第一个参数 `web_paths`。它要传的是一个字符串，或者一个序列化的字符串——意思是允许你一次爬一个网页，也可以爬多个网页，多个网页就放在一个列表或者元组里。举个例子，假设要爬两个网页，列表里逗号隔开，再写另一个 URL 就行；我们这个案例就一篇博客：

```python
import bs4
from langchain_community.document_loaders import WebBaseLoader

loader = WebBaseLoader(
    # 第一个参数：要爬取的网页地址；多个网页用列表/元组，逗号隔开接着写
    web_paths=(
        "https://…",   # 本案例：那篇讲大模型与 Agent 整合的英文长文
    ),
    # 第二个参数：透传给 BeautifulSoup 的参数
    bs_kwargs=dict(
        parse_only=bs4.SoupStrainer(
            # 只解析这三个类选择器包含的内容
            class_=("post-header", "post-title", "post-content"),
        )
    ),
)
```

第二个参数那里多解释一句：`header_template` 可以不传，我们真正要传的是 `bs_kwargs`。为什么要传它？因为这是一篇网页，网页里是一个一个的标签。你打开页面源代码看，全是一堆标签——但这些标签对我们有用吗？没用。做 RAG 的交互式问答，其实只需要文本：标题的文本，发布日期、作者的文本，再加上正文的内容，我就要这三部分。这三部分藏在网页的标签里，所以得有一个帮我们解析网页标签的解析器。如果你学过爬虫就知道，爬虫里专门解析 HTML 标签内容的解析器叫 BeautifulSoup，简称 BS4；之前安装 langchain_community 的时候它会自动安装，这里导入一下就能用。

`bs_kwargs` 接的是一个字典，所以用 `dict` 来包，里面按名字传参数：第一个名字叫 `parse_only`，表示"仅仅解析哪些内容"；解析器用 `bs4.SoupStrainer`。SoupStrainer 的参数里，按标签名筛的那个其实不用传，我们只要传 `class_`——也就是类选择器。

#### 去网页里找类选择器

`class_` 里该填什么？BeautifulSoup 负责帮我们解析整个 HTML 文档，但整个文档里到底要解析哪一块、要拿哪些内容，得先观察：你要取的内容在哪个标签里。举个例子，我想把标题拿出来，就在页面源代码里搜标题文字——找到了，标题在 h1 标签里，它外层的类选择器是 post-header，标题本身是 post-title。一般来说，我们用 BeautifulSoup 解析文本内容，是根据 id 或者类选择器来定位的；这里没有 id，就用类选择器。怕单词写错的话，直接从源代码里复制那一段就可以了。

那为什么我解析的是 post-header，而不只写 post-title？因为如果你只写 post-title，它只会帮你解析出标题；但标题下面还有一个 div，里面是这篇博客发布的日期、作者——这些我也要。写 post-header 就行，它把这个 div 也包进去了，你顺着标签的结束位置一看就知道。单独写 post-meta 去取那个 div 也行，两种写法都可以；我们就写两个：post-header 和 post-title，这样标题和作者、日期这些信息就都截下来了。

接下来是正文。正文放在一个什么样的标签里？往下找，正文被一个大的 div 整个包起来，从源代码第 297 行那个 div 开始，一直包到最后。想直接在源代码里翻它的结束标签，说实话真不好找。最好的办法是选中这行，用浏览器的"检查"去看：鼠标放上去，页面上立刻高亮定位，一眼看出来这个 div 从头到尾包含了所有的文章内容。找到了，它的类选择器叫 post-content——怕写错照样复制粘贴过来。

也就是说，我要解析这三个类选择器——post-header、post-title、post-content——里面所包含的文本内容。

#### load 出来一个 Document

解析完之后，把它变成文档，一行代码：

```python
docs = loader.load()
print(len(docs))
print(docs)
```

代码写得很少。运行一下，看看解析出来的文本是什么样子：docs 是一个数组，长度只有 1——整篇这一篇博客就是一个文档。打印出来看，这个 Document 你应该很熟悉，之前讲过它的结构：

- `metadata`：原数据，里面的 `source` 就是这篇文档的来源，也就是它的网址；
- `page_content`：文档的内容。开头是标题，接着是作者、发布时间这些原数据信息，再往后就是长长的正文——内容非常多，几万字肯定是有的。

> **提示**：Document 的 `metadata` 与 `page_content` 两个属性，前面的章节拆解过，这里只是换了个数据来源，结构没变。

文章这么大，我们不可能直接拿它去建向量空间，这样不合适。所以接下来做第二件事：切割。

### 切割大文本：RecursiveCharacterTextSplitter

为什么一定要切？把话说全：切割对索引数据、以及把内容传递给模型是很有用的——不能把整个几万字的一篇文章直接丢给模型，大块的数据很难去搜索，而且不适合模型有限的上下文窗口。

这就要用一个新类：RecursiveCharacterTextSplitter，从 LangChain 的文本切割模块里导入：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
```

先别急着切博客，拿一小段文本把这个切割器试明白，试完再放到正式代码里。构造这个切割器的时候，第一个参数其实是分隔符——但实际上没必要传：大部分情况下，我们的文本是没有固定分隔符的。比如按行来切割就不合适，一行不一定是一句话。我们想让它智能地帮我们做切割，靠的是两个参数：`chunk_size`，表示每一个片段最多包含多少个字符，演示阶段我随便写个小的，20；`chunk_overlap`，允许相邻片段重复的字符数，先写 4——什么叫重复 4 个字符？运行一下你就知道了。

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=20,      # 每个片段最多 20 个字符（演示用，故意设小）
    chunk_overlap=4,    # 相邻片段允许重复 4 个字符
)

res = splitter.split_text(text)   # 传入测试文本，切完得到一个数组
for s in res:
    print(s + "***\n")
```

调用 `split_text` 把文本传进去，切完得到一个数组；遍历打印，每个片段后面补一个 `***` 加换行，切成了几片、每片是什么，一眼就能看清。

#### 小文本试切

看输出。第一片是 hello world——hello world 明明不够 20 个字符，为什么后面还跟了个 how？因为 chunk_size=20 表示每个片段最多 20 个字符，hello world 凑不满，切割器就把后面的 how 也拉进来凑。再看下一片，它又从 how 开头——这个 how 就是重复的，由 chunk_overlap=4 这个参数决定：相邻片段之间最多重复 4 个字符，为的是保证每一句话的完整性。所以如果你的单词长一点，这个值也要跟着调长一点；你要是写成 2，how 这种三个字母的短词就没办法整体重复，它只能拿两个字母来做重复——那就没有意义了，我们肯定要以单词为单位。再往后看，thanks I'm fine 是完整一句话，machine learning class（机器学习的分类）也是一句话——这样切出来，说实话是蛮智能的。

有一点要说清楚：输出里一行不一定是一句话，它是一个片段。因为片段最大就 20 个字符，一句话超过 20，也只能被切成两段。但它不会把一个单词从中间切开——你翻一遍输出就能发现，这一点确实蛮智能。

#### 正式切割文档

真用的时候，20 肯定不合适，片段也太小了，要调大：chunk_size 调成 1000，也就是一个片段包含 1000 个字符；chunk_overlap 也从 4 调大，200 这个量级（100 也可以）。刚才测试用的小文本注释掉。那这次要切的是谁？想想也知道——切我们的文档，就是上面加载出来的 docs：

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,    # 一个片段最多 1000 个字符
    chunk_overlap=200,  # 相邻片段重复约 200 个字符
)

split_docs = splitter.split_documents(docs)   # 切的是 Document 列表
```

`split_documents` 跑完，得到一个一个的片段。到这里，五步里的加载数据、分割就都完成了。接下来是第三件事：把这些片段存储起来，再从存储里得到一个检索器——存储的代码我们之前也讲过。怎么存、怎么检索，下节课接着讲，这一讲先到这里。

## 会话式 RAG 问答应用：从检索链到历史感知检索器
> 对应块：BLK12 | 覆盖分集：P36-P37 | 块标题（分集名）：《【补习篇】构建RAG问答应用(二)》

继续回到第五个案例，把 RAG 对话应用往下做。前面两件事已经完成：第一，加载了一篇博客的数据；第二，把整篇博客切成一小块一小块，每一块最多占 1000 个字符——这是我们在参数里设置的。接下来要补齐的，就是那张流程图里剩下的部分。

### 流程全貌：数据从哪来，走到哪去

先把整张图摆出来：

```text
加载文档（互联网上的 / 本地文本文档 / 关系型数据库）
        |
        v
切分：长文章切成一个个片段（每片最多 1000 字符）
        |
        v
向量化：用 Embedding 把每个片段变成向量
        |
        v
存储：向量存进向量数据库（向量空间）
        |
        v
检索器：用户提问先检索出相关片段
        |
        v
检索结果 + 提示模板 --> 大语言模型 --> 给出答案
```

读图一句话：前四步是"知识入库"，最后两步是"问答"——问题先过检索器，再把检索内容和提示一起交给大模型，由它给出答案。

数据从哪来？可能是互联网上的，也可能是你本地的文本文档，还可能是关系型数据库的——后面的案例会专门讲数据库这种情况。本地的文本文档就得自己去读：之前的课程里我们教过怎么读 PDF、把 PDF 里面的文本拿出来，道理是一样的。

那要不要切？看文章体量。一篇文章本来也就一两万字，那你就不用切；十万字以上的大文章，才有必要切。所以第三件事，就是把大到一定程度的文本文章切成一个一个的片段。

### 向量库存起来，检索器变出来

切完之后要向量化、存储。存储用一个我们之前讲过的类——Chroma：

```python
splits = text_splitter.split_documents(docs)  # 切出来：每个片段是一个 document
vector_store = Chroma.from_documents(splits, OpenAIEmbeddings())
```

函数叫 `from_documents`，因为我们手里得到的是一个个的 document。这些 document 从哪来的？就是 split 切割之后的一个个片段，每一个片段就是一个 document，把它们传进去。第二个参数是做向量化的 embedding，我们还是采用 OpenAI 的。

> **易错点**：`OpenAIEmbeddings` 是一个类，要创建对象使用，后面一定要加括号。

有了存储，接着把它变成检索器，以便后面根据用户的问题帮我们做检索：

```python
retriever = vector_store.as_retriever()
```

就这么简单。到这里，向量空间、检索器都齐了。图不用多讲，重要的是把代码实现出来——接下来就是和大模型整合。

### 提示模板：给 AI 一个定位

整合的第一件事是定义提示。这是一个提示模板：一部分通过 system 角色传给 AI，一部分通过 human 角色（也就是用户角色）传给 AI。

```python
prompt = ChatPromptTemplate.from_messages([
    ("system",
     "You are an assistant for question-answering tasks. "
     "Use the following pieces of retrieved context to answer the question. "
     "If you don't know the answer, just say that you don't know. "
     "Use three sentences maximum and keep the answer concise."),
    MessagesPlaceholder("chat_history"),
    ("human", "{input}"),
])
```

注意：我们的文本内容都是英文的，所以提问的时候最好也用英文去问。

system 这段话，说白了就是给 AI 一个定位：你是一个助手，一个专门做问答任务的助手；使用下面检索器检索出来的内容去回答问题；如果不知道答案，就直接说你不知道；如果知道，最多用三句话来回答，并保证答案简洁。归拢一下就是：AI 要先去我们指定的这篇博客里检索，再根据检索到的内容给我答案；检索不出来或者不知道，就说不知道；知道，就尽量简短地告诉我答案。

`MessagesPlaceholder("chat_history")` 是用来记录提问和回答的历史的。为什么要有它？因为我们是问答系统，问答系统不可能只问一个问题。这个键名是我随手定义的——之前第二个案例里我们把它叫 `messages`，其实你用别的字符串来表示这个名字都可以。每一次的提问，都是从 human 的 `input` 这个变量传进去的。

### 组装两条链：先建提问链，再挂检索器

模板准备好了，接下来创建链。这次采用一种全新的方式——通过函数调用来得到链。

第一条链用内置函数 `create_stuff_documents_chain`，意思是创建一个作用于多个文档的链——这里还没涉及搜索，就是把多个文本整合进一条问答链。它要传两个参数：第一个是大语言模型 LLM，把前面定义的 model 传进去；第二个是提示模板，就是我们刚定义的那个。

```python
chain1 = create_stuff_documents_chain(model, prompt)
```

要看清楚这条链做了什么：它只是把模型和提示整合起来，仅仅是一个"提问的链"，没办法帮我们做检索。链本身也可以理解为一个组件，所以我们给它取名叫 chain1。

第二条链调 `create_retrieval_chain`，retrieval 就是检索器的意思：

```python
chain2 = create_retrieval_chain(retriever, chain1)
```

第一个参数传检索器 retriever，第二个参数把 chain1 传进去。想想 chain2 里包含了什么？chain1 负责帮我们做问答，chain2 在问答的基础上增加了一个检索器——它可以先帮我们做检索，然后再做问答。

### 第一次跑通：三个坑

先试一把，看看有没有效果：

```python
resp = chain2.invoke({"input": "What is task decomposition?"})
print(resp)
```

invoke 里要传参：一个字典，键写 `input`——这是模板里定义的变量名——值就是你的问题。我问的是"什么是任务的拆解"，这个问题其实就来自我们那篇博客里的相关内容，拿它来问最合适。

运行之前把 OpenAI 的 API key 配好。一跑，坑就一个接一个来了。

第一个坑：报错说预期是字符串或者字节数据，实际传入的不是。检查报错的第 45 行——传的是 docs，好像没错啊？docs 是什么？是 document，之前我们打印过的。真正的问题在这一行调用的函数不对：调成了 `split_text`，应该是 `split_documents`。

```python
# 错误：docs 是 Document 对象的列表，split_text 期望的是字符串
# splits = text_splitter.split_text(docs)

# 正确：切割文档对象，用 split_documents
splits = text_splitter.split_documents(docs)
```

如果你切的是文本、拿到的是字符串，用 `split_text` 没问题；但现在你给的是 document 对象，那就得切割文档。

第二个坑：一条提示，说缺少某个环境变量。这不是报错，只是一个提示，而且那个环境变量我们根本不用，不用管它。

第三个坑：报错说缺少 history。这个其实是我们自己在模板里埋下的——模板里确实写了 `chat_history`，但历史记录我们还没有去保存。所以先把涉及历史记录的部分注释掉，这一块等会儿补，先看看这个问题能不能被回答。

> **易错点**：模板里声明了 `chat_history`，调用时却没有历史可传，就会报缺少 history 的错。要么先把这段注释掉，要么等历史记录功能补上再跑。

这次跑通了。打印出来的结果非常多：有 input，有 context，还有 answer。我们只要答案，把打印改成按键取值：

```python
print(resp["answer"])
```

### 验证：答案真的来自那篇博客吗

答案出来了，可它跟我们的文档内容相关吗？得去博客里对一对。我把博客翻译成中文，方便找答案。博客里关于任务分解是这样说的：思维链已经成为在复杂任务中增强性能的标准提示技术——让模型一步一步地思考，利用更多的测试时计算，把困难的任务分解成更小、更简单的任务；它可以把任务分成多个可管理的子任务，并对模型的思维过程做出解释。我们问的"什么是任务拆解"，答案和这个对上了。

有个细节要留意：你把 AI 的答案直接复制到原文里是搜不到的——它不可能照着原文给你回答。那怎么验证？把答案放进翻译器翻译一下，对照着看。AI 给的答案是：

> 任务分解，就是将一个复杂的任务分解成更小的、更易于管理的部分或者步骤的过程。像思维链（CoT）和思维树（Tree of Thoughts）这样的技术被用于增强这一过程，分别允许详细的逐步推理和探索多种推理可能性。这种方法有助于管理复杂性，并提高规划和解决问题的执行阶段的清晰度。

说实话，这个答案比我们自己看网页的中文直译反而更准确、更看得懂一些。那它是不是紧跟着我们的博客的？是的。反过来想：假设没有这篇博客，你直接去问 OpenAI 同样的问题——什么是任务分解——你得到的答案一定不是这样子的。

到这一步，我们完成了第一件事：把大模型以外的数据和我们的模型整合起来，得到一个增强型的 RAG 大语言模型问答系统。不过它还没有历史记录——问答不可能只问一句，这块马上补。

### 检索器也需要上下文

先把难点说清楚。针对一篇人写好的博客做提问，这种提问注定是答疑式的、聊天式的，所以一定要有提问的历史记录。按一般的做法——之前第二个案例就是这么讲的——构建链的时候直接用 `MessagesPlaceholder` 把问答记录传进去关联上下文，模型理解了历史，上下文就接上了。一般情况下，这样做就够了。

但在这个案例里，光让模型理解上下文不够——查询检索器也需要上下文才能被理解，否则检索器自己就会出问题。

举个例子。假设我是张三，你是李四，我们俩对话。张三先问："请问任务的分解是什么？"李四回答完，张三接着问："请问他有哪些方法可以做到？"第二个问题里的"他"是什么意思？人肯定是能理解的——"他"就是任务分解，你是在问任务分解有哪些方法。大语言模型也一样，你只要把聊天的或者问答的历史记录给它，它就能理解上下文，知道"他"指什么。

问题出在检索器上。这个检索，是由大模型生成一个检索指令去执行的。你总不能拿"他有哪些方法"这句话当关键词，直接扔进检索器里做相似搜索吧？请问它能匹配到最相似的一些向量吗？匹配不到，或者说很难搜到我们想要的结果。所以这是一种非常特殊的情况。

解决方法：添加一个子链。这个案例里会有两个链，其中一个大的链里包含一个子链。子链拿的是最新用户的问题和历史聊天记录——注意，第一个问题的时候可能没有聊天记录，问到第二、第三个问题之后，历史就攒起来了——并且在问题引用历史信息的地方，重新进行表述。"他有哪些方法"要重新表述成"任务分解有哪些方法"。你可以简单地认为，这是在构建一个新的、历史感知的检索器。

> **定义**：历史感知的检索器——能结合对话上下文，把引用了历史的问题改写成独立表述之后再去检索的检索器。子链的目的就一句话：让检索过程融入对话的上下文。

### 子链：把问题改写成"独立问题"

这个案例比较复杂，注释写清楚一点：这是子链的提示、指令提取模板。先看它的 system 指令：

```python
contextualize_q_system_prompt = (
    "Given a chat history and the latest user question "
    "which might reference context in the chat history, "
    "formulate a standalone question which can be understood "
    "without the chat history. Do NOT answer it, just "
    "reformulate it if needed and otherwise return it as is."
)
```

逐句翻译一下：给我聊天历史，以及最新的用户问题——这个问题可能会引用聊天历史中的上下文；请你改写出一个"独立的问题"，一个不依赖聊天历史也能被理解的问题；不要回答它！需要改写就转述改写，不需要就原样返回。记住，这句话是给 system 的，是告诉 AI 大模型的。

接着用它组装子链的提示模板：

```python
retrieval_history_template = ChatPromptTemplate.from_messages([
    ("system", contextualize_q_system_prompt),
    MessagesPlaceholder("chat_history"),
    ("human", "{input}"),
])
```

三件套：第一个是 system，放 AI 的定位，就是上面那段指令；第二个放历史记录——传历史记录要用 `MessagesPlaceholder`，聊天历史你得给它一个键，这个键爱填什么填什么，但要跟后面传参的地方保持一致；第三个是用户最新的问题，键还是 `input`。

有了模板，才真正开始创建子链：

```python
history_chain = create_history_aware_retriever(
    model, retriever, retrieval_history_template
)
```

参数：第一个是大语言模型 model；第二个是检索器 retriever；第三个是提示模板，就是刚定义的 `retrieval_history_template`。这就是一个子链了。当然，这个子链我们不直接用——它后面还要合并到一个大的链里面去。

还有一处要收拾干净。你可能会问：前面测试的时候不也是两条链吗？那两条很好理解，就是把没有检索器的提问链和检索器连起来。现在检索器已经在子链里加进去了，所以把原来的 chain2 注释掉，相关的测试也不要了，只留 chain1——里面就是模型，加上让模型理解上下文的那个模板。

### 会话历史：按 session_id 存取

接下来解决保存历史记录的问题，代码之前写过：

```python
from langchain_community.chat_message_histories import ChatMessageHistory

store = {}

def get_session_history(session_id):
    if session_id in store:
        return store[session_id]
    store[session_id] = ChatMessageHistory()
    return store[session_id]
```

store 是一个字典：以每一个会话的 id 作为键，以该会话所有的历史记录对象作为值。`get_session_history` 按会话 id 取历史：这个 id 已经在 store 里，就直接返回对应的记录；不在，就新建一个 `ChatMessageHistory` 存进去再返回。`ChatMessageHistory` 来自 langchain 的 community 包。这个函数之前讲过，这里不再多说。

### 父链与会话包装：RunnableWithMessageHistory

现在把两个链组合起来，创建一个父链：

```python
chain = create_retrieval_chain(history_chain, chain1)
```

注意，`create_retrieval_chain` 的第一个参数除了检索器，也可以是一个 Runnable——这里传的就是前面那个子链，因为子链本来就是干检索的，所以把它放到第一个参数；第二个参数是之前的 chain1。整合之后，得到一个完整的链。

整个结构现在是这个样子：

```text
用户提问 input
    |
    v
父链 chain（create_retrieval_chain）
    |
    +--- 子链 history_chain（历史感知检索器）
    |        输入：聊天历史 chat_history + 最新问题 input
    |            |
    |            v
    |        模型把问题改写成"独立问题"
    |            |
    |            v
    |        检索器 retriever --> 相关片段
    |
    +--- chain1（问答链）
             输入：检索到的片段 + 提示模板
                 |
                 v
             模型 --> answer（最多三句话的简洁答案）

最外层再包一个 RunnableWithMessageHistory：
按 session_id 存取会话历史，自动接上 chat_history
```

读图一句话：问题先被子链改写成不依赖历史的独立问题，交给检索器取回相关片段，再由 chain1 结合提示模板生成答案；最外层负责按会话保存和取回历史。

有了完整链，还要做会话化包装。先创建一个可调用的 Runnable 对象，之后用它去 invoke 会方便一些——因为这里面要传参，我们最终要得到一个真正意义上完整的、包括传参的链：

```python
result_chain = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="chat_history",
    output_messages_key="answer",
)
```

这几个参数一个一个看：

| 参数 | 传什么 | 要注意什么 |
| :--- | :--- | :--- |
| 第一个参数 | 要包装的链，就是上面的父链 `chain` | 它接的是一个 Runnable，也就是一条链 |
| `get_session_history` | 按会话取历史记录的函数 | 千万不要加括号——传函数本身，不是在这里调用它 |
| `input_messages_key="input"` | 用户输入问题的键 | 要跟模板里 human 的变量名保持一致 |
| `history_messages_key="chat_history"` | 保存历史记录的键 | 要跟模板里 `MessagesPlaceholder` 的键保持一致 |
| `output_messages_key="answer"` | 返回结果的键 | 之后取答案就按这个键来取 |

> **易错点**：`get_session_history` 只传函数名，不要加括号。加了括号就成了在这里把函数调掉，而不是把"按会话取历史"这个能力交给包装器。

### 两轮提问实测："它"终于被理解了

第一轮提问：

```python
resp1 = result_chain.invoke(
    {"input": "What is task decomposition?"},
    config={"configurable": {"session_id": "张三1234"}},
)
print(resp1["answer"])
```

invoke 里要传两个东西：第一个是字典，键 `input`，值是用户的问题；第二个是 config。config 不用提前创建，直接写在调用里：先是一个 `configurable` 键，后面跟一个字典，字典里定义 `session_id`——会话的 id，随便写的。

第二轮，问题变了。不能直接把"任务分解"这个词写进问题里，我们问的是：

```python
resp2 = result_chain.invoke(
    {"input": "What are common ways of doing it?"},
    config={"configurable": {"session_id": "张三1234"}},
)
print(resp2["answer"])
```

"What are common ways of doing it?"——这个"it"代表什么？对我们人类来说，我们知道它指的就是任务分解，整句翻译过来就是"任务分解有哪些常用的方法"。但如果它没有上下文，这个答案肯定是乱七八糟的，不符合我们的要求。

> **易错点**：两轮提问的 `session_id` 必须一致。必须在同一个会话之内，它才能识别"它"指的是什么；你要是把 id 改了，它根本识别不到。

跑一下。第一个问题的答案，和我们最初问"什么是任务分解"时一样，把任务分解的定义讲清楚了，没问题。第二个问题的答案一出来，第一句就是"执行任务分解常用的方法包括"——后面还没看完你就知道，答的就是"它有哪些常用方法"。对照博客，三种方法都在：任务分解可以通过 LLM 完成，配一个简单的提示（比如"实现某件事有哪些步骤"）；可以通过特定于任务的指令（比如"写一个故事大纲"）；还可以结合人工输入来指导分解过程。而且我发现，这个答案比网页里直接的翻译更准确、可读性更高——不知道你们是不是也有这种感觉。

### 反例：换一个会话 id

再做一个反例，看看离开上下文会怎样。把第二个问题的会话换到另一个 session——换成李四的会话，只改 session_id 这一处：

```python
# 反例：只改 session_id，换成李四的会话（新 id 随便写，只要不是张三那个）
resp2 = result_chain.invoke(
    {"input": "What are common ways of doing it?"},
    config={"configurable": {"session_id": "李四001"}},
)
print(resp2["answer"])
```

李四的会话里没有前面那段聊天历史，它理解不了"它"指什么。这回 AI 给的答案是：我不知道，根据你提供的上下文，无法得到这个问题的答案。第一个问题不受影响——它不依赖历史，照样答得出来。但第二个问题，没了上下文就彻底答不上来。历史记录是绑定在会话 id 上的：id 一换，上下文就丢了。

到这里，一个正儿八经的 RAG 大模型应用案例就完整跑通了。这个案例真的有用。

### 这个案例能拿来做什么

想想未来我们自己开发产品。比如专门分析学校里每个学生写的论文：我懒得自己看，把论文交给 AI 处理完之后，问它一些非常核心的问题——如果你真的是某一个科研方向的教授或者科学家，你问的问题可以直接问到最核心的部分。然后看 AI 给的答案对不对：如果答案是错的，那大概率是这篇论文本身有问题，我再去细看论文到底错在哪。这就是非常快速、高效地帮我们解析论文、解析文章的方式。

## 当大模型连上数据库：LangChain 的表格数据问答
> 对应块：BLK13 | 覆盖分集：P38-P39 | 块标题（分集名）：《【补习篇】Langchain读取数据库》

先问你一个问题："请问销售部下面有多少人？"你要是一时答不上来，太正常了——我哪知道你们公司销售部有多少人。上个月卖了多少订单、总共销售了多少金额，这些数据你们公司的销售数据、部门数据、人员数据，全都躺在公司的关系型数据库里。只要你会写 SQL，直接去数据库里查一下，答案马上就有。

但问题是，现在我自己不会写 SQL，或者说我就是不想写 SQL。那怎么办？把问题交给大语言模型：它根据你的问题，结合数据库里表的字段，自动生成 SQL 语句；拿着 SQL 去数据库里执行；执行的结果再交回给大模型，跟你的问题一结合，最终给你一个答案。这就是本案例要做的事——用 LangChain 把关系型数据库中的数据作为数据源，让 AI 大模型针对这些数据做问答、做摘要这类文本处理。

其实它不光能做文本处理。数据库的查询操作它可以执行，增删改其实也都可以，只是要在数据库里执行各种操作的话，需要代理（agent）去实现。本案例介绍的是在数据库表格数据上构建问答系统的基本方法，链（chain）和代理都会涵盖到。两者最主要的区别在于：代理可以根据需要多次循环查询数据库来回答问题，而链相对简单一些，代理能够执行的次数、循环的次数更多，当然也更复杂。

### 整体思路：问题进，答案出

把整个流程画成一张图，就是下面这样：

```text
用户提问："请问销售部下有多少人？"
                     │
                     ▼
┌───────────────────────────────────────────┐
│ 大语言模型：问题 + 表字段 → 生成 SQL       │
└───────────────────────────────────────────┘
                     │  拿着 SQL 去数据库执行
                     ▼
┌───────────────────────────────────────────┐
│ 关系型数据库：执行 SQL，得到查询结果       │
└───────────────────────────────────────────┘
                     │  结果返回
                     ▼
┌───────────────────────────────────────────┐
│ 大语言模型：问题 + 查询结果 → 自然答案     │
└───────────────────────────────────────────┘
                     │
                     ▼
     "员工表中有五条数据" —— 完整的自然语言回答
```

读这张图就三步走：先生成 SQL，再执行 SQL，最后把问题、结果合在一起作答。中间那一步的"执行"，用链也好、用代理也好，都会帮你做。

对用户来说，这就非常爽了。整个数据库对用户来说就像个黑匣子：他不知道数据库里有哪些表，甚至不知道数据库在哪，也不知道每个表里有哪些字段。他只知道一句话——公司所有的数据，包括部门的数据、人员的数据、商品销售的数据，全部在公司的关系型数据库里面，别人是直接访问不到的。我们写好一个程序，让大语言模型去整合这个数据库，来回答用户想问的问题。只要用户的问题可以被转换成 SQL 语句，它就会转换成 SQL 去查；如果你问的问题不需要查库，大模型直接给你一个答案。

了解完这个思路你会发现，在未来的企业实际开发过程中，这个案例的用处是非常大的。

### 连接数据库：SQLAlchemy 出场

要把大语言模型和关系型数据库整合，你必须先连接数据库，这是绕不开的第一步。LangChain 里面用的是 SQLAlchemy 来解决这件事。SQLAlchemy 连数据库也需要一个驱动，总体方式就是调用一个函数，给函数传一个数据库 URL 的参数——这个函数你不用去记，它是 SQLAlchemy 内部的，关键是把 URL 写对。

这个 URL 的格式是这样的：

```text
dialect + driver :// username : password @ host : port / database ?charset=utf8

方言 + 驱动 :// 用户名 : 密码 @ 主机 : 端口 / 数据库名 ?charset=编码格式
```

方言（dialect）就是告诉你连的是哪种数据库，你别把"方言"这个词搞得很复杂。冒号斜线是固定的；用户名和密码中间用冒号隔开；@ 符号后面接数据库的主机名和端口号，端口号可以省略，MySQL 默认就是 3306；最后接你要访问哪个数据库，后面还可以再指定一个编码格式。

SQLite 这种小型数据库支持得很简单，它没有什么方言讲究，`sqlite://` 后面直接接 SQLite 的 db 文件路径就可以了，而且要用绝对路径。UNIX 或者苹果电脑一种写法，Windows 是另一种写法，Windows 上还可以在字符串前面加个 `r`。

如果你用的是 MySQL 这样的关系型数据库，连接写法有三种：

| 连接写法 | 用什么驱动 | 说明 |
| :--- | :--- | :--- |
| `mysql://` | 默认 DBAPI | 需要在你电脑上额外装 MySQL 连接器，太麻烦，一般不用 |
| `mysql+mysqldb://` | mysqlclient | 用哪个驱动，就安装哪个 |
| `mysql+pymysql://` | PyMySQL | 我这里用的就是这个 |

前面都是以 `mysql` 开头的——`mysql` 就是方言，它只负责告诉你这是什么数据库。第一种不加驱动，因为它用的是默认的 DBAPI，默认的话还需要在你电脑上装 MySQL 的连接器，麻烦；所以我们一般用下面两种。用了 `mysqldb` 就要安装 mysqlclient 这个库，用了 `pymysql` 就安装 pymysql，安装方式就是最普通的 pip：

```bash
pip install pymysql
# 或者
pip install mysqlclient
```

> **提示**：数据库的 URL 地址要是不会写，直接从网上抄一份就行。每一种数据库网上都有对应的 URL 写法，你记不住规律没关系，复制粘贴过来也能用。

### 动手连库，先自测一把

我在 demo5 的基础上新建了一个 demo6，把该删的代码全删掉，创建模型的语句先注释掉——不着急，先把数据库的事情说明白。

用的是 MySQL 数据库，URL 通过 format 把参数传进去拼出来：

```python
from langchain.sql_database import SQLDatabase

# 初始化 MySQL 数据库的连接
mysql_url = "mysql+pymysql://{username}:{password}@{host}:{port}/{database}?charset=utf8".format(
    username="root",        # 数据库用户名
    password="******",      # 数据库密码
    host="localhost",       # 数据库在哪台机器上
    port="3306",            # 端口号，不写默认就是 3306
    database="test_db8",    # 要访问哪个数据库
)

db = SQLDatabase.from_url(mysql_url)  # 根据 URL 初始化，得到一个数据库连接
```

导包来自 LangChain 的 sql_database，里面有一个 `from_url`，根据你的 URL 初始化得到一个数据库连接。有了这个连接，它就可以帮我们执行 SQL 语句，LangChain 就能访问你的数据库了。

连上之后先别急着接大模型，测一下这个连接到底好不好使。怎么做？输出一点跟数据库有关的东西，比如看看库里一共有多少张表，或者对数据库进行一次查询：

```python
# 测试连接是否成功：打印库里可以用的表名
print(db.get_usable_table_names())

# 执行一条测试 SQL，把员工表的数据拿出来
result = db.run("SELECT * FROM t_emp LIMIT 10;")
print(result)
```

`get_usable_table_names` 拿到的是那些可以用的表名；`db.run` 会执行一条 SQL 语句，`LIMIT 10` 表示最多返回十条数据，末尾加分号表示这条 SQL 语句结束——如果你之前了解过 SQL，这种语句你应该信手拈来。

我本地数据库跑的是官方的 MySQL Workbench 客户端。test_db8 这个库是我以前课程用到的，一共八张表：t_emp 存的是员工数据，t_dept 存的是部门数据，t_person 存的是人的数据，t_role 存的是角色数据，t_user 存的是用户数据，t_idcard 存的是身份证数据，还有一张用户和角色之间关联关系的中间表。

> **提示**：这些表你可以自己随便找、随便造。AI 大模型对你有两张表、三张表还是十张表无所谓，表里有多少条数据也无所谓，表名也无所谓——LangChain 会自动去找你的表名，其实它也是调用 db 去找的。

跑一下：八张表名全部打印出来了；员工表里的五条数据也全查出来了，第一条记录的 id 是 1，名字叫李四。到这里连接测试成功——注意，这一步还没有涉及到 AI 大模型，我们只是先确认关系数据库这边 OK。

### 用 create_sql_query_chain 试试水

上一步的测试代码删掉，把之前创建模型的语句打开，接下来就交给 AI 大模型帮我们提问题了。先说第一种比较简单的方式：直接使用大模型和数据库。顺便说一句，我第一次跑的时候报错说没有 OpenAI 的 API Key，把 key 配置好再跑就行。

我们通过调用一个函数得到一个链，这个函数叫 create_sql_query_chain，看名字就知道了——创建一个数据库查询的链。我给它取名叫 test_chain，说实话这条链只是为了带大家熟悉一下：

```python
from langchain.chains import create_sql_query_chain

test_chain = create_sql_query_chain(model, db)  # 创建数据库查询链

resp = test_chain.invoke({"question": "请问员工表中有多少条数据"})
print(resp)
```

参数第一个传大语言模型 model，第二个传 db，也就是数据库连接。两个都有了的瞬间，链就成了——链是什么？链就是把组件进行组合。

> **易错点**：invoke 传入的 input 对象是一个字典，一定要记住这一点。键取名叫 question，值就是你的问题。你不能直接传一个列表或者字符串进去，会报错的。

我问的是：请问员工表中有多少条数据。如果你是一个了解数据库的正常人，马上就知道这个问题要执行一条 SQL——查 t_emp 这张表——然后告诉你员工表里有五条数据。现在我假设自己不会写 SQL，让大模型来回答，看看它给什么。

用 GPT-4 跑出来的结果是 `SQLQuery: SELECT COUNT(*) ... FROM t_emp` 这样的输出：这条 SQL 跟我自己手写的那条本质上一模一样，该用大写的用大写，该用别名的用别名，写得比较标准。但注意——它只是生成了 SQL，并没有执行。

换成 GPT-3.5-turbo，其他代码一个字都不改，输出就少了一个前缀：直接给你 SQL 语句，而且里面没有反引号。这条 SQL 同样是正确的、也能运行。

| 模型 | 生成的 SQL 长什么样 | 会不会帮你执行 |
| :--- | :--- | :--- |
| GPT-4 | 带 `SQLQuery:` 前缀（还带反引号），SQL 本身写得比较标准 | 不会 |
| GPT-3.5-turbo | 直接给 SQL，没有前缀、没有反引号 | 也不会 |

所以这种"大模型和数据库直接整合"的方式只能生成 SQL 语句——根据你的问题生成语句，仅此而已。你想想，这是我想要的吗？难道我还要自己复制这条 SQL 语句，再到数据库里去执行吗？那太麻烦了。这种方式只是测一下，让大家知道这个意思。

### 模板、工具与完整大链

接下来要把整个体系全部完成：用 LangChain 的链，帮我们生成 SQL 语句、执行 SQL 语句，并且回答我们想要的结果。

#### 先备好回答模板

要定义一个提示模板。这个模板以后大家用的时候基本都长这样：

```python
from langchain.prompts import PromptTemplate

answer_prompt = PromptTemplate.from_template(
    "给定以下用户的问题、对应的SQL语句和SQL执行的结果，回答用户问题。\n\n"
    "Question: {question}\n"
    "SQL Query: {query}\n"
    "SQL Result: {result}\n"
    "Answer: "
)
```

很多同学看到这个模板可能觉得有问题："SQL 语句你让用户怎么给定？"确实给定不了，也不用来给，不着急——因为 SQL 本来就是大模型帮我们生成的，我们只是通过一个数据库工具去执行它，最后才得到答案。

回想一下之前那张图：最后那个大语言模型要拿到三样东西——用户的问题、SQL 语句、SQL 执行的结果，三者结合它才给答案。所以这个模板是针对最后一个大模型的提示。那第一个生成 SQL 的大模型，它的提示为什么不用我们给定？你想想，它就是生成 SQL 语句，create_sql_query_chain 内部已经帮你搞定了。模板里的文字当然可以改，参数名对上就行。

#### 再备一个执行 SQL 的工具

前面的方式生成 SQL 还要你自己复制粘贴去执行，没必要。我们创建一个执行 SQL 语句的工具，取名叫 execute_sql，用的是 QuerySQLDataBaseTool，初始化时把 db 传进去：

```python
from langchain.tools import QuerySQLDataBaseTool

execute_sql = QuerySQLDataBaseTool(db=db)  # 创建一个执行 SQL 语句的工具
```

有了它，先生成 SQL、再执行 SQL，全程自动。

#### 把生成、执行、回答串成一条链

现在把组件组装成一个大的链：

```python
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from operator import itemgetter

chain = (
    RunnablePassthrough.assign(query=test_chain)       # 第一步：生成 SQL，命名为 query
    .assign(result=itemgetter("query") | execute_sql)  # 第二步：执行 SQL，结果命名为 result
    | answer_prompt                                    # 第三步：问题、SQL、结果一起进模板
    | model                                            # 交给大语言模型
    | StrOutputParser()                                # 输出纯文本答案
)

resp = chain.invoke({"question": "请问员工表里面有多少条数据"})
print(resp)
```

逐段拆开看。`RunnablePassthrough` 你可以理解为一个可以调用的对象，`.assign(query=test_chain)` 是在它身上挂一个断言：先生成一条 SQL 语句，并且把它命名为 query。query 这个名字不能乱写——模板里就是用 query 作为键名，把生成的 SQL 传进去的。test_chain 我们前面已经测过，作用就是生成 SQL 语句。

接着 `.assign(result=itemgetter("query") | execute_sql)` 再挂一层：itemgetter 是 Python 内置的一个工具函数，作用是从字典（或者列表）里取出某一个元素的值。这里取出 query 也就是生成的 SQL，通过管道交给执行 SQL 的工具去运行，执行之后的结果用 result 这个变量名存起来。result 同样要传到模型里面去。

到这里，前半部分就完成了"生成 SQL 语句并且执行 SQL 语句"这一整个整体；后面再用竖线接上提示模板、大语言模型和输出解析器，链就通了。

#### 运行与排错

第一次运行没跑通，报了两处错，都是典型问题：

> **易错点**：创建工具那行代码写法有讲究，初始化 QuerySQLDataBaseTool 的时候要指定参数的名字，写成 `QuerySQLDataBaseTool(db=db)`。我一开始直接把 db 传进去，运行就报错说参数不对。

> **易错点**：另一处报错信息指到 invoke 那一行，其实错不在那里，而在定义链的那一行——最后一步的 StrOutputParser 后面没有加括号。加括号才表示创建这个类的实例。

把这两处修好再跑，问题还是那个问题：请问员工表里面有多少条数据？答案我们自己是知道的，五条。看它给的答案——"员工表中有五条数据"。注意，这次给我的是一个完整的回答，而不是直接甩过来一条 SQL 语句。

### GPT-4 的 SQLQuery 前缀坑

当前这个案例有个特点：我们用的是 GPT-3.5-turbo。如果我们换成 GPT-4，它生成的 SQL 会带一个 `SQLQuery:` 前缀，而链是直接拿着返回的 SQL 去执行的，所以会执行失败。报错提示说 SQL 查询语句存在语法错误——有意思的是，报错信息自己就知道"员工表"对应的是 t_emp 这张表，非常智能，并且指出实际语句前面多了一个 `SQLQuery:` 这样的前缀。

那 GPT-4 就不能用了吗？是可以用的，只是在现在这种链式写法下，只能使用 GPT-3.5-turbo。

现在我们走的是第一种方式：用链把工具、模型、提示模板整合起来。这个整合确实很复杂，代码写起来麻烦，大家看代码都看得郁闷。事实上，我们可以用代理来做这个事情，用代理就非常智能了——不管你用 GPT-3.5 还是 GPT-4，都没问题。下一讲我们就用代理把整个流程重新实现一遍。

## Agent 整合数据库：工具代理与向量库持久化实战
> 对应块：BLK14 | 覆盖分集：P40-P41 | 块标题（分集名）：《【补习篇】Agent整合数据库》

### 上节课的链式写法，为什么这次要换

上节课我们已经完成了这样一条完整链路：用户提一个问题，大语言模型根据问题生成一条 SQL 语句，交给工具去执行，最后把 SQL 语句、用户的问题、SQL 执行之后的结果一起交给模型，得到一个完整的答案。

当时我们用的是 LangChain 本身来做各种组合。大家一看那个组合就知道有多复杂：里面有 chain，还有内嵌的子 chain——指令后面挂提示模板，提示模板后面挂模型，模型后面再挂输出解析器。输出解析器直接把它解释成一个字符串，这是可以的，因为返回的本来就是一个字典，说白了就是一个字符串，我们把字符串里面的数据拿出来就行。

这一节我们换一种写法，需求一模一样，思路不同：改用代理来完成这件事。我把这个案例记作 6-2，而且这次模型不再用 3.5 了，改用 GPT-4 Turbo，其余的组合全部删掉，只留代理。这个代理，我们把它称为「工具代理」。

| 对比项 | 链式写法 | 代理写法 |
| :--- | :--- | :--- |
| 组合方式 | chain 套内嵌子 chain，模板、模型、解析器层层拼 | 一个工具代理全包 |
| 提示模板 | 要传 SQL、执行结果等一大堆参数 | 只给一个定位，其余全在工具内部 |
| 模型 | GPT-3.5 | GPT-4 Turbo |

### 创建数据库工具

代理要干活，先得有工具。创建工具跟之前一样，通过一个工具包的生成器来做：

```python
toolkit = SQLDatabaseToolkit(db=db, llm=model)
tools = toolkit.get_tools()
```

打包的时候传两个参数：一个是 `db`，就是我们的数据库；一个是 `llm`，把模型传进去。拿到工具包之后，调用它的 `get_tools()`，这是个空参数构造方法，一调就把工具拿到手了。

有了工具，接下来才谈得上用代理去完成整个数据库的整合。这里最关键的一点是：SQL 语句的生成、SQL 语句的执行、执行结果的拿取，这一系列操作全都在工具内部实现了，全都在 Agent 里面实现了，外面不用再操心。

### 给代理立规矩：系统提示词逐条拆

接下来是提示模板。这个提示模板跟之前的一定不一样——为什么？因为之前那个模板要传很多参数，要定义这么多「船舱」：SQL 语句、SQL 执行结果等等。现在这些都在工具内部实现了，我们只需要给模型一个通常的定位，不用再传 SQL 进来，也不用传执行结果进来。

下面这份系统提示的文本模板，对大家是有借鉴和参考意义的——我们写的这个案例，不就是针对数据库来问一些问题吗？它正好就是按这个场景写的：

```text
你是一个被设计用来与 SQL 数据库交互的代理。
给定一个输入的问题，创建一个语法正确的 SQL 语句并执行，
然后查看查询结果，并返回答案。

除非用户指定了他们想要获取的示例的具体数量，
否则始终将 SQL 查询限制最多为 10 个结果。
你可以按照相关列对结果进行排序，以返回数据库中最匹配的数据。

你可以使用与数据库交互的工具。
在执行查询之前，你必须仔细检查查询语句。
如果在执行查询时出现错误，请重新编写查询语句再试。

不要对数据库做任何 DML 语句（新增、修改、删除）。

首先，你应该查看数据库中的表，看看可以查什么，不要跳过这一步。
然后查询最相关表的模式（schema）。
```

逐条拆开看，每一条都有它的用意。

第一条是定位：一个被设计用来与 SQL 数据库交互的代理，给定输入问题，创建语法正确的 SQL 并执行，查看结果，返回答案。这就是给代理划定了它的职责范围。

> **提示**：始终把查询限制为最多 10 个结果。这句话是防止生成的 SQL 一次性从数据库里查询大量数据，造成内存溢出。理解过数据库的人应该知道：每次执行 SQL，不要从数据库里返回太多数据——几十条没问题，上百条也没问题，上千条以上就有问题了。这里干脆最多让它返回 10 条。

接下来是容错：执行查询之前必须仔细检查；执行时出了错，就重新编写查询语句再试。代理自己会纠错，这是它比一次性生成可靠的地方。

> **易错点**：不要对数据库做任何 DML 语句。这一条是明令禁止 AI 对数据库做新增、删除、修改。为什么卡得这么死？你想想，用户随口问一句「张三这个用户可能不需要了吧」，AI 要是开放了新增和删除权限，搞不好理解完这句话就把张三那条数据给删了——但实际上用户的意思并不是真的要删库里的数据。所以我们做了范围限制，不允许大模型替我们执行 DML 操作。

最后两条是工作流程：先查看数据库中的表，看看可以查什么，不要跳过这一步；然后查询最相关表的模式。意思是让 AI 根据表名自己去判断这张表里是什么。比如我们的库里有一张 `DEPT` 表，你自己判断这是不是部门表；`EMP` 这张表，你自己判断是不是员工表；还有 `person`，你自己判断里面是人、是用户还是什么。AI 通过「翻译」是完全可以判断出来的。

### 创建代理执行器：一次 invoke 的事

有了工具、有了系统提示，就可以创建代理了。这里我们借助一个专门初始化 Agent 的库——langgraph。它里面有个函数，打开一看第一个就是：创建一个工具调用的代理。因为我们这里用到的正是工具，所以就用这个函数。

这个函数要传的东西不少，但核心就三样：

```python
from langgraph.prebuilt import create_react_agent

agent_executor = create_react_agent(model, tools, state_modifier=system_message)
```

第一个参数是模型；第二个参数才是工具，把刚才 `get_tools()` 拿到的 `tools` 传进去；第三个是 `system_message`——它的类型是一个系统 message，说白了就是我们给这个 AI 的定位、那个提示模板。把系统消息传进去就可以了，后面的参数都可以不传，核心都在这三样里头。

这一步创建出来的，准确说是一个「代理执行器」（executor），它本身就是可以直接调用的。执行就一行：

```python
resp = agent_executor.invoke(
    {"messages": [HumanMessage(content="请问员工表中有多少条数据")]}
)
```

`invoke` 里面接的是一个字典，人家明确告诉你接的是 dict。字典的键一定是 `messages`，值是一个中括号列表，里面放一个 `HumanMessage`，把问题写进去。这里我们先拿上节课那个非常简单的问题来测：员工表里有多少条数据。等会儿可以换不同的问题。

> **结论**：代理执行的返回值因为传入的键叫 `messages`，收到的也是 `messages`——用 `resp["messages"]` 取出来。

### 读懂消息数组：成对的 AIMessage 与 ToolMessage

打印之前，先想清楚一件事：这个 `messages` 是个数组，里面有很多对象。用过代理的话你就知道，代理执行之后的结果里包含很多种类型：第一个对象是 `HumanMessage`，第二个是 `AIMessage`，第三个是 `ToolMessage`……总而言之，往后要么就是 `AIMessage`，要么就是 `ToolMessage`。

我们打印三样东西：整个数组、数组的长度、数组的最后一条：

```python
print(resp["messages"])
print(len(resp["messages"]))
print(resp["messages"][len(resp["messages"]) - 1])
```

一跑，数组非常长，一共有十个对象。为什么这么多？你要注意：我们让代理可以根据需要多次循环查询数据库来回答问题，它每一次查询至少产生两个对象——一个 `AIMessage`，一个 `ToolMessage`。因为 `AIMessage` 一定是 AI 给出的一条执行指令，比如「去执行这条 SQL」；执行 SQL 之后又得到一个结果，这个结果是工具带回来的信息，所以叫 `ToolMessage`。

```text
 [HumanMessage]   用户提问
       |
       v
 +----------------- 代理循环（可多轮） -----------------+
 |  [AIMessage]     AI 给出指令：生成并执行某条 SQL        |
 |       |                                                |
 |       v                                                |
 |  [ToolMessage]   工具返回：SQL 执行结果                  |
 |       |                                                |
 |       +----- 还答不上来？把结果喂回去，再来一轮 ------+  |
 +--------------------------------------------------------+
       |
       v
 [AIMessage]   最后一个元素 = 最终答案
```

读图要点：消息数组按「指令—结果」成对增长，一轮问答可以包含若干对；我们要的答案永远在最后一个元素里。取最后一个也很简单，`len(result) - 1` 就是它的下标，说白了就是最后一个。把最后一个拿出来，内容里明明白白：员工表中一共有五条数据。后续要拿这个字符串，取它的 `content` 属性就可以了。

| 消息类型 | 由谁产生 | 装的是什么 |
| :--- | :--- | :--- |
| HumanMessage | 用户 | 提出的问题 |
| AIMessage | 模型 | 下一步指令（比如去执行某条 SQL） |
| ToolMessage | 工具 | SQL 执行结果等信息 |

你看这代码，比上节课的链式写法简洁多了，直接通过代理帮我们把整件事做完了。

### 问题逐级加码：从数条数到连表查询

第一个问题太简单了，我们把它弄难一点：哪种性别的员工人数最多？

换成一个人来做，要怎么下手？首先得去数据库里看看员工表有没有性别字段——有，字段取值就是 `woman`、`man` 这种正确的合法单词，一个是女人、一个是男人。用人的眼睛去观察数据，一看就知道男人最多，四名。但现在不是我们看，是叫 AI 去做这个事情，它内部要做很多操作：先要知道表里有哪些性别，然后每个性别的人数是多少，再降序排序，找到人数最多的那种性别。

运行之后耐心等一等，出来的同样是十个对象，答案是：数据库中人数最多的性别是男性（man），共四名员工——跟我们人观察到的完全一样，而且它还自动把 man 翻译成了「男性」。取答案还是拿 `content` 属性就行。

再换一个更复杂的，这就涉及到连表查询了：哪个部门下面的员工最多？

还是看员工表：其中有一个字段是跟部门关联的，`dept_id`。数据里，员工张七并没有分配部门；李四、张三、王五、孙六是分配了部门的，其中 id 为 3 的这个部门人数最多。但 id 为 3 的部门是什么部门？我不知道。我现在人都不知道，我要想知道，就必须去部门表里面看一眼——一看，是销售部。你看，这个问题光靠一张表答不出来，必须连表查询。

AI 能不能搞定？可以。运行结果出来，答案非常清晰：部门中员工人数最多的部门、它的名字、共有几名员工，全都给你弄出来了。你还可以继续问「销售部下面有多少员工」「张三有几种角色」这样的问题，它都能帮你识别出来。

到这里你应该能体会到 AI 的强大之处了：以后我们不用写 SQL 语句，直接拿到一个关系型数据库，通过问问题就能查到想要的东西。SQL 语句搞不好就是 AI 帮我们生成的，而且反而是最好的、最优的那种 SQL。那照这么说，专门对数据库进行操作的程序员都不需要了？好像确实也如此——大家可以试一下，最基本的那些查询它都能帮你搞定；非常复杂的、涉及复杂业务的，可能暂时没办法，但未来应该也是可以的，因为它才刚刚起步。

### 换个场景：拿 YouTube 字幕建搜索引擎

接下来进入案例七：使用 LangChain 来检索 YouTube 的视频字幕。这是什么意思？YouTube 里面有很多视频，每一个视频的字幕你都可以理解为就是文本，就是人说的话。假设我能拿到 YouTube 里很多很多视频的字幕，那我就有了大量的文本。基于这些用户录制的视频字幕，可以构建一个简单的搜索引擎，再把用户的原始问题传递给这个搜索引擎系统，得到我们想要的答案——针对视频字幕内容做出的智能回答。

要做的事情就两件：第一，获取 YouTube 里某些视频的字幕；第二，把这些字幕构建成向量空间，或者说向量数据库。

爬取 YouTube 字幕需要用一个第三方库，名字叫 `youtube_transcript_api`（YouTube Transcript API）。3 月 24 号有一位博主专门写过博客介绍它，标题叫「解锁视频字幕的无限可能」。一句话说清楚：这个库就是帮我们获取 YouTube 视频字幕的——不是 B 站，也不是优酷。它是 GitHub 上的一个 Python 开源项目，专注于获取 YouTube 视频的自动字幕，并提供方便的 API 接口，开发者和普通用户都可以轻松拿到视频的文字内容。

那为什么它能拿到？最核心的是它利用了 YouTube 的公开接口。YouTube 本身提供了很多 API 接口，允许你访问某些视频的字幕，所以才有这个第三方库能拿到数据。那不用这个库、直接调 YouTube 的公开接口行不行？也可以——你拿到字幕之后，手动把它们变成一个个 Document 就行。还记得 Document 吗？

> **定义**：Document 是 LangChain 中构建向量空间、向量数据库的最基本单位。

有同学可能会问：那国内的 B 站、优酷如果也提供了公开接口，允许获取视频字幕，是不是也可以这样做？是的。但据我所知，至少优酷没有提供这样的公开接口，所以现在要做这个案例，你只能用 YouTube 的。

还要说清楚一点：YouTube 的字幕不是所有视频都能拿。要看它的公开接口允许哪些视频，只有一部分视频可以，尤其是最新的一些视频肯定不行；稍微老一点、比如三个月之前的，倒是有可能。因为这个接口每更新一次，你能获取到的视频字幕可能就更多一些；它要是一直不更新，你就只能拿到之前公开的那些。

其实这个案例的重点，还不是拿字幕本身，而是两个知识点：**怎么保存向量数据库，怎么加载向量数据库**。比如不用 YouTube 的数据，我们公司内部就有一大堆文档数据，要构建向量数据库——总不能每次都放在内存里吧？放在内存里，程序一停，内存就没了，下次还得重新读文档。正确的做法是：第一次从文档里读取文本，每个文本转成 Document，存进向量数据库，然后把这个向量数据库持久化到磁盘；第二次需要用的时候，不用再读那些 Word、PDF 文档，直接从磁盘把向量数据库加载进来。

```text
第一次（建库 + 持久化）：
  字幕/文档 --转成--> Document --切割--> 片段 --嵌入--> 向量数据库 --保存--> 磁盘目录

第二次（直接用库）：
  磁盘目录 --加载--> 向量数据库
  （不再爬字幕、不再读 Word/PDF、不再重新做嵌入）
```

读图要点：磁盘目录就是两次运行之间的「存档点」，建库的代价只付一次。

### 爬字幕、转 Document

回到代码里来实现，工程名叫 demo7。我们是通过大量案例让大家掌握知识点，这些案例未来你一定用得着：要从文档中获取数据、要从网页里获取数据、要从数据库中获取数据，都可以从这些案例里找到类似的代码。模型我留着，用的是最贵的 GPT-4 Turbo——不过这一段构建持久化的代码其实用不到模型，先把它注释掉。

首先指定一个持久化目录。因为我们是通过 Chroma 这个向量数据库来操作的，目录名就取成 `chroma_data_dir`：

```python
chroma_data_dir = "./chroma_data_dir"  # 存放向量数据库的持久化目录
```

这是个相对路径，运行的时候会在当前工程目录下自动创建这个目录，向量数据库就存在里面。

然后准备原始数据。我找了一些跟 AI、大模型、工具整合、Agent 整合有关的视频，在 YouTube 里都能打开，一共初始化了十几个视频的 URL 地址。获取字幕之后，全部放进一个 `docs` 列表——一个 Document 的数组：

```python
from langchain_community.document_loaders import YoutubeLoader

docs = []
for url in urls:
    docs.extend(YoutubeLoader.from_youtube_url(url, add_video_info=True).load())
print(len(docs))
```

这里要先装两个包——忘记给大家说了，就这两个，你必须要装一下，不装的话拿不到这个工具。我已经装过了，大家直接按照文档中的命令一步步装就行。

处理逻辑是：遍历一个个 URL，用 LangChain 里的 `YoutubeLoader` 工具，它的 `from_youtube_url` 会根据你指定的 URL 把字幕拿出来。这里还传了一个参数 `add_video_info=True`，意思是把视频的元数据也要拿出来——视频的元数据就是标题、播放时长、发布时间这些。最后调用它的 `load()`，就变成一个个 Document 了。一个 YouTube 视频对应一个 Document，全部 `extend` 进数组，打印 `len(docs)` 就知道一共多少个。

### 给元数据补一个发布年份

拿到 Document 之后，我可能还要对数据做一些处理。刚才说了，元数据里有视频标题、发布时间，其中发布时间精确到年月日时分秒。我想额外添加一项：把发布的年份单独弄出来。每一个 Document 都要填：

```python
from datetime import datetime

for doc in docs:
    doc.metadata["publish_year"] = int(
        datetime.strptime(doc.metadata["publish_date"], "%Y-%m-%d %H:%M:%S").strftime("%Y")
    )
```

这段代码分三步走。第一步，`strptime` 按照原来的格式把字符串转成日期对象——原来的 `publish_date` 里年月日、时分秒都有，格式对应 `%Y`、`%m`、`%d` 和 `%H`、`%M`、`%S`。第二步，`strftime("%Y")` 再把它格式化成只有年份的字符串——实际上我们只需要「年」。第三步，年份拿到的其实是个字符串，所以再套一层 `int()` 做类型转换。

写完打印 `docs[0].metadata` 验证一下，看看元数据里是不是多了一个发布年份。

常有同学问：内容数据在哪？这个之前讲过——`docs[0]` 拿到第一个 Document，每个 Document 分为两部分：一部分叫元数据 `metadata`，另一部分叫 `page_content`。`page_content` 就是字幕的内容，字幕内容我们不用处理，它可能很长，打印前 500 个字符出来看看是什么就行了。

### 切分文本，构建并持久化向量数据库

得到一个个 Document 之后，接下来就根据它们构建向量数据库。但先要考虑一个问题：视频比较长的话，字幕里包含的文本也比较多，所以我们还得做文本切割。用之前用过的那个切割类就行，直接把之前的代码复制粘贴过来，一模一样，只是数字可以调——我们用 2000 个字符作为一个片段，上下可以重复 30 个字符：

```python
text_splitter = RecursiveCharacterTextSplitter(chunk_size=2000, chunk_overlap=30)
split_docs = text_splitter.split_documents(docs)
```

注意这里调用的是 `split_documents`，因为如果你手上已经有文档了，切割的就应该是 Document，切完得到很多小片段，我给它取名叫 `split_docs`。

然后基于这些片段创建向量数据库：

```python
embedding = OpenAIEmbeddings(model="text-embedding-3-small")

vectorstore = Chroma.from_documents(
    split_docs,
    embedding,
    persist_directory=chroma_data_dir,
)
```

嵌入模型还是 `OpenAIEmbeddings`。之前我们直接用空参数构造方法，其实按道理说应该指定嵌入模型的名字。可选的嵌入模型有好几个，之前课程里讲过的，这里我记得有一个叫 `text-embedding-3-small`——`small` 是小的；你要是不加 `small`，好像就是一个大的嵌入模型。我们用小的算了，速度快一些。

`Chroma.from_documents` 传三个参数：第一个是切完之后的片段 `split_docs`；第二个是嵌入 `embedding`；第三个——如果你还要把向量数据库持久化到磁盘，就必须传——是持久化之后的目录 `persist_directory`，用前面定义好的那个变量就行。

> **结论**：到这一步，不单是创建了向量数据库，而且完成了向量数据库的持久化——说白了就是把它保存到磁盘里面去了。

正确的键名去哪儿找？答案就藏在我们自己的打印输出里。代码里打印过第一个 document，而这份 document 是包含元数据的，往下翻就能看到元数据部分——果然，真正的发布日期，它的键名叫 `publish_date`。把这个名字复制过来改对就行。

把字段名改对之后再运行。这次等了大概三四十秒，程序又抛出一个新错误：`strptime` 这个函数要给两个参数，但实际上只给了一个。这是我上节课临场翻车的地方，正好把这对函数讲清楚。

| 函数 | 方向 | 参数 |
| :--- | :--- | :--- |
| `strptime` | 字符串 → 日期时间对象 | 两个：待解析的字符串、格式 |
| `strftime` | 日期时间对象 → 指定格式的字符串 | 一个：格式 |

`strptime` 干的事，是把一个字符串按照我们给的格式变成一个日期时间对象，所以它必须传两个参数。但我们这里其实根本不是要得到一个日期对象——我们只是要把日期里面的年份拿出来，得到一个年份的字符串。所以是函数调错了，应该调 `strftime`：格式化，把我们的时间按照指定格式变成一个字符串，只要传一个参数就够了。

```python
# strptime：字符串 -> 日期时间对象，必须传两个参数
datetime.strptime("2024-05-01", "%Y-%m-%d")

# strftime：日期时间对象 -> 指定格式的字符串，只要传一个格式参数
publish_year = publish_date.strftime("%Y")   # 只拿年份，得到 "2024" 这样的字符串
```

改完这一处再运行，这次应该就没有什么问题了。

vector_store = Chroma(

### 先来一次不接大模型的相似度搜索

加载完之后，这个向量数据库本身就可以支持搜索。前面讲过，直接对向量数据库进行搜索，其实就是一个相似度搜索——但它这种搜索是不智能的。不智能归不智能，可以先试一下。

怎么搜？得到一个 result，调 vector_store 的搜索函数就行。`similarity_search_with_score` 和 `similarity_search` 这两个函数你调谁都行，默认都是根据分数来进行搜索，只是传的参数不一样：用带 with_score 的那个，结果中会带分数。

查询语句这次要写一句英语——为什么呢？因为字幕里面全是一些英语单词，没有中文。这句话的意思就是"怎么去构建一个 RAG 的 Agent"。

```python
result = vector_store.similarity_search_with_score("how to build a RAG agent")

print(result[0][0].metadata["publish_year"])   # 只看第一个：最相似的排在最前面
```

搜回来肯定有很多个结果，我们其实不用看那么多，只要拿第一个就可以了——前面讲过，相似度搜索会把最相似的放在最前面，第一个一定是最相似的。

这里注意：搜回来的是一个 document。为什么？因为当时往向量数据库里存放的数据，就是一个个的 document。而 document 分为两部分：一部分是元数据 metadata，另一部分是内容数据，内容数据你可以理解为就是 page_content。想看元数据就点 `.metadata`（这个属性在 IDE 里是没有提示的），metadata 里还可以继续拿具体的字段，比如发布年份 `publish_year`，或者发布日期 `publish_date`，都是可以的。

```text
Document
├── page_content    正文内容：视频字幕全文
└── metadata        元数据
    ├── source / url / title / author
    ├── description / length / view_count
    ├── publish_date     发布时间
    └── publish_year     发布年份（我们自己加上去的）
```

读图说明：一个 document 就是"正文 + 元数据"两块，后面要做的按元数据检索，玩的全部是 metadata 这一半。

第一次跑就翻了个车：打印直接报错，说 tuple 对象没有一个叫 metadata 的属性——它是一个元组！因为我们用的是带分数的搜索，拿到的是分数，元组里面的第一个元素才是 document。所以想真正打印里面的内容，得这样取：

```python
doc, score = result[0]    # 带分数搜索返回的是 (Document, score) 元组
print(doc.metadata["publish_year"])
```

如果你不想看到分数，后面不要加 with_score 就行了，把 with_score 去掉，直接用 `similarity_search`。

跑起来的结果：2024——这就是它的发布年份。我们搜到了离搜索语句最相似、最接近的那一篇 document。当然不只可以打印发布时间，它的内容、很多很多信息都可以打——这个 document 实际上整个都拿出来了：metadata 里面有作者、描述、长度、发布时间、发布年份，还有 source、URL、title；往下翻还有 page_content，就是整篇 document 的内容。

这种搜索我们理解为测试用的搜索，先把它放到一边，加个注释：测试向量数据库相似搜索。因为这种搜索没有和大模型进行整合。

### 接上大模型：系统提示与链的骨架

接下来我们要把它和大模型进行整合。整合的话，首先是不是得有一个提示模板？

这个提示模板首先定义的是给系统的部分——告诉我们这个 AI 是个什么东西。那段话比较长，意思是：你是一个将用户问题转化为数据库查询的专家——注意，是向量数据库的查询专家，因为我们接下来就是要去向量数据库里做检索；你可以访问一个"构建大语言模型驱动的应用程序的软件库"的教程视频数据库——为什么叫教程视频数据库？因为我们拿到的这些视频字幕数据，都是跟 RAG 相关的一个个构建教程，所以把这个库理解为教程数据库。

模板里还有一句很关键的告诫：如果你有不熟悉的缩略语或者单词，不要试图改变它，直接把它作为你要检索的向量，去数据库里找它的相似度。为什么这么定？因为在专业术语里，比如 RAG，在计算机编程这个语境里代表的是检索增强——增强的 AI、增强的检索的意思；但同一个词放到另外一个环境中、不在计算机这个语境中，它又是另外一个意思了。你一"热心改写"，检索就偏了。

> **提示**：缩略语的价值就在于它的原样。让大模型抽检索条件时，遇到拿不准的缩写要原封不动保留，直接拿去算相似度，而不是替用户"翻译"一遍。

有了提示模板，接下来就可以用模板加上之前的模型，得到一个链（chain）。链的最开始，传入的是提示模板中的参数：模板里的参数名是固定的，叫 `question`，所以把这个 question 拿出来放到这里；参数值现在不可能传死，用什么？用一个叫 `RunnablePassthrough` 的东西，表示你后面再去传，先构造这个对象占住位置。然后才是提示模板，再接下来就是我们的模型。

```python
chain = {"question": RunnablePassthrough()} | prompt | model
```

模型呢，直接写到这里——但正是这个位置要做一点改造，先往下看。

### 相似度搜索的天花板：按元数据检索做不到

前面这种搜索，没办法做到精细化或者细腻度的检索。我们想对数据库里面的数据进行检索，它只能帮我们检索内容。但事实上我们不但要检索内容，还可能要基于某一个元数据的字段去检索。

为什么可以这么玩？前面讲过一个 document 里包含 page_content——就是文本内容；还包含 metadata，metadata 里面又分很多很多的字段：发布时间、发布年份、作者、长度等等，刚才打印的时候都看到了。那有没有可能，我做检索的时候不检索文本内容，就是为了检索某一个元数据？比如"2024 年发布的所有教程"，或者"长度不小于 1024 的教程"。你想想，我说的这句话里面的检索条件，是不是专门基于元数据进行的？是的。

再比如我们要搜索"09 年以前出生的人，并且头发是黄色的"——这句话的检索包含了两个非常重要的信息：一个是这个人的出生时间，是 2009 年之前出生的；第二个是头发颜色是黄色。如果数据库里存的人的信息中，就存了这个人的元数据——包括头发颜色、出生年月——那我是不是就可以基于这两个元数据来进行搜索？这个时候你给我的搜索条件，我要验证一下是不是包含这两个条件数据，同时还要进行一个序列化。

要做到这件事，首先要使用 Pydantic 来构建一个模型。

Pydantic 这个库大家可能不熟悉。如果你做过 Python 的 web 开发，你其实应该听过它：它是一个专门做数据管理的库，包括数据的验证、数据的定义、模型的定义等等。比如做 web 开发要接收数据、响应数据：接收什么样的数据，可以用 Pydantic 构建一个模型，数据包含哪些字段、每个字段有什么规格，都在模型里定义好，模型会帮我们自动完成数据的校验、数据类型的转换以及数据的接收；想响应一个指定规格的数据，也可以基于它构建响应的数据模型，功能非常强大。总而言之，它就是专门在 Python 里做数据管理、数据验证、数据定义和序列化操作的一个非常综合的库。

搜索的时候我们也需要用它：搜索的时候要接收搜索条件，这其实跟接收请求数据差不多——搜索条件不一定只针对文本，比如刚才那种基于元数据的条件。

### 用 Pydantic 定义检索数据模型

先把话说清楚：这里要定义的"模型"，不是大语言模型、AI 的那个模型，而是数据模型——说白了就是我们 Java 程序员经常讲的 POJO 类，或者 Python 程序员里、尤其是做 web 开发的经常讲的数据模型，一个道理、一个意思。

我们来定义一个模型类，叫什么都可以，这里就叫 `Search`。它不能随随便便定义一个类，要继承 `BaseModel`。注意导包是 Pydantic 里面的——编辑器会给你两个选择，一个是 `pydantic`，一个是 `pydantic.v1`，其实这是版本的区别，我们统一使用 v1。

接下来定义数据模型中的字段。检索根据什么？一个是根据内容的相似性，还有一个是根据发布年份，所以定义两个属性。

第一个属性是内容，叫 `query`——其实叫什么无所谓，类型是 `str`，说白了就是你要检索的那条语句。给它赋一个 `Field`，代表它是一个检索字段（Field 也是 Pydantic 里的，v1 的导包跟着前面保持一致）。括号里首先要写默认值 default，一开始给一个空值；然后写 description 描述，随你写——query 这个字段的目的就是根据内容做相似度搜索，所以描述就写"搜索我们视频中的字幕"。

第二个字段是发布年份 `publish_year`。这个字段名要不要跟 document 元数据里的字段名保持一致？不一定，你爱叫什么叫什么；我们保持一致也是可以的，只是这样代码看起来好看一些。年份有可能没传，所以类型用 `Optional`——选项、可选的意思，你可以针对年份来搜索，也可以不经过它。注意这个 Optional 是 typing 里面的，表示可选类型，里面写 `int` 表示实际类型就是 int，但这个字段可以传也可以不传。描述改成"视频发布的年份"。

```python
from typing import Optional
from pydantic.v1 import BaseModel, Field

class Search(BaseModel):
    # 内容相似度检索：你要检索的那条语句
    query: str = Field(default=None, description="搜索我们视频中的字幕")
    # 可选的元数据过滤：视频发布的年份
    publish_year: Optional[int] = Field(default=None, description="视频发布的年份")
```

这一句其实就是定义一个数据模型。这个数据模型干嘛用？就是和我们的模型——大语言模型——进行整合，便于大模型进行搜索：大模型会根据你检索时传入的 question，自动从 question 里面把数据信息提取出来，提取出来之后封装成一个这样的 Search 模型；拿着这个 Search 模型，再去向量数据库里进行搜索。

### 结构化输出：把用户问题变成检索指令

模型定义好了，接下来把链里那个"模型"的位置稍微改造一下：通过 `model` 调它的 `with_structured_output` 函数，和 Search 进行整合——你可以理解为和一个结构化搜索的输出进行整合。这个刚刚定义的数据模型，既可以理解为结构化的搜索，也可以作为结构化的输出模型。

```python
structured_llm = model.with_structured_output(Search)   # 让大模型按 Search 的结构输出
chain = {"question": RunnablePassthrough()} | prompt | structured_llm
```

做了一下包装，得到一个链。有了这个链，接下来就可以用它来"搜索"了：直接 `chain.invoke`，把问题传过去。随便传一个，还是那句话："我怎么样去构建一个 RAG 的 Agent"——加个问号吧，当然你加不加无所谓。再把输出的结果打印一下。

然后搜索另外一个，把刚才那两行复制一份改一改："查找视频中关于 RAG 的部分，发布时间是 2023 年"。你会发现这句话不单有文本的相似度过滤，还有时间——发布时间是 2023 年的，其他年份我都不要。专门放这两个问题，是为了让大家对比得更清楚一些。

```python
print(chain.invoke("我怎么样去构建一个 RAG 的 Agent?"))
print(chain.invoke("查找视频中关于 RAG 的部分，发布时间是 2023 年"))
```

跑出来你会发现：得到的不是搜索结果！它非常智能地根据你用户传入的 question，自动分析出来应该构建成一个什么样的数据模型。第一个 question 翻译出来的模型是：直接检索内容，按照内容相似度进行检索，不用去管发布时间；第二个不单要检索内容——内容是关于 RAG 的——同时还要检索发布时间是 2023 年的。它会自动把你用户输入的问题变成搜索条件，可以这样理解。

它怎么知道要变成搜索条件？最关键的就是你用户输入的内容、这个提示模板，以及最重要的是：大语言模型和我们这个数据模型进行整合（`with_structured_output`），才能做到。前面如果直接给一个模型，它只会做内容搜索，不会做得这么精细化。

> **提示**：到这里，链的输出是 Search 对象——一条"检索指令"，不是检索结果。请问它真正去向量数据库里搜了吗？没有做。这一步只是生成了我们要去向量数据库中进行检索的指令，下一步才是根据生成的检索指令，去向量数据库里进行真正的检索。

### 真正执行检索：retrieve 函数与过滤条件

前面我们定义了数据模型，再结合大模型，就得到了一个检索指令——根据用户输入的问题，自动智能地解析出我们想要搜索的数据结构，就是前面定义的那个 Search。接下来就该根据这个数据模型的结构来进行检索了：去哪里检索？去我们的 Chroma 向量数据库里面进行检索。

首先定义一个函数，叫 `retrieve`，就是检索的意思。让它传一个检索的结构——就是前面定义的 Search 类型；然后返回搜索结果，是一个列表，列表中由一个个 document 组成。注意这个 document 要用 Chroma 对应包里的 Document 类型。当然你不写类型标注也可以。

拿到这个搜索指令想想：它其实就是一个结构化的检索条件，里面有两个检索字段——query 和 publish_year。query 一定是根据内容进行相似度检索；但 publish_year 不是根据内容，它是判断元数据是否和我们要检索的值具有相等的关系。所以这两个要分开处理。

分开处理之前先做判断：search 里面的 publish_year 可能没有——比如第一条检索指令里就只有 query，publish_year 是 None。所以如果 `search.publish_year:` 成立（你可以理解为就是 publish_year 存在），才去构造过滤条件。

过滤条件给它取个变量名，变量名随便叫，这里叫 `_filter`，它是一个字典。大括号里面写你要搜索的是哪个元数据字段——注意，这个键要跟 document 元数据里的字段保持一致，也就是 `publish_year`；检索的条件值又是一个字典：`$eq`。这是固定语法，Chroma 的固定语法，我相信大家一猜也就猜出来了——`$eq` 代表等于的意思。谁等于谁？Search 里的 publish_year 的值，等于向量数据库里 document 的 publish_year。比如要搜索的就是发布时间等于 2023 年的那些 document。

```python
def retrieve(search: Search) -> list[Document]:
    _filter = None                                   # 先给空值，原因见下
    if search.publish_year:                          # 年份存在才拼过滤条件
        _filter = {"publish_year": {"$eq": search.publish_year}}
    return vector_store.similarity_search(
        query=search.query,      # 内容相似度检索
        filter=_filter,          # 额外的元数据过滤条件
    )
```

其他情况下其实可以什么都不做，不过 `_filter` 要先定义一下：一开始给它一个空值 None。因为如果不满足 if 条件，就不会执行构造过滤条件的那一行，`_filter` 这个变量就不存在、没有定义——可后面我要用它。

> **易错点**：`_filter` 必须在 if 之前先置为 None。否则问题里不带年份时，这个变量根本没被定义，后面引用就直接报错了。

真正的检索还是使用这个 vector_store，通过相似度进行搜索——这次我们不再返回分数了。第一个参数传 query，就是 search 里面的 query，因为 search 里的 query 才是根据内容做相似度检索的；第二个参数可以传一个 filter，就是其他的一些过滤条件——你不但要根据相似度来检索，还可以再传一些额外的过滤条件。publish_year 有值的话，就有一个额外条件，就是 `_filter`。

这种检索就非常灵活了。这才叫真正的向量数据库检索：它不纯粹只是根据向量之间的相似度来进行检索，还可以基于一些特定的值、额外的搜索条件，两者结合。

### 链尾接函数，整个案例跑通

搜索函数写好之后，再把它和我们之前的链整合一遍，得到一个新的链：

```python
new_chain = chain | retrieve
```

原来的 chain 加个竖线 `|`，和 retrieve 这个函数整合。一整合之后它就明白了：把原来这个链根据你传入的数据搜索完之后得到的指令，传给 retrieve 这个函数。

现在就可以调了：`result = new_chain.invoke(...)`，invoke 里面还是传你的问题。我们传这个问题："2023 年关于 RAG 的一个教程"。到这一步，它其实已经自动帮我们搜到结果了。

把结果打印出来——把各种各样的信息都打印出来，用一个列表推导式，里面包含一个个的元组：for doc in result，拿 doc.metadata 里的 title；逗号隔开，再拿发布年份 publish_year。实际上你还可以继续拿其他的字段，逗号隔开接着写就行。

```python
result = new_chain.invoke("2023 年关于 RAG 的一个教程")
print([(doc.metadata["title"], doc.metadata["publish_year"]) for doc in result])
```

跑出来看结果：排名第一个的是 2023 年的——为什么是 2023 年？因为你指定了你的发布时间是 2023 年。第二个、第三个……一共返回了三个，也就是说符合我们这个条件的只有三个。很有可能其他一些视频字幕中也包含 RAG 的教程，但发布时间不是 2023 年，就被过滤掉了。当然每一个结果对应的是哪个视频，要把原始数据打印出来才能知道。

我们再试一下：问题里不包含年份。注意，不是"不传年份"，而是问题里面本身不含年份——比如就问"检索一下所有 RAG 的教程"。这个问题里解析不出任何跟时间、年份有关的内容，大模型就不会把发布年份抽出来，不满足 if 条件，`_filter` 保持 None，只按 query 进行相似度搜索。这时候结果就多了：关于 RAG 教程的，一共四个。

当然这个问题还可以继续变化，不断检查一下搜索的结果是不是达到你满意的效果。

整个案例的链路长这样：

```text
用户问题："2023 年关于 RAG 的一个教程"
    |
    v
chain = {"question": RunnablePassthrough()} | prompt | model.with_structured_output(Search)
    |   解析出检索指令：Search(query="RAG", publish_year=2023)
    v
retrieve(search)
    |   publish_year 有值 -> _filter = {"publish_year": {"$eq": 2023}}
    |   publish_year 没值 -> _filter = None
    v
vector_store.similarity_search(query=search.query, filter=_filter)
    |
    v
[Document(page_content=字幕内容, metadata={title, publish_year, ...}), ...]
```

读图说明：整条链路分两步——先由大模型把自然语言问题结构化成 Search 指令，再由 retrieve 拿着指令去 Chroma 里执行"相似度 + 元数据过滤"的组合检索。

最后回顾一下，刚刚整个案例我们做了一件什么事情：使用 LangChain 来检索我们的向量数据库，而且可以做到智能化的检索——它会自动根据我们用户所输入的问题，先做一下结构化，得到一个检索的数据模型；检索数据模型拿到之后，再根据生成的检索数据模型，真正地去向量数据库中实现检索。

把两种检索放在一起看：

| | 直接相似度搜索 | 结构化智能检索 |
| :--- | :--- | :--- |
| 检索依据 | 只有内容相似度 | 内容相似度 + 元数据过滤 |
| 检索条件来源 | 手写死在代码里 | 大模型从用户问题里自动抽取 |
| 能力边界 | 不智能，做不到精细化 | 可按发布年份等元数据字段精细过滤 |

> **承前启后**：上一节讲完「向量数据库的落库、加载与结构化智能检索」，下一节接着讲「让大语言模型读写结构化数据：从文本提取到数据合成」。

## 让大语言模型读写结构化数据：从文本提取到数据合成
> 对应块：BLK16 | 覆盖分集：P46-P49 | 块标题（分集名）：《【补习篇】提取和输出结构化数据》

这一节我们直接进案例——用 LangChain 来提取结构化数据。我们要构建一个链，让它从非结构化的文本中提取结构化的数据，而且是一种非常智能的提取。

这种案例有什么用？在自然语言处理里，表格数据抽取是一个非常重要的任务。但你想想，你拿到的往往并不是一张真正的表格，而是一大堆文本。我想把这堆文本变成表格化的——表格化其实你就可以理解为就是结构化的数据。那怎么变？那就需要一个大语言模型，能够理解语义，而且是非常智能地理解语义，帮我们把文字里隐藏的那些结构化的、或者我想要的数据提取出来，供后面再做其他处理。这个案例你在实际项目里搞不好用得着，因为它在提取数据这一块，确实非常智能。

> **定义**：所谓"表格化"，说白了就是结构化数据——数据有明确的字段、明确的类型，一张表就能装下。

### 提取之前，先定义一个人的数据模型

照惯例，我在 demo7 的基础上复制一份叫 demo8，里面的代码该删的全部删掉，只留下 model，前面的导包也清掉——导得太多了，其实我们用不着，时间相关的也暂时用不着。

要提取信息，你还记得吗？上节课我们是不是讲了一种数据模型，用的就是 Pydantic？这里再把它的作用捋一遍。Pydantic 主要干三件事：

- **处理数据**：比如接收参数、接收你的数据或者响应数据；
- **验证数据**：数据合不合格，它来把关；
- **定义数据格式**：数据到底是个什么样，包含哪几个属性，每个属性是什么。

再往细里说，序列化和反序列化、类型转换，这些也都包括在内——Pydantic 就是专门来处理数据的。现在我们要把一段文本里隐藏的、我想要的结构化数据拿出来，这个过程就一定会用到 Pydantic，至少你应该知道，反序列化就用得上。

所以假设你真的要提取数据，首先要做的第一件事，就是定义一个数据模型。这个模型的代码我就不带大家一个一个写了。假设未来我要从一段话中提取一个人的信息，那我就定义一个这样的数据模型：

```python
from typing import Optional

from pydantic.v1 import BaseModel, Field


class Person(BaseModel):
    """关于一个人的数据模型：某段话中包含人的信息时，
    把这些信息提取出来，最后封装成一个 Person 对象"""

    name: Optional[str] = Field(default=None, description="人的名字")
    hair_color: Optional[str] = Field(default=None, description="头发的颜色")
    height: Optional[str] = Field(default=None, description="身高，以米为单位")
```

几个要点说清楚：

- 继承的一定是 `BaseModel`。不是随便一个类都叫数据模型类，这一点之前讲过。
- 导包我们一直用的是 `pydantic.v1` 里面的；`Optional` 来自 `typing`；`Field` 也一样，先导包，保持一致，都用 `pydantic.v1` 的。
- `name` 为什么是可选的 `Optional[str]`？因为这个属性可能提取不到——文本的描述里没有嘛。后面两个字段跟它是一个意思。
- `Field` 里的 `default=None`：默认值我们没有，就是允许为空的意思；`description` 写上描述，写不写无所谓，这里表示人的名字。

字段当然可以有很多。到底要定义多少个属性？根据你要提取的信息未来有可能包含哪些来定——有多少你就提取多少，你就写多少个属性。这个模型非常简单，到这里就定义好了，做一下格式化，接下来就可以去搭链了。

### 提示模板与提取链

接下来定义提示模板。它是干嘛用的？当你输入一段话——或者是人输入的，或者是我从某个 Word 文档里读出来的一段话——要从这段话里提取结构化的信息，这段话就一定得放到提示模板里面去。模板我也直接复制粘贴过来，注释都带着：

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system",
     "你是一个专业的提取算法，只从非结构化的文本中提取相关信息。"
     "如果你不知道要提取的属性的值，返回该属性的值为空。"),
    MessagesPlaceholder("chat_history"),  # 需要结合上下文提取时才用得上
    ("human", "{text}"),
])
```

第一条是给当前这个 AI 的 system 提示，表示 AI 的定位：你是一个专业的提取算法，只从非结构化的文本中提取相关信息。假设你不知道这个人的名字，就把名字设置为空；假设你从文本中无法得到这个人的头发颜色，就给它一个空——就这意思。

中间这个 `MessagesPlaceholder` 是聊天历史记录。如果未来你的文本要根据上下文来提取——比如我还要根据你上一句话的意思，才能提取到我想要的内容——那你就加上这个记录上下文消息的占位符。不知道怎么存储上文消息记录的话，参考我们之前的案例，第二个案例里就讲过。最后 `{text}`，就是程序主动从某个文本文件里拿到的、要提取的文本。

然后是链。先说传参的写法：上节课第七个案例，我们是先定义好传参，比如 `question` 等于一个 `RunnablePassthrough`，表示提示模板中的参数未来再传，先定义在那里。这种写法其实也可以替换成现在这种字面量的写法，两者差不多——也就是说这个参数可以传也可以不传，不用那种方式传，用这种方式传也行。按照我的习惯，我个人的感觉是字面量的写法大家比较容易接受一些，那我们就用这种方式来定义这个链。注意参数名叫 `text`，不叫 `question` 了。

```python
chain = prompt | model.with_structured_output(schema=Person)

text = "马路上走来一个女生，长长的黑头发披在肩上，大概1米7左右。"
resp = chain.invoke({"text": text})
print(resp)
```

后面接模型的时候，**不能直接接模型**——模型要先调 `with_structured_output`，表示你这个模型的输出是一个结构化的数据。一定要加这句话。那这个结构化的数据到底是什么类型的、按照什么数据模型来得到？传一个数据模型进来就行，只要传这个 `schema`，`schema=Person`，这样一个链就有了。

拿来测试的这句话，就当它是从某个 Word 文档或者某个故事里拿到的其中一句。一个人读它，马上就知道里面有一个人物：头发是黑色的，大概 1 米 7，只是不知道这个女生叫什么名字。但现在不是人去理解，我们需要 AI 帮我们去理解，理解完之后还帮我们提取出来。

> **易错点**：我第一次点运行就报错了——点下去的一瞬间才反应过来，`invoke` 里根本没传参数，没传 `text`。`invoke` 传的键必须跟模板里的变量名对上，这里就是 `text`。

把 `text` 传过来再跑，信息就提出来了：人的名字不知道，是空；头发颜色是 black；身高 1.7 左右。以后每次只要换一下这个 `text` 就可以了。

有同学要问了：这个 black 为什么是英文的？你要想换成中文，把提示词稍微改一下就行；其实你还可以再通过一个链，把输出出来的数据再交给大语言模型翻译一遍，不也可以吗。这个程序比较简单，我就不带着改了。

现在这个链的数据流向是这样的：

```text
text ──▶ prompt（system 提示 + {text}）
              │
              ▼
model.with_structured_output(schema=Person) ──▶ Person 对象（name / hair_color / height）
```

读图一句话：要提取的文本塞进提示模板，模板接到"开了结构化输出"的模型上，链的出口就不再是自然语言，而是符合数据模型的结构化数据。

### 一段话里有好几个人怎么办

把女生那句话注释掉，换一句新的。前面跟上面一样：马路上走来一个女生，长长的黑头发披在肩上，大概在 1 米 7 左右；走到她旁边的是她的男朋友刘海，比她高 10cm。请问这句话里面有几个人？我相信只要是个正常的人，马上能理解出来是两个：一个女的、一个男的。女的是 1 米 7，男的多少？比她高 10cm，人在脑海中一算，应该是 1 米 8（$1.7 + 0.1$）。

现在需要用 AI 帮我们把文本里的所有人提取出来。你说这里面只有两个人？实际上无所谓，两个、三个、四个人都行，都得提出来。先把程序原样跑一下，看看效果。

结果出来了，大家发现什么问题？只提出了一个人，还是这个女生，1 米 7 黑色头发，刘海没有提取出来。你要是拿这个程序去 Word 文档里统计一共有多少个主人公，那永远只能提取一个，而且是第一个——这不行。我的要求很简单：我不管文本里面到底涉及多少人，只要是人的信息，就要把所有的全部提出来。

怎么解决？思路还是从数据模型开始。既然要提取多个人，那首先是不是也要定义一个数据模型？我给它取个名字叫 `ManyPerson`，多个人。它也是数据模型类，所以继承 `BaseModel`。那怎么在一个类里面代表多个人？我相信大家马上就知道了——弄一个列表嘛：

```python
class ManyPerson(BaseModel):
    """数据模型：代表多个人"""

    people: list[Person]
```

`people` 的类型是 `list`，中括号里面是 `Person`——你看，这就用到了前面那个 Person 数据模型类，新的模型类跟之前人的数据模型类是有关联关系的。列表里包含到底多少个人无所谓，两个人、一个人都行。

然后只需要一处改动：把 `with_structured_output` 的参数 `schema` 换成 `ManyPerson`，表示一次性可以提取多个人——当然也可以只包含一个人。就加了这么一点点代码，再运行。

出来了：得到一个 `people`，是个数组。数组里第一个 Person，黑色头发、1 米 7；第二个 Person，刘海，头发不知道——文本里没说，为空——但是身高是 1 米 8。他怎么知道刘海是 1 米 8？你想想，一定是 AI 理解了"比她高 10cm"这句话的含义，否则他不可能知道刘海这个人的身高。

再告诉大家一个事：这个程序不但支持中文，还支持英文。把 `text` 换成一段英文——我的名字叫 Jeff，头发颜色是黑色的，身高多少多少；还有另外一个人叫 Arm，有相同的颜色。跑一下，一下就提取出两个人：第一个人 Jeff，头发颜色 black，1 米 83；另外一个人 Arm，头发颜色也是黑色——"相同的颜色"它也识别出来了——身高你没说，所以为空。

> **结论**：这个程序不单可以提取一个人，还可以提取多个人，多少人无所谓，甚至能根据文本的语义计算出每一个人的头发颜色和身高。

这个案例未来搞不好确实有用。做简单的数据分析、数据挖掘时，公司给你的数据可能不再是结构化的。举个例子：我们需要 AI 帮我们捋一下整个红楼梦里面的人物关系，那首先是不是得把红楼梦里的所有人物提取出来？那我是不是要把红楼梦这篇小说再看一遍？不用了。只要把红楼梦这本小说变成电子档的，交给 AI，AI 帮我们看一遍，自动就能提取出来有哪些人、每个人有些什么特征。这个特征不就是我们所谓的面向对象的属性吗？属性到底定义是什么，由你自己来决定。案例八就到这。

接下来是案例九：用大语言模型自动帮我们生成一些数据。说白了，就是使用 AI 来帮我们进行合成数据。

### 用 AI 合成数据

合成数据这件事，现在很热。很多新的大语言模型，训练数据就是由之前的 AI 合成出来的。因为真实数据有两个问题：

1. 真实数据你很难获得，需要很高的成本；
2. 你就算获得了，它的鲁棒性、它对训练集的友好度，也不一定是很好的。

而我们自己通过 AI 合成或者生成的数据，可以根据我自己的格式、我自己设置的风格、我自己设置的样式，来生成我想要的数据。它生成的这些随机数据，搞不好对我们新模型的训练反而更好一些。关于 OpenAI 下一代模型的训练数据怎么来的，网上有些论文，甚至 OpenAI 自己也流传过一些文章，大家可以了解一下。确实，现在不管是国内还是国外，新的大语言模型的数据，其中有一部分——不是全部，至少有一部分——是合成的数据。

别说大语言模型的训练，未来搞不好我们自己在企业里面做一些小模型的训练，也是全部采用合成的数据。因为合成或生成的数据，可以模拟真实数据，同时又不会泄露隐私、不会遇到现实世界的限制。比如从网络上爬虫获取数据：一个是你现在很难爬；第二个，就算爬下来，你还不一定敢用于商业的模型训练——被人查出来，他可能会告你。那我这个数据是自己生成的呢？你告了没用啊。

要生成数据，需要安装一个依赖包，它也是来自 LangChain 的一个子项目，叫 `langchain_experimental`，专门帮我们合成和生成数据用的，里面有很多东西，连常量都有。这里插一句临场的话：你跟着我写代码的时候，首先一定要记住，课件里需要你安装的第三方库，你一定要先安装一下——你别看我没装，其实我提前就已经把这些都装好了。

幻灯片上列了合成数据的九个优势，说实话这些优势大家不用我说，自己也理解：什么数据的增强性、灵活性、还有成本效益以及监管合规。我觉得最重要的其实就是模型的鲁棒性——它可以带来泛化更好的 AI 模型。我们训练模型的时候，最重要的考虑其实就是泛化这一点。

所以我个人的看法是：未来你在企业里面做大语言模型的调优或者大语言模型的训练，完全可以使用 AI 自动生成的数据，但生成的数据肯定要满足你的项目需要。所以你一定要掌握：通过 AI 来生成数据时，怎么定义数据的格式、怎么定义数据的风格，这个要掌握。

### 先从生成一句话开始

回到 PyCharm，照惯例在 demo8 的基础上复制一份换成 demo9，该删的删掉——注意 `os` 不能删，删掉之后后面全都是错误。

模型我们一直用的是 OpenAI 的 gpt-4-turbo。这个模型是最贵的，你使用的时候要是感觉太贵了，可以换成 3.5，一样的，其实效果差不太多。然后还可以指定一些其他参数，比如温度 `temperature`。生成数据的话，你一定要生成多样的，所以可以设高一点，我们设成 0.8——最高可以到 2.0。

生成数据也是一样，先创建一个链。有了大语言模型之后，调用一个函数——注意，这个函数来自我们新安装的这个库，函数名字叫 `create_data_generation_chain`，创建数据嘛，generation 就是生成器的意思：

```python
import os

from langchain_openai import ChatOpenAI
from langchain_experimental.synthetic_data import create_data_generation_chain

model = ChatOpenAI(model="gpt-4-turbo", temperature=0.8)

# 创建生成数据的链：第一个参数是大语言模型；第二个参数是模板，一开始可以先不传
chain = create_data_generation_chain(model)
```

`create_data_generation_chain` 要传参：第一个参数就是模型，大语言模型；有没有第二个？有，就是那个模板。但模板一开始不着急，我们暂时没有模板，先不传，可以给一些提示就行。

然后生成数据，我们先从最简单的开始：生成一句话。一般生成数据，多多少少要给它一些关键词，我就随便给它一些颜色：

```python
# fields 放关键词；preferences 放风格等偏好，暂时不需要就先给一个空字典
result = chain({"fields": ["蓝色", "黄色"], "preferences": {}})
print(result)
```

调用的时候注意：这个 `chain` 你直接调，不用调用 `invoke` 了，就像调用构造函数一样——其实呢，这个并不是构造函数，只调用它这个链的启动函数。里面传一个 `input`，是一个字典，用花括号括起来。这个字典有两个键是固定的，记住啊：一个是 `fields`，字段，里面放关键词，比如蓝色、黄色——我搞一些颜色，两个都给；另一个是 `preferences`，选项、参数的意思——比如你要生成什么样风格的，或者给它一些提示。一开始你可以不给，不给就给它一个空的字典就行了。

我们这里没有任何风格，它也不知道要生成什么，所以默认就生成一个文本。打印出来，结果里前面那一块不用看——你可以理解为就是我们的输入，重点看 `text`：

> 在清晨的蓝色的天空中，一轮明亮的黄色太阳升起，照耀着整个海滩，将沙子染成金黄色，海水泛着宝石般的蓝色光芒……让人感到一种宁静和活力并存的美好。

你看，这里面大量使用了你的关键词。它生成这么一段话，比一般——至少比我写出来的文章里面的语言——要漂亮一些、美好一些，看起来舒服一些，读起来也舒服一些。你再运行一下，它随机又生成一句，跟上面这句肯定不一样，我是懒得再执行一遍了。

### 指定风格：像诗歌一样

参数给得不同，生成的数据就不一样。刚才只是让它生成一句比较优美的画，现在我想让它生成一种我指定的风格。风格这个单词叫 `style`，什么风格呢？我先只给它一个中文提示：像诗歌一样。意思是，我给你这些关键词，你生成的文本得像一首诗、像一首诗歌一样，懂我意思吧：

```python
result = chain({
    "fields": ["蓝色", "黄色"],
    "preferences": {
        "style": "像诗歌一样"
    },
})
print(result)
```

（前面那段要注释掉，否则它会生成两遍——当然我们最终只打印最后一遍。）

生成的结果：在蔚蓝色天空下，一轮明月好像像诗歌一样照耀着大地。但是你看，这句有点不太对，我们可以再调整一下：明确地把要求写详细——我输入的就是一些颜色，根据我给你的这几个颜色，你帮我生成一些文字，这个文字得像诗歌一样，这是我主要的目的：

```python
result = chain({
    "fields": ["蓝色", "黄色"],
    "preferences": {
        "style": "我输入的就是一些颜色，根据我给你的这几个颜色，"
                 "你帮我生成一些文字，这个文字得像诗歌一样，这是我主要的目的"
    },
})
print(result)
```

再看：蓝色的天空如诗般纯净，与黄色的太阳相互辉映，仿佛是大自然最美的交响乐章。这个差不多可以了，跟诗歌的关系还在里面。这就是我们的风格。

当然，这个风格生成得也不是非常准确，因为它生成的文本多样性太多了——我们给它的温度是 0.8 嘛，有时候它生成的是满足你要求的，有时候就不满足。

总而言之，这就是生成文本，我们先讲了怎么生成一些文本。但你想，我们最终不是为了生成文本。生成数据的话，一定是那种结构化的数据，而且是严格规定格式的——风格可以自己去调。接下来详细讲讲怎么生成那种结构化的数据。

### 生成严格格式的结构化数据

案例九继续。刚才通过 AI 生成的是文本数据，但这并不是我们想要的——我们想要的数据，是指定格式、指定风格的那种结构化的数据，这才是未来可能用得最多的。还是在 demo9 的基础上做调整，代码可能会变得复杂一点。先给大家捋一下：要完成整个结构化数据的生成，一般来说有五个步骤——第一步定义数据模型，第二步提供样例数据，第三步创建提示模板，第四步创建数据生成器。我们一步步来。

#### 定义数据模型：医疗账单

第一步，定义你要生成的数据模型。怎么定义之前讲过了，代码我就不再带大家写了，直接把写好的复制粘贴过来。我要生成的是一种结构化的数据，叫医疗账单数据，`MedicalBilling`，继承的还是 `BaseModel`——之前提过，我们一般选 `pydantic.v1` 里面的。

```python
from pydantic.v1 import BaseModel


class MedicalBilling(BaseModel):
    """医疗账单数据模型"""

    patient_id: str                  # 患者ID
    patient_name: str                # 患者姓名
    diagnosis_code: str              # 诊断代码
    total_charge: float              # 总费用
    insurance_claim_amount: float    # 保险索赔金额
    # 一共六个属性，都是一张医疗账单里该有的信息
```

一共定义了六个属性，都属于这个医疗账单数据模型：患者的 ID、患者的姓名、诊断代码，还有总费用、保险索赔的金额——就是总费用是多少、保险报销了多少，大概这个意思，这是一张医疗账单。当然这只是给大家举个例子，你可能感觉属性还是太少了，不应该只有六个，应该有 26 个——你自己看着办。

注意，这里我们不再一个一个定义 `Field` 了。其实定义 `Field` 也是可以的，它有一个好处：描述可以写得更详细一些。那你想想，假设你不写描述，计算机是不太理解你这个属性是什么的。你别看我这里加了注释——我这个注释只是为了让你看得懂、让其他程序员看得懂，而不是说这个注释是让 AI 能看得懂的，这一点你要明白。那 AI 怎么去理解每个字段是啥东西？等会就要给它样例数据。

估计还有人要问：模型类我能看得懂，类型后面确实不用加等号去 new 一个 `Field`，可你这里面类型怎么都不是可选的呢？原来我们定义数据模型类，一般都是可选的。你想想，我们为什么要定义可选？因为当时是为了提取数据——提取数据有没有可能提不到？肯定的嘛。那现在这节课讲的是什么？生成，通过 AI 帮我们生成或者合成我们想要的数据。你让 AI 帮我们合成数据，是不是要尽可能让它把所有数据都合成出来，每个字段都不少？肯定的嘛。你不可能说 AI 帮我们合成一些随机的数据，还少几个字段——你觉得有意义吗？所以这里就不需要 `Optional` 了。

| 场景 | 字段要不要设成可选 | 原因 |
| :----------------- | :------------------- | :----------------------------------------- |
| 提取数据（案例八） | 要，用 `Optional`    | 文本里可能根本没有这个信息，提不到只能给空 |
| 生成数据（案例九） | 不要，每个字段都必填 | 就是要 AI 把所有字段都合成出来，少字段没意义 |

#### 提供样例数据

第二步，提供样例数据。你把样例数据给 AI 之后，AI 才知道你到底要生成的数据大概是一个什么样的结构。样例数据我也不直接带大家敲了，敲这个没有任何意义。我定义了三条样例数据，每一条都是一个字典，每个字典的键叫 `example`：

```python
examples = [
    {"example": "患者的id: 123456, 患者姓名: ……, 诊断代码: ……, 总费用: $……, 保险索赔金额: $……"},
    # 一共三条，每条一个字典；字段出现的顺序严格跟数据模型类保持一致
]
```

你看 `example` 里面，实际上是一段文本，看起来并不像是结构化的，但事实上是按照结构化的样子去给它的：患者的 id 是 123456，患者的姓名等等的，后面都有。

样例数据有几条规矩，千万注意：

- **顺序**：一定要按照数据模型类里面字段的顺序去提供，千万注意，一定要按照这个顺序；
- **键用文字描述，不要下划线**：Python 中定义属性名字，每个单词之间使用下划线，但你提供的样例数据，尽量用文字描述，它就没有所谓的下划线——比如"患者的id"，中间不要加下划线；
- **换成中文行不行**：可以的，患者的 ID、保险的索赔金额，都可以换成中文。当然用英文的话，生成的数据可能更准确一些，因为我们用的是 OpenAI 的模型，它对英文文字的理解确实比中文稍微好一点点；
- **值随便给**：患者的 id、患者的姓名，以及后面这个金额，你给什么都行。就算金额带了美元符号也没关系——浮点类型本身是不能带 `$` 符号的，但你可以给，AI 会自动知道：不管前面这个美元符号，只要考虑后面那一串数字就可以了；
- **每个字段都得给**：尽量每个字段都得给，你不能少。少了之后，后面生成的数据可能就不准确；
- **数量不用多**：三五条就可以了，三条最起码，多的话给个十条，一般最多给十条就够了。你给的再多，没有用，没有任何意义。

#### 创建提示模板

第三步，创建一个提示模板，用来指导 AI 生成符合规定的数据。为什么要模板？样例数据最后是要传给模型的，可模型不知道你这个样例数据是一个什么样格式的，所以得有模板告诉它。

这个提示模板是两层的。先建单条样例的模板：new 一个 `PromptTemplate` 类的实例。第一个参数 `input_variables`——这个参数没有提示，我们直接自己敲——表示输入的参数有哪些，写在一个中括号里，多个参数用逗号隔开。那这里输入的参数是什么？你想想，这跟之前聊天、提问不一样：聊天的话，要不断给大语言模型发送一些问题、发送一些聊天的信息；生成数据的话，你要输入给 AI 大模型的只有样例数据，其他的我们不要。那输入的样例数据有没有参数？参数就是 `example`——参数我们只有一个。这个参数名字随你叫，你不叫 `example`、叫 `medical_billing` 也可以，反正我们最终不是要读这个字典中的键，而是读这个键所对应的值——那才是 AI 要读的数据。

```python
from langchain_core.prompts import PromptTemplate

example_prompt = PromptTemplate(
    input_variables=["example"],   # 输入参数：一条样例；名字随你，前后保持一致即可
    template="{example}",          # 通过变量替换的方式传参，读出键对应的值
)
```

然后 `template`，真正正儿八经地在模板中定义参数：通过变量替换的方式传参，写一个 `{example}`。这个模板对象的作用，就是告诉 AI：你输入的样例数据，要读的部分是哪一部分——我们是通过一个个 `example` 传过去的。模板里这个参数名字，跟 `input_variables` 里的那个，肯定要保持一致：你的参数是一条一条的，每一条都是一个 `example`，`example` 到底怎么传到模板里面，就是按你指定的这种格式传过去的。

> **易错点**：别以为到现在为止就已经得到提示模板了。其实还要基于这个模板，再创建一个比较复杂一点的模板——因为未来生成数据的格式虽然已经通过模型类确定了，但这个模型类你发现没有？传到 AI 那边去了吗？没传。所以我们还要定义一个真正的模板。

真正的模板用 `FewShotPromptTemplate`，参数传得比较多：

```python
from langchain_core.prompts import FewShotPromptTemplate
from langchain_experimental.synthetic_data import (
    SYNTHETIC_FEW_SHOT_PREFIX,
    SYNTHETIC_FEW_SHOT_SUFFIX,
)

few_shot_prompt = FewShotPromptTemplate(
    prefix=SYNTHETIC_FEW_SHOT_PREFIX,       # 前缀：带指导性上下文的指令，包里的常量
    suffix=SYNTHETIC_FEW_SHOT_SUFFIX,       # 后缀：跟前缀差不多，换个常量
    examples=examples,                      # 三条样例数据
    example_prompt=example_prompt,          # 每条样例怎么渲染
    input_variables=["subject", "extra"],   # 固定死的参数名：主题 + 额外要求
)
```

- `prefix` 是前缀，我们用 `SYNTHETIC_FEW_SHOT_PREFIX`——它是包含指导性上下文指令的一个前缀，这个前缀其实是一个常量，直接从包里复制粘贴过来就可以了；
- `suffix` 是后缀，跟前缀差不多，复制粘贴，只是把 `PREFIX` 换成 `SUFFIX`，一样导包；
- `examples`，样例数据传过去，这个大家可能好理解；
- `example_prompt`，就是上面那个单条样例模板；
- 最后还有一个 `input_variables`——这个参数的名字是固定死的，都来自这个类本身（当然没有参数提示）。它是一个数组，里面规定两个东西：`subject`，你要生成的数据的主题是什么；`extra`，有没有额外的一些提示。那我到底要生成一个什么主题的数据？等会就通过 `subject` 和 `extra` 这两个参数名字，把主题和额外的要求再传过去——模板后面还可以继续传值。

到这里，模板的组装关系就清楚了：

```text
examples（3 个字典，每个字典的键都叫 example）
    │  逐条交给 example_prompt 渲染
    ▼
few_shot_prompt = PREFIX（指导指令） + 3 段样例文本 + SUFFIX
    │  subject（主题）、extra（额外要求）由后面继续传值
    ▼
第四步：创建结构化数据的生成器
```

读图一句话：三条样例套进单条渲染模板，再夹上前缀、后缀两段指令，就得到一个能告诉 AI"照这个样子、按这个主题"生成数据的完整提示模板。

到了第三步，才真正把模板创建出来。接下来是第四步——生成，就是创建一个数据生成器，一个结构化数据的生成器。

## LangChain 结构化数据实战：合成数据、文本分类与文本摘要
> 对应块：BLK17 | 覆盖分集：P50-P53 | 块标题（分集名）：《【补习篇】生成结构化的数据(二)》

这一讲承接上一讲的合成数据案例：数据模型类和提示模板都已经备好，现在把它们组装成生成器，把十条医疗账单真正跑出来。跑完之后趁热打铁，用同一套结构化输出的思路再打两个案例——文本分类和文本自动摘要。动手第一步就出了个小插曲：敲完 `generator` 一检查，这个单词是不是写错了？还真少了个字母，改过来，继续。

### 合成医疗账单：把生成器跑通

#### 创建生成器：三个参数各就各位

直接定义一个变量叫 `generator`，调用 `create_openai_data_generator` 函数来创建它。写的时候一定要看一眼 IDE 的参数提示——调用函数的时候，每个参数要传什么，提示里都写得清清楚楚。

```python
generator = create_openai_data_generator(
    output_schema=MedicalBilling,   # 指定输出数据的格式：前面定义好的 Pydantic 数据模型类
    llm=llm,                        # 大语言模型：之前已经创建好了
    prompt=prompt_template,         # 指定提示模板：前面也已经创建好了
)
```

第一个参数是输出的 schema，也就是输出数据的格式——就是我们前面定义的那个数据模型类；第二个是 LLM，大语言模型已经有了；第三个是指定模板，把前面创建好的提示模板传进去。这样就能创建得到一个生成器。

这个生成器其实就相当于之前我们讲的链，但它和链还是有区别的：它确实是一个可调用的东西，不过它一调用就直接生成数据，所以调用的函数不一样——生成器调的是 `generate()`，这个函数之于生成器，就相当于 `invoke` 之于链。

#### 调用生成器：主题、指导信息与条数

调用生成器就可以得到我们想要的数据了：

```python
result = generator.generate(
    subject="医疗账单",   # 指定生成数据的主题
    extra="人名可以随机，但请使用比较生僻的人名，不要用张解放、建国这类年代感很强的常见名字",  # 额外的指导信息
    num_runs=10,          # 指定生成数据的数量
)
print(result)
```

要传什么参数，是由你前面提示模板中定义的变量决定的。模板里规定了要传入的参数叫 `subject`，那你在调用生成器的时候，参数名也必须是 `subject`，要跟它保持一致。`subject` 是什么？就是我们指定的生成数据的主题，这里写"医疗账单"。

第二个参数是 `extra`，额外的一些指导信息。这个指导信息是用来辅助规范化生成数据风格的。比如我们希望生成出来的患者人名不要和真实的人名相冲突：人名可以随机，但不要张解放、建国这类一看就跟年代绑定的常见名字，给我生成一些比较生僻的人名。你其实还可以接着往下写：生成的账单金额大一些、总费用呈正态分布、甚至设置一个报销的比例范围，都可以，这些统统属于额外的指导信息。

> **易错点**：`generate()` 的参数名必须与提示模板里定义的变量名完全一致。模板里叫 `subject`，你就不能写成别的名字；后面链的 `invoke` 传参也是同一个道理。

最后一个参数 `num_runs`，表示生成的数据一共有多少条，我们生成十条。

#### 跑起来之后：现场调教

第一次运行有点慢，它会帮我们生成十条数据。这里说明一下为什么模型换成了 3.5-turbo：生成十条数据要消耗的 token 已经不少，如果生成 100 条，token 就更多了，用太贵的模型，价格很多人承受不起，所以换成 3.5-turbo。

看生成的结果，每条账单一位患者：梁秋雪——我也没听过有没有这个人；王芳倒是挺平常的；还有沈春梅、赵雪婷、李欣怡、朱灵……说实话都不算生僻，可能是我们给它的提示模板不对。那就换个写法，顺便让金额也带点规则：

```python
extra = (
    "人名可以随机，但请使用比较生僻的人名。"
    "医疗总费用呈现正态分布，最小的总金额为 1000"
)
```

因为生成的数据可能是中文的，模型对中文的理解不一定非常好，所以做数据生成的时候，这些提示尽可能使用英文，一定会更好一些。

再跑一遍看总金额：800、950、985.2、975……都压在 1000 附近。我估计模型是把"最小的总金额为 1000"里的 1000 理解成了正态分布的均值。所以更好的写法是"呈现正态分布，均值是多少"——明确把均值写出来，这样做可能更好一些。具体数值大家自己去调。总而言之，它已经帮我们生成出想要的数据了。

还有一点：得到的结果是一个列表，就相当于 Java 里叫数组一样的东西。想把数据插入数据库？后面非常简单——遍历之后，直接用 INSERT 的 SQL 语句把它插到数据库里去。这个案例就讲到这里。

### 文本分类：让 AI 给文章打标签

接下来进入案例十：用 LangChain 实现文本分类。文本分类是自然语言处理中非常重要的一个任务。如果你学过我们的 AI 核心课程，里面机器学习部分有个小项目，是做用户评论数据的情感分类——评论数据就是文本，把这些评论按情感或其他维度分类，都属于 NLP 的文本分类。

文本分类旨在将文本数据自动归类到预定义的类别中，是实现信息检索、智能推荐、情感分析等应用的基础技术之一。先把文本分成类，后面再做检索或者推荐，就容易多了。主流的应用场景：情感分类，就是刚才说的用户评论情感分类；话题标记——给你一些人的聊天信息，根据聊天记录分辨整段对话是针对一个什么话题的；新闻分类——体育新闻、国际新闻等等；还有对话分类，后面不一一列了。

那到底按情感分、按话题分还是按新闻分？你首先要把这些分类定义出来。分类的维度由你来定，由我们程序员来规定。回到 PyCharm 中，边写代码边说情感分类怎么做。

#### 先把温度设为 0

在 9-2 的基础上复制一份项目，命名为 10，把里面没用的东西删掉——大语言模型那部分肯定要留着。原来温度设的是 0.8，情感分类可不能这么设。想想温度是什么意思？每次执行之后，输出的多样性会增加。但情感分类恰恰不应该有多样性——你规定这篇文本是什么类别，它就是什么类别，不能这次运行是 A 类别、下次运行是 B 类别，这种不确定性要不得。

所以做文本分类，强烈建议大家把 `temperature` 设置为 0。至于用哪个模型倒无所谓：3.5-turbo、4o、4-turbo 都可以。

```python
llm = ChatOpenAI(temperature=0)   # 用哪个模型都行：3.5-turbo、4o、4-turbo 都可以
```

#### 数据模型决定文本怎么分

接下来定义数据模型类——什么叫数据模型类之前解释过，也用过几次了：写一个类继承 `BaseModel`。

```python
class Classification(BaseModel):
    sentiment: str = Field(description="这段文本的情感")
    aggressiveness: int = Field(
        description="描述文本的攻击性，预期为 1~10 的整数，数字越大表示越具有攻击性"
    )
    language: str = Field(description="这段文本是用什么语言写的")
```

`sentiment` 就是"情感"这个单词，`Field` 是域、字段的意思，给它一个描述。这个数据模型决定了我们未来把文本怎么个分法：定义了情感字段，未来的分类就是基于情感的分类。

估计有人说：我不单要对文本做情感分类，还要做其他的分类，怎么办？其实你可以一次性给文本打很多标签——所谓文本分类，其实也称之为打标签。举个实际点的例子：假设给你一篇 500 字的文章让你做分类，说白了就是给这篇文章打上各种各样的标签。

情感标签怎么打？可以用"非常生气""心情美好"这样的词；还可以把心情从"非常好"到"生气"做成一个分值：0 分表示心情非常好，1 分表示心情一般般、也蛮好，2 分、3 分表示心情一般，4 分开始有点生气，5 分就非常生气了，6 分那是去爆发了——通过分值来定义情感的级别。不用分值也行，直接用单词：心情非常好、心情好、有点生气、非常生气，四种。具体怎么规定后面就讲，不着急。

标签不可能只有一个。同一篇文章还可以打话题标签：这篇文本是正常描述一件事，打个"正常描述"的标记；也可能整篇都在批判某个人、批判某个观点，而且措辞非常强烈——那就打一个"攻击性比较强"的标签。攻击性到底有多强，同样可以用数字来区分，或者用不同的单词来处理。还可以打语言标签——文本可能是中文，也可能是其他语言的文章。

所以这个 Pydantic 数据模型的作用就是：未来根据该模型完成文本分类。到底要分多少个维度，就看你在这里定义了多少个属性。我定义了三个属性，未来就给一篇文章打三个标签：第一个标签代表文章的情感，第二个代表攻击性有多强，第三个代表用的是哪种人类语言；你再写第四个、第五个、第六个甚至十个属性都行——第四个标签还可以代表这篇文章属于哪种新闻类别——由你的项目决定。

#### 模板、链与一次调用

有了类，接下来定义提示模板。提示模板之前讲过太多太多了，直接用 `ChatPromptTemplate` 创建，内容非常简单：

```python
prompt = ChatPromptTemplate.from_template(
    "从以下段落中提取所需要的信息，只提取 Classification 类中提到的属性。\n\n{input}"
)
```

意思是：我只让你提取这个类中规定的那些属性、那些标签，其他的我不要你了。段落由用户输入的参数 `input` 提供——变量名你爱叫什么叫什么。怎么写提示模板的感觉，大家可以在这里慢慢培养。

然后组链。一般来说有模板就先写模板，竖线接模型；模型后面一定要接一个函数 `with_structured_output`，把 Classification 通过参数传进去——它规定大模型返回的数据必须采用结构化类型，必须按照我们定义的这个数据模型来返回。一定要这样写：

```python
chain = prompt | llm.with_structured_output(Classification)
```

调用非常简单。`invoke` 的参数名跟着模板走：模板里的参数叫 `input`，这里就传 `input`，输入的值就是那段文本。我们随便写一句话——最近看到一篇新闻，就写"中国人民大学的王教授师德败坏，做出的事情让我非常生气"。你可以写得更复杂一些：

```python
input_text = "中国人民大学的王教授师德败坏，做出的事情让我非常生气。"
result: Classification = chain.invoke({"input": input_text})
print(result)
```

请问大模型调用完之后，得到的结果是什么类型的？一定是结构化类型的 Classification——因为我们调用了 `with_structured_output`，规定了返回类型就是 Classification。所以这里我给 `result` 标注了类型。这种 Python 写法就是给变量定义类型，不标也完全可以，只是为了让大家看起来好看一点：一眼就知道 `invoke` 调用完之后，返回的是 Classification 类型的对象。

第一次右击 Run 大概率会失败，因为运行配置里没加 OpenAI 的 key——把项目"九"的运行配置拷贝过来就能跑了。

#### 两段文本试跑

跑出来一看，`result` 确实是 Classification 对象：情感分类是一个英文单词，生气级别是 5——已经算比较高的了，语言是 `chinese`，识别出是中文。

那个情感单词是 negative。有些人不知道啥意思，拿翻译工具一查——注意，翻译成"阴性"是不对的，它在这里表示的是消极、负面。确实如此，这段文字的情感就是比较消极。

> **提示**：`negative` 在这里要理解为"消极（负面）"，不是生物意义上的"阴性"；同理 `positive` 是"积极（正面）"，不是"阳性"。别被翻译软件的字面直译带偏。

再换一种语言测。这段西班牙语是我从别的地方直接复制粘贴过来的，说实话它具体啥意思我也不太清楚——拿去一翻，是"很高兴遇见你，我想我们会成为很好的朋友"，就是一句打招呼的友好问候，表示心情比较好。跑出来：`positive`——同样别理解成"阳性"，是积极、正面；生气级别是 0，就是没有生气；`language` 是 `spanish`，西班牙语。你看，找了一个比较小众的语言它都识别得出来，当然你用英语它更能识别。

这不就打上标签了吗？情感是一个标签，攻击性是一个标签，语言也是一个标签；属性再多，标签就更多。

收尾之前留一个问题：文本的情感不可能永远只分积极、消极两种，我想分成四种、五种怎么办？或者我不想用 positive、negative 这些单词，想换成其他的词来代表文章的情感，可不可以？可以——但要你自己去规定。怎么规定，下一节继续。

### 给标签上硬约束：用枚举细化取值

#### 第一版粗糙在哪

上一节的文本分类案例，说实话比较粗糙。来分析一下代码：数据模型里有没有规定文本的情感到底分为哪几种、每一种用什么单词来标记？没有。那 AI 只能根据你的描述自由发挥——你要它打情感标签，它就返回"积极的"或者"消极的"这些词。我不想用这个词可不可以？可以，但你要自己去规定，这是第一个问题。

第二个问题：攻击性打分，字段描述里写的是"预期为 1~10"。可它真的就是 1 到 10 吗？不是。你没有硬性规定，AI 实际上不知道——别以为你在描述里写了，AI 就知道最低 1 分、最高 10 分。你看它打出过 0 分，很明显就不符合我们的要求。最低我见到过 0 分；最高是多少我也不清楚，我没试过。

> **易错点**：写在字段描述或注释里的"预期 1~10"只是描述，不是约束。不给模型规定硬性的取值集合，它就可能给出范围之外的值。

那怎么办？要做严格的规定才行——把这个类重新写一遍。

#### 每个字段加一个 enum

把原来的类注释掉，重新定义。每个字段都用 `Field(..., enum=[...])` 的写法：前面的 `...` 表示该字段必填，后面的 `enum` 用枚举规定取值集合。

```python
class Classification(BaseModel):
    sentiment: str = Field(
        ...,
        enum=["happy", "neutral", "sad"],
        description="这段文本的情感",
    )
    aggressiveness: int = Field(
        ...,
        enum=[1, 2, 3, 4, 5],
        description="文本的攻击性打分，最低 1 分，最高 5 分",
    )
    language: str = Field(
        ...,
        enum=["english", "spanish", "french", "中文", "italian"],
        description="这段文本是用什么语言写的",
    )
```

情感的枚举用了三个单词：`happy`、`neutral`、`sad`——高兴、一般、心情非常烦躁。换成中文也可以，只是英文可能稍微准确一点点。这三个字符串就是预期的三个情感标签，后面的结果里只会出现这三个单词的其中一个。

攻击性的枚举是 1 到 5。为什么最低一分、最高五分？因为枚举里就这么规定的——很明显最低是一分、最高是五分，中间还可以打 2、3、4。也就是说，你给我的文本的攻击性打分，只能打 12345 这五个分值中的一个。

语言这边，之前模型返回的是 `chinese`，我们不想用这个词，就用中文的"中文"来标记：枚举里写上 `english`、`spanish`、`french`、"中文"、`italian`。

其他地方一个字都没改，只改了数据模型类。重点就是给每一个字段加了一个枚举——说白了就是给每个分类、每个标签做了规定，做了细化。所以未来你要做文本的情感分类，一定要按第二种这种写法来定义模型类；枚举里放什么内容，你根据项目需求随意去填。

再跑一遍。西班牙语那句问候：用的单词是 `happy`——高兴的嘛；分值是 1，不再是 0 了；语言 `spanish`。换回中文那句抱怨：`language` 直接就是"中文"了；打 5 分，表示已经很生气了；情感是 `sad`。为什么是 sad？你想，"做出的事情实在令我生气"，心情是不是稍微有点糟糕？

我这个文本很短，大家肉眼就能判断；实际上你换成一大篇 1000 字、2000 字的文章，它一样能帮你分类——大语言模型做文本的情感分类，不管文本的大小：一句话、两句话、100 字、1000 字，都 OK。

你发现没有，非常简单，不难。整个案例最重要的就是：怎么根据你的项目需求，来定义这个 Pydantic 数据模型类。

### 文本自动摘要：三种方式先立骨架

接下来进入案例十一：用 LangChain 完成文本的自动摘要。这个案例，我觉得对做学术研究的人、专门做文本处理的人是特别爽的。比如看到一篇文章，它主要讲什么？正常你得把整篇看完才知道；但文章特别长的时候，我们不需要花那么长时间通读，可以让 AI 大语言模型自动帮我们把整篇文章做一个总结和摘要。

假设你有一组 Word、PDF、网页，或者一堆客户的问题等等，想把内容总结一下——鉴于大模型在理解和综合文本方面的熟练程度，它是完成这项任务的绝佳工具。到现在为止，大模型帮你做文本的总结和摘要已经非常准确，大部分情况下，甚至比人来做文本的总结和自动摘要还更准确一些。

当前案例需要额外安装两个库：`tiktoken` 和 `chromadb`，必须要装上；安装过程不说了，命令都给过了。

要实现文本自动摘要，一共有三种方式。这里一定要去读英文单词：第一种 `stuff`，中文叫"填充"——光看"填充"这两个字你根本不知道要干嘛，中文直译在这种场景下并不准确；第二种 `map reduce`；第三种 `refine`。

| 方式 | 核心思路 | 适用情况 |
|:-----|:---------|:---------|
| stuff | 提示加整篇文档一次性交给大模型，直接得到最终摘要 | 文本较小，没超过模型的 token 上限 |
| map reduce | 分而治之：切块、逐块摘要、再汇总 | 超长文本，一次性喂不进模型 |
| refine | 与 map reduce 类似，懂了 map reduce 再看它就很容易 | 本讲先点名，后面再展开 |

用得最多的也是前两种。先把难啃的 map reduce 讲透。

#### map reduce：分而治之

map reduce 我要多说一句。我本人从 2013 年开始就专门做大数据开发，学的第一个大数据分析引擎（框架）就是 Hadoop，而 Hadoop 里有一个非常重要的东西就叫 MapReduce——单词跟这里的一模一样。所以了解过 Hadoop 的 MapReduce、或者大数据里其他分布式计算引擎的同学，等会一听就懂；没学过大数据的话，这个地方还有点难理解。

MapReduce 的总体思想就是四个字：分而治之。把很大的一个 document 切成一小块一小块，每一小块分别去做文本摘要，然后再把这些小块得到的摘要汇总起来，汇集成整篇文章的文本摘要。这个过程就叫 map reduce。

那为什么要这么绕？大家跟着我的思路推一遍。做文本摘要，输入数据肯定是一篇很长的文章——短的文章你有必要用 AI 来做摘要吗？不需要。肯定是几万字、几十万字甚至上百万字的那种文本。这篇文章交给大模型，模型是不是就得把整篇都读进来？请问，假设这篇文章有 50 万字，有没有超过 OpenAI 大语言模型能接收的最大 token 数量？这个大家一定能回答——别说 50 万，5 万汉字的一篇文章都超了。token 我们之前讲过，现在几乎所有大模型都按 token 的个数收费。超过了就一定会报错：不管你调哪种大模型、不管你账户里钱再多，它都无法一次性接收那么多的文字内容。

所以只能先把这个 document 切割成很多个小 document。假设 50 万字切成 500 字一片，那就是差不多 5000 个小文档，每一个只包含 500 个汉字。500 个汉字有没有超过最大的 token 限制？肯定没有——大部分情况下，模型能接收的 token 数几乎都在 1024 以上，500 个汉字连标点符号都算上，一般也不会超过 1024，完全满足大语言模型接收数据的 token 限制。

但切完马上出现一个新问题。你有 5000 个这样的小文档，请问其中一个片段做完摘要之后，能不能代表整篇 50 万字文章的摘要？不能，肯定不能。所以解决的办法就是：先把 5000 个小文档一个一个地做摘要，做完之后再汇总。这个大体思路，就叫 map reduce。

```text
整篇超长文档（例如 50 万字）
    │
    │ ① 切割：切成约 5000 个小片段，每片约 500 字
    ▼
片段1、片段2、片段3 …… 片段5000
    │
    │ ② 逐片分别做摘要（map）
    ▼
摘要1、摘要2、摘要3 …… 摘要5000
    │
    │ ③ 汇总（reduce）
    ▼
整篇文章的最终摘要
```

读图：先切割，再逐片摘要，最后把所有片段的摘要汇合成整篇的摘要——单片摘要代表不了整篇，所以"汇总"这一步不能省。

顺带把第三种方式也点了：refine 跟 map reduce 其实差不多，了解了 map reduce 之后再去看 refine，你会发现很容易理解。

#### stuff：小文本一次喂完

那讲了半天 map reduce，stuff 呢？stuff 更简单。文章比较小的情况下，直接一次性交给大模型：

```text
提示（prompt template）＋ 整篇文档（document）
        │
        ▼
     大语言模型
        │
        ▼
最终摘要（final summary）
```

读图：给一个提示模板，再加上输入的 document，一步到位得到最终的摘要——`summary` 就是摘要，`final summary` 就是最后的摘要。stuff 的意思就是：把整篇文章一次性直接给我，配上提示，大模型就能给你最终摘要。

所以你发现没有，stuff 只能处理没有超过大模型指定输入 token 上限的情况。一旦超过了，stuff 就用不了，只能用后面两种：map reduce 和 refine。小文本用 stuff，稍微大一点的文本就不能用它了。

这一讲先把核心概念立住。map reduce 的整个过程，下一讲详详细细地展开讲。

## 用 LangChain 做文本自动摘要：Stuff、MapReduce 与 Refine
> 对应块：BLK18 | 覆盖分集：P54-P56 | 块标题（分集名）：《【补习篇】文本自动摘要Stuff方式》

### 从"一篇长文读不完"说起

这一讲进入案例 11：用 LangChain 来完成文本的自动摘要。这个案例对做学术研究的人、专门做文本处理的人来说是特别爽的。设想一个场景：我拿到一篇文章，想知道它到底讲什么，按老办法只能把全文从头读到尾，看完才知道这篇文章在说什么；可文章特别长，花那么长时间去读太不划算。这时候就可以让大语言模型帮我们自动把整篇文章做一个总结和摘要。

哪怕你手里是一组 Word、PDF、网页，或者一堆客户的问题，只要你想总结这些内容，都可以交给它。大语言模型在理解和综合文本方面非常熟练，是完成这项任务的绝佳工具——而且到现在为止，它做文本总结和摘要已经非常准确，大部分情况下甚至比人来做文本总结和自动摘要还要更准确一些。

动手之前要额外安装两个库：一个叫 tiktoken，一个叫 chromadb。安装命令已经给到大家了，安装过程就不赘述了。

要实现文本的自动摘要，一共有三种方式。先把名字亮出来，再看它们各自的打法。

### 三种方式，先把名字认对

三种方式分别叫 Stuff、MapReduce 和 Refine。这里一定要去读英文原词：Stuff 中文直译叫"填充"，可你看完"填充"两个字根本不知道它要干嘛——中文直接翻译这种情况是不准确的，还是英文单词来得直接。

我们用得最多的是前两种：Stuff 和 MapReduce。第三种 Refine 跟 MapReduce 其实差不多，等你了解了 MapReduce 再去看 Refine，会发现非常容易理解。

MapReduce 这个词值得多说一句。我从 2013 年开始专门做大数据开发，学的第一个大数据分析引擎就是 Hadoop，Hadoop 里有一个非常重要的东西就叫 MapReduce，单词跟这里的一模一样。所以如果你了解过 Hadoop 里的 MapReduce，或者大数据里的其他分布式计算引擎，那你大概已经知道什么叫 MapReduce 了，等下讲起来一下就能听懂；没学过大数据的话，这个地方理解起来会稍微难一点。

MapReduce 的总体思想就是四个字：分而治之。把很大的一篇 document 切成一小块一小块，每一小块分别去做文本摘要，然后再把这些小块得到的摘要进行汇总，由多个小块的摘要汇总出整篇文章的文本摘要——这个过程就叫 MapReduce。

三种方式的路径可以先用一张图立个骨架：

```text
方式一  Stuff       提示模板 + 整篇文章 ──► 大语言模型 ──► 最终摘要
方式二  MapReduce   整篇文章 ──► 切块 ──► 逐块摘要 ──► 分组递归汇总 ──► 最终摘要
方式三  Refine      整篇文章 ──► 切块 ──► 逐块喂入、滚动更新摘要 ──► 最终摘要
```

图里三条路径的差别就在"整篇文章怎么进模型"：一条直接塞，两条切块处理。下面从最简单的 Stuff 说起。

### Stuff：小文本一次性塞进去

Stuff 的做法最简单：文章比较小的情况下，给一个提示模板，再加上我们输入的 document，直接一次性交给大语言模型，直接得到最终的摘要——final summary（summary 就是摘要的意思，final 就是最后的摘要）。

所以 Stuff 的意思就是：把整篇文章一次性直接给我，再给我一个提示模板，大语言模型就能帮你得到最终的摘要。

但你也发现了，它只能处理没有超过大语言模型指定输入 token 上限的文本。超过了，就没办法使用 Stuff。记住这一条就够了：Stuff 只针对小文本，稍微大一点的文本就不能用它，只能用后面两种。

### 大文本的坎：50 万字怎么进模型

那大文本为什么非得用后面两种？我们来算一笔账。做文本摘要，输入数据肯定是一篇很长的文章——短的文章你有必要使用 AI 来做文本摘要吗？不需要。肯定是几万字、几十万字以上，甚至上百万字的那种文本。

请问：假设这篇文章真的是 50 万字，有没有超过你的 OpenAI 大语言模型最大能接收的 token 数量？这个问题的答案我相信你一定能脱口而出——别说 50 万，5 万汉字的一篇文章都超过了。

顺带把 token 这个概念再钉一下：现在几乎所有大语言模型的收费，都是按照 token 的个数来计费的。而一旦超过模型能接收的 token 上限，调用就一定会报错——不管你账户里有多少钱，模型都无法一次性接收那么多的文字内容。

所以办法只有一个：先把这个 document 切割成很多个小的 document。比如 50 万字，按 500 字一片来切，差不多就是 5000 个小文档，每一个只包含 500 个汉字。那 500 个汉字有没有超过最大 token 数量？没有——大部分情况下，模型能接受的最大 token 数量几乎都在 1024 以上，1024 已经算最低的了，500 个汉字一般来说连标点符号算上都不会超过 1024，完全满足大语言模型接收数据的限制。

但是切割会带来一个新问题，你跟着我的思路走：这 5000 个小文档，每一个做完摘要之后，这一篇 500 字小文档的摘要能不能代表整个 50 万字大文章的摘要？肯定不能。所以要解决的办法就是：先把这 5000 个小文档一个一个地做摘要，做完摘要之后我再汇总。这个大体思路，就叫 MapReduce。

> **结论**：大文本进不了模型，就先切块、逐块摘要、再汇总——这正是分而治之。

### MapReduce 的完整流程

map 阶段跑完之后得到的是什么？以我们之前讲的那个案例为例，得到的是 5000 个摘要，从 S1 一直到 S5000。注意，是 5000 个摘要，不是 5000 个文档、5000 个文本——文档在 map 之前就切完了，map 之后得到的是摘要。

```text
整篇文章（比如 50 万字）
  │  ① 切割：每 1000 个 token 一小片，片与片之间不重叠
  ▼
[D1] [D2] [D3] ...... [D5000]
  │  ② map：每个小文档分别做摘要，得到 S1..S5000
  ▼
S1, S2, S3, ...... S5000
  │  ③ combine：按 token 分组（每组累计不超过 4000），
  │     每组交给 StuffDocumentsChain 做一次中间汇总
  ▼
汇总结果整体仍超过 4000 个 token？──是──► 回到第 ③ 步继续分组递归
  │否
  ▼
④ 最后一次 StuffDocumentsChain 汇总（这一次才是真正的 reduce）
  ▼
最终摘要
```

从上往下读：①②③④四步各自干什么都标在箭头旁；唯一的分支判断出现在 combine 之后——整体还超过 4000 个 token 就回去再来一轮，不超过就进最后一次汇总。下面把中间最容易绕晕的两步掰开。

#### 摘要本身也可能超限

这 5000 个摘要，一次性交给大语言模型它同样承受不住，也可能超出模型规定的输入 token 最大数量。那怎么办？把这 5000 个摘要再分成一组一组地传给大语言模型。

怎么分？在 reduce 阶段，我们要按 token 的数量来分，而不是按文档的篇数来分：每 4000 个 token 一组。这个 4000 是我随便规定的，其实你可以自己规定，代码里怎么规定的等下就能看到。

举个例子：一篇摘要能有多少字？可能几十个字，最多也就一百字。假设 S1 到 S2000 这 2000 篇摘要加起来，token 数量才到达 4000 个，那么 S1 到 S2000 就是第一组；假设 S2001 到 S3000 这 1000 篇摘要加起来也刚好 4000 个 token，那它们就是第二组；S3000 后面的可能就是第三组。规则就一条：只要累积的 token 数量没有超过 4000，就归进同一批，也就是把摘要以小于等于 4000 个 token 的批次递归地传递出去。

> **易错点**：reduce 阶段分组要按 token 数量分，不能按摘要的篇数分——"每 1000 篇一组"只是随口一说的例子，真正的分组依据只有 token。

#### combine 到什么时候为止

每一组的 token 都没超过 4000，那这一组单独做摘要的汇总，是不是直接可以用上一节讲的 Stuff 文档链？当然可以——Stuff 文档链本来就是帮我们处理 token 数量不多、不大的那种场景的。

于是整个流程就递归起来了：为什么递归？因为组有很多种嘛。每做一下汇总，token 数量一定会慢慢变小；一直到所有汇总之后的摘要，token 数量小于 4000 了，再把它们一次性全部交给最终的 Stuff 文档链，做最后一次的摘要汇总。

> **结论**：前面一轮一轮的中间汇总都叫 combine，最后一次才是我们所说的 reduce。

### 把整条 MapReduce 链拼出来

思路清楚了，接下来看代码怎么落。map 阶段的提示模板和链上一节已经搭好，reduce 阶段的套路跟它完全一样：把模板换一份，名字从不叫 map 改成叫 reduce，模板变量同样保持一致。reduce 模板的正文大意是：以下是一组总结，请将这些内容提炼成一个最终的统一的总结摘要——到了这一步，手里已经拿到很多个小的 document 摘要，要把它们归拢成一个。

#### combine 链与 ReduceDocumentsChain

先定义一个 combine 链。它本质上是一个 StuffDocumentsChain：

```python
# combine 链：中间汇总链，本质是一个 StuffDocumentsChain
combine_chain = StuffDocumentsChain(
    llm_chain=reduce_chain,          # staff 其实也是一种 reduce，只是叫"中间汇总"
    document_variable_name="docs",   # 参数名字必须与模板变量一字不差，照抄即可
)
```

这里的参数名字是没办法改的，只能是复制粘贴——document_variable_name 指的就是模板里面的那个变量名，map、reduce 各处的变量名我们都保持一致，统一叫 docs。

有了 combine 链，再构建递归汇总的载体 ReduceDocumentsChain：

```python
# reduce 链：内部通过递归不断调用上面的 combine 链
reduce_documents_chain = ReduceDocumentsChain(
    combine_document_chain=combine_chain,  # 中间汇总用的链
    token_max=4000,                        # 将文档分组的最大 token 数，默认 3000
)
```

token_max 就是"将文档进行分组的最大 token 数"，注释里写的 4000 就在这里定义。它的默认值是 3000，我们改成 4000——其实改成 4096 可能更好一些，算了，不管那么多了，就 4000。这个 reduce chain 是一个组合，里面实际上是在不断地通过递归调用 combine 链，也就是那个 StuffDocumentsChain。

#### 合并所有链

接下来把整个 MapReduce 合并成最终的一条链，用的类就叫 MapReduceDocumentsChain：

```python
# 合并所有的链：得到最终的 MapReduce 链
map_reduce_chain = MapReduceDocumentsChain(
    llm_chain=map_chain,                            # map 阶段：每个小文档做摘要
    reduce_documents_chain=reduce_documents_chain,  # reduce 阶段：递归汇总
    document_variable_name="docs",                  # 传给 reduce 的变量名，统一用 docs
    return_intermediate_steps=False,                # 不返回中间的汇总结果
)
```

它要传的参数稍微多一点，一行一行写清楚。第一个是 map 链，就是给每一个小的 document 做汇总摘要的那条链；第二个是我们刚构建的递归汇总链；然后是变量名字，统一用 docs；最后一个参数的意思是：是否把中间的 map 或 combine 步骤的结果——也就是那些还没完全汇总的摘要总结——也返回出来。它默认值就是 false，我本来就不想返回中间结果，这里显式写出来是 false。

#### 补上切割，再调用

还有一步别忘了：切割。其实切割放在最前面做是最合适的，这一步叫切割阶段，把一个大的 document 切成一个个小的。代码之前写过，用 tiktoken 来量 token：

```python
# 切割：每一个小文档 1000 个 token
text_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    chunk_size=1000,   # 每个小文档 1000 个 token
    chunk_overlap=0,   # 片段之间不允许有重复 token
)
split_docs = text_splitter.split_documents(docs)  # 把整篇大文章真正切开
```

chunk_size 和 chunk_overlap 这两个参数之前都讲过：每个小的 document 是 1000 个 token，切的过程中允许重复的 token 数量设为 0，表示每一个 document 之间不会有任何重复。如果对这两个参数不太明白，回过头去看之前的代码，我还在旁边写了注释。到底能切成多少片，要根据你这篇总共的文章一共有多少个 token 为准；当然 from_tiktoken_encoder 只是配置，真正切还要调用 split_documents 这个函数，把完整的大的 document 传进去，切成一个个 1000 个 token 的小文档。

最后拿着最终这条链去调用：

```python
result = map_reduce_chain.invoke(split_docs)  # 把切割完之后的多个 document 传过去
print(result)
```

代码到这里就写完了。运行时间肯定会长一点，我试过大概要一分多钟才能搞定。

### Refine：顺序迭代，滚动更新

MapReduce 的代码写好后确实执行了一下，没有报任何错误，也出现了最终的摘要汇总。第三种方式的背景交代完了，接下来看 Refine。它的定义只有一句话：通过顺序迭代文档来更新滚动摘要。你如果真正读懂了这句话，立马就明白了 Refine 这种方式的主要原理。

#### 一句话读懂 Refine

Refine 类似于映射规约（MapReduce），文档链通过循环遍历输入文档、逐步更新答案来构建响应：对每一个文档，它把当前文档和最新的答案一起传递给大语言模型，以获得最新的答案。

这句话如果你没听懂，我给你举个例子。它首先还是切成一小块一小块的小文档，怎么切上面代码里都有。给每个小文档取名叫 D1、D2……假设最多切到 D5000：先拿着 D1 连同提示交给大语言模型，得到一个摘要 S1；接着把 D2 和 S1 一起交给大语言模型，得到一个新的 S1；再把 D3 和这个新的 S1 交给大语言模型，又得到一个新的摘要；以此类推，再把 D4 和最新摘要一起送进去……当它遍历到最后一个小的 document 的时候，其实就得到了最后的总结摘要。

```text
D1  ──(提示模板)──►  大语言模型  ──►  S1
D2 + S1          ──►  大语言模型  ──►  S1'
D3 + S1'         ──►  大语言模型  ──►  S1''
......
Dn + 最新摘要     ──►  大语言模型  ──►  最终摘要
```

从上往下读一遍就清楚了：Refine 没有分组、没有递归，就是拿着下一个文档不断更新当前摘要，循环遍历，没有其他的。

#### 快不起来，但问题解决了

这种方式你发现没有，速度上一定是没有 MapReduce 快的——一定的。虽然它也解决了我们这个 document 数量超过大语言模型限制的问题，确实解决了，但从性能上讲，我个人觉得它的速度比不上 MapReduce。因为 MapReduce 这种解决方式的思维是比较先进的，它其实来自大数据的分而治之；而 Refine 就是一个循环遍历，不断地更新我们的摘要：每次拿到下一个小的 document，就更新一下当前的摘要，遍历到最后一个，就得到了最终结果。所以大家只要了解一下就好。

#### 最简写法：一个 chain_type 的事

Refine 的代码反而是最省事的。我们在 MapReduce 版本的基础上复制一份，把 map、reduce、combine 那些链的代码全部删掉，只保留切割——第一步还是切割，因为要切成一个个的片段。然后直接讲这种比较简单的写法：只需要设置一下我们的 chain_type：

```python
chain = load_summarize_chain(
    model,
    chain_type="refine",   # 默认值是 stuff，这里换成 refine
)
result = chain.invoke(split_docs)  # 把切割完之后的小文档传过去
```

代码非常简洁：load_summarize_chain 这个函数之前讲过，第一个参数传模型，第二个参数 chain_type 的默认值是 stuff，我们不用 stuff，用 refine。真正干活的就是这一行——指定 chain_type 为 refine，然后把切割完的 split_docs 传进去调用。

这一版没有加提示。如果你要加提示，代码会变得复杂一些：入口还是同一个，只是里面可以加各种提示模板，我提供了一套英文的提示模板，也提供了一套中文的提示模板，两种都可以用。加提示的这版代码大家理解一下就可以了，不是必须的，这里直接复制粘贴、不再展开讲。运行时间也是蛮长的，要耐心等待一下。

### 三种方式放在一起看

三种方式我们都跑过真实结果了，放在一起比一比。MapReduce 那次的汇总明显比第一次用 Stuff 跑出来的内容要多：它还提到了一些相关研究和工具，末尾还有一句"整体而言，这些文档深入讨论了 LLM 在不同领域的应用和发展，以及在处理复杂任务和问题中的潜力和挑战"——后面这句在第一次执行摘要总结的时候是没有的，MapReduce 的摘要总结更加完善。Refine 的汇总也出来了，比第一种方式要长。而 Stuff 那份摘要，我个人觉得是不完整的，因为它肯定超过了 OpenAI 最大的那个 token 数量。

| 方式 | 核心思想 | 能处理多大的文本 | 这一讲的观察 |
| :-- | :-- | :-- | :-- |
| Stuff | 提示模板 + 整篇文本一次性交给模型 | 只能是小文本，超限没法用 | 摘要不完整，文本超出了 token 上限 |
| MapReduce | 分而治之：逐块摘要，再按 token 分组递归汇总 | 大文本没问题 | 结果更完善，多出了相关研究等细节 |
| Refine | 顺序迭代文档，滚动更新摘要 | 大文本没问题 | 代码最简洁，但速度一定比不上 MapReduce |

> **结论**：小文本 Stuff 一步到位；大文本在 MapReduce 和 Refine 里选，要速度就选 MapReduce，它背后是大数据那套分而治之的先进思维。

### 11 个案例的收官交代

到这里，LangChain 的基本知识点就全部讲完了。回顾一下，我们是通过 11 个案例来掌握其中各个细节的，每个案例都包含一个或者多个小的知识点：
