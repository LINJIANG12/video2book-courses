## 从"帮我写个程序"到"帮我修好这个 issue"：构建 coding agent 的训练、工具与评估
> 对应块：BLK06 | 覆盖分集：P06 | 块标题（分集名）：《06｜面向编程与软件开发的 agent【中文配音》

### 这节课其实要从语言模型讲起

在座各位应该很多人、甚至所有人都在用 coding agent，它们底层的功能是什么，我基本不用多讲。我想聊的是另一件事：怎么构建 coding agent，以及构建 coding agent 需要具备哪些必要条件。

不过我刚发现这页幻灯片的标题可能有点名不副实。我首先想讲的，其实是一个"能写代码的语言模型"意味着什么——不是 agent，是语言模型。这两者之间的差距，正好是这一整节课要展开的地方。

先看看一个能写代码的语言模型能干什么。最显而易见的一种：用英文说"我要你写一个程序，把这份数据可视化"，你在 prompt 里给它一个 CSV 文件，它就为这份数据生成柱状图。估计很多人经常做这类事，在 ChatGPT 或者某个 coding agent 里写。

但还有很多涉及生成代码的任务，不是这种一次一个 prompt 就能了事的。你可以让它修改整个仓库、修改多个文件——这就更像是在这个仓库里修复某个问题、或者做某个改进。

最后，开发软件不只是写代码、修问题、加功能，还涉及很多其他事情，这部分我也想讲讲。

> **提示**：一个能写代码的语言模型，一次 prompt 一段代码；而 coding agent 要面对的是"在真实仓库里改多个文件，并把改动验证到能过测试"。

和其他所有 agent 一样，这三件事一个都不能少：写 prompt、给 agent 提供工具、还得有个能真正解决这类任务的好 LLM。这节课我主要聚焦第二和第三部分，因为前两节课我们讲了技能、记忆，以及怎么处理长上下文；prompting 方面很多内容上一节课已经讲过。

所以第一个要素，就是一个具备写代码能力的大语言模型。

### 写代码这件事，模型得会三样

这里的例子就是写代码。根据 prompt 写代码，你基本上得覆盖几件事。先说明一下：这里说的是**单步**、不是 agentic 的代码编写，是单步语言模型。要在单步内具备写代码的能力，你得：

- **理解你要用的编程语言**；
- **会编辑**——因为我们通常不会写一次代码就扔掉，虽然偶尔也会。我们通常是迭代改进的，而这不是语言模型天生就会的，你得把它训练进模型里；
- **会推理**。

编程一直是推理模型比较成功的应用之一。理由和数学——推理模型另一个成功的应用——一样：你可以比较容易地验证你做得好不好。

如今每个语言模型都是 coding 模型，不存在不会写代码的语言模型。原因是编程是语言模型最有价值、使用最广的用例之一。但这显然不是白来的。

那训练一个擅长生成代码的模型需要做哪些事情？在进入正题之前，我先问问大家：先不谈 agentic 任务，你们觉得可能需要做些什么？

大家给出的答案非常完整，我总结一下：

- 要确保你的**分词器**里包含代码中会出现的那些 token——代码里有些 token，非代码模型未必需要；
- 需要**大量编程数据**来训练；数据从哪来？GitHub。
- 编程有**专门的工具**，比如 grep 和操作系统工具。这一点非常重要，更偏向 agentic 侧，但在单步场景下也肯定得懂这些工具——比如你要写 bash 脚本的话。

这些全都对。而在此之上还有一层：预训练阶段你要在一个大规模语料上做预训练，**这个语料要包含代码，但不能只有代码**，因为模型还得理解英文，或者你提问时用的其他语言；分词也一定要做对，这我待会儿会讲。

后面还有两步：中期训练（持续预训练、监督微调我放在一起讲，它们差不多是一回事），这一步要在**代码混合数据**上训练；以及**强化学习后训练**。这几轮的具体机制我们后面都会详细讲，所以这节课我聚焦编码相关的细节，SFT 和 RL 后训练的整体流程留到以后。

| 阶段 | 做什么 | 编码相关的关键点 |
| --- | --- | --- |
| 预训练 | 在大规模语料上优化下一个 token 的预测 | 语料含代码但不能只有代码；分词器必须覆盖代码 token；grep、操作系统工具这类编程工具也要懂 |
| 中期训练（含持续预训练、监督微调） | 在代码混合数据上继续训练 | 提高代码曝光量的同时保住通用能力；处理超长上下文；学会中间填充 |
| 强化学习后训练 | 拿测试结果当奖励 | 具体机制后面课再展开 |

### 预训练：先把代码语料挑干净

预训练本质上就是从代码和文本里学习，这个阶段通常就是在优化下一个 token 的预测。

训练编程模型时，和只回答问题的模型不同，你除了要混入网页文本——每个模型都从网页文本学习——还要混入技术性文章（比如解释代码怎么工作的文章），还有数学内容（这些能提升逻辑推理能力），以及源代码、文档，来源非常多。

> **易错点**：这里有个坑我得提醒一下。大家可能在我之前那届学生入行之前，有一段时间我们会做**空白符归一化**——把所有空格压缩成一个空格，诸如此类。写 Python 就很糟，对吧？因为空白符是有含义的。所以这类问题要小心，文件边界也要小心，还要考虑怎么表达文件边界。另外你得能处理 API，并且保留文本和代码之间的关系——比如文本里有 Markdown 块，要确保它仍然留在该块里。

当然训练过程中你还要做评估，通常就是看 loss 有没有降下来。编码任务也一样，但你要把评估设计好，让它覆盖你想覆盖的那些方面。

这里有个很要紧的判断：训练文本模型时，选数据和清洗数据就已经很难了；训练编程模型**更难**，因为代码的分布非常非常独特。

#### 过滤：语言、来源、许可证与敏感数据

第一件事是按语言和来源做过滤。网上有大量完全自动生成的代码，从训练的角度看这些代码没什么价值，可以去掉；还有编码错误的、低价值的重复代码。

> **定义**：低价值重复代码的一个典型样本是 **fork**。你去 GitHub 上看，同一个仓库的 fork 有几千到几万，甚至几十万个。如果直接下载拿来用，就会遇到很多麻烦。

顺便提一下，我下面这些内容很多来自一篇叫 **StarCoder** 的论文，它是最早研究预训练代码模型的论文之一。如果你对这些细节感兴趣，可以仔细看看那篇论文。我记得 Daniel 参与了这项工作，更多细节可以问他。

另一件有意思的事，是有人会考虑、有人不会考虑的：记录**许可证、来源日期和退出选项**，还有**敏感数据过滤**。

举个数许可证的例子：如果你用专有许可证的代码训练，然后发布了模型，靠这个模型赚了 10 亿美元；两年后，持有那份专有许可证的人会找上门说"嘿，你用我的代码训练了，得赔我 1 亿美元，因为我的代码为你的模型做了贡献"。你可能不想这样，也可能不在乎，但你得做决定。其实美国版权法对要不要在乎这件事也有点含糊。

**来源日期**的逻辑更简单：不想要老代码，就只要新代码。还可以允许人们选择退出。

**敏感数据**方面，大家会上传各种不该上传的东西，比如 API key。咱们班没人会这么干，对吧？请不要把 API key 推到仓库里——但确实有人这么干。有一些工具可以帮你做敏感数据过滤，比如我和 Hugging Face 用的 **TruffleHog**，基本能识别所有 API key。

最后，如果你想构建训练集或测试集，那你就得去构建训练集或测试集。但这也很困难，因为有 fork 和其他各种问题。

#### 分词器：给代码单独造一套

接下来讲 token。随着代码越来越重要，这块也得跟着演进。这里我写的是**对代码和普通文本都做字节级 BPE**；不过 BPE 本质上就是任意一種子词分词方法，大多数人都熟悉它，你也可以换成任何你想要的分词方法。

需要小心的一点是**保留空白符**。

还有把**高频出现的内容压缩起来**。在大家大量处理代码之前，空白符可能就是一个 token——也就是说，如果你要生成缩进 16 格的 Python 代码，就得输出 16 个空格之类的东西。所以通常的做法是把它压缩成一个 token，比如"三个空格加一个换行"合成一个。从这里开始，你就得专门针对代码来设计分词了。

另一件可做可不做的事，是把代码规范化，让它更标准一些，但这不是必须的。

还有一点需要考虑：你想处理哪些语言。比如 StarCoder 的做法是建模很多语言，不是全部，但涵盖了很多非常流行的语言。自然，训练数据多的那些语言，在特定任务上表现就更好。另外你还要考虑用户会想用哪些语言、哪些语言写起来更容易、或者你的 agent 框架支持哪些语言。

#### 模型的"语言偏科"

举几个例子。如果你让模型做一件事，不指定语言，它会用哪种语言？你有没有说过"帮我写个应用"，它会用哪种语言？

对，主要是 Python，我觉得主要还是 Python。但也有相反的情况：你要仪表盘，它就用 React；其他几乎任何东西，它都用 Python。

当然你也可以指定别的语言。我有一个很重的数据处理流水线，最初是用 Python 写的，我让模型把它转成 Rust 来提速，模型也照做了。但之后每次它运行另一个程序又用 Python 来跑，所以我每次都得说"用 Rust，用 Rust"，它才照做。

所以它们有很强的偏好。这种偏好我觉得有两个原因：一是语言好写，Python 比较简洁一些；二是流行度；还有第三点不太显眼，但同样重要——**下游的 RL 训练用了什么**。模型很可能是用 Python 解释器做 RL 训练的，所以更偏向这门语言。

> **提示**：既然偏好这么强，与其指望模型自己选对，不如在每一轮对话里显式指定语言。

关于预训练还有什么问题吗？有同学问：**有没有情况你会想修改 tokenizer，比如把"空格加换行"单独作为一个 token？** 这样模型内部更不容易区分语言 token 和代码 token，尽管它们本质相同。

这是个好问题。例子里的"换行加三个空格"确实有这种情况。但更有意思的一点是：**其实你不需要把空白符和其他 token 区别对待**，字节级编码本来就是用来合并字节的。不过实际上，几乎所有情况下人们还是会区别对待空白符。原因是比如模型表现稍差时，输出半个词会显得很奇怪，所以他们想引导模型不要输出半截的词或词元。通常他们会把空白符和非空白符分开来分词。

但也还有别的情况。如果允许**跨空白符合并 token**，能得到更高效的表示，尤其对代码。在 encoder 那篇论文里我们就这么做了，token 能少 40% 左右。但它也会以奇怪的方式出问题——就像 Graham 说的那样。比如 `import numpy as np` 变成了一个 token，结果模型停在 `import numpy as` 就补不全了，你得退回来做类似约束解码的处理。而且改动一个分词要非常小心，因为规模一大就可能出问题。

所以这里总结两个要点：**允许分词时不管有没有空白符**，你能得到高效得多的分词，但它也会以奇怪的方式出问题——代码模型里 `import numpy as np` 就是一个 token，做自动补全之类就会很麻烦，因为它太长了。怎么做得聪明点很关键，有几篇论文我们可以分享。

### 中期训练：把通用模型改造成代码模型

接下来讲中期训练。我这里有几个例子，一个来自 **Code Llama**，另一个来自 **Qwen-Coder**。这些公开论文讲了他们如何把预训练好的非代码模型改造成代码模型——这能很好地展示非代码模型和代码模型的区别。

第一件事是**提高代码的曝光量**。如果原本的数据集比较杂，就可以加大代码的占比；你还可以根据实验来选配比，既提升代码能力，又保住通用能力。比如 Code Llama，他们拿 Llama 2 又额外训练了 5000 亿个 token。

**上下文拓展**在这里也很重要。这是 Qwen2.5-Coder 的一个实验结果：他们说"这是代码模型，我们要把代码能力做到很强"，所以就只用 100% 的代码，后续也全用代码来训练。但问题是它在数学等其他重要任务上分数很差，比如数学或问答。但如果继续训练时不全用代码，而是混入文本和数学，代码性能只小幅下降，其他能力却能保住。

> **结论**：既可行又重要，因为现在没人只用模型来写代码。

另一件事是**长上下文处理**，这个我之前课上讲过不少了，这里再稍微展开一点细节。本质上你要构造出连贯的序列来训练模型。

构造数据有个很天真的做法，对代码模型来说，就是把整个仓库拿来，把所有文件直接拼在一起。但全部拼在一起，往往连最长上下文的模型都装不下——毕竟训练通常最多也就到 100 万 token。很多代码库，大多数正经的都超过 100 万 token。比如 Google 的 monorepo，据说有几十亿行代码，对吧？这根本不在同一个数量级上。

但你还是希望模型能连贯地理解文件。你可以只把一个目录下的内容都拿来，也可以解析依赖图，顺着依赖关系把相互依赖的文件拼在一起，诸如此类。

举个例子，Qwen2.5-Coder 先在 8k 上训练，再用 **YaRN** 拓展到 128k——几节课前我讲过 YaRN，这一点也很重要。这类上下文操作就能帮你做到。它可以配合**跨文件补全、infilling 中间填充**，以及**短上下文保持**来验证，这些稍后细讲。

### 中间填充：把双向填空改写成自回归

infilling 中间填充这一块，其实该让 Daniel 来讲，他是专家，这主要是他的论文。不过还是讲讲，大家可以问他。他有一篇叫 **InCoder** 的论文，是最早一批用 infilling 中间填充目标训练强代码模型的论文——让模型不只做代码补全，还能预测代码的**中间部分**。

举个例子：有个函数叫 `is_positive`，我们想预测它的返回类型，这就是一个典型场景。

问题在于，普通自回归模型只看左边的函数体，你根本猜不出来，对吧？`is_positive` 本身没什么信息；也许能从名字猜出是布尔，但也可能是字符串、枚举什么的。**但要是看到右边这部分，就能确定返回类型了。**

那怎么做呢？答案出人意料，而且简单得出奇——**把 infilling 中间填充任务转化成自回归任务就行了**。

```text
  一个空洞：
    原序列   prefix   [ 空洞 ]   suffix
    训练     prefix    M0     suffix    M0    content
                                               ↑ 模型只在末尾预测 content，
                                                 不在原位预测那些被替换掉的 mask
    推理     prefix    M0     suffix    M0   ──模型生成──▶  content

  多个空洞（推广到任意数量）：
    训练     prefix  M0  mid1  suffix  M1  mid2  ...  M0  M1  content1  content2
                                     先生成 M0 对应的内容，再生成 M1 对应的内容
```

也就是说，你有前缀、有后缀，然后填充中间这一段；`M0` 是你放在前缀和后缀之间的那个标记，紧跟着的 `M0` 才是真正要预测内容的起点。推理时你就在前缀和后缀之间放一个 `M0`，再放一个 `M0`，模型就会生成要填的那段。如果有多个空洞，就用 `M0` 和 `M1`，先生成 `M0` 的内容，再生成 `M1` 的内容——这是做任何 infilling 中间填充任务的通用方法。

从软件工程角度看，这能干很多有用的事：在**大文件中间补全代码**、**推断类型**（就像刚才的返回类型）、**注释生成**、**变量重命名**——全都是 infilling 中间填充任务。这是 InCoder 论文里的一些实验结果：他们在单行、多行等若干任务上做从左到右推理，成绩大概是 48 对 24 和 25。如果用从左到右生成 10 个候选、再用整个文件的上下文重排，效果会好一些，但仍然不够，远比不上专门训练模型做这件事的提升。而且这完全不需要重排，用的就是基于中间填充的推理。

而且可以证明，加入中间填充训练后，**标准的代码补全能力仍然能保持**：如果加上因果掩码，也就是把从左到右的部分遮住，性能依然能保持。所以这两者其实并不构成取舍。

有同学问了一个关键问题——**span 是怎么采样的？** 答案是：按一个**长尾分布**随机抽取若干个 span。大多数时候就只抽一个，抽两个的少一些，抽三个的次数更少，输出长度也是类似的处理；最多可以抽到 100 个，但概率非常小。对每个 span 采样对应内容，这些都是连续 token，然后把这些内容**移到末尾**，用 mask token 替换原来的部分——模型不在原位预测这些 mask，而是在末尾预测它们。

> **提示**：如果你愿意，还可以参照现实中真实出现的填充来设计这个分布。

### 除了代码本身，还能从哪儿学

从代码中学习其实可以有很多有创意的做法，来源有很多种。

**第一种是 commit diff**。如果你有改动之前的文件，再加上 pull request 之类的说明信息，就能生成 diff，也就是改动后的结果——这样就能训练出很好的**代码编辑模型**。

**第二个思路是从诊断信息中学习**：拿有问题的代码加报错信息去生成修复。哪里能几乎免费地拿到大量这类数据？Stack Overflow 是个好来源，不过不是我想的那个。GitHub issue？可能更接近一点。GitHub pull request 也不错。

不过再想想——如果你是开发者，你在哪里会看到代码出错？是在 GitHub 之类的地方吗？

**对，是测试。** 我特别想讲的是**持续集成测试**，也就是你往仓库 push 时会跑的那些测试。这些历史都记录在 GitHub 上，而且是公开的：你可以看到某个版本的代码跑挂了、报了错之后，某个版本最终通过并被合并进来。这是非常丰富的一类测试数据，而且**不用你自己去生成，因为自己生成会很痛苦**。当然，你也可以跑一个 agent 来生成这类数据——这个我后面会讲。

**另一个是执行轨迹**，这个还挺有意思的，有点小众但很酷。你可以在测试时给程序插桩，再运行，观察它实际是怎么执行的。比如你可以让语言模型生成"程序执行到某个时刻的调用栈"之类的东西，或者生成程序执行到某处的输出。讲到后面我会简单讲讲**代码世界模型**，它就依赖这类方法。

### 怎么判断写出来的代码好不好

评估有几种范式，其中最直观的一种，我们大概在 2017 年的一篇论文里用过，就是**和参考解做对比**：你有一份人工写的代码，拿它来比较——不是比运行结果，而是直接问机器生成的代码和人工写的像不像。

#### 和参考解比：BLEU 与它的接班人们

很久以前有个很出名的指标叫 **BLEU**，衡量的是输出代码的 token 和 n-gram 重叠程度（还有人真的在用它吗？——没想到还有这么多人知道它）。

它能找出表面上相似的代码，但有局限：

- 大于等于号只差一个 token，程序行为上却差别非常大；
- 反过来，有些写法不同的表达式，从 token 重叠看差别很大，但实际上是等价的。

针对这个问题已经有几种解决思路。其中一种是 **CodeBLEU**：它不比较 token 层面的表面相似度，而是比较**抽象语法树**——程序有个特点，每个程序都能转成一棵树，这棵树规定了程序按编程语言的逻辑如何执行。CodeBLEU 基于语法树来比较，还比较了**语法数据流匹配**和**语义数据流匹配**，也就是看哪些变量来自哪些地方。

另一种比较代码相似度的方法是基于**嵌入**的：这是我们在 2023 年做的一个东西，叫 **CodeBERTScore**。基本思路是你拿一段代码——这是代码的一个例子，这是另一个例子——对代码里的每个 token 做嵌入，然后检查每个 token 在另一段代码里是否都有一个对应得上的 token。这样你就能看出这段代码是不是基本上都在另一个实现里有所体现。这些例子效果都不错。至于这个场景的取舍，几页之后我会专门讲。

#### 让代码真的跑起来

我们换到另一种范式吧，这是如今更主流的做法：**真的把它跑起来**。你有一个候选输出，再准备一批测试用例，拿候选输出去跑这些测试用例——如果全部通过就得一分，如果没有全部通过就得零分。

这两类方法各有优劣。先看基于执行的评估：

它的**好处**是能接受不同的正确实现，模型写出功能等价但长相不同的代码不会被冤枉。

它的**缺点**是要写出真正好的单元测试非常难。你能找到的每个知名基准，背后都有一篇论文在抱怨单元测试有多差：

- 要么有**假阳性**——测试不够严格，放过了错误的实现；
- 要么有**假阴性**——给 agent 的输入信息不足以让它通过所有单元测试。

举个例子：需求可能只写着"我要在界面右上角放一个好看的按钮，上面写着 Learn More"之类。这听起来挺好，但测试可能还会检查按钮的背景颜色什么的——因为这个要求在测试一开始并不明显，是后来才显现出来的。

> **结论**：这就是现在训练 coding agent 最大的难题之一。因为任务越来越难了，要造出既低假阳性又低假阴性的测试非常困难。

不过，通过执行来**发现语义错误**效果确实很好——但这需要好的测试，还需要在隔离环境里把依赖装好。如果你要跑测试，只用 Python 标准库那很简单，否则就得提前装好所有依赖，常见做法是用一个 **Docker 容器**把依赖都装进去。但你可能以为依赖都装好了，却没考虑到**版本问题**：版本一升级，测试就跟不上了，结果你只是因为测试过时，就给新模型打了更低的分。这是我们得处理的另一个问题。

最后一点，你需要一个**长期稳定的执行环境**。对一个很大的代码库跑测试可能非常耗时；我们接触的很多基准里，包括待会儿要讲的 SWE-bench，都想办法解决了这个问题，但这确实是个难点。

#### 单步代码生成的基准

简单介绍几个流行基准。**HumanEval** 算是经典的标准基准，不过它已经过时了，因为每个语言模型都能拿高分。它是最简单的一类：给一个带 docstring 的 Python 函数，你要生成补全，背后有隐藏的单元测试。这个基准其实是 OpenAI 的人手工造出来的——他们设计了一批挺有技巧性的 Python 函数让人去实现，所以它不一定能反映真实世界的使用情况。

稍难一点的是 **CodeContests**，这有点像 Codeforces 的风格，更偏竞赛编程。还有很多其他评测基准，难度从简单到复杂不等。

有意思的是，我觉得没多少人能第一次尝试就毫无差错、百分之百正确地解出一道 Codeforces 的题——但这恰恰是我们要求单步语言模型做到的事。所以这其实是相当难的任务，需要大量的推理。

这里有一个例子，我给大家看看 2021 年提出 HumanEval 的那篇论文。各位如果知道现在的 Codex 是什么，听到这个也叫 Codex 可能会很困惑——但这篇是 2021 年为 GitHub 实现的最早的代码补全模型。做的事情就是评估模型能通过多少：可以看到模型越大，通过的就越多。

这里有两个指标：

- **pass@1**：只生成一个输出，看它能不能通过；
- **pass@k**：生成 5 个输出，其中有没有一个是正确的。这是个稍微宽容一点的指标，也可以用来评估。

### 拿测试当奖励：单步代码模型的强化学习

对单步代码生成模型来说，一种典型的训练方法就是**用测试结果做强化学习**。从 RL 任务的角度看这很直接：采样一些回答，跑一遍测试，然后更新模型。这没什么特别出人意料的地方。

但很重要的一点是，这让你能进行训练**大型推理模型**。一步到位解出 Codeforces 的题相当难，这要求模型对回答进行非常仔细的思考，而推理模型在这方面非常有有帮助，所以这是可以做到的。

关于效率有一个线索：做 Codeforces 之类题时，很多竞赛编程任务会给你一个**执行超时限制**，一旦超过执行时限，这道题基本就拿不到分了。效率这条线索就从这里进来。

而且可以证明，在中期训练之后做这种强化学习能进一步提升结果。这只是论文 **DeepSeek-Coder** 里的一个例子，你们可以查：他们先在 16K 上下文训练了一段时间，又在 32K 上下文训练了更久，最后报告的是 64K 上下文的结果。

有同学问了一个我很喜欢的两个问题。

**第一个：代码的效率或复杂度，是怎么纳入训练的？** 答案是——对非 agent 任务来说，基本没有纳入训练。他们基本不考虑代码跑得快还是慢，主要只看代码对不对。不过也有几个例外，例外之一是论文 **NoFunEval**：这里的意思是，你不仅要评估**功能需求**（程序能不能正确完成它该做的事），还要评估**运行时效率**这类指标，比如延迟、资源占用，还有基于静态检查的**可维护性和安全性**。所以也有工作在评估这些方面。对 agent 任务来说，考虑效率就更常见了，我稍后会讲到。

**第二个问题也很好：代码里包含的那些注释，为什么会是这个样子？为什么明明解题用不着，代码里还是会有注释？**

这里我只能给些猜测，因为我不完全确定我最常用的那些模型——GPT 和 Claude——到底在做什么，所以我想回头再多读一点相关资料。不过我的猜测是两点：第一，模型是在现有代码上训练的，代码里有注释，所以他们也会补注释；第二，他们被训练做推理，我觉得可能有个**隐性激励**：多写注释能多换一些 token，这样在生成代码的同时还能想想下一步做什么。

> **易错点**：这是关于当前主流模型行为的一个公开的、大家都会观察到的现象，多解释为推理训练带来的隐性 token 激励，没有任何一条可靠的一手依据，所以只能当猜测看待，别当成结论去引用。

我可以肯定的是，现在（半年前可能还不是），他们已经引入了某种**非功能分类器或代码质量模型**，它会要求写注释、注释数量要合适，不能太多也不能太少。因为以前大家对编码模型的一大抱怨就是：它们会生成海量没人看的注释，啰唆得要命。我记得最新版 Codex 发布的时候，他们强调的一点就是不会给你塞一堆注释垃圾，会写得简洁。

**还有同学问：有没有专门针对代码质量的训练方法，让代码更易读？** 我觉得最直接的做法就是搞一个评判代码质量的模型，在强化学习时加进奖励里。具体细节我不清楚，但我想大家做后训练的时候，往往会把**可读性作为一项单独收集的指标**，拿它当评判标准。给后排再重复一下：做后训练时通常有个类似 **RLHF** 的步骤，训练一个**奖励模型**来预测输出有多好，可读性就是可以从人类标注员那里收集的指标之一，然后它会通过奖励模型间接得到提升。

### Agentic coding：定位、编辑、验证

接下来一定要讲讲 agentic coding。单步编码和 agentic coding 最大的区别在于：现在我们和所有 agent 一样，要做**迭代式的工具调用**。

#### 一个跑圈的循环

我们先讲最常见的场景：在 GitHub 仓库或代码仓库里修 bug，或者实现新功能。做这类事情通常有三个步骤：

```text
     ┌────────┐     ┌────────┐     ┌────────┐
     │ 1.定位 │────▶│ 2.编辑 │────▶│ 3.验证 │────▶ 结束
     └───┬────┘     └────────┘     └───┬────┘
         │                             │
         └────────── 失败信息 ─────────┘

  定位：复现行为，找到需要修改的地方
  编辑：只做必要的改动（如只在值为 None 时设默认值）
  验证：跑测试，失败就把失败信息喂回去
```

**定位**本质上就是找到需要修改的地方。**编辑**就是改动那个需要修改的地方，比如只在值为 `None` 的时候设置默认值。**验证**就是检查你是不是真的做好了。通常这一整套会放在一个循环里，如果发现验证没通过，你就回头迭代，直到全部通过为止。

这就是那个贯穿的例子。假如你的任务是：找到那个地方，`retries` 在值为 0 时没有正确地设默认值。你会先**定位**到实现代码并复现这个行为；然后**编辑**，进去改代码；然后**验证**，跑全部测试。如果测试失败，就用失败信息来指导你下一步怎么做。

这就是 agentic coding——你基本上就是把它放进一个循环里，用我马上要讲的那些工具。

我想指出一点：还有一种**替代方法，不用任何迭代式 agentic 流程**也能做仓库级编码。有一篇论文叫 **Agentless**，作者是 Steven Xiao，我们这里新来的助理教授。他们做的事情基本上不是让 agent 自由调用工具来做定位，而是**把定位拆成一个独立步骤**：先预测需要改哪些文件，再预测需要改哪些类和函数，然后具体挑出需要改的行，接着只用一个单步语言模型生成补丁。

有一段时间它效果出奇的好，挺让人郁闷的——因为那时我正在做 coding agent，我们发现**不少语言模型用这种流程跑得比 coding agent 还好**。原因在于，当时的语言模型被重度训练成擅长单步代码修复，却没有被重度训练成擅长 agentic 工具调用和验证循环。总之这是解决仓库级代码生成的另一种办法，但现在大家基本都用 agent 了。

#### 只有一个工具：bash

怎么把 agent 用在这上面呢？一个答案是**只给 agent 一个工具**——运行 bash 命令的能力。这就呼应了前面说的"会用 bash 命令非常重要"。

**mini-SWE-agent** 是 SWE-bench 的那批人做出来的，本质上就是一个只用 bash 命令来解决问题的 agent。这样就能定位问题了。具体做法是：

- 定位：用 `grep`、`ripgrep` 这种表达力更强的 grep，还有 `cat`、`find` 这些工具；
- 编辑文件：用 `sed`，或者跑个一次性的 Python 脚本，可以用 `patch`；
- 跑检查：用 `pytest` 或构建命令就行了。

所以至少在理论上，要实现一个 coding agent，需要的就这么多。

谁能说说这样作为什么可能不太理想？

答案是像 **gdb** 这样的工具就那么几个。另外还有些别的工具——比如 gdb 这类工具，其实你用 bash 命令就能直接跑，对吧？我不是说你只能给 agent 提供这些工具，我是说你只给 agent 一个工具，就是 bash。

这个观点很好。再强调一遍刚才的意思：大部分工具调用都会是这些，如果大部分工具调用都属于这类，把它们封装成一个**更高效的工具**，agent 就能干得不错。

我举个例子：假如我想编辑文件，agent 每次都得琢磨用 sed、Python 还是 patch。但如果你专门做一个**为 agent 打磨的标准文件编辑工具**，让它用起来效果好，那 agent 基本就会依赖这个工具，改文件也就改得更准了。

#### 文件编辑工具的格式之争

用 sed 跑起来就是这个样子，这样就能把相关的行都匹配上，诸如此类。可要是你要替换的东西里有一堆**反斜杠**之类的呢？那你就得一直写反斜杠，数量还必须完全正确。所以有不少原因让 bash 未必是处理文件这类工作的最佳接口。

所以大多数、甚至所有主流 coding agent 最大的改动，就是**至少再加一个文件编辑工具**。你可以整个文件重写，也可以在文件内做查找替换；通常这些操作都通过一个工具完成，它用固定的格式来执行。

其中一种被研究过的方式是 **Unified diff 统一差异格式**，基本上它的样子就是行号加需要做的修改。但问题是：让 agent 去对行号，它经常搞错，补丁就打不上。

所以更常见的做法是这样的——你给的东西**看起来很像一个 diff，但它不是纯粹的 diff，也不指定行号**。这大概是最常见的做法，很多 coding agent 都在用。

有人能想到用右边而不是左边的坏处吗？觉得它会在哪里出问题？

> **对，没错**：如果文件里有多处 `retries = 3`，就匹配不上，也没法确定该改哪一个。这时 coding agent 得多写几行，直到没歧义。

右边做法的好处远大于这个缺点，所以几乎所有 coding agent 都用它。**diff 格式影响很大，文件编辑工具的格式同样影响很大。**

这是有个叫 **Aider 代码编辑基准**的例子，它评估了当时的模型 GPT-4 Turbo，比较查找替换和 unified diff 两种方式。结论是 GPT-4 Turbo 更适合 unified diff——训练的时候见得多。现在这个问题没那么突出了，但依然存在：就在最近之前，**Gemini 在不少 harness 上表现很差**，因为它训练用的是自己那套编辑格式，跟别人都不一样，所以效果不好。我想他们过去几个月修好了，但这可能是个非常非常大的瓶颈；处理不好，agent 就跑不好。

#### 找到相关代码

下一件事是**找到相关代码**，先从搜索你手头的信息开始。`ripgrep` 是最常用的工具，也可以用 `grep` 或专门的代码搜索工具。接着顺着**引用追踪**下去，agent 就去修复问题。

关于代码定位，人们也研究过一些更复杂的方法。举个例子，有一篇论文叫 **LocAgent**，它给 agent 提供了一个特殊的工具，这个工具能让它沿着**依赖路径**追踪。比如你找到了 issue，找到了 `config.py`，就能接着往下追——找到 `config.py` 之后，你想的话就能用这个工具自动跳到其他相关文件。

这挺有意思。不过根据我的经验，**这类方法很难做得比简单方法更好**，后面我会举一些实际例子。

### SWE-bench：这场考试是怎么出的

评估 coding agent 的基准就是 **SWE-bench**，很多人应该听说过它，在座的多数人都听说过吧？不过我猜不是所有人都听说过这个基准的**构建方式**。

大致是这样的：它从 GitHub issue 构建——取一个 issue，就是问题本身；再取 issue 被解决时的代码库状态，也就是 **pull request 之前的状态**；他们还会找出与这个 issue 相关的测试。这些测试因为它们是和这个 issue 一起引入的，所以它们测的应该就是 issue 里要修复的功能。

在此之上，让一个 agent 生成补丁，然后应用这个补丁，跑测试，得出结果：如果所有相关测试都通过，得分就是 1；只要没全通过，得分就是 0。

这里有一个术语要澄清：**harness**（测试 harness）指的是单纯跑测试，跟 agent harness 不是一个意思。但有一点要提：在这些 GitHub 仓库跑完整测试套件代价很高，比如有些是 Django、NumPy 这类项目，每评估一个样例，跑测试就要 5 到 10 分钟甚至更久。所以他们挑出了一个更小的测试子集，只要这些通过就认为 issue 被解决了。这些测试分两类：

| 测试集合 | 含义 | 作用 |
| --- | --- | --- |
| FAIL_TO_PASS | PR 之前失败、PR 之后通过 | 测的正是 PR 里实现的功能 |
| PASS_TO_PASS | PR 之前就通过，之后也必须通过 | 确认你没有破坏任何东西、没有引入回归 |

要构建**可运行的基准任务**（这个在评估基准的作业里你们还会深入做），基本上需要这样一个结构：

```text
  ┌──────────────┐
  │  起始状态    │  那些需要被修改的文件（PR 合并前的代码库状态）
  ├──────────────┤
  │  依赖        │  装得上、跑得起来的环境
  ├──────────────┤
  │  测试命令    │  怎么把测试跑起来
  ├──────────────┤
  │  issue       │  要求实现的行为
  ├──────────────┤
  │  检查项      │  那些测试
  └──────────────┘
```

#### 把考卷变成训练集

现在做 agent 有个好消息：**评估其实是进行 agent 最大的难题之一**。因为只要你能把它做好，生成大量评估，你就能在这些评估基准上做强化学习，把 agent 训练好。只要你能批量生成大量这样的输出，就真的可以训练出一个模型——具体做法就是让模型生成输出，然后根据它做得好不好来计算奖励。

我们最早做这件事的论文之一叫 **SWE-gym**。SWE-bench 的问题在于，它只是一个评估数据集，或者说他们只给评估数据集配好了环境。在 SWE-gym 里，我们额外搭建了**训练环境**并在上面对模型做了训练。结果表明：**一个原本很弱、准确率只有约 11% 的模型，哪怕只用 500 个样例，也能提升到相当不错的水平**，好得多。这个我先不多讲，后面的课会专门讨论。我们还证明了，如果**生成大量输出再重新排序**，就能做推理时扩展，效果更好。

这方面最大的一个项目——我刚发现幻灯片里没放它，但值得了解——叫 **SWE-rebench**。它在持续不断地创建更多 SWE-bench 环境：它们是用 PR 创建出来的，时间范围是 2024 年 12 月到 2026 年 6 月 30 日。我最近刚和作者聊过，他们大概**每 10 个月会更新一次**。它就是不断产出更多这样的环境，还分成训练集和开发集。这大概是 SWE-bench 格式下大规模公开可用的 coding agent 数据里最好的例子。

#### 不靠 PR 的合成数据

不过创建这类数据还有一些更轻量的方法。上面那种做法的问题是：你造的每个训练样本都需要对应一个**单独的 pull request**。

这里有个来自 **SWE-Smith** 的例子，它不依赖 pull request，而是靠**人为注入的 bug**：先准备一个能跑通的基线，然后改动代码，但保留测试。

那么，有多少人听说过**变异测试**？没几个人——好，这其实是软件工程实践里一个很有意思的想法。

> **定义**：变异测试的想法是：如果你不确定自己的测试好不好——比如你有单元测试，但不确定套件够不够全面——就对代码做些**本意让它出错的小改动**，再看测试过不过。如果测试还是通过，那这些测试就算不好，它们没覆盖到真正的破坏，你应该扩充测试套件。

SWE-Smith 这项工作就是受这个想法启发的，但不完全一样：区别在于，他们是**改动仓库里的代码，然后去找之后会失败的测试**。这样做本质上能让你造出合成的带 bug 数据，只用现有的测试和代码库就能拿来训练模型。

来看个例子。假如你有一段代码，现有的四个测试全部通过，然后你进去把代码改一改：

```python
# 改之前
if value is None:
    ...

# 改之后
return ... if not value
```

这时可能就有一个测试挂了。所以这是个好例子——你基本上能构造出这样的情形，得到一条"请修复这个问题"的任务。

好在哪里？这样做非常轻量，几乎能生成**无限量**的数据。坏处是，这些**不一定是你真正想处理的自然训练样本**——真要上手做的话。

另外，用这个框架也能扩展到不同的编程语言。有个叫 **Multi-SWE-bench** 的，还有个叫 **SWE-bench Multilingual**，基本上都扩展到了多种编程语言。唯一的实际困难是各语言的约定不同，你需要处理它们。好消息是现在 coding agent 做这个很容易，改约定没那么难。

#### 多 harness 训练

最后我想讲的是**多 harness 训练**。就像我之前提到的，如果语言模型预期的编辑格式和 harness 预期的差别很大，大多数语言模型在**没训练过的 harness 上表现会更差**。

所以现在语言模型厂商普遍会在多个 harness 上训练：他们不只训一个 harness，而是在 **OpenHands、OpenCode、Codex** 等各种 harness 上都训。举个例子，你可以看看 **NVIDIA Nemotron** 的报告，他们刻意在好几个（我记得是五个以上）harness 上做了训练，让模型能适配很多不同的 harness。

### 内循环之外的那些活儿

我们剩下的时间不多了，快速过一下几个不同的例子、几个不同的任务，不只是直接的 issue 修复。这些在研究里没那么主流，但如果你想做一个能用的模型，它们非常重要。

#### 前端开发与多模态

**前端开发**就是其中之一。有个前端开发基准叫 **SWE-bench Multimodal**，它只专注于修复前端的 bug——所以它并不是专注于开发新前端，更多还是 issue 修复那一类。

做多模态模型有两个不同之处：

- **输入端**：通常你会觉得要做这件事得用多模态模型接收并理解输入，也就是需要一个训练过能读图像的语言模型；
- **验证端**：在浏览器里验证有几种方法，一种是在浏览器里写能跑的测试，另一种是直接看输出。

现在大家大概有两种做法：一种常见做法是把**基于 GUI 的 agent 当作 coding agent 的一个组件**，或者让一个 agent 同时能处理 GUI 任务和编码任务——下节课会讲 GUI agent，所以怎么构建我就不展开了。另一种做法是**写一个脚本来测试 GUI**。比如 **Playwright** 就是一个常用的基于 GUI 的测试库，很多人用它来做这类事。

举个例子：假设你有个问题"输入长度为 0 也能提交"，那你可以用视觉方式验证这种情况确实发生了，或者你可以写一个 Playwright 脚本，确保输入 0 之后会出现要求填写非空名字的提示。SWE-bench Multimodal 就是评估这类能力的一种方式。

> **注意**：几个月前有个很惊人的结果——有个流行的模型叫 **GLM**，GLM-4 是新发布的模型，它**不是多模态**，却在 frontend design arena 夺冠。这动摇了我对"做好前端开发 coding agent 需要什么"的假设。不过我还是觉得多模态能力可能挺重要的。

#### 内循环、外循环，和微软 2019 年的那张表

开发里有一个很有名的概念：**内循环和外循环**。我到目前为止讲的基本就是开发的内循环，它本质上就是修 bug、跑测试这类事情的迭代过程。**外循环**就是除此以外的一切。

| 循环 | 覆盖什么 | 难点 |
| --- | --- | --- |
| 内循环 | 修 bug、跑测试这类迭代过程 | 已经有比较成熟的工具和基准 |
| 外循环 | 代码审查、部署与监控、维护、做规划、提需求 | 理想情况是 agent 能帮我们搞定所有这些事，但这些事更难定义，也更难找到训练数据 |

这是微软 2019 年一份有意思的调查。现在情况可能不一样了，但 2019 年他们调查了自己的软件开发者，问你有多少时间花在写代码上：

| 时间花在哪儿 | 占比 |
| --- | --- |
| 写代码（issue 开发、新功能开发、issue 修复） | 15% |
| 开会和邮件 | 25% |
| 调试 | 14% |
| 跑测试 | 8% |
| 其余各项 | 讲台上没给出具体数字 |

所以你看，其实这也是软件开发工作里很大的一部分——写代码只占 15%。

那我们能做的就是把这些任务做个对比。比如**修复**（issue 修复）我已经讲过了。但还有：

- **从零开始创建东西**；
- **为代码写好测试**；
- **修复失败的部署**；
- **在很长一段时间里持续开发应用**。

#### 任务清单与几个值得知道的名字

第一个例子是专门针对**定位**来训练，也就是让模型特别擅长判断一个编码任务该从哪里入手。我们有一个做这件事的 RL 方法，叫 **CodeScout**。如果你想给项目做个和 RL 相关的题目，这个可能挺有意思，因为它类似 coding agent，但更可控，用小模型也更容易做。如果你觉得有意思，可以看看我们的 CodeScout 论文。

第二个任务是**从零开始创建应用**。有个叫 **VibeBench** 的基准，专门评估 agent 做 vibe coding 的整体水平。这非常难做，因为你得能正确评估它们，所以需要设计出好的验证器。

第三件是**完整实现后端库**的，这方面有几个基准：老的叫 **Commit0**，新近流行的叫 **ProgramBench**。ProgramBench 本质上是要你**逆向工程一个二进制文件，再从零重新实现它**——你可以运行这个二进制文件，根据输入输出去探测，然后写出新的实现。这很有意思，因为它的周期非常长，而短周期任务越来越容易，它现在是新的挑战之一。

对基准感兴趣的另一个例子是 **SWE-milestone**，它的基本思路是：你不是只实现一个 issue，而是在一个阶段里实现**很多 issue**，并且要确保你逐个实现 issue 时，不会把代码库搞得一团糟、变得难以维护——因为这是一些 coding agent 的大问题。这个基准就是用来评估这一点的。

如今另一个很大的问题，是**生成能验证你有没有把 issue 修好的测试**。因为我觉得现在有了 coding agent，如果你能写出真正好的测试来验证 issue 已解决，这等于成功了一半——你明确了任务，agent 就特别擅长反复迭代把它做好。**SWT-bench** 就是这样一个基准，它基于我之前提到的变异测试。

最后一类任务更偏**运维**一些，比如部署这类任务。不过我觉得还没有真正好的，目前还没有特别好的基准，而且它比较难做，因为需要真实的基础设施来运行。不过我有一个参考例子是 JetBrains 做的，感兴趣的话可以看看。

已经 5 点 50 了，我们超时了，这个我就非常简略地讲一下。另外还有一些别的是 CMU 这里的人做的工作：包括我，另一个是 Daniel 参与的，叫 **SWE-playground**。**SWE-playground** 和 **HyperGym** 基本上是自动创建基准，覆盖的不只是写代码，还有软件工程里的其他环节。

## 让 AI 亲手操作你的电脑：CUA 的建模、评测与训练
> 对应块：BLK07 | 覆盖分集：P07 | 块标题（分集名）：《07｜操作电脑的 agent【中文配音版】》

先做个小调查：计算机使用 agent，最早是什么时候出现的？——有几位觉得在 2020 年之前？好，我看到几只手动起来了。那觉得在 2024 年之后的呢？

答案是 2017 年。第一篇 CUA 论文是那一年 OpenAI 的 World of Bits。按 AI 的标准，这已经相当古老了，对吧？那会儿他们搭了一个极其简化的玩具环境，界面看着有点像手机上的页面，但简化得完全不像真的，基本全是合成数据。当时的模型连这种玩具都做得很差——我觉得这个项目是超前于时代的。

不过在展开这段历史之前，我们先把 CUA 是什么讲清楚。因为它和这门课里我们讲过的那些 agent，确实不太一样。

### CUA 是什么：一个和你抢同一个鼠标的 agent

CUA 就是 computer use agent。它的输入在大多数应用里不是文本，而是图形用户界面本身：它可以是网页浏览 agent，可以是操作你桌面电脑的 agent，也可以是操作手机这类移动设备的东西。广义上这些全是计算机使用 agent——它们通过和人**完全相同的图形界面**来操作东西，以截屏作为输入，输出的动作也和人同一类：点击、滚动、滑动、点按。

> **定义**：CUA（计算机使用 agent）= 通过与人完全相同的图形界面来操作设备、以截屏为主要输入、以点击/滚动/输入等人类动作作为输出的 agent。

关键区别在于，它和人待在**完全相同的空间**里。这一条让建模和评估同时冒出了很多有意思的问题：建模上，你面对的是像素而不是符号；评估上，你很难找到一个现成的"标准答案"来对答案。

大体的运行方式是这样的：用户把任务给模型，同时给模型一个环境观测——通常就是一张截屏，也就是你电脑屏幕或手机当前显示的内容。它也可以是别的基于文本的表示，但目前大多数前沿 CUA 都用截屏，因为那基本就是用户自己做这个任务时会看到的东西。观测和任务一起进模型，模型通常先产生一段推理轨迹（就是思维链），再产生它想执行的下一个动作。动作可以是环境允许的任何动作：点击、滚动、打字。我们把这个动作丢到环境的基础设施里真的执行掉——如果是点击，就真的在屏幕上点一下——执行完得到新的观测，然后循环往复。

```text
  任务 T（自然语言，例如"帮我买一个 20 美元以下的蓝色马克杯"）
      |
      v
  [ 观测 o_t = 截图 S_t，环境当前显示的内容 ]
      |
      v
  [ 策略 = 一个 LLM ]
      |  先产生一段推理轨迹（思维链）
      v
  [ 动作 a_t：click(x, y) / scroll / type ... ]
      |
      v
  在环境的基础设施里真的执行（浏览器 / 桌面 / 手机）
      |
      v
  [ 新观测 o_{t+1} = 执行之后的新截图 ]
      |
      └──▶ 把 a_t 和 S_{t+1} 一起拼进上下文，回到第一步
```

拿"帮我买一个蓝色马克杯"走一遍就很清楚。初始观测可能来自浏览器，进去之后模型说：我看到屏幕中央有个蓝色马克杯，我要点它。然后它生成一个格式化的待执行动作——对环境做一次左键点击。我们真的在环境里点下去，于是拿到新截图，能看到马克杯的详情页。模型接收这个新观测，接着说：配送信息在下面，我要往下滚动去找，于是生成滚动动作。我们再执行，再拿新观测。就这样重复，直到模型认为任务完成。

> **提示**：整个循环的终止条件有三种——模型自己认为做完了、环境或裁判给了成功奖励、或者预算（调用次数、时间、token）用完。任务越复杂，这个循环叠代的次数就越多。

一般你会在结束时拿到某种奖励，来自环境、人类用户或者某个裁判，告诉模型做得成不成功。绝大多数情况下这个奖励就是 0 或 1 的二值奖励，但某些场景下也可以给部分奖励。

> **结论**：计算机使用 agent 就是一个"观测—推理—行动"的循环，不断重复，直到任务完成或预算耗尽。

### 九年时间：从极简玩具到全生成的界面

回到刚才那个调查。2017 年 World of Bits 之后，情况并不是一帆风顺的。

```text
  2017         World of Bits     OpenAI，极简玩具环境，基本全是合成数据
  2022         WebShop           模拟的购物网站，模拟点亚马逊，比玩具真实得多
  2022 - 2024  WebArena          CMU，模拟环境 + 从真实网站抓来的真实数据
  2024         OSWorld           真实 Linux 虚拟机，369 个任务 / 9 个应用
  2025 - 2026  全生成环境        用编程 agent 端到端生成整个应用和网站
  2025 - 2026  GUIWorld          CMU，长尾专业软件 + 真实数据
  2026         GPT-4o-extra      大多数计算机使用基准上已超过人类基线
```

2022 年语言模型兴起，关注度开始上升，出现了 WebShop。它也做了简化的购物环境，但比 World of Bits 真实得多——你就是在模拟的亚马逊网站上点击。虽然还是有点假，但完全是两个量级。这个阶段有意思的是，语言模型 agent 开始在这些任务上**起色了**，而且当时并没有像 World of Bits 那样专门训练它们。

2022 到 2024 年，CMU 有一项我认为是开创性的工作叫 WebArena。它建了很多模拟环境，比 WebShop 和 World of Bits 都更真实：里面填充的数据通常是从真实网站抓来的，来自亚马逊、Reddit 之类的真实站点，数据和环境都是真的。我认为这也标志着模型开始在这类问题上真正取得进步。

2024 年前后几乎同期出现了 OSWorld。我认为它如今是最标准的计算机使用基准之一：同样用真实应用和真实数据，但针对的是**桌面操作**而不是网页浏览，更通用，支持 Linux、Windows 等系统。这和 WebArena 是两回事——WebArena 是网页浏览，OSWorld 是完整的桌面操作。

2025 到 2026 年，情况又变了。编程 agent 变强了很多，于是很多人开始**端到端地生成环境**。WebArena 和 OSWorld 的路子是拿这些应用的开源实现，再往里填真实数据——也就是说，所有软件都是人写好并开源的。而 Mind2Web-Bench 以及这前后的一些别的基准，是直接用编程 agent 端到端生成整个应用和整个网站。展示的这么一个 Gmail 克隆，外观和真的非常接近，整个东西完全由一个 LLM 编程 agent 生成，里面预置的数据也全是合成的。可以说很多前沿 CUA 环境如今已经完全是被生成出来的，数据也全是合成的。

> **注意**：而且它们效果有时候**比真实应用还好**——因为生成的环境更干净、噪声更少。

GUIWorld 也是 CMU 的项目，用的是真实软件。我觉得它有意思的地方在于软件更偏长尾——比如天文学、生物学这类领域才会用的软件。它把评测从消费级应用延伸到了非常专业的桌面软件，数据我认为是真实使用场景下载下来再加载进环境的。

最近刚发布的一个演示是 GPT-4o-extra 在计算机使用上的一次巨大跳跃。它基本解决了大多数计算机使用基准，目前已经超过人类基线。演示的是它操作 CAD 软件做 3D 建模——注意，画面是加速了 30 倍的，实际上比你看到的要慢 30 倍。它比之前的模型快了不少，但仍然很慢、很贵。

> **结论**：就能力而言，现在的模型已经很强了。我们从 World of Bits 那个玩具环境出发，九年后有了能在大量计算机任务上达到甚至超过普通人类水平的模型。进展非常快，令人兴奋。

### 为什么计算机使用比数学更难验证

从研究的角度看，我们得想想该怎么衡量这些问题。基准测试是衡量这类 agent 进步速度的核心手段之一。

但计算机使用这件事，比这门课讲过的其他 agent 都更难验证一些。在软件工程或者数学里，你有单元测试、有符号验证器，能明确告诉你任务是否成功完成。计算机使用不一样：**一个任务算不算成功完成，就连人自己通常都意见不一。** 写程序化的验证器因此非常有挑战。

整个评估可以拆成四个大类：静态评估、端到端评估（网页）、端到端评估（桌面 / 移动）、以及长时程评估。它们的共同点是都在回答同一个问题：agent 到底做成没有。但"怎么判断"这件事，从头到尾都在变化。

### 静态评估：又快又便宜，但没测到你真正关心的东西

回到那个任务：把一个 20 美元以下的蓝色马克杯加入购物车，但不要购买。静态评估衡量的是 agent 轨迹上**每一步动作**是否正确。

比如 agent 从这张截图开始，尝试点击这里的蓝色马克杯。我们有标准答案：要求 agent 预测的 $(x, y)$ 坐标落在目标框内。落在红框里得一分，落在外面得零分——意思是它这一步没有执行正确的下一个动作。之所以叫"静态"，是因为你没法让 agent 端到端地跑起来，我们只考察每一步的动作对不对。

这个领域一个经典的基准叫 Screenspot-Pro，它是个 grounding 基准，测的就是截屏上的动作定位。它涵盖各种应用和操作系统，大约有 1500 个不同的截屏样例。指标是**逐点准确率**。比如"构建 UV 球面网格"这个任务，你看到的是一张 Blender 的截屏——注意，这只是一张截屏，**agent 没有任何可交互的环境**，它只拿到这张图，目标是判断它产出的动作是否落在红色边界框里。落在框内就算对，否则不给任何奖励。

静态基准的另一个例子是 Mind2Web，它测更多样的动作。你可以把它理解成**下一步动作的模仿学习**：给定当前截屏和任务，比如"在布鲁克林中心租一辆车"，预测 agent 的下一步动作。标准答案可能是点"租车"标签页。这个任务里不会真的执行任何动作，你拿到的是一系列截屏，agent 根据截屏预测下一步动作。预测出来之后我们给它打分，然后**从离线数据集里给它下一张截屏**。

所以这两者都不是真的在环境里执行动作——根本没有环境，它就是一组静态截屏加一组标准答案动作。

| 对比维度 | 静态评估 | 端到端评估 |
| --- | --- | --- |
| 看什么 | 每一步的动作对不对 | 最后有没有真的做成 |
| 谁来判定 | 固定的标准答案，答案集合封闭 | 程序化验证器或裁判自己定义"做成" |
| 典型误差 | 大量假阴性 | 假阳性，也就是 reward hacking |
| 成本 | 极快、极便宜，不用搭环境 | 要搭环境或部署，昂贵得多 |
| 测到了什么 | 测不到你真正关心的东西 | 测的就是你真正关心的东西 |

> **易错点**：静态评估最大的问题是**假阴性**。同一张截屏、同一个任务，其实有很多不同动作都可以算对——不一定要点"租车"标签页，先去调日期同样是有效动作。但在静态评估里，因为标准答案是固定的，这些动作全会被判成错误。这就是静态评估的主要缺点：**很快，但没有测到你真正关心的东西**，也就是真正的端到端表现。

### 端到端评估：查结果，而不是查步骤

于是有了第二类：端到端评估。还是那个买蓝色马克杯的例子，我们让 agent 在环境里或真实网页上真的执行任务，最后检查它做得对不对。

#### 在模拟环境里跑程序化验证器

在模拟环境里做这件事，本质上就是程序化检查。agent 可能已经尝试了这个任务，轨迹结束时我们运行一批单元测试式的检查：马克杯是否在购物车里？价格是否低于 20 美元？agent 是否没有真的下单（检查订单数是不是 0）？**所有单元测试都通过，才给 1 分奖励。**

这时候你确实有一个环境，agent 想怎么操作都行；我们不检查它每一步执行了什么，只检查它最后有没有靠这些测试真的完成任务。如果单元测试足够全面，这就是非常好的奖励信号——我们不用监督每一个动作，只在最后看它做没做对。

WebArena 就是最早这么做的基准之一。它是一个模拟网页导航基准，搭载 4 个不同的应用，大约 800 个任务。目标之一是"建一个叫 awesome-llm-reading 的空仓库"，agent 会进入这个**本地搭建的模拟 GitLab** 去做。关键在于：**在 WebArena 里，agent 任何时刻都不会访问真实网页**，只能在模拟环境里设法完成目标。

任务结束时我们运行程序化验证器，检查一堆条件——本质上就是看它有没有成功创建这个仓库。这些验证器都是手写的，其实是 CMU 的研究生写的，他们为 WebArena 里的每个任务都手写了一个。假设学生们写得没问题，执行结束后你就有了个验证器能告诉你 agent 到底成没成功。

> **注意**：验证器不够全面，还是会有假阴性和假阳性。但总体上这是个很不错的基准——它确实让业界开始更认真地对待计算机使用 agent 的评测。和静态评测对比很重要，因为它测的是**真正的端到端表现**。只看结果，不关心具体步骤，只要 agent 做对就行。
>
> 但会有 **reward hacking（奖励作弊）**：agent 可能想办法骗过验证器，而不是真的去做那件事。这是大多数 CUA、agent 评测乃至训练中的常见问题。

VisualWebArena 是 WebArena 的扩展，它把这个问题当作**多模态问题**来处理。WebArena 发布时，大多数模型处理 CUA 或网页浏览任务用的是 accessibility tree（无障碍树），算是 HTML 的简化版。VisualWebArena 则想让大家相信该用截屏方式操作。它包含 910 个视觉定位任务，所以里面的问题都得用多模态表示才能解决；评测方式类似，同样有程序化检查，但额外加了一些多模态程序化检查——有些问题只靠 HTML 是解不出来的。

#### 裁判型评估：换成另一个 LLM 来判

另一类做法是不用程序化验证器，而是**用另一个 LLM 来判断**模型到底做成没有。做法很简单：拿到模型的轨迹之后，你 prompt 另一个 VLM 或 LLM（文本或多模态视觉语言模型），把 agent 的轨迹喂给它，问它任务有没有成功完成。

这方法之所以常用，是因为你不可能给每一个关心的任务都写验证器。这种情况下你同样拿到 agent 完成的轨迹，但不用程序化验证器，而是给一组 **rubric 评分细则**，或者干脆直接交给 LLM 自由裁量：把轨迹和任务一起给它，LLM 就会告诉你它认为 agent 有没有成功。

这些裁判通常先输出一小段思维链，再给出判断，比如通过或不通过；有时也打一个浮点分数，但一般就是告诉你通过还是不通过。这样更通用，因为不用给基准里的每个任务都写验证器。

> **易错点**：但它也更容易误判。LLM 裁判很容易被糊弄，以为任务完成了，其实并没有。

采用这种裁判方式的基准里，**WebVoyager** 是最早测试 agent 在真实网页上导航能力的之一。它和 WebArena 很不一样：他们选了 15 个不同的网站，在上面设计了 600 个任务，要求 agent 真的上这些网站去完成目标。你可以实际去看这些网站——比如 Allrecipes 食谱网站——你能看到之前 agent 试过的痕迹留在上面。

> **易错点**：这其实不太好，但也正好说明了为什么我们可能不想在真实网页上评测 agent。

不过 WebVoyager 仍然很有价值，因为它测试了 agent 在**非模拟环境下**的能力，这基本上是最接近真实世界的评测方式了。比如"找出 star 数最多的气候变化数据可视化 GitHub 项目"，他们让 agent 真的去 GitHub 上做一堆搜索，找出这个任务下 star 数确实最多的仓库。这种情况下，因为是在真实网页上，你没法用程序化验证器——你没法查询真实网页的状态。所以这里就是 VLM 裁判：另一个 LLM 拿到 agent 执行的一系列动作和观察到的截图，也拿到原始任务，然后判断 agent 有没有成功。

你可以把它想象成相当狂野西部式的 eval：把东西部署到真实网页上，跑一个裁判，最后告诉你成没成功。但很多人喜欢这种方式，因为它在某种程度上是最接近真实世界的评测。

**Online-Mind2Web** 是继 WebVoyager 之后的另一个 eval，它更全面一些，裁判也更强。他们证明裁判和人类的一致率大约是 **85%**——这已经非常接近人类水平的裁判一致性了。它同样扩展到了真实网站：大约 136 个网站、300 个任务，裁判更复杂，带不同的 rubric 评分细则和标准。整套流程全自动化：一个 LLM 在真实世界执行任务，另一个 LLM 评判。

> **注意**：不过现在人们已经不太用它了，因为它基本上已经被现代模型解决了。而且随着计算机使用 agent 越来越流行，大家在把它们部署到真实世界时也更谨慎了——这些网站的主人可不喜欢一大批 agent 反复访问他们的网站跑基准。你可以想象，如果你的网站被收进某个基准，流量突然暴增，你大概也不会高兴。

#### 桌面上的端到端评估

网页很有意思，因为能在上面做很多事，我个人大部分时间也花在 Chrome 上。但还有另一类任务要求你去操作一台真正的虚拟机或真正的桌面。

**OSWorld** 是最经典的 CUA 基准之一。它是一个可以启动的**真实 Linux 虚拟机**，包含大约 369 个任务，分布在 9 个不同的应用上——GIMP、LibreOffice、Chrome 等等。每个任务都有程序化验证器，agent 得进入虚拟机、跨多个应用尝试完成任务，最后我们跑一些类似单元测试的检查看它有没有成功。

OSWorld 里的任务长什么样：比如要更新这张 LibreOffice Calc 表格，用的是另一个文件夹里的收据。agent 得先导航到那个文件夹，找到收据，把对应的数值填进这个工作簿里，还要保存工作簿。它得在不同应用之间来回操作，只凭一句初始用户指令完成整个任务。等 agent 觉得做完了，我们就跑单元测试：检查表格里是不是有我们认为该有的条目，给它打 0 或 1 分。

> **结论**：精神上它和 WebArena 很像，但这里用的是**真实应用**——都是人们日常真正用的软件，同样运行在完整的虚拟机里。它不再局限于 Chrome 或网页，而是在包含 9 个应用的整个虚拟机里运行，覆盖面广得多。可以想见，**桌面 agent 能自动化的任务种类会比纯网页浏览 agent 多得多**。

**Windows Agent Arena** 是另一个基准，灵感来自 OSWorld，是微软创建的，用来测 agent 在 Windows 机器上的表现。毕竟世界上很多实际工作就是在 Windows 机器上完成的。它的任务都是企业工作流或各类公司里非常常见的那些。同样是启动一台 Windows 虚拟机，让 agent 去做任务，最后用验证器判断对不对。因为用的是程序化验证器，也同样容易出现假阳性或假阴性——和 LLM 裁判一样，各有优缺点。

#### 人工审查仍然是黄金标准

这里有一点很重要：我们讲过的这些评测指标，不管是程序化验证器还是 LLM 裁判，本质上都是 **proxy 指标**，用来代理判断我们有没有成功完成任务。

**人工审查，让人类来判断 agent 做得怎么样，可能仍然是黄金标准。** 这些论文大多也做了人工评估基线：让人来审查 agent 的轨迹，每条轨迹找几个人判断 agent 是否成功，最后再让几个人投票看 agent 到底成没成功。

问题就是这非常贵，不可能对基准里的每个任务、每次运行都这么做。所以大多数基准的创建者还是会在开头做一两次，找人实际去尝试或评判任务，确认 agent 和基准本身是合理的。

到这一步，我们讲过的三种判定方式可以并排放在一起看，它们的取舍其实非常清楚：

| 判定方式 | 怎么判 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 程序化验证器 | 手写单元测试式检查环境状态 | 客观、快、可复现 | 写不全就有假阴性和假阳性；容易被 reward hacking |
| LLM 裁判 | 另一个 VLM/LLM 读轨迹 + rubric 给出通过或不通过 | 灵活，不用为每个任务写验证器 | 更容易被糊弄，误判率明显更高 |
| 人工审查 | 几个人分别判，再投票 | 至今仍是黄金标准 | 极贵，只适合在开头做一两次 |

### 长时程基准：光看最终结果太稀疏了

这些基准大多已经被现代模型解决得相当好了——最近发布的 GPT-4o-extra 在大多数基准上远超人类。所以社区的注意力已经从它们身上移开了一些，转向**更长时程、更专门**的基准。

任务类型其实还是那些，但时间跨度长得多：有些任务真人要花几个小时，甚至两三个小时。对照一下就知道差别——OSWorld、WebArena 里很多任务人类大约 10 到 20 分钟甚至更短就能完成，而接下来这些任务可能要花好几个小时，还要操作专门的软件。

> **结论**：我们正朝着让 agent 超过人类专家用电脑的水平迈进。

很多这类长时程基准采用非常相似的评估策略。你会拿到一条动作轨迹，记录 LLM 在环境里执行过哪些动作，然后是几种不同的检查。

**为什么不能只用最终结果奖励？** 因为信号太稀疏了。长时程任务里，agent 中间可能做了很多有用的工作，最后却因为某一个环节没做到而拿不到满分。所以长时程计算机使用需要更细粒度的奖励：

- **状态检查 / 阶段性奖励**：检查 agent 是否完成了某个中间任务，类似基于 rubric 的奖励；
- **过程奖励**：检查 agent 是否端到端完成了整个任务，相当于最终奖励；
- 但两者都需要，中间奖励用来保证长时程任务里有非零信号。

> **注意**：还有一个很重要的点——**最终交付物好，并不总是长时程计算机使用的好指标**。因为任务太长了，你必须靠一些阶段性奖励来确保模型一直在做有产出的事情。

**Odyssey** 是我们在 CMU 做的基准，衡量长时程网页浏览。它包含 200 个任务，每个任务都有一组 rubric 评分细则，也就是我们认为模型应该完成的一组事项。比如"规划一趟去棕榈泉参加婚礼的行程"这个任务，模型要满足 **8 条 rubric** 才能拿满分：你得找到一条从匹兹堡到洛杉矶的直飞航班，还得找到上午 9 点到下午 4 点之间的车程，还有一堆类似的条件都要满足。

> **结论**：所以 Odyssey 是按多条 rubric 打分的，这样你就能拿到部分奖励，而不是最后只有一个二元的通过或失败。这是一种折中——大部分验证仍然是 LLM 做的，但这是**细粒度的 LLM 验证**，因为最后给出的不只是一个通过或失败的奖励。

**OSWorld 2** 是 OSWorld 的续作，挑战长达一小时的工作流。OSWorld 1.0 的任务大多只需要人类几分钟，而 OSWorld 2 有大约 108 个任务，人类完成的中位时间是 **1.6 小时**。这些工作流里有一些非常复杂——需要做 CAD 建模、3D 建模或者修图，所以我们进入了更专门的软件使用领域。平均来看，被测试的大多数前沿 agent 大约需要 **300 次调用**，也就是说光跑一次基准测试通常就要几个小时。

> **提示**：评估很贵，但很神奇的是，你启动一个 eval，一小时后回来，发现 agent 还在高效推进任务——这就是这些模型能连续好几个小时保持高效工作的证据。

OSWorld 2 里有个示例任务是"制作一个猫形支撑支架，并导出符合这张图纸的模型"：左边给你参考图纸，agent 的目标是操作某种 CAD 软件做出右边这个东西。普通人我不敢说，反正我肯定没法轻松完成。人类也要花大概一小时，至少也得半小时才能完成。里面的难点很具体：它需要在 3D 空间里导航，需要知道这个环境里有哪些工具可用，而且要能持续工作好几个小时。

> **注意**：再强调一次，这里同样是加速了 30 倍的演示，实际要慢得多。不过它确实能把这些 3D 零件设计得相当好。相比两年前的模型，这是巨大的领先。

**CoWorld-Long** 是 CMU 的另一个基准，专攻长程计算机使用。它的环境非常专业化，涵盖医疗类、工程类，还有建筑和设计类任务，包含 200 个这样的任务，大多需要 500 次甚至更多次 LLM 调用，相当于人类几小时的工作量。这个基准今年年初发布时，大多数模型的成绩都很差；但我觉得包括 GPT-4o 在内的近期模型，成绩已经大幅提升，他们在这个基准上已经能拿到接近 **90%** 的成绩。

> **结论**：长程计算机使用、乃至整个计算机使用领域，已经接近被解决了——有人甚至说已经解决了，因为这些模型在很多这类任务上已经超过人类。

### 答疑：基准设计里那几个真问题

#### 细粒度扣分到底有没有必要

有人问：这些基准里有没有给中间步骤打 rubric 奖励？比如任务是"往购物车里加一个高评分商品"，你确实做到了，但过程中出了别的问题、加了不相干的商品，会不会被扣分？

这问题问得好。我觉得**在很多基准里奖励设计都很棘手**。WebArena 里有些任务确实有这种扣分机制，但很多时候人们设计这些基准时会让答案尽量没有歧义。这类问题某种程度上有点人工——比如 WebArena 可能会说"把评分最高的商品加进购物车，做到了就能拿满分"。我见过 agent 靠往购物车里塞一大堆东西来 reward hacking，想以此完成目标。

这很看具体基准。一般来说人们通常不会去做这么细粒度的扣分，不过这也是因为这些基准刚被做出来的时候情况就是那样，agent 还很弱，所以有些奖励标准一开始就定得比较宽容。

> **结论**：所以有些基准确实有这类机制，但我不觉得它特别普遍。对，我觉得大家**宁可误判为通过，也不愿误判为失败**。

#### rubric 是谁写的

那 rubric 本身每个任务都不同，这些是专家写的，还是模型合成的？另外还有 reward hacking 方面的问题。

在 Odyssey 里，rubric 多为 LLM 生成、人工核验。生成 rubric 的一个常见做法其实和我们前面那个问题有关：**你给模型特权信息，也就是比评测时更多的信息**——比如一些提示，或者 HTML 表示——让它的表现比真实评测场景下更好。有了特权信息，你就能据此生成更准确的 rubric。

所以不管是 Odyssey 还是很多业界 benchmark，如今 rubric 通常都是 **LLM 生成 + 人工核验**；有时甚至不是人工核验，而是由另一个掌握不同信息的 LLM 来核验。

> **提示**：我觉得如今用合成生成的方式还是挺合理的，但我个人仍然觉得，放进 benchmark 的每样东西总得有人看过一眼，确认它靠谱。

至于训练时的 reward hacking——那个我们到训练部分再细说，但总之它是个大问题。而 **rubric 奖励比结果奖励更防 reward hacking**，因为你得同时满足好几个不同的标准。比如你只想买评分最高的商品，那模型可以作弊，把网站上所有东西都加进购物车；你可以想象，基于 rubric 的奖励就会检查这一点。

#### 要不要在 benchmark 上训练

有人问，学界和业界会不会直接在 benchmark 上训练？

按理说你**不该**在 benchmark 上训练，因为那等于拿训练集去测试。但业界很常见的做法是生成和 benchmark 非常类似的任务——大家常造出类似 OSWorld 或 WebArena 的任务，拿这些来训练。这样分布相近，但没在同一个测试集上训练。

GUI-World 其实是明确有训练集的，有些 benchmark 会提供训练集、验证集，理想情况下还有测试集供大家训练用。但你不应该在真正的评测集上训练——不过遗憾的是，大家确实会找 proxy 信号来变相这么做。

### CUA 是怎么被表示和建模的

回到刚才那个悬着的问题：CUA 的动作空间到底是什么？

先说表示，再说动作空间。CUA 和如今大多数 AI 模型一样，**基本上就是一个 LLM**——准确说通常是视觉语言模型，因为大多数模型以截屏作为输入。

输入有两个：目标，用自然语言表示（还是那个例子，"帮我买一个 20 美元以下的蓝色马克杯"），以及一张初始截屏（取决于环境最初的状态）。这两个输入进策略，策略本质上就是一个 LLM，然后 LLM 产出一个动作，通常以**文本形式**表示——它用文本来生成自己想执行的动作的结构化表示，比如一个带 $(x, y)$ 坐标的点击动作。接着我们执行这个动作，把它加进下一步喂给 LLM 的上下文里。

```text
  喂给 LLM 的那条多模态序列（每一步都在变长）：

  任务 T(文本) → 截图 S0(视觉) → 动作 a0(文本) → 截图 S1(视觉) → ... → 截图 St(视觉)

  文本切成 text token，截屏切成 visual token（或某种基于像素的表示），
  两者交错拼成一条很长的序列，喂给语言模型 → 以此为条件生成下一个动作
```

这个循环通常叫 **ReAct 循环**，即推理（Reasoning）加行动（Acting）。每一步你都把产出的动作连同新截屏一起拼进不断增长的上下文，再喂回 LLM。所以你手上是一份**视觉与语言交错的动作历史**：有自然语言形式的目标和动作，也有像素输入，可能还有其他元数据。执行完动作 $a_t$ 会在截图 $S_t$ 上得到截图 $S_{t+1}$，然后我们把它拼进已有上下文，再喂给 LLM，产出下一个动作。

对模型来说，看起来就是每一步都有一堆 embedding 被喂进去，模型产出一个动作，你把它 tokenize 之后拼到上下文里，不断重复。当然不是直接喂原始像素——大多数语言模型都会先做 tokenize：自然语言切分成文本 token，截屏转换成视觉 token。现代语言模型的好处是这些通常直接拼接起来就行。

> **结论**：我觉得这是一种非常简洁优雅的表示方式，而且效果出奇地好。文本会转成 token embedding，截屏会转成视觉 embedding，最终整合到一起交错拼接，传给语言模型。如今语言模型就是 Transformer，由它来生成下一轮的动作，显然很自然。

**动作空间**则因模型而异，也取决于你想把模型部署到什么环境里。粗略看它们大体相似：一般都有"一组可以输出的动作"，比如点击、滚动，或者你环境里有的其他动作。不同模型输出动作的格式略有差异——可能输出成 **PyAutoGUI 的指令**，也可能输出成工具调用或 XML，然后你需要解析它，传给能在环境里实际执行的东西。

#### 为什么是截屏，而不是 HTML

那为什么用截屏呢？HTML 是不是也可以？

HTML 也是可行的，不过 **HTML 很乱**，也有人用简化版的 HTML 来做表示。我觉得一个原因是：最近的模型大多不用 HTML，而是主要依赖截屏。它们有时还是会用元数据，但总的来说主要就是截屏。

原因很朴素：**截屏简单得多**。给电脑截个图比处理底层的 accessibility 元数据要容易得多。网页上拿 HTML 很容易，但桌面操作就没那么容易了——你得面对各种不同的原生桌面软件。而且让一些人意外的是，基于截屏的表示已经取得了非常好的成绩，HTML 或其他结构化表示几乎显得没必要了。

> **结论**：它很简单，而且效果出奇地好。这个问题问得很好，因为一年前很多人其实不太能接受这一点；现在多模态模型足够强，做起来出乎意料地容易。

那除了截屏这种基于像素的表示，用其他模态有没有好处？肯定有。OpenAI 说过，至少之前的模型（包括 GPT-4o）在可用时**确实会用计算机的 accessibility 表示**。macOS 上有 accessibility 表示，是为视障用户设计的，它有点像 XML 那样的表示，告诉你哪个区域是什么，比如这块是 Chrome 窗口、这块是 Dock 栏。我觉得这类信息很有价值，尤其是想让模型更稳健的时候。

不过我个人很喜欢纯截屏的表示方式，因为它**非常简洁、非常通用**。你训练一个直接吃截屏的模型，就能部署到任何设备上，不需要访问设备底层的内部信息。所以在 Windows 上训练的模型更容易泛化到 Linux 或 Mac 上，因为它们的底层 accessibility 表示各不相同。

至于"能不能建个数据库，把图标的位置之类记下来让模型直接查"——这其实也是一种合理的做法。现在的模型并不是被训练成单一用途的 CUA：GPT-4o、Claude 并不总是只执行计算机操作，它们会穿插调用 Bash、写代码，**模型通常会用最高效的方式来解决问题**。

#### 动作执行之后：等一下还是直接截屏

执行完一个动作之后，是马上截一张还在加载的截屏，还是怎么办？

我觉得计算机使用这件事既烦人也很有意思，因为跟数学或编程模型比，你会遇到很多边界情况和基础设施问题。

> **易错点**：最常见、也最简单的做法是：执行完动作先睡几秒——通常是三秒左右——再截屏执行下一步。如果那时候确实看到一个加载页面，模型一般会被训练成再等一段指定的时间。也有更复杂的做法，比如设计模型一直等到截屏不再变化为止。但最简单也最常见的办法就是睡一会儿。

### 训练一个 CUA：预训练、行为克隆、强化学习

说到训练，大多数计算机使用 agent 都是基于**预训练的视觉语言模型**。训练分几个不同阶段。

先提醒一句：当你把 GPT-4o 部署成计算机使用 agent 的时候，你部署的不是"只会计算机使用的 GPT-4o 专用版"——它是一个通用模型，计算机使用只是它的能力之一，而且大家越来越倾向于这么做。

```text
  大规模互联网数据（含噪、合成为主）
                  |
                  v
  [ 预训练 ]      学 grounding：截图 -> 边界框 / (x, y)
                  学动作预测：HTML 元素 -> (x, y)
                  |
                  v
  [ SFT ]         行为克隆：模仿"看到截图 -> 下一个动作"
                  人类演示 + 用特权信息合成的轨迹
                  |
                  v
  [ RL ]          把模型丢进模拟环境自己跑：
                  成功轨迹里的动作加权，失败轨迹减权
                  成功率大约 0.5 -> 0.6 甚至更高
                  |
                  v
  [ CUA ]         强大的计算机使用 agent
```

#### 预训练：先把 grounding 学出来

预训练阶段，模型用大规模互联网数据训练。CUA 专用数据通常以几种格式注入。

**一是 grounding 数据**——引导模型去学习在截屏中定位信息。这类数据通常长这样：一张截屏，加上一串边界框和对应的坐标。模型在这里要学的是：想点某个按钮，就得给出这样的 $(x, y)$ 坐标。给定截屏，模型通常被训练去预测一长串描述的下一个 token，本质上就是在预测页面上各元素的位置、这个标签卡在哪里——预测 $(x, y)$ 坐标，或者边界框的宽和高。

> **注意**：这类 grounding 数据非常容易大规模收集。比如这些截屏数据来自具体的网站，边界框和 grounding 很好生成，跑个 JavaScript 脚本就能提取出全部边界框。**这是非常嘈杂的数据**，但你可以想象能大规模拿到海量这种数据——而预训练正需要这种量大但含噪的数据。

**二是动作预测数据。** 同样从 HTML 页面里你可以拿到元素名称或元素元数据，把页面上某些东西喂给模型，让它预测对应的 $(x, y)$ 坐标。这更偏于易理解——给它一个 HTML 元素，它要预测想做什么、想点哪里。

这些其实都是非常底层的能力，就是在教 CUA 理解截屏、定位页面上的各种元素：学会理解截屏、学会定位，也就是知道元素在页面上的位置。它还能学到元素之间的关系，比如"租车按钮在酒店按钮右边"，这类关系可能会以某种方式进入预训练数据。这类数据通常大规模生成，混入前沿模型预训练的早期阶段，让模型之后学 grounding 和动作生成更轻松。

> **提示**：顺带回答一个被问到的问题——做预训练时，坐标表示能不能泛化？比如在 Mac 上训练，能泛化到平板或者分辨率不同的电脑吗？一般来说我们收集坐标数据的方式是做**归一化**：坐标不用绝对格式表示，而是用 **0 到 1000** 这样的范围，0 表示屏幕左上角，1000 表示屏幕右下角。坐标是完全归一化的，据我的经验，即使绝对分辨率不同，迁移效果也相当好。

#### 后训练：对齐人类演示

预训练之后通常进入后训练阶段。这一步现在通常和其他模型能力混在一起训练，但为了简化，我们先假设只关心 CUA。后训练的第一个步骤通常是做 **SFT（监督微调）**，让模型模仿人类演示计算机使用任务的过程。

**人类数据**怎么来？你付钱请一批人来标注轨迹。给个任务，比如"找一份 3 小时能做完的墨西哥炖肉塔可食谱"，然后由真人通过浏览器实际去完成。这里的例子来自 Mind2Web，他们收集了大约 **36,000 条人类轨迹**——每一步都记录截屏观察和人类的动作，最终你得到一堆"截屏、动作、截屏、动作"的轨迹。

开源的 CUA 数据集里，**Mind2Web** 和 **AgentNet** 这两篇论文本质上都是收集人类演示。这是训练 CUA 模仿人类行为的好方法，也就是让模型以截屏为条件，预测序列中的下一个动作。

**合成数据**现在也常混进来。一个很典型的方法来自 Mind2Web：把网站的 **accessibility tree**（无障碍树）喂给模型——就是我们前面提到的那个"元数据"，给模型元数据，它们的表现会好很多。他们先训练出一个用 accessibility tree 的模型，然后把简化的 HTML 表示给它，让它在 accessibility tree 的空间里 rollout 动作，并收集同样的一批轨迹。

这样你就拥有了一个**在使用特权信息的模型**——这些信息在实际评测和推理时是拿不到的——所以它比只用截屏输入时表现好得多。这个 rollout 模型收集了大约 **10.5 万条合成轨迹**。而且不是所有轨迹都会保留，你可以审视这些轨迹，按某种指标只留下质量较高的，比如用另一个 LLM 来评判，或者用人工来筛选。

> **结论**：轨迹的收集无非两条路——要么靠人类演示，要么靠合成数据。而这种"用特权信息做合成数据"的方式，我很喜欢一个类比。我不确定是不是真的，但我听说 **Tesla 在训练阶段部署了装有 LiDAR 的车**，这些车显然是在做自动驾驶，有三维 LiDAR 信息时表现会好很多；他们收集这些轨迹，然后**丢掉 LiDAR 信息，只训练模型使用像素信息**。相当于有一个老师，用的信息比推理时能拿到的要好得多。我觉得很多计算机使用 agent 的应用里，大家也试过注入元数据或额外信息来收集更好的轨迹，所以这是引入合成数据的一个很好的方式。

#### 强化学习：把它丢进沙盒里自己撞墙

最后一个阶段是后训练中的 **RL**。这个阶段一年前还不常见，但现在 CUA 普遍都会经历。

具体做法是：把 CUA 放进模拟环境（或真实世界）里，给它一件事做。比如试着去买那个蓝色马克杯，奖励可能来自 rubric 评分细则、来自验证器，或者让一个 LLM 当裁判——总归用某种方式给它奖励，然后做强化学习，去强化那些成功的轨迹。

> **结论**：这挺有意思，因为这些任务**没有人类演示**。你就是把模型放进沙盒里放开跑，它尝试各种做法，从成功和失败中学习，不断重复，直到它能成功完成任务。现在大家对 RL 都非常兴奋，但其他阶段也很重要——它们保证模型有扎实的基础去做 RL。

具体到更新规则：把模型部署好，让它在模拟环境里执行动作，结束时你会从环境或某个裁判那里得到奖励，然后根据奖励更新策略。大体上，**如果奖励是正的，你就把那条轨迹里的动作权重调高一些；如果奖励是零或负的，就调低这些动作的权重**。所以模型本质上是在学习最大化环境中的奖励，而这个过程完全自主，不需要人类演示。模型尝试的任务可能来自人类，但它的运行方式通常是完全自主的。

> **易错点**：这也解释了你为什么会需要模拟环境。很多任务我们并不想在真实世界里反复执行——比如你在 Uber 上订机场接送，订几次就会被封号，或者钱就花光了。所以强化学习必须跑在模拟环境里。

这张图说明了 RL 环节对形成强大的 CUA 能力有多重要：**SFT 之后成功率大约是 0.5，做了强化学习之后最终能爬升到 0.6 左右，甚至更高**。这是 CUA 训练中很关键的一环，而且据经验，它还能带来单靠人类演示很难学到的能力——用强化学习训练模型处理长时程任务会容易得多，因为你通常没有超长任务的人类演示，收集起来成本太高了。

### CUA 和别的 agent 到底不一样在哪

CUA 和这门课里其他 agent 最大的不同，是它**直接在和人类相同的界面上操作**。这一点既让它格外有用，也让它格外难评——评估 CUA 很棘手，人们也探索了一段时间，关键是要选对指标和行为层面。

它的建模方式也很特别：是一种**跨模态的设计，从交错的视觉历史中预测动作**。上下文里交错着截屏和你之前执行过的动作，模型要基于这些生成下一个动作。

训练上则分成多阶段：先用大规模含噪数据做预训练，然后用 SFT 对人类或合成演示做行为克隆，最后是 RL 阶段，让模型在模拟环境里自行探索，好的行为给奖励、坏的行为给惩罚。

至于接下来往哪儿走，我建议大家去看看幻灯片，里面还有一些我对 CUA 未来可改进方向的想法：**速度**仍然是个问题；**个性化**是很有潜力的研究方向；**基础设施和用户体验**也是大问题。我自己对**多 agent 系统**也很期待。
