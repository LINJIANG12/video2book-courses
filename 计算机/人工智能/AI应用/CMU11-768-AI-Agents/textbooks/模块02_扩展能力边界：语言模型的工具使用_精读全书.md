## 一台只会猜下一个 token 的机器，是怎么学会办事的
> 对应块：BLK02 | 覆盖分集：P02 | 块标题（分集名）：《02｜语言模型智能体的工具使用【中文配音版】》

### 工具到底给了语言模型什么

欢迎来到第二节课。今天讲语言模型的工具使用——这是 Agent 最根本的能力，也是它们区别于语言模型的地方。

基本思路其实一句话就能说清：**所谓工具，就是语言模型调用外部计算机程序的一个接口。**而语言模型自己做不到这一点，因为它本质上就是一台预测 token 的机器。有了工具，你能做的事一下就多多了：搜索、计算器、浏览器、Python、任意 API。

大家会看到，工具调用的**方法**是标准化的，但调用之后下游怎么用，可以非常不同。

工具有基本上两大好处。这些内容来自我发布在网站上的阅读材料，想深入了解的可以去读，那是一篇综述，是我和 Daniel 还有我们的学生 Zora Wang 一起写的：

- **拓展语言模型的能力**——让语言模型能做一些它本质上做不到的事，比如访问超出它动作空间的信息或操作；
- **辅助语言模型**——这件事语言模型本质上能做到，但如果不让模型亲自做，会容易得多。

> **定义**：工具的两大类别——「拓展」与「辅助」。前者是做不成的，后者是做得成的但费劲。

这里其实已经有个例子了。语言模型本质上做不到的，是知道四个月前的时间之类的：它看到最新的信息就是四个月前的，而且参数已经冻结，不调用外部函数它不可能知道。

属于「辅助」这一类的例子是：如今语言模型其实算数学算得相当不错，但比调计算器慢得多，因为它们得一步步推理。你让它做乘法，算两个七位数相乘，它要花很久；计算器一下就算出来了。这就是这两大基本类别。

再往深处讲一点，你还可以用它查实时信息——好处是能为你的回答提供新鲜的依据；用计算器或 Python 做精确计算，执行起来比语言模型自己算更可靠、也更快；访问私有状态，也就是让模型拿到用户的信息，从而根据用户的状态来回应；或者改动你的外部环境，比如浏览网页、调用 API。

### 你现在拿 ChatGPT 做什么，就需要什么工具

想想 ChatGPT 刚出来的时候，真的就只是文本进、文本出，它唯一能做的就是用文字回答你的问题。现在它差不多是个万能应用了，能做很多不同的事情。

那你们现在用 ChatGPT 最多的场景有哪些？我们现场收集一下。

> 好，写代码。那这种需求需要什么工具呢？
>
> 等等，那不是 ChatGPT，对吧？那是 Cursor 或 Codex。在 ChatGPT 界面里，他们能用 Blender——就是渲染出 Blender 的东西。举个例子，既要执行代码，还要用合适格式把它展示出来。

> 还有别的吗？
>
> 好像有同学说了生成图片。对，这就是调用图像生成工具。还有其他的吗？
>
> 另一种是推荐产品，比如推荐个搅拌机。你觉得需要什么工具？可能要通用网页搜索，或连 Google、Amazon 的 API。

还有什么更奇怪的吗？有没有让你惊讶的 ChatGPT 能做的事？

> 对，它能很好地抓取多个网页和最新信息。你给它一堆乱糟糟的文件，它能给你生成 PDF。对，它渲染 LaTeX 很好——我其实不确定这是工具还是前端界面的事，可能只是在浏览器里渲染。它生成 PDF，那这就是工具了，很棒。还有能跟 Slack 之类的交互。

最后那一条属于另一种专用 API。各种各样的事都有。

### 我认为最典型的那些工具

我把这些大致归成了一份清单，是我认为最典型的工具，其他大多数工具也都能归进这几类。

#### 文本回复：最无聊的一种

这是最无聊的一种，直接给你个答案。在 Agent 循环里有两种实现方式。

顺便说一句：ChatGPT 现在已经是个 Agent 了。它不只是聊天应用，它会对你的问题做迭代式的工具调用——所以是 Agent，这差不多就是 Agent 的定义了。

两种实现方式：一是设置一个 finish 工具，意思是「好，我跟用户的交互结束了」，我就收尾并输出一段文本；另一种是 Agent 决定不调用工具，就直接结束循环。这算是最简单、最显而易见的一种。

#### 搜索网络：RAG 没死，只是隐形了

另一个极其常见的例子——这些都是工具，理论上都能看作 API，不过我想再细拆一下——还有一种是搜索网络，也就是从各种不同的来源拉取信息。

有多少人听过「检索增强生成」？上过这里 NLP 课的人应该都听过，应该有不少人。那有多少人听过「RAG 已死」这种说法？人数还挺多的。语言模型圈里一直有争论，说检索增强生成是两年前的老古董了，没人理会了。

而我的观点是：**检索增强生成——就是先检索上下文、再基于它生成答案——已经变得太普遍了，大家甚至意识不到自己正在用它，所以它活得好好的，反而让人觉得它死了。** 但基本上，搜索网络、检索信息、再基于它生成答案，如今在这些应用里已经是标配了。所以这也是几乎所有聊天界面都广泛提供的一种工具。

#### 代码执行

还有一种是代码执行，就是丢进去一段代码，让它做计算或者类似的任务。做计算非常好用，还有我们前面讲到那些场景——既要执行代码，又要用合适格式展示出来，全靠它。

#### 图像生成：查询词会被大幅扩写

另一个常见的是图像生成工具，这在 ChatGPT 里显然也是很热门的用法。

这个有点不一样，因为前面讲的那些工具基本上都是跟文本打交道的，而这里它是跟图像打交道的。有个有意思的地方：你注意到这里实际用的查询词和你输进去的不一样。比如「一幅水彩，机器人在图书馆里学习」，送进图像生成器的查询词是不一样的。

> **提示**：调用图像生成很关键的一步，其实是决定往里面放什么查询词——所以语言模型调用图像生成 API 之前，会大幅扩写查询词。我不确定现在在 ChatGPT 里还能不能看到这个，但以前你下载图片时，会发现它的说明文字跟你给的完全不同，这样你就能间接看到图像生成器实际发给图像工具的查询是什么。

#### 自定义函数

接下来还有各种自定义函数。比如说「帮我买香蕉、牛奶和咖啡」，它可以帮你生成购物车，然后调用 Instacart 的 API 来完成。

这些工具你想怎么玩都行，想加哪个就加哪个。

### 代码是一种元工具

思考工具调用有很多不同的角度。第一种理解方式就是很简单的：给 Agent 一份列表，里面有 50 个或 70 个 API 函数供它交互，它就可以调用这些 API。这样做的话，基本就是每一步调用一个 API，或者用并行工具调用一次调用多个。

不过代码是一种比较特殊的 API，因为代码的表达力极强——你可以把代码看成一种元工具，对吧？

比如「面包师烤了 200 个面包，还剩多少个面包？」这个问题，听起来简单，但它其实是在调用一个赋值工具、调用赋值工具、再调用减法工具、再调用赋值工具，诸如此类一直下去。

本质上，很多人修过程序员课、或者对程序员有些了解的话，基本上你可以这样表达：**每段代码都是由这些函数调用构成的一棵树。**

```text
  200 ──赋值──► bakeries
  50  ──赋值──► sold
              │
              └──减法──► (bakeries - sold) ──赋值──► remaining
                     │
                     └──还可以是循环 / if / 函数调用 ……

  树里还能有循环和其他控制流，所以它本质上是一种非常丰富的
  调用工具的方式。树的每个叶子都是一次具体调用。
```

而且它还能引入外部库——这些库就成了你拉进系统里的自定义 API。你看，一旦你调用 Pandas，就等于打开了 Pandas 里的所有工具，对吧？另外你还可以构建自己的工具函数，随时调用你想要的各种专用函数。

代码确实很特别，它的特别之处在于它和其他工具不同，能让你以全新的方式调用工具。而且确实有研究工作证明了这种方式非常有效。

我们现在基本把它当成理所当然，但三四年前我们调用工具还不是这样的——那是我们刚开始用 LLM 构建 Agent 的时候。当时的标准做法是：拿到一个查询，比如「确定买某款手机在美国、日本、德国和印度四个国家里最划算」，然后你就得一步步反复执行：调用查询汇率工具查德国，再调用手机价格查询工具，然后调用文本转换工具，接着再查一次汇率，再查一次手机价格……这样来回折腾，才能最终得到结果。

但如果写代码，你只用写一个程序就能完成了。这样调用工具的方式更丰富，也更高效。

这个方法叫 **CodeAct**，有一篇相关论文。论文的核心结果基本上是：成功率上升了，平均交互轮数也下降了。而且这甚至包括了那些传统上不需要代码的任务——这些任务原本被视为普通工具使用任务，但代码就是完成它们的好载体。

### 为什么不是事事都用程序化工具调用

但人们并不会事事都用程序化工具调用，这是有原因的。这在很大程度上取决于你想给 Agent 多大的权限。

代码能力很强、表达力丰富，还给你循环、变量和函数库，这很好。但代价可能是什么呢？大家有什么想法吗？

> **循环和变量**：对，它可能会卡住，它可能写出死循环，那你就得在系统里处理死循环，对吧？这就有点烦了。
>
> **库呢？库有什么问题？**
>
> 对，安全问题算一个，还有版本管理之类的。我不确定大家熟不熟悉，现在网络安全领域 Agent 的一大问题就是：Agent 会引入已被入侵的库，Agent 被攻破了，整个系统也就被攻破了，所以这点要非常小心。
>
> **代码的行动空间很大，也更难约束。** 所以更难做验证，也更难得到可预期的行为。
>
> **它们的影响也更大**，会占用更多内存、磁盘、CPU 之类的资源。

> **注意**：正因如此，安全那节课我们会细讲——一旦用上程序化工具调用，你就得考虑沙箱，考虑怎么把 Agent 关在里面之类的问题。

### 工具调用是怎么表达出来的

接下来我想讲讲提供工具的机制。现在每个语言模型调用工具都挺熟练的，但这件事并不是理所当然的。

基本上，工具调用是以 token 的形式表达的。比如文本续写「天气晴朗」，而工具续写就像一次工具调用，里面会有 `get_weather` 之类的函数，而且两者经常出现在同一个输出里。

还记得 ReAct 吗？就是之前讲过的那个，我可以直接在黑板上画一下。ReAct 的结构大致是这样：上面是文本部分，然后是工具调用，工具调用写在下面；然后模型一边发起工具调用，一边给人回复，是边发起工具调用边回复。

```text
  文本（thought + 给用户看的回复）
        │
        ▼
  工具调用  ──►  工具执行  ──►  观察 Observation
        ▲                                    │
        └────────────────────────────────────┘
                  回到下一轮补全

  这样 ReAct 循环就不再用分开的代码来表达了，
  而是表达成一次完整的补全输出。
```

如果你用的是推理模型——就是能做推理、有很长推理链的那种模型——前面可能有思考 token，然后是消息，最后是工具调用。

```text
  ┌────────────────────────────────────────────────┐
  │  思考 token   非常冗长，不会展示给用户          │
  ├────────────────────────────────────────────────┤
  │  文本/消息    简短一些，展示给用户               │
  ├────────────────────────────────────────────────┤
  │  工具调用     那里实际的输出                     │
  └────────────────────────────────────────────────┘
```

#### 词表里必须先有这些 token 吗

有个同学问了个很好的问题：工具调用的 token 必须在预训练时就在词表里吗？

答案是：这些服务 token 都会在词表里——但答案可能是否定的。

我把问题重复一遍：这些 token 在预训练时就**必须**在词表里吗？通常来说，如果你是在整个互联网上做预训练，词表里不一定非得有这些 token。有些情况下你可能也会加上，但更常见的做法是在**中期训练**阶段引入它们，也就是介于预训练和后训练之间的那个环节：在这个阶段，你用中等规模的数据，按你想要的格式来训练模型。之后你可能还会做强化学习，但在整个互联网上预训练时不一定有它们。

#### 聊天格式、工具 schema 与各家方言

这部分内容对大家来说应该比较眼熟——之前在自然语言处理之类的课程里实现过东西的同学都见过。如果你用聊天格式，比如 OpenAI 的聊天格式，里面就有系统消息、用户消息、助手消息这些。然后这些消息会以类似 JSON 的形式表示，比如你在 Python 里调用模型的时候就是这样。但这些会被转换成带特殊 token 的形式：系统消息这里，这就是一条系统提示词，然后是要简洁之类的内容。所以每条聊天消息都有特殊 token。

工具基本上就是给请求增加了一个结构。比如你有这样一个工具定义，它告诉你这是一个函数，函数名是 `get_weather`，参数是 `city`，类型是字符串，而且这是必填的。这个 schema 会传给调用 OpenAI 时使用的 chat completions 函数。

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "parameters": {
      "type": "object",
      "properties": {
        "city": { "type": "string" }
      },
      "required": ["city"]
    }
  }
}
```

所以当 prompt 里有类似内容时，这个定义会出现在 prompt 的 `tools` 部分，输出最终就是类似 `name` 是 `get_weather`，再带上合适的参数，比如城市是 Pittsburgh：

```json
{ "name": "get_weather", "arguments": { "city": "Pittsburgh" } }
```

有意思的是——你可能不会做预训练，但至少从中训练开始往后，你都要训练模型去适配**某种特定的工具调用格式**。而每个模型的工具调用格式都不一样，也许不是所有，但很多都不同：

- **Qwen** 用 `<|im_start|>`、`<tool_call>`、`<|im_end|>` 这样的标记；
- **Mistral** 用 `[TOOL_CALLS]` 列出所有调用；
- **DeepSeek** 有自己的 DSML 标记语言做函数调用——他们不叫工具调用，叫函数调用，用 `<invoke>`。

这些格式基本上都能用。如果用同样的数据和同一个模型训练，哪种格式性能更好差别其实很小。你需要知道的是：**这些格式各不相同**，不能想当然地认为适用于 DeepSeek 的解析代码换个 Qwen 也能用，反过来也一样。

> **易错点**：如果你在做微调，从已训练好的模型出发，一定要匹配它的工具调用格式，别让它做没训练过的事。好在 Hugging Face 里都用 `apply_chat_template` 函数实现好了，套用现成的 chat template 就行。如果实现得不完善，你可以进去提个需求让他们补上，或者自己动手——总之现在这套已经标准化了。但我希望大家了解这背后的机制，因为不了解的话就会出错，模型可不会给你好脸色。

### 从模型的输出到真正执行

那完成这一步之后，下一件事就是工具调用解析。这个我放到下一节再细讲，这里先不展开。

但我们先假设：语言模型输出的内容，你有办法把它解析成函数参数。然后在初始化时注册这个工具，还要有一个解析机制让你得到一个映射，从名字映射到你要执行的工具。大多数 Agent 框架都提供添加新工具的方式：每个工具有自己的名字，对应一个 Python 函数之类，Python、TypeScript 都行。调用时就会带上相应参数，分发到那个函数。

所以每次的流程是：

```text
  模型输出
     │
     ▼
  解析 ──► 查找工具（名字 → 函数的映射） ──► 按参数校验
                                              │            │
                                          失败 ▼            ▼ 成功
                                    模型给了错误的调用     执行函数
                                                            │      │
                                                       失败 ▼      ▼ 成功
                                                 形式没问题但    观察结果
                                                 运行时才失败          │
                                                             带调用 ID 一起返回
```

在**校验阶段**就可能失败，比如模型给了你错误的工具调用。在**执行阶段**也可能失败——有些调用虽然形式上没问题，但实际上仍然是无效的。比如你有个执行 Python 的工具，它可能接受任何字符串当 Python 代码，但真正运行时可能失败。之后无论它成功还是失败，你都会得到一个观察结果。

这里还有一个细节，实现 Agent 时如果搞错了，它会很有帮助，但也会非常烦人：**基本上每次工具调用都会被分配一个 ID。** 当你运行它时——不管是由语言模型的推理代码还是 Agent 代码来跑——然后你会得到一个结果，而结果会带有匹配的调用 ID。这在并行工具调用的场景下特别有用，我待会儿会讲。有了 ID 的对应关系，你就知道哪个工具调用对应哪个结果。

> **易错点**：但问题在于，比如说 Anthropic，如果某个工具调用没有匹配的工具结果，它会直接报错挂掉。它会告诉你这是无效的历史——「我不会接受这种历史，也不会再为你生成任何输出。」 根据我的实际经验，有时候 assistant 刚发出一个工具调用，突然你的程序挂了，或者出了类似的状况，结果没写出来；恢复之后把这段历史原样发回去，Anthropic 会拒绝。记住这点。

（有人问工具调用是异步的吗？这个我下一节会讲。）

### 格式永远可能是错的

接下来是一个在技术上、算法上都很难的问题，它可能让你很感兴趣，也可能完全不感兴趣。但如果不感兴趣，你就庆幸有人替你解决这个问题吧。

**语言模型生成的工具调用绝对不保证格式正确。** 这就是一个例子——你能看到这一段 JSON 少了最后一个右括号：

```text
  {"name": "get_weather", "arguments": {"city": "Pittsburgh"}
                                                       ↑ 少了这个 }
```

这是格式有问题的 JSON，放进你的 JSON 解析程序，它会抛出异常，你也提取不出数据了。我见过无数人去检查是不是缺了括号，然后事后补上一个——但你真不该这么干，这么做一点也不好玩。

其实你可以给每个工具调用设定一系列约束条件。

#### 三层约束：语法、结构、类型

第一个是**语法**：必须是合法的 JSON，这算是最基本的要求了，首先得能解析。第二个是**结构**：如果有预期字段或必填字段，就必须把它们都填上。第三个是**类型**：比如城市这个字段，它必须是字符串；如果是数值，单位也得是正确的单位。

这些都能用 JSON Schema 表达，或任何 Schema 库也行。比如这是一个城市字段，类型是字符串，单位可以是摄氏度或华氏度，而且城市是必填的。

这样做的好处是：它有机器可读的验证规则，你可以据此检查一次调用是否符合 Schema。

#### 从正则文法到下推自动机

而要表达一个 Schema 是有效还是无效，一种办法是在它之上定义一个**文法**。有多少人学过上下文无关文法或者类似的内容？比如正则文法这类的东西，有多少人懂正则表达式？——好，很多人。正则表达式就是一种正则文法。有人知道怎么去解析一个正则表达式吗？——终于有人答了，**有限状态自动机**，对，完全正确。

有限状态自动机可能有些同学不太熟悉，它大概是这样的一种东西，它看起来有点像这样：

```text
              a                 b 或 c
   q0 ─────────────► q1 ────────────────────► q2
 （起始状态）      （读到 a）                （读到 b 或 c）
```

它处理的是一种叫正则文法的东西。像 `.*` 这类你用来搜索文本的正则表达式，都可以用正则文法来表达。

但 JSON Schema 是无法用正则文法表达的，它可以用一种叫**上下文无关文法**的东西来表达。上下文无关文法基本能构建出一棵类似这样的树，所以每个 JSON 表达式两侧都可以有括号，成员之间可以有逗号，这里可以是一个字符串，这里可以是一个单位：

```text
  schema  ::=  "{"  members  "}"
  members ::=  member (","  member)*
  member  ::=  key  ":"  value
  key     ::=  STRING
  value   ::=  STRING | NUMBER | units
  units   ::=  "C" | "F"          ← 不含 "K"，到这里就构建失败
```

如果 JSON Schema 格式正确，你就能构建出一棵完整的树；如果 JSON Schema 格式不对，你或许能构建出大部分的树，但到了单位这一项——单位不能是 K，基本上就构建失败了，尽管单位其实可以取 K，但我们定义成不接受开尔文作为温度单位。

所以基本上，**只要你能用 JSON Schema 定义的上下文无关文法来解析工具调用，就能做到这一点。** 细节我就不展开了：有限状态自动机解析不了上下文无关文法，但有个叫**下推自动机**的东西可以做到。它是在正则文法的基础上加了一个栈，你把内容压入栈，再从栈里弹出，最终就能判断输出能不能被解析。

```text
  从下推自动机的起始状态出发，在从左到右生成输出的过程中，
  同步验证它：

    生成一个 token ──► 查文法，合法？ ──► 压栈 / 弹栈 ──► 下一个 token
                          │
                          └── 不合法 ──► 该 token 直接出局

  全部生成完 ──► 栈必须正好见底，且处于接受状态
                 ＝ 这一串输出能被这个文法解析
```

#### XGrammar：一边生成一边查文法

这里我用 XGrammar 来举例。XGrammar 实际上被广泛用在各种 LLM 推理库里，它其实是机器学习系的人开发的。

所以这意味着每一次语言模型的运作都是如此：要预测下一个 token 的 logits 时，你就查一下文法——如果文法说这是合法的下一个 token，就记 1 分；如果是不合法的下一个 token，就记 0 分。

```text
  原始 logits:  [z₁  z₂  z₃  z₄  z₅  z₆]
                合法 合法 非法 合法 非法 合法
                    ↓  把不合法的置为 -∞
  掩码后:      [z₁  z₂  -∞  z₄  -∞  z₆]
                    ↓  重新归一化
  分布:        只在合法 token 上有概率，非法 token 概率为 0
```

写成公式就是：

$$p(t \mid \text{prefix}) = \frac{\exp z_t \cdot \mathbb{1}\!\left[t \in \mathcal{V}_{\text{legal}}\right]}{\sum_{t' \in \mathcal{V}_{\text{legal}}} \exp z_{t'}}$$

这样就又得到了一个合法的分布，概率只落在合法 token 上。这就能保证你生成合法的输出。

这是 XGrammar 论文里的另一张图，他们做了一些巧妙的处理：有些 token 永远有效或永远无效，这些可以预先算出来；还有些 token 只在某些上下文中才有效，只在特定的栈上下文里有效，这些就得实时计算。如果你喜欢算法，这非常非常有意思；就算不喜欢，也该庆幸机器学习系的人在替你做这件事。

正因如此，只要你启用了这个功能，并设置好相应的 JSON Schema，几乎总能得到格式规范的工具调用。

#### 快速小测验：token 用完了

这很棒，但**有一种情况是做不到的**，就算有这些手段也拿不到规范的工具调用。

我来出个快速小测验，这题非常非常难，不知道有没有人能答出来。有人想得到什么情况下连这都不够用吗？可能得对大语言模型很熟悉才行。

> **答案**：当 token 用完的时候。模型只能生成固定数量的 token，你可能还在自动机的合法路径上，但没走到最终状态，于是只生成了一部分 JSON 就输出了。

答得很好。我自己其实就遇到过这种情况。理论上有办法解决：就是数一数还剩多少可输出的 token，然后提前截断。不过——如果有人想在 XGrammar 里实现这个，可以当附加分作业，我很乐意看到。

### 把工具交给 Agent：编程调用、REST 与 MCP

接下来我们讲 REST API 调用。表达工具有几种不同的方式，我想大多数人应该都已经熟悉 REST API 了，这是大家和网页服务交互的方式。

不过，抱歉，其实还有别的调用 API 的方式。

#### 编程式工具调用：一个 .py 文件就是全部

一种是**通过编程工具调用**：基本上就是给模型一个 Python 程序，让它用这个程序里的东西来调用工具。

你可能会写一个 `weather_lib.py`，放着 `get_weather` 函数，带上 `city` 和 `units` 参数，说需要时就调用它；再给它执行 Python 的能力，就能调那个工具了。

编程工具调用可行，但这样**没法远程调用**，而且也没法通过你平时使用的标准工具调用方式来调用——不用编程工具调用时那种标准方式。

有办法把它转成 REST API。有人用过 FastAPI 吗？这是个很常用的库，很多人用过。

#### FastAPI 与 curl

FastAPI 能让你极其简单地搭起一个网页后端：基本上你只要建一个 FastAPI，提供一个 API key 让用户来验证，再写个 Python 装饰器，`weather` 就变成了这样。

这样做有几个好处：

- **第一个**，如果你不想让别人查看天气，就可以阻止他们。但更重要的是，如果你不想让人拿到你的个人数据之类，就可以要求 API key——这样就能挡住所有没有合适 API key 的人。
- **另一个**，它能免费给你一个 JSON Schema。我说「免费」其实是 FastAPI 实现好的功能，但你的整个 API 都能表示成 JSON Schema，原样提供给语言模型，模型就能用它来指定哪些调用是允许的。然后你可以处理这个 Schema，每当 Agent 发起工具调用，就发给你的 API 服务器执行。

调用这些 API 的另一种方式就是直接用 `curl` 命令——`curl` 基本上可以让你像这样直接调用这些 API。所以如果 coding agent 能访问 bash，就能像这样调用。

> **提示**：如果你还没玩过 FastAPI，它挺好用的，上手很容易。我之所以先讲这个，是因为这算是 Agent 出现之前的**传统编程方式**。

#### MCP：初衷、架构与那把「无害的钥匙」

有个东西叫 **MCP**，就是 Model Context Protocol，大概是两年前或者一年半前由 Anthropic 推出的。它的设计初衷是提供一种标准方式来给你的模型补充上下文。

我第一次看到它的时候，其实心想：为什么我们需要这玩意儿？我搞不懂为什么要这样做，让我们的 Agent 直接调用 API 不就行了？

不过确实有一两个重要的点，让 MCP 和直接调用普通 API 不一样。我先解释一下，为什么我当时没意识到——就是我觉得它其实没必要存在。

原因基本上是这样的：每次你搭建一个 MCP，你要做的就是有一个 AI 应用，然后再配置几个、设置几个 MCP 客户端。比如这是你的天气客户端，这是你的天气 MCP，还有 GitHub MCP 之类的。这样就能查天气，还能推送到你的 GitHub 上。

```text
   AI 应用 / Agent 进程
         │
         │  持有 MCP API 密钥（相对无害的那把）
         ▼
   ┌───────────┐        ┌───────────┐
   │ 天气 MCP  │        │ GitHub MCP│
   │  服务器   │        │  服务器   │
   └───────────┘        └───────────┘
         │                    │
         │  持有上游 API 密钥   │  持有 GitHub token
         ▼                    ▼
    天气服务 API          GitHub（Agent 永远拿不到 token）
```

我当时觉得没必要，是因为：调用 API 还需要跑个程序吗？调用 API 有很好的方式，直接发给 REST API 就行了。

好，这算是稍微岔开一点话题。稍后我会回到这个点。先插一句，有个很好用的库叫 **FastMCP**——FastMCP 基本上就是 MCP 版的 FastAPI。所以你想为任何东西创建 MCP 服务器，只要把 FastAPI 换成 FastMCP，就能非常轻松地搭出来。你还可以拿 REST API 生成的 spec，直接转成一个 MCP。

这就是你可能想用 MCP 的主要原因：**相比普通 API，它给你多加了一层安全保障。**

- MCP 有自己的 **MCP API 密钥**，这个你需要提供给运行 Agent 的那个进程；
- 除此之外还有**上游 API 密钥**。比如你让 Agent 连接你的 GitHub，上游 API 密钥就是 GitHub token——给 MCP 服务器，**不给 Agent**；
- 而你给 Agent 的，是 MCP API 密钥，用它来登录 MCP 服务器。

> **定义**：凭证分层的思路——Agent 只拿一个作用范围受限的临时凭证，真正的长期凭证留在 MCP 服务器那一侧。

这么做重要的原因在于：如果你把 GitHub token 给了 Agent，而它突然觉得把这个 token 推到你的公开仓库是个好主意，那会怎么样？你的账号会被入侵，所有仓库都可能被装上恶意软件。所以你要给 Agent 一个**相对无害的东西**——这样即使它因为某种原因泄露了，泄露本身也无伤大雅，真正的凭证依然安全。这基本上就是它背后的设计初衷。

简单总结一下，这两种方式都能让你给 Agent 添加一组 API，但很多其他方面是不一样的：

| 维度 | 普通 API（JSON Schema 直给） | MCP |
| --- | --- | --- |
| 工具发现 | 可能得去获取一份 OpenAPI 文档 | 有专门的 API 可以列出所有工具 |
| 调用 | 调用的是一个 HTTP 接口 | 有自己的传输层，方式多种多样：标准输入输出、socket 诸如此类 |
| 认证 | 往往是上游凭证直接暴露 | MCP API 密钥 + 上游 API 密钥分层 |
| 额外能力 | —— | 还可以添加资源、prompt 和扩展 |

这里不展开细讲。

#### 插一句：MCP Registry

其实还有两件事我想提一下，我猜是忘了把它们加进幻灯片了。

第一件是 **MCP Registry**，就是官方的 MCP 注册中心。如果你想找到能实现这类功能的 MCP，可以去这个注册中心——能找到数量非常多的 MCP。还有一大堆 MCP Server 网站可以访问，它们都是按排名排列的，受欢迎程度之类的内容。

第二件纯粹是插曲：我一直在讲匹兹堡的天气。有意思的是，今天——这些幻灯片我当然是提前准备好的，但今天匹兹堡的天气真的同时又是雨天又是晴天。结果我把 API 搞挂了，它没法同时返回多个天气。不过这确实挺巧的，你能同时看到倾盆大雨和明媚的阳光。

好，回到正题。

### 并行工具调用

最近另一个重要进展就是并行工具调用。

它要解决的基本问题，和我讲 CodeAct 以及程序化工具调用时说的一样：**工具只能一个一个地调用。** 哪怕是很简单的操作也会变得很长，因为你可能先查个天气，再看一眼日历，然后查个航班。但如果这些工具调用互相独立，你就可以同时发起调用。做法很简单——你只需要添加多个工具调用就行了。

这里有几个需要注意的细节：

- **第一个，只有当工具调用之间没有依赖关系时，你才能并行执行。** 比如查匹兹堡的天气、读今天的日历、查航班状态，这几个并行就挺好。但如果要先找客户 ID，再查订单，然后退款，那显然不能并行。所以并行工具调用是有上限的。如果你的日历或航班依赖天气，那显然也会有问题。
- **你会不会真的并行执行这些工具调用？** 答案是通常会。你可以用常规的 Python 语法写一堆工具调用，然后执行它们，再用 `asyncio.gather` 这类方法，在它们同时运行时把结果返回回来。这种做法很常见。

另外我想指出一点，这也是**高效的语言模型和低效的语言模型之间的一个重大区别**。现在 Agent 语言模型里有一个很奇怪的悖论：**按任务逐个衡量的话，更贵的模型实际上可能更省钱。** 这有两个主要原因：第一个，更贵的模型可能更聪明，能更快选到合适的解决方案；另一件事是，更新的模型并行工具调用做得好得多，能同时发起一大堆调用。

所以如果你在用编程 Agent 之类的工具，用一些更好的模型，你会发现它们同时查看一批图片，或者同时写一堆不同的文件——这就是因为它们并行工具调用做得好。

有人知道它们为什么在这方面进步这么大吗？虽然并行工具调用机制早就存在，但直到大约半年前这都不是个大事儿。

> 是强化学习逼着它们这么做的。对，没错，强化学习算是逼着它们这么做了。
>
> 因为模型被强烈激励着要尽快完成任务，而并行工具调用正是好办法之一。所以如果你在强化学习时对任务执行时长施加重惩罚，就能得到多得多的并行工具调用。

### 怎么评估工具用得好不好

今天这节课最后我想讲的是评估工具使用。

我先不讲怎么评估端到端的 agentic 任务，而是先讲语言模型工具使用能力的评估——因为这是语言模型做好 agentic 任务的前提。

这方面有不少数据集，最著名的是 **Berkeley Function Calling Leaderboard**。它有四个版本，最初从第一版起步，第一版基本上就是单轮工具调用。经过四个版本的演进，现在它涵盖了多轮工具调用，它也有 agentic 工具调用——但这更多是工具调用型 Agent，而不是端到端的编码 Agent 那种。他们还测工具调用的**鲁棒性**，比如参数的幻觉。他们也测**格式敏感性**，就是刚才讲的那些不同格式，榜单里有相关指标。

那么，当你要去评估整个技术栈时，有几件事需要评估：

| 维度 | 具体看什么 |
| --- | --- |
| 工具选择 | 有没有为任务选对合适的工具——它可能选了个不合适的工具，根本没法完成这个任务 |
| 参数 | 填的值对不对 |
| 执行顺序 | 如果是 agentic 工具调用，看执行顺序对不对 |
| 端到端 | 端到端的任务准确率 |
| 效率 | 多快能完成任务，花了多少 token、成本多少 |
| 可靠性 | 工具调用超时了会不会合理地重试？某个工具出故障了，它能换一个吗？ |
| 安全性 | 存在对抗性输出、让它以不当的方式使用工具时，它还能正确处理吗？ |

这些都是这个榜单里的指标。这个基准经过四次迭代，覆盖了以上所有维度。

### 同一个模型，换个服务商就差 15%

还有一个非常有趣的基准，是 OpenRouter 的工具调用错误率基准。在座有人用过 OpenRouter 或见过这个吗？——可能没有。

好，这是针对**同一个模型**的测试，所有条目唯一的变量是：**由谁来给你提供这个模型**。

这一点显然很重要，因为你会想：我要用这个模型，可能觉得不管谁提供效果都一样。但实际上差距从 **15%** 一直到 **0.01%**，最低到 **0.005%**。有人知道为什么会这样吗？——课上有提过一些线索，也有一些没提到。对，说得很好，我再说一遍。

**第一，各家用的解码或推理算法可能不一样。** 一个很大的差别是他们用不用模型量化，或者用的量化精度是多少。我自己的经验是 FP8 模型——FP8 差不多是模型量化的默认精度——比 FP4 模型的工具调用错误少得多。因为 FP4 压缩得非常狠，是帮推理服务商省钱，但模型通常也更差，能保持同等性能的 FP4 量化方案并不多。

**还有一个是投机解码。** 这门课应该不会花太多时间讲投机解码，也许讲到长上下文的时候会提；其实还有一些专门为 Agent 设计的算法，挺有意思，到时也许可以讲。简单说，投机解码就是用一个更便宜的小模型去预测大模型接下来要输出什么，用它来加速推理。无损的投机解码按理说不该造成差别，因为它的输出本来就是一样的，并不改变模型本来的输出结果；但如果用的是**有损的投机解码**，结果就可能不一样了。不过那样的话，还把它叫同一个模型恐怕也不太合适。

**还有另一个原因我之前提到过**——有人猜到是什么吗？其实今天课上刚刚讲过。怎样才能让工具调用更成功？——对，**约束解码**，完全正确。所以这些不同的服务商用的约束解码算法可能各不相同。实际操作中，很多提供商都会自己实现自己的推理算法，也就是从零开始完整写一套自己的推理算法；有些提供商会用 vLLM 或 SGLang 这类开源方案，而 vLLM 和 SGLang 支持不同的语法解码算法，所以有些提供商可能压根就没实现这个。这样一来，他们就完全靠语言模型自己把工具调用做好，否则就可能出错。

工具调用失败的最后一个比较无趣的原因是：推理提供商可能不稳定，有时候会宕机，工具调用就失败了。

### 这套东西是怎么叠起来的

好，今天要讲的主要内容就是这些。**工具使用基本上是一个分层系统。**

```text
  工具 schema ──► prompt 的 tools 字段 ──► 模型发出工具调用
                                                  │
              约束解码（语法 / 结构 / 类型）◄─────┘
                        │                        ← 只保格式，不保语义
                        ▼
      解析 ──► 查找 ──► 校验 ──► 执行 ──► 按调用 ID 匹配结果
                        │                              │
                  REST / MCP 对接              依赖编排 + 并行
                                                   │
                                                   ▼
                                                 评估
```

工具带来了各种能力——检索、执行、生成、应用，正是它们让 Agent 成为 Agent，但这并不是白来的。

你可以把 schema 加入 prompt，模型发出调用，然后你验证、分发，再按 ID 匹配结果。我们还可以加约束，比如基于语法的解码，但**并不保证语义正确**——比如一个 Python 程序，就算你生成的字符串能被解析成 Python，程序本身仍可能是错的。对接的方式也有好几种，比如直接做 REST 调用，或者用 MCP。还有很多系统负责编排依赖关系和并发，让我们进行评估。

关于工具调用我想讲的就是这些。这部分会出现在第一个搭建 Agent 的 harness 作业里，到时要自己处理。下次课我们要讲的是长上下文，LLM 中的上下文管理。

### 本讲提到的题目

**快速小测验（以及讲师顺手指出的附加分作业）**

- **题干**：语言模型生成的工具调用绝对不保证格式正确。启用基于 JSON Schema 的约束解码（文法 + 下推自动机 + 掩码 logits）之后，几乎总能拿到规范的工具调用——但**有一种情况连这也不够用**。是什么情况？
- **答案**：token 用完的时候。解码上限是固定的，模型可能还停在自动机的合法路径上，但没走到最终状态，于是只生成了一部分的 JSON 就输出了。此时输出在文法上是「合法前缀」而非「合法句子」，任何逐 token 合法性检查都拦不住它。
- **延伸（附加分作业）**：理论上有办法解决——数一数还剩多少可输出的 token，然后提前截断。课上原话是「如果有人想在 XGrammar 里实现这个，可以当附加分作业，我很乐意看到」。线索在正文的下推自动机那一节：栈深度、接受状态、以及生成循环里每一步的栈快照，都是算这个剩余长度的切入点。
