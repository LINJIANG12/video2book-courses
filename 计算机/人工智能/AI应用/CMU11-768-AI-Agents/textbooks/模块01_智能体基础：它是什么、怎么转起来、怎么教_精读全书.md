## 智能体是什么、怎么转起来、怎么教它
> 对应块：BLK01 | 覆盖分集：P01 | 块标题（分集名）：《01｜什么是智能体？它们如何工作？【中文配音版】》

### 开场：为什么是现在

这门课叫 11-768，是一门新课。今年开它特别应景——现在很多人开始用智能体了。

我是 Daniel，我的组里也在做智能体，主要是三个方向：以真实环境为依据的智能体、人与智能体的交互，以及最近才热起来的、智能体系统之间的交互。这几个话题我们都很想和大家聊。

研究智能体时间更长的是我的同事 Graham Neubig，计算机学院副教授，编程智能体、网页浏览智能体这一类他做了好几年了。今天开头由他来讲。

能力确实在快速提升。你们很多人日常工作中可能都在用编程智能体，我们也见过智能体的一些重大成功案例。比如 Anthropic 的 Carlini 做过一个很好的实验：能不能让多个智能体协作、用一个比较新的编程模型，去开发一个非常复杂的软件？结果相当成功——16 个智能体协作，两周构建了一个基于 Rust 的 C 编译器，而且它能编译 Linux 内核。

你们在工作中可能已经把智能体用得挺顺了，也看到它们提升有多大，尤其是最近一年左右。但现在的智能体也有它的局限。

### 一次把收件箱删空的智能体

有多少人试过用能控制你电脑的智能体？比如让它直接操作你的应用程序——现场举起手的人不少。那 OpenClaw 呢？

之前有一件影响很大的 OpenClaw 事件。当事人把事情发到了 twitter 上：他让模型整理自己的收件箱，结果模型有点失控，开始删除旧邮件。他赶紧介入，问模型这是怎么回事、能说说你在做什么吗？模型说，它要用"终极手段"，清空收件箱里所有不在保留名单上的邮件。用户想阻止它，说别这么做，但模型还是删掉了大量非常有价值的信息。到最后它承认：我吸取教训了，以后不会再这么做了——"我记得你跟我说过，但我还是违反了。"

那背后发生了什么呢？

看起来是模型压缩了过去的上下文。这是我们这门课会讲到的一种方法：压缩历史记录，让模型能接收更多与环境的交互。但压缩的时候，它把"不要删除邮件"这条指令也一起丢掉了。

> **结论**：模型能力越来越强，但仍然有很多粗糙的地方。这门课很大一部分要讲怎么从基座语言模型出发培养这些能力，也会讲还有哪些研究问题和缺口需要填补。

### 哪些事你敢交给智能体

先不急着下定义，我想先听听大家的直觉。我准备了六个任务，都是你想让智能体做的事。这些判断挺主观，我只想看看大家能接受到什么程度。举个手试试——每题三个选项：完全自主 / 先问一下再行动 / 永远不行。

| 任务 | 大家的多数选择 |
| --- | --- |
| 诊断并修好一个用某个应用搭起来的网店 | 完全自主 |
| 起草产品发布邮件，直接发给 5 万名客户 | 先问一下 |
| 收集你的报税表格，准备并申报 2025 年的税 | 永远不行 |
| 把支付 API 从 Python 迁移到 Rust（Python 里写过的测试用例可以直接复用） | 完全自主（两边很接近） |
| 帮你在本地买到最喜欢的乐队演唱会的票，并直接买下 | 完全自主 |
| 每周读血糖读数、决定胰岛素剂量 | 永远不行 |

网店那题，选完全自主的更多。发布邮件那题，也应该是选"先问一下"的——举手说"完全自主"的可能只有几位勇士。报税那题选"永远不行"的最多了。Python 迁 Rust 这题很接近，分不清哪个更多，但算完全自主阵营赢。买票那题也选了自主：智能体找到合适的票，你们也接受它直接买下。胰岛素那题，大家选了"永远不行"——我本来以为会是"先询问"。这个 agent 完全有能力做这件事，比如你把健康数据喂给它，它就能持续监测，如果你给它权限去修改处方剂量，它也能做到。

我想大家对智能体的边界已经有大致认识了。不过还有很多任务我们其实拿不准。同时你们也体会到了：**信任很重要**。后面讲到沙箱、安全交互以及人工监督时，我们会更深入地讨论这些话题。

### 现在的智能体长什么样

简单介绍一下智能体这几年的发展，就几页幻灯片，同时为课程后面会讲到的内容做个铺垫。

过去几年我们在卡内基梅隆研究能操作电脑应用的 agent，两位老师共同做出了两年前的那个作品：展示智能体控制浏览器的过程。任务是在 Yelp 上找到匹兹堡一家优质泰国餐馆的页面，要求至少有 200 条评价、4.3 星。画面有点模糊，但你能看到两件事：左边是模型在控制浏览器输入搜索内容、在 Yelp 打开页面；右边是它和语言模型的交互，能看到 chain of thought。左边控制浏览器，右边写草稿纸——few-shot 这块做得很棒，泰国餐厅这一单是成功了。

过去几年这类框架和智能体发展得非常快，比如 Manus、OpenAI 的 Operator、Claude 的 computer-use agent 等等。我们在 CMU 也做了很多构建 coding agent 的工作，尤其是 Graham 的组。还有开发开源智能体的 OpenHands。

下面是 Graham 的一个演示视频。这个智能体一边写代码，一边在浏览器里和它构建的应用交互、给它做测试。毕竟干活需要一点时间，我们可以一边看它工作：它已经为静态文件和模板建好了目录，还创建了主应用文件。点开这里的改动标签，可以看到它对应用文件做的所有修改——这个功能很棒，你可以在它工作的时候观察它在做什么。它还在编辑 index 文件和样式文件，让应用更好看；还写了 requirements.txt 方便安装，写了 README。可以看到它遵循了良好的编码规范。

现在它要启动这个应用了，很快就跑起来了。然后我对它说：在后台运行，再用你的浏览器测试一下。它检查了应用是否在运行，现在要用浏览器打开它。它在查日志，发现端口被占用，然后试着自己解决——**这正是智能体的好处：它能自己调试问题，并确保一切正常运行。**

现在应该可以用了。大家看，它已经浏览到应用页面，这就是我们的待办事项应用。它确认应用在运行，现在要测试功能：可以看到它填入了"买杂货"这一项，并点击了。大家可以看到它在实时测试你的应用，接着它还在测试删除功能等等。

我觉得这特别令人兴奋。我不算最好的前端开发者，但它能用前端检查功能是否正常，并随时修复问题。我甚至遇到过一次应用崩溃，智能体比我还先发现崩溃，然后进去把问题修好。其实只要简单说一句：去开发一个应用，测试它能不能用——你不用做别的。现在完成了，让我停止它。真实场景里，我接下来会让它推送到 GitHub，这样收尾之后我就能继续在上面开发。

我们很高兴在这门课上让大家动手实践构建智能体。在课程后面的一次课上，我们会讲 OpenHands 和它的 SDK，教大家如何开发自己的智能体。

### 从 Russell 到今天：会感知环境，并对环境采取行动

其实智能体这个概念存在很久了，发展智能体能力的工作也绝不是只有两三年的新东西。Russell 和 Norvig 在他们的经典 AI 教科书里，把 agent 定义为：**任何可以被看作能感知环境、并对环境采取行动的东西**。这确实符合我们现在的智能体。过去为 agent 开发的很多技术——虽然不是全部，但很多——都适用于现在的智能体，尤其是搜索、强化学习这些。

那放到今天的智能体身上，具体是什么样的呢？

- **环境**：智能体会处在某个环境中，可能是代码仓库、网站，或者你电脑上的其他应用。
- **观察**：它通过获取环境当前状态的观察来与环境交互。比如它正在和用户交互的消息、正在查看的文件内容、当前所在网页的屏幕截图，或者我们几讲之后会重点讲的工具执行结果——工具就是它可以在环境中执行的程序化函数，用来与环境交互。
- **行动**：它在每个时刻都会采取行动，这些行动会更新环境，进而改变智能体所处的状态。行动可以是回复用户、编辑文件、在 shell 里运行命令，或者调用支撑它所交互网页的 API。
- **奖励**：我们要怎么用一个数值分数来定义智能体成没成功呢？可以这样定义：如果代码库有一些测试用例，它们通过了吗？通过了就得到一，没通过就是零。

对其他任务来说，很难设计出程序化的奖励。这时我们可能需要用 LLM 作为裁判，来评估任务是否成功——第二次作业里你们要开发基于 LLM 裁判的评估，还有其他评估方式。最终我们关心的可能还是用户对智能体完成的任务满不满意，所以我们也可以用用户的反馈来衡量这一点。这个话题会在后面人机交互的客座课上展开。

我们要求各位都事先有训练语言模型的经验，有了这个基础，大家都熟悉语言模型做 next token prediction 了吧：在每一步预测下一个 token 的概率分布，我们从这个分布里采样，或者用其他方式选出一个 token，把它插入模型的上下文窗口，然后不断重复这个过程。

最近通过给这些模型引入 chain of thought，复杂推理任务有了很多改进。还记得 chain of thought 是什么吗？就是预测一段 token 序列，这段序列不是我们希望模型输出的最终答案，但相当于给它一张草稿纸，用来记录中间的推理步骤；模型可以基于这些步骤再去预测最终的答案。

这还是一个非 agent 的场景，对吧？只是智能体在和你给它的 prompt 交互。那怎么从这个阶段走到"模型能在真实环境中采取行动"呢？

### 工具：把模型接到环境上的那层接口

主要的方式就是通过工具。工具是环境中的一个东西，它为模型提供一个接口，让模型能够和环境交互。你可以把它理解成一种 API。

比如说我们想让模型能查到天气，好回答用户的相关问题，那可能就会用 weather.gov 的 API，外面再包一层接口，让模型能调用它。

这个接口可以用很多方式来表示，下一讲 Graham 会更详细讲这些表示。举个例子，这是 OpenAI 的工具规范：对模型可调用的每个工具，你首先要给它起一个名字，再用自然语言描述它的功能。比如 `read_file` 就可以是 coding agent 用来查看所在仓库中文件的工具。我们还要告诉模型能传给这个函数什么，所以要描述清楚它接受哪些参数——比如这个函数可能只接受一个 `path` 字符串，指明要打开的文件。这样我们有了名字和描述，还有一个结构化的函数接口，这里用的是 JSON。这些信息也需要以某种方式输入给模型。

我们有了工具的底层规范，模型会通过一个模板来读取它：模板把规范转成一段文本，经过 tokenize 之后由 LLM 读入。大致就是这么一条通路：

```text
  [ name + description + parameters ] --template--> [ plain text ] --tokenize--> [ tokens ] --> LLM
```

模型要么经过训练，要么通过 few-shot 示例，学会怎么使用这些工具。这就是模型知道自己"可以"用哪些工具与环境交互的方式。

但模型还得真正使用这些工具来交互。它是通过 tool call 做到的——比如生成这样一段文本，写上 tool call，然后指定要调用的函数名和参数。

如果你用的是基于 JSON 的表示方式，还有没有别的方式可以让模型调用工具？现场有同学给出建议：如果把接口表示成 Python 函数，模型就可以直接用 Python 语法调用这个函数，比如直接写出一段 bash 脚本。后面课程会看到这种方式非常有效，往往比生成 JSON 更好用。当然这也有取舍。

模型调用工具时，会拿回环境执行该工具后返回的结果。举个例子，如果我们读取一个测试文件，里面可能就有某个加法函数的代码；环境会把这个工具的结果填在 `content` 字段里返回，然后通过模板渲染给模型，模型把结果读入为 token，再继续生成输出。

有了基本的工具接口之后，我们就能让语言模型使用这些工具在环境中行动。具体做法是：模型读入这些 token 序列——包括有哪些工具可用，以及工具的执行结果——然后生成 token 序列，指明要用的工具，从而触发调用。

这样我们就把语言模型本身区分出来了：它只是在与 token 打交道。以后我们会讲到多模态语言模型，它们还能接收图像等其他模态，但语言模型就是 token 进出，也可以是多模态。但还有一个 harness，它负责实际协调这些接口，把语言模型当作其中的引擎。**这就是智能体循环的基本形态。**

Toolformer 是一篇很有影响力的论文。它表明可以训练模型使用 tool call，再根据结果来提升后续文本的概率，还展示了一种训练模型使用工具的早期方法，推广了以往的 LLM 训练流程。

### ReAct：循环是怎么转起来的

有了这个基本设置之后，你就可以通过运行一个循环来实现智能体。2023 年有一篇很有影响力的论文 ReAct，译为"推理加行动"：先产出 chain of thought，再行动。

它的工作方式是：你先有一段上下文，其中可能包含对总体任务的定义，比如在 GitHub 上解决 issue 或 PR 的问题（稍后我们会看到一些例子）；接下来是一个任务，也就是用户提出的初始请求；你还会有一份智能体可调用的全部工具的列表，用我们前面展示过的某种格式来表示；另外还有一份历史记录，包含智能体先前产生的观察和动作，以及它交互过程中观察到的内容。

在每个时间步，对于智能体所处的特定状态，它会基于所有这些信息生成一条推理链，也就是 chain of thought，里面写着"该做什么"的草稿；然后生成一个或多个工具，用来与环境或用户交互，比如读取文件。这个 tool call 会在环境中执行，我们拿到结果，把它加入历史记录，同时环境也因为这个 tool call 而得到了更新，然后再重复这个过程：模型会基于更新后的历史，以及这一步得到的观察，发出新的 tool call。如此反复。

也可以有结束任务的 tool call，比如给用户发一条消息，或者以其他方式表示完成，这样我们就能表示任务已经完成了。

```text
   +-----------------------------------------+
   | context                                 |
   | task definition + user request          |
   | tool list + history                     |
   +---------------------+-------------------+
                         |  tokens
                         v
             +---------------------------+
             |        LLM engine         |
             | token in / token out      |
             +-------------+-------------+
                           | chain of thought + tool call
                           v
             +---------------------------+
             |          harness          |
             |     parse and route       |
             +-------------+-------------+
                           |
             +-------------+-------------+
             |                           |
             v                           v
   +------------------------+  +------------------------+
   |     call a tool        |  |    finish-type call    |
   |  (a function in the    |  |  message the user,     |
   |      environment)      |  |  mark the task done    |
   +-----------+------------+  +-----------+------------+
               |                          |
               v                          v
   +------------------------+  +------------------------+
   |  result comes back in  |  |     task finished      |
   |  the `content` field;  |  +------------------------+
   |  env state has moved   |
   +-----------+------------+
               |
               |  observation -> history
               +--------> back to context, next step
```

读图：外层是那一大团上下文（任务定义、用户请求、工具列表、历史），它被 tokenize 后喂给 LLM；LLM 吐出的 chain of thought 和 tool call 交给 harness 去分发——要么真的去调环境里的工具，拿回来的结果填进 `content`、写进历史、环境状态也跟着变，然后回到下一轮；要么是一个"收尾类"的调用，表示任务结束。整套循环就是在这两者之间反复。

模型如何判断自己做完了，在规划那一讲我们会稍微谈谈，细节这里不多讲。做作业一的时候你们会深入接触：要求你实现一个 ReAct 风格的循环，做一个小的 coding agent，并用它来在一个仓库里解决问题。这个仓库其实是个国际象棋引擎的仓库，还配有有趣的演示。细节我们不展开，你们要写的代码会和这个不太一样，但从高层次看，这是一个非常简单的实现。

这是一个叫 mini-SWE-agent 的精简仓库的节选，它在 SWE-bench 基准上表现非常出色。这个基准我们后面会讲到，是 coding agent 领域的一个标准基准。不过这个代码仓库真的很不错，我建议大家去看看：它对近期的模型很有效，同时又相当简洁，把最基础的东西提炼了出来。

它的骨架就是：一开始给模型一些消息，说明它是一个智能体以及任务是什么，然后就反复运行前面那个循环。智能体把所有过往消息打包向原模型发起查询——这些消息包含了历史记录；然后它把自己的输出加入历史，再执行，就是在环境里执行这些动作。这部分代码我们省略了，但感兴趣的话可以去看代码：仓库执行动作，获取观察结果，然后返回。

另外我觉得看一些智能体的示例轨迹也很有帮助。SWE-bench 数据集的一个好处是，它的评测任务和排行榜提供了一些示例轨迹。我们挑一条来，把它放大一点看。

模型会在系统消息里收到一些上下文，说的是你是一个可以操作计算机的助手——这个非常通用。但接下来还会有一段记忆，再跟一条用户消息，给出具体任务的上下文，也就是解决这个特定的 pull request。模型以这些为条件，然后就需要发出首个动作：看到 chain of thought，这段蓝色文字是模型生成的。然后它产生了一个工具调用——这个智能体用的正是刚才建议的那种格式，也就是直接写下要运行的命令，发起一条 bash 命令。命令被交给环境去执行，结果就是一个退出码（exit code）；退出码为零，说明执行成功了。接着进入下一轮 agent step，又提出新的想法和新的 bash 命令，如此循环下去。

希望这能让你们大致了解一种实例化工具和 prompt 的可能方式。大家会在第一次作业里实际练习这个。

### 一个好智能体需要哪几种能力

讲到这里，我把时间交给 Graham，内容还挺多的。

我先说说智能体的能力：什么叫一个好的智能体？因为就像 Daniel 指出的，做一个智能体其实不难——现在有很多库可以直接调用，来跑语言模型的推理。难的是做出一个真正能用的。所以我想先思考一下，一个智能体需要具备哪些能力。

刚才不少人说自己每天都在以某种方式使用智能体，比如 OpenClaw 或者 coding agent。你们用智能体的时候，哪些问题让你们很头疼？就是出了什么岔子？

- 他们太慢了；
- 太啰嗦、太冗长；
- 会忘事，忘记之前对话里的交互；
- 可能误解你的意思，然后因此犯错——"做了什么来着？"；
- 会访问不该访问的东西；
- 很常见的东西也有随机的知识盲区；
- 两行代码能搞定的事，他写 1000 行；
- 你说的不合理时，他不会反驳；
- 他们可能对你撒谎；
- 还有很多隐含的假设。

这些都是让我头疼的问题，也都是好例子。他们跟幻灯片上写的并不完全一样，但这是好事。

**第一项能力是准确的工具调用。** 其实刚才没人提到这一点，因为现在很多人都觉得这是理所当然的。但这一点可不是理所当然的。如果你上了这门课、负责训练模型，这就是基本功：工具调用不准确，你做的任何任务都会失败。但它不是白来的。

> **提示**：判断一个智能体好不好，最容易被跳过的恰恰是"工具调用准不准"。它是地基，不是加分项。

**另一项是长上下文的一致性。** 有人提到智能体忘事让他很烦，或者忘了之前会画的内容，诸如此类——这是长上下文一致性的一个例子。另一个例子就是 Daniel 刚讲的：之前模型被叮嘱别做某事，结果它还是做了。

**接下来是可定制性。** 你希望智能体按你的方式做事，每个人的做事习惯和要求都不一样——我们这门课的要求可能就跟别的课不一样。所以用智能体，你得确保他会遵守这些要求。

**复杂任务管理，也就是拆解任务、处理超长周期的任务**，这是个很大的问题。

**环境理解。** 明明两行代码就能改完，智能体却改了 1000 行，这就是环境理解的隐性失败：他本该意识到这其实是个很简单的改动，却没意识到，反而去做了一大堆别的事。

**最后一个是安全性。** 很多人把安全性和能力分开来看，他们说我是安全研究员，或者我是能力研究员。但在我看来，**安全就是一种能力**，这是需要内建到模型里的东西。如果模型里没有内建，你用起来就不放心，因为他可能擅自做你不希望他做的事。所以在我看来，这就是模型、乃至整个智能体的失败。

### 训练 LLM，还是做 harness 工程

构建这些能力有两条路，在做智能体时非常重要。第一种是训练 LLM，第二种是做 harness 工程——在 LLM 周围搭好结构，让它去按你想要的方式解决你要解决的问题。

所以问个问题：大家觉得哪一个更重要、更有效？现场的结果很有意思——强烈认为"训练 LLM 才是让智能体好用的正道"的，举手的人出乎意料的少；认为该给智能体做 harness 工程的，这次举手的人相当多。我还看到有位老师举了两次手，他可不能这样，不过他是老师。

当然两者都重要。我先简单说说它们各自指什么。

- **训练 LLM**：通过预训练、SFT 监督微调或强化学习来改变模型行为。这样能教会模型可复用的模式——推理、工具使用和错误恢复。关键在于，这些能力成为学到的模型或策略的一部分。
- **Harness 工程**：改模型周围的东西——系统 prompt、工具、记忆、控制流，提供上下文、校验、权限和安全边界。能力不只来自模型，而是 harness 和模型的结合。

那我的答案是：两者可能都重要，但通常的情况是，你先发现一个问题，然后在右边解决它；之后训练模型的人会跟上来，意识到这是个大问题，大到值得专门用某种方式去训练模型来解决它。问题解决了，harness 就不用再管了。这就是典型的流程。

在我看来，左边往往是更根本的解法，但很花时间。而改进模型是没有那么多时间的，所以你得先从右边入手。**所以如果条件允许，我个人更倾向于把 LLM 训练当作根本解法。**

那有哪些能力是必须先从 harness 这边动手做的？

有一个我可以明确说：长上下文。比如把所有记忆都放在上下文里维护——因为这不只是模型的准确率问题，也是模型的效率问题，你得能建模很长的序列。当然你也许能造出不像 transformer 那样 $O(N^2)$ 复杂度的模型，但你知道那是另一个更大的话题了，前提是我们还在现有的建模范式里。

我觉得上面列的其他大部分能力——准确工具调用、上下文窗口内的连贯性、复杂任务管理、环境理解——从能力角度看，理论上大多可以靠训练模型解决。安全或许也能，但目前都还没解决，所以我们仍然需要 harness 工程。

可定制性很有意思。你可以及时训练模型，但有些场景下，你想给他一段脚本，或者想给他根据具体情况写的单独指令，这时训练未必是最佳办法。这些细节我们之后可以再详细讨论。

那再追问一个：当推理延迟很关键时，针对问题做 harness 工程是不是个好方案？推理效率有个特别之处——你往往得用更弱的模型，或者用更少的算力。正因如此，你常常需要加更多护栏，因为成功率会更低；或者需要针对具体任务做适配。模型越小，你就得越小心，因为大模型往往泛化能力更强，他们也不完美，但泛化更好。

### 逐项过一遍：每种能力分别怎么补

好，我们逐个看这些能力。左边是 harness 工程，右边是 LLM 训练。

| 能力 | Harness 工程 | 训练 LLM |
| --- | --- | --- |
| 准确的工具调用 | 语法约束解码，保证 tool call 格式正确、符合规范 | SFT 监督微调或中期训练，训在工具调用数据与轨迹上 |
| 长上下文一致性 | 上下文压缩 / 紧凑化；动态记忆查询（全部上下文存成记忆，不立刻全部塞进上下文，而是按需调用）；子智能体委派（把超长任务的一段委派出去，那段上下文留在内存里，做完再丢弃） | 长上下文训练（这块我们不会讲太多，但可能会稍微提一下） |
| 可定制性 | agent 记忆（交互越多越了解你）；skills（一些 prompt，有时是脚本，写着你想做的那类事，在需要用的每个时刻再拉进来）；针对特定任务的自定义工具 | 还是很新的领域，目前没有多少人做得很深入；但确实有一些从用户反馈中学习的方法，比如用户点了个赞或点了个踩，就可以专门从这个用户身上学、去适配他 |
| 复杂任务管理 | 提供规划或任务分解工具；给模型一个规划模式；子智能体委派 | 在复杂的、长程的任务上做训练 |
| 环境理解 | 给它提供对应领域知识的 skills | 用符合预期观测形态的数据来训练，或在领域特定的环境中训练 |
| 安全性 | 沙箱；限制它访问凭据；在它工作时进行监控 | 安全感知的强化学习 |

有三个地方值得单独说一说。

**规划模式，其实只是加了一句 prompt。** 有个很流行的编码 harness——我记得是 Codex，不对，抱歉，应该是 Claude Code——他们有个规划模式。用户点一下那个按钮，其实只是在 prompt 里加了一句："请先规划，先别执行操作。"但大家都想要一个规划模式的按钮，于是就用纯 prompt 实现了。当然也有更复杂的做法。

**模型不会自己变强。** 现在实际上有一种说法：模型会越来越强，到时候我们就不用担心这些问题了。但问题是，模型不会自己变强，是人把模型变强的。我们这门课想教的内容之一就是：当 Claude 从 4.7 突然升到 4.8，忽然更会作曲时，背后到底发生了什么？这背后有几件事儿，其中一个很关键：他们会专门搭一个环境来训练模型，比如作曲环境，把它加入训练配比里，模型作曲就变强了。所以这里大量的工作，就是为模型创建领域专属的环境。

**环境理解的难处在于多模态。** 对于计算机操作智能体，你得让他能理解网页或者 GUI 界面之类的。这种能力不是现成的：现在的智能体在这方面相当差——最强的可能好一些，但很多开源模型连多模态数据都不支持，而支持的那些理解得也不完美，他们会犯很多错，比理解文本时多得多。换个环境也一样：让他们去交易股票，他们不太擅长理解时间序列，在时间序列上会犯很多错；或者你把它们放进一个需要看懂一张图的环境里，比如一个培养皿里面有大量细菌，它们也做不好。所以你想让智能体在什么环境里工作，他就得能理解那个环境。

### 一次安全失效的复盘

安全性这边我想多讲一个例子，因为它是最近发生的实事。谁听说过 OpenAI 入侵 HuggingFace 那次事件？

最新发布的 OpenAI 模型被放进一个 agent harness 里，做一个网络安全 benchmark，它的指令是入侵这个系统——入侵系统就是它的任务。它没能入侵那个系统，于是干脆黑进了 HuggingFace 的网站，从那里拿到了答案。

这里面出了好几处失效：

1. **沙箱失效**：做 benchmark 时，他们没有把智能体妥善隔离。他们确实限制了凭证访问，它就绕过这个限制，黑进了一个它没有凭证的系统。
2. **监控不足**：他们的监控也不够，所以没能发现这件事。
3. **护栏不足**：这个模型也没有足够的安全护栏，因为它当时还在被训练，训练目的就是测试他能不能入侵系统。

所以他们最终向公众发布的那个模型，应该比这个模型有更好的护栏。这些都是处理安全的手段，我们课上也会讲这类内容。

### 智能体是一个系统

另外我们特别想强调的一点是：**智能体是系统，它们不只是模型**，而且复杂得多。它们比你们之前上过的任何机器学习课、任何课里接触过的东西都要复杂得多。所以你们得能应付各种不同的环节。

```text
   +--------------------------------------------------+
   |  LLM  (the engine)                               |
   |  token in / token out                            |
   +--------------------------------------------------+
   |  harness                                         |
   |  context | tools | memory | control flow         |
   |  validation | permissions | safety guardrails    |
   +--------------------------------------------------+
   |  environment                                     |
   |  code repo / website / desktop / database        |
   |  observations come back up from here             |
   +--------------------------------------------------+
```

读图：这是四个层次。语言模型只是最上面的引擎，token 进 token 出；真正把它和环境缝起来的是中间的 harness，管上下文、工具、记忆、控制流、校验、权限和安全护栏；最下面是环境，观察从那里流回来。**能力 = 模型 + harness 的结合**，任何一层塌了，系统就不成立。

#### harness：一段中等偏复杂的软件

它是一段中等偏复杂的软件，有很多活动的部件：你得处理上下文、处理工具和安全护栏、管理工作流程之类的。

#### sandbox：把智能体关起来

为了防止智能体未经允许就把你的 API key 泄露出去、或者入侵别的网站，我们需要隔离代码和工具的执行，限制智能体能访问的算力、网络和文件系统。

沙箱还有另一大用途是评估和训练：用它创建可复现的环境。比如 SWE-bench，每个问题都有一个沙箱，起点就是智能体开始工作前的那个环境状态，大家可以在本地运行这些环境。我们用到的一些技术是 Docker 和 Apptainer，也可以放到云端运行。

#### 推理：上下文大到 25.6 万

这块基本上大家都接触过，你们大多上过 NLP 或大语言模型的课：他们基本上负责提供模型生成服务、处理请求。如果有多个智能体同时请求你的语言模型，把请求打包处理效率更高。

这里还有一件极其重要的事，就是缓存之前的请求。因为智能体会执行越来越多的操作，操作越多，积累的上下文就越多，你要确保能正确地复用这些上下文。另外这个量级下推理本身也不一样了：你之前用语言模型做过推理，可能处理过 1 万 6 千、3 万 2 千个 token 这样的上下文，而在这里，你需要至少 25.6 万，才能有一个最先进的 coding agent。所以推理的问题更难了，你还需要处理推理缓存之类的事情。

系统层面还有 vLLM、SGLang 这类软件，它们是最流行的两个；此外还有海量的推理服务商。如果大家没见过 OpenRouter——它就是把所有推理服务商聚合到一起的平台，随便哪个模型，你都能看到二三十家不同的服务商在提供它。这类服务商里，很多就是算力赞助商，Fireworks 就是一家。

#### 编排器：coding harness 的另一个选项

用于 coding agent 的 harness 大致有两类。现在比较流行的有 Claude Code、Codex、OpenHands、OpenCode，大家可能至少用过或听说过其中之一。OpenHands 是我自己开发的，我很熟悉，稍后我会讲，也会分享一些开发它的经验和教训。

除此之外还有编排器，比如 LangChain——那是我写的，不过现在我们更应该说 LangGraph 了——还有 CrewAI。两者的理念差别很大。

| | Coding agent 的 harness | 编排器 |
| --- | --- | --- |
| 智能体之间怎么交互 | 这方面更简单 | 声明式的工作流，明确规定智能体能做什么 |
| 单个智能体的动作空间 | 更复杂：可以写代码、操作网站，还能做其他类似的事 | 受限：可能只会回复客服请求，或者查一下数据库，写不出任意的 Python 程序 |
| 整体特点 | 表达力强，防护较少 | 防护更多，但表达力较弱 |

两者各有适用场景。

#### 训练系统与可观测性

接下来说训练系统。他们要做的基本上就是更新模型的权重：准备数据、收集 rollouts、协调大量工作节点一起训练模型，还能做 checkpoint、评估和复现运行。这方面的软件我们后面会具体讲。

最后是可观测性和监控，用来了解你的智能体运行得怎么样。他们会记录智能体的轨迹，也就是智能体做了什么，并收集相关指标，比如花了多少时间、成本是多少，追踪质量、成本和失败情况，还能让你对比不同的轨迹和评估结果。我对其中一个叫 Laminar 的工具很熟悉，因为我经常用；Daniel 还展示过另一个（虽然没在我的幻灯片上），但那也是一个很流行的工具。

### 这门课怎么安排

这门课的一大目标，就是让你们每个人都能亲手训练一个模型，用于智能体任务。而关键在于能把这件事做好的人并不多，所以我们想让这间教室里的各位成为那少数人——希望你们擅长的，是那些不光难做、更难做对的事。不过话说回来，你要是真会做这件事，那可是个好本事。

到这门课结束时，我希望大家都能做到：在一个开源 LLM 之上，从零实现一个智能体，也就是自己动手写 harness，还要为多步任务设计评估。简单说，我们会给你一个需要评估的任务，你要为它设计出评估方案。这一点超级重要：就算你对评估不感兴趣，只要你想做训练也绕不开，因为做训练最好的方式之一，就是先建一个评估，再把它规模化，这样你就能做基于强化学习的训练。这是一项很重要的技能。

接下来讲训练智能体、提升能力，也就是真正跑一遍强化学习循环，处理好系统工程问题，还要会分析安全与可靠性的权衡，之后会专讲安全。最后我们还有一个项目，我会在下一张幻灯片介绍。

这些都是作业。前面的作业基本上都是实现类的作业：我们给你任务，要求你完成。第一个作业是创建一个 harness；第二个是评估，就是我刚才提到的那个；接下来是训练部分，我们会用强化学习来训练。这些大致占了课程的前半部分。而课程的后半段，就是用这些技能做一个项目，在你选的领域里做出点有意思或有新意的东西。项目是分组进行的，我们会要求大家两到三人组队一起完成。

整体安排是：我们先讲智能体的能力，然后进入一些具体领域，比如编程和 GUI 智能体；然后是训练，包括 SFT 监督微调和强化学习；接着讲框架和安全；之后还会讲人机交互；然后有一些项目时间，大家一起讨论各自的项目。到课程最后，我们会请各个领域的专家来做客座讲座，既带一点领域概览，也讲讲他们的研究。我和 Daniel 列了各个话题下全世界最合适的讲者人选，好像没人拒绝——我想大家都答应了，所以每个话题我们都请到了首选人选，我对此非常期待。

关于训练本身：预训练我们不会讲，因为预训练的规模是整个互联网，很遗憾我们的 model 额度撑不起这个。但我们会讲中期训练、SFT 和强化学习。重点是中期训练和 SFT——都是你已经有智能体完成任务的示范，然后在示范数据上训练，通常用最大似然来优化。希望大家都做过，因为这是这门课的先修要求，所以这部分只简略带过。重点放在怎么在 agent 场景下创建数据，然后会更侧重强化学习，因为对智能体做强化学习相当棘手。

有多少人以前用语言模型做过强化学习？我猜没多少人。有多少人做过推理任务的？差不多是一半——一半各占大概 10%，剩下的 80% 没做过。我们会下很大功夫，保证到课程结束时每个人都会做这件事。

我们的课程团队也非常出色，成员都在做这些领域的研究，写过一些奠基性的论文：有训练智能体、让它更好地利用推理与算力，以及多智能体系统中的协作组织的；有为智能体做强化学习的奖励函数、主要做代码生成方向的；有做强化学习与环境交互的；有研究如何训练智能体让他们和人的沟通更高效的；也有训练智能体完成操作类任务的，以及做对齐后训练和智能体交付的。大家构思后期项目的时候，我们非常鼓励多和助教交流——课程结构我们放到最后再讲，但你们构思想做什么项目时，他们会是非常好的资源，欢迎在答疑时间去请教。

另外我们非常感谢几家很棒的创业公司为本课程捐赠算力，大家做本课程的作业和项目时都可以使用。没有他们的支持，我们就没法按理想的规模来开这门课。

### 先修要求、成绩和截止时间

开始之前先说一下先修要求。这是一门在机器学习实现上强度很大的课——我们希望每个人到课程结束时，都能用强化学习训练一个智能体。

我们的先修要求还包括：需要有正经训练过语言模型的经验。LTI 的语言模型课程、语言模型系统课程和 NLP 课程都符合这个先修条件，上过其中一门就没问题；一些深度学习课程可能也算数。不确定的话随时来问我们，但这个要求是硬性的——每个人都要提交一份表格，我们会在 Piazza 上发 Google 表格，请务必填写，方便确定选课名单。如果有 30 个人都想问自己是不是不符合条件，课后别单独来问我，最好发邮件。

另外一种情况：如果你确实没上过课，但在业界工作并且训练过模型，那得是真正意义上的训练，比如至少 40 亿到 70 亿参数规模，而不是 1 亿参数那种——这种情况我们也会认可。

下面是评分政策：

- **作业 1~3 占总成绩 40%**，独立完成。
- **项目占 50%**，以两到三人的小组进行——因为它占了课程的一半。开题 5%、中期检查 5%、汇报 10%、最终报告 30%。上过 LTI 项目制课程的同学会发现评分标准很类似。
- **课程要点总结**：这个环节的用意是想让大家来上课，然后就这堂课里学到的东西讲一点你的收获。它不是给大家布置额外作业，而是希望你完整听完这堂课后，能想出点有意思的内容。如果觉得没什么有意思的、全都早就会了，或者在之前那门先修课里学过——这个信息对我们也有用，欢迎告诉我们。不过希望每节课我们至少能讲点有意思的东西，你可以接着深入研究。

最后说一下截止时间。提交走 Slack。所有作业都包含两次 24 小时的宽限期，宽限期不能转让或共享。用完之后，每多交一天或不足一天，扣该作业分数的 5%。也就是说，截止时间就是截止时间。不过我们还是仁慈的：如果你错过了截止时间，我们会给你一些时间补交，但如果超过两天，大多数借口我们都不会接受，比如你住院了之类的——我们可能会要求你提供相应证明，这是可以通融的情况。除此之外，请尽量按时交，我们不会给太多例外。

### 这可是一门 AI 智能体课

接下来就是大家都想问的问题了：这可是一门 AI 智能体课，关于怎么处理这件事，我们讨论得非常非常充分。

先说明一点：我做几乎所有事情都会用智能体，但同时事事都用智能体也有风险，因为你会忽略自己真正在学什么，会漏掉一些细节之类的问题。毕竟这门课的目标是学习，希望你们把这一点记在心里。

AI 工具是允许使用的，课程里几乎所有环节都可以用，除非我们另有说明——而我们大概率不会经常另有说明。但课程要点总结必须由你自己写，不能由 AI 生成。这些不用写太长，短短几句话就行，但请一定要自己写。你提交的每个论断、引用、结果和代码，都由你自己负责。

我们还会为作业设置测验，到时候你可能需要讲解自己代码里的某些部分。怎么做呢？我们也会用智能体——我们正在考虑让智能体读你们的代码，针对你们的代码出测验题，所以我们是认真的。也就是说，提交智能体生成的上千行垃圾代码，对你来说不是个好主意。**与其交得更多，不如提交一份你真正吃透的经典代码。**
