## 智能体的长上下文：让它长到一百万 token
> 对应块：BLK03 | 覆盖分集：P03 | 块标题（分集名）：《03｜智能体的长上下文建模【中文配音版】》

我原本想把这一讲直接取名叫"长上下文"。今天要讲的大部分内容其实算是比较通用的 LM 知识，但长上下文对做 agent 来说特别特别重要，而 LM 先修课不一定把它讲得很到位，所以我会讲得比较细，还会把很多最先进的开源模型正在用的长上下文架构过一遍——好让大家看到处理超长上下文时的最佳实践。

先看一个具体到有点吓人的数字。

假设初始 system prompt 大约一千个 token，每调用一次 agent 大约新增五千个 token。第一次调用之后上下文是六千，接着一万一千、一万六千、两万一千、两万六千，这个数字会一直往上走。如果完全不做任何处理，五次调用加起来就是八万个 token。

而这个过程可以持续非常长。有人问我一次编码会话能用多久，我自己也说不准，但我自己肯定连续用过好几天，几乎一整天都在用。你可以想象这能变得有多大。

更要命的是实际的计算复杂度比这还大。

```text
  轮次        上下文长度      累计处理量（无任何处理）
  ------------------------------------------------------
   第 1 次        6,000            6,000
   第 2 次       11,000           17,000
   第 3 次       16,000           33,000
   第 4 次       21,000           54,000
   第 5 次       26,000           80,000
   第 n 次      5,000n            2.5e9 · (n+1)·n/2
```

于是有两个主要挑战。

**第一个是容量**：模型到底能不能装下这么多信息。这之所以是个挑战，是因为要让模型学会处理超长上下文很难，你得在架构、位置编码、训练数据这些方面下功夫，同时你还得能评估自己到底做得好不好。

**第二个是效率**：系统负担不负担得起这么大的服务量。如果你只是用 Claude Code 或 Codex 这类工具用久了，可能会觉得这理所当然——但他们其实在做非常了不起的工程壮举：把一个几万亿参数量的模型在几秒内完成响应，而且要反反复复地做。Codex 有两千五百万用户，你可以想象两千五百万日活每隔几秒就来请求一次这个巨大的模型。如果愿意，可以在心里算算这大概是多少 FLOPs。

### 效率账本：预填充、解码与四个指标

要谈效率，就先回到推理本身。基本上你得能完成两件事：prefill（预填充）和 decode（解码），每步算输入、算输出。学过语言模型或深度学习系统的同学应该都处理过这一步。

不过还有一些问题要想：**怎么调度多个并发的查询**，以及**怎么把结果存进 KV 缓存以便复用**，而不是一遍遍重新计算。

推理分几个阶段。第一个叫 prefill，你也可以叫它"编码"，但我认为 prefill 是如今更通用的术语：你把所有不需要生成的输入 token 都拿进来，为每个 token 生成对应的 key 和 value。到了 decode，你基本上是拿着 prompt 的 key-value 对生成一个输出，把它的 key-value 对加进去。所以 **decode 是逐步增量的，prefill 是批量一次做完的**。

把它看成一个服务系统，我们有很多指标来衡量好坏。

第一个是 **TTFT**（time to first token，首字时间）。也就是从你提交一段输入、等待服务端处理，到你开始看到第一个输出为止要等多久。ChatGPT 这类工具你一用就有感觉：输入越长，开始出结果就越慢，TTFT 就越高。

第二个是**每个输出 token 的时间**，即生成一个 token 要等多久。你可以去 OpenRouter 这样的网站上看纵轴——那里基本就是每个输出 token 所花的时间。我基本可以肯定他们没有把 prefill 算进去，就是把中间那段时间排除了。不过即使每个数字都很小，逐个对比之下差距还是很明显：有的服务商只有每秒三个 token，有的能到每秒几百个 token。这会极大地影响你的使用体验。

而大家用 agent 的方式不同，在意的点也不同。打个比方，我们一起合作干活——在常用的编程 IDE 里跑交互式任务，你就会特别关心 TTFT 和每个输出 token 的时间；但如果是让 agent 在后台跑通宵任务，你可能完全不在意这两个数。

```text
  交互式场景：前台开车 ──► 人在等，TTFT 与每 token 时间是命脉
  批处理场景：后台拉货 ──► 人不等，吞吐量与成本是命脉

  吞吐量 throughput = 完成的 token 数（或请求数） ÷ 总时间
  （通常是在整个系统的整体层面来看）
  成本 cost = 花多少钱
```

这两者之间有权衡：吞吐量、成本、以及拿到 token 的速度。我的公司也提供编程 agent 服务，跟服务商谈的时候他们常会问我们更看重哪一个，这样才能针对更看重的那一项优化系统。确实有办法做到，我后面也会讲。

这里补一句标准注意力的复习，因为今天要讲的很多内容就是围绕它。公式里有 query、key、value，你有了这些之后做 softmax（可能还会加一些位置偏置），就算出完整的注意力场：

$$\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}+B\right)V$$

这样你就考虑了当前 token 和之前所有 token 的关系，同时遮掉未来所有的 token。当然这非常昂贵，因为计算量对序列长度是二次的。

### 装得下不等于用得上

就算你有一个模型，或者有一个能接收一百万 token 的服务系统，也不一定意味着你就能有效地用上一百万 token。这里有一个很老派的例子——大海捞针评测（needle-in-a-haystack）。

它大致长这样：拿一堆 Paul Graham 的随笔——他是著名创业者 Y Combinator 的创始人——往里面插一句话，比如"旧金山吃三明治最好的地方是什么"，然后问模型旧金山吃三明治最好的地方在哪儿。模型必须正确回答。他们还把上下文越做越长，用更长的上下文来评测模型，最终较弱的模型在超长上下文上就开始表现变差。

这类评测还有不少，RULER 和 HELMET 是大家常用的基准。总结起来就是：**上下文非常长的时候，模型处理起来就可能开始变差。**

你们用 coding agent 用久了，注意过这种情况吗？或者任何 agent 用久了，见过什么常见的失败案例？

- 会忘掉之前的上下文；
- 会忘记对话开头、忘记你给的初始指令；
- 我还遇到过这种情况：我在对话中途告诉它别做某件事，结果它还是去做了。

有个特别糟糕的例子，我记得 Daniel 讲过：用户已经明说了"别删这个"，它还是把它删了，因为它已经忘了这段上下文。

在 agent 场景里这可能是个很大的问题，因为用户是在不断追加指令的。接下来我会讲几个不同的方面：架构、训练、推理和上下文压缩。先从架构讲起，因为它既关系到效率，也关系到准确性。

### 架构：怎么把二次方压下去

就像刚才说的，标准注意力是全局的，它会对所有 token 做两两比较，问题就在于这显然是平方级的复杂度。

那么如今最先进的语言模型，标准的上下文长度是多少？二十五万到一百万。我觉得大多数厂商现在都瞄准一百万——因为谁也不想别人都是一百万，自己只有二十五万。

大家快速心算一下这是多少次两两比较：十的十二次方方。用英文念就是 ten to the twelve——对一百万长度的序列，每次生成要做 $10^{12}$ 次比较，而每一次比较都需要你去做乘法，把很大的向量一遍又一遍地互相相乘。这样算下来，数量级大概就到 $10^{20}$ 附近了。这可不少，对单个序列来说需要非常大量的计算。

人们有一些解决它的办法，基本上几乎都归为同一类：**把这个二次方的计算，再给每个时间步的比较次数加上某种常数上限**，这样就把 $O(n^2)$ 降到了 $O(nW)$，其中 $W$ 指窗口——但也不一定非得是窗口，只要是每次比较数量的上限就行。

于是就有了局部模型和全局模型的概念：局部模型就是把计算上限限制在一个局部窗口内；全局模型可能有也可能没有计算上限，但这个上限不是局部化的，这样信息就能贯穿整个序列传递。

我觉得如今存在、或者说广泛流行的模型，几乎都是某种混合模型：做很多局部计算，再来一次全局计算，又是很多局部计算，一次全局计算。

```text
  层内重复若干次：
  [局][局][局][全][局][局][局][全][局][局][局][全] ...
   ▲             ▲
   │             └── 每 N 层做一次全局注意力（稀疏或稠密）
   └── 大多数层做局部计算（窗口 / DeltaNet / Mamba）

  效果：靠前面几十层的局部计算把信息汇总成状态，
        每隔 N 层用一次全局注意力把这个状态贯穿整段序列
```

具体来说我会讲六个模型。标准做法就是混合模型：用某种局部计算，加上稀疏或稠密的全局注意力。

| 模型 | 局部 / 循环计算 | 全局注意力 | 比例 |
| --- | --- | --- | --- |
| Qwen | 门控 DeltaNet | 稀疏注意力 | 3 : 1 |
| GLM | DeltaNet 的一种变体 | 稀疏注意力 | 3 : 1 |
| Kimi | DeltaNet 的一种变体 | 稠密注意力 | 3 : 1 |
| 一款以 Mamba 为骨架的模型 | Mamba（循环式） | 稠密注意力 | 4 : 1 |
| 走滑动窗口路线的模型 | 滑动窗口注意力 | 稠密注意力 | 5 : 1 |
| DeepSeek | 滑动窗口里交错稀疏分支 | 稀疏分支 | — |

最后这个稍微有点不一样，它有点像窗口注意力，但有一些稀疏的分支交错在里面。前面几个 DeltaNet 相关的方法我都会讲，不会每项都深入太多细节，但足够你之后自己去查了。

#### 滑动窗口注意力

滑动窗口注意力概念上可能是最简单的。做法是把输出切成一块一块的：当前这一块加上之前固定数量的块——不是所有之前的块。比如当前块是 512 个 token 左右，前面还有两块各 512 个 token。

你会注意到它很简单：注意力本身没改动，效果就是这样。但它妙在第一层——你传递的是前一两块的信息；到下一层，前面的块也带着它们之前块的信息，所以窗口就这样逐层逐渐扩大。这种方法用得相当广泛。

#### 线性注意力：把注意力变成一个状态矩阵

现在更主流的做法是用某种形式的线性注意力。线性注意力的原理基本上是从这样一个思路入手的：我们的标准注意力里包含一个 softmax 操作，这就是它难算的原因——你要算指数，还要做除法。正因为这样，你基本上没别的选择，只能把所有 key 和 query 的计算都展开，也就是 key 乘 query 那些计算，复杂度是平方级的。

线性注意力做了什么呢？它从标准注意力的公式出发，把这里的 softmax 去掉，或者说归一化其实无关紧要，但 softmax 要去掉，剩下的就只是 key 和 query 的点积。

这肯定表达力更弱。你实际上是在移动一些东西：从一个接收一堆实数的东西，变成一个把它们归一化成 0 到 1 之间的概率数、总和为一的东西。这种非线性正是注意力的优点所在，也是它的卖点——能让你聚焦于相关的上文。而线性注意力基本上把这个能力拿掉了：你删掉了相对比较，只剩下 query 和 key 之间的点积。

但它也让你能做一件很妙的事——**利用结合律来重排运算**：

$$o_t=\sum_{i\le t}\left(q_t^\top k_i\right)v_i=q_t^\top\underbrace{\left(\sum_{i\le t}k_i v_i^\top\right)}_{S_t}$$

你可以把之前所有 key 乘上 value 的结果求和，转换成一个单独的状态矩阵 $S_t$。这个状态矩阵本质上是一个函数，一个从 query 映射到 value 的线性函数。

> **易错点**：标准注意力因为中间夹了 softmax，本身**不是**线性的；只有把 softmax 去掉之后，"query 到 value 的线性映射"这句话才成立。这也是线性注意力能重排的原因。

妙处在于这个状态矩阵可以被分解，所以你只需要一直保存它，每来一个新的 value 就常数时间更新一次。这样一来它基本上就变成了一个循环神经网络，你能够用线性时间更新状态矩阵，完全不需要平方方的计算量。$O(n^2)$ 变成了 $O(n)$，而且解决得非常彻底——$O(n)$ 里面连 $W$ 这一项都没有，因为每次更新完全只依赖上一个状态。

#### DeltaNet：预测得准，还要忘得掉

不过这里也有一些代价。最大的局限就是我刚才提到的那一点：**它就是个表达能力更弱的函数，没法在之前的 token 之间做相对比较**，诸如此类。

针对这个问题，大家提出了不少变通办法，试图构造一个表达能力更强的函数，同时还能执行类似注意力的计算。如果你深入看它们的数学原理，本质上都在努力更准确地预测注意力最终会算出的那个值。具体机制你们可以去翻论文，这里我主要从机制层面讲。

第一个是 DeltaNet。背后的想法是这样的：你可以预测出你希望得到的那个值。这里的 $k_t$ 就是时间步 $t$ 的 key，你要拿它和时间步 $t-1$ 的状态矩阵做比较，算出 $\tilde{v}_t$——而这本质上是对 $k_t$ 的预测结果。另一方面，你也知道真实的 value 应该是多少。两者一减，得到的**误差**就出来了：

$$\text{误差}=v_t-S_{t-1}k_t$$

你想把这个误差降下来，于是更新状态矩阵：把误差项乘上 $k_t$ 加进去。

$$S_t=S_{t-1}+\beta_t\left(v_t-S_{t-1}k_t\right)k_t^\top$$

做完这一步之后，如果再把 $k_t$ 乘进新矩阵，误差就没有了。但你不希望更新幅度太大，所以加上这个 $\beta$ 项——它本质上类似学习率，会让更新变得更小。这样你基本上就能把矩阵往某个方向轻轻推过去，推向那个"长得像当前 key 的 query 能输出你想要的 value"的方向。

但这样做有一个问题：**你会在之前的位置积累起大量的上下文**，而线性注意力没有任何机制能阻止很远处的上下文对你的后续预测产生坏影响。如果很久之前有一个很奇怪的 key，它可能在之后对你产生非常大的影响。

他们解决这个问题的方法基本上是加一个衰减项，让矩阵在每个时间步稍微衰减一点——通过每步稍微衰减矩阵，他们实际上是在折损久远的过去：

$$\tilde S_t=\lambda_t S_{t-1},\qquad S_t=\tilde S_t+\beta_t\left(v_t-\tilde S_t k_t\right)k_t^\top$$

衰减设得越强，它就会越快忘掉之前的上下文。所以你可以让它更局部一些，或者不那么局部。

门控 DeltaNet 用在了 Qwen 模型里，所以它现在是比较流行的做法之一。但 GLM 和 Kimi 这两个最先进的模型用的都是表现力稍强一点的版本：它们基本上带有一个**逐元素**的衰减项，这样每个元素就能以不同的速度衰减。由于每个元素的衰减速度不同，你可以让上下文里的某些部分各自按不同的速度衰减——有的能保留很长时间，有的只能保留很短。

门控 DeltaNet 的思路和这个非常类似，只是数学上稍微复杂一点，所以我不展开，我在语言模型那门课里讲得更多。

#### 稀疏注意力：少看几个 token

稀疏注意力基本上就是这样一种方法：不是去关注之前上下文里的所有内容，而是只关注其中一部分，也就是限制你去查找的数量。做法有几种。

最早 OpenAI 发过一篇稀疏注意力的论文，那是挺久以前了，大概五年前。他们的做法是**每隔一段 token 就安排一次全量注意力**，比如 512 个 token 做一次。这样做意味着：它对序列长度仍然是二次的，但计算量少了 512 倍。这就很够了。

另一种做法是**内容依赖的稀疏注意力**：用一种非常廉价的方式来计算注意力。比如你可以把注意力向量降维投影成非常非常小的向量，然后在这些非常小的注意力向量上做注意力，挑出前 K 个，再对这 K 个做完整注意力。这是另一种实现方式，DeepSeek 用的就是这个。top-k 检索是在低维空间里算相似度，用余弦距离做检索——不过一般不是用余弦，其实就是点积，但差不多是这个意思，也可能他们事先做了归一化，这个细节我不太确定。

总的来说这是一种非常廉价的实现全局注意力的方式，因为它只需要写个 kernel 就能完成；而另一种做法需要跑两遍，但精度可能更高。这两种我都见过，用得很普遍。

#### KV 压缩：让缓存装得下

有多少人在语言建模课上见过 KV 压缩？我来解释一下。

在标准多头注意力里有很多个头，每个头都有自己的 key 和 value，它们都有各自的维度。你会有一定数量的注意力头，设为 $H$ 吧。要解决或缓解 KV 缓存过大、开销过高的问题，主要有两种方法。

**第一种是分组查询注意力 GQA**：用比 $H$ 更少的头——通常是 $H$ 除以二的某次方——来提供 key 和 value。因为存的是 K 和 V 缓存（不含 Q），减少所用的 key 和 value 就能降低存放 KV 缓存所需的显存。这一点很重要，因为缓存太大会限制单张 GPU 能装下的数量，通常能缩减到 1/4 或 1/8 左右。

**多查询注意力 MQA** 就是只有一组的分组查询注意力，这个你们基本可以直接略过，你已经明白了。

**第二种是多头潜在注意力 MLA**：它本质上是做降维投影，把 key 和 value 的尺寸降下来。它不是减少头的数量，而是把每个头变小——这跟我前面讲的 top-k 注意力类似。当然两种方法也可以结合起来用，比如分组查询注意力配上更小的 key 和 value。

有了这些模型，就能处理多达一百万个 token，可以说这就让效率成为了可能。

### 训练长上下文

这件事其实相当难。原因在于：如果你想让模型处理十二点八万甚至更多的 token，实际上互联网上并没有那么多由十二万八千个连贯 token 组成的数据。这个量级已经相当于一整本书了，比大多数维基百科条目都长——而互联网上并没有那么多书。

#### 先短后长：为什么不能一步到位

所以通常的做法是分三步：先做短上下文的预训练，再用更长的文档做继续训练，最后进行长上下文的适配。

顺便说一个容易被误解的做法——**打包序列**（packing），把多份文档拼进一条序列。它对效率是有用的，但对学习长上下文没什么用。因为比如说你把十份文档打包进一条序列，模型学到的并不是跨文档的注意力，而且其实也不应该这样学。所以你真正需要的是连贯的长篇数据，才能完成对超长上下文的适配。

#### 位置编码：RoPE、NoPE 与长度外推

训练模型来处理超长上下文，第一件事是处理位置编码。

**绝对位置编码**大家应该都见过了：每个词嵌入都会得到一个位置向量，通常由某种函数计算出来，比如用正弦余弦。这个大部分人都见过，我就略过了。

**RoPE**（旋转位置编码）大家可能也见过——不过比我预想的要少，也可能大家只是不太想举手。在我看来 RoPE 在数学上还是挺优雅的。他们想解决的问题是：**让位置嵌入被完全去掉，由两个 token 之间的相对距离来决定**。至于他们为什么想这么做，是因为他们不想让绝对位置影响两个 token 会不会互相注意。这个方法相当有效，而且有很多很多模型都在用。数学细节我今天不展开，因为它不是重点——但它用到了旋转、虚数这些有意思的东西。

另外还有一种做法是干脆完全不用位置编码。如果你上过 Transformer 的课，你可能听过这种吓人的说法：Transformer 必须用位置编码，不然位置 1 和位置 5 的词会得到完全相同的表示。比方说这句里的 "cat" 和那句里的 "cat"，模型对两个词的注意力就会一样多。

理论上 Transformer 刚提出时也许是真的，但现在我们用的 Transformer 已经不成立了。为什么？

我们回到 Transformer 的公式：公式里有 key、有 query，再看 query。即使位置 2 和位置 5 都是 cat，位置 2 的 cat 只能看到前一个 token，而位置 5 的 cat 能看到前面四个 token——两者其实已经不同了。**至少从第一层注意力开始，哪怕是完全相同的词，它们的表示就已经不一样了。** 有一篇挺反直觉的论文证明了你根本不需要那么多位置编码，在自回归 Transformer 里尤其如此。

而**在非自回归 Transformer 里，所有 token 相互注意，你仍然需要位置编码**。这一点在讲门控 DeltaNet 的时候尤其明显：门控 DeltaNet 有衰减项之类的机制，能让每个 token 都不一样，所以一旦有了这类局部偏置，我们其实就不再需要位置编码了。

看一下各家的情况：前两个用的是 RoPE，或者至少是部分 RoPE；后两个是 NoPE，也就是没有位置编码，其中一个完全依赖 Mamba 这类循环结构自带的顺序信息；另外几个用的是相对位置编码。所以用不用相对位置编码，基本上是一半一半。

> **提示**：这里说的 NoPE 只对**自回归**架构成立。encoder-decoder 或全注意力双向的架构里没有因果掩码，每个 token 看到的上下文一样，位置信息必须显式提供。

但假设我们确实用了位置编码，长上下文里有一件事你要注意，那就是**位置差值或者说位置扩展**：如果你的预训练范围有限，你就需要把模型扩展一下，让它能处理更长的序列。

RoPE 的承诺是它只依赖 token 之间的相对位置，也就是序列中不同 token 之间的相对位置。只要相对位置还在某个范围内，这似乎没问题。其实有两个原因说明这并不成立：

1. 如果你在长度为 $L$ 的序列上训练，然后扩展到长度为 $sL$ 的序列，那模型从没见过有两个 token 相距超过 $L$ 还互相注意，所以相距超过 $L$ 的 token 就很难彼此注意，你也很难把这种情况处理好。
2. 相对位置编码其实只是故事的一部分，自回归掩码这些因素也都有影响。所以你不能光靠 RoPE，就指望它在更长的序列上也表现很好。

修复这个问题的常见做法是利用 RoPE 里的一个参数：RoPE 有个 $\theta$ 参数，它决定每一步旋转多少，然后你把 $\theta$ 除以序列扩展的倍数：

$$\theta_i\ \longrightarrow\ \frac{\theta_i}{s}$$

这相当于在拉伸 RoPE 的位置，使位置 $s$ 处的 RoPE 位置能够对应到更远的位置上——原来的位置 5 会变成 $5s$，正好对应扩展后上下文里 $5s$ 这个位置。

另外还有一种更精细的做法叫做 **YaRN**。它思路上有几分像 Kimi 的 Delta 注意力：基本思路是我们希望有些信息传得很远，有些则不用传那么远。本质上是让一部分维度扩展得多、一部分扩展得少，所以并不是所有维度都用同一频率去插值。出于时间考虑，这块我不会展开太多细节。

#### 长数据从哪儿来

从具体的建模细节里跳出来，讲讲你可以用什么数据来训练。

就像之前说的，打包样本可以把一大堆东西塞进上下文长度里，这样能训练模型处理上下文窗口末尾附近的内容，但它学不到那种全局连贯性。所以人们有不少不同的做法：

- **直接找很长的文档**，比如书籍之类的，这类文档不多，但数还是有的；
- **代码仓库**。代码仓库通常比较连贯，下载一个大代码仓库肯定能拿到更多 token；
- **某种多文档语料**。比如你可以收集一大堆同一主题的文档，这样至少它们之间有主题上的连贯性；
- **专利**。因为专利的公开数据很多，而且你可以把它们关联起来；
- **agent 轨迹**。现在一大来源就是这个，因为你只要跟 agent 交互一会儿，它就能产生非常非常长的轨迹；
- **合成任务**。很多评测本身就是合成任务，所以这条路也走得通。

具体怎么做的例子我这里有一些模型。顺便说，很多模型训练公司不愿意跟你分享这些细节，因为这属于比较敏感的信息。像 Anthropic 连架构细节都不会公开；而开源公司必须公开架构细节，不然跑不了他们的模型。那他们保密什么呢？他们保密的是数据配比和训练策略。

不过每一家都多少介绍了点自己的数据配比：清理过的样例文档和视频、文档仓库文件、issue、PR、长文档、问答、科学论文和技术报告；然后他们还会造大量合成任务；而且通常有一套扩展策略，比如 8 到 64、256 到 100 万这种。

#### 上下文并行：建模的人和基建的人会打架

还有一个你可能需要处理的实操细节，也可能不用，取决于你训练的模型有多大。比如你的项目如果想开始搞大一点的模型，就会碰到上下文并行。

训练和推理做并行有多种方法，概括地说就是数据并行和模型并行。模型并行可以有很多种：比如专家并行，把不同的专家放到不同的机器上；更一般的是张量并行，把要计算的张量拆分到不同机器上，也就是把参数切开；还有流水线并行，把不同的层放到不同的设备上。

不过**上下文并行对 agent 来说越来越重要**，因为训练 agent 时你要用非常长的上下文来训练它。它的原理是这样的：你先算出一段上下文的 key 和 value，把它发给下一个设备，那个设备算出自己那部分的 key 和 value，再发给下一个设备，就这样一直传下去。

这非常有用，一旦上下文超过三万二左右，它就变得重要了。但它也挺麻烦的：

```text
  建模的人："我要我的门控 DeltaNet！"
  基建的人："等等，那我得给它实现上下文并行的 kernel，
                得保证真的能跑通，还能反向传播……"
                       ↓
              这两边的需求经常直接冲突
```

这些事我自己就碰到过。我之前想训练比较小的 Qwen 模型，比如 1.3B、3.5B，我想给它用上下文并行，结果发现网上根本找不到门控 DeltaNet 的 kernel。所以你要么自己动手实现这个 kernel，要么就换个方案。

好消息是，标准注意力、滑动窗口注意力这些，它们的 kernel 都比较容易找到。现成的容易，难就难在你不做标准注意力运算的地方。

### KV 缓存：agent 账单里最大的一笔省钱空间

这一点非常关键。哪怕你不是亲手实现语言模型的人，哪怕你只是自己去跑 agent，我也会讲讲它的技术实现细节，让你至少对它的原理有个清晰的认识。

#### 缓存为什么能便宜十倍

当我们生成 agent 调用时，会有一个输入，输出一段消息和工具调用，然后工具返回结果。所以我们在计算输入这一步时执行的就是 prefill 预填充，计算输出的时候基本上就是在做解码。

在 prefill 和 decode 时都要算 KV 缓存，prefill 部分一次性处理完成，解码则在每次生成 token 时都会做。做完之后、输出结束之前，每个位置的 key 和 value 我们就都有了，这样就可以把它存进缓存，以后就不用再算了。

工具结果属于新增内容，因为我们没有对它做过计算，这样它又变成新的输入；我们生成输出，再得到一个工具结果，然后进入下一步——在 prefill 阶段对新输入算 KV 缓存并生成输出。不过缓存是可以复用的，接下来我们就这样反复迭代。

```text
  第 1 步  输入: [system | 用户任务] ──► prefill ──► KV 缓存 = [system, 用户任务]
                                                     │
                                                     └─► decode 输出:
                                                          助手消息 + 工具调用
                                                                │
  工具结果（尚未计算过的新内容）  ◀──────────────────────────────┘
  第 2 步  输入: [system | 用户任务 | 上一步的全部内容]
               └─► 前缀全部命中缓存，只对新增部分做 prefill 写入缓存
               └─► decode 输出: 新的助手消息 + 新的工具调用
  ……循环

  到第 50 步时：不做任何优化，要处理的上下文规模 ≈ 新输入的 50 倍
  有缓存时：    只算新增的那几个 token，历史一律只读不算
```

论文里研究这个问题的例子可以看到：横轴是不同 GPU 上的 token 长度，一列是使用缓存、一列是不使用缓存各自需要的计算量；同一颜色里下面那条是使用缓存的情况，上面那条是不使用缓存。可以看到序列越长，不用缓存的那条呈二次方增长，用缓存的基本是线性增长。

这也体现在你运行 agent 要花多少钱上。这些数字都是从官方定价页上拉来的，包括商业模型的——你会发现**缓存命中的 token 价格通常只有未缓存的 1/10**。所以你要非常清楚自己的 token 有没有被缓存，一旦没缓存，你运行 agent 就要花很多钱。

那么多高的缓存命中率才算好呢？有人说 80% 到 90%，也有人说 95% 以上。我的印象是 **90% 到 95% 一切正常**；低于这个数也许还能用，但可能在什么地方吃了亏——所以说，你的大部分 token 其实都可以被缓存。

另一个有意思的倍数关系是：输出这边的开销通常在输入的五倍，而输入命中缓存之后又只有未缓存输入的十分之一，于是输出和缓存输入之间差了 50 倍。这正好反映了两者成本上的差距，也就是你在做服务时能省下多少。

那为什么缓存会便宜这么多？原因其实比较明显：你只需要把这些东西查出来，而不是真的对它们做计算。尤其是 Transformer 里前馈网络的计算非常昂贵，所以能跳过这一步是特别大的优势。

#### 分页注意力与基数树

那我们实际要怎么管理它呢？第一个问题是怎么把它存在内存里。

最流行的两个开源 LLM 服务库是 vLLM 和 SGLang。催生 vLLM 的核心创新叫 **PagedAttention**（分页注意力）。它的工作原理大致是：你有一块块物理 GPU 内存，把它们组织得像内存块或磁盘块那样——就像在更典型的基于 CPU 的机器上那样。所以你可能有块 0、块 1、块 2，而你要实际计算的逻辑块可以被放进块 7、块 1、块 3。生成的时候，你有一个索引指向其中每一块。

他们这么做是为了能并行生成很多序列：当你生成完毕就可以把它淘汰出内存，这样你能一次性淘汰整个内存块，让计算更高效。这就是他们用来实现并行服务的一个技术技巧。

催生 SGLang 的技术创新叫 **RadixAttention**（基数注意力），它专门针对的是复用已经缓存过的输入。他们的做法是构建一棵树——基本上就是一棵基数树——用它来查找已经用过的前缀。它刚出来的时候主要是针对像 ChatGPT 这样的聊天机器人，因为用户会开启一段对话再继续聊下去，这样已完成对话的一部分就能被缓存住。

但现在这对 agent 更重要，因为 agent 的对话更长也更频繁，所以我们需要更频繁地做这种查找。

#### 缓存感知路由与淘汰策略

另一个要考虑的问题，比如 SGLang 的新版本里已经处理了：假设你在做多机服务，也就是在不同的机器上提供服务——也许你有个数据中心，有 64 个或 128 个节点之类的。每次请求进来，你都想把它路由到存有你 KV 缓存的那台机器，那台机器上的 KV 缓存最适合你来访问。这就有了**缓存感知路由**：把请求路由到合适的地方，让持有最匹配 KV 缓存的那个 worker 来处理请求。

我很喜欢从 OpenRouter 拿服务统计数据，因为他们数据量很大，而且覆盖了我想讲的所有内容。我记得他们甚至还有一个按缓存命中率给服务商排名的榜单——数据不会说谎。你可以看到有的服务商缓存命中率是最差的，而像阿里云、硅基流动这些服务商命中率就更高。

> **提示**：这并不完全说明这个服务商就差，也可能只是他们跑的负载不一样。

有几个因素会影响这个缓存命中率，其中之一是缓存路由做得好不好，另一个是缓存淘汰得有多快。服务商不会永远帮你保存缓存，过一段时间后他们就会把你的缓存淘汰掉。

主流服务商一般保留多久呢？据我所知，Anthropic 以前是 5 分钟，现在接近一小时。基本上只要你们还保持着活跃的对话、中间没停下来，缓存就会一直保留；一旦停下对话，你就会被逐出缓存。我想现在至少有延长到一小时的选项，但选一小时的话费用会稍微贵一点。说到底，他们不想一直留着这些缓存，因为占用的内存实在太多了——能用就保留，用不上就淘汰，这也是影响缓存命中率的另一个策略。

对我们用户来说，坏消息是：不管提供商的路由和缓存淘汰做得多好，价格都不会变。你可能仅仅因为他们淘汰得太快就多花了钱，这感觉有点不公平。

那他们有没有用缓存分层，就是把快的缓存放在设备内存里、再放一层更慢的在磁盘之类的存储上？说实话我也不知道答案，这倒是值得我们后续跟进研究。另外开源库可能也没闭源方案那么精细——你看 OpenRouter 上那些提供商，他们本职工作就是把推理服务做到极致，所以有些人可能用的是开源库，但会在上面自己搭建东西，这算是他们的竞争壁垒。所以推理提供商的内部方案在缓存分层这块很可能比开源的更好一些，他们通常把缓存从 GPU 卸到 CPU 上，因为 GPU 显存实在太宝贵了。

#### 写框架时千万别把缓存弄坏

我漏讲了一个重要的部分。如果你只是在设计框架、并不负责部署模型，这意味着什么呢？**这意味着你要非常非常小心，别在无意中把缓存弄坏了。**

记住：**只有整个前缀完全一样，缓存才能生效。** 我们想过不少看起来很合理的改动，但最后认定都是很糟糕的主意，因为我们不想破坏缓存。

有一件事是完全禁止的：**你绝对不要每次都改系统消息**。每走一步就改一次，因为这基本上等于完全没有缓存，你连一条能缓存的消息都没有。

有个听起来很合理的想法是，把当前时间和日期附在系统消息后面，这样 agent 就知道现在几点——**千万别这么做**。因为时间日期每一步都在变，会破坏你的缓存。如果你确实要附加，就附加到最后的用户消息，或者最后一次工具调用的结果里。

在对话中途动态更换工具，这个可以没问题。

另一个很合理的想法是：每一步路由到不同的模型。比如这一步看起来很关键，就交给一个强大的模型；接下来三步换到便宜的模型上省钱。但问题是钱还是省不掉——下次再用那个贵的模型，你还得付那十倍的价格。如果想靠切换来省钱，那你真的要非常节制地控制切换的次数。

### 上下文压缩

有多少人日常用 coding agent 会用到上下文压缩？看到"正在压缩上下文"的时候，有人觉得兴奋吗？

没人举手。很好。

上下文压缩的基本思路是这样的：在这之前你有一大堆历史，包括所有的观察和动作，而之后你要做的就是把之前的上下文压碎，只留下之前上下文的精华。大家之所以不太愿意用它，显然是因为一旦做得不好，agent 就会忘事，开始做完全不同的事情，甚至可能删掉你的文件系统。

我们可以把压缩看成是在尝试找到一种对历史的表示，使得你未来的动作序列保持不变——你把历史压缩得到一个工作状态，你希望未来的动作序列能保持不变，压缩后和之前相似，甚至可能更好。同时还有一个约束：**你的状态必须是有界的**，也就是要足够小到你还愿意继续往下工作。

#### 压什么、留什么

那压缩之后什么东西能留下来？做法有好几种。一个常见的策略是**留几个锚点**。

```text
  压缩前：
  [ 开头的锚点 ][ 历史动作 1 ][ 历史动作 2 ] ……… [ 最近几步动作 ]
     很长很长很长 ..............................  短

  压缩后：
  [ 开头锚点 ][ 中间部分的编码摘要 ][ 最近几步 ]
       逐字保留        有 界          逐字保留

  两条约束：
    1. 压缩后模型未来的动作序列要和不压缩时保持一致（甚至更好）
    2. 状态必须有界，小到你还愿意继续往下工作

  兜底：命令行 coding agent 的完整历史一般保存在磁盘上，
        知道存在哪，就能让 agent 回去把之前的结果读回来
```

回到我刚才问大家"agent 会忘掉什么"，这个问题有个回答是：有时候他们会忘掉会话最开头的东西。这其实可能是你所用 agent 框架的设计缺陷——一些好的框架会有意避免删除会话最开头的内容，觉得那部分更重要。当然视情况不同，有时也难免避不开。

另外你希望中间部分的内容被编码后放回上下文，而最近的尾部通常也会保留，人们往往会留下最近的几步操作。除此之外，虽然我不太常见到，你还可以把证据存进一个证据库——更正一下，证据通常就是会存进证据库的。

#### 什么时候压、压成什么

怎么定义压缩策略？有几种方式。

**第一个是触发条件**，基本上是两种做法：一种是 token 阈值，就是给 token 设个上限，比如"我最多只用 20 万 token，一旦超过就压缩上下文"；另一种是被迫这么做，也就是服务商强制的、相当于对 token 数量的硬性上限；最后你还可以手动触发，比如很多 coding agent 工具包都有 `/compact` 这样的命令可以用来压缩上下文。

**触发之后你就要做选择了**：可能保住开头、留下最近的尾部，然后压缩较旧的部分，把它换成一段摘要。这个摘要可以是结构化的，有时会要求通过 tool call 来生成，也就是规定这些内容必须写进压缩摘要里；有时候就是自由文本；还有一种我记得可能只有 OpenAI 在用，他们把上下文压缩成加密的东西，你读不了，所以看不到他们怎么压缩的，因为不想让你偷走他们宝贵的压缩算法。

然后你就可以继续在这个基础上工作。

这里的一个风险是：**你可能会反复不停地压缩。** 第一次没问题，但压缩的次数越多，丢失的信息就越多——这也是人们不喜欢压缩的原因之一，它会让 agent 跑偏。所以我们评估它的方式通常是从整体层面来看：你可以替换不同的压缩算法，用你现有的基准来评估它。

#### 基准不掉分，不等于它真的好用

关于这一点，我想提醒大家，我有个故事。当年我们刚开始开发 OpenHands 的时候，其实做出了最早的一个生产级的压缩算法。我们用 SWE-bench 来评估它，这是编码 agent 很常用的基准。我们下了不少功夫，把它当成一个研究项目，做了大概一个月左右。当时我们觉得压缩策略很棒：分数完全没降，还省了大量 token。

后来真正用到系统里，它就犯了一些特别蠢的错误。比如**每压缩一次就发一个 PR，因为它忘了自己已经向 GitHub 发过 PR**，同一个功能我们收到了五个；它还会忘掉对话中途用户发的指令——因为我们只在单轮对话上评估过，那种只有一条用户消息的场景，我们把多条用户消息都压缩掉了。

> **结论**：光靠基准测试是不够的。除非你的基准足够健壮、能覆盖每一个使用场景，你还必须在真实环境里测一测。

## 记住上一次：AI 怎么把过去的经验变成技能
> 对应块：BLK04 | 覆盖分集：P04 | 块标题（分集名）：《04｜智能体的记忆与技能【中文配音版】》

上一讲我们讲，agent 可以选择在上下文窗口里保留哪些内容，以此作为一种存储信息的方式，在任务内部进行存储，并用这些信息判断什么是重要的，从而把任务做得更好。今天很大一部分内容要往前推一步：AI 如何超越上下文窗口，把信息跨任务存到外部存储里，用来帮助自己提升未来任务的表现——这就是**技能归纳**。

我们会先基于过去一些关于 AI 记忆系统的工作，看看怎么把它们应用到 agent 上。不过技能还有另一种视角：可以把最佳实践、或者你对"这个任务该怎么做"的理解，直接编码进去。这两种视角其实是互补的。

> **提示**：你可以想象这样一个系统——有人参与其中，让 agent 从自己的经验里提出一些潜在的最佳实践，再由人来修改，如此往复；或者反过来，一条由人写好的指令、一项技能，由 AI 根据经验来加以完善。视角确实很多，但希望到这一讲结束时，你们能看到它们是怎么融合在一起的。

### 上一次搜过的商品，这次还想直接用

先从动机讲起：为什么想让 AI 记住一个任务里的东西，用到另一个任务上？

比如我们有一个 agent 在网站上执行任务，比如购物网站。你给他一个任务，比如"把索尼耳机加到我的心愿单"。讲到 GUI agent 的时候，我们会深入这类系统的表示空间、动作空间的细节，但从高层来看，它会产生这样一串动作：

```text
导航到商店网站 → 找到搜索框 → 在搜索框里输入文字 → 点击"搜索"
```

这部分就是搜索耳机，对吧。然后我们再对这些耳机做点什么——找到符合用户要求的那些商品，放进心愿单。以后我们可能还会执行别的任务，比如查找无线键盘的价格区间。

如果是在同一个网站上做很多操作，这一段都能复用，对吧？我们进商店、找到搜索框，用类似的方式搜索另一个商品，然后做些不同的事，比如拿到价格再汇报给用户。但如果 agent 很难弄清怎么完成这个搜索，那他一旦学会了，就应该能在以后复用这个知识，把未来的任务做得更好。

> **结论**：很多结构会反复出现，今天要讲的就是如何表示这种共享结构。

于是三个问题跟着来了。最好是直接保留 agent 执行这个子任务时产生的原始操作吗？还是说更好的做法是把它抽象成一个代码函数——可以当黑盒运行，可以测试，甚至能分层调用其他函数？我们还会关心，agent 如何判断任务的哪些部分以后值得复用。另外，任何时候我们都要从经验中构建记忆，这时就会有这些问题：我们该怎么让这份记忆增长？是一直往里加吗？遇到冲突信息怎么办？找到更好的做法时，我们可能想对它做修改；如果某些内容不再适用，我们可能想删掉它们。那怎么管理这些学到的技能和子任务表示的生命周期呢？

### 让 AI 更新自己的三种方式

我认为要让 AI 更新自己大致有三种方式。

#### 上下文窗口里的历史

第一种我们上节课讲过，就是模型上下文窗口里维护的内容，也就是标准的 ReAct 记录方式：过去观察和操作的历史、用户发来的消息、来自环境的反馈。你需要决定保留哪些内容，这要考虑上下文窗口的限制，以及模型利用这些信息的能力。我们讲过很多关于压缩的方法，以及管理上下文窗口内容的方式。

问题是，即使我们现在的上下文窗口已经很长了，比如一百万个 token，让 agent 执行多个任务时，你还是会超出这个上下文窗口。你会想记住过去任务中的东西，来帮助完成未来的任务。

#### 窗口之外的外部存储

如果我们在窗口之外存储信息，那看起来就像一个需要某种方式管理的数据库，或者一个 agent 可以访问的文件系统。这一讲要讲的就是如何把信息放进这些存储里，以及怎么使用和更新它们。

#### 直接更新模型权重

最后一种方式是真正去更新模型的权重，这更像是标准的监督微调或者强化学习，几节课之后我们会讲到。

这几种方式各有利弊，但用外部产物，我认为一个主要的好处是它们可以跨模型移植，对吧？比如你有一份搜索产品方法的描述，那么框架里的很多不同模型都可以用它。而如果你是直接更新模型的权重，那只是针对那个特定模型的更新，没法迁移到其他模型。另外外部产物也更容易被人检查：写下最佳实践，比如"网站怎么搜索"，agent 就能用上；agent 也可以提出类似的文本建议，你查看之后再做修改。只要你的记忆和更新方式是可解释的，人和系统之间就更容易建立交互界面。

| 方式 | 存的是什么 | 好处 | 代价 |
| --- | --- | --- | --- |
| 上下文窗口 | 历史观测、动作、消息，按 ReAct 格式排 | 模型直接就能用 | 窗口有限；跨任务用不上；压缩会丢信息 |
| 窗口之外的外部存储 | 记忆、事实、技能 | 可跨模型移植、可被人检查、可跨任务复用 | 得自己设计一套管理和检索的机制 |
| 更新模型权重 | 监督微调、强化学习的结果 | 直接改变模型行为本身 | 绑死在特定模型上，不好检查，也难"忘掉"旧知识 |

在讲具体方法之前，先打听一下大家的实况。有多少人在使用编程 agent 时用过技能？——大多数。有多少人自己动手写过技能？——大概占一半。有多少人让 agent 替你写过技能？——还真不少。那让 AI 写技能，你们的体验怎么样？AI 写出来的技能，有多少次能直接拿来就用？

有个同学提到的失败模式很典型：模型有时会在技能里写太多内容，有点过度推断该做什么，然后交给另一个模型时，他会严格照办，做的比你实际想要的还多。也有很成功的例子：你在给某个系统排查生产问题的时候，给它三四张支持工单，然后告诉它"看看大家以前是怎么调试这个问题的，给自己创建一个技能，让以后遇到的也能用同样的方式来排查"——效果就非常好。就是说，让它替另一个 agent 写操作指引，他还挺擅长模拟 agent 会怎么做的。

> **提示**：我有时发现，模型不太擅长模拟别人、或另一个 agent 看到指令时的想法，但只要你提示它这么做，效果就会好很多。

### 什么值得留下来：经历、事实、技能

那对 AI 来说，有哪几种不同类型的经验是值得保留的？

#### 经历（episode）

第一种是 episode，也就是你从环境、用户和执行者那里得到的一系列观察。这基本上是保真度最高的方式，对吧？你就是把所有内容都保留下来，那个环境的各种细节、用户给的具体指令都在。

但它的成本也最高，对吧？需要最多的 token 来表示，而且你多半不需要全部这些。就像做监督学习时，我们不会保留每个细节，我们要抽象出关键的东西，才能在未来泛化。

#### 事实（fact）

我们也可以保留一些事实，比如关于环境或者用户的知识。在早期关于记忆系统的研究里，很多工作都聚焦在事实上。比如用户在和助手交互时给出一些个人信息，像年龄多大、住在哪里，系统就可以把这些存进记忆，之后再利用这个事实来改进未来的交互。

如果你用过 Anthropic 或 ChatGPT 的记忆系统，他们基本上就是这么做的，对吧？你可以进设置查看他们关于你的记忆，那里有一段文本是模型从你过去的交互中提取出来的那些事实。这有点像压缩：由 LLM 生成一段总结性的东西，存到这个外部存储里。

#### 技能（skill）

最后一种更针对 agent：它说的是怎么在完成任务的一部分时，把任务的具体细节抽象掉。就像我们前面看的例子，怎么在某个网站上搜索商品，而不用记住搜索某个具体商品的那些细节。

技能只有在你需要重复执行同一个子任务时才会派上用场。我们可以想想记忆、技能以及两者之间的交集：记忆就是我们从 agent 自身交互中保存下来的东西，比如你之前在某个网站买过什么产品；而技能是关于如何在环境中行动的可复用知识。

可复用知识可以用多种方式来表示。比如你要发布一个应用、把它推上生产环境，技能可以是一份清单，写明上线之前你需要逐项检查的内容。技能可以像这个例子一样由人来写，但我们也可以把记忆和技能结合起来用：我们可以从 agent 过往的经验中归纳出技能并存下来，希望之后能做得更好。比如 AI 过去成功搜索过某个商品，如果我们认为那次是成功的，就可以从中提炼出类似技能的东西，来指导它之后的行动。

技能也可以看作指令。这种指令可能是人写的，用来表达自己的偏好，也可能是组织规范，比如"我们公司就是这么写和测代码的"。人工编写的技能，我们知道它的来源，质量上也更容易把控，但编写和维护都很花时间。如果是让 AI 自己学习并生成技能，好处是可以自动化地完成这件事：可以做个循环，归纳出技能，用它重做同样的任务，看效果是否变好，在某个指标上看效果。但它也可能有噪声，尤其是当你把这些技能给其他 agent 用时，还可能带来意想不到的后果。


### 人工编写的技能长什么样

好，我们先来讲讲人工编写的技能：它们的相关标准，以及目前 agent 里的使用方式。听起来在座的很多同学已经有相关经验了。

OpenHands 有一篇很好的博客文章里面讲了怎么使用技能。如果你还没用过技能，或者想了解创建和使用技能的最佳实践，可以参考它。他给了一个很典型的例子：假设你发现自己总是在给 coding agent 下类似的指令——你想用几种不同的 linter 来检查写好的代码，想加类型注解、固定格式、写 docstring、所有函数跑 pytest。如果你每次都这么做，当然可以每次都把这套指导手动输入到系统里，但还有一个更自然也更快的做法，就是把这些指导存成一个文本文件，然后让 agent 把它当作指令来使用。

> **结论**：所以当你想按照固定规范反复做某件事时，就应该用技能。AI 会根据上下文自行决定怎么解释这个规范，但总体指令是一样的。

#### SKILL.md 与可选的资源目录

在目前叫做 Agent Skills 的技能标准里，它的实现方式就是一组 agent 可以读取的文件。比如我们要构建一个 Python 代码审查的技能，就会有一个结构如下的文件夹：

```text
python-code-review/
├── SKILL.md              # 必须有：YAML 元数据 + 详细做法
├── scripts/              # 可选：可执行代码，如跑 linter 的 Python 脚本
│   └── run_lint.py
├── references/           # 可选：补充文档，不是每次都要用
│   └── style_guide.md
└── assets/               # 可选：模板和静态资源，按条件加载
    └── review_template.md
```

SKILL.md 是必须有的，它是一个 Markdown 文件，开头是一段 YAML 元数据：你需要给技能起个名字，还要写一段简短描述。这段描述会告诉语言模型这个技能应该在什么时候使用。头部之后是对技能如何应用的更详细说明，比如列出所有应该用的 linter、测试该怎么做等等。

另外还有几个可选的文件夹，可以放一些额外资源供 agent 执行技能时使用。`scripts` 文件夹放可执行代码，像跑 linter 的 Python 脚本就放进去，然后在 SKILL.md 里描述它；`references` 文件夹放补充文档，你可能不需要每次使用技能时都用到它，但可以在技能文件里放一个指向这份文档的引用，agent 按需加载；`assets` 主要放模板和资源，在相关任务里需要 agent 按条件加载它。

#### 渐进式披露：按需把内容送进上下文

这些信息可能很多，对吧？我们肯定不想把模型可能用到的所有技能都塞进上下文窗口里。所以有一个叫渐进式披露的机制，只在需要时向 agent 展示技能的相关部分。

```text
┌────────────────────────────────────────────────────────┐
│            第 1 层 · 系统 prompt 里始终都在            │
├────────────────────────────────────────────────────────┤
│ SKILL.md 的 YAML 元数据：name + description            │
└────────────────────────────────────────────────────────┘
         │  模型判断相关 → 工具调用读取
         ▼
┌────────────────────────────────────────────────────────┐
│                   第 2 层 · 条件加载                   │
├────────────────────────────────────────────────────────┤
│ SKILL.md 正文：具体做法、该用哪些 linter、怎么跑测试   │
└────────────────────────────────────────────────────────┘
         │  SKILL.md 指路 → 再次工具调用
         ▼
┌────────────────────────────────────────────────────────┐
│                  第 3 层 · 更细的资源                  │
├────────────────────────────────────────────────────────┤
│ scripts/ · references/ · assets/                       │
└────────────────────────────────────────────────────────┘
```

第一层是 SKILL.md 文件里的元数据，也就是名称和描述。只要技能被加载了——也就是模型可以使用它——这些信息就始终会显示在系统 prompt 里。所以这个描述要写得简洁一点，这样即使技能很多，也不会把空间占得太满。

第二层是 Markdown 文件里的其余文本。如果模型判断这个技能相关，并通过工具调用来读取文件的其余部分，这层会被按条件加载。

再下一层就是那些可选目录里的所有资源，他们也会通过工具调用来加载。所以 SKILL.md 里得写清楚足够的信息，让模型知道执行技能时应该去那些额外的文件夹里找更多资源。

#### 跑起来是什么样：一个系统提示和三个观察

那渐进式披露是怎么工作的？首先得让模型能访问第一层内容，对吧？让它知道有哪些技能可用。这时你会看到一个类似这样的系统 prompt——这个例子取自 Hermes agent，它算是一个标准的开源 agent，能够使用和归纳技能。你要在里面描述一下什么是技能，还要告诉模型有这样一个"查看技能"的工具，模型可以用它读 Markdown；其余部分再列出所有技能。这里只有两个技能，一个代码质量技能和一个工作流技能，这些就是那两个技能文件里的 YAML 元数据。

这样模型就能通过工具调用，来展开技能的其余内容：

```text
┌────────────────────────────────────────────────────────────────────┐
│                             系统 prompt                            │
├────────────────────────────────────────────────────────────────────┤
│ 什么是技能 · 有一个工具可以查看技能 · 技能索引                     │
│ （两个技能的 YAML 元数据一直留在这里）                             │
└────────────────────────────────────────────────────────────────────┘
        │  用户："帮我审查这段 Python 代码"
        ▼
┌────────────────────────────────────────────────────────────────────┐
│ 发起工具调用，拿到 SKILL.md 正文                                   │
│ 作为一条消息（观察）插入上下文                                     │
└────────────────────────────────────────────────────────────────────┘
        │
        ├─▶  运行 scripts/ 里的脚本 → 运行结果作为观察进上下文
        │
        └─▶  查看技能包里的其他文件（references/、assets/）
```

系统提示里始终有技能索引，但如果看起来相关，比如用户要求审查一段 Python 代码，模型可以选择发起工具调用，打开 Python 审查技能，然后他会拿到那个 Markdown 文件，把它作为一条消息插进上下文，也就是作为观察结果。既能查看工具的返回结果，系统也可能选择运行 scripts 目录里的某个东西，然后把脚本的运行结果作为观察放进上下文窗口，还可能选择查看技能包里的其他文件。

### 技能多了、格式换了、平台也换了

好，刚才提的这些问题——比如多余的技能会不会带来负面影响、技能是否在合适的地方被触发——我们一个一个来。

#### 技能多了会不会拖后腿

有同学问：原数据是始终加载的，那如果技能数量特别多呢，比如有一万、五千个，如果占用太多上下文会不会影响性能？

会，肯定会影响。即使每个技能的元数据都很短，技能一多也会。所以你要把技能数量控制在一定范围内，最好按需加载。最先进的 agent，比如 Hermes agent，我不确定它有多少技能，但系统提示里技能描述加起来大约 3000 个 token。

> **结论**：接下来会看到几篇论文表明，技能太多反而会让性能变差。比如加入无关的技能会拉低性能，因为上下文变长了，模型可能被那些实际无关的内容分散注意力。不过拥有 1 万个或 1000 个技能其实很少见，通常规模小得多，而且你可以按手头软件任务的需要来加载技能。

那这些触发机制有多灵敏？这是个好问题。这些触发就是模型生成的 tool call，所以要不要调用完全取决于模型——取决于模型根据过往上下文和对该技能的了解，能不能预判出它应该被触发。这既取决于模型，也取决于你写的描述，所以我们才需要做评测。

#### 为什么是 SKILL.md 和 Markdown

有同学问标准化的问题：比如你想让代码也能在多个平台上用，怎么办？SKILL.md 是个标准化的文件名，这个标准就叫 Agent Skills 标准，模型和 agent 框架都训练过怎么使用它、怎么加载它。所以如果你想用别的格式，先尽量往这个标准靠；但如果你有特殊需求，也可以变通处理，比如放在 references 里的特别内容，直接写进 SKILL.md 也行。这些其实都是给语言模型的指令，只要你描述清楚，它对其他配置也能应付。

那为什么技能都是用 Markdown 来写呢？我觉得就是在机器可读性和人类可读性之间找平衡。有没有比 SKILL.md 更好的格式？它其实是很线性的：可以加超链接，这挺好，也能嵌入图片，这些都挺好的。不过呢，要表示动态的东西就比较难了。比如你想给模型演示数据可视化的各种不同方式，也许用交互式的 JavaScript 应用之类会更好。对，你可以把那部分做成一个会执行的代码文件，然后在 Markdown 里引用它。

> **结论**：所以我觉得 Markdown 已经是兼顾通用性和可读性的最佳尝试了，其他格式就得靠语言模型去解释。文献里基本上就是两种方式：文本的写在 Markdown 里，程序化的写在脚本里，把这两类都算上，覆盖面就很广了。

#### 技能也做检索

有没有人做过技能检索，就是不用把技能放进上下文？比方说你做一个修改云基础设施的 agent，你在某家大银行工作，AWS 里有海量的东西，你希望能直接让模型去修改某个东西，但正因为东西太多，你不可能为每个小组件都准备一个工具，所以看起来用检索会很好。

在某些研究论文里确实是这样。问题是：大家会不会从大规模的技能集合里做检索？会在接下来要看的一些研究论文里看到，确实有人这么做。要么就是用基于文本的 embedding 检索，要么用更偏向按领域条件筛选的方式，比如这些技能适用于某个网站，交互时就加载这些技能。我猜生产系统也会这么做，不过我一时想不起有什么相关的参考。

### 技能从哪里来，又该怎么检验

好，技能可以来自很多不同的来源。它们可能随运行框架捆绑提供，也可能由人编写——听起来在座不少人已经这么做了，然后按照所用框架规定的格式把它安装进去。但技能也可以由 agent 自己创建：Hermes 有一个技能管理工具，OpenHands 有一个创建技能的命令，引导你走完整个创建流程。

#### 凭空写出来的技能效果很差

创建技能时，我认为很重要的是以你过往的实际交互为基础，而不是凭空硬写。SkillsBench 论文里的一些结果表明，当只凭任务描述让模型自己写技能时，效果很差，反而会让性能下降。人来写通常更好，因为你知道自己想要怎么做。

> **结论**：但最好的做法还是基于你做过的事儿。因为做任务的过程，会揭示一些你事先可能想不到的偏好。

#### 用人的采纳率检验审查类技能

OpenHands 的博客文章里就有一个很好的案例。假设你创建了这个代码审查技能，那怎么检验它是否有效、必要时又怎么改进它？

这里以审查 pull request 为例：agent 产出审查后，由人逐条查看这些审查评论，决定是否采纳；之后再用模型裁判统计有多少条被人实际采纳——这就能反映审查质量的高低。你可以在大量 pull request 上重复这个过程，都由 agent 用这个技能来审查。如果在几百上千个例子上做这件事儿，你就能收集到大量证据，知道哪些有效、哪些没用。

然后你可以用推理模型总结这些发现，比如得出结论"生成忽视仓库规范的代码"没有帮助，但确实采纳了不少修改建议。接着你可以让模型给技能文件提一些更新，让系统产出的评审意见更容易被人采纳。


### 自动记住过去：MemGPT 与会改的记忆

接下来我们谈谈怎么让模型自动记住过去经验中的东西，然后在这个基础上讲怎么从经验中归纳技能。

#### 窗口外的工作上下文

这是一篇比较老的论文了，2023 年的，但它影响挺大，而且是最早的一批论文之一，叫 MemGPT。它是最早提出在语言模型上下文窗口之外管理记忆的方法的论文之一。这是一篇很有系统设计色彩的论文。

我记得几节课前我们讲过：记忆层级就是访问起来快的部分，对语言模型来说就是上下文窗口；然后还有一个更大但更慢的部分，在这个场景下那就是外部存储。

```text
┌─────────────────────────────────────────────────────────────────────┐
│                   语言模型这一侧，都在上下文窗口里                  │
├─────────────────────────────────────────────────────────────────────┤
│ 系统指令（不更新）                                                  │
│ 工作上下文（可更新）                                                │
└─────────────────────────────────────────────────────────────────────┘
      ▲ 写入检索结果                    │ 模型发出工具调用（读 / 写）
                                  ▼
┌────────────────────────────────┐   ┌────────────────────────────────┐
│ 外部记忆（事实、摘要）         │   │ 消息存储（系统实际收到的消息） │
│ 检索、增、删、改               │   │ 管理方式与事实记忆相近         │
└────────────────────────────────┘   └────────────────────────────────┘
```

这篇论文是几年前写的，那时上下文窗口更短，大概只有 8000 个 token，所以这种方法当时非常有说服力，哪怕只是和助手系统对话也一样。如今上下文窗口更大了，但你想往里面存的内容也多得多，所以这种方法对 agent 来说也很有意义。

基本思路是：你有系统指令，这部分不会被更新；你还有一个工作上下文，它会从外部记忆里取内容，同时你也会往这个外部记忆里存东西，这些读写操作由模型发出的工具调用来控制。另外还有一个单独的存储，用来保存系统实际收到的消息，但它的管理方式跟这个事实记忆差不多。

举个例子：你跟模型交互，用户提到了六旗乐园，就可以发起一个工具调用，在这个存储里搜索过去交互中提到六旗乐园的记录；系统会取回这些记录放进工作上下文，而这个工作上下文是存在语言模型的上下文窗口里的，这样模型在输出回复时就能用上这些信息。

#### 记忆也要能改能删

但重要的是，除了往记忆里添加，还得能做别的事。比如你跟系统聊自己的工作，说我在 X 公司上班，可后来你换了工作，你就希望系统能用上最新的信息。

有一篇叫 Mem0 的论文就提出了让记忆也能更新的方法。它的做法是：每收到一条消息，就用一个语言模型从中提取一些记忆，也就是你可能想存储或更新的一些潜在事实；同时你还有一个外部数据库，你会去检查这个数据库里有没有跟从消息里提取的事实相关的内容。你会检索 top-k，用 embedding 检索模型，跟我们之前讲的类似，找出相似的事实，比如"六旗乐园"，或者"我在 X 公司上班"；然后再用一个语言模型去检查，这些从最新消息里提取的记忆，在这些检索到的相似记忆里有没有出现过：

- 如果没有出现，那可能就应该把它加进去；
- 如果它是对已有内容的更新，我们就该用新信息替换掉原来存的那条；
- 如果它否定了已有的内容，比如你先说"我任职于 X 公司"，后来又说被裁了，那最好直接删掉这条事实，而不是更新；
- 如果完全不相关，就直接忽略。

具体细节大家可以去看论文，因为这套细节在 agent 系统里也会不断变化。但我觉得这个思路很有价值：出现冲突时，系统能更新已有知识，这非常实用。

有同学记得上节课讲上下文管理时，有什么方法的目标跟这个类似吗？——就是能更新或删除记忆。说到这个，那篇论文其实就做了这件事。对，线性注意力只能往记忆里追加值，但 DeltaNet 会真正检索出某个查询对应的存储内容，然后修改它，改掉那些存下来的向量。这确实提升了性能。这就相当于它的文本版，目标很相似。

> **提示**：你也可以想想第三种学习方式——直接更新模型权重。在那种情况下，能遗忘一些东西也很有帮助，尤其是存在相互冲突的知识时。现在大家也开始发展一些这类方法，比如机器遗忘（machine unlearning）就是一种做法。

### 从反馈里进步：Reflexion 与轨迹检索

以上就是一些面向助手开发的记忆方面的基础论文。对 agent 来说，来自轨迹的反馈可以非常有用。

#### 自然语言反馈

有一篇叫 Reflexion 的论文影响力很大，方法非常简单，但有效，能让 agent 利用反馈做得更好。这个方法绝对值得了解：如果你的项目希望 agent 能从过往经验中受益，它是个很值得实现的东西。

它的做法是：给定某个任务的多次尝试，我们来提升 agent 的表现。比如你让 agent 在网站上搜索一个商品，他尝试了一次，说自己完成了，而你能拿到一些反馈，判断他到底做对了没有。反馈可以来自人工检查，也可以来自用模型当裁判；拿到反馈之后，你希望模型再试一次，争取做得更好。

这篇论文展示的是，针对尝试结果的自然语言反馈，对模型第二次尝试时的条件参考非常有帮助。比如模型要回答某个系列战役的问题，他可能只提到了一场战役，然后语言模型知道这个答案不对；再看问题和答案给出的反馈，可能就是"你只给了一场战役，而不是一个系列"。可以想象，这种反馈对模型再次尝试时非常有帮助，他就能答对了。论文表明，以这种自然语言描述哪里出了错作为条件参考，效果确实很好。

我们还可以把这个方法推广开，让 agent 在做不同任务时也能不断进步。这里是在同一个任务上提升，但你可以想象，只要反馈足够通用，它也能帮助提升类似任务的表现。

#### 记住整条轨迹

最后一种帮助 agent 改进的基础方法，是记住轨迹，也就是他们过去完成的整条轨迹、整个回合，并用它来影响未来任务中的做法。这方面已经有很多论文了。

这些任务可以是一组示范，也可以是 agent 逐个执行任务时自己产生的，你要把这些任务汇总起来，可能还会额外生成一些描述反馈的文本，就像上一页 Reflexion 做的那样。这样你就有了这批经验；等新任务来了，你就从这组轨迹以及生成的相关文本里检索，找出与当前正在做的任务相关的内容，把它放进模型的上下文窗口，通常就能帮你做得更好。

> **结论**：这有点像是给 agent 用的 RAG，而且效果相当不错。

有同学问：这里的轨迹指的是什么？是一连串的工具调用吗？对。对 agent 来说，轨迹一般是指它从环境或用户那里收到的消息序列，也就是观测；它执行的动作，比如工具调用；还有可能也包括它生成的思维链。你可以把它理解为，基本上就是模型上下文窗口里那整串消息。

检索可以有很多种做法。你可以用普通的嵌入检索，也可以比较整个过程序列。通常的做法是：给模型一个新任务的描述让它去执行，你手上有这段文本描述，先把它做嵌入，用嵌入模型来嵌入，然后基于其他任务的描述来检索——这些任务各自都关联着一条轨迹。你还可以加个限定，比如只检索我们当前所在领域的任务。

这基本上是一整类方法，实例化的方式有很多，怎么积累经验、怎么做检索都各有不同。我只是想让大家有个概念：如果我们把过去成功的轨迹当作示例展示给 agent，它往往能表现得更好。


### 技能就是任务里可复用的那一段

有了这些铺垫，我们就可以正式讲怎么从经验中归纳技能了。我们可以把技能理解为任务中那些能跨不同任务复用的部分。

回到开头提到的搜索商品的例子。我们告诉 agent"给我看这个搜索词的结果"，AI 可能会产出这样一条思维链，接着执行这些真正和网页交互的动作，比如点击由这个 ID 标识的元素，也就是搜索框，在里面输入查询词，然后再点击另一个元素，也就是真正执行搜索的按钮。

任务的这一块内容，在未来的任务中可能会被复用。比如我问"这个商品的价格区间是多少"，它可能需要原样重复这些步骤之后，再做一些额外操作。所以我们可以把技能看作对任务中这部分可复用内容的一种规格描述。

> **易错点**：这样表示技能合适吗？有谁能想到什么问题吗？——如果页面上的元素 ID 变了，这个技能就会失效。情况有好几种：可能是同一个页面，只是元素编号的方式不一样了，这个可以调整动作空间来解决，那节课会讲；但如果换到一个搜索界面不同的网站，它就会失效。

评估技能归纳和使用系统的典型方式是在线学习设定：说你和 agent 交互时，可能会让它连续执行一堆任务，其中有些任务会彼此相似，你希望系统能从这些交互里学到东西，然后在以后做得更好。这就是在线学习：任务一个接一个地来。

举个例子，你可能会说"把索尼蓝牙耳机加到我的心愿单"。我们在解决这些任务的同时，会逐步积累一份技能和记忆，中间会有一个归纳步骤，创建出像"搜索商品""把商品加入心愿单"这样的技能。然后可能又来了另一个任务，我们把那些技能用在未来的任务上，比如这个任务可能也要搜索商品，那么有了从上一个任务归纳出的技能，我们希望能在这个任务上做得更好。以此类推。

> **结论**：我们关心的是：如果能衡量每个任务的成功与否，我们的成功率是不是在越来越好？我们能不能边从经验中学习、边积累这些简单任务的做法，从而解决越来越复杂的任务。

就像 Graham 说的，我们通常会对比用文本还是用代码来表示技能。我想先简要介绍几篇很棒的早期论文，我认为他们为技能归纳、也就是从经验中学习技能打下了基础。

一篇叫 Voyager，它控制 Minecraft 里的一个 agent，用代码来控制这个 agent，代码函数实现各种具体任务，比如合成某个物品或者跟僵尸战斗，把这些子任务表示成函数，函数之间就能互相调用。这样 agent 学会了简单任务的函数后，就能把它们组合起来，在其他函数里调用，从而完成越来越复杂的任务。

程序归纳领域也有一系列工作在做类似的事，很好的代表是 DreamCoder 这个工作，以及几篇在他基础上发展的论文。在那里你们是针对要构造的东西、比如对象，来建立文法的：你有一些完整对象的例子，它们是用非常底层的函数构造出来的；然后你在其中寻找反复出现的模式，找到能抽象成函数的模式，反复这样做。其实就是在压缩构造这些对象的程序。后来还有一些后续工作，把大语言模型、Python 代码和自然语言描述也结合了进来。这些论文里的一些思路，对用语言模型与世界交互的 agent 同样有用。

### 工作流：让语言模型从工具调用里归纳出来

接下来要看的这几篇论文，探讨的是从经验中学习技能、建立技能库这个领域的不同侧面，并追问技能归纳出来之后该怎么处理。

一般有一个学习步骤：任务不断进来，我们尝试从中提炼技能，再决定要不要把它存进逐渐积累的记忆里。然后是实际使用这份技能记忆的步骤，用它来提升我们正在执行的任务的表现。最后如果技能太多了，我们可能要简化它们：比如删掉那些用不上的；如果技能太具体，我们可能要让它更通用，或者合并整理多个技能。

我们会深入讲一篇论文，我觉得它很能代表技能归纳的这类方法。这项工作也是在 CMU 做的，由 Zora Wang 主导，他之后会来课程里做一次客座讲座，讲一些其他的主题。这篇论文叫 Agent Workflow Memory，它的做法是应用在网页任务上——这是我和 Graham 一起做的工作，我们把它应用在了网页任务上。

比如你有这样一个查询："告诉我，我们的商店到目前为止收到了多少条评论。"agent 执行这个任务时，会产生这些实际的工具调用，我们就有了一个工具调用序列，然后想识别其中哪些部分未来可能可以复用。

大家应该能猜到我们怎么做：让一个语言模型看这个工具调用序列，找出那些看起来对未来任务有用的部分。我们让模型输出所谓的"工作流"，它有点像技能的文本表示，包含文本和动作。一个工作流会包含对子任务的描述，比如搜索某个特定商品，然后还有你执行这个子任务所用的一系列动作。我们让模型把这个写得稍微更通用一些，这样它也能适用于搜索其他内容——所以我们让它创建一个模板，把初始动作序列中的一些部分抽象出来。

你可能在想，这看起来开始像代码了，对吧？确实如此。稍后我们会把代码和这个方法做个对比，展示它在某些方面怎么更好，但也会让事情变得更脆弱。

这个过程里很重要的一环是：我们会用一个评判模型来看这条轨迹，让它预测轨迹看起来是不是正确的，然后据此判断要不要把归纳出的工作流真正存进记忆。因为我们不想记住错误的东西，那可能会在将来把模型带偏。

那我们怎么让模型访问到这些工作流的集合呢？方法就是把它们直接放进模型的上下文窗口。这看起来很像是那个 Agent Skills 标准：你可以选择全部展示，也可以只展示文本描述，怎么选可能取决于你有多少技能，以及模型的上下文长度。

我们确实发现，拥有这种过往子任务的记忆能帮助 agent 在在线学习过程中提升表现。这张图里，X 轴是按固定顺序排列的不同任务，这个基准测试要求和地图工具交互。蓝线是没有记忆的 baseline agent，它在这些任务上的准确率收敛到 10% 左右；这条黑线加入了子任务记忆，提升相当明显。而且它还能完成越来越复杂的任务，比如找到这个位置附近的酒店、显示步行路线——这些 baseline agent 是做不到的。


### 代码技能：更快，也更死板

上面是用文本和示例动作的混合来表示技能，但我们也可以考虑用代码。这两个都是"搜索商品"函数的实现。

#### 文本与代码的取舍

如果只用这种文本和示例，它会被放进模型的上下文窗口，然后在新环境下，它还得重新生成这些工具调用才能完成同样的子任务。所以这种方式很灵活：模型可以选择插入不同的搜索词去搜别的商品；如果网站改版了、搜索框对应的那个元素没了，agent 就可以选择改用正确的那个元素。

但这也意味着，这些工具调用都得由 agent 自己生成。如果用代码，agent 其实可以直接把这个函数当成工具来调用，对吧？只要参数传对、函数本身没错，它就不用做任何事了：它不用自己生成那些底层动作，工具在环境里执行时会自动完成。

| 维度 | 文本 + 示例动作 | 代码函数 |
| --- | --- | --- |
| 动作从哪来 | 模型读了示例后，在新环境里重新生成工具调用 | 直接当工具调用，参数对就执行 |
| 灵活性 | 高：能换搜索词，改版后能换元素 | 低：只照着函数里的步骤走，没有偏离余地 |
| 可测性 | 只能对整条轨迹做评判 | 能单独给这个函数写测试用例、执行验证 |
| 结构 | 扁平的一段说明 | 可嵌套成函数，做成分层结构 |
| 后续维护 | 只能改文字 | 可以做重构这类操作 |

有人能想到用这样的函数来表示技能有哪些优缺点吗？它风险很大，对，它非常死板：模型调用这个工具就只会照着这三步执行，完全没有偏离的余地。对，这是一个主要缺点。

但用代码的好处也有很多，对吧？我们可以嵌套函数做成分层结构；还能单独给这个函数生成测试用例，不用管它所在的整条轨迹；还能做重构这类操作。

#### 归纳出函数，并用执行来检验它

Zora 有篇论文叫 Inducing Programmatic Skills，也就是 agent 技能归纳（IPS）做的就是这事。它和我们刚才用来归纳文本工作流的方法非常相似：你有这样一条带工具调用的轨迹，我们就利用语言模型也擅长写代码这一点去提示模型，让它生成一些函数，把这条轨迹里的很多行为抽象出来。

看一个真实例子：模型写出了 `search_reviews` 函数和文档字符串，底层工具调用另一个打开商品评论的工具；我们还会让它基于原始轨迹重写一版，把那些工具给用上。

> **结论**：代码有一个很好的地方，就是我们可以通过执行来测试它。这样就不用像之前那样，把评判模型用在原始轨迹上，而是执行这段生成的抽象代码，再把评判模型用在其最终结果上。如果结果看起来是对的，那就能更强地说明你归纳出的这些代码技能也是对的。

如果没问题，我们就把它们存入记忆，语言模型就能把它们当做工具来用了——这其实就是在构建一个工具库，模型可以在以后的例子中使用。我们也证明了它能提升性能。

代码技能的一个好处是，可以只对技能本身进行测试，SkillWeaver 就在做这件事。这就是我刚才展示的那个循环的伪代码：

```text
        │  归纳出代码技能
        ▼
┌────────────────────────────────────┐
│ 一个任务                           │
└────────────────────────────────────┘
        │  用这组技能执行
        ▼
┌────────────────────────────────────┐
│ 一组代码技能                       │
└────────────────────────────────────┘
        │  奖励模型评判
        ▼
┌────────────────────────────────────┐
│ 一个完整回合                       │
└────────────────────────────────────┘
┌────────────────────────────────────┐
│                分叉                │
├────────────────────────────────────┤
│ 成功 → 技能存进记忆                │
│ 失败 → 按 linter / 奖励反馈修改技能│
└────────────────────────────────────┘
```

先有一个任务，你为它提出一组代码技能，然后试着用这些技能去执行任务，你会得到一个回合，再对它应用一个奖励模型：如果成功了，就可以把归纳出的这些技能都存进记忆；如果不成功，可以对它做一些修改。

技能可能失败的情况有好几种，对吧？一个做法是对归纳出的技能运行一个 linter。这是论文里的一个真实例子：有个归纳出的技能叫 `identify_pill`，用于和药品网站交互，这个函数带了很多参数，比如药片的颜色；但在 AI 最初写出的这个技能版本里，它其实没用上所有参数，把这个颜色参数忽略了。你可以让 linter 给这个技能提供反馈，然后像 Reflexion 那样参考这个反馈，生成函数的更新版本存起来；或者先试着运行一遍再存下来。你在修订技能的时候，也可以利用这个奖励模型的反馈，以它为条件来做修改。

> **提示**：这些是代码的一些好处——就算代码函数本身会更死板一些，它们也能成为优势。

#### 效率账：与页面交互的次数

另一个好处是，这些归纳出来的函数现在就是工具调用，能大幅减少 agent 与环境交互的次数。看一个来自 IPS 的例子：这样一个任务，"更新页面上的两个地址"，换成基础 agent 就得执行所有底层操作，翻遍这些表单、输入地址里的各项信息。但如果模型已经归纳出这些代码技能——这是研究里的真实例子，我们归纳出了 `navigate_to_address_settings` 和 `update_address_details` 这两个函数——那我们三步就能完成这个任务，假设这两个技能很适合这个网站，直接调用这两个函数就能完成任务。

agent 也快了很多，因为它不用再重新观察网站、生成工具调用，然后再观察新页面、再生成新的工具调用。客座讲座里讲网页智能体的那一节课，你会看到这些模型的一大瓶颈其实就是与网站交互的次数：图像会占用大量 token，而且每个动作之前生成思维链也要占用大量 token，这些内容都得生成出来。所以效率在这里非常关键。

在这项工作中，我们对文本技能和代码技能做了对照比较。这组任务本身带有比较多的重复结构，我们对比后发现：和没有记忆相比，文本技能有帮助，代码技能在准确率上的提升更大，同时效率也有很大提升，agent 需要与页面交互的次数明显减少了。

#### 跨网站失效：下拉框变成单选按钮

就像之前讲过的，技能的一个大问题在于它可能不够通用。这里就有一个失败案例，而且是这些代码技能的失败案例：我们想看看技能能不能跨网站泛化，先在一个网站上归纳出这些代码技能，再试着用到像 Target 这样的真实购物网站上去。

在那边是有效的，但它假设你要交互的元素是这种下拉框，而在 Target 网站上是一组单选按钮，于是他在那里就失败了。这就需要模型能根据交互过程中环境的反馈，实际去编辑这个技能。

不过代码对此有解决方案，对吧？我们可以有抽象类，他们能以不同方式实例化。有一篇论文就是这么做的：他们用代码做表示，某种程度上是基于我们这篇 Agent Workflow Memory 工作的模型。第一次与新网站交互时，先写一个抽象类方法，不做实现，但可以有效地"搜索商品""加入购物车""结账"这样的操作；然后他还会写一个针对具体网站的实现，比如这个 Amazon 的版本。

之后当他和别的网站交互时，可以用一些元数据，或者干脆让语言模型来判断这个具体实现不再适用了，接着就写一个抽象类的不同实例化版本。他们证明了这确实有效。

这个方法还有个好处：可以拥有大量具体技能，但同一时刻只有真正相关的那部分处于激活状态。这说得通，对吧？其实就是把软件工程的最佳实践，也应用到 AI 上了。

好，这些内容我们其实都讲过了，大家对这几种表示方式各自的优缺点也都心里有数。不过要知道，技能标准是允许你把两者结合起来的；至于怎样组合这些表示方式最好——就像刚才说的——还有很多研究要做好。

### 从失败里学：文字反馈比负样本管用

接下来我们快速过几篇论文，看看技能生命周期各个环节的不同做法：怎样归纳和管理技能才是最好的方式。这是一个非常开放的研究课题，细节可以去看论文，感兴趣的话，在课程后期的项目里也可以继续探索这个方向。

到目前为止，我们讲的都是在从成功中学习，但从失败中学习也可能很有帮助。比如模型去执行一个任务，像搜索蓝牙耳机，但这个特定网站处理搜索词用的是"或"而不是"与"，于是你会拿到所有蓝牙耳机或索尼的东西。这个真实例子来自 Google 的 ReasoningBank 论文：结果有 5000 条，agent 直接崩了，它得把这 5000 条结果一页页翻过去，慢慢就忘了自己在做什么任务，最后失败了。

但如果我们像 Reflexion 那样观察这条失败的轨迹，就能写出一些文字，指导以后怎么避免：比如应该用更具体的搜索词，而不是这么宽泛的关键词；还要一次显示更多条目，这样模型一次就能在上下文窗口里拿到更多信息。这篇论文整体用的还是 Agent Workflow Memory 和 agent 技能归纳那套框架，但不是只对正确轨迹做抽象，而是生成这种文字反馈，而且也适用于失败的轨迹——这也正是你自己写技能时会写的那种内容。他们发现这很有效。

这是几种不同类型的记忆：

| 方法 | 存进记忆的是什么 | 加入负样本（把失败轨迹直接放进去） |
| --- | --- | --- |
| SNAP | 完整轨迹：所有动作、观察、工具调用和消息 | 不会提升性能 |
| Agent Workflow Memory | 较抽象的轨迹，也就是工作流 | 不会提升性能 |
| ReasoningBank | 对策略的文字描述 | 提升很明显 |

说到底也说得通：因为你还可以概括地描述怎么避免失败，而不是去记住失败，再以此为条件来行动。

另一个重要问题是。我们在决定是否把轨迹这些东西存进记忆，还是决定从例子中推断哪种策略时，都是看我们判断这个轨迹是否成功。具体来说，在大部分这类工作中，是用一个模型来当裁判：他看轨迹的最终状态、看你要解决的任务，然后判断结果是否正确。所以这里一个很好的问题是：裁判的质量在多大程度上影响算法的性能？因为我们知道裁判并不完美。

ReasoningBank 这篇论文做了控制：他们先用一个完美的裁判来运行方法，直接使用任务是否成功的真实信息，然后他们往其中加入一些噪声，这样才能控制判断轨迹的模拟准确率。性能确实会下降，但他们发现存在一个最佳区间：在这个区间里记忆能带来提升，而且在一段比较宽的准确率区间内，用裁判来归纳记忆都还是有帮助的。不过这块肯定还有后续研究的空间。


### 经验越多未必越好

#### 检索器与记忆规模

好，趁最后几分钟，我想回到之前的话题。之前有人问过，技能数量超过实际需要，会不会反而损害性能？也有人问，如果是从一个集合里检索技能，那个检索器重不重要，也就是说检索器的质量重要吗？

ReasoningBank 这篇论文里有一些很好的消融实验，控制了从记忆中检索的经验数量，结果显示可用的东西越多，性能确实会下降。

这可能有好几个原因。比如你的 agent 可能还没在那么多任务上跑过；也可能记忆里本来就没有相关内容，往里塞更多东西只会是不相关的——那更像是这种方法在那个场景下的根本局限，对吧？只有学习素材和应用对象之间有相似之处，你才学得起来。但也可能是模型本身的局限：上下文窗口里东西多了，模型可能就被带偏了。这个问题可以通过训练模型来解决，让它更不容易被无关上下文干扰，更善于推理什么才是真正相关的。

另外，显式地缩小记忆规模也可能有用，这样一来，语言模型从中做挑选的负担就更小。我们做过一些相关工作，用类似缓存的做法：看看记忆里的某条内容过去被用过多少次，如果某条记忆很少被用到，就把它删掉。这样做能明显提升方法的效率，因为放进上下文窗口的内容更少了；如果模型容易被无关内容干扰，这样还能提高成功率。

#### 直接用强化学习训练技能归纳

最后要讲的一点是，这一整套做法某种程度上都有点临时拼凑，对吧？我们只是让原模型去看过去的经验，然后生成一个技能，存进记忆里，以后再拿出来用。但说白了，我们只是在用 prompt 让语言模型去预测什么将来可能有用。那一个很自然的问题就是：能不能直接训练语言模型来做这件事？

可以，这是最近才开始被探索的方向，这些论文今年才刚刚在 ACL 上发表。但基本思路是：我们对依次出现的多个任务做强化学习——我们之前用来做评估的那个在线学习设定，现在也拿来做训练。我们会依次收到多个相似的任务，同时不断构建记忆，构建方式和之前讲的一样：从经验中归纳技能，再把记忆用在后续任务上。

这个过程非常复杂，对吧？比如我们用了好几个不同的模型，要往记忆里存东西、要检索、还要使用。但好消息是，强化学习不在乎这些：你可以把强化学习直接用在这样复杂、不可微的过程上，后面会有几节课讲怎么做。奖励信号可以来自第二个任务是不是成功了、他有没有用上过去归纳出的技能，所以我们直接拿这个奖励做强化学习就行。

> **结论**：目前有几篇论文探索了这个方向，都发现这样做是有帮助的。其中一篇有个有意思的结果：如果你在奖励里再加一项，鼓励模型复用已归纳的技能，成功率会进一步提升。你还可以想象引入其他类型的奖励项，比如控制技能库的规模，让整个方法保持正则化，避免过度拟合。这个方向还有很多有意思的工作可以做。

今天的时间差不多就到这里了。希望大家对技能的归纳方式有了一些了解，也了解了技能怎么写，可以在课程项目里用，也能在研究里探索。有问题可以问我。
