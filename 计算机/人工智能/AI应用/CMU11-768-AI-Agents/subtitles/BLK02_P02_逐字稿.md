今天我要讲的是语言模型、Agent 的工具使用。这是 Agent 最根本的能力，也是它们区别于语言模型的地方。

基本思路是：所谓工具，就是语言模型调用外部计算机程序的一个接口，而语言模型自己做不到这一点，因为它本质上就是一台预测 token 的机器。有了工具，你能做的事就多多了，可以搜索、调用计算器、调用浏览器、调用 Python、调用任意 API。大家会看到，工具调用的方法是标准化的，但调用之后下游怎么用，可以非常不同。

工具基本上有两大好处，这些内容来自我发布在网站上的阅读材料，想深入了解可以去读，那是一篇综述，是我和 Daniel 还有我们的学生 Zora Wang 一起写的。第一个好处是拓展语言模型的能力，就是让语言模型能做一些它本质上做不到的事，比如访问超出语言模型动作空间的信息或操作。第二个是辅助语言模型，意思是这件事语言模型本质上能做到，但如果不让模型亲自做会容易得多。

代码确实很特殊，它的特别之处在于它和其他工具不同，能让你以全新的方式调用工具。而且确实有研究工作证明了这种方式非常有效。现在我们基本把它当成理所当然，但三四年前我们调用工具还不是这样的，那是我们刚开始用 LLM 构建 Agent 的时候。当时的标准做法是拿到一个查询——抱歉，这字有点小，大致是说确定购买 Codec V 这款手机最划算的国家，要考虑的国家是美国、日本、德国和印度。基本上你就得调用查询汇率工具去查德国，再调用手机价格查询工具，然后调用文本转换工具，然后再查一次汇率，接着再查手机价格，你得这样一步步反复执行，才能最终得到结果。但如果写代码，你只用写一个程序就能完成了，这样调用工具的方式更丰富，也更高效。

这个方法叫 CodeAct，有一篇相关论文。论文的核心结果基本上是：成功率上升了，平均交互轮数也下降了。而且这甚至包括了那些传统上不需要代码的任务，这些任务原本被视为普通工具使用任务，但代码就是完成它们的好载体。

但我们假设语言模型输出的内容，你有办法把它解析成函数参数，然后在初始化时注册这个工具，还要有一个解析机制让你得到一个映射，从名字映射到你要执行的工具。大多数Agent框架都提供添加新工具的方式，每个工具有自己的名字，对应一个Python函数之类，Python、TypeScript都行。调用时就会带上相应参数分发到那个函数。

所以每次的流程是先解析，查找工具，根据参数校验这个操作，然后执行，最后返回结果。但在校验阶段就可能失败，比如模型给了你错误的工具调用。在执行阶段也可能失败，有些调用虽然形式上没问题，但实际上是无效的，也就是隐式无效。举个例子，如果你有个执行Python的工具，它可能接受任何字符串当做Python代码，但真正运行时可能失败，这就属于执行错误。之后无论它成功还是失败，你都会得到一个观察结果。

这是另一个细节，实现Agent时如果搞错了，它会很有帮助，但也会非常烦人。基本上每次工具调用都会被分配一个ID，当你运行它时，不管是由语言模型的推理代码还是Agent代码来跑，然后你会得到一个结果，而结果会带有匹配的调用ID。这在并行工具调用的场景下特别有用，这个我待会儿会讲。有了ID的对应关系，你就知道哪个工具调用对应哪个结果。

但问题在于，比如说Anthropic，如果某个工具调用没有匹配的工具结果，它会直接报错挂掉。它会告诉你这是无效的历史，我不会接受这种历史，也不会再为你生成任何输出。根据我的实际经验，有时候assistant刚发出一个工具调用，突然你的程序挂了，或者出了类似的状况，结果没写出来，恢复后却它，Anthropic会拒绝，记住这点。

好，接下来是一个在技术上、算法上都很难的问题，它可能让你很感兴趣，也可能完全不感兴趣。但如果不感兴趣，你就庆幸有人替你解决这个问题吧。

语言模型生成的工具调用绝对不保证格式正确。这就是一个例子，你能看到这一段JSON少了最后一个右括号。这是格式有问题的JSON，放进你的JSON解析程序，它会抛出异常，你也提取不出数据了。我见过无数人去检查是不是缺了括号，然后事后补上一个，但你真不该这么干，这么做一点也不好玩。

其实你可以给每个工具调用设定一系列约束条件。第一个是语法，也就是必须是合法的JSON，这算是最基本的要求了，对吧？首先得能解析。第二个是结构，也就是说如果有预期字段或必填字段，就必须把它们都填上。第三个是类型，比如城市这个字段，它必须是字符串，抱歉，对，就是城市必须是字符串；如果是数值，单位也得是正确的单位。这些都能用JSON Schema表达，或任何Schema库也行。比如说，这是一个城市字段，类型是字符串，单位可以是摄氏度或华氏度，而且城市是必填的。

这样做的好处是它有机器可读的验证规则，你可以据此检查一次调用是否符合Schema。而要表达一个Schema是有效还是无效，一种办法是在它之上定义一个文法。有多少人学过上下文无关文法或者类似的内容？比如正则文法这类的东西，有多少人懂正则表达式？

好，很多人。正则表达式就是一种正则文法。有人知道怎么去解析一个正则表达式吗？终于有人答了有限状态自动机，对，完全正确。

有限状态自动机可能有些同学不太熟悉，它大概是这样的一种东西，它看起来有点像这样：你有一个状态，每次输入一个token，你就转移到一个不同的状态。收到a就到这个状态，收到b或者c就到那个状态。

它处理的是一种叫正则文法的东西，像`.*`这类你用来搜索文本的正则表达式，都可以用正则文法来表达。而JSON Schema是无法用正则文法表达的，但可以用一种叫上下文无关文法的东西来表达。上下文无关文法基本能构建出一颗类似这样的树，所以每个JSON表达式两侧都可以有括号，成员之间可以有逗号，这里可以是一个字符串，这里可以是一个单位。

如果JSON Schema格式正确，你就能构建出一颗像这样的树；如果JSON Schema格式不对，你或许能构建出大部分树，但到了单位这一项，单位不能是k，基本上就构建失败了，尽管单位其实可以取k，但我们定义成不接受开尔文作为温度单位。

所以基本上只要你能用JSON Schema定义的上下文无关文法来解析工具调用，就能做到这一点。细节我就不展开了，有限状态自动机解析不了上下文无关文法，但有个叫下推自动机的东西可以做到。它是在正则文法的基础上加了一个栈，你把内容压入栈，再从栈里弹出，最终就能判断输出能不能被解析。你要做的是从这个下推自动机的起始状态出发，一步步往前走，在从左到右生成输出的过程中，同步验证它。

这里我用XGrammar来举例，XGrammar实际上被广泛用在各种LLM推理库里，它其实是这里机器学习系的人开发的。所以这意味着每一次语言模型的运作情况都是如此，要预测下一个token的logits时，你就查一下文法，如果文法说这是合法的下一个token，就记1分，如果是不合法的下一个token，就记0分。你把所有不合法token的输出logits设成负无穷，然后重新归一化，这样就又得到一个合法的分布，概率就只落在合法token上。这就能保证你生成合法的输出。

这是XGrammar论文里的另一张图，他们做了一些巧妙的处理，有些token永远有效或永远无效，这些可以预先算出来；还有些token只在某些上下文中才有效，只在特定的栈上下文里有效，这些就得实时计算。如果你喜欢算法，这非常非常有意思。就算不喜欢，也该庆幸机器学习系的人在替你做这件事。

正因如此，只要你启用了这个功能，并设置好相应的JSON Schema，几乎总能得到格式规范的工具调用。这很棒，但有一种情况是做不到的，就算有这些手段也拿不到规范的工具调用。

我来出个快速小测验，这题非常非常难，不知道有没有人能答出来。有人想得到什么情况下连这都不够用吗？可能得对大语言模型很熟悉才行。

我觉得这基本接近我想说的答案了。就是说当token用完的时候，模型只能生成固定数量的token，你可能还在自动机的合法路径上，但没走到最终状态，于是只生成了一部分JSON，输出。答得很好，我自己其实就遇到过这种情况，理论上有办法解决，就是数一数还剩多少可输出的token，然后提前截断。不过那是如果有人想在XGrammar里实现这个，可以当附加分作业，我很乐意看到。

好，接下来我们讲REST API调用。表达工具有几种不同的方式，我想大多数人应该都已熟悉REST API了，这是大家和网页服务交互的方式。

不过，抱歉，其实还有别的调用API的方式，一种是通过编程工具调用，基本上就是给模型一个Python程序，让它用这个程序里的东西来调用工具。这是你可能会写一个weather_lib.py，放着get_weather函数，带上city和units参数，说需要时就调用它，再给它执行Python的能力，就能调那个工具了。编程工具调用可行，但这样没法远程调用，而且也没法通过你平时使用的标准工具调用方式来调用，不用编程工具调用时那种标准方式。

有办法把它转成REST API。有人用过FastAPI吗？这是个很常用的库，很多人用过。基本上它能让你做到的是，它能让你极其简单地搭起一个网页后端，只要建一个FastAPI，提供一个API key让用户来验证，再写个Python装饰器，weather就变成了这样。这样做有几个好处：

第一个，如果你不想让别人查看天气，就可以阻止他们。但更重要的是，如果你不想让人拿到你的个人数据之类，就可以要求API key，这样就能挡住所有没有合适API key的人。

另一个好处是它能免费给你一个JSON Schema。我说免费这其实是FastAPI实现好的功能，但你的整个API都能表示成JSON Schema，原样提供给语言模型，模型就能用它来指定哪些调用是允许的，然后你可以处理这个Schema，每当Agent发起工具调用，就发给你的API服务器执行。

好，调用这些API的另一种方式就是直接用curl命令。curl命令基本上可以让你像这样直接调用这些API，所以如果coding agent能访问bash，就能像这样调用。

如果你熟悉REST之类的，这些可能还挺简单直接的。有什么问题或想法吗？

如果你还没玩过FastAPI，它挺好用的，上手很容易。我之所以先讲这个，是因为这算是Agent出现之前的传统编程方式。

有个东西叫MCP，就是Model Context Protocol，大概是两年前或者一年半前由Anthropic推出的，它的设计初衷是提供一种标准方式来给你的模型补充上下文。

我第一次看到它的时候，其实心想为什么我们需要这玩意儿？我搞不懂为什么要这样做，让我们的 Agent 直接调用 API 不就行了？不过确实有一两个重要的点，让 MCP 和直接调用普通 API 不一样。我在这里解释一下，但首先，我先解释为什么我当时没意识到，就是说我觉得它其实没必要存在。

原因基本上是这样的，每次你搭建一个 MCP，你要做的就是有一个 AI 应用，然后再配置几个、设置几个 MCP 客户端，比如这是你的天气客户端，这是你的天气 MCP，还有 GitHub MCP 之类的。这样就能查天气，还能推送到你的 GitHub 上。我当初觉得没必要，是因为调用 API 还需要跑个程序吗？调用 API 有很好的方式，直接发给 REST API 就行了。

好，这算是稍微岔开一点话题。稍后我会回到这个点。先插一句，有个很好用的库叫 FastMCP。FastMCP 基本上就是 MCP 版的 FastAPI。所以你想为任何东西创建 MCP 服务器，只要把 FastAPI 换成 FastMCP，就能非常轻松地搭出来。你还可以拿 REST API 生成的 spec，直接转成一个 MCP。

这就是你可能想用 MCP 的主要原因。相比普通 API，好处是它给你多加了一层安全保障。MCP 有自己的 MCP API 密钥，这个 MCP API 密钥你需要提供给运行 Agent 的那个进程。除此之外，还有上游 API 密钥，比如你让 Agent 连接你的 GitHub，上游 API 密钥即 GitHub token 给 MCP 服务器，不给 Agent。而你给 Agent 的则是 MCP API 密钥，用它来登录 MCP 服务器。

这么做重要的原因在于，如果你把 GitHub token 给了 Agent，而它突然觉得把这个 token 推到你的公开仓库是个好主意，那会怎么样？那可不好，对吧？你的账号会被入侵，所有仓库都可能被装上恶意软件。所以你要给 Agent 一个相对无害的东西，这样即使它因为某种原因泄露了，泄露本身也无伤大雅，真正的凭证依然安全。这基本上就是它背后的设计初衷。

简单总结一下，这些方式都能让你给 Agent 添加一组 API。你可以通过普通的 JSON Schema 来做，也可以通过 MCP。但很多其他方面是不一样的，比如工具发现可能得去获取一份 OpenAPI 文档，而 MCP 有专门的 API 可以列出所有工具。调用方面，这里调用的是一个 HTTP 接口，而 MCP 有自己的传输层，方式多种多样，你可以通过标准输入输出连接，也可以通过 socket 诸如此类。认证我已经讲过了。MCP 还有一些其他的便利功能，比如可以添加资源、prompt 和扩展。不过这里不展开细讲。

好，其实还有两件事我想提一下，我猜是忘了把它们加进幻灯片了。第一件事是 MCP Registry，就是官方的 MCP 注册中心。如果你想找到能实现这类功能的 MCP，可以去这个注册中心，找到数量非常多的 MCP。还有一大堆 MCP Server 网站可以访问，它们都是按排名排列的，受欢迎程度之类的内容。

另外，我一直在讲匹兹堡的天气。有意思的是，今天——这些幻灯片我当然是提前准备好的，但今天匹兹堡的天气真的同时又是雨天又是晴天。结果我把 API 搞挂了，它没法同时返回多个天气。不过这确实挺巧的，你能同时看到倾盆大雨和明媚的阳光。

好，回到正题。最近另一个重要进展就是并行工具调用。并行工具调用要解决的基本问题，和我讲 Codact 以及程序化工具调用时说的一样，那就是工具只能一个一个地调用。哪怕是很简单的操作也会变得很长，因为你可能先查个天气，再看一眼日历，然后查个航班。但如果这些工具调用互相独立，你就可以同时发起调用。做法很简单，你只需要添加多个工具调用就行了，快就行了。

这里有几个需要注意的细节：第一个，只有当工具调用之间没有依赖关系时，你才能并行执行。比如查匹兹堡的天气、读今天的日历、查航班状态，这几个并行就挺好。但如果要先找客户 ID，再查订单，然后退款，那显然不能并行。所以并行工具调用是有上限的。如果你的日历或航班依赖天气，那显然也会有问题。

之前有人问过你会并行执行这些工具调用吗？答案是通常会。你可以用常规的 Python 语法写一堆工具调用，然后执行它们，再用 `asyncio.gather` 这类方法，在它们同时运行时把结果返回回来。同时运行，这种做法很常见。

另外我想指出一点，这也是高效的语言模型和低效的语言模型之间的一个重大区别。现在 Agent 语言模型里有一个很奇怪的悖论：按任务逐个衡量的话，更贵的模型实际上可能更省钱。这有两个主要原因：第一个是更贵的模型可能更聪明，能更快选到合适的解决方案；但另一件事是更新的模型并行工具调用做得好得多，能同时发起一大堆调用。所以如果你在用编程 Agent 之类的工具，用一些更好的模型，你会发现它们同时查看一批图片，或者同时写一堆不同的文件，这就是因为它们并行工具调用做得好。

有人知道它们为什么在这方面进步这么大吗？虽然并行工具调用机制早就存在，但直到大约半年前这都不是个大事儿。是吗？强化学习逼着它们这么做的。对，没错，强化学习算是逼着它们这么做了。因为模型被强烈激励着要尽快完成任务，而并行工具调用正是好办法之一。所以如果你在强化学习时对任务执行时长施加重惩罚，就能得到多得多的并行工具调用。

好，今天这节课最后我想讲的是评估工具使用。我先不讲怎么评估端到端的 agentic 任务，而是先讲语言模型工具使用能力的评估。因为这是语言模型做好 agentic 任务的前提。

这方面有不少数据集，最著名的是 Berkeley Function Calling Leaderboard。它有四个版本，最初从第一版起步，第一版基本上就是单轮工具调用。经过四个版本的演进，现在它涵盖了多轮工具调用，它也有 agentic 工具调用，但这更多是工具调用型 Agent，而不是端到端的编码 Agent 那种。他们还测工具调用的鲁棒性，比如参数的幻觉。他们也测格式敏感性，就是刚才讲的那些不同格式，榜单里有相关指标。

那么，当你要去评估整个技术栈时，有几件事需要评估。第一是语言模型有没有为任务选对合适的工具，它可能选了个不合适的工具，根本没法完成这个任务。另一项是参数，就是看填的值对不对。如果是 agentic 工具调用，还可以看执行顺序对不对，并且能测端到端的任务准确率。这些都是这个榜单里的指标。

另外还有效率，比如你多快能完成任务，比如花了多少 token、成本多少，还有可靠性。你想，如果工具调用超时了，它会不会合理地重试？如果某个工具出故障了，它能换一个吗？还有安全性，也就是存在对抗性输出，让它以不当的方式使用工具时，它还能正确处理吗？这个基准经过四次迭代，覆盖了以上所有维度。对，这个我其实已经讲过了。

还有一个非常有趣的工具调用基准，是 OpenRouter 的工具调用错误率基准。在座有人用过 OpenRouter 或见过这个吗？可能没有。好，这是针对同一个模型的测试，所有这些都是我想这是 GLM 5.3，所以是同一个模型。同一个模型，测的是工具调用的错误率。

很简短，唯一改变的变量是由谁来给你提供这个模型。这一点显然很重要，因为你会想我要用这个模型，可能觉得不管谁提供效果都一样，但实际上差距从 15% 一直到 0.01%，最低到 0.005%。有人知道为什么会这样吗？

课上有提过一些线索，也有一些没提到。

对，说得很好，我再说一遍：第一，各家用的解码或推理算法可能不一样；一个很大的差别是他们用不用模型量化，或者用的量化精度是多少。我自己的经验是 FP8 模型——FP8 差不多是模型量化的默认精度——比 FP4 模型的工具调用错误少得多。因为 FP4 压缩得非常狠，是帮推理服务商省钱，但模型通常也更差，能保持同等性能的 FP4 量化方案并不多。

还有一个是投机解码。这门课应该不会花太多时间讲投机解码，也许讲到长上下文的时候会提。其实还有一些专门为 Agent 设计的算法，挺有意思，到时也许可以讲。简单说，投机解码就是用一个更便宜的小模型去预测大模型接下来要输出什么，用它来加速推理。无损的投机解码按理说不该造成差别，因为它的输出本来就是一样的，并不改变模型本来的输出结果，但如果用的是有损的投机解码，结果就可能不一样了。不过那样的话还把它叫同一个模型恐怕也不太合适。

还有另一个原因我之前提到过，有人猜到是什么吗？其实今天课上刚刚讲过。

怎样才能让工具调用更成功？对，约束解码。完全正确。所以这些不同的服务商用的约束解码算法可能各不相同。实际操作中，很多提供商都会自己实现自己的推理算法，也就是说从零开始完整写一套自己的推理算法。有些提供商会用 vLLM 或 SGLang 这类开源方案，vLLM 和 SGLang 支持不同的语法解码算法，所以有些提供商可能压根就没实现这个。这样一来，他们就完全靠语言模型自己把工具调用做好，否则就可能出错。

工具调用失败的最后一个比较无趣的原因是推理提供商可能不稳定，有时候会宕机，工具调用就失败了。

好，今天要讲的主要内容就是这些。工具使用基本上是一个分层系统。工具带来了各种能力，比如检索、执行、生成、应用，正是它们让 Agent 成为 Agent，但这并不是白来的。

你可以在 prompt 里加入 schema，模型发出调用，然后你验证、分发，再按 ID 匹配结果。我们还可以加约束，比如基于语法的解码，但并不保证语义正确。比如一个 Python 程序，就算你生成的字符串能被解析成 Python，程序本身仍可能是错的。对接的方式也有好几种，比如直接做 REST 调用，或者用 MCP。还有很多系统负责编排依赖关系和并发，让我们进行评估。
