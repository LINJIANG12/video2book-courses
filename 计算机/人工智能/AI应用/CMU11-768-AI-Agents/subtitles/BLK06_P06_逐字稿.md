第一件事是提高代码的曝光量。如果原本的数据集比较杂，就可以加大代码的占比。你还可以根据实验来选配比，既提升代码能力，又保住通用能力。比如 Code Llama，他们拿 Llama 2 又额外训练了 5000 亿个 token。

上下文拓展在这里也很重要。这是 Qwen2.5-Coder 的一个实验结果。他们说这是代码模型，我们要把代码能力做到很强，所以就只用 100% 的代码，后续也全用代码来训练。但问题是它在数学等其他重要任务上分数很差，比如数学或问答。但如果继续训练时不全用代码，而是混入文本和数学，代码性能只小幅下降，其他能力却能保住。这显然既可行又重要，因为现在没人只用模型来写代码。

另一件事是长上下文处理，这个我之前课上讲过不少了。这里再稍微展开一点细节。本质上你要构造出连贯的序列用来训练模型。构造数据有个很天真的做法，对代码模型来说，就是把整个仓库拿来，把所有文件直接拼在一起。但全部拼在一起，往往连最长上下文的模型都装不下，毕竟训练通常最多也就到 100 万 token。很多代码库，大多数正经的都超过 100 万 token。比如 Google 的 monorepo，据说有几十亿行代码，对吧？这根本不在同一个数量级上。

但你还是希望模型能连贯地理解文件，你可以把一个目录下的内容都拿来，也可以解析依赖图，顺着依赖关系把相互依赖的文件拼在一起，诸如此类。

接下来讲 infilling 中间填充。其实这该让 Daniel 来讲，他是专家，这主要是他的论文。不过还是讲讲，大家可以问他。他有一篇叫 InCoder 的论文，是最早一批用 infilling 中间填充目标训练强代码模型的论文，让模型不只做代码补全，还能预测代码中间部分。举个例子，比如有个函数叫 `is_positive`，我们想预测它的返回类型，这就是一个典型场景。

问题在于，普通自回归模型只看左边的函数体，你根本猜不出来，对吧？`is_positive` 本身没什么信息，也许能从名字猜出是布尔，但也可能是字符串、枚举什么的。但要是看到右边这部分，就能确定返回类型了。

那怎么做呢？答案出人意料的……这是在提问吗？不是。好，我觉得这个答案说出来会让人意外。简单得出奇，把 infilling 中间填充任务转化成自回归任务就行了。你有前缀，有后缀，然后填充中间这一段。这个 M0 就是你填充的第一段，而这个是接在 M0 后面的部分。推理时你在前缀和后缀之间放一个 M0，再放一个 M0，模型就会生成要填充的那段。

这也能推广到一个或多个空洞。如果多个空洞，就用 M0 和 M1，先生成 M0，再生成 M1。这是做任何 infilling 中间填充任务的通用方法。

从软件工程角度看，这能干很多有用的事。比如在大文件中间补全代码，或推断类型，就像刚才的返回类型、注释生成、变量重命名，都是 infilling 中间填充任务。这是论文里的一些实验结果。

他们在单行、多行等若干任务上做从左到右推理，成绩大概是 48 对 24 和 25。如果用从左到右生成 10 个候选，再用整个文件的上下文重排，效果会好一些，但仍然不够，远比不上专门训练模型做这件事的提升。而且这完全不需要重排，用的就是基于中间填充的推理。

而且可以证明，加入中间填充训练后，标准的代码补全能力仍然能保持。如果加上因果掩码，也就是把从左到右的部分遮住，性能依然能保持，所以这两者其实并不构成取舍。这里有问题或想补充的吗？

对，就是随机选取的问题。对，你是按一个长尾分布随机抽取若干个 span，大多数时候就只抽一个，不过我想最多可以抽到 100 个，其实概率非常小。对每个 span 采样对应内容，这些都是连续 token，然后把这些内容移到末尾，用 mask token 替换原来的部分，模型不在原位预测这些 mask token，而是在末尾预测它们。

BLEU 这个指标衡量的就是输出代码的 token 和 n-gram 重叠程度。谢谢。它能找出表面上相似的代码，但问题在于这样做有它的局限。比如大于等于号只差一个 token，但程序行为上差别非常大。反过来，有些写法不同的表达式，从 token 重叠看差别很大，但实际上是等价的。

针对这个问题，已经有几种解决思路。其中一种是一个叫 CodeBLEU 的指标。它的做法是不比较 token 层面的表面相似度，而是比较抽象语法树，也就是程序之间的语法树。程序有个特点，每个程序都能转成一棵树。这棵树规定了程序按编程语言的逻辑如何执行。他们基于语法树来比较，还比较了语法数据流匹配和语义数据流匹配，也就是看哪些变量来自哪些地方之类的。另一种比较代码相似度的方法是基于嵌入的方法。

这是我们在 2023 年做的一个东西，叫 CodeBERTScore。基本思路是你拿一段代码——这是代码的一个例子，这是另一个例子——你对代码里的每个 token 做嵌入，然后检查每个 token 在另一段代码里是否都有一个对应得上的 token。这样你就能看出这段代码是不是基本上都在另一个实现里有所体现。这些例子效果都不错。至于这个场景，抱歉，其实几页之后我会专门讲它们的取舍。

那我们换到另一种代码评估范式吧，这是如今更主流的做法。现在评估代码的典型方式就是真的把它跑起来。具体做法是你有一个候选输出，再准备一批测试用例，拿候选输出去跑这些测试用例，然后评估如果全部通过就得一分，如果没有全部通过就得零分。

这两种方法各有优劣。先看执行检查、基于执行的评估。它的好处是能接受不同的正确实现。缺点是要写出真正好的单元测试非常难。你能找到的每个知名基准都有一篇论文在抱怨单元测试有多差，说它们要么有假阳性，也就是测试不够严格，放过了错误的实现；要么有假阴性，也就是给 Agent 的输入信息不足以让它通过所有单元测试。举个例子，需求可能写着“我要在我界面右上角放一个好看的按钮，上面写着 Learn More”之类。

这听起来挺好，但测试可能还会检查按钮的背景颜色什么的，因为这个要求在测试一开始并不明显，是后来才显现出来的。这就是问题所在，也是现在训练 coding agent 最大的难题之一。因为任务越来越难了，要造出既低假阳性又低假阴性的测试非常困难。

那么，另一个好处是通过执行来发现语义错误效果很好，但这需要好的测试，还需要在隔离环境里装好依赖。比如你要跑测试，如果只用 Python 标准库那很简单，否则就得提前装好所有依赖。常见做法是用一个 Docker 容器把所有依赖都装进去。但你可能以为依赖都装好了，却没考虑到所用库的版本问题。版本一升级，测试...

测试就跟不上了，结果你只是因为测试过时了，就给新模型打了更低的分。这是我们得处理的另一个问题。

最后一点，你需要一个长期稳定的执行环境。对一个很大的代码库跑测试可能非常耗时，在我们接触的很多基准里，包括待会儿要讲的 SWE-bench，他们都想办法解决了这个问题，但这确实是个难点。

简单介绍几个单步代码生成里流行的基准。HumanEval 算是经典的标准基准，不过它已经过时了，因为每个语言模型都能拿高分。它是最简单的一类，给一个带 docstring 的 Python 函数，你要生成补全，背后有隐藏的单元测试。这个基准其实是 OpenAI 的人手工造出来的，他们设计了一批挺有技巧性的 Python 函数让人去实现，所以它不一定能反映真实世界的使用情况。稍难一点的一个叫 CodeContests，这有点像 Codeforces 的风格，更偏竞赛编程。还有很多其他的评测基准，难度从简单到复杂不等。

有意思的是，我觉得没多少人能第一次尝试就毫无差错、百分之百正确地解出一道 Codeforces 的题，但这正是我们要求单步语言模型做到的事。所以这其实是相当难的任务，需要大量的推理。

这里有一个例子，我给大家看看 2021 年提出 HumanEval 的那篇论文。各位如果知道现在的 Codex 是什么，听到这个也叫 Codex 可能会很困惑，但这篇是 2021 年为 GitHub 实现的最早的代码补全模型。这里他们做的事情就是评估模型能通过多少。可以看到模型越大，通过的就越多。这是 pass@1，pass@1 的意思是只生成一个输出，看它能不能通过；但也会报告 pass@k，也就是生成 5 个输出，其中有没有一个是正确的。这是个稍微宽容一点的指标，也可以用来评估。

对非 agent 任务来说，基本没有纳入训练。他们基本不考虑代码跑得快还是慢，主要只看代码对不对。不过也有几个例外，例外之一是这篇论文 NoFunEval。这里的意思是，你不仅要评估功能需求，也就是程序能不能正确完成它该做的事，还要评估运行时效率这类指标，比如延迟、资源占用，还有基于静态检查的可维护性和安全性。所以也有工作在评估这些方面。对 agent 任务来说，考虑效率更常见，我稍后会讲到。

我们继续。对单步代码生成模型来说，一种典型的训练方法是用测试结果做强化学习。从 RL 任务的角度看这很直接：采样一些回答，跑一遍测试，然后更新模型。这里没什么特别出人意料的地方。

但很重要的一点是，这让你能进行训练大型推理模型。就像我说的，一步到位解出 Codeforces 的题相当难，这要求模型对回答进行非常仔细的思考，而推理模型在这方面非常有帮助，所以这是可以做到的。关于效率的一个线索是，做 Codeforces 之类题时，很多竞赛编程任务会给你一个执行超时限制，一旦超过执行时限，这道题基本就拿不到分了。总之这就是这里可以用到的方法。

而且可以证明，在中期训练之后，做这种强化学习能进一步提升结果。这只是论文 DeepSeek-Coder 里的一个例子，你们可以查。他们先在 16K 上下文训练了一段时间，又在 32K 上下文训练了更久，最后报告的是 64K 上下文的结果。

这个问题很好，我复述一下问题：代码里包含的那些注释为什么会是这个样子？为什么明明解题用不着，代码里还是会有注释？

这里我只能给些猜测，因为我不完全确定我最常用的那些模型 GPT 和 Claude 到底在做什么，所以我想回头再多读一点相关资料。不过我的猜测是：第一，模型是在现有代码上训练的，代码里有注释，所以他们也会补注释。第二，他们被训练做推理，我觉得可能有个隐性激励：多写注释能多换一些 token，这样在生成代码的同时还能想想下一步做什么。所以模型爱写注释，背后可能就有这种隐性激励。

我可以肯定的是，现在（半年前可能还不是），他们已经引入了某种非功能分类器或代码质量模型，它会要求写注释，注释数量要合适，不能太多也不能太少。因为以前大家对编码模型的一大抱怨就是他们会生成海量没人看的注释，啰唆得要命。我记得最新版 Codex 发布的时候，他们强调的一点就是不会给你塞一堆注释垃圾，会写得简洁。

有没有专门针对代码质量的训练方法，让代码更易读？

我觉得最直接的做法就是搞一个评判代码质量的模型，在强化学习时加进奖励里。具体细节我不清楚，我想大家做后训练的时候往往会把可读性作为一项单独收集的指标，拿它当评判标准。给后排再重复一下，做后训练时通常有个类似 RLHF 的步骤，训练一个奖励模型来预测输出有多好，可读性就是可以从人类标注员那里收集的指标之一，然后它会通过奖励模型间接得到提升。

接下来我一定要讲讲 agentic coding。单步编码和 agentic coding 最大的区别在于我们现在和所有 agent 一样，要做迭代式的工具调用。

我们先讲最常见的场景：在 GitHub 仓库或代码仓库里修 bug 或者实现新功能。要做这类事情通常有三个步骤：第一步是定位，基本上我们之前有个例子是修一段代码让返回值变得正确，所以这里的定位本质上就是找到需要修改的地方。然后编辑就是改动那个需要修改的地方，比如说只在值为 None 的时候设置默认值。然后验证就是检查你是不是真的做好了。通常这一整套会放在一个循环里，如果发现验证没通过，你就回头迭代，直到全部通过为止。

这就是那个贯穿的例子。假如你的任务是找到那个地方，retries 在值为 0 时没有正确地设默认值，你会先定位到实现代码并复现这个行为。然后就是编辑，为了修补问题你会进去改代码，然后跑全部测试来验证。如果测试失败，就用失败信息来指导你下一步怎么做。

这就是 agentic coding，你基本上就是把它放进一个循环里，用我马上要讲的那些工具。

我想指出一点，还有一种替代方法，不用任何迭代式 agentic 流程也能做仓库级编码。有一篇论文叫 Agentless，作者是 Steven Xiao，我们这里新来的助理教授。他们做的事情基本上不是让 agent 自由调用工具来做定位，而是把定位拆成一个独立步骤：先做定位，先预测需要改哪些文件，再预测需要改哪些类和函数，然后具体挑出需要改的行，接着只用一个单步语言模型生成补丁。这是一种替代方案。

有一段时间它效果出奇的好，挺让人郁闷的，因为那时我正在做 coding agent。我们发现不少语言模型用这种流程跑得比 coding agent 还好。原因在于当时的语言模型被重度训练成擅长单步代码修复，却没有被重度训练成擅长 agentic 工具调用和验证循环。总之这是解决仓库级代码生成的另一种办法，但现在大家基本都用 agent 了。

怎么把 agent 用在这上面呢？一个答案是只给 agent 一个工具。你给 agent 的这一个工具就是运行 bash 命令的能力，这就呼应了前面说的会用 bash 命令非常重要。mini-SWE-agent 是 SWE-bench 的那批人做出来的，本质上就是一个只用 bash 命令来解决问题的 agent。这样就能定位问题了。具体做法是用 grep、ripgrep 这种表达力更强的 grep，还有 cat、find 这些工具。要编辑文件的话可以用 sed 或者跑个一次性的 Python 脚本，可以用 patch。要跑检查的话，用 pytest 或构建命令就行了。所以说，至少在理论上要实现一个 coding agent 需要的就这么多。

谁能说说这样作为什么可能不太理想？

答案是像 gdb 这样的工具就那么几个。另外还有些别的工具，比如 gdb 这类工具，其实你用 bash 命令就能直接跑，对吧？先说明一下，我不是说你只能给 agent 提供这些工具，我是说你只给 agent 一个工具，就是 bash。

这个观点很好。再强调一遍刚才的意思，大部分工具调用都会是这些，如果大部分工具调用都属于这类，把它们封装成一个更高效的工具，agent 就能干得不错。我举个例子：假如我想编辑文件，agent 每次都得琢磨用 sed、Python 还是 patch。但如果你专门做一个为 agent 打磨的标准文件编辑工具，让它用起来效果好，那 agent 基本就会依赖这个工具，改文件也就改得更准了。

举个例子，用 sed 跑起来就是这个样子，这样就能把相关的行都匹配上，诸如此类的。可要是你要替换的东西里有一堆反斜杠之类的呢，那你就得一直写反斜杠，数量还必须完全正确。所以有不少原因让 bash 未必是处理文件这类工作的最佳接口。

所以大多数甚至所有主流 coding agent 最大的改动就是至少再加一个文件编辑工具。你可以整个文件重写，也可以在文件内做查找替换。通常这些操作都通过一个工具完成，它用固定的格式来执行这些操作。

其中一种被研究过的方式是 Unified diff 统一差异格式。基本上它的样子是这样的：行号和需要做的修改。但问题是让 agent 去对行号，它经常搞错，补丁就打不上。所以更常见的做法是这样的：你给的东西看起来很像一个 diff，但它不是纯粹的 diff，也不指定行号。这大概是最常见的做法，很多 coding agent 都在用。

有人能想到用右边而不是左边的坏处吗？觉得它会在哪里出问题？对，没错。如果文件里有多处 `retries = 3`，就匹配不上，也没法确定该改哪一个。这时 coding agent 得多写几行，直到没歧义。

右边做法的好处远大于这个缺点，所以几乎所有 coding agent 都用它。diff 格式影响很大，文件编辑工具的格式同样影响很大。这是个叫 Aider 代码编辑基准的例子，它评估了当时的模型 GPT-4 Turbo，比较查找替换和 unified diff 统一差异格式两种方式。GPT-4 Turbo 更适合 unified diff，训练见得多。现在这个问题没那么突出了，但依然存在。就在最近之前，Gemini 在不少 harness 上表现很差，因为它训内用的是自己那套编辑格式，跟别人都不一样，所以效果不好。我想他们过去几个月修好了，但这可能是个非常非常大的瓶颈，处理不好，agent 就跑不好。好，这里有问题吗？

下一件事是找到相关代码，先从搜索你手头的信息开始。ripgrep 是最常用的工具，也可以用 grep 或专门的代码搜索工具。接着顺着引用追踪下去，agent 就去修复问题。关于代码定位，人们也研究过一些更复杂的方法。举个例子，有一篇论文叫 LocAgent，它给 agent 提供了一个特殊的工具，这个工具能让它沿着依赖路径追踪。比如你找到了 issue，找到了 config.py，然后就能接着往下追。找到 config.py 之后，你想的话就能用这个工具自动跳到其他相关文件。

这挺有意思。不过根据我的经验，这类方法很难做得比简单方法更好，后面我会举一些实际例子。

Coding agent 的评估和训练最流行的做法是这样的：评估 coding agent 的基准就是 SWE-bench。很多人应该听说过它，在座的多数人都听说过吧？好，不过我猜不是所有人都听说过这个基准的构建方式。大致是这样的：它从 GitHub issue 构建，取一个 issue，就是问题本身，再取 issue 被解决时的代码库状态，也就是 pull request 之前的状态。他们还会找出与这个 issue 相关的测试。这些测试因为它们是和这个 issue 一起引入的，所以它们测的应该就是 issue 里要修复的功能。在此基础上，让一个 agent 生成补丁，然后应用这个补丁，跑测试，得出结果。如果所有相关测试都通过，得分就是 1；只要没全通过，得分就是 0。

这里的 harness 和 agent harness 的含义其实不一样，它指的是测试 harness，就是单纯跑测试。但有一点要提一下：在这些 GitHub 仓库跑完整测试套件代价很高，比如有些是 Django、NumPy 这类项目，每评估一个样例，跑测试就要 5 到 10 分钟，甚至更久。所以他们挑出了一个更小的测试子集，只要这些通过就认为 issue 被解决了。这些测试分几类：第一类是 FAIL_TO_PASS，也就是 PR 之前失败、PR 之后通过的测试，它们测的正是 PR 里实现的功能；第二类是 PASS_TO_PASS，这些是相关测试，在提交 PR 之前就能通过，之后也必须通过，用来确保你没有破坏任何东西，没有引入回归。

要构建可运行的基准任务——这个在评估基准的作业里你们还会深入做。可运行的任务基本上需要一个起始状态，也就是那些文件，可能还需要依赖，以及测试命令、issue，就是要求实现的行为，而检查项就是那些测试。

现在做 agent 有个好消息，其实评估是改进行 agent 最大的难题之一。因为只要你能把它做好，生成大量评估，你就能在这些评估基准上做强化学习，把 agent 训练好。只要你能批量生成大量这样的输出，就真的可以训练出一个模型。具体做法就是让模型生成输出，然后根据它做得好不好来计算奖励。

我们最早做这件事的论文之一叫 SWE-gym。SWE-bench 的问题在于，它只是一个评估数据集，或者说他们只给评估数据集配好了环境。在 SWE-gym 里，我们额外搭建了训练环境并在上面训练模型。结果表明，一个原本很弱、准确率只有约 11% 的模型，哪怕只用 500 个样例，也能提升到相当不错的水平，好得多。这个我先不多讲，后面的课会专门讨论。我们还证明了，如果生成大量输出再重新排序，就能做推理时扩展，效果更好。

这方面最大的一个项目——我刚发现幻灯片里没放它，但值得了解——它叫 SWE-rebench。它在持续不断地创建更多 SWE-bench 环境。他们是用 PR 创建出来的，2024 年 12 月到 2026 年 6 月 30 日，我最近刚和作者聊过，他们大概 10 月会更新一次。它就是不断产出更多这样的环境，还分训练集和开发集。这大概是 SWE-bench 格式下大规模公开可用的 coding agent 数据里最好的例子。

不过创建这类数据还有一些更轻量的方法。这样作的一个问题是，你造的每个训练样本都需要对应一个单独的 pull request。这里有个来自 SWE-Smith 的例子，它不依赖 pull request，而是靠人为注入的 bug。做法是先准备一个能跑通的基线，然后改动代码，但保留测试。

那么，有多少人听说过变异测试？没几个人，好。这其实是软件工程实践里一个很有意思的想法。它是这样的：如果你不确定自己的测试好不好，比如你有单元测试，但不确定套件够不够全面，就可以对代码做些本意让它出错的小改动，再看测试过不过。如果测试还是通过，那这些测试就算不好，它们没覆盖到真正的破坏，所以你应该扩充测试套件。我觉得这项工作就是受这个想法启发的，但不完全一样。区别在于，他们是改动仓库里的代码，然后去找之后会失败的测试。这样做本质上能让你造出合成的带 bug 数据，只用现有的测试和代码库就能拿来训练模型。

来看个例子：假如你有一段代码，现有的四个测试全部通过，然后你进去把代码改一改，比如把：

```python
if value is None:
```

改成：

```python
return ... if not value
```

这时可能就有一个测试挂了。所以这是个好例子，你基本上能构造出这样的情形，一条“请修复这个问题”的任务。好，这里有什么问题吗？好处是这样做非常轻量，几乎能生成无限量的数据。坏处是这些不一定是你真正想处理的自然训练样本，真要上手做的话。

另外，用这个框架也能扩展到不同的编程语言。有个叫 Multi-SWE-bench 的，还有个叫 SWE-bench Multilingual，基本上都扩展到了多种编程语言。唯一的实际困难是各语言的约定不同，你需要处理它们。好消息是现在 coding agent 做这个很容易，改约定没那么难。

最后我想讲的是多 harness 训练。就像我之前提到的，如果语言模型预期的编辑格式和 harness 预期的差别很大，大多数语言模型在没训练过的 harness 上表现会更差。所以现在语言模型厂商普遍会在多个 harness 上训练，他们不只训一个 harness，而是在 OpenHands、OpenCode、Codex 等各种 harness 上都训。举个例子，你可以看看 NVIDIA Nemotron 的报告，他们刻意在好几个（我记得是五个以上）数据来源上做了训练，五个以上的 harness 上训练，让模型能适配很多不同的 harness。

好，我们剩下的时间不多了。我们快速过一下几个不同的例子、几个不同的任务，不只是直接的 issue 修复。这些在研究里没那么主流，但如果你想做一个能用的模型，它们非常重要。

前端开发就是其中之一。有个前端开发基准叫 SWE-bench Multimodal。这个基准只专注于修复前端的 bug，就是修前端任务里的 bug，所以它并不是专注于开发新前端，更多还是 issue 修复那一类。做多模态模型有两个不同之处：第一个是通常你会觉得要做这件事得用多模态模型接收并理解输入，也就是需要一个训练过能读图像的语言模型。另一件事是验证，在浏览器里验证有几种方法：一种是在浏览器里写能跑的测试；另一种是直接看输出。现在大家大概有两种做法：一种常见做法是把基于 GUI 的 agent 当作 coding agent 的一个组件，或者让一个 agent 同时能处理 GUI 任务和编码任务。下一节课会讲 GUI agent，所以怎么构建我就不展开了。另一种做法是写一个脚本来测试 GUI。比如 Playwright 就是一个常用的基于 GUI 的测试库，很多人用它来做这类事。基本上比如你有个问题：输入长度为 0 也能提交，那你可以用视觉方式验证这种情况确实发生了，或者你可以写一个 Playwright 脚本，确保输入 0 之后会出现要求填写非空名字的提示。SWE-bench Multimodal 就是评估这类能力的一种方式。几个月前有个很惊人的结果：有个流行的模型叫 GLM，GLM-4 是新发布的模型，它不是多模态，却在 frontend design arena 夺冠。这动摇了我对做好前端开发 coding agent 需要什么的假设。不过我还是觉得多模态能力可能挺重要的。

开发里有一个很有名的概念：内循环和外循环。我到目前为止讲的基本就是开发的内循环，它本质上就是修 bug、跑测试这类事情的迭代过程。外循环就是除此以外的一切。软件开发里还有很多不属于内循环的工作，比如代码审查是一个，部署和监控是另一个，还有维护，还有做规划、提需求也是例子。理想情况是 agent 能帮我们搞定所有这些事，但难点在于这些事更难定义，也更难找到训练数据。

这是微软 2019 年一份有意思的调查。现在情况可能不一样了，但 2019 年他们调查了自己的软件开发者，问你有多少时间花在写代码上，答案是 15%。这指的是也就是 issue 开发、新功能开发和 issue 修复。他们花 25% 的时间在开会和邮件上，14% 在调试，8% 在跑测试，等等等等。所以其实这也是软件开发工作里很大的一部分。

那我们能做的就是把这些任务做个对比。比如修复，也就是 issue 修复，这个我已经讲过了。但还有从零开始创建东西，还有为代码写好测试、修复失败的部署，以及在很长一段时间里持续开发应用。

第一个例子是你可以……

专门针对定位来训练，也就是让模型特别擅长判断一个编码任务该从哪里入手。我们有一个做这件事的 RL 方法，叫 CodeScout。如果你想给项目做个和 RL 相关的题目，这个可能挺有意思，因为它类似 coding agent，但更可控，用小模型也更容易做。如果你觉得有意思，可以看看我们的 CodeScout 论文。

第二个任务是从零开始创建应用。有个叫 VibeBench 的基准，专门评估 agent 做 vibe coding 的整体水平。这非常难做，因为你得能正确评估它们，所以需要设计出好的验证器。

另一件事是完整实现后端库的，这方面有几个基准，老的叫 Commit0，新近流行的叫 ProgramBench。ProgramBench 本质上是要你逆向工程一个二进制文件，再从零重新实现它。你可以运行这个二进制文件，根据输入输出去探测，然后写出新的实现。这很有意思，因为它的周期非常长，而短周期任务越来越容易，它现在是新的挑战之一。

对基准感兴趣的另一个例子 SWE-milestone，它的基本思路是你不是只实现一个 issue，而是在一个阶段里实现很多 issue，并且要确保你逐个实现 issue 时，不会把代码库搞得一团糟，变得难以维护，因为这是一些 coding agent 的大问题。这个基准就是用来评估这一点的。

如今另一个很大的问题，是生成能验证你有没有把 issue 修好的测试。因为我觉得现在有了 coding agent，如果你能写出真正好的测试来验证 issue 已解决，这等于成功了一半。你明确了任务，agent 就特别擅长反复迭代把它做好。SWT-bench 就是这样一个基准，它基于我之前提到的变异测试。

最后一类任务更偏运维一些，比如部署这类任务。不过我觉得还没有真正好的，目前还没有特别好的基准，而且它比较难做，因为需要真实的基础设施来运行。不过我有一个参考例子是 JetBrains 做的，感兴趣的话可以看看。
