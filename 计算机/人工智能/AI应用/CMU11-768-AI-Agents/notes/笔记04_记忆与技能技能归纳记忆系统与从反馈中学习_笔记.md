# 记忆与技能：技能归纳、记忆系统与从反馈中学习

## 技能归纳的问题起点

* **技能归纳（skill induction）**

    * > **定义**：让 agent 超越上下文窗口，把跨任务有用的信息存进外部存储，用它提升未来任务表现的机制。

    * 单纯在上下文窗口里保留内容属于任务内部存储；技能归纳把存储推到任务之间。

    * 两种互补视角并存：从自身经验中归纳潜在最佳实践；把人对"这个任务该怎么做"的理解直接编码进去。

    * 二者可以混合：人参与修订 AI 归纳出的技能，或 AI 依据经验去完善一条人写好的指令。

* **为什么需要跨任务记忆**

    * 购物网站上的 GUI agent 执行"把索尼耳机加到我的心愿单"时，高层动作串是：导航到商店网站 → 找到搜索框 → 在搜索框里输入文字 → 点击"搜索"。

    * 同一网站上的后续任务（如查无线键盘的价格区间）要复用其中的进站、找框、搜索这几步，只是后续处理不同。

    * 三个随之而来的问题：是否直接保留 agent 执行子任务时产生的原始操作，还是抽象成可当黑盒运行、可测试、可分层调用的代码函数；如何判断任务的哪些部分以后值得复用；如何管理记忆的生命周期。

* **记忆的生命周期问题**

    * 增长：这份记忆该怎么长，是一直往里加吗。

    * 冲突：遇到互相矛盾的信息怎么办。

    * 修改：找到更好的做法时想改掉原有内容。

    * 淘汰：某些内容不再适用时想删掉。

## 让 AI 更新自己的三种方式

* **上下文窗口里的历史**

    * 标准 ReAct 记录方式：过去观察和操作的历史、用户发来的消息、来自环境的反馈。

    * 保留哪些内容要同时考虑上下文窗口的限制，以及模型利用这些信息的能力。

    * 即使窗口已经到一百万个 token，agent 连做多个任务时仍会超出。

* **窗口之外的外部存储**

    * 形态上像一个需要某种方式管理的数据库，或者一个 agent 可以访问的文件系统。

    * 存的是记忆、事实和技能。

    * 核心课题是如何把信息放进这些存储，以及怎么使用和更新它们。

* **直接更新模型权重**

    * 相当于标准的监督微调或强化学习，作用在模型行为本身。

* **外部产物的优势**

    * 可跨模型移植：一份"网站怎么搜索"的方法描述，框架里很多不同模型都能用；更新权重则只针对那个特定模型，无法迁移。

    * 更容易被人检查：写下最佳实践 agent 就能用上，agent 也能提出类似的文本建议，人查看之后再做修改。

    * 只要记忆和更新方式可解释，人和系统之间就更容易建立交互界面。

| 方式 | 存的是什么 | 好处 | 代价 |
| :--- | :--- | :--- | :--- |
| 上下文窗口 | 历史观测、动作、消息，按 ReAct 格式排 | 模型直接就能用 | 窗口有限；跨任务用不上；压缩会丢信息 |
| 窗口之外的外部存储 | 记忆、事实、技能 | 可跨模型移植、可被人检查、可跨任务复用 | 得自己设计一套管理和检索的机制 |
| 更新模型权重 | 监督微调、强化学习的结果 | 直接改变模型行为本身 | 绑死在特定模型上，不好检查，也难"忘掉"旧知识 |

## 值得保留下来的经验类型

### 经历（episode）

* > **定义**：从环境、用户和执行者那里得到的一系列观察，原样全部保留下来。

* 保真度最高，环境的各种细节和用户给的具体指令都在。

* 成本也最高：表示它需要最多的 token，而且多半不需要全部这些内容。

* 类比：像做监督学习时不会保留每个细节，要抽象出关键的东西才能在未来泛化。

### 事实（fact）

* > **定义**：关于环境或用户的知识。

* 早期记忆系统研究大多聚焦在事实上，例如用户交互时给出年龄、住址，系统存进记忆，之后用这些事实改进未来交互。

* Anthropic、ChatGPT 的记忆系统基本就是这个做法：设置里有一段文本是模型从过往交互中提取出来的关于你的事实。

* 实现上接近压缩：由 LLM 生成一段总结性的东西，存到外部存储里。

### 技能（skill）

* > **定义**：完成子任务时把任务的具体细节抽象掉的知识，描述"怎么在环境中行动"。

* 例子：在某个网站上搜索商品，而不用记住搜索某个具体商品的那些细节。

* 只有在需要重复执行同一个子任务时才会派上用场。

### 记忆与技能的关系

* 记忆是从 agent 自身交互中保存下来的东西，比如你之前在某个网站买过什么产品。

* 技能是关于如何在环境中行动的可复用知识。

* 两者可结合：从 agent 过往经验中归纳技能并存下来，希望之后做得更好——如果 AI 过去成功搜索过某个商品，并认为那次是成功的，就可以从中提炼出技能来指导之后的行动。

* 表现形式之一是清单：发布应用、推上生产环境时，写明上线之前要逐项检查的内容。

* 表现形式之二是指令：人写的偏好，或"我们公司就是这么写和测代码"这类组织规范。

* 人工编写的技能来源已知、质量更易把控，但编写和维护都很花时间。

* 让 AI 自己学习并生成技能，好处是可做自动化循环：归纳出技能、用它重做同样的任务、看某指标上效果是否变好。

* > **易错点**：AI 生成的技能可能带噪声，尤其是把这些技能交给其他 agent 用时，可能带来意想不到的后果。

## Agent Skills 技能标准

### 技能的文件形态

* > **定义**：Agent Skills 标准下，一个技能的实现方式就是一组 agent 可以读取的文件，按目录形式安装。

* 动机：总是给 coding agent 下同类指令（用几种不同 linter 检查代码、加类型注解、固定格式、写 docstring、所有函数跑 pytest），存成一个文本文件让 agent 当指令用，比每次手动输入更自然也更快。

* 结论：当想按照固定规范反复做某件事时，就应该用技能；AI 会根据上下文自行决定怎么解释这个规范，但总体指令是一样的。

* 目录结构如下，其中只有 SKILL.md 是必须项：

    ```text
    python-code-review/
    ├── SKILL.md              # 必须有：YAML 元数据 + 详细做法
    ├── scripts/              # 可选：可执行代码，如跑 linter 的 Python 脚本
    │   └── run_lint.py
    ├── references/           # 可选：补充文档，不是每次都要用
    │   └── style_guide.md
    └── assets/               # 可选：模板和静态资源，按条件加载
        └── review_template.md
    ```

* SKILL.md 是 Markdown 文件，开头是一段 YAML 元数据：给技能起名字，再写一段简短描述；这段描述告诉语言模型这个技能应该在什么时候使用。

* SKILL.md 头部之后是对技能如何应用的更详细说明，比如列出所有应该用的 linter、测试该怎么做。

* `scripts` 放可执行代码，像跑 linter 的 Python 脚本就放进去，然后在 SKILL.md 里描述它。

* `references` 放补充文档，不一定每次都用，可以在技能文件里放一个指向它的引用，agent 按需加载。

* `assets` 主要放模板和资源，在相关任务里由 agent 按条件加载。

### 渐进式披露

* > **定义**：只在需要时向 agent 展示技能相关部分的机制，避免把模型可能用到的所有技能都塞进上下文窗口。

* 第 1 层是 SKILL.md 里的元数据（名称和描述）。只要技能被加载、也就是模型可以使用它，这些信息就始终显示在系统 prompt 里。

* 第 1 层的描述要写得简洁，这样即使技能很多，也不会把空间占得太满。

* 第 2 层是 SKILL.md 里的其余文本，模型判断这个技能相关并通过工具调用来读取文件其余部分时，这层被按条件加载。

* 第 3 层是那些可选目录里的所有资源，同样通过工具调用来加载。

* 因此 SKILL.md 里得写清楚足够的信息，让模型知道执行技能时应该去那些额外文件夹里找更多资源。

### 一次运行的完整流程

* 系统 prompt 里要描述什么是技能、告知存在这样一个"查看技能"的工具（模型可以用它读 Markdown），其余部分再列出所有技能。

* Hermes agent 是标准的开源 agent，能够使用和归纳技能；它的一个例子里只有代码质量技能和工作流技能两个，系统提示里放的就是这两个技能文件的 YAML 元数据。

* 用户说"帮我审查这段 Python 代码"时，模型发起工具调用打开 Python 审查技能，拿到那个 Markdown 文件后作为一条消息（也就是观察结果）插进上下文。

* 系统也能选择运行 scripts 目录里的某个东西，把脚本的运行结果作为观察放进上下文窗口。

* 还可能选择查看技能包里的其他文件（`references/`、`assets/`）。

## 技能规模、格式与平台

### 技能多会不会拖后腿

* 元数据始终加载在系统 prompt 里，技能一多一定影响性能，即使每个技能的元数据都很短。

* 参考规模：Hermes agent 的系统提示里技能描述加起来大约 3000 个 token。

* 控制手段：把技能数量控制在一定范围内，最好按需加载；也可以按手头软件任务的需要来加载。

* 多篇论文表明技能太多反而会让性能变差，加入无关的技能会拉低性能，因为上下文变长、模型被那些实际无关的内容分散注意力。

* 拥有 1 万个或 1000 个技能其实很少见，通常规模小得多。

### 触发灵敏度

* 触发机制就是模型生成的 tool call，要不要调用完全取决于模型。

* 既取决于模型根据过往上下文和对该技能的了解，能不能预判出它应该被触发，也取决于你写的描述。

* 所以需要做评测。

### 为什么用 Markdown

* 理由是在机器可读性和人类可读性之间找平衡。

* Markdown 很线性：可以加超链接，也能嵌入图片。

* 要表示动态的东西就比较难，例如演示数据可视化的各种不同方式，也许用交互式的 JavaScript 应用更好。

* 变通做法是把这部分做成一个会执行的代码文件，然后在 Markdown 里引用它。

* 文献里基本就是两种方式：文本的写在 Markdown 里，程序化的写在脚本里，把两类都算上覆盖面就很广。

### 跨平台与标准

* SKILL.md 是标准化的文件名，这个标准叫 Agent Skills，模型和 agent 框架都训练过怎么使用它、怎么加载它。

* 想让代码在多个平台上用，就先尽量往这个标准靠；特殊需求也可变通，比如把 references 里的特别内容直接写进 SKILL.md。

* 这些本质上都是给语言模型的指令，只要描述清楚，模型对其他配置也能应付。

### 技能检索

* 需求场景：在某家大银行做修改云基础设施的 agent，AWS 里东西太多，不可能为每个小组件都准备一个工具，用检索看起来更好。

* 某些研究论文确实从大规模技能集合里做检索。

* 两种做法：基于文本的 embedding 检索；更偏按领域条件筛选，比如技能适用于某个网站，交互时就加载这些技能。

* 生产系统是否也这么做，长文未说明。

## 技能的来源与检验

### 三种来源

* 技能可能随运行框架捆绑提供。

* 技能可以由人编写，按所用框架规定的格式安装进去。

* 技能也可以由 agent 自己创建：Hermes 有一个技能管理工具，OpenHands 有一个创建技能的命令，引导你走完整个创建流程。

### 凭空写出来的技能效果很差

* SkillsBench 论文的结果表明：当只凭任务描述让模型自己写技能时，效果很差，反而会让性能下降。

* 人来写通常更好，因为人知道自己想要怎么做。

* 最好的做法还是基于你做过的事儿，因为做任务的过程会揭示一些你事先可能想不到的偏好。

### AI 写技能的实际表现

* 典型失败模式：模型有时会在技能里写太多内容，有点过度推断该做什么；交给另一个模型时，它会严格照办，做的比你实际想要的还多。

* 成功案例：排查生产问题时给 agent 三四张支持工单，让它"看看大家以前是怎么调试这个问题的，给自己创建一个技能，让以后遇到的也能用同样的方式来排查"，效果非常好。

* 也就是说，让它替另一个 agent 写操作指引，它还挺擅长模拟 agent 会怎么做的。

* 但模型不太擅长模拟别人、或另一个 agent 看到指令时的想法，只要显式提示它这么做，效果就会好很多。

### 用人的采纳率检验审查类技能

* 以审查 pull request 为例：agent 产出审查后，由人逐条查看这些审查评论、决定是否采纳。

* 之后再用模型裁判统计有多少条被人实际采纳，这就能反映审查质量的高低。

* 可以在大量 pull request 上重复这个过程，都由 agent 用这个技能来审查；在几百上千个例子上做，就能收集到大量证据，知道哪些有效、哪些没用。

* 然后用推理模型总结这些发现，比如得出"生成忽视仓库规范的代码"没有帮助、但确实采纳了不少修改建议。

* 接着可以让模型给技能文件提一些更新，让系统产出的评审意见更容易被人采纳。

## 窗口外的记忆系统

### MemGPT

* > **定义**：2023 年的论文，最早的一批论文之一，也是最早提出在语言模型上下文窗口之外管理记忆的方法之一，很有系统设计色彩。

* 记忆层级：访问起来快的部分就是上下文窗口；还有一个更大但更慢的部分，在这个场景下就是外部存储。

* 系统指令不更新；工作上下文可更新，它从外部记忆里取内容，同时也往外部记忆里存内容，读写都由模型发出的工具调用控制。

* 另有一个单独的消息存储，保存系统实际收到的消息，管理方式跟事实记忆差不多。

* 例子：用户提到六旗乐园，就发起一个工具调用，在存储里搜索过去交互中提到六旗乐园的记录；系统取回这些记录放进工作上下文，而工作上下文存在语言模型的上下文窗口里，模型输出回复时就能用上。

* 成文时上下文窗口更短、大概只有 8000 个 token，所以当时非常有说服力；如今窗口更大，但要存进去的内容也多得多。

### 记忆也要能改能删（Mem0）

* > **定义**：Mem0 提出的记忆更新方法，每收到一条消息就用一个语言模型从中提取潜在事实，再与外部数据库比对。

* 用 embedding 检索模型检索 top-k，找出相似的事实，比如"六旗乐园"或"我在 X 公司上班"。

* 再用一个语言模型检查这些从最新消息里提取的记忆，在检索到的相似记忆里属于哪种情况。

* 没出现过：那可能就应该把它加进去。

* 是对已有内容的更新：用新信息替换掉原来存的那条。

* 否定已有内容（先说"我任职于 X 公司"，后来又说被裁了）：最好直接删掉这条事实，而不是更新。

* 完全不相关：直接忽略。

* 这类思路的价值在于出现冲突时系统能更新已有知识。

* 上下文管理中有目标类似的工作：线性注意力只能往记忆里追加值，而 DeltaNet 会真正检索出某个查询对应的存储内容并修改那些存下来的向量，确实提升了性能。

* 直接更新模型权重这条路上，能遗忘同样有帮助，尤其存在相互冲突的知识时；机器遗忘（machine unlearning）就是一种做法。

## 从反馈与轨迹中学习

### Reflexion 的自然语言反馈

* > **定义**：给定某个任务的多次尝试，把针对尝试结果的自然语言反馈作为条件参考，提升 agent 下一次尝试的表现。

* 方法非常简单但有效；如果项目希望 agent 能从过往经验中受益，它是个很值得实现的东西。

* 反馈可以来自人工检查，也可以来自用模型当裁判。

* 例子：模型要回答某个系列战役的问题，可能只提到了一场战役，语言模型知道这个答案不对；再看问题和答案，反馈可能是"你只给了一场战役，而不是一个系列"，模型再次尝试时就能答对。

* 论文表明，以自然语言描述哪里出了错作为条件参考，效果确实很好。

* 可以推广到不同任务：只要反馈足够通用，它也能帮助提升类似任务的表现。

### 轨迹记忆与检索

* > **定义**：把 agent 过去完成的整条轨迹、整个回合存起来，用它影响未来任务中的做法。

* 轨迹来源可以是一组示范，也可以是 agent 逐个执行任务时自己产生的；把它们汇总起来，还可能额外生成一些描述反馈的文本。

* 轨迹指 agent 从环境或用户那里收到的消息序列（观测）、执行的动作（工具调用），以及可能包括的思维链——基本就是模型上下文窗口里那整串消息。

* 检索做法：给一个新任务的文本描述做嵌入，用嵌入模型嵌入，再基于其他任务的描述检索，这些任务各自关联一条轨迹。

* 还可以加限定，比如只检索当前所在领域的任务。

* 效果有点像给 agent 用的 RAG，而且相当不错；把过去成功的轨迹当示例展示给 agent，它往往能表现得更好。

## 技能归纳的建模与早期工作

### 技能是任务里可复用的那一段

* 搜索商品的例子里，AI 可能产出一条思维链，接着执行真正与网页交互的动作：点击由这个 ID 标识的元素（搜索框）、输入查询词、再点击另一个元素（真正执行搜索的按钮）。

* 任务的这一块内容在未来任务中可能被复用，比如问"这个商品的价格区间是多少"时，可能需要原样重复这些步骤之后，再做额外操作。

* 技能可以看作对任务中这部分可复用内容的一种规格描述。

* 另一条路线是把同一段表示成代码函数：可以当黑盒运行、可以测试，甚至能分层调用其他函数。

* > **易错点**：以元素 ID 为锚的表示一旦页面元素 ID 变了就会失效。同一页面只是元素编号方式不同，可以调整动作空间解决；换到搜索界面不同的网站则彻底失效。

* 一般学习步骤：任务不断进来 → 尝试从中提炼技能 → 决定要不要存进逐渐积累的记忆 → 用这份技能记忆提升正在执行的任务 → 技能太多时简化，删掉用不上的，或让太具体的技能更通用、合并整理。

### 在线学习设定

* > **定义**：与 agent 交互时让它连续执行一堆彼此相似的任务，系统从这些交互中学到东西并在以后做得更好。

* 典型流程：任务"把索尼蓝牙耳机加到我的心愿单"到达 → 解决任务的同时逐步积累技能和记忆 → 中间有归纳步骤，产出"搜索商品""把商品加入心愿单"这样的技能 → 下一个任务也需搜索商品时套用这些技能 → 以此类推。

* 关注指标是：如果能衡量每个任务的成功与否，任务成功率是不是在越来越好，能不能边积累简单任务的做法边解决越来越复杂的任务。

* 在这种设定下评估技能归纳与使用系统。

### 程序归纳的早期工作

* Voyager 控制 Minecraft 里的一个 agent，用代码实现各种具体任务，比如合成某个物品或跟僵尸战斗，把子任务表示成函数，函数之间可互相调用，从而组合出越来越复杂的任务。

* DreamCoder 是程序归纳领域的代表：针对要构造的对象建立文法，手里有一些用非常底层函数构造出来的完整对象例子，在其中寻找反复出现的模式，抽象成函数，反复这样做。

* 这实质上是在压缩构造这些对象的程序；后续工作把大语言模型、Python 代码和自然语言描述也结合了进来。

## 工作流与工作流记忆

### 工作流（workflow）

* > **定义**：技能的一种文本表示，包含文本和动作，由对子任务的描述加上执行该子任务的一系列动作构成。

* 出处：CMU 的工作，由 Zora Wang 主导，作者把它应用在网页任务上。

* 例子：任务"告诉我，我们的商店到目前为止收到了多少条评论"产生一串工具调用，让一个语言模型看这串调用、找出看起来对未来任务有用的部分。

* 让模型把工作流写得稍微更通用一些，这样也能适用于搜索其他内容——具体做法是让它创建一个模板，把初始动作序列中的一些部分抽象出来。

* 这看起来开始像代码，因此后面要把代码方案拿来做对比：它在某些方面更好，但会让事情变得更脆弱。

* 关键一环是用评判模型看这条轨迹、预测轨迹看起来是不是正确，据此决定要不要把归纳出的工作流真正存进记忆，因为不想记住错误的东西，那可能会在将来把模型带偏。

* 使用方式是把工作流直接放进模型的上下文窗口；可以全部展示，也可以只展示文本描述，取决于你有多少技能以及模型的上下文长度。

* 这与 Agent Skills 标准很像，技能标准也允许把文本表示和代码表示结合起来。

### 子任务记忆的实验结果

* 基准测试按固定顺序排列不同任务，要求与地图工具交互。

* 没有记忆的 baseline agent 准确率收敛到 10% 左右。

* 加入子任务记忆后提升相当明显，而且能完成越来越复杂的任务，比如找到某个位置附近的酒店、显示步行路线，这些 baseline agent 做不到。

## 代码技能

### 文本与代码的取舍

* 文本 + 示例动作：被放进模型的上下文窗口，在新环境里还得重新生成这些工具调用才能完成同样的子任务。

* 代码函数：agent 可以直接把它当成工具来调用，只要参数传对、函数本身没错，就不用自己生成任何底层动作，工具在环境里执行时会自动完成。

| 维度 | 文本 + 示例动作 | 代码函数 |
| :--- | :--- | :--- |
| 动作从哪来 | 模型读了示例后，在新环境里重新生成工具调用 | 直接当工具调用，参数对就执行 |
| 灵活性 | 高：能换搜索词，改版后能换元素 | 低：只照着函数里的步骤走，没有偏离余地 |
| 可测性 | 只能对整条轨迹做评判 | 能单独给这个函数写测试用例、执行验证 |
| 结构 | 扁平的一段说明 | 可嵌套成函数，做成分层结构 |
| 后续维护 | 只能改文字 | 可以做重构这类操作 |

* > **易错点**：代码函数的风险很大、非常死板——模型调用这个工具就只会照着函数里那几步执行，完全没有偏离的余地，这是它的主要缺点。

### Inducing Programmatic Skills

* > **定义**：IPS（agent 技能归纳）用提示让语言模型把一条带工具调用的轨迹抽象成函数，归纳出程序化技能。

* 与归纳文本工作流的方法非常相似，同样利用语言模型擅长写代码这一点，让它生成函数把轨迹里的很多行为抽象出来。

* 真实例子：模型写出 `search_reviews` 函数和文档字符串，底层工具调用另一个打开商品评论的工具；还会让它基于原始轨迹重写一版，把那些工具给用上。

* 检验方式的关键优势是通过执行来测试：不再把评判模型用在原始轨迹上，而是执行这段生成的抽象代码，再把评判模型用在其最终结果上；结果看起来是对的，就能更强地说明归纳出的代码技能也是对的。

* 没问题就把它们存入记忆，语言模型把它们当工具使用，这其实就是在构建一个工具库；论文证明它能提升性能。

* SkillWeaver 做的事就是只对技能本身进行测试，而不必管它所在的整条轨迹。

* 循环的伪代码如下：

    ```text
            │  归纳出代码技能
            ▼
    ┌────────────────────────────────────┐
    │ 一个任务                           │
    └────────────────────────────────────┘
            │  用这组技能执行
            ▼
    ┌────────────────────────────────────┐
    │ 一组代码技能                       │
    └────────────────────────────────────┘
            │  奖励模型评判
            ▼
    ┌────────────────────────────────────┐
    │ 一个完整回合                       │
    └────────────────────────────────────┘
    ┌────────────────────────────────────┐
    │                分叉                │
    ├────────────────────────────────────┤
    │ 成功 → 技能存进记忆                │
    │ 失败 → 按 linter / 奖励反馈修改技能│
    └────────────────────────────────────┘
    ```

* 失败时的修正手段之一是对归纳出的技能运行一个 linter。

* 论文里的真实例子：有个归纳出的技能叫 `identify_pill`，用于和药品网站交互，函数带了很多参数（比如药片的颜色），但 AI 最初写出的版本没用上所有参数，把颜色参数忽略了。

* 拿到 linter 反馈后，可以像 Reflexion 那样参考它生成函数的新版本存起来；也可以先试着运行一遍再存下来，或者以奖励模型的反馈为条件做修改。

* 即使代码函数本身更死板一些，这些代码属性也会成为优势。

### 效率账

* 任务"更新页面上的两个地址"，基础 agent 得执行所有底层操作，翻遍这些表单、逐项输入地址里的信息。

* 研究中真实归纳出的函数是 `navigate_to_address_settings` 和 `update_address_details` 两个，调用它们三步就能完成任务，假设这两个技能很适合这个网站。

* 快的原因是不用再重新观察网站、生成工具调用、再观察新页面、再生成新的工具调用。

* 网页智能体的一大瓶颈就是与网站交互的次数：图像占用大量 token，每个动作之前生成思维链也要占用大量 token。

* 文本技能与代码技能的对照实验选了本身带较多重复结构的任务：与没有记忆相比，文本技能有帮助；代码技能在准确率上的提升更大，效率也有很大提升，与页面交互的次数明显减少。

### 跨网站失效与抽象类方案

* 失败案例：先在一个网站上归纳出代码技能，再试着用到 Target 这样的真实购物网站上。

* 在那边有效的前提是假设要交互的元素是下拉框，而 Target 网站上是一组单选按钮，于是就失败了。

* 这就需要模型能根据交互过程中环境的反馈，实际去编辑这个技能。

* 代码层面的解决方案是抽象类：一篇论文用代码做表示，某种程度上基于 Agent Workflow Memory 的工作。

* 第一次与新网站交互时先写一个抽象类方法、不做实现，但可以有效地执行"搜索商品""加入购物车""结账"这样的操作。

* 随后再写一个针对具体网站的实现，比如这个 Amazon 的版本。

* 之后与别的网站交互时，可以靠一些元数据、或者干脆让语言模型判断具体实现不再适用，接着写抽象类的另一个实例化版本；论文证明这确实有效。

* 附带好处：可以拥有大量具体技能，但同一时刻只有真正相关的那部分处于激活状态，相当于把软件工程的最佳实践也应用到 AI 上。

* 至于怎样组合这些表示方式最好，还有很多研究要做好。

## 从失败里学

### ReasoningBank 的失败案例

* 任务：搜索蓝牙耳机。

* 真实问题：某个特定网站处理搜索词用的是"或"而不是"与"，于是拿到所有蓝牙耳机或索尼的东西。

* 结果集有 5000 条，agent 直接崩了，得把这 5000 条一页页翻过去，慢慢就忘了自己在做什么任务，最后失败。

### 文字反馈优于负样本

* 做法：像 Reflexion 那样观察这条失败的轨迹，写出一些文字指导以后怎么避免。

* 具体指导包括：应该用更具体的搜索词，而不是这么宽泛的关键词；还要一次显示更多条目，让模型一次就能在上下文窗口里拿到更多信息。

* 这类文字也适用于失败的轨迹，而不只是正确轨迹——这也正是你自己写技能时会写的那种内容。

* 该论文整体仍用 Agent Workflow Memory 和 agent 技能归纳那套框架，但不是只对正确轨迹做抽象，而是生成对策略的文字描述。

* 关键差别在于存进记忆的是哪种粒度的内容：完整轨迹和较抽象的轨迹都无效，策略的文字描述提升很明显。

* 这也说得通：概括地描述怎么避免失败，比记住失败再以此为条件来行动更有效。

| 方法 | 存进记忆的是什么 | 加入负样本（把失败轨迹直接放进去） |
| :--- | :--- | :--- |
| SNAP | 完整轨迹：所有动作、观察、工具调用和消息 | 不会提升性能 |
| Agent Workflow Memory | 较抽象的轨迹，也就是工作流 | 不会提升性能 |
| ReasoningBank | 对策略的文字描述 | 提升很明显 |

### 裁判质量的影响

* 决定是否把轨迹存进记忆、还是从例子中推断哪种策略时，都要看判断这条轨迹是否成功。

* 大部分这类工作用一个模型当裁判：它看轨迹的最终状态、看要解决的任务，判断结果是否正确；裁判并不完美。

* 好的问题是裁判的质量在多大程度上影响算法性能。

* ReasoningBank 做了控制：先用一个完美的裁判来运行方法，直接使用任务是否成功的真实信息，再往其中加入噪声，从而控制判断轨迹的模拟准确率。

* 性能确实会下降，但存在一个最佳区间：在这个区间里记忆能带来提升；而且在一段比较宽的准确率区间内，用裁判来归纳记忆都还是有帮助的。

## 经验越多未必越好

### 检索器与记忆规模

* ReasoningBank 的消融实验控制了从记忆中检索的经验数量，结果显示可用的东西越多，性能确实会下降。

* 可能原因一：agent 可能还没在那么多任务上跑过。

* 可能原因二：记忆里本来就没有相关内容，往里塞更多东西只会更不相关——只有学习素材和应用对象之间有相似之处才学得起来。

* 可能原因三：模型本身的局限，上下文窗口里东西多了模型可能被带偏；这可以通过训练模型来解决，让它更不容易被无关上下文干扰、更善于推理什么才是真正相关的。

### 显式缩小记忆规模

* 显式缩小记忆规模也可能有用，这样语言模型从中做挑选的负担就更小。

* 类似缓存的做法：看记忆里某条内容过去被用过多少次，如果某条记忆很少被用到，就把它删掉。

* 这样能明显提升方法的效率，因为放进上下文窗口的内容更少了；如果模型容易被无关内容干扰，还能提高成功率。

## 用强化学习训练技能归纳

### 动机

* 这整套做法某种程度上有点临时拼凑：只是用 prompt 让原语言模型去看过去的经验、生成一个技能、存进记忆里，以后再拿出来用。

* 说白了是在用 prompt 让语言模型预测什么将来可能有用。

* 一个很自然的问题就是：能不能直接训练语言模型来做这件事。

### 做法

* 这个方向最近才开始被探索，相关论文今年才在 ACL 上发表。

* 基本思路是对依次出现的多个任务做强化学习，把之前用来做评估的在线学习设定拿来做训练。

* 依次收到多个相似任务的同时不断构建记忆，构建方式和之前讲的一样：从经验中归纳技能，再把记忆用在后续任务上。

* 过程非常复杂：用了好几个不同的模型，要往记忆里存东西、要检索、还要使用。

* 强化学习不在乎这些复杂度，可以直接用在这样复杂、不可微的过程上。

* 奖励信号可以来自后续任务是不是成功了、agent 有没有用上过去归纳出的技能。

* 奖励里再加一项、鼓励模型复用已归纳的技能，成功率会进一步提升。

* 还可以引入其他类型的奖励项，比如控制技能库的规模、让整个方法保持正则化，避免过度拟合。
