# 工具使用：工具的定义、表达与调用约束

## 工具到底给了语言模型什么

* **工具（tool）**

    * > **定义**：语言模型调用外部计算机程序的一个接口。

    * 语言模型自己做不到这一点，因为它本质上就是一台预测 token 的机器。

    * 工具调用的方法是标准化的，但调用之后下游怎么用可以非常不同。

* **工具的两大类别**

    * **拓展**：让语言模型去做它本质上做不到的事，比如访问超出它动作空间的信息或操作。

    * **辅助**：语言模型本质上能做到，但不让它亲自做会容易得多。

    * 拓展的典型例子是知道四个月前的时间：模型看到最新的信息就是四个月前的，而且参数已经冻结，不调用外部函数它不可能知道。

    * 辅助的典型例子是算乘法：如今语言模型算数学相当不错，但比调计算器慢得多，因为它们得一步步推理；让两个七位数相乘要花很久，而计算器一下就算出来。

* **更细一层的用途**

    * 查实时信息，好处是能为回答提供新鲜的依据。

    * 用计算器或 Python 做精确计算，执行起来比语言模型自己算更可靠、也更快。

    * 访问私有状态，也就是让模型拿到用户的信息，从而根据用户的状态来回应。

    * 改动外部环境，比如浏览网页、调用 API。

## 拿 ChatGPT 做什么，就需要什么工具

聊天刚出来时只是文本进、文本出，唯一能做的就是用文字回答问题；现在它差不多是个万能应用。下面这张表是按使用场景倒推出的工具需求。

| 使用场景 | 需要的工具 |
| :--- | :--- |
| 写代码 | 执行代码的工具；在 ChatGPT 界面里同类能力还落在 Cursor、Codex 这类工具上 |
| 在 Blender 里渲染出东西 | 既要执行代码，又要用合适格式把它展示出来 |
| 生成图片 | 调用图像生成工具 |
| 推荐产品（比如推荐一台搅拌机） | 通用网页搜索，或连接 Google、Amazon 的 API |
| 抓取多个网页和最新信息 | 广泛的信息抓取与检索能力 |
| 把一堆杂文件生成 PDF | PDF 生成工具 |
| 渲染 LaTeX | 不确定是工具还是前端界面的事，可能只是在浏览器里渲染 |
| 与 Slack 之类的交互 | 另一类专用 API |

## 我认为最典型的那些工具

* **文本回复**

    * 最无聊的一种，直接给答案，在 Agent 循环里有两种实现方式。

    * 一是设置一个 finish 工具，意思是「我跟用户的交互结束了」，收尾并输出一段文本。

    * 二是 Agent 决定不调用工具，直接结束循环。

    * 附带的一个界定：ChatGPT 现在已经是个 Agent 了，它不只是聊天应用，会对问题做迭代式的工具调用——这差不多就是 Agent 的定义。

* **搜索网络**

    * 从各种不同的来源拉取信息，理论上都能看作 API。

    * > **定义**：检索增强生成（RAG）是先检索上下文、再基于它生成答案。

    * 现状判断：RAG 已经变得太普遍，大家甚至意识不到自己正在用它，所以它活得好好的，反而让人觉得它死了。

    * 搜索网络、检索信息、再基于它生成答案，如今在这些应用里已经是标配，几乎所有聊天界面都广泛提供这种工具。

* **代码执行**

    * 丢进去一段代码，让它做计算或者类似任务。

    * 做计算非常好用；「既要执行代码，又要用合适格式展示出来」这类场景全靠它。

* **图像生成**

    * 与前面那些跟文本打交道的工具不同，它跟图像打交道。

    * 一个有意思的地方：实际用的查询词和你输进去的不一样，比如「一幅水彩，机器人在图书馆里学习」送进图像生成器的查询词完全不同。

    * > **提示**：调用图像生成很关键的一步是决定往里面放什么查询词，所以语言模型在调用图像生成 API 之前会大幅扩写查询词。以前下载图片时会发现说明文字跟你给的完全不同，这样可以间接看到实际发给图像工具的查询。

* **自定义函数**

    * 比如「帮我买香蕉、牛奶和咖啡」，可以生成购物车然后调用 Instacart 的 API 完成。

    * 工具想怎么玩都行，想加哪个就加哪个。

## 代码是一种元工具

* **元工具视角**

    * 第一种理解方式很直接：给 Agent 一份列表，里面有 50 个或 70 个 API 函数供它交互。基本做法就是每一步调用一个 API，或者用并行工具调用一次调用多个。

    * 代码是一种比较特殊的 API，因为代码的表达力极强，可以看成一种元工具。

    * 「面包师烤了 200 个面包，还剩多少个面包？」听起来简单，其实是在调用一个赋值工具、调用赋值工具、再调用减法工具、再调用赋值工具，诸如此类一直下去。

    * > **定义**：每段代码都是由这些函数调用构成的一棵树。

    ```text
      200 ──赋值──► bakeries
      50  ──赋值──► sold
                  │
                  └──减法──► (bakeries - sold) ──赋值──► remaining
                         │
                         └──还可以是循环 / if / 函数调用 ……

      树里还能有循环和其他控制流，所以它本质上是一种非常丰富的
      调用工具的方式。树的每个叶子都是一次具体调用。
    ```

    * 代码还能引入外部库，这些库就成了你拉进系统里的自定义 API：调用 Pandas 就等于打开了 Pandas 里的所有工具。

    * 也可以构建自己的工具函数，随时调用想要的专用函数。

* **CodeAct**

    * 三四年前刚开始用 LLM 构建 Agent 时的标准做法是逐步反复调用：拿「确定买某款手机在美国、日本、德国和印度四国里最划算」这个查询，先调汇率工具查德国，再调手机价格查询工具，再调文本转换工具，接着再查汇率、再查价格，来回折腾。

    * 写代码则只要写一个程序就能完成，调用工具的方式更丰富也更高效。

    * 这个方法叫 CodeAct，相关论文的核心结果基本上是：成功率上升了，平均交互轮数也下降了。

    * 这个提升甚至包括那些传统上不需要代码、原本被视为普通工具使用任务的任务——代码就是完成它们的好载体。

* **程序化工具调用的代价**

    * 循环和变量：它可能会卡住，可能写出死循环，你就得在系统里处理死循环。

    * 库：安全问题和版本管理。网络安全领域 Agent 的一大问题是 Agent 会引入已被入侵的库，Agent 被攻破了整个系统也就被攻破了。

    * 代码的行动空间很大，也更难约束，所以更难做验证，也更难得到可预期的行为。

    * 它们的影响也更大，会占用更多内存、磁盘、CPU 之类的资源。

    * > **注意**：一旦用上程序化工具调用，就得考虑沙箱，考虑怎么把 Agent 关在里面之类的问题。

## 工具调用是怎么表达出来的

* **工具调用即 token**

    * 工具调用是以 token 的形式表达的。

    * 文本续写「天气晴朗」，而工具续写就像一次工具调用，里面会有 `get_weather` 之类的函数。

    * 两者经常出现在同一个输出里。

* **ReAct 的结构**

    * 上面是文本部分，工具调用写在下面；模型一边发起工具调用，一边给人回复。

    ```text
      文本（thought + 给用户看的回复）
            │
            ▼
      工具调用  ──►  工具执行  ──►  观察 Observation
            ▲                                    │
            └────────────────────────────────────┘
                      回到下一轮补全

      这样 ReAct 循环就不再用分开的代码来表达了，
      而是表达成一次完整的补全输出。
    ```

    * 如果用的是推理模型（能做推理、有很长推理链的那种），输出会分成三段：前面是思考 token，然后是消息，最后是工具调用。

    ```text
      ┌────────────────────────────────────────────────┐
      │  思考 token   非常冗长，不会展示给用户          │
      ├────────────────────────────────────────────────┤
      │  文本/消息    简短一些，展示给用户               │
      ├────────────────────────────────────────────────┤
      │  工具调用     那里实际的输出                     │
      └────────────────────────────────────────────────┘
    ```

* **服务 token 必须预训练时就在词表里吗**

    * 这些服务 token 都会在词表里，但「预训练时是否必须在词表里」的答案可能是否定的。

    * 通常来说，如果你是在整个互联网上做预训练，词表里不一定非得有这些 token。

    * 更常见的做法是在中期训练阶段引入它们，也就是介于预训练和后训练之间的那个环节：在这个阶段用中等规模的数据，按你想要的格式来训练模型。

    * 之后可能还会做强化学习，但在整个互联网上预训练时不一定有它们。

* **聊天格式与工具 schema**

    * 聊天格式里有系统消息、用户消息、助手消息，以类似 JSON 的形式表示，比如在 Python 里调用模型时就是这样。

    * 这些会被转换成带特殊 token 的形式，所以每条聊天消息都有特殊 token。

    * 工具基本上就是给请求增加了一个结构：告诉调用方这是一个函数、函数名是 `get_weather`、参数是 `city`、类型是字符串、且为必填。

    ```json
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "parameters": {
          "type": "object",
          "properties": {
            "city": { "type": "string" }
          },
          "required": ["city"]
        }
      }
    }
    ```

    * 这个 schema 会传给调用 OpenAI 时使用的 chat completions 函数，出现在 prompt 的 `tools` 部分，输出最终是一个带 `name` 和合适参数的调用。

    ```json
    { "name": "get_weather", "arguments": { "city": "Pittsburgh" } }
    ```

    * 你可能不会做预训练，但至少从中训练开始往后，你都要训练模型去适配某种特定的工具调用格式。

* **各家方言**

    | 模型 | 工具调用格式 |
    | :--- | :--- |
    | Qwen | `<\|im_start\|>`、`<tool_call>`、`<\|im_end\|>` 这样的标记 |
    | Mistral | `[TOOL_CALLS]` 列出所有调用 |
    | DeepSeek | 自有的 DSML 标记语言做函数调用，不叫工具调用而叫函数调用，用 `<invoke>` |

    * 这些格式基本上都能用，用同样的数据和同一个模型训练，哪种格式性能更好差别其实很小。

    * 需要知道的是它们各不相同：不能想当然地认为适用于 DeepSeek 的解析代码换个 Qwen 也能用，反过来也一样。

    * > **易错点**：做微调从已训练好的模型出发，一定要匹配它的工具调用格式，别让它做没训练过的事。Hugging Face 里都用 `apply_chat_template` 函数实现好了，套用现成的 chat template 就行；实现得不完善可以进去提需求让他们补上，或者自己动手。

## 从模型的输出到真正执行

* **解析、查找、校验、执行**

    * 前提是语言模型输出的内容能解析成函数参数；在初始化时注册这个工具，还要有一个解析机制得到从名字到要执行工具的映射。

    * 大多数 Agent 框架都提供添加新工具的方式：每个工具有自己的名字，对应一个 Python 函数之类，Python、TypeScript 都行；调用时带上相应参数，分发到那个函数。

    ```text
      模型输出
         │
         ▼
      解析 ──► 查找工具（名字 → 函数的映射） ──► 按参数校验
                                              │            │
                                          失败 ▼            ▼ 成功
                                    模型给了错误的调用     执行函数
                                                            │      │
                                                       失败 ▼      ▼ 成功
                                                 形式没问题但    观察结果
                                                 运行时才失败          │
                                                             带调用 ID 一起返回
    ```

    * 校验阶段就可能失败，比如模型给了你错误的工具调用。

    * 执行阶段也可能失败：有些调用虽然形式上没问题，但实际上仍然无效，比如执行 Python 的工具可能接受任何字符串当代码，但真正运行时才失败。

    * 无论成功还是失败，你都会得到一个观察结果。

* **调用 ID**

    * 基本上每次工具调用都会被分配一个 ID。

    * 运行它时——不管是由语言模型的推理代码还是 Agent 代码来跑——得到的结果会带上匹配的调用 ID。

    * 这在并行工具调用的场景下特别有用，有了 ID 的对应关系就知道哪个工具调用对应哪个结果。

    * > **易错点**：Anthropic 在某个工具调用没有匹配的工具结果时会直接报错挂掉，提示这是无效的历史，「我不会接受这种历史，也不会再为你生成任何输出」。实践中 assistant 刚发出一个工具调用时程序可能就挂了，恢复之后把这段历史原样发回去会被拒绝。

## 三层约束与约束解码

* **格式永远可能是错的**

    * 语言模型生成的工具调用绝对不保证格式正确，例如这段 JSON 少了最后一个右括号。

    ```text
      {"name": "get_weather", "arguments": {"city": "Pittsburgh"}
                                                           ↑ 少了这个 }
    ```

    * 缺括号的 JSON 放进解析程序会抛出异常，事后手工补上一个不该这么干，这么做一点也不好玩。

    * 更好的做法是给每个工具调用设定一系列约束条件。

* **三层约束**

    * **语法**：必须是合法 JSON，这只是最基本的要求，首先得能解析。

    * **结构**：如果有预期字段或必填字段，就必须把它们都填上。

    * **类型**：城市这个字段必须是字符串；如果是数值，单位也得是正确的单位。

    * 这些都能用 JSON Schema 表达，或用任何 Schema 库也行，产出机器可读的验证规则，可以据此检查一次调用是否符合 Schema。

* **从正则文法到上下文无关文法**

    * 要表达一个 Schema 有效还是无效，一种办法是在它之上定义一个文法。

    * 正则文法就是正则表达式，而解析正则表达式对应的是有限状态自动机。

    ```text
                  a                 b 或 c
       q0 ─────────────► q1 ────────────────────► q2
       （起始状态）      （读到 a）                （读到 b 或 c）
    ```

    * 有限状态自动机处理的是正则文法，像 `.*` 这类用来搜索文本的正则表达式都能用它表达。

    * JSON Schema 无法用正则文法表达，可以用上下文无关文法表达，它能构建出一棵树。

    ```text
      schema  ::=  "{"  members  "}"
      members ::=  member (","  member)*
      member  ::=  key  ":"  value
      key     ::=  STRING
      value   ::=  STRING | NUMBER | units
      units   ::=  "C" | "F"          ← 不含 "K"，到这里就构建失败
    ```

    * 格式正确就能构建出完整的树；格式不对或许能构建出大部分的树，但到了单位这一项就构建失败——尽管单位其实可以取 K，这里定义成不接受开尔文作为温度单位。

    * 推论：只要你能用 JSON Schema 定义的上下文无关文法来解析工具调用，就能做到这一点。

    * 有限状态自动机解析不了上下文无关文法，但下推自动机可以：它在正则文法的基础上加了一个栈，把内容压入栈、再从栈里弹出，最终判断输出能不能被解析。

    ```text
      从下推自动机的起始状态出发，在从左到右生成输出的过程中，
      同步验证它：

        生成一个 token ──► 查文法，合法？ ──► 压栈 / 弹栈 ──► 下一个 token
                              │
                              └── 不合法 ──► 该 token 直接出局

      全部生成完 ──► 栈必须正好见底，且处于接受状态
                     ＝ 这一串输出能被这个文法解析
    ```

* **XGrammar：一边生成一边查文法**

    * XGrammar 实际被广泛用在各种 LLM 推理库里，是机器学习系的人开发的。

    * 每一次语言模型的运作都是如此：要预测下一个 token 的 logits 时就查一下文法，合法记 1 分，不合法记 0 分。

    ```text
      原始 logits:  [z₁  z₂  z₃  z₄  z₅  z₆]
                    合法 合法 非法 合法 非法 合法
                        ↓  把不合法的置为 -∞
      掩码后:      [z₁  z₂  -∞  z₄  -∞  z₆]
                        ↓ 重新归一化
      分布:        只在合法 token 上有概率，非法 token 概率为 0
    ```

    * 写成公式就是：

    $$
    p(t \mid \text{prefix}) = \frac{\exp z_t \cdot \mathbb{1}\!\left[t \in \mathcal{V}_{\text{legal}}\right]}{\sum_{t' \in \mathcal{V}_{\text{legal}}} \exp z_{t'}}
    $$

    * 这样又得到了一个合法的分布，概率只落在合法 token 上，保证生成合法的输出。

    * 论文里的另一处处理：有些 token 永远有效或永远无效，可以预先算出来；还有些 token 只在某些上下文中、特定的栈上下文里才有效，就得实时计算。

    * 只要启用了这个功能并设置好相应的 JSON Schema，几乎总能得到格式规范的工具调用。

* **约束解码也拦不住的情况**

    * 答案：当 token 用完的时候。

    * 模型只能生成固定数量的 token，你可能还在自动机的合法路径上，但没走到最终状态，于是只生成了一部分 JSON 就输出了。

    * 此时输出在文法上是「合法前缀」而非「合法句子」，任何逐 token 的合法性检查都拦不住它。

    * 理论上有办法解决：数一数还剩多少可输出的 token，然后提前截断。切入点是栈深度、接受状态，以及生成循环里每一步的栈快照。

## 把工具交给 Agent

* **编程式工具调用**

    * 基本上就是给模型一个 Python 程序，让它用这个程序里的东西来调用工具。

    * 你可能会写一个 `weather_lib.py`，放着 `get_weather` 函数，带上 `city` 和 `units` 参数，说需要时就调用它；再给它执行 Python 的能力，就能调那个工具了。

    * 它可行，但没法远程调用，也没法通过你平时使用的标准工具调用方式来调用。

* **FastAPI 与 curl**

    * FastAPI 能让你极其简单地搭起一个网页后端：建一个 FastAPI，提供一个 API key 让用户验证，再写个 Python 装饰器，服务就搭好了。

    * 第一个好处是认证：可以要求 API key，挡住所有没有合适 API key 的人；不想让别人拿到你的个人数据之类时尤其重要。

    * 另一个好处是免费得到一个 JSON Schema：你的整个 API 都能表示成 JSON Schema，原样提供给语言模型，模型就能用它来指定哪些调用是允许的；每当作 Agent 发起工具调用，就发给你的 API 服务器执行。

    * 调用这些 API 的另一种方式是直接用 `curl` 命令；coding agent 能访问 bash 就能这样调用。

    * > **提示**：FastAPI 挺好用且上手很容易，它算的是 Agent 出现之前的传统编程方式。

* **MCP（Model Context Protocol）**

    * 由 Anthropic 在大概两年前或一年半前推出，设计初衷是提供一种标准方式给你的模型补充上下文。

    * FastMCP 基本上就是 MCP 版的 FastAPI：把 FastAPI 换成 FastMCP 就能非常轻松地搭出 MCP 服务器；还可以拿 REST API 生成的 spec 直接转成一个 MCP。

    * 每次搭建的结构是：一个 AI 应用 / Agent 进程，配置几个 MCP 客户端，比如天气客户端、天气 MCP、GitHub MCP，这样就能查天气、推送到 GitHub。

    ```text
       AI 应用 / Agent 进程
             │
             │  持有 MCP API 密钥（相对无害的那把）
             ▼
       ┌───────────┐        ┌───────────┐
       │ 天气 MCP  │        │ GitHub MCP│
       │  服务器   │        │  服务器   │
       └───────────┘        └───────────┘
             │                    │
             │  持有上游 API 密钥   │  持有 GitHub token
             ▼                    ▼
          天气服务 API          GitHub（Agent 永远拿不到 token）
    ```

    * 想用 MCP 的主要原因是相比普通 API 多了这一层安全保障。

    * MCP 有自己的 MCP API 密钥，需要提供给运行 Agent 的那个进程。

    * 除此之外还有上游 API 密钥，比如连 GitHub 时上游 API 密钥就是 GitHub token——给 MCP 服务器，不给 Agent。

    * > **定义**：凭证分层——Agent 只拿一个作用范围受限的临时凭证，真正的长期凭证留在 MCP 服务器那一侧。

    * 要紧的原因：如果你把 GitHub token 给了 Agent，而它突然觉得把这个 token 推到你的公开仓库是个好主意，你的账号会被入侵，所有仓库都可能被装上恶意软件；给 Agent 一个相对无害的东西，即使泄露也无伤大雅。

    | 维度 | 普通 API（JSON Schema 直给） | MCP |
    | :--- | :--- | :--- |
    | 工具发现 | 可能得去获取一份 OpenAPI 文档 | 有专门的 API 可以列出所有工具 |
    | 调用 | 调用的是一个 HTTP 接口 | 有自己的传输层，方式多种多样：标准输入输出、socket 诸如此类 |
    | 认证 | 往往是上游凭证直接暴露 | MCP API 密钥 + 上游 API 密钥分层 |
    | 额外能力 | —— | 还可以添加资源、prompt 和扩展 |

* **MCP Registry**

    * 官方的 MCP 注册中心，想找到能实现这类功能的 MCP 可以去这里找，能找到数量非常多的 MCP。

    * 另外还有一大堆 MCP Server 网站可以访问，都按排名排列，给出受欢迎程度之类的内容。

## 并行工具调用

* **要解决的问题**

    * 它要解决的基本问题，和程序化工具调用一样：工具只能一个一个地调用，哪怕很简单的操作也会变得很长，比如先查天气、再看一眼日历、然后查航班。

    * 如果这些工具调用互相独立，就可以同时发起，做法很简单，只需要添加多个工具调用。

* **两个细节**

    * 第一个：只有当工具调用之间没有依赖关系时才能并行执行。查匹兹堡的天气、读今天的日历、查航班状态这几个并行就挺好；但先找客户 ID、再查订单、然后退款显然不能并行；如果日历或航班依赖天气，也同样会有问题。

    * 第二个：你会不会真的并行执行这些工具调用？答案是通常会——可以用常规的 Python 语法写一堆工具调用，用 `asyncio.gather` 这类方法在它们同时运行时把结果返回回来，这种做法很常见。

* **高效与低效模型的一个重大区别**

    * 存在一个奇怪的悖论：按任务逐个衡量的话，更贵的模型实际上可能更省钱。

    * 第一个原因是更贵的模型可能更聪明，能更快选到合适的解决方案。

    * 第二个原因是更新的模型并行工具调用做得好得多，能同时发起一大堆调用。

    * 所以编程 Agent 之类的工具用更好的模型时，会同时查看一批图片，或者同时写一堆不同的文件。

    * > **提示**：并行能力的大幅进步是强化学习逼出来的——模型被强烈激励要尽快完成任务；在强化学习时对任务执行时长施加重惩罚，就能得到多得多的并行工具调用。

## 怎么评估工具用得好不好

* **Berkeley Function Calling Leaderboard（BFCL）**

    * 这是评估语言模型工具使用能力最著名的数据集，评估这一能力是因为它是语言模型做好 agentic 任务的前提。

    * 它有四个版本：第一版基本上就是单轮工具调用；经过四个版本演进，现在涵盖多轮工具调用，也有 agentic 工具调用（更多是工具调用型 Agent，而不是端到端的编码 Agent）。

    * 它还测工具调用的鲁棒性，比如参数的幻觉；也测格式敏感性，榜单里有相关指标。

* **评估整个技术栈的维度**

    | 维度 | 具体看什么 |
    | :--- | :--- |
    | 工具选择 | 有没有为任务选对合适的工具——它可能选了个不合适的工具，根本没法完成这个任务 |
    | 参数 | 填的值对不对 |
    | 执行顺序 | 如果是 agentic 工具调用，看执行顺序对不对 |
    | 端到端 | 端到端的任务准确率 |
    | 效率 | 多快能完成任务，花了多少 token、成本多少 |
    | 可靠性 | 工具调用超时了会不会合理地重试？某个工具出故障了，它能换一个吗？ |
    | 安全性 | 存在对抗性输出、让它以不当的方式使用工具时，它还能正确处理吗？ |

    * 这些都是该基准里的指标，这个基准经过四次迭代覆盖了以上所有维度。

* **OpenRouter 工具调用错误率基准**

    * 这是一个针对同一个模型的测试，所有条目唯一的变量是由谁来提供这个模型。

    * 差距从 15% 一直到 0.01%，最低到 0.005%。

    * 原因一是各家用的解码或推理算法可能不一样，一个很大的差别是用不用模型量化、量化精度是多少：FP8 大概是模型量化的默认精度，工具调用错误比 FP4 模型少得多；FP4 压缩得非常狠，是帮推理服务商省钱，模型通常也更差，能保持同等性能的 FP4 量化方案并不多。

    * 原因二是投机解码——用一个更便宜的小模型去预测大模型接下来要输出什么来加速推理；无损的投机解码按理说不该造成差别，因为它不改变模型本来的输出结果，有损的投机解码结果就可能不一样。

    * 原因三是约束解码：很多提供商都自己实现推理算法，有些用 vLLM 或 SGLang 这类开源方案，而它们支持不同的语法解码算法，所以有些提供商可能压根没实现，就完全靠语言模型自己把工具调用做好。

    * 最后一个比较无趣的原因是推理提供商可能不稳定，有时候会宕机，工具调用就失败了。

## 这套东西是怎么叠起来的

* **工具使用是一个分层系统**

    ```text
      工具 schema ──► prompt 的 tools 字段 ──► 模型发出工具调用
                                                      │
                  约束解码（语法 / 结构 / 类型）◄─────┘
                            │                        ← 只保格式，不保语义
                            ▼
            解析 ──► 查找 ──► 校验 ──► 执行 ──► 按调用 ID 匹配结果
                            │                              │
                    REST / MCP 对接              依赖编排 + 并行
                                                     │
                                                     ▼
                                                   评估
    ```

    * 工具带来的各种能力——检索、执行、生成、应用——正是它们让 Agent 成为 Agent，但这并不是白来的。

    * 你可以把 schema 加入 prompt，模型发出调用，然后你验证、分发，再按 ID 匹配结果。

    * 也可以加基于语法的解码约束，但并不保证语义正确：一个 Python 程序就算生成的字符串能被解析成 Python，程序本身仍可能是错的。

    * 对接方式有好几种，比如直接做 REST 调用或者用 MCP；还有很多系统负责编排依赖关系和并发。
