# 长上下文建模：容量、结构、训练与压缩

## 上下文增长的量级

* **Agent 循环的 token 累积**

    * > **定义**：一次 agent 调用把 system prompt、已有历史与新增的工具返回全部串进同一条序列，使上下文随轮次持续膨胀。

    * 初始 system prompt 约 1,000 token，每次调用约新增 5,000 token。

    * 第 $n$ 次调用时上下文长度约 $5{,}000n$；不做任何处理时累计处理量约 $2.5\times 10^{9}\cdot (n+1)n/2$。

| 轮次 | 上下文长度 | 累计处理量（无任何处理） |
| :--- | :---: | :---: |
| 第 1 次 | 6,000 | 6,000 |
| 第 2 次 | 11,000 | 17,000 |
| 第 3 次 | 16,000 | 33,000 |
| 第 4 次 | 21,000 | 54,000 |
| 第 5 次 | 26,000 | 80,000 |
| 第 $n$ 次 | $5{,}000n$ | $2.5\text{e}9\cdot (n+1)n/2$ |

    * 一次编码会话可能连续持续好几天、几乎一整天都在用，单次会话能长到多大无法预估。

## 容量与效率

* **容量挑战**

    * > **定义**：模型到底能不能装下这么多信息。

    * 难点在于要让模型学会处理超长上下文很难，必须在架构、位置编码、训练数据这些方面同时下功夫。

    * 还必须能评估自己到底做得好不好。

* **效率挑战**

    * > **定义**：系统负担不负担得起这么大的服务量。

    * 表现形式是让一个几万亿参数量的模型在几秒内完成响应，而且要反反复复地做。

    * 面向编程的工具（Claude Code、Codex 类）长期高频使用正依赖这类工程能力，用久了容易觉得这理所当然。

    * Codex 有两千五百万用户，按每隔几秒一次请求估算，FLOPs 量级极高。

* **装得下不等于用得上**

    * > **定义**：能接收一百万 token 的模型或服务系统，并不意味着能有效用上一百万 token。

    * 上下文非常长的时候，模型处理起来就可能开始变差。

    * 在 agent 场景里问题被放大，因为用户是在不断追加指令的。

## 推理阶段与效率指标

* **预填充（prefill）**

    * > **定义**：把所有不需要生成的输入 token 一次拿进来，为每个 token 生成对应的 key 和 value。

    * 也可叫「编码」，但 prefill 是如今更通用的术语。

    * 批量一次做完。

* **解码（decode）**

    * > **定义**：拿着 prompt 已有的 key-value 对逐步生成输出，并把新输出 token 的 key-value 对加进去。

    * decode 是逐步增量的，prefill 是批量一次做完的。

* **推理阶段的两个附加问题**

    * 怎么调度多个并发的查询。

    * 怎么把结果存进 KV 缓存以便复用，而不是一遍遍重新计算。

* **首字时间（time to first token, TTFT）**

    * > **定义**：从提交一段输入、等待服务端处理，到开始看到第一个输出为止要等多久。

    * 输入越长，开始出结果越慢，TTFT 越高。

* **每个输出 token 的时间**

    * > **定义**：生成一个 token 要等多久。

    * OpenRouter 之类网站展示的纵轴基本就是这个；该数字基本可以肯定没有把 prefill 算进去。

    * 逐个对比差距仍很明显：有的服务商只有每秒三个 token，有的能到每秒几百个 token。

* **吞吐量（throughput）与成本（cost）**

    * > **定义**：吞吐量 = 完成的 token 数（或请求数）÷ 总时间，通常在整个系统的整体层面来看。

    * > **定义**：成本 = 花多少钱。

    * 交互式场景（在编程 IDE 里跑任务、人在等）把 TTFT 与每个输出 token 的时间当命脉。

    * 批处理场景（让 agent 在后台跑通宵、人不等）把吞吐量与成本当命脉，对前两个指标可以完全不在意。

    * 服务商谈单时常会问更看重哪一个，这样才能针对更看重的那一项优化系统。

* **标准注意力**

    * > **定义**：由 query、key、value 组成，经 softmax（可能加位置偏置）算出完整注意力场的运算。

    * $$\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}+B\right)V$$

    * 同时考虑了当前 token 和之前所有 token 的关系，并遮掉未来所有 token。

    * 非常昂贵，因为计算量对序列长度是二次的。

## 长上下文失效的观测

| 评测 | 机制 |
| :--- | :--- |
| 大海捞针（needle-in-a-haystack, NIAH） | 一堆长文本中插一句话，再就该句提问，模型必须正确回答 |
| RULER | 长上下文基准 |
| HELMET | 长上下文基准 |

* **大海捞针评测（needle-in-a-haystack, NIAH）**

    * > **定义**：在一堆真实长文本中插入一句指定事实，再就该事实提问的检索式评测。

    * 典型做法是拿一堆 Paul Graham（Y Combinator 创始人）的随笔，往里面插一句「旧金山吃三明治最好的地方是什么」，然后问模型旧金山吃三明治最好的地方在哪儿。

    * 把上下文越做越长来评测模型，最终较弱的模型在超长上下文上就开始表现变差。

* **agent 高频失败案例**

    * 会忘掉之前的上下文。

    * 会忘记对话开头、忘记你给的初始指令。

    * 对话中途明确说了「别做某件事」，结果仍然去做了。

    * 用户已经明说「别删这个」，它还是把它删了，因为它已经忘了这段上下文。

## 架构：把二次方压下去

* **业界上下文长度的量级**

    * 最先进的语言模型标准上下文长度是 25 万到 100 万，大多数厂商瞄准 100 万——谁也不想别人都是一百万而自己只有二十五万。

    * 对 100 万长度序列，每次生成要做 $10^{12}$ 次两两比较，每次比较都需要把很大的向量一遍又一遍互相相乘。

    * 数量级到 $10^{20}$ 附近，对单个序列需要非常大量的计算。

* **从 $O(n^2)$ 到 $O(nW)$**

    * > **定义**：给每个时间步的比较次数加上某个常数上限，把二次方复杂度降下来。

    * 基本上所有解法都归为这一类：$O(n^2)\to O(nW)$，其中 $W$ 指窗口，但不一定是窗口，只要是每次比较数量的上限。

* **局部模型与全局模型**

    * > **定义**：局部模型把计算上限限制在一个局部窗口内。

    * > **定义**：全局模型可能有也可能没有计算上限，但这个上限不是局部化的，信息因此能贯穿整个序列传递。

* **混合模型（hybrid model）**

    * > **定义**：做很多局部计算，再做一次全局计算，如此往复的架构。

    * 如今存在并广泛流行的模型几乎都是某种混合模型。

    * 机制：

        ```text
          层内重复若干次：
          [局][局][局][全][局][局][局][全][局][局][局][全] ...
           ▲             ▲
           │             └── 每 N 层做一次全局注意力（稀疏或稠密）
           └── 大多数层做局部计算（窗口 / DeltaNet / Mamba）

          效果：靠前面几十层的局部计算把信息汇总成状态，
                每隔 N 层用一次全局注意力把这个状态贯穿整段序列
        ```

* **六个混合架构的配比**

| 模型 | 局部 / 循环计算 | 全局注意力 | 比例 |
| :--- | :--- | :--- | :---: |
| Qwen | 门控 DeltaNet | 稀疏注意力 | 3 : 1 |
| GLM | DeltaNet 的一种变体 | 稀疏注意力 | 3 : 1 |
| Kimi | DeltaNet 的一种变体 | 稠密注意力 | 3 : 1 |
| 以 Mamba 为骨架的模型 | Mamba（循环式） | 稠密注意力 | 4 : 1 |
| 走滑动窗口路线的模型 | 滑动窗口注意力 | 稠密注意力 | 5 : 1 |
| DeepSeek | 滑动窗口里交错稀疏分支 | 稀疏分支 | — |

    * DeepSeek 那一行稍有不同：有点像窗口注意力，但有一些稀疏的分支交错在里面。

## 局部计算的三条路线

* **滑动窗口注意力（sliding window attention）**

    * > **定义**：只让当前块与之前固定数量的若干块做注意力。

    * 概念上最简单：把输出切成一块一块的，当前块约 512 个 token，前面还有两块各 512 个 token，而不是所有之前的块。

    * 注意力本身没改动，效果就是这样。

    * 妙在第一层传递的是前一两块的信息；到下一层，前面的块也带着它们之前块的信息，窗口就这样逐层逐渐扩大。

    * 用得相当广泛。

* **线性注意力（linear attention）**

    * > **定义**：从标准注意力公式出发把 softmax 去掉，剩下的只是 key 和 query 的点积。

    * 标准注意力难算的根源是中间的 softmax——要算指数还要做除法，因此基本上只能把所有 key 与 query 的计算全部展开，复杂度是平方级。

    * 表达力更弱：它把「接收一堆实数」变成「归一化成 0 到 1 的概率数、总和为一」，而这种非线性正是注意力的优点与卖点——能聚焦于相关的上文。线性注意力基本把这个能力拿掉了，只剩 query 与 key 之间的点积，删掉了相对比较。

    * 关键收益是利用结合律重排运算：$o_t=\sum_{i\le t}\left(q_t^\top k_i\right)v_i=q_t^\top\underbrace{\left(\sum_{i\le t}k_i v_i^\top\right)}_{S_t}$

    * 状态矩阵 $S_t$ 本质是一个函数，一个从 query 映射到 value 的线性函数。

    * 状态矩阵可分解，因此只需一直保存它，每来一个新的 value 就常数时间更新一次。

    * 于是它基本变成循环神经网络：能线性时间更新状态矩阵，$O(n^2)$ 变成 $O(n)$，而且解决得非常彻底。

    * > **易错点**：⚠️ 标准注意力因为中间夹了 softmax，本身**不是**线性的；只有去掉 softmax 之后，「query 到 value 的线性映射」这句话才成立，这也是线性注意力能重排的原因。

    * > **注意**：$O(n)$ 里连 $W$ 这一项都没有，因为每次更新完全只依赖上一个状态。

* **DeltaNet**

    * > **定义**：把 key 与上一步状态矩阵的乘积当作对目标 value 的预测，用真实 value 减出误差再更新状态矩阵的线性递归。

    * 预测值 $\tilde v_t$：拿时间步 $t$ 的 key $k_t$ 和时间步 $t-1$ 的状态矩阵做比较算出，本质上是对 $k_t$ 的预测结果。

    * 误差项：$\text{误差}=v_t-S_{t-1}k_t$

    * 状态更新：$S_t=S_{t-1}+\beta_t\left(v_t-S_{t-1}k_t\right)k_t^\top$

    * 把 $k_t$ 乘进新矩阵后误差就没有了；但不希望更新幅度太大，所以加 $\beta$ 项——它本质上类似学习率，把矩阵轻轻推向「长得像当前 key 的 query 能输出你想要的 value」的方向。

    * > **易错点**：⚠️ 会在之前的位置积累起大量上下文，而线性注意力没有任何机制能阻止很远处的上下文对后续预测产生坏影响——很久以前一个很奇怪的 key 可能在之后产生非常大的影响。

    * 缓解手段是加衰减项，让矩阵在每个时间步稍微衰减一点，通过每步衰减实际折损久远的过去：$\tilde S_t=\lambda_t S_{t-1},\qquad S_t=\tilde S_t+\beta_t\left(v_t-\tilde S_t k_t\right)k_t^\top$

    * 衰减设得越强忘得越快，因此可以在「更局部一些」与「不那么局部」之间调节。

* **门控 DeltaNet 与逐元素衰减变体**

    * > **定义**：门控 DeltaNet 是在 DeltaNet 上加入门控衰减、让状态按步衰减的变体，用在 Qwen 模型里，是目前比较流行的做法之一。

    * > **定义**：带逐元素衰减项的 DeltaNet 变体，每个矩阵元素以不同速度衰减，GLM 与 Kimi 这两个先进模型用的是表现力稍强一点的这一版本。

    * 因为每个元素衰减速度不同，上下文的不同部分可以各自按不同速度衰减：有的能保留很长时间，有的只能保留很短。

    * 门控 DeltaNet 的思路与之非常类似，只是数学上稍微复杂。

## 稀疏注意力

* **间隔式稀疏注意力**

    * > **定义**：每隔固定数量的 token 安排一次全量注意力。

    * OpenAI 约五年前发过一篇稀疏注意力论文，做法是每 512 个 token 做一次全量注意力。

    * 它对序列长度仍然是二次的，但计算量少了 512 倍。

* **内容依赖的稀疏注意力**

    * > **定义**：先用极廉价的方式算出候选位置，只在这些位置上做完整注意力。

    * 把注意力向量降维投影成非常小的向量，在这些非常小的注意力向量上做注意力，挑出前 K 个，再对这 K 个做完整注意力。

    * top-k 检索是在低维空间里算相似度、用余弦距离做检索；一般不是真的用余弦，其实就是点积，也可能事先做了归一化。

    * DeepSeek 用的就是这个实现方式。

* **两种实现的取舍**

    * 间隔式是一种非常廉价的实现全局注意力的方式，只需要写个 kernel 就能完成。

    * 内容依赖式需要跑两遍，但精度可能更高。

    * 两种做法都被广泛使用。

## KV 压缩

* **分组查询注意力（grouped-query attention, GQA）**

    * > **定义**：用比注意力头数 $H$ 更少的头来提供 key 和 value，以缓解 KV 缓存过大。

    * 存的是 K 和 V 缓存（不含 Q），减少 key 和 value 就能降低存放 KV 缓存所需的显存。

    * 缓存太大会限制单张 GPU 能装下的数量，因此这一项很关键。

    * 头数通常是 $H$ 除以二的某次方，缓存通常能缩减到 1/4 或 1/8 左右。

* **多查询注意力（multi-query attention, MQA）**

    * > **定义**：只有一组的分组查询注意力。

* **多头潜在注意力（multi-head latent attention, MLA）**

    * > **定义**：做降维投影，把 key 和 value 的尺寸降下来。

    * 它不减少头的数量，而是把每个头变小——与内容依赖稀疏注意力的 top-k 思路类似。

* **组合使用**

    * GQA 与更小的 key、value 尺寸可以结合起来用，比如分组查询注意力配上更小的 key 和 value。

    * 有了这些模型，就能处理多达一百万个 token，效率由此成为可能。

## 训练长上下文

* **数据量的硬约束**

    * > **定义**：超长上下文训练的真正瓶颈不是方法而是语料存量。

    * 想让模型处理十二点八万甚至更多 token，实际上互联网上并没有那么多由十二万八千个连贯 token 组成的数据。

    * 这个量级已经相当于一整本书，比大多数维基百科条目都长，而互联网上并没有那么多书。

* **先短后长三步法**

    * > **定义**：把长上下文训练拆成短上下文预训练、更长文档继续训练、长上下文适配三步。

    * 顺序是：先做短上下文的预训练，再用更长的文档做继续训练，最后进行长上下文的适配。

* **打包序列（packing）**

    * > **定义**：把多份文档拼进一条序列以提高数据利用率。

    * 它对效率是有用的，但对学习长上下文没什么用。

    * 把十份文档打包进一条序列，模型学到的并不是跨文档的注意力，而且其实也不应该这样学。

    * 真正需要的是连贯的长篇数据，才能完成对超长上下文的适配。

* **长数据的来源**

    * > **定义**：直接从公开语料中获取连贯长篇样本的取数路子。

    * 直接找很长的文档，比如书籍之类的，这类文档不多，但数还是有的。

    * 代码仓库——通常比较连贯，下载一个大代码仓库肯定能拿到更多 token。

    * 某种多文档语料——收集同一主题的一大批文档，至少它们之间有主题上的连贯性。

    * 专利——公开数据很多，而且可以把它们关联起来。

    * agent 轨迹——现在一大来源，跟 agent 交互一会儿它就能产生非常非常长的轨迹。

    * 合成任务——很多评测本身就是合成任务，所以这条路也走得通。

    * 打包样本可以训练模型处理上下文窗口末尾附近的内容，但学不到全局连贯性。

* **数据配比与训练策略的保密**

    * Anthropic 连架构细节都不公开。

    * 开源公司必须公开架构细节，不然别人跑不了他们的模型。

    * 两边真正保密的是数据配比和训练策略。

    * 各家通常会介绍一部分数据配比：清理过的样例文档和视频、文档仓库文件、issue、PR、长文档、问答、科学论文和技术报告，再加大量合成任务。

    * 通常还有一套扩展策略，比如 8 到 64、256 到 100 万这种。

## 位置编码与长度外推

* **绝对位置编码**

    * > **定义**：每个词嵌入都得到一个位置向量，通常由正弦余弦之类的函数计算。

* **旋转位置编码（rotary position encoding, RoPE）**

    * > **定义**：让位置嵌入被完全去掉，由两个 token 之间的相对距离来决定。

    * 设计动机是不希望绝对位置影响两个 token 会不会互相注意。

    * 方法相当有效，被很多很多模型采用；数学上用到了旋转与虚数这些有意思的东西。

* **无位置编码（NoPE）**

    * > **定义**：干脆完全不使用位置编码。

    * 「Transformer 必须用位置编码，不然位置 1 和位置 5 的词会得到完全相同的表示」这个说法在当今 Transformer 上不成立。

    * 即使位置 2 和位置 5 都是 cat，位置 2 的 cat 只能看到前一个 token，位置 5 的 cat 能看到前面四个 token，两者其实已经不同。

    * 至少从第一层注意力开始，哪怕是完全相同的词，它们的表示就已经不一样了。

    * 门控 DeltaNet 的衰减项之类机制能让每个 token 都不一样，一旦有了这类局部偏置，就不再需要位置编码。

    * 业界现状：有两家模型用 RoPE 或至少部分 RoPE，另两家是 NoPE（其中一家完全依赖 Mamba 这类循环结构自带的顺序信息），还有几家用相对位置编码——用不用相对位置编码基本上是一半一半。

    * > **易错点**：NoPE 只对**自回归**架构成立；encoder-decoder 或全注意力双向的架构里没有因果掩码，每个 token 看到的上下文一样，位置信息必须显式提供。

* **RoPE 承诺为何落空**

    * RoPE 承诺只依赖 token 之间的相对位置，只要相对位置还在某个范围内似乎就没问题；但有两个原因说明这并不成立。

    * 在长度为 $L$ 的序列上训练再扩展到 $sL$，模型从没见过有两个 token 相距超过 $L$ 还互相注意，所以相距超过 $L$ 的 token 很难彼此注意。

    * 相对位置编码其实只是故事的一部分，自回归掩码这些因素也都有影响，因此不能光靠 RoPE 就指望它在更长序列上表现很好。

* **θ 缩放式外推**

    * > **定义**：利用 RoPE 中决定每步旋转量的 $\theta$ 参数做长度外推。

    * $$\theta_i\ \longrightarrow\ \frac{\theta_i}{s}$$

    * 这相当于拉伸 RoPE 的位置，使位置 $s$ 处的 RoPE 位置能够对应到更远的位置上——原来的位置 5 会变成 $5s$，正好对应扩展后上下文里 $5s$ 这个位置。

* **YaRN**

    * > **定义**：比 θ 缩放更精细的扩展方法，思路与 Kimi 的 Delta 注意力有几分相似。

    * 基本思路是希望有些信息传得很远、有些则不用传那么远。

    * 本质上是让一部分维度扩展得多、一部分扩展得少，并不是所有维度都用同一频率去插值。

## 并行策略与上下文并行

* **并行方法的分类**

    * > **定义**：训练与推理的并行可概括为数据并行和模型并行两类。

    * 数据并行之外，模型并行又分多种：专家并行把不同专家放到不同机器；张量并行把要计算的张量拆分到不同机器、也就是把参数切开；流水线并行把不同的层放到不同的设备上。

* **上下文并行（context parallel）**

    * > **定义**：把一段上下文的 key/value 计算沿设备链接力传递的并行方式。

    * 原理是先算出一段上下文的 key 和 value，发给下一个设备，那个设备算出自己那部分的 key 和 value，再发给下一个设备，就这样一直传下去。

    * 它对 agent 越来越重要，因为训练 agent 时要用非常长的上下文来训练它。

    * 一旦上下文超过三万二左右，它就变得重要了。

    * > **易错点**：门控 DeltaNet 的上下文并行 kernel 网上根本找不到——想给 1.3B、3.5B 这类较小的 Qwen 模型用上下文并行，要么自己动手实现 kernel 并保证能跑通、能反向传播，要么换个方案。

    * 建模侧与基建侧的需求经常直接冲突：一头要「我的门控 DeltaNet」，另一头要「给它实现上下文并行的 kernel」。

    * 标准注意力、滑动窗口注意力的 kernel 都比较容易找到；现成的容易，难就难在你不做标准注意力运算的地方。

## KV 缓存

* **写入时机与复用**

    * > **定义**：把每个位置的 key 和 value 存下来，使后续步骤不必重算历史的机制。

    * 一次 agent 调用是：输入 → 输出一段消息和工具调用 → 工具返回结果。计算输入执行的是 prefill，计算输出基本上是在做解码。

    * prefill 和 decode 时都要算 KV 缓存：prefill 部分一次性处理完成，解码则在每次生成 token 时都会做。

    * 做完之后、输出结束之前，每个位置的 key 和 value 都有了，存进缓存以后就不用再算了。

    * 工具结果属于新增内容（没有对它做过计算），又变成新的输入；再生成输出、再得到一个工具结果，然后进入下一步，在 prefill 阶段对新输入算 KV 缓存并生成输出，缓存反复迭代复用。

    * 前缀命中时的行为：

        ```text
          第 1 步  输入: [system | 用户任务] ──► prefill ──► KV 缓存 = [system, 用户任务]
                                                       │
                                                       └─► decode 输出:
                                                            助手消息 + 工具调用
                                                              │
          工具结果（尚未计算过的新内容）  ◀────────────────────────┘
          第 2 步  输入: [system | 用户任务 | 上一步的全部内容]
                     └─► 前缀全部命中缓存，只对新增部分做 prefill 写入缓存
                     └─► decode 输出: 新的助手消息 + 新的工具调用
          ……循环

          到第 50 步时：不做任何优化，要处理的上下文规模 ≈ 新输入的 50 倍
          有缓存时：     只算新增的那几个 token，历史一律只读不算
        ```

* **缓存的收益曲线**

    * 论文中的对照实验：横轴是不同 GPU 上的 token 长度，同一颜色里下面那条是使用缓存、上面那条是不使用缓存。

    * 序列越长，不用缓存的那条呈二次方增长，用缓存的基本是线性增长。

* **缓存计价与命中率**

    * 缓存命中的 token 价格通常只有未缓存的 1/10（数字取自各家官方定价页，包含商业模型）。

    * 命中率 90% 到 95% 一切正常；低于这个数也许还能用，但可能在什么地方吃了亏。

    * 另有说法认为 80% 到 90% 够用，也有说法要求 95% 以上；结论是大部分 token 其实都可以被缓存。

    * 缓存便宜十倍的原因很直接：你只需要把这些东西查出来，而不是真的对它们做计算——尤其 Transformer 里前馈网络的计算非常昂贵，跳过这一步是特别大的优势。

    * 倍数关系：输出这边的开销通常在输入的五倍，输入命中缓存后又只有未缓存输入的十分之一，于是输出和缓存输入之间差了 50 倍，正好反映服务时能省下多少。

    * > **注意**：要非常清楚自己的 token 有没有被缓存，一旦没缓存，运行 agent 就要花很多钱。

* **分页注意力（PagedAttention）**

    * > **定义**：把物理 GPU 内存组织成大小固定的块，让逻辑块可以非连续映射进去的缓存管理机制，是催生 vLLM 的核心创新。

    * 原理是有一块块物理 GPU 内存，把它们组织得像内存块或磁盘块：你可能有块 0、块 1、块 2，而实际计算的逻辑块可以被放进块 7、块 1、块 3，生成时有一个索引指向其中每一块。

    * 目的是能并行生成很多序列：生成完毕就可以把它淘汰出内存，一次性淘汰整个内存块，让计算更高效。

* **基数注意力（RadixAttention）**

    * > **定义**：构建一棵基数树来查找并复用已缓存输入前缀的机制，是催生 SGLang 的技术创新。

    * 它专门针对复用已经缓存过的输入，构建一棵树来查找已经用过的前缀。

    * 刚出来时主要针对 ChatGPT 这类聊天机器人：用户开启一段对话再继续聊，已完成对话的一部分就能被缓存住。

    * 现在对 agent 更重要，因为 agent 的对话更长也更频繁，需要更频繁地做这种查找。

* **缓存感知路由（cache-aware routing）**

    * > **定义**：把请求路由到持有最匹配 KV 缓存的那个 worker 上。

    * 场景是多机服务，比如一个数据中心里 64 个或 128 个节点；每次请求进来都路由到存有你 KV 缓存的那台机器。

    * SGLang 的新版本里已经处理了这个问题。

    * OpenRouter 上有按缓存命中率给服务商排名的榜单，数据不会说谎：有的服务商命中率最差，阿里云、硅基流动这些命中率更高。

    * 影响命中率的两个因素：缓存路由做得好不好，以及缓存淘汰得有多快。

    * > **提示**：命中率低并不完全说明这个服务商差，也可能只是他们跑的负载不一样。

* **保留时长与淘汰**

    * 服务商不会永远保留缓存，过一段时间就会淘汰。

    * Anthropic 以前是 5 分钟，现在接近一小时；只要保持活跃对话、中间不停止，缓存就会一直保留，一旦停下对话就会被逐出缓存。

    * 现在至少有延长到一小时的选项，但选一小时费用会稍微贵一点；说到底他们不想一直留着缓存，因为占用内存实在太多。

    * > **注意**：对用户来说，不管提供商的路由和缓存淘汰做得多好，价格都不会变——你可能仅仅因为他们淘汰得太快就多花了钱。

* **缓存分层的未知数**

    * 把快缓存放设备内存、再放一层更慢的在磁盘这类分层是否被采用并不清楚，值得后续跟进研究。

    * 推理提供商的内部方案在缓存分层上很可能比开源的更好，他们通常把缓存从 GPU 卸到 CPU 上，因为 GPU 显存实在太宝贵。

    * 开源库可能也没闭源方案精细：OpenRouter 上的提供商本职工作就是把推理服务做到极致，部分人用开源库但会在上面自己搭建东西，这算竞争壁垒。

## 写框架时别把缓存弄坏

* **前缀一致性**

    * > **定义**：只有整个前缀完全一样，KV 缓存才能生效。

    * 只负责设计框架而不部署模型时，必须非常非常小心别在无意中把缓存弄坏；想过的不少合理改动最后都被认定是很糟糕的主意，因为不想破坏缓存。

* **系统消息**

    * > **易错点**：绝对不要每次都改系统消息，每走一步就改一次——这基本等于完全没有缓存，连一条能缓存的消息都没有。

* **时间与日期**

    * > **易错点**：不要把当前时间和日期附在系统消息后面，因为时间日期每一步都在变，会破坏缓存。

    * 确实要附加，就附加到最后的用户消息，或者最后一次工具调用的结果里。

* **工具切换**

    * 在对话中途动态更换工具没有问题。

* **模型切换**

    * 每一步路由到不同模型（比如这一步看起来很关键交给强模型，接下来三步换便宜的模型）钱还是省不掉——下次再用那个贵的模型，还得付那十倍的价格。

    * 想靠切换来省钱，就必须非常节制地控制切换的次数。

## 上下文压缩

* **上下文压缩（context compaction）**

    * > **定义**：把之前包含全部观察和动作的历史压碎，只留下之前上下文的精华。

    * 做得不好时 agent 就会忘事、开始做完全不同的事情，甚至可能删掉你的文件系统，这是人们不喜欢它的主要原因。

* **压缩的两条约束**

    * > **定义**：压缩可视为寻找一种对历史的表示，使未来的动作序列保持不变。

    * 把历史压缩得到一个工作状态，希望未来的动作序列与压缩前保持一致，压缩后甚至可能更好。

    * 状态必须有界，足够小到你还愿意继续往下工作。

* **压什么、留什么**

    * > **定义**：以「开头锚点 + 中间编码摘要 + 最近几步」为骨架的保留策略。

    * 开头锚点逐字保留，最近几步逐字保留，中间部分换成有界的编码摘要。

    * 一些好的框架会有意避免删除会话最开头的内容，觉得那部分更重要；当然视情况不同，有时也难免避不开——agent 忘掉会话最开始的东西有时是框架设计缺陷。

    * 证据通常会存进证据库，压缩后仍留在上下文里。

    * 兜底手段：命令行 coding agent 的完整历史一般保存在磁盘上，知道存在哪，就能让 agent 回去把之前的结果读回来。

* **触发条件**

    * > **定义**：决定何时执行压缩的判定方式，共三类。

    * token 阈值——给 token 设个上限，例如「我最多只用 20 万 token，一旦超过就压缩上下文」。

    * 被迫触发——服务商强制的、相当于对 token 数量的硬性上限。

    * 手动触发——很多 coding agent 工具包都有 `/compact` 这样的命令。

* **摘要形态**

    * > **定义**：触发之后对较旧部分做的替换物形式。

    * 结构化摘要，有时会要求通过 tool call 来生成，也就是规定这些内容必须写进压缩摘要里。

    * 自由文本摘要。

    * 加密压缩——记忆里可能只有 OpenAI 在用，压成读不了的东西，因为不想让你偷走他们宝贵的压缩算法。

* **反复压缩的风险**

    * > **易错点**：可能反复不停地压缩，压缩次数越多丢失的信息就越多，agent 会跑偏。

    * 评估方式通常是从整体层面看：替换不同的压缩算法，用你现有的基准来评估。

* **基准不掉分不等于真的好用**

    * OpenHands 刚开始开发时做出了最早的一个生产级压缩算法，用编码 agent 很常用的 SWE-bench 评估，当研究项目做了大概一个月。

    * 当时结果是分数完全没降，还省了大量 token。

    * 上线后它犯了一些特别蠢的错误：每压缩一次就发一个 PR，因为它忘了自己已经向 GitHub 发过 PR，同一个功能收到了五个。

    * 还会忘掉对话中途用户发的指令——因为只在单轮对话上评估过，那种只有一条用户消息的场景，把多条用户消息都压缩掉了。

    * > **结论**：光靠基准测试是不够的；除非基准足够健壮、能覆盖每一个使用场景，还必须在真实环境里测一测。
