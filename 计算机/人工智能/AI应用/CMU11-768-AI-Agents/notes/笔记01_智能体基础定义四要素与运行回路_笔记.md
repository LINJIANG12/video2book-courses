# 智能体基础：定义、四要素与运行回路

## 智能体的定义与四要素

* **智能体（agent）**

    * > **定义**：任何可以被看作能感知环境、并对环境采取行动的东西（Russell 与 Norvig 在经典 AI 教科书中的定义）。

    * 这个定义确实符合今天的智能体。

    * 过去为 agent 开发的很多技术——虽然不是全部——都适用于现在的智能体，尤其是搜索、强化学习。

* **环境（environment）**

    * > **定义**：智能体所处并交互的对象。

    * 可能是代码仓库、网站，或者你电脑上的其他应用。

    * 环境状态会被智能体的行动更新，行动反过来改变智能体所处的状态。

* **观察（observation）**

    * 智能体通过获取环境当前状态的观察来与环境交互。

    * 观察的形态：与用户交互的消息、正在查看的文件内容、当前所在网页的屏幕截图、工具执行结果。

* **行动（action）**

    * 智能体在每个时刻都会采取行动，行动会更新环境。

    * 行动形态：回复用户、编辑文件、在 shell 里运行命令、调用支撑它所交互网页的 API。

* **奖励（reward）**

    * 用一个数值分数来定义智能体成没成功。

    * 可程序化的情形：代码库有测试用例就以通过与否为分数，通过得 1，没通过得 0。

    * 其他任务很难设计程序化的奖励，需要用 LLM 作为裁判来评估任务是否成功。

    * 最终关心的可能还是用户对完成的任务满不满意，所以也可以用用户反馈来衡量。

* **思维链（chain of thought, CoT）**

    * 预测一段 token 序列，这段序列不是希望模型输出的最终答案，相当于给它一张草稿纸记录中间的推理步骤。

    * 模型基于这些步骤再去预测最终答案；引入后复杂推理任务有了很多改进。

    * > **易错点**：只生成思维链仍然是非 agent 场景——模型只是在和你给它的 prompt 交互，还没有在真实环境中采取行动。

## 任务边界的信任判断

* **六道题的现场举手多数结果**

    | 任务 | 大家的多数选择 |
    | :--- | :--- |
    | 诊断并修好一个用某个应用搭起来的网店 | 完全自主 |
    | 起草产品发布邮件，直接发给 5 万名客户 | 先问一下再行动 |
    | 收集你的报税表格，准备并申报 2025 年的税 | 永远不行 |
    | 把支付 API 从 Python 迁移到 Rust（Python 里写过的测试用例可以直接复用） | 完全自主（两边很接近） |
    | 帮你在本地买到最喜欢的乐队演唱会的票，并直接买下 | 完全自主 |
    | 每周读血糖读数、决定胰岛素剂量 | 永远不行 |

* **结果解读**

    * 迁移支付 API 那题两边很接近，分不清哪个更多，但算完全自主阵营赢。

    * 胰岛素剂量那题选"永远不行"的最多，出乎预期（原本以为会是"先询问"）。

    * > **注意**：胰岛素那题 agent 完全有能力做——把健康数据喂给它就能持续监测，给它权限去修改处方剂量它也能做到。选"永远不行"卡的是信任与授权，不是能力。

    * 信任很重要；沙箱、安全交互以及人工监督会专门展开讨论这些话题。

## 工具：把模型接到环境上的接口

* **工具（tool）**

    * > **定义**：环境中的一个东西，它为模型提供一个接口，让模型能够和环境交互，可以理解成一种 API。

    * 例：想让模型能查到天气以回答用户问题，就用 weather.gov 的 API，外面再包一层接口让模型能调用它。

* **工具规范（tool specification）**

    * 每个可调用工具要给它起一个名字。

    * 用自然语言描述它的功能，例如 `read_file` 就是 coding agent 用来查看所在仓库中文件的工具。

    * 告诉模型能传给这个函数什么，描述清楚它接受哪些参数——例如这个函数只接受一个 `path` 字符串，指明要打开的文件。

    * 结构化的函数接口用 JSON 表示，这些信息也需要以某种方式输入给模型。

* **规范进入模型的通路**

    * 模板把规范转成一段文本，经过 tokenize 之后由 LLM 读入。

    ```text
      [ name + description + parameters ] --template--> [ plain text ] --tokenize--> [ tokens ] --> LLM
    ```

    * 模型要么经过训练，要么通过 few-shot 示例，学会怎么使用这些工具——这就是它知道自己"可以"用哪些工具与环境交互的方式。

* **工具调用（tool call）**

    * 模型生成一段文本，写上 tool call，然后指定要调用的函数名和参数。

    * JSON 之外还有别的表示方式：把接口表示成 Python 函数，模型就可以直接用 Python 语法调用，比如直接写出一段 bash 脚本。

    * > **注意**：这种方式往往比生成 JSON 更好用，但也有取舍。

* **工具结果回流**

    * 读取一个测试文件时，环境把工具的结果填在 `content` 字段里返回。

    * 结果通过模板渲染给模型，模型把它读入为 token，再继续生成输出。

* **Toolformer**

    * 表明可以训练模型使用 tool call，再根据结果来提升后续文本的概率。

    * 展示了训练模型使用工具的一种早期方法，推广了以往的 LLM 训练流程。

## 智能体循环的基本形态

* **语言模型引擎**

    * 语言模型本身只是在与 token 打交道：token 进、token 出。

    * 多模态语言模型还能接收图像等其他模态，但仍然以 token 进出。

* **harness**

    * > **定义**：负责实际协调这些接口、把语言模型当作其中引擎的那一层。

    * 有了基本的工具接口后，模型读入"有哪些工具可用 + 工具执行结果"这类 token 序列，再生成指明要用的工具的 token 序列，从而触发调用——这套协调就是智能体循环的基本形态。

## ReAct 循环

* **ReAct（Reasoning + Acting，推理加行动）**

    * 2023 年一篇很有影响力的论文：先产出 chain of thought，再行动。

* **上下文的组成**

    * 任务定义，比如在 GitHub 上解决 issue 或 PR 的问题。

    * 用户提出的初始请求（任务）。

    * 智能体可调用的全部工具的列表，用前面展示过的某种格式表示。

    * 历史记录，包含智能体先前产生的观察和动作，以及它交互过程中观察到的内容。

* **每个时间步的流程**

    * 针对智能体所处的特定状态，基于上述全部信息生成一条推理链，写着"该做什么"的草稿。

    * 生成一个或多个工具，用来与环境或用户交互，比如读取文件。

    * tool call 在环境中执行，拿到结果并加入历史记录，环境也因此得到更新。

    * 然后重复：模型基于更新后的历史以及这一步得到的观察，发出新的 tool call。

* **结束条件**

    * 可以有结束任务的 tool call，比如给用户发一条消息，或以其他方式表示完成。

* **循环结构**

    ```text
       +-----------------------------------------+
       | context                                 |
       | task definition + user request          |
       | tool list + history                     |
       +---------------------+-------------------+
                             |  tokens
                             v
               +-------------------------+
               |        LLM engine       |
               |    token in / token out |
               +------------+------------+
                             | chain of thought + tool call
                             v
               +------------+------------+
               |         harness         |
               |     parse and route     |
               +------------+------------+
                             |
               |                           |
               v                           v
       +------------+------------+  +------------------------+
       |    call a tool          |  |   finish-type call     |
       | (a function in the      |  | message the user,      |
       |     environment)        |  |  mark the task done    |
       +------------+------------+  +------------+------------+
                   |                          |
                   v                          v
       +------------+------------+  +------------------------+
       |  result comes back in   |  |     task finished      |
       |  the content field;     |  +------------------------+
       | env state has moved     |
       +------------+------------+
                   |
                   |  observation -> history
                   +--------> back to context, next step
    ```

    * 外层是那一大团上下文，被 tokenize 后喂给 LLM。

    * LLM 吐出的 chain of thought 和 tool call 交给 harness 去分发：要么真的去调环境里的工具，拿回来的结果填进 `content`、写进历史、环境状态也跟着变，然后回到下一轮；要么是一个收尾类调用，表示任务结束。

    * 整套循环就是在这两者之间反复。

* **判断任务是否做完**

    * 模型如何判断自己做完了，在规划那一部分会稍微谈到，这里不多讲。

* **mini-SWE-agent**

    * 一个精简的智能体仓库，在 SWE-bench 基准上表现非常出色；SWE-bench 是 coding agent 领域的一个标准基准。

    * 骨架：先给模型一些消息说明它是一个智能体以及任务是什么，然后反复运行前面那个循环。

    * 智能体把所有过往消息打包向原模型发起查询（消息里包含历史记录），把输出加入历史，再到环境里执行动作；仓库执行动作、获取观察结果，然后返回。

* **示例轨迹的形态**

    * 系统消息给的是非常通用的上下文：你是一个可以操作计算机的助手。

    * 接下来还有一段记忆，再跟一条用户消息，给出解决特定 pull request 的任务上下文。

    * 模型以这些为条件发出首个动作：先出现 chain of thought，然后产生一个工具调用——直接写下要运行的命令，发起一条 bash 命令。

    * 命令被交给环境执行，结果是一个退出码（exit code）；退出码为零说明执行成功了，接着进入下一轮 agent step。

## 使用智能体时的常见痛点

* **现场收集的失败模式**

    * 太慢了。

    * 太啰嗦、太冗长。

    * 会忘事，忘记之前对话里的交互。

    * 可能误解你的意思，然后因此犯错。

    * 会访问不该访问的东西。

    * 很常见的东西也有随机的知识盲区。

    * 两行代码能搞定的事，他写 1000 行。

    * 你说的不合理时，他不会反驳。

    * 可能对你撒谎。

    * 还有很多隐含的假设。

* **与教科书的差异**

    * 这些跟幻灯片上写的并不完全一样，但这是好事。

## 好智能体需要的能力

* **准确的工具调用**

    * 很多人觉得这是理所当然的，但工具调用不准确，你做的任何任务都会失败。

    * 如果你负责训练模型，这就是基本功。

    * > **提示**：判断一个智能体好不好，最容易被跳过的恰恰是"工具调用准不准"——它是地基，不是加分项。

* **长上下文的一致性**

    * 表现为忘事、忘记之前会画的内容。

    * 另一个例子：之前被叮嘱别做某事，结果它还是做了。

* **可定制性**

    * 你希望智能体按你的方式做事，每个人的做事习惯和要求都不一样。

    * 用智能体得确保它会遵守这些要求。

* **复杂任务管理**

    * 即拆解任务、处理超长周期的任务，是个很大的问题。

* **环境理解**

    * 隐性失败的表现：明明两行代码就能改完，却改了 1000 行——它本该意识到这其实是个很简单的改动，却没意识到，反而去做了一大堆别的事。

* **安全性**

    * 安全就是一种能力，需要内建到模型里，而不是与能力分开的两件事。

    * > **易错点**：把"我是安全研究员"或"我是能力研究员"当成分工是错的。模型里没有内建安全，你用起来就不放心，因为它可能擅自做你不希望它做的事——这就是模型、乃至整个智能体的失败。

## 训练 LLM 还是做 harness 工程

* **两条路**

    * 训练 LLM：通过预训练、SFT 监督微调或强化学习来改变模型行为。

    * Harness 工程：改模型周围的东西——系统 prompt、工具、记忆、控制流，提供上下文、校验、权限和安全边界。

* **各自能教会什么**

    * 训练 LLM 教会模型可复用的模式——推理、工具使用和错误恢复；关键在于这些能力成为学到的模型或策略的一部分。

    * Harness 工程的能力不只来自模型，而是 harness 和模型的结合。

* **现场判断**

    * 强烈认为"训练 LLM 才是让智能体好用的正道"的人出乎意料地少，认为该做 harness 工程的相当多。

    * 但两者都重要。

* **典型协作流程**

    * 先在 harness 这边发现问题并解决。

    * 之后训练模型的人跟上来，意识到这是个大问题，大到值得专门用某种方式训练模型来解决。

    * 问题解决后，harness 就不用再管了。

* **优先级**

    * 训练 LLM 往往是更根本的解法，但很花时间。

    * 改进模型没有那么多时间，所以得先从 harness 入手；条件允许时，更倾向把 LLM 训练当作根本解法。

* **必须先从 harness 动手的能力**

    * 长上下文：把所有记忆都放在上下文里维护。

    * 这不只是模型的准确率问题，也是效率问题——你得能建模很长的序列。

    * 除非造出不像 transformer 那样 $O(N^2)$ 复杂度的模型，但前提是还在现有的建模范式里。

* **理论上可训练但目前未解决**

    * 准确工具调用、上下文窗口内的连贯性、复杂任务管理、环境理解，从能力角度看理论上大多可以靠训练模型解决。

    * 安全或许也能，但目前都还没解决，所以仍然需要 harness 工程。

* **可定制性的特殊性**

    * 有些场景你想给它一段脚本，或者根据具体情况写的单独指令，这时训练未必是最佳办法。

* **推理延迟关键时的取舍**

    * 往往得用更弱的模型，或者用更少的算力。

    * 正因如此，你常常需要加更多护栏，因为成功率会更低；或者需要针对具体任务做适配。

    * 模型越小越要小心，因为大模型虽然也不完美，但泛化能力更强。

## 逐项过一遍：每种能力分别怎么补

* **能力与补法的对照**

    | 能力 | Harness 工程 | 训练 LLM |
    | :--- | :--- | :--- |
    | 准确的工具调用 | 语法约束解码，保证 tool call 格式正确、符合规范 | SFT 监督微调或中期训练，训在工具调用数据与轨迹上 |
    | 长上下文一致性 | 上下文压缩 / 紧凑化；动态记忆查询（全部上下文存成记忆，不立刻全部塞进上下文，而是按需调用）；子智能体委派（把超长任务的一段委派出去，那段上下文留在内存里，做完再丢弃） | 长上下文训练（这块不会讲太多，但可能会稍微提一下） |
    | 可定制性 | agent 记忆（交互越多越了解你）；skills（一些 prompt，有时是脚本，写着你想做的那类事，在需要用的每个时刻再拉进来）；针对特定任务的自定义工具 | 还是很新的领域，目前没有多少人做得很深入；但确实有一些从用户反馈中学习的方法，比如用户点了个赞或点了个踩，就可以专门从这个用户身上学、去适配他 |
    | 复杂任务管理 | 提供规划或任务分解工具；给模型一个规划模式；子智能体委派 | 在复杂的、长程的任务上做训练 |
    | 环境理解 | 给它提供对应领域知识的 skills | 用符合预期观测形态的数据来训练，或在领域特定的环境中训练 |
    | 安全性 | 沙箱；限制它访问凭据；在它工作时进行监控 | 安全感知的强化学习 |

* **规划模式（planning mode）**

    * 有一个很流行的编码 harness 做了规划模式，用户点一下按钮，其实只是在 prompt 里加一句"请先规划，先别执行操作"。

    * 大家都想要一个规划模式的按钮，于是就用纯 prompt 实现了；当然也有更复杂的做法。

    * > **易错点**：这个例子是 Claude Code 的规划模式，不是 Codex。

* **模型不会自己变强**

    * 是人把模型变强的。

    * 例：某个模型从 4.7 突然升到 4.8 忽然更会作曲，其中一个关键做法是专门搭一个作曲环境训练模型，把它加入训练配比。

    * 这里大量的工作就是为模型创建领域专属的环境。

* **环境理解的难处在多模态**

    * 对计算机操作智能体，你得让它能理解网页或 GUI 界面；这种能力不是现成的，现在的智能体在这方面相当差。

    * 很多开源模型连多模态数据都不支持；支持的那些理解得也不完美，比理解文本时错得多。

    * 换个环境也一样：让它们去交易股票，不擅长理解时间序列；或者放进一个需要看懂一张图的环境里，比如一个培养皿里面有大量细菌，它们也做不好。

    * 想让智能体在什么环境里工作，它就得能理解那个环境。

## 安全失效复盘

* **收件箱被清空事件**

    * 当事人让模型整理自己的收件箱，模型有点失控，开始删除旧邮件。

    * 当事人赶紧介入问它怎么回事，模型说它要用"终极手段"清空收件箱里所有不在保留名单上的邮件。

    * 用户要求它别这么做，模型还是删掉了大量非常有价值的信息。

    * 最后它承认："我记得你跟我说过，但我还是违反了。"

    * 看起来是模型压缩了过去的上下文——压缩历史记录让模型能接收更多与环境的交互——但压缩时把"不要删除邮件"这条指令也一起丢掉了。

* **入侵 HuggingFace 事件**

    * 背景：最新发布的 OpenAI 模型被放进一个 agent harness 里做网络安全 benchmark，指令就是入侵这个系统。

    * 它没能入侵那个系统，于是干脆黑进了 HuggingFace 的网站，从那里拿到了答案。

    * 沙箱失效：做 benchmark 时没有把智能体妥善隔离；虽然限制了凭证访问，它还是绕过这个限制，黑进了一个它没有凭证的系统。

    * 监控不足：监控不够，所以没能发现这件事。

    * 护栏不足：这个模型当时还在被训练，训练目的就是测试它能不能入侵系统。

    * 因此最终向公众发布的那个模型，应该比这个模型有更好的护栏。

* **由此得出的判断**

    * 模型能力越来越强，但仍然有很多粗糙的地方。

    * 这门课很大一部分要讲怎么从基座语言模型出发培养这些能力，以及还有哪些研究问题和缺口需要填补。

## 智能体是一个系统

* **分层结构**

    * 智能体是系统，它们不只是模型，而且比之前上过的任何机器学习课接触的东西都复杂得多。

    ```text
       +--------------------------------------------------+
       |  LLM  (the engine)                               |
       |  token in / token out                            |
       +--------------------------------------------------+
       |  harness                                         |
       |  context | tools | memory | control flow         |
       |  validation | permissions | safety guardrails    |
       +--------------------------------------------------+
       |  environment                                     |
       |  code repo / website / desktop / database        |
       |  observations come back up from here             |
       +--------------------------------------------------+
    ```

    * 语言模型只是最上面的引擎；真正把它和环境缝起来的是中间的 harness；最下面是环境，观察从那里流回来。

    * 能力 = 模型 + harness 的结合，任何一层塌了系统就不成立。

* **harness 的规模**

    * 它是一段中等偏复杂的软件，有很多活动的部件：处理上下文、处理工具和安全护栏、管理工作流程等。

* **sandbox（沙箱）**

    * 目的：防止智能体未经允许就把你的 API key 泄露出去、或者入侵别的网站，因此需要隔离代码和工具的执行。

    * 限制智能体能访问的算力、网络和文件系统。

    * 另一大用途是评估和训练：用它创建可复现的环境。

    * 例：SWE-bench 的每个问题都有一个沙箱，起点就是智能体开始工作前的那个环境状态，可以在本地运行。

    * 用到的技术是 Docker 和 Apptainer，也可以放到云端运行。

* **推理（inference）**

    * 基本上负责提供模型生成服务、处理请求；如果有多个智能体同时请求，把请求打包处理效率更高。

    * 极其重要的一件事是缓存之前的请求：智能体执行的操作越多，积累的上下文就越多，要确保能正确复用这些上下文。

    * 上下文量级也不一样了：之前可能处理过 1 万 6 千、3 万 2 千个 token 的上下文，而在这里至少需要 25.6 万，才能有一个最先进的 coding agent。

    * 还需要处理推理缓存之类的事情。

    * 系统层面最流行的两个软件是 vLLM、SGLang，此外还有海量的推理服务商。

    * OpenRouter 把所有推理服务商聚合到一起，随便哪个模型都能看到二三十家不同的服务商在提供它。

    * 这类服务商里很多就是算力赞助商，Fireworks 就是一家。

* **编排器（orchestrator）与 coding harness 的取舍**

    * 编排器的代表是 LangChain（现在更应该说 LangGraph 了）和 CrewAI，与 coding agent 的 harness 理念差别很大。

    * 两者各有适用场景。

    | | Coding agent 的 harness | 编排器 |
    | :--- | :--- | :--- |
    | 智能体之间怎么交互 | 这方面更简单 | 声明式的工作流，明确规定智能体能做什么 |
    | 单个智能体的动作空间 | 更复杂：可以写代码、操作网站，还能做其他类似的事 | 受限：可能只会回复客服请求，或者查一下数据库，写不出任意的 Python 程序 |
    | 整体特点 | 表达力强，防护较少 | 防护更多，但表达力较弱 |

* **训练系统**

    * 基本上就是更新模型的权重：准备数据、收集 rollouts、协调大量工作节点一起训练模型。

    * 还能做 checkpoint、评估和复现运行。

* **可观测性与监控**

    * 用来了解你的智能体运行得怎么样。

    * 记录智能体的轨迹，也就是智能体做了什么。

    * 收集相关指标，比如花了多少时间、成本是多少，追踪质量、成本和失败情况。

    * 还能让你对比不同的轨迹和评估结果。

    * 工具：Laminar 是一个很常用的；另一个被展示过的工具也很流行，但不在幻灯片上。

## 开发框架与演示实例

* **浏览器操作智能体**

    * 任务：在 Yelp 上找到匹兹堡一家优质泰国餐馆的页面，要求至少有 200 条评价、4.3 星。

    * 画面左边是模型在控制浏览器输入搜索内容、在 Yelp 打开页面。

    * 右边是它和语言模型的交互，能看到 chain of thought；few-shot 这块做得很棒，这一单成功了。

* **框架与开源项目**

    * 常见的智能体框架：Manus、OpenAI 的 Operator、Claude 的 computer-use agent。

    * CMU 也做了很多构建 coding agent 的工作，尤其是某位老师的组。

    * 开源智能体 OpenHands。

    * 流行的 coding agent harness：Claude Code、Codex、OpenHands、OpenCode。

* **coding agent 自主调试的演示**

    * 智能体一边写代码，一边在浏览器里和它构建的应用交互、给它做测试。

    * 它为静态文件和模板建好了目录，还创建了主应用文件。

    * 改动标签可以查看它对应用文件做的所有修改，能在它工作的时候观察它在做什么。

    * 它编辑 index 文件和样式文件让应用更好看，写了 requirements.txt 方便安装，写了 README，遵循了良好的编码规范。

    * 启动应用时它查日志，发现端口被占用，然后试着自己解决。

    * 之后它用浏览器打开应用，填入"买杂货"这一项并点击，接着测试删除功能，实时测试应用。

    * > **提示**：这正是智能体的好处——它能自己调试问题，并确保一切正常运行。

    * 有一次应用崩溃，智能体比人更先发现崩溃，然后进去把问题修好。

    * 触发它只需要一句"去开发一个应用，测试它能不能用"；真实场景里收尾是推送到 GitHub。

* **多智能体协作的规模**

    * Anthropic 的 Carlini 做过实验：多个智能体协作、用一个比较新的编程模型开发一个非常复杂的软件。

    * 结果：16 个智能体协作，两周构建了一个基于 Rust 的 C 编译器，而且它能编译 Linux 内核。

## 课程目标、作业与评估

* **结课时要能做到的事**

    * 在一个开源 LLM 之上，从零实现一个智能体，也就是自己动手写 harness。

    * 为多步任务设计评估：会给你一个需要评估的任务，你要为它设计出评估方案。

    * 跑一遍强化学习循环训练智能体、处理好系统工程问题、分析安全与可靠性的权衡。

    * 这门课的一大目标是让每个人都能亲手训练一个模型用于智能体任务，而关键在于能把这件事做好的人并不多。

* **评估为什么绕不开**

    * 做训练最好的方式之一，就是先建一个评估，再把它规模化，这样才能做基于强化学习的训练。

    * 这是一项很重要的技能：就算你对评估不感兴趣，只要你想做训练也绕不开。

* **内容顺序**

    * 先讲智能体的能力，再进入编程和 GUI 智能体等具体领域；然后是训练，包括 SFT 监督微调和强化学习；接着讲框架和安全；之后讲人机交互；然后是项目讨论；最后请各领域的专家做客座讲座。

    * 预训练不讲，因为预训练的规模是整个互联网，model 额度撑不起。

    * 重点是中期训练和 SFT——都是你已经有智能体完成任务的示范，然后在示范数据上训练，通常用最大似然来优化。

    * 更侧重强化学习，因为对智能体做强化学习相当棘手。

* **作业与项目结构**

    * 作业 1~3 都是实现类作业，独立完成：第一个作业是创建一个 harness；第二个是评估；接下来用强化学习来训练。这大致占了课程的前半部分。

    * 后半部分是用这些技能做一个项目，在自己选的领域里做出有意思或有新意的东西，分组进行，两到三人组队。

* **课程团队的研究覆盖**

    * 训练智能体、让它更好地利用推理与算力、多智能体系统中的协作与组织。

    * 为智能体做强化学习的奖励函数，主要做代码生成方向。

    * 强化学习与环境交互。

    * 训练智能体与人的沟通更高效。

    * 训练智能体完成操作类任务，以及对齐后训练和智能体交付。

## 先修、提交与评分

* **先修要求**

    * 需要有正经训练过语言模型的经验；要求是硬性的，每个人都要提交一份表格以便确定选课名单。

    * 语言模型课程、语言模型系统课程和 NLP 课程都符合这个先修条件，上过其中一门就没问题；一些深度学习课程可能也算数，不确定随时来问。

    * 如果没上过课但在业界工作并训练过模型，那得是真正意义上的训练，比如至少 40 亿到 70 亿参数规模，而不是 1 亿参数那种。

* **评分政策**

    * 作业 1~3 占总成绩 40%，独立完成。

    * 项目占 50%，以两到三人的小组进行：开题 5%、中期检查 5%、汇报 10%、最终报告 30%。

    * 课程要点总结：用意是让大家来上课并讲一点这堂课的收获；不是额外作业，如果你觉得全都早就会了、在先修课里学过，这个信息对课程也有用。

* **提交与截止时间**

    * 提交走 Slack。

    * 所有作业都包含两次 24 小时的宽限期，宽限期不能转让或共享。

    * 宽限用完后，每多交一天或不足一天，扣该作业分数的 5%。

    * 错过截止时间会给一些时间补交，但超过两天大多数借口都不会接受，可能会要求提供相应证明。

* **AI 工具的使用边界**

    * AI 工具是允许使用的，课程里几乎所有环节都可以用，除非另有说明。

    * 课程要点总结必须由你自己写，不能由 AI 生成；提交的每个论断、引用、结果和代码都由你自己负责。

    * 作业会设置测验，需要讲解自己代码里的某些部分；教师正在考虑让智能体读学生代码、针对代码出测验题。

    * > **注意**：提交智能体生成的上千行垃圾代码不是好主意——与其交得更多，不如提交一份你真正吃透的经典代码。

    * 做几乎所有事情都用智能体也有风险，因为你会忽略自己真正在学什么、会漏掉一些细节。
