# 面向编程的智能体：语料、训练与定位验证循环

## 单步代码生成与 agentic 编码的差距

* **单步代码生成（single-step code generation）**

    * > **定义**：一个 prompt 换一段代码，语言模型只做一次前向产出，不涉及工具调用与验证迭代。

    * 在单步内具备写代码能力，需要覆盖三件事：理解要用的编程语言、会编辑、会推理。

    * 「会编辑」不是语言模型天生具备的：实际开发是迭代改写而不是一次写完就扔掉，必须靠训练灌进去。

    * 编程一直是推理模型比较成功的应用之一，理由与数学同源——这类结果比较容易验证好坏。

* **Agentic 编码（agentic coding）**

    * > **定义**：在真实仓库里改动多个文件，并把改动验证到能过测试的迭代式编码任务。

    * 一次 prompt 画一张柱状图属于单步任务；修改整个仓库、修某个 issue、做某项改进属于 agentic 任务。

    * 两者共同的三个要素一个都不能少：写 prompt、给 agent 提供工具、备一个真正能解这类任务的好 LLM。

    * 开发软件不只是写代码、修问题、加功能，还涉及很多其他环节。

* **编程模型的三段式训练**

    * > **定义**：预训练学下一个 token 预测，中期训练把通用模型改造成代码模型，强化学习后训练用任务结果做奖励。

    * 预训练语料必须含代码，但不能只有代码——模型还得理解英文以及用户提问所用的其他语言。

    * 中期训练把持续预训练与监督微调放在一起讲，机制接近，都在代码混合数据上继续训练。

    * 「如今每个语言模型都是 coding 模型」这一现状是训练出来的结果，不是天然属性。

| 阶段 | 做什么 | 编码相关关键点 |
| :--- | :--- | :--- |
| 预训练 | 在大规模语料上优化下一个 token 预测 | 语料含代码但不能只有代码；分词器必须覆盖代码 token；grep、操作系统工具这类编程工具也要懂 |
| 中期训练（含持续预训练、监督微调） | 在代码混合数据上继续训练 | 提高代码曝光量的同时保住通用能力；处理超长上下文；学会中间填充 |
| 强化学习后训练 | 拿测试结果当奖励 | 具体机制另有专门内容展开 |

## 预训练语料

* **语料构成**

    * > **定义**：编程模型预训练语料在网页文本之外额外混入的代码相关材料。

    * 混入技术性文章（解释代码怎么工作的）、数学内容（提升逻辑推理能力）、源代码与文档，来源非常多。

    * 编程有专属工具，比如 grep 和操作系统工具；单步场景下也得让模型懂这些工具，因为写 bash 脚本要用。

    * 训练编程模型比训练纯文本模型更难，根因是代码的分布非常独特，数据选择与清洗的难度都被放大。

* **空白符与文件边界**

    * > **易错点**：早期做数据清洗会做空白符归一化，把所有空格压缩成一个空格。对写 Python 是糟糕的，因为空白符在代码里是有含义的；文件边界怎么表达同样要小心。

    * 必须能处理 API，并保留文本与代码之间的关系：文本里有 Markdown 块，要确保内容仍然留在该块里。

* **训练期评估**

    * 常规做法是看 loss 有没有降下来；编码任务也要看，但必须把评估设计成覆盖你关心的那些方面。

## 预训练数据的过滤

* **语言、来源与重复**

    * 第一层按语言和来源过滤：网上有大量完全自动生成的代码，从训练角度看没什么价值，可以去掉。

    * 再去掉带编码错误的代码和低价值的重复代码。

    * > **定义**：**fork** 是低价值重复代码的典型样本——同一个仓库在 GitHub 上有几千到几万、甚至几十万个 fork，直接下载会引入大量麻烦。

* **许可证、来源日期与退出选项**

    * 记录许可证、来源日期、退出选项以及敏感数据过滤，是有人会考虑、有人不会考虑的一层。

    * 许可证风险的形态：用专有许可证的代码训练并发布模型赚钱后，权利人可能在若干年后就训练数据的贡献提出赔偿主张；美国版权法对要不要在乎这件事本身也有点含糊，所以必须自己做出决定。

    * 来源日期的逻辑更简单：不想要老代码就只要新代码，并且允许人们选择退出。

* **敏感数据过滤**

    * 风险源是用户把不该上传的东西推上仓库，最典型的是 API key。

    * > **提示**：已有成熟的敏感数据扫描工具，TruffleHog 基本能识别所有 API key。

* **训练集与测试集的构建**

    * 想构建训练集或测试集就得真的去构建，而 fork 之类的问题让这件事本身很难。

## 代码专用分词器

* **字节级 BPE 与空白符**

    * > **定义**：对代码和普通文本都做字节级 BPE（Byte Pair Encoding，字节对编码）；BPE 本质上只是任意一种子词分词方法，换成别的分词方法也成立。

    * 需要小心保留空白符。

    * 常规做法是把高频出现的内容压缩：在大量处理代码之前，空白符可能就是一个 token，生成缩进 16 格的 Python 就要输出 16 个空格，因此常把「三个空格加一个换行」合成一个 token。

    * 从压缩空白符这一步开始，就必须专门针对代码设计分词。

    * 把代码规范化让它更标准属于可做可不做，不是必须。

* **覆盖哪些语言**

    * StarCoder 的做法是建模很多语言，不是全部，但涵盖了大量非常流行的语言。

    * 训练数据多的语言在特定任务上表现更好；还要考虑用户想用哪些语言、哪些语言写起来更容易、agent 框架支持哪些语言。

* **跨空白符合并 token**

    * > **定义**：把跨越空白符边界的模式合并成单个 token，例如「换行加三个空格」。

    * 好处是表示效率显著提高，在 encoder 那篇论文里这样做 token 数量少了约 40%。

    * > **易错点**：跨空白符合并会以奇怪的方式出问题。`import numpy as np` 变成一个 token 后，模型停在 `import numpy as` 就补不全，必须退回做类似约束解码的处理。

    * 改动分词要非常小心，规模一大就可能出问题。

* **空白符要不要区别对待**

    * 把「空格加换行」单独作为一个 token 的动机，是让模型内部更不容易区分语言 token 和代码 token，尽管两者本质相同。

    * 从字节级编码的角度其实不必区别对待，字节级编码本来就是用来合并字节的。

    * 但几乎所有情况下人们还是会区别对待空白符：模型表现稍差时输出半个词会显得很奇怪，单独分词空白符可以引导模型不要输出半截的词或词元。

## 模型的语言偏科

* **默认语言偏好**

    * 不指定语言时，让模型「帮我写个应用」这类任务主要用 Python；反过来要仪表盘就用 React；其他几乎任何东西都用 Python。

    * 偏好的三个来源：一是语言本身好写，Python 比较简洁；二是流行度；三是下游的强化学习训练用了什么——模型很可能是用 Python 解释器做 RL 训练的，因此更偏向这门语言。

    * 实例：把一条原本用 Python 写的重数据处理流水线转成 Rust 提速后，模型运行其他程序时仍用 Python，必须每次显式重复「用 Rust，用 Rust」才照做。

    * > **提示**：既然偏好这么强，与其指望模型自己选对，不如在每一轮对话里显式指定语言。

## 中期训练

* **提高代码曝光量**

    * 原本数据集比较杂时加大代码占比；也可以根据实验选配比，既提升代码能力又保住通用能力。

    * Code Llama 的做法是拿 Llama 2 额外再训练 5000 亿个 token。

* **上下文拓展的取舍**

    * Qwen2.5-Coder 曾只用 100% 纯代码训练以把代码能力做到很强，结果在数学、问答等重要任务上分数很差。

    * 继续训练时混入文本和数学，代码性能只小幅下降，其他能力却保住了。

    * > **结论**：这件事既可行又重要，因为现在没人只用模型来写代码。

* **长上下文处理**

    * > **定义**：把原本非连贯的语料构造成连贯序列来训练模型，让它能连贯理解仓库里的文件。

    * > **易错点**：最天真的做法是把整个仓库所有文件直接拼在一起，但全部拼起来往往连最长上下文的模型都装不下——训练通常最多到 100 万 token，而很多正经代码库都超过这个量级，Google 的 monorepo 据说有几十亿行代码。

    * 可行的替代：只取一个目录下的内容；或解析依赖图，顺着依赖关系把相互依赖的文件拼在一起。

    * Qwen2.5-Coder 先在 8k 上训练，再用 YaRN 拓展到 128k；这类上下文操作可配合跨文件补全、中间填充以及短上下文保持来验证。

## 中间填充

* **中间填充（infilling）**

    * > **定义**：让模型预测一段代码的中间部分，而不只是做从左到右的补全；InCoder 是最早一批用 infilling 目标训练强代码模型的论文。

    * 典型场景是推断返回类型：函数名 `is_positive` 本身没有信息，只看左边函数体猜不出返回类型，可能是布尔、字符串、枚举；看到右边就能确定。

    * > **结论**：把中间填充任务转化成自回归任务就行，这是做任何 infilling 任务的通用方法。

```text
  一个空洞：
    原序列   prefix   [ 空洞 ]   suffix
    训练     prefix    M0     suffix    M0    content
                                               ↑ 模型只在末尾预测 content，
                                                 不在原位预测被替换掉的 mask
    推理     prefix    M0     suffix    M0   ──模型生成──▶  content

  多个空洞（推广到任意数量）：
    训练     prefix  M0  mid1  suffix  M1  mid2  ...  M0  M1  content1  content2
                                     先生成 M0 对应的内容，再生成 M1 对应的内容
```

    * M0 是放在前缀和后缀之间的标记，紧跟着的 M0 才是真正要预测内容的起点；有多个空洞时用 M0 与 M1。

* **span 的采样方式**

    * > **定义**：训练时按长尾分布随机抽取若干个 span，对每个 span 采样对应的连续 token 内容，再把这些内容移到末尾、用 mask token 替换原位置。

    * 大多数时候只抽一个 span，抽两个的少一些，抽三个更少，最多可以抽到 100 个但概率非常小；输出长度也按类似的长尾方式处理。

    * 模型不在原位预测那些 mask，只在序列末尾预测它们。

    * > **提示**：分布也可以参照现实中真实出现过的填充来设计。

* **能力与代价**

    * 中间填充能支撑大文件中间补全代码、推断类型、注释生成、变量重命名等软件工程任务。

    * > **结论**：加入中间填充训练后，标准的从左到右代码补全能力仍然保持——加上因果掩码把从左到右部分遮住，性能依然维持，所以这两者并不构成取舍。

    * InCoder 论文里从左到右推理在单行、多行等任务上约为 48 对 24 和 25；用从左到右生成 10 个候选再用整个文件的上下文重排会好一些，但仍然远不及专门训练 infilling 的提升，而且这套重排完全不需要。

## 代码之外的学习来源

* **commit diff**

    * > **定义**：改动之前的文件加上 pull request 之类的说明信息，可以生成 diff，也就是改动后的结果。

    * 用这种方式可以训练出很好的代码编辑模型。

* **诊断信息**

    * 拿有问题的代码加报错信息去生成修复；可能来源包括 Stack Overflow、GitHub issue、GitHub pull request。

    * > **结论**：开发者看到代码出错最常出现的地方不是 GitHub，而是测试——尤其是持续集成测试，也就是往仓库 push 时会跑的那些测试。

    * CI 历史公开记录在 GitHub 上，能看到某个版本跑挂了报了错、之后某个版本通过并被合并，是非常丰富的测试数据，而且不用自己生成，因为自己生成会很痛苦。

* **执行轨迹**

    * > **定义**：在测试时给程序插桩再运行，观察它实际是怎么执行的，用来生成「程序执行到某时刻的调用栈」或「执行到某处的输出」这类监督信号。

    * 执行轨迹是代码世界模型依赖的基础方法。

## 代码质量的评估范式

* **与参考解比较**

    * > **定义**：拿一份人工写的代码作参考，直接问机器生成的代码与人工写的像不像，而不是比较运行结果；这套方法大约在 2017 年的一篇论文里用过。

    * BLEU 衡量输出代码的 token 与 n-gram 重叠程度。

    * > **易错点**：BLEU 的局限是它只认表面相似——大于等于号只差一个 token，程序行为可能差别非常大；反过来写法不同但实际等价的表达式，token 重叠差得很大。

* **基于抽象语法树与嵌入的改进**

    * > **定义**：**抽象语法树（Abstract Syntax Tree，AST）**是每个程序都能转换成的树，它规定了程序按编程语言的逻辑如何执行。

    * CodeBLEU 不比较 token 层面的表面相似度，而是基于语法树比较，并加入了语法数据流匹配与语义数据流匹配，也就是看哪些变量来自哪些地方。

    * CodeBERTScore 是 2023 年的工作，走基于嵌入的路线：对两段代码里的每个 token 做嵌入，检查每个 token 在另一段代码里是否都有一个对应得上的 token，从而判断这段代码是不是基本都在另一个实现里有所体现。

* **基于执行的评估**

    * > **定义**：拿候选输出去跑一批测试用例，全部通过得一分，没有全部通过得零分；这是如今更主流的做法。

    * 好处是能接受不同的正确实现，模型写出功能等价但长相不同的代码不会被冤枉。

    * > **易错点**：坏处是写出真正好的单元测试非常难——要么有假阳性（测试不够严格，放过了错误实现），要么有假阴性（给 agent 的输入信息不足以让它通过所有单元测试）。典型例子：需求只写「界面右上角放一个好看的按钮，上面写着 Learn More」，测试却还检查按钮背景颜色，因为这个要求在测试里一开始并不明显。

    * > **结论**：这是现在训练 coding agent 最大的难题之一，任务越来越难，造出既低假阳性又低假阴性的测试非常困难。

    * 通过执行发现语义错误效果确实很好，但需要好测试，也需要在隔离环境里把依赖装好；常见做法是用 Docker 容器把依赖都装进去。

    * > **易错点**：以为依赖装好就没事，还要考虑版本问题——版本一升级测试就跟不上，结果只是因为测试过时，就给新模型打了更低的分。

    * 还需要长期稳定的执行环境：对很大的代码库跑测试可能非常耗时，Django、NumPy 这类项目每评估一个样例跑测试就要 5 到 10 分钟甚至更久。

* **单步代码生成的基准**

    * > **定义**：**HumanEval** 是经典标准基准，给一个带 docstring 的 Python 函数让模型生成补全，背后有隐藏的单元测试；它由 OpenAI 的人手工构造，设计了一批有技巧性的 Python 函数。

    * HumanEval 已经过时，因为每个语言模型都能拿高分，而且它不一定反映真实世界的使用情况。

    * **CodeContests** 稍难一点，风格接近 Codeforces 的竞赛编程。

    * > **结论**：很少有人能第一次尝试就毫无差错地解出一道 Codeforces 题，而这恰恰是对单步语言模型的要求，所以这类任务相当难，需要大量推理。

    * 2021 年提出 HumanEval 的那篇论文评估模型能通过多少，结果显示模型越大通过的越多；同期的 Codex 是当时为 GitHub 实现的最早代码补全模型，与今天的 Codex 同名但不是一回事。

    * pass@1：只生成一个输出，看它能不能通过。

    * pass@k：生成 5 个输出，看其中有没有一个是正确的，是稍微宽容一些的指标。

## 拿测试当奖励的强化学习

* **测试驱动的单步 RL**

    * > **定义**：采样一些回答、跑一遍测试、用测试结果更新模型；这让训练大型推理模型成为可能，因为一步到位解出 Codeforces 题要求模型对回答做非常仔细的思考。

    * 效率这条线索来自竞赛编程任务自带的执行超时限制，一旦超过执行时限这道题基本就拿不到分。

    * 在中期训练之后做这种强化学习能进一步提升结果；DeepSeek-Coder 是这样一个例子：先在 16K 上下文训练了一段时间，又在 32K 上下文训练了更久，最后报告的是 64K 上下文的结果。

* **效率与可读性是否进训练**

    * 对非 agent 任务，代码的效率或复杂度基本没有被纳入训练，主要只看代码对不对。

    * 也有例外：NoFunEval 指出评估不应只看功能需求（程序能不能正确完成它该做的事），还要评估运行时效率这类指标，比如延迟、资源占用，以及基于静态检查的可维护性和安全性。

    * 对 agent 任务来说，考虑效率就更常见。

    * 针对代码可读性的直接做法是训练一个评判代码质量的模型，把可读性作为强化学习奖励里的一项；后训练通常有类似 RLHF 的步骤，训练奖励模型来预测输出有多好，可读性就是可以从人类标注员那里收集的指标之一，再通过奖励模型间接提升。

    * > **易错点**：为什么代码里总会带上解题用不着的注释，这里只有猜测——模型是在带注释的现有代码上训练的所以会补注释；以及被训练做推理后可能存在「多写注释能多换一些 token」的隐性激励。一手依据并不充分，只能当猜测看待。

    * 可以肯定的是，主流模型已经引入某种非功能分类器或代码质量模型，要求写注释且数量合适、不太多也不少；早期对编码模型的一大抱怨是生成海量没人看的啰唆注释，最新版 Codex 发布时强调不会塞一堆注释垃圾。

## 定位、编辑、验证的循环

* **内循环三步**

    * > **定义**：在仓库里修 bug 或实现新功能时的标准三步——定位、编辑、验证，失败信息回灌形成循环，直到全部验证通过。

    * 定位是找到需要修改的地方并复现行为；编辑只做必要的改动，比如只在值为 `None` 时设默认值；验证是跑测试，测试失败就把失败信息喂回去指导下一步。

    * 贯穿的示例任务是找到 `retries` 在值为 0 时没有正确设默认值的那个地方。

* **不用迭代式流程的替代路线**

    * > **定义**：**Agentless** 不让 agent 自由调用工具，而是把定位拆成独立步骤——先预测要改哪些文件，再预测要改哪些类和函数，然后挑出要改的行，最后只用一个单步语言模型生成补丁。

    * 它有一段时间效果出奇地好，不少语言模型用这种流程跑得比 coding agent 还好。

    * > **结论**：原因是当时的语言模型被重度训练成擅长单步代码修复，却没有被重度训练成擅长 agentic 工具调用和验证循环；现在大家基本都用 agent 了。

## 只用 bash 的 agent

* **单工具方案**

    * > **定义**：只给 agent 一个工具——运行 bash 命令的能力，这呼应了「会用 bash 命令非常重要」这个训练要点。

    * **mini-SWE-agent** 是 SWE-bench 团队做出来的，本质上就是一个只用 bash 命令解决问题的 agent。

    * 定位用 `grep`、`ripgrep` 这种表达力更强的 grep，还有 `cat`、`find`；编辑文件用 `sed`，或跑个一次性的 Python 脚本，可以用 `patch`；跑检查用 `pytest` 或构建命令。

* **为什么单工具不够**

    * 像 gdb 这样的工具就那么几个；不是不能提供这些工具，而是只给一个工具时，agent 每次编辑文件都得重新琢磨用 sed、Python 还是 patch。

    * > **结论**：如果大部分工具调用都属于这类，把它们封装成一个更高效的工具，agent 就能干得不错；专门做一个为 agent 打磨的标准文件编辑工具，agent 基本会依赖它，改文件也更准。

## 文件编辑工具的格式之争

* **为什么 bash 不够好**

    * 用 sed 替换时要一直写反斜杠，数量还必须完全正确；有不少原因让 bash 未必是处理文件这类工作的最佳接口。

* **Unified diff 的问题**

    * > **定义**：**Unified diff（统一差异格式）**基本形态就是行号加需要做的修改。

    * > **易错点**：让 agent 去对行号，它经常搞错，补丁就打不上。

* **查找替换格式**

    * 更常见的做法是给一段看起来很像 diff、但不是纯 diff 也不指定行号的内容，这大概是最常见的做法，很多 coding agent 都在用。

    * > **易错点**：靠右边上下文匹配时，如果文件里有多处 `retries = 3` 就匹配不上，也没法确定该改哪一个，这时 coding agent 得多写几行直到没歧义。

    * > **结论**：右边做法的好处远大于这个缺点，所以几乎所有 coding agent 都用它；diff 格式影响很大，文件编辑工具的格式同样影响很大。

    * Aider 代码编辑基准比较过查找替换与 unified diff 两种方式在当时模型 GPT-4 Turbo 上的表现，结论是 GPT-4 Turbo 更适合 unified diff，因为训练的时候见得多。

    * > **提示**：模型在没见过的编辑格式上会明显掉分——近期 Gemini 在不少 harness 上表现很差，原因就是它训练用的是自己那套编辑格式，跟别人都不一样；处理不好这可能是个非常大的瓶颈。

## 找到相关代码

* **搜索与引用追踪**

    * 从搜索手头的信息开始：`ripgrep` 是最常用的工具，也可以用 `grep` 或专门的代码搜索工具。

    * 接着顺着引用追踪下去，agent 就去修复问题。

* **更复杂的定位方法**

    * > **定义**：**LocAgent** 给 agent 提供一个特殊工具，让它沿依赖路径追踪——比如找到 issue、找到 `config.py` 之后，用这个工具自动跳到其他相关文件。

    * > **结论**：根据经验，这类方法很难做得比简单方法更好。

## SWE-bench 的考卷构造

* **基准的构建方式**

    * > **定义**：**SWE-bench** 从 GitHub issue 构建——取一个 issue，取 issue 被解决时的代码库状态（也就是 pull request 之前的状态），再找出与这个 issue 相关的测试。

    * 这些测试是与这个 issue 一起引入的，所以测的应该就是 issue 里要修复的功能。

    * 让 agent 生成补丁、应用补丁、跑测试：所有相关测试都通过得分就是 1，没全通过就是 0。

    * > **定义**：**harness** 在这里指单纯跑测试的测试 harness，与 agent harness 不是一个意思。

    * 跑完整测试套件代价很高，Django、NumPy 这类项目每评估一个样例跑测试就要 5 到 10 分钟甚至更久，所以挑出了一个更小的测试子集，只要这些通过就认为 issue 被解决。

* **两类测试集合**

| 测试集合 | 含义 | 作用 |
| :--- | :--- | :--- |
| FAIL_TO_PASS | PR 之前失败、PR 之后通过 | 测的正是 PR 里实现的功能 |
| PASS_TO_PASS | PR 之前就通过，之后也必须通过 | 确认没有破坏任何东西、没有引入回归 |

* **可运行基准任务的结构**

    * > **结论**：要构建可运行的基准任务，基本上需要起始状态、依赖、测试命令、issue、检查项这五件套。

```text
  ┌──────────────┐
  │  起始状态    │  那些需要被修改的文件（PR 合并前的代码库状态）
  ├──────────────┤
  │  依赖        │  装得上、跑得起来的环境
  ├──────────────┤
  │  测试命令    │  怎么把测试跑起来
  ├──────────────┤
  │  issue       │  要求实现的行为
  ├──────────────┤
  │  检查项      │  那些测试
  └──────────────┘
```

## 把考卷变成训练集

* **评估是训练的最关键的一环**

    * > **结论**：评估是做 agent 最大的难题之一，也是最大的机会——只要能做好并批量生成大量这样的输出，就能用它们做强化学习把 agent 训练好。

* **SWE-gym**

    * SWE-bench 只是一个评估数据集，或者说只给评估数据集配好了环境；**SWE-gym** 额外搭建了训练环境并在其上做了模型训练。

    * 结果表明：一个原本很弱、准确率只有约 11% 的模型，哪怕只用 500 个样例，也能提升到相当不错的水平。

    * 还证明了如果生成大量输出再重新排序，就能做推理时扩展，效果更好。

* **SWE-rebench**

    * > **定义**：**SWE-rebench** 持续不断地创建更多 SWE-bench 环境，用 PR 创建，时间范围是 2024 年 12 月到 2026 年 6 月 30 日，并分成训练集和开发集。

    * 它大约每 10 个月更新一次，是 SWE-bench 格式下大规模公开可用的 coding agent 数据里最好的例子。

* **不靠 PR 的合成数据**

    * > **定义**：**变异测试（mutation testing）**的做法是如果你不确定自己的测试好不好，就对本意让它出错的小改动施加到代码上，再看测试过不过；如果测试还是通过，说明这些测试没覆盖到真正的破坏，应该扩充测试套件。

    * **SWE-Smith** 不依赖 pull request，而是靠人为注入的 bug：先准备一个能跑通的基线，然后改动代码但保留测试。

    * 它与变异测试的差别在于：它是改动仓库里的代码，然后去找之后会失败的测试；本质上能造出合成的带 bug 数据，只用现有的测试和代码库就能拿来训练模型。

```python
# 改之前
if value is None:
    ...

# 改之后
return ... if not value
```

    * 好处是非常轻量，几乎能生成无限量的数据；坏处是这些不一定是你真正想处理的自然训练样本。

    * 这个框架也能扩展到不同编程语言：Multi-SWE-bench 与 SWE-bench Multilingual 都扩展到了多种语言，唯一的实际困难是各语言的约定不同。

* **多 harness 训练**

    * 语言模型预期的编辑格式和 harness 预期的差别很大时，大多数语言模型在没训练过的 harness 上表现会更差。

    * > **提示**：厂商因此普遍在多个 harness 上同时训练；NVIDIA Nemotron 刻意在五个以上 harness 上做了训练，让模型能适配很多不同的 harness。

## 内循环与外循环

* **两个循环的划分**

    * > **定义**：内循环是修 bug、跑测试这类迭代过程；外循环是除此以外的一切。

| 循环 | 覆盖什么 | 难点 |
| :--- | :--- | :--- |
| 内循环 | 修 bug、跑测试这类迭代过程 | 已经有比较成熟的工具和基准 |
| 外循环 | 代码审查、部署与监控、维护、做规划、提需求 | 理想情况是 agent 能帮我们搞定所有这些事，但这些事更难定义，也更难找到训练数据 |

* **开发者时间的实际分布**

    * 微软 2019 年调查自家软件开发者「有多少时间花在写代码上」，结果如下。

| 时间花在哪儿 | 占比 |
| :--- | :--- |
| 写代码（issue 开发、新功能开发、issue 修复） | 15% |
| 开会和邮件 | 25% |
| 调试 | 14% |
| 跑测试 | 8% |
| 其余各项 | 未给出具体数字 |

* **前端开发与多模态**

    * > **定义**：**SWE-bench Multimodal** 是专注修复前端 bug 的前端开发基准，它并不是专注开发新前端，更多还是 issue 修复那一类。

    * 做多模态模型有两个不同之处：输入端需要训练过能读图像、接收并理解输入的语言模型；验证端可以在浏览器里写能跑的测试，也可以直接看输出。

    * 两种常见做法：把基于 GUI 的 agent 当作 coding agent 的一个组件，或让一个 agent 同时能处理 GUI 任务和编码任务；另一种做法是写一个脚本来测试 GUI，比如用 Playwright 这类基于 GUI 的测试库。

    * 示例：问题是「输入长度为 0 也能提交」，可以用视觉方式验证这种情况确实发生，也可以写一个 Playwright 脚本，确保输入 0 之后会出现要求填写非空名字的提示。

    * > **注意**：非多模态的 GLM-4 在 frontend design arena 夺冠，这动摇了「做好前端开发 coding agent 需要什么」的假设。

### 定位、从零创建与测试生成类任务

* **定位专项训练**

    * > **定义**：**CodeScout** 是专门针对定位训练的 RL 方法，让模型特别擅长判断一个编码任务该从哪里入手；它类似 coding agent 但更可控，用小模型也更容易做。

* **从零开始创建应用**

    * > **定义**：**VibeBench** 专门评估 agent 做 vibe coding 的整体水平；做这个基准非常难，因为得能正确评估它们，所以需要设计出好的验证器。

* **完整实现后端库**

    * **Commit0** 是较早的基准，**ProgramBench** 是新近流行的；ProgramBench 本质上要求逆向工程一个二进制文件再从零重新实现，可以运行这个二进制文件、根据输入输出去探测，然后写出新的实现。

    * > **结论**：ProgramBench 的周期非常长，而短周期任务越来越容易，长周期因此成为新的挑战之一。

* **里程碑式开发**

    * > **定义**：**SWE-milestone** 的基本思路是实现一个阶段里的很多 issue，并确保逐个实现时不会把代码库搞得一团糟、变得难以维护；这是一些 coding agent 的大问题。

* **生成验证用的测试**

    * > **结论**：现在最大的问题之一是生成能验证 issue 已修好的测试；能写出真正好的测试来验证 issue 已解决，等于成功了一半——任务一旦明确，agent 就特别擅长反复迭代把它做好。

    * **SWT-bench** 就是一个这样的基准，它基于变异测试。

* **运维类任务与自动造基准的框架**

    * 部署这类更偏运维的任务目前还没有真正好的基准，也比较难做，因为需要真实的基础设施来运行；可参考 JetBrains 做的例子。

    * SWE-playground 与 HyperGym 基本是自动创建基准，覆盖的不只是写代码，还有软件工程里的其他环节。
