# 操作电脑的智能体：定义、基准、表示与训练

## 计算机使用 agent 的定义与运行回路

* **计算机使用 agent（computer use agent，CUA）**

    * > **定义**：通过与人完全相同的图形界面来操作设备、以截屏为主要输入、以点击/滚动/输入等人类动作作为输出的 agent。

    * 广义上包含网页浏览 agent、操作桌面电脑的 agent，以及操作手机这类移动设备的东西。

    * 它和人待在完全相同的空间里，这一条让建模和评估同时冒出很多问题：建模上面对的是像素而不是符号，评估上很难找到现成的标准答案来对答案。

* **观测—推理—行动循环**

    * 观测 $o_t$ 通常就是一张截屏，代表环境当前显示的内容；也可以是别的基于文本的表示，但目前大多数前沿 CUA 都用截屏，因为它基本就是用户自己做这个任务时会看到的东西。

    * 策略通常先产生一段推理轨迹（思维链），再产生它想执行的下一个动作 $a_t$：click(x, y)、scroll、type 等环境允许的任何动作。

    * 动作被丢进环境的基础设施里真的执行——如果是点击，就真的在屏幕上点一下——执行完得到新的截图 $o_{t+1}$，然后循环往复。

    * > **提示**：整个循环的终止条件有三种：模型自己认为做完了、环境或裁判给了成功奖励、或者预算（调用次数、时间、token）用完。任务越复杂，这个循环迭代的次数就越多。

    * 结束时一般会拿到某种奖励，来源是环境、人类用户或某个裁判；绝大多数情况下是 0 或 1 的二值奖励，某些场景下也可以给部分奖励。

```text
  任务 T（自然语言，例如"帮我买一个 20 美元以下的蓝色马克杯"）
      |
      v
  [ 观测 o_t = 截图 S_t，环境当前显示的内容 ]
      |
      v
  [ 策略 = 一个 LLM ]
      |  先产生一段推理轨迹（思维链）
      v
  [ 动作 a_t：click(x, y) / scroll / type ... ]
      |
      v
  在环境的基础设施里真的执行（浏览器 / 桌面 / 手机）
      |
      v
  [ 新观测 o_{t+1} = 执行之后的新截图 ]
      |
      └──▶ 把 a_t 和 S_{t+1} 一起拼进上下文，回到第一步
```

* **一个完整走通的例子**

    * 初始观测来自浏览器，模型说屏幕中央有个蓝色马克杯，于是生成一个格式化的待执行动作，对环境做一次左键点击。

    * 真的在环境里点下去，拿到新截图，能看到马克杯的详情页；模型接收新观测，说配送信息在下面，于是生成滚动动作，再执行、再拿新观测。

    * 重复直到模型认为任务完成。

## 基准演进时间线

```text
  2017         World of Bits     OpenAI，极简玩具环境，基本全是合成数据
  2022         WebShop           模拟的购物网站，模拟点亚马逊，比玩具真实得多
  2022 - 2024  WebArena          CMU，模拟环境 + 从真实网站抓来的真实数据
  2024         OSWorld           真实 Linux 虚拟机，369 个任务 / 9 个应用
  2025 - 2026  全生成环境        用编程 agent 端到端生成整个应用和网站
  2025 - 2026  GUIWorld          CMU，长尾专业软件 + 真实数据
  2026         GPT-4o-extra      大多数计算机使用基准上已超过人类基线
```

* **玩具环境阶段**

    * 第一篇 CUA 论文是 2017 年 OpenAI 的 World of Bits，搭了一个极其简化的玩具环境，界面看着有点像手机上的页面，但简化得完全不像真的，基本全是合成数据。

    * 当时的模型连这种玩具都做得很差，这个项目是超前于时代的。

    * 2022 年语言模型兴起后出现的 WebShop 也做了简化的购物环境，但比 World of Bits 真实得多——你就是在模拟的亚马逊网站上点击，完全是两个量级；这个阶段语言模型 agent 开始起色，而且当时并没有专门训练它们。

* **真实数据进入模拟环境**

    * 2022 到 2024 年 CMU 的 WebArena 建了很多模拟环境，比 WebShop 和 World of Bits 都更真实，数据通常是从亚马逊、Reddit 等真实站点抓来的，数据和环境都是真的。

    * 2024 年前后的 OSWorld 同样用真实应用和真实数据，但针对的是桌面操作而不是网页浏览，支持 Linux、Windows 等系统，是如今最标准的计算机使用基准之一。

    * WebArena 是网页浏览，OSWorld 是完整的桌面操作，这是两回事。

* **环境被端到端生成**

    * 2025 到 2026 年编程 agent 变强，很多人开始端到端地生成环境：WebArena 和 OSWorld 是拿应用的开源实现再往里填真实数据，软件都是人写好并开源的；而 Mind2Web-Bench 及这前后的一些基准是直接用编程 agent 端到端生成整个应用和整个网站。

    * 展示的 Gmail 克隆外观和真的非常接近，整个东西完全由一个 LLM 编程 agent 生成，里面预置的数据也全是合成的。

    * > **注意**：生成的环境效果有时候比真实应用还好，因为生成的环境更干净、噪声更少。

    * GUIWorld 同样是 CMU 的项目，用真实软件，但更偏长尾，比如天文学、生物学这类领域才会用的软件；数据是真实使用场景下载下来再加载进环境的。

* **能力现状**

    * GPT-4o-extra 基本解决了大多数计算机使用基准，目前已经超过人类基线，演示的是操作 CAD 软件做 3D 建模。

    * > **注意**：这类演示画面是加速了 30 倍的，实际比看到的要慢 30 倍；它比之前的模型快了不少，但仍然很慢、很贵。

## 评估的困难

* 基准测试是衡量这类 agent 进步速度的核心手段之一。

* 计算机使用比课上讲过的其他 agent 都更难验证：在软件工程或数学里有单元测试、有符号验证器，能明确告诉你任务是否成功完成；计算机使用不一样，一个任务算不算成功完成，就连人自己通常都意见不一。

* 因此写程序化验证器非常有挑战，整个评估拆成四个大类：静态评估、端到端评估（网页）、端到端评估（桌面／移动）、以及长时程评估，它们的共同点是都在回答 agent 到底做成没有。

## 静态评估

* **静态评估**

    * > **定义**：衡量 agent 轨迹上每一步动作是否正确，不让 agent 端到端地跑起来。

    * 判定方式：要求 agent 预测的 $(x, y)$ 坐标落在目标框内，落在框内得一分，落在外面得零分，意思是它这一步没有执行正确的下一个动作。

    * 之所以叫静态，是因为根本没有环境，它就是一组静态截屏加一组标准答案动作。

* **Screenspot-Pro**

    * 静态领域一个经典的 grounding 基准，测的就是截屏上的动作定位，涵盖各种应用和操作系统，大约有 1500 个不同的截屏样例。

    * 指标是逐点准确率。

    * agent 没有任何可交互的环境，只拿到一张图；例如"构建 UV 球面网格"任务给的是一张 Blender 截屏，目标是判断模型产出的动作是否落在红色边界框里，落在框内就算对，否则不给任何奖励。

* **Mind2Web**

    * 测更多样的动作，可以理解成下一步动作的模仿学习：给定当前截屏和任务，比如"在布鲁克林中心租一辆车"，预测 agent 的下一步动作，标准答案可能是点"租车"标签页。

    * 这个任务里不会真的执行任何动作，你拿到的是一系列截屏，agent 根据截屏预测下一步动作，预测出来之后给它打分，然后从离线数据集里给它下一张截屏。

* > **易错点**：静态评估最大的问题是假阴性。同一张截屏、同一个任务其实有很多不同动作都可以算对——不一定要点"租车"标签页，先去调日期同样是有效动作——但在静态评估里因为标准答案是固定的，这些动作全会被判成错误。它很快，但没有测到你真正关心的东西，也就是真正的端到端表现。

| 对比维度 | 静态评估 | 端到端评估 |
| --- | --- | --- |
| 看什么 | 每一步的动作对不对 | 最后有没有真的做成 |
| 谁来判定 | 固定的标准答案，答案集合封闭 | 程序化验证器或裁判自己定义"做成" |
| 典型误差 | 大量假阴性 | 假阳性，也就是 reward hacking |
| 成本 | 极快、极便宜，不用搭环境 | 要搭环境或部署，昂贵得多 |
| 测到了什么 | 测不到你真正关心的东西 | 测的就是你真正关心的东西 |

## 模拟环境中的程序化验证

* **程序化验证器**

    * 让 agent 在环境里或真实网页上真的执行任务，轨迹结束时运行一批单元测试式的检查。

    * 以"把一个 20 美元以下的蓝色马克杯加入购物车，但不要购买"为例，检查项是：马克杯是否在购物车里、价格是否低于 20 美元、agent 是否没有真的下单（检查订单数是不是 0）。

    * 所有单元测试都通过才给 1 分奖励；不检查每一步执行了什么，只检查最后有没有靠这些测试真的完成任务。

    * 只要单元测试足够全面，这就是非常好的奖励信号——不用监督每一个动作，只在最后看它做没做对。

* **WebArena**

    * 最早这么做的基准之一，是模拟网页导航基准，搭载 4 个不同的应用，大约 800 个任务。

    * 目标之一是"建一个叫 awesome-llm-reading 的空仓库"，agent 会进入本地搭建的模拟 GitLab 去做；在 WebArena 里 agent 任何时刻都不会访问真实网页。

    * 验证器全是手写的，是 CMU 的研究生为 WebArena 里的每个任务手写了一个，任务结束时运行程序化验证器检查它有没有成功创建这个仓库。

    * > **注意**：验证器不够全面，还是会有假阴性和假阳性；它测的是真正的端到端表现，只看结果、不关心具体步骤，确实让业界开始更认真地对待计算机使用 agent 的评测。

* > **易错点**：程序化验证会带来 reward hacking（奖励作弊）——agent 可能想办法骗过验证器，而不是真的去做那件事；见过 agent 靠往购物车里塞一大堆东西来 reward hacking，以此完成目标。

* **VisualWebArena**

    * WebArena 的扩展，它把这个问题当作多模态问题来处理，想让大家相信该用截屏方式操作。

    * WebArena 发布时，大多数模型处理 CUA 或网页浏览任务用的是 accessibility tree（无障碍树），算是 HTML 的简化版。

    * VisualWebArena 包含 910 个视觉定位任务，里面的问题都得用多模态表示才能解决；评测方式类似，同样有程序化检查，但额外加了一些多模态程序化检查，有些问题只靠 HTML 是解不出来的。

## 裁判型评估

* **LLM 裁判**

    * 做法是拿到模型的轨迹之后，prompt 另一个 VLM 或 LLM（文本或多模态视觉语言模型），把 agent 的轨迹喂给它，问它任务有没有成功完成。

    * 这方法之所以常用，是因为你不可能给每一个关心的任务都写验证器；替代方案是给一组 rubric 评分细则，或者干脆直接交给 LLM 自由裁量。

    * 裁判通常先输出一小段思维链，再给出通过或不通过；有时也打一个浮点分数，但一般就是告诉你通过还是不通过。

    * 更通用，因为不用给基准里的每个任务都写验证器。

    * > **易错点**：它也更容易误判，LLM 裁判很容易被糊弄，以为任务完成了其实并没有。

* **WebVoyager**

    * 最早测试 agent 在真实网页上导航能力的基准之一。

    * 团队选了 15 个不同的网站，在上面设计了 600 个任务，要求 agent 真的上这些网站去完成目标；你可以实际去看这些网站，比如 Allrecipes 食谱网站，能看到之前 agent 试过的痕迹留在上面。

    * 因为在真实网页上没法用程序化验证器——你没法查询真实网页的状态——所以用 VLM 裁判：另一个 LLM 拿到 agent 执行的一系列动作和观察到的截图，也拿到原始任务，然后判断有没有成功。

    * 例如"找出 star 数最多的气候变化数据可视化 GitHub 项目"，让 agent 真的去 GitHub 上做一堆搜索，找出 star 数确实最多的仓库。

    * > **易错点**：把东西部署到真实网页上跑基准会打扰网站运营，这正好说明了为什么可能不想在真实网页上评测 agent。

    * 它仍然很有价值，因为它测试了 agent 在非模拟环境下的能力，这基本上是最接近真实世界的评测方式。

* **Online-Mind2Web**

    * 继 WebVoyager 之后的另一个 eval，更全面一些，裁判也更强。

    * 证明了裁判和人类的一致率大约是 85%，这已经非常接近人类水平的裁判一致性。

    * 同样扩展到了真实网站：大约 136 个网站、300 个任务，裁判更复杂，带不同的 rubric 评分细则和标准。

    * 整套流程全自动化：一个 LLM 在真实世界执行任务，另一个 LLM 评判。

    * > **注意**：现在人们已经不太用它了，因为它基本上已经被现代模型解决了；而且随着 CUA 越来越流行，大家把它们部署到真实世界时也更谨慎了——网站被收进基准后流量突然暴增，网站主人大概也不会高兴。

## 桌面端到端评估

* **OSWorld**

    * 最经典的 CUA 基准之一，是一个可以启动的真实 Linux 虚拟机，包含大约 369 个任务，分布在 9 个不同的应用上——GIMP、LibreOffice、Chrome 等等。

    * 每个任务都有程序化验证器，agent 得进入虚拟机、跨多个应用尝试完成任务，最后跑一些类似单元测试的检查看它有没有成功，打 0 或 1 分。

    * 任务示例是更新一张 LibreOffice Calc 表格，用的是另一个文件夹里的收据：agent 得先导航到那个文件夹，找到收据，把对应的数值填进工作簿里，还要保存工作簿；它得在不同应用之间来回操作，只凭一句初始用户指令完成整个任务。

    * 精神上和 WebArena 很像，但这里用的是真实应用，都是人们日常真正用的软件，同样运行在完整的虚拟机里，覆盖面广得多。

    * 可以想见，桌面 agent 能自动化的任务种类会比纯网页浏览 agent 多得多。

* **Windows Agent Arena**

    * 另一个基准，灵感来自 OSWorld，是微软创建的，用来测 agent 在 Windows 机器上的表现，毕竟世界上很多实际工作就是在 Windows 机器上完成的。

    * 任务都是企业工作流或各类公司里非常常见的那些；同样是启动一台 Windows 虚拟机让 agent 去做任务，最后用验证器判断对不对。

    * 因为用的是程序化验证器，也同样容易出现假阳性或假阴性——和 LLM 裁判一样，各有优缺点。

* **人工审查**

    * 程序化验证器和 LLM 裁判本质上都只是 proxy 指标，用来代理判断有没有成功完成任务。

    * 人工审查让人类来判断 agent 做得怎么样，可能仍然是黄金标准：这些论文大多也做了人工评估基线，让人审查 agent 的轨迹，每条轨迹找几个人判断是否成功，最后再让几个人投票看 agent 到底成没成功。

    * 问题是这非常贵，不可能对基准里的每个任务、每次运行都这么做；所以大多数基准的创建者还是在开头做一两次，找人实际去尝试或评判任务，确认 agent 和基准本身是合理的。

| 判定方式 | 怎么判 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 程序化验证器 | 手写单元测试式检查环境状态 | 客观、快、可复现 | 写不全就有假阴性和假阳性；容易被 reward hacking |
| LLM 裁判 | 另一个 VLM/LLM 读轨迹 + rubric 给出通过或不通过 | 灵活，不用为每个任务写验证器 | 更容易被糊弄，误判率明显更高 |
| 人工审查 | 几个人分别判，再投票 | 至今仍是黄金标准 | 极贵，只适合在开头做一两次 |

## 长时程基准

* **动机与时间跨度**

    * 已有的基准大多被现代模型解决得相当好了，社区的注意力转向更长时程、更专门的基准。

    * 对照差别：OSWorld、WebArena 里很多任务人类大约 10 到 20 分钟甚至更短就能完成，而长时程任务可能要花好几个小时，还要操作专门的软件——有些任务真人要花两三个小时。

    * > **结论**：我们正朝着让 agent 超过人类专家用电脑的水平迈进。

* **为什么需要细粒度奖励**

    * 不能只用最终结果奖励，因为信号太稀疏：长时程任务里 agent 中间可能做了很多有用的工作，最后却因为某一个环节没做到而拿不到满分。

    * 状态检查／阶段性奖励检查 agent 是否完成了某个中间任务，类似基于 rubric 的奖励；过程奖励检查是否端到端完成了整个任务，相当于最终奖励。

    * 两者都需要，中间奖励用来保证长时程任务里有非零信号。

    * > **注意**：最终交付物好，并不总是长时程计算机使用的好指标；因为任务太长了，必须靠一些阶段性奖励来确保模型一直在做有产出的事情。

* **Odyssey**

    * CMU 做的基准，衡量长时程网页浏览，包含 200 个任务，每个任务都有一组 rubric 评分细则，也就是我们认为模型应该完成的一组事项。

    * 例如"规划一趟去棕榈泉参加婚礼的行程"，模型要满足 8 条 rubric 才能拿满分：得找到一条从匹兹堡到洛杉矶的直飞航班，还得找到上午 9 点到下午 4 点之间的车程，还有一堆类似条件都要满足。

    * > **结论**：它按多条 rubric 打分，这样就能拿到部分奖励，而不是最后只有一个二元的通过或失败；大部分验证仍然是 LLM 做的，但这是细粒度的 LLM 验证。

* **OSWorld 2**

    * OSWorld 的续作，挑战长达一小时的工作流；OSWorld 1.0 的任务大多只需要人类几分钟，而 OSWorld 2 有大约 108 个任务，人类完成的中位时间是 1.6 小时。

    * 工作流非常复杂，需要做 CAD 建模、3D 建模或者修图，所以进入了更专门的软件使用领域。

    * 平均来看，被测试的大多数前沿 agent 大约需要 300 次调用，光跑一次基准测试通常就要几个小时。

    * 示例任务是"制作一个猫形支撑支架，并导出符合这张图纸的模型"：左边给参考图纸，agent 的目标是操作某种 CAD 软件做出右边这个东西；难点很具体——需要在 3D 空间里导航，需要知道这个环境里有哪些工具可用，而且要能持续工作好几个小时。

    * > **提示**：评估很贵，但很神奇的是，你启动一个 eval，一小时后回来，发现 agent 还在高效推进任务——这就是这些模型能连续好几个小时保持高效工作的证据。

* **CoWorld-Long**

    * CMU 的另一个基准，专攻长程计算机使用，环境非常专业化，涵盖医疗类、工程类，还有建筑和设计类任务。

    * 包含 200 个这样的任务，大多需要 500 次甚至更多次 LLM 调用，相当于人类几小时的工作量。

    * 今年年初发布时大多数模型的成绩都很差，但包括 GPT-4o 在内的近期模型已经能拿到接近 90% 的成绩。

    * > **结论**：长程计算机使用、乃至整个计算机使用领域，已经接近被解决了——有人甚至说已经解决了，因为这些模型在很多这类任务上已经超过人类。

## 基准设计的关键问题

### 细粒度扣分

* 问的是：任务"往购物车里加一个高评分商品"确实做到了，但过程中出了别的问题、加了不相干的商品，会不会被扣分。

* 奖励设计在很多基准里都很棘手；WebArena 里有些任务确实有这种扣分机制，但很多时候人们设计这些基准时会让答案尽量没有歧义。

    * 例如 WebArena 可能会说"把评分最高的商品加进购物车，做到了就能拿满分"，这种问题某种程度上有点人工。

* 一般来说人们通常不会去做这么细粒度的扣分，不过这也是因为这些基准刚被做出来的时候 agent 还很弱，所以有些奖励标准一开始就定得比较宽容。

* > **结论**：有些基准确实有这类机制，但并不特别普遍；大家宁可误判为通过，也不愿误判为失败。

### rubric 的来源

* rubric 本身每个任务都不同，Odyssey 里多为 LLM 生成、人工核验。

* 生成 rubric 的一个常见做法和另一个问题有关：你给模型特权信息，也就是比评测时更多的信息，比如一些提示或者 HTML 表示，让它的表现比真实评测场景下更好；有了特权信息，就能据此生成更准确的 rubric。

* 不管是 Odyssey 还是很多业界 benchmark，如今 rubric 通常都是 LLM 生成加人工核验；有时甚至不是人工核验，而是由另一个掌握不同信息的 LLM 来核验。

* > **提示**：放进 benchmark 的每样东西总得有人看过一眼，确认它靠谱。

* > **结论**：rubric 奖励比结果奖励更防 reward hacking，因为你得同时满足好几个不同的标准——比如你只想买评分最高的商品，那模型可以作弊把网站上所有东西都加进购物车，基于 rubric 的奖励就会检查这一点。

### 在 benchmark 上训练

* 按理说你不该在 benchmark 上训练，因为那等于拿训练集去测试。

* 业界很常见的做法是生成和 benchmark 非常类似的任务——大家常造出类似 OSWorld 或 WebArena 的任务，拿这些来训练，这样分布相近，但没在同一个测试集上训练。

* GUI-World 其实是明确有训练集的，有些 benchmark 会提供训练集、验证集，理想情况下还有测试集供大家训练用。

* 你不应该在真正的评测集上训练，不过遗憾的是，大家确实会找 proxy 信号来变相这么做。

## 表示与建模

### 多模态交错序列

* **输入**

    * 目标，用自然语言表示，比如"帮我买一个 20 美元以下的蓝色马克杯"。

    * 一张初始截屏，取决于环境最初的状态。

* **策略**

    * CUA 和如今大多数 AI 模型一样，基本上就是一个 LLM——准确说通常是视觉语言模型，因为大多数模型以截屏作为输入。

    * LLM 通常以文本形式产出动作，它用文本来生成自己想执行的动作的结构化表示，比如一个带 $(x, y)$ 坐标的点击动作；接着把动作加进下一步喂给 LLM 的上下文里。

* **ReAct 循环**（reasoning 加 acting）

    * 每一步都把产出的动作连同新截屏一起拼进不断增长的上下文，再喂回 LLM。

    * 执行完动作 $a_t$ 会在截图 $S_t$ 上得到截图 $S_{t+1}$，然后把它拼进已有上下文，再喂给 LLM 产出下一个动作。

    * 于是手上是一份视觉与语言交错的动作历史：有自然语言形式的目标和动作，也有像素输入，可能还有其他元数据。

    * 不是直接喂原始像素，模型会先做 tokenize：自然语言切分成文本 token，截屏转换成视觉 token，现代语言模型通常直接拼接起来就行。

    * > **结论**：这是一种非常简洁优雅的表示方式，而且效果出奇地好；文本转成 token embedding，截屏转成视觉 embedding，交错拼接后传给 Transformer 生成下一轮动作，显然很自然。

```text
  喂给 LLM 的那条多模态序列（每一步都在变长）：

  任务 T(文本) → 截图 S0(视觉) → 动作 a0(文本) → 截图 S1(视觉) → ... → 截图 St(视觉)

  文本切成 text token，截屏切成 visual token（或某种基于像素的表示），
  两者交错拼成一条很长的序列，喂给语言模型 → 以此为条件生成下一个动作
```

### 动作空间

* 动作空间因模型而异，也取决于你想把模型部署到什么环境里；粗略看它们大体相似，一般都有"一组可以输出的动作"，比如点击、滚动，或者你环境里有的其他动作。

* 不同模型输出动作的格式略有差异：可能输出成 PyAutoGUI 的指令，也可能输出成工具调用或 XML，然后你需要解析它，传给能在环境里实际执行的东西。

### 为什么是截屏而不是 HTML

* HTML 也是可行的，不过 HTML 很乱，也有人用简化版的 HTML 来做表示；最近的模型大多不用 HTML，而是主要依赖截屏，有时还是会用一些元数据。

* 原因很朴素：截屏简单得多，给电脑截个图比处理底层的 accessibility 元数据要容易得多。网页上拿 HTML 很容易，但桌面操作就没那么容易了——你得面对各种不同的原生桌面软件。

* 让一些人意外的是，基于截屏的表示已经取得了非常好的成绩，HTML 或其他结构化表示几乎显得没必要了。

* > **注意**：OpenAI 说过，至少之前的模型（包括 GPT-4o）在可用时确实会用计算机的 accessibility 表示；macOS 上的 accessibility 表示是为视障用户设计的，有点像 XML，告诉你哪个区域是什么，比如这块是 Chrome 窗口、这块是 Dock 栏。

* 纯截屏的表示方式非常简洁、非常通用：训练一个直接吃截屏的模型就能部署到任何设备上，不需要访问设备底层的内部信息。

* 因为不同系统的底层 accessibility 表示各不相同，所以在 Windows 上训练的模型更容易泛化到 Linux 或 Mac 上。

* 建一个数据库把图标的位置之类记下来让模型直接查，也是一种合理的做法。

* 现在的模型并不是被训练成单一用途的 CUA：GPT-4o、Claude 并不总是只执行计算机操作，它们会穿插调用 Bash、写代码，模型通常会用最高效的方式来解决问题。

### 动作执行后的等待

* 执行完一个动作之后到底是马上截一张还在加载的截屏，还是等一会儿再截，这是个必须处理的边界问题；跟数学或编程模型比，计算机使用会遇到很多边界情况和基础设施问题。

* > **易错点**：最常见也最简单的做法是执行完动作先睡几秒——通常是三秒左右——再截屏执行下一步；如果那时候确实看到一个加载页面，模型一般会被训练成再等一段指定的时间。

* 也有更复杂的做法，比如设计模型一直等到截屏不再变化为止，但最简单也最常见的办法就是睡一会儿。

## CUA 的训练

大多数计算机使用 agent 都基于预训练的视觉语言模型，训练分几个不同阶段。要提醒的是，把 GPT-4o 部署成计算机使用 agent 时，你部署的不是"只会计算机使用的 GPT-4o 专用版"，它是一个通用模型，计算机使用只是它的能力之一，而且大家越来越倾向于这么做。

```text
  大规模互联网数据（含噪、合成为主）
                  |
                  v
  [ 预训练 ]      学 grounding：截图 -> 边界框 / (x, y)
                  学动作预测：HTML 元素 -> (x, y)
                  |
                  v
  [ SFT ]         行为克隆：模仿"看到截图 -> 下一个动作"
                  人类演示 + 用特权信息合成的轨迹
                  |
                  v
  [ RL ]          把模型丢进模拟环境自己跑：
                  成功轨迹里的动作加权，失败轨迹减权
                  成功率大约 0.5 -> 0.6 甚至更高
                  |
                  v
  [ CUA ]         强大的计算机使用 agent
```

### 预训练

* **grounding 数据**

    * 一张截屏加上一串边界框和对应的坐标，引导模型去学习在截屏中定位信息。

    * 给定截屏，模型通常被训练去预测一长串描述的下一个 token，本质上就是在预测页面上各元素的位置、这个标签卡在哪里——预测 $(x, y)$ 坐标，或者边界框的宽和高。

    * > **注意**：这类数据非常容易大规模收集：截屏来自具体网站，边界框和 grounding 跑个 JavaScript 脚本就能提取；这是非常嘈杂的数据，而预训练正需要这种量大但含噪的数据。

* **动作预测数据**

    * 同样从 HTML 页面里拿元素名称或元素元数据，把页面上某些东西喂给模型，让它预测对应的 $(x, y)$ 坐标，即给它一个 HTML 元素，让它预测想做什么、想点哪里。

* **关系与坐标归一化**

    * 这些数据教 CUA 理解截屏、定位页面上的各种元素，还能学到元素之间的关系，比如"租车按钮在酒店按钮右边"，这类关系可能会以某种方式进入预训练数据。

    * 这类数据通常大规模生成，混入前沿模型预训练的早期阶段，让模型之后学 grounding 和动作生成更轻松。

    * > **提示**：坐标表示的泛化靠归一化——坐标不用绝对格式表示，而是用 0 到 1000 这样的范围，0 表示屏幕左上角，1000 表示屏幕右下角；坐标是完全归一化的，即使绝对分辨率不同，迁移效果也相当好。

### 监督微调

* 预训练之后通常进入后训练阶段，这一步现在通常和其他模型能力混在一起训练；后训练的第一个步骤通常是做 SFT（监督微调），让模型模仿人类演示计算机使用任务的过程。

* **人类演示数据**

    * 做法是付钱请一批人来标注轨迹：给个任务，比如"找一份 3 小时能做完的墨西哥炖肉塔可食谱"，然后由真人通过浏览器实际去完成。

    * 来自 Mind2Web 的例子收集了大约 36,000 条人类轨迹，每一步都记录截屏观察和人类的动作，最终得到一堆"截屏、动作、截屏、动作"的轨迹。

    * 开源的 CUA 数据集里，Mind2Web 和 AgentNet 这两篇论文本质上都是收集人类演示，让模型以截屏为条件预测序列中的下一个动作。

* **合成数据**

    * 一个很典型的方法来自 Mind2Web：把网站的 accessibility tree（无障碍树）喂给模型，给模型元数据，它们的表现会好很多。

    * 他们先训练出一个用 accessibility tree 的模型，然后把简化的 HTML 表示给它，让它在 accessibility tree 的空间里 rollout 动作，并收集同样的一批轨迹。

    * 这个 rollout 模型收集了大约 10.5 万条合成轨迹；不是所有轨迹都会保留，可以按某种指标只留下质量较高的，比如用另一个 LLM 评判或用人工筛选。

* > **结论**：轨迹的收集无非两条路，要么靠人类演示，要么靠合成数据。

* **特权信息类比**

    * 这种"用特权信息做合成数据"的方式有一个类比：听说 Tesla 在训练阶段部署了装有 LiDAR 的车，有三维 LiDAR 信息时表现会好很多，他们收集这些轨迹，然后丢掉 LiDAR 信息，只训练模型使用像素信息。

    * 相当于有一个老师，用的信息比推理时能拿到的要好得多；很多计算机使用 agent 的应用里，大家也试过注入元数据或额外信息来收集更好的轨迹。

### 强化学习

* RL 是后训练中的最后一个阶段，这一年前还不常见，但现在 CUA 普遍都会经历。

* 具体做法是把 CUA 放进模拟环境或真实世界里，给它一件事做，比如试着去买那个蓝色马克杯；奖励可能来自 rubric 评分细则、来自验证器，或者让一个 LLM 当裁判，然后做强化学习去强化那些成功的轨迹。

* 更新规则是：奖励为正就把那条轨迹里的动作权重调高一些，奖励为零或负就调低这些动作的权重，模型本质上是在学习最大化环境中的奖励。

* > **结论**：这些任务没有人类演示，你就是把模型放进沙盒里放开跑，它尝试各种做法，从成功和失败中学习；模型尝试的任务可能来自人类，但它的运行方式通常是完全自主的。

* > **易错点**：这也解释了你为什么会需要模拟环境。很多任务我们并不想在真实世界里反复执行，比如你在 Uber 上订机场接送，订几次就会被封号，或者钱就花光了。

* 效果上，SFT 之后成功率大约是 0.5，做了强化学习之后最终能爬升到 0.6 左右甚至更高，这是 CUA 训练中很关键的一环。

* RL 还能带来单靠人类演示很难学到的能力：用强化学习训练模型处理长时程任务会容易得多，因为通常没有超长任务的人类演示，收集起来成本太高。

## 与其他 agent 的差异

* **界面**

    * CUA 和课上其他 agent 最大的不同，是它直接在和人类相同的界面上操作；这一点既让它格外有用，也让它格外难评。

* **建模**

    * 是一种跨模态的设计，从交错的视觉历史中预测动作：上下文里交错着截屏和你之前执行过的动作，模型要基于这些生成下一个动作。

* **训练**

    * 分成多阶段：先用大规模含噪数据做预训练，然后用 SFT 对人类或合成演示做行为克隆，最后是 RL 阶段，让模型在模拟环境里自行探索，好的行为给奖励、坏的行为给惩罚。

* **可改进方向**

    * 速度仍然是个问题；个性化是很有潜力的研究方向；基础设施和用户体验也是大问题；多 agent 系统同样值得期待。
