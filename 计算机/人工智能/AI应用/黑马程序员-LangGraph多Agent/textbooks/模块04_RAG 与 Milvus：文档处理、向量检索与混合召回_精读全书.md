## 从一本正经地胡说八道，到会查库的保险顾问
> 对应块：BLK27 | 覆盖分集：P103-P105 | 块标题（分集名）：《Agent 工具扩展与 RAG 基本原理》

现在这个客服已经能实现基本的聊天功能了。我跟他打个招呼，他也能回一句：你好，我是保险顾问，请问你想了解哪方面的保险问题呢？是想给自己或家人配置保险，还是……

但我接着往下问——让他给我推荐保险，他知道该怎么推荐吗？

他肯定不知道。因为他现在纯粹是靠模型本身的能力在回答，我问任何问题，他都是拿着训练数据在那儿一本正经地胡说八道。我说给我推荐一些保险，他只能根据自己训练过的数据去猜，他根本不知道我们这个商城里现在有哪些保险产品。

所以这个 agent 现在是有问题的。问题不在"会不会聊天"，在于它手里没有任何一件关于我们业务的真东西。

### 先让它看见库里真实的产品

要让 agent 能给用户做保险推荐，就必须让它能看到数据库里真实的保险产品。做法是给它加一个工具：当用户咨询产品、或者需要产品推荐时，不许在那儿瞎编，而是先去查数据库里的候选产品，再根据查到的结果来回答。

这个逻辑很顺：模型擅长的是理解和表达，不擅长的是"记住你公司昨天刚上架的那款产品"。那就把"记"这件事交给数据库，把"查"这件事交给工具，模型只负责"看了查回来的东西再说话"。

而工具是什么？之前说过，LangChain 里的工具就是一个函数。所以这件事落到代码上非常简单：定义一个函数，这个函数负责查询候选产品，然后把它注册成工具。就这样。

### 接口是现成的，只差一层工具

记不记得第三天最后留的那个作业——查询推荐的候选产品？当时就讲了，有这么一个接口，它接收三个东西：

- `category`：产品分类；
- 保费上限：也就是用户的心理预期价格，不能超过这个数；
- 每个险种最少查几条。

举个例子。假如我提问"请帮我推荐几款寿险"，那"寿险"对应到分类里就是 `life`。如果我说"帮我推荐一些寿险和重疾险"，这里的种类就是 `life` 加上重疾险对应的那个分类。我们产品库里的分类一共四种：

| 用户口中的险种 | `category` 取值 |
| :--- | :--- |
| 寿险 | `life` |
| 重疾险 | `critical_illness` |
| 医疗险 | `medical` |
| 意外险 | `accident` |

所以当用户说"给我推荐一些寿险和医疗险"，将来调这个接口时，`category` 就传寿险和医疗险这两个分类；再告诉他我的心理预期——预算不超过 5000，那这个参数就是 5000，本质上是"最高价不能超过 5000"；最后是每个险种的数量，比如 5，意思是我希望你给我推荐的寿险和医疗险，每一类最少查五条。

查完了以后，把这五条寿险、五条医疗险返回给 AI，AI 就能基于这批真实数据给我们分析，挑出最符合要求的那几款。

这个接口是现成的，而且整条链路都写好了：`product` 的 router 里有一个 `list_candidate`，它调 service 里的 `list_candidates`，service 又调 repository 里的 `find_candidates`；repository 里就是按 `category` 循环，每个险种查几条，查完扔进 `products`，最后返回。也就是说我们不需要重复写查询逻辑，只需要把这个函数变成一件工具，提供给 agent 用。当时没做这个作业的，可以照这个思路补一下。

> **提示**：参数叫"保费上限"，但过滤时是拿每个产品的最低保费去跟它比——只保留最低保费小于该值的候选产品，不是要求产品的所有价格都低于预算。

工具放哪儿？agent 的定义统一放 `agents` 包，业务放 `modules` 包，工具属于 agent 的一部分，理论上直接写在 `insurance_advisor` 里也行：初始化模型、定义工具、创建 agent，一个文件全齐。

但一个复杂的 agent，工具会非常之多——不是一两个，可能是十个八个，甚至二三十个。全写在一个文件里，这个文件只会越滚越大。所以工具的定义通常单独放一个文件，在 `agents` 包里新建一个 `tools.py`，工具都在这儿维护，将来定义模型、创建 agent 的时候引用它就行。

### session 别从 FastAPI 那套里拿

工具的名字跟着笔记走，叫 `query_candidate_products`——`candidate` 就是候选，加上 `products`，一眼能看出是查候选产品。

工具里要调 `ProductService` 的 `list_candidates`。要 service 就得先有 session，session 从哪来？

有同学马上想到：`infra` 的 `database` 里不是有个 `get_session` 吗？——那个东西现在用不了。

`get_session` 是提供给 FastAPI 用的，它是为每一个 FastAPI 请求创建 session 的。你把它放进 `Depends` 里，FastAPI 会主动来调用它，帮你完成依赖注入，生命周期管理、上下文管理它自己会做。可我们这个工具将来是给 FastAPI 用的吗？不是，它是在 agent 里边用的。agent 没有办法使用 FastAPI 的那套生命周期管理，上下文管理它也用不了。

所以在脱离了 FastAPI 的场景下，不能再用 `get_session` 取 session，只能通过 session factory 手动取：从 `app.info.database` 拿到 `async_session_factory`——这是最基础、最原始的那个会话工厂——然后 `async with async_session_factory() as session`，一行代码就拿到了。

> **易错点**：`get_session` 不是"坏了"，是"用错地方了"。它服务于 router 里的依赖注入；在 agent 的工具里用它，你得自己造上下文，反而更麻烦。工具里统一手动开 session，别混着来。

拿到 session，创建 `ProductService` 的对象、把 session 传进去，第一步初始化就完成了；第二步调 `service.list_candidates`，把分类、保费上限、每个分类查几条传进去；第三步就是把结果返回。

```python
from decimal import Decimal

from fastapi.encoders import jsonable_encoder
from langchain_core.tools import tool

from app.info.database import async_session_factory
from app.modules.product.service import ProductService


@tool
async def query_candidate_products(
    category: list[str],
    max_premium: Decimal | None = None,
    limit: int = 5,
) -> str:
    """根据险种和保费条件查询可用于推荐的候选保险产品。

    当用户咨询具体保险产品，或需要保险产品推荐时使用。

    Args:
        category: 产品分类列表，可选值为 medical、critical_illness、life、accident。
        max_premium: 保费上限，可选。只返回最低保费小于该值的产品。
        limit: 每个险种查询的数量。
    """
    async with async_session_factory() as session:
        service = ProductService(session)
        products = await service.list_candidates(category, max_premium, limit)
    return jsonable_encoder(products)
```

### 参数是 AI 聊出来的，不是我写死的

这里有个关键点：我们在定义工具的那一刻，并不知道将来会传什么参数。

产品分类是什么？用户的心理预期是多少？我一个定义工具的人，怎么可能知道。这两样东西是 AI 在跟用户聊天的过程中得知的——AI 问用户"你对什么保险产品感兴趣啊""你的心理预期是多少啊"，用户说"我对寿险和医疗险感兴趣"，`category` 就出来了；用户说"我的心理预期是 5000"，保费上限就出来了。

所以参数从哪来？不是我在这儿瞎编，是让调工具的人给我传。调工具的人是谁？是 AI，是大模型。大模型跟用户聊天，聊的过程中就知道了用户想查什么保险、对什么感兴趣、预算价格是多少，然后把这些值填进工具参数里。

这样一分工，工具的职责就变得很干净：你给我分类和预算，我负责去库里把符合条件的候选产品捞出来；至于分类和预算从哪来，那是模型和用户的事。

第三个参数是"每个种类查多少条"，这个值没那么重要，可以给默认值 5。

> **提示**：`limit` 给默认值不代表 AI 不能改。它第一次查五条，发现没有一款价格符合用户要求，就会再调一次这个工具，把数字调大一点再查。你只要把工具提供给它，到底该传几，它自己会分析。

保费上限是金额，用的是高精度数值类型，不是 `int`；同时它可以是"没有上限"——万一用户是个土豪，说我的心理预期没有上限，那这个值就是 `None`，所以得给它一个 `None` 的默认值。

### 返回值要转成 JSON

第三步是返回。怎么把结果返回给 AI？不用特意做什么——工具的返回值会自动交给 AI。

以前定义工具的时候就是这样。回忆一下 LangChain 快速入门里那个查天气的工具，最后是不是直接 `return` 了一个字符串，类似"current weather in 某个地址 is 晴"？这个值就返回给 AI 了，AI 一看就知道当前天气是什么，就能回答用户。同理，我们在这里只要把查到的产品返回给 AI 就行了。

不过 `products` 是一个列表，里面装的是 `Product` 类的对象。对象直接返回，对 AI 来讲不太好解读。AI 最喜欢什么数据格式？JSON 和 Markdown。所以返回之前，最好把产品处理成 JSON。

怎么转？以前在 router 里是沾了 FastAPI 的光——框架自带了一个转换工具，响应模型一挂，序列化它替你做了。但在工具里没这层东西，得自己动手。

第一种办法，绕两步走：`product` 里有一个 `ProductResponse`，它是产品的 schema，约束前端响应用的，继承了 `BaseSchema`，也就是我们那个 `BaseModel`。`ProductResponse.model_validate(product)` 能把一个普通对象转成当前的 schema 对象——只要两个类的属性长得一样就行。`ProductResponse` 和 `Product` 的字段名一模一样，`id`、`name`、分类名这些全对得上，所以这一步一定成功。

```text
Product 对象
    │  ProductResponse.model_validate(product)
    ▼
ProductResponse（BaseModel 的子类，字段一一对应）
    │  .model_dump_json()
    ▼
JSON 字符串
```

转成 `ProductResponse` 之后，它自带 `model_dump_json()`，再调一下，对象就成了 JSON。也就是说，为了让 `Product` 能变成 JSON，我们绕着转了两圈：先转成 `ProductResponse`，再转成 JSON。写成推导式就是链式编程，一行里连着两次转换，代码会比较长。

第二种办法更省事：用现成的转换工具。FastAPI 里自带一个 JSON 处理工具 `jsonable_encoder`——就是学 AI 伴侣那会儿，把列表转成 JSON 用的那个。导个包，把 `products` 整个扔进去，一次就转完了，连推导式都不用写。

```python
from fastapi.encoders import jsonable_encoder

return jsonable_encoder(products)
```

两种都行，看习惯。既然有现成的、代码又短，就用现成的。

### 文档注释是工具的一部分

定义完函数体，还有一件事必须做——写文档注释。

不是"要写"，是"必须写"。因为定义工具这件事，函数本身只是一方面，最重要的是让 AI 知道这个工具是干什么的。你不写文档注释，它不知道，那就无从判断什么时候该调你。

文档注释分两段。第一段写这个工具做什么、什么时候用：

> 根据险种和保费条件查询可用于推荐的候选保险产品。当用户咨询具体保险产品，或需要保险产品推荐时使用。

第二段是 `Args`，逐个说明参数：`category` 是产品分类列表，可选值是 `medical`、`critical_illness`、`life`、`accident`；`max_premium` 是保费上限，可选，只返回最低保费小于该值的产品；`limit` 是每个险种查询的数量。

有了这些解释，AI 看到工具就能判断它的作用、知道参数该怎么填。这就是文档注释在工具里比在普通函数里重要得多的原因：普通函数的读者是人，工具的第一个读者是模型。

到这儿，查候选产品的工具才算定义完成。

### 接进 agent，跑一遍真实对话

工具定义好了怎么用？回到 `agents` 这边，把它扔进 agent 的 `tools` 列表就行：从 `tools` 模块导入 `query_candidate_products`，往列表里一放。

提示词理论上也该改一改，让它知道有这么个工具存在。不过笔记里这会儿没改，那就先试试——现在模型越来越强，提示词不写那么复杂，可能也能用。

实测走一遍。刷新页面重来：

我说"喂你好，我想买保险"。它回：很高兴为您服务，我是安心宝的智能保险顾问，在给您推荐之前，我想先了解一下您的具体情况——您想为谁投保、您担心什么、您的预算是多少，还贴心地给了个例子，比如 30 岁。

我说：给自己投保，我今年 30，预算 2 万以内。

它接着说：在推荐之前，还要确定一些关键信息，以便更精准——您比较看重哪方面的保障？

我说：我不确定，最好全面一点，职业是程序员。

它回：程序员这个职业很好，属于低风险职业，在意外险、寿险投保上都很方便。

班里当场笑了一片——程序员算低风险职业吗？这个先不争论。

然后它给了一套四种都包含、保额合计四十多万的方案，接着说了一句关键的话："我先帮您查一下目前有哪些合适的产品，您稍等。"

说明它去查数据库了。后台没打日志，调用记录看不到，但它紧接着报出来的四款产品是：复星联合新手2号（医疗险）、达尔文12号（重疾险）、太平洋小蜜蜂6号（意外险）、富有一生2025（寿险）。

这四款在我们库里有没有？回数据库对一遍：达尔文12号有，就是第二个重疾险，另外还有个"宝贝计划"应该是给小孩子买的；小蜜蜂6号有；富有一生2025有；新手2号也有。而且正好一个险种一款。它报的合计预算大概 8500 到 1.7 万，也在"小于 2 万"的范围里。

> **结论**：产品名对得上、险种对得上、预算对得上，说明这些不是编的，是真从库里查出来又综合过的。到这一步，这个保险顾问就不再是纯粹的聊天机器人了——它能查数据库，能结合你的年龄、职业和预算给你出方案。

### 方案要能存下来：两张表

再往下想一步：AI 给我推荐了一套方案，如果我认了这套方案，它是不是应该被保存下来？

应该。保存下来，下次我再来聊，AI 能接着这套方案往下说，不至于每次都从头问"你叫啥、你多大了"。这是我跟你聊过一次之后，你本来就该知道我是谁。

数据库里本来就有一张保险方案的表，专门存方案。一个方案由哪些数据组成？

首先是用户画像——这个用户今年的年龄、职业、预算等等，这些信息都叫用户画像。然后是方案本身的基本信息：方案说明、总预算。再往下，一个方案里还要包含很多款保险产品：每个产品推荐的是哪个险种、预算多少、为什么推荐它。推荐是有理由的，比如"程序员经常久坐加班""这款含猝死责任，程序员高强度工作很有必要"——现场那套方案里每一条都带着理由。

所以一个完整方案的信息分成两块，对应两张表：

| 表 | 字段 | 含义 |
| :--- | :--- | :--- |
| `insurance_plans` | `id` | 方案 ID，由数据库生成 |
| `insurance_plans` | `user_id` | 方案属于哪个用户，跟着当前登录用户走 |
| `insurance_plans` | `plan_name` | 方案名称，由 AI 生成 |
| `insurance_plans` | `summary` | 方案的整体说明，由 AI 生成 |
| `insurance_plans` | `insurance_profile` | 用户画像，AI 总结年龄、身份等信息形成 |
| `insurance_plans` | 总预算 | 用户说多少就是多少 |
| `insurance_plans` | 投保状态 | 默认未投保，投保后变化 |
| `insurance_plans` | 创建时间 / 更新时间 | 常规时间字段 |
| `insurance_plan_items` | `id` | 方案项 ID，数据库生成 |
| `insurance_plan_items` | `plan_id` | 所属方案的 ID |
| `insurance_plan_items` | `product_id` | 这个方案项对应的产品 |
| `insurance_plan_items` | 展示顺序 | 1、2、3、4，按顺序展示 |
| `insurance_plan_items` | 推荐理由 | 由 AI 生成 |
| `insurance_plan_items` | 保费 | 这个产品对应的预算 |
| `insurance_plan_items` | 投保状态 | 默认未投保 |

`insurance_plans` 存方案的整体信息：这个方案是给哪个用户规划的、用户画像什么样、方案叫什么名字、整体说明、总预算、投保状态。`insurance_plan_items` 是"方案项"——`item` 就是条目，方案里有几个产品，就有几个方案项。刚才那套四款产品的方案，在方案表里是一行，在方案项表里是四行：第一行对应新手2号，第二行对应达尔文12号，第三行对应小蜜蜂6号，第四行对应富有一生2025。

> **提示**：方案项必须带 `plan_id`。因为所有人的所有方案都存在同一张表里，不挂上 `plan_id`，你根本分不清这条记录属于哪个用户的哪套方案。

这套东西落到代码上，就是新建一个 `insurance_plan` 模块，有自己的 models、schemas、repository 和 service——但**不需要 router**。因为这个模块的功能不是给前端用的，是给 agent 用的。

```text
app/modules/insurance_plan/
├── models.py       两张表对应的 ORM 模型
├── schemas.py      新增方案、新增方案项时各需要哪些字段
├── repository.py   方案与方案项的新增
└── service.py      调 repository，对外提供保存能力
```

模型建两个：一个对应方案表，一个对应方案项表，再加增删改查的逻辑。

这里有个心态上的转变：这两张表的数据从哪来？不需要你写，是 AI 帮你写的。用户确认方案之后，AI 把方案名、摘要、用户画像、总预算、四个方案项一起生成出来，通过工具往库里写。你要做的，只是把约束定好——新增方案需要什么字段、新增方案项需要什么字段（schemas），再定一个 repository 实现方案和方案项的新增，一个 service 去调 repository，最后在 `tools.py` 里定义一个"保存保险方案"的工具，扔给 AI。

```text
用户确认方案
    │
    ▼
Agent（模型）
    │  调用 save_insurance_plan 工具
    │  参数：方案名 / 摘要 / 用户画像 / 总预算 / 四个方案项

Service
    │
    ▼
Repository
    ├──► insurance_plans        插入 1 行
    └──► insurance_plan_items   插入 4 行
```

工具写好之后，你在对话里把方案敲定，AI 就会自己把这套由四个产品组成的方案写进数据库。现场还顺手试了改选：它又给了几个备选推荐，我说那就还是新华人寿吧，看着保得高一点——这套方案就算定下来了。

但这不是"毕业"。这里讲的其实是一个思想：我们开发智能客服、拓展它的能力，本质上就是给它加更多的工具。

所以后面不带着大家一个一个开发了——那就是纯粹的业务逻辑。而业务开发，大家以后不是用 Python 来做，是用 Java 写。将来你要加一个新能力，在 Python 这边定义工具、去调 Java 那边的接口，扔进 agent 就行了。我们的重点是学会 agent 的开发。

### RAG：考试允许带小抄

那什么是 RAG？

RAG 的全称是 Retrieval-Augmented Generation。第一个词 Retrieval，检索的意思；第二个词 Augmented，增广的、增益的、扩张的，说白了就是增强；第三个词 Generation，生成。三个词合在一起，就是**检索增强生成**。

> **定义**：RAG 是通过检索加载额外的知识作为上下文，来增强大模型生成的回答。

为什么要这么干？因为大模型生成的回答有幻觉。

举个例子。我们是一家保险商城，开了个 7×24 小时在线的客服，专门回答与保险产品条款有关的问题。如果只是直接调 DeepSeek，当用户来问某款产品的条款，比如"尊享E生2026的免赔额是多少"，会怎么样？

DeepSeek 根本不知道我们公司自己的产品——它没有拿我们公司的产品条款训练过。所以用户问它，它只能根据自己训练的数据来回答，甚至在那儿一本正经地胡说八道。这就是所谓的幻觉。

那怎么解决幻觉？回到刚才那句话：检索增强。

问题之所以存在，是因为它不知道我们公司产品的条款。那如果我把条款给它呢？它基于条款来回答，不就能回答了？相当于考试的时候给它带了个小抄——答案都给你了，照着答案说，你还能不会说吗？

具体做法就是：用户提问时，把用户的问题和我们公司的保险条款一起发给模型，让模型去读条款里的信息，再根据条款里的信息回答用户的问题。

有人会问：既然条款能给，为什么不直接把条款给用户，让用户自己看？

> **提示**：条款给用户有两个问题。第一，条款非常多，用户根本不知道自己要的那一条在哪；第二，条款写得很专业，用户读不懂。给模型，模型读懂了，再用自然语言回答你——这才是价值所在。

所以在这套逻辑里，保险条款就是那份"额外的知识"，也叫外挂知识库。用户提问时，把这份外挂知识和用户的问题一起发给模型，让模型基于外挂知识来回答。这就是 RAG 的字面意思：先检索，用知识库做增强，再生成回答。

听起来挺不错吧？这个事是不是就解决了？

没有。理想很丰满，现实很骨感。

### 理想很丰满，现实很骨感

一家保险公司，产品非常之多；产品多，条款就更多。

我手上的资料里其实有一些保险条款，还只是一小部分：随便点开一个 PDF，就是 1081KB——一千多 KB，已经一兆多了，有的接近两兆。而这只是很少的一部分。

我们做的是一个保险商城，会有全国各大保险公司的各类产品，产品数以百计、千计，每一个产品可能还有好几份条款。将来总的条款数量会非常庞大。

把这么庞大的条款一起发给模型，会撞上两堵墙。

第一堵墙是上下文窗口。模型不是无限的，你每次跟它聊天时携带的信息有一个上限，不同模型不一样：目前最顶尖的模型是一兆 token，不能超过；而大部分模型还限制在 200 多 K。你把公司所有条款都发过去，发不过去——先不说 PDF 转成纯文本会小一些，那也是一个远超上限的量。

第二堵墙是钱。token 是非常昂贵的。DeepSeek 还算便宜，但马上也要涨价，大概输入的 token 每 100 万——也就是每一兆——一两块钱。你想想看，如果每回答用户一个问题都要塞进全量条款，相当于公司每回答一个问题就花掉几块钱。用户随手发个"hi"，一块钱没了；上百万用户在同一瞬间发一句"hi"，一百万没了。这个账你耗得起吗？马斯克来了也耗不起，就他那点家产，分分钟给你干没。

> **提示**：这里有两个"兆"，别混。说文件大小的时候，兆是 MB，1081KB 差不多一兆；说上下文和 token 的时候，兆是"百万 token"，一兆 token 和一兆字节完全不是一回事。

所以结论很清楚：不能把所有东西都发过去。

### 把条款切开，只取相关的那几片

换个角度想：要回答用户的某一个具体问题，我们真的需要把整个公司的所有条款都发过去吗？

不需要。我们只需要发跟用户问题相关的那一部分条款。

那怎么办？把这些条款切分——切一切、拆一拆，拆成小块。一份一兆多的条款里有很多很多内容，就把它拆成一小段一小段的，每一段大概几百个字，或者上千个字。所有条款都这么处理，全部拆成很小的块，每一块里带一点完整的条款内容。这个动作就叫知识切分。

切完之后，用户再来提问，我们只需要从这些切出来的知识片段里，找到跟用户问题相关的那几片，返回给模型，把片段和问题一起发过去。

这样一改，刚才那两堵墙都塌了：片段体积小，不会超出上下文窗口；片段占的 token 少，成本也低。完美解决。

但新的问题马上来了：我们把知识切成了这么多小块，到底哪一块是跟用户问题相关的？你怎么才能找出那一片？

> **易错点**：这一步找错了，整个 RAG 就废了。你把不相关的片段和用户问题一起发过去，模型基于错的材料回答，照样答不对——检索错了，后面生成得再流畅也是错的。

所以这就牵扯到下一个问题：如何从众多的知识片段中，找出与用户问题相关的那一片。这叫知识检索。

现在再看 RAG 这三个字母，就全对上了：

| 字母 | 单词 | 中文 | 在流程里干什么 |
| :--- | :--- | :--- | :--- |
| R | Retrieval | 检索 | 从海量知识片段中快速找出与用户问题相关的片段 |
| A | Augmented | 增强 | 把检索到的片段与用户问题结合，作为额外上下文 |
| G | Generation | 生成 | 模型基于这份外挂上下文生成回答 |

注意这里的检索不是检索"文档"，是检索"知识片段"。知识被拆成一个个小片段之后，数量可以达到数以百万甚至千万级；我们要从如此多的片段里快速找到相关的那几片，模型才可能答对。这个检索的过程，就是 RAG 里的 R。

```text
【离线：建库】
条款 PDF ──切分──► 知识片段库（几百字一段，规模可达百万、千万级）

【在线：问答】
用户问题 ──检索──► 相关知识片段
                      │
                      ├── 与用户问题拼成上下文
                      ▼
                    模型 ──► 回答
```

读图：上半部分是提前做好的准备工作，把条款切碎存成片段库；下半部分是每次提问时走的在线路径，先检索、再拼接、最后生成——这条在线路径正好对应 R、A、G 三个字母。

那到底该怎么检索？别着急，这是下一节要讲的事。

> **承前启后**：上一节讲完「从一本正经地胡说八道，到会查库的保险顾问」，下一节接着讲「从词向量到 RAG 蓝图」。

## 从词向量到 RAG 蓝图
> 对应块：BLK28 | 覆盖分集：P106-P108 | 块标题（分集名）：《向量检索原理与 RAG 架构》

新的问题来了：知识已经被切成一堆一堆的片段，体量如此庞大，到底该怎么检索？怎么从这海量片段里，把真正跟用户问题相关的那一条捞出来？

我先问一句：检索这门技术，你们以前学过吗？没学过？那就好办了——没学过才有的讲，因为这块本来就是新东西。

### 两类检索方案：从百度说起

知识检索目前有两大类方案。注意是两大类，不是两种。

第一类，就是百度那样的。大家都用过百度，搜「Java 培训」或者「Python 培训」，回车下去，出来一大片网页——广告先不算，剩下的结果里，每一条都带着「Java 培训」这几个字。全球各地有数以亿计的网页，百度凭什么把这几条挑出来？靠的就是关键字检索：它去文档里找，看有没有对应的关键字。

这个办法很直接，也很好理解。但回到我们的业务场景，它不合用。

### 关键词的死角

为什么不合用？因为用户问的问题和知识片段之间，不一定存在精准的关键词匹配。

用户提问是口语化的。他问「天空为什么是蓝色」，对应的知识是什么？是那一套光学效应。可你拿着「天空」「蓝色」这些字去知识库里检索，检得到吗？检不到——知识片段里压根不会出现「天空为什么是蓝色」这种句子。

再看条款场景。条款里写的是「免赔额」，用户问的却是「多少钱不能赔」。这两句话意思很接近，可「多少钱不能赔」里没有「免赔额」这三个字。你拿它去检索，同样检不到。

> **结论**：关键字检索要求字面对得上，而用户提问偏偏不爱用术语。这条路在我们这里走不通，得换成按语义来检索。

按语义检索——话说得轻巧。代码怎么理解语义？到今天为止，我们写的代码能理解人类语言的含义吗？根本不能。所以要讲语义，就得先讲一个概念：词向量。

### 词向量：把词放进坐标系

AI 为什么能理解人类的语言？大家平时都叫它大模型，全称是 large language model，大语言模型。它凭什么叫「语言」模型？因为它的底层，就是靠人类语言的词向量撑起来的；这类模型最初设计出来，干的就是理解人类语言这件事。

词向量，英文叫 word embedding。定义一句话就能说完：把词变成多维空间向量的一种技术。

拆开是三步。第一步，把人类的自然语言拆成一个一个的片段，这些片段叫 token，你也可以把它理解成「词」。要注意 token 不一定等于一个单词，有时候一个单词会被劈成两半。为了讲着方便，下面统一叫词。

第二步，把每一个词通过模型计算，变成一个浮点数数组。

第三步，把这个浮点数数组当作向量的坐标。三步走完，一个词就成了空间里的一个向量。

听上去还是悬：什么叫把词变成数字？什么叫坐标？

先说向量。一个数组里只有两个元素，把第一个元素看作横坐标、第二个元素看作纵坐标，我们就能在平面直角坐标系里定位到一个固定的点。从原点向这个点画一条线——这条线有方向，也有长度。既有方向又有大小的量，就叫向量。

所以一个两元素的数组，就是二维平面上的一个向量；三元素数组，多一个 z 轴坐标，就成了三维空间里的向量；四元素数组，就是四维空间里的向量。

有人抬杠：人类生活在三维世界，哪来的四维？我反问一句：谁告诉你这个世界一定只有三维？蚂蚁在纸上爬，它只知道那是个平面，它感觉不到纸面之外还有方向。人类是三维生物，所以觉得世界就是三维的——可世界为什么不能是四维、五维、甚至一万维？完全可以，只是你无法直观想象而已。数学家在这件事上是很「变态」的，他们认为维度可以无限。

> **提示**：高维空间没法在脑子里画出图，但只要它满足向量的运算规则，就能参与计算。「想象不出来」和「不成立」是两件事，别把前者当后者。

于是，一个一万维的数组，就是一万维空间里的一个向量。这么大的空间人类认识不了，可数学概念上它不但存在，还能拿来做运算。

词向量就落在这里。在 GPT 里，一个词转出来的浮点数数组有一万二千二百八十八个元素——也就是说，任何一个词都能转成一个 12288 维的向量。这么大的向量你无法想象，但数学上没问题。

转成向量到底有什么用？用处在于：让这些向量在多维空间的不同方向上，表达不同的语义。

一开始当然做不到。一开始词扔进向量空间，生成的浮点数全是随机的，毫无意义。然后人类开始训练：拿现实生活里大量的自然语言语料去喂这个生成算法，反复调整，让语义相近的词在空间里靠得近一点，语义相反的离得远一点。生成得不对就调，再不对再调。就这么一路调下去，这些浮点数数组才慢慢变成「有意义的向量」。

### 训练出来的方向，就是语义

训练到什么效果？多维咱理解不了，退到二维来看。

空间里有两个词向量，一个代表「男人」，一个代表「女人」——注意这是训练之后的结果。用女人向量减男人向量，得到的是什么？向量减向量还是向量，它从男人指向女人。

再找一组：国王、王后。用王后向量减国王向量，你会惊奇地发现，这个差向量跟刚才男人女人的差向量，方向和长短几乎一模一样。

为什么？男人和女人的差异是性别差异，国王和王后的差异也是性别差异。也就是说，在这个空间里，「朝着这个方向」代表的含义，大概率就是性别。

不止这两组。阿姨减叔叔、妈妈减爸爸，算出来的差向量都跟它们非常接近。方向一致，长度也一致。于是我们认定：这个方向，就是空间里的「性别」。

一万多维的空间里，方向有多少个？数不清。而每一个方向，将来都可能对应一种语义。人类世界里所有词语的语义，能不能都用这些方向表达出来？完全可以。

能表达，就能推理。

比如我只知道爸爸的向量，不知道妈妈的向量在哪儿，但我知道男人和女人的差代表性别。那我就把爸爸向量沿着「性别」这个方向推过去，落点周围最近的那个向量，大概率就是妈妈。这是一次推理：我并没有见过「妈妈」这个向量，可我拿空间里的方向概念加上已有的爸爸向量，算出了它大致的位置。

再换一个。我说「有一个知名的男艺人」，让模型猜是谁——它猜不出来。但空间里一定有「艺人」这个向量。我继续给提示：「他擅长唱歌」，模型就到空间里找表达「唱歌」的方向和大小，拿「艺人」向量跟它做运算，调一次；「他还擅长跳舞」，再往「跳舞」的方向上调一次；「他还会打篮球」，接着调；「他爱穿背带裤」，再调。几轮下来，落在最后那个位置附近的词向量指向谁，答案就非常明确了。

> **结论**：所谓模型推理，不是它心里早存着一个答案，而是它在多维空间里沿着语义方向一次次挪位置，挪到哪儿，哪儿就是答案。

### 相似度怎么量

绕回开头那个问题：要从海量知识片段里找出与用户问题相关的那一条。有了词向量，做法就顺理成章——把用户问题转成向量，把知识片段也转成向量，然后比：问题向量跟哪条片段向量最接近，哪条片段的语义就跟问题最接近。

> **定义**：用向量之间的距离或夹角来衡量语义接近程度，这套做法叫向量相似度检索。

怎么比较两个向量近不近？算法有好几种：余弦相似度、欧式距离、点积。

先说欧式距离。两个点分别代表向量 $\mathbf{v}_1$ 和 $\mathbf{v}_2$，欧式距离就是这两个点之间的直线距离：对应坐标相减、各自求平方、求和，再开平方根。推广到 $n$ 维就是：

$$d(\mathbf{v}_1,\mathbf{v}_2)=\sqrt{\sum_{i=1}^{n}(v_{1i}-v_{2i})^2}$$

距离越小，两个向量越接近，相似度越高。

但欧式距离有个毛病。想两个向量：一个短、一个长，方向完全一样。它们的欧式距离非常远，可方向上一致，从语义上讲应该算很相似——至少方向是一样的。欧式距离却判它们差得很远，这就不太合理。

于是有了余弦相似度：不看长度，只看夹角。求两个向量夹角的余弦：

$$\cos\theta=\frac{\mathbf{v}_1\cdot\mathbf{v}_2}{\lVert\mathbf{v}_1\rVert\,\lVert\mathbf{v}_2\rVert}$$

余弦的脾气是：角越大，余弦越小；角越小，余弦越大。角小说明两个向量方向贴近，语义也相近。为了让它变成「越小越相似」的距离，用 $1-\cos\theta$——角越小，$1-\cos\theta$ 也越小，正好跟欧式距离一个口径。

还有一种是点积。点积是多维向量之间的运算，比前两个复杂，这里不展开。

> **提示**：$1-\cos\theta$ 能当距离用，是因为余弦值域是 $[-1,1]$，减完落在 $[0,2]$：方向一致时为 0，垂直时为 1，完全相反时为 2。

最终要的效果只有一句话：语义越接近的文本，在向量空间里越近；语义越相反的，越远。

| 度量方式 | 怎么算 | 数值含义 | 短板 |
| :--- | :--- | :--- | :--- |
| 欧式距离 | 各维差值的平方和再开方 | 越小越相似 | 只看绝对位置，方向相同但长度不同的向量会被判得很远 |
| 余弦相似度 | 夹角余弦 $\cos\theta$ | 越大越相似 | 只反映方向，丢掉了长度信息 |
| 余弦距离 | $1-\cos\theta$ | 越小越相似 | 同上，长度信息不参与 |
| 点积 | 对应分量相乘再求和 | 本讲未展开 | 多维向量运算，复杂度更高 |

### 向量模型与向量数据库

用户问题和知识片段都得转成向量，谁来转？不是我们自己写算法，将来用专业的向量模型。把文本交给它，它自动帮你转成向量。

用哪家？阿里云百炼上有一堆向量模型可用，别家也有。咱们项目里统一走百炼，理由很实际：阿里云百炼的模型是免费的。所以整个项目的向量转换，全部用百炼里的向量模型。

转出来的向量往哪儿存？知识片段一多，量就上来了：所有条款都拆开，片段可能到百万级的规模。这么多向量，自己拿个列表存着、自己写循环比相似度？太麻烦，也扛不住。

于是有了向量数据库。它主要两个作用：一是存储向量数据，把知识片段转成向量存进去；二是基于相似度检索向量数据，也就是把知识片段捞回来。

> **定义**：向量数据库 = 向量存储 + 相似度检索，两件事一体，不是单纯的「数据库」。

市面上的向量数据库非常多，而且大部分 LangChain 都支持，所以将来直接用 LangChain 提供的 API，就能操作各种各样的向量库，不必挨个去学各家的 SDK。

其中最流行的是 Milvus。这个名字来自一种鸟——飞得很快的一种鸟，取的就是「快」的意思，速度非常快、效率非常高。它在市面上用得最广，后面我们也会专门学它。

### RAG 的完整蓝图

到这儿，检索这块拼图齐了，RAG 的完整流程也就浮出来了。

RAG，检索增强生成。三个词挨个拆开：

- **检索**：用向量相似度把知识片段检索出来；
- **增强**：把检索到的知识片段连同用户问题一起交给模型，增强输入，减少幻觉；
- **生成**：模型基于这些知识片段生成答案。

> **易错点**：RAG 不是「让模型记住知识」。模型本身没变，变的是它这一次提问时看到的上下文——知识是现场塞进提示词的。

核心流程分两大阶段：离线阶段和在线阶段。

```text
离线阶段（上线前做，可提前准备）
  原始资料（保险条款等）
        │ 解析成文档
        ▼
  知识切分（每片 500~800 字）
        │
        ▼
  向量化（向量模型）
        │
        ▼
  存入向量数据库（Milvus）

在线阶段（用户每次提问时，实时）
  用户问题
        │ 向量化
        ▼
  向量库按相似度召回 top-n
        │
        ▼
  片段 + 问题拼成提示词
        │
        ▼
  模型生成答案
```

读图：上下两条流水线共用同一个向量模型和同一个向量数据库，离线那条把知识灌进去，在线那条把知识取出来用。

为什么一个叫离线、一个叫在线？因为离线阶段可以在项目上线之前提前做完：所有知识提前切好、转好、存好，不用等用户来了才临时处理。所以数据规模再大也不怕，提前准备就行。

在线阶段不一样，它是用户来提问才触发的，是实时的。每一次提问，都要现场走一遍检索。

#### 离线阶段：建知识库

四步。

第一步，知识加载和清洗。把公司所有的保险条款拿过来，读到内存里，解析、处理，形成文档。为什么要费这道工序？因为实际的保险条款格式非常复杂，排版五花八门，还有表格，直接拿来根本没法用，必须先解析干净。

第二步，知识切分。把文档切成一个一个片段，体积要小一些，比如每片五百字、八百字，差不多一篇小学生作文的长度。

第三步，向量化。用向量模型把每个片段转成向量。

第四步，存储向量。把转好的向量存进向量数据库。

一句话串起来：加载清洗、切分、向量化、入库。

#### 在线阶段：一次提问走三步

第一步，问题向量化。用户问什么，就把这个问题转成向量，同样用向量模型。这里有一条硬要求：**必须跟离线阶段用同一个模型**。同一个模型转出来的向量才在同一套标准下，才有可比性；模型换了，两边的向量不在一个空间里，比较就失去意义。

第二步，知识召回。拿问题向量去向量数据库里检索，召回与用户问题最相关的片段。不一定是 Top1，可以取 Top5、Top10，一次召回一批。

第三步，拼接并生成。把召回的知识片段和用户问题拼成新的提示词，发给模型，让它据此生成答案。

> **提示**：这两大阶段、每个阶段各几步，是面试题，我强调一下。你去面试一定会被问到「RAG 的核心流程分哪两大阶段、每个阶段干什么」。离线四步、在线三步要能一口气说清，还要能解释为什么这么分。过两天我会抽人回答。

## 从文档到知识片段：文档加载与切分策略
> 对应块：BLK29 | 覆盖分集：P109-P112 | 块标题（分集名）：《文档加载与切分策略》

### 离线建库的四步流水线

上一段我们把 RAG 的代码预览从头到尾过了一遍。回头看，整个 RAG 其实就两步：第一步构建知识库，第二步检索——一步在离线阶段做，一步在在线阶段做。现在先把第一部分拆开。

离线阶段这条线，完整流程是四件事：先把文档加载到内存里形成 `Document`，再把文档切成一个一个片段，然后把片段转成向量，最后把向量存进向量数据库。

```text
企业文档（PDF / Word / PPT / Excel / HTML / 扫描件）
        │
        ▼
①  加载    ──►  list[Document]   （page_content + metadata）
        │
        ▼
②  切分    ──►  list[chunk]      （一个个知识片段）
        │
        ▼
③  向量化  ──►  每个片段转成一个向量
        │
        ▼
④  入库    ──►  向量数据库
```

图里是一根单向链条，每一步的产物就是下一步的输入，中间哪一环做糙了，后面都补不回来。这一部分先把前两步讲透：加载和切分。

> **结论**：加载决定你拿到什么形态的原文，切分决定你喂给向量库的知识片段长什么样。这两步定下来的东西，会一路带到检索环节。

### 所有加载器都共用一个入口

企业里真实的情况是：文档种类非常多，不是只有一类，处理起来的差异很大。更麻烦的是那些复杂的 PDF——里面有各种表格，有图文混排，甚至有整页的扫描件。这种文档处理起来非常费劲。

好在 LangChain 已经把文档加载器准备齐了：针对不同的文件类型有不同的加载器，不用自己从零实现。官网上这类加载器多到学不完，也没必要学完。只要抓住一件事——所有加载器都实现了统一的接口。

> **定义**：`BaseLoader` 是所有加载器的顶级父类，里面有一个 `load` 方法。不管用 LangChain 里的哪一个加载器，加载都调这个方法。

统一接口带来的好处很直接：学会一个，其余的换个类名就能用，用法一模一样。

`load` 的返回值是 `list[Document]`，不是单个 `Document`。为什么是列表？因为读文档时可能一次读到很多份，也可能把同一份文档处理成很多份（比如按页拆开），所以统一用列表装。

而 `Document` 代表一篇文档，核心就两个字段：

| 字段 | 装的是什么 | 典型内容 |
| :--- | :--- | :--- |
| `page_content` | 文档的原始内容 | 正文本身，后面的切分与向量化都以它为准 |
| `metadata` | 描述这份文档的元数据 | 文件名、文件来源、页码等 |

拿到一篇文档要取内容，就取 `document.page_content`；要取它的描述信息，就取 `document.metadata`。这两个字段得分清：一个说的是"文档里写了什么"，一个说的是"这份文档本身是什么"。

### 用 PyPDFLoader 走通第一次加载

先把定位说清楚：`PyPDFLoader` 是 `langchain_community` 里的社区版加载器，而这个包已经不再由 LangChain 官方维护了。所以这里拿它做入门演示，不是推荐你在真实项目里用它。第一次运行会蹦出一段过期警告，大意是 `langchain_community` 已经 sunset、不再活跃维护——不维护不代表不能用，它照样能跑。

依赖项目里已经装好，直接开工：在 `day07` 下新建 notebook，叫 `02_文档加载器之PyPDF`。

```python
from langchain_community.document_loaders import PyPDFLoader
```

初始化时给两个参数：

- `file_path`：要加载的文件路径。示例写的是 `resources/simple.pdf`，这是相对路径，相对当前工作目录。项目里没有 `simple.pdf`，换成 `resources/贵州茅台.pdf`。
- `mode`：加载模式，`single` 和 `page` 两种。

> **定义**：`single` 把整个文件当成一页加载，一个 PDF 最终只得到一个 `Document`；`page` 按 PDF 的物理分页加载，十页的文档就返回十个 `Document`。

先跑 `page`。

#### page 与 single：一次加载出几个 Document

贵州茅台这份 PDF 有六页。按 `page` 模式加载，返回的列表里就应该是六个 `Document`。这是个很好的先猜后验的机会：页数已知，模式的含义已知，那加载结果的数量是可以提前算出来的。

```python
loader = PyPDFLoader(
    file_path="resources/贵州茅台.pdf",
    mode="page",
)
docs = loader.load()
```

不管用的是哪个加载器，拿到的都是 `BaseLoader` 的 `load`，所以这一步永远是 `loader.load()`，返回的一定是 `list[Document]`。跑出来数一数，正好六个，跟 PDF 的页数对上。

#### enumerate：给每个片段带上编号

打印这六篇文档时，需要知道"这是第几个"。直接 `for doc in docs` 拿不到下标，用 `enumerate` 就能同时拿到下标和元素。

`enumerate` 是枚举的意思：遍历元素的同时给你一个角标。这个角标默认从 0 开始，所以打印出来是 `012`。它还支持 `start` 参数，指定从几开始数——写成 `start=1`，编号就变成 `123`。

这个工具看着小，实际用起来非常顺手：以后要把片段按序号落盘、要把第几页和第几个 `Document` 对上、要在日志里标出处理到哪一条，都得靠它。

```python
for i, doc in enumerate(docs, start=1):
    print(f"===== 第 {i} 篇 =====")
    print(doc.metadata)
    print(doc.page_content)
```

#### metadata 里到底有什么

先看 `metadata`。打印出来会发现，大部分键是空的，真正有值的是这么几个：

- `moddate`：文件的修改时间；
- `subject`：文档的主题；
- `title`：文档标题；
- `source`：文件的来源；
- `total_pages`：总页数；
- `page`：当前页是第几页。

这些就是元数据——对文档的一种描述信息。它不参与内容理解，但在工程上很有用：出问题能追到源文件，检索命中后能告诉用户"这句话出自第几页"，做引用溯源靠的就是它。

再看 `page_content`，这就是实打实的正文：第一个 `doc` 里是第一页的文字，第二个 `doc` 里是第二页的文字。每一页文档都由 `metadata` 和 `page_content` 两部分组成，结构一模一样。

#### 我为什么劝你别按页加载

`page` 模式跑通了，但我通常不建议把文档分页加载，建议用 `single`。

改成 `single` 再看，加载出来看着还是个列表，但列表里只有一个 `Document`，整个 PDF 作为一篇文档返回，全部内容都在里面。

理由不是"少一次循环"这么表面，而是加载只是第一步。加载完还要做切分——你在这就把文档切成一页一页了，等会再切是不是就不方便了？

更要紧的是，按页切很可能把一个完整的内容拆开。有些文档的上下页之间是有关系的：一句话写到页尾没写完，下一页接着往下写。这时候按页切，一个完整段落就被劈成两半，语义还完整吗？不完整了。

所以真正用的时候，用 `single` 把整个 PDF 作为一页加载进来，切分的事留到切分阶段再说。加载阶段不要切。

> **易错点**：加载阶段的"分页"和后面的"切分"不是一回事。分页是 PDF 的物理版式边界，切分要按语义边界来。两件事混在一起做，等于让排版替你决定语义。

### 社区版加载器搞不定的 PDF

`PyPDFLoader` 确实能把文件读进来，但读进来的效果很差。

原因在文档本身：行业里的 PDF 结构往往非常复杂，有左右分栏的、有复杂表格的、有图文混排的、还有整页图片扫描的。打开项目里那份保险条款 PDF 就知道——左右分栏、图文混排、中间还夹着表格，一份文档里全齐了。对付这种文档，靠按文本流抽取的加载器显然不够。

要啃下这种复杂 PDF，背后得有一整套模型：文档结构识别模型判断版面区块，多模态模型处理图文关系，表格处理模型把表还原成结构化数据，必要时还得上 OCR 模型。这是一条很重的处理链。LangChain 默认的 PDF 加载工具做不了这些，那就得换成专门的文档处理工具。

#### 四种常见的高级工具

这个方向上最常见的工具有四种：

| :--- | :--- | :--- | :--- |
| Docling | IBM 出品，现为 Linux 基金会项目 | 开源，商用友好 | 企业级多格式处理，PDF / Word / PPT / Excel / HTML / 图片全支持，公式识别、表格提取、多栏文档加载都强 |
| Marker | — | 收费，商业受限 | 能力很强，但授权限制多 |
| MinerU | 上海人工智能实验室 | 开源，商用友好 | 中文与复杂文档解析见长，有专门模型做公式识别，表格提取、多栏识别、处理速度都很突出 |
| unstructured | — | 核心库开源，高级功能闭源收费 | 老牌解析库，社区里用得广 |

Docling 最省心的一点是一个加载器通吃各种文档格式，还支持公式识别、表格提取和多栏文档加载，性能很强，实际项目里用得很多。Marker 虽然强，但它是收费的、商业受限，这里就不多说了。MinerU 是上海 AI 实验室出的，定位就是高精度中文和复杂文档解析，公式识别有专门的模型撑着，学术论文的还原度非常高，表格和多栏识别也极强，处理速度很快。unstructured 属于另一种商业形态：核心库开源，高级功能闭源收费。

这四种在 LangChain 里基本都有对应的集成，可以按需挑。

顺带说一个常被混进来的东西：RAGFlow。它不是一个文档加载器，而是一个完整的 RAG 服务器——里面自带离线的文档加载、文本切分、向量化流程，还自带向量检索的流程。它内置的文档加载工具叫 DeepDoc，名字你可能听过。DeepDoc 是开源的，但它不是一个能独立安装的软件，而是长在 RAGFlow 内部；想单独用它，只能把 RAGFlow 源码下到本地，再把 DeepDoc 相关的代码复制出来，很麻烦。它也是国产的，这里不往下展开。

### 为什么最后落在 MinerU 上

先把结论摆出来：这四个里开源的是三个——Docling、MinerU、unstructured；这三个里文档处理能力最强的是 Docling 和 MinerU。而 MinerU 是国人开发的，处理速度非常优秀，所以选它。

#### 能不能本地部署

还有一个现实考量：数据隐私。公司内部的文档要做成知识库，很多是不方便暴露给外部服务的，那就得能本地部署。MinerU 和 Docling 都支持本地部署，本地只要买了显卡，还支持 GPU 加速，性能很好。对数据隐私要求高的团队走本地部署；数据敏感度没那么高的中小团队，直接用它的公共 API 就行。

#### 免费额度与两种解析服务

MinerU 的公共 API 是免费的：每天 5000 个、单份不超过 200 页的文档，小于 20 页的文档则不限数量。不掏钱，每天还能有 5000 份的额度，对绝大多数中小企业来说这个量是很舒服的。

免费不等于不用注册——要注册，但注册不要钱。注册之后对外是两种服务：

| 服务 | 是否要 token | 单文件大小 | 页数上限 | 数量 |
| :--- | :--- | :--- | :--- | :--- |
| 轻量解析 | 不需要，免登录免注册，直接能用 | ≤ 10 MB | ≤ 20 页 | 不限 |
| 精准解析 | 需要 token（注册后在 API 管理里创建） | ≤ 200 MB | ≤ 200 页 | 每天 5000 份 |

轻量解析的优势是零门槛，劣势是页数卡在 20 页；精准解析支持更高级的能力，页数与体积都放宽到 200，代价是得有 token。

那选哪个？对大多数情况，轻量解析就够用了，只有复杂场景才需要精准解析。但具体到我们的保险条款文档，点开一看大多超过 20 页，有的直接五十页，那没得选，必须走精准解析，也就必须去注册账号。

注册完在网站上还能直接拖拽上传、在线免费试用——手头有不好处理的 PDF，扔给它先看效果，这是最快的验证方式。要在代码里通过 API 调，就进 API 管理，创建一个 token 复制出来。每天 5000 份的额度，正常项目根本用不完。

### 把 token 接进项目配置

拿到 token 的第一件事不是写代码，是把它安置好。硬编码进脚本是最糟的做法，正确姿势是两级：`.env` 存明文，配置类读环境变量，业务代码只认配置对象。

第一步，把 token 粘进 `.env`，键名叫 `MINERU_TOKEN`。这个 token 很长，粘贴时注意别漏字符。

第二步，去 `app/config` 里加配置类。已有的配置是按职责分开的：`AVSettings` 管项目通用配置，另外还有数据库配置、模型配置、日志配置。MinerU 这属于 RAG 相关的配置，跟上面几类都不搭，所以单独建一个类，叫 `RAGSettings`。

类里加一个字段 `mineru_token`，字段别名必须和 `.env` 里的键对上。别名的写法要一字不差，差一个字符这个值就读不出来。这个字段没有默认值——token 是外部凭证，代码里不该写死一个兜底值。类的说明就写"RAG 相关配置"，将来 RAG 的所有配置都往这里放，现在先放这一个。

第三步，让新配置生效。照着已有那四个配置的写法复制一份，把名字改成 `RAG`。这样 `settings` 里就多了一个 `RAG` 参数项，`RAG` 底下就有 `mineru_token`。

```text
.env                        app/config
┌──────────────────┐        ┌───────────────────────────────┐
│ MINERU_TOKEN=... │──────► │ RAGSettings                   │
└──────────────────┘        │   mineru_token                │
                            │   alias = "MINERU_TOKEN"      │
                            └───────────────┬───────────────┘
                                            │ 挂载为 settings.RAG
                                            ▼
                            settings.RAG.mineru_token
                                            │
                                            ▼
                            MinerU(token=...)  ← 精准模式客户端
```

图里是这条配置的读取路径：明文只落在 `.env`，配置类负责把它翻译成有类型的字段，业务代码通过 `settings.RAG.mineru_token` 取值，最后交给客户端。以后要换 token，只改 `.env`，代码一行都不用动。

> **提示**：别名和 `.env` 的键必须对齐，这是这类配置最容易翻车的地方。取值拿到 `None` 时，先回去比对这两处的拼写，不要急着怀疑客户端。

配置不会写也没关系，项目文档里有现成的片段，复制粘贴即可。

### 走官方 SDK：两种模式与实战细节

MinerU 的用法有两条路：一条是直接用官方 SDK，一条是跟 RAG 框架结合。它支持的框架里有 LangChain、RAGFlow 这些，我们用的正是 LangChain，看起来该走第二条。但 LangChain 那份集成文档托管在 GitHub 上，网络不通打不开，只好走第一条——官方 SDK 支持的版本很全，Python、JS、Go 都有，功能一点不少。

依赖里包含 `openai` SDK，项目里已经装好，不用再装。

```python
from mineru import MinerU

client = MinerU()
```

客户端创建好，接下来调哪个方法就决定了用哪种模式。

#### 快速模式：不给 token 也能解析

`flash_extract` 就是快速模式，不需要 token，直接能用。

```python
result = client.flash_extract("resources/xxx.pdf")
```

传进去的文件地址可以是在线文档，也可以是本地路径。本地路径写 `./resources/xxx.pdf` 或 `resources/xxx.pdf` 都行——后者是相对当前工作目录的写法。

解析完拿到的不是一段字符串，而是一个 `result` 对象，里面的东西相当多：可以转成 Markdown，可以转成 docx（也就是 Word），还能把文档里的图片单独取出来——毕竟原文是图文混排，图片本身就是内容的一部分。

#### 精准模式：token 从配置里读

精准模式换一个方法：`extract`。区别在客户端初始化时要带 token，这个 token 就从刚才配好的地方读。

```python
from app.config import settings

client = MinerU(token=settings.RAG.mineru_token)
result = client.extract("resources/xxx.pdf")
```

`extract` 支持更多的页数，走的就是精准解析那条额度。模式和方法的对应关系很干脆：`flash_extract` 对快速，`extract` 对精准。

#### 打开 OCR，扫描件也能读

MinerU 还能做 OCR，这对扫描件是救命的功能。项目文档里有一份 `small_ocr.pdf`，打开一看根本不是文字，是整张扫描出来的图片，字迹还很模糊。这种文档用普通文本抽取只能拿到空白。

做法是在 `extract` 上加一个参数：

```python
result = client.extract("resources/small_ocr.pdf", ocr=True)
```

跑完对照原图看，所有文字都被完整解析了出来，一点没漏。这就是扫描件的能力——到这一步，基本上任何 PDF 都不用担心了。

而且 MinerU 不止吃 PDF，html、ppt/pptx、doc/docx、xls 这些 Word 全家桶都支持。企业里 99% 的文档形态它都能接住，还免费。

#### 结果落盘：目录与网络的两个坑

解析成功不等于保存成功，这两个坑都踩过。

第一个坑：`save` 传一个 `resources/r2.md`，本意是存成这个文件，结果它在 `resources` 下建了一个叫 `r2.md` 的目录，真正的完整内容躺在目录里的 `full.md`，图片等资源也一并放在这个目录里。也就是说这个参数被当成目录名来用了。知道了这一点就不会慌：去目录里找 `full.md`，那才是解析出来的正文。

第二个坑是报错 `No zip data available`。这次现象很迷惑：上面打印出来的完整文档一点问题没有，说明解析本身成功了，只是保存那一步挂了。判断下来是网络问题——本地文件要先上传，网速差的时候上传就会出岔子。换成在线文档再试，三秒就完成，保存也顺利。

所以调试顺序要定成：先打印验证解析结果，再单独试保存。两件事分开看，才不会被一个 save 报错误导成"整个解析失败"。

还有速度。正常情况十秒左右能完成，快的时候三秒；第一次发请求时客户端要初始化，会慢一点；网络不好的时候拖到快一分钟也有过。这类延迟属于环境问题，不要急着改代码。

> **提示**：判断"MinerU 是不是坏了"之前先看两件事——解析结果打印出来了没有，以及当前网络能不能正常上传文件。这两个都正常，问题通常不在调用方式上。

### 切分要同时盯住两件事

文档加载进内存了，按知识库构建的流程，下一步就是切分：把内存里的文档切成一个个片段。

为什么要切？因为模型有上下文窗口的限制，不可能把整个文档一股脑塞进去，所以要切。真正难的不是"要不要切"，而是"切多大"。这个问题上有两个关键点必须同时考虑。

#### 检索精准度与语义完整度

> **定义**：检索精准度，是指在成千上万个知识片段里，能精准找到与用户问题最相关的那个片段。片段在英文里叫 chunk，就是"知识片段"的意思。语义完整度，是指检索到的这个片段必须覆盖回答用户问题所需的全部信息。

完整度出问题，往往就是切在了句子中间。举保险条款里最常见的例子：犹豫期那一条本来是一整句话，切的时候正好从中间咔一刀，前半句在上一块、后半句在下一块。这个条款还完整吗？不完整。用户问到犹豫期，检索到半截条款，回答自然也是半截。

#### 块越大越完整，但越难检索

先问一个问题：想保证完整度，块是切大好还是切小好？

直觉上，大块更好。把整段作为一个块，语义当然完整。但代价马上跟着来了。

每一个片段将来都要转成一个向量，这个向量表达的是这一整段的语义。一个块里同时装着合同构成、合同成立、投保范围、犹豫期，内容越多，向量的语义就越泛，噪音也越多。用户来问"犹豫期"，他这句话转出来的向量，核心含义就是犹豫期；而你那个大块里混着合同成立、合同构成，噪音一多，两边向量的相似度就降下来了。相似度一降，这个块就排不到前面，精准度就掉了。

反过来，切得很小——一句话一个块。这一小块精准地在描述"犹豫期是多长时间"，语义非常干净，精准度上去了。但这个条款被切断了，理赔相关的信息留在了别的块里，完整度下来了。

| 切法 | 检索精准度 | 语义完整度 | 典型后果 |
| :--- | :--- | :--- | :--- |
| 块偏大 | 低 | 高 | 一个块混着好几个主题，向量被稀释，问"犹豫期"却匹配到讲"合同成立"的大段 |
| 块偏小 | 高 | 低 | 条款被切断，片段确实命中了，但信息不全，答不完整 |

> **结论**：片段越大，信息完整度越高，但检索精度越低；片段越小，检索精度越高，但语义完整度越低。这两条是反向的。

那到底切多大？这件事没有标准答案，也没有任何一个人能给你一个放之四海皆准的数字。切多大、切多小，必须具体业务具体分析：文档是什么类型、用户会怎么问、答案需要多长的上下文，答案都藏在这些条件里。

不过没有标准答案，不等于没有章法。有一些常见的切分策略，能在一定程度上把这两个指标同时往上抬——优化的不是那个数字，而是切的位置。

### 五种常见切分策略

#### 固定长度切分

最简单的一种：按预设的大小切。比如预设 500 字符一块，就从开头数到第 500 个字符，咔一刀切下来；再往后数 500 个，再切一刀。从头到尾只认数字，不看内容。

优点是简单、速度最快，没有任何判断成本。缺点是它不认句子边界，非常容易在一句话中间截断，语义完整性被破坏得很彻底。

所以这种切法只适合对语义完整度要求不高的场景，比如日志、代码这类内容——它们本来就是按行组织的，切在哪儿损失都不大，检索时也不需要一整段连贯的论述。

#### 递归切分

递归切分允许你设置多个分割优先级，比如段落是第一优先级，句子是第二优先级。

它同样要设一个长度上限，比如 500。切的时候先按第一优先级来：按段落把文本拆开，然后判断这个段落有没有超过 500。没超过，这一段本身就是一个片段，收工；超过了，比如某一段有 800 字符，那就降一级，用第二优先级的句子边界来处理——在这个段落里一句一句往后累加，加到 500 就收，剩下的部分另起一块。

```text
段落（约 800 字符，超过 500 上限）
      │
      │ ① 按「段落」切 ──► 还是 800，超限
      ▼
      │ ② 按「句子」逐句累加，到 500 就收
      ▼
片段 1（≈500 字符）  +  片段 2（余下部分）
```

这样一段虽然被分成了两部分，但没有把任何一句话切开，完整度还保得住。分隔符可以设很多层，具体设多少由你决定；整套逻辑就是先用大块的分隔符试，不行就换更细的，一层层递归下去，直到满足大小要求为止。

因为它是沿着文档自身的结构往下退，切出来的块结构更完整、语义完整性更高，所以这是我首选的方案。拿不准该用哪种策略时，就用递归切分。

#### 语义切分

语义切分更狠一点：让模型帮你切。

把文档交给大模型，让它判断哪里是语义的自然边界，再按它的判断下刀。效果最好，但成本也是最高的——文档一大，这个成本会非常可观，因为每一段都要过一遍模型。

所以它通常只用在对语义完整性要求极高的场景：学术论文、法律文档这一类，一句话的意思断了就出大事的地方，才值得付这个代价。

#### 结构感知切分

结构感知切分，顾名思义，是利用文档的元数据来识别逻辑区块，按区块切。

举个最直观的例子：Markdown。Markdown 有严格的格式约定，一级标题、二级标题、正文段落，层级关系是写在语法里的。有了这层结构信息，就完全可以按标题切、按段落切——一个逻辑区块就是一个块，结构本身就是语义边界。

这类切法实现起来反而简单，因为文档天然就有结构，不用再去猜哪里该断。切出来的结构清晰、位置准确。适合的对象也很明确：天然带结构的文档，Markdown、HTML 都是典型。

缺点是它对文档素质有要求——文档格式必须规范。格式一旦不准，比如标题层级乱了、段落没有正确分隔，切出来的块就是歪的。垃圾结构进来，垃圾片段出去。

#### 滑动窗口切分

最后一种很少单独使用，通常跟前几种搭配：滑动窗口。

问题是这样产生的：假设按固定长度 500 切，而文档里有一段很长，整整 800 字符。那么第一刀落在第 500 个字符上，很有可能正好是一句话的中间——这一句的前半截在上一块，后半截在下一块。

解决办法是让相邻两个块允许重叠。比如重叠 20%，对 500 字符的块来说就是 100 个字符：第二块不是从第一块的断点接着往后切，而是往回退 100 个字符再开始，于是两块之间有了一段公共区域。

```text
块 1   第 1 字 ───────────────────── 第 500 字
块 2                  第 400 字 ───────────────────── 第 900 字
                             └──── 重叠 100 字 ────┘
```

被第一块切断的那半句话，在第二块的重叠区里是完整的，语义就接上了。第三块再和第二块重叠一部分，如此往下滑。窗口一路往后滑，重叠一路保留，这就是"滑动窗口"这个名字的来处。

它换来的东西很实在：一定程度上的语义完整性。代价也很实在：同样的内容被存了不止一份，向量库会变大，检索时也可能召回内容相近的重复片段。所以它是补偿手段，不是主力方案。

到这儿五种策略就说完了。要不要自己实现？不用，LangChain 全都实现好了，调用它提供的 API，把切分策略对应的参数配好就行。

## 从切分到向量：知识库的中间两步
> 对应块：BLK30 | 覆盖分集：P113-P117 | 块标题（分集名）：《文本切分与向量模型》

文档加载完，手上是一整篇 Markdown——一份评估点，几十页的 PDF 正文，几千字。这时候先别急着往向量库里塞。整篇扔进去做向量，等于把一本书压成一个点：它能匹配上一切，也就匹配不上任何一个具体问题。所以中间必须有一刀，切。

LangChain 里的切分器一大把，名字一个比一个长。但先别急着背名字。所有文档切分器都实现同一个接口，叫 `TextSplitter`。把这张脸认下来，后面换多少个类，你只是在换参数。

### 切分器都长一个样：先认接口，再认类名

`TextSplitter` 接口里就两个函数：`split_text` 和 `split_documents`。

`split_text` 收的是 `str`，返回的是 `List[str]`。你给我一个长字符串，我给你切成一堆短字符串——这很合理吧？切分嘛，本来就是这样。

有人会问：怎么是字符串？不是文档吗？那我反问一句：这一整篇文档拿到内存里，是不是就是个字符串？这还能是啥。所以"长字符串进、短字符串出"不是偷懒，它就是这件事的本来面目。

`split_documents` 收的是 `Iterable[Document]`，返回的是 `List[Document]`。你给我一堆 Document，我切完还你一堆 Document——粒度变了，类型不变。

| 方法 | 入参 | 返回值 | 什么时候用 |
| :--- | :--- | :--- | :--- |
| `split_text` | `str` | `List[str]` | 手上是一整篇文本，比如 `f.read()` 读回来的 Markdown |
| `split_documents` | `Iterable[Document]` | `List[Document]` | 上一步是 LangChain 的 loader，返回的本来就是 Document 集合 |

用哪个不用背，看你上一步拿到了什么。LangChain 自己的 loader，加载完返回的就是 `Document` 的集合，那直接把它扔给 `split_documents`，切完就完事。但我们实操里用的是 MinerU：PDF 进去，Markdown 出来，`f.read()` 读回来就是一个字符串，这时候只能用 `split_text`。选错方法不是逻辑错，是类型对不上。

```text
LangChain Loader ──► List[Document] ──► split_documents() ──► List[Document]
MinerU / open()  ──► str            ──► split_text()      ──► List[str]
```

两条路径最后都得到更碎的块，区别只在于块是裸字符串还是带着 `metadata` 的 Document。

> **提示**：`split_documents` 的形参写的是 `Iterable`，不是 `List`，但意思就是"能遍历的一串 Document"。loader 返回的正是这种对象，直接扔进去就行。

接口这一层认完了，后面无论换成哪一种切分器，代码骨架都不动——变的只是类名和构造参数。

### 固定长度切分：按字符数硬切

这是最省事的一种，也是我最不推荐的一种。演示一遍，你看着就知道它差在哪。

LangChain 里对应的类叫 `CharacterTextSplitter`：character text 是字符文本，splitter 是切割器，合起来就是"字符文本切割器"。创建它的时候要指定三个参数。

- `separator`：切分的分隔符。传空字符串，意思就是任意位置都能下刀——这个字和那个字之间、这句话说到一半的地方，都可以切。
- `chunk_size`：每一块的大小。设成 200，就是从开头数，数够 200 个字符就封一块，然后接着往下数。
- `chunk_overlap`：块与块之间重叠的字符数量。LangChain 这个切分器虽然是按长度硬切，但它自带滑动窗口的效果，允许你让相邻两块咬合一段。

```python
from langchain_text_splitters import CharacterTextSplitter

splitter = CharacterTextSplitter(
    separator="",       # 空字符串：任意位置都能切
    chunk_size=200,     # 每块 200 个字符
    chunk_overlap=40,   # 相邻块重叠 40 个字符
)

chunks = splitter.split_text(text)
```

切完先别急着看内容，把三个数打出来：原文多长、切了几块、每块多大。

```python
print("原始长度:", len(text))
print("块数:", len(chunks))

for i, chunk in enumerate(chunks):
    print(f"第 {i + 1} 块，长度 {len(chunk)}")
    print(chunk)
    print()
```

这里用的是 `split_text` 而不是 `split_documents`，因为手上是一个字符串。要是手上是 Document，就得换成 `split_documents`——同一个切分器，两个方法都在。

两个尺寸怎么定？没有固定答案。真到了公司里，你也是先随便设一个值，跑一版看检索效果，不好就调，再跑，慢慢逼近那个最合适的位置。但有两个经验区间可以先框住你：

> **结论**：`chunk_size` 通常在 200 到 1000 之间，不要超过 1000——切得太大，语义的精准度会急剧下降，一块里塞了三件事，检索命中哪一件都说不清。`chunk_overlap` 取 `chunk_size` 的 10% 到 20%，这里是 200 配 40，正好 20%。

跑一下看结果。原始文本 706 个字符，按 200 切，你会以为切成 4 块，实际切出来是 5 块。为什么多一块？因为重叠。每切一块，起点只往前挪 200 − 40 = 160 个字符，于是起点依次落在 0、160、320、480、640——五刀，五块。最后一块只剩个尾巴，照样单独成块。

第一块 199 个字符，切口落在"……缺乏专业领域知识等"这句话中间。这就是硬切的毛病：它不认句子，只认数。第二块开头会往回咬 40 个字符，把上一块结尾那段再接一遍，这就是 `chunk_overlap` 干的事——好歹让一句话不至于在这一块断了下半截就没人管。

那这种切法行不行？看起来好像还行，其实不太行。因为你会把语句从中间切开，做了重叠也还是切开：一块的结尾是半句话，另一块的开头是这半句话的后半截，语义的完整性始终是断的。

> **易错点**：这种切分只适合对语义完整度要求不高的场景。它会把文档从中间劈开，所以别指望它保住句意。了解即可，不作为首选。

### 递归字符切分：先保结构，长度不够再降级

真正推荐用的是 `RecursiveCharacterTextSplitter`。前缀 `recursive` 就是递归，后半截 `CharacterTextSplitter` 和刚才那个硬切器同名——所以它本质上还是一种按长度切，只是多了一个效果：切分的方式可以递归。

块大小和块间重叠这两个参数，跟固定长度切分一模一样，这里不再赘述。差别全在分隔符上：硬切器只能传一个分隔符，你传个空，它就在任意位置下刀，非常死板；递归切分器可以传一个**多级分隔符列表**。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=40,
    separators=["\n\n", "\n", "。", ""],  # 段落 → 行 → 句号 → 任意位置
)

chunks = splitter.split_text(text)
```

这个列表就是一张"降级顺序表"：先按段落切，段落不行按行，行不行按句号，句号还不行才落到任意位置硬切。

顺序不能随便调。它是优先级，不是备选集合。你要是把最后的 `""` 挪到第一位，等于告诉它"上来就从任意位置切"，这个切分器立刻退化成刚才那个硬切器——多级分隔符全白配了。所以粗的放前面，细的放后面，兜底的放最后。

整个流程是这样走的：

```text
原始文档
   │  用 "\n\n"（段落）切
   ├── 块 A：长度 ≤ chunk_size ──► 直接保留为最终块
   └── 块 B：长度 > chunk_size
          │  降到 "\n"（行）再切
          ├── B1：长度 ≤ chunk_size ──► 保留
          └── B2：长度 > chunk_size
                 │  降到 "。"（句号）再切
                 ├── B2-1：≤ chunk_size ──► 保留
                 └── B2-2：> chunk_size
                        │  降到 ""（任意位置）兜底硬切
                        └── 切到每块都进得了 chunk_size 为止
```

看图就明白它为什么叫递归：每一层切完都要回头检查一遍大小，合格的当场收下，不合格的带着"这块还太大"这个问题，交给下一级分隔符再处理一次。层级越往下，切口越碎，但只有上一级切不动了才往下走——所以它优先保住的是文档的结构，段落能整就整，实在整不了才动句子。

换成这个切分器，代码只有类名和 `separators` 变了，`split_text` 的调用、遍历打印的循环，一行都不用改。这是接口统一带来的好处。

跑出来的效果和硬切明显不同：它按段切，一段一块，块头块尾都是完整段落。整段被留下的那些块，你甚至看不出重叠的痕迹——根本不需要，因为一段本来就没被切断。

真正的考验在中间那一段：它实在太长，眼看就超过 200。这时候它降了一级，按句号断——注意是**句号之前**断开，前半句仍然是完整的一句话，不是从半中间劈开。也就是在这一段上，重叠出现了：下一块的开头会把上一块结尾那句话再带一遍。

两相对照就看出差别了。硬切是"先切了再说，断了的地方靠重叠糊一下"；递归切分是"能不切就不切，非切不可也挑个句子边界切"。前者是补救，后者是预防。

> **结论**：不确定该用哪个切分器的时候，就用递归字符切分。它是最通用的一个。到了公司里面对一堆没见过的文档，先用它跑通，再谈优化。

### 结构感知切分：让 Markdown 标题自己分块

再往上一层，是结构感知切分。思路很直接：不靠自己猜哪里该断，而是利用文档自身的结构来识别边界——Markdown 里的标题、JSON 里的字段、HTML 里的标签，都是现成的边界。

LangChain 为这几种结构都备了切分器：按 Markdown 标题切的 `MarkdownHeaderTextSplitter`，按 JSON 结构递归切的 `RecursiveJsonSplitter`，按 HTML 标签切的，还有基于其他格式的一堆，不一一介绍。

这里面我最推荐 Markdown 的那一个。原因在前一步就埋下了：MinerU 把 PDF 处理完，吐出来的就是 Markdown——它天生带结构，一级标题、二级标题、三级标题摆得清清楚楚。既然结构都在，为什么还要当成一坨纯文本来硬切？

演示用的那份 `评估点.md`，结构非常标准：一级标题"第一章"，下面二级标题"第一节"，再下面三级标题"第一部分""第二部分"……三级标题底下才是正文。第一章讲完，轮到第二章，标题级别又回到一级，重新往下分。这种文档，就该交给结构感知切分。

#### headers_to_split_on：按哪几级标题切

第一个参数是 `headers_to_split_on`，直译就是"用来切割的标题"。它是个列表，列表里装元组，每个元组两部分：

- 第一部分是标题级别。Markdown 里一个 `#` 是一级标题，两个 `##` 是二级，三个 `###` 是三级。你写 `("#", "header1")`，就是告诉它"碰到一级标题就切一刀"。
- 第二部分是给这个级别起的名字，随便起。叫什么，将来就会变成 `metadata` 里的 key。这里叫 `header1`、`header2`、`header3`，只是图个直观。

```python
splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "header1"),
        ("##", "header2"),
        ("###", "header3"),
    ],
    strip_headers=False,
)

chunks = splitter.split_text(md)
```

它的底层其实也是递归：先按一级标题切，切完看这个一级标题底下有没有正文——有，就直接成一个块；没有（下面全是更细的标题），就降到二级再切；二级底下还是没有正文，继续降到三级。所以一份"一级 → 二级 → 三级 → 正文"的文档，真正的切点落在三级标题上，因为只有那一层底下才挂着内容。文档要是有四级标题，往列表里再加一个元组就完了。

#### strip_headers：正文里要不要留标题

第二个参数 `strip_headers`，字面容易读成"是否携带标题"，准确说是**是否去除正文里的标题**。传 `False` 就是不去除，标题会跟着正文一起留在块里；传 `True` 就是去掉，块里只剩正文。

先用 `False` 看效果最直观：打印出来的每一块，正文第一行就是它头顶那个三级标题——因为这块内容紧跟着的就是这个标题，`False` 让它留在原地。改成 `True` 再看，正文里干净了，标题一行不剩，只剩内容。

留还是不留，取决于你后面怎么用。标题留在块里，检索出来的片段自带上下文；去掉标题，块更纯，`metadata` 里反正还存着一份。

#### 接口上的例外：字符串进，Document 出

这里有个坑，而且是这一节最需要记住的一条。

按前面立下的规矩，`split_text` 传字符串、返回字符串列表。可这个切分器打印出来，块的类型是 `Document`。点进类定义看一眼就明白了：它**没有继承** `TextSplitter` 接口。前面那些切分器都继承了，所以规矩成立；这一个没继承，规矩就不适用。

它的 `split_text` 是"字符串进、`List[Document]` 出"，而且它压根没有 `split_documents` 这个方法。前面学的两条规矩，到它这里两条都不作数。

```text
TextSplitter 家族（大多数）
  split_text(str)              ──► List[str]
  split_documents(Documents)   ──► List[Document]

MarkdownHeaderTextSplitter（例外）
  split_text(str)              ──► List[Document]     ← 返回类型变了
  split_documents              ──► 不存在
```

读图记住一句话：别的切分器是"什么进、什么出"，它偏偏是"字符串进、文档对象出"。

拿到 Document 之后，直接 `print` 会很难看。它继承自 Pydantic 的 `BaseModel`，自带 `model_dump()`，把它转成字典再用 `json.dumps` 带上缩进打印，结构就一目了然：

```python
import json

print(json.dumps(chunks[0].model_dump(), indent=2, ensure_ascii=False))
```

打出来是这么个形状：

```text
Document
├── page_content : "第一部分\n国内学记……"        ← 这一块的正文
└── metadata
    ├── header1 : "第一章"
    ├── header2 : "第一节"
    └── header3 : "第一部分"
```

`page_content` 是内容，`metadata` 是元数据。元数据里那三个 key，正是你在 `headers_to_split_on` 里起的名字，值是这一块所属的一级、二级、三级标题。你要是把名字改成 `h1`、`h2`、`h3`，打出来就是 `h1`、`h2`、`h3`——key 由你定，值由文档定。

对着原文核一遍就知道它切得对不对：第一块的正文正好落在"第一部分"底下，第二块的正文正好落在"第二部分"底下，讲的是《学记》的主要思想。切点对，归属也对——它切出来的不是"看着像样"的块，而是每一块都能对回原文的某个小节。

> **易错点**：`metadata` 里的标题不是额外的装饰，它是这一块在原文里的位置坐标。后面做检索、做引用、做溯源，靠的就是这三个字段。

到这里，结构感知切分就讲完了：按哪几级标题切、正文里留不留标题、以及它那个不合群的接口。三条记牢，用起来不会出错。

### 向量模型怎么选：从 0.6B 到 8B

文档加载了，也切好了，知识库构建的前两步走完。第三步是把这些块转成向量，这一步得请向量模型出场。

向量模型非常多，先按体量分成两档看。

小的一档，适合中小企业、也适合你先跑通流程：千问3 的 `Embedding` 0.6B、jina 的 0.5B 级模型、BGE-M3 的 0.56B。这里的 B 是十亿，0.6B 就是 6 亿参数规模。参数规模理论上越大性能越强，但不是绝对——千问3 这个只有 0.6B，下面那些模型有 1B 的、1.5B 的、1.6B 的，可它在 MTEB 榜单上拿到 64.34 分，几乎跟 1.6B 级别的模型相差无几。这就是小模型的价值：体积小、能本地跑、效果还不掉队。而且这些都是开源免费的。

大的一档就夸张了，8B、7B，几十亿参数。评分确实更高：榜单排第一的是一款 8B 模型，千问3 那个大号排第三，70 分。

| 档位 | 代表 | 参数规模 | 特点 |
| :--- | :--- | :--- | :--- |
| 小模型 | 千问3 Embedding | 0.6B（6 亿） | MTEB 64.34，接近 1.6B 级模型，本地可跑 |
| 小模型 | BGE-M3 | 0.56B | 开源免费，适合小规模使用 |
| 大模型 | 8B / 7B 级 | 几十亿 | 评分更高，排第一的是 8B，千问3 大号 70 分排第三 |

到底选哪个？分两种情况。公司有实力、要自己部署，那上面这些开源模型随便挑一款，拉到本地部署就完事。想省事、不想养机器，就用云服务。

LangChain 这边对 Embedding 模型支持四类后端：OpenAI 的模型、阿里云百炼的模型、本地开源的 HuggingFace 模型、以及 Ollama 的模型。前两个是云模型——别人部署好了，你配个 key 直接用；后两个是自己下载自己部署。HuggingFace 就是大家口中的"抱抱脸"，全球最大的模型平台，各种模型都能下载。

我演示两种：阿里云百炼代表云服务，Ollama 代表本地部署。OpenAI 和 HuggingFace 都得翻墙，跳过。

阿里云百炼的模型广场里，筛"向量模型"，表面上好像就列了两三个，点进去才发现一大堆，规模大小、性能各不相同。最新的那一款千问3 系的文本向量模型非常强，还有 100 万免费额度，放心大胆地用。

> **注意**：Ollama 里那个 `qwen3-embedding:0.6b` 不是聊天模型，别在命令行里跟它对话，聊不了。它不是大语言模型，唯一的作用就是把文本转成向量。

### Ollama 向量模型实操：单条查询与批量文档

先走本地这一路。`langchain-ollama` 这个依赖项目里已经装了，不用再安。要用的时候从里面导一个类出来：`OllamaEmbeddings`。

`embedding` 这个词是"嵌入"的意思，但在这一层，它代表的就是向量模型。`OllamaEmbeddings` 就是 Ollama 的向量模型封装。

Ollama 本身只是个本地部署的平台，它不决定具体用哪个模型——模型名要你自己传。我们前面让大家在本地拉过一个 `qwen3-embedding:0.6b`，这里就用它。

```python
from langchain_ollama import OllamaEmbeddings

embeddings = OllamaEmbeddings(
    model="qwen3-embedding:0.6b",
    dimensions=1024,
)
```

第二个参数 `dimensions` 是向量维度：文本转成向量之后，这个向量是几维的。所谓维度，就是生成出来那个数组里有多少个元素。0.6B 这个模型支持 1024 维，所以将来每条文本都会变成 1024 个浮点数。维度越大，语义的精细度越高，内存占用也越大——这个是可以自己控制的。

这里没有配任何 URL。没配 URL，它默认连的就是 `localhost`，也就是本机。所以跑之前，本地的 Ollama 必须先启动起来，否则连不上。

模型拿到手，先测单条。这个对象里有个方法叫 `embed_query`，query 是"查询"——用户提问时，你把问题交给它，它帮你转成向量。传什么内容随你，真实场景里传的就是用户的问题。我这里传一句"我爱上班"。

```python
query_vec = embeddings.embed_query("我爱上班")
print(len(query_vec))  # 1024
```

第一次跑会慢一点，模型要加载。跑完拿到一个 `vector`，长度 1024，里面的数全是浮点数。转成向量时会做归一化，所以值都落在 -1 到 1 之间。

单条能转，批量也能转，方法是 `embed_documents`。document 加了 s，就是很多文档——这正是知识库入库要干的事：文档切成的那些片段，一片一片全转成向量，这是批处理；而用户提问时拿一个问题去转，那是单条处理。

```python
docs = ["我要躺平", "我爱工作", "拒绝加班"]
doc_vecs = embeddings.embed_documents(docs)

print(len(doc_vecs))     # 3
print(len(doc_vecs[0]))  # 1024
```

| 方法 | 入参 | 返回值 | 对应场景 |
| :--- | :--- | :--- | :--- |
| `embed_query` | 一个字符串 | 一维向量，长度 1024 | 用户提问，单条处理 |
| `embed_documents` | 字符串列表 | 二维列表，3 × 1024 | 知识库片段入库，批量处理 |

批量返回的是个二维数组——列表里套列表。外层长度是 3，因为转了三条文档；里层每个元素又是一条长度 1024 的向量列表。第一条装"我要躺平"的向量，第二条装"我爱工作"的，第三条装"拒绝加班"的，顺序跟传进去的列表一一对应。

### 用余弦相似度验一验：向量到底懂不懂语义

向量转出来了，最终要干的事只有一件：拿用户的问题向量，去这一堆文档向量里找出最相关的那个。

比相似度的方法有好几种——余弦相似度、欧式距离、点积，随便挑一种都能算。但你会写吗？我不会。我让 AI 帮我写了一个 `cosine_similarity`，就是一个函数，传进去两个向量，返回它俩的相似度。

$$\cos(\theta)=\frac{\mathbf{a}\cdot\mathbf{b}}{\lVert\mathbf{a}\rVert\,\lVert\mathbf{b}\rVert}$$

这个式子算的是两个向量夹角的余弦：方向越一致，值越接近 1；互相垂直是 0；方向相反就是负的。所以分数越高，语义越近。

拿它把"我爱上班"和三条文档挨个比一遍：

```python
for i, v in enumerate(doc_vecs):
    score = cosine_similarity(query_vec, v)
    print(f"{docs[i]} -> {score:.2f}")
```

输出是：

```text
我要躺平 -> 0.40
我爱工作 -> 0.80
拒绝加班 -> 0.40
```

谁最高？"我爱工作"，0.80。因为它跟"我爱上班"本来就是一个意思，两句话贴得最近。"我要躺平"和"拒绝加班"，一个不想干、一个不肯多干，方向跟"我爱上班"正好相反，分数都掉到 0.40。

这个结果准不准？很准。注意"我要躺平"和"拒绝加班"字面上都带着"班"的影子，可向量给它们的分数并不高——它比的不是字面撞了几个词，是整句话在语义空间里的方向。

> **提示**：0.80 和 0.40 是相似度分数，不是"80% 的概率"。余弦相似度衡量的是方向的一致程度，读的时候按"越接近 1 越像"来理解就够了。

这一步跑通，检索的底子就有了：文档切块、块转向量、问题转向量、算相似度、取最高的那几个。整条链路里，切分决定每一块讲的是不是一件事，向量决定这件事能不能被找出来——两头都稳，检索才稳。

## 向量模型与 VectorStore
> 对应块：BLK31 | 覆盖分集：P118-P123

如果对数据的隐私度要求不高，或者本地机器的性能不行、根本部署不了向量模型，那这时候就可以把向量化这件事交给云端。云端不止阿里云一家，腾讯云、火山云都提供向量模型，这一节先拿阿里云把这条路走通。

### 本地跑不动，就把向量模型搬到云上

阿里云的向量模型有不少版本，`text-embedding-v3`、`v4` 都在其列。注册阿里云就能免费使用 100 万的模型 token，所以这里我们就白嫖一下。

不过这里有个坑，我上次测试的时候发现：阿里云以前是可以直接用 OpenAI 那套接口的，现在用不了了，必须走 `langchain-community` 社区版的 DashScope 封装。而社区版前面已经讲过，官方不再维护了，跑起来会给你弹一条警告。所以这条路现在有点将就——能跑，但别指望它长期稳定。要用它，得先装 `langchain-community` 和 `dashscope` 两个依赖，项目里已经装好了。

代码跟上一节用 Ollama 的那份几乎一模一样，只是开头换了个东西：

```python
from dotenv import load_dotenv
from langchain_community.embeddings import DashScopeEmbeddings

load_dotenv()  # 把 .env 里的 DASHSCOPE_API_KEY 与接口地址读进环境变量

embedding = DashScopeEmbeddings(model="text-embedding-v3")
```

`DashScope` 就是阿里云在 LangChain 社区包里的名字。注意这里只指定了模型名，没有传 `api_key`——因为在 `.env` 里早就配好了 `DASHSCOPE_API_KEY` 和接口地址，构造对象时它会自己去读。本来这类云端模型是要收费的、必须显式给 key，但环境变量一加载，它就自动读到了，你就不用再手动指定。当然，手动传 key 也完全可以，这里走自动方案。

模型换好之后，实验照旧：把「我爱上班」做一次向量化，再把「我爱工作」「我要躺平」「拒绝加班」分别向量化，两两算余弦相似度。结果是这样的：

| 对比对象 | 余弦相似度 |
| :--- | ---: |
| 我爱工作 | 0.82 |
| 我要躺平 | 0.40 |
| 拒绝加班 | 0.41 |

「我爱工作」跟「我爱上班」最接近，「我要躺平」和「拒绝加班」离得最远——这个排序跟本地 Ollama 跑出来的几乎一样，分数也差不多。也就是说，换成 DashScope 这套云端模型同样能干活。

所以这段代码不用记。你唯一要盯住的变化，是初始化那一行：刚才是 `OllamaEmbeddings`，现在是 `DashScopeEmbeddings`，除此以外一个字都没改。真正要掌握的是「怎么把 embedding 模型初始化出来」，至于用哪家、类名叫什么，查一下就行。

### 向量库的两个职责：存与取

到这里，知识库构建的四步已经走完了三步：文档加载、文档切分、文档向量化，就差最后一步——存入向量数据库。

向量数据库干两件事。第一件是存，把向量化之后的文档存进去；第二件是检索，把向量化的文档查出来。一方面它是仓库，另一方面它提供了检索能力。这个分工在 RAG 里刚好对上：离线阶段把切好的文档向量化后往里存，在线阶段用户的问题来了，就去里面检索。

但这个「检索」不是大家想象中的样子——不是拿着一个向量，跟库里的向量一个一个比。刚才我们敢那么比，是因为统共就三个向量：打开开发工具数一数，就三条，比完就完了。可实际开发中，你的文档列表会有多少？成千上万，甚至数以百万。要从几百万条里找出跟问题最接近的那一条，还在 `for` 循环里逐条比较，你觉得这合理吗？肯定不合理。

所以真正的检索在内部要做各种各样的优化，而这些优化全部由向量数据库承担。这也是为什么向量库重要——第一是存，第二是检索，两件事都不轻。

### 先用内存版把 API 学会

LangChain 支持的向量数据库很多。最典型的一个叫 `InMemoryVectorStore`，顾名思义，它就是一个基于内存的向量库：数据放内存里，不需要任何配置，导入之后直接就能用。它的定位很明确——做开发和测试，换句话说，是拿来学习和做实验的。能不能在生产规模里用？不能。

除了它，还有 Chroma，还有 Milvus 等等。这一节我偏偏挑内存版来讲，原因很简单：我们现在就是在学，通过它把 `VectorStore` 的 API 学会、把增删查的用法摸熟；等进了项目，再去部署真实的向量库。所以今天先用一个「假」的内存库，过几天讲真实向量库的时候，你会发现代码几乎不用改。

这些向量库在官方文档里都能找到。Integration（集成）那一栏往下翻，角落里有一个 Vector Store 的入口，点进去就是向量库的集成总览：前面讲基本用法，最后列出 LangChain 支持的全部向量库，数量非常多。

### 一个接口，三个方法

那怎么使用向量库？跟前面一样，LangChain 里所有的向量库都实现了同一个接口，叫 `VectorStore`。这个接口提供同样三个方法：

- `add_documents`：往里存文档；
- `delete`：删文档；
- `similarity_search`：搜索。

存文档调第一个，删文档调第二个，搜索用第三个。你只要知道这三个就够了——将来不管换哪个库，都是这三个方法。所以我们就学这三个，别的先一个都不学。

这里还有一件事必须说清楚：LangChain 里的 `VectorStore` 并不是向量数据库本身，它只是一个接口，定义了上面这三个方法。而且在这个接口内部，它还做了一件事——把向量数据库和 embedding model，也就是向量模型，合并在一起了。

这话什么意思？回想最开始讲 RAG 流程时，离线阶段是四步：加载、切分、向量化、存入。而在 LangChain 里，向量模型和向量数据库被合并成了一个 `VectorStore`，于是我们还需要自己去做向量化吗？不需要了。把切好的片段直接扔给它，它自己转向量、自己存。

```text
入库：
  原始文档 ──加载──▶ Document ──切分──▶ 文档片段
                                          │
                                          ▼
                              vector_store.add_documents(片段)
                                          │
                        ┌─────────────────┴─────────────────┐
                        ▼                                   ▼
                 向量模型（内部持有）                  向量数据库（内部持有）
                 自动把片段转向量                      存向量与原文
```

检索时同理。以前要自己把用户的问题转向量，现在不用了：你把问题扔给 `VectorStore`，它在内部自己转向量、自己检索，然后把结果给你。

```text
检索：
  用户问题
      │
      ▼
  vector_store.similarity_search(问题)
      │
      ├─ 内部：向量模型把问题转向量
      ├─ 内部：向量库按相似度打分排序，取前 k 条
      │
      ▼
  list[Document]
```

所以前面讲向量化时折腾的那一堆 API，其实你需要掌握吗？不需要。只要把向量模型交给 `VectorStore` 就行了。将来我们直接拿着文档来存、拿着问题来搜，中间那层向量化的细节它自己处理。

再重复一遍：`VectorStore` 是一个统一的接口，内部持有了向量模型和向量数据库。调用 `add_documents` 传文档进去，它自动向量化、自动存入；调用 `similarity_search` 传问题进去，它自动向量化、自动检索。我们只要记住增、删、搜这三个方法。

### 准备文档：加载、切分、编号

正式用向量库之前得先准备文档。因为你要往库里存东西，总得先有文档；拿到文档还要切分，切完才能存。所以顺序是：先把文档加载回来，再切好，这叫准备完毕。

代码本身不复杂，新建一个 notebook，第一步就是把 `resources` 目录下的那份 `评估点.md` 读进来，让它进到内存里。

#### 按标题层级切分文档

加载完只是第一步，第二步是切分。这次是 Markdown 文件，该用哪种切法？结构感知。也就是按标题层级切，把一、二、三级标题都交给切分器，让它在标题的边界上把正文断开。

结构感知的切分器有个特点：它只有一个方法 `split_text`，把文本传进去，返回一堆文档片段。要注意返回结果是一个 `list`，里面装的是 `Document` 对象，不是字符串。

```python
from langchain_text_splitters import MarkdownHeaderTextSplitter

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "一级标题"), ("##", "二级标题"), ("###", "三级标题")]
)

chunks = splitter.split_text(text)
print(len(chunks))  # 21
```

跑完得到 21 条文档。到这里，文档就算准备了一半。

#### 给每个片段补上字符串 id

把切出来的文档逐条打印看看：每一篇都有 `metadata` 和 `page_content`，内容都在，但 `id` 一律是 `None`。这样后面演示起来不好看，也不方便指定删除，所以我们给所有片段都赋一个 id。

赋值的办法很直接：用 `enumerate` 遍历，从 1 开始递增。`enumerate` 就是「边遍历边编号」，想要从 1 开始，把 `start` 设成 1 就行，这样 `i` 依次是 1、2、3……但注意，`id` 要求是字符串，它很变态，直接塞数字不行，所以拼一下，写成 `doc_1`、`doc_2` 这种形式。

```python
id_list = []
for i, doc in enumerate(chunks, start=1):
    doc.id = f"doc_{i}"
    id_list.append(doc.id)
```

顺手用一个 `id_list` 把每个 id 收集起来，后面批量删除时正好要用。跑完之后，21 条文档的 id 就从 `doc_1` 一路排到 `doc_21`。

### 初始化：先有向量模型，才有 VectorStore

第二步是准备 `VectorStore`，它又细分成两小步：先初始化向量模型，再初始化 `VectorStore`。

向量模型的初始化代码记不住很正常，把前面 Ollama 那段复制过来就行；本地没有 Ollama 也没关系，换成阿里云那套 DashScope 一样可以，用哪个随意，我不干涉。模型那两行照抄上一节，这里只看 `VectorStore` 这两行：

```python
from langchain_core.vectorstores import InMemoryVectorStore

vector_store = InMemoryVectorStore(embedding)
```

初始化 `VectorStore` 时要把向量模型传进去，而且它是一个位置参数，直接传即可。为什么非要传？因为前面强调过，LangChain 的 `VectorStore` 要把向量模型和向量库绑定在一起，模型必须握在它手里。

注意现在用的是 `InMemoryVectorStore`。将来换成基于 Milvus 的，类名就变成 `MilvusVectorStore`，那时候它自己会去连那个库；而内存版不用连，因为它就在本地。所以这里直接传一个向量模型，对象就建好了。就这么两步：定义模型、定义 `VectorStore`、把模型传进去。

### 加进去，再删掉

文档准备好了，`VectorStore` 也准备好了，接下来就是添加。方法叫什么？`add_documents`，传文档的集合进去。

```python
ids = vector_store.add_documents(chunks)
print(ids)
```

注意这里没有再单独传一个 `ids` 参数。因为前面已经把 id 写进每个 `Document` 里了，文档自带 id，就不用再传一遍。当然传了也不冲突。

运行之后不仅添加成功，它还把 id 给你打印了出来，看到那一串 `doc_1` 到 `doc_21`，就知道是真的加进去了。

那怎么验证添加成功？说实话，现在没法验证——搜索还没学，`similarity_search` 还没用上，我们不知道库里到底有没有。但方法既然返回了 id，这里应该是成功了。

内存版有个特别爽的好处：它内部有个 `store`，从名字就能看出来是「存储」的意思，打开它可以直接看见数据。21 条文档整整齐齐躺在里面，一条不少。这个便利只有内存版有，真实的向量库得靠检索来验证。

删除同样简单，方法叫 `delete`，要传的是 id 列表：

```python
vector_store.delete(id_list)
```

也就是说它支持批量删除——给我一堆 id，我一次全删。刚才准备的 `id_list` 正好派上用场。传进去、执行，再回头看 `store`，数据没了。删掉之后剩 20 条，因为 `doc_1` 已经被干掉了。想恢复的话再 `add_documents` 一次就回来了。

到这儿，添加和删除就都演示完了：`add` 是增，`delete` 是删。

### 相似度检索的四个参数

接下来是检索。`VectorStore` 提供了多个检索方法，比如 `search`、`similarity_search` 等等。最开始介绍的就是 `similarity_search`，也就是相似度搜索，这是用得最多的一个。还有一个 `similarity_search_with_score`，意思是不仅做相似度搜索，还会把相似度的得分一起返回。这两个用法基本一样，讲透一个，另一个自然就会了。

`similarity_search` 有一个核心参数 `query`，这是必填的，代表查询条件，也就是用户提的问题。剩下的都是可选参数，主要有三个：

| 参数 | 是否必填 | 作用 |
| :--- | :--- | :--- |
| `query` | 必填 | 查询条件，用户的问题；它是位置参数，可以不写参数名 |
| `k` | 可选 | 最多返回几条文档，默认 4 |
| `score_threshold` | 可选 | 相似度得分阈值，低于这个值的文档直接丢弃 |
| `filter` | 可选 | 按文档的元数据做筛选 |

`k` 控制返回数量。相似度搜索会给每篇文档按与问题的相似度打分，分数越高排名越靠前，形成一个排序；`k=4` 就是取前四条，剩下的直接放弃。

`score_threshold` 是打分的门槛。既然检索有分数，就可以设一个阈值，低于它的文档不返回，这样能把相关度过低的片段直接挡在外面。

`filter` 则是对文档的元数据做筛选，属于另一条过滤通道，不是按向量分数，而是按 metadata 里的字段来。

这四个参数里，唯一必选的就是 `query`。

### 一次排名靠后的检索，问题出在切分上

就在这个已经装好 20 条数据的 `VectorStore` 上直接测。输入几个字母，编辑器就会把 `similarity_search` 的签名提示弹出来：第一个是 `query`，第二个是 `k`。`query` 是位置参数，可以不写参数名直接给值，写了名字也没问题。

问什么好呢？这份文档里有很多中外教育家的思想，其中一位是孔子，孔子写了《论语》，《论语》里有教育的作用、教育的对象、教育的目的。那就拿它来试：

```python
vector_store.similarity_search("论语中教育的目的是什么", k=4)
```

返回的是个列表，里面是四篇 `Document`。但你仔细看排名，孔子那一篇并没有排在前面——排在前面的反而是孟子、荀子的段落。

为什么会这样？两个原因。

第一，语义上确实接近。「教育的原则」「启发诱导」这些内容和「教育的目的」在向量空间里离得不远，别的段落自然也能拿到不错的分数，一挤就把目标那篇挤下去了。

第二，也是更隐蔽的一条：前面切分文档时，我们把标题去掉了。那篇的标题是「论孔子及论语的主要思想」，被剥掉之后，正文里只剩下「教育的作用、教育的目的」这类内容，通篇再也找不到「论语」两个字。检索的时候，向量模型凭什么判断这段话一定跟《论语》有关？判断不了。排名自然又被拉低一截。

> **易错点**：`MarkdownHeaderTextSplitter` 默认会把标题从正文里剥掉（`strip_headers=True`）。标题里恰好带着关键实体（人名、书名、章节主题）时，这个默认行为会直接削弱这一段的检索命中率。

这就引出一个问题：切分的时候，标题到底要不要去？答案得结合实际需求。就当前这份语料而言，不能去——因为每一篇的标题都是有含义的，它告诉你这段内容是谁说的、讲的是哪一家。标题一去，正文就变成一段「无主」的话，谁知道这是孔子说的还是别人说的？

要保留标题，就把 `strip_headers` 改成 `False`：

```python
splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "一级标题"), ("##", "二级标题"), ("###", "三级标题")],
    strip_headers=False,
)

chunks = splitter.split_text(text)
```

改完不能只重切就完事，整条链路要重新跑一遍：重新切分文档、重新给文档加 id、重新创建向量库、重新往里添加。因为旧的库里存的还是剥掉标题的那批片段，不重建就白改。

重建之后再打开看，正文里已经带上标题了。再搜一次同样的问题：

```python
vector_store.similarity_search("论语中教育的目的是什么", k=4)
```

这次排第一的是 `doc_3`，就是「孔子及论语的主要思想」那一篇。

> **结论**：检索效果不只由向量库和向量模型决定，切分策略同样决定检索效果。切分方式一变，同一句话、同一个库、同一个模型，排名就能翻过来。

这个思想要记住。很多人调不好 RAG，第一反应是换向量模型、换向量库，其实问题常常出在最前面的切分上。

`k` 的作用这时也看得很清楚：默认返回 4 篇，把 `k` 改成 2，就只剩 `doc_3` 和 `doc_4` 两篇，其余的都不返回。`k` 控制的就是返回文档的数量。

### 带得分的检索：返回结构变了

想看分数，就得换成 `similarity_search_with_score`。参数一个不变，还是 `query` 和 `k`，唯一的变化是函数名多了 `_with_score`，以及返回结果的结构。

先看清楚普通检索返回什么：一个 `list`，里面装的是 `Document`。所以直接遍历，拿到的就是一篇篇文档。

带得分的检索返回的还是一个 `list`，但里面装的不是 `Document` 了，而是元组——圆括号那一对。元组的第一部分是 `Document`，第二部分是得分，得分是个 `float` 浮点数。

| 方法 | 返回类型 | 元素结构 |
| :--- | :--- | :--- |
| `similarity_search` | `list` | `Document` |
| `similarity_search_with_score` | `list` | `(Document, float)` 元组 |

处理这种结果就用解构，一次把两部分取出来：

```python
results = vector_store.similarity_search_with_score("论语中教育的目的是什么", k=2)

for doc, score in results:
    print(f"--- {doc.id} 得分：{score}")
    print(doc.page_content)
```

遍历出来的每个元素是元组，`doc` 接第一个元素，`score` 接第二个元素：前者是文档，后者是分数，然后分别打印。

跑出来的结果：`doc_3` 得分 0.72，`doc_4` 得分 0.64，每一条的 metadata、id、正文都跟着一起出来了。参数上跟普通检索没有任何区别，差别只在函数名和返回结构——记住这一点，两种检索就都通了。

## 把检索接进对话：RAG 检索模式与 Milvus 基础
> 对应块：BLK32 | 覆盖分集：P124-P128 | 块标题（分集名）：《RAG 检索模式与 Milvus 基础》

### 离线阶段结束，在线阶段只剩三件事

经过上一阶段的学习，离线阶段已经全部完成：文档加载、文档切分、文档向量化、文档存储——知识库构建这一整套流程，一件不落地全都实现了。那接下来该做哪个阶段？在线阶段。

在线阶段要做的事，说到底就是一句话：用户来提问，我们把问题转向量，拿着问题向量去检索知识片段，再把检索到的片段组织成提示词发给模型。

如果只是照着这个流程做，其实谁都会做——因为“拿问题去检索文档”这件事，上一阶段已经讲过了。`similarity_search` 这个方法，你只要传一个问题进去，它就自动返回文档，等于把“问题向量化”和“向量检索”两步合二为一了。所以在线阶段真正要写的只剩最后一环：把检索到的片段与提示词合并，合并完发给模型。

整个流程因此简化成这样：

```text
用户提问
  ↓
知识检索：similarity_search（问题向量化 + 向量查询，一步完成）
  ↓
把检索到的知识片段与用户问题拼成提示词
  ↓
调用模型，生成答案
```

读这张图只需要记住一件事：跟以前“用户提问 → 组织提示词 → 调模型”的老流程相比，RAG 只是在中间插了一个知识检索的步骤。以前是直接回答，现在是先查资料再回答。

> **结论**：RAG 对话，就是在每次调用模型之前多了一步知识检索；前面那两步（向量化 + 检索）已经被一个方法包掉了，剩下要自己动手的只有“拼接提示词”和“调模型”。

### 把在线流程手动跑一遍

流程清楚了，先不封装、不抽象，带大家手动走一遍。因为还要用向量库，就干脆还在原来那个文件里写。

四步：写用户提问、根据问题检索知识片段、拼接提示词、调模型。

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()

# 第一步：用户提问
query = "论语中教育的目的是什么"

# 第二步：根据问题检索知识片段
documents = vector_store.similarity_search(query)

# 第三步：把知识片段与问题拼接成提示词
context = "\n".join([doc.page_content for doc in documents])

prompt = f"""你是一个教资考试的专家，你需要根据提供的上下文来回答用户的问题，不能自己编造答案，答案要简短，直接引用原文。

上下文：{context}

用户问题：{query}"""

# 第四步：调用模型生成答案
model = init_chat_model(
    model="deepseek-v4-flash",
    extra_body={"thinking": {"type": "disabled"}},
)
response = model.invoke(prompt)
print(response.content)
```

第二步拿到的 `documents` 是一个列表，列表里装着一个个 `Document` 对象。这些对象里我们真正关心的只有 `page_content`，因为要发给 AI 的就是正文内容。

所以第三步分两小步来做。第一小步，用推导式把这个 `Document` 列表变成字符串列表：

```python
[doc.page_content for doc in documents]
```

`for doc in documents` 一次取出一个文档，`doc.page_content` 取出它的正文，外面套上方括号，得到的就是一个纯字符串的列表——原来装的是文档对象，现在装的是每篇文档的内容。

第二小步，把字符串列表拼成一个字符串。拼接有个很省事的写法，就是 `join`。举个最小的例子：`"*".join(["Rose", "Lucy"])`，返回的是 `"Rose*Lucy"`——`join` 的意思是“加入”，它把分隔符插进列表每两个相邻元素之间，返回值是一个字符串。这里分隔符换成 `"
"`，多个文档就用换行的形式拼在一起，得到的这个变量就叫 `context`，也就是上下文。

上下文有了，接下来写提示词。提示词是有固定写法的：

```text
你是一个教资考试的专家，你需要根据提供的上下文来回答用户的问题，
不能自己编造答案，答案要简短，直接引用原文。
```

这几句是在要求 AI 怎么回答：根据上下文回答，不能自己编，答案要简短，并且直接引用原文。约束说完，再把上下文告诉他，把用户提问告诉他，提示词就成了。如果你想让 AI 分得更清楚，可以给上下文和问题各加一对引号把它们引起来，以防两者相互干扰——不过这个不是必须的。

最后一步调模型。模型用 `init_chat_model` 初始化，里面传模型名 `deepseek-v4-flash`。API Key 不用手写死在代码里，`load_dotenv()` 把环境变量加载进来就够了。再指定一个参数让它不要思考：

```python
extra_body={"thinking": {"type": "disabled"}}
```

模型有了，调用就是 `invoke`，直接把提示词传进去——最简单的传法是传字符串，复杂一点可以传消息列表，这里传字符串就行。调用时不用 `stream`，就走同步阻塞的方式。拿到结果后打印 `response.content`，`content` 是原始文本，`text` 是纯文本，这里看原始文本。

跑一下，AI 的回答是：根据原文，论语中教育的目的是以完善人格为教育目的，培养君子。这个答案百分之百正确。

> **提示**：有了这样一个模型，再有教资问题不会，直接提问就能拿到标准答案。这就是把检索接进对话之后的威力——它不再是凭记忆瞎答，而是拿着召回的知识回答。

回过头对照一遍代码和流程图：用户一上来先提问；紧接着是知识检索，`similarity_search` 内置了问题的向量化和查询，我们不用管；然后是组织提示词，把检索回来的文档里的 `page_content` 提取出来，用 `join` 拼成上下文，再把上下文和用户的问题一起塞进提示词，要求它根据上下文回答、不能自己编造；最后一步调用模型，把提示词传进去就得到答案。流程完全符合。

### 2 Step 模式：把固定流程封成函数

上面这套流程跑通了，但它有个前提没被检验：是不是每次回答用户的问题，都得做一次知识检索？

想想看，用户问的问题跟知识库有关，那当然应该检索；可如果用户只是打个招呼、问一句“你好”，还有必要去知识库里翻一遍吗？没有必要。所以一个 RAG 系统并不是每次都要按完整流程走——简单问题直接回答，复杂问题才走检索。可我们刚写的代码做不到这件事：流程被写死了，进来就检索。

这就不得不聊到 RAG 系统设计时的几种架构模式了。一共三种：2 Step 模式（两步模式）、Agentic RAG（智能模式）、混合模式。我们刚才实现的，就是最朴素的 2 Step 模式。

它极其简单：严格遵循 RAG 流程，每次用户来了都去做一次检索，检索完了拼接，拼完了调模型，先检索再生成，一步不落。正因为流程固定，它天然可以封装成一个函数——固定的流程封成函数，以后谁要提问，把问题传进来就行。

```python
def rag_chat(query: str):
    """固定两步：先检索，再生成"""
    # 第一步：根据用户提问检索知识片段
    documents = vector_store.similarity_search(query)

    # 第二步：把片段拼成上下文
    context = "\n".join([doc.page_content for doc in documents])
    print("用户提问：", query)
    print("检索文档：", context)

    # 第三步：组织提示词
    prompt = f"""你是一个教资考试的专家，你需要根据提供的上下文来回答用户的问题，不能自己编造答案，答案要简短，直接引用原文。

上下文：{context}

用户问题：{query}"""

    # 第四步：调用模型生成答案
    response = model.invoke(prompt)
    print("AI回答：", response.content)
    return response.content
```

函数体里就是那条老链路：用户提问进来，先检索知识片段，再把片段拼进提示词，最后调用模型生成答案。有一处要注意——模型初始化别放进函数里。放函数外面，初始化一次，后面一直能用；塞进函数里，每调一次就重新建一个模型对象，纯属浪费。

为了看清楚每一步到底发生了什么，函数里加了三处打印：进来先打印用户提问，拿到上下文后打印检索到的文档，拿到答案后打印 AI 的回答。

调一下：

```python
rag_chat("论语中教育的目的是什么")
```

输出顺序一目了然：先“用户提问”，再“检索文档”（检索回来好几篇），最后“AI 回答”。这条链路就被固定成两步走了——请求来了先检索片段、拼接提示词，然后调模型。

那么问题来了：流程既然写死了，用户问一句“你好”会怎么样？

```python
rag_chat("你好")
```

它照样去检索文档了。只是打个招呼，却把整个知识库翻了一遍，这不是浪费是什么。

> **结论**：2 Step 模式极其简单，把架构写死了——用户提问先检索文档，再组织提示词，固定的两步。用户问的是知识库相关的问题还好，一旦问的是简单问题，检索纯属浪费。它更适合专用的问答机器人：这个机器人别的啥都不干，只回答跟知识库有关的问题。这种场景用 2 Step 又简单又够用。

可需求一旦复杂起来——我们希望动态地选择要不要调工具、要不要检索——这种模式就不行了。

### Agentic RAG：把检索做成工具交给模型决定

那就看第二种模式：Agentic RAG，也就是智能化的 RAG。这一次不再是简单的两步走，而是把 RAG 做成一个 agent，让它自主决定何时检索、检索什么、要不要检索。

思路一句话就能说完：把检索的逻辑封装成一个工具（tool）。在 agent 里，模型自己会思考要不要调用工具，工具就摆在那儿，要不要做 RAG 由它自己判断。

用户提问进来之后，我们先把问题交给模型，由模型自己判断是否需要检索文档——因为我们给它提供了一个专门做检索的工具。它觉得需要，就去调用；用户问的复杂、跟知识库有关，它就调；用户问的简单，它就不调，直接生成答案。检索完了，片段回传给模型，模型还要再判断一次：这些片段能不能回答用户的问题？回答不了，它就再检索一次。

```text
用户提问
  ↓
模型判断：这个问题要不要检索？
  ├─ 不需要 → 直接生成答案
  └─ 需要 → 调用工具 retrieve_docs
                ↓
          similarity_search 检索知识片段 + 拼接上下文
                ↓
          工具结果回传给模型
                ↓
          模型判断：这些片段够不够回答？
                ├─ 够 → 生成答案
                └─ 不够 → 换个查询词，再检索一次
```

读这张图抓住两点：一是“要不要检索”这个判断从代码里挪到了模型脑子里；二是检索不是一次性的，模型可以反复查，直到它认为材料够了为止。所以它不仅能跳过简单问题，对复杂问题还能多次检索，从而找到最佳答案。

具体怎么做？在原来的文件基础上复制一份出来，叫 `rag_agent`。前面啥都不改：文档准备好、扔进 vector store，相当于准备好了一个向量库。

接下来按定义 agent 的老流程走：加载环境变量、初始化模型、定义工具，这个演示不需要记忆，最后直接定义 agent 并绑定模型和工具。

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain_core.tools import tool

load_dotenv()

model = init_chat_model(
    model="deepseek-v4-flash",
    extra_body={"thinking": {"type": "disabled"}},
)

@tool
def retrieve_docs(query: str) -> str:
    """检索知识库，获取与用户提问相关的知识片段"""
    documents = vector_store.similarity_search(query)
    context = "\n".join([doc.page_content for doc in documents])
    print("检索文档：", context)
    return context

agent = create_agent(
    model=model,
    tools=[retrieve_docs],
    system_prompt="""你是一个教资考试的专家，你需要调用工具来检索文档，根据文档来回答用户的问题，不能自己编造答案，答案要简短，直接引用原文。
回答与教资相关的问题时，必须调用工具检索文档，然后根据文档回答问题。""",
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "论语中教育的目的是什么"}]
})
print(result["messages"][-1].content)
```

工具这一段有三个要点。第一，函数上面要加 `@tool` 装饰器，不加它，这就只是个普通函数，模型看不见。第二，工具内部的逻辑跟前面那个函数是同一套，但**不包含模型调用**——它只做两件事：拿到用户的问题，做知识检索，把检索到的片段拼成一个上下文，然后 `return` 回去。连提示词都不用在这里拼。

为什么要 `return`？因为工具的执行结果会直接交给模型，不是交给用户。上下文一发回去，模型自己会组织语言回答。

第三，必须有文档注释（docstring）。这不是可有可无的装饰，模型就是靠这句“检索知识库，获取与用户提问相关的知识片段”来判断这个工具是干什么的、该不该调。少了它，模型根本不知道手里这个工具能干啥。

然后是 `create_agent`，里面传模型和工具——工具就是上面那个 `retrieve_docs`。

不过光有工具，agent 还不知道自己该干什么。得给它一段系统提示词。提示词可以直接沿用刚才那套说法，只改一处：刚才说“根据提供的上下文回答”，可这里根本没有现成的上下文，所以改成让模型调用工具去检索文档，根据文档来回答，不能自己编造，答案要简短，直接引用原文。

再加一条限制，把条件说死：回答与教资相关的问题时，必须调用工具检索文档，然后根据文档回答问题。这样一来，只有回答教资问题时才检索，其他情况一概不检索。

agent 有了，下一步就是调用它。这里必须记牢一句：agent 的调用传的是字典，返回的也是字典。传进去的字典键叫 `messages`，值是一个消息列表，列表里放一条条消息，比如一条 human 消息；返回的字典同样带 `messages`，取最后一条，就是模型的最终回答。这么基础的东西可不能再忘了。

跑起来验证一下。中间打印出了“检索文档”，说明工具确实被调用了，最后给出答案。答案对不对？对的，还是那句“以完善人格为教育目的，培养君子”。

有意思的地方在检索文档那一行：我问的是“论语中教育的目的是什么”，可打印出来的 query 变成了“论语教育目的”。这是怎么回事？

因为我传进去的那句话只是一条 user message，真正调工具的不是我，是模型。模型在调工具的时候自己决定传什么 query 进去——它发现我问的这句话里口语化的东西太多，就只提取了关键词：“论语”和“教育的目的”。这专不专业？太专业了。

这个技术叫**查询重写**（query rewrite）。它把人类口语化的问题改写成更专业的词汇再去查，召回的可能性比拿原句去查要高得多。以前这是一个要单独写代码去做的专业环节，而在 agent 模式下，它自动就实现了。

> **提示**：查询重写不是我们写出来的逻辑，是模型在调用工具前自己完成的。这也是 Agentic RAG 比 2 Step 更聪明的地方之一——检索词的质量不取决于用户怎么问。

再试一个反例：“你好”。看中间有没有检索的打印？没有。它直接回答“你好，我是教资助手”。这就是智能模式：发现不需要查库，就直接输出。

Agentic RAG 到这里就实现了。简单来说，就是把 RAG 里检索文档的逻辑封装成一个工具，由 agent 自己决定什么时候调、是否需要调。整个代码结构跟之前的 agent 调用没有任何区别——加载环境变量、初始化模型、定义工具、定义 agent；唯一的区别是，这个工具本身做的是 RAG 的知识库检索。

再说说它的代价。好处很明显：动态地让模型思考要不要 RAG，不需要的时候不调，需要的时候再调，提高了 RAG 的利用率，也提高了整体的智能程度。缺点是会有多次模型调用——问题先扔给模型，让它判断要不要调工具（这已经是一次调用了）；模型判断需要，接着调工具；工具返回结果给模型，模型还要再思考这个结果能不能回答问题；不能回答，还要再检索一次。所以哪怕是最简单的问题，也要过一次模型生成；稍微复杂一点、需要 RAG 的，调用次数就上去了。

| 对比项 | 2 Step 模式 | Agentic RAG |
| :--- | :--- | :--- |
| 流程 | 写死：先检索，再生成 | 模型自主决定要不要检索 |
| 简单问题 | 照样检索，纯属浪费 | 直接回答，不检索 |
| 复杂问题 | 只检索一次 | 可多次检索、自己换查询词 |
| 模型调用次数 | 一次 | 多次 |
| 适用场景 | 专用问答机器人 | 需要动态判断的通用助手 |

所以并不是说 Agentic RAG 就是万能的。但如果你需要的是更智能的 RAG，推荐用这种方式。

RAG 的三种架构说完了，接下来换个话题：Milvus。

先从这个单词说起。这个词拿去字典里搜，是搜不到的——前缀像 `mil`，后半截像 `vers`，合起来才是 Milvus。这个单词一定要会读，不然别人问你用的什么库，你念都念不出来，那就有点尴尬了。

它由 Zilliz 这家公司开发。这家公司的名字同样是字典里查不到的新词。这家公司很特殊：开源的所有项目都以鸟命名，象征着自由、远见，还有技术的敏捷演进。Milvus 就是鹰科鸢属的一种猛禽，飞行速度极快，视力敏锐，还有非凡的适应能力。

名字翻过来就是产品特点：快，适应能力强，检索能力也强。

Milvus 提供了三种部署方式。

| 部署方式 | 形态 | 适合的场景 |

最轻的是 Milvus Lite。它有点像本地模拟库，跟 in-memory 的 vector store 类似——但它不是 memory 的，是基于本地文件来存的。拿它做开发、做测试非常舒服，尤其是在 Jupyter Notebook 里试。可惜它只能在 Linux 系统上运行，我们这里是 Windows，所以没办法演示它。

第二种是 Milvus Standalone，单服务器部署。简单说就是把 Milvus 以及它依赖的所有东西打包到一个 Docker 镜像或多个镜像里，然后一键部署。这是我们在学习阶段要用的方式。

第三种是 Milvus Distributed，分布式部署，把 Milvus 部署在 K8s 集群上。集群数量可以任意动态扩展，几十台甚至上百台，能够为数以十亿量级的检索提供支持。也就是说，文档数量达到几百万、几千万甚至亿级都没有关系，它都能实现快速搜索。到了公司里，要么用 Standalone，要么用 K8s 集群部署——后者是运维的活儿，我们做个了解就行。

### 一个向量库里到底存了什么

Milvus 是向量数据库——前面一直在强调这个词。它的主要作用就是存储向量、检索向量。

当然，真正存的时候不可能只存一个向量。我们要把知识片段以及片段对应的向量一起存进去；检索的时候根据向量去查，查回来的才是知识片段。

> **定义**：向量库存的是“向量 + 它对应的原始数据”，查询时拿向量去比，返回的是这段向量背后的原始内容。

既然它是数据库，那就绕不开一个类比：MySQL 也是数据库，两者都是用来存东西的，概念上有很多相似之处。

MySQL 里有 database，database 里有表，表里有列（字段），表里有行。Milvus 里的对应关系是：表叫 `collection`（集合），列叫 `field`（字段），行叫 `entity`（实体，复数是 entities）。

一张 collection 长什么样？它跟我们熟悉的表几乎一模一样：

```text
collection: article
+----+--------------+----------------------+----------------+
| id | title        | title_vector         | link           |
+----+--------------+----------------------+----------------+
| 1  | doc_001      | [0.012, -0.330, ...] | https://...    |
| 2  | doc_002      | [0.087,  0.120, ...] | https://...    |
+----+--------------+----------------------+----------------+
  ^    ^              ^                      ^
每一列是一个 field，每一行是一个 entity
```

这张图里，`id`、`title`、`title_vector`、`link` 这些就是 `field`，对应数据库表里一个一个的列；横着看是一行一行的数据，在 Milvus 里一行就叫一个 `entity`。整张 collection 一共八个字段，这里只画出了其中四个：`title` 存的是标题，`title_vector` 存的是标题对应的向量——`vector` 这个词就是向量的意思。所以原始数据和它对应的向量，在这里都有。

如果事先不说是 Milvus，你看着它就像一张 MySQL 表，结构非常相似。

### schema：没有 SQL，就用代码约束字段

表里的字段不是随便塞的，得有约束。MySQL 建表时写的那段语句，本质上就是对表的约束：这张表必须有这几个字段，字段名固定、作用固定。比如一张五个字段的表，`id` 必须写成 `bigint`，`title` 必须写成 `varchar(200)`——一旦有了这种约束，将来往表里插数据，就必须符合这些条件。

Milvus 的 collection 同样需要这套约束，这个概念叫 `schema`。

> **定义**：`schema` 直译是“纲要、图解”，在计算机里就叫“模式”——它约束的是结构：约束 collection 里每个字段的信息。MySQL 里表的建表语句起到的也是这个作用，所以表的 DDL 也可以称为 schema。

schema 约束哪些东西？常见的有这么几项：

| 属性 | 约束什么 | 什么时候需要 |
| :--- | :--- | :--- |
| `field_name` | 字段的名字 | 通用 |
| `data_type` | 字段的数据类型 | 通用 |
| `description` | 对字段的说明 | 通用 |
| `is_primary` | 当前字段是否为主键 | 主键字段 |
| `auto_id` | 主键是否自动生成 | 主键字段 |
| `max_length` | 字符串的最大长度 | 字符串类型 |
| `dim` | 向量的维度 | 向量类型 |
| `element_type` | 数组元素的类型 | 数组类型 |
| `max_capacity` | 数组的最大容量 | 数组类型 |

这里可能有人会犯嘀咕：以前学 MySQL，约束字段名不就直接写个名字吗？约束数据类型不就在后面写个 `bigint` 吗？对，因为 MySQL 用的是 SQL 语句，语法是约定好的：先写字段名，再写数据类型，有长度再约定长度，再约定是否为空、是否为主键——顺序固定，所以一行就够了。

但 Milvus 没有类似 SQL 的语法。它约束字段的方式是写代码，是面向对象的：每个字段就是一个对象，约束就是这个对象的属性。

```python
# 伪代码：Milvus 里约束一个字段，是造一个对象、给属性赋值
field = Field(
    field_name="title",
    data_type="VARCHAR",
    description="文章标题",
    max_length=200,
)
```

上面这张表里的属性，不是每个都必须写：前三个是通用的；`is_primary` 和 `auto_id` 是跟主键配套的，不是主键就不用加；`max_length` 是给字符串用的，数字类型不需要；`dim` 是给向量用的，不是向量就不用加；`element_type` 和 `max_capacity` 是给数组用的，不是数组也不用加。所以它们是可选的，按字段类型挑着写。

拿一篇文档做例子最直观。一篇文章当然可以存进向量库——文档、文章都算知识，都能加进去。存的时候：

- 标题，纯文本，对应 `VARCHAR` 类型；
- 作者信息，字段多，用一个 JSON 结构来装；
- 图片地址，纯文本；
- 内容，纯文本，但它必须再生成一份对应的向量。

内容为什么一定要生成向量？因为检索就是按内容检索的。将来会把内容交给一个模型，让模型把它转成向量；原文要存进库里，模型算出来的向量也要存进库里，两份都留着。

这篇文档的字段定义里还能看到 Milvus 常见的数据类型：整型、`VARCHAR`、JSON、`int32`、`float vector`（向量类型）等等。这些类型现在不用急着记，等实际用到了再细说。

到这里，Milvus 里这几个概念就能对上了：

| MySQL | Milvus | 说明 |
| :--- | :--- | :--- |
| 表 table | `collection` | 装数据的集合 |
| 列 / 字段 column | `field` | 一条数据里的某一项 |
| 行 row | `entity` | 一条完整的数据 |
| 表结构约束 | `schema` | 约束字段名、类型、长度等 |

一句话收口：Milvus 的 `collection` 就是表，`field` 就是列，`entity` 就是行，`schema` 就是对字段的约束、对应表的结构约束。概念对齐之后，再看 Milvus 的 API 就不会被这些名词绊住了。

## Milvus 的索引类型与 Collection 建表
> 对应块：BLK33 | 覆盖分集：P129-P131 | 块标题（分集名）：《Milvus 索引类型与 Collection 管理》

### 索引：从 MySQL 的主键说起

刚才我们把 Milvus 里的一些基本概念过了一遍，还有一个非常关键的东西得单独拎出来讲——索引。

索引听说过吧？它的作用是什么？提高数据的检索速度。这个不用我多说，MySQL 里天天见：主键一定带索引，InnoDB 的主键索引就是聚簇索引，`id` 上必然有索引；除了主键，其他字段也可以加。你去建索引的时候会发现，索引本身还分好几种：

- 主键索引：`primary key` 建出来就是它；
- 唯一索引：值不允许重复；
- 全文索引：给大段文本做检索；
- 空间索引：给地理位置这类数据用。

很多人以前没注意过索引还分类型，这很正常，等学到 MySQL 高级部分自然会展开。现在心里先有一个概念就够了：**字段可以加索引，加了索引查询就快；索引不是只有一种，类型可以有很多种。**

Milvus 是同一个道理。它为了提高查询效率，也可以给字段加索引，类型同样很多。从大类上分，常见的是三类：

| 索引大类 | 加在什么上 | 一句话说明 |
| :--- | :--- | :--- |
| 稠密向量索引 | 稠密向量字段 | 加速语义检索 |
| 稀疏向量索引 | 稀疏向量字段 | 加速关键词检索 |
| 标量字段索引 | 普通字段（向量以外的一切） | 思路跟 MySQL 索引几乎一样 |

第三类尤其好理解：标量字段的索引，你可以直接当成 MySQL 里的索引来看，底层可以用倒排索引、Bitmap 等等方式实现。至于前两类为什么要分开，得先把"什么是稠密、什么是稀疏"讲清楚。

### 标量字段：向量字段以外的一切

什么样的字段算普通字段？定义简单得有点粗暴：**除了向量字段以外的，全都叫普通字段，也叫标量字段。**

这个逻辑要立住，后面所有字段的划分都靠它。拿一篇文章举例：它有标题、有作者信息、有图片（链接）、有正文内容——这些在没转向量之前，全都是普通字段吧？可一旦我们把正文内容用模型转成向量，那个向量字段就不再是普通字段了，它变成了向量字段。

再换一个更贴近项目的例子。一条保险产品的 JSON 文档，里面是三个字段：

| 字段 | 含义 | 属于哪一类 |
| :--- | :--- | :--- |
| `product_name` | 产品名称 | 标量字段 |
| `category` | 产品类型 | 标量字段 |
| `content` | 保险条款内容（其中一个切片） | 标量字段 |

这三个字段全是标量字段。产品和分类将来不需要做向量检索，因为真正要检索的是条款内容：用户问"等待期"怎么算，命中的是写着等待期的那段条款。所以只有 `content` 需要转向量，而且是转两种——稠密向量和稀疏向量。

```text
切片（3 个标量字段）
  product_name   产品名称
  category       产品类型
  content        条款内容
        │
        │  由 content 生成两种向量
        ▼
入库记录（5 个字段）
  product_name   标量字段  ← 将来可做条件过滤
  category       标量字段  ← 将来可做条件过滤
  content        标量字段  ← 检索出来后交给模型
  dense_vector   稠密向量  ← 用于语义检索
  sparse_vector  稀疏向量  ← 用于关键词检索
```

读图说明：一条切片看起来只有三个字段，真正存进向量库时会膨胀成五个——原有的三个标量字段一个不少，`content` 再额外派生出稠密、稀疏两个向量字段。前两个标量字段将来可能用来做条件过滤，`content` 主要是搜出来之后喂给模型看的，两个向量字段才是拿来检索的。

这个过程不难，难的是两个词：什么是稠密，什么是稀疏。

### 稠密向量：1024 个位置全都填满

其实稠密向量你们已经用过了。Day07 学 RAG 的时候，我们用 Ollama 的 embedding，或者阿里云的 embedding（千问3 text embedding）把文本转成向量，转出来的那些全都是稠密向量。

它的作用是什么？基于向量之间的距离或者相似度，做**语义检索**。

> **定义**：基于向量相似度来实现语义检索的向量，就叫稠密向量。

为什么叫"稠密"？因为它是真的稠。文本转成向量之后是一个数组，昨天我们生成的都是 1024 个元素，数组长度 1024，里面装 1024 个浮点数。你找一个空着的位置给我看看——没有，每个位置都有值。

这里容易说岔一句：判断稠不稠，看的不是数组有多长，而是**有值的元素占比有多高**。1024 个位置全都有值，这就叫稠密，直白得很；如果大部分位置是空的，只有少数位置有值，那它就成了稀疏向量。名字就是这么来的，没有什么玄机。

### 稀疏向量：语义检索够不着的地方

那问题来了：语义检索都有了，不就够了吗？我们想做的不就是语义检索吗，为什么还要整一个稀疏向量？

因为语义检索在大多数情况下都好用，但在少数情况下不好用。

先看好用的一面。用户问"什么情况下保险不能赔"，这实际上是在问免赔条款、免责声明。原始文档里写的是"遇到以下情形之一，不予理赔"——字面上跟用户的问题不怎么相干，但语义上是近的，稠密向量能把这段捞出来。这就是语义检索的强项。

再看不好用的一面：用户问的是一个很精准的专业名词。有些专业名词是失之毫厘、差之千里的。医疗里的药名、病名，差一个字，意思完全不一样。如果用户说的是某一个病，我们拿这个病名去做语义检索，很可能搜回来一个"意思相近"的病——可这两个病在医学上根本不是一回事。这时候语义越"聪明"，错得越离谱。

所以光靠语义检索不够。稠密向量适合语义检索，稀疏向量适合**关键词检索**。

关键词检索是什么？你在百度搜"Python基础教程"，返回的文档里一定包含"Python""基础""教程"这些字样——你得有这个词，我才返回你；没有这个词，我就不返回。这就是拿着词做精确匹配。病名、保单编号这类东西，本来就该精确匹配，一个字都不能差。

| 对比项 | 稠密向量 | 稀疏向量 |
| :--- | :--- | :--- |
| 检索方式 | 语义检索 | 关键词检索 |
| 匹配依据 | 向量距离／相似度 | 词有没有命中、命中多少 |
| 强项 | 换个说法也能找到 | 专有名词、编号一字不差 |
| 弱项 | 一字之差的专业词容易串 | 换个说法就搜不到 |

那关键词检索为什么会被叫成"稀疏向量检索"？别急，把稀疏向量怎么来的讲一遍就通了。

### 稀疏向量是怎么被数出来的

关键词检索的思路是这样：先有一份人类语言的词表。

词表有两种获得方式，一种是统计获得，一种是模型训练获得。先说统计。

假设我们手上有 1000 万份知识片段，把所有片段里出现过的词统计出来，形成一张列表。这张列表有多长？有可能到 10 万甚至 20 万。为什么是这个量级？人类语言里最常用的词汇大概就是这个数量：汉语最常用的也就几千个，再加上英语和其他语种，合起来最常用的十几二十万，差不多。

有了词表就好办了：整一个十几二十万长度的数组，给每个位置编个号——0、1、2、3……一直到 10 万（就按 10 万举例），然后把词一个个放进去，每个位置对应一个独立的词。这张表就叫词表，**每个词对应一个索引**。

接下来拿一篇文档。这篇文档是一个知识片段，长度往往很短，之前切分是 200 一切，对吧？200 长度的片段，不可能把 10 万个词全包含进去。

那就新建一个长度同样是 10 万的数组，逐个看这篇文档里出现了哪些词。比如出现了"被保人"，查词表知道"被保人"的索引是 3，就在数组的第 3 个位置记一个权重值。权重是什么？就是这个词在这篇文档里出现的次数、频率——出现得越多，权重越高。文档里没出现的词，对应位置记 0。

一篇短文只包含几个、十几个、几十个词，所以长度 10 万的数组里，只有十几个或几十个位置有值，剩下几万个位置全是 0。你说它稀不稀疏？这就叫稀疏向量。

```text
全局词表（长度 10 万，每个词一个编号）
  0  ……
  1  ……
  2  ……
  3  被保人
  4  等待期
  5  ……

某篇文档的稀疏向量（长度同样是 10 万）
  0  0
  1  0
  2  0
  3  2.7   ← 文中出现过"被保人"，记权重
  4  0
  5  0
  ……  绝大多数位置都是 0
```

读图说明：上面是全局词表，负责"词 → 编号"；下面是某一篇文档的向量，只在文中出现过的词对应的编号上记权重，其余位置全是 0。

这样一来，关键词检索就成立了。用户问"等待期"，先查词表，"等待期"的索引是 4，然后去每一篇文档的向量里看第 4 个位置有没有值：有值，说明这篇文档里出现过"等待期"，跟问题相关；没值，就是无关。这不就是基于关键词的精确匹配吗？

而且这种匹配效率极高：词表是一一对应的，关键词能精确定位到索引，再拿索引去向量里精确定位到权重，两步就完了。精准度也高，因为它是字面命中。当然，它也只适用于关键词检索。

不过，长度为 10 万的列表里只存三五个值，实在太浪费。真实系统里会把这个列表转成一个字典：键就是索引，值就是权重，只存有值的位置。

```text
[0, 0, 0, 2.7, 0, 1.4, 0, …… 0]     长度 10 万，绝大多数是 0
                │
                ▼  只保留非零位
{3: 2.7, 5: 1.4}
```

读图说明：字典的键是词表里的编号，值是权重；没有值的位置直接不存，空间省下来了，但查法完全一样——按 key 找 value。

> **提示**：转成字典之后，它看起来不像向量了，但它依然是向量，只是换了一种更省空间的存法。

### 统计式与学习式：稀疏向量的两条来路

稀疏向量的生成方式有两种：统计生成和训练生成。

统计式就是我刚才走的那条路：一份份文档查过去，统计出现了哪些词，形成词表，再做词频统计。常见的算法是 BM25、TF-IDF 这一类。它的好处是需要的计算资源少、速度非常快；边界也很清楚——只认字面，换个说法就匹配不上。

学习式是用模型训练来生成稀疏向量，代表是 BGE-M3、SPLADE 这些模型。它要吃 CPU／GPU 资源，计算速度慢，但理解能力更强：它也带一点语义分析能力，做的是关键词检索，同时又能带上一点同义词的效果。

| 生成方式 | 代表算法／模型 | 资源与速度 | 效果 |
| :--- | :--- | :--- | :--- |
| 统计式 | BM25、TF-IDF | 资源少，速度快 | 纯字面匹配，精确但死板 |
| 学习式 | BGE-M3、SPLADE | 需要 GPU，速度慢 | 关键词检索 + 一点同义词效果 |

实际选哪一种，看企业需求。大多数情况下，你要的就是按词精确匹配，那更推荐统计式——速度快，还不烧显卡。如果你希望带一点语义分析，而且手上有很强的显卡，那就上学习式。

到这可以把两种向量收个尾：稠密向量做语义检索，稀疏向量做关键词检索，两者是互补的。语义检索很多场景需要，关键词检索同样需要，所以向量库里两种都存。

### 三类字段，三套索引

回到索引。稠密向量和稀疏向量各有各的索引类型。

稠密向量的索引有 HNSW、IVF_FLAT 等等；记不住也没关系，不知道用哪个就写 `AUTO`，让 Milvus 自己选。

稀疏向量的索引基本只有一种：倒排索引。什么叫倒排索引？就是我们刚才建词表的那套索引——从词出发，反查哪些文档里有它。所以稀疏向量通常都用倒排索引。

普通字段的索引就非常多了，等用到了再讲。

> **提示**：这三类索引现在不用背。知道"稠密有一堆、稀疏基本只有倒排、标量一大堆"这个格局，用的时候再查就够了。

### 环境准备：客户端、端口与配置

概念讲完，该动手了。

第一件事是选客户端。注意，我们不是一上来就用 LangChain 封装的 Milvus 客户端，先用 Milvus 自己的客户端——`pymilvus`。项目里已经装好了，不用再装。

Milvus 部署在虚拟机里，项目要连它，就必须知道地址和端口。端口有两个：

| 端口 | 用途 | 怎么用 |
| :--- | :--- | :--- |
| `9091` | Web UI，看集群状态 | 浏览器打开，能看到集群运行状态与 collection 信息 |
| `19530` | 供代码访问 | 客户端连这个 |

配置分两步：先把 host 和 port 写进 `.env`，再在 `config` 的 rag 配置里加两个字段读它们——昨天那里加过一个 LLM 的配置，今天加 Milvus 的 `milvus_host` 和 `milvus_port`。

光有 host 和 port 还不够，客户端要的是一个完整的地址，得拼成 `http://host:port`。所以在配置类里写一个"看起来是函数、实际当属性用"的计算字段：

```python
# app/core/config.py 中 rag 配置的关键部分
milvus_host: str
milvus_port: int

@computed_field
@property
def milvus_url(self) -> str:
    return f"http://{self.milvus_host}:{self.milvus_port}"
```

拼出来长这样：`http://192.168.150.101:19530`。

将来到了企业里，你其实就改这两个值；一般端口不用动，改 host 就行。

### 备料：能切的文档与能转的模型

环境变量好了，还得有两样东西才能真正玩向量库：文档和向量模型。要往库里存数据，总得先有数据。

在 notebook 目录下建一个 `day08`，新建 `milvus.ipynb`，把 Day07 用的那份 markdown 资源拷进来——在 `resources` 下新建文件夹放进去就行。为什么特意用 markdown？因为它的结构清晰，方便等会儿切分，切完就能往向量库里存。

切分用的是 Day07 那套老流程：读文件 → 创建 Markdown 标题切分器 → `strip_headers=False`（正文里保留标题）→ 一路切下去 → 得到一堆 `Document` → return。把它封装成一个函数，一调就有文档。

每个 `Document` 里有两个属性：`metadata` 和 `page_content`。`metadata` 装的是 H1、H2、H3 这些标题层级，`page_content` 是正文。

```text
resources/*.md
      │  读取
      ▼
Markdown 标题切分器（strip_headers=False）
      │  按 H1/H2/H3 切开
      ▼
[Document, Document, Document, ……]
      │
      ├─ metadata     ← H1 / H2 / H3 标题层级
      └─ page_content ← 这一段正文
```

读图说明：一份 markdown 进去，出来的是一个 `Document` 列表；标题层级没被丢掉，而是留在 `metadata` 里，正文留在 `page_content` 里。后面往向量库里存，存的就是这些 `Document`。

文档有了，再把向量模型准备好。用 Ollama 也行，用阿里云也行。用 Ollama 的话得先把 Ollama 启动起来；电脑性能差的同学就别选 Ollama 了，直接选阿里云。

如果用的是阿里云，有个地方要补：API Key 和 Base URL 虽然配在 `.env` 里，但没有放进 `config`，代码里读不到。这两个值属于模型本身的配置，可以放进 `llm_settings` 里，照着已有的写法加两项，比如 `dashscope_api_key` 和 `base_url`；然后初始化向量模型时，从 `app.core.config` 导入 `settings`，把这两个值取出来传进去就行了。

> **提示**：用 Ollama 的同学不用做这一步；用阿里云的同学照着自己项目里已有的配置格式补两项即可，关键是初始化时要能从 `settings` 里取到值。

### Collection 的三步建表法

准备工作做完，下面开始操作 collection。步骤一定要先记清楚，一共三步，跟数据库建表一模一样。

第一步，定义 `schema`，也就是字段的约束。这就像你在 MySQL 里建一张表，得先写清楚表里有哪些字段、每个字段什么类型、有什么约束。在 Milvus 里，就是写 collection 中字段的约束。

第二步，给字段加索引。注意，不是所有字段都要加，**要用到的才加，用不到的别加**。这就相当于在 MySQL 里给 `id` 或者别的要查询的字段建索引。

第三步，创建 collection。传三个东西就够了：collection 的名字（相当于表名）、前面定义好的 `schema`（字段约束）、前面定义好的 `index_params`（索引）。

这里跟写 SQL 不一样：SQL 一条 `CREATE TABLE` 能把字段和索引一起写完，而这里用的是面向对象的方式，必须一步一步来——先建 `schema`，再建索引，最后建 collection。

```text
定义 schema（字段与约束）
        │
        ▼
给用到的字段建索引（index_params）
        │
        ▼
create_collection(name, schema, index_params)
```

读图说明：三步是有先后依赖的，后面一步要拿前面一步的产物当参数；名字起好一次，后两步一直用。

### 初始化客户端

动手的第一件事是连上 Milvus，连上了才有 collection 可操作。

连接用的是 `pymilvus` 里的 `MilvusClient` 类，创建它的对象就行。它需要不少参数：`uri` 是第一个参数，后面还有用户名、密码、`db_name` 等等。咱们这套 Milvus 部署的时候没加权限校验，所以没有用户名密码，把 `uri` 传对就够了。

`uri` 不要手写。我们已经把它配到 `app.core.config` 的 `settings` 里了，直接从里面取。

```python
from pymilvus import MilvusClient

from app.core.config import settings

client = MilvusClient(uri=settings.rag.milvus_url)
collection_name = "my_collection1"
```

这段代码干了两件事：一是用配置里的地址创建客户端对象，二是提前把 collection 的名字定下来，因为后面会一直用到它。

写的时候还有个命名上的小插曲。这个字段最初叫 `url`，取的时候写 `settings.rag.url`，看着就别扭——这是谁的 URL 呢？一个配置类里可能不止一个地址，只叫 `url` 说明不了问题。改成 `milvus_url` 就专业多了，一看就知道是 Milvus 的地址。配置里改完，代码里同步换成 `settings.rag.milvus_url`，两边必须一致。

到这一步，客户端就初始化好了，文档有了，向量模型也有了，接下来才是真正往 collection 里写东西。

## Milvus Collection 与 Entity 读写
> 对应块：BLK34 | 覆盖分集：P132-P134

客户端已经准备好了，接下来就按流程走：定义 schema、定义 index、创建 collection。可真到动手的时候，第一件事不是敲代码，而是把前面切好的文档摆出来看一眼——我们截出来的文档就长那样：`page_content` 是一大段文本，`metadata` 里挂着各级标题。看着挺全，可我问你们一句：它有 id 吗？

没有。我忘了给它加 id 了。

这不是小事。id 是文档的唯一标识，到了 Milvus 里还得是主键。所以我们在建表之前，先得把“每一篇文档到底要带哪些字段进来、各自是什么类型”这件事想清楚，否则 schema 根本没法写。

```text
定义 schema（字段与约束）
        │
        ▼
定义 index（给要搜索、要过滤的字段建索引）
        │
        ▼
create_collection（把名字、schema、index 一起交出去）
        │
        ▼
写入 entity（insert / upsert / delete）
```

整块内容就围着这条线展开：先把 Collection 建出来，再往里写 Entity。

### 从切出来的文档倒推字段设计

建 collection 跟建表是一回事，schema 就是字段约束。约束从哪来？不能拍脑袋，得看着我们手里现有的数据来定：哪些字段必须存、哪些字段可以只挑一个、哪些字段到了 Milvus 里根本找不到对应类型，都要逐个过一遍。

#### id：主键跑不掉

文档原本没有 id，补起来也简单，用 `enumerate` 边遍历边编号：

```python
for i, doc in enumerate(docs):
    doc.id = str(i + 1)
```

这里有个小要求：LangChain 这边的 id 得是字符串。编完再跑一次，文档上就有 `1、2、3……` 了。

但 Milvus 里 id 的类型不是字符串，而是 `INT64`，而且必须是主键。两边对不上怎么办？不用改文档结构，等会儿写 entity 的时候把它转成 `int` 就行。字段本身的性质先记住：**唯一标识、必须存在、主键**。

> **易错点**：`enumerate` 默认从 0 开始。编号给文档用时可以加一从 1 起，但后面拿它去取向量列表时，索引必须回到 0 基——这一处对齐关系后面还会再遇到一次。

#### metadata 不能整坨塞进去

`metadata` 是个字典，里面装着 `h2`、`h3` 这些标题信息。字典这种结构，Milvus 的 schema 里没有对应类型，硬塞是塞不进去的。

那怎么办？不存那么多。我们只挑一个 `h2` 存进去，它代表这一篇的二级标题，将来可以做过滤条件。只存 `h2`、不存 `h3` 行不行？行，演示数据没必要全量搬进去，想换成 `h3` 也行，我不拦着你。

`h2` 是字符串，对应 Milvus 的 `VARCHAR`，长度限制给 `128`。这就像在 MySQL 里写 `varchar(128)`，只不过 Milvus 这边是用面向对象的方式配参数。

#### page_content 必须原样留下

`page_content` 是一整段原始文本，既是将来给人看的内容，也是生成两路向量的原料，所以一定要存，类型同样是 `VARCHAR`。文档内容可能很长，长度上限给到 `2048` 个字符。

#### 两个向量字段各管一路检索

真正特殊的是两个向量字段，它们都不是从文档里直接搬过来的，而是由 `page_content` 加工出来的：

- `dense`：稠密向量，类型必须是 `FLOAT_VECTOR`。维度要写死，这里填 `1024`，因为前面准备的 Ollama 嵌入模型输出的就是 1024 维。
- `sparse`：稀疏向量，类型是 `SPARSE_FLOAT_VECTOR`。它不用指定维度——稀疏向量的维度是跟着词表动态变化的。

把五个字段拢在一张表里，结构就清楚了：

| 字段 | Milvus 类型 | 关键约束 | 数据来源 |
| :--- | :--- | :--- | :--- |
| `id` | `INT64` | 主键，不自动生成 | 文档编号转成整数 |
| `h2` | `VARCHAR` | `max_length=128` | `metadata["h2"]` |
| `content` | `VARCHAR` | `max_length=2048`，允许分词 | `page_content` |
| `dense` | `FLOAT_VECTOR` | `dim=1024` | 嵌入模型生成 |
| `sparse` | `SPARSE_FLOAT_VECTOR` | 维度动态 | Milvus 的 BM25 自动生成 |

### 先把 schema 立起来

这段建表代码看起来非常复杂，但跟之前一样，你们不用从零把它写出来，只要会复制、会改就行。就像建表语句，你现在能徒手写出来吗？写不出来吧。可你能看懂、会改，要加字段就复制一行，改个名字、改个类型，这就够了。

事实上这份代码我也是从 Milvus 官网复制过来改的，不是我手写的。官网有完整的示例，你要做的是看懂每一行在约束什么，然后按自己的字段改。

#### create_schema 的两个开关

先拿到一个空的 schema 容器：

```python
schema = client.create_schema(
    auto_id=False,
    enable_dynamic_field=False,
)
```

两个参数都是开关，但管的事情完全不同。

`auto_id=False` 的意思是“不自动生成 id”。我们的 id 是自己编好、自己传进去的，所以必须关掉自动生成。

`enable_dynamic_field` 是“是否允许动态字段”。什么叫动态字段？假设定义 schema 时只写了一个 id，别的什么都没写；等你往里插数据，带了 `h2`、`content`，Milvus 会动态地替你把这两个字段补出来，还替你推断类型。听起来很方便，但这件事不靠谱：类型是它自动判的，万一判得不符合你的要求呢？更根本的是，一张表的格式得是固定的，一旦允许动态加字段，这张表的结构就不再受控了。所以这里一律改成 `False`，不让它动态生成。

#### add_field 的套路

schema 有了，接下来一行一行往里加字段，用的都是 `add_field`：

```python
from pymilvus import DataType

schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True)
schema.add_field(field_name="dense", datatype=DataType.FLOAT_VECTOR, dim=1024)
schema.add_field(field_name="sparse", datatype=DataType.SPARSE_FLOAT_VECTOR)
schema.add_field(field_name="h2", datatype=DataType.VARCHAR, max_length=128)
```

`datatype` 不用手写字符串，它是 `DataType` 这个枚举里的属性，写 `DataType.INT64`、`DataType.FLOAT_VECTOR` 就行，写错了编辑器会提示。

id 这一行多了个 `is_primary=True`，意思就是主键。稠密向量那一行多了个 `dim=1024`，把维度锁死。稀疏向量那行没有 `dim`，因为维度动态。`h2` 那行的 `max_length=128` 就是标题的长度上限。

看明白第一行，后面的就是同一个套路换参数。字段名可以自己起，但**schema 里叫什么，后面写数据、建索引就得叫什么**，三处必须一致，这是后面最容易犯的低级错误。

#### content 要开分词

`content` 字段比前面几个多两个参数：

```python
schema.add_field(
    field_name="content",
    datatype=DataType.VARCHAR,
    max_length=2048,
    enable_analyzer=True,
    analyzer_params={"type": "chinese"},
)
```

为什么要开分词？因为稀疏向量是靠词表统计出来的，而一大段中文文本要先切成一个个词——“教育概述”“教育”“第一节”“中文教育”，这些词得先分出来，才能建词表、才能算 BM25。分词本身不用我们写代码，但得允许 Milvus 对这个字段做分词。

`enable_analyzer=True` 就是“允许对该字段做分词”。`analyzer` 在计算机科学里可以理解成分词器；`analyzer_params` 里的 `type` 指定分词器类型，这里写 `chinese`，用的是 Milvus 内置的中文分词器。不想用它也行，可以指定别的分词器，但这一讲用默认的中文分词就够。

> **注意**：`enable_analyzer` 这个参数很关键。不开它，`content` 只是一段普通字符串，Milvus 不会替你切词，后面的 BM25 也就无从谈起。

这两个参数配好之后，插入数据时 Milvus 会自动完成“分词 → BM25 统计 → 稀疏向量”这一整条链路。但稠密向量它不管，那一路得我们自己调模型来转。两条路的差别可以画成这样：

```text
content 原文
   │
   ├── chinese 分词器 ──► 词序列 ──► BM25 统计 ──► sparse（自动）
   │
   └── 嵌入模型 embed_documents ──► dense（手动）
```

#### 用 BM25 function 把 content 接到 sparse 上

光有分词器还不够，还得告诉 Milvus：拿哪个字段转、转出来的结果放到哪个字段。这就是 BM25 function 干的事：

```python
from pymilvus import Function, FunctionType

bm25_function = Function(
    name="text_bm25_emb",
    function_type=FunctionType.BM25,
    input_field_names=["content"],
    output_field_names=["sparse"],
)
schema.add_function(bm25_function)
```

这个 BM25 生成器是 Milvus 内置的，不用我们实现，我们只负责把输入、输出和函数类型告诉它。

function 的名字随便起，这里叫 `text_bm25_emb`。真正要对应上的是输入和输出：输入字段是 `content`，输出字段是 `sparse`。为什么输出叫 `sparse`？因为前面定义稀疏向量字段时名字已经定成 `sparse` 了，这里必须跟它一致。生成方式由 `FunctionType.BM25` 指定，最后用 `schema.add_function` 把这个函数挂进 schema。

到这一步，schema 才算真正定义完。

### 建索引与创建 Collection

schema 只解决了“表里有哪些字段”，还没解决“怎么查得快”。哪些字段要建索引？一句话：**将来用来做搜索和过滤的字段，都要加索引**。

我们将来一定会拿向量做检索，稠密和稀疏两路都要，所以 `dense`、`sparse` 这两个索引非加不可。除此之外，可能还要按标题、按 id 做过滤——先筛一批，再在里面做向量搜索，这种需求很常见，所以普通标量字段也可以加。id 是主键，本身就有默认索引，不用重复加。结论就是：**两个向量字段必须加，其他字段看需求**。

#### 稠密向量索引

先拿一个索引参数容器：

```python
index_params = client.prepare_index_params()

index_params.add_index(
    field_name="dense",
    index_type="AUTOINDEX",
    metric_type="COSINE",
)
```

`add_index` 这里有三个参数。

`field_name` 是给哪个字段加索引，必须跟 schema 里定义的名字一模一样。上面定义叫 `dense`，下面就得叫 `dense`；你也可以不叫这个名字，但两处必须统一。

`index_type` 是索引类型。稠密向量的索引类型有很多种，不知道选哪个就填 `AUTOINDEX`，交给 Milvus 自己判断。它会根据数据量大小来选，数据规模变了，底层用的索引也可能跟着变。

`metric_type` 是相似度的计算方式。稠密向量是靠向量相似度来算的，前面讲过余弦、欧式距离、内积这几种；这里 `COS` 代表余弦相似度，`IP` 代表内积。我们这里指定 `COSINE`。

#### 稀疏向量索引

```python
index_params.add_index(
    field_name="sparse",
    index_type="SPARSE_INVERTED_INDEX",
    metric_type="BM25",
)
```

函数还是同一个 `add_index`，真正变的是参数。字段名换成 `sparse`；索引类型写 `SPARSE_INVERTED_INDEX`，这是稀疏倒排索引——稀疏向量本来就采用倒排索引；相似度计算方式写 `BM25`。

这一段可以认为是固定的写法，只有字段名 `sparse` 是可变的，而且还得跟 schema 里的名字对上。

> **易错点**：倒排索引只能用 BM25 做相似度计算，不能填内积。只有“用模型生成的稀疏向量”才可以用内积来算；我们这里的稀疏向量是 BM25 统计出来的，走的是倒排索引，所以这里必须是 `BM25`。

#### 普通标量字段也能加索引

如果还想给别的普通字段加索引，函数还是 `add_index`：

```python
index_params.add_index(
    field_name="h2",
    index_type="AUTOINDEX",
)
```

标量字段不涉及向量相似度，所以只需要字段名和索引类型两个参数，不用写 `metric_type`。这里同样用 `AUTOINDEX`，让 Milvus 自动选。

#### 三样齐了就能建表

建 collection 的方法接收三个核心参数：

```python
client.create_collection(
    collection_name="my_collection1",
    schema=schema,
    index_params=index_params,
)
```

第一个是 collection 的名字，第二个是前面 `create_schema` 建出来的 schema，第三个是 `prepare_index_params` 攒出来的索引参数。这三样在前两步都已经准备好了，现在只是把它们一起交给 `create_collection`，就能得到一张完整的表。

把这段逻辑封进一个 `create_collection` 函数里，初始化客户端之后调一下，表就出来了。

> **提示**：运行时如果报 `DataType` 找不到，是少导了依赖，补一句 `from pymilvus import DataType` 即可；用到 `Function`、`FunctionType` 时同理。

### 查看、删除与 Attu 图形界面

代码跑完提示成功，怎么确认表真的建出来了？别只看运行提示，回到 Milvus 里查。

#### list_collections 与 drop_collection

`MilvusClient` 里有现成的方法：

```python
client.list_collections()
client.drop_collection(collection_name="my_collection1")
```

`list_collections` 不传参数，返回 Milvus 里所有的 collection。我们只建了一个，所以列表里只有 `my_collection1`。记不住方法名也没关系，在 `client.` 后面敲 `collection`，补全里就能看到 `create_collection`、`drop_collection`、`list_collections` 这些方法，看名字就知道谁管创建、谁管删除、谁管查看。

`drop_collection` 只需要一个 `collection_name`，传前面定义好的名字即可。删完再 `list` 一次，列表就空了；再把创建那段代码跑一遍，它又回来了。Collection 层面的创建、查看、删除，就是这三个动作。

#### 在 Attu 里核对表结构

如果觉得命令行来回切麻烦，Milvus 还提供了图形化界面 Attu，课程环境里已经把它部署在虚拟机上了。在浏览器里打开对应地址，它连的是 Milvus 的 `19530` 端口。

第一次访问时是注册流程，用户名和密码由你自己生成，不是什么预设账号；注册好之后，下次登录用这套账号密码就行。

登录进来，点开数据浏览器，能看到刚建的 `my_collection1`。字段一个个列在那里：`id` 是 `int64`，`dense` 是稠密向量，`sparse` 是稀疏向量，`h2` 和 `content` 是字符串。下面还挂着一个 BM25 函数，负责把 `content` 转成稀疏向量。

表结构、字段类型、函数都跟代码里写的一致，说明这张表建对了。

### Entity：Milvus 里的一条数据

Collection 有了，字段也有了，可 Attu 里看过去一条数据都没有。接下来就往里写。

数据在 Milvus 里叫什么？叫 entity，实体。这一块先学三个操作：`insert` 新增、`upsert` 修改、`delete` 删除，查询先不讲。

### 写入前先把 Document 加工成字典

`insert` 对数据格式要求很严格：entity 必须是一个字典，或者一个装字典的列表。可我们手里是 LangChain 切分出来的 `Document` 对象，里面是 `id`、`metadata`、`page_content`，跟 Milvus 要的结构对不上。

Milvus 要的字典长这样，四个键，正好对应 schema 里除 `sparse` 之外的字段：

```python
entity = {
    "id": i + 1,
    "h2": doc.metadata.get("h2"),
    "content": doc.page_content,
    "dense": dense_vectors[i],
}
```

为什么没有 `sparse`？因为稀疏向量由 Milvus 的 BM25 函数自动生成，我们不用管；稠密向量没人替我们生成，必须自己算。所以写入之前要做两件事：先把所有文档的稠密向量生成出来，再把每个 `Document` 转成上面这样的字典。

```text
docs（Document 列表）
   │  取出 page_content
   ▼
texts（字符串列表）
   │  embed_documents 批量转向量
   ▼
dense_vectors（与 docs 顺序一一对应）
   │
   ├── id       = i + 1
   ├── h2       = doc.metadata.get("h2")
   ├── content  = doc.page_content
   └── dense    = dense_vectors[i]
          │
          ▼
      entity 字典（sparse 由 Milvus 写入时自动补）
          │
          ▼
      insert / upsert
```

图里只画了我们手工加工的部分：`docs` 先抽出文本、整批算出向量，再把每条文档的字段和对应向量拼成字典，最后交给写入方法；`sparse` 不在字典里，由 Milvus 在落库时补齐。

#### 先批量算出稠密向量

先把所有 `page_content` 抽成一个字符串列表，再整批交给嵌入模型：

```python
texts = [doc.page_content for doc in docs]
dense_vectors = ollama_embedding.embed_documents(texts)
```

`embed_documents` 是批量生成稠密向量的方法，接收一个字符串列表，返回一个向量列表。这里有一个特别重要的对应关系：**返回的向量顺序跟传入的文档顺序完全一致**。第 0 篇文档的向量就在 `dense_vectors[0]`，第 1 篇在 `dense_vectors[1]`，一条对一条，不能乱。

#### 再把每个 Document 转成字典

先老老实实写循环：

```python
entities = []
for i, doc in enumerate(docs):
    entity = {
        "id": i + 1,
        "h2": doc.metadata.get("h2"),
        "content": doc.page_content,
        "dense": dense_vectors[i],
    }
    entities.append(entity)
```

重新跑过切分之后，`docs` 里又没有 id 了，所以这里用 `enumerate` 现场编号。几个取值方式也要注意：`metadata` 是个字典，不能直接 `doc.metadata.h2`，得用 `get("h2")` 或者中括号取。正文对应的是 `doc.page_content`，不是 `doc.content`。稠密向量从 `dense_vectors[i]` 里拿。

这里有个容易翻车的地方：`enumerate(docs)` 默认从 0 开始，而 id 我们想从 1 开始。那就让 `i` 保持 0 基，写 id 的时候用 `i + 1`，取向量的时候继续用 `dense_vectors[i]`。如果你图省事写成 `enumerate(docs, start=1)`，id 是好看了，但 `dense_vectors[1]` 配到的就是第二篇文档，整批数据会错位一条。

> **易错点**：id 的起始值和向量列表的下标是两回事。id 可以加一，下标不能跟着加一；一旦让 `i` 从 1 起，取向量时就得写 `dense_vectors[i - 1]`，否则文档和向量全对不上。

#### 写成推导式更清爽

上面那段循环可以收成一个列表推导式：

```python
entity_list = [
    {
        "id": i + 1,
        "h2": doc.metadata.get("h2"),
        "content": doc.page_content,
        "dense": dense_vectors[i],
    }
    for i, doc in enumerate(docs)
]
```

数据来源还是 `docs`，`for i, doc in enumerate(docs)` 负责同时拿到下标和文档，前面那个字典原样搬过来，`id` 用 `i + 1`，其余从 `doc` 和 `dense_vectors` 里取。逻辑跟循环版一模一样，只是写得更短。

怕你们看懵，循环版我也留在代码里，以后想对照可以看；实际写的时候用推导式就行。跑一遍，点开 `entity_list` 检查：id 从 1 开始递增，`h2`、`content`、`dense` 都在，结构就跟 schema 要求对上了。

### insert：把实体批量写进去

数据准备好了，写入就是一句话：

```python
result = client.insert(
    collection_name="my_collection1",
    data=entity_list,
)
```

`insert` 只认两个参数：往哪儿插、插什么。第一个是 collection 的名字，前面已经定义好了；第二个是数据，可以是单个字典，也可以是字典的列表，我们现在传的是列表，一次把 21 条全推进去。

写入的时候，Milvus 会拿每条 entity 里的 `content` 自动走一遍分词和 BM25，把 `sparse` 补齐；`dense` 我们已经算好放在字典里了，直接存。

跑完会返回一个结果，里面有 `insert_count`，告诉你成功写入了多少条，还有每条对应的 id。这次是 21 条，id 从 1 往后排。

到底有没有真的进去？打开 Attu，点数据页看一眼：id 从一开始递增，`dense` 是一长串向量，`sparse` 显示的是系统生成，`h2`、`content` 全都有。到这儿，新增就算通了。

回顾一下这条链路：数据从 LangChain 的 `Document` 来，但 Milvus 只收字典，所以中间要做两次加工——先把 `page_content` 整批送进嵌入模型生成 `dense`，再用推导式把每个 `Document` 转成带 `id`、`h2`、`content`、`dense` 的字典。`insert` 拿到的就是这个字典列表，加上 collection 名字，两件事说清楚就能写。

### upsert：先删旧的，再插新的

`upsert` 这个名字看着特殊，其实是个合成词：`up` 来自 update，`sert` 来自 insert，合起来就是“更新 + 新增”。

它的底层做法很直接：你传进来一条 entity，它先看这条 entity 的 id，把库里同 id 的旧数据删掉，再把你这条新的插进去。旧记录一删、新记录一插，效果不就等同于修改吗？比如 id 为 1 的那条，原来标题是 A，你传一条 id 还是 1、标题改成 B 的进去，旧的那条被删掉，新的那条顶上来，标题就改了。

那如果传进去的 id 在库里根本不存在呢？删的时候什么都没删到，剩下的动作就只有插入。所以 `upsert` 同时具备两种语义：**id 存在就是更新，id 不存在就是新增**。

拿两条数据试一下：

```python
data = entity_list

data[0]["h2"] = "测试一下"

data[1]["id"] = 88
data[1]["h2"] = "再测试一下"

result = client.upsert(
    collection_name="my_collection1",
    data=[data[0], data[1]],
)
```

`data[0]` 是 id 为 1 的那条，id 没动，只把标题改成“测试一下”——id 存在，走更新。`data[1]` 原本是 id 为 2 的那条，把 id 改成 88，标题改成“再测试一下”——88 在库里不存在，走新增。所以这一批两条，一条更新、一条新增。

`upsert` 的参数跟 `insert` 完全一样：collection 名字加数据，数据同样可以是单个字典或字典列表。跑完返回 `upsert_count=2`，涉及的两个 id 是 1 和 88。

> **注意**：验证结果要去 Attu 里刷新看，别盯着 Python 里那个 `entity_list`。那只是我们本地拼出来的列表，库里改了它不会跟着变，是“死”的。刷新之后能看到 id 为 1 的标题变成了“测试一下”，id 为 88 的那条新出现了，这才算验证成功。

以后分不清什么时候用 `insert`、什么时候用 `upsert`，那就永远用 `upsert`：存在就更新，不存在就新增，一个方法把两种情况都兜住。前提是 id 得由你控制得住，否则它没法判断该覆盖谁。

### delete：按主键删，参数必须是列表

删除也是调客户端里的方法，名字就叫 `delete`：

```python
result = client.delete(
    collection_name="my_collection1",
    ids=[88],
)
```

两个参数：collection 名字，以及要删的 id。这里有个硬性要求——`ids` 必须是列表，哪怕只删一条，也得写成 `[88]`，不能直接传一个 `88`。

跑完返回 `delete_count=1`，回 Attu 刷新，88 号那条就没了。再删一次 88 呢？它已经不存在了，删了也白删，没有任何意义。

### 三种写操作的分工

到这里，Entity 的增、改、删就齐了。把三个方法放在一起对比，边界很清楚：

| 操作 | 方法 | 语义 | id 已存在 | id 不存在 |
| :--- | :--- | :--- | :--- | :--- |
| 新增 | `insert` | 只负责插入 | 不是它的处理范围 | 插入新记录 |
| 更新或新增 | `upsert` | 先删同 id 旧记录，再插入 | 覆盖旧记录，等同更新 | 插入新记录 |
| 删除 | `delete` | 按主键移除 | 删除该记录 | 无效果 |

`insert` 和 `upsert` 的参数完全一样，都是 collection 名字加 entity 字典或字典列表；`delete` 换成了 collection 名字加 id 列表。分不清就用 `upsert`，它把更新和新增都包了，但前提是 id 在你手里控制得住。

Collection 和 Entity 这两层打通之后，后面的检索才有东西可查——表建好了，数据也进去了，接下来才轮到怎么从里面把相似的向量找出来。

## Milvus 的向量检索：稠密、稀疏与混合
> 对应块：BLK35 | 覆盖分集：P135-P139 | 块标题（分集名）：《Milvus 稠密与稀疏向量检索》

collection 建出来了，数据也增了、删了、改了，到这一步 Milvus 的基本数据操作就算走完了。但有一件事一直没碰：搜索。而这恰恰是整个向量库最核心的动作——前面建表、写数据，全是为了这一刻能拿一个问题把相关的知识片段捞回来。

Milvus 里做向量相似性搜索的核心接口就叫 `search`。检索的路子有两条：稠密和稀疏。先把稠密讲清楚。

### 搜索之前：为什么不能拿问题向量挨个比

Milvus 的稠密检索用的是近似近邻算法，英文缩写 ANN。要弄明白它为什么这么设计，先看它的反面——KNN。

KNN 是相当"变态"的一种算法：把向量空间里所有的向量都拎出来，跟查询里的这个向量逐个比较，找出最相似的那几个。搁到具体场景里说，库里存了一万条文档，用户问了一句话，我就得把这句话转成的向量，跟这一万条文档向量分别算一遍相似度，再排序看谁得分最高。

一万条勉强能忍。可文档到了十万、百万、千万呢？Milvus 撑得住数以亿计的量。这么多文档还一个一个比，合理吗？不合理，非常耗时，也非常吃资源。所以 KNN 在真实规模上没法用。

在 Milvus 的索引类型里，这种蛮力打法是有名字的：`FLAT`。最直接也最直白，一条一条比，效率非常差，但准确度是最高的——它是拿时间换精度的极端。

ANN 换了个打法：它先准备一份索引文件，索引里记着向量的排布顺序；检索时照着这份索引，快速定位到"可能和查询向量最相似"的那一小部分向量，只在这一小部分里算。

"快速定位到一小部分"这句话还是太抽象。落到具体算法上就清楚了。Milvus 里稠密向量的索引不止一种，最有代表性的两种值得认识。

#### IVF_FLAT：先圈一片地，再在地里细找

`IVF_FLAT` 中文一般叫倒排文件扁平索引，这个名字直译过来其实不太贴切，但原理一点都不玄。

建索引时它用的是 K 均值聚类：把整个向量空间划成一片一片的区域，每一片装十个、二十个、上百个向量不等，分多大由你自己定。划好之后，对每一片算一个中心值——这一片所有向量的平均位置，叫中心点。这个中心点能代表这一片向量的整体位置。

索引就这样成形了：每个中心点，对应它名下的一批向量。

检索时的动作就变了。不用拿问题向量去跟每一条文档比，只跟这些中心点比，看问题向量离哪个中心点最近。比如离灰色那片最近，那这片区域里的向量跟问题相似的概率就最高。于是把这片里的几百上千个向量取出来，逐个跟问题向量算相似度，挑最相关的返回。

```text
                    全部向量
                        │
               K 均值聚类划分区域
                        │
        ┌───────┬───────┬───────┬───────┐
        │ 区域A │ 区域B │ 区域C │ 区域D │
        │ 中心a │ 中心b │ 中心c │ 中心d │
        └───────┴───────┴───────┴───────┘
                        ▲
                    问题向量
                        │
            只跟各区域的中心点比距离
                        │
           锁定最近的一片（比如区域B）
                        │
          在区域内逐条精算 → 返回 Top K
```

读图：上面是建索引阶段，把散落的向量按聚类切成若干区域，每区留下一个中心点当代表；下面是检索阶段，先用问题向量跟这几个中心点比，锁定一片，再进片里逐条算。

先锁定大范围，再在大范围里精细检索，检索量一下就降下来了。这个思路说白了就是给数据分块：上千万篇文档的库，按每 100 条或每 1000 条划一片，就切成上万个区域；拿问题向量跟这些中心点快速比一遍，精确锁定一片，再进片里细算。中心点本身也是有排序的，所以这一步能做得很快。

#### HNSW：在分层的图上逐层下探

Milvus 里当然不止 IVF 这一种。还有一种叫 `HNSW`，是基于图的索引算法，性能非常强。

它的做法是先按数据之间的关联关系，把所有向量连成一张图；这张图还分层，一层比一层细。最上面那层的索引最粗、覆盖范围最大，越往下越精细。检索时从上层开始逐层往下走，每下一层就把候选范围收窄一点，最后要比较的向量数量就少了很多。

这种算法有兴趣可以自己去了解，Milvus 官网的用户指南里把这些索引类型一条条列着，想深挖可以对着翻。但真正用的时候，我们不用关心底层怎么实现：指定索引方式，剩下的交给 Milvus 自动完成。这些检索算法做个了解就够了，不必每一种都把底层研究透。

最后落到我们自己身上：当初建 collection 时索引类型填的是 `auto`，让 Milvus 自己选。自动模式下，大概率用的就是 `IVF_FLAT`，也就是先建索引文件、把索引划成块、按块检索这一套。

### search 的参数：照着 SQL 的写法理解

`search` 能传的参数非常多，第一次看到那一长串容易发怵。其实先分清哪些是必填的、哪些是常用的，剩下的用到了再查就行。

#### 三个必填：搜哪张表、哪个字段、拿什么去搜

第一个 `collection_name`：搜的是哪个 collection。这相当于 SQL 里的 `from 哪张表`——表名不写，查什么都不知道，所以必须指定。

第二个 `data`：要拿去比的东西。它可以是一个列表，也可以是列表的列表。为什么？因为它既支持传一个向量，也支持传多个向量：一个向量本身就是个列表（一堆数字装在一起），那传多个向量自然就是列表的列表。也就是说 Milvus 支持批量查询，一次问一个问题可以，一次问好几个问题也可以。业务场景里通常就一个，装成 `[query_vector]` 这样的列表传进去。

这个参数名字叫 `data`，实际装的不是"数据"，是问题向量。现阶段用户的问题要先转向量，转完再塞进 `data`。

第三个 `anns_field`：基于哪个向量字段来搜。存向量的那个字段叫什么名字，得告诉它。我们这个表里就是 `dense`——拿问题向量去比，当然比的是稠密向量字段。

把这几个参数对着 SQL 摆一遍就通了：

```sql
select * from 表名 where name like '%关键词%' limit 10
```

| 参数 | 是否必填 | 作用 | 对应 SQL |
| :--- | :--- | :--- | :--- |
| `collection_name` | 必填 | 搜哪个 collection | `from 表名` |
| `anns_field` | 必填 | 拿哪个向量字段比 | `where` 里的字段 |
| `data` | 必填 | 问题向量（列表；可传多个 → 批量） | `like` 后面的值 |
| `limit` | 常用 | 返回多少条相似结果 | `limit 10` |
| `output_fields` | 常用 | 结果里带回哪些字段 | `select` 的列 |

#### limit 与 output_fields：返回几条、带回哪几列

`limit` 就是 SQL 里的 `limit 10`，指返回的相似结果数量。Milvus 默认按相似度打分排序，分越高排越靠前，`limit=3` 就是取 Top 3。

`output_fields` 是搜索结果里需要返回的字段，列表形式，比如 `["id", "color", "price"]`。这里有个坑：它不能写 `*`。SQL 里 `select *` 一把梭没问题，这里不行，字段名得一个个点出来。

#### 剩下的可选参数，先知道有这回事

`search_params` 是检索时的扩展参数。做向量检索最常配的是 `metric_type`，指定相似度怎么算：内积 `IP`、欧式距离 `L2`、还是余弦 `COSINE`。这个值必须和建索引时的度量方式一致——建索引用余弦，检索就得用余弦；当时用内积 `IP`，这里也得是 `IP`。两边不一致，算出来的分数没有意义。`search_params` 里还有 `offset`，和 `limit` 搭起来做分页。

`filter` 是在向量搜索之前先做一次标量过滤，把搜索范围缩小。

`order_by_fields` 是排序字段，默认一定不要传。不传的时候按相似度打分排；一旦传了，就按你指定的字段排了——传价格，结果就按价格排序，跟相似度没关系了。

`ids` 是按 id 做精确匹配过滤。传了 `ids=[1, 2]`，它就不再走向量查询，`data` 和 `anns_field` 也就不用给了——这两组参数是互斥的。

还有一个时区参数，平时用不上。

参数确实多，记不住很正常，用到哪个再查哪个，不必现在就背下来。

### 稠密检索：把问题转向量，再交给 search

先演示稠密检索，这也是我们一直在用的那种。前面用 LangChain 的 vector store 做检索，底层走的就是稠密向量；现在不借助 LangChain，直接在 Milvus 客户端上调，同样能做。

代码不长，逻辑就三步：问题向量化、检索、打印。

```python
def dense_search(query):
    # 第一步：把问题转成问题向量
    query_vector = embedding.embed_query(query)

    # 第二步：拿着问题向量去检索
    result = client.search(
        collection_name=collection_name,
        data=[query_vector],                # 必须是列表
        anns_field="dense",                 # 检索字段：稠密向量
        limit=3,
        output_fields=["h2", "content"],
        search_params={"metric_type": "COSINE"},
    )

    # 第三步：打印结果
    for hits in result:
        for hit in hits:
            print(hit)
```

第一步 `embed_query`。之前处理文档用的是 `embed_documents`，把文档批量转向量；现在是问题，用 `embed_query`，把用户问的这一句转成问题向量。

第二步 `client.search`，传的就是前面讲的几个参数：`collection_name` 是表名，`data` 里装问题向量（它要求是列表，所以把 `query_vector` 再套一层列表），`anns_field` 传 `dense`，`limit=3` 表示最多三条，`search_params` 里的 `metric_type` 用 `COSINE`——必须和建表时 `dense` 字段的度量方式一致，当时用的是余弦，这里就得用余弦。

`output_fields` 指定了 `h2` 和 `content`。id、dense、sparse 这些字段要不要返回？不要。检索的目的是把知识片段捞回来，真正要给模型用的是 `content` 那段正文，`h2` 是标题；向量字段返回来只是一堆数字，没用。

第三步是遍历打印，这里套了两层循环：

```text
result                一次查询的返回，是个列表
└─ hits               列表第 1 个元素：第 1 个问题向量的结果集
   ├─ hit[0]          排第 1 的文档
   ├─ hit[1]          排第 2 的文档
   └─ hit[2]          排第 3 的文档
```

为什么是两层？因为 `data` 支持传多个问题向量——用户一次问两个问题，一起搜。那返回的自然也是个列表，列表里每一项对应一个问题的结果集。我们这里只传了一个问题，它照样是列表。所以第一层遍历拿到的 `hits` 是"某个问题的结果集"，第二层遍历拿到的 `hit` 才是"一条文档"。将来传两个问题，`result` 里就会多出第二个 `hits`，装的是第二个问题的结果。

这段代码将来可以直接复制着改，改动的地方无非四样：`anns_field`（检索字段可能变）、`limit`（条数可能变）、`metric_type`（相似度算法可能变）、`output_fields`（要返回的字段可能变）。其余都是固定的。

再往深一层看，这套代码不是"稠密检索专用"的，它其实是个通用的检索骨架：把检索字段换掉、把传进去的向量换掉、把度量方式换掉，它就成了另一种检索。语法是固定的，变的只是那几个参数。

### 词对不上、语义对得上：稠密检索的用武之地

函数写好，拿个问题试一下。这次不查《论语》了，换成："教育的负面作用是什么"。

先在文档里用关键词搜一遍——搜不到。"负面作用"这四个字在我们的文档里根本不存在。但内容其实是有的：有一篇讲教育的消极功能、负向功能，人家用的词是"负向功能"。语义上"负面作用"和"负向功能"是一回事，字面上却完全对不上。关键词搜索遇到这种情况，一点办法都没有。

那语义搜索呢？我们现在写的这个稠密检索，做的就是语义检索。跑一下，搜到了三篇，id 是 15、16、21，得分分别是 0.6、0.5、0.5。

但看不到内容——因为我没传 `output_fields`。`entity` 里装的就是 `output_fields` 指定的东西，不传，默认只返回 id 和得分，文档本身不回来。把 `output_fields` 补成 `["h2", "content"]` 再跑一次，第 15 篇浮上来了：标题是"教育的功能"，内容是教育的基本原理、教育的负向功能，排第一。

这就是稠密检索或者叫语义检索的价值：它能搜到语义接近、但字面完全不同的东西。哪怕用户问的措辞和文档里的写法对不上，也能把答案捞回来。

### 专有名词一来，语义就不够用了

再看它不擅长的：关键词、专有名词。

换成"给教师的建议是谁写的"。"给教师的建议"不是随口一句，它是我们文档里的一本书的名字——这是一份教资考试的语料，文档里"给教师的建议"这种说法到处都是，因为到处都在给老师提建议。可我要找的是那本书本身。

跑一遍，第一篇是"论演说家的教育"，接着是教育家的教育思想，还有"普及教育的目的，是培养哲学王"这类内容。这些从语义上看都算"给老师提的建议"——提倡对学生进行和谐全面发展，这不就是对教师的建议吗？语义上很近，但都不是我要的那本书。真正那本书的片段被挤到了第三。

差得有点远了。这就是稠密检索的短板：它擅长语义分析，不擅长精确匹配。书名、人名、型号、代码这类专有名词，它容易被"意思相近"的内容带偏。

### 稀疏检索：连向量化都省了

稀疏检索的脾气正好反过来：擅长关键词，不擅长语义分析。

代码跟刚才那段几乎一样，只改两处。

```python
def sparse_search(query):
    result = client.search(
        collection_name=collection_name,
        data=[query],                       # 直接传原始问题字符串
        anns_field="sparse",                # 检索字段：稀疏向量
        limit=3,
        output_fields=["h2", "content"],
        search_params={"metric_type": "BM25"},
    )

    for hits in result:
        for hit in hits:
            print(hit)
```

第一处，`data` 里不再传向量，直接传原始的问题字符串，包成一个列表。为什么可以不转向量？因为稀疏向量不是我们自己生成的——建表时在 `schema` 里挂了一个把文本转成稀疏向量的 BM25 函数。有了这个函数，检索时把 query 字符串扔进去就行，Milvus 在内部替我们做转换。

第二处，`anns_field` 从 `dense` 改成 `sparse`，`metric_type` 从 `COSINE` 改成 `BM25`。稀疏向量用的是 BM25 算法，度量方式自然不能再用余弦。

其余都不动，就这两个参数的事。

还是拿刚才那两个问题试。第一个"教育的负面作用是什么"——这是语义分析，稀疏检索不擅长。搜出来的是"教育社会关系""生产力对一切起决定作用"这类内容，讲负向功能的那条根本没露面。为什么？字面上没有重合的词，BM25 靠的就是词。

反过来，"给教师的建议是谁写的"——直接命中，那本书排第一，得分非常之高。

```text
                       两条检索路线，落点不同

  稠密检索：问题 → 转成向量 → 比语义 → 捞回“意思相近”的片段
  稀疏检索：问题 → 拆成词 → 比词重 → 捞回“字面对得上”的片段
```

| 维度 | 稠密检索 | 稀疏检索 |
| :--- | :--- | :--- |
| 检索字段 | `dense` | `sparse` |
| 度量方式 | `COSINE`（须与建索引一致） | `BM25` |
| `data` 传什么 | 问题向量，自己转 | 原始问题字符串，库内 BM25 函数代转 |
| 擅长 | 语义相近，换个说法也能找到 | 专有名词、关键词精确命中 |
| 短板 | 专有名词容易被语义带偏 | 同义改写、语义相近的内容直接漏掉 |

稠密与稀疏，各有所长，也各有所短。

### 混合检索：多路召回，再融合重排

把两次演示摆在一起，结论很清楚：稀疏检索能精确匹配专业名词，但会漏掉同义说法、语义相近的内容；稠密检索擅长语义搜索，却可能错过专业名词，甚至连关键词都错过。单用哪一种，效果都不算好。

最佳方案是把两种结合起来——这就是混合检索。

混合检索的流程就两步。第一步叫多路召回：通过稀疏、稠密等多种方式分别查询文档列表，得到多个结果集。也就是说稀疏走一遍、稠密走一遍，各查各的。第二步叫融合重排：把多路召回的这些结果集融合成一个列表，重新打分、重新排序。

```text
                    向量库（成千上万篇文档）
                                │
            ┌───────────────────┴───────────────────┐
            │                                       │
                search 请求一        search 请求二
                sparse · 稀疏        dense · 稠密
            │                                       │
              结果集甲（红圈）     结果集乙（黄圈）
            └───────────────────┬───────────────────┘
                             │ 融合
                                ▼
                            重新排序
                                │
                        最终结果（绿圈）
```

读图：同一个向量库，同时发两个 search 请求，上面那个搜 `sparse vector`，下面那个搜稠密向量；两次检索各自锁定一片文档范围（红圈、黄圈），融合之后重排，得到绿色那圈最终结果，返回。

#### 多路召回不止两路

一说到多路召回，很容易以为就是稀疏加稠密两路。不是。稀疏和稠密只是最常用的那两路，在复杂场景里还有多模态检索——除了文本，图片、音频、视频都可以做搜索，以图搜图就是典型。用图片搜，本质上就是把图片转成向量，再拿这个向量去检索。

所以多路召回真的可以是多路，两路只是起步。

#### 重合的文档听谁的：三种融合重排

这里马上会冒出一个问题：稀疏有一部分结果，稠密有一部分结果，怎么合并？如果同一篇文档在两边都出现了，但排名不一样，以谁为准？两边优先级怎么定？

常见的融合重排有三种做法。

第一种是加权求和重排。稀疏检索和稠密检索都会给文档打分，那就把两边的分数按权重加起来，得到一个新分数，按新分数重排。谁的分量重，权重就往哪边偏。

第二种是 RRF，它不看分数，只看排名。同一篇文档在稀疏里排第一、在稠密里排第五，就结合这两次排名算出最终排名。这个思路像《我是歌手》：前一场比赛排个 1 到 7 名，第二场再排一轮，最后把两场的排名综合起来得出名次——只看名次，不看具体得了多少票。

第三种是 Cross Encoder，最"变态"的一种：用神经网络模型直接对结果重新打分。效果最好，但也最消耗资源。

三种方式各有取舍，落到代码上分别怎么写，从加权融合开始。

## 混合检索的三种融合路线
> 对应块：BLK36 | 覆盖分集：P140-P143 | 块标题（分集名）：《混合检索：加权融合、RRF 与重排》

前面那套稠密检索和稀疏检索的代码，我们已经一行一行跑过了。跑完你会发现一个挺尴尬的事实：这两路各有各的脾气。稠密那一路认语义，同一个意思换一种说法问，它照样能找出来；可一旦问句里出现一个具体的书名、一个人名，它就开始发虚。稀疏那一路正好反过来，关键词对上了就是死准，换一种说法立刻抓瞎。

既然两路各有一半的本事，最直接的想法就是——两路都跑，把结果合起来。混合检索干的就是这件事。而把它落地的最朴素的办法，叫加权融合。

### 加权融合：每一路先配一个权重

> **定义**：加权融合就是把多路召回的文档分配不同的权重，再按文档在每一路中的打分做加权求和，用求和的结果重新排序。

用公式写出来，两路召回是这样的：

$$score(d) = w_{dense}\cdot s_{dense}(d) + w_{sparse}\cdot s_{sparse}(d)$$

其中 $s_{dense}(d)$ 是文档 $d$ 在稠密检索里的得分，$s_{sparse}(d)$ 是它在稀疏检索里的得分，$w$ 是两个权重，满足 $w_{dense} + w_{sparse} = 1$。

举个具体数字。把稠密和稀疏的权重设成 0.6 比 0.4，同一篇文档在稠密里得分 0.5，在稀疏里得分 0.8，那它最终的得分就是：

$$0.5 \times 0.6 + 0.8 \times 0.4 = 0.3 + 0.32 = 0.62$$

稠密的得分乘稠密的权重，稀疏的得分乘稀疏的权重，两段加起来就是最终结果。就这么一条式子。

那如果还有第三路呢？权重比例就得改，不能还是 0.6 比 0.4 了。因为**权重最终相加必须等于 1，不能超过 1**——总共就一分，你得分给三路。所以加权融合是支持多路的，只是路一多，权重就得切得更细。

这里先记住这个隐患，后面还会回来找它算账。

### 分数不在一个量级，加权求和就失真

加权求和的思路本身很直白，可你只要真的把两路的分数摆到一起看，问题立刻就冒出来了。

回到前面跑过的那次检索。稀疏那一路是内置的 BM25，打出来的分是 5 分、2 分；稠密那一路走的是余弦相似度，打出来是 0.6、0.5。一边是个位数，一边是零点几，压根不是一个量级。

现在设想某一批查询里，稀疏打出 5 分、6 分，稠密还是零点几。你去加权求和：$5 \times 0.4 = 2$，$6 \times 0.4 = 2.4$；稠密那边哪怕拿到 0.9，$0.9 \times 0.6 = 0.54$。0.54 对 2.4，差了一个数量级还不止，稠密这一路的意见被彻底盖掉了。你权重调得再讲究也没用，分数尺度大的那一路直接主导了结果。

> **结论**：每一路的得分如果分值差异较大，直接加权求和就会失真。做加权求和之前，必须先对分数做归一化。

这不是某一批数据的偶然现象，是两种检索器本身的性质决定的：BM25 的分值往往落在 0 到 10 之间，零点几分、一点几分、五点几分，甚至更大；向量的余弦相似度落在 0 到 1，有时候是 -1 到 1。尺度差这么多，不加处理直接相加是没有意义的。

### 归一化：把分数折到同一把尺子上

归一化就是把这个分值按照某种方式重新算一遍，转换成 0 到 1 之间的一个数。

这个动作我们其实早就熟。以前考试有百分制，也有 150 分制，你在 150 分制里考了 140 分，要换算到百分制里，得乘一个系数走一道转换算法。归一化是一回事，只不过更狠一点——它要把 0 到 10 之间的数压进 0 到 1。

算法有很多种，常见的三个：

| 算法 | 做法 | 特点 |
| :--- | :--- | :--- |
| min-max | 用最小值、最大值把区间线性拉到 [0,1] | 最直观，但受极值影响 |
| z-score | 减去均值再除以标准差 | 对分布敏感 |
| softmax | 取指数后归一 | 会放大高分者 |

> **提示**：这些算法你一个都没听过也不要紧。它们全是现成的，不需要你去实现，只要知道该在哪儿用、会调用就行。

做完归一化，加权求和的完整流程就是下面这张图的样子。

```text
   查询
    │
    ├─► 稠密检索 ──► 原始得分 0 ~ 1
    │
    └─► 稀疏检索 ──► 原始得分 0 ~ 10
                        │
                        ▼
                   归一化函数
                        │
                        ▼
                  统一到 0 ~ 1
                        │
                        ▼
                    加权求和
                        │
                        ▼
            最终得分 ──► 重排输出
```

读图：不管分数是稠密那一路算出来的还是稀疏那一路算出来的，都不直接拿去相加，而是先统一过一个归一化函数，把量纲压到 0 到 1（或者 -1 到 1）这个区间里，然后才做加权求和，最后按求和结果排序。前后顺序不能换——先归一，后加权。

### 混合检索的三步固定流程

方案说清楚了，就该动手。混合检索的流程是固定的三步，不管后面换成哪种融合策略，骨架都不动：

```text
   ① 创建多路请求 ──► ② 配置融合策略 ──► ③ 发起请求
      稠密请求            加权 / RRF           hybrid_search
      稀疏请求            模型重排             统一执行
```

读图：先分别把每一路检索封装成一个请求对象，再挑一个融合策略（ranker），最后一次性交给混合检索接口，由它去跑多路、合并、重排。

第一路是稠密检索。稠密检索的第一步永远是**手动把 query 转成向量**，所以代码里先过一遍 embedding 模型，再拿这个向量去构造请求：

```python
# 第一路：稠密检索请求
dense_req = AnnSearchRequest(
    data=[embedding_model.embed_query(query)],  # 查询向量：先手动转向量
    anns_field="dense_vector",                  # 查询字段：稠密向量字段
    param={"metric_type": "COSINE"},            # 检索参数：余弦相似度
    limit=3,                                    # 这一路返回几条
)
```

这四个参数跟前面单独做稠密检索时用的完全是同一套：`data` 是查询向量，`anns_field` 是查询字段，`param` 是检索参数（这里用余弦），`limit` 是数量。区别只有一个——`collection_name` 和 `output_fields` 没传。因为现在还没到真正执行的时候。

第二路是稀疏检索，用的还是同一个请求类，只是参数换了：

```python
# 第二路：稀疏检索请求
sparse_req = AnnSearchRequest(
    data=[query],                        # 稀疏不用你转向量，内置 BM25
    anns_field="sparse_vector",          # 换成稀疏字段
    param={"metric_type": "BM25"},       # 换成 BM25
    limit=3,
)
```

`data` 不再传向量了——稀疏检索内置了 BM25，不需要你算向量；`anns_field` 从稠密字段换成稀疏字段；`param` 换成 BM25。这样第二路就备好了。

两路请求往一个列表里一放，多路召回就成型了：

```python
reqs = [dense_req, sparse_req]
```

接下来调的不是 `search`，而是 `hybrid_search`。hybrid 就是混合的意思：

```python
results = client.hybrid_search(
    collection_name=COLLECTION_NAME,   # 集合名，在这里统一指定
    reqs=reqs,                         # 多路请求
    ranker=ranker,                     # 融合策略
    limit=2,                           # 最终总共返回几条
    output_fields=["content"],         # 输出字段，在这里统一指定
)
```

前面两个请求里缺的 `collection_name`、`output_fields`，到这一步统一补齐了。请求对象只负责描述"这一路怎么搜"，而"搜哪个集合""返回哪些字段"是所有路共用的，所以放在最外层。

这里有两个 `limit`，别混。请求里的 `limit=3` 是"这一路各搜 3 条"，两路合起来是 6 条候选；`hybrid_search` 里的 `limit=2` 是"从这 6 条里最终选出 2 条"。也就是六选二。这个值随便填，不一定非得是 2。

最后多出来的是 `ranker`，它才是决定用哪种融合的地方。这个词值得掰一下：`rank` 不是"军衔"，是"排列"；加了 `-er` 就是排序器、专门用来排序的东西；前面再加个 `re-`（再一次），`re-ranker` 就是重排器。Milvus 把它简写成了 `ranker`，意思就是"排序方式"。

> **提示**：`hybrid_search` 里的 `ranker` 是我特意做成参数的，没写死。这样这段代码就是一段通用代码——传加权融合的 ranker，它就是加权版的混合检索；传 RRF 的 ranker，它就是 RRF 版的混合检索。将来你复用的时候，要改的只有检索字段和检索类型两处，其余不用动。

### WeightedRanker：加权的现成实现

要加权融合，就得有一个加权的 ranker。写起来只有一行——一个叫 `WeightedRanker` 的类，构造时把权重按顺序传进去：

```python
from pymilvus import WeightedRanker

ranker = WeightedRanker(0.5, 0.5)   # 两路，权重各一半，加起来等于 1
```

0.5 逗号 0.5，就是两路的权重比例，对半分。只有两路就传两个；有多路就传多个，照样要满足总和为 1。

前面讲了那么久归一化、加权求和，真到用的时候一行都不用你实现——pymilvus 里已经给封装好了，`WeightedRanker` 内部把归一化和加权求和全套逻辑都做完了，你只管给它权重。

把 ranker 和 query 一起丢进去跑两个查询：

```python
hybrid_search("教育的负面作用是什么", ranker)
hybrid_search("给教师的建议是谁写的", ranker)
```

第一个查询，"教育的负向功能"那篇文档被搜到了，虽然没排到第一，排到了第二。第二个查询，"给教师的建议"排第一。

这两个结果合起来说明了一件事：混合检索同时具备稠密检索和稀疏检索两套本事，所以不管你是问语义相关的内容，还是问关键词相关的内容，它都能给出一个像样的排名。这就是第一种方案，加权融合。

### RRF：不看分数，只看名次

加权融合有个隐含前提：你得相信两路的分数。可分数这东西太不可靠了，量纲不一样、分布不一样，还得先归一化。那能不能干脆绕开分数？

第二种融合方案叫 RRF，全称 Reciprocal Rank Fusion，翻译过来是"倒数排名融合"。这个译名不一定完全准确，但道理就是这个道理：**它不关心文档得了多少分，只关心文档排在第几名。**

公式是这样一个式子：

$$score(d) = \sum_{i=1}^{n} \frac{1}{k + rank_i(d)}$$

$rank_i(d)$ 是文档 $d$ 在第 $i$ 路检索结果里的排名位置，$k$ 是一个常量，通常取 60。

光看公式有点抽象，摆个表就清楚了。我们现在是两路召回——稠密和稀疏，假设有 A、B 两篇文档：

| 文档 | 稠密检索名次 | 稀疏检索名次 | RRF 得分 |
| :--- | :--- | :--- | :--- |
| 文档 A | 1 | 6 | $\frac{1}{60+1} + \frac{1}{60+6} = \frac{1}{61} + \frac{1}{66}$ |
| 文档 B | 4 | 3 | $\frac{1}{60+4} + \frac{1}{60+3} = \frac{1}{64} + \frac{1}{63}$ |

文档 A 在稠密里排第 1，代入公式就是 $1/(60+1) = 1/61$；在稀疏里排第 6，就是 $1/(60+6) = 1/66$。两段相加，得到 A 的最终得分。

文档 B 同理：稠密第 4 得 $1/64$，稀疏第 3 得 $1/63$，两段相加就是 B 的最终得分。两个分数一比，谁大谁靠前。

算出来的数会很小（都是六十分之一上下），但小不要紧，排序只看相对大小。

这个式子带来的效果很有意思：**排名越高，分母越小；分母越小，整个值越大。**第 1 名贡献 $1/61$，第 2 名就只有 $1/62$，往下越来越小。所以名次本身就是一种"分数"，只不过这个分数不由检索器给，而由名次换算出来。

> **易错点**：RRF 里的"排名"是名次序号，不是得分。你在两路里各拿一个名次，分别换算成一个很小的数，再相加；不是把两路的原始得分相加，也不是把名次直接相加。

这就是 RRF 的全部算法：拿名次算分，把所有路的分加起来，按总和排序。

### RRF 的取舍：不用分权重，也不认分数

RRF 的优势，恰好都长在加权融合的痛点上。

第一，它不需要分配权重。加权那套一到多路就难受：加第三路，原来的 0.5 比 0.5 就不能用了，得重新切成 0.4、0.3、0.3 这样才凑得齐一份；加第四路，前面又得重来。总共就一分，路一多，权重量根本没法分。所以加权融合不适合路太多的多路召回。RRF 完全没有这个顾虑，随便几路都行。

第二，它不用算得分，所以你分数是大是小跟它没关系，也就不需要做分数归一化。它的几条好处是连着的：

- 与分数无关，不用归一化；
- 对离群值不敏感，某一路偶尔蹦出一个特别大的分，影响不了大局；
- 计算简单，效率高；
- 可以融合任意数量的检索列表。

缺点也有两条，得记住。

一条是它对排名靠后的文档不太敏感。名次往后走，$1/(k+rank)$ 这个值越压越平——第 1 名和第 10 名分别是 $1/61$ 和 $1/70$，差得出来；再往后，相邻两名之间的差就越来越小，尾部基本分不出高低了。

另一条更要紧：**所有检索源的权重是一样的。**在 RRF 眼里，稀疏和稠密一视同仁，你是十路还是一百路，也是同权。可现实中你未必想一视同仁——比如你更看重语义，希望稠密那一路说话更算数，这时候 RRF 就处理不了了。

> **结论**：要控制"哪一路更重要"，用加权；要省掉权重和归一化的麻烦、还想随便加路，用 RRF。两者在演示里的表现也差不多——同一个问题、同一篇文档，都排到了第二；真正把精度拉开的是第三种方案。

### 换一个 ranker 就是 RRF 版本

实现起来跟加权那套一模一样，一行都不用新写。因为混合检索的函数早就把 `ranker` 留成参数了，你只要换一个 ranker 实例。

```python
from pymilvus import RRFRanker

ranker = RRFRanker()        # k 默认 60，不传就是这个值
hybrid_search("教育的负面作用是什么", ranker)
hybrid_search("给教师的建议是谁写的", ranker)
```

`RRFRanker` 构造时那个 `k`，默认是 60。默认不等于最佳——60 只是通常够用的经验值，具体多少合适要你自己调。调法也很朴素：先按默认值跑一遍，看召回结果好不好；不好就改 `k` 再跑，看是变好还是变差；继续调，直到找到最合适的那个值。权重的 0.5 比 0.5 也是同一个道理，谁也没说这就是最佳比例。

只不过绝大多数情况下，用 60 就够了，所以这个参数不传也行。

跑同样的两个查询：`教育的负面作用是什么`，"教育的负向功能"排到了第二；`给教师的建议是谁写的`，排第一。跟加权那次一样——语义检索和关键词检索都能找到对应的文档。虽然那篇没排第一，但整体还找得回来。

加权融合和 RRF 这两种融合方案，到这里就都过完了。它们解决的是"怎么把两路结果合起来"，但两路的底子还是 bi-encoder，精度也就到那儿了。想要再往上走，得换思路。

### Cross-encoder：让问题和文档一起进模型

第三种方案叫 Cross-encoder，中文译作交叉编码。什么叫交叉？**把用户的问题和文档一起输入给模型，让模型对它俩做交叉运算，从而精确打分。**

为什么这件事值得单独起个名字？因为在它之前，我们干的全是反着的事。

回想一下离线阶段和在线阶段的分工：离线阶段把一篇篇文档转成向量存起来，在线阶段把用户的问题转成向量，最后拿两个向量去比。问题和文档从头到尾是分开处理的，各自进各自的编码器，只在最后一步拿向量碰了个面。

这种分别处理的模式叫 bi-encoder，也就是双塔编码、并行编码。

它的问题在于：模型拿到文档的时候没看到问题，拿到问题的时候没看到文档，两者在运算过程中根本没有放在一起比较过，只比了各自最后吐出的那个向量。信息在压缩成向量的那一步就丢掉了一部分，所以准确度会差一点。

但它的速度极快。因为它把工作劈成了两半：离线阶段可以把数以千万甚至数以亿计的文档全部转好，在线阶段只转一个问题。查询时的开销只有一次 embedding。

> **结论**：bi-encoder 精度差一点、速度快，适合做初筛——也就是初步筛选。我们前面讲的稠密检索和稀疏检索，都属于 bi-encoder 这一路。

Cross-encoder 反过来：同一个模型、同一时刻，把文档和问题一起传进去，一起算。这时候模型是真的能比较"这个问题"和"这段文档"之间的关系——是不是在回答同一件事、关键词有没有对上、语义有没有偏移，它都能看见。所以它给出的得分和排名，准确度要高得多。

代价是慢。每一条候选文档都要跟问题配成一对，送进模型跑一遍完整的前向计算，没法像 bi-encoder 那样离线预计算。

所以它的位置很清楚：**做精排。**如果说前面那套是初筛或初排，这一步就是更精细的处理，准确度更高，速度更慢、效率更低。

于是工业界的常规组合就出来了：

```text
   查询
    │
    ├─► 稀疏检索 ──► 召回 10 条
    │
    └─► 稠密检索 ──► 召回 10 条
                        │
                        ▼
                  20 条候选结果
                        │
                        ▼
              cross-encoder 逐对打分
                        │
                        ▼
                    最终排名
```

读图：先用 bi-encoder 那套（稀疏、稠密随便组合）做初步筛选，稀疏搜出十条、稠密搜出十条，二十条一起扔给 cross-encoder 这种专用模型，由它重新打分、重新排序，得到最终排名。

注意这一步的性质变了：这次的融合既不是加权，也不是 RRF，是**模型在融合**。所以整个方案的关键不在融合算法，而在于那个负责重排的模型。

### 重排模型怎么挑

Cross-encoder 不是随便拿个向量模型改改就能用的，它需要专业的 re-rank 模型。

市面上常见的有这么几类，效果、排名、适用场景各不相同。

千问系列的重排模型，比如 Qwen3-Reranker-4B，是这一类里相当能打的：支持的上下文长度高达 32K，也就是说你塞进去的文档片段可以很长，32K 都扛得住；精准度也高，能拿到 70 多分——在这个任务上，70 多分已经是很高的分数了；而且是中英文都行。

另一类是 bge 系的重排模型，比如 bge-reranker-v2-m3。它主打中英文混合场景，特点是**小**：参数规模五百多 M，也就是 0.5B 左右。对比千问那个 4B，差了将近一个数量级。社区里用得最多的就是它，因为体积小，占用的资源也小。

还有一类只擅长外语，中文表现不太好，选的时候要留意——中英文混合的语料上，这类模型会明显掉分。

> **提示**：看模型卡上的参数规模别被单位绕晕。这里比的是同一个量级：0.5B（五亿）和 4B（四十亿），后者是前者的八倍左右，能力更强、占的显存也更多。

怎么选，按部署方式分两条路：

| 场景 | 推荐 | 理由 |
| :--- | :--- | :--- |
| 公司内网本地部署 | bge-reranker | 体积小，占用的计算资源少 |
| 调云端模型 | 千问 rerank | 性能最强，32K 上下文，中英文俱佳 |

如果你要在自己公司的服务器上部署，就选 bge-reranker，因为体积小、占用资源少、计算压力小。如果你打算用云模型，那就用千问。

云上的入口在阿里云百炼：模型广场 → 全部模型 → 文本向量模型，里面能看到千问的 rerank 系列，而且不止一种 rerank 模型，可以按需挑。

### Milvus 把重排做成了内置能力

好消息是，这套流程不用我们自己搭。Milvus 天然支持 cross-encoder 重排，而入口还是那个 `ranker`——我们前面写的那段混合检索函数，一个字都不用改，只是把 `ranker` 从加权或 RRF 换成一个 Milvus 自带的 cross-encoder ranker，它就变成了模型重排。

整个流程长这样：

```text
   用户提问
      │
      ▼
   多路检索（稀疏 + 稠密，可多路）──► 召回候选结果（如 10 + 10 = 20 条）
      │
      ▼
   Ranker：把 (query, document) 成对送进重排模型
      │
      ▼
   模型逐对重新打分 ──► 按新分数重排 ──► 最终结果返回给业务代码
```

读图：我们向 Milvus 发一个请求，它先执行标量检索和向量检索（也就是混合检索）拿到候选结果，再把候选结果交给 ranker 模型。模型工作时把 query 和 document 作为一对一起送进去重新打分——这一点是 cross-encoder 的关键，发的是原始文档和原始问题，不是向量——然后按新分数重排，最后把结果返回。

那这个模型从哪来？Milvus 支持多家外部模型服务商，大致可以分成两类：一类是**自己部署**的模型服务，一类是**别人部署好、你直接用**的平台。

| 提供方 | 形态 | 说明 |
| :--- | :--- | :--- |
| vLLM | 自部署 | 类似 Ollama，但面向生产环境，只能在 Linux 上跑 |
| TEI | 自部署 | 轻量级模型服务，比 vLLM 更轻 |
| Cohere | 外部服务 | 一类专门的重排模型服务 |
| DashScope | 云平台 | 阿里云，Milvus 3.x 起支持 |
| SiliconFlow | 云平台 | 硅基流动 |
| HuggingFace | 云平台 | 抱抱脸 |

vLLM 可以理解成一个更专业的 Ollama：Ollama 是桌面级、自己玩玩的，生产环境一般用 vLLM。但 vLLM 只能在 Linux 系统上跑，Windows 上跑不了，所以这里不展开。TEI 同样是自部署，只是更轻量一点。

下面三个是平台，不需要你部署，别人部署好了你直接用：硅基流动（SiliconFlow）、DashScope（阿里云）、HuggingFace（抱抱脸）。

这三个里只有 DashScope 是国产的，而且不用自己部署，就用它。

> **注意**：DashScope 作为重排提供方，是 Milvus 3.x 版本才开始支持的。如果公司里用的是老版本，这一路走不通。我们现在装的是 3.0，刚好落在支持范围内。

前面那些自部署的方案其实也能用，但部署起来太麻烦，公司里有人部署好了你再用就行；没人部署，就走 DashScope。官方文档里每种重排模型怎么配都写得很细——vLLM 怎么用、TEI 怎么用、硅基流动怎么用，这里只讲 DashScope 这一种。

### 把密钥交给 Milvus

第一件事是配密钥。不管用哪家服务商——阿里云也好、硅基流动也好——都得有一个 API Key，这个在阿里云百炼里申请，你应该已经申请过了。

关键在于把这个 Key 交给谁。不是给我，不是给代码，**是给 Milvus**。因为最终是 Milvus 去调那个重排模型，调用关系发生在 Milvus 和阿里云之间，业务代码并不直接参与。

配置位置在虚拟机的 `deployed` 目录下：

```text
   deployed/
   └── milvus/
       └── user.yaml        ← 要改的就是这个文件
```

打开 `user.yaml`，找到 `credential.dashscope.api_key` 这一项，结构大致是这样：

```yaml
credential:
  dashscope:
    api_key: <你的 DashScope API Key>
```

把申请到的 Key 粘进去，编辑器会自动保存。

配完之后必须重启 Milvus，否则它读不到新配置：

```bash
docker compose restart
```

> **易错点**：这条命令必须在 `deployed` 目录下执行，也就是 `docker-compose.yml` 所在的那个目录。换个目录执行，命令根本找不到要重启的容器。

重启之后，Milvus 会重新读一遍配置，把刚才写进去的 Key 加载进来。到这一步，Milvus 就具备了调用 DashScope 重排模型的能力。

### 用 Function 造一个重排器

准备工作做完，下一步是定义 ranker。这个 ranker 比前面两个麻烦一点，因为它创建的时候要带着 query 一起造——重排模型必须知道"拿什么去跟文档比"，所以问题得提前传进去。

```python
from pymilvus import Function, FunctionType

def build_ranker(queries: list[str]) -> Function:
    return Function(
        name="dashscope_rerank",                 # 名字可自定义
        input_field_names=["content"],           # 原始文档字段，不是向量
        function_type=FunctionType.RERANK,       # 固定值
        params={
            "reranker": "model",                 # 用模型做重排
            "provider": "dashscope",             # 模型由谁提供
            "model_name": "gte-rerank-v2",       # 具体模型
            "queries": queries,                  # 查询条件，必须是列表
            "batch_size": 32,                    # 一次发多少条
        },
    )
```

这段代码基本是固定的，直接从官方文档拷过来就行。逐项看一下：

`name` 是这个重排器自己的名字，将来可以自定义，但没必要改，按默认的写就行。

`input_field_names` 指的是**原始文档字段**。这一项最容易想错——做 cross-encoder 时，要传给模型的是原始文档内容，不是向量。模型自己拿原始文档和原始的用户问题去打分。所以这里填的是文档里存正文的那个字段名，比如 `content`。你的字段要是叫别的名字，这里就得跟着改。

`function_type` 是固定值，写 `FunctionType.RERANK`。

`params` 里几个键各有分工：

- `reranker` 写 `"model"`，意思是基于模型做重排，也就是 cross-encoder。这是固定的，不要动。
- `provider` 指这个模型由谁提供。阿里提供就写 `dashscope`；换成硅基流动就写硅基流动；换成 vLLM 就写 `vllm`。这一项会变。
- `model_name` 填具体模型名，这里用的是 `gte-rerank-v2`，是阿里云百炼文本向量模型里的一个。上面还有别的 rerank 模型，理论上也能用，这里先用它。这一项也会变。
- `queries` 是查询条件。模型要把查询和文档一起发过去，所以这里放的就是用户的查询条件。它**必须是个列表**，所以我在函数签名上就把 `queries` 定义成列表参数——将来传进来不同的问题，就能生成不同的 ranker。
- `batch_size` 是批处理的文档数量，也就是向模型发请求做重排时，一次发多少条。它可以批量处理，不用一条一条发。

> **提示**：官方示例里有一处把单个 query 字符串直接传给了 `queries`，而这里要的是列表。照抄的时候记得补一层方括号，或者按上面这样把 `queries` 声明成列表参数。

所以将来需要改的只有四处：`provider`、模型名、`queries`、文档字段名。其余照抄，不用动。

### 跑通模型精排

把 ranker 生成函数定义好，剩下的事情跟前面两次没有区别：

```python
query = "教育的负面作用是什么"

results = hybrid_search(query, build_ranker([query]))
```

只是要留意这里有两个 query：`hybrid_search` 的第一个参数是这次检索用的查询，`build_ranker([query])` 里那个是拿去生成 ranker 的查询。两者分开发，因为一个是"搜索要搜什么"，另一个是"模型重排时拿什么跟文档配对"，虽然现在填的是同一句话，语义位置不同。

这次会慢一些，因为请求绕出去调了阿里云。

第一个查询，"教育的负向功能"排第一。这里值得对比一下：刚才用加权和 RRF 的时候，这篇文档都没排到第一，都排到了第二。现在换成模型排序，准确度明显高了一档——虽然慢一点，但准。

第二个查询，"给教师的建议是谁写的"，依然排第一。这次很快，200ms 左右。

> **结论**：用 cross-encoder 让模型做精排，排序效果非常好。只要是真正相关的文档，它一定会排到前面。

三种方案到这里就都过完了。最后把过程收一下：所谓 cross-encoder 融合，说到底就是先定义一个函数，这个函数的作用是**生成重排器**——你只要把 query 给它，它就能给你生成一个重排器；检索的时候创建这个重排器，把 query 和重排器一起交给 `hybrid_search`，剩下的它自己完成。

### 三条路怎么挑

三种方案摆在一起，差别一目了然：

| 方案 | 排序依据 | 要不要归一化 | 要调什么 | 多路扩展 | 精度 | 速度 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 加权融合 | 各路原始得分 × 权重 | 要 | 权重（和为 1） | 差，路多权重难分 | 中 | 快 |
| RRF | 各路名次换算出的倒数 | 不要 | `k`（默认 60） | 好，任意路数 | 中 | 快 |
| Cross-encoder | 模型对（query, document）的打分 | 不要 | provider、模型名 | 好 | 高 | 慢 |

前两种是"算分"的路子：一个信分数、一个信名次，都靠数学把多路结果拼起来，快但精度有限。第三种是"请外援"的路子：把候选集交给专业模型重新判一遍，准但慢，还得依赖外部模型服务。

所以它们不是三选一的关系，常见的用法是串起来：先用 bi-encoder（稀疏 + 稠密，走加权或 RRF）把候选缩到十几二十条，再用 cross-encoder 在这小批量上做精排。初筛负责"不漏"，精排负责"排得准"——候选集越小，模型重排的开销越可控，这也是为什么精排一定要放在初筛后面，而不是拿它去扫全库。

真要在前两种里选一个：需要压某一路的权重、明确知道语义该更重，用加权；路数会涨、懒得维护权重，用 RRF。而只要对最终排名有要求，最后一棒交给 cross-encoder。

## 先过滤，再检索：Milvus 条件过滤与 LangChain 集成
> 对应块：BLK37 | 覆盖分集：P144-P147 | 块标题（分集名）：《Milvus 条件过滤与 LangChain 集成》

### 检索之外，还需要一道过滤

到这里，检索是不是就没有任何问题了？接下来我们要聊的是对检索的一种补充——过滤。

向量搜索是为了找出最相关的文档；而过滤的作用，是缩小搜索的范围，从而提高检索效率。这话听着有点抽象，落到 Milvus 上就很具体：它支持我们先通过标量字段做一次过滤，过滤完了以后再来做向量检索。

举个例子。collection 里有四个字段：`id`、`vector`、`chunk`、`data`。`chunk` 可以理解成片段，`vector` 就是向量。搜索的时候传两个参数，第一个是查询向量，第二个是 `filter`：

```python
filter='chunk like "%red%"'
```

这写法像不像 SQL 语句？非常像。Milvus 就是故意这么设计的，为的是兼容数据库的语法。因为这种针对非向量字段的检索，本质上就是标量检索，它干的事跟数据库很像，所以干脆借了数据库的写法。上面这句话的意思就是：先到 collection 这张表里，看看哪些文档的 `chunk` 里包含 `red`；筛出这批文档之后，再在这批文档里做向量检索。

```text
              collection（全部文档）
                       │
                       ▼
        filter: chunk like "%red%"     ← 先按标量字段过滤
                       │
                       ▼
              缩小后的候选文档子集
                       │
                       ▼
        向量检索: 用 query 向量算相似度
                       │
                       ▼
               最相关的若干条文档
```

看图就明白了：如果整个框是完整的 collection，那么经过 filter 过滤以后，一定能够锁定其中的一个范围，检索范围就缩小了；在这个范围里再做向量检索，范围小了，搜索的效率自然也就高了。所谓过滤，干的就是这么一件事。

那在咱们的项目里，将来需不需要这个东西？必须用。为什么呢？我们是一家保险商城，商城里的保险条款会非常多，每一个保险产品都有自己的保险条款。

注意听，我再说一遍：每一个保险产品都有自己的保险条款。比如说同样是重疾险，复星联合的重疾险、优选康的重疾险、信美相互的重疾险，这三个都是重疾险，它们的条款有很多相似之处——因为都是重疾险嘛，但肯定也有大量的不同之处。

现在所有的条款将来都会放到同一个 collection 里面去，也就是同一张表里。因为它们的身份都是"条款"，所以都往一个地方放。

那么现在用户来问：信美相互星辰守护这款产品，条款里"等待期"是怎么规定的？你拿这个问题去表里搜"等待期"，会搜到很多跟等待期有关的条款——这款产品里有，那款产品里也有，凡是出现过"等待期"这个概念的可能都被搜出来了。因为你把所有条款都存进去了。

搜出来这么多条，它们可不一定都是星辰守护的。你拿着别家产品的条款去回答用户的问题，回答一定是错的。大家想是不是这样？

所以怎么办？将来在咱们的 collection 中，一定会把产品的名字放进去，作为一个过滤条件。相当于先用产品名做过滤，把筛选范围缩减到一个具体的产品，然后在这个产品的条款片段里边，再去检索出与用户问题相关的那个片段。这个逻辑能理解吧？

> **结论**：filter 非常的重要。它不参与"像不像"，它只负责"是不是这个产品的"。

### 过滤语法就是 SQL 的 where

那怎么去做这种 filter 呢？Milvus 里的 filter 过滤语法，跟 MySQL 里的 where 条件几乎一模一样。

它就是一个字符串，可以写 `=`、`!=`、`>`、`<`、`>=`、`<=`，可以写 `like`，还可以写 `in`，等等等等，我就不一一赘述了，大家可以自己去看文档。

除此以外还有正则表达式，还有算术运算符——能做加减乘除；还有位运算；还有逻辑运算 `and`、`or`。有人问数据库里有 `or` 吗？当然有，数据库里也有 `and`、`or`，所以它这边也支持。

基本上跟我们在 MySQL 里写 where 的语法非常像，因此学习成本极低。你只要知道它能做这个过滤就够了，具体某个操作符怎么写，翻文档就行。

### 给 search 加一个 filter 参数

过滤放在哪？就放在最开始讲的那个 `dense_search` 里。`search` 的时候是支持 `filter` 参数的。

如果我想给 `dense_search` 添加过滤功能，只需要在后面加一个参数就可以了，叫 `filter_query`，类型是字符串或者 `None`，给个默认值 `None` 就行——也就是说，可以填，也可以不填。

```python
def dense_search(self, query: str, filter_query: str | None = None):
    ...
    results = self.client.search(
        ...,
        filter=filter_query,
    )
```

填了的话，就把它拼到 Milvus 的 `filter` 参数上去；没填就是 `None`，相当于不启用过滤。

我们试一下。正常搜索是没问题的：搜"教育的负面作用是什么"，能搜到；搜"给教师的建议是谁写的"，也能搜到，但排名在第三。这是没有任何过滤的情况。

现在我加上 `filter_query`。先看一个前提：这个过滤必须根据普通标量字段来做，`h2` 和 `content` 都属于标量字段，所以可以拿它们过滤；不能根据向量字段过滤。

比如我要求内容里必须出现"给教师的建议"：

```python
filter_query='content like "%给教师的建议%"'
```

这里有个引号的小坑。`like` 后面跟的那个字符串，里面必须写成双引号，那外边就只能写单引号，不然会冲突。字符串本来就可以用单引号，也可以用双引号，我们里面写双引号，外面就写单引号。

效果怎么样？原本能搜到好几条，加了条件以后是不是就只剩这一条了？因为我先做了过滤，要求内容里必须有"给教师的建议"，再来搜，就只能搜到这一条。

上面那条也一样，用等值过滤：

```python
filter_query='h2 == "教育的功能"'
```

因为值里带空格，必须加引号，单引号双引号都行。这样搜下来也只剩一条，因为强调了 `h2` 必须是"教育的功能"。

所以说，用 `like` 也好，用等值也好，都可以，其实就是这么做的。

那既然 `dense_search` 里能加，其他 search 里能不能加？比如混合检索。混合检索这个方法目前传了 `query`、传了 ranker，那我能不能让它再传一个 `filter`？可以传。这个 `filter` 加进去以后，稠密和稀疏两条路都带上 `filter_query`，然后搜索的时候把这个参数传进去，就还是这个效果：当前搜到两条，加上 `h2` 的等值条件，就只剩一条了。

> **注意**：这个参数可传可不传，想传就传，不想传就算了。千万不能弄成必传的——弄成必传，就相当于每次都必须有过滤条件了。

### 为什么还要再学一套 LangChain 的写法

前面学的都是基于 Milvus 的官方客户端。用它写代码，写着写着大家也发现了：其实还是有点繁琐。所以接下来我们学 LangChain Milvus，用它来写，代码就会非常简单。

那有人要问：既然如此，为什么不直接学 LangChain 呢？因为 LangChain 虽然用起来更简单，但它存在一些限制：

- 混合检索只支持稀疏和稠密两种方式，你想实现更多方式，不行；
- 不支持多模态的向量检索；
- 不支持对普通字段加索引；
- 稀疏检索只支持 BM25，不支持基于模型的稀疏向量检索。

所以它有很多很多的限制。不过大多数场景已经够我们用了——八九十%的情况下，已经能够满足我们的需求。所以我们就来学一下 LangChain 这种方案，因为它更简单。

### 准备工作：文档和向量模型照旧

第一步是安装依赖。不过大家也不用装，项目里我已经给大家装好了。

第二步是准备文档，这段代码还要再写一遍，放到新建的 LangChain Milvus 演示文件里。

准备文档的代码跟刚才完全一样：读那份 Markdown，用切分器做切分，切完得到 docs。唯一的区别是在 for 循环里加 id 那一步——我们不加了。因为加 id 有很多同学觉得有点晕，这次咱就不加了，切完直接返回，跟刚才一模一样。

不加 id 会有一个什么问题呢？将来这个 id 由谁生成？由 Milvus 自动生成。自动生成的 id 会比较大，而我们自己写，可以从 1 开始，就这么一个区别。当然，将来如果要加 id，你应该知道怎么加：在遍历 docs 的过程中给它塞一个 id 就行。这次我们就原生地让 Milvus 帮我们生成 id。

文档准备好了，第一步搞定。第二步依然需要向量模型，这里还是用 Ollama。两个准备工作全部做好。

### 初始化 Milvus vector store

第三步，初始化 vector store。这里先回忆一下：在 LangChain 里，咱们之前用的 vector store 是 `InMemoryVectorStore`，创建的时候就是空参，直接一句 `vector_store = InMemoryVectorStore(...)` 就完了，然后就能用它里面的几个方法：

- `add_documents`：批量添加文档；
- `delete`：删文档；
- `similarity_search`：相似度搜索。

就这三个函数，有没有印象？接下来我们还是按这个逻辑走，唯一的区别是 vector store 换了，不再是 InMemory 了。

```python
from langchain_milvus import Milvus, BM25BuiltInFunction

vector_store = Milvus(
    embedding_function=embeddings,        # 稠密向量模型
    collection_name="langchain_collection",
    builtin_function=BM25BuiltInFunction(),
    vector_field=["dense", "sparse"],     # 顺序不能反
    connection_args={"uri": "http://127.0.0.1:19530"},
    drop_old=True,
)
```

这里面的参数，一个个说清楚。

`embedding_function` 是向量模型。我们一直在强调，vector store 自带向量模型——只要给了向量模型，它就能利用模型自动做向量化，需不需要你手动转？不需要。所以在 `add_documents` 的时候可以直接填文档，不用手动生成向量。这里指定的是稠密向量模型，将来它自动根据 `page_content` 生成稠密向量。

`collection_name` 是集合名，将来要创建的 collection 就叫这个。不用你手动创建。

`builtin_function` 指定 `BM25BuiltInFunction()`。刚才我们在官方客户端里是手动创建了一个 BM25 的 function，现在不用创建了——BM25 这个 function 已经被 LangChain 内置了，直接指定就行。

`vector_field` 是手动指定向量字段名。注意顺序：第一个是稠密向量，第二个是稀疏向量。第一个字段名默认会被当成稠密向量的字段名，第二个会被当成稀疏向量的字段名。所以这两个名字一定要起好，别把 `sparse` 放第一个、`dense` 放第二个——它是按位置来的，不是按名字来的。你在这起了 `dense` 和 `sparse`，它就自动把 `text` 里的原始文本，用你提供的向量模型转成稠密向量存到第一个字段，再用你提供的 BM25 function 转成稀疏向量存到第二个字段。

`connection_args` 是连接参数。毕竟它也是个 vector store，要连咱们虚拟机上的 Milvus，`uri` 就是那个连接的地址。

`index_params` 是索引参数。如果你要自定义索引，这个是一定要指定的；但我们现在没有这个需求——它默认会自动给稠密向量和稀疏向量加索引。所以这里不传。真想手动加索引，就得把稠密、稀疏那两套索引代码都拿过去，现在用不上。

`drop_old=True` 的意思是：创建的时候是否自动删除已有的 collection，从而避免重复创建。

> **对比**：用官方客户端时，准备 schema、准备 index、最后创建 collection，这一大段代码一行都不用写。回到这边，指定向量模型、集合名、BM25 function、向量字段名、连接参数，就完事了。

### schema 是 LangChain 替你推出来的

有同学马上会问：不对呀，字段都不指定，它怎么知道？`id` 字段、`dense`、`sparse`、`h1`、`h2`、`h3`，这些都不用指定吗？

不用。这里非常关键：LangChain 会自动根据 Document 中的数据来生成 schema。注意，这个 schema 不是我们填的，而是基于 Document 里的数据生成的。

而 Document 长什么样？就三个东西：`id`、`page_content`、`metadata`。

```text
        Document
        ├── id            ──────────────►  pk        （固定名，主键）
        ├── page_content  ──────────────►  text      （固定名，原文）
        └── metadata
            ├── h1        ──────────────►  h1        （普通标量字段）
            ├── h2        ──────────────►  h2
            └── h3        ──────────────►  h3
                              text ──┬──►  dense     （embedding 模型生成）
                                     └──►  sparse    （BM25 生成）
```

看图：左边是 Document，右边是它推导出来的 collection 字段，一一对应。

第一个固定字段叫 `pk`，也就是主键。它不叫 `id`——哪怕你给它起名叫 id，它也不叫 id，它就叫 `pk`。如果你提供了 id，就用你的 id 值，但字段名还是 `pk`；如果没有指定 id，就由 Milvus 自动生成。

第二个固定字段叫 `text`，就是原始文本字段，对应 Document 里的 `page_content`。你之前起名叫 `content`，到这里它也不叫 content，就叫 `text`，固定名。

id 和 page_content 都确定了，还差什么？还差 `metadata`。metadata 会被展开：其中的每一个字段都会成为 collection 里的一个普通字段。比如这里 metadata 有三个字段 `h1`、`h2`、`h3`，那么这三个就会成为最终 schema 里的普通字段，都是字符串。

最后是向量字段。它会自动根据 `text` 的值生成稠密和稀疏向量，名字可以自定义——你指定叫 `dense`、`sparse`，还是叫别的，都行；但值是它自动生成的。这个逻辑能不能理解：名字你定，值它生成。

| Document 里的部分 | 落到 collection 的字段 | 说明 |
| :--- | :--- | :--- |
| `id` | `pk` | 固定字段名，不叫 id；不提供则由 Milvus 生成 |
| `page_content` | `text` | 固定字段名，存原始文本 |
| `metadata.h1/h2/h3` | `h1`/`h2`/`h3` | metadata 摊平成普通标量字段 |
| `text` + 向量模型 | `dense` | 名字自定义，值自动生成 |
| `text` + BM25 | `sparse` | 名字自定义，值自动生成 |

所以以这篇文档为例，最终一条记录里有七个字段：`pk`、`text`、`dense`、`sparse`、`h1`、`h2`、`h3`。将来一定会生成这样一个结构。

还有一个细节：它会自动给向量字段加索引，其他字段不会加。

这里有个特别容易误会的地方——vector store 创建好了，collection 创建了吗？没有。为什么？因为 schema 是根据 Document 里的数据生成的，而我们现在还没往里填 Document。所以此刻并没有 collection，到这一步我们只是把 vector store 这个对象创建好了。

### 批量新增与去 ATTU 验货

第四步，往里边添加数据。调哪个函数？`add_documents`。刚才刚回顾完，vector store 三个函数：批量新增、删除、搜索。新增就是它。

添谁呢？添刚才准备好的 docs。docs 里现在有没有 id？没有。没有的话它会自动生成 id，直接往上填就好了，不用你转向量，不用你做任何处理。

```python
vector_store.add_documents(docs)
```

运行一下，会看到一个警告：你没有提供 id，所以它会自动生成 id。生成好了，去浏览器里的 ATTU 刷新一下，看有没有 `langchain_collection`。点进去看字段：`text`、`pk`、`dense`、`sparse`、`h1`、`h2`、`h3`——跟刚才分析的完全一样。

再看数据，21 条全部插进来了。`pk` 是自动生成的，从 90 开始一条条往上排。表结构是自动生成的，主键也是自动生成的。

到这里，vector store 的初始化加批量新增就演示完了。

顺带说一句，新增那一套里其实还支持 `upsert`：按 id 先删除再新增，id 存在就修改，id 不存在就新增。这次我们不用它，我们做删除。

### 删除：传一组 id

新增的时候因为没有填 id，用的是自动生成的 id，所以删除也只能用这个 id。

```python
vector_store.delete(ids=[90])
```

它接收的是一个 id 集合，一个 list。但你看它很变态，声明里要求里面传字符串。可我们的 id 其实是数字——因为 id 是自动生成的，它就是数字。那我们传个数字试试，行不行？返回 True，去 ATTU 刷新，90 那条确实删掉了。

也就是说，虽然它要求字符串，但我们传数字没有问题。

> **提示**：这是它 API 设计时类型标注写得不够严谨，但实际传参没问题，不用为了迁就标注去手动 `str()` 一层。

### 检索：加权与 RRF 两种重排

最后一个，检索。vector store 的检索我们都知道，就是 `similarity_search`：想看得分就加一个 `with_score`，不想看就直接 `similarity_search`；传 `query` 是查询条件，传 `k` 是查询的文档数量。

但是别忘了，我们之前检索是普通检索，今天可是学了混合检索。混合检索牵扯到重排策略的问题：你用加权重排，还是 RRF 重排，还是 cross-encoder 重排？混合有这么三种融合重排的策略，所以你需要去传这个重排策略。

在 LangChain 里就是多了一个参数 `rank_type`（重排策略），目前只支持两种：`weighted` 和 `rrf`。然后还要指定 `rank_params`，也就是重排的参数。重排参数是可以不一样的，你可以手动指定，比如权重 `0.4`、`0.6`，或者 `k` 取 60。也就是说，如果你的重排类型是 weighted，传参数的时候就传 weights；如果重排策略是 RRF，传参数就传 `k`。

```python
result = vector_store.similarity_search_with_score(
    query="给教师的建议是谁写的",
    k=4,
    rank_type="weighted",
    rank_params={"weights": [0.4, 0.6]},
)
```

> **注意**：在 LangChain 当中，一旦你加入了稠密、稀疏向量，它默认就会开启加权混合检索。也就是说，现在你想做纯粹的稠密检索，做不了了；想做纯粹的稀疏检索，也做不了了。这是 LangChain 这个 Milvus 封装的一个限制——一旦加入了稀疏向量，将来它必然会做混合检索。这也是它不够灵活的一个点。

带得分搜索，返回值是一个列表，列表里装的是元组：先是文档，再是得分。所以后面处理的时候也要按这个顺序 unpack。

```python
for doc, score in result:
    print(score)
    print(doc.model_dump_json(indent=2))
```

这里还有一个很尴尬的点：`rank_type` 这个参数没有类型提示，IDE 不给你补全。没有提示的情况下，是不是就很容易写错？所以我建议大家不要手写。我手敲的时候把 `weighted` 敲成了 `waited`，`rank_params` 也拼错，错得太多，干脆不手写了，复制。

### 一个分词器引发的排序 bug

第一次跑加权融合的检索，搜"给教师的建议是谁写的"，结果竟然没排到第一，排第二。这不对呀，加了权重怎么还排第二呢？

回到文档看 `text` 字段用的分词器：标准分词器（standard）。这就找到原因了——标准分词器在做关键字检索的时候，没有办法对中文做准确的分析。这算是测出来一个 bug。

怎么修？先把 collection 删掉，重新来。原来我们添加字段时指定过 `analyzer_params={"type": "chinese"}`，在 LangChain 里，这个指定放在 `BM25BuiltInFunction` 里面：

```python
builtin_function=BM25BuiltInFunction(
    analyzer_params={"type": "chinese"},
)
```

比较特殊，分词器是在这个内置函数里指定的，不是在字段上。这样一来，它就知道你用的分词器是中文分词器了。

然后重新跑一遍建库、插数据。去 ATTU 里看这个 `text` 字段，显示的分词器还是 standard——我怀疑是不是没加载，刷新、重新加载，还是标准，这不应该啊。

别急着下结论，直接拿检索结果验证。再搜一次"给教师的建议是谁写的"，排第一了。所以看起来好像没生效，但其实生效了。刚才为什么失败？就是分词的原因：指定的时候忘了指定分词器，它用的是英文分词，中文切不准；指定成中文分词之后，同样的检索就正常了。

> **提示**：改完分词器要重建 collection 才生效（`drop_old=True` 或手动删掉重来）；ATTU 里字段信息有显示滞后，别拿界面当唯一判据，用检索结果验证最可靠。

那如果想用 RRF 呢？要改的只是 `rank_type`：

```python
result = vector_store.similarity_search_with_score(
    query="给教师的建议是谁写的",
    rank_type="rrf",
)
```

这时候它不需要 weights 了，需要的是一个 `k`。不传行不行？默认就是 60，也可以。同样排第一，只是得分不一样——RRF 的得分比较小，零点几，但排名还是第一。

### 过滤在 LangChain 里叫 expr

差点把过滤忘了。LangChain 里的过滤是基于表达式来做的，参数名叫 `expr`，语法还是 MySQL 那种写法。

```python
result = vector_store.similarity_search(
    query="教育的功能",
    expr='h3 like "%代表人物%"',
)
```

先不过滤搜一下，能搜到好几篇文档：这篇排第一，后面还有第二、第三、第四。加上 `expr` 之后再看，只剩两篇，而且这两篇里都有"代表人物"。

命名确实奇怪，它不叫 filter，叫 `expr`，不知道为什么要这么起名。但传参的方式跟以前一样，单引号双引号都可以。

### 自己造一个 Cross-Encoder 重排器

最后一种是 cross-encoder 混合检索，这个就比较麻烦了。

LangChain 默认是不支持 cross-encoder 混合检索的——刚才说过，它的 `rank_type` 只支持两种。要用 cross-encoder，就得自定义 ranker，这个咱们上节课讲过：从 Milvus 官方 SDK 里拿到，自己定义出来。

有一个变化要特别注意：定义的时候 `input_field` 不能再写 `content` 了，要写成 `text`。因为 LangChain 把原始文档存在 `text` 字段里，不再是原来那个 `content` 字段。

然后定义一个函数 `cross_encoder_search(query)`，做两步：第一步创建 ranker，把 query 以列表的形式传进去；第二步调用 `similarity_search` 做检索。

```python
def cross_encoder_search(query, expr=None):
    # 第一步：用交叉编码器把 query 包成一个 ranker，字段名用 text
    ranker = create_cross_encoder_ranker([query])

    # 第二步：检索时不再传 rank_type / rank_params，改传 ranker
    result = vector_store.similarity_search(
        query=query,
        ranker=ranker,
        expr=expr,
    )

    for doc, score in result:
        print(score)
        print(doc.model_dump_json(indent=2))

    return result
```

调检索的时候，原来的 `rank_type`、`rank_params` 这俩还要不要了？不要了，人家不让传了，要传的是 `ranker`。`k` 和 `fetch_k` 可以不指定。

> **提示**：这个参数名在官方文档里查不到。我是自己翻源码找到它有这么个参数，然后再填进去的——所以这段别指望靠文档补全，照抄就完了。

如果还想加过滤，就在这个函数里加一个参数，默认给 `None`，想过滤就传 `expr` 进来。这样就封装成了一个既能查询、又能过滤、而且用的是 cross-encoder 检索的函数。

打印结果的时候注意顺序：`doc` 在前、`score` 在后。我一开始写反了，写成 score 在前、doc 在后，结果怎么都打印不出文档来——因为元组的顺序就是先文档后得分。

试一下：搜"给教师的建议是谁写的"，排第一；搜"教育的负面作用是什么"，也排第一。到这，基于 LangChain 的 cross-encoder 混合检索就实现了。

将来完全可以把这段封装成一个函数，凡是要用就调这个方法，传一个 query 进去，就能自动完成检索。这是 LangChain 检索里最复杂的一个，其他的都比较简单。

### 这一块到底新在哪

到这里，LangChain 关于 Milvus 的用法就说完了。

其实相比于前面学的 LangChain vector store，没有什么新东西。新的只有 vector store 的初始化——从 `InMemoryVectorStore` 换成 `Milvus`；其他都不变：该新增的时候还是 `add_documents`，该删除还是 `delete`，该搜索还是 `similarity_search`。

变化主要在混合检索上：

| 方案 | 关键参数 | 特点 |
| :--- | :--- | :--- |
| 加权融合 | `rank_type="weighted"`、`rank_params={"weights": [0.4, 0.6]}` | 两种得分按权重相加，得分在 0 到 1 附近 |
| RRF | `rank_type="rrf"`、`rank_params={"k": 60}` | 按排名融合，`k` 不传默认 60，得分偏小 |
| Cross-Encoder | 自己造 `ranker`，检索时传 `ranker=...` | 需要手动写重排器，`input_field` 要写 `text` |

权重的和 RRF 的都不说了，比较简单。如果以后要去做 cross-encoder 的混合检索，一定要记得：手动写一个 ranker 函数，然后封装到检索里，而且参数名叫 `ranker`。

这个你去官网都查不到，是我自己看源码找到的，有这么个参数，我把它填进去的。所以算是独家秘籍，传授给大家了。
