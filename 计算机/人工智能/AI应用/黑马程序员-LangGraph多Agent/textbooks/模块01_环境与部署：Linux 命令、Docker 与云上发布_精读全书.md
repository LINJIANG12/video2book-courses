## 从零搭一套企业级 AI 保险顾问
> 对应块：BLK01 | 覆盖分集：P01-P04 | 块标题（分集名）：《课程导学与 Linux 环境搭建》

### 这套课是怎么来的

说起这套课程的来源，那就是小孩没娘，说来话长了。

我是黑马程序员的虎哥。今年上半年，我发布过一套 LangChain 全家桶的课程，受到了不少网友的喜爱。不过到 5 月份的时候停更了一段时间，有同学开玩笑说这套课“太监”了。其实没有，每年暑假是 IT 培训的高峰期，我去线下授课了，这才耽搁了更新。上个月刚闲下来，我立马就把这套 LangChain 全家桶完结了。

但全家桶这套课，主要是带大家学 LangChain、LangGraph 的 API。虽然说里面也有一些实战案例，可它缺少一个系统化的企业实战项目。我也看到不少网友在评论区里求项目，所以就有了咱们这套从零开发企业级 AI 保险顾问的新课程。

那为什么非要强调“从零开发”？因为关注黑马的不少同学是从 Java 转 AI 开发的，对 Python 项目的开发规范并不了解。所以我就贴心地推出了这套从零开发的课程，手把手带着你从零搭建一个 Python Agent 项目，熟悉 Agent 项目开发的完整流程和规范。

### 一个卖保险的网站，为什么需要一个 AI 顾问

我们要做的，是一个面向个人和家庭的在线保险商城。它的功能分成两大部分：一是保险商城的业务，二是保险的智能顾问。

保险商城的业务，主要包含保险产品的浏览、保费的测算、投保、保单管理、理赔等等这些服务。但这里有个现实问题：大多数消费者对繁杂的保险种类、保险产品都缺少了解，对投保、理赔这些复杂流程也比较陌生。所以我们就需要开发一个智能的保险顾问，借助于大模型，通过自然语言帮助用户去理解产品、查询条款，帮助他配置保险方案，甚至指引他完成理赔的流程，最终跟商城本身的业务连接起来。

课程的重点，就是开发这个保险顾问的功能。其中会用到 LangChain 的 Agent 开发、RAG 开发，以及 LangGraph 的多智能体等知识。

课程里有一个很典型的例子：一位 32 岁的程序员，通过与保险顾问的沟通，获得了与其信息相配的一套保险方案。这中间就涉及保险产品的查询、方案推荐等 Agent 功能。如果你对某个保险产品有疑问，还可以继续提问，Agent 会根据用户的问题找出对应产品的合同条款，来精准地回答，避免出现幻觉——这就是所谓的 RAG 技术。不仅如此，为了提升 AI 答案的可信度，我们还可以把 AI 生成答案所引用的来源文档展示出来，这就是 RAG 中的引用溯源技术。

```text
用户用自然语言提问
        |
        v
   保险顾问 Agent
        |
        +----> 产品查询、方案推荐等业务工具
        |
        +----> 保险条款检索（RAG）
        |            |
        |            v
        |      命中条款原文，附带引用来源
        v
   基于条款作答，避免幻觉
```

这张图里，用户的自然语言先进入保险顾问 Agent，Agent 再按需要调用两类能力：一类是商城本身的业务工具，负责查产品和推荐方案；另一类是 RAG 检索，负责从合同条款里找依据。答案出来时一并带上引用来源，可信度就上来了。当然，Agent 还有更多其他功能，可以在后续课程中自行探索。

### 四个阶段的学习路线

整套课程分成四个阶段，从搭地基到多 Agent 协作，一层一层往上走：

```text
第一阶段  项目基础
          Linux、Docker、PostgreSQL、Milvus 等基础设施，Python 项目规范与初始化

第二阶段  基础保险顾问
          LangChain 基础、PostgreSQL + 线程池的会话记忆、SSE 流式对话、业务工具

第三阶段  RAG Agent
          文档加载、文档切分、向量模型、Milvus 检索与重排、引用溯源

第四阶段  多 Agent
          基于 LangGraph 的协作工作流：意图识别、咨询、RAG、闲聊
```

四个阶段不是并列的知识点，而是同一个项目不断长出来的四层能力：先有能跑的环境和工程骨架，再有能对话的顾问，再让顾问说话有依据，最后让多个各司其职的 Agent 协作。

#### 先把地基打好

第一阶段是项目的基础阶段。既然是从零开发，这一阶段就从零去搭建项目的基础设施，学习 Python 项目开发的规范，初始化项目，并完成一些基础功能的开发。

需要注意的是，项目的基础设施会涉及 PostgreSQL、Milvus 等复杂环境的部署，这就需要用到 Docker。为了照顾新手同学，我们会从 Linux 和 Docker 学起，并且还会给大家准备一套拿来即用的虚拟机环境，里边有项目所需要的一切基础设施，将来只需要一键部署就可以了，非常方便。

如果你已经是老手，已经熟悉 Linux 和 Docker，这两节课程可以跳过。

#### 再做出一个能对话的顾问

第二阶段去实现基础的保险顾问功能。这一部分会重新回顾 LangChain 的基础知识，然后基于这些知识去搭建保险顾问的 Agent。

这里要特别说一句：AI 技术更新迭代很快，LangChain 相比于半年前已经有了不小的变化。我们会在课程中使用最新版本的 LangChain，所以不要觉得重讲一遍 LangChain 基础有点多余，内容跟上一版其实是有变化的。

还有一点，我们实现保险顾问时，会使用 PostgreSQL 结合线程池的方式来实现会话记忆，这更符合企业的需要。除此以外，还会实现 SSE 流式对话、保险业务的各种工具开发等等，最终实现一个具备基础功能的保险顾问 Agent。

#### 让回答有据可查

第三阶段是 RAG Agent 的开发。这一部分会逐一去学习 RAG 中的各个组件：文档加载 Document Loader、文档切分 Text Splitter，以及各种不同的切分策略和它们的使用场景；还有一些常见的向量模型，以及向量数据库 Milvus 的用法。

在 Milvus 中，我们还会学习稀疏检索、稠密检索、混合检索，以及检索结果重排等 RAG 的优化手段。

最后，我们会结合保险顾问这个 Agent 里的保险条款——一种比较特殊的文档——来讲解复杂业务中 RAG 的各种优化细节。这可不是纯讲技术，而是真正实战、真正去解决问题。前面提到过的引用溯源功能，也会在这部分用到。

#### 让多个 Agent 分工协作

第四阶段是多 Agent，基于 LangGraph 来实现多智能体的协作开发。我们会学习如何基于 LangGraph 搭建 Agent 协作的工作流，并结合保险顾问这个项目，实现一个包含意图识别、咨询 Agent、RAG Agent、闲聊 Agent 等多 Agent 协作的智能客服顾问。

### 装 VMware 之前，先看清机器现状

后边的课程要用到虚拟机，所以需要在课前提前把它装好。装 VMware 有几件事得先说明白，不然很容易白折腾一遍。

第一，VMware 一旦卸载，很容易导致注册表残留。你再去安装新版本，会发现它也会安装失败。这不是安装包的问题，是上一次没卸干净。

第二，如果你的电脑上本来就已经有 VMware，就不要再重新装了，更不要卸掉去装我这个版本，没有必要。你有就用之前的，能用就用；除非我提供的虚拟机镜像你用不了，再考虑去卸载。

第三，如果你手太快，已经卸载了，那就去看文档的第五部分，里面有怎么清理注册表，照着做一下。

第四，如果之前压根没装过，那就简单了，直接按文档里 1、2、3 的步骤安装就行。

> **结论**：能用就用，不能用了再考虑重新安装；重新安装要按第五部分的步骤先卸载、清残留，再装。

### 安装过程中的几个关键选择

课前资料里第一项就是虚拟机。VMware 这个软件我给大家提供了两个版本：一个是 64 位版本，一个是普通（旧）版本。如果你的电脑比较老旧，不支持 64 位，就装旧版本；如果是最近几年的新电脑，可以装最新的 64 位版本。两个版本的安装过程大同小异。

双击安装包，选择“是”，弹出安装向导后点“下一步”，选择“我接受许可协议中的条款”，再点“下一步”。

这时安装程序会提示：检测到主机启用了 Hyper-V，虚拟机将通过 Windows 的虚拟机监控程序平台来启动。这个提示没问题。虚拟机本身是一套虚拟电脑，它需要用到 Hyper-V，所以不用管它，继续“下一步”。

接下来是安装位置。这里我不建议大家直接装到 C 盘，因为很多同学的 C 盘空间有限，装在这里将来可能就不够用了。点“更改”，换一个位置，比如放到 D 盘的 `develop` 下。但注意，不要直接选 `develop` 这个目录本身，否则 VMware 会直接装在 `develop` 里，将来这个目录除了你的软件还会多出很多很多东西。

正确做法是：在 `develop` 下专门新建一个空目录，起名叫 `vmware`，然后把安装位置指定到它下面。

> **易错点**：安装路径不要包含中文、不要包含空格、不要包含特殊字符。像 `D:\develop\vmware` 这样就是最好的。

选好目录点“确定”，再点“下一步”。安装程序会提示“更改安装文件夹是不推荐的”，意思是装完之后最好不要再改这个目录，我们确定就行。接着问要不要创建桌面快捷方式，让它创建。最后点“安装”，耐心等一段时间。

安装完成后，桌面会出现 VMware Workstation Pro 的快捷图标，开始菜单里默认也已经有了，双击就能启动。

### 怎么确认 VMware 真的装好了

安装程序显示“完成”，桌面图标也出来了，双击还能正常启动——但能启动不代表你的 VMware 就是正常的。

怎么才算真的正常？打开系统设置，找到“网络”，再找到“高级网络设置”，在这里应该能看到 VMnet1 和 VMnet8 两张网卡。能看到，才说明安装没问题。

如果是老版本的 Windows，在网络设置里看不到 VMnet1 和 VMnet8，甚至看不到这个选项，也不要紧：在设置里搜索“控制面板”，打开后选择“网络和 Internet”，点“查看网络状态”，再选择“更改适配器设置”，这里会弹出所有的网卡，效果跟刚才那里看到的一样。你要找的还是 VMnet1 和 VMnet8。

为什么需要这两张虚拟网卡？因为 VMware 里跑的是一台虚拟机，也就是一台虚拟的电脑；我们的计算机也是一台电脑。两台电脑要连接，就得通过这种虚拟的网卡。所以 VMware 安装完成后，会自动创建这两张网卡。

> **结论**：安装完没有 VMnet1 和 VMnet8，就是安装失败了，需要卸载重来。多半是因为之前没卸载干净。

### 装失败了，先把残留清干净

确认装失败，就回到文档第五部分做注册表的清理。那里提供了两种办法。

第一种，用资料软件里带的 CCleaner，直接做清理，文档里有具体步骤，照着做就行。

第二种，用 Geek Uninstaller。这是一个非常高级的卸载工具，它卸载软件时不只是卸载软件本身，还会把这个软件所有的残留都卸掉，包括注册表。双击打开，界面会展示你电脑上所有的软件，在下面的搜索框里输入要找的程序名，比如 `vmware`，就能找到。找到以后右键选择“卸载”，它首先会打开 Windows 的卸载工具把软件卸掉；卸完以后还会弹出一个窗口，说发现了残留痕迹，你选择“完成”，它就会把所有残留清洗干净。最后重启电脑，就可以重装了。

> **提示**：如果你之前没有卸载，只是安装失败了，建议直接用第二种方法，它清理得非常干净。

### 导入现成的 CentOS 镜像

VMware 装好、两张网卡也确认了，接下来要在 VMware 里有一台虚拟机。理论上讲需要自己创建一台，但没必要——课前资料的第二项“镜像”里，就是我给大家提供好的镜像。

你只需要把镜像复制一份，放到平时放软件的地方，比如还是 `develop`。这里我提前创建好了一个目录叫 `VM`，你也可以自己重新建一个，叫什么自己说了算。`VM` 就是 virtual machine 的意思，叫 `vm image`、`VM1` 也都行。把镜像粘进去，然后解压。

解压时要注意：选择“解压到 CentOS7”，让它解压到一个目录里，而不是散出来。我操作的时候就手快，选成了“解压到当前文件夹”，结果所有文件都散在了 `VM` 目录下，这个操作其实不太对。

散出来了也不是没救：把压缩包删掉，手动新建一个文件夹，比如叫 `CentOS7`，再把这些文件全部扔进去。这样就等于让它待在一个独立目录里。

为什么要一个虚拟机一个目录？因为将来你再创建更多虚拟机，`VM` 下面就会有更多子目录，所有虚拟机镜像都整整齐齐放在这一个地方，不会互相搅在一起。

整理好之后，找到那个 `.vmx` 文件——这是虚拟机的配置文件——双击一下，它就会自动加进 VMware。也有可能弹一个窗口问用哪个应用打开，选择用 VMware 打开就行。

加载进来以后先不要着急启动，还有一件事要做：虚拟网络配置。

### 把虚拟网络统一到 150 网段

在 VMware 里点“编辑”，再点“虚拟机网络编辑器”。

如果打开后这里没法修改，提示需要具备管理员特权，那是因为启动 VMware 时没有用管理员身份。点“更改设置”，选择“是”，相当于给它管理员权限，现在这个地方就能编辑了。

要改的是 VMnet8。先选中 VMnet8，再把子网 IP 改成 `192.168.150.0`，也就是说第三个部分必须是 150。我这台机器刚好就是 150，所以不用改；但笔记里默认的可能不是 150，有可能是 200，那就要改成 150。

子网 IP 下面的 NAT 设置里，网关和 DHCP 地址段也要一并改掉，全部统一到 150 网段，跟我改的一模一样。改的时候一定要先选中 VMnet8，再改它，不要改别的。

改完点“确定”，再点一次“确定”，然后耐心等一段时间。因为你把 IP 地址改了，它会重置你的虚拟机网络。

怎么知道重置完成了？还是看 VMnet8 的状态，看地址是不是 150 网段。如果是，就没有问题。用 Win11 的同学，在 VMnet8 上点“查看其他属性”，也能看到。

> **注意**：这一步所有人都必须改，把 IP 地址统一成 150 网段，跟我改的一模一样，不然后面虚拟机连不上。

### 第一次启动，以及给自己留一颗后悔药

网络配置成功、镜像也加载进来了，这时候就可以启动。找到你的虚拟机，点“开启虚拟机”。

启动时可能会提示“侧通道缓解”，让我们去禁用。现在就让它不提示，将来再禁用；接着如果弹出“我已移动该虚拟机”，选它就行。然后等一会儿。

出现登录界面，就证明虚拟机已经启动成功了。因为这台虚拟机装的是 Linux 系统，不是 Windows，所以它没有图形界面，是一个命令行界面。

如果现在就要在里面操作，需要把鼠标点进去。点进去以后鼠标会看不见，这是正常的，直接输入就行。用户名是 `root`，密码是 `123321`。注意，输密码的时候屏幕上是不显示任何字符的，不要以为键盘坏了；输完回车，它会提示登录成功。鼠标晃一下就能出来。

其实平时不需要登录，这里只是带你走一遍登录流程。

看完之后要把它停掉。点上面的箭头，选择“关机”。不要点那两个等号——那等于直接挂起，不是关机。

关机以后还有一件事：拍快照。为什么要拍快照？因为将来操作虚拟机，有可能把它给玩坏，拍了快照就能随时还原。

在 VMware 里点小齿轮，现在是没有快照的，直接点“拍摄快照”，名字可以随便起，比如“初始化”，然后确认，一个初始化快照就有了。

将来你用了一段时间，把虚拟机用坏了，或者觉得里面东西越来越多、太臃肿，就点小齿轮／小扳手，选中“初始化”这个快照，点“转到”。它会提示恢复此快照会丢失当前状态，不要紧，一点它就会自动恢复到最初那个干净的状态。这就是一键还原的意思。

> **提示**：快照要在这台虚拟机干净、还没开始折腾的时候拍，后面才有“后悔药”可吃。

### Linux 是怎么来的

Linux 是一套免费使用、自由传播的操作系统。

这个系统是怎么来的？是林纳斯·托瓦兹在 1991 年 10 月 5 日发布的，距今已经 30 多年了。这套系统开源免费，也就是不收钱——大家都知道 Windows 其实是收钱的。

最初，林纳斯·托瓦兹还在上大学。他当时对教学中使用的那个操作系统不太满意，于是一怒之下，基于个人的爱好，自己设计了一个操作系统。你听听这是人话吗？一怒之下自己开发了个操作系统。然后他把它发布到了芬兰最大的 FTP 服务器上，让用户可以免费下载。

结果不到 3 年的时间，它就成为一个风靡全球、使用最广泛、功能完善并且稳定可靠的操作系统。什么叫天才？这就叫天才。

而且不只是 Linux。大家以后还会学到一个东西叫 Git，工作过的同学应该听说过，它是一个版本管理系统。最开始大家用的不是 Git，是 SVN；后来林纳斯不买 SVN 的账，一怒之下花了一个星期开发了 Git，于是一下就取代了 SVN，成为全球使用最广泛的版本管理软件。

这哥们儿是不是非常变态？非常变态，很厉害。脾气也很暴躁，看不惯那些普通人写的普通代码，天天看见垃圾代码就破口大骂。这段历史大家做个了解就可以了。

### 桌面、服务器、移动端：操作系统的版图

在实际生产当中，除了 Linux 和大家熟悉的 Windows，还有很多其他操作系统。按使用场景分，大致是这么三块：

| 场景 | 常见系统 |
| :--- | :--- |
| 桌面级 | Windows、macOS、Linux |
| 服务器 | UNIX（商业收费）、Linux、Windows Server |
| 移动设备 | Android、iOS、HarmonyOS |

桌面级我们最熟悉的是 Windows，还有 macOS；Linux 也有桌面级的版本。服务器系统主要是三种：UNIX 是商业收费的，Linux 是免费的，还有 Windows Server。移动设备就不多说了，安卓、iOS、鸿蒙，大家都熟。

今天重点介绍的是 Linux。

### 内核与发行版：一个管硬件，一个管你好不好用

Linux 系统本身，还要知道它分成了内核版和发行版两种。

内核版就是这个系统的核心、操作系统的核心。这个核心是谁发明、谁写的？就是林纳斯·托瓦兹以及他的团队开发和维护的。这个核心免费开源，它的主要职责是与操作系统的硬件进行交互，然后对外暴露一些基本的接口和函数库。这就是所谓的内核。

那发行版是什么？发行版是基于林纳斯他们开发的这个内核，在它的基础上去开发了一些与用户进行交互的图形界面，扩展了一些更方便使用的程序和功能。简单理解：发行版就是在内核版的基础上做了一些额外的开发。

常见的发行版有 Ubuntu、Red Hat、CentOS、Fedora 等等，很多很多。这些系统通常会提供图形化界面，也就是说你可以用鼠标进行操作。

对比一下就清楚了：内核不能用鼠标操作，只能使用一些基础的内部函数和指令，而这些函数和指令操作起来非常复杂；发行版就在内核的基础上做二次开发，对外提供更容易让用户操作的方式。

### 壳：为什么命令行也算壳

先看内核和外壳之间的关系。

内核是操作系统的核心，只有它能接触计算机资源。什么是计算机资源？CPU、内存、磁盘、显卡、显示器、网络，这些都是电脑的资源。内核负责操作这些系统资源，然后对外暴露一些简单的函数库和接口。这相当于内核在说：我来操作系统资源，你想操作，就要经过我——这样内核就可以做一些安全性的处理和校验。

但问题来了，这些指令和接口太复杂，普通人根本无法使用。于是就有人在外面套了一层“壳”，这个壳叫 shell，翻译过来就是壳。

```text
应用程序
   |
Shell（壳，用户交互接口）
   |
内核 Kernel（文件系统、函数库、对外接口）
   |
计算机资源：CPU、内存、磁盘、显卡、显示器、网络
```

这张图从下往上看：最底下是计算机资源，只有内核能直接碰；内核对外暴露接口；壳跟内核交互，把这些复杂的接口包起来，对外提供方便用户使用的界面；最外层的应用程序，则安装在壳上面。所以应用程序、壳、内核、硬件，是这么一层套一层的关系。

既然内核我们操作不了，那我们学的一定不是内核，而是发行版，也就是套完壳的东西。

这里还有一个容易误解的地方：CentOS 只提供两种版本，一种是图形界面版本，一种是纯命令行版本，我们学的是纯命令行版。不要觉得命令行就不是壳——命令行也是壳。为什么呢？因为每一个命令的背后其实也是一个应用程序。我们用命令行，其实也是在直接跟壳交互，这个命令底层再去调内核的函数库。

> **提示**：图形界面是壳，命令行也是壳，只是两者让用户操作的方式不同。真正碰硬件的始终只有内核。

### 为什么最后选的是 CentOS

既然要学发行版，那选哪一个？我们学的是 CentOS。

CentOS 最早的时候是开源社区做的，免费。它是从哪来的呢？它是基于 Red Hat 编译过来的：Red Hat 是一个收费版，社区基于这个收费版编译出了一个免费版，让大家免费用。所以 CentOS 使用非常广泛，全球各地用得都很多。后来 Red Hat 官方把 CentOS 收购了，但依然免费提供，所以我们依然可以用它，没问题。

安装方式上，可以物理机安装，也可以虚拟机安装。我们采用的是虚拟机——将来你们到了公司，肯定就用物理机了，公司的服务器上装就完了；现在先用虚拟机把环境跑起来。整个虚拟机的安装过程这里就不展开了，照着资料一步一步做即可。

### Linux 没有盘符，只有一棵树

登录虚拟机之后，就能看到 Linux 的目录结构。

它一上来是个什么玩意儿？是一个斜杠 `/`。

咱们的 Windows 是什么结构？是有盘符的，C 盘、D 盘、E 盘。所以在 Linux 里进到目录，相当于只保留了盘符后面那一截斜杠，前面那个盘符没有了。

这就意味着，Linux 系统没有盘符的概念。没有盘符，上来就是目录，这个系统永远只有一个根目录，不会像 Windows 有多个根目录。所有的文件都在根下面。

Linux 的目录结构就像一棵树：有一个根，根下边挂很多目录，目录下边再挂目录。所以我们可以把整个 Linux 系统结构，看作 Windows 中的某一个盘——Windows 的某一个盘也是以某一个根开始的，根下面才有这些目录。相当于 Linux 只有一个盘，而 Windows 分成了好几个盘。当然，Windows 也可以不分盘，你装电脑的时候让装机的人别分盘，只用一个盘，也是可以的。

```text
/
├── bin
├── boot
├── dev
├── etc
├── home
│   ├── user1
│   └── user2
├── lib
├── opt
├── root
├── sbin
├── tmp
├── usr
└── var
```

这棵树只有一个起点 `/`，所有目录都从它分叉出去；普通用户的家目录在 `/home` 下面一人一个，而超级用户的家目录单独放在 `/root`。

### 根目录下每个文件夹是干什么的

根目录下面这些文件夹，各自有各自的职责：

| 目录 | 存放的内容 |
| :--- | :--- |
| `/bin` | 二进制的可执行文件（bin 就是 binary 的缩写） |
| `/boot` | 系统引导、启动时使用的各种文件 |
| `/dev` | 设备文件 |
| `/etc` | 系统配置文件 |
| `/home` | 普通用户的家目录；每新增一个用户，就在这下面新增一个文件夹 |
| `/lib` | 程序运行所需要的共享库和内核模块，相当于各种系统依赖 |
| `/opt` | 一些可选的应用程序 |
| `/root` | 系统超级用户 root 的目录 |
| `/sbin` | 可执行文件，但只有 root 用户才能访问，相当于系统级的应用 |
| `/tmp` | 临时文件 |
| `/usr` | 系统应用程序；用户自己装程序，一般装到这里 |
| `/var` | 系统运行过程中的临时数据，比如日志 |

`/home` 这个目录有点像 Windows C 盘里的 `Users`：每新建一个用户，这里就会多一个目录，普通用户的文件都放在自己的目录里。

> **易错点**：`/home` 放的是普通用户的文件，而系统超级用户 root 的目录是 `/root`，不在 `/home` 下面。这两个不要搞混。

这套目录结构了解一下就行了，不需要背。你只要知道有这些目录，将来看到的时候大概有个认识就够了。

### 登录之后，先确认自己站在哪

登录成功以后，我是用什么用户登录的？root。当一个用户登录以后，默认会进入这个用户所在的目录。由于我是用 root 用户登录，所以我现在就在 `/root` 目录下。

怎么知道呢？有一个命令叫 `pwd`，它会显示你所在的位置。执行 `pwd`，输出的是 `/root`，这就对上了。

`/root` 下面有很多文件。除了 `/root`，根目录下还有 `boot`，放的是系统引导文件；还有 `etc`，放的是一些环境变量和配置文件；还有很多其他的，就不一一去看了。

到这里，Linux 的目录结构就先有个整体印象：一个根 `/`，下面挂着一棵目录树，每个目录有固定的分工；登录后先 `pwd` 看一眼自己在哪，后面再操作就不容易迷路。

## Linux 命令入门：从命令格式到目录与文件操作
> 对应块：BLK02 | 覆盖分集：P05-P08 | 块标题（分集名）：《Linux 常用命令：目录操作与文件管理》

接下来我们就开始学 Linux 的命令。学命令的目的其实很单纯——就是为了操作这个系统上的东西。

你以前刚接触 Windows 的时候，学过 Windows 的命令吗？多半没有，没关系。命令的用法在哪都差不多：把 Linux 这一套弄明白了，以后再去碰 Windows 的命令，套路是类似的。我们先从命令长什么样说起。

### 命令也是应用程序，由三部分组成

先说一件容易被忽略的事。我们现在所接触到的系统，其实是系统的“壳”。而我们敲的这些命令，我告诉你，它们本身也属于应用程序。

那这些应用程序放在哪儿？全都放在 Linux 系统的目录里——`/etc`、`/run`、`/usr/bin` 这些系统目录，里面肯定躺着一些可执行的文件。换句话说，你所学的每一条命令，都是一个应用程序，不是一个什么玄学符号。这一点一定要注意。

既然是应用程序，它就有自己的输入：每一个命令都可以接收参数。参数分两种，一种叫 option，也就是可选项；一种叫 parameter，就是这个选项所对应的参数。当然，有时候没有选项，直接加参数，也可以。

所以一条命令主要由三个部分组成：command 是命令名，option 是可选项，parameter 是具体的参数，可以是零个，也可以是一个或多个。

```text
 command      option      parameter
---------    --------    ------------------
 命令名       可选项       命令作用的对象
 rm           -f          要删除的文件名
```

读图：一条命令从左到右依次是“叫什么、怎么调、对谁下手”。中间那一段可以没有，最后一段也可以没有，但第一段永远必须有。

拿最经典的 `rm -f` 举例。`rm` 是命令名，它是 remove 的缩写，删除的意思；`-f` 是选项；后面跟的那个名字就是参数，也就是要删的东西。

| 组成部分 | 例子 | 说明 |
| :--- | :--- | :--- |
| command | `rm` | 命令名，remove 的缩写，表示删除 |
| option | `-f` | 可选项，这里用了短格式 |
| parameter | 文件名 | 命令作用的对象，可以零个、一个或多个 |

选项还分长格式和短格式。长格式往往加两个杠，比如 `--help`；短格式往往是一种缩写，比如 `-h`，大多数情况下 `-h` 就代指 `--help`——但不是一定的，别把它当成公式背。

### 记不住就查 --help

命令太多，记不住怎么办？记不住不要紧，有个选项可以现学现卖：`--help`。

手上有个新命令 `ls`，不会用，就跟上一个 `--help`，回车，它会把这条命令的具体用法告诉你。

```bash
ls --help
```

输出的开头会写明用法：`ls` 后面跟选项，选项后面跟具体的文件。再往下是一大段选项列表，`-a`、`-A`、`-b`、`-B`……每一条后面都标着它对应的长格式。你会看到 `-b` 对应的长格式是 `--escape`——短格式一定跟长格式长得像吗？不一定。所以别凭感觉猜字母，一定要去参考具体的帮助才知道。

学命令时一定要学的一个选项，就是 `--help`。哪条命令忘了，`--help` 一敲，它自己会告诉你这条命令是干什么的、后面该接什么、有哪些选项可挑。

比如 `rm` 我不知道啥意思，`rm --help`，头一句就写着 remove，删文件；用法是 `rm [选项] 文件`。再看 `-f`，长格式 `--force`，force 是强制。帮助里的原文大意是：忽略不存在的文件和参数，每次删除之前都不提示。翻译成人话就是——默认情况下你删文件，它是会问你一句的；加了 `-f`，就不问了，直接删。

> **提示**：`--help` 是命令自己带的说明书，`-h` 只是它常见的缩写。碰到 `-h` 不生效、或者行为跟想象不一样的情况，老老实实敲 `--help`，不要硬猜。

### 少敲键盘的几手：补全、历史、清屏

#### Tab 补全，以及连按两次

命令敲到一半敲不出来了，用 Tab 键。

Tab 在哪？在大小写的上边、Q 键的左边、波浪线的下边。找到它。

比如 `/tmp` 下有个名字很长的 `.ini` 文件要删，名字我懒得敲全，就敲一个开头字母 `m`，然后按下 Tab——自动补全了，整个文件名一次性补齐。这就是补全：当前目录里以这个前缀开头的文件唯一时，它把名字替你写完。

连按两次 Tab 还能给提示。比如我敲了个 `r`，后面记不得了，连按两次 Tab，它会把 `r` 开头的所有命令列出来，里头就有 `rm`。所以 Tab 不只是“补全”，它还是“列清单”：路径、命令名都能这么问。

#### 上下箭头翻历史

上下箭头可以快速调出曾经用过的命令。

按一下上键，跳到刚才敲过的 `ll`；再按一下，`rm`；再按一下，还是 `ll`。之前敲过的命令全在这条队列里，按上键往上翻，按下键往下翻。凡是你执行过的命令都能在这儿找到——想重复执行一条，就不用重新敲了，翻出来回车即可。

#### 清屏，以及大小写这件正事

命令敲多了，一屏都是输出，看着乱。输入 `clear`，或者按 Ctrl+L，屏幕直接清空，清爽一些。

还有一条必须刻在手上的规矩：命令和参数严格区分大小写。千万别觉得大小写随便输都一样。回到 `ls --help` 的输出里看，`-a` 和 `-A` 是两个含义不同的选项，`-b` 和 `-B` 也是两个含义不同的选项。所以敲命令的时候，大小写是要抠清楚的。

> **结论**：上手前把这五样备齐——`--help` 查用法、Tab 补全、连按两次 Tab 看候选、上下箭头翻历史、`clear` 清屏，另外牢牢记住大小写有别。这几手比背命令表管用得多。
### 目录操作：ls、cd、mkdir、rm

接下来是跟目录操作有关的命令，主要就四个。

#### ls 和 ll：目录里到底有什么

`ls` 的作用是展示指定目录下的内容。语法是这样：先是 `ls` 这个命令本身，中间加选项，后面跟你要查看的目录。如果你不传目录，默认查的就是当前目录。

最常见的选项是两个，`-a` 和 `-l`：`-a` 决定要不要显示所有文件，包括隐藏文件；`-l` 除了展示文件名，还会把文件的形态、权限、拥有者、大小这些详细信息都列出来。

```bash
ls
ls -a
ls -al
```

先敲一个光秃秃的 `ls`，什么都不加。看到的就是当前目录下的东西——几个文件，外加一个“在线文档地址”。这跟左侧文件树里看到的是完全一致的。

再加上 `-a`。你会发现多出来好多东西，其中一批是以点开头的。以点开头的都是隐藏文件，`-a` 就是把它们也放出来。

接着加 `-l`，写成 `ls -al`。这里注意：`-a` 和 `-l` 是两个选项，当出现两个选项时，可以合并成一个写，`-al` 和 `-a -l` 是一个道理。

`-l` 的输出比光秃秃的 `ls` 清爽得多：一行一个条目，一行里塞满了信息。

| 在行内的位置 | 内容 | 怎么看 |
| :--- | :--- | :--- |
| 行首第一个字符 | 文件类型 | `d` 表示目录，不是 `d` 就是文件 |
| 紧随其后那一串 | 权限 | 形如 `rwxrwxrwx`，r 是读权限、w 是写权限、x 是执行权限 |
| 中间某个字段 | 一个计数字段 | 这里先不管它 |
| 再往后 | 所属用户与组 | 哪个用户创建的，以及这个用户在哪个组 |
| 再往后 | 大小 | 文件大小 |
| 再往后 | 时间 | 文件创建的时间 |
| 行尾 | 文件名 | 条目的名字 |

那串权限为什么重复三遍？因为它按“当前用户、当前用户所在的组、其他组的用户”分了三组权限。现在先不用管那么细，知道这一串代表权限就够了。

`ls -l` 实在是太常用了，于是 Linux 给了一个快捷方式：`ll` 就等于 `ls -l`。直接敲 `ll`，效果一模一样。`ll` 后面当然也能继续加 `-a`。

`ll -a` 的输出里有两个很特殊的条目，最上面一个 `.`，最下面一个 `..`。点代表当前目录，点点代表上级目录。所以 `ll -a .` 等于什么也没写——不写也是当前目录；`ll -a ..` 查的就是上一级目录。如果你当前正待在一层目录下，`..` 就是整个系统的根。

也可以在后边指定要看的目录，比如 `ll -a /root`。注意这个斜杠：写了 `/root`，是从根目录开始找的 root；不写斜杠、直接跟一个名字，那是在当前目录下找这个名字。同理，想看 `/usr`，就是 `ll /usr`。

#### cd：切换目录

`cd` 是切换的意思。比如我现在在 `/tmp`，想回 root，就 `cd /root`，回车，位置就变了。如果终端里勾了 Follow terminal folder，左边的文件树会自动跟着切过去，不用手动点。

想去 `/usr`，`cd /usr`。想再往下走，可以连着写，`cd /usr/local`。路径写到一半忘了名字怎么办？先敲一个 `l` 按 Tab，它会把 `l` 开头的目录列出来让你挑；再补上第二个字母 `o`，候选就唯一了，再按 Tab 自动补全。它非常智能。

回自己的用户目录有个更省事的写法：`cd ~`。波浪线代表当前用户所在目录，注意 `cd` 和 `~` 中间有空格。刚才在 `/usr/local`，`cd ~` 一回车，就回到 root 了。

还有一个：`cd -`。减号是回到上一次所在的目录。我在来 root 之前待的是 `/usr/local`，`cd -` 就回去了。这两个目录之间来回跳，用这个特别顺手。

顺带一句，`.` 和 `..` 在 cd 里同样管用：`cd ..` 就是回上一级。

#### mkdir：建目录，用 -p 建多级

`mkdir` 顾名思义，make directory，创建目录。你给它一个目录名，它帮你建出来。

```bash
cd /tmp
mkdir hello
ll
```

回车，`ll` 一看，多了个 hello，是个文件夹。目录就这么建出来了。

`mkdir` 还有一个 `-p` 选项。它的意思是：确保目录名称存在，不存在就创建，可以同时创建多层目录。

```bash
mkdir a/b/c
mkdir -p a/b/c
```

第一行直接回车会报错，说父目录不存在——上一级都没有，怎么建下级？第二行加上 `-p`（小写），没报错。`ll` 看到 a，`ll a` 看到 b，`ll a/b` 看到 c，三层全建出来了。这就是 `-p` 的价值：一次把整条路径铺出来。

> **易错点**：别在目录名前随手加斜杠。`ll /a` 里那个斜杠代表根，查的是根目录下的 a；当前目录下的 a 要写 `ll a`，或者写 `ll ./a`——点杠就是当前目录，`./a` 和 `a` 是一回事。另外，`-a` 是选项不是目录名，`ll -A` 不会去帮你看一个名叫 A 的目录。

#### rm：删除，递归，以及那条碰不得的命令

`rm` 是删除。它有两个选项要记牢：`-f` 是无需确认直接删除，`-r` 是把目录及目录中的文件逐一删除，也就是所谓的递归删除。

先看 `-f`。当前目录里有个叫“在线文档地址”的文件，我要删它。名字长不想敲，敲个开头按 Tab 自动补全，`rm -f 文件名`，回车，文件直接就被干掉了——强制删除，不询问。

不加 `-f` 呢？`rm 文件名`，回车，它会弹一句问你要不要删。输入 `N`，也就是 no，那就不删。`ll` 一看，文件果然还在。这就是默认的保护，`-f` 干的事就是把这道保护关掉。

再看 `rm -f hello`。hello 是个目录，能不能删？不能。为什么？因为目录里可能还有别的东西，而 rm 默认只能删“一个东西”，也就是一个文件；要删目录、要一次删多个，就必须加 `-r`。

递归的意思是：我删 hello 这个目录，如果目录里还有东西，也会顺着往下接着删。不信可以先在 hello 里新建一个空文件 `1.txt`，再 `rm -rf hello`——回车之后，hello 连影子都没了，里面的文件一起被端掉。

```bash
rm -rf hello
rm -rf *
```

这里要停一下。`rm -rf *` 里的星号代表所有，等于把这个目录里所有的东西全删掉，而且还是递归删除。回车之后，空空荡荡，什么都没有了，刷新一下也还是空的。所谓“先删库再跑路”，就是这个命令。

还有一条更狠的：`rm -rf /`。斜杠是根目录，等于把根目录下的一切全删了，直接能把操作系统干没。这才是真正的删库跑路。所以切记不要执行，太危险，少儿不宜。

顺便说句实在话：昨天讲完，很多同学都不听话。我讲虚拟机的时候就说，装完之后建个快照，有同学偏偏不建。你建个快照，万一真删了，还能恢复。上课要听话，让你建快照就建快照。
### 文件查看：cat、more、less、head、tail

下边是第二套命令，跟文件相关。这一段只讲“看”文件，不讲编辑文件——就是把文件内容读出来看。

#### cat：把整个文件打出来

`cat` 用于显示文件的内容。语法是 `cat -n 文件名`：命令，接一个 `-n` 选项，再加文件名。`-n` 是问要不要输出行号，不加就不输出，加了就输出。

```bash
cat /etc/profile
cat -n /etc/profile
```

看 `/etc/profile`。文件名不用敲完，敲一部分按 Tab 自动补全。回车，屏幕上哗啦一下出来一大片内容，这就是查看文件内容的效果。再加上 `-n`，每行前面多了行号，一眼能看出这是第几行。

挺简单的，`cat` 加 `-n` 就完事。

#### more 和 less：一屏一屏地翻

有了终端客户端，`more` 其实可以不用——除非文件特别长。文件要是超级长，一屏根本显示不全；鼠标滚吧，滚也滚不到头。这个时候才轮到 `more`。

`more` 后面跟上文件名，它支持这么几个操作：

| 按键 | 动作 |
| :--- | :--- |
| 回车 | 向下滚动一行 |
| 空格 | 向下滚动一屏 |
| B | 向上返回一屏 |
| Q 或 Ctrl+C | 退出 |

```bash
more /etc/profile
```

回车之后，底部会显示一个 `more 41%`，说明眼下展示到全文的 41%。按空格翻一屏，按回车一行一行往下走，按 B 往回退一屏，按 Q 退出。既能一行一行挪，也能一次翻一大块，随你。

`less` 跟它效果很像，也是一屏一屏地查看，用法类似。

#### head：只看开头几行

`more` 和 `less` 是让你一页一页地滚，`head` 是不滚——我就想看文件开头那几行。

`head -n 文件名`，n 就是行数。这里要留神：这个 `-n` 跟 `cat` 的 `-n` 不是一回事。`cat -n` 是“输出行号”，`head -n` 的 n 是“几行”，n 是行数的占位。

```bash
head -5 /etc/profile
head -10 /etc/profile
```

`head -5` 显示前五行，数一数，12345，正好；空行也算行。改成 `head -10`，就是前十行。作用是固定的：我想查前面几行，就查前面几行。

#### tail：从尾巴看，用 -f 盯住日志

与 `head` 相对的还有一个 `tail`。它看的不是文件头，而是文件尾。

`tail -n 文件名` 查尾部的几行，它还可以加一个特殊参数 `-f`，这个就很重要了。

先准备一个 `error.log`。这个文件六百多 K，里面内容超级多，滚轮翻不到头，想从里面找东西也不太好找，看末尾就得用 `tail`。

```bash
tail -10 error.log
```

出来之后你可能会觉得：这不是十行吧，怎么超过十行了？其实是因为某一行内容太长，在终端里折了行，看起来像好几行，实际就是十行。

重点是 `-f`。

```bash
tail -5 error.log
tail -5f error.log
```

先跑 `tail -5`，五行显示完，命令就结束了，回到提示符。再跑 `tail -5f`，五行显示完，它卡在那儿不动了——没有结束。

为什么？因为 `-f` 是 follow，不断跟随、跟踪的意思。它不会结束，会一直查着这个文件。这时候你在日志里再写一行保存，新加的那一行立刻就冒出来了；再添两句自己的内容，保存，又冒出来了。

```text
程序运行 ──写入──▶ error.log（不断变长）
                        │
                        └── tail -f 一直盯着文件尾部 ──▶ 终端实时显示新行
```

读图：程序不停往日志文件里追加内容，`tail -f` 一直守在文件尾部，文件一长它就往下读一行，所以屏幕上会持续刷新。

这个作用叫日志跟踪。将来程序跑起来，会不断产生新的日志；用了 `-f`，日志就不断输出，你这边也就不断看到新日志，方便调试，看看程序到底出了什么问题。这就是 `-f` 的用处。

要退出怎么办？按 Ctrl+C。Ctrl+C 就是那个复制键，但在 Linux 里它不是复制，而是终止运行。这个组合键平常会经常用到：一条命令输到一半你不想输了，Ctrl+C 一按，它就不再运行了。

### 拷贝与移动：cp 和 mv

#### cp：复制，目录要加 -r

`cp` 这个命令，不是你理解的那个 CP，它不是用来炒的。它是 copy 的缩写，用来复制文件或者目录。

`cp` 后面可以加 `-r`，`-r` 还是递归的意思：如果你要复制的是目录、并且目录里有东西，那就必须加 `-r`；如果只复制单个文件，直接 `cp` 就行。

`cp` 后面跟两个东西：source 和 dst。source 是源，dst 是目标——从谁复制，复制到哪里去。复制虽然简单，但能带来很多实用的效果。

```bash
cp error.log ./test.log
```

`/tmp` 里现在只有一个 `error.log`。`cp error.log` 是源，目的地写 `./` 表示当前目录。那复制到当前目录叫什么呢？如果不给新名字，就会跟原来那份重名，所以必须给个新名字，比如 `test.log`。`./` 可写可不写，不写也是当前目录的意思。

这条命令的含义就是：把 `error.log` 复制一份到当前目录，并且重命名为 `test.log`。回车，`ll` 一看，有了。

#### 目标是目录，还是文件名

复制到别的目录也行。先建个目录 `a`，然后 `cp test.log a`。

```bash
mkdir a
cp test.log a
cp test.log a/test2.log
```

先把目录 `a` 建出来，然后 `cp test.log a`：目标是一个目录，效果就是把这个文件复制一份放进那个目录里，名字保持不变。回车之后看当前目录，没有变化；再看 `a` 目录，里面多了一个文件。

再写一行 `cp test.log a/test2.log`，就是在复制的同时改名——在目标目录后面再跟一个名字，文件就按这个新名字落进去。

> **结论**：目标是目录，就只是复制过去，名字不变；目标是“目录 + 文件名”，就是复制过去并且改名；目标写成当前目录下的一个文件名（`test.log`），就是复制到当前目录并改名。三种写法，一条规律。

要复制的是目录呢？比如把整个 `a` 复制一份，起名叫 `b`。这时候不加参数是复制不了的，因为它是目录，必须加 `-r`（小写）。

```bash
cp -r a b
cp -r a /root
```

`cp -r a b` 把 `a` 这个目录复制一份，新名字叫 `b`。看 `b` 里面，原来 `a` 里的文件也一起复制过去了，这就是递归复制。

`cp -r a /root` 是复制到别的目录去：把 `a` 复制进 `/root`，没有重命名，就直接复制走。`ll /root` 一看，里面有个 `a`。

#### mv：移动就是剪切

`mv` 是一个单词的缩写，move，移动的意思。看到名字你就该知道它跟 `cp` 的区别了：`cp` 是复制一份，`mv` 是直接给你拿走，等同于剪切。

既然等于剪切，那它自然也能顺手改名。先看文件：当前目录里有 `test.log`，`mv test.log test1.log`。

```bash
mv test.log test1.log
mv test1.log a
```

第一行的效果是：把 `test.log` 移动到当前目录，并改名叫 `test1.log`。`test.log` 还在不在？不在了，位置没动、名字变了，这不就是重命名吗。

第二行 `mv test1.log a`：当前目录里的 `test1` 没了，去 `a` 里了，里面多了一个 `test1`。这是纯移动。

移动的同时当然也能改名：把 `a` 里的那个文件拿出来，同时起个新名字，它就连人带名一起搬回当前目录。`a` 里的那份没了，当前目录多了个新名字的文件。

目录也一样能移。`mv a dira` 把目录 `a` 改名成 `dira`；`mv b dira` 把整个 `b` 目录扔进 `dira` 里面去——当前目录的 `b` 没了，点开 `dira`，里面多了个 `b`。

| 对比项 | cp | mv |
| :--- | :--- | :--- |
| 本质 | 复制一份，原件保留 | 剪切，原件不再留在原处 |
| 复制/移动目录 | 必须加 `-r` | 不用加任何参数 |
| 顺手改名 | 目标写成“目录/新名字” | 直接写新名字即可 |

所以 `mv` 用起来更省事一点：它不需要 `-r`，目录直接搬。你只要记住一句话——`cp` 是“再来一份”，`mv` 是“挪走”，剩下的用法都是这两个意思的自然延伸。

## Linux 文本处理与软件环境：从打包到部署
> 对应块：BLK03 | 覆盖分集：P09-P14 | 块标题（分集名）：《Linux 文本处理与软件环境安装》

命令学到这个阶段，单个文件怎么看、怎么拷、怎么挪，都已经顺手了。可真实场景里很少只有一个文件：一个项目目录下面套着子目录，子目录里还有日志、图片、配置，你要把它整个交给别人，或者从测试机搬到服务器上，一个一个传显然不现实。所以接下来要解决的是「一堆文件怎么变成一个文件」，以及「怎么让它变小」。

### tar：一个命令，四种操作

打包和解包是一对，压缩和解压是一对。四件事听起来像四个命令，实际上全是 `tar` 一个命令，靠选项决定它这一次干哪件。

基本格式长这样：

```bash
tar [选项] [包文件名] [要打包的文件...]
```

第一个文件名，是打包之后那个产物的名字——包总得有个名。后面跟的是「你要打包谁」，它可以是一个列表，一次传多个；`tar` 就把这些文件统统塞进前面那个新建的包里。

解包的时候，后面这一段就不用给了。包已经在那儿，只要告诉 `tar` 解哪一个就行：

```bash
tar [选项] [要解的包文件名]
```

> **结论**：`tar` 后面那个文件名，打包时是「产物名」，解包时是「来源名」；再往后的文件列表，只在打包、压缩时给。

控制这四件事的，是五个选项。

| 选项 | 全称 | 作用 | 是否必给 |
| :--- | :--- | :--- | :--- |
| `-z` | gzip | 调用 gzip 压缩或解压 | 可选，要压缩才加 |
| `-c` | create | 创建包，即打包或打包压缩 | 与 `-x` 二选一 |
| `-x` | extract | 解包或解压 | 与 `-c` 二选一 |
| `-v` | verbose | 显示处理过程，打包或解压了谁 | 可选 |
| `-f` | file | 指定包文件名 | 必给 |

`-c` 和 `-x` 是互斥的，加了 `-c` 就不能加 `-x`，反之亦然。这里有个特别容易记岔的地方：`-c` 不是 compress，它是 create，管的是「创建一个包」，这个包压不压缩跟它没关系，压缩归 `-z` 管。`-x` 也一样，它管「把包里的东西取出来」，取出来的是没压缩的包还是 gzip 包，同样看 `-z`。

所以 `-z` 是「要不要压」的开关，`-c` 和 `-x` 是「往里装还是往外拿」的方向，`-v` 是「要不要说话」，`-f` 是「包叫什么」。五个选项里只有 `-f` 是必须的，其余都能省。

> **易错点**：`-c` 与 `-x` 只能出现一个；`-z` 在压缩和解压时要成对出现——压的时候加了 `-z`，解的时候也得加，否则 `tar` 不知道这是 gzip 包。

命名也有约定：`.tar` 表示只是打包，`.tar.gz` 表示打包并且压缩过。后缀名本身不参与解包逻辑，`tar` 认的是 `-z`，但人和脚本都靠后缀判断，所以别乱起名。

拿一个目录试一遍就清楚了。当前目录下有个 `DIRA`，里面套着 `B` 目录，塞了一堆文件，还丢了一张 32KB 的图片进去——就是要让它「有点分量」，压缩效果才看得出来。

先只打包，不压缩：

```bash
tar -cvf a.tar DIRA
```

`-c` 创建、`-v` 显示过程、`-f` 指定产物。回车之后屏幕上一行行列出来：打包了 `DIRA`，打包了里面的日志，打包了图片——这就是 `-v` 的作用，让你看见它到底装了什么。产物 `a.tar` 的大小是 2836480 字节。

再打一次，这回加上 `-z`，产物名改成 `a.tar.gz`：

```bash
tar -czvf a.tar.gz DIRA
```

同样的目录，产物只有 112549 字节。两千八百多 KB 变成一百一十 KB，差了二十多倍，接近一个数量级。这就是打包和压缩的区别：打包只是把散文件捆成一个大文件，体积基本没变；压缩才真正把内容压小。

| 命令 | 产物 | 大小 |
| :--- | :--- | :--- |
| `tar -cvf a.tar DIRA` | `a.tar` | 2836480 字节 |
| `tar -czvf a.tar.gz DIRA` | `a.tar.gz` | 112549 字节 |

打包完把原目录删掉，试试能不能还原。解包用 `-x`：

```bash
tar -xvf a.tar
```

解开之后 `DIRA` 回来了，进去看，`B` 在，图片也在，一个不少。

再删一次，这回解压缩包，`-x` 加上 `-z`：

```bash
tar -xzvf a.tar.gz
```

同样全部还原，文件内容也都正常。到这里四件事就都过了一遍：`-cvf` 打包、`-czvf` 打包压缩、`-xvf` 解包、`-xzvf` 解压。记住这四个组合，日常够用了。

> **提示**：选项习惯写成 `-czvf`，把 `-f` 放在最后，因为它后面紧跟着的就是包文件名，放中间容易把顺序弄乱。写成 `-c -z -v -f` 也等价。

### vi 与 vim：三种模式来回切换

到这儿为止，所有文件操作都还停留在「查看」：列目录、翻内容、拷来拷去，没有真正改过一个字。要改文件就得用文本编辑器，Linux 里最经典的是 `vi`，它的增强版叫 `vim`，用法基本一样，任选一个都行。

区别在装没装：`vi` 是系统默认就有的；`vim` 要自己装，`yum install vim`。敲 `vim` 时提示命令找不到，敲 `vi` 就能进。装也行，但全班一起下载会卡，为了一点语法高亮不值得，直接用 `vi`。真要装，`vim` 比 `vi` 多的其实就是高亮——写 Python 时代码会着色，其余操作完全一致。

`vi` 的麻烦不在命令多，而在模式。它有三种模式：命令模式、插入模式（也叫编辑模式）、底行模式。插入模式才是唯一能真正写字的状态；命令模式和底行模式都是「非编辑状态」，一个负责下快捷键指令，一个负责下长命令。

一打开文件，默认进的是命令模式。这个模式下能看内容、能移光标、能删东西，但一般改不了字。想下命令直接按键盘，屏幕上不显示你按了什么——这一点最容易让人以为编辑器卡死了。

命令模式里常用的几个：

| 按键 | 作用 |
| :--- | :--- |
| `gg` | 跳到第一行 |
| `G` | 跳到最后一行（`Shift` + `g`） |
| `dd` | 删除光标所在行 |
| `3dd` | 从当前行起删掉 3 行 |
| `u` | 撤销 |

`gg` 是连按两次小写 g；`G` 是大写，得按住 Shift。数字加 `dd` 是批量删，`3dd` 一次删三行，比一行一行按快得多。

然后是三个切换键：`i`、`a`、`o`。这三个都从命令模式进编辑模式，差别只在落点——`i` 是原地插入，`a` 是在光标后面追加，`o` 是另起一行往下写。三个键本质相同，都是「进编辑」，记住一个 `i` 就够干活，另两个是顺手。

写完按 `Esc`，退回命令模式，光标又能用来移、用来删了。

第三种是底行模式。在命令模式下按一个冒号 `:` 或者斜杠 `/`，屏幕最底下会开出一行命令输入区，这就是底行模式。冒号管保存、退出这类操作，斜杠管内容匹配和替换。

底行模式的常用命令：

| 命令 | 作用 |
| :--- | :--- |
| `:q` | 退出 |
| `:q!` | 强制退出，不保存 |
| `:wq` | 保存并退出 |
| `:set nu` | 显示行号 |

三种模式的关系可以画成这样：

```text
              按 i / a / o
   命令模式 ─────────────────→ 插入模式
      ↑  ←─────────────────
      │       按 Esc
      │
      │ 按 : 或 /
      ↓
   底行模式 ───── 按 Esc ────→ 命令模式
```

看这张图只需要抓住一点：命令模式是枢纽。进来是它，插入模式按 `Esc` 回它，底行模式按 `Esc` 也回它；而进插入、进底行，都只能从它出发。所以任何时候迷路了，连按两下 `Esc`，一定回到命令模式。

光看模式没感觉，走一遍完整流程。先建一个 Python 文件：

```bash
vi hello.py
```

文件不存在也没关系，`vi` 会先打开一个空缓冲区，保存时才真正落盘。进来是命令模式，按 `i`，左下角出现 `-- INSERT --`，说明已经在插入模式，可以随便写了：

```python
print("hello world")
```

写完按 `Esc`，`-- INSERT --` 消失，回到命令模式，这时候再按数字字母只会被当成命令，打不出字。接着按 `:` 进底行，输入：

```text
wq
```

回车，保存并退出。想确认文件在不在，`cat hello.py` 看一眼；想跑，直接：

```bash
python hello.py
```

屏幕上打出 `hello world`，说明这台机器自带 Python 解释器，装好系统就能直接跑，不用额外配。

再复习一遍「改了不保存」的场景。重新 `vi hello.py`，按 `i` 随便加几行，`Esc` 回命令模式，然后 `:q`——它不让你退，提示你文件被修改过。这时有两条路：`:wq` 保存走人，或者 `:q!` 强制丢弃。选 `:q!` 之后再看文件，还是原样，刚才加的内容一个字都没留下。

命令模式里的 `gg`、`G`、`dd`、`u` 也可以顺手试：`gg` 跳到首行，`G` 跳到末行，`dd` 删一行，`5dd` 删五行，删多了按 `u` 撤销。这几个动作不用退出文件，在命令模式里随按随生效。

### find 找文件，grep 找内容

文件一多，凭 `ls` 一层层翻就不现实了。查找类的命令，先看 `find`：它管的是「在磁盘上找一个文件」。

格式是「先目录，后条件」：

```bash
find [在哪个目录找] -name [找什么名字]
```

比如在当前目录下找所有 `.log` 文件：

```bash
find . -name "*.log"
```

`.` 是当前目录，`-name` 是按名字匹配，`"*.log"` 是通配写法。回车之后，不光当前目录的 `error.log` 被找出来，子目录里的 log 也一起被翻出来了——`find` 会递归往下找，这正是它比 `ls` 强的地方。

> **易错点**：通配符必须加引号。不加引号，shell 会先拿 `*.log` 在当前目录做一次展开，等传给 `find` 时已经变成具体的文件名列表了，匹配范围就不对了。

`find` 有个很特殊的脾气：它的长选项只有一个杠。`-name` 是一个杠，`find --help` 里列出来的参数也全是一个杠。正常 Linux 命令的长选项都是两个杠（`--help`、`--version`），`find` 不遵守这个惯例，看到 `-name` 不要以为少打了一个。

想全盘找，把目录换成根 `/` 就行：

```bash
find / -name "*.log"
```

但整个磁盘扫一遍很慢，没必要别这么干。

`find` 找的是文件名，`grep` 找的是文件里的内容。这两个经常被混，记住一句：**find 找文件，grep 找行**。

```bash
grep [要找的词] [在哪个文件里找]
```

手上有个 `error.log`，里面全是 error，`grep error error.log` 一搜一大片，反而看不出哪条是哪条。换个内容有区分度的文件更直观：新建 `test.log`，随手敲几行普通内容，其中一行写上 `error`，后面跟一句请求失败的描述，装作是一份系统运行日志。

```bash
grep error test.log
```

这一行被挑出来了，其余行不显示。但只看到一行，前后文都没有，判断不了这个错误是怎么发生的。`grep` 给了两个参数来补上下文：

| 参数 | 作用 |
| :--- | :--- |
| `-i` | 忽略大小写 |
| `-n` | 显示行号 |
| `-A N` | 命中行之后再多显示 N 行 |
| `-B N` | 命中行之前再多显示 N 行 |

```bash
grep -A 5 -B 5 error test.log
```

命中行前后各五行一起打出来，错误的来龙去脉就清楚了。

> **易错点**：数字写在选项字母后面，`-A 5 -B 5`，而且两个选项要分开写。写成 `5A5B` 或者 `-A5B5` 都不认。

顺便说个实在话：真到了公司里，有了图形化工具，文件双击就能打开、直接编辑，还需要 `vi` 吗？日常自己干活确实不必，双击改完保存，比在黑窗口里按模式切换舒服得多。`vi` 真正的用武之地是服务器——只有 SSH 连过去的一个终端，没有图形界面，这时候会 `vi` 就能救急。所以把它当保底技能，不用当日常主力。

### 管道：把前一个命令的输出交给后一个

`grep` 好用，但它有个前提：得有一个具体的文件给它读。可有时候我们想知道的东西根本不在文件里，而在另一个命令的输出里。

比如想看 `ls` 有哪些参数跟隐藏文件有关。`ls --help` 一敲，帮助文档刷满一屏，几十个参数混在一起，肉眼找「隐藏」两个字太费劲。想用 `grep` 筛，可帮助文档不是文件，是 `ls` 刚刚打印出来的一堆文字，`grep` 后面跟谁？

这就需要管道。写法很简单，一条竖线：

```bash
命令一 | 命令二
```

它的作用是把命令一的输出，直接当成命令二的输入。于是刚才那件事可以写成：

```bash
ls --help | grep 隐藏
```

`ls --help` 先把帮助文档打出来，管道把这些文字接住，喂给 `grep`，`grep` 在其中筛出含「隐藏」的行，屏幕上就只剩下一条：

```text
-a, --all    不隐藏任何以 . 开始的项目
```

一条命令就定位到了想找的参数。

> **提示**：方向别记反——是前一个命令的**输出**，成为后一个命令的**输入**。管道左边负责生产，右边负责消费。

```text
ls --help
   │
   │ stdout：一整篇帮助文档
   ▼
grep 隐藏
   │
   │ 只留下包含「隐藏」的行
   ▼
-a, --all   不隐藏任何以 . 开始的项目
```

管道真正的价值在于「先全量、再筛选」这个套路，凡是输出太长看不清的命令，都可以在后面接一个 `grep`。

查进程就是最典型的例子。`ps -ef` 会把系统里正在跑的所有进程列出来，几十上百行，想找某一个只能翻。接上管道：

```bash
ps -ef | grep mysql
```

`ps -ef` 负责全量，`grep` 负责筛。结果里能看到一个 `mysqld` 进程，说明系统里的 MySQL 正在运行。

同样的套路查 Python：

```bash
ps -ef | grep python
```

能翻出两个 Python 进程。以后自己写的服务跑起来，想确认它到底起没起，也就是这一条命令的事。

到这里，Linux 的常用基础命令就算过了一遍。命令当然远不止这些，但不必背完——真碰到不会做的事，把需求描述清楚去问 AI，它会把命令给你，照着敲就行。这一节讲的这些，作用是把「看不懂 AI 给的命令」这件事解决掉。

### Linux 装软件的几条路子

会装软件，才谈得上部署项目。Linux 上装软件主要有三类方式，区别在于「谁替你编译」这件事。

第一类是自己动手：拿到源码或者二进制发布包，自己配置、编译、安装。这条路最灵活，也最麻烦。麻烦在两点：一是要先做配置，配置对了才能编译；二是编译过程中经常缺依赖，缺什么还得自己去找、自己去装，一层套一层。所以除非有特殊需求，现在用的人已经很少了。

第二类是 `rpm`，第三类是 `yum`。这两个本质是一回事：别人已经把软件编译好、打成包了，你只需要用命令把它下载到本地装上。

| 方式 | 做法 | 特点 |
| :--- | :--- | :--- |
| 源码编译（二进制包） | 下源码或二进制包，配置、编译、安装 | 灵活但麻烦，依赖要自己补，现在少用 |
| `rpm` | 安装别人打好的 `.rpm` 包 | 简单直接，但依赖要手动解决 |
| `yum` | 从软件源在线安装 | 自动处理依赖，最常用 |

但这里有一条硬限制必须记住：`rpm` 和 `yum` 只在红帽系的发行版上有效，也就是 Red Hat Enterprise Linux、CentOS、Fedora 这几个。换个发行版，这两个命令就不好使了，得用那套发行版自己的包管理器。

为什么是这三个？因为 `rpm` 的全称就是 Red Hat Package Manager，红帽的软件包管理器。而 CentOS 和 Fedora 都是红帽这条产品线上的：

| 发行版 | 定位 |
| :--- | :--- |
| Fedora | 先行版，新功能先上，比较激进 |
| CentOS | 开源免费版，基于红帽，功能有删减 |
| Red Hat Enterprise Linux | 稳定企业版 |

三者同源，所以包管理的方式通用。

> **提示**：判断一个 Linux 该用哪套命令，先看发行版。红帽系用 `yum`，Debian 系（Ubuntu）用 `apt`，这是两条完全不同的线。

装软件这件事本身不用发怵。几乎所有软件官网都会给安装说明，照着抄命令就行。顺手打开 nginx 官网找安装方式，文档一打开先愣住——nginx 是俄罗斯出的东西，文档看着费劲，切到英文还是费劲。这时候最省事的办法是直接问 AI：「如何在 CentOS 中安装 nginx」，它会把命令列出来，复制粘贴就完事。换成 Ubuntu 也照样问，AI 会换成 `apt` 那一套。

所以真正的能力不是背下所有软件的安装命令，而是知道去哪问、问的时候把系统说清楚。

### yum 源为什么必须换成国内的

`yum` 装软件的时候，包不是凭空变出来的，它得去一个「软件源」下载。这个源默认指向国外——因为 `yum` 是红帽提供的，服务器自然在境外。国内直接连，常见的结果是连不上，或者慢到让人怀疑网络坏了。

解决办法是把源换成国内的镜像。换源就三步：

1. 先把本地的源配置文件备份一份。这一步是为了留退路，改坏了还能还原；
2. 下载阿里云的源文件，替换掉本地那份；
3. 清掉旧缓存，再重建缓存。

第三步的两条命令是固定的：

```bash
yum clean all
yum makecache
```

`clean all` 把本地缓存的软件包索引清空，`makecache` 按新的源重新拉一份索引下来。不 clean 直接 makecache，旧的索引还混在里面，容易出莫名其妙的错。

> **注意**：换源之前一定先备份。源文件改错会导致 `yum` 彻底不能用，有备份才能一条命令退回去。

演示环境里这一步已经提前做完了，源已经指向阿里云，所以 `yum install` 走的是国内线路，下载速度正常。

Mac 用户的情况要单独说。Mac 上跑 Linux 一般是虚拟机或容器，CPU 架构分两种：

| 机器 | 架构 | 镜像源 |
| :--- | :--- | :--- |
| Intel 芯片的 Mac | x86_64 | 可以直接用现成的 x86 镜像 |
| M 系列芯片的 Mac | ARM | 必须换 ARM 版镜像源 |

ARM 版的源阿里云和华为都提供，华为还有一个专门给 ARM 系统用的镜像站。用错架构的源，装包时会报架构不匹配，所以 M 系列芯片的机器不能图省事直接套用 x86 的配置。

### 用一条命令装好 uv

前面做项目一直用 `uv` 管依赖，到了 Linux 上自然也要装它。`uv` 官网给了两套安装方式，Windows 一套，macOS 和 Linux 共用一套。Linux 这套只有一行：

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

这行命令把前面学的管道又用了一遍，拆开看是三段：

- `curl` 负责把 `install.sh` 这个安装脚本从网上下下来；
- `|` 把下载到的脚本内容交给后面的命令；
- `sh` 负责执行这个脚本。

也就是说，它下载的不是一个安装包，而是一段安装程序，真正干活的是这段脚本。脚本跑完会提示 `Everything is installed`，`uv` 和 `uvx` 两个命令都装好了。

验证一下：

```bash
uv --version
```

能打出号就说明装成功了。整个过程不用手动解压，也不用自己去编译，脚本跑完直接就能用。

> **提示**：`curl ... | sh` 这种写法等于「下载一段代码并立刻执行」，方便，但前提是来源可信。从官网复制的命令可以这么用，来路不明的脚本不要往 `sh` 里灌。

### MySQL 与 systemctl：所有服务一个管法

MySQL 在演示环境里已经装好了，安装步骤直接跳过。跳过不是因为它不重要，而是因为它太碎、太长，一步走错后面全乱。

装 MySQL 的真实流程大概是这样的：系统里往往自带一个 MariaDB，它是 MySQL 的一个衍生开源版本，两者会互相干扰，所以第一步是查有没有旧的 MySQL 或 MariaDB，有就卸掉，卸载还得用 `rpm -e` 加一堆包名；卸干净之后上传安装包，安装包是 `.tar.gz` 的，先解压；解压出一堆目录，进去做配置；配置完编译；编译完才安装。中间任何一步缺依赖，都得回头补。

所以这台机器上的 MySQL 是提前装好的。安装可以跳过，但装好之后怎么管，必须掌握——因为 Linux 里有一大批「开机就自己跑起来」的程序，它们的管理方式全是同一套。

这类程序叫服务（service），管理它们的命令统一是 `systemctl`，后面跟一个动作，再跟服务名：

```bash
systemctl [动作] [服务名]
```

六个动作，全是四级词汇：

| 动作 | 含义 |
| :--- | :--- |
| `start` | 启动服务 |
| `stop` | 停止服务 |
| `status` | 查看服务状态 |
| `restart` | 重启服务 |
| `enable` | 设为开机自启 |
| `disable` | 取消开机自启 |

```text
systemctl ──┬── start     启动
            ├── stop      停止
            ├── status    查看状态
            ├── restart   重启
            ├── enable    开机自启
            └── disable   取消开机自启
```

这套命令的好处是通用：今天管 MySQL，明天装了别的服务，服务名换掉，动作一个字都不用改。所以真正要记的不是某个软件的命令，而是 `systemctl` 这六个动作。

命令敲不全没关系，Tab 键能补。敲一个 `sys`，连按两次 Tab，所有以 `sys` 开头的命令都会列出来，从中挑 `systemctl` 即可。这是 Linux 终端的通用习惯：记不住全名就敲前几个字母，让 Tab 帮你补。

先查 MySQL 的状态：

```bash
systemctl status mysqld
```

注意服务名是 `mysqld`，不是 `mysql`。`mysql` 是客户端命令，`mysqld` 才是那个在后台跑的服务进程。状态显示 `running`，说明正在运行。

把它停掉：

```bash
systemctl stop mysqld
systemctl status mysqld
```

状态变成 `inactive (dead)`，服务确实停了。再启动：

```bash
systemctl start mysqld
```

状态回到 `running`。这就是 `start` 和 `stop`。

那为什么这台机器一开机 MySQL 就在跑？因为之前执行过 `systemctl enable mysqld`，把它设成了开机自启。反过来不想让它自启：

```bash
systemctl disable mysqld
```

> **注意**：`stop` 和 `disable` 是两件事。`stop` 只停这一次，下次开机照样起来；`disable` 是取消开机自启，但当前正在跑的进程不会因此停下。要彻底关掉，得两条都执行。

服务起来了，接下来验证数据库能不能用。用客户端连本机：

```bash
mysql -u root -p
```

`-u` 指定用户，`-p` 表示要输密码。第一次输 `1234` 进不去，因为初始密码不是它，默认密码是 `MySQL1234`。用默认密码登进去之后，就可以改：

- 一条语句改本机登录密码；
- 另一条语句改远程连接密码；
- 最后执行 `flush privileges;` 刷新权限，让改动立刻生效。

本地密码和远程密码是两套，只改本地，远程照样连不上，这是 MySQL 权限表的设计。

改完退出，再用新密码 `1234` 登录，进去了，密码重置成功。进去之后看一眼库：

```sql
show databases;
```

能列出系统自带的库，说明本机访问没问题。

但本机能连，不代表远程能连。这两件事在 MySQL 里是分开授权的，所以还得用图形化客户端从外面连一次才算验证完。

### 防火墙：先放行端口，再决定关不关

新建一个连接：主机填虚拟机的地址 `192.168.150.101`，用户 `root`，密码 `1234`，数据库先不选，点测试。转了一会儿圈，连接失败。

密码没错、服务也在跑，问题出在防火墙上。Linux 默认带着一道防火墙，它会把进来的请求全部拦下，除非你明确放行某个端口。

防火墙本身也是个服务，服务名叫 `firewalld`：

```bash
systemctl status firewalld
```

状态是 `running`，确实开着。既然它是个服务，操作方式就跟刚才管 MySQL 一模一样——`start`、`stop`、`status`，一个字都不变。

```text
远程客户端 ──→ [ firewalld ] ──→ mysqld : 3306
                   │
                   └─ 未放行 3306：请求被丢弃，客户端一直转圈
```

图里这一刀砍在防火墙上：请求到了机器，但没到 MySQL，所以客户端只能超时。

企业里的正规做法是放行端口，而不是关防火墙。MySQL 用的是 3306，放行它：

```bash
firewall-cmd --zone=public --add-port=3306/tcp --permanent
```

`--zone=public` 指定作用区域，`--add-port` 指定端口和协议，`--permanent` 表示写进永久配置。刚加的规则还没生效，要重新加载一次：

```bash
firewall-cmd --reload
```

再确认一下开没开：

```bash
firewall-cmd --list-ports
```

列表里出现 `3306/tcp`，说明放行成功。回到客户端再测，连接通了。

> **提示**：`--permanent` 加与不加的区别是「重启后还在不在」。不加只对当前生效，防火墙一重启规则就没了；加了要 `--reload` 才载入。

理论上，企业里就该这么干：用哪个端口开哪个，最小暴露面。但这台是本地虚拟机，后面项目要用的端口一个接一个，每来一个就配一次规则太折腾。所以这里干脆把防火墙整个关掉，一劳永逸：

```bash
systemctl stop firewalld
systemctl disable firewalld
```

先停当前进程，再取消开机自启，两条都执行完，它才算彻底不挡路。

> **注意**：这套操作只适用于自己的本地虚拟机。云服务器、公司服务器上绝对不能这么干——该开哪个端口就开哪个，云主机还要在安全组里单独放行，两层都配对了才通。图省事直接关防火墙，等于把机器裸奔在公网上。

到这里，数据库部署完成，本地能连、远程也能连。库里现在还是空的，一张表都没有，等后面建了表，就能正常读写了。回头看这一整段：文件能打包压缩、能编辑、能按名字和内容查找，软件能装、服务能起停、端口能放行——一台机器从「能用」到「能部署项目」，靠的就是这些。

> **承前启后**：上一节讲完「Linux 文本处理与软件环境：从打包到部署」，下一节接着讲「前后端分离、Nginx 部署与 Docker 初识」。

## 前后端分离、Nginx 部署与 Docker 初识
> 对应块：BLK04 | 覆盖分集：P15-P18 | 块标题（分集名）：《前后端分离部署与 Docker 入门》

### 前后端分离：一个页面，两半内容

接下来要装一个东西，叫 Nginx。装之前先把它是干什么的弄清楚，不然装完了也不知道自己在装什么。

Nginx 是一个轻量级的 web 服务器，作用就两个：部署前端静态资源，对请求做反向代理。这两个作用不是并列摆着好看的，它们正好对应一个页面里的两类内容。

先把之前做的 AI 伴侣翻出来看。那个项目里，`app` 目录是后端，`static` 目录是前端——前后端都在同一台服务器上。真实企业开发不是这样：招聘网站上既有前端岗位，也有服务端岗位，前端有自己的团队，不可能跟后端挤在一个项目里开发，各写各的。所以企业里前后端一定是分离的，前端独立部署，后端也独立部署。

那前端和后端分别给用户提供什么？

我启动本机的 MySQL，访问一直用的 `127.0.0.1:8000`。前端给的是 HTML、JS、CSS——这些只提供样式，是个架子，一个花架子。可页面上那些绘画作品名（「第一天」「第二天」「第四天」）是哪来的？后端给的。

刷新页面看加载过程：先下来一大堆 JS、CSS 这些基础文件，样式就有了。但光有样式不够：要展示绘画列表，得发一个请求查绘画列表；要展示预设列表，得发一个请求拿全部预设；要查绘画历史，还得再发一个请求。

于是能确定一件事：浏览器渲染出来的页面分两部分。一部分是静态资源，就是页面样式；另一部分是动态数据，就是下拉框里的内容、列表里的条目。而且动态数据是可变的——写页面的时候根本不知道你有什么数据，只有请求发出去、结果拿回来，页面才知道。

> **结论**：前端展示样式，后端展示数据。

那么前后端分离到底怎么落地？将来要有一台专门的前端服务器，就是 Nginx；还要有一台专门的后端服务器，就是我们自己写的那个项目，跑在 8000 端口上。

用户访问 `localhost:8000` 那一刻，首先要加载页面，也就是 `index.html`；而 `index.html` 底下又依赖 CSS 样式和 JS。这些统一叫静态资源，将来全放到 Nginx 上。Nginx 发现你请求的是静态资源，而它自己磁盘上就有，就直接返给你，前端拿到就能渲染。

渲染完，你看到的是页面的基本样子，但此时没有数据。紧接着前端向后端发新的请求：`/api/preset-process` 拿预设，`/api/session` 拿会话列表。

这些请求到了 Nginx，Nginx 上有这些东西吗？没有，因为它们是后端的。所以 Nginx 会把请求代理到后端服务，后端把结果返回给 Nginx，Nginx 再返回给浏览器。这样前端就看到结果了。

```text
浏览器
  │
  │ ① 请求 index.html、app.js、*.css、图片
  ▼
Nginx（前端服务器，192.168.150.101:80）
  │  这些文件就在磁盘的 html 目录里 → 直接返回，页面渲染出样式
  │
  │ ② 页面渲染完成后，前端再请求 /api/preset-process、/api/session
  ▼
Nginx 判断：不是静态资源 → 反向代理
  │
  ▼
后端服务（8000 端口）
  │  查数据库、组织数据
  ▼
结果原路返回：后端 → Nginx → 浏览器
```

读图：静态资源走 ①，Nginx 自己就地返回；动态数据走 ②，Nginx 只当中间人，把请求转给后端，再把后端的响应原样带回浏览器。

所以前端需要静态资源和动态数据：静态资源放前端服务器，动态数据放后端服务器。Nginx 的两个作用正好对应这两件事——你要静态资源，它直接给；你要动态数据，它替你去后端取。这种部署方式，就叫前后端分离。

| 对比项 | 静态资源 | 动态数据 |
| :--- | :--- | :--- |
| 具体内容 | HTML、CSS、JS、图片 | 绘画列表、预设列表、会话历史 |
| 由谁提供 | 前端服务器 Nginx | 后端服务器 |
| 写页面时是否确定 | 确定，就是磁盘上的文件 | 不确定，请求回来才知道 |
| 存放位置 | Nginx 的 html 目录 | 数据库，由后端查询后返回 |

### 安装 Nginx：配置、编译、安装三步

Nginx 编译需要一堆依赖，这些我已经提前装好了，你不用再动，直接从 Nginx 本体开始。

资料里的「其他软件」里有一个 `nginx-1.20.2.tar.gz`。上传到哪都行，`/root` 或 `/tmp` 都可以，我习惯传 `/tmp`。先把 `/tmp` 里原有的东西清掉，再把压缩包拖上去。

解压用 `tar`，参数这样记：压缩包是 gzip 的，加 `z`；这次是解压，用 `x`；再跟 `v` 和 `f`，最后是文件名：

```bash
tar -zxvf nginx-1.20.2.tar.gz
```

解压很快，多出一个 `nginx-1.20.2` 目录。进去执行配置命令：

```bash
cd nginx-1.20.2
./configure --prefix=/usr/local/nginx
```

这条 `configure` 是配置命令，作用是决定 Nginx 编译好之后安装到哪个目录，这里定成 `/usr/local/nginx`。

> **注意**：`configure` 只是配置，还不算编译。配置完还要 `make` 编译、`make install` 安装，三步一步都不能省。

```bash
make
make install
```

`make` 要跑一会儿。装完退出源码目录——这时源码就没用了，程序已经落到 `/usr/local/nginx`，源码留着白占空间，可以直接删。

到 `/usr/local/nginx` 下看，装好的 Nginx 就四个目录，各管一摊：

| 目录 | 放什么 | 什么时候用到它 |
| :--- | :--- | :--- |
| `conf` | 配置文件，包括 `nginx.conf` | 改端口、改站点配置 |
| `html` | 前端静态资源 | 部署页面、图片 |
| `logs` | 日志 | 排查访问和报错 |
| `sbin` | 可执行文件 | 启动、停止服务 |

`conf` 顾名思义放配置文件，`html` 放前端静态资源，`logs` 放日志，`sbin` 里是可执行文件——要启动它，就得找 `sbin` 里的 `nginx`；要放静态资源，就放 `html`；要改配置，就进 `conf`。

### 端口、location 与静态资源目录

启动很简单，进到 Nginx 目录，敲 `sbin/nginx`：

```bash
cd /usr/local/nginx
sbin/nginx
```

回车之后什么都不打印，别以为没启动。它是后台服务，输出不会占着你的终端。用 `ps` 看进程：

```bash
ps -ef | grep nginx
```

能看到两个进程：`master` 主进程和 `worker` 工作进程，两个都起来了，说明服务在跑。

服务器总要有端口。端口就写在它的配置文件 `conf/nginx.conf` 里，文件里东西很多，最关键的有一句 `server` 下的 `listen 80`——说明这个服务监听的是 80 端口。

那就在浏览器访问虚拟机地址 `192.168.150.101`，输入 80 和不输 80 是一回事，浏览器会把 80 藏掉。

> **提示**：HTTP 协议的默认端口是 80，HTTPS 的默认端口是 443。访问百度时不写端口，走的就是默认的那一个。

一访问就看到了 Nginx 的欢迎页。为什么是它？看 `nginx.conf` 里 `server` 下面这段：

```nginx
server {
    listen 80;
    location / {
        root   html;
        index  index.html;
    }
}
```

`location /` 有点像之前写 FastAPI 时的 `@app.get("/")`，处理的是斜杠这个路径。整段的意思是：前端请求的是 `/`，就默认去 `root html` 这个位置找；`root` 指的是 Nginx 的安装根目录 `/usr/local/nginx`，所以 `root html` 合起来就是 `/usr/local/nginx/html`；`index index.html` 再指定首页是 `index.html`。

去 `html` 目录看，里面确实有 `index.html`，内容就是 Welcome to Nginx，所以我们看到的才是那个欢迎页。

改它试试。把文案换成中文，刷新——乱码了。原因是页面没声明编码：网页的响应头里要带 `Content-Type: text/html; charset=UTF-8` 这样的信息，浏览器才知道用什么编码解析；没声明，它只能猜，中文就花了。在页面头部补上这一行：

```html
<meta charset="UTF-8" />
```

再刷新就正常了。改 `index.html`，前端页面跟着变，这说明 Nginx 返回的就是这个文件本身。

既然静态资源全放在 `html` 目录里，那要部署自己的东西怎么办？往 `html` 里扔就行。我扔一张 jpg 进去，访问 `192.168.150.101/图片名.jpg`，图片直接出来了。

> **结论**：部署静态资源不用改任何配置，把文件放进 `/usr/local/nginx/html` 就算部署成功。

要停掉它，还是找 `sbin` 里的 `nginx`，加 `-s stop`：

```bash
cd /usr/local/nginx
sbin/nginx -s stop
```

### 部署后端：上传、改 .env、装依赖

Nginx 装好了，接下来真正部署项目。资料里「课前代码」下有一个 robot 项目，里面 `backend` 和 `frontend` 两个目录：`frontend` 就是那个页面，`backend` 是后端。先部署后端，因为它简单——一个 Python 项目，扔上去启动一下就行。

第一步，上传。传到任意目录都可以，比如 `/tmp`，先清空再上传。

> **易错点**：后端目录里有个 `.env` 文件，以点开头，默认隐藏。不打开「显示隐藏文件」你根本看不见它，还会以为自己没传上去。务必先确认 `.env` 在，再往下做。

第二步，改 `.env`。要改的其实就三样：

- DeepSeek 的 API Key，换成你自己的；
- 数据库地址与端口，`localhost:3306`；
- 数据库密码，如果你本机 MySQL 的密码改成了 1234，这里也写 1234。

模型名保持原样即可。数据库地址为什么不用改？因为数据库和这个项目都部署在同一台虚拟机上，用 `localhost` 就能连到，没问题。

第三步，装依赖。这是一个 uv 项目，项目根目录里有 `pyproject.toml`，你装过的所有依赖都记录在这里面。有了这个文件，装依赖就是一条命令：

```bash
cd backend
uv sync
```

`uv sync` 会把项目需要的东西全部拉下来。记住这个动作：拿到一个新的 uv 项目，第一件事就是 `uv sync`，跟你拿到一个前端项目先执行 `npm install` 是一个道理。

第四步，启动。用 `uv run` 起服务，端口 8000。

第一次启动会报错：`Unknown database 'robot'`。这不是连不上数据库，是 `robot` 这个库还没建——库不存在，表自然也没有。客户端工具里不方便直接建库，就用 SQL 建一个：

```sql
CREATE DATABASE robot;
```

刷新一下能看到 `robot` 库了，重新启动，成功。访问 `192.168.150.101:8000/docs`，Swagger 文档出来了：注册、登录、聊天会话，还有会话和绘画的增删改查，跟你们做的 AI 伴侣效果一样。

所以部署后端就四步：上传项目 → 改 `.env` 里的 Key 和数据库账号密码 → `uv sync` 装依赖 → `uv run` 启动。

### 用 systemd 把项目变成系统服务

项目能跑了，但这样跑有个毛病：命令敲下去，控制台就卡在那儿，什么都干不了；按 Ctrl+C，服务立刻停；就算不按，控制台一关，服务也跟着没了。

> **定义**：这种占着终端不放、终端一断服务就死的运行方式，叫前台运行。

想后台运行，得把它注册成系统服务。在 `/etc/systemd/system` 下新建一个文件，名字随便叫，比如 `robot-api.service`：

```bash
vim /etc/systemd/system/robot-api.service
```

没有 `vim` 就用 `vi`。打开之后先按 `i` 进插入模式，看到 INSERT 再粘贴——千万别直接粘，不在插入模式粘贴会贴得乱七八糟。粘完按 `Esc`，输入 `:wq` 保存退出。

> **易错点**：服务文件里写的是项目的绝对路径。我这次把 `backend` 传到了 `/tmp`，可文件里配的是 `/root/backend`，启动当然找不到。要么把目录搬过去，要么一开始就传到 `/root`：

```bash
cp -r /tmp/backend /root/
```

写完还要让 systemd 认识这个新服务，并给文件加上可执行权限：

```bash
systemctl daemon-reload
chmod +x /etc/systemd/system/robot-api.service
```

之后就能像管 MySQL 一样管它了：

| 命令 | 作用 |
| :--- | :--- |
| `systemctl start robot-api` | 启动服务 |
| `systemctl status robot-api` | 查看状态 |
| `systemctl stop robot-api` | 停止服务 |
| `systemctl enable robot-api` | 开机自启 |

先 `status` 看一眼，状态是 dead；`start` 之后再 `status`，变成 running；回浏览器刷新，页面照常。想停就 `stop`，服务干净地停下。

到这里，后端部署的完整链条是：上传项目 → 改 DeepSeek 的 Key 和数据库用户名密码 → `uv sync` 装依赖 → 配一个 service 让它开机自启。

### Docker：把装环境变成一条命令

最后认识 Docker。昨天的预习任务里有 Docker 安装的笔记，很多同学已经照着做了——不用做，虚拟机里我已经装好了。

Docker 的安装和其他应用一样，都得用包管理器装；区别是先卸旧的、再装新的、还要设软件源、设开机启动、配镜像加速，整体流程挺繁琐。这些我都替你们配完了。

那 Docker 到底是个什么东西？装好之后，它跟 MySQL 一样，是你本地的一个服务。`systemctl status docker` 一看，运行状态。

既然是服务，就能操作——就像你用 `mysql -u` 连上 MySQL 再敲命令一样，Docker 也是启动起来放在那儿，我们通过命令去用它。

> **结论**：Docker 最重要的作用，是帮我们搭建项目环境、做部署。

为什么需要它？回想装 MySQL 的过程：步骤非常多，很多同学装到最后服务都跑不起来。传统安装有几个绕不过去的问题：

- 安装包不好找——不给你安装包，你根本不知道去哪下载；
- 要区分系统版本——Linux 和 Windows 下的包不一样；
- 下载完要解压，解压完还有一堆命令等着执行；
- 命令太多记不住，安装包太多不知道去哪下，步骤太复杂容易出错。

Docker 就是来解决这一串问题的。用它装 MySQL，只需要一条命令：文档上那条命令看着有好几行，其实是一条——行尾的反斜杠只是「这句还没写完，换行接着写」的意思，不是命令结束。复制、粘贴、回车。

一瞬间就结束了。MySQL 装好了吗？装好了，而且已经启动。它映射出来的端口是 3307，密码是 123123。打开 MySQL 客户端（用 PyCharm 连也是一样的），填上端口和密码，连上了；执行 `show databases;`，能出结果。

> **结论**：有了 Docker，环境不用再背一堆命令去装，一条命令、等它跑完，MySQL 就起来了。

| 传统安装 | Docker |
| :--- | :--- |
| 先卸旧版，再找安装包 | 一条命令 |
| 要按系统版本挑包 | 不用挑 |
| 手动解压，逐个执行命令 | 自动完成 |
| 命令记不住、步骤易出错 | 敲回车等它跑完 |

前端有 Nginx 接着，后端有 systemd 管着，环境有 Docker 一键铺开——一个项目从「在我电脑上能跑」，到「在服务器上能跑」，靠的就是这三样东西。

## Docker 从一键安装说起：镜像、容器与常用命令
> 对应块：BLK05 | 覆盖分集：P19-P21 | 块标题（分集名）：《Docker 运行架构与常用命令》

### 一键安装的背后，Docker 到底做了什么

刚才那条命令敲下去，MySQL 就起来了，快得像什么都没发生。可你要是换一台什么都没准备过的电脑，同样的命令绝不会这么利索——它会老老实实把过程走给你看：先告诉你本地没有，再去远处取，取完再替你启动。

真实的情形是这么两行：

```text
Unable to find image 'mysql:latest' locally
latest: Pulling from library/mysql
```

第一行是在说本地找不到 `mysql` 这个镜像；第二行开始 `Pulling from library/mysql`，pull 就是拉取，说得直白点就是下载。你没有告诉它安装包在哪，也不用告诉它——你只说了要装什么（MySQL），外加一些参数配置（比如端口），剩下的找包这件事它自己包了。

这正好对上传统装 MySQL 最头疼的两件事。

第一件，不知道安装包在哪里。你得翻官网、挑版本、对系统，还得担心下错了。现在还要你管吗？不需要，人家自动去下载。

第二件，命令太多，记不住。现在也不用记了，命令是给你准备好的，复制粘贴就完事，一条就够，不用背一长串。

下载完之后，它还不只是把包下好——下完直接给你启动起来，把运行环境一并准备好。所以那个"环境到底配没配对"的问题，也轮不到你操心了。

> **结论**：一条 `docker run`，等于替你把"找包、下载、装好、启动"这四步串成了一步。它内部其实是先做一次 pull 再 run，所以你用它的时候，根本不需要事先下载镜像。

能一键搞定，是因为它下载的东西压根不是我们平常说的安装包。这件事得从镜像讲起。

### 镜像不是安装包，是自带环境的一整套运行条件

有个问题很值得停下来想一想：Docker 的命令是不区分操作系统的。你在 Windows 上敲 `docker run`，在 Linux 上还是这一条，一个字都不用改。它下载的时候，也不用管两边环境的差异。

它是怎么做到的？凭什么不用管环境？

因为它下载的这个东西不是普通的安装包。我们平常自己下安装包，得先考虑系统环境——Windows 一个版本、Linux 一个版本，下完还要配不同的环境，装完可能还跑不起来。Docker 下的这个玩意，叫镜像，英文 image。

镜像里装的不只是 MySQL 本身，还有它运行所需要的环境、配置、系统级函数库，甚至一个模拟出来的操作系统环境。

拿 MySQL 举例：MySQL 底层可能要调一些系统函数，依赖一些系统环境；可你的电脑可能是 Windows，可能是 Linux，有同学还是 Mac，这些函数库和配置在你机器上可能压根就不存在。那怎么办？它就把 MySQL 运行时需要的环境配置、系统级函数库统统准备好，再给它准备一个"像操作系统一样"的环境，全部打包到一起——这个打包出来的东西，就是镜像。

所以镜像能满足自己的运行需求，可以独立运行，不依赖外部环境。

> **提示**：镜像和安装包不是一回事。安装包给你一堆零件，装到哪台机器上还得看那台机器有没有配套的水电；镜像给你的是一间零件齐全、水电都接好的小车间，搬到哪都能直接开工。这也是同一条命令能横跨 Windows、Linux、Mac 的原因。

### 容器是跑起来的镜像，一间隔离的房子

镜像拿到了，接下来是运行。而在运行这一步，Docker 还有更狠的一手：它会帮你模拟出一个操作系统的隔离环境。

注意这个说法的分寸——它模拟的是一个操作系统环境，有点像虚拟机，但它不是虚拟机，比虚拟机轻量得多。它没有真的虚拟出一整套硬件，只是把操作系统上"有哪些文件、有哪些函数库"这套文件环境给你模拟出来。

然后，它把下载好的 MySQL 丢进这个独立的环境里启动。这样一个与外界隔离的运行环境，就叫容器。

我为什么要反复强调"独立、隔离"？因为有了隔离，一个镜像在运行时可以同时跑好几份容器。

爱玩游戏的同学对这个概念应该很熟，叫多开，也叫双开：一份游戏客户端，同时开好几个，自己一个人操纵好几个账号一起玩。再想想微信、QQ——你电脑上就下载了一份微信，平常只能启动一份；多开工具用某种隔离手段，让同一份程序同时启动多份，你就化身成了"时间管理大师"，同时跟 N 个人聊天互动。

要是没有容器这种隔离，你在自己电脑上能同时开好几个微信吗？不能，它们会打架，起都起不来。

```text
              镜像 mysql:8.0
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
   容器 mysql    容器 mysql2   容器 mysql3
    端口 3307     端口 3308     端口 3309
```

三个容器用的是同一份镜像，各自住在一间独立环境里，跑各自的进程，互相不干扰；外界要访问谁，就走谁自己的端口。

> **结论**：镜像解决的是"到哪都能跑"，容器解决的是"跑几份都不打架"。这两层合起来，才是一套完整的隔离。

### 镜像存在哪：仓库、官方与加速器

镜像这么强，那去哪下载？

Docker 官方有一个专门管理和存储镜像的网站，叫 Docker Hub，域名是 `hub.docker.com`。可惜国内现在访问不了。

那我刚才的镜像是从哪下的？我提前把 Docker 的镜像加速配好了。配进去的是这么一串地址：第一个是网易的镜像，第二个是清华大学的，第三个是搜狐的，然后是阿里的、腾讯的……各大云厂商的我都配进去了。它将来会自己挨个去试，一个不行再试第二个，所以总能成功。

那这些镜像本身又是谁做的？这也不用你管。它们是现成的：一部分由 Docker 官方制作，一部分由软件方自己做——比如 MySQL 官方做好，再上传到 Docker Hub。

像这种专门提供 Docker 镜像管理和存储服务的服务器，有个专门的叫法：docker registry，翻译过来就是镜像仓库。

| 仓库类型 | 例子 | 说明 |
| :--- | :--- | :--- |
| 官方仓库 | Docker Hub | 镜像最全，官方出品，国内直连不顺 |
| 第三方仓库 | 阿里云、华为云、网易、清华源 | 各大云厂商和高校提供，通常要登录，能加速 |
| 私有仓库 | 公司自建 | 公司内部镜像不便外传时自己搭一个 |

所以"镜像去哪下载"这个问题，答案是：默认去官方仓库，实际多半走第三方仓库或私有仓库，而配好镜像加速之后，具体走了哪家你都不必关心。

### 一条 docker run 走完的完整链路

现在把镜像、容器、仓库这三个概念串起来，看一条命令从头到尾都发生了些什么。

Docker 装好之后，它其实就是一个服务，一个 server，一直在那儿跑着。这个进程叫 docker daemon，就是后台守护进程的意思，它待在那儿等着你敲命令来操作它。

```text
docker run mysql:8.0
        |
        v
docker daemon 收到命令
        |
        |  (1) 先看本地镜像库：有 mysql 吗？
        +---- 有 ------> 跳过拉取
        |
        +---- 没有 ----> 去 registry 拉取，存进本地镜像库
        |
        v
  (2) 用镜像创建容器
        |
        v
  (3) 在隔离环境里启动容器，服务跑起来
```

我从上往下走一遍。你敲下 `docker run`，守护进程监听到这条命令，一看后面跟的是 MySQL，它就知道你要跑 MySQL；于是先去镜像仓库里找，找到之后拉取到本地，放进本地的镜像库。镜像到位以后，它自动创建一个容器——一个模拟了一台计算机的隔离环境，环境里已经备好了 MySQL 运行所需的依赖、系统函数库和配置，所以它能自己跑起来，不依赖外界。容器起来之后，由于是隔离的，同一个镜像还能再起好几份容器，彼此互不影响。

这里有个细节特别值得拎出来：拉取这个动作是一次性的。

一旦拉完，下次你再执行 `docker run mysql`，它会先来本地找；发现本地有了，就不会再去拉。这也解释了刚才演示时的一个反常现象——命令一回车就好了，你们根本没看到下载过程。不是网络快，是我在本地已经把镜像都给你们准备好了，所以你们不需要下载。

> **提示**：第一次 `docker run` 会带一段下载过程，第二次起就是秒开。如果你发现一条命令下得特别久，先别怀疑命令写错了，多半是镜像还没落到本地。

### 拆开 docker run：每个参数在说什么

刚才执行的那条命令看起来挺复杂，一行里塞了好几个看不懂的部件。我们一行一行拆开看，看到最后你会发现它其实不难。

```bash
docker run -d --name mysql -p 3307:3306 \
  -e TZ=Asia/Shanghai \
  -e MYSQL_ROOT_PASSWORD=123 \
  mysql:8.0
```

写一行也行，写长了你就在行尾加个反斜杠换行；我习惯分几行写，每行一个参数，看着清楚。

`docker run` 本身是固定写法，意思是创建并运行一个容器。注意"创建"和"运行"两个动作都在里面——所以一开始是没有容器的，只有镜像；你 run 了一次，才有容器。

`-d` 是让容器在后台运行。前台运行和后台运行的区别，前面讲过：前台运行就是命令卡在那儿，命令一结束，服务也跟着停了；后台运行则是命令敲完立刻回你，程序自己在后面跑着，不用你管。以前配个后台服务要折腾一堆东西，现在一个 `-d` 就完事。

`--name mysql` 是给容器起个名字，名字可以自定义，但必须唯一，不能跟别的容器重名。所以这条命令你要是原样再执行一遍，它会报错——报的就是名字重复。以后你看到"容器名已存在"这类报错，不用怀疑别的，就是名字被占了。同一个命令不要重复跑，要跑就换个名字。

`-p 3307:3306` 这个参数最需要讲清楚。容器是一个隔离环境，MySQL 装在容器内部，那么理论上讲，外界的人能不能访问它？不能，任何人都会被拦在外面。隔离不是白隔离的，它就是不让你进。

可要真是谁也访问不了，我装它干啥？我最终的目的就是能连上它。这时候就轮到端口映射出场了：把宿主机的某个端口，映射到容器内的某个端口。

```text
MySQL 客户端
     |
     |  连接 192.168.150.101:3307
     v
宿主机（CentOS 虚拟机）的 3307 端口
     |
     |  -p 3307:3306 这条映射规则
     v
容器内部的 3306 端口  --->  MySQL 进程
```

`192.168.150.101` 是我们那台 CentOS 虚拟机的 IP，也就是 Docker 所在的那台机器——我们把它叫宿主机。宿主机上装了 Docker，Docker 里跑着 MySQL 容器。你连宿主机 IP 的 3307，因为配了映射规则，请求会被转到容器内的 3306，于是你就间接地访问到了容器里的 MySQL。

> **易错点**：`-p` 后面冒号左边是宿主机端口，冒号右边是容器内端口。方向只有这一种，写反了就连不上。`-p 3307:3306` 读作"把宿主机的 3307 映射到容器内的 3306"。

那为什么我非要写 3307，宿主机上也用 3306 行不行？行，你想叫什么都行，你自己说了算——只要宿主机本身的 3306 没被别人占用。我写 3307 纯粹是为了让你一眼看出这俩数字不一样，好讲清楚谁是谁。要是宿主机的 3306 已经被占了，那就不能用它。

后面两个 `-e` 是环境变量，固定格式是 `key=value`。第一个 `TZ=Asia/Shanghai` 是在配时区，TZ 就是 time zone，配成亚洲上海，也就是东八区。第二个 `MYSQL_ROOT_PASSWORD=123` 是给 MySQL 的 root 用户设密码，这里设的是 `123`。

这些环境变量我是怎么知道该这么配的？去镜像的官网查的——每个镜像支持哪些 `-e`，官方文档里写着。不过你们不用去查，我直接把该配的给你们，照着写就完了。

最后一个 `mysql:8.0` 是镜像的名字。前面说了，`docker run` 要先拉镜像再跑容器，那你到底要跑哪个镜像？就是它。你告诉 Docker 镜像名，它去下载，下载完在本地运行。

这个镜像名还分两段，中间用冒号隔开：冒号前面的叫 repository，冒号后面的叫 tag。tag 是什么？就是版本。所以镜像通常由这两部分组成——镜像名加版本号。

那能不能不写版本？能。不写版本的时候，默认按 `latest` 处理，latest 就是最新的意思。

到这里命令就拆完了，回顾一遍：`run` 是创建并运行容器，`-d` 后台运行，`--name` 起名字，`-e` 设环境变量，`-p` 设端口映射（宿主机端口在前、容器内端口在后），最后跟上 `repository:tag` 形式的镜像名。

那我当场问你们一个问题：现在我想再跑一个 MySQL 容器，让它用 3306 端口，命令怎么写？

```bash
docker run -d --name mysql2 -p 3306:3306 \
  -e TZ=Asia/Shanghai \
  -e MYSQL_ROOT_PASSWORD=123 \
  mysql:8.0
```

名字不能再叫 `mysql` 了，换一个，`mysql2` 就行。端口左边写 3306——因为上一个容器占的是宿主机的 3307，3306 还空着——右边仍然是容器内的 3306，环境变量原样复制。回车，一个新容器就创建好了，拿客户端连 `3306`，`show databases` 一切正常。

同学们，在同一个电脑上，我说启动就启动一个全新的 MySQL。你想想，如果没有 Docker，你想同时装两个 MySQL，这现实吗？根本不现实，光是让两份 MySQL 各跑各的、互不干扰，就够折腾半天。现在就是一行命令的事，甚至这行命令你都不用敲，复制过来改两个字就行。这就是 Docker 的厉害之处。

### 命令全景：镜像一套，容器一套

快速入门跑通之后，很多同学的第一反应是：我启动的应用长啥样？进程怎么查？

用 `systemctl` 是不行的。`systemctl` 管的是装在宿主机上的应用，而我们这些应用都跑在容器里，容器归 Docker 管。所以从这儿开始，得学 Docker 自己那一套命令。

Docker 的命令说到底就两类：对镜像的操作，和对容器的操作。下面这堆不用背，看一遍有个印象，用的时候回来查。

镜像这条线，逻辑是顺着"镜像怎么来、怎么用、怎么走"展开的：

| 命令 | 作用 | 重要程度 |
| :--- | :--- | :--- |
| `docker pull 镜像名` | 从仓库拉取镜像到本地 | 一般，`run` 会自动做 |
| `docker images` | 查看本地有哪些镜像 | 常用 |
| `docker rmi 镜像名/镜像ID` | 删除本地镜像 | 常用 |
| `docker build` + Dockerfile | 自己构建一个镜像 | 常用 |
| `docker save` | 把镜像保存成压缩包 | 了解 |
| `docker load` | 加载别人给的镜像压缩包 | 了解 |
| `docker push` | 把镜像推送到远程仓库 | 了解 |

`pull` 是拉取镜像，后面跟镜像名，比如 `mysql:8.0`，你得告诉它拉哪个。`images`（`image` 加个 s）是查看本地镜像。`rmi` 是删除镜像，`rm` 是 remove，`i` 是 image 的缩写。`build` 配合 Dockerfile 用来自己打包镜像——仓库里没有你想要的，就自己做一个，这个后面会讲。`save` 把本地镜像存成压缩包，通过网络传给同事用；同事那边用 `load` 加载回来。这两种方式多用于局域网，或者自己玩一玩。如果你想让全世界都能用，那就 `push` 推到官方镜像仓库去。

> **易错点**：`rmi` 后面跟的是镜像名或镜像 ID，`rm` 后面跟的是容器名。一个是删镜像，一个是删容器，别搞混。

容器这条线，逻辑是"创建、看状态、停启、删除、看日志、进入"：

| 命令 | 作用 | 重要程度 |
| :--- | :--- | :--- |
| `docker run` | 创建并运行一个容器 | 常用 |
| `docker ps` | 查看运行中的容器 | 常用 |
| `docker ps -a` | 查看所有容器，含已停止的 | 常用 |
| `docker stop 容器名` | 停止容器 | 常用 |
| `docker start 容器名` | 启动一个已停止的容器 | 常用 |
| `docker restart 容器名` | 重启容器 | 常用 |
| `docker rm 容器名` | 删除容器 | 常用 |
| `docker rm -f 容器名` | 强制删除运行中的容器 | 常用 |
| `docker logs 容器名` | 查看容器运行日志 | 常用 |
| `docker exec -it 容器名 bash` | 进入容器内部 | 了解 |

最常用的其实就是那几个：`docker images`、`docker rmi`、`docker build`、`docker run`、`docker ps`，剩下的知道有这回事就行。

`docker run` 之所以能顶掉 `pull`，是因为它内部先做了一次 pull 再 run，所以你不需要自己先拉一遍。

`ps` 是 process status 的缩写，看的是进程状态，也就是容器在不在跑。`-a` 是 all，带上它就连已经死掉的容器一起看。

`rm` 和 `rmi` 只差一个字母，作用完全不同：`rm` 删容器，`rmi` 删镜像。

这些命令值得存成一张图，哪天忘了某个命令，回来扫一眼就行。

### 上手第一轮：拉取、查看、删除镜像

接下来做一组实验，把刚才说的命令挨个跑一遍：找一个 nginx 镜像，拉取到本地，创建并运行容器，查看容器，停止、启动、进入、删除。

第一件事是去 Docker Hub 搜 nginx 镜像。可惜 Docker Hub 现在访问不了，很尴尬。那阿里云能搜吗？理论上应该能——一试，不让访问，镜像服务要登录才行。找了个第三方镜像仓库，nginx 倒是搜得到，但都不是官方的，什么社区维护的、2024 年的旧货，算了，放弃。咱们就假装搜到了：镜像名叫 `nginx:open`。

顺便说一句，`open` 这个位置是 tag，也就是版本号，但版本号不一定非得长成 `1.0`、`2.0` 的样子，`open`、`latest`、`alpine` 这些都可以是 tag。别一看到不是数字就以为写错了。

镜像名有了，拉取它。拉取镜像用 `pull`：

```bash
docker pull nginx:open
```

回车之后网络卡了一下，我还以为是网络太差，稍等片刻进度就出来了，拉取成功。

拉完怎么知道本地有没有？查看本地镜像：

```bash
docker images
```

本地镜像非常多，滚了一屏。刚拉的 `nginx:open` 就在里面，此外还有 Python、Postgres 之类。列表的列含义是：第一列 repository，镜像名；第二列 tag，版本；第三列 image id，每个镜像自己的 ID；再往后是创建时间，多少天以前之类的。

> **易错点**：最后一列那个时间不是你拉取的时间，是这个镜像被构建出来的时间。刚刚拉取不等于刚刚创建，这两件事别搞混。

列表里还有一个没有 tag 的"坏"镜像，标签一栏是空的，估计是以前不小心弄出来的。删掉它：

```bash
docker rmi IMAGE_ID
```

`IMAGE_ID` 那个位置，放进 `docker images` 里那一列查到的实际值。

删除镜像除了能传镜像名，也能传镜像 ID。像这种没有 tag 的，名字已经没法用了，只能靠 ID 删。回车，删掉。

到这儿三个命令已经演示完了：`pull` 拉取、`images` 查看、`rmi` 删除。

### 上手第二轮：起容器，和一次真实的翻车

学会了拉取、查看，接下来创建并运行一个 nginx 容器。命令还是那套：`run`，加 `-d` 后台运行，加 `--name` 起名字（就叫 `nginx` 吧），加 `-p` 做端口映射——nginx 默认监听 80 端口，那就把宿主机的 80 映射到容器内的 80。环境变量这次不配，因为我没查官网，不知道 nginx 有什么可配的，不配也能跑。

```bash
docker run -d --name nginx -p 80:80 nginx:open
```

回车，返回了一长串数字。这一串是什么？是你刚创建的这个容器的 ID。

那我怎么知道它到底起没起来？看进程：`docker ps`。ps 是 process status，查看进程状态。

```bash
docker ps
```

结果里面只有两个容器，都是 MySQL。我的 nginx 呢？不在。不在就说明没运行起来，运行失败了。

加上 `-a` 再看：

```bash
docker ps -a
```

看到了，有一个已经死掉的 nginx，状态那一列写着 `Exited`，也就是已退出。

所以 `ps` 和 `ps -a` 的区别很清楚了：不加 `-a` 只看运行中的容器，加了 `-a` 连已经停止的容器一起看。屏幕上信息比较密，我把列的意思捋一遍：第一列容器 ID，第二列这个容器用的镜像，第三列在容器里执行的命令，然后是创建时间，接着是状态——`Up` 表示运行中，`Exited` 表示已退出，最后是端口和容器名字。

已经跑着的 MySQL 状态是 `Up`，死掉的 nginx 状态是 `Exited`，一眼就能分辨。

那它为什么死？看日志，`docker logs` 后面跟容器名：

```bash
docker logs nginx
```

一串报错，里面提到 PID，还带着 `operation not permitted` 之类的话，看着像是权限问题。

这就很奇怪了：容器内部是一个隔离环境，隔离环境里怎么会有权限问题？我第一反应是本地那个 nginx 在捣乱——本地的 nginx 我没停吗？停掉，再试，还是不行。把本地的全干掉，再试，还是不行。完了，翻车了。

最后我换了个思路：把镜像删掉，重新拉一个最新版本的再试。同一条命令，一个字没改，这次起来了。

> **结论**：同样的命令、同样的参数，换个镜像版本就能跑，说明命令本身没问题，问题出在镜像版本上。以后遇到"命令完全没写错但容器就是起不来"，先别怀疑自己，去看看镜像本身，`docker logs` 里那一串报错往往就是线索。

顺带说一个看着更舒服的写法。演示时 `docker ps` 后面加了个格式化参数，输出只留容器 ID、镜像名、端口号、状态和名字，比默认那一大排清爽得多——默认输出列多、字挤，格式化之后只剩你关心的那几列。这个格式串太长，谁也背不下来，所以不用掌握，知道有这回事、知道它是干什么的就行。

### 生命周期：停、启、重启、删除

现在这些容器，有的在跑，有的停着。停和启怎么弄？

停止容器用 `docker stop`，后面跟容器名：

```bash
docker stop mysql mysql2
```

两个可以连写，一次停两个。停完 `docker ps -a` 一看，三个容器全是停止状态。

想再把它跑起来，用 `docker start`，注意不是 `run`：

```bash
docker start mysql
```

`docker ps -a` 再看，状态变成 `Up`，后面跟着"5 秒前"，说明刚启动。

这两个命令最容易混：`run` 是创建并运行容器，`start` 只是把一个已经存在的、停掉的容器重新提起来。所以对一个已经存在的容器再 `run` 一次，只会得到名字冲突的报错——因为 `run` 又想去创建一遍。

那重启呢？猜一下也知道：`docker restart`。停、启、重启，三个动作凑齐，容器就能在停止和运行两种状态之间来回切换。

删除容器用 `docker rm`，后面跟容器名：

```bash
docker rm nginx mysql2
```

也能连写，一次删两个，回车照删。删完 `docker ps` 一看，只剩 `mysql` 了。

那 `mysql` 也删掉？删不了。它会告诉你无法删除这个容器，因为这个容器正在运行。所以运行中的容器不能直接删，除非你先把它停掉，或者强制删除：

```bash
docker rm -f mysql
```

`-f` 是 force，强制删除。删完 `docker ps -a`，一个容器都没有了。

到这儿容器的创建、运行、查看状态、停止、启动、重启、删除全都走了一遍。剩最后一个命令——进入容器内部，那是这堆命令里最"高级"的一个。

### 进入容器内部看一眼

最后一个命令是 `docker exec`，作用是进入容器内部，看看里面的情况。

```bash
docker exec -it nginx bash
```

`-it` 其实是两个参数合写。`-i` 对应 interactive，保持标准输入打开，让你敲的字能送进容器；`-t` 对应 tty，给这次会话分配一个伪终端。合在一起就是"给我一个终端交互的接口"。

为什么非得要终端？因为容器模拟的就是一台计算机，一台隔离环境里的计算机，它没有图形界面。你要跟这台"计算机"交互，唯一的办法就是用黑窗口，用终端敲命令。所以 `-it` 就是建立这样一个命令行终端。

后面的 `bash` 是要运行的程序。bash 就是命令行本身——我们现在跟虚拟机交互用的那个命令行终端，其实就可以理解成一个 bash。

回车之后，提示符变了：前面多出一串像 `8b55bc...54ef` 这样的字符。这就是容器 ID，它的出现意味着你已经进到容器里面了，而且打开了一个终端。

进来之后长什么样？敲个 `ls -l`：

```bash
ls -l
```

看到的结构是不是有点似曾相识？这就是 Linux 系统的根目录结构。前面说过，容器模拟了一台计算机，内部有一套虚拟出来的文件系统，CPU、内存这些资源也一并虚拟出来，是个完整的隔离环境。所以你进来一看，这里有一个完整的操作系统该有的目录。

> **易错点**：现在你看到的这些目录，不是宿主机上的文件系统，是容器内部的。提示符前面那串容器 ID 就是提醒——你已经换了一个"房间"。同样敲 `ls`，宿主机和容器里看到的东西不是一回事。

进来了能干什么？能干各种操作。比如你要能摸到 nginx 放页面的那个目录，就可以直接改里面的 html 文件，改完页面效果就变了——因为你改的是容器里真正在跑的那份文件。

看完了退出来，敲 `exit`：

```bash
exit
```

提示符回到宿主机，前面那串容器 ID 没了，你又站在外面了。

`docker exec` 属于比较高级的用法，通常排查问题、临时改配置才会用到，日常开发用不到几次。但你要知道有这么个命令，知道它能带你进容器内部，这就够了。

### 本讲提到的题目

**题干**：已经用 `docker run -d --name mysql -p 3307:3306 -e TZ=Asia/Shanghai -e MYSQL_ROOT_PASSWORD=123 mysql:8.0` 跑起了一个 MySQL 容器，现在要再跑一个，让它占用宿主机的 3306 端口，命令怎么写？

**答案**：

```bash
docker run -d --name mysql2 -p 3306:3306 \
  -e TZ=Asia/Shanghai \
  -e MYSQL_ROOT_PASSWORD=123 \
  mysql:8.0
```

**解析**：

- `--name` 必须换。容器名要求唯一，上一个已经叫 `mysql`，再叫 `mysql` 会直接报名字重复，所以换 `mysql2`。
- `-p` 左边可以写 3306，因为上一个容器占的是宿主机的 3307，3306 空着；如果宿主机的 3306 已经被别的程序占用，这条命令就会失败。
- `-p` 右边必须还是 3306，因为容器里跑的是 MySQL，它监听的端口就是 3306，容器内的端口不能乱改。
- 环境变量原样照抄，时区和 root 密码跟上一个容器配成一样即可。

命令执行完会返回一个新的容器 ID，用客户端连 `3306` 能正常 `show databases`，就说明两个 MySQL 已经同时跑在同一台机器上了——这件事在没有容器的年代，几乎没法轻松做到。

## 数据卷与项目部署：让数据不再随容器一起消失
> 对应块：BLK06 | 覆盖分集：P22-P25 | 块标题（分集名）：《Docker 数据卷与项目部署》

前面进容器里看的时候，里面是一整套完整的文件系统，该有的目录一个不少，跟一台独立的小机器没什么区别。这正是容器该有的样子：一个隔离的运行环境。可也正是这份隔离，让一件本来很普通的事变得麻烦——容器跑起来会不停产生数据，而这些数据，全都长在容器身上。

### 容器里的数据，为什么成了麻烦

#### 容器越跑越胖

容器一运行，就会产生各种各样的数据：日志是最常见的，还有临时文件、缓存。它们都落在容器的文件系统里，越积越多，容器的体积也就越来越大。

Nginx 还算个小个子，感受不明显。如果装的是 MYSQL 呢？MYSQL 里要建表、要写数据，几百 G 都是常事。几百 G 的东西全堆在容器内部，这个容器迟早会胖到出问题。

#### 升级一次，数据跟着没

第二个问题更要命。数据既然在容器里，那这个容器就动不得。

假设现在要升级 MYSQL：原来用 8.0，想换成 9.0。升级的路子是什么？下载新镜像、创建新容器，把旧容器销毁。旧容器一销毁，里面那些表呢？跟着一起没了。

> **结论**：容器里存着业务数据的时候，"重建容器"这个再正常不过的操作，就等于删库。

#### 改个配置还得进容器敲 vi

第三个问题，配置也在容器内部。

想改配置，先得进容器，再费半天劲去找配置文件在哪个位置，找到才能改。改的时候还没有图形界面可用——我们现在看到的这个图形界面是宿主机的，不是容器的，容器里没有它。所以只剩一条路：vi。改一个字符，在 vi 里折腾半天。

麻烦不麻烦？太麻烦了。

#### 静态资源塞不进去

第四个问题，在部署场景里最直接。

Nginx 内部有一个 html 目录，静态资源扔进去就能被代理。可这个目录在容器里，它在哪，你知道吗？不知道。访问页面只能看到结果，想改是改不了的，除非先摸到那个 html 目录。

如果只是一个 `index.html` 还好说；如果是一套复杂的前端系统，前端代码超级复杂，几百上千个文件，难道一个个手动往容器里写？这不合理。

> **结论**：这四件事看着不一样，根子是同一个——容器内的数据跟容器绑死在一起。所以解决方向也只有一个：让容器运行时产生的数据、运行时需要的配置，与容器解耦。容器只负责提供一个运行环境，数据归数据，配置归配置，都放到容器外面去。

### 数据卷：容器与宿主机之间的一座桥

怎么解耦？靠一个东西：数据卷。

> **定义**：数据卷是一个虚拟目录。它不是一个真实存在的磁盘分区，而是容器内目录与宿主机目录之间映射的一座桥梁。

拿 Nginx 举例。Nginx 容器里有两个目录最关键：`/etc/nginx/conf.d` 放配置文件，`/usr/share/nginx/html` 放静态页面。这两个目录现在都在容器里，想往里塞东西，只能进容器。往 html 里存前端代码，代码一多根本没法弄。

那就在外面创建两个数据卷，一个叫 `html`，一个叫 `config`。

#### 卷创建时，docker 在宿主机上做了什么

创建数据卷的那一刻，docker 服务会在宿主机文件系统的固定位置给你建目录。位置固定在 `/var/lib/docker/volumes/` 下面，建出来的目录跟卷同名，每个卷目录里还有一个 `_data` 子目录：`html` 卷对应 `/var/lib/docker/volumes/html/_data`，`config` 卷对应 `/var/lib/docker/volumes/config/_data`。

这是 docker 服务替我们建的，位置固定，不用我们操心。

```text
宿主机文件系统                                容器
/var/lib/docker/volumes/
├── html/_data/        ──── 挂载 ────►   /usr/share/nginx/html
└── config/_data/      ──── 挂载 ────►   /etc/nginx/conf.d
```

左边是 docker 在宿主机上维护的两个目录，右边是 Nginx 容器里的两个目录，中间的挂载关系一旦建立，两边就是同一份内容。

#### 映射建立之后

卷建好了，接着在创建 Nginx 容器时，把容器里的目录跟这两个卷关联起来——也就是把容器的目录挂载到数据卷上，形成一个映射。

映射一旦建立，事情就不一样了：我们改宿主机上对应的目录，容器里那个目录跟着改；容器里产生新数据，也会同步写回宿主机。

这一下解决了两个问题。

第一，数据不再绑在容器上。假设跑的不是 Nginx 而是 MYSQL，运行过程中产生几百 G 的表和数据，做了挂载之后，这些数据并没有存在容器里，而是通过映射落到了宿主机的目录上。这时候把 MYSQL 容器删了，宿主机目录受影响吗？不受，数据还在。将来升级版本、换一个新容器，只要新容器还挂同一个卷，照样能读到原来那些表。数据一点不丢。

第二，部署静态资源和改配置不用进容器了。往宿主机的 html 目录里扔静态资源，自动同步进容器，刷新页面就是最新内容；要改配置，改宿主机 config 目录里的文件，同样同步进去。

> **提示**：卷第一次挂到一个本来有内容的容器目录上时，docker 会把镜像里原有的内容复制进卷里。所以挂载完成后去宿主机的 `_data` 目录看，里面不是空的，而是 Nginx 自带的 `index.html`、`50x.html`——这跟手动装 Nginx 时看到的是同一套文件。

### 既然能直挂宿主机目录，为什么还要隔一层卷

讲到这儿一定有人要问：既然最后都是落到宿主机的目录上，直接把容器目录跟宿主机目录挂上不就行了？为什么还要先经过一个卷？

直接挂当然可以，宿主机的目录本来就能直接跟容器挂载。但卷多出来的这一层，换来的是解耦。

卷是中间桥梁。有了它，容器跟宿主机之间就松开了：容器需要知道宿主机目录在哪吗？不需要，它只要知道有一个卷存在。这个卷到底对应宿主机上哪个路径，是 docker 服务管的，跟容器没关系。

解耦带来的直接好处是可迁移。现在我们在 Linux 上部署 Nginx，挂的是 Linux 的宿主机目录；将来把这个容器迁到另一台机器上，那台机器可能是 Windows，文件系统完全不一样，路径可能是 C 盘底下某个位置。但没关系——容器对应的始终是那个卷，卷再去跟宿主机关联。所以随便迁，对容器没有任何影响，因为容器从来没有跟宿主机的某个具体路径绑死。

> **结论**：容器只认卷名，不认路径。路径那头的绑定关系，是 docker 服务的事。

### 数据卷的五条命令

数据卷的操作都挂在 `docker volume` 这个子命令下，常用的就五个。

| 子命令 | 作用 |
| :--- | :--- |
| `create` | 创建一个全新的数据卷 |
| `ls` | 查看所有数据卷 |
| `rm` | 删除指定数据卷 |
| `inspect` | 查看某个数据卷的详情 |
| `prune` | 清除所有未使用的数据卷（数据一起删掉） |

记不住参数没关系，`docker volume --help` 会把它们列出来。

> **提示**：按常规流程是先创建卷、再跟容器绑定，但实际没必要手动创建。创建容器时用 `-v` 指定一个还不存在的数据卷，docker 会在那一刻自动把它建出来。卷不存在就自动创建，这是默认行为。

### 动手：给 Nginx 换掉默认首页

先清场。本地已经有一个 Nginx 容器，把它删掉，保证接下来是干净的环境。

然后创建新容器，关键在 `-v` 这个参数：

```bash
docker run -d --name nginx -p 80:80 -v html:/usr/share/nginx/html nginx
```

前面 `-d`、`--name`、`-p` 都是老面孔。新出现的是 `-v`，专门用来做数据卷配置。它的写法分左右两半，中间一个冒号：冒号左边是数据卷的名字，冒号右边是容器内的目录。这里写的是 `html:/usr/share/nginx/html`——卷名 `html`，容器内目录 `/usr/share/nginx/html`，正是 Nginx 放静态页面的那个目录。

运行起来，`docker ps` 能看到容器已经启动。但先别急着下结论，得验证两件事：卷到底有没有建出来，容器到底有没有挂上。

先看卷：`docker volume ls`。会看到三个卷，其中两个没见过——先放一放，后面再说；剩下的那个就是 `html`。这说明创建容器的那一刻，卷被自动初始化了，我们并没有手动执行过 `docker volume create`。

再看挂载：`docker inspect nginx`，在输出里找 `Mounts` 这一段，它就是挂载信息。`Type` 是 `volume`，`Name` 是 `html`，说明挂的就是这个卷；`Source` 是卷在宿主机上的位置，`Destination` 是它对应到容器内的位置——`/usr/share/nginx/html`，跟我们刚才在 `-v` 里手写的完全一致。

`docker inspect` 的输出太长，也可以直接用 `docker volume inspect html`，同样能看到挂载位置，看起来清爽得多。

位置拿到了，`cd` 进去：`/var/lib/docker/volumes/html/_data`。里面是 `index.html` 和 `50x.html`——眼熟吧？之前手动装 Nginx 的时候，html 目录里就是这两个文件。这时候访问 192.168.x.x，看到的就是 "Welcome to nginx"。

现在换掉它。注意，我们操作的是宿主机：改的是数据卷挂载的那个目录下的 `index.html`，一个字都没碰容器。把页面内容改成 `welcome to heima`，保存，刷新页面——变了。没写中文，因为一会儿还得处理乱码，不如直接英文，省事。

这就证明数据卷挂载已经生效。从此以后，部署静态资源就是往宿主机的这个目录里扔文件，改页面就是改这个目录里的文件，不用再进容器。

### 那些凭空多出来的匿名卷

回头说 `docker volume ls` 里那两个没见过的卷。

所有卷都放在 `/var/lib/docker/volumes` 下。点进去看：结构一样，也有 `_data`，里面的东西是本机 MYSQL 的 data 目录里那一套——数据文件，还有表。

哪来的？回想一下，一开始我们运行过两个 MYSQL 容器，当时没有创建过任何数据卷。所以这两个卷是 MYSQL 容器自己建的：自己创建、自己挂载，存自己的数据。

> **定义**：这种卷叫匿名卷。名字是随机生成的，长得超级长，因为根本没人给它取过名字。

镜像为什么要这么设计？因为它自己清楚：数据存在容器里不安全，容器一没，数据就没了。所以在做镜像的时候就把数据目录挂到一个卷上，让数据落到宿主机。这样 MYSQL 容器删了，数据还在宿主机上；以后再起一个容器关联同一个卷，数据就回来了。

但平时我们不会用匿名卷。名字随机又长，你根本没法操作它。真要装 MYSQL，应该手动创建数据卷，或者干脆用本地目录挂载。匿名卷这个东西，知道它存在、知道它是镜像作者替你做的保护，就够了。

### 直接挂本地目录：更省事的做法

数据卷好用，但有个很现实的问题：目录太深。

`/var/lib/docker/volumes/xxx/_data`，每次要找都得 `inspect` 查一遍，记不住。官方推荐归推荐，它确实能解耦；可实际开发中很多人不爱用，更喜欢把宿主机目录直接跟容器目录挂载——因为方便，省事。

挂法跟数据卷几乎一模一样：`-v 本地目录:容器内目录`。也可以挂单个文件：`-v 本地文件:容器内文件`。一个挂目录，一个挂文件，两种都能理解。

两种方式摆在一起，差别其实很清楚：

| 对比项 | 数据卷挂载 | 本地目录挂载 |
| :--- | :--- | :--- |
| 写法 | `-v 卷名:容器目录` | `-v /绝对路径:容器目录` 或 `-v ./相对路径:容器目录` |
| 宿主机上的位置 | 固定在 `/var/lib/docker/volumes/<卷名>/_data` | 你自己指定的任意路径 |
| 可迁移性 | 好，容器只认卷名 | 差，容器跟具体路径绑死 |
| 日常操作 | 路径深，得先 inspect 查一遍 | 目录就在手边，方便 |
| 使用场合 | 官方推荐 | 实际开发中用得更多 |

既然语法一模一样，那怎么区分我挂的是数据卷还是本地目录？

#### 一条规则分清卷名和目录

> **易错点**：本地目录或文件，必须以 `/` 或 `./` 开头。以名字开头的，一律被识别为数据卷名，而不是本地路径。

```bash
-v mysql:/var/lib/mysql      # mysql 是数据卷名
-v ./mysql:/var/lib/mysql    # 当前目录下的 mysql 目录
```

上面那条挂的是卷，下面那条挂的是当前目录下名为 `mysql` 的目录。

那如果写成 `-v mysql/xxx:/var/lib/mysql` 呢？还是卷。判断只看什么开头，中间有没有斜杠不算数。只不过这个卷的名字很变态，叫 `mysql/xxx`，将来宿主机上就会建出一个名字长这样的目录，看着很诡异。

> **易错点**：区分靠的是开头，不是中间有没有 `/`。写成 `mysql/xxx` 不会变成子目录，只会变成一个名字里带斜杠的卷。

#### 三个挂载点装好一个 MYSQL

这次拿 MYSQL 练手。MYSQL 镜像自带匿名卷，名字超级长，没法操作，所以这次用本地目录挂。要挂三个位置。

| 容器内目录 | 作用 | 挂载的本地目录 |
| :--- | :--- | :--- |
| `/var/lib/mysql` | 数据目录 | `/root/mysql/data` |
| `/docker-entrypoint-initdb.d` | 初始化脚本目录 | `/root/mysql/init` |
| `/etc/mysql/conf.d` | 配置文件目录 | `/root/mysql/config` |

第一个是数据目录。容器默认就往这儿写数据。把本地 `data` 挂上去，MYSQL 产生的数据就落到本地，容器删了也不丢。

第二个可以理解成容器的初始化目录。容器创建好以后，默认会执行这个目录里的脚本。把本地 `init` 挂上去，里面提前放好 SQL 脚本，容器一创建就会执行——效果就是数据库自动初始化。

这个目录为什么值得专门挂？我们之前用 docker 装的数据库，建好以后里面是空的，一张表都没有。可项目部署一定要有初始化的表。把建表 SQL 放进这个目录，容器一启动，表就齐活了。

> **提示**：`/docker-entrypoint-initdb.d` 里的脚本只在数据目录为空、容器第一次初始化的时候执行一次。数据目录里已经有数据了，再启动容器不会重复跑一遍，所以不用担心重启一次表被重建一遍。反过来说，想让初始化脚本重新生效，得先把挂出去的 `data` 目录清空。

第三个放 MYSQL 的配置文件。把本地 `config` 挂上去，配置写进这个目录就能改 MYSQL 的配置了。

课件资料里已经准备好这三个目录，在 `06-其他软件` 的 `mysql` 下：`data` 是空的，数据让 MYSQL 自己跑出来；`init` 里放了一个 SQL 脚本，建一个叫 `robot` 的数据库，再建若干张表，就是昨天那个 robot AI 项目要用的脚本；`config` 里是配置，主要把编码统一成 UTF-8，不然将来会乱码——本机装的 MYSQL 里那个 `my.ini` 配的也是这个效果。

把这三个目录上传到 `/root/mysql` 下，然后执行：

```bash
docker run -d \
  --name mysql \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=123456 \
  -v /root/mysql/data:/var/lib/mysql \
  -v /root/mysql/init:/docker-entrypoint-initdb.d \
  -v /root/mysql/config:/etc/mysql/conf.d \
  mysql
```

`-d`、`--name`、`-p` 不用多说，端口这次用 3306；`-e` 是环境变量，设置 root 密码。关键是三个 `-v`：冒号前半部分全部以 `/` 开头，所以挂的是本地目录，分别是 `data`、`init`、`config`，正好对应刚上传的那三个；后半部分是容器内的三个目录，一一对上。最后一个词是镜像名。

跑起来之后验证三件事。

`docker ps` 看到容器处于 up 状态；回头看本地的 `data` 目录——上传的时候还是空的，现在有内容了，说明数据落到了宿主机上；再用客户端连 3306，里面能看到 `robot` 库，表也全都在，说明 `init` 里的脚本被自动执行了。

这一套就是项目部署的标准动作：初始化 SQL 放好、挂到初始化目录，容器一启动，表就有了。

### 部署到底难在哪

到这儿，用 docker 部署应用的常见命令和概念都过了一遍。那现在让你部署一个应用，会不会？

很多人的答案是：不会。为什么不会？因为命令不会敲。可这个命令需要你敲吗？不需要，它是复制粘贴的。

把刚才装 MYSQL 的过程拆开，一共三步：第一步，把 mysql 那一堆文件一股脑上传到 `/root/mysql`；第二步，把命令复制一下、粘贴到终端；第三步，敲回车。

这三步哪一步不会？上传会，复制粘贴会，敲回车也会。

到了公司里场景变了怎么办？库名不一样——改库名；密码不一样——改密码；初始化脚本不一样——改脚本。除了这些，还有什么要改的？没有了。

再往上一层：会用 AI 吗？直接跟它说"我要用 docker 部署 MYSQL，帮我写个命令"，它给你的是能上生产的那种：带持久化、带时区、带字符集，密码、默认数据库名、默认用户名和密码（生产环境不让用 root）、端口、卷挂载，一应俱全。它给的版本没有初始化脚本，那就补一句"给我一个带初始化脚本的命令"，脚本版也出来了。复制过去就能用。

> **结论**：命令本身不是门槛，AI 时代连背都不用背。真正要掌握的是三件事——有哪些东西需要挂出来、分别挂到容器的哪个位置、每个位置管什么用。数据目录、初始化脚本目录、配置目录，这三样清楚了，命令让 AI 写，部署就完成了。

> **承前启后**：上一节讲完「数据卷与项目部署：让数据不再随容器一起消失」，下一节接着讲「从自己造镜像到一键起全套：Dockerfile 与 Docker Compose」。

## 从自己造镜像到一键起全套：Dockerfile 与 Docker Compose
> 对应块：BLK07 | 覆盖分集：P26-P28 | 块标题（分集名）：《自定义镜像与 Docker Compose 语法》

理论上讲，Docker 装好之后，你已经能部署任何一个应用了——不管这东西你学没学过，命令一敲，它自己会去把镜像拉下来，然后跑起来。

但这里有个前提，我想先问一句：你去下这个镜像，是不是因为**别人已经给你准备好了**？

那如果我要部署的不是别人写好的应用，而是我自己写的呢？

前几天我们写的那个 AI partner，就是自己一行一行敲出来的。这么多代码，若干文件，一堆依赖，你上哪儿去找一个现成的镜像？没有任何人给你提供。那只能怎么办——**自己先构建一个镜像**。

这就是接下来要干的事。而自定义镜像这件事，第一步不是写命令，是先弄明白一个镜像到底长什么样：你要是连它里面该装什么都说不清，构建出来的东西肯定跑不起来。

### 一个 Python 应用要跑起来，需要哪些东西

前面我们已经说过，镜像之所以能让我们一键部署，是因为它把应用需要的东西全打包进去了：系统函数库、环境配置、依赖，一样不少。当时我们还钻到容器里看过——`docker exec -it nginx sh` 进去，`ls -l` 一敲，里面就是一个和 Linux 一样的文件系统，满屏的 `lib` 就是 nginx 跑起来依赖的那些函数库。

> **提示**：那个文件系统看着完整，其实不是完整的操作系统。它只装了 nginx 需要的那部分函数库，nginx 用不到的这里就没有——体积就是这么压下来的。

既然镜像等于"应用本身 + 它需要的一切"，那我要构建一个 Python 应用的镜像，就得先回答一个更具体的问题：一个 Python 应用要跑起来，到底需要什么？

顺着部署的思路捋一遍就出来了：

1. 一台 Linux 服务器；
2. 在上面装 Python；
3. 装 UV；
4. 用 UV 把项目依赖装上；
5. 把项目源码拷进去；
6. 写一个启动脚本，`uv run ...` 把服务拉起来。

这六样备齐，应用就能自己跑起来了，一个 Python 应用的全部家当也就这些。所以构建镜像的流程，无非是把这六件事按顺序在一层一层的环境里做一遍。

### 镜像是摞出来的

第一步永远是准备一个能跑的 Linux 环境，比如 CentOS 7，里面带着系统函数库、环境变量、配置文件。这一层就是整个镜像的地基。

地基有了，在上面装 Python、装 UV；装完再拷贝源码，然后执行 UV 命令装依赖；最后写启动脚本。到这儿，一个 Python 应用就打包好了，一个镜像也就算构建完了。

把这一串操作摊开看，它的结构是这样的：

```text
基础镜像 base image（Linux 系统函数库 / 环境变量 / 配置文件）
        │
        ├── 安装 Python 与 UV          → 新的一层
        │
        ├── 拷贝项目源码               → 新的一层
        │
        ├── uv 装项目依赖              → 新的一层
        │
        └── ENTRYPOINT 启动脚本        → 入口层
```

读图：底下那一层是别人做好的底子，往上每做一步改动就多出一层，最上面那层是镜像启动时的入口。

这里我要强调一个词——**层**。一个镜像不是一坨东西，它是很多层摞起来的。

#### 基础镜像层

最底下那层叫基础镜像层，里面就是基础的系统函数库、环境变量、配置文件这些东西。

像 CentOS 这样的镜像，Docker Hub 上就能直接下载。这种"专门用来被别的镜像当作起点"的镜像，我们把它叫 **base image，基础镜像**。

#### 写时复制

那"新的一层"到底是什么意思？为什么每动一下就会多一层？这背后用了一个技术，叫 **Copy on Write**，写时复制。

道理不难：我们下载下来一个基础镜像，现在要在这上面装 UV。如果直接在原来那层上动手，一定会改掉里面的东西，那一层就被破坏了——而这一层可能全世界都在共用，你不能动它。

所以它不在这层上改，而是直接新建一层。新层里看起来有 `etc` 目录、有 `lib` 目录，其实里面是空的，只是用类似软链接的方式指到下面那一层去：你在这个层里看，好像什么都有，实际上没有，只是链过去了。

等装 Python、装 UV 的过程中真需要改某个文件了，才把这个文件从下层复制上来，在这一层里改。

```text
第 2 层（新层）
  /etc   ──链接──▶  第 1 层的 /etc      本层没有实体内容，只是指过去
  /lib   ──链接──▶  第 1 层的 /lib
  /lib/xxx.so        真要改这个文件时，才把它复制到第 2 层再改
```

读图：新层里只有"被真正改过的东西"才占空间，没碰过的一律只是链接；两层合起来看，就是一套完整的系统。

> **结论**：每次操作只要修改了文件，就一定会产生新的一层，这就是写时复制；好处是镜像体积能压住。

#### 入口层

最后那层启动脚本，有个专门的名字：**entrypoint，入口**。

镜像构建好了，将来一启动，是不是得有个入口告诉它先干什么？这个启动脚本就是入口，也就是镜像启动时执行的命令。

到这里一个完整镜像就齐了：基础镜像层、中间若干层、再加一个入口层。

### 分层是为了什么

有人肯定会问：为什么要分层？我不分层，就在原来那一层上整一堆东西，不也能用吗？

能用。但这样整会带来一个问题——**层与层之间不可复用**。

你想想这个场景：今天我打包一个 Python 应用，得构建第一层、第二层，再拷源码；明天你要打包另一个 Python 应用，前两层是不是还得再执行一遍、再构建一遍？可既然都是 Python 应用，前两层本来就是通用的，重来一遍纯属多余。

分层之后就不一样了：构建的时候发现第一层别人已经构建过了，直接复用；第二层也有人构建过了，继续复用；那我只需要从第三层开始构建。

这个好处在下载镜像的时候最直观。还记得我们最开始装 MySQL 时的那个 `docker pull` 吗？它不是一个完整镜像一口气下下来的，而是**一层一层下载**的。下载时如果发现前两层本地已经有了，直接跳过，只下后面几层——所以镜像拉得也更快。

> **结论**：镜像分层的根本目的就是复用，构建时复用已有的层，拉取时复用本地的层。

### 我不亲手造层，我只描述结构

结构讲清了，那是不是就让你照着这个图一层一层自己去整？

不会的，你也整不了。别的不说，就那个写时复制，让你自己去做，你做得出来吗？做不出来。

真正做镜像的时候，不是你自己动手，而是**你把每一层要干什么描述出来**，然后交给 Docker 去干。Docker 装完之后本身就是一个后台服务，我们敲的所有命令最终都是它在执行。所以我们的活儿是：用某种方式描述镜像的结构，描述每一层做什么，Docker 服务按你描述的结构把镜像构建出来。

这么一来，问题就换了：不再是"我怎么亲手构建镜像"，而是"**我怎么把镜像结构描述清楚**"。

描述用的语法叫 **Dockerfile**。它就是一个文件，把镜像每一层要做的事用固定的语法写出来，交给 Docker 去执行——记录这些层结构的文件，就叫 Dockerfile。

### Dockerfile 里常用的几条指令

Dockerfile 的语法很多很多，谁也学不完。常用的其实就下面这么几条，够用了。

`FROM` 用来指定基础镜像。你要构建一个应用，总得有个底子，比如一个 CentOS 系统，那就写 `FROM centos7`。对应到刚才的结构图，它管的就是第一层——基础镜像层从哪儿来。

`ENV` 用来设置环境变量。

`COPY` 把本地文件拷贝到镜像里的指定目录。中间构建的时候不是有一步要拷自己的源码吗？那就是靠它。它有两个参数：第一个是源码的位置，第二个是你想放到镜像里的哪个位置。基础镜像模拟出了一整套文件系统，所以你必须说清楚拷到哪个目录去，比如拷到 `/tmp`，那就写成 `COPY 你的源码 /tmp`。

> **提示**：这一步和写时复制是配合的。当你要往 `/tmp` 里写东西的那一刻，它才把 `/tmp` 这个目录给你整过来，然后把源码放进去，加在这一层里——这正是写时复制的意思。

`RUN` 用来执行 Linux 命令。源码拷进去了，还得用 UV 装项目依赖吧？装依赖就得跑命令，跑命令就用 `RUN`。比如：

```bash
RUN tar -xvf uv.tar.gz && pip install uv && uv sync
```

这三条命令用 `&&` 串起来，意思是依次执行：先解压，解压完装 UV，UV 装好了再去装项目依赖。到这一步，运行环境就准备齐了。

`EXPOSE` 指定容器运行时的端口。说句实话，它**并没有实际意义**，它是给镜像的使用者看的——告诉别人"我这个镜像内部将来要占的是 8000 端口"。别人看到这一行，写 `docker run -p` 的时候就知道了：冒号后面得跟 8000，不能写 8001；冒号前面写什么随你。

`ENTRYPOINT` 就是入口，指向那个启动脚本。比如写 `ENTRYPOINT uv run xxx`，意思就是用 UV 把这个应用跑起来。

### 一份真实项目里的 Dockerfile

语法认识完了，看一个真的。注意它的第一行 `FROM`，它可不是从操作系统开始写的：

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

COPY pyproject.toml ./
RUN uv sync

COPY ./src ./src

EXPOSE 8000

ENTRYPOINT ["uv", "run", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

为什么不是从 CentOS 开始？从操作系统开始当然是一种场景，但接着你不是还得装 Python 吗？而 Python 这种环境实在太常见了，常见到有人干脆把"系统 + Python"这两层提前合并、打成了一个基础镜像，就是 `python:3.12-slim`。

所以 `FROM` 不一定非得从最底层开始，完全可以从别人的镜像开始。我 `FROM` 这个 3.12，等于前两层它都替我准备好了，我直接从"拷源码"这一层往上干，省掉了 Python 环境的安装。

再往下看，`WORKDIR` 是个前面没讲过的新指令，它指定的是运行的时候在哪个目录——这里是镜像内的 `/app` 目录。这个目录如果没有，它会自动创建。

`COPY --from=...` 这一行看着像拷贝，但拷的不是本地文件，是从网上拿。`--from` 后面跟的是一个镜像地址，UV 本来就是从网上下载的，本地根本不会有一个现成的 UV 给它拷，所以走的是这种方式：把 UV 拷到镜像里的 `/usr/local/bin/uv`。

接着 `COPY pyproject.toml ./`，拷贝的是 `pyproject.toml`——就是记录项目依赖的那个文件。依赖清单进去了，才有下一步 `RUN uv sync`：有了依赖文件，它才知道你需要哪些依赖，才会照着它去装。

依赖装完，再把 `./src` 拷进去，然后 `EXPOSE 8000` 声明端口，最后 `ENTRYPOINT` 启动。

> **提示**：先拷 `pyproject.toml` 再 `uv sync`、最后才拷源码，这个顺序不是随便排的——按前面分层的道理，依赖这一层只跟依赖清单有关，源码怎么改都动不到它，这一层就能一直复用。当然你反过来先拷源码再拷依赖清单也能跑，只是白搭了复用的好处。

`ENTRYPOINT` 这里因为命令太长，用了一个数组，把每个部分一个一个拼起来：

```text
["uv", "run", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`uv run` 是运行，后面跟 `uvicorn src.main:app`，再跟 host 和 port。这套东西眼熟吧？跟我们在 `main` 里写 `uvicorn.run(app, host=..., port=...)` 是一回事——只不过那边是用代码写的，这边是用命令写的。

### 让 Docker 把描述变成镜像

Dockerfile 写好了，它只是一份描述结构的东西，得让 Docker 照着它构建。命令是 `docker build`：

```bash
docker build -t backend .
```

`-t` 是 tag 的意思，就是给镜像起名字。名字得是 `仓库名:标签` 的格式，标签不写就默认 `latest`。所以 `-t backend` 等于 `backend:latest`。

光有名字还不够。你只是告诉它"给我构建个叫 backend 的镜像"，可**它怎么知道按什么结构构建？Dockerfile 在哪儿？** 它不知道。所以命令最后那个参数是 Dockerfile 的位置，而且这个位置是**目录**。

`.` 就是当前目录，意思是"在当前目录构建"。所以这条命令只能在 Dockerfile 所在的那个目录里运行，换个目录就对不上了。

在课前代码的 robot 项目里，后端目录其实早就放好了一份 Dockerfile，我们直接进去执行。构建一开始就能看到它在下载东西——因为第一行是 `FROM python:3.12-slim`，它得先把基础镜像拉下来；拉完再执行 `COPY --from=...` 去下 UV。

输出里那一行 `FROM` 对应的是 stage 0，也就是第一阶段、第一层；后面的每一段对应新的一层。这一路下载慢得让人怀疑人生，一分钟才下了一半——因为它连的是 `docker.io`，国外站点。这种地址应该换成国内的加速地址，速度立刻就不一样了。

构建完成，`docker images` 一看，`backend` 和 `latest` 都在，镜像有了。

### 镜像起来了，容器却没连上数据库

有了镜像就运行它：

```bash
docker run -d --name backend -p 8000:8000 backend
```

`-d` 后台运行，`--name` 给容器起名，`-p` 做端口映射——宿主机端口映射到容器内的 8000。镜像名写 `backend`，不写版本号默认就是 `latest`。

命令敲下去，容器起来了。可是 `docker ps` 里从头翻到尾，压根没看见它。

> **易错点**：容器"启动成功"不等于"跑起来了"。进程可能刚起来就挂了，`docker ps` 只列还活着的容器。

那就看日志：

```bash
docker logs -f backend
```

日志里写着启动失败，原因是连不上 `mysql`——它连的是 `localhost`。

这里就得追问一句：**用 `localhost` 为什么不对？** 我们三个容器不都跑在同一台虚拟机上吗？

不对。容器是隔离环境。它们三个虽然跑在同一台虚拟机、看起来像在一起，但彼此是隔离的，谁也看不见谁，各自还有各自的网络地址。所以在 backend 容器里访问 `localhost`，找的是**它自己容器内部**的 MySQL——那个容器里当然没有 MySQL，所以连不上。

这个坑先放这儿。镜像有没有构建起来？构建起来了。容器有没有跑起来？跑起来了，只是连不上数据库。

### 容器一多，命令就敲不过来了

刚才这一趟走下来暴露了两件事。

第一件，网络麻烦。三个容器一个连一个，还得用容器互联一个个把网络接起来。第二件，顺序麻烦——得先部署 MySQL，再部署 Nginx，再部署后端，一个都不能少。

一个大型项目往往有数十个甚至上百个不同的服务。Docker 部署一个服务已经够简单了，可一百个服务让你一个一个来，你还嫌不嫌麻烦？跑一个还行，跑一百个就真要命了。

所以我们需要 **Docker Compose**。它的 logo 是只大章鱼，一只手上还抱着个箱子——那箱子就是容器。以前是我们手动一个一个部署容器，现在换成：**用一个文件定义一组相关联的容器**，把想跑的全写进去，然后把这个文件扔给 Docker Compose，它一键帮你全部部署好。

省事的地方还不止一键——它在部署过程中会顺带把网络互联也做掉，刚才那种复杂的互联你根本不用管了。这么一来，刚才那种一个一个 `docker run` 的部署方式，基本也就被淘汰了。

所以要用 Compose 部署项目，关键就一件事：**把那个文件写好**。

### 一个文件就是一个项目，一个容器就是一个服务

先认清两个称呼。

整个 Compose 文件，叫一个**项目（project）**。为什么叫项目？还是拿 robot 举例：robot 本身就是一个项目，它底层依赖数据库，前端要用 Nginx 部署，三个东西合在一起才是一个完整项目。所以一个 Compose 文件本质上是部署一个项目的。

项目里的每一个容器，叫一个**服务（service）**。robot 里要起 Nginx 服务、MySQL 服务，最后还要起我们那个 Python 应用的服务，一共三个。

叫法不重要，重要的是格式：文件里从 `services` 开始，底下依次列容器 A、容器 B、容器 C。

### 这种格式叫 YAML

Compose 文件用的格式我们之前没接触过，叫 **YAML**，文件后缀一般是 `.yml` 或 `.yaml`。

它的写法很简单：一个键、一个冒号、一个值。

```yaml
key: value
```

简单的内容一行写完就够。复杂一点的就往下嵌套：`k1` 冒号下面写 `k2`，`k2` 下面再写 `k3`，最后才是值；`k2` 下面还可以并列好几个 `k4`。这时候某个深层配置真正的键，是把整条路径拼起来——`k1` 拼 `k2` 再拼 `k3` 再拼 `k4`。

```text
k1:
  k2:
    k3: value
    k4: value
```

读图：层级不是靠括号，是靠缩进——**两个空格一级**，`k3` 和 `k4` 同属 `k2` 底下的并列项。缩进错了，层级就全乱了。

### 把 docker run 翻译成 service

懂了格式，接下来的问题是：怎么在这个文件里描述一个容器？

以前描述容器用的是 `docker run`：容器名、端口、环境变量、网络、后台运行，一堆参数。现在不用 `run` 了，换成 Compose 的语法——**其实就是换了个写法，参数还是那批参数**。

拿之前部署 MySQL 的那条 `docker run` 跟 Compose 里的写法对一下：

| `docker run` 里的写法 | Compose 里的写法 | 作用 |
| :--- | :--- | :--- |
| `--name mysql` | `container_name: mysql` | 容器名 |
| `-p 3306:3306` | `ports:` 下写 `- "3306:3306"` | 宿主机端口映射到容器端口 |
| `-e KEY=VALUE` | `environment:` 下写 `KEY: VALUE` | 环境变量 |
| `-v 本地:容器` | `volumes:` 下写 `- "本地:容器"` | 数据卷挂载 |
| `--network xxx` | `networks:` 下写 `xxx` | 加入网络 |

差别只是符号：`-p` 变成 `ports`，`-e` 变成 `environment`，`=` 变成 `:`。效果一模一样——`ports` 冒号左边是宿主机端口，右边是容器内端口；`volumes` 冒号左边是本地目录，右边是容器内目录。

写成文件，一个 MySQL 服务大致是这个样子：

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: mysql
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: 你的密码
      MYSQL_DATABASE: robot
    volumes:
      - mysql-data:/var/lib/mysql
    networks:
      - app-net
```

`ports`、`environment`、`volumes`、`networks` 底下都有缩进，说明这些配置全都属于 `mysql` 这个服务；每个键底下要配几项，就并列写几行——比如数据卷有三个挂载点，`volumes` 底下就并列三条。

反过来验一验自己看懂没有：现在让你配一个 Nginx 的服务，怎么配？

服务名自定义，就叫 `nginx`；镜像也用 `nginx`，想指定版本就加个标签；容器名随便起；端口写 `- "80:80"`；环境变量没有，那一整段可以不写；数据卷要挂就挂一个。

> **提示**：能照着一个 MySQL 的服务改出一个 Nginx 的，就说明这套语法你看懂了。对大家的要求就是**看得懂 Compose 文件**，能照着改一改、配一配，那就更好。

### 一个完整项目的三个服务

真的项目文件长这样：

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: chatbot-mysql
    environment:
      MYSQL_ROOT_PASSWORD: 你的密码
      MYSQL_DATABASE: robot
    ports:
      - "3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build: ./backend
    container_name: chatbot-backend
    ports:
      - "8000:8000"
    depends_on:
      mysql:
        condition: service_healthy

  frontend:
    image: nginx
    container_name: chatbot-frontend
    ports:
      - "80:80"
    volumes:
      - ./frontend/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./frontend/public:/usr/share/nginx/html
    depends_on:
      - backend

volumes:
  mysql-data:
```

`services` 底下三个服务：`mysql` 是后台数据库，`backend` 是我们的后端，`frontend` 是用 Nginx 部署的前端。

#### 数据库服务

镜像用 `mysql:8.0`。为什么是 8.0？因为前面演示数据卷的时候一直用的就是 8，这里接着沿用。

容器名叫 `chatbot-mysql`，叫 `mysql` 也行，不影响。文件里本来还有一行以前没见过的 `restart: unless-stopped`——自动重启，除非你主动把它停掉；有了它，虚拟机重启之后容器会自己起来。**这一行我们不加了**，知道有这么个东西就行。

环境变量配两个：一个是密码，密码随意；一个是默认数据库名 `robot`。时区这里没配，也不打紧。

端口就是 `3306:3306`。数据卷这里只挂了一个，而且注意——它用的是**数据卷**，不是本地目录。

最后多出来的 `healthcheck` 是健康检查，相当于隔一会儿就去连一下 MySQL，看能不能连通。不加它也不影响；加了它，后端才能等数据库"健康"之后再启动。

#### 前端服务

镜像用 `nginx`，容器名 `chatbot-frontend`，同样不需要自动重启。

端口 `80:80`。数据卷挂了两个，都写在 `volumes` 底下、都有缩进，所以两个都属于这个服务：

- 把 `frontend/nginx.conf` 挂到容器里 Nginx 的配置目录。Compose 文件就在当前目录，它找的就是当前目录下的 `frontend`，那里有 Nginx 配置；
- 把 `frontend/public` 挂到容器内的 HTML 目录。`public` 里放的是静态资源，正好给 Nginx 当站点根目录。

配置那一行末尾跟了个 `ro`，代表**只读**——容器只能读这些文件，不能改。

最后一行 `depends_on` 写的是 `backend`，意思是这个前端依赖于后端。加上之后的效果：启动这一组容器时，先起后端，后端启动成功了才起前端。

#### 后端服务

到这里数据库有了、前端有了，就差后端。

前端和数据库都是**基于现成镜像**部署的，后端不是——后端没有镜像，它需要我们自己的那个 Dockerfile 现构建。所以它写的不是 `image`，而是 `build`：

```yaml
backend:
  build: ./backend
```

这个 `build` 就等于 `docker build`。也就是说，用 Compose 部署项目时，**镜像都不用手动构建了**：你只要告诉它 Dockerfile 在哪（当前目录下的 `backend` 目录），它自己会去执行构建，构建完自动创建容器、配置端口、配置环境，再把依赖项配上——依赖 MySQL，就写 `depends_on`。

> **提示**：这也顺带把前面那个 `localhost` 的坑填了。Compose 启动时会自动建一个网络，服务之间可以直接用服务名互相访问，后端连数据库写 `mysql` 就行，不用再管容器互联。

### 一键启动时，它按什么顺序干活

把这些依赖串起来，一条 `docker compose up` 的流程是这样：

```text
docker compose up
      │
      ├──▶ mysql      最先启动，等健康检查通过
      │
      ├──▶ backend    等 mysql 健康后才开始
      │                先自动 build 镜像，再创建容器、做端口映射
      │
      └──▶ frontend   等 backend 启动成功后才开始
```

读图：整条链是按依赖关系推着走的，前一个没就绪，后一个不会动。

所以将来只要按这份文件配好，一启动，它先跑 MySQL；MySQL 健康了，再来执行 backend——执行 backend 的时候会先自动构建镜像，构建完自动创建容器、完成端口映射；backend 起来了，最后自动执行 frontend。一次性把所有的都给你准备好。

## 一条命令完成部署：Docker Compose 与模型环境准备
> 对应块：BLK08 | 覆盖分集：P29-P31 | 块标题（分集名）：《Docker Compose 一键部署与云端环境准备》

docker compose 文件写完了，语法也弄明白了，接下来才是真正见真章的地方：这份文件怎么才能跑起来。

部署这件事，在企业里最后落到人手上的往往只有一行命令；但这一行命令背后，得先把项目、配置、容器编排都摆到位。这一篇就沿着这条线走：先看 compose 的命令怎么用、把项目真正部署一遍，再补齐项目要用的模型账号，最后在本地装一套 Ollama 作为兜底。

### 命令先摆上桌

编写好 docker compose 文件以后，要部署项目，就得用 `docker compose` 命令。它的用法是 `docker compose` 后面跟一些选项，再跟指令；选项一般情况下可以不加，只加指令就够了。

| 指令 | 作用 |
| :--- | :--- |
| `up` | 创建并启动所有的 service 容器 |
| `down` | 停止并移除所有的容器 |
| `ps` | 查看已启动的容器 |
| `logs` | 查看日志 |
| `stop` | 停止 |
| `start` | 启动 |
| `restart` | 重启 |

看完这几个指令，大概会有种熟悉感：`up`、`stop`、`start`、`restart`，跟 `docker run`、`docker stop` 那一套太像了。像归像，前缀是 `docker compose`，两者非常接近，区别在于操作对象从单个容器变成了一组 service。

> **易错点**：`stop` 只是把容器停下来，容器还在；`down` 是停止并移除，连 up 时自动创建的网络一起清掉。临时停一下用 `stop`，彻底收摊用 `down`。

### 清场、上传、改配置

真正动手之前，先把环境清干净。之前是手动在 backend 里把服务跑起来的，现在换成 compose，旧容器留着会冲突，所以把现有的容器全部 `docker rm -f` 删掉，MySQL、Nginx 那一批一起清。清完 `docker ps -a` 一看，干干净净。

项目整个传到 `/usr/local` 下。其实传到哪里都无所谓，说了放 `/usr/local`，就放这儿，传完 `/usr/local` 下多了一个 `robot` 目录。

配置要换一份。之前手工启动 backend 时，读的是项目里层那份配置；现在走 compose，得用外层那份 prod 配置（`.env.prod`）。这份配置里真正要改的只有一样：API Key，换成自己的。

数据库那几项不用动：主机名 `mysql`、端口 `3306`、用户名 `root`、密码 `mysql123`。密码到底是几，取决于 compose 文件里的设置；MySQL 容器是这次重新创建的，配什么密码都行，但两边必须保持一致。所以最省事的做法就是密码不动，只改 API Key。

中间还有个小插曲：打开 compose 文件一看，感觉不太对劲，这份不是原来那份，是之前让 Claude Code 帮忙重写的。想了想还是换回原来那份，不然还得重新调试一遍。这也说明一件事：compose 文件可以让 AI 写，但写出来的东西你得看得懂、改得动。

运行之前有一条死规定：必须 `cd` 到 compose 文件所在的目录，`docker compose` 才能找到它。所以先进 `/usr/local/robot`，确认目录里有那份 compose 文件，再执行命令。

> **提示**：这一阶段最容易出岔子的就是两处对齐——执行命令时人在不在 compose 文件所在的目录，数据库密码在 compose 文件和 `.env.prod` 里是不是同一个值。

### 一条 up -d 之后发生了什么

命令是 `docker compose up -d`。`up` 是一键启动配置文件里的所有容器——MySQL、backend、frontend；`-d` 是后台运行，加了它就不用守着终端，它自己去做。

启动顺序不是随便排的，而是由依赖关系定死的：

```text
docker compose up -d
        |
        v
  自动创建 network + volume
        |
        v
  [mysql] 容器创建，等待健康检查通过
        |
        v
  [backend] 自动构建镜像 -> 自动创建容器
        |
        v
  [frontend] 创建并启动
        |
        v
  浏览器访问前端 -> 注册 / 登录 / 新建对话
```

MySQL 先建，健康了 backend 才被放行；backend 一运行就自动构建镜像、自动创建容器；最后才轮到 frontend。顺序卡在这里是有道理的：backend 一起来就要连数据库，MySQL 没就绪，它根本连不上。

终端里一行行往下刷，那是在自动构建镜像，六步走完，紧接着自动创建了一个 network、一个 volume，再把三个容器创建出来。用 `docker compose ps` 一看，backend、frontend、MySQL 全部启动成功。

打开浏览器访问前端，注册一个账号（密码有长度要求，试的短密码被挡了回来，加长之后就通过了），登录，新建一个对话，发一句“嗨”，正常回复。

这才叫一键部署：项目往上一扔，一条 `docker compose up -d`，前端、后端、数据库全部署好。企业里的部署就是这个样子。

一键部署麻烦的地方在前期写这份 compose 文件，那份文件写起来费劲——当然也可以让 AI 写。但只要写好了，人去执行就极其简单，一行命令搞定。

> **结论**：一键部署的成本不在执行，而在那份 compose 文件。文件写对一次，后面每一次部署都只剩一行命令。

### down 之后不留痕迹

不想部署了，想把它停掉，就 `docker compose down`。

这个 down 很厉害：up 的时候自动创建了网络、自动创建了容器；down 一执行，容器删掉，网络也删掉。`docker ps -a` 一看，没有容器；`docker network ls` 一看，刚才那个网络也不在了，全部干干净净。

运行的时候一键运行，清除的时候一键清除，不留任何痕迹。你说舒服不舒服？非常舒服。将来部署项目就是这么部署。

那这份 compose 文件以后要不要我们写？不需要，这是运维干的事，AI 也能代劳。但你自己要部署，就得会执行：`up` 启动、`down` 停止，这两个最常用；再加 `ps` 查看、`logs` 看日志、`stop` 停单个容器，基本就够用了。

### 模型是另一件要提前备好的东西

项目里的准备工作，主要就是模型这一块：项目会用到模型，所以要提前把模型准备好。

第一个要用的模型是 DeepSeek：注册一个账号，充几块钱，用一用。不想用这个也行，充了别家的照样能用，不是不行；只是我讲的时候会用 DeepSeek 来讲。DeepSeek 怎么注册以前讲过，这里就跳过。

问题在于，DeepSeek 只有一种模型——纯文本对话的大语言模型。想要实现一些更高级的功能，它就没有了。这类有特殊能力的模型，阿里云上比较多，所以还需要注册一个阿里云百炼的账号。

### 阿里云百炼：从登录到开通

注册比想象中省事：访问百炼的地址，不用点注册，直接点登录就可以。它支持手机号，也支持支付宝、淘宝账号登录——大家都有淘宝、有支付宝，在这里输入淘宝账号和密码也能进，它是联动的、单点登录的，支付宝、淘宝甚至闲鱼，随便什么账号都可以。想重新注册一个新账号也没问题。

首次注册要做实名认证：用支付宝扫一个二维码，会进入支付宝里，用人脸识别验证，通过之后就可以使用了。这个躲不掉——访问大模型必须实名，是国家安全层面的要求。

登录百炼平台的时候，第一次会弹窗问你是否同意开通百炼服务，选择确认开通；如果还没做实名认证，它会弹窗提示你必须先认证，不认证不让访问。前面认证过的，就没有这个提示。

首次注册阿里云，会自动赠送每个模型 100 万 token 的使用权。

百炼是一个平台，不是一个模型。通义千问自己的千问 Max、千问 Plus，还有第三方的 DeepSeek、智谱的 GLM、月之暗面的 Kimi、MiniMax、小米的模型，全都支持，可以随意使用。每个模型默认赠送 100 万 token。

免费额度在哪看？点「模型」，再点左侧的「用量和费用」，就能看到各模型的免费额度，一个用完了换下一个就行。这部分不用花钱。

千问3.8 是阿里现在的旗舰模型，能力非常强，几乎接近 Kimi K3。免费额度列表里一眼扫过去好像只有 3.7，看不到 3.8，搜一下是有的，也有 100 万 token，可以用。

### API Key 只给你看一次

注册完还要申请一个 API Key，所有平台都是这个流程。位置还是在「模型」底下，最下面有一个「API Key」——它早先叫「密钥管理」，现在名字变了。阿里的这个页面天天在变，图也得天天改，所以这里只能作为一个参考。

创建的时候有个关键变化：早期阿里的密钥创建完以后是可以复制粘贴的，有复制按钮；但从现在开始，新建的 API Key 仅仅在创建后显示一次，离开这个对话框就再也无法取回了。也就是说，阿里连自己都不保存你的密钥。

所以流程是：在「API Key」里创建，随便起个名字，点确定，它生成一个 Key；下面还有对应的 URL 地址和路径。把 Key、OpenAI 兼容的地址、DeepSeek 兼容的地址全部复制一份，找一个文件保存下来，或者直接下载到本地。用不用先不说，反正先保存下来，因为以后你再也见不到了，就这一次机会。

每个人的路径都不一样，在座的每个人都不一样。将来记住自己的 URL、自己的 Key 就行了。

> **易错点**：新建的 Key 只在创建后显示一次，关掉对话框就取不回来。创建完第一件事是把 Key 和配套地址复制存档，而不是先回去改代码。

这里有件真事值得说。我之前创建 Key 的时候没点「用完即停」，就把它放在那儿，结果不知道哪个同学拿了我的 API Key——大家都知道 Claude Code 是可以随便配模型的，阿里云又支持 gemini-2.5，当时 gemini-2.5 非常强，他就用我的 Key 配上 gemini-2.5，在自己的 Claude Code 里天天用。等我翻账单的时候，已经扣了我好多钱，给我气坏了。所以大家不要干这种事，也没几个钱，自己用自己的就行。顺手把「免费」那一栏的「用完即停」点上。

模型怎么用？随便点一个进去，上面是模型的名字，下面是介绍和 API 示例代码。那段代码看着很眼熟——以前配的是 DeepSeek，现在换成这个，把 Key 和地址一改，拿代码一跑，肯定能跑通。所以代码本身没什么好说的。

### 403 暴露出来的写死问题

把百炼的 Key 和地址贴进项目的配置文件，重启项目。之前那个项目连的是本地数据库，数据库没起来不要紧，启动一下就行。

访问前端，登录，新建一个会话，发一句“嗨”——失败了，403。

403 说明请求被拒。检查下来：Key 改了，base URL 也改了，唯独模型名没改。顺着发请求的代码翻下去才发现，模型名是在那一段请求里直接拼进去的，还写着原来那个。更根本的问题在于，这个模型名是写死在代码里的——这不合逻辑，换个平台就得改代码，那配置还有什么意义？

于是把模型名也提出来，作为一项配置（比如 `chat_model`）放进 settings，代码里从 settings 里取，不再写死。然后把值换成千问的旗舰模型 `qwen3.8-max`，心里想着我就不信了，再发一次“嗨”——这回成了，可算聊上了。

所以切换模型平台，本质就三样东西：API Key、base URL、模型名。千问和 DeepSeek 用起来没什么区别，唯一的麻烦是百炼的路径很变态，而且每个人的路径都不一样，记住自己的 URL 和自己的 Key 就够了。

> **结论**：换平台只动这三处，任何一处还写死在代码里，就会以 403 这样的错误找上门。

### 本地兜底：Ollama

阿里云的 100 万 token，也有可能被用完。用完了还想继续跑，可以在本地部署模型。

企业里做专业部署会用 vLLM，但可惜它只支持 Linux 系统，配置也比较复杂，这里就不讲了；后面讲高级部署方案的时候再说。对刚入门的同学来说，用一个最基本的、最简单的就够了——Ollama。

Ollama 是一个专门用来在本地部署模型的软件。访问它的官网 ollama.com，图标是一只小绵羊，首页上写着 The easiest way to build with open models——搭建本地模型最简单的方式。说实话是真简单，一键部署。

理解它有个好用的类比：Ollama 跟 Docker 很像，它本身就是一个服务；Docker 用来部署应用，Ollama 用来部署模型。

它支持 Windows、Linux、Mac，不用担心系统。用 Mac 的同学下 Mac 版本，用 Windows 的同学下 Windows 版本。可以命令行安装，也可以直接点击下载安装。Windows 同学不用下载了，资料里的「其他软件」中有安装包 `OllamaSetup`，1.69G，双击，一路下一步就好。

装完就是个小绵羊图标，而且它自带一个聊天窗口。但现在还不能用——要用的前提是本地得有模型。

先看设置，里面有几项值得动：第一项是自动下载更新，你的 Ollama 要不要自动更新，不想让它更新就去掉；第二项是要不要把 Ollama 暴露到网络当中、允许外部访问，默认不暴露，想暴露自己开；第三项是模型的存放地址，默认在 C 盘，不想让 C 盘爆炸的话，在这里调一个位置。其他的就不用调了。

> **提示**：模型文件动辄几个 G，默认落在 C 盘很快就会把系统盘塞满。装完先改存放路径，再下载模型，顺序别反。

### 命令几乎和 Docker 一模一样

下载模型有两种办法。第一种是在图形界面里找想要的模型，点下载，而且支持搜索，比如输入 deepseek 就能搜到；但搜索结果里会混进来一些奇怪的仓库，不太可靠。最好的方案是用命令下载，而且这套命令跟 Docker 命令很像。

| 指令 | 作用 |
| :--- | :--- |
| `ollama pull` | 拉取一个模型到本地 |
| `ollama push` | 推送一个模型到远端仓库 |
| `ollama list` | 查看本地模型 |
| `ollama run` | 运行模型 |
| `ollama stop` | 停止一个模型 |
| `ollama ps` | 查看运行中的模型 |
| `ollama rm` | 删除模型 |

演示一下：`ollama list` 查看本地模型，本机有两个；`ollama ps` 查看运行中的模型，空的；`ollama run qwen3.5:0.8b`，转一会儿圈，启动好了，它提示你发消息；发个“嗨”，回复很快。

回复分两段：一段是思考，一段是正式回复。一个“嗨”思考了挺长一段，看着像有问题，但这个模型本身还是挺厉害的——它支持图片识别。放一张照片问“这是谁”，它一本正经说成明朝的某位，认错人了，我刚夸它两句。

这就是本地模型。装好 Ollama，就能在自己机器上部署模型，但也不是任意模型都能跑，它对内存和显卡有一定的要求。

### 参数量、显存，以及你能跑多大

打开千问3.5 的模型页，会看到同一个模型支持很多种尺寸：0.8B、2B、4B、9B、27B、35B、122B。这些数字后面的 B 是 billion，十亿。

英文是三位一进制：million 是百万，百万再乘以 1000 才是十亿。所以 B 代表十亿，指的是模型的参数规模。参数规模越大，模型越强，但占用的显存也越高。

122B 就是 1200 亿参数，要占 80 多个 G——注意是显存，不是内存，显存就是显卡上的存储。目前国内最强的模型之一 Kimi K3，参数规模到了 3 万亿，单位是 trillion，比 billion 又高了一个数量级（3000 billion），反正就是很大。

算算自己的显卡：我这台是 5070Ti，12G 显存，加 18G 共享显存，合在一起 29G。所以我只能部署 27B、9B 这一档，再大的模型就部署不了。没有独立显卡的同学，那就 0.8B 玩一玩就行了。

顺带说一句显卡的价格：5070Ti 现在都买不到了，价格飙涨，这样一台机器现在怎么着也得一万七八甚至两万；内存也特别贵，我买的电脑都成理财了。

所以下去装好 Ollama，把 `qwen3.5:0.8b` 拉下来就行，别下大的。拉取是 `ollama pull qwen3.5:0.8b`，它会去拉取，本地已经有了就不会重复拉——跟 Docker 拉镜像是同一个玩法。模型名别手写，去页面上复制，少打错字。装了 5090 的同学，那当我没说。
