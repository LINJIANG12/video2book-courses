## 保险条款 RAG 的父子块设计
> 对应块：BLK38 | 覆盖分集：P148-P149 | 块标题（分集名）：《保险顾问 RAG 总体设计》

保险条款这份材料，我一直建议先亲手打开看一眼，再谈怎么切、怎么检索。项目资料里有个 `08 保险条款` 目录，里面是这门课要用的各家产品的条款 PDF。随便点开一份，第一眼会觉得平平无奇：前面是目录，后面是"第一条""第二条"这样的条款文字，字号规整、段落清爽。可这恰恰是它最坑人的地方——你看到的那些"段落"，压根不是段落。

把截图工具打开，沿正文拉一个框，表格线就显形了：整篇正文其实是一张表。左边一列放编号，右边一列放内容，只是没有画边框，看着像排版好的文章。

编号的含义也就清楚了：单独一个"一"，是第一章；下面的"1.1"，是第一章第一小节，"1.2"是第二小节，往后依次类推。

更麻烦的是这张表根本没在当页画完。表格画到页面底部就被截断，下一页接着续，续到一半再断，再下一页再续。整份 PDF 一共 55 页，从头到尾就是这么一张跨了几十页的大表。

```text
第 1 页   ┌──────┬──────────────────────────────┐
          │  一  │ 第一章  总则                 │
          │ 1.1  │ 第一条 ……                    │
          │ 1.2  │ 第二条 ……                    │
          └──────┴──────────────────────────────┘
                        ↓ 表格在页底被截断
第 2 页   ┌──────┬──────────────────────────────┐
          │ 1.2  │ （接上页的内容）……           │
          │ 1.3  │ 第三条 ……                    │
          └──────┴──────────────────────────────┘
                        ↓ 再次截断
第 3 页   ……
```

这样一份文档，市面上能见到的解析工具我基本都试过，没有一个能把结构完整地还原出来。像 MinerU 这种级别的 PDF 处理工具，也不敢保证处理得完好如初。整条 RAG 的顺序是定死的：先离线把知识库建起来，再做在线的检索增强；而建库的第一步就是文档加载——这一步在保险条款这里就是个真问题，不是"找个 loader 读一下"能糊过去的。

### 转成 Markdown 的真正理由

读进来之后，我们希望它变成什么？Markdown。

理由不是"Markdown 好看"，而是这份文档的编号结构本身就是一棵标题树。翻到缴费那一章，编号是 `3` 如何缴纳保险费，底下 `3.1` 保费的缴纳、`3.2` 宽限期；再看内容，`3.1` 底下讲的就是保费怎么交，`3.2` 底下讲的就是宽限期。一个小节，正好是一个条款。

这跟 Markdown 的层级是一一对应的：章就是一级标题，小节就是二级标题。

> **结论**：先把 PDF 解析成带标题层级的 Markdown，再按标题去切，一个小节就是一个条款，条款的完整性天然被保住。

所以第一步要做的事情定下来了：解析成 Markdown，让它形成标题结构。切分放到第二步。

### 结构感知切分：方案最理想，现实最骨感

切分这一步，最理想的方案几乎是显而易见的：既然一个小节就是一个条款，那就按文档结构感知切分，一个小节切一段。一个小节一段、一个小节一段，还有比这更完美的吗？

理想很丰满，现实很骨感。有些小节长得离谱。比如"免赔额"那一节，一整节文字铺下来，屏幕都翻不完；第二章 `2.1` 责任免除也是一节顶别人好几节。

块大小的经验区间一般建议在 200 到 1000。一节几千字，早就破表了。为什么不能忍？块太大，噪音就多，一段文本压成一个向量之后，"主题"被稀释，检索精度就掉下来了。

这笔账得算清楚，它是后面所有设计的出发点：

| 切法 | 语义完整度 | 噪音 | 检索精度 |
| :--- | :--- | :--- | :--- |
| 块大 | 高 | 多 | 低 |
| 块小 | 低 | 少 | 高 |

> **易错点**：块大小不是"越大越省事"。大块省的是切分的心，亏的是召回的钱——检索回来一大坨，模型要么被噪音带偏，要么干脆抓不住重点。

矛盾就摆在这里：要么完整但不精准，要么精准但不完整。而保险条款这个场景两个都要——条款必须整条交给模型，检索又必须准。单一的切分粒度满足不了。

### 父子块：同一份条款，两种粒度

解决办法是把切分拆成两层，叫父子块切分。先说明一句：这不是某个现成的工具，没有哪个 splitter 叫"父子块切分器"，它是我们自己设计的一套流程，需要手动实现。

第一层，先按文档结构感知切分，一个小节切一个大块。这个大块叫父块，英文就是 parent chunk——它天然对应一个完整条款。

第二层，当发现某个小节特别大时，比如 `2.1` 责任免除，再对这个父块做递归切分，把大块切成若干小块。这些小块叫子块。示例里 `2.1` 被拆成了三个子块。

拆完会带来一个新问题：三块散开了，模型单看其中一块，怎么知道它在讲什么？所以要让这三个子块共享同一个标题——把父块的标题拼进每个子块的正文里。这样三块都带着"责任免除"这四个字，谁都清楚自己属于哪一条，只是被分成了三个部分而已。

两个角色，分工就此确定：

| 角色 | 存在哪里 | 用在哪 | 保什么 |
| :--- | :--- | :--- | :--- |
| 父块 | 普通数据库（PostgreSQL） | 拼进 prompt 发给模型 | 条款完整度 |
| 子块 | 向量库 | 向量检索（含过滤） | 检索精度 |

于是存入向量库的是子块，用来检索的也是子块，检索精度有了。

可这里马上冒出一个新问题：假设 `2.1` 被切成三块，用户的问题只命中了第二块，另外两块没被召回，那条款是不是就不完整了？

会。向量检索只保证"最像"，不保证"最全"。所以必须能从子块回爬到它所属的父块。办法是建关联：数据库里的每条记录都有唯一标识 `id`，每个父块自然也有自己的 `id`；那我们往向量库存子块时，顺手给子块加一个 `parent_id` 字段，写上它所属父块的 `id`。

字段可以随便加，这正是向量库的方便之处。同一小节切出来的三个子块，`parent_id` 是同一个；换了别的小节，`parent_id` 自然就不一样了。

召回链路就通了：

```text
用户提问
   │
   ▼
向量库检索 ──► 命中子块 ID = V2
   │
   │ 子块里存着 parent_id = 1003
   ▼
PostgreSQL：SELECT * FROM parent_chunks WHERE id = 1003
   │
   ▼
取回父块（完整条款）
   │
   ▼
父块 + 用户问题 ──► 模型 ──► 答案
```

代入具体数据看一眼会更清楚。父块表里躺着几条记录：`1001` 讲"我们保什么"，`1002` 讲等待期，`1003` 讲免责。用户问"哪些情况不赔"，向量库召回的那个子块，`parent_id` 恰好是 `1003`。拿 `1003` 去数据库里 `where id = 1003`，命中"免责"这一整条，把它返回，再和用户问题一起送进模型。

> **结论**：子块负责"找得到"，父块负责"说得全"。子块检索、父块喂模型，两个粒度各管一头，精度和完整度就不再互相拉扯。

### 子块字段：三个够用，第四个为了过滤

按上面的分工，子块的数据结构几乎能顺着推出来。

它要在向量库里被检索，首先得有自己的 `id`——向量库入库时自带，名字可能叫 `pk`，也可能叫 `id`，我们代码里统一按 `id` 处理就行。其次要有 `parent_id`，标记它属于哪个父块，回爬时全靠它。第三是 `content`，也就是子块的正文，将来用来生成稀疏向量和稠密向量。

理论上，这三个字段就够了。

但前面我们提过一个坑：库里不止一个产品。保险产品非常多，每个产品都有自己的条款，而这些条款之间很可能有重复或相似的内容。比如达尔文的医疗险，和相守系列（12 号、2 号）的医疗险，都属于医疗险，都必然有免责条款、都必然有等待期——不同产品，条款文字却长得像。

这时候如果直接拿"免责条款"去搜，很可能用户问的是 A 产品，召回的是 B 产品的免责条款。答案看起来有鼻子有眼，实际答错了产品，这在客服场景里是要出事的。

所以必须保证：用户问 A，搜出来的只能是 A 的条款。

`products` 表里每个产品都有自己的 `id`。那就在存子块时再加一个字段 `product_id`，把产品身份钉在片段上：

| 字段 | 类型 | 作用 |
| :--- | :--- | :--- |
| `id` | 字符串 | 子块自身唯一标识 |
| `parent_id` | 字符串 | 指向父块，用于回爬完整条款 |
| `content` | 文本 | 生成稠密 / 稀疏向量，参与检索 |
| `product_id` | 整数 | 检索前按产品过滤 |

检索时两件事一起做：`query` 是"等待期是多久"，`filter` 里写 `product_id = 3`（假设 `3` 就是达尔文 12 号）。有查询、有过滤的情况下，过滤优先：先按 `product_id` 把搜索范围锁定到该产品的那一批片段，再在这批片段里做向量检索。

```text
向量库全量片段（混着多个产品）
┌──────────────┬──────────────┬──────────────┐
│ product_id=1 │ product_id=2 │ product_id=3 │
└──────────────┴──────────────┴──────────────┘
                      │
                      │ filter: product_id = 3
                      ▼
      ┌──────────────────────────────┐
      │  仅 product_id = 3 的片段    │
      └──────────────────────────────┘
                      │
                      │ query: 等待期是多久
                      ▼
                   Top-K 命中子块
```

先缩小范围，再做相似度——顺序反了，精度就没了。

### Document 进向量库：metadata 会被摊平

子块最终是以 LangChain 的 `Document` 形式交给向量库的。而 `Document` 只有三个字段：`id`、`page_content`、`metadata`。

那 `parent_id` 和 `product_id` 往哪放？只能塞进 `metadata`。

这不算妥协，因为 `Document` 一旦扔进向量库，`metadata` 会被自动展开，摊平成一层标量字段——前面讲过，向量库不认识"嵌套字典"，它只认平铺的键值。

所以同一个子块，写的时候和存进去之后是两副样子：

```text
写入时（Document）
┌────────────────────────────────────────────┐
│ id            : "V2"                       │
│ page_content  : "……责任免除……"             │
│ metadata      : { parent_id: "1003",       │
│                  product_id: 3 }           │
└────────────────────────────────────────────┘
                    │ 入库，metadata 自动展开
                    ▼
落库后（一条向量记录）
┌────────────────────────────────────────────┐
│ pk / id      : "V2"                        │
│ text         : "……责任免除……"              │
│ parent_id    : "1003"                      │
│ product_id   : 3                           │
│ dense_vector : [0.013, -0.227, …]          │
│ sparse_vector: { 条款: 0.41, 免责: 0.33 }  │
└────────────────────────────────────────────┘
```

对照着看就明白：`id` 对应 `pk`，`page_content` 对应 `text`，`metadata` 里的两个键各自变成同名的独立字段，最后再加上自动生成的稠密向量和稀疏向量。写入时的嵌套结构，落库后被彻底摊平。

### 父块字段：内容给模型，元信息给人

子块结构定了，父块反而更容易推，因为它只干两件事。

第一件事，存完整条款正文，将来发给模型生成答案。这对应一个 `content` 字段。

第二件事，是保险条款这个业务特有的：条款是要展示给用户看的。你在 DeepSeek 上问过带联网的问题就有印象——答案里会冒出 `[1]`、`[4]` 这样的小标号，点一下能看到对应的网页。那个标号就是这个说法、这句话的来源，也就是引用溯源。有了它，答案的可信度立刻不一样：不是模型瞎编的，是从真实页面里拿的，不是幻觉。

客服答条款是同一个道理。用户问"等待期多久"，你不能只甩一句"180 天"就完了，得让他点开看到：这是哪个产品的哪一条，在第几章第几节。所以父块除了正文，还要带上条款名称和章节路径——前端点开引用时，展示的就是"条款完整名称 + 所属章节 + 完整内容"这三样。

于是父块的字段定下来了，五个业务字段加一个时间：

| 字段 | 类型 | 用途 |
| :--- | :--- | :--- |
| `id` | uuid | 唯一标识，被 `parent_id` 命中，召回整块 |
| `product_id` | int | 所属产品 |
| `content` | text | 完整条款正文，发给模型生成答案 |
| `clause_name` | text | 条款名称，前端展示引用来源 |
| `section_path` | text[] | 章节路径，前端展示"第几章第几节" |
| `create_at` | timestamp | 创建时间，继承时间混入类自带 |

`section_path` 用列存，因为章节是分层的：一级标题、二级标题、三级标题，可能还有四级。把每一级标题按顺序放进数组，前端就能拼出"二 提供保障 / 2.3 保险责任 / 2.3-1 等待期"这样一条路径。

`id` 和 `content` 是给机器用的：`id` 用来被召回，`content` 用来喂模型；`product_id` 用来划归属、做筛选；`clause_name` 和 `section_path` 是给人看的——点开引用时，条款名称和所属章节由它们拼出来，正文还是取自 `content`。

> **提示**：父块不进向量库，但一定要落库。它不参与相似度计算，只负责被 `id` 精确命中——这类查询交给关系型数据库，比向量库合适得多。

落到表上就是这六个字段。`create_at` 不用自己写，继承时间混入类之后自带。

对应的映射类叫 `ParentChunk`，表名 `parent_chunks`。这张表已经建好了，打开数据库客户端就能看到，里面暂时没有数据，表结构就是上面这套。这个 model 继承 `Base`——也就是那个时间混入类。

代码组织上有个小决定：RAG 属于比较特殊的一块功能，不要和普通业务混在一起，单独放一个包。新建 `rag` 包，里面再建 `models.py`，把这个映射类放进去。数据模型一到位，后面所有增删改查就都有抓手了。

### 完整流程：离线建库，在线增强

把前面每一步串起来，整个 RAG 就两条链路。

#### 知识库构建

1. 拿到某个产品的条款 PDF；
2. 用 MinerU 把 PDF 解析成 Markdown；
3. 用 `MarkdownHeaderTextSplitter` 做结构感知切分，切成父块；
4. 父块写入数据库（PostgreSQL）；
5. 父块再用递归切分拆成子块；
6. 子块连同 `parent_id`、`product_id` 写入向量库。

#### 增强回答

1. 用户提问，问题向量化；
2. 带 `product_id` 过滤，去向量库检索子块；
3. 从命中的子块里取出 `parent_id`；
4. 拿 `parent_id` 去数据库查父块；
5. 父块正文和用户问题一起交给模型，生成答案。

```text
【离线：建库】
条款 PDF ──► MinerU ──► Markdown ──► 结构感知切分 ──► 父块
                                                        │
                                                        ├──► PostgreSQL（parent_chunks）
                                                        │        整条落库，供回查
                                                        │
                                                        └──► 递归切分成子块
                                                                    │
                                                                    ▼
                                                                 向量库
                                                      （带 parent_id / product_id）

【在线：问答】
用户问题 ──► 向量化 ──► 向量库检索（filter: product_id）──► 子块
                                                              │
                                                     取 parent_id
                                                              ▼
                                               PostgreSQL 查父块（完整条款）
                                                              │
                                                              ▼
                                        父块 + 用户问题 ──► 模型 ──► 最终答案
```

这张图值得记在脑子里。面试的时候如果有人问"你们这个 RAG 是怎么做的"，把这两条链路、五个字段、`parent_id` 回爬讲清楚，就是一份能拿得出手的答案——因为它不是"我调了个 LangChain 的链"，而是一个针对业务文档结构做出的设计决策。

一开始会觉得这套东西有点复杂，别急，一步一步做下来，每一块都不难：文档解析、结构切分、父子两套数据结构、两条链路，仅此而已。

## 父子块结构与条款文档的解析流水线
> 对应块：BLK39 | 覆盖分集：P150-P153 | 块标题（分集名）：《父子块数据结构与文档解析》

切分策略一讲完，数据结构其实就已经没什么悬念了。你把东西存到哪儿、将来给谁用，字段自己就长出来了——父块要进数据库，因为它保存的是完整条款，将来得原样返回给模型去生成回答；子块要进向量库，因为它只负责检索，把跟问题相关的片段捞出来，捞到之后带上父块的 `id` 就够了。所以这一段不是"设计"，是"推导"，推完你会发现每个字段都有它的去处，没有一个是为了好看加的。

推完子块再推父块，两个结构定下来，整条 RAG 流程就能画成一张图；图一画出来，接下来要写的代码就是照着图填空。这一讲先把这张图讲透，然后动手走它的前两步：把产品对应的条款文件查出来，再把 PDF 解析成 markdown。

### 从"存哪儿、给谁用"倒推字段

先看子块。子块是用来检索的，那么第一个字段必然是它自己的 `id`——往向量库里存，它本来就自带主键，只不过这个主键的名字可能不叫 `id`，可能叫 `pk`。名字无所谓，我们在自己的代码里统一叫 `id` 就行，别被底层存储的叫法牵着走。

第二个字段是 `parent_id`。子块得标记自己属于哪个父块，将来检索命中之后，就是靠它回去把完整条款捞出来的，这个字段省不掉。

第三个字段是 `content`，也就是子块自己的正文。它是用来生成稀疏向量和稠密向量的，检索能命中谁，全看这段文字。

讲到这儿，理论上三个字段就够了：`id`、`parent_id`、`content`。但真到业务里，还差一个。

> **易错点**：子块的字段不是"够存就行"，而是"够查才行"。少一个过滤字段，检索就会串产品，而且串得很隐蔽——返回的条款读起来完全通顺，只是属于另一款产品。

问题出在保险这个业务本身。数据库里的保险产品非常之多，每个产品都有自己的条款，而这些条款里大量存在重复或者相似的内容。你比如都是医疗险，医疗险里都会有免责条款：达尔文那款医疗险有免责条款，另外一家公司的医疗险也有免责条款。产品不同，条款内容自然不一样，可它们长得像、说法像、用词也像。

一旦只拿"免责条款"这样的语义去搜，会发生什么？用户问的是 A 产品，检索命中的却是 B 产品的免责条款。模型拿着 B 的条款一本正经地回答 A 的问题，答案看起来毫无破绽——这比检索不到更可怕，因为它不会报错。

所以必须保证一件事：用户问 A，搜出来的一定是 A 的条款。做法我们前面讲过，就是过滤。`products` 表里每个产品都有一个 `id`，那么存子块的时候，除了那三个字段，再存一个 `product_id` 进去。

这个字段的用法是有先后顺序的：先用 `product_id` 把范围锁死，从向量库里筛出跟这个具体产品有关的全部条款片段；再在这一批片段里，找出跟用户问题最相关的那一条。两步走，而不是一步到位。

```text
全库碎片   [p1] [p2] [p3] [p1] [p3] [p2] ...
                    |
                    |  filter: product_id = 3
                    v
候选集     [p3 的碎片] [p3 的碎片] [p3 的碎片] ...
                    |
                    |  query: 等待期是多久（向量检索）
                    v
命中子块   （带 parent_id，回去查父块）
```

读这张图只要记住一句：**有查询、有过滤的时候，过滤优先**。过滤不参与相似度计算，它只是把候选集缩小；缩小之后再算向量距离，才不会算到别人家的条款上去。

举个具体的：用户问"等待期是多久"，同时指明了产品是达尔文 12 号，假设它在库里的 `product_id` 是 3，那这次检索就带上 `product_id == 3` 这个条件。整库的碎片先被切成"只属于 3 号产品"的一堆，再在这堆里找跟"等待期"最像的那一段。同理，相似产品切出来的那一堆碎片虽然也在库里，但一开始就被过滤条件挡在外面，根本进不了相似度比较。

到这儿子块的结构就齐了：`id` 是自己，`parent_id` 用来召回父块，`content` 用来生成稠密和稀疏向量、用来做检索，`product_id` 用来做过滤。

### 子块真正落进向量库的样子

结构定完，还得落到具体的载体上。LangChain 的 `Document` 一共就三样东西：`id`、`page_content`、`metadata`。你会发现刚才推出来的四个字段里，只有 `id` 和 `content` 有地方放，`parent_id` 和 `product_id` 无处安放。

没地方放，就塞进 `metadata`。`Document` 是这么写的：`id` 存子块自己的 id（字符串），`page_content` 存片段正文，`metadata` 里放 `parent_id` 和 `product_id` 两个键。

这一步没什么玄机，真正要记住的是下一步：这份 `Document` 一旦扔进向量库，`metadata` 会被展开，变成一个个标量字段。这不是我们自己展开的，是入库时自动发生的——前面讲过这件事，忘了就回头翻一眼，因为后面查库、写过滤条件全靠它。

```text
LangChain Document                  向量库中的一条记录
-------------------                 -------------------
id            子块 id      --->     id / pk
page_content  片段正文      --->     text
metadata.parent_id   --展开-->      parent_id     （标量字段）
metadata.product_id  --展开-->      product_id    （标量字段）
                                    dense_vector  （自动生成）
                                    sparse_vector （自动生成）
```

存进去是左边那个样子，落到库里是右边那个样子。对比着看就清楚了：`Document` 里那个叫 `page_content` 的东西，进了库改叫 `text`；`metadata` 里的两个键脱掉了外壳，跟 `id` 平起平坐，成了可以写过滤条件的标量字段；最后两个向量字段不是我们给的，是入库时按 `text` 自动算出来的，稠密一个、稀疏一个。

> **结论**：子块的设计只存在于 Python 这一侧；进了向量库，它就是一条"两个标量 + 两个向量 + 一个主键"的普通记录。写过滤条件时用的是 `product_id` 这个标量，不是 `metadata.product_id`。

### 父块：既要喂模型，也得给用户一个交代

子块管检索，父块管交付。它要存进数据库，第一个用处是保存完整的文档内容，将来把这段内容发给模型，让模型生成答案。

但父块不止这一个用处。保险条款生成完回答之后，是要展示给用户看的——不是把答案往那儿一扔就完了，还得让用户知道这句话是从哪儿来的。

你在 DeepSeek 上如果开着联网问过问题，一定见过答案里冒出来的那种小角标：一句话后面跟着「1」「4」。这两个数字是它联网搜到的网页编号，意思是这句话的来源就是这两个网页。点一下就能跳过去看原文，这就是引用溯源。它的价值不在于好看，而在于它精准地告诉用户：这个回答引用了什么。点开能对上原文，可信度立刻就上去了——这句话不是它瞎编的，不是幻觉，是从真实页面里抠出来的。

客服场景同理，而且要求更硬。用户问的是一条条款，你答的是这条条款的信息，那就必须把出处摆出来：条款叫什么名字、属于哪一章哪一节、完整内容是什么。我们把这几样东西直接展示在回答下面，用户看到的形如「2.3 保险责任 / 2.3-1 等待期」，前面还有更上一层的章节「二、提供保障」，点开就是完整条款。用户一眼就能判断这条回答靠不靠谱，而不是只能选择相信或者不相信。

所以父块里的字段，除了内容，还得有身份和位置：

- `id`：唯一标识，用 uuid，将来被子块的 `parent_id` 反查；
- `content`：父块正文，也就是完整条款内容，发给模型用；
- `product_id`：这个父块属于哪个产品，`int`；
- `class_name`：条款名称，其实就是条款文件名；
- `section_path`：章节路径，用一个列表存，把一级标题、二级标题、三级标题甚至四级标题一层层装进去。

`section_path` 为什么是列表而不是字符串？因为章节本来就是分层的：有一级标题，有二级标题，可能还有三级、四级。用列表存，前端想拼成什么样式就拼成什么样式，想只显示最后一级也只取最后一个元素；用字符串拼死，前端再想拆就难了。

到数据库里，这张表叫 `parent_chunks`，字段跟上面一一对应，`section_path` 落到库里是数组类型（`array`），再额外带一个创建时间字段。这个时间字段不用自己写——继承时间混入类就自带 `created_at` 了，`Base` 里已经处理好。

> **提示**：五个业务字段其实分成两组。`id` 和 `content` 是给机器用的：一个负责被召回，一个负责喂模型。`product_id`、`class_name`、`section_path` 是给人看的：用户点开引用时，前端拿这三个字段渲染出「条款名 + 章节 + 全文」。设计的时候把这两组分清，后面加字段就不会乱。

表已经建好了，打开数据库客户端就能看到 `parent_chunks`，现在是空的，结构就是刚才分析的这套。对应的映射类叫 `ParentChunk`，表名也叫 `parent_chunks`，字段有 `id`、`product_id`、`class_name`、`section_path`、`content`，加上继承来的时间。

这个类放哪儿？RAG 属于比较特殊的一块功能，不适合跟普通业务模块混在一起，所以单独开一个包，就叫 `rag`，里面再建一个 `models`，把这个映射类放进去。多写两行 import 的代价，换来的是"哪些代码属于 RAG"一眼可见。有了它，将来对这张表做增删改查就有抓手了。

### 把两端接起来：一条完整的 RAG 链路

子块、父块都定完，整条链路就能串成一张图了。

```text
【建库】
条款 PDF
   |
   v
MinerU 解析  --->  markdown
   |
   v
MarkdownHeaderTextSplitter（结构感知切分）
   |
   +----> 父块（大块） ----> 数据库 parent_chunks
   |
   +----> 递归切分 ----> 子块（小块） ----> 向量库（dense + sparse 自动生成）

【问答】
用户问题 ---> 向量化 ---> 向量库检索 ---> 子块
                                            |
                                            v  取 parent_id
                                       数据库查父块
                                            |
                                            v
                                  父块正文交给模型 ---> 生成答案
                                            |
                                            +--> 前端展示：条款名 / 章节 / 全文
```

上面那条是建库：拿到某个产品的条款 PDF，用 MinerU 解析成 markdown，用 `MarkdownHeaderTextSplitter` 做结构感知切分，切出来的大块就是父块，直接进数据库；再把大块递归切一刀，切成子块，写进向量库。

下面那条是问答：用户提问，问题向量化，拿向量去库里检索，命中子块；子块身上有 `parent_id`，拿它回数据库查父块；把父块的完整内容交给模型，模型生成答案，前端再把条款名和章节一并展示出来。

两条链路唯一的交接点就是那个 `parent_id`。它是整张图的铰链：没有它，检索到的碎片和完整条款就是两个世界的东西。

### 知识库构建是一条流水线

建库这件事听起来复杂，其实是一个固定流程。任何一份文档进来，都是先加载解析——把普通的 PDF 变成纯文本的文档；再用切分器切，切出父块和子块；父块进数据库，子块进向量库做相似度检索。

严格说，进向量库之前应该先做向量化再存。但我们用的是 LangChain 的 Milvus 封装（也就是 vector store），它把"向量化"和"入库"这两个动作合成了一个——你把文档交给它，它自己算完向量就存进去了。所以实际写起来就是：加载、切分，父块存数据库，子块存 vector store，向量化那一步被封装吃掉了。

这个流程像什么？像工厂加工原材料。工厂里处理原料就是一条流水线：一条传送带，原材料放上去，经过一个又一个机械臂、一个又一个车间，不断被加工，最后出来的是成品。文档也一样——进来是第一道工序：加载解析；第二道：切分；第三道：入库。工序是固定的，变的只是过传送带的原料有多少。

英文里这条流水线就叫 pipeline。既然它是固定的，事情就好办了：把每一个步骤都开发成一个组件——加载解析一个组件、切分一个组件、入库一个组件——然后把组件组装起来，拼成一条流水线。以后不管来十个、一百个、一千个甚至一万个文档，只要扔给这条流水线，出来就是知识库。这就是组件化的意义：你不是在解决"这一份 PDF 怎么入库"，你是在造一台能吃任何 PDF 的机器。

不过在动手写组件之前，先别急着一个个开发。为了看清每一步加工到底把文档变成了什么样，我们先在 notebook 里把每个步骤模拟一遍，观察效果，再把模拟出来的模块组装成流水线。这样出错的时候你知道是哪道工序出的问题，而不是对着一条黑箱流水线猜。

这里有个顺序上的坑：按流程图，第一件事应该是"加载解析文档"，但其实不是。你要加载解析，得先有文档；文档从哪儿来？从数据库里查。所以真正落到代码上的第一步是查询。

四步定下来：

1. 查询保险产品及其条款文件；
2. 加载并解析条款文档，把它变成纯文本；
3. 切分文档，切出父块和子块；
4. 存入向量库和数据库。

### 先去数据库把原材料取出来

新建 notebook 的位置是 `notebooks/day09/`，文件名 `01_rag_pipeline`。第一步，查产品。

这一步不用自己往数据库里写 SQL。原来做业务模块的时候写过一个"首页产品列表"接口，它调的是 `ProductService` 里的 `list_product`：你把产品分类告诉它，它按分类查；分类不传，它查的就是全部产品。现成的服务，直接调。

调之前得先有数据库会话。`ProductService` 创建对象的时候要传一个 `session`，而 `session` 从 `app.infra.database` 里的 `session_factory` 拿。

```python
from app.models.product.service import ProductService
from app.infra.database import session_factory

async with session_factory() as session:
    service = ProductService(session)
    products = await service.list_product()
```

创建 service 要传 `session`，查询要 `await`——因为它底下是异步的 ORM。`list_product` 不传分类，查回来 12 条产品，每条里都有 `id`、`class_name` 和一整套产品详情。

这 12 条里我们真正要的只有两个字段：`id` 和 `class_name`。原因就是前面推结构时说的那两条——父块要知道自己属于哪个产品、条款叫什么名字，前端要展示；子块要知道 `product_id`，将来做过滤。剩下的字段对建库没用。

接下来不必把 12 个产品全处理一遍，取一个就够：`product = products[0]`。打印出来能看到它的 `id` 和 `class_name`，`class_name` 就是条款名称。知道条款名称，就能找到对应的条款文件。

文件在哪儿？在课前资料的「08 保险条款」里，目录结构是 `data/raw/kb/`，三层。里面躺着各家公司的条款 PDF，文件名就是 `class_name` 里那个名字。

要做的事是把这个 `data` 目录整个复制一份，放到 `agent_service` 项目的根目录下。注意别只拷 `kb` 那一层——`data` 里还有别的文件，将来做别的业务还要用，整个目录搬过去最省事，也最不容易在后续课程里再回头找。

为什么非要放进项目目录？因为要读文件。放在别处路径不好拼，读起来别扭；放在项目里，加载的时候就是"当前项目的 `data/raw/kb/` + 条款文件名"，一句话说清。

在 notebook 里，当前目录是 `notebooks/day09`，往上退两级才是项目根，所以路径得写成：

```python
f"../../data/raw/kb/{product.class_name}"
```

`../../` 退到项目根，再 `data/raw/kb/` 进去，最后接上文件名。这段路径没有魔法，就是目录层级数出来的——数错一级，后面解析就会报文件不存在。

### MinerU 解析，以及它翻车的那一下

文件找到了，第二步是加载解析。这里用的是前天在 RAG 那部分学的 MinerU。

MinerU 怎么用？说实话不用背。这些代码不需要你会默写，只要找到原来那段，复制过来，改一改路径就行。创建客户端的部分一个字都不用动，需要改的只有"解析哪个文件"这一处——把原来那个示例路径换掉，换成刚才拼出来的 `../../data/raw/kb/{product.class_name}`。

还有一个开关要注意：OCR 不用开。因为我们要解析的 PDF 是文字型的，不是扫描出来的图片型；没有图片要识别，开了 OCR 只是白花时间。

跑一下，11 秒，可以接受。解析结果在 `result` 里，正文取 `result.markdown`：

```python
markdown = result.markdown
```

然后就是关键的一步——验货。别看到有输出就以为成了，得看看这份 markdown 到底写成什么样。把值复制出来，贴到本地一个 `.md` 文件里打开看。

一眼就看出问题了：标题前面没有 `#`。

markdown 的标题靠井号标识，`#` 是一级，`##` 是二级，没有井号那就是普通的一行字。可这份解析结果里，"第一章"之类本该是标题的行，前头光秃秃的，一个井号都没有。看源码也确认了：确实没有。也就是说，这次解析在结构上是失败的——文字都在，骨架没了。

为什么会这样？回到那份 PDF 本身看：它是一个横跨几十页的超大表格。表格结构一旦复杂到这个程度，解析器就开始力不从心——第一个表格还能认对，第二个、第三个就认错了，以至于 MinerU 在处理时把结构识别错了，最终输出的 markdown 自然也跟着错。有些段落被解析成了表格，有些压根没解析出来，还有些侥幸被认成了标题。

> **易错点**：PDF 解析"有文字输出"和"结构正确"是两件事。文字型 PDF 提文字几乎不会失败，失败的一定是层级——标题、编号、表格边界。这类错误不会报异常，只会让你在后面切分时切出一堆没有章节信息的碎片。

而且这不是换一个解析器就能一劳永逸的问题。各家保险公司的条款格式差异极大：刚才那份是超大表格；换一份意外险，它没有表格，是按"第一条、第二条"排下来的，下面还有圆括号的标题、一级标题；再随便点开几份，又是另一套样子，有的又是表格。

> **结论**：条款文档的结构差异不是"个别脏数据"，而是行业常态。任何指望"一个解析器通吃所有公司模板"的想法，都会在这些差异面前失效。

### 解析坏了，四条路可选

把结构修回来，有四条路。先摆在一起看，再逐条说清楚它们各自卡在哪儿。

| 方案 | 做法 | 优点 | 局限 |
| :--- | :--- | :--- | :--- |
| 人工修正 | 逐份调整标题编号和表格 | 最可靠 | 只适合少量文档；条款变更后要重做 |
| 规则清洗 | 用正则或程序规则识别标题编号、删噪声、修格式 | 不用人、速度快、成本低、结果相对稳定 | 只能处理预先考虑过的格式，格式一变就作废 |
| 模板化处理 | 按不同保险公司的条款模板分别写转换逻辑 | 比规则清洗更稳定 | 每来一套新模板都要重新开发维护，通用性差 |
| 模型优化 | 让大模型理解语义，重排标题、层级编号和段落结构 | 不需要模板，兼容性最好 | 增加调用时间和成本，需要提示词防护 |

第一种，人工修正。逐份把标题编号和表格调对。这种方案最可靠，因为人看得懂内容，改出来一定是对的。但它只适合少量文档：几十份还能忍，几百上千份就是纯人力消耗，耗时长得离谱；更麻烦的是条款会变更，条款一改，之前手工修过的还得重来一遍。可靠性是用人力换的，而人力不可扩展。

第二种，规则清洗。写代码，用正则表达式或者程序规则去识别标题编号、删掉噪声、修正格式——本质是把你肉眼判断"这行是三级标题"的经验，翻译成 if-else 和正则。它的优点很实在：不用人盯着，执行速度快，成本低，处理结果相对稳定，同样的输入永远给同样的输出。

但它有两个硬伤。一是写不出来。你得先能识别出"这一行的编号错了、应该往下降一级"，这个逻辑本身就要求你对所有格式变体都穷举过；连正则都没系统学过的时候，让你写这个，非常困难，虽然可以让 AI 帮你写，但写出不代表写对。二是它只认预先考虑过的格式：保险商城上了一款新产品，条款格式跟以前都不一样，之前那套规则当场作废，你得改代码。

第三种，模板化处理。针对不同保险公司的条款模板，分别写不同的转换逻辑——A 公司一套，B 公司一套，根据模板类型走不同分支。这其实是第二种的升级版：把"一套通用规则"换成"每家公司一套专用规则"，稳定性更高，因为每套规则只需要对付一种格式。

代价是维护。每出现一套新模板，就要重新开发、重新调试、重新上线；模板越多，代码分支越多，通用性越差。它适合格式长期稳定的场景，不适合"每个月都有新保险公司接进来"的场景。

> **提示**：前三种方案本质上都在做同一件事——把"理解结构"这件事，提前用人力、规则或模板固化下来。固化的部分越精确，覆盖面就越窄。

第四种，模型优化。让大模型去理解文档的语义，重新整理标题、层级编号和段落结构。它不需要你准备模板：模型是靠读懂内容来判断"这一行是第几章、这一节属于谁"的，所以哪家公司的条款都能处理，格式怎么变都不影响。

它的好处是兼容性最好——不挑食，随便什么格式丢过来都能处理。代价有两个：一是增加调用时间和成本，每份文档都要过一次大模型；二是必须做提示词防护，明确告诉它"不要修改条款正文"，否则它可能在重排结构的时候顺手把内容也改了，那问题就大了——条款是不能被模型改写的，一个字都不行。

那为什么最后选它？因为前三种对我们现在的阶段来说太难了，需要的编码复杂度远超目前学到的东西；而模型优化是四条路里实现起来最简单的，适应性、兼容性又最强，唯一的顾虑是成本——可 DeepSeek 本身就便宜，就算涨过价，也比别家便宜。这笔账算下来，选它。

### 让大模型把结构重排回来

方案定了，先在对话窗口里手工验证一遍，看看这条路走不走得通。

打开 DeepSeek，开一个新对话，不开联网搜索，不用专家模式，就用快速模式。然后粘一段提示词进去：

```text
下边这份 markdown 文档是从保险条款 PDF 解析出来的。由于 PDF 的各个小节是表格形式存在，
所以解析时出现了错乱。你分析内容，帮我转为格式正确的 markdown 标题，特别是编号要正确；
标题等级要从一级开始逐层增加；目录和文档名不计入标题等级；输出结果不包含正文开始之前的部分；
结果只包含 markdown 正文，不要解释，不要代码围栏，不要修改保险条款。
```

这段提示词里每一句约束都不是凑数的，都是在堵一个具体的坑：

- **"特别是编号要正确"**——解析错乱最典型的表现就是编号层级错位，本该属于下一级的内容被提到了上一级，模型得按语义把编号重新捋顺；
- **"标题等级要从一级开始逐层增加"**——不能让文档一上来就是三级标题，那样后面的结构感知切分就找不到顶层边界；
- **"目录和文档名不计入标题等级"**——PDF 开头的目录页长得极像标题，如果被当成标题，切分时会多出一堆假父块；
- **"输出结果不包含正文开始之前的部分"**——目录、封面、免责声明这些前置内容对问答没用，留着只会污染知识库；
- **"不要解释、不要代码围栏"**——要的是能直接落盘的 markdown 正文，不是一段"好的，以下是整理后的内容"；
- **"不要修改保险条款"**——这是红线。模型只许动结构，不许动内容。

然后把那份解析错的 markdown 原文，用三个反引号包起来贴进去。围栏的作用是告诉模型"这是一整块文档"，别把它当成指令去执行；原文里万一有像指令的句子，也不会被误当成要求。

发出去，速度很快。输出的结果：一级标题、二级标题、编号层级，全都对上了。刚才那份连井号都没有的文本，现在是一份结构规整的 markdown。这就是我们要的效果——不动内容，只把骨架装回去。

但紧接着发现第二个问题：它没写完。

页面上出现了"继续生成"的按钮，输出停在 7.2 附近。可这份条款是星辰守护 B 款，不止到 7.2——它有第八章，而且第八章特别长，最后几十页全是第八章的疾病定义，后面还有第九章。

这不是模型偷懒，是 `max_tokens` 到顶了。所有大模型都有这个参数，它控制一次生成最多能吐多少 token。默认值通常不大，可能只有 1K 或者 2K；输出写到 7.2 的时候正好撞上这个上限，于是后面的内容就生成不出来了。所以你看到的"戛然而止"，其实是硬截断。

> **定义**：`max_tokens` 是单次生成输出长度的上限，按 token 计。它限制的是"这次能说多少"，不是"模型懂多少"；撞上上限的表现就是话说到一半停住，且不报错。

顺便说一句，第八章那几十页的疾病定义，严格讲不算条款的一部分，真截在 7.9 也能用。但"能用"和"知道为什么停"是两回事——你得先判断出这是上限截断，而不是解析又坏了，否则后面调参会一直找不到方向。

手工验证完，就得让代码来做，总不能每生成一份都跑来粘一次。代码结构很简单：一段提示词（就是上面那段）、初始化模型、调模型。

初始化的时候传 DeepSeek 的 API Key，关掉思考模式；`max_tokens` 这个参数可以先不指定，先跑一轮看效果。调用的方式是先传系统提示词，再把用户提示词——也就是 `result.markdown`——传进去，让模型处理。返回的结果就是最终可用的 markdown。

第一版先不传 `max_tokens`，跑一遍看看效果。因为用的是阻塞式调用，不像页面上流式输出那样一边生成一边显示，所以会慢一些，得等。等它回来，结构是对的，一级二级三级四级标题都在，但内容同样不完整——原因和页面上那次一模一样，还是上限。

把 `max_tokens` 调大，再跑，输出就完整了。

于是"文档加载和解析"这一步的最终形态是两道工序：先用 MinerU 把 PDF 解析成 markdown，再用大模型把结构调优。先加载，再优化——这两步不是这一份文档的特殊处理，而是以后每份条款进来都要走的固定流程，它后面会作为流水线上的一个组件被固定下来。

> **承前启后**：上一节讲完「父子块结构与条款文档的解析流水线」，下一节接着讲「父子块切分与入库」。

## 父子块切分与入库
> 对应块：BLK40 | 覆盖分集：P154-P156 | 块标题（分集名）：《知识库构建：父子块切分与入库》

文档已经解析成 markdown 了，接下来这一步就轮到切它。

切分不是随手拿把刀乱剁。前面已经把思路定下来了：先用 markdown 结构感知切分，按章节把整篇切成一块一块，得到的是父块（parent chunk）；再把父块交给递归切分，切成更小的子块（child chunk）。

这条规矩再钉一遍：一个父块至少要有一个子块。如果父块本身的大小没超过我们设的上限，也就是 `chunk_size`，那这个父块就原样复制一份，当作子块——这时候子块和父块的内容一模一样。为什么要留这么一份"复制品"？因为将来要往向量库里扔的是子块，向量库里必须有它这一条，父块多大都得有个子块跟它对应上。反过来，父块要是超了 `chunk_size`，它就会被递归切成多个子块。所以"一个父块至少一个子块"这句话，两头都成立。

思路清楚了，剩下就是动手。说句实话，这段代码我都不太想写——逻辑已经摊开在桌面上了，照着搭就行。

### 两把切分器先就位

这里需要两个文档切分器：一个是 markdown 的，一个是递归的。这两个如果不会写，不用慌，直接回到之前讲文档切分的那一节，把结构感知和按长度递归那两段代码拷贝过来就行。

结构感知切分器就是 `MarkdownHeaderTextSplitter`，它要传的是"按几级标题切"。之前演示的时候我们只切到三级，这次多给了一级，切到四级。为什么？因为我们的文档里确实出现了四级标题，甚至还有五级。切到四级就够了，不用再往下切——再深就没必要了，剩下的细碎长段落交给递归切分去处理，它本来就更擅长干这个。你要是想切得更细也没问题，再加一个 `H5` 的井号对就行。

递归切分器这边，块大小设成 500，重叠 `overlap` 设成 50，也就是 10% 左右。切的时候每 500 作为一块；某一块超过 500，它就从中间找地方断开。怎么找？默认先按段落切，没有段落再按换行，没有换行按句号，句号没有再按分号，分号没有最后按逗号。这个顺序是有讲究的——尽量在语义边界上下刀，避免把一句话劈成两半。

```python
parent_splitter = MarkdownHeaderTextSplitter(   # 结构感知：按 H1–H4 切，先去掉标题头
    headers_to_split_on=[("#", "H1"), ("##", "H2"), ("###", "H3"), ("####", "H4")],
    strip_headers=True,
)

child_splitter = RecursiveCharacterTextSplitter(   # 递归切分：每块 500，重叠 50（约 10%）
    chunk_size=500,
    chunk_overlap=50,
)
```

### 标题头到底去不去

`strip_headers` 这个地方我给了 `True`。`strip` 是去掉，`headers` 是标题头，合起来就是把头去掉。

有人立刻会反问：不对啊，我们前面反复强调这个头很重要——在一块内容里，头就是它的身份，你把头去掉了，我怎么知道这一块是在讲什么？这个质疑完全合理，理论上头确实不该去。

那为什么还是去了？你想，如果保留头，这个头会连着正文一起成为一个块，然后我们在这个基础上再切成更小的子块：

```text
保留标题头去切：
  [ 头 + 正文A + 正文B + 正文C ]  →  [头+A] [B] [C]      只有第一块有头

先去掉头，再切：
  [ 正文A + 正文B + 正文C ]       →  [A] [B] [C]          三块都没头

从 metadata 取回 H1…H4，逐块拼回：
                                  →  [头+A] [头+B] [头+C] 三块都有头
```

一个父块切成三块，头只留在第一块里，后面两块光秃秃的——这就不合理了。我们要求的是每一个子块都带着头。那最省事的做法就是：一上来先把头干掉，让结构感知切出来的正文里根本没有头；等切完子块，再给每一块单独把这个头拼上去。这样三块就都有头。

那头都去掉了，将来还知道头是什么吗？记得结构感知切分干的另一件事——它会把 H1、H2、H3、H4 全都塞进 `metadata` 里。头并没有丢，只是从正文搬到了 `metadata`。所以整个动作是：切的时候从正文里去掉，切完再从 `metadata` 里取出来，拼回每个子块。

> **提示**：这里的取舍可以记成一句话——头不是不要，是"晚一点给、给每一份"。切分阶段去掉，是为了避免只有第一块继承到它；回填阶段补上，是为了让每一块都能独立被检索到、独立被读懂。

### 第一刀：切出小节，一节一个父块

两个切分器就位，开始切文档。第一刀用结构感知切分器，切的是那份优化好的 markdown，把它切成大块。切出来是什么？是一个一个的小节——这是一节，那是另一节，按章节一节一节地切下来。

调用 `split_text(markdown)`，结果叫 `sections`。这里的每一个 `section` 都是一个 `Document` 对象：`metadata` 里是 H1、H2，如果有三级四级就继续往后加；`page_content` 是原文内容，而这份内容里已经没有标题了——正好符合我们的预期。

接下来对每个小节做两件事：先封装成父块，再切成子块。

父块的类在搭 RAG 的 model 时就写好了，它对应数据库里那张表，字段有 `id`、`product_id`、`clause_name`、`section_path`、`content`。现在要做的就是把一个 `Document` 装进这个类：

```python
parent_chunks = []

for section in sections:
    section_path = list(section.metadata.values())

    parent_chunk = ParentChunk(
        id=uuid4(),
        product_id=product.id,
        clause_name=product.clause_name,
        section_path=section_path,
        content=section.page_content,
    )
    parent_chunks.append(parent_chunk)
```

逐个字段说：

- `id` 的类型是 UUID，用 `uuid4()` 现场生成一个。这是 Python 内置的能力，不用自己写算法。
- `product_id` 取 `product.id`。`product` 是前面查出来的那条产品记录，直接从句柄上取。
- `clause_name` 是条款名称，同样在 `product` 上，`product.clause_name`。
- `section_path` 是一个字符串列表，装的就是"这是第几章第几节"那条路径。它来自 `section.metadata`——字典里每个键是 `H1`、`H2` 这样的名字，我们要的不是键，是值，所以 `list(section.metadata.values())`，把值掏出来塞进列表。
- `content` 就是 `section.page_content`，这个小节的正文。

一个父块封装好就 `append` 进 `parent_chunks`。一个 `Document` 变成一个父块，一圈下来父块列表就有了。

顺带一句：如果你愿意，也可以把 `section_path` 拼进 `content` 里，这样父块自己的内容也带着标题。做不做都行，我这里没拼。

### 第二刀：传 section，切出子块

父块有了，接下来拿递归切分器切子块。这里有两个坑，必须先说清楚。

第一个坑：用 `split_text` 还是 `split_documents`？

`split_text` 切的是文本，传字符串进去，出来的是字符串列表；`split_documents` 切的是 `Document` 对象，传 `Document` 列表进去，出来的是 `Document` 列表。这里我建议一律用 `split_documents`，理由很实在：将来往向量库里存，调的是 `add_documents`，它接收的是 `Document` 集合，不是文本集合。你用 `split_text` 拿到一堆字符串，后面还得手动一个个转成 `Document`；直接用 `split_documents`，切出来就是 `Document`，拿到手就能存。

第二个坑更要命：传谁进去切？

要传 `section`，不能传 `parent_chunk`。`parent_chunk` 是我们自己封装的表对象，`section` 才是 `Document`。`split_documents` 要的是 `Document`，你给它一个表对象，它切不了。而且 `parent_chunk.content` 本来就来自 `section.page_content`，切 `section` 就等于切父块，内容一致。

所以写法是手工造一个列表，把当前这个 `section` 放进去——因为是"遍历一个、切一个"，每次列表里只有一个元素。它本身是支持批量的，你扔一个长列表进去，它一次就能切完；只是我们这里按父块逐个处理，所以一次只放一个：

```python
child_chunks = child_splitter.split_documents([section])
```

> **易错点**：切分 API 是"传什么切什么"——`split_text` 传字符串得字符串列表，`split_documents` 传 `Document` 列表得 `Document` 列表。这一条记死了，你就不会出现"切完还得手动转回 `Document`"这种返工。

### 子块的四个字段，有两个只能塞进 metadata

子块的结构前面分析过，不记得就回头翻一眼：子块要往向量库里存，它需要四个字段——自己的 `id`、父块的 `parent_id`、子块内容、还有用来区分不同产品的 `product_id`。

`id` 好办，Milvus 那边开了 `auto_id`，让它自己生成。这里说的是子块；父块的 id 是我们自己用 `uuid4()` 生成的，两码事，别混。

剩下三个要装进 `Document`。问题来了：`Document` 只有三个字段——`page_content`、`metadata`、`id`。这个类不是我们写的，是 LangChain 生成的，你没法给它加自定义字段。所以 `parent_id` 和 `product_id` 想放进去，只有一条路：塞进 `metadata`。

于是切之前先做一件事——把 `section.metadata` 整个覆盖掉：

```python
section.metadata = {
    "parent_id": parent_chunk.id,
    "product_id": product.id,
}

child_chunks = child_splitter.split_documents([section])
```

原来的 `metadata` 里是 H1、H2 这些标题，不符合子块的要求，直接换掉。换成 `parent_id` 和 `product_id` 之后再切。

为什么覆盖一次就够，不用给每个子块单独设？因为切分时切出来的每一个小 `Document` 都会继承父 `Document` 的 `metadata`——父亲长什么样，儿子就长什么样。所以同一个父块切出来的所有子块，`parent_id` 和 `product_id` 天然一模一样；不同父块切出来的，自然就不一样。这正是我们要的效果。

### 切完的子块要把标题拼回去

切完了，但还没完。刚才把标题头从正文里干掉了，现在得还回去。每个子块的 `page_content` 里是没有标题的——从头切开，第一段没头，第二段也没头。所以要做一次拼接：把 `section_path` 用换行连成一个字符串，放到每个子块正文的前面。

```python
header = "\n".join(section_path)

for child in child_chunks:
    child.page_content = header + "\n" + child.page_content

child_chunks_all.extend(child_chunks)
```

`"
".join(section_path)` 会把 H1、H2、H3、H4 那些标题值按顺序用换行拼起来，得到一个完整的头部字符串；再和子块原本的 `page_content` 拼一起，重新赋回 `page_content`。这样每一块都是"头 + 体"，谁都不缺身份。

顺序不能错：先设 `metadata`，再切，切完拼头，最后才 `extend` 进总列表。中间任何一步提前，比如先拼头再切，头又会被切散，白干一趟。

最后往总列表里放，用 `extend` 不用 `append`。`append` 是加一个元素，而这里切出来的本来就是多个子块，得整体摊进去，`extend` 正好干这个。

### 切完先核对：数量与归属

跑一遍看结果。

`parent_chunks` 的长度是 54，`sections` 的长度也是 54——每个小节作为一个父块，对得上。子块最后切出来 69 个。

父块是 `ParentChunk` 对象，字段齐全；子块是 `Document` 对象，每一个都是。

重点看同一父块下的子块。随手挑一组：有三个子块的 `parent_id` 一模一样，它们都来自 1.4 小节"等待期"。等待期条款很长，超过了 500，所以被切成了三部分，而这三块的 `metadata` 也完全一样——都是 `product_id` 加 `parent_id`。

```text
1.4 等待期（父块，正文超过 500）
        |
        +-- 子块 1（头 + 等待期前段）  --+
        +-- 子块 2（头 + 等待期中段）  --+-- parent_id / product_id 三者完全相同
        +-- 子块 3（头 + 等待期后段）  --+
```

这就是父子块切分该有的样子：一个长父块生出三个共享同一个 `parent_id` 的子块。为什么 `metadata` 一定一样？因为切之前就把 `section.metadata` 设好了，切的时候儿子们继承父亲的 `metadata`，同一个父亲生的儿子当然共享同一份。

反过来说，这个"继承"也是我们要提前覆盖 `metadata` 的唯一原因——切分器不负责给你补字段，它只会照抄父亲的。父亲身上有什么，儿子就有什么；父亲身上没有的，儿子永远不会有。

### 子块进向量库

切完就该入库了：子块入向量库，父块入数据库。先看向量库这边。

这段代码简单得有点不像话，因为 LangChain 已经把路铺平了——有 `vector_store`，调一个 `add_documents` 就完事。前提是先把 `vector_store` 建出来，而建它之前得先有向量模型，所以顺序是：先准备 embedding 模型（用 Ollama 的就行，也可以换成阿里云），再准备 Milvus 的 vector store，最后往里塞子块。

Milvus 这边的配置项都眼熟，但有一个细节要注意——collection 的名字别沿用之前练习的那些，专业一点，叫 `insurance_collection`，就是保险业务的这个集合。

| 配置项 | 作用 |
| :--- | :--- |
| 向量模型 | 把文本转成稠密向量（Ollama，也可以换阿里云） |
| collection name | `insurance_collection`，这个业务的专属集合 |
| builtin function | BM25 转换函数，用来生成稀疏向量 |
| analyzer | 中文分词器 |
| vector field | 两个向量字段：一个稠密、一个稀疏 |
| connection args | Milvus 的连接地址 |
| auto id | `True`，让 Milvus 自动生成主键 |

> **提示**：`auto_id=True` 只针对子块——子块进向量库时不用我们填 id，Milvus 自己生成。父块的 id 早就用 `uuid4()` 生成好了，两者不冲突，也不要在一条链路上混着想。

配置齐了，最后一步就是把前面切好的子块往里一扔：

```python
vector_store.add_documents(child_chunks_all)
```

就这么简单。

有没有成功？打开浏览器进 Attu，刷新一下，多出来一个新的 collection，69 条。

先看 schema。这个 schema 跟我们一开始分析的应该完全一致：有 `pk`，有 `text`，有 `dense`，有 `sparse`，最关键的是后面这两个 id——`product_id` 和 `parent_id`。前面讲过，`metadata` 里的数据将来一定会被展开放进来，现在它就是这么做的，跟预期完全相符。有了这两个字段，将来就能按 `product_id` 和 `parent_id` 做过滤。

`product_id` 目前是没有索引的，你可以给它加，比如 inverted 索引，过滤效率会更快。这里我先不加，够用。

再看数据。文本里标题都带着——回填那一步没白做，每一块的正文前面都有 H1 到 H4 的标题路径。主键是自动生成的，后面依次是稠密向量、稀疏向量、`product_id`、`parent_id`。目前插进来的全是同一个产品，所以 `product_id` 完全一样；将来产品多了，这里自然就不一样了。

输个"等待期"试试，搜到了，还高亮了。排在前三的就是那三个子块——同一个父块切出来的三个儿子，全都命中了。有意思的是"等"和"期"也成了关键词：分词的时候它把"等待期"拆成了"等"、"期"、"等待期"三个词，所以三个词都拿去检索，命中的范围自然就宽了。

到这里，子块入向量库这一步就算彻底跑通了。

### 父块进数据库

父块不进向量库，进数据库。进数据库就得自己写增删改查，没有 `add_documents` 这种现成的了。

准备工作其实已经齐了：model 里有 `ParentChunk` 的表映射，数据库连接里有 session 工厂。缺的是一个 repository——按我们一贯的写法，凡是要落库的模块都单独写一个 repository 类。新建一个文件叫 `repository`，类名跟表走，叫 `ParentChunkRepository`（RAG 这块对应的表就是 `parent_chunk`，名字干脆统一）。

类的骨架就两件事：构造函数接一个 session，攥在手上；然后是具体方法。

```python
class ParentChunkRepository:
    def __init__(self, session: AsyncSession):
        self.session = session

    def add_all(self, parent_chunks: list[ParentChunk]) -> None:
        self.session.add_all(parent_chunks)

    async def delete_by_product(self, product_id: int) -> None:
        await self.session.execute(
            delete(ParentChunk).where(ParentChunk.product_id == product_id)
        )
```

`add_all` 收的是什么？就是切完的那一堆父块——`parent_chunks` 本来就是 `list[ParentChunk]`，切完直接传给我，我直接往库里扔。`session.add_all` 接收的刚好就是个列表，所以里面只有一行，代码就写完了。

没有完。除了新增，还要写删除。

为什么要删？两种场景。一种是我们某个产品下架了，库里的块得清掉；后来它又上架了，得重新插。另一种更常见：产品条款发生了变更——今天这个条款叫这个名字，明天发现有问题，改了口径。这种情况下你直接往库里插，旧的不走、新的又来，库里就有两份互相打架的条款。所以必须先删旧的，再插新的。

按什么删？按 `product_id`。因为变更这件事是整个产品维度的，跟这个产品有关的所有 chunk 都得清掉，不能只清某一条。

对应的 SQL 就是这么一句：

```sql
DELETE FROM parent_chunks WHERE product_id = ?
```

那代码怎么写？这里有个选择：`session.delete` 是删一个对象的，我们要带条件删一堆，用不了它。得用 SQLAlchemy 的 `delete` 语句配 `execute`——`delete` 从 `sqlalchemy` 里导进来。

用 ORM 写条件删除，记住这三句对应关系就够了：表对应类，字段对应类的属性，数据对应类的对象。所以"从 `parent_chunks` 这张表里删掉 `product_id` 等于某个值的记录"，在代码里就是 `delete(ParentChunk).where(ParentChunk.product_id == product_id)`，再交给 `execute` 执行。

> **易错点**：`session.delete(obj)` 和 `delete(Model).where(...)` 是两套东西。前者按对象删一条，后者按条件删一批。要批量清某个产品的块，只能用后者。

这两个方法写完，父块入库的通路就有了。

### 联调：先删再插，一路踩着坑过去

回到 notebook 里测。要建 repository 对象，先得拿 session；session 从 `infra.database` 的 session 工厂来。

```python
async with AsyncSessionFactory() as session:
    await session.begin()
    repo = ParentChunkRepository(session)
    await repo.delete_by_product(product.id)
    repo.add_all(parent_chunks)
```

先删，再加。这个顺序不能反。

第一次跑，报错。原因是异步的——`delete_by_product` 里用了 `session.execute`，它是异步方法，调用时得 `await`，我写的时候忘了。补上 `await` 再想一遍：`add_all` 里是 `session.add_all`，它不是异步的，所以这里不用 `await`。别看着同一个类里的方法就无脑全加 `await`——加错了同样跑不起来。

改完再跑，还是不生效。这就尴尬了：因为这个类是在 `repository.py` 里，notebook 里 import 的是启动时加载的那份，改了源文件不 restart kernel 就不生效。而一 restart，前面那一整段全得重跑：查产品、解析文档、切分……光解析就要等三四十秒。为什么这么慢？`max_tokens` 设得长，模型要输出的内容就长，输出越长越慢。

> **提示**：测这种多阶段的流水线，先把中间产物落下来。优化完得到的那份 markdown，单独存一份（或者直接写在 notebook 的一个 cell 里），下次从这份 markdown 开始切，就省掉了重新解析这一大段等待。这一步不省，每改一行代码都要多等半分钟。

重启、重跑、切分，全都重来一遍。向量库已经入过了，跳过，直接存数据库。

又报错了，而且这个错有点长。还是那句话，滚到最下面看解释——它说 `parent_chunks` 这张表里没有 `clause_name` 这一列。

回数据库看表，表结构里果然少了一个字段：`clause_name` 没加。手工补上，类型选 `varchar`，长度给 500——条款名称，一般不会长到哪去，500 够了。保存。

再跑一次，一下就成功了。

这里值得停一下：model 里写了 `clause_name`，数据库表里没有这一列，ORM 一 insert 就找不到列，直接报错。表结构和 model 必须严格对齐，这是入库前值得专门核对一遍的东西。

刷新数据库看数据：全部插进来了，条款名称有，`section_path` 有，`content` 也有，一个字段都不缺。

### 向量库同样得先删再添

刚说完父块要先删再插，立刻有同学问了一句很到位的话：数据库要清旧的，那向量库里的子块呢？是不是也得先删再添？

对，也得。这个问题问得好，因为它戳的是同一件事的两半：产品条款一变，数据库里的父块删了，向量库里的子块还留着，检索时照样会把已经作废的条款捞出来——这比检索不到更糟，模型会拿过期的条款去回答用户。

那怎么删？`delete` 平时我们都是按 id 删，可这里的子块 id 是 `auto_id` 自动生成的，我们手上根本没有。这时候换个参数：它除了接收 id，还接收 `expr`，也就是过滤表达式。过滤条件的写法和 SQL 的 where 一样，你可以写任意条件。

我们要删的是某一个产品的所有子块，而 collection 里正好有 `product_id` 这个字段，那就按它删：

```python
expr = f"product_id == {product.id}"
vector_store.delete(expr=expr)
```

注意这里要写成 f-string，把真正的 `product.id` 拼进去，不能写死成 `1`——写死的那次能跑通，只是因为当前查出来的产品 id 恰好是 1。

> **提示**：表达式的值类型要和字段类型对上。`product_id` 在 collection 里如果是字符串字段，值就得加引号；如果是整数，就直接写数字。类型不匹配时表达式会报错或匹配不到。

删一下，返回 `True`。回数据库刷新，数据没了。再执行一次插入，数据又回来了。先删再加，闭环。

到这儿，子块入向量库、父块入数据库，两个方向全写完了，知识库构建的整条 pipeline 我们从文档解析一路走到了两份存储：

```text
markdown（优化后）
      |
      | MarkdownHeaderTextSplitter（切到 H4，strip_headers=True）
      v
sections：54 个 Document（metadata 存 H1…H4，正文无标题）
      |
      +--- 封装 ParentChunk ---------------> 数据库 parent_chunks（54 条）
      |
      +--- RecursiveCharacterTextSplitter（500 / 50）
                    |
                    v
             子块 69 个（回填标题头）
                    |
                    v
             向量库 insurance_collection（pk / text / dense / sparse / product_id / parent_id）
```

读这张图抓住一件事：父块和子块从同一批 `section` 分出去，各自进各自的库；连接它们的是子块 `metadata` 里那个 `parent_id`，将来检索到子块，靠它就能把对应的父块捞回来。这就是"父子块"这个名字的落点。

## 从零散代码到一条流水线：知识库构建与检索设计
> 对应块：BLK41 | 覆盖分集：P157-P159 | 块标题（分集名）：《知识库 Pipeline 与检索设计》

前面我们已经用 notebook 把整条流水线模拟过一遍：加载、解析、切分、存向量库、存数据库，每一步单独跑通了。接下来要做的，是把这些散落的代码组装成一条真正的流水线。为什么要多这一步？因为等会儿要添加的文档不止一个——手上有一大堆保险条款都要进知识库，把流程封装起来才可复用。

### 为什么要组装一条流水线

在 notebook 里，每一步都是手动串起来的：先查到一个保险产品，再顺着它找到条款文件，然后解析、切分、写向量库、写数据库。验证阶段这样最灵活，改一行就能重跑。可一旦要正式建库，问题就来了——要添加的文档不止一个，手里是一大堆保险条款，十几个产品，每个都要走一遍同样的动作。

所以要把前面讲的加载、解析、切分、存向量库、存数据库的代码组装成一条流水线。组装的目的不是让代码看起来整齐，而是让它可复用：写一次，之后每个产品都拿同一套流程去跑，不用再复制粘贴一遍。

代码落在 `app/rag` 包下，新建一个 `pipeline.py`。RAG 相关的东西都收在这个包里，流水线自然也该住在这里。

### 四个步骤，和一个绕不开的 product

先定义一个类，叫 `RAGPipeline`，整个文档处理的流程都放在这个类里。对外只暴露一个入口方法，用来吃进一个产品、把它的条款送进知识库。这个方法我一开始顺口叫 `ingest`，落到笔记里统一成了 `index`——名字不同，干的事一样。

方法里就是四步：加载并解析文档、切分文档、存入向量库、存入数据库。按这个顺序一一去做就完了。

为什么入口参数是 product？回头看看 demo：一上来先查询到一个保险产品，后面所有操作都是基于这个 product 展开的——通过它的条款名找到对应的文件，找到文件才开始加载、解析。也就是说，product 是整条链路的起源，后面的每一步都从它派生。所以 `index` 接收一个 product；至于这个 product 从哪里来，先不用管，那是调用方的事。

```text
                  product
                     │
                     ▼
        ┌────────────────────────┐
        │ 1. 加载并解析文档       │  MinerU → Markdown
        └────────────────────────┘
                     │
                     ▼
        ┌────────────────────────┐
        │ 2. 切分文档             │  先父块，后子块
        └────────────────────────┘
                     │
                     ▼
        ┌────────────────────────┐
        │ 3. 存入向量库           │  子块 → Milvus
        └────────────────────────┘
                     │
                     ▼
        ┌────────────────────────┐
        │ 4. 存入数据库           │  父块 → 关系库
        └────────────────────────┘
```

读图：四步严格串行，上一步的产物就是下一步的输入；整条链路的起点只有一个 product。把类骨架摆出来，结构就是这样：

```python
class RAGPipeline:
    def __init__(self, vector_store: Milvus):
        self._vector_store = vector_store
        self._mineru = ...                  # 文档解析客户端，只建一次
        self._llm = init_chat_model(...)    # 文档优化用的大模型
        self._md_splitter = ...             # Markdown 切分器，切父块
        self._recursive_splitter = ...      # 递归切分器，切子块

    async def index(self, product):
        markdown = self._parse_document(file_path)                 # 1. 加载并解析
        parent_chunks, child_chunks = self._split_documents(       # 2. 切分
            markdown, product
        )
        self._save_child_chunks(child_chunks)                      # 3. 存向量库
        await self._save_parent_chunks(parent_chunks, product)     # 4. 存数据库
```

骨架里能看出一个关键取舍：构造函数的入参只有 `vector_store`，其余客户端都在内部建。为什么是它特殊，下面单独说。

### 构造函数：谁的初始化该只做一次

写解析的时候第一反应是 `MinerU()` 直接写在 `index` 里。不行——这意味着每当有人来做一次处理，都要重新创建一个 MinerU，没必要吧。所以放到构造函数里：`self._mineru = MinerU(...)`。前面加一个下划线表示私有，类外面不该伸手去用。

优化文档的大模型同理。加载完文档要用模型把内容优化一遍，初始化模型这件事也不能每次加载都做一遍，于是 `self._llm = init_chat_model(...)` 也放进构造函数。这样 pipeline 创建那一刻，所有客户端就都准备好了，下面直接用 `self._llm.invoke(...)` 拿到优化后的 markdown。

切分器也一样。这里有两个：一个 Markdown 切分器负责切父块，一个递归切分器负责切子块。两个都加 `self._`，都在构造函数里一次性建好。它们本身不持有状态，更没理由每次切分重新 new 一个。

最后是向量库。它虽然同样不该在 `index` 里创建，但也不该在构造函数里创建。原因不是"重"，而是"共用"：vector store 不只用来写数据，将来检索也要用它查数据。如果在 pipeline 里初始化，等检索那边要用的时候还得再建一个，等于同一个东西创建了多份，没有必要。

所以构造函数改成接收一个 `vector_store`，类型限定为 Milvus：我不管你从哪来，反正你得给我传一个能用的进来，我拿着用就完了。将来外部只初始化一次，写库和检索共享同一个实例。

| 组件 | 初始化位置 | 原因 |
| :--- | :--- | :--- |
| MinerU 解析客户端 | 构造函数，私有成员 | 重客户端，不能每次 ingest 都重建 |
| 优化用大模型 | 构造函数，私有成员 | 每次加载都建一次模型没有必要 |
| Markdown / 递归切分器 | 构造函数，私有成员 | 无状态工具，一次建好反复用 |
| 向量库 | 构造函数外，由调用方传入 | 写库与检索共用同一个实例，避免重复创建 |

### 文件路径：别再数 ../..

解析代码从 notebook 搬过来，路径那一行得改。notebook 里写的是 `../../` 这种相对路径，在 pipeline 里执行时位置变了：从 `app/rag/pipeline.py` 往上两级，好像也能指到项目根，看着"也对"。但这么写不专业——文件多挪一层，路径就断了，而且读代码的人得替你数层级。

我们其实早就准备过工具。`settings` 里有一个获取项目根目录的 `app_root`，当时只是简单提了一嘴：

```python
app_root = Path(__file__).parents[2]
```

它是从 `app/core/settings.py` 出发，向上找两级：一级到 `app`，再一级到项目根。既然如此，直接沿用它就行。把 `app_root` 和 `settings` 一起从 settings 模块导进 pipeline，路径就可以写成一段一段的拼接：

```python
file_path = app_root / "data" / "RAW" / "KB" / product_name
```

`Path` 对象重载了 `/`，每加一个斜杠就是往下拼一层，这是 pathlib 的特殊语法。嫌中间段数多，也可以把连续几层写成一段字符串再拼，效果一样——`/` 本来就是干拼接这件事的。这样写出来的路径跟当前文件在哪无关，永远从项目根算起。

### 把一大坨代码拆成四个方法

把解析、切分、入库的代码原样粘进 `index`，代码量会变得非常变态：一个方法里几百行，四件事糊在一起，读的人根本看不出流水线在哪。

办法很直接：把加载解析、切分、存向量库、存数据库四个动作分别抽成四个方法，`index` 里只留四次调用。

抽第一个的时候是手动做的：把解析那段剪切出来，定义一个 `_parse_document(file_path)`，把代码粘进去，末尾把 markdown `return` 出来；原来的位置改成一行调用，`markdown = self._parse_document(file_path)`。切分同理，导好 `Document`（langchain 里的）和 `uuid` 的包，把切分器引用改成 `self._`，方法接收 markdown 和 product，返回父块和子块。

后面就不用这么费劲了。选中要抽的代码，右键 Refactor → Extract Function（快捷键 `Ctrl+Alt+M`），IDE 会问函数名，起个 `_split_documents`，预览里还能看到它推断出的返回值和参数。这里有个细节：它自动生成的返回值顺序是子块在前、父块在后，得手动改成父块在前、子块在后，调用处才不用反着接。

> **提示**：抽取函数不只是少敲几行。它把"这段代码属于流水线的哪一步"写进了方法名里，后面回头看 `index`，四行调用就是四步流程。

存向量库的代码只有两行，理论上也可以不抽。但还是抽了，叫 `_save_child_chunks`，这样每一步都有名字，结构清晰，一眼知道在做什么。子块入库之前先删后增：把该产品上一版的旧块清掉，再写新的。笔记版在这里还多了一层判断——collection 存在才删，不存在就直接建。

存数据库那段照搬事务代码：开启事务，先删旧块，再添新块。这个方法要加 `async`，因为数据库操作是异步的；同样 `Ctrl+Alt+M` 抽成 `_save_parent_chunks`。

最后补两件收尾的事。一是把删除方法的名字对齐成 `delete_by_product`，按产品删，语义直接。二是加一个 `close`，关掉 MinerU 客户端——它是个比较重的客户端，项目关闭时应该把它关掉，不能一直挂着。

到这里，`index` 里只剩四行调用，和开头那张四步图完全对得上：加载解析走第一行，切分走第二行，存向量库走第三行，存数据库走第四行。这就是我们说它"符合流水线"的意思——方法体本身就是流程图的文字版。

### 这条流水线会在什么时候被调用

写完之后自然会有个问题：这条 pipeline 到底有什么用，什么时候用？其实它的作用有两个。

第一个作用是作为初始化脚本被调用。项目上线之前，要把目前所有的保险产品对应的条款都过一遍 pipeline，完成知识库的初始化。这是一次性任务：上线前做一次，把现有产品全部放进知识库就够了，不需要反复执行。所以等会儿只需要写一个一次性的脚本。

第二个作用是增量更新。上线之后，大多数情况下保险产品很长一段时间都不会变更，那就不需要动知识库。但时间一长，总会有新产品上架，或者老产品的条款被更新。这种情况下原有的知识库数据就旧了，不可用了，需要再调一次 pipeline，把这些新增或被更新的产品条款重新处理，把最新的条款信息更新进知识库。

| 用法 | 触发时机 | 执行频率 |
| :--- | :--- | :--- |
| 初始化 | 项目上线前 | 一次性 |
| 增量更新 | 产品新增或条款修改时 | 不定期，可能多次 |

增量更新这个任务跟保险产品的新增、修改业务是绑定的——业务发生时就该触发它。目前我们还没有做这些业务，所以先放着，将来做到相关业务时再回来接上。真接起来也不复杂，发现新增或修改了，调一下 pipeline 就完了。最关键的代码已经实现了，剩下的只是触发时机。

当前阶段先做第一件事：定义初始化脚本，一次性把项目里所有保险条款交给 pipeline 处理，完成知识库构建。

### 让 AI 来写那个一次性脚本

这个脚本要做的事不止"调一下"那么简单，拆开是五件：

1. 初始化 embedding model，也就是向量化模型；
2. 初始化 vector store，也就是 Milvus——有了向量模型才能创建它；
3. 初始化 pipeline——它需要 vector store，所以必须排在第二步之后；
4. 调 product service 的 `list_products` 方法，查询所有 products；
5. 遍历查到的产品，逐个调用 pipeline 的 `index`，生成知识库。

顺序不能乱：模型先于向量库，向量库先于 pipeline。第四步之后必须遍历，不能只调一次——`index` 一次只处理一个产品。notebook 里我们一开始查了一批产品，但只处理了其中一个；要批量处理所有产品，就得把 products 逐个扔给 `index`。

理论上，照着 notebook 里怎么初始化向量模型、怎么创建 vector store、怎么建 pipeline，这段脚本大家应该能自己写出来。不过我们一直在讲 AI 编程，今天就让 AI 来写。

提示词要交代清楚几件事：我已经在 `app/rag` 包下写好了 RAG 的 pipeline；请在 `scripts` 下写一个脚本，叫 `index_rag.py`；具体可以参考 notebook 下 day09 的 `01_rag_pipeline` 文件，那里有完整的初始化流程；脚本要依次完成上面五步，其中查询产品调 product service 的 `list_products`。

> **提示**：参考文件这一句不能省。不告诉它去看哪份现成代码，AI 很可能自己另起一套写法，跟你项目里的结构对不上；指了参考，它就会照着已有的初始化方式来写。

`scripts` 这个目录有一点要注意：它是目录，不是包。它不属于项目代码，凡是这类非项目代码的辅助脚本，都统一放成普通目录，不要加 `__init__.py` 把它变成包。

动手的时候还有两个小插曲。一是创建目录时名字拼错了，敲成了别的单词，还好检查了一下改回 `scripts`。二是第一次跑的时候 DeepSeek 的 API key 填错了，AI 没法正常处理，停下来改好 key 再重试。这类事情在企业里也常见，工具没问题，配置错了而已。

重试之后，AI 会先查看相关文件、了解现有代码结构和用法，然后请求创建文件的许可，再请求执行语法检查的许可。一路允许就行，甚至可以选"允许所有文件操作""允许所有命令"，省得每次点。到公司里跟 AI 交互，做得最多的事可能就是点许可——听着夸张，流程确实是这样。剩下的时间就是泡杯咖啡等着。

生成完之后必须自己审一遍。这个脚本的结构是：`main` 进来先初始化 Ollama 的 embedding，再按之前的代码初始化 Milvus vector store（collection 对得上），切分器等配置跟原来完全一致，读取 settings，初始化 pipeline；然后用 SQLAlchemy 的 session factory 拿到 session，创建 service，查询 products，最后 for 循环逐个调 pipeline。整段代码非常好懂，就是 notebook 流程加了一层循环。

有个细节值得一提：我在提示词里把方法名说成了 `list_products`，AI 看完代码后指出实际叫 `list_product`，并按真实的签名写了。它能自己发现这种不一致，确实挺智能。

跑起来之后，输出是：RAG pipeline 初始化完成，查询到 12 个产品，正在构建第一个产品"达尔文宝贝计划"。剩下的就是等它把 12 个产品的条款全部处理完，知识库构建这一步就结束了。

### 检索为什么先要重写用户的问题

知识库建好，接下来是检索。我们之前分析过 RAG 的两种模式：two step 模式和 agentic 模式。项目里用的是 agentic 模式——把 RAG 的检索流程封装成一个工具，交给 agent，由 agent 自己判断要不要检索、该怎么检索。

所以接下来注意力就落在一个问题上：怎么封装一个 RAG 检索工具。

完整的检索增强流程里，用户提问之后的第一步不是检索，而是查询重写。为什么？因为用户的问题往往很口语，不是专业术语。比如他问"这个保险什么情况下不赔"，这就是一句大白话；直接拿这句话去搜，大概率很难搜到准确的信息。可他真正想问的是什么？是免责条款。既然我们和知识库都知道这件事该用"免责条款"来表达，就应该把用户的问题重写一遍，改成更适合检索的关键字。

> **定义**：查询重写，就是在检索之前把用户的原始问题改写成更贴近知识库表述、更适合检索的查询词或查询句。

这种重写需不需要我们自己写一套？不需要。只要用的是 agentic RAG——把 RAG 封装成工具、让模型来调工具并传入 query——模型就不会把用户的问题原样传给检索工具，它会先分析问题，再生成检索用的关键字。这个过程本身就已经实现了查询重写。

查询重写的方案其实很多：有基于关键字的改写，把口语问题压成检索词；有 HyDE，先让模型虚构一份答案或文档，再拿这份虚构内容去检索；还有 multi-hop，把复杂问题拆成几个子问题，分多跳去查。这三种都不用我们管——工具已经交给 AI 了，由它思考要不要调工具、调哪一个、传什么 query 进去。知道有这些方案，是为了在别人问起时说得出名字。

> **提示**：如果面试被问到检索增强的流程，第一步一定要答出查询重写。这一步在实际项目里可能是 agent 顺手完成的，但它确实是流程的一环，不能漏。

### 完整检索链路里，真正要动手的只有最后一小段

把整条检索增强的链路摊开，是这样：

```text
用户问题
   │
   ▼
[1] 查询重写            agent 分析问题，生成更适合检索的 query
   │
   ▼
[2] 混合检索            稠密检索 + 稀疏检索，两路并行
   │
   ▼
[3] 结果融合            RRF，把两路排序合成一份
   │
   ▼
[4] 重排                cross-encoder 对候选精排
   │
   ▼
[5] 召回子块            child chunk，里面带着 parent_id
   │
   ▼
[6] 按 parent_id 查父块  回关系数据库取完整上下文
   │
   ▼
[7] 父块交给模型        生成最终回答
```

读图：前四步是"找得准"的部分，后三步是"答得全"的部分；分界线在子块召回这里。

重写之后的查询可能是一句话，也可能是一组关键字，这不影响后面的处理。拿着它分别做稠密检索和稀疏检索：稠密走向量语义这一路，稀疏走词面匹配这一路，两路各有所长。两路结果要融合，用的是 RRF，把两份排序合成一份；融合完还要重排，用 cross-encoder 对候选逐条精算相关性，比单纯的向量相似度更准。重排之后，召回的是子块。

为什么召回的是子块？因为子块小，检索时更容易精准命中。但子块上下文不完整，直接丢给模型回答不够。所以子块里存了父块的 id，拿着这个 `parent_id` 回数据库查出完整的父块，再把父块交给模型——子块负责"找得准"，父块负责"答得全"。

这条链路上，大部分功能已经有人替我们做完了。稠密检索、稀疏检索、RRF 融合、重排，这一整套 Milvus 的 vector store 已经帮我们实现；查询重写由 agent 完成。真正留给我们的只有三件事：召回子块、根据子块查父块、把父块发给模型。

所以封装检索工具时，重心就放在这一小段上——前半部分直接调 Milvus vector store 就能拿到子块，我们要补的是从子块到父块的那一跳，以及最后把父块组织成模型能用的上下文。

> **承前启后**：上一节讲完「从零散代码到一条流水线：知识库构建与检索设计」，下一节接着讲「父块召回与 Retriever：把子块换回父块」。

## 父块召回与 Retriever：把子块换回父块
> 对应块：BLK42 | 覆盖分集：P160-P162 | 块标题（分集名）：《父块召回与 Retriever 实现》

前半截已经做完了：子块进了向量库，只要调 Milvus 就能把子块召回。所以现在真正要补的不是"搜"，而是"换"——拿到一个子块，从它身上取出 `parent_id`，再拿着这个 id 去数据库里把对应的父块换回来。

这个动作看着简单，但有几处不能想当然：一次召回不是一个子块，所以查父块不能写等号；数据库查回来的顺序跟召回顺序对不上，所以查完还得排回去；而 LangChain 交回来的 Document 里根本没有 `parent_id` 这个字段，它藏在 `metadata` 里。这几个坑，一个一个填。

### 先补最后一块拼图：按 id 批量查父块

子块的 `parent_id` 其实就是父块的 `id`。`parent_chunks` 这张表本来就有 `id` 字段，所以子块带着 `parent_id` 过来，天然就是一次按 id 的查询：

```sql
SELECT * FROM parent_chunks WHERE id = ?
```

但这里不能写等号。一次召回里可能召回很多个子块，这些子块的 `parent_id` 各不相同，拿到手的一定是一批 id，而不是一个 id。所以条件得换成 `IN`：

```sql
SELECT * FROM parent_chunks WHERE id IN (?, ?, ?)
```

语句有了，方法就能写。到 `repository` 里加一个函数：

```python
async def query_by_ids(self, ids: list[str]) -> list[ParentChunk]:
    result = await self.session.scalars(
        select(ParentChunk).where(ParentChunk.id.in_(ids))
    )
    return result.all()
```

参数 `ids` 是一个列表，列表里装的是字符串——因为我们的 id 是 UUID，UUID 在传递时就是字符串格式。函数名 `query_by_ids`，就是"按 id 批量查"。

顺着这几行看几个对应关系。`select(ParentChunk)` 里的 `ParentChunk` 是类，类对应表，所以这一句就等于 `select ... from parent_chunks`；`.where(ParentChunk.id.in_(ids))` 里的 `id` 是类属性，属性对应表字段，`in_` 对应 SQL 的 `IN`。查多条要调 `session.scalars()`，不能调只返回单条的 `scalar()`；`await` 拿到结果集，再 `.all()` 收集成列表，列表里装的是 `ParentChunk` 对象。

> **提示**：这几行要是自己写不顺，直接让 AI 按"根据 id 列表批量查询"生成一版，再对着字段名改，也比卡在这里强。

写完先测。开一个新的 notebook，把仓库和 session 工厂导进来：

```python
from app.infrastructure.database import AsyncSessionFactory
from app.rag.repository.parent_chunk_repository import ParentChunkRepository

async with AsyncSessionFactory() as session:
    repo = ParentChunkRepository(session)
    parents = await repo.query_by_ids([
        "从数据库里随手拷一条 id 过来",
        "再拷一条",
    ])
    parents
```

第一次跑，忘了写 `await`，拿回来的是个协程对象，什么也查不到；补上 `await`，两条记录整整齐齐地出来了。中间编辑器还弹了一个 "was never awaited" 的警告，明明已经 await 了——这种警告可以先放着，数据回来了就说明查询本身没问题。

### 换个文件，叫 Retriever

这段代码不短：召回、取 id、去重、查库、排序，全塞进原来的业务文件里会很难看。所以单开一个文件，叫 `retriever.py`。

`retriever` 这个词，`retrieve` 是取回、找回、检索的意思；`retriever` 除了"寻回犬"，就是检索器、召回器。我们做的正是检索召回这件事，拿它当类名正合适。

类名叫 `ParentChunkRetriever`——它取的是父块，名字里带 `ParentChunk`，一看就知道这个检索器最后吐出来的是谁。

这里顺带留一个用词习惯：类用名词，函数用动词。类叫 `Retriever`，里面的方法就把尾巴那个 `r` 去掉，写成 `retrieve`。一个字母的差别，词性从名词变成动词，读代码的人一眼分得清哪个是东西、哪个是动作。这种习惯值得养。

### 构造函数与 retrieve 的骨架

往类里写构造函数之前，有一个决定要先做：Milvus 是自己建，还是让人传进来？

答案跟 pipeline 那边一样——传进来。pipeline 也要用 Milvus，但它里面并没有自己创建，而是从外面接一个 Milvus 类型的 vector store，下面直接用。为什么？因为如果 pipeline 建一个、retriever 再建一个，两个人各建各的，就是重复创建。所以这里同样接收一个 vector store，构造函数只负责把引用记下来：

```python
from langchain_milvus import Milvus
from langchain_milvus import create_cross_encoder_ranker


class ParentChunkRetriever:
    def __init__(self, vector_store: Milvus):
        self.vector_store = vector_store
```

接着写召回函数。名字是 `retrieve`，异步函数，因为后面既要异步查向量库，也要异步查数据库。

参数怎么定？第一个必须有 `query`，这是检索的输入，没有它没法往向量库里查。第二个是 `k`，也就是最终返回的文档数量——这个值不要写死，让调用方传，`k` 是个 `int`。第三个是 `product_id`，也是 `int`，因为产品编号就是 1、2、3 这样的整数。

> **提示**：`k` 提前写死也行，`k=5` 直接钉在函数里，一样能跑，这就看你怎么设计。区别是写死之后换个场景要改源码，做成参数只改调用处。

整个方法要干四件事，顺序不能乱：

```text
query + product_id
        │
        ▼
① 混合检索：稠密 + 稀疏 → 重排 → top k 个子块
        │
        ▼
② 从子块的 metadata 里取 parent_id，并去重
        │
        ▼
③ 按这批 id 批量查 parent_chunks
        │
        ▼
④ 把父块按 ② 的顺序排回去
        │
        ▼
   有序的父块列表
```

上图就是 `retrieve` 的骨架：前两步在向量库和内存里完成，第三步落到关系库，第四步纯粹是内存里的重排。代码就按这个顺序往里填。

### 召回子块：还是那套稠密、稀疏加重排

第一步跟之前写过的一模一样，只是换了个位置调用。向量库里做检索的函数叫 `similarity_search`；想同时拿到得分，用 `similarity_search_with_score`；想不要得分，就直接 `similarity_search`。

但我们这里是异步函数，所以用它的异步版本 `asimilarity_search`。同步和异步两套接口都在，用哪套看调用它的地方是不是异步。

```python
child_chunks = await self.vector_store.asimilarity_search(
    query,
    k=k,
    fetch_k=10,
    expr=f"product_id == {product_id}",
    ranker=create_cross_encoder_ranker(query),
)
```

除了 `query`，剩下四个参数每一个都有说法。

#### k 和 fetch_k：初筛和终选是两回事

`k` 是最终返回的条数，得分最高的 k 条。

`fetch_k` 是初筛时每一路返回的条数。我们的检索是稠密加稀疏的混合检索，分初筛和重排两段：`fetch_k=10` 就是稠密返回 10 条、稀疏返回 10 条，这 20 条一起交给重排器，最后由 `k` 决定留几条。两者的职责不同，所以可以分开配——初筛管捞多少上来，终选管最后留几条。

> **易错点**：`fetch_k` 不是"总共取多少条"，而是每一路的条数。写成 `fetch_k=10` 时，实际进重排的是两路各 10 条，不是 10 条。

#### expr：不按产品过滤，条款就会串味

这个过滤条件不是可选项，是必须项。

向量库里不止一个产品的条款：`product_id` 为 1、2、3、4、5 的都在同一张表里。搜"等待期"的时候，如果不加过滤，1 号、2 号、3 号、4 号、5 号的条款会一起回来——这些产品确实都有等待期。

但用户问的是 1 号产品，你把 5 号、4 号产品的等待期端上去，这就不合理。所以必须按 `product_id` 过滤：

```python
expr=f"product_id == {product_id}"
```

#### ranker：重排器别忘了带

混合检索要做 rerank，`ranker` 这个参数一漏，重排这道工序就没了。重排器不是手写的，是用一个生成函数造出来的，函数叫 `create_cross_encoder_ranker`，它来自 `langchain_milvus`，不是别的包里的。

这个函数里有一个字段名很关键：重排的时候，它要把原始文档和查询条件一起发给重排模型，所以那个字段名必须跟文档里存文本的字段对上。我们的原始文档字段就叫 `text`，所以不用改。模型、provider 也都不用改。函数放文件上边还是最下边都行，放上边方便用。

还有一处用着别扭的地方：这个函数内部要的是 query 的列表，可我们检索永远只传一个 query。让调用方天天包一层列表不舒服，所以函数对外收一个字符串，在函数里手动包成列表——用的人只管传一句话。

到这里，稠密、稀疏、融合、重排全部走完，子块也召回了。这一整段是前面已经写熟的代码，重新走一遍只是把它挪进新类里。

### Document 里没有 parent_id 这个字段

下一步是从子块里取 `parent_id`。这里有个容易踩的地方：`asimilarity_search` 是 LangChain 的方法，它返回的是 `list[Document]`，不是数据库里那一行数据。

Document 只有三个字段：`id`、`page_content`、`metadata`。而向量库里的行是另外一套：`pk`、`text`、`dense`、`sparse`、`product_id`、`parent_id`。两边的对应关系是固定的：

```text
Milvus 行字段              Document
-------------------        --------------------------------
pk                --->     id
text              --->     page_content
dense / sparse    --->     只在检索打分时用，不进 Document
product_id        --->     metadata["product_id"]
parent_id         --->     metadata["parent_id"]
```

所以 `parent_id` 不在 Document 的第一层，它在 `metadata` 这个字典里面。要取它，得先拿 `metadata`，再从字典里 `get`：

```python
parent_ids = [child.metadata.get("parent_id") for child in child_chunks]
```

拆开看这个推导式：`for child in child_chunks` 是数据来源，`child.metadata.get("parent_id")` 是每一项的结果。遍历一遍，就得到了一个 parent id 的列表。

不习惯推导式，写成普通 `for` 循环一行一行 append 也完全一样，看你顺手。

> **易错点**：`page_content` 是文本内容，`metadata` 才是 `product_id`、`parent_id` 这些标量字段的家。要字段就去 `metadata` 里翻，别指望在 `page_content` 上点出属性来。

### 去重，顺手把顺序留住

拿到 parent id 列表之后先别急着查库，先问一句：这些 id 会不会重复？

会。两个子块完全可能来自同一个父块，它们的 `parent_id` 长得一模一样。重复的 id 拿去查库，查回来的父块也是重复的，返回给模型就是同一段话出现两遍。所以要先做去重。

老办法是用 `set`：先 `set(parent_ids)` 去掉重复，再 `list(...)` 转回列表。能用。

还有一个更省事的写法：

```python
parent_ids = list(dict.fromkeys(parent_ids))
```

`dict.fromkeys` 把列表里的每个元素当成字典的 key。字典的 key 天生唯一，重复的自动被吞掉，所以这一步本身就完成了去重；外面再套一个 `list(...)`，又变回列表。一行搞定。

> **提示**：`dict.fromkeys` 和 `set` 都能去重，差别在顺序。`set` 不保证顺序，`dict.fromkeys` 按元素第一次出现的顺序保留。这条差别在下一步很关键——后面要靠 `parent_ids` 的顺序把父块排回去，`set` 一过顺序就散了。

以前没这么去重过的话，可以记一下这个写法，它比 `set` 转 `list` 少一步，而且留序。

### 查库之前先挡一下空结果

去重完，拿着 id 列表去查父块。查父块的函数刚刚已经写好了，就在 `repository` 里，导进来直接用：

```python
from app.rag.repository.parent_chunk_repository import ParentChunkRepository
from app.infrastructure.database import AsyncSessionFactory
```

但要用 repository，就得有 session；要有 session，就得用 session 工厂：

```python
async with AsyncSessionFactory() as session:
    repo = ParentChunkRepository(session)
    parents = await repo.query_by_ids(parent_ids)
```

`async with` 负责开和关，出了这个块 session 自动收掉。这一段看着眼熟——刚才测 `query_by_ids` 的时候已经写过一遍了。

查之前补一句健壮性判断：

```python
if not child_chunks:
    return []
```

有没有可能一个子块都没召回？有可能。过滤条件卡得紧、这个产品压根没入库、或者 query 跟库里内容完全不沾边，都会返回空列表。空列表往下走，`parent_ids` 是空的，`IN ()` 这种查询也没意义，不如直接结束。这是笔记里补的逻辑，一开始写的时候漏了，补上更稳妥。

### 数据库查回来的父块是乱的

拿到 `parents` 之后，直接 `return parents` 行不行？

差一点意思。

召回的这批子块是有顺序的：按向量相似度得分排，重排器又重排过一遍，相似度高的在前、低的在后。所以 `parent_ids` 的顺序，本身就是"哪个父块更该被先看到"的顺序。

可数据库查询默认是按 id 排的。按 id 排，等于把刚才费力排好的相似度顺序整个打乱。返回给模型时，模型看到的是一堆乱序的块，哪段最相关它看不出来——我们前面做稠密稀疏融合、上重排器，费了那么大劲，最后一步把它排乱，前面的功夫就白费了。

> **结论**：顺序是检索结果的一部分，不是附带信息。谁把顺序弄丢，谁就得负责补回来。

怎么补？利用 `parent_ids` 本身有序这个事实：遍历它，每拿到一个 id，就从查回来的父块里取出对应的那一个，依次放进列表。走完，列表就是有序的。

问题是"按 id 从 `parents` 里找"不好找——`parents` 是个列表，只能线性扫。所以先把它变成一个字典，key 是父块的 id，value 是父块本身：

```python
parent_map = {parent.id: parent for parent in parents}
```

这是字典推导式：`for parent in parents` 是数据来源，`parent.id: parent` 是结果，冒号左边是 key，右边是 value。变成字典之后，拿 id 一查就中，不用扫。

然后按 `parent_ids` 的顺序从字典里往外取：

```python
parent_chunks = [parent_map.get(pid) for pid in parent_ids]
```

`for pid in parent_ids` 保证顺序，`parent_map.get(pid)` 保证按 id 取到对应的父块。两个一合，得到的就是按召回顺序排好的父块列表，直接 `return parent_chunks`。

> **提示**：笔记里的版本还多写了一个条件——只有 id 在字典里存在才放进结果，不存在就跳过。我没加。数据健康的话，查出来的 id 一定能在库里找到对应的行，不会出现取不到的情况。真要加也行，属于防御性写法，不加不影响功能。

这一步不会写也没关系，把意图说清楚让 AI 生成："按 parent_id 的顺序，把查到的父块重新排序"，它给你的代码跟上面这两行是一个意思。

### 测出来一串 None

代码写完不测等于没写。回 day09 的 notebook——那里 `vector_store` 已经建好了，可以直接拿来用，省得重新初始化。

```python
from app.rag.retriever import ParentChunkRetriever

retriever = ParentChunkRetriever(vector_store=vector_store)
chunks = await retriever.retrieve(query="等待期是多久", k=5, product_id=1)
chunks
```

按设计，传 `product_id=1`，过滤条件就卡在 1 号产品上，检索结果里应该只有 1 号产品的条款。

跑完一看，`chunks` 里躺着的全是 `None`。

不是空列表，也不是报错，而是一串空的占位——每个位置都有东西，但每个东西都是 `None`。这说明最前面几步都在正常跑，只是最后一步取歪了。

这时候没有日志很难猜。最土也最快的办法：一层一层打印。

```python
print(child_chunks)     # ① 子块召回的结果
print(parent_ids)       # ② 去重后的父块 id
print(parents)          # ③ 数据库查回来的父块
print(parent_map)       # ④ 转成的字典
```

逐个对：

- 子块召回没问题，检索到了；
- `parent_ids` 也没问题，取出来的都是字符串；
- `parents` 也没问题，数据库把对应的父块查出来了；
- `parent_map` 打印出来看着也没问题，key 就是那串 id。

可 `parent_map.get(pid)` 就是取不到。看一下打印出来的对象类型，问题就露头了：从数据库查出来的 `parent.id` 不是字符串，是 UUID 对象。所以这个字典的 key 是 UUID，而 `parent_ids` 里装的是字符串。拿字符串去取 UUID 的 key，取不到。

`dict.get()` 有个特性：取不到不报错，返回 `None`。于是每一次取不到，就在结果里留下一个 `None`，安安静静地混在中间，连异常都不给你一个。

> **易错点**：UUID 在 Python 里是对象，不是字符串。数据库驱动把它读回来是 `uuid.UUID`，从 JSON、从 `metadata` 里读回来是 `str`。两者不相等，拿来做字典 key 尤其容易踩——不报错，只是查不到。

修法很简单：建字典时把 key 转成字符串。

```python
parent_map = {str(parent.id): parent for parent in parents}
```

因为 `parent_ids` 那边是字符串集合，字典这边也得是字符串 key，两边对齐才找得到。

改完重新跑一遍。notebook 里改了源码要重启内核，但不用从头来——从 `vector_store` 那一格重新往下执行就行，前面初始化的东西还在。

再看，字典的 key 已经是字符串了，`chunks` 里也取到了父块，不再是 `None`。

核对内容：结果里每一条的 `product_id` 都是 1，内容都是等待期相关，其中一条写着"自本合同生效之日起180日为等待期"。过滤生效了，排序也生效了，整条链路通了。

修完的 `retrieve` 完整长这样：

```python
async def retrieve(self, query: str, k: int, product_id: int):
    child_chunks = await self.vector_store.asimilarity_search(
        query,
        k=k,
        fetch_k=10,
        expr=f"product_id == {product_id}",
        ranker=create_cross_encoder_ranker(query),
    )

    if not child_chunks:
        return []

    parent_ids = [child.metadata.get("parent_id") for child in child_chunks]
    parent_ids = list(dict.fromkeys(parent_ids))

    async with AsyncSessionFactory() as session:
        repo = ParentChunkRepository(session)
        parents = await repo.query_by_ids(parent_ids)

    parent_map = {str(parent.id): parent for parent in parents}
    return [parent_map.get(pid) for pid in parent_ids]
```

回头把这一段捋一遍，其实就四件事：混合检索召回子块、从 metadata 取 id 去重、按 id 批量查父块、按召回顺序把父块排回去。

前三件事里，混合检索是现成的，取 id 和查库各是几行。真正花心思的是第四件——如果不排，"重排"这道工序的效果会在最后一步丢干净。而让第四件失效的，又是那个不声不响的 UUID 类型差异。

> **结论**：这一段的坑不在逻辑，在类型。逻辑通了、类型不对，结果是一串 `None`，比报错更难查。所以看到"都跑通了但结果是空的"，先打印中间变量，看类型，不要先怀疑算法。

## RAG 工具化与 LangGraph 编排
> 对应块：BLK43 | 覆盖分集：P163-P166 | 块标题（分集名）：《RAG 工具化与 LangGraph 概览》

我们手里已经有 retriever 了，而且能跑通。但有一个问题摆在面前：pipeline 和 retriever 这两个东西，以后是要被反复用到的，可现在 retriever 还只是一个类，一个我们自己写出来的普通类，它还不是一个工具。等一会儿我们就要把它变成 Agent 能调用的工具。

一旦变成工具，它就会被频繁调用。每一次调用都重新 `new` 一个 retriever，这显然不行。所以我们对这两个东西的期望很明确：**项目启动时创建一次，之后一直复用**。

### 检索器和流水线只该建一次

想清楚"只建一次"，接下来要解决的是"建在哪儿"。

我的做法是把 pipeline 和 retriever 的初始化写到一个固定的地方，项目启动时让它执行，项目关闭时把资源释放掉。这个固定的地方，就是 RAG 包的 `__init__.py`。

`__init__.py` 大家应该不陌生。它是包的标记文件，一个最常见的用途是控制这个包往外导出什么——也就是 `__all__` 干的事：加了 `__all__`，别人 `from app.rag import *` 就只能拿到你列出来的那几个名字；不加，包里的东西都能导出去。但 `__init__.py` 不只干这个，它里面还可以写初始化脚本。我们的 pipeline 和 retriever 正好适合放这儿。

```python
# app/rag/__init__.py

# 先建向量模型和 vector store（沿用前面写过的两步）
vector_store = ...

# 两个组件共享同一个 vector store
rag_pipeline = RAGPipeline(vector_store)
retriever = ParentChunkRetriever(vector_store)


def close_rag():
    # vector store 本身没有 close，要关的是它内部的 client（也就是 Milvus）
    vector_store.client.close()
    rag_pipeline.close()


__all__ = ["rag_pipeline", "retriever", "close_rag"]
```

这段代码里有两处值得多说两句。

第一，顺序不能乱。`rag_pipeline` 初始化需要一个 vector store，`retriever` 初始化也需要一个 vector store。既然两个都要，那就在上面先把 vector store 建好，下面两个组件都拿同一个对象——共享一份连接，而不是各建一份。

第二，这段代码没有定义类，也没有定义方法，它就写在模块里。这意味着：**只要这个模块被加载，这些代码就会立刻执行**，pipeline 和 retriever 当场就被初始化掉了。

那能不能写成 `init_rag()` 函数，等调用了再初始化？当然可以，把这一堆代码塞进函数里就行。但有个连带问题：变量定义在函数里是局部变量，函数执行完就没了，所以必须把 pipeline 和 retriever 返回出来，不返回你拿到的就是空值。这样能行，只是麻烦一点。这里我们就简化，直接放在模块里。

> **提示**：模块级初始化的代价是"导入即执行"——导入发生在什么时候，初始化就发生在什么时候。后面接 FastAPI 的 lifespan 时，这个特性既是我们要利用的开关，也是必须小心的地方。

### 关闭的顺序，决定收尾安不安全

有初始化就得有释放。先写 `close_rag()`，关的时候要挨个问：谁有资源，谁没资源。

`vector_store` 本身没有 `close` 方法。我原以为有，翻了一遍 API 才确认没有——真正能关的是它内部的 `client`，也就是我们连的那个 Milvus。所以关 vector store 的正确姿势是 `vector_store.client.close()`。

`rag_pipeline` 要关。它内部用到了 Milvus，而这个 Milvus 客户端我们之前是写过 `close` 方法的，调 pipeline 自己的关闭逻辑就行。

`retriever` 不用关。它里面除了 vector store 没有别的资源，而 vector store 那层的连接已经处理过了。

接下来是把这两个动作挂到 FastAPI 的 lifespan 上。这里的关键是**导包的位置**。

因为这个模块一导入就执行，所以不能把 `from app.rag import ...` 写在 main 文件的最外层——那样服务还没启动，RAG 就先建好了，而且不管你有没有真的要用。要把这个导入放进 lifespan 里面：项目启动时执行 lifespan，lifespan 里执行导入，导入触发初始化，三步串起来，初始化就正好落在启动时刻。

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动：导入 app.rag 模块，模块级代码执行，pipeline 和 retriever 随之初始化
    from app.rag import close_rag

    # 然后是数据库连接的初始化
    ...

    # 再是 checkpointer、agent 的初始化
    ...

    yield

    # 关闭：先关 RAG，再关数据库，最后关 checkpointer
    close_rag()
    ...
```

关闭阶段那一句 `close_rag()` 是收尾动作，别漏。

顺序是这样的：启动时 RAG 在最前面（因为导入写在前），然后是数据库连接初始化，然后是 checkpointer、agent 初始化。停止时整个顺序反过来——先 close RAG，再 close 数据库，最后 close checkpointer。

```text
启动
  导入 app.rag（初始化 RAG）
        │
        ▼
  数据库连接初始化
        │
        ▼
  checkpointer / agent 初始化

关闭
  close_rag()
        │
        ▼
  关闭数据库连接
        │
        ▼
  关闭 checkpointer
```

启动项目就能看到这个过程：先打印 RAG pipeline 初始化，接着是数据库连接初始化，再是 checkpointer 和 agent 初始化。停止时顺序倒过来，只是 RAG 之后的关闭动作没打日志，所以看不到——想看清楚，自己在关闭逻辑里加几行日志就行。

> **注意**：关闭顺序不能反。pipeline 和 retriever 都要用数据库，如果先关数据库，RAG 还没关、可能还在用它，这时候数据库已经断了，就会出问题。原则是**被依赖的东西最后关**。

### 把检索包成一个 Agent 工具

初始化和关闭都安排好了，接下来是最后一步：把 retriever 封装成一个 RAG 工具，交给 agent 使用。

工具统一放在 agent 下的 tools 里。目前那里只有一个工具，就是之前写的保险产品推荐；现在要加第二个，做知识库检索，具体说是检索保险条款。函数名就叫 `retrieve_insurance_clause`。

整个工具只有三步：检索、整理、返回。

```python
async def retrieve_insurance_clause(query: str, k: int, product_id: int) -> list[str]:
    """根据用户的提问检索保险条款，返回条款原文片段。

    Args:
        query: 检索关键词。
        k: 返回文档的数量。
        product_id: 要检索的保险产品 ID。
    """

    from app.rag import retriever

    chunks = await retriever.retrieve(query=query, k=k, product_id=product_id)

    return [
        f"section: {chunk.section_path}\ncontent: {chunk.content}"
        for chunk in chunks
    ]
```

先看那三个参数。它们都不是我们自己填的，是**调工具的人**给的——也就是模型。

到底要搜什么，不是我们说了算，是用户问什么，由问题来产生条件。所以 `query` 必须作为参数让模型生成：模型在跟用户对话时，一旦发现用户问的是条款信息，就根据用户提的问题组织查询条件。

`k` 可以让模型给，也可以在这里写死，看你怎么设计。`product_id` 同样由模型给：用户在上下文里说"达尔文"，模型就去聊天记忆里找达尔文对应的 id。

> **定义**：查询重写，指模型在调用检索工具之前，把用户的口语化问题改写成适合检索的关键词，而不是把原句直接丢进向量库。

真正要动脑的是返回值的处理。

`retrieve` 返回的 `chunks` 是一个列表，里面装的是 `ParentChunk` 对象。这个对象字段很多：`class_name`、`content`、`id`、`product_id`、`section_path`（路径）。全都丢给模型吗？没必要。我们把这些内容给 AI，目的是让它回答用户的问题，`id` 这类东西跟它没关系，它真正需要的只有 `content`。

所以只取两样：`content`，外加 `section_path`。为什么多带一个路径？因为路径里可能藏着有用的关键字，比如"等待期"这类词会出现在章节标题里，对回答有帮助。把两者拼成一个字符串，每篇文档变成一条，整体做成一个列表返回。

> **易错点**：不要图省事把整个对象序列化后丢给模型。字段一多，模型反而抓不住重点，还平白多烧 token。

还有一件事很容易漏：文档注释。工具只有函数名和参数名，模型看不出它是干什么的、每个参数什么意思，所以 docstring 必须写；多加的 `k` 也要在注释里说清楚——它是要返回的文档数量。不写这个，工具等于白做。

另外提一句类型的事。`chunks` 一开始在编辑器里点不出属性，是因为 `retrieve` 没标返回类型；补上类型（一个装 `ParentChunk` 的列表）之后，`chunk.content`、`chunk.section_path` 就都有补全提示了。这不是功能问题，但省事。

笔记里那份实现是把所有结果用 `"".join()` 拼成一整条字符串，而不是返回列表；道理是一样的，两种都能用。

### 让工具真的被调用起来

工具写完不会自动生效，要挂到 agent 身上。

在 agent 里把新工具导入进来（原来只导了一个，现在多导一个），然后放进工具列表。光放进去还不够，系统提示词也要把话说死：当用户询问保险条款问题时，必须调用工具查询条款，并根据条款回答，不能自己编造。

> **提示**：工具列表决定"能调用什么"，系统提示词决定"什么时候必须调用"。只给工具不写约束，模型很可能凭训练记忆直接作答。

到这里工具就生效了。剩下的是见证奇迹的时刻——跑一遍。

启动服务，打开 `localhost:5173`，新开一轮对话：

"你好，我要买保险" → "给我自己买" → "预算 2 万" → "不确定买啥，你帮我推荐吧"。

模型推荐了几款产品，其中就有达尔文 12 号。接着问一句："达尔文的等待期是多久？"

这一问问的是条款。它先说"让我来帮你查一下条款"，然后回答：已经查到达尔文 12 号的等待期条款，等待期 180 天。

这 180 天是编的，还是查出来的？翻条款文档核对：达尔文 12 号是重疾险，等待期 180 天，对得上。确实检索到了，不是瞎编。

想看调用细节，把日志级别改成 debug 再问一遍，完整的调用链就出来了：先是历史消息（"你是安心宝的智能保险顾问"、我第一次说的"给自己买、预算 2 万"），然后是 `query_candidate_products` 查候选产品，再往后是我问等待期那一轮，模型决定调用 `retrieve_insurance_clause`。

参数是这样：

- `query`：不是"达尔文的等待期是多久"，而是重写之后的关键词；
- `k`：5，模型自己定的；
- `product_id`：2，它从聊天记忆里找到"达尔文"，再对上达尔文 12 号的 id。

返回结果的 `section_path` 是 `2.3.1`，正好是等待期那一节，`content` 就是等待期的条款原文。

换个产品再试一次，问"尊享一生的等待期是多久"。模型自动匹配到对应产品，然后回答：条款中多次提到了等待期，但没有给出具体天数。这个回答本身就是证据——它没有编一个数字，而是如实说查到的内容里没有。日志里同样能看到这次调用和召回的条款片段。

到这里，RAG 的功能算真正实现了：问条款的时候，它不再瞎编，而是基于知识库回答。

### AI 应用的三级台阶

RAG 这条线收尾了，换一个话题：LangGraph。

介绍 LangChain 的时候就说过，LangChain 和 LangGraph 都属于 LangChain 这个框架体系，两者都是用来做 agent 开发的。那问题就来了：既然已经会用 LangChain 做 agent 了，为什么还要再学一个 LangGraph？

要回答这个，得先看 AI 应用是怎么一步步长成今天这样的。

#### 一次问答就结束

2022 年、2023 年那会儿，GPT 刚发布，最早的 AI 应用简单到不能再简单：用户问题来了，直接发给模型，模型回答，结束。就这么三步。

别小看这种应用。当年有个游戏风靡一时，叫哄哄模拟器。玩法是让 AI 扮演你的女朋友：先选性格类型、选星座、选一个恋爱场景，然后开局。开局时女友的情绪是"非常生气"，初始分 20 分，AI 生成一个生气的理由，接下来你就开始哄——哄得好加分，哄得不好扣分，加到 100 就赢，扣到 0 就输。

它的本质是什么？就是向模型发请求。用户选的那些东西，最后被拼成一段系统提示词，之后用户发什么就转给模型，让它回复，没有别的。

就这么个东西，用户量超过 60 万，调用超过 2000 万次，作者挣了很多钱。所以哪怕是最简单的一次调用，也有它自己的场景。

但这种应用的短板很清楚：不能调工具，不能访问外部数据，也做不了多步骤的任务。

#### 用代码串起一条链

应用往前走一步，就从单次调用变成了链式调用。

什么叫链式？把整个工作流变成一条流水线：请求来了，先做知识检索，检索完调模型，模型调完再调工具，工具回来可能还要再调一次模型。它是一条线性的路，**没有回头路**，先干什么后干什么，全部由我们的代码提前写死，按固定顺序串起来，形成一条链。

LangChain 这个名字其实就是这个意思：Large Language Model 加 Chain，大语言模型形成一条链。它早期的编程范式就是管道式的：拿到用户问题 `query`，用管道交给提前建好的模型，模型出结果，再交给做结构化输出的那一步，再交给下一个处理环节。代码执行时自动按这个顺序往下走。

好处是稳定可靠。流程是人写的，跑 1000 次、1 万次，流程都不会变，不会出现意外。

代价是缺乏自主智能。这条链上没有任何一处是让模型思考"我该干什么"，agentic 这块很弱。

#### 把流程交给模型

再往后就是智能体。智能体的核心变化是：工作流不再由人控制，而是由模型控制。

这里有两个层次。浅一层，第一步仍然由程序控制，程序把请求交给模型，让模型判断接下来走哪条分支——相当于让模型做意图识别，再做条件分支，这已经有智能性了。深一层，请求直接扔给模型，由它自己规划先干什么再干什么，然后一步步执行。Claude Code、Codex、WorkBuddy 这类工具都属于后面这种，你跟它说一句话，剩下的事它自己安排。

自主性最强，可靠性最差。智能体写得不好，或者模型的"智商"不够，执行过程就可能完全不是你想要的样子。

### 稳定性与自主性是一对矛盾

把这三代应用摆在一条轴上，会看到一个很清楚的对立：

```text
自主性   低 ◄────────────────────────────────────────► 高
可靠性   高 ◄────────────────────────────────────────► 低
         传统代码 / 固定链      意图识别 + 条件分支      完全由模型规划
```

模型对应用的控制越多，自主能力越强，可靠性越低；控制越少，自主性越弱，稳定性越强。这是过去一直存在的局面：想要智能，还是想要可靠，只能二选一。

| 维度 | 链式应用 | 智能体 |
| :--- | :--- | :--- |
| 流程由谁控制 | 代码，提前写死 | 模型，运行时决定 |
| 稳定性 | 高 | 低 |
| 自主性 | 低 | 高 |

LangGraph 要解决的正是这个二选一。

> **结论**：LangGraph 的作用，是在保持 agent 自主控制程度不变的前提下，把它那层的稳定性抬上去。智能性由模型本身决定，可靠性由 LangGraph 补。

这句话的分寸要拿准：它不是把 agent 变回固定流程，自主控制的程度不变，变的是同一份自主性之下的可靠程度。图上就是把那条曲线整体抬高一些。

### 图由节点、边和状态组成

怎么抬？先说第一件事：LangGraph 允许你自定义 agent 内部的工作流，以及工作流里的每一个节点。

这句话是它的全部要害。节点是你自己写的，那么"需不需要稳定"这件事就由你决定：需要稳定的节点，用传统编程写死那段代码；需要自主的节点，交给模型去做。流向也是你定的，但流向中间的一部分可以按模型的控制走——模型与自定义控制就这么结合到了一起。

第二件事，是它给了一整套 harness。

现在大家常聊一个说法：agent 等于 model 加 harness。harness 是马鞍、鞍具的意思，也可以理解成一套套索——用来控制这匹马的东西。模型是那匹马，跑得快、力气大，但没有鞍具你骑不上去。LangGraph 提供的就是这一整套：记忆、工作流编排等等，全都在里面。

第三件事，也是最重要的：工作流不再是链，而是图。

在 LangGraph 里，工作流有分支、有循环，不是 LangChain 那种一路向前的线性链。有了分支和循环，画出来就是一张图，这也是 graph 这个名字的由来。

那么这张图由什么构成？三个最基本的要素。

| 要素 | 英文 | 职责 |
| :--- | :--- | :--- |
| 节点 | node | 真正干活的代码，可以是工具调用、知识检索、模型调用 |
| 边 | edge | 连接节点、控制工作流走向的路径 |
| 状态 | state | 整个工作流中流转的数据 |

节点是写业务流程的地方。工具调用、知识检索、模型调用，真正的活都在节点里干。

边就是线。只有节点不够——这些节点先执行谁、后执行谁，得按一定顺序连起来，用来连接它们的就是边。有些线是实线，表示固定顺序；有些线是虚线，表示条件判断，可能走这条也可能走那条，二选一。边还可以是循环的，走一圈再回来。

```text
      ┌────────────────┐
      │     START      │
      └───────┬────────┘
              │ 实线：固定顺序
      ┌───────▼────────┐
      │ 节点：检索     │◄──────┐
      └───────┬────────┘       │
              │ 虚线：判断     │ 边可以循环
      ┌───────▼────────┐       │
      │ 节点：模型     │       │
      └───────┬────────┘       │
              │                │
      ┌───────▼────────┐       │
      │ 节点：工具     │───────┘
      └───────┬────────┘
              │
              ▼
              END
```

图里每个方框就是一个节点，节点之间那些线就是边；从 START 一路流到 END、被反复加工的那份数据，就是 state。

状态这个概念最好用车间流水线来理解。整条工作流就是一条长长的传送带，边是传送带本身，节点是传送带上一个个工位上的工人，工人负责加工传送过来的东西——那个东西就是 state。节点是对数据的加工，边决定数据被送到哪个工位，state 是数据本身，也是整幅图的状态。

所以 LangGraph 提供了一套机制，让你自己编写工作流、编写图，从而控制 agent 的走向。走向可控，稳定性和可靠性自然就上去了。

### 记忆系统顺带带来的能力

除了工作流，LangGraph 还提供了记忆系统，也就是前面说过的 checkpointer。LangChain 里那个 checkpointer，底层其实就是 LangGraph 实现的。

有了这套记忆系统，能做的不只是"记住前面聊过什么"：

| 能力 | 实际表现 |
| :--- | :--- |
| 记忆 | 多轮对话的上下文得以保留与传递 |
| 故障恢复 | 程序走到某个节点突然终止，还能从断点位置继续执行 |
| 人机交互 | 执行到某处暂停，等用户批准再往下走 |
| 时间回溯 | 已经执行到 node3，后悔了能退回 node1 |
| 长期记忆 | 除了 checkpointer 的短期记忆，还支持长期记忆与上下文传递 |

人机交互这一条，用 Claude Code 的时候应该都体验过：让它执行某些任务，它有时会停下来问你——我要做这件事，你让不让我做？这就是执行到某个节点暂停、等用户确认，LangGraph 里同样能做。

时间回溯也一样：流程跑到第三个节点，你发现方向错了，可以撤回第一个节点重新走。

到这里，"harness 全套"这句话就落地了。它确实是那个控制模型这匹马的鞍具，把 agent 的稳定性实实在在抬了一截。

> **结论**：模型负责聪明，LangGraph 负责别跑偏。要自主，让模型去控制流向；要可靠，把关键节点用代码写死。这两件事在一张图里同时成立，不用再二选一。

## LangGraph 节点与默认 Reducer：一张图是怎么长出来的
> 对应块：BLK44 | 覆盖分集：P167-P168 | 块标题（分集名）：《LangGraph 节点与 State 默认 Reducer》

### 节点是一个函数，状态是一个类

前面已经把 LangGraph 的三个概念过了一遍：状态、节点、边。概念听懂了，接下来真正的问题只有一个——这三样东西在代码里到底长什么样，又怎么拼成一张能跑的图？

先把分工摆清楚。状态是整个工作流程里流转的数据；节点才是工作流里真正干活的代码，它负责加工、处理 state 里的数据。既然节点是在加工数据，那它在代码里就一定是一堆逻辑，而一堆逻辑用什么装？用函数装。所以在 LangGraph 这三个概念里，**节点就是一个函数**。

状态是数据，数据用什么定义？用类。类里有字段，字段里能存数据。所以**状态就是一个类**。

剩下的边更简单，它就是把节点连起来的那根线：一条边一根线，把开始连到节点，把节点连到结束。

```text
START ──> node1 ──> node2 ──> END
```

一张最简单的图就是这三样东西凑出来的：两个特殊节点卡在两端，中间若干干活的节点，边把它们串成一条链，而整条链上从头到尾流转的就是 state。

#### 状态类必须继承 TypedDict

写状态类的时候，名字随你起，叫 `State` 也好、叫 `SimpleState` 也好，都不是固定的。但有一样是死的：这个类必须继承 `TypedDict`。

`TypedDict` 没见过也不影响用，把名字拆开就懂了。type 是"类型的"，dict 是"字典"，合起来就是**带类型的字典**。

> **定义**：`TypedDict` 是一个"看起来像类、其实是字典"的类型。你用 class 的写法声明字段，运行时它仍然是一个 dict。

#### 为什么非要绕这一道：普通字典管不住 key

普通字典就是一对大括号，里面写 key、写 value。问题在于这个 key 你管得住吗？管不住。今天叫 `name`，明天叫 `age`，后天叫 `a`、叫 `b`，随便写，字典对 key 没有任何约束力。

可一张图要处理什么数据，是固定的。如果放开让人随便传字典，key 立刻就花了：你传 `{"k1": "v1"}`，节点里却要取 `state["name"]`，取不到。这种错不该拖到运行时才炸。

`TypedDict` 解决的就是这件事——你写的字段成了固定字段：

```python
class SimpleState(TypedDict):
    name: str
    greeting: str
```

这么一写，这个"字典"的 key 就必须叫 `name`、必须叫 `greeting`，值的类型也得对得上。它仍然是字典，但不是随便什么字典都能冒充它：只有 key 对得上的字典，才能当这个 state 用。

| 对比项 | 普通 `dict` | `TypedDict` 类 |
| :--- | :--- | :--- |
| key 是否固定 | 随便写，无约束 | 由字段声明钉死 |
| 值的类型 | 不做检查 | 按类型注解约束 |
| 运行时本质 | 字典 | 仍是字典 |
| 取值方式 | `d["k"]` 或 `d.get("k")` | 一样，中括号或 `get` |

取值那一栏值得多看两眼。既然它本质是字典，那在节点里写 `state.name` 是点不出来的——补全列表里根本没有 `name` 这个属性。要么 `state["name"]`，要么 `state.get("name")`。点不出来不是编辑器坏了，是它真的不是一个普通对象。

### 节点只返回你要改的那几个字段

节点的形状定下来就两条：入参是一个完整的 state 对象，返回值也是 state——不过返回值用字典给就行，而且**只放你要更新的字段**。

为什么可以只放一部分？举个例子。state 里有 `name` 和 `age` 两个字段，节点里算了一通，只想改 `age`，`name` 不动。那返回 `{"age": 31}` 就够了，不必把 `name` 原样抄回来。

更新到底是怎么发生的？不是在节点里直接改 state 那个对象，而是通过返回值。LangGraph 拿到你返回的字典，把里面的新值合并回 state：返回了的字段换成新值，没返回的字段保持原样。

所以写一个节点，心里就三步：先从 state 里读出旧数据，再写你自己的计算逻辑——调模型也好、执行工具也好，随你；最后返回你想更新的那部分。

> **易错点**：在节点里写 `state["age"] = 31` 然后 `return state`，不是这套用法。要改什么，用返回值说。返回值是唯一的合并入口，后面你会看到，合并规则正是作用在这个返回值上的。

### START 和 END 是白送的两个节点

一张图总得有入口和出口。这两个节点 LangGraph 默认就给了，不用自己定义：

- `START`：开始节点，整张图的入口；
- `END`：结尾节点，整张图的出口。

它们是从 LangGraph 里导进来的两个常量，和 `StateGraph` 一起 import 即可。你看到的那条 `START → 节点 → END` 的链子，两头就是这两个常量在撑。

### 搭一条最小链路：输入名字，输出大写问候

动手之前先交代一句：图里的节点不一定非得调模型。节点内部干什么，是你自己说了算的——可以调模型、可以执行工具、可以读数据，也可以什么都不干只拼字符串。所以第一张图挑个最土的例子，把骨架走通：

```text
START ──> node1（按 name 生成问候语） ──> node2（把问候语转大写） ──> END
```

用户从 START 进来给一个 name，node1 拼出 `Hello, 某某`，node2 把这句话转成大写，到 END 结束。要定义几个节点？两个。再配三条边，这条链就闭上了。

#### 先定 State

按前面的规矩，先想清楚这幅图要流转什么数据。名字得有，叫 `name`，字符串。写到 node1 要返回问候语时才会发现第二个字段：问候语得交给 node2，而节点之间传数据的唯一通道就是 state，所以 `greeting` 也必须进 state。

这就带出一条判断标准：**state 里既要有将来输入的原材料，也要有将来产生的中间结果**。凡是需要跨节点传递的东西，都得先在 state 里开个字段；不然节点算出来的东西没地方放，下一个节点也拿不到。

```python
from typing import TypedDict


class SimpleState(TypedDict):
    name: str        # 输入：用户的名字
    greeting: str    # 中间结果：生成的问候语
```

#### 写两个节点

node1 干三件事：取出 name、拼问候语、把问候语写回 state。

```python
def node1(state: SimpleState):
    print(f"node1 is running，接收到了 name：{state.get('name')}")
    return {"greeting": f"Hello, {state.get('name')}"}
```

取 name 用的是 `state.get("name")`，不是 `state.name`，理由前面说过——它本质是字典。拼问候语本来可以先存两个中间变量、再拼一次、再返回，其实没必要，直接在 `return` 的字典里拼掉就行，整个函数压成一行。`print` 是给自己看的，确认这个节点真的被执行了。

node2 接着干：把 state 里的 `greeting` 取出来转大写，再写回去。

```python
def node2(state: SimpleState):
    print(f"node2 is running，接收到了 state：{state}")
    return {"greeting": state.get("greeting").upper()}
```

node2 凭什么能取到 `greeting`？因为边决定了 node1 先跑，node1 已经把 `greeting` 写进 state 了。**节点的执行顺序不是你写函数的顺序，是边连出来的顺序。**

#### 把节点和边装进 builder，再编译

三样东西齐了，开始装配。第一步先拿 builder：

```python
from langgraph.graph import StateGraph, START, END


builder = StateGraph(SimpleState)
```

`StateGraph` 是"带状态的图"。它第一个参数叫 `state_schema`，要的就是你那个 state 的约束——等于告诉 LangGraph：这张图内部流转的数据长这个样子。它返回的还不是图，是一个**图的构建器**，后面所有的添加动作都往这个 builder 上做。

第二步把节点塞进去：

```python
builder.add_node("node1", node1)
builder.add_node("node2", node2)
```

`add_node` 要两个参数：先一个字符串当节点名，再传节点函数本身。名字不是装饰，后面连边全靠它。注意第二个参数只写函数名，别写成 `node1()`——加了括号就是把函数当场执行一遍，传进去的是返回值，不是节点。

> **易错点**：一定要先 `add_node`，再 `add_edge`。节点还没进图就去连边，等于指着一个还不存在的名字连线。

第三步连边。这张图一共三条边：`START → node1`、`node1 → node2`、`node2 → END`。

```python
builder.add_edge(START, "node1")
builder.add_edge("node1", "node2")
builder.add_edge("node2", END)
```

`add_edge(start, end)` 就是一条边：从哪开始、到哪结束。两头用的都是名字——`START`、`END` 是常量，中间的节点名就是你在 `add_node` 时起的那个字符串。

第四步编译：

```python
graph = builder.compile()
```

到这一步为止，前面做的都只是"把图的构成定义出来"，还不是一张能跑的图。`compile()` 编译一下，才得到最终可执行的对象。

#### 调用整张图

整张图都在加工 state，所以调用时传进去的是 state，拿回来的也是 state——而 state 本来就是字典，那就传字典、收字典。

```python
result = graph.invoke({"name": "杰克"})
print(result)
```

只传 `name` 就够了，`greeting` 是执行过程中产生的，不用预先给。整条链跑下来，state 是这样一步步变的：

```text
invoke 传入        {"name": "杰克"}
node1 执行后       {"name": "杰克", "greeting": "Hello, 杰克"}
node2 执行后       {"name": "杰克", "greeting": "HELLO, 杰克"}
```

读这三行注意两件事：一是 `greeting` 是执行中长出来的字段，传进去时没有；二是 node2 拿到的 state 里已经有 node1 写好的 `greeting`，所以它才能接着改。最终 `result` 就是第三行那份 state，`name` 和 `greeting` 都在里面。

跑起来的打印顺序也会印证这一点：先 `node1 is running`，再 `node2 is running`，而 node2 打印出来的 state 里，`greeting` 已经是 `Hello, 杰克` 了。

#### 把图显示出来

图连好了，屏幕上却什么都没有。想看看它长什么样，有两种手段。

第一种是在 notebook 里直接把图渲染出来：从 `IPython.display` 里导入 `display` 和 `Image`，再把 `graph.get_graph()` 的结果交给 `display`。`get_graph()` 这一步有点像 X 光，穿透到图里面去照了一张相，节点和边就都现形了。

```python
from IPython.display import display, Image

display(Image(graph.get_graph().draw_mermaid_png()))
```

> **提示**：不同版本里这个"拍照"方法的名字可能不一样（`draw_mermaid_png`、`draw_png` 之类），渲染风格也略有差别，按本机那一版的补全提示来就行；图出不来，先确认绘图依赖装没装。

第二种是用开发工具里的调试面板看图。我这边那个插件当时没把图渲出来，纯是插件自己的毛病，图本身是好的，换个环境一般就正常显示。

渲染出来的样子应该和设计对得上：START 到 node1，node1 到 node2，node2 到 END，一条直链，没有分叉。

### 默认 Reducer：什么都不写就是覆盖

节点讲完，回头看状态。它确实贯穿了整个执行过程：定义节点时传的是 state、返回的也是 state，调用整张图时还是传 state、收 state。state 里定义的，就是整幅图的数据字段，既可以是输入字段，也可以是运行的结果。

现在问一个前面没问的问题：如果两个节点更新了同一个字段，会是什么效果？

是覆盖。第一个节点写进去的值，被第二个节点写进去的值盖掉。

其实上一张图里已经用过一次了：node2 改的正是 node1 写过的 `greeting`，最后留下的是全大写那一版，`Hello, 杰克` 没留痕——那就是覆盖。

这就是节点的默认数据更新策略。一个节点返回 state 之后，这个返回值怎么合并进去，取决于一个叫 `reducer` 的东西；而且 state 里的**每一个字段都有自己的 reducer**。

#### Reducer 是一个函数

> **定义**：reducer 是每个 state 字段各自的合并规则，决定节点返回的新值该怎么和旧值合成最终结果。

它的本质是一个函数：接收原本的数据（旧值）和新数据（新值），返回最后的结果。默认的 reducer 短得不能再短：

```python
def reducer(old, new):
    return new
```

新值进来，旧值出局，所以默认效果就是覆盖。这段函数你没在代码里写过，看不见，但它存在——默认行为就是它。

节点返回一个字典之后，LangGraph 是逐字段去合并的，每个字段都拿自己那份 reducer 算一遍：

```text
节点返回      {"greeting": "HELLO"}
                    │
                    ▼
        取 state 里 greeting 的旧值  "Hello"   ┐
        取返回值里 greeting 的新值   "HELLO"   ┘
                    │
                    ▼
        reducer(old="Hello", new="HELLO")
                    │
                    ▼
        return new  →  写回 state：{"greeting": "HELLO"}
```

看这张图能明白两件事：一是 reducer 是**按字段**生效的，`greeting` 的规则管不到 `name`；二是没出现在返回值里的字段压根不进这道流程，所以它们保持原样。

#### 用两个节点把覆盖验证一遍

再搭一张最小的图，专门看这件事。state 只要一个字段：

```python
class DefaultReducerState(TypedDict):
    value: str
```

两个节点干的事一样，都是改 `value`，只是改成不同的值：

```python
def node1(state: DefaultReducerState):
    print(f"node1 接收到了 state：{state}")
    return {"value": "node1 value"}


def node2(state: DefaultReducerState):
    print(f"node2 接收到了 state：{state}")
    return {"value": "node2 value"}
```

装配还是那套动作：

```python
builder = StateGraph(DefaultReducerState)
builder.add_node("N1", node1)
builder.add_node("N2", node2)
builder.add_edge(START, "N1")
builder.add_edge("N1", "N2")
builder.add_edge("N2", END)
graph = builder.compile()

result = graph.invoke({"value": "initial value"})
print(result)
```

节点名这里起的是 `N1`、`N2`，随便叫什么都行——名字的唯一作用就是给边指路，只要 `add_edge` 里写的和 `add_node` 里起的对得上，图就成立。

跑起来看三处：

| 观察点 | 拿到的 value | 说明 |
| :--- | :--- | :--- |
| node1 收到 | `initial value` | `invoke` 传进去的初始值 |
| node2 收到 | `node1 value` | node1 的返回值已经顶掉了初始值 |
| 最终 result | `node2 value` | node2 又顶了一次 |

三行串起来就是一条覆盖的证据链：初始值活不过第一个节点，node1 的值活不过第二个节点。默认 reducer 的脾气就是新值盖旧值，后写的赢。

### 搭图的四步骨架

把整条路收成四步，写代码之前先在脑子里过一遍，代码基本就顺着出来了。

| 步骤 | 做什么 | 要点 |
| :--- | :--- | :--- |
| 一、定义 State | 继承 `TypedDict`，列出字段 | 输入参数和中间结果都算流转的数据，都得有字段 |
| 二、定义节点 | 普通函数，入参是 state | 只返回要更新的字段，不必原样抄回整个 state |
| 三、装配成图 | `StateGraph` → `add_node` → `add_edge` → `compile` | 先加节点再连边；边里传的是节点名 |
| 四、调用 | `graph.invoke(字典)` | 传 state、收 state，两头都是字典 |

严格说前三步是"造图"，第四步是"用图"。造图时最容易漏的是第一步——只想着输入，忘了中间结果也要塞进 state；最容易错的是第三步——节点还没加就去连边，或者连边时把函数对象当名字传了进去。

这两张图自己敲一遍，节点和 state 的手感就有了。往后的花样，都是在这个骨架上加节点、加分支。

## 自定义 Reducer 与图控制流：状态怎么拼，节点往哪走
> 对应块：BLK45 | 覆盖分集：P169-P172 | 块标题（分集名）：《自定义 Reducer 与图控制流》

问题来了：如果我不想让它覆盖呢？

默认 reducer 干的事只有一件——节点返回一个新值，它就拿着新值把旧值顶掉。可要是我的需求不是覆盖，而是不断往里追加、把每次的新内容拼到一块儿，那默认 reducer 就不够用了。不能用了怎么办？自己写一个 reducer。

这就是这一讲的起点：先把 state 的更新权从默认行为手里拿回来，再看图里的边怎么把节点串起来、岔开、绕过——普通边、并行、条件边，最后到 `Command`，让节点自己在返回值里报出下一站。

### 自定义 reducer：不想覆盖，就自己接管

要让某个字段不走默认 reducer，得靠 `Annotated`。这个东西我们之前用过一次，就在 FastAPI 里获取请求头那会儿，可能有人已经不记得了。它的身份很简单：一个标记、一个注解。注解里分两截——第一截写这个字段的数据类型，第二截写你要传给它的 reducer。

下面这段就是笔记上的写法，`custom_reducer_state` 是自定义 reducer 的 state：

```python
from typing import Annotated, TypedDict
import operator

class CustomReducerState(TypedDict):
    count: int
    notes: Annotated[list[str], operator.add]
```

看这两个字段的差别。第一个 `count` 只写了 `int`，没挂任何 reducer，那它走的就是默认 reducer——新值覆盖旧值。第二个 `notes` 外面套了 `Annotated`：`list[str]` 是它的数据类型，`operator.add` 是这个字段要用的 reducer。

`operator.add` 是个什么东西？它就是加法操作符的原始写法。平时我们写操作符直接写一个 `+` 号就行了，可 `+` 属于特殊符号，不能当成一个对象往这儿放，所以标准库把它包成了 `operator` 模块里的 `add` 函数，`add(a, b)` 干的事就是 `a + b`。以前没见过很正常，它代表的就是加。点进它的源码看，其实是运算符重载，读起来不太容易懂，不看也不影响用。

为什么这里偏偏要用加？因为列表加列表，等于把两个列表合并。`["node1"] + ["node2"]` 得到 `["node1", "node2"]`，这正是"追加"想要的效果。所以 `operator.add` 放在 `notes` 这个列表字段上，语义刚刚好。

当然，不想用 `operator.add`，自己写一个 reducer 也完全可以。下面就把这套东西跑起来。

先建一个演示脚本，state 里放两个字段：`count` 记次数，`notes` 记"执行过哪些节点"。`notes` 一开始故意不加 `Annotated`，就按最普通的写法来：

```python
class CustomReducerState(TypedDict):
    count: int
    notes: list[str]
```

节点一和节点二干的事差不多：先把手里的 state 打出来，再更新 `count` 和 `notes`。节点一让 `count` 等于原来的值加一——如果初始是 0，到这儿就变成 1；`notes` 则直接返回一个只装了 `"node1"` 的列表。节点二照抄，只是把名字换成 `"node2"`。

```python
def node1(state: CustomReducerState):
    print("node1 收到:", state)
    return {"count": state["count"] + 1, "notes": ["node1"]}

def node2(state: CustomReducerState):
    print("node2 收到:", state)
    return {"count": state["count"] + 1, "notes": ["node2"]}

builder = StateGraph(CustomReducerState)
builder.add_node("node1", node1)
builder.add_node("node2", node2)
builder.add_edge(START, "node1")
builder.add_edge("node1", "node2")
builder.add_edge("node2", END)
graph = builder.compile()

graph.invoke({"count": 0, "notes": []})
```

图还是那张串行的图，调用时初始 `count` 给 0，`notes` 给空列表。按"不断累加、不断拼接"的预期，第一次跑完 `count` 该是 1，第二次该是 2；`notes` 第一次该是 `["node1"]`，第二次该是 `["node1", "node2"]`。跑出来是这样：

```text
node1 收到: {'count': 0, 'notes': []}
node2 收到: {'count': 1, 'notes': ['node1']}
最终: {'count': 2, 'notes': ['node2']}
```

`count` 确实一路加到了 2，这个没问题。但 `notes` 只剩 `['node2']`——第一次写进去的 `"node1"` 不见了。原因就摆在眼前：`notes` 没定义 reducer，走的是默认 reducer，node2 返回的新列表直接把 node1 留下的旧列表盖掉了。所谓"不断覆盖"，就是这个样子。

现在给 `notes` 加上 `Annotated`，再配一个自己写的 reducer 函数：

```python
def add(old: list[str], new: list[str]) -> list[str]:
    return old + new

class CustomReducerState(TypedDict):
    count: int
    notes: Annotated[list[str], add]
```

这个 `add` 就是 reducer。它接收两个参数：旧值和新值。旧值是 state 里 `notes` 原来的内容，新值是本次节点要写进来的内容，两个都是列表。函数体只有一句 `old + new`——两个列表一拼，返回的结果就是拼接后的新列表。

它什么时候被调用？node1 执行的那一刻，LangGraph 发现你更新了 `notes`，就把 `notes` 的旧值当第一个参数传给 `add`，把节点返回的 `["node1"]` 当第二个参数传进去。这时候旧值是什么？是我们 invoke 时传进去的空列表。空列表加上 `["node1"]`，拼出来就是 `["node1"]`。

轮到 node2 执行，同样发现 `notes` 被更新了，这次传进去的旧值是 `["node1"]`，新值是 `["node2"]`，两者一拼，变成 `["node1", "node2"]`。跑一遍验证：

```text
node1 收到: {'count': 0, 'notes': []}
node2 收到: {'count': 1, 'notes': ['node1']}
最终: {'count': 2, 'notes': ['node1', 'node2']}
```

跟推断完全相符。想看得更细，可以开 debug 单步跟：初始灌入 state 的那一步，reducer 也会被调一次，此时旧值、新值都是空列表；第一次正经传参是旧值空、新值 `["node1"]`；第二次是旧值 `["node1"]`、新值 `["node2"]`，合并后返回，最终 state 里就是两者拼接的结果。

前面自己写的那个 `add`，换成 `operator.add` 效果一模一样，因为它表达的就是"加"。所以平时不必自己造这个函数，直接用 `operator` 自带的 `add` 就行，运行结果不会有任何差别。

> **定义**：reducer 是一个函数，接收 state 中某个字段的旧值和本次更新带来的新值，返回值作为该字段的最终值。

把这句话反过来看，默认 reducer 的行为也就清楚了：它不加工，直接把新值原样返回，所以旧值必然被覆盖。加了自定义 reducer，等于在"新值落盘"之前插了一道合并逻辑；不想覆盖，就得靠这一道。

### 边决定流向：普通边与条件边

state 管的是"数据怎么更新"，边管的是"节点按什么顺序跑"。边就是连线，连的时候就把执行顺序定下来了。连法有两种。

第一种是普通边，把一个节点连向另一个节点，流向是固定的：A 执行完执行 B，就这么一条路走到底。刚才 node1 连 node2 用的全是普通边。

第二种叫条件边，英文 conditional edge。它添加的时候就不是固定终点了，而是给一个判断条件，条件成立走这边，不成立走那边，或者走第三条。它是带条件的一种执行。

条件边接收三个参数。第一个参数是 node A，也就是这条边的起点；第二个参数不是 node B 了，而是一个函数——通常叫路由函数（route），它的返回值就是下一个节点的名字。返回值不一样，下一个节点自然就不一样，所以你在这个函数里可以写各种判断条件，根据不同的条件返回不同的结果，节点 A 就能动态地连向 B、C、D 里的任意一个。

第三个参数是 mapping，可选。它是给这种情况兜底的：万一路由函数返回的东西不是节点名，跟节点名对不上，就用这个字典去映射——字典的 key 是路由函数的返回值，value 是下一个节点的名字。不过这么写明显麻烦，所以一般建议路由函数直接返回节点名，mapping 就能省掉。

有了这两种边，能拼出来的图就不只是串行了。

| 连法 | 形态 | 特点 |
| :--- | :--- | :--- |
| 普通边·串行 |  A → B → C  | 整个工作流只有一条路径 |
| 普通边·并行 | A 之后同时接出 B、C、D，三个都跑完再汇到 E | 多个节点拿到同一份 state，各处理各的 |
| 条件边 | A 之后按判断去 B、C 或直接结束 | 运行时才知道走哪条，图上画虚线 |

串行我们一直在用，不重复了；条件边留到后面单独做案例。先把并行这张图落地。

### 普通边的并行工作流

并行的图长这样：开始节点一上来先找 A；A 执行完，不是只找 B，而是同时找 B 和 C；B、C 各自跑完，结果汇总再交给 D；D 跑完到结束。

```text
              ┌──> B ──┐
START ──> A ──┤        ├──> D ──> END
              └──> C ──┘
```

注意这里说的"同时"不是"同时刻执行"。CPU 同一时刻只能执行一个任务，这点绕不过去。并行的意思是 B 和 C 互不干扰：A 更新完的 state 会同时给到这两条边，两边拿到的 state 一模一样，然后各自处理各自的那一份。

代码在自定义 reducer 那份上改造，计数不要了，只做节点名称的统计。state 叫 `ParallelState`，字段只有 `notes`，挂的还是 `add`：

```python
class ParallelState(TypedDict):
    notes: Annotated[list[str], operator.add]

def node_a(state: ParallelState):
    print("node_a 收到:", state)
    return {"notes": ["A"]}

def node_b(state: ParallelState):
    print("node_b 收到:", state)
    return {"notes": ["B"]}

def node_c(state: ParallelState):
    print("node_c 收到:", state)
    return {"notes": ["C"]}

def node_d(state: ParallelState):
    print("node_d 收到:", state)
    return {"notes": ["D"]}
```

每个节点只干一件事：把自己这个名字追加进 `notes`。A 放 `"A"`，B 放 `"B"`，依次类推。有了 `operator.add`，这几个列表会一路拼起来，而不是互相覆盖。

然后把边连出来。`add_node` 时节点名就叫 `A`、`B`、`C`、`D`，对应的函数是 `node_a` 到 `node_d`：

```python
builder = StateGraph(ParallelState)
builder.add_node("A", node_a)
builder.add_node("B", node_b)
builder.add_node("C", node_c)
builder.add_node("D", node_d)

builder.add_edge(START, "A")
builder.add_edge("A", "B")
builder.add_edge("A", "C")
builder.add_edge("B", "D")
builder.add_edge("C", "D")
builder.add_edge("D", END)

graph = builder.compile()
print(graph.get_graph().draw_ascii())
```

数一下边：A 到 B、A 到 C、B 到 D、C 到 D，这是四条；再加上开始到 A、D 到结束，总共六条。心里把图过一遍，这六条边一条都不会多、一条都不会少。

调用的时候连初始值都不用传，直接 `graph.invoke({})`。传空也行，`notes` 一开始就是个空列表。跑出来：

```text
node_a 收到: {'notes': []}
node_b 收到: {'notes': ['A']}
node_c 收到: {'notes': ['A']}
node_d 收到: {'notes': ['A', 'B', 'C']}
```

逐个看。A 接到的是空，很合理；A 往里面塞了 `"A"`，于是 B 和 C 接到的都是 `['A']`——一模一样，因为 A 更新完的 state 同时给了这两条边。这也正是"并行"的全部含义：不是同时启动、同时计算，而是这两个节点拿到的输入完全相同，然后各自处理。B、C 分别往里加了自己的名字，所以到 D 手上就不只是 A 了，而是 `['A', 'B', 'C']`。

这里就冒出一个很容易被追问的问题：既然是并行，为什么一定是 `A、B、C`，而不是 `A、C、B`？

先别猜，这种事儿没有那么玄乎。我一开始也怀疑是边的添加顺序——先写 A 到 B、再写 A 到 C，那不就先 B 后 C 吗？把两条边的顺序调过来，先 A 到 C、再 A 到 B，图不变，重新跑一遍——结果没变。所以跟边的添加顺序没关系。

那跟什么有关？据我判断，是跟节点的名字有关。把 C 这个节点整个改名叫 `AC`，所有引用一起改，再跑——`AC` 跑到 B 前面去了。这就对上了：多个并行节点往同一个字段里填内容时，LangGraph 按节点名称的字典顺序排列。什么叫字典顺序？背英文单词都背过，第一个词是 abandon，一上来就放弃，然后是 b、是 c，这就是字典顺序。`B` 排在 `C` 前面，所以先 B 后 C；节点改叫 `AC`，`AC` 就排到 `B` 前面了。

> **提示**：这个顺序本身不重要，不用记。只要记住 B 和 C 是并行关系就够了——它们拿到同一份 state，各算各的，谁先谁后不影响结果。

> **定义**：并行执行指的是同一份上游 state 被同时分发给多个下游节点，各节点互不干扰地处理；它不表示多个节点在同一时刻一起运行。

### 条件边：用分数决定去向

普通边接收的是起点和终点，从哪开始到哪去，写死就行。条件边不一样：第一个参数还是起始节点，第二个参数换成一个路由函数。这个函数你自己写，但它的返回值会作为下一个节点的名字——返回谁，就执行谁。

案例做一个成绩判定的图。用户输入一个分数，先进入分数节点拿到分数，然后判断：大于等于 60 走成功节点，小于 60 走失败节点，成功和失败节点里分别打印结果。

```text
START ──> score ──> route(state)
                       ├── 返回 "success" ──> success 节点 ──> END
                       └── 返回 "fail"    ──> fail 节点    ──> END
```

state 就叫 `ScoreState`，存两样东西：分数 `score`，以及最后要展示的结果 `result`。

```python
class ScoreState(TypedDict):
    score: int
    result: str
```

三个节点刚好够用。第一个 `score_node` 负责拿分数，这里用 `input()` 做键盘录入，提示用户输入分数：

```python
def score_node(state: ScoreState):
    score = int(input("请输入用户分数："))
    return {"score": score}
```

`input()` 拿回来的永远是字符串，而 state 里 `score` 声明的是 `int`，所以必须用 `int()` 转一道再写回去，否则后面拿它做大小比较会直接报错。

第二个是成功节点 `success_node`，第三个是失败节点 `fail_node`，各自返回一条结果：

```python
def success_node(state: ScoreState):
    return {"result": "恭喜考试通过"}

def fail_node(state: ScoreState):
    return {"result": "考试没通过，节哀"}
```

三个节点写好，接着写路由函数。写法和写节点很像，参数同样是 state：

```python
def route(state: ScoreState):
    score = state["score"]
    if score >= 60:
        return "success"
    return "fail"
```

从 state 里取出分数，大于等于 60 就返回 `"success"`，否则返回 `"fail"`。这个返回值不是随便写的字符串，它必须是下一个节点的名字——这一点是条件边的命门。

建图时，开始边和最后的收尾还是普通边，只有 `score` 往下这一跳用条件边：

```python
builder = StateGraph(ScoreState)
builder.add_node("score", score_node)
builder.add_node("success", success_node)
builder.add_node("fail", fail_node)

builder.add_edge(START, "score")
builder.add_conditional_edges("score", route)
builder.add_edge("success", END)
builder.add_edge("fail", END)

graph = builder.compile()
print(graph.get_graph().draw_ascii())
```

现在把图打出来，会觉得奇怪：`score` 下面什么都没有，看上去走完 `score` 图就断了。

这不是边写漏了，而是 LangGraph 不知道 `score` 之后要去哪。我们确实指定了 `score` 要走一个路由，可路由不是节点——它只是个普通函数，不在图里。建图的时候 LangGraph 只认得节点和边，它没法钻进函数体里去看你 `return` 了什么，自然不知道 `score` 会连向 `success` 和 `fail`。

解决办法是给路由函数加上返回值类型标注：

```python
from typing import Literal

def route(state: ScoreState) -> Literal["success", "fail"]:
    score = state["score"]
    if score >= 60:
        return "success"
    return "fail"
```

`Literal` 是字面量类型，里面列的就是这个函数可能返回的那几个值。为什么这一步非加不可？因为你把这个函数交给 LangGraph 时，它能看到的只有函数名、参数和返回值类型，函数体里的代码它是看不到的。返回类型标上 `Literal["success", "fail"]`，它才知道这个路由只可能去这两个节点，才能把这幅图画出来。

加上之后再看，`score` 到 `success`、`score` 到 `fail` 的两条线都出来了，而且是虚线——虚线表示的正是动态的条件边。

> **注意**：凡是用条件边、自己写判断函数，返回值类型一定要用 `Literal` 把可能的下一个节点名罗列出来。少了这一步，程序照样能跑，但图是画不出来的。

调用的时候什么都不用传，`graph.invoke({})` 就行。`input()` 会弹出来问你要分数——在 Jupyter 里它自带弹窗，在 `.py` 文件里跑就是控制台输入。填 98，返回"恭喜考试通过"；再来一次填 58，返回"考试没通过"。填 59 是最可怜的，就差一分，照样得节哀。

条件边到这里就讲完了。和普通边比，差别只有一处：起点照旧，但没有一个写死的终点，而是塞进去一个函数，在函数内部靠逻辑判断返回结果，这个结果就当作这条边的终点。所以返回值一定要是节点名，**一定得是**；返回的不是节点名，就得再补一个 mapping 去映射，很麻烦。同时在返回值类型上用 `Literal` 声明清楚你会返回哪几个节点，图才画得出来。

### Command：让节点自己决定下一站

回头看看刚才那个 `route` 函数，它唯一干的事就是写一段判断逻辑。既然判断逻辑这么简单，能不能直接搬进 `score` 节点里？让 `score` 这个节点不仅能拿到用户分数，还能顺手把分数判断了，判断完直接告诉我们下一个节点去哪。这样一来，条件边和路由函数就都省了。

想法很顺，但直接写会撞墙。两边的职责是矛盾的：路由函数必须返回下一个节点的名字；普通节点必须返回一个字典，也就是 state 要更新的内容。一个要返回 state，一个要返回节点名，怎么融合？

`Command` 就是为这件事准备的。它把"state 的更新"和"下一个节点的名字"合而为一，塞进一个对象里。这个对象有两个字段：

```text
score 节点内部
    ├─ 拿到分数
    ├─ 判断 score >= 60 ? goto = "success" : goto = "fail"
    └─ return Command(update={...}, goto=goto)
                 │
                 ├─ update → 要写回 state 的字典（普通节点的职责）
                 └─ goto   → 下一个节点的名字（路由函数的职责）
```

`update` 放你原来节点本来该返回的那个字典，比如 `{"score": score}`，它负责更新 state；`goto` 放下一个节点的名字。一个返回值，两件事一起办，一举两得。

思路通了就动手改。把分数节点改成这样：拿到分数后先不急着返回字典，而是就地判断，用一个变量接住去向：

```python
from langgraph.types import Command

def score_node(state: ScoreState) -> Command[Literal["success", "fail"]]:
    score = int(input("请输入用户分数："))
    goto = "fail"
    if score >= 60:
        goto = "success"
    return Command(
        update={"score": score},
        goto=goto,
    )
```

注意这里 `goto` 的初值直接给了 `"fail"`，也就是默认按失败处理；只有分数大于等于 60 才改成 `"success"`。这样 `else` 就省掉了，逻辑还更清楚：默认走失败，达标才翻盘。返回值类型后面挂的 `Command[Literal[...]]` 先照写，它为什么必须加，等把边删完就明白了。

返回值写成 `Command(update=..., goto=...)`，`update` 里放要写回 state 的内容，`goto` 里放刚才算出来的去向。原来那个 `route` 函数可以整个删掉，条件边也不需要了。

```python
builder = StateGraph(ScoreState)
builder.add_node("score", score_node)
builder.add_node("success", success_node)
builder.add_node("fail", fail_node)

builder.add_edge(START, "score")
builder.add_edge("success", END)
builder.add_edge("fail", END)

graph = builder.compile()
```

边删干净之后，图看上去是残缺的：开始连到 `score`，`score` 后面没有了；`success` 和 `fail` 各自连到结束，但没有人指向它们。

问题还是同一个：走向藏在 `goto` 里，LangGraph 不知道 `score` 到底去了哪。所以返回值上必须声明清楚——`Command` 后面跟一个方括号，里面装 `Literal`，把可能的下一个节点列出来：

```python
def score_node(state: ScoreState) -> Command[Literal["success", "fail"]]:
    ...
```

这样 LangGraph 就知道 `score` 只可能去 `success` 或 `fail`，图就能画出来了，画出来和刚才条件边那版一模一样。

跑一遍。输入 98，走成功分支；输入 55，走失败分支。这次把分数也拼进结果里，成功和失败两个节点从 state 里取 `score`：

```python
def success_node(state: ScoreState):
    return {"result": f"恭喜你，考了 {state['score']} 分，考试通过"}

def fail_node(state: ScoreState):
    return {"result": f"节哀，考了 {state['score']} 分，考试没通过"}
```

调用还是 `graph.invoke({})`，把返回结果里的 `result` 打印出来：98 得到"恭喜你，考了 98 分，考试通过"，55 得到"节哀，考了 55 分，考试没通过"。功能与条件边那一版完全一致，只是控制权从路由函数挪进了节点自己的返回值里。

> **提示**：`Command` 后面这个 `Command[Literal[...]]` 的声明，不加也能调用，程序照跑不误，只是图画不出来。加它的唯一目的就是让图能看见。所以别把它当成运行必需，但也别省——省了以后排查流程会很难受。

三种走法摆在一起，区别就很清楚了：

| 写法 | 谁决定下一站 | 状态更新写在哪 |
| :--- | :--- | :--- |
| 普通边 | 建图时 `add_edge` 写死 | 节点返回的字典 |
| 条件边 | `route` 函数的返回值 | 节点返回的字典 |
| `Command` | 节点返回的 `goto` | 节点返回的 `update` |

从普通边到条件边，是把"往哪走"从建图时挪到了运行时；从条件边到 `Command`，是把"往哪走"和"改什么"从两个地方合回一个返回值里。图还是那张图，控制权一步步交给了节点自己。

> **承前启后**：上一节讲完「自定义 Reducer 与图控制流：状态怎么拼，节点往哪走」，下一节接着讲「用 LangGraph 手搓一个 Agent」。

## 用 LangGraph 手搓一个 Agent
> 对应块：BLK46 | 覆盖分集：P173-P175 | 块标题（分集名）：《用 LangGraph 构建 Agent》

到这里，LangGraph 的入门部分算是过了一遍：节点能定义，状态能定义，边也能连，各种复杂的图都拼得出来。可有一件事一直没干——我们还没让模型开口说过一句话。

所以接下来要做的，就是用 LangGraph 构建 agent。

这事听起来像另开一个大话题，其实拆开看特别朴素：构建一个 agent 无非是加入模型调用；模型调用本身就是一段代码；代码能不能封装进节点里？能。那就没有新东西了，只是把"调模型"这段代码塞进一个节点，再把节点连成图。

> **结论**：最小的 agent 不需要任何额外的框架概念——一张只有三个节点的图，其中一个节点的函数体里调一次模型，它就已经是 agent 了。

### 从一个只会调模型的图开始

要做的图就三个节点：开始、调用模型、结束。

```text
START ──► llm（调用模型） ──► END
```

这就是一张最普通的线性图，从头到尾只有一条路。

按之前讲过的基本流程，操作 LangGraph 的顺序是：先创建 state，再创建节点，然后添加边，把节点连成 graph，最后调用 graph。今天在这条流程最前面再加一步——初始化模型。道理很简单：你要调模型，总得先有一个模型。

所以整段代码的顺序是：初始化模型 → 创建 state → 创建节点 → 添加边 → 编译 → 调用。

先初始化模型。模型名传进去，理论上只传这一个参数就够了；如果想控制它的行为，还可以用 `extra_body` 把思考关掉——把 thinking 的 type 设成 `disabled`，让它别在那儿想半天。

```python
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()

model = init_chat_model(
    "deepseek-v4-flash",
    extra_body={"thinking": {"type": "disabled"}},
)
```

这里的 `load_dotenv()` 不是可有可无的。不传 API Key 的时候，模型会自己去读环境变量；先把 `.env` 读进环境变量，就不用每次手动传 key——偷个懒，它自动就取到了。

接着创建 state。名字随便起，叫 `LLMState` 就行，是个模型调用的 state，没有什么特殊用意。要紧的是必须继承 `TypedDict`，这一点千万别忘。

state 里放什么？我们一再强调过：state 里存的是你传进去的东西和运行产生的结果。那这是一个模型调用的 state，传进去的就是用户的提问，返回的就是 AI 给的结果。所以两个字段：`input` 和 `output`。叫 `response` 也行，不必跟笔记一字不差。

```python
from typing import TypedDict

class LLMState(TypedDict):
    input: str
    output: str
```

有了 state 就能创建节点了，这里只需要一个节点。节点的入参一定要是 state，类型标注上 `LLMState`；函数体里干的事就是调模型回答用户问题。

调模型是 `model.invoke`，最简单的方案是直接传字符串，而 `state["input"]` 里正好就是用户那句话。拿到响应之后，把文本取出来写进 `output`。

```python
def llm_node(state: LLMState):
    response = model.invoke(state["input"])
    return {"output": response.text}
```

这里取的是 `response.text` 而不是 `response.content`：`content` 是原始的内容块，`text` 才是最终拼好的纯文本，更专业一点的说法就是用 `text`。

最后建图。`StateGraph` 里的泛型参数是 state 的类型；builder 拿到手之后添加节点、添加边——起点是 `START`，从 `START` 连到 `llm`，再从 `llm` 连到 `END`，最后编译。

```python
from langgraph.graph import StateGraph, START, END

builder = StateGraph(LLMState)
builder.add_node("llm", llm_node)
builder.add_edge(START, "llm")
builder.add_edge("llm", END)

graph = builder.compile()
```

编译完如果想眼见为实，可以把图的拓扑渲染出来看一眼；这纯属可选项，不画也不影响后面调用。

调用就一句 `graph.invoke`，传进去的字典就是 state 的初值——这里只传 `input`：

```python
result = graph.invoke({"input": "你好，你是谁"})
print(result)
```

```text
{'input': '你好，你是谁', 'output': '你好呀，我是 DeepSeek……'}
```

跑通了。

回头看这一段，其实和我们前面写的那些图没有任何区别：创建 state、创建节点、添加边连成图。唯一的变化是模型节点里多了一次模型调用。

只不过大家对调模型这段代码可能有点生疏了，这里把最容易混的地方摆清楚：

> **提示**：直接调模型和调 agent 长得像，入参与返回却完全不同。`model.invoke(...)` 收的是字符串或 `BaseMessage` 的列表，返回的是一个 `AIMessage` 对象；`agent.invoke(...)` 收的是一个字典（里面有 `messages`），返回的也是字典（里面也有 `messages`）。两边别搞错。

模型这一侧，传字符串可以，传 `HumanMessage` 这类消息对象也可以；但传消息对象时必须给列表。这一点在下一版改造里马上就会撞上。

### 把字符串换成消息对象

图虽然跑通了，但有个地方越看越别扭：输入是一条字符串，输出也是一条字符串。可对 LangChain 来讲，人家是有专业的 message 类型的，我们这里全用裸字符串，就显得有些业余了。

那就把输入和输出都改成基于 LangChain 的 message 方式，这样更专业一点。

先改输入：不要字符串了，用 message。用户输入叫什么 message？`HumanMessage`。输出的叫什么？`AIMessage`。于是 state 的两个字段类型跟着换：

```python
from langchain_core.messages import HumanMessage, AIMessage

class LLMState(TypedDict):
    input: HumanMessage
    output: AIMessage
```

节点里也跟着改。既然 `state["input"]` 取出来本来就是 `HumanMessage`，直接传给 `invoke` 看起来顺理成章——但这样一跑就报错，它说参数只接受 string 或者 list。

原因就是上一节那条规矩：模型要么收字符串，要么收 `BaseMessage` 的列表。你塞进去单个 message，它不认。所以哪怕只有一条消息，也要拿列表包起来：

```python
def llm_node(state: LLMState):
    response = model.invoke([state["input"]])
    return {"output": response}
```

返回值这一侧反而更省事了。`response` 本身就是 `AIMessage`，不用再取 `.text`，直接把对象放进 `output` 就行。

调用时同理，`input` 不能再传字符串，得传一个 `HumanMessage`：

```python
result = graph.invoke({"input": HumanMessage("你好，你是谁")})
print(result)
```

打印出来的这一版，`input` 是一条 `HumanMessage`，`output` 是一条 `AIMessage`——专业了。

> **易错点**：只要走 message，就必须是 message 的列表，哪怕只有一条。`model.invoke(HumanMessage(...))` 这种写法必错，`model.invoke([HumanMessage(...)])` 才对。

### 所有轮次收进一个 messages 列表

专业是专业了，但这一版有个硬伤：`input` 和 `output` 是两个分开的字段，一旦要多轮交互，第二次调用就会把第一次的 `input` 覆盖掉，`output` 也一样。

模型永远只看得到最后一句话，这不叫对话。

所以换个思路：别分输入输出了，把它们合到一起，起个名字叫 `messages`，做成一个消息的列表。将来输入的放到这里边，输出的也从这里取、也放回这里。

列表里放什么类型？`HumanMessage`、`AIMessage` 都继承 `BaseMessage`，所以标 `BaseMessage` 就行，两类都能装：

```python
from typing import Annotated
from operator import add
from langchain_core.messages import BaseMessage

class LLMState(TypedDict):
    messages: Annotated[list[BaseMessage], add]
```

注意这里多出来的东西：光写 `list[BaseMessage]` 不够，还得加 reducer。因为 state 默认的更新语义是覆盖——你返回什么，它就变成什么。要让它能不断往里面拼，就得用 `Annotated` 给这个字段挂一个 `add`（也就是 `operator.add`）。有了它，新旧值走的是列表拼接，而不是替换。

state 改造完，节点跟着改两处。

取值这一处变简单了：`state["messages"]` 取出来本来就是列表，直接丢给模型，不用再包一层。

返回这一处要多包一层：`response` 是一条 `AIMessage`，但 reducer 干的是"列表 + 列表"，所以必须用列表装一下再返回，让拼接去完成剩下的活。

```python
def llm_node(state: LLMState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}
```

图和上一版完全一样，一行都不用动。调用时字段名换成 `messages`，值还是列表：

```python
result = graph.invoke({"messages": [HumanMessage("你好，你是谁")]})
print(result)
```

返回的是一个字典，字典里 `messages` 是一个列表：第一条 `HumanMessage`，第二条 `AIMessage`。

数据是怎么一点点攒起来的，画出来最清楚：

```text
invoke({"messages": [HumanMessage]})
        │
        ▼
    ┌────────┐
    │ START  │
    └───┬────┘
        │  state["messages"] = [Human]
        ▼
   ┌──────────┐
   │ llm_node │
   └────┬─────┘
        │  model.invoke(state["messages"]) ──► AIMessage
        │  return {"messages": [AIMessage]}
        ▼
   reducer: 旧 [Human] + 新 [AI] = [Human, AI]
        │
        ▼
    ┌────────┐
    │  END   │
    └────────┘
```

一次调用里 reducer 会被用两次：进来时把外部传的消息并进空列表，模型答完后再把 `AIMessage` 并进已有列表。

这里最容易糊涂的是 reducer 到底什么时候被调用、`old` 和 `new` 各是什么，把执行过程拆开看一遍就清楚了：

| 时刻 | old（已有值） | new（本次返回） | state 落库结果 |
| :--- | :--- | :--- | :--- |
| invoke 进入图 | 空 | `[HumanMessage]` | `[HumanMessage]` |
| 进入 `llm_node` | — | — | `[HumanMessage]`，整包传给模型 |
| 节点返回后 | `[HumanMessage]` | `[AIMessage]` | `[HumanMessage, AIMessage]` |

第一次进图时，传进去的字典就是 state 的初值，`messages` 原本是空的；reducer 收到一个空的 `old` 和一个装着 `HumanMessage` 的 `new`，拼出一条消息。

接着走到模型节点，此时 `state["messages"]` 里只有这一条 `HumanMessage`，把它整包传给模型，就是发起了一次调用。

模型回来的是 `AIMessage`，节点返回 `{"messages": [AIMessage]}`；更新 state 时 reducer 再次被调用，`old` 是 `[HumanMessage]`，`new` 是 `[AIMessage]`，两个列表拼到一起，列表里就既有 `HumanMessage` 又有 `AIMessage` 了。

> **结论**：`AIMessage` 不是节点自己 append 进去的，是 reducer 拼进去的。节点只负责"返回一个装了新消息的列表"，合并这件事由 state 的 reducer 完成。

到一个字段里同时存下所有消息，这件事就成了。

### 越看越像 Agent 的调用约定

写完这一版，再盯着调用方式看一会儿，会觉得眼熟。

传入的是一个字典，字典里有 `messages`，`messages` 是一个消息列表；返回的也是一个字典，字典里也有 `messages`，装的也是消息列表。

在哪见过？用 LangChain 调 agent 的时候就是这样：传字典，字典里 `messages` 装着 `HumanMessage`；返回也是字典，里面是消息列表。阻塞调用是这样，改成流式调用还是这样，一模一样的形状。

不是巧合。LangChain 的 agent 底层就是 LangGraph。

点进 `create_agent` 的源码看，它最后的返回值类型写着 `CompiledStateGraph`——`StateGraph` 是 builder，编译之后得到的就是 `CompiledStateGraph`。我们这一路写下来，`StateGraph(...)` 加 `compile()`，产出的正是同一个东西。

所以以前当作黑盒用的 agent，内部结构就是刚才这几样：一张图、一个 state、state 里一个 `messages` 列表、一个负责追加的 reducer。

你 `invoke` 时传的字典，就是 state 的初值；模型答完，`AIMessage` 通过 reducer 追加进列表；下一轮列表更长，模型看到的就是完整上下文。

> **结论**：agent 所谓的"记忆"，不是模型记住了什么，而是 state 里的消息列表越来越长，每次调用都把整包消息重新喂给模型。

这么一看，今天写的不是"另一个框架的入门"，而是把以前调过的 agent 拆开看了一遍内部。

### 用现成的 MessagesState

那以后写 agent，难道每次都要手写一遍 `messages` 列表 + reducer？

不用。LangGraph 里备好了一个默认 state，叫 `MessagesState`。

点进去看，里面就是一个 `messages` 字段，类型是消息列表（它起的名字叫 `AnyMessage`，作用和我们的 `BaseMessage` 一样），后面挂着一个 `add_messages`——那是它自带的 reducer，专门负责消息拼接。

也就是说，`MessagesState` 跟我们手写的那个类长得一模一样。既然一模一样，就没有理由再手写一遍：

- 想加自己的字段，就继承 `MessagesState` 再写；
- 没有额外字段，继承之后 `pass` 就完事；
- 连继承都省了，直接拿它当 state 类型用也可以。

于是整个 state 定义可以整段注掉，改造后的完整代码只剩这么几行：

```python
from langgraph.graph import StateGraph, START, END, MessagesState

def llm_node(state: MessagesState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(MessagesState)
builder.add_node("llm", llm_node)
builder.add_edge(START, "llm")
builder.add_edge("llm", END)

graph = builder.compile()

result = graph.invoke({"messages": [HumanMessage("你好，你是谁")]})
```

调用方式跟以前调 agent 完全一致：传一个字典，字典里 `messages` 装一条 `HumanMessage`。

流式调用同样能跑。因为编译出来的就是同一个东西，没有理由不支持——把它换成流式接口，传同一个字典，从流里逐块取 `.text` 打印出来，打印时把 `end` 设成空字符串、`flush` 设成 `True`，就能像打字机一样一段一段往外吐。

> **提示**：手搓到这里，你已经写出一个 agent 了。真正的难点不在 API，而在时刻记住 `messages` 是一个列表：从 state 里取出来是列表，往 state 里返回时也要先装进列表。

### 加 checkpointer 才有会话记忆

历史消息是有了，可它只是内存里的一个列表。程序一停，消息就没了。

要让消息持久化保存、形成真正的会话记忆，还得给它加 checkpointer——这个概念前面学过，LangGraph 同样支持。

要注意挂载的位置：不是在 `create_agent` 的时候指定，而是在 `builder.compile()` 编译的时候传进去。这是和以前用 agent 时最大的差别。

演示用内存版就够：

```python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
```

编译完，这个 graph 就不只有历史消息，还有 checkpointer 做持久存储，具备了会话记忆的功能。

光有 checkpointer 还不够，调用时必须告诉它"这是哪个会话"，所以要准备一个 config，里面放 `thread_id`，值随便写，这里用 `T1`：

```python
config = {"configurable": {"thread_id": "T1"}}

result = graph.invoke({"messages": [HumanMessage("12 个苹果平均分给 3 个人，每人分几个？")]}, config)
print(result)
```

它答 4 个。接着再问一句，这次只发新问题，不重复前提：

```python
result = graph.invoke({"messages": [HumanMessage("如果是 4 个人呢？")]}, config)
print(result)
```

答 3 个。

凭什么它能接上？看返回的 `messages` 列表就明白了：里面依次是 `HumanMessage`（第一轮提问）、`AIMessage`（第一轮回答）、`HumanMessage`（第二轮提问）、`AIMessage`（第二轮回答）——两轮对话都在。

```text
thread_id = "T1"
   │
第 1 轮  invoke({"messages": [Human]})
   │      └─► checkpointer 存下 [Human, AI]
   ▼
第 2 轮  invoke({"messages": [Human]})   ← 只发新问题
   │      └─► 读回 [Human, AI]，reducer 把新消息追加进去
   ▼          得到 [Human, AI, Human]，模型看到完整上下文，答出 3 个
```

第二轮之所以能拼上，靠的还是那个 reducer：checkpointer 把上一轮的 state 取了回来，新的 `HumanMessage` 通过 `add` 拼进旧列表，模型拿到的就是三条消息（两问一答），自然知道"4 个人"是在接着上一题问。

> **结论**：在 LangGraph 里做会话记忆，用的还是 checkpointer，但指定位置变了——不是 `create_agent` 时，而是 `builder.compile()` 编译时；调用时把 `thread_id` 放进 config 传进去，剩下的和以前一模一样。流式调用也照传 config。

到这里，一个能对话、能记住上下文的 agent，就是自己一行一行搭出来的了。

## 工具型 Graph 与工作流模式
> 对应块：BLK47 | 覆盖分集：P176-P178

到上一节为止，我们搭出来的 graph，模型只会干一件事：你给它消息，它还你一句话。它没有调工具。

而一旦要在 graph 里调工具，整个流程立刻就变得非常"变态"。

为什么？因为模型自己执行不了函数。它只能"说"——我要调哪个工具、参数是什么。真正把函数跑起来、把返回值拿回来的，仍然是我们自己的 Python 代码。

所以要跑通一次工具调用，就得这么走：先把用户的问题和本地有的工具一起发给模型，让模型思考要不要调工具、要调哪个；模型返回说我要调 `get_weather`，参数是杭州；然后我们手动去调这个工具；调完再把结果返回给模型；模型最后生成答案。

一条用户提问，中间两次模型调用，还要我们夹在中间做一次解析和一次转发。这就是全部复杂度的来源。

```text
请求
  │
  ▼
模型节点 ──思考──▶ 要不要调工具？调哪个？
  │
  │ 返回 AIMessage，里面带 tool_calls（工具名 + 参数 + 调用 id）
  ▼
工具节点 ──按名字查字典──▶ 手动 invoke 工具，拿到结果
  │
  │ 把结果封装成 ToolMessage，带上对应的 id
  ▼
模型节点 ──再思考──▶ 还要不要继续调？
  │
  │ 不需要了
  ▼
最终答案
```

读这张图：中间那一段是可以重复的。模型调完一次工具、拿到结果，可能觉得还不够，还要再调一次；也可能觉得够了，直接回答。所以真实的形状不是一个直线流程，而是一个带出口的环。

### 带工具的 Graph 到底复杂在哪

把上面那条流程落到节点上，就只有两个节点。

模型节点负责调模型。它的职责是思考：要不要调工具、要调哪个。工具节点负责解析模型返回的结果，从里面找出要调的工具，完成调用，再把结果发回给模型，让模型再思考要不要继续调。

听起来两个节点而已，但麻烦都在细节里：模型的返回不是一个函数调用，而是一段结构化的描述，你得写代码去解析它；解析出来可能是零个、一个、好几个调用；调完的结果不能随便扔回去，得包成模型认识的工具消息；最后还得判断这次要不要继续。

> **提示**：这一节的代码不要求你们会写，我讲它只是让你们知道 agent 底层在转什么。真要写带工具的 agent，后面有省事得多的办法。你现在要带走的是这张流程图的形状，以及两个节点各自管什么。

### 工具、按名索引的字典，与一次手动调用

新建一个 notebook，先把依赖导进来。工具的定义跟以前在 LangChain 里没有任何区别：一个 `get_weather`，注释写清楚是查城市天气，内部放北京、上海、杭州三条假数据，传进来的 `city` 在字典里就返回对应天气，找不到就返回"未找到"；再加一个算平方根的 `sqrt`。平方根这个工具其实可以不要，放着只是让"多个工具"这件事成立。

两个工具定义完，第一个真问题就来了：AI 返回的结果里只会告诉你"我要调 `get_weather`"，它给的是一个**名字**，一个字符串。你怎么根据名字找到那个函数？

得有一张表：key 是工具名，value 是工具本身。

```python
tools = [get_weather, sqrt]

tools_by_name = {tool.name: tool for tool in tools}
```

一个推导式，遍历 `tools`，用 `tool.name` 当 key，用工具自己当 value。于是这个字典的 key 就是 `get_weather` 和 `sqrt`，值就是那两个工具。将来不管谁给我一个工具名，我 `tools_by_name[name]` 一下就能拿到工具。

拿到之后怎么调？这里有个容易忽略的点。你拿到的不是普通函数，是 LangChain 包装过的 `StructuredTool`：它有 `name`、有 `description`、底层才是那个函数本身，同时它带一个 `invoke` 方法。

```python
tools_by_name["get_weather"].invoke({"city": "北京"})
```

传北京，得到晴天 25 度；传杭州，得到小雨 22 度。注意 `invoke` 的入参**必须是一个字典**，key 是参数名，不是位置参数。这个"必须传字典"的规矩，等一下会和模型返回的 `args` 严丝合缝地对上——不是巧合，是 LangChain 有意把两边对齐的。

> **易错点**：编辑器的补全里可能看不到 `invoke`，因为这时变量的类型还没声明。声明类型之后它就在了，不用怀疑工具被包坏了。

### 绑定工具：把工具说明交给框架去拼

模型这块跟前面一样，`init_chat_model` 指定模型名，再用 `extra_body` 补上厂商特有的参数。代码不重写，直接复制。

真正要加的是下一步。调模型的时候，得把工具清单一起发过去，否则模型根本不知道你手里有什么工具。你要是自己发，就得在请求里塞一个 `tools` 字段，把每个工具的名字、描述、参数 schema 一坨一坨拼成 JSON。

LangChain 把这件苦力收了：

```python
model_with_tools = model.bind_tools(tools)
```

`bind_tools` 接收工具列表，返回一个绑好了工具的模型。以后你调 `model_with_tools`，它会自动把工具的参数信息封装进请求，不用你手动组织。

> **定义**：绑定不是把工具塞进模型里，只是给模型配了一份"可用工具清单"。真正执行工具的仍然是你的 Python 代码，模型只负责挑。

### 模型返回的 tool_calls 长什么样

在写节点之前，先手动调一次，看看它到底返回什么。传一条"杭州天气如何"，打印出来。

返回的是一条 AIMessage，里面多了一个 `tool_calls`，是个列表。列表里每个元素是个字典，三个字段最要紧：

```text
tool_calls = [
    {
        "name": "get_weather",        # 要调的工具名，就是函数名
        "args": {"city": "杭州"},      # 参数，已经是字典
        "id":   "call_xxxxxxxx",      # 这一次调用的唯一标识
    },
]
```

看到这个结构，前面两件事一下就通了：`name` 拿去查 `tools_by_name`，`args` 直接喂给 `invoke`。

```python
response = model_with_tools.invoke([HumanMessage(content="杭州天气如何")])
tool_call = response.tool_calls[0]

tool = tools_by_name[tool_call["name"]]
result = tool.invoke(tool_call["args"])
```

跑出来是"小雨 22 度"。这条链路一通，工具节点就没有任何神秘感了——它干的不过是把上面这几行放进一个循环，再把结果包成消息。

`id` 现在还没用上，先记着，封装工具消息的时候少不了它。

### 模型节点：换成带工具的模型就行

```python
def llm_node(state: MessagesState):
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response]}
```

跟之前的模型节点一模一样：从 state 里取出消息列表，调模型，把 response 塞进列表返回。唯一的区别是用 `model_with_tools` 而不是 `model`。State 也不用自己定义，直接用 `MessagesState`。

别急着说这很简单。节点确实没变，但它返回的东西变了：response 里现在可能带着 `tool_calls`。后面所有的分支判断、循环、消息封装，全是冲着这个字段来的。

### 工具节点：循环解析、执行、封装 ToolMessage

工具节点要干的事很具体：取出 state 里最后一条消息（一定是 AI 那条），从里面拿 `tool_calls`，挨个调工具，把结果封成消息还回去。

第一个坑：不能写 `tool_calls[0]`。我演示结构的时候用了 `[0]`，那只是为了看清楚里面长什么样。你问一句"杭州和北京天气如何"，模型一次就返回两个 tool_call：一个 name 是 `get_weather`、args 里 city 是杭州，另一个 name 还是 `get_weather`、args 里 city 是北京。同一个问题里可以有多次调用，所以这里必须循环。

第二个坑是反向的：也可能一个都没有。你问一句"你好"，返回里根本没有 `tool_calls`，那就什么都不用做，直接结束。

```python
def tool_node(state: MessagesState):
    tool_calls = state["messages"][-1].tool_calls

    if len(tool_calls) <= 0:
        return {"messages": []}

    tool_messages = []
    for tool_call in tool_calls:
        tool = tools_by_name[tool_call["name"]]
        result = tool.invoke(tool_call["args"])
        tool_messages.append(
            ToolMessage(content=result, tool_call_id=tool_call["id"])
        )

    return {"messages": tool_messages}
```

第三个坑，也是最容易漏的：工具的执行结果不能直接扔回消息列表，得包成 `ToolMessage`。这个类型就是专门表示"工具说的话"的消息，它至少要有两样东西——`content` 是执行结果，`tool_call_id` 是这次调用对应的 id。

为什么非要带 id？因为一次可能回去好几条工具消息。模型得知道哪条结果对应它哪一次调用，不然两个城市的天气它就对不上号。id 是模型发起调用时自己生成的，每次调用各不相同，我们原样带回去就行。

返回值仍然是字典，`{"messages": [...]}`。列表里的消息会被 state 的 reducer 自动拼接到已有消息后面，不用你手动合并。

> **提示**：这一段我第一次看也没看懂，正常。所以前面反复说这个不要求你们会写——它需要你手动解析模型返回的结构，再手动把结果拼回消息协议里，纯体力活。

### 条件边：有 tool_calls 才去工具节点

模型节点之后，走向是不确定的：模型要调工具，就去工具节点；模型能直接答（比如你只是问"你好"），就该结束。这是一条条件边，不是普通边。

判断依据简单得有点意外：看最后一条消息里有没有 `tool_calls`。

```python
def should_continue(state: MessagesState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return END
```

有就返回 `"tools"`，去工具节点；没有就返回 `END`，直接结束。这就是所谓的条件路由，整张图唯一的"智能"就长在这三行里。

### 把这张图搭起来并跑通

```python
builder = StateGraph(MessagesState)

builder.add_node("llm", llm_node)
builder.add_node("tools", tool_node)

builder.add_edge(START, "llm")
builder.add_conditional_edges("llm", should_continue, ["tools", END])
builder.add_edge("tools", "llm")

graph = builder.compile()
```

一段一段看：

- `StateGraph(MessagesState)`：状态直接用消息列表，自带 `add_messages` 这一层 reducer；
- 两个节点，`llm` 和 `tools`，就这两个；
- `START → llm`：请求一进来先进模型；
- `llm` 出去是条件边，交给 `should_continue` 决定，候选只有 `tools` 和 `END`；
- `tools → llm`：工具执行完必须回到模型，让它基于工具结果再想一次。

最后这条边我第一遍写的时候漏了。打印图的时候才发现工具节点是个死胡同——执行完没有出边，流程就断在那儿了。

```text
              START
                │
                ▼
           ┌─────────┐  没有 tool_calls   ┌─────────┐
           │   llm   │ ─────────────────▶ │   END   │
           └────┬────┘                    └─────────┘
                │ 有 tool_calls
                ▼
           ┌─────────┐
           │  tools  │
           └────┬────┘
                │ 执行完必须回到 llm
                └──────────────▶ llm
```

读这张图：`llm` 是唯一的判断点，它要么直接结束，要么去 `tools`；`tools` 没有选择权，必须回 `llm`。这就是 agent 的底层形状——一个大循环，出口只有一个，就是模型不再要求调工具的那一刻。

跑一下：

```python
response = graph.invoke(
    {"messages": [HumanMessage(content="杭州和北京天气怎样")]}
)

for m in response["messages"]:
    m.pretty_print()
```

`invoke` 传的是字典，返回的也是字典，所以取消息要写 `response["messages"]`。

消息列表是这样一层层长起来的：

```text
第 1 轮 llm 之后  :  Human, AI(tool_calls×2)
工具节点执行之后   :  Human, AI(tool_calls×2), Tool, Tool
第 2 轮 llm 之后  :  Human, AI(tool_calls×2), Tool, Tool, AI(最终答案)
```

打出来的过程对得上：human 问杭州和北京天气；AI 返回两次调用，参数分别是杭州和北京；接着两条 ToolMessage，是我们自己的工具节点封的，内容是两地天气；最后一条 AI 说，根据最新的天气信息，杭州小雨记得带伞，北京天气不错适合活动。

用 debug 单步走一遍更直观：进 `llm`，看 response 里确实有两条 `tool_calls`；跳到 `should_continue`，判断出有工具调用；进 `tools`，第一个 tool_call 查杭州拿到结果封装，第二个查北京拿到结果封装；两条消息拼进列表；回到 `llm`，这次它看到的是 1 条 human + 1 条 AI + 2 条 tool；生成最终答案，又回到 `should_continue`，这次没有 `tool_calls`，走 `END`。

这一遍走下来，我关心的不是你能不能默写这段代码——是这条流程你能不能讲明白：请求进来先去哪，凭什么拐弯，拐完为什么必须回来。

state 在循环里不断变长，所以那个 reducer 必须是 `add_messages` 这种"追加"语义，不能是覆盖。

### 预定义节点：ToolNode 与 tools_condition

回头复盘一下，这一整段里最复杂的是哪两块。

一是工具调用节点——取 name、取 args、取 id，循环、invoke、封 `ToolMessage`；二是 `should_continue` 那个路由判断。其余的呢？工具定义是以前写过的，模型只是多了个 `bind_tools`，模型节点一行没改。

所以真正麻烦的就这两块。而这两块又是完全通用的：任何带工具的 agent 都要写一遍同样的东西。LangGraph 干脆把它们预置好了，一个叫 `ToolNode`，一个叫 `tools_condition`。

把自己写的工具节点删掉，换成：

```python
from langgraph.prebuilt import ToolNode, tools_condition

builder.add_node("tools", ToolNode(tools))
```

`ToolNode` 的第一个参数要传工具列表本身，不是工具名的字符串。因为节点内部的活它替你干了，但它总得知道有哪些工具可调、每个工具怎么调。

`should_continue` 也删掉，条件边直接换成 `tools_condition`：

```python
builder.add_edge(START, "llm")
builder.add_conditional_edges("llm", tools_condition)
builder.add_edge("tools", "llm")
```

`tools_condition` 内部就是我刚写的那段：取最后一条消息，用 `hasattr` 看它有没有 `tool_calls`，有就返回 `"tools"`，没有就返回 `END`。它连返回值的映射都替你约好了，所以不用再传候选节点列表。

于是整份代码缩成四步：定义工具 → 定义模型并绑定工具 → 定义模型节点 → 拼图。原来的工具节点和条件函数全没了，图的结构一点没变。跑一遍，问杭州和北京，两次工具调用、两条结果、一句最终回答，跟手写版一模一样。

### 那还需要自己写吗：create_agent 与它的适用边界

> **结论**：这段代码同样不要求你们写。

要一个带工具的 agent，LangChain 里有 `create_agent`，一行就是这个效果，跟手搭出来的图完全等价。

那为什么还要看这一层？两种情况你会真的自己搭：

- 公司的 agent 有很多自定义的东西，不想用 `create_agent` 这个黑盒；
- 你想把细节全部攥在自己手里，比如工具节点里要加日志、加权限校验、加人工确认，或者模型节点前后要插自己的处理。

这时候预定义节点不够用了，你得自己写节点、自己连边。

除此之外，90% 的情况都没必要。我本来都不打算讲这一节，是你们非要听的——不过既然看了，以后别人给你一张 agent 的图，你至少知道里面那个环是怎么转起来的，知道哪一段在解析、哪一段在兜底。

### 工作流模式：LangGraph 真正要解决的问题

到这儿，LangGraph 的大部分内容我们过完了：能用节点和边组成工作流，能定义 agent。

但这不是学 LangGraph 的目的。最开始讲的时候我说过，它最重要的事情是**提高复杂智能体的稳定性**——在完全由 AI 自主的 agent 之上再加一层编排，让它既有 AI 的能力，又能按照我们要求的路径去做事。

怎么加？就是工作流编排。官方文档在 workflows 和 agents 这两块给出的模式，workflows 五种，agents 一种，一共六种。

这六种其实分两档。前一档比较简单：模型只是工作流里的一个节点，走到哪个节点、走几条分支，全由你画的边决定。后一档更复杂：不只是让模型当节点，还让模型来主导工作流的执行路径——走哪条路，模型说了算。

| 模式 | 谁决定走哪条路 | 形态 | 典型场景 |
| :--- | :--- | :--- | :--- |
| 串行 prompt chaining | 边写死 | 模型 A → 模型 B → 结束 | 先起草，再润色 |
| 并行 parallelization | 边写死 | 一份输入分多支，最后合并 | 同一份材料多角度同时处理 |
| 编排者 orchestrator-worker | 编排模型 | 拆任务 → 多个 worker → 汇总 | deep research 写研究报告 |
| 评估优化 evaluator-optimizer | 评估模型 | 生成 ↔ 评估，循环迭代 | 写小说、反复打磨 |
| 路由 routing | 路由节点 | 认意图 → 派到不同分支 | 一个入口处理多种任务 |
| agent | 模型自己 | 模型循环决定调什么工具 | 开放式任务 |

前五种是 workflow，模型只是里面的一个节点或一个调度角色；最后一种是 agent，路径完全交给模型自己走。

#### 串行与并行

串行就是最基本的 prompt chaining：调模型，把输出喂给下一个模型，最后结束。整条路径是边写死的，模型没有选择权。

并行是 parallelization：同一份输入分给几个分支同时处理，再把结果合并。

串行我们前面已经写过，并行只是把同一步横向铺开成几条支路。两者的共同点是——模型只是工作流里的一个普通节点，跟一个函数、一次数据库查询没有本质区别。路径由你画，模型负责干活。

#### 编排者模式

编排者（orchestrator-worker）多了一个角色：有一个人专门负责编排。

它把一个大任务拆成若干子任务，分给不同的 worker 去执行，最后把结果汇总成一份答案。

最典型的例子是 deep research 这类做研究报告的 agent。你给它一句话："我想开发一个游戏，帮我写一份研究报告。"它不会自己一口气写完，而是把这件事拆开——市场调研、竞品分析、技术方案各一路——分给不同的 worker，最后合并成报告。

适合的就是这种场景：任务复杂、能拆成几块互不依赖的子任务、最后需要一个统一答案。

#### 评估优化模式

这一种是两个角色唱双簧：一个 evaluator（评估员），一个 optimizer（优化器）。

先生成一版，交给 evaluator 评估，评估报告再回给生成方，让它照着改，改完再评，来回迭代，直到结果能看。

写小说是最贴切的场景：先让模型写一章，评估员挑出节奏、人物、逻辑上的问题，模型带着这些问题重写。

它和 agent 的循环不一样：agent 是自己判断"我还要不要再调一次工具"，评估优化的循环判据在评估者手里——是另一个角色在说"还不行，再改"。

#### 路由模式

路由（routing）解决的是入口问题：你有一个入口，但背后有很多种完全不同的任务。

做法是先识别用户意图，再按意图把请求派到对应的下游节点或子流程，让各自干各自的活。

这种模式在我们项目里会用到，也是下面要动手做的。串行和并行前面演示过了；编排者和评估优化在项目里用不上，就不展开了，官网 workflows 那一栏每种模式都有示例，有兴趣自己翻。

## 意图路由与子图嵌套
> 对应块：BLK48 | 覆盖分集：P179-P183 | 块标题（分集名）：《路由模式与子图嵌套》

前面我们看过几种 Workflow 的组织方式，接下来讲其中最常见的一种：routing，路由。这个模式太常见了，常见到你几乎每个像样的智能客服里都能翻出它的影子。

它的活儿其实一句话就能说完：接收用户的输入，把请求引导到与用户请求相关的那几个任务节点上。

拿电商的智能客服打比方。用户进来第一句话可能是"这个手机还有货吗"，也可能是"我要退货"，还可能是"我买的耳机坏了怎么赔"。这几件事背后要干的活完全不一样，所以在动手之前，它得先判断这句话属于哪一类问题，然后把请求路由到售前咨询、退款、退货这些各自对应的节点上去。知识问答机器人也一样，先识别问题落在哪个知识领域，再把请求交给那个领域的专业节点。

说白了就是分工。活儿拆开，分给不同的节点去干，中间站一个路由节点，专门负责判断"用户这句话属于哪一种类型"，判完了再交给具体节点去干活。

```text
                    ┌──────────────────┐
   用户请求 ──────▶ │   route（路由）   │  识别意图 / 问题类型
                    └────────┬─────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
   售前咨询节点          退款节点             退货节点
   （各干各的活）        （各干各的活）       （各干各的活）
```

看这张图就明白这个模式的意思了：将来我可以写一个售前咨询节点、写一个退款节点、再写一个退货节点，用户请求来了以后由 route 识别意图，根据意图派发到不同的节点，各自完成对应的工作。

### 先把需求立起来：三个节点加一个意图识别

光看图不过瘾，我们直接写一个能跑的工作流。为了不把业务搞复杂，需求就定成三个干活的节点加一个判意图的节点：

- 天气节点，负责查天气；
- 闲聊节点，负责闲聊；
- 翻译节点，负责翻译；
- 再加一个意图识别节点，叫 route。

用户问题进来以后，先由意图识别节点判断用户想干什么，判断结果存到 state 里，state 里专门有一个字段叫 `intent`，也就是意图。然后由条件边根据这个 `intent` 判断到底进闲聊、天气还是翻译。最后各节点干完活，把结果发给用户。

```text
   START ──▶ route ──┬──▶ chat（闲聊）─────────┐
   （用户请求进来）    │                        │
                     ├──▶ weather（查天气）────┤
                     │                        │
                     └──▶ translate（翻译）────┤
                                              ▼
                                             END
```

整张图就这么点东西，需求清楚，下面直接开写。

### 写图的老四步，state 直接继承 MessagesState

按 LangGraph 定义图的一般流程，第一步通常都是先定义模型——有了模型才能往下用。模型这块不用重新写，把前面写过的 `init_chat_model` 那段直接拿过来就行。

第二步定义 state。我们这个 state 里其实有两部分内容：第一部分是 agent 工作流里的历史消息，这部分从今往后都不用我们自己操心，全放进 `messages` 里就行；第二部分是意图，因为后面要根据意图判断往哪走，所以你必须把意图存下来，字段就叫 `intent`。

不用从零定义这个 state。从零写的话，你得自己写 `messages` 字段，还得写 `Annotated` 那一堆，反而麻烦。正确姿势是写个类继承 `MessagesState`：

```python
from langgraph.graph.message import MessagesState


class IntentState(MessagesState):
    intent: str
```

继承下来，`messages` 的能力就直接具备了——`MessagesState` 里本来就是用 `add_messages` 这个 reducer 管着消息列表的，多条消息进来会自动累加而不是覆盖。我们在这基础上加一个 `intent` 记录用户意图，就完事了。

第三步定义节点，节点负责干活。第四步创建 graph，用 `edge` 把节点连起来。下面按这个顺序走。

### 意图识别节点：把判断权交给模型

意图识别这件事，往往得由模型来做，不是人来做。因为用户就说了一句话，"这句话到底要干啥"——我们的代码能判断出来吗？判断不出来。只有模型能判断。

所以这个节点要做的事情就是调用模型，让模型帮我们分析用户的意图。调用的时候照例带一个系统提示词：

```python
def intent_node(state: IntentState):
    system_prompt = (
        "请根据用户的请求判断用户的意图，"
        "可选的意图有 weather、translate 和 chat。"
    )
    query = state["messages"][-1].content
    response = llm.invoke([
        SystemMessage(content=system_prompt),
        HumanMessage(content=f"用户问题：{query}"),
    ])
    return {"intent": response.content}
```

提示词为什么这么写？因为接下来那三个节点的名字刚好就是 `chat`、`weather`、`translate`。我等于已经明确告诉模型：你就照着这三个值判，只能是这仨，不能是别的。这一步很关键，后面会省掉一堆映射的麻烦。

那模型怎么知道用户问了什么？从 `state["messages"]` 里取消息列表，取最后一条。最后一条一定是用户消息——这个节点是整张图的第一个节点，请求一进来先到它这儿，那此刻 state 里最后一条消息百分之百是用户刚说的话。拿到这条消息，点 `content`，用户提问的问题就到手了。

把这个问题拼进 `HumanMessage` 发过去，注意只发这一条用户消息加系统提示词，不要把整个消息列表都塞进去。有人问为什么不把 `messages` 全发过去？没必要。意图识别只需要最后一条，前面那些历史消息带过来纯属浪费，就带最后一条足够了。

调完模型拿到的是一个 `AIMessage`。但这个结果我们不要放进消息历史里——它只是一个用户意图的判断，不是给用户的答案。而且既然意图只有三个值，它里面应该就是这三个值中的一个。所以我把 `response.content` 取出来，存进 `intent`：

```python
return {"intent": response.content}
```

state 就这么更新了。我们可以先单独验一下识别准不准：问"杭州天气如何"，识别出来是 `weather`；问"翻译一下什么叫做惊喜，翻译成英文"，识别出来是 `translate`；说一句"你好"，识别出来是 `chat`。三个都对，非常准确，一点毛病没有。把用户问题拼进去、调模型、把结果存进 state，这个节点就写好了。

### 三个干活节点：一个写死，两个调模型

闲聊节点最简单，直接把 state 里的 `messages` 丢给模型让它回答，返回的 `AIMessage` 塞回消息列表：

```python
def chat_node(state: IntentState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}
```

有人会问：你这个节点里也没看见 `messages` 字段啊，怎么能更新它？——因为我们继承了 `MessagesState`，`messages` 本来就在，可以更新。

天气节点这里要停一下。天气查询咱们现在没法真实现，前面没做过，手上也没有可用的天气接口。那怎么办？写死。弄个假的，模拟一下，直接手写一条 `AIMessage`：

```python
def weather_node(state: IntentState):
    return {"messages": [AIMessage(content="今天天气晴朗，温度25度")]}
```

这不丢人，就是个占位，等后面有了真工具再把这一行换掉。

翻译节点可以让模型真干。提示词要交代清楚两件事：一是根据用户的要求翻译，二是直接返回翻译的内容，不要有任何解释信息。然后把用户问题发给他：

```python
def translate_node(state: IntentState):
    system_prompt = (
        "根据用户的要求进行翻译，直接返回翻译的内容，不要有任何解释信息。"
    )
    response = llm.invoke([
        SystemMessage(content=system_prompt),
        HumanMessage(content=state["messages"][-1].content),
    ])
    return {"messages": [response]}
```

四个节点里，只有闲聊和翻译是真调模型的，天气那个是写死的。

### 条件边与路由函数：意图值刚好就是节点名

四个节点写完，最后一步是建图。

```python
builder = StateGraph(IntentState)
builder.add_node("route", intent_node)
builder.add_node("chat", chat_node)
builder.add_node("weather", weather_node)
builder.add_node("translate", translate_node)
```

节点加完，接着连边。第一个边：`START` 到 `route`，请求一进来先去做意图识别。

`route` 往下就不能老老实实连一条固定边了——它要动态判断。这里要上条件边：条件边的起点是 `route`，但具体去哪儿要通过条件边函数来判断。所以这里少了东西，得先定义一个路由函数，作用是根据意图路由到目标节点：

```python
from typing import Literal


def intent_router(state: IntentState) -> Literal["chat", "weather", "translate"]:
    return state["intent"]
```

这个函数短得有点过分。原理是：刚才模型识别出的结果已经存进 state 的 `intent` 里了，而这个 `intent` 的取值刚好就是 `chat`、`weather`、`translate`——刚好就是三个节点名。所以路由函数根本不需要写 `if/elif`，直接从 state 里把 `intent` 取出来返回，就完成了。

这就是前面提示词限定那三个值的回报：意图值直接等于节点名，路由映射一行都不用写。函数返回值上的 `Literal` 只是标一下有三种情况，起个说明作用。

然后挂上条件边，三个节点各自收尾到 `END`，最后编译：

```python
builder.add_edge(START, "route")
builder.add_conditional_edges("route", intent_router)

builder.add_edge("chat", END)
builder.add_edge("weather", END)
builder.add_edge("translate", END)

graph = builder.compile()
```

把编译好的图打印出来看一眼，结构和我们画的那张草图完全一致。

> **提示**：写 LangGraph 就这么写——一行一个节点，一个节点一个函数，写完一起一拼就好了。别一开始就想着把所有逻辑塞一个函数里。

最后测试三个分支。调用 LangGraph 传进去的是字典，返回的也是字典，所以可以从结果里取 `intent`，也可以取消息列表最后一条的 `content`：

```python
result = graph.invoke({"messages": [HumanMessage(content="你好")]})
print("用户问题：", "你好")
print("识别意图：", result["intent"])
print("最终回复：", result["messages"][-1].content)
```

三个用例的结果：

| 用户问题 | 识别出的 intent | 最终回复 |
| :--- | :--- | :--- |
| 你好 | `chat` | 你好呀，很高兴见到你 |
| 翻译一下 handsome | `translate` | 虎哥很帅 |
| 今天杭州天气如何 | `weather` | 今天天气晴朗，温度25度 |

三个分支全通，证明整个意图识别工作流没有任何毛病，可以正常工作。

### 图一大就该拆：父图与子图

上面这个例子只有四个节点，还好。但真实业务里的工作流往往非常庞大，全堆在一张图里不利于维护。这时候就该把它拆成多层子图。

还拿天气查询说事。天气查询本身其实挺复杂的，不是调个模型就完了——你得调工具，可能还得处理工具返回、失败重试、结果整理。如果直接在这个意图路由的图里继续往里写，图画得越来越大，很快就不成样子了。

所以遇到这种情况，我们的建议是把复杂工作流拆分，把一些子任务也用一张单独的 graph 来表示。这时最外层那张 graph 我们称之为父图，内部的那些称之为子图，也就是 subgraph。

LangGraph 支持把已经编译好的子图，直接作为父图的一个节点来用。也就是说你可以专门写一张天气查询的 graph，写完编译好，往父图的节点位置一放，它就当成一个普通节点使了。复杂任务就这样被拆开了。这种模式就叫子图嵌套模式。

拆成父子之后有两个直接的好处：一是每张图都短，单独看得懂、改得动；二是任何一个节点都是可插拔的，你想替换哪一个就替换哪一个，整个系统就组件化了。

### 两种嵌法：直接嵌入与包装调用

子图嵌套有两种做法，差别很大，选错了后面全是麻烦。

#### 直接嵌入

把已经编译好的 graph 作为父 graph 的一个节点。就是 `add_node` 的第二个参数——第一个参数是节点名称，第二个参数通常是我们自定义的节点函数，但这里除了填函数，还可以填一个别人写好的 graph。相当于把另一张 graph 拿来当我自己的一个节点用。

这种方式下，父和子的 checkpoint 是可以自动复用的，两者共享。父图 checkpointer 里、state 里存的东西，子图能用；而且子图里发生的事件也能被父图捕捉到，自定义事件、`interrupt` 事件都可以自动向上冒泡。这样看起来它们就是一张图。

但你真正写的时候是分开写的，所以既好维护，又保持了一体感。

#### 包装调用

这种不是把子图当节点，而是在父图的节点函数里，用 `subgraph.invoke(...)` 手动调用子图——把子图当成一个工具来调，用这种方式实现父子融合。

它的问题很明显：复杂，而且父子之间什么都不共享。要做数据传递，你得自己从 state 里取出来、自己拼成子图要的格式传进去、再把结果取出来拼回父图的 state。两套 state、两套 checkpoint 各维护各的。

> **结论**：两种模式里更推荐直接嵌入。我们之所以做父子拆分，只是因为想把任务拆开，但它们本质上还是同一个 agent、同一个大 agent。既然是一个 agent，就没必要父一套子一套地各维护自己的 checkpoint——除非你真有这样的业务需求。

#### 直接嵌入时，数据是怎么共享的

父 state 和子 state 可以共享数据，规则有两条。

第一条，父图会自动把自己的 key 共享给子图。父里有的字段，子图也能读到、也能用。

第二条，子向父写回：子图更新了 state，如果父图里也有同名字段，就按父图的 reducer 写回。也就是说子图可以去写父图的数据，但写回方式听父图的。

第二条为什么值得强调？想象父图里有个 `messages` 字段，装着消息列表。父和用户交互的过程产生了一堆消息，子图在交互中也会产生消息。子图更新 `messages` 的时候不会覆盖父图的消息，而是走父图的 reducer 去拼接——`messages` 的那个 `add_messages` 会把新消息追加进去。于是子图的消息自然就拼进了父图的消息流里，父子看起来就是共享同一份会话。

反过来，子图修改的 key 如果是它自己特有的、父图没有的，那对父图来说完全不可见，不影响父图。这就给了子图自由度：它完全可以有自己的任务、自己的字段。

所以这套机制很灵活：想跟父图共享，字段就起一样的名字，甚至直接继承父图的 state；不想共享，就起自己的名字，互不干扰。

### 动手把天气查询做成子图

回到刚才的路由工作流。父图已经做了意图识别和路由，但天气查询是假的。现在把它做成一张真正的子图，再塞回父图。

第一步，准备父子的 state。不管建哪张图，state 都是首当其冲的——先 state，再节点，最后才是图。而且父和子的 state 之间通常有关联，所以可以提前把两边都建好。

父 state 沿用 `IntentState`：有 `intent`，还继承了 `messages`。

子 state 需要什么？子图就是做天气查询——用户问题来了，工具一调，结果拿到，直接返回。除了消息以外，真没有什么需要特别保存的信息。那还需不需要定义 state？其实可以不定，直接跟父共用一个 state 也行。但为了把机制演示清楚，我们单独写一个：

```python
class WeatherState(MessagesState):
    # 子图若要记录自己的中间数据，在这里加字段即可；父图看不见这些字段
    pass
```

子 state 至少需要 `messages`，所以让它继承 `MessagesState`。这样父和子就有了共同字段 `messages`——只要有相同字段，将来这个字段就会共享，而且按父 state 的处理方案来处理。至于子图特有的字段，你想加就随便加，父图看不见。

第二步，做子图。子图本质上就是一个查天气的 agent。前面我们写 agent 的时候用的是手动创建工具那套写法，现在看有点笨。因为我们后来讲过：LangChain `create_agent` 创建出来的 agent，本质上也是一张 graph。既然是一张编译好的 graph，那它天然就能当子图用。

所以这里不折腾了，直接用 `create_agent`：

```python
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model

model = init_chat_model(
    "deepseek-v4-flash",
    extra_body={"thinking": {"type": "disabled"}},
)

weather_agent = create_agent(
    model=model,
    tools=[get_weather],
)
```

定义 agent 就两样东西：模型加工具。工具已经有了（导入的 `get_weather`），差的只是模型。模型这里指定 `deepseek-v4-flash`，`extra_body` 里把 `thinking` 的 `type` 设成 `disabled`，把这个模型的思考过程关掉。

到这一步，子图就创建好了。你说它是个 graph 吗？看它的返回值——是个 compiled state graph，一张编译好的图。一个带工具的 agent，其实就是一个子图。

给它一个单独的测试，确认它自己能跑：

```python
response = weather_agent.invoke({
    "messages": [HumanMessage(content="杭州天气如何")]
})
for m in response["messages"]:
    m.pretty_print()
```

注意它不能直接传字符串，得传字典，字典里 `messages` 是一个列表，列表里放 `HumanMessage`。跑之前记得从上到下把 cell 执行一遍，不然会报 `init_chat_model is not defined`——前面的 cell 没执行，模型都没定义出来。跑通了会看到它确实调了工具，拿到了杭州的天气结果。

第三步，父图。代码沿用之前的，只改一处：原来那个写死的 `weather_node` 不要了，因为现在有真子图了。

```python
builder.add_node("route", intent_node)
builder.add_node("chat", chat_node)
builder.add_node("weather", weather_agent)   # 子图直接当节点
builder.add_node("translate", translate_node)
```

就是把 `weather_node` 换成 `weather_agent`。就这么简单——你写一个新的 agent，然后把它替换掉原来那个节点，完事。

把新图打印出来看，明显复杂了一层：

```text
父图
┌──────────────────────────────────────────────────────────┐
│  START ──▶ route ──┬──▶ chat ──────────────────────┐     │
│                    ├──▶ translate ─────────────────┤     │
│                    └──▶ weather ──▶（子图）────────┤     │
│                                                     ▼     │
│                                                    END    │
└──────────────────────────────────────────────────────────┘

weather 子图内部
┌──────────────────────────────────────────┐
│  START ──▶ model ──▶ tools ──▶ model …    │
│               ▲          │               │
│               └──────────┘ （需要用时再回）│
│                      ▼                   │
│                     END                  │
└──────────────────────────────────────────┘
```

请求进来先到 `route`，路由可以去闲聊、去翻译、也可以去 `weather`；而 `weather` 本身又是一个 agent，它内部有自己的开始、结束、模型和工具。这就是父子嵌套的图。

功能复测：问"你好"，识别成闲聊，正常回；问"翻译一下 handsome"，回"虎哥很帅"，正常；问"今天杭州天气如何"，走子图查天气，也 OK。三种操作都能执行，父子就融合到一起去了。

作为对照，包装调用长什么样？`weather_node` 保留，图里也还是写 `weather_node`，只是函数体内不再写死消息，而是手动调子图：

```python
def weather_node(state: IntentState):
    result = weather_agent.invoke({"messages": state["messages"]})
    return {"messages": [result["messages"][-1]]}
```

自己把 state 里的消息取出来发给 `weather_agent`，拿到结果后再从里面取最后一条返回。麻烦就麻烦在这——消息不能直接共享，得自己取、自己拼。这种方案了解一下就行，不推荐。

### Think in LangGraph：业务流程就是节点加边

开发一个 LangGraph 的 agent 或图，必须用 LangGraph 的思维来思考。它最基本的概念就三样：节点、边、state，也就是数据。其中 node 和 edge 决定了整张图的结构。

而这个结构受什么影响？受项目的业务流程影响。你的业务流程是什么样——先干嘛、再干嘛——那"先干嘛"和"再干嘛"就是一个个节点；它们之间的先后顺序，就是所谓的边。

所以分析业务流程，就能分析出 graph 的架构：

- 先梳理业务流程，按业务边界划分职责，一个 node 负责一个职责，节点就出来了；
- 再按业务流程的顺序定义节点的执行顺序，边就出来了；
- 节点和边都有了，图就有了。

保险智能顾问的职责其实很多，远不止前面做的聊天和咨询：

- 闲聊——但最终不能一直闲聊，得往保险产品上引；
- 产品咨询——了解产品信息；
- 保险组合方案推荐；
- 产品投保；
- 理赔咨询；
- 复杂问题需要人工介入。

这些职责每一个背后都有相当复杂的流程。比如保险组合方案推荐：先获取用户画像，再推荐方案，推荐完还要跟用户确认是否满意，满意了保存，不满意得重新生成。投保流程更复杂：保费试算、客户健康告知、保单信息填写、订单确认支付、生成保单，一整套下来。

所以理论上讲，这里每一个职责都应该由独立的智能体来完成。刚刚划分的六个职责——闲聊、产品咨询、保险推荐、投保、理赔、人工介入——每一个都是一条独立的任务线，都有复杂流程，每一个理论上都是一个独立的 agent。将来这些 agent 要组合在一起，形成一个大的 agent，那它们就是子 graph，组合起来的那一层就是父 graph。

```text
                       ┌────────────────┐
       用户请求 ──────▶ │  父 agent       │
                       │  只做意图识别    │
                       │  与任务分发      │
                       └───────┬────────┘
                               │
     ┌──────────┬──────────┬───┴──────┬──────────┬──────────┐
     ▼          ▼          ▼          ▼          ▼          ▼
   闲聊      产品咨询    方案推荐    投保        理赔      转人工
  (子图)     (子图)      (子图)     (子图)     (子图)     (子图)
```

请求进来先做统一的意图识别：用户是在闲聊，还是要做保险方案推荐，还是要投保、要理赔，还是需要人工介入，或者什么都没识别出来、得走 fallback。识别完分到对应的子流程去。连闲聊都有流程——你得判断用户的闲聊次数，次数超标就该拦住他继续闲聊。所以每个流程都不简单，每个都该是一个独立的 agent，再由父 agent 把它们组织起来。

父 agent 只做一件事：意图识别，然后把信息分给不同的子 agent 去完成。

> **提示**：今天有同学问我，LangGraph 到底什么时候用、在什么业务里用？你现在应该知道了。像保险顾问这种业务，职责多、每条线都有复杂流程，它就适合用 LangGraph 做分发。

那为什么不把所有功能塞进一个 agent 里？能写，但会出两个问题。第一，agent 会变得非常臃肿，可控制性变差——同一个 agent 一会儿做投保、一会儿做理赔咨询、一会儿又干别的。第二，所有功能揉在一起，数据会很多，容易产生冲突；而且内容越来越长之后，AI 分析时越来越容易出幻觉。所以最好是分开，每个 agent 只干自己的事。

职责划清，由多个 agent 去做，再有一个统一的编排者来分配工作给不同的工作流——这就是我们要的结构。

### 五个子图，一个编排者

为了控制复杂度，这里不搞六七个，做五个就够：闲聊、保险方案咨询与推荐、理赔、转人工、fallback。

- **闲聊**：专门处理闲聊。别以为没人这么干——人工客服都经常碰到闲得没事干来找人聊天的，AI 客服一样得有这个出口。
- **保险方案咨询与推荐**：给用户推荐保险方案、咨询保险条款，最后生成保险方案。
- **理赔**：负责理赔相关功能。
- **转人工**：复杂问题交给人。
- **fallback**：识别失败时再跟用户追问一句，补充信息。

这五个挂在主 graph 下面，主 graph 收请求、做意图识别，然后分发。子图的命名直接用英文短名，好记好检索：

| 节点 | 英文名 | 职责 |
| :--- | :--- | :--- |
| 意图识别 | `route` | 识别用户意图，决定往哪个子图走 |
| 保险方案咨询与推荐 | `insurance_advisor` | 推荐方案、咨询条款、生成方案 |
| 理赔 | `claim` | 保单查询、理赔查询、订单进度查询、理赔指引 |
| 闲聊 | `chat` | 承接闲聊 |
| 转人工 | `human_handoff` | 复杂问题转人工 |
| 兜底追问 | `fallback` | 意图识别失败时追问补信息 |

主 graph 一共就这六个节点：一个 `route` 负责意图识别，剩下五个是它分发出去的目标。这五个子图之间还会共享一些工具。

```text
                        ┌──────────────┐
          START ──────▶ │  route node  │  意图识别
                        └──────┬───────┘
                               │ 条件边
      ┌───────────────┬────────┼─────────┬───────────────┐
      ▼               ▼        ▼         ▼               ▼
 insurance_        claim     chat   human_handoff    fallback
 advisor          （理赔）  （闲聊）   （转人工）      （追问补信息）
（咨询与推荐）
      │               │        │         │               │
      └───────────────┴────────┴─────────┴───────────────┘
                               ▼
                              END
```

将来还会有一个统一的 state，里面主要放历史消息和任务状态。

这些业务节点既可以是普通函数，也可以是 LangChain 的 agent，还可以是 LangGraph 里的图——三种都行。因为节点的本质通常是个函数，但塞一张图或者一个 agent 进去照样能跑，前面我们都试过了。所以具体某个子 agent 定义成函数还是 agent，看需求定。

子 agent 太多，不可能全带着做。这次先做两个：一个是闲聊 agent（它不是单纯闲聊，里面还要加一些逻辑），一个是保险顾问咨询 agent——这个之前其实已经写好了，现在要做的是把它整合进这张大图。剩下的理赔之类，留作练习，自己按同样的路子补上。

### state 里为什么必须存三个字段

最后还得把 state 分析清楚。子图各自需要什么 state 先不管，先说父图需要什么。

父图是用来做意图识别的，首先得有历史消息——要实现会话记忆，`messages` 必须得有。然后就是意图识别的信息。但这里的意图识别不能像上一节那个 demo 一样简单，不能只存一个"AI 识别出的意图是什么"就完事。

为什么？因为复杂的多轮交互里，用户发过来的信息可能极其简单。举个例子：你正在做保险推荐，问用户"你是否确定这套保险方案"，用户回了一个"确定"。就这三个字，你把它发给 AI 让它做意图识别，它能识别出你要干嘛吗？

你跟 AI 聊过天就知道，在 DeepSeek 里发个"好"，或者在 Claude Code 里发个"确定"，这种词本身没有任何信息量。它能判断出你属于哪一个子工作流吗？判断不出来。

那怎么才能识别得更准？除了把用户这一句发给 AI，你还得告诉它上一轮工作流是哪一个：上一次聊的是保险方案，还是在做理赔。再结合本轮用户说的"确定""好"，这个"好"大概率还是接着上一轮那个工作流。再把上一轮 AI 返回的内容也带上，信息齐了，意图识别才准。

所以 `route` 节点里不能只保留消息历史，还要带上：

- `messages`：跨工作流共享的会话消息，负责会话记忆，也是意图识别的原材料；
- `previous_workflow`：上一轮对话的工作流，用来消解"确定""好"这种无信息量输入；
- `active_workflow`：本轮对话的工作流。

`active_workflow` 有两个作用。第一，本轮意图识别的结果要存下来，后面才知道往哪儿路由。第二，它是下一轮推算 `previous_workflow` 的唯一依据。

这一点容易绕，捋一遍时序就清楚了：

```text
第 N 轮
  请求进来
    └─ 意图识别之前：active_workflow 里存的还是第 N-1 轮的工作流
       └─ 把它抄进 previous_workflow，连同 messages 一起交给模型
          └─ 识别完成后：active_workflow 改写为第 N 轮的工作流
             └─ 按 active_workflow 路由到对应子图

第 N+1 轮
  请求进来
    └─ 意图识别之前：active_workflow 天然就是第 N 轮的工作流
       └─ 于是又能直接抄进 previous_workflow ……
```

注意关键一点：本轮意图识别完，`active_workflow` 记录的是本轮工作流；等下一轮请求进来、在意图识别之前，此时 `active_workflow` 里装的就是上一轮的工作流了。所以记录本轮工作流的深层目的，是为了让下一轮能知道上一轮是谁，从而把它写进 `previous_workflow`。

反过来说，如果没有 `active_workflow` 这个字段，"记住上一轮工作流是谁"这件事根本做不到——上一轮的值没有地方落。所以这个字段必须有。

到这儿，整个 graph 的分析就做完了：有哪些节点、state 长什么样，都清楚了。下一步照着这个分析动手实现。
