# RAG 基础：原理、文档处理与向量检索

## Agent 工具扩展

### 工具的定义与注册

* **工具（Tool）**

    * LangChain 里的工具就是一个函数，用 `@tool` 装饰器注册；不加装饰器就只是普通函数，模型看不见它。

    * 工具的参数不写死，由模型在对话中提取用户信息后填入；工具只负责"拿到条件就去查"，条件从哪来是模型与用户的事。

    * 每个险种的查询数量可以给默认值 5，但模型第一次查不到合适结果时会自行调大再查一次。

    * 险种分类的取值固定四种：`life`（寿险）、`critical_illness`（重疾险）、`medical`（医疗险）、`accident`（意外险）；一次提问涉及多个险种时传分类列表。

    * 工具集中在 `agents` 包下单独的一个 `tools` 模块里维护，因为一个复杂 agent 的工具可能达到十个八个甚至二三十个，全塞进 agent 定义文件会失控。

    * 工具内的业务查询复用现成的 service，不重写查询逻辑；查询候选产品按分类逐类取数，保费上限的过滤方式是保留"最低保费小于该值"的产品，而不是要求该产品所有价格都低于预算。

* **工具返回值**

    * 工具的返回值自动交给模型，不需要额外封装；模型偏好 JSON 与 Markdown，所以对象列表应先转成 JSON。

    * `jsonable_encoder` 可一步把对象列表转成 JSON；另一条路是先 `ProductResponse.model_validate` 转成 schema 对象，再 `model_dump_json()` 转字符串，绕两次。

### 会话获取与返回值

* **会话工厂（Session Factory）**

    * FastAPI 的 `get_session` 依赖依赖注入与请求生命周期管理，只在 router 场景可用；agent 的工具脱离 FastAPI，无法使用这套生命周期。

    * agent 场景统一从数据库模块取 `async_session_factory`，用 `async with async_session_factory() as session` 手动开、手动关。

    * > **易错点**：`get_session` 不是坏了，是用错地方了；工具里必须手动开会话，不要和 FastAPI 那套混着用。

    * 保费上限用高精度数值类型 `Decimal` 而不是 `int`，并允许为 `None`，表示用户没有预算上限。

### 工具文档注释

* **文档注释（Docstring）**

    * 工具的文档注释是必写项，不是装饰；模型靠它判断这个工具是干什么的、什么时候该调、参数怎么填。

    * 第一段写工具做什么、什么时候使用；`Args` 段逐个说明参数含义、是否可选、可选值枚举。

    * 普通函数的读者是人，工具的第一个读者是模型，这是文档注释在工具里比在普通函数里重要得多的原因。

### 方案落库

* **方案表与方案项表**

    * 方案主表保存：所属用户、方案名称、方案摘要、用户画像（年龄、职业、预算等）、总预算、投保状态（默认未投保）、创建与更新时间。

    * 方案项表保存：所属方案 ID、产品 ID、展示顺序（1、2、3、4）、推荐理由、该产品对应的保费、投保状态（默认未投保）。

    * 一个包含四款产品的方案，在主表是一行，在方案项表是四行；方案项必须带 `plan_id`，否则同一张表里分不清某条记录属于谁的哪套方案。

    * 该模块只建 models、schemas、repository、service，不建 router——它的能力是给 agent 用的，不是给前端用的。

    * 方案名称、摘要、用户画像、总预算与各方案项都由模型在用户确认后生成，开发者只定义字段约束与保存能力，再把它包装成一个保存方案的工具。

    * 扩展智能客服能力的本质就是不断加工具：理赔咨询、理赔查询、保单、订单等业务接口都能分别变成工具挂进 agent。

## RAG 的定义与动机

### 幻觉与外挂知识库

* **检索增强生成（Retrieval-Augmented Generation，RAG）**

    * > **定义**：通过检索加载额外的知识作为上下文，来增强大模型生成的回答。

    * 模型只知道训练数据，不知道企业内部昨天刚上架的产品与条款，被问到时只能凭训练数据猜测，输出看似合理实则错误的内容，这就是幻觉。

    * 解决办法是把企业知识作为外挂知识库，用户提问时把问题与相关知识一起发给模型，让模型基于这份材料回答，相当于考试允许带小抄。

    * 不把条款直接交给用户的理由有两条：条款数量太多，用户找不到需要的那一条；条款写得专业，用户读不懂，模型读懂后再用自然语言转述才有价值。

### 全量投喂的两堵墙

* **上下文窗口**

    * 每次对话携带的信息有上限，不同模型不同：最顶尖的模型为一兆 token，多数模型限制在 200 多 K token。

    * 企业全部条款转成纯文本后仍远超该上限，全量投喂发不过去。

* **成本**

    * token 按量计费，输入 token 每 100 万（一兆）约一两块钱；每次提问都塞全量条款，等于每回答一个问题花掉几块钱。

    * > **提示**：文件大小里的兆是 MB，上下文与 token 里的兆是"百万 token"，两个兆完全不是一回事。

### 切分与检索

* **知识切分（Chunking）**

    * 把长条款拆成几百字到上千字的小块，每块保留一段相对完整的条款内容。

    * 片段体积小，既进得了上下文窗口，token 成本也低，两堵墙同时消失。

* **知识检索（Retrieval）**

    * 从切好的海量片段中找出与用户问题相关的那几片，再与问题一起发给模型。

    * 检索的对象是知识片段而非整篇文档；片段规模可达百万甚至千万级。

    * > **易错点**：检索错了整个 RAG 就废了；把不相关片段发给模型，生成再流畅也是基于错材料答错。

| 字母 | 单词 | 中文 | 在流程里的作用 |
| :--- | :--- | :--- | :--- |
| R | Retrieval | 检索 | 从海量知识片段中快速找出与问题相关的片段 |
| A | Augmented | 增强 | 把检索到的片段与问题结合成额外上下文 |
| G | Generation | 生成 | 模型基于这份外挂上下文生成回答 |

## RAG 的双阶段流程

### 离线阶段

* **知识加载与清洗**：把企业文档读入内存，解析复杂排版与表格，形成可用文档；不先清洗，原始格式根本没法用。

* **知识切分**：把文档切成片段，每片五百字到八百字，约一篇小学生作文的长度。

* **向量化**：用向量模型把每个片段转成向量。

* **存储向量**：把向量写入向量数据库。

* 离线阶段可以在项目上线前提前完成，数据规模再大也不怕，不需要等用户来了才临时处理。

### 在线阶段

* **问题向量化**：用户提问后，用向量模型把问题转成向量。

* **知识召回**：拿问题向量去向量库检索最相关的片段，不一定取 Top1，可一次召回 Top5、Top10。

* **拼接并生成**：把召回片段与用户问题拼成新提示词，发给模型生成答案。

### 阶段间的硬约束

* 在线阶段必须与离线阶段使用同一个向量模型；同一模型生成的向量才在同一套标准下，才具备可比性。

* 模型一换，两边的向量不在同一个空间，相似度比较就失去意义。

* 两个阶段共用同一个向量模型和同一个向量数据库：离线往里灌，在线从里取。

### 最小实现的边界

* 一份排版复杂、带表格的茅台研报 PDF 可以跑通整条链路，收盘价问题回答 1458.5，原文为 1458.49。

* 市盈率问题答出 22 倍，但文档中明明存在的市净率未被读出——复杂 PDF 里的表格信息不一定被完整解析、切分、召回。

* 这说明最小 demo 的天花板在文档解析与切分环节，后续复杂 RAG 技术解决的就是这类信息漏检。

## 关键词检索的边界

* **关键词检索**

    * 在文档里查找是否出现对应关键字，搜索引擎式的做法，直接且易理解。

    * > **定义**：要求字面对得上，命中关键字才算相关。

    * 用户提问是口语化的，与知识片段之间不一定存在精准的关键词匹配：问"天空为什么是蓝色"，知识里讲的是光学效应，片段不会出现这句原话。

    * 条款场景更典型：条款写"免赔额"，用户问"多少钱不能赔"，意思接近但字面不含"免赔额"，关键词检索检不到。

    * 结论：用户提问不爱用术语，字面匹配这条路在业务场景走不通，必须换成按语义检索。

## 词向量

### 词向量的构成

* **词向量（Word Embedding）**

    * > **定义**：把词变成多维空间向量的一种技术。

    * 第一步把自然语言拆成一个个 token；token 不一定等于一个单词，一个单词有时会被劈成两半。

    * 第二步用模型把每个 token 计算成一个浮点数数组。

    * 第三步把这个数组当作坐标，数组有几个元素就是几维空间里的一个向量。

    * 一个数组的两个元素可看作横纵坐标，从原点指向该点的线既有方向又有长度，这就是向量；三元素是三维，四元素是四维。

    * GPT 里一个词转出的浮点数组有 12288 个元素，即 12288 维；维度高到无法想象，但满足向量运算规则就能参与计算。

    * > **提示**："想象不出来"和"不成立"是两件事，高维空间无法在脑中画图，不妨碍它在数学上存在并可运算。

### 语义方向

* 词刚映射进空间时，生成的浮点数全是随机的，毫无意义；用大量自然语言语料反复训练、调整，才让语义相近的词靠近、语义相反的远离。

* 训练后的空间里，方向承载语义：女人向量减男人向量、王后向量减国王向量、阿姨向量减叔叔向量、妈妈向量减爸爸向量，差向量的方向与长度几乎一致，这个方向就代表性别。

* 空间里的方向数量不可数，每个方向都可能对应一种语义，人类语言的语义可以都用这些方向表达。

### 语义推理

* 已知爸爸向量与"性别"方向，沿该方向推移，落点附近最近的向量大概率是妈妈——没有见过妈妈的向量，也能算出它的大致位置。

* 给出"知名男艺人"，再依次追加"擅长唱歌""擅长跳舞""会打篮球""爱穿背带裤"，每轮沿对应语义方向调整一次位置，最终落点指向的向量就是答案。

* 所谓模型推理，不是心里早存着答案，而是在多维空间里沿语义方向一次次挪位置，挪到哪儿，哪儿就是答案。

## 相似度度量

### 三种度量

* **向量相似度检索**

    * > **定义**：用向量之间的距离或夹角来衡量语义接近程度，这套做法叫向量相似度检索。

    * 做法是把用户问题转成向量、知识片段也转成向量，比较问题向量与哪条片段向量最接近。

* **欧式距离（Euclidean Distance）**

    * 对应坐标相减、各自平方、求和、再开平方根，$n$ 维形式为：

$$d(\mathbf{v}_1,\mathbf{v}_2)=\sqrt{\sum_{i=1}^{n}(v_{1i}-v_{2i})^2}$$

    * 距离越小越相似。

    * 短板是只看绝对位置：两个向量方向完全一致但一长一短，欧式距离会很远，语义上却应该算相似。

* **余弦相似度（Cosine Similarity）**

    * 不看长度只看夹角，求两个向量夹角的余弦：

$$\cos\theta=\frac{\mathbf{v}_1\cdot\mathbf{v}_2}{\lVert\mathbf{v}_1\rVert\,\lVert\mathbf{v}_2\rVert}$$

    * 夹角越小余弦越大，方向越贴近；值域为 $[-1,1]$，越大越相似。

    * 转成距离用 $1-\cos\theta$：方向一致为 0、垂直为 1、完全相反为 2，值域 $[0,2]$，越小越相似。

* **点积（Dot Product）**

    * 对应分量相乘再求和；多维向量运算更复杂，未展开。

| 度量方式 | 怎么算 | 数值含义 | 短板 |
| :--- | :--- | :--- | :--- |
| 欧式距离 | 各维差值的平方和再开方 | 越小越相似 | 只看绝对位置，方向相同但长度不同的向量会被判得很远 |
| 余弦相似度 | 夹角余弦 $\cos\theta$ | 越大越相似 | 只反映方向，丢掉长度信息 |
| 余弦距离 | $1-\cos\theta$ | 越小越相似 | 长度信息不参与 |
| 点积 | 对应分量相乘再求和 | 未展开 | 多维向量运算，复杂度更高 |

### 实测校验

* 以"我爱上班"为查询，与三条文档逐一算余弦相似度：我爱工作 0.80，我要躺平 0.40，拒绝加班 0.40。

* 换成云端向量模型后排序不变，分数为 0.82、0.40、0.41，说明换模型不改语义判别结论。

* "我要躺平""拒绝加班"字面都带"班"，分数却不高，说明向量比的是整句在语义空间里的方向，不是撞了几个字。

* > **提示**：0.80 是相似度分数，不是"80% 的概率"；按"越接近 1 越像"理解即可。

## 向量模型与向量数据库

### 模型档位

* **小模型档**

    * 千问3 Embedding 为 0.6B（6 亿参数），在 MTEB 榜单拿到 64.34 分，几乎追平 1.6B 级模型。

    * 同档还有 jina 的 0.5B 级模型与 BGE-M3 的 0.56B；共同点是体积小、可本地跑、开源免费。

    * 参数规模理论上越大性能越强，但不是绝对，小模型可以做到效果不掉队。

* **大模型档**

    * 8B、7B 级，几十亿参数；榜单第一名是一款 8B 模型，千问3 的大号以 70 分排第三。

| 档位 | 代表 | 参数规模 | 特点 |
| :--- | :--- | :--- | :--- |
| 小模型 | 千问3 Embedding | 0.6B（6 亿） | MTEB 64.34，接近 1.6B 级模型，本地可跑 |
| 小模型 | BGE-M3 | 0.56B | 开源免费，适合小规模使用 |
| 大模型 | 8B / 7B 级 | 几十亿 | 评分更高，第一名是 8B，千问3 大号 70 分排第三 |

### 四类后端

* LangChain 对 Embedding 模型支持四类后端：OpenAI、阿里云百炼、HuggingFace、Ollama。

* 前两类是云模型，别人部署好、配个 key 直接用；后两类是自己下载、自己部署，HuggingFace 是全球最大的模型平台。

* 项目里统一走阿里云百炼的向量模型，因为百炼的模型免费；新用户注册可获 100 万免费 token 额度。

### 本地 Ollama 初始化

* `OllamaEmbeddings(model="qwen3-embedding:0.6b", dimensions=1024)` 初始化本地向量模型。

* `dimensions` 是向量维度，即生成数组的元素个数；该模型支持 1024 维，每条文本都会变成 1024 个浮点数。维度越大语义越精细，内存占用也越大。

* 不配 URL 时默认连 `localhost`，运行前必须先启动本机 Ollama，否则连不上。

* `embed_query` 处理单条字符串，返回一维向量；`embed_documents` 处理字符串列表，返回二维列表，外层长度等于文档条数，顺序与传入列表一一对应。

* 向量化时会做归一化，数值落在 -1 到 1 之间。

* > **注意**：`qwen3-embedding:0.6b` 不是聊天模型，不能在命令行里跟它对话；它唯一的作用是把文本转成向量。

### 云端 DashScope 初始化

* `DashScopeEmbeddings(model="text-embedding-v3")` 是阿里云在 LangChain 社区包里的封装，需安装 `langchain-community` 与 `dashscope`。

* 只指定模型名即可，不传 `api_key`；`load_dotenv()` 把 `.env` 里的 `DASHSCOPE_API_KEY` 与接口地址读进环境变量后，构造对象时自动读取。

* 社区版已不再由官方维护，运行会弹过期警告；能跑，但不适合长期依赖。

* 换云端模型时只需替换初始化那一行，`embed_query`、`embed_documents` 与相似度计算代码一个字都不用改。

### 向量数据库

* 向量数据库有两个职责：存储向量化后的文档，以及基于相似度检索向量化文档。

* 三个向量时可以手工逐条比较，百万级向量不可能在 `for` 循环里逐条比；内部的索引与近似检索优化全部由向量库承担。

* > **定义**：向量数据库 = 向量存储 + 相似度检索，两件事一体，不是单纯的数据库。

* 市面上的向量数据库很多，大部分 LangChain 都支持，统一 API 操作，不必逐个学各家 SDK；Milvus 是其中使用最广的一个。

## 文档加载

### BaseLoader 与 Document

* **加载器基类（BaseLoader）**

    * > **定义**：`BaseLoader` 是所有加载器的顶级父类，内含 `load` 方法；无论用哪个加载器，加载都调这个方法。

    * 统一接口的好处是学会一个，其余换个类名即可用，用法完全一致。

    * `load` 返回 `list[Document]` 而不是单个 `Document`，因为可能一次读到多份文档，也可能把一份文档按页拆成多份。

* **文档对象（Document）**

    * `page_content` 装文档原始内容，后续切分与向量化都以它为准。

    * `metadata` 装描述信息，如文件名、来源、页码；它不参与内容理解，但用于问题追溯、引用标注与出处说明。

    * 一个说"文档里写了什么"，一个说"这份文档本身是什么"，两个字段必须分清。

### PyPDFLoader 的两种模式

* `PyPDFLoader` 属于 `langchain_community` 社区版，该包已不再由官方维护；首次运行会弹出过期警告，不维护不代表不能用。

* 初始化参数 `file_path` 是文件路径，相对路径按当前工作目录解析。

* `single` 把整个文件当成一页加载，一个 PDF 只得到一个 `Document`。

* `page` 按 PDF 的物理分页加载，十页的文档返回十个 `Document`；六页 PDF 实测得到六个。

* 加载后 `metadata` 里有值的键包括 `moddate`（修改时间）、`subject`（主题）、`title`（标题）、`source`（来源）、`total_pages`（总页数）、`page`（当前页）。

* `enumerate` 可在遍历时同时给下标，默认从 0 开始，传 `start=1` 后编号从 1 开始；按序号落盘、页码对齐、日志定位都靠它。

### 加载阶段的取舍

* 推荐用 `single` 把整个 PDF 作为一篇文档加载，切分留到切分阶段再做。

* 按页加载等于在加载阶段先切了一刀；后续再切时不方便，且上下页连续的内容会被劈开——一句话写到页尾未完、下一页接续，按页切就得到两个半句。

* > **易错点**：加载阶段的分页是 PDF 的物理版式边界，切分要按语义边界；两件事混做，等于让排版替你决定语义。

## MinerU 的接入

### 凭证配置

* 凭证分两级存放：`.env` 存明文 token，配置类读环境变量，业务代码只认配置对象。

* 在 `.env` 里新增 `MINERU_TOKEN`；token 很长，粘贴时注意别漏字符。

* 在配置层单独建 `RAGSettings` 类，字段 `mineru_token` 的别名必须与 `.env` 的键一字不差；该字段不设默认值，外部凭证不该在代码里写死兜底值。

* 把配置类挂载为 `settings.RAG`，业务代码通过 `settings.RAG.mineru_token` 取值，最后交给客户端；换 token 只改 `.env`，代码不动。

* > **提示**：别名与 `.env` 的键必须对齐，这是这类配置最容易翻车的地方；取值拿到 `None` 时先比对两处拼写，不要急着怀疑客户端。

### SDK 调用

* 快速模式调用 `flash_extract`，不需要 token，客户端直接 `MinerU()` 创建。

* 精准模式调用 `extract`，客户端初始化时必须带 token：`MinerU(token=settings.RAG.mineru_token)`。

* 方法与模式一一对应：`flash_extract` 对快速，`extract` 对精准。

* 传入的文件地址可以是在线文档，也可以是本地路径；相对路径按当前工作目录解析。

* 解析结果不是字符串，而是一个结果对象，可转成 Markdown、转成 docx，也能把文档里的图片单独取出。

* 扫描件在 `extract` 上加 `ocr=True`，整页图片也能完整解析出文字，这是普通文本抽取拿不到的能力。

```python
from mineru import MinerU

client = MinerU()
result = client.flash_extract("xxx.pdf")

client = MinerU(token=settings.RAG.mineru_token)
result = client.extract("xxx.pdf", ocr=True)
```

### 结果落盘与排错

* `save` 的参数会被当成目录名使用：传入的 Markdown 文件名会变成一个同名目录，完整正文与图片等资源都放在该目录里，找正文要进目录再找。

* 报错 `No zip data available` 时，解析本身往往已经成功，挂的是保存环节；本地文件要先上传，网速差时上传会出岔子，换在线文档可能三秒完成。

* 调试顺序应固定为：先打印验证解析结果，再单独试保存；两件事分开看，才不会被保存报错误导成"整个解析失败"。

* 正常解析十秒左右完成，快时三秒；首次请求客户端要初始化会慢一点，网络不好时可能拖到近一分钟，这类延迟属于环境问题。

* > **提示**：判断解析服务是否出问题前先看两件事——解析结果有没有打印出来、当前网络能不能正常上传文件；两者都正常，问题通常不在调用方式上。

## 切分的两难

### 检索精准度与语义完整度

* **检索精准度**

    * > **定义**：在成千上万个知识片段里，能精准找到与用户问题最相关的那个片段。

    * 片段在英文里叫 chunk，即"知识片段"。

* **语义完整度**

    * > **定义**：检索到的片段必须覆盖回答用户问题所需的全部信息。

    * 完整度出问题，往往是因为切在了句子中间；犹豫期条款被从中间切断，前半句在上一块、后半句在下一块，检索到半截条款只能答出半截。

### 块大小的反向关系

* 块偏大时，一个片段里同时装着合同构成、合同成立、投保范围、犹豫期，向量的语义变泛、噪音变多；用户问犹豫期，问题向量与这块的相似度被稀释，排名下降，精准度降低。

* 块偏小时，一句一块语义干净、精准度高，但条款被切断，理赔所需信息留在别的块里，完整度降低。

| 切法 | 检索精准度 | 语义完整度 | 典型后果 |
| :--- | :--- | :--- | :--- |
| 块偏大 | 低 | 高 | 一块混着多个主题，向量被稀释，问"犹豫期"却匹配到讲"合同成立"的大段 |
| 块偏小 | 高 | 低 | 条款被切断，片段确实命中，但信息不全，答不完整 |

* 片段越大信息完整度越高、检索精度越低；片段越小检索精度越高、语义完整度越低，两个指标方向相反。

* 切多大没有标准答案，必须结合文档类型、用户问法、答案所需上下文具体分析。

* 没有标准答案不等于没有章法：常见策略优化的不是那个数字，而是切的位置。

## 文本切分器

### 统一接口

* **文本切分器（TextSplitter）**

    * > **定义**：所有文档切分器共同实现的接口，只有 `split_text` 与 `split_documents` 两个方法。

    * `split_text` 收 `str`、返回 `List[str]`：长字符串进、短字符串出。

    * `split_documents` 收 `Iterable[Document]`、返回 `List[Document]`：粒度变了，类型不变。

    * 方法选择取决于上一步产物：LangChain 加载器返回 Document 集合，直接交给 `split_documents`；解析工具或 `open()` 读回的是字符串，只能用 `split_text`。

    * 选错方法不是逻辑错，是类型对不上。

| 方法 | 入参 | 返回值 | 使用场景 |
| :--- | :--- | :--- | :--- |
| `split_text` | `str` | `List[str]` | 手上是一整篇文本 |
| `split_documents` | `Iterable[Document]` | `List[Document]` | 上一步是 LangChain 的 loader |

* 两条路径最终都得到更碎的块，区别只在块是裸字符串还是带 `metadata` 的 Document。

### 固定长度切分

* **字符文本切割器（CharacterTextSplitter）**

    * `separator` 是分隔符，传空字符串表示任意位置都能下刀。

    * `chunk_size` 是每块字符数，从开头数够就封块，再继续往下数。

    * `chunk_overlap` 是相邻块重叠的字符数，这个切分器虽按长度硬切，但自带滑动窗口效果。

```python
from langchain_text_splitters import CharacterTextSplitter

splitter = CharacterTextSplitter(
    separator="",
    chunk_size=200,
    chunk_overlap=40,
)
chunks = splitter.split_text(text)
```

* 706 个字符按 200 切、重叠 40，实际得到 5 块而不是 4 块：每块起点只前移 200 − 40 = 160 个字符，起点依次落在 0、160、320、480、640，最后一截尾巴也单独成块。

* 第一块 199 个字符，切口落在句子中间；第二块开头回咬 40 个字符，把上一块结尾再接一遍。

* 经验区间：`chunk_size` 通常在 200 到 1000 之间，不要超过 1000，切太大语义精准度急剧下降；`chunk_overlap` 取 `chunk_size` 的 10% 到 20%。

* 优点是简单、速度最快、无判断成本；缺点是不认句子边界，语义完整性被破坏得很彻底，只适合日志、代码这类按行组织、对语义完整度要求不高的内容。

* > **易错点**：硬切会把文档从中间劈开，加了重叠也救不回完整句意——一块结尾是半句话，另一块开头是后半截，语义始终是断的；了解即可，不作为首选。

### 递归字符切分

* **递归字符切分器（RecursiveCharacterTextSplitter）**

    * 本质上仍按长度切，块大小与重叠参数和固定长度切分一致，差别在分隔符可以传一个多级列表。

    * `separators=["\n\n", "\n", "。", ""]` 表示一张降级顺序表：先按段落切，不行按行，行不行按句号，最后才落到任意位置硬切。

    * 顺序是优先级，不是备选集合；把 `""` 挪到第一位，等于一上来就从任意位置切，切分器立刻退化成硬切器，多级分隔符全白配。

* 流程是每一层切完回头检查大小：合格的当场收下，不合格的带着"这块还太大"降一级再切，直到每块都进得了 `chunk_size`。

* 层级越往下切口越碎，但只有上一级切不动才往下走，所以它优先保住文档结构，段落能整就整。

* 效果是块头块尾都是完整段落；真正超长的段落降级到句号处断开，断点在句号之前，前半句仍是完整一句话，重叠只在这种被切开的段落上出现。

* 硬切是"先切了再说，断了靠重叠糊一下"，递归切分是"能不切就不切，非切不可也挑句子边界切"；前者是补救，后者是预防。

* 不确定用哪种切分器时就用递归字符切分，它是最通用的一种；面对没见过的文档先用它跑通，再谈优化。

### 语义切分

* 让模型判断哪里是语义的自然边界，再按判断下刀。

* 效果最好，成本也最高：文档一大，每一段都要过一遍模型，开销非常可观。

* 只用于对语义完整性要求极高的场景，如学术论文、法律文档——一句话意思断了就会出大事的地方才值得付这个代价。

### 结构感知切分

* 利用文档自身的结构识别逻辑区块：Markdown 的标题层级、JSON 的字段、HTML 的标签都是现成边界，不必再猜哪里该断。

* LangChain 对应提供按 Markdown 标题切的 `MarkdownHeaderTextSplitter`、按 JSON 结构递归切的 `RecursiveJsonSplitter`、按 HTML 标签切的切分器等。

* **标题切分参数（headers_to_split_on）**

    * 列表里装元组，第一部分是标题级别（`#` 一级、`##` 二级、`###` 三级），第二部分是给该级别起的名字，名字会变成 `metadata` 里的 key。

    * 底层也是递归：先按一级标题切，标题底下有正文就直接成块；没有正文（下面全是更细标题）就降到二级，二级还没有就降到三级。一级到三级再到正文的文档，真正切点落在三级标题上，因为只有那层挂着内容。

    * 文档若有四级标题，往列表里再加一个元组即可。

* **标题保留参数（strip_headers）**

    * 字面容易读成"是否携带标题"，准确含义是"是否去除正文里的标题"；传 `False` 保留，标题跟着正文留在块里；传 `True` 去掉，块里只剩正文。

    * 标题留在块里，检索出的片段自带上下文；去掉标题块更纯，`metadata` 里反正还留着一份。

* 优点是实现简单、切出的结构清晰、位置准确，因为文档天然有结构，不用猜；适合 Markdown、HTML 这类天然带结构的文档。

* 缺点是对文档素质有要求：格式必须规范，标题层级乱了、段落没正确分隔，切出来的块就是歪的——垃圾结构进来，垃圾片段出去。

* > **易错点**：`MarkdownHeaderTextSplitter` 默认 `strip_headers=True`，会把标题从正文里剥掉；标题里恰好带关键实体（人名、书名、章节主题）时，这个默认行为会直接削弱该段的检索命中率。

* > **易错点**：`metadata` 里的标题不是额外装饰，而是这一块在原文里的位置坐标；检索、引用、溯源都靠这些字段。

### 切分器的接口例外

* `MarkdownHeaderTextSplitter` 没有继承 `TextSplitter` 接口，前面立下的两条规矩到它这里都不作数。

* 它的 `split_text` 是"字符串进、`List[Document]` 出"，返回类型变了；它压根没有 `split_documents` 方法。

* 别的切分器是"什么进、什么出"，它偏偏是"字符串进、文档对象出"。

* 拿到的 Document 继承自 Pydantic 的 `BaseModel`，直接打印很难看；用 `chunks[0].model_dump()` 转字典，再交给 `json.dumps(..., indent=2, ensure_ascii=False)`，结构立刻清楚。

* `metadata` 里的 key 由 `headers_to_split_on` 中起的名字决定，值是这一块所属的一级、二级、三级标题；key 由人定，值由文档定。

### 滑动窗口切分

* 让相邻两个块允许重叠：500 字符的块重叠 20%，即 100 个字符，第二块不从断点接着往后切，而是回退 100 个字符再开始，于是两块之间有公共区域。

* 被第一块切断的半句话，在第二块的重叠区里是完整的，语义接上了；第三块再与第二块重叠一部分，窗口一路往后滑，重叠一路保留。

* 换来的是一定程度上的语义完整性，代价是同样内容存了多份，向量库变大，检索时可能召回内容相近的重复片段。

* 它通常与前几种策略搭配使用，是补偿手段，不是主力方案。

## VectorStore

### 接口与内部绑定

* **向量存储接口（VectorStore）**

    * > **定义**：LangChain 中所有向量库共同实现的统一接口，只提供 `add_documents`、`delete`、`similarity_search` 三个方法。

    * `VectorStore` 不是向量数据库本身，而是接口；它内部把向量数据库与 Embedding 向量模型合在一起。

    * 存文档时调用 `add_documents`，它自动把片段转向量再存入；检索时调用 `similarity_search`，它自动把问题转向量再按相似度取前 k 条。

    * 因此不必自己调用向量模型的 API，只要初始化时把向量模型交给 `VectorStore`，中间层细节由它处理。

* **内存向量库（InMemoryVectorStore）**

    * 数据放内存，无需任何配置，导入即用，定位是开发与测试，不能用于生产规模。

    * 初始化时把向量模型作为位置参数传入：`InMemoryVectorStore(embedding)`；换成 Milvus 时类名变为 `MilvusVectorStore`，它会自行连接数据库。

    * 内存版内部有 `store` 属性，可直接打开查看已存数据，这个便利只有内存版有；真实向量库要靠检索验证。

### 写入与删除

* 存文档前先准备：加载、切分、给每条片段赋 id。

* `Document` 的 id 要求是字符串，直接塞数字不行，需拼成 `doc_1`、`doc_2` 这种形式；用 `enumerate(chunks, start=1)` 遍历赋值，并顺手收集成 `id_list` 供批量删除使用。

* `add_documents(chunks)` 会返回写入的 id 列表；因为 id 已写进每个 Document，不必再单独传 `ids` 参数。

* `delete(id_list)` 接收 id 列表，支持批量删除；删掉一条后剩余条数相应减少，重新 `add_documents` 即可恢复。

### 相似度检索的参数

* `similarity_search` 是最常用的检索方法；`similarity_search_with_score` 用法基本一样，额外返回得分。

| 参数 | 是否必填 | 作用 |
| :--- | :--- | :--- |
| `query` | 必填 | 查询条件，用户的问题；它是位置参数，可以不写参数名 |
| `k` | 可选 | 最多返回几条文档，默认 4 |
| `score_threshold` | 可选 | 相似度得分阈值，低于该值的文档直接丢弃 |
| `filter` | 可选 | 按文档的 `metadata` 字段筛选 |

* `k` 控制返回数量：检索会给每篇文档按与问题的相似度打分并排序，`k=4` 取前四条，其余放弃。

* `score_threshold` 是分数门槛，用于挡掉相关度过低的片段。

* `filter` 走的是元数据过滤通道，不按向量分数，而按 metadata 里的字段筛。

* 四个参数里唯一必选的是 `query`。

### 带得分的检索

* 普通检索返回 `list`，元素是 `Document`；带得分检索返回的也是 `list`，但元素变成 `(Document, float)` 元组。

| 方法 | 返回类型 | 元素结构 |
| :--- | :--- | :--- |
| `similarity_search` | `list` | `Document` |
| `similarity_search_with_score` | `list` | `(Document, float)` 元组 |

* 处理结果用解构：`for doc, score in results`，一次取出文档与分数。

* 参数与普通检索完全一致，差别只在函数名多了 `_with_score` 以及返回结构。

* 实测检索"论语中教育的目的是什么"，`doc_3` 得分 0.72、`doc_4` 得分 0.64，metadata、id、正文随文档一起返回。

### 切分对检索结果的影响

* 同一句话、同一个库、同一个模型，只改切分方式，排名就能翻过来：检索效果不只由向量库和向量模型决定，切分策略同样决定结果。

* 初次检索时孔子相关段落没有排在前面，原因有二：教育原则、启发诱导等内容在向量空间里本就与"教育的目的"接近；更隐蔽的一条是标题被剥掉，正文通篇不再出现"论语"两个字，向量模型无从判断这段与《论语》有关。

* 把 `strip_headers` 改成 `False` 保留标题后，必须整条链路重跑：重新切分、重新赋 id、重新创建向量库、重新写入；旧库里仍是剥掉标题的那批片段，不重建等于白改。

* 重建后同一问题检索，排第一的变成讲"孔子及论语的主要思想"的那一篇。

* `k` 的作用也由此看清：默认返回 4 篇，改成 2 就只剩排名前两篇。

* 很多人调不好 RAG 第一反应是换向量模型、换向量库，问题常常出在最前面的切分上。

## 在线问答与架构模式

### 手动链路

* 在线阶段只剩三件事：检索知识片段、拼接提示词、调用模型；`similarity_search` 已把问题向量化与向量检索合并成一步。

```python
query = "论语中教育的目的是什么"
documents = vector_store.similarity_search(query)

context = "\n".join([doc.page_content for doc in documents])

prompt = f"""你是一个教资考试的专家，你需要根据提供的上下文来回答用户的问题，
不能自己编造答案，答案要简短，直接引用原文。

上下文：{context}

用户问题：{query}"""

response = model.invoke(prompt)
```

* 检索结果是 Document 列表，真正要发给模型的是 `page_content`；先用推导式取正文，再用 `join("\n")` 拼成一个字符串，这个字符串就是上下文。

* `join` 把分隔符插进列表每两个相邻元素之间，返回一个字符串；`"*".join(["Rose", "Lucy"])` 得到 `"Rose*Lucy"`。

* 提示词固定三件事：根据上下文回答、不能自己编造、答案简短并直接引用原文；再附上上下文与用户问题。给上下文和问题各加一对引号可减少相互干扰，但不是必须。

* 模型初始化要放在函数外，只建一次；塞进函数里会导致每次调用都重建模型对象。

* 调用用 `invoke` 传字符串，不用 `stream` 即同步阻塞；结果取 `response.content`。实测回答"以完善人格为教育目的，培养君子"，与原文一致。

### 两步模式

* **两步模式（2 Step）**

    * > **定义**：严格遵循 RAG 流程，每次用户提问都先检索、再生成，流程写死，一步不落。

    * 正因为流程固定，可以整体封装成一个函数：问题传进来，内部依次检索、拼上下文、组织提示词、调模型，返回答案。

    * 函数内加打印可看清执行顺序：先打印用户提问，再打印检索到的文档，最后打印 AI 回答。

    * 用户问"你好"时也照样翻一遍知识库，简单问题上的检索纯属浪费。

    * 适合专用问答机器人：机器人只回答与知识库有关的问题，这种场景用 2 Step 又简单又够用。

    * 需求一旦要求动态决定要不要检索，这种写死流程的模式就不够用了。

### Agentic RAG

* **智能检索增强（Agentic RAG）**

    * > **定义**：把检索逻辑封装成一个工具交给 agent，由模型自主决定何时检索、检索什么、要不要检索。

    * 用户提问先交给模型判断是否需要检索：问题复杂且与知识库相关就调工具，问题简单就直接生成答案。

    * 工具返回片段后模型再判断一次这些片段够不够回答问题；不够就换个查询词再检索一次，可以反复查直到材料足够。

    * 工具函数要加 `@tool` 装饰器；工具内部只做"拿问题→检索→拼上下文→返回"，不包含模型调用，也不在这里拼提示词。

    * 工具必须写文档注释，模型靠它判断工具用途与调用时机；没有注释模型不知道这个工具能干什么。

    * 工具的执行结果直接交给模型而不是用户，模型自己组织语言回答。

* **agent 组装**

    * `create_agent(model=model, tools=[retrieve_docs], system_prompt=...)` 绑定模型与工具。

    * 系统提示词要说明：根据文档回答、不能编造、答案简短、直接引用原文；并写死调用条件——回答与教资相关的问题时必须调用工具检索，其他情况不检索。

    * agent 调用传字典、返回字典：传入 `{"messages": [{"role": "user", "content": "..."}]}`，取返回 `result["messages"][-1].content` 即最终回答。

* **代价**

    * 好处是动态判断、按需检索，提高 RAG 利用率与整体智能程度。

    * 缺点是模型调用次数增加：判断要不要调工具是一次调用，工具返回后判断够不够回答又一次，不够还要再检索；最简单的问题也要过一次模型生成。

### 查询重写

* **查询重写（Query Rewrite）**

    * 模型调用工具时自己决定传什么 query：用户原话"论语中教育的目的是什么"被改写成"论语教育目的"，去掉口语化成分，只留关键词。

    * 把口语化问题改写成更专业的词汇再去检索，召回概率比拿原句查更高。

    * 这项能力不是开发者写的逻辑，而是模型在调用工具前自己完成的，是 Agentic RAG 比 2 Step 更聪明的地方之一——检索词质量不再取决于用户怎么问。

### 模式对比

| 对比项 | 2 Step 模式 | Agentic RAG |
| :--- | :--- | :--- |
| 流程 | 写死：先检索，再生成 | 模型自主决定要不要检索 |
| 简单问题 | 照样检索，纯属浪费 | 直接回答，不检索 |
| 复杂问题 | 只检索一次 | 可多次检索、自己换查询词 |
| 模型调用次数 | 一次 | 多次 |
| 适用场景 | 专用问答机器人 | 需要动态判断的通用助手 |

* RAG 系统设计共有三种架构模式：2 Step、Agentic RAG、混合模式；前两种是主要实现形态。

## Milvus

### 命名与定位

* Milvus 由 Zilliz 开发，该公司的开源项目都以鸟命名，象征自由、远见与技术敏捷演进。

* Milvus 是鹰科鸢属的一种猛禽，飞行速度极快、视力敏锐、适应能力强；名字对应产品特点：快、适应能力强、检索能力强。

* 它的主要作用是存储向量与检索向量，是市面上使用最广的向量数据库。

### 部署形态

| 部署方式 | 形态 | 适合的场景 |
| :--- | :--- | :--- |
| Milvus Lite | 轻量级 Python 库，数据落在本地文件 | 开发测试，Jupyter Notebook 里最舒服 |
| Milvus Standalone | 单服务器部署，把 Milvus 与依赖打成镜像一键拉起 | 学习环境与中小规模生产 |
| Milvus Distributed | 分布式部署，跑在 K8s 集群上 | 亿级向量、超大规模检索 |

* Milvus Lite 类似本地模拟库，但不是内存存储，而是基于本地文件；可惜只能在 Linux 上运行。

* Standalone 把 Milvus 及依赖打包进一个或多个 Docker 镜像，一键部署，是学习阶段使用的方式。

* Distributed 部署在 K8s 集群上，节点可动态扩展到几十上百台，可支撑数十亿量级检索；公司里要么用 Standalone，要么用 K8s 集群，后者属于运维工作。

### 单机部署的容器

* `docker compose ps` 必须在 `docker-compose` 文件所在目录执行，先进入部署目录再运行。

* 一套 Standalone 由四个容器组成：

| 容器 | 作用 |
| :--- | :--- |
| `milvus` | 向量数据库本体 |
| `minio` | 文件存储系统，存 Milvus 里的数据文件 |
| `etcd` | 存储与集群管理 |
| `attu` | Milvus 官方提供的图形化界面客户端 |

* `minio` 与 `etcd` 是 Milvus 依赖的组件；`attu` 相当于 MySQL 的图形界面客户端，用于在界面上查看库里的数据。

### 数据模型

* > **定义**：向量库里存的是"向量 + 它对应的原始数据"，查询时拿向量去比，返回的是这段向量背后的原始内容。

* 只存向量没有意义，必须把知识片段与片段对应的向量一起存；检索按向量查，取回的是原文片段。

* 与 MySQL 的概念一一对应：

| MySQL | Milvus | 说明 |
| :--- | :--- | :--- |
| 表 table | `collection` | 装数据的集合 |
| 列 / 字段 column | `field` | 一条数据里的某一项 |
| 行 row | `entity` | 一条完整的数据 |

* 一张 collection 的结构与普通表几乎一样：`id`、`title`、`title_vector`、`link` 等各是一列即一个 `field`，横向一行即一个 `entity`；`title` 存标题原文，`title_vector` 存标题对应的向量。

* 数据库里的 `database` 概念在 Milvus 中同样存在，表叫集合、列叫字段、行叫实体，概念对齐后看 API 就不会被名词绊住。

### schema 与字段属性

* **模式（Schema）**

    * > **定义**：约束 collection 里每个字段信息的结构定义；MySQL 的建表语句起到的就是同一作用，所以表的 DDL 也可称为 schema。

    * MySQL 用 SQL 语句按固定顺序写字段名、类型、长度、是否为空、是否主键，一行就能表达约束。

    * Milvus 没有类似 SQL 的语法，它用代码约束字段：每个字段是一个对象，约束就是这个对象的属性。

| 属性 | 约束什么 | 什么时候需要 |
| :--- | :--- | :--- |
| `field_name` | 字段的名字 | 通用 |
| `data_type` | 字段的数据类型 | 通用 |
| `description` | 对字段的说明 | 通用 |
| `is_primary` | 当前字段是否为主键 | 主键字段 |
| `auto_id` | 主键是否自动生成 | 主键字段 |
| `max_length` | 字符串的最大长度 | 字符串类型 |
| `dim` | 向量的维度 | 向量类型 |
| `element_type` | 数组元素的类型 | 数组类型 |
| `max_capacity` | 数组的最大容量 | 数组类型 |

* 属性不是每个都必须写：前三个通用；`is_primary` 与 `auto_id` 只在主键字段加；`max_length` 只给字符串；`dim` 只给向量；`element_type` 与 `max_capacity` 只给数组，按字段类型挑着写。

* 一篇文档入库时：标题是纯文本对应 `VARCHAR`；作者信息字段多用 JSON 结构装；图片地址是纯文本；正文是纯文本，但必须再生成一份对应向量——检索按内容检索，原文与向量两份都要存。

* Milvus 常见数据类型包括整型、`VARCHAR`、JSON、`int32`、`float vector` 等；类型细节用到时再查即可。
