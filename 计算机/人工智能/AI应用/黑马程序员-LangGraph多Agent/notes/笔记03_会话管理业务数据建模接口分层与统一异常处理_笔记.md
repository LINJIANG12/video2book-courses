# 会话管理业务：数据建模、接口分层与统一异常处理

* **业务模块五件套**（Model、Schema、Repository、Service、Router）

    * > **定义**：一个完整的业务模块由表映射模型、请求响应模型、仓储层、业务层、路由层五部分合起来构成，缺一层就不成模块。

    * Model 照着数据库表写，Schema 照着请求与响应写，两者方向相反，不能互相顶替。

    * 会话管理包的包名定为 `chat_thread`（`chat` 是聊天，`thread` 指会话），与产品业务 `product` 平级，不再往 `product` 里塞。

    * 包内结构与既有业务模块同构，`models`、`schemas`、`repository`、`service`、`router` 五个子包一一对应五件套。

    * 新业务不必重新设计骨架，照抄既有模块的五件套目录，业务代码自己重写即可。

* **编写顺序**

    * 表结构没定，增删改查就无从谈起，所以先做 Model 与 Schema，再做 Repository、Service、Router。

    * 依赖方向固定为 Router → Service → Repository → Session → 数据表，上层可以调下层，下层不得反向依赖。

    * 依赖谁就在构造函数里注入谁：Service 依赖 Repository，Repository 依赖 Session。

| 层 | 只负责 | 不该出现的内容 |
| :--- | :--- | :--- |
| Router | 接收请求、声明响应模型、调用 Service | 业务判断、拼 SQL |
| Service | 组织业务动作、划定事务边界 | 手写 SQL 语句 |
| Repository | 执行单条 CRUD 语句 | 业务判断、对象组装 |

## 会话表字段设计

* **五个必备字段**

    * > **定义**：一条会话至少要记住「它是谁、属于谁、叫什么、何时建、何时动」，对应 `id`、`user_id`、`title`、`create_at`、`update_at`。

| 字段 | 类型 | 作用 |
| :--- | :--- | :--- |
| `id` | UUID | 会话主键，唯一标识一条会话 |
| `user_id` | int | 标记这条会话属于哪个用户 |
| `title` | varchar(200) | 会话标题，列表里第一眼看到的内容 |
| `create_at` | 时间 | 创建时间 |
| `update_at` | 时间 | 更新时间，每聊一句都会变 |

* **主键选择与标题的局限**

    * 标题会重复、会改，靠标题区分不同会话不准；数据库设计里每张表都该有主键，区分不同对象最靠得住的永远是 id。

    * 会话 id 会出现在页面地址里，点不同会话那一串就变；后台正是拿这个 id 去查对应的聊天记录，所以它非常要紧。

    * UUID 不是自增计数器排出来的，而是按算法算出来的：不同代算法取的要素不同，有的取机器码、网卡地址和时间，`uuid4` 取的是随机数。

* **更新时间的作用**

    * 改标题会更新，更主要的是每聊一句会话就变了，更新时间应跟着变。

    * 列表按时间倒序排时，最近聊过的会话被顶到最前；七年前建的会话只要随手说一句，也会立刻回到顶部，这正是 `update_at` 的作用。

    * 只有创建时间做不到这一点，列表顺序会永远固定在建会话的先后上。

* **user_id 与数据归属**

    * 所有用户的会话存在同一张表里，没有归属字段就无法区分哪条属于谁。

    * 用户登录后只能看到自己的会话，数据隔离要靠 `user_id` 实现，它是给后台用的，不是给前端展示的。

## 表映射类 ChatThread

* **ChatThread**

    * > **定义**：映射类是表的影子——表有哪些字段，类就有哪些属性；先定字段再写类，不能反过来。

    * 继承 `Base` 获得 ORM 元数据，同时继承 `CreateAtMixin` 与 `UpdateAtMixin`：一个提供创建时间，一个提供更新时间，表里刚好要这两个字段，继承过来就不用重写。

    * 类里只显式声明三个字段，看不到 `create_at`、`update_at`，不是漏了，而是混入类自动落表。

    * `__tablename__ = "chat_thread"` 指定物理表名。

    ```python
    class ChatThread(Base, CreateAtMixin, UpdateAtMixin):
        __tablename__ = "chat_thread"

        id: Mapped[UUID] = mapped_column(PGUUID, primary_key=True, default=uuid4)
        user_id: Mapped[int] = mapped_column(Integer)
        title: Mapped[str] = mapped_column(String(200))
    ```

* **UUID 的类型对应**

    * Python 侧从标准库 `uuid` 导入 `UUID`，不用额外安装；数据库侧从 `sqlalchemy.dialects.postgresql` 导入的类也叫 `UUID`，两个名字撞车，所以给数据库侧起别名 `PGUUID`，含义是「Postgres 里的 uuid」。

    * 写法上类里的类型是 `UUID`，落到数据库是 `PGUUID`，一层对应关系由 `mapped_column(PGUUID, ...)` 建立。

    * `primary_key=True` 声明主键，`default=uuid4` 让插入时自动生成 id，调用方不必自己给。

    * `uuid4` 是第四代生成算法，取 128 位随机数；`uuid` 另有 1、2、3 代，取机器码、网卡地址、时间等不同要素，只有第 4 代取随机数。

    * 生成一次与生成一亿次，重复概率都低到工程上可以当成不会发生，正因为它不重复，拿它当主键才合适。

    * > **提示**：`uuid4` 靠 128 位随机数保证唯一，撞车概率小到可忽略，但不是数学意义上的「绝对不重复」；工程上当唯一标识用完全够。

* **可省的 server_default**

    * `title` 上写 `server_default="新会话"` 是在数据库层给默认值；前端创建会话时一定会传标题，写了也用不上，换成 `String(200)` 即可。

    * 写上不算错，省掉也不算错，两种都能跑。

    * 这类映射代码是死代码，格式固定，换个业务复制一遍改个名就行，精力该花在业务逻辑上。

## 请求 Schema 与字段校验

* **ChatThreadCreate**

    * > **定义**：接住创建会话请求体的 Pydantic 模型，类名由业务名 `ChatThread` 加动作名 `Create` 组成。

    * 即使请求体只有一个字段，也必须有一个类来接，因为它是 JSON 风格的请求体；JSON 请求体不能拿一个裸参数接。

    * 继承自定义的 `BaseSchema` 而不是直接继承 `BaseModel`：基类打开了「允许从对象属性构造」的开关，将来做对象转换才能自动完成。

    * 字段写成 `title: str = Field(description="会话标题", min_length=1, max_length=200)`，`Field` 提供描述与长度约束。

    * `Field` 里的约束就是请求参数校验，Pydantic 模型天生带校验能力，写上去即自动生效，脏数据在进入业务逻辑之前就被拦下。

* **前置处理的写法**

    * 纯空格标题能通过 `min_length=1` 的检查：八个空格长度是 8，规则上合法，业务上却等于没有标题。

    * 值由别人传入、校验由框架执行，中间插不进一句「先 strip」，所以要用 `field_validator(..., mode="before")` 在赋值与校验之前动手。

    * 三个部件各管一件事：`field_validator` 是字段校验器，第一个参数指明字段名 `title`，`mode="before"` 表示在赋值之前处理。

    ```python
    class ChatThreadCreate(BaseSchema):
        title: str = Field(description="会话标题", min_length=1, max_length=200)

        @field_validator("title", mode="before")
        @classmethod
        def validate_title(cls, value: str) -> str:
            return value.strip()
    ```

    * 执行顺序是先处理值、再校验、再赋值，这就是「前置处理」的含义。

    * `strip()` 去掉首尾空白后，八个空格长度归零，`min_length=1` 随即报错，错误信息仍是「至少得有一个字符」。

    * 换别的字段时只改三处：校验的字段名、函数名、值的处理方式；处理方案自己定，可以填空值、可以去空白，格式固定。

* **Schema 的三要素**

    * > **结论**：一个完整的 Schema 需要字段（名字与类型）、约束（`Field` 里的长度限制）、前置处理（`field_validator(mode="before")`）三样，缺一样脏数据就能进来。

    * 只有字段和约束，形似空标题的纯空格数据照样通过；约束管得住长度，管不住内容是不是空白。

    * > **易错点**：改完 Schema 源码必须重启当前运行环境再测。类已经被导入内存，源文件改了内存里仍是旧定义，不重启会误判成校验没生效。

* **校验的实测路径**

    * 所有 Pydantic 模型都有 `model_validate`，作用是把收到的数据转成自己的对象；前端提交的 JSON 到 Python 是一个字典，正好喂给它。

    * `ChatThreadCreate.model_validate({"title": "我的第一个会话"})` 返回一个对象，字典进、对象出，转换成功。

    * 传空字符串 `{"title": ""}` 立刻报错，提示字符串至少要有一个字符，校验在 `model_validate` 这一步自动发生，一行校验代码都没写。

    * 传八个空格 `{"title": "        "}` 第一次能通过，加上 `mode="before"` 的 `strip` 之后才被拦住。

## 响应 Schema 与类型转换

* **ChatThreadResponse**

    * > **定义**：描述接口返回结构的 Pydantic 模型，字段为 `id`、`title`、`create_at`、`update_at` 四个，全部是字符串。

    * 表里有五个字段，响应故意少一个 `user_id`：用户 id 属于敏感信息，查会话只需把会话自身的信息返回前端，没必要把「这条数据属于谁」带出去。

    * `user_id` 是后台做数据隔离用的，不是给前端展示用的；响应结构里省略它是有意为之，不是漏字段。

    ```python
    class ChatThreadResponse(BaseSchema):
        id: str
        title: str
        create_at: str
        update_at: str
    ```

* **入库类型与传输类型分离**

    * `id` 声明为 `str` 而不是 `UUID`：库里存的 UUID 本质就是一长串字母数字，返回前端时不必把 UUID 类型带出去，中间做一次 UUID 到字符串的转换即可。

    * 两个时间字段同样声明为 `str`：时间可以转成字符串返回，前端不需要知道服务端怎么存，只关心拿到什么。

    * > **易错点**：库里的类型和接口的类型是两回事。库里 `id` 是 UUID、时间是时间类型，对外传输统一成字符串；照库里的类型写响应模型会与接口文档对不上。

    * 响应模型按接口文档定义的字符串类型来写，不按数据库里的 UUID、时间类型来写。

* **响应结构的复用价值**

    * 创建会话返回四个字段，查询列表里每个元素也是这四个字段，重命名返回的还是这四个字段。

    * 同一个 `ChatThreadResponse` 被三个接口复用，查询列表只是把它包成 `list[ChatThreadResponse]`，一行新代码都不用写。

    * 响应结构抽成 Schema 的收益就在这里：结构一致时复用，结构变化时只改一处。

## Repository 层

* **职责边界**

    * > **定义**：仓储层只负责 CRUD，接收实体、执行语句，别的不管。

    * 判断一段代码该不该放这里，看它是否只跟数据库打交道；凡是带业务判断的，都不属于这一层。

    * 「创建会话」翻译成数据库语言就是往 `chat_thread` 表插一条记录；五个字段里 `id` 自动生成、两个时间靠继承自动填，真正需要传的只有 `user_id` 和 `title`。

* **构造函数注入 session**

    * 类名 `ChatThreadRepository`，前缀是业务名、后缀是 `Repository`，所有增删改查封装成类里的方法。

    * 构造函数接收 `AsyncSession` 并存成实例属性，类里所有方法都能直接用 `self.session`，不必每个方法再传一遍。

    ```python
    class ChatThreadRepository:
        def __init__(self, session: AsyncSession):
            self.session = session
    ```

* **session.add 的语义**

    * > **定义**：对象关系映射（Object-Relational Mapping，ORM）把数据库表映射成 Python 类、把表里的一行映射成类的对象。

    * `chat_thread` 表对应 `ChatThread` 类，表里一行对应一个 `ChatThread` 对象；「向表里插入一条数据」在 ORM 里就是「往 session 里放一个对象」。

    * `add` 收的是对象，不是字典，也不是几个字段值，记住这一点 `add` 就不会写错。

    * `AsyncSession.add()` 是同步方法，只把对象挂到 session 上，并不真的发 SQL，所以调用时前面没有 `await`；真正跟数据库打交道的是 `flush`、`commit`，那些才需要 `await`。

* **add 的两种签名**

    * 早期写法自己创建对象、塞进去、再返回：`async def add(self, user_id: int, title: str) -> ChatThread`。

    * 最终写法更纯粹：对象由调用方创建并传入，塞进去之后不返回。

    ```python
    async def add(self, chat_thread: ChatThread) -> None:
        self.session.add(chat_thread)
    ```

    * 改的理由是分工：Repository 若连对象组装都干了，Service 就没事可干；Repository 不该关心数据从哪来、对象怎么拼。

    * 谁调 `add` 谁负责造对象，所以对象初始化归 Service。

* **查询语句的三条对应**

    * `select` 后面写类，不写表名：`select(ChatThread)` 里的 `ChatThread` 就是 `chat_thread` 表。

    * `where` 里面写类属性，不写列名：`ChatThread.user_id`、`ChatThread.id` 分别对应表里的同名字段。

    * 多个条件用逗号隔开，SQLAlchemy 会当成「并且」拼进 `WHERE`，等价于 `WHERE id = ? AND user_id = ?`。

* **scalar、scalars 与 execute**

    * 传统写法用 `execute`，取结果还要再剥一层；`scalars()` 直接把每行的 ORM 对象摊开给你，省掉 `row[0]` 的取值。

    * 只要一条记录时用 `scalar`：比 `execute` 再取 `scalars().first()` 省事，查不到返回空值。

    * 要一组记录时用 `scalars(...)` 再 `.all()`，返回的是对象列表。

* **按主键取单条**

    * `session.get(ChatThread, "会话ID")` 第一个参数传表对应的类，第二个参数传主键值，拿回来的就是那个 `ChatThread` 对象。

    * 主键查询传字符串形式的 UUID 完全可以，不必先转成 UUID 对象。

## Service 层

* **ChatThreadService 的构造**

    * > **定义**：业务层负责组织一次业务动作、划定事务边界，由它调用 Repository。

    * Service 干活需要 `session` 和 `repository` 两样东西：`repository` 在构造函数里创建，因为它需要 `session`；`session` 自己不知道从哪来，就让别人注入。

    ```python
    class ChatThreadService:
        def __init__(self, session: AsyncSession):
            self.session = session
            self.repository = ChatThreadRepository(session)
    ```

    * 构造函数收到 `session`，一手交给 `repository`，一手自己留一份，后面任何方法都能直接取用。

* **add：组装、交付、返回**

    * 方法参数是 `user_id` 和 `title`，这两个值最终来自前端，由参数列表接住。

    * 方法里三件事：组装对象、交给 Repository、把对象返回；`id` 与两个时间不用管，要么有默认值、要么靠混入类自动填。

    * `await self.repository.add(chat_thread)` 必须带 `await`，因为 Repository 那个 `add` 声明成了 `async def`；本模块方法统一写成 `async def`。

    * 返回对象是因为响应体要 `id`、`title` 和两个时间，Router 拿这个对象转成 `ChatThreadResponse` 就完事。

    ```python
    async def add(self, user_id: int, title: str) -> ChatThread:
        async with self.session.begin():
            chat_thread = ChatThread(user_id=user_id, title=title)
            await self.repository.add(chat_thread)
            return chat_thread
    ```

    * > **易错点**：组装对象时字段名必须写全。写成 `ChatThread(user_id, title)` 会按字段顺序对号入座，第一个值被当成 `id`、第二个当成 `user_id`，`title` 反而没值；只有五个字段一个不落按序传齐才能省字段名。

* **事务边界的位置**

    * `async with self.session.begin():` 开启事务，正常跑完自动 `commit`，中途出异常自动 `rollback`。

    * 单次新增看不出差别，在 Service 或 Repository 里开都一样；业务一旦包含两次数据库操作，差别立刻出现。

    * 假设一次业务先 `add` 再 `delete`，这两步必须同成同败，不能出现「新增落库、删除却没生效」的中间状态。

    * 事务开在 Service，`async with` 把两次调用一起包住，它们落在同一个事务里；开在 Repository 则是两个独立事务各自提交，第一次成功第二次失败时无法保证同成同败。

    * > **结论**：事务边界由业务决定，业务逻辑住在 Service，所以只要一个业务动作包含多次数据操作，事务就必须开在 Service。

    * Repository 只管一条 SQL 干不干净，Service 才管这一次业务是不是一个整体；这个分工定下来，复杂业务才不会出现两个事务各管一半的窟窿。

    ```text
    Router        接收请求，按 Schema 校验入参
       │
       ▼
    Service       组装 ChatThread 对象
       │          事务边界在这里：async with session.begin()
       ▼
    Repository    只做一件事：session.add(对象)
       │
       ▼
    chat_thread   落库，插入一条记录
    ```

## 事务内返回与对象刷新

* **ORM 的自动更新**

    * 一条数据查出来之后，修改这个对象的任意字段，ORM 会自动把改动写回数据库，不需要手写 `UPDATE`。

    * 有修改就必须开事务，这是硬要求：`session.get` 取出对象、改字段，外面必须套一层 `session.begin()`。

    * 这一特性直接决定 Repository 的写法：只留一个查询函数就够，不必再补「根据 ID 修改标题」的方法，改标题在 Service 里改对象属性即可。

* **返回旧值的成因**

    * 查出来的对象在内存里存的是查询那一刻的值；改 `title` 触发 ORM 发 `UPDATE`，数据库那一行变了，内存对象不会自动重新加载。

    * 打印或返回这个对象，拿到的仍是查出来时的那份数据，`update_at` 看起来跟修改前一模一样。

    ```text
    查出来（内存里是旧对象，update_at = 旧时间）
            │
            ├── 改 title ──▶ 内存对象的 title 变了，update_at 没变
            │
            └── 提交事务 ──▶ 数据库那一行被 UPDATE，update_at = 新时间
                                  │
                                  └── 内存对象不跟着变，返回出去仍是旧值
    ```

* **两条解法与现实结果**

    * 第一条是把读取放到事务外面，事务结束再取；但项目配了提交后不过期（`expire_on_commit=False`），提交后对象不会被标记为过期，再取也不会重新查库。

    * 实测更直接：`update_at` 字段干脆没了，对象里只剩 `create_at`，这条路走不通。

    * 第二条是手动刷新：`await self.session.flush()` 把当前事务里挂起的改动写回数据库，`await self.session.refresh(chat_thread)` 拿对象重新查一次库、把最新值灌回对象。

    * `flush` 不是提交事务，事务还是那个事务，只是把 SQL 发出去；两个动作合起来，`update_at` 才变成最新时间。

    * > **易错点**：业务里改了数据、又要在同一个事务里立刻返回这条数据，必须做一次 `refresh`。少这一步接口会稳定返回旧值，而数据库里是对的，排查时容易误判成更新没生效。

## 接口层：路由与依赖注入

* **接口文档翻译成四件事**

    * > **定义**：写 Router 就是定义 FastAPI 接口，接口形状全部由接口文档决定，不靠猜。

    | 接口文档里的信息 | 落到代码的哪里 |
    | :--- | :--- |
    | 请求方式（POST / GET / PATCH） | 装饰器 `@router.post` / `@router.get` / `@router.patch` |
    | 请求路径 | `APIRouter` 的 `prefix` 加装饰器里的相对路径 |
    | 请求参数 | 函数参数列表，还要判断它在请求体、请求头还是路径 |
    | 响应值类型 | 装饰器的 `response_model` |

    * 最容易被看漏的是第三件的后半句——参数放在哪儿：请求体要用一个类接，请求头要用 `Header` 接，路径里只要写一个同名参数；位置不同，写法完全不同。

    * 创建与查询列表路径相同，只是请求方式一个 POST 一个 GET，所以把公共路径提到 `APIRouter` 的 `prefix` 上，装饰器里不再重复。

    ```python
    router = APIRouter(
        prefix="/api/v1/chat/threads",
        tags=["会话管理"],
    )
    ```

    * `prefix` 固定公共路径，`tags` 是接口文档里的分组名，这个模块所有会话接口都归在一组。

    * > **易错点**：`tags` 一定要加中括号，它是列表不是字符串。

* **装饰器与 response_model**

    * 创建会话是 POST，路径与 prefix 完全一致，装饰器里的路径直接留空，写成 `@router.post("", response_model=ChatThreadResponse)`。

    * `response_model` 填 Schema 里的响应类；返回给前端的就是 id、标题、创建时间、更新时间那个格式。

    * 业务层返回的是 Model 对象，接口层声明的是 Schema，类型对不上也能直接 return：FastAPI 拿到返回值会按 `response_model` 做序列化，而 Model 与 Schema 都继承 `BaseSchema`，基类已打开「允许从对象属性构造」的开关。

    * 业务层返回 model、接口层声明 schema，中间这层转换不用手写。

* **依赖注入（Dependency Injection，DI）**

    * > **定义**：需要什么就在参数列表里声明什么，由框架负责把对象送进来，而不是主动去调工厂函数。

    * 基础设施模块提供 `get_session`，但不在函数体里手动调用，而是声明 `session: AsyncSession = Depends(get_session)`。

    * `Depends(get_session)` 告诉 FastAPI：这个参数的来源是 `get_session`，你调它、把返回值给我；冒号后是类型，等号后是来源。

    * 多个接口都要创建 Service，于是把创建过程封装成函数，函数自己也在用依赖注入：

    ```python
    def get_service(session: AsyncSession = Depends(get_session)) -> ChatThreadService:
        return ChatThreadService(session)
    ```

    * 接口里改成声明 `service: ChatThreadService = Depends(get_service)`，以后不论写几个接口，拿 Service 都是同一句话。

    * 这套写法可记成三句：把要的东西的创建过程封装成函数、在参数列表里声明它的类型、用 `Depends` 告诉 FastAPI 它从哪来。

* **路由挂载与报错定位**

    * router 定义了不挂载，它只是一个躺在模块里的对象，FastAPI 根本不知道它存在，请求直接 404。

    * 入口文件里必须补两行：导入并起别名（每个模块都有名为 `router` 的变量，直接导会打架），再 `app.include_router(chat_thread_router)`。

    * 挂载后浏览器地址栏访问变成 405：地址栏发的是 GET，而接口只注册了 POST，路径对得上、方法不允许就是 405。

    * > **结论**：404 先查挂载，405 先查请求方式。一个在入口文件，一个在装饰器，都不在业务代码里。

## 请求头参数与接口签名

* **用户 id 的来源**

    * 请求头里带着名为 `x-user-id` 的字段，用户 id 从那里取，不从请求体或查询参数取。

    * 企业开发里用户信息基本都走请求头：走参数别人一眼就看见 id，走请求头相对隐蔽，也更安全。

    * 请求头的名字大小写不敏感，写 `X-User-Id` 与 `x-user-id` 是一回事；前端换头名时只改别名，数据类型与变量名不动。

* **Header 的两种写法**

    * 原始写法把类型放冒号后、来源放等号后；`Annotated` 写法把类型和来源一起塞进中括号，读起来更清楚。

    | 写法 | 声明 | 读法 |
    | :--- | :--- | :--- |
    | 原始写法 | `user_id: int = Header(alias="x-user-id")` | 类型在冒号后，来源在等号后 |
    | Annotated 写法 | `user_id: Annotated[int, Header(alias="x-user-id")]` | 中括号第一段是类型，第二段是来源 |

    * `Annotated` 来自 `typing`，直译是「带注释的」，作用是给类型挂额外说明；两种写法表达同一件事，工程上统一用 `Annotated`。

    * `Header(alias="x-user-id")` 里的别名就是前端发请求时那个头的名字；这句话翻译过来是：参数是 int，从请求头取，取的是 `x-user-id`。

* **参数顺序的硬约束**

    * 没有默认值的参数必须排在带默认值的参数前面。

    * `user_id` 没有默认值，`service` 后面挂着 `Depends(...)`，所以 `user_id` 要往前挪，不能顺手写到最后。

    ```python
    @router.post("", response_model=ChatThreadResponse)
    async def create_chat_thread(
        request: ChatThreadCreate,
        user_id: Annotated[int, Header(alias="x-user-id")],
        service: ChatThreadService = Depends(get_service),
    ):
        return await service.add(user_id, request.title)
    ```

## 三个接口的落地差异

| 对比项 | 创建会话 | 查询会话列表 | 重命名会话 |
| :--- | :--- | :--- | :--- |
| 请求方式 | POST | GET | PATCH |
| 请求路径 | `/api/v1/chat/threads` | 同左 | `/api/v1/chat/threads/{thread_id}` |
| 请求参数 | 请求体 `title` + 请求头 `user_id` | 只有请求头 `user_id` | 路径 `thread_id` + 请求体 `title` + 请求头 `user_id` |
| 响应模型 | `ChatThreadResponse` | `list[ChatThreadResponse]` | `ChatThreadResponse` |

### 创建会话

* 请求体用 `request: ChatThreadCreate` 接住，前端发 `{"title": "..."}`，FastAPI 按类解析，字段名一样就自动塞进去；校验在进函数之前已经做完。

* 参数名叫 `request` 只是习惯，叫什么都行，关键是类型是 `ChatThreadCreate`；取字段写 `request.title`。

* 业务逻辑三步：拿到 Service、调新增、返回结果，三步各占一行，没有多余的加工。

### 查询会话列表

* 文档写「请求参数：无」，指的是没有请求体和查询字符串参数，不代表没有身份信息；说明里那句「查询当前用户的会话」才是关键。

* 所以真正的隐含参数是请求头里的 `user_id`，拿它去表里查 `user_id` 等于该值的所有会话，别人的不能给。

* 响应是列表，元素四个字段与创建接口返回同构，`ChatThreadResponse` 直接复用，只把 `response_model` 写成 `list[ChatThreadResponse]`。

* 文档还有一条附加要求：按时间倒序，先按 `update_at`，再按 `create_at`，这样最近动过的会话永远排最前。

* 仓储层写法对应为 `select(ChatThread).where(ChatThread.user_id == user_id).order_by(ChatThread.update_at.desc(), ChatThread.create_at.desc())`，再 `scalars(...)` 取 `.all()`。

* Service 这一层只做转手：`return await self.repository.list_by_user(user_id)`，不做加工；不是每个 Service 方法都得有逻辑，它的职责是对上层统一提供业务入口。

* 接口层从创建接口复制一份改四处：装饰器换成 `get`、`response_model` 换成列表、删掉请求体参数、调用换成 `list_by_user`；请求头与 `service` 两行原封不动。

* 整个接口仍是一行，但 `await` 千万别漏：异步函数不 await 拿到的是协程对象，返回给前端直接报错。

* > **易错点**：第一遍写查询容易只顾条件、漏掉排序，跑通之后回文档才补上。接口文档里那些「附加说明」往往就是最容易漏的部分。

### 重命名会话

* 请求体与创建会话完全一致，只有一个 `title`，`ChatThreadCreate` 原样复用，一个字都不用改；响应也是 `ChatThreadResponse`，Model 同样不动。

* 需要新写的只有三处：Repository 的归属校验、Service 的先查再改、Router 的 `PATCH` 接口。

* 接口说明「修改当前用户指定会话的标题」一句话里有三个关键点：当前用户、指定会话、标题，落到参数上就是 `user_id`、`thread_id`、`title` 三个。

* 三个参数分居三处，正好覆盖三种接收方式：路径占位符写同名参数即可接住 `thread_id`，请求体仍用一个类接 `title`，请求头继续用 `Header` 加别名。

    ```text
    /api/v1/chat/threads/{thread_id}
                         └─ 路径占位符：要改哪一条会话

    请求头  x-user-id: 1         ── 你是谁（隐含参数）
    请求体  {"title": "新名字"}   ── 改成什么标题
    ```

* 装饰器路径在上层 prefix 之后补上 `/{thread_id}`，请求方式用 `PATCH`；`GET`、`POST`、`PUT`、`DELETE`、`PATCH` 本来就按语义分工，前端要求 `PATCH` 就用 `PATCH`。

* 响应模型与路由挂载都不用动：重命名与创建属于同一个 router，返回结构也相同，只是给 router 加了一个新方法。

## 归属校验

* **归属校验的必要性**

    * `thread_id` 是公共的、肉眼可见的，会话地址里那串 id 挂在浏览器上谁都能看到。

    * 别人拿到你的会话 id，手动构造一个带新标题的请求发过去，服务端若二话不说就改，改的却是你的会话。

    * 所以请求头里的 `user_id` 不是摆设，它是用来做验证的：验证这条会话是否属于当前用户。

    * > **结论**：更新本身很简单，`update` 这张表、`set` 一下 `title`、`where` 跟上 `id` 就完事；难的是「能不能改」这一步，必须先把 `id` 与 `user_id` 两个条件凑在一起查一遍。

* **require_owner**

    * > **定义**：要求调用者必须是这条会话的拥有者，才有资格继续；`require` 是「要求」，`owner` 是「拥有者」，不是「老板」。

    * 入参是 `user_id` 与 `thread_id`，两个值都由调用方传入，仓储层自己不生产数据。

    * 用一条同时带两个条件的查询判断归属：`id` 等于传入的会话 id，`user_id` 等于当前用户 id，两个条件逗号隔开即为「并且」。

    * 查得到说明匹配，会话确实属于当前用户；查不到说明要么不存在、要么存在但不属于你，两种情况业务上是一回事，都不该让你改。

    ```python
    async def require_owner(self, user_id: int, thread_id: str) -> ChatThread | None:
        stmt = select(ChatThread).where(
            ChatThread.id == thread_id,
            ChatThread.user_id == user_id,
        )
        return await self.session.scalar(stmt)
    ```

* **返回类型与职责归属**

    * 返回值标 `ChatThread | None` 是给下游用的：不标的话 IDE 不知道拿回来的是什么，改 `title` 时既没提示也没类型检查。

    * `scalar` 查不到返回空值，用不匹配的 `user_id` 实测走的就是空值分支，标注成可空是对的。

    * `require_owner` 严格来说不算 CRUD 里的「改」，它干的仍是「查」，只是查的目的是校验；持久层只执行语句，业务判断留给 Service。

* **校验之后的闸门**

    * 查回来是空值时若不判断，下一行 `chat_thread.title = title` 就是对着空值改属性，立刻报错，这种错误是「撞」出来的，报错信息说明不了业务含义。

    * 正确做法是先判断、没值就 `raise` 一个异常，代码立刻终止，后面的修改与返回都不会执行。

    * 异常一旦抛出，后面的修改与返回都不会执行，非法请求因此不会带着半成品结果返回。

## 自定义异常体系

* **ChatThreadNotFound 的初版**

    * 直接抛 `Exception` 可以，但不专业；会话不存在、用户不存在、权限不够这类场景会很常见，每种都该有明确类型，方便上层分辨。

    * 写法就是定义一个继承 `Exception` 的类，一个普通类一旦继承 `Exception` 就成为异常类。

    ```python
    class ChatThreadNotFound(Exception):
        pass
    ```

    * 这个异常表达「当前会话不存在，或者不属于当前用户」，两种情况在业务上归为一类——反正你都改不了它。

    * 异常类不写在 Service 里：Service 是写业务的地方，异常塞进去会越堆越乱；惯例是单独放 `exceptions.py`，模块内所有异常收在一起，需要时导入。

* **ApplicationError 基类**

    * 每多一个异常就抄一个处理器并不成立：业务复杂起来上百个异常，不可能写上百个处理器。

    * 病根有两条：异常类型不统一，捕获必须写具体类型，只能一个一个分开捕；返回内容不统一，状态码、错误码、错误消息各不相同，处理逻辑没法共用。

    * 破法对应两条：给所有自定义异常一个共同父类，捕获时只写父类就能接住所有子类；让异常自己带上状态码、错误码、错误消息，处理器从对象里取而不是写死。

    * 父类放在核心模块的 `exceptions.py`，类名 `ApplicationError`，代表应用内部的业务异常。

    ```python
    class ApplicationError(Exception):
        def __init__(
            self,
            status_code: int = 500,
            code: str = "application_error",
            message: str = "服务器内部错误",
        ):
            self.status_code = status_code
            self.code = code
            self.message = message
    ```

    * 三个默认值 500、`application_error`、「服务器内部错误」是兜底：子类忘了填，至少还能给出像样的响应。

    * > **注意**：`ApplicationError` 只是父类，默认值不等于最终答案，真正决定返回什么的是具体抛出的那个子类。

* **子类接入统一基类**

    * `ChatThreadNotFound` 不再继承 `Exception`，改成继承 `ApplicationError`，在构造时把 400、`chat_thread_not_found`、「当前会话不存在或者不属于当前用户」填进去。

    * 链路由此闭合：业务层抛子类，子类是 `ApplicationError` 的后代，被唯一的处理器接住，取出来的三项正是子类填的那三项。

    * 若某处直接抛 `ApplicationError` 本身，取出的就是默认的 500、`application_error`、「服务器内部错误」。

    ```python
    class ChatThreadNotFound(ApplicationError):
        def __init__(self):
            super().__init__(
                status_code=400,
                code="chat_thread_not_found",
                message="当前会话不存在或者不属于当前用户",
            )
    ```

## 全局统一异常处理

* **异常的传递路径**

    * Service 里 `raise` 的异常抛给调用者 Router，Router 不处理继续上抛，最终由 FastAPI 接住，所以处理它的人应该是 FastAPI。

    * `app = FastAPI()` 在入口文件里，`app` 就是 FastAPI 实例，异常处理代码写在 `main` 里。

    * 写法固定：一个函数加一个装饰器；参数是请求对象与异常对象两个，顺序不能反。

    ```python
    @app.exception_handler(ApplicationError)
    async def application_error_handler(request: Request, exc: ApplicationError):
        return JSONResponse(
            status_code=exc.status_code,
            content={"code": exc.code, "message": exc.message},
        )
    ```

* **装饰器与响应体部件**

    * `app.exception_handler` 是装饰器，`exception` 是异常、`handler` 是处理器，合起来是「异常处理程序」；加上它普通函数就变成全局异常处理器。

    * 装饰器参数写要捕获的异常类型，写父类 `ApplicationError` 就能接住所有子类。

    * 函数体返回 `JSONResponse`：`status_code` 指定 HTTP 状态码，`content` 是响应体。

    * `Request` 与 `JSONResponse` 都要手动导入，IDE 不一定自动补。

    * > **易错点**：函数第二个参数的类型标注必须与装饰器里捕获的类型一致，装饰器写 `ApplicationError`、参数标成别的类型，类型检查会报错。

* **三种码的分工**

    * HTTP 状态码属于协议层，告诉客户端这一类请求出了什么性质的问题。

    * 错误码（`code`）属于业务层，给前端做判断用，例如 `chat_thread_not_found`。

    * 错误消息（`message`）给人看，用于直接展示或记录，例如「当前会话不存在或者不属于当前用户」。

    * 前端拿到这份响应，状态码、错误码、错误消息一次俱全，判断与展示都不缺东西。

* **不处理的异常边界**

    * 只在业务里主动抛的异常才处理；框架层与数据库层的异常放任外抛。

    * 参数要整数却传字母，是 FastAPI 在参数校验阶段就拦下的类型错误，归框架管，不插手。

    * 传 `0` 能通过类型校验，一路走到查询查不到，走业务分支抛 `ChatThreadNotFound`，最后还是 400，属于业务异常，本来就在处理范围里。

    * 格式很怪的值一路到数据库、SQL 报参数错误，是数据库层的语句异常；理论上能捕，但意义不大，它说明调用方把数据搞坏了，不是业务规则拦下的。

    * 界线划得很清楚：业务异常是我们定义的、知道怎么向用户解释；框架异常与数据库异常有它们自己的处理方式，硬接过来反而会盖住真正的问题。

    * > **提示**：暂时不会写异常处理可以先跳过，让异常直接抛出去变 500，接口照样能跑通；等功能都通了再回头补，顺序不影响结果。

## 状态码语义与常见误判

* **500 的误用**

    * 500 的含义是「服务内部错误」，前端看到 500 第一反应是「服务端挂了」。

    * 用不属于自己的会话 id 改标题，责任在调用方传了非法参数，服务端只是拒绝了这次请求；报成 500 等于把责任揽到自己身上，前端也无法判断该重试、该提示用户还是该找后端。

    * 按 RESTful 约定，请求参数有误应给 400，含义很明确：你传的东西不对。

| 状态码 | 含义 | 典型场景 |
| :--- | :--- | :--- |
| 200 | 成功 | 正常返回数据 |
| 400 | 请求参数有误 | 参数不合法、归属校验不通过 |
| 404 | 资源不存在 | 访问的路径或资源找不到 |
| 405 | 方法不允许 | 路径对，但用的 HTTP 方法不对 |
| 500 | 服务内部错误 | 服务端代码抛了未处理的异常 |

* **重命名的完整执行链**

    ```text
    service  raise ChatThreadNotFound（400 / chat_thread_not_found / 当前会话不存在或不属于当前用户）
       │
       ▼
    router   不处理，继续往上抛
       │
       ▼
    FastAPI  @app.exception_handler(ApplicationError) 接住
       │
       ├── exc.status_code ──▶ HTTP 状态码 400
       ├── exc.code        ──▶ 错误码 chat_thread_not_found
       └── exc.message     ──▶ 错误消息 当前会话不存在或者不属于当前用户
       │
       ▼
    前端     JSONResponse，三者一次拿全
    ```

* **测试结论**

    * 正确的一对 `user_id` 与 `thread_id` 返回 200，返回的是刷新后的最新数据。

    * 把 `user_id` 换成不相干的值，返回 400，响应体里是 `code` 与 `message` 两个字段。

    * 自定义异常返回自定义结果，到这一步全局统一异常处理才算真正落地；一个处理器管住所有业务异常，每个异常返回什么由它在定义时决定。
