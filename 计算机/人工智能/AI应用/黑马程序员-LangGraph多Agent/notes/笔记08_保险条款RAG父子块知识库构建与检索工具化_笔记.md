# 保险条款 RAG：父子块知识库构建与检索工具化

## 条款文档的版式真相

### 版式与层级

* **隐形表格排版（Borderless Table Layout）**

    * > **定义**：保险条款 PDF 的正文并不是排版好的段落，而是一张无边框的两列表——左列放编号，右列放内容，只有拉开选框才会显出表格线。

    * 编号自带层级语义：单独一个「一」是第一章，其下的「1.1」是第一章第一小节，「1.2」是第二小节，依次类推。

    * 表格不在当页画完：画到页底被截断，下一页续排、再截断、再续排，整份 55 页从头到尾就是同一张跨几十页的大表。

    * 这种结构超出通用解析器的识别能力，即便 PDF 处理能力较强的工具也不能保证还原完好。

* **编号树即标题树**

    * 编号结构本身就是一棵标题树，与 Markdown 的层级一一对应：章是一级标题，小节是二级标题。

    * 一个小节的内容正好是一个条款：缴费一章下「3.1 保费的缴纳」讲怎么交，「3.2 宽限期」讲宽限期。

    * > **结论**：先把 PDF 解析成带标题层级的 Markdown，再按标题切分，一个小节就是一个条款，条款完整性天然被保住。

### 切分粒度的取舍

* **结构感知切分的现实阻力**

    * 理想方案是按小节切分，一节一段；问题在于小节长度极不均匀。

    * 「免赔额」一节长到一屏翻不完，责任免除一节顶别人好几节。

    * 通用经验块大小区间是 200~1000，数千字的小节早已破表；块太大时一段文本压成一个向量，主题被稀释，检索精度随之下降。

* **切分粒度与检索精度的取舍**

    * 块大则语义完整、噪音多、检索精度低；块小则语义完整度低、噪音少、检索精度高。

| 切法 | 语义完整度 | 噪音 | 检索精度 |
| :--- | :--- | :--- | :--- |
| 块大 | 高 | 多 | 低 |
| 块小 | 低 | 少 | 高 |

* > **易错点**：块大小不是「越大越省事」。大块省的是切分的心，亏的是召回的钱——检索回来一大坨，模型要么被噪音带偏，要么抓不住重点。

## 父子块双层切分

### 两层结构与回爬

* **父子块切分（Parent-Child Chunking）**

    * > **定义**：把切分拆成两层——第一层按文档结构切出对应完整条款的大块，第二层对超限的大块递归切出若干小块，两种粒度分别服务于完整度与精度。

    * 这不是现成工具，没有哪个 splitter 叫父子块切分器，是一套需要自己实现的流程。

    * 父块天然对应一个完整条款；子块是父块超限后的递归产物。

    * 同一父块切出的多个子块共享父块标题：把父块标题拼进每个子块正文，子块散开后仍知道自己在讲哪一条。

* **父块与子块的分工**

    * 父块进普通关系数据库，用来拼进 prompt 发给模型，保的是条款完整度。

    * 子块进向量库，用来做含过滤的向量检索，保的是检索精度。

| 角色 | 存在哪里 | 用在哪 | 保什么 |
| :--- | :--- | :--- | :--- |
| 父块 | 普通关系数据库 | 拼进 prompt 发给模型 | 条款完整度 |
| 子块 | 向量库 | 向量检索（含过滤） | 检索精度 |

* **回爬（Parent Lookup）**

    * > **定义**：向量检索只保证「最像」不保证「最全」，所以子块必须携带父块标识，命中子块后按标识回关系库取出完整条款。

    * 关联字段是 `parent_id`：父块记录本就有唯一 `id`，往向量库存子块时附带一个 `parent_id`，写它所属父块的 `id`。

    * 同一小节切出的子块 `parent_id` 相同，换了小节自然不同。

    * 完整链路：用户提问 → 向量库检索命中子块 → 取子块的 `parent_id` → 按 id 查父块表 → 父块与问题一起交给模型 → 生成答案。

    * 具体一例：父块 1001 讲「我们保什么」、1002 讲等待期、1003 讲免责；用户问「哪些情况不赔」，命中的子块 `parent_id` 恰好是 1003，按 id 取回免责整条再喂模型。

    * > **结论**：子块负责「找得到」，父块负责「说得全」；子块检索、父块喂模型，精度与完整度不再互相拉扯。

### 两条链路

* **两条链路的总图**

    ```text
    【离线：建库】
    条款 PDF ──► 解析 ──► Markdown ──► 结构感知切分 ──► 父块
                                                          │
                                                          ├──► 关系库 parent_chunks（整条落库）
                                                          │
                                                          └──► 递归切分 ──► 子块
                                                                              │
                                                                              ▼
                                                                           向量库
                                                                  （带 parent_id / product_id）

    【在线：问答】
    用户问题 ──► 向量化 ──► 向量库检索（filter: product_id）──► 子块
                                                                │ 取 parent_id
                                                                ▼
                                                        关系库查父块（完整条款）
                                                                │
                                                                ▼
                                              父块 + 用户问题 ──► 模型 ──► 答案
    ```

* **唯一的交接点**

    * 建库与问答两条链路唯一的交接点就是 `parent_id`；没有它，检索到的碎片与完整条款就是两个世界的东西。

    * 两条链路、五个业务字段、`parent_id` 回爬，这三样讲清楚，就是一份针对业务文档结构做出的设计决策，而不是「调了个链」。

## 子块的数据结构

* **四个字段的由来**

    * 自身 `id`：向量库入库时自带主键，底层可能叫 `pk` 也可能叫 `id`，代码里统一按 `id` 处理。

    * `parent_id`：指向父块，回爬时全靠它。

    * `content`：子块正文，用来生成稀疏向量与稠密向量、参与检索。

    * `product_id`：整数，检索前按产品过滤。

* **为什么第四个字段省不掉**

    * 库里的保险产品非常多，每个产品都有自己的条款，而这些条款大量重复或相似——同为医疗险，免责条款、等待期几乎人人都有，说法和用词都很像。

    * 只按语义搜「免责条款」，用户问 A 产品却可能召回 B 产品的免责条款；答案读起来完全通顺，只是属于另一款产品，而且不会报错。

    * 产品表里每个产品都有 `id`，存子块时把产品身份钉在片段上，才能保证「用户问 A，搜出来的只能是 A」。

    * 该字段的用法有先后顺序：先用它把范围锁死，再在这批片段里找最相关的一条，两步走而不是一步到位。

    * > **易错点**：子块字段不是「够存就行」，而是「够查才行」。少一个过滤字段，检索就会串产品，而且串得很隐蔽。

* **过滤优先于相似度**

    * 有查询、有过滤时，过滤优先：先按 `product_id` 锁定候选集，再在这批片段里算向量距离。

    * 顺序反过来，相似度就会算到别人家的条款上。

    * 一例：`query` 是「等待期是多久」，`filter` 是 `product_id = 3`（假设 3 就是达尔文 12 号）；整库碎片先被切成只属于 3 号产品的一堆，再在这堆里找最像的一段。

    ```text
    全库片段（混着多个产品）
    ┌──────────────┬──────────────┬──────────────┐
    │ product_id=1 │ product_id=2 │ product_id=3 │
    └──────────────┴──────────────┴──────────────┘
                        │  filter: product_id = 3
                        ▼
            ┌────────────────────────────┐
            │  仅 product_id = 3 的片段  │
            └────────────────────────────┘
                        │  query: 等待期是多久
                        ▼
                     Top-K 命中子块
    ```

## Document 与向量库记录的对应

* **写入时的三字段**

    * `Document` 只有 `id`、`page_content`、`metadata` 三个字段；它是 LangChain 的类，不能给它加自定义字段。

    * `id` 存子块自身标识，`page_content` 存片段正文，`parent_id` 与 `product_id` 只能塞进 `metadata`。

* **入库时 metadata 被摊平**

    * `Document` 一旦扔进向量库，`metadata` 会被自动展开成一层标量字段，无需手动处理。

    * 落库后的记录由六部分组成：主键（`pk`/`id`）、`text`、`parent_id`、`product_id`、`dense_vector`、`sparse_vector`。

    * 对应关系固定：`id` 对应 `pk`，`page_content` 对应 `text`，`metadata` 的两个键各自变成同名独立字段，两个向量字段按 `text` 自动生成。

    * > **易错点**：写过滤条件时用的是 `product_id` 这个标量字段，不是 `metadata.product_id`；落库后 `metadata` 那层壳已经不存在。

    ```text
    写入时（Document）                     落库后（一条向量记录）
    ┌──────────────────────────────┐      ┌──────────────────────────────┐
    │ id           : "V2"          │      │ pk / id      : "V2"          │
    │ page_content : "……责任免除……"│  ──► │ text         : "……责任免除……"│
    │ metadata     : {             │      │ parent_id    : "1003"        │
    │   parent_id  : "1003",       │      │ product_id   : 3             │
    │   product_id : 3 }           │      │ dense_vector : [0.013, …]    │
    └──────────────────────────────┘      │ sparse_vector: {条款: 0.41}  │
                                          └──────────────────────────────┘
    ```

* **子块设计的边界**

    * 四字段设计只存在于 Python 这一侧；进了向量库，它就是「一个主键 + 两个标量 + 两个向量」的普通记录。

## 父块的数据结构

### 字段设计

* **六个字段**

| 字段 | 类型 | 用途 |
| :--- | :--- | :--- |
| `id` | uuid | 唯一标识，被子块 `parent_id` 命中，召回整块 |
| `product_id` | int | 所属产品，划归属、做筛选 |
| `content` | text | 完整条款正文，发给模型生成答案 |
| `clause_name` | text | 条款名称，前端展示引用来源 |
| `section_path` | text[] | 章节路径，前端展示「第几章第几节」 |
| `create_at` | timestamp | 创建时间，继承时间混入类自带 |

* **section_path 用数组的理由**

    * 章节本身是分层的：一级、二级、三级甚至四级标题，把每一级标题按顺序装进列表，前端要拼成什么样就拼成什么样。

    * 前端可以只取最后一层，也可以拼出「二 提供保障 / 2.3 保险责任 / 2.3-1 等待期」这样一条完整路径。

    * 拼成字符串就把结构写死了，前端再想拆就难。

* **字段的两组用途**

    * 给机器用：`id` 负责被召回，`content` 负责喂模型。

    * 给人看：`product_id` 划归属，`clause_name` 与 `section_path` 在用户点开引用时拼出「条款名 + 章节」，正文仍取自 `content`。

    * > **提示**：设计时先把这两组分清，后面加字段就不会乱。

### 引用溯源与落库

* **引用溯源（Citation）**

    * > **定义**：在答案旁标出每句话的来源，让用户能点开看到对应的条款名称、所属章节与完整内容，而不是只能选择相信或不相信。

    * 联网问答里答案后跟的角标就是这种机制：标号指向真实页面，证明回答不是模型瞎编的。

    * 客服答条款的要求更硬：用户问「等待期多久」，不能只甩一个「180 天」，得让他看到这是哪个产品的哪一条、在第几章第几节。

    * 条款是要展示给用户看的，所以父块除了正文，必须再带条款名称与章节路径。

* **映射与代码组织**

    * 对应表名 `parent_chunks`，映射类 `ParentChunk`，字段与表一一对应，`section_path` 落库为数组类型。

    * 这个类继承 `Base`，也就是时间混入类，`create_at` 不用自己写。

    * RAG 属于比较特殊的一块功能，不与普通业务混在一起，单独放一个 RAG 包，映射类放进包内的 models 模块；多写两行 import，换来「哪些代码属于 RAG」一眼可见。

    * > **提示**：父块不进向量库，但一定要落库。它不参与相似度计算，只负责被 `id` 精确命中，这类查询交给关系型数据库比向量库合适。

## 从产品记录到条款文件

* **入库前的真实第一步是查询**

    * 按流程图第一件事像是「加载解析文档」，但解析得先有文档，文档要从数据库查，所以代码上的第一步是查询产品及其条款文件。

    * 四步固定为：查询保险产品及条款文件、加载并解析成纯文本、切分父块与子块、存入向量库与数据库。

* **复用现成的产品服务**

    * 不必自己写 SQL：已有「首页产品列表」接口，调用的是产品服务里的 `list_product`，传分类就按分类查，不传就查全部。

    * 服务对象创建时要传一个数据库会话，会话从基础设施层的会话工厂取；查询要 `await`，因为底层是异步 ORM。

    * 不传分类查回 12 条产品，每条都带 `id`、条款名称和一整套详情。

    * 建库真正要的只有两个字段：`id` 与条款名称（`clause_name`）。父块要知道自己属于哪个产品、条款叫什么名字，子块要 `product_id` 做过滤，其余字段对建库无用。

    * 验证阶段取一个产品即可：`product = products[0]`，它的条款名称就是条款文件名。

    ```python
    async with session_factory() as session:
        service = ProductService(session)
        products = await service.list_product()
    ```

* **文件放哪儿与路径怎么拼**

    * 条款文件统一放在项目目录下的数据目录里（数据根/原始/知识库三层），文件名就是产品记录上的条款名称。

    * 要把整个数据目录复制到项目根，而不是只拷知识库那一层——里面还有别的文件，将来别的业务要用；放在项目里，加载时就是「项目数据目录 + 文件名」，一句话说清。

    * notebook 位于两层子目录下，路径要先用两级上跳退回项目根，再进数据目录、接上文件名；层级数错一级，解析就会报文件不存在。

## 文档解析与结构修复

### 解析与验货

* **解析客户端直接复用**

    * 解析用 MinerU，代码不需要会默写：把原来那套创建客户端的代码复制过来，只改「解析哪个文件」这一处路径。

    * OCR 不用开：要解析的是文字型 PDF，不是扫描图片型，没有图片要识别，开了只是白花时间。

    * 解析约 11 秒，结果正文取自 `result.markdown`。

* **验货：结构失败比文字缺失更隐蔽**

    * 把 `result.markdown` 贴到本地 Markdown 文件里打开看，问题立刻显形：标题前面没有 `#`。

    * 没有井号就不是标题，只是一行普通文字；文字都在，骨架没了，结构上算解析失败。

    * 根因是那份 PDF 本身：横跨几十页的超大表格，第一个表格还能认对，第二、第三个就认错，结构识别错乱，输出自然跟着错——有些段落被解析成表格，有些没解析出来，有些侥幸被认成标题。

    * > **易错点**：PDF 解析「有文字输出」和「结构正确」是两件事。文字型 PDF 提文字几乎不会失败，失败的一定是层级——标题、编号、表格边界；这类错误不报异常，只会在切分时切出一堆没有章节信息的碎片。

    * 换解析器不能一劳永逸：各家保险公司条款格式差异极大，有的是超大表格，有的是「第一条、第二条」加圆括号标题，随便再点几份又是另一套样子。

    * > **结论**：条款文档的结构差异不是「个别脏数据」，而是行业常态；指望一个解析器通吃所有公司模板，必然在这些差异面前失效。

### 四条修复路线

* **四条结构修复路线**

    * 人工修正最可靠，因为人看得懂内容，改出来一定对；但它只适合少量文档，几十份还能忍，几百上千份就是纯人力消耗，而且条款一改，之前手工修过的还得重来。

    * 规则清洗把「肉眼判断这行是三级标题」的经验翻译成 if-else 与正则，同一输入永远给同一输出；硬伤有两个：一是写不出来（要求穷举所有格式变体，AI 代写也不代表写对），二是只认预先考虑过的格式，新产品格式一变规则当场作废。

    * 模板化是规则清洗的升级版：从「一套通用规则」换成「每家公司一套专用规则」，稳定性更高，代价是每来一套新模板就要重新开发、调试、上线，模板越多分支越多、通用性越差。

| 方案 | 做法 | 优点 | 局限 |
| :--- | :--- | :--- | :--- |
| 人工修正 | 逐份调整标题编号和表格 | 最可靠 | 只适合少量文档；条款变更后要重做 |
| 规则清洗 | 用正则或程序规则识别标题编号、删噪声、修格式 | 不用人、速度快、成本低、结果相对稳定 | 只能处理预先考虑过的格式，格式一变就作废 |
| 模板化处理 | 按不同保险公司的条款模板分别写转换逻辑 | 比规则清洗更稳定 | 每来一套新模板都要重新开发维护，通用性差 |
| 模型优化 | 让大模型理解语义，重排标题、层级编号和段落结构 | 不需要模板，兼容性最好 | 增加调用时间和成本，需要提示词防护 |

* **模型优化的取舍**

    * 模型优化让大模型读懂内容后重排标题、层级编号与段落结构，不需要模板，哪家公司的条款都能处理。

    * 代价有二：每份文档都要过一次大模型，增加调用时间与成本；必须做提示词防护，明确要求「不要修改条款正文」，否则它可能在重排结构时顺手改内容——条款一个字都不能被改写。

    * 选它的理由是前三种的编码复杂度远超当前阶段，而模型优化实现最简单、适应性最强；成本顾虑也被便宜的模型价格抵消。

    * > **提示**：前三种方案本质在做同一件事——把「理解结构」提前用人力、规则或模板固化下来；固化的部分越精确，覆盖面就越窄。

## 结构重排的提示词与长度上限

### 提示词约束

* **六条约束各堵一个坑**

| 约束 | 堵的坑 |
| :--- | :--- |
| 编号要正确 | 解析错乱最典型的表现是编号层级错位，本该属于下一级的内容被提到上一级 |
| 标题等级从一级开始逐层增加 | 不能让文档一上来就是三级标题，否则结构感知切分找不到顶层边界 |
| 目录和文档名不计入标题等级 | 目录页长得极像标题，被当成标题会切出一堆假父块 |
| 输出不含正文之前的部分 | 目录、封面、免责声明对问答无用，留着只会污染知识库 |
| 不要解释、不要代码围栏 | 要的是能直接落盘的 Markdown 正文，不是「好的，以下是整理后的内容」 |
| 不要修改保险条款 | 红线：模型只许动结构，不许动内容 |

* **围栏与验证方式**

    * 手工验证时开新对话、不开联网搜索、不用专家模式，用快速模式即可。

    * 把解析错的 Markdown 原文用三个反引号包起来再贴进去：围栏告诉模型「这是一整块文档」，原文里万一有像指令的句子，也不会被当成要求执行。

    * 输出结果一级、二级、三级、四级标题与编号层级全部对上——不动内容，只把骨架装回去。

### 输出长度上限

* **max_tokens 截断**

    * > **定义**：`max_tokens` 是单次生成输出长度的上限，按 token 计；它限制的是「这次能说多少」，不是「模型懂多少」。

    * 撞上上限的表现是话说到一半停住，页面出现「继续生成」按钮，且不报错。

    * 示例里输出停在 7.2 附近，而条款还有第八章（几十页疾病定义）与第九章；默认上限通常只有 1K 或 2K token，写到那里正好到头。

    * 判断顺序很重要：先确认这是上限截断，而不是解析又坏了，否则后面调参会一直找不到方向；第八章的疾病定义严格说不算条款，真截在 7.9 也能用。

* **代码化的固定两道工序**

    * 代码结构只有三件事：一段提示词、初始化模型（传 API Key、关掉思考模式）、调模型；调用时先传系统提示词，再把 `result.markdown` 作为用户提示词传进去。

    * 第一版先不传 `max_tokens`，跑一遍看效果；阻塞式调用不像页面流式输出，会慢一些，结果结构对但内容同样不完整——原因还是上限。

    * 把 `max_tokens` 调大再跑，输出才完整。

    * 文档加载解析的最终形态固定为两道工序：先 MinerU 把 PDF 解析成 Markdown，再用大模型把结构调优；往后每份条款进来都走这两步，最终作为流水线上的一个组件固定下来。

## 父子块切分的实现

### 切分器与去头策略

* **两把切分器**

    * 结构感知切分器是 `MarkdownHeaderTextSplitter`，参数是「按几级标题切」；这里切到四级，因为文档里确实出现了四级标题、甚至五级，再深的细碎长段落交给递归切分更合适。

    * 递归切分器块大小设 500、重叠 50（约 10%）；某块超过 500 就从中间找地方断开。

    * 递归分隔符的优先序是段落 → 换行 → 句号 → 分号 → 逗号，目的是尽量在语义边界下刀，避免把一句话劈成两半。

    ```python
    parent_splitter = MarkdownHeaderTextSplitter(   # 结构感知：按 H1–H4 切，先去掉标题头
        headers_to_split_on=[("#", "H1"), ("##", "H2"), ("###", "H3"), ("####", "H4")],
        strip_headers=True,
    )

    child_splitter = RecursiveCharacterTextSplitter(   # 递归切分：每块 500，重叠 50（约 10%）
        chunk_size=500,
        chunk_overlap=50,
    )
    ```

* **一个父块至少一个子块**

    * 父块大小没超过 `chunk_size` 时，原样复制一份当子块，此时子块与父块内容完全相同。

    * 留这份「复制品」的理由：往向量库扔的是子块，父块多大都得有对应的子块。

    * 父块超过 `chunk_size` 则被递归切成多个子块；两头都成立，所以这句话没有例外。

* **strip_headers 的取舍**

    * `strip_headers=True` 是把标题头从正文里去掉；直觉上会反对——头就是一块内容的身份，去掉怎么知道它在讲什么。

    * 但保留头再切，头只留在第一块里：`[头 + 正文A + 正文B + 正文C]` 切成 `[头+A] [B] [C]`，后两块光秃秃。

    * 先去头再切，三块都没头，再从 `metadata` 取回 H1…H4 逐块拼回，三块就都有头。

    * 头并没有丢：结构感知切分会把各级标题塞进 `metadata`，动作只是「切的时候从正文去掉，切完从 `metadata` 取出、拼回每个子块」。

    * > **提示**：头不是不要，是「晚一点给、给每一份」——切分阶段去掉，避免只有第一块继承到它；回填阶段补上，让每一块都能独立被检索、独立被读懂。

### 两刀切分与回填

* **第一刀：切出小节**

    * 调用 `split_text(markdown)`，结果每个 `section` 都是 `Document`：`metadata` 里是 H1、H2 直到 H4，`page_content` 是原文且已无标题。

    * 实测 54 个小节，对应 54 个父块。

    * 父块封装时逐字段取值：`id` 用 `uuid4()` 现场生成，`product_id` 取 `product.id`，`clause_name` 取产品记录上的条款名，`section_path` 取 `list(section.metadata.values())`（要的是值不是键），`content` 取 `section.page_content`。

    * 也可以把 `section_path` 拼进父块 `content`，让父块自身带标题；做不做都行，这里没拼。

    ```python
    parent_chunks = []

    for section in sections:
        section_path = list(section.metadata.values())

        parent_chunk = ParentChunk(
            id=uuid4(),
            product_id=product.id,
            clause_name=product.clause_name,
            section_path=section_path,
            content=section.page_content,
        )
        parent_chunks.append(parent_chunk)
    ```

* **第二刀：子块与 metadata 继承**

    * 用 `split_documents` 而不是 `split_text`：前者传 `Document` 列表、返回 `Document` 列表；后者传字符串、返回字符串列表，而向量库的 `add_documents` 收的是 `Document` 集合，用 `split_text` 还得手动转回去。

    * 要传 `section`，不能传 `parent_chunk`：`parent_chunk` 是表对象，切分器只认 `Document`；而 `parent_chunk.content` 本来就来自 `section.page_content`，切 `section` 等于切父块。

    * 因为是「遍历一个、切一个」，每次手工造一个只含当前 `section` 的列表传进去；接口本身支持批量，扔长列表可一次切完。

    * 切之前把 `section.metadata` 整个覆盖成 `{"parent_id": parent_chunk.id, "product_id": product.id}`：原来的 H1、H2 不符合子块要求，直接换掉。

    * 覆盖一次就够，因为切出的每个小 `Document` 都继承父 `Document` 的 `metadata`——父亲有什么儿子就有什么，父亲没有的儿子永远不会有。

    * > **易错点**：切分 API 是「传什么切什么」——`split_text` 传字符串得字符串列表，`split_documents` 传 `Document` 列表得 `Document` 列表；记死这一条，就不会出现「切完还得手动转回 `Document`」的返工。

    ```python
    section.metadata = {
        "parent_id": parent_chunk.id,
        "product_id": product.id,
    }

    child_chunks = child_splitter.split_documents([section])
    ```

* **回填标题与顺序纪律**

    * 每个子块 `page_content` 里没有标题，要还回去：`header = "\n".join(section_path)`，再与子块正文拼成 `header + "\n" + child.page_content` 重新赋值。

    * 顺序不能错：先设 `metadata` → 再切 → 切完拼头 → 最后 `extend` 进总列表；任何一步提前（比如先拼头再切），头又会被切散，白干一趟。

    * 汇总用 `extend` 不用 `append`：切出来本来就是多个子块，要整体摊进去。

    ```python
    header = "\n".join(section_path)

    for child in child_chunks:
        child.page_content = header + "\n" + child.page_content

    child_chunks_all.extend(child_chunks)
    ```

* **切完先核对数量与归属**

    * 实测父块 54 个、小节 54 个，一一对应；子块切出 69 个。

    * 同一父块下的子块 `parent_id` 完全相同：1.4 小节「等待期」正文超过 500，被切成三块，三块的 `metadata` 都是同一组 `product_id` 加 `parent_id`。

    * 反过来看，「继承」正是提前覆盖 `metadata` 的唯一原因——切分器不负责补字段，它只会照抄父亲的。

    ```text
    1.4 等待期（父块，正文超过 500）
            |
            +-- 子块 1（头 + 等待期前段）  --+
            +-- 子块 2（头 + 等待期中段）  --+-- parent_id / product_id 三者完全相同
            +-- 子块 3（头 + 等待期后段）  --+
    ```

## 子块写入向量库

* **配置项**

    * 顺序是：先准备 embedding 模型，再建 Milvus 的 vector store；collection 名字用 `insurance_collection`，是这个业务的专属集合。

    * 稀疏向量由 BM25 转换函数生成，中文分词器负责切词，向量字段一个稠密一个稀疏，`auto_id` 打开让 Milvus 自动生成主键。

| 配置项 | 作用 |
| :--- | :--- |
| 向量模型 | 把文本转成稠密向量（Ollama，也可换阿里云） |
| collection name | `insurance_collection`，这个业务的专属集合 |
| builtin function | BM25 转换函数，用来生成稀疏向量 |
| analyzer | 中文分词器 |
| vector field | 两个向量字段：一个稠密、一个稀疏 |
| connection args | Milvus 的连接地址 |
| auto id | `True`，让 Milvus 自动生成主键 |

* **入库动作与结果核对**

    * 入库只需 `add_documents(child_chunks_all)`；LangChain 的封装把「向量化」和「入库」合成一步，算完向量就存进去。

    * 首次报错是连不上 Ollama——服务没启动；这类错误滚到最下面读最后几行解释即可，不必猜。

    * 再跑约 4 秒完成；在可视化客户端刷新，多出一个 collection，69 条数据。

    * schema 与预期完全一致：有 `pk`、`text`、`dense`、`sparse`，以及摊平出来的 `product_id`、`parent_id`。

    * 文本里标题都带着，说明回填没白做；主键自动生成，目前全是同一产品，所以 `product_id` 完全一样。

    * `product_id` 可以建 inverted 索引提升过滤效率，这里没建也够用。

* **两种检索都可用**

    * 向量检索走稠密向量，全文检索走 BM25 的倒排索引。

    * 搜「等待期」能命中并高亮，排前三的正是同一父块切出的三个子块。

    * 分词会把「等待期」拆成「等」「期」「等待期」三个词，三个词都参与检索，命中范围自然更宽。

    * > **提示**：`auto_id=True` 只针对子块——子块进向量库不用填 id；父块的 id 早已用 `uuid4()` 生成，两者不冲突，不要在一条链路上混着想。

## 父块写入关系库

### 仓储与删除

* **仓储类的骨架**

    * 凡是要落库的模块都单独写一个 repository，类名跟表走，叫 `ParentChunkRepository`。

    * 构造函数接一个 session 攥在手上；方法只做两件事：新增与按产品删除。

    * `add_all` 收的就是切完的那一堆父块，`session.add_all` 本身接收列表，方法体只有一行。

    ```python
    class ParentChunkRepository:
        def __init__(self, session: AsyncSession):
            self.session = session

        def add_all(self, parent_chunks: list[ParentChunk]) -> None:
            self.session.add_all(parent_chunks)

        async def delete_by_product(self, product_id: int) -> None:
            await self.session.execute(
                delete(ParentChunk).where(ParentChunk.product_id == product_id)
            )
    ```

* **为什么必须有删除**

    * 场景一：产品下架要清掉块，重新上架要再插。

    * 场景二更常见：产品条款变更，直接插会让新旧两份条款同时躺在库里互相打架，必须先删旧的再插新的。

    * 按 `product_id` 删，因为变更是整个产品维度的事，跟这个产品有关的所有 chunk 都要清掉，不能只清某一条。

    * 对应 SQL 就是 `DELETE FROM parent_chunks WHERE product_id = ?`。

    * ORM 写条件删除记住三句对应关系：表对应类、字段对应类的属性、数据对应类的对象；`session.delete` 只能删对象，删一批要用 `delete(Model).where(...)` 配 `execute`。

    * > **易错点**：`session.delete(obj)` 和 `delete(Model).where(...)` 是两套东西——前者按对象删一条，后者按条件删一批；批量清某个产品的块只能用后者。

### 联调与先删后增

* **联调顺序与踩坑**

    * 事务里先删再加，顺序不能反：`async with` 开会话 → `await session.begin()` → 建仓储 → `await repo.delete_by_product(product.id)` → `repo.add_all(parent_chunks)`。

    * 第一次报错是漏了 `await`：`delete_by_product` 内部用异步的 `session.execute`，调用要 `await`；但 `add_all` 内部是同步的 `session.add_all`，不能无脑加 `await`。

    * 改完不生效是内核没重启：notebook 里 import 的是启动时加载的那份源码；一重启，查产品、解析、切分全要重跑，光解析就要等三四十秒（`max_tokens` 设得长，输出越长越慢）。

    * 再报错是表里没有 `clause_name` 列：model 里写了、数据库表里没建，ORM 一 insert 就找不到列；手工补上 `varchar(500)` 后成功。

    * 表结构与 model 必须严格对齐，这是入库前值得专门核对一遍的东西。

    * > **提示**：测多阶段流水线先把中间产物落下来——把优化后的 Markdown 单独存一份，下次从这份 Markdown 开始切，省掉重新解析的大段等待。

* **向量库同样先删再添**

    * 产品条款一变，父块删了而子块还留着，检索时照样会把作废条款捞出来——这比检索不到更糟，模型会拿过期条款回答用户。

    * 子块 id 是 `auto_id` 自动生成的，手上没有；`delete` 除 id 外还接收 `expr` 过滤表达式，写法同 SQL 的 where。

    * collection 里有 `product_id` 字段，就按它删：`expr = f"product_id == {product.id}"`，再 `vector_store.delete(expr=expr)`。

    * 必须用 f-string 拼真实 id，不能写死成 `1`——写死那次能跑通，只是因为当前产品 id 恰好是 1。

    * 删除返回 `True`，刷新数据库数据消失，再执行插入数据回来，先删再加的闭环成立。

    * > **提示**：表达式的值类型要和字段类型对上：字段是字符串，值就要加引号；是整数就直接写数字。类型不匹配会报错或匹配不到。

* **切分到入库的全景**

    ```text
    markdown（优化后）
          |
          | MarkdownHeaderTextSplitter（切到 H4，strip_headers=True）
          v
    sections：54 个 Document（metadata 存 H1…H4，正文无标题）
          |
          +--- 封装 ParentChunk ---------------> 关系库 parent_chunks（54 条）
          |
          +--- RecursiveCharacterTextSplitter（500 / 50）
                        |
                        v
                 子块 69 个（回填标题头）
                        |
                        v
                 向量库 insurance_collection
           （pk / text / dense / sparse / product_id / parent_id）
    ```

    * 父块与子块从同一批 `section` 分出去，各自进各自的库；连接它们的就是子块 `metadata` 里的 `parent_id`。

## 知识库 Pipeline 封装

### 类骨架与初始化

* **为什么要组装流水线**

    * notebook 里每一步手工串起来最适合验证，改一行就能重跑；正式建库时十几个产品都要走同样的动作，必须把加载、解析、切分、存向量库、存数据库封装成可复用的流水线。

    * 组装的目的不是让代码整齐，而是写一次、每个产品都跑同一套流程。

    * 流水线住在 RAG 包里，单独一个 pipeline 模块。

* **RAGPipeline 的类骨架**

    * 对外只暴露一个入口，吃进一个产品、把它的条款送进知识库；方法名从 `ingest` 统一成 `index`。

    * 入口参数是 product，因为整条链路从它派生：靠它的条款名找到文件，找到文件才谈解析、切分、入库。

    * 方法体就是四步：加载并解析、切分、存向量库、存数据库，严格串行，上一步的产物是下一步的输入。

    ```python
    class RAGPipeline:
        def __init__(self, vector_store: Milvus):
            self._vector_store = vector_store
            self._mineru = ...                  # 文档解析客户端，只建一次
            self._llm = init_chat_model(...)    # 文档优化用的大模型
            self._md_splitter = ...             # Markdown 切分器，切父块
            self._recursive_splitter = ...      # 递归切分器，切子块

        async def index(self, product):
            markdown = self._parse_document(file_path)                 # 1. 加载并解析
            parent_chunks, child_chunks = self._split_documents(       # 2. 切分
                markdown, product
            )
            self._save_child_chunks(child_chunks)                      # 3. 存向量库
            await self._save_parent_chunks(parent_chunks, product)     # 4. 存数据库
    ```

* **初始化位置的取舍**

    * 构造函数只接收 `vector_store`，类型限定为 Milvus：不管从哪来，传一个能用的进来就行。

    * 解析客户端与优化用大模型都是重客户端，不能每处理一次就重建，放进构造函数做私有成员。

    * 切分器本身不持有状态，更没有理由每次切分重新 new 一个。

    * 向量库不在构造函数里建，原因不是「重」而是「共用」：它不只用来写数据，检索也要用它查数据，各自建一份等于同一个东西创建多份。

| 组件 | 初始化位置 | 原因 |
| :--- | :--- | :--- |
| 解析客户端 | 构造函数，私有成员 | 重客户端，不能每处理一次就重建 |

## 检索链路的设计

* **两种 RAG 模式**

    * two step 模式把检索与生成拆成固定的两步，先检索再生成，流程由代码写死。

    * agentic 模式把整套检索流程封装成一个工具交给 agent，由它自己判断要不要检索、该怎么检索；项目用的是这一种。

    * 选 agentic 的直接后果：接下来注意力落在一个问题上——怎么封装一个 RAG 检索工具。

* **查询重写（Query Rewriting）**

    * > **定义**：在检索之前把用户的原始问题改写成更贴近知识库表述、更适合检索的查询词或查询句。

    * 用户的问题往往很口语：「这个保险什么情况下不赔」是大白话，直接拿去搜大概率搜不准；他真正想问的是免责条款，而知识库也用「免责条款」表述。

    * agentic 模式下不需要自己写重写逻辑：把 RAG 封装成工具、让模型调工具并传入 query，模型不会把原句直接丢给检索工具，它会先分析问题再生成检索关键字，这个过程本身就实现了查询重写。

    * 常见方案还有关键字改写（把口语问题压成检索词）、HyDE（先让模型虚构一份答案或文档，再拿虚构内容去检索）、multi-hop（把复杂问题拆成子问题分多跳查）；这些都不用自己管，知道名字即可。

    * > **提示**：被问到检索增强的流程，第一步一定要答出查询重写；它在项目里可能是 agent 顺手完成的，但确实是流程的一环。

* **完整七步链路**

    * 前四步解决「找得准」，后三步解决「答得全」，分界线在子块召回。

    * 重写后的查询可能是一句话也可能是一组关键字，不影响后续处理；稠密走向量语义、稀疏走词面匹配，两路各有所长。

    * 两路结果用 RRF 融合成一份排序，再用 cross-encoder 对候选逐条精算相关性，比单纯向量相似度更准。

    * 召回子块是因为子块小、更容易精准命中；但子块上下文不完整，所以拿 `parent_id` 回库取完整父块，再交给模型。

    ```text
    用户问题
       │
       ▼
    [1] 查询重写            agent 分析问题，生成更适合检索的 query
       │
       ▼
    [2] 混合检索            稠密检索 + 稀疏检索，两路并行
       │
       ▼
    [3] 结果融合            RRF，把两路排序合成一份
       │
       ▼
    [4] 重排                cross-encoder 对候选精排
       │
       ▼
    [5] 召回子块            child chunk，里面带着 parent_id
       │
       ▼
    [6] 按 parent_id 查父块  回关系数据库取完整上下文
       │
       ▼
    [7] 父块交给模型        生成最终回答
    ```

* **真正要动手的只有三件事**

    * 稠密检索、稀疏检索、RRF 融合、重排，这一整套 Milvus 的 vector store 已经实现；查询重写由 agent 完成。

    * 留给自己的只有：召回子块、按子块查父块、把父块发给模型。

    * 所以封装检索工具时，重心就放在这一小段——前半部分直接调 vector store 拿子块，要补的是从子块到父块的那一跳，以及把父块组织成模型能用的上下文。

## Retriever 的召回实现

### 类结构与混合检索

* **类与入口**

    * 代码不短（召回、取 id、去重、查库、排序），单开一个 retriever 模块，类名 `ParentChunkRetriever`——名字里带 `ParentChunk`，一看就知道最后吐出来的是父块。

    * 用词习惯：类用名词 `Retriever`，方法去掉尾巴的 `r` 写成动词 `retrieve`，一个字母的差别让读代码的人分得清哪个是东西、哪个是动作。

    * 构造函数同样接收外部传入的 vector store，不在内部自建；流水线建一个、检索器再建一个就是重复创建。

    * `retrieve` 是异步函数（既要异步查向量库，也要异步查数据库），三个参数：`query` 是检索输入，`k` 是最终返回条数，`product_id` 是产品编号（整数）。

    * > **提示**：`k` 写死也能跑，区别是换个场景要改源码；做成参数只改调用处。

    ```python
    class ParentChunkRetriever:
        def __init__(self, vector_store: Milvus):
            self.vector_store = vector_store
    ```

* **四步骨架**

    * 前两步在向量库与内存里完成，第三步落到关系库，第四步纯粹是内存重排。

    * 四步顺序不能乱：先召回子块，才能取 `parent_id`；先去重，才能批量查库；先查库，才能按召回顺序排回去。

    ```text
    query + product_id
            │
            ▼
    ① 混合检索：稠密 + 稀疏 → 重排 → top k 个子块
            │
            ▼
    ② 从子块的 metadata 里取 parent_id，并去重
            │
            ▼
    ③ 按这批 id 批量查 parent_chunks
            │
            ▼
    ④ 把父块按 ② 的顺序排回去
            │
            ▼
       有序的父块列表
    ```

* **asimilarity_search 的四个参数**

    * `k`：最终返回条数，取分数最高的 k 条。

    * `fetch_k`：初筛时每一路返回的条数；混合检索分初筛与重排两段，`fetch_k=10` 是稠密返回 10 条、稀疏返回 10 条，这 20 条一起进重排器，最后由 `k` 决定留几条。

    * `expr`：按产品过滤，不是可选项而是必须项——库里 1、2、3、4、5 号产品的条款同在一张表，搜「等待期」不加过滤，五家的等待期会一起回来，而用户问的只是其中一家。

    * `ranker`：混合检索要做重排，参数一漏这道工序就没了；重排器由 `create_cross_encoder_ranker` 生成，来自 `langchain_milvus`。

    * 重排器里字段名必须与文档存文本的字段对上（这里是 `text`），模型与 provider 都不用改。

    * 该函数内部要的是 query 列表，而检索永远只传一个 query，所以对外收字符串、在函数内部包成列表，用的人只管传一句话。

    * 同步与异步两套接口都在，用哪套看调用方是不是异步。

    * > **易错点**：`fetch_k` 不是「总共取多少条」，而是每一路的条数；写成 10，实际进重排的是两路各 10 条。

    ```python
    child_chunks = await self.vector_store.asimilarity_search(
        query,
        k=k,
        fetch_k=10,
        expr=f"product_id == {product_id}",
        ranker=create_cross_encoder_ranker(query),
    )
    ```

### 父块回查与排序

* **从 Document 里取 parent_id**

    * `asimilarity_search` 返回的是 `list[Document]`，不是数据库里那一行数据；`parent_id` 不在第一层，在 `metadata` 字典里。

    * 取值写法：`parent_ids = [child.metadata.get("parent_id") for child in child_chunks]`；不习惯推导式就写普通 for 循环逐条 append，效果一样。

    * 两边的字段对应是固定的，向量只在检索打分时用，不进 `Document`。

| Milvus 行字段 | Document |
| :--- | :--- |
| `pk` | `id` |
| `text` | `page_content` |
| `dense` / `sparse` | 只在检索打分时用，不进 Document |
| `product_id` | `metadata["product_id"]` |
| `parent_id` | `metadata["parent_id"]` |

* **去重且保序**

    * 两个子块完全可能来自同一个父块，`parent_id` 一模一样；重复 id 查回来的父块也重复，返回给模型就是同一段话出现两遍，所以必须先去重。

    * `set` 去重能用，但 `set` 不保证顺序，而后面要靠 `parent_ids` 的顺序把父块排回去，`set` 一过顺序就散。

    * 更省事的写法：`parent_ids = list(dict.fromkeys(parent_ids))`——字典 key 天生唯一，重复自动被吞掉，外层再转回列表；一行完成去重且按元素第一次出现的顺序保留。

    * > **提示**：`dict.fromkeys` 与 `set` 的差别就在顺序，这条差别在下一步是关键。

* **按 id 批量查父块**

    * 子块的 `parent_id` 就是父块的 `id`，天然是一次按 id 的查询；但一次召回可能命中多个子块，拿到手的是一批 id 而不是一个，条件必须用 `IN` 而不是等号。

    * 参数 `ids` 是字符串列表，因为 id 是 UUID，传递时用字符串格式。

    * 对应关系：`select(ParentChunk)` 等于 `select ... from parent_chunks`；`.where(ParentChunk.id.in_(ids))` 中 `id` 是类属性、表字段，`in_` 对应 SQL 的 `IN`。

    * 查多条要用 `session.scalars()` 而不是只返回单条的 `scalar()`；`await` 拿到结果集再 `.all()` 收集成 `ParentChunk` 对象列表。

    * 调用前先挡空结果：`if not child_chunks: return []`——过滤卡得紧、产品没入库、query 完全不沾边都会返回空列表，空列表往下走 `IN ()` 没有意义。

    * 会话用 `async with` 开和关，出了块自动收掉。

    ```python
    async def query_by_ids(self, ids: list[str]) -> list[ParentChunk]:
        result = await self.session.scalars(
            select(ParentChunk).where(ParentChunk.id.in_(ids))
        )
        return result.all()
    ```

* **把乱序的父块排回去**

    * 数据库查询默认按 id 排，等于把前面费力排好的相似度顺序整个打乱；返回给模型时它看不出哪段最相关，稠密稀疏融合与重排的功夫就白费了。

    * 两步补救：先 `parent_map = {str(parent.id): parent for parent in parents}` 把列表变成按 id 索引的字典，再 `[parent_map.get(pid) for pid in parent_ids]` 按召回顺序逐个取。

    * `for pid in parent_ids` 保证顺序，`parent_map.get(pid)` 保证按 id 取到对应父块。

    * 也可以加「id 在字典里存在才放入」的条件，属于防御性写法，数据健康时不加也不影响功能。

    * > **结论**：顺序是检索结果的一部分，不是附带信息；谁把顺序弄丢，谁就得负责补回来。

* **UUID 类型差异造成的静默 None**

    * 测试时 `chunks` 里全是 `None`：不是空列表也不是报错，说明前面几步都在跑，只是最后一步取歪了。

    * 逐层打印 `child_chunks`、`parent_ids`、`parents`、`parent_map`，每层看着都正常，可 `parent_map.get(pid)` 就是取不到。

    * 看类型才露头：数据库查回的 `parent.id` 是 `uuid.UUID` 对象，而 `parent_ids` 里是字符串；拿字符串去取 UUID 的 key，取不到。

    * `dict.get()` 取不到不报错，只返回 `None`，于是每个位置安安静静留一个 `None`，连异常都不给。

    * 修法：建字典时把 key 转成字符串——`{str(parent.id): parent for parent in parents}`，两边都是字符串才找得到。

    * > **易错点**：UUID 在 Python 里是对象不是字符串；数据库驱动读回来是 `uuid.UUID`，从 JSON、从 `metadata` 读回来是 `str`，两者不相等，拿来做字典 key 尤其容易踩——不报错，只是查不到。

    * 修完重跑：结果每条 `product_id` 都是 1，内容都是等待期相关，其中一条写着「自本合同生效之日起 180 日为等待期」，过滤与排序都生效。

    * > **结论**：这一段的坑不在逻辑，在类型；逻辑通了、类型不对，结果是一串 `None`，比报错更难查。看到「都跑通了但结果是空的」，先打印中间变量看类型，不要先怀疑算法。

    ```python
    async def retrieve(self, query: str, k: int, product_id: int):
        child_chunks = await self.vector_store.asimilarity_search(
            query,
            k=k,
            fetch_k=10,
            expr=f"product_id == {product_id}",
            ranker=create_cross_encoder_ranker(query),
        )

        if not child_chunks:
            return []

        parent_ids = [child.metadata.get("parent_id") for child in child_chunks]
        parent_ids = list(dict.fromkeys(parent_ids))

        async with AsyncSessionFactory() as session:
            repo = ParentChunkRepository(session)
            parents = await repo.query_by_ids(parent_ids)

        parent_map = {str(parent.id): parent for parent in parents}
        return [parent_map.get(pid) for pid in parent_ids]
    ```

## 检索工具化

* **工具的三步结构**

    * 工具统一放在 agent 下的 tools 里，函数名 `retrieve_insurance_clause`，整个工具只有检索、整理、返回三步。

    * 三个参数都不是自己填的，是「调工具的人」给的——也就是模型。

    * `query` 必须由模型生成：到底搜什么由用户的问题产生条件，模型发现用户在问条款信息时，就根据提问组织查询条件。

    * `k` 可以让模型给也可以写死，取决于设计；`product_id` 同样由模型给——用户在上下文里说「达尔文」，模型就去聊天记忆里找它对应的 id。

    * 模块级 `retriever` 用函数内导入而非文件顶层导入，避免模块导入即触发初始化。

    ```python
    async def retrieve_insurance_clause(query: str, k: int, product_id: int) -> list[str]:
        """根据用户的提问检索保险条款，返回条款原文片段。

        Args:
            query: 检索关键词。
            k: 返回文档的数量。
            product_id: 要检索的保险产品 ID。
        """

        from app.rag import retriever

        chunks = await retriever.retrieve(query=query, k=k, product_id=product_id)

        return [
            f"section: {chunk.section_path}\ncontent: {chunk.content}"
            for chunk in chunks
        ]
    ```

* **返回值只留两样**

    * `retrieve` 返回的 `chunks` 是 `ParentChunk` 列表，字段很多：`clause_name`、`content`、`id`、`product_id`、`section_path`。

    * 全丢给模型没必要：目的是让它回答问题，`id` 这类东西与回答无关，真正需要的只有 `content`。

    * 多带一个 `section_path`，因为路径里可能藏着有用关键字，比如「等待期」会出现在章节标题里，对回答有帮助。

    * 把两者拼成一个字符串，每篇文档一条，整体做成列表返回；把所有结果拼成一整条字符串也能用，道理一样。

    * > **易错点**：不要图省事把整个对象序列化后丢给模型。字段一多，模型反而抓不住重点，还平白多烧 token。

* **docstring 与类型标注**

    * 工具只有函数名和参数名，模型看不出它是干什么的、每个参数什么意思，所以 docstring 必须写，多加的 `k` 也要在其中说清是返回文档数量；不写这个，工具等于白做。

    * `chunks` 一开始在编辑器里点不出属性，是因为 `retrieve` 没标返回类型；补上「装 `ParentChunk` 的列表」之后，`chunk.content`、`chunk.section_path` 就有补全提示了。

* **挂到 agent 上才算生效**

    * 在 agent 里导入新工具并放进工具列表；光放进去不够，系统提示词还要把话说死：用户询问保险条款问题时，必须调用工具查询条款并据此回答，不能自己编造。

    * > **提示**：工具列表决定「能调用什么」，系统提示词决定「什么时候必须调用」；只给工具不写约束，模型很可能凭训练记忆直接作答。

    * 实测：先聊「我要买保险 → 给自己买 → 预算 2 万 → 帮我推荐」，模型推荐了几款含达尔文 12 号；接着问「达尔文的等待期是多久」，它先说「让我帮你查一下条款」，再答等待期 180 天。

    * 核对条款文档，达尔文 12 号是重疾险、等待期确实是 180 天，说明是检索到的而不是编的。

    * 日志级别调成 debug 可看到完整调用链：先历史消息，再 `query_candidate_products` 查候选，再到本轮决定调用 `retrieve_insurance_clause`。

    * 参数：`query` 是重写后的关键词而非原句，`k` 是模型自定的 5，`product_id` 是 2（它从聊天记忆里找到「达尔文」再对上达尔文 12 号的 id）；返回的 `section_path` 是 `2.3.1`，正是等待期那一节。

    * 换产品再问「尊享一生的等待期是多久」，模型自动匹配产品后回答：条款中多次提到等待期，但没有给出具体天数——这个回答本身就是证据，它没有编数字，而是如实说查到的内容里没有。

## RAG 的单例初始化与关闭

* **只建一次，建在包里**

    * pipeline 与 retriever 以后会被反复调用，每调一次就 new 一个显然不行；期望是项目启动时创建一次、之后一直复用。

    * 初始化写在 RAG 包的包初始化模块里，项目启动时执行，项目关闭时释放资源。

    * 包初始化模块除了用 `__all__` 控制导出，也可以写初始化脚本；`__all__` 里列出的名字就是 `from 包 import *` 能拿到的全部。

    * 顺序不能乱：pipeline 与 retriever 都需要 vector store，所以先建 vector store，下面两个组件共享同一个对象、共享一份连接。

    * 这段代码没有定义类也没有定义方法，直接写在模块里，意味着模块一旦被加载就立刻执行，两个组件当场初始化。

    * 改成 `init_rag()` 等到调用再初始化也行，但局部变量函数结束就没了，必须把两个组件返回出来，麻烦一点；这里直接放模块里。

    * > **提示**：模块级初始化的代价是「导入即执行」——导入发生在什么时候，初始化就发生在什么时候；后面接 FastAPI 的 lifespan 时，这个特性既是开关也是必须小心的地方。

    ```python
    # RAG 包的包初始化模块

    # 先建向量模型和 vector store（沿用前面写过的两步）
    vector_store = ...

    # 两个组件共享同一个 vector store
    rag_pipeline = RAGPipeline(vector_store)
    retriever = ParentChunkRetriever(vector_store)


    def close_rag():
        # vector store 本身没有 close，要关的是它内部的 client（也就是 Milvus）
        vector_store.client.close()
        rag_pipeline.close()


    __all__ = ["rag_pipeline", "retriever", "close_rag"]
    ```

* **关闭时谁有资源**

    * `vector_store` 本身没有 `close` 方法，翻 API 才确认；真正能关的是它内部的 `client`，所以写法是 `vector_store.client.close()`。

    * `rag_pipeline` 要关：它内部用到 Milvus，那个客户端有 `close` 方法，调流水线自己的关闭逻辑即可。

    * `retriever` 不用关：它里面除了 vector store 没有别的资源，而那一层连接已经处理过了。

* **挂到 lifespan 上的顺序**

    * 关键是导包位置：模块一导入就执行，所以不能把导入写在 main 文件最外层——那样服务还没启动 RAG 就先建好了，不管用不用得上。

    * 要把导入放进 lifespan 里面：启动执行 lifespan → lifespan 执行导入 → 导入触发初始化，三步串起来，初始化正好落在启动时刻。

    * 启动顺序：RAG 最前（导入写在前）→ 数据库连接初始化 → checkpointer / agent 初始化。

    * 关闭顺序整个反过来：`close_rag()` → 关闭数据库连接 → 关闭 checkpointer。

    * 启动时能看到打印顺序；停止时顺序倒过来，只是 RAG 之后的关闭动作没打日志，想看就在关闭逻辑里加几行日志。

    * > **注意**：关闭顺序不能反。pipeline 和 retriever 都要用数据库，先关数据库时 RAG 可能还在用它，连接已断就会出问题；原则是**被依赖的东西最后关**。

    ```python
    @asynccontextmanager
    async def lifespan(app: FastAPI):
        # 启动：导入 RAG 包，模块级代码执行，pipeline 和 retriever 随之初始化
        from app.rag import close_rag

        # 然后是数据库连接的初始化
        ...

        # 再是 checkpointer、agent 的初始化
        ...

        yield

        # 关闭：先关 RAG，再关数据库，最后关 checkpointer
        close_rag()
        ...
    ```

    ```text
    启动
      导入 RAG 包（初始化 RAG）
            │
            ▼
      数据库连接初始化
            │
            ▼
      checkpointer / agent 初始化

    关闭
      close_rag()
            │
            ▼
      关闭数据库连接
            │
            ▼
      关闭 checkpointer
    ```

## LangGraph 的定位

### 三代形态与矛盾

* **三代 AI 应用**

    * 一次问答就结束：用户问题直接发给模型，模型回答，结束；用户选的东西被拼成一段系统提示词，之后发什么就转给模型。

    * 这类最简单的一次调用也有自己的场景：曾有一款让 AI 扮演女友的哄哄模拟器，情绪初始 20 分，哄得好加分、哄不好扣分，加到 100 赢、扣到 0 输；用户量超过 60 万、调用超过 2000 万次。

    * 短板很清楚：不能调工具、不能访问外部数据、做不了多步骤任务。

* **链式调用**

    * 把工作流变成一条流水线：请求来了先知识检索，检索完调模型，模型调完再调工具，工具回来可能还要再调一次模型。

    * 这是一条线性的路，没有回头路，先干什么后干什么全部由代码提前写死，按固定顺序串成一条链。

    * LangChain 这个名字就是 Large Language Model 加 Chain；早期编程范式是管道式，`query` 交给提前建好的模型，模型出结果再交给结构化输出那一步，再交给下一个环节。

    * 好处是稳定可靠：流程是人写的，跑一万次都不会变。

    * 代价是缺乏自主智能：链上没有任何一处让模型思考「我该干什么」，agentic 能力很弱。

* **智能体**

    * 核心变化是工作流不再由人控制，而由模型控制。

    * 浅层：第一步仍由程序控制，程序把请求交给模型，让模型判断走哪条分支，相当于意图识别加条件分支，已经有智能性。

    * 深层：请求直接扔给模型，由它自己规划先干什么再干什么并逐步执行；Claude Code、Codex 这类工具属于后一种，说一句话剩下的事它自己安排。

    * 自主性最强，可靠性最差：写得不好或模型「智商」不够，执行过程可能完全不是想要的样子。

* **稳定性与自主性的矛盾**

    * 模型对应用的控制越多，自主能力越强、可靠性越低；控制越少，自主性越弱、稳定性越强。

    * > **结论**：LangGraph 的作用是在保持 agent 自主控制程度不变的前提下，把它那一层的稳定性抬上去；智能性由模型本身决定，可靠性由 LangGraph 补。

    * 分寸要拿准：它不是把 agent 变回固定流程，自主控制的程度不变，变的是同一份自主性之下的可靠程度。

    ```text
    自主性   低 ◄────────────────────────────────────────► 高
    可靠性   高 ◄────────────────────────────────────────► 低
             传统代码 / 固定链      意图识别 + 条件分支      完全由模型规划
    ```

| 维度 | 链式应用 | 智能体 |
| :--- | :--- | :--- |
| 流程由谁控制 | 代码，提前写死 | 模型，运行时决定 |
| 稳定性 | 高 | 低 |
| 自主性 | 低 | 高 |

### 图结构与记忆能力

* **LangGraph 提供的三件事**

    * 允许自定义 agent 内部的工作流以及工作流里的每一个节点：需要稳定的节点用传统编程写死，需要自主的节点交给模型；流向由你定，中间一部分可以按模型控制走。

    * 给一整套 harness：agent 等于 model 加 harness，harness 是马鞍、鞍具，也可以理解成一套套索；模型是马，跑得快力气大，没有鞍具骑不上去，记忆、工作流编排等都在这一整套里。

    * 工作流不再是链而是图：有分支、有循环，不是一路向前的线性链，画出来就是一张图，graph 之名由此而来。

* **图的三要素**

    * 节点是写业务流程的地方，工具调用、知识检索、模型调用，真正的活都在节点里干。

    * 边就是线：实线表示固定顺序，虚线表示条件判断（可能走这条也可能走那条），边还可以循环，走一圈再回来。

    * 状态用车间流水线理解：整条工作流是传送带，边是传送带本身，节点是工位上的工人，被反复加工的那份数据就是 state；节点是对数据的加工，边决定数据送到哪个工位。

    * 图里每个方框是一个节点，节点之间的线是边，从 START 一路流到 END、被反复加工的那份数据是 state。

| 要素 | 英文 | 职责 |
| :--- | :--- | :--- |
| 节点 | node | 真正干活的代码，可以是工具调用、知识检索、模型调用 |
| 边 | edge | 连接节点、控制工作流走向的路径 |
| 状态 | state | 整个工作流中流转的数据 |

```text
      ┌────────────────┐
      │     START      │
      └───────┬────────┘
              │ 实线：固定顺序
      ┌───────▼────────┐
      │ 节点：检索     │◄──────┐
      └───────┬────────┘       │
              │ 虚线：判断     │ 边可以循环
      ┌───────▼────────┐       │
      │ 节点：模型     │       │
      └───────┬────────┘       │
              │                │
      ┌───────▼────────┐       │
      │ 节点：工具     │───────┘
      └───────┬────────┘
              │
              ▼
              END
```

* **记忆系统带来的能力**

    * LangGraph 提供记忆系统，也就是 checkpointer；LangChain 里那个 checkpointer 底层就是 LangGraph 实现的。

    * 人机交互在 Claude Code 一类工具里很常见：执行某些任务时停下来问「我要做这件事，你让不让」，就是执行到某节点暂停、等用户确认。

    * > **结论**：模型负责聪明，LangGraph 负责别跑偏；要自主就让模型控制流向，要可靠就把关键节点用代码写死，这两件事在一张图里同时成立。

| 能力 | 实际表现 |
| :--- | :--- |
| 记忆 | 多轮对话的上下文得以保留与传递 |
| 故障恢复 | 程序走到某个节点突然终止，还能从断点位置继续执行 |
| 人机交互 | 执行到某处暂停，等用户批准再往下走 |
| 时间回溯 | 已经执行到 node3，后悔了能退回 node1 |
| 长期记忆 | 除 checkpointer 的短期记忆，还支持长期记忆与上下文传递 |
