# Linux 环境、Docker 容器与项目部署

## 虚拟机环境准备

### VMware 安装

* 安装包分 64 位版与普通旧版：新电脑装最新 64 位版，不支持 64 位的旧电脑装旧版，两者安装过程大同小异。

* 机器上本来就有 VMware 就沿用，不必卸掉重装；只有提供的镜像确实用不了，才考虑卸载后重装。

* 安装位置不建议放 C 盘，避免将来空间不够；也不要把安装目录直接指向上一级目录，应在其下新建一个空目录专门安放。

* > **易错点**：安装路径不能包含中文、空格与特殊字符，像 `D:\develop\vmware` 这样只由盘符、英文与反斜杠组成的路径最稳。

* 安装时提示检测到主机启用了 Hyper-V、虚拟机将通过 Windows 虚拟机监控程序平台启动，属于正常提示，继续下一步即可。

* **VMware 卸载残留**

    * > **定义**：卸载 VMware 后留在注册表里的旧配置，会让新版本安装直接失败。

    * 清理有两种办法：用清理工具做注册表清理，或用专业卸载工具卸载并连同残留一起清掉，后者卸完会提示发现残留痕迹，确认后清理干净并重启，再重装。

* 安装是否真的成功，看虚拟网卡：系统设置的网络与高级网络设置里应出现 `VMnet1` 与 `VMnet8`。

    * 老版本 Windows 走控制面板 → 网络和 Internet → 查看网络状态 → 更改适配器设置，效果相同。

    * 这两张网卡是宿主机与虚拟机通信的通道：虚拟机也是一台电脑，两台电脑要连起来就得靠虚拟网卡，安装完成会自动创建。

* > **结论**：装完看不到 `VMnet1` 与 `VMnet8` 就是安装失败，需要卸载重来，多半是之前没卸干净。

### 镜像导入与虚拟网络

* 一个虚拟机放一个独立目录：解压镜像时选「解压到指定目录」而不是解压到当前文件夹，避免所有文件散在上一层。

    * 已经散开也能救：删掉压缩包，手动新建一个目录，再把散落的文件全部移进去。

    * 这样将来建更多虚拟机时，各镜像目录并列摆放、互不搅在一起。

* 镜像里的 `.vmx` 文件是虚拟机的配置文件，双击即自动加入 VMware；弹出选择应用时选 VMware 打开。

* 虚拟网络编辑器默认不可编辑，提示需要管理员特权时点「更改设置」并确认，相当于临时授予管理员权限。

* 要改的是 `VMnet8`：子网 IP 改成 `192.168.150.0`（第三段必须是 150），下面的 NAT 网关与 DHCP 地址段一并统一到 150 网段。

* > **注意**：这一步所有人都必须改，把地址统一成 150 网段，不然后面虚拟机连不上；改完点两次确定并等待网络重置，再看 `VMnet8` 地址是否已是 150 网段。

### 登录、关机与快照

* 出现登录界面就说明虚拟机启动成功；系统是纯命令行界面，没有图形界面。

* 用户名 `root`、密码 `123321`；输密码时屏幕上不显示任何字符属于正常现象，输完回车即可。

* 鼠标点进虚拟机后光标会消失，晃一下即可移出。

* 关机要点「关机」选项，不要点那两个等号——那等于直接挂起，不是关机。

* **快照（Snapshot）**

    * > **定义**：在某个时刻保存虚拟机完整状态的存档，之后可一键转回该状态。

    * 要在虚拟机干净、还没开始折腾的时候拍，比如命名为「初始化」；将来环境被改坏或太臃肿，选中该快照点「转到」即可还原。

    * 快照要在这台虚拟机干净、还没开始折腾的时候拍，后面才有后悔药可吃；恢复快照会丢失当前状态。

## Linux 系统与目录结构

### 内核、发行版与外壳

* **Linux**

    * > **定义**：一套免费使用、自由传播的操作系统，1991 年 10 月 5 日由林纳斯·托瓦兹发布，源码开放、不收费。

    * 最初的开发动机是对教学所用的操作系统不满意，个人设计后发布到芬兰的 FTP 服务器上供免费下载，不到三年就成为风靡全球、使用最广泛、功能完善且稳定可靠的操作系统。

* **内核（Kernel）**

    * > **定义**：操作系统的核心，由林纳斯·托瓦兹及其团队开发维护，负责与硬件交互，并对外暴露基本的接口与函数库。

    * 只有内核能直接接触 CPU、内存、磁盘、显卡、显示器、网络这些计算机资源；其它程序想操作资源必须经过内核，内核借此做安全校验。

    * 内核只提供基础函数与指令，使用方式复杂，不能靠鼠标操作。

* **发行版（Distribution）**

    * > **定义**：在内核基础上做二次开发，增加与用户交互的图形界面、扩展更方便使用的程序与功能之后的版本。

    * 常见发行版有 Ubuntu、Red Hat、CentOS、Fedora，一般提供图形化界面，可以用鼠标操作。

    * 分工关系：内核管硬件与资源、只暴露复杂接口；发行版管好不好用，把接口包装成人能操作的形式。

* **Shell（壳）**

    * > **定义**：套在内核外面的一层用户交互接口，把内核复杂的指令与函数库包起来，对外提供方便使用的操作界面。

    * 图形界面是壳，命令行同样是壳：每一条命令背后其实都是一个应用程序，命令底层再去调用内核的函数库。

    * 层次自下而上是计算机资源、内核、Shell、应用程序；应用程序装在壳上面，真正碰硬的始终只有内核。

```text
应用程序
   |
Shell（壳，用户交互接口）
   |
内核 Kernel（文件系统、函数库、对外接口）
   |
计算机资源：CPU、内存、磁盘、显卡、显示器、网络
```

### 操作系统版图与 CentOS 的定位

* 按使用场景划分，生产环境里的操作系统分三类。

| 场景 | 常见系统 |
| :--- | :--- |
| 桌面级 | Windows、macOS、Linux |
| 服务器 | UNIX（商业收费）、Linux、Windows Server |
| 移动设备 | Android、iOS、HarmonyOS |

* **CentOS**

    * > **定义**：开源社区基于收费的 Red Hat 编译出来的免费发行版，后来被 Red Hat 官方收购，但仍免费提供。

    * 使用范围很广，既可物理机安装也可虚拟机安装；课程环境用虚拟机，公司里则直接装在服务器物理机上。

    * 只提供两种版本：图形界面版与纯命令行版，学习使用纯命令行版。

### 目录树与根目录分工

* Linux 没有盘符，不存在 C、D、E 盘的概念，整个系统只有一个根目录 `/`，所有文件都在根下面，结构是一棵树。

    * 可以把整个 Linux 看成 Windows 里的一个盘：那个盘也以一个根开始，根下面才是各级目录；区别只是 Linux 只有一个根。

    * 进到某个目录，相当于只保留了 Windows 盘符后面那一截斜杠，前面的盘符不存在。

```text
/
├── bin
├── boot
├── dev
├── etc
├── home
│   ├── user1
│   └── user2
├── lib
├── opt
├── root
├── sbin
├── tmp
├── usr
└── var
```

* 根目录下每个文件夹有固定职责。

| 目录 | 存放的内容 |
| :--- | :--- |
| `/bin` | 二进制可执行文件，bin 是 binary 的缩写 |
| `/boot` | 系统引导、启动时使用的文件 |
| `/dev` | 设备文件 |
| `/etc` | 系统配置文件 |
| `/home` | 普通用户的家目录，每新增一个用户就多一个文件夹 |
| `/lib` | 程序运行所需的共享库与内核模块，相当于系统依赖 |
| `/opt` | 一些可选的应用程序 |
| `/root` | 系统超级用户 root 的目录 |
| `/sbin` | 可执行文件，但只有 root 用户能访问，相当于系统级应用 |
| `/tmp` | 临时文件 |
| `/usr` | 系统应用程序，用户自己装的程序一般放这里 |
| `/var` | 系统运行过程中的临时数据，比如日志 |

* **pwd**

    * > **定义**：显示当前所在目录的命令。

    * 用户登录后默认进入自己的家目录，用 root 登录就落在 `/root`，执行 `pwd` 输出 `/root` 即说明位置正确。

    * > **易错点**：`/home` 放的是普通用户的家目录，超级用户 root 的家目录是 `/root`，不在 `/home` 下面，两者不要混。

## 命令行的组成与操作习惯

### 命令的三个组成部分

* 一条命令由命令名、可选项、参数三段构成，读法是「叫什么、怎么调、对谁下手」。

```text
 command      option      parameter
---------    --------    ------------------
 命令名       可选项       命令作用的对象
 rm           -f          要删除的文件名
```

* 三段中命令名永远必须有，选项与参数都可以为零个；参数可以是一个或多个。

* **option（可选项）**

    * 长格式通常带两个杠，如 `--help`；短格式通常是缩写，如 `-h`。

    * 短格式不一定与长格式形似，例如 `ls` 的 `-b` 对应 `--escape`，所以不能凭字母猜含义，必须查帮助。

* **parameter（参数）**

    * 命令作用的对象，可以是零个、一个或多个。

    * 例：`rm -f 文件名` 中 `rm` 是 remove 的缩写表示删除，`-f` 是选项，文件名是参数。

* 命令本身也是应用程序，可执行文件放在 `/etc`、`/run`、`/usr/bin` 这类系统目录里，不是玄学符号。

### 帮助、补全与终端操作

* **`--help`**

    * 任何命令后跟 `--help` 会打印它自己的用法：能做什么、后面接什么、有哪些选项可挑。

    * `rm --help` 开头就写明 remove 与用法 `rm [选项] 文件`；`-f` 的长格式为 `--force`，含义是忽略不存在的文件与参数、删除前不提示。

    * > **提示**：`-h` 只是 `--help` 常见的缩写，并非一定等价；`-h` 不生效时老老实实敲 `--help`。

* **Tab 补全**

    * 前缀在当前目录下唯一时，按一次 Tab 把文件名或路径一次补齐。

    * 连按两次 Tab 会列出所有以该前缀开头的候选，命令名与路径都能这样问。

* 上下箭头在历史命令队列里上下翻，翻到即可回车重跑，不必重敲。

* `clear` 或 `Ctrl+L` 清空屏幕。

* > **易错点**：命令与参数严格区分大小写，`-a` 与 `-A`、`-b` 与 `-B` 都是含义不同的两个选项。

## 目录与文件操作

### 目录查看与切换

* **ls**

    * > **定义**：展示指定目录下的内容，不传目录就查当前目录。

    * `-a` 显示所有文件，包括以点开头的隐藏文件；`-l` 除文件名外还列出文件类型、权限、拥有者、大小等详细信息。

    * 多个选项可以合并写，`-al` 等价于 `-a -l`。

* `ls -l` 的输出一行为一个条目，各字段含义如下。

| 在行内的位置 | 内容 | 怎么看 |
| :--- | :--- | :--- |
| 行首第一个字符 | 文件类型 | `d` 表示目录，不是 `d` 就是文件 |
| 紧随其后那一串 | 权限 | 形如 `rwxrwxrwx`，r 读、w 写、x 执行 |
| 中间某个字段 | 计数字段 | 暂不关心 |
| 再往后 | 所属用户与组 | 哪个用户创建、该用户在哪个组 |
| 再往后 | 大小 | 文件大小 |
| 再往后 | 时间 | 文件创建时间 |
| 行尾 | 文件名 | 条目名称 |

* 权限串重复三遍，是按「当前用户、当前用户所在组、其他组用户」分成的三组权限。

* **ll**

    * > **定义**：`ls -l` 的快捷方式，敲 `ll` 与 `ls -l` 效果完全一样，后面也能继续加 `-a`。

* **`.` 与 `..`**

    * 一个点代表当前目录，两个点代表上级目录；`ll -a .` 等于什么都不写，`ll -a ..` 查的是上一级。

    * 路径写法有方向之分：`/root` 从根目录开始找 root；只写 `root` 则在当前目录下找。

* **cd**

    * > **定义**：切换当前所在目录。

    * `cd /usr/local` 可以连着写多级；`cd ~` 回当前用户的家目录，注意 `cd` 与 `~` 之间有空格。

    * `cd -` 回到上一次所在的目录，适合在两个目录之间来回跳；`cd ..` 回上一级。

* > **易错点**：目录名前不要随手加斜杠，`ll /a` 查的是根目录下的 a，当前目录下的 a 要写 `ll a` 或 `ll ./a`；`-A` 是选项，`ll -A` 不是查看名为 A 的目录。

### 目录创建与删除

* **mkdir**

    * > **定义**：make directory，创建一个目录。

    * `-p` 表示确保目录名称存在、不存在就创建，可一次创建多层：`mkdir a/b/c` 会因父目录不存在报错，`mkdir -p a/b/c` 三层全部建出。

* **rm**

    * > **定义**：remove，删除文件或目录。

    * `-f` 是无需确认直接删除；`-r` 是递归删除，目录及其中的文件逐一删除。

    * 不加 `-f` 时删除会先询问，输入 `N` 即放弃；`-f` 干的事就是把这道保护关掉。

    * 目录不能直接 `rm`，因为目录里可能还有别的东西，必须加 `-r`；`rm -rf hello` 会把目录连内容一起端掉。

    * `rm -rf *` 删除当前目录下所有东西（`*` 代表所有），`rm -rf /` 会删掉根目录下一切，能把操作系统直接干掉。

* **cp**

    * > **定义**：copy，复制文件或目录，原件保留。

    * 格式为 `cp 源 目标`；复制目录且目录里有东西时必须加 `-r`。

    * 目标是目录时原名复制过去；目标是「目录/新名字」时复制并改名；目标是当前目录下的文件名时复制到当前目录并改名。

    * `cp -r a b` 把目录 a 复制为 b，里面的文件一并复制，这就是递归复制。

* **mv**

    * > **定义**：move，移动即剪切，原件不再留在原处。

    * 移动目录不需要加任何参数；`mv test.log test1.log` 位置不动只改名，等于重命名。

    * `mv a dira` 把目录 a 改名为 dira；`mv b dira` 把整个 b 目录扔进 dira 里面。

| 对比项 | cp | mv |
| :--- | :--- | :--- |
| 本质 | 复制一份，原件保留 | 剪切，原件不再留在原处 |
| 复制/移动目录 | 必须加 `-r` | 不用加任何参数 |
| 顺手改名 | 目标写成「目录/新名字」 | 直接写新名字即可 |

### 文件内容查看

* **cat**

    * > **定义**：把文件内容整体打印到终端。

    * `cat -n 文件名` 加 `-n` 会在每行前输出行号，不加则不输出。

* **more 与 less**

    * `more 文件名` 一屏一屏查看，底部显示当前进度百分比，如 `more 41%`。

    * `less` 与 `more` 效果很像，同样是一屏一屏查看，用法类似。

    * `more` 的按键约定如下。

| 按键 | 动作 |
| :--- | :--- |
| 回车 | 向下滚动一行 |
| 空格 | 向下滚动一屏 |
| B | 向上返回一屏 |
| Q 或 Ctrl+C | 退出 |

* **head**

    * `head -n 文件名` 只看开头 n 行，`head -5` 显示前五行，空行也算一行。

    * > **易错点**：`cat -n` 的 n 是「输出行号」的开关，`head -n` 的 n 是「几行」的占位，两个 n 不是一回事。

* **tail**

    * `tail -n 文件名` 查看文件尾部 n 行；某行内容太长在终端折行，看起来会超过 n 行，实际仍是 n 行。

    * `-f` 是 follow，命令不会结束，一直盯着文件尾部；日志里新增一行就立刻输出一行。

    * 这种用法叫日志跟踪，程序不停往日志追加内容，`tail -f` 就持续把新行刷到终端，方便调试。

    * 退出用 `Ctrl+C`：在 Linux 里它不是复制，而是终止当前运行。

```text
程序运行 ──写入──▶ error.log（不断变长）
                        │
                        └── tail -f 一直盯着文件尾部 ──▶ 终端实时显示新行
```

## 文本编辑与内容检索

### vi 的三种模式

* **vi 与 vim**

    * `vi` 是系统默认自带的文本编辑器，`vim` 是它的增强版，用法基本一致。

    * `vim` 需自己装（`yum install vim`），比 `vi` 多的主要就是语法高亮，其余操作完全相同。

* 三种模式：命令模式、插入模式（也称编辑模式）、底行模式。

    * 插入模式是唯一能真正写字的状态；命令模式负责下快捷键指令，底行模式负责下保存、退出这类长命令。

    * 一打开文件默认进入命令模式，此时可看内容、移光标、删东西，但一般改不了字，按键也不会显示在屏幕上。

    * 进插入与进底行都只能从命令模式出发，两者按 `Esc` 都回命令模式，所以命令模式是枢纽；迷路时连按两下 `Esc` 一定回到命令模式。

```text
              按 i / a / o
   命令模式 ─────────────────→ 插入模式
      ↑  ←─────────────────
      │       按 Esc
      │
      │ 按 : 或 /
      ↓
   底行模式 ───── 按 Esc ────→ 命令模式
```

### 命令模式与底行模式的操作

* 命令模式常用按键。

| 按键 | 作用 |
| :--- | :--- |
| `gg` | 跳到第一行 |
| `G` | 跳到最后一行（Shift + g） |
| `dd` | 删除光标所在行 |
| `3dd` | 从当前行起删掉 3 行 |
| `u` | 撤销 |

* `i`、`a`、`o` 三个键都从命令模式进插入模式，差别只在落点：`i` 原地插入、`a` 在光标后追加、`o` 另起一行往下写；记住 `i` 即可干活。

* 底行模式用 `:` 或 `/` 从命令模式进入，屏幕最底下开出命令输入区。

| 命令 | 作用 |
| :--- | :--- |
| `:q` | 退出 |
| `:q!` | 强制退出，不保存 |
| `:wq` | 保存并退出 |
| `:set nu` | 显示行号 |

* 文件被修改过时 `:q` 不让退出，只有 `:wq` 保存走人或 `:q!` 强制丢弃两条路。

* 完整流程：`vi hello.py`（文件不存在时先打开空缓冲区，保存才落盘）→ 按 `i` 看到 `-- INSERT --` → 写入内容 → 按 `Esc` → `:` 输入 `wq` 回车。

* 边界：日常开发有图形工具时双击就能改，`vi` 真正的用武之地是服务器——只有 SSH 连过去的一个终端、没有图形界面，此时会 `vi` 就能救急，把它当保底技能而非日常主力。

### find 与 grep

* **find**

    * > **定义**：在磁盘上按名字查找文件，格式为「先目录、后条件」：`find [在哪个目录找] -name [找什么名字]`。

    * `find . -name "*.log"` 从当前目录递归往下找，子目录里的 log 也会被翻出来，这是它比 `ls` 强的地方。

    * 全盘查找把目录换成 `/`：`find / -name "*.log"`，但整盘扫描很慢，没必要别这么干。

    * 长选项只有一个杠（`-name`），不遵守普通命令两个杠的惯例，不要以为少打了一个。

* **grep**

    * > **定义**：在文件内容里按关键词筛选行，格式为 `grep [要找的词] [在哪个文件里找]`。

    * 记忆口径：find 找文件，grep 找行。

    * 常用参数如下。

| 参数 | 作用 |
| :--- | :--- |
| `-i` | 忽略大小写 |
| `-n` | 显示行号 |
| `-A N` | 命中行之后再多显示 N 行 |
| `-B N` | 命中行之前再多显示 N 行 |

* > **易错点**：`find` 的通配符必须加引号，不加引号 shell 会先按当前目录展开 `*.log`，传给 find 时已变成具体文件名列表，匹配范围就错了。

* > **易错点**：`grep` 的上下文参数要把数字写在字母后面并分开写，`-A 5 -B 5` 有效，`5A5B` 或 `-A5B5` 都不认。

### 管道

* **管道（pipe）**

    * > **定义**：用一条竖线把前一个命令的输出，直接当成后一个命令的输入。

    * 写法就是 `命令一 | 命令二` 一条竖线。

    * `ls --help | grep 隐藏` 把帮助文档交给 grep 筛选，整屏参数里只留下含「隐藏」的那一条。

    * 方向不能记反：左边负责生产输出，右边负责消费输入。

```text
ls --help
   │
   │ stdout：一整篇帮助文档
   ▼
grep 隐藏
   │
   │ 只留下包含「隐藏」的行
   ▼
-a, --all   不隐藏任何以 . 开始的项目
```

* 管道的价值在「先全量、再筛选」：凡是输出太长看不清的命令，后面都可以接一个 `grep`。

* 查进程是典型用法：`ps -ef` 列出系统所有进程，`ps -ef | grep mysql` 只筛出 mysql 相关的一款，`ps -ef | grep python` 同理，可用来确认自己写的服务有没有起来。

## 打包压缩与软件环境

### tar 的五个选项

* `tar` 一个命令同时承担打包、解包、压缩、解压四件事，靠选项决定这一次干哪件。

```bash
tar [选项] [包文件名] [要打包的文件...]
```

* 打包时第一个文件名是产物名，后面跟要打包的对象列表；解包时只给要解的包文件名，不再给文件列表。

| 选项 | 全称 | 作用 | 是否必给 |
| :--- | :--- | :--- | :--- |
| `-z` | gzip | 调用 gzip 压缩或解压 | 可选，要压缩才加 |
| `-c` | create | 创建包，即打包或打包压缩 | 与 `-x` 二选一 |
| `-x` | extract | 解包或解压 | 与 `-c` 二选一 |
| `-v` | verbose | 显示处理过程 | 可选 |
| `-f` | file | 指定包文件名 | 必给 |

* `-c` 不是 compress 而是 create，管的是「创建一个包」，压不压缩与它无关；`-z` 才是「要不要压」的开关，`-c`/`-x` 是方向，`-v` 是说不说话，`-f` 是包叫什么。

* 命名约定：`.tar` 表示只打包，`.tar.gz` 表示打包并压缩；后缀不参与解包逻辑，tar 认的是 `-z`，但人和脚本靠后缀判断。

* > **易错点**：`-c` 与 `-x` 只能出现一个；`-z` 在压缩与解压时要成对出现，压的时候加了，解的时候也必须加，否则 tar 不知道这是 gzip 包。

### tar 的四个常用组合

* `tar -cvf a.tar DIRA` 只打包不压缩，`-v` 会逐行列出行囊内容。

* `tar -czvf a.tar.gz DIRA` 打包并 gzip 压缩，同一目录体积从约 2.8 MB 降到约 110 KB，相差二十多倍。

* `tar -xvf a.tar` 解包，`tar -xzvf a.tar.gz` 解压，两种都能把原目录与内部文件完整还原。

* > **提示**：选项习惯写成 `-czvf`，把 `-f` 放最后，因为它后面紧跟的就是包文件名；写成 `-c -z -v -f` 也等价。

### 软件安装的三条路径

* 三条路区别在「谁替你编译」：自己编译、装别人打好的包、从软件源在线装。

| 方式 | 做法 | 特点 |
| :--- | :--- | :--- |
| 源码编译（二进制包） | 下源码或二进制包，配置、编译、安装 | 灵活但麻烦，依赖要自己补，现在少用 |
| `rpm` | 安装别人打好的 `.rpm` 包 | 简单直接，但依赖要手动解决 |
| `yum` | 从软件源在线安装 | 自动处理依赖，最常用 |

* `rpm` 全称 Red Hat Package Manager，红帽的软件包管理器，因此 `rpm` 与 `yum` 只在红帽系发行版上有效。

| 发行版 | 定位 |
| :--- | :--- |
| Fedora | 先行版，新功能先上，比较激进 |
| CentOS | 开源免费版，基于红帽，功能有删减 |
| Red Hat Enterprise Linux | 稳定企业版 |

* 换发行版就换包管理器：红帽系用 `yum`，Debian 系（Ubuntu）用 `apt`，两条完全不同的线。

### yum 换源与 uv 安装

* `yum` 装包要从软件源下载，默认源指向国外，国内直连常见结果是连不上或极慢。

* 换源三步：备份本地源配置文件 → 下载阿里云源文件替换 → 清缓存并重建缓存。

```bash
yum clean all
yum makecache
```

* `clean all` 清空本地软件包索引，`makecache` 按新源重新拉一份；不 clean 直接 makecache 会让旧索引混在里面，容易出莫名其妙的错。

* > **注意**：换源前一定先备份，源文件改错会让 yum 彻底不能用，有备份才能一条命令退回去。

* Mac 上跑 Linux 要按 CPU 架构选源：Intel 芯片是 x86_64，可直接用现成 x86 镜像；M 系列芯片是 ARM，必须换 ARM 版镜像源，阿里云与华为都提供，用错架构会在装包时报架构不匹配。

* **uv** 在 Linux 上一条命令安装，官网 macOS 与 Linux 共用同一套。

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

* 这行命令拆成三段：`curl` 把安装脚本下载下来，管道把脚本内容交给后面的命令，`sh` 负责执行脚本；装的不是安装包而是一段安装程序。

* 跑完提示 `Everything is installed`，`uv` 与 `uvx` 两个命令都装好，`uv --version` 能打出号即成功。

* > **提示**：`curl ... | sh` 等于「下载一段代码并立刻执行」，前提是来源可信；官网复制的可以用，来路不明的脚本不要灌进 `sh`。

### 服务管理与防火墙

* **systemctl**

    * > **定义**：管理 Linux 服务（开机自启的后台程序）的统一命令，格式为 `systemctl [动作] [服务名]`。

    * 好处是通用：今天管 MySQL、明天管别的服务，只换服务名，动作一个字都不用改。

    * 服务名是 `mysqld` 而不是 `mysql`：`mysql` 是客户端命令，`mysqld` 才是后台跑的服务进程；状态显示 `running` 为运行中，`inactive (dead)` 为已停止。

    * 六个动作覆盖服务的全部日常操作。

| 动作 | 含义 |
| :--- | :--- |
| `start` | 启动服务 |
| `stop` | 停止服务 |
| `status` | 查看服务状态 |
| `restart` | 重启服务 |
| `enable` | 设为开机自启 |
| `disable` | 取消开机自启 |


* > **注意**：`stop` 与 `disable` 是两件事，`stop` 只停这一次、下次开机照样起来，`disable` 取消开机自启但当前进程不会停；要彻底关掉得两条都执行。

* **firewalld**

    * > **定义**：Linux 默认开启的防火墙服务，会把进入的请求全部拦下，除非明确放行某个端口。

    * 放行 MySQL 的 3306 端口要用三条命令，先加规则、再重载、最后确认。

    * `--zone=public` 指定作用区域，`--add-port` 指定端口与协议，`--permanent` 写进永久配置；不加 `--permanent` 只对当前生效，防火墙一重启规则就没了。

    * 列表里出现 `3306/tcp` 说明放行成功；规则刚加完必须 `--reload` 才载入。

```bash
firewall-cmd --zone=public --add-port=3306/tcp --permanent
firewall-cmd --reload
firewall-cmd --list-ports
```


* 本地虚拟机可图省事整个关掉：`systemctl stop firewalld` 加 `systemctl disable firewalld`，两条都执行才彻底不挡路。

* > **注意**：关防火墙只适用于自己的本地虚拟机；云服务器、公司服务器必须按端口放行，云主机还要在安全组里单独放行，两层都配对才通，直接关等于把机器裸奔在公网上。

* 用客户端连本机是 `mysql -u root -p`：`-u` 指定用户、`-p` 表示要输密码；初始密码是 `MySQL1234`，登进去后本机密码与远程密码是两套，只改本地远程照样连不上；改完执行 `flush privileges;` 让改动立刻生效。

## 前后端分离与 Nginx 部署

### 静态资源与动态数据

* **Nginx**

    * > **定义**：一个轻量级的 Web 服务器，作用有两个——部署前端静态资源、对请求做反向代理。

    * 这两个作用正好对应一个页面里的两类内容：静态资源它自己就地返回，动态数据它转给后端取回。

* 浏览器渲染出的页面分两部分：一部分是静态资源，即页面样式；另一部分是动态数据，即下拉框内容、列表条目。

| 对比项 | 静态资源 | 动态数据 |
| :--- | :--- | :--- |
| 具体内容 | HTML、CSS、JS、图片 | 列表、预设、会话历史等业务数据 |
| 由谁提供 | 前端服务器 Nginx | 后端服务器 |
| 写页面时是否确定 | 确定，就是磁盘上的文件 | 不确定，请求回来才知道 |
| 存放位置 | Nginx 的 html 目录 | 数据库，由后端查询后返回 |

* 落地的部署形态是两台「服务器」：一台专门放前端，就是 Nginx；一台专门跑后端项目，监听 8000 端口。这种部署方式叫前后端分离。

* > **结论**：前端展示样式，后端展示数据；静态资源放前端服务器，动态数据由后端服务器查库返回。

```text
浏览器
  │
  │ ① 请求 index.html、app.js、*.css、图片
  ▼
Nginx（前端服务器，192.168.150.101:80）
  │  这些文件就在磁盘的 html 目录里 → 直接返回，页面渲染出样式
  │
  │ ② 页面渲染完成后，前端再请求 /api/preset-process、/api/session
  ▼
Nginx 判断：不是静态资源 → 反向代理
  │
  ▼
后端服务（8000 端口）
  │  查数据库、组织数据
  ▼
结果原路返回：后端 → Nginx → 浏览器
```

### Nginx 的编译安装

* 安装分三步：`configure` 配置、`make` 编译、`make install` 安装，一步都不能省。

```bash
tar -zxvf nginx-1.20.2.tar.gz
cd nginx-1.20.2
./configure --prefix=/usr/local/nginx
make
make install
```

* `configure --prefix=/usr/local/nginx` 决定编译好之后装到哪个目录；`configure` 只是配置，还不算编译。

* 装完源码目录就没用了，程序已经落到 `/usr/local/nginx`，源码留着白占空间。

* 装好的 Nginx 只有四个目录，各管一摊。

| 目录 | 放什么 | 什么时候用到它 |
| :--- | :--- | :--- |
| `conf` | 配置文件，包括 `nginx.conf` | 改端口、改站点配置 |
| `html` | 前端静态资源 | 部署页面、图片 |
| `logs` | 日志 | 排查访问和报错 |
| `sbin` | 可执行文件 | 启动、停止服务 |

### 端口、location 与静态资源

* 启动就是进到安装目录敲 `sbin/nginx`，回车后没有输出属于正常——它是后台服务，不占终端。

* `ps -ef | grep nginx` 能看到 `master` 主进程与 `worker` 工作进程，两个都在跑说明服务已起。

* 端口写在 `conf/nginx.conf` 的 `server` 段里，关键一句是 `listen 80`。

```nginx
server {
    listen 80;
    location / {
        root   html;
        index  index.html;
    }
}
```

* `location /` 类似后端框架里的根路由，处理斜杠这个路径；`root html` 中的相对路径以 Nginx 安装目录为基准，合起来就是 `/usr/local/nginx/html`；`index index.html` 指定首页文件。

* > **提示**：HTTP 默认端口是 80，HTTPS 默认端口是 443；访问时不写端口就走默认那一个，浏览器会把 80 藏掉。

* 改 `html/index.html` 页面内容就跟着变，说明 Nginx 返回的就是这个文件本身；往 `html` 里扔图片，访问 `地址/图片名.jpg` 就能打开。

* > **结论**：部署静态资源不需要改任何配置，把文件放进 `/usr/local/nginx/html` 就算部署完成。

* 中文乱码的原因是页面没声明编码：响应头要带 `Content-Type: text/html; charset=UTF-8` 之类的信息浏览器才知道怎么解析，页面头部补上 `<meta charset="UTF-8" />` 即正常。

* 停止服务用 `sbin/nginx -s stop`。

### 后端部署与 systemd 托管

* 后端部署四步：上传项目 → 改配置 → 装依赖 → 启动。

    * 配置只改三样：模型的 API Key 换成自己的、数据库地址与端口、数据库密码；模型名保持原样。

    * 数据库与项目在同一台机器上时，地址写 `localhost` 就能连到，不用改。

    * uv 项目根目录有 `pyproject.toml`，拿到新项目第一件事就是 `uv sync`，等价于前端项目先执行 `npm install`。

    * 启动用 `uv run`，端口 8000；报 `Unknown database 'robot'` 不是连不上库，而是库还没建，执行 `CREATE DATABASE robot;` 再启动即可。

* > **易错点**：后端目录里的 `.env` 以点开头、默认隐藏，不打开「显示隐藏文件」根本看不见，容易误以为没上传成功。

* **前台运行**

    * > **定义**：命令占着终端不放、终端一断服务就死的运行方式。

    * 想后台常驻，要在 `/etc/systemd/system` 下新建一个 `.service` 文件，把项目注册成系统服务。

    * 编辑时先按 `i` 进插入模式、看到 INSERT 再粘贴，粘完 `Esc` 后 `:wq` 保存；不在插入模式直接粘会贴得乱七八糟。

* 服务文件里写的是项目的绝对路径，路径与实际位置不一致就会启动失败，要么把目录搬过去，要么一开始就传到对应位置。

```bash
systemctl daemon-reload
chmod +x /etc/systemd/system/robot-api.service
```

* 之后就能像管 MySQL 一样管它：`systemctl start robot-api`、`status`、`stop`、`enable`，状态从 dead 变 running 即启动成功。

## Docker 镜像与容器

### 镜像与安装包

* **Docker**

    * > **定义**：安装在本地的一个后台服务，通过命令操作，最重要的作用是搭建项目环境与做部署。

    * 装好后 `systemctl status docker` 可看运行状态；用法类似 MySQL，服务先跑起来，再用命令去用它。

* 传统安装的四个绕不过去的问题：安装包不好找、要按系统版本挑包、下载后要解压并执行一堆命令、命令太多记不住且步骤易错。

* Docker 自身的安装同样要用包管理器，流程是先卸旧版、再装新版，还要设软件源、设开机启动、配镜像加速，整体比较繁琐。

* **镜像（Image）**

    * > **定义**：应用本身加上它运行所需的全部条件——环境配置、系统级函数库、甚至一个模拟出来的操作系统环境——打包成的一整套可独立运行的东西。

    * 镜像不依赖外部环境，所以同一条 `docker run` 在 Windows、Linux、Mac 上一个字都不用改。

    * 镜像与安装包的区别：安装包只给零件，装到哪台机器还得看那台机器有没有配套；镜像给的是零件齐全、水电都接好的车间，搬到哪都能直接开工。

* `docker run` 一条命令等于把「找包、下载、装好、启动」四步串成一步，它内部先做一次 pull 再 run，所以不需要事先下载镜像。

* 第一次运行会打印 `Unable to find image 'mysql:latest' locally` 与 `latest: Pulling from library/mysql`，说明本地没有、开始远程拉取。

### 容器与隔离

* **容器（Container）**

    * > **定义**：把镜像丢进一个与外界隔离的环境里启动，这个独立、隔离的运行环境就叫容器。

    * 它模拟的是一个操作系统环境，像虚拟机但不是虚拟机，比虚拟机轻量得多：没有虚拟出整套硬件，只把「有哪些文件、有哪些函数库」这套文件环境模拟出来。

    * 因为隔离，同一份镜像可以同时跑好几份容器，各自跑各自的进程、互不干扰，外界访问谁就走谁自己的端口。

```text
              镜像 mysql:8.0
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
   容器 mysql    容器 mysql2   容器 mysql3
    端口 3307     端口 3308     端口 3309
```

* > **结论**：镜像解决「到哪都能跑」，容器解决「跑几份都不打架」，两层合起来才是完整的隔离。

### 镜像仓库与加速

* **镜像仓库（Registry）**

    * > **定义**：专门提供 Docker 镜像管理与存储服务的服务器。

| 仓库类型 | 例子 | 说明 |
| :--- | :--- | :--- |
| 官方仓库 | Docker Hub | 镜像最全、官方出品，国内直连不顺 |
| 第三方仓库 | 阿里云、华为云、网易、清华源 | 云厂商与高校提供，通常要登录，能加速 |
| 私有仓库 | 公司自建 | 内部镜像不便外传时自己搭一个 |

* Docker Hub 域名是 `hub.docker.com`；镜像一部分由 Docker 官方制作，一部分由软件方自己做，例如 MySQL 官方做好再上传。

* 镜像加速会一次配多个地址（网易、清华、搜狐、阿里、腾讯等），拉取时挨个尝试，一个不行再试下一个，所以总能成功。

### docker run 的执行链路

* Docker 装好后是一个常驻服务，后台进程叫 **docker daemon（守护进程）**，等你敲命令来操作它。

```text
docker run mysql:8.0
        |
        v
docker daemon 收到命令
        |
        |  (1) 先看本地镜像库：有 mysql 吗？
        +---- 有 ------> 跳过拉取
        |
        +---- 没有 ----> 去 registry 拉取，存进本地镜像库
        |
        v
  (2) 用镜像创建容器
        |
        v
  (3) 在隔离环境里启动容器，服务跑起来
```

* 拉取是一次性的：一旦落到本地，下次再 `docker run` 会先查本地，有就不再拉，所以第二次起是秒开。

* > **提示**：一条 `docker run` 下得特别久，先别怀疑命令写错，多半是镜像还没落到本地。

### docker run 的参数

```bash
docker run -d --name mysql -p 3307:3306 \
  -e TZ=Asia/Shanghai \
  -e MYSQL_ROOT_PASSWORD=123 \
  mysql:8.0
```

* `run` 是创建并运行容器，两个动作都在里面；一开始只有镜像，run 过一次才有容器。

* `-d` 让容器在后台运行，命令敲完立刻回你；不加则是前台运行，命令一结束服务也跟着停。

* `--name` 给容器起名，名字可自定义但必须唯一，重复执行同一条命令会报名字重复。

* `-p 3307:3306` 是端口映射，把宿主机的某个端口映射到容器内的某个端口；容器是隔离环境，不映射外界根本访问不到。

```text
MySQL 客户端
     |
     |  连接 192.168.150.101:3307
     v
宿主机（CentOS 虚拟机）的 3307 端口
     |
     |  -p 3307:3306 这条映射规则
     v
容器内部的 3306 端口  --->  MySQL 进程
```

* 宿主机端口写多少自定，只要没被占用；容器内端口不能乱改，MySQL 监听的就是 3306。

* `-e` 是环境变量，格式固定为 `key=value`；`TZ=Asia/Shanghai` 配时区为东八区，`MYSQL_ROOT_PASSWORD` 配 root 密码。

* 镜像名写成 `repository:tag`，冒号前是镜像名、冒号后是版本；不写版本默认按 `latest` 处理。

* > **易错点**：`-p` 冒号左边是宿主机端口、右边是容器内端口，方向只有这一种，写反就连不上。

### 镜像与容器的命令

* 镜像这条线顺着「怎么来、怎么用、怎么走」展开。

| 命令 | 作用 | 重要程度 |
| :--- | :--- | :--- |
| `docker pull 镜像名` | 从仓库拉取镜像到本地 | 一般，`run` 会自动做 |
| `docker images` | 查看本地有哪些镜像 | 常用 |
| `docker rmi 镜像名/镜像ID` | 删除本地镜像 | 常用 |
| `docker build` + Dockerfile | 自己构建一个镜像 | 常用 |
| `docker save` | 把镜像保存成压缩包 | 了解 |
| `docker load` | 加载别人给的镜像压缩包 | 了解 |
| `docker push` | 把镜像推送到远程仓库 | 了解 |

* `save` 与 `load` 多用于局域网内传给同事；想让全世界都能用就 `push` 到官方仓库。

* 容器这条线顺着「创建、看状态、停启、删除、看日志、进入」展开。

| 命令 | 作用 | 重要程度 |
| :--- | :--- | :--- |
| `docker run` | 创建并运行一个容器 | 常用 |
| `docker ps` | 查看运行中的容器 | 常用 |
| `docker ps -a` | 查看所有容器，含已停止的 | 常用 |
| `docker stop 容器名` | 停止容器 | 常用 |
| `docker start 容器名` | 启动一个已停止的容器 | 常用 |
| `docker restart 容器名` | 重启容器 | 常用 |
| `docker rm 容器名` | 删除容器 | 常用 |
| `docker rm -f 容器名` | 强制删除运行中的容器 | 常用 |
| `docker logs 容器名` | 查看容器运行日志 | 常用 |
| `docker exec -it 容器名 bash` | 进入容器内部 | 了解 |

* `ps` 是 process status，`-a` 是 all；`docker images` 各列依次是 repository、tag、image id、创建时间。

* > **易错点**：`rmi` 删的是镜像、`rm` 删的是容器，只差一个字母，作用完全不同。

* > **易错点**：`docker images` 最后一列的时间是镜像被构建出来的时间，不是你把它拉下来的时间。

* 状态列 `Up` 表示运行中、`Exited` 表示已退出；不加 `-a` 只看活着的容器，这是「命令明明执行了却找不到容器」的常见原因。

* `run` 与 `start` 的区别：`run` 创建并运行一个新容器，`start` 只是把已存在但停掉的容器重新提起来；对已有容器再 `run` 一次只会得到名字冲突。

* 运行中的容器不能直接 `rm`，要么先 `stop`，要么加 `-f` 强制删除。

* 同样的命令、同样的参数，换个镜像版本就能跑起来，说明命令没问题、问题在镜像本身；`docker logs` 里那串报错往往就是线索。

* **docker exec**

    * > **定义**：进入容器内部执行命令，格式为 `docker exec -it 容器名 bash`。

    * `-i` 对应 interactive，保持标准输入打开；`-t` 对应 tty，分配一个伪终端；合起来就是给一个终端交互接口。

    * 容器没有图形界面，要跟这台「计算机」交互只能靠终端；提示符前多出的一串容器 ID 说明你已经进到容器内部。

    * 容器内是一套虚拟出来的文件系统，敲 `ls -l` 会看到完整的 Linux 目录结构，但它不是宿主机上的文件系统。

* > **易错点**：容器里看到的目录属于容器，不是宿主机；同样一条 `ls`，在宿主机与容器里看到的不是一回事。

* 退出容器敲 `exit`，提示符前那串容器 ID 消失即回到宿主机。

## 数据卷与目录挂载

### 容器数据的四个麻烦

* 容器一运行就产生日志、临时文件、缓存，全落在容器自己的文件系统里，越积越多，容器越跑越胖；换成 MySQL 这类要建表写数据的服务，几百 G 都是常事。

* 数据存在容器里，容器就动不得：升级版本要下载新镜像、创建新容器、销毁旧容器，旧容器一销毁里面的表跟着没。

* 配置也在容器内部：改配置得先进容器，再费力找配置文件位置，容器里没有图形界面，只剩 `vi` 可用。

* 静态资源塞不进去：Nginx 的 html 目录在容器里，位置不明，复杂前端几百上千个文件，不可能一个个手动写进容器。

* > **结论**：四个问题根子是同一个——容器内的数据与容器绑死。解法只有一个：让运行时产生的数据、运行时需要的配置与容器解耦，容器只提供运行环境。

### 数据卷的机制

* **数据卷（Volume）**

    * > **定义**：一个虚拟目录，不是真实存在的磁盘分区，而是容器内目录与宿主机目录之间映射的一座桥梁。

    * 创建卷时 Docker 服务会在宿主机固定位置建目录：`/var/lib/docker/volumes/` 下与卷同名的目录，里面还有一个 `_data` 子目录。

```text
宿主机文件系统                                容器
/var/lib/docker/volumes/
├── html/_data/        ──── 挂载 ────►   /usr/share/nginx/html
└── config/_data/      ──── 挂载 ────►   /etc/nginx/conf.d
```

* 映射一旦建立，两边就是同一份内容：改宿主机目录，容器内跟着改；容器内产生新数据，同步写回宿主机。

* Nginx 容器里最关键的两个目录是 `/etc/nginx/conf.d`（配置文件）与 `/usr/share/nginx/html`（静态页面），把这两个挂出去，配置与页面就都不用进容器改了。

* 挂载顺带解决升级问题：MySQL 的数据通过映射落到宿主机，删掉容器数据不受影响，换新容器只要还挂同一个卷，照样读到原来的表。

* > **提示**：卷第一次挂到一个本来有内容的容器目录上时，Docker 会把镜像里原有的内容复制进卷；所以挂载后去 `_data` 里看不是空的，而是 Nginx 自带的 `index.html`、`50x.html`。

* 有了卷这一层，容器只认卷名、不认路径：容器不必知道宿主机目录在哪，卷对应哪个路径由 Docker 服务管。换来的是可迁移——容器迁到另一台机器，哪怕那台是 Windows、文件系统完全不同，也照样能跑。

### 数据卷命令与验证

* 数据卷操作都挂在 `docker volume` 子命令下，常用五个。

| 子命令 | 作用 |
| :--- | :--- |
| `create` | 创建一个全新的数据卷 |
| `ls` | 查看所有数据卷 |
| `rm` | 删除指定数据卷 |
| `inspect` | 查看某个数据卷的详情 |
| `prune` | 清除所有未使用的数据卷（数据一起删掉） |

* 记不住参数就 `docker volume --help`。

* > **提示**：常规流程是先建卷再绑容器，但实际不必手动创建；创建容器时用 `-v` 指定一个还不存在的卷，Docker 会在那一刻自动建出来。

* 完整挂载与验证，关键在 `-v`：冒号左边是卷名、右边是容器内目录。

```bash
docker run -d --name nginx -p 80:80 -v html:/usr/share/nginx/html nginx
docker volume ls
docker inspect nginx
docker volume inspect html
```

* `docker inspect` 输出里找 `Mounts` 段：`Type` 是 `volume`、`Name` 是卷名、`Source` 是卷在宿主机上的位置、`Destination` 是容器内对应位置；嫌输出长就直接 `docker volume inspect 卷名`。

* 验证生效的办法：改宿主机 `/var/lib/docker/volumes/html/_data/index.html`，刷新页面内容跟着变，全程没碰过容器。

* **匿名卷（Anonymous Volume）**

    * > **定义**：由镜像自己创建、自己挂载、名字随机生成的卷，因为从没人给它取过名字，所以名字超长。

    * MySQL 镜像自带匿名卷：它清楚数据存在容器里不安全，于是把数据目录挂到卷上，容器删了数据还在宿主机，再起容器关联同一个卷数据就回来。

    * 平时不用匿名卷：名字随机又长，根本没法操作；真要装 MySQL 应手动创建具名卷，或直接挂本地目录。

### 本地目录挂载的判定

* 本地目录挂载写法与数据卷几乎一样：`-v 本地目录:容器内目录`，也可以挂单个文件 `-v 本地文件:容器内文件`。

| 对比项 | 数据卷挂载 | 本地目录挂载 |
| :--- | :--- | :--- |
| 写法 | `-v 卷名:容器目录` | `-v /绝对路径:容器目录` 或 `-v ./相对路径:容器目录` |
| 宿主机上的位置 | 固定在 `/var/lib/docker/volumes/<卷名>/_data` | 自己指定的任意路径 |
| 可迁移性 | 好，容器只认卷名 | 差，容器跟具体路径绑死 |
| 日常操作 | 路径深，得先 inspect 查一遍 | 目录就在手边，方便 |
| 使用场合 | 官方推荐 | 实际开发中用得更多 |

* > **易错点**：本地目录或文件必须以 `/` 或 `./` 开头；以名字开头的一律被识别为数据卷名，而不是本地路径。

```bash
-v mysql:/var/lib/mysql      # mysql 是数据卷名
-v ./mysql:/var/lib/mysql    # 当前目录下的 mysql 目录
```

* 判定只看开头：写成 `-v mysql/xxx:/var/lib/mysql` 挂的仍是卷，只是这个卷名很怪，宿主机上会建出一个名字里带斜杠的目录。

### 三个挂载点部署 MySQL

* MySQL 要挂三个位置，各自职责不同。

| 容器内目录 | 作用 | 挂载的本地目录 |
| :--- | :--- | :--- |
| `/var/lib/mysql` | 数据目录 | `/root/mysql/data` |
| `/docker-entrypoint-initdb.d` | 初始化脚本目录 | `/root/mysql/init` |
| `/etc/mysql/conf.d` | 配置文件目录 | `/root/mysql/config` |

* 数据目录是容器默认写数据的位置，挂出去之后数据落到本地，容器删了也不丢。

* 初始化目录里的脚本会在容器创建后自动执行，提前放好建库建表的 SQL，容器一启动表就齐了。

* > **提示**：`/docker-entrypoint-initdb.d` 里的脚本只在数据目录为空、容器第一次初始化时执行一次；数据目录已有数据不会重复跑，想让脚本重新生效得先清空挂出去的 data 目录。

* 配置目录用来覆盖 MySQL 配置，常见做法是把编码统一成 UTF-8，否则将来会乱码。

```bash
docker run -d \
  --name mysql \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=123456 \
  -v /root/mysql/data:/var/lib/mysql \
  -v /root/mysql/init:/docker-entrypoint-initdb.d \
  -v /root/mysql/config:/etc/mysql/conf.d \
  mysql
```

* 三个 `-v` 冒号前半部分全部以 `/` 开头，所以挂的是本地目录，分别对应上传好的 data、init、config；后半部分是容器内三个目录。

* 验证三件事：`docker ps` 看到容器 Up、本地 data 目录从空变成有内容、客户端连 3306 能看到库与表。

* > **结论**：部署命令本身不是门槛，真正要掌握的是三件事——有哪些东西需要挂出来、分别挂到容器哪个位置、每个位置管什么用。

## 镜像分层与 Dockerfile

### 镜像的分层结构

* 一个 Python 应用要跑起来需要六样东西，构建镜像就是把这六件事按顺序做一遍。

    * 一台 Linux 服务器；

    * 在上面装 Python；

    * 装 UV；

    * 用 UV 把项目依赖装上；

    * 把项目源码拷进去；

    * 写一个启动脚本，用 `uv run` 把服务拉起来。

* 第一层永远是能跑的 Linux 环境，带着系统函数库、环境变量、配置文件，这一层是镜像的地基。

* **基础镜像（Base Image）**

    * > **定义**：专门用来被别的镜像当作起点的镜像，里面是基础的系统函数库、环境变量与配置文件。

    * 这类镜像可以直接从仓库拉取，构建时从它往上叠，不必从零装系统。

```text
基础镜像 base image（Linux 系统函数库 / 环境变量 / 配置文件）
        │
        ├── 安装 Python 与 UV          → 新的一层
        │
        ├── 拷贝项目源码               → 新的一层
        │
        ├── uv 装项目依赖              → 新的一层
        │
        └── ENTRYPOINT 启动脚本        → 入口层
```

* **入口层（Entrypoint）**

    * > **定义**：镜像最上面那层启动脚本，规定镜像启动时先执行什么命令。

    * 一个完整镜像 = 基础镜像层 + 中间若干层 + 入口层。

* 镜像里的文件系统看着完整，其实不是完整的操作系统：只装了应用需要的那部分函数库，用不到的就没有，体积正是这么压下来的。

### 写时复制

* **写时复制（Copy on Write）**

    * > **定义**：每次操作只要修改了文件，就在原层之上新建一层，只把真正被改动的文件复制上来，没碰过的一律链接到下层。

    * 不能在原来那层上直接改：那一层可能全世界都在共用，改了就把别人共用的地基破坏了。

    * 新层里看起来有 `etc`、有 `lib`，其实里面是空的，只用类似软链接的方式指向下面那一层；真要改某个文件时才把它复制上来。

```text
第 2 层（新层）
  /etc   ──链接──▶  第 1 层的 /etc      本层没有实体内容，只是指过去
  /lib   ──链接──▶  第 1 层的 /lib
  /lib/xxx.so        真要改这个文件时，才把它复制到第 2 层再改
```

* 新层里只有被真正改过的东西才占空间，两层合起来看才是完整系统；镜像体积能压住靠的就是这个。

### 分层的目的

* 根本目的是复用：构建时复用已有的层，拉取时复用本地的层。

* 不分层也能用，但层与层之间不可复用：今天打包一个 Python 应用要建前两层，明天打包另一个还得再建一遍，而这两层本来就通用。

* 复用最直观的体现是 `docker pull`：镜像不是一口气整包下载，而是一层一层下，前几层本地已有就直接跳过。

### Dockerfile 指令

* **Dockerfile**

    * > **定义**：用固定语法记录镜像每一层要做什么的描述文件，交给 Docker 服务按描述构建镜像。

    * 构建镜像不是自己动手做层，而是把结构描述清楚，由 Docker 去执行。

* 常用指令。

| 指令 | 作用 | 说明 |
| :--- | :--- | :--- |
| `FROM` | 指定基础镜像 | 管第一层从哪来 |
| `ENV` | 设置环境变量 | 构建与运行时可用 |
| `COPY` | 把本地文件拷进镜像 | 两个参数：源位置、镜像内目标目录 |
| `RUN` | 执行 Linux 命令 | 装依赖等构建期动作 |
| `EXPOSE` | 声明容器端口 | 无实际作用，只给使用者看 |
| `ENTRYPOINT` | 指定入口命令 | 镜像启动时执行 |

* `RUN` 可以串多条命令，用 `&&` 依次执行。

```bash
RUN tar -xvf uv.tar.gz && pip install uv && uv sync
```

* `EXPOSE` 并没有实际意义，它只是告诉镜像使用者容器内部将来占的是哪个端口，别人写 `-p` 时就知道冒号后面该填什么。

* `COPY` 与写时复制配合：要往 `/tmp` 写东西的那一刻，才把 `/tmp` 目录整过来、把源码放进去，加在这一层里。

### 构建示例与构建命令

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv

COPY pyproject.toml ./
RUN uv sync

COPY ./src ./src

EXPOSE 8000

ENTRYPOINT ["uv", "run", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

* `FROM` 不必从操作系统开始：Python 环境太常见，有人把「系统 + Python」提前合并成 `python:3.12-slim`，从它开始等于前两层都省了。

* `WORKDIR` 指定运行时所在目录，目录不存在会自动创建；`COPY --from=...` 拷的不是本地文件，而是从指定镜像地址取，UV 就是这么装进来的。

* 顺序有意为之：先拷 `pyproject.toml` 再 `RUN uv sync`、最后才拷源码，依赖层只跟依赖清单有关，源码怎么改都动不到它，这一层就能一直复用。

* `ENTRYPOINT` 用数组写法把命令逐段拼起来，效果与代码里 `uvicorn.run(app, host=..., port=...)` 相同，只是一个用命令写、一个用代码写。

```bash
docker build -t backend .
```

* `-t` 是 tag，给镜像起名字，格式为 `仓库名:标签`，标签不写默认 `latest`，所以 `-t backend` 等于 `backend:latest`。

* 命令最后那个参数是 Dockerfile 所在的位置，而且必须是目录；`.` 表示当前目录，所以这条命令只能在 Dockerfile 所在目录里跑。

* 构建日志里 `FROM` 对应 stage 0，后面每一段对应新的一层；拉基础镜像慢多半因为连的是国外站点，换国内加速地址速度立刻不同。

### 容器网络的隔离

* 容器虽然跑在同一台虚拟机上，彼此却是隔离的。

* 在 backend 容器里访问 `localhost`，找的是它自己容器内部的服务，而不是同机器上另一个容器里的 MySQL，所以连不上。

* > **易错点**：容器「启动成功」不等于「跑起来了」，进程可能刚起来就挂，`docker ps` 只列还活着的容器；此时要看 `docker logs -f 容器名`。

## Docker Compose 编排

### 项目与服务的概念

* 一个大型项目往往有数十甚至上百个服务，一个一个 `docker run` 部署不现实，还需要手工把网络互联、启动顺序都接起来。

* **Docker Compose**

    * > **定义**：用一个文件定义一组相关联的容器，把文件交给它就能一键全部部署，并顺带完成网络互联。

* **项目（Project）**

    * > **定义**：一整个 Compose 文件所描述的部署单元，对应一个完整项目。

    * 一个项目底层依赖数据库、前端要用 Nginx 部署、中间还有自己的后端，三部分合起来才是一个完整项目。

* **服务（Service）**

    * > **定义**：Compose 项目里的每一个容器，一个容器就是一个服务。

    * 结构上从 `services` 开始，底下依次列各个容器。

### YAML 格式

* Compose 文件用 **YAML** 格式，后缀一般是 `.yml` 或 `.yaml`。

* 基本写法是一个键、一个冒号、一个值，简单内容一行写完。

```yaml
key: value
```

* 复杂内容往下嵌套，层级不靠括号而靠缩进，两个空格一级。

```text
k1:
  k2:
    k3: value
    k4: value
```

* `k3` 与 `k4` 同属 `k2` 底下的并列项；某个深层配置真正的键是把整条路径拼起来；缩进错了层级就全乱。

### docker run 到 service 的映射

* 从命令换成文件，参数还是那批参数，只是换了写法与符号。

| `docker run` 里的写法 | Compose 里的写法 | 作用 |
| :--- | :--- | :--- |
| `--name mysql` | `container_name: mysql` | 容器名 |
| `-p 3306:3306` | `ports:` 下写 `- "3306:3306"` | 宿主机端口映射到容器端口 |
| `-e KEY=VALUE` | `environment:` 下写 `KEY: VALUE` | 环境变量 |
| `-v 本地:容器` | `volumes:` 下写 `- "本地:容器"` | 数据卷挂载 |
| `--network xxx` | `networks:` 下写 `xxx` | 加入网络 |

* `ports` 冒号左边是宿主机端口、右边是容器内端口；`volumes` 冒号左边是本地目录、右边是容器内目录，方向与 `docker run` 完全一致。

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: mysql
    ports:
      - "3306:3306"
    environment:
      MYSQL_ROOT_PASSWORD: 你的密码
      MYSQL_DATABASE: robot
    volumes:
      - mysql-data:/var/lib/mysql
    networks:
      - app-net
```

* `ports`、`environment`、`volumes`、`networks` 底下都有缩进，说明这些配置都属于 `mysql` 这个服务；一个键下要配几项就并列写几行。

### 多服务编排的关键字段

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: chatbot-mysql
    environment:
      MYSQL_ROOT_PASSWORD: 你的密码
      MYSQL_DATABASE: robot
    ports:
      - "3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build: ./backend
    container_name: chatbot-backend
    ports:
      - "8000:8000"
    depends_on:
      mysql:
        condition: service_healthy

  frontend:
    image: nginx
    container_name: chatbot-frontend
    ports:
      - "80:80"
    volumes:
      - ./frontend/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./frontend/public:/usr/share/nginx/html
    depends_on:
      - backend

volumes:
  mysql-data:
```

* **healthcheck**

    * > **定义**：健康检查，隔一段时间去连一次 MySQL 看能不能连通。

    * 不加不影响运行；加了后端才能等数据库「健康」之后再启动。三个参数是间隔 `interval: 10s`、超时 `timeout: 5s`、重试 `retries: 5`。

* **depends_on**

    * > **定义**：声明服务之间的启动依赖，前一个没就绪，后一个不会动。

    * 前端写 `depends_on: backend` 表示后端启动成功才起前端；后端写 `depends_on: mysql` 并配 `condition: service_healthy`，表示 MySQL 健康才放行后端。

* **build**

    * 后端没有现成镜像，需要用自己的 Dockerfile 现构建，所以写 `build: ./backend` 而不是 `image`。

    * 这个字段等价于 `docker build`：告诉它 Dockerfile 在哪个目录，它自己构建、自动创建容器、配好端口与依赖。

* 前端要挂两个卷：`frontend/nginx.conf` 挂到容器内 Nginx 配置目录，`frontend/public` 挂到 HTML 目录当站点根。

* 配置那一行末尾的 `:ro` 代表只读，容器只能读这些文件、不能改。

* 文件末尾的顶层 `volumes: mysql-data` 是对具名卷的声明；`restart: unless-stopped` 表示自动重启、除非主动停掉，虚拟机重启后容器会自己起来，属于可选项。

* Compose 启动时会自动建一个网络，服务之间可以直接用服务名互相访问，所以后端连数据库写 `mysql` 就行，`localhost` 那个坑自然就填了。

### 启动顺序与部署流程

```text
docker compose up -d
        |
        v
  自动创建 network + volume
        |
        v
  [mysql] 容器创建，等待健康检查通过
        |
        v
  [backend] 自动构建镜像 -> 自动创建容器
        |
        v
  [frontend] 创建并启动
        |
        v
  浏览器访问前端 -> 注册 / 登录 / 新建对话
```

* 顺序不是随便排的：backend 一起来就要连数据库，MySQL 没就绪它根本连不上，所以卡在这里。

* 一条 `up -d` 走完：先自动创建 network 与 volume，再按依赖依次创建三个容器；`docker compose ps` 能看到全部启动成功。

* 运行前有一条死规定：必须先 `cd` 到 compose 文件所在目录，`docker compose` 才能找到它。

* 配置用外层的 prod 配置，真正要改的只有 API Key 一样；数据库主机名、端口、用户名、密码一般不动，但密码必须与 compose 文件里的设置保持一致。

* > **提示**：这一阶段最容易出岔子的就是两处对齐——执行命令时人在不在 compose 文件所在目录、数据库密码在 compose 文件与配置文件里是不是同一个值。

* 部署完成的验收方式是走一遍业务：访问前端、注册账号（密码有长度要求）、登录、新建对话、发消息能正常回复。

### compose 命令与清理

| 指令 | 作用 |
| :--- | :--- |
| `up` | 创建并启动所有的 service 容器 |
| `down` | 停止并移除所有的容器 |
| `ps` | 查看已启动的容器 |
| `logs` | 查看日志 |
| `stop` | 停止 |
| `start` | 启动 |
| `restart` | 重启 |

* 用法是 `docker compose` 加指令，选项一般可以不加；动作与 `docker` 那一套很像，区别是操作对象从单个容器变成一组 service。

* > **易错点**：`stop` 只是把容器停下来、容器还在；`down` 是停止并移除，连 up 时自动创建的网络一起清掉。临时停一下用 `stop`，彻底收摊用 `down`。

* `down` 之后 `docker ps -a` 没有容器、`docker network ls` 里网络也不在，运行与清除都是一键，不留痕迹。

* > **结论**：一键部署的成本不在执行，而在那份 compose 文件；文件写对一次，后面每次部署都只剩一行命令。

## 模型账号与本地模型

### 模型平台与配额

* DeepSeek 只有纯文本对话的大语言模型；想要更高级的能力（识图等）就没有了，这类有特殊能力的模型在阿里云上比较多。

* **阿里云百炼**

    * > **定义**：一个模型平台，不是一个模型；通义千问的千问 Max、千问 Plus，以及第三方的 DeepSeek、智谱 GLM、月之暗面 Kimi、MiniMax、小米的模型全都支持。

    * 登录可直接用手机号，也支持支付宝、淘宝账号单点登录；首次使用要做实名认证，用支付宝扫码并人脸识别。

    * 首次注册会自动赠送每个模型 100 万 token 使用权；免费额度在「模型」下的「用量和费用」里查看，一个用完换下一个。

    * 千问 3.8 是阿里现在的旗舰模型，免费额度列表里可能一眼看不到，搜一下也有 100 万 token。

### API Key 与三处配置

* **API Key**

    * > **定义**：调用模型平台接口的凭证，创建后仅在创建的那一刻显示一次。

    * 新建的 Key 关掉对话框就再也取不回来，平台自己也不保存；所以创建完第一件事是把 Key 与配套地址复制存档，而不是先回去改代码。

    * 创建时顺手打开「用完即停」，避免额度被持续消耗。

    * 每个人的 base URL 路径都不一样，记住自己的地址与自己的 Key。

* 切换模型平台本质只动三样东西：API Key、base URL、模型名。

* 403 的排查路径很固定：Key 改了、地址改了，模型名没改——模型名被直接拼在请求代码里且写死，换平台就会以 403 找上门。

* > **结论**：换平台只动 API Key、base URL、模型名这三处；模型名要作为配置项（如 `chat_model`）从 settings 读取，任何一处还写死在代码里，都会以 403 这类错误找上门。

### Ollama

* **Ollama**

    * > **定义**：专门用来在本地部署模型的软件，官网口号是搭建本地模型最简单的方式。

    * 类比 Docker：它本身就是一个服务，Docker 用来部署应用，Ollama 用来部署模型；支持 Windows、Linux、Mac。

    * 装完自带聊天窗口，但要用得先有本地模型；设置里值得改的三项是自动下载更新、是否允许外部访问、模型存放地址（默认在 C 盘）。

* > **提示**：模型文件动辄几个 G，默认落在 C 盘很快会把系统盘塞满；装完先改存放路径，再下载模型，顺序别反。

| 指令 | 作用 |
| :--- | :--- |
| `ollama pull` | 拉取一个模型到本地 |
| `ollama push` | 推送一个模型到远端仓库 |
| `ollama list` | 查看本地模型 |
| `ollama run` | 运行模型 |
| `ollama ps` | 查看运行中的模型 |
| `ollama stop` | 停止一个模型 |
| `ollama rm` | 删除模型 |

* 命令几乎与 Docker 一模一样；`ollama pull` 本地已有就不会重复拉，与 Docker 拉镜像是同一个玩法。

* 模型名不要手写，去模型页面上复制，少打错字。

* 企业里做专业部署会用 vLLM，但它只支持 Linux 系统、配置也较复杂，入门阶段用 Ollama 就够。

### 参数量与显存

* 模型名后面的 **B** 是 billion，十亿，表示参数规模；参数规模越大模型越强，占用的显存也越高。

* 同一个模型往往支持多种尺寸，如 0.8B、2B、4B、9B、27B、35B、122B。

* 122B 就是 1200 亿参数，要占 80 多 G 显存；显存是显卡上的存储，不是内存。

* 国内最强模型之一 Kimi K3 参数规模到 3 万亿，单位是 trillion，比 billion 又高一个数量级（3000 billion）。

* 显卡决定能跑多大：12G 显存加 18G 共享显存，合起来约 29G，只能部署 27B、9B 这一档；没有独立显卡就 0.8B 玩一玩。
