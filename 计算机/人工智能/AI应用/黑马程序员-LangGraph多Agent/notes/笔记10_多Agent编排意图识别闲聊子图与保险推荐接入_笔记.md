# 多 Agent 编排：意图识别、闲聊子图与保险推荐接入

## 模块划分与命名

* **图内数据约束层（schema）**

    * > **定义**：只服务于图内部节点之间传参、不落库、不与前端交互的数据结构层。

    * 与 model 的界线：model 在本项目里指与数据库打交道的那一层；state 不落库，所以归 schema。

    * 边界：命名没有硬性规定，团队里叫 model 也不算错，关键是全项目口径统一——今天叫 schema 明天叫 model，读代码的人就得多跳一次。

* **编排者（orchestrator）**

    * > **定义**：一张判断用户请求该进哪条分支、并把分支结果交回的图。

    * 词义：orchestrator 在专业语境里是编排、协调，不是管弦乐家。

    * 命名收益：目录里出现 orchestrator 一眼可知用途，比 `A`、`B` 这类名字可读。

* **代码按职责分家**

    * schema 层装三样：意图常量、意图识别结果、主图 state。

    * 编排层只负责调用：识别完往哪走、节点怎么连。

    * 识别层装规则、模型、兜底三套，与编排逻辑互不干扰。

    * 闲聊单独成模块，内部再封一个类，不塞进编排文件，否则该文件很快不可读。

```text
agents
├── schema          意图常量 · 结果对象 · 主 state
├── orchestrator    主图：只决定"识别完往哪走"
├── intent_router   意图识别：规则 + 模型 + 兜底
├── chat_chat       闲聊子图
└── advisor         已有的保险推荐 agent
```

## 意图契约

### 常量与结果对象

* **意图（Intent，Literal）**

    * > **定义**：把主图五个分支名收敛成一个 Literal 类型，供所有返回值注解复用。

    * 五个取值：`chitchat`、`recommendation_plan`、`claim`、`human_handoff`、`fallback`。

    * 存在理由：意图识别节点要声明返回类型为 Literal，不抽常量就得在注解和别处各抄一遍五个字符串。

    * 与图结构的对应：五个分支节点、五条去向、五种意图，三者是同一套名字。

    * 等价关系：这些字符串既是意图名，也是节点名；`add_node` 用什么名字、`goto` 就往哪儿跳，两边必须一模一样。

    * > **易错点**：少一个下划线、多一个字母，图编译时不会提示"你是不是想写另一个"，只在运行时报找不到节点。

* **意图识别结果（IntentResult）**

    * > **定义**：用类而不是字符串承载识别结论，一次表达"是什么、为什么、有多确定、有没有风险"。

    * 两个基础字段：`intent` 类型为 `Intent`，只能填五种之一；`reason` 记录判成该意图的理由。

    * `reason` 的用途：意图由 AI 判定，必须留下判断依据；正常时是一条日志，判错时是排查抓手。

    * 真实项目常见扩展：置信度（AI 自评正确概率）、风险标记（布尔，本轮输入有无风险）、子意图（父意图下的细分）。

    * 字段谁来填：给模型绑定结构化输出约束后，字段由 AI 按结构生成，八个十个都一样。

    * 类的收益：字符串只能表达"是什么"；类多了置信度就能做路由降级，多了风险标记就能做风控拦截。

* **结果类的命名口径**

    * 主图侧定义时称 `IntentResult`，识别模块引用时称 `IntentRouteResult`，两者指同一个结果对象。

    * 引用方要以实际定义的名字为准，改名时两处同步，否则导入即失败。

## 主图状态

### 状态字段与取值时序

* **保险顾问状态（InsuranceAgentState）**

    * > **定义**：主图的数据契约，继承 `MessagesState` 后只额外补两个工作流字段。

    * 基类收益：`MessagesState` 自带 `messages`，对话历史这一块不用自己写。

    * 两类流通信息：一类是对话消息，一类是工作流；state 就按这两类长。

    * `previous_workflow: Intent`：上一轮走的是哪条分支。

    * `active_workflow: Intent`：本轮走的是哪条分支。

    * 类型都写 `Intent`：不管上一轮还是本轮，结果必然是五种之一，不会跑到别处。

    * 不加 `NotRequired` 的理由：类型标注已经够用；首轮可能没有值这件事，留到读取时用默认值处理。

* **用 `active_workflow` 反推上一轮**

    * > **定义**：本轮路由开始前，state 里残留的 `active_workflow` 就是上一轮写入的结果，读它即得"上一轮"。

    * 时序机理：

    ```text
    第 1 轮
      请求进来 → route_node 读 state["active_workflow"]（还没有值）
               → 写入本轮结果，例如 chitchat
               → 图跑完，state 留下 active_workflow = chitchat

    第 2 轮
      请求进来 → route_node 读 state["active_workflow"]
                 这个值仍是上一轮的 chitchat —— 它就是上一轮的结果
               → 再写入本轮新结果，把它覆盖
    ```

    * 结论：每一轮路由都产生新的 `active_workflow`；上一轮的 `active_workflow` 在下一轮路由执行前，就是这一轮的 `previous_workflow`。同一块数据，在两个时间点上含义不同。

    * 结构收益：`previous_workflow` 不需要额外维护，不必在图末尾再挂一个搬运节点，路由节点自己顺手记下。

* **首轮空值**

    * 第一轮请求进来时 state 里还没有 `active_workflow` 这个键。

    * 取值一律用 `state.get("active_workflow", "")`，不要用 `state["active_workflow"]` 下标取值。

    * 现象：下标取值直接抛异常，报"取不到 active_workflow"，而字段名并没有拼错。

    * 空字符串是安全的初值：后续 `previous_workflow` 只作上下文描述，不参与节点跳转。

## 节点与 Command 路由

### 节点清单与命令返回

* **主图节点清单**

    * `route`：意图识别路由节点，所有请求的第一站。

    * `recommendation_plan`：保险方案推荐与咨询。

    * `claim`：理赔咨询。

    * `chitchat`：闲聊。

    * `human_handoff`：转人工。

    * `fallback`：意图识别失败时的兜底。

    * 结构概括：六个节点、五个分支、一个入口。

* **占位实现**

    * > **定义**：能力尚未开发时先写假函数，让图形状完整、可编译可跑通，回头再把真逻辑塞进同一函数。

    * 统一契约：所有节点入参都是 `state`，返回值都是要并进 state 的内容。

    * 五个分支节点的形状一致：`return {"messages": [AIMessage(content="…")]}`。

    * 占位文案示例：推荐"保险方案推荐功能尚未完成"、理赔"理赔咨询功能尚未完成"、转人工"你的请求已转人工，请耐心等待"、兜底"无法识别你的意图，请再说一遍"、闲聊"哈哈，你又来了，欢迎你来到安心宝商城，今天聊点啥"。

    * 为什么返回 `messages`：这几个能力最终都是给用户一句话，一句话就是一条消息，消息存在 state 的 `messages` 里。

    * 占位的价值：形状写对了，将来换成真实现，外面的结构与边一行都不用动。

* **命令对象（Command）**

    * > **定义**：一个返回值同时携带"要并入 state 的更新"和"下一步去哪"的节点返回类型。

    * 两个字段：`update` 是合并进 state 的内容；`goto` 是目标节点名。

    * 替代方案对比：普通节点只能 return 字典更新 state，要指定走向得另写路由函数配条件边；`Command` 让路由节点自己说完下一站，省掉那条额外的边。

    * `goto` 与路由结果同值：`goto=active`，因为"本轮路由结果"就是"要去的地方"。

    * 类型标注 `Command[Intent]`：LangGraph 读到这个泛型参数，就知道该节点可能跳向这五个节点，五条分支边自动生成，一条条件边都不用手写。

    * 导入来源：`from langgraph.types import Command`。

    * > **易错点**：从别处随手导一个同名 `Command`，不会立刻报语法错，而是运行到这一步才炸，排查很费时间。

## 建图与生命周期装配

### 建图流程与启动装配

* **`init_insurance_agent(checkpointer)`**

    * > **定义**：把建图、加节点、连边、编译收进一个可调用函数，供启动时调用一次。

    * 不写模块顶层的原因：顶层直接 `StateGraph(...)` 会让 import 成为副作用——谁 import 谁就建一张图；图是 agent，应该在项目启动时加载一次。

    * 第一步构造器：`StateGraph(InsuranceAgentState)`，builder 由此知道图的数据长什么样。

    * 第二步加节点：`add_node(名字, 函数)`，名字不要手打，直接从常量复制。

    * 第三步连入口：`add_edge(START, "route")`。

    * 第四步连出口：五个分支各自 `add_edge(分支名, END)`，不需要汇总节点。

    * 第五步编译：`builder.compile(checkpointer=checkpointer)`，编译出来的才是能跑的图。

    * checkpointer 的来源：由调用方传入，函数不关心它从哪来、怎么配，只管用。

    * 易错点：五个出口边容易漏，漏了也"看着差不多连完了"，加完要对着图数一遍——六个节点，一入口一路由，剩下五个都得有去处。

* **分支不汇总 vs 生产加围栏**

    * 本项目五个分支直连 `END`，因为每个子节点自己就能把结果返回给用户。

    * 这与"所有分支最后汇到一个汇总节点"的画法不是一回事，别混。

    * 生产环境常在 `END` 前加一道围栏节点：对 AI 生成内容做校验，查隐私泄露与安全风险，命中就拦下并回固定话术。

    * 更细的系统在前面再加一道输入校验，前后两层构成安全围栏；本项目为控制复杂度不加，但结构上可以这么长。

* **lifespan 装配**

    * > **定义**：用 FastAPI 的 lifespan 在启动时创建一次主图，存入 `app.state`，运行期所有请求共用。

    * 动作：删掉旧 agent 的初始化，改为 `app.state.agent = await init_insurance_agent(checkpointer)`。

    * 异步要求：这里要 `await`，所以初始化函数必须写成 `async def`。

    * 接口解耦：对话接口从 `request.app.state.agent` 取 agent，只认"有一个能对话的 agent"，不关心它是单个 agent 还是一张编排图。

    * 结论：换 agent 不用改接口；装配点在启动时，调用点在运行时，两边解耦。

    * 验证：启动后前端聊天，实际对话对象已经是主图。

## 三段式意图识别

### 顺序与分工

* **完整链路**

    * > **定义**：生产级意图识别由寒暄规则、模型识别、异常兜底三段串联，只做模型识别只是三分之一。

    * 第一段：寒暄识别，用代码判断是不是"嘿/你好/再见/谢谢"这类消息，命中就直接返回固定回复，不调模型。

    * 第二段：模型识别，确认是正式对话后才交给模型；这一步用小模型就够，意图判断本身是简单任务。

    * 第三段：兜底，模型故障、访问失败、超时，改用备用模型或退回传统代码识别。

    * 排序原则：先便宜后昂贵、先确定后不确定——规则匹配几乎零成本，模型调用要花钱还可能失败，兜底是给模型调用上的保险。

```text
用户请求
   │
   ▼
规则判断是否寒暄 ──命中──▶ 返回固定回复 ──▶ 结束
   │
   │ 不是寒暄
   ▼
模型意图识别 ──正常──▶ 按 intent 路由 ──▶ 结束
   │
   │ 报错 / 访问失败
   ▼
兜底：备用模型或传统代码识别 ──▶ 结束
```

* **实现节奏**

    * 三套不必一次写完：先写模型识别跑通，再补寒暄与兜底。

    * 理由：代码是一步步长出来的，一次塞三套，出错时无法定位是哪一段的锅。

    * 模型选型：本项目自始至终一个模型；公司环境里可让小模型做简单判断、大模型做复杂工作。

### 路由模型与结构化输出

* **意图路由类（IntentRouter）**

    * > **定义**：把规则、模型、兜底三套识别逻辑收进一个类，构造时只准备模型与结构化输出绑定。

    * 模型初始化：`init_chat_model(模型名, api_key=settings.LLM_API_KEY, extra_body={"thinking": {"type": "disabled"}})`。

    * `api_key` 手动传：当前没有配环境变量，模型不会自己从环境读；取自配置里 LLM 那一段的 key。

    * 关闭思考：`thinking` 的 `type` 设 `disabled`，判断一句话属于哪一类用不着长篇推理。

    * 换模型只改一处：识别逻辑全挂在 `self.model` 上。

* **结构化输出**

    * 绑定方式：`self.route_model = self.model.with_structured_output(IntentRouteResult)`。

    * 作用：把"你要按什么格式交答案"变成模型调用的一部分，schema 有哪些字段，模型就按这些字段产出。

    * 收益：返回的已经是结果对象本身，不用再解析字符串。

    * 边界：结构化输出约束的是"结果怎么交出来"，不改变"判断意图"的能力，别指望它提升准确率。

### 上下文构造

* **两个入参**

    * `query`：用户本轮提问。

    * `context`：历史对话信息，包含上一轮工作流名与上一轮 AI 回复。

    * 为什么必须带历史：单看本轮无法判断。用户回"好的""确认""去做吧"，任何人、任何模型都不知道要它继续干什么，必须往回看。

    * 三信息合判的例子：上一轮 AI 说"我给你推荐了这样一套方案，你看一下怎么样"，上一轮工作流是方案推荐，用户回"好的"——三条一碰就知道本轮仍在方案推荐线上，不是开新话题。

* **上一条 AI 消息的取法**

    * 直觉写法 `state["messages"][-2]` 不可靠：用户消息之前可能夹着工具调用、工具返回结果，倒数第二条未必是 AI 正文。

    * 稳妥做法：从后往前遍历，找最近一条有内容、且不带工具调用的 AI 消息。

    * 实现要点：`messages[:-1]` 切掉本轮用户消息，`reversed` 从近往远，三道筛子依次跳过非 `AIMessage`、跳过 `tool_calls` 非空、只接受 `content` 非空。

    * 返回规则：第一次命中即最近一条；一圈无命中返回空字符串。

    * 上下文拼装：`上一轮工作流：{previous_workflow}` 换行 `上一轮AI回复：{previous_ai}`。

### 路由方法与提示词

* **`route(query, context)`**

    * > **定义**：一次模型调用，输入系统提示词加一条拼好的用户消息，输出结构化结果对象。

    * 消息构成：`SystemMessage(SYSTEM_PROMPT)` 加 `HumanMessage(f"用户问题：{query}\n上下文：{context}")`。

    * 返回标注必须写 `-> IntentRouteResult`，不写则后续取 `result.intent` 时 IDE 认不出类型。

* **系统提示词骨架**

    * 角色与任务：你是保险商城智能客服的意图识别节点，判断用户消息该交给哪个工作流。

    * 候选枚举：`intent` 只能从给定选项里选。

    * 职责说明：每个选项后面必须写清它是干什么的——方案推荐管什么、投保管什么、理赔管什么、转人工何时走、闲聊接什么、兜底什么情况用。

    * 为什么必须写职责：只给模型六个英文单词，它推不出 `claim` 是理赔；职责写清楚，判断才准。

    * > **易错点**：提示词里的意图列表与图里的 `goto` 分支是同一个契约。多写一个或少写一个选项，`goto` 就会指向不存在的节点；改列表时两边一起改。

### 接进主图

* **替换假路由**

    * 识别对象在模块末尾创建并导出（`router = IntentRouter()`），调用方不用自己 new。

    * 主图只导这一个对象，用它的 `route` 方法完成识别。

    * `query` 取 `state["messages"][-1].text`；`context` 按上节拼装；`result.intent` 同时写入 `active_workflow` 和 `goto`。

    * 收益：识别出什么意图就去哪个节点，编排图里一句判断都不用写。

* **消息对象与字符串**

    * 错误写法 `query = state["messages"][-1]` 拿到的是消息对象，不是字符串。

    * 正确写法 `query = state["messages"][-1].text`，取出消息里的文本。

    * 为什么不报错：对象拼进 f-string 时 Python 会调 `__repr__` 转成字符串，模型收到的是 `HumanMessage(content='哈哈')` 这类东西，勉强能猜对。

    * 边界：函数声明要字符串就该给字符串，这种"能跑"的写法在别的环节按类型使用时会炸。

    * `find_previous_ai_message` 不用改，它返回的本来就是 `content` 文本。

## 寒暄规则层

### 正则基础

* **正则表达式（Regular Expression，regex）**

    * > **定义**：一种用符号描述字符串模式的语言，可理解为高度专业化的搜索框。

    * 三种用途：

    | 用途 | 干什么 | 例子 |
    | :--- | :--- | :--- |
    | 验证 | 检查字符串是否符合规则 | 手机号格式对不对 |
    | 提取 | 从大段文字里捞出符合条件的内容 | 从文本里抓出所有邮箱 |
    | 替换 | 把符合条件的内容换掉 | 把问号叹号清理干净 |

    * 本处只用第一种：验证用户输入是不是寒暄。

* **常用符号**

    | 符号 | 含义 |
    | :--- | :--- |
    | `.` | 任意字符 |
    | `\d` | 任意数字 |
    | `\w` | 字母、数字或下划线 |
    | `\s` | 空格 |
    | `*` | 零个或多个 |
    | `?` | 零个或一个 |
    | `+` | 一个或多个 |

    * 组合示例：邮箱正则＝开头一串字母数字下划线（可带加减号）＋ `@` ＋ 任意数量字母数字下划线 ＋ 点 ＋ 域名。

    * 边界：不必现在就会写，能看懂匹配寒暄的那几条正则即可。

### 三类寒暄

* **寒暄枚举（social intent）**

    * `greeting`：打招呼，典型输入"你好、您好、嗨、哈喽"。

    * `thanks`：感谢，典型输入"谢谢、多谢"。

    * `goodbye`：再见，典型输入"再见、拜拜"。

    * 配套数据：每类一组正则模式，每类一句固定回复（greeting 为"你好，我是保险顾问，可以帮你咨询产品"，thanks 为"不客气"）。

* **匹配与回复**

    * `normalize` 先格式化：用正则替换能力清掉问号、叹号等无效字符；用户打"你好！！！"或"你好?"也能命中。

    * `match_social_intent`：清理后的文本逐个正则试，哪一类先命中就返回哪一类，全不命中返回 `None`。

    * `get_social_response`：按寒暄类型从固定回复表取一句，取不到给空串。

    * `re` 是标准库，必须显式 `import re`；忘了导会报 `NameError`，别在业务代码里找半天。

    * > **注意**：`if social_intent:` 不能省。不命中时返回 `None`，少了这句 `None` 会被当成命中，去回复表取回空字符串，用户收到一片空白。

### 类型分叉

* **寒暄返回字符串**

    * `route` 的返回类型因此是 `IntentRouteResult | str`：命中寒暄返回固定回复字符串，走模型返回结果对象。

    * 收益：寒暄命中零 token、零延迟；非寒暄才付出模型调用成本。这就是把规则放在模型前面的全部意义。

    * 报错现象：`'str' object has no attribute 'intent'`，位置在编排图取 `result.intent` 那一句。

    * 根因：编排图不知道 `route` 有两种返回类型，一律按对象取 `.intent`，碰到字符串就炸。

    * 修法：编排图里先 `isinstance(result, str)` 分流。

* **寒暄分支的三处更新**

    * `active_workflow` 写 `"chitchat"`：寒暄本质也算闲聊，归到闲聊这条线上。

    * `messages` 塞一条内容是固定回复的 `AIMessage`：这句话要发给用户看，不进消息列表前端什么都收不到。

    * `goto=END`：直接结束，不再往下走任何节点。

```python
if isinstance(result, str):
    return Command(
        update={
            "active_workflow": "chitchat",
            "messages": [AIMessage(content=result)],
        },
        goto=END,
    )
```

## 兜底与日志

### 失败路径与日志

* **`try / except` 包住模型调用**

    * > **定义**：模型调用可能因网络抖动、接口挂掉、超时失败，失败时必须交出一个合法结果，让流程继续。

    * 兜底结果：`IntentRouteResult(intent="fallback", reason="意图识别出现异常")`。

    * 后续行为：编排图照常按 `fallback` 分支往下走，用户收到兜底话术。

    * 其他花样：类里可准备多个模型，当前模型失败就换下一个；也可以直接返回固定结果。

    * > **易错点**：兜底必须写 `except`，不能写 `finally`。`finally` 无论成败都执行，在里面改 `result` 会把正常识别的结果也覆盖成兜底值，等于所有请求都退化成 fallback。

* **`return` 放在 `try / except` 之后**

    * 日志内容：`log.info("意图识别完成", intent=result.intent, reason=result.reason)`。

    * 顺序要求：先完成识别（成功或兜底）→ 记日志 → `return result`。

    * 写错位置的后果：`return` 写在 `try` 内，成功那一支直接返回，异常那一支走不到日志，失败情况永远记不上。

```text
进入 route
   │
   ├─ 命中寒暄 ──▶ 返回固定回复（字符串），直接结束
   │
   ▼
调模型识别
   │
   ├─ 成功 ──▶ result = IntentRouteResult
   │
   └─ 异常 ──▶ result = IntentRouteResult(intent="fallback", reason="…")
              两条路在此汇合：记日志 ──▶ return result
```

## 闲聊子图

### 设计四层

* **什么交给模型**

    * 与业务无关的开放式闲聊可以交给模型回，但提示词必须限定身份与服务边界。

    * 不能任意瞎聊：违法违规内容不答，并尽量把话题自然引回当前服务范围。

* **闲聊里冒出业务意图**

    * 一旦发现用户在闲聊中提到业务，不再陪着聊，快速路由到产品咨询、理赔、投保等对应工作流。

    * 原则：闲聊可以是入口，不能是终点。

* **轮次统计**

    * 有人会反复闲聊、调戏 AI，每一轮都是成本，必须计次。

    * 超过阈值就回固定模板，不再让模型生成。

* **计数重置**

    * 上一轮不是闲聊，说明用户已回到正常业务，计数清零。

    * 不清零的后果：次数一路累加，用户偶尔聊一句就顶到上限，之后永远只收到固定模板，回不到正常业务。

    * > **注意**：计数与重置是一对。只加计数不重置，阈值变成一次性；只重置不计数，限流不存在。设计"连续行为限制"时两个动作必须成对出现。

### 子状态

* **闲聊状态（ChatChatState）**

    * > **定义**：继承父 state，白拿消息列表与上一轮工作流，只补一个闲聊计数器。

    * 写法：`class ChatChatState(InsuranceAgentState)` 加 `chat_count: int`。

    * 继承收益：`messages` 来自父 state，`previous_workflow` 来自父 state，不用重复定义。

    * 放层原则：看谁拥有它。全局共用的放父 state，只有一个子图自己用的放子 state。

    * 放错层级的后果：别的节点莫名多出一个永远不读的字段，子图又拿不到自己该有的上下文。

    * 类型注解要写子 state，不要图省事标父 state；标错后编辑器会一直报"字段不存在"，因为父 state 里确实没有 `chat_count`。

* **节点写成类方法**

    * 签名因此多一个 `self`，这是把节点写成类方法的必然代价。

    * 不影响它当节点：LangGraph 认的是 `state` 那一个参数，`self` 由 Python 自己补。

    * 不要因为多了 `self` 就把方法拆到类外：类里能直接用 `self.model`，拆出去反而要到处传模型。

### 节点内部流程

* **取数与清零**

    * 取次数：`count = state.get("chat_count", 0)`，第一次进来没有该键，给 0 才聊得起来。

    * 清零条件：`if state.get("previous_workflow") != "chat_chat": count = 0`，上一轮不是闲聊就从零计。

    * > **易错点**：清零必须放在"判上限"之前。顺序反了，先拿旧次数判一次，用户仍会被误拦。

* **超限短路**

    * 阈值：`MAX_CHAT_COUNT = 2`。设多少没有技术答案，是业务问题，应与产品商定；写死在代码里不理想，宜放进配置。

    * 判定：`if count >= MAX_CHAT_COUNT:` 直接返回固定话术。

    * 返回形状：`{"messages": [AIMessage(content=FALLBACK_REPLY)]}`，节点返回值一定是字典，键是 messages，值是消息列表。

    * 固定话术："我主要协助处理保险产品投保和理赔咨询，请告诉我想办理或了解的事项。"既是拒绝，也是一次业务引导。

    * 超限支路不用更新 `chat_count`：已经超标，加不加一都会被这一支拦住。

* **正常对话**

    * 调用：`await self.model.ainvoke([SystemMessage(content=SYSTEM_PROMPT), *state["messages"]])`。

    * 列表套列表的坑：`state["messages"]` 本身是列表，直接放进去模型不认。

    * 两种解法等价：解构 `[system_message, *state["messages"]]`，或拼接 `[system_message] + state["messages"]`。

    * 返回：`{"messages": [response], "chat_count": count + 1}`，同时更新消息与计数。

    * 系统提示词的两类内容——业务引导："每次回复都自然引导用户回到保险产品的投保和理赔业务"；安全边界："不回答医疗、法律、投资、政治等高风险的专业建议""超出能力范围时如实说明无法提供"。

    * 提示词里的"最多两句话"不是客套：闲聊回复越长越容易把话题带跑，两句话是能收住的上限。

### 建子图

* **编译与共享**

    * 四步套路：创建 `StateGraph(ChatChatState)` → `add_node("chat_chat", self.handle_chat)` → 连边 → 编译。

    * 连边两种写法等价：`add_edge(START, "chat_chat")` 与 `add_edge("chat_chat", END)`，或 `set_entry_point("chat_chat")` 与 `set_finish_point("chat_chat")`。

    * `compile(checkpointer=True)` 的含义：子图消息记入父图 checkpoint，成为会话记忆的一部分。

    * `False` 则不记；只有想让子 agent 与父 agent 记忆隔离，才自己重新定义 checkpointer，默认共享。

    * 子 agent 需要历史：它一直在用 `state["messages"]`，必须挂在某个 checkpointer 上，直接共享父的那一份即可。

    * 封装：`init_chat_agent()` 一行返回建好的图，调用方不用两步散在外面。

* **挂进主图**

    * 删掉原来那个假的闲聊函数，改为 `add_node("chat_chat", init_chat_agent())`。

    * 效果：闲聊从占位假节点变成真正建好的子图，主图节点可以是普通函数，也可以是子图或 agent。

    * 扩展性：子图以后往下长，在它自己的包里加节点加边即可，主图不用动。

    * 可拆细：现在只有开始、闲聊、结束三个节点；想拆可拆成"路由判断节点 + 发请求的 LLM 节点"，超限直接跳结束。

## 子图消息的流式输出

### 现象与根因

* **后端答了前端空白**

    * 现象：请求状态 200，后台无报错，只一条不影响功能的 v3 警告，但前端什么都没拿到。

    * 分界判断：刷新页面查历史会话，这段对话又查得到——说明消息已正常写进 checkpoint，只是没有实时推给前端。

    * 因此问题不在 agent 逻辑，在流式输出那一段。

* **messages 流的边界**

    * 调用链：接口层收请求 → 服务层调 `astream_events` 的 v3 模式 → 处理 messages 这条流。

    * 原实现：一个循环遍历消息块，从每块取文本推给前端。

    * > **定义**：messages 流只能处理父图的消息，父子嵌套时子图内部产生的消息根本不会出现在这条流上。

```text
前端 ──> 路由 ──> 服务 ──> astream_events（主图流）
                              │
                    START ──> 意图识别 ──> chat_chat（子图）
                                                  │
                                            handle_chat
                                                  │
                                                 END

messages 流：只看得到主图这一层吐出的消息
             子图内部产生的消息不在其中 → 前端一个字都收不到
```

### 两条修法

* **方案一：合并两条事件流**

    * 思路：messages 流看父图，另开 subgraphs 流专门拿子图消息。

    * 撞上的问题：两个 `for` 属于两个事件循环，messages 流遍历完时主图已跑完，再遍历 subgraphs 拿不到数据。

    * 解法：引入 `aiostream` 的 `merge`，把两条异步流合成一条，再在这条流上做一次循环。

    * 评价：复用官方流、取消息代码不用改，但把简单的取消息变成"两路流 + 一个合并库"，收益与复杂度不成比例，了解即可。

* **方案二：手动解析完整事件流**

    * 做法：不再遍历 `stream.messages`，直接 `for` 遍历 `stream`，拿到完整事件流。

    * 收益：除了消息事件，还能拿到子图消息、自定义事件、interrupt 事件等。

    * 代价：数据格式复杂，要自己逐层认结构。

| 维度 | 方案一：合并事件流 | 方案二：手动解析 |
| :--- | :--- | :--- |
| 做法 | messages 流 + subgraphs 流，用 `aiostream.merge` 合并 | 直接遍历 `stream`，按字典结构逐层取 |
| 优点 | 复用官方流，取消息代码不用改 | 一条流拿全所有事件，子图消息也在其中 |
| 代价 | 两个事件循环要合并，多引一个库 | 解析代码繁琐，要自己认结构 |
| 取舍 | 了解即可 | 项目里用这个 |

### 事件结构

* **单条事件（event）**

    * 顶层：`type` 为 `event`，`method` 是事件类型（`message`、`custom`、`values` 等）。

    * `params` 是字典，装三样：

    | 字段 | 含义 | 用法 |
    | :--- | :--- | :--- |
    | `namespace` | 当前所在的 agent | 值为 `chat_chat` 说明事件来自闲聊子图 |
    | `timestamp` | 事件产生的时间戳 | 排查时序用 |
    | `data` | 这一轮对话的数据 | 真正要解析的东西 |

    * `data` 是元组，取 `[0]` 拿到第一部分。

    * 第一种形态：手动返回的 `AIMessage`，直接 `.text` 取文本。

    * 第二种形态：让 AI 生成的，是字典 `{"event": "content_block_delta", "data": {"type": "text_delta", "text": "哈哈"}}`，最终文字在 `data.text`。

    * 流式本质：打印出来的 `text` 是模型一个字一个字吐的碎片，先"哈哈"、再逗号、再"我可不会编故事啊"；解析目标就是把每片文字捞出来推给前端。

* **解析代码的五个动作**

    * 遍历 `stream` 拿到 `event` 大字典。

    * 取 `method`，不等于 `message` 就跳过，只处理消息事件。

    * 取 `params`，再取 `params["data"]`；`namespace` 与 `timestamp` 这次用不上。

    * `data` 是元组，用 `[0]` 取第一部分。

    * 第一部分是 `AIMessage` 就 `.text` 推出；否则按字典走 `data` → `text` 这一层。

    ```python
    async def stream_chat(agent, inputs, config):
        async for event in agent.astream_events(inputs, config=config, version="v3"):
            if event.get("method") != "message":
                continue

            data = event["params"]["data"][0]

            if isinstance(data, AIMessage):
                yield data.text
            elif isinstance(data, dict) and data.get("data", {}).get("text"):
                yield data["data"]["text"]
    ```

    * > **易错点**：最后一步必须是 `elif`。写成两个独立 `if`，`AIMessage` 走完第一支不停，继续走第二支调 `.get()`，直接崩：`'AIMessage' object has no attribute 'get'`。

## 保险推荐 Agent 接入

### 三处改动

* **复用既有 agent**

    * > **定义**：主图节点可以是普通函数、子图，也可以是一个早已写好并跑通的 agent，三者都能当节点用。

    * 前提：推荐流程此前已实现——一套提示词加一堆工具，早已跑通，本次只做接入，不重写。

* **改动清单**

    * 第一处，checkpointer：该 agent 自己的 `compile` 原来挂着 checkpointer，改为 `compile(checkpointer=True)`，state 已从父继承，直接共享父 checkpoint。

    * 第二处，初始化函数改名：原名与主图的初始化函数重名，改成 `init_insurance_advisor`，避免导入时打架。

    * 第三处，主图换节点：删掉假的推荐函数，改为 `add_node("recommend_plan", await init_insurance_advisor())`。

    * `await` 不可省：初始化函数是异步的，不加 `await` 拿到的是协程对象，挂进图里必然报错。

    * 异步口径：FastAPI 项目里所有函数都该定义成 `async def`，别一半同步一半异步，调用时容易漏 `await`。

* **接入后的验证**

    * 闲聊"讲个笑话"正常，仍会被往保险上引。

    * "我想买保险"被识别成推荐分支，进入原有的导购流程：问预算、是否买过、给谁买、年龄。

    * 信息补齐后工具查询正常返回保险方案。

    * 追问条款如"免赔额是多少"时报错，原因是向量库服务没启动，不是项目代码问题，起服务即可。

### 通用接入套路

* **新增子能力三步**

    * 新开一个文件或包，在里面把 agent 写出来：用 LangChain 方式创建 agent 可以，用 LangGraph 搭一张 graph 也可以，都能当子节点。

    * 到主图里，把原来那个占位的普通函数节点替换成开发好的 agent。

    * 如果子 agent 要共享父记忆，把它的 `checkpointer` 改成 `True`。

```text
START ──> 意图识别路由 ──┬──> chat_chat（子图）──────────> END
                        ├──> insurance_advisor（agent）──> END
                        ├──> 理赔（待接入）──────────────> END
                        └──> 转人工（危险 / 违法内容）───> END
```

* **架构收益**

    * 每加一个能力不动别人：只加一个新文件、换一个节点、改一处 checkpointer。

    * 业务越多，父图挂的子 agent 越多，整体能力自然越强。

## 运行验证与偏差

### 轮次计数

* **日志观测点**

    * 初次验证：加日志打印 `count`，首轮聊完显示 0，看着不对。

    * 原因：自增写在 `return` 里，日志打在自增之前，打印的是本轮开始时的旧值；功能没问题，是观测点放错。

* **自增位置的影响**

    * 把 `+1` 挪到取完次数之后、判上限之前：首轮日志为 1，第二轮 `count` 已是 2，`2 >= 2` 立即命中上限。

    * 结果：两轮里只聊了一轮。

    * > **结论**：自增放在判断之前，等于把上限提前消耗一格，实际可聊轮次变成 `MAX_CHAT_COUNT - 1`；这种"差一轮"偏差不报错，只会让业务方觉得"怎么刚开口就不让聊了"。

    * 恢复做法：`+1` 留在 `return` 里。日志显示的是本轮开始前已聊次数，依次 0、1、2，读到 2 才拦下，正好聊满两轮。

### 三条验证

* **轮次限制**

    * 后台计数依次走 0、1、2，到 2 的那次返回固定话术。

* **跨业务清零**

    * 上一轮问理赔，`previous_workflow` 变成理赔分支；本轮回闲聊，计数从 0 重新开始。

* **安全兜底**

    * 问危险问题（如"如何造炸弹"），请求压根没进闲聊节点，意图识别直接判转人工。

    * 双层防护：上游路由先挡掉违法危险请求，闲聊节点的系统提示词是第二道保险。

    * 分层判断比让闲聊节点自己拒绝更专业。
