## 结构化输出模式（Pydantic 进阶、TypedDict 与 JSON Schema）
> 对应块：BLK11 | 覆盖分集：P44-P49 | 块标题（分集名）：《结构化输出模式（Pydantic进阶、TypedDict与JSON Schema）》

在前一讲里，我们见识过了 Pydantic 的基础用法，能够把大模型的自由文本约束成干净的键值对。但在实际业务开发中，真实世界的数据从来不会这么听话——你拿到的绝不会只是单个人名、单个年龄这种扁平数据。很多时候，一段文本里会冒出一整批人员名单，一张电商评论里既有打分又有数十条优缺点，甚至是一张复杂的采购发票，里面嵌套着多级明细与商品列表。更要命的是，业务上往往还会对数值设卡：年龄不能超过 150 岁，价格必须大于零，库存不能为负。

面对这些复杂的结构化诉求，光会定义一个扁平的 Pydantic 模型显然不够用了。这一讲我们就把结构化输出彻底摸透：先带大家吃透 Pydantic 的高级特性（列表提取、多层嵌套与边界限制条件），拆解其底层的转换工作流；接着横向对比另外三种主流模式——TypedDict、原始 JSON Schema 和 `@dataclass`；最后，我们还要搭建一个虚拟服务器（Fake Server），给大模型故意下套，亲手测一测这四种模式在数据错位时的真实类型校验底线。

### Pydantic 高级特性

#### 列表提取与批量数据建模
在实际提取任务中，我们经常遇到提取目标不是单一实体，而是一整组同类对象的情况。比如从一段杂乱的会议记录中提取参会人名单，或者从社交媒体评论中提取所有提及的优缺点。如果直接使用单一实体模型去绑定，模型往往只能提取第一个，或者把多个实体强行拼成一个字符串。正确的建模方式是构建两层结构：内层定义单个实体的模型，外层定义一个包含列表字段的容器模型。

例如，我们要从文本中批量提取人物信息。我们先定义单个实体的 `Person`，接着定义容纳多个人的 `PersonList`：

```python
from pydantic import BaseModel, Field
from typing import List
from langchain_openai import ChatOpenAI

class Person(BaseModel):
    name: str = Field(description="姓名")
    age: int = Field(description="年龄")

class PersonList(BaseModel):
    persons: List[Person] = Field(description="人物列表，包含多个 Person 对象")

# 绑定结构化输出模型
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_model = model.with_structured_output(PersonList)

# 调用测试
result = structured_model.invoke("张三 30岁，李四 40岁")
print(result)
```

调用完成后，`result` 会被直接解析为一个 `PersonList` 实例，其 `persons` 属性是一个包含了多个 `Person` 对象的标准 Python 列表：`[Person(name='张三', age=30), Person(name='李四', age=40)]`。每一个元素都可以通过属性方式直接访问字段。

这种列表提取模式在实际场景中有极强的通用性。再看两个典型业务场景：

第一个是产品评论分析。当用户对一款手机写下长篇评价时，优点和缺点往往各有数条，此时可以把优缺点分别定义为字符串列表：

```python
class ProductReview(BaseModel):
    product_name: str = Field(description="产品名称")
    rating: float = Field(description="产品评分，满分5分")
    pros: List[str] = Field(description="产品的优点列表，可包含多条")
    cons: List[str] = Field(description="产品的缺点列表，可包含多条")

structured_model = model.with_structured_output(ProductReview)
result = structured_model.invoke("iPhone 17 很棒，摄像头强大，手感也好，但是价格贵，没有充电器，4分。")
```

此时大模型会自动将“摄像头强大”、“手感好”归入 `pros` 列表，把“价格贵”、“没有充电器”归入 `cons` 列表，精准完成归纳聚合。

第二个是发票与账单明细提取。一张采购发票通常由发票头信息与明细列表组成：

```python
class Invoice(BaseModel):
    invoice_number: str = Field(description="发票号码")
    date: str = Field(description="开票日期")
    total_amount: float = Field(description="总金额")
    items: List[str] = Field(description="采购的商品名称列表")

structured_model = model.with_structured_output(Invoice)
```

如果商品本身还需要记录单价、数量等维度，只需要把 `items` 的元素类型由 `str` 替换为自定义的 `Item` 模型即可。这就是列表提取的核心范式：用内层模型刻画单体，用外层 `List[...]` 承载集合。

#### 嵌套结构与层级深度约束
当数据之间存在从属或层级关系时，单纯的扁平字段或同级列表就无法表达其真实结构了，这就需要使用嵌套结构（Nested Structure）。所谓嵌套结构，就是在一个 Pydantic 模型里，将另一个自定义的 Pydantic 模型作为字段类型。

最直观的例子是公司与地址的关系。公司有名称，同时有一个地址属性；而地址本身并不是一个简单的字符串，它包含城市、行政区等具体字段：

```python
class Address(BaseModel):
    city: str = Field(description="城市")
    district: str = Field(description="区域或行政区")

class Company(BaseModel):
    name: str = Field(description="公司名称")
    address: Address = Field(description="公司所在地详细地址")

structured_model = model.with_structured_output(Company)
result = structured_model.invoke("阿里巴巴坐落在杭州的滨江区")
print(result)
```

解析后的结果会呈现清晰的树形结构：`Company(name='阿里巴巴', address=Address(city='杭州', district='滨江区'))`。访问时可以通过链式语法获取属性：`result.address.city`。

在更复杂的场景中，嵌套与列表常常组合出现。比如电影信息提取，一部电影除了标题、年份、导演和评分外，还包含一个演职员列表，而演职员本身又包含名字和扮演的角色：

```python
class Actor(BaseModel):
    name: str = Field(description="演员名称")
    role: str = Field(description="饰演的角色名称")

class Movie(BaseModel):
    title: str = Field(description="电影名称")
    year: int = Field(description="上映年份")
    director: str = Field(description="导演")
    rating: float = Field(description="评分")
    actors: List[Actor] = Field(description="演职员列表")

structured_model = model.with_structured_output(Movie)
```

大模型在处理这类输入时，既要提取外层的标量字段，又要针对内层循环匹配演员与角色，构成了典型的复合嵌套结构。

再来看一个多维度评价抽取的例子。一段针对商品的详细长评往往涵盖多个维度（如质量、价格、服务）：

```python
class DimensionReview(BaseModel):
    dimension: str = Field(description="评价维度，例如：质量、价格、服务")
    score: float = Field(description="该维度的评分")
    comment: str = Field(description="针对该维度的具体评价描述")

class ComprehensiveReview(BaseModel):
    sentiment: str = Field(description="整体情感倾向：积极、中性、消极")
    overall_score: float = Field(description="综合评分")
    summary: str = Field(description="一句话总结")
    dimensions: List[DimensionReview] = Field(description="各个维度的详细评价列表")
```

> **注意**：这里整体情感字段如果要求更严格，可以使用 `Literal["积极", "中性", "消极"]` 或 `Enum` 枚举类来强制约束取值范围。若仅在 `description` 中用自然语言限定，模型较弱时偶尔可能输出范围外的词汇。

针对嵌套结构，这里必须给出一个关键工程告诫：
> **易错点**：虽然 Pydantic 支持无限深度的模型嵌套，但**大模型的上下文结构理解能力是有限的，工程实践中嵌套层级建议保持在三层以内（即层级 $\le 3$）**。

这就像我们平时编写业务代码一样，极少会写三层以上的嵌套循环，一旦超过三层，通常都会通过拆分函数或优化算法进行降维。大模型同理，一旦结构嵌套达到四层甚至更深，模型生成 JSON 时极易发生括号错配、字段错位或漏填。遇到四层以上的深层结构，务必将其拆解为多次大模型调用，逐级递进提取；同时，一定要为每一个嵌套类和每一个字段编写详尽精准的 `description`，辅助模型准确定位字段语义。

#### 字段约束条件与平台适配差异
在定义模型时，除了限定类型，业务系统往往还需要对数值范围或字符串长度设定硬性限制。Pydantic 提供了丰富的校验参数，可以直接写在 `Field(...)` 内：
- 字符串长度约束：`min_length`（最小字符数）、`max_length`（最大字符数）。
- 数值大小约束：`gt`（大于，greater than）、`ge`（大于等于，greater than or equal）、`lt`（小于，less than）、`le`（小于等于，less than or equal）。

我们先在纯 Python 环境下验证这些限制条件的拦截机制：

```python
from pydantic import BaseModel, Field, ValidationError

class User(BaseModel):
    name: str = Field(description="姓名", min_length=2, max_length=50)
    age: int = Field(description="年龄", ge=0, le=150)
    email: str = Field(description="电子邮箱")

# 正常测试
user1 = User(name="Tom", age=20, email="Tom@126.com")
print(f"OK: {user1}")

# 越界测试
try:
    user2 = User(name="Tom", age=200, email="Tom@126.com")
    print(f"OK: {user2}")
except ValidationError as e:
    print(f"Fail: 捕获到校验异常 -> {e}")
```

当传入 `age=200` 时，由于超过了 `le=150` 的上限，Pydantic 在实例化阶段会立即抛出 `ValidationError`，阻断非法数据进入下游。

然而，当我们把带限制条件的 Pydantic 模型传递给大模型时，情况就变得非常微妙了。大模型到底能不能理解并遵守这些数字边界？我们通过一个产品库存模型，在不同模型平台上进行实测：

```python
class Product(BaseModel):
    name: str = Field(description="产品名称", min_length=2)
    price: float = Field(description="产品价格", gt=0)
    stock: int = Field(description="产品库存", ge=0)
```

如果输入的文本是正常的商品描述，各大平台都能顺利输出合法结果。但如果我们故意输入负数极端数据，例如“某试验产品，价格为 -10 元，库存为 -100 件”，不同模型平台的处理逻辑出现了显著的分化：

- **智谱 AI 平台表现**：
  模型在解析后输出 `price=10.0`，`stock=100`。智谱的大模型在底层发现输入违反了大于零的约束，擅自帮用户把负号干掉了，直接转换成了正数。这种行为看似“智能”，实则“管得太宽”。如果用户本意就是要记录异常输入或排查错误数据，这种自作主张的纠偏反而会掩盖真实问题。
- **OpenRouter 平台表现**：
  同样面对负数输入，OpenRouter 平台驱动的模型输出 `price=1.0`，`stock=0`。因为模型要求 `price > 0`，模型在输入非法的情况下，给出了满足约束条件的最小下限正数 `1.0`；要求 `stock >= 0`，模型给出了满足边界条件的最小值 `0`。

> **结论**：在处理数值限制条件时，OpenRouter 等严谨遵循 JSON Schema 边界规则的平台表现更可控，它不会篡改用户数值极性，而是在满足校验约束的合法值域内选择临界值；而部分国产平台可能会出现主动过度修正的现象。在设计高可靠系统时，不能完全寄希望于大模型自带的边界意识，必须依赖 Pydantic 的本地运行时二次校验。

### Pydantic 模式底层运行机制

#### 结构化转换与工具调用链路
很多开发者在使用 `model.with_structured_output(PydanticModel)` 时，会误以为大模型本身直接懂得 Python 的 Pydantic 类。其实大模型只认识文本和 JSON，它与 Python 代码之间存在一条完整的编译与反序列化链路。

整个转换链路的核心执行逻辑包含以下关键环节：
1. **模型导出 Schema**：LangChain 接收到传入的 Pydantic 模型（例如 `BookInfo`）后，在内部调用 Pydantic 核心方法 `model_json_schema()`，将 Python 类定义静态编译成符合工业标准的 JSON Schema 规范字典，包括所有字段名、类型映射、`Field` 描述文本以及必填字段列表。
2. **载荷组装与工具调用**：现代主流模型（包括 OpenAI、Anthropic、DeepSeek、Gemini 等）普遍支持函数调用（Function Calling / Tool Calling）。LangChain 会把生成的 JSON Schema 打包成工具参数规范，作为底层 API 请求体的一部分发送给大模型服务端。
3. **模型严格生成**：大模型接收到底层的函数定义后，在生成 `AIMessage` 时受到语法引导机制的约束，强制按照该 JSON Schema 结构生成规范的 JSON 文本字符串。
4. **字符串反序列化**：LangChain 拦截到大模型返回的 JSON 字符串后，首先通过标准解析器将其还原为 Python 原生字典（`dict`）。
5. **强类型实例化与校验**：LangChain 将该字典解包并传入原始的 Pydantic 模型类中进行实例化。此时，Pydantic 会在运行时对每一个字段的类型、数量、限制条件进行二次硬校验。
6. **异常与重试处理**：如果在实例化环节发生了字段缺失、类型不匹配或越界，Pydantic 会立即抛出 `ValidationError`。如果配置了重试机制，LangChain 会将错误信息自动拼装成纠错提示词再次发起请求；若未配置或重试耗尽，则将错误向上抛出。校验通过后，最终向开发者交付一个安全可信的 Pydantic 类实例。

---

#### 数据流转图解与执行步骤
为了更直观地理解从类定义到实例交付的完整时序，我们将整个机制的数据流向整理为如下架构图：

```text
+-----------------------+
|  Pydantic 模型定义    |  (如 BookInfo，包含 Field 描述与类型定义)
+-----------+-----------+
            |
            v  model_json_schema()
+-----------+-----------+
|   标准的 JSON Schema  |  (描述字段名、类型、必填项与描述说明)
+-----------+-----------+
            |
            v  with_structured_output(method="function_calling")
+-----------+-----------+
|   大模型 API 请求     |  (以工具/函数参数形式注入请求载荷)
+-----------+-----------+
            |
            v  大模型生成响应
+-----------+-----------+
|    JSON 格式字符串    |  (大模型严格遵循 JSON Schema 输出的文本)
+-----------+-----------+
            |
            v  json.loads() / 反序列化
+-----------+-----------+
|    Python 原生字典    |  (内存中的 dict 结构)
+-----------+-----------+
            |
            v  Pydantic 实例化与校验
+-----------+-----------+
|   Pydantic 类实例     |  (校验失败抛出 ValidationError / 触发重试)
+-----------------------+
```

上图展示了从 Pydantic 模型声明到最终生成类实例的完整底层数据流向与转换节点。通过这套机制，开发者既享受了在 Python 端面向对象点语法访问属性的便捷性，又获得了严密的运行时类型防御。

### TypedDict 模式与类型元数据

#### 轻量字典结构与类型提示
虽然 Pydantic 功能强大，但在一些极简场景下，我们可能只是需要提取一个普通的字典，并不希望引入 Pydantic 的类实例化开销与重度依赖。针对这种需求，Python 3.8 官方标准库引入了 `TypedDict`。

> **定义**：`TypedDict` 是 Python 标准库 `typing` 模块提供的一种类型提示工具。它本质上仍然是一个普通的 Python 字典，但允许开发者通过类语法为字典声明键的名称与预期的值类型。

需要格外明确的是：普通的 `dict` 没有任何键或类型的约束；而 `TypedDict` 明确指出了字典中应该存在哪些键、每个键对应的类型是什么。然而，**`TypedDict` 主要用于静态类型检查（如 Mypy、IDE 智能提示与警告），它不是运行时的强校验器**。

我们可以通过一段代码直观体会它的工作特性：

```python
from typing import TypedDict

class MovieDict(TypedDict):
    title: str
    year: int

# 正常赋值
movie_correct: MovieDict = {"title": "星际穿越", "year": 2014}

# 缺少字段或字段不匹配
movie_error: MovieDict = {"name": "星际穿越", "year": 2014}
```

在 IDE（如 PyCharm 或 VS Code）中，`movie_error` 下方会出现波浪线警告，提示缺少必须的 `title` 字段；但是如果我们直接运行这段 Python 代码，解释器不会抛出任何异常，代码能够正常执行完毕。这就是它与 Pydantic 最本质的差异。

---

#### Annotated 元数据注解与嵌套定义
当我们在 LangChain 中使用 `TypedDict` 作为结构化输出的 Schema 时，单纯写类型（如 `str`、`int`）是无法向大模型传达字段语义描述的。在 Pydantic 中我们使用 `Field(description="...")`，而在 `TypedDict` 中，我们需要借助 Python 3.9 的 `typing.Annotated` 结构。

`Annotated` 的核心作用是在基本类型声明之外附加额外的元数据（Metadata）：
- 第一个参数表示真实的 Python 类型（如 `str`、`int`、`float`）；
- 后续参数可以放置任意描述信息、约束说明等元数据。

下面以电影信息抽取为例，演示 `TypedDict` 的标准写法：

```python
from typing import TypedDict, Annotated, List

class MovieDict(TypedDict):
    title: Annotated[str, "电影的名称"]
    year: Annotated[int, "电影的上映时间，四位数的年份"]
    director: Annotated[str, "电影的导演"]
    rating: Annotated[float, "电影的评分，满分10分，可包含一位小数"]

structured_model = model.with_structured_output(MovieDict)
response = structured_model.invoke("给我介绍一下电影《星际穿越》")

print(response)
print(type(response))
```

运行后打印出的 `type(response)` 显示为 `<class 'dict'>`。与 Pydantic 返回类实例不同，`with_structured_output` 绑定 `TypedDict` 时，直接返回 Python 原生字典。

`TypedDict` 同样完全支持复杂嵌套与列表嵌套。如果我们要提取电影的演员列表，只需先定义一个 `Actor` 的 `TypedDict`，然后将其作为类型嵌套在外层字典中：

```python
class Actor(TypedDict):
    name: Annotated[str, "演员的名字"]
    role: Annotated[str, "演员扮演的角色名称"]

class MovieWithActors(TypedDict):
    title: Annotated[str, "电影的名称"]
    year: Annotated[int, "电影的上映年份"]
    director: Annotated[str, "电影的导演"]
    rating: Annotated[float, "电影评分"]
    actors: Annotated[List[Actor], "演员列表"]

structured_model = model.with_structured_output(MovieWithActors)
response = structured_model.invoke("给我介绍一下电影《星际穿越》")
```

此时解析得到的是一个深层嵌套的字典结构，`response["actors"]` 是一个包含多个演员子字典的标准列表。

---

#### 省略号必填声明与平台表现
在使用 `Annotated` 时，除了传入描述字符串，还经常会见到传入省略号 `...`（Python 内置单例对象 `Ellipsis`）的写法。例如：

```python
class MovieDict(TypedDict):
    title: Annotated[str, ..., "电影的名称"]
    year: Annotated[int, ..., "电影的上映时间"]
    director: Annotated[str, ..., "电影的导演"]
    rating: Annotated[float, ..., "电影的评分"]
```

在 LangChain 的上下文中，`Annotated` 内传入的省略号 `...` 具有明确的语义约定：**它充当占位符，明确声明当前字段为必须填充项（Required），在下游 Schema 转换时会被标记为不可缺省**。

但在实际面对不完整输入时，不同模型供应商对该标记的支持力度存在显著差异。我们给定一段缺失评分的输入：“根据这段话抽取《盗梦空间》的信息，不包含的信息可以留空。《盗梦空间》2010 年上映，由诺兰导演。”

实测结果对比：
- **智谱 AI 平台**：
  输出的字典中仅包含 `title`、`year` 和 `director` 三个键，直接把 `rating` 漏掉了。省略号在智谱平台未能起到强制约束作用，必填规则失效。
- **OpenRouter 平台**：
  输出的字典中强制保留了 `rating` 键，并赋予其默认数值 `rating: 0`。因为模型底层识别到了该字段的 `required` 约束，在原语料无对应信息的情况下给出了保底数值。

> **提示**：省略号 `...` 的必填约束在不同平台上的生效程度，高度依赖于具体模型供应商对 JSON Schema 适配器的实现质量。如果业务逻辑对字段存在性有绝对刚性的要求，切忌仅依赖 `TypedDict` 的省略号，而应转用 Pydantic。

### JSON Schema 原始模式

#### 标准规范结构与字段映射
第三种结构化输出模式是直接手写原始的 JSON Schema 字典。无论上层的 Pydantic 还是 TypedDict，底层的本质都是先被转译成 JSON Schema，再发给大模型。因此，LangChain 允许我们跳过任何 Python 类型定义，直接将一个纯粹符合 JSON Schema 规范的字典传入 `with_structured_output(...)`。

一个标准的电影信息 JSON Schema 结构定义如下：

```python
json_schema = {
    "title": "movie",
    "description": "电影的基本信息结构",
    "type": "object",
    "properties": {
        "title": {
            "type": "string",
            "description": "电影的中文名称"
        },
        "year": {
            "type": "integer",
            "description": "电影上映年份，四位整数"
        },
        "director": {
            "type": "string",
            "description": "导演姓名"
        },
        "rating": {
            "type": "number",
            "description": "电影评分"
        }
    },
    "required": ["title", "year", "director", "rating"]
}

structured_model = model.with_structured_output(json_schema)
response = structured_model.invoke("给出《盗梦空间》的信息")
print(response)
print(type(response))
```

将该字典与之前的类定义做映射，各层级含义一目了然：
- `title`：对应类名（如 `Movie`），必须为英文字符串；
- `description`：结构的总体说明，支持中文；
- `type`：顶层数据类型，对象格式为 `"object"`；
- `properties`：属性映射字典，内部每个键对应一个字段，必须显式指明其 JSON 数据类型（`"string"`、`"integer"`、`"number"`、`"boolean"`、`"array"` 等）和 `description`；
- `required`：必填字段列表，包含在此列表中的键即相当于 Pydantic 的无默认值字段或 TypedDict 中的省略号。

如果需要实现嵌套列表（例如演员列表），则需要在 `properties` 内声明一个类型为 `"array"` 的字段，其 `items` 再指向一个嵌套的 `"object"` 字典结构：

```python
complex_schema = {
    "title": "MovieInfo",
    "description": "包含演职员的电影信息",
    "type": "object",
    "properties": {
        "title": {"type": "string", "description": "电影名"},
        "year": {"type": "integer", "description": "年份"},
        "director": {"type": "string", "description": "导演"},
        "rating": {"type": "number", "description": "评分"},
        "actors": {
            "type": "array",
            "description": "演员列表",
            "items": {
                "type": "object",
                "properties": {
                    "name": {"type": "string", "description": "演员名字"},
                    "role": {"type": "string", "description": "角色"}
                },
                "required": ["name", "role"]
            }
        }
    },
    "required": ["title", "year", "director", "rating", "actors"]
}
```

显而易见，这种原始 Schema 写法极其冗长，嵌套层级稍微变多就容易出现括号错配或语法遗漏。因此，在日常开发中极不推荐手写原始 JSON Schema，掌握它主要是为了理解底层协议。

---

#### 结构化调用方法与平台兼容性
在直接使用 JSON Schema 或其他结构化输出时，`with_structured_output` 方法提供了一个名为 `method` 的可选参数：

```python
structured_model = model.with_structured_output(json_schema, method="json_schema")
```

关于该参数的运行机理，需要掌握以下两点：
1. **默认模式**：当不显式指定 `method` 时，LangChain 默认取值为 `"function_calling"`。这意味着 LangChain 会将 Schema 包装成一个虚拟的工具函数，利用大模型底层的 Tool Calling / Function Calling 通道进行交互。
2. **显式 JSON 模式**：当指定 `method="json_schema"` 时，LangChain 会要求模型走底层的结构化 JSON 响应模式（如 OpenAI 的 `response_format={"type": "json_object"}` 或严格 JSON Schema 模式）。

> **注意**：`method="json_schema"` 是否可用，高度取决于具体的模型提供商以及 LangChain 底层适配器的实现。例如在原生 DeepSeek API 或某些开源模型服务中，可能并未完整适配直接传 `method="json_schema"` 的调用通道。在跨平台场景下，保持默认的 `"function_calling"` 通常具有最好的稳定性和兼容性。

---

### 数据类模式（@dataclass）

#### 数据类装饰器与方法自动生成
第四种结构化输出模式是使用 Python 标准库提供的 `@dataclass` 装饰器。它是 Python 3.7 引入的用于简化以数据为核心的类定义的语法糖。

在传统 Python 面向对象编程中，如果我们写一个纯数据载体类，往往需要机械地编写大量样板代码：

```python
class MovieManual:
    def __init__(self, title, year, director, rating):
        self.title = title
        self.year = year
        self.director = director
        self.rating = rating

    def __repr__(self):
        return f"MovieManual(title={self.title}, year={self.year}, ...)"

    def __eq__(self, other):
        # 逐字段比较对象相等性
        pass
```

使用 `@dataclass` 修饰后，Python 会在类创建时自动为我们合成并注入三个核心特殊方法：
1. `__init__()`：根据声明的字段类型自动生成带参构造函数；
2. `__repr__()`：自动生成易于打印和调试的友好字符串表示形式；
3. `__eq__()`：自动实现基于字段值比较的相等性判断逻辑。

---

#### 数据类特性与应用场景
在 LangChain 中使用 `@dataclass` 定义结构化输出的形式非常简洁：

```python
from dataclasses import dataclass

@dataclass
class MovieDataClass:
    title: str
    year: int
    director: str
    rating: float

structured_model = model.with_structured_output(MovieDataClass)
response = structured_model.invoke("给出《盗梦空间》的信息")

print(response)
print(type(response))
```

经过测试可以发现，将 `@dataclass` 类传入 `with_structured_output` 后，最终拿到的返回值类型依然是一个 Python 原生字典（`<class 'dict'>`），而不是该数据类的实例对象。

> **结论**：使用 `@dataclass` 修饰的类在底层仍然是一个标准的 Python 类，但它被标准库贴上了数据类标记，携带了字段元信息。在 LangChain 的四种模式选型中：
> - 如果需要强类型校验与对象化操作，首选 **Pydantic**；
> - 如果仅仅需要轻量级的字典输出，首选 **TypedDict**；
> - `@dataclass` 处于两者之间，在 LangChain 结构化输出场景中并没有展现出独特的不可替代性，了解其语法即可。

---

### 四种结构化模式的类型校验实测

#### 虚拟服务端异常响应构造
前面我们讲解了四种不同的结构化输出模式（Pydantic、TypedDict、JSON Schema、@dataclass）。在理论上，Pydantic 宣称具备运行时强校验，而其他三种模式缺少严格的校验拦截。但光听理论不够，我们需要通过实测代码来验证：**当大模型响应的数据格式与本地声明的 Schema 产生冲突时，四种模式究竟会如何表现？**

然而在实际测试时会遇到一个障碍：现代主流大模型（如 GPT-4o、DeepSeek-V3 等）的指令遵循能力极强，给定标准的 Schema 后，几乎 100% 能返回完全匹配的字段名，正常调用很难触发字段错位。为了精准测试客户端的校验容错能力，我们必须特意构建一个虚拟的假服务器（Fake Server）。

我们编写一个轻量的本地服务端脚本 `fake_server.py`，模拟一个兼容 OpenAI / DeepSeek 协议的端点。无论客户端请求什么字段，服务端在返回响应时都故意搞破坏，返回带有后缀序号的错误字段名：
- 本地客户端期望字段：`title`, `year`, `director`, `rating`
- Fake Server 故意返回字段：`title1`, `year2`, `director`, `rating`

```python
# fake_server.py 核心模拟逻辑片段
# 无论请求传入的 Schema 为何，底层响应数据硬编码为带有错误键名的 JSON：
fake_response = {
    "title1": "盗梦空间",
    "year2": 2010,
    "director": "诺兰",
    "rating": 9.3
}
```

启动该 Fake Server 后，我们在本地 Jupyter Notebook 中把大模型客户端的 `base_url` 指向该虚拟服务器地址，分别用四种模式发起结构化提取请求。

---

#### 客户端校验容错实测
当本地客户端以相同的 prompt 发起请求，面对服务端返回的包含 `title1` 和 `year2` 的非法响应时，四种模式产生了截然不同的反应：

1. **Pydantic 模式实测**：
   运行代码后，程序等待数秒，控制台直接抛出红色致命异常：`pydantic_core._pydantic_core.ValidationError`！
   异常信息明确指出：在解析数据时，未能找到必填字段 `title` 和 `year`。因为 Pydantic 在拿到字典后执行强类型实例化，发现字典中的键为 `title1` 和 `year2`，无法完成对象映射，立即拒绝执行并抛出异常。
2. **TypedDict 模式实测**：
   运行完全相同的调用，程序没有任何报错，顺畅执行完毕。终端打印出的字典内容赫然写着：`{'title1': '盗梦空间', 'year2': 2010, 'director': '诺兰', 'rating': 9.3}`。本地虽然定义了 `MovieDict(title=..., year=...)`，但由于没有运行时拦截机制，客户端无条件信任了服务端的返回，将错误字段原封不动吞了下去。
3. **JSON Schema 模式实测**：
   与 TypedDict 一致，程序完全不报错，直接输出了带有 `title1` 和 `year2` 的字典，定义在 Schema 内的 `required: ["title", "year"]` 在客户端彻底形同虚设。
4. **@dataclass 模式实测**：
   同样不报错，直接原样交出包含错误键名的原生字典。

通过这场刻意设计的压力对比实验，代码行为验证了我们的判断：除 Pydantic 之外，其余三种模式在客户端层面均没有任何运行时防御能力。

---

#### 校验机制对比与选型指南
我们将四种模式在底层行为、校验强度以及推荐场景上的差异汇总为如下对照表：

| 模式名称 | 返回数据类型 | 字段类型与必填校验 | 字段错位/多余时的运行时表现 | 生产落地选型建议 |
| :--- | :--- | :--- | :--- | :--- |
| Pydantic | 类实例（BaseModel） | 运行时强校验 | 立即抛出 `ValidationError` 并阻断流程 | 生产级工程核心首推，防御性最高 |
| TypedDict | 原生字典（dict） | 仅静态类型提示，无运行时强校验 | 静默接受非法字段，原样输出字典 | 仅用于追求启动速度与无依赖的轻量字典场景 |
| JSON Schema | 原生字典（dict） | 仅服务端协议约束，客户端无强校验 | 静默接受非法字段，原样输出字典 | 仅用于定制复杂底层协议或无 Python 代码环境 |
| @dataclass | 原生字典（dict） | 仅静态标记，客户端无强校验 | 静默接受非法字段，原样输出字典 | 功能定位与 TypedDict 重叠，通常不必特意选用 |

在真实的生产级 AI 应用中，大模型偶尔出现幻觉、漏掉字段或输出错误键名是无法彻底杜绝的概率事件。如果没有客户端的强校验防护，错误的数据就会顺着业务链路一路下渗，最终在数据库写入或下游计算环节引发难以排查的严重灾难。

因此，最终的工程选型结论非常清晰：**在企业级严谨业务中，无脑优先选用 Pydantic 作为唯一的结构化输出方案**；借助 Pydantic 抛出的 `ValidationError`，我们能够快速触发自动化重试或容错熔断，真正构建起鲁棒可靠的生产级智能体应用。

### 结构化结果提取的双轨演进

#### 原生结构化绑定机制

在大模型交互过程中，让模型稳定返回符合业务规范的对象，是接入自动化系统的刚需。现代 LangChain 推荐的标准范式是直接调用模型的 `with_structured_output` 方法。该接口在底层直接让模型理解给定的数据结构模式，并在推理完成后直接返回反序列化好的对象。

在使用 `with_structured_output` 时，可以通过传入参数 `include_raw` 控制返回粒度。该参数默认为 `False`，即只返回解析完成的目标对象；若将其显式设置为 `True`，返回的结构将从单一对象变为字典，包含更完备的原始通信上下文：

```python
import os
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from pydantic import BaseModel, Field
from rich import print as rprint

load_dotenv()

# 初始化模型
model = init_chat_model(
    "deepseek/deepseek-chat",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url=os.getenv("DEEPSEEK_BASE_URL")
)

# 定义业务数据契约
class Movie(BaseModel):
    title: str = Field(description="电影名称")
    year: int = Field(description="上映年份")

# 启用原始响应保留
structured_model = model.with_structured_output(Movie, include_raw=True)
response = structured_model.invoke("帮我介绍一下星际穿越这个电影")

rprint(type(response))
rprint(response)
```

当 `include_raw=True` 时，返回的字典对象包含三个核心字段：

1. `raw`：包含解析前的原始 `AIMessage` 实例。内部完整保留了模型的原始文本 `content`、Token 消耗统计（`token_usage`）以及模型层面的元数据。
2. `parsed`：解析成功后的目标对象实例（本例中为 `Movie` 类的实例）。
3. `parsing_error`：解析异常信息。当采用 Pydantic 格式校验失败时，若未捕获则可能抛出错误；在正常解析通过时，该字段值为 `None`。

> **提示**：如果业务链路只需要纯粹的数据对象，保持 `include_raw=False` 可以获得极简的对象调用体验；若系统需要统计 Token 计费或归档原始大模型交互记录，则应当开启 `include_raw=True`。

#### 传统输出解析器转换路径

在 LangChain 0.3 早期版本中，结构化输出的主流解法是依赖 LCEL（LangChain Expression Language）构建的输出解析器管道。其整体运行逻辑为：通过提示词模板向模型注入输出格式说明，模型生成符合规范的纯文本，最终由专门的解析器将文本反序列化为目标数据。

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser
from pydantic import BaseModel, Field

# 1. 提示词模板
prompt = ChatPromptTemplate.from_template("请介绍电影 {movie_name}，并以 JSON 格式输出电影的名称和上映年份。")

# 2. 基础模型
model = init_chat_model("gpt-4o", model_provider="openai")

# 3. 输出解析器
class MovieSchema(BaseModel):
    title: str = Field(description="电影名称")
    year: int = Field(description="上映年份")

parser = JsonOutputParser(pydantic_object=MovieSchema)

# 方式一：LCEL 链式调用
chain = prompt | model | parser
response_chain = chain.invoke({"movie_name": "星际穿越"})
print("LCEL 调用结果：", response_chain)

# 方式二：底层嵌套调用
prompt_value = prompt.invoke({"movie_name": "星际穿越"})
model_output = model.invoke(prompt_value)
response_nested = parser.invoke(model_output)
print("传统嵌套调用结果：", response_nested)
```

在实际执行上述传统解析器时，会暴露出生成后转换机制的固有缺陷：模型由于先自由生成长文本，解析器在从文本中提取 JSON 时，往往会附带产生非预期的冗余字段（例如偶发多出 `description` 或 `content` 字段，且字段命名随模型运行多次漂移）。

| 维度 | `with_structured_output` 绑定机制 | 传统输出解析器（`JsonOutputParser`） |
| :--- | :--- | :--- |
| **生效时机** | 在模型调用前在 API 契约层深度绑定 | 模型文本生成后的二次转换提取 |
| **输出稳定性** | 字段纯净，严格锁定 Schema 定义 | 易受模型自由发挥影响，偶发插入冗余字段 |
| **架构地位** | LangChain 1.0 首选推荐方案 | 早期版本主要手段，现作为特定场景补充 |
| **对象形态** | 直接返回 Pydantic 实例或结构化字典 | 经文本截取转换而来的字典 |

> **结论**：在当前的技术选型中，应当首推基于 Pydantic 类的 `with_structured_output` 方式，其通过在底层协议级约束格式，能够规避中间文本转换阶段产生的幻觉与格式漂移。

### 智能体核心架构与演进范式

#### 智能体定义与要素构成

AGI（通用人工智能，Artificial General Intelligence）被公认为人工智能演进的终极愿景。而在当下大模型的工程落地进程中，智能体（Agent）则是最核心的工程承载形态。构建现代大模型应用，本质上就是构建不同特化能力的智能体。

> **定义**：智能体（Agent）是以大语言模型为核心推理与决策引擎，深度整合记忆与工具调用，具备规划决策能力并能自主完成复杂任务的软件实体。

智能体系统的核心要素在工程实现中呈现出不同的存在状态：

```text
+-------------------------------------------------------------+
|                        用户输入 / 目标任务                    |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                      智能体核心控制循环                       |
|                                                             |
|  +-------------------------------------------------------+  |
|  |                 大语言模型推理与决策引擎                 |  |
|  |              （必选要素：负责生成内容与规划）            |  |
|  +-------------------------------------------------------+  |
|          |                                   ^              |
|          v                                   |              |
|  +-------------------+               +-------------------+  |
|  |     工具执行层    |               |     状态与记忆    |  |
|  | （几乎总是存在）  |               | （核心必备要素）  |  |
|  +-------------------+               +-------------------+  |
|          |                                   ^              |
|          +------------ 反馈调用结果 ----------+              |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                        最终整合响应输出                      |
+-------------------------------------------------------------+
```
*图说明：智能体架构以大模型为推理中枢，双向连接记忆状态与工具执行层，实现自主循环决策。*

1. **行动（Action）**：系统必须存在的要素。大模型对输入的理解、思维链推导以及生成内容的过程，就是最基本的推理行动。
2. **工具（Tools）**：几乎总是存在的要素。大语言模型的静态知识无法实时更新且不具备环境读写能力，工具调用的引入彻底突破了模型的能力边界。
3. **规划决策（Planning）**：有条件存在的要素。对于复杂的长链条任务，模型需要将其拆解为子任务并编排执行顺序；简单单一意图任务则无需冗余规划。
4. **记忆（Memory）**：最容易被忽视但工程上不可或缺的要素。维持多轮对话状态、上下文轨迹与知识关联，必须依赖记忆机制。

提炼到最简工程模型，赋能智能体自主进化的双核要素正是**工具**与**记忆**。

#### 框架创建模式的代际收敛

在 LangChain 0.x 时代，框架的设计哲学倾向于“针对特定场景创建特定类型”。开发者需要针对不同机制分别实例化特定的类：

- 推理思维链场景：`ReAct Agent`
- 结构化输出场景：专门的结构化 Agent 类
- 工具调用场景：专门的工具交互 Agent 类

在早期模式下，构建出的 Agent 对象本身并不能直接独立运行，开发者必须将其包裹进一个名为 `AgentExecutor` 的执行器组件中，再由 `AgentExecutor.invoke()` 驱动。这种模式导致 API 严重碎片化，开发者必须单独记忆各类型 Agent 的初始化参数，且难以在多智能体系统之间建立统一的编排调度。

随着 LangChain 1.0 的到来，框架完成了架构层面的大幅收敛，全面废弃了繁杂的特定 Agent 类与 `AgentExecutor`，改由统一的入口函数 `create_agent` 接管全局。其底层不再依赖旧式的硬编码执行循环，而是完全基于 LangGraph 的状态图编译机制构建，使复杂状态转移、重试以及后续的中间件扩展拥有了标准化的基础设施。

### 智能体实例化的模型装配

在 `create_agent` 的参数列表中，存在两个最核心的支柱参数：负责逻辑推理与决策的 `model`，以及负责扩展执行边界的 `tools`。针对决策大脑 `model` 的装配，框架提供了两种不同粒度的传入方式。

#### 字符串标识符装配

第一种方式是直接向 `model` 参数传入模型标识字符串。在字符串中可以通过斜杠指定提供商与具体模型名称：

```python
import os
from dotenv import load_dotenv
from langchain.agents import create_agent

# 必须加载环境变量以提供底层 API Key 与端点配置
load_dotenv()

# 通过字符串直接创建智能体
agent = create_agent(model="deepseek/deepseek-chat")

# 观察生成的智能体底层类型
print("Agent 底层类型：", type(agent))

# 导出并可视化底层计算图
graph = agent.get_graph()
# print(graph.draw_mermaid())
```

> **易错点**：传入字符串时，框架会在底层自动调用 `init_chat_model` 寻找对应的供应商驱动（例如 `ChatDeepSeek`）。该驱动会直接从系统环境变量中读取 `DEEPSEEK_API_KEY` 等参数。若未预先执行 `load_dotenv()`，程序将在实例化或调用阶段直接抛出缺少 API Key 的环境变量缺失异常。

通过打印 `type(agent)` 可以发现，返回的对象是 `langgraph.graph.state.CompiledStateGraph` 的实例。这验证了 LangChain 1.0 中智能体的底层本质：一个经过编译的状态图，其拓扑连接了输入起点、模型推理节点、工具调度节点与终点。

#### 显式模型对象装配

第二种方式是预先初始化具体的模型实例，再将该对象注入 `create_agent` 中。这种方式允许开发者显式传入特定的网络代理、超时时间或认证凭证：

```python
import os
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain_openai import ChatOpenAI
from langchain.agents import create_agent

load_dotenv()

# 途径 A：使用 init_chat_model 构造实例
model_init = init_chat_model("deepseek-chat", model_provider="deepseek")

# 途径 B：直接实例化特定驱动类
model_explicit = ChatOpenAI(
    model="gpt-4o",
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_BASE_URL")
)

# 传入显式模型对象
agent = create_agent(model=model_explicit)
```

两种传入方式在底层行为上最终殊途同归，字符串方式更加精炼快捷，显式对象传入则在复杂生产环境配置中拥有更高的控制自由度。

### 智能体调用与消息总线

#### 消息驱动的输入输出协议

智能体遵循 LangChain 标准的 Runnable 接口规范，通过调用 `invoke()` 执行驱动。与底层单纯调用大模型略有不同，智能体的输入与输出均被规范在字典结构的消息总线之中。

智能体的输入字典必须包含名为 `messages` 的键，其值是一个消息列表：

```python
{"messages": [消息条目1, 消息条目2, ...]}
```

在构造输入消息列表时，有两种书写方式：

1. **标准字典结构**：通过标准的键值对声明角色与内容，例如 `{"role": "user", "content": "你好"}` 或 `{"role": "system", "content": "..."}`。
2. **纯字符串简写**：在消息列表中直接放置纯文本字符串（例如 `["你好"]`）。系统在内部处理时会自动将其转译包装为 `HumanMessage` 实例。

智能体执行完毕后返回的同样是一个包含 `messages` 键的字典。返回的列表包含了本次交互生命周期中的所有完整会话轨迹，按时间顺序排列：用户的初始输入（`HumanMessage`）、模型的中间决策（`AIMessage`）、工具调用的结果载荷（`ToolMessage`）以及模型最终产出的汇总响应。

若需要提取最新的最终回复文本，应当通过索引 `-1` 获取列表最后一个元素，并读取其 `content` 属性：

```python
final_answer = response["messages"][-1].content
```

#### 对话与推理调用实践

通过具体的代码调用，可以清晰观察多角色消息在智能体总线中的流转过程：

```python
from rich import print as rprint

# 案例：注入角色设定的计算推理任务
input_payload = {
    "messages": [
        {
            "role": "system",
            "content": "你是一个精通数学的老师，擅长以通俗易懂的方式讲解数学问题。"
        },
        {
            "role": "user",
            "content": "100 + 20 * 3 = 多少？"
        }
    ]
}

response = agent.invoke(input_payload)
rprint(response)
```

输出的字典中，`messages` 列表依次包含三项：
1. `SystemMessage`：固化在上下文开头的角色提示词设定；
2. `HumanMessage`：用户的数学算式提问；
3. `AIMessage`：大语言模型推理得出的详细解答过程与最终结论 `160`。

在整个交互过程中，由于未装配额外工具，智能体仅依托模型自身的大脑算力即完成了闭环输出。

### 工具绑定与执行循环

#### 工具调用状态机机制

大语言模型与智能体之间存在着本质的分水岭：**大语言模型能够识别意图但无法行动，智能体既能识别意图又能直接执行**。

在单纯的大模型工具调用中，模型在识别到需要工具时，仅能生成一个包含 `tool_calls` 参数元数据的 `AIMessage`；模型自身不具备执行本地 Python 代码或发起网络请求的能力，以往必须由外部编写业务逻辑去调用 `tool.invoke()`，再将结果喂回模型。而智能体将大模型的推理决策与运行时的执行引擎融为一体，构成了自主的状态机循环：

```text
               +----------------------------------+
               |        用户输入 HumanMessage      |
               +----------------------------------+
                                 |
                                 v
+------------> +----------------------------------+
|              |        模型推理分析是否需工具     |
|              +----------------------------------+
|                   /                        \
|       [需调用工具] /                          \ [无需工具]
|                 v                            v
|  +------------------------------+   +------------------------------+
|  | 生成 AIMessage(含 tool_calls)|   | 最终生成 AIMessage 文本内容  |
|  +------------------------------+   +------------------------------+
|                 |                                  |
|                 v                                  v
|  +------------------------------+           [任务结束，返回输出]
|  | Agent 自动调度执行目标工具   |
|  +------------------------------+
|                 |
|                 v
|  +------------------------------+
|  |   生成执行结果 ToolMessage   |
|  +------------------------------+
|                 |
+-----------------+
```
*图说明：智能体内部的执行循环状态转移图，展示了从意图解析、工具调度到多轮再入模型的闭环逻辑。*

在 `create_agent` 中，工具的静态绑定通过 `tools` 参数实现，该参数接收一个工具实例列表。

#### 自定义工具的注册与生命周期

自定义工具可以直接通过 LangChain 提供的 `@tool` 装饰器修饰标准 Python 函数实现。函数的文档字符串（Docstring）遵循规范的书写格式，大模型正是依据函数的名称、整体描述以及参数说明来精准判定调用时机的。

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询天气的一个工具。
    
    Args:
        city: 具体的城市名称。
    """
    return f"{city}天气晴朗，温度是15℃"

# 绑定自定义工具并创建智能体
agent_weather = create_agent(
    model=model_explicit,
    tools=[get_weather]
)

# 发起天气查询提问
response_weather = agent_weather.invoke({
    "messages": [
        {"role": "system", "content": "你是一个查询天气的助手，根据用户的提问查询天气。"},
        {"role": "user", "content": "北京的天气如何？"}
    ]
})

rprint(response_weather)
```

观察上述调用的执行轨迹，`messages` 列表展示了完整的四阶段演进：

1. `HumanMessage`：用户询问“北京的天气如何？”。
2. `AIMessage`（第一轮）：模型做出决策，其 `content` 为空，但在 `tool_calls` 中明确指出需要调用 `get_weather`，提取参数 `{"city": "北京"}`。
3. `ToolMessage`：智能体执行环境自动调用 `get_weather` 函数，拦截返回值并包装为 `ToolMessage`（内容为“北京天气晴朗，温度是15℃”）。
4. `AIMessage`（第二轮）：智能体将 `ToolMessage` 作为新的上下文重新输入模型，模型据此生成面向用户的最终自然语言答复。

#### 内置搜索工具集成

除自定义函数外，智能体可无缝装配 LangChain 官方生态内置的丰富工具集。以广泛使用的 Tavily 搜索引擎为例，它专门为大模型智能体优化了检索结果结构。

使用内置工具前，需要在对应平台注册并获取 API Key，随后配置在环境变量中：

```python
import os
from langchain_community.tools.tavily_search import TavilySearch
from langchain.agents import create_agent

# 实例化内置搜索工具，限制最多返回 2 条关联条目
web_search = TavilySearch(
    max_results=2,
    tavily_api_key=os.getenv("TAVILY_API_KEY")
)

# 注册内置工具
agent_search = create_agent(
    model=model_explicit,
    tools=[web_search]
)

# 发起实时性问题检索
response_search = agent_search.invoke({
    "messages": [
        {"role": "user", "content": "帮我查询一下 2024 年诺贝尔物理学奖得主是谁？"}
    ]
})

rprint(response_search)
```

在执行内置搜索时，系统产生真实的网络 I/O，执行耗时明显增加。在第一轮生成的 `AIMessage` 中，模型识别并调用的内置工具默认标识名为 `tavily_search`。返回的 `ToolMessage` 携带了两条权威搜索摘要，模型随即将摘要事实提炼整合，产出精准的时效性回答。

#### 多工具协同调度与消息流分析

在面对复合业务意图时，智能体可以在 `tools` 列表中同时挂载多个功能异构的工具：

```python
from langchain_core.tools import tool

@tool
def get_news() -> str:
    """获取今天热点新闻的工具。"""
    return "今日热点：全球人工智能技术大会在杭州顺利召开。"

# 同时绑定天气与新闻两款工具
multi_agent = create_agent(
    model=model_explicit,
    tools=[get_weather, get_news]
)

# 发送包含双重意图的复合提问（使用简写消息传入）
query = ["你好，杭州的天气如何？今天有哪些新闻？"]
response_multi = multi_agent.invoke({"messages": query})
rprint(response_multi)
```

在此次执行中，智能体的内部状态机展现了高度的协同能力：
- 用户输入虽然是一句话，但大模型一次性规划出两个平行的工具调用意图；
- 首轮 `AIMessage` 的 `tool_calls` 字段内同时包含了 `get_weather`（参数 `city="杭州"`）与 `get_news` 两个指令；
- 智能体引擎并发执行两个工具，并相继生成两条独立的 `ToolMessage`；
- 模型汇总两个工具的执行结果，输出一段兼顾天气与新闻的完整自然语言答复。

### 本讲提到的题目

#### 复合意图下智能体消息链规模预测题

**题目描述**：

在同时绑定了 `get_weather`（天气查询工具）与 `get_news`（新闻获取工具）的智能体实例中，若调用 `invoke` 传入如下复合问题：

```python
["你好，杭州的天气如何？今天有哪些新闻？"]
```

在调用顺利执行完成并成功响应后，返回字典中的 `messages` 列表中总共有多少个 Message 对象？各自的具体类型与职责是什么？

**题目解析**：

整个交互过程严格遵循智能体的状态转移时序，消息流中累计生成 5 条消息：

1. **第 1 条（`HumanMessage`）**：由传入的简写字符串包装而成的用户原始输入，包含杭州天气与今日新闻的双重意图。
2. **第 2 条（`AIMessage`）**：模型的首轮决策消息。此时其 `content` 为空，但内部的 `tool_calls` 列表包含了 2 项工具调用请求（分别对应 `get_weather` 与 `get_news`）。
3. **第 3 条（`ToolMessage`）**：智能体执行 `get_weather(city="杭州")` 返回的执行结果消息。
4. **第 4 条（`ToolMessage`）**：智能体执行 `get_news()` 返回的执行结果消息。
5. **第 5 条（`AIMessage`）**：模型将上述两条 `ToolMessage` 的内容进行综合归纳后，生成的最终面向用户的自然语言回复。

**参考答案**：

响应结果的 `messages` 列表中共有 **5** 条消息。依次为：1 条 `HumanMessage`、1 条携带工具调用的 `AIMessage`、2 条分别承载执行结果的 `ToolMessage`、以及 1 条最终归纳回复的 `AIMessage`。

## 工具调用执行链路与 Agent 结构化输出策略
> 对应块：BLK13 | 覆盖分集：P55-P59 | 块标题（分集名）：《工具调用链路分析与ToolStrategy结构化策略》

在掌握了基础的工具定义、Agent 绑定与调用之后，一个核心的工程问题随之浮现：大语言模型与外部工具之间究竟是通过怎样的状态机协同工作的？当工具调用遭遇临时网络故障、需要连续多步推导，抑或是要求输出严格规范的业务数据时，底层的执行拓扑与消息载荷是如何流转的？

深入理解 LangChain 的执行机制，需要从底层的 ReAct 循环链路切入，厘清多轮工具交互与异常重试的内部时序，掌握 Agent 的身份标识与系统提示词规范，并彻底吃透基于伪工具机制实现的结构化输出策略。

---

### 工具调用执行链路与 ReAct 运行机理

LangChain 的 Agent 并非简单地进行单次问答，而是将底层大模型与外部工具组件结合，通过基于 LangGraph 的图结构状态机来编排整个执行流程。这种编排模式完整实现了经典的 ReAct 架构，通过推理与行动的交替迭代，推动复杂任务向前演进。

#### ReAct 状态循环与执行阶段

ReAct 架构的核心由两个词构成：`Reasoning`（推理）与 `Action`（行动）。在具体执行生命周期中，这一循环拆解为三个不可或缺的核心阶段：

1. **思考（Reasoning / Thought）**：底层大模型分析当前的对话上下文与任务目标，判断是否需要借助外部工具来获取额外事实。若需要，模型在返回的响应中构建 `tool_calls` 参数列表，输出带有调用指令的 `AIMessage`。
2. **行动（Action）**：调度系统拦截到包含 `tool_calls` 的消息后，提取工具名称与入参，派发给对应的具体函数执行。
3. **观察（Observation）**：工具函数执行完成并返回数据，系统将执行结果包装为 `ToolMessage`，注入到消息历史中回传给大模型。
4. **决策判定（Decision）**：大模型接收包含工具结果的完整上下文，再次进行推理。若模型判定任务已满足，则输出不带 `tool_calls` 的最终 `AIMessage`，循环终止（Finish）；若判定信息仍不充分，则继续发起下一次工具调用。

```text
               +----------------------------------+
               |      用户输入 (HumanMessage)       |
               +-----------------+----------------+
                                 |
                                 v
+-------------------------> [ 模型思考 ] <--------------------------+
|                                |                                  |
|            +-------------------+-------------------+              |
|            | 包含 tool_calls                       | 无 tool_calls |
|            v                                       v              |
|     +--------------+                       +---------------+      |
|     |  AIMessage   |                       |   最终结束    |      |
|     | (请求调工具) |                       |  (输出结果)   |      |
|     +------+-------+                       +---------------+      |
|            |                                                      |
|            v                                                      |
|     +--------------+                                              |
|     |  工具执行    |                                              |
|     |   (Action)   |                                              |
|     +------+-------+                                              |
|            |                                                      |
|            v                                                      |
|     +--------------+                                              |
|     | ToolMessage  |                                              |
|     | (Observation)| ---------------------------------------------+
|     +--------------+
```
上图展示了基于 ReAct 循环的状态转移拓扑：大模型基于观察结果反复迭代，直至产出无工具调用的终态响应。

> **定义**：ReAct（Reasoning and Acting）是一种将大语言模型的逻辑推理能力与外部环境交互行动相结合的执行范式。模型通过“思考-行动-观察”三元状态环，动态分解任务并在不确定环境中实现多步收敛。

#### 递进调用与故障重试机制

在真实的工程交互中，工具调用往往不会在单次往返中结束，主要表现为两种典型的循环时序：

一种是**工具递进调用（Chained Tool Calling）**。此时任务具备链式依赖，前一个工具的输出构成后一个工具的输入依据。例如接收到需求“找出当前最流行的无线耳机并检查它的库存”时，执行链路如下：

1. **第一轮推理**：模型接收用户问题，判断必须首先获取热销品名，因此向工具调度器发起 `search_products` 检索；
2. **第一轮观察**：工具返回检索结果，识别出当前排名第一的特定无线耳机型号；
3. **第二轮推理**：模型在上下文中感知到耳机型号已确定，但库存未知，随即发起针对第二工具 `check_stock` 的调用；
4. **第二轮观察**：库存查询工具返回具体数值（如 `10` 件）；
5. **终态收敛**：模型结合两轮观察的事实，整合生成最终的自然语言总结，不再携带工具指令，完成闭环。

另一种是**同一工具的反复调用与重试机制（Tool Retrying）**。当外部第三方 API 遇到并发受限、网络抖动或临时服务维护时，工具可能返回故障提示，此时 Agent 可以在提示词的引导下进行自主重试。

```python
from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from rich import print as rprint

flag = 1

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气状况。"""
    global flag
    if flag < 3:
        flag += 1
        return "天气服务暂时不可用，请稍后重试"
    else:
        return f"{city}天气晴朗，气温 22 摄氏度"

model = init_chat_model("gpt-4o-mini", model_provider="openai")
tools = [get_weather]

system_prompt = (
    "你是一个天气助手。当天气查询工具返回临时故障时，"
    "请尝试重新查询。如果连续 3 次查询均失败，再向用户说明情况。"
)

agent = create_agent(model=model, tools=tools, system_prompt=system_prompt)

response = agent.invoke({"messages": [{"role": "user", "content": "帮我查一下杭州的天气"}]})
```

在这段重试逻辑中，全局变量 `flag` 模拟了前两次调用因服务不可用而熔断的场景。执行时，控制台消息时序呈现出清晰的多轮往返：

1. 初始调用：模型产生包含 `get_weather(city="杭州")` 的 `AIMessage`；
2. 首次回传：`ToolMessage` 内容为“天气服务暂时不可用，请稍后重试”，`flag` 递增至 2；
3. 二次调用：模型根据系统提示词判断需重试，再次发起 `get_weather` 调用；
4. 二次回传：`ToolMessage` 依然反馈服务不可用，`flag` 递增至 3；
5. 三次调用：模型执行第三次重试，工具满足分支条件，返回“杭州天气晴朗”；
6. 最终收尾：模型根据成功返回的天气数据生成终态答复，调用链正式截断。

### 工具调用工程常见问题与调优经验

在 Agent 投入生产环境的运行过程中，工具选择错误、工具漏调以及无限死循环是发生率最高的三类工程异常。针对这些场景，需要建立严格的诊断与约束规范。

#### 工具匹配与未调用原因排查

Agent 对外部工具的路由寻址，完全依托于工具定义中的元数据。

> **结论**：Agent 选择工具的唯一事实依据是工具的 `description` 与函数 docstring 文档注释。底层大模型在推理阶段将用户意图与各工具的功能描述进行语义相似度与适用性匹配，以此计算出应该触发哪一个函数。

当出现“预期该调工具却未调用”的现象时，排查顺序应当遵循以下三个维度：

1. **工具描述语焉不详**：docstring 未能清晰陈述函数输入前置条件、功能边界及应用场景，模型无法判定当前问题是否在其处理能力范畴内；
2. **用户意图表述模糊**：用户输入的提问缺乏必要实体或触发词，语义偏离工具定义的作用域；
3. **模型参数知识自满**：大模型根据预训练权重认为自身已掌握充足信息，推断无需通过外部工具辅助即可独立回答，从而越过工具直接响应。

#### 工具误选防范与调用频次限制

当 Agent 挂载的工具集逐渐扩大时，极易诱发工具误选与路由混乱。

> **易错点**：为单个 Agent 挂载过多工具是导致调用失准的首要根因。在实际工程落地中，**单个 Agent 绑定的工具数量应严格控制在 2 到 5 个为最佳**。若一次性挂载数十个工具，且各工具间的职责边界存在重合，模型的注意力分配将被严重稀释，导致调用准确率剧烈波动。

为消除工具选错与震荡，必须在工具的 docstring 中确立互斥的功能边界，并在系统提示词中显式列出不同工具的互斥使用场景。

此外，Agent 在理论上并不限制工具调用的次数，但若缺乏安全防线，遇到网络死循环或逻辑分支无法收敛时，极易造成上下文耗尽与高额调用费用消耗。限制工具调用的关键参数是运行配置中的 `recursion_limit`。

```python
# 通过 config 配置项将整个 Agent 的最大执行递归层数硬性截断为 5 次
response = agent.invoke(
    {"messages": [{"role": "user", "content": "查询最新技术资讯"}]},
    config={"recursion_limit": 5}
)
```

在底层执行图内部，每一次“模型思考 -> 工具执行”都会消耗图的一个递归步长。通过将 `recursion_limit` 设置为指定阈值（如 5），一旦因模型逻辑死循环或工具返回异常导致调用超出限制，系统将直接抛出异常中断执行，确保系统具备确定的资源安全边界。

### Agent 基础属性与运行时配置

在构建工业级复杂应用时，Agent 需要从单个临时的执行单元升级为可溯源、可管控的独立实体。LangChain 在 `create_agent` 工厂函数中提供了名称与系统提示词等关键控制参数。

#### Agent 标识命名与应用场景

通过为 Agent 显式赋予名称，能够在整个执行拓扑中沉淀稳定的身份标识：

```python
agent = create_agent(
    model=model,
    tools=tools,
    name="agent01"
)
```

当为 Agent 指定了 `name` 属性后，执行返回的 `AIMessage` 内部将携带该名称字段。通过遍历返回的上下文消息列表并调用 `pretty_print()`，可以清晰观察到该标识的存在：

```text
================================== Ai Message ==================================
Name: agent01

杭州今天天气晴朗，气温适宜。
```

Agent 的显式命名在单智能体简单交互中并不显山露水，但在系统化工程建设中承担着关键职责：

1. **多智能体（Multi-Agent）协同调度**：在复杂架构中，不同 Agent 负责规划、检索、编码或质检。显式的 `name` 是区分不同计算节点、编排通信拓扑的核心主键；
2. **流式输出分发（Streaming Routing）**：在前端流式渲染吐字时，事件流携带的 `name` 能够让客户端无歧义地判定当前 Token 片段由哪一个 Agent 输出，从而渲染至对应的会话面板；
3. **身份标识与审计追踪**：会话历史落盘、安全审计日志以及回放系统依赖 `name` 判定发言角色与权限边界；
4. **链路可观测性（LangSmith Tracing）**：在分布式调用链监控中，可直观在链路树（Trace Tree）中快速折叠或下钻特定 Agent 的耗时与调用细节；
5. **组件化封装**：将具备专属名称的 Agent 作为黑盒服务进行二次组合与微服务化部署。

#### 系统提示词配置规范与消息层级表现

系统提示词是决定 Agent 角色定位与行为规范的核心抓手。在 `create_agent` 中，支持通过 `system_prompt` 参数注入配置：

```python
from langchain_core.messages import SystemMessage

# 方式一：直接传递纯文本字符串
agent = create_agent(model=model, tools=tools, system_prompt="你是一个专业的天气分析助手。")

# 方式二：传递显式的 SystemMessage 消息对象
agent = create_agent(model=model, tools=tools, system_prompt=SystemMessage(content="你是一个数学运算助手。"))
```

在系统提示词的工程编写上，推荐涵盖三项核心要素：
1. **明确角色定位**：限定 Agent 扮演的专家角色及业务领域边界；
2. **界定输出要求**：规定结果呈现的语调、文本格式或排版风格；
3. **规范工具触发时机**：明确声明在何种业务判定下必须使用何种工具，以及遇错时的降级方案。

> **易错点**：无论使用字符串还是 `SystemMessage` 对象设置 `system_prompt`，在 Agent 调用完成返回的 `response["messages"]` 列表中，**绝对不会**看到该系统提示词独立出现在消息数组内。系统提示词在底层直接挂载到大模型的系统上下文通道中，返回的消息列表默认从用户的 `HumanMessage` 开始呈现。

以下是一个具备多步加法计算调用的典型多轮交互场景：

```python
from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain_core.messages import SystemMessage

@tool
def add(a: int, b: int) -> int:
    """计算两个整数之和。"""
    return a + b

model = init_chat_model("gpt-4o-mini", model_provider="openai")
tools = [add]
system_message = SystemMessage(content="你是一个数学助手，专门解决日常算术问题。")

agent = create_agent(model=model, tools=tools, system_prompt=system_message)
response = agent.invoke({"messages": [{"role": "user", "content": "计算 10 加 20 再加 30 的结果是多少"}]})
```

在该案例中，大模型必须处理多重依赖关系。分析其输出消息序列，可以清晰看到工具调用 ID 的对应时序：

```text
[HumanMessage] content='计算 10 加 20 再加 30 的结果是多少'
[AIMessage] tool_calls=[{'name': 'add', 'args': {'a': 10, 'b': 20}, 'id': 'call_lid'}]
[ToolMessage] tool_call_id='call_lid' content='30'
[AIMessage] tool_calls=[{'name': 'add', 'args': {'a': 30, 'b': 30}, 'id': 'call_9vr'}]
[ToolMessage] tool_call_id='call_9vr' content='60'
[AIMessage] content='计算结果为：10 + 20 + 30 = 60。'
```

系统提示词在此处默默发挥着指引作用，确保模型专注于算术逻辑，而不会在返回的历史中引入冗余的系统文本声明。

### Agent 结构化输出架构与宏观策略

当业务系统要求 Agent 输出确定性的业务实体（如 JSON 数据、强类型数据对象）以供下游微服务解析时，传统的纯文本响应便不再适用。

#### 模型层与 Agent 层结构化机制对比

在 LangChain 中，大模型（ChatModel）本身具备结构化输出能力，而 Agent 作为组合系统同样支持结构化输出。两者在设计哲学与运行时机制上存在本质区别：

| 维度 | 模型层结构化（ChatModel） | Agent 层结构化（Agent） |
| :--- | :--- | :--- |
| **作用对象** | 底层大模型实例 | 高阶 Agent 实例 / 状态图 |
| **解析时机** | 单次调用生成 `AIMessage` 时即刻解析 | 完成所有多轮工具交互后，在任务终态进行格式化 |
| **绑定方法** | `model.with_structured_output(...)` | `create_agent(..., response_format=...)` |
| **产物位置** | 直接作为 `model.invoke()` 的返回值 | 存储在响应字典的 `response["structured_response"]` 键中 |

模型层的结构化输出是一锤子买卖，模型只能依靠自身记忆直接输出目标结构；而 Agent 层的结构化输出则具备极强的复合能力——它可以先调取外部数据库、调用第三方 API 搜集充分的动态事实，最后在任务结束时将所有多轮推导事实一并封装为结构化对象输出。

#### 结构化输出的四种宏观策略

在配置 Agent 的 `response_format` 参数时，LangChain 提供了四种宏观策略：

1. **`ProviderStrategy`（供应商原生策略）**：依赖具体模型供应商特有的结构化能力（例如 OpenAI 的 JSON Schema Mode / Structured Outputs 原生接口）；
2. **`ToolStrategy`（工具调用策略）**：通过“伪工具（Pseudo Tool）”调用机制实现结构化输出。**这是整个生态中通用性最强、工业应用最广泛的策略**。只要模型支持 Function Calling，便能无视厂商底层协议差异无缝使用；
3. **`AutoStrategy`（自动适配策略）**：根据绑定的底层模型元数据，自动在原生策略与工具调用策略之间仲裁切换；
4. **`None`**：关闭结构化输出通道，返回纯文本形式。

`ToolStrategy` 之所以能实现跨模型的极高通用性，核心在于其底层的“伪工具”运行机理：

```text
+---------------------------------------------------------------------------------+
|                               Agent 运行生命周期                                 |
|                                                                                 |
| 真实业务阶段:                                                                   |
| [HumanMessage] -> [调业务工具 A] -> [ToolMessage A] -> [调业务工具 B] -> ...    |
|                                                                                 |
| 结构化收尾阶段 (ToolStrategy 介入):                                              |
| 模型发起伪工具调用:                                                             |
| AIMessage(tool_calls=[{'name': 'StructuredOutput', 'args': {...}}])             |
|                        |                                                        |
| 系统生成对应观察结果:  v                                                        |
| ToolMessage(name='StructuredOutput', content='...')                             |
|                        |                                                        |
| 解析并挂载到终态输出:  v                                                        |
| response['structured_response'] = <解析成功的结构化数据对象>                    |
+---------------------------------------------------------------------------------+
```
上图阐明了 ToolStrategy 的执行本质：系统自动注册一个匹配目标 Schema 的伪工具，迫使模型在最终收敛时通过工具调用的标准协议回传目标数据。

`ToolStrategy` 包含三个核心配置参数：
- **`schema`**：定义输出数据规范的核心载体，支持 Pydantic 模型、TypedDict、JsonSchema、dataclass 以及 Union 联合类型；
- **`tool_message_content`**：可选参数，用于自定义伪工具返回的 `ToolMessage` 文本内容；
- **`handle_errors`**：指定校验失败时的重试机制，控制当模型输出字段不合规时如何向模型抛出修正提示。

---

### ToolStrategy 结构化输出的多模式实战

在深入工程落地时，`ToolStrategy` 的 `schema` 参数允许开发者使用多种 Python 语法体系来定义业务规范。以下围绕真实的客户数据分析业务，分别呈现四种定义模式的落地实现与对比。

#### Pydantic 数据规范与多工具联动链路

Pydantic 是 Python 生态中最主流的强类型数据验证库。在选择模型服务商时需注意底层的支持力度：

> **提示**：不同大模型服务商对 Pydantic 的高级特性（如复杂的默认值、类型约束限制）支持存在差异。CloseAI 等聚合中转网关在基础调用上成本低廉且易于接入，但在深层结构化约束校验时偶尔会出现兼容性损耗；而 OpenRouter 等海外原生网关对结构化参数的协议对齐更加严格。开发者应根据实际业务场景在易用性与完备性之间权衡。

在纯信息抽取场景下，直接通过 `ToolStrategy` 指定 Pydantic 类型即可完成端到端结构化收敛：

```python
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from rich import print as rprint

class ContactInfo(BaseModel):
    name: str = Field(description="联系人姓名")
    email: str = Field(description="电子邮箱地址")
    phone: str = Field(description="联系电话")

model = init_chat_model("gpt-4o-mini", model_provider="openai")
agent = create_agent(
    model=model,
    response_format=ToolStrategy(schema=ContactInfo)
)

response = agent.invoke({
    "messages": [{"role": "user", "content": "小明的邮箱是 xiaoming@example.com，电话是 13012341234。"}]
})

rprint(response["structured_response"])
```

控制台将输出一个强类型的 `ContactInfo` 类实例对象，数据已自动映射到对象属性中。

而在现实业务中，最强大的场景是**真实业务工具调用与终态结构化输出的深度联动**。以下案例演示了“先查客户数据库 -> 判断等级发感谢邮件 -> 最终生成规范分析报告”的完整体系：

```python
from typing import Literal
from pydantic import BaseModel, Field
from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from rich import print as rprint

@tool
def search_customer_db(name: str) -> dict:
    """查询客户核心数据库，获取客户的基础等级与消费信息。"""
    # 模拟内部数据库存储
    mock_db = {
        "张三": {"level": "VIP", "active": "高", "spending": "高"},
        "李四": {"level": "普通", "active": "中", "spending": "低"}
    }
    return mock_db.get(name, {"error": "查无此人"})

@tool
def send_thank_email(name: str) -> str:
    """向 VIP 客户发送尊享感谢邮件。"""
    return f"已成功向 VIP 客户 {name} 发送感谢邮件"

class CustomerAnalysis(BaseModel):
    name: str = Field(description="客户姓名")
    level: Literal["VIP", "普通"] = Field(description="客户等级")
    recent_active: str = Field(description="近期活跃度")
    spending_level: str = Field(description="消费水平")
    email_sent: bool = Field(description="是否已发送感谢邮件")

model = init_chat_model("gpt-4o-mini", model_provider="openai")
tools = [search_customer_db, send_thank_email]

system_prompt = (
    "请分析指定客户的运营情况。你必须严格遵循以下流水线：\n"
    "1. 优先使用 search_customer_db 工具检索客户数据；\n"
    "2. 若客户为 VIP 客户，必须调用 send_thank_email 发送感谢邮件；普通客户绝不发送；\n"
    "3. 在完成上述工具交互后，基于真实查询与执行结果，生成最终的结构化分析报告。\n"
    "注意：若客户不存在，返回空对象且不得发送邮件。"
)

agent = create_agent(
    model=model,
    tools=tools,
    system_prompt=system_prompt,
    response_format=ToolStrategy(CustomerAnalysis)
)
```

> **易错点**：为什么必须在 `system_prompt` 中严格规定执行顺序？因为 `ToolStrategy` 的本质也是一个伪工具。如果提示词未加约束，大模型在接收到任务时，往往会贪婪地直接调用输出报告的伪工具一步到位，导致真实的数据库查询与发信工具被彻底跳过！因此，必须在提示词中确立“先查库、再发信、后报告”的刚性顺序。

对该 Agent 进行双向测试，其内部时序呈现出显著的自适应分支路径：

##### VIP 客户（张三）执行链路
1. `HumanMessage`：分析张三客户；
2. `AIMessage`：发起真实工具调用 `search_customer_db(name="张三")`；
3. `ToolMessage`：返回 `{"level": "VIP", "active": "高", "spending": "高"}`；
4. `AIMessage`：识别为 VIP，触发第二真实工具 `send_thank_email(name="张三")`；
5. `ToolMessage`：返回“已成功向 VIP 客户张三发送感谢邮件”；
6. `AIMessage`：真实工具全部执行完毕，触发终态伪工具调用 `customer_analysis(...)`；
7. `ToolMessage`：伪工具完成数据捕获；
8. 最终响应：`response["structured_response"]` 包含强类型对象，其中 `email_sent=True`。

##### 普通客户（李四）执行链路
1. `HumanMessage`：分析李四客户；
2. `AIMessage`：发起真实工具调用 `search_customer_db(name="李四")`；
3. `ToolMessage`：返回 `{"level": "普通", "active": "中", "spending": "低"}`；
4. `AIMessage`：识别为普通客户，模型主动剪枝跳过发信工具，直接触发终态伪工具调用；
5. `ToolMessage`：伪工具完成数据捕获；
6. 最终响应：`response["structured_response"]` 包含强类型对象，其中 `email_sent=False`。

#### TypedDict 字典约束与原生 JSON 兼容

在很多基于原生字典传递的系统或低延迟数据服务中，开发者并不希望引入 Pydantic 的类实例化开销，而是希望直接获得标准 Python 字典格式。此时可以使用标准库的 `typing.TypedDict`。

```python
from typing import TypedDict, Annotated, Literal
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from rich import print as rprint

class ContactInfoTypedDict(TypedDict):
    name: Annotated[str, ..., "联系人姓名"]
    email: Annotated[str, ..., "电子邮箱地址"]
    phone: Annotated[str, ..., "联系电话"]

class CustomerAnalysisTypedDict(TypedDict):
    name: Annotated[str, ..., "客户姓名"]
    level: Annotated[Literal["VIP", "普通"], ..., "客户级别"]
    recent_active: Annotated[str, ..., "近期活跃度"]
    spending_level: Annotated[str, ..., "消费水平"]
    email_sent: Annotated[bool, ..., "是否发送感谢邮件"]
```

在 `TypedDict` 规范中，字段描述必须通过 `Annotated` 进行元数据修饰。其中第二个参数 `...`（Ellipsis 省略号）代表必填约束，第三个参数传入对字段的文字说明。

```python
agent = create_agent(
    model=model,
    tools=tools,
    system_prompt=system_prompt,
    response_format=ToolStrategy(CustomerAnalysisTypedDict)
)

response = agent.invoke({"messages": [{"role": "user", "content": "请分析李四客户"}]})
rprint(response["structured_response"])
```

> **结论**：使用 `TypedDict` 作为 Schema 时，底层伪工具调用的链路逻辑与 Pydantic 完全相同，但最终写入 `response["structured_response"]` 的结果不再是自定义类实例，而是标准的原生 Python 字典（JSON 兼容格式）。

#### JsonSchema 原生模式与维护成本评估

除了 Python 类型注解外，`ToolStrategy` 还允许直接传入原生的 JSON Schema 字典来描述约束：

```python
contact_json_schema = {
    "title": "ContactInfo",
    "description": "联系人基础信息结构",
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "联系人姓名"},
        "email": {"type": "string", "description": "电子邮箱地址"},
        "phone": {"type": "string", "description": "联系电话"}
    },
    "required": ["name", "email", "phone"]
}

customer_json_schema = {
    "title": "CustomerAnalysis",
    "description": "客户综合运营分析报告",
    "type": "object",
    "properties": {
        "name": {"type": "string", "description": "客户姓名"},
        "level": {
            "type": "string",
            "enum": ["VIP", "普通"],
            "description": "客户级别"
        },
        "recent_active": {"type": "string", "description": "近期活跃度"},
        "spending_level": {"type": "string", "description": "消费水平"},
        "email_sent": {"type": "boolean", "description": "是否发送感谢邮件"}
    },
    "required": ["name", "level", "recent_active", "spending_level", "email_sent"]
}

agent = create_agent(
    model=model,
    tools=tools,
    system_prompt=system_prompt,
    response_format=ToolStrategy(customer_json_schema)
)
```

尽管原生 JSON Schema 能够产出合规的字典结果，但在实际工程架构中应尽量避免手动书写：
1. **书写极其繁重**：嵌套层次深，字段多时极易出现格式与键名遗漏；
2. **缺乏静态类型检查**：IDE 无法对字典键值提供补全与代码重构支持；
3. **完全可被替代**：若目标输出形式是 JSON 字典，使用 `TypedDict` 能以优雅直观的 Python 原生语法获得完全相同的输出效果。

#### 数据类 dataclass 模式与四种规范横向对比

对于追求轻量化、不愿引入第三方依赖但仍希望获得对象化属性访问体验的项目，标准库的 `dataclass` 是理想的选择：

```python
from dataclasses import dataclass
from typing import Literal
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from rich import print as rprint

@dataclass
class ContactInfoDataClass:
    name: str
    email: str
    phone: str

@dataclass
class CustomerAnalysisDataClass:
    name: str
    level: Literal["VIP", "普通"]
    recent_active: str
    spending_level: str
    email_sent: bool

agent = create_agent(
    model=model,
    tools=tools,
    system_prompt=system_prompt,
    response_format=ToolStrategy(CustomerAnalysisDataClass)
)

response = agent.invoke({"messages": [{"role": "user", "content": "请分析张三客户"}]})
rprint(response["structured_response"])
```

使用 `@dataclass` 声明的数据结构不需要继承任何基类，解析结果将直接实例化为数据类对象，支持直接通过属性点语法（如 `result.name`）访问。

综合考察上述四种在 `ToolStrategy` 中指定 Schema 的方式，其工程特性对比如下：

| Schema 类型 | 依赖来源 | 运行时输出产物类型 | 强类型静态校验 | 适用业务场景推荐 |
| :--- | :--- | :--- | :--- | :--- |
| **Pydantic** | 第三方库（`pydantic`） | Pydantic Model 实例对象 | 支持，具备强大校验规则 | 复杂业务校验、严苛数据治理、大型企业系统 |
| **TypedDict** | 标准库（`typing`） | 原生 Python 字典（JSON） | 支持键名与类型推导 | 轻量字典交互、前后端 JSON 直接透传 |
| **dataclass** | 标准库（`dataclasses`） | 自定义 dataclass 实例对象 | 支持对象属性点语法 | 零外部依赖、注重纯粹对象化访问的系统 |
| **JsonSchema** | 无（原生 Python `dict`） | 原生 Python 字典（JSON） | 不支持，手动维护成本极高 | 仅用于跨语言协议动态组装，日常开发不推荐 |

在实际项目选型时，应优先采用 Pydantic 应对强校验场景，选用 TypedDict 应对轻量级字典流通场景，从而在保证类型安全的同时，兼顾代码的可读性与工程维护成本。

## 智能体异常处理、流式输出与综合助手实战
> 对应块：BLK14 | 覆盖分集：P60-P63

在前面的学习中，我们通过 `ToolStrategy` 的 `schema` 参数实现了结构化输出，让智能体具备了按照预设契约返回标准数据模型的能力。然而在真实业务开发中，结构化输出底层的交互机制会暴露出新的问题：底层用于传递结构化数据的伪工具消息往往过于冗长，无谓地消耗了大量 Token；同时，由于大语言模型本身的概率输出特性，生成的响应并不总能完美契合验证规则，一旦出错整个执行链便可能直接崩溃中断。

此外，当智能体需要执行复杂的工具调用与多步推理时，采用单次阻塞式的调用方式会让终端用户陷入漫长且无反馈的等待。如何让智能体在发生异常时具备自愈与优雅降级能力，如何根据不同的业务端侧需求实时流式推送执行进度，以及如何将模型、工具链、提示词与记忆机制整合成一个健壮的高内聚智能应用，是构建生产级智能体必须跨越的核心门槛。

### 结构化输出的工具消息内容定制

#### 伪工具消息机制与冗余内容痛点

我们在配置 `ToolStrategy` 进行结构化输出时，LangChain 底层实际上采用了一种“伪工具调用（Fake Tool Call）”的机制：框架会将预定义的 Pydantic 数据契约转换为大模型能够理解的工具描述注入提示词，当大模型响应并触发该结构提取时，系统底层会生成一条匹配的 `ToolMessage` 消息对象。

```text
[用户输入文本] ---> [大模型评估并触发结构提取]
                           |
                           v
          [生成 AIMessage: 包含伪工具调用请求]
                           |
                           v
          [框架底层注入对应的 ToolMessage]
                           |
            +--------------+--------------+
            |                             |
            v                             v
     [默认未定制行为]              [显式配置参数]
ToolMessage.content = 完整 JSON    ToolMessage.content = "已成功抽取信息"
(数据体积大、浪费大量 Token)       (语义清晰友好、大幅节约 Token)
            |                             |
            +--------------+--------------+
                           v
         [最终 structured_response 保留真实解析对象]
```

图解说明：伪工具消息是结构化提取过程中的协议中间件，`ToolMessage.content` 仅用于填充会话历史中的工具反馈字段，而最终结构化数据由独立的 `structured_response` 字段承载。

在默认未配置任何定制参数时，这个 `ToolMessage` 的 `content` 字段会自动填充大模型生成的完整结构化响应文本（通常是一整串 JSON 格式的明文字符串）。如果提取的数据结构字段众多、嵌套层级深，该字符串在整个会话上下文链条中就会占据极大的篇幅。这不仅导致上下文冗长繁杂，更会在后续的多轮追问中无谓消耗大量不必要的上下文 Token。

#### tool_message_content 参数应用与 Token 节约

为了解决默认消息冗长的问题，`ToolStrategy` 提供了 `tool_message_content` 参数。我们可以通过传入简明、自然的人类可读文本（例如 `"已成功抽取信息"` 或 `"格式化输出成功"`），直接替换掉底层生成的冗余 JSON 字符。

```python
from pydantic import BaseModel, Field
from langchain.agents.strategies import ToolStrategy
from langchain.agents import create_agent

class ContactInfo(BaseModel):
    name: str = Field(description="联系人姓名")
    email: str = Field(description="电子邮箱")

# 场景一：未配置 tool_message_content（默认行为）
strategy_default = ToolStrategy(
    schema=ContactInfo
)

# 场景二：配置 tool_message_content 定制友好消息
strategy_optimized = ToolStrategy(
    schema=ContactInfo,
    tool_message_content="已成功抽取信息"
)
```

在实际执行时，许多开发者容易产生一个顾虑：把 `content` 替换成一句简短的中文提示后，模型真正抽取得出的结构化数据会不会丢失？答案是**没有任何影响**。因为最终的结构化解析对象会被安全完整地保存在执行结果的 `structured_response` 容器中，它完全不依赖 `ToolMessage.content` 文本字段的存在与否。

> **提示**：`tool_message_content` 参数具有条件触发机制。该文本仅在工具被模型正常且成功调用时才会显式呈现在 `ToolMessage` 中；如果调用发生异常，该字段仍会保留真实的错误信息以辅助系统定位。

通过这种方式，我们以最简短自然的描述替代了繁琐的数据载荷，在保留完整提取结果的同时，有效压低了多轮上下文中的 Token 消耗。

### 结构化输出的异常处理机制与重试策略

#### 结构化输出异常的五种处理策略

受限于大语言模型推理能力的波动性，模型输出的内容在某些边界条件下很可能不符合严格的 Pydantic 类型约束，或者误解了指令从而返回了不符合预期的工具请求。为了避免整个系统因局部校验失败而抛错崩溃，`ToolStrategy` 内置了 `handle_errors` 参数，提供了五种由浅入深的容错控制策略：

| 处理策略配置方式 | 运行时机制 | 适用业务场景 |
| :--- | :--- | :--- |
| `True`（默认策略） | 捕获所有格式异常，使用内置错误提示词自动发起重试 | 绝大多数通用业务场景，追求自动纠错与高容错性 |
| `False` | 严格关闭自动重试，捕获到任何格式异常均直接抛出并中断执行 | 开发调试排查、对输出质量有严苛要求、禁止重试开销的场景 |
| 静态字符串（`str`） | 捕获所有异常，将错误内容覆盖为指定的友好提示并驱动重试 | 具有明确业务导向的场景，向模型提供统一的人工引导文案 |
| 指定异常类型（`Exception Type`） | 精准捕获指定异常类并重试，其余未知异常立即向外抛出 | 需对部分预期内错误自动恢复、同时防范未知异常隐蔽传递的场景 |
| 自定义函数（`Callable`） | 接收捕获的异常对象，由开发者按需执行分支判断并动态返回提示 | 生产级复杂系统，需精细化记录日志并针对不同错误动态引导模型纠错 |

#### 异常捕获与抛出的布尔控制

当 `handle_errors` 设置为 `True` 时（也是系统默认缺省值），框架会开启全局异常容错机制。一旦大模型返回的数据未能通过结构化验证，LangChain 内部的错误提示模板会立即介入，将错误详情格式化为一条新的反馈消息回传给模型，提示模型指出具体解析错误并要求其根据规则重新生成。该重试过程会循环进行，直到数据完全契合 Schema 规范，或触发最大重试次数上限为止。

相反，如果将 `handle_errors` 显式设为 `False`，框架将彻底关闭底层的所有自动重试逻辑。任何输出格式不匹配或工具调用冲突都会立即化作 Python 运行时异常向上抛出，中断当前的执行进程。

```python
# 策略一：开启默认自动容错与重试
strategy_retry = ToolStrategy(
    schema=ContactInfo,
    handle_errors=True
)

# 策略二：严格抛出，遇到错误立即中断
strategy_strict = ToolStrategy(
    schema=ContactInfo,
    handle_errors=False
)
```

> **易错点**：在对调用时延敏感或 Token 预算极度受限的环境中，盲目依赖 `handle_errors=True` 可能会导致多次连续重试，带来不可控的计费与耗时增长；而在生产稳定运行的脚本中盲目设置为 `False`，又容易因模型的偶发格式漂移造成链路大面积中断。

#### 静态文本友好的异常提示

在许多特定业务中，系统自带的默认英文堆栈提示对大模型并不友好，无法给模型提供清晰的业务上下文引导。此时，可以将 `handle_errors` 设置为一个具体的静态字符串（例如 `"请检查输入的数据"`）。

```python
# 策略三：覆盖默认错误内容为固定引导字符串
strategy_custom_string = ToolStrategy(
    schema=ContactInfo,
    handle_errors="请检查输入的数据"
)
```

这种机制的工作原理类似于经典控制语句：
```python
try:
    execute_structure_extraction()
except Exception:
    print("请检查输入的数据")
```
当大模型出现格式或逻辑解析错误时，`ToolMessage` 的内容会被静默替换成开发者指定的这句固定文本，大模型在下一步根据该文本获知之前的输入存在瑕疵，从而基于新线索调整生成策略。

#### 特定异常类型捕获与常见错误分析

如果业务只希望拦截特定几种已知的异常，而让未知的严重错误正常抛出暴露，可以向 `handle_errors` 传入具体的异常类或异常类构成的元组。在 LangChain 结构化处理过程中，最典型的两个异常类型为：

1. `MultipleStructuredOutputsError`（多重结构化输出错误）：
   当业务在 `schema` 中使用了 `Union` 联合类型联合了多个不同的 Pydantic 模型时，底层的语义约束要求模型必须在其中严格执行“多选一”（单一匹配原则）。若大模型在一轮推理中判定多个结构均符合条件，并同时发起了针对两个结构的工具调用请求时，框架便会抛出该异常。
2. `StructuredOutputValidationError`（结构化验证错误）：
   大模型响应的数据键名或数据类型与 Pydantic 规范不符（例如模型将 Schema 中定义的 `title` 错写为了 `title1`，或者数值类型返回了无法转换的非数字字符串）时抛出。

```python
from langchain_core.exceptions import (
    MultipleStructuredOutputsError,
    StructuredOutputValidationError
)

# 策略四：仅对多重输出与验证错误两类异常进行定向拦截
strategy_specific_errors = ToolStrategy(
    schema=ContactInfo,
    handle_errors=(MultipleStructuredOutputsError, StructuredOutputValidationError)
)
```

```text
       大模型返回工具调用响应
                 |
                 v
       校验器执行类型与字段检查
                 |
        [发生运行错误 Exception]
                 |
        +--------+--------+
        |                 |
        v                 v
[在指定的元组列表中]    [不在指定列表中]
        |                 |
        v                 v
[捕获并触发自动纠错]     [直接中断并抛出异常]
```

图解说明：通过元组指定异常类型实现了异常路由机制，仅将预估之内的格式类偏差引入纠错重试，避免未知系统级故障被意外掩盖。

#### 自定义错误处理函数与动态修复提示

面对最为严苛的复杂生产场景，静态配置往往无法满足差异化的应对策略。此时最灵活的方案是为 `handle_errors` 绑定一个可调用的自定义异常处理函数。该函数以捕获到的原始 `Exception` 实例作为入参，返回一段定制的字符串作为发给大模型的下一次纠错提示词。

```python
from typing import Union
from langchain_core.exceptions import (
    MultipleStructuredOutputsError,
    StructuredOutputValidationError
)

def custom_error_handler(error: Exception) -> str:
    """自定义精细化异常处理器"""
    error_type = type(error).__name__
    error_detail = str(error)
    
    # 打印服务端日志以供监控分析
    print(f"捕获到的错误类型是: {error_type}")
    print(f"错误详情: {error_detail}")
    
    # 根据具体异常类型进行多分支业务归流与针对性提示
    if isinstance(error, MultipleStructuredOutputsError):
        return "检测到多个响应，请选择最相关的一个进行返回"
    elif isinstance(error, StructuredOutputValidationError):
        return "数据格式有误，请检查字段是否符合要求"
    else:
        return f"系统处理发生异常: {error_detail}"

# 策略五：挂载自定义错误处理函数
strategy_advanced = ToolStrategy(
    schema=ContactInfo,
    handle_errors=custom_error_handler
)
```

在该函数内部，我们可以精确获取异常的类名与底层详细调用栈，并在代码层面针对不同的错误分支，给出直击要害的修正指令。例如明确告知大模型“当前二者只能选其一”或“某个字段缺失”，大幅提升大模型在重试时的修正命中率。

### 智能体流式输出模式与执行监控

#### 流式输出机制与 stream_mode 架构

传统的 `agent.invoke()` 采用单次全阻塞式调用，在多工具串行推理的复杂任务下，用户往往需要面对数秒甚至十几秒的完全静默期。为了大幅削减终端用户的等待焦虑，并让复杂任务的处理过程具备高度可观测性，LangChain 为智能体提供了 `agent.stream()` 接口。

在调用 `stream` 时，通过参数 `stream_mode`，开发者能够精确控制数据流送的颗粒度与观察视角。框架总共支持七种不同的流式工作模式：

```text
                  +--------------------------------+
                  |     agent.stream(...,          |
                  |       stream_mode="...")       |
                  +--------------------------------+
                                   |
         +-------------------------+-------------------------+
         |                         |                         |
         v                         v                         v
   [状态追踪域]              [文本渲染域]              [底层监控域]
   - values (全量状态)       - messages (打字机Token)  - tasks (生命周期)
   - updates (增量变化)                               - debug (细粒度步骤与时间戳)
                                                       - checkpoints (检查点持久化)
                                                       - custom (业务自定义推送)
```

图解说明：七种 `stream_mode` 按照关注维度可划分为状态追踪、文本呈现与底层监控三大应用范畴，满足从终端 UI 交互到生产排障的差异化需求。

#### 状态累积模式 values 与增量更新模式 updates

在流程编排和状态回溯场景中，`values` 与 `updates` 是最常对比的两种状态级模式：

```text
[values 模式：输出每一步执行后的全局累积状态列表]
Step 1: [HumanMessage]
Step 2: [HumanMessage, AIMessage(tool_call)]
Step 3: [HumanMessage, AIMessage(tool_call), ToolMessage, AIMessage(final)]

[updates 模式：仅输出当前执行节点产生的局部增量]
Step 1: [AIMessage(tool_call)]
Step 2: [ToolMessage]
Step 3: [AIMessage(final)]
```

图解说明：`values` 类似连续快照，每一步都带有截止当前的全部历史消息；`updates` 是纯差量事件，每一步只吐出当前节点新产出的独立消息。

1. `values` 模式：智能体每执行完图中的一个节点，都会把当前上下文内包含的**完整状态快照（所有历史消息与现有数据的完整列表）**完整推送出来。该模式适用于需要对每一步的全局执行上下文进行数据持久化或回滚归档的场景。
2. `updates` 模式（**默认缺省模式**）：每一步节点执行完毕后，**仅仅增量输出本步骤内发生变化的那部分数据**。例如本轮模型决定调用工具，就只输出一个包含 `tool_calls` 的 `AIMessage`；工具执行完毕，就只输出对应的 `ToolMessage`。该模式非常适用于在前端界面展示智能体的思考与工具执行步骤。

```python
# 采用 updates 默认模式观察增量步骤
for chunk in agent.stream(
    {"messages": [HumanMessage(content="查询客户 cust_1234 的完整信息与历史订单")]},
    stream_mode="updates"
):
    print(chunk)
    print("-" * 50)
```

#### 逐字生成模式 messages 与打字机效果实现

对于类 ChatGPT 的终端交互界面，用户最期待的是文字像打字机一样一个 Token 接一个 Token 地逐字跳出，而不是等待整句话生成完毕后一次性弹出。`stream_mode="messages"` 正是为此而生。

在该模式下，生成器会以非常细的粒度实时推送模型吐出的每一个 Token 增量块（`AIMessageChunk`）及其携带的元数据。此时 `chunk` 的结构通常为一个元组，元组首项即为消息分块对象。我们可以通过提取其 `content` 属性，并结合 Python 的标准流式刷新机制实现打字机效果：

```python
# 实现类打字机的实时终端文本输出
for chunk in agent.stream(
    {"messages": [HumanMessage(content="分析客户销售趋势")]},
    stream_mode="messages"
):
    message_chunk = chunk[0]
    # 仅当文本内容非空时进行无换行冲刷打印
    if message_chunk.content:
        print(message_chunk.content, end="", flush=True)
```

通过这一配置，大模型每一次向外流式发射词元时，终端都可以毫无时滞地实时呈现，给用户带来极致顺滑的交互体验。

#### 任务生命周期监控 tasks 与调试模式 debug

当智能体部署于后台工程流水线时，运维与开发人员往往需要密切关注底层工作单元的调度生命周期：

1. `tasks` 模式：聚焦于执行节点的生命周期事件。每次底层任务开始调度、执行完成或发生故障时，该模式都会流式抛出包含任务唯一 ID、执行状态及启动与结束时间戳的数据块，用于监控调度任务的生命周期演进。
2. `debug` 模式：在 `tasks` 的基础上进一步强化，提供最详尽的底层执行轨迹。它不仅包含了当前任务的明确序号步骤（如 Step 1、Step 2），还附带精细的高精度时间戳（Timestamps）、任务流转类型（Task / Task Results）等内部追踪信息，是本地开发排查隐蔽死锁或调度异常的首选利器。

#### 状态持久化模式 checkpoints 与自定义进度输出 custom

最后两种模式面向高阶控制与定制业务：

1. `checkpoints` 模式：与状态持久化机制紧密挂钩。当智能体配置了检查点保存器（如 `MemorySaver` 等 `checkpointer` 节点）时，每当系统在关键推理边界成功创建一个持久化检查点快照，就会触发一次流式推送。输出的数据体完整包含检查点内的全部状态字典与当前会话 ID，为长程会话中断恢复提供了底层事件驱动基础。
2. `custom` 模式：为开发者提供自主的业务进度上报通道。在自定义工具函数的执行体内，开发者可以调用 `get_stream_writer()` 获取流式写入器实例，在耗时操作的不同阶段显式调用 `writer.write()` 推送业务进度：

```python
from langchain_core.tools import tool
from langchain_core.runnables import get_stream_writer

@tool
def generate_sales_report(query: str) -> str:
    """生成销售数据分析报告"""
    writer = get_stream_writer()
    if writer:
        writer.write({"progress": 10, "status": "开始拉取数据库销售明细..."})
        # 模拟中间计算过程
        writer.write({"progress": 60, "status": "正在汇总各类目营收与净利润..."})
        writer.write({"progress": 100, "status": "报告渲染完毕"})
    return "2026年Q1季度销售额稳步上升，环比提升15%。"
```

当外部以 `stream_mode="custom"` 启动流式调用时，上述由代码主动写入的进度字典会被原样实时流出，让前端进度条或状态文本获得实时的业务感知。

#### 流式模式多选组合策略与选型场景

在实际架构设计中，面对这七种流式模式，选型可以参照以下原则：

- **终端打字交互**：选择 `messages` 模式；
- **观察多步推理思考轨迹**：选择 `updates` 模式；
- **排查系统调度与执行耗时**：选择 `tasks` 或 `debug` 模式；
- **前后端耗时业务进度条联动**：选择 `custom` 模式。

不仅如此，`stream_mode` 参数不仅支持传入单个模式名称的字符串字面量，还支持传入模式构成的序列列表（`Sequence[str]`）。例如：

```python
# 组合模式：既要前端逐字打字机效果，又要获取每一步的工具调用增量更新
agent.stream(
    {"messages": [HumanMessage(content="查询天气并计算体感温度")]},
    stream_mode=["messages", "updates"]
)
```

这种“既要又要”的组合传参机制，使得单一流通道可以同时下发不同维度的数据流，在复杂的全功能交互端上能够兼顾界面文本打字与侧边栏工具追踪的同步刷新。

### 多功能综合智能助手实战构建

#### 系统功能需求与四大开发步骤

作为智能体章节的综合落地实战，我们要构建一个高内聚、高可用的多功能智能助手应用。该助手需要在一个统一的会话体系内支持五大维度的综合业务能力：
- 天气实时查询（`get_weather`）
- 数学逻辑计算（`calculate`）
- 系统时间查询（`get_time_info`）
- 货币汇率转换（`convert_currency`）
- 全网综合搜索（`search_info`）

整个项目的落地遵循严谨的工业级四大开发步骤：
1. **模型初始化**：建立与大语言模型服务端的稳定连接；
2. **工具集规范定义**：使用 `@tool` 装饰器编写业务函数，配置高信息量的语义 Docstring；
3. **面向对象架构封装**：定义智能体助手类，内部统一管理 `model`、`tools`、`system_prompt` 及长期累积的 `messages` 状态列表；
4. **主测试程序与人机交互驱动**：提供自动化流水线验证与控制台交互式 REPL 运行环境。

#### 模型初始化与五大核心工具定义

首先进行模型实例的构建以及底层工具链的开发。为了保证当前教学闭环与实操独立性，天气与信息搜索暂时通过 Mock 数据驱动模拟；在后续进阶章节中，可以直接无缝替换为标准的 MCP（Model Context Protocol）服务连接外部生产接口（如 OpenWeather 与 DuckDuckGo/Tavily）：

```python
import datetime
from langchain_core.tools import tool
from langchain_anthropic import ChatAnthropic

# 步骤一：模型初始化
model = ChatAnthropic(model_name="claude-3-5-sonnet-20241022")

# 步骤二：五大功能工具定义
@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气状况，返回温度与天气描述。"""
    mock_weather = {
        "北京": "晴，气温 18℃，空气质量优良",
        "广州": "多云有阵雨，气温 26℃，湿度 80%"
    }
    return mock_weather.get(city, f"抱歉，天气查询工具暂不支持城市：{city}")

@tool
def calculate(expression: str) -> str:
    """执行数学四则运算表达式，例如 '4 + 5 * 4'。"""
    try:
        # 实际生产中应采用安全数学解析库，此处用于演示核心逻辑
        result = eval(expression)
        return f"计算结果为：{result}"
    except Exception as e:
        return f"数学表达式计算失败: {str(e)}"

@tool
def get_time_info() -> str:
    """获取当前的系统准确时间与日期。"""
    now = datetime.datetime.now()
    return f"当前系统时间为：{now.strftime('%Y-%m-%d %H:%M:%S')}"

@tool
def convert_currency(amount: float, from_curr: str, to_curr: str) -> str:
    """进行货币汇率转换，如美元兑人民币。"""
    rates = {
        ("USD", "CNY"): 7.23,
        ("EUR", "CNY"): 7.85
    }
    pair = (from_curr.upper(), to_curr.upper())
    if pair in rates:
        target_val = amount * rates[pair]
        return f"{amount} {from_curr} 等于 {target_val:.2f} {to_curr}"
    return f"暂不支持从 {from_curr} 到 {to_curr} 的汇率换算"

@tool
def search_info(query: str) -> str:
    """搜索各类通用信息或百科知识。"""
    return f"关于 '{query}' 的搜索结果：LangChain 是构建 LLM 应用的现代框架。"

tools = [get_weather, calculate, get_time_info, convert_currency, search_info]
```

#### 智能助手类封装与历史消息维护

在传统脚本式写法中，状态与调用逻辑往往散落在全局作用域，难以复用与扩展。这里采用标准的面向对象思想（OOP），将整个智能体封装为 `MultiFunctionalAssistant` 类：

```text
+-------------------------------------------------------------+
|                  MultiFunctionalAssistant                   |
+-------------------------------------------------------------+
| - model: BaseChatModel                                      |
| - tools: list[BaseTool]                                     |
| - system_prompt: str                                        |
| - agent: CompiledGraph / AgentExecutor                      |
| - messages: list[BaseMessage] (在对象内维护长期累积的会话状态)   |
+-------------------------------------------------------------+
| + __init__(model, tools, system_prompt)                     |
| + chat(user_input: str) -> str                              |
| + reset() -> None                                           |
+-------------------------------------------------------------+
```

图解说明：`MultiFunctionalAssistant` 类在实例生命周期中直接持有全局 `messages` 列表，实现了会话上下文跨调用的自动累积与内聚隔离。

```python
from langchain.agents import create_agent
from langchain_core.messages import HumanMessage, AIMessage, BaseMessage

class MultiFunctionalAssistant:
    def __init__(self, model, tools, system_prompt: str = "你是一个多功能个人智能助手，请礼貌且高效地回答用户问题。"):
        self.model = model
        self.tools = tools
        self.system_prompt = system_prompt
        
        # 编译并创建智能体运行时
        self.agent = create_agent(
            model=self.model,
            tools=self.tools,
            system_prompt=self.system_prompt
        )
        
        # 维护对象自身的历史消息链表
        self.messages: list[BaseMessage] = []

    def reset(self):
        """重置当前对话历史，开启全新会话"""
        self.messages = []
```

#### 结果反向解析与会话重置实现

在 `chat` 方法的具体交互过程中，我们把用户的输入文本包装为 `HumanMessage` 并填入调用链。当 `agent.invoke({"messages": self.messages})` 执行完成后，返回的 `result["messages"]` 是一个包含了本轮全量流转过程的消息数组：

```text
result["messages"] = [
    HumanMessage(content="北京天气怎么样"),
    AIMessage(tool_calls=[{"name": "get_weather", "args": {"city": "北京"}}]),
    ToolMessage(content="晴，气温 18℃，空气质量优良"),
    AIMessage(content="北京今天天气晴朗，气温为18℃，空气质量优良。")  <-- 真正需要呈现给用户的最终答案
]
```

如果直接将整个列表输出给终端用户，界面会夹杂中间的工具调用结构与底层返回内容，破坏阅读体验。为了仅抽取大模型最终整理出的自然语言回复，我们在方法内采用反向遍历（`reversed`）机制：

```python
    def chat(self, user_input: str) -> str:
        """接收用户文本输入，驱动 Agent 执行并提取最终文本回复"""
        # 1. 组装用户消息并追加进历史列表
        self.messages.append(HumanMessage(content=user_input))
        
        # 2. 调用智能体执行完整推理与工具调用链
        result = self.agent.invoke({"messages": self.messages})
        
        # 3. 将包含中间步骤在内的完整执行结果回写至实例的 messages 字段
        self.messages = result["messages"]
        
        # 4. 从后向前遍历，检索最后一条由 AI 发出的最终总结消息
        for msg in reversed(self.messages):
            if isinstance(msg, AIMessage):
                return msg.content
        return "未能获得有效回答"
```

> **注意**：第三步中 `self.messages = result["messages"]` 的回写操作至关重要！它不仅记录了本次的用户输入与最终回答，连同模型发起的工具调用请求（Tool Calls）及工具的返回值（Tool Results）一并固化在上下文链条中。只有这样，后续多轮追问时大模型才能确知此前已经调用过哪些工具以及获得了什么实测数据。

#### 控制台多轮交互运行验证与上下文累积验证

为了验证整个系统在面对连续提问时的表现，我们可以编写主函数驱动测试：

```python
def main():
    assistant = MultiFunctionalAssistant(model=model, tools=tools)
    
    print("=" * 50)
    print("多功能智能助手已启动！支持多轮交互。输入 'reset' 重置，输入 'exit' 退出。")
    print("=" * 50)
    
    # 模式一：批量流水线测试用例
    test_queries = [
        "北京天气怎么样",
        "帮我计算一下 4 + 5 * 4 等于多少",
        "现在几点了",
        "把 100 美元兑换成人民币是多少钱"
    ]
    
    print("\n--- 开始自动化多轮测试 ---")
    for q in test_queries:
        print(f"\n[用户提问]: {q}")
        reply = assistant.chat(q)
        print(f"[助手回复]: {reply}")

    # 模式二：交互式命令行 REPL
    print("\n--- 进入控制台交互模式 ---")
    while True:
        try:
            user_input = input("\n请输入问题: ").strip()
            if not user_input:
                continue
            if user_input.lower() in ("exit", "quit"):
                print("程序已安全退出。")
                break
            if user_input.lower() == "reset":
                assistant.reset()
                print("会话历史已成功重置！")
                continue
                
            response = assistant.chat(user_input)
            print(f"助手: {response}")
        except KeyboardInterrupt:
            print("\n程序中断退出。")
            break

if __name__ == "__main__":
    main()
```

运行测试后，系统能够按需准确路由并调用对应的底层工具，输出干净利落的自然语言总结。在连续输入多轮问题且未调用 `reset()` 时，系统完美保持了跨轮次的状态记忆。

### 本讲提到的题目

在讲解多功能智能助手的多轮调用与状态管理机制时，课上提出了一个关于上下文生命周期的核心问题。

#### 多轮提问中的消息列表累积机制

**【题目题干】**
我们在主程序中使用同一个智能助手实例连续调用 `assistant.chat()` 提问：问完第一个问题后问第二个，问完第二个又问第三个。在这个过程中，底层的 `self.messages` 消息列表是每次调用前都被初始化成一个全新的空列表，还是在原有各轮消息的基础上持续累积增长？如果大模型在第二轮回答时需要参考第一轮的提问背景，该机制是如何提供支持的？

**【题目解析】**
1. 观察 `chat` 方法的内部执行流程：
   ```python
   self.messages.append(HumanMessage(content=user_input))
   result = self.agent.invoke({"messages": self.messages})
   self.messages = result["messages"]
   ```
2. 当执行第一个提问（如“北京天气怎么样”）时，`self.messages` 最初为空，追加该问题后传入 `invoke`。执行完毕后，`result["messages"]` 包含 4 条消息（用户提问、工具调用、工具响应、最终回复），并被重新赋值给 `self.messages`。
3. 当执行第二个提问（如“帮我计算 4 + 5 * 4”）时，代码直接在已经存有前 4 条消息的 `self.messages` 末尾执行 `append`，追加新的用户提问。此时传入 `invoke` 的是一个包含了上一轮完整交互痕迹的混合消息列表。
4. 这种在原有基础上**持续累积赋值**的机制，赋予了大语言模型天然的多轮上下文记忆能力。大模型在处理当前轮次时，能够完全感知前置轮次讨论过的实体与计算结果。只有显式调用 `assistant.reset()` 将 `self.messages` 赋为空列表时，上下文累加才会被截断清空。

**【参考答案】**
消息列表是在原有消息的基础上**持续累积增加**的，绝非每次新建空列表。每一次调用 `chat` 都会保留之前所有轮次产生的 `HumanMessage`、`AIMessage`（包含工具调用明细）和 `ToolMessage`。正因如此，智能体在后续提问中能够完整知悉历史对话背景；若业务希望隔绝上下文关联，必须显式调用 `reset()` 进行重置。
