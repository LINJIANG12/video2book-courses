### 课前问答：Vulkan、物理引擎与小引擎近况

正式开讲之前，先把社区里攒下来的问题集中回应一下。过去一个多星期，我们在社区里大概回答了两百多个问题。其中有个现象想专门说说：有女同学悄悄告诉我们，有些问题其实很简单、很基本，但她们不知道这样的问题适不适合问，怕一问出来显得自己水平不够。我非常能理解这种感受——我以前也是这样，特别怕有人问"有没有问题"，我鼓起勇气问了一个，大家都看着我笑了。但这恰恰是我们要克服的东西：千万不要觉得你的问题简单，每一个问题都值得被回答。这门课的跨度非常大，从只有一点点编程基础、甚至没有基础的同学，到已经从业好些年的行业同学都有。如果我们收不到大家真实的问题，就会误判——以为这个公式很简单、这个方法大家都懂，这里可以讲得简单一点；收到的问题越多，我们越清楚哪一块大家还没有基本概念，需要讲清楚、讲懂。所以把问题提出来，是我们把这门课讲对的前提。

小引擎阅读起来有很多困难，这个问题我们也收到了，现在正在整理一份文档，结合大家的问题，把小引擎里的一些难点、困难点整理出来。顺便交代一句课程本身的难处：这一节课的课件，是我们整个课程准备起来压力最大的一节。因为 104 这门课和其他课很大的不同，是我们所有的东西都是现做的——游戏引擎的资料非常分散，而且很多技术、概念在行业内大家都有 debate（争论）。我们作为一门中立的课程，会把各方面的资料都搜集起来，基于对行业的理解，尽可能给出一个相对中立、又相对客观的描述；实在搞不清楚的，我们就承认不懂，跟大家讲问题在哪里。所以这门课的准备会花很多时间，后面我们会把更多时间分给小引擎，给大家更多解释。

被问得最多的问题之一：为什么小引擎要选 Vulkan 这么抽象、这么难的 API？大家学图形学，一上来学的肯定是 OpenGL：set 一个 viewport、gluLookAt，最好用的还有 GLUT 这种工具，上来设置一个 lookAt，所有东西全能搞完。为什么我们偏要给大家直接打开 hard 模式？两个原因。第一，就像前面图形学那节课讲的，我们特别想让大家明白游戏引擎这个行业未来真正的发展方向：现代 graphics 硬件一定会走向让用户可以定制、可以自己去规划 pipeline 的时代，compute shader 这些东西起来之后更是如此。Vulkan、DX12 相对于上一代图形 API——比如 DX11、早期版本的 OpenGL——是有代际差的。我们直接教下一代的东西，今天学不懂没有关系，但你的 foundation 是正确的，将来真想在这方面精进的时候，就不用把基础浪费在前面那些过时的东西上。这就像我们国家造航母：直接上来就电磁弹射，不搞蒸汽弹射——那套技术积累没什么用处了，逻辑就是这样。第二，Vulkan 是真正跨平台的：DX12 和 Vulkan 其实是等价的，但 DX12 主要面向 Windows 平台，而我们的同学有在 Mac 的、有在 Linux 上的，还包括移动端，这一点上 Vulkan 有很大优势。这节课我们提供了两个 reference 网站，Vulkan 相关的问题在上面都可以查到；Piccolo 引擎具体的问题，可以直接问课程组。

另一个同学问得比较多的：meta parser——我们的反射处理器——什么时候开源？这个确实是难度比较大的一块，里面要用到一点 LLVM、Clang 的东西。我们的计划是：等这节课把反射的基础原理讲完之后，差不多就开始把代码开源出来。具体时间还要给课程组一点点准备时间，把文档各方面配套齐全一点。但大家不用担心，一定会开源——小引擎的精神就是开源。

还有同学说，小引擎的环境好难搭建。这我们非常能理解，它确实是个两难问题。我当年学编程的时候，用简单的 VC 打开就能直接建个工程；而小引擎对大家有一个很大的卡点：你需要用 CMake 去生成整个工程（solution）文件，而且 Mac 和 PC 上的方法还不一样。要提供一个跨平台的解决方案，我们没有别的选择，CMake 就是最好的选项，但它就是一道门槛。我的建议是：第一，严格按 README 一步步操作——小引擎最开始的环境搭建不是我做的，是我们团队同学一起做的，我自己也是照着 README 一步步搭的，其中几处 README 的修改，还是因为我操作遇到了卡点、大家一起把它改掉的；第二，可以查一些资料，我们这边也给大家准备了一点 environment setup 的资料；第三，如果以上步骤都用过了还有问题，就像一开头说的那样，不要不好意思，直接到我们的微信群问我们，课程组的小伙伴会非常积极地回答。希望大家能尽快进到 Piccolo 这个小引擎里面去遨游。

说到小引擎：它经过差不多两三个月的发展，特别是课程开始后一个多月收集到的反馈，基本的体系已经构建得比较完备了——包括整套编辑模式（play in editor）、基于 forward rendering 的整个技术架构、shadow、动画系统，还有最近刚刚接入的物理系统。有同学问：为什么接 Jolt 这个小物理引擎？跟大家分享一点背景：这个引擎我们是真认真挑过的。物理引擎的选项很多，比如我们都用过的 Havok Physics，还有其他一些开源物理引擎。选 Jolt，就是因为它很轻很小——有兴趣的话你可以进去读源码，如果我没记错，它只有几万行代码；而且它虽然小，却是被大作用过的：《地平线》（Horizon）这样的作品就用它做物理引擎，所以它的算法、稳定性、鲁棒性没有什么太大的问题。因为我们认为，做一个小小的游戏引擎，没有物理这一趴，感觉就会差很多。最近随着大家一起努力，我们又把 character、motor 系统也装了进去，所以今天的小引擎基本上已经很完备了，还能跑在 Windows、Linux、macOS 上。有同学问"我为什么要学 104 这门课"——至少有一点：做毕设的时候，你用 Piccolo 做出来的东西，我保证可以秒杀你的室友。这就是我们一个很有意思的目标：学完 104，人均一个自研引擎。

### 工具链：引擎里最默默无闻的奉献者

好，那么接下来开始我们今天的正主了。今天这节课讲游戏引擎里面我认为最默默无闻的奉献者——工具链。为什么这么说？你看每一个游戏引擎宣传自己的时候，讲的都是"你看我有什么特别厉害的光照效果、特别厉害的视觉效果、特别逼真的物理仿真"，很少有人会讲"我的工具又有哪些进化"。为什么呢？因为大家听不懂——老百姓哪知道工具是什么。但你再看这类发布活动的后半场，到面向专业听众的那一部分，才会讲"同学们，我们最近工具又做了什么升级"。而我们真正做引擎的人，第一趴看看也就过了，基本五分钟就明白了，真正花时间看的，是它在工具上做了什么变化——这才是引擎最核心的东西。

整个引擎的工具链是非常大的一个模块。大家知道我们最近的课程日程做了调整：本来工具链只有一节课，但是我们做完准备之后发现，一节课根本讲不完，所以毅然决然多加了一节课。当然，有另外一个模块的课被我们挤掉了——就不点名了，好可怜。

工具链分两讲，还是我们的传统节奏。第一讲是基础：怎么去构建一个最简单的工具链，怎么解决资源的加载与存储，怎么让这些工序之间不要打架、能形成一个链条让数据可以传递，怎么实现最简单的所见即所得（What You See Is What You Get）的编辑，还包括工具链的 plugin 系统——这些是工具链最基础的东西。第二讲讲相对高级的内容：第一，在一个实战型的游戏 pipeline 中，这些工具到底是怎么在一起协同工作的，你到底需要哪些编辑器、每个编辑器的实际要点是什么；第二，讲一些工具链比较深的东西，比如反射——大家很关心的、一直想问我们要的 meta parser 源码，如果你不懂反射这一趴，源码给大家也很难看得懂；再比如协同编辑这样的高级概念。

### 工具链在引擎架构中的位置

那首先给大家讲一下，游戏引擎的工具链到底是什么。

这是我们画的一张游戏引擎架构图。游戏引擎本身的复杂度，真的像一个小型的操作系统——现在一个游戏引擎基本都要达到千万级代码的复杂度。很多时候，很多人会把渲染、把 rendering 当成游戏引擎，但其实渲染只是其中很小的一部分；那物理仿真是不是游戏引擎？物理仿真也是其中的一部分；网络通讯、状态模拟是不是？也是其中的一部分。你把这些东西全部合到一起，得到的东西是一个 runtime——我们叫 engine runtime。而在 engine 之上，有大量的工具：比如各种各样的 editor，大家最常见的是场景编辑器，在这儿可以构建一个你想要的世界；然后你要编辑各种各样的游戏逻辑，像连电路板一样的图形化编辑器，我们一般叫 graphic editor，有些引擎叫 blueprint（蓝图）；我们还有各种各样的材质编辑器、shader 编辑器、脚本编辑器，各种各样的东西。

这一系列东西的复杂度，或者说整个体量，对于一个成熟的商业引擎来讲，一般会超过 runtime。我们都觉得 runtime 代码很难写，对不对？但是引擎工具链代码的总开发量、开发成本，实际上是会高于引擎本身的——这是商业级引擎里的一个 general practice。

> **结论**：对一个成熟的商业引擎来说，工具链的复杂度和开发成本一般会超过引擎 runtime 本身。

那么这么一个庞大庞杂的系统，它最源头的基础是什么呢？我们叫做 DCC：各种各样的第三方软件，比如 3ds Max、Maya、ZBrush、Photoshop，还有现在比较火的 Houdini。它们生成大量的资产素材，这些数据都是异构的，要经过我们的工具链，再进入到整个引擎的 pipeline。这个地方有个大家以前听过的词：ACP——asset conditioning pipeline（资产条件化管线）。工具链，其实就在 ACP 的这一层。

```text
  DCC 软件层：3ds Max / Maya / ZBrush / Photoshop / Houdini …
        │  生成大量异构的资产素材
        ▼
  工具链 Toolchain（就位于 ACP 的这一层）
        │  场景编辑器 · 蓝图编辑器 · 材质编辑器 · Shader 编辑器 · 脚本编辑器 …
        │  把素材加工、组织成引擎可用的游戏数据
        ▼
  引擎 Runtime：渲染 · 物理 · 网络与状态模拟 …
        │  复杂度像一个小型操作系统，千万行级代码
        ▼
  最终跑起来的游戏
```

读图：DCC 产出的异构素材先经过工具链（也就是 ACP 所在的层）加工成引擎可用的数据，再进入引擎 runtime 的 pipeline；而场景、蓝图、材质这些编辑器，都架在 runtime 之上。

### 工具真正解决的问题：让不同思维方式的人协同

工具链真正解决的问题是什么？这是我想让所有学过游戏引擎开发的同学，将来拿去跟没有学过的同学解释的。你问"为什么引擎要做工具、工具核心解决的问题是什么"，如果别人告诉你说"它只是为了做编辑、生成游戏数据"——你就可以"嘲笑"他了：不好意思，你这个讲的还是业余的。我给你讲一个最专业的观点：引擎工具最核心解决的问题，其实不只是为了造游戏，它是在调和几种不同思维方式的人在一起协同工作的这么一个平台。

为什么？大家想象一下一个游戏团队真实的情况。最简单的有三类人。第一类，是我们思维方式特别严谨、动手能力非常强的程序员同学：每天戴着眼镜、穿着格子衬衫，非常严谨、逻辑性很强，什么事情都要跟你讲逻辑。还有一类，是我们的 artist：他不在乎你的算法是怎么回事，不在乎你的光照模型底层的数学、物理原理是什么，他要的是"这个山水更暖一点、那个更冷一点""这个场景、这个角色动起来要更有质感一点"——这些语言和我们程序的语言是完全不搭嘎的。Artist 对世界的理解非常感性、非常非定量，但又非常敏锐；他对游戏的表达，实际上是一种用户体验向的表达。第三类是我们的设计师（designer）：非常有创意——"我希望那一拳打下去，能够打出一个非常爆炸的伤害；而且我每一拳上来的时候速度要慢、突然一下子加速，我要的就是这种打击感，刀刀入肉、拳拳入肉的那种感觉。"Designer 很在乎游戏的打击反馈，很在乎游戏数值的合理。

这三类人在一起，对同样一个游戏，各自打开工具的时候，看到的东西是完全不一样的。程序员看见的是各种数据在跑：这个场景里有多少个静态物体、多少段动画。艺术家看见的是什么？"这个色彩我要调"——还记得上节课给大家讲的 color grading 吗？就是那种非常符合 artist 感觉的东西："我要的是这张照片的这种年代感。"完了，程序员就疯掉了。但 artist 明白他怎么去表达这个世界，所以他需要有自己的工具——当然真实需求其实还要更复杂。Designer 看见的是什么呢？一堆策划数据：比如打击出去的攻击判定——在我的角色前面画一个方块，刀挥过去的地方形成一串方块，然后哪些是暴击区、哪些是轻击区，哪一个地方我能把对方打出硬直。

所以，我们的工具实际上是让这几种说完全不同语言的人，在一起能够共同演奏一首乐曲。我经常把一个游戏团队想象成一个乐队、一个交响乐队，而游戏引擎的工具链，就是调和这种不同设定的人在一起工作的基础建设。这就是工具链在整个游戏研发中的定位：所以它在设计上，要充分考虑到不同的使用者的思维习惯和需求是不同的。

以 Unreal 为例：美术从一版白模的关卡出发，在各种各样的工具里面换来换去——一会儿构建你的材质，一会儿做一个小的物体，然后迅速地去摆放，最终形成自己这样的一个世界。这大概将近三十秒的操作里面，其实已经 involve 了很多工具模块：比如粒子（particle）、材质、蓝图等等，后面我会详细讲。而这还只是展示了 artist 那一侧，实际上策划那边的工具还没有完全展开。

### 做工具的第一道门槛：GUI

如果我们想做工具，首先最难的一个东西是什么？是 GUI——graphics user interface，图形用户界面。其实无论设计师也好还是美术也好，面对游戏引擎、打开工具链的时候，都要输入大量的数字、要调很多东西，于是就会有大量的 user interface 需求在里面。最早的人机交互界面是什么？全是文本——最早的有一个操作系统叫 DOS，那个时代一切都是命令行；然后逐渐变成了 Windows 时代。而现代游戏引擎的工具链用到的 GUI 非常非常复杂，里面各种各样的控件。这么丰富和复杂的 UI，是你做游戏引擎工具链时首先要驾驭的东西。这个事情简单吗？其实非常复杂。GUI 是我做工具的第一道门槛——我首先得会画控件，我不会画控件，怎么给大家做工具呢？

好消息是，这件事的实现方式归纳起来就两大类。

#### 即时模式（Immediate Mode）

第一种我们叫做 immediate mode，直接模式。它非常简单，也很淳朴：OK，我想画一个编辑框，我想画一个下拉框，我想画一个按钮——OK 我就画吧，直接画上去。每一帧，游戏逻辑直接告诉 GUI 系统"我要画哪些控件"，就直接打到控件上去了。

这种模型非常简单和好用。它的好处就是直接、简单，而且非常快，非常容易做原型。但它的坏处是什么？第一，扩展性是有限的；第二，它会把很多业务压力压到逻辑这一侧。现在有些引擎的 GUI 系统（的一部分）还在用这种模式：比如 Unity 的 IMGUI、开源的 ImGui，包括我们小引擎的 GUI 系统，也是这样一个直接模型——因为它实现起来比较简单。

#### 保留模式（Retained Mode）

另一种，当我们去做工具的 GUI 模型时，一般会用 retained mode（保留模式）。最简单的理解：当我要画一个东西的时候，我并不是直接画到屏幕上去，而是先说"我要画一个 box，这个 box 的大小尺寸是什么"，把这些所有的信息全部交给一个缓冲——其实很像我们在 graphics 里讲的 command buffer——把我所有的这些指令全部存储在这儿；然后到了 GUI 自己的绘制逻辑的时候，它根据已经存的这些指令自己去画了。

这样的好处是什么？我相当于把业务逻辑和 GUI 的绘制两个东西分开了。而且这个模型扩展性非常强，性能也很好。为什么？因为你的这些命令全部 cache 到一起，统一处理——它不会是逻辑执行到一层就画一次，而是全放在一起统一处理。另外一个，如果你不去改变它，就不用再去更新它的指令。这其实也非常符合我们游戏架构的理论模型。

所以目前大部分游戏工具用的 GUI 模型，实际上是 retained mode。比如 Unreal 的 UI，比如最著名的 WPF（Windows Presentation Foundation，Windows 做 UI 的那个框架），包括大家特别喜欢的 Qt——我知道大学里做课件、做实验的时候大家特别喜欢用 Qt，我也蛮喜欢 Qt 的——其实也是用这样的模型去做的。所以在搭建 GUI 系统最主要的两大方式里，我们肯定会推荐大家用 retained mode。

| 对比维度 | 即时模式（Immediate Mode） | 保留模式（Retained Mode） |
| :--- | :--- | :--- |
| 绘制方式 | 每一帧由逻辑直接告诉 GUI 画什么，直接画上去 | 先把要画什么、尺寸多少等指令存进缓冲，GUI 绘制逻辑稍后统一绘制 |
| 扩展性 | 有限 | 非常强 |
| 性能特点 | 逻辑执行到一层画一次，业务压力压到逻辑这一侧 | 指令全部缓存、合批统一处理；不改变就不更新指令 |
| 典型代表 | Unity 的 IMGUI、ImGui、小引擎 GUI | Unreal 的 UI、WPF、Qt |

### UI 架构的三种经典模式

Retained mode 再往深处去讲，还有很多设计的细节，我们叫 design pattern：你的数据怎么去组织、你的绘制怎么去组织、你的 view 怎么去组织。学过 design pattern 的同学一定已经想到了：这个地方是不是要讲 MVVM、MVP、MVC？对，你猜对了。在讲整个工具 UI 系统构建的时候，design pattern 非常重要。你写一个两个工具、写一个两个功能的时候没什么感觉；但当你写到一个工具里面有上百个功能、然后十几个工具在一起的时候，如果你不去遵循某一个 design pattern——至少以我的开发经验来讲——基本上一定会炸的。这也是做游戏引擎很有趣的一件事：它是一个非常考验工程架构能力的软件开发。

#### MVC：把数据流变成单行线

这里面最著名的几个 pattern 中，被称为鼻祖的是 MVC。它是 1978 年提出来的——真的很早，真的很了不起的一个模型。它最早要解决的问题其实非常简单：以前做 UI 的时候，UI 中有大量的代码去修改数据，而数据中间又有很多逻辑，那你的 UI 万一改错了怎么办？而且 view 要改数据、数据要改 view 的呈现，两个代码系统就全绞合在一起了。所以在 40 多年前，大家就提出了 MVC 这个模型。

这个模型里，很多人对 Controller 的理解每个人都不一样，但我个人的理解是：它其实把数据流清晰化了。Model 把数据单向地输送给 View；View 不能再反过来写 Model——Model 把数据输送给 View，但 Model 本身不会被弄脏；你想修改 Model 里的数据，只能通过 Controller，它进行各种处理、各种过滤之后，再去修改你的 Model。这个环流因为变成单行线了，所以很清晰、很容易切断、很容易管理。这就像城市里面的交通：如果全是双行线、全交错在一起的时候，你就很难管理交通；你们会发现有些地方为什么实现了单行线管理？其实也是这个逻辑。

```text
 ┌─────────┐   数据单向输送（Model 本身不会被弄脏）  ┌─────────┐
 │  Model  │ ────────────────────────────────────→ │  View   │
 └─────────┘                                       └─────────┘
      ▲                                                 │
      │            Controller：处理、过滤               │
      └─────────────────────────────────────────────────┘
              修改数据的请求只能经由 Controller 回到 Model
```

MVC 是把 View 和 Model 解耦（decoupling）开来的最经典的架构。直到现在，它在 web 前端还有很多用处，而且大家对它做了很多的变种、很多的演进——它的变种是我目前知道最多的一个 pattern。

#### MVP：让 View 彻底不认识 Model

MVC 之后另一个模型是 MVP。我当年在大学学 VC 的时候，第一反应就是：为什么这个时候还要让 view 知道 model 呢？view 可不可以完全不知道 model 的存在？后来我学到 MVP 的时候就发现——哦，原来我这个"笑话"别人老早就想到了。MVP 可以认为是一个更彻底的、把 view 和 model 解耦的模型：view 完全不知道数据逻辑的存在，它只管它自己的各种展示控件；presenter 负责从 model 里取数据、呈现给 view，也负责把 view 里的用户交互反馈给 model。

这个好处是什么？像我们这种超大型软件工程，有很多功能模块，最大的需求之一就是 unit test（单元测试）：我要测试你的逻辑，那你的 UI 做还是没做、做成什么样，其实跟 model 的正确性没有太大的关系了。大家想想对不对？比如我的 model 里面是一个学生成绩排名系统、三好学生评判系统，那和你在 view 中怎么去展示三好学生，是不是没有什么关系？MVP 模型把这个分得很开，所以它是一个我个人认为更干净的架构。

当然，它带来的代价是什么？它把所有的复杂度扔到了 presenter——presenter 得既听得懂 model 的语言、又听得懂 view 的语言。中间人是最辛苦的，两种完全不同的语言他都得懂；这时候 view 轻松了，model 也轻松了。MVP 模型写不好的话，presenter 经常会写得非常臃肿和肥大。

```text
 ┌─────────┐   取数据 / 回传用户交互   ┌───────────┐   呈现 / 收集交互   ┌─────────┐
 │  Model  │ ←────────────────────── │ Presenter │ ─────────────────→ │  View   │
 └─────────┘                         └───────────┘                    └─────────┘
        Model 与 View 之间没有任何直接连线；Presenter 两种语言都得听得懂
```

#### MVVM：用绑定替掉写死的调用

在目前的整个工具实践中，我个人比较推荐的是第三种模型：MVVM。这个名字很多同学应该非常熟了——如果我没记错，最早是微软提出来的。它跟 MVC、MVP 都有很深的关系，但它做了一个我认为非常了不起的决定：第一，像 MVP 模型一样，把 view 和 model 彻底分开；第二，中间那一层不再叫 presenter，而叫 view model；第三，也是最关键的——层与层之间的关系不再用代码写死（在 presenter 里去调用 view 的 API、调用 model 的 API），而是用了一种叫做 binding（绑定）的机制。

这个绑定机制为什么了不起？因为它观察到一个非常重要的事实——跟刚才讲工具的价值是一个道理：你是要把几种完全不同设定的人放在一起工作。比如去设计一个工具的整个 UI 的时候，实际干这件事的是 UX designer（交互设计师）：他不会写代码，也不想写代码；他在乎的是什么？是"我这个按钮放在这里是不是合适""这个按钮按下去，出下拉框还是滑动轨更合理、更好看""我应该用什么颜色"。他希望在一个完全独立的 ecosystem 里定制自己的用户交互，因为他只对用户交互和体验负责。所以 view 不再去写什么逻辑，也不需要知道别人的东西，它希望用最简单的语言——比如 XML 或者 XAML——直接把界面这种声明式的东西描述出来，而且我们尽量实现他们想要的所见即所得。View model 是程序员写的，但其实只定义一种简单的绑定关系；真正复杂的 model，则由写它的人自己去写自己的数据。这样，model 和 view 就真的是彻底、彻底地分离开来了，整个系统非常干净。

```text
 交互设计师 ──写──→ View（XML / XAML 声明式描述，所见即所得）
                        │  binding：声明式绑定，自动同步
                        ▼
                 ViewModel（程序员写，只定义简单的绑定关系）
                        │
                        ▼
                    Model（真正复杂的业务数据，各自写各自的）
```

当然，想实现 MVVM 的模型，你必须要在现成的框架生态里做。比如 WPF 就给你提供了很好的框架：很多设计师用 XAML 脚本或者它的编辑器，就可以自动生成各种各样的 UI；然后你写一些非常简单的 C# 代码，就可以把这 UI 全部做出来。以前我们用 C、C++ 写 UI 的时候很痛苦，而且很难 debug，经常是 UI 就崩掉了；但是今天大家用 C#，你会发现非常灵活、非常方便，而且别人写好的控件也很容易拿来用。这就是 MVVM 模型很大的一个好处：灵活性。

这个模型也有自己的困难。第一，它需要在自己的生态里面：在 Windows 的情况下，你做 MVVM 最好的选择，目前我看到的还是 WPF。但是以前像 Mono 这些东西做得不够好，现在 .NET 系的框架在 Linux 上支持得不是特别好的时候，你想把它迁移到 Linux、迁移到 Mac 上怎么办？就很痛苦——所以它对环境的要求比较高。第二个，对于一些极其简单的 UI 需求，这套框架的可维护性（或者说 debuggability）本身也有一点点挑战：大家特别容易在 binding 那个地方出错——view 和 viewmodel 你都只是做了一些 declaration（声明），这个逻辑到底是不是真的对、两者之间的关联是不是真的有效，你不把整个系统跑起来是没有办法验证的；一旦这里面的数据出问题，debug 起来是比较痛苦的。但是这毫不妨碍 MVVM 是一个在商业上已经被证明了非常成功的模型，而且这个模型现在也还在不断地演进——因为我们现代的软件系统确实越来越复杂。

讲到这儿，大家首先明白了 GUI 大概以什么框架去构建。那实际做工具链的时候怎么选？我们的建议是：大家不要自己造轮子。我们的关注点首先是游戏引擎、是游戏里的东西，而工具链的 GUI 体系非常重要，而且需要有非常强的工程可扩展性，你才能够支撑你全部的需求——所以要选择最成熟的结构和方案。比如做小引擎，你如果真的急了、想用 Qt 去写，我认为也是可以的，但这一定比你自己去写一个要靠谱得多。如果你在 Windows 下、不考虑跨平台，那 WPF 肯定是一个比较好的选项，你就 follow MVVM 这个模型，这样你能够快速地构建各种各样你想要的工具。

### 序列化：远不止是存文件

有了 GUI，接下来你要面对的问题就是数据。我们在工具链里面要传递的是大量的数据，那数据的第一个需求是什么？load and save——加载和存储，因为数据不能总放在内存里。这个事情等我们真正设计工具链的时候会发现，它并不是一个 trivial 的问题，并不是一个非常简单的问题。

先跟大家讲一个学术名词，这个词其实非常高大上：serialization and deserialization，序列化与反序列化。听上去好像非常唬人，其实就是 save and load 反过来：serialization 就是存出去，把内存里的数据变成一个可以传递的二进制块；deserialization 就是把一个二进制块，变回我内存中可以解析、可以处理的数据。

> **定义**：序列化（serialization）把内存中的数据打包成可传递的二进制块；反序列化（deserialization）把二进制块解包还原成内存中可处理的数据。

> **易错点**：序列化与反序列化并不只是单纯地指文件。这两个概念的外延很广——可以存成磁盘上的文件，可以存成数据库里的一个 block data，还可以作为网络上的数据流来传输。

展开说这三条路。第一，存成磁盘上的文件，这是最直觉的。第二，存数据库：比如一个对象的描述——大家记得我们讲过游戏里一切皆 GameObject——我可以把一个 GO 的状态 serialize 成一个二进制的数据块，把它存到数据库中，用 object id 去引用它，这样我随时随地都可以访问它。第三，走网络：我的客户端 A 向客户端 B、或者向服务器发送一个消息的时候，实际上要把一个游戏对象的所有描述 serialize 成一个二进制的数据流，通过网络协议传到另外一个客户端；对方拿到这个二进制的数据流怎么办呢？它要对这个数据流做 deserialization，把那个游戏对象再构建出来。我们后面还有一章会讲 networking——怎么做可以互联的游戏——到时候会详细讲，里面有很多有意思的东西；而序列化与反序列化，正是 networking 的一个很重要的 foundation。所以这两个概念可以说是现代系统、特别是现代游戏引擎非常 foundation 的概念：在工具链和游戏引擎里面，我们每天面对的就是数据，打包、解包、打包、解包——这就是我们每天日常干的活。

```text
                serialization（打包）
 内存中的游戏对象 ────────────────────→ 二进制数据块
                                            │
      ┌─────────────────────────────────────┼─────────────────────────────────┐
      ▼                                     ▼                                 ▼
 磁盘上的文件                        数据库里的 block data              网络上的数据流
（本地 save / load）          （object id 引用，随取随用）       （客户端 ↔ 服务器 / 客户端）
      │                                     │                                 │
      └─────────────────────────────────────┼─────────────────────────────────┘
                                            ▼  deserialization（解包）
                        在内存里把游戏对象重新构建出来
```

### 数据格式：先用文本，再上二进制

#### 文本格式：最朴素的起点

那打包的方法，最简单的方法是什么呢？是 text 文件。大家不要笑——text 文件虽然非常简单，但实际上在最早期，比如网络之间的通讯，大家想象一下是怎么做的？我们可以用 text 明文来做。同学们大概听过不少互联网八卦：某某很厉害的、某某国的什么重点系统，结果它重要的信息都是用 text 明文存的——大家觉得笑掉大牙，但实际上这是个很常见的事情。

text 有很多好处。第一，它本身非常容易被理解、被人读；第二，你用任何一个工具就能打开它，这样你去 debug、去追踪、去分析都特别容易。

实际上，最早同学们如果学图形学，应该接触过一种格式叫 .obj。这是个非常古老的格式，它就是真的很淳朴：v 打头表示我是个 vertex（顶点），接下来三个数字就是我的顶点坐标；然后 f 打头表示一个面（三角形），后面跟着顶点的索引，1、2、3……就这么把一个模型描述完了。

```text
v 0.000000 1.000000 0.000000        # 顶点坐标
v 1.000000 0.000000 0.000000
f 1 2 3                             # 用顶点索引组成一个三角形
```

这些最古老的 text format，真的就是每个程序员自己想到一出是一出、就这么定下来的。等到后来大家就会发现，这样胡乱定是有问题的，于是后来就出现了一些结构化描述语言，比如 XML。XML 是个非常了不起的发明：它意识到了这些文本实际上是个容器，然后它通过一个树状的标注系统，能够把任何一种结构化的信息都装进去——这个东西是很多系统的 foundation。当然后来大家就发现，XML 这个废话特别多：每个描述都带一大堆标号、尖号。于是后来有人就提出了更轻量的方法，比如 JSON：它的功能跟 XML 非常接近，但是文件大小会小很多，parser 的处理也会快很多。类似的还有 YAML 这些语言。

那为什么 Piccolo 选择了 JSON 作为数据的语言？其实就是为了方便大家阅读和理解。如果用二进制的格式，同学们根本不知道那个数据里藏了什么东西，而且它的数据读取也非常抽象：最后进了引擎，数据正确了——不得了，谢天谢地；数据错误了呢——哎呀完蛋了，无从下手。大家如果 debug 过二进制数据的解析，就知道那个事情真的非常痛苦。类似的选择其实还有：Unity 也提供了一种用纯文本的方式去存储你的 asset；CryEngine 也有类似用 XML 或者 JSON 的存储模型。

所以我推荐大家：在写引擎、写工具链的时候，如果你做的体量不是特别复杂，先用 text file 去上手——因为你一开始写的时候会有很多的 bug。这样其实相当于给你的引擎加入了一个 debug mode：任何一个数据错了，你先把数据转成 text 格式 debug 一遍，没有问题了，再转成 binary 格式。这是一个非常好的 option。

> **提示**：引擎先支持文本格式的资产，等于自带一个调试通道——数据出问题先转成文本排查，确认无误再切回二进制。

#### 二进制格式：小而快，但难调

第二种大家很自然会想到：我存这么多蠢蠢的文字，肯定是最慢的嘛，我直接用 binary 去存。它的存储容量优势确实很明显：像 Unreal，它所有的模型基本上都是 binary 的；CryEngine 也有 binary mode。而且如果你有了一个基于 text 的结构化表达，把它转成二进制，实际上也是非常自然的一个表达。

这两者的差距有多大？举一个模型的例子：FBX 是行业里现在特别通用的一种数据模型的表达格式。它就很聪明，提供了两种 format——一种 binary、一种 text，这就是为了 debuggability。你会发现同一个模型，text 版本的文件基本上接近 binary 版本的十倍以上。而且大家都知道，读二进制的时候几乎不需要进行语法处理；但要读文本的时候，实际上要做语法 parsing：我得把你的逗号、句号、尖角号，包括你的注释，都要做语法、语义的过滤，我要生成一个 AST，再把语义建成 keyword、dictionary——要做很多很多的处理。所以 text 的加载速度，确实比 binary 慢将近十倍不止。

| 对比维度 | 文本格式 | 二进制格式 |
| :--- | :--- | :--- |
| 文件体积 | 大：同一个 FBX 模型，文本版接近二进制版的十倍以上 | 小得多 |
| 加载速度 | 慢：要做语法解析、生成 AST 与词典，慢将近十倍不止 | 快：几乎不需要语法处理 |
| 可读性与调试 | 任何工具都能打开，debug、追踪、分析特别容易 | 数据藏在块里，读取抽象，错了常常无从下手 |
| 适用阶段 | 开发与调试期，相当于引擎的 debug mode | 上线游戏的资产格式（此外还要防破解，可能还要加密） |

真正的、你要做一个上线的游戏的时候，你的资产、整个 asset 的格式，一定是要换成 binary 的。还有一个点：你不想被别人破解。所以其实资产有的时候是需要加密的——那就是另外一套很神奇的算法了，今天就不展开了。

### 资产的组织：引用、实例与数据继承

在资产里面，我们会发现很有意思的一件事情：打开一个游戏的关卡，你会发现很多资产是重复的。那怎么办？最自然的想法：把有些资产提取出来复用。比如我要表达一个场景，这个场景里面有 1000 栋房子，但这 1000 栋房子可以用 20 种房子去表达。所以在定义数据结构的时候，我们要引出一个很重要的东西：asset reference——资产的引用。无论你定义的是二进制还是 text format 的 asset 系统，你一定要支持跨文件的这种引用（cross-file reference）；有了这样的引用之后，你才能把这些重复的东西全部提取出来。

这也是当我们去做一个引擎工具链时一个很根本的认识：你面对的不是一块巨大的数据，你面对的是成千上万的离散的文件，而且这些文件彼此之间是关联的。你觉得做个特效就是特效自己的事？不好意思，你做个特效，首先可能引用到一个特效的蓝图；如果是 Unreal 的话，你可能会用到你自己的 texture，需要动画的 texture，可能还要用到 animation。所以这个过程其实蛮复杂的。游戏里面成千上万、上十万、上百万的资产文件，是像一张网一样彼此关联在一起的。

> **结论**：引用（reference）是资产系统、也是工具链最核心的底层逻辑——工具链面对的从来不是一坨大文件，而是像网一样彼此关联的成千上万个离散文件。

```text
 关卡 level
 ├── 房子 instance × 10 ──引用──→ 房子 definition（只有一份）
 ├── 特效 ──引用──→ 特效蓝图 ──引用──→ 贴图 / 动画贴图
 └── 角色 ──引用──→ 动画 305
```

有了引用，最简单的做法就是：一栋尖顶的房子在我的场景里出现了十次，我只需要放十次它的引用。这十次出现都叫这个房子的 instance（实例），而房子本身的定义叫 definition。这个概念，前面讲 instancing 相关内容的时候反复跟大家讲过。

但是当我们做工具链——工具链会直接影响到你底层的数据结构——会遇到一个真实的情况，这个时候就反映出 artist 和程序员思维方式的不同了。比如这个 artist 把一块地板拷了十遍。作为程序员的想法是：我都已经让你能拷十遍了，而且还只用了一份的存储空间，我已经很厉害了对不对？不好意思，artist 说：我觉得拷了十遍，虽然它们分散在各个地方、你提供了让它旋转、放缩做各种变化，但是我觉得还是不过瘾——我想把其中五个的贴图换成其他的贴图。程序员就很抓狂：你换了它的贴图，那你应该做一种新的定义呀。但不好意思，作为艺术家，他不会这样去做，因为他在编辑环境里面希望所见即所得：我看见这个贴图不爽，我马上就要把这个图换掉。

所以我们在工具链中对每一个对象进行实例化的时候，要给它提供一种叫做 variants 的能力——做它的变种的能力，让用户能够直接在工具链中把一个物体做出变化。那最简单粗暴的做法是什么？我把这个物体在我的关卡里面再拷贝一份，你想改啥就改啥——大哥你牛，你拷完之后随便你怎么改。但这个做法从数据处理上来讲是一个低效的做法。为什么？第一，一个物体的描述可能有几百个数据，你只动了一个——比如它的颜色、它一张贴图纹理的路径——其实你改的东西很少；第二，比如我想对原始的物体做一个总体上的调整，比如把它的网格做了调整，我希望它的其他分身都相应地发生变化——但一旦你拷贝之后，它们之间的关联就彻底断掉了。

所以这个时候，我们引入一个很重要的概念：data inheritance——数据继承。这实际上也是工具链一个非常重要的底层技术：用户在这么多工具中来回操作，会产生很多数据，而数据是可以继承的。大家在学高级语言、学 C++ 的时候，定义了一个类，类的派生就是继承于它的父类，方法很容易继承。数据继承是什么意思？一个 structure 的实例，比如一个正方体的 box 设了长宽高；我另外一个数据继承于你，长宽都不改，只改你的高——我这个数据就是继承来的。

这个方法其实你说它难吧也不难：实际上就在于我们定义数据资产、定义 asset 格式的时候（比如我们用的类似 JSON 的格式），加入一些相应的属性段，描述"我这个数据继承于哪一个数据，哪个 field 我要改掉、我把它改掉"。这样的话，当我们的工具链或者引擎读到这一块数据的时候，我就知道：先把原始数据拷过来，然后根据你修改的部分把它修改掉——这样我就造出了一个新数据。

其实非常有意思：大家去理解工具链的时候会发现，工具链玩的全是数据——实际上是各种各样的数据在各个工具之间流来流去。怎么深刻地理解数据、怎么保证数据的灵活多样、但又不会混乱，实际上是我们在做 toolchain 时非常核心的一个发力点。

### 加载的真相：先把文件解析成一棵树

好，我们知道这些数据怎么去存了，把数据存到硬盘上了——其实刚才讲了那么多，我只是把 serialization 这一部分给讲完了。我的标题叫 load and save，但讲了半天，只讲了如何定义数据、如何 save 数据。那真正难的问题就来了：磁盘上的数据我怎么去 load？也就是我怎么去 deserialization？这事儿其实并不简单。如果你不去做引擎，不用太关心，反正人家定好的 format 直接用就好了；但如果我们 GAMES104 的小伙伴想做自己的引擎、想定义自己的工具链，那这一趴同学们要去听一听了。

对一个 asset，加载进来之后，并不是像大家想象的沿着文件一通读就完事儿了——实际上它是一个 parsing（解析）的过程。什么叫 parsing？大家想象一下，一个场景文件里面有很多的数据块，每个数据块有很多 field，有些 field 有不同的 value、不同的 type。那你怎么去处理它？实际上你要对整个文件进行扫描——不是依次去读它。扫描的时候，你要去检查每一个 field 是不是存在：比如你检测到一个 key value，它的名字叫什么；接下来你说"我找到你的值了"；然后我把你的名字、值、type 放到一块，变成一个 pair。

但有的时候会出现这种情况：一个数据指向了另外一块数据，而那块数据其实我还没有读到。大家想象一下：我们看数据的时候，是把它当成一个完整的、整合在一起的东西看的；但电脑——记得我以前讲过图灵机对不对？图灵机是什么？是一条纸带，它只能一格一格地读、一格一格地写，另外带一个小小的 memory。比如你这个角色的第三个动作，是要用到动画 305 的；好，305 这个动画还没读到，那我继续往后读、读、读、读，读到后面的时候，才把动画 305 读到，读过来之后我才知道这个数据是什么。所以说，其实我并不是一上来把所有的数据全部加载进来，而是一上来先要把这个数据拆分成一个个的语义，然后把这些所有的关键的 key、value、type 全放在一起。它最后会生成一个什么东西呢？生成一个树状结构：所有 field 的 key、它是什么类型、还有它的值，形成一棵树。

大家如果去分析一下所有像 XML、JSON 这样的语言，你会发现无论多复杂的文件、多复杂的 asset，它都是个树状结构。其实我们在做游戏引擎资产管理的时候，用的也是这种结构——树状结构。这很像大学里编译原理的那个 AST（abstract syntax tree，抽象语法树）：你写了一段很长、很妙笔生花的源代码，交给编译器的时候，它管你写得多漂亮，给你生成了一坨非常抽象的 AST。AST 长什么样？大家稍安勿躁，我们在下一节课讲反射的时候，会让大家见识一个让你大跌眼镜的 AST 长什么样，今天不展开。但逻辑上，其实就是这样的一个结构。

其实这就是我们对世界的表达。就像我们去理解这个宇宙、理解这个世界：如果我把对象一个个都罗列出来的时候，我们是没办法理解这个宇宙的。那我们怎么去理解一个国家？很简单，前几节课讲过这个概念——我们构建一个树状结构：第一个根节点叫"国家"，把国家分成省，省分成市，市再分成每一个区，市里面每个区里面再分人；这是其中一个分支。另外的分支呢？比如按企业、行业、部门、部队这样一个个分。我用一个树状结构，就可以把一个极其庞大复杂的系统给表达出来。而且这里面，它们彼此之间还可以相互引用：比如有一个个体的人，他属于哪个省、哪个市；但是他又属于哪一个政府部门，他又是从事什么职业的，然后他和谁谁谁又有什么配偶关系。所以这样的一个树状结构、它们彼此之间能够相互引用，实际上就是我们 asset 真正的底层的结构。

```text
  磁盘上的资产文件
        │  对整个文件做扫描（不是从头到尾依次读就完事）
        ▼
  一个个 (key, value, type) 语义对
        │  引用先记下来：目标可能还在文件后面
        │  （例：角色第 3 个动作要用动画 305，而 305 在文件后面才读到）
        ▼
  树状结构：所有 field 的名字 / 类型 / 值
        │  第二次处理：按引用取数，构建资产
        ▼
  内存中可用的游戏资产
```

#### 文本的加载路径

如果我们去加载一个 text format 的资产，实际上前面需要一个非常复杂的 parsing 过程。大家去理解一下、看看我们的小引擎：我们不是用 JSON 作为数据载体吗？你如果读那段代码，会发现我们首先调用的是第三方的库，它把 JSON 的文件变成一个 tree structure——你也可以叫它 dictionary（字典）；然后我要任何数据，我就去问它，通过它的第二次处理，我就可以拿到我想要的资产。

#### 二进制的加载路径与字节序

但如果你是二进制的话呢？其实一般在二进制的头部，我们会把这个树状描述存下来：比如我有多少个 field、它的名字叫什么、它的 type 是什么、它的位移在哪里——数据就在那里。因为我知道了 type，就知道我要读多久。我先把整个二进制文件的描述放在前头，接下来的数据我就可以快速地去处理了。所以这是我们做 deserialization 时非常重要的一个方法。

但是，如果我们用二进制做 deserialization——特别是我们在做真正的工具链的时候——大家要特别注意一个事情：endianness。这个词中文叫什么呢？说句实话，我也不知道该怎么优雅地翻译（一般译作"字节序"），而且这个东西我个人是实打实觉得头疼的一件事。大家知不知道，在计算机系统的早期有两派之争：一个叫 big endian，一个叫 little endian——这个很像甜豆浆和咸豆浆之争，真的特别特别无聊，但是给我们惹了很大的麻烦。同样一个整数，高位的部分是存在前面还是存在后面，两派的做法是不一样的：大端（big endian）把高位字节放在前，小端（little endian）把低位字节放在前。听起来像无聊的口水仗，但只要你的数据要在不同字节序的机器之间流转，它就是一个实打实会翻车的坑。

## 工具链的深水区：版本兼容、鲁棒性与所见即所得
> 对应块：BLK29 | 覆盖分集：P16下 | 块标题（分集名）：《第十三节：引擎工具链基础》

低位存在前面，还是高位存在前面？就为这么一件事，两派打起来了：Intel 的 x86 架构是 little-endian，IBM 的 PowerPC 架构偏要来一个 big-endian——你说这有意思没意思？但没办法，这就是事实。我们要兼容 Linux 的各种硬件平台，要兼容 Mac、各种 Android 设备，还有游戏主机和 PC，这些看起来很奇怪的问题就都得解决。字节序还只是道开胃小菜——这一讲往深处走，全都是真正动手做引擎工具链才会撞上的硬骨头。

### 字节序：跨平台的第一个坑

这个问题复杂吗？其实一点也不复杂。工具链里面我们一般会这么约定：既然通常是拿 PC 作为编辑器平台，那就把整个工具链统一锁死为 little-endian，编辑器里面随便用。字节序的分歧留到数据出口去解决——当我在做序列化处理、也就是加载这些数据的时候，比如突然发现我是在一台 PlayStation 上解压数据，那我就做一次 swapping（字节交换），把所有 little-endian 的数据变成 big-endian。这个过程甚至可以离线做：给 PS5 打包的时候就把这件事做好，这也是完全可以的。

> **结论**：编辑器一侧统一锁死为 little-endian，把字节序差异推迟到数据出口一次性解决——要么在加载时做字节交换，要么在打包阶段离线完成。

写引擎工具链的时候，这一点确实要注意——我们自己现在就已经撞上这个问题了。所以同学们以后做引擎，要记住：跨平台里面，endianness 是一个很头疼的小问题。

### 资产版本兼容性：工具链最难的问题

讲到这儿，大家可能会觉得：虽然听得半懂不懂，但工具链基于资产系统怎么构建，我知道了；GUI 怎么做，我知道了；数据怎么组织，我也知道了——接下来再学会怎么构建这些编辑器，我基本上就能动手做了，对不对？现在我来讲一个更有意思、也是我一直认为做工具链最难的一个问题：你怎么做到资产的版本兼容性。

很多人第一反应是：怎么还有个版本兼容？想想你用 Word 的时候——有多少人意识到，Word 其实是一个非常难写的软件？我是 2010 版的 Word，编辑了一个文档；现在 2023 版的 Word 出来了，它还要能打开我 2010 版编辑的文件。这个向下兼容，大家想想怎么写？有同学说：这很简单嘛，我 check 一下版本号，if 你的版本对应 2010，我就怎么怎么样。这个做法当然可以。但更偏激的问题是：假设这个文件是 2023 版编辑完的，你 2010 版还能不能打开它？实话实说，现在 Word 的处理是很糟糕的——基本上没办法打开，它只会告诉你"你这个版本号更高，我打不开"。

> **定义**：backward compatibility（向后兼容）——新版本的工具要能打开旧版本产生的数据；forward compatibility（向前兼容）——反过来，老版本的工具也要能正确处理新版本产生的数据。

#### 向后兼容：三年前的场景必须打得开

先想一下，一个游戏真实的研发过程有多久？大概是 3 年左右。3 年前，大家做了很多资产：编辑了一个很漂亮的动画，做了一个很酷的场景。这 3 年里，引擎会不停地升级，工具也在不停地升级——会加很多很多数据，也会删掉一些数据。那难道美术 3 年前做的那个场景就不能打开了吗？你想想看，美术是不是要跟你拼命？人家工作了几个月的成果，你以为你老人家版本一升级，大家就完蛋了？

#### 向前兼容：老工具也要能读新数据

还有一种情况：在一个团队里面，大家的工具版本基本上每隔一两天就升级，但有的时候，有的同学手里还是老的工具，却要打开未来同学们的版本创造出来的素材——这个情况是真实存在的。我们也希望这种时候工具不要崩掉、引擎还能继续跑。你可能觉得：只要做好团队管理，"用老平台跑未来数据"这种事应该不需要吧？但在很多环境中、特别是在分布式部署的环境里面，这个需求是很刚需的。

这就特别像大家很好奇的元宇宙。我个人一直认为元宇宙这个概念现在很不成熟，就是因为它有大量这样的问题：比如我几年前开发的一个应用，未来别人生产的 application 产生了一个虚拟人，他要进入我 3 年前开发的虚拟游戏场环境——他在我这儿也能玩。我不能因为他的那个 application 就再去升级我的游戏，因为很可能做那个老 application 的团队已经解散掉了。实际上在 metaverse 上会有很多 application 就是这么跑不起来的。这里讲得比较深，但我想让大家建立一个概念：当我们要定义一个真正商业级的游戏引擎时，资产的版本兼容性是一个非常专业、非常重要、必须认真思考的东西。

#### 字段删了、字段多了，怎么办

具体讲起来很简单，你会遇到两种情况：一种是你原来的一个 field 被人删掉了，比如里面的 transform 被人干掉了；另一种是未来系统越做越复杂，field 越加越多，而你的数据文件还放在那儿，你得把它打开。

那怎么办？有一种简单粗暴的做法：每个资产由程序员手写版本号。检查的时候一看：我已经升级到 7 号版本了，你的资产还是 6 号版本——我就知道有一个数据是你没有的，好，给你塞一个 default value（缺省值）；反过来，如果你的数据多了，那我就不读，虽然还读得到，但我不处理它，把它跳过去。这个方法实话实说，我个人不是特别敢苟同：随着一个系统 3 年、4 年以上的发育，你会发现要兼容的 version number 越来越越来越多——这是很糟糕的一个方法。

#### Protocol Buffers：给每个字段一个唯一编号

给大家推荐一个做法，这是 Google 提出来的。Google 是全球可能最大的分布式系统应用场景，肯定会遇到这种问题：它的平台上要跑成百上千种不同生态的软件，这些软件由不同的开发商开发，版本各自以不同的频率更替，之前的数据还要来回通讯——张三的软件更新了，李四的没更新，王五的软件又回退了，那数据通讯就全部完蛋了。于是 Google 提出了一个叫 Protocol Buffers（protobuf）的 format。

它的想法我认为又简单又好使，其实非常简单粗暴：定义每一个数据 field（属性）的时候，给它生成一个 unique id，你保证这个 id 一直单调递增就好了。这样，当数据不断更新的时候，我就比较你这个 id 有没有发生变化。

```proto
string guid      = 1;
string file_name = 2;
```

这里必须吐槽一下它的语法定义，我真的不敢恭维。作为一个有点强迫症的 C++ 开发者，我当时看到：大哥，你这不是让我在赋默认值吗？要是我们这种 XML 控、JSON 控，会说"你给我加个冒号"——`guid: 1` 我都好一点，都能忍；你让 field 直接 `= 1`，我就会觉得你在赋缺省值。但可能大家习惯了也就好了。我相信 Google 大大这么做一定有它的道理，我不懂，只能说明我水平不够——所以大家完全可以无视我这段点评，但一定要去学习它的思维方式，这个思维方式真的非常好。

游戏引擎面对的环境跟 Google 有点像：它有大量的模块，由不同的开发者开发和维护，版本变化很快。一个商业级游戏引擎的数据 format 可以达到几十甚至上百种，每一种格式都由不同的团队开发和维护；而 artist 打开一个工具——比如地图编辑器——的时候，可能会同时面对几十种完全异构的数据。我们怎么能保证整个工具体系的鲁棒性？版本兼容性就是一个非常重要的核心指标。而且在网络环境下、分布式部署情况下，这个问题会变得更加复杂。所以我一跟同学们讲就是：游戏引擎是一个大型软件工程。这个时候大家应该有一点点感觉了——你要伺候成百上千的艺术家老爷、设计师老爷，就要求你这个系统做得相当鲁棒。

### 鲁棒性：背锅侠的自我修养

你要知道，做游戏引擎的人在游戏团队里，大家是不是觉得地位很高？实际上你们错了：做游戏引擎的团队是地位最低的。为什么？因为我们在服务所有的人，包括程序员——程序员要基于游戏引擎开发游戏嘛。举个例子，在我们这个行业里，如果一款游戏失败了，大家首先想到背锅的是谁？不是策划，不是美术，不是程序——一定是游戏引擎："对不起，我的游戏引擎选错了，所以我这个游戏就失败了。"所以大家如果想做游戏引擎，一定要有这个觉悟：做好背锅侠的准备。

既然要背那么多锅，那我们就索性把系统做得再鲁棒一点，少挨点骂。特别是工具链，它的鲁棒性要求是非常高的：游戏引擎的工具链一旦出问题，对整个团队的影响非常大。大家想象一下，你的游戏引擎工具崩了，几百人一上午什么事情都干不了，等着你把这个 bug 修好——你作为一个引擎开发者，内心压力有多大？我们是亲身经历过的，那种感觉真的如坐针毡，会觉得欠了大家很多很多钱。所以让工具鲁棒、易用，是工具链非常核心的一个点。

那怎么让工具变得鲁棒？首先、也是大家最需要的东西，就是 Undo/Redo。

#### Undo/Redo：所有编辑器最后的核心

Undo/Redo 听上去不起眼。我最早做编辑器的时候，脑子里想的都是很多花里胡哨的 feature：做一个很酷的植被系统，刷子一刷，山川河流都给你变出来；要做最酷的悬崖峭壁；要做刮风下雨。但实际上你会发现，artist 跟你讲的是："大哥，我刚才做了一个误操作怎么办？"你总不能让人家把数据删掉重新再来一遍吧？那你就疯掉了。你会明白：所有的编辑器到最后，最核心的功能其实就是 Undo/Redo。

而且对游戏引擎来讲，Undo/Redo 非常复杂。为什么？因为它的很多数据编辑是相互关联（correlate）的。举个例子：我现在改了一个房子的颜色——房子没问题；绕着房子旁边种了一些树——也没有问题；这时我突然决定把地面往上拉个 3、4 米，形成一个小土坡，房子和树都会相应地发生变化；然后我看这个房子不错，又在旁边自动生成一些 decal——房子周边往外延拓的沙地、空白地的感觉。这时候让你 undo，你会发现有些操作会影响到其他东西：你首先把房子给干掉了，旁边那一圈 decal 可能就有问题；当你把刚才地形的调整改回去之后，刚才种的那些树，角度可能也都会发生变化。所以在游戏引擎里，Undo 和 Redo 彼此之间有很深的 correlation。

#### 崩溃恢复："还我数据"

另外一个问题：你做得再好的工具，都会 crash。crash 之后，艺术家编辑了一个小时的东西——人家也不会想着去存盘——突然就崩掉了，那怎么办？那是要你的命了："还我数据！"我怎么还？我又不会画画，又不会做关卡。作为游戏引擎工具链的开发者，这是非常需要花时间想明白的一个问题。

幸好，我们有伟大的 design pattern 支持我们。这个问题在软件体系里是一个 well-studied problem——被研究得非常透的问题。大家用 Word 写文档、用 PowerPoint 写 PPT：挂了之后再打开，它会告诉你有一个 recovery，redo/undo 也都非常方便。它背后就是一个非常标准的 command pattern。

### Command 模式：把编辑拆成原子

Command pattern 的思路是：把用户所有的操作分解成无数的小 command，这些小 command 逐渐累加，非常原子化地执行。注意一个细节：不是每一个用户操作对应一个 command——有的时候，用户的一步操作我们会分解成好多好多 command，这是有一定道理的：尽量让 command 原子化。然后，我们会把这些 command 定时地存到磁盘上，万一系统挂了，就从磁盘上找回来。用户要 undo 的时候，简单地说就是 revoke——把刚才的操作回退出去；执行则叫 invoke。这套 pattern 非常符合人的直觉。

#### 一个 Command 长什么样

Command 的定义比大家想象的要简单得多。最简单的描述：每个 command 给它一个唯一 ID——待会解释为什么要有它；然后要有一串 data；它是一个 interface，每一种 command 要自己去定义。最核心的是两个函数：一个叫 invoke——这个 command 要去执行它；一个叫 revoke——我不干了，退回去一步。

还有两个函数大家可能注意不到：serialize 和 deserialize。仔细想想其实有道理：把这个 command 存到磁盘上怎么存？从磁盘加载怎么加载？有时比较多的 command 操作，我们甚至会存在临时文件里，甚至内存文件、内存数据库里，都是有可能的——所以序列化与反序列化很重要。还有一点（这个下节课会讲）：如果我们要做协同编辑，这个东西是不是也有用？

#### 唯一 ID：保住操作的原始顺序

为什么每个 command 要给一个编号？这个编号首先是唯一的、单调递增的。当 command 不断累加时，唯一性意味着什么？意味着一种隐含的序列。这为什么重要？因为当我进行回退（revoke）、进行恢复（recovery）的时候，我希望它的执行严格遵循原始的顺序。真正做编辑操作的时候大家会知道：很多操作如果执行的顺序不一样，结果会完全不一样。所以唯一 ID 就是保证顺序的核心——单调递增这一点，在写 command 系统的时候一定要注意。

> **易错点**：command 的唯一 ID 不只是为了去重，它隐含了执行的序列。回退与崩溃恢复必须按原始顺序严格重放——顺序一变，结果就变。

#### 序列化交给数据自己

Command 系统里的序列化，一般不是 command 系统自己写的，而是由数据自身提供标准的 serialize / deserialize 方法。比如我要加一个 GO（Game Object）——加一个角色：那这个 GO 自己要提供"把我当前在内存中的全部状态（比如这个 character 的所有数据）序列化下来"的方法；command 系统说 OK，我现在决定创建一个角色，这个角色所有的数据，就按 GO 自己的序列化方法存下来。

所以实现这套 command 系统还有一个副产品：它会变相地逼着我们把整个引擎的系统写得非常干净，让引擎所有的操作都能原子化。

#### 三类原子命令就够了

Command 系统里，目前大家总结下来最标准的就是三类。第一类是 Add：创建一个对象——它可能是一个 GO，也可能是别的东西；第二类是把一个对象删掉；第三类是对对象的某个值进行改变——改变对象的一个 field，比如它的速度、大小。你会发现，无论多么复杂的 API 系统，用这三类 command 基本上就能表达。有空可以去研究一下文本编辑器：它所有的 revoke/invoke，基本上就是增加一个 text、删除一个 text、更新一个 text 三类操作就解决了——这是非常了不起的一件事，也很有道理。

#### 这套结构一定要趁早架

如果同学们要搭自己的工具链，我会非常建议在很早期的阶段，就把这一套结构架好：早期架好之后，随着工具链的功能越来越复杂，你不断地丰富和完善它，这个系统就会比较稳定。你千万不要等工具链已经做得比较大了，再开始做这套系统——我告诉你，这个事情非常痛苦，因为我们自己是经历过这个痛苦的：一天上百个 bug 扑面而来的感受，大家想象一下，压力很大。

讲到这里你发现没有？我讲了这么多，还没有讲一句话"工具链到底怎么写"。为什么？因为每个工具的写法都不一样。但是这些 foundation——资产系统、command 系统、GUI 体系——才是做工具链最重要的基础。这也是让大家不要急着写：我经常看到有同学说"我做了一个编辑器，做得特别帅，你看我这个地图可以拖动什么什么"。是的，这东西单独做一个是很容易，做十几个功能也没有问题；但你真的开始面对一个 editor、面对上百个功能、十几个不同的 editor 的时候，你会发现前面这些事情没做对的话，你会非常痛苦。

### Schema：异构数据的统一语言

为什么这些基础那么重要？因为我们要构建的不是一个单一的工具，而是一个工具链（toolchain）——很多工具在一起，它们彼此之间是有血缘关系的：要彼此通讯、彼此联系，互相说的话要互相听得懂，这就是很挑战的一件事。工具链面对的是完全不一样的 user，每个人的需求都不一样。如果每一个工具都单独去写，这个工具链就没有可扩展性、也没有可维护性——因为这些数据全部都是异构的。虽然前面讲了 asset 怎么定义，但 asset 之间每一个工序长得都不一样：我一会儿要编一个点光源，一会儿要编一个角色动作，一会儿要编场景 decal 的分布——每个数据我都知道怎么定义，但它们彼此之间是异构的。

所以这里要引入一个非常重要的思维方法：从各种各样的数据中找出共性。当你打开一个数据，你会发现：再复杂的数据，都是由很多简单的 building block 构成的。比如去描述一个点光源，很多时候就是：一个 vector3 的坐标（点的位置），它的方向也是一个 vector3，再有一个颜色——各种各样的颜色（比如 diffuse）。这些都是非常基础的 building block。

在这里面我们观察到一件事：任何复杂的数据，都可以把它描述成一些简单数据的集合。这像什么呢？就像现在的物理学——虽然这个世界非常复杂，但我们会找到基础的原子，一百来种原子，就可以通过它们的组合去表达这个世界的任何一种物质。

#### 从原子到"分子式"

那么，如果这些"原子"找到了，接下来我们需要一个东西，叫 schema。这个词很有意思：a description structure，一种描述的结构。用刚才的类比来讲，schema 更像分子式：它描述这个物质是由哪些原子构成的。比如今天我要定义一个长方体，它的描述就是三个量：float 的 x、y、z，代表它的长宽高；我要表示一个圆，其实一个 float2 就表达出来了。这个"float 加一个东西"的结构，就是一个 schema；按照这个 schema 写出的数据，就是一致的。

> **定义**：Schema 是一种描述结构（a description structure）——像分子式一样，声明一份数据由哪些基础字段构成、每个字段的语义是什么。

Schema 系统是游戏工具链最核心的一个底层：在游戏工具链里流转的所有数据，都要用 schema 统一地描述和定义，这样数据彼此之间才能解读。

#### 工具是怎么"看懂"数据的

比如地图编辑器打开了一个角色：这个角色如果有 schema，我就知道它的 character name 叫什么、它的放缩是多少、它用的是哪个 mesh、哪个动画。这样一个角色拖进编辑器，编辑器的 panel 里就会出现它的名字、它的动画；你点那个动画的播放，角色自己就可以动起来。注意：这些代码全部不是角色自己的 code——全是通过 schema 告诉各种各样的工具，该怎么理解这个数据、每一个数据的语义到底是什么。

Schema 还可以用这些最简单的元素，构建出各种你想要的 high-level 数据。举个例子：一条 curve。Curve 在游戏引擎里很重要，比如粒子系统里怎么表达一条色带随时间的变化？我可以把 RGB 通道变成 curve，在 schema 里把它表达成一组点的集合。用最简单的元素，schema 就能构建出各种各样的 high-level 数据。

#### 继承与引用

Schema 本身是一个非常复杂的体系，这里讲两个概念。第一，设计 schema 时需要有继承关系——这非常像高级语言里类的派生继承，因为 schema 本身就描述了一种类。比如定义一个"人"的 schema：身高、长相、体重等等，所有的数据。第一类派生叫"军人"：你不用重写一遍，从人的 schema 派生出来，再加两个 field，比如战斗力是多少、血量是多少；再派生一个"商人"：他有多少钱、经商能力是多少。Schema 实际上就非常像高级语言里的类型系统。

第二，schema 里要允许互相 reference data——前面讲过 reference data 非常重要。比如定义一个车的描述时，有些 field 就是指向另外的资产和数据的。所以 asset 之间的关联有两种：一种是动态的，就是数据实例之间真实的关联；另一种是类型之间的关联。比如表达一个角色，它会引用到一堆文件：网格、动画、行为树……而在这个 mesh 文件里，又会引用到纹理、贴图……这些文件就全部引用起来了——在数据定义层面，也会形成一个关系树。

所以构建游戏引擎的时候：首先，一定要构建一个 schema 系统；第二，设计 schema 系统的时候，我会强烈推荐大家建立 schema 之间的继承——这样可以不断地派生出各种各样的变种；再一个，中间要允许用户定义各种各样的数据引用。

#### 两种定义流派：独立文件 vs 代码内定义

Schema 的定义非常像高级语言，所以产生了两个流派。有一类流派直接用类似脚本的语言、或者用 XML——其实 JSON 也可以——直接定义 schema，数据很干净；然后用一套方法把它反射成引擎的代码，让引擎直接根据 schema 就知道怎么去读资产文件：资产文件怎么读、怎么写、怎么编辑，全部自动生成（这里其实值得画一张更有意思的图，我们就不展开了）。另一种方法大家非常熟悉，比如像 Unreal 的做法：我定义了一个 C++ 高级语言的类，但通过一个宏去描述"这个东西是一个可以反射的数据"；类里面定义了很多变量，我不用所有的变量，只挑出几个希望它在文件中有反射的变量，包括一些方法也都能反射。

大家回想一下，我们的 Piccolo 引擎用的是哪个方法？Piccolo 用的其实是 defined in the code，跟 Unreal 的方法是一样的；另一种方法我们也写过。哪个好哪个坏？说实话，我很难给出评判，我个人觉得这两种方法各有利弊：

| 对比维度 | 独立文件定义（脚本 / XML / JSON） | 代码内定义（C++ + 宏反射） |
| :--- | :--- | :--- |
| 可理解性 | 非常好理解，数据定义一目了然 | 相对复杂，要理解反射机制 |
| 与工程的关系 | 数据定义和工程实践彻底剥离 | 数据定义与引擎高度匹配，编译完自成一套 |
| 方法与 API | 很难定义接口与动作，强行靠反射显得笨 | 可以直接把方法包进去 |
| 版本一致性 | 依赖代码生成器，schema 与引擎二进制版本容易不一致 | 不太会出现两个版本不兼容 |
| 出错形态 | 检测到不一致就拒绝启动，非技术同学觉得蛋疼 | 改数据结构动辄编译失败或运行崩溃，debug 成本高 |

先看独立文件定义。它的好处是非常好理解，而且真正彻底地把数据的定义和工程实践剥离开了。但它比较麻烦：第一，它需要一个自动的代码生成器，根据你的 schema parsing 生成各种各样的代码，很容易出现 schema 版本过新或过老、而引擎二进制跟它版本不一致的问题。当然有很多方法可以检测——比如它发现 checksum 是错的，引擎就拒绝启动，死给你看；你说"我知道了，schema 文件配错了"，但对非技术性的同学来说，这个事情就特别的蛋疼。所以两边版本不兼容，是这种方法经常会遇到的问题。第二个经常遇到的问题：文本方式很难定义"这个东西能做什么"——比如一个角色有很多的接口、可以做很多动作（API）。当然可以强行做：把函数名写在那儿，通过反射在 C++ 里总是能找得到的，但这个事情就显得有点笨。

而如果把数据定义彻头彻尾剥开了、真的变成一个纯粹的数据定义，反而在引擎里用代码直接定义 schema 有它的优势：可以直接把一些方法包进去；而且因为数据定义和引擎高度匹配，一编译完，整套就全下来了，不太会出现两个版本不兼容。但它的问题是复杂：比如像虚幻引擎，很多使用者会发现，当你真正去动引擎代码、改变一些数据结构定义的时候，经常编译就挂了；或者编译编得过、跑起来就崩了，之后要花很长时间去 debug。而且工具链一旦炸掉，对整个团队的影响就会非常大（当然我们会通过单元测试尽可能覆盖）。所以在 code 中定义 schema，对于巨型系统来讲，对你的工程稳定性和架构鲁棒性要求是蛮高的，否则特别容易出现把整个引擎加工具链一起搞死的情况。

所以两种方法很难说好坏、各有利弊，大家可以根据自己的情况去选择。我们这次做 Piccolo 的时候，是想教给大家一些有意思的概念，所以选择了宏（macro）这套方法。大家一直很想知道 macro 这套机制是怎么 work 的——你看懂了宏反射的机制，就不会觉得虚幻引擎的反射很难理解了，它们的核心底层逻辑是非常接近的。

### 同一份数据的三张脸

Schema 其实还反映了一件事：同样一个数据，在我的工具链中、在整个游戏生产体系里，有三张脸。

| 三张脸 | 形态 | 优化目标 |
| :--- | :--- | :--- |
| 硬盘上的脸 | 二进制或文本 | 节约存储空间 |
| 内存里的脸 | 只能是二进制 | 高效处理 |
| 工具里的脸 | 面向人的视图 | 人类好理解 |

第一张脸是给硬盘的：你可以存成二进制，也可以存成文本格式——硬盘存储空间大，随便你怎么存都可以。但真正做商业级游戏的时候，我们还是会很在意存储空间：几十个 G 和上百个 G 的体量，体验是完全不一样的；而且上百个 G 的文本，加载速度那可是非常感人的——应该没有任何一个商业级游戏公司会这么干。

第二张脸在内存中：没得选，一定是二进制的，它的核心是以高效处理为目标——内存里的数据结构定义，一切以数学运算快为依据：加减乘除、拷贝、添加、删除，速度优先。而在存储中，我们一般尽量节约空间。举个例子：投影矩阵，虽然它是个 4×4 的矩阵，但实际上你用到的往往是 4×3，甚至 3×3 加一列平移——这时我们就会做很多数据的压缩处理，这是一个非常重要的方法。

第三张脸最有意思，就是工具的 view。这里有个细节：schema 里定义的一个 color，数据上是三个整数；但在工具里，我们会把它变成大家看得到的颜色——点开之后，是一个符合人类理解的调色板。这就是工具最核心要解决的问题：对不同的人展开不同的 view。

举个简单的例子：设置引擎数据的时候，很多时候我们会设置角度。引擎中一般用弧度——为什么？因为所有数学库的 sin、cos、tan 这类计算全部是基于弧度的；你如果理解计算机里怎么做数学运算，就知道弧度是最基础的表示。但你跟 artist 讲"你输入一个 3/4 π"？直接就疯掉了。所以我们输出给用户的全部是欧拉角：270 度、180 度、360 度、45 度——这样人类就非常好理解。类似这样的东西，在整个工具链里非常重要：设计工具链的时候，一定要把数据变成一个人类可以理解的 view。

同时，有些数据非常复杂，怎么办？我们可以提供两种 view：一种是 default 的简单 view，只放必要的、你可以调的数据；另一种是比较丰富的、展开的 view。这都在解决同一个问题。这意味着当我们在定义 schema 的时候，对每一种数据类型，实际上要提供"为它定制不同 view"的能力——这也是做工具链很重要的一种方法。

### 所见即所得：工具体系的核心精神

最后讲一个名字很酷的东西：WYSIWYG。现在这种缩写满天飞，你第一次看见它肯定会觉得：哇，这什么玩意儿，这么长、这么诡异——倒是没有 YYDS 那么传神。但它其实是一句很酷的话：What You See Is What You Get——所见即所得。可以把它理解成我们构建整个工具体系的核心精神。

为什么这件事情这么重要？因为工具对于 artist 来说，是一个最重要的 preview 的东西。

#### 美术与设计师各要什么

最早以前，很多游戏引擎的工具是独立去写的，后来 artist 为什么不满意？因为他不能接受：我在你的编辑器里调出的效果——它的光照、材质质感、人物动作——和真实游戏跑起来的东西不一样。如果这两个不一样，艺术家的效能将极度下降。所以他要求在工具链里实现一比一、百分之百还原的 preview：我要知道这东西放到游戏里长什么样，否则这个材质我没法做。

对 designer 来讲，工具链是一个非常重要的 gameplay prototype 的工具：他要在这边用最快的方法做原型。比如快速决定加一组墙去阻断，这时候我要感受一下：玩家拿到这把枪的时候，射击的感觉是什么样；我能看到什么、不能看到什么。设计师需要用最快的速度、最低的成本，去尝试不同的关卡 layout。无论设计师还是艺术家，对工具链提出的要求就是：我希望所见即所得。

#### 从独立工具到架在游戏之上

那之前是怎么做的？这就要讲工具链在整个引擎里的架构方法。

最早期的架构，一般是把工具链独立放在一边。为什么独立？因为工具链的逻辑非常复杂、编辑的细节非常多。想象一下，对一个简单的物理对象做拖动和移动操作——那个小旋钮叫 gadget——它背后协调的逻辑很复杂：要实现自动吸附；旋转的时候要按整数角度步进，比如 5 度一格；还有自动 alignment；快捷键要在旋转、平移、放缩之间来回切换；而且你还要自动对齐。大家用过 Vi、用过 Word 这些软件就知道，这些细节其实非常多，里面有很多很脏的代码，而且非常 special。

所以你最自然的感觉就是：我要保持一个非常 clean 的引擎——你可以共享我一些代码，OK，但工具链这些脏的部分，比如如何编辑一个动画、如何做行为树、如何管理资产的摆放，全部独立出去，它是一个独立的工具链。但这种架构会出一个比较严重的问题：特别是在 artist 那一趴，真的所见非所得；对 designer 来讲，你虽然能帮我快速摆放，但我没有办法直接在游戏中 play 一模一样的东西。所以这种方法现在在商业级引擎中用得越来越少了。

现在大家真正用得比较多的架构是：把工具整个架在游戏之上。说白了，我在工具里面直接调用的就是游戏。大家首先想到的是地图编辑器：在地图编辑器里直接编辑场景，然后一键就可以 play——这肯定需要。但实际上不只是地图编辑器：比如做特效编辑器，我希望它一上来跑的也是游戏引擎；包括动画编辑器，还有一些 cinematic——比如虚幻最著名的 Sequencer 编辑器，其实下面跑的就是一个游戏。

```text
  地图编辑器 / 特效编辑器 / 动画编辑器 / Sequencer ...
                       │
                       │  工具直接调用游戏（架在游戏之上）
                       ▼
  编辑层 editing：编辑场景 + 所有编辑逻辑、中间数据与状态
                       │
                       ▼
               引擎 Runtime（游戏本体）
```

读图：工具不再各自为政，而是整体架在游戏之上——编辑器里看到的效果，就是游戏运行时的效果。

这样的好处是：我调好的材质、做好的动作、调好的光、设计好的特效，在游戏中看到的东西和在编辑器里看的东西一模一样。这个方法本身从设计架构上要求是蛮高的——它要求游戏引擎能够向上兼容编辑器的需求；但它带来的好处、特别是对生产效率的帮助是巨大的。所以在现代商业级游戏里，我们一般都会采用这个架构，包括 Piccolo 用的也是这个架构。

这个模型实际上会要求在引擎的 Runtime 上面加一层编辑层（editing）：管理编辑的场景、所有编辑的逻辑，以及编辑相关的各种中间数据和状态；再往上，生成独立的编辑器 UI——就是刚才讲的 GUI 体系，一层层往上去了。这个结构维护起来是比较复杂的。但是如果你们想做一个好的游戏工具链，我会非常强烈推荐大家用这个模型。当然，未来这个结构被淘汰也是有可能的——肯定有人会发明更好的结构；目前为止，行业里大概会觉得这个结构是最好的，因为它能真正实现我们的所见即所得。

### Play In Editor：一键试玩的两条路

这时候还有另外一个很重要的概念：Play In Editor（PIE）。这个功能不仅对设计师重要，其实对艺术家也很重要。我做好了一个关卡，实际去编它的时候，和我真的去玩它的时候，感觉是不一样的。比如我作为一个关卡设计师做 FPS，做了个关卡，我想感受一下在里面打枪穿行的感觉——所以我希望有一键就能 play 的功能，这就是 Play In Editor。PIE 是现代游戏引擎很核心的一个需求。

但 PIE 有两个实现的方法。

#### 直接在编辑器里玩

第一种：我在编辑器里面直接就可以 play。这种做法结构比较简单，而且非常容易实现——等于把编辑的状态直接无缝地去 play。我们的 Piccolo 小引擎就是这个模型。大家记得上次讲小引擎时提过它的一个特点：这个角色跑跑跑，跑到某一帧的时候，你突然说"我要编辑了"，切回编辑器，会发现角色就停在那个位置、保持着那个动作——这就是 play in editor 这个结构。

它的优点是非常简单；缺点呢？编辑的数据和游戏引擎的数据，有的时候会混到一起。混到一起会出什么问题？editor 里面有大量的数据，会污染游戏 play 的逻辑数据。理论上我们会认为两者是分开的，但你写这么复杂的系统，有的时候就是分不了那么清楚。这时可能出现一个问题：这个玩法在 editor 模式里面没有 bug，但当我编成独立的游戏、编成 release 版的时候，突然遇到了一些问题；反之亦然——editor 版里明明有问题，游戏里跑却又没有问题。你可以说这其实是个 bug，但确实，很多时候这么复杂的系统，你很难把它切分得那么干净。

#### 复制一个世界再玩

第二种：像虚幻采取的模型。当你去点 play 按钮的时候，会形成一个专门的 PIE 模式：把现在编辑的所有东西整个拷贝一份，在一个沙盒（sandbox）里面全部重新创造一遍，把环境全部重置，然后在这个 PIE 模式里面去玩这个游戏。相当于我多花了一些内存，给这个世界做了一个单独的 play 分身。

这个逻辑能解决上面说的数据混染问题，而且它本身更能模拟游戏单独的一个运行环境。我个人认为：如果你要做一个大型复杂的游戏，我倒会建议这种模型。这种模型虽然会浪费很多内存，但现在内存还好——我们电脑配个 60 多 G 的内存也能配得出来——实际上是一个比较好的方法。

```text
方式一（编辑器内直接 play）：
  编辑器状态 ──无缝切换──▶ 同一个世界里，游戏逻辑原地运行

方式二（PIE 沙盒世界，虚幻采用）：
  编辑中的世界 ──整体拷贝──▶ 沙盒世界（环境重置）──▶ 独立运行
```

读图：方式一省内存、结构简单，但编辑数据与游戏数据同处一个世界；方式二多花一份内存，换来一个干净、独立、贴近真实发布环境的运行世界。

所以大家做游戏引擎工具链的时候，可以在这两个模型中自己选择、选择适合你自己的模型：如果你做的是一个小型的、不是特别复杂的游戏引擎，那我觉得"编辑器内直接 play"基本上就够用了；但如果你真的希望做到商用级、给很多很多人用起来，而且面对的是一个复杂的游戏系统，我们会建议你考虑 PIE 沙盒这个模型，会更好一点。

### 插件：One More Thing

这是我们真正的最后一个 part 了——one more thing：plugin。对，这个真的是 one more thing。为什么？因为讲到这儿，基本上你所有的工具该怎么做，你都知道了。那为什么我们还要做 plugin？

#### 引擎的本质是一个平台

因为做一个游戏引擎，你要支撑的游戏千变万化，完全不受你控制。你根本想象不到——作为一个游戏引擎开发者，你根本不知道你的用户会用它做什么样的游戏、需要什么样的功能。我们从来不会自大地认为我们做出了所有用户需要的工具——这是不可能的。所以我们一定要允许用户自由地开发各种各样的工具。比如 UE 的一个插件：第三方开发者可以自由地开发一个完整的水体交互插件，水的各种属性都可以在里面调——怎么模拟、怎么仿真。这实际上就奠定了现代引擎的可扩展性（extensibility）：插件是现代商业引擎最重要的一种开发能力。

所以我们经常讲：现代游戏引擎的本质是什么？我认为它是个平台——在这上面可以集成各种各样的功能，而这些功能都是由第三方开发者开发的。举个例子：大家去打开 3ds Max、Maya，比如 Houdini、ZBrush，其实它们都有大量的插件，提供丰富的功能给大家，让你快速地完成功能、适应千变万化的需求。所以插件是一个很重要的系统。

那插件对我们整个引擎、特别是工具链引擎的要求是什么？实际上我们需要提供大量的 API，开放给第三方开发者：他通过我们的接口，能够注册各种各样他想要的功能，定制他想要的 UI，然后对这个世界进行他自己想要的编辑。这里面 API 的设计就非常重要。比如我们要在工具栏上加一个 PIE 的按钮：我知道你的 API，把我的 plugin 注册进去，把我的按钮创建进去——这时 plugin manager 就会帮我把整个东西构建起来。今天当我们去设计一个游戏引擎的时候，它的可扩展性、plugin 的方便能力，我们认为是个刚需。成熟的商业引擎在这方面发展得真的非常好：在虚幻的主菜单（main menu）里加入一个你定制的 menu，其实是非常简单的事。同学们如果想真的做引擎往前走，我会非常建议大家向这些引擎学习，看看它们怎么提供这些接口，让我们的引擎变得真的有可扩展性。

#### 把自己的功能也 API 化

这也反过来对我们的整个引擎架构提出了要求：你要尽可能把你的各种功能 API 化。你自己的编辑器功能——比如做一个 level editor、做地编、做自动 grouping、做 prefab——我尽量通过调用这些 API 的方式组合起来。这样的话，当别人来开发我们引擎的插件的时候，我们彼此是平等的：你用插件，我也用插件，他至少不会受到太强的限制。所以现代游戏引擎在做架构的时候，一定对它的可扩展性、对未来无限扩张的兼容性，提出了一个非常高的架构性需求。

所以同学们如果励志想做游戏引擎——大家肯定都会想"我知道各种各样很厉害的算法，我会做很多很多效果"——但我希望同学们意识到一件事：做现代游戏引擎，其实是一个软件工程学的问题。它最核心的东西，是你要搭一个平台，能够让成百上千、甚至上万、上十万的优秀工程师和创造者跟你一起工作，这样你的平台才可能会成功。这就是基础工具这一章最后想让大家带走的：可扩展性，是工具的一个很核心的诉求。

### 课堂问答

#### 做工具链需要什么能力

第一个问题是"工具链开发需要的能力是什么"——这个问题问得很大，也很有意思。我个人的理解，第一：你对游戏的基本制作要有基本的理解。你最好有时间参与一些游戏的真实开发，真实地看到设计师、艺术家是怎么工作的——这样你才能特别理解我前面讲的那句话：大家的思维方式差别真的非常大，但每个人都是非常合理的。

第二：你对软件架构、软件工程特别感兴趣。你并不一定需要知道很多很精深的算法，但你要有非常好的软件系统架构师的思维方式——因为工具链最核心的就是软件架构。一个功能，你有十种不同的方法把它做出来，但好的真的只有那一两种。为什么？因为好的方法在未来有真正的可扩展性。所以，如果你有一颗励志做软件架构师的心，本身又对游戏很感兴趣，我觉得你就可以成为一个非常好的工具链开发者。

#### Web 前端做工具链，行不行

有同学问：工具链用 web 前端做的多不多？这是一个非常前沿的讨论，我自己现在也没有下最后的结论——我们内部已经做了很多场讨论。首先，现在工具链用 web 前端的好像还不多，比如大家很熟悉的 Unity，包括其他一些商业引擎。但是，随着现在的 H5 越来越强大、web 开发效率越来越高、懂的人越来越多，我自己一直在思考：基于 web 前端的工具开发，是不是也是一个很好的方向？因为它的底层逻辑、底层结构，很多东西是很接近的。特别是基于刚才讲的 in-game 模式来做工具链：最复杂的东西我们全部交给了引擎来处理，那跟用户交互的部分——那些 UI、界面逻辑——用 web 前端的方法去做，效率说不定还是挺高的。

所以这一点，我现在更愿意说它是一个 open question。如果同学们对这个事情有兴趣，我非常希望大家拉上我们的课程组一起讨论——我很想把它变成一个 R&D 的课题：说不定我们可以用 web 技术做出一个完全不一样的工具链体系。比如拿 Piccolo 下手？我们真正的工具链体系可以全部用 web 的技术做一做，看看这里面有没有什么坑。因为确实，专业软件选型的时候，很多时候有很多很性感的技术在那边诱惑我们；但大家会考虑到很多工程上的不确定性——一旦一个决定下了之后，它的成本是非常高的，所以我们会比较谨慎。但这毫不妨碍我们大胆地去想象，用一些前沿的技术去表达。

#### 协同编辑走到哪一步了

还有同学问：协同编辑有没有很好的实现？首先，以目前行业来看，我觉得实现还处在一个早期阶段。比如虚幻 5（UE5），最近它最大的卖点之一就是协同编辑，提出了很多概念。具体协同编辑怎么实现，下一节课我们会简单地讲一下。如果大家有兴趣，其实就算基于 Piccolo 引擎，你都可以做一个非常简单的协同编辑实验——当然，我不会把它做成作业，因为这个有点难。

我认为协同编辑这件事情的重要性在非常快速地提升，大家的方案也会越来越成熟。我个人很相信，大概在 5 年左右，协同编辑这个问题会得到一个非常好的解决：它的基础理论已经基本成熟了，接下来是大量的工程问题需要解决。因为无论哪一个商业级游戏引擎，现在都是千万行代码的规模——这么复杂的一个系统，你要让它全面支持协同编辑、又想保证这些功能不会丢失，工程上的挑战（比如很多向前兼容的问题）其实还是蛮复杂的。

举个例子：大家都觉得 Word 很厉害，它是一个非常成熟的文字编辑系统。但我们一旦把 Word 云化、让大家协同编辑，你会发现它被迫要做很多的减法。我们看到这类系统在过去几年发展得非常快，今天用各种网上协同编辑软件，已经感觉越来越顺手了；但大家看到这个过程，可能需要三到五年的迭代和完善。直到今天，你在本地编辑 Word 的那种强大性、易用性，还是会超过网上协同编辑的 Word。这一点，其实很能反映我们的游戏引擎将来要面临的问题。

## 工具链进阶：世界编辑器与插件架构
> 对应块：BLK30 | 覆盖分集：P17上 | 块标题（分集名）：《第十四节：引擎工具链高级概念与应用》

按惯例，开讲之前先回答两个来自社区的问题。这两个问题看起来是在问"为什么不用某某现成的东西"，背后其实都是引擎设计里实打实的取舍，正好当这节课的引子。

### 为什么不用 FBX：中间格式不等于引擎格式

有同学问：你们为什么不用 FBX 这类公开的格式？这些格式直接来自 DCC 软件，现在也有很多人在用。但我们当时最核心的考虑有两件事。

第一，尽可能让 Piccolo 引擎越简单越好。大家如果研究一下就会发现，FBX 格式非常成熟、丰富、完善——真要支持它，我们就得接入一个完整的第三方库（FBX SDK）去处理这种文件格式，而且数据读进来之后，还要再做一步相当复杂的转换。我们的目标是让同学们能够快速理解反射、引擎的基础、数据流的架构这些东西，不是把精力耗在解析一个庞然大物上。

第二，在真正的商业级引擎里，我们一般不会直接用 DCC 的格式。FBX 虽然非常好，作为在不同工作室、不同工序之间传输的中间格式（intermediate format）很合适，但它并不是一个效率上、引擎上 friendly 的格式。对真正的游戏来讲，我们对数据格式的要求是非常高的：要能打包（packaging）、能加密、能流式传输，等等。

> **结论**：FBX 这类格式是工序之间的中间格式，不是引擎格式。引擎格式要服务打包、加密、流式传输这些真实需求；而从 schema 反射到 custom format，是一套完整的组合关系。

所以我们想让同学们一上来就习惯"自定义文件格式"（custom file format）这件事，而且让你的 schema 系统能够和它连接起来。我们相当于用最简单的格式，把这套机制教给大家。

### 为什么 Mac 上不用 Metal：一个 Vulkan 版本走天下

第二个问题：Mac 版本为什么没有用 Metal，而是在上面用了 MoltenVK 这样的翻译层？其实这个原因很简单。首先，我们已经因为"为什么要用 Vulkan"被同学们狂喷过了：相比 OpenGL，Vulkan 实际上复杂很多。当时我们的考虑，是让大家直接接触现代 GPU 的一些 API 的结构——它真的非常接近 driver 的写法，效率是最高的，也是最具工业化的基础的东西。

那 Vulkan 本身已经非常复杂了，这个时候如果再上一个 DX12 版本、再上一个 Metal 版本，肯定是最好的——性能最好，也最符合各个平台的设定。但首先，开发团队的工作量会非常大，要同时支持三个版本；大家想象一下，我们是一个开源小引擎，同学们都是用业余时间在写。其次，同学们掌握和学习起来的门槛也会更高：先要理解第一层 RHI 的抽象做得好不好，接下来还要针对不同的平台，用不同的版本。

所以基于这个考虑，我们一上来说 OK，统一用 Vulkan 一个版本。其他平台搞不定的，就强行用一个中间件把它给转过去——其实在 Mac 上跑的还是 Metal 的指令，只是我们写的时候只写了 Vulkan，中间件自动把它翻译成 Metal 的原生指令而已。

### 这节课想怎么讲：架构，而不是用法

好，进入课程的正题——继续讲工具。工具这件事真的是博大精深。说实话，这节课是我们比较难以准备的一节课：上一节讲的全是工具链里基本 的、fundamental 的原理，这一节要讲一些高级的、应用的东西。准备的时候我一直在思考一个问题：怎么才能把这节课讲得不像网上随处能找到的那种"游戏引擎使用教学"——那种视频非常大量，教你每个工具的详细功能、怎么去用、怎么去组合。我们今天讲的，还是如何去编写、如何去架构你自己的一个游戏引擎。

所以这节课的课程准备，我个人觉得是我们最"精分"的一节：我们会尽可能讲一些 fundamental 的、底层的东西，上面的一些 application 会点一下。为什么不反过来？因为如果你不知道 application，就理解不了底层为什么这么写；但如果只专注上面的 application，又会忽视掉底下其实有一层架构级的解决方案。这节课就是想找到这两者之间的平衡点。

今天大概分成这么几个部分：

- 先非常快速地让大家对真实游戏的 production 有一个感觉；
- 然后围绕大家最熟悉的地图编辑器（World Editor）——基本上所有摸过游戏引擎的同学都知道这个东西——讲一讲如果要架构一个地图编辑器，我们怎么去架构；
- 接着展开上一节讲过的 plugin：插件机制是工具体系最核心的一个机制，今天稍微展开一点点，讨论一下在游戏引擎里 plugin architecture 该怎么做、有哪些坑、可能会在哪里踩雷；
- 后面是两个重点系统。第一个是线性的叙事性系统在工具里怎么表达——我会拿 Sequencer 举例，但大家一定要意识到，在游戏里线性系统绝不止 Sequencer 一个，其实很多系统都是线性的：你希望点一个 play，然后依次发生所有你想发生的事情；
- 另一个是很多同学一直期待的问题：小引擎里面的反射系统到底是怎么做的——反射是工具链里做 gameplay 非常重要的一个基础，我们会花几页笔墨详细讲一下；
- 最后点一下一个比较有意思的高级话题：协作式编辑。我们认为协作式的编辑工具，会是下一代游戏引擎发展的一个重点方向——因为我们现在要处理的游戏世界，越来越丰富、越来越复杂了。

### 真实的游戏生产现场

先一起看一下，游戏的 production 到底是什么状态。我们拿育碧自家的 in-house 引擎当样本：在这样一个真实的游戏 studio 里，艺术家会用各种各样的工具——有人在建场景的 layout，有人在设计 gameplay。当我们点了一键的 play 之后，游戏里会产生各种各样复杂的行为。这里面有大量的 PCG——程序化方法自动生成的东西，也有大量面向 designer 的 framework 和框架性的东西；艺术家甚至可以自动化地生成一整个城市。当然还有 concept artist，负责设定角色和场景的外观；再往后要生成大量的 3D 模型。这所有东西全部连接在一起，才形成了我们真正的一个商业级游戏的 production。

最后交付到大家手上的东西是非常有意思的：你会看到一个很棒的游戏，而且这个游戏里所有的东西都是有语义的，所有的东西都尽可能让玩家可交互、可 play。

继续讲。整个工具链还有一个很大的挑战：真正在实战的游戏中，游戏有很多类型。这里教给大家一个有意思的词——genre，我们经常讲的"游戏类型"，这个词来自法语，表示各种各样不同类型的游戏，比如 RPG、FPS、MOBA 都叫 genre。对不同的 genre 的游戏来说，它所要做的编辑操作、它的 gameplay 设置，甚至关卡的 layout、关卡的组织规范，都会完全不一样。这也是工具体系非常复杂的一个原因。

### 所见即所得：工具链的第一性原则

工具体系要和很多工具在一起协作。这张图大家应该有点熟悉——第一节课就给大家展示过，也是我推荐的那本教材 Game Engine Architecture 里很经典的一张图。但这里面我要跟大家讲一个 fact：实际上这张图是"错的"。什么意思呢？这张图根本没有把游戏的工具层画全，缺了很多很多的工具，而且有些工具之间的关系，在现代游戏引擎里已经发生了一些变化。不过没关系，我只想让大家看这张图明白一个道理：真正做工具链体系设计的时候，我们要解决的，就像我一上来讲的，是让来自于完全不同思维方式的人——艺术家、设计师、程序员——在一起协同协作的问题。

而且在整个过程中，我们都要保证那个很高大上的原则是什么？WYSIWYG——这个名字比 YYDS 听上去酷多了——就是所见即所得。这实际上是现代游戏生产中一个非常重要的指标。

为什么？因为和大量的艺术家、设计师在一起工作时会发现，如果我们没有办法在工具这一层保证大家的所见即所得，它会极大地影响游戏产品——不仅是效率，效率肯定是周期会变长；还会影响它的质量。为什么？举个例子，比如关卡设计师，如果他不能真的快速看到他调整完的关卡长什么样子，而且自己真的能身临其境地在中间走，那他很多时候的判断——比如"这个地方我希望天上掉一个落石""那个地方我希望有一个小怪蹦出来"——这些体验实际上是全错的，他完全不能模拟用户真实的体验。如果你不能带入到用户真实的体验中，那你给出来的设计一定是不好的。

> **结论**：所见即所得同时决定生产的效率与质量。设计师必须能在工具里"住进"玩家的视角，才可能做出好的设计。

这就对工具产生了一个非常大的挑战：做工具的时候，你有大量的额外信息、额外操作，才能够允许艺术家或者设计师真正对它进行编辑和调整，甚至还要解决同步版本控制的问题；但是你又要求这一切看起来跟真实的游戏一模一样。这两个东西有的时候是"忠孝不可两全"的。不过上一节课也讲到了，最后大家总结出来：把工具直接包在游戏引擎外面，是一个现在大家公认的比较好的解法——当然这也会给游戏引擎带来一些挑战，后面会详细讲到这一点。

### World Editor 是个 Hub，不是拖拉拽工具

接下来我们从一个工具开始讲起。游戏引擎课并不需要讲所有的游戏工具链上的工具——那个数量可能是几十个为单位的。我们就讲一个 World Editor（世界编辑器）。

很多人讲 World Editor 的时候说：哎，不就是个拖拉拽的工具嘛，各种东西拖进来拽出去。但从我们专业的游戏引擎架构思想来讲，我们认为它是一个 hub——一个平台。什么意思呢？它实际上是一个平台，我们把游戏世界里需要构建的逻辑、玩法、场景内容，都作为能够插进去的东西，放在中间进行构建。所以上一节讲的 plugin 机制，在这里就接上了。当我们自己去架构自己的 World Editor 的时候，首先把这句话记在脑子里面：千万不要一上来就写编辑器，去写那种类似 3ds Max 的拖拽、框选的逻辑。这种东西重不重要？非常重要。但这种快速的做法，会让你快速得到一个看上去很酷的编辑器，而且你甚至会因此产生一个错觉——"我是不是可以跟 Unreal PK 一下了？"我以前就经常在论坛上看到有人说"我这个什么东西超过了虚幻"。从专业的游戏研发来讲，我觉得我们还是要非常尊重那些优秀的商业级引擎，因为它们的核心不在于一个一个的 feature，而在于整个体系是按什么一种逻辑把它架构起来的。这是我认为做 World Editor 的时候，最先要在脑中建立的一个概念。

```text
World Editor（Hub：把玩法、逻辑、场景内容的构建都"插"进来的平台）
 ├─ Viewport          用户与游戏世界交互的窗口（跑着一个完整游戏 + editor mode）
 ├─ 对象系统          万物皆 editable object；一份数据、多种视图（树/layer/搜索）
 ├─ 属性面板          Schema 反射属性 → 自动生成编辑 UI
 ├─ Content Browser   资产海洋：按名字检索即所得
 └─ Rule System       环境元素之间的程序化规则（道路×植被×地形×水系）
```

（这张图先把骨架立起来，下面几节就沿着这几个部件一个个讲过去。）

以虚幻为例，你打开它的源码看，会发现上面摆的东西特别多：Viewport、上面一大排按钮、layout、layers、levels、outliner、details，还有 content browser 一大堆东西。看着很复杂，而且这还只是面板展示的方式之一。打开一个商业级引擎的 World Editor，它的面板可以切换到很多很多的 view。你去看一个真实的游戏团队就会发现：同样是打开一个引擎，做 animation 的、做场景编辑的、做玩法编辑的，它的面板完全不一样。这就解释了为什么说 World Editor 是个 hub——它实际上集成了很多功能，但对不同的用户，它又呈现出不同的 view。

### Viewport：跑在编辑模式下的完整游戏

在这样一个庞大的体系里，最重要的几个体系是什么？我按个人的理解给大家总结一下，抛砖引玉。

第一个我认为最重要的，是编辑器里面的 Viewport。Viewport 是什么？是你的用户和你想构建的游戏世界交互的窗口。那这个东西是怎么做的？上一节课我们已经点过了，这里再明确讲一遍：它下面跑的就是一个游戏引擎、就是一个游戏，只不过这个游戏的版本上面打了一个 flag，叫 editor mode。在 editor mode 下，你就能做很多真实的游戏不能做的事情：我的相机可以自由地飞来飞去；我可以无视所有的碰撞；我可以把很多东西变成透明的；我还可以显示很多 debug draw、线框（wireframe）模式。

这里面会提供很多我们叫做 gadget 的东西：小坐标系给你显示一下，选点、选中，还有一些 grouping、画线这些基础操作。这些最基础的东西，需要在引擎里用 native code 给你实现，因为这样效率非常高；上面一些更复杂的逻辑，当然可以由编辑器自己来处理。

这里面有一个很有意思的细节：这就意味着我们的引擎代码里，会有一些叫 editor only 的代码，它的编译版本是不一样的。这里我要特别提醒一件事，也是初级的、新入行的同学特别容易犯的一个错误：如果我们不小心把这些编辑器的代码，编译到我们上线发布的游戏里面去，那它极有可能成为别人写外挂的一个重要入口——"我让整个世界都透明了""我选取直接就有了""我可以直接飞来飞去"。当然，真实的外挂并不是这么写的，但只要人家找到那些函数名和指针，用起来会特别方便。特别是在一个大型的游戏团队里，引擎团队的人数非常多，工程师可能到上百人左右，就特别容易出现没有经验的同学，应策划和设计师的要求做了一个工具和功能，大家都觉得很好用，策划、美术都很满意——但是他忘了把这段代码包在 editor only 的宏下面，结果这段代码就被编译出去了，有的时候就会产生这样的问题。所以这件事情一定要区分清楚。

> **易错点**：editor only 代码必须用宏严格隔离在编辑器构建里。一个"大家都说好用"的编辑功能忘加宏进了发布包，等于给外挂作者递了现成的函数入口。

Viewport 这件事大家记牢了：它实际上跑的是一个完整的游戏。这一点非常重要，因为它是所见即所得最基本的一个保证。特别是对美术很敏感的那些东西——比如材质：光从这边打过来，我希望它反射几下、把一个角色照亮；包括做一个过场动画，我希望那个角色正好走进阴影。这些很细腻的光和反射，必须要通过这样的一个架构才能实现得了。所以 Viewport 是做 World Editor 最重要的一个部件，而且它最好不要做成 plugin——它本身也没有必要做成 plugin。

但这里要讲一个有意思的细节：实际上在真正的、商业级的 World Editor 里面，Viewport 有的时候不止一个。比如你在做过场动画的时候，你在一个 Viewport 里编辑，但你还希望有另一个 Viewport 去看它，你甚至会开好几个 Viewport。所以当我们去做一个编辑系统架构的时候，经常要让 Viewport 支持多个 view。这其实对你的引擎架构也提出了一个要求：你不能把数据同时拷贝好几份——你编辑了一份，还要向好几份引擎拷贝去同步数据？那不相当于在本地写了一个小型的网络同步嘛。所以我们在写这种 editor viewport 的时候，实际上是要对引擎那边做一个改造，让它能兼容多个 view。当然，有的时候在某些游戏里，我们也需要实现画中画，所以多 view 本身也是游戏本体的一个需求。

### 万物皆可编辑：对象系统与多视图

第二个很重要的东西，是整个游戏世界里的对象。游戏世界里有很多很多的东西：天上的云、地上的 NPC、树上的一花一木一草——在编辑器里，我们要编辑的元素特别多。这里有一个很重要的原则，第二节课讲得特别清楚：所有的东西都是物体、都是 object。那么在编辑器里面，我们更进一步：所有的 object 都是 editable 的，都是可被编辑的。当然，不同的引擎说法不一样：虚幻引擎里面叫 actor，Unity 里面叫 object，像我自己做的引擎也叫 object。这不重要，重要的是：不论你是什么——天上的飞鸟、地上的每一个人、大地、天空、云——你都是有一些可以编辑的东西的：我至少能选中你吧？至少能改变你的位置吧？至少能旋转你吧？我点中你的时候，想编辑你的一些属性吧。所以这是我们做 World Editor 的时候，最核心要思考的第一件事情：在架构上，把这个世界里的一切，都抽象成一个共同的 editable object。它跟引擎里普通的 object 还有一点点不太一样——相当于在 object 之上再往上走一步。

那么其实马上就产生第二个问题，也是你自己写 World Editor 一定会遇到的：一个真实的实战游戏产品，一个场景里面对象数有多少？基本上至少是几千个，甚至上万个、更多。大家有没有想象过：如果我给你一个文件目录，里面放着上万个文件，你怎么去管理它？文件少的时候，1 到 10 你都记住了，没问题；但第二天你回来再打开这个编辑器的时候，问"第 973 号文件到底是什么东西"，你根本不知道。你说可以通过文件名？当对象数足够多的时候，实际上你已经完全失控了。注意，这里你看到的还不是对象文件——资产文件是不会重复的；我们在世界里看到的大量的，是对象的 instance，一个一个的实例，这个数量就会非常大。

所以你会发现，商业级引擎在设计它的 World Editor 的时候，要对这么多的 object 设计出很多种不同的 view。最经典的是树状的 view：把这些物体归类，一个个目录去存储。有时候会分成不同的 layer：这是地上的植被，这是城市左边的建筑群，那边是所有地上的石头——用大的 layer 去归类，也可以把它 group。但其实这样还不够，有的时候我们还需要 search 去寻找它。所以一个商业级引擎，对这样的对象列表会提供很多种 view。而对美术来讲，会根据他们的习惯来用：比如有的人就是专门做 environment、专门做天空大气系统的——那好，其他的 view 对我不重要，我会让你们都锁住，不让你编辑它，或者把它隐藏掉，让我专注地去调整天上这个天空、云和雨这种感觉的效果；调完了再把你接回来，看整体效果。

> **定义**：MVVM，上一节讲过的模型—视图分离。数据 model 一定要"动"起来，view 可以提供很多种：完全可以根据艺术家的情况定制，甚至在未来允许不同的 designer、artist 用不同的 view 去管理自己的对象。

### 属性面板：让 Schema 自动生成编辑界面

有了 view 的列表，大家想到的最正常、最直观的编辑是什么？不是什么特殊的编辑器，就是在这个地图编辑器里，我选中一个东西，就想直接编辑它的属性。比如我选中一个 NPC，我想设置它的血量。

这个时候，上一节课讲的 schema 系统就很重要了：我点中它，通过 schema 可以反射出来它身上到底挂了多少属性数据，然后我们的编辑器可以根据属性的类型，自动生成它所需要的编辑界面。像这样的一个界面，几乎是所有引擎的 World Editor 都有的一个小 panel：虚幻里面这个 panel 叫 details，有的引擎叫 properties，叫什么都可以。它让你可以直接编辑选中的对象。这是构建 World Editor 的时候，一定要有的一个窗口。

### Content Browser：从静态目录到资产海洋

最后这个东西，是我在大家写引擎的时候，希望大家一定要注意的：content browser。这里我要小小的自夸一下：我们的 Piccolo 真的是一个小到不能再小的引擎，就几万行代码；但是当时架构的时候，这么小的引擎，我们的团队还是架构了一个 content browser。我看到这个架构的时候，真的非常惊喜。为什么？因为真实的一个游戏引擎，是给大家做游戏开发的。而游戏开发的实际情况是：一个游戏产品有几十个甚至上百个 artist，我们会生产几万到几十万件不同的资产——有动画，有三维的模型，还有声音效果，还有我们想要的一些漂亮的 UI 贴图、动图。这些东西非常丰富和复杂。

那最直观地想：这些东西怎么管理？在我刚刚进入游戏引擎行业的时候，我们没有 content browser，怎么做呢？我们有一位非常厉害、非常有经验的 technical artist，他会根据你的产品把所有的资产设定好。比如我那时候做 Halo 3：所有的资产分成 objects、foliage（植被）、vehicle（载具）、weapon（枪），分得很清楚；然后再点进去，再分哪个目录是贴图的、哪个目录是模型的、哪个目录是原始数据的。我的天呐，你钻下去，会发现是一个非常深的树状结构。我们的团队很遵守规则，大家都把数据放进去了，形成了一个很漂亮的树状 view。

但问题就来了：当我做完了 Halo 3 之后，要做 Halo 4 怎么办？Halo 4 不是所有资产都全部重新来过一遍，很多资产还要从 Halo 3 继承。那这些资产怎么重用、怎么共同管理？比如一个艺术家在做 Halo 4 的时候，想用 Halo 3 的某一把枪——他还得到那个目录里面去找。那好了，这个资产到底应该放到 Halo 3 的目录，还是 Halo 4 的目录？你讲不清楚了。而且这个目录结构一旦设置好——它是三年四年之前某一个人设置好的——很多时候他不能预判整个游戏发展到后来的这种复杂的变化，后面会产生很多很多不同的需求。

所以差不多在十年前左右，大家提出了 content browser 这个想法。当然，我们还会支持基于文件夹的结构，但它更多的只是一个 view。那我们怎么去看待所有的资产呢？我们会认为它们像放进一个巨大的 ocean 里面、一个池子里面：资产扔进去，你只需要知道你要什么东西、它叫什么名字，然后你就能检索到它、把它挂上来；你可以根据不同的项目，形成这个资产的一个 view——这个 view 你也可以用树状去管理，但没关系，资产就放在那儿，你不用管，甚至这个资产都不需要放到你的本地，它可以放到一个数据库里面。

其实最早我刚开始学引擎、还在美国的时候，我们就很有兴趣地研究过一个概念：我们要不要本地都不要存这些资产？因为这数据都特别特别大，我们把它放在 studio 的一个中央的数据仓库里面，每个人需要用到什么资产的时候，只是把它加载到内存里——因为你本质上是要跑个游戏嘛。这样就省去了好几个 T 的资产在上百台机器中来回拷贝的时间，而且还有很多预计算可以提前做掉——这个今天就不展开了。content browser 实际上就是这件事情最重要的一个解决方案：我们真的把 asset 从一个静态的文件目录，变成了一个资源的海洋。ocean 这个词，现在很多现代游戏引擎的公司里都已经用起来了。所以今天如果我们假设要做一个面向未来的游戏引擎，content browser 是大家必须要考虑的东西。

### 鼠标选取：一切交互的基础

讲完这些东西，大家再去分析 World Editor 上的各种小元件，基本上也就清楚了——它无非解决三个问题：第一个是 layout 的问题，各种东西的摆放、一些碰撞检测；第二个是以地形为基础的东西，比如上面的植被、decorator——各种各样的小杂物；第三个是我们需要的 environment，比如天空、天光、光源这些所有的东西。这些就是一个最基本的 World Editor 的各个 unit、各个系统。

那大家很关心：我这个 World Editor 下去写，最关键的东西是什么？第一步要写的是什么？如果架构没有问题的话，第一个要写的，还真的是鼠标的选取。因为鼠标选取是一切的基础——我们在用很多编辑器的时候，觉得顺手不顺手，实际上跟鼠标选取写的好坏有很大的关系。而且很多时候，鼠标的选取甚至要故意模糊一点，让艺术家用起来更自然。

有两种比较简单的做法。一种是用 raycasting：既然这个世界里所有的物体都有包围盒，那我就 raycasting，cast 一下，hit 到它了。这个用的其实是物理引擎，或者说我们对这个世界的物理表示。它有的时候做得粗一点是很快的；但如果要做得精准，大家知道物体的形状是七扭八拐的：一个角色站在那儿，你在远处看着就是小小的一块，但他可能有几万个三角形面片。用它的胶囊去做选取的话，可能你想选的是他身后的那棵树，结果错误地选中了前面的人。

所以有的引擎的做法是：直接加一个额外的选取 pass——把每个 object id 打到 frame buffer 上，然后你去取到那个像素，就知道选中的是什么了。这就是刚才讲的：引擎跑在 editor mode 下，你可能就要加一个 extra 的 pass，去渲染这样一张带有 object id 的 texture。这个肯定会费一点，但没关系——一般来讲，我们做编辑的时候用的电脑，会比玩家的电脑更好。做过主机开发的同学知道，PlayStation 和 Xbox 都有一个开发者的 dev mode，开发者版本会多出一块内存；我们的开发者 PC 也一样，会额外加很多内存、配最好的显卡。所以程序员经常踩的一个坑是："在我本机跑起来完全没有问题啊，为什么在用户那边电脑卡？"很多时候就是因为做开发、做编辑用的电脑配置都比较高——artist 有时候也会这样。但没关系，这都是细节。

```text
方法一 raycasting：    鼠标 ──射线──► 包围盒 / 物理表示 ──► 命中对象
                      （粗选快；精细选取容易被胶囊体带偏）

方法二 object id pass：场景 ── 额外一个 pass ──► 写满 object id 的 texture
                      鼠标 ──取像素──► 直接得到选中的 object id
```

（方法一便宜但粗糙，方法二精准但要额外渲染一遍；编辑器机器比玩家机器好，费一点可以接受。）

所以首先，鼠标能选中一个物体这件事，就得认真写一写。而且这里面有个细节：假设这个场景里面有很多透明性的物体——比如很多 particle，你想选中一个 particle 怎么办？想选中一块玻璃怎么办？按照我们之前讲的，透明物是不写 depth buffer 的，它会被直接过滤掉。所以这个时候，你们需要写一些特殊的代码和逻辑去表达它。举个例子：像 particle，很多引擎的做法是，在粒子发射器那个地方放一个虚拟体——其实你选中的不是那个 particle，你选的是下面那个根上的虚拟体，把它选中，就能拖来拖去了。其他一些更复杂的选取，一般来讲也都会有一些特殊的 code 来解决它。真的去做游戏引擎的选取，你会发现要考虑的情况特别的多。

### Transform 工具：易学难精的打磨活

当我们可以选中一个物体之后，大家会发现在游戏引擎里有大量的物体的 transform 操作：把它平移、旋转，还有放缩。这些在一开始讲 object、讲物理的时候都讲过大量的内容，但其实在做 World Editor 的时候，这些地方反而是特别容易出问题的。为什么？因为 3ds Max、Maya，包括其他的游戏引擎，给我们的 artist 形成了非常多优良的操作习惯，这些习惯都是经过很多项目常年总结下来的。你会发现，就是一个简单的旋转，都很有讲究：当你按哪个热键会出现旋转的 gizmo；当你的鼠标往上移动、移动到 gizmo 的百分之多少的时候，它的 X 轴、Y 轴还是 Z 轴的旋转会被高亮——都会有很多讲究。如果你做得不好，别人用起来就非常别扭。

给大家讲个小例子：做旋转的时候，你会发现我只要鼠标一动就旋转好了，对吧？但我们的设计师需要一个模式：我希望按整度数旋转，比如每隔五度旋转一下，这样方便我快速对齐——比如 90 度、45 度、180 度、135 度这几个常用的度数，或者 30 度、60 度。所以这些东西，如果真的想写好的话，很多时候你会写好几个月，而且要很细心地打磨。

为什么跟大家去讲这个？因为在真的做一个 World Editor 或者一个工具链的时候，大的框架很容易讲得清楚；但当我们真正去写它的时候，你会发现要想写好，还是有很高的门槛。这也是商业级引擎让大家觉得很敬畏的地方。

### 地形与笔刷

有了这两个工具，我们就可以摆 layout 了。接下来讲地形和地形相关的一些东西。地形在前面图形那部分大家都知道了：地形我知道，很简单，不就是一个高度图嘛——高度图无非就是一个 heightfield 再加上一个 texture。对的，确实就是这么简单。然后再加上高度图到底怎么生成——前面讲了 PCG，用程序化自动生成。但实际上在现在的游戏中，很多时候我们可能还要加很多其他的小工具：这上面不止是山川河流，我们有大量的植被、大量的地形的变化，这些东西是怎么生成的？在构建一个 World Editor 的时候，我们最核心要提供的模块是什么？这里我只给大家点几个比较重要的。

#### Height Brush：smooth 才是灵魂

大家首先猜到的就是 height brush，就是说我能够对高度进行刷。大家想象一下，height brush 是不是非常简单？定义好了嘛：一个锥形的山，或者一个平台状的山，我就给你拉起来嘛。但实际上，当你对一个有限密度的 heightfield 网格进行笔刷操作的时候，你会发现：对这个信号进行合理化的 smooth，是最重要的。也就是说，你会发现艺术家会说："你提供了所有形状的笔刷功能，但我总是拉不出我想要的那座山的形状。"其实你们的差距并不是笔刷的种类，而是什么呢？是你拉出来之后，艺术家希望它的过渡尽可能自然。而这个"自然"是怎么定义的？所以 smooth 有很多的细节和讲究。

大家再想象一下，我们的 heightfield，网格三角形是斜着一条条排过去的——你可以把它理解成一块布，它本身是沿着某一个轴向被切割过的。当你拉高度拉得不好的时候，你会发现有一条很明显沿着切向的过渡棱，你能感觉到那个高度场有"锯齿"一样的感觉。所以其实如何有效地让刷出来的山看上去更 smooth、更自然，是 height brush 一个很重要的东西。

另外一个，也是我们在实践中发现的一个点：其实艺术家很多时候希望的，是一种可扩展的能力。虽然我们作为技术人员，会给大家提供很多的笔刷；但是当我们真的写一个游戏引擎的时候，我会强烈建议大家提供让艺术家自己导入一个高度图、自己定义一个笔刷的能力——这个东西会让他们乐此不疲。当然，大家如果研究一下 Houdini 的话，你会发现这方面它做得更加强大。这也是我们做工具的时候，首先脑子中要有的一个问题：不要专注的是"我的算法多么厉害"，而是"我的这个东西，它的扩展性有多强"。

> **提示**：做工具的第一个问题不是"我的算法多强"，而是"我的扩展性多强"。给艺术家留出"自己导高度图、自定义笔刷"的口子，他们真的会用。

#### Instance Brush：刷树刷草的主力

另外一种笔刷就非常非常常见了：instance brush，刷各种各样的实体。比如刷小的 detail、刷 decorator——地面上的小草，当然也包括刷 tree。这个东西非常直觉：当我要大面积地刷草、种树的时候，我就会用这个方法去做。

它首先非常简单、非常好：比如刷树，我一下能刷很多很多棵出来，而且每一棵树都是独立存储的。这样的话，其实我真的能实现：我看到它在这个位置，游戏跑起来它一定在这个位置；这棵树现在是偏黄色的，游戏跑起来它一定也是偏黄色的——因为这些所有的属性，全部是静态地放在那儿的。这个时候如果我对这一棵树不满意，或者想挖一条小道出来，我上手一棵一棵去改，也没有问题。这是 instance brush 非常好的一个点。

但它的缺点是什么呢？如果以一个实战型的游戏来看——比如方圆几十平方公里——你会发现，光是你把这些树的位置去存一存，它的内存占用就已经非常大了；而且它有很多的预处理，非常麻烦。后面可能要用 PCG 的方法去解决它，这里就不展开。但这不妨碍 instance 笔刷是游戏引擎里很关键的一个笔刷。

#### 环境与光源：像拍电影一样布光

还有一种笔刷我就不展开了——对大量光源的摆放，具体的算法在图形那部分已经讲过了。不过有个观察值得说说：现代游戏引擎，随着我们的 GPU 能力越来越强，我有时候觉得我们越来越像电影行业。你知道在电影里面拍摄一个场景的时候，艺术家会布置很多辅助性光源，把角色刻画得特别好，或者把某一个场景的气氛渲染得特别好。其实现在游戏研发的时候，很多时候气氛都是靠这种光、滤镜，包括天空的云、天光打出来的。这些 environment，实际上都是由各种各样的插件来协作完成的。所以我们今天再去做 World Editor 的时候，一定要给这些插件留下空间。

### Rule System：环境编辑的灵魂

其实刚才讲的这一个个的插件，你说做下来难不难？其实不难——前面所有的算法你都知道了。真正难的是什么呢？这些东西彼此之间是有一些规则的。这是 World Editor 里大家思考的时候特别容易忽略、但是很重要的一点。

举个例子：我们在这个世界里要修一条路。这个路就有很多规则了：路上不能长树，对吧？总不能树长在路中间；而且那些杂草也不应该长在路的两边。然后这个路我画出来，它是一个方向，对不对？但如果我的 terrain 有高低起伏，这个路不能够"逢山开山、逢水架桥"，它应该沿着 terrain 的起伏有一个起伏——但是它又要修改 terrain。为什么？因为路得平嘛。你们很少看到哪个路修成倾斜十度、十五度的。所以路实际上既要符合 terrain 的高低，又要在 terrain 上进行一个切割的操作。还有呢？我们的一些石头——碎石头——应该沿着路的两边，形成一个路基这样的东西。所以其实一个最简单的 road 系统：上一节讲 road 系统很简单，你拉个 line 就完事了；但实际上你真的在一个 World 里面做一个 road 系统的话，是很麻烦的。

大家说：那我可不可以不处理？很简单，大不了先把路弄好，然后 artist 上手：该砍树的砍树，该把 decorator 清理掉的清理掉，terrain 我上手去修。同学们想象一下，这个工作量是不是非常大？OK，没关系，工作量很大我忍受得了。但第二个问题就来了——这其实是更严重的问题：今天我作为一个 level artist，我认为这个路这样开是有道理的；但是我的设计师说：你路这样修，我的战斗就没法打了——敌人直接就冲过来了。我得在这边做个拐角，这样我可以在这边设埋伏，敌人的大炮不能直接射到我，这样我的游戏才有的玩。好，设计师要求 level artist 重新改路的方向——大家知道吗？这个时候就整个完蛋了：你前面做的所有手工工作，全部得重做一遍。

所以其实我们必须要用一种 procedural 的方法，用程序的方法自动解决这个问题。怎么办呢？就靠一套 rule system：我们通过一套复杂的 graph——图——把这些规则都表达出来；同时我们把原始的数据分层分得很清楚：这是你画好的 tree 的分布，这是 road 的分布，这是上面这些 object 的分布——因为我们不希望树长到房子里面，我们希望房子周边多少米之内不能长树——包括你的河流、水在哪里，我也标注出来。这些所有的地形元素全部都有之后，交给计算机，用我们的规则体系，生成一套我们想要的、合理的分布——比如合理的树的分布。这个时候，这个效果才是对的。

```text
[道路分布] [手绘树木分布] [房屋/物体分布] [河流水系]   ← 分层存放的原始数据
        │
        ▼
   Rule System（用 graph 表达的规则：路边不长树、房旁留空、
                路随地形起伏又切割 terrain、碎石沿路成路基）
        │
        ▼
   生成合理的植被 / 物件分布
   （改局部时，已满意区域不被重新生成 —— locality）
```

（原始数据分层存放，规则用图表达，程序化生成分布；locality 保证改局部不重算全局。）

这件事情讲讲很简单，其实你真的让它简单生成一下，很简单。但这里面我个人认为——一直以来我一直在思考、想解决的一个问题——叫 deterministic。什么意思呢？树的分布大家希望是随机的嘛，对吧？但当我改了一个局部的时候，我希望其他已经生成好了、我已经满意的地方，那些树不要再全部重新生成一遍。因为有的时候，我对你上次生成的结果是很满意的，我只想改个局部。所以如何能保证这种 generated data 具有一种叫 locality 的性质——局部性——其实是一个实战化的 World Editor 很重要的一个属性。

这个技术差不多十几年前大家就开始研究了。到今天，特别是基于深度学习这些技术的成熟，实际上已经是一个 well-studied problem——大家已经解决得相当好了，基本上商业级引擎都要提供这样的功能：刷植被的时候，它会很快检测到有路、有石头的地方，就让开，包括这么大件的树也是这样；而且这个时候如果对路进行改造，所有的植被都会相应地发生变化。

但这里面真正难的问题是什么呢？是如何去定义一套形式化的语言，让我们的设计师能够定义这套规则，而且这套规则要很简单、很易懂、很好维护。这其实是一个很有意思的问题。这里再讲个细节：真正在做的时候——如果我没记错，应该是十几年前的 Crytek 引擎——他们就有很多人在做这个东西，要精细到什么程度呢？热带地区的植被应该是什么规则；到了高纬度寒带地区的植被是什么规则；东半球是什么规则，西半球是什么规则——你会发现它的规则都有一些细微的变化。包括用这种方法自动生成城市：不同的亚洲风格的城市、日本风格，欧美风格——欧洲风格和美国的大都市风格——都完全不一样。所以这里面真的钻研下去，会非常的有意思。

### 插件架构：世界编辑器的矩阵难题

刚才讲了这么多东西，实际上都不可能一上来全部写到我们的 World Editor 里面。这个时候我们就明白：需要用 plugin 这个机制。事实上，在大量的商业软件的实践中，都会用插件这个机制：比如著名的 Qt，比如浏览器，比如我们的 Unreal，都是用插件的结构。

那当我们回头去看、去构建一个 World Editor 的时候，你会发现你看到的是一个矩阵。这个矩阵里面有两个维度：一个维度是各个系统，比如 mesh 的编辑系统、particle 的系统、动画的系统——你会发现它正好和我们以前讲 object component 的时候，一个个 component 类型发生了勾连。另一个维度是纵向的：各种类型的物体。比如我要编辑一个 NPC；我要编辑环境；像鸟群（flock）这样的群体系统；还有天空这样的系统。纵向的各种类型物体，和横向的各个系统之间，形成一个交叉矩阵。

|            | mesh 编辑 | particle | 动画 | …（系统/组件维度） |
| :---       | :---:     | :---:    | :---: | :---:            |
| NPC 编辑    | ·        | ·        | ·    |                  |
| 环境编辑    | ·        | ·        | ·    |                  |
| 鸟群（flock）| ·        | ·        | ·    |                  |
| 天空系统    | ·        | ·        | ·    |                  |

（纵轴是对象类型，横轴是系统/组件维度；每个交叉点，都是一次"插件可以落点"的编辑能力组合。）

#### 横切还是竖切：答案是都要

那我问大家一个问题：如果我们要给 World Editor 设计 plugin 的时候，到底应该按照纵向的 object 类型去切分，还是按照横向的各个系统去切分——比如按 particle system 来切？

其实这个问题的答案是：都要。这就是今天这节课想跟大家具体讲的：World Editor 里面 plugin 在设计的时候，大家需要考虑的问题。

举两个例子。第一个，particle system：大家想想看，当我做好了一个 World 的架构之后，particle system 是不是最好用 plugin 的形式单独做，不要把它变成 World Editor 的一个内嵌功能？因为你可能有各种各样的 particle：今天我做一个普通的粒子系统；明天发现显卡特别强，我想实现一个 GPU driven 的 particle——GPU particle。GPU particle 可能会和一般的 particle 有一点点区别，那最简单的做法是什么？通过加一个 plugin 来做——将来的形式还会发生变化。

第二个例子：今天我要做一个 NPC 行为的插件。我想写的是：你可以直接选择这个 NPC 的职业、年龄、他的行为模型。这个时候我想影响的是什么呢？我要随机给他一个外观，随机给他一个性格，我甚至要影响他的 animation、他的 AI 的所有行为，包括他可以交互的东西。所以其实在一个真正的 World Editor 里面，我们要支持这种矩阵性的数据存取访问，让任何一个 plugin 能够纵向地、横向地，都对这个世界施加影响。

#### 四种插件模型

大家如果学过软件工程的话，应该知道 plugin 其实有很多种模型。

第一种，大名鼎鼎的覆盖模型（override）：我新版本的 plugin，能够把老的 plugin 的功能全部盖掉，直接用我的功能。这个东西在游戏引擎有没有用？当然有用。比如地形编辑：引擎给你提供了一个版本；但今天我要做地形编辑的时候，我想做一个"小小星球"这样的东西——我希望整个地面全是 curved 的，能形成一个球（sphere），这样我所有的摆放都能在球面上做。这个时候就意味着：你的新的地形 plugin，最好能够覆盖掉以前那个老的——因为你要解决的问题完全不一样了。

第二种，我们叫做分布式（distribute）：所有的 plugin 都是独自工作，每个人解决自己的问题，互相不影响，最后结果合到一起。这个模型就更不用讲了：大家想象一下，在我们的 World Editor 里面，是不是大部分的 plugin 都是这样的？我做 particle 的，跟地形没有太大关系；我做打光、做 light 部署的 plugin，可能跟 particle 又没有什么太大关系。所以我们感受到的 plugin，大部分时候都是这种分布式的：大家分头把活干完，合到一起，形成协作的机制。

第三种，著名的方法叫 pipeline（流水线）：我的数据一个串一个。我们在做 editor 的时候会不会用到呢？实话实说，会用到——当我们进行数据处理和导出的时候。打个比方：我们要做一个物理的效果。物理效果前面的东西是什么？我要对这个世界进行 partition——比如对一个对象进行几何的切割，我希望用一个几何的插件，形成我想要的碎片的类型；而物理的那个 plugin，更多的只是设置它的物理属性。这个时候，几何的那个插件插进来，会插在物理前面先对数据进行处理，它的输出，就是物理 plugin 的输入。

第四种就是洋葱圈（onion）：我要和别的 plugin 同时进行输入和输出。听上去好像有点抽象了——这么复杂的结构我们会用吗？刚才讲的 rule system，其实就有点像洋葱圈。为什么？因为它几乎会和所有的 plugin 都 talk：它要读地形笔刷的那个 plugin、要读地形；要读所有刷 decorator 的 plugin、读所有的 tree 和 foliage 的 plugin。我根据读来的数据，自己对它进行处理；处理完之后，我还把结果反过来写回去，改写你们的状态。

| 模型                 | 机制一句话                         | World Editor 里的实例                     |
| :------------------- | :--------------------------------- | :---------------------------------------- |
| 覆盖（override）      | 新插件整体盖掉旧插件的功能           | 球形世界的新地形插件，盖掉引擎自带地形插件    |
| 分布式（distribute）  | 各插件独立工作、互不影响，结果合并    | 粒子、打光部署等互不相干的插件               |
| 流水线（pipeline）    | 数据一个串一个，前者输出即后者输入    | 几何切割插件先处理，物理插件接力设属性        |
| 洋葱圈（onion）       | 与其他插件同时读写、操作同一份数据    | Rule system 读地形/植被插件数据，处理后再写回 |

这里面我想跟大家讲的是：今天当我们真的站在一个引擎的视角，去架构一个 World Editor 或者各种各样的 editor 的时候，在你的设计结构上，一定要保持一种很强的开放性。因为当一个真实的游戏 production 的需求来的时候，它对工具的要求，实际上各种 plugin 的模型都会用到。所以千万不要上来先给一个假设，说要求所有的 plugin 都按某一个模式去走——至少以我个人的工程实践来讲，我觉得这事好像搞不定。

所以有的时候我想：做软件工程，真的就是在两个很"精分"的需求中间达到一个平衡。我们去追求软件体系的那种严谨性和一致性；但同时我们要理解，工程上为了解决问题——我的 scenario 非常复杂——我必须妥协，我必须允许很多种不同的 pattern。

## 时间轴、反射、代码渲染与协同编辑：引擎工具链的高级概念
> 对应块：BLK31 | 覆盖分集：P17下 | 块标题（分集名）：《第十四节：引擎工具链高级概念与应用》

### 从“世界上最好的语言”聊起：对插件的工程实用主义

程序员有个万年不变的话题：哪个语言是世界上最好的语言。我们常常看到有评论说，从学术上讲，这个语言设计得不够 elegant，不够优雅。作为一个码农，我对这句话是很不屑的：优雅有什么用呢？一点用处都没有，它不能解决我的问题。所有能帮我解决问题的语言，都是好语言。

研究 plugin 的设计模式时，我建议大家秉持同样的实用主义原则：任何架构，只要能解决我们的问题，那就是个好的架构。plugin 这里面的其他问题其实非常复杂，举个例子。

一个庞大的游戏引擎体系发育起来之后，你会发现引擎的内核在不停地升级：版本结构、数据都会升级。但很多 plugin 并不能严格保证跟着你的版本结构升级。最理想的情况当然是每次引擎一升级，所有 plugin 全部升级一遍——但这件事做不到，特别是大型商业引擎，有成千上万的人为它写插件，这些插件不同版本之间的兼容性会是一个非常大的问题。所以希望大家在一开始设计这些接口的时候，就要考虑清楚：比如对接口进行版本编号。你的插件包只用了我这样一些 SDK，SDK 是有版本号的，那个版本号只要不变，你的 plugin 我就认为是有效的；但如果我发现我要变了，那就无效。

> **易错点**：这里面有个很难的挑战——作为引擎研发者，你虽然开放了这些接口，但你根本不知道那些写 plugin 的老哥是怎么用这些接口的。很可能他用了一个你完全想不到的方式，通过接口修改了你的内部数据，而你并不知道。等你对内部结构做升级的时候，那位老哥的东西可能直接就崩掉了，你还纳闷：我的接口函数没有变啊，该提供的服务都提供了呀，为什么会崩？但有的时候，你就会产生这样的问题。

一个好的引擎设计，在这个地方特别能体现出它的功力。实话实说，这一点我认为还是蛮难的，非常难。所以同学们刚开始入门游戏引擎的时候，也不要对自己提那么高的要求——说实话，Piccolo 就没有认真考虑这个问题，我们做得还是比较简单，就是怕同学们太难。但当你从业五到十年左右的时候，你确实可以认真考虑这个问题；我个人认为，编程十年以下，考虑这个问题为时过早。

顺带说一句我自己的想法：我不建议程序员写了几年代码，就觉得“我要做管理”。技术开发里的很多东西，没有十年到二十年的沉淀，你很难理解它的复杂度、它体系的丰富度。所以我一直认为，架构师是程序员的终极归宿。

这就是我们结合 World Editor 给大家详细讲的 plugin 结构。

### 时间轴：让每个参数都随时间动起来

接下来给大家讲个有意思的东西：在游戏中，怎么去表达一种线性的、叙事性的东西？

游戏里一个最重要的挑战叫做 storytelling（叙事）。我经常嘲笑很多 3A 游戏做到后来已经不是游戏了，就是个交互电影——虽然我个人觉得这违反了游戏的精神，但实话实说，作为一个玩家我还是很 enjoy 的，而且这让我云游戏起来一点罪恶感都没有：云完之后，这个游戏 80% 以上的内容我已经知道了，为什么还要辛苦自己，去受苦完成剩下的 20% 的交互部分呢？但这不妨碍叙事在游戏世界里非常重要。可以看到，游戏做得越来越像电影：每一个镜头、每一个角色的动作、每一道光、每一次爆炸、每一次入场，都是被精心设计过的。

而这一切发生在哪里？发生在一个时间轴上。在这个时间轴里，到什么时候我开始播放什么背景音，这个时候我应该播放什么样的爆炸效果，这个时候我希望角色做一个什么动作——比如打招呼、开枪，或者躲进掩体。你会发现，我们有大量的元素、大量的 parameter，是在时间上发生变化的。

举个看得见摸得着的例子：虚幻五里很重要的概念叫 sequencer。它对世界里的每一个 object（在虚幻里叫 actor）定义了一个东西叫 track。在 track 里面，它的任何一条属性都可以定义一个在时间轴上的变化。把这些变化集中到一条 timeline 上，设定一些 keyframe（关键帧），也就是每个关键的变化节点；然后在 keyframe 之间做插值——用线性也好，用曲线也罢，都是我们的选择。这些东西结合在一起，就形成了一个 sequence。用这些简单的东西，最后就能展现出让你觉得很丰富的世界。

```text
timeline ──────────────────────────────────────────────▶
│
├─ 角色 track：动作（打招呼 / 开枪 / 躲掩体）  K1──────K2──────K3──
├─ 特效 track：爆炸                            K1───────────K2──
├─ 声音 track：背景音进入                        ▲
└─ ……
     每两个 keyframe（K）之间做插值：线性或曲线
```

这张图就是 sequencer 的骨架：每个对象一条 track，track 上用 keyframe 描述属性在时间轴上的关键变化，中间靠插值补齐。

你可以把它理解成拍一部电影。正常的想法是：你有三个演员，好，1、2、3，action！所有人开始说话、对话、做动作。但在游戏世界里这件事非常难，我们会这样做：演员一，你的动作是走到桌前拿起书开始读，整个时间是五秒——走到桌子是几秒、拿起书是几秒、读是几秒；演员二，你要坐到椅子上，开始张口说一段话，这段话说几秒；演员三坐在他对面，坐下来也开口讲话。当我把这三个演员的 timeline 对齐到一起，一点播放，你看到的画面就是：一个演员在认真读书，另外两个演员坐在图书馆的椅子上开始聊天——你看到的东西是在同时发生的。但真正在游戏世界里，这些东西是一次一次、一个一个去做出来的。

这就是我经常跟大家讲的、游戏为什么这么难做：作为用户，你看到的一件事都好像顺理成章，就该是这样；但在游戏引擎和游戏世界里，所有的东西我们都要用零和一、用一行行脚本、一行行代码，让它一个要素一个要素地生成——而当这些要素合到一起的时候，还要非常合理，符合你对自然的认知。所以我经常讲，我们是躲在零一之后的人，是躲在像素之后的人。

举个小例子：我们如何让一个小鸡动起来？以 UE 为例，首先要把小鸡绑到 object 上去，绑成 actor；接着它就有了一个 track，小鸡开始可以定义行为了；然后把它的 transform——它的位移——绑上去，有了一个叫 property track 的东西；第三件事，就可以给小鸡在各个不同的位置设置 keyframe。大家看过我们动画那几讲的话，会觉得这太简单了：不就是位移吗？在时间轴的第一段放一个位置，第二段放第二个位置，沿着时间轴一走，不就形成了一个插值吗？对，很简单。如果我希望给小鸡形成一个路径规划，就可以非常简单地让它在几个 keyframe 之间来回走来走去。各个 track 改的到底是什么？就是 component 的一个 parameter——transform 的位置。这个 case 非常简单，这只小鸡看上去特别傻；但游戏里那些酷炫的东西——《黑客帝国：重装上阵》里的那些表演、《战地》里让你感叹“哇真棒”的段落——实际上就是一个个角色、一个个效果在这条 timeline 上表达出来的，是很多设计师一个 keyframe 一个 keyframe、一个 object 一个 object 把序列排好，最后呈现出的结果。

所以这对整个游戏的工具体系来讲非常重要：工具体系有一大类需求，就是在时间轴上让 parameter 动起来、让对象动起来。这不止讲的是剧情——包括特效，包括游戏里的 UI。UI 很多时候你点一个东西，后面发生一系列事情：比如你暴击了一个人，产生一系列的击杀头衔、你 who kill 了谁、暴击率是多少——这一切全是在一个时间轴上发生的，UI 体系里也有大量基于 timeline 的顺序。控制光源、控制天空的光照、控制场景，甚至一下子切换场景——很多过场动画其实都偷偷把场景换掉了——用的也是这样一套架构。

用 sequencer 举这个例子，就是让同学们知道：你看到的那些复杂的、沿着时间轴的线性交互，背后都是同一个体系——一个叫 timeline 的体系，在 timeline 里面修改各个对象的属性。

### 反射：引擎与工具之间的桥梁

这就引出一个非常有趣的话题：反射（reflection）和 gameplay。大家看，刚才讲的 sequencer 体系，最核心的就是在时间轴上调了 component 里的几个 parameter，对不对？那这件事是怎么做到的？我的工具怎么知道去修改 runtime 里面那个对象的数据？中间这条链路是怎么建立起来的？当然，我们有 schema——但 schema 只是帮你做了描述，你得找到那个数据啊，你得 set 和 get：首先要知道它当前的数据，还要去改它的数据。这就引入了我们很重要的 reflection。可以说，reflection 是 sequencer 的 foundation 之一。

再往 gameplay 这头看。游戏中的 gameplay 非常丰富和复杂，而作为一个引擎，我根本不会知道未来基于这个引擎开发的各种游戏会有什么样的 gameplay。举个例子：我希望场景里有个机关，我把它顶上去之后，它能射出一根箭，这根箭还能拉动什么东西——这些东西不可能写到引擎里面去，对不对？有同学会说，没关系，我们可以用数据配置把逻辑配出来。实际上你会发现，有的玩法是用数据配不出来的——任何语言的表达都是有上限的，而数据本身也是一种语言。那怎么办？我们要允许游戏开发团队基于这个引擎不断地扩展玩法、不断地增加新的接口和新的功能，工具必须要支持他这么做。

这时大家最熟悉的东西就来了：各种基于 visual 的 script 语言。大家很熟悉 Blueprint，但 Blueprint 只是 visual script 语言的一种；现在很多引擎、甚至一些游戏之外的应用，都在用这样的方法。这从某种意义上有点像现在很流行的概念——低代码、零代码开发：不需要用代码，你就可以构建你的东西。实话实说，在游戏引擎里，我们处理的情况是最复杂的。

在游戏引擎里设计 visual scripting 语言，最核心要解决的问题是可视化编程语言的可扩展性。道理很简单：如果编程语言的各种节点是预设好的，我只是开放各种接口让你去连接，这件事难不难？其实有点挑战，但是可以做，不难。但它有一个很大的缺陷：就像今天我要加一个新的 feature——假设左边定义了一个角色，他有一个跳的动作，那我右边就要在可视化节点代码里写“好，我知道每个人类有一跳这个动作”；明天说不好意思，我又支持了这个角色可以停止跳这个动作，那我是不是就得在工具这一层再加代码，让工具里那个节点增加一个接口，而且它能正确地调用那个函数？这个调用我们一般叫做 invoke。这样一旦游戏逻辑增加，我这边就要不停地去修改工具。当然可以通过 C++ 的派生和继承，不去每次改它的基本结构，只派生一个新类来支持这件事；但工具那边会变得非常复杂——这就是一个不可扩展、不可维护的东西。

所以大家最喜欢的东西就来了：反射。

> **定义**：反射是指代码写好之后，系统能告诉你到底有哪些新的功能被暴露了出来；其他调用者不需要跟你的代码链接、编译到一起，就能知道这些新功能接口的入口，能够调用它们。

反射是游戏高级语言里一个非常常用的概念，也是这些年语言一个很大的发展。早期的语言比较像汇编，比如 C、C++，是没有反射的——什么东西都是上来手写。我的感觉有点像读书时幻想的一种画面：半夜寝室里亮着灯，有人拿着小刀在光盘上刻出一个操作系统。大家知道早期的存储就是那一张张光盘，我们只是在YY那种最土法炼钢的感觉。汇编、C 这些语言确实没有反射，它实际上就是一段非常 native 的代码，扔给机器就跑了。但到了 Java、C# 这种高级语言，就全面支持了反射。这是一个非常重要的现代语言的拓展。

工程上我印象也很深：很早很早以前架前几代引擎的时候，因为没有用高级语言，引擎里面都是 C 和 C++，我们用了很多很奇怪的模板 hack。它的核心目的是什么？就是找到类似反射的感觉：我定义了一个结构、定义了一些方法，外面的接口不需要跟你重新编译，就能把你的方法找到、就能调用。等我们有了反射之后才知道，哎呀，这些工作到后来全是无用功。

那反射到底给了我们什么？我认为它实际上是在代码和工具之间、在引擎里面构建了一个很好的桥梁：引擎实现了一些功能，写好之后，通过反射生成一个表，告诉我引擎开放了哪些类的接口、有哪些功能、有哪些数据可以访问，并且生成了一堆 invoke 让你去调用它的函数，一堆 set and get 让你修改和改变它的变量。这个时候我写工具就会非常简单。比如我写一个我的脚本语言，发现你定义了一个功能叫做“人”，这个人有很多属性——身高、体重、血量——我都可以 set and get；又发现你可以让他走、跑、跳，这些功能我都有。那当我在可视化脚本语言里创建一个叫做“人”的节点时，它所有的这些属性参数就全部都能显示出来。

而且还有一点：我知道它的类型是什么。比如走、跑、跳是一个动作，那我就可以去 invoke 它，这个节点可能是个三角形的标记——动作流可以走过来；如果它是属性，是个 property，那我可以显示它，甚至可以编辑它，找一个 modifier 去修改它：比如把你的血量减去这把武器的伤害，再重新得到你的一个新血量。用一个脚本、一张简单的 visual scripting 的图，就可以把这个算法给写出来。

有同学会说：我作为一个程序员，这个东西让我去写代码会更简单、更好，为什么非要用 visual scripting 的方法来解决？这件事情其实让我研究和思考了很久。我以前一直不理解：脚本也很方便，可以对引擎功能进行扩展，我作为程序员写代码 debug 效率最高、也很方便，为什么大家后来会用 visual script 这种语言？我自己后来的理解是：我们作为程序员，天然地认为这东西很方便；但对于大量的设计师和艺术家来讲，光是建立那一套语言的编译环境、确保按照你的语法去写不会出错，这个事情对他们的门槛就非常非常高。他们很多时候需要的是什么？是这个块拖进来——不同颜色的接口，红的接口连红的线，蓝的接口连蓝的线，红色对红色、蓝色对蓝色，三角对三角、方块对方块、圆形对圆形——其实对于他们来讲，这是一种最自然的表达方式。

所以我自己也被“洗脑”了：我认为 visual scripting 实际上是引擎未来发展的一个方向，因为它真的能够把引擎开放给足够多的用户。而反射——如果你们认为这是一个正确的方向的话——它就是构建在引擎和工具之间的一个重要的桥梁。

### 用 C++ 实现反射：Piccolo 的做法

接下来讲一个有意思的细节。这门课一般是不讲细节的，但今天为什么一定要讲细节呢？因为课程里的同学们一直在插话，请课程组讲一下 Piccolo 的反射到底是怎么做的。那今天我们就夹带点私货，给大家讲一下：在 C++ 里面，我们到底是怎么实现反射的。

这个事情讲起来没啥秘密，非常的简单。大家知道，所有现代高级语言都要通过一个遵循统一规范的编译系统把它编译出去，而整个编译过程也不是我们自己能瞎写的——它也有一套非常规范的 pipeline：前面要进行语法分析，要 parsing；你要生成 AST，就是抽象语法树；然后还要对它形成一个中间代码；中间代码再生成我们的 target code，就是机器能跑的。这一整套 pipeline 在过去的几十年里，已经被无数先贤整理、总结得非常完善——谢天谢地——而且正好还有大量开源的编译器，比如 Clang，它就非常的好，可以把你的语言翻译成 AST。

```text
源代码 ──▶ 语法分析（parsing）──▶ AST（抽象语法树）
              ──▶ 中间代码 ──▶ target code（机器可执行）
```

大家仔细观察一下：给 Clang 一个 C++ 里面的类和它的变量定义，经过 Clang 的分析之后，它会形成一个非常好被解读的、树状结构的表。在这个表里面，我们就可以很容易地把任何一个类的接口函数、它的 member variable 全部提取出来。而且这个东西是不区分语言的，其他的语言扔进去它也能处理。有了这样的东西之后，大家想想，去生成我们想要的 schema 应该是很简单的，对吧？

Piccolo 选的就是 Clang。为什么选 Clang？其实有很多原因：第一，它开源，而且很模块化，你可以自由地加载；而且它本身是一个非常稳定、成熟、被最广泛验证过的平台。所以 Piccolo 的选择就是挑一个最简单、最可靠的插件。我个人认为 Clang 是个很好的选择，大家有兴趣的话，通过 Piccolo 也能知道 Clang 最简单的一个用法。这里有个细节：在 Piccolo 里面，我们并没有显式地把 schema 文件存出来，我们只是在内存中定义了一个 schema，大家可以找到那个数据结构。

再讲一个细节：实际上反射比大家想象的要有一些更精准的控制。为什么呢？一个引擎代码就算精简了也有几万行，里面应该有几百个数据结构——我并不是所有的数据结构都需要反射的。我们实际上很多时候是需要和资源打交道的数据才要反射。那怎么办？我们通过定义一些描述词来控制。Piccolo 里面有两类描述词：第一类是一个叫 CLASS 的宏，定义一个类，后面写了一个标记，意思是我这个 class 里面所有的 member variable 都要被反射出来。看上去没毛病对吧？但实际上我们在定义有些类的时候，并不希望所有的 member 都被反射出来。为什么呢？因为有些变量并不需要在内存和磁盘文件之间交换，它实际上是我计算用的中间结果。那就在后面加一个描述词，叫 whitelist only。这样我就知道了：这个类里面虽然有十个不同的成员，但只有我看到带 meta enable 这类标记的，我才知道这些是我要反射成我想要的数据。

这东西怎么实现的呢？再讲一个细节，不好意思又讲细节了。它实际上是通过宏来做的。大家对 C++ 语言有了解的话会发现：编译器真的编译 exe 的时候，这些所有的描述全部都是无效的；但当我们编译反射、要获取 reflection 的时候，实际上用 ifdef 把它们 define 成那样的一个标识。这里注意，Clang 提供了一个方法：你可以定义一个叫 attribute 的特殊关键词，attribute 里面有一种类型叫做 annotation，就是标记，然后你可以把各种标记打进去；在你最后生成的 AST 代码里，它会给你生成 attribute 括号 annotation 的形式，把你的文字放进去。我们只要检测到这个东西的时候，就知道你下面到底想让我干什么。所以大家仔细看，看上去非常神秘——一段 C++ 代码放在这，我就能生成所有的反射——但实际上它就是一个非常简单的字符游戏。

说到字符游戏，分享一个小故事：程序员到最后对字符都非常敏感，基本上都有强迫症——对缩进、什么时候打逗号、大括号到底同行还是不同行，都非常的 geek，甚至会为此吵得面红耳赤、脖子粗。实际上就是因为我们的职业属性，会让我们对这些东西特别的敏感——毕竟你看到的所有精妙的游戏，本质上都是一个字符游戏而已。

Piccolo 的反射还是蛮具有代表性的：比如你想学习一下 Unreal 的反射怎么做，虽然它比我们做得复杂，但它基础的方法和结构跟这个非常接近。

最后回答一个大家常问的问题：反射会不会影响运行效率？

> **结论**：反射对引擎本身来讲没有什么影响——那些反射代码你不用它，它不会产生任何的 overhead。

但当你频繁地在工具里面去调用这些反射代码——get、set、invoke——效率问题就来了。工具里很多时候我们是通过字符串去找到那些函数指针的，要根据字符串去 search 一个 map。当然我们可以把字符串优化成一个 id，叫做 string id 的东西，查找会更快一点；但这个流程本身有的时候还是会产生效率开销，特别是对于大批量数据的编辑：比如刷草和植被的那个刷子，可能一下子会创建很多物体，很多物体的属性都要被 set 一遍；包括做 sequencer 的时候，要改变很多 parameter。编辑的时候可能会有一些效率影响，但 runtime 的时候不受影响——因为反射主要是 editing 时会用到的东西。

### 代码渲染：让机器去写 accessor 代码

讲完反射大家就知道了：给一段 C++ 代码，加上这些特殊的标记，我就能够自动找到你所有想开放的结构，还能生成它的 schema 描述，这都没有问题。但这还不够，因为我的工具要大量地访问、修改这里的数据，调用你们的方法。所以我们要为每个 reflection 生成很多的 accessor——你可以理解成就是三类函数：get、set、invoke。就是获取一些数值、改变一些数据，或者找到一个方法之后，把这个方法给调用一遍，invoke 它一下。

这就牵扯到一个非常有意思的概念，叫代码渲染。大家想象一下：一个引擎需要反射的类可能有几十个，反射做出来之后，这些函数谁去写呢？如果这些函数也变成了需要程序员去写——首先这些代码非常的冗余；第二，不是说好了自动化吗？说好了接口自动生成吗？为什么又突然让我去写代码了？

所以这里就有一个很有意思的工具，叫做代码渲染。这个东西其实不是什么高深的概念：web 端很早就发现了这个问题——我要生成各种各样的页面，但是它们的逻辑其实是大同小异的，只是数据不一样，我希望前端的代码能自动生成。比如要显示两个不同的 UI，唯一改变的是里面三个颜色的名字，其他东西一概不变——这个时候，模板渲染就是一个非常好的工具。

我现在都几乎找不到代码渲染什么缺点。它的好处：第一，能够大量地减少冗余代码开发；甚至它会减少你犯错——渲染出来的代码一次性调通过之后，以后很少会出错。就像我们做的那个 schema 系统，代码放在那差不多也快 10 年了，但几乎不出错。为什么？因为这些代码全是自动生成的：如果出错，它早就出错了；如果不出错，你写 10 万行、生成 100 万行，它也不会出错。还有一点：它非常完美地把数据和逻辑进行了分离。以前我们在写代码的时候，有些东西我们认为是数据，却必须要写进代码里；现在我们可以实现数据和逻辑更加彻底的 decoupling。

> **结论**：当我们在架构一个大型系统的时候，我一直认为，能够通过自动化生成的代码就尽量自动化生成，不要自己手写。手写的过程是不可控的，很容易就是你昨天那个版本写得没有问题，后天那个版本写出来就是有问题了。

在 Piccolo 里面，我们用了一个非常有意思的小工具：mustache。mustache 的英文原意叫胡子。确实，因为它要求你在描述代码的时候加很多的大括号，感觉像这个人套了很多大胡子一样；然后它通过你的数据对语法的翻译，自动地把你想要的代码渲染出来。这个东西其实非常的简单，而且也是很稳定的一个系统。在 Piccolo 引擎里，这就是我们真正实战的东西：内存中生成的 schema 数据，配上写好的模板描述，就可以自动地生成各种各样的代码。

同学们今天基本上听完这几趴，如果技术基础过关的话，基本上就能够看懂 Piccolo 的代码生成器是怎么做的了：

```text
C++ 源码（带 CLASS / whitelist only / attribute-annotation 等标记）
      │ Clang 解析：检测标记，提取类、成员、方法
      ▼
    AST ──▶ schema（在内存中生成，不落盘）
      │ + 预先写好的代码模板（mustache）
      ▼
    accessor 代码：get / set / invoke
      │
      ▼
    引擎里定义的任何一个结构，编辑器里就能看到、改到、调到
```

它首先就是调 Clang，生成内存中的 schema；schema 生成之后，根据预先写好的程序模板，再调 mustache 生成大量的 accessor 代码。这样就能实现：引擎里面可以定义任何一个结构，在编辑器里面就能互相看到。

基本讲到这儿，我们的引擎工具链就讲完了，就是这些东西。当然，真实的引擎工具是非常复杂的，我再讲下去的话，基本上讲的就是引擎使用教学课程了——引擎使用教学这个东西说实话我并不擅长，我不是个特别好的引擎使用者，但是我非常有兴趣讨论引擎的架构。

### 协同编辑：下一代引擎的关键战场

这节课我再额外补充一个小小的一部分。我个人认为，现代游戏引擎有一个很重要的发展方向，叫做协同编辑。为什么？大家看现在的 3A 游戏，包括我们经常讲的开放世界，数据量和数据的维度远远超过我们一个人能够 handle 的能力，客观上就需要很多人共同编辑。而只要大家一共同编辑，这个事情就很头疼：比如当你要编辑这么大规模的一个场景，里面有大量的素材，这些素材可能有几十个甚至上百个 artist 共同产生——我们彼此之间怎么样才可以不打架呢？

有人说我们全部用 P4 这类版本管理、全部用 procedural 的方法生成，听上去好像很了不起。但真正游戏的核心，还是一个叫做 novelty 的东西——一种新鲜度，或者说生动度、创新度。这就意味着，一个 procedural 算法哪怕足够成熟，它的 pattern 还是会很容易被玩家发现，所以我们还是需要大量 artist 灵光一闪的创意。当然，这句话说得有点为时过早：说不定按某些人的预测，2030 年我们实现了强人工智能，novelty 这件事情我们也可以交给 AI 去解决——这是有可能的，到那时我们的工具体系会重新设计一遍，很多 artist 可能会因此失业，这是个很悲惨的故事。但我们今天先假设强人工智能还很遥远，实际上就还需要很多人在一起共同协作。

那怎么协作？协作最容易出的问题就是冲突：我去改了一个东西，和你改的东西发生了冲突。所以传统的做法中，我们会把这个场景分成很多很多不同的文件，让你编辑完之后去 merge。这个做法其实很笨，但其实也很有效。在这里面我们会把物体进行不同的划分，有三种完全独立的划分思路。

#### 划分思路一：把世界分层

第一种是把世界进行分层：编辑地形的编辑地形，编辑植被的编辑植被，编辑建筑物的编辑建筑物；甚至我在物体里面再区分，你编辑的是建筑物本身，还是周围的小装饰物。这样每一个不同 layer 的东西放在不同的分层里面，每一个 artist 只编辑自己的分层。好不好？好的。这是最古老的方法，很早很早以前引擎就已经支持了。

但这里面会出现一个比较大的问题：这个分层你很难分得特别好，而且很多时候不同层的东西是有相互依赖的。举个例子，做地形的 artist 一旦对地形进行修改，那上面那些植被的排布是不是相应都要发生变化？举个最简单的例子：一个 artist 改变了房子的位置，那你在周边种的所有的树、对地面做的调整，是不是都要相应地发生变化？但如果这件事情是三个互相看不见的 artist 一起来做的话，这个地方就会产生无数的问题。所以有个很土的做法：三个 artist 轮流做，第一个做完把他的分层锁定，另外一个基于它继续做。这样可以，但你真的想同时去做的时候，效果很多时候就很差。

#### 划分思路二：把世界分块

一种更土但更有意思的做法：对世界进行划分，分成块一、块二、块三、块四、块五。这个地块的事情归你了，那个地块已经归我了，非常简单好用。但它会出现一个有意思的问题：我们有很多房子——我就是跨界了，怎么办？比如作为一个山脉、一片植被、一个湖泊，我很可能跨两个块。那我是不是要支持不规则的世界划分？

其实这件事情在真实世界里面很存在。我以前看过很多有意思的旅行小文章：在很多欧洲国家的国境上，有一栋房子左边属于一个国家、右边属于另一个国家——那这栋房子的归属问题怎么解决？包括有一些山也是这样的，一些河流也是这样。所以对世界进行划分，很多时候是非常有效的，能解决很多问题；但是在有些地方，它很难解决那些跨边界（cross boundary）的 case。

还有一点：我们看一个场景，特别是玩家去看一个场景，它是连续的。所以如果这个世界真的是割裂的，你感觉到边界那边有很明显的区别，玩家、艺术家很多时候是接受不了的。当然了，这里我们有很多方法，比如最后再来一波 artist，对边界这个地方再进行专门的修理——这也是可以的。所以这个方法也是一个非常简单、非常可用的方法。

#### 划分思路三：一个对象一个文件

另外一种下面只给大家提一下，因为也是现在刚刚在推出的一些技术：比如 Unreal 5 最近推的 One File Per Actor，简称 OFPA。它就很极端了：你们既然觉得这个世界容易冲突，好，游戏世界里面每个对象，我就给你创建一个文件，你们每个人只改自己的文件，你们彼此再也不会冲突了。这听上去非常的了不起，我个人觉得也是非常了不起的一个尝试。

但我自己简单看了 OFPA，我们团队也在交流：它的问题在于会产生无数的小文件。当然其实它也没那么傻，做了很多机制对小文件进行管理。但事实上会产生两个比较现实的问题。第一，版本管理：比如场景做完之后，我要提交一个新的版本，我发现我要提交很多很多的文件。大家如果用过真正的 source control 软件就知道，Perforce、SVN 这类软件，如果一下子做大量文件的版本管理，对它们来讲就很痛苦——到最后你会发现整个工作室都卡住了，卡不动，更新不了数据。第二，cooking：这些碎文件不能原样留在内存里，不然游戏的性能会特别低；所以 cooking 的时候，要把这些所有文件还是打包到一个 level 的文件里面去。这样的话，在对数据进行打包的时候就多了一个额外的过程，而且这个时候你面对的可能是上万个小文件。大家对操作系统有所了解的话就会发现，操作系统最恨什么东西呢？最恨的就是小文件。所以这会产生很多额外的负载。

| 划分思路 | 核心想法 | 好处 | 别扭之处 |
| :--- | :--- | :--- | :--- |
| 分层 | 按地形、植被、建筑等类型分层，各管一层 | 最古老，引擎很早就支持 | 层间相互依赖，很难分干净，难以同时开工 |
| 分块 | 世界切块，谁的地块谁负责 | 简单直观、立刻可用 | 山脉湖泊房子跨界难归属，边界割裂感明显 |
| 一对象一文件 | 每个对象一个文件，各改各的 | 从根上消灭冲突 | 海量小文件拖垮版本管理与 cooking |

不过，虚幻提出来肯定是有它的道理的——我们能想到的东西，他也想到了。所以我认为这是一个非常值得大家关注的前沿方向，因为这里面我讲的每一个问题，总是有一些技术方法可以绕过去的，而这个方法确实能彻底地解决协同编辑里产生冲突的问题。

#### 实时协同：原子化的 command 是地基

当然了，我讲的是协同编辑里面最简单的情况：我们几个人各自编辑，最后合在一起。实际上协同编辑的终极状态是什么呢？我们同时在编辑——张三、李四、王五在编辑的时候，彼此之间都能看到。而这个时候，实际上就要有一套网络的架构：一般来讲是在局域网里面，工作室内网的性能非常高，我编的东西别人都能看到。这里面真正的难度其实不是状态的同步，难度是什么呢？保持它的语义的高度一致性。

大家还记得上一节课讲的一个概念，叫 command。我就讲过，做工具系统做编辑的时候，我们实际上争取把用户的每一个操作——一个拖动、一个选取、一个平移、一个改颜色、一个改材质、改一个参数，包括 sequencer 里面每一个 keyframe 的增加删除——全部变成原子化的操作，变成一个 command，然后在所有人的电脑上同步你的 command。这样的好处，就是能够让协同编辑这件事真的能够去写。我讲起来其实非常简单——这一趴我本来准备了蛮多的 PPT 页数，后来被我全部删掉了，因为确实讲起来太深太复杂了——但它的核心是：

> **结论**：对整个编辑操作进行原子化处理，是协同编辑的一个基础。如果你没有这样的一个基础，那你所谓的协同编辑一定是个 hack：可能看上去大概像那么回事，但当艺术家真的用的时候，会发现很多地方违反了人的直觉。

这里面有个很有意思的比喻：人对协同的直觉，就像几个小朋友在一起在画布上画画。他会认为：你画了个蓝色，我画一个紫色；如果你的蓝色先画下去，我的紫色再画下去，我的紫色穿过你蓝色的区域，就应该把你覆盖掉——因为我在你的后面，对不对？然后这个时候，另外一个小朋友再点了一个绿色的点，这个点可能一半点在蓝色区域、一半点在紫色区域。这时候画紫色的小伙伴说：我想撤销一下，我觉得我刚才做得不好。哎呀，这个问题就来了：那个绿色的点和那条紫色的杠之间，到底有什么关系？这就是我们认为做协同编辑非常难的一个问题：怎么解决 undo、redo，怎么让不同的 operation 交错进行。

这里面其实有很多非常前沿的设计。先讲一个最简单的做法：加各种锁。比如一个对象，我给它加个锁，这是很自然的——声明这一篇东西都是我的了，它所有的语义都被我锁上了，你们不能编辑了。那很好，大家肯定没有冲突，但这里面会产生竞争。还有一种：这个资源是我的，你不能动。这个有的时候是有用的。举个例子，比如我去做一个模型，这个模型我打算改它的材质，但我不希望其他人再去改它的材质，因为彼此之间会冲突——那我就会显式地告诉你：这个资源我锁上了。这个锁信号可以以几十毫秒的速度瞬间同步给别人。

但即使有这样的两种锁，实际上你在处理 undo、redo 的时候，还是有非常多的问题。因为有的时候，你创建了一个 instance 并对它进行编辑，然后别人觉得你这个构图很好、这棵树很好，又对你的树进行了其他调整；然后你过了一会儿觉得这棵树不对，想重新种一棵，把那棵树撤销掉——那个小伙伴做的所有操作可能当场就会崩掉。所以这其实是我们在做编辑的时候特别复杂的一个问题。

这里面当然也有一些 pattern：比如 OT（operational transformation），非常的理论、很难；比如像我们真正在引擎里面经常用的 CRDT 这个方法——希望通过一套规则体系，让 conflict 变成 conflict-free，然后让各个状态在各终端那边都能同步。展开了就非常细节了。协同编辑是一个在理论上非常热的领域：随着网络的普及，协同操作是一个越来越重要的需求。比如上节课讲到的文本编辑，大家用的各种各样的网上文本编辑器已经越来越成熟了。我印象特别深，最早我用 Google Docs 的时候，它的功能是蛮受限的，但第一次发现我们能彼此看见对方的光标，实际上还是很震撼的。今天协同编辑，比如 Photoshop，已经做得非常好、很成熟了，但这个过程是非常非常的漫长。

现在的协同编辑里面，有很多种方案在一起竞争。比如现在我们会比较推荐的是：把所有的操作不要直接 apply 它的最终结果，先找一个 server，把所有操作聚在一起，结算完之后再统一地发还给大家。这就有点像我们以前做的网络架构里的 C/S 模型：所有客户端只是发起你的动作，你不要操作，由 server 统一结算完之后，把最终的结果返回给每个 client，你们自己去看。这样做至少有一个好处：你没有争议。你付出的代价是一点点的延迟——在一个局域网的情况下是可以接受的。这其实也是现在很多游戏引擎的协同编辑会采用的结构。

```text
客户端 A ──操作──▶┐
客户端 B ──操作──▶┤   server：收齐所有操作 → 统一结算 → 得出最终结果
客户端 C ──操作──▶┘
        ◀────── 把最终结果统一发还给每个客户端 ──────
```

但它可能会带来一个有意思的问题：如果客户端那台机器炸了，没关系，就它自己炸了；但如果被选做 server 的那个 artist 的机器炸掉之后，一群人直接就崩掉了。所以这个系统的健壮性和鲁棒性，其实还是有一些东西需要去设计的。

所以这件事情，我认为还在一个非常早期的阶段，但它是下一代游戏引擎研发很关键、很前沿的方向。在这里点一下，让大家有点感觉。

### DCC 工具与引擎工具的边界是动态的

课上有同学问了一个比较挑战的问题：在现在的游戏开发中，DCC 工具和引擎工具之间的分工到底是什么？首先这个问题非常大，也非常的难——说句实话，我自己现在有的时候也有一点点的晕。我跟大家讲两个有意思的发展方向。

第一个方向：现代的 DCC 工具，比如 3ds Max、Maya，包括 ZBrush、包括 Houdini，其实越来越强大。它们很多时候都 prefer 你能够在它们的工具里面做尽可能多的东西，甚至能提供一个类引擎 runtime 的 preview 给你；你甚至可以把你的引擎集成进去，给它做一个 viewer。这是 DCC 工具在推的一个方向。

但我又发现另外一个有意思的趋势：在一些前沿的引擎里面，我们希望把很多 DCC 的功能直接集成到引擎里面来。这个背后是有很深的道理的。举个简单的例子：大家如果看虚幻五的发布，里面就有这样的系统——可以在引擎里面直接手 K 动画。大家都知道，以前动画是由 Max、Maya 这些 DCC 软件做的。但在我们实战的游戏研发中，会出现一个问题：比如我场景中有一个扶手，我希望这个角色手抓着这个扶手跟你说话。这就很有意思了：我怎么做一个动画，让这个角色能够非常准确地抓住这个扶手？这件事情就很麻烦。传统做法是这样的：把场景导成模型，导到 3ds Max、Maya 里面——因为这个模型本来就有嘛；把角色放在我想放的位置，让 artist 在里面精准地把那只手放上去，然后开始说话；整个动画再导回到引擎里去，我只要把角色的朝向、位置、大小全部对准之后，在游戏的过场动画里面，这个角色就能精准地做这个操作。大家仔细想想，这个过程是不是特别的麻烦？非常非常的痛苦，对不对？而 artist 希望的是：既然你们的引擎工具做得那么强大了，把这个角色的手 K 一下这个动画有什么难？我们想想好像也不难，确实可以做。好，那我们就干脆把这动画这块也做掉了。包括你会发现，有些引擎会直接把一些 DCC 工具买进来，集成到自己的体系里面去。

所以我看到的是什么呢？我很难讲两边在分家，我看到的是大量、大量的融合。这其实也是符合引擎作为一个生产力工具的客观需求：实际上是以艺术家怎么方便怎么来。这也是我个人比较关注的一个方向：在引擎里面，怎么把这些 DCC 的功能直接集成进来，减少 artist 在不同工具之间来回切换的痛苦。《Game Engine Architecture》里那张经典的分层图，我一直讲那个图是比较古老、比较传统的：事实上每一个 DCC 工具的 exporter、importer，数据来回倒一次，就会产生一次出错的机会，还会极大地降低我们内容生产的效率，让整个内容生产变得更加不直观、很容易出错。所以两边的融合这个趋势现在特别的明显。你让我说哪个工具归 DCC、哪个归引擎，我认为这个边界是动态的，一直在变化。

### 本讲提到的题目

四节课基本结束的时候，照例给大家布置作业。讲完了整个工具体系、讲完了这些反射系统，我们有一个想法：如果同学们最想了解、最想掌握的是 Piccolo 这个小引擎，那它最核心的就是它的资产——为什么我们要做自己的 format、JSON 这个 format；做了自动的 schema 和反射系统；editor 里面可以自动产生所有的编辑界面；甚至做了一个小小的 content browser，还有旁边的 property panel。

**题干（开放式命题）**：尝试在 Piccolo 的资产（asset）里面定义一种你自己的属性。比如大家看到我们现在的这个角色，它有刚体（rigid body）、有它的 mesh、有它的 animation。现在你想对这个世界做一点小小的逻辑，无论做什么都可以——比如希望这个角色会自动打枪，或者有个血量：我想给它增加一个血量的属性，让它从高处跳下来会摔死，并且定义两个变量：从多高摔下来、受到的伤害是多少。请尝试在 Piccolo 这个引擎里面，把这些属性增加到 character 里面去：你可以在编辑器里编辑它，而且一键点 play 的时候，这些属性真的能跟你的引擎代码起作用。因为现在二次开发的接口还没完全开放出来，所以你还需要直接改 Piccolo 的代码，没关系；但你至少要把这条链路全部打通：从资产——那个 JSON 的 asset 文件——到引擎内部的数据，到整个编辑器。

**解析**：这条链路正是本讲讲的整套体系。第一步，在 character 的 C++ 定义里用 CLASS 宏把新属性标记出来（注意“全部成员反射”与 whitelist only 两种描述词的取舍——像摔落高度、伤害值这种需要和资产文件交换的数据才要反射，纯计算中间结果不必）；第二步，按反射的编译路径走预处理宏，让 Clang 解析出带标记的 AST，在内存中生成 schema；第三步，schema 套上预先写好的 mustache 模板，生成 get/set/invoke 这些 accessor，编辑器的属性面板因此能自动显示并编辑新属性；第四步，在 JSON 资产文件里把新字段读得进来、存得出去；第五步，在 gameplay 逻辑里读取这些属性（落体高度映射到伤害），一键 play 就能看到真实效果。做到“你自定义的 data 通过整套反射 schema 系统能够反射上来，同时在资产里真的读得进来、存得出去，并且真实地产生 gameplay 效果”，这道作业就算完成了。

这道题目其实蛮开放的，血量只是给大家举的一个例子，同学们可以自由发挥。提交作业的方法也是老方法：把作业的思路、实现的代码和效果的截图展示出来发给我们，我们给大家一些反馈。这是我们第一次尝试做一个开放性的作业——对写了 Piccolo 的我们来讲很简单，但相信对同学们来讲，一上手摸它还是有些挑战。

到这里，这一趴的内容就全部讲完了；下节课，我们进入非常有意思的 Gameplay。
