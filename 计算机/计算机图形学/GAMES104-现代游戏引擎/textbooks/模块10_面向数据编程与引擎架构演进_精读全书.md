### 课前三问：反作弊、微服务与全球联机

#### 反作弊永远是个动态平衡

第一个问题相对好回答：游戏到底有没有可能彻底解决反作弊？至少就我目前知道的，答案肯定是 No，搞不定。这玩意儿真的是道高一尺、魔高一丈，是全世界所有 online gaming 极其头疼的问题。

从技术上讲，你可以加密、可以通过各种方法去解决，但无论你用什么方法，总有人能破解。那接下来还有办法：从设计上就尽量避免别人作弊的时候能够获益。比如有的游戏把判定彻底放在服务器上，这当然是一种解法，但它会影响手感——不再用本地物理或其他本地手段来解决问题，而是改用更多可控的机制来进行判定。

我自己个人觉得还有一个很有意思的方法，是采取一种很奇怪的社交化思路。举个例子，比如 Steam 上的反作弊 VAC：你只要在一款产品里被发现作弊，就会被报到 VAC 那里，整个 Steam 账号都可能受影响。想一想，我 Steam 上那么多游戏，要是因为在一个游戏里开挂，导致那一串游戏都不能玩了——我想打死我也不作弊了。我觉得这可能是一个很好的方法。

简单来讲，游戏里的反作弊是一场长期的、艰苦卓绝的斗争，要持续不断地更新；而且我一直认为它不是一个纯技术问题，实际上还需要我们和社区一起、和玩家一起联动去解决和发现问题。所以它永远是一个动态的平衡。

#### 微服务和分布式不是"区别"的关系

第二个问题就非常专业了：微服务和分布式的服务器架构到底有什么区别？其实这两个不是"区别"的关系，我个人理解是这样。

分布式的服务器架构是一个标准的、也是最经典的服务器选择方法。它的对立面，是你把所有业务写到一个进程里面去。分布式的意思是：我会在多台物理机上，用多个进程或线程协同工作，每个人各司其职完成工作。它的具体形态可以有很多种：比如把数据库的访问和游戏逻辑分开；比如游戏里开很多战局，每个战局形成一个独立的 game server。只要你把整个游戏世界的业务拆成一个一个单独的进程或线程，这就叫分布式的游戏服务器架构。

而微服务（microservice）其实是一种设计理念，我认为它是分布式服务器架构的一种实现方法。它讲的思想是：把服务器后台的东西，拆成尽可能干净、单一的业务单元——比如邮件、聊天、用户登录、房间匹配等等，都变成独立的服务。微服务还有两个特点：最早期大家都尽量争取让服务无状态，为的是可以很容易地对它扩容、减负，支持弹性的变化；另外，一旦某些服务出了问题，可以通过服务发现发现问题，然后再 spawn 出更多的服务。所以它是一种非常好的、基于容器的分布式服务器系统实现方式。

这两者无所谓高下。你真去研究一下现代 online game 的服务器架构就会发现：它也不是完全的微服务——有些服务用微服务架构去做，有些东西还是要全局地自己去管理。所以就像我一直讲的：当大家真的开始做游戏的时候，千万不要纠结于某些具体的概念，不要一直争甜豆浆、咸豆浆到底哪个好——适合你这个项目的，就是最好的方案。

#### 全球联机对战难在哪

第三个问题就太难了：如何构建一个全球能够联网对战的战斗系统？这个问题要是真能回答清楚，你到很多游戏大厂里，可以申请比较资深的开发者职位了。全球联网的开房间对战游戏，技术上确实有蛮多挑战，比如全球物理连接的延迟——这么多节点来回，延迟怎么办？

概念层面其实不复杂。首先，服务器要进行分布式架构：在世界各地都有服务器，这些服务器之间要建立高速通讯。一个简单的做法，是给它们加一些我称为"高速主干线"的干线——专线，让全球各个机房之间通讯速度足够快。当然，你再快也快不过光速。

这里有个有意思的小细节：比如从中国连接美国或者欧洲，中间最大的延迟来自什么地方？实际上并不是光传播的速度——光传播过去差不多也就 100ms 左右，甚至不到。真正慢在无数次的网关路由上：数据不停地转发、转发、转发，每一次都会带来很多延迟。

所以如果你真的要做全球联网的游戏，那是一件很花钱的事：你要在世界各地购买或者自己建设专用机房，机房之间用光纤尽可能直接连起来；当然也有一些通讯服务商提供的虚拟专用通道。同时还有一层：比如欧洲的用户来自各地，不要让他们直接连你的服务器，你可以提供一些离他们本地更方便的节点。

举个实际的例子。你要服务南美玩家，南美洲看起来是一整块大洲，但它西侧有个国家叫智利，特别长；还有那条从北美洲一路贯穿到南美洲的山脉，号称世界最长。山脉左边和右边虽然都在南美洲，网络却是非常隔绝的：有些国家连接亚洲的速度，比连接这块大陆另一边的速度还要快。所以当你去服务南美洲这样一个区域的时候，实际上要做很多专门的处理：服务器到底架在墨西哥还是阿根廷？千万不要架到智利去；跟北美到底是直接连接，还是通过其他方式？这里面有很多有意思的问题——全世界网络的图谱其实非常好玩，下次有机会给大家详细讲。

所以这个问题从概念层面上讲不是很复杂，但你真的去实施它的时候会发现：你还真的需要知道全球高速光纤的分布图。

### 游戏引擎的处境：1/30 秒里的极限要求

现在进入正题，先讲为什么要做这件事。

现代游戏引擎跑在各种各样的操作系统上，操作系统又跑在各种各样的硬件上。游戏引擎最大的特点是什么？我们对 performance 的要求非常高。但带宽是有限的，算力也是有限的：我们要在 1/30 秒里完成大量的逻辑运算、物理的模拟；还要一瞬间渲染出几百万、上千万个像素里面无数的光的反射积分——rendering 那一讲里那些运算有多恐怖，大家还记得吧？后面讲到物理、讲到游戏逻辑、讲到一大堆动画系统的时候，大家想想，对算力的要求都太高了。

更"恐怖"的是，1/30 秒全部算完还不够。玩家说我不满意，我要 60 帧；60 帧感觉还不对，我要打电竞，我要 120 帧。好了，游戏引擎就疯掉了——臣妾做不到啊，我就这么一个 CPU，怎么做到这么高的要求？

所以当我们在设计游戏引擎的时候，实际上需要把操作系统、把硬件的所有性能几乎压榨到极限。这就是为什么所有重型游戏团队、引擎团队，基本上都是硬件和操作系统性能的大师——就是这个道理。

### 并行编程的由来：核越堆越多，主频上不去了

今天先从第一趴开始讲起：并行编程（parallel programming）。准备这一趴的时候，我和课程组的小伙伴一边写一边在笑——它让我回想起了大学上操作系统课的时候。那位老师年纪很大，一位老教授，每次扶着眼镜看着我们和那么厚的一本教材；我每次听课都昏昏欲睡，考完试基本上全还给他了。结果这次准备并行编程，我发现：哎呀，老教授讲的所有的东西，我又全部回想起来了。今天我尽量不切换到老教授模式，还是用简单的语言，把并行编程里有意思的东西讲清楚——因为它是 Job System 的基础。

并行编程的第一推动力，其实就是一个事实：现在的集成电路工艺已经 almost hit 到它的量子力学上限了。制程还在往前冲——大家都在做 2nm 量级的突破——但理论极限据说只有 0.5nm，而且这几乎是不可能达到的；再往下，1nm，接下来再怎么上也上不去了。

经常买电脑的同学会有感觉：过去这几年，核是越堆越多，但主频基本上三点几 GHz 就上不去了。我们团队有一块英特尔送来的 CPU，主频可以冲到四点几 GHz——但那个声音已经基本上有点吓人了。整个 processor 已经到了它的理论上限：再往上冲，无论是散热也好、功耗也好，都有很大的问题。

那解决方法是什么？既然不能把核越做越快，那我能不能用更多的核解决这个问题？所以今天大家买电脑，什么四核、八核、十六核已经是常态。而当我们有了这么多的核之后，就必然要想办法把这些核的算力全部利用起来。

> **结论**：单核的性能天花板是物理规律决定的，性能增长只剩"更多的核"这一条路；并行编程的全部动机，就是把散落在各个核上的算力重新收拢回来。

### 进程、线程与多任务

在传统操作系统里，我们很熟悉的两个概念就是进程和线程。还记得进程和线程有什么区别吗？我上操作系统课的时候，老教授问我的第一个问题就是这个。

进程拥有独立的存储单元，它的存储是完全独立的、由系统去管理；而线程在进程之内，实际上共享了同一份 memory。所以线程写不好，互相内存会打架；但线程要比进程轻量很多——不过这是 Windows 下的情况，在 Linux 下，进程也可以做得很轻量。

| 对比 | 进程 | 线程 |
| :--- | :--- | :--- |
| 存储空间 | 完全独立，由系统管理 | 进程内部共享 |
| 交换信息 | 必须通过特殊机制 | 共享内存本身就是通道 |
| 代价 | 重 | 轻量，但内存会"打架" |

我自己的理解是：线程之间会共享很多 memory，这块共享内存就是它们的数据交换通道；而进程之间，必须通过特殊的机制才能彼此交换信息。这是我们所有并行化编程的基础。

有了这么多核，我们就要去做 multi-tasking：既然有那么多核，就让它同时处理很多很多事情。大家回想一下前面课程里讲的游戏引擎：要做动画、要做物理、要做逻辑，还要做 rendering 的表现——游戏引擎天然就是 multi-tasking 的。如果你有四核、八核、十六核，我非常开心，直接用起来。

### 抢占式与非抢占式

这么多 tasking 在一起怎么去管理呢？这里有两个很经典的模型。

第一个是 preemptive multitasking，抢占式多任务——这就是操作系统的那一套。它的意思是：一个线程在跑的时候，调度者如果认为你该出去了，就把你调出去，过一会儿再把你调回来；这是调度者自己决定的。比如来了一个 high priority 的事情，我就要打断你——调个中断，哥们儿你出去，我进来。听上去很霸道，但大家仔细回想一下我们的操作系统，比如 Windows，它是什么性质？它就是抢占式的。因为不可能让你一个进程把整个系统资源全吃光了——那操作系统本身怎么跑呢？

第二个是 non-preemptive，非抢占式：你既然在干活，我不会主动打断你，除非你自己说结束了。它的好处是：如果所有的任务都是你给的，你对它的控制能力其实很强。但缺点是：万一你写坏了，一直把资源占着不走，其他所有人都被迫要等着你。这种方式在操作系统里实际上很少用，但在一些 real-time 要求非常高的操作系统里，也会采用这种非抢占式的多任务模型。

| 对比 | 抢占式（preemptive） | 非抢占式（non-preemptive） |
| :--- | :--- | :--- |
| 谁来切换 | 调度者随时打断、随时调回 | 任务自己结束才让位 |
| 控制力 | 操作系统兜底，谁也别想吃独食 | 任务都是你给的，控制力很强 |
| 风险 | 切换本身有开销 | 写坏一个任务，所有人陪等 |
| 典型场景 | Windows 等通用操作系统 | real-time 要求极高的系统 |

这两个东西，是我们做整个多线程系统的两大基础。

### 线程切换的真实代价

既然可以启动很多线程，线程之间就会不断被打断、在多个任务之间来回切换。比如我启动了 20 个 thread，但是只有 4 个核，那就意味着我要在这 20 个线程之间来回切换。你会发现，这个切换其实非常不"廉价"。

首先，一个线程被打断要掉一个中断，这个中断至少要 2000 多个 CPU cycle。想想看，最快的指令只要 1 个 cycle——大部分指令确实不止一个 cycle，但 2000 多个 cycle 实在是很慢。更麻烦的是：你把现场切换出去、再切换回来的时候，新进来的线程面对的数据并不在它的各级缓存里，它要从内存里重新去调这些数据——这个时候的延迟，可能在 1 万甚至 100 万个 cycle 之间。

> **结论**：线程之间的切换很贵很贵。这也是后面我们讲 Job System 的时候，它的设计是 fiber-based 的道理——Job System 正是意识到了这件事其实非常 expensive。

今天讲的东西稍微有点硬核，我会被迫讲很多硬件是怎么操作的、操作系统是怎么操作的，大家甚至要理解 CPU 各级的 cache。没关系，大家先姑且一听，以后一边学、一边自己写代码，一边就能感觉到了。

### 并行化的两类问题

在写并行化编程的时候，我们一般会遇到两类不同的多线并行化问题。

第一类非常简单：这些任务我不打断你，你该做就做完，我不会让你停下来。这样的好处是，它不会有 thread interaction 或者 thread swapping 的问题。它就是一堆独立的问题，各自算完，然后大家一起收口。这个模型最简单的案例就是蒙特卡洛积分：每个线程负责撒 1000 个采样点，合起来采够 100 万个采样点，这个事情就做完了。这样的话，其实不会遇到 thread swapping 的瓶颈。

但在真实的游戏案例里，我们没有办法把一个游戏所做的模拟分得那么清楚：各个系统之间有大量的数据依赖；还有一种依赖关系叫 dependency——我得等你这个事情做完之后，才能启动我的事情。这就会让并行编程变得非常复杂。只要有一点点并行化编程的经历，这是你一定会遇到的问题。

### Data race：一切麻烦的核心

那这个问题怎么解决？首先要理解：这里面会产生的问题是什么。最容易出的就是 data race（数据竞争）：同一个数据，当一个线程在读它的时候，另外一个线程正在改变它。如果你的逻辑是"读完它的值、根据它做一个判断、再去做一个操作"，很可能你读的时候是一个值，等你真去对它操作的时候，那个值已经被修改成另外的值了——这两个东西是不是就有问题了？

大家有没有试过三四个小伙伴一起在墙上轮流写东西？你看到的，和你落笔写上去的，完全是两回事。data race 就是围绕着所有并行编程的核心问题：产生的死锁、产生的种种乱象，核心都是这件事。

### 临界区与锁：阻断式的解法

最简单的做法，是做一个 blocking 的方法。这里有一个词叫 critical section（临界区）。以前学操作系统的时候，老师一开始就跟你讲什么叫 critical section，我心想：critical 这个词英文直接翻译过来，就是"很重要的、很艰难的部分"这种感觉嘛。其实它本质上讲的是：这一段代码，从我进去直到我出来，你们不要捣乱——我必须完整地执行完，其他人都不许执行同一个点；也就是说，在别的线程里面，这段代码不能够被同时重复执行。

举个实际的例子：比如我们有学生注册，每个人注册时往一个计数器里加一，然后还要把学生塞入一个数据库的表里面。如果这个数据库是单线程的，好，那每个往数据库里塞东西的操作，我就通过一个 mutex 把它全部控制住——同一时刻只有一个人能进这段代码。

critical section 在现代编程语言里已经有很多种实现方法了：比如真的显式定义一个 critical section，可以通过 mutex，还可以通过 semaphore（信号量）这些东西——都能够去解决它。

> **定义**：critical section（临界区）——同一时刻最多允许一个线程进入执行的代码段；mutex、semaphore 等都是实现它的阻断式手段。

但这样一种阻断式的并行化编程，会产生比较严重的问题。

第一个是死锁：我在写一个变量、又在等一个变量，其实很容易产生死锁。

另一个问题其实蛮头疼：假设我们并行化同时启动了几十个甚至上百个任务——在真正的大型系统里，你并不能保证这些 task 一定会成功，有些 task 甚至写的会自己死掉。一旦有一个 task failure、甚至 crash 了，它会导致整个系统的死锁。写代码不小心的时候，很多时候就会出现这种很严重的问题。

还有一点：一旦进入 critical section，它实际上是被彻底保护住的。有一些更高优先级的任务想进来，按照目前的调度算法，它其实是不会被打断的——你的高优先级的东西很难去动它。所以用 lock 的这种方法，有时候就是你很难去动它。这是一种很古典的架构。

所以当我去架构一个很大型的系统时，关于 lock 有个简单的原则：能不用就不用，要用也是越少越好。后面讲 Job System 的时候会讲：这个东西我会用，但是会用到非常非常少。

### Lock-free：把保护下沉到一条指令

再往下有一种叫 lock-free 的编程。它的想法很简单：既然有些变量很敏感、怕所有人同时去改变它，怎么办？我把它变成原子性操作。

原子性操作其实很神奇：它是在硬件和底层支持的一个东西。说实话我到现在也没完全搞清楚 CPU 到底是怎么实现这件事的，但它确实在硬件底层实现了：它能保证你对一个变量的读写操作，不会被多个任务同时侵占。

这里面有两个核心概念：load 和 store。把数据从内存中读出来看一眼，这是 load；往 memory 里写进去，这是 store——load 和 store 是原子性操作很核心的概念。说实话我最开始理解的时候，load/store 对我来讲还是有点抽象的。在这基础上还有一系列听着都很高大上的指令：比如 RMW（read-modify-write），你去读它的数据、修改它的数据、再写进去；还有 CAS（check-and-set）：先 check，再去 set 改变它。这是一系列的原子指令。

它们共同的核心想法是：你不需要把一整段代码锁住——因为这段代码里面如果有崩溃、有什么样的问题，你是控制不住的；我只在一个绝对保证能够执行下去的指令里面，保证对这一个内存数值的操作具有原子性。这个数值一般来讲是个 integer，也可以是一个布尔。

> **定义**：原子操作（atomic operation）——由硬件在指令级保证不可分割的内存读写；它保护的是一个值的一次操作，而不是一整段代码。

如果大家用过那种抓取多核硬件、抓系统 profile 的软件，会看到一张让你很有压力的图。像我们这种强迫症，看见引擎跑起来之后曲线上面有很多空洞，就很难受——空洞说明什么？说明那段时间我的 CPU 在 idle，在等其他任务启动。实际上，大家在写多线程编程的时候，大概率会写成这样：

```text
理想中的 CPU 利用率              现实中的 CPU 利用率
core0 ####################       core0 #####____########____####
core1 ####################       core1 ##____########______######
core2 ####################       core2 ########______##########___
core3 ####################       core3 #____##########____#########
```

图里的下划线就是那些空洞：CPU 没有在算你的活儿，而是在干等。

lock-free 编程的好处，是它能够通过原子操作尽可能地避免死锁；但因为原子变量之间彼此等待、彼此依赖，它还是会产生很多的空洞。

### Wait-free：理论上的满分答案

还有一种编程范式，是理论上的，叫 wait-free——等待几乎为零的编程。它事实上有一套数学的方法，能保证在多线程的研发中，尽可能把所有的 CPU 资源全部占掉。

但 wait-free 这个编程实际上挺复杂的，说实话我自己都没有完全搞清楚。大家可以看到：给你一个非常复杂的系统，你能保证这个系统彼此之间对 CPU 的利用率是百分之百——这件事情几乎是不太可能的，到目前为止我没看到一个理论的架构能做到。但是，你对一个具体的结构——比如对一个队列——把它的操作变成 wait-free，这件事情现在在行业里已经有解法了。

如果你做的应用对性能非常 critical，比如写那种高频的通讯协议，那你可能就要用这种结构的编程。而这种编程需要严格的数学和推演证明：证明它不会产生我们前面讲的各种各样的异常。

所以我的看法是：做引擎的时候，很多时候大家能掌握到 lock-free 这一层就可以了。因为接下来大家会看到，那些 gap 在 Job System 里面能够相对好地去解决。

### 编译器和 CPU 都不按你写的顺序执行

多线程里的问题，其实比大家想象的还要更复杂一点。我们写一段代码的时候，天然认为这个代码会顺序地执行下来：1、2、3、4、5。像我们小时候学的解释执行语言——不知道有多少同学真的还写过，现在的很多脚本语言也还是解释执行——你可以非常清楚地看到它一行一行地执行下来。我觉得最早的 Basic 语言就是解释性语言。

但当我们去写一些高级语言，比如 C 语言，交给现代的编译器之后，编译完你完全不知道它真实的汇编是怎么实现的。你定义了一个操作在前、一个在后；或者这个变量你先设成一个值，比如零，然后对它加一，然后重新设成三，再对三做减一——编译器很可能会把你优化成两段无序的代码。为什么呢？因为它只要保证你顺序执行下来结果是一致的，它就认为这是一个有效的编译。但这种情况，可能在多线程的情况下就会出很大的问题。

给大家举个简单的例子：

```cpp
int a = 0;
int b = 1;

// 线程 1
void thread_one() {
    a = b + 1;      // b 此刻是 1，所以 a 变成 2
    b = 0;
}

// 线程 2
void thread_two() {
    while (b != 0) {
        // b 还没被清零，说明线程 1 还没执行到那一步，持续等待
    }
    assert(a == 2); // 直觉：既然 b 已经清零，a 必然已经是 2
}
```

大家去理解一下：假设我们的代码真的按我们想的这个顺序去执行，看到的应该是这样一个结果——当你看到 b 等于零的时候，a 一定等于二，对不对？

但实际上，编译器在编译线程 1 的时候，会认为上面的 a 和下面的 b 是两个无关的变量。它最后出来的结果，b 是等于零的、a 也是等于二的，但次序可以变：它可能用一个临时寄存器先把要写的值备好，把"b 设为零"这件事提前了；而 a 呢，抢先用了前面那个 b 的旧值把它设成二。于是当你在这边看到 b 等于零的时候，"a 已经完成了等于二这个操作"的假设是不成立的——断言就炸了。

这种编译器的乱序，在我们做并行化开发的时候，是特别特别容易出问题的地方。再给大家讲一件很恐怖的事情：我们的各种硬件——从 PC 的 x86 架构，到 PowerPC，再到 ARM 架构——很多 CPU 其实并不能保证你一定按照代码的顺序依次执行下来。特别是 ARM 架构，它非常追求功耗和性能，所以要追求尽量简单。比如你写了一个 100 行的函数，编译器分析完之后，把你的函数框框切成大几段，里面的变量一通乱替换，最终保证结果是一样的，这个结果就出来了。而我们人天然理解函数执行顺序的时候，会认为第一个 section 做完之后我就会做第二个 section，第二个 section 是基于第一个的——单线程里这没有问题；但是你在另外一个线程里面，假设那边事情的发生也是 section one、section two、section three 这样的话，那你就完蛋了。

所以同学们在做移动端开发的时候，会遇到这样一种情况：有时候在 PC 的模拟器上，我的代码跑起来完全没有问题；为什么到真机上就突然 down 得死去活来？其实就是这个原因。

而且这一点，在新一代的 C++ 语法里——如果我没记错，应该是 C++11——其实可以显式地要求编译器，确保这些东西的执行顺序是一致的。但是你付出的代价是什么？实际上是它的执行性能会变得更差。

> **易错点**：单线程下，乱序优化完全无害——只要结果一致；可一旦有另一个线程也在盯着同一批数据，"我按顺序写的"就不再等于"它按顺序执行"。跨线程共享的数据，永远不要依赖"目测顺序"。

那为什么编译器要乱序？这就要说到现代 CPU 的原理（后面也会提到）：CPU 实际上要从内存中反复地读出你的数据和指令，而 CPU 的速度很快，它总是会饥饿地等着数据。所以现代 CPU 有的时候不会等着你的指令一条条执行、再根据指令决定什么时候去读数据，它恨不得把一大段函数一整块切成很多股，一股脑扔进去，让你的指令和数据同时在里面运行——这样它的结果才会快。现代编译器基本上也是按照这个原理去优化的。

在单线程的世界里，这些"自作主张"都与你无关；可一旦踏入多线程，这就是你每天都要面对的现实。

## 游戏引擎的并行化之路：从固定线程到 Fiber Job System
> 对应块：BLK48 | 覆盖分集：P27下 | 块标题（分集名）：《第二十节(上)：现代游戏引擎架构：面向数据编程与》

### 先立一条常识：CPU 执行是乱序的

为什么写多线程代码的时候，debug 版一切正常，release 版却莫名其妙地挂掉？这件事值得先讲透，因为它是这一讲所有讨论的地基。

做程序开发的都知道，我们有一个 release 版，还有一个 debug 版。debug 版有个特点：函数执行的时候，你基本可以认为它的顺序是对的。可一旦编到 release 版，最后编译出来的汇编和它的执行逻辑，可能跟你想的完全不一样。我自己在这方面有很多惨痛的经验：写一段多线程代码，debug 版跑起来逻辑都很成立，写得很开心；一到 release 版，经常莫名其妙就挂了。而且这种 bug 非常难查——因为你根本不知道编译器的优化做成了什么样。

所以当我们进行并行编程（parallel programming）的时候，这是必须建立起来的基本常识：一段函数在 CPU 中的执行是乱序的，你不能假设这些变量的值符合你写下来的那个顺序。

> **易错点**：debug 版"看起来没问题"不等于代码没问题。debug 只是让执行顺序贴近你的书写顺序，把问题暂时藏住了；release 一开优化，乱序执行立刻把你隐含的顺序假设全部戳穿。

### 最朴素的方案：每类任务一条线程

知道了这些常识，回到课程正题：在游戏引擎中，我们怎么做并行编程？framework 要怎么搭？

最简单的做法，也是大部分现代游戏引擎用过的做法：把每一类任务分给一条线程——rendering 的事归渲染线程，simulation（比如物理）归模拟线程，游戏逻辑再给一条线程，一人一条线程，井水不犯河水；彼此之间的通讯，就在每帧开始的时候交换一下数据。如果去看一些比较古典的游戏引擎，很多就是这样一个架构。

这个架构其实挺好使的。在两到四个核的情况下，它真的很好，而且你可以切分得非常清楚。但它有一个绕不过去的问题：你很难保证这几条线程的 workload 是一样的。有的线程活很轻，很快就结束了，但没办法，只能等；有的线程 workload 很大，你就得等着它。这是个木桶效应——所有人都得等最慢的那条线程完成它的任务，这一帧才能结束。

```text
渲染线程   ########............
逻辑线程   #####...............
模拟线程   ####################  <- 最慢的线程决定这一帧何时结束
```

图中实心块是有效工作，空心点就是白白空转的等待时间：轻的线程早早收工，也只能陪最慢的那条一起耗到帧末。

那有同学会说，那很简单啊，把比较重的 workload 拆掉，分给那些很轻的线程，不就均衡了？这件事情其实非常复杂，很难。难在两件事：

第一件，数据访问的 locality。我们希望一条线程访问的数据尽量集中在一块地方——比如渲染，我们希望渲染的基础数据就是集中在一起的。你不能说渲染的基础数据本来在渲染线程里访问，看到 simulation 线程有空，就把这部分访问挪到 simulation 线程里去——那完蛋了。这些数据全在同一条线程里读写是安全的；多个线程同时对一块数据进行读写，前面讲的那些麻烦（data racing）就全来了。所以很多时候，这个数据你没办法分。

第二件，对一个游戏来讲，不同的场景下每条线程的负载完全不一样。有的场景在某些环境下渲染特别慢；换到另一个环境，游戏里角色和敌人特别多，逻辑又忙不过来。而这些全都发生在同一个游戏里——你不可能让玩家玩到不同阶段的时候，把这些线程的分工做一些动态的调整，那会导致更多的 bug。

所以这种固定多线程架构的问题就在这里。去看用固定线程架构做并行的产品，凭我的感觉，大概至少有三分之一左右的计算资源是浪费掉的。当然这个数据不一定准，只是个经验数据。

固定线程法还有一个最大的尴尬。你一上来分了四条线程，结果跑到一台双核电脑上怎么办？很尴尬——只能是两条线程在同一个核上来回竞争，而线程来回切换有多慢，前面刚讲过。另一种情况是个幸福的烦恼：玩家配了八核十六核的电脑，你不可能让引擎根据这种情况把线程分布动态地改制——这种事非常难调试，根本做不了。那就只能眼睁睁看着那么多计算资源放在那儿，用不了。很多游戏你感觉已经卡住了，CPU 资源却没有被占满，其实就是这个原因。

### Fork-Join：重活摊给工人，做完再收

另外一种思路叫 fork-join。它的出发点是一个观察：动态调整线程分工很难，但我发现游戏计算中有些东西一致性非常高，计算量又很大——比如动画。前面动画课里学过动画的结算，那是非常复杂的重复运算，一下子有很多平衡方程、线性代数、矩阵运算，这些运算全部可以拆开来算。

于是就有一个 pattern，叫 fork-join：到了一定的时候，把固定线程手里的活 fork 出去，扔给 worker thread——我们预先申请好的一批工作线程；做完之后，把这些线程收回来，把结果合到一起。现在很多基于 Unreal、基于 Unity 引擎做的游戏，basically 走的就是 fork-join 这条路。

它的好处是能够相对充分地利用多核算力：四个核也好，八个核、六个核，都能相当程度地利用起来。因为 worker thread 的数量，很多时候就是问操作系统"你有多少核给我"，有多少开多少——你有这些工人，我不用白不用。所以它的适应性比固定线程要好那么一点点。

但问题也还在：即便这样，执行时间线上仍然有很多地方是空的。fork-join 的工作还是难以 balance，中间产生了很多 gap。

看一下 Unreal 会更有感觉：它实际上就有两种线程。一种叫 named thread，很明确地告诉你这条是跑游戏逻辑的、那条是跑 rendering 的；此外还有很多 working thread，物理这类计算可以整个展开、扔到这些线程上去。抓一个用虚幻做的游戏，用 profiler 抓出来的图，大概就是这个样子。

总的来说，fork-join 是一个比较清晰、也比较鲁棒的架构。如果对多线程的要求没有那么高，这是一个非常好的选择。

### Task Graph：把任务和依赖交给系统

第三种方法比 fork-join 更复杂一点。fork-join 是一棵树，展开来再收回来；还有一种更复杂的，叫 task graph。以前有一个很著名的 SDK，TBB，就可以创建很多任务，把这些任务之间的 dependency 设置好，然后一下子扔给这些核去处理；这些核可以根据任务之间的 dependency，自动决定哪个先执行、哪个后执行、哪些能够并行执行。

想想看，如果我们今天要做一个多线程系统，这是很自然的、我们认为本来就应该发生的事情。而对游戏这个 scenario 来讲，任务依赖这件事尤其重要——因为游戏创建的大量的计算任务是有 dependency 的。你要用多核的方法去运行它，又不想把这些任务写死——task 2 我就把你扔给这条线程，task 3 我就把你扔给 animation thread——那实际上你必须构建 dependency graph。现在很多引擎用的也是这样一个技术。

task graph 怎么做？其实比大家想象的要简单得多，很淳朴：在代码里一个一个 link 去构建——先表示 task 1 的 dependency 是 task 2，task 1 的下一个是 task 3……一个一个标记下来；把这些依赖关系全部做好之后，就形成了一张依赖图。系统拿到这张图之后，就可以执行下去了。非常简单。

但它的问题是什么？第一，这个 task 树的构建，对很多技术来讲是不透明的。第二，它假设 task 1 执行完之后才能执行 task 2——可真实的游戏引擎里经常发生的事情是：一个任务执行到一半，突然发现还得做很多很多事情，才能把这个任务做完。比如我要做一个角色的动画，做到一半，突然意识到得先做完它的一些物理，甚至会 fork 出它的伤害检测等等这些任务，然后这些任务完成之后才能回到我身上。真实的游戏引擎里，这些任务彼此是在运行中不断地创新、不断地设置越来越复杂的 dependency 的。

静态的 task graph 面对这种局面有两个很大的问题：一是在运行中动态地不断增加节点，实际上非常复杂；二是它的早期版本并没有实现"我做到一半，要等其他的事情做完之后才能继续走"这个机制——这个东西必须要靠后面的系统才能解决。

把这三种方案摆在一起看：

| 方案 | 核心思路 | 好处 | 短板 |
| :--- | :--- | :--- | :--- |
| 固定线程 | 渲染、模拟、逻辑各占一条线程，帧首交换数据 | 划分清楚，2~4 核时代很好使 | 木桶效应，负载没法均衡，核数不匹配时更尴尬 |
| Fork-Join | 在重活处 fork 出一批同类任务给 worker thread，做完再收回 | worker 数量跟着核数走，多核适应性更好 | 只在成批同类任务处并行，仍难 balance，时间线上仍有空隙 |
| Task Graph | 声明任务和依赖，系统按依赖图调度 | 调度自动化，符合多线程直觉 | 静态图：动态加节点复杂，不支持"做到一半等别人" |

好，讲了这么多——加上前半节课，差不多讲了半个小时——我们才能回到今天的第一个主角：job。这是现代游戏引擎里大家谈得比较多、也有引擎在实践中真正验证过的东西。

### 协程：执行到一半，可以"让道"

讲 job system 之前，先讲一个概念：协程（coroutine）。这个词听上去还挺高大上，实际上它是一个非常轻量的"多线程执行上下文"的一种方式——这话说得不太像人话了，简单来讲就是：一个函数执行到一半，可以调一条指令叫 yield。yield 就是英文"让道"的意思：我执行到一半，要等别的事情发生，我把执行权让过去；过一会儿，别人再把我 invoke、把我激活，我又可以按照刚才那个地方继续执行下去。

打个比方，讲一个大家好理解的例子。假设我是一个学生，要去学校报名。报名这件事做到一半，我突然发现缺了材料，怎么办？我得先把手里的事让一下——先去找打印机，把我所有的报名材料打印出来，才能走下面的流程。可打印机不是你当场要打就能打的，得让它打完。直到打印机打完我的材料，我才能回来，继续进行下面的操作。

协程的核心就是这个原理：你虽然在做一个任务，但这个任务中间可以让道出去；过一会儿别人把我唤醒的时候，我还能回到原地，接着往下做。

> **定义**：协程（coroutine）就是"执行到一半可以 yield 让道、之后还能从原地 resume 接着跑"的函数执行方式，切换完全由程序自己的逻辑控制。

这件事情在现代很多高级语言、特别是并行化编程里是原生支持的。比如 Go 语言原生就支持；C# 里这些概念用得也特别多——有了这样的结构，写一个并行化的程序就会非常方便。但非常遗憾，在 C++ 里，协程这件事情就很蛋疼。为什么头疼，待会儿解释。

### 协程与线程：换座位要不要报备

协程相对于线程，有一个很大的区别。

线程是靠硬件中断来切换的：硬件中断发生的时候，它的栈、所有的环境、context 全部会重置一遍，所以它的成本非常高。对性能有所了解的同学都知道，线程之间切换的时候，操作系统的开销是非常非常高的。

协程一般是由程序自己定义的，而且一般是在同一条线程里，让很多个协程之间来回切换。从 CPU 看来，这还是同一条线程，从来没掉过中断——是我们自己的程序逻辑让它们之间换来换去。所以这里根本没有激活 kernel 的 switch。

线程切换为什么那么贵？因为你要不断地调中断，那是整个 kernel 级的东西，操作系统全都知道这件事了。你想，这事就麻烦了。就像平时你给你的小伙伴换个座位：你们俩互相商量一下，"咱们俩座位换一下"，这事就完了。但如果这件事被教导主任发现了，你觉得这事儿就很麻烦了。

所以协程和线程的区别就在于：线程是公事公办，整个学校系统全部报备；协程呢，就相当于读书的时候跟同桌商量一下，我们俩把座位自己换一换——班主任发现不了，也不需要向学校报备。而且今天换到这、明天换到哪，随便我们根据自己的需求来。这样一来，整个 overhead 就下降非常多。

### 有栈协程与无栈协程

协程实际上有两种类型。先说声抱歉，现场我可能会叫错名字——coroutine，它分两类。

#### 有栈协程（Stackful）：回来时一切如初

一种叫 stackful，有栈的、有状态的。想想看，一个函数执行到一半，这里面有什么？有很多局部变量，还有很多计算状态。比如我在函数里定义了一个局部变量 a，初值是 5，一路算到了 100，接下来要做 a+1。这时候你跟我说调了个 yield——行，没问题；但过一会儿我回来的时候，a 以及所有这些变量，是不是要全部复原？

难点就在这：函数跳出去了没问题，可那个时候有其他的函数来了，那块栈空间别人就要用掉了——这时候栈怎么恢复？这件事情非常难。但从编程的角度讲，程序员写代码的时候，会天然地认为：我从 yield 的地方再回来的时候，我所有的 local variable、所有的寄存器，全部都不应该被污染——否则这个代码的逻辑根本写不下去。这跟上次讲 RPC 的道理一样：人脑对一段业务逻辑的理解，天然就是一口气记下来的。

还是拿学生报名举例。你前面已经要来了你的学号、你的班级号，ok，这时候你打算去打印你的申请表格，于是 yield 了。好，表格纸打印回来，你开始填写——你其实天然地 assume：我知道我的学号和我的班级号。记住，在你完成报名这个任务的过程里，学号和班级号是你本地的变量；你的大脑实际上把这些东西记录下来了。等那张纸拿到的时候，你的大脑 resume，整个 coroutine 就继续往下走下去了。

所以 stackful 这件事情非常关键：我能不能把函数执行的所有 context 恢复回来。

#### 无栈协程（Stackless）：回来时一笔勾销

相对于 stackful，另外一种就是 stackless——无栈、无状态的 coroutine。它的意思是：我回来了，我不管了——你前面所有的局部变量、所有的寄存器，我全认为被清掉了。

这么做的话，协程就非常好写。比如在 C 语言里，你想实现一个无状态的 coroutine 怎么写？很简单：写一个 goto，直接从函数里面跳出去，然后你有本事再跳回去——你整个状态就全错掉了。这个事情我建议大家轻易别做，因为它有很多很多的问题。

stackless 的好处是它实现起来相对简单；但它对这种 coroutine 的开发者要求非常高，而且一旦写不好，它会产生大量的 bug。

#### 引擎的取舍：把困难留给自己

这里顺便讲一下游戏引擎开发的一个核心挑战是什么：不是我的技术越高端越好。实际上，一个游戏引擎只是一个基座——当我们去做不同的游戏产品、在上面做应用的时候，很多人会基于你的接口进行开发。如果你对这个开发者的要求特别高，比如他必须非常清晰地理解并行编程的各种坑，那基本上这个引擎是没人能用的，因为这个挑战太大了。

所以游戏引擎有一个很重要的任务：把困难留给自己，把最难的东西留给自己。对开发者来讲，你能用简单的代码解决的问题，尽量用简单的代码；你能用脚本写完的，最好；你能连几张图（graph）就能完成的任务，那是更好。

按这个逻辑，取舍就清楚了：stackless coroutine 除非在很底层、我们自己用，否则我们会尽量不用。但它并不是一无是处——无状态的 coroutine 一个很大的好处，是不需要再去保存和恢复整个栈和 local register 的状态。所以如果这些代码非常高频、又非常底层，只有少数几个很核心的同学去写，那用 stackless 也是一种方法——只是对写这个代码的同学的水平要求非常高。

而当我们作为一个引擎，想做一个高度并行化的引擎，让所有的游戏开发程序员也能享受并行化的乐趣的时候，我们会非常强烈地推荐使用有状态的 coroutine，也就是 stackful；stackless coroutine 我们会建议用在非常底层、只有少数人控制的地方，而且是非常 native 的代码——甚至你惹急了，写汇编也没有问题。

两种实现无所谓高下，摆在一起看就清楚了：

|  | 有栈协程（Stackful） | 无栈协程（Stackless） |
| :--- | :--- | :--- |
| 回来时恢复什么 | 局部变量、寄存器、整个执行 context 全部复原 | 一律不管，默认全部清空 |
| 实现难度 | 高：栈被别人用了还要能恢复，要动汇编 | 低：跳出去、再跳回来就行 |
| 对写的人 | 业务代码按同步思路写，程序员心智负担小 | 要求极高，写不好就是大量 bug |
| 开销 | 每次 yield/resume 要保存、恢复栈，栈大有成本 | 不需要保存恢复栈和寄存器，极轻 |
| 该用在哪 | 引擎通用并行框架，推荐给所有游戏程序员 | 非常底层、少数核心同学维护的高频 native 代码 |

### C++ 的现实：协程得自己造

stackful coroutine 有一个很大的难点：在不同的操作系统下，native 语言——特别是 C 和 C++——并不原生支持 coroutine 这个机制。

比如在 Windows 下想实现 coroutine，有一些方法：Boost 有一套底层机制，实际上能帮你实现 stackful 这种机制。但如果你仔细读它的代码，你会发现它里面调的是汇编——要把寄存器、堆栈全部导出来；而且栈的大小你还得设置，也就是一上来要告诉系统：我这个程序里每个函数的栈空间有多大。

栈空间设置小了会怎样？你的函数写着写着，栈空间就炸掉了。写过递归代码、或者有些函数的局部变量又申请得太大的同学，会遇到一个问题，叫栈空间爆炸（stack overflow）。只写 Python 或者 Haskell 这类语言的同学可能很少遇到，但写 C++ 的同学一定会遇到。

那栈空间的大小怎么权衡？设小了，stackful coroutine yield 出去的时候，要把这一段栈空间拷贝出去、在内存中保存起来、最后再恢复——快，性能高。设大了呢，每一次 coroutine 的 yield 和 resume，成本就会高。所以你会发现很有意思：写这样一段系统的时候，你要对操作系统调度的底层、内存在中怎么分配、数据怎么存、代码怎么存，理解得非常清楚。

还有一件很蛋疼的事情：这一套 coroutine 的底层实现机制，在不同平台上做法不一样。Windows 是一套；PlayStation 好像原生支持 coroutine——哎，这是好消息，好像我如果没记错是这样的——哎呀不好意思，这好像是保密的信息，我就不讲了。而在 ARM base 的芯片上面，好像要自己通过一段汇编去实现类似 coroutine 的机制。好消息是，这些方法在网上有很多很好的样例，实在不行参考一下 Boost，也能知道怎么做。

所以协程——特别是 stackful coroutine——是我们在构建游戏引擎基础设施时的一个 foundation。

### Fiber-based Job System：理想的多线程形态

有了 stackful coroutine 这样的东西，接下来我们就开始有趣的东西了。这个东西听上去非常高大上，叫 fiber-based job system。fiber 这个词怎么说呢——光纤的英文好像也是 fiber——听着就蛮高大上的；它是 Windows 的一个概念。为什么我对这个词特别有感情？因为十几年前，我在美国参与架构下一代引擎的时候，我们就想加多线程、高度并行化，所以那时候就研究了 fiber 这个技术。所以我觉得这个词特别酷。

其实 fiber 你可以理解成：我们架构一个高速的线程管道，往里面高速地放很多 task；这些 task 里面可以自由地进行各种 coroutine 的切换。而塞进 fiber 里面的这些任务，我们叫做 job。job 可以设置 dependency，还可以进行各种 priority 的设置。

这个想法其实非常简单。想想看，当我们去实现一个真正的多线程系统的时候，job system 是不是我们最理想的情况？原则上来讲，你有 100 个、1000 个不同的任务，我有 10 个核，大家就纷纷根据每个任务的长短，像搭积木一样凑在一起，尽量确保所有 worker 的任务在同一时间进来、相近的时间完成。这就是 fiber-based job system 最简单的一个想法。

这里有一个有意思的细节：fiber 你可以想象成一条 worker thread。那我到底申请多少个 worker？我的游戏跑起来，发现这台电脑有 4 个核，申请多少条？假设发现这台电脑有 16 个核，又申请多少条？这里面有一个 trick，也是 fiber 系统很核心的一个思想：我尽可能让一条 worker thread 对应一颗核。这个核可以是逻辑核，也可以是物理核；一般我们会对应逻辑核。逻辑核什么概念？大家看现在的 CPU 都是 hyper-thread（超线程）的：一颗物理核，逻辑上分成两颗。一般来讲，一条 hyper-thread 我们给它配一条 working thread。

这样的好处是什么？当我不停地往里面加不同各种各样的 job 的时候，我并不需要这些 thread 进行 swap。这是 fiber 系统最核心的一个思想：在这个系统里面，thread 的 swap 几乎是零。这非常重要——每一次 thread 的切换是非常昂贵的，前面刚讲过。

所以你看，这就很淳朴了：有多少颗核，我就生成多少条 working thread。

### Job Scheduler：谁先谁后有讲究

整个系统怎么转起来？用户生成了一个个 job，压到 fiber 里面去，让它们依次执行；working thread 就是个可怜的工人，开始一个一个执行所有的 job。

注意，job 之间有两个很核心的概念：一是它们之间有优先级（priority），二是它们之间有 dependency——一个 job 可以 fork 出来很多其他的 job。那 working thread 怎么去调度？

```text
        用户 fork 出一批 job（带 dependency / priority）
                          |
                          v
              +---------------------+
              |    Job Scheduler    |   <- 全局调度：按各 worker 的饱和度分发任务
              +---------------------+
               /         |         \
              v          v          v
          Worker#1    Worker#2    Worker#3       <- 一条 worker 对应一颗逻辑核
          [j][j][j]   [j][j]      [j][j][j][j]   <- 每个 worker 自带一个 job 栈（LIFO）
              |
              |  job yield：依赖未就绪 -> 挪进 Waiting List，先去执行别的可执行任务
              v
        Waiting List --(依赖齐了再捡回来继续)--> 交回 worker 执行

        闲下来的 Worker#1 --(Job Stealing)--> 从忙着的 Worker#3 栈里偷几个 job
```

读这张图：任务不是直接塞给某条线程，而是全部交给 scheduler，由它按每条 worker 的饱和状态分发；每个 worker 独占一颗核、自带一个 LIFO 的 job 栈；被 yield 的任务挂进 waiting list 等依赖，闲下来的 worker 也不许闲着——去别人栈里偷活。

这里首先有一个全局的调度系统，叫 job scheduler。你的 job 其实并不是直接递给 working thread 的：job scheduler 会根据每一条 working thread 的饱和状态，把这些任务扔进去。

这和 fork-join 模型有一个本质的不同。fork-join 那个模型，实际上还是单线程的：只是跑到一段之后，突然生成了一大批类似的任务，你们做完之后再合到一起——它并不是真正的全面并行化模型。而真正的全面并行化模型一定是这样的一个系统：我有个 scheduler，所有硬件的计算资源对我来讲只是 resource、都是我的 worker，然后由我来决定——你这个任务大一点，就把你扔到这儿，你就做得长一点；你任务小一点，我就给你多塞几个小任务——我尽量保证大家的任务基本是均衡的。

#### 后进先出：一个反直觉的选择

这里面就有一个非常有意思的问题：worker 面前有一摞任务，是先扔进去的先执行——像一个队列，first in first out——还是最后扔进去的任务先执行？last in first out，这是个堆栈。我相信所有的同学天然的理解都是：那肯定是 first in first out 嘛，先来的任务先做完，后续的才能做嘛。

诶，做游戏引擎 job system 的时候要注意一点：在游戏引擎的工程实践中，我们实现 job system 的时候，一般——我只能讲一般，这个东西不一定，也许我讲的是不对的——会用 last in first out。

为什么？因为在游戏引擎中，很多 job 的产生方式是这样的：前一个 job 做到一半，突然发现要产生四五个不同的 job；而这个 job 在执行到一半的时候，又会产生新的 job——它们彼此之间是 dependency 关系。那就意味着：我 fork 出来的这些任务如果不去完成的话，我自身是完成不了的。所以它的实施方法其实是 last in first out，像个堆栈一样。这个很有意思，也是实际动手做的时候特别容易犯的一个错误。

> **易错点**：调度次序直觉上选"先来先做"（FIFO），工程上却常常该用"后进先出"（LIFO）。fork 出来的子任务不完成，父任务就收不了口——让最新产生的子任务先上，才能把依赖链一路做穿。

#### yield 与 waiting list：让 CPU 不空转

job 的执行是按 dependency 走的。如果执行中发现我的 job 被 yield 掉了，我们就会把 yield 掉的任务全扔到一个 waiting list 里面去——这个事情谁干？scheduler 干。

所以在 working thread 里，你的任务塞进去了，并不是永久占着这条线程的：我会依次执行；一旦发现你被 yield 了，就把你"框"一扔，去执行下一个可以执行的任务。想象一下，这样是不是就可以把 CPU 尽可能地利用起来？——你要等着你的那些 dependency 执行完之后，你才回得来、才能执行得了，那就先把位置让出来，别占着坑空转。

### Job Stealing：闲不住的工人去偷活

还有一个很重要的东西，叫 job stealing。

working thread 里堆了很多 job。但实际上，无论你的 scheduler 做得再好，你并不能估计一个任务要跑多久。因为有两种情况：第一种，这个任务的运算太复杂了——你看它是一个函数壳，但里面给我算了一堆很神奇的计算，那我等半天也等不了；有的时候我的 job 是要等 IO 的，这很疯狂，等 IO 能等很久。第二种，任务本身不复杂，但它在执行过程中产生了一堆 dependency，或者它天然就有很多 dependency。

也就是说，给你 100 件任务，scheduler 是没有办法 estimate 每个任务要执行多久的。所以一定会出现：有些 worker 的活已经做完了，有些 worker 还剩下很多活没做完。那怎么办？worker 会很聪明地把那些没做完的 worker 里面的任务偷过来，放到空闲的 worker 里面——这就是 job stealing。

仔细看，这个想法其实非常简单。整个 job system 就像工厂里有一个经理，时刻看着每个工人手上的活：这些任务相对独立，但彼此又有依赖——比如我们造一双鞋，有人刷鞋底、有人做鞋面、有人穿鞋带，还有皮鞋、凉鞋一起做。这么多任务、这么多部件塞过来的时候，这个经理就会不停地把任务堆到这些人前面，不停地观察工人的状态，尽量保证每个人手上都有活干；而且他用 last in first out 的方法，尽可能保证前导工序做完之后，再去完成后面的工序。

job system 说起来是一个很高大上的概念，实现起来其实还是蛮复杂的，特别是对游戏这种 case 来讲。但它最核心的思想就是这些：更彻底地用并行化编程、多线程的思想，充分利用所有的 CPU 资源。

> **结论**：job system 的全部精髓——scheduler 按饱和度分发、LIFO 保依赖、yield 挂 waiting list、闲了去偷活——目标只有一个：让每一颗核在每一刻都有活干。

我个人认为，未来随着计算机的核越来越多——x86 架构里八核、十六核、三十二核是一定会发生的事情；ARM base 的芯片核也会越来越多，为什么？因为我们不能做得太快，要降低功耗——job system 真的会是未来一种很重要的实施方式。

### Job System 好在哪，难在哪

job system 是一个非常好的系统：它非常容易实现任务的 schedule，也很容易处理任务之间的 dependency。不像刚才讲的 task graph，你要很傻地在程序启动之前不断地定义这些 task、定义它的 dependency——那个东西你写写就知道，很难受。

但 task graph 也不是没用：现在很多引擎或者平台里面，一些大模块之间的 dependency，还真得用那种方法定义下来。但当我在一帧里面产生几百个、上千个、上万个 dependency 的时候，实际上只有 job system 才能非常高效地解决这个问题。

而且每一个 job 的堆栈都是独立的，彼此之间不会干扰。再加上它是基于 coroutine 的架构，每条 working thread 独占一颗核，所以它不存在 context switching——只要不触发硬件的中断，它的效率就会非常高。

那它的挑战是什么？首先，C++ 语言 natively 并不支持 fiber，你得自己实现一套 coroutine 机制。刚才讲了，实在不行用 Boost；如果你嫌 Boost 特别大，把 Boost 里面的代码抠出来，其实也是可以的。只是它在不同的目标平台上，实现的方法不一样。

另外一个挑战是：这样的系统真正实现起来，挑战还是非常大的，特别是你去实现 job system 底层的时候。因为它的特点是：对上面的这些 coroutine 业务逻辑的开发者来讲，底下全部是透明的、你看不见的——你觉得好像我的任务扔进去了，我在中间 fork 一个 job，job 就出来了，任务数据结果就拿到了，很开心，这个任务你就可劲地写。写完跑起来，profiler 一看——诶，这东西像小砖头一样垒得整整齐齐的。job system 跑出来的 profile 特别满足强迫症患者，比如我就是个强迫症患者，你会发现 CPU 看着特别整齐，很开心，有种拼花拼图的快感。

但是，你真的要实现一个这么鲁棒和稳健的 job system，要求你对多线程硬件的底层开发非常了解。

### ABA 问题：最难缠的 bug 长什么样

多线程硬件开发中会产生很多 data racing 的挑战，有时会产生一些非常难被发现、非常难 debug 的问题。举个例子。

我们内存中分配了一段空间。一条线程说：这个空间我认为无效了，我要把它释放掉。过段时间，这条线程要检测一下这个释放是否成功——靠读那个位置的值来判断：如果数据没被释放掉，我就继续走我的逻辑。但就在这中间，另外一条线程发现这段内存空了，它又产生了一个新的分配任务。heap——就是系统管内存分配的那个堆——分配内存的时候，把同一段内存地址又重用了，而且好死不死，它在那个地方放的数值又是一模一样的。等到后面的逻辑在检查这个数据的时候，它发现数据"没有变化"，于是完全没检测到这块内存其实已经被换过一茬了。

这个 case 叫什么？我们叫做 ABA case。就是你在一个线程里，前面一段代码对数据做了修改，后面再去检测的时候发现它没变——没变，你的逻辑就往另一个方向走了；但实际上在这两次之间，另外一个线程已经把这个数据改过去一遍、又改了回来。

这种 bug 的特点是：你基本上可能跑几天几夜，然后系统突然异常、挂掉了；而且你几乎没有办法复现它——因为内存分配是很随机的过程，它还得随机到"那个地方的数据恰巧又被写回原来的状态"。于是你很多的检测函数全部无效。

> **提示**：ABA 的名字就是它的过程——值从 A 变成 B、又变回 A。只比对值相等与否的检测在这种场景下会全部失效，这也是并行底层系统最经典的陷阱之一。

### 给底层实现者的几句告诫

当我们真的去实现一个对上层开发者来讲简单好用的 job system 时，在底层写它的人，一定要非常小心谨慎地把 parallel programming 可能出现的所有异常 case 都防范掉。

不然会怎样？说说我们最怕的问题。如果一个 bug 百分之百当场 crash——这种 bug 我们其实很开心：QA 报上来说这东西 crash 了，我问第一个问题：这东西能不能复现？答：能复现。复现率多少？百分之百。那我就很开心了：你们不要怕这个问题，我们一定能修得好。但如果他告诉我：我们这个服务器开服了三天之后，有概率突然就挂掉了——哇，遇到这种问题我们就很惨，真的很害怕。

所以做并行化开发、实现 job system 的时候，大家一定要注意：千万、千万要把你的理论功底、基本功练得足够扎实，然后才开始去搭这些底层系统。否则你很容易搭出一个看上去很酷的东西，但当丰富、复杂的业务逻辑压进来之后，你会在各种很奇怪的地方挂掉。

对这种 parallel programming 的底层核心系统，我会建议大家多做形式化的推导——从理论上证明这个东西是安全的，而不是完全基于自己的经验看它是不是合理。另外一个，多去网上查一些资料：国外有很多开发者社区，很多程序员总结了很多 pattern——当你并行化的时候，在这里会遇到什么问题，人家都踩过一遍了。

这节课讲的是高级课，讲怎么去实现一个彻头彻尾并行化的游戏引擎，用 job system 听上去很高大上，我也想去做。但当大家真的去做这件事情的时候——这里面你很可能吭哧吭哧搞了半年，然后整个系统挂得四处漏风。这，就是这个事情的挑战。

## 面向数据编程（DOP）与 ECS：现代引擎的高性能内核
> 对应块：BLK49 | 覆盖分集：P28 | 块标题（分集名）：《第二十节(下)：现代游戏引擎架构：面向数据编程与》

接下来这一讲，轮到大家都特别喜欢、听上去就高大上的 DOP——面向数据编程（Data-Oriented Programming）。不过正式开讲之前，我先带你们快速过一遍各种各样的编程范式（programming paradigm）：面向过程的编程、面向对象的编程……OOP 我相信是所有同学学得最多的。其实做游戏引擎的时候，各种编程范式我们都会用。这也是我后来进到游戏引擎这个行业才真正意识到的一件事：我总觉得自己写代码还不错，凭一点小聪明就够用了；但当你面对游戏引擎这么复杂的一个系统，你会发现不读书是不行的——真的要读书，要学各种各样的编程模式，也就是 design pattern。以前有本书特别好玩，封面上是个戴眼镜的女孩盯着你看，专教各种 pattern：listener 啊、publisher-subscriber 啊，都在里面。

对游戏引擎来讲，选哪种范式是一开始就要想清楚的问题。早期引擎简单，做一个小乌龟吃豆子的游戏，面向过程就够了：一个函数，各种情况进来，数据做各种处理，各种输入和输出，非常简单。但一旦讲到现代游戏引擎，大家会很自然地想起前面讲过的 component 系统：万物皆 GO，一个 GameObject 可以组合派生出 vehicle、飞机、武器、人，什么都可以。这个思想就是面向对象编程（Object-Oriented Programming，OOP）。这个思想非常了不起——从它诞生至今，它极其符合我们人类对这个世界的认知，写起代码来你会觉得很舒服。

那 OOP 是不是完美的呢？今天我就要开始黑它了。为了抬出我们今天的主角 DOP，先狂黑一波我们的老朋友 OOP。

### 先把老朋友"黑"一遍：OOP 在大型系统里的老毛病

OOP 的第一个问题：它虽然理论上让你觉得很舒服，但有很多的两义性。

#### 动作到底挂在谁身上

举个例子。一个怪物（一条龙）是一个 actor，一个人也是 actor，它们都是 GO。现在"人去攻击怪物"这件事——这个动作到底写在哪边？是写在攻击者这边：我发起 attack，我去 apply damage to，把 target 的 actor 或 GO 传进去？还是写在受害者那边：我被击中了（been damaged），谁来打了我、给我造成多少伤害？

你会发现，虽然面向对象看起来把数据组织得非常清楚，但"操作"这东西在 OOP 里就是一个 function——大家想象一门面向对象的语言，一个类下面有很多变量、很多 function，function 就是动作。这个动作到底挂在攻击者身上，还是受益者身上？这是有两义性的。而且不同的程序员有不同的写法：你真的打开一个商业级游戏的逻辑代码，那么多程序员一起写，你会发现有的程序员就喜欢从攻击者的角度写，有的程序员就喜欢从数据的角度写——this is real，真的就是这样。这时候你就很蛋疼了：代码一致性强迫症患者彻底受不了。

#### 深不见底的继承树

第二个问题：OOP 实际上是一棵非常深的继承树。假设我要对一个东西造成魔法伤害——这个"魔法伤害"到底在哪一层实现？是在 base class、GameObject 那一层做的？还是在 Actor 层，所有 actor 都能受到魔法伤害？还是在 Monster 层，所有 monster 都能受到魔法伤害？还是派生出会飞的、能变身的 monster，在那里面实现？

大家想想看：当你面对几百万行的真实游戏引擎代码，产生了一个需求，想知道这个功能到底是在哪个函数里实现的，你要在这棵深不见底的继承树里一层层去找——这是非常头疼的一件事。

而且就像前面说的，它有很强的两义性：有的人觉得这是个通用需求，要写进基类，"放基类才是有道理的"；有的人觉得不行，这个太特别了，得写进派生类。结果派生到最后发现这东西又是共用的，怎么办？把函数又移回基类去。写 OOP 的同学都知道，这是我们的日常：我们经常在"这到底属于基础服务还是特殊服务"这个问题上纠结很久——这也是程序员之间的日常对话。

#### 基类变成"全家桶"

第三个问题：base class 会做得非常繁复。讲个案例——就不点名了，某引擎的 Actor 基类，大家有时间可以研究一下：我的天呐，这个 actor 里面放了无数的功能，连 debug 这种功能都放在里面。我第一次看到这段代码的时候，就是一句"我的天呐"。但你仔细想想，如果我们在做一个真正的商业级游戏引擎，你会发现你还真是这样的——里面就是会放很多很多功能。

于是问题来了：当我去写一个很小的功能、派生一个 actor 的时候，我本来只需要这么几个功能，结果你给了我一个全家桶。大家想想，这是不是商业销售的经典套路？在我们程序员的开发里，有时候也会干这样的事。所以基类的肮脏臃肿，是 OO 做大型系统做到后期大概率会发生的问题。想切身体会的话，打开任何一个商业引擎的源代码，你就知道我在讲什么了。

#### 性能：内存东一块西一块

第四个问题，也是最要命的：性能其实很低。为什么？OOP 非常符合我们人对数据的直觉理解，但代价是这些数据全部分散到各个 object 里；而且对象通过派生继承，数据全是异构的；每个对象的 allocate、deallocate 都是分散进行的。所以你把一个 OO 系统的内存抓下来看，真的就是东一块西一块、东一块西一块。大家想想，CPU 拿到这样的内存布局怎么处理？很疯狂，很难受，对不对。

还不止数据。OO 里的类有派生、继承，很多函数会被重载，还有虚函数——虚函数是什么？全是指针。所以代码在内存里也是跳来跳去的：本来这段执行代码在一个地方，执行到某一句，突然跳到另一个地方去执行另一个函数了。所以 OO 系统你用 profile 工具去看，它的 profiling 是非常丑的：那边有一张性能图，不管你懂不懂高性能开发，看到那张图你基本就能得出结论——这个系统的性能做得不好，非常不稳定。

#### 单元测试几乎没法写

最后一个问题，也是我觉得更难的问题：可测试性。想象一个非常复杂的系统，几百上千个模块，我要测其中某个业务逻辑——比如伤害结算这个逻辑对不对、有没有被人改坏，我要确保公式和最后的测试项全部通过。用 OO 写的系统，为了测这个伤害计算，你得把整个环境创建起来：把所有对象、所有东西全部拉起来，然后才能测中间那一个函数。

而现代软件工程里我们讲 unit test，最理想的情况是什么？你有一个庞大的 code base，代码可以一直改，但我有几十上百个 unit test，每个只去测一个特定模块的数据。OO 里对象一层套一层、一层套一层，你很难把面向对象世界里的一个元素单独提取出来，对它进行测试。所以面对一个非常重度的 OO 系统，unit test 的代码非常非常难写——这是 OO 传统上的大问题。

当然，克服这个问题不只有面向数据编程一条路，比如函数式编程也能解决，今天不展开。但为什么会有这么多不同的编程范式存在？跟这个有很深的关系——特别是在超大型的软件工程里。因为一个游戏引擎真正到达可用的规模，一般都是几百万行以上的代码，这时候对可测试性的要求非常高。

前面十几节课、差不多十九节课，我一直用 OOP 的思路给大家讲游戏引擎架构；今天为了卖我们的面向数据编程，就把 OO 狠狠黑了一遍。这叫什么？喜新厌旧。我们都是大猪蹄子，看见好东西就新人胜旧人——以前的小甜甜，现在叫牛夫人了。好，接下来就看看我们的小甜甜长什么样。

### 硬件现实：CPU 与内存差着数量级

我们的小甜甜叫 DOP，面向数据编程——这个名字听上去就非常高大上，确实也很高大上。那它的基础原理是什么？得从现代计算机发展的一个有趣特点讲起：我们的 processor 速度越来越快，但内存访问速度的增长跟不上 CPU 的速度。

你们可能觉得这跟前面讲的矛盾了——前面不是说过 CPU 的发展已经到瓶颈、必须走多核了吗？怎么现在又讲 CPU 把内存甩到后面去了？其实所有的东西都是相对的，没有办法。事实是：过去 20 年里，我们的 CPU 快了将近上千倍；但内存访问速度大概只提高了 10 倍左右，一个数量级。这两者之间的差距，已经拉开了两到三个数量级以上。

> **定义**：面向数据编程（DOP）的出发点就是这道鸿沟——CPU 与内存的速度差了两三个数量级，数据的摆放与访问方式，直接决定程序跑得快不快。

这道鸿沟直接导致了现代计算机里复杂的 cache（缓存）机制——讲渲染的时候已经给大家提过一次了；也正是它，催生了面向数据编程的思想。

#### 一座缓存金字塔

为了弥合这道鸿沟，现代计算机架构里做了分级缓存。你可以把它理解成一个水泵系统：CPU 在最上面，最靠近 CPU 的是 L1 cache，它是最快的 cache，体量也比较小；接下来是第二级 L2 cache，一般来讲十兆左右——我记得最早以前买电脑的时候，L2 只有 2 兆，现在大家动不动就能买到十兆的 L2——它的速度比 L1 大概慢一个数量级。那 L2 是不是直接跟内存打交道？其实不是，早前只有两层缓存，现在一般还会做 L3 cache，一般在十几兆到上百兆之间，比 L2 又慢一个数量级；然后才到主内存，内存又慢一个数量级。所以从 L1 一路到内存，依次差下来，累计是 1000 倍的差距。

```text
CPU <-> L1 Cache <-> L2 Cache <-> L3 Cache <-> 主内存
        最快、最小    约 10 MB    十几MB~上百MB   再慢一个数量级

L2 比 L1 慢一个数量级，L3 比 L2 慢一个数量级，内存再慢一个数量级；
从 L1 到主内存一路累计下来，大约是 1000 倍的差距。
```

读图：数据像水泵一样从内存一级级往上抽——内存抽到 L3，L3 抽到 L2，L2 抽到 L1，然后 CPU 才能对数据进行处理。那 CPU 处理时发现数据没有了怎么办？先问 L1；L1 说没有，问 L2，从 L2 调上来；L2 说"我也没有"，好，那 L3 调；L3 说"我也没有"，不好意思，那就只能从内存去拿了。这一路问完，一旦决定要从内存中调数据，基本上就是 1000 倍以上的成本，速度变得很慢。

所以今天我们做高性能编程，脑子里要一直有这张图——always keep in mind：你写的东西，对 cache 到底 friendly 还是不 friendly。

#### 数据要"扎堆"：locality 与 SIMD

这就引出写代码时非常讲究的一件事：数据要有 locality——数据总是紧紧地待在一起，处理的时候尽量一次性处理。这个概念是不是很熟悉？对的，因为讲渲染的时候我们说过：渲染要做得好，必须理解 GPU 是怎么工作的。GPU 里也有 cache，每一个计算单元也是要从各级 cache 里读数据的，数据之外还有显存这一层——所以它同样要求数据尽可能 local，这样 GPU 才能疯狂地跑起来。

那最简单的一个方法是什么？SIMD。现代 CPU 基本上全都实现了 SIMD：对四个 float 的加减乘除，你可以把它看成一个 vector4，一条指令全部做完；它一次性读四个内存空间，一次性写四个空间。所以我们打包（packing）数据的时候，要尽可能把它 pack 成 SIMD 友好的、比如 16 个字节这样的空间。

#### 缓存怎么"换血"：LRU 与随机扔

SIMD 够不够？其实还不够。cache 里的数据是有管理原则的：cache 一旦满了，就得扔东西。最简单的经典做法：最近一直在用的东西留住，把最久没有被用到的扔掉——这是一个非常简单也非常经典的调度算法（LRU）。

但实际上还有一种算法：随机扔掉。大家会觉得，你不是说"最近没用的扔掉"才合理吗，随机扔算什么？其实这是个概率问题。想象 cache 足够大，比如 1 兆，我每个 tick 随机扔掉 64 个或 128 个字节——相对于整个存储空间来讲，可能是千分之一左右。随机扔掉的基础是"这个数据没有被访问到"；从概率上去讨论，你会发现随机策略其实也符合我们的数学期望：谁最久没被用到，它就有最大的概率被扔掉。所以随机替换也是一种 cache 管理机制。

> **提示**：这也是为什么我们打包数据和代码时，要尽可能把会一起用的东西放到一起——无论 LRU 还是随机策略，都在奖励"扎堆"的数据。

#### 缓存行：一次 64 字节的读写

接下来要理解一个概念：cache line。CPU 从 L3 往 L2、从 L2 往 L1 搬数据，每次取的是一个 cache line，大概是 64 个字节，一行一行地读写。

讲起来有点抽象，举个例子：我们定义了一个 integer。当 CPU 对它进行计算时，它在最顶级的 L1 cache 里有一段内存，在 L2 里也有一段，L3 里也有一段，内存里也有一段——而且 CPU 要保证这三层 cache 和 memory 里的数据最终是一致的。这些读和写的操作，都是按 cache line 进行的：一次读 64 个字节；这些数据发生改变、必须写回主内存时，也是一次性地一级一级写下去。

#### 亲手就能测出来的差距：按行还是按列

cache line 机制会直接反映到你访问数据的顺序（order）上。同一个矩阵，假设数据是一行一行存储的，那你逐行去读它，效率可能比逐列去读高出几百倍甚至上千倍。为什么？当矩阵非常大的时候，它在内存里是连续存放的；你如果按列去遍历，虽然只是 y 坐标加了 1，但在 cache line 上可能已经跳过了很多次，每一次都要被迫从 memory 一层一层地往上搬数据——效率自然非常低。

所以我们对数据进行访问时，order 非常重要，要顺着数据的存储顺序来。这个事大家写代码的时候就能有感觉，有兴趣的话可以亲手测一下，差距非常直观。

### DOP 的核心：代码也是数据

明白了硬件现实，就可以讲面向数据编程的核心思想了。DOP 认为：游戏里所有发生的事情、所有事情的表达，都是数据；那代码呢？代码也是一段数据。我核心关注的点是什么？是把这一切在 CPU 里的 cache miss 降得越低越好。

注意，不只是数据会造成 cache miss，代码也会：这段代码执行完了，我要加载新的一段代码，新代码同样会导致 cache miss。我给大家看过一个 profile：时间消耗里将近 7% 是什么？是"这段代码执行完了，被迫再去弄一段新的代码"——7% 的性能损耗花在代码加载上。大家想象一下，这是不是远远高于我们的想象？我们一直觉得是数据访问慢、数据处理慢，其实代码本身也是高性能编程时要去思考的对象。

> **结论**：DOP 把数据和代码看成一个整体——它们在内存中可能是分开的，但在 cache 里要尽可能地待在一起：这段代码执行完，这批数据刚好处理完，然后 swap 下一批数据和代码进来。

打个比方，还是继续用鞋厂：我们希望做鞋的工人、他手上的工艺、要处理的原料全部放在一起，这样他一次性能处理完一批，再把工人和做好的鞋一起 swap 出去，换下一组工人和他们的活——效率就非常高。千万不要出现两种情况：第一种，这个工人只会做一道工序，做到一半，后面的工序需要另一个工人，你得从 memory 里把工人调出来，让这些数据干等；第二种，工人明明能把这些鞋处理完，但原料四散在各个地方，做到一半得跑去别的地方调原料。这两种情况，就是面向数据编程最核心想去避免的东西。

这样做的收益有多大？比传统 OO 快一到两个数量级是很正常的。大家听听这个数据：数据和代码安排好了，能快将近 100 倍——这真的不夸张。比如 Unity 做过一个测试，用它的 DOTS 系统做了同样的一个东西，大概能快到接近 100 倍以上。这就是为什么你的系统和代码必须这样去架构，才能有这样的能力。

### 高性能代码的三条纪律

知道了这些基础知识之后，真正动手写超高性能的代码，有几条纪律要遵守。

#### 别让两个线程踩同一条缓存行

第一条：做任务的时候，尽量避免任务之间的执行顺序依赖（order dependency）——前面讲任务系统的时候跟大家提过，尽可能让任务之间 order 无关。为什么这么重要？因为这里有个很重要的概念，叫 false sharing（伪共享）。

什么意思？两个函数——或者两个线程上的任务——在读写同一个变量：一个人在读，一个人在写，或者两个人同时在改。如果这个变量在内存里正好落在同一条 cache line 里（也就是正好在这 64 个字节里面），那对整个系统来说负载就特别大。为什么？你去读它，系统要保证这个数据一路同步到 L1 cache；你改了它，另外一个人去读，或者两个人同时写——整个同步和读取的过程要专门做两遍，才能让数据一致。

所以当我们写这种超高性能的系统时，要尽量避免两个线程同时读写同一条 cache line。这意味着：不要把很碎的数据同时交给两个线程去访问；基本上一个线程访问的数据就是自己的那一块，双方尽量不要有任何交集。

> **易错点**：你会觉得自己什么都没做错——两边写的地址明明不一样——但只要这两个地址落在同一条 cache line 的范围里，整个内存同步（swap）的成本就会高非常非常多。

#### 分支预测：CPU 在赌你的 if

第二条，是大家以前写代码时经常不注意的：我们会写 if-else，if something else something，写起来非常舒服、逻辑非常清楚。但现代 CPU 里有一个东西叫 branch prediction（分支预测）：它会预测你这个 branch 往哪边走。大家会觉得奇怪，你凭什么预测我接下来发生什么？但是没办法，CPU 为了追求极高的性能就是这么干的。实践中它发现：很多时候你 100 次进入这个判断，可能有 99 次甚至 100 次走的都是上面那个分支，可能第 101 次才会走到下一个。所以 branch prediction 在实践里是非常有效的手段：CPU 会提前把预测的那段分支代码——比如 100 行——加载到 L1 cache 里去，CPU 可以直接执行。

注意，这里又出现了 DOP 的一个核心概念：我们优化的不仅仅是数据，还有代码。

但问题来了：如果下一次进来执行的时候，条件突然不满足了——L1 里的这段代码就无效了，要被 swap 出去，然后我再去调 else 那 200 行代码进来。这一调，如果很不幸这段代码既不在 L2 cache、也不在 L3 cache，是一段冷代码、在 memory 里，那麻烦就大了，系统要等很久。

举个例子。一个很简单的函数：遍历数组，如果里面的数字大于某个阈值，就做第一种工作；不大于，就做第二种工作。数据是乱序的：前面走到 8 都没问题，一碰到超过阈值的元素（比如那个 11），预测就错了——CPU 说好，把下面 else 里的代码调进来；结果做着做着，又碰到一个小于阈值的数，怎么办？再把 if 那段代码也调进来。这样来回倒腾，系统的性能就会掉得非常低。大家可以做个测试：用非常随机的数据去跑比较复杂的 if-else 判断，你会发现性能非常非常低——就是因为 CPU 的 branch prediction 错了太多次。

那怎么办呢？答案你其实就能想到：先对数据排个序。排完序之后再看这个序列：只有在越过阈值的那一个点上需要切换一次，前面全是 if 的代码，后面全是 else 的代码。排序的时间不算的话，这个函数的性能就会高于前面那个。大家想想看，同样是逻辑的代码，实现方式不同，效率差别就会非常大。

而在真正更高性能的要求下，一般来讲我们会提前把数据分好：简单来说，尽可能避免复杂的 if-else——在创建每个数据的时候，就把它加到不同的数据容器里去；然后对一个容器，只做一种逻辑，保证整个处理逻辑的高度一致性。大家会觉得这件事真的那么重要吗？但如果你真的在写高性能代码、特别是高频执行的代码，你就会意识到它对性能的影响真的非常大。尤其是 branch prediction 失败的时候，哪怕你的数据就在 cache 里也没有用了——因为代码要去 swap，而代码 swap 有时又会导致数据失效，非常麻烦。所以非常鼓励大家：写高性能计算的时候，尽量减少 branch 运算。

#### 数据怎么摆：AoS 与 SoA

第三条：数据该怎么摆。前面讲过一些基础概念——面向对象的数据，会通过各种各样的引用、指针满天飞。特别是现在很多同学已经不太接触 C、C++ 这种底层语言，对一个对象在内存中到底是怎么放的，其实没有感觉：我们都把东西扔进各种容器，容器里什么功能都有，反射啊什么都有，特别特别方便——这些代码写起来确实真的很方便。但如果你要去写高性能的开发，你还真的需要理解汇编、C 语言这些底层的东西，arrange 你的 memory 的时候要非常讲究。

这里有两个很重要的概念：一个叫 array of structure（AoS），一个叫 structure of array（SoA）。听上去很高大上，其实想法非常简单。大家想象一下，用 OO 的思想去定义一个粒子（particle）：它所有的属性是一个 structure——position、velocity、color、age。那么 100 个 particle，最自然的内存排布是什么？第一个 particle 的 position、velocity、color、age，接下来第二个、第三个、第四个……这就叫 array of structure。

这时候问题来了：假如你写一个更新 position 的函数，你实际上要读的是它的 velocity 和 position——可你每处理一个 particle，都要跳过后面的 color 和 age。跳来跳去，你的 cache coherence 就不够好了。

而当我们需要进行超高速的数据处理时，很多时候是把数据摆成 structure of array：同一种数据，直接排成一条超长的数组来进行处理。

```text
AoS（每个元素是一个完整的结构体）：
  [p1: pos|vel|color|age] [p2: pos|vel|color|age] [p3: pos|vel|color|age] ...
         ^ 更新 position 时要用 vel，却每次都得跨过 color 和 age

SoA（同一种属性排成一条长数组）：
  pos:   [p1][p2][p3][p4] ...   <- 要一起算的字段紧挨着，一口气刷完
  vel:   [p1][p2][p3][p4] ...
  color: [p1][p2][p3][p4] ...
  age:   [p1][p2][p3][p4] ...
```

读图：AoS 里每前进一步都要跨过不需要的字段；SoA 把要一起处理的数据排在一起，一条 cache line 拉进来的全是有效数据。

这个思想其实有一个特别类似的参照物：compute shader。大家理解一下，为什么同样一个运算，上了 GPU、上了显卡就变得非常快？因为显卡骨子里就是一个以数据为驱动的编程模型：每一个 shader 你可以理解成一个函数，而数据非常紧致地排在一起。所以当我们去 arrange 数据的时候，想追求高性能，一般就按 SoA 的方法去排所有的数据。

### ECS：把零散概念串成一个架构

如果大家懂得了上面这些概念，就进入了大名鼎鼎的 ECS 系统——Entity-Component-System。对游戏引擎感兴趣的同学，对这几个概念应该耳熟能详。

在展开之前，我先道个歉：说实话，这节课讲的东西比较晦涩，要求你有一定的开发基础，而且概念非常多，概念之间的关联又不像大家想的那么紧密，很难做到一环套一环。为什么？因为 ECS 实际上就是把前面那么多零散的概念，最后串在一起之后，大家提出来的一个架构。

我们最开始构建游戏引擎的时候，会天然地想到前面讲过的 component-based 系统：用组件搭出一个我们想要的东西。而最自然的实现方式，就是用 OO 的方式——构建很多对象，一层层派生继承。显然，这样的代码分散在各个类里，虚函数指针一塌糊涂，数据也非常分散，执行效率非常低。尝试过用 OO 方法实现 component-based 系统的同学应该有体会：当你的 entity 里的 component 多起来、GameObject 多起来，每一帧去 tick 它，你会发现性能比你想象的慢很多很多。有时候你都很郁闷：我其实没做什么特别复杂的运算，为什么我的系统性能这么慢？

其实，如果你听懂了前面讲的 CPU、内存、cache 是怎么协作的，你就知道：很多时候我们都浪费在非常无效的等待上——CPU 等指令加载、等数据加载：执行到一半发现数据没有了，去找数据；数据算到一半，发现要调另外一个函数，这个函数是个虚指针，要去找它的实现；找到之后，又要再把那段代码加载进来……就这样来回倒腾，搞得一塌糊涂。

你可以认为这就像一个工厂没有人管理：所有的师傅凭自己的感觉干活，缺原料了就去库房拿原料；我只会做鞋底，他会做鞋面，我就把鞋底递给做鞋面的师傅，大家各干各的——整个任务的调度完全无序。这就是 component-based 加上 OO 导致的一个很大的问题。ECS 系统，就是想彻底解决这个问题。

#### Entity：轻到只剩一个 ID

ECS 的核心想法，第一条：对我们所有的 GO——在 ECS 里我们叫它 entity——在以前的 component-based 系统里，它是一个类，这个类里面可以装很多 component；而在 ECS 里，entity 非常非常轻量：它就是一个 ID，这个 ID 指向了一组 component。

#### Component：纯数据，不许有逻辑

第二条，组件。ECS 里的 component 指的就是一块数据：比如一份位移数据、一份速度数据。而这个 component 没有任何业务逻辑。

> **易错点**：这一点和前面讲的 component-based 系统特别容易弄混。以前我们讲的 component 有很多接口：什么 tick 啊、get property 啊、set property 啊，一堆函数；而 ECS 里的 component 是不允许有业务逻辑的——它就是纯数据，你可以对它读、对它写，但它本身并不知道自己的意义。

#### System：一类逻辑处理一类数据

第三条，是一个更抽象的概念：system。system 来对这些 component 进行处理。比如我有一个 MovingSystem，它会根据你的速度去改你的 position；我有一个 HealthSystem，它会根据你受到的 damage 去调整你的 health 值。等等等等。

所以 ECS 实际上做了两件事：把数据全部打平，把数据从它的 owner——以前的一个个 GO——全部剥出来，每一类数据集中在一起存储；每个 entity 只是用一种非常离散的关系关联起来："我用了多少号的 transform，我用了多少号的 velocity"。而对数据的处理，交给 system。

这里有个概念大家一定要弄清楚：system 对 component 的处理，并不是一次只处理一个 component——以前在 GO 的体系里，component 很多时候是对自己的 member 数据进行处理；而现在，因为我们把单位拆得非常非常细，system 很多时候会同时处理好几类 component 的数据。

ECS 就是大家提出的这样一个理论框架：认为用这种模型构建的系统，能够充分利用数据的 cache coherence，充分压榨面向数据编程的性能。而且你可以发现，system 的操作是非常简单的，很容易把 system 的计算分散到很多很多核上去——这也是 ECS 系统一个很大的优势。

大家听上去是不是有点晕了？很抽象，对不对。确实，这些概念是有点抽象。但你会发现，它在实际中真的很有用。

### Unity DOTS：一套落地的 ECS

要把这套抽象概念真正讲明白，最好的办法是看一个实际的应用。备课的时候我想到了一个帮手：把大名鼎鼎的 Unity 的 DOTS 系统搬出来。Unity 提出了 DOTS——好像现在他们已经决定放弃了，但没关系，不妨碍我们拿它来分析 ECS 系统的整个应用。

Unity 自己讲，它的 DOTS 系统有三根支柱：

```text
+------------------------------------------------------------------+
|                           Unity DOTS                             |
+--------------------+----------------------+----------------------+
|        ECS         |    C# Job System     |    Burst Compiler    |
|  面向数据重新组织   |  把 System 并行化     |  把 C# 编译成 native |
|  整个引擎的计算框架 |                      |                      |
+--------------------+----------------------+----------------------+
```

读图：ECS 负责数据的组织，Job System 负责把处理并行化，Burst 负责把代码变成机器真正喜欢的形态——三者共同工作，才撑起 DOTS 这套架构。

第一根支柱是 ECS：重新地、面向数据地去组织整个引擎的计算框架。第二根，一个基于 C# 的 job system——既然数据都变成了 component、处理都变成了 system，那就非常容易把它们并行化，于是做了一个非常简单的 job system。第三根很有意思：Burst Compiler——他们竟然重新做了一个编译器！待会儿我会解释，为什么他要干这件听起来很疯狂的事情。

#### Archetype 与 Chunk：内存怎么摆

Unity 的 ECS 也是把系统拆成无数个 component，但它在上面抽象了一个概念，叫 archetype——你可以叫它原型，或者泛型的概念。什么意思？比如我要做一个 NPC，它用到的 component 大概就那几个；我要做一个可以跟我战斗的怪物，monster 就是另一个 archetype，可能多一些攻击属性、伤害属性、行为属性；我再做一个载具（vehicle），又有它相应的一组 components。所以你可以认为：archetype 就是 type of GO——这一类 GO，就是一个 archetype。

为什么要做 archetype？你想，当游戏中有几百个上千个 entity 的时候，每个 entity 底下挂的 component 都是不一致的。那 system 在处理这些 entity 的时候，总不能一个一个地去问："你有没有这个 component？这个 component 我能不能用？"——这就很慢。有了 archetype，system 就知道哪些 entity 是我要处理的，处理的速度会变得很快，而且也方便别人去理解。

接下来是 Unity ECS 最经典的一张图：它首先把内存定义成了一个个的 chunk（块），然后把同一类 archetype 的所有 component，按照 component 的类型，一个个摆进 chunk 里。这样做的好处藏在一个细节里：一个 chunk 里面一定是同一类 archetype。那意味着当某个 system 认为这个 chunk 我需要处理的时候，我只要看这个 chunk 的 archetype：哦，这是一个 NPC 的 archetype，我现在要做一个对话的 system，NPC 这个 archetype 里有几个我需要的 component？一定有，那我就对它处理；而如果这是一批载具的 archetype，那这几十个载具我彻底不需要考虑——因为我没有跟你对话的需求。

一个 chunk 一般多大呢？早期的架构里一般设成 16KB——主要是考虑 cache line、考虑 L1/L2 cache 是怎么 swap 的。不过在现在的计算机上，这个 chunk 的大小好像变大了那么一丢丢：我看了一些最新的资料，我们团队上次看，我记得虚幻那边把它提到了 128KB 或者更大一点。具体数据大家可以去查——这是一个你可以调的量。

> **提示**：为什么 Unity 不把所有同类型的 component 全放在一起（比如所有 transform 放成一个超大数组）？第一，这些数据量会非常大，反而不符合 locality 的要求；它的本意，是让"这一段代码 + 它要处理的一小块数据"正好一起塞进 cache，处理完，再把下一个 system 和它对应的 chunk 换进来——这样处理效率才是最高的。这是 ECS 系统非常巧妙的一个地方，大家如果去写这类系统，我非常建议这么干。

有了这些，system 就变得非常简单了。比如我们现在做一个"往前移动、更新 position"的 system：我只要拿到你的 velocity component 和 translation component，做一次运算——运算完，这个 chunk 里所有物体的 translation component 都被更新了一遍。因为不管读还是写，它们都在一起，所以效率非常高。Unity 也说，ECS 系统的效率提升，就是前面讲的接近 100 倍。

#### 为什么非要自研一个编译器

现在可以回答那个问题了：为什么 Unity 要费那么大力气，自己写一个 Burst 编译器？

如果整个系统是用 C# 写的，那这些代码——你申请的一个 array、你定义的一个数据结构——在硬件上到底对应的是什么东西，完全是一个黑盒：它是跑在 C# 的虚拟机里的。大家想一下，在 C# 里定义一个变量，它根本就"不是一个变量"：真正存储的数据只是很小的一块，旁边还有一堆反射数据。

但是，如果你要写这种几乎和硬件一对一对抗的高性能代码，你最需要的是什么？是 native 的东西。所以在 Unity 的 ECS 里，你看着写的确实是 C#，但你定义 array 的时候，必须明确地用它要求的 native container——那实际上就很像 C 语言里真的分配了一块内存的裸指针。只有这样，它才能和内存里的数据一一地、连续地映射起来，你对它的数据访问才是可控的。否则，对于高级语言来说，它底下发生的事情基本上是不可控的。

而一旦变得这么 native，你就要加很多安全上的检查：写 C# 的时候，你不用去管内存的释放；但写这种代码，你就要花很多力气去考虑泄漏、无用资源这些问题。Unity 希望在编译器层面、在 job system 层面，确保所有该释放的资源都会被释放掉——其实这件事情非常非常困难。所以它必须写一个自己的 compiler：把你的这门"只借用了 C# 语法的语言"，编译成非常底层的语言，并且完成必要的检查。

所以我自己去理解 DOTS，觉得它做的是件蛮艰难的事情：它希望把复杂度全部藏在自己身上。对上层的业务开发者来讲，你不需要理解这么多复杂的 cache 机制，只需要按照它规定的 flow 去写 C#，就能实现想要的高性能。这里面有个细节：如果你想做 DOP 的开发，用 C# 的基础语法是很难写出来的——分配啊、释放啊，你根本不知道内存在什么地方，这些东西都变得非常抽象和复杂。用 Burst 编译之后，性能又提高了很多倍。所以这也是 DOTS 实现难度这么大的原因——说到底，这是 C# 这门语言天生的一个弊端。C# 是一个非常了不起的语言，我觉得它非常好；但在高性能开发、特别是 DOP 类型的开发上，它确实有这样的弊端。

### Unreal MASS：另一个范本

讲完 Unity，就不得不提另一个很厉害的引擎——虚幻引擎。最近因为备课，我们课程组兴致勃勃地把 UE5 最新的 MASS 系统整个研究了一遍。大家想想 UE5 最好的 demo 是什么？就是那个 Matrix 的 demo——《黑客帝国：觉醒》：中间的曼哈顿，有成千上万的汽车、行人。而 MASS 系统，实际上就是 UE 自己实现的一套类似 ECS、类似 job system 的东西。

这套系统怎么说呢，我觉得其实也没什么好单独讲的，它很像 Unity 的 DOTS——我甚至怀疑他们两个互相抄作业。到底谁抄谁，我就不去评论了。

#### 命名的学问：Fragment 与 Processor

MASS 里 entity 的概念和 DOTS 一样，也只是个 ID。但每个 ID 带一个 serial number——一个单独的、永远往上递增的数字——实际上就保证了这个 ID 永远不会被重用。这有点像之前讲作业的时候教过大家的 handle 机制：handle 里会有一个 salt，保证你的 ID 被重用时也不会串号。但要注意，串行号和 salt 是两个不一样的数字。这是个小细节。

我觉得 MASS 比较有意思的地方，是它给另外两个概念换了好名字。

component 在 MASS 里叫 fragment（碎片）。我觉得这个词取得特别好。为什么？想象一下你是写 Unreal MASS 的人：你会很头疼——UE 那边已经有一千多万行的代码，里面定义了无数的 component；你现在告诉我，因为你实现了 ECS 的 pattern，你这个数据也叫 component？此 component 非彼 component。而且我个人觉得 component 这个名字本来取得就不好：它会让人想起 COM 这些接口，天然让人以为这是"数据和服务绑在一起"的东西；但实际上在 ECS 架构里，component 就是 purely 的 data。所以 MASS 把它叫做 fragment——一小块内存的碎片、一小块数据——这个名字听上去就到位了。每个 entity 拥有一组这样类型的 fragment，叫起来也顺口。

system 在 MASS 里叫 processor（处理器）。既然把 component 改叫 fragment 了，system 这个名字怎么办？它也处理得非常好：我叫 processor——你给了我这么多数据放在这儿，我一个 processor 把你的数据全部处理完。很贴切。所以 MASS 里这两个命名，我个人是比较推崇的。

| 概念 | Unity DOTS | Unreal MASS |
| :------- | :---------------------- | :------------------------------------ |
| 实体 | Entity：一个轻量 ID | Entity：ID + 只增不减的串行号，永不重用 |
| 数据 | Component：纯数据 | Fragment：一小块数据碎片 |
| 逻辑 | System | Processor |
| 同类分组 | Archetype | Archetype |

#### Processor 的两步：Query 与 Execute

一个 processor 有两大核心功能。

第一大功能是 query（fragment query）：我要对哪些 entity 进行处理？我需要哪几类 fragment？对它们是读还是写？——它先用一段描述把这些说清楚，就像写数据库一样：我先定义一个 query，然后执行这次 query，就把所有的 entity 扫了一遍，把我需要的数据拿出来。那怎么扫呢？MASS 里同样用了 archetype 的概念；而且这种 query 是有缓存的——上一次 query 完之后，这一次如果没有变化，我基本上就不用动了。这样，所有我所需要的 archetype、entity、fragment 就全部拿到了。

第二大功能是 execute。大家去看它的 execute 代码，其实非常简单：因为 query 做完之后，所有需要的 fragment 都拿到了——注意，拿到的是引用，并不是真的把数据搬过来。为什么不需要搬？因为对每一类 archetype 而言，它的数据本来就集中存储在一个个 chunk 里。所以我处理的时候，一个 processor 处理完这个 chunk，切换到下一个，也是整个 chunk 整个 chunk 地切过去的。这样后面的处理就相对非常简单。

这套最底层机制的好处是什么？它能让我们在 UE5 里看到那么庞大的一个曼哈顿——成千上万的汽车、人物，其实就是用这套系统实现的。这也是 ECS 系统一个非常典型的应用案例。

### 实战者的忠告：别把整个引擎 ECS 化

说到这里，我想多说几句掏心窝的话。ECS 听上去非常高大上——很多同学一直想让我们讲 ECS，甚至说：小引擎里我们是不是也实现一个 ECS？好像我们的引擎用了 ECS、用了 DOP，就是一件非常了不起的事情。

但以我个人的理解：游戏是一个非常复杂的东西，它里面的很多业务 dependence 非常乱、非常复杂，几乎很难把整个引擎变成 ECS 的。这就是我一直在讲的：同学们学了这些前沿知识，很多时候会陷入一种理想主义的冲动——"我要搭一个彻底基于 DOP、彻底基于 ECS 的下一代游戏引擎"。这件事说起来非常高大上，但如果你真的做一个实战型的引擎，你会发现面临的问题和挑战绝对没有那么简单和抽象。

所以，ECS 对引擎来讲：在有些单点的地方，你就去用它，非常好；但不适合的地方，千万不要到处用——它会极大地增加你代码维护的复杂度，而且开发难度也非常大，因为它确实很抽象：很多人天然就很难理解"数据和业务分开了"这件事。而且你想，很多时候我们写一个业务逻辑，都是下意识地"问数据"：数据 A 怎么样、数据 B 怎么样、数据 C 怎么样，问自己、问别人一大堆，然后再说我的东西怎么办。大家如果写过真实的游戏逻辑就知道，90% 以上的逻辑都是这么写的。

所以 ECS 一般会用在非常确定的情况下。比如强如虚幻五，它的 ECS 也是放在了 MASS 这个非常特别的场景里，很彻底地用 ECS 架构做了一遍；而它的主体引擎，还是前面被我黑出翔的那个——面向对象的、component-based 的架构。

这里我给大家解释一下：虽然我今天把 OO 黑得一无是处，但实际上那只是为了烘托气氛，为了抬出我们今天的主角 DOP。在一个实战型的游戏引擎里，这两种架构是同等重要的——甚至坦白讲，OO 的重要性可能还要更大那么一点点，而基于 DOP 的 ECS，稍微小那么一点。

还有一个概念我想再 clarify 一下：fiber-based 的 job system 和 ECS 有关系，但没有那么直接。fiber-based job system 更多是一种 high level 的任务之间的调度；而 ECS 更像是在大量运算的时候，面向数据去组织我的计算。这两个之间有交集，但又不完全高度一致。所以并不是说我用了 ECS，就一定要实现 fiber-based 的 job system——其实你用 join 的 pattern，一样可以运行得很好。生成一个静态的 dependency graph，行不行？能做。而且如果我没记错，Unity 的 DOTS 和 UE 的 MASS，就不是一个完整的 fiber-based job system：实际上是基于 dependency graph 构建了任务的 fork——把任务 fork 出去，等它做完，再做下一件事。这个效果也非常好，没有任何问题。

所以还是那句话：做游戏引擎架构，千万不要执念，一定要实事求是——关键是在什么地方，把你的技术用对。

### 一张延迟账单：所有优化都对着它做

先跟大家道个歉。操作系统这门课，我大学的时候就没学好；后来工作了，因为需要还认真补了一下。但今天讲这门课的时候我发现，留给它的时间特别特别少。所以像多线程、像 mutex、像 atomic（原子操作）这些到底是怎么回事，今天没有深度展开。对多线程深感兴趣的同学，可以花时间自己钻研；把 job system 的核心思想理解了、把 parallel programming 的挑战在哪里理解了，就差不多了——DOP 真正去实现的时候，还是有很多细节需要注意的。

今天讲了这么多，我感觉内容特别散，零零散散的——我怎么总结今天做的所有事情？后来我想到了一张图。如果你理解了这张图，其实就理解了这节课讲的所有的东西：我们本质上讲的是高性能编程。前面课程里，我们更多学的是怎么去表达一个业务逻辑；但当你真的懂了怎么编程，当你面对一个像游戏引擎这样对性能如此 critical 的系统，你就被迫要去理解操作系统和硬件——CPU、memory、cache 是怎么协作的。

这张图大家如果有时间，可以一行一行看下去：一条 ALU 指令到底花多少时间；一次硬件级别的中断要花多少；一次线程的上下文切换（context switch）需要多少；C++ 里一次函数调用、一次虚函数调用、一次栈的切换，又要花多少代价。今天我们讲的几乎所有的解决方案，本质上就是对着这张图来优化的。

注意这张图里的差别不是线性的，是数量级的：十的零次方、一次方、二次方，一路到四次方、五次方——最高到一百万倍这个量级，挺吓人的，对不对？所以一个系统如果写得不好，同样的逻辑、同样的代码，真的慢 100 倍是很正常的。

> **提示**：如果你有志于做系统架构——我个人一直认为，我们并不缺 programmer，但我们非常缺 architect——这节课讲的东西非常值得你深入钻研。钻研的抓手，就是把这张图一行一行看明白：为什么这里快、为什么那里更慢。这张图看懂了，你再回过头看这门课前面讲的东西，自然而然就通了。这也是第一次让大家真的碰到引擎最内核的东西：如何实现超高性能的编程。

### 课后问答实录

下面是这节课后的几个提问，都很有代表性，我把回答也整理进来。

#### 自旋锁把 CPU 跑满怎么办

第一个问题就很硬核：自旋锁把 CPU 跑满了怎么办？我的天哪，这个问题实在太硬核了。我个人觉得，这可能是你的任务安排不太合理。一般 CPU 跑满之后，会触发一系列问题：线程堵在那儿，被迫 swap 出去。所以我们在很多时候要尽量避免把 CPU 全部跑满——跑满之后，很多进程、线程会拥塞在那里，很多行为会发生变化。说实话，我个人目前没有一个特别好的通用办法。我们自己的做法是：我们的 job system 会一直 monitoring 每一个核的占用情况，如果某个核的使用率超过阈值——比如 80% 到 90%——我们就不再给它塞任何 job：job 挂在那儿，但我不让它启动。用这种方式尽量避免跑满的情况。

#### 并行程序怎么 debug

第二个问题也很难：并行编程有没有比较好的 debug 方法？实话实说，我首先就不是一个非常好的并行编程开发者，因为这真的是非常难。很多时候我们是通过 log 去抓：看到一些数据出了问题，没办法，就疯狂打 log 去看。但 log 有个很大的问题：log 本身在很多系统里很慢——写文件的速度是很慢的——结果就导致时序发生变化，问题可能因此变形甚至消失。

举个我们自己的例子：我们做 fiber 系统的时候，会专门做一个功能——一键把 fiber 变成单线程，把所有的 job 按照 dependency 一次性依次执行。先用它确保业务逻辑基本没有错：如果单线程执行不会出问题，那我再去看是不是多线程出了问题，比如去猜测某些资源在竞争。

所以多线程编程的 debug 本身就非常难，这也是为什么我们会建议：做引擎的 parallel programming 时，让尽可能少的程序员接触到多线程，是一个正确的解法。团队里让几个技术最扎实、思维最缜密的同学，把原子操作、锁这些机制做完，做成一个底座；上层的程序员尽可能简单地开发逻辑，他能访问的数据、能调用的函数都约束好——最好上面的同学只写脚本就好了，不用关注底下真正发生的事情。这是现代游戏引擎被迫支持多线程之后，我建议的开发模式。当然，新一代的 VC 在这方面已经做得越来越好，能让你看到很多状态；但它最难的一点是：有时出了问题你根本断不下来——你都不知道该在哪个 thread 上断下来。我们自己的同学写 job system 的时候，前期遇到了大量非常难 debug 的问题，真的有一个问题出来，可能会花一两个星期才能找到。

#### 渲染线程和逻辑线程怎么同步

第三个问题：渲染线程和逻辑线程的同步怎么做？现在大家比较常见的方法是：逻辑线程算完了，把所有的值一股脑扔给渲染——一帧一帧地，逻辑线程形成一个逻辑上的 frame，交给渲染，渲染自己去做就好了。

这样做实际上就会导致我们经常讲到的那个问题：渲染线程总是比逻辑线程慢一帧——因为它要等逻辑全部算完之后，数据才能到渲染。目前大家也在探讨其他可能的架构来避免这个问题，但至少目前为止，一个成熟的商业引擎，很多时候还是被迫要让渲染等逻辑线程全部算完——否则数据会产生很多奇怪的二义性。当系统复杂到这个程度，我们必须给每一类任务一个清晰的分界线：就像前面讲的，如果你用固定线程法去划分游戏引擎的架构，那这一类任务就不能轻易地在渲染线程、逻辑线程、或者物理 simulation 线程之间来回跳——它们做的事情完全不一样，而且很多时候数据依赖关系就摆在那里。

顺着这个话题再强调一下 job system：它虽然听上去高大上，但在真实的游戏引擎里，你不太可能把整个引擎全部扔进 job system——可能只有 50% 到 60% 的 workload 可以扔进去做并行化；物理这些部分都要做一些特殊的处理，才能够真的跑得很好。所以讲理论是很简单的，但你真的面对一个引擎的实际情况，一般来讲你会对算法进行定制，为特殊的 scenario 做定制。

### 写在最后：太阳底下没有新鲜事

今天讲的东西确实是蛮硬核的。同学们千万不要好高骛远，先把引擎的基础东西做好。后面如果有时间，我们尝试在我们的小引擎里做一些小样，给大家感受一下——但这个 flag 不能立：小引擎现在已经有同学喊看不懂了，改完之后可能就更看不懂了，对吧。

最后，再次感谢我们的课程组——这里面大部分的工作都是团队做的，我作为"工具人"负责把这些知识传递给大家。课程组也分享了很多资料：比如 cache 系统到底是怎么 work 的；比如各种 blocking、non-blocking 的方法；比如在游戏引擎里怎么做 parallel framework；还有大家心心念念的 DOP、面向数据编程的一些文档，会告诉大家怎么去做研发。今天 reference 的阵容是比较大的，课程组这次准备得也是比较用力的——尤其如果你已经是从业者，这些文章很值得你去读。

特别要提醒一句：大家如果想写并行化的程序，千万不要土法炼钢。做研发，我一直有一个观点：太阳底下没有新鲜事。我们自己拍脑袋想出来的很多解决方法，别人可能在 10 年前、20 年前就已经遇到过无数次了；而且整个行业提炼和总结出来的这些 paradigm——这些范式，实际上已经是能被理论证明是成功的东西。去 follow 它，千万不要发明创造。这是做大型软件系统的时候，应该有的一个觉悟。
