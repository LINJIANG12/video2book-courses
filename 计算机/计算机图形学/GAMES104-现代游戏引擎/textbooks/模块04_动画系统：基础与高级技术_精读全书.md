## 让角色动起来：游戏动画的由来与蒙皮动画的地基
> 对应块：BLK15 | 覆盖分集：P09上 | 块标题（分集名）：《第八节(上)：游戏引擎的动画技术基础》

过完五一长假回来，躺了几天、胡吃海喝了几天，感觉胖了好多——估计大家也是"每逢过节胖三斤"。收收心：渲染这一大趴到这里终于告一段落，从今天起，我们进入游戏引擎的另一个大系统——动画。

今天的课件虽然比较长，但我个人觉得是整个课程里最好懂的部分之一，因为动画非常直观、也非常有意思，而且我会尝试把它最基础的原理给大家讲清楚。动画是游戏里最重要的系统之一，非常值得钻进去看看里面的门道。

### 从岩画到阿凡达：人类一直在琢磨"动"

为什么我们要做动画系统？因为人类在很早的时代，就对会动的东西非常感兴趣。我们观察到的自然界本身就是动的，可是最早的表达手段只有绘画。有意思的是，几万年前先辈在岩石上留下的画，动感就很足；先祖的陶器上，画的也是一连串人物的动态，而不是一个静止的姿势。那个时代没有投影技术，但我想先祖脑子里想的，就是一个动起来的世界——我们其实一直在探索把"动"表达出来的方法。

直到近代，人类发现了一个非常有意思的现象：视觉残留。

> **定义**：视觉残留——影像在我们眼里会残留大约 $1/24$ 秒。这是所有电影、电视、显示设备，包括游戏和游戏动画，最底层的理论支撑。

我们没有办法真的实现自然界那种连续不断、可以无限细分的动画系统，只能靠这 1/24 秒的残影去骗过眼睛。

早期有一个特别有意思的尝试，叫西洋景。在科学不发达的年代——我最近看了部电影，里面的牧师用的就是这种办法：点一支蜡烛之类的亮光源，让大家在很暗的地方看到一个会走动的小人投影。还包括小时候在纸上画的小人动画：我读书的时候，经常在每一本教科书上画一个故事，两个人打架怎么样了，翻起页来就动了——这是我小时候最爱玩的游戏之一。这些其实就是现代动画的基础。

那么动画的先驱是谁？可以这么认为：是电影行业。游戏动画的基础理论、基础工具，几乎全部来自电影行业——从最早的迪士尼 2D 动画，到七八十年代电影里开始把生成的虚像和实拍影像合在一起，到《侏罗纪公园》的时候，计算机动画技术已经到了一个非常高的高度：当年美国的电影院里看到那只怪兽的时候，所有人都非常震撼。再到《阿凡达》，又达到了一个更高的高度——我一直在讲，当年看到阿凡达，就觉得这确实是我们未来要努力的方向。今天我们在游戏里实现的很多动画效果，实际上就是在逼近当年离线渲染的效果。

这里还要提一部动画片，它号称是第一部完全用游戏引擎实时渲染出来的动画片。我觉得这代表了动画未来的方向：以前动画是个离线的东西，今天变成了实时的东西。

那这些动画技术，底层到底是什么？从最早的电影说起，其实非常简单：就是 2D 的、一帧一帧手绘出来。后来大家发现，可以用很多台摄像机拍摄演员的动作——演员身上贴很多 marker（标记点），通过光学的方法追踪这些点，就能把人物的动作恢复出来，这就是动作捕捉。前段时间我很喜欢的一部电影《阿丽塔：战斗天使》，人物表现得非常真实、非常自然，用的就是这样的动捕技术；相信大家在很多电影的幕后花絮里都见过它。这些技术，也是我们游戏动画的核心基础。

接下来就轮到游戏引擎了。今天这节课不是讲电影里的动画怎么做，是讲游戏里怎么做的——但必须 highlight 一下：我们动画的老祖宗，绝对还是电影行业。

### 游戏动画的童年：贴图、翻页与伪 3D

最早期的游戏动画非常简单，就是几张图片翻来翻去。这里面不得不提两个游戏。

一个是早年的《波斯王子》。仔细看里面的那个小人，动作看上去是不是特别灵活？实际上他是用一张张图片做出来的。那为什么动作看上去那么鲜活？当年做波斯王子的程序员，把自己的弟弟拍了一遍，让弟弟模仿游戏里所有的动作，再把照片上的人物动作一张一张抠下来，做成了游戏里的角色。所以在那个时代，波斯王子的动作非常自然——你看他一跳、挂在墙沿上的那个样子，是不是很自然？实际上，即便今天我们讲很高端的 3D 基于骨骼的动画技术，我们追求的这种自然感，还是来自于真实的人。而人类对这种自然真实感，是非常非常敏感的。

另一个是 Doom。这个游戏看上去是不是像一个 3D 游戏？但它完全是用 2D 动画实现的：你看到墙体等所有东西给你的空间感，实际上是通过图片的变形实现的；开枪、怪物被打倒，用的是一组照片——根据你当前的相机角度，贴上不同的贴片，让你以为真的在一个 3D 空间里旋转、绘制这个场景。这说明人类真的非常聪明，这也是我们游戏动画的鼻祖。说实话，我入行的时候就已经是 3D 时代了，备这节课的时候我才意识到，原来 Doom 是用 2D 的方法做出来的——那个时代居然能做得这么好，我也非常震惊。

再往后，我们进入 3D 时代，开始有显卡了。最早像《生化危机》，人物开始有动画了，但你会看到很多穿帮的地方——为什么会穿帮，待会儿讲骨骼的时候大家就明白了：它只是在动很硬的骨骼。到后来开始用蒙皮动画，动画就像真人一样自然一点了——不过以今天的眼光看，还是觉得土。再到《神秘海域》这种作品，就越来越真实细腻：既有物理仿真，又有非常自然的人物动画。这代表了现代游戏动画的高度，也是我们今天要着重讲的东西。

### 游戏动画为什么难：跟电影的三点不同

动画技术放到游戏引擎里，挑战和电影行业很不一样。电影做动画，很多时候你做好了，一帧一帧播放给观众就可以了。游戏不行，主要有三个挑战。

**第一个挑战：我们不能预设玩家的行为。** 玩家一开始走着走着，突然决定要跑；跑的时候看到前面有个障碍物，要去跳；跳起来之后觉得有个东西，要抓住。所以在游戏世界里，动画是要和很多 gameplay 去互动的：既要接受很多来自用户的输入，同时动画还受制于游戏的整个环境——比如跑到一半撞到一面墙，要表现一个被撞到的动画；或者走着走着，突然一个怪物把你抓起来、把你打倒。这些 gameplay 的东西、这些物理的反馈，怎么在动画系统里及时反应、表现得非常自然？这就是游戏动画系统相对于电影来讲挑战的地方。

**第二个挑战：一切都是实时的。** 从渲染那一趴开始我一直跟大家讲，游戏引擎里所有东西都是实时的——Everything is real time。无论你想出多复杂、多高端的算法，永远要在 $1/30$ 秒里把它烧完。而且记住：绘制、动画、游戏逻辑、物理、AI，每一个系统都要竞争这 1/30 秒、也就是 30ms 左右的窗口。但现代游戏又希望角色越做越新颖、场景越来越宏大，这给动画系统造成了巨大的挑战——挑战不仅仅是我们算不过来，还包括动画数据本身非常大：不停去取这些数据来计算，在内存里跳来跳去——还记得渲染那一趴讲的吗——性能是非常低的。所以我们今天会讲动画压缩，就是在解决这样的挑战。

**第三个挑战：对自然感和真实度的要求越来越高。** 动画师在做动画的时候，一般会预设你在一个无限延伸的平面上做反复循环的动作；但真实的游戏里，角色每时每刻都要接受来自用户的输入，动作就要变得非常自然。现在 3A 游戏里最火的 motion matching 技术，就是把很多很多动作融合在一起，让你看起来这个角色非常鲜活。角色还要跟环境进行各种符合物理规则的互动，我们叫 physics based animation。还有更难的：当相机推得足够近，我们就可以看到角色的脸——那时候我们就进入人类最敏感的东西，叫做表情。表情直到现在，在游戏里都是非常挑战的东西，你想做好质量非常难。大家对游戏引擎实现的效果逼近电影，已经越来越习惯；屏幕也越来越大，从 4K 到 8K，将来还有 VR——我们就希望有一个非常高保真（high fidelity）的虚拟人物站在面前。而讲虚拟人技术，最核心的就是它的动画技术。

### 这两节课的动画路线图

动画这两节课，我争取三个小时左右讲完，一节课一个半小时，把动画系统最核心的技术给大家过一遍。

第一趴就是今天：介绍一些非常基础的动画系统技术，上完这节课，你基本上能做一个带动画系统的简单游戏了。那从哪儿开讲呢？可能会让大家有点意外——我们首先讲 2D 动画技术。为什么？因为这节课讲的是游戏引擎，大家不要认为今天的游戏全是 3D 的：这个星球上最 popular、最赚钱的游戏，其实很多是 2D 游戏，2D 动画技术也是非常重要的技术。接下来讲 3D 动画技术；其中会辟出一个专门的章节，讲蒙皮动画的真正实施细节。为什么？因为提到 3D 动画，核心就是蒙皮动画——游戏里见得最多的角色动画。蒙皮动画的原理讲起来非常简单，但当你钻下去、真的开始写一个游戏引擎而不是简单地调用引擎的时候，会发现里面有很多基础理论、基础数学的问题。动画就是这样：很多时候你认为自己懂了，但写的时候，如果基础知识掌握得不够扎实，可以写出很多 bug 出来。第四部分讲动画数据的处理，讲一个非常简单但又非常实用的东西：动画数据是如何压缩的——今天你要写游戏引擎，动画数据是一定要压缩的，否则会有很多问题。最后介绍整个动画真正生产的 pipeline。因为写游戏引擎的时候，你不只是写引擎里的那些东西，大概率还要写很多 3ds Max、Maya 的插件，帮助艺术家把动画导成你自己的引擎能接受的格式——这就要求你对艺术家整个动画素材和数据生产的流程有所了解。基本上听完今天第一节课，你就能做一套完整的动画 pipeline 了。

第二节课讲相对高端一点的东西——其实也不算多 fancy，应该属于现代游戏引擎的标配：动画到底是怎么 blending 的，也就是根据游戏的操作逻辑进行各种合理的混合；IK 技术，让动画和环境进行互动；整个复杂的 animation pipeline；还有大家喜闻乐见的动画图（animation graph）——它的设计原理、有哪些节点、怎么运作。最后讲两个比较有意思的东西：一个是面部动画（facial animation）——你们会发现，面部动画和普通的形体动画是两套技术体系、两套完全不同的方法论；另一个是 animation retargeting——我做好了 A 角色的动画，把它的形体变一变：本来是一个人在走路，能不能把它转移到大怪兽的走路上面？这些技术比第一节课讲的难一点，但如果你想做一个 3A 级的游戏引擎，这些也属于入门级的技术体系。至于 motion matching 这种比较前沿的东西，争取整个课程上完之后，在高级课里跟大家讲。

如果你将来想成为游戏动画师，或者 gameplay 的 designer、gameplay 的 programmer，或者想做动画方面的专家，这两节课的内容跟你的相关度会非常高。

### 2D 动画：从精灵到 Live2D

2D 动画，事实上是我们整个游戏引擎动画的鼻祖。

#### 精灵动画：一帧帧图片循环播

最标准的就是精灵动画（sprite animation）。想法非常简单：把游戏角色的整个动作一帧一帧全部记下来，然后在游戏里循环播放——是不是就是一个很完美的 2D 动画？我们童年的回忆其实全是这样的 2D 动画。不知道大家有没有玩过某个游戏主机——任天堂啊、小霸王啊，暴露年龄系列对吧。不知道在座的同学里有多少人见过小霸王的机器，那上面的游戏，全是用这种 2D 动画技术做出来的。

这里面特别要讲《超级马里奥》。我记得第一节课就聊过：那个时代做游戏的人，根本不需要游戏引擎，他们真的非常聪明。比如那只小蘑菇，当它动起来的时候，它实际上就是一张图——把这张图 flipping 左右左右翻转着播放，你就感觉一个小家伙瞪着眼睛向你走过来。那个年代资源很少，大家做东西非常有想象力。

而 Doom 在这条路上又前进了一步：为了表现角色更生动、让你觉得像个 3D 空间里的真实角色，它在各个视角都采了一系列动作，然后根据你的相机位置，播放不同的 sprite 动画，给你一种很虚拟的 3D 感觉。

这些技术虽然很古老，但在现代游戏引擎里并没有被淘汰掉——就算在很高端的纯 3D 游戏引擎里。比如粒子系统（particle system，后面有专门的课讲）：大家看到的烟和爆炸，爆炸出来的每个粒子不是一张静态的图，而是一个序列帧——你可以看到一个烟球慢慢扩散开来的效果。序列帧这套东西，在特效系统里应用非常广泛。

#### Live2D：简单技术做到的"王道"

接下来是大家经常"氪金"的那种游戏——动不动先充个 648 的——用的更高端的 2D 动画技术：Live2D。这真的是个非常了不起的系统，我个人非常喜欢这个技术体系：非常简单，但给艺术家的空间特别大。你看二次元角色那么鲜活，就是用一系列图片通过变形、通过编辑做出来的。如果同学们想做卡牌游戏、想做二次元游戏，又觉得预算有限、时间有限，这一趴就是你们最关注的东西。

Live2D 的想法非常简单。第一，把角色上面的所有元素——她的头发、她的眼睛、她的眉毛——变成一个个小图源，把这些图片拼在一起，变成一个大资源放进去。第二，里面每个图源，通过旋转、放缩，还有 warping（变形）来编辑。warping 简单来讲，就是你给它套一个框架，你对框架做各种拉伸的时候，框架里每一个小三角形或者四边形，会做一次仿射变换——通过这种变化，各种元素的效果就做出来了，让你觉得很鲜活。

具体到做角色，它会把所有图源设置成各种深度：深度定义了图源出现的先后与彼此的层次关系，动起来的时候互相不会乱、不会穿插。然后，把每一个图片元素生成一个控制网格，在网格上你可以随意加控制点；移动那些点，图源就跟着变。这个非常聪明：比如一个角色开心不开心，眉毛一会儿皱、一会儿弯下来笑，用这种简单的技术就能实现——二次元这种表达本身，就已经非常具有表达力。

那怎么 K 一个动画呢？这么多图源，先 K 第一个 key frame：这一帧角色眼睛还睁着；下一帧眼睛闭上了，头再动一下；再下一帧，摇摇头。把这几帧串起来，key frame 中间一帧一帧插过去，一个非常鲜活的角色就出来了。这就是 Live2D 的原理。

这个工具非常符合艺术家的直觉，而且它是少有的、不用理解什么 3D、变换、三角形、投影、矩阵这些复杂数学，就能做出很棒游戏的体系。Unity、Unreal，包括我们自己的引擎，都会全面支持 Live2D——它做得太好了，我觉得真的没有必要再做一遍。我还是非常敬佩：这个星球上最厉害的游戏，其实是 2D 游戏，不是 3D 游戏。3D 游戏很多时候是技术上非常复杂、做得非常真实；但从游戏性上来讲，2D 游戏真的是王道。所以做引擎的时候，2D 游戏引擎也是一个很值得大家关注的方向——有些很前沿的游戏引擎，2D 这一块做得非常好，我们也看到一些非常优秀的作品，里面其实有很多很有意思的技术。

好，我们今天课程的主体，还是要回归 GAMES104 的核心主题：做一个 3D 的、像阿凡达、像很棒的 3A 级游戏那样的引擎。所以重点要放回 3D 动画技术。

### 3D 动画技术一览：先搞懂自由度

如果你的游戏是个 3D 游戏，会用到哪些动画技术？讲这些技术之前，先介绍一个概念。

#### 自由度：广告里的 6DOF 到底是什么

这个概念叫 degree of freedom，自由度：一个物体有多少个自由度，也就是你可以在多少个维度上去变化。前段时间，国内某大厂出了一款 VR 眼镜，上面有个核心广告词，叫"6DOF 设计"。我觉得很多消费者看了之后就懵掉了：什么叫 6DOF？

> **定义**：三维空间里的刚体，运动的自由度一共是 6 个——3 个平移 + 3 个旋转。

为什么？首先，它有平移的三个自由度：你可以把它沿 X、Y、Z 三个方向平移。想象一个小方块：你怎么平移它，它朝着你的方向永远朝着你、背着你的方向永远背着你——朝向不变，这就是三个平移自由度。但这是个刚体，刚体还有个能力：旋转。它旋转可以沿着三个轴：以 X 轴为中心绕着转、以 Y 轴为中心绕着转、以 Z 轴为中心绕着转——又是三个。所以三维空间里所有刚体的自由度，就是 $3+3=6$。

```text
刚体在三维空间的自由度 = 6 DOF
  平移：沿 X / Y / Z 方向各 1 个  →  3 个自由度
  旋转：绕 X / Y / Z 轴  各 1 个  →  3 个自由度
```

上下两行各贡献三个自由度，加起来就是刚体在三维空间里的全部运动能力。所以所谓很高端的"六自由度"VR 眼镜，本质上就是：你可以在这个世界这样看、那样看，可以上看下看——that's it，就是这样了。所以买东西之前，还是要学一点引擎的基础知识，至少不会被这种广告词带节奏带走。

我们的整个游戏动画，核心就是基于自由度的表达——也就是对刚体运动的表达。

#### 层次结构刚体动画：皮影戏的数字版

游戏里做 3D 动画，最基础的，是基于层次结构（hierarchy）的刚体动画。它其实非常像我们小时候看的皮影戏：把角色的每个关节做成一个可动的东西，去动它的时候，整个角色就动起来了。这些关节本身有一个树状结构，一层一层下来，我们叫 hierarchy。从最早的《生化危机》开始，你就可以看到这种最基础的 3D 动画系统。

但它有一个问题：当我把 mesh 的每个地方跟一根骨骼绑定的时候，骨骼动起来，这些 mesh 彼此会穿插。大家想，皮影戏的各个关节之间是不会互相穿插的——硬绑骨骼的数字角色就会，这正是我们前面说《生化危机》动画穿帮的原因。怎么解决？往下看。

#### 顶点动画：把每个顶点的运动存成纹理

先介绍一个大家平时可能注意不到、但玩的 3A 游戏里基本都用到的技术：顶点动画（vertex animation）。

比如游戏里的旗帜，想表现得特别好，要么用的是物理动画，要么用的是顶点动画。为什么？要表达风吹过布料的效果，如果放骨骼，你都不知道要放多少根骨骼。那干脆换个思路：把每一个顶点的位置随时间的变化，直接存下来。

存下来用什么装？一般存两张 texture。第一张 texture：横向轴是每一个顶点——顶点 1、2、3……假设你有 1 万个顶点，那就是 1 万个；纵向轴是帧数——假设动画有 100 帧，那就是 100 帧。把每个顶点的 offset（平移量）逐帧全部存下来。但顶点位置一动，表面的法向是会变的——还记得上一节课讲过，直接用顶点的位置去算表面法向，有时候会算出问题；为了效率，我们就把每一帧、每个顶点的法向也直接存下来，这就是第二张 texture。

```text
顶点动画纹理（vertex animation texture）的布局
          帧0       帧1       帧2      ...     帧99
顶点0   [offset]  [offset]  [offset]   ...   [offset]
顶点1   [offset]  [offset]  [offset]   ...   [offset]
 ...      ...       ...       ...      ...     ...
顶点N   [offset]  [offset]  [offset]   ...   [offset]

另一张同样布局的 texture：存每一帧、每个顶点的法向
```

读法：一行就是一个顶点在整个动画过程中的逐帧位移；每个顶点的每一帧都占一格。这张图一般是用物理引擎模拟出来的：离线把布料模拟好，存成顶点动画 texture，这样在引擎里就能展现出非常真实的旗帜效果。包括下面那个瀑布，也是顶点动画——大家想象不到，游戏里表现像水流这样的效果，也是用顶点动画去做的。

#### Morph Target 动画：捏脸系统的真相

接下来是 morph target 动画。它其实也是一种顶点动画，但跟传统顶点动画不太一样：它引入了顶点影响权重，在几种不同的 key pose 之间，对每个顶点做 key frame 插值。

这个东西在什么地方最有用？做人脸。相信很多小伙伴特别喜欢玩游戏的捏脸系统——我一直认为，很多游戏的捏脸系统就是游戏的本体：大家拿到一个游戏，愿意花三四个小时去捏个脸。那为什么可以一会儿捏出个蒜头鼻、一会儿捏出高鼻梁尖鼻子？你会不会想：是不是放一根骨骼，把它捏一捏、缩放缩放？确实可以这样。但是你会发现，当这种变形过大的时候，脸上那些五官看上去就不自然了。那个时候，实际上很多时候，我们是在各个不同的 morph target 之间进行插值。这个我们在下一节课讲面部动画的时候，详细给大家讲。

#### 蒙皮动画：本课的主角

我们这节课非常重点讲的，是 3D 蒙皮动画（skin animation）。为什么？因为游戏里最多出现的对象是什么？是人、是动物。人和动物最大的特点是什么？表面有一层皮肤——随着身体动的时候，皮肤不会自我穿插；但里面，其实是刚体的骨骼。

那为什么刚体骨骼在驱动的时候，蒙皮也跟着动，看上去那么自然？核心思想是：每一个顶点，受它影响的不止一根骨骼，而是多根骨骼在一起同时作用。这样能保证这个对象运动的时候是水密的（watertight），不会互相穿插。它比早期刚体 skeleton 动画要做得更好，也是现代游戏引擎最常见的动画模型。

这里断开一笔：蒙皮动画这套技术，在 2D 动画里现在也有很多人在用。为什么？一样的问题——如果你只是用骨骼去驱动一张张小图片运动，这些图片之间彼此肯定会有穿插，看上去角色就像机器人一样。用同样的原理，把 2D 的角色也用蒙皮动画的方法来做，你能看到人动的时候，整个身体相对自然地去变形。技术原理是一致的——今天我们在 3D 里讲的这些数学运算，在 2D 里也是完全起作用的。

#### 物理动画：布娃娃、衣料与 IK

最后一种动画形式，是 physics based animation，相对来讲比较难。

比如角色一旦受击、或者死亡的时候，就会进入一个我们叫 ragdoll 的系统，中文叫布娃娃系统——相信很多同学都听过。早期的布娃娃系统，把人做得跟沙袋一样；现在做得更讲究了：既有一部分设计师设计的 animation 的感觉，又有整个人摔在地上的感觉。

物理模拟的动画用得最多的地方在哪里？衣料。现在很多小伙伴玩游戏，会非常在意角色身上的衣料表达得好不好——但衣料模拟，其实是游戏动画、游戏物理里最难的东西之一；还包括流体的模拟。

最后一个，我们在下节课会讲：IK，中文叫反向动力学。它指的意思是：给定一个指定点，角色的身体该怎么运动，看上去才最自然。这件事情讲起来很简单——比如我在你面前放个苹果，你去抓它，这件事我是不需要训练你的，你天然就会了。但在游戏里，如何让这个动作整个一气呵成，实际上是非常非常复杂的。大家会不会觉得奇怪：为什么电脑会比人笨？你仔细观察一下小朋友：只有 0 到 6 个月大的时候，你在他面前放个东西，他其实是抓不住的；他要练习很久，才能够准确地一下子抓到苹果。所以我一直认为，人其实是用深度学习（deep learning）的方法、经过了长达以年为单位的训练，才练就了这种准确的抓取能力。那今天我们在游戏里，用什么算法也能模拟出人的这种聪明？实际上就是 IK 这个系统干的事情。physics based animation，也是动画非常重要的一个分支方向。

### 动画从哪儿来：手 K 与动捕

基本上，animation 在 run time 就是上面这些方法。另一个同样重要的维度，是 animation creation——动画本身怎么创造出来。传统方法有两种：一种是动画师在编辑器里手 K 动画——我们经常叫"手K"，K 的意思就是 key frame；动画师真的可能花上一个月，一帧一帧把动画 K 出来，后面我会详细讲。另一种就是 motion capture（动捕）——现在无论在电影还是游戏里，动捕已经用得非常非常广泛了。

### 蒙皮动画怎么做：流程很简单，写起来会炸

接下来，我们进入这节课真正核心、数学也比较密集的部分：我们知道了蒙皮动画这个需求，那它到底是怎么做的？顺便，把整个动画系统给大家讲清楚。

首先，给你一个模型（mesh），如何让它动起来？流程其实非常简单：

1. 先做一个模型，也就是 mesh，让它处在绑定姿势（bind pose）下；
2. 给它做一副骨骼——跟人类的骨骼一样，内嵌在皮肤之下，并且跟 mesh 的样子正好可以 align 到一起；
3. 刷蒙皮：给每个顶点指定——"你该受哪根骨骼的影响？哪根骨骼对你的影响大一点、哪根小一点？"具体怎么刷大家不用管，听上去也很直觉，对吧？
4. animator 让骨骼动起来——你的顶点不是被我刷了蒙皮了吗？它们也就跟着动了。

你想，蒙皮动画的原理，是不是就这个？非常简单。但是，如果你真的开始动手写代码，你看到的情况大部分时候是这样的：骨骼真的在动了，但那个角色一直傻站在那儿；或者整个角色直接动飞掉了。大家写动画系统的时候——动画我们一般在 shader 里做，在 `vertex shader` 里对每个顶点计算——经常是一个公式算错了，或者一个矩阵放错了，模型直接就炸开来。我们经常讲，把模型"写炸掉了"：本来角色好好地放在这儿，动画代码一上去，四分五裂。

> **易错点**：蒙皮动画的公式和矩阵没有完全推对的时候，最常见的两个症状就是"骨骼在动、角色不动"和"角色炸飞"。这是写动画系统最容易踩的坑，根源都在变换链没算对。

为什么我们这节课真正的主体，要把这个地方讲清楚？因为这是一切动画系统的 foundation。把蒙皮动画的数学和整个实现搞明白之后，你后面再去理解 IK、理解其他动画技术，难度就不大了。这也是我们今天特别想跟大家讲明白的游戏引擎基础。

### 一切计算都发生在空间里：三个坐标系

讲蒙皮之前，首先要讲三个空间。因为动画系统里所有的计算，都是在各自的空间里进行的。这个东西提上去，是不是有点抽象？空间不是很明确吗——我面前放着 XYZ。

第一层，是世界坐标系（world space）。在游戏里我们会建立坐标系，渲染那一趴讲过：世界坐标系可以做得非常大，大到整个太阳系的距离。

第二层，对每一个角色来讲，实际上有一个自己的坐标系。大家想：这是不是就是 local 坐标系？哎，不对——这个地方我们叫模型坐标系（model space），以我自己为中心：比如我站在这儿，我面前大概两立方米的空间，就是这个角色的 model space。

那模型坐标系和世界坐标系是什么关系？记住，它不是一个简单的平移关系。因为我的朝向可能会变，我整个人可能会仰过来。开个玩笑：假设你踩在地球表面上，整个宇宙的坐标系是 XYZ，但你站在地球 45 度纬度和站在南极北极，人的朝向是不是都变了？当然，一般我们永远认为自己是头朝上站着的。所以从世界坐标系到模型坐标系，就发生了刚才教给大家的那个东西——DOF，还记得吗？六个自由度的变化：我会发生平移 XYZ，还会绕 X、Y、Z 轴旋转。这样，就能定义一个唯一的、空间中的姿态。

讲到这儿已经很晕了，对不对？但前面讲渲染的时候，其实也讲过这个概念：怎么从世界坐标系变换到模型坐标系、再进行投影——讲的就是这个道理。

但做动画的时候，在模型之上还有一层坐标系，我们叫局部坐标系（local space）。这就有点抽象了。它指的是：在动画里，每一根骨骼——大家想，骨骼是一根一根一层层连上来的——每一根骨骼自己会发生平移、发生旋转，那它相对于模型坐标系，是不是又发生变化了？而且这个事情很讨厌的地方在于：每一根骨骼的标架（坐标系）都是不一样的。

举个例子：某根骨骼的朝向是这个方向，当你从它的根部、一路往手指尖传递的时候，这个方向就可能发生很大的改变。我现在手掌的朝向，实际上是由这一个坐标系、这一个坐标系、这一个坐标系……一路传递下来、共同形成的。

```text
world space（世界坐标系：整个游戏世界共用一个）
   │  刚体姿态：平移 XYZ + 绕三轴旋转（6 DOF）
   ▼
model space（模型坐标系：以角色自身为原点）
   │  骨骼逐级变换：每根骨骼的标架都不一样
   ▼
local space（局部坐标系：一根骨骼自己的小世界）
   ……从根到指尖，一个坐标系一个坐标系传递过去
```

所以，整个动画的表达，很多时候是在局部坐标系（local space）里进行的；而你要把 local 坐标系一路从根节点累算上来——一层一层乘上来——才能算出它在模型坐标系下的结果；再把模型坐标系放到世界坐标系里，角色顶点最终在世界里的位置，才算得出来。这条"局部 → 模型 → 世界"的变换链，正是接下来蒙皮动画数学登场的舞台。

## 让角色动起来：骨骼、姿态与旋转的数学
> 对应块：BLK16 | 覆盖分集：P09下 | 块标题（分集名）：《第八节(上)：游戏引擎的动画技术基础》

要让一个角色在你的游戏里活起来，第一步不是急着让它跳舞，而是先搞清楚"它在哪、朝哪"。角色自身站的位置和它的旋转，记录在它自己的坐标系里；只有把它变换到世界坐标系，这个角色才会被渲染出来。所以这几套坐标系，是我们在做动画系统之前，一定要搞得非常清楚的一个体系。理解了坐标系，我们就可以开始给角色构建骨骼了。

### 骨骼怎么搭：从胯部出发的一棵树

骨骼这个东西，理论上你可以任意构建，但在游戏的实践里我们不会乱来。比如人形的物体——我们叫 biped，两足生物——我们会构建一个跟人类骨骼非常接近的骨骼结构。在这个结构里，大家一定要记住一个点：它的起点在哪里。我们讲的是个树状结构，这个起点一般在人的胯部，我们叫 pelvis——就是脊椎最后一根骨头、尾椎那个地方。为什么选那儿？从那个点出去之后，你会发现它向下可以分化出你的两条腿，向上就是你的脊椎——脊椎决定你的身体是弓的还是直的；然后到肩膀一展开，它就变成两只手。所以整个角色的中心点，就在 pelvis 这里，有时候我们还会在附近再做一个 root，这个后面细说。

```text
root（两脚之间，像手办的支架）
 └─ pelvis（尾椎，树状结构的起点）
     ├─ 向下：分化出两条腿
     └─ 向上：脊椎（决定身体是弓的还是直的）
          └─ 肩膀一展开：两只手
```

读图说明：人形骨骼是一棵以 pelvis 为起点的树，引擎里通常还会在两脚之间另立一个 root 节点，专门用来表达角色的整体位置。

这样的结构，对游戏里大部分应用已经够用了。但游戏里我们还要做很多可爱的小动物，小动物就很讨厌了——它是趴在地上的，我们叫 quadruped，四足动物，它的骨架就又不一样了。

那为什么我们要把骨骼定义成这种标准结构？因为当我们去生产动画资源的时候——特别是做 motion capture、做资源生产的时候——我们不太可能去生产那么多不一样的资源。如果你的骨骼基础结构老是在变，动画师是很难做的：他手里有大量的资源库，你的骨骼拓扑老是在变，一会儿以脚趾头为起点、一会儿以脑袋为起点，那这些动画资源之间就很难复用。所以这套树状结构，也是我们这个行业约定俗成的一个结构。

### 存的是关节，不是骨头

在这里，我要给大家 clarify 一个特别容易混淆的概念——这个概念包括我自己讲的时候，也会经常顺嘴说"骨骼、骨骼、骨骼"，说我们用骨骼构建了 skeleton。skeleton 英文的意思就是骨架。但实际上，在游戏引擎里，我们并不是真正表达一根根骨头，我们表达的是 joint，关节。

> **易错点**：引擎存储的是每个关节 joint 的数据，而不是骨头本身。两个相邻关节之间才定义出一根骨头；关节一动，它前面那根刚体骨骼跟着动。

比如我们存的是肘关节的数据：因为肘关节前面连了一根刚体的骨骼，所以当你的肘关节发生旋转、或者发生偏移平移的时候，这根骨骼也会跟着动——但我们并不会直接存储骨骼的数据。那肘关节的下一个子节点、树状结构的下一个节点是什么？是腕关节——手腕这个关节前面，就控制了我的手掌。

```text
肩关节 ──骨── 肘关节 ──骨── 腕关节 ──骨── 手掌骨骼
```

读图说明：相邻两个关节之间定义一根骨头；引擎里存的是关节的数据——肘关节一转，它前面那根刚体骨骼跟着动，腕关节一转，控制的是手掌。

当然，没关系：大家看游戏引擎的代码、或者自己写的时候，真的把它写成 bone 也没有关系。但从数学上，我想把它定义清楚：joint 本身是有很多自由度的，而 bone 本身没有——因为 bone 是由两个 joint 联合定义出来的。

那为什么存 joint 不存 bone？因为 joint 是个刚体参照，它不会被 twist（扭转）；但你想想我的骨骼，其实像这边的肌肉一样，是可以被 twist 的。为什么？假设骨骼不是刚体：肘这个地方是一个 joint，那边是另外一个 joint，这两个 joint 可以这样转——那中间这一段 bone，实际上就被扭曲了。蒙皮（skinning）动画里我们也会看到这种扭曲。这就是用 bone 来表达的不严谨性。

### 标准骨骼之外：表情与变形都要加骨头

在游戏中构建骨骼，除了人正常要的这些骨骼之外，实际上我们还会加很多很奇怪的额外骨骼。最恐怖的时候：一个标准骨骼可能也就 100 多个左右，但我要考虑人脸、要做很细致的表情，可能又要加七八十个甚至到 100 个骨骼——眼睛、眉毛的运动，比如大家经常看到的眼球运动（这个我们下节课会讲），都是用骨骼去驱动的。

然后，游戏动画对人有很多变形：我们会要给他做个大翅膀、做那种斗篷，还有我手上拿的武器——各种各样的变形，这些骨骼实际上都会加到角色的标准骨骼上面。所以当我们想做一个游戏引擎的时候，一般第一步就要定义一个标准角色的"标准组合"是多少。这也是我们的 TA 团队——技术美术团队和技术团队——最核心要确定的东西。

### 挂点 mount：武器绑在一只手上

举个具体的例子。比如我手上拿了一把大斧：武器实际上有一个叫武器 mount 的骨骼——也就是说，我手上不管是拿巨剑还是拿大斧，它都是 mount 到我手上一个叫 weapon 的 joint 上面的。你看到这个角色好像两只手拿着武器，但一般来讲，很多动画师是把武器单一地绑在手上的——角色通常用右手拿武器，所以就是绑在右手骨骼上。

包括人骑乘在一个生物上面，它会有一个骑乘的 mount 骨骼点。这个 mount 到底怎么把两个对象接在一起，讲完 root 我们马上回头看。

### Root 骨骼放哪里：手办的支架

刚才提到，很多骨架都是从尾椎 pelvis 开始的，但在真正的游戏引擎里，我们一般会额外定义一个叫 root 的骨骼。以人形为例，root 一般会定义在两脚中间。为什么放这儿？大家想想看：比如我们在游戏里表达一个角色的移速，或者他跳起来了——我说这个人的离地高度是 0.5 米。如果你用 pelvis 那根骨骼来存，当这个人蹲在那、或者跳起来、或者站起来的时候，它的离地高度都会变；但我们关心的离地高度，一般指的其实是它的脚。所以 root 反而更加自然：当我们去决定一个角色的移速、他跳起来的高度的时候，我们一般从 root 开始算。

这就像什么呢？大家喜欢玩手办，对不对？无论那个手办摆出各种各样很漂亮的姿势，你发现没有，手办下面总有一根支架，那根支架是插到台座上面的；那个台座，你可以在你的桌子上移来移去。那根支架插下来的地方，就是我们的 root 骨骼。这根骨骼其实非常非常重要。

四足动物这个地方就更有意思了。想象一下，我们一个演员如果想让他扮演一匹小马，他的尾椎在哪里？是不是正好在马的屁股那边？所以动画师一般会把 pelvis 那根骨骼，放到马的尾椎那个地方；但是他的 root 呢？诶，他很聪明地放到母马的肚子下面。为什么？因为我现在要表达这匹马的位置的时候，一般都会以它的中心点那个位置来表达。你会发现，当这些骨骼结构在行业里约定俗成的时候，它背后还有很深的道理——都是为了方便让我们对它的位置表达得非常准确。

### 绑定动画：总有那一帧，人绑死在座椅上

大家还记得前面讲 gameplay 系统的时候，讲到 object 之间是有父子关系的。为什么我们需要父子关系？因为在游戏中，有很多动画、很多角色之间的行为是绑定的。

最经典的就是人骑在马上。人是播放人的动画，马是播放马的动画，那我怎么让两者的动画一致呢？我在人的身上会有一个叫 mount 的 joint，在马的马鞍那个位置，也有一个 mount 的 joint，这两个 joint 重合在一起。

记住啊，这个重合不是一个简单的 XYZ 空间重合，还有旋转的重合——也就是说，你可以想象两个坐标系，它的轴是整个对接在一起的。大家想象一个卡槽：它不是一个简单的点连接，点连接只是位置重合；它是连你的朝向都接上了——马前倾的时候，你人要跟着前倾；马后仰的时候，你要跟着后仰——这样完美地卡在一起。这就实现了我们的 bound animation（绑定动画）。

> **定义**：绑定动画（bound animation）——把角色身上的 mount 关节与另一个对象（坐骑、载具）上的 mount 关节做位置与朝向的双重对齐，让两者的运动从此绑在一起。

绑定动画对角色来讲非常重要，因为我们有大量的载具。比如大家经常在游戏里看到的开汽车：角色实际上展开了一系列很花哨的动作——拉开车门、翻身跳进车里面，你看着很厉害吧？但他总有那一帧，这个角色的屁股就绑死在汽车的某一个座椅上了；然后这个时候，车怎么动，人就跟着动。这就是游戏引擎实现绑定动画的方式。

这个功能引擎必须要实现，而且它一般会和 gameplay 系统连接得非常近。所以为什么我一直讲，如果大家想做 gameplay 的程序开发，一定要理解动画系统——因为这两个是不可分割的紧密关联。

### T-pose 还是 A-pose

工业上还有一个常见的现象。早期我们做游戏引擎的时候，角色和骨骼的绑定，我们用 T-pose——我相信大家能想到，很自然，对吧，整个人双臂张开。但随着现在商业游戏的发展，大家逐渐发现 T-pose 有问题：这个角色的肩膀这个地方，其实是被挤压的。想象一下，我要做一个比较复杂的角色，这边的肩胛要展开、要做变形的动作的时候，你这边的精度其实就不够了。

| 绑定姿势 | 姿态 | 问题与取舍 |
| :--- | :--- | :--- |
| T-pose | 双臂水平张开 | 肩部被挤压，做肩胛展开等复杂动作时精度不够 |
| A-pose | 整个人站得相对自然 | 肩部区域精度更高，现代 3A 游戏越来越多采用 |

所以在现在的 3A 游戏中，我们越来越多地用 A-pose：整个人站得相对自然一点，肩膀这个地方就会给它相对高的精度。这是行业里的一个实践。

### 一个 pose，九个自由度

有了骨骼、有了 mesh，当我去动这个骨骼——比如表达"走"——把这个动作做出来之后，这一个静止的状态叫什么呢？我们叫做一个 pose。这个词大家很熟吧？就是姿势、姿态。比如你拍照片的时候，我说你摆个 pose。在动画中，一个 pose 指的就是一帧：你的脚摆在这，或者你的手举在这，这就叫一个 pose。把很多 pose 连到一起，就会形成一个动画。

这里有个细节我要补上——本来这页幻灯片上少了一行：其实我们真正表达动画的 pose 的时候，它是有九个自由度的。刚才我讲刚体的运动，不是只有旋转，还有平移和旋转；实际上真正做动画的时候，我们还有一个叫 scale 的放缩。平移三个、旋转三个、放缩三个，一共就是九个自由度。

放缩在很多时候其实非常有用：比如我去做人脸的变形、做一些角色的弹性变化的时候，我们需要用到放缩。这个其实比较简单，我们后面再讲。

### 旋转的数学：从二维到三维

接下来这一趴，就是我们今天这节课相对来讲比较硬核的部分——它真正的数学是什么。在理解动画之前你们会发现，如果我们的动画是用各个关键点去表达的，那手上这些关节做得最多的运动是什么？是旋转，对吧。而这个旋转很难：它有很多自由度，不是一个简单的绕一根轴转——我们人的关节也设计得非常精巧。那么，如何能在 3D 空间里表达旋转？这件事情还真的不简单。

#### 二维旋转：三角函数与旋转矩阵

最简单的旋转，是二维空间里的。假设重要的一个角度叫 $\theta$，它有两种表达：一种是在角度空间里，我们叫 $\theta$ 角；另一种，在我们大名鼎鼎的笛卡尔坐标系里，旋转可以用一个向量表达：

$$x = r\cos\theta, \qquad y = r\sin\theta$$

当两个旋转叠加——我转完一个 $\alpha$，再去转一个 $\beta$ 角——结果等于多少呢？我们中学就学过三角函数的和角公式。我记得我高中学的就是三角函数，相信大家中考就要背这些东西了。

到了大学我们学了线性代数，对不对？我们就可以用线性代数的方法，把旋转表达成一个 $2 \times 2$ 的矩阵：

$$R(\theta) = \begin{bmatrix} \cos\theta & -\sin\theta \\ \sin\theta & \cos\theta \end{bmatrix}$$

把任何一个向量 $(x, y)$ 放进去，乘上它，它就能旋转。这就是二维空间的旋转矩阵——非常的 elegant，非常的美，很好看。

#### 三维旋转与欧拉角

但这件事情到了三维之后，就会变得复杂了。二维空间里，旋转的轴只有一个，就是绕着中心点转；三维空间里，轴不是变成两个，而是一下子变成了三个——你可以绕着 X 轴做一个旋转，也可以绕着 Y 轴、绕着 Z 轴做旋转。实际上更难的是什么呢？你可以绕着任意轴去旋转。没有谁规定一个东西只能绕着一个特定的、跟坐标对齐的（axis-aligned）方向去旋转，这就表达起来很麻烦了。

但是数学家证明了：你在这个空间上的任何一个旋转，我可以用这三个轴的旋转把你叠加出来。假设我依次沿着 X 轴、Y 轴、Z 轴旋转，沿每个轴转的角度分别是 $\alpha$、$\beta$、$\gamma$，那我们就可以算出三个 $3 \times 3$ 的矩阵。你注意：如果只沿着 X 轴转，你会发现这个旋转矩阵里的很多项都是 0——它真正有效的只有中间那 $2\times 2$ 的四个因子，其他的 1 和 0 都是配平的。这个公式大家自己可以推一下，其实非常简单。

然后，当我沿着 X 轴转一个 $\alpha$ 角度、沿着 Y 轴转一个 $\beta$ 角度、沿着 Z 轴转一个 $\gamma$ 角度，把这三个矩阵垒在一起，就得到一个看上去很复杂的形式——但计算机写起来是很简单的。你把任何一个空间上的点或者方向 $(x, y, z)$ 带进去，就能算出它沿着这三个旋转之后的样子。这就是一个典型的欧拉角（Euler angles）。大家应该在高中的立体几何或者解析几何里学过这个概念——欧拉角是一个很早期、很经典的，对三维空间旋转的表达。

#### 飞行员的语言：yaw、pitch、roll

欧拉角这个东西实际上非常重要。你们玩所有的空战模拟游戏、玩航海游戏，或者说你们真的在开一个游艇、开一个飞机的时候，会知道有个概念叫 yaw、pitch、roll。yaw 就是航向角，我们传统上一般用 $\phi$ 来表达；pitch 我们叫做攻角，指飞机在气动力上对空气的攻角——pitch 这个词，就是往上进攻的意思。比如飞机失速，就是 pitch 角太大导致升力骤减，让飞机在空中解体了。roll 是什么呢？就是飞机自己往左往右地这样摇摆——我这样模拟一下，很笨拙，但基本上能表达这个 yaw、pitch、roll。

其实 yaw-pitch-roll，就是欧拉角的另外一种话术表达。你可以认为现在的导航、航空器，用的都是这些很基础的概念。你们要做一个 vehicle 系统（载具系统）、或者一个空战模拟系统，这就是你最核心的几个概念；包括做气动力模拟的时候，我们也要用 yaw-pitch-roll 这个概念。这都是欧拉角的典型案例。

### 欧拉角的麻烦

欧拉角其实是有问题的，而且不止一个。我们先讲一个我自己认为最讨厌的问题。

#### 最讨厌的问题：顺序依赖

你对它的计算是严格的 order dependency——顺序依赖的。刚才讲的是沿着 X 轴转 $\alpha$、沿着 Y 轴转 $\beta$、沿着 Z 轴转 $\gamma$，但是你去 apply 这个运算的时候，顺序不一样，得出的结果是不一样的。想象图上那个例子：我先沿着 X 轴转 90 度，再沿着 Z 轴转 90 度，转出来的结果，和你反过来转的结果，是完全不一样的。这就是三维空间的复杂度。你会发现二维上没有这个问题——二维你只有一个自由度；三维你有三个自由度，这三个度之间，如果你的顺序错了，旋转结果完全不一样。

> **易错点**：用欧拉角时一定要约定旋转顺序——必须先沿 X 轴、再沿 Y 轴、再沿 Z 轴（或事先约定的固定次序），否则整个顺序就是乱的。

#### 万向节：欧拉角最实用的化身

欧拉角这个东西在实践里，最贴近的一个实用价值，就是万向节（gimbal）。万向节其实非常符合人类对空间旋转的感知。在现代游戏引擎里，我们让艺术家（artist）来表达旋转的时候，用的全是万向节的方法，也就是欧拉角。

万向节为什么非常有用？我给大家举一个大家可能注意不到的东西。大家拍摄像的时候，有一种叫云台的机头架：相机放在那，无论你怎么动，它的朝向永远对着那个方向。这个东西用的其实就是万向节的技术——三个自由度的旋转，永远保证它的朝向。包括大家喜欢飞的无人机，比如大疆无人机：你的飞机飞的时候其实有很多抖动、很多朝向变化，但是你会发现，你的画面总是很稳定，对不对？包括我们现在叫微云台的这种技术，它实际上里面用的也是一个变了形的万向节，保持这个方向非常稳定。

另外一个非常重要的应用是陀螺仪。请大家想象一下：在没有 GPS 导航的时代，我们一枚导弹打出去，它是怎么不偏航的呢？实际上导弹里面有一个高速旋转的陀螺，这个陀螺因为惯性的原理，始终指向一个方向。但是导弹的身体会一会儿上、一会儿左、一会儿右，那它怎么能保证那个陀螺永远指向一个方向呢？——它这个地方其实就做了一个万向节。而且我去测量每一个节点旋转的角度，实际上我就知道你这个导弹的方向是怎么偏的；那么我把这个导弹沿着时间轴上所有的方向偏移做一个积分，再和它的速度在一起积分，我就可以算出它的轨迹。所以这个事情真的很了不起：用这么简单的一个原理——比如一根空速管测出我的速度，再加上一个方向的积分——我就能够对我的导弹进行导航。当然了，那个时候的误差还是很大的：我飞 1000 公里，能误差个几百米。但是这已经非常了不起了。你会发现，游戏动画里很多的数学概念，实际上在真实的世界里也是非常有用的东西。

#### 万向节死锁：旋转被锁死的退化

但万向节其实有一个小问题。我们回归到刚才那个旋转的方程：欧拉角的这种表达方式，当你沿着 Y 轴转了 90 度之后，你会发现——因为 X 轴的旋转是这样转的——你的 Z 轴，实际上转得跟 X 轴是共轴了。这个时候你沿着 Z 轴做的任何一个旋转，本身已经没有太大意义，只有这两个旋转之间——$\alpha$ 角和 $\gamma$ 角之间的差值——才有真正的数学意义。

这就是我们经常讲的欧拉角的一个退化情况。这个退化情况会导致整个模型的旋转被锁死，它只能沿着那个定死的方向转。另外一个呢，比如我有两个空间上的旋转，要从旋转一插值到旋转二，在这个地方它就会出很大的问题——这也是欧拉角很挑战的地方。

#### 三道过不去的坎

虽然欧拉角非常有用、非常符合人的直觉，它还有几个我认为比较难的问题。

第一个，它非常难以插值。给你一个欧拉角的旋转 $(\alpha_1, \beta_1, \gamma_1)$，还有一个 $(\alpha_2, \beta_2, \gamma_2)$，他俩的插值，其实不能简单地用线性去做——你差一下就知道，这个值是错的。

第二个，旋转的叠加（combination）非常难。假设我有两个旋转，一个 $(\alpha_1, \beta_1, \gamma_1)$，另一个 $(\alpha_2, \beta_2, \gamma_2)$，我按第一次旋转、再加上第二次旋转去做——就像刚才我举的动画的例子：我这个关节做完了一个旋转，再在这个关节做一次旋转，这个旋转比较复杂，我在这个方向再转一下，那最后我问你，这个手掌转成什么样子了？你会发现，它不能简单地用两组角度数学加在一起——这个值是错的。

第三个，也是欧拉角最难的问题：定轴旋转。刚才我们对所有旋转的表达，都是沿着坐标轴——X 轴、Y 轴、Z 轴。但是大家想一想，在真实的世界里，大部分的旋转并不是严格沿着空间上的 XYZ 去做的。举个例子：当我的手这样放着的时候，我可能要沿着一个斜向的角度——这个角度可能指向空间的 $-45$ 度、60 度那个方向——去做这样的一个旋转。大家发现没有？这其实是非常常见的。那我给定一个定轴、任意空间的一个轴的方向的时候，这个旋转就会变得很难。

> **结论**：欧拉角一般用在给 artist 做编辑、特别是物体摆放的场景里；真正做动画的时候，我们不能用欧拉角——因为它不好插值、不好叠加，而且很难做定轴运算。但它非常符合我们的自然认知，所以在编辑器里它依然是主角。

这里面，就要引出我们大名鼎鼎的四元数了。

### 四元数登场：桥上想出来的数学

四元数真的是非常非常了不起。我前几节课一直在讲这样一个概念：我觉得我们人类，一定要感谢这些非常伟大的数学家——当我们遇到一个真正要解决的问题的时候，数学家一般在 100 到 200 年前，就已经把数学工具给你准备好了。

哈密尔顿（Hamilton）就是一个非常了不起的人，这个人应该是个爵士。他有一段跟他儿子的对话：孩子老是在问我——对于三维空间的旋转，能不能像复数一样，非常简单地通过一些代数运算，就能完成旋转的叠加？哈密尔顿老先生呢，每天早饭散步过那座桥的时候，都会在脑子里面去想这个问题。直到有一天他过桥的时候，突然产生了这个伟大的想法，叫四元数。所以他去世之后，他的家乡人就在他那个桥上，刻下了这段故事。他确实非常了不起地把这件事情解决掉了。

那怎么理解四元数呢？理解四元数之前，首先理解复数。复数有一个非常好的性质：对于二维空间的任何一个旋转，我可以用一个归一化的复数值 $a + bi$ 来表达——$i$ 就是复空间的那个轴，$i^2 = -1$ 这样的定义。这样，两个旋转的叠加就能非常优雅地表达出来。大家记得刚才的三角函数公式，对不对？$a$ 其实就是 $\cos\theta$，$b$ 就是 $\sin\theta$；这时候来了另一个 $a' + b'i$，比如 $\cos\gamma + \sin\gamma\, i$，那么两个角度的叠加，实际上用复数乘法那个公式就可以完成，而且这个公式非常简单。

哈密尔顿老先生就在想：那对于三维空间的旋转，我怎么去表达呢？我给大家讲一个非常粗暴的概念：三维空间的旋转，你有三个轴；二维空间只有一个轴。那我再加两个维度行不行？你看复数是实部加虚部，那我再加两个虚部，是不是正好就是四元数？我这个解释听上去是不是很有道理？但实际上呢，这个解释是非常不正确的。

我们前段时间研究的时候，我自己做下去才发现：四元数这东西为什么 work——实际上只有在三维空间的旋转，我用四元数能够表达，你再往上走，它就不行了。这实际上是用群论证明的：只有在这种特定的三维空间的情况下，你这套数学方法才是 work 的。这个就非常复杂了，说实话我都没看懂。我记得我当年想研究一下"为什么五次以上的方程就没有解析解"的时候，还冒死去看了一点群论，然后直接就被无情地教育了一遍。所以这个地方我就不带大家入坑了，因为我也没学会。当然，四元数的原理其实是非常的 elegant、非常的漂亮的。

### 四元数的运算法则

四元数首先定义了三个虚数单位：$i$、$j$、$k$。对于任何一个空间上的旋转，我们可以尝试用这样的形式去表达：

$$q = a + b\,i + c\,j + d\,k$$

大家在游戏引擎里经常可以看到 Quaternion，指的就是四元数。这三个虚数单位之间，是有一个数学规律的：

$$i^2 = j^2 = k^2 = -1, \qquad i\,j\,k = -1$$

优雅的东西来了。既然我知道 $i\,j\,k = -1$，那我就问：$i\,j$ 等于什么呢？这件事情好像没有定义，对不对？哎，这个时候我们就想起了数学的配平原理：在 $i\,j\,k$ 后面再补一个 $k$，那么 $i\,j\,k^2 = -1 \cdot k = -k$；因为 $k^2 = -1$，所以 $-(i\,j) = -k$，也就是说 $i\,j = k$。其实你会发现，三个虚轴都有这样一个轮换关系：

$$i\,j = k, \qquad j\,k = i, \qquad k\,i = j$$

这就是数学的优美：你定义了它的基础算术之后，它的整个交换和组合，就全部定义出来了。

对它的表达，一般我们有三种形式：可以写成 $a + bi + cj + dk$ 的虚实部形式；有时候我们也会用向量的形式去表达，就是一列四分量的向量；有时候我们会用实部加一个虚部向量的形式，比如 $a + \mathbf{v}$，其中 $\mathbf{v}$ 本身表达的就是 $(b, c, d)$。

那么刚才定义了 $i$、$j$、$k$ 的乘法关系，两个四元数的乘法怎么定义呢？幻灯片上那个矩阵看上去很复杂，但是它实际上是非常简单的：你得到了一个 $(a, b, c, d)$ 的第一个四元数、一个 $(e, f, g, h)$ 的第二个四元数，它两个的乘法，你可以认为是 $a$ 去乘上 $(e, f, g, h)$ 所有的虚实部，然后 $b$ 再一次乘一遍、$c$ 全部乘一遍、$d$ 再全部乘一遍；这里面有的时候是 $i$ 碰到了 $i$、有的时候 $i$ 碰到了 $j$、有时候实部和 $j$ 碰到了，你把那一组 $i$、$j$、$k$ 的变换规则带过去，你发现你得到的就是那个矩阵。这个矩阵其实非常简单，课上我不展开了——我没有办法在这里依次给大家推导——但是你简单运算一下，会非常有意思，它的运算就是那样的一个矩阵。

既然是空间上的某种高维数字，无论在线性代数里还是解析几何里，我们都会定义它的模。模最标准的定义是什么？就是各个维度上的值 $a^2$、$b^2$、$c^2$、$d^2$ 的平方和再开根号：

$$\|q\| = \sqrt{a^2 + b^2 + c^2 + d^2}$$

一个四元数的模假设等于 1，我们认为它就是一个单位的四元数，也就是单位向量。跟复数一样，我们引入共轭的概念：把它的虚部全部变成负数，也就是 $q^* = a - bi - cj - dk$。

这个公式里其实还少写了很重要的一条：如果我这个四元数本身是 normalized 的——就是一个单位的四元数——那么它的共轭就是它的逆。逆是怎么定义的？就是这个四元数按照刚才那个乘法，乘上另外一个四元数，正好等于 1。这个逆非常有用：为什么？逆就表示了——我假设四元数表达的是旋转的话，它的逆就表示相反方向的旋转。它这个数学上就是这么定义的，这个概念大家稍微消化一下：它的核心原理跟复数非常相像，但是它的乘法矩阵，计算步数稍微多一点。

> **定义**：单位四元数的逆就是它的共轭，$Q^{-1} = Q^*$；几何上，逆就是反方向的旋转。

### 用四元数做旋转

有了四元数的运算法则，我们就能看到它真正干活的样子了。

#### 夹着转：前面乘 Q，后面乘逆

我们用四元数如何表达一个旋转？哈密尔顿老先生给出了这样的定义，这个和大家的理解可能不太一样：我们天然会认为，它不应该是一堆 $\alpha$、$\beta$、$\gamma$ 的 sin 和 cos 的组合吗？但是哈密尔顿给出的公式里面，全是二分之阿尔法、二分之贝塔、二分之伽马。为什么是半角？看到它怎么旋转，你就明白了。

用四元数做旋转的时候——比如我给你任何一个空间上的轴也好、坐标也好，假设它是 $(b, c, d)$ 这样一个位置——你首先要把这个空间上的三维，变成四元数的形式：把它的实部设成 0，然后把三个轴上的投影写到三个虚部里面，就是 $0 + bi + cj + dk$。你对它做了这个表达之后，你的四元数对它进行旋转，实际上是用 $Q$ 放在第一个——旋转在前——把刚才你凑出来的那个四元数夹在中间，然后再把 $Q$ 的逆放到后面：

$$p' = Q \, p \, Q^{-1}$$

```text
复数（2D）  ：  p' = p · q          —— 乘一次就够了
四元数（3D）：  p' = Q · p · Q⁻¹    —— 前面乘一次，后面还要再乘个逆
```

读图说明：二维复数旋转只要乘一次；三维四元数旋转必须像三明治一样前后各夹一次，所以四元数里的角度各只承担一半。

记住啊：如果我们用复数去表达旋转，我只要把这个轴乘上那个复数就完了；但是你在三维空间表达旋转的时候，前后都要加一个——你要乘上它，再乘上一个逆。大家如果学过线性代数，这个很像我们线性代数里面的那个 SVD 分解：中间有一个列向量放在中间，两边一边放了一个矩阵、另一边放个矩阵的逆，其实非常像。所以四元数的很多原理，跟矩阵运算是非常非常接近的。

那么你把前面定义的四元数运算串起来——单位四元数的逆就是它的共轭；两个四元数的乘法实际上是一个矩阵的运算——那么 $Q$ 和 $Q^{-1}$ 的连乘，你就可以依次算过去，就是矩阵的连乘。这个时候你就会得到一个非常有意思的公式：我的任何一个空间上的向量在 rotation 的时候，算出来的作用就是一个 $3 \times 3$ 的矩阵——因为有些项消掉了，你只需要知道它的 x、y、z。这个就是一个四元数的旋转变换。这就意味着，你不需要再去算什么 sin、cos 了——你实际上就是乘上这个矩阵，任何一个方向、任何一个角度都可以被旋转起来。这是非常有道理、非常有意思的一个东西。

#### 反向旋转与旋转叠加

你有了四元数之后，想表达一个反向旋转，我只要求它的逆就可以了。逆我讲过：如果它是个标准化的单位四元数，你就是把它的 $i$、$j$、$k$ 整个翻成负数就可以了。是不是非常的简单？

那我有第一个旋转 $Q_1$，还有一个旋转 $Q_2$，假设想把一个点、一个向量、一个方向，按 $Q_1$、$Q_2$ 两次旋转，怎么旋转呢？其实那个合成的旋转四元数，就是 $Q_1$ 乘 $Q_2$。这个公式我不展开，但其实你们可以证明：这两件事情是等价的。

#### 两个现成公式：从 U 转到 V、绕定轴转 θ

还有一个比较厉害的：我有一个方向 $U$，我要转到方向 $V$，怎么办？它的原理非常简单。大家想想：两个方向，是不是定义了一个面？这个面是不是就可以有一个法向方向？所以用右手坐标系、右手原则，我们可以找到往外延伸的那个轴：

$$W = U \times V$$

然后，这个旋转四元数的实部，用这个公式去表达：$U$ 点乘 $V$，加上开根号的（$W$ 点乘 $W$，加上 $U$ 点乘 $V$ 的平方）；它的虚部是什么呢？就是 $W$ 本身——如果 $W$ 你算出来是 $(x, y, z)$，就把 $x, y, z$ 放到三个虚部里面去：

$$q_{U \to V} = \Big(U\cdot V + \sqrt{\,W\cdot W + (U\cdot V)^2\,}\Big) + W_x\,i + W_y\,j + W_z\,k$$

这个四元数本身，就能够表达从 $U$ 向 $V$ 的这样一个旋转。它其实非常的简单。

同样，你想表达沿着一个给定轴的旋转，也就非常简单了。想法也很简单：对于任何一个轴，你要去旋转它的时候，我其实定义了一个围绕这个轴旋转的四元数。你会发现，假如你要转 $\theta$ 角，它的实部就是 $\cos$ 的二分之 $\theta$；它的虚部，是把那个轴的 $x, y, z$ 放进去，乘上 $\sin$ 的二分之 $\theta$：

$$q = \cos\frac{\theta}{2} + \hat{n}\,\sin\frac{\theta}{2}$$

你用这个四元数去运算，任何一个向量都可以转得过去。所以有了这个数学方法，当我有了空间方向，从给定了任何一个轴——比如说它是一个不是轴对齐的轴——我其实就可以算出它的旋转了。

当然，这里面都是有很多数学推导的。这节课我不打算展开——当时我在做动画系统的时候，也不会过于地把这些公式再证明一遍：基本上这些公式，教科书里都有，我们直接拿来用；而且你用完一遍之后会发现，基本上不会用错。

### 把三角函数问题变成线性代数问题

你会发现，我们把一个非常复杂的空间旋转、包括大量三角函数运算的这个问题，变成了一个非常简单的线性代数问题。这件事情其实非常的重要。同学们如果自己推导一下：假设我全部用欧拉角，有第一组旋转 $(\alpha_1, \beta_1, \gamma_1)$，有第二组旋转 $(\alpha_2, \beta_2, \gamma_2)$，你把两次旋转的结果，想用一个 $(\alpha_3, \beta_3, \gamma_3)$ 去表达的话，其实非常的难、很复杂，而且可能还有多义性。为什么？因为旋转超过了 $2\pi$，它不就又转了一遍嘛；而且你可以正向旋转，也可以反向旋转。那么当你用四元数的时候，它就变得是一些简单的、没有任何歧义的数学运算。

所以四元数实际上是哈密尔顿对数学的一个非常关键的贡献。而且这个贡献，当我们进入了计算机时代、进入了游戏和虚拟现实的时代——其实他在做机械、做刚体的各种轨迹计算的时候，也是非常有用的一个东西。

这，就是我们整个游戏动画的一个数学基础。为什么呢？因为 rotation，是动画的最核心的一个元素。

## 骨骼动画的数学与工程实现
> 对应块：BLK17 | 覆盖分集：P10 | 块标题（分集名）：《第八节(下)：游戏引擎的动画技术基础》

上一讲我们把表达 rotation 的数学基础——四元数——彻底讲透了。有了这个地基，这一讲就能回答一连串更落地的问题：一个关节（joint）的姿态到底怎么表达？蒙在骨架上的皮肤怎么跟着骨头走？一秒只存十几帧的动画，怎么在 60 帧、120 帧的游戏里平滑播放？动辄两三个 GB 的动画数据又怎么塞进游戏？把这些问题串起来，你就拥有了一个能真正上战场的动画系统。这一讲信息量很大，我们一个一个来。

### 先把一个关节的姿态拆成三个量

先说一个措辞上的细节：表达关节朝向时，我更喜欢用 **orientation** 这个词。它和 rotation 很像，但 rotation 更"平民"一点，orientation 更能表达"空间上的朝向"这层意思。关节在任何时刻都有朝向的变化，而在大量动画里，绝大多数关节的运动就是以旋转为主——你把关节和它父关节之间的关系摆出来看，会发现它们之间通常**既不发生平移，也不发生放缩，只有旋转**。所以，旋转的表达是动画最核心的东西。

那 position（平移）呢？两个 joint 之间的位移一般是个常数：父骨骼定在那，子骨骼相对它的位置就不变，父骨骼转了，子骨骼跟着转。但这个数值在引擎里还是有用的，因为有几类特殊情况真的会平移：

- **骨盆（pelvis）**：人蹲下再站起来，骨盆相对 root 的位置是不是变了？整个角色的站立和蹲下，就是靠这根骨骼"顶"起来的，所以它有大量的平移变化；
- **表情动画**：脸上也存在大量的平移变化；
- **特殊机械结构**：比如做一把古代的弩，弩箭拉开、松起，对应的骨骼同样有平移变化。

除了这些场合，你要是随便给关节加平移变化，角色看上去就会非常奇怪。

最后是放缩（scale）。去看大量动画数据的话，scale 这一项基本都是 1，谁都不动它。但有些场合用得还蛮多：比如面部表达——给角色做个大眼睛、小眼睛、大鼻头、高鼻头、鹰钩鼻、塌鼻梁，用的就是放缩；而且沿 X、Y、Z 三个轴的放缩比例可以各不相同。

| 姿态分量 | 数据表达 | 通常情况 | 什么时候真的在动 |
| :--- | :--- | :--- | :--- |
| 旋转 rotation | 四元数 | 动画的绝对主体 | 几乎所有关节、所有动作 |
| 平移 translation | Δ(x, y, z) | 父子关节间通常是常数 | 骨盆蹲起、表情、弩箭等机械结构 |
| 放缩 scale | (sx, sy, sz) | 几乎恒为 1 | 面部捏型，且三轴比例可不同 |

### 把姿态装进一个仿射矩阵

任何一个 joint 的姿态，都可以分解成三个元素：旋转、平移、放缩。四元数可以展开成一个 $3\times3$ 的旋转矩阵；平移和放缩也能装进矩阵。把所有东西放在一起，就形成一个 $3\times4$ 的**仿射矩阵（affine matrix）**。

为什么是 $3\times4$ 而不是 $4\times4$？表达平移时，我们要给 XYZ 额外补一个 1（齐次分量）。渲染里的投影矩阵算完 XYZW 之后，要把 X、Y、Z 分别除以 W 才能得到屏幕上的位置——那是透视变换才需要的步骤。但骨骼动画里的变换永远是仿射变换，**不存在除以 W 这一步**，矩阵底行 $(0,0,0,1)$ 根本用不上，干脆不存。

> **提示**：不要把骨骼的仿射矩阵和渲染的投影矩阵搞混——前者没有透视除法，底行恒为 $(0,0,0,1)$；后者必须除以 W。这是骨骼动画和透视投影在数学上的一个本质区别。

所以引擎里表达一个 joint，数据语言就是：旋转用四元数的四个分量 $(a,b,c,d)$，平移用 $\Delta(x,y,z)$，放缩用 $(s_x, s_y, s_z)$，合起来就是那个 $3\times4$ 仿射矩阵。这就是游戏里对骨骼、对顶点做运算的**核心数据系统**。到这里没有跟丢吧？这就是表达一个关节姿态最核心的矩阵。

### 动画数据为什么要存在局部坐标系

有了矩阵，下一个问题是怎么存。动画数据一般都存在每个关节自己的 **local space** 里——我只存它相对父关节的变化。直观原因很省钱：一个角色动起来的时候，很多骨骼其实没有任何动画，或者只有一点点旋转。

但更深层的是一个数学原理。假设动画数据全存在模型坐标系里，插值就会出大问题：第一帧我的胳膊在这个位置，第二帧胳膊到了那个位置，肘关节不动——你在模型坐标系里对两个关节的位置做插值，插出来的中间位置正好落在两点连成的直线上，和定住不动的肘关节凑在一起，骨头就一会儿变长、一会儿变短，看上去像一个被硬拉变形的三角形。而我们真正该插的，是这两个关节各自的 **rotation**：把旋转的插值逐级累积上去，你看到的就是骨骼绕着关节"定长"地转过去——这才符合人对运动的直觉。

> **结论**：动画系统用局部坐标系进行插值，背后有很深的数学原理——对位置插值会改变骨长，对旋转插值才是骨骼运动的正确表达。

### 顶点怎么跟着一根骨骼走：绑定恒等式与蒙皮矩阵

关节存的是 local space 的 pose，那么渲染时真正要求的，是每个关节在模型坐标系里应该长什么样——做法是从根节点开始，一根骨骼一根骨骼地叠乘上来。现在先看最简单的情形：**一个顶点只和一根骨骼关联**。

这里有个特别容易搞混的点：我的 joint 在这个位置，但跟它绑定的顶点在另一个位置——顶点和关节之间是有相对位移的。当这个 joint 自己发生平移、旋转时，我希望表皮上的 mesh 跟着动。这两者之间的数学映射，比大家想象的要复杂一点。

数学上这么看：绑定的时候（比如 A-pose 姿态），顶点在模型空间有个位置，记作 $V^{bind}$，上标用来标记它在哪个空间、哪个姿态下；同时，这个顶点相对绑定骨骼的局部坐标系也有一个位置，记作 $V^{BL}$。绑定关系要满足一个**恒等式**：只要绑定关系不变，无论这个 joint 在空间里怎么移动、怎么旋转，顶点在骨骼局部坐标系里"看上去"的位置，必须和绑定那一刻**严格一致**——不然就不叫绑定了。你可以想象绑定时刻在骨骼的局部标架中间钉了一个蓝点，骨骼动到第 $t$ 帧，新的点在骨骼两个局部坐标轴上的投影，和当初那个蓝点必须分毫不差。正因为这个恒等式成立，关节动的时候，表皮才会严丝合缝地跟着动。

把这个恒等式写成公式。任意关节在 $t$ 时刻的模型空间矩阵，是从根节点一路叠乘上来的；顶点新的模型空间位置就等于：

$$V^{new}_{model} = M_{pose}(t)\, M_{bind}^{-1}\, V^{bind}_{model}$$

这个推导不算难，建议大家自己动手推一遍——讲起来抽象，但说白了很简单：顶点绑定的时候有个位置，先乘上绑定关节仿射矩阵的**逆**，得到"我和关节的相对位置"；等关节在模型空间里发生了各种变化之后，把这个相对位置再乘上关节当前的变化，就得到顶点在模型空间里的新坐标。

其中 $M_{pose}(t) \cdot M_{bind}^{-1}$ 这个矩阵，就是大名鼎鼎的**蒙皮矩阵（skinning matrix）**，也有人直接叫它动画矩阵：给你模型上任何一个点，只要知道它绑定的是 032 号骨骼，你就找到 032 号骨骼的蒙皮矩阵，把原始 mesh 里的坐标 XYZ 乘上去，出来的就是骨架动过之后它的新位置。

> **易错点**：做这套运算时大家最常忘的，就是**把绑定的逆矩阵乘上去**。没有 $M_{bind}^{-1}$，整个推导都不成立。

落到引擎的数据结构上：每根骨骼除了存绑定时的时间位置、旋转（scale 一般是 1），还会**预先存好绑定矩阵的逆**。为什么？学过线性代数就知道，仿射矩阵的逆虽然相对好求，但求逆本身还是比较慢，所以提前把逆算好存起来；运行时拿"当前动画 pose 在模型空间的矩阵"乘上"预存的逆"，一步得到蒙皮矩阵。

接下来是工程上非常关键的一步：假设角色有 70 根骨骼，编号 0 到 69，把所有骨骼的蒙皮矩阵一圈算好，形成一个**矩阵表（matrix palette）**。为什么要先算成一张表？很简单：正式绘制时，一个角色身上的顶点可能有几万个，骨骼却只有几十根——绝不能每算一个顶点再回头去算骨骼应该怎么样，而是先把所有骨骼的蒙皮矩阵算好，顶点用的时候直接重用。而且接下来讲加权蒙皮时，每一个关节的矩阵会被访问非常非常多次，这件事就更重要了。

真正送进渲染时，蒙皮矩阵还要再左乘一个从模型坐标系到世界坐标系的变换，三个因子乘到一起：

```text
S_final = M_world x M_pose(t) x inverse(M_bind)
            |          |             |
            |          |             +-- 绑定姿态下该关节在模型空间的
            |          |                 transform 的逆（预计算，随骨骼存）
            |          +-- 当前动画 pose 下该关节在模型空间的 transform
            |              （从根节点沿骨架逐级叠乘得到）
            +-- 渲染时再左乘的模型→世界变换
```

读图：最外层是模型到世界的整体变换；中间是这根关节依赖的骨骼当前在模型空间的动画 pose；最右是绑定姿态下同一根骨骼在模型空间的 transform 的逆。三者的乘积，构成完整的蒙皮矩阵表。

> **结论**：做动画系统，其实就两个数学——第一，四元数要理解透；第二，这套矩阵怎么一步步运算过来要理解透。这两块吃透，你基本就可以动手写自己的动画系统了。

### 蒙皮：让多个关节一起拉扯一个顶点

前面解决的是"一个顶点绑一根骨骼"。所谓蒙皮动画（skinning animation），就是在这个基础上，让表面上的一个点**同时受多个 joint 影响**。它的原理非常简单：加权平均。

每个顶点可以和不止一个 joint 关联。关联数量原则上不设上限，但实践中我们一般**不超过 4 个**；并且，所有影响这个顶点的关节，权重加起来**必须等于 1**——不等于 1 就会出现很多很奇怪的变形。

有了权重，新位置怎么算？非常直觉：先相对 joint 1 算出顶点在模型空间的新坐标，再相对 joint 2 算出第二个坐标，两个坐标按一开始给的权重做平均，就是蒙皮后的位置。

这里有一个非常重要的细节：**这个加权平均必须发生在模型空间**，绝对不能在各 joint 的 local space 里做——每个 joint 的 local space 都不一样。比如小臂的 twist 效果：joint 1 转过一个角度，joint 2 又多转了一些，表皮上的一个顶点先用 joint 1 的矩阵算出一个模型空间位置，再用 joint 2 的矩阵算出另一个，两者按权重一混，就是我们想要的扭转效果。你要是在 local space 里做这件事——肯定完蛋，根本插不出来。

> **易错点**：做真正的蒙皮动画时，顶点的加权混合一定要在模型坐标里做完，千万不能放到 local space 里做，一做就错。

### 旋转插值：NLERP、最短路径与 SLERP

把一帧帧 pose 连在一起，动画里叫做一个 **clip**（动画剪辑，也有人叫动画资产）——一个走路的 clip、一个跳跃的 clip、一个跑步的 clip。clip 一般每秒只存 15 帧、20 帧这样的密度，但我们的游戏现在跑的是 60 帧、120 帧，所以渲染时必须在两个 pose 之间**插值**，动画才能平滑。

平移和 scale 好办，用线性插值基本都能看。复杂的是旋转。设第一帧某关节的朝向是四元数 $q_1$，第二帧是 $q_2$，最简单的做法是线性插值再加归一化：

$$q(t) = \mathrm{normalize}\big((1-t)\,q_1 + t\,q_2\big)$$

这就是 **NLERP**（normalized LERP）。这里要感叹一下四元数的好：如果给你的是欧拉角，或者两个表达旋转的矩阵，问它们之间怎么插值——那个计算非常麻烦。哈密尔顿几乎给出了我们这个行业旋转插值的**唯一解**。

NLERP 有一个必须处理的细节：**最短路径原则**。两个旋转之间插值，按人的直觉要走球面上最短的那条路——就像从北京到新疆，直飞过去就是最短路径；你要是从北京往美国飞，沿太平洋、大西洋绕过整个欧洲再从亚欧大陆撞回来，虽然最后也能到新疆，但完全不符合人的直觉。实现上就是一个小运算：算 $q_1 \cdot q_2$（点积），大于 0 说明夹角小于 180 度，直接插；小于 0 说明夹角超过 180 度，把其中一个四元数取反再插。不做这个处理，角色的关节会在某些时刻突然做个翻转；做了，看上去就自然多了。我们的小引擎里已经做了这个处理。

但即便做了最短路径，NLERP 还有个小毛病：它在角度空间里的插值速度**不均匀**——插值参数从 0 匀速变到 1，转过的角度却不是匀速的，两端慢、中间快。对质量要求很高的动画，看上去就有点不自然。所以现在的 3A 游戏提出了 **SLERP**（球面插值）：用反余弦把两个旋转之间的夹角 $\theta$ 找出来，再按 $\theta$ 的比例均匀地插：

$$\theta = \arccos(q_1 \cdot q_2), \qquad q(t) = \frac{\sin\big((1-t)\,\theta\big)}{\sin\theta}\,q_1 + \frac{\sin(t\,\theta)}{\sin\theta}\,q_2$$

SLERP 效果好，但有两个代价：第一，反三角函数运算很费——计算机里算这类函数要查表，不可能实时真算；第二，当 $\theta$ 非常小时，$\sin\theta$ 做分母，插值在数值上是不稳定的。

所以游戏实践里的一般做法是给定一个 **magic number**（阈值）：两个旋转的夹角很小，就不折腾了，直接用最简单的 NLERP；夹角比较大，才用 SLERP。两个方法都不难，同学们自己写引擎的时候，我建议就按这个混合方案实现，基本能达到现代引擎的效果。我们的小引擎目前只用了 NLERP——后面说不定会出个作业，让大家亲手写一个 SLERP，写完你对四元数和整个动画运算的理解会上一个台阶。

| 插值方法 | 计算方式 | 效果与代价 | 适用场景 |
| :--- | :--- | :--- | :--- |
| NLERP | 线性混合 + 归一化，非常便宜 | 角速度不均匀，两端慢中间快 | 夹角小、对质量要求一般的场合 |
| SLERP | 需要 arccos（查表），较贵 | 角速度均匀，质量高；小角度数值不稳 | 夹角大、质量要求高的动画 |

### 一帧动画在引擎里的运行时管线

把前面所有部件串起来，就是一个最简单的动画 runtime 管线：

```text
动画 clips（走路 / 跳跃 / 跑步，每个 clip 存着一串 pose）
   |  按"当前帧 + 下一帧"采样（frame 和 pose 的概念很相似）
   v
姿态插值（平移 / scale 用 LERP，旋转用 NLERP / SLERP）
   |  得到骨架本帧真正的 local space pose
   v
从根节点逐级叠乘，把局部姿态换算到模型空间
   |
   v
逐骨骼计算蒙皮矩阵，组成蒙皮矩阵表（matrix palette）
   |
   |     - - - - 传统引擎的 CPU / GPU 分界线 - - - -
   v
GPU（vertex shader）：逐顶点取蒙皮矩阵，
     几千到上万个蒙皮顶点 x 几十到上百根骨骼的矩阵，
     真正让角色活灵活现地动起来
```

读这张图：CPU 侧负责从 clip 采样、插值、把 pose 换到模型空间、算出每根骨骼的蒙皮矩阵；到了蒙皮矩阵表这一步，传统游戏引擎会把前面的活全在 CPU 上干完，后面的逐顶点蒙皮交给 GPU，在 vertex shader 里完成——带蒙皮的顶点每个都要去查这几十到上百根骨骼的矩阵表。

但现在大家讲 **GPU driven**：主流 3A 游戏里，前面那部分运算也越来越多地直接放进 GPU 去算——CPU 算这些实在没有必要。到这一步，你的游戏基本就可以去做了。不过，真实游戏里还有一个绕不开的技术：**动画压缩**。

### 动画数据有多大：为什么必须压缩

很多人觉得动画数据不大，其实不然。算笔账：以《英雄联盟》——大家口中的"撸啊撸"——为例，100 多个英雄，每个英雄大概 5 到 10 秒的动画，每秒存 30 帧，每帧每个关节要存平移、放缩、旋转三套数据——加在一起，光这一个简单 case，动画数据量就将近两到三个 GB。现在的 3A 游戏只会更大：一个角色 70 个关节，每个关节每秒 30 个 pose，每个 pose 都带着平移、旋转、放缩，数据量非常大。

但你仔细观察动画数据，会发现很有意思的特点：

- 对同一个 joint，很多数据**根本不变**：大部分骨骼的放缩是常数 1；大部分骨骼在 local space 下的位移也不变——只要骨头不打断，两个 joint 之间就一直连着；
- 大量数据其实是 **rotation**，而且 rotation 的变化在不同骨骼上极不均匀：人走路时手指头不会一边走一边捏来捏去，手上十几根指骨几乎没有旋转动画；上臂有一些，但幅度很小；大腿则是整块抬起来、放下去，数据变化就大得多。

摸清这些性质，降低数据量的思路就出来了。

### 关键帧约减与 Catmull-Rom 曲线

第一步最粗暴：**不变的 track 直接干掉**。scale 整条砍掉；translation 不用沿时间轴存一串，只存一个值就完事了。哪些骨骼完全没有位移变化，很快就能自动识别出来。这是非常常用的一招。

第二步，对 rotation 引入一个关键概念：**关键帧（keyframe）**。整个运动信号，可以用少量关键帧"拉"出来，关键帧之间靠插值还原。怎么挑关键帧？从时间 0 选取第一个关键帧，依次往前走，走过的相邻点之间做线性插值；一旦原始数值和插值出来的数值之间的误差超过阈值，就把当前点退回来，把上一个点输出为关键帧，再以它为起点继续往前插——**永远保证 error 小于阈值**。这样，几百帧的动画就能变成几十个关键帧连成的动画。

> **注意**：关键帧和关键帧之间的时间间距是**不均等**的，间距取决于信号在时间轴上变化的快慢——变化剧烈的地方关键帧密，平缓的地方稀。

但线性插值对旋转数据其实不太合身。观察真实数据：关节的旋转（即使表达成四元数）很多时候是一条**光滑的弧线**，用线性插值去逼近，误差会很大，得塞很多关键帧；线性插值的好处只有一条——runtime 时计算非常简单。这就引出了大名鼎鼎的 **Catmull-Rom 曲线**：一个非常经典的多项式曲线，基本是三阶的，有个参数 $\alpha$ 叫"锐度"，一般只用 $\alpha = 0.5$。给定任意两个点 $P_1$、$P_2$，从 $P_1$ 往外延拖出 $P_0$、从 $P_2$ 往前拖出 $P_3$，就能定义一条 C0、C1 连续的多项式曲线，非常光滑、好看。这是一个被研究得非常透（well-studied）的经典问题，今天不展开推导——但你以后做任何一个东西，几乎都要用到 Catmull-Rom 曲线。

有了 Catmull-Rom 曲线，去逼近真实的 rotation 信号，所需的**关键帧数量会少很多**，插值精度也更好控制。整个过程都是**离线计算**的，不用担心复杂度；到实时运行时，你看到的只是控制点，最多拿 4 个点的数据、做一次多项式求值，就能把值插出来。

### 定点数与四元数的 48 位压缩

曲线之外，数值本身也别傻乎乎地全存浮点数。浮点数 32 位，存储压力很大。有个很简单的办法：如果知道一个数值的范围（比如 $-50$ 到 $120$），就把这个区间归一化到 $[0,1]$ 上，区间里任何一个数值都用 16 位整数来表达——精度可以达到 0.01 甚至更细，对很多数值表达来说已经够了。

四元数的定点化更巧妙，用到了它一个非常有意思的数学性质：归一化的四元数，每个分量都在 $[-1,1]$ 之间波动；但把**最大的那个分量扔掉**之后，剩下三个分量**一定都小于 $\frac{\sqrt{2}}{2}$**。

> **定义**：四元数压缩——用 2 个 bit 记录"哪个分量是最大值"，剩下的三个分量各用约 15 bit 存下来；解压时利用"四个分量的平方和等于 1"，把被扔掉的最大分量反解回来，整个四元数就完整还原了。

算一笔账：不压缩的做法是存 4 个 float，一个 float 4 个字节，一共 16 个字节；用上面的方法，一个四元数只要 48 个 bit，也就是 6 个字节——省掉了六成多的空间。所以工业上压缩四元数，绝不是傻存四个 float。

动画数据压缩，对所有引擎都是非常重要的东西：做真正实战的游戏引擎，动画数据一定要压缩。我们的小引擎（Piccolo）因为时间紧张、不想搞得太复杂，数据没有压缩——但你要把它改成实战级，一定要把压缩算法加进去。

### 压缩的代价：误差会沿着骨架传播

压缩不是免费的。每个关节的动画压缩时，都把 error 控制住了，但动画是从一个关节传递到下一个关节的——很自然地想一想：这个 error 会不会一直传播（propagation）下去？会。前面几根骨骼看，error 还可以；但从骨盆一路传到手指尖，error 就大得有点离谱了。

后果是什么？大家想想武器挂在哪——挂在手上。动画压缩没做好的话，压缩完的动画里，你手上的武器会一直在那儿抖啊抖。最糟糕的情况是长柄武器。我印象特别深：以前做《光环》（Halo）的时候，第一版动画压缩就是我做的——那个大块头拿一根很长的武器，跳起来往地上一砸，砸到地上那一刻就开始"噔噔噔噔"地抖，跟触电了一样，特别明显；他另一只手还抓着柄，那个柄和手一直错开，一直浮空。这就是压缩没做好。所以要意识到：**不同的骨骼，对 error 的敏感度是完全不一样的**。

那 error 怎么定义？

- 最简单的做法：直接量每个关节四元数、平移、旋转各自的误差。最简单，但**不符合人的认知（perception）**——动画压缩本质上希望的是"在人的认知上不产生差距"。
- 行业里真正最关注的是 **visual error**，视觉上的误差。最粗暴的做法：把模型上所有的点，压缩前后逐帧比较，算像素级的差距。大家想想这事怎么算——那么多动画、每一帧、几万个顶点，这不要死人吗？
- 实用的做法：在每个关节上定义**两个垂直的探针点**，给出一定的 offset。特别敏感的关节，offset 给大一点；小骨骼、不重要的骨骼，offset 给小一点。用这套点就能定量估计压缩前后，整个 skeleton 的 error 到底产生了多少——比较两个压缩算法的好坏，用的也是这个方法。

还要坦白一句：今天讲的是最简单的压缩算法，动画压缩在现代游戏引擎里是一个非常重要的研究领域，到现在我也认为它没有被解决得非常好。

有一个听起来非常有道理、实际会翻车的思路：**误差补偿**。既然 error 会沿骨架一路传递，那上一根骨骼压缩产生了 error，下一根 joint 能不能反向补偿它？这很像控制系统里的误差补偿原理。但你真去做就会发现：末端骨骼原来的动画数据是非常平滑的低频信号；为了补偿上面五六七根骨骼传过来的 error——每根骨骼的频率不一样，这些频率压缩后产生的 error 会依次叠加——结果在末端骨骼上产生**非常高频**的数据。第一个效果是末端骨骼的压缩质量很差，第二个是产生很多奇怪的高频抖动：动作幅度不大，但看着就是怪。现在有些前沿方法，会把部分末端骨骼单独存成模型坐标系下的 track，涉及 forward 和 inverse kinematics 结合的方法——今天时间不够，不展开了。

所以给将来做商业级引擎的同学一句告诫：第一，数据一定要压缩；第二，只要压得不好、或者方法选得不对，一定会产生很多奇怪的 error——到时候 artist 来找你，你会把头发抓破，想到底哪一步做错了。

### 一段动画的完整生产线

最后轻松一点，讲讲一段动画到底是怎么被做出来的。整条生产线长这样：

```text
高精度 mesh --取低模--> low poly mesh（关节处额外加几圈网格）
      |
      v
搭建骨架（3ds Max / Maya 有现成 biped 骨架）
      |  对上 A-pose / T-pose 的角色
      |  + gameplay joint（武器骨骼等）
      |  + pelvis 和 root 连到底部的骨骼（很多工具要自己加）
      v
蒙皮（skinning）：auto skinning 自动算权重
      |  自动结果像橡皮糖 -> 动画师手动校正
      |  权重像 paint 一样"刷"上去，颜色 = 骨骼对顶点的影响权重
      v
动画师 K 帧：只做关键帧 + 关键帧间隔（不是一秒画 30 帧）
      |
      v
导出（引擎程序员写导出工具；root 位移单独导成位移曲线）
      |
      v
FBX 等文件格式 -> 游戏引擎
```

几个环节展开说说。

美术构建 mesh 时用的都是高精度模型，但那种非常高精度的 mesh 做动画、做蒙皮非常麻烦，所以我们一般用 **low poly mesh** 去做动画。这里有个细节：为了保证动画效果，动画师会在很多关节的地方**额外加几圈 mesh**，保证动的时候那里不变形。你们将来做引擎程序员就会看到，角色模型在不少关键部位——比如手肘（elbow）——会多出一圈一圈的网格，就是这么来的，这个非常重要。

接下来搭骨架。现代工具已经非常发达，3ds Max、Maya 都有现成的 biped 骨架：artist 做好 A-pose 或 T-pose 的角色，直接在工具里拉出一副骨架，一根一根对上，就得到一副和 mesh 匹配的绑定 skeleton。然后还要加一些 **gameplay joint**，比如武器的骨骼；再加上 pelvis 和 root 连到底部的骨骼——很多工具里，这些骨骼需要你自己加。

再往下是最神奇的部分：**skinning**。现在很多工具会自动算蒙皮权重（auto skinning）；基于深度学习的自动蒙皮，也是当前引擎算法里很热门的研究方向。最简单的自动蒙皮，3ds Max、Maya 已经算得非常好了，但算出来的效果会让角色看起来像橡皮糖一样软，所以 artist 需要手动校正：这个关节点应该在哪、这一带的权重不要传得太厉害，等等。比起以前，这已经快了非常非常多。我一直爱用一个词——**paint**：看动画师调权重的时候，真的就像画颜色一样，五颜六色的，那个颜色代表的就是每一根骨骼对该顶点影响的权重。

然后 animator 开始做动画。核心思想和前面讲过的 Live2D 很像：他**不会**一秒钟做 30 帧——那样不得了，动画师就下不了班了——他只做关键帧，设置每个关键帧之间的时间间隔，做好了角色就能动起来。

这时候引擎程序员该干什么？写**导出工具**。这里有个细节：大部分动画直接导出就行；但如果 root（比如 pelvis）本身发生了位移——典型如跳跃动作，root 一直在变——root 的动画一般不按关节动画存，而是**单独导成一条位移曲线**，交给引擎用。写引擎的时候，一定要注意这个小细节。

到这里，一个完整的动画系统就实现了。数据最后变成各种各样的文件格式——FBX 就是我们常用的格式。你今天在现代游戏里看到的各种 3C 动画、各种精确的表达，万变不离其宗，都是用刚才这一整套技术做出来的。说真的，很难想象：用四元数、用矩阵、用各种插值、用 Catmull-Rom 这些数据变换，最后能让电脑表达出这么 fancy 的、动起来的现代游戏世界。所以我认为，**动画系统是几乎所有想做引擎、想做 gameplay、想做游戏设计的同学都必须理解的系统**。

### 课堂问答

#### 一个顶点最多能绑几根骨骼？

原则上没有限制，你绑 50 个关节也行；但实践中一般**不超过 4 个**——绑太多，每个顶点的计算量非常大，每个顶点都要算一遍，太费了。另外，一个角色的关节总数一般也会控制，比如**最多不超过 255 个**：0 到 255 正好用一个 byte（8 bit）表达，每个顶点都要存绑定关节的 joint index，一个字节就能存下，存储和数据访问的效率都会高很多。

#### 骨骼动画怎么和场景碰撞？

这个问题有点难，而且答案和直觉不太一样：**不是拿骨骼去和场景算**。骨骼动起来后我们看到的蒙皮表面，只是一个 visual 的东西；真正和场景互动的是**刚体（rigid body）**——这属于物理系统，物理那一部分会专门讲。比如人身上 75 个关节、一直到小手指，但做物理的时候只挑其中十几根骨骼，绑上简简单单的圆柱或方块，这些形状就可以和静态场景发生碰撞。拿刀砍下去这个动作：武器所在的关节上绑了 rigid body，砍到墙上时算出交点在哪里，沿着切割的轨道生成火星。很多游戏里，角色一拳打出去、前面有个东西，这一拳会停下来，甚至切成另一个动画——靠的不是 skinning matrix，而是 rigid body：一个 100 个 pose 的攻击 clip，放到第 16 个 pose 撞上了东西，立马切到"攻击失败、手很疼"的另一个 clip。这是用另外一套系统解决这个问题。

#### Morph target 动画和蒙皮动画的区别？

两个方法差别蛮大。**蒙皮动画**核心动的是 joint（骨骼），一根骨骼可以驱动几十甚至上百个顶点，顶点上**不存**动画数据；**morph target 动画**存的直接是**顶点的位置**——每一组顶点位置就是一个 keyframe，顶点在 KF1、KF2 之间做插值。所以 morph target 动画更像前面讲过的 vertex animation（顶点动画）。下一讲讲人脸怎么做、表情怎么做的时候会讲得很清楚——特别是大家特别喜欢的捏脸系统。

## 让角色行云流水：动画混合、状态机、动画树与 IK
> 对应块：BLK18 | 覆盖分集：P11上 | 块标题（分集名）：《第九节：高级动画技术：动画树、IK和表情动画》

上节课大家花了很长时间听我讲绕来绕去的四元数，讲了一大堆公式——不过说实话，这些公式比渲染还是少很多了。我们终于搞明白了：给了一组骨骼，怎么让它动起来；骨骼动起来之后，蒙皮网格怎么像人的皮肤一样，跟着骨骼一起动。但我们学了那么多，其实还只是一个**基础的动画浏览**。

今天这节课，我要跟大家讲一些**高级的动画技术**——这些技术是现代游戏引擎里最实战的一些技术。大家准备好冒险了吗？

先想一想这个问题：我们已经知道动画在 DCC 里怎么做、引擎怎么把它导进来、怎么做蒙皮动画，还知道什么叫动画 pipeline——看上去一切了然于心了。可如果我用 DCC 生成了几十个、上百个甚至上千个动画，那它就是一个一个孤立的动画。为什么今天我们玩起现在的游戏，角色的动画行云流水，你看不出它是动画 A、动画 B、动画 C，好像完全自然地连接在一起了？

这件事是怎么发生的？这就是今天要讲的重点：当我们有了所有的动画算法、所有的动画素材之后，怎么让我们游戏里的角色，真的按照我的意愿活灵活现起来。

### 动画 Blending：从走路到跑步的无极变速

第一趴叫动画 blending。当我有几百上千个动画素材——我们叫 clips——的时候，游戏引擎不是依次去播放它、或者随机去播放它，而是要把很多动画素材按照一定的规则、根据我的 gameplay 混合（blend）在一起。**动画 blending 是动画系统最重要的一个底层系统。**

举个最简单的例子，还是我们小引擎的那个角色。我们做了一个它走的动画，假设速度是 1.5 米每秒；再做一个它跑的动画，3 米每秒。现在这个角色要从走逐渐到跑，从 1.5 米每秒慢慢加到 3 米每秒，中间怎么过渡？我们不可能为每一个速度都做一遍动画——学到 GAMES104 这里的同学都知道，游戏引擎绝对不会这么傻，我们多聪明啊。

那如果只设一个速度阈值，到了就硬切呢？你会看到一个很明显的切换跳变——我们肯定也不会那么傻。所以大家一定会一拍脑袋：那还不简单，做线性插值（lerp）嘛。对，这就是你要的结果：一个从走到跑非常 smooth 的 transition。

这其实就是动画 blending 最基础的原理，也是最经典的案例——**为什么动画要做 blending？因为我们要无极变速。**

> **定义**：动画 blending，就是把多个动画 clip 按权重混合成一个 pose，让角色的动作随游戏状态连续变化。

Blending 具体怎么做？上节课基本已经讲清楚了，就是 lerp：对每一个 joint 的平移、放缩、旋转做插值——特别是旋转，因为骨骼上旋转是最多的。四元数你可以用 NLERP，可以用 SLERP，whatever lerp，反正就是可以做线性插值。

但有一点一定要分清楚：上节课讲的插值，是在**一个动画 clip 内部**、帧与帧之间插值；而 blending 的插值，是**在不同的动画之间**插值——比如在"走"和"跑"里各取一帧来插。所有的动画 blending，都是在多个 clips 之间进行的。插值算法本身，上过上一节课的同学应该都会写了，这里不赘述。

那两边的权重怎么算？方法非常直觉：既然是因为移动速度发生了变化，我就用**速度作为自变量**，推导权重的变化。假设走路速度是 $\text{speed}_1$、跑步速度是 $\text{speed}_2$，根据当前速度，我就能算出走路动画的权重 $w_1$ 和跑步动画的权重 $w_2$，只要保证：

$$w_1 + w_2 = 1$$

速度越来越快，权重就在 0 到 1 之间过渡——你靠近哪个信号，哪个动画的权重就重一点。这很直觉，大家肯定觉得"这个我也会"。

### 循环动画必须对好节拍

接下来这一趴，是做 blending 时特别容易忽视的问题。

能做这种插值的动画，很多时候我们希望它是**循环的**。大家想一想：走路和跑步，步频是不是不一样的？跑的时候步子又快又大，走的时候步频相对慢——这两个动画之间实际上是**并不同步**的。那你插值的时候，该用跑的哪一帧、走的哪一帧？这是动画 blending 系统里最基本的问题，但一开始做的时候，你很难意识到。

所以我们会要求动画师：做循环动画的时候，无论这个循环做多长，首先它必须是循环的；而且，假设走路动画是左右脚各迈一次，那跑步动画也得是左右脚各迈一次；两个动画脚落地的时间，最好大致一致——也就是把两个循环动画的时间轴对齐（timeline alignment）。对齐之后，插值才能保证这样的节拍：t 为 0 的时候，双脚都没抬；0.25 的时候，左脚踢到空中；0.5 的时候，左脚落下来；0.75 的时候，右脚踢到空中；1.0 的时候，右脚落下来，重新开始。

**Timeline alignment 是很多动画能够 blend 的一个基础。**

> **易错点**：blending 直觉上非常简单、非常好理解，但如果你对这些基础概念理解得不够准确，特别容易写出各种各样的 bug——timeline 对齐做不好，或者速度和两边的权重没有形成合理的关系、角色推进的步进速度也没有配合，你会发现这个人走路在地上 ice skating，脚在地上滑步。游戏中的滑步，是一个我们一定要解决的问题。

有了这样一个非常简单的算法，你就完成了一个最简单的 animation blending 系统，可以得到任何一个无极变速的动画表现。看到这里，我相信很多同学都会想："我懂了，原来高端游戏就是这么做的？就这么简单啊。"——确实就这么简单，比如我们的小引擎里好像已经实现了一个最简单的 blending。但它离真正游戏引擎的全套动画系统还差得很远，不过，这是一切的基础。

### Blend Space：一维与二维的动画采样空间

Blending 实际上是由一个自变量左右控制的。接下来讲一个有意思的事情：假设我的角色有一个向前走的动画、一个向左走的动画、还有一个向右走的动画。大家想想，玩游戏的时候这个角色是不是受我控制，一会儿左一会儿右？按照前面那一趴的思想，我是不是可以让这个轴在左右之间自由地插值，在三个动画中选一个百分比？这个插值空间，就叫**一维的 blend space**。

这里注意一个细节：刚才"走"和"跑"只有两个动画，我们只在两点之间插值；现在把它 general 化——虽然还是一维插值，采样点不是两个了，是三个。那能不能再加四个、再加五个？比如往左边慢移动、往左边快移动、站在中间直接往前走、往右边慢移动、往右边快移动，五个采样动画，是不是也一样？

所以一维 blend space 有两个自由度：**我们并不规定采样点（clip）的总数，也不要求这些 clip 在这个轴上均匀分布**——它可以有时候密一点、有时候疏一点。比如人正常走的时候，动作变化不大；但一旦开始侧移，动作会发生很大的变化，很可能在一个很小的速度，我就要切换成另一个动画了；而往更快的速度侧移时，动作变化又没那么大，直到发生显著的变化，我再切换到第三个动画。

那同学们肯定会说：你这个做得不完整。我往前走可以快可以慢，往左走一样可以快可以慢，我甚至可以往斜方向走，怎么办？——很自然，我们需要**二维的 blend space**：最下面那个点是 idle，站在原地不动；沿一个轴往前走是 walk，再往前就是 run；左前方走、左前方跑、右前方走、右前方跑——整个角色的动画就会完全不一样。这样就得到了一个二维的采样空间，**采样空间里的每一个采样点，就是一个动画素材**，我们用它来表达这个角色的整个动画行为。

> **注意**：blend space 里的所有 clips，要么全部循环，要么全部不循环（一次性播完就结束）。一部分循环、一部分不循环，会产生很多很奇怪的东西。

这里动画师要出场了。动画师是观察生活非常细腻的人，他会告诉我们的游戏引擎程序员：我们发现一个细节——这个人从走到跑，如果加上横侧向移动，他会很快进入一个侧向跑的状态。因为侧向跑的时候，人身体很难保持平衡，所以速度只要超过一个简单的阈值，他就必须切换到跑的动画，否则看上去很不真实。这个东西讲起来很细节，但如果你们以后跟动画师团队合作，会发现他们对人的肢体行为变化，是非常非常敏感的。这就回到了刚才那个概念：动画素材在采样空间上的分布其实是不均匀的，动画师觉得哪里需要更细腻的表达，就在那里再加一个 clip。那作为引擎程序员怎么办？好吧，随便你怎么放，我都理解了——接下来就是选插值的方法。

但你看，现在有这么多动画了，大概七八个。难道每次 blending 要把七八个动画全部 blend 在一起、算它们的平均权重？那计算机是比较费的：每一个动画 clip 都要先算出它当前这一帧的 pose，再把七八个 pose 放在一起 blending，计算量会非常大。

这时候我们发现了一个规律：用 **Delaunay 三角化**。这是个数学方法，大家有兴趣可以去查一下，其实非常简单：给你一堆二维空间的点，我根据这些顶点，生成这个空间的三角形划分（这个算法在三维也可以做，但三维好像比较复杂，二维的话算法比较简单）。于是，你现在在任何一个速度、任何一个方向上，都确定了二维空间里一个唯一的点；我就选它所在三角形的三个顶点——也就是临近的三个动画 clips——用**重心坐标**（barycentric，前面反复讲过的那个方法）在这三个 clips 之间插值。

这就是一个完整的 2D blend space 的实现。

Blend space 在游戏引擎早期，非常好地解决了一个问题：艺术家只需要做几个角色行为的动画，但我们在整个游戏引擎里，可以实现非常丝滑的角色运动。我们的小引擎现在 blend space 还没有实现——说不定我们会把它作为小引擎的一个作业，先不剧透，我只是说这是一个非常好的做作业练习的东西。因为你会发现，奇迹就会发生：你本来看到的是一堆很离散的动画，但有了 blend space，你用摇杆去控制它，无论什么速度、无论什么朝向，这个角色的行为看上去都很舒服、很 smooth。

Blend space 是实时动画处理中非常核心、也非常基本的一个数据单元。现在很多游戏号称自己是 data-driven 的、是 Motion Matching 的动画——但实际上，blend space 还是一个非常基本的元素，很多地方都要用到它。

### 骨骼遮罩混合：上半身鼓掌，下半身随便动

再讲一种 blending。我们的小机器人特别喜欢大家，很欢迎大家来跟它玩，它要鼓掌。但我们的小机器人有很多 pose：它可能一会儿站在这儿，可能蹲在那儿——大家觉得这个小机器人很可爱——它甚至可能在走。这种情况下，我们还希望给它混合一个鼓掌的动画。可是鼓掌的动画，我不可能为每个姿势都做一个，我可能只能做上半身，但下半身的行为又会不一样。怎么办？

我相信聪明的同学们很快就能想到：很简单，我们对 skeleton 做一个 **mask**（遮罩）。有些动画只 apply 到上半身，有些动画只 apply 到下半身——比如下半身 apply 一个"这个人蹲在那儿"的动画，上半身 apply 一个鼓掌的动画。

这样做有两个好处：因为只有这一部分 joints 参与了这个动画，动画的数据量变得更小；而且因为有 mask，apply 到 skeleton 的时候只拍到一半的骨骼，计算量也下降很多。这个时候我就可以自由地把两种、甚至更多的动画，在同一个角色身上进行混合。这也是一种 blending——**skeleton mask blending**。

有了这样的方法，你就可以看到这样的效果：小机器人无论是什么造型、无论在什么位置，都在鼓掌欢迎我们。这也是我觉得非常好的一个小引擎的作业，大家可以拿这个效果来做作业。

### 加法混合：在任意姿态上叠一层

最后一种 blending。假设我们对这个小机器人提出更高的要求：你不仅要对我鼓掌，你还要向我点头示意。这里有一个引擎的要求：你要**向着我**点头——鼓掌你比划着怎么都行，但头，我们希望机器人始终朝着我。假设我做了向前点头、向左点头、向右点头三个动画，那我要让他有各种坐姿，手在不停地鼓，而且还希望他的头看着我不停地点。怎么做？

这里就有一个很重要的 blending，叫做 **additive blending**。意思是：这个动画不仅只作用到 skeleton 的局部，而且它只存动画的**变化量**，不存绝对量。这样，无论你的 skeleton 已经被处理成什么样的结果，我在这个结果之上，再加一个额外的旋转（rotation）、平移（translation）或者缩放（scale），就等于在上面又 apply 了一层动画。有了这个技术，你就可以实现这样的效果——很多机器人冲着你点头了。

到这里，blending 的主力就齐了：第一种是非常简单的 lerp，线性插值，全身的；第二种是 mask blending，只对局部骨骼进行 blending；第三种是 additive blending——你们的 blending 全部做完了之后，我再在上面加一个修饰、加一个差分量。再加上前面一维、二维 blend space 那套线性、双线性、三角形重心插值，这四样基本上就是游戏引擎里 blending 最主体的东西。

| 混合方式 | 作用范围 | 存的是什么 | 典型场景 |
| :--- | :--- | :--- | :--- |
| 线性插值 / Blend Space | 全身 | 动画的绝对姿态 | 走到跑的无极变速 |
| Skeleton Mask | 遮罩内的局部骨骼 | 绝对姿态，只 apply 到一半骨骼 | 下半身走路 + 上半身鼓掌 |
| Additive | 叠加在混合结果之上 | 变化量（offset） | 任意姿态上点头 |

有了这些东西，你就可以把那几百个上千个动画，按照你想要的方法各种叠加在一起，根据你的 gameplay——这其实已经可以做一些简单的小游戏了。如果你这时候不在乎引擎是真的给 artist 用的、自己直接拿来做游戏，有了这四个算法，基本够用了。

但这里面要讲一个细节：additive blending 如果做得不好，特别容易产生各种我们称之为 broken case 的情况。比如说，这个角色本身做了一个转身的动作，他的脖子已经扭了；然后你再给他加上一个扭头看别人的动作——他的脖子可能就超过了旋转的上限，这个时候这个角色看上去就非常不自然。所以 additive blending 一般做起来要非常谨慎，而且在后面规划角色运动的时候，我们会非常有意识地避免过度叠加这些动画，因为它会让有些 joint 的行为非常异常。

到这里，blending 这一套基本讲完了。但是，我们的引擎设计师是不满足的。为什么？因为我们的目标是要做**工具**，不是做算法。工具的目标是什么？是把它变成可以交给我们的设计师、交给我们的艺术家、能够自由地构建他的世界的东西。所以我们对动画的表达，会希望有一种更可视化的、更形式化的方式。这里就要介绍一个大名鼎鼎的概念——**动画状态机**（Animation State Machine，ASM）。这个词我在幻灯片上还拼错了，不好意思；反正一般大家都直接叫它 state machine，状态机。

### 动画状态机：一个跳跃为什么拆成三段动画

为什么状态机在动画中很重要？因为刚才我们只讲了 blending，但实际上动画系统里，很多时候是**状态在切换**的。

举一个非常简单的例子。大家还记得上节课讲的：一个角色跳起来的动画，我们要把它的**位移去掉**。为什么？因为在游戏中，这个角色跳多高、包括多久能落地，都不是动画能作主的。大家想象一下：我站在一个斜坡上、站在一个台阶上，从台阶上往下跳——虽然我跳起的高度是一定的，但这个台阶有多深我并不知道，所以我并不知道什么时候落地。

所以一般我们会把一个跳跃做成三个动画：第一个是**起跳**（jump start）；第二个是**空中的 loop**——你在空中浮空的时候，很优雅地把腿啊、手啊摆来摆去："我现在飞在空中，I believe I can fly"；最后一个就是"我的天，我要快落地了"——**落地**（landing）动画。

这个时候你会发现，你没有办法用 blending 去解决它了——因为它不是个 blending 的问题，它是一个**彼此依赖的状态切换**的问题。当我决定按下一个按钮——Xbox 上经常按的是 A 键，PS 是圈——我播放这个角色起跳；起跳动作播完之后，我就要切到空中的 loop。为什么是播完就切？因为那个时候，他向上还有惯性，还在往上走；但他下面是地面还是悬崖，我并不知道——如果下面是一个无尽的悬崖，他就会一直"啊啊啊"那样摆下去。然后，当他快落地的时候——注意，这里面其实有个很讲究的东西：我**不是**在落地那一瞬间才播放落地的动画，一般是**快落地的时候**，我会让这个角色做出一种紧张的姿势，准备落地，然后播放落地动画。当然，如果不那么讲究，也可以是检测它的位置到地面的距离，到值了，就播放一个"用脚去削减势能"的动作。Anyway，这都可以。

你会发现，它是**在三个状态里有序地切换**的——而这，就是一个非常经典的状态机要求。

```text
        按 A 键起跳          起跳动作播完（仍有向上的惯性）
 [idle] ──────────► [jump_start] ──────────► [jump_loop]
    ▲                                               │
    │                                  快落地时先摆出紧张的姿势
    │                                               ▼
    └─────────────────────────────────────────── [landing]
```

读图：`jump_loop` 在空中一直循环播放——因为你不知道脚下是地面还是无尽悬崖；直到检测到快落地，才切进 `landing`，播完后回到 `idle`。

### 状态机的两个核心元素

那我们就需要正式定义动画状态机了。动画状态机一般有两种核心元素。

第一种核心元素是**节点**（node / state）。动画的 clip——原来的原始动画素材——就是它的节点。其实你还可以把一整个 blend space 打包成一个节点，比如刚才讲的前后左右混在一起的那个；你甚至可以把一个动画蓝图都放进去做节点——这里我借用 Unreal 的概念。它非常灵活，但**最终产出的一定是一个动画，就是一个 pose**。

第二种核心元素是**切换**（transition）：当满足了一定条件之后，它会自动地从状态 A 切到状态 B。

回到刚才的案例，这就是一个最简单的状态机：从 idle 开始，收到玩家跳起来的输入，就进入 jump：先是 jump start，到高点之后 jump start 停掉，变成 jump loop；jump loop 一直循环，直到"我要落地了"，状态切换到 landing；landing 要把自己播完之后，才能回到 idle。只有这样的一个系统，角色的行为看上去才是自然的。

Transition 其实就比较复杂了。我这里给出一个最简单的定义：你只需要知道它的起点是谁、终点是谁。那中间要不要做插值呢？如果要，从动画 A 切到 B 就不要"啪"一下马上过来，中间有一个 blending 的过程，比如 0.2 秒、0.3 秒——0.2 秒是我以前经常用的一个 magic number，我也不知道为什么很多 artist 都喜欢填 0.2 秒，好像这个数字看上去就那么舒服。

但其实真正复杂的是什么？是这个 transition **在什么时候激活**。待会儿我们会讲，它其实有很多条件触发；而且一个完整的动画状态机实现里，transition 的条件可能不止一个，可能是很多个。

### Smooth 还是 Frozen：过渡的方式与曲线

这里面讲一下 fade，一个非常简单的数学原理。fade 一般有两种。

一种就是从动画一到动画二，动画一的贡献量越来越少、动画二的贡献量越来越多——这是非常容易理解的一种插值，叫 **smooth transition**。

但其实还有一种，叫 **frozen transition**：动画一要切动画二的时候，动画一**先停住**，然后动画二逐渐逐渐地进来——但这个"进来"，是基于你现在动画一停住的那个基础的。这件事情有点抽象，比较难理解，但实际上在我们的动画系统里真的有用处：有些动作，当你要发生切换的时候，如果继续播放动作一，它和动作二混合在一起，看上去反而更不自然。

就拿刚才起跳的例子来说：如果用 smooth transition，你会觉得这个人在空中还在试图跑步——当然，这也是一种表现方法了，比如跨栏；但用 frozen transition，你会觉得这个人好像先试图停一下，在原地起跳。你说到底哪个好？我觉得这是 artist 决定的。但作为 engine designer，我们实际上要给大家**提供一个选项**。

| | smooth transition | frozen transition |
| :--- | :--- | :--- |
| 动画一 | 继续播放，贡献量逐渐减少 | 先停住，冻结在当前姿态 |
| 动画二 | 贡献量逐渐增加 | 基于动画一停住时的姿态逐渐进入 |
| 观感 | 起跳像"在空中还在试图跑步" | 起跳像"先停一下，原地起跳" |

再多说一句：两个信号之间的 fade，是有非常多讲究的。大家看到这么多名目繁多的曲线，本质上就是在找各种各样的可能的形状——还记得讲材质模型的时候说过的吗？这个信号到底要尖锐一点，还是下面的波峰要拖得再长一点？其实大家都只是在找形状。

比较多的形状就两种：一种是 linear，线性的插值；还有一种我们叫做 ease-in ease-out——用 cubic 的方法，或者用贝塞尔（Bézier）曲线：先平平的，中间长得比较快一点，到结束的时候再慢一点。这是用得比较多的。其他的，比如指数这些，至少在我们的动画系统里，用的是比较少的。你会发现动画大部分时候，要么就是线性插值，要么就是 ease-in ease-out 的插值。

但这不妨碍大家知道这些基础的理论，因为这个东西在我们的引擎很多地方都会用到——比如后面我讲 particle 系统的时候，粒子的明暗变化，可能就要用这些曲线来表达。

### Unreal 里的状态机长什么样

给大家举一个真实的案例：用 Unreal 引擎做的一个 ASM 案例。你会看到上面每一个小小的双箭头，其实就表示一个 transition；你打开这个 transition，里面有很多属性——属性比较复杂，我就不一一展开了。这里面你看得特别清楚的是：我的 duration 到底要插值多久，包括我大概是什么样的插值类型。还有一个比较复杂的东西在图上没有展开：我这个 transition 什么时候发生、触发的条件到底是什么——这个地方其实非常有意思，我在后面讲。

另外，大家要注意一件事情：这里的每一个 node、每一个 state，**不是大家想象中非常简单的一个动画素材**。实际上你点开来可以发现，它可以做成一个非常复杂的动画蓝图——很多很多动画按照一定的规则去融合；当然你也可以只放一个，比如前面讲的 1D 或者 2D 的 blend space，这都可以。

这也是为什么我这节课在讲动画树的时候，大量用了 Unreal 做案例。因为我们比较下来——我个人认为——Unreal 的这个动画系统，设计的是非常好的。它一个很大的、我认为设计得好的地方在于：它非常灵活，你可以根据自己的需要自由地嵌套、自由地组合；而且它的很多图标、包括交互设计，非常符合设计师的直觉。所以如果诸位想做游戏引擎，你的动画树系统、或者叫动画蓝图系统，Unreal 是一个非常好的参考，而且非常符合我们讲的动画系统这个概念。

### Layered ASM：分层状态机的古典时代

当我们有了动画状态机这个基础，真实地在游戏中表达一个角色——在最古典的时代，我们用的一个东西叫做 **layered ASM**，多层次的动画状态机。比如这个角色的上半身，我们有一套复杂的状态机，表达他受击、或者各种攻击别人的动作；然后下半身，根据玩家的 control，比如这个角色在跑、跳、走。几层东西叠在一起：上一层管上半身，下一层管下半身，还有一层可能管这个头，还有一层可能管这个角色的受击。几层状态机做好之后，基本上能够在游戏中表达一个活灵活现的角色。

这里我举一个例子，鬼泣五。你会发现这个角色为什么让你觉得很有打击感？因为他下身跳的各种动作，和他上身打怪的各种攻击动作，基本上是可以独立控制的——这样你会觉得这个角色特别的"活"，而不那么僵。这就是 layered ASM 一个很大的好处，也是一个最经典的设计。

### 动画树：把动画表达成一棵表达式树

但是现代游戏引擎里，我们基本上切到了什么呢？动画树。动画树这个概念，我相信同学们应该至少是久仰大名了，或者很多同学已经用过了。

动画树最原始的 idea——至少我个人的理解——是从**表达式树**开始的。大家想想看：layered ASM 无非不就是信号 A 加 B 加 C 加 D 嘛？那其实我们对整个动画的表达，可以表达成一种表达式：比如速度做个差运算、动画 A 加动画 B、然后在某一点 C、再受制于什么东西。如果是这样一个表达式的话，我们用树的形式表达，是不是更好？

所以大家仔细看动画树：它其实是一个**单向展开的树**，它并不是一个图；它最终一定要有一个流出的节点——就像表达式树一样，最终有一个根节点。

```text
 叶节点:   [idle]    [walk]    [run]        ← 素材 / blend space / ASM 都可以
              \        |        /
 中间节点:      [ 1D Blend Space ]          ← 权重由控制变量决定
                       |
               [ Additive 点头 ]            ← 在混合结果上再叠一层差分量
                       |
                       v
                    最终 pose               ← 根节点：整棵树唯一的流出
```

读图：动画树从叶节点一路单向流向根节点，根节点输出的就是这一帧最终的 pose。

动画树的节点，就像前面介绍的，其实非常简单。最最常用的就是**线性插值节点**。注意：动画树里最简单的二元线性插值节点，你输出的是一个权重——0 就表示我全部选用 clip A，1 就全部选用 clip B，0.5 就各取一半。那如果是三通道的系统呢？它的权重我们一般会单独让你输入：w1、w2、w3，你自己来控制它——这个像不像电路板？包括刚才讲的 additive blending，动画树里也有专门的节点，你可以把它放进去，做你想做的事情。

那刚才讲的 layered ASM，是不是就可以很轻松地用这样一个结构的动画树表达出来？所以动画树，你可以认为是 **layered ASM 的超集**——它可以表达所有 layered ASM 能表达的东西。

但动画树真正酷的地方在于：**它实际上是一个递归结构**。至少在现在的游戏引擎里，我看到大家越来越把它变得更 general。这里我不得不 highlight 一下虚幻引擎：它在动画树的节点设计中非常灵活——节点既可以是一个动画素材，也可以是一个 blend space，也可以是一个 ASM，这样你最终只要输出一个节点就可以了。刚才讲了，一个 ASM 点开之后，里面又内嵌很多的 node；这些 node 中间，又可以在内嵌一棵小的动画树——这个听上去就很丧心病狂了，你套我、我套你。但这东西你觉得很复杂吧？其实如果写过编程的同学就知道：类的定义、类之间，就可以你套我我套你，代码就可以互相套起来嘛。所以这些数据怎么去组织、怎么去归类——这个结构，就给我们的设计师提供了一个非常大的自定义空间。

这些节点我们一般叫做**叶节点**；叶节点往上的话，有很多中间的计算节点，最常见的就是各种 blend 节点——additive 的、mask 的，两通道的、三通道的、多通道的。这里是一个非常简单的 Unreal animation blueprint 案例：两个 ASM 接受一个控制信号，输出了最终玩家的动作。

### 控制变量：动画树的灵魂

听上去好像很简单。但这棵动画树放在这儿，它为什么可以**一直变换它的输出**？你说，树的数据放在那儿是静态的，它为什么可以根据鼠标、键盘的输出，包括游戏的状态，产生不同的 pose？

这里有一个关键的东西：动画树最核心的，**你要定义它的控制变量**。在动画树中，我们会定义大量的变量，暴露给外面的 gameplay 系统来控制：比如我现在的移动速度、我现在的朝向、我现在的健康状态、我是不是现在要跳起来、我现在是不是受到了别人的攻击。这些大量的控制变量，实际上改变的是这棵树里面的**混合行为**。

你可以想象成：动画树是无数个流着水的管道，每个管道汇在一起的话，它有一个阀门，会控制我用红颜色的液体多一点、还是蓝颜色的液体多一点，这个阀门就是用控制变量来控制的。假设我有 12 种颜色的液体，按照各种数学规律预先放好在这儿，可以一层一层地混合；那我只要输入这些阀门的控制变量，是不是就可以决定最终流出来的、混合出来的那个液体的颜色？大家想象一下有颜色的水管，是不是这样一个逻辑？**动画树的控制变量，实际上是动画树的灵魂——它能控制住整个行为。**

在虚幻引擎里，它定义了叫 variable 的东西——我们自己一般也会定义这个词：一个变量，暴露出来。这里的 variable 大家注意有两类。

第一类是**环境的参数**。就像刚才讲的：我的速度、我的朝向、我的健康值。比如我根据健康值来混合：我现在血量只剩一半了，那我的动作可能切换到那种"哎呀、很虚弱"的动作——这种动作动画师提前就做好了；如果我血量很满，那我的动作就是另外一组，走起来昂首挺胸的。反正两组动作我都混合在这儿，但是那个开关，就取决于我的血量是不是大于 50%。这个很好理解。

第二类我们称之为 **event**：当一件事情发生的时候，我会去修改一些变量。这个修改一般是 event 发生的时候，把动画树里面的一些局部的标记给修改掉。举个例子：我现在手上拿了一把步枪，突然接到一个指令，说我要把步枪换成一个火箭筒——好了，那我拿枪的上半身动画，就会彻底地从一个动作，变成另一个动作。这个信号一来，我就会修改动画树内部的一些状态——如果大家有编程的技术，你可以认为这就是类中间的 private 变量、私有的变量，但它可以被外部的一个状态**激活并且修改**。

所以大家对动画树的理解，可以分成两趴：第一趴，是这些动画像流水一样、各种颜色的动画，通过这些阀门控制它怎么去混合；那阀门怎么控制呢？动画树中还有很大的一块**计算结构**，去算每个阀门的开放百分比——通过我的变量、通过外部的控制信号，在动画树中进行一些简单的加减乘除、比较，或者说等于的运算——这些运算是最常见的，能实现我想要的效果。

### 土法炼钢：自己也能搭一个动画树

大家如果真的想实现一个高级的动画树动画系统，我会非常建议大家去认真研究一下虚幻引擎，因为它是我目前见过的做得非常完备的一个系统，你会理解里面的基本概念。而这节课，我把最基础的概念教给大家：实际上有了这两层概念，你基本上就能够搭建一个动画树系统了。

比如你现在想做个引擎，说"哎呀太复杂了，我搞不了这么多"——其实很简单：你可以定义一些接口的变量，让你的 gameplay 系统可以去修改它；而你的动画系统做好了之后，在每个节点读取这些变量，然后允许它支持一些简单的运算，比如加减乘除、比较大小，或者是等于——实际上，你也可以实现一个"有点那么个意思"的动画系统了。所以我们**土法炼钢**，也是可以炼出来的。

这里放的是 Unreal 里一个很基础的动画树教程，讲得就比较清楚。动画树的实现流派，每一家厂商其实都有点区别——比如你看 DICE 的引擎，就是战地的 Frostbite 引擎，它就有很多自己的节点，因为根据产品不同、游戏不同；但是最基础的概念基本上就是这样，大家大同小异。

### 前向与反向：IK 要解决什么问题

知道了动画树这些东西，一个角色的动画系统——角色的运动——基本上就能表现出来了：你能表现这个角色，让它跟 gameplay 环境连接在一起。但是，角色的动画不是孤立的，它实际上是和环境在一起的；而跟环境在一起，环境就有很多对它的约束。

所以这里我先跟大家讲几个基本的概念。其实我们前面讲的所有的动画，它是什么？是我们叫做 **forward kinematics**（FK，前向动力学）的东西：我们去驱动关节，从根到梢一节一节往前走；动画树的混合也是这个道理——就是往前传递的动力学。

但是**反向动力学**（inverse kinematics，IK）的意思是什么呢？假设我约束好：我就是要让你的手抓到这个点——那你这个动画该怎么做？就是给定一个约束，反向去解每一个 joint 应该怎么动（上节课我们已经提到这个概念了）。这个东西在游戏中非常有用：最经典的，就是游戏中你能抓到一个把手；摔跤的时候，你能抓到一个人。

那么在游戏引擎中，我们怎么帮助设计师去表达"我希望这个角色的某一个骨骼的运动，符合我这个反向动力学的约束"呢？我们叫做 **end effector**——末端效果器。也就是说，我们会在这个骨骼上说：我要加一个 end effector，我希望它总是能够贴到地上——这是什么？这就是贴地的需求。

### Two Bone IK：用三角形把脚按在地上

一个最经典的案例：当角色在一个颠簸不平的地上走的时候，我们希望它的脚总是踩在地面上。但是动画做出来的动画——大家如果看过动画师做的动画——它永远假设面前是一望无垠的平地。所以大家看早期的游戏，那些角色在地上就是这样，各种乱踩一气，特别明显的就是上楼梯。

所以在这种情况下，我们特别希望，哎呀，有一个大神，能在我这个角色迈出去每一步的时候，都帮助这个角色把他的脚按在地面之上。这怎么解决呢？其实最简单的解决方法，叫做 **two bone IK**——只有两根骨骼约束的 IK。

以人为例：他的大腿和他的小腿这两根骨头，是三角形的两条边；我的目标点也确定了；那目标点离我大腿根部的距离，也是确定的。我就知道了**三条边长**。三条边长，就可以唯一地确定一个三角形——用最简单的初中三角函数，我们就可以知道你的大腿要迈多少度、小腿迈了多少度，我就可以算出你的动画。这就是 two bone IK，一个非常简单的两球求交的问题。

但这里面有个比较讨厌的事情：当我去给定一个约束点、给定大小腿这两根骨骼的时候，你会发现它的解空间，相当于**两个球的交点**——它解出来是一个**圆环**。也就是说，圆环上的任何一个点，这个解都是有效的。以这个角色为例：大家是不是发现，他无论是内八字还是外八字，这个动作实际上都可以保证他的脚踩在那个点上。但这个，我们的艺术家肯定是不答应的。

那解决这个问题也非常简单：我们让艺术家给一个 **reference vector**，告诉你说，这个人不是往前走吗？如果我需要做 IK，我的腿的整个朝向应该朝什么方向。我就沿着那个朝向的方向，去找它的解。解法其实非常简单：因为你给了我一个 reference vector，再加上我的大腿根部和目标点的连线，我可以确定一个**平面**；这个平面和那个圆环相交，肯定就有**两个交点**，其中一个是正向的、一个是反向的；用一个简单的向量点积——大于零就是同向，小于零就是逆向——你就可以把那个点解出来了。这个时候，你基本上就可以非常完美地解决脚踩在地上的问题。而且这也是 IK 最简单的方式。

### 长链 IK：自由度爆炸，解有无穷多个

但是，这个世界上的事情不是那么简单——如果这个事情这么简单，我们就很开心了。事实上，IK 的 scenario 比这个要复杂很多：比如我们要让这个角色看一个方向，look at——那我们在角色脖子这个地方，其实是有很多根骨骼的；包括当我们的角色在空中飞舞的时候，它要抓住一个东西；包括游戏里其实有很多上下左右翻飞、全身的 IK。

那 IK 真正难的地方在哪里呢？如果参与这个 IK 的 joint **不止两个**、你有一条**链**的时候，你怎么去解？它有两个问题。

第一个，自由度太高。它是一个高维方程；而且它是一个**非线性**的方程——因为有大量的旋转角度在里面，它不是线性方程，所以接下来就很蛋疼。

第二个，关键是它的解**有无穷多个**。就以刚才的情形为例：你连接了这个起点和目标点，中间这些 joint 是不是有很多种摆放的可能？实际上它是无限多种可能性。

那在游戏引擎里，我们怎么解决这种常见的 IK 呢？

### 先判断够不够得着

第一件事情是说：我们得判断这玩意儿能不能够得着。你想，你花了半天写一个通用的 IK，如果它本来就够不着，我们是不是在浪费我们的时间？比如我要用身体去够一个苹果——这时候我两个胳膊不够，身体还要前倾——你首先要判断，我能不能够得着它。

有两个非常简单的判断方法。但我要先说明：这个方法其实是后面会讲的——它是不完整的。

第一种：我把所有的骨骼**全拉直**，我的长度够不够？如果长度不够，我肯定是不够的。

第二种：把最长的那一根骨骼放在那儿，把所有其他的骨骼对着它去折——如果这些骨骼无论怎么折，都没有办法覆盖那根最长的骨骼，那么在我靠近根部的区域，其实也有一个**盲区**。

这是大家在写这种 IK 的时候，经常会忽略的事情：然后你会发现，你解了很久，拿不到一个解；有的时候如果代码写得不好，它就会无限次迭代下去——你就会在这个地方踩坑。

### 关节不是想转就转：解剖学给出的约束

那还有更难的一个问题：实际上对于一个人形的角色来讲，我们的骨骼是**不能乱动**的。其实我们每一个 joint，它的活动范围都是有它自己的约束的。

比如我们大腿和胯这个地方，是一个标准的**球状关节**——你会发现大腿上的骨头像个小圆球，然后它在你的盆骨那边，可以来回转、转转转。然后你的脚踝那个地方和上面的小腿骨，那个关节是可以平移的，像个小磨盘，在一个平面上。那我们的脖子这个地方是什么呢？像个 pivot，它可以这样转来转去。那我们最熟悉的，比如手掌——手掌是一个**马鞍面**的关节，叫 saddle，马鞍型的关节。你会发现，为什么手掌前后这样转很方便，但是这样（侧向）转的时候，活动范围就有限了。

怎么样，做游戏引擎有意思吧？上次讲渲染的时候，大家觉得你要上懂天文、下懂地理；接下来就是：哎呀，我做游戏引擎，我还得成为一个解剖学家，还要理解人体的骨骼结构。确实是这样——如果我们要想把一个角色做得好，我们确实需要知道解剖学结构大概是怎么回事。

这个东西叫 **joint constraints**（关节约束）：当我去做一个人体的 skeleton——biped skeleton——的时候，每个 joint 是有它特定的活动范围的。而这个时候，我们把所有这些约束放到一起再去解它，是不是很痛苦？所以这就是 IK——对长链的 IK 很蛋疼的一件事情。

最后说一下这个东西为什么这么重要。这里我们选了几个游戏的例子——这是课程组的小伙伴找到的，我觉得他们真的很棒，勾起了我很多童年的回忆。大家一定记得，在游戏里面各种各样的有趣的镜头——其实，都是 IK 惹的祸。

## 把角色做活：IK 求解、表情动画与动画重定向
> 对应块：BLK19 | 覆盖分集：P11下 | 块标题（分集名）：《第九节：高级动画技术：动画树、IK和表情动画》

### 一切都是 IK 惹的祸

你们一定见过这样的画面。一名球员开球，一脚踢到了另一个人身上，动画系统立刻开始解 IK，结果方程解崩了，整个人『啪』地解成一团乱麻；旁边那位裁判更冤，只是撞了一下别人，整条手臂的姿势全部扭掉；最有意思的是那位探员，脑袋啪一下扭了将近 360 度。

这些事故其实都是 IK 惹的祸：joint 的约束没有控制好，方程的解就报错了。特别是那种剧烈的受击动画——角色被大力击中时，你很容易 hit 到这类 IK 导致的 weird situation。所以在讲任何 IK 算法之前，先把这句话放在最前面：**约束（constraint）在 IK 系统里非常重要**。

先不吓唬大家。接下来我们介绍几个非常经典的算法，我会尽量讲得简单一点——今天争取放放水。这些算法共同的出发点是：**先用最 heuristic 的启发式方法去解决问题**。因为真的去解那么复杂的高维非线性方程很麻烦：现成的数值方法不是不能用，但第一，它们本身不一定稳定；第二，非常 expensive。游戏引擎研发在这方面确实非常聪明，引入了一批简单好用的小算法。最著名的一个，我认为就是 CCD。

### CCD：一节一节翻向目标

CCD 的想法非常简单：你不是要让末端够到目标点吗？那我先把最末端那根 joint，往『它上一根 joint 与目标点之间的连线』方向翻过去——这样末端就靠近目标了，对不对？接着再去翻下一根骨头，以此类推。一路翻下去，你会感觉整条骨骼链以端点不动的方式，尝试往目标的方向『翻滚』过去。翻完一轮，再从端点做一遍：第一轮如果是内翻，那下一趴是不是应该外翻？如此迭代若干次，你会发现整条链越来越接近目标，最终几乎完全重合在目标点上。这个方法就叫做 CCD（Cyclic Coordinate Descent，循环坐标下降），非常简单，也非常淳朴。

有一个细节要注意：示意动画里你会觉得第一次就基本翻到了，但在真实的游戏里，CCD 迭代个十几次很正常。好在这种迭代每一次的计算都不复杂。这也是目前行业里公认最经典、最简单的一个链式 IK 算法。

当然，CCD 可以对它做很多优化。这个算法有个毛病：一开始翻得太猛烈，翻到后面就『没有那点意思』了——比如上半身已经歪得不行，腰却还是笔直的，看上去就是不对。后面就有很多针对性的优化。一种做法是：每次翻动时先不精确对准目标点，而是在目标点周围取一个相对大的范围，大致翻到就差不多了；第二次迭代再逐渐往中心点收缩，让它看起来更像一点。另一种做法是：每一次翻动的角度变化给它设一个上限，不允许超过这个变化量——这样旋转就能在整个骨骼上均摊一点。

那这些优化的数学原理是什么？我得实话实说：**这全是 hack**。但我认为它背后对应的直觉，是『表面弹簧的能量最低』。假设原始的骨骼状态是一根已经固定好的弹簧：你去掰每个 joint，掰的角度越大，储存的弹性势能就越大——把一个 joint 掰得很多，能量是以二次方往上涨的（$E \propto \theta^2$）。现在想象一条由无数个弹簧连接起来的链条：你掰它两头的时候，它会相对均匀地把形变分散到各个 joint 之间。IK 算法本质上要的就是这么一个结果，只是各自找了无数的 hack 去逼近它。

> **提示**：理解各种 IK 算法时，用『弹簧连接棒』这个模型去想，就能明白它们为什么这么设计。比如想做出更自然的旋转，我们可以约定：越靠近根节点的关节，旋转幅度越小；越靠近末端的，旋转越大——这正符合『总体势能往偏小的方向走』的原则。

这是一个非常简单好用的算法，有兴趣的话建议自己动手写一下——要不我们干脆把 CCD 作为动画系统的作业题目？我觉得这个题目非常好，这也是我特别喜欢的那种小算法。

### FABRIK：向前够、向后收

接下来是另一个大名鼎鼎的算法：FABRIK。名字听上去非常高大上，但其实翻译过来非常直觉——Forward And Backward Reaching Inverse Kinematics：后面两个词就是 IK，前面几个字说人话就是『向前迭代一遍，向后再迭代一遍』，反反复复来来回回，就把 IK 问题解决了。大家记 FABRIK，就这么记就好了。

FABRIK 的原理和 CCD 不同。CCD 是老把骨骼掰来掰去，FABRIK 说：哎呀你们太麻烦了，我只做位移。它的 forward pass 是这样的：先从端点开始，把第一个 joint 强行拉到目标点上；再根据这个 joint 和它上面那根还没动的 joint 连一条线，把骨骼旋转到这条连线上。但骨骼长度是固定的，所以一定会『呲出去』，对不对？好，呲出去了——那下一根骨骼要跟我连，它就以我呲出去的那个反向端点作为自己的目标点，也去对上；如此如法炮制，一根一根往上窜，一直窜到根节点的骨骼。

```text
forward pass : 端点 ──拉到目标──▶ 沿连线逐节向上摆 ──▶ 根节点被带飞
backward pass: 根节点 ─拉回原位─▶ 沿连线逐节向下摆 ──▶ 端点出现误差
                  （一来一回算一轮，端点逐轮逼近目标）
```

读图：forward 一路把误差往根部赶，backward 再把根部归位、把误差赶回端点；每跑完一轮，端点都离目标更近一步。

这样会出现什么结果？**根节点飞了**——我为了让末端凑到目标点，把根节点也带跑了。这个时候 backward pass 就来了：这样不行啊，我把整个链条倒过来，从根节点开始，先把根节点拉回原来的位置；它一拉，又发生偏移，那就哒哒哒哒一路拉到这头的端头。端头会出现一些误差。但一般这样迭代下来你会发现：经过这一来一回，根节点先被锁住了，整条骨骼链也满足了约束，同时最远端那根骨骼离目标点的距离明显近了很多——除非这个目标本来够不着。接着再如法炮制，forward、backward 再来一遍，经过若干次迭代，端点就会非常接近目标点。

无论 CCD 还是 FABRIK，我个人觉得都要设置一个 error tolerance（误差容忍度）：它们都不能完全保证你一定 hit 到那个目标点，但基本上都能得到一个可以接受的结果。

顺带讲一段轶事。写 FABRIK 的那位老哥，在论文里声称自己的算法效率比 CCD 更高。前段时间备课我们还真去查了一遍：结果发现他给的所有性能数据，都是 MATLAB 里跑出来的。大家知道，MATLAB 的性能和真实引擎里跑出来的性能是没有可比性的。所以我后来想，还是算了，我不敢引用他的结论，也不敢说 FABRIK 一定比 CCD 快。事实是：这两个算法在行业里一直平行地在用，谁也没有取代谁。如果你想做简单的链式 IK，它们就是最主流的两个选择。

### 约束怎么加进迭代

前面开场那些翻车事故，说到底就是没管住约束。那 CCD 和 FABRIK 怎么处理约束？都很简单。FABRIK 的做法：链条第一段一动的时候，根据约束的转动范围求一个垂直平面，把目标点投影到这个平面上，用投影点作为这一步的 target，再让骨骼动过去；如果每根骨骼都有约束，就依次这样投影。CCD 的道理也一样（前面讲 CCD 时这一趴我没展开）：核心思想就是骨骼每次动的时候，不要超过约束范围就好。这样一来，第一根骨骼够不着的时候，就交给第二根骨骼去够——同样能解决骨骼约束的问题。

把两个算法放在一起对照一下：

| 维度 | CCD | FABRIK |
| :--- | :--- | :--- |
| 核心动作 | 逐关节旋转，朝『上一关节—目标点』连线翻过去 | 只做位移：端点拉到目标，骨骼沿连线摆放 |
| 迭代结构 | 从端到根反复翻滚，内外翻交替 | forward 窜到根、backward 拉回，一来一回 |
| 约束处理 | 每次转动不超过约束范围，够不着交给下一根 | 按转动范围求平面，目标投影后作为 target |
| 收敛保证 | 需设 error tolerance，不保证精确命中 | 同样需设 error tolerance |

但它们有个共同的问题：**需要无数次来回迭代**。一条几十根骨骼的链条，迭代个几十次是很正常的。

### 多个控制点：从攀岩说到雅可比矩阵

刚才讲的约束都比较简单，都是单一的约束点。但真正在游戏引擎里，我们经常发现 IK 的输出点特别多。举个例子：攀岩。这时候你的左脚、右脚要分别踩到岩石的某个地方，手还得够到另一个点，整个角色的 skeleton 都是被拉伸着的。

大家想想，为什么我们经常开玩笑说『育碧爬墙党』、总这样嘲讽一笔？但今天讲到动画这一趴，我得给育碧稍微洗脱一点罪名：要做一个爬墙时活灵活现的角色，从动画系统来讲门槛其实非常高——最难的就是 IK 和动画混合的体现。像 Zelda 那个例子：攀岩的时候，同时要控制的 IK 点可能达到三个甚至四个以上。这个时候角色的行为会怎么样？

IK 里那个要去够目标点的末端关节，叫末端效果器（end effector）。多控制点 IK 最大的难点是：当我用刚才那些简单算法去构造一个点的时候，因为公共节点发生了变化，其他点再去够它们各自的目标点时，就会把已经就位的这个点偏来偏去。CCD 和 FABRIK 其实也都提出过多约束（multi-constraint）的解决方法，但我个人觉得还是比较 hack，这里就不展开了。行业里最经典的解法，叫做雅可比矩阵（Jacobian matrix）的解法。

看到这里，大家是不是又嗅到了我们 104 课程久违的气息？我已经感到了——前方高能预警。但我得跟大家讲，这是个假情报。为什么？因为我们经过慎重的研究和决定，认为在动画这节课要保持轻松愉快，所以决定把非常复杂有趣的雅可比矩阵，放到后面讲物理系统的时候再跟大家去讲。这里只讲它一个最简单的概念。

设想一条长链条，每一个轴都有旋转。这一堆旋转做完之后，你的端点在空间里就是一个坐标值、一个位置，而这个位置随着旋转一直在变。多个约束点，其实就是多个位置点的问题。你可以把所有关节的角度想象成一个向量 $X$，把你要控制的那些 end point 在空间上的位置，想象成关于 $X$ 的一个方程——它的自变量是一个向量，输出是三维空间里的一个 vector；端点与目标点之间的距离（或者说空间位移），也可以成为这个方程的结果。

雅可比矩阵说的是：对于这样一种空间上的高维方程组，你可以用它的梯度——在当前这个 pose 下，把角度动那么一点点，最终点的位置会产生一个微分，这个微分可以表达成一个导数的矩阵。听上去是不是有点抽象？所以今天不展开。但它的核心思想是：既然知道了这个趋势，我就可以解这个矩阵。比如我先把目标点设得离当前端点非常近，反向求出每个角度该动的小小的 $\Delta\theta$，让端点离目标再近一点；然后我再往前走一小步，再构造矩阵、再解出每个 joint 的小小 $\Delta\theta$，又往前进一点。经过一次次『构造矩阵—反向求解』，就求出了每根轴一点一点的变化，最后让端点 hit 到目标点。

听上去是不是很简单？但我知道我是在骗你们——这东西真的不简单，雅可比矩阵求解起来挺复杂。大家最简单的理解就是：**用雅可比矩阵做多目标点优化，实质是一个逐渐逼近的过程**——每一次从当前端点向目标点靠近一小步，求解每个 joint 应该转的角度数；这一步当然有误差，转完之后再算出真实位置，再去构造雅可比矩阵、再去求解。这是过去游戏引擎行业处理多 joint、多约束 IK 的一个标准解法。但实话实说，它计算非常复杂，而且也比较费（贵）；所以有很多工作专门在讲怎么样快速求解雅可比矩阵。

实际上，行业里 IK 用得还是非常多，方法也在往前走。比如基于物理的 IK（physics-based IK）——因为 IK 有时候不是一个纯的焦点约束问题，它还有物理上的合理性；还有基于 position based dynamics 的方法，是现在前沿的一些引擎在用的；基于 PBD 的 full body IK 也是现在比较 hot 的方向。所以现在看：雅可比矩阵是经典解法，physics-based 和 position based 的方法越来越热。

### IK 至今没解决的三件事

IK 是一个非常难的问题，到现在为止还是有很多挑战。

第一，**自穿插**。IK 求解假设骨骼是纯抽象的、没有空间体积；但当我给它蒙上蒙皮之后，IK 解出来的结果会自我穿插、自我交叠。这个问题到今天还是比较难解决。

第二，**感知与预判（perception）**。我们的 IK 很多时候是『约束点到了才反应』，但人身上是有预知的：前面的障碍还没到面前，你就会早早地弯下腰，让自己能穿过去。这件事说起来很简单，在游戏里做起来并不简单。你现在回想一下看过的 3A 大作：角色跟环境能很聪明地做出这样那样的互动，实际上都是 designer 老早在那边放了很多检测器——『哦，你要靠近一个洞了』，这个时候我就让角色很聪明地知道怎么弯下腰。检测器可以自动生成，但真正能感知环境（perceive the environment）、并且像人一样（human like）地控制身体姿态，是个非常难的问题。到底有多难？课后有人问我动画领域最前沿的问题是什么，我的回答里就有它：IK 最难的其实不是数学上解不出来——数学上总能解得出来——最难的是你这个解看上去要非常像人。比如够一个东西的时候，腰部的扭转、腿部动作的配合、手的动作要自然；你去够一个很高的地方，如果只是直挺挺地够，你会觉得这个动作很僵，但如果他的脚尖稍微垫了一下，你就会觉得很自然。这种 human like 的东西，才是真正难的。

第三，**平衡**。IK 解出一个结果，它什么都不管——不管平衡的问题。但我们做出的每一个动作，实际上重心都是要平衡的：哪只脚是支撑脚、重心在哪里，都要符合动力学的规律。而这一点，刚才讲的所有 IK 算法都不会去解决。这就是为什么现在游戏里很多 IK 看上去就是不那么自然的一个原因。

所以 IK 是一个至今仍在快速演进的研究领域。我们课程组找过资料：过去十几年里，IK 方面的文章越来越多，特别是最近 10 年。为什么最近 10 年 IK 算法大爆发？因为 3A 游戏的要求越来越高，我们希望角色更加 environment aware（对环境有感知）。以前的游戏，角色是自说自话的：我放出一个大招，这一拳是塞到墙里了，还是打穿到别人的肚子里了，都没关系，反正我的意思到了。但现在的 3A 游戏、包括高端游戏产品，非常在意角色看上去是不是真实可信。IK 就是在这个背景下被一路推着狂奔的。

> **结论**：关于 IK 这一趴，大家 take away 两件事就够了。第一，知道了三个经典的东西：CCD、FABRIK，以及一个叫雅可比矩阵的数学工具——其中 CCD 和 FABRIK 希望大家理解透，平时做一个简单游戏，用这两个基本上可以了。第二，如果你的数学基础特别好、又对这件事特别感兴趣，我强烈推荐把 IK 当作研究方向——它非常有意思，而且研究到后来你会发现，它和人工智能、perception、行为学的关系都蛮大。在这一点上我不敢妄称专家，因为很多团队做得非常好。

### IK 落进管线：动画的 post process

IK 为什么这么重要？因为在实际的商业游戏引擎里，**IK 会实实在在地改变动画的 pipeline**。大家还记得上一节课讲的动画 pipeline 吗？那时还比较简单：把动画的 clip 拿到之后，采样成各种各样的 pose，再把 pose 一起 blend。但有了 IK 之后，事情就变了：你要先把这个 blend 后的 pose 反向算回模型坐标系，再反向算到世界坐标系；然后在世界坐标系里——也就是在我的环境里——跟各个约束在一起，反向结算 IK，算出每根骨骼该怎么调整；再根据 IK 的结果，去调整提交给渲染器的动画。

```text
动画 Clip ──▶ Pose ──▶ Blend（动画树 / 状态机）
                          │
                          ▼ 反向变换
                    模型坐标系下的 Pose
                          │
                          ▼ 反向变换
                    世界坐标系下的 Pose
                          │
                          ▼ 与环境中的各个约束一起反向结算 IK
                    调整后的最终 Pose ──▶ 提交给渲染器
```

读图：IK 不是混在 blend 里做的，而是在 blend 之后插入的一个独立结算阶段——blend 出来的 pose 必须先『还原』到世界坐标系里，才有资格和环境约束对话。

这个过程在动画开发里叫做 post process（后处理）。注意，这个地方的后处理，和渲染那一节课讲的 post process 不是一个概念。动画系统的 post process，很多时候指的就是 IK——让我的动画符合环境对它的各种各样的约束。有了这一趴之后，才是一个基本完整的动画 pipeline。

### 表情动画：从 43 块肌肉说起

讲完硬核的，我们讲点轻松的——大家最喜闻乐见的：可爱的小姐姐，各种各样非常可爱的游戏角色。一个角色能让人觉得可爱，这也是动画系统干的很重要的活，叫做表情动画。有的游戏跳票了，官方让角色出来道个歉——连道歉都能道歉得这么萌，我就选择了原谅。这些角色之所以让大家这么感动、这么有感觉，就是因为整个表情、人物的表面做得非常细腻。

先讲一个非常学院派的概念：人的表情是怎么来的？来自皮下那很多很多根肌肉——如果我没记错的话应该是 40 多根，我上面写了，**43 块肌肉**。它们有的横向、有的纵向、有的做放缩，共同形成了人的表情。

人类的表情在进化学上有很多讨论：整个动物界好像只有人类，进化出了如此丰富、如此细腻的表情系统。我们甚至认为，人类社会之所以能进化出高级文明，就是因为表情帮助了我们在族群内部的沟通。顺便说说为什么你们要养宠物——大部分动物是读不懂人类表情的，而我们的狗跟着人类上万年，是少有的几个能看懂人类表情的物种。人类的表情非常非常 subtle，所以你们家的狗，你一定要对它真实——因为它是真的会对你察言观色的。

表情为什么难？举个例子，一个演员的表演：她从嫌弃你，到有点喜欢你的暧昧，几乎没有明显动她的五官——但我相信所有同学仔细看的时候，都能看出她微表情的变化。我们管这个叫 subtle 的 expression。这就是表情特别难做的地方。早年我们做计算机人物角色，实际上只能做简单的表情：张口说话、大笑、哭，都非常浮夸。而现代游戏引擎越做越细腻、越做越真实，追求的就是这种真实度——因为它的精度要求是非常非常高的。

### FACS：把表情定量化

那怎么去表达表情？这不得不感谢我们的电影行业。很早以前，电影行业就引入了一个系统叫 FACS（Facial Action Coding System，面部动作编码系统）：它把人类常用的表情归纳成 46 种标准的 action unit（AU，表情单元），认为任何表情都可以用这 46 种表情单元组合表达出来。这件事做得非常了不起。

我不得不说，电影行业的这些老哥有非常好的理工科基础——用很工科的方法，把这么一个文科的事情给定量化了。就像上次讲渲染后处理时说的：电影行业一出来，我们所有的滤镜瞬间失色。当电影工业的同学说『我来教你们做表情』的时候，我们游戏行业的人基本上就是：大哥，你告诉我怎么做，你说怎么做我就怎么做，你说的永远是对的。确实是这样——他们对真实度的要求远远高于我们的游戏行业。看看最近几年的奥斯卡电影就知道，虚拟拍摄、虚拟角色的水平越来越高，他们是走在行业真正前沿的。

AU 之间可以用某种方式组合。举个例子：这个男人的眉毛皱起来是一个 AU，眼睛睁大又是一个 AU；『眉毛放下来 + 眼睛睁大』这样一个组合动作，我自己试过一次，发现还是有点难的——后来我才知道，专业演员的表情肌是要经过专门训练的，反正我是做不到。但我们需要理解的概念是：**这些表情动画单元可以像函数一样自由组合，组合出各种各样的表情**。

有了 FACS 这个概念，很多事就可以做了。这里面要提到 Apple 做的一个很有用的总结：46 个 AU 太多了，把它整理成实用的 28 个最核心的 AU；其中 23 个是对称的——比如左眼的闭合、右眼的闭合，存一份就够用了：两眼同时睁开、两眼同时闭上、睁一只闭一只，都能用这一份镜像表达出来。因为人体大量的表情天生就是对称的，所以行业里一般用 28 个（单侧）AU 就好了。这要感谢 Apple 给我们做了这样的总结。

### Morph Target：把表情存成顶点偏移

有了 AU 的概念，做法就呼之欲出了。上一节课讲过一个很重要的动画形式，叫 vertex animation（顶点动画）——每个顶点存一个动画，不很简单吗？你不就是 28 个 AU 吗？那我每个 AU 存一个动画行不行：这个角色嘴巴歪一下、眼睛睁开……两个表情叠在一起，就能形成我想要的表情。看上去是不是非常简单？

是的，非常简单。但这种简单的线性叠加会产生一个小问题。如果我存的是『每个顶点在这个表情下的位置』，那动画的叠加就是一个线性插值产生的结果，可能不是我想的。举个例子：第一个动画是这个人张大嘴、眼睛睁得很大；第二个我想混合的表情是闭上眼睛、张大嘴。把这两个表情做线性加法合到一起，得到的角色是：嘴巴张开了，但眼睛是**半闭**着的。为什么？眼睛『睁开』和『闭上』中间的差距，不是『半闭』。

> **易错点**：线性叠加顶点的绝对位置，会把两个表情在中间『和稀泥』，得到谁都不像的中间态。

实际上，一个 AU 都是在脸上的局部区域做处理的——每个 AU 只牵动脸上的一小块。所以我们想要的结果是：嘴巴这个区域，我要用你张嘴的动画；眼睛这个地方，我要百分之百地用闭眼的动画。因此在真实实现里，存一个 AU 存的是：**这个表情下，该区域相对于 neutral face（中性表情）顶点的 offset**。这样我们就可以自由地把这些动画合在一起。

> **定义**：morph target animation——为每个表情单元存储『相对中性表情的局部顶点偏移』，按区域混合叠加，就能组合出任意表情。

这个方法就叫 morph target animation。大家去看，大部分游戏的表情动画都是用这个技术做的；那些女性角色的各种表情，都可以这样做出来。大家可能会奇怪：为什么不用骨骼动画去做表情？骨骼动画可以做，表达简单的动作——比如眼皮张开、合上——是可以的；但你要表达嘟嘴、收嘴这种动作，骨骼动画就比较麻烦，而且不自然。所以一些细腻的动画表现，主要用的就是 morph target animation。如果你学完了前面渲染课、理解了什么叫 vertex animation，那理解表情动画的表达和绘制方式就非常简单。

不过在实际的游戏引擎中，不会完全只用 morph target animation——现在的游戏还是会用骨骼做大量的表情表演。为什么？骨骼有很多好处。比如角色的眼球：用 morph 就很难做，眼球很灵动，一会儿左一会儿右，这肯定得用骨骼去做。再比如一些比较大的动作，像嘴巴张开，骨骼也很有用。

骨骼还有一个更有用的地方，就是大家特别喜欢的**捏脸**：我给你一张标准的脸，你捏出一个你想要的脸。这里面既有 morph 的功劳，又有骨骼的功劳。但这个系统会很复杂，而且它其实不是引擎技术的问题，是你的艺术家同学有多强的问题。在一个 3A 级游戏里，特别是我们常玩的那些韩式游戏里，光一个捏脸系统，可能就是一个团队做 3 年以上。所以我们经常讲，捏脸本身就是一个游戏。实话实说，我们要对这件事情表达敬畏：它的复杂度和工作量就在那个地方——你要花大量时间精细地调表皮下的骨骼，同时做大量的 morph target animation，让这个角色有各种各样的外形变化，而且动起来各种表情看上去很自然。

顺带回答一个课后的提问：面部表情是不是也靠顶点动画做？按我个人的经验，是一半一半——骨骼动画不能忽略，它很重要；morph target 是画龙点睛的那一趴。还有大家容易注意不到的一层：**法向贴图的变化**。有时候做表情，不是几何变了，而是你表面上的皱纹发生了变化——这对面部表情的影响也非常大。所以一个活灵活现的角色，是多系统共同作用的结果：骨骼动画、morph target 动画（基于蒙皮的）、再加上 dynamic 的 bump map 贴图甚至材质变化，综合在一起，才让你产生非常真实的角色感。很难讲哪个最重要。要往下讲就非常深了——这方面电影行业的同学研究得非常非常深。

### 表情的其他路线：贴图与肌肉模拟

再顺便提一下：引擎中表达表情，不只是用几何表达。如果你做一个 2D 的动画，texture 是不是也能表达角色的各种动画？大家还记得上节课讲的 Live2D 方法吗？把 Live2D 变成一张 texture，apply 到一个几何上，是不是也能表现各种活灵活现的角色效果？对很多卡通化渲染的游戏来讲，这一路绝对比 morph target animation 加骨骼动画更实用，而且效率更高。

最后一个方向纯属科研性质。现在还有一批人在研究非常前沿的东西：真正把那 43 块肌肉动起来，去表达一个人。这需要非常细腻地定义：骨骼怎么运动，骨骼上面的肌肉怎么运动，肌肉又怎么牵动皮肤运动。这件事现在有些初步结果，但在游戏引擎里还看得比较少，更多是影视行业在用。它的结果确实非常漂亮。而且也许随着未来计算机算力足够强，我们就不需要再用这么复杂的 morph target animation 了——morph target 虽然算法非常简单，但它的数据存储量很大；而且它的计算量会随着表面细节越来越多而越来越复杂。所以肌肉模拟，也许会成为未来更高精度的角色表达。表情动画（facial animation）实际上是一个非常前沿的领域：简单做做很简单，真的要做得非常好，非常挑战。

比如说 Unreal 的 MetaHuman，我认为这是目前整个行业的天花板——它对角色细腻微表情的表达，包括眼珠、整个角色的自然态和真实态。大家想一下：要做得这么好、这么自然，可能不仅仅是怎么用 morph target animation 和骨骼动画来表达的问题，还包括你怎么 capture、怎么采集到这个东西。动作捕捉可以在身上绑几个绑点就可以采集；而表情的采集，现在是相机对着你，拍到的是一帧帧的照片——我怎么从你的一帧帧 video 中 decompose、解构出你的表情：你是皱眉了，是颧骨这边动了一下，还是脸上挤出了一个小酒窝、小笑纹？这是非常非常挑战的技术。好在感谢这个行业，这项技术目前已经有相对成熟的基础；但要做到这种质量，还是有很多挑战。

### 动画重定向：一套动画，全角色通用

最后讲一个相对简单的东西：动画重定向（animation retargeting）。它的核心应用场景是：做动画系统的时候，我们当然希望动画师给每一个角色都做很多很多动画，让角色活灵活现——但实际上动画师做不到。特别是现在越来越多地依赖 motion capture 动捕设备，我们不可能为不同高低胖瘦的角色都重新录一套完整的动画。所以，把一个角色的动画也能 apply 到另一个身材比例不一样的角色上，这是一个刚需。retargeting 要解决的核心问题就是：**采集一套动画，可以应用在各种各样的角色上面**。

#### 名词与一比一的骨骼映射

先定义名词（terminology）——以后你出去跟人家说『我学过游戏引擎』，就可以讲这些很专业的词汇了：

| 术语 | 含义 |
| :--- | :--- |
| source character | 原始采集动画的角色（原角色） |
| target character | 要把动画 apply 过去的目标角色 |
| source animation | 原角色上的原始动画（走、跑、跳） |
| target animation | apply 到目标角色身上之后看到的动画 |

听上去非常高大上，实际上非常简单直觉：一个是数据源，一个是数据的目的地——角色就叫原角色，动画就叫原动画，反之亦然。名词定义好了，后面就好理解了。

那具体怎么 apply？其实很简单：**骨骼一根对一根**。至于骨骼之间的位移差异——比如大怪物的脖子可能有 2 米多高，那个女孩子可能只有 1 米 4、1 米 5——没关系，我们就认为它们还是一一对应的，忽略所有的位移项。

#### 关键细节：相对 binding pose，而不是绝对旋转

这里有一个很小的细节，但非常重要。动画播放的时候，比如这个女生点个头：她的脖子骨骼初始是垂直的，动画把它向前掰了 30 度。但大怪物有点驼背，脖子初始就向前倾了 15 度。那这份动画怎么 apply？答案是：**apply 的是『相对于原始 binding pose（绑定姿态）的旋转差量』，而不是绝对的 local space 旋转**。否则的话，一个本来驼着背站着的怪物，被 retarget 了一份站姿笔直的女孩子的走路动画，播放的时候那个怪物会『唰』地一下站直——整个角色的姿态定义就没了。

所以我们传递过去的，是相对于 binding pose 的相对旋转、相对放缩和相对位移。当然，动画存储的时候，很多时候存的就是相对的旋转、scale 和位移，那这个问题不大；但如果你的存储模式是 local space 里的绝对旋转，这里就要做一个小小的变化：大怪物一开始是驼背的，播放动画的时候要让它保持驼背、保持它整个的姿态。真跟 artist 合作过你会发现，角色一开始的姿态——耸肩也好、驼背也好——其实就是这个角色本身的定义。

有了这个原则，把所有旋转动画依次 apply 到对应的骨骼上，这个角色就能动起来了。

#### 位移、缩放与浮空的脚

如果动画里有 translation（平移），怎么办？把涉及的骨骼的相对长度考虑进去，按等比例去放缩——讲起来简单，实际做起来有点复杂，这里不详细展开了。缩放也是一样，直接等比例放过去就拉倒了。这样基本上你能得到一个『有点意思』的角色动画。

特别容易出问题的是两条腿。每个角色大腿、小腿的比例、身高都不一样，你强行把动画放过去之后，这个角色大概率双脚是浮空的。最简单的做法：通过角色的腰线连到地面，就知道这个角色的高度比例。比如大怪物腰线离地 1 米，女生腰线离地 0.8 米，那播放位移动画的时候，我就按等比例把位移相应地往上提一下——这能缓解双脚离地的问题。同时，走路的位移我们经常会作为一个 offset 曲线存在动画里；我们希望角色走的速度，和他的腰线离地高度成正比：大怪兽腰离地 1 米、女生离地 0.8 米，那大怪兽播放同样动画的时候，移动速度也要快一点点。否则你会看到两只脚在地上凭空滑步——**foot skating**：脚像滑冰一样在地上滑，人却没有往前走；或者人走得太快、脚滑的速度跟不上。这是特别明显的一类 artifacts。

但实际上，大部分时候我们会发现：两个角色体型差得很多的时候，这些问题还是解决不了。举个例子：三个角色高度一样，最左边是 source，右边两个是 target；两个 target 的腰部高度都和 source 一样，但大腿关节的长短不一样。当你播放一个蹲在那儿的动画时：一个 target 小腿太长，直接钻地而出；另一个小腿太短，直接悬空了。所以真的要把 retargeting 做好，实际上是要配一些 IK 的：**把脚锁死在地上**，看上去才自然。retargeting 想做好，还有很多这样的小细节。

不过有的时候这个问题也不用太怕：很多时候 retargeting 是采取离线的方法做好的。比如我游戏里就那些角色，动画师做完一个角色的动画，我可以用离线的软件、一些更高级的算法，把 retargeting 做得更加自然和真实。

#### 骨骼拓扑不一致怎么办

讲到这里其实有个隐含假设：动画在不同角色之间传递时，骨骼的拓扑结构是一样的。但事实上我们做各种各样的角色，骨骼真的不一致。比如有的角色 spine（脊椎）只有一根骨骼，有的角色 spine 有三根。那它们之间的动画能不能互相传递？这方面的算法非常多，我不展开，给大家讲一个最简单的方法：**根据骨骼名字去找对应**。你会发现它们之间共同的骨骼很多；在两个共同骨骼之间，我们可以定义一种类似（插值映射）的关系。

讲一个大名鼎鼎的例子：NVIDIA——就是做 N 卡的那位黄老板——的 Omniverse 里很厉害的系统。它怎么解决这个问题？非常简单：**把两个名字相同的骨骼中间的所有骨骼看成一个映射，都归一化到 0~1**。比如 source 是四五根骨骼、target 只有三根，那就根据每根骨骼之间的相对长度，把 target 的每根骨骼规划成 0~1 之间的一个参数。这样 target 的第一根骨骼，参数一算，很可能落在 source 两根骨骼中间的某个点上——我就把骨骼插到那个中间点上；再插第二个点，再插上去。你会发现：虽然每根骨骼并不会和 source 的骨骼严格一致，但大体上呈现出了这个形状。这个算法非常符合直觉、非常简单，效果我觉得做得还是不错的。大家去看 Omniverse 里 retargeting 的结果，我个人觉得非常 expressive——录这样一段动捕动画本来就很麻烦，要把这份动画在这么多大大小小的角色上再做一遍，其实挺难的。当然，能做得这么好，我怀疑不止靠这么一个简单算法，可能还需要 deep learning 的算法，或者一些更 human behavior、更 natural 的处理，让这些角色看上去更自然。

#### 重定向的难题与它为什么是刚需

跟 IK 一样，如果你真的想做，retargeting 也是一个非常 hot 的研究领域，里面有很多很难解决的问题。比如**自穿插**：我们所有的计算都假设一个抽象的、没有空间体积的骨骼；当一个瘦瘦女生的动作 apply 到一个胖胖的角色上时，那个角色自己的手会穿出自己的身体。再比如**语义动作**：很多动作是有寓意的，比如鼓掌——如果两个角色的肩宽不一样，retarget 完之后这个手就合不起来了。还有更难的：走跑跳、或者去够一个东西的时候，身体是要追求一种平衡感、一种符合动力学的自然感的；retargeting 的时候如何保证这一点，是现在比较 hot 的研究问题。当然，如果两个角色相差没有那么大，很多时候 retarget 的结果是可以接受的。

但不管多难，这个技术非常有用：当你去做一个大型游戏、大型产品的时候，你一定要有这样的技术。比如做一个广场，上面几百上千的 NPC 是很常见的（上万可能太多了），你希望他们高矮胖瘦都不太一样，又要都走来走去——这时你一定要用 retargeting。所以 **retargeting 相当于动画能力的能量放大器**：把有限的动画资源，放大到多种多样的游戏角色里面。有了它，动画师才不会因为反复做大量动画而累死。

#### Morph Target 的重定向：闭不上的眼睛

retargeting 不止发生在骨骼动画上，morph target animation 同样有 retarget 的问题。为什么？举个例子：我们做人脸的时候，一般会把人脸的拓扑（topology）全部一致化，这样才能表达各种各样的人脸。捏脸的时候，你通过骨骼一变动，整张脸都不一样了；但这时你的表情动画可能是基于一张标准脸做出来的——脸变了，动画还要保持一致。因为 morph 动画本身存的是顶点的相对 offset，很多时候直接 apply 的结果还可以。但有一种情况大家要小心，还是跟鼓掌一样的道理：**有些动作是有寓意的**。比如眼睛闭上——当这个角色的眼睛做得大了那么一点点，你原来那份 morph target animation 里『眼睛能闭上』的动作，这时其实就闭不上了。嘴巴也一样：嘴巴张开、紧张地闭起来，也是一个约束。

所以这时我们会加入一些**额外的约束点**：这个动画里，我希望这些顶点一定要重合到一起——比如上眼睑和下眼睑，我们就加一些约束点。做法今天不展开，其实比较简单：先 apply 动画，发现这些控制点没有重合，就强行把这些点拉到重合；然后用一个简单的**拉普拉斯算子**去平滑周边——你可以把它理解成模拟一个橡皮表面：拉几个点，其他的点也带着一点弹性跟着被拉上来。这样整个眼睛就能闭得起来了。做 facial animation retargeting 的时候，这是需要重点考虑的东西；具体算法不难，大家可以去查资料。

### 课堂问答两则

**问：有没有三维的 blend space？**

这个问题问得我无言以对——确实没见过三维的 blend space。理论上应该可以，你其实可以加入更多的控制变量；但实际当中好像没人这么做。我猜测的道理是：二维 blend space 的图上，那个点动来动去非常直观，要加更多 clip 也知道往哪儿加；换成三维空间，往里面加一个点就费劲多了——用过 3ds Max 的同学都知道，光是习惯那个旋转、标点就要花很久，很头疼。如果你真的有三个控制变量的插值需求，做法其实比较简单：做两个 2D blend space，中间再加一个 lerp 节点，把第三个维度变成 lerp 节点的控制变量——两路插值的结果再插值一次，就形成了三维的插值。现代很多动画树里还提供 alias 这类把已有节点复用为输入的手段；不过注意，这里上下两路的两个 blend space 应该是两张不同的图，不是同一份重复两份。

**问：动画领域还有什么最前沿的问题？**

除了前面说的 human like 的 IK 之外，还有一个现在用得越来越多、也很前沿的方向：基于 motion matching 的动画混合——这个我们在高级课里会讲。为什么它前沿？因为整个 pose space 非常大，怎么快速 searching、怎么用深度学习选最好的解，都是开放问题，也是比较前沿的方向。

### 四块拼图：高级动画系统全景

讲到这里，我们的动画系统基本上就全部讲完了——两节动画课到这里收官。把这两节课的东西都掌握，你基本就可以做一个完整的动画系统。既然这一讲叫『高级动画系统』，大家学到的东西可以归成四块：

**第一，blending。** 混合系统连接了 gameplay 和动画系统：我们通过 gameplay 去控制动画混合系统——不管你是动画状态机还是 blend tree——有很多信号控制它，它能混合出你想要的各种动作。这是 FK（forward kinematics）的核心系统，负责输出角色的基础动作。

**第二，IK。** 角色是在环境里的，要跟环境有各种互动，所以需要 inverse kinematics 给角色加入环境的反向约束，让角色跟环境的互动看上去更加自然。它落地在动画管线的 post process 阶段。

**第三，表情。** 用骨骼加上 morph target animation 的方法，实现更精细的角色表情表达。这样角色身体的动作有了，脸上的动作也有了——全套了，对不对？

**第四，retargeting。** 游戏中角色的外形——无论长相还是身高体重——都会有变化，通过 retargeting，让有限的动画资源在各种各样的角色上都能用起来。它就是动画能力的能量放大器。

有了这样一套系统，你基本上就能做一个看上去很像那么回事的游戏了。当然，很多事情都是这样：**入门容易，精通难**。这里面的每一个点，水都很深——动画树有很多很多概念，需要你理解很久、结合你的产品去体会；IK 研究起来非常辛苦，有大量的数学，今天我还没有抛出我那个最高能的雅可比矩阵，大家等着我下节课争取把它抛出来；表情动画还好，不是很难，但素材做起来比较辛苦；retargeting 本身不是那么难，但要想做好，其实非常难。

讲完 rendering，我说过从此再也不看 rendering、再也不写 shader 了；现在讲完 animation，我从此再也不讲 animation 了——累死了，每讲完一个系统都如释重负。最后汇报一下小引擎：非常感谢社区同学的反馈，我们正在积极地对小引擎做重构，希望把它改得方便大家理解、方便大家使用，大概会分两三次逐步放出来。这一次主要把关卡、GameObject/component 系统重新重构一遍，把 editor 和引擎 runtime 的分层切得更清楚——我们自己回头看代码的时候，也越来越能理解大家的视角，之前有些架构确实有点想当然，不够专业也不够清晰，我们自己还蛮自责的。同时修掉了同学们报的很多 bug（比如几个显卡之间打架的问题），做了一些简单的优化。小引擎的征名活动也接近尾声了，我们会从 200 多个名字里选出最喜欢的一个来命名它。还要说一句：虽然课是我在讲，但课件准备、小引擎迭代、作业互动，大部分都是课程组的小伙伴们做的——要感谢，请多多感谢他们。下周的课程，我们就进入高能的 GAMES104 物理那一趴了。
