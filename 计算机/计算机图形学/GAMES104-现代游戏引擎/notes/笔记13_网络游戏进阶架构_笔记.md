# 网络游戏进阶架构

## 帧同步与状态同步的混用

   * **混合使用**

       * 真实游戏里两种同步经常混在一起用：MOBA 进入对局的 gameplay 多用帧同步；大厅里玩家特别多、对游戏逻辑的要求没那么严格，用状态同步即可。

       * 云游戏还没有出现真正的云游戏引擎，但可以肯定的是：超大规模的游戏仍需要大量状态同步——不可能把所有用户的输入直连服务器，用户从不同地域接入时，前端总得有一些较轻的节点做处理；未来更可能是帧同步与状态同步混合的形态，目前仍在前沿探索阶段。

   * **帧同步的防作弊边界**

       * 帧同步下所有人跑的是一模一样的逻辑，原则上确实能防范很多作弊——但防不住所有作弊。

       * > **易错点**：⚠️ 帧同步把所有状态全部同步到了本地，全图透视这类"信息型"作弊依然成立：战争迷雾完全失效，对方出什么英雄、在商店里出了什么装备都可能看得一清二楚，必须另做防范。

## 位移同步

### 朴素转发的延迟链

   * **Replication（复制）**

       * > **定义**：把一端的状态"复制"到另一端；角色位移同步要解决的就是让 replicate 过来的移动看上去平滑。

       * 朴素做法（每收到一条消息就把对方挪一步）不成立：真实玩家自己有 tick，状态包先走一程网络延迟才到服务器；服务器还要等自己的 tick（一般就十来帧每秒）再缓一拍转发；包再走一程延迟到观察端——链路上每一站都在加延迟。

       * 延迟小且稳定时（每 1/10、1/20 秒来一条消息）看上去还行；网络的 latency 一不稳定，观察端画面里的人就一抖一抖，整个状态看上去非常奇怪。

```text
真实玩家 A（authority，自带 tick）
   │ 状态包 ──► 一程网络延迟
   ▼
服务器 S（还要等自己的 tick，一般十来帧每秒，再缓一拍）
   │ 状态包 ──► 又一程网络延迟
   ▼
观察端 B：每收到一条消息才挪一步
   └──► 网络一抖，画面里的人就一抖一抖
```

### 内插值

   * **内插值（interpolation）**

       * > **定义**：把陆续到达的服务器状态缓存下来，按时间在已到达的两个状态点之间插出一条光滑过渡；网络包可密可疏都没关系。

       * 可选曲线：Catmull-Rom 能过所有控制点且线条光滑，以多项式的计算复杂度即可；B 样条、贝塞尔更复杂但不过控制点；分段折线也能插。

       * 关键 trick：不能每次拿到数据就急急忙忙立刻插值——内插是"跟未来插值"，插在 S1 与 S2 之间时后面的数据还没来。必须把从 server 端来的角色状态先缓存进 buffer，并给渲染时钟加一点 time offset 故意落后一点，保证插值区间右边的数据已经到手。

       * 代价：延迟被加剧——server 到 client 延迟 50ms 时，本地往往还要多 buffer 约 100ms；收益：客户端看到对方的移动无比平滑。核心特点就是用更大的延迟换平滑。

       * 副作用：对方高频跑跑停停的状态也会被一并 smooth 掉；但人眼观察世界时天然倾向连续信号，移动光滑、不急停急走反而显得更自然。

       * 根本问题：两个客户端互相看对方的世界，状态严格不一样——各慢 150~200ms；赛车游戏里一辆车认为"我该撞到你了"、另一辆认为"我已经跑掉了"，形成罗生门。对碰撞不敏感的个人跑跳还可以；战舰世界、online GTA 那种互相开车碰撞的游戏就很头疼。

### 外插值

   * **外插值（extrapolation）**

       * > **定义**：对自己的 latency 有一个估计（如 150ms）时，根据对方最近上报的位置、速度、加速度，预测"如果这中间没有其他事情发生，此刻他应该出现在哪里"。

       * 核心是"预判了别人的预判"：信息在路径传递中耽误的时间可以推算，虽然还没收到新的信息包，已经能算出对方现在实际在哪。

       * > **易错点**：⚠️ 时钟不对齐与相对论无关：这是牛顿的绝对时空观，不是相对时空观——绝对时空里"此时此刻对方实际在哪个位置"是可以推算的，不能做民科。

       * 风险：外插本质是个危险的东西，可能把人插进墙里、插进死胡同——authority 端看自己正常走动，replicated 端的人却已经钻到墙那头，过一会儿又被拉回来；解决方法之一是本地再做一层物理检测，保证不穿墙。

### Dead Reckoning 与 PVB

   * **航位推算（Dead Reckoning）**

       * > **定义**：源自航空航天航海的老概念——没有 GPS 的时代，凭出发点位置、空速管测得的相对空气的速度与大气风的方向速度（海上还要对抗洋流），推算自身位置并规划路径，最终精准到达目标点。

       * 用在同步里：收到网络包、发现自己的状态跟对方真实状态已经不一样后，不能直接朝对方当前姿态去追（追到时对方又到了另一个姿态），必须预判对方下一步的动作。

   * **Projective Velocity Blending（PVB）**

       * > **定义**：经典的追赶算法——在固定时间 $t_b$（b 即 blending）内，用两次线性插值把本地复制状态平滑地混到对方预测出的真实状态上。

       * 对方上报修正：真实位置应为 $p_0'$、速度 $v_0'$、加速度 $a_0'$；先按牛顿运动定理算出他在 $t_b$ 时刻的预测位置 $p_{T_b}' = p_0' + v_0' \cdot t_b + \frac{1}{2} a_0' \cdot t_b^2$。

       * 两次插值：对速度做线性插值，到 $t_b$ 时与对方速度一致；对位置在"自己这个粒子沿原速度路径继续走出的位置"与"对方路径上的预测位置"之间依次做线性插值——开始完全用自己的位置，越到后面越用对方那条路径的数值。

       * 性质：PVB 并不符合动力学原理（过程中速度、加速度可能一直在变），但到了 $t_b$ 目标时刻位置与速度都跟对方重合、加速度也换成对方的——之后如果没有新的变化，两边结果就是一致的；好处是位置不会被瞬间掰过去，而是逐步追上。

       * 边界：等追到之后新的包又来了、发现中间又发生了新变化，只能重新开始追——复制端的轨迹一直在努力追赶 authority 端的真实轨迹。调试时可在 authority 端反向把 replicated 数据传回来，比较两条曲线的重合度与追赶耗时，再人为加上固定网络延迟看大延迟下会不会出问题。

### 外插与物理的冲突

   * **穿插与弹飞**

       * 双方都在外插时，两辆车其实已经撞到一起，外插过来的位置却不管不顾地插进对方车头；物理引擎检测到刚体穿插，会给它们一个很大的 impulse 猛地推开——看似不重的碰撞被恐怖地弹飞。玩带一点物理模拟的网游见到这种 bug，很可能就是对方用了外插值一类的算法。

       * 这个问题非常复杂、真的很难：要针对赛车、飞机、船只等不同游戏单独考虑、单独设计。

   * **控制权切换**

       * 简单思想：客户端提前进行物理检测，一旦检测到与某面墙或另一个物体发生碰撞，就把位置同步的控制权从网络同步算法切换给本地物理引擎，过一段时间再逐步交还给来自网络端的消息——《看门狗》撞车后约一秒钟内完全交给本地 client 的物理结算，之后交还以保证世界状态同步。

       * 难点一：不同客户端的物理模拟结果不一样（determinism 问题），同一辆车被撞飞时两个世界的飞行姿态不同——位置不会相差非常大，但很麻烦。

       * 难点二：有的算法在预测到可能要撞时，干脆把玩家的控制关掉——利用"人类的反应时间不会快过 100ms"的假设，若提前 50ms 判断要撞车，就把这几十毫秒全部交给双方的插值和位置同步，让结果尽可能一致。

### 内插与外插的取舍

   * **按运动的性质选**

       * 游戏里加速度最大的不是跑车（百公里加速两三秒顶多如此），而是玩家操控的 controller 角色——为了灵活与响应感，角色的加速减速几乎瞬时、跳跃落地经常反物理；真按人类的提速过程或重力系数做进游戏，手感会非常粘滞。

       * FPS、MOBA 的角色移动一般用内插值比较多：相对稳定、安全。

       * 外插适用于整个运动符合物理学规律的对象：开船、开车——给油门调 throttle，位置和速度的变化都符合物理规律，对未来的 prediction 才是准的。类比：自动瞄准打一辆车容易算提前量，打一个翻滚摇摆的人很难算。

       * 真实游戏常把两种算法合到一起：像战地这样的游戏，角色移动用内插确保安全性，上了符合物理学原理的载具就用外插。

       * 方法没有优劣：被造出来的方法一定有它的应用场景，能解决问题就是好方法。

| 对比 | 内插值 interpolation | 外插值 extrapolation |
| :--- | :--- | :--- |
| 基本思路 | 缓存历史状态，在已到达的两点之间补出光滑过渡 | 用位置、速度、加速度向前预测"此刻该在哪" |
| 延迟 | 进一步放大（要留 buffer 的 time offset） | 不放大显示延迟，还能追上真实位置 |
| 风险 | 看到的世界滞后 150~200ms，碰撞易出"罗生门" | 可能插进墙里、死胡同，穿插后触发物理弹飞 |
| 适合的运动 | 瞬移、急停急起等反物理的角色运动 | 服从物理规律的载具运动（车、船） |
| 典型用法 | FPS、MOBA 的角色移动 | 赛车、战舰类；战地里角色内插、载具外插 |

## 命中判定

### 命中判定的本质

   * **命中判定（hit registration）**

       * > **定义**：在延迟与不确定并存的网络环境下，让所有客户端对"这一枪算不算命中"达成一个共识的机制。

       * 追求的是共识，而不是 fact 或 reality：每个人的世界里，开枪的时间点、对方和环境所在的状态、对方所在的位置全都不一样——"这一枪有没有打中"并不存在 ground truth（真实的解），这是让人绝望但必须接受的结论。

       * 这个问题尝试了很多方法，但到目前为止还没有得到一个完美的解决。

   * **hit detection 与 hit registration 的分工**

       * 命中交给客户端来决定，一般叫 hit detection（射击检测）；交给服务器端来处理，才叫 hit registration。

   * **延迟链与三大难题**

       * 敌人从真实出现到被"看见"：经过半个 RTT 同步到服务器 → 服务器先 buffer 一下（攒一批再传）→ 又一段 RTT 传到客户端 → 客户端再 buffer 加内插 offset → 自己的反应时间——真实的物理世界里已发生无数次时间偏移和延迟。

       * 三大难题：敌人到底在哪里（看到的他已比真实的他落后至少两三个身位）；怎么打中一个移来移去、同步又不稳定的目标；掩体问题（他自认已经进了掩体不愿被打死，而我看到他还在掩体之外）。

       * 弹道还要叠加：有飞行过程的 projectile、加重力下坠的抛物线（战地里的狙击枪有下垂）。

| 对比 | 客户端判定 hit detection | 服务器判定 hit registration |
| :--- | :--- | :--- |
| 谁说了算 | 开枪的客户端以本地画面为准，把结果报给服务器 | 服务器把世界状态回拨到开枪瞬间再做检测 |
| 手感 | 精准、符合直觉，能做精准爆头与复杂操作 | 依赖延迟补偿的质量与网络的稳定性 |
| 服务器负担 | 轻，只需做简单验证（如 raycasting） | 重，每个 tick 都要给世界状态做快照 |
| 安全性 | 差，客户端或网络包一破就非常麻烦 | 好，拔网线之类的小动作可以直接无视 |
| 代表 | 早期 PUBG、守望先锋 | 部分敢用状态同步做射击判定的网游 |

### 客户端判定

   * **客户端判定（hit detection）**

       * > **定义**：hit scout——开枪时只以本地看到的东西为准做一次命中试探，把结果报给服务器。

       * 适用特征：玩家极多、难以让上百个玩家跟服务器一起达成共识（PUBG 早期版本即客户端判定，这也是它外挂多的一个原因）；世界非常动态、有大量破坏（战地里可以把屋子一块一块整个拆掉、从拆墙的边缘射击）。

       * 优点：高效、准确、符合直觉——计算麻烦的事全在本地做完，服务器只做很快的 raycasting；客户端判定的射击游戏手感普遍比较好。

       * 三种弹道在客户端用哪种都没问题：开枪瞬间命中、速度无限快的射线（早期射击游戏的设计）；有飞行过程的子弹（Halo 的直线弹，以及慢速到可以翻滚躲开的火箭）；加抛物线的更拟真弹道。

       * 服务器 verification 三件事：验证报告的开枪点是否造假（与服务器上你的位置差十万八千里就认定作弊、踢掉）；验证命中点是否乱说（与被击中者实际位置差得很大即视为作弊，防"本地把所有敌人拉到面前一枪一枪枪毙"式外挂）；从 shoot point 到 hit point 之间连线做 raycasting，看有没有穿过墙体去打人（防开全图透视却无视墙与掩体的低级外挂）。

   * **守望先锋的判定盒**

       * 客户端检测 + 服务器验证：服务器以目标人物为核心做一个比他本人大很多的 box，只要打中那个 box 就算打中——按其公开资料就是这样粗暴地做服务器端 verification，却也成就了不错的设计手感。

   * **相信客户端的代价**

       * 最大的问题是非常不安全：客户端一旦被破解、或网络包一旦被破解就非常麻烦；选了相信客户端，服务器端的检测很多时候基本上是靠蒙的，只能做勉强说得过去的验证，其余交给信任。

       * lag switch 作弊：用软件或硬件把网络当场断一下——没有新包过来，面前的敌人暂时"时间静止"，一枪一枪往面前爆头，过 0.5~1 秒再把网络接回去；时间太短服务器不会判断掉线，却收到一份"相对真实的"击杀报告，对方移动不大时真能得手。

       * 上报 hit 的逻辑写得不好时还能做到无限弹药——根源都是客户端 detection 本身的不可靠。

### 服务器判定与延迟补偿

   * **延迟补偿（Lag Compensation）**

       * > **定义**：服务器收到"张三开了一枪"的消息后，不拿当前状态里目标的位置做检测，而是把世界状态时钟往回拨到"张三开枪那一瞬间他看到的世界"再做检测——即猜测每个 shooter 开枪的瞬间，他的世界是什么状态。

       * 动机：服务器上目标的位置一定比开枪者本地看到的旧（位置本来就是要通过服务器同步的，可能慢 100ms 以上）；拿服务器当前状态做检测，只要对象在运动就永远打不中。

       * 回拨量 = 当前时间 − 各路 latency − 客户端做内插用的 offset；服务器知道 offset，因为跑的是同一个游戏，知道你内插用的什么算法。

       * 前提：服务器在每个 tick 都要对世界状态做一份快照、并保存一段时间形成 buffer——这样 50ms、100ms、150ms 等不同延迟的客户端都能找得到对应的"过去的人"。

       * 生效条件：网络波动基本稳定（不会一直抖），且服务器的 tick 周期、客户端的 tick 周期、客户端的插值算法全部"对焦"过——这是有些射击游戏敢用状态同步把射击判定放在服务器端的底气。

       * 附带好处：客户端的小动作可以直接无视——拔网线就拔，按预测的延迟你肯定打不中。

       * 边界：内插值与外插值在补偿里要单独处理；若外插又叠加了本地物理检测，方法会更复杂。

   * **微调的可检测性**

       * 客户端判定下基本判不出：方案的假设就是客户端不会被 compromise（不被 hack 进去）——守望式大 box 下，客户端微调确实查不出来。

       * 服务器判定 + 延迟补偿下分两种：微调"靶子的位置"（让本地位移与插值算法、服务器自己算的结果对不上）能被判出来；微调"枪口"——通过外挂把枪真实地对准对方去打——服务器端确实判断不出来。

### 掩体与延迟的不对等

   * **掩体的两副面孔**

       * 躲进掩体仍被击中：对方在 0.1~0.2 秒之前开的枪，判的是你当时的位置；而且延迟补偿以开枪者那边的世界为准（这是 fair 的）——在对方客户端里你还没进掩体，所以你被打死了；这种场景下规则对开枪者有利。

       * 掩体后偷窥的先手优势：你已经看到对面来了人，但你的位置还没同步过去，他的世界里你还躲在掩体后；无论先发现还是先开枪你都抢到先手——网络延迟大时，从掩体后冒出来的一瞬间你就是优势方，对方可能 100ms 之后才能看到你。

   * **peeker 与 holder**

       * > **定义**：行话里从掩体后面冲出来的人叫 peeker，在外面卡住位置架枪的人叫 holder；网络延迟大的情况下，冲出来的 peeker 实际上有优势。

       * 延迟之下这个"宇宙"是不对等的：不同的 scenario 会产生不同的优势方和劣势方——网络对战游戏做不好，就容易出现某种操作必然有先天优势。

       * 职业比赛对策：FPS 竞技一般用局域网把延迟控制到十几毫秒，并把服务器的 tick rate 调得非常高，尽可能压低每一个环节的延迟，对双方选手才相对公平。

### 手感补偿设计

   * **前摇**

       * 发动攻击时让角色播放几帧炫酷的起手动作，看似表演，实则给网络同步争取了 50~100ms，能有效降低网络波动下客户端与服务器状态不同步的问题；做动作游戏建议在设计上多做前摇。代价：前摇太长会被抱怨"起手太慢"——没有免费的午餐。

   * **本地先给反馈**

       * 用的是服务器端判定，但本地检测觉得命中时，先播放巨大的雪花粒子、特效或暴击数字（暴击可以在本地做预算）；否则消息到服务器、算完再回来要 150~200ms，感觉像在打空气。

       * > **提示**：本地特效只是让你"感受好一点"的糖；真实的伤害数字——结算——还是以服务器的计算为准。

## MMO 服务器架构

### MMO 与子系统

   * **MMO（massive multiplayer online gaming）**

       * > **定义**：很多很多玩家在多人的世界里 online 连接在一起——不一定是 MMORPG，用户量足够大、玩家彼此在线相连的 FPS 也已经是 MMO。

       * 源头：最早的联网游戏是几个人一起走迷宫、互相竞技；最早的多人 role playing game 是文字游戏 MUD。

   * **一下子多出来的子系统**

       * 玩家数据管理（user management）；匹配（matchmaking）；交易（有的会牵扯真实世界的货币、有经济属性，道具被偷严重时直接产生法律责任，必须严格保护玩家安全）；社交（好友、聊天、组织社群、发公告）；数据系统。

### 三层骨架

```text
  玩家     玩家     玩家 ……
   │        │        │
   ▼        ▼        ▼
────────────────────────────────────
连接层 link
  login server：登录、握手、账号密码验证
  gateway × N：用户唯一入口、防火墙
────────────────────────────────────
服务层
  大厅 │ 每局对战 │ 社交 │ 存储 │ 匹配 ……
────────────────────────────────────
数据存储层（以数据库为核心构建）
```

   * **三层划分**

       * 第一层连接层（link）负责把用户所有的连接管理好，里面有 login server 与 gateway；第二层服务层提供账号、房间大厅、每一局对战、社交、存储等各种服务；最底下是真正的数据存储层，以数据库为核心构建。

       * 这三层就是网游架构最核心的部分。

### 连接层

   * **登录服务器（login server）**

       * 这么复杂的 MMO 服务器本体是必须被保护起来的东西，所有用户都不直接往服务器里连：先跟 login server 完成链接与握手，真实场景一般用 HTTPS 经更安全的加密信道，验证账号密码后才允许登录游戏。

   * **网关（gateway）**

       * > **定义**：用户唯一入口——用户永远只跟 gateway 通信，由 gateway 负责去跟内部的角色服务器、大厅（lobby）服务器、邮件服务器等通信。

       * 本质是一个防火墙：账号密码对了也可能发很多奇怪数据来破解，gateway 要验证所有信息的合法性与有效性；游戏服务器遭遇 DDoS 攻击时，gateway 这边要有一定的拦截功能。

       * 解压缩这些所有操作都在 gateway 里做完，工作任务很重，所以一般同时开很多个、随玩家数量增多越开越多——像公司里接待所有人的客服团队。

### 服务层

   * **大厅（lobby）**

       * 大厅很多时候就是一个游戏场景、一个特殊的游戏模式：不能放技能、不能跟别人打架（有的大厅允许决斗，就要开放一定 gameplay 功能）；作为缓冲池把等待 matchmaking 的玩家管理起来；有的大厅甚至不是真实场景，只是一个虚拟大厅。

   * **角色服务器（character server）**

       * > **定义**：所有玩家属性数据的唯一管理者。

       * 一个角色的数据量轻松达到几兆甚至几十兆，且随游戏时间越来越大（发生的所有事情、获得的所有道具、完成的任务）；这些数据会被各种 server 都来问，若分散在战斗、交易、聊天各处就七零八落谁也管不了，所以必须集中管理，负担特别重。

       * 分工：战斗中发生的事（交易成功获得道具、受了很重的伤）有些不会马上同步过来；"我现在是不是装备了某个道具"这类查询是它的任务。

   * **交易系统**

       * 有非常重的金融属性，安全性要求足够高：每一笔交易保证绝对的原子性，全部可以 rollback；对方 client 交易到一半断线、或服务器异常时，每个 transaction 都要能被准确记录，不出现异常数据。

   * **社交系统**

       * 聊天、邮件看似简单，实际要支持拉黑、组队、开小群组聊天、分频道，写起来并不简单；很多人同时彼此发邮件、聊天时单一 server 会炸掉，所以要分成若干种不同的 server，邮件甚至有专门的邮件 server。

   * **匹配系统（matchmaking）**

       * 把天梯分（ranking 值）差不多的玩家集中到一起，玩起来才相对公平；全球联合匹配的射击游戏还要考虑把延迟相近、延迟不太大的玩家匹配到一起，才能保证大家的体验。

       * 开黑的特殊情况：强行要在一起的没办法，系统只能配合；但一般会把开黑玩家扔进单独的池子去匹配其他开黑的人，否则对那些路人是不公平的。

### 数据存储层

| 存储类型 | 典型代表 | 常放的数据 | 为什么用它 |
| :--- | :--- | :--- | :--- |
| 关系数据库 | MySQL、Oracle | 游戏核心数据 | 强结构化查询；配并行表、冷热表与灾难备份 |
| 非关系数据库 | MongoDB | log、临时 game state | 轻量、访问快；数据量大但查询不苛求及时 |
| 数据仓库 | —— | MMO 的海量历史数据 | 支撑海量检索与验证，如客服找回道具 |
| 内存数据库 | —— | 各服务的中间数据、公共数据 | 高效管理，免去较重的磁盘读写 |

   * **关系数据库**

       * 代表是 MySQL（有钱可以用 Oracle，不过很少听说网游用）；游戏中很多核心数据用它存储。

       * 海量数据面前实际采用类似分布式数据库的架构：同时写时写到好多个并行的表里，确保写的效率、读的效率足够高；万一一台服务器挂掉，数据不会丢掉或毁坏；还有冷热表与各种各样的灾难备份。

   * **非关系数据库**

       * MongoDB 这类轻量 DB：关系库存一条数据要把索引、关系表建好哈希好才能用各种 query 组合查，负载比较重；而游戏 log 一天产生的量可以以 TB 为单位、查询不需特别及时，临时 game state 也基本直接往里倒成一个大数据集。

   * **数据仓库**

       * 处理 MMO 每时每刻产生的海量数据：典型场景是客服从巨量 log、game state 的缓存数据里把你的状态找出来、验证你说的事情都是真的，然后把丢的道具还给你——对一款网游非常重要的能力。

   * **内存数据库（in-memory storage）**

       * 现代网游跑起来可能有几百个 server，产生很多中间数据；随手一扔，查询和管理都会非常复杂——内存数据库效率非常高、把数据管理起来又不用那么重地读写磁盘，在服务器端架构中越来越流行；server 之间的中间数据、公共数据用它可能是更好、更整洁的处理方法。

   * **从数据开始思考**

       * > **提示**：架构 MMO 的网络服务器时建议从数据开始思考——把数据想清楚了，上面各个系统的结构也就清楚了（与做引擎先从数据结构思考同理）。

## 分布式服务器改造

### 拆分的动因与代价

   * **为什么拆**

       * 1 万多个玩家一台服务器扛得住；10 万玩家同时在线可能就扛不住；百万玩家同时在线则无论怎么优化一台都扛不住——解决方法是分布式系统：把各个服务变成可用多个进程同时跑，且服务可以加、可以减，架构就有了弹性。

       * 典型拆法：character server 同时管 1 万个玩家属性一个进程就够；10 万玩家同时登录时一个进程可能一个 CPU 就吃爆了，必须拆成十个服务。

   * **三大新问题**

       * 数据竞争：同一份数据被拆开的这些 service 访问时，彼此不能冲突、不能产生竞争、不能死锁。

       * 幂等性（idempotency）：同一条消息重复到达也不出现异常，能自动把冗余信息过滤掉、正常执行逻辑——这么多服务难免不稳定，消息会冗余地发过来。

       * 部分失败：系统一旦分布式，中间总有地方会挂掉，挂掉之后也不能影响整个逻辑。

   * **会震荡、还会放大的 bug**

       * 服务分得特别开时，一个服务产生的 bug 若没做必要防护，可能在整个分布式系统里来回震荡并放大：错误数据传给另一个服务、被再放大再传出去，RPC 互相调来调去甚至无限震荡。

       * 真实团队遇到过：一个很难被检测的低频 bug 一旦开始震荡就很难发现，却会导致服务器性能急剧下降；把 RPC dump 下来看，才发现有些 RPC 很诡异地被调用了非常非常多次。

       * 构建分布式系统时用的整套架构思维方式已是复杂系统的范畴（震荡这种现象在复杂系统里确实存在）；还要解决各业务之间数据的一致性：同一业务处理完后，A 服务与 B 服务产生的结果必须一致，才能保证业务绝对安全。

   * **行业判断**

       * 早期有些很厉害的游戏整个服务在一台物理机上就跑完；现代网游复杂度越来越高，越来越多服务器架构采取分布式，整个行业处于过渡阶段——预计三到五年内会逐渐成熟并成为行业标配。

       * > **提示**：不建议刚入学还在写基础就一上来搭这么复杂的系统架构——"写"本身其实不难，难的是真的上线测试、把各种边界情况处理掉，那个周期非常漫长；只要 bug 能确定地重现就一定能解决，最恐惧的是上线跑了三天才偶然出现一次、连抓都抓不住的恶劣 bug。

### 一致性哈希

   * **一致性哈希（consistent hashing）**

       * > **定义**：把服务器与数据分别哈希到同一个环形值域上，数据沿固定方向找到离自己最近的 server 作为归属——不需要任何 RPC 查询，就知道每条数据属于哪个 server。

       * 要解决的问题：玩家捡到道具要写进 character server，十个 server（S1~S10）到底存哪个？逐个轮询"在不在你这儿"效率极低。等比分配 id 区间的前提也不成立：character id 不重用、一直往上加，玩家离开后又空出 id，"多少到多少的 id 分给哪个 server"本身不稳定；server 数量还随在线人数变（2 万玩家两个 server 够了、3 万就变三个，事先约定的奇偶划分全被打乱，释放 server 时那些角色怎么办）。

       * 三步：服务器以其 IP 地址、端口号为输入、player 以 id 为输入，各算一个哈希（两种不同的哈希），都映射到 $0 \sim 2^{32}-1$（假设用一个 int 作为整个值域的上限管理）；把整个值域变成一个环——0 的下一个元素就是 $2^{32}-1$，首尾相接；定义一个非常简单的规则（如逆时针规则）：数据沿逆时针找到的第一个 server 就是它的存储，server 存储数据也遵照同一规则。

```text
        哈希值域环（0 ~ 2^32-1，首尾相接）

                 0
                 ●
              ╱     ╲
        S1 ●           ● S2
           │  逆时针归属  │
        S4 ●           ● S3
              ╲     ╱
                 ●
             2^32-1

   数据落在环上之后，沿逆时针撞见的第一个 server 就是它的家
```

       * 增删都简单：把 S2 退出去，原来 S1 与 S3 之间放在 S2 上的数据沿逆时针顺延找到 S3、全部扔给 S3 就好；新增一个 server 相当于把一段环区间从中间对半分开。

       * 为什么叫"一致性"：player 的哈希函数与 server 的哈希函数定下来之后，不需要进行任何 RPC 查询，就知道每个 player 属于哪个 server。对比轮询：RPC 本身就有成本——指令先 serialize、经网络传输、那边还要 deserialize，一次确认一般是两次调用，对方还大概率要做一次至少 $O(\log n)$ 的查询。

       * > **易错点**：⚠️ 哈希函数必须认真设计：函数设计得不好、或 player 分布得过于集中，负载照样不均衡。

   * **虚拟节点（virtual server node）**

       * 在环上再随机哈希出来几个虚拟 server 节点，对环区间做更详细的划分，然后映射回原始的 server——让负载相对均衡；真用一致性哈希写分布式系统时可以去用。

### 服务发现

   * **为什么服务要被管理**

       * 服务不断创生与关停：玩家登录多了，要创建一些 character server、game server 去处理业务；到了半夜玩家走了，这些服务还得关掉。

       * 服务会静默挂掉：几百个、上千个服务里，有的跑着跑着产生逻辑错误自己挂掉了，别人都不知道，其他服务就跟着灾难性地、雪崩式地一起崩溃。

       * 服务互相找不到对方：真实 MMO 里各服务之间的连接像一团乱麻——spaghetti（意大利面），一筷子下去整碗面都起来了。

   * **服务发现（service discovery）**

       * > **定义**：管理服务的创建、发现与恢复的机制；代表工具有 Apache 的 ZooKeeper，还有 etcd（名字大概 stands for /etc + distributed——分布式系统的 /etc）。

       * etcd 用法：服务创建好之后，通过一个简单的注册流程注册进去——带上服务的标识与地址；其他任何服务想找它，用这个标识就能找到；还可以 query"这个服务有没有"；再通过 watch 订阅变化——这服务有什么风吹草动（挂了、异常），马上告诉你。

       * 故障处理：etcd 发现某个服务内存爆了、自己死掉了，就把这个进程杀掉，同时通知所有的观察者，需要重启这个服务的就重启。

       * 服务的 recovery、discovery、management（恢复、发现与管理）在做大型分布式系统时非常重要，是 MMO 引擎必须做的——一款网游的服务器跑起来至少是上百个服务；典型如房间服务器随开局不停创生、加加减减（有的房间可以复用 reuse），管理实际上挺复杂。

## 带宽优化

### 带宽压力的构成

   * **为什么必须优化**

       * 带宽与实战成本息息相关，做 MMO、尤其大场景时数据量特别大；就算付得起钱，数据量不优化会产生拥塞——这是网络协议本身保证的——拥塞产生 latency，latency 过大时有的网关甚至会主动把连接掐断（类似小区策略：你对网关的需求量太大，其他人就没得用了）。

   * **三个因素**

$$带宽压力 \approx 玩家数量 \times 同步频率 \times 单次数据量$$

       * 带宽优化就是对这三个点分别优化：要给多少玩家传数据、大概多长时间跟用户做一次数据沟通、每次同步多少数据。

### 量化压缩

   * **量化（quantization）**

       * > **定义**：把浮点数转成定点数来传输——网游中最常用的数据压缩方法。

       * 动机：表达一个位置要用 vector3 的 x、y、z 三个 float 共 12 字节，速度 velocity 又是一个 vector3；而很多游戏是基本 2D 的玩法、或虽然不是 2D 但人都是贴地的，只传 x、y 就少一个分量。

       * 做法：世界不是特别大时，用 16 位的定点数就能把人的位置精确到以厘米为单位；表达角色朝向（orientation quaternion）有时 4 个字节就够了；为配合精度还会对游戏地图分区——每一个区不弄得特别大，定点数就能表达得非常准确。

       * 在线流数据的压缩方法虽有，但有些网游不一定用——还要考虑 gateway 的负载。

       * 实战效果非常非常好：很多时候很容易就把带宽降下一半以上，对网络游戏体验稳定性帮助非常大。

### 兴趣区域过滤

   * **兴趣区域（Area of Interest，AOI）**

       * > **定义**：以每个玩家自己为中心，只同步他周围值得关心的对象的状态。

       * 动机：开放世界地图方圆几百平方公里，但大部分对象并不重要；近战动作游戏的关注范围更小——只把相关物体传给我，就够本地做各种 gameplay 了。

       * 静态 zone 法：把世界分成一个个静态的 zone、把玩家放进 zone，每个区域之间用 portal（传送门）连接隔开——城外发生的事跟城内没有关系，进到巨大 building 里面后里面的事也被隔开；能非常有效地屏蔽掉大量不必要的状态同步。

       * 真开放世界不希望有传送门，就用 AOI：最简单的做法是给一个半径、在整个世界里做一次范围查询——射击游戏可能半径 300~500 米就是范围（游戏空间是被扭曲过的，500 米之外已经觉得很远），之外不管。

       * > **提示**：加入网游团队做 game server，一上来接触到的很可能就是 AOI：做任何消息的 RPC 同步、任何的状态同步、结算，首先要考虑"我只和 AOI 范围内的物体有关系"；放一个技能、做一个开枪动作都要考虑 AOI 范围。

   * **双重收益**

       * 不只降低带宽，也节约服务器端和客户端的算力：不做 AOI，客户端要对一大堆逻辑状态做更新、负载很大，服务器要把每个角色的状态都传送出去、压力可想而知。

       * 理解服务器端的好比喻：它很像一个快递公司——每个 client 像一个家庭住址，服务器要把包裹发给每个不同的地址，非常辛苦。

## AOI 的实现

### 网格法

   * **zone 划分**

       * 早期网游最常用的尺寸是 100 米 × 100 米一个格子，称 zone 或 region；每个角色扔进对应的 zone——在空间中画格子是个非常鲁棒、非常好用的方法。

       * 玩家站在一个 zone 里时向四周扩展一圈，感知范围为 3×3 共九个 zone，九个格子里的所有人构成他的 AOI 列表。

   * **进出事件**

       * 有 entity 进入或离开这 3×3 范围就发 event：有人进到某个 zone，AOI 列表就被更新；有人离开就删掉；反过来自己进入、退出 zone 也会 notify 其他人各自更新。

       * 实际是相对低频的事情：100 米的格子自己在游戏里跑也得几秒才跨一次，一个服务器一次往往只需要处理几十条这样的消息，没有想象的那么高频。

       * 本质是一次空间换时间：在空间上维护了一个点状的分布结构，用空间的组织换来"查周围有谁"的高效。

       * > **易错点**：⚠️ 格子不是想画多密就多密：画得太密，zone 的数量太多；画得太稀疏，一个 zone 里面的 character 又太多，过滤的效果就没达到。

### 十字链表法

   * **十字链表**

       * > **定义**：把所有 object 沿 x 轴排成一条有序链、再沿 y 轴排成一条有序链，用两条链上的区间扫描取交集求 AOI。

       * 查找：AOI 半径 150 米时，在 x 轴有序链上从自己的位置向前、向后各扫 150 米得到一圈 entity 的 id，y 轴同样处理；凡同时在两个候选集合里的（两个集合的交集）就是 AOI。

       * 任何物体在世界里移动时相应 notify 别人、更新各自的 AOI；本身是一个非常高效的算法，但大量物体高速移动时会有一点维护上的需求。

       * 与画格子之间没有"一定谁好谁坏"，各自选择。

### 预可见集

   * **PVS（Potentially Visible Set）**

       * > **定义**：根据你现在所在的位置，把这个世界预先做好一份可见性集合；不在我 PVS 里面的东西，可以直接不关注。

       * 定位是 AOI 之外更宏观的一层粗筛，提前快速 filter out 掉一大批不关心的对象；对空间分割能力、分割感更强的游戏更实用。

### 按距离调整同步频率

   * **距离分级**

       * 离得近的 object 同步频率略高：身边突然疾驰而过的车、跑过去的人要高频更新。

       * 分级降频：对方在 50 米开外频率就降下来；100~200 米开外每隔一秒同步一次就够——前提是对方没有进行过多的急转弯。

       * 敢降的依据：插值与外插算法基本能保证这个东西平滑地运转，而且那么远的地方你不一定注意到；按远近调频才能让带宽被最大效率地利用，实际做网游能真正节约运营成本。

## 反作弊

### 反作弊的分量

   * **生死线**

       * Steam 的调研：70% 的玩家如果发现别人在作弊，就不想玩这个游戏了——一旦有人作弊，对游戏、对玩家都是巨大的伤害。

       * 心态很矛盾：玩单机游戏时人人都用过作弊神器，可以自己作弊却受不了别人作弊；所以任何 online game 都必须正面面对和解决反作弊。

       * 反外挂实际上是一场长期战、持久战：每天要忍受用户的各种指责，而这件事非常难，是下一代 online gaming 必然面对的问题。

   * **法治差异**

       * 有的国家游戏内作弊直接是违法行为，几乎没人作弊，开发者也就不需要花很多时间写反作弊代码；希望有一天作弊违法能让反作弊压力小很多——但全球落地的可能性还比较小，国家太多、每个国家的法律基础不太一样。

### 作弊的攻击面

   * **改内存**

       * 定位内存中哪个数据存的是最敏感的数据，然后把它改掉——单机锁血的经典手法；很多在客户端做校验的游戏逻辑，作弊器就是在客户端里找到数据改掉。

   * **透明挂**

       * > **定义**：把 D3D 这类渲染 SDK 底层的函数入口重载掉，画画面元素时全部被变成线框——线框世界里所有东西一目了然，防不胜防。

   * **软件注入与破解**

       * 通过一个钩子勾到游戏里、把代码注入到引擎代码里；甚至把客户端整个破解掉。

   * **网络劫持**

       * 不碰系统、也不注入客户端，用第三台机器把网络通讯劫持掉、发一些假消息——同样能产生很多作弊花样。游戏一旦变成 online game，作弊的口子就特别多，会变得非常 vulnerable（脆弱）。

   * **改本地资源**

       * 把本地贴图资源全部改掉（吃鸡类游戏改成发光材质）：穿迷彩、趴在地上全部无视，所有敌人一目了然——相当于直接开了地图透视挂；很多网游最开始遭到的攻击都是篡改本地文件这一类。

### 客户端加固

   * **加壳**

       * 给客户端加个壳：把客户端加密，游戏运行起来时再实时地在内存中把壳解掉，exe 就能运转；有专门的公司帮客户端加壳做保护——对用客户端判定的射击游戏，防止客户端被注入是核心需求。

       * > **注意**：悲观的现实：至少以所知，几乎所有的客户端加壳服务都被别人攻破过。

   * **内存混淆**

       * 把最关键、最敏感的数据在内存中进行加密，只有在用的那一瞬间把它读出来，写回去的时候再把它变掉；这招比较难破解（但好像也有人能破）。

       * 真同步（帧同步）的游戏防的恰恰是偷窥——数据都在本地，怕你看到不该看的信息；策略也正是内存混淆：把高度敏感的 gameplay 数据在内存中加密，要用才读，写回再变。

   * **资源哈希校验**

       * 要求客户端不停地计算本地资源文件的哈希值、上传到服务器进行比较；一旦发现不对，就认为篡改了本地数据、直接踢下线——这基本上是现代 online gaming 引擎都会做的一件事。

### 通讯加密

   * **对称加密**

       * > **定义**：客户端和服务器共享一个密钥，之间的通讯都用这个密钥。

       * 比较简单、快；问题在于密钥存在哪——客户端被破解，别人很容易知道密钥，通讯内容就等于大白于天下（相当于打电话的所有话被人旁听）。

   * **非对称加密**

       * > **定义**：客户端只拿一个公钥，服务器端握着一把私钥，两者不对称。

       * 即使客户端被破解、知道了公钥，没有私钥也打不开数据；代价是速度比较慢、成本比较高。

| 对比 | 对称加密 | 非对称加密 |
| :--- | :--- | :--- |
| 密钥怎么分 | 客户端与服务器共享同一把密钥 | 客户端只拿公钥，私钥只在服务器 |
| 被破解的后果 | 密钥泄露，通讯内容大白于天下 | 拿到公钥也打不开数据 |
| 性能代价 | 快 | 慢、成本高 |

   * **混合加密流程**

       * 建立连接时先通过像 SSL 这样高度安全的网络链接（走的就是非对称加密），登录的时候用一次就够；再用它把一把一次性的对称会话密钥传下去；之后客户端和服务器之间的通讯全部用会话密钥加密——万一被破解只破坏掉这一个客户端、不影响后面所有的链接，而且这把钥匙有必要时还可以不停更换。

       * 网游的网络 traffic 是一定要加密的；做网络游戏引擎，建议把加密作为引擎底层提供的一种服务。

```text
第一步 建立登录连接（只走一次）
   客户端 ── SSL 高安全链接（非对称加密，慢、贵）──► 服务器
第二步 下发会话密钥
   客户端 ◄── 用这条安全通道传一把"一次性的对称密钥" ── 服务器
第三步 正式通讯
   客户端 ◄════ 全部流量用会话密钥加密 ════► 服务器
        （被破解只伤这一个客户端；密钥有必要可不停更换）
```

### 反作弊软件与外挂签名

   * **反作弊软件（VAC、EAC）**

       * 核心工作原理大同小异：扫描内存中游戏的签名——发现游戏被注入了奇怪的代码、或内存里游戏的 checksum/哈希值不对，就知道被外挂挂上去了、被人修改掉了，直接认为你作弊。

       * 盯可疑程序：开着那些经常被使用的内存修改器等可疑软件时，会被检测到并报警"这个账号可能在作弊"。

   * **外挂签名扫描**

       * 外挂程序一般都是牟利的，必然会在网上叫卖；把已知的、别人做的外挂的特征（signature）识别出来，在自己的内存中扫描，只要扫到已知外挂的东西就知道你作弊了——对所有商业性外挂都是非常好的方法。

### AI 作弊

   * **AI 作弊**

       * > **定义**：用人工智能直接从图像里识别出敌人在哪里，再去模拟鼠标和键盘的操作、训练这个机器人——对方是"真实"的操作，前面所有作弊防范方法基本全部失效。

       * 门槛越来越低：像 YOLO 这样的模型已经出到了 v5、v7，在一张图片里自动识别出人，甚至可以通过 skeleton 精准识别哪些是关节、哪些是重要的头部——"枪枪爆头"的门槛持续下探，对抗性越强的游戏越要重点考虑。

       * 防御困境：可以检测虚拟的鼠标键盘操作，但这已经很难；连云游戏也救不了——AI 模拟的就是鼠标键盘操作、读取的就是屏幕信息，照样防不了。

       * 可能的方向："用魔法打败魔法"——用 AI 来识别 AI 作弊，但还在非常早期的阶段；到目前为止也没有想到什么好的方法。

### 统计与人工手段

   * **人力审查**

       * 通过大数据统计发现可疑行为（爆头率、击杀数跟传统水平明显对不上），再让玩家打分判定到底有没有作弊；但并不知道裁判是不是相对公平——听过不少行云流水的高玩被其他玩家误判为作弊然后被干掉；作为威慑无所谓，作为常规手段有点狠，是唯一一个跟技术无关的反作弊方法。

   * **信用模型**

       * 正常玩家的行为有一个 pattern，把开挂用户的信用模型训练成另一个 pattern，不纠结于单次操作，能从浩如烟海的战局数据里 detect 出作弊；前提是写 AI 作弊器的人比较笨——如果只提供一个"辅助瞄准"、让发挥好那么一丢丢、大部分操作还是人在做，发现难度对深度学习算法要求很高，属道高一尺魔高一丈的未来方向。

## 开放世界架构

### 三种扩展模型

   * **副本（instancing）**

       * > **定义**：把世界分成一个个副本：游戏里可能有几万甚至更多的人在一个服务器里，但同时下副本的就那么十几个人，每个副本里面处理起来比较简单。

   * **分区（zoning）**

       * > **定义**：把世界横向地、按空间分块成一个个 zone，人可以在 zone 之间来来去去；难点是怎么把世界做得让人感受不到边界的存在。

   * **分层（replication）**

       * > **定义**：把世界纵向分成很多虚拟的层，把成千上万的玩家分到不同的层上去——很像分布式系统里的 load balance：每层 hosting 约 1 万个玩家，10 万玩家在世界里跑就分十层，数据也能处理。

       * 构建开放世界最重要的是让 game server 具备可扩展性（scalability）：先把这个世界做得足够大、能放入足够多的 character。

### zone 的动态划分

   * **分布不均问题**

       * 几十万玩家撒在一个几千平方公里的很大的开放世界上，分布是不均匀的：很多 zone 里面可能没有人，主城这种 zone 已经塞爆了，可能就要炸掉。

       * 对策：zone 是可以动态创建、添加、划分的——一般用四叉树不断地划分，但划分到一定小的时候就不划分了；里面有很多小细节要处理好。

### 边界 ghost

   * **ghost**

       * > **定义**：当角色进入 zone 之间的 border（边界区域）时，相邻 zone 的服务器上为它做的一个"影子"——B 区的玩家能看到它，但真正的逻辑、真正的行为仍由原来 zone A 的服务器 hosting。

       * 动机：没有 ghost 时，玩家从 zone A 走到 zone B 的瞬间，B 里的玩家会"突然看见你出现"，感觉非常奇怪；进入边界区域（虽然人还在 zone A）就让 zone B 的玩家先能看到你，问题就完美解决了。

       * 因为只处理 border 区域里的情况，ghost 不会太多；本体永远只有一个，逻辑始终在归属的服务器上跑。

   * **跨界切换与防抖**

       * 跨越 zone 时做一次简单的翻转（flip）：entity E 从 zone A 跨到 zone B，本来是"A 服务器里是实体、B 服务器里是 ghost"，把数据迁移一下——变成"B 里是实体、A 里是 ghost"，就完事了。

       * 实做要加一个缓冲阈值：有的玩家专在边界上来回来去地抖动（他其实不知道切换线画在哪），会让两边服务器不停地把数据拷来拷去；一般要求穿过边界 20~30 米才考虑迁移，从 B 后悔往回跑也要跑过一段距离才切回——避免高频震荡。

### 分层镜像与组合拳

   * **replication 的展开**

       * 每个 character 被扔到多个世界的镜像里去处理：一个城市被分成很多层，每个玩家被扔到不同的层，每层平均处理 1 万个市民；其他九层的市民在本层上是一个 ghost，而且往往是虚拟的——很多时候只是在自己需要的时候，才去取一下它的数据。

   * **自适应划分 + replication**

       * 真实构建大世界推荐把两个方法结合起来：空间划分最好要是自适应的（adaptive）——玩家都喜欢聚集在主城、野外大量空置，zone 划多大都不合适，一定是当用户聚集时划分变得更密。

       * 但不能划分得过于密：老是动态切割，数据就会在各服务器之间来回地跑；zone 又不能变得太小——AOI 一般要一两百米左右，zone 太小了数据就老是搬来搬去。

       * 兜底组合：方圆 100×100 米的地方角色数量超过单台服务器的 hosting 能力时，在它下面再用 replication 去分担压力——这两个东西的结合是一个相对完整的解决方案，想做开放大世界游戏可以尝试这个结构。

## 大世界 MMO 的难点

   * **复杂度爆炸**

       * 玩家不是只看到彼此：可以开枪打到远处的敌人、突然把一堵墙摧毁掉，还有大量 transaction 的行为——这些交互让复杂度变成 $N^2$；世界若只是静态地走来走去、say hi、跳个舞、做简单战斗还好，真要能在世界里构建战斗、创造所有的事情，复杂度就非常非常大了。

   * **现状与差距**

       * 今天很多网游的架构实际上还是分房间的架构：用户进入战斗模式时，很多时候还是进入一个个房间；真要让几万甚至几十万人在同一个世界里同时移动、战斗、交易、对话，不仅是 hosting server，连聊天在内的几乎所有 server 都得按分布式、负载均衡的架构重新架一遍，而且要保证它们叠在一起还能 work。

   * **底层引擎的要求**

       * 最早是 Epic 的 Tim Sweeney 在游戏引擎界讲 metaverse（元宇宙）；他自己也讲过构建 metaverse 的底层引擎要求非常高：persistency（持久性）、整个世界的事务原子性等——商业引擎都在往这个方向努力，但还没有人敢说交付了这样的技术平台，可能还需要五到十年。
