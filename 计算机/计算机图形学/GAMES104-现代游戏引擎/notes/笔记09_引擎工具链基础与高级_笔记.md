# 引擎工具链：基础与高级

## 工具链在引擎架构中的位置

   * **资产条件化管线（Asset Conditioning Pipeline，ACP）**

       * > **定义**：位于 DCC 软件与引擎 Runtime 之间的加工层，把第三方软件生成的异构素材加工、组织成引擎可用的游戏数据；整套工具链就处在 ACP 这一层。

       * DCC 指 3ds Max、Maya、ZBrush、Photoshop、Houdini 等生成资产素材的第三方软件，其数据是异构的，必须经过工具链才能进入引擎 pipeline。

       * 场景编辑器、图形化逻辑编辑器（蓝图）、材质编辑器、Shader 编辑器、脚本编辑器等，全部架在 Runtime 之上。

```text
DCC 软件层：3ds Max / Maya / ZBrush / Photoshop / Houdini …
      │  生成大量异构的资产素材
      ▼
工具链（ACP 所在层）：场景 · 蓝图 · 材质 · Shader · 脚本编辑器 …
      │  加工、组织成引擎可用的游戏数据
      ▼
引擎 Runtime：渲染 · 物理 · 网络与状态模拟
      ▼
最终运行的游戏
```

   * **工具链与 Runtime 的体量关系**

       * 引擎 Runtime 的复杂度像一个小型操作系统，现代引擎基本达到千万行级代码；渲染、物理仿真、网络通讯与状态模拟都只是其中一部分。

       * 对一个成熟的商业引擎，工具链的复杂度和开发成本一般会超过引擎 Runtime 本身。

   * **工具链的核心使命**

       * > **定义**：工具链最核心解决的问题不只是编辑与生成游戏数据，而是让程序员、艺术家（artist）、设计师（designer）三类思维方式完全不同的人协同工作的平台。

       * 程序员看到的是数据在运行：场景里有多少个静态物体、多少段动画；艺术家在意"色彩再暖一点、动起来更有质感"这类感性、非定量但敏锐的体验向表达。

       * 设计师看到的是策划数据：在角色前方画出攻击判定方块、划分暴击区与轻击区、标出能打出硬直的位置，在乎打击反馈与数值合理。

       * 工具设计必须充分考虑不同使用者的思维习惯；美术一段约三十秒的搭建操作，就可能同时用到粒子、材质、蓝图等多个工具模块。

## GUI 框架

### 即时模式与保留模式

   * **即时模式（Immediate Mode）**

       * > **定义**：每一帧由游戏逻辑直接告诉 GUI 系统要画哪些控件、直接画上去的绘制模型。

       * 优点是直接、简单、非常快、容易做原型；缺点是扩展性有限，业务压力被压到逻辑这一侧。

       * 代表：Unity 的 IMGUI、开源的 ImGui，以及 Piccolo 的 GUI 系统。

   * **保留模式（Retained Mode）**

       * > **定义**：先把"画什么、尺寸多少"等指令全部存入缓冲（类似图形学里的 command buffer），再由 GUI 自己的绘制逻辑统一绘制的模型。

       * 把业务逻辑与 GUI 绘制分开；扩展性非常强、性能好：指令全部缓存、合批统一处理，不改变就不更新指令。

       * 大部分游戏工具采用保留模式：Unreal 的 UI、WPF（Windows Presentation Foundation）、Qt。

| 对比维度 | 即时模式 | 保留模式 |
| :--- | :--- | :--- |
| 绘制方式 | 每帧由逻辑直接告诉 GUI 画什么 | 指令存入缓冲，GUI 绘制逻辑统一绘制 |
| 扩展性 | 有限 | 非常强 |
| 性能 | 逻辑执行到一层画一次，业务压力在逻辑侧 | 指令缓存合批统一处理，不改变就不更新 |
| 典型代表 | Unity IMGUI、ImGui | Unreal UI、WPF、Qt |

### MVC、MVP 与 MVVM

   * **模型-视图-控制器（Model-View-Controller，MVC）**

       * > **定义**：把数据流变成单行线的架构——Model 单向输送数据给 View 且自身不会被弄脏，View 不反写 Model，修改数据的请求只能经由 Controller 处理、过滤后回到 Model。

       * 1978 年提出，是解耦 View 与 Model 最经典的架构；环流成为单行线后清晰、容易切断、容易管理，如同城市交通的单行线。

       * 至今在 Web 前端仍被大量使用，变种数量是各种模式中最多的。

   * **模型-视图-表示器（Model-View-Presenter，MVP）**

       * > **定义**：更彻底的解耦——View 完全不知道数据逻辑的存在，只管展示控件；Presenter 负责从 Model 取数据呈现给 View，并把 View 的用户交互反馈给 Model。

       * 最大收益是利于单元测试（unit test）：Model 的正确性与 UI 做没做、做成什么样无关。

       * 代价是 Presenter 最辛苦：Model 与 View 两种语言都得懂，写不好会非常臃肿肥大。

   * **模型-视图-视图模型（Model-View-ViewModel，MVVM）**

       * > **定义**：View 与 Model 彻底分开，中间层为 ViewModel，且层与层之间不用代码写死调用，而以绑定（binding）机制声明式关联。

       * View 由不写代码的交互设计师（UX designer）用 XML/XAML 声明式描述、所见即所得；ViewModel 由程序员编写、只定义简单的绑定关系；真正复杂的 Model 各自独立维护。

       * 依赖框架生态：Windows 下首选 WPF，用 XAML 加少量 C# 即可快速搭出 UI；.NET 系框架在 Linux/Mac 支持不佳，跨平台迁移痛苦。

       * > **易错点**：⚠️ View 与 ViewModel 都只是声明，绑定关系是否真的有效、不把系统跑起来无法验证；一旦绑定数据出错，调试相当痛苦。

### GUI 选型

   * 不要自己造轮子：工具链的 GUI 体系需要极强的工程可扩展性，应选最成熟的结构和方案；情急之下用 Qt 也远比自己写一个靠谱。

   * 只在 Windows 下且不考虑跨平台时，WPF 加 MVVM 是好选择，能快速构建所需的各种工具。

   * 前沿方向：用 Web 前端做工具链目前还不普遍；但在"工具架在游戏之上"的架构下，最复杂的部分已交给引擎，交互层用 Web 技术的效率可能很高——行业内部也视之为待验证的开放问题。

## 序列化与数据格式

### 序列化的本质与三条出路

   * **序列化（Serialization）与反序列化（Deserialization）**

       * > **定义**：序列化把内存中的数据打包成可传递的二进制块；反序列化把二进制块解包还原成内存中可解析、可处理的数据。

       * > **易错点**：⚠️ 这对概念的外延远不止文件——可以存成磁盘文件、存成数据库里的一个 block data（用 object id 引用、随取随用），也可以作为网络数据流传输，由另一端反序列化重建出游戏对象。

       * 序列化是网络同步（networking）的重要基础；工具链与引擎每天的工作就是数据的打包与解包。

### 文本格式与二进制格式

   * **文本格式**

       * 人能直接读懂，任何工具都能打开，调试、追踪、分析特别容易。

       * 最古老的格式由程序员随手约定：`.obj` 文件里 `v 0.000000 1.000000 0.000000` 表示一个顶点坐标，`f 1 2 3` 表示用顶点索引组成的三角形。

       * 结构化文本的演进：XML 以树状标注系统装下任何结构化信息，是很多系统的基础，但标号冗余多；JSON 功能与 XML 接近、文件小得多、解析更快；同类还有 YAML。

       * Piccolo 选 JSON 是为了方便阅读与理解——二进制数据出错时常常无从下手；Unity 支持纯文本存资产，CryEngine 也有 XML/JSON 存储模型。

       * 引擎先支持文本资产等于自带调试通道：数据出错先转成文本排查，确认无误再切回二进制。

   * **二进制格式**

       * 存储容量优势明显，读取几乎不需要语法处理；文本要过滤标点与注释、生成 AST、按语义建词典，加载速度慢将近十倍不止。

       * 同一个 FBX 模型，文本版文件接近二进制版的十倍以上；FBX 同时提供 binary 与 text 两种格式，正是为了可调试性。

       * 上线游戏的资产一定要换成二进制；为防破解，资产有时还需要加密。

| 对比维度 | 文本格式 | 二进制格式 |
| :--- | :--- | :--- |
| 文件体积 | 大（FBX 文本版接近二进制版十倍以上） | 小得多 |
| 加载速度 | 需语法解析、生成 AST，慢十倍不止 | 几乎不需要语法处理 |
| 可调试性 | 任何工具可打开，排查容易 | 数据藏在块里，出错常无从下手 |
| 适用阶段 | 开发调试期，相当于引擎的 debug mode | 上线资产格式（可能还要加密） |

### 字节序

   * **字节序（Endianness）**

       * > **定义**：多字节数据的内存字节顺序约定——大端（big endian）高位字节在前，小端（little endian）低位字节在前。

       * 两派之争：Intel x86 是 little-endian，IBM PowerPC 是 big-endian；同样一个整数高位在前还是在后，两派做法相反。

       * > **注意**：只要数据要在不同字节序的机器（Linux 各硬件平台、Mac、Android 设备、游戏主机与 PC）之间流转，字节序就是实打实会翻车的坑。

   * **工程约定**

       * 编辑器平台通常是 PC：把整个工具链统一锁死为 little-endian，编辑器内随便用。

       * 差异推迟到数据出口一次性解决：反序列化加载时（如在 PlayStation 上解压数据）做一次字节交换（swapping），或在打包阶段离线完成（如给主机打包时直接做好）。

## 资产的组织与加载

### 引用、实例与变种

   * **资产引用（Asset Reference）**

       * > **定义**：资产系统中跨文件指向另一份数据的关联，是资产系统、也是工具链最核心的底层逻辑。

       * 无论二进制还是文本格式，资产系统必须支持跨文件引用（cross-file reference），才能把重复内容提取出来复用——1000 栋房子可用 20 种房子的定义表达。

       * 工具链面对的从来不是一坨大文件，而是像网一样彼此关联的成千上万个离散文件：做一个特效可能引用特效蓝图、贴图、动画贴图与动画。

   * **实例（Instance）与定义（Definition）**

       * 一栋房子的定义（definition）只存一份；场景中出现的十次都是它的实例（instance），各放一条引用即可。

   * **变种（Variants）**

       * > **定义**：让用户在工具链里直接对实例化物体做出变化的能力。

       * 动机是艺术家要求所见即所得："这五个房子的贴图我想马上换掉"，而不是先去新建一种定义。

       * 最粗暴的实现是把物体在关卡里再拷贝一份随便改，但数据处理上低效：物体几百个字段往往只改一个；且拷贝后与原始定义的关联彻底断掉，原始物体调整网格时无法传导到拷贝。

### 数据继承

   * **数据继承（Data Inheritance）**

       * > **定义**：一份资产数据声明"继承于哪个数据、哪些 field 被我改掉"，读取时先拷贝原始数据、再套用修改部分生成新数据的机制。

       * 实现方式：在资产格式（如类 JSON 格式）中加入属性段，描述父数据与被修改的字段——类似高级语言里派生类只改部分成员。

### 加载即解析

   * **解析（Parsing）**

       * > **定义**：加载资产时对整个文件做扫描（而非从头到尾依次读），把每个 field 的名字、值、类型整理成 (key, value, type) 对并组织成树状结构的过程。

       * 引用目标可能还在文件后面（如角色的第 3 个动作要用动画 305，而 305 在文件靠后位置才被读到），所以先记下引用，第二次处理再按引用取数构建资产。

       * 无论多复杂的 XML/JSON 文件都是树状结构，类似编译原理的抽象语法树（Abstract Syntax Tree，AST）；"树状结构 + 节点间相互引用"（如同国家—省—市—区—人的层级加交叉归属）就是资产真正的底层结构。

   * **两种加载路径**

       * 文本：先用第三方库把 JSON 文件解析成树结构（dictionary），再通过第二次处理取出想要的资产。

       * 二进制：把树状描述存在文件头部——有多少个 field、名字、类型、位移各在哪里；知道类型就知道要读多久，后续数据即可快速处理。

## 资产版本兼容性

### 向后兼容与向前兼容

   * **向后兼容（Backward Compatibility）**

       * > **定义**：新版本的工具要能打开旧版本产生的数据。

       * 游戏研发周期约 3 年，期间引擎与工具不停升级、字段有增有删；美术 3 年前做的场景必须还能打开。

   * **向前兼容（Forward Compatibility）**

       * > **定义**：老版本的工具也要能正确处理新版本产生的数据。

       * 团队里工具每隔一两天就升级，总有人拿老工具打开未来版本创造的素材，要求不崩、引擎能继续跑；在分布式部署环境里这是刚需。

       * 反例参照：新版 Word 打开旧文档尚可；旧版 Word 面对高版本文件基本只会报"版本号更高，打不开"。

### 兼容的实现方案

   * **手写版本号**

       * 做法：每个资产由程序员手写版本号；旧数据缺的字段塞缺省值（default value），多出的字段跳过不处理。

       * 缺点：系统发育 3、4 年后要兼容的版本号越来越多，是很糟糕的方法。

   * **Protocol Buffers（protobuf）**

       * > **定义**：为每个数据 field 生成一个唯一 id 并保证其单调递增的格式约定；数据更新时比较 id 即可识别字段的增删。

       * 由 Google 提出：其平台有成百上千种不同生态、不同更替频率的软件要来回通讯；写法如 `string guid = 1;`，结尾数字就是该字段的唯一编号。

       * 游戏引擎面对的环境类似：数据 format 可达几十上百种、每种由不同团队维护，艺术家打开一个地图编辑器可能同时面对几十种异构数据；版本兼容性是工具体系鲁棒性的核心指标，网络与分布式部署会让问题更复杂。

## 编辑器鲁棒性与 Command 模式

### 鲁棒性要求

   * 引擎团队在游戏团队里服务所有人；游戏失败时首先被问责的往往是引擎，做引擎要有"背锅侠"的觉悟。

   * 工具链的鲁棒性要求极高：工具一旦崩溃，几百人一上午什么都干不了，全在等这个 bug 修好。

### Undo/Redo 与崩溃恢复

   * **撤销/重做（Undo/Redo）**

       * 所有编辑器到最后最核心的功能就是 Undo/Redo：艺术家发生误操作时，不可能让他删掉数据重来一遍。

       * 游戏引擎里它特别复杂，因为数据编辑相互关联：改房子颜色、在旁边种树、把地面拉高 3~4 米形成土坡（房子和树随之变化）、再自动生成周边 decal——撤销时先删房子会让 decal 出问题，把地形改回去后树的角度也已经不对。

   * **崩溃恢复**

       * 工具做得再好都会崩溃，而艺术家编辑了一小时的东西往往没存盘；这是软件体系里被研究得很透的问题——Word/PowerPoint 崩溃后重新打开有 recovery、undo/redo 依然方便，背后就是标准的命令模式。

### Command 模式

   * **命令模式（Command Pattern）**

       * > **定义**：把用户的所有操作分解成大量原子化的小 command 逐个执行、可按序回退的模式；执行叫 invoke，撤销叫 revoke。

       * 不是每个用户操作对应一个 command——一步操作常常分解成多个 command，以尽量保持原子性。

       * command 要定时存到磁盘（也可存临时文件、内存文件、内存数据库），系统挂了就从磁盘找回。

       * 序列化不由 command 系统自己写，而由数据自身提供标准的 serialize/deserialize 方法：如"创建一个角色"这条 command，就把该游戏对象（Game Object，GO）的全部状态按它自己的序列化方法存下来。

       * 副产品：实现这套系统会变相逼着把引擎写得非常干净、所有操作都能原子化；这套结构一定要在工具链早期就架好——等工具链做大了再补，痛苦程度以"一天上百个 bug"计。

   * **Command 的字段与唯一 ID**

       * 每个 command 有一个唯一且单调递增的 ID、一串 data，是一个 interface；核心函数是 invoke 与 revoke，另需 serialize/deserialize 支持落盘（将来做协同编辑时同样有用）。

       * > **易错点**：⚠️ 唯一 ID 不只是为了去重——它隐含了执行的序列；回退与崩溃恢复必须按原始顺序严格重放，顺序一变结果就变。

   * **三类原子命令**

       * Add（创建对象，可能是一个 GO 或别的东西）、Delete（删除对象）、Modify（改变对象的某个 field，如速度、大小）；无论多复杂的 API 系统，这三类基本都能表达。

       * 文本编辑器的撤销/重做本质就是增加、删除、更新一段 text 三类操作。

## Schema 系统

### 从构建块到分子式

   * **构建块（Building Block）**

       * 再复杂的数据都由简单数据构成：描述一个点光源通常就是一个 vector3 坐标、一个 vector3 方向、一个 diffuse 颜色——如同物理世界用一百来种原子组合出任何物质。

   * **模式（Schema）**

       * > **定义**：一种描述结构（a description structure）——像分子式一样声明一份数据由哪些基础字段构成、每个字段的语义是什么。

       * 例：长方体的 schema 是三个 float（x、y、z 表长宽高），圆用一个 float2 就能表达；按 schema 写出的数据是一致的。

       * Schema 系统是游戏工具链最核心的底层：工具链里流转的所有数据都要用 schema 统一描述和定义，数据彼此之间才能解读。

       * Schema 还能用最简单的元素构建 high-level 数据：如把粒子色带随时间变化的 RGB 通道表达成一组点的集合（curve）。

### 工具读取数据的机制

   * 地图编辑器打开一个角色时，通过 schema 知道它的名字、放缩、用的哪个 mesh、哪个动画，于是面板显示名字与动画、点播放角色就动起来——这些代码全部不是角色自己的代码，而是 schema 告诉每个工具数据的语义。

   * 构建建议：一定要构建 schema 系统；强烈推荐建立 schema 之间的继承；并允许数据引用。

### Schema 的继承与引用

   * **继承**

       * Schema 描述的就像高级语言里的类，支持类似类派生的继承：定义"人"（身高、长相、体重），派生"军人"再加战斗力、血量两个字段，派生"商人"再加钱、经商能力。

   * **引用**

       * Schema 要允许互相 reference data：如车的描述里有些 field 指向另外的资产和数据。

       * 资产间的关联有两种：动态的（数据实例之间真实的关联）与类型之间的关联；角色引用 mesh、动画、行为树，mesh 又引用纹理贴图——在数据定义层面形成关系树。

### 两种定义流派

   * **独立文件定义**

       * 用类脚本语言或 XML/JSON 直接定义 schema，数据干净，再通过代码生成器反射成引擎代码，资产的读、写、编辑全部自动生成。

       * 弱点：依赖代码生成器，schema 与引擎二进制版本容易不一致（检测到 checksum 错就拒绝启动，对非技术同学特别困扰）；文本方式很难定义"这个东西能做什么"（接口与动作），强行靠反射显得笨。

   * **代码内定义**

       * 在 C++ 里定义类、用宏描述"这是可反射的数据"，只挑出希望反射的变量（与方法）；Unreal 与 Piccolo 都用这种。

       * 优势：可直接把方法包进去；数据定义与引擎高度匹配，编译完自成一套，不太会出现两个版本不兼容。

       * 弱点：相对复杂；动数据结构定义容易编译失败或运行崩溃，debug 成本高；对巨型系统的工程稳定性与架构鲁棒性要求很高。

| 对比维度 | 独立文件定义（脚本/XML/JSON） | 代码内定义（C++ + 宏反射） |
| :--- | :--- | :--- |
| 可理解性 | 一目了然 | 相对复杂，要理解反射机制 |
| 与工程的关系 | 数据定义与工程实践彻底剥离 | 与引擎高度匹配，编译完自成一套 |
| 方法与 API | 很难定义接口与动作 | 可直接把方法包进去 |
| 版本一致性 | schema 与引擎二进制易不一致 | 不太会出现版本不兼容 |
| 出错形态 | 检测到不一致就拒绝启动 | 编译失败或运行崩溃，debug 成本高 |

### 同一份数据的三张脸

| 三张脸 | 形态 | 优化目标 |
| :--- | :--- | :--- |
| 硬盘上的脸 | 二进制或文本 | 节约存储空间 |
| 内存里的脸 | 只能是二进制 | 高效处理 |
| 工具里的脸 | 面向人的视图 | 人类好理解 |

   * 硬盘：商业级游戏在意几十 G 与上百 G 的体验差异，上百 G 的文本加载速度无法接受，上线资产用二进制。

   * 内存：一定是二进制，一切以数学运算快为依据（加减乘除、拷贝、增删）；投影矩阵名义上是 4×4，实际往往只用 4×3 甚至 3×3 加一列平移，要做数据压缩。

   * 工具视图：schema 里的 color 数据上是三个整数，工具里点开是符合人类理解的调色板；引擎内部用弧度（数学库的 sin/cos/tan 全基于弧度），输出给用户的却是 270 度、180 度、45 度这样的欧拉角。

   * 每种数据类型都要提供定制不同 view 的能力：default 的简单 view 只放必要可调数据，另备一种展开的丰富 view。

## 所见即所得与编辑器架构

### 所见即所得的价值

   * **所见即所得（What You See Is What You Get，WYSIWYG）**

       * > **定义**：工具里看到的效果与真实游戏运行的效果一比一、百分之百一致——构建整个工具体系的核心精神。

       * 对艺术家：工具是最重要的 preview；编辑器里调的光照、材质质感、人物动作若与游戏实际运行不一致，艺术家效能极度下降，这个材质就没法做。

       * 对设计师：工具是 gameplay prototype 工具——用最快速度、最低成本尝试不同的关卡 layout，感受射击手感、视野遮挡；不能带入玩家真实体验的设计一定是不好的设计。

   * **对生产效率与质量的决定作用**

       * 所见即所得同时决定生产的效率（否则周期变长）与质量；关卡设计师若不能快速看到调整后的关卡、身临其境地在里面走，"这里掉个落石、那里蹦个小怪"这类判断会全错。

       * 困境：编辑需要大量额外信息、额外操作，还要解决同步版本控制，但又要求界面看起来与真实游戏一模一样——两者有时"忠孝不可两全"；公认较好的解法是把工具直接包在游戏引擎外面。

### 从独立工具到架在游戏之上

   * **独立工具链（早期架构）**

       * 把编辑逻辑（如何编辑动画、行为树、管理资产摆放）整体独立出去以保持引擎干净——因为编辑细节非常"脏"：一个拖动物体的小旋钮（gadget）背后要协调自动吸附、按整数角度步进（如 5 度一格）、自动对齐、快捷键在旋转/平移/放缩间切换。

       * 后果：对艺术家所见非所得，设计师也无法直接 play 一模一样的东西；商业级引擎中用得越来越少。

   * **架在游戏之上（现代架构）**

       * > **定义**：工具直接调用游戏本体——地图编辑器、特效编辑器、动画编辑器、过场编辑器（如 Sequencer）下面跑的都是同一个游戏。

       * 结构：在 Runtime 之上加一层编辑层（editing），管理编辑的场景、编辑逻辑与中间数据状态；再往上生成独立的编辑器 UI（GUI 体系）。

       * 代价是对引擎架构要求高（要向上兼容编辑器需求）、维护复杂；但对生产效率帮助巨大，是现代商业级游戏的通行做法，Piccolo 也采用。

### Play In Editor 的两条路

   * **编辑器内试玩（Play In Editor，PIE）**

       * > **定义**：在编辑器里一键进入试玩——对设计师与艺术家都重要：编好的关卡要亲手在里面跑一局感受一下，是现代游戏引擎很核心的需求。

       * 有两种实现方法。

   * **编辑器内直接试玩**

       * 编辑状态无缝切换成游戏运行（Piccolo：角色跑到某一帧切回编辑器，就停在原位保持那个动作）；结构简单、易实现。

       * 缺点：编辑数据与游戏数据可能混在一起，出现"编辑器里没 bug、release 版有问题"（或反之）的错位。

   * **PIE 沙盒世界**

       * 点 play 时把当前编辑的所有东西整体拷贝一份，在沙盒（sandbox）里重建、重置环境后运行；多花一份内存，换来干净、独立、贴近真实发布环境的运行世界，解决数据混染。

       * 大型复杂游戏建议采用这种模型；小型引擎用"编辑器内直接 play"基本够用。

## 工具链面对的真实生产

   * **生产现场**

       * 以大型自研引擎工作室（如育碧）的真实生产为例：有人建场景 layout、有人设计 gameplay；一键 play 后产生各种复杂行为；大量内容由 PCG（程序化生成）自动产出——甚至自动化生成一整座城市；concept artist 定角色与场景外观，再生成大量 3D 模型；最终交付的游戏里所有东西都有语义、尽可能可交互可 play。

       * 工具链上的工具以几十为单位，无法逐一展开；世界编辑器是其中最核心的一个。

   * **游戏类型（Genre）**

       * genre（源自法语）指 RPG、FPS、MOBA 等不同游戏类型；不同 genre 的编辑操作、gameplay 设置、关卡 layout 与组织规范完全不一样——这是工具体系非常复杂的一个原因。

## 世界编辑器

### Hub 定位

   * > **定义**：World Editor（世界编辑器）是一个平台（hub）：把游戏世界的玩法、逻辑、场景内容的构建都作为能"插进来"的东西在其中完成——插件机制在这里接上。

   * 不要一上来就写 3ds Max 式的拖拽、框选逻辑：那会快速得到一个看起来很酷的编辑器，并产生"能与商业引擎 PK"的错觉；商业级引擎的核心不在单个 feature，而在整个体系按什么逻辑架构起来。

   * 它的基本单元解决三类问题：layout（摆放与碰撞检测）、以地形为基础的内容（植被与 decorator 小杂物）、environment（天空、天光、光源）。

   * 同一个编辑器，做动画、做场景、做玩法的人看到的面板完全不一样——它集成很多功能，又向不同用户呈现不同 view。

### Viewport

   * > **定义**：用户与游戏世界交互的窗口；下面跑的就是一个完整游戏，只是打上了 editor mode 的 flag。

   * editor mode 下能做真实游戏不能做的事：相机自由飞行、无视碰撞、物体透明化、debug draw 与线框（wireframe）显示。

   * gadget（小坐标系、选点、grouping、画线）等基础操作用引擎 native code 实现以保证效率，更复杂的逻辑交给编辑器处理；Viewport 最好不要做成 plugin。

   * > **易错点**：⚠️ 编辑器代码必须用宏严格隔离在 editor only 构建里——一个"大家都说好用"的编辑功能忘加宏进了发布包，等于给外挂作者递了现成的函数入口（全图透明、直接选取、自由飞行）。

   * 商业级编辑器常需要多个 Viewport（如做过场动画时一个编辑、一个预览，甚至开更多）：引擎要支持多个 view 共享同一份数据，而不是拷贝几份数据互相同步——后者相当于在本地写小型网络同步；画中画本身也是游戏本体的需求。

### 对象系统与多视图

   * > **定义**：把世界里的一切（飞鸟、NPC、大地、天空、云）都抽象成共同的 editable object——在引擎普通 object 之上再走一步，至少可被选中、移动、旋转、编辑属性；各引擎命名不同（虚幻叫 actor，Unity 叫 object），本质一致。

   * 实战场景的对象数至少几千、甚至上万：数量大到靠文件名已经完全失控；且场景里大量是对象的 instance，数量比资产文件大得多。

   * 因此要提供多种 view：树状归类、layer（植被层、建筑群层、石头层）、group、search；艺术家可锁定或隐藏其他层、专注调自己的部分（如专调天空大气），调完再接回来看整体——model 一份、view 多种，view 可按艺术家习惯定制。

### 属性面板

   * 选中对象（如 NPC）直接编辑属性（如血量）：通过 schema 反射出对象挂载的属性数据，编辑器按属性类型自动生成编辑界面。

   * 几乎所有引擎的 World Editor 都有这个小面板：虚幻叫 details，有的引擎叫 properties。

### Content Browser

   * **内容浏览器（Content Browser）**

       * > **定义**：把资产从静态文件目录变成"资源海洋（ocean）"的资产管理体系——资产扔进池子，按名字检索即得、按项目形成 view。

       * 动机：几十上百个 artist 会生产几万到几十万件资产（动画、三维模型、音效、UI 贴图与动图），静态目录管不住。

       * 前史：早期靠资深 technical artist 按产品预设目录树（objects、foliage、vehicle、weapon，再分贴图/模型/原始数据目录）；规则漂亮但脆弱——续作继承前作资产时说不清该放哪个目录，且目录结构是三四年前定的，无法预判后续变化。

       * 现代形态：文件夹结构仍支持，但只是 view；资产可放中央数据仓库甚至不落本地，按需加载进内存——省去几个 T 资产在上百台机器间来回拷贝的时间，预计算也能提前做掉。

### 鼠标选取

   * > **定义**：World Editor 一切交互的基础——架构没问题的话第一个要写的就是它；编辑器顺手与否很大程度取决于选取写的好坏，有时还要故意模糊一点让艺术家用起来自然。

   * 方法一 光线投射（raycasting）：万物都有包围盒，发射线命中即可——用的是物理引擎或对世界的物理表示；粗选快，但精细选取会被胶囊体带偏（想选角色身后的树，却选中了有几万个三角形面片的角色）。

   * 方法二 object id pass：额外加一个渲染 pass，把每个 object id 写进 frame buffer，取鼠标下的像素直接得到选中的对象；精准但费一点——编辑用电脑本就比玩家电脑好（主机开发机也会多一块内存），可以接受；也因此常出现"我本机能跑、用户机器卡"的错觉。

   * 透明物（粒子、玻璃）不写 depth buffer，会被常规选取过滤：常见做法是在粒子发射器根部放一个虚拟体，选中的是虚拟体而不是单个粒子，选中后即可拖动。

### Transform 工具

   * 平移、旋转、放缩易学难精：DCC 软件给艺术家养成了大量操作习惯——按哪个热键弹出 gizmo、鼠标移到 gizmo 的某个比例时高亮对应的 X/Y/Z 轴，都有讲究。

   * 设计师需要整度数旋转模式：每 5 度一步进，方便快速对齐 90、45、180、135、30、60 度这类常用角度；这类细节想写好往往要几个月的细心打磨。

## 插件系统

### 引擎即平台

   * **插件（Plugin）**

       * > **定义**：允许第三方开发者自由开发并注册进引擎的功能扩展——引擎要支撑的游戏千变万化、开发者不可能预做所有工具，可扩展性（extensibility）由此而来；插件是现代商业引擎最重要的一种开发能力。

       * 现代游戏引擎的本质是一个平台：3ds Max、Maya、Houdini、ZBrush 都靠大量插件适应千变万化的需求；Qt、浏览器同样采用插件结构。

       * 对引擎的要求：提供大量 API 开放给第三方，让其注册功能、定制 UI、编辑世界；插件管理器（plugin manager）负责把注册的按钮、菜单构建起来（如在工具栏加一个 PIE 按钮、往主菜单插一个定制菜单）。

   * **功能 API 化**

       * 引擎自己的编辑功能（关卡编辑、地编、自动 grouping、prefab）也应尽量通过调用 API 组合，使第三方插件与官方功能彼此平等、不受强限制。

### 插件接口的版本化

   * 引擎内核不停升级，而成千上万人写的插件不可能保证同步升级；做法是对接口版本编号：插件包声明所依赖的 SDK 版本号——版本号不变则插件有效，引擎要变接口时该插件判定无效。

   * > **易错点**：⚠️ 引擎开放了接口，却根本不知道插件作者会怎么用——他可能用完全想不到的方式通过接口改了内部数据；等内部结构升级，他的插件崩了，而接口函数与提供的服务都没变。这是最难的设计功力之一，入门阶段不必强求。

### 插件矩阵与四种模型

   * **插件矩阵**

       * World Editor 的插件空间是一个矩阵：横向是各系统/组件维度（mesh 编辑、particle、动画……），纵向是各对象类型（NPC、环境、鸟群 flock、天空……），每个交叉点都是一次插件落点。

       * 横切还是竖切？答案是都要：粒子系统适合按系统横切做成独立插件而非内嵌功能（将来要加 GPU particle 时加一个插件最简单）；NPC 行为插件则纵向影响一个对象——随机外观、性格、动画、AI 行为与可交互物；插件要能对世界施加纵横双向的影响。

   * **四种插件模型**

| 模型 | 机制 | World Editor 中的实例 |
| :--- | :--- | :--- |
| 覆盖（override） | 新插件整体盖掉旧插件的功能 | 球形世界的地形插件盖掉引擎自带地形插件 |
| 分布式（distribute） | 各插件独立工作、互不影响，结果合并 | 粒子、打光部署等互不相干的插件 |
| 流水线（pipeline） | 数据一个串一个，前者输出即后者输入 | 几何切割插件先切碎对象，物理插件接力设物理属性 |
| 洋葱圈（onion） | 与其他插件同时读写同一份数据 | 规则系统读地形/植被插件数据，处理后再写回 |

   * 设计原则：真实 production 的需求来时各种模型都会用到，架构上必须保持很强的开放性，不要预设所有插件按某一模式走——软件工程是在"严谨性与一致性"与"为复杂场景必须妥协"之间找平衡。

## 地形编辑与规则系统

### 高度笔刷

   * **高度笔刷（Height Brush）**

       * > **定义**：在高度图（heightfield 加 texture）上刷出山体的笔刷；地形本体就是高度图，可由 PCG 程序化生成。

       * 真正决定手感的不是笔刷种类，而是对有限密度网格信号的合理化平滑（smooth）：艺术家说"拉不出想要的山形"，差距不在形状库，而在过渡是否自然。

       * heightfield 网格三角形沿某一轴向斜排（像一块被切割的布），拉得不好会出现沿切向的明显过渡棱，高度场有"锯齿"感。

       * 必须留扩展口子：支持艺术家导入自定义高度图、自定义笔刷——做工具的第一问是"扩展性有多强"，不是"算法有多强"。

### 实例笔刷

   * **实例笔刷（Instance Brush）**

       * > **定义**：大面积刷出独立实体的笔刷——刷小草（detail/decorator）与树的主力。

       * 每棵树独立存储、属性全部静态存放：所见即所得——这里偏黄的树，游戏跑起来就是偏黄的；对单棵不满意或想挖条小道，一棵棵手改也没问题。

       * 缺点：几十平方公里的实战关卡里，仅存树的位置内存占用就非常大、预处理麻烦；更大规模要靠 PCG 解决，但它仍是关键笔刷。

### 光源与环境

   * 第三类笔刷是大量光源的摆放；随着 GPU 能力增强，游戏研发越来越像电影行业——气氛靠大量辅助光源、滤镜、天空云层与天光打出，如同电影片场用辅助光刻画角色与渲染氛围。

   * 这些 environment 由各种插件协作完成——World Editor 必须给它们留出空间。

### 规则系统

   * **规则系统（Rule System）**

       * > **定义**：用一套以图（graph）表达的程序化规则，处理地形元素彼此之间的约束（道路 × 植被 × 建筑 × 水系），自动生成合理分布——环境编辑的灵魂。

       * 以一条路为例：路上与路边不长树和杂草；路随 terrain 起伏，又反过来切割 terrain（路要平，很少修成倾斜十度十五度）；碎石沿路两边形成路基。

       * 不做规则化的代价：艺术家手工砍树、清杂物、修地形，工作量巨大；更致命的是设计师一句"路这样修战斗没法打，要加个拐角设埋伏"，前面所有手工工作全部重做——所以必须程序化。

       * 做法：原始数据分层存放（道路分布、手绘树木分布、房屋/物件分布、河流水系，含"房旁多少米内不长树"这类约束），规则用 graph 表达，由规则体系生成合理的植被与物件分布。

       * 关键性质是局部性（locality）：树的分布允许随机，但修改一个局部时，已经生成好、已经满意的区域不能全部重新生成——generated data 具有局部性是实战化 World Editor 的重要属性。

       * 真正的难点：定义一套简单、易懂、好维护的形式化语言，让设计师自己写规则；规则还能细分到气候与地域（热带与寒带植被规则不同、东半球与西半球有细微差异）与城市风格（亚洲、日本、欧洲、美国大都市各不相同）。

## 时间轴与线性叙事

### Sequencer 的骨架

   * **时间轴（Timeline）**

       * > **定义**：让世界里的每个对象、每条属性都能定义"在什么时间变成什么值"的线性表达体系；游戏的叙事（storytelling）——每个镜头、每道爆炸、每次入场——都发生在时间轴上。

       * 以虚幻的 Sequencer 为例：每个对象（虚幻称 actor）定义 track；track 里任何一条属性都可定义在时间轴上的变化；关键变化节点设 keyframe（关键帧），相邻 keyframe 之间用线性或曲线插值；合起来形成一个 sequence。

```text
timeline ─────────────────────────────────────▶
│
├─ 角色 track：动作（打招呼 / 开枪 / 躲掩体）  K1────K2────K3
├─ 特效 track：爆炸                            K1─────────K2
└─ 声音 track：背景音进入
     相邻 keyframe（K）之间做插值：线性或曲线
```

   * 多个对象的 timeline 对齐后一点播放，画面里"一个演员读书、另外两人聊天"就同时发生——但工程上是每个演员的每段动作、每个时间拆分逐个做出来的。

### 时间轴的应用面

   * 最小示例的完整链路：把小鸡绑成 actor → 获得 track → 把 transform（位移）绑成 property track → 在各位置设 keyframe → 插值形成来回走动的路径规划；track 改的就是 component 的某个 parameter（transform 的位置）。

   * 应用远不止剧情：特效、UI（暴击后击杀头衔、击杀播报、暴击率一连串时序展示）、光源与天空光照控制、场景切换（过场动画里偷偷换场景）都靠同一套 timeline 体系。

## 反射系统

### 反射的定义与价值

   * **反射（Reflection）**

       * > **定义**：代码写好之后，系统能告诉你到底有哪些新功能被暴露出来；其他调用者不需要与你的代码链接、编译到一起，就知道这些接口的入口并能调用它们。

       * 反射是 Sequencer 的 foundation 之一：schema 只负责描述，真正找到数据、set/get、invoke 要靠反射打通"工具 → runtime 对象数据"的链路。

       * C/C++ 没有反射（代码是 native 的，扔给机器就跑）；Java、C# 这类高级语言全面支持反射；早期引擎常用奇怪的模板 hack 模拟"不重新编译就能找到并调用方法"的感觉，有了反射后回头看全是无用功。

   * **工具为什么需要反射**

       * 引擎不可能预知未来游戏的 gameplay（机关顶起射箭、箭再拉动别的东西这类逻辑写不进引擎；数据配置也配不出所有玩法——数据本身也是一种语言，任何语言的表达都有上限），必须允许游戏团队不断扩展玩法与接口。

       * 反射在代码与工具之间造了一座桥：引擎功能写好后，反射生成一张表——开放了哪些类的接口、哪些功能、哪些数据可访问——并生成一堆 invoke（调函数）与 set/get（改变量）；工具据此就能在可视化脚本里创建"人"节点并自动展示其身高、血量与走跑跳。

### Visual Scripting 的动机

   * 可视化脚本（Blueprint 只是其中一种，思路类似低代码/零代码开发）的核心难题是可扩展性：节点若预先写死，游戏每加一个新动作，工具层就要加代码、加接口、保证 invoke 正确——不可扩展也不可维护。

   * 有了反射，脚本节点按类型自动呈现：动作接口可 invoke（三角标记、动作流），属性（property）可显示、可编辑——用 modifier 就能写出"血量减武器伤害得新血量"这类计算。

   * 为什么不让设计师直接写代码：为语言搭建编译环境、按语法写不出错，对设计师与艺术家门槛太高；"红接口连红线、蓝接口连蓝线、三角对三角"才是他们最自然的表达方式——visual scripting 能把引擎开放给足够多的用户。

### 基于编译前端的实现

   * 实现原理：现代语言的编译流水线是固定的——语法分析（parsing）→ AST → 中间代码 → target code；把源码喂给开源编译器 Clang，就得到一棵好解读的树状表，可从中提取任何类的接口函数与成员变量，且不区分语言。

   * 选 Clang 的理由：开源、模块化可自由加载、稳定成熟被最广泛验证；Piccolo 生成的 schema 只存内存、不落盘。

   * 精准控制：引擎几万行代码、几百个数据结构，不是全部都要反射——只有与资源打交道的数据才需要；描述词有两类：CLASS 宏（标记整个类的成员变量都反射）与 whitelist only（类里只有带 meta enable 标记的成员才反射，因为有些变量只是计算中间结果、不需要在内存与磁盘间交换）。

   * 底层机制：靠宏实现——正常编译可执行文件时这些标记全部无效；编译反射时用 ifdef 把它们 define 成标识；Clang 的 attribute 关键词里有一种类型叫 annotation（标记），标记会以 attribute(annotation) 的形式出现在生成的 AST 里，检测到即可知意图——看似神秘，实为一个简单的字符游戏。

   * 这套方法与 Unreal 反射的基础方法与结构非常接近，看懂它就不觉得 Unreal 的反射难。

### 反射的效率边界

   * 对引擎本身没有影响：反射代码不用就不产生任何 overhead。

   * 开销只出现在工具侧的频繁调用：工具里通过字符串查 map 找函数指针再做 get/set/invoke，大批量编辑（刷草刷子一次 set 大量物体属性、Sequencer 改大量 parameter）时有性能开销；可把字符串优化成 string id 加快查找。

   * runtime 不受影响——反射主要是编辑期使用的东西。

## 代码渲染

   * **存取器（Accessor）**

       * > **定义**：为每个反射类型生成的三类函数——get（取数值）、set（改数据）、invoke（找到方法并调用）。

       * 几十个反射类的 accessor 不可能靠程序员手写：代码冗余，且违背"接口自动生成"的初衷。

   * **代码渲染（Code Rendering）**

       * > **定义**：用模板加数据自动生成源码的技术；Web 前端早有先例——页面逻辑大同小异、只有数据不同，模板渲染即可自动产出。

       * 三大好处：大量减少冗余代码开发；减少犯错（渲染出的代码一次调通后几乎不再出错——自动生成的代码若会出错早就错了，生成 100 万行也不会错）；把数据和逻辑彻底解耦。

       * 架构准则：大型系统能自动化生成的代码就尽量自动化生成——手写过程不可控，昨天生成的没问题，后天手写的版本就可能有问题。

       * 工具选型：模板引擎 mustache（原意"胡子"，因模板里大量大括号得名），简单且稳定。

```text
C++ 源码（带 CLASS / whitelist only / attribute-annotation 等标记）
      │ Clang 解析：检测标记，提取类、成员、方法
      ▼
    AST ──▶ schema（在内存中生成，不落盘）
      │ + 预先写好的代码模板（mustache）
      ▼
    accessor 代码：get / set / invoke
      │
      ▼
    引擎里定义的任何一个结构，编辑器里就能看到、改到、调到
```

   * 实战检验：给角色新增自定义属性（如血量、摔落高度与摔落伤害）走的就是这条链——CLASS 宏标记新字段（需与资产文件交换的数据才反射，纯计算中间结果不必）→ Clang 生成内存 schema → mustache 渲染 accessor → 编辑器属性面板自动出现并可编辑 → JSON 资产文件里读得进、存得出 → gameplay 逻辑读取生效。

## 协同编辑

### 协同编辑的动机

   * 3A 与开放世界的数据量和维度远超一个人能 handle 的范围，客观上需要几十上百个 artist 共同编辑而互不打架。

   * 纯程序化生成不够：游戏的核心是 novelty（新鲜度/生动度/创新度），程序化算法的 pattern 容易被玩家识破，仍需要大量艺术家灵光一闪的创意。

   * 传统做法：把场景分成很多文件让各人编辑、最后 merge——笨但有效。

### 三种世界划分

| 划分思路 | 核心想法 | 好处 | 别扭之处 |
| :--- | :--- | :--- | :--- |
| 分层 | 按地形、植被、建筑分层，各管一层 | 最古老，引擎很早就支持 | 层间相互依赖难分干净（地形一改植被跟着变），难同时开工 |
| 分块 | 世界切块，谁的地块谁负责 | 简单直观、立刻可用 | 山脉、湖泊、房子跨界难归属（cross boundary）；边界割裂感玩家接受不了 |
| 一对象一文件 | 每个对象一个文件，各改各的（One File Per Actor，OFPA） | 从根上消灭冲突 | 海量小文件拖垮版本管理（一次提交上万文件，Perforce/SVN 会卡住整个工作室）与 cooking（须打包回 level 文件；操作系统最恨小文件） |

   * 分层的变通：几个 artist 轮流做，前一个完成后锁定分层，下一个基于它继续——同时开工时效果很差。

   * OFPA 是值得关注的激进尝试：每个现实问题总有技术能绕过，而它确实彻底解决了协同编辑里的冲突。

### 实时协同的架构

   * 终极形态：多人在局域网（工作室内部网性能高）同时编辑、彼此可见；真正的难点不是状态同步，而是保持语义的高度一致。

   * **原子化 command 是地基**：把每个编辑操作（拖动、选取、平移、改颜色、改材质、改参数、Sequencer 里 keyframe 的增删）都变成原子 command，在所有人电脑上同步 command——没有这个基础，协同编辑一定是 hack，用起来处处违反直觉。

   * undo/redo 是协同编辑最难的问题：想象小朋友共画一幅画——紫线画在蓝色之上，绿点一半在蓝一半在紫，此时紫色想撤销，绿点与紫线是什么关系？错综的操作交错让撤销语义极其复杂。

   * 最简单的手段是加锁：对象锁（声明这片语义都是我的）会引入竞争；资源锁（这资源我锁上了、几十毫秒内同步给所有人）适合"我改材质时不想让别人同时改"的场景；但即使两种锁都有，undo/redo 交错仍可能让别人基于你旧版本的操作当场崩掉。

   * 理论方法：OT（Operational Transformation，操作转换）非常理论化、很难；引擎里更常用 CRDT——通过一套规则让冲突变成 conflict-free，各终端状态皆可同步。

   * 主流工程方案（C/S 结算）：客户端不直接 apply 操作结果，而是把操作发给 server 统一结算，再把最终结果发还各端——没有争议，代价是一点点局域网内可接受的延迟；风险是 server 端机器崩掉会带走一群人，健壮性需要专门设计。

```text
客户端 A ──操作──▶┐
客户端 B ──操作──▶┤  server：收齐所有操作 → 统一结算 → 最终结果
客户端 C ──操作──▶┘
        ◀────── 最终结果统一发还给每个客户端 ──────
```

   * 行业现状：协同编辑仍处早期阶段（已是新一代引擎的重点方向）；基础理论基本成熟，剩下的是海量工程问题——千万行代码的引擎要全面支持协同且不丢功能、处理大量向前兼容；文字协同软件走过多年迭代才顺手，本地软件的强大性至今仍胜过协同版。

## DCC 与引擎工具的边界

   * **边界的动态性**

       * DCC 工具与引擎工具的分工边界是动态的、一直在变，看到的是大量融合而非分家；根本逻辑是引擎作为生产力工具，一切以艺术家方便为准。

   * **两个融合方向**

       * DCC 一侧：3ds Max、Maya、ZBrush、Houdini 越来越强，倾向让你在它们内部做尽可能多的事，提供类引擎 runtime 的 preview，甚至可以把引擎集成进去做 viewer。

       * 引擎一侧：前沿引擎把 DCC 功能直接集成进来——如在引擎里直接手 K 动画：让角色的手精准抓住场景扶手说话，传统流程要把场景导进 Max/Maya、摆好再导回引擎并对齐朝向位置大小，极其痛苦；引擎内直接 K 完事；有的引擎甚至直接把 DCC 工具买进来集成。

   * **融合的理由**

       * 每多一次 exporter/importer 的数据倒手，就多一次出错机会，且拉低内容生产效率与直观性——融合趋势因此特别明显。
