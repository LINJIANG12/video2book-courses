# 面向数据编程与引擎架构演进

## 引擎的算力困境与并行动机

   * **引擎的性能处境**

       * 游戏引擎跑在各种各样的操作系统与硬件之上，对性能要求极高：要在 1/30 秒里完成大量逻辑运算与物理模拟，还要一瞬间渲染出几百万、上千万个像素里无数的光的反射积分；玩家还不满足——要 60 帧，打电竞要 120 帧。

       * 所以设计游戏引擎实际上要把操作系统与硬件的性能几乎压榨到极限——重型游戏团队与引擎团队基本上都是硬件和操作系统性能的大师。

   * **单核性能天花板**

       * 集成电路工艺已经几乎撞上量子力学上限：制程还在冲 2nm 量级，但理论极限据说只有 0.5nm 且几乎不可能达到。

       * 主频基本停在三点几 GHz 上不去；个别 CPU 能冲到四点几 GHz，但散热的声音已经吓人——再往上散热与功耗都有很大问题。

       * 于是 CPU 走"更多核"路线：四核、八核、十六核已是常态，必须想办法把这些核的算力全部利用起来。

       * > **提示**：单核性能天花板由物理规律决定，性能增长只剩"更多的核"这一条路；并行编程的全部动机，就是把散落在各个核上的算力重新收拢回来。

   * **并行化的两类问题**

       * 第一类任务彼此独立：不打断、各自算完再一起收口，不会有 thread interaction 或 thread swapping 问题；最简单的案例是蒙特卡洛积分——每个线程撒 1000 个采样点，合起来采够 100 万个就完成。

       * 第二类是真实游戏的情况：各系统之间有大量数据依赖，还有 dependency（等你这件事做完我才能启动），这让并行编程变得非常复杂。

## 进程、线程与调度模型

   * **进程与线程**

       * > **定义**：进程拥有独立的存储单元，存储完全独立、由系统管理；线程在进程之内，与其他线程共享同一份 memory。

       * 线程间交换信息靠共享内存本身就是通道；进程间必须通过特殊机制才能交换信息——这是所有并行化编程的基础。

       * 线程比进程轻量很多（Windows 下的情况），但线程写不好会互相内存"打架"；在 Linux 下进程也可以做得很轻量。

   * **游戏引擎天然 multi-tasking**

       * 引擎要同时做动画、物理、逻辑与 rendering，天然就是多任务系统，有四核、八核、十六核就直接用起来。

   * **抢占式与非抢占式多任务**

       * 抢占式（preemptive）：调度者随时把线程调出去、过一会儿再调回来，例如来了 high priority 的事情就中断你；Windows 这类通用操作系统就是抢占式——不可能让一个进程把整个系统资源吃光。

       * 非抢占式（non-preemptive）：不主动打断正在干活的任务，除非它自己说结束；任务都是你给的所以控制力很强，但一个任务写坏了占着资源不走，其他所有人陪等；通用操作系统里很少用，real-time 要求极高的系统会采用。

   * **线程切换的真实代价**

       * 20 个线程跑在 4 个核上就要来回切换；一个线程被打断要触发一次中断，至少花 2000 多个 CPU cycle——而最快的指令只要 1 个 cycle。

       * 更麻烦的是现场切回来时，新进线程面对的数据不在它的各级缓存里，要从内存重新调，延迟可能在 1 万甚至 100 万个 cycle 之间。

       * > **提示**：线程之间的切换很贵很贵；Job System 之所以设计成 fiber-based，正是意识到了这件事非常昂贵。

## 数据竞争与锁

   * **数据竞争（data race）**

       * > **定义**：同一个数据，当一个线程在读它时另一个线程正在改它——"读完值、根据它做判断、再做操作"的逻辑里，读的时候是一个值，真去操作时已经被改成另外的值。

       * 它是围绕所有并行编程的核心问题：死锁与种种乱象的核心都是这件事。

   * **临界区（critical section）**

       * > **定义**：同一时刻最多允许一个线程进入执行的代码段——从我进去到我出来必须完整执行完，在别的线程里这段代码不能被同时重复执行。

       * 现代编程语言的实现手段：显式定义的 critical section、mutex（互斥量）、semaphore（信号量）等，都属于阻断式方法。

       * 典型用法：学生注册往计数器加一、再把记录塞进单线程数据库的表——每个写库操作用 mutex 控住，同一时刻只有一个人能进这段代码。

   * **阻断式同步的三个问题**

       * 死锁：一边写着一个变量、一边又在等另一个变量，很容易互相卡死。

       * 连坐：并行启动几十上百个任务的大型系统无法保证每个 task 都成功，一个 task failure 甚至 crash 会导致整个系统死锁。

       * 僵化：一旦进入 critical section 就被彻底保护，更高优先级的任务按现行调度算法也打断不了它——一种很古典的架构。

       * > **提示**：架构大型系统时 lock 的原则是能不用就不用，要用也是越少越好。

## Lock-free 与 Wait-free

   * **原子操作（atomic operation）**

       * > **定义**：由硬件在指令级保证不可分割的内存读写——对一个变量的读写操作不会被多个任务同时侵占；它保护的是一个值的一次操作，而不是一整段代码。

       * 两个核心概念：load（把数据从内存读出来看一眼）与 store（往 memory 写进去）。

       * 在此之上的一系列原子指令：RMW（read-modify-write，读-改-写）与 CAS（check-and-set，先检查再设置）。

       * 核心想法：不把一整段代码锁住——段里有崩溃、有什么问题你是控制不住的；只在一条绝对保证能执行下去的指令里，保证对单个内存数值（一般是 integer，也可以是布尔）操作的原子性。

   * **Lock-free 的收益与局限**

       * 收益：通过原子操作尽可能避免死锁。

       * 局限：原子变量之间彼此等待、彼此依赖，CPU 时间线上仍会产生大量空洞——那段时间 CPU 在 idle，干等其他任务启动。

   * **Wait-free：理论上的满分答案**

       * 有一套数学方法，保证多线程研发中尽可能把所有 CPU 资源全部占掉。

       * 给一个非常复杂的系统、保证彼此之间对 CPU 的利用率百分之百，这件事几乎不可能；但对一个具体结构（比如一个队列）把操作做成 wait-free，行业里已经有解法。

       * 适用场景：对性能 critical 的应用（比如高频的通讯协议）；并且需要严格的数学和推演证明，证明它不会产生前面那些异常。

       * > **提示**：做引擎掌握到 lock-free 这一层就可以了，剩下的空洞 Job System 能相对好地解决。

## 乱序执行

   * **编译器乱序**

       * 现代编译器只要保证顺序执行下来结果一致，就认为是一次有效编译，完全可能把代码优化成两段无序的汇编。

       * 经典例子：线程 1 执行 `a = b + 1; b = 0;`，线程 2 等 `b == 0` 后断言 `a == 2`——编译器认为 a、b 是两个无关变量，用临时寄存器先把要写的值备好、把"b 设为零"提前，a 却抢先用了 b 的旧值设成 2；于是看到 b 为零时"a 已经完成"的假设不成立，断言炸了。

       * > **易错点** ⚠️：单线程下，乱序优化完全无害——只要结果一致；可一旦有另一个线程也在盯着同一批数据，"我按顺序写的"就不再等于"它按顺序执行"。跨线程共享的数据，永远不要依赖"目测顺序"。

   * **CPU 硬件乱序**

       * 从 x86 到 PowerPC 再到 ARM，很多 CPU 并不保证按代码顺序依次执行；ARM 为追求功耗和性能把架构做得尽量简单，会把上百行的函数切成大几段、变量一通乱替换，最终只保证结果一样。

       * 这就是移动端"PC 模拟器上完全正常、真机上突然 down 得死去活来"的常见原因。

       * 根因：CPU 要从内存反复读出数据和指令，而它速度太快、总是饥饿地等数据，于是恨不得把一大段函数切成很多股一股脑扔进去，让指令和数据同时流动；现代编译器基本按同样原理优化。

   * **顺序约束的代价**

       * C++11 起可以显式要求编译器确保执行顺序一致，代价是执行性能变得更差。

   * **debug 版正常、release 版挂**

       * > **易错点** ⚠️：debug 版只是让执行顺序贴近书写顺序，把问题暂时藏住了；release 一开优化，乱序执行立刻把隐含的顺序假设全部戳穿——这类 bug 非常难查，因为根本不知道编译器的优化做成了什么样。

## 并行架构的三种范式

   * **固定线程**

       * > **定义**：每类任务分给一条专用线程——rendering 归渲染线程、simulation（如物理）归模拟线程、游戏逻辑再给一条，井水不犯河水，彼此在每帧开始时交换一次数据；很多古典引擎就是这个架构。

       * 在两到四个核的情况下真的很好，切分得非常清楚。

       * 致命短板是木桶效应：几条线程的 workload 很难一样，所有人都得等最慢的那条做完，这一帧才能结束；凭经验大约有三分之一的计算资源被浪费（经验数据）。

       * 数据挪不动：一条线程访问的数据要 locality 集中（如渲染的基础数据集中在一起），看到别的线程有空就把访问挪过去，多线程同时读写一块数据，data race 就全来了。

       * 负载随场景变：有的环境渲染特别慢，换一个环境角色敌人特别多、逻辑忙不过来，而这些发生在同一个游戏里——不可能让玩家玩到不同阶段时动态改线程分工，那会导致更多 bug。

       * 核数不匹配的尴尬：四条线程跑在双核机上，只能是两条线程在同一个核上来回竞争切换；玩家配了八核十六核，又不可能为此动态改线程分布——很多游戏感觉卡住了、CPU 资源却没占满，就是这个原因。

   * **Fork-Join**

       * > **定义**：跑到重活处，把固定线程手里的任务 fork 出去，扔给预先申请好的一批 worker thread；做完之后把线程收回来，把结果合到一起。

       * 适用对象是一致性非常高、计算量又很大的运算，例如动画结算里成批的平衡方程、线性代数与矩阵运算——全部可以拆开来算。

       * worker thread 的数量很多时候就是问操作系统"你有多少核给我"，有多少开多少，所以多核适应性比固定线程好；基于 Unreal、Unity 做的游戏基本走的都是这条路。

       * 局限：只在成批同类任务处并行，整体仍难以 balance，执行时间线上还是有很多 gap。

       * Unreal 的形态：named thread 明确分工（这条跑游戏逻辑、那条跑 rendering），之外还有大量 working thread，物理这类可以整体展开的计算扔上去。

       * 总评：比较清晰、也比较鲁棒的架构，对多线程要求不高时是非常好的选择。

   * **Task Graph**

       * > **定义**：在代码里把任务之间的 dependency 一个一个 link 出来构成依赖图，交给系统按图自动决定哪个先执行、哪个后执行、哪些能并行执行；以前有一个很著名的 SDK 叫 TBB。

       * 构建方式很淳朴：先表示 task 1 的 dependency 是 task 2、下一个是 task 3……全部标记完就形成依赖图，系统拿到图就能执行下去。

       * 问题一：task 树的构建对很多技术来讲是不透明的。

       * 问题二：静态图假设 task 1 执行完才能执行 task 2，而真实引擎的任务经常执行到一半发现还得先做很多别的事（如角色动画做到一半要先做物理、fork 出伤害检测），任务在运行中不断创新、设置越来越复杂的 dependency；运行中动态增加节点非常复杂，早期版本也没有"做到一半等别的事做完再继续"的机制。

       * 定位：大模块之间的 dependency 现在很多引擎仍用这种方式定义；但一帧内产生几百、上千、上万个 dependency 时，只有 Job System 才能高效解决。

| 方案 | 核心思路 | 好处 | 短板 |
| :--- | :--- | :--- | :--- |
| 固定线程 | 渲染、模拟、逻辑各占一条线程，帧首交换数据 | 划分清楚，2~4 核时代很好使 | 木桶效应，负载无法均衡，约三分之一算力浪费，核数不匹配更尴尬 |
| Fork-Join | 重活处 fork 一批同类任务给 worker thread，做完再收回 | worker 数量跟着核数走，多核适应性更好 | 只在成批同类任务处并行，仍难 balance，时间线有空隙 |
| Task Graph | 声明任务与依赖，系统按依赖图调度 | 调度自动化，符合多线程直觉 | 静态图：动态加节点复杂，不支持"做到一半等别人" |

## 协程

   * **协程（coroutine）**

       * > **定义**：一种轻量的执行上下文切换方式——函数执行到一半可以调一条指令 yield（让道），把执行权让出去等别的事情发生；过一会儿被重新唤醒，还能从刚才那个地方继续执行下去；切换完全由程序自己的逻辑控制。

       * 学生报名的比方：报名做到一半发现缺打印材料，yield 出去等打印机打完；被唤醒时，你天然知道自己已拿到的学号和班级号，接着往下走流程。

       * Go 语言原生支持协程；C# 里这类概念用得也特别多——有了这样的结构，写并行化程序非常方便；C++ 里协程就很麻烦。

   * **协程与线程的区别**

       * 线程靠硬件中断切换：栈、所有环境、context 全部重置一遍，是 kernel 级的事，操作系统全程都知情，成本非常高。

       * 协程一般由程序自己定义，在同一条线程里让很多个协程来回切换：从 CPU 看来还是同一条线程、从来没掉过中断，没有激活 kernel 的 switch。

       * 比方：线程切换是换座位被教导主任发现——整个学校系统全部报备，事就麻烦了；协程切换是和同桌自己商量换座位——班主任发现不了、不用报备，overhead 下降非常多。

   * **有栈协程（Stackful）**

       * > **定义**：yield 回来时把局部变量、寄存器、整个执行 context 全部复原的协程——程序员按同步思路写业务逻辑，心智负担小。

       * 难点在恢复：函数让出去后那块栈空间被别的函数用掉了，回来时要把所有状态恢复回来——这非常难，实现要动汇编、把寄存器与堆栈全部导出。

       * 每次 yield/resume 都要保存、恢复栈：栈设小了拷贝保存快、性能高，但函数写着写着就炸（栈空间爆炸，stack overflow）；设大了每次 yield/resume 的成本就高。

   * **无栈协程（Stackless）**

       * > **定义**：回来时默认所有局部变量、寄存器全被清空、一笔勾销的协程。

       * 实现相对简单——在 C 语言里写一个 goto 直接从函数里跳出去、有本事再跳回去就行；但对开发者的要求非常高，一旦写不好会产生大量 bug，轻易别做。

       * 好处：不需要保存和恢复整个栈与 local register 的状态，极轻——适合非常高频、只有少数核心同学维护的底层 native 代码（甚至写汇编也没有问题）。

   * **引擎的取舍**

       * 游戏引擎只是一个基座，很多应用基于它的接口开发；如果要求开发者必须精通并行编程的各种坑，这个引擎基本没人能用。

       * 所以引擎要把困难留给自己：做高度并行化引擎、让所有游戏程序员享受并行化时，强烈推荐有状态的 stackful；stackless 建议只用在非常底层、少数人控制的地方。

       * 两种实现无所谓高下。

   * **C++ 实现的现实**

       * C/C++ 在不同操作系统下并不原生支持协程：Windows 下可借助 Boost 的底层机制——内部调用汇编导出寄存器与堆栈，且一上来要设置每个函数的栈空间大小；ARM base 的芯片上可能要自己写一段汇编实现类似机制；网上有很多好样例，实在不行参考 Boost。

       * > **提示**：协程——特别是 stackful coroutine——是构建游戏引擎基础设施的一个 foundation。

## Fiber-based Job System

   * **Fiber-based Job System**

       * > **定义**：把 worker thread 架成一条高速的线程管道，往里面高速地放很多 task——这些塞进 fiber 的任务叫 job；job 可以设置 dependency，还可以进行各种 priority 设置；fiber 是 Windows 的一个概念。

       * 理想形态：100 个、1000 个不同任务配 10 个核，按每个任务的长短像搭积木一样凑在一起，尽量让所有 worker 同时进来、相近时间完成。

   * **一条 worker 绑一颗核**

       * 尽可能让一条 worker thread 对应一颗核，一般对应逻辑核——现在的 CPU 都是 hyper-thread（超线程）：一颗物理核逻辑上分成两颗，一条 hyper-thread 给它配一条 working thread。

       * 有多少颗核就生成多少条 working thread：这样不停往里加各种 job 时不需要 thread swap，整个系统里 thread 的 swap 几乎是零——这是 fiber 系统最核心的思想。

   * **Job Scheduler：全局调度**

       * > **定义**：job 并不直接递给 working thread，而是由 scheduler 根据每一条 working thread 的饱和状态分发任务。

       * 与 fork-join 的本质不同：fork-join 实际还是单线程跑到一段、突然生成一批同类任务做完再合流，并不是真正的全面并行化模型；真正的全面并行化是——所有硬件计算资源只是 resource、都是 worker，任务大就多占一会儿、任务小就多塞几个小的，尽量保证大家基本均衡。

   * **后进先出（LIFO）**

       * 游戏引擎中很多 job 的产生方式是：前一个 job 做到一半突然 fork 出四五个 job，执行到一半又会产生新 job——fork 出来的任务不完成，自身就完成不了。

       * 所以 worker 面前的任务堆一般用 last in first out（像堆栈）：让最新产生的子任务先上，把依赖链一路做穿；所有同学天然理解的 first in first out 在工程实践中常常是错的。

       * > **易错点** ⚠️：调度次序直觉上选"先来先做"（FIFO），工程上却常常该用"后进先出"（LIFO）——fork 出来的子任务不完成，父任务就收不了口。

   * **yield 与 waiting list**

       * job 按 dependency 走：一旦发现 job 被 yield，就把它扔进 waiting list（这件事由 scheduler 干），worker 转去执行下一个可以执行的任务。

       * 等那些 dependency 执行完，再从 waiting list 捡回来继续执行——任务塞进线程并不永久占着线程，别占着坑空转，这样才能把 CPU 尽可能利用起来。

   * **Job Stealing（偷活）**

       * > **定义**：闲下来的 worker 把那些还没做完的 worker 里的任务偷过来，放到空闲的 worker 里执行。

       * 必要性：无论 scheduler 做得再好，也没办法 estimate 每个任务要跑多久——有的任务函数壳小、里面算了堆很神奇的东西，有的 job 要等 IO 能等很久，有的执行中产生一堆 dependency；所以一定会出现有的 worker 活做完了、有的还剩很多。

       * 整个 job system 像工厂里的经理：不停把任务堆到工人面前、不停观察状态保证每人手上都有活，并用 last in first out 保证前导工序做完之后再去完成后面的工序。

       * 调度全景：

```text
      用户 fork 出一批 job（带 dependency / priority）
                        |
                        v
            +-------------------+
            |   Job Scheduler   |   <- 全局调度：按各 worker 的饱和度分发
            +-------------------+
             /        |        \
            v         v         v
        Worker#1   Worker#2   Worker#3     <- 一条 worker 对应一颗逻辑核
        [j][j][j]  [j][j]     [j][j][j][j] <- 每个 worker 自带 LIFO job 栈
            |
            | yield：依赖未就绪 -> 挪进 Waiting List，先去执行别的任务
            v
      Waiting List --(依赖齐了再捡回来)--> 交回 worker 继续

      闲下来的 Worker#1 --(Job Stealing)--> 从忙着的 Worker#3 栈里偷 job
```

   * **优势与代价**

       * 优势：非常容易实现任务的 schedule、处理任务之间的 dependency；每个 job 的堆栈独立、彼此不干扰；基于协程、每条 working thread 独占一颗核，不存在 context switching（只要不触发硬件中断），效率非常高；profiler 图像小砖头一样垒得整整齐齐。

       * 挑战一：C++ 语言 natively 不支持 fiber，要自己实现一套协程机制——可以整体用 Boost，嫌它特别大也可以把里面的代码抠出来；且在不同目标平台上实现方法不一样。

       * 挑战二：真正实现起来挑战非常大——对上层开发者全部透明（任务扔进去、中间 fork 一个 job、结果就拿到了），但底层实现者必须对多线程硬件底层非常了解，否则复杂业务压进来后会在各种奇怪的地方挂掉。

       * > **提示**：job system 的全部精髓——scheduler 按饱和度分发、LIFO 保依赖、yield 挂 waiting list、闲了去偷活——目标只有一个：让每一颗核在每一刻都有活干。核数只会越来越多（x86 八核、十六核、三十二核一定会发生；ARM 靠堆核降功耗），job system 会是未来很重要的实施方式。

   * **与实体组件系统（Entity-Component-System，ECS）的关系**

       * fiber-based job system 更多是 high level 的任务之间的调度；ECS 更像是在大量运算时面向数据去组织计算——两者有交集，但不完全高度一致。

       * 用了 ECS 不一定要 fiber-based job system：用 join 的 pattern、生成一个静态的 dependency graph 一样可以运行得很好；Unity DOTS 和 Unreal MASS 都不是一个完整的 fiber-based job system——实际上是基于 dependency graph 构建任务的 fork，做完再做下一件事，效果也非常好。

       * 真实引擎不可能把整个引擎全部扔进 job system：一般只有 50% 到 60% 的 workload 可以扔进去做并行化；物理这些部分要做特殊处理才能跑好，为特殊的 scenario 定制算法是常态。

## 并行底层陷阱与实践

   * **ABA 问题**

       * > **定义**：在一个线程里，前面一段代码对数据做了修改，后面再去检测时发现它"没变"，于是逻辑往另一个方向走——实际上这两次之间，另一个线程已经把这个数据改过去一遍、又改了回来（值从 A 变 B、又变回 A）。

       * 典型场景：一条线程释放一段内存后，靠读那个位置的值判断释放是否成功；中间另一条线程触发新的分配，heap 把同一段内存地址重用、且好死不死放的数值一模一样，后面的检测完全没发现这块内存已被换过一茬。

       * 危害特性：可能跑几天几夜后系统突然异常挂掉；内存分配是很随机的过程，还要随机到"数据恰巧被写回原状态"，几乎无法复现——于是很多检测函数全部无效。

   * **崩溃的可修性与开发纪律**

       * 百分之百当场 crash 且能复现的 bug 其实很开心、一定修得好；开服三天之后有概率突然挂掉的服务器问题才最惨、最害怕。

       * > **提示**：写并行底层核心系统要多做形式化推导——从理论上证明它是安全的，而不是凭经验看它是否合理；并行化的坑别人 10 年、20 年前就踩过无数遍，多查开发者社区总结的 pattern，太阳底下没有新鲜事，去 follow 行业范式、千万不要土法炼钢。

   * **CPU 被自旋锁跑满怎么办**

       * CPU 跑满后会触发一系列问题：线程堵在那里被迫 swap 出去，很多进程线程拥塞、很多行为发生变化——要尽量避免跑满。

       * 可行做法：job system 一直 monitoring 每一个核的占用情况，某个核使用率超过阈值（比如 80% 到 90%）就不再给它塞任何 job——job 挂在那儿，但不让它启动。

   * **并行程序的调试**

       * 常用手段是疯狂打 log，但 log 本身很慢（写文件的速度很慢），会导致时序发生变化，问题可能因此变形甚至消失。

       * 实用技巧：给 fiber 系统做一键单线程功能——把所有 job 按 dependency 一次性依次执行；先用它确保业务逻辑基本没有错，再去看是不是多线程在某些资源上竞争。

       * 组织建议：让尽可能少的程序员接触多线程——让技术最扎实、思维最缜密的几个同学把原子操作、锁这些机制做完做成底座；上层程序员能访问的数据、能调用的函数都约束好，最好只写脚本、不关注底下真正发生的事。

       * 即便如此，一个难缠的问题也可能花一两个星期才能找到——新一代 VC 已能看到很多状态，但最难的是出问题时根本断不下来，不知道该在哪个 thread 上断。

   * **渲染线程与逻辑线程的同步**

       * 现在常见的方法：逻辑线程算完后把所有值一股脑扔给渲染——一帧一帧地，逻辑线程形成一个逻辑上的 frame 交给渲染，渲染自己去做。

       * 代价：渲染线程总是比逻辑线程慢一帧——它要等逻辑全部算完之后数据才能到渲染；成熟的商业引擎目前大多仍被迫让渲染等逻辑全部算完，否则数据会产生很多奇怪的二义性。

       * 推论：用固定线程法划分引擎架构时，必须给每一类任务一个清晰的分界线——任务不能在渲染、逻辑、物理 simulation 线程之间轻易来回跳。

## OOP 在大型系统里的老毛病

   * **范式选择的背景**

       * 做游戏引擎各种编程范式都会用；早期引擎做一个小乌龟吃豆子级别的游戏，面向过程就够了。

       * 现代引擎的 component 系统——万物皆 GO，一个 GameObject 可以组合派生出 vehicle、飞机、武器、人——就是面向对象编程（Object-Oriented Programming，OOP）的思想：极其符合人类对世界的认知，写起来舒服，但下面是它做大型系统的老毛病。

   * **动作的两义性**

       * "人攻击怪物"这个动作挂在谁身上？写在攻击者这边（发起 attack、apply damage to、把 target 传进去），还是写在受害者那边（been damaged、谁来打了我、造成多少伤害）？OOP 没有答案。

       * 商业级游戏的逻辑代码由很多程序员一起写，有人从攻击者角度写、有人从数据的角度写——代码一致性很差。

   * **深不见底的继承树**

       * "魔法伤害"到底在哪一层实现？GameObject 基类层、Actor 层、Monster 层，还是派生的会飞的、能变身的 monster 层？面对几百万行代码想知道功能在哪个函数里实现，要在这棵深不见底的继承树里一层层找。

       * 函数还会在基类与派生类之间来回搬家：有人觉得通用要进基类、有人觉得特别要进派生类，派生到最后发现又是共用的再搬回基类——"这到底属于基础服务还是特殊服务"是程序员之间的日常对话。

   * **基类全家桶**

       * 商业引擎的 Actor 基类里放了无数功能，连 debug 这种功能都放在里面；写一个很小的功能去派生 actor，本来只需要几个功能，结果背上整个全家桶。

       * 基类的肮脏臃肿，是 OO 做大型系统做到后期大概率会发生的问题。

   * **性能低下**

       * OOP 符合人对数据的直觉，代价是数据全部分散到各个 object、通过派生继承全是异构的、每个对象的 allocate/deallocate 分散进行——内存布局东一块西一块，CPU 拿到很难受。

       * 类的派生继承带来重载与虚函数——虚函数全是指针，代码在内存里跳来跳去；用 profile 工具看，OO 系统的性能图非常丑、非常不稳定。

   * **单元测试几乎没法写**

       * 测一个伤害结算逻辑，得把整个环境（所有对象、所有东西）创建起来才能测中间那一个函数；OO 里对象一层套一层，很难把一个元素单独提取出来测试。

       * 游戏引擎真正到达可用规模一般都是几百万行以上代码，对可测试性要求非常高；克服这个问题不只有面向数据编程一条路，函数式编程也能解决。

## 缓存友好：CPU 与内存的速度鸿沟

   * **速度鸿沟**

       * 过去 20 年里 CPU 快了将近上千倍，内存访问速度大概只提高了 10 倍左右（一个数量级），两者差距已经拉开两到三个数量级以上。

       * 这道鸿沟直接导致了现代计算机复杂的 cache 机制，也是 DOP 的出发点：数据的摆放与访问方式直接决定程序跑得快不快。

   * **缓存金字塔**

       * > **定义**：为弥合鸿沟做的分级缓存——最靠近 CPU 的 L1 最快、体量最小；L2 一般十兆左右、比 L1 慢一个数量级；L3 一般十几兆到上百兆、又比 L2 慢一个数量级；主内存再慢一个数量级——从 L1 一路到内存累计约 1000 倍的差距。

       * CPU 取数顺序：先问 L1；L1 说没有问 L2，L2 说没有问 L3，L3 说没有只能从内存拿——一旦决定从内存调数据，基本就是 1000 倍以上的成本，速度变得很慢。

       * 做高性能编程要一直把这张图放在脑子里：自己写的东西对 cache 到底 friendly 还是不 friendly。

   * **缓存行（cache line）**

       * > **定义**：CPU 在各级缓存与内存之间搬数据的基本单位——每次取一个 cache line，大概 64 个字节，一行一行地读写。

       * 一个 integer 被计算时，在 L1、L2、L3 与内存里各有一段，CPU 要保证这几层数据最终一致；数据发生改变写回主内存时，也是一次性地一级一级写下去。

   * **访问顺序：按行还是按列**

       * 同一个按行存储的矩阵，逐行读比逐列读效率可能高出几百倍甚至上千倍。

       * 原因：矩阵很大时在内存里连续存放；按列遍历虽然只是 y 坐标加了 1，在 cache line 上却可能已经跳过很多次，每一次都要被迫从 memory 一层层往上搬数据——访问 order 要顺着数据的存储顺序来。亲手测一下，差距非常直观。

   * **缓存替换策略**

       * 经典 LRU（最近最久未使用）：最近一直在用的留住，把最久没有被用到的扔掉——非常简单也非常经典。

       * 随机替换也成立：比如 1MB 的 cache 每个 tick 随机扔掉 64 或 128 个字节（约千分之一），从概率上讲谁最久没被用到谁就有最大概率被扔掉，符合数学期望——随机策略也是一种 cache 管理机制。

       * > **提示**：无论 LRU 还是随机策略，都在奖励"扎堆"的数据——打包数据和代码时，要尽可能把会一起用的东西放到一起。

   * **局部性（locality）与 SIMD**

       * 数据要有 locality：数据总是紧紧地待在一起，处理的时候尽量一次性处理；GPU 同理——显存之外每个计算单元也要从各级 cache 读数据，数据尽可能 local，GPU 才能疯狂地跑起来。

       * 单指令多数据（SIMD）：现代 CPU 基本全都实现——对四个 float 的加减乘除可以看成一个 vector4，一条指令全部做完，一次性读四个内存空间、写四个空间。

       * 打包（packing）数据时，要尽可能 pack 成 SIMD 友好的空间，比如 16 个字节。

## 面向数据编程的核心思想

   * **面向数据编程（Data-Oriented Programming，DOP）**

       * > **定义**：认为游戏里所有发生的事情、所有事情的表达都是数据，而代码也是一段数据的编程观；核心关注点是把这一切在 CPU 里的 cache miss 降得越低越好。

       * 不只数据会造成 cache miss，代码也会：这段代码执行完了要加载新的一段代码，新代码同样会导致 cache miss；profile 显示时间消耗里将近 7% 花在"被迫再去弄一段新的代码"上——代码本身也是高性能编程要思考的对象。

       * > **提示**：DOP 把数据和代码看成一个整体——它们在内存中可能是分开的，但在 cache 里要尽可能地待在一起：这段代码执行完、这批数据刚好处理完，然后 swap 下一批数据和代码进来。

       * 鞋厂比方：做鞋的工人、他手上的工艺、要处理的原料全部放在一起，一批处理完连人带鞋一起 swap 出去；要避免两种情况——工人只会一道工序（做到一半要从 memory 里调另一个工人，数据干等）和原料四散（做到一半得跑去别的地方调原料）。

   * **收益量级**

       * 数据和代码安排好了，比传统 OO 快一到两个数量级很正常——将近 100 倍不夸张；Unity 用 DOTS 系统做同样的东西，实测能快到接近 100 倍以上。

## 高性能代码的三条纪律

### 伪共享（False Sharing）

   * **伪共享（false sharing）**

       * > **定义**：两个线程读写的变量虽然地址不同，但正好落在同一条 cache line（64 字节）里，导致整个系统负载特别大的现象。

       * 机理：一个人在读、一个人在写，或两个人同时改——系统要保证数据一路同步到 L1 cache；你改了他读、两人同时写，整个同步和读取的过程要专门做两遍才能让数据一致。

       * 对策：做任务时尽量避免任务之间的执行顺序依赖（order dependency）；不要把很碎的数据同时交给两个线程去访问——一个线程访问的数据就是自己的那一块，双方尽量不要有任何交集。

       * > **易错点** ⚠️：你会觉得自己什么都没做错——两边写的地址明明不一样——但只要这两个地址落在同一条 cache line 的范围里，整个内存同步（swap）的成本就会高非常非常多。

### 分支预测（Branch Prediction）

   * **分支预测（branch prediction）**

       * > **定义**：CPU 预测 if-else 往哪边走、提前把预测分支的代码（比如 100 行）加载到 L1 cache 直接执行的机制——依据是实践中 100 次进入这个判断，可能有 99 次甚至 100 次走的都是同一个分支。

       * 失败代价：下次进来条件突然不满足，L1 里这段代码就无效了、要被 swap 出去，再去调 else 的代码进来；如果很不幸这段代码既不在 L2 也不在 L3、是 memory 里的冷代码，那系统要等很久。

       * 典型翻车：数据乱序时遍历数组按阈值分支——碰到超阈值的元素把 else 代码调进来，做着做着又碰到小于阈值的数，再把 if 那段代码调进来，来回倒腾性能掉得非常低；用非常随机的数据跑复杂 if-else 判断可以亲测性能非常低。

       * 对策一：先对数据排序——排完序只在越过阈值的那一个点上切换一次，前面全是 if 的代码、后面全是 else 的代码，同样逻辑效率高得多。

       * 对策二：更高性能要求下提前把数据分好——在创建每个数据的时候就把它加到不同的数据容器里，对一个容器只做一种逻辑，保证整个处理逻辑的高度一致性。

       * > **注意**：branch prediction 失败时哪怕数据就在 cache 里也没有用——要 swap 的是代码，而代码 swap 有时又会导致数据失效；写高性能计算（尤其高频执行的代码）要尽量减少 branch 运算。

### 数据布局：AoS 与 SoA

   * **底层觉悟**

       * OO 的数据通过各种各样的引用、指针满天飞；很多同学已不太接触 C/C++ 这类底层语言，把东西扔进功能齐全的容器非常方便——但要写高性能开发，真的需要理解汇编、C 语言这些底层的东西，arrange memory 要非常讲究。

   * **AoS（array of structure）**

       * > **定义**：每个元素是一个完整结构体的排布——用 OO 思想定义 particle（position、velocity、color、age），100 个 particle 的完整结构首尾相接。

       * 问题：更新 position 的函数实际要读的是 velocity 和 position，但每处理一个 particle 都要跳过后面的 color 和 age——跳来跳去，cache coherence 就不够好了。

   * **SoA（structure of array）**

       * > **定义**：同一种数据直接排成一条超长数组来处理——pos 一条、vel 一条、color 一条、age 一条；要一起算的字段紧挨着，一条 cache line 拉进来的全是有效数据。

       * 追求高性能时，一般就按 SoA 的方法去排所有的数据。

       * 参照物：compute shader——GPU 骨子里就是一个以数据为驱动的编程模型，每一个 shader 可以理解成一个函数、数据非常紧致地排在一起，所以同样一个运算上了 GPU 就非常快。

```text
AoS（每个元素是一个完整的结构体）：
  [p1: pos|vel|color|age] [p2: pos|vel|color|age] [p3: pos|vel|color|age] ...
         ^ 更新 position 要用 vel，却每次都得跨过 color 和 age

SoA（同一种属性排成一条长数组）：
  pos:   [p1][p2][p3][p4] ...   <- 要一起算的字段紧挨着，一口气刷完
  vel:   [p1][p2][p3][p4] ...
  color: [p1][p2][p3][p4] ...
  age:   [p1][p2][p3][p4] ...
```

## ECS 架构

   * **实体组件系统（ECS）**

       * > **定义**：把数据全部打平、从 owner（以前的一个个 GO）身上全部剥出来、每一类数据集中在一起存储；每个 entity 用一种非常离散的关系关联（"我用了多少号的 transform、多少号的 velocity"），而对数据的处理交给 system。

       * 目标：认为用这种模型构建的系统能够充分利用数据的 cache coherence，充分压榨面向数据编程的性能。

       * 由来：component-based 系统最自然的实现方式是 OO——构建很多对象一层层派生继承；代码分散在各个类里、虚函数指针一塌糊涂、数据也非常分散、执行效率非常低；entity 里的 component 和 GameObject 多起来之后每帧去 tick，性能比想象的慢很多很多。

       * 慢的实质：大量浪费在无效的等待上——执行到一半发现数据没有了去找数据；算到一半要调一个虚指针、找到它的实现再把那段代码加载进来，来回倒腾。

       * 工厂比方：一个没有人管理的工厂——师傅凭感觉干活、缺原料自己去库房拿、只会做鞋底的把鞋底递给做鞋面的师傅，整个任务调度完全无序；ECS 就是想彻底解决这个问题。

   * **Entity：轻到只剩一个 ID**

       * > **定义**：以前的 component-based 系统里 GO 是一个可以装很多 component 的类；ECS 里的 entity 非常非常轻量——就是一个 ID，这个 ID 指向了一组 component。

   * **Component：纯数据，不许有逻辑**

       * > **定义**：component 指的就是一块数据——一份位移数据、一份速度数据，没有任何业务逻辑；可以对它读、对它写，但它本身并不知道自己的意义。

       * > **易错点** ⚠️：这一点与 component-based 系统的 component 特别容易弄混——那里的 component 有 tick、get property、set property 等一堆接口；ECS 里的 component 是不允许有业务逻辑的。

   * **System：一类逻辑处理一类数据**

       * > **定义**：对这些 component 进行处理的抽象单元——MovingSystem 根据你的速度去改你的 position，HealthSystem 根据你受到的 damage 去调整你的 health 值。

       * system 并不是一次只处理一个 component：单位拆得非常非常细之后，system 很多时候会同时处理好几类 component 的数据（以前 GO 体系里 component 多对自己的 member 数据进行处理）。

       * 优势：system 的操作非常简单，很容易把 system 的计算分散到很多很多核上去。

## Unity DOTS：一套落地的 ECS

   * **Unity DOTS 三支柱**

       * > **定义**：Unity 提出的高性能技术栈，三根支柱——ECS：面向数据重新组织整个引擎的计算框架；C# Job System：数据变 component、处理变 system 之后非常容易并行化，于是做了一个非常简单的 job system；Burst Compiler：把 C# 编译成 native 的自研编译器。

       * 状态：备课当时 Unity 似乎已决定放弃 DOTS，但不影响拿它分析 ECS 的整个应用。

   * **Archetype（原型）**

       * > **定义**：type of GO——一类 GO 就是一个 archetype：做 NPC 用到的那几个 component 是一个 archetype，做会战斗的 monster 多一些攻击/伤害/行为属性，做载具又有相应的一组 components。

       * 动机：游戏中有几百上千个 entity 时，每个 entity 底下挂的 component 都不一致，system 总不能一个一个问"你有没有这个 component、我能不能用"——那就很慢；有了 archetype，system 直接知道哪些 entity 是要处理的，处理速度变得很快、也方便别人理解。

   * **Chunk：按 archetype 摆内存**

       * > **定义**：把内存定义成一个个 chunk（块），把同一类 archetype 的所有 component 按 component 的类型一个个摆进 chunk；一个 chunk 里一定是同一类 archetype。

       * 收益：system 判断要不要处理一个 chunk 只需看它的 archetype——NPC archetype 里一定有对话 system 需要的那几个 component 就处理；一批载具 archetype 则这几十个载具彻底不需要考虑（没有对话需求）。

       * 大小：早期架构一般设成 16KB——主要考虑 cache line、考虑 L1/L2 cache 是怎么 swap 的；现在的计算机上这个值变大一丢丢，有的引擎把它提到了 128KB 或更大——这是一个可调的量。

       * > **提示**：为什么不把所有同类型的 component 全放在一起（比如所有 transform 放成一个超大数组）？数据量会非常大，反而不符合 locality 的要求；本意是让"这一段代码 + 它要处理的一小块数据"正好一起塞进 cache，处理完再把下一个 system 和它对应的 chunk 换进来——这样处理效率才是最高的。

   * **System 的高效执行**

       * 例：做一个"往前移动、更新 position"的 system，只要拿 velocity component 和 translation component 做一次运算——运算完这个 chunk 里所有物体的 translation component 都被更新了一遍；因为不管读还是写它们都在一起，效率非常高。

   * **Burst Compiler：为什么自研编译器**

       * C# 代码跑在虚拟机里：申请的一个 array、定义的一个数据结构在硬件上到底对应什么东西完全是黑盒；在 C# 里定义一个变量，真正存储的数据只是很小的一块，旁边还有一堆反射数据。

       * 写几乎和硬件一对一对抗的高性能代码最需要 native：Unity ECS 里定义 array 必须用它要求的 native container——非常像 C 语言里真的分配了一块内存的裸指针，只有这样它才能和内存里的数据一一地、连续地映射起来，数据访问才是可控的。

       * 变得这么 native 之后要补安全检查：写 C# 不用管内存释放，写这种代码就要花很多力气考虑泄漏、无用资源；Unity 希望在编译器层面、job system 层面确保所有该释放的资源都会被释放——这件事情非常困难，所以必须写自己的 compiler：把这门"只借用了 C# 语法的语言"编译成非常底层的语言，并完成必要的检查。

       * 设计哲学：把复杂度全部藏在 DOTS 自己身上——上层业务开发者不需要理解这么多复杂的 cache 机制，只需要按照它规定的 flow 去写 C#，就能实现想要的高性能。

       * 用 C# 的基础语法很难直接做 DOP 开发（分配、释放、内存在什么地方都变得非常抽象复杂）；Burst 编译之后性能又提高很多倍——这是 C# 这门语言在天生的高性能、特别是 DOP 类型开发上的弊端。

## Unreal MASS：另一个范本

   * **Unreal MASS**

       * > **定义**：UE5 自己实现的一套类似 ECS、类似 job system 的系统；UE5 最好的 demo《黑客帝国：觉醒》——中间的曼哈顿有成千上万的汽车、行人——就是用这套系统实现的；整体与 Unity DOTS 高度相似。

   * **Entity 与串行号**

       * MASS 里 entity 的概念和 DOTS 一样只是个 ID，但每个 ID 带一个 serial number——一个单独的、永远往上递增的数字，实际上保证了这个 ID 永远不会被重用。

       * 有点像 handle 机制里的 salt（保证 ID 被重用时也不会串号）；但串行号和 salt 是两个不一样的数字——这是个小细节。

   * **Fragment：component 的新名字**

       * MASS 把 component 叫 fragment（碎片）：UE 已有一千多万行代码、里面定义了无数的 component，再把这个数据也叫 component 就成了"此 component 非彼 component"。

       * component 这名字本来也取得不好：容易让人想起 COM 这些接口，天然以为它是"数据和服务绑在一起"的东西；而 ECS 架构里它就是纯粹的 data——fragment（一小块内存的碎片、一小块数据）这个名字听上去就到位了。

   * **Processor：system 的新名字**

       * "你给了我这么多数据放在这儿，我一个 processor 把你的数据全部处理完"——命名很贴切，这两个命名都比较值得推崇。

   * **Processor 的两步：Query 与 Execute**

       * query（fragment query）：先用一段描述说清楚要对哪些 entity 进行处理、需要哪几类 fragment、对它们是读还是写——就像写数据库：先定义一个 query、再执行，把所有 entity 扫一遍拿出需要的数据；扫描基于 archetype，而且 query 有缓存——上一次查完之后这一次如果没有变化，基本上就不用动了。

       * execute：query 做完后所有需要的 fragment 都拿到了——拿到的是引用，并不是真的把数据搬过来；因为对每一类 archetype 而言数据本来就集中存储在一个个 chunk 里，processor 处理完一个 chunk 就整个 chunk 整个 chunk 地切到下一个。

       * 底层机制的收益：曼哈顿那种成千上万汽车、人物的庞大场景就是这么跑出来的。

| 概念 | Unity DOTS | Unreal MASS |
| :--- | :--- | :--- |
| 实体 | Entity：一个轻量 ID | Entity：ID + 只增不减的串行号，永不重用 |
| 数据 | Component：纯数据 | Fragment：一小块数据碎片 |
| 逻辑 | System | Processor |
| 同类分组 | Archetype | Archetype |

## ECS 的适用边界与延迟账单

   * **不要把整个引擎 ECS 化**

       * 游戏是一个非常复杂的东西，里面很多业务 dependence 非常乱、非常复杂，几乎很难把整个引擎变成 ECS；"搭一个彻底基于 DOP/ECS 的下一代引擎"是理想主义的冲动。

       * 正确姿势：在有些单点的地方用它非常好；不适合的地方千万不要到处用——会极大增加代码维护的复杂度，开发难度也非常大，因为"数据和业务分开了"这件事很多人天然就很难理解。

       * 90% 以上的游戏业务逻辑是"问数据"式写法：先问数据 A 怎么样、数据 B 怎么样、数据 C 怎么样，问自己问别人一大堆，然后才说我的东西怎么办。

       * 强如虚幻五：ECS 也只放在 MASS 这个非常特别的场景里很彻底地用了一遍；它的主体引擎仍是面向对象的、component-based 的架构。

   * **实战引擎的架构权重**

       * 在一个实战型的游戏引擎里，OO 与 DOP 这两种架构是同等重要的——甚至坦白讲 OO 的重要性可能还要更大一点点，基于 DOP 的 ECS 稍微小那么一点。

   * **一张延迟账单**

       * 一条 ALU 指令、一次硬件级别的中断、一次线程上下文切换（context switch）、C++ 里一次函数调用、一次虚函数调用、一次栈的切换——代价从 $10^0$ 一次方一路到 $10^4$、$10^5$，最高到一百万倍这个量级；而且差别不是线性的，是数量级的。

       * 所以一个系统如果写得不好，同样逻辑、同样代码真的慢 100 倍很正常；这一整套优化方案，本质上都是对着这张账单来做的。

       * > **提示**：有志于做系统架构的人值得把这张延迟账单一行一行看明白——为什么这里快、为什么那里更慢；看懂之后再回头看引擎的方方面面，自然而然就通了。

## 服务器架构与联机三问

   * **反作弊没有终极解**

       * 技术上无论加密还是各种方法，总有人能破解；设计上可以让作弊无法获益——例如把判定彻底放在服务器上，代价是影响手感（不再用本地物理等本地手段判定，改用更多可控的机制）。

       * 社交化思路：Steam 的 VAC——只要在一款产品里被发现作弊就会报到 VAC、整个 Steam 账号都可能受影响，一串游戏都不能玩，想打死也不作弊。

       * > **提示**：反作弊是一场长期的、艰苦卓绝的斗争，不是纯技术问题，要和社区、玩家联动去发现和解决问题，永远是一个动态的平衡。

   * **微服务与分布式的关系**

       * 两者不是"区别"的关系：分布式服务器架构是标准的、最经典的选择——在多台物理机上用多个进程或线程协同工作、各司其职（把数据库访问和游戏逻辑分开、每个战局形成一个独立的 game server），它的对立面是把所有业务写进一个进程。

       * 微服务（microservice）是一种设计理念、分布式服务器架构的一种实现方法：把后台拆成尽可能干净、单一的业务单元——邮件、聊天、用户登录、房间匹配等等都变成独立的服务；最早期大家尽量让服务无状态，为的是容易扩容减负、支持弹性变化；某些服务出了问题可以通过服务发现发现问题，再 spawn 出更多服务——一种非常好的基于容器的分布式实现方式。

       * 现代 online game 也不是完全的微服务：有些服务用微服务架构做，有些东西还是要全局地自己管理；不要纠结具体概念，适合项目的就是最好的方案。

   * **全球联机对战的难点**

       * 概念不复杂：服务器做分布式架构，在世界各地都有服务器、服务器之间建立高速通讯——购买或自建专用机房、机房之间用光纤尽可能直接连起来（"高速主干线"专线），或用通讯服务商提供的虚拟专用通道；欧洲这类用户来自各地的，还要提供离他们本地更方便的接入节点。

       * 跨洋延迟的大头不在光速——光传播过去差不多 100ms 左右甚至不到；真正慢在无数次的网关路由上：数据不停地转发、转发、转发，每一次都带来很多延迟。

       * 区域网络结构千奇百怪：南美洲西侧的智利特别长，那条贯穿南北美的世界最长山脉左右两侧网络非常隔绝，有些国家连接亚洲的速度比连接本大洲另一边还快——服务南美要做专门处理：服务器架在墨西哥还是阿根廷（千万不要架到智利去）、跟北美直接连接还是通过其他方式。
