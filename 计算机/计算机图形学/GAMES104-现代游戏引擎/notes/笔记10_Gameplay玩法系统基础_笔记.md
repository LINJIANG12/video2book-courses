# Gameplay玩法系统基础

## 玩法系统的范围与挑战

   * **玩法系统（Gameplay）**

       * > **定义**：游戏里 almost everything 都算玩法——驱动游戏世界中一切内容与规则的逻辑层；它不像物理、渲染那样边界清楚，是一个非常庞杂、难以划清边界的系统。

       * 玩法系统的基础骨架有四件事：事件系统（世界里游戏对象之间如何通讯互动，是做玩法的基础）、脚本系统（写"上去砍一刀血量怎么扣"这类玩法规则）、可视化脚本（visual scripting，如 Blueprint）、3C 系统（角色、控制、相机）；AI 系统是玩法系统的另一大块。

   * **玩法工程师的三重挑战**

       * 挑战一，设计师动动嘴、程序员跑断腿：一个"打击感"就要同时驱动动画系统、特效系统、音效系统、控制系统、UI（double kill、暴击弹字），还要靠渲染系统的卡帧（打击帧）把画面钉住；玩法工程师不必亲手写每个系统，但必须能和所有系统的工程师沟通——gameplay engineer 是个杂学家。

       * 挑战二，玩法千奇百怪、扩展性必须拉满：同一款《巫师》，核心战斗是砍怪放法印，昆特牌又是一套完整玩法；网游里抛绣球、踢足球、吃鸡、打牌、下五子棋、参加科举全都统称玩法——玩法系统的架构与可扩展性要求极高。

       * 挑战三，快速迭代：《堡垒之夜》原定位末世题材生存类 MMO（大型多人在线游戏），从决定转型吃鸡到把 Fortnite Battle Royale 做出来只给了两个月；而渲染的一个 feature 从决定到落地往往要半年以上、有的系统要做一年以上。

       * 玩法的研发节奏：几天、几周就要出一个新玩法，几个月以上的也会拆成多个小 sprint 突击着做、看效果再迭代；引擎侧必须支撑这种全游戏最快的迭代速度——能调用所有系统、有强扩展性（叙事、对抗、探索都能装）、能低成本快速产出，"杂学 + 价廉物美"才能撑起丰富的游戏体验。

## 事件系统与发布-订阅模型

   * **发布-订阅模式（Publish-Subscribe pattern）**

       * > **定义**：消息的生产者只管发布，使用者提前订阅自己关心的消息，双方不直接调用对方——这是事件系统的设计范式，相当于给整个游戏世界建立一套通讯协议。

       * 背景：游戏世界由无数游戏对象（game object，GO）构成，GO 之间要能玩起来首先彼此要能通讯——炸弹要广播"我要炸了你们"，坦克开炮要广播"一只炮弹正在飞来"；把通讯写死成 if-else / switch case 分支循环，代码会崩到无法维护，所以把世界里发生的每件事抽象成一个 event（message），每个 tick GO 之间互相"写信"、收信者各自做出响应。

   * **事件系统三大核心组件**

       * 事件定义（event）：类型 + 参数（event payload），描述"发生了什么、带什么数据"。

       * 事件分发器（event dispatcher）：像物流公司一样把消息分拣、派送到各个接收方；信息的分拣派送非常在乎效率、讲究算法。

       * 回调（callback）：处理某类消息的函数，必须提前注册——"这类消息来了，就调我"。

       * 量级：每一帧会产生几百甚至上千个各种各样的消息，全靠 dispatcher 送达对应接收方。

       ```text
       发布者：只管把事件扔出来
               │  事件 = 类型 + 参数（event payload）
               ▼
       Event Dispatcher（物流公司）：分拣、派送，讲效率、讲算法
               │  按订阅注册关系路由
               ▼
       Callback：先注册、后执行——“这类消息来了，就调我”
       ```

## 事件的定义与扩展

   * **事件的构成**

       * > **定义**：每个 event 由类型（type）与携带数据（event arguments，也叫 payload）构成——爆炸事件要带爆炸地点、伤害数值、伤害类型。

       * 类型的最简实现：定义枚举用数字；或用"看起来像字符串、实际会被算成唯一标识号"的注册式命名。

   * **事件定义权在设计师手里**

       * 早期引擎的 event type 由程序员手打（"我定义了 100 种不同的 event"）；后来连 type 都要交给设计师创建——90% 的情况下玩法不由程序员决定，"大 boss 血量掉到一半、马上切第二阶段"这类消息在写引擎代码时根本无法预知。

       * 面向对象做法（event 基类 + 各派生类定义自己独有的数据）没有问题，但只适用于整个 gameplay 都由 C++ 等面向对象语言编写的场合。

   * **核心引擎之外的扩展**

       * 商业项目的定义流程：给 event 起一个名字 → 用一个并不复杂的算法生成唯一标识 → 定义这个 event 需要的数据结构 → 用代码生成（code generation）渲染出引擎代码，把新 event 类型定义进去。

       * 若设计师每改一次 event 就要重编整个引擎，迭代就死了；核心能力是允许设计师在核心引擎代码之外扩展 event 定义——一部分 event 用纯数据方式定义，放在工具链和 gameplay 系统里。

       * 各家路线：有的引擎提供可视化定义方法、实际生成的还是 C++，由引擎在运行时（runtime）把新编译出来的代码当动态链接库（DLL）注入；有的在上层做一层 C# 接口，便于动态挂接和扩展；有的用脚本语言直接在脚本里定义 event。

## 回调与对象生命周期

   * **回调函数（callback）**

       * > **定义**：提前注册、在对应消息到达时被激活执行的处理函数；语义上更接近 invoke（触发）——不是"回"过来，而是把预先准备好的功能模块激活。

       * 典型注册：收到 damage 事件回调伤害处理函数；收到 status change（如弹药数变化）或 reloading 消息触发重新装弹。

   * **注册与执行的时间分离**

       * 回调先注册、后执行，两者在时间上分离；就像和朋友约好喝茶，到了礼拜六对方可能出各种幺蛾子——你手上的"入场券"可能白买。

       * 风险链条：注册"血量受伤害"处理函数时没有任何问题；下一帧对象已经死亡销毁，旁边一颗手雷爆炸再调它的回调，就掉到野指针上，整个系统在那边犯错甚至崩塌。

       * "删除对象时把它注册的回调一并删掉"可行但难管：引擎里管理着几千上万个 GO，注册的 callback 函数可能是 GO 数量的十倍以上，这种管理非常复杂、极易写出 bug。

       * > **易错点** ⚠️：回调的注册与执行在时间上分离，中间隔着的正是"那个对象还活着吗"的不确定性——对象生命周期与回调安全性，是引擎里最复杂、最容易出问题的组合之一。

   * **强引用（strong reference）**

       * > **定义**：我引用你，你就不许销毁——回调注册在对象上，对象就不能删除，以此保证引用安全。

       * 代价：本该销毁的对象因为还有人引用而死不掉，系统内存越来越大；现在已经很少这么做。

       * 游戏内的有效形态是把它理解成 persisted（拥有、控制）：GO 之间形成嵌套关系，父物体不销毁、子物体就不能销毁，表达一种内存锁定关系——只要房间不销毁，里面的物体随外界怎么依赖都不销毁，除非整个房间 offload。

   * **弱引用（weak reference）**

       * > **定义**：你要删就真删；我用之前多加一步，先判断对象有没有被删掉——对应 C++11 smart pointer 的行为：owner 没了指针就无效，接下来的所有处理都不做，并把自己置成无效。

       * 收益：内存的释放变得容易、高效。

       * 典型场景："我能看见的敌人"列表——攻击目标是前几帧遍历选出来的，本帧发起攻击前先检查有效性；对方可能早已死亡、垃圾回收（garbage collection，GC）已经把内存释放，一检查就知道引用无效。

   * **强引用与弱引用对比**

       * 两派语义、代价与典型场景：

| 对比项 | 强引用（Strong Reference） | 弱引用（Weak Reference） |
| :--- | :--- | :--- |
| 语义 | 我引用你，你就不许销毁 | 你要删就真删，我用之前先检查 |
| 代价 | 该销毁的对象死不了，内存越用越大 | 每次访问多一步有效性判断 |
| 典型场景 | GO 父子嵌套：父不亡，子不灭 | 回调函数、"我能看见的敌人"列表 |

   * **使用准则与两难**

       * 真实写引擎时 strong 与 weak reference 都是非常重要的支撑性功能，一定要用对、千万不要用错；对 callback function 来说，大多数时候弱引用用得比较多。

       * 两难：一个 GO 会被几十个系统用不同逻辑操作、一会儿让它生一会儿让它死，任何系统引用它时都不能假设它有效；但到处做大量有效性判断，引擎速度又会变慢——没有标准答案，必须带着这个意识写代码。

## 消息分发与事件队列

   * **直接派发（来了就办）的三个问题**

       * 最朴素方案（每个 GO 把所有消息从头扫一遍、扫到就分发）的代价：每帧 N 个消息、每个 GO 有 M 个 callback、共 K 个 GO，计算量是 $M \times N \times K$，还要反复存取、释放消息内存——效率非常低。

       * "消息一到马上 call 对应函数"的直接派发，问题一是调用链被打断、层层嵌套：一个函数执行到一半突然被打断、跳出去执行另一段再回来，类似协程（coroutine）；单线程下就真的停在那儿等。

       * 链式事件下调用栈爆炸：一颗手雷引爆旁边几颗、那几颗再引爆更多，一层层掉下去，call stack 深不见底；大型系统宕机时看栈，同名函数只因对象不同就被疯狂反复调用，debug 起来非常痛苦。

       * 问题二，不是所有操作都是瞬时的：减血量只是 HP 加减数值，很快；但"手雷炸了要加爆炸烟雾"要创建几百个 particle、算它们的运动、再渲染出来，做不完——直接派发让所有游戏逻辑等粒子系统做完，帧率会突然变得很不稳定。

       * 问题三，没法并行：调用一层套一层、像串珠串一样吊在一条时间轴上，很难在动辄八核十六核的现代计算机上并行——这是面向数据编程架构要回头解决的问题。

   * **事件队列（event queue）**

       * > **定义**：把这一帧产生的所有 event 全部收集到一个队列，下一帧开始时由各 GO 依次处理——用"这一帧只收集、下一帧统一处理"把调用链在队列处斩断。

       * 内存布局靠序列化/反序列化：把几百个类型各异的 event 拍进一大块连续内存（block of memory），一个连一个排在一起，用的时候再反向拆开。

       * 实现靠反射：每个数据结构占多少内存是已知的，拿到 event 的描述结构就知道它有多大；反过来给一段二进制空间，也能反向填回一个 C++ 结构——event 系统对反射的依赖非常多。

       ```text
       第 N 帧游戏逻辑：产生事件 A、B、C……
               │
               ▼
       Event Queue：一块连续内存 / ring buffer，事件一个连一个拍在一起
               │
               ▼  下一帧开始时统一分发
       各 GO 依次执行自己注册的 Callback
       ```

   * **环形缓冲区（ring buffer）**

       * > **定义**：事件池的内存管理方式——按每帧事件上限（如 1000～5000 个）一次性分配环形空间，event 处理完 head 前移一步、新事件让 tail 后移一步，空间一直重用，不用反复申请内存。

       * head 和 tail 重合说明 buffer 溢出（overflow），很多时候是某个 GO 在错误地、不停地发 event——这是写出 bug 的一个标志；此时把 queue 截断：游戏逻辑可能错几帧，但整个引擎不会崩塌掉。

       * > **提示**：head 追上 tail，先别怀疑容量不够，要怀疑有没有对象在疯狂刷事件；截断队列保住引擎，比让整个游戏崩掉划算得多。

   * **按类别分而治之**

       * 把所有 event 混在一起，一帧过滤几百上千上万条还要查注册表找回调，来回调用很慢；实践上按大类拆分：网络 event 单独一个 ring buffer、单独一个 dispatcher 管理；战斗类、动画类各自集中。

       * 收益是效率与可调试性（debuggability）双提升：出错时"此处应该有一个动画消息，怎么没有产生"——直接去动画 queue 里找，不用在整个 event queue 里翻找。

       * 理想上、原则上不分类也成立，但不分类效率会下降很多，强烈推荐分类。

## 攒帧的代价

   * **顺序无法保证**

       * 动画、AI、战斗等系统在很多引擎里执行顺序是固定死的；event 队列把处理统一推到下一帧后，同类消息集中到一起，无法保证谁先谁后——业务逻辑必须写得健壮，这也是很多游戏特别容易产生 bug 的地方。

       * 这个问题至今没有漂亮解法，有时只能 hardcode：个别 event 保留立即处理的能力，个别函数被刻意放在特定位置去安全地改数据——都要经过很精心的设计。

   * **处理时机的三种选择**

       * 消息处理共三种方法：马上处理（immediate）；下一帧处理——又分 pre-tick 与 post-tick 两种：

| 处理时机 | 事件何时被执行 | 特点与注意 |
| :--- | :--- | :--- |
| Immediate | 消息产生的当场立即执行 | 实时性最好；但会嵌套打断、阻塞、难并行 |
| Pre-tick | 下一帧 tick 一开始统一处理 | 走事件队列的默认路径；晚一帧 |
| Post-tick | 本帧 tick 结束后的位置处理 | 同样延迟，只是时点不同 |

   * **时机选择的难度**

       * 一个现代游戏引擎三种方法都要支持；用哪种要求程序员对系统的调用方式理解非常深——这里特别容易产生 bug。

       * 更难的是怎么把这件事告诉设计师、让他们不会用错——设计师对此普遍头疼，至今没有好答案。

   * **延迟（latency）**

       * 队列机制下绝大多数行为都在下一帧才处理：event A 触发 B、B 触发 C 的递进逻辑，每一步都要慢一帧。

       * 打击感实例：这一帧砍中敌人，按事件流程下一帧 health 系统先处理、粒子特效才出（看到飙血）；health 再检测出暴击、发事件要震屏，再下一帧屏幕才抖——看到震屏已是两帧之后，几乎就是 100ms 之后的事，打击感明显不对。

       * 结论：实时性敏感的效果需要 hardcode 直接绕过事件队列——这是 event 系统使用时要非常小心规避的 latency 问题。

## 脚本语言的动机与机制

   * **直接用 C++ 写玩法的三个死结**

       * 死结一，改一点、编全部：每改一点点 gameplay，整个游戏引擎就要重新编译；早期游戏简单还能忍，复杂后不可持续——连反射系统都会加重它（反射编译器每次生成的 generated code 会被编译器当成"脏代码"，触发一轮重新编译；理论上 schema 没改就不该触发，实现是复杂工程）。

       * 死结二，线上 bug 无法热修：暴击触发不了、装备掉落出错，开发者很急，但让玩家重新下载一个版本不现实；C++ 这类编译语言非常难以热更新（hot update），硬 hack 可以但极其麻烦，且每点改动都可能触发整体重新 link——有大型引擎（如 Hero 引擎）编译一次要半小时，专门花一年才压到 10 分钟，几百万上千万行代码的引擎必须做分布式增量编译，否则每人每天一半时间在等编译。

       * 死结三，用户错位：玩法系统最大的用户是设计师而非程序员，设计师没受过编程训练、学的是如何设计好玩的游戏；艺术家也要定制玩法功能——让这些人直接改 C++ 不现实。

   * **脚本语言的三大价值**

       * 简单：易学、易上手。

       * 热更新方便：解释执行型语言走到一步看一步，函数还没执行前被换掉，后续就按新逻辑运转。

       * 沙箱隔离：脚本一般运行在虚拟机（沙箱）里，可以自己 crash 但不会把引擎本体 crash 掉——大不了把这段逻辑重新载入再跑。

   * **沙箱价值的极致场景：网游服务器**

       * 大型 MMO 一旦跑起来，背后可能是几百个进程同时启动（专门管聊天的、专门管发邮件的……），分布在各台机器上随时可能挂掉；实际系统是"发现某个服务挂掉就把它重启、重新通过脚本接入进去"——这就是玩家几乎见不到大型网游宕机的原因。

   * **脚本的工作原理**

       * 脚本文本 → 脚本自己的编译器编译成字节码（bytecode）→ 虚拟机执行 bytecode：每条 instruction 就是"做什么操作、哪些数字相加相乘、内存该怎么移动"，最终是一段二进制 block。

       * 相当于在游戏操作系统之上又跑了一个虚拟机，所以本身非常鲁棒；代价是速度可能会比较慢。

   * **脚本承载的玩法**

       * 网游里脚本用得特别多：开宝箱、打装备刷装备、交任务触发事件等业务逻辑大量由脚本承载；策划也可以直接写脚本。

       * 结论：真要做一个好的游戏引擎，一定要有脚本系统，否则它很难做出扩展性。

## 热更新

   * **实现原理**

       * > **定义**：不重新编译发版、在运行中替换逻辑的机制——脚本热更很多时候就是把函数实现替换掉：老函数由函数指针指向，新函数来了把指针重新指向新实现，热更新即告完成。

       * > **易错点** ⚠️：脚本里有很多局部变量（local variable）和全局变量，热更新时这些变量一定要注意重置或对数据做必要处理；否则热更没做好，会导致整个游戏崩塌。

   * **商业级风险**

       * 上百万人同时在线时热更：有人正在充值、有人正在点开时装箱、有人正在打一个很重要的 boss；热更搞坏一次，可能有几千甚至上万人同时来找你——讨要装备、讨要 boss 进度。

       * 因此做引擎架构时要特别考虑工程上的鲁棒性。

   * **平台限制**

       * PC 时代热更非常方便，大型 MMORPG（大型多人在线角色扮演游戏，如《魔兽世界》）没有热更基本没法运营——这么复杂的产品一定有很多想象不到的问题。

       * 现在有些平台不一样：管得严的 iOS 为防止审核后注入未受审核的新内容而不让热更；主机（PlayStation、Xbox）上游戏被平台加密、加密过程不受开发者控制，热更沟通成本很高——做 online game 的开发者为此非常痛苦。

       * 两种可能未来：平台越来越封闭、大家都不干了；或大家意识到超复杂游戏没有热更没法做，慢慢想方法开放授权。

## 引擎与脚本的分工

   * **两种架构方向**

       * 方案一，引擎调脚本（Unity 思路）：引擎每帧 tick，走到某个特定 component 时执行该组件对应的脚本——Unity 里每个 component 都可以扩展成一个脚本，用 C# 去写。

       * 方案二，脚本包引擎：引擎变成一个 SDK 库，只提供各种基础服务，由脚本控制整帧的 tick flow——脚本说"你们这些 animation 可以休息了"，把名单发回引擎，引擎照单执行；早期一些很著名的大作真用过这种结构，现在少多了。

       * 走方案二必须认真设计引擎往外暴露的接口。

       ```text
       方案一：引擎调脚本（Unity 思路）
         引擎每帧 tick
           └─ tick 到某个特定 component
               └─ 执行该组件对应的脚本

       方案二：脚本包引擎（引擎变成 SDK 库）
         脚本控制整帧的 tick flow
           ├─ 按需调用引擎暴露的基础服务
           └─ 把处置名单发回引擎，引擎照单执行
       ```

   * **GO 归谁管：引擎统一管理**

       * 问题本身：脚本里每个非玩家角色（NPC）有一个脚本对象，引擎里每个 NPC 又有一个 GO——它的整个生命周期与销毁到底谁负责？主城里几十个 NPC 玩完不销毁，内存就一直被占用；这个决定在引擎设计时非常关键。

       * 引擎流派：C++ 引擎效率最高、做过大量安全性测试，GO 全部放引擎内核管理，NPC 逻辑坏了由脚本发指令让引擎删掉。

       * 两个要求：脚本每次访问 GO 都要先问对象有没有被销毁；引擎的对象管理要写得相对严谨——C++ 内存管理一旦做不好就是内存泄漏。

       * 麻烦：业务复杂后很多 GO 的创建与消亡由玩法决定——扔出一个道具突然变成三个会捡石头砸你的小怪物，石头又是 GO；这种创建逻辑写在脚本里最简单，每次都绕引擎一圈非常麻烦。

   * **GO 归谁管：交给脚本与 GC**

       * 脚本流派：玩法丰富复杂的游戏把 GO 的创建和管理交给脚本系统，引擎只引用脚本创建的 GO、不负责其生命周期管理。

       * 销毁靠垃圾回收（GC）：发现对象不再被人需要，就专门找时间把这个对象清掉。

       * GC 爱恨：爱——省事，无脑创建、用完就扔，不碰 C++ 式野指针与内存泄漏；恨——算法特别慢，每一次要整个扫描上下文（context）里的引用关系。

       * 代价量级：脚本写得非常复杂时 GC 效率会非常低，有的复杂游戏产品里 GC 本身要吃掉整个游戏时间的 1/10 左右；重度脚本化复杂 MMO 团队的核心话题就是优化 GC。

   * **怎么选**

       * 对象不多但每个都有极丰富的动作与 AI 细节（欧美单机常见形态）：倾向把生命周期交给引擎管理。

       * 业务特别复杂、玩法经常产生大量新 GO 的游戏（最典型是 MMORPG）：一般把生命周期放在脚本里管理，玩法系统里创建销毁物体都很自由。

       * 两种方法各有利弊，完全取决于游戏类型与引擎；"GO 归谁管"是引擎与脚本两边拉扯的问题，还没有被彻底解决。

## 脚本语言的软肋与选型

### 效率与 JIT

   * **效率短板**

       * C++ 最快，Java 慢一点，C# 速度其实还可以；Lua 这类脚本语言比原生语言慢很多——这是脚本语言被诟病最多的软肋。

   * **即时编译（JIT，just-in-time）**

       * > **定义**：一边解释一边编译，等下一次执行时直接运行已生成的机器码；LuaJIT 是大名鼎鼎的实现。

       * JIT 的独门优势：它一边运行一边编译，知道代码的实际执行路径——脚本里 99% 点几的情况都走不到的分支，整个脚本跑遍后 JIT 直接把这些分支全部优化掉；理论上 JIT 做得好可以超过编译语言。

       * 事实基准：LuaJIT 比原生态 Lua 快一个数量级没什么太大问题——脚本语言的效率问题其实解决得蛮好。

### 弱类型

   * **弱类型（weak type）的两面**

       * 表现：C++、C# 的面向对象结构做得非常好；而 Lua 里创建的对象没有类型，根本不知道那是什么东西。

       * 好处：什么都塞得进去——一个结构、一个函数都能存进去、都能调用。

       * 坏处：想反射它内部到底是什么数据挺麻烦——得去抠 Lua 内部的结构，抠是能抠出来，但效率比较低。

### 三种主流选择

   * **选型考量**

       * 挑脚本语言看自带 feature：库是否丰富（很多操作一行指令搞定）、是否高效轻量省内存、面向对象封装是否好（不用自己搭复杂数据结构）。

   * **三种语言的画像**

       * Lua：虚拟机非常轻、节约内存、效率高、与 C++ 的接口效率做得非常高；缺点是基本上什么库都没有，各种扩展都要自己写——《魔兽世界》用一己之力把 Lua 介绍给了整个中国游戏行业。

       * Python：库特别强大丰富、天然面向对象、扩展库支撑强；问题是非常重——虚拟机一跑起来几百兆内存就没有了。

       * C#：借助 Mono（.NET 现已官方支持）可以把这种原生态编译语言当脚本语言用；学过 C/C++ 后上手成本非常低，社区与库支撑强大——Unity 完全依托 C# 的可扩展性。

| 维度 | Lua | Python | C# |
| :--- | :--- | :--- | :--- |
| 执行效率 | 一般垫底 | 也快不到哪去 | 高很多 |
| 内存占用 | 最省 | 最重（虚拟机一跑几百兆） | 中间，找到平衡 |
| 生态与库 | 基本没有，都要自己写 | 库强大丰富、天然面向对象 | 社区与库支撑强大 |
| 代表场景 | 魔兽世界带火它 | 数据处理、大数据 | Unity 完全依托它 |

   * **改造脚本语言的代价**

       * 踩坑实录：最早接 Lua 时嫌弱类型难管理，把整个 Lua 改造成面向对象——结果 GC 变得特别慢；上 LuaJIT 后 JIT 基本不能加速，因为没按它最原生态的方法去写（Python 天然面向对象，反而不存在这个问题）。

       * > **易错点** ⚠️：给脚本语言"补"一套面向对象不是免费的——自己改造出来的对象体系会拖垮 GC、还会让 JIT 失去原有的优化空间；要用脚本语言，就按它最原生态的习惯用。

   * **混合编程的现实**

       * 一个真正的现代游戏引擎是十几种完全不同语言的复合体：服务器用 Go，脚本、UI 可能用 C#，管理服务器用 Python，还有 C++、Java 与前端语言——每个场景选一个更适合它的语言。

       * 实现引擎与脚本系统对接，就是第一次真正感受"混合编程做大型系统"的地方。

## 可视化脚本

   * **为什么需要可视化脚本（visual scripting）**

       * 对非程序背景的开发者——特别是设计师和艺术家——编程成本非常高：变量怎么声明、生命周期怎么管理都不可控，一个设计师想写几行能编译通过的代码就已经哭爹喊娘。

       * 写代码的错误（对象类型用错、函数调得不对）在写的时候看不出来，只有执行时才知道；可视化脚本通过各种提示与关系锁定把这些 error 提前屏蔽——Blueprint、Unity Visual Scripting 以及基本上所有现代引擎都提供可视化脚本，就是这个原因。

   * **理解框架：编程语言六要素**

       * 变量（定义数据）、表达式（加减乘除带函数运算）、语句（执行动作，如 print、画线）、控制流（if-else 控制行为）、函数（把一堆操作打包成包体便于反复调用）、类（把类似功能和它的数据打成一个包）。

       * Unreal 的 Blueprint 是做得最成熟、最老牌的可视化脚本语言，上述概念基本都被完整实现。

       * 掌握这套基础结构后，做一个类似 Blueprint 的简单系统难度并不大：用 WPF 做 UI、加上脚本语言知识就能搭出基本可用的简易可视化编程语言；有的引擎做叙事系统（story flow）用的就是这套方法。

### 变量与引脚

   * **变量的两个核心**

       * 类型：布尔、int、颜色、向量……

       * 作用域（scope）：变量属于谁——角色血量跟角色相关、世界温度跟整个世界相关；角色血量的变化不影响其他角色的血量，更不会影响世界的温度。

   * **引脚（pin）**

       * > **定义**：脚本图（graph）里定义变量的接口——几乎所有可视化编程语言都用不同形状或颜色的引脚表示数据类型，从物理上避免把错误的数据接进它的输出。

       * 对艺术家的价值：看颜色连线即可（绿连绿、蓝连蓝），完全不用管类型系统；可直接转换的类型（float 转 int、int 转 float）由引擎直接加一个类型转换器节点。

       * 调试时鼠标移上去就能看到这个值此刻是多少——比 C 语言时代"编译器事后报错"更直接。

### 语句、表达式与控制流

   * **表达式节点**

       * 加减乘除、比大小；所有可视化脚本语言都会 highlight 一个巨大的符号，明示这是加法、比较还是乘法。

   * **语句节点**

       * > **定义**：执行一个动作的节点——在状态机（state machine）或蓝图类语法里通常画成类似三角形的符号，动作做完再回去走下一个动作。

       * 例子：execute print string——给它一个输出变量（字符串内容），执行完游戏上方的控制面板就打印出一行字；再比如"让屏幕的相机抖三抖"，抖完三抖继续走下一个 flow。

       * 真正执行的 flow 用语句节点走，另外很多节点只做表达式运算。

   * **控制流（control flow）**

       * 负责比较大小、要求依次执行等；要区分两种比较：数据的比较与执行的比较。

### 函数与类

   * **函数**

       * 动机：很多运算经常被调用、希望有更清晰的输入输出——把一系列操作打包到一起、抽象出输入；执行入口只有一个，出口可能有很多个，进出边界清晰后函数成为封装单元。

   * **类与 Blueprint 的相似性**

       * 类：希望数据和它的处理形成闭包、打包成一个整体。

       * Unreal 的 Blueprint 非常像一个类：定义很多只属于自己的局部变量，有的设成 private 只能自己看到、有的别人也能看到；虚幻是非常深受 C++ 思想影响的引擎，Blueprint 体系结构基本是把 C++ 的概念用图形化的方法表达出来——理解了这一点，它的难度就不大。

   * **辅助体验**

       * 鼠标悬停可以非常快速地测试这些节点；从一个点拖出连线时直接给提示——这类功能极大提高使用者效率，自研引擎做完基础功能后非常值得补。

       * 引擎的本质是生产力工具：引擎的好坏不由功能数量决定，而由别人用起来的效率决定——如何做让别人用起来效率很高的引擎，门槛非常高。

### 调试、合并与可读性

   * **调试很直觉**

       * 逻辑全部可视化后：对象处于什么状态，对应节点就被 highlight，鼠标一上去能看到各种值——对没有编程基础的人，debug 变得非常简单、非常直觉（程序员反而常觉得 Blueprint 没有写代码舒服）。

   * **合并（merge）很痛苦**

       * 代码 merge 比较简单：Beyond Compare 一类工具就够，而且容易理解"这一行加上去语义发生了什么变化"；图的 merge 不同——节点的添加、删除、移动之后，就算 merge 出结果，结果的语义已经没有一个人能讲清楚。

       * 工程铁律：大团队用带可视化编程的引擎，prototype 阶段用可视化脚本非常快；一旦进入产业化生产，工程师一定会把它变成 C++ 原生代码或用其他脚本语言替代——为了可管理、可 merge，也因为早期 Blueprint 执行效率比较低。

   * **可读性差**

       * 代码是线性的、可以依次读下去，且有函数定义、类定义、不同文件上下文的分块性，清晰易读；真正商业级游戏产出的可视化脚本有时就像一团乱麻——除了画图的人自己，别人接手根本看不清怎么用的。

       * 定位：给设计师和艺术家做 prototype 的好工具；工业化应用时必须用很多方法把它变成可规范、可追踪、可 debug 的东西。

### 可视化脚本的本质

   * **可视化脚本与脚本的关系**

       * > **定义**：可视化脚本系统和脚本是一模一样的东西——把 Blueprint 或 Unity Visual Scripting 的图（visual graph）直接编译成一个 Lua 或 C# 脚本，两者可以执行出完全一模一样的效果。

       * 实现路径：先写一套自己的脚本系统，再做一个图形化逻辑系统，中间只差一步"把 visual graph 渲染成脚本代码"，前面所有逻辑都不用动。

       * 演进：现在很多引擎不再绕道脚本，直接把图编译成字节码，效率更高；若想增加可调试性（debuggability）或少写代码，也可以走"图 → 脚本 → 机器码"的链路，效果完全一样。

   * **实现代价**

       * 入门概念简单、细节复杂度高：要在可视化系统里定义各种新 event、扩展游戏功能、兼容其他脚本的额外功能，系统就会变得非常复杂。

       * 工作量标尺：实现一个简单的可视化编程系统，一个人做几个月真的能做出来；商业级可用的一群人干一两年很正常——Blueprint 已迭代多年、至今仍在快速演进。

## 3C 系统

   * **3C 的构成**

       * > **定义**：角色（Character）、控制（Control）、相机（Camera）——玩家通过角色感知并介入游戏世界，通过相机看到并感知角色；游戏最直接的体验来自 3C（它不是所有玩法的核心，但是最直接体验的来源）。

       * 标杆案例：《双人成行》（It Takes Two）把 3C 做到极致，很多地方比 3A 大作做得都到位。

### 角色

   * **角色系统管什么**

       * 不是角色的模型与动画，而是移动、战斗、血量（health）与放魔法的技能体系这些 feedback 系统——它们对感知游戏的影响最直接。

   * **移动的细节密度**

       * 3A 游戏的角色移动要响应无数细节：碰障碍物、上坡下坡、走着走着突然停、穿过一道门、面前有个小坎儿；不做这些，角色看起来就很僵——没有人喜欢玩一个像 robot 的角色，看山看平地都一个走法。

   * **与环境的互动**

       * 走着走着突然抓一个东西吊起来；踩到冰面整个动作变成滑冰；跳进水里行为又不一样。

       * 还要跟 terrain 系统配合（地面是沙地还是雪地），并在不同环境下产生各种各样的音效与 particle 效果——都是角色系统跟环境的互动。

   * **与物理的协作**

       * 滑翔时要模拟空气的 flow——既要有自己的控制，又要有物理的输出。

   * **实现方式：状态机**

       * 角色系统一般用状态机的方法实现：动画状态机里的每个节点还可以是一段脚本系统——动画切换的同时挂着复杂业务逻辑；一个好的 character 系统是大量内嵌逻辑的动画 script / graph 综合的结果。

       * 引擎侧的正确姿势：引擎做物理、动画、脚本系统，但要允许这些系统的状态互相通讯，并把"通讯后发生什么逻辑"开放给设计师定义——control 与 camera 同理。

### 控制

   * **控制系统的核心任务**

       * 处理五花八门的输入设备：方向盘、手柄、鼠标键盘、飞行模拟器、VR 手势……输入与游戏并非直接关联，control 负责把 input 变成真正的 gameplay，且不同 gameplay 感受不同。

   * **射击瞄准的细节拆解**

       * 按下鼠标右键瞄准：状态切换，相机与 UI 聚焦——FOV 变小（望远镜效果同款原理）、相机位置变化，更聚焦地看目标点。

       * 按下左键开火：产生 aim、shoot 这样的 event，行为随之变化。

       * 准星吸附：引擎侧要开放一个编辑系统给设计师和艺术家——先定义哪些东西是目标；脚本判断"我和它的夹角小于多少度"时触发吸附；吸附不是一瞬间完成，有一个过渡过程。这件事对游戏手感影响非常大。

       * > **提示**：眼睛看到目标、反映到手上、手柄传输到主机、主机再处理——这条链路的 latency 可达将近一两百毫秒，准星移动还带惯性；这就是主机射击游戏普遍要做瞄准吸附（aim assist）的原因——不做吸附基本套不中人，更别说用狙瞄。

   * **反馈（feedback）**

       * 手柄震动：《双人成行》里让人"太想去了"的桥段很大程度靠震动做出来；高级飞行摇杆、赛车方向盘与整套座舱都有力反馈。

       * 键鼠也有答案：RGB——打游戏紧张时键盘/游戏本背光变化、残血时突然变成一片血红；做不了力反馈时，最简单的光效也能给一点代入感。

       * 现代设备越来越注重反向的多态反馈：PS5 手柄带小喇叭（玩恐怖游戏突然响）和麦克风（能听到其他玩家说话）。

   * **控制是游戏与电影的分界**

       * 电影是被动媒体（passive media）：做啥你看啥、不要任何反馈；游戏是主动的（proactive）媒体，最核心的精髓是游戏世界与玩家行为之间的互动——control 就是解决这个互动最核心的系统。

   * **输入的多态与开放**

       * 同一按键在不同环境下产生的操作完全不一样——这不该由程序员控制，引擎只能提供接口，让设计师、艺术家通过可视化脚本或脚本来定义。

       * 用户输入本身是多态的：可以是组合键（combo），也可以是一串按键序列——《街霸》的按键序列就是玩家反复苦练的东西。

       * control 是最被低估的系统：只会"按什么键做什么事"的直接翻译成不了系统；3A 级的 control 才是丝滑手感的由来，实际上决定了整个游戏的手感。

### 相机

   * **相机的任务**

       * 最简形态 = 设定相机位置（POV）+ 张角（FOV）；但精妙之处在于：相机与角色绑定后，随角色跑动走动，相机的距离远近都会变化——并不是固定死在身后某个长度上、只由视角决定。

   * **弹簧臂（spring arm）**

       * 第三人称视角左右移动时保证相机尽量不穿墙；处理有分支：有的场合不能穿墙，有的场合可以穿但要把墙做成透明——到今天还有游戏做不到、留有这类 bug。

       * 进入 focus 模式时，相机要变得更聚焦。

   * **相机笼（camera cage / camera track）**

       * 设计师为角色在不同状态下精心定义相机参数（包括位置），最后在空间上可视化出来，像一个形状很奇怪的笼子。

   * **主观感受（subjective feeling）**

       * > **定义**：相机表达的是人非常强的主观感受——恐惧时瞳孔放大、FOV 缩小、更聚焦眼前的敌人；放松时瞳孔缩小、视野更宽泛；相机系统就是让设计师有能力精准表达这种主观感受。

       * 玩家并不真的在游戏世界里，但隔着屏幕能感受到身临其境的紧张感与代入感——这是相机系统的核心命题。

       * 表现手法：motion blur（运动模糊）+ 相机抖动 + 视野放缩，构成滑道的速度感与代入感；相机有自己的惯性、自己的逻辑，角色运动才显得"活"——机械地绑在角色身上，你不会觉得相机死，会觉得角色很僵。

       * 相机有时还负责产生电影般的画面。

   * **相机效果（camera effect）**

       * 最著名的是抖屏；还有打一下屏幕突然全屏白掉、黑掉——打击感里用到了很多相机技术，这类效果要开放给设计师。

   * **相机管理器（camera manager）**

       * 真实游戏里有很多台相机按游戏状态来回切换，玩家以为屏幕后面只有一台：

       ```text
       端起枪瞄准   ->  第一人称相机（看不到自己）
       收枪走路     ->  第三人称相机
       拎起加特林   ->  相机位置又变；左右张望时视角再变
       急奔冲刺     ->  又一台相机
       进入赛车     ->  相机位置与逻辑再变
       ```

       * 光"端枪—收枪—拎枪"这么一个简单过程已经切换了三次相机；camera manager 负责管理相机池，还要在相机之间实现插值。

   * **引擎支撑与性价比**

       * 引擎侧必须允许用脚本系统或可视化脚本编辑相机行为：读取角色速度、调用各种相机效果、调整 FOV、让相机抖动……否则别人做不出高质量游戏。

       * 相机系统是让游戏有"大作感"的性价比极高的系统——类比渲染里性价比很高的后处理查找表（look up table，LUT）。

## 玩法系统的本质

   * **Gameplay is Everything**

       * 玩法系统的边界并不清楚：物理、渲染边界特别清楚，而游戏玩法的几乎所有东西都是 gameplay——它很难被定义边界。

       * 行业多年沉淀的三件套：用 event 系统统一游戏内各对象之间的 communication（让通信有序、可管理）；逻辑写不进引擎就开放 scripting 系统，让设计师、艺术家定制玩法；scripting 太难学就再上 visual scripting，让大家更方便地掌握玩法的开放。

   * **没有一招鲜**

       * 真要做一个 RPG、卡牌、FPS 或 RTS，它们的 gameplay 差别非常大，很多上层代码甚至引擎里的某些东西都要被改掉。

       * 很难找到一个能 cover 所有游戏的"一招鲜"架构；基本上每一个优秀作品在 gameplay 系统上都有自己的想法与突破——这也是不同类型游戏各有引擎 preference 的原因。

   * **可视化脚本与脚本并存**

       * 两者不是替代关系：可视化脚本多用于早期 prototype、开放给艺术家和设计师；脚本往往写得效率更高、更好维护，一般都会保留——可视化脚本做得最好的虚幻引擎，很多团队用它的同时也一定会再开发一套自己的脚本系统。

       * 建设顺序：先把脚本系统支持了，再去支持可视化脚本；有了可视化脚本之后也不要喜新厌旧，两套系统都要保留。

   * **逻辑与表现分离吗**

       * 取决于游戏类型：传统 MMORPG 表现相对简单（技能打出去、伤害怎么结算），逻辑可以由设计师团队单独写——策划像向艺术家下订单（"要这几个特效、打多远、从低级到高级"），配好数值、结算、音效后表现直接调用；工种分离、decoupling 越好开发效率越高，团队规模也做得很大。

       * 现代游戏的要求变了：玩家不再满足纯数值，要打击感、动作表现、角色与环境互动的细节——捡装备要弯腰拿起来看两眼、发光装备上身有特效、负重让走路姿态都变化；逻辑与表现的关系越来越密切，客观上要求设计师、艺术家、程序合力把玩法与表现糅在一起做，对团队与引擎都提出更高要求。

       * 实践判断（尤其主机游戏）：玩法与表现比较难以分开——3C 本身就不只是表现，它跟玩法高度相关；架构上保持开放性，若有能分开的更好架构值得尝试。

       * 对引擎的最终理解：现代游戏引擎不是完美的理想架构，而是做了大量妥协、保持各种可能性的工程基础平台——按游戏类型选取其中模块去强化，表现自己游戏的内容。
