# 番外漫谈：从20万播放唠嗑到图形学成长

## 课程定位与入门门槛

   * **写引擎课程（engine-building course）**

       * > **定义**：课程补的是“怎么写出一个引擎”的空白，而不是“怎么使用一个引擎”。

       * 立项理由：市面上铺天盖地是教怎么用引擎的课程，很少有课程教怎么去写引擎。

       * 核心判断：引擎看起来难、神秘，但一项项拆下去，每个技术点都学得会、做得到。

   * **入门痛苦期**

       * 典型时长：刚接触引擎时整整半年不会写代码——每个算法都懂，但不知道该怎么写。

       * 第一次动笔的结果：鼓起勇气写第一行代码，等待的一定是整个 crash。

       * 越过的标志：成功写出第一段小代码时会一下茅塞顿开；小引擎持续重构就是为了让人更容易写出第一段引擎代码。

   * **专业背景与入行条件**

       * 引擎知识点和面特别广，无论喜欢什么、有什么才能，都能在引擎里找到发力点。

       * 团队成员来自生物、土木工程、无线电、信号等专业，专业不对口不构成障碍。

       * 三个条件：思维方式清晰、对引擎感兴趣、肯学习；具备后大约一年可以入行。

       * 软件工程是离引擎开发最近的行业之一，因为引擎本质上是对真实世界的模拟，非常符合直觉。

   * **课程节点与社区约定**

       * 播放量突破 20 万。

       * 约定到 30 万时，由观众留言指定课程组“整活”。

       * 曾向社区征集小引擎名字：先查重，再把无重复的名字连同取名寓意发到社区投票。

       * 对穿帮、穿模镜头的态度：复杂系统在特殊情况下会遇到特殊问题，从业者更关注整体游戏性，不点评一两个 bug。

       * 理由：自己写游戏、写引擎也写出过很多 bug，包括早期在主机游戏项目中贡献的严重 bug，不仅不引以为耻，还引以为豪。

## 小引擎的重构与协作

   * **重构动机与范围**

       * 原架构的问题被概括为“想得太多、做得太复杂”，中间有些代码太绕。

       * 重构持续约两个多星期，把 framework 整体简化掉。

   * **框架层**

       * 彻底去掉复杂的 singleton 机制：没有必要，且会让很多生命周期管理变复杂。

       * component 系统重构后更简单、更清晰。

   * **渲染层与 RHI**

       * 原先同时引入 Vulkan 与很多中间概念，理解门槛高；这次对整个 rendering 做了一次大清洗，pipeline 与体系更简单清晰。

       * RHI 这次只提供简化版本，先让人能看、能懂，后续继续优化。

   * **编辑器与引擎的边界**

       * 编辑器层与引擎层的划分更清楚。

       * 鼠标键盘输入此前分得不够清楚，新版本尽可能分清。

       * 社区贡献了给其他编辑器编写代码的辅助支持，Visual Studio 之外的工具也有更好的开发体验。

   * **开源与文档节奏**

       * MetaParser 首次未开源，原因是担心编译过于复杂。

       * 开源顺序：先把小引擎的问题解决，再把 MetaParser 开源给社区。

       * 小引擎约 3 万多行，读起来、理解起来仍有困难，因此持续用 Wiki 介绍结构。

   * **社区贡献与命名**

       * 第一个由社区小伙伴完整贡献的 feature 是 FXAA，已并入小引擎。

       * 小引擎原名 Pilot，图标受喜爱。

       * 最终名称由社区投票选出。

       * 结课彩蛋的落点是 “Welcome to Piccolo”——小引擎的世界叫 Piccolo。

## 物理在引擎中的位置

   * **直觉认知的载体**

       * > **定义**：物理是游戏里玩家对世界产生直觉认知的最重要表达；没有物理，很难相信这个世界是真实的。

       * 任何输入操作、角色运动，都会让玩家感到世界在跟自己互动。

   * **动态环境改变 gameplay**

       * 打掉面前的墙，视野与战术随之变化。

       * 《彩六》以穿墙、钻地板为核心，在 FPS 赛道里开出新赛道，是最经典的 dynamic environment。

   * **真实可互动世界的样本**

       * 《半条命：Alyx》被视为当前 VR 的巅峰之作，对真实感的营造做到极致。

       * 可以把椅子、垃圾桶扔进洗衣机盯着滚筒看——物理满足玩家的“恶趣味”。

   * **表现层依赖物理**

       * particle、smoke、水体等表现都依赖物理系统。

       * cloth：斗篷抖得好不好、角色跑起来衣服是否飘逸，直接影响对游戏质量的判断。

   * **两节课的分工**

       * 基础课讲物理语言如何表达世界、物理世界有哪些元素及其关系，点到物理引擎底层算法；不想碰硬核部分的人只需理解基本概念与“怎么接入一个物理引擎”。

       * 进阶课讲角色控制、ragdoll 布娃娃、破坏、衣料仿真、载具系统，以及 PBD。

       * PBD（基于位置的物理）在最新一代一线引擎里已在逐渐引入。

## Actor 的四种类型

   * **Actor 与 Shape**

       * > **定义**：物理世界里的对象统称 actor 或 shape；每个 actor 带 shape、质量与物理材质。

       * 渲染、动画看到的小人只是“壳”，负责表现；物理世界里有一个孪生 actor 参与解算，两者一一对应。

       * 物理通常放在 logical part；用物理做 particle 时，它同时可能属于逻辑与表现。

       ```text
       渲染与表现（rendering part）
         网格 / 动画 / 材质 / 光照
         玩家看到的小人
               │  每个对象在物理世界里都有一个孪生
               ▼
       物理与逻辑（logical part）
         Actor：静态 / 动态 / Trigger / Kinematic
         每个 actor 带 Shape、质量、物理材质
       ```

   * **静态 Actor（static actor）**

       * 状态每帧不变，不参与解算；地面、墙、挡板、曲面都属于这一类。

       * 角色移动会受这些静态物体阻拦。

       * 大部分游戏里静态 actor 数量最大。

       * 《彩六》里看起来东西很多，绝大部分仍是静态的；哪些桌子、灶台可摧毁是预先设计好的。

   * **动态 Actor（dynamic actor）**

       * 符合动力学原理：踹一脚会往前滑；放在斜面上，在重力与摩擦力作用下产生惯性。

       * dynamic 指动力学（dynamics），不是日常语义的“会动”。

       * 每帧都要解算受力与状态，成本高，一般不要做太多。

   * **Trigger**

       * 与物理无关，只负责发消息，是逻辑触发器。

       * 典型用法：超市自动门前放一个 Trigger；任何 Character 或 Pawn 走近，就发消息让门打开。

       * 动画树里大量改变状态的 Event，来源很大程度上也是 Trigger。

   * **Kinematic Actor**

       * > **定义**：由设计师或动画直接设定运动状态的 actor，本质反物理，不遵循牛顿定律。

       * 角色跑步时手挥到下一帧的某个位置，由动画直接给定；加速度、阻力都不由物理解算。

       * IK 称为反向动力学；Kinematics 本身在中文里没有给出对应译名。

       * 一定要用，但必须慎用：反物理会让数学运算 degenerate（失效），可能算出无穷大。

       * > **易错点**：kinematic actor 处理不好会产生无穷大的作用力或冲量，表现为角色或物体突然飞掉、飞到无穷远处，是经典 bug 之源。

       * 例子：牛抬脚踢角色，脚上绑的是 kinematic 骨骼；反物理的碰撞若参数不对，冲量可能变成无穷大。

       * 例子：推箱子时力没设好，箱子会直接飞走。

| Actor 类型 | 物理解算中的地位 | 主要用途 | 使用提醒 |
| :--- | :--- | :--- | :--- |
| 静态 Static | 不解算，每帧状态不变 | 地面、墙、挡板等世界基础与阻碍 | 数量最大；可摧毁与否要预先设计 |
| 动态 Dynamic | 每帧解算受力与状态 | 可被推动、会滑会滚的物体 | 不要做太多，解算成本高 |
| Trigger | 不参与解算，只发消息 | 自动门、动画状态切换等逻辑触发 | 与物理无关，只负责事件 |
| Kinematic | 反物理，由动画或设计直接设定状态 | 角色肢体、夹板等 gameplay 需要 | 最重要也最危险，参数务必设对 |

## Shape 与包裹策略

### 形体谱系

   * **从简的动因**

       * 体与体求交本身很复杂：四面体与不规则凸多面体求交，写起来就知道痛苦。

       * 物理引擎优先采用解析方法能快速表达的形体，作为基础 actor 形状。

   * **球（Sphere）**

       * 定义只需一个球心加一个半径；球心一动，球就动。

       * 求交、移动、碰撞检测都最简单，是最便宜的 shape。

       * 用途：桌球等球类。

       * 各种小物件可用球做大致的近似。

   * **胶囊（Capsule）**

       * 上下两个球，中间一个圆柱，算法简单。

       * 用途：人形角色（biped）。

       * 一米七、一米八的人通常裹成一个一米八到一米九的胶囊。

       * 打开很多游戏的开发模型，会看到人上下裹着一个小胶囊。

   * **盒体（Box）**

       * 由长、宽、高三边定义；物理引擎里的 box 常是长方体而非正方体。

       * 包裹只是 approximation；非常精细的结构用 box 大致表达即可。

       * 用途：门、箱子，以及精细结构的大致包裹。

   * **凸包（Convex Hull）**

       * 两个条件：必须是封闭空间包裹，不能有洞、不能漏；必须处处外凸，沿任一面无限延伸都不会交到其他面，不应有反向折痕。

       * 能表达的形状比球、胶囊、box 更多样，但更贵；一般只用于局部。

       * 用途：可破坏地形的碎片、复杂石块——看上去逼真，是因为碎片几乎用 convex mesh 表达；算多了也很费。

       * Manifold 是更数学的概念，此处不展开。

   * **三角网格（Triangle Mesh）**

       * 由一组三角形构成封闭表面，第一个要求是密闭。

       * 很贵。

       * 目前在物理引擎里一般只允许静态物体使用。

       * 用途：房子等无法用简单形体表达的建筑；让这类物体动来动去再求交会特别复杂。

   * **高程图（Heightfield）**

       * 用一张高度场表达地形。

       * 全局通常只有一个。

       * 只能处理静态物；在地形上扔球弹跳，若做成凸包或 box 都会非常复杂，所以物理引擎支持 heightfield。

| Shape | 怎么定义 | 限制与代价 | 典型用途 |
| :--- | :--- | :--- | :--- |
| 球 Sphere | 球心加半径 | 最便宜，求交与碰撞检测最简单 | 桌球、球类、小物件近似 |
| 胶囊 Capsule | 上下两个球加中间圆柱 | 便宜，算法简单 | 人形角色（biped） |
| Box | 长、宽、高三边 | 便宜，包裹只是近似 | 门、箱子、精细结构的大致包裹 |
| 凸包 Convex Hull | 封闭且处处外凸的多面体 | 较贵，一般只用于局部 | 可破坏地形碎片、复杂石块 |
| 三角网格 Triangle Mesh | 一组三角形构成的封闭表面 | 很贵，一般只允许静态物体使用 | 房子等无法用简单形体表达的建筑 |
| 高程图 Heightfield | 一张高度场 | 全局通常只有一个，只处理静态物 | 地形 |

### 包裹原则

   * **近似优先**

       * shape 只是 approximation，是估计，不需要包得非常精细。

       * 物理做精细非常费，计算复杂度很高。

       * 复杂结构用简单形体大致包住即可。

   * **简单优先**

       * 代价顺序：球 < 胶囊 < Box < 凸包 < 三角网格。

       * 能用球、胶囊、Box 包住时，不要用凸包；更不要用三角网格。

       * 高程图全局通常只有一个，只服务地形这类静态世界。

       * 对象有几千甚至上万个时，shape 不能乱用；用错会让游戏突然变慢或产生莫名 bug。

   * **理解优先**

       * 做引擎的人不一定需要知道物理具体怎么算、数学方法是什么，但必须清楚每种 actor、每种 shape 的基本概念。

       * 物理解算的数学复杂度高于 rendering 与动画；物理一旦用错，表现是变慢或 bug，且很难定位原因。

### 质量、密度与质心

   * **质量（mass）**

       * 每个 shape 要么设质量，要么设密度，两者都可。

       * 若世界是闭包，给定密度可以反算质量。

       * 物理引擎假设每个 actor、每个 shape 的质量均匀分布。

   * **均匀质量与冈博茨（Gömböc）**

       * 以往认为任何形体在空间上至少有三个稳定平衡点（三个或以上），数学家长期无法证明。

       * 后来有数学家做出只有一个静稳态点的匀质物体，即冈博茨；密度均匀，却永远只趋向一个平衡点。

       * 不倒翁靠质量不均匀实现；匀质物体通常有多个平衡点，冈博茨是目前发现的只有一个静平衡点的形状。

       * 应用：海龟龟壳形状近似该形体，被翻过来会自己翻正。

       * 制造精度极高：误差容限在千分之一到万分之一量级，成品要上百美金。

   * **质心（center of mass）**

       * 普通模拟里质心不显眼；做载具（vehicle）时直接决定车辆稳定性。

       * 越野拉力类游戏里调整车身重心高度，驾驶感差别会非常大，即使在虚拟世界中也一样。

## 物理材质

   * **与 PBR 的区分**

       * > **定义**：物理材质（Physics Material）描述表面的力学属性，如摩擦力、弹性；PBR（基于物理的材质与光照）的“物理”指符合物理的光学特征。

       * > **提示**：PBR 讲光学上的物理正确，Physics Material 讲力学属性，两者不是同一个东西。

   * **摩擦与弹性**

       * 摩擦力：决定物体在表面上是滑还是涩。

       * 弹性：橡皮小鸭与钢制小鸭扔到地上，弹跳表现完全不同。

       * 有的引擎参数会更多。

       * 物理材质还常用来告诉引擎“这是什么材质”，并与声效、特效关联。

   * **参数改变行为**

       * 同样推一张桌子，桌面上的物件设为橡皮与设为光滑玻璃（玻璃弹珠），行为完全不一样。

       * 材质设置好之后扔进物理引擎，行为就会完全不同。

## 力与运动表达

### 力与冲量

   * **力（force）**

       * 没有力，物理世界是僵的；力是让 actor 动起来的东西。

       * 常见长期、稳定的力：重力、摩擦力。

       * ragdoll 倒地是重力拉着一节节往下倒；敌人从山上滑下是重力与摩擦力共同作用。

   * **冲量（impulse）**

       * > **定义**：冲量是短时间作用的冲力，用于车辆撞击、爆炸等极端行为。

       * “把你炸飞”就是冲量把物体推开。

       * 力乘上时间就是冲量；两者可视为一致，也可视为不同。

### 牛顿定律的数学形式

   * **牛顿第一定律**

       * 内容：物体不受力时倾向保持匀速直线运动。

       * 速度写法：$v(t+\Delta t)=v(t)$。

       * 位置写法：$x(t+\Delta t)=x(t)+v(t)\Delta t$。

       * 中学用形象直观的方法表达运动；引擎里用数学方法表达。

   * **牛顿第二定律与质量**

       * 加速度与力的大小成正比，与质量成反比。

       * 质量是物体阻抗其运动变化的量：越不愿意别人改变运动状态，质量越大。

       * 现代物理把质量本质解释为微观粒子与希格斯场的相互作用。

       * 更简单的解释：质量是拒绝改变物理状态的倾向性；重量不是固有物理量。

       * 位移与时间是平方关系：$x(t+\Delta t)=x(t)+v(t)\Delta t+\frac{1}{2}a\Delta t^2$。

### 变力与积分

   * **变力问题**

       * 真实世界大部分运动的受力随时间变化，速度一直在变，无法用恒定加速度表达。

       * 速度：当前速度加上加速度在 $\Delta t$ 上的积分。

       * 位置：当前位置加上速度在 $\Delta t$ 上的积分；速度本身已是积分，所以位置是两重积分。

$$v(t+\Delta t)=v(t)+\int_{t}^{t+\Delta t}a(t')\,\mathrm{d}t'$$

$$x(t+\Delta t)=x(t)+\int_{t}^{t+\Delta t}v(t')\,\mathrm{d}t'$$

   * **圆周运动的验证**

       * 地球绕太阳的圆轨道：离心力与万有引力在每一点平衡；位置、旋转、速度、角速度形成多向量约束。

       * 解析解很容易证明 $x(t)$ 在空间中画出一个圆，速度是位置对时间的导数。

       * 若只给“力随位置与距离的约束”，让计算机一步步模拟，画出来仍是圆，才说明画法正确。

       * 游戏把时间切成小片，引擎 tick 常为 $\frac{1}{30}$ 秒。

       * 普朗克时间约 $10^{-43}$ 秒，可类比世界的 tick。

       * 角速度每秒一弧度时，转完一圈约六秒多。

## 显式欧拉积分

   * **算法来源**

       * 欧拉在《Calculus》（微积分学）中提出；那个时代还没有计算机，却把这个问题研究得很透彻。

       * 核心思想：把整个时间切成一小片一小片，用当前状态推出下一刻。

   * **算法步骤**

       * 由当前位置求出受力，再由受力求出加速度 $a(t_0)$。

       * 先更新速度：$v(t_0+\Delta t)=v(t_0)+a(t_0)\Delta t$。

       * 再更新位置：$x(t_0+\Delta t)=x(t_0)+v(t_0)\Delta t$。

       * 关键：算下一个位置时用的是旧速度；速度的新值只对再下一步的位置生效。

       ```text
       t0 时刻
         │
         ├─ 由位置求出受力，再由受力求出加速度 a(t0)
         ├─ v(t0 + Δt) = v(t0) + a(t0)·Δt     ← 先更新速度
         └─ x(t0 + Δt) = x(t0) + v(t0)·Δt     ← 位置用的仍是旧速度
       ```

   * **直觉例子**

       * 第 1 秒位置在 $(0,0)$、速度为 1；算第 2 秒位置时先移动一步得到 1，再因加速度把速度改为 2，下一秒改为 3，如此累积。

       * 这是一种非常简单的数值积分算法。

   * **固有缺陷**

       * 总是用当前状态去预测下一刻。

       * 计算只要有一点误差，表现与行为就会完全不一样。

## 图形学从业路线

### 入行路径的分野

   * **共同点**

       * 三条路径分别对应学术界、工业界与创业，但三人回头看都没有认真找过工作。

       * 这并不等于没有门槛：每条路径都有具体的偶然与限制。

   * **学术界路径**

       * 工业界这头没找过工作：实习归实习，不进学术界可以直接去工业界。

       * 学术界 graphics 坑位本来就少，rendering 还常被调侃“这算什么问题”。

       * 投了很多地方，几乎没面试、没 offer，情况极端到接近没有 offer，很绝望。

       * 很多同学、前辈的经历类似，不是个例。

       * 最后靠 UCSB 收留，否则就去工业界。

   * **工业界路径**

       * 清华毕业前一个月才意识到要毕业，学校待不下去，去找老板；老板反应平淡：“哦，你毕业了呀，那好吧。”

       * 走过场面试，题目是拉普拉斯算子，当场忘光没解出来；对方说“算了，你进来再学吧”，第一份工作这样开始。

       * 第一年过后觉得每天都是同一套流程、像一个 loop，决定去真正最前沿的行业。

   * **创业路径**

       * 人还没毕业、手上没有 offer 时，红杉（后来成为太极图形的天使投资人）就找上门：“看你骨骼清奇，给你一笔钱，出来创业吧。”

       * 其他投资人说法大同小异；像武侠小说里被老头塞武功秘籍，但现实中并没有上来就打满级怪。

       * 认真考虑后选择做有挑战的事：人年轻，承受得起这个机会成本，最后下决心创业。

       * 本科阶段把自己关在宿舍写太极（Taichi）、疯狂写论文，一天不写代码、不写论文就浑身难受。

### 元宇宙与内容创作

   * **概念判断**

       * 元宇宙概念太大，相当于把原本不太相关的概念装进同一个框。

       * 喊两年元宇宙与能做出元宇宙是两件事情。

       * 有话题是好事：能让整个领域集中思考“为了实现元宇宙里的东西，到底要做哪些”，对学术界有好处。

   * **内容创作问题**

       * 谁来生产这些资产？不可能指望普通人也去学 Maya、3ds Max，去做以前艺术家做的事。

       * 真正要问的是：有没有一种方式能把创作门槛降下来。

       * 这更是“内容创作的本质问题”，而不是“元宇宙的本质问题”；元宇宙把所有东西都往里装，反而无从下手。

   * **全虚拟的“绿洲”**

       * 想做一个技术平台，支撑《头号玩家》里那个全虚拟的“绿洲”。

       * 把前沿 graphics research 算法真正变成工业界的东西：上 10 亿级用户、在各种设备上、在现有算力下跑得起来，并且能交互、连接、无限内容创造。

       * 工程挑战非常大，但够做 10 到 20 年；构建真正可无限连接、无限交互、无限内容创造且超逼真的世界，就是目标。

       * 到那时 VR 眼镜可以做得非常轻薄。

       * Z 世代 00 后会天然认为那就是“我的世界”，对那个世界的价值会超过真实世界。

   * **元宇宙里出生的婴儿**

       * 婴儿一出生就生活在元宇宙里，所有感知都由这个“上帝”给，类似《黑客帝国》的设定。

       * 长大后他问“世界是什么样”，感受到的可能就是那个虚拟模型本身；photorealistic 渲染对他而言已经是“世界”。

       * 关键差别：要造的是一个全新世界，不是把现在这个世界搬过去；而今天图形学科研做的恰恰是把现实世界了解明白。

       * 这个反差对思维有冲击，而能被冲击到是好事。

## 渲染前沿与恐怖谷

### 可解性反证

   * **物理同样有大量问题**

       * 那么大的游戏世界怎么模拟，肯定不能指望一台机器就跑得动。

       * 做这一行有个朴素信念：程序员只要有代码可写，心里就很踏实。

   * **“没有问题可解”的不安**

       * 某处技术上已经“没有问题可解”，反而会涌上一种莫名其妙的不安全感。

       * 做科研多少憋着一口气：不希望别人一直说 rendering 没东西可解。

### ground truth 的相对性

   * **比较套路**

       * 做出一个结果，要跟所谓 ground truth 比较。

       * 但 path tracing 本身也不是绝对正确，rendering equation 也不是绝对正确。

   * **物理公式只是简化**

       * 近年出现一套在波动光学下的光传播体系；回过头看，之前的物理公式是极大的简化。

       * 新体系也未必一定对；规律摆在那里，要想办法去打破它。

       * > **易错点**：把 ground truth 当成绝对真理，它只是当前物理认知下的近似，“标准答案”自己也会被改写。

### 剩余空间判据

   * **以假乱真的缺口**

       * 不管拿什么东西 render 出来，告诉你“那是真的，你信不信”，你总还是不信，总觉得还差一些。

       * 只要还差一些，就有东西可做。

   * **恐怖谷（uncanny valley）**

       * rendering 现在百分之百已经掉在恐怖谷里：准确度做到 80%~90%。

       * 要把大家想看到的最后 20% 做出来非常难；从谷底到 100% 是真正难啃的一段。

       * 正因为掉在谷里，后面要前进的事情非常多，有很多激动人心的事可做。

       ```text
       0% ──────────────────── 80% ~ 90% ──────────────────── 100%
          渲染已经做到的区间       ↑             完全以假乱真
                    恐怖谷（uncanny valley）卡在这里
                       最后 20% 是最难啃的一段
       ```

### 三维创作门槛

   * **目标用户**

       * 让一个小白用户也能创造出非常炫酷的 3D 场景。

       * 让 2D 设计师也能设计出漂亮的 3D 场景。

   * **现状与需求**

       * 现状远未解决：现在的这些软件都太难用。

       * 产业需求明确：电商广告从平面越来越多转向立体、3D 展示。

## 图形学的学习路径

### 学科定位与框架

   * **一群“物理学家”**

       * 做图形学的人像一群物理学家：剽窃上帝的设计，然后 try to mimic。

       * 在离散的世界里很笨拙地模拟、模仿上帝伟大的创作。

   * **环境与导师**

       * 数学方程与技术都需要环境：好的导师、好的环境，把知识的结构和框架告诉你。

       * 有了结构化地图，再看所有 graphics 技术和技巧，才不会一下子钻进某个细节里无限追、无限钻。

   * **现实限制**

       * 未必人人都有好导师与好师兄师姐，限制性因素很多。

       * 没有条件时，可以尝试自己造轮子。

### 造轮子与飞轮

   * **正向反馈**

       * 图形学写一些代码立马就能看到结果。

       * 正向反馈能把飞轮转起来，推着人造越来越 fancy 的东西，靠这种方式激励自己。

   * **课程的共同目标**

       * 三门图形学课程都在做同一件事：帮大家把知识的结构系统梳理出来。

       * 其中一门课的自评：质量远不及另外两门课，等公司平稳一些要重做一版。

### 入行动机

   * **同辈压力**

       * 竞争环境：有人本科毕业就有三四篇 CVPR；五年前这是厉害的成就，今天调侃高中生都有 CVPR。

       * 另一种节奏：有人本科毕业才有一篇论文出手，中间要坐冷板凳。

   * **因为喜欢**

       * 答案就是喜欢：因为喜欢，所以它就是对的，不用太在乎大环境。

   * **偶然的入口**

       * 小时候喜欢《暗黑破坏神》，在 BBS 问“以后想做游戏要学什么”，一位“上古大神”回帖说“学计算机图形学”。

       * 大学里老师问实验室做哪个方向，听到“真实感渲染”当场拍板：要做出来、看起来真实、用在游戏里；老师带去看人，就此入门。

   * **像素之后的人**

       * SIGGRAPH 的说法：做 graphics 的人是 the men and women behind the pixels——躲在像素之后的男人和女人。

       * 玩家说光照不对、动画僵硬时，做图形学的人知道屏幕上每一个像素都是一行行 shader 写出来的。

       * “值不值”很难正面回答，用一个词回答：好玩；别人做不来我能做来就很厉害，做不来也不亏。

## 结课彩蛋《擎空》

### 歌曲与学不懂的体验

   * **歌曲性质**

       * 《擎空》是一首唱给所有学游戏引擎的人的歌。

       * 它不总结任何知识点，却把一路的学习体验唱得比大纲还准：从看不懂的算法、像密码的代码，到那个一直渲染不出来的梦。

   * **摸不到与看不懂**

       * “摸不到”的发问：那种看不见、摸不着、人人都说很厉害的内功。

       * “看不懂的算法，是否来自太空”：难得不像人间的产物。

   * **论文与代码**

       * 论文：真相有没有烂熟于胸先不论，人已经被折腾得一身伤。

       * “别人写的代码，看着像密码”：类名、函数、调用链单看每个词都认识，连起来就是天书。

### 代码、构建与渲染的梦

   * **编译通过不是终点**

       * 程序构建成功、运行起来，状况照样不断。

       * 跑起来才是考验的开始。

   * **脑内架构与屏幕现实**

       * 副歌：“渲染的线程天天马行空，为何渲染不出我的梦？”

       * “马行空”的是脑内架构：线程怎么拆、管线怎么排，在脑子里跑得又快又漂亮，屏幕上却迟迟渲染不出。

       * 梦里我很轻松，随手一写就能成功；醒来面对的是构建成功也救不了的现实。

   * **“梦”的三次变形**

       * 先是“渲染不出我的梦”——被卡住的梦。

       * 然后是“梦里的我很轻松”——做梦时的轻松。

       * 最后变成“绽放的美梦”与“梦里那片绿洲”。

### 课堂符号与浪漫

   * **面向对象的三板斧**

       * 第二段副歌点名继承、多态、封装。

       * 面向对象的三板斧全在歌里。

   * **服务器上的会合**

       * “冲破身边服务器的线，在远方会和。”

       * 天南海北的人最后在同一台服务器里碰头。

### 体积光聚成剑

   * **行话当材料**

       * 歌词：“将体积光聚成剑，将箭射向苍穹，绽放出我的美梦。”

       * “体积光”本是渲染里的行话，拿课堂行话当铸剑的材料。

   * **歌名的落点**

       * “擎空”的擎是向上举；把光聚成剑、把箭射向苍穹，撑起的就是那片天。

       * 梦在这里翻面：从“渲染不出我的梦”变成“绽放出我的美梦”。

       * 梦里那片绿洲等着遨游，想要的东西越要越大——星星、月亮，甚至太阳。

### 首尾弧线

   * **开头的天**

       * 开头问“看不懂的算法是否来自太空”。

       * 前面还有“摸不到”的发问：两种“学不懂”的形态齐了，一种玄得摸不着，一种难得不像人间的产物。

   * **结尾的天**

       * 结尾唱“我想要星星月亮，甚至是太阳”。

       * 同一片天从“看不懂的天”变成“要摘下来的天”，整首歌的弧线藏在一头一尾之间。

### 结尾与落点

   * **自嘲与感谢**

       * 结尾先打趣“几何几何”：什么都要追问几何，结课快被唱成“玄学”，数学之重自嘲得明白。

       * 认真的那句：“在我脑海中闪过往坎坷的路，感谢你们相助。”

       * 最后一个落点是“终成眷属”，把一路相伴同行的人用最喜庆的方式谢了一遍。

   * **现场与下一站**

       * 现场还有闹钟、“为什么会停啊”“你是吃饭闹钟吗”“我是干饭的”“这就是打工人”这类没排练过的真实。

       * 收尾是“明年再见”，接着一声接一声的 “Welcome to Piccolo”。

       * 最后落在“欢迎来到 Piccolo 小引擎的世界”。
