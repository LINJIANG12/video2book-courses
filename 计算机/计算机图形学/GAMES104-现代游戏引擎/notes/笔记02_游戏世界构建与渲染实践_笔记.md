# 游戏世界构建与渲染实践

## 游戏世界的构成

   * **动态物（dynamic game object）**

       * > **定义**：游戏世界里可交互、能动来动去、会根据玩家行为做出反应甚至可被直接操作的对象，如地上跑的坦克、天上飞的无人机、端枪冲锋的 NPC 小兵、火炮与导弹。

       * 是大家最容易关注到的一类物体。

   * **静态物**

       * > **定义**：不可交互、默默立在原地的物体，如高高的瞭望塔、飞机机棚、房子。

       * 虽然不可交互，但整个构成了游戏里各种关键性场景元素。

   * **环境元素（environment）**

       * 地形系统：无处不在、无限绵延的大地，是所有动态物与静态物赖以支撑的托盘，在游戏引擎里一般是一个单独的系统。

       * 天空：要表现日夜变化、阴天晴天下雨、天上变幻莫测的云，这类动效与视效本身并不简单；日夜变换系统专门有个说法叫 TOD（time of day）。

       * 植被：固定在一个地方不太能动，但风吹了、炸弹炸了它又有交互且自身会变化，特点是量特别大——介于静态物与动态物之间。

   * **触发器（trigger box）**

       * > **定义**：玩家看不见的检测体，走进去它就知道了——如夺旗点走过去积分一直涨的判定区，或开飞机飞得正嗨时提示「已飞出 war zone」、五秒后把飞机击落的边界。

       * 游戏中用得最多的不可见物体是 trigger：单机游戏里走到某处天上突然掉下一个 boss 开始虐你，那个位置一般就是一个 trigger。

       * 空气墙常做成物体：单机游戏在没做内容、几何又做得不好的地方人为放一个 blocker 把玩家阻断；做 visibility 视觉裁剪时也会放看不见的东西，提示引擎玩家走到这里要加载场景内容，否则会看到空的一边。

       * 空气墙有时用一个大的物体就解决，有时分成很多很小的，shape 随引擎开发者怎么定义。

       * > **提示**：空气墙、触发器这类不可见物体一律用最简单的形体构建——用简单的面、圆柱或参数曲面表达，不要直接导美术 mesh。

   * **游戏对象（game object，GO）**

       * > **定义**：现代游戏引擎把游戏世界里的一切——动态物、静态物，连同触发器、空气墙、玩法规则——统一抽象成的对象。

       * 大地和天空是独立的系统，不并入 GO。

       * 整个游戏的玩法规则也可以抽象成一个物体。

       * GO 与 Go 语言、围棋的英文 Go 都不是一个东西，只是 game object 的缩写。

       * 构建游戏世界，就是把这一系列 GO 管理好。

## 属性与行为

   * **属性（property）与行为（behavior）**

       * > **定义**：属性是描述物体「是什么样」的数据——几何外形与动画、空间位置、血量、油量、电池量；行为是物体「做什么」——移动、沿固定路线巡逻、由 AI 算法控制的追踪与攻击。

       * 两类加在一起几乎就能描述所有物体，游戏引擎设计也是按这个分类进行的。

   * **朴素的类定义**

       * 定义一个类（如「无人机」），属性全部做成成员变量：位置用三维向量 Vector3，血量用 0 到 100 的标量，油量用 0 到 1；行为做成成员函数：move、巡逻。

       * 把数据和所有方法放在一起，最早期游戏引擎真的就是这么架构的——非常简单、非常直觉。

   * **用继承扩展**

       * 察打一体无人机 = 基础无人机加一个 attack（攻击）行为、加一个 armor（弹药量）属性——加两行就得到行为更多的无人机。

       * 对象的派生与继承是最标准的面向对象思维方式，与人对世界的认知一致。

   * **继承的缺陷**

       * 世界越做越复杂，物体间没有清晰的父子关系：坦克派生自车辆、巡逻艇派生自船，水陆两栖坦克的「爷爷」到底是车辆还是船？这是面向对象的经典问题，不只出现在游戏引擎架构上，现代编程语言里也有。

       * 经典解法是组件化，也是现在引擎最常用的方法。

## 组件化

   * **组件（Component）**

       * > **定义**：把对象按行为拆分出的功能积木——component 是 GO 的原子，一个 GO 由一组组件拼装、协同工作而成。

       * 直觉类比：玩具挖土机把铲子换成各种部件就变成小压路机、小推土机、小举重机；射击游戏给枪加三倍镜就是狙击枪、加消音器就是微冲——组件化思想十几年前甚至更早就被现代引擎用来重新描述和定义世界。

       * Unity、Unreal 这类商业引擎都提供 component 概念：打开 Unreal 点开任何物体，下面会出现一小串组件，组件可以增加、可以自定义、甚至可以写脚本。

       * 组件能力非常综合：点光源、面光源、方向光在 Unreal 里都会被定义成组件；Unity 里动画、物体模型也都是组件——组件作为积木构建出现代游戏引擎的整个技术结构。

   * **无人机的组件拆解**

       * 空间位移与占用给 Transform，外形给 Model，运动属性给 Motor，血量给 Health，AI、物理、动画行为各成一个小组件——七个小组件拼在一起就是一架完整的无人机。

```text
无人机 GO
├── Transform  组件 —— 空间位置与占用关系
├── Model      组件 —— 外形表达
├── Motor      组件 —— 最快爬升速度 / 加速度 / 移动惯性
├── Health     组件 —— 还剩多少血
├── AI         组件 —— 巡逻 / 追踪 / 攻击决策
├── Physics    组件 —— 物理行为
└── Animation  组件 —— 动画行为
```

   * **组件基类（ComponentBase）**

       * > **定义**：统一约定每个组件基础行为接口的基类，必含 tick 函数。

       * Transform、Model、Animation、Physics 等类全部派生自 ComponentBase；无论用 Java、C# 还是 C/C++，自己动手写 component 基类时一定要加一个 tick 函数。

```text
ComponentBase   <- 统一组件的基础行为接口，必含 tick 函数
   ▲
   ├── Transform
   ├── Model
   ├── Motor
   ├── Health
   └── ...（AI / Physics / Animation 等）
```

       * 换组件即换物体：把 AI 组件换成 ATTACK AI 模块，再加一个帮助瞄准、索敌的战斗系统组件——两个组件一换，侦察无人机就变成察打一体机。

   * **引擎要符合人的直觉**

       * 游戏引擎的架构本质是生产力工具，不是技术炫耀体：第一要让开发者好维护、好理解，同时要交给大量艺术家和设计师使用，把世界的组织与各种交互做成符合他们天然直觉的样子。

   * **Unreal 概念辨析**

       * Unreal 里所有东西都派生自 UObject，但它不是 GO——更像是高级语言里 C# 的 object，负责任何对象的生命周期管理（创建、内存释放），也就是 GC 需要的那个句柄（handle）；Unity 里的 Object 也是这个概念。

       * Unreal 里更像 GO 概念的，是 Actor 这一族的东西。

       * > **易错点** ⚠️：`UObject` ≠ GO。`UObject`（以及 Unity 的 `Object`）相当于语言层面的根对象，管生命周期与 GC 句柄；表达「游戏世界里的一个东西」，在 Unreal 里对应 `Actor` 一族。

   * **组件模式的代价**

       * 效率：最基础的实现每次都要找到那个组件、再找到它的接口去访问，肯定没有直接写一个 class 高——ECS 把同样的组件、全部数据放到一起快速处理，就是为了避免切换成本特别高的问题。

       * 通讯：一个组件并不知道同一个 GO 里还有多少组件——AI 组件要根据血量决定攻防倾向，就得不停 query「这个 GO 挂了血量组件吗？现在血量多少？」，这种查询在高频率调用下对效率影响非常大，是组件模式自身带来的巨大弊端。

       * 凡事有利都有弊，这是引擎愿意付出的代价。

## tick 机制

   * **tick**

       * > **定义**：引擎最核心的函数——每隔 $\frac{1}{30}$ 秒让整个世界往前走一步，如同真实世界里的普朗克时间。

       * 传导方式：把每个 GO 的每个组件依次 tick 一遍。坦克示例：Motor 知道速度每秒 10 米，$\frac{1}{30}$ 秒约 0.03 秒，前移 0.3 米（30 厘米）；动画组件跟着卷履带、转主炮；战斗系统 tick 开火。

       * 真实引擎比这更复杂，还有 pre-tick、post-tick，用来解决各种时序性问题。

   * **按对象 tick 与按系统 tick**

       * 按对象 tick：每个 GO 把自己的组件依次 tick 一遍——非常符合直觉，架构中依然存在。

       * 按系统 tick：把每种组件作为一个系统，横扫场景里所有 GO——先 tick 所有 Motor 让一切位移到位，再 tick collision（物理碰撞检测与位移阻挡检测），然后再做动画——听上去反直觉，现代引擎为追求效率逐渐转向它。

| | 按对象 tick | 按系统 tick |
| :--- | :--- | :--- |
| 做法 | 每个 GO 把自己的组件依次 tick 一遍 | 每种组件作为一个系统，横扫场景里所有 GO |
| 直觉 | 非常符合直觉 | 听上去反直觉 |
| 走势 | 架构中依然存在 | 现代引擎为追求效率逐渐转向 |

       * 高效的原因是流水线（pipeline）：汉堡店五个工人各人独立烤面包、烤牛肉、洗蔬菜、放 butter 再合成汉堡，效率显然不高；有人专门烤面包、有人专门烤牛肉、有人专门洗菜，配合好一起合成，效率最高。

       * 计算机上的额外好处：把所有 component 的数据尽可能集中在一起，一次处理就是一次批处理——图灵机的纸带上，把同样的数据放到一起、读写一起做，架构效率最高。

       * 一句话记忆：造一个流水线，流水线可以批处理，所以效率高。ECS、DOTS 这类架构属于更高级的话题。

   * **tick 超时的处理**

       * 前提：假设每 30ms tick 一次，但有时要算的东西太多一个 tick 算不完，下次再来时可能已过 40ms、60ms。

       * 步长补偿：每个 tick 把步长传进去，位移这类东西按实际经过的时间做补偿，人不太会注意得到。

       * 跳帧：直接跳过一个 tick、一次 tick 两帧——比较危险。

       * 延迟处理（deferred processing）：爆炸一下子产生几十上百个物体受击事件处理不过来时，不放在一帧里全处理，而是分批——一批处理 20 个、差五帧处理完；五帧在人的视觉里约 0.2 秒，有时大家能接受。

       * 实际上一般还是会去优化整个引擎和游戏的设计。

   * **逻辑线程与渲染线程**

       * 引擎有「两大神兽」：tick logic tick 各组件的逻辑部分；tick render 做各种数据准备等 render specific 的工作——粒子系统的 tick 就在渲染线程里进行。

       * 现代引擎架构里都不只是一个线程做渲染，可能是很多个线程在做渲染和数据准备。

       * 最简单的同步模型：tick logic 产生的结果，由排在其后的 tick render 使用；引擎做得不好时，逻辑先跑了一帧、看到的画面就延迟一帧。

```text
手柄输入 → tick logic → tick render → framebuffer 交换 → 眼睛看到画面
```

       * 这条链上每一步都可能吃掉延迟：早期 Xbox、PlayStation 手柄从操作到眼睛看见可达 100 多毫秒，即三到四帧的 lag——靠大量设计 trick 才让打击感显得很实时。

       * 一般 tick logic 会比 tick render 稍微早一点，且两者分成两个不同的线程。

## 事件机制

   * **hot code（硬编码）**

       * > **定义**：在事件逻辑里直接查询周边对象并逐类写死处理的粗暴写法——炮弹爆炸时挨个判断：是人减血、是飞机减血、是坦克减血、是石头完全没有影响。

       * 背景细节：GO 开炮时它的 component 可以再 spawn 生成一个新 GO——炮弹；炮弹每个 tick 往前跑，某个 tick 发现上一 tick 位置与即将到达位置的连线与地面有交点，就知道「我要炸了」。

       * 最早期的游戏引擎有时真的这么写，初学也常这么写；但游戏世界越来越复杂，hot code 就不 work 了。

   * **事件机制（event）**

       * > **定义**：GO 之间不直接敲门喊话，而是给方圆内每家「门口的邮箱」投一封事件信；收信方在下个 tick 开箱读信，按自己组件的逻辑决定反应。

       * 信箱版炮弹流程：爆炸后给方圆 20 米内每家邮箱投一封 damage 信——不认识邻居、也不需要知道邻居是什么；下一个 tick 小兵的 Health 组件一查只有 70 血、信上要扣 100，「那好吧，我只能死给你看了」。

       * 价值是解耦合（decoupling）：GO 间通讯原本需要知道所有可能相关的对象类型、每个 GO 里 component 的类型，太复杂；统一成 event 机制后，发出一个 event 给对应的 GO 让它处理即可，各 GO 与 component 之间的逻辑就解耦合了。

       * 这是现代游戏引擎最重要的机制之一，基本所有商业级引擎都要做这样的机制。

   * **商业引擎的事件实现**

       * Unity：注册一个 message、注册一个 event 再 send，用字符串标识（如 damage event）；物体的 Health 组件收到后回调函数被激活去扣血——字符串匹配（string match）就可以了。

       * Unreal：用 C++ native code 实现，需要一套比较复杂的反射机制——注册 event 时声明当它发生时每个 component 的哪个函数被回调；注册后蓝图里会增加这种消息类型：炸弹蓝图写「撞到地面发出 damage」，另一个东西的 Health 蓝图收到后可加一条「收到 damage 怎么处理」。

       * 本质是让接口与消息可不断扩张定义：做游戏引擎最核心的事情之一，就是做一个可扩展的消息系统——让开发者不断定制和自己玩法相关的消息类型，再定制组件对这些事件的处理逻辑。

   * **事件机制的调试**

       * Unreal 的蓝图可以逐帧看它的走动，看到这个时候一个 GO 发出了多少事件；有的游戏锁定一个 GO，把它发出去、收到的所有消息全部在头顶上顶出来。

       * 黑科技是 log：一帧里真的有很多很多条事件，在 log 文件里找那一刻发生了什么，往往是最有效的 debug 机制。

       * 可视化 debug：游戏里开 debug 模式把这一帧 pose 住，把所有消息及内容显示到 3D 空间里，判断是消息没发出来、还是发出来了 component 没有处理——设计师等非技术背景同学也要 debug 组件行为，这类模式现在非常多。

       * > **注意**：消息的发送、接收、分发本身如果做得不好，也会成为引擎的效率瓶颈——引擎最核心的挑战是一切都要实时。

## 绑定、时序与确定性

   * **物体绑定**

       * 开车时人是 GO、车本身也是 GO，那一刻人被绑到车上：车在动，人的位移被车锁定，两者要联动。

       * 一般要求父节点先 tick、挂在上面的东西在后面 tick：自己被 tick 时先问「我的车在哪里」——车已前移 30 厘米，那我也前移 30 厘米再做相应动作；挂上来的东西更多时，tick 顺序就会变得相对复杂。

       * 现代 tick 很多时候分散到很多 CPU 上并行执行，并行执行的时序非常重要。

   * **直接投递的逻辑悖论**

       * 分手信公案：兴冲冲写好分手信去投递，却撞见女友正从寝室出来、手上拿着另外一封信——谁先谁后、谁耍赖谁说不清；GO 直接彼此写信会产生很多逻辑上的混乱（ambiguity），这种混乱很多时候注意不到，但对游戏影响非常大。

   * **邮局：统一收、统一发**

       * 所有人不许再直接投递信件：信先寄到邮局；邮局在统一时间把信发到每一个人，每人都是统一的「第二天」收到；收到后决定下一步，新写的信同样只能当天寄邮局、第二天早上才到——时序严格一致。

       * 所有 GO 在同一时刻收到同一批信，谁也不比谁早，时序就锁死了。

   * **确定性（deterministic）**

       * > **定义**：一样的输入一定跑出一样的结果，与执行多少次、何时执行无关。

       * 精彩回放的实现：不把游戏过程、整个状态全部录下来（录像文件会大到存不下来），只录每一个玩家的输入，把游戏重新跑一遍——跑出来的效果与刚才打的时候一模一样；回放本身是引擎提供的一种核心能力。

       * 所有物体依次执行时，顺序定好了结果就确定；一旦并行到不同的核、多线程运行，结果就会完全不一样。

   * **循环依赖与时序陷阱**

```text
Motor：移动速度 5 米/秒 → 状态从走路变成跑步
  ↓
Animation：走路动画换成跑酷动画
  ↓
Physics：腿迈出去，碰撞体跟着伸出一下 → 可能撞到什么
  ↓
状态变化又反过来影响位置 →（回到 Motor）
```

       * 组件之间常出现这种绕一圈又回到起点的依赖，是组件系统里最常见的循环依赖。

       * 引擎写得不够好时，经常发现某个行为有大概一到两帧的 lag（延迟），很多时候就是时序问题导致的。

       * > **注意**：每个组件发消息后，对象在哪一帧收到（当前帧还是下一帧）？收到后是当场做动作还是等？这些对游戏核心逻辑的影响非常非常大，是自研引擎时最要注意的精妙之处。

   * **物理与动画互相影响**

       * 受击表现的演进：最早直接切布娃娃系统（ragdoll），整个人像没有骨头一样被打飞——物理真实但看着假；动画师再设计很酷炫的受击动画，物理和动画就彼此影响上了。

       * 主流做法是插值：受击刚开始先切动画的表现；越到后来，把动画的位移（肩膀被打得往后靠、手伸长）作为物理的初始输入让物理再去模拟，越来越多交给物理——倒地姿势既有设计感又物理真实，最后手脚姿势随机、真实。

## 场景管理

   * **UID 与 position**

       * 每个 GO 一般有一个唯一的编号 UID（unique id），呼应资源管理里的 GUID（全球唯一标识）——像家里的门牌号；再加空间位置 position——像经纬度；两样齐了就可以进行场景管理。

       * 规模量级：单机游戏一般有几百个活跃的 GO；很多游戏里可能到几千甚至上万个。

   * **N 平方挑战**

       * 最简单的管理是不管理：爆炸时把场景里所有 GO 全部发一遍消息，或查询每个 GO 的位置、判断到爆心距离是否小于爆炸半径——做小游戏完全没有问题。

       * 每个物体都可能和其他物体互动，每次互动都和另外所有物体问一遍就是 $N \times (N-1) \approx N^2$；1 万个物体即约 $10^8$（一个亿），对计算机是巨大负担——尤其数据分散在内存各处时效率非常低。

   * **均匀格子：分而治之（divide and conquer）**

       * 把世界划成均匀的格子，相当于每个格子有门牌号，事件发生时只找临近的格子；方法简单，但在很多场景里真实在用——只要场景不是特别大。

       * 唯一会出问题的地方：场景里物体分布不够均匀。3A 主机大作看似广阔，玩家能走的地方非常受限——行话叫 trench（战壕）：设计师给玩家挖了很多条战壕，沿战壕的东西放得非常详细密集，战壕外非常稀疏；对这么大的世界均匀打格子，又慢又浪费。

   * **层级结构（hierarchy）**

       * 像行政区划管理空间：世界分成国家、国家分成行省、行省分成城市、城市分成街区、街区再分成街道；事件发生时知道是北京海淀区某条大街上的事，只需在那个小区域里找。

       * 四叉树：根据地图上 GO 的分布以空间四分的方式不断划分——区域里物体足够少（只剩一两个）就不再划分，物体很多就不停划分，形成树状结构；查找时只需向上（parent 节点）、向下（子节点）或找 sibling（兄弟节点）。

   * **空间划分流派**

       * BSP：最简单的二叉树流派，把世界一刀一刀分掉；划分有时做得更精致——比如沿着墙去分。

       * 八叉树（octree）：对空间不断细分的经典方法。

       * 包围盒层级树（Bounding Volume Hierarchy，BVH）：每个物体有一个小小的包围盒，从小往大慢慢合并；最常见用途是视锥裁剪——用包围盒快速把大量看不见的东西全部扔掉；打一条子弹、一个弹道时也需要它快速定位。

       * 按产品选择：2D 平台跳跃（platformer）游戏可能不需要这么复杂的场景管理；COD、Quake 这样的游戏一定要花心思仔细设计场景管理，尽量节约计算资源。

   * **动态物体的划分更新**

       * 最笨的做法是每一帧把空间中 1000 个物体全部重新生成一次二叉树、八叉树——效率特别低；BVH、BSP、octree 都有共同的问题：如何更新——节点消失了要合并、插入后要分裂、移动了要考虑怎么表达。

       * 选择原则：选更新起来比较轻量的结构。

       * 室内静态世界（只有人和小怪走来走去）：把世界做静态划分就行，用 BSP tree 或 PVS 这类技术，甚至设置一些窗口让区域能看到彼此。

       * 类战地的 open world：BSP 更新起来效果不好、效率也不高，用更简单的 BVH 更好——包围盒做成一个个球时，球合并后半径变得更大，更新的代价非常低；场景中所有东西都在动时推荐 BVH。

       * 做引擎建议支持两三种以上比较经典的空间划分算法，交给游戏产品按自己的需求选择。

## 图形学理论与游戏渲染的分野

   * **绘制系统的地位**

       * 很多人一提游戏引擎就问「是不是就是绘制引擎」——引擎不止绘制，但绘制确实是非常重要的一派，从技术难度到专业壁垒都是最高的一趴。

       * 不需要绘制系统的游戏真实存在：文字游戏 MUD——打字告诉它「你进入了一个房间，房间里有一张桌子」；但今天绝大部分游戏都需要绘制。

   * **四道分野**

| 维度 | 计算机图形学理论 | 游戏引擎的绘制系统 |
| :--- | :--- | :--- |
| 问题边界 | 一次解决一个明确问题：绘制一两个物体、实现一种特定效果（透明物体 translucency、折射反射、水面、3S 半透明材质） | 成千上万物体、形式各异（水体、植被、角色、云），毛发、皮肤、水体、植被、地面材质算法各是各的一套，再叠加大量的后处理与光照运算——everything into one container |
| 硬件假设 | 关注算法与数学的正确性，不关注硬件怎么实现 | 必须深度适配当代真实硬件（PC、主机、Switch） |
| 时间预算 | 实时、交互、离线皆可，几天一帧也行 | 一切装进 $\frac{1}{30}$ 秒（约 33 毫秒）的死预算，帧率不许掉 |
| 资源占用 | 可以吃满计算资源 | 显卡可吃满，CPU 只让出 10%~20% |

       * 图形学侧的帧率口径（早年的同学标准）：做到 30 帧以上算 real-time；只能算到十帧左右叫 interactive，算有交互性；不能实时但画面极好、几个小时甚至几天渲染一帧，是电影级 CG 离线渲染；数据大到内存装不下、要很多台机器离散存储，叫 out-of-core rendering。

       * 图形学里还有完全按光学理论给出的辐射度算法（radiosity）：计算机跑个几天，算出一张非常漂亮的图。

   * **游戏侧的死预算**

       * 场景千变万化——一会儿在密闭小房间里几个怪物围着打，突然跑到楼顶看到整个城市——无论看到的大还是小、细腻还是粗糙，都要保证在 $\frac{1}{30}$ 秒内跑完；帧率一掉，大家就觉得游戏不好玩。

       * 要求还在加码：打 FPS 的电竞要求 60 帧、电竞屏已要求到 120 帧左右；画幅从 1080P 高清到 4K、即将 8K——给的时间越来越小、对画面的要求越来越高，绘制算法必须装进非常固定的预算，绝对不能超。

       * CPU 吃满了，游戏逻辑、玩法、网络就跑不起来——显卡的算力可以百分之百吃掉，CPU 只能吃掉 10% 到 20%，剩下的大部分让给其他 gameplay 系统。

       * 引擎侧的纪律是 profiling：现在一般游戏引擎里 profiling 都是全自动的，每天自动跑，超预算的系统会被警告「赶快改回去，否则这个游戏就不许发布」。

       * 这也是做引擎的人跟设计师、美术天天「打架」的地方：效果弄得太复杂就会影响游戏性。

   * **实践科学**

       * 绘制系统不是理论模型，而是工程实践过、经过行业近 30 年迭代优化（heavily optimized）的软件系统——一门实践科学。

       * 它代表最前沿的制造技术、计算机体系结构技术、引擎与渲染技术，随硬件与产业环境快速迭代；学它更该问的是「工程上为什么这么做、为什么这么多最优秀的人最后发现这么做是最优的」。

   * **渲染管线要不要自写**

       * 渲染是工业化的问题：随着时间的积累，在同样的技术水平下，大家最后的解决方案大同小异。

       * 建议：多学习、多请教、关注行业最前沿，然后选择最主流的方案构建管线；自己写可以，但架构尽可能符合整个行业和工业的标准——特别标新立异、跟别人都不一样的方案，维护和发展起来的挑战非常大。

   * **图形代码的调试**

       * 图形程序员的 debug 难度仅次于服务器端：大量计算全在 GPU 里，子弹打出去了根本不知道里面发生了什么，最后一个结果才出来。

       * 好在显卡 driver 与各厂商提供了很多 debug 工具：每个像素、每一个 draw call 都可以看到数值的变化，shader 也可以单步 debug。

       * 方法论：把算法拆成很多小步，每一小步实现、验证、反复验证，证明没问题再往上加一步；千万不要看到算法厉害就一次性全写完——到时候出了问题连死在哪都不知道。

## 渲染的基本运算与纹理采样

   * **渲染的骨架**

       * 空间中很多顶点连成一个个的面 → 经投影矩阵投到屏幕上 → 光栅化（rasterization）把三角形拆散成一个个小像素 → 在每个小像素上找到对应材质与纹理、考虑光照与花纹渲染出颜色 → 输出结果。

       * 规模量级：上百万的顶点和三角形、几千万以上的像素、10 亿级的 ALU 与 texture 运算。

       * 绘制做的就是「躲在像素之后的事情」——看到的那幅壮丽画面，是现代计算机一个像素一个像素堆起来的。

   * **着色的三种运算**

       * 常量的访问：屏幕的长宽、有多少个像素这类常数，每个像素都要访问。

       * 加减乘除的数学运算：算 Phong 模型时，知道法线在哪里、光线在哪里、眼睛在哪里，就能算出这个光有百分之多少会被衰减掉。

       * 纹理的访问：把贴图上对应点的颜色取出来放到一起——这几种运算像炒菜的原料，合起来就能得到想要的结果。

   * **纹理采样：被低估的昂贵操作**

       * 问题来源：砖墙离得近时屏幕上一个像素对应纹理上一个像素；离得非常远时屏幕一个小像素在纹理上隔了很多很多像素——不滤波（专业说法叫低频滤波），砖墙由近及远移动时画面会一直抖动，即走样；图形设置里的抗锯齿（防走样）是另一类重要的反走样方法。

       * 做法：每张贴图会存很多很多层；屏幕上一个小像素去取纹理时，位置不一定正好落在某个纹素上，要取四个点做插值，还要在两层的分辨率层级上各取一次。

       * 一道数学题的答案：一次纹理采样要采样 8 个纹素的数据、做 7 次插值——两层各取 4 个点，每层做 3 次双线性插值，两层结果之间再做 1 次，$3 + 3 + 1 = 7$。

       * 只想取一个最简单的颜色，计算机要做这么多工作——纹理采样因此成为绘制中很重要的运算，也是显卡里要有专门处理它的硬件单元的原因。

## GPU 硬件架构

   * **SIMD（Single Instruction, Multiple Data，单指令多数据）**

       * > **定义**：一条指令同时对多个数据做运算——四维向量做一次加法指令，XYZW 四个坐标同时在运算。

       * 现代 CPU 已广泛使用：C++ 代码里的 SSE 扩展宏就是在调用 SIMD 指令；渲染中大量的矩阵运算、坐标变换正是 SIMD 的主场。

   * **SIMT（Single Instruction, Multiple Threads，单指令多线程）**

       * > **定义**：把计算内核做得很小但数量极多，一条指令下去，在非常多个核上同时做同样的指令操作。

       * 算力直觉账：SIMD 一次算 4 个数，100 个核一起跑就是在 SIMD 乘 4 的基础上再乘 100，放大 400 倍；N 卡放的就是无数的 CUDA 核——现代显卡本质上是一个大蜂巢。

       * 编程要领：做所有绘制运算时，尽可能用同样的代码让大家一起跑、每个人分别访问自己的数据，代码在显卡上才能跑得远快于 CPU——图形程序员最重要的概念。

   * **GPU 与 CPU 的算力差距**

       * 度量是 FLOPS（一秒钟能完成多少次浮点计算）：现代显卡一般能达到 10 个以上 TFLOPS（如 Xbox、PS5），而现在的 CPU 很难达到 1 TFLOP——差距超过一个数量级。

       * 本质：CPU 很老实，一个人闷头处理所有的事情；显卡招了很多能力不强的小伙伴协作，算力就非常快。

   * **费米（Fermi）架构**

       * 网上的架构图密密麻麻，其实结构是重复的；费米大约是十年前的 N 卡架构（后来有安培 Ampere、最新的 40 系用更新的架构），技术原理都差不多。

```text
一块 GPU 显卡
└── GPC（Graphics Processing Cluster，图形处理集群）× 多组
    └── SM（Stream Multiprocessor，流式多处理器）× 若干
        ├── CUDA 核（很多小核）—— 干大量的数学运算
        ├── Texture Unit —— 专门处理昂贵的纹理采样
        ├── SFU —— 专门算 sin/cos 这类复杂函数
        ├── Shared Memory —— 核与核之间交换数据的共享内存
        └── 新架构的 SM 里还会塞进：Tensor Core、RT Core
```

       * SM 里两件专门的硬件：Texture Unit 处理非常「废」的纹理采样；SFU 处理复杂函数——显卡跑加减乘除没有太大问题，算 sin、cos 这类三角函数速度就比较慢。

       * 一个 SM 里的几十个核不仅并行处理工作，还可以通过 shared memory 互相交换情报、形成协作体——核与核之间能交换数据，就能做非常酷炫的运算；现代 GPU 最重要的架构，几乎所有的运算都跑在这样的架构上。

       * 最新的安培架构 SM 里还塞了 Tensor Core（著名的人工智能核心）与 RT Core（光追，里面有专门的核心支持）。

   * **硬件在变，架构跟着变**

       * DX11 时代（约十年前）：更细分的曲面（tessellation）、更灵活的 shader、更通用的计算 shader；到今天出现了更容易处理的 mesh shader 这类新结构。

       * 从 PC 走向主机：主机是 UMA（统一内存架构），内存全部共享，引擎架构又不一样。

       * 手游移动端要考虑功耗与处理芯片的能力——访问数据是最昂贵的——因此发展出 Tile-Based Rendering（分块渲染）：手机上 1080P 甚至更高清的 4K 画面，实际是一小块一小块渲染出来的。

       * 所有引擎架构都和硬件架构息息相关：学渲染前先了解显卡怎么工作，对渲染引擎算法的理解会更深；艺术家掌握这些概念也有好处——设计玩法时知道硬件在什么地方会卡，不会把场景做得无限复杂。

## 数据搬运与缓存

   * **冯·诺依曼架构的代价**

       * 核心是把计算和数据分开，好处是硬件设计变得非常简单；最大问题是每一个计算可能都需要去找数据，而找数据特别慢，数据在不同的计算单元之间搬来搬去也非常慢。

       * 经典 PC 架构（南桥北桥）里，北桥一边放 CPU、另一边放显卡，CPU 那边装主内存——把主内存的数据上传到显卡显存，速度非常慢。

   * **readback 是要避开的事**

       * 设想一个计算：CPU 准备好交给显卡算 → 显卡算好把数据读回 → CPU 基于结果做判断 → 再告诉显卡怎么绘制。

```text
CPU 准备数据 → 上传到显存 → GPU 计算 → 读回 CPU → CPU 判断 → 再指挥 GPU
              （这一个来回，可能吃掉半帧到一帧的延迟）
```

       * 现代引擎架构中绘制和逻辑一般是不同步的；一个绘制运算若要等来回 readback，很可能导致半帧到一帧的 latency（延迟），表现就是逻辑和画面不同步。

       * > **结论**：游戏引擎绘制系统的架构原则是尽可能把数据单向传输——CPU 送到显卡就完事，尽可能不要从显卡里读数据。

   * **缓存：性能的隐形天花板**

       * CPU 上做一次加减乘除可能一个 clock 就做完；但若数据不在缓存、在内存上——内存已经算非常快了——CPU 实际要等 100 多个时钟周期，这段时间本来可以做几十上百个运算。

       * cache hit：每次计算时数据恰好都在缓存上；cache miss：数据不在缓存，就要等很久。「数据一定要放在一起」其实就是在为 cache 做准备；有些数据过大之后，也会导致 cache 很难被利用好。

   * **瓶颈黑话：bound**

       * ALU bound：数学计算太多，纹理采样什么都来得及，就都在等数学运算的结果。

       * memory/bandwidth bound：所有运算都算完了，但把结果写到缓存的速度太慢，大家一直堵在那等。

       * 现代计算机整个就是一条流水线：只要有一个环节没平衡好、卡住了，其他东西优化得再快也会被它卡住。

## Renderable：可绘制物

   * **Renderable（可绘制物）**

       * > **定义**：绘制系统的核心数据对象——拿到了这个 renderable 物体，就能把它绘制出来。

       * 逻辑上表达的游戏对象（它是一辆车、可以有血量、有各种行为）只是逻辑的描述，其实是绘制不了的；逻辑上表达的游戏对象和真实可以绘制的东西，是两个东西。

       * 载体是网格组件：有引擎叫 mesh component，有引擎叫 skin mesh component（假设 mesh 是有骨骼的、可以一直变形，做角色时能动来动去）；名字不同，底层理念大同小异。

   * **Renderable 的构成**

       * mesh：几何形体（头盔、很帅的枪）；每个 mesh 上有各种各样的材质（像布、像金属、像皮肤）；材质上有很多花纹即各种 texture；再叠上 normal 表达 mesh 没办法表达的更细的细节——这些是 renderable 最简单的 building block，现代引擎的 renderable 比这更复杂。

   * **从自身坐标到屏幕**

```text
自身坐标系 ──模型矩阵──▶ 世界坐标系 ──视图矩阵──▶ 相机坐标系 ──正交/透视投影──▶ 屏幕坐标系
```

       * 每个物体先乘模型矩阵（model matrix）从自身坐标系到世界坐标系；再乘视图矩阵（view matrix）到相机坐标系；最后经正交或透视投影变成屏幕坐标系里的东西。

       * 绘制提交：把 vertex buffer、index buffer（mesh 的东西）提交上去，再把材质参数、一个个 texture 提交给显卡，最后给一小段代码——「显卡，你看到的每一个顶点、每一个像素就这么执行」——显卡跑完，物体就真的被绘制出来了。

## 网格数据

   * **mesh primitive**

       * > **定义**：引擎里 mesh 的基础表达——很多顶点，顶点上带位置、法向朝向、UV 及其他各种属性；每三个顶点放在一起变成一个三角形，三角形放在一起形成物体的外观与形状。

   * **vertex data + index data**

       * 把所有顶点放在一起，三角形不再把顶点数据存一遍、只存顶点的索引值。

       * 为什么省：打开真实模型会发现很多顶点被很多三角形共用——很多模型顶点数量大概只有三角形数量的一半，一个三角形里又有三个顶点，用 index 理论上存储量可以节约六倍以上；顶点数据很贵：空间位置要存三个 float，法向不必老老实实存三个 float，还有一大堆 UV。

   * **triangle strip（三角形带）**

       * 一笔画式表达：顶点编号 01234567 时，012 是一个三角形、123 是一个、234 又是一个——不用单独存储 index buffer 也能表达一个 mesh。

       * 附加好处：每个三角形绘制时对顶点数据的访问都是顺序的，对缓存最 friendly——早期引擎尽可能把模型变成 triangle strip 就是这个道理；现在游戏一般比较强大，不太特别强调这件事了。

   * **顶点法向必须单独存**

       * 每个三角形可以算出它的朝向，用邻近几个三角形 average（平均）出顶点朝向，大部分情况下是对的。

       * 但表面有硬表面、有一条折线时，两个顶点的位置重合、法向却完全不一样——例子是正方体。

       * > **易错点** ⚠️：定义顶点数据时，一定要给每个顶点单独定义它的法向方向，不要想当然地用三角形平均出来。

## 材质、纹理与着色器

   * **材质系统的演进**

       * 从图形学最经典的 Phong 模型（那时大家讨论塑料、金属、石头这种非金属的反射各是什么样子），到基于物理的渲染（physics based rendering，PBR），再到半透明 3S 材质这类特殊效果——行业积累了一大批优秀的材质模型。

       * 物理材质（physics material）是另一码事：表达摩擦系数、撞上去之后的弹性反弹力；它与视觉材质容易混到一起，但现代引擎中绘制系统里定义的只是视觉材质，物理材质单独去定义。

   * **纹理决定材质观感**

       * 觉得一个材质像金属还是像生锈的非金属表面，很多时候不是由材质的参数决定，而是由它的纹理决定：区分光滑的金属表面与生锈表面，靠的就是 roughness（粗糙度）这样的纹理。

   * **shader（着色器）：既是源码又是数据**

       * 引擎里一般分两类东西：数据/资产（asset）与源码（source code）——艺术家设计师碰数据，程序员碰源码；shader 首先肯定是源码（用大量代码写材质表达），但在引擎中又会当成数据来处理。

       * 处理方式：绘制每个东西时，除了告诉显卡「画一个球、贴虎皮花纹」，还要给它一小段代码——一个 block、一段编译好的 shader 二进制数据块——「你就用这个程序，把这些元素合到一起，绘制成我要的东西」。

       * 形态变化：从固定管线时代的著名材质模型，到现代引擎的 shader graph——艺术家像搭积木一样把各种元素按自己的方法组合，实际生成一个个不同的 shader 代码，编译成数据后与 mesh 存储在一起，形成多样的游戏世界；shader 代码也是 renderable 的一种关键数据。

## Submesh、资源池与实例

   * **submesh（子网格）**

       * > **定义**：把 GO 的一个 mesh 按身上用的材质不同切分出的绘制单元，每个 submesh 对应自己的材质、纹理与 shader code。

       * 存储方式：顶点、三角形全部放到一个大的 buffer 里；每个 submesh 只存一个 offset——index buffer 从哪个点到哪个点；绘制时就知道从起点到端点之间这些三角形该设什么材质、什么 shader、什么 texture。虚幻引擎等很多引擎都有类似结构，名字可能不一样。

       * 引擎绘制核心要解决的就是 mesh 模型、材质这些数据之间的关系——最经典的 mesh 与 submesh 就是很好的学习样本；最前沿已有 cluster-based pipeline 这样的变化。

   * **资源池（pool）**

       * 动机：每个物体都存完整一套（mesh、submesh、材质、shader、texture）数据量非常大，而仔细观察会发现很多 mesh、有些贴图、甚至 shader 是一样的。

       * 做法：所有 mesh 放一起成 mesh pool；所有 texture 放一起（一个人身上的很多纹理在其他人身上可能共用）；shader 尤其要池化——都用 PBR 时 shader 长得一模一样，1000 个这样的对象只需存一份。

       * 绘制场景里各种角色、小兵时，只是通过一个指引指向各自所需的材质、mesh——存储空间最小的经典架构。

       * 自研引擎记两点：第一，通过 submesh 把每个 mesh 按材质切分；第二，切分后相同材质归类到一起、相同纹理归类到一起入大 pool，相同 mesh 放一起入大库。

   * **实例化（instancing）：定义与实例**

       * > **定义**：前面所有数据都是「定义」（object definition）——比如定义一个小兵的 renderable 长什么样；当屏幕上画了几千个小兵时，每个小兵只是那份定义数据的一个实例（object instance）。

       * 这对概念在引擎设计中从头贯彻到尾——不只绘制这一趴，做游戏逻辑、场景物的管理处处都是；做引擎必须把「这份数据是我的定义」「那份数据是我的实例」区分得非常清楚。

       * 用定义创建出实例之后，还可以再给实例加一点点的变化。

       * GO 就是活教材：资产数据里「一个方块放在哪、长多大、什么样子」是定义；关卡里那堵墙可以横着放、竖着放、放很多个——每一堵墙就是一个 instance。

       * 音效同理：「子弹打中墙的声音」是定义；拿加特林对着墙一扫，一瞬间听到十几个子弹打中墙的声音——每一个声音都是 instance；粒子系统、地表的草与植被，全是用 instance 概念做的。

## 按材质排序与批量绘制

   * **显卡很「懒」**

       * GPU 的特点：设置了一个参数后每次去改变它都很烦——「要改我的参数了？要换贴图？要换 shader 代码？」回想 SM 结构：每次换数据，SM 里那一堆核心都要停下来等你换好再运转。

       * 关键在于：把场景按材质排序归拢后，算计算量好像跟原来一样，但交给显卡速度真的会变快——因为「换状态」这笔开销根本没记在计算量账本里。

   * **按材质排序与批量绘制**

       * 地上那一大片碎木头其实都是同一个材质——相同材质意味着相同的参数、相同的纹理；把整个场景的物体按材质排序、相同材质归拢到一起：材质只设置一次，一口气绘制这一批 sub mesh。

       * 现代图形 API 的设计取向一致（DX12、Vulkan 把 CPU 侧的状态设置专门抽象成 render state object，各家命名不太一样）：对显卡的状态设置预先做好、一次性设好、尽量不要动，然后再做一大堆绘制——材质排序归集 sub mesh 就是顺着硬件的脾气干活。

   * **GPU based batching rendering**

       * 很多子物体一模一样时，一个一个依次绘制、一遍又一遍设置 VB/IB 很浪费；用 compute shader 或其他 shader 能力，一次设置好 VB/IB，再放进一列每个物体的位移数据——一个 draw call（一次绘制指令）能把几百个、上千个东西全部创建出来。

       * 最有用的场景：画大量看起来都差不多的树、草，一下铺到几百米开外甚至上公里远。

       * > **结论**：现代游戏引擎架构中，会尽可能把绘制运算交给 GPU 来做，而不是用 CPU。

   * **GPU driven**

       * 这个趋势的大词叫 GPU driven：把很多原来在 CPU 上做的复杂运算搬到显卡上，利用 GPU 十倍以上的高速处理性能——例如现在很多动画系统全部移到显卡上做了，是 GPU 帮 CPU 分担负担的重要发展方式。

## 可见性裁剪

   * **Visibility Culling（可见性裁剪）**

       * > **定义**：在绘制之前把看不见的东西剔除掉——游戏绘制系统最基础的底层系统。

       * 动机：视锥（view frustum）是一个锥形的东西，任何时候看这个世界，其他部分其实是看不见的；相机移动时七八成以上的空间看不见——里面的物体、粒子效果、地形都不需要绘制。

       * 最基础思想：给定四棱锥形的 view frustum，做最简单的数学运算就能判断一个包围盒是否在视锥里面；但要做得快、做得好，里面有一整套学问。

       * 核心思想：通过运算把要绘制的东西减到越少越好。优化的大神级答复也叫 do nothing——通过算法让计算机尽可能少地做事情，效率一定是最高的。

   ### 包围盒

   * **包围盒（bounding volume）**

       * > **定义**：用一个简单形状大致表征复杂物体「占领的地方」，供「这时候子弹能不能打中你」「这时候能不能看见你」这类判断使用——一个角色几万个面，不可能逐一计算。

       * 不只是在绘制，包括 AI 逻辑、物理都要用到它，是很多计算的基础。

| 包围盒 | 构造 | 特点与代价 |
| :--- | :--- | :--- |
| 包围球（Bounding Sphere） | 把物体装进一个最紧的球 | 最朴素的一种 |
| 轴对齐包围盒（AABB，Axis-Aligned Bounding Box） | 各面都与游戏世界的 XYZ 轴对齐，只要存两个端点就能构建 | 更常用，计算效率也是最高的 |
| 有向包围盒（OBB，Object Oriented Bounding Box） | 盒子贴着物体自身的方向走 | 比 AABB 更贴身 |
| 凸包（Convex Hull） | 把物体的外表面绷一层凸壳 | 最贴身也最贵，很多物理运算中特别常用 |

       * 依次拿包围盒去跟视锥算就能做 culling，但效率一定不高——这就轮到空间划分。

   ### BVH

   * **包围盒层级树（Bounding Volume Hierarchy，BVH）**

       * > **定义**：把包围盒像树状结构一层层往上摞，culling 时从上到下一层层询问。

       * 询问逻辑：几十个物体聚成一个节点，先问「你这个最大的包围盒是不是能看得见」——看不见，这几十个物体就不用画了；看得见，继续问「你里面有没有更精细的划分」，一直问到叶子，就知道哪些物体可见——计算复杂度下降非常非常多。

       * 为什么用得特别多：这个算法非常简单、也不是最高效，但现在的游戏里「动的东西」很多——BVH 树构建好之后，节点发生变动时重建的成本要尽可能低，这一点它优势明显；culling 速度非常快但每次建树花的时间最久就亏了，动态物体特别多的场景 BVH 是很自然的选择。

   ### PVS

   * **潜在可见集（Potential Visibility Set，PVS）**

       * > **定义**：预先算好「站在每个房间里最多能看见哪几个房间」，渲染时只画潜在可见集合内的房间与物体。

       * 出身：游戏引擎行业的教父约翰·卡马克（John Carmack）做早期 FPS（记不清是 Doom 还是 Quake）时的想法——机器性能那么差，在一个小房间里打来打去却把那么多房间的东西都画了，很亏。

       * 做法：先用 BSP 把空间划分成一个个小格子，格子之间通过 portal 连接（门、窗那样连接两个空间的「窗口」）；站在一个房间，通过门和窗最多能看见哪几个房间是固定的——站在 7 号房间，就只渲染 6、1、2、3 这几个房间里的东西，无论房间本身还是里面的物体。

       * > **易错点** ⚠️：PVS 存的是「最多能看见」的房间集合——宁可多列、不可漏列；只有站在这个房间的任何角落都看不见的房间，才敢整个不画。

       * 现状与遗产：现在真的全面用 PVS 做裁剪的已经没有那么多了，但「把世界分成 zone、算清区域之间可见关系」的思想非常有用——3A 大作的关卡多是 linear 线性的（觉得在开放世界里，实际走的都是设定好的路线），把玩家能经过的世界分成一个个 zone，zone 之间往往有峡谷、关口甚至一道门，在每个 zone 里就知道「你能看见其他哪几个 zone」。

       * 这件事除了 visibility 还有资源加载的大好处：闯关打过 boss、通过一道门时感觉卡夹了一小会儿，就是因为换了一个 zone——这时能看见的、特别是有些远处 zone 的资源在这时候被加载上来了。

   ### GPU 裁剪与 Early-Z

   * **把裁剪直接扔给 GPU**

       * 遮挡查询（occlusion query）：把很多物体扔给显卡，显卡反馈一个位数组——一串由 0 和 1 构成的数组：1 可见、0 不可见；显卡是并行算的，非常快。

       * 视锥裁剪也一样：可以很粗暴地把包围盒直接扔过去让显卡算完，速度也不会太慢；想精细一点，还能用现在的 compute shader 在显卡上构建一个 hierarchy 的数据结构，并不是特别难。

       * > **注意**：千万不要用老的算法去限制你的想法——能在硬件上做的事情，一定在硬件上做完。

   * **early-Z**

       * 显卡很聪明的能力：一帧都是几千万以上的像素点，要绘制一个像素时发现它其实已经被别的东西挡住了，就不画了。

```text
Pass 1：只画深度，不做任何着色
        → 得到一张遮挡物的深度图（图上白 = 离我近，黑 = 离我远；
          显存里实际存的深度值跟图上黑白是反的）
Pass 2：正式绘制时，每个东西先跟这张深度图比一比
        → 被挡住的：整个绘制跳掉，甚至整个物体跳掉
```

       * 现在还有更复杂的做法，比如基于 hierarchy 的方法去做 Z 的处理，但思想大同小异：用 GPU 高速的并行化能力，以尽可能快、尽可能廉价的成本形成一群遮挡物的深度图，把能扔掉的东西尽可能扔掉。

       * 收益量级：进入一个房间时，可以发现这个世界的 99% 以上都「不见」了——只需要关注这个房间里的人和物；对非常复杂的场景特别有用。

## 纹理压缩

   * **为什么不能用照片压缩格式**

       * 照片存 JPG、PNG（BMP 基本上没有人用），压缩过的 JPG 与未压缩的 BMP 差别有时能到十倍以上；但游戏绘制的图片压缩不能用这些非常好的算法。

       * 两个原因：这些压缩算法不能随机访问——给一个 JPG 文件，突然要看坐标 7567832 的那个点，很难快速拿到；而且解码的计算复杂度非常高。

   * **block based（分块压缩）**

       * > **定义**：把图片切成一个个小块（最经典是 4×4 的小块），对每一块做压缩——整个计算机图形学里的 texture compression 都基于这个 block compression 思想。

       * 经典算法：对一个 4×4 的小色块，找颜色最鲜艳（最亮）的那个点和颜色最暗的那个点，认为块里其他所有的点都是这两个点之间的插值。

       * 为什么可以：很多图片相邻像素之间其实有一定关联度（coherence）——每个像素只要存一个「我是离最大值近、还是离最小值近」的比例关系，就可以近似表达这个小色块的颜色。

   * **两大流派**

| | DXT → BC 系列 | ASTC |
| :--- | :--- | :--- |
| 主战场 | DirectX 里最经典的压缩全家桶 | 手机上用得比较多 |
| 分块 | 经典 4×4 的小块 | 不再是严格的 4×4，可以用各种块形状 |
| 效果 | 经典可靠 | 据说压缩的效果是最好的，解压缩效率也不低 |
| 压缩时机 | 压缩、解压缩效率都非常高，生成纹理时可在 CPU 上实时（on the fly）压缩 | 压缩的运算稍微有点费，不能 on the fly 在运行中压缩 |

       * > **注意**：构建游戏引擎时，对纹理的压缩和管理是一个非常重要的模块；下载到显卡里的数据，基本上应该是压缩过的格式。

## 资产构建工艺

   * **传统建模**

       * 工具：3ds Max、Maya，以及现在越来越流行、越来越强大的 Blender；在软件里用点、线、面构建模型——最经典如做一把枪：卡线，卡住一个个关键的点，由粗到细地把模型建出来。

       * 这条路线十几年前非常火，但现在受到了巨大的冲击。

   * **雕刻（sculpting）**

       * 代表工具是大名鼎鼎的 ZBrush：像雕塑家不断把材料切削掉形成形状，而在计算机里这种雕刻行为可以更自由——不仅可以切削掉，还可以把材料往上拎出来，构建更自由的形体。

       * 基于 ZBrush 的 sculpting 素材生成方式现在也越来越火。

   * **扫描**

       * 手机上有些 app 绕着一个物体拍几张照片，就能把 3D 的东西建起来——得益于深度学习与配准（registration）算法的提升；3A 游戏行业里基于实体扫描的模型越来越多。

       * 精度量级：一个非常复杂的古代武士盔甲，通过一圈扫描能形成高精度、达到十几个亿面级别的细腻网格，远远超过人手工构建的网格。

       * 难题：首先得有这个东西——著名的故事是某大厂为了做一个游戏，先去逛淘宝把要的东西买到手、扫描过来，就可以进到游戏里了。

   * **程序化生成**

       * 通过一些算法、一些规则自动生成网格：Houdini 这样的强大工具能生成漂亮的地形网格；前沿的人工智能研发可以生成 mesh 上要的很多细节。

       * 这是游戏引擎工业未来一个很重要的发展方向——把艺术家从越来越繁琐的细节工作中解放出来，真正专注在创意上。

   * **工艺与数据**

       * 四种方法各有利弊：有的更 flexible 一点，有的难以调整一点；不同的工艺制作方法会产生不一样的数据——这些数据是计算机绘制的粮食、口粮。

## Cluster-Based Mesh 管线

   * **细节爆炸的压力**

       * 同样一个射击游戏、同样的精度，开放世界的射击游戏每一帧里看到的数据量比传统射击游戏可以大十倍以上——整整一个数量级；sculpting、3D 扫描的普及又让模型数据量越来越大，一个很简单的小雕像推近了看有无数细节。

       * 恰恰是它对现代引擎的基础架构产生了巨大冲击——游戏引擎的绘制系统不是一个静态的东西，它的技术一直在往前进步。

   * **cluster-based mesh pipeline**

       * > **定义**：把非常精细的模型分成一个个大小固定的小簇（cluster，也叫 meshlet，如 32 个或 64 个三角形）来处理的新模型表达管线。

       * 出处与趋势：基本思想很早就有了，约 2015 年前后最著名的是育碧做《刺客信条：大革命》那一作——非常华丽的建筑、非常多的细节；经过五六年的发展、硬件越来越成熟，越来越多引擎在往这条新管线转移。

       * 例：一条大概几十万面片的龙，切成很多很多个 64 面片的小块。

       * 为什么可行：现代显卡已经能够非常高效地基于数据凭空创建几何细节——不需要像传统管线那样预先把 vertex buffer、index buffer 构建好、把 mesh 传进去；给一个三角形，它可以生成无数个三角形；把每个 meshlet 的大小固定住之后，计算就是高效而一致的。

       * 为什么高效：显卡就是很多很多小盒子（SM）——大小一致的小块，恰恰是显卡处理起来最高效的形状。

   * **着色器的演进**

       * 经典管线：构建好模型材质后，有一个 VS（每个顶点的着色器）与一个 PS（每个像素的着色器）；再往前倒，最经典的连 VS、PS 都还没有。

       * 十几年前起：发现可以在显卡里创建很精细的几何，于是加入 hull shader、domain shader、geometry shader——核心目的是把放进来的三角形无限细化，生成想要的细节。

       * 最新硬件：干脆提供 mesh shader 或 amplification shader（在 OpenGL、Vulkan、DirectX 里名字都不太一样）——可以用一个算法基于数据凭空生成很多几何，而且可以根据离相机的远近选择它的精度。

   * **meshlet 级裁剪**

       * 每一个 meshlet 都有它自己的包围盒，在 GPU 上可以实时算出来：目前相机状态下这一小块东西不需要绘制了——以前裁剪只能按照物体去裁剪，现在可以把怪物手的一部分裁剪掉，效率非常非常高。

       * 虚幻引擎大名鼎鼎的 Nanite——那个「像素级的网格密度」——可以认为是这个思想又往前走了一步、更加工业化、更加成熟。

   * **它会取代经典管线吗**

       * 方向判断：硬件不可能越来越简单，一定会越来越复杂、功能越来越强大；mesh shader 的核心计算理念——把所有东西全部并行化，每一个单元只处理简单的运算——是正确的，至少未来 10 年一定往这个方向走；这条 pipeline 未来可能取代经典管线。

       * 但经典管线还是要学：即使切到那个 pipeline，材质、网格、index，包括根据材质对世界做划分，这些基础逻辑还是需要在的。

       * 代价与收益：对程序员的要求比以前高很多，要做大量的处理和运算，代码写起来已经不太好理解；好处是可以产生无数的细节，艺术家可以自由地发挥。

## Piccolo 小引擎的架构

   * **工程结构**

       * 引擎核心工程严格按平台层、核心层、资源层、功能层从下往上一层一层垒起来；编辑器被单独做成一个工程、与引擎核心做出区隔；shader 也单独放在一个工程里——它虽然也是源码（选 GLSL），但编译出的 binary 需要单独管理。

       * build 目录需要自己构建：按不同平台的 CMake 指令正确运行后生成工程文件（一般放到 build 目录下），得到 solution 文件。

       * 整改后约 2 万多行代码，大部分基本是重写的——为的是给出一个相对完整、方便阅读的框架。

   * **编辑器**

       * 操作：按住鼠标右键上下左右调整相机，ASWD 像 FPS 游戏一样飞来飞去；鼠标左键点住物体会出现坐标轴表示选中，旁边展开它的各个 component 面板——编辑 UI 都是用反射的方法自动生成的；动任何一个数值，立刻可以看到场景里数据的变化。

       * 标准编辑器架构：object list 列出场景中所有物体；content browser 里所有资产都能看见、点击可以加载进场景——麻雀虽小五脏俱全。

   * **组件组合因物体而异**

       * 一堵墙有碰撞体、能拦住你；展示对照用的小物件只有 transform 和 mesh、没有碰撞，可以直接穿过去；最复杂的是主角：transform + 动画 component + Motor（设置移动速度）+ 相机 component（一旦进入游戏模式就起作用）。

       * 编辑模式与游戏模式一键切换；游戏模式里按一下 Alt 鼠标释放，再切回编辑模式角色停在原地。角色暂为循环播放一个动画——根据速度和位移在站立 idle 与漫步等状态之间切换，需要动画混合（animation blending）的基础，暂未开放。

       * 渲染实现：一个简单的 PBR 材质，光照能看到很多细节；为简单暂用前向渲染（forward）管线。

   * **反射与资产**

       * 预编译（precompile）工程用了类似虚幻的反射机制：在 C++ 里定义各种数据类型，打上 decoration（标记），自动反射出「这类资源在资产里应该用什么方式去读取」——生成的代码全是全自动生成的，是游戏引擎非常重要的东西。

       * 资产全部用 JSON 去存数据：每种可以反射、可以读进来的资源类型在代码里以 REFLECTION_TYPE 宏标注；结构一层层嵌套——每个变量的名字最后会变成 JSON 里的一个描述字段（如 name；transform 里的 position、rotation、scale），与代码里的定义一一对应。

   * **有意的取舍**

       * ECS 的代码太抽象、本身扩展性也不是特别好，先撸掉以后再说。

       * 多线程架构没有放出来——那会极大地降低整个代码的可读性；学习阶段要经常加断点，去看每个功能到底是怎么跟进去的。

       * 模型暂用 OBJ 格式，后面可能切到 FBX 方便构建想要的模型；mesh、submesh 的整个结构会搭起来，还会做简单的动画混合系统。
