# 游戏引擎导论与架构分层

## 什么是游戏引擎

   * **游戏引擎（game engine）**

       * > **定义**：游戏引擎有三层本质——它是构建虚拟世界的底层技术框架（the foundation of the Matrix）；是把创意与想象力变成可交互世界的生产力工具；是一门复杂性的艺术——几乎不存在完美、紧致的引擎架构，它是一系列妥协与决策的结果。

       * 维基百科式定义（"专为游戏开发设计的软件框架、工具合集"）是循环论证：要么概括到什么都没说，要么只罗列组成器官，都点不中本质。

       * 游戏几乎集成计算机科学的所有知识门类，复杂度相当于一个操作系统；引擎是躲在游戏下面看不见的部分，集结现代计算机科学最前沿技术，被称为行业的"皇冠上的钻石"，也是技术与设计的结合体、技术壁垒最高的环节。

   * **会用引擎 ≠ 会造引擎**

       * 会用 Unity、Unreal 相当于学会了开车；造车要懂发动机的工作原理、所需的技术与材料——越往核心走，会的人越少。

       * > **易错点** ⚠️：**会用游戏引擎不等于懂引擎**——"我会用 Unity"与"我能造引擎的发动机"是两种能力。

   * **做渲染 ≠ 会做引擎**

       * 经典教材《游戏引擎架构》的结构图里，图形学只占整个引擎很小的一部分；从"会做渲染"到"会做引擎"，还要再学另外 90% 的知识体系。

       * 算法与系统有本质区别：做一个算法从想法到发表论文约六个月；做系统则要先接受严格的系统工程训练，开工后一整年可能什么都看不见。

   * **图灵机（Turing Machine）**

       * > **定义**：现代计算机的基础理论模型——一条可打孔的纸带加一个读写头，按机械规则运动即可完成一切复杂运算；本质是"读写、计算"的循环。

       * 虚拟世界的一切最终都由 0/1 的简单逻辑表达：用最简单的机制模拟出无比复杂的世界，正是引擎复杂度的来源。

   * **一句话行为下的隐藏复杂度**

       * "两个玩家联网互相攻击"一句话，下面同时藏着渲染器、动画系统、物理碰撞系统、控制系统与网络同步：A 在自己的世界按下攻击键，B 的世界要看到同样的操作；B 若做了闪避，闪避成功与否还需要统一裁决——所有这些复杂度都躲在一句话描述的游戏行为之下。

## 引擎的应用版图

   * **虚拟人**

       * 虚幻引擎的 MetaHuman 与"鹿鸣"式虚拟形象背后，是游戏业十到二十年积累的皮肤 3S 材质与毛发模拟技术。

       * 未来打开支付、银行终端与你交互的可能都是虚拟人助手，其背后就是游戏引擎。

   * **影视虚拟化制片**

       * 好莱坞用游戏引擎在巨型 LED 平台上生成虚景供演员实地拍摄；许多广告与电影场景已由引擎实时渲染，导演能在现场调整光照与布景——这与传统离线渲染农场是两条路线。

   * **军事模拟**

       * 世界各国用游戏引擎训练军队：步兵、坦克、飞机的战术演练都需要最真实的场景；现代战争是系统对系统的对抗，模拟的重要度持续上升。

   * **数字孪生**

       * 工业 4.0、工业数字化、元宇宙背后共同的热门概念：把现实世界虚拟化地表达进计算机，帮助人类更好地理解、管理与构建未来世界。

       * 无人驾驶约 99.9% 的驾驶里程跑在游戏引擎里——不可能让真车在路上跑 10 亿公里，只能用引擎模拟各种下雨、路面与行人异常情况；下一代车载系统的人机交互立体界面背后同样是引擎。

   * **工程类引擎与游戏引擎同源**

       * BIM（Building Information Modeling，建筑信息管理）引擎要读 Revit 等建筑图纸格式，WebGL 为多端运行裁剪功能，但底层架构逻辑与游戏引擎相通。

       * 两类引擎面对同一挑战：让别人能编辑、能再次创作；游戏引擎身处充分竞争的市场，最前沿的理论都在其中被尝试过，突破最远、最可借鉴。

   * **时代判断**

       * 未来 10 到 20 年，每个人都需要多少了解虚拟世界如何构建；这个虚拟世界最重要的 foundation 就是 game engine。

## 实时约束与算力天花板

   * **实时（real-time）**

       * > **定义**：游戏引擎设计的核心边界条件——无论算法多么出色，只要不能在 1/30 秒（33 毫秒）之内提交计算结果，就是无效算法。

       * 一整帧的总预算只有 33ms，单个子系统（如流体模拟、水体、物理爆炸）往往只分到 1–2ms。

       * 现代动作游戏低于 60 帧就难以接受：60 帧意味着一整帧的计算只有 16ms 左右，所有效果都要塞进这个时间片。

   * **与"上帝的引擎"的资源差距**

       * 真实世界（假设是虚拟的）的模拟者拥有无限算力、无限存储、无瓶颈带宽、零延迟，可以采用暴力算法；我们的计算机四项全部受限：

| 资源 | 上帝的引擎 | 我们的计算机 |
| :--- | :--- | :--- |
| 算力 | 无限，可采用暴力算法 | CPU 主频涨速放缓，几乎触及摩尔定律上限 |
| 存储 | 无限 | 硬盘与内存容量有限 |
| 带宽 | 没有瓶颈 | 每秒可传输的数据量有限 |
| 延迟 | 没有 | 数据从 A 地传到 B 地存在传输延迟 |

       * 在四重约束下模拟一个逼近真实的世界，就是游戏引擎复杂度的根源。

   * **算力增长与系统复杂度**

       * PS1 的算力仅 0.06 GFLOPS，PS5 达 10 TFLOPS——提升了整整 20 万倍；算力越强，可表达的效果与涵盖的模块越多，系统随之越复杂。

       * 现代游戏引擎动辄几百万到上千万行代码，算法密度极高；与操作系统同理——早期谁都能写，如今只有极少数公司有能力维护上亿万行的操作系统。

## 行业简史

   * **前引擎时代**

       * 游戏行业只有 50 多年历史；红白机时代没有引擎概念，最核心的能力是把复杂元素塞进约 40KB 的存储空间。

       * 极限技巧：白云贴图换个颜色放到地上就当草丛用；小乌龟贴图正反两帧来回播放，看起来就是乌龟在走。

       * 那时一个人一年能做四款游戏（某微软副总裁加入微软前的纪录）；如今几百人做三年才出一款 3A——游戏简单带来创意的野蛮生长，像寒武纪生命大爆发。

   * **卡马克与第一款引擎**

       * John Carmack 先做出 Wolfenstein（《重返德军总部》），开创了 FPS 时代；今天看到的每一种游戏类型，都是被某款产品定义出来的。

       * 做 DOOM 时他把核心代码抽成了游戏引擎，授权给另一家公司做出 ShadowCaster 并在商业上成功——公认全球第一款游戏引擎，第一款就商业成功。

   * **Quake 与现代引擎的开端**

       * "现代游戏引擎"的概念从 Quake 时代开始：它是那个时代最经典的射击对战游戏，有著名的"火箭跳"（用 RPG 轰地面借反作用力跳得更高）。

       * Quake 是第一款系统性研究联网对战网络同步的游戏，也是抓住第一代显卡的第一代 3D 游戏，画面与沉浸感震撼了整个时代。

   * **显卡的划时代意义**

       * 最早的计算机没有显卡；后来业界才意识到图形运算是大量向量运算、且高度可并行，用 CPU 处理很吃力——第一代显卡 Voodoo 应运而生。

       * FPS 老玩家熟悉的"晕 3D"（打着打着就吐），用 Quake 体验最直接。

## 引擎生态与中间件

   * **引擎生态三大阵营**

| 阵营 | 代表 | 特点 |
| :--- | :--- | :--- |
| 商业通用引擎 | 虚幻引擎（Unreal）、Unity、CryEngine | 面向全行业的商业级引擎；CryEngine 前些年很强，近年稍有掉队 |
| 大厂自研引擎 | EA 寒霜（Frostbite）、育碧 Anvil（铁毡）、Valve Source | 全球游戏大厂都有自己的引擎，为自家产品深度定制 |
| 免费引擎 | Godot、Armory | 以轻量休闲、偏 2D 的简单游戏为主，复杂度与商业大厂引擎尚有差距 |

       * 自研引擎的能力证据：EA 寒霜成就了《战地》系列开阔战场的感觉；育碧 Anvil 打造的《刺客信条》巴黎圣母院，在大火之后成了人们追忆其原貌的数字载体。

   * **中间件（middleware）**

       * > **定义**：把引擎中复杂到值得单独立项的能力抽出来、由专门公司做成的独立模块。

| 领域 | 代表 |
| :--- | :--- |
| 物理 | Havok、PhysX |
| 声音 | Wwise、FMOD |
| 植被 | SpeedTree |
| 几何简化 | Simplygon |

       * 声音中间件的价值：恐怖游戏里脚步在声场中的回声、炮弹在身边爆炸的耳鸣感，都由专门的声音引擎实现；SpeedTree 造出了《阿凡达》茂密葱茏的外星植被。

       * 生态规律：中间件公司不断爆发但生命周期普遍不长，业界戏言其最好归宿是被游戏大厂或引擎大厂收购；程序化内容生成（PCG）类内容与场景生成中间件也在持续涌现。

## 引擎的评判与协作

   * **二次开发能力**

       * > **定义**：引擎搭好之后，游戏程序员能否在上面快速开发出自己的特定玩法——这是评判引擎好坏最硬的标准之一。

   * **可协作**

       * 现代游戏工作室动辄上百人、约二三十个大分工：会写程序的人很少，艺术家内部还细分贴图、建模、动画、环境、气氛与过场——这群人必须靠引擎的工具链协作起来。

       * 做引擎的人的心理姿态：把自己放得特别低，目标就是服务好设计师与美术师——工具就是生产力。

   * **飞行中换引擎**

       * 引擎底层技术要持续升级（更漂亮的光照、更细腻的细节、更逼真的物理），而过去制作的资产与游戏逻辑必须始终能跑。

       * 行业比喻：在一架飞着的飞机上把零部件逐渐换掉、甚至换掉整台引擎，而飞机不能掉下来——这要求架构在最初设计时就为持续升级做好打算。

   * **引擎的双重用户**

       * 最大用户是艺术家与设计师：动画师用角色编辑器编辑动画、行为、物理与布料模拟；关卡设计师摆放山川河流；设计师设计规则与 AI 行为。

       * 程序员同样是重要用户：引擎不可能预置所有玩法（动作闯关、开放世界冒险、剧情向 MMORPG 的变化无穷），要把玩法的可能性交给程序员实现。

## 学习方法与入门路径

   * **只沿主干道行进**

       * 游戏引擎像云遮雾绕的珠峰，往哪个方向走都与你相关；学习策略是选定一条主干道一路走到顶，其余支线点到不展开。

   * **先建体系框架**

       * 学习大型系统工程，体系结构（framework）最重要：学完不等于成为专家，而是未来遇到任何挑战时，知道该去翻哪本书、问题处在哪个体系里、去哪找最前沿的资料。

       * 取向是重体系、轻技巧：不要求先精通 C++，目标是让美术与设计师也能听懂引擎课。

   * **读引擎的入口**

       * 打开任何一个引擎（虚幻、Unity 或教学引擎）的代码，先找那个每隔 1/30 秒被调用的 tick（update）函数；从入口顺藤摸瓜，能抓到引擎的全部细节。

       * 配套教学引擎 Pilot 的 runtime 严格按平台、核心、功能分层（约一万三千行），外加约两千行的独立编辑器，内置完整反射、一键 play 与一套小型 ECS；从 TickLogic、TickRender 读起即可看懂全部逻辑。

   * **参考书**

       * 系统学习可配合《游戏引擎架构》通读：它是全面思考引擎架构的工具书，一千多页，其中功能层部分占比最大。

   * **引擎研发的组织方式**

       * 引擎研发像"数据结构"这门课的形成过程：工程实践反复总结出方法，实践足够多后再体系化固化成可重用的模式。

       * 现代引擎开发不是一层一层盖楼：平台、功能、核心常由不同成员并行编写，前提是一开始就定好规范。

## 引擎子系统全景

   * **渲染管线**

       * 引擎渲染讲的是体系结构：把材质、光照、网格、动画、大气组织进一条实时 pipeline，全部塞进约 30ms。

       * 经典路线有延迟渲染（deferred rendering）与前向渲染（forward rendering），各有优劣；一个小小的透明物体（玻璃）就能给渲染管线带来巨大困难；可定制的管线（如 SRP）与卡通化渲染是现代方向。

   * **动画系统**

       * 引擎动画要解决的是把 Max/Maya 做好的素材"玩起来"：走与跑如何过渡、移动中被攻击时动作如何打断切换。

       * 核心组织结构是动画树（animation tree）与混合树（blend tree），让设计师能参与搭建；"空手接白刃"式的精确交互（保证剑砍来时手一定接得准）是游戏动画系统的核心设计理念。

   * **物理表达**

       * 世界在画面之外还有另一重"物理表达"，与眼前所见互为孪生世界。

       * 基础是最简单的刚体——盒体（box）、胶囊体（capsule）、球体（sphere）——配刚体力学模拟运动；可压变形的软体引入弹性力学；水、烟、头发引入流体模拟；车轮在雪地与泥地上表现不同则是系统级整合。

       * > **易错点** ⚠️：**墙打不倒别怪策划**——那面墙很可能只做了碰撞体、没做破坏，甚至在技术上根本做不了。

   * **游戏性（gameplay）架构**

       * 渲染、物理、动画只构成一个"世界模拟器"（simulator）；让世界好玩的是规则——子弹打掉敌人五点血、敌人受伤呼叫队友支援。

       * 这些规则由设计师而非程序员设计，因此需要事件系统、脚本系统与图形化的规则表达，让设计师也能"告诉计算机"世界如何运转。

       * 所有现代游戏，本质上是一个规则体系；在节点图上连线同样是编程——用元件构建逻辑就是编程，不必对着电脑敲代码。

       * gameplay 系统像电路板设计软件：引擎提供二极管、三极管、电容，设计师用它们组装出收音机、电视或智能电灯开关。

   * **特效系统**

       * 冒烟、冒火等特效不能程序写死，要提供一整套框架与结构让艺术家创造各种可能性；游戏特效做不好同样是"五毛钱特效"。

   * **寻路系统**

       * 人靠眼睛扫描世界认路，游戏 AI 无法扫描——需要一套体系告诉 AI 哪里有墙、哪里有路、哪里有障碍。

   * **相机系统（3C）**

       * 射击游戏的"枪感""镜头感"由相机系统决定：玩家每天都能感觉到、却最容易忽略的系统。

   * **网络同步**

       * 商业引擎过去在网络这块较弱，但现代游戏越来越需要连接彼此；上帝模拟世界只需一份，联网游戏则是每台机器各跑一个小宇宙，里面放着彼此的克隆，靠信号来回传递让各宇宙发生的事尽可能一致——所谓联网，就是无数个平行宇宙之间的信息传递。

       * "我放大招明明打中了"而对面没中，多半是网络延迟或同步算法问题；基础算法有著名的帧同步与状态同步，服务器方向深度极深，可以再写一整本书。

       * 离元宇宙还很遥远：让几千、上万人同在一个世界互动，绘制、网络同步、状态同步与游戏规则处处是大挑战。

## 前沿技术方向

   * **Motion Matching（运动匹配）**

       * 用 search 算法加一点 deep learning，让角色活灵活现地适应各种场景；大量动画由 searching、matching 自动合成。

   * **程序化内容生成（PCG）**

       * 开放世界动辄几百到上千平方公里，逐棵种树、逐块摆石头不现实；把植被等规则写成算法自动生成，是热门前沿方向。

       * 目前最强的技术能直接用算法生成一座中世纪的巴黎城。

   * **面向数据的编程（DOP）与任务系统（job system）**

       * DOP 以数据为中心来组织逻辑；job 系统把复杂模拟拆成一个个原子小任务，由调度者把任务分给各个核、完成后再收回。

       * 目标是把 30ms 内要完成的世界模拟铺到八个、十几个甚至几十个核上——未来引擎架构一定是多核架构，底层设计应从多核开始思考。

   * **实体-组件系统（Entity Component System，ECS）**

       * > **定义**：现代游戏引擎组织对象与组件的一种模型。

       * 为了更高性能地模拟世界，数据要按 DOP 的方式组织，计算机才能快速批处理所有构件——ECS 与 DOP 的关系度很高。

   * **Lumen 与 Nanite**

       * 虚幻五最重要的两个特性：Lumen 负责全局光照；Nanite 提供无限几何细节，面片细到像素级。

   * **VR 游戏**

       * 仍处发展早期，受制于头显算力：强调强交互、强体验，不拼视觉细节。

       * 无线传输延迟太大，主流方案是把计算全放在头显上；未来若双眼 8K、120 帧刷新，才是真正的沉浸式体验。

---

## 五层架构总览

   * **五层架构（5+1 层）**

       * > **定义**：把现代游戏引擎的代码与体系简化为五层——自下而上为平台层、核心层、资源层、功能层、工具层，旁边再挂一个"+1"：第三方库；记住这 5+1 层，就涵盖了现代游戏引擎几乎所有的代码与体系。

```text
┌────────────────────────────────────────────────────────
│  工具层 Tool        关卡编辑器 · 蓝图 · 材质编辑器
├────────────────────────────────────────────────────────
│  功能层 Function    渲染 · 动画 · 物理 · 脚本 · AI · UI
├────────────────────────────────────────────────────────
│  资源层 Resource    资产加载管理 · 引用 · GUID · Handle
├────────────────────────────────────────────────────────
│  核心层 Core        内存管理 · 容器 · 数学库 · 线程
├────────────────────────────────────────────────────────
│  平台层 Platform    图形 API（RHI）· 文件系统 · 输入输出
└────────────────────────────────────────────────────────
          五层旁边还挂着 "+1"：第三方库
```

       * 从下往上读：平台层抹平设备差异，核心层提供基础服务，资源层把资产喂进来，功能层把游戏跑起来，最上面的工具层供人创造内容。

       * 这是极简分法：实际可以分得更细，各流派分法不同；虚幻、Unity 等商业引擎大同小异——平台无关、核心、资源各层家家都有，功能层差别最大（很多引擎里又细分好几层）。

   * **第三方库（+1）**

       * 典型代表：物理的 Havok Physics、植被的 SpeedTree、面片简化的 Simplygon。

       * 两种集成形态：一种以 SDK 形式随引擎一起编译进去；另一种是独立工具，与引擎只通过文件格式交换数据。

       * Simplygon 的双份用法：引擎外备一套，让艺术家把几十万面片的复杂几何逐层简化；引擎内也可集成一套，对特别复杂的对象做实时简化。

   * **用"做一个会动的角色"检验五层**

       * 从下往上把代码写进引擎：资源层把角色模型、贴图、动画导入成 asset 并用组合资产建立引用；功能层在 TickLogic 里挂动画 tick、在 TickRender 里逐帧绘制；核心层提供内存、容器与数学库支撑；平台层至少抹平文件路径与图形接口差异；工具层为后来的合作者准备整套编辑器。

## 资源层

   * **资源层的职责**

       * > **定义**：加载并管理游戏的全部数据文件——现代游戏的数据文件量级在上万到上十万，来自 Photoshop、3ds Max、Maya 及声音编辑软件。

       * 它是给功能层供弹药的仓库：导不进角色模型与动画，功能层就无东西可画——如同不给导演场景，再大的本事也拍不出电影。

### 资源与资产

   * **资源（resource）**

       * > **定义**：DCC 工具产出的原始文件——`.max`、Maya、`.psd` 等格式各异。

       * 这些格式为各自的工具服务、结构复杂且含大量无效信息；引擎不可能逐个适配，直接加载效率极低。

   * **资产（asset）**

       * > **定义**：原始资源经过引擎导入流程转换后、能被引擎高效使用的资产数据——资源层的第一课就是分清这两个词。

   * **导入（importing）**

       * resource 变成 asset 的转换流程：像把 Word 文稿只取正文存成 TXT——体积骤减，编辑用数据全部丢弃。

   * **DDS 贴图**

       * JPG/PNG 的压缩为存储设计，放进 GPU 绘制效率低；导入时所有贴图统一转成 DDS——按每块 16 字节组织的格式，可直接灌进显存当纹理。

### 引用与标识

   * **引用（reference）**

       * > **定义**：数据之间的关联，现代游戏最核心的功能之一。

       * 未打包的游戏目录里有几十万甚至上百万个文件，贴图、声音、动作像一张网彼此关联；发布时一般打包成几个大 package。

   * **组合资产（composite asset）**

       * 描述"关系"的脚本型资产：例如用 XML 定义一个 robot——写明 mesh 是什么、纹理是什么、用哪些动画；引擎读它就知道要去加载哪些资源；它本身也是资产之一。

   * **全局唯一编号（GUID）**

       * 每个资产一张"身份证"：靠路径找资产像只记朋友的住址，朋友一搬家就失联；靠身份证号，无论人搬到上海还是北京都永远查得到。

   * **句柄（handle）系统**

       * 信箱模型：东西搬来搬去也无妨，我始终握着"105 号信箱"的钥匙，主人在不在问信箱即可；与运行时资产管理配套使用。

### 生命周期管理

   * **运行时资产管理器（runtime asset manager）**

       * 游戏运行时（runtime）资产仍以文件形态存在（去头去尾只留内容）并互相指向，由它统一管理。

   * **生命周期**

       * 资源层最核心的职责是管理所有资产的生命周期：闯关从关卡 A 到 B 到 C，旧资产失效卸载、新资产下载，中间引用关系极其复杂——GUID 与 handle 系统都在解决这个问题。

   * **垃圾回收（GC）**

       * 现代 GC 普遍做不好，会拖垮整个系统效率：关卡切换时上万上十万资源瞬间回收，没写好当场卡死一帧；游戏"玩着玩着突然变慢"多半是 GC 没做好。

   * **延迟加载**

       * 内存小、硬盘大，于是人走到哪资源下到哪；角色刚出现时贴图模糊、随后逐渐变清晰，就是延迟下载的表现。

   * **数据先行**

       * 引擎开发真正的核心常从数据开始：先定义数据格式与 schema，再定义数据在引擎、编辑器、文件中分别如何呈现——许多资深引擎开发者的第一个半年没写一行渲染与特效。

## 功能层

   * **功能层的职责**

       * > **定义**：让虚拟世界被看得见（渲染）、动得起来（动画）、玩得起来（脚本、AI、规则）——核心模块包括渲染、动画、物理、脚本、AI 与人机界面（UI）。

       * 血条这类界面元素与三维绘制无关：它是数值一直在变的二维小物件（gadget），却是现代商业游戏必备又最容易被忽略的部分。

### Tick 驱动

   * **tick**

       * > **定义**：引擎的心跳——每隔固定间隔（约 1/30 秒）把整个世界的逻辑与绘制完整推演、描绘一遍，世界往前走一小格；相当于这个游戏世界的"普朗克时间"。

```text
一个 Tick（每隔约 1/30 秒）：
    读输入输出 → 动相机 → 动人物角色 → 播动画
    → 绘制一帧画面 → 内存 GC → 整个逻辑往前走一格 → 下一个 Tick
```

       * 上帝的 tick 是普朗克时间——任何物理过程都不能小于它；游戏里每个 tick 就是所构建世界的时间最小刻度。

   * **TickLogic 与 TickRender**

       * tick 内的两大神兽，一般先 TickLogic 再 TickRender——对世界的模拟为先：先把这一帧世界的姿态算出来（有没有人观察它都存在），再由观察者的视角生成二维画面，后者才是渲染。

       * 逻辑做的是读输入输出、算物理、动 camera、推角色运动、做碰撞检测；"张三打中李四、扣五点血"是逻辑的事——不管你看见没看见，这一击都已成立。

       * 渲染做的是专业绘制：裁剪（看不见的被裁掉）、光照、相机的 shadow；动画之所以成立，是人靠视觉残留感知连续世界，这一点被现代游戏充分利用。

       * > **易错点** ⚠️：**表现绘制与逻辑必须严格分离**——未受系统训练的开发者常把两边的代码写混；只要一开始就分开，之后无论怎么写都不会搅在一起。

### 引擎与游戏的边界

   * **功能层的体量**

       * 《游戏引擎架构》中功能层的内容最多、无所不有，是占比最大的部分。

   * **归属模糊带**

       * 相机控制（手持摄像机的摇晃感、镜头模糊、拉远拉近）与特定游戏强相关，属于游戏代码而非引擎代码；rendering pipeline 与资产管理则一定属于引擎。

       * 哪些功能属于游戏、哪些属于引擎，基本就在功能层"打架"。

### 多核架构演进

   * **四个演进阶段**

```text
演进一  单线程    [ Logic ── Render ── … ]              一个线程跑到死
演进二  多线程    线程A: TickLogic  线程B: TickRender    线程C: 下载
演进三  任务并行  主核 + 物理/动画等易并行计算 fork 到多个核（主流商业引擎）
演进四  Job系统   [job][job][job][job][job]…            不停塞满每一个核（未来方向）
```

       * 单线程是最早形态，一个线程跑到死；基础多线程把 TickLogic 与 TickRender 分进两个线程，另留下载等线程。

       * 任务并行是把物理、动画等容易并行的计算单独 fork 出来、分散到很多核上——虚幻等主流商业引擎现在的做法。

       * job 系统把所有任务变成原子的 job，不管 4 核、8 核还是 16 核都持续喂满——公认的未来方向。

   * **肉眼判别法**

       * 打开游戏再开 Windows 的 CPU profiling 小窗口：若有的核吃得很满、有的吃不满，它的多线程大概率没用高级 job 系统。

   * **依赖（dependency）管理**

       * 高效多核架构的真正难点：计算之间有先后依赖——动画系统先算完手的位置，粒子系统才能在正确位置发出特效；依赖管不好就会出乱子。

## 核心层

   * **核心层的定位**

       * > **定义**：为上层所有逻辑提供基础服务的底座——内存管理、容器、数学库、线程管理，像一把瑞士军刀；上层所有游戏相关的逻辑管理全部架在它上面。

       * core 在整个引擎层次里扮演的角色，与操作系统底层类似。

### 数学库

   * **自建数学库**

       * 绘制与游戏逻辑所需的数学并不高深：矩阵、向量、坐标变换，大学线性代数基本够用，关在自习教室一个周末就能补齐。

       * 仍要自己写：引擎一切为效率服务、必须实时响应用户输入，对数学库的效率极其敏感。

   * **卡马克平方根倒数**

       * Quake 3 中求 $1/\sqrt{x}$：按浮点指令走"开根号+除法"是无数条指令、极慢；卡马克用一段含 magic number 的代码先求近似解，再用牛顿迭代快速逼近精确值。

       * 引擎常不要求数值绝对正确、大致正确即可；该实现的效率远高于直接调用系统 math 库的 sqrt 再做除法。

   * **SIMD**

       * 引擎数学的高频操作是 4×4 矩阵（16 个数）与 4 维向量的加减乘除；SIMD 用一条指令把四个运算一次做完。

       * 读引擎代码看到注释 SSE，即该段在做向量运算：直接调动 CPU 的向量并行能力，比逐个算浮点数快好几倍。

### 数据结构与内存

   * **弃用 STL 的原因**

       * C++ 标准容器在高频增删时产生大量内存空洞、内存使用不受控：如 vector 预留 100 个元素遇到第 101 个会把空间粗暴翻倍，最终内存消耗不可知且分散，游戏变慢。

       * 内存管理没做好，效率可以下降一个数量级（慢十倍）；EA 寒霜团队为此自研了 EASTL——更高效、更紧致的容器库，最新的 C++ 标准也在逐步吸收这类思路。

   * **自研数据结构**

       * 核心层要提供几乎没有内存碎片、访问效率极高的容器：数组、链表、二叉树这些基础概念并不复杂，难点全在让内存行为可控。

   * **内存池（pool）**

       * 引擎像操作系统一样管理内存（堆、栈机制），但策略是预先申请一大块内存"圈地"，之后向量、树、链表都在池内自行分配——追求最高效率。

   * **CPU 缓存（cache）**

       * 同厂同主频的 CPU 价差悬殊，差别往往在紧贴 CPU 的 cache：缓存极贵，但越大取数效率越高。

       * 买 CPU 不要只看主频、内存也不是越大越好——缓存很多时候才是核心卡点。

   * **图灵机三条铁律**

       * 数据尽可能放在一起；访问尽可能按顺序（1234567 而非 179356）；读写尽可能一次一批、不要逐个抹改。

       * 引擎底层内存管理、乃至各种高端内存特性的底层逻辑，基本就是这三条。

   * **core 层的纪律**

       * core 代码质量要求极高、要保证绝对的安全与效率，写完几年不动；几十上百人的引擎团队里，能写 core 的只有少数资深工程师。

## 平台层

### 平台无关

   * **平台无关（platform agnostic）**

       * > **定义**：平台层把所有平台的差异掩盖掉，上层写核心代码时可以无视平台区别、直接写核心逻辑。

       * 无论用户来自什么输入输出设备（键盘鼠标、手柄，乃至 Kinect 体感、驾驶方向盘），进入游戏世界都要被翻译成统一的语言。

   * **差异清单**

       * 硬件：PC、Mac、手机、Xbox、PlayStation，用户设备千千万万。

       * 发布平台：Steam、Epic Games Store、XGP 的接口与收费模型可能完全不同。

       * 连文件路径格式都不同：正斜杠与反斜杠、`C:\` 与 `volume:`。

### 图形接口封装

   * **图形 API 分裂**

| 平台 | 图形 API |
| :--- | :--- |
| Windows PC | DX11 / DX12 |
| Mac | Metal |
| Android | OpenGL ES / Vulkan |

       * 在上面写图形特效与 shader 的人若要直面这些差异会非常崩溃。

   * **渲染硬件接口（Render Hardware Interface，RHI）**

       * > **定义**：引擎重新定义的一层 graphics API，把各个硬件 SDK 的差异封装起来。

       * RHI 函数普遍是虚函数：编译成 Metal、PC、移动端版本时各自实现一遍；上层写效果的人完全不用管。

       * > **易错点** ⚠️：**DX11 代码不能直接搬成 DX12 代码**——两者同属微软全家桶但设计理念完全不同；直接搬会让游戏不是变快反而突然变慢，必须利用 DX12 的特性重做底层优化。

### 硬件架构差异

   * **PS3 的协处理器**

       * PS3 除传统 CPU（PPU）外还有几个速度极快但访存方式特别的小协处理器（SPU）；索尼建议把绘制中的数据预处理与独立 AI 逻辑放到 SPU 上跑。

       * 代价：写 AI 与逻辑的人要关心算法跑在哪个核；换到 Xbox、PC、Mac 上怎么办——这是引擎平台层著名的痛苦来源。

   * **大小核**

       * 现代 ARM 芯片有大小核概念，哪个算法放哪个核才合理，同样是平台层要回答的问题。

   * **引擎水平的分水岭**

       * 平台层最容易被忽略，但其好坏对引擎效率影响极大，是引擎水平高下的重要分水岭。

       * 简单游戏把文件路径搞对就能跑；而《全战》《使命召唤》级别的产品，这一层必须非常用心地设计。

## 工具层

   * **工具层的定位**

       * > **定义**：引擎两大块之一（另一块是实时的 runtime）——允许别人与引擎打交道、创造游戏内容的全部编辑器与管线。

       * 它是真正的生产力工具：使用者的创造力靠这一层释放。

### 编辑器家族

   * **以关卡编辑器（level editor）为中心**

       * 工具层是一系列编辑器：关卡（地图）编辑器居中，外围有蓝图逻辑编辑器、材质编辑器、角色编辑器等。

   * **材质编辑器**

       * 同一资产在 3ds Max/Maya 里的效果与引擎里的效果不同；材质编辑器必须保证编辑器内预览与真实游戏运行效果一模一样——对艺术家极其重要。

   * **可视化编程**

       * 蓝图（Blueprint）这类图形化编程的判断：是未来——想象力不需要编程训练，可视化编程会成为创意者重要的基础编程语言与人机交互界面。

### 开发方式与体量

   * **开发效率优先**

       * 引擎 runtime 用 C++ 追求最高运行效率；工具层以开发效率为优先：C++/Qt、C#/WPF、甚至 H5/Web 都可以，各引擎选择不同。

       * 不变的目标只有一个：允许别人创造游戏的内容。

   * **代码量反超引擎**

       * 五层中工具层只占一层，但其代码量很多时候比引擎还大，维护门槛与复杂度更高。

### 工具间的数据通道

   * **数字内容创作（Digital Content Creation，DCC）**

       * 别人开发的资产生产工具：3ds Max、Maya、Photoshop、FMOD，以及做出大量电影特效的 Houdini。

   * **资产处理管线（asset conditioning pipeline）**

       * 由各种导出器与导入器组成：把 DCC 工具与自研编辑器产出的数据统一变成引擎的 asset；自研编辑器加导入导出器共同构成工具层。

   * **反射体系（reflection）**

       * 工具体系最重要的底层概念之一：引擎对象能被工具枚举、编辑全部属性——教学引擎里点击任意元素即可编辑其所有属性，靠的就是完整反射。

       * 工具会不停升级数据格式，但过去与未来的数据都必须兼容：这样做出 100 个、1000 个工具，彼此仍能对话。

   * **数据互通格式**

       * 十几种自研编辑器加七八种外部工具连成一条链，数据必须彼此"说话"，因此需要统一的数据格式。

       * 业界推过 FBX（十几年前的方案）与 Pixar 主导的 USD（更多用于电影行业）；游戏引擎一般还是定义自己的一套格式。

## 分层设计原则

   * **解耦（decoupling）**

       * > **定义**：分层的第一目的——用"控制变量法"解耦复杂度：每一层只关注自己的事，越往下的层提供基础服务。

       * 城市类比：水电排污等百姓看不见的基础设施像平台层与核心层；物流与资源调度（垃圾场不会爆掉）像资源层；生活、经商、创造财富像功能层。

   * **封装（encapsulation）**

       * > **定义**：现代系统科学的核心概念——把足够多的低层概念合并成一个可整体使用的高层概念。

       * 原子构成篮球，你玩篮球不必关心它由多少原子构成；一群人打篮球又封装成"一场篮球比赛"；没有封装的散乱概念既不可理解、也不可管理。

   * **稳定阶梯**

       * 越底层越不要动：平台层、核心层的代码写完后几年不改——一改上面全麻烦；功能层的代码改来改去；工具层几乎每天都在变。

       * 好处：需求不断涌来时不必从上到下动所有系统，只动上层即可——越往上越灵活，越往下越稳定。

   * **调用方向**

       * > **易错点** ⚠️：**只允许上层调用下层**；下层反向调用上层绝对不允许——这是分层架构的核心体系结构。

   * **归属判断先行**

       * 接到任何需求，先想清楚这件事属于资源层、核心层还是功能层，再动手写算法；把一堆功能框框堆在一起秀效果，是没受过系统训练的做法。

   * **好引擎的检验**

       * 去研究现代引擎：做得好的引擎一定分层清晰、每一层的职责都很明确。
