# 纹理生成压缩与着色器优化

## 纹理与材质的数学表达

* **纹理（Texture）**

    * > **定义**：程序中的多维固定数组，一维、二维、三维都有，可存放浮点、整型等不同类型的元素。

    * 材质定义几何物体如何与光交互：只有几何、没有纹理材质的场景没有颜色甚至无法渲染；真实感渲染的两大关键是几何与材质。
    * 因为本质是数组，纹理不止能表达材质：深度、帧缓存等都可用纹理承载；材质表达是纹理应用最多的场景。

* **双向反射分布函数（bidirectional reflectance distribution function，BRDF）**

    * > **定义**：描述"每个入射方向的光，有多少被反射到每个出射方向"，由入射、出射两个球面方向 $(\theta,\phi)$ 共同决定，天然是四维函数。

    * 渲染方程的核心组成部分：出射光要对所有入射光积分，BRDF 给出其中每个入射方向的反射率。
    * 获取需专门仪器采集，且只描述单一材质（铝、纸板这类）。
    * 4D 表要用巨大数组储存，实时渲染乃至真实感渲染都不直接使用，一律用解析模型逼近。

* **空间变化 BRDF（spatially-varying BRDF，SVBRDF）**

    * > **定义**：在 BRDF 上引入空间变量 $x$（定义在物体表面的 UV 参数域上）表达材质随位置变化，是六维函数 $f(x,\theta_i,\phi_i,\theta_o,\phi_o)$。

    * 动机：真实物体表面因风化、腐蚀，每一点材质都可能不同，"这块是金的、那块是银的"式单一材质表达不了。
    * 与 4D BRDF 一样，因维度太高、精确测量代价太大而很少直接使用。

* **解析模型**

    * > **定义**：用有限参数的解析函数逼近 BRDF，把表达维度从四维压到零维。

    * Phong 模型只需储存一个 shininess（即 alpha）值就能定义一种材质；Blinn-Phong 是更进一步的版本。
    * 储存成本从巨大的方向查表降到几乎为零。

* **PBR metallic/roughness 工作流**

    * > **定义**：当前最经典的解析 PBR 工作流，把 BRDF 拆成漫反射分量 $f_d$ 与镜面反射分量 $f_s$，镜面部分用微表面（microfacet）模型表达。

    * D 项：法线分布函数（normal distribution function），描述法线在微表面下如何变化，通常用 GGX 函数表达。
    * F 项：Fresnel 项，即视角接近掠射时反射增强的菲涅尔效应。
    * G 项：geometry 项，也叫 shadowing-masking，描述微表面下统计意义上的遮挡关系。

* **PBR 四参数**

    * 表达一种 BRDF 通常只需 albedo、metallic、normal、roughness 四个值，可能再补充 $F_0$ 等参数。
    * > **易错点**：⚠️ 这里的 normal 是微表面的法线方向，不是统计意义上的法线。

* **用纹理表达 SVBRDF**

    * 把 albedo、metallic、法线方向、roughness 分别存成一张 2D 图，六维 SVBRDF 就降成了多通道二维纹理——常见的纹理本质上都是 SVBRDF 的表达。
    * 基本四图之外还可能有高度图（height map）、AO 图、各向异性图（anisotropic map）、透明度图等；多通道纹理合起来表达一个完整 PBR 材质。
    * 相比巨大的 SVBRDF 查表，纹理表达 compact 得多，因而大量用于实时渲染。

## 纹理生成路线

* **拍照 + 手工处理**

    * 最直接的获取方式：用相机、手机拍砖墙、地面、皮肤这类局部照片，再处理成材质图。
    * albedo 的本质：把带光照信息的 RGB 图片转化为去掉光照、只保留本来颜色的图。
    * 也可理解为用不同滤镜生成不同纹理图——例如 normal map 滤镜把颜色变成偏蓝的 normal map；还有更直接的材质转换工具，把一张 RGB 图转化为多通道纹理图，本质就是用不同 filter 生成纹理。
    * 最早由 artist 用 Photoshop 完成；这一步非常讲究技巧，并不容易。
    * 墙面这类平面纹理好拍、不用做 UV unwrapping；要把纹理贴到复杂几何上，就必须展开 UV，问题立刻变复杂。

* **physically based 与 physically plausible**

    * > **提示**：physically based 要求严格按物理规律还原材质，需要光照、拍摄位置等信息，非常困难；physically plausible 只要求"看起来合理"。工业界大多数真实渲染场景要的是后者。

* **纹理合成（texture synthesis）**

    * > **定义**：在尺度不变的前提下，把一张小 patch 生成更多带 variation 的 pattern、扩成更大的图；发明可追溯到上世纪 90 年代相机分辨率很低的年代。

    * > **易错点**：⚠️ 纹理合成 ≠ 超分辨。合成不改变尺度——拍一块地砖要的是同尺度铺满地面的更多块砖、带点变化，而不是把一块砖放大往地上贴；超分辨是把图案本身放大。

    * 三大缺点：分辨率低——很多老工作假设实际工作分辨率在 512 左右，现代游戏、电影要 1K、2K，高清材质包要 4K、8K；多数算法有肉眼可见的瑕疵；复杂度与分辨率直接相关，硬上 4K 以上速度极慢。

* **过程式纹理（procedural texture）**

    * > **定义**：把纹理写成一段程序算出来而非存像素；简单例子有棋盘格（checkerboard）、Perlin noise，工业级做法是用计算图（node graph）生成复杂 pattern。

    * node graph 思路：先有多个 noise，用节点 blend 混合、调颜色、调 pattern 分布，最终组成一张与真实照片非常像的图——Blender 的 shader graph 是同一思路。
    * 优点一：可编辑性极强——改 scale、把脏的地方弄得更脏、变干净都是直接调参数。
    * 优点二：分辨率只是一个参数，设成 8K 就能算出 8K，理论上分辨率无穷、有无限尺度的细节。
    * 优点三：高度优化的 node graph system 可交互式设计——放进 3ds Max、Maya 插件实时渲染，不满意立刻改参数得到反馈。
    * 缺点：不好设计——没有专业背景与经验很难搭出这样的计算图；相比之下拍照转换、上网搜素材容易得多。
    * Adobe Substance Painter 的笔刷本身就是一个 procedure（过程式纹理计算图），程序化地在几何模型上"画"，让设计流程相对简易。

| 生成路线 | 优点 | 局限 |
| :--- | :--- | :--- |
| 拍照 + 手工处理 | 素材来自真实世界，最容易获得 | 不保证 physically based；处理讲究技巧；平铺容易有接缝 |
| 纹理合成 | 尺度不变地把小 patch 扩成大图 | 分辨率偏低、有肉眼可见的瑕疵、复杂度随分辨率暴涨 |
| 过程式纹理 | 强可编辑、分辨率理论上无穷、可交互式设计 | 设计门槛高，没有经验很难搭出计算图 |

## AI 时代的纹理工作流

* **深度学习材质获取**

    * 思路：不再需要好相机、好光源加 Photoshop 手工处理，直接用手机拍摄，让深度学习方法学出它物理上应如何正确表达；在渲染系统里重新 render，结果与真实照片非常像。
    * 复杂几何的贴图难题：更多工作直接做几何与纹理的重建，方法包括微分渲染、NeRF。

* **纹理编辑**

    * 普通贴图目前主要靠 Photoshop 逐像素编辑，效率低下；期望的方向是 example-based、text-based 的编辑方法。

* **AI 纹理工作流链条**

    * 典型链条：手机拍照 → crop 小 patch → Photoshop 拼成大图 → tiling 露出接缝 → generative AI 无缝化（seamless）→ Substance Sampler 转换 → PBR 材质图。

    ```text
    手机拍照 --> crop 几个小 patch --> Photoshop 拼成大图 --> tiling 后露出接缝
            --> generative AI 无缝化（seamless） --> Substance Sampler 转换 --> PBR 材质图
    ```

    * 接缝是要害：只有无缝（tileable）纹理才能像砖一样一块块贴满墙面看不出缝，否则就是有缝的马赛克砖；接缝以前靠 Photoshop 逐像素修、非常麻烦，现在交给 generative AI 做无缝处理。

* **text-based 纹理生成**

    * 用 text prompt 获得大量 variation 再从中挑选喜欢的纹理；diffusion model（如 Stable Diffusion）、ControlNet 都能产出各种 2D 平面纹理，还有大量工作直接做 3D、4D 纹理生成。
    * diffusion 得到的纹理再经材质图生成工具转成 PBR 材质图——pixel-based 方法因 AI 工具获得很多可能性，整个 workflow 都在改变。

* **程序空间的生成**

    * 过程式纹理本质是一段程序：node graph 里每个 node 是一个小函数，把输入输出连起来就是程序。
    * 借鉴 program synthesis（程序合成）与 Copilot 式编程辅助的思路，已有大量工作用 GPT、transformer 架构直接生成一段程序来表达计算图、表达程序式纹理——generative AI 不止作用于 pixel space，还能作用于 procedure space、program space。

## 纹理采样与走样

* **纹理访问的本质**

    * > **定义**：纹理是连续材质信号的离散采样（拍照即采样），访问纹理是用 0~1 的小数坐标（uv）去重建原来的连续信号，而不是用整数下标读数组。

    ```text
    连续的真实材质信号 --拍照/采样--> 离散的纹理数组 --访问(uv)--> 重建出的连续信号
    ```

* **走样（aliasing）**

    * 成因：采样频率不够。墙面延伸到远方时，远处 texel 在屏幕上分布得非常密集，说明那边信号频率非常高（screen space 上变化率非常高）；只用点采样——取离得最近的那个样本——就会产生走样的信号。
    * 表现：黑色直线变成锯齿形——中文常把 aliasing 译作"锯齿"；对抗手段即抗锯齿、反走样。
    * 对抗：分辨率固定时只能靠滤波把高频预滤掉，让画面看起来更平滑。
    * 增大采样率的两重限制：性能会下降，且纹理分辨率本身固定、实时做滤波代价高——所以需要把滤波提前的 mipmap。

## Mipmap 与各向异性过滤

* **预处理哲学**

    * 实时渲染的重要哲学：能预处理的东西就预处理，运行时直接访问，为速度考虑。
    * 纹理通常与几何绑定、运行时储存的值基本不变，正好适合提前把滤波做好。

* **mipmap**

    * > **定义**：把一张图做成一串不同等级的预滤波版本：mip 0 是原图，每级先用 filter 滤波（变模糊、分辨率降低），再横、纵各减半，面积变为上一级的 1/4，一直做到 1×1。

    ```text
    1024x1024 --> 512x512 --> 256x256 --> 128x128 --> ... --> 1x1
       mip 0      mip 1      mip 2      mip 3             mip n
    每一级都是上一级先滤波（模糊），再横、纵各减半，面积变为上一级的 1/4
    ```

    * 作用：把各频率段提前滤波好，运行时按需取用；没有 mipmap 的最近邻点采样会让远方满屏锯齿（采样频率太低、重建出的信号是错的）。
    * trilinear mipmap 在更高层级上采样，高频已被丢掉，远处呈光滑过渡；但相比各向异性过滤仍有模糊现象，并非最好。
    * > **提示**：mipmap 是封装好的单元，通常用 API 自动生成；要求纹理尺寸为 2 的幂（每级横纵减半的前提）；整条 mip 链的额外储存开销是原图的 1/3，换来性能与质量提升是值得的。

* **mipmap 层级选择**

    * 规则：采样点信号频率越高，采的层级越大——更高层级正是高频被滤掉、pre-filter 过的版本。
    * 度量：texel 在屏幕空间分布越密集代表频率越高，即 uv 在屏幕空间变化越剧烈，就要采更大层级的 mipmap。

* **ddx 与 ddy**

    * GPU 执行 pixel shading 时以 2×2 quad 为单位并行计算，硬件借此求出屏幕空间梯度 $\partial u/\partial x$、$\partial v/\partial x$、$\partial u/\partial y$、$\partial v/\partial y$，用于估算 mipmap 等级。
    * 经验式估算：把梯度取模再取 log，$\lambda \approx \log_2 \rho$（$\rho$ 为梯度的模）；模越大说明 uv 每变化一个 pixel 的幅度越大、频率越高，要采更深（滤波范围更大）的层级。
    * > **提示**：这是 physically plausible 的经验估计而非精确结果，但大量实验表明视觉上足够合理；各 API 的具体写法不一样。

* **各向异性过滤（anisotropic filtering）**

    * > **定义**：让采样分布遵循屏幕空间采样脚印（椭圆）规则的过滤方法；现在大多数游戏、实时渲染都在使用。

    * 问题根源：mipmap 是正方形、在 uv space 里做 pre-filter，而斜视地面时每个像素理论想 sample 的是椭圆形区域——正对墙面时屏幕上就是完整正方形，mipmap 表现很好；斜地面用 trilinear 各向同性采样，远处全是糊的、重建效果不好。
    * 本质差别：texel space 假设正对着看纹理，view space 里可能在接近 90 度的极倾斜方向看，两者差别很大。
    * 做法：实时地在 uv 坐标周围取不同数量的采样点；样本越多重建越精准、越清晰，计算代价也越高——从最近邻开始加到 2 个、4 个、8 个，质量递增。

## 纹理压缩

### 压缩动机与硬指标

* **显存账本**

    * 一张 4K RGB 贴图展开成数组是 $4096\times4096\times3\,\text{B}\approx 48\,\text{MB}$，加 mip 链乘 $\tfrac{4}{3}$ 约 64 MB；平时磁盘上的 JPEG、PNG 都是压缩过的，直接以数组形式存放根本放不下。
    * HDR 贴图（float 形式）更大：每通道 4 字节，连 mipmap 要占约 1/4 GB。
    * 这还只是单张 RGB 图；实际要存的是 albedo、normal、roughness 等一大堆 multi-channel 贴图的集合，而并非人人都有 12G、24G 显存的卡——不压缩直接展开放 GPU 显存必然吃不消。

* **四条硬指标**

    * 并行友好的随机单点访问：输入 uv 坐标快速返回纹理值，且查询能高度并行化执行——pixel shader 是并行执行的。
    * 解码速度极快：一次采样、尤其滤波时要查很多 texel，不可能解码慢。
    * 访问局部性：解压一个点只动它附近的局部数据；不能访问 $(3,3)$ 还对很远的 $(100,100)$ 做操作计算，否则额外资源占用太大。
    * 可变压缩比：桌面 GPU 显存大（至少 8G、或 24G），要的是质量而不是压得越小越好；移动端显存小、速度慢，需要更大的压缩比。
    * > **结论**：JPEG、PNG 这类（包括小波变换那类）压缩算法难以满足这些要求，纹理压缩需要单独的一类算法。

### 块压缩与 BC1

* **块压缩（block compression）**

    * > **定义**：把一组像素组成的块压缩成固定长度的向量，解压时再由固定长度还原出像素块。

    * 最大优势就是局部性（locality）：解压一个像素不需要访问离它很远的数据。
    * 代表算法众多（如早期的 S3 texture compression，S3TC）；ASTC 是非常常用的一种——把不同数量的像素块都压成 128 bit 的向量，从而得到不同程度的压缩比，通常比特率越高、解出的图越清晰。
    * 直观算例：4×4 块 16 个 texel，未压缩每 texel 16 bit 共 256 bit；压成每 texel 摊 8 bit、块 128 bit，即 2:1 的压缩率。

* **BC1**

    * > **定义**：DirectX 10 里的标准块压缩格式：4×4 的 RGB888 块（16 texel × 3 byte = 48 byte）压成 8 byte，压缩比 6:1。

    ```text
    BC1: 4x4 RGB888 block (16 texels x 3 bytes = 48 bytes) --> 8 bytes, 6:1

    +----------------+----------------+  +------------------------------+
    |     color0     |     color1     |  |  index map: 2 bit per texel  |
    | RGB565, 2 byte | RGB565, 2 byte |  |  16 texels = 32 bit = 4 B    |
    +--------+-------+--------+-------+  |   i00 i01 i02 i03            |
             |                 |         |   i10 i11 i12 i13            |
             v                 v         |   i20 i21 i22 i23            |
      00 -> color0                       |   i30 i31 i32 i33            |
      01 -> color1                       +------------------------------+
      10 -> 2:1 blend(color0, color1)
      11 -> 1:2 blend(color0, color1)
    ```

    * 结构：两个经量化（quantize）的颜色值——24 bit RGB 压成 16 bit RGB565、各占 2 byte——加 16 个 2 bit 颜色索引（每 texel 一个，共 32 bit = 4 byte）。
    * 四色索引：00 → color0；01 → color1；10 → $c_2=\tfrac{2}{3}c_0+\tfrac{1}{3}c_1$；11 → $c_3=\tfrac{1}{3}c_0+\tfrac{2}{3}c_1$——整个数据块里只存在四种颜色，每个 texel 从中选一种。
    * 解码只需访问本块：fetch 出 color0、color1，再 fetch 该 texel 的 2 bit 索引即可，额外计算与储存开销都非常低。
    * BC 家族从 BC1 延续到 BC7，按数据类型区分编码：纯 RGB、带 alpha、单分量（one-component，只有 R 红通道）、双分量（two-component）等，且仍在不断演变。

### 跨平台转码与极限压缩

* **Basis Universal**

    * 问题：BC 适合 desktop、ASTC 适合 mobile，deploy 到不同平台难道要压两份、存两份？
    * 方案：一种纹理数据交换系统——生成一种中间压缩数据，并能快速转码为其他压缩类型；deploy 时只存 .basis 这一种中间格式，运行时再转码成目标平台需要的压缩类型，复用压缩数据、有效节省部署存储量。

* **过程式纹理：压到零维的极限**

    * 类比解析模型把 4D BRDF 压到 0 维：一张 2D 纹理也可以直接从 2D 压到 0 维——过程式纹理只存参数或一段程序，严格来说是 storage-less 的，是最极限的压缩。
    * 但现实中几乎没人直接在 uv 坐标上实时 evaluate 过程式纹理，都是先 bake 成材质图再用，原因有三：
    * 频率与滤波：纹理使用要做 mipmap、pre-filtering 滤掉高频才正常；过程式纹理每个点都是实时计算的，实时 filtering 代价极高，纹理越复杂问题越大。
    * 点查询：纹理压缩的关键是 point query——给 uv 立刻给值；Substance 这类过程式纹理中间很多操作是 filter，filter 无法点查询，要求一个 pixel 必须把整张图 evaluate 出来，等于还是要展开成完整图再去取值，本末倒置。
    * 速度：evaluate 一个 Perlin noise、棋盘格也许还行，复杂过程纹理求值特别特别慢，而渲染需要的是大量 query；在 3ds Max、Maya 实时渲染器里做到 interactive 没问题，游戏要 60 帧、120 帧就很难。
    * > **易错点**：⚠️ 过程式纹理是"最极限的压缩"，却不是"最好用的纹理"——赢在几乎为零的存储，输在无法点查询、无法预滤波、求值慢。

* **改进方向**

    * 解析滤波：把卷积过程用解析（closed-form）形式表达，直接 evaluate 卷积的解析式而非逐点算；但可泛化性不强——只对某种具体数学形式可推导，node graph 这种复杂结构没有任何工具能做解析滤波。
    * 神经网络压缩：已出现用 AI 做纹理压缩的最新研究；判断标准仍是点查询、快速解压这几条——不局限于 block-based 也可以设计自己的压缩算法。

## 着色器优化的动机

* **两条优化路线**

    * 着色器优化分手动优化与自动优化两条路线；自动优化的本质就是把手动那一整套交给机器。

* **shader 越来越大**

    * 3A 大作的 shader 越来越复杂：材质蓝图（Material Blueprint）这类工具节点非常多——取不同材质、做各种转移再全部拼接，展开成代码后非常巨大。
    * 庞大代码要每像素执行一遍，开销非常大；加速每像素这份计算是加速整个游戏绘制的核心中的核心。

* **设备压力同时在涨**

    * fragment shader 每像素执行一次，Deferred Shading 这类管线尤其如此。
    * 分辨率从 iPhone 4 的 960×640 到今天旗舰 Pro 机型已涨不止十倍；刷新率从最开始的 30Hz、60Hz 涨到 90Hz，甚至有设备直接按 120Hz 设置。

## 编译阶段优化

* **编译器已替你做掉一部分**

    * 源码里一段很短的伪代码或 C++ 代码，编译出来是一串非常长的指令；编译时编译器已经做掉一些优化——两段代码有一段多加一个赋值，编译出的指令集可能完全相同。
    * shader 编译器优化主要围绕常量与变量，分以下几类。

* **常量传播**

    * `x = 1` 之后用到 x 的地方，编译器检测到这两处的相关性后，可直接把变量赋值拿掉。

* **常量折叠**

    * `x = y`、再拿 x 给 z 赋值——两步实际是给 z 间接赋同一个值；检测到关联性后可折叠或删减中间变量。

* **复写传播**

    * A 复制到 B、x 先赋值传播到 y、y 再传播到 return 的渐进式传播过程，可被检测并消除。

* **公共子表达式消除**

    * 检测可互相替代的关系式：`x + y` 与 `y + x` 可用同一个 temp 表达；temp×2 与 temp×6 可做算式合并成 `z = temp * 8` 直接 return，省掉复杂 OP。

* **无用代码消除**

    * 算出来完全没被用到的值（dead code）直接省略，较易检测。

* **函数内联**

    * 显式把 subfunction 定义成 inline（Cg function 常见）时，函数体直接展开替换进调用点中间；非常复杂的函数编译器不去展开。

> **提示**：编译器不一定是稳定的——有时帮你优化、有时不管，归根到底要养成良好的代码习惯。

## 执行阶段优化与资源层级

* **两个层面**

    * 代码级优化：把复杂操作简化掉，把分支、循环干掉。
    * 算法级优化：用不同算法实现同一件事、在复杂度上做优化——最体现功力的部分，资深程序员非常在意。

* **无损与有损优化**

    * > **定义**：无损优化——性能提升、画质不降；有损优化——用近似（如查表、用 texture 替代计算）换取性能，接受可控的质量损失。

    * 有损质量的评估：资深程序员可直接分析（debug 场景、根据光的远近判断）；最不济真跑起来看 metrics 的测量结果。
    * 优化前先接触性能分析工具：分清哪些是 ALU 瓶颈、IO 瓶颈、迭代的瓶颈。

* **GPU 存储层级**

    * 优化与硬件高度相关：必须知道 GPU 有几级存储缓冲层级、每级之间的代价。

    ```text
    寄存器 (VGPR)              <- 最快，容量有限
      |
      +-- LDS / shared memory   <- 一个 block 内的 thread 可共享
            |
            +-- cache / global memory(显存)  <- 跨 block，速度比较慢
                  |
                  +-- CPU 内存           <- 跨过去读就特别慢
    ```

    * shader 需要的 memory 在一个 block 的 thread 之间可共享（LDS、shared memory）；global memory 跨 block 可访问但速度比较慢；读 CPU 侧的数据就特别慢。

## 手动优化基本准则

* **清楚代码消耗的资源**

    * VGPR（向量寄存器）容量有限：最好能少用就少用，要用就不要超出上限；编译到中间代码后会动态显示每一行产生的寄存器消耗。
    * 共享内存（LDS、shared memory）用量可通过 profile 拿到；再往外 L1/L2 cache 是更慢的缓冲。
    * 以上都超了，最后就会拿显存来造临时寄存器使用——应尽量避免。

* **减少 IO**

    * 内存 IO、显存、寄存器相关的读写能减就减，尤其 CPU 内存到显存那条路要非常注意。

* **有序读写**

    * 规则：一个 block 里相邻的 thread、相邻的 pixel 读显存、读内存时，要一整块一整块地读；交叉、中间隔一个 stride 的读法不行；一般对齐到 128 给一个 stride，能较好读出。
    * 现在的硬件大多已优化，但老版本、某些硬件上尤其要注意读写是有序的。

    * > **易错点**：⚠️ 完全随机的读写基本会把整个程序卡崩。

* **减少循环和分支**

    * 代码的循环、`if/else` 分支能少用就少用。

* **少用复杂 OP**

    * `sin`、`cos` 这类复杂 OP 由特殊指令集、特殊计算单元实现，不能用简单 ALU 完成，要尽量避免。
    * 替代：数值近似——把常用数值范围先算好做成表，运行时查表插值取结果；在不需要非常高精度时完全够用。

## 常用优化技巧

* **把计算移到顶点着色器**

    * fragment/pixel shader 每像素算一次，而球体这类模型的顶点数远低于像素数；在顶点上把颜色算好传给 fragment shader 可省下很大一块计算——Gouraud shading 是最直接的例子。
    * UV 坐标变换这类新坐标计算、切线变换这些不那么高频的计算，都可移到指定着色器上，对画质不会产生太大影响。

* **用预计算**

    * 查表思想：复杂计算提前算出来存储。noise 用数值方法算很耗时，预生成后运行时只做一次 UV 采样即可得到较好的 noise——这在 sampling 时很重要。
    * Ambient Occlusion 本质是自遮挡、与模型自身强相关、接近静态，可预计算下来，免去实时采样。
    * 更夸张的：整个 shading 的结果都可以预计算烘培成纹理——一般用在背景、静态光源上，整个场景房间只需一次纹理读取直接给出颜色，计算量相当低。

* **查表与计算互换**

    * 正向：用存表省计算；反向：PBR 里用 preintegrated（预积分）相关量与 NdotV 去采样一张 LUT 纹理会多一次访存，也可反过来用数值函数逼近这张表、直接把结果算出来。
    * 选择标准：想减小计算、访存带宽还比较宽裕就查表；反过来就换成算式。

* **确定的数值写成常数**

    * 数值确定就直接给到编译器，它会帮你提前处理；π、half π 这类常用值直接 define 好，不要运行时计算。
    * 不要放太多 uniform、数值确定就不要自作主张包太多变量；这与编译器优化直接相关，仍是养成良好代码习惯的问题。

* **用低精度数据类型**

    * shader 支持 float、half 等类型：HDR、UV 及一些确定可控的数值，半精度其实够；颜色这类用 fixed 也够；这在 mobile device 上会比较敏感。

* **优先做标量计算**

    * 两个标量乘一个向量：先把标量全部乘起来再乘向量，最后只有 3 个分量的乘法；反过来先标量×向量（展开成 3 次乘法）、再乘另一标量（又是 3 次乘法），计算量加倍。
    * 原则：优先把能合并的、维度比较低的计算合并掉。

* **避免分支**

    * GPU 是 SIMD（Single Instruction Multiple Data）：指令控制器非常少、数据通道多，如 32 个 thread 共享一条指令流；若 16 个 thread 产生分支，分支里和分支外两个东西都分别执行了一遍，白算。
    * 替代：用并行 OP 替代 if/else——`if (x == y)` 可以纯粹用数值方法：算 `x - y`，相等就返回 0，利用这一点直接用并行运算替代判断；总体减少分支发散的数量。

* **合并 shader、减少 pass**

    * 从软件工程角度 shader 各写各的更干净；但实机跑时要尽量把一些 shader 合并起来、降低它们之间的传输、减少 pass 数量，也就是减少 DC 的数量。

## 着色器的 LOD

* **着色器 LOD 原理**

    * 与 mesh 的 LOD 同理：近的地方用特效更强、贴图更复杂的 shader，远的地方用简化掉的 shader——这是可以规范化的常用手段（其余技巧更多靠个人修行）。

* **按光照模型 LOD**

    * LOD0、LOD1、LOD2 用不同光照模型做同一件事：GGX 最复杂、最真实、也最慢 → 换 Blinn-Phong 这类更简单的模型 → 更远处 micro-facet、次表面散射这些特征直接不要 → 再远用 uniform 采样给一个简单颜色 → 最远直接用预计算好的颜色。

* **按光照成分 LOD**

    * 把最终光照结果拆成不同成分做 LOD：最近处 diffuse、specular 全部加上 → 稍远去掉 specular 只留 diffuse → 更远处 indirect light 去掉、直接光这些也拿掉。

* **烘培 LOD**

    * 把颜色提前烘进 texture；烘培跟着几何走——几何做 LOD 时烘培自动简化，烘出的 texture 自带 mipmap，随距离自动过滤。

## 自动优化框架

* **为什么自动化**

    * 手动优化高度依赖经验：怎么调代码、怎么评估修改后的效果、怎么平衡质量与速度都要经验，不停 try 各种 tip 枯燥繁琐。
    * 自动优化就是让计算机自动调整代码、自动评估调整后的质量、自动找质量与速度的平衡。

* **框架流水线**

    * 输入不止 shader code：还要优化目标场景的 mesh 与 per-uniform 参数（如光照）——shader code 产生的结果与场景和参数相关。
    * 优化器尝试产生不同优化后的代码并评估质量——把它们渲出来是最蠢但效果最好的评估办法。

    ```text
    input:  shader code + mesh + uniforms
      -> optimizer: 尝试各种简化 -> 产生大量 shader variant
      -> evaluate:  渲出来 + 跑起来（遍历 configuration x 材质 x camera）
      -> recurse:   基于当前最优继续简化，循环往复
      -> output:    Pareto front (error x time) -> 选 LOD / 优化设置
    ```

* **Pareto 前沿**

    * 横轴误差、纵轴时间，做时间与误差的平衡——要落在 Pareto 线上，沿这条线挑所需的 LOD 或优化设置。

    ```text
     time
      ^
      |  o
      |   o
      |    o      x        x = 被支配的点：又慢、误差又大
      |     o    <- Pareto front：沿这条线挑 LOD / 优化设置
      |      o
      |        o
      |          o
      +-----------------------------> error
    ```

    * 实际用法：给误差上限——在未超上限的变种里找时间最优的点；或反过来给时间上限——找误差最低的。

* **两大研究内容**

    * 一类研究怎样优化着色、产生这些 variants；另一类研究怎样评估误差、更好地加速 Pareto front 的寻找。

## 自动简化的实现与规则

* **AST + 依赖图**

    * 表达式先解析成 parse tree，再生成更抽象、更简洁的抽象语法树（abstract syntax tree，AST）；实际用 glslang、DirectX compiler 这类工具自动生成。
    * 修改靠 AST 加内部相互依赖的依赖图一起做：由依赖图找出不再需要的东西，把对应 code 连同其上游一起处理掉，产生新代码。
    * 新代码先做语法检查；有问题就直接丢进 shader 编译器编译，能编过就没问题。

* **简化的对象与迭代**

    * 自动简化就是替换 shader 里某一个变量——一般是纹理，也可能是变量或随机 sample 的变量：尝试拿掉一个输入，其前面相关的那一行依赖也随之拿掉，产生一个 shader variant。
    * 评估：把变种编译出来放到它的场景里跑，遍历不同 configuration、材质、camera 估计质量得分，同时评估 performance（直接跑）。
    * 迭代：某步简化不错就继续尝试其他简化、一行行往下处理再评估；最暴力的迭代甚至直接拿 ambient 当输出——整个空间多评估几遍。

* **常见简化规则**

    * 表达式简化：最常见也最有效——例如 normalize 表达式里拿掉 ldir 或另一个 dir，就产生不同变种让机器自动评估。
    * 循环缩减：收敛类、迭代算法（找最优、递归最优这类）可以降低循环次数。
    * 表达式替换：把 $N \cdot L$ 替换成 $N \cdot H$（H 是 half vector 半程向量，N 表达物体表面的 normal）也能产生很多变种。
    * 计算上移：把 fragment 里的代码从 fragment shader 上移到 vertex shader——顶点上算出三个顶点的值，每个 pixel 拿自己的重心坐标对顶点值做插值，fragment 只负责插值；有 tessellation 时可移到 tessellation shader，把原始三角面片细分成很多细小三角面片再求值，逼近粒度更细。
    * 常量替换：某变量在当前 configuration 下变化 smooth、变化不大，就用常量替代；典型如背景这类离得很远的物体，跟视线方向相关的变量基本方向无关，最后都可能被常量改掉。
    * 高阶逼近：用 Bezier 曲面等逼近函数——线性逼近的进化版，可做非线性、高阶的 baking。

## 搜索与评估加速

* **variant 空间问题**

    * variants 可能非常多有上万个，不能盲搜、暴力搜：现代 shader 很长，combination 太多、空间太大。
    * genetic programming：某父节点产生的 variant 质量、error 都比较好且指令数小，就基于它进一步简化——优秀的 variant 产生更多变种（父子关系）。

* **评估为何慢**

    * 评估一个变种本身很耗时：要各种各样的视角、各种各样的性能。
    * 评估规则也不一样：只简单评估颜色用一个误差指标就行；要评估能耗就复杂得多；有时还要比更多指标，实际使用时确定——没有一个所谓最优的东西。

* **策略一：贪心搜索**

    * 从最原始的 shader 开始搜它的一个最优子节点，再沿着这个方向用贪心方法搜下一个、下一个。
    * 本质是 NP-hard 问题，贪心逼近肯定会漏，但能在时间上做时间和质量的平衡。

* **策略二：不真跑的时间估计**

    * 不直接评估着色器的运行时间（省掉 compile 甚至实际 run 的时间），而是根据统计数据，按指令类型和操作数做加权平均来估计；会带来一些误差。

* **误差缓存**

    * 把某次表达式简化产生了多少误差的"操作-误差值"做成 table 存起来；其他 shader variant 再碰到同样操作、删减同样节点时，直接拿缓冲代替最真实的 run。

## 运行时实时优化

* **动机**

    * 前述 shader 简化方法都是离线的，而游戏过程中每一帧、每个场景都在实时变化——需要边变化边优化 shader。

* **离线聚类 + 运行时匹配**

    * 离线：从原始 shader code 产生大量 shader variants，按 shader 之间的相似度做 clustering，把整个优化空间变得很小，每一簇里留下代表。
    * 运行时：不再搜索，直接拿当前帧状态在简化后的小空间里按 shader 特征做匹配、找最优解，达到实时的 shader 优化。

    ```text
    offline:  shader code -> 生成大量 variants -> 按相似度 clustering -> 很小的空间
    runtime:  当前帧状态   -> 在小空间里做匹配  -> 找最优解           -> 实时优化
    ```

## 机器学习着色器简化

* **Shader Transformer**

    * 思路：语言模型做序列处理这套能力很强，用 transformer 结构直接解读 shader code，让网络来估计 shader 的质量。
    * 结构：输入 shader code 与场景 configuration，经过一系列 transformer 输出一个可自由删减的表达；节点打掉之后再 decode 回来，就得到简化后的 shader。
    * 本质：把 shader code 的编码映射到 latent 空间里的一个表示。

* **效果**

    * 人物模型、皮肤表达模型这些例子上，可自动得到不同的 LOD 档位。
    * 多目标（既优化时间又优化误差）场景画出误差-时间的空间，同样可以在其中找 Pareto front，实现多目标优化。
