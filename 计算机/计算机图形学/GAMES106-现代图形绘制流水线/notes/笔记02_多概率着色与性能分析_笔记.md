# 多概率着色与性能分析

## 计算频率全景

   * **单频率认知的局限**

       * 「一顶点执行一次 vertex shader、一像素执行一次 pixel shader」是 DX9 时代的认知，只对一小半：从输入网格开始就有曲面细分，过光栅化后样本分成可见性样本和着色样本，进了可编程着色器，各种效果的计算频率、缓存频率也都不一样。

   * **几何管线**

       * > **定义**：光栅化之前的全部阶段统称几何管线，这一路上的所有改动改的都是几何；光栅化之后的一路，改的都是着色的粒度。

       * 几何管线主干为 IA → VS → TCS/HS → 固定功能细分器 → DS → GS，现代路径是 Task/Amplification → Mesh Shader。

       * 着色管线包含着色采样和着色器两块，核心问题是 sample rate 应该怎么做。

```text
输入网格
   │
   ├─ IA → VS → TCS/HS → 固定功能细分器 → DS → GS      （几何管线）
   │        └──── 现代: Task/Amplification → Mesh Shader ┘
   ▼
光栅化
   │
   ├─ 可见性样本 (深度/覆盖, MSAA, 亚像素粒度)
   ├─ 着色样本   (像素 → quad → tile, VRS)
   ▼
像素着色(PS) → 样本写入 → resolve → 输出
```

   * **计算频率与着色频率的分工**

       * 计算频率决定的是性能和调度；着色频率解决的是图像质量——怎么利用计算频率和着色质量之间的平衡做优化，是多频率着色的核心问题。

       * 几何过于复杂、像素过多、抗锯齿，归根结底都是性能问题，背后永远是画面质量和性能之间的平衡；正确理解画面信号是什么样的、为什么出这种问题，才能做出自己的优化选择。

   * **着色粒度谱系**

       * 由细到粗依次为：MSAA 可见性样本（亚像素，每像素 N 个深度/覆盖样本）→ 像素（PS 执行粒度，每三角形每像素最多一次）→ quad（2×2，ddx/ddy 差分的粒度）→ tile（VRS，如 2×2 像素才 shade 一次、其余插值）→ 物体/材质 tag（per-draw 直接指定整个物体的 rate）。

## REYES 与 split and dice

   * **REYES（Render Everything You Ever Saw）**

       * > **定义**：1987 年为影视制作服务的绘制管线；当年制作用的是参数曲面，大银幕上人物必须连续平滑，只用三角形会看出很明显的棱角——Catmull-Clark 细分这类方法最初就是为生成平滑曲面准备的。

       * 架构叫 split and dice，分两步走。

       * split：把一大块输入的参数图元切成更小的参数图元，切到适合计算机处理的粒度。

       * dice：把参数曲面细分成三角形、四边形这类更小的多边形，每个多边形大概一个像素大小。

       * 有了这些微多边形后，每个顶点做 displacement 把更多的几何细节加上去；着色也在顶点上做——求交、光照计算都在顶点上完成。

       * sample：像素颜色由顶点着色结果插值得到。

       * 现代管线里很多概念就是从这里逐渐衍生出来的——实时绘制最终还是希望尽量逼近影视的质量效果。

## 几何管线的演化

   * **DX9：只有 VS 与 PS**

       * 只有 vertex shader 和 pixel shader 两个可编程阶段，几何非常受限——基本上 input 是什么，output 才是什么。

   * **DX10：geometry shader（GS）**

       * 提供了相对非常自由的几何管线构造，但其实不算成功，因为太过自由。

   * **DX11：曲面细分**

       * Vulkan 里叫 tessellation control shader / tessellation evaluation shader，概念很接近 REYES 的 split and dice，就是不断细分的架构。

   * **compute shader 与 GPU driven pipeline**

       * compute shader 类似 CUDA 这种通用计算，推出之后大家非常喜欢这个东西，于是引入了 GPU driven pipeline。

   * **DX12：mesh shading**

       * 为特化的需求引入的架构：task shader（amplification shader）加 mesh shader。

   * **需求驱动**

       * 实时管线本身的发展是受需求驱动的：需要越来越快、引擎和游戏里常用什么技术，就需要什么样的东西。

## 输入装配与顶点着色

   * **input assembly（IA）**

       * > **定义**：几何管线的第一步，只需定义好拓扑并组织顶点输入数据。

       * 拓扑最常用 triangle list，有些特殊需要才用 line、strip、fan。

       * 顶点数据最简单可以只提供 vertex buffer，常用的一般还会提供 index buffer——双层索引，GPU 从 index buffer 里找到对应顶点的数据。

       * 做 instancing 时还会有 instance buffer；这些都通过 semantics、vertex id、instance id 来使用——id 是管线定义好的顶点/实例顺序，顺序本身就可以拿来做事，比如想做顶点动画，vertex id 就能用上。

   * **顶点着色器（vertex shader，VS）**

       * GPU 执行时按顶点序号顺序来：三角形 0、1、2 三个顶点，先执行 0 号顶点的 VS、写入 vertex output buffer，然后 1 号、2 号，按顺序组队；在 VS 执行这个时刻其实还没有 primitive 的概念。

       * 共享顶点靠顶点 cache：GPU 执行过的顶点结果留着，不用重新再执行一遍 VS 才能拿到 vertex output。

       * VS 一个最大的问题：只能在 CPU 端给定几何——CPU 端输入什么，吐出来的就是什么，灵活性大大降低；什么东西都在 CPU 上做性能扛不太住，可变的东西也没法编起来。

## 几何着色器

   * **geometry shader（GS）**

       * > **定义**：DX10 引入、能非常自由修改几何的阶段——一个三角形进来，可以重新构造出一个 normal，或者构造出多个三角形，甚至直接做细分都是没问题的，比如通过 GS 给每个顶点输出法线的可视化。

       * 存储量限制：一个 shader 里最多输出 1024 个三角形这样的数据量。

       * 失败根源：一个三角形进来可能输出十个、也可能输出五个，甚至拓扑结构都改变了——GPU 整个是大量吞吐的机器，这样自由之后反而不知道怎么调度，速度提不起来；而且因为预先不知道会生成多少个，调度也没法做。

       * 结局：geometry shader 的推出其实算一个失败，用到的地方相对少很多，最主要的原因就是没速度；它的价值在于输入时能知道 primitive、知道拓扑长什么样，作为通往细分管线的过渡。

## 曲面细分

   * **三段式流程**

       * 先经 tessellation control shader（DX 里叫 hull shader）设置细分参数（tessellation factor）——以三角形举例，三条边各有一个边的细分参数，中间还有一个内部的细分数；再经硬件的固定功能曲面细分器（fixed function tessellator）生成更多的顶点，比如原来是三个点、现在变成六个点；每个点再去执行 tessellation evaluation shader（DX 里叫 domain shader），它做的事情类似 VS：点的位置、属性都要重新通过插值算出来——一个三角形就此变成六个三角形。

       * input assembler 的拓扑要相应从三角形改成 patch list——patch 就是 REYES 里对参数曲面的称呼；除了普通的三角形细分，也可以在 patch 上做 parametric 曲面细分，只是实践中不怎么见得到。

   * **细分参数的两类因子**

       * inner factor：三角形内部要细分成多少，控制好中心部分的细分。

       * edge factor：每条边分裂成几段——它主要控制的是你和邻近三角形怎么匹配。

       * 每条边、每个面都可以设不同的 factor，这就提供了控制三角形细分 pattern 的自由度——比如做地形的时候，可以做出类似 LOD 的效果。

   * **执行频率**

       * tessellation factor 是按面、按边各设定一次的；tessellation control shader 基本上是每个 patch 执行一次。

       * DX 提供了每个 patch 一次的入口（hull shader 里的 patch constant 部分），专门去控制每一个 tess factor；OpenGL 的 TCS 是按输出控制点跑的，每个点都要把顶点属性复制一遍，这样后面的 domain shader 里才能用到——shader 里会有 `gl_InvocationID == 0` 这样的写法，就是为了让其中一个 invocation 去设置 tess factor。

   * **典型用途**

       * 最简单常用的是 PN triangles，能得到更平滑的几何——但 PN triangle 在真正的游戏引擎里用得反而不那么多；用得多的是增加几何细节的 displacement mapping，还有地形。

       * 即便到现在，因为有了更好的 compute shader，很多时候顶点 buffer、几何可以直接用 compute 生成出来，tessellation 的用武之地也在被蚕食。

## 细分裂缝的成因与处理

   * **来源一：edge factor 不匹配**

       * 两个相邻三角形，左边那条共享边细分了两次（边上有三个顶点），右边细分参数还是 1、没细分，交界处就出现 T-joints，观察时会产生很细微的裂缝。

       * > **易错点**：相邻面片的共享边必须使用相互匹配的 edge tessellation factor，否则交界处会出现 T-joints 和细微裂缝。

   * **来源二：displacement 不匹配**

       * 细分经常和顶点位移（沿 normal 方向做偏移）一起用：原来两个点在未细分三角形上位置一样，细分之后各自沿各自的 normal、各自的偏移量移动，如果 normal 或者偏移不一致，原本看起来没问题的 mesh 就有裂缝了。

   * **处理核心：用共享的、一致的顶点数据**

       * 面法线可用 `cross(AB, AC)` 算出，但 mesh 里 B 这个点往往被 ABC、BCD 多个三角形共享；导入时如果把 B 拆成 B1（属于 ABC）和 B2（属于 BCD）各自算 normal，首先光照上就不平——normal 不一致光照就不平滑；更关键的是后面做 displacement 时两个点各移各的，B、C 之间就会出现 crack。

       * 导入时如果确认 B、C 是共享点，就把相邻面片的法线做平均再 normalize——按面积加权还是怎么处理都行——保证两点使用同样的 normal 数据，这就是 smooth vertex normal；这样细分位移的时候两边挪的位置一样就没问题了，前提是它们逻辑上真的属于共享顶点。

       * > **易错点**：光滑组标记的位置一定不能共享——美术用光滑组保证这个位置的 normal 必须不一样，虽然位置上连续、normal 就各是各的（如 cube 每个面的法线不同）；这种情况就接受不平滑，走拆开的路线。

       * 正常 mesh 在 UV 边界被拆开时，position 一样、normal 甚至几何都一样，但 UV 不一样——采样 displacement 贴图时会踩到不同的地方去，位移照样对不上；这时候要生成 additional（duplicated）vertex：这块要做细分，就强制保证参与细分的这些顶点的所有属性完全一样。

       * 即便做了这些事情，实践中有时候还是会遇到浮点精度的问题。

   * **检查清单**

       * edge factor 是不是一致——共享边用同样的细分参数。

       * 顶点数据是不是一致——position 之外，normal 和 UV 是不是一致；全部一致才能保证 tessellation 出来的结果没有 crack。

## 网格着色

   * **曲面细分的固定模式问题**

       * tessellation 最大的问题是 fixed pattern：虽然可以调整——fractional odd 之类的参数——但本质上差别不大，比如一个三角形拆下去会固定变成六个小三角形，整个几何规模增长的力度还是很大。

   * **compute 时代的 cluster 并发**

       * DX11 后期的 compute shader（类似 CUDA 的通用计算）让自由度一下大了很多：把 mesh 切割成很多小的 cluster——比如 64 个或 128 个三角形——以 cluster 的粒度做并发，就可以在上面做剔除（culling）这些事情；compute 不光可以做剔除，还可以生成更多的 mesh。

   * **mesh shading（DX12）**

       * task（amplification）shader 可以调度更多的任务；有了更多任务之后，mesh shader 里就可以建立更多的三角形出来——生成三角形、剔除三角形都 OK。

## 几何阶段执行对比

| 阶段 | 执行粒度 | 知道拓扑吗 | 硬件表现 |
| :--- | :--- | :--- | :--- |
| vertex shader | 每顶点一次 | 不知道（无 connectivity） | 有顶点 cache，共享顶点不重复执行 |
| geometry shader | 每 primitive 一次 | 知道输入 primitive 的拓扑 | 输出数量可变，调度不动，速度上不去 |
| 曲面细分 | 固定功能细分器 + 两个 shader | patch 级 | pattern 固定但快，细分在片上，有 locality 加速 |
| mesh shader | compute 粒度（task + mesh） | cluster 级 | 自由度高，可剔除、可生成三角形 |

   * 曲面细分的整个顶点输出处理在片上（on-chip）完成，实测相比直接从 vertex buffer 拿顶点，还能获得一些 locality 上的加速。

   * 自由度越高，程序员能做的事情就越多——但最核心的还是找到适合的应用：需要做什么样的应用，就选什么样的事情。

## 像素着色的执行单位

   * **quad 执行模型**

       * > **定义**：pixel shader 的执行以 quad（2×2 像素）为单位——4×4 的像素块上画一个三角形，三角形尖部可能只触及两个像素的中心点，但实际上整个 quad 的四个像素都会执行 PS。

       * 原因是差分：`ddx`、`ddy` 这类指令需要跟邻近的像素做对比，才能知道梯度是什么样的——也就是这个三角形画在屏幕上属性的变化率。

       * 这个梯度最实用、最常见的用途是选贴图的 mip（mipmap 层级）；有了 mip 之后才能做纹理的抗锯齿，同时也有更好的 locality。

       * 写入只发生在 coverage 覆盖的部分：只有像素中心被覆盖的像素才会写入（还要过深度测试这些）——这就引出普通光栅化一个大的问题：本来好好的一个三角形，边界变成了奇怪的形状——锯齿。

---

## MSAA

   * **MSAA（multi-sample anti-aliasing）**

       * > **定义**：核心理念就是名字里的多个样本点；多出来的样本叫可见性样本，可简单理解为 depth 可见性，只负责判断覆盖与深度；真正算颜色的着色样本默认就是像素中心，一个像素只算一次。

       * 4x MSAA 的一个像素里会有固定的 4 个样本点，摆成一个固定的 pattern；多了这些可见性样本，就能近似知道三角形 cover 了这个像素多少比例的面积。

       * 所有 shading 的 API 都会提供 coverage 这个 semantics，告诉你哪个样本点被 cover 了、哪个没有被。

       * 计算 shading 还是在像素中心来算、算一次颜色；但像素中心可能落在 primitive 外面，这时候整个属性值会外差（extrapolate）。

       * > **提示**：像素中心在 primitive 外时，默认插值会外差；在 fragment shader 里把属性定义成 centroid 插值，可以保证插值一定落在 primitive 内部——一般情况下直接用默认的也没问题。

       * 执行上的连带效果：某个像素只有样本点被 cover（像素中心没被 cover），这个像素现在也要执行 PS 了；这个像素一执行，它所在的 quad 整个都要执行——之前不执行的那几个像素现在也执行了。

       * 写入方式：在像素中心算出颜色 c，也知道这个颜色对应的样本覆盖比例，按比例把颜色分摊到这个像素的各个样本上；对比普通光栅化「盖住中心才写入」的粗糙结构，边界的梯度会更连续一点——单看边缘，效果就是抗锯齿。

   * **代价账（4×4 像素块画一个三角形）**

       * 深度样本：原来 16 个；4x MSAA 下就是 16×4=64 个，深度测试的成本直接增加。

       * pixel shader 执行次数：之前是 12 次（3 个 quad）；带 MSAA 后，原来不执行的像素因为样本被 cover 也要执行，quad 变多，PS 执行 16 次。

       * 写入的颜色个数：之前是 7 个，现在变成 10 个。

       * > **易错点**：MSAA 省的是着色，不是深度——4x MSAA 的深度测试样本是 4 倍；而且细碎三角形在边界处会让 PS 执行次数不降反升。

   * **与直接提高分辨率的对比**

       * MSAA 的核心优势是减少了 pixel shader 的执行数量：一个像素对每个三角形最多只执行一次 PS，不管这个三角形盖住了多少个样本。

       * 例外：如果多个三角形同时部分覆盖同一个像素——尤其在三角形边界处、很多细碎三角形的情况下——每个三角形都要为这个像素执行一次 PS，整个像素执行数量还是会变多。

       * 接口：Vulkan 里通过 `VkPipelineMultisampleStateCreateInfo` 设定样本数，2 倍、4 倍或者更多倍——一般硬件到 8 倍左右就结束了。

## 采样控制与 resolve

   * **sample shading 与 sample mask**

       * sample shading：MSAA 有 4 个可见性样本，但默认只 shade 一次；也可以做到 per-sample shading——4 个 depth sample 就执行 4 次 shading，或者按一定比例做（比如 4 个样本最多执行 2 次），用 `minSampleShading` 这类参数控制。

       * sample mask：4 倍 MSAA 一定产生 4 个样本，但可以通过这个 mask 把一些可见性样本剔除掉、不写入。

   * **resolve**

       * > **定义**：把多个样本合并成一个像素最终结果的步骤——有多个样本，最终要输出一个抗锯齿的结果。

       * 合并方式：最普通的就是 average——按覆盖比例分摊本质上就是平均；还会有 min/max sample，比如对 depth，可能需要取最深的或最远的 depth；也可以全部默认使用 sample 0。

       * 硬件自动 resolve：绑一张 4x MS 的 attachment，再提供一张普通的（1x）buffer 作为 resolve attachment，硬件会自动把结果做好写进去。

       * 手动 resolve：调 `vkCmdResolveImage` 这条指令，输入一张 MSAA buffer，得到一张普通纹理。

       * Vulkan 1.0、1.2、1.3 自由度越来越多：可以直接在 shader 里读 texture2DMS——MSAA 版本的 texture2D——自己做自己的事情，比如随意丢弃某些样本，或者不做普通的平均 resolve、自己定制。

## 可变速率着色

   * **变量着色率（variable rate shading，VRS）**

       * > **定义**：比像素更大的着色粒度——分辨率涨得太快，需要少画一些像素；2x2 的 shading rate 意思是每 2×2 个像素才执行一次 shading，其他像素通过插值得到，代价就是画面会更模糊。

       * 设置方式一 per-draw basis：这个物体本身就没那么精细，给它打个 tag，材质上直接标 2x2 shading，执行数量就少一点。

       * 设置方式二 shading rate image：物体级的控制有时比较麻烦，那就对整个屏幕根据内容来做——引擎提供接口，输入一张 shading rate image，每个 texel 对应一个 16×16 的 tile，在图里标明每个 tile 应该用什么样的 rate，硬件就会自动在这个区域按 2x2、那个区域按别的 rate 来做。

   * **static 与 adaptive**

       * static shading rate：场景固定，这块区域就该用高的、那块用低的，直接标好；最典型的应用是利用人的视觉——人一般更关注画面中心的细节，提高中间的 shading rate、降低旁边的；这种在 VR 里用得比较多，一是因为有透镜，二是 VR 里整个转动的幅度也不大、注意力非常 focus 在中心。

       * adaptive shading rate：根据场景内容动态做。

       * variable shading rate 也可以和 MSAA 结合。

       * adaptive 之后有个问题：shading rate 比较低的地方，画面质量怎么让它损失得少一点。

## 信号频率判断

   * **几何信号**

       * > **定义**：几何信号的高频 = 法线变化多、几何细节多（高曲率区域）；低频 = 平滑、平坦或光滑的区域。简单判定：一个点的曲率比较高，就认为这里细节比较多。

       * 几何的多频率其实不强调「主动优化」，但这种频率思想用在了各个方向：比如做简化——把高频的区域保留下来，很平的地方就不用那么多三角形；再比如生成 displacement map、normal map——把几何里高频的细节部分烘到贴图上，剩下的 base mesh 是低频的，绘制的时候再从贴图把高密度 mesh 中的细节恢复出来。

   * **着色信号**

       * > **定义**：着色信号的高频 = 光照变化剧烈、或纹理细节丰富的地方（中高频）；低频 = 光照平缓、纹理比较一致、而且比较远的地方。

## 内容自适应着色率

   * **误差推导（论文 "Visually Lossless Content and Motion Adaptive Shading in Games"）**

       * 第一步：假设做半分辨率的采样，通过推导可以算出——全分辨率和半分辨率之间的误差，约等于像素之间的差别（梯度）。

       * 第二步：有了半分辨率这层推导之后，再通过频谱分析加预计算，可以得到半分辨率和 1/4 分辨率之间的误差关系——频谱分析发现，1/4 分辨率的结果可以完全通过半分辨率的计算近似得到，中间那个系数 k 是一个常量、或者预计算就能得到的值。

       * $$E_{1/2} \approx \left|\Delta_{\text{pixel}}\right|, \qquad E_{1/4} \approx k \cdot E_{1/2}$$

       * 其中 $\Delta_{\text{pixel}}$ 是相邻像素之间的差分（梯度）。

       * 判据闭环：运行时拿到着色结果的差分（gradient——可简单理解为像素之间的差别），就知道要把误差降低到某个程度以下，这块区域该用全分辨率、半分辨率还是 1/4 分辨率。

   * **《Call of Duty》2020 年的实战方案**

       * 未必要用 VRS 硬件：variable rate shading 这个思想不一定非要 VRS 硬件实现——MSAA 也可以理解为对 shading rate 的分解，因为它把 shading 分成了 shading rate 和 visibility rate 两个 rate，所以他们用 MSAA 来做可变 shading rate。

       * 更在乎 temporal 的影响：不只看画面本身的空间梯度，更看一帧一帧之间的梯度——因为画面里除了运动（motion），还有移动带来的遮挡变化（disocclusion），而且 TAA 用得非常多、各帧之间还有 jitter；所以他们会保留更多帧，用多帧之间的差别算出像素间的 gradient，再用这个差别指导 shading rate 应该怎么做。

## 逐项着色率

   * **matte rate**

       * > **定义**：把着色信号拆得更细——拆到 shader 内部看每一项的频率，按着色项（diffuse / shadow / specular）分别指定不同的着色率。

       * diffuse：normal 变化不大（比如一个平面上的 diffuse）一般认为是低频；normal 变化很大就是高频。

       * shadow：半影区刚好是明暗交界处、频率变化非常大，是高频；其他地方是低频。

       * specular：lobe 之内高光很强、数值变化很大，是高频；lobe 之外的区域变化反而没那么大。

   * **学术进展**

       * 代表工作：何勇 2014 年做的 adaptive multi-rate shading——比像素级怎么变频率更进一步：shader 的某些部分（某些 term）也可以在不同的地方以不同的频率执行；属于比较新的学术界进展、更新的硬件方向。

       * 同一思想的应用还有：coarse pixel shading 这类做法（跟 VRS 思路类似）、object 空间的 matte reshading、2014 年前后在 MSAA 框架下研究 matte rate shading 的工作。

## 多频率思想的应用

   * **半分辨率惯例**

       * AO 本身频率不高，低频的地方用半分辨率算，再通过模糊处理——这就是这个思想的直接应用；GI 的时候用半分辨率，同理。

   * **计算上移**

       * 像素多了之后，所有代价基本上都是像素代价；如果你这个计算频率很低——比如 diffuse 之类的本身频率就不高——把本来写在 pixel shader 里的计算挪到顶点或者 tessellation 里去算，像素上通过插值得到，也是一种正经做法。

## 帧率与性能目标

   * **帧率即性能**

       * 在绘制里，高性能最简单的描述其实就是帧率：高帧率意味着更流畅的画面、更低的延迟——比如玩 FPS 游戏，你的视角会比别人更流畅，开枪触发也更准确。

   * **帧率目标**

       * > **定义**：主机一般 60fps 就差不多；手机 30fps 也能玩；VR 因为对延迟的要求更高，得奔着 90fps 去。

   * **平稳性**

       * 帧率除了本身要高，平稳性也有要求：不同视角下都要稳定达到目标帧率，不能一帧高一帧低。

## CPU 与 GPU 的分工

   * **架构差异**

       * CPU 是 cache 大、控制单元多，适合写很复杂的 C++ 逻辑；GPU 则是为吞吐量而生的，天生就是干高并发、处理大量数据的——架构上的这种差异决定了写程序时要同时兼顾两头，CPU 和 GPU 得很好地协作才能写出高性能的代码。

   * **CPU 端第一件事：成批提交**

       * 把绘制数据按批次准备好、成批地交给 GPU：GPU 一次可能能吃几千个任务，你要是一次只慢吞吞地给一点，就会造成 GPU 等待。

   * **CPU 端第二件事：并行化**

       * CPU 虽然没有 GPU 那么多核、那么多线程，但核数一直在涨：现代图形 API 怎么做并行的提交——command list 这些东西，本质上就是在 API 层面为 CPU 的多核化做准备；2014、2015 年那阵子大家就在讲 CPU 的任务怎么并行化。

## 一帧的执行链路

   * **game loop 的任务结构**

       * 拿 Unity 的基本 game loop 举例：一开始是 physics——物理引擎这些东西，是纯 CPU 计算的；接着处理不同的场景世界；再跑一大堆脚本——处理怪物、攻击、各种判定这样的逻辑。相对 gameplay，render 反而是逻辑比较清晰的一块：做 render 本身，之外还有 shadow、GI 这类各种各样的计算。

   * **引擎线程拆分**

       * game thread 专门干主逻辑：物理、gameplay 这些；CPU 有那么多核，game 里适合并发、适合异步的任务——比如大量物体的物理判定、大量物体 game logic 的执行——也会扔给任务线程去做。

       * render thread 管绘制这件事怎么控制：game thread 把所有物体、物理都决定好了、动画也播放到位了，render thread 就把场景里要绘制的物体做剔除、把绘制数据（包括材质在内）准备好后提交；UE 其实还会提供一个 RHI thread 专门做绘制指令的提交，讨论时常把它和 render thread 统在一起——从 gather 把 game 已经弄好的数据接过来，直到绘制指令提交出去，都算 render thread 的活。

```text
game thread：物理 / 脚本 / gameplay 主逻辑（适合并发的任务扔给任务线程）
      │  gather：把本帧要画的东西交出去
      ▼
render thread：剔除、准备绘制数据，记录并提交 Vulkan 指令
      │  提交（此时指令还没到 GPU）
      ▼
驱动：把 Vulkan 指令翻译成 GPU 指令，放进队列排队
      │
      ▼
GPU：按自己的调度从队列取指令执行，画进离屏的 frame buffer
      │  V-Sync 信号到来
      ▼
交换链 display：把这一帧刷到屏幕上
```

   * **指令的旅程**

       * 在代码里写了一个 Vulkan 指令（比如 `vkCmdDrawIndexed`），这个时候它其实还没到 GPU 上去；指令提交给 GPU 之后，GPU 也会把它放进一个 queue，然后 GPU 按自己的调度、等有空闲了再真正执行这批指令。

       * 执行结果画进离屏的 frame buffer；等 V-Sync 信号来了、交换链 display 的时候，把这一帧刷到屏幕上——整个引擎就是以流水线的形式在干这件事。

       * 一帧不是一条线程从头跑到尾，而是沿着 game thread → render thread → 驱动 → GPU → 屏幕这条链流动，级与级之间都隔着队列。

## 瓶颈判定原则

   * **最慢一环决定帧率**

       * > **定义**：流水线里只要有一个人慢，就会拖累整个最终表现——最慢的一环决定最终的帧率。

       * UE 里用 `stat` 这类指令可以看到各线程一帧的执行时间：game thread；render thread——通常意义说的 draw；RHI thread——专门做绘制指令提交的；还有真正的 GPU 执行。比如示例里 GPU 执行是 9.1ms，那整个帧率就是被 GPU 执行这一环卡死的——也就是常说的 GPU bound。

       * 当性能不达标——比如预期 60 帧、现在只跑 30 帧——首先要定位的是：这条异步提交的管线里，到底哪一环出了问题？这就需要测量，把每个环节大概花多少时间量出来。

   * **display 这一环不用测**

       * 显示器的刷新是固定的：虽然有 V-Sync、G-Sync 这些东西，但基本可以认为它是恒定的——比如开了 V-Sync 就锁 60 帧。

       * 要测的话，把 V-Sync 关掉再测：关掉之后，整个指令流就不会等 V-Sync 信号了。

## 计时方法

   * **CPU 侧计时**

       * game thread、render thread 都跑在 CPU 上，测试相对简单：每帧之前、之后用 C++ 标准库的 `std::chrono` 打两个时间戳，一减就得到这一帧的耗时。

   * **GPU 侧的常见误解**

       * > **易错点**：把 Vulkan 指令的提交时间点当作 GPU 的执行时间点是错的——提交时间点只说明你把指令交出去了，完全不能代表它真的执行完了；两者之间隔着驱动翻译和 GPU 队列，通常要延后几帧。可以用 `flush` 这类指令强制刷新，但这会严重影响真实的性能。

   * **GPU 时间戳查询**

       * 做法：提交本帧第一条 Vulkan 指令之前，先写一个时间戳 t0；提交完最后一条指令之后，再写第二个时间戳 t1；GPU 真正执行到这两条记录动作时，会把当时 GPU 上的时间分别记下来；之后通过 get query 这类查询接口把时间戳取回来，`t1 - t0` 才是这一帧在 GPU 上真实的执行时长。

```text
vkCmdWriteTimestamp(t0)   ← 本帧第一条绘制指令之前
……本帧全部绘制指令……
vkCmdWriteTimestamp(t1)   ← 本帧最后一条指令之后
隔两三帧、确认已执行完后非阻塞查询：t1 - t0 = 本帧 GPU 真实耗时
```

       * 细节：正因为提交和执行之间有延迟——一般要延后两三帧，具体取决于 double、triple buffering 的配置——查询的时候要等上几帧，确认这部分工作真的执行完了再去取；而且要非阻塞地取，别让 CPU 干等。

       * 有了 game thread 一帧的耗时、render thread 的耗时、GPU 的耗时，大致就能知道这一帧是被管线里的哪一环拖累了——需要解决的瓶颈在哪，就去哪做针对性的优化。

## 常用分析工具

   * **CPU 端**

       * Visual Studio 的 Profiler 最简单：能给出每个函数、每条指令大概耗费了多少 CPU 时间。

       * 如果是 Intel 的 CPU，还可以用 Intel VTune Profiler 做更细致的分析：不只是函数本身，还能看到核、线程这些层面的东西。

       * UE、Unity 也都提供引擎内部的 profiler：让你了解引擎内部各个阶段在干什么、各耗时多少，真实定位到问题瓶颈出现在哪个地方。

   * **GPU 端**

       * GPU 就需要额外的工具了：有些是做性能分析的，有些是做 debug 的——但 debug 工具也能帮你看性能，因为它能展示整个 GPU 的状态、每条指令做了什么。

       * PC 上常见的是 RenderDoc、Nsight；移动端不管是骁龙还是苹果，也都会提供对应的性能分析工具，只是方便程度不如 NVIDIA。

       * GPU profiling 的概念各家大同小异，都是管线那一套。

## SIMD 与 SIMT

   * **CPU 的并行手段**

       * 一种是 OpenMP 这类，把 for 循环并行化；另一种是 CPU 提供的特殊指令 SIMD（single instruction multiple data）：发射一条指令，可以同时处理多个数据，靠的是 AVX、AVX2 这类向量单元，一次能处理非常多的数据。

       * SIMD 的问题出在编程模型：向量化得由编程者自己解决——你得人肉搞清楚数据应该怎么 pack、怎么摆；所以在 CPU 上用向量化做加速本身没问题，就是写起来不算复杂、但确实麻烦。

   * **GPU 的 SIMT**

       * > **定义**：SIMT（single instruction multiple thread）与 SIMD 一字之差，差的就是 data 和 thread——data 只是数据的描述；thread 是一个完整的逻辑单元，至少在编程端表现出来的就是一个函数。

       * 编程者的心智负担其实就只是写好一个 thread 的执行体；整个调度、数据怎么摆、并行怎么执行，都由 GPU 自己的 instruction decode 和 warp scheduler 完成，而且 GPU 的并行单元比 CPU 上的向量单元多得多。

       * 开普勒（Kepler）架构 GPU 上一个 SM（流多处理器）里密密麻麻全是「核」——严格讲这些也不能叫核，它们就是一个个 float32 的处理单元，一条条 lane。

| 对比项 | CPU SIMD | GPU SIMT |
| :--- | :--- | :--- |
| 一次发射 | 一条指令处理多个数据 | 一条指令发射多个线程 |
| 编程单位 | 数据怎么 pack 要人肉安排 | 写一个线程函数，调度交给硬件 |
| 典型载体 | AVX / AVX2 向量单元 | warp（32 线程 lockstep） |

---

## warp 执行模型

   * **warp / wavefront**

       * > **定义**：GPU 的指令按线程执行的单位——一条指令发射出去，多个线程同时执行这一条；CUDA 里比较常用 warp 这个叫法，AMD 叫 wavefront。

       * warp 的大小：NVIDIA 一般是 32 线程，AMD 的 wavefront 是 64 线程，手机上可能还有不同的大小，比如 16 线程之类的。

       * 关键是记住一条：以 32 个线程为单位，这 32 个线程执行的指令是一样的，而且同一时刻一起执行——这叫 lockstep（锁步）执行。

       * SIMT 的这个特点意味着：编程者写代码时大概率只需要管这一个线程大概怎么跑（当然有些访存你可能要关心），数据怎么存放、寄存器怎么管理大部分时候不用你操心，由 GPU 自己来管，心智负担减少很多。

   * **thread group 到 warp 的映射**

       * 写 compute shader 时，一个 thread group（thread block）里有很多线程，你写的时候自然把它当成自己的并行单元——这样想没毛病；但 GPU 真正调度的时候是按 warp 的数量去执行的：哪怕你有 240 个线程，也是每 32 个线程组成一个 warp 去执行，因为硬件一次就是 32 个一起动。

```text
thread group：240 个线程
  → 按 32 线程/warp 向上取整 = 8 个 warp（256 个槽位）
  → 最后一个 warp 只有 16 个线程真正活跃，其余 16 个 inactive
```

       * 240 个线程凑成 8 个 warp，就多出 16 个槽位——最后一个 warp 只有一半线程真正活跃，另一半是 inactive 的、白付的并行位；但硬件还是按 warp 粒度去调度，保证最大并发度。

       * compute shader 是 DX11 推出来的，相当于给 graphics 提供了直接用 GPU 做通用计算（GPGPU）的能力；但在更早的时候，vertex shader 这类着色器就已经在通用流水线上并行执行了。

## 图形管线中的 warp

   * **vertex shader 的执行**

       * 这一帧要处理很多顶点，它们就是并行执行的，同样是一批一批来：32 个顶点或者 64 个（不同厂商不一样），一起执行 vertex shader。

       * VS 执行完的数据会放进 post-transform vertex cache；后面按 primitive 往下走的时候，碰到重复的顶点就直接剃掉。

   * **pixel shader 的执行**

       * PS 是以 quad 为单位的——一个 quad 是 2×2 四个像素，对应四个线程；执行的时候，GPU 会把屏幕空间（RT 空间，也叫屏幕空间）分成比如 128×128 的大 tile，由 GPU 里对应的 tile 单元去扫这个屏幕，找出活跃的 quad。

       * 这些 quad 会被打包成 warp：还是按 32 线程一个 warp 执行，一个 warp 就能同时装下 8 个 quad——32 个线程、8 个 quad 一起跑。

       * helper lane：quad 里没被三角形覆盖到的像素就是 helper lane（helper thread）；helper lane 的存在是有用的——算梯度需要 2×2；但 GPU 也能让你知道某个 lane 是 helper：通过比较新的 HLSL 指令里的 intrinsic，可以查到这个 lane 是不是 helper lane、它能拿来干嘛。

       * PS 虽然没有像 threadgroup 那种显式的并行映射让你操作，但底层同样是以 warp 为单位执行的。

## 分支的代价

   * **情况一：warp 内发散**

       * warp 内的线程走不同分支（比如偶数线程走 work1、奇数线程走 work2——一个 warp 里 0、1、2 号线程走的就是不同的任务）时，两条分支里的算术指令都会执行。

       * GPU 会在判断的时候通过 predicate 知道这条指令对哪些线程是有用的、哪些线程是 inactive 的；为了保证安全，inactive 线程的读写会通过 mask 屏蔽掉——读写不会真的发生；但时间上，你还是把两条分支的代价都付出了。

   * **情况二：warp 内一致**

       * 执行尺度不止 warp 一层——一次可能要调度一千多个线程，比如前 64 个线程做一件事、后 64 个做另一件事；这时每个 warp 内部走的指令完全一样，第一个 warp 和第二个 warp 各走各的分支，对 warp 内部来说完全没有负担。

       * 如果分支条件来自 uniform，那就属于情况二：指令上的性能负担只是取 uniform 本身，if 里真正那些指令根本不会执行。

       * 判定规则：分支的代价以 warp 为单位衡量——warp 内一致，没走的分支不付钱；warp 内发散，两条分支都得执行，只是无效 lane 的读写被 mask 掉。

## 线程切换与 occupancy

   * **调度器与零开销切换**

       * 以 CUDA 架构为例：一个流处理器（SM）上有 4 个 warp scheduler，支持双发射——一次可以发射两条指令；双发射更多是在指令有并行度的时候才能做得更好；理论上，4 个调度器可以同时执行 8 个 warp 的指令。

       * 麻烦在访存：如果碰到 cache miss，或者下一条指令要读 texture 而 texture 还没回来，这条指令就有 latency，得等十来二十个 clock；GPU 的对策是尽快切换——这个 warp 在等，就切到下一个已经 ready 的 warp，去执行它的指令。

       * 在 CPU 上上下文切换是有负担的，但 GPU 上切换本身没有 overhead——因为寄存器、shader memory 这些资源都是预先分配好的：比如来了一个 1024 线程的 thread group，整个 group 就在这个流处理器上优先分好了位置；虽然一次只能执行 4 个 warp，但其他 warp 的资源也都已经分配好了，所以这个 warp 一等，马上就能刷到下一个 OK 的 warp 上去执行。

   * **对写 shader 的启示与 occupancy**

       * 指令量别太少，要保证流处理器下面有足够的 warp 供你调度——这个 warp 在等访存，立刻有别的 warp 顶上，SM 就闲不着。

       * > **定义**：occupancy——你到底有没有把流处理器的性能占得足够满。

       * 如果本来就没多少 warp 在流处理器上，整个并行度就高不起来；访存卡住也一样，active 的并发度上不去。

   * **寄存器是硬天花板**

       * 一个 SM 上最常见的限制出在寄存器：一个 SM 的寄存器就那么多——比如一共 1 万个；又因为线程资源是预先分配好的——

```text
SM 寄存器总量（举例）：10000
  每线程用  100 个 → 最多容纳  100 个线程
  每线程用 1000 个 → 最多容纳   10 个线程
```

       * 寄存器用量直接决定 SM 上能驻留多少线程，这是很大的限制度；profile 里能看到每个 shader 用的寄存器数量是多少，看到了就回头看你 shader 怎么优化。

## 访存模型

   * **存储层级**

       * GPU 也是各种级别的存储：DRAM 是显存，对显存的访问下面有 L2、L1 这样的多级缓存。

       * GPU 有一点不一样——它是从 graphics 发展起来的，所以除了 L1 之外，还有一个专门的只读缓存（CUDA 里可能叫 read-only cache；对应到 graphics，大部分就是 texture cache），还有 constant cache——更多是服务 uniform 这种东西；流处理器上本身还有 shared memory。

   * **访存粒度**

       * 访存也是以 warp 为单位做的：GPU 的 L1 跟 CPU 一样有 cache line 的概念——128 byte；GPU 访存的基本单位可能是 32 byte，叫一个 segment，一次可以请求 1 个、2 个或 4 个 segment，也就是一次请求的量可以是 32 byte、64 byte 或者 128 byte。

   * **一次访存的全过程**

       * 一个 warp 要访存时，因为 32 个线程是并行执行的，每个线程只会提供一个地址，warp 一共给出 32 个地址，硬件会把这 32 个地址整合成请求。

       * 假如读的是只读数据，就先到 L1 里沿 cache line 找：这 32 个地址如果能整合成一个对齐的 128 byte cache line，那发一个请求就够了；如果是不对齐的 128 byte，可能就得拆成两个请求。

       * cache line miss 了，再把这个 cache line 请求变成对内存的请求——比如打到 L2，拆成 4 个 32 byte 分段（4×32）作为一个请求；非对齐的话就变成两个二分段请求，以此类推。

   * **texture 的特殊路径**

       * texture 的处理跟普通 cache 不太一样：按每 4 个线程为一个请求单位——32 线程的 warp 会生成 8 个请求，硬件再把这 4 个一组合并成若干内存地址请求；这 4 个一组更多是考虑了 quad 这种东西（属讲者推测，未找到确切资料）。

       * 优化依据：一个 warp 内请求的地址越对齐、越集中，整个访存的代价就越小——这是写 shader 时优化访存最朴素的依据。

## 图形管线的专用硬件

   * **专用与通用之分**

       * graphics 管线里有一些特别的东西：从 input assembly（IA）开始就有专门硬件，处理 primitive 和 vertex 的输入；vertex shader 要用的顶点抓取也有专门单元——比如专门为 vertex 做准备的 PD、VAF 这类单元；往下还有处理 primitive 的 VPC 这类单元；光栅器是 graphics 本身就有的；做 frame buffer 操作的也是专门的硬件。

       * 大家通用的是 SM 的 pipeline 和内存这一块——float32 运算、load/store 这些基本一样；shader 部分更多的还是调度、计算以及 memory，跟 CUDA 类似。

## Nsight 性能分析

   * **为什么能看进 GPU 内部**

       * GPU 内部各种管线的执行状态，只有驱动厂商才掌握那么多细节——驱动里就有各种 counter，记录 GPU 的运行状态。

   * **Speed of Light（SOL）**

       * > **定义**：GPU profiling 里最大的一个着眼点——GPU 是高度并行化的系统，核心指标就是吞吐量，以前叫 Speed of Light（SOL）：你跑这个元器件、这个单元，是不是把它跑满了、是不是跑到百分之百；跑到百分之百，它就是瓶颈。

       * Nsight 的 profiler 里有一个简单流水线的展示：各单元大概用了多少，绿色的格子配一个数字表示占用百分比；整个 profiling 就是基于「当前任务对 GPU 各单元的占用」来做性能分析的。

   * **Frame Profiler：指令重放**

       * 本质是指令重放，跟 RenderDoc 这类抓帧工具的逻辑类似：hook 住你的 DLL，Vulkan/D3D 指令的每次调用都被记下来，下次再重放出来；这样每个事件都能看——比如一个 draw，mesh、几何是什么样子，输出的贴图是什么样子。

       * 它比一般抓帧工具做得更细：每条指令之后，还能对应采集这条指令在 GPU 里执行时的各种 counter——把你的东西放一遍，甚至多放几遍，记下平均每次跑的时候 counter 是什么样子。

       * 代价也要心里有数：因为是重放，重放时的 GPU 活跃度、负载跟你真实执行时不一样；而且为了统计这些信息——这个 thread 是不是在执行、是不是活跃、访存怎么样——统计本身也有 overhead。

       * > **注意**：Frame Profiler 给的绝对耗时别当真，相对值是准的——比如某个 pass 显示 6ms，未必是你真实在 GPU 上跑的 6ms；但你优化之后它变成 5.5ms，就能确认这个优化的比例是成立的。

       * 有了这个能做非常细致的分析：某个 draw 里某一个特别的三角形、某一个特别的 draw call，它内部的代价是什么样子，都能比较清楚地看到。

   * **GPU Trace：实时但粗粒度**

       * 相对轻量级：直接挂在正在跑的程序上，立马就能知道当前 GPU 真实执行的时间怎么样、比例怎么样，可以连着抓很多帧；但没那么细，只有大概念层面的信息。

   * **抓帧实例读出的两个信号**

       * 抓帧实操：把某个特性打开、关闭各抓一次，对比性能有没有变化——因为你能看到每个 pass 的执行情况，就知道你的优化对哪些单元起了作用。

       * 信号一：看 forward pass，画这个东西的时候 SM 的吞吐量已经成为限制——SM 吞吐量就是你现在应该优化的方向，按这个去找问题。

       * 信号二：GPU 真正开始执行的时间不是一帧开始的时间，前面有一段空闲——这段时间里 GPU 根本没有任务、GPU 跑太快了在等 CPU 给我们提供数据；这时瓶颈可能就不在 GPU，而是 CPU 该怎么把 GPU 更好地利用起来、喂得更饱。

       * 图的右侧会逐项告诉你每一项吞吐量的含义：比如 bus 正常应该能传多少 GB/s、现在只用了 6 GB/s，是不是没用满；又比如 SM 本来能执行 10 个 warp、现在因为一些原因只执行了 5 个——这些都在告诉你哪些地方可以去优化。

   * **逐单元认识计数器**

       * VAF：管 vertex attribute fetch——VS 在 SM 上执行时，你的顶点数据、顶点 attribute 的 fetch 用了多少，它都有账；vertex input 里 position、normal、texcoord 可以一直往里堆，但一个顶点要是写了十个、二十个属性，这个单元就会产生很大的瓶颈。

       * PD：更多关联 index buffer、primitive 这类东西；如果瓶颈出在这，要考虑 index buffer 是不是有问题——比如格式：float 不该用；现在是 int32 的话，int16 会不会更好。

       * 图元处理的统计单元：管顶点、图元处理这一层的各种数据，都跟图元相关。

       * Rasterizer：不用多讲，三角形光栅化的代价是多少。

       * SM：真正的计算执行与调度——这段 shader 执行的时候，问题出在哪。

       * L1、L2、VRAM：整个 GPU 缓存层级的东西。

       * Depth ROP、Color ROP：到了 RT（render target）这一层要管的事。

## 优化方法论

   * **错误姿势与核心口诀**

       * > **易错点**：最常见的错误姿势是拿着一份通用清单挨个试——核心就一句话：peak performance percentage，找到当前为止性能最大的问题，按瓶颈往下钻。

```text
帧率不达标：逐层往下找
────────────────────────────────────────
game thread   ── 脚本 / 物理 / 网络
render thread ── 动态物体 / 灯数量 / draw call 数量
GPU           ── 找最耗时的 pass，追问它为什么耗时
      │
      ├─ GPU 不活跃（帧首空闲）→ 为什么没喂够指令？查 CPU 提交
      ├─ GPU 活跃 → 看吞吐量最高的单元，针对它优化
      └─ 整体吞吐低（如 <60%）→ 为什么吞不动？
            ├─ 在等资源 → 查等待原因
            ├─ 访存太密集 → 减访存
            └─ 调度不过来 → 查 occupancy（寄存器），
                            或用 async compute 填满空闲
```

   * **找到最耗时的 pass 之后**

       * 先按瓶颈找到最耗时的那个 pass——比如它耗了 9ms，那就问这 9ms 到底是因为什么。

       * GPU 不活跃？就像帧首空闲那种——那就看为什么没有提交足够的指令（查 CPU 提交）。

       * GPU 已经比较活跃？那就看吞吐量最高的单元是什么，针对它优化。

       * 整体吞吐量不高（比如小于 60%）？那要找为什么吞不动：是资源没到位在等，就查等待原因；是访存太密集、跟不上，就要减访存；是 shader 本身写得不好（比如寄存器用太多）导致没有足够的 warp 可供调度，就查 occupancy 是不是 OK；调度实在调不过来，能不能用 async compute 这类手段把其他任务填进来、把空闲填满。

   * **平台差异**

       * > **注意**：不同平台瓶颈不一样——你在这个平台优化好了，它在别的平台上可能完全不是瓶颈；console 好做一些，照着一个固定配置优化就能做得很极致；PC、手机碎片化严重，在这上面做的优化到别的平台可能是负优化，所以还是得实测，没有放之四海皆准的基准。

   * **算法先行**

       * 你得大致了解每个 pass 是怎么做的、算法大概什么样：如果是访存型，到底有哪几次访存、访存是密集还是非常稀疏——心里有这个概念，才能做好针对性的优化。

## 优化动作与单元影响

   * **几何减面**

       * 模型面数变少、顶点数变少，VAF 的属性抓取肯定变少；顶点数、面数变少，裁剪、光栅化的代价都会变小。

   * **裁掉一部分绘制**

       * 对 VS 来说，shader 执行数量变少了，SM 的执行压力就变小，对应的访存压力也会变小。

   * **shader LOD**

       * 更直接作用于流处理器：删掉一次贴图采样，贴图缓存、访存速度都会变快；删掉某段 for 循环，整个指令数变少。

   * **texture LOD**

       * 主要针对访存。

   * **实测与工具验证**

       * > **注意**：这跟 GPU 平台强相关——如果你的 GPU 特别好，把一万面片优化成一千面片可能完全没感知（反正跑不满）；一定要在瓶颈端做优化，才会有收益。

       * 有了 profiling 工具，后续做完简化放到 GPU 上一跑：首先统计上能看到面数确实少了；其次能看到这个优化对管线里哪一部分造成了什么样的影响——不再只是盯着一个帧率，能确认变化是不是符合预期。
