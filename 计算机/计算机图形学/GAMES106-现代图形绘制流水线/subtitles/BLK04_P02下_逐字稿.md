刚才有同学问：队列，明明我一个实例化也能用很多队列，那么为什么我还需要有不同的逻辑的？是因为队列它会有一个簇，或者叫做 Queue Family。这个簇它的能力是不一样的，每个队列簇只允许部分的操作。比如说它可以实现渲染功能，实现计算着色器相关的功能；它可以支持复制 Buffer，做拷贝的功能。并不是每一个队列都能够实现所有的功能，有些队列只能实现部分，有些队列可能是另外一部分，也有可能硬件实现就没有一个队列能够实现所有的部分。这个时候你就需要根据队列不同来做操作。包括你的 Swapchain Buffer，绘制到的东西画到屏幕上去，也需要队列簇来实现它能够支持的功能，你才能够把这个命令扔到队列簇的队列里面去。

我们这边可以看一下我们的队列簇。看一下当我们要去获取一下我们的队列簇。在我的电脑上是有三个队列簇，这个 Flag 就是表示它们的能力，15、12、14。这个也是依赖于一个枚举变量，课堂就不去仔细看是为什么了，然后每个队列的数量是多少。

再后面就是我们要做的逻辑设备，就是 VkDevice。我们有了物理设备之后，我们的程序需要跟物理设备打交道，这个时候我们就需要有一个逻辑设备来跟我们的物理设备去打交道。我们在创建这个逻辑设备的时候可以去做开关。比如说我们的程序并不需要几何着色器或者细分着色器，或者某些压缩纹理的时候，我们就可以把这些开关关掉。当我的程序必须要用几何着色器才能实现，我们可以去 Query 出我们的物理设备能不能支持这个功能。它不支持，那这个时候我们的初始化就可以结束了，因为它无法执行我们的程序。后面如果成功创建好了逻辑设备之后，就可以从逻辑设备中去获得我们的命令队列，就是 Queue。这个命令队列其实是我们的队列簇中的一条队列。

建好逻辑设备之后，我们整个 Vulkan 的初始化就完成了。下面是要跟我们的 Vulkan、跟我们的屏幕去做交流。这个东西其实是个扩展。我们可以看到 Vulkan 跟我们的屏幕的交流是个扩展，并不属于 Vulkan 核心的一部分。这个也很好理解，因为核心渲染并不属于核心渲染的一部分，不同平台肯定是需要有一个不同的渲染方式，Windows、Linux，每个平台都会有渲染方式，所以他们给 Vulkan 提供了一个扩展。比如我们在 Windows 上面用的就是 Win32 的 Surface，需要这个扩展来实现。包括我们建 Swapchain 这个事情，其实也是 Vulkan 的一个扩展。因为 Vulkan 并不需要一个输出，对 Vulkan 来说，它只是说我渲染，渲染到一张图里面去就可以了，并不需要输出到 Swapchain 上。基于 Swapchain 里面，所以它当然也是 Vulkan 的一个扩展。

我们需要查询队列簇。刚才提到队列簇，我们可能刚才已经选择了一个队列簇去创建了我们的逻辑设备，这个时候我们去验证一下，我们创建的逻辑设备选择的队列簇是否支持这个 Surface。如果不支持，那么你就需要另外去重新选择一个队列簇。如果恰好你所有的功能并不存在那么一个队列簇的情况下，假如运气非常不好，它的 Swapchain 的队列簇需要额外建一个 Device，那么你的 Queue 就得扔到另外一个 Device 里面去做了。当然比较幸运的是，一般而言应该没有这种驱动。

我们在创建我们 Swapchain 的时候，一般而言需要定义这样的东西：比如说颜色空间，是 sRGB 的还是 HDR 的；你的刷新模式是同步的，有没有开垂直同步，还是不开垂直同步。当然 Vulkan 里面并不是简单的“是否开垂直同步”，它里面还是有些别概念的，有兴趣可以再去查阅一下 Vulkan 的手册。还有一个是缓冲的数量，是双缓冲还是三缓冲。双缓冲、三缓冲这个概念的话，胡老师应该有提过吧。最后我们要从 Swapchain 里面去找到 Vulkan 的 Image，就缓冲对应的 Image，用于后面的去创建 Framebuffer，然后去绘制到我们的 Swapchain 上。我们如何绘制到 Swapchain 上的？就是把它画到 Swapchain 的 Image 上面，作为我们 Pass 的输出，就可以了。

刚才有同学问到：移动端设备支持的特性少吗？这个是肯定的，移动端设备支持的特性一般而言都是要比 PC 要少一点的。至少移动端的 Ray Tracing 基本上，可能最新的部分手机是有的，大部分手机还是不支持的，对吧。

接下来是我们的绘制管线。我们在提到绘制管线的时候，可能会跟 OpenGL 不太一样的一个地方，就是你需要知道你的绘制管线的所有功能、所有的能力，它是没有一个传说中的默认值这么一个东西，其实是不存在的。所有的属性、所有的参数都需要你去设置过一遍，只不过说你这个功能可以开、可以关，但是你都要去显式地去说你要开还是显式地要关，这样子。像 OpenGL 的话，它其实是有一些默认值的，比如说深度检测我要不要检测，对吧。

一般情况下我们就是通过绘制管线把刚才说到的几何信息、贴图画到屏幕上去。我这里会讲到的是我们一般情况下最核心的一个绘制管线，这边就没有 Mesh Shader、几何、细分这些不太常用的功能，就不在我们的课程里面了。当你学会绘制管线之后，后面的几何、细分，你自己去自学一下其实也是非常容易的，也是非常有趣的一件事情，特别是 Mesh Shader，我觉得挺有趣的一个功能。

最后讲到不同的 API，其实我们刚才讲的不同平台，大概 D3D11、OpenGL、Vulkan，还有苹果的 Metal，其实它们细节上可能会有一些出入，可能有些命令它这边是没有的，那它那边是有的，但是整体逻辑是一样的。比如说后面再说吧。

第一个阶段就是我们的顶点输入。顶点输入我们需要有一个叫做顶点数据缓存。顶点数据缓存就是缓存了你的——有同学说是不是可以在 Pipeline 中定义自定着色器流程长短？是的，所有的 Pipeline 流程都是你自己来定义的，你可以不去加那些你不想有的流程。

比如说我们想画个三角形，三角形我们需要有个三角形的空间位置、三角形的法线。如果要给它上纹理的话，需要一张纹理坐标，可能还有一些别的属性，比如说顶点颜色之类的一些别的属性。这些属性我们要把它扔到一张顶点缓存中去。

举个例子，我们这边通过两块缓冲，一块缓冲只存储顶点的坐标，另外一块缓冲存储顶点的法线。然后有一块缓冲存储纹理跟其他的顶点属性，缓冲在 Buffer 0 里面；Buffer 1 缓冲了顶点坐标与顶点法线。为什么要这样做呢？是因为我们的逻辑中，顶点坐标跟顶点法线可能会实时变化。实时变化的原因可能有多种多样，可能是由于自定义的功能，比如说想要计算某些蒙皮动画功能的时候，可能就需要每帧去更新 Buffer 1。这个时候把 Buffer 1 跟 Buffer 0 放在一起就显得不合适了。

第二点是顶点缓冲的排布，跟 Vertex Input 会有一定的性能影响。这个时候我们也有一个优化的算法库，叫 mesh... 会有各样的算法库可以给大家去用。

第二个是所有索引的顶点。比如画三角形，它的三个顶点索引分别有索引 0、索引 1、索引 2。对应到过去就是一个顶点复用的关系。这个顶点在这个三角形中是这个顶点，在另外的三角形中其实也是这个顶点，是相同的顶点，这个时候就没有必要在顶点缓冲里面再去产生一份了。在索引的时候会发现，三个索引指向三个顶点。这个时候会有一个比较常见的优化：索引指向的顶点位置在顶点属性分配中不能隔得太远。比如我这边举了个不太好的例子（这里纠正一下，这不是索引，这是顶点属性）。三角形前三个顶点分别指向了第一个顶点、第三个顶点跟最后一个顶点，这就是非常不好的例子。大家学过计算机硬件的时候知道有缓存的概念，GPU 其实也是有缓存概念的。顶点属性如果隔得非常远，就会造成 Cache Miss。一旦产生 Cache Miss，就会引发 I/O 的一些性能损耗。相对于计算代价来说，这个性能损耗远远大于计算代价。所以在写 Vulkan 的时候一定要考虑到 Cache Miss 的问题。一般来说它的影响远远大于计算复杂度之类带来的影响，这也是一个工程经验。

第三个是图元拓扑类型，即绘制的是顶点、线还是三角形。我们可以看一下 Homework 1，这是第一个课时的作业。这里有画面的方式，也有画线的方式，用来绘制不同的效果。

最后会有 Draw 调用，这边其实是有四种 Draw Call。当只有顶点数据的时候，直接调用 `vkCmdDraw` 就可以了；当有了顶点索引缓冲的时候，就需要用 Draw Indexed；后面对应有两种叫做 Indirect，即间接绘制。这是什么意思呢？我们在画 Mesh 的顶点有多少个的时候，CPU 端通常是知道的，比如模型有多少个顶点在 CPU 端是明确的，就可以在函数调用时直接把参数写进去。但有些时候是不知道的，比如 Mesh 是通过物理模拟或程序化生成的方式由 GPU 计算出来的，GPU 把看不见的东西剔除掉了，这个时候 CPU 端就不知道具体需要画多少个顶点。Indirect 方式就会把前面两个函数的调用参数作为一个 GPU Buffer 传递给 GPU，这是对应的另外两种进阶绘制方式。

下面一个阶段是 Vertex Shader，即顶点着色器。Vulkan 提供了很多的着色器编译方式，可以使用 HLSL 或者 GLSL。GLSL 是 OpenGL 的 Shader 语言，HLSL 是 DirectX 的语言。编译器大概常用的有三种：一个是 DXC (DirectX Shader Compiler)，有同学问这明明是 DirectX 的编译器，能不能编译 Vulkan？其实是可以的，而且表现还挺好；这些编译器都可以在最新的 Vulkan SDK 里面找到。另外还有 glslc 和 glslang。大家可以选择自己觉得方便的编译器去写对应的 Shader。我个人比较喜欢写 HLSL。

几何信息经过顶点着色器计算，经过旋转变换、透视变换画到屏幕上去。这里需要提一点 Vulkan 的坑：Vulkan 的 NDC 空间（屏幕空间）跟别的图形 API 不太一样。一般的屏幕空间横向是 X 轴。

关于 Shader 开启 Print 扩展，目前是不支持的。Shader 里面做调试通常是把数值作为颜色输出，很少会直接打印。

在绘制三个轴时，X 轴是横向的，Y 轴朝下，Z 轴朝前。因为与 OpenGL 一样属于右手坐标系，必须满足右手坐标系的前提，但它又定义 Z 轴沿着正方向。裁剪空间一般是 0 到 1，而 OpenGL 的实现中 Z 轴沿着负方向，它会把裁剪空间先映射到 -1 到 1，再映射成 0 到 1。这听起来似乎没有什么偏差，但实际并非如此，因为计算机浮点数计算是有精度要求的。在离 0 比较近的地方，有效精度会更高。因为 0 附近数值以 0.000... 开头，前导零不占有效位；而离 1 比较近时有效精度就会减弱，例如数值是 0.99999，从第一个有效数字开始计算，精度分配就受限了。所以通常精度最好的算法是 Reverse-Z，即离观察点越远的深度值为 0，离最近的位置深度值为 1。

接下来是光栅化部分。光栅化部分需要定义填充方式，是实体填充还是线框填充。刚才那个图示应该属于填充方式的范畴，通过填充模式来实现不同的表现效果。

此外还有剔除方式，需要设置正面剔除还是背面剔除，看不见的背面就不进行绘制。还有正方向的定义，是顺时针为正方向还是逆时针为正方向。这也与 NDC 空间的定义有关，同样的数据在 OpenGL 里面可能是顺时针，在 Vulkan 下面可能就变成了逆时针。

后面是我们的视图，我们要绘制视图区域，窗口跟我们的视图，你会发现视图就是真正绘制的那块区域，窗口就是比如画的屏幕。视图区域比窗口小，大家很容易理解，很多时候我们只想画窗口的一小部分作为某个控件，这样画就可以了。

但是有的时候，我们的视图会比窗口大很多。什么样的情况会有呢？比如我们现在的场景里面，我想要把中间这块地方抠出来，抠成 1080p 的区域，那我就可以把这个视图拉得足够大，让窗口的位置恰好在视图的这块区域。

通过这种方式会需要来一个这样的功能。有些 CSM 的实现，你看他们的实现代码，可能就是通过这种方式来实现的，把一块局部区域的分辨率给它提高。

最后还有一个剔除方式。这个剔除方式大部分情况下是不太会用到的，但是我们的 UI 可能会用得比较多。比如我们在左边两个会看到一个开启的一个关闭的，这个大家看得不是特别明显，就是在这个区域的效果差异。

再是 Fragment Shader。Fragment Shader 是渲染管线最核心的一个部分，大家所有的计算都会在这个地方。包括我们的纹理，纹理大部分是用于颜色，有的时候会用于数据的编码或者是干嘛的。Vertex Shader 的顶点属性，我们刚才说了它计算好了顶点属性之后，会经过一个线性插值，插值到我们的 Fragment Shader，你也可以选择不进行线性插值。

还有一个缓冲区。缓冲区的话有一个 Uniform Buffer，或者叫 Storage Buffer，分别叫 std430、std140。std140 其实是指 OpenGL 的版本。还有一个叫 Push Constant，这个是 Vulkan 特有的一种缓冲区，你可以每帧都去更新，频繁更新的数据可以放到 Push Constant 里面去。

最后是我们要注一个事情，在移动端上面我们要注意浮点数的精度。我们一般来作为颜色计算，16 位精度是完全够用了；但是作为顶点位置计算的时候，就需要一个 32 位的浮点数才足够用。颜色一般是 RGBA8，可能 8 位都够用了。在移动端上我们要非常注意到这个事情，一定要优先把所有的浮点数都改成半精度的 16 位，然后再看哪些可能不够，再把它改成 32 位的，这样就可以了。

最后是 Frame Buffer 输出。Fragment Shader 输出之后会算出一个颜色到 Frame Buffer 里面去。Frame Buffer 里面会做两个事情：一个是混合，是你的输出颜色跟原有的颜色去做一个混合，或者 Alpha 混合之类的这些功能；还有一个是深度检测，还有模板剔除检测。

深度检测一般要做的事情是，比如画家算法，离得近会把远的给挡住，深度检测干的就是这个事情。模板检测我这里就不举例子了，大家如果后面遇到的话就会用到。

深度检测这个东西其实一般的现代驱动都会做一个 Early-Z 的操作，就是说在你的 Fragment Shader 里面不做 discard 或者不去修改深度，那我这深度其实在 Vertex Shader 出来的时候我就已经知道了。这个当我的深度检测一定会失败的时候，这个像素就不会画了。

这种东西大家可以想下，就会天然想到一个优化，叫做 Pre-Depth。就是我在绘制之前，我先把深度先写一遍，Fragment Shader 什么都不干，就 Vertex Shader 把深度给写到屏幕上去。我后面再去真正地绘制，那我就可以提前把深度一定过不了的这些东西给剔除掉了。

但是这种方式是一个 PC 端常见的优化方式。但是，移动端这个方式其实是没有意义的，因为移动端的硬件架构是 Tile-Based Rendering。在这种绘制方式下面，你先把所有的 GPU 命令先堆到那个地方去，它会去做 Pre-Depth，它会把所有的 Draw Call 命令累积到一定程度，在所有的 Draw Call 里面去计算你的深度，远的我就把它剔掉，会被剔掉的就被剔掉，然后再去绘制。但是 PC 端一般的显卡可能就不会做这样子的事情。

这里就要提到，我们可以想象一下，在 Tile-Based Rendering 的时候，半透——就是你开了 Blend Test、Target Blend，或者你在 Fragment Shader 做了深度的修改、discard，那么这种 Mesh 的绘制我永远没有办法去提前把它剔掉，因为我永远不知道你的深度检测会不会成功还是失败，因为你的 Shader 里面会改。在移动端上尽量不要去绘制这两种类型的东西，有一些优化。

这里有个很有趣的优化，我们在画 UI 的时候，一般会有个半透，要抠一个形状，比如有个兔子，旁边的图是方方的，中间有个兔子，兔子是个 UI。一种优化就是我提前生成兔子边框的三角面片去抠一个兔子出来，不是一个方方的一个三角面片，而是把兔子的轮廓给抠出来。那么这样子你会发现它在移动端的绘制会更高效一点，虽然说它的面片数更多。

这个是我们光栅化的一般的绘制流程。我在 PPT 之中也会提到 Vulkan 对应的对象。

我们再回到 Vulkan。Vulkan 在我们的绘制管线里面有个重要的概念叫 Render Pass。我们刚才提到的整一个绘制是一次 Draw Call。Vulkan 的一个 Render Pass 里面是它的一个最小的绘制的单元，它可以有多次 Draw Call。

比如我从左到右讲，第一个 RenderPassBegin，它可以去定义你的 Frame Buffer，就是我们输出的纹理是什么；第二个是绑定你的 Vertex 跟 Index 的 Buffer，就是我们的 Vertex Input，去定义你的输入的那块 Buffer，这个 Buffer 是需要有一个堆，你自己去管理堆去创建内存，然后去使用；在 Command Buffer 里面去设置你的 Viewport；最后是要绑定你的 Pipeline。

这个 Pipeline 是一个 Vulkan 不同于传统绘制管线的地方。之前有同学问到 Vulkan 是不是可以自己定义绘制流程？其实是可以的，因为你在 Pipeline 里面的 Shader 你不去绑，那么这个流程就不会去走；你在 Pipeline 里面只去绑 Vertex Shader 跟 Fragment Shader，那么它就只会走这两个阶段流程。我们刚才提到的光栅化部分，包括 Fragment Shader 的深度检测、Stencil 检测什么之类的，这些都是定义在 Pipeline 中的。所以说 Pipeline 是定义了整一个绘制流程的基本的东西。在 OpenGL 下面其实你是一个状态机，要一个属性一个属性去设；D3D11 大概是抽象了三四个对象，你要去一个三四个对象去绑。

有同学问 Subpass 是做什么的，这个我会在第三节课来讲，这个是主要也是针对移动端的一个优化的功能。

然后我们要绑定 Descriptor Set，这个就是我们传给 Shader 的 Uniform，传给 Shader 的参数，包括采样器、纹理，还有 Buffer。我们的 Descriptor Set 也是需要我们自己去管理，它有一个 Descriptor 的池。最后我们 Draw Call，Draw Call 结束之后，我们再 RenderPassEnd。

那么有同学就要问了，我这个……

Render Pass，我定义了两个 Render Pass，那么我在 Render Pass 的作用域外面我能干什么呢？在 Render Pass 作用域外面，你可以更新你想要的属性。这个属性我们在 Render Pass 里面是不能更新的，比如我想要把 CPU 的数据传给 GPU，这个操作你是不能在 Render Pass 里面做的，你只能在 Render Pass 外面做。

所以我们下面提了一个简单的一个串行的渲染绘制流程。我在绘制第一个 Render Pass 之前，我先把 Render Pass 0 的所有的更新掉，所有需要的 GPU 更新掉，然后再去绘制 Render Pass 0。然后我在绘制第二个 Render Pass 1 的时候，再更新 Render Pass 1 的所有结果，然后以此类推，直到所有 Render Pass 绘制完了，然后全部一股脑地扔给 GPU。

Render Pass 是一个图形绘制的一个最小单元。它定义了绘制的输出，这个我要着重讲一下它的 frame buffer 的输出。然后它是定义了一个 I/O 操作，就是说我在 begin Render Pass 之前，我的 Render Target，就是我那个输出的图，或者叫 frame buffer——不同的东西可能这个名字不一样，我这边有些叫 Render Target，有些地方叫 frame buffer，其实指的都是同一个东西。

我的 frame buffer 我是否要把它的图片里面原有的像素里面的值保存下来，还是说我并不需要管它，还是说我要把它清理掉？然后我绘制完了之后，我的这个东西我要不要把它写回到内存里面去？这个操作在 Vulkan 下面是需要你显式地去定义好这个事情的。

这个事情在 OpenGL 里面的时候驱动会帮你干。驱动觉得你最后画到屏幕上去的时候，你这张图没准没人用了，我会给你用 don't care；假如你后面调了一次 clear color 的颜色，那么我会把你定义成 clear 的那个颜色。当然这只是我的猜测，因为我也没有看过 OpenGL 的驱动的实现。

大家可能会对于这种为什么我要定义这个这么复杂的东西会有一些疑问，我大概解释一下。比如第一种，我们在读操作里面为什么要选择 load？比如我之前已经画好了这个模型，都画好了，画到这张图里面去了。这时候我要再画个背景，画背景是一个新的 Render Pass，那么我这个模型里面的深度包括颜色我是否都是需要的呢？对吧。我需要保持原来人物模型的颜色在那张图里面，这是要 load 的这种情况。

什么时候是 don't care 呢？我有一个 pass 专门做一个比如高斯模糊，那我高斯模糊是一个全屏的一个操作，那么全屏的一个操作，这个时候它的输出我就可以不需要知道它原来的图里面是什么了。

然后 clear，什么时候是 clear 呢？我的 pass 里面比如也是画模型吧，画模型并不是一个全屏的操作，我的背景其实是需要一个背景颜色，这个时候我需要把它设成 clear。这种情况通常来说深度图一般是需要的，因为深度图通常我们需要设置成一个最远的值，一般来是 1。然后我们再去画深度的时候，再去作深度的比较。

这里我回答些同学的问题。一个是“pass 是不是可以异步也可以串行的？”是的，确实是可以异步也可以串行的。关于是否异步、串行这个事情，因为我是一个入门的教程，可能只会提到串行的，后面第三节课我会讲到异步的情况下面这个 pass 该怎么去设计它。

然后我们渲染好了之后，Render Target 的时候也可以选择是否要 store，就是写回去，或者是 don't care。

我们什么时候是需要 store 呢？比如我们画完了这个图，我们画到、写到屏幕上去。这个时候我觉得大家可能会有一个疑问：我明明我的绘制就是为了绘制到屏幕，绘制出一张图出来，那么我为什么明明已经绘制了，我还需要把它扔掉呢？

假如我绘制好的东西印到屏幕上去，那么这张图的颜色的那张图我其实是需要的，对吧？但是深度那张图我可能就不需要了，因为深度我只是用来做深度检测我才需要它，我不做深度检测其实我是不需要它的。那么我把它最后放到屏幕上的这个 Render Pass，我就不需要那张深度图了。那我之前的深度我用完了，做完深度检测了之后，我就可以把它给 don't care 掉，就是我不要它里面的数据了。

这个操作大家会觉得比较复杂，但是在移动端上这个其实是蛮重要的。这个我也想要举个例子，我们同样的 Vulkan 的程序在小米手机上跑得挺快的，但是在华为手机上就挺慢的，大概差了一个数量级吧，6 帧跟 60 帧的区别。为什么呢？是因为我们的 Vulkan 用了非常保守的一些方式，在没有优化前用了非常保守的方式，都选择了 load 跟 store。华为的驱动可能就没有管你这个是否合理了，它就按照你写的直接来运行了；小米的可能就按照——高通手机可能就会发现它的驱动可能做得比较厚，就会觉得你这个事情可能后面没有用到，它就给你踢掉了。

有同学问：“提交到不同队列才是异步？”异步同步的话，其实你在一条 command buffer 里面的所有命令肯定都是同步的，你的不同的 command buffer 中间才会有异步的这种事情。
