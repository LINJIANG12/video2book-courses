第一个 Vulkan 的简介。Vulkan 它跟 OpenGL 比较类似，毕竟一开始在提出 Vulkan 这个东西的时候，它的名字不叫 Vulkan，是叫 glNext，就是下一代的 OpenGL。所以它也跟 OpenGL 一样，其实是有一个官方的标准，我们定好了一个统一的接口、统一的标准，那么具体的实现，每个硬件厂商自己去实现，并没有一个组织去审核你的硬件实现的能力。

然后这个区分于苹果的 Metal 或者 D3D11、12 不一样的地方就在这个地方。你在 D3D11、12，当你的文档标准里面说它支持这个功能，或者说当你 query 出你的硬件、你的设备、你的系统能够支持这个功能的时候，那么它一定是有得。但是在 Vulkan 的或者 OpenGL、Vulkan 的那一套里面，其实是不一定的，这个事情是要打个问号的。他们可能很声称了我支持了 Vulkan，现在是 1.3 吧，可能他们自己声称了 Vulkan 1.1、1.2 的核心功能，但是它并不是真的所有的核心功能它都实现了。你只能去经过一些测试，它才可能某些功能是 OK 的，某些功能其实是不 OK 的。

然后还有一个是 Vulkan 相对于它作为一个开源的框架的话，主要还有一个特征就是扩展。每一个平台会有一个自己的扩展，比如说在 Ray Tracing 刚出来的时候，在 N 卡上 Vulkan 的 N 卡有一个 Ray Tracing 的扩展，然后这个扩展在 AMD 上面你是用不了的，你在手机端上也是用不了的。因为它是针对 N 卡的一个扩展。然后在后续，你的扩展可能就会被吸收到 Vulkan 的核心的功能里面。所以我们在看到 Vulkan 的很多函数的时候，会经常看到一些后缀，两个函数几乎长得一样的，就是 `vkXXXXX_NV`，或者 `vkXXXXX_HUAWEI`，这个是华为做的扩展，然后 `vkXXXXX_AMD`，这是 AMD 的扩展，然后 `vkXXXXX_ANDROID`，这是安卓上的一个扩展。我们在 Vulkan 开发的时候这个是需要注意一下，你想要它的某些功能，那个功能其实跟你的硬件设备或者跟你的显示平台是非常强相关的一个事情。

我们下面讲一下对比传统的RHI跟现代的RHI。因为Vulkan、DirectX 12跟Metal，我们可以算作是现代的RHI。传统的RHI其实它们会有一个叫做上下文的概念，它们是一个状态机。这个Context可能像OpenGL会有个隐式的Context，它跟你的线程是绑定的。D3D会有个显式的Context，有个叫ID3D11DeviceContext这么一个对象。在这个对象里面它也是一个状态机，当你改了一个什么东西，它就会有个状态记录在里面。

这个状态机有什么不好呢？我可以举一个例子。比如说我们开发了一个SDK，用OpenGL开发的功能，我们自己去管理了一些设备，管理一些图片的纹理，我们自己去建了。假如刚好有个图片纹理它的ID就是12，因为OpenGL图片对象就是一个整型，我们就是12。外面在调用我们SDK的人，他们外面也会有他们对应的图片资源。假如运气非常不好，他的代码写得有问题的，他们很久以前有一个纹理ID叫12的这么一个纹理已经释放掉了，但是他并没有把12给置为0。等到了后面他再想去回收资源的时候发现，我有一个纹理12，我想去把它给释放掉。他以为释放的是外面的对象，但是真正释放的是我们提供的一个SDK内部的一个纹理，然后就会发生一些不可控的或者无法预料的问题了。可能程序会崩溃，或者直接黑屏，或者怎么样。对接我们SDK的人就会觉得，你这个SDK有问题。你看我用了你的SDK，我的这个程序就崩溃了。好吧，这个问题你要去解决了。这种东西我们也知道很难查，因为这个逻辑并不是我们能够控制的，是外部的错误调用导致的。这个就是传统的RHI、OpenGL会带来的一方面的问题，它的状态机管理，外部如果修改了，内部其实是无法感知的。

第二个事情是驱动会帮你干很多事情。传统RHI的驱动它会帮你做同步。比如说OpenGL你想从纹理里面去把贴图读出来，那么这个时候就会有个隐式的同步。它会让把所有输出到这张贴图的渲染相关的所有的命令都结束了之后，我再去从这张贴图里面把这个东西给读出来。这些事情都是驱动帮你干了。你在写的时候你会感觉好像glReadPixels这个函数会特别的慢。但这慢并不是它卡住了，或者说这个函数有多慢，只是因为CPU在等GPU在干活。CPU在那喊：“GPU你快点干啊，我等着要你的结果呢。”GPU说：“好好好，你慢慢等，你稍微再等一等，我马上就好了。”然后等到GPU干完活了，CPU再把干出来的结果给拿出来。

这种东西好处就是说，你在写代码、开发这个功能的人当然是非常开心的，反正结果是正确的。但另一个方向，你想要写得非常高效，你就没有任何手段了。

所以所有OpenGL的驱动一般说来就会比较重，或者D3D11的驱动就会做得很重。因为它要保证你的所有的功能都是完善的，所有的东西都是OK的，所以它帮你做好多事情，包括同步、竞争。比如说你这个东西谁先用，然后又由谁先读之类的，假如你还写了多线程，OpenGL也是可以写多线程的，类似的事情驱动都要帮你把这些东西给解决掉。那么当一家写驱动的公司的软件开发能力比较弱的时候，比如说个别的显卡，他们的表现可能就不是太美妙了。当一家公司的软件开发能力、驱动写得非常好的时候，他们的表现就会非常棒。你会觉得，这时候对于用户的感觉就好像你这个设备就不太行，这个设备就可以。同一个游戏我在这个显卡上明明你的算力更强，但是好像跑起来会更慢，大概就是这种原因。

我们的现代的RHI驱动层会做得非常的薄，驱动只做最核心最核心的事情。就会依赖于你的开发人员需要对你的程序是非常清楚的，你想要干什么。你画了一张图出来，这张图后面是否会需要再被复用，这张图后面会是怎么样，这张图是不是画好了之后直接画到屏幕上去，你都是得清楚这个事情。包括我们的更新机制，再包括你这个东西是否要多线程同步还是什么的，这些都是需要开发人员知道得非常清楚。你的各种依赖关系，开发资源的依赖关系，包括你的资源分配。

讲到资源分配的话，这也是Vulkan或者D3D12需要做的事情。你在写D3D11或者OpenGL的时候，可能是永远没有思考过当我开辟一块纹理的时候，我还要去思考这个纹理的内存是怎么管的。一般来说我就直接开辟，申请一块空间，就像new了一块空间一样就可以了。但Vulkan它不行，Vulkan的一般操作是你首先要申请一个足够大的一块内存，然后你自己去分配这块内存的哪块区域给这张图，这块区域给另外一张图，第三块区域给第三张图。所以Vulkan的话，你需要这种内存分配的事情要自己去考虑，自己去管理。当然这种东西是会有一些比较友好的第三方库。

它对于多线程也是友好的，因为它的接口是基于Command Buffer。所谓的Command Buffer其实就是把所有的GPU的命令我扔到了一个队列里面去。这个队列你在往里面塞的时候GPU其实是并不知道的，等到我队列都已经定义完了之后，我再去扔给GPU。它是通过这个方式然后可以实现多线程的友好。

我们再回过头看传统RHI的时候，因为有一个上下文的概念，有个状态机。那个时候如果要实现多线程就会很麻烦。比如说OpenGL我可能有三个线程，每个线程我都会需要绑定一个Context，然后每个Context之间它们资源的需要做共享，然后每个Context我还要去管理好它们的生命周期，每个Context它们有一个自己的状态机维护，这个就会非常的不友好。

这两个区别的话，是现代RHI驱动其实等于说不会帮你干任何事情，然后是你要自己去……

理解你的程序是要干什么的，你才能够写出更好的东西。

然后第二个是你如果用现代 RHI，你可以——不是很容易写出高性能的程序，是它提供了一个你可以写出高性能程序的能力，但是你要真的写出那个高性能能力，是需要一个非常熟练的情况。你需要对你的硬件，包括你的程序运行的逻辑都非常了解，你才能够写出一个非常高性能的东西。所以说熟练的程序员就可以体验到掌握了一切的感觉，你可以充分地分配你的 GPU 的硬件资源。

还有一个比较大的体现，就是当你的程序卡在了 CPU 调用上面，而不是 GPU 上面的时候，那么你用现代 RHI 的情况就可以非常好的提升。

我刚才提到的 command buffer，Vulkan 的 command buffer 是能够复用的。这个什么意思呢？就是有的时候我们每一帧画的东西其实是一模一样的。OpenGL 的话，每一帧你都会要去调用那些绘制的东西，每一帧都要重复去调用一遍 OpenGL 的命令。Vulkan 的话，你只要建好了那条 command buffer，你如果确定后面的所有的 frame 都一样的，那你就把那条 command buffer 复用就可以了，你每次都是把那条 command buffer 给扔进去。

我这边推荐的学习曲线，我是不太推荐直接上来，就是你什么都没有学习过的话，就用 Vulkan 来学习，或者是 D3D12，我是不太推荐的，因为它们的概念太多了，你需要知道的事情就很多。特别是 Vulkan 的初始化，你去理解一下我觉得就挺费时间的。不像 OpenGL，你只需要有一个库，比如说 GLFW 或者什么之类的，你的上下文就直接建了。

我提一下，OpenGL 的上下文其实每个平台是有自己的实现的。Windows 上有 Windows 的实现是 WGL，手机上是 EGL，苹果上就是 EAGL，Linux 是——Linux 我有点不记得叫什么了。

所以我觉得上手你们可能最好的选择是 OpenGL，因为它真的非常简单，而且接口上手特别快，你可以很容易地去写出你想要做的各种效果。这个只是学习的状态，当然当你想更深入的时候，你想要做一些效果更好的事情，OpenGL 其实就显得有点薄弱了。

第二个我想推荐的是 D3D11，我是蛮推荐大家学习的时候是从 D3D11 来入口。因为 D3D11 虽然说也是有一个状态机的概念，但是它接口基本上都是基于 OOP 的，所以你对于它的绘制管线理解起来会更容易，直接看它的接口就知道了我的绘制管线是长这样子的，不像 OpenGL 每一个都是状态机。

曾经我在初学 OpenGL 的时候，我的老师就有这样子一句我觉得非常有趣的话，就是当你学习 OpenGL 的时候，你去看 OpenGL 的教程，它要实现某个功能，可能会按照 OpenGL 的函数一行一行地写下来。在你不太理解的时候，你就一行一行地抄下来，不要觉得某一行是没有用的然后把那行关掉，都是有用的。

这个我举个例子。最近我有个同事在做的一个工作就是 Vulkan 转换成 OpenGL，就是 Vulkan 的一个图片转换成 OpenGL 在手机上。它的路径就是 Vulkan 转换成一个叫 AHardwareBuffer 的 Android 对象，然后再把 AHardwareBuffer 绑定到一个 OpenGL 的对象。这个听起来挺容易的对吧？但是它一直在手机上都画不上去，他也觉得很奇怪。而且画不上去也不是所有手机都画不上去，小米手机是 OK 的，能画上去，但是华为的就不行。

后来去查，看了之后的结果是他 OpenGL 在创建纹理的时候，省掉了教程中的一些设置采样器的这一步，他就没有设置了。他觉得这个好像你设置或不设置总有个默认值吧。但其实不是的，这个完全是看驱动的。华为的驱动就没给你设置默认值，那么你就画不上去了；但是小米的高通芯片就帮你做了这件事情，就可以画上去了。这个就是我说的真正的实现是很依赖于你的硬件设备。

所以当你要写 Vulkan 的时候，尽量按照标准的方式去实现，按照标准的流水线去实现，不要去省略一些东西。当你想用某种扩展的时候，硬件里面吹嘘说 Vulkan 支持这个功能扩展，其实是不一定的，这个是要打个问号的，你需要一些别的手段来去验证它是否支持。这个问题在 OpenGL 中存在，Vulkan 中也是存在的。

下面我来讲一下这个课程的主要内容。第一个是初始化的部分，第二个是渲染的主循环，最后渲染完了之后我们要退出程序。我们可以看到我们的作业 Homework 0、Homework 1 绘制的一个三角形。

这里面其实也是，这个就是我们的初始化：设置窗口，然后创建资源的对象，这是我们的初始化的一个阶段；这个就是我们的主循环的阶段，我们对应的代码部分是这样子的。

我们初始化的话，首先要做三个东西的初始化。一个是创建窗口，创窗口的话我们一般会用 GLFW 或者 SDL 之类的第三方库来做。我相信应该没有人会愿意用 Win32 的 native API 或者 Linux 的 Wayland 或者是 X11 去创建窗口，那个太复杂了。

第二个是我们要初始化 Vulkan。初始化 Vulkan 其实是程序首先要去载入 Vulkan 的驱动库；第二个是我 Vulkan 要跟我的显示设备来取得联系，告诉我这些命令得让哪个硬件设备来帮我渲染；最后我渲染完了、计算好了，最后的结果我要呈现到屏幕上去，这个就是我们的第三步，要创建一个叫 swapchain 的对象。这个 swapchain 就可以让 Vulkan 跟显示的窗口取得联系，让我们最后的东西绘制在窗口上。这个是初始化的部分。

后面再是渲染的主循环。我们可以把渲染想象成一个函数，函数的输入是什么呢？几何信息，还有一些 uniform。uniform 其实就是 CPU 端传给 GPU 的参数。我们程序想要输出的就是屏幕中显示的画面。我们的逻辑就是着色器。着色器之前胡老师应该有简单的提过。

我们的主循环大概就会有三个阶段：第一阶段是更新 CPU 端的业务逻辑，一般大部分游戏可能就是游戏的业务逻辑，我们这边可能就非常简单，可能只是一些 UI 逻辑或者一些鼠标控制相机之类的逻辑；第二个阶段就是你要把 CPU 更新好的数据拷贝到 GPU 中；第三个阶段就是你要生成你的 command buffer，把你的渲染任务扔给 GPU，然后让 GPU 在屏幕中显示出来。最后，当你主循环结束了，你要退出程序，把所有的资源释放，然后关闭你的程序窗口，这样子就结束了我们的整个流水线。我们可以对照着我们的 Homework 1 的 Hello Triangle 来对比一下这个流程。

首先是初始化我们的 Vulkan。第一个我们要调用 API 来实现窗口，这个地方其实跟 OpenGL 不太一样的地方就是，你的窗口类型 Vulkan 是需要知道的，比如你的窗口是 Win32 建的，还是 XCB 建的，还是 Wayland 建的，还是 Mac 上的东西建的。因为 Vulkan 后续在创建 swapchain 的时候是需要这个信息，然后来选择对应的扩展，才能建出我们想要的一个 swapchain。比较好消息的就是 SDL、GLFW 这些窗口的第三方库可以很方便地获得这些信息，包括窗口的类型，包括怎么去建 swapchain 之类的，它都可以帮你去实现好这些功能，可以帮助你去初始化 Vulkan。这个就像 GLFW 里面去初始化 OpenGL 的上下文一样，其实你真的去看它的 OpenGL 上下文创建的话，其实还是挺复杂的。

但是我们要回想一下，Vulkan 在设计的时候为什么要设计得这么复杂？其实想想也比较容易理解。当你有四块 4090，你想玩游戏的时候，就是我们以前说的四路 Titan，现在就是四路 4090，你如果去操控，让这块显卡干这部分的活，这块显卡干这个事情，让另外一块显卡干另外的事情，让每个显卡都能够尽可能充分利用这个事情。怎么做到呢？OpenGL 告诉你，很困难。但是 Vulkan 你可以对应的物理设备，当你四块 4090 的时候，其实你一个实例能够 query 出四个物理设备。然后你这个实例可以去选择这个物理设备，比如第一块显卡、第二块显卡、第三块显卡。第一块显卡只用来做物理模拟，拿了物理模拟结果扔给了第二块物理设备；第二块物理设备纯粹做渲染的某一部分；第三块再去处理某些事情；最后在最后的一张显卡，那张显卡专门只做渲染，把渲染出来的结果给画上去。那么这个时候你所有的显卡都会有了。

有人问为什么一个物理设备会出现多个逻辑的 Vulkan device 呢？一个逻辑设备你可以想象成其实是对于一个队列的实例化。我们真正的 API 其实传输给的是逻辑设备，并不是物理设备。所以逻辑设备的时候它会去，后面会提到队列其实是有不同类型的。我这个逻辑设备的队列只用来计算图形管线，那么我所有的图形管线命令我得扔给它。我后面的队列假如我只是用来计算 compute shader，就是计算着色器，类似 CUDA 之类的东西，那么我所有的命令可以扔给它。当然通常情况下我们并不需要去做这种事情，因为我们只需要有一个这样的就可以了。

也有人问有多个 Vulkan 实例的用处是啥呢？目前我也不是很清楚，因为我也没有遇到过我需要多个实例的情况。大部分来说，游戏场景或者各种场景，一个实例就足够了，不需要那么多的实例。所以我们只需要考虑这种情况就可以了，但是我们要明确知道 Vulkan 的设计可以让你来做这种事情。

有人说一个逻辑设备不是可以有多个队列吗？对，这是可以有多个队列的，但是每个队列会有它的功能的限制，不是所有的功能都可以在所有的队列里面去运行，队列跟队列其实是不一样的，这个我下面的 PPT 会讲。

我们刚才说了层，那么这个层到底是干什么的呢？我们想要初始化 Vulkan，有一个函数，比如我们这边要读 function A、B、C、D、E，那么 layer A 它是重写了 A、B、C 三个函数，layer B 它是重写了 C、D、E 三个函数。最后我们的接口肯定也是有 A、B、C、D、E 这五个函数。它的意思是，当我 load 我去调用的 Vulkan function A 的时候，还是取 C 吧，它调用了 Vulkan function C 的时候，它会首先调用 layer A 的 function C；layer A 的 function C 它的程序结束之后，它会去调用 layer B 的 function C；然后再去调用最后真正的接口的 function C。

换句话说，其实我们可以把这个 layer 当作函数重载来理解，它其实是提供了一个函数重载的方式，或者叫 hook。OpenGL 的 hook 会很麻烦。Vulkan 你们都喜欢 hook，好，我提供一个官方的方式让你们去 hook。这样子你们所有的调试工具，你们都可以很自由自在地去 hook 了，你们调用的所有 Vulkan 命令都可以记录下来，你们自己想做任何检查都可以了。以前在 OpenGL 调试的时候，经常干的事情把你所有的 OpenGL 的命令给打出来，包括时间、线程之类的。这个时候如果你有兴趣，你就可以自己建一个自己的 layer，然后把所有的 OpenGL 的命令把它 hook 住，根据线程、根据时间戳，把所有的 Vulkan 的调用给打印出来。当然官方是有提供这样的一种方法的，这个就是 Vulkan 的 layer 的概念。
