## 性能分析：先找瓶颈，再谈优化
> 对应块：BLK09 | 覆盖分集：P06 | 块标题（分集名）：《6. 性能分析》

这一讲讲性能分析——注意，是先讲"分析"，不是急着讲"优化"。内容大概分三块：先介绍性能相关的概念，再补一课基础的 GPU 架构，最后落到 PC 端常用的 GPU profiling 工具上。

一切从一个最基本的问题开始：为什么要写出高性能的代码？

在绘制里，高性能最简单的描述其实就是帧率。高帧率意味着更流畅的画面、更低的延迟——比如玩 FPS 游戏，你的视角会比别人更流畅，开枪触发也更准确。帧率目标则跟着平台和游戏类型走：

> **定义**：主机一般 60fps 就差不多；手机 30fps 也能玩；VR 因为对延迟的要求更高，得奔着 90fps 去。

除了帧率本身要高，帧率的平稳性也有要求：不同视角下都要稳定达到目标帧率，不能一帧高一帧低。

### CPU 和 GPU：架构不同，必须配合

要跑出高帧率，CPU 和 GPU 两边都会涉及，而这两颗芯片从设计定位上就很不一样。CPU 是 cache 大、控制单元多，适合写很复杂的 C++ 逻辑；GPU 则是为吞吐量而生的，天生就是干高并发、处理大量数据的。架构上的这种差异，决定了你写程序时要同时兼顾两头——CPU 和 GPU 得很好地协作，才能写出高性能的代码。

对 CPU 来说，第一件事是把绘制数据按批次准备好、成批地交给 GPU：GPU 一次可能能吃几千个任务，你要是一次只慢吞吞地给一点，就会造成 GPU 等待。这一点很早之前就在特别强调——把任务打包好、整批扔给 GPU。

第二件事，CPU 虽然没有 GPU 那么多核、那么多线程，但它自己也在不断扩充多任务能力，核数一直在涨。2014、2015 年那阵子，大家就在讲并行编程应该怎么做：CPU 的任务怎么并行化，尤其是现代图形 API 怎么做并行的提交——command list 这些东西，本质上就是在 API 层面为 CPU 的多核化做准备。

### 一帧的旅程：从 game loop 到屏幕

从引擎层面看，完成一个绘制任务要经过很多东西。拿 Unity 的基本 game loop 举例：一开始是 physics——物理引擎这些东西，是纯 CPU 计算的；接着处理不同的场景世界；再跑你的一大堆脚本——处理怪物、攻击、各种判定这样的逻辑。相对 gameplay，render 反而是逻辑比较清晰的一块：做 render 本身，之外还有 shadow、GI 这类各种各样的计算。从这个 loop 就能看到，任务有明显的分阶段、分类型。

为了应对这种任务结构，现在的引擎一般会把线程拆开。一个是 game thread，专门干主逻辑：刚才说的物理、gameplay 这些。当然 CPU 有那么多核，game 里适合并发、适合异步的任务——比如大量物体的物理判定、大量物体 game logic 的执行——也会扔给任务线程去做。另一个是 render thread，管绘制这件事怎么控制：game thread 把所有物体、物理都决定好了，动画也播放到位了，render thread 就把场景里要绘制的物体做剔除、把绘制数据准备好——包括材质在内——准备好后提交。UE 其实还会提供一个 RHI thread，专门做绘制指令的提交；我们这里把它和 render thread 统在一起说，render thread 就更多管绘制的东西——从 gather 把 game 已经弄好的数据接过来，直到绘制指令提交出去，都算 render thread 的活。

```text
game thread：物理 / 脚本 / gameplay 主逻辑（适合并发的任务扔给任务线程）
      │  gather：把本帧要画的东西交出去
      ▼
render thread：剔除、准备绘制数据，记录并提交 Vulkan 指令
      │  提交（此时指令还没到 GPU）
      ▼
驱动：把 Vulkan 指令翻译成 GPU 指令，放进队列排队
      │
      ▼
GPU：按自己的调度从队列取指令执行，画进离屏的 frame buffer
      │  V-Sync 信号到来
      ▼
交换链 display：把这一帧刷到屏幕上
```

读图：一帧不是一条线程从头跑到尾，而是沿着 game thread → render thread → 驱动 → GPU → 屏幕这条链流动，级与级之间都隔着队列。

具体展开说：你在代码里写了一个 Vulkan 指令，比如 `vkCmdDrawIndexed`，这个时候它其实还没到 GPU 上去。指令提交给 GPU 之后，GPU 也会把它放进一个队列——用 Vulkan 的时候你能看到 queue 这种东西——然后 GPU 按自己的调度，等有空闲了，再真正执行你这次提交的这批指令。执行结果画进离屏的 frame buffer；等 V-Sync 信号来了，交换链 display 的时候，把这一帧刷到屏幕上。整个引擎就是以流水线的形式在干这件事。

### 最慢的一环决定帧率

既然是流水线，测帧率的时候就记住一条：最慢的一环决定最终的帧率。流水线里只要有一个人慢，就会拖累整个最终表现。

UE 里用 `stat` 这类指令可以看到各线程一帧的执行时间：game thread；render thread——通常意义说的 draw；RHI thread——专门做绘制指令提交的；还有真正的 GPU 执行。比如示例里 GPU 执行是 9.1ms，那整个帧率就是被 GPU 执行这一环卡死的——也就是我们常说的 GPU bound。

所以当性能不达标——比如预期 60 帧、现在只跑 30 帧——你首先要定位的是：这条异步提交的管线里，到底哪一环出了问题？这就需要测量，把每个环节大概花多少时间量出来。

display 这一环一般不用测：显示器的刷新是固定的。虽然有 V-Sync、G-Sync 这些东西，但基本可以认为它是恒定的——比如开了 V-Sync 就锁 60 帧。要测的话，把 V-Sync 关掉再测：关掉之后，整个指令流就不会等 V-Sync 信号了。

### CPU 好测，GPU 有陷阱

把 display 排除掉之后，要测的就是各线程一帧的耗时、瓶颈在什么地方。game thread、render thread 都跑在 CPU 上，测试相对简单：每帧之前、之后用 C++ 标准库的 `std::chrono` 打两个时间戳，一减就得到这一帧的耗时。

真正容易想错的，是 GPU 时间怎么测。一个常见的误解，是把 Vulkan 指令的提交时间点当作 GPU 的执行时间点。这是不对的：提交时间点只说明你把指令交出去了，完全不能代表它真的执行完了。当然你可以用 `flush` 这类指令强制刷新，但这会严重影响真实的性能。

> **易错点**：Vulkan 指令的提交时刻 ≠ GPU 的执行时刻。两者之间隔着驱动翻译和 GPU 队列，通常要延后几帧。

要真正知道 GPU 上的执行时间，用的是 GPU 的事件查询——Vulkan 提供了自己的时间戳函数。做法是：提交本帧第一条 Vulkan 指令之前，先写一个时间戳 t0；提交完最后一条指令之后，再写第二个时间戳 t1。GPU 真正执行到这两条记录动作时，会把当时 GPU 上的时间分别记下来；之后通过 get query 这类查询接口把时间戳取回来，`t1 - t0` 才是这一帧在 GPU 上真实的执行时长。

```text
vkCmdWriteTimestamp(t0)   ← 本帧第一条绘制指令之前
……本帧全部绘制指令……
vkCmdWriteTimestamp(t1)   ← 本帧最后一条指令之后
隔两三帧、确认已执行完后非阻塞查询：t1 - t0 = 本帧 GPU 真实耗时
```

这里有个细节要注意：正因为提交和执行之间有延迟——一般要延后两三帧，具体取决于 double、triple buffering 的配置——你查询的时候要等上几帧，确认这部分工作真的执行完了再去取；而且要非阻塞地取，别让 CPU 干等。

有了 game thread 一帧的耗时、render thread 的耗时、GPU 的耗时，你大致就能知道这一帧是被管线里的哪一环拖累了——需要解决的瓶颈在哪，就去哪做针对性的优化。

### 定位之后：常见毛病与趁手工具

常见的瓶颈分布大致是这样：game thread 上，去看脚本、物理、网络这些东西；render thread 上，是不是动态物体过多、灯的数量过多、draw call 数量过多；到了 GPU，就会涉及贴图资源、三角形数量、贴图数量、分辨率、raytracing（如果 raytracing 太复杂）、显存——这些都会吃掉很多。

CPU 端的工具相对好找。用 VS 开发的话，Visual Studio 的 Profiler 最简单，能给出每个函数、每条指令大概耗费了多少 CPU 时间；如果是 Intel 的 CPU，还可以用 Intel VTune Profiler 做更细致的分析——不只是函数本身，还能看到核啊、线程啊这些层面的东西。UE、Unity 也都提供引擎内部的 profiler，让你了解引擎内部各个阶段在干什么、各耗时多少，真实定位到问题瓶颈出现在哪个地方。

GPU 就需要额外的工具了。有些是做性能分析的，有些是做 debug 的——但 debug 工具也能帮你看性能，因为它能展示整个 GPU 的状态、每条指令做了什么。PC 上常见的是 RenderDoc、Nsight；移动端不管是骁龙还是苹果，也都会提供对应的性能分析工具，只是方便程度不如 NVIDIA。今天重点讲 Nsight——GPU profiling 的概念各家大同小异，都是管线那一套。

### 补一课 GPU 架构：SIMD 与 SIMT

在讲 GPU 性能分析之前，得先强行插一段基础的 GPU 架构——不补这一课，后面 profiler 里那些单元你看不懂。

先看开普勒（Kepler）架构 GPU 上一个 SM（流多处理器）的构成：里面密密麻麻全是"核"。严格讲这些也不能叫核，它们就是一个个 float32 的处理单元，一条条 lane。再对比 CPU 和 GPU 上指令形式的差别，就能看到两种并行哲学。

CPU 上其实也有并行手段。一种是 OpenMP 这类，把 for 循环并行化；另一种是 CPU 提供的特殊指令 SIMD——single instruction multiple data：发射一条指令，可以同时处理多个数据，靠的是 AVX、AVX2 这类向量单元，一次能处理非常多的数据。但它的问题出在编程模型：向量化得由你编程者自己解决——你得人肉搞清楚数据应该怎么 pack、怎么摆。所以在 CPU 上做计算，用向量化做加速本身没问题，就是写起来不算复杂、但确实麻烦。

GPU 同样是并行处理大批量数据、大吞吐量，但编程模型偏向 SIMT——single instruction multiple thread。和 SIMD 一字之差，差的就是 data 和 thread：data 只是数据的描述；thread 是一个完整的逻辑单元——至少在编程端表现出来的，就是一个函数。你作为编程者的心智负担，其实就只是写好一个 thread 的执行体；整个调度、数据怎么摆、并行怎么执行，都由 GPU 自己的 instruction decode 和 warp scheduler 完成。而且 GPU 的并行单元，比 CPU 上的向量单元多得多。

| 对比项 | CPU SIMD | GPU SIMT |
| :--- | :--- | :--- |
| 一次发射 | 一条指令处理多个数据 | 一条指令发射多个线程 |
| 编程单位 | 数据怎么 pack 要人肉安排 | 写一个线程函数，调度交给硬件 |
| 典型载体 | AVX / AVX2 向量单元 | warp（32 线程 lockstep） |

#### warp：锁步执行的基本单位

这里有个重要概念：warp，或者叫 wavefront。CUDA 里比较常用 warp 这个叫法，AMD 叫 wavefront。SIMD 是一条指令处理多个数据；GPU 里是按线程来的——一条指令发射出去，多个线程同时执行这一条。warp 的大小：NVIDIA 一般是 32 线程，AMD 的 wavefront 是 64 线程，手机上可能还有不同的大小，比如 16 线程之类的。这些都是概念上的差别，关键是记住一条：以 32 个线程为单位，这 32 个线程执行的指令是一样的，而且同一时刻一起执行——这叫 lockstep（锁步）执行。

SIMT 的这个特点意味着：编程者写代码时，大概率只需要管这一个线程大概怎么跑——当然有些访存啊、这些你可能要关心——但数据怎么存放、寄存器怎么管理，大部分时候不用你操心，由 GPU 自己来管，心智负担减少很多。

#### 从 thread block 到 warp：多出来的 inactive

warp 和 compute shader 里 thread group 的映射关系值得单独说。写 compute shader 时，一个 thread group（thread block）里有很多线程，你写的时候自然把它当成自己的并行单元——这样想没毛病。但 GPU 真正调度的时候，是按 warp 的数量去执行的：哪怕你有 240 个线程，也是每 32 个线程组成一个 warp 去执行，因为硬件一次就是 32 个一起动。

```text
thread group：240 个线程
  → 按 32 线程/warp 向上取整 = 8 个 warp（256 个槽位）
  → 最后一个 warp 只有 16 个线程真正活跃，其余 16 个 inactive
```

240 个线程凑成 8 个 warp，就多出 16 个槽位——最后一个 warp 只有一半线程真正活跃，另一半是 inactive 的、白付的并行位。但硬件还是按 warp 粒度去调度，保证最大并发度。

顺带一提：compute shader 是 DX11 推出来的，相当于给 graphics 提供了直接用 GPU 做通用计算（GPGPU）的能力。但在更早的时候，vertex shader 这类着色器就已经在通用流水线上并行执行了。

### 图形管线里也有 warp

#### 顶点着色：成批执行与顶点缓存

vertex shader 相对简单：这一帧要处理很多顶点，它们就是并行执行的——上一节课也讲过。它同样是一批一批来：32 个顶点或者 64 个，不同厂商不一样，一起执行 vertex shader。VS 执行完的数据会放进 post-transform vertex cache；后面按 primitive 往下走的时候，碰到重复的顶点就直接剃掉。这一级执行完，流水线走到下一步——比如从这个 post-transform vertex cache 里去拿数据。

#### 像素着色：quad、tile 与 helper lane

pixel shader 有一点不同。PS 是以 quad 为单位的——上节课讲过，一个 quad 是 2×2 四个像素，对应四个线程。执行的时候，GPU 会把屏幕空间（RT 空间，也叫屏幕空间）分成比如 128×128 的大 tile，由 GPU 里对应的 tile 单元去扫这个屏幕，找出活跃的 quad。然后这些 quad 会被打包成 warp：还是按 32 线程一个 warp 执行，一个 warp 就能同时装下 8 个 quad——32 个线程、8 个 quad 一起跑。

跟 compute 里"凑不满的线程是 inactive"一样，PS 也有对应的概念：quad 里没被三角形覆盖到的像素，就是 helper lane（helper thread）。helper lane 的存在是有用的——算梯度需要 2×2；但 GPU 也能让你知道某个 lane 是 helper：通过比较新的 HLSL 指令里的 intrinsic，可以查到这个 lane 是不是 helper lane、它能拿来干嘛。PS 虽然没有像 threadgroup 那种显式的并行映射让你操作，但底层同样是以 warp 为单位执行的。

### 分支：warp 内发散才付代价

PS 里大家最关心的性能问题就是分支。分支指令也是以 warp 为单位执行的，所以分两种情况。

情况一：warp 内的线程走不同分支。看代码示意：偶数线程走 work1，奇数线程走 work2——那在一个 warp 里，0、1、2 号线程走的就是不同的任务。

情况二：warp 内走的是同一个分支。因为执行尺度不止 warp 一层——一次可能要调度一千多个线程——比如前 64 个线程做一件事、后 64 个做另一件事。这时每个 warp 内部走的指令完全一样，第一个 warp 和第二个 warp 各走各的分支，对 warp 内部来说完全没有负担，各走各的指令就行。

如果分支条件来自 uniform，那就属于情况二：指令上的性能负担只是取 uniform 本身，if 里真正那些指令根本不会执行。

而情况一就不同了：两条分支里的算术指令都会执行——work1 和 do other work 都会跑。GPU 会在判断的时候通过 predicate 知道这条指令对哪些线程是有用的、哪些线程是 inactive 的；为了保证安全，inactive 线程的读写会通过 mask 屏蔽掉——读写不会真的发生。但时间上，你还是把两条分支的代价都付出了。

> **结论**：分支的代价以 warp 为单位衡量。warp 内一致，没走的分支不付钱；warp 内发散，两条分支都得执行，只是无效 lane 的读写被 mask 掉。

### 切换零开销：用别的 warp 藏住等待

分支说的是 warp 内部的事；把尺度放大——屏幕上有海量像素、一次要调度非常多的线程——那就是线程调度的问题了。

还是以 CUDA 架构为例。一个流处理器（SM）上有 4 个 warp scheduler，支持双发射——一次可以发射两条指令。双发射更多是在指令有并行度的时候才能做得更好；理论上，4 个调度器可以同时执行 8 个 warp 的指令。

麻烦在访存。如果碰到 cache miss，或者下一条指令要读 texture 而 texture 还没回来，这条指令就有 latency，得等十来二十个 clock。GPU 的对策是尽快切换：这个 warp 在等，就切到下一个已经 ready 的 warp，去执行它的指令。

在 CPU 上，我们说这种上下文切换是有负担的；但 GPU 上切换本身没有 overhead——因为寄存器、shader memory 这些资源都是预先分配好的。比如来了一个 1024 线程的 thread group，整个 group 就在这个流处理器上优先分好了位置：虽然一次只能执行 4 个 warp，但其他 warp 的资源也都已经分配好了。所以这个 warp 一等，马上就能刷到下一个 OK 的 warp 上去执行。

这对写 shader 的启示是：指令量别太少，要保证流处理器下面有足够的 warp 供你调度——这个 warp 在等访存，立刻有别的 warp 顶上，SM 就闲不着。这里引出一个很重要的概念：occupancy——你到底有没有把流处理器的性能占得足够满。这个后面还会展开。

### 访存：32 个地址如何变成请求

除了执行调度，还有一个很重要的事实：访存。GPU 也是各种级别的存储：DRAM 是显存，对显存的访问下面有 L2、L1 这样的多级缓存。GPU 有一点不一样——它是从 graphics 发展起来的，所以除了 L1 之外，还有一个专门的只读缓存（CUDA 里可能叫 read-only cache；对应到 graphics，大部分就是 texture cache），还有 constant cache——更多是服务 uniform 这种东西；流处理器上本身还有 shared memory。

访存也是以 warp 为单位做的。GPU 的 L1 跟 CPU 一样有 cache line 的概念——128 byte；GPU 访存的基本单位可能是 32 byte，叫一个 segment，一次可以请求 1 个、2 个或 4 个 segment，也就是一次请求的量可以是 32 byte、64 byte 或者 128 byte。

具体到一次执行：比如一个 warp 要访存，因为 32 个线程是并行执行的，每个线程只会提供一个地址，warp 一共给出 32 个地址，硬件会把这 32 个地址整合成请求。假如读的是只读数据，就先到 L1 里沿 cache line 找：这 32 个地址如果能整合成一个对齐的 128 byte cache line，那发一个请求就够了；如果是不对齐的 128 byte，可能就得拆成两个请求。cache line miss 了，再把这个 cache line 请求变成对内存的请求——比如打到 L2，拆成 4 个 32 byte 分段（4×32）作为一个请求；非对齐的话就变成两个二分段请求，以此类推。

texture 的处理跟普通 cache 不太一样：刚才说的是 32 个线程的 32 个地址由硬件整合成 cache line 或多个 segment 的请求；texture 则是按每 4 个线程为一个请求单位——32 线程的 warp 会生成 8 个请求，硬件再把这 4 个一组合并成若干内存地址请求。这 4 个一组，我怀疑更多是考虑了 quad 这种东西，但我没找到确切的资料，不敢确定。

> **结论**：一个 warp 内请求的地址越对齐、越集中，整个访存的代价就越小。这是写 shader 时优化访存最朴素的依据。

### 图形管线的专用硬件

刚才说的都是通用的流处理器——它更多负责执行和调度，跟 GPGPU、compute、CUDA 的硬件比较接近。但 graphics 管线里还有一些特别的东西。从 input assembly（IA）开始就有专门硬件：处理 primitive 和 vertex 的输入；vertex shader 要用的顶点抓取也有专门单元——比如专门为 vertex 做准备的 PD、VAF 这类单元。往下，还有处理 primitive 的 VPC 这类单元；光栅器是 graphics 本身就有的；做 frame buffer 操作的也是专门的硬件。大家通用的是 SM 的 pipeline 和内存这一块——float32 运算、load/store 这些基本一样；shader 部分更多的还是调度、计算以及 memory，跟 CUDA 类似。

### Nsight：Speed of Light 与吞吐量

有了架构概念，就可以看 NVIDIA 的 GPU profiling 了——选 Nsight 只是因为它工具好、大家手上更方便。

为什么我们能看进 GPU 内部？因为 GPU 内部各种管线的执行状态，只有驱动厂商才掌握那么多细节——驱动里就有各种 counter，记录 GPU 的运行状态。

GPU profiling 里最大的一个着眼点：GPU 是高度并行化的系统，核心指标就是吞吐量，以前叫 Speed of Light（SOL）——你跑这个元器件、这个单元，是不是把它跑满了？是不是跑到百分之百了？跑到百分之百，它就是瓶颈。Nsight 的 profiler 里有一个简单流水线的展示，各单元大概用了多少，绿色的格子配一个数字表示占用百分比。整个 profiling 就是基于"当前任务对 GPU 各单元的占用"来做性能分析的。

#### Frame Profiler：指令重放

Nsight Frame Profiler 本质是指令重放，跟 RenderDoc 这类抓帧工具的逻辑类似：hook 住你的 DLL，Vulkan/D3D 指令的每次调用都被记下来——我就知道你每次执行了什么、调用了什么——下次再重放出来。这样每个事件都能看：比如一个 draw，mesh、几何是什么样子，输出的贴图是什么样子——每条指令都重新算一遍，把里面所有的输入输出都缓存下来展示给你。

它比一般抓帧工具做得更细：每条指令之后，还能对应采集这条指令在 GPU 里执行时的各种 counter——把你的东西放一遍，甚至多放几遍，记下平均每次跑的时候 counter 是什么样子，把这些数据全给你，就能分析每个 GPU 单元的具体情况。

代价也要心里有数：因为是重放，重放时的 GPU 活跃度、负载跟你真实执行时不一样；而且为了统计这些信息——这个 thread 是不是在执行、是不是活跃、访存怎么样——统计本身也有 overhead。

> **结论**：Frame Profiler 给的绝对耗时别当真，相对值是准的。比如某个 pass 显示 6ms，未必是你真实在 GPU 上跑的 6ms；但你优化之后它变成 5.5ms，就能确认这个优化的比例是成立的。

有了这个，能做非常细致的分析：某个 draw 里某一个特别的三角形、某一个特别的 draw call，它内部的代价是什么样子，都能比较清楚地看到。

#### GPU Trace：实时但粗粒度

另一种是 Nsight GPU Trace，相对轻量级：直接挂在正在跑的程序上，立马就能知道当前 GPU 真实执行的时间怎么样、比例怎么样，可以连着抓很多帧。但没那么细，只有大概念层面的信息。

### 一个抓帧实例：读出两个信号

给一个实际抓到的例子，做 mesh shading 的——拿 VS 这类场景举一反三。可以看到各单元的占用分布；比如把某个特性打开、关闭各抓一次，对比性能有没有变化——因为你能看到每个 pass 的执行情况，就知道你的优化对哪些单元起了作用。而且它给的是任意时刻 GPU 上各单元的吞吐量：一路往下滑，右边会告诉你每一项吞吐量的含义。比如 bus——正常应该能传多少 GB/s，现在只用了 6 GB/s，是不是没用满？又比如 SM——本来能执行 10 个 warp，现在因为一些原因只执行了 5 个。这些都在告诉你：哪些地方可以去优化。

这张图里能读出两个典型信号。

第一，看 forward pass：画这个东西的时候，SM 的吞吐量已经成为限制——SM 吞吐量就是你现在应该优化的方向，按这个去找问题。

第二，GPU 真正开始执行的时间不是一帧开始的时间，前面有一段空闲。这段时间里 GPU 根本没有任务——GPU 跑太快了，在等 CPU 给我们提供数据。这时瓶颈可能就不在 GPU，而是 CPU 该怎么把 GPU 更好地利用起来、喂得更饱。

### 逐单元认识这些计数器

接着看 profiler 里到底列了哪些单元。从上往下、顺着管线过：

- **VAF**：管 vertex attribute fetch。VS 在 SM 上执行时，你的顶点数据、顶点 attribute 的 fetch 用了多少，它都有账。vertex input 里你写 position、normal、texcoord……可以一直往里堆，但一个顶点要是写了十个、二十个属性，这个单元就会产生很大的瓶颈。
- **PD**：更多关联 index buffer、primitive 这类东西。如果瓶颈出在这，要考虑 index buffer 是不是有问题——比如格式：float 不该用；现在是 int32 的话，int16 会不会更好？
- **图元处理的统计单元**：管顶点、图元处理这一层的各种数据，都跟图元相关。
- **Rasterizer**：不用多讲，三角形光栅化的代价是多少。
- **SM**：真正的计算执行与调度——这段 shader 执行的时候，问题出在哪。
- **L1、L2、VRAM**：整个 GPU 缓存层级的东西。
- **Depth ROP、Color ROP**：到了 RT（render target）这一层要管的事。

### occupancy：寄存器数量的硬天花板

这些单元里绕不开的一个老问题是 occupancy——之前也提过——你的流处理器上到底能跑多少 warp。如果本来就没多少 warp 在上面，整个并行度就高不起来；访存卡住也一样，active 的并发度上不去。

一个 SM 上最常见的限制出在寄存器。一个 SM 的寄存器就那么多——比如一共 1 万个；又因为前面说过线程资源是预先分配好的，所以：

```text
SM 寄存器总量（举例）：10000
  每线程用  100 个 → 最多容纳  100 个线程
  每线程用 1000 个 → 最多容纳   10 个线程
```

寄存器用量直接决定 SM 上能驻留多少线程，这是很大的限制度。profile 里能看到每个 shader 用的寄存器数量是多少，看到了就回头看你 shader 怎么优化。

### 方法论：按瓶颈往下钻

最常见的错误姿势是拿着一份通用清单挨个试。其实核心就一句话：peak performance percentage——找到当前为止性能最大的问题。先按瓶颈去找：

```text
帧率不达标：逐层往下找
────────────────────────────────────────
game thread   ── 脚本 / 物理 / 网络
render thread ── 动态物体 / 灯数量 / draw call 数量
GPU           ── 找最耗时的 pass，追问它为什么耗时
      │
      ├─ GPU 不活跃（帧首空闲）→ 为什么没喂够指令？查 CPU 提交
      ├─ GPU 活跃 → 看吞吐量最高的单元，针对它优化
      └─ 整体吞吐低（如 <60%）→ 为什么吞不动？
            ├─ 在等资源 → 查等待原因
            ├─ 访存太密集 → 减访存
            └─ 调度不过来 → 查 occupancy（寄存器），
                            或用 async compute 填满空闲
```

大层面先分清是 game thread、render thread 还是 GPU；到 GPU 层面，先找耗时最久的那个 pass——比如它耗了 9ms，那就问这 9ms 到底是因为什么：

- GPU 不活跃？就像刚才帧首空闲那种——那就看为什么没有提交足够的指令。
- GPU 已经比较活跃？那就看吞吐量最高的单元是什么，针对它优化。
- 整体吞吐量不高，比如小于 60%？那要找为什么吞不动：是资源没到位在等，还是访存太密集、跟不上——那就要减访存；还是 shader 本身写得不好（比如寄存器用太多），导致没有足够的 warp 可供调度——查 occupancy 是不是 OK。调度实在调不过来，能不能用 async compute 这类手段，把其他任务填进来、把空闲填满？

说到底就是具体问题具体分析，后面附的文档里 AMD 会给很多具体例子。但真实做下来你会发现：不同平台瓶颈不一样——你在这个平台优化好了，它在别的平台上可能完全不是瓶颈。console 好做一些，照着一个固定配置优化就能做得很极致；PC、手机碎片化严重，在这上面做的优化，到别的平台可能是负优化，要非常 careful。所以还是得实测，没有放之四海皆准的基准。

另一点：你得大致了解每个 pass 是怎么做的、算法大概什么样——如果是访存型，到底有哪几次访存、访存是密集还是非常稀疏。心里有这个概念，才能做好针对性的优化。

### 给后面的课准备一把尺子

今天讲这一课，其实也是在为后续课程做准备。后面我们会做很多 geometry、shader、texture 相关的东西，它们都会 impact 到 GPU 管线的不同单元：

- 做几何相关的减面：模型面数变少，顶点数变少，VAF 的属性抓取肯定变少；顶点数、面数变少，裁剪、光栅化的代价都会变小。
- 把一部分绘制裁掉：对 VS 来说，shader 执行数量变少了，SM 的执行压力就变小，对应的访存压力也会变小。
- shader LOD：更直接作用于流处理器——删掉一次贴图采样，贴图缓存、访存速度都会变快；删掉某段 for 循环，整个指令数变少。
- texture LOD：主要针对访存。

有了这样的 profiling 工具，后续做完简化放到 GPU 上一跑：首先统计上能看到面数确实少了；其次能看到这个优化对管线里这一部分造成了什么样的影响——不再只是盯着一个帧率，能看到更细节的东西。希望后面做完作业之后，大家能用这样的工具去看一下 GPU 大概是什么样子，你的变化是不是符合预期。

但有一点要注意：这跟 GPU 平台强相关。如果你的 GPU 特别好，把一万面片优化成一千面片，可能完全没感知——反正跑不满。还是那句话，具体问题具体分析，而且一定要在瓶颈端做优化，才会有收益。

## 三维模型的表示方式与网格基本概念
> 对应块：BLK10 | 覆盖分集：P07上 | 块标题（分集名）：《7. 几何处理与模型减面引言》

终于又回来了。课程作业的事情交代完，我们从这一讲开始进入几何处理。先把接下来三节课的目录摆在这儿：今天这一讲讲两件事——一是三维模型在计算机里如何表示，都有哪几种方法；二是大致过一过模型减面都有哪些思路。下一节课重点讲在保纹理的前提下如何减面；再下一节课介绍各种不保纹理的模型减面。中途有疑问就直接发评论，我看到会及时回答。

### 表示三维模型的几种方式

要在计算机里把一个三维模型的形状用数字表示出来，路子其实不止一条，我们挨个看。

#### 参数化曲线曲面：CAD 的老朋友

最早就有、至今也很常见的一种表示，是参数化的曲线、曲面（当然也有体）。直觉是这样的：二维平面里的一条曲线，它的 $x$、$y$ 两个坐标都可以写成一个参数 $t$ 的函数，用 $t$ 来控制它的形状；嵌在三维空间中的一张表面（surface），就用两个参数来控制——一个 $u$ 方向的参数，加一个 $v$ 方向的参数。比如我们学过的 Bézier 曲线、曲面，就是这个路数。

这种表示的三维模型长什么样？是一片一片的曲面片——这里的示例图来自 OnShape 这个 CAD 网站。参数化曲线曲面这种表示方式，在 CAD（计算机辅助设计）、工业化制造这一块非常常见、非常流行，大家一般都是用它来表示三维模型、去做建模。

#### 多边形网格：渲染的主角

另一种表示就是网格。想象一下，一个连续的表面其实可以用离散化的概念来解释：用很多多边形拼接起来去逼近它，而且这种多边形的离散化方式可以逼近任何复杂的表面。多边形最常见的是三角形，也可以是四边形、五边形等等——但最终渲染的时候，还是要转成三角形来表示。对网格表面贴上贴图、赋予一些材质（比如颜色），就可以拿去做渲染了。

#### 点云与距离场

再有一种表示是点云。如果只是想大概看到模型的样子，点云也够用。它一般来自三维扫描仪——激光扫描仪扫出来的数据就是点云。

跟点云息息相关的另一种表达，是距离场。点云只是离散地在模型表面上"踩"了一些点，而我们有时希望表达出连续的表面，那就可以用距离场的形式：在整个空间中，对任意一点计算它到真实表面的距离。空间中一点离表面越近，颜色越浅，由近及远有个颜色的渐变。这种表达方式本身没有表面的样子——没有真实的网格数据，所以很难直接把 surface 画出来，需要用专门的技术把它转化、提取出来；它的优点则是对它做距离一类的查询会非常方便。

中间插一个评论区的问题：自研游戏引擎属不属于游戏开发？当然算。游戏开发就是跟游戏相关的技术研发，而游戏引擎里集成的正是各种各样的技术。

#### 用神经网络表达模型：NeRF

还有一种，是最近非常流行的：用神经网络（neural net）来表达模型的数据，代表就是 NeRF。什么意思呢？输入是一个五维的信息：$x,y,z$ 表示三维空间中的一个点，$\theta$ 和 $\phi$ 表示观察到这个点的方向——比如一条视线的方向；经过这个神经网络，就得到这个点的 RGB 颜色，以及 $\sigma$——它的 density，密度信息。注意，这个输出要结合体渲染的方式，才能把模型可视化出来。前面那些表示——点云、距离场、网格、参数化曲线曲面——是结合我们之前讲过的光栅化（rasterization）或者光线追踪来渲染的；NeRF 则更多是跟体渲染结合。

它最近流行，主要是因为效果逼真：输入只是一些照片，数据量比较少，通过训练这个神经网络，就能获得一个可以从更多视角去观察的模型表达，非常逼真。

用一张示意图概括这种表达：

```text
输入 (x, y, z, θ, φ) ──►  神经网络  ──►  输出 (RGB, σ)
 位置 + 观察方向                        颜色 + 密度
                    （输出要配合体渲染，才能把模型画出来）
```

这行字符画读下来就是：五个数进网络，出来颜色和密度，再走体渲染成像。

当然，关于模型的表示还有很多种，比如 neural 的 SDF 等等，这里就不介绍太多了——我们更关注渲染，所以后面会集中在网格模型这种表示方式上。最后用一张表把几种表示收拢一下：

| 表示方式 | 一句话理解 | 用在哪、怎么渲染 |
| :--- | :--- | :--- |
| 参数化曲线曲面 | 参数 $t$ 控制曲线、$u,v$ 控制曲面，模型是一片一片的曲面片 | CAD、工业化制造建模 |
| 多边形网格 | 多边形拼接逼近任意复杂表面，渲染时转成三角形 | 光栅化、光线追踪 |
| 点云 | 离散"踩"在表面上的一堆点，多来自激光扫描 | 光栅化、光线追踪 |
| 距离场 | 空间中每点存到真实表面的距离，查询方便，画表面要先提取 | 光栅化、光线追踪 |
| 神经网络（NeRF） | 5D 输入换出颜色与密度，少量照片训出逼真模型 | 体渲染 |

### 形状靠点线面，颜色靠贴图

网格模型怎么表示，我们再进一步说。比如从网上下载了一个三维模型，渲染出来是某个样子。要把这个样子表达出来，一头需要网格——点、线、面和它们的组合——来表达模型的形状：轮廓长什么样、原型如何、曲面怎么起伏，全靠网格数据。另一头，模型还有颜色。颜色怎么表达？靠一张图片，我们一般叫它贴图（texture）。要做的就是把这张图贴到 mesh 的表面上去。

那怎么贴上去呢？这里需要建立一个 UV 展开。模型表面是三维的，贴图是躺在平面上的二维图片；把三维的东西映射到二维，一般需要先对它做展开，希望建立"三维表面上任意一点"到"二维平面上一点"的对应关系，而且最好是一一对应——这样，三维表面上任意一点，都能在图上找到它对应的颜色、对应的 pixel。实际使用中，反过来也希望二维平面上的任意一个点，在三维空间中有它的对应。为了简化、让大家容易理解，我们先按一一对应来讲；实际上，图片里的一个点是可以映射到三维表面上的不同点的，这样能更好地压缩信息。

那怎么把一个复杂的三维表面摊到平面上、还能保持一一对应呢？往往需要对模型做 cut——把它切割成一片一片的，就像图里那样：这里一大片对应的大概是脸部，这一片、还有这一片是两只耳朵。这个把三维表面摊开铺到二维平面的过程，就叫 UV 展开。为什么叫 UV？因为平面是两个维度嘛——一个 u 坐标、一个 v 坐标，所以叫 UV 展开。

这样，我们就建立了三维表面与二维纹理的对应关系。渲染的时候，逐个三角形、逐个点去着色，就能从这张图里查询、获取对应的颜色，也就把模型的样子画出来了。

```text
三维表面（网格，点线面定形状）── 切开 + 摊平 ──► 二维贴图（图片定颜色）
      任意点 p      ◄────── 一一对应（UV）──────►      像素 (u, v)
渲染时逐三角形逐点，拿 (u, v) 去贴图里查颜色，模型的样子就画出来了
```

这张图的关键就是中间那座"一一对应"的桥：UV 展开先把表面切开摊平，渲染时再靠它查回颜色。

### 把网格看成一张图：连接关系

接下来是网格模型的几个基本概念：连接关系、拓扑、几何量，以及在写代码时如何组织、表达三维模型的数据。这里只讲跟实际应用相关、尤其是后面讲减面方法会用到的那几个概念——真要详细展开，得花上好几节课，这里先压缩着讲。顺带回答评论区的一个问题：有同学问，这一块讲的是建模还是图形学？其实都是图形学。你做渲染、做动画、做模拟，都绕不开建模这一块——模型的表示、属性、压缩和优化处理，跟后面关心的渲染、动画的表现是息息相关的。

先说连接关系。一个网格有点、有线、有面；所谓连接关系，就是把它形成一种 graph——就是本科里学过的图，只不过除了点和边之外，我们这里还加上了面。下面仍以三角形网格为例。再重复一遍：网格不一定是三角形的，四边形、五边形都可以——评论区有同学总结"两点成线、三线成面，面模型要三边面或者四边面"，对的，当然也有五边面、六边面，建筑里六边面还比较常用。

第一个概念是度数：一个点的度数是多少？就是这个点相邻多少条边。当然也有人用一个点相邻多少个三角形来表示度数，所以理解的时候，要根据具体文献的上下文辨别它说的是哪个。

> **易错点**：顶点的"度"在网格文献里有两种口径——相邻边数，或相邻三角形数（后者也常写作 valence）。两种说法都存在，读文献先看它怎么定义。

第二个概念是边界与内部。一条边如果只相邻一个三角形，一般就是边界边；如果相邻两个三角形，那它一般在内部——这是对流形模型而言的划分方式，流形马上讲。边界上的点，它相邻的边数和相邻三角形的数目是不一样的——所以讲一个点的度数（或 valence）时，还是得根据上下文来辨别。

第三个概念是邻域。一阶邻域，就是通过一条边就能直接到达的点——围着中心点的"这一环"；这一环里的边，有时指从中心点连出去的边，有时指环上的边，还包括环里面的那些三角形。二阶邻域，就是走两条边（两步）能够到达的点，以及这样构建出来的整个局部网格里包含的信息。跟连接关系相关的概念其实还有很多，这里只留几个常用的。

### 流形与非流形

拓扑这里重点讲流形（manifold）这个概念。我们现在讲的一般是表面网格模型，通常是二维流形：表面上任意一点，取它局部的、很 local 的一个 neighborhood，这片连起来的小区域如果都能同胚地建立与二维圆盘的一一映射——也就是说能摊平到一个圆盘上——那这个模型就是流形的。

> **定义**：表面网格是（二维）流形，当且仅当表面上任意一点的局部邻域都能同胚地映射到一个二维圆盘上。

反例就是非流形：如果某一个点，它自己和它临近的区域无法映射到一个二维的圆盘上，那这个模型就是非流形。这是连续的概念。落到离散的网格上，具体怎么判断一个网格是流形还是非流形？其实挺简单。

点的非流形：看一个点以及它一阶邻域里所有相邻的三角形。这堆三角形如果能围出一个环——边界是一个环——那它就能映射到圆盘上，没问题；如果像两把扇子只在顶点处相接那样，边界是两个环，那就是非流形。

边的非流形：一条边如果相邻的不只是两个三角形，而是三条、四条、五条等等，那也是非流形。

还有一种情况：某个点的邻域摊是摊开了，但边界并不是一个简单环——像麻花一样拧了一圈再接回来——它同样不同胚于圆盘，也不是流形。

所以对表面网格来说，非流形一般是点的非流形和边的非流形这两类。顺带把边的情形总结成一句口诀：

```text
一条边挨着几个三角形？（对流形网格而言）
   1 个 → 边界边        2 个 → 内部边        3 个及以上 → 非流形边
```

一行读图：挨着一个三角形的边露出在模型边缘，挨着两个的藏在内部，挨着三个及以上的边直接违反流形定义。

### 欧拉–庞加莱公式

接下来介绍一个个人认为非常重要的公式：欧拉–庞加莱公式。它讲什么呢？它构建了点、线、面以及其它拓扑信息之间的一个恒等式。

记号先说清楚：$V$ 是网格里顶点的数目，$E$ 是边的数目，$F$ 是面的数目——这个面是通用的（general）多边形面数：模型里不管有三角面、四边面还是五边面，都算进去。

$$V - E + F = 2S - 2G - H$$

右边三个量一个一个说。

$S$ 是连通数（英文一般叫 number of components）：模型由几块互相连通的表面组成。比如一个模型有两块互不相连的表面——外面的环到不了里面，中间没有任何连接信息——它的连通数就是 2；一个球面，连通数就是 1。

$G$ 是亏格（genus）。通俗地讲：把模型切开，切几刀它还连在一起？球面的话就是 0——你再 cut 一刀，它就能整个翻开了；环面的话亏格是 1——切一刀，它还是连在一起的。

$H$ 是洞数：比如球面，没有洞，是 0；在球面上抠两个洞，它就带了边界——出现两个环——洞数就是 2。

```text
V − E + F  =  2·S  −  2·G  −  H

V 顶点数   E 边数   F 面数（通用多边形面，三角/四边/五边都算）
S 连通数 —— 模型由几块互不相连的表面组成（两块分离表面 = 2，球面 = 1）
G 亏格   —— 切几刀表面还连在一起（球面切一刀就整个翻开 = 0，环面切一刀还连着 = 1）
H 洞数   —— 表面抠洞带来的边界环个数（完整球面 = 0，抠两个洞 = 2）
```

一行读图：左边是纯粹的几何元素计数，右边把"几块、几个柄、几个洞"这些拓扑信息补进来，两边永远相等。

> **提示**：这里我把概念都通俗化了，有的地方可能不是很严格——还没到那种严格的几何分析的层次，大家觉得有问题可以指出来。但这个公式有时候还挺重要的。

### 常用几何量

下面这些几何量，是我个人觉得非常重要、也很常见的一些概念，大家有必要理解——这样后面介绍具体算法、冒出这些专有名词的时候，你才接得住。

**边长**：两点一线，这条线段的长度就是边长。

**面积**：三角形面积很直接；四边形的面积就有点让人困惑了——因为三维空间中的四边形经常不是一个平面，它可能是个翘起来的曲面，这时算它的面积有一定的歧义。大家一般会把它拆成两个三角形来算，也可以拆成多个三角形，取决于具体应用。

> **易错点**：三维空间中的四边形四点常不共面，"四边形的面积"并没有唯一答案——拆成两个三角形只是其中一种约定，换一种拆法结果可能不同。

**二面角**：一条边相邻着两个三角形，这两个三角形所在平面之间的夹角，就是二面角。这个量也非常常用。

**法向**：三维表面上任意一点，垂直于该点切平面的那个方向，就是这个点的法向的朝向；它还需要是单位长度。法向也就是平时说的法线。

**相交**：一类是模型自己跟自己交叉——模型的面片自己插起来了，这就是自相交；另一类是一个模型跟另一个模型交叉，比如一个 human 的三维模型跟一个 box 交叉，一个模型深入到另一个里面去了。

**退化单元**：单元就是点、线、面这些元素。常理认为三角形面积一般不为零，但从拓扑角度来说，三个点、三条线段就只能表达出一个三角形；而几何上它可能是退化的——面积为零的三角形，可以退化成一条直线，甚至退化成一个点。退化边就是边长等于零的边。这些概念虽然简单，但澄清一下，有利于大家保持对概念的一致理解。

### 包围盒：给算法一个尺度基准

还有一个概念是包围盒（bounding box）。包围盒的计算方式有很多种，这里说最常见的一种：对一个三维模型，能把它给框起来的一个盒子——比如一辆汽车的三维模型，我们计算它的包围盒。包围盒跟被包围的三维模型的紧致程度有关系；有 axis-aligned（轴对齐）的，也有非轴对齐的，都是一个长方体。

那为啥要提包围盒呢？很多时候我们在做几何处理时会经常用到这个概念，特别是在设置算法参数的时候。比如算法里涉及到模型的边长或者模型的大小——三维数据的模型大小差别可以非常大，面积可以接近于 0，也可以（把模型放缩得非常大时）接近于无穷大。我们又希望算法对各种尺度的模型都能处理，那一般的做法，是把设置的参数跟包围盒的某个尺寸挂钩——比如以包围盒对角线的长度做归一化的基准——这样算法就跟模型的尺度基本不相关，有力提升算法的鲁棒性。

### 曲率：一条线一个数，一张面无数个数

另一个概念是曲率，一般用它来描述模型表面弯曲的程度。对于曲线上的任意一点，它的曲率只有一个；但对三维模型的表面上一点，其实可能有无数个曲率——因为通过一点可以画无数条曲线，每条都有自己的曲率。

示意图画的就是这件事：对表面上某一点，先画出它的切平面（tangent plane）；在这个切平面的参考下，可以从无数个曲率里辨别出两个 principal curvature，即主曲率——一个是最小的曲率，一个是最大的曲率。主曲率的计算跟法向的定义非常相关。详细的概念可以去看延伸阅读里列的那篇文章；示例模型的可视化图展示的，就是各点的最小曲率、最大曲率分别长什么样。

### 特征：离开应用没法谈

最后一个概念是特征。什么是特征？这个因不同的应用而不一样，对它的理解需要真的结合上下文。举一个我自己的例子：我之前有一篇文章，做的是特征保持的六面体网格化。那在这篇文章里，"特征"具体指什么？输入一个三维模型，我要保持它的什么特征——把模型的表面做了一个划分，先提取出一些 corner（角点），这些就是这套方法里要"保持"的特征。

同样的词，在不同的算法里可能指完全不同的东西，所以读文献遇到 feature 时，先看那篇文章的应用背景是怎么定义它的。

到这里，网格的基本概念就铺垫齐了——连接关系、流形、欧拉公式、各个几何量，都是为后面做的准备：讲到具体的减面方法时，它们会一个一个派上用场。

## 网格处理入门：基本概念、半边结构与模型减面总览
> 对应块：BLK11 | 覆盖分集：P07下 | 块标题（分集名）：《7. 几何处理与模型减面引言》

这一讲是网格处理与减面的引言：先把几个绕不开的基本概念立住——特征、Hausdorff 距离、面的翻转、凸包；再看网格在程序里到底怎么存——一个构思很巧妙的半边结构；然后进入正题：模型减面。为什么要减、方法怎么分类、保纹理与不保纹理两条路线各自长什么样，一条条来。

### 网格上的几个基本概念

#### 特征：用二面角找出尖锐边

一个模型上棱角分明的地方，机器是怎么"看"出来的？做法是先提取出 corner，或者说比较尖锐的边。那什么样的边算尖锐边？判据还是二面角：一条边两侧两个面的夹角，如果离 180° 比较远——比如 120°、150°，或者 90°、60°——我们就认为它比较尖锐。

这些尖锐边会形成一个 graph；边与边之间、曲线与曲线之间，又会形成一些 corner——一个 corner 上可能连着好几条 sharp 边。这些 graph 还有可能把表面划分成不同的区域：黄色标出的是一块区域，粉红色标出的是另一块，区域之间的边界就是这些尖锐边。

我把这样的信息叫作**特征**。做网格处理的时候，我想保持这个特征——该尖的地方还是尖，该分开的区域还分开。

> **课间一问**：有同学问起游戏引擎。游戏引擎一般都会带一个物理引擎。那物理引擎是不是只涉及光学、声学、力学？我的理解是：物理引擎的目的就是更好地模拟这个世界——用你的数据去还原现实世界中发生的现象，所以不只是光学、声学、力学，热学这类跟物理相关的都可能涉及。其实整个计算机科学这门学科，涉及的知识点可以说是包罗万象。

#### Hausdorff 距离：两个形状差多远

距离的定义有好几种，这里讲一个比较常见的：Hausdorff 距离（豪斯多夫距离）。尤其在衡量几何处理算法效果的时候，经常用到它。

对两个形状，比如蓝色的和绿色的，我想知道从蓝色到绿色差多远：把蓝色上的每一个点，都去找它在绿色上最近的点，记下这个最近距离；所有这些距离里取最大值——这就是从蓝色到绿色这一个方向的 Hausdorff 距离。反过来，从绿色到蓝色也可以同样算一遍。把蓝色记作 $A$、绿色记作 $B$，写成公式：

$$H(A,B)=\max_{a \in A}\ \min_{b \in B}\ \lVert a-b \rVert$$

也就是说，一个形状里"离对方最远的那个点"离对方有多远，Hausdorff 距离就是多少——它抓住的是最坏情况下的形状差异。

#### 面的翻转：颜色为什么会跑错位置

下一个概念是面的翻转。谈翻转，一般先对面的方向做定义：比如所有的三角面，对顶点做一个排序——顺时针或者逆时针——大家都取同一个方向；根据这个统一的方向去算平面的法向，所有面的朝向就都是一致的。

> **定义**：若某个面的法向朝向跟周围的面都不一样了，我们就说这个面翻转了。

那这个概念为什么值得单独强调？拿 UV 一想就明白。UV mesh 本身也是个网格，跟三维网格的面一一对应。如果 UV 网格里有一块发生了翻转——比如另外一个三角形覆盖了它——那么纹理上同一个图像点，就同时映射到了两个三角形上，一个 color 就被分配到两个不同的地方去。渲染出来，这一块的颜色可能莫名其妙就跑到那里去了——这就不对了。你的初衷绝不是这样，是翻转让这种错误发生了。所以面翻转这个概念还是蛮重要的。

> **易错点**：翻转最典型的受害者是 UV——纹理上同一个点被映射到两个三角形上，颜色被分配到两个地方，渲染时就"串色"了。

#### 凸包：橡皮筋收缩出来的轮廓

再一个概念是凸包。凸包跟凸集合的定义相关。给一组点，凸包就是能把这组点都包起来的、最简单的形状——二维里就是一个凸的 polygon。什么叫凸的多边形？它里面每个内角都小于 180°。而且在凸多边形内部，任意两点做线性插值，结果仍在这个凸多边形内部——这正是凸集合的性质。

这个定义可以想象成：拿一根橡皮筋，从一个很大的区域开始收缩，直到不能收缩为止——最外圈那些边界点勾勒出来的轮廓，就是这个集合的凸包。三维的 mesh（网格）同样有凸包的概念。

### 网格的数据结构：存什么，怎么权衡

概念立住了，接下来看数据结构——网格的信息到底是怎么存储的。

一个三维模型都有什么信息？点、线、面，以及 UV 和纹理。这里先不谈 UV 和纹理，只看网格本身：你只要知道点——每个点由三维坐标定义，这就是模型的轮廓形状；再加上三角形——它定义了这个 mesh 的连接关系。知道这两样，其实就能恢复出完整的信息。

那数据结构怎么设计？肯定是简洁性和效率之间的一个平衡。我们整个图形学其实就是在平衡这两件事：一个是表达逼真的效果，另一个是希望用尽量快的速度。

具体可以存的信息有：几何的顶点位置；除了位置，每个顶点上还可以存一些其他信息，比如颜色、UV，甚至动画模型里的蒙皮权重；再就是基本几何单元——边、面——的连接关系：这个点连接的边是哪些、连接的面有哪些，这条边由哪几个点组成，这个面由哪几个点组成，等等。这些连接关系在程序实现时怎么取舍，对算法的设计有非常大的影响。

考虑平衡，主要有三方面：一是存储空间；二是如何能快速地获取数据；三是数据的更新——数据发生更改时，如何快速地改掉，并且保持数据的一致性，全局的一致性、局部的一致性，都有这方面的讲究。

> **课间一问**：一直有同学对"图形 API 与图形学的关系"感到模糊。图形学是一个学科、一个方向；API 更多是实现层面的概念——比如图形 API 就是 OpenGL、Vulkan 这种，它们连接软件和硬件，更多涉及渲染怎么跟硬件打交道。那能不能理解成"把图形学提出的概念，用图形 API 来实现"？不完全是——图形 API 的实现比较狭隘，更多针对渲染的某一部分；图形学整体还包括建模、模型的表达、模型的处理（比如压缩、细化、光滑）、渲染，以及动画、模拟等等。

### 半边结构：把一条边拆成两半

数据结构其实有很多种，这里介绍一个构思很巧妙、当然也有一点复杂性的结构——半边结构。

它的核心想法一句话就能说完：把一条边拆成两个半边来表示，这两个半边方向相对。

具体存什么信息？一张表看清楚：

| 存储对象 | 存的内容 |
| :--- | :--- |
| 顶点 | 位置；一条从它出发的半边的索引 |
| 半边 | 起始点的索引；左手边那个连接面的索引；同一面内上一个、下一个半边的索引 |
| 面 | 它包含的某一个半边的索引 |

两个共享一条边的三角形长这样：

```text
            v0
           /  \
          / F0 \
         v1----v2
          \ F1 /
           \  /
            v3

   F0 里沿公共边的半边：v1 -> v2
   F1 里沿公共边的半边：v2 -> v1
   两个半边方向相反，互为对边
```

读图：一条公共边在两个面里各对应一条半边，方向相反；每个半边存的"左面"，就是沿它的方向看过去左手边的那个三角形——比如从 v1 指向 v2 的半边，左面是 F0。

逐项过一遍：对每个顶点，存它的位置，再存一条出半边的索引——一个顶点连着很多半边，存一条就够了，为什么一条就够用，看完下面的一环遍历就明白了。对每条半边，存起始点的索引——半边有方向，起点是哪个点要记下来；存左边连接面的索引——沿方向看，左手边连的是哪个三角形，它的 id 是什么；还要存同一面内上一个和下一个半边的索引——比如三角面里的某条半边，它的"上一个"是哪条、"下一个"是哪条，存下这两个边的 id。对面来说就更省了：一个面只需要存一条它包含的半边的 id。

就靠这几个 id，我们可以非常快速地做数据的索引。举个最常用的例子：遍历一个顶点的一环邻域。

```text
   从顶点 v 出发
     |  取出 v 存的那条出半边 h
     v
   跳到 h 的对边
     |  对边是能拿到的
     v
   在对边所在的面里取"下一个半边"
     |  这条 next 半边又是从 v 出发的
     v
   回到"跳对边"那一步，依次往复
     绕 v 一圈，v 的所有相邻面就都被提取出来了
```

读图：每做一轮"对边 → 面内下一个半边"，就从一个相邻面跨到下一个相邻面，而且每条 next 半边都从 v 自己出发；依次往复，绕 v 转一圈，一环邻域的面就全部拿到了。

### 为什么要减面：从一屏游戏画面说起

前面介绍了网格模型的表示，还有一些基本的拓扑、几何概念。接下来进入正题：对模型进行压缩或者简化，都有哪些方法，目前的概况是什么样子。这一讲先介绍大体的样子，具体算法是怎么回事，后面再展开。

先看一小段游戏的截屏：里面有建筑，有飘在空中的气球，还有花——全都是三维模型数据。这种数据，数量越大，呈现的效果当然就越逼真；但另一方面，数据量大了，就会对我们的硬件和计算造成负担。手机游戏最典型：手机的存储、计算能力都非常有限，如果里面模型的数据已经很大，甚至大于内存，那就不可能有任何游戏体验了。所以我们希望尽可能压缩数据的大小，同时尽可能保证一定的渲染效果。

### LOD：离视角越远，用的面越少

通常常用的一个手段叫 LOD 渲染，Level of Detail，层次细节渲染。

拿一个白膜举例——白膜就是没有带任何材质的 mesh。最原始的模型大概包含 5000 多个面。近处看的时候，需要用这么高保真的模型来渲染；但当视角拉得很远、越来越远的时候，其实可以用少量数据：1000 多个面、300 多个面、80 多个面，甚至 20 多个面——离得越远，用越少的面数来表达这个模型，同时渲染出来的效果也还可以，远看它还是个球的样子。

这就是 LOD 渲染的核心思想：离视角越近，用更多的数据；离视角越远，用更少的数据。当然，这些不同层级的数据一般要提前计算好。但它们是怎么算出来的？这就非常有讲究了——这正是接下来要讲的：怎么能获得层次细节的网格表达。

这里再点一次网格模型本身的两个事实：mesh 有点、线、面，一般来说，面数的数目对渲染效率的影响非常大；mesh 还有对应的一个二维的 mesh，也就是 UV mesh——两者的面是一一对应的，只是顶点的位置不一样。

### 保纹理的简化方法

模型的简化方法，在实际应用中我一般把它分为两类：一类是保纹理的简化方法，一类是不保纹理的简化方法。

什么叫保纹理？拿原来的模型举例：它有纹理——一张图片，还有 UV 的 mesh；纹理通过 UV mesh 映射到三维表面上去，画出这个三维模型。现在我要简化它，也就是减少面数。保纹理的意思是：简化了的 mesh，我只剪它的网格和 UV，不对纹理做任何操作——渲染的时候，依然调用原来的那张纹理。只要简化出来的模型在渲染时照样用最初始的纹理，这就叫保纹理的简化方法。

它的优点是省数据。一张贴图它也很大呀，我们本来就在想尽办法省数据——能重用原来的贴图，就省掉了这一块图片的大小。

那要注意什么？剪 UV 的时候，UV 的排布要尽可能地跟原来的排布一致。因为你要保持从 UV 获取 texture 再贴到三维表面的一致性——原来贴图画的是一只站在花坛里的企鹅，那你简化完了之后，它也得是这个外表。

> **提示**：保纹理简化里，纹理是原样重用的，动的只是网格和 UV；UV 的排布要尽量贴着原来的排布走，否则贴图到三维表面的对应关系就断了。

简化成什么样？结果是一串数字：从 18000 多个面，简化到 9000 多个面，再到 1000 多个面、900 多个面等等。数据量越小，失真就越明显：这个模型里是花的地方、镂空的地方，在另一个模型里可能就是连在一起的；仔细观察细节，都有变化；面数越少，跟原始模型的差别越明显。我们简化的时候，实际上是尽可能保持外观一致，但数据量的减少不可避免地会带来损失——我们能做的，是把损失降到最小。

#### 主流：基于 QEM 的逐边坍缩

这一类方法非常多。我一般就叫它"跟 QEM 相关的"——基于 QEM（Quadric Error Metric）这种 metric 的简化方法。这基本上可以说是保纹理简化方法的核心，或者说是主流——没有几百篇，也得有几十篇这样的文章和思路。这也是我们作业的主题：实现这个方法。

它的做法一般是通过逐条边地对每条边进行坍缩，来达到逐步减边、逐步简化的效果。这一脉的具体论文很多，想深入了解可以按图索骥去读原文。

#### 其他思路：从聚类到内蕴三角形

除了 QEM 这一脉，还有几类思路，各自都有对应的论文可以查。

一类是聚类式的简化：对输入的模型，根据一些衡量指标把三角面做聚类；聚完之后，每一类的这些三角面可以用一个多边形表示出来；再对这个多边形重新做三角形划分，面数自然就减下来了。

一类是针对四边形网格的简化：模型上的网格不再是三角形，每个单元都是一个四边形——而且不一定非得是正四边形，可以是通用的四边形。

还有两个工作，对"以渲染为目标的保纹理简化"来说并不算实用，但我觉得有必要提一下，因为能给大家提供一些新思路。

一个是用机器学习的方法来给模型减面，同时尽可能保持原模型上某些顶点的位置。不过它实际上可以看成一种重新网格化的方式，应该是不会保持 UV 的——至少我不太容易想象，怎么对它做修改或者稍微改进，让它去保持 UV。

另一个是今年 SIGGRAPH 的工作，做的是内蕴三角形（intrinsic）表达上的简化。这跟我们前面几个工作里的三角形不是一个概念：前面的叫外蕴三角形，每个三角形由三个点、三条边定义，边是欧式空间中的直线；而内蕴三角形的一条边，可以是欧式空间中的一条折线——用一堆折线来表达一条边。这个方向的应用不在渲染，更多是在三维模型表面上做几何计算，比如表面上点的测地距离（geodesic distance）、对 mesh 做有限元计算、解 PDE 方程等等。把它放在这里，是为了拓宽思维。

### 不保纹理的简化方法

另一类就是不保纹理的简化方法。什么意思？还是前面那个原始模型，有纹理、有 UV。不保纹理是指：剪完了面之后，我们不用原来的纹理了。

为什么呢？因为这时模型的连接关系已经完全打乱，我们重新组织了一个新的网格；也就是说，它的 UV 网格跟原来的 UV 网格相比，pattern 已经完全变了。完全变了之后，就需要再生成一张新的贴图，来对应现在这个网格。这类方法简化出来的 UV 排布会非常不一样——比如原来那个圆盘的底座，在新的 UV 里甚至都看不出它是不是底座了。

这类方法的优点，是可以获得更加简单的简化效果，同时跟原来的模型还挺相似——面数可以减到更少：这边是 290 多个面，而前面保纹理的例子里是 900 多个。

不过这条路非常复杂，包含几个大的步骤：

```text
   原始模型（网格 + UV + 贴图）
        |
        v
   [1] 重新网格化  -- 只关注网格本身，把连接关系重新组织
        |
        v
   [2] 展 UV      -- 把新网格摊到二维平面上
        |
        v
   [3] 生成贴图    -- 重新烘焙出新网格配套的纹理
```

读图：三步走，每一步内部都各有一堆方法可选。

重新网格化这一步就有各种不同的方法，可以说是五花八门。比如有一类方法，用一些大的平面片——比如四边形板子——交叉着把模型勾勒出来，每个板子对应贴图里的一大块，把它们排布起来；这类方法一般用来简化植被、建筑一类的模型。还有一类，关注的是输入模型连接出来的 mesh 质量不太好的情形，对它做重新网格化，让它更加规律。还有一类，根据输入模型先拟合出一组平面，再根据平面之间的交叉集合，用某种优化方法从中选出一组子平面，用它们表达出一个非常简化的原模型样子。

再有就是 Visual Hull（视觉外壳）思路的两个工作：我从某个视角观察，把看到的样子勾勒成一个体；换别的视角再勾勒；不同视角交叉出来的形状就是模型。第二个工作解决的是第一个的局限——第一个方法更适合处理建筑或者比较规则的形状。这两个工作是去年和今年 SIGGRAPH 的，我和我的学生们一起做出来的；到第三节课，我们会更详细地阐述、重点介绍。这几类方法各自的论文，感兴趣都可以顺着去查。

把两条路线放在一张表里对照一下：

| 对比项 | 保纹理的简化 | 不保纹理的简化 |
| :--- | :--- | :--- |
| 简化时动什么 | 只剪网格和 UV，纹理不动 | 连接关系完全打乱，重组新网格 |
| 渲染用哪张贴图 | 原来的那张，原样重用 | 重新生成、与新网格配套的贴图 |
| UV 排布 | 尽量与原来的排布一致 | pattern 完全变了 |
| 例子里压到的面数 | 900 多 | 290 多 |
| 流程 | 逐边坍缩等简化算法 | 重网格化 → 展 UV → 纹理烘焙 |

### 展 UV：切、摊、拼

前面说了，不保纹理的路线里，重网格化得到三维网格之后，需要对它展 UV——把它摊到二维平面上去。展 UV 的方法非常多，不用纠结，有现成的公开库可以用，比如 xatlas，直接拿它来展就行。

不管用什么方法，基本上都是三大步。第一步，先对模型做 cut——把它切成一块一块的，cut 出边界；第二步，对每一块，把它转到平面上去；第三步，把这些块组合起来——所谓组合，就是把一块一块拼接得紧凑一点，这样纹理空间会更省。

为什么要抠这点空间？因为我们这一切的一切，目的就是为了什么？就是为了压缩数据、压缩掉多余的数据。展 UV 相关的文献也非常多，这里只是点到为止，欢迎大家讨论。

### 纹理烘焙：把高模的信息"烤"到低模上

展完 UV，下一步就是把纹理生成出来——这个过程叫纹理烘焙。烘焙的方法倒不算多，主要有两大思路：一种是最传统的 ray casting，就是发射射线的方式；另一种比较新颖，是通过可微渲染（differentiable rendering）的方式。

先说 ray casting。拿一张二维的简单示意图来看：黄色的曲线是高模——最原始的模型；黑色的折线是简化了的 mesh，也就是低模。

```text
      高模（平滑曲线，细节起伏）
        ,--~~-.__,--~~-.__
       /                   \

      ^          ^          ^     <- 投射线
      |          |          |
   ---+----------+----------+-----  <- 低模（折线，整体向外放大了一点）

      射线与高模的交点，就是要取颜色的地方
```

烘焙的目的，是把高模上的纹理信息传递到低模上——"烘焙"这个词就是这么来的：把蛋糕放进微波炉或者烤箱里，把它烤上去。要传的是高模上的颜色信息也好、法线信息也好。具体做法：先把低模稍微放大一圈；放大之后，低模上的点和它原来的位置有一一对应关系；从这个放大后的位置向原来的地方投射线，射线可以跟高模发生交点——比如这条视线跟高模交在这里——那我就把高模上这个点的颜色值，赋给低模上这个点对应 UV 上那个像素的颜色。原理就是这么个原理，非常简单，所以叫 ray casting：通过投射线，来计算低模和高模之间的对应关系。

但它有个缺点：没法做到一一对应。低模和高模差距太大的时候，射线往往会投错——有些点就投到错误的地方去了。

另一类方法就是可微渲染。它是现在图形学、渲染里相对比较火热的一个课题。它其实更多的不是"渲染"——它是把整个渲染过程变得可微；变得可微之后，用来优化渲染里的那些量：三维模型、光照、camera，等等。这个东西恰巧可以用来做纹理烘焙。比如给你一个高模、一个低模，它可以把 diffuse map（也就是 RGB）、specular map、normal map 这些都烘出来，烘完渲染出来的样子，就跟原来一致。

到这里，两类简化方法的套路基本就介绍完了。下一节课，我们会重点介绍保纹理的模型简化算法具体是怎么工作的。

## 保纹理的模型减面：简化框架与 QEM 详解
> 对应块：BLK12 | 覆盖分集：P08 | 块标题（分集名）：《8. 几何处理与模型减面之保纹理的模型减面》

一只企鹅站在台阶上。这是对输入的一个三维模型做可视化之后看到的样子。那这个颜色是怎么上去的？渲染的时候——不管你走光栅化还是 ray tracing——都是在屏幕空间里逐三角形地工作：查这个三角形应该怎么上色，就顺着它查到 UV 空间，再查到纹理坐标上对应的纹理像素值，然后染色。所以这样一只企鹅的背后，其实存着三份数据：三维网格数据；UV 数据——它本质是一个二维网格，三角形面数跟三维网格完全一样，只是坐标从三维变成了二维；再加一份纹理贴图。

上节课我们讲了三维模型的各种表达方式，专门针对网格讲了拓扑属性、几何属性和常用术语，还过了几种模型简化——通俗点说就是数据压缩——的路子以及各自的优缺点。这节课我们集中讲其中一种：保纹理的模型减面，也就是减少模型三角形个数的方法里，专门保着纹理的那一类。

什么叫"保纹理"？就是减少面数的时候，我们希望简化后的结果依然使用输入模型的那张纹理贴图。这一下就省掉了什么？省掉了给简化模型重新创建一份贴图的数据量。

> **定义**：保纹理的模型减面——在减少模型面数的同时，输出结果依然使用输入模型的纹理贴图；UV 网格的 pattern 跟输入保持一致，不需要为新网格重新生成贴图。

这是目前游戏行业大家非常喜欢的方式——除非实在没有别的办法，一般都更偏好它，因为它更省数据。在游戏里，数据量的大小对性能、对质量会产生非常多的影响，所以业界在优化数据量这件事上花的时间、精力、人力物力和计算资源是非常大量的——不说最多，也是数一数二的地方。

这类方法其实二三十年前就有了，但一直到今天，都还是业界做数据压缩比较偏好的方法。方法有很多，其中最经典的，是基于 quadratic error metric（二次误差度量，以下简称 QEM）的简化。我们今天整节课就只讲它，详细讲它是怎么运作的；而我们的几何处理、模型减面作业，也就是实现这篇论文。听的过程中有什么不理解、或者我讲得不清楚、甚至讲错了的地方，及时指出来。

### 问题定义：输入、输出与那些无形中的要求

先把问题钉下来。输入有几样：一个网格模型——可以是二维的也可以是三维的，不过一般来说都是三维的；它带着 UV——现实中可能带也可能不带，我们假设它带着；还有对应的纹理贴图。另外还有一个输入：用户希望的目标面数，或者目标面数相对输入面数的比值——这是比较常用的、用户喜欢的参数设置。

输出呢？简化后的三维网格，和它对应的 UV 网格。注意，纹理材质不会输出——因为输出模型用的就是输入那一套纹理材质。

那要求是什么？如果没有任何要求，那随便删面、删点都无所谓了，但这在实践中是不可能的。我们这么想：渲染这个应用，一方面追求极致的渲染效果，希望越真实越好地展现出三维场景的画质；另一方面又希望计算速度尽可能快。提速的路子有很多，比如改进渲染技术；另一个路子是在相同的渲染技术下，压缩要渲染的数据量——渲染 100 万个面的三维场景，跟渲染 100 个面的三维场景，速度肯定是不一样的。所以我们这个问题，就是从数据压缩这个角度去提升效率；但压缩的同时，又希望能尽可能保证画质。这就无形中给问题提出了要求：减面、压数据量的时候，如何让渲染出来的最终效果跟没压缩之前一样？有时候压得太狠，确实保不住了，但我们要尽可能让它一样。

当然，这是从渲染这个角度看的。三维模型不只会拿去做渲染，还会拿去做动画、做物理模拟，那些应用可能会有额外的要求。举几个例子让大家感受一下：

- **保拓扑**：输出模型跟输入模型的拓扑是一致的。拓扑是什么、都有哪些样子，上节课讲过；
- **不自相交**：如果输入模型没有自相交（穿模），也希望输出没有；
- **表面距离尽量小**：模型的表面是嵌在三维空间里的一个面，输入的表面和输出的表面之间可以定义各种距离——欧氏距离也好、别的距离也好——希望这个距离尽量小。严格说这不叫"保距离"，是让距离尽量小：距离小到零，两个模型就没有差别了。

具体问题都可能有具体的要求，这些只是我们能想到的一些例子。

### 一个几乎通用的简化框架

直接说：简化算法的框架，我把它列在这里。这个框架非常通用——不能说百分之百，但绝大部分保纹理的减面方法，基本上都遵循这么一套框架。

整个算法是围绕"简化操作单元"展开的。拿到输入模型之后，先定义清楚简化操作单元是什么；然后第一步，把输入模型里所有的操作单元提取出来，计算它们的误差。为什么每个操作都能算出一个误差？因为操作单元是朝"降低模型复杂度"去的，它一执行就会减少面数；面数一减少，模型必然发生改变——模型一改变，我们就能把这次改变算出一个误差来。误差都算完之后，根据它们构建所有操作单元的优先队列。

接着就进入主循环：只要队列不为空、并且还没有达到停止条件，就取出队列里的第一个操作单元，检查它是否有效。没通过检查，就重复上面的动作，继续 pop 下一个；通过了，就执行这个操作单元，并更新跟它相邻的那些操作单元、更新它们的误差、把它们加回优先队列。这样循环往复，直到达到停止条件为止。

停止条件是用户自己根据具体问题设置的。比如：已经简化到了想要的面数；或者简化后的渲染效果已经差到不能接受、不能再差了，等等。最简单的、也是最常用的停止条件，就是目标面数或者面数比值。

```text
输入：带 UV 的三维网格 + 纹理贴图 + 目标面数（或面数比值）
   |
   v
定义简化操作单元（如：每一条可折叠的边）
   |
   v
提取所有操作单元，并计算每个操作的简化误差
   |
   v
按误差从小到大构建优先队列
   |
   v
进入主循环：
   队列为空 或 已满足停止条件？
     |-- 是 --> 输出简化结果，结束
     |-- 否：
           pop 队首操作单元（当前误差最小者）
           有效性检查不通过？
             |-- 是 --> 丢弃该记录，回到队首判断
             |-- 否 --> 执行该操作（如一次边折叠）
                        更新受影响的相邻操作单元及其误差
                        带时间戳重新加入优先队列
```

先记住这张流程图，后面每一个环节我们都会拆开来填肉。

### 简化操作单元：删点、塌边、合并相近点

哪些操作可以拿来减少面数？估计有些同学已经有所了解，甚至挺熟悉了。给定一个网格模型，基本有这么几种操作。

**删点（vertex removal）**：选中某个点把它删掉，它一阶邻域里的所有三角形都跟着删掉——一阶邻域的概念前面讲过。删完之后那里就成了一个多边形；但我们最终要的是整个模型保持三角网格，所以要对它做一次重新三角化，重新连成三角网格。看图里这个例子：数一数，原来是一、二……七个三角形；删掉一个点、重新连完，变成五个。所以删一个点，就减少了两个三角形。

**塌边（edge collapse）**：这是最常见、最常用的一种简化操作。网格里每条边由两个点组成，把这两个点合并成一个点，这条边就没了；与此同时，这条边原来相邻的三角形也被删掉——图里画的是两个，实际中可能是一个或者多个，取决于模型的拓扑长什么样。不过这个算法对拓扑其实不敏感，它是个很通用的算法。

**合并相近点**：还有一种情况——输入模型里这两个点之间并没有连接的边，但它们在空间里非常近，那我们也可以根据距离把它们合起来。有同学可能会问：这种情况不会出问题吗？这取决于具体问题、具体需求。有些情况下，先把相近的点合起来，会对进一步的操作有帮助——比如帮助后续的塌边做得更顺，也就是进一步简化三角形。所以原论文里也提到，这种操作往往需要跟其他真正能减少面数的操作联合使用；只用它自己，其实没什么用处，因为它不会减少三角形的数目。它最常见的用武之地是这样：输入模型里有些点是重复的——坐标一模一样、只是 id 不一样——这时候我们就希望把它们 merge 起来，方便以后的操作。

| 操作单元 | 怎么做 | 对面数的影响 | 使用要点 |
| :--- | :--- | :--- | :--- |
| 删点 vertex removal | 删掉一个顶点及其一阶邻域内所有三角形，再把留下的洞重新三角化 | 删一个点约减两个三角形（例：7 → 5） | 需要重新三角化 |
| 塌边 edge collapse | 把一条边的两个端点合并成一个点，边随之消失 | 删掉该边相邻的三角形，一般两个 | 最常见最常用；对拓扑不敏感 |
| 合并相近点 | 把没有边相连但距离很近的两个点合并 | 不减少三角形 | 要与塌边等操作联合使用；常用于合并重复点 |

当然还有别的操作单元，比如一次性移除整个三角形、一次移除一批三角形等等，这里不具体展开。接下来我们集中讲塌边，因为它最常用。

> **提示**：不管选哪种操作单元，实现时都要遍历顶点、访问邻接信息。有同学问：算新顶点需不需要遍历顶点坐标、要不要半边结构？计算新顶点位置肯定要用到周围的信息，这绕不开；但遍历本身不一定非用半边结构——无非是把所有信息都存储起来，一样容易遍历，它本质上就是一个 graph。

### 核心就两点：怎么排序，新点放哪

框架搭好了，它的核心中的核心其实就两点。

第一点：你怎么对操作单元排序？输入模型里有那么多条边，先剪哪条边、再剪哪条边，这个顺序会大大影响最终简化出来的模型的质量。

第二点：collapse 合并两个点的时候，会形成一个新的顶点。这个新顶点的位置，对简化结果有非常大的影响。为什么？因为模型的外形，基本上就是被点的位置大致勾勒出来的，再加上点与点的连接关系，渲染出来就是一个完整的三维模型——所以点的位置是非常关键的。

这两点其实都跟简化操作以及误差的计算息息相关：你怎么去衡量一次边折叠的误差？这就是接下来要展开的。

### 误差怎么定义：几何误差与视觉误差

误差计算，取决于你怎么定义这个误差。定义非常多——过去二十多年里，针对这个课题的研究有非常多，很多人提出各种各样的误差，其中大部分是几何误差，也就是衡量折叠之前和折叠之后这两个 mesh 的区别；另外还有一类是视觉误差，看的是简化完了之后在视觉上造成的影响。

**先说几何误差里的 Hausdorff 距离**，上节课讲过：蓝色物体到绿色物体，每个点都去找它到对方表面的最近点距离，取其中的最大值；再从绿色物体到蓝色物体同样做一遍；两个方向各自的最大值里再取最大的——这就是衡量两个物体的 Hausdorff 距离的连续定义。

问题是，这个距离真正算起来很慢，有时候甚至无法精确算出来。同一个问题在学术界基本上都有好几种解法，Hausdorff 也有连续的做法和相对连续的做法，但比较常用的还是基于采样的方法来近似。这里我贴了一个大家比较常用的库，算法就是那篇论文，细节可以去看。

举一维的例子感受一下。一条折线，我们假设要把红色的边折叠掉，折叠之后形成绿色的形状；并且假设我们已经决定好了 collapse 之后新点的位置。现在要衡量折叠之前和折叠之后这两个形状的距离，怎么做？用采样的方式：对原来的曲线采样一些点，对新生成的曲线也采样一些点，然后算这两组点对之间的离散 Hausdorff 距离；或者算 chamfer distance——视觉领域里经常用 chamfer distance 来衡量这种距离。当然，近似的具体做法有很多种，这里只简单提一种。

```text
折叠前：  A ●──────●──────● B        中间那条红色边将被折叠
折叠后：  A ●─────────────● B        两个端点合并成新点 v̄

在折叠前后的两条折线上各采样一批点，
用两组采样点之间的离散 Hausdorff / chamfer 距离，
来近似衡量两次形状的差异。
```

（有同学问：这看着像贝塞尔曲线的计算方式？不是。这跟贝塞尔曲线差别很远，完全是不同的定义。）

**再说视觉误差**。除了几何上的各种量——距离、距离的平方、法向、曲率等等——还有几个工作把视觉因素加进来考虑。举个茶壶的例子：你从不同的视角去看它，表面上的有些区域是看不到的，比如茶壶柄那种比较凹陷的地方、被遮挡比较多的地方。把视角离散化之后统计一下就会发现：这些区域被看到的视角数目相对少；而外凸的区域，几乎哪个视角都看得见。有工作就利用这种信息，对整个模型做了一个"视觉影响"的估计，再把这个估计作为某种度量，结合到前面讲的 QEM 上面去，指导我们的简化。这样一来，简化这个模型的时候，实际上就融入了最终简化模型对视觉造成的区别，相当于给所有的边又做了一层区分度。具体细节可以看那篇论文。

误差的定义就粗浅地过这几种。接下来重点讲 QEM——它是怎么算的，在三维中是怎么算的。

### QEM：从平面方程到二次误差度量

从最简单的开始。三维平面公式：

$$ax + by + cz + d = 0$$

满足这个公式的所有点，都在这组系数所定义的平面上；当然我们也要求 $a^2 + b^2 + c^2 = 1$，也就是把法向归一化。一个点在这个平面上，等价于它的齐次坐标跟平面系数做点积等于零：

$$v^\top p = 0, \qquad v = (x, y, z, 1)^\top,\; p = (a, b, c, d)^\top$$

点积等于零，就是这点到平面的距离为零。这个大家都学过，稍微回顾一下。

QEM 到底有多经典？它是二十五年、二十六年前的一个算法了，直到二十多年后的今天，依然是工业界最常用、最经典的方法。它如此经典，以至于我们的作业、这节课的重点就是只讲它——也可以说，它是最实用的方法。

QEM 是针对每个点来算的。假设有一组平面——先不管这组平面是哪来的——当前这个点 $v$ 相对这组平面的 QEM 误差，就是它到每个平面的距离的平方，加合起来，记作 $\Delta(v)$：

$$\Delta(v) = \sum_i \left(v^\top p_i\right)^2$$

这个平方和越小，说明误差越小。

> **定义**：QEM（二次误差度量）——一个顶点相对一组平面的误差，等于它到每个平面距离的平方和，$\Delta(v)=\sum_i (v^\top p_i)^2$；平方和越小，误差越小。

**怎么跟塌边接上？** 每个点在网格里相邻一组三角形；三点唯一确定一个平面，所以每个点都有相邻的一组平面。这个点到它自己相邻的这组平面的距离肯定是零——它的 QEM 值就是零，对吧？但是两个点合并成一个新的点之后，这个新点就不一定还落在原来那一组平面上了。于是我们就定义：新点到原来这组平面的 QEM 值，就是这次塌边产生的 error。就这么简单。

刚才说的是塌边；其实你去 remove 一个三角形，或者重新三角化式的 remove 一个点，稍微改一改，也可以灵活地用上 QEM。而且 QEM 不仅能用在三角网格上，也能用在其他网格上——这个后面会讲。

**把它矩阵化。** 把 $\Delta(v)$ 展开，每个平方项是 $v^\top p_i$ 再乘 $v^\top p_i$ 的转置，也就是 $v^\top p_i p_i^\top v$。因为 $v$ 只有一个，可以把求和挪进去：

$$\Delta(v) = \sum_i v^\top \left(p_i p_i^\top\right) v = v^\top \left(\sum_i p_i p_i^\top\right) v = v^\top \bar{Q}\, v$$

里面加起来的是一个矩阵——前提是把 $v$ 整成齐次坐标，也就是四维的 $(x, y, z, 1)^\top$。我们把这个矩阵记作大 $\bar{Q}$。把它按平面系数 $a, b, c, d$ 摊开，长这样：

$$
\bar{Q} = \sum_i
\begin{bmatrix}
a^2 & ab & ac & ad \\
ab & b^2 & bc & bd \\
ac & bc & c^2 & cd \\
ad & bd & cd & d^2
\end{bmatrix}_i
$$

为了方便，把这些元素重新命名成 $q_{11}, q_{12}, \dots$，然后把式子重写一遍：

$$\Delta(v) = v^\top \bar{Q}\, v, \qquad v = (x, y, z, 1)^\top$$

因为 $v$ 就是 $x, y, z$ 加一个 1，直接把它展开，得到的就是一个标量——这一坨加起来，就是我们的 QEM。

### 把 QEM 接到边折叠上：求误差，顺手求最优点

现在问题来了：做边折叠的时候，这一套怎么用？

首先，折叠之前，输入模型的每个点——只要有这个点、有它相邻的一组平面——就可以构造出一个 Q，对吧？折叠之后呢？直接把两个 Q 加起来：$\bar{Q} = \bar{Q}_1 + \bar{Q}_2$，作为新顶点 $\bar{v}$ 的 QEM 矩阵。大家后面可以自己验证一下：这并不完全 exactly 相等——因为这两个顶点在统计各自的平面时，中间相邻的那两个三角形（共享的那两个平面）被重复计算了一次。

> **易错点**：$\bar{Q}_1 + \bar{Q}_2$ 并不严格等于新顶点真实的 Q——两个顶点共有的那两个三角形平面被重复计了一次。工程上先忽略这点误差，换取"不用重算平方和"的速度；对精度有点影响，但当前可以先不管。

于是这次塌边的误差就是：

$$\Delta(\bar{v}) = \bar{v}^\top \bar{Q}\, \bar{v}$$

别忘了更重要的一件事：定义了这个简化操作之后，你可以把整个东西整成一个优化式子。什么意思？我还要计算新顶点的位置呢，而顶点位置对误差的影响非常大。$\Delta$ 是关于 $\bar{v}$ 的二次形式，所以可以比较容易地求得使误差最小的那个 $\bar{v}$——怎么求？对 $\bar{v}$ 的三个分量 $x, y, z$ 分别求偏导，令偏导等于零就是极值。二次函数嘛，极值点只有一个。

比如对 $x$ 求偏导（$\bar{Q}$ 对称，写出来就是）：

$$\frac{\partial \Delta}{\partial x} = 2\,(q_{11}x + q_{12}y + q_{13}z + q_{14}) = 0$$

这就是一个关于 $x, y, z$ 的线性方程。再对 $y$ 求偏导、对 $z$ 求偏导，就构建出三个线性方程；补上齐次坐标 $w = 1$ 这个约束，凑成一个 $4 \times 4$ 的线性方程组。矩阵里每个系数都是已知的，求逆，就出来了。

到这里其实就讲完了：如何用 QEM 求出让误差最小的顶点位置。求出位置之后，你完全可以带回 $\Delta(\bar{v}) = \bar{v}^\top \bar{Q}\, \bar{v}$，把这次操作的误差算出来。于是，每一个简化操作——每一条边的折叠——都能算出一对新东西：最优顶点位置和它的误差。对输入模型提取所有的边，算出每条边折叠后的误差，按误差排序建优先队列，进入主循环。这就是 QEM 的完整用法。

### 解不唯一的三种情况

这套东西虽然很简单、听上去非常漂亮，但有的时候会有问题：这个解可能不唯一，取决于矩阵的形式。基本上可以归为三种情况。

第一种：有唯一的最小值解——就一个点、一个值。这种情况下矩阵是可逆的，我们能求出一个最小值点，皆大欢喜。

第二种：解是一条线。举个例子：一个模型，被折叠的这条边两个顶点所相邻的那些平面，可以归成两类，每一类各自都是共面的——都在一个面上。那你最终实际上就是在对两个互成夹角的平面求"距离平方和最小"的点，这样的点构成一条线。

第三种：那组平面全部共面，甚至全部平行，那解空间就是一个面。

后两种情况下我们就需要做一些选择：共线的时候，可以从这条边的两个端点（包括中点）里选一个误差最小的当新顶点；共面的时候，也是选一个点交差。总之别让程序在退化情形上卡住。

### 有效性检查：别让一次错误的塌边毁掉整个模型

回到主循环。不满足停止条件，就 pop 队首操作单元，然后检查它是否有效。什么叫有效性？就是"我做了这次简化之后，结果还能不能接受"。最简单的情况下，你可以不做任何有效性检查；最复杂的时候，你可以有一串检查——一、二、三、四、五，满足一，再 check 二；满足三、四、五，全都过了，才算通过。下面举几个我认为在实践中比较有价值、比较常用的检查。

#### 距离检查：体素近似

简化之前和简化之后，局部表面的形变不能太大——局部那个表面跟简化之前的表面之间的距离（Hausdorff），我不希望它超过很大很大，超得明显就说明造成了很大的形变，我们希望限制这种距离。前面说了，直接算 Hausdorff 又耗时又费力，有时甚至无法精确算出来，所以大家设计了各种各样的近似方法。有一种我认为比较实用：对输入模型做体素化（voxelize），并且用不同大小的体素格子，做成层次化（hierarchical）的结构；随着简化的深入，让体素越来越大，也就是越来越宽容更大的距离偏差。具体细节可以看论文。

#### 拓扑检查：link condition

希望简化之前和之后，拓扑是一样的。检验工具就是前面提到的欧拉公式——上节课讲过的那个拓扑公式。最粗暴的做法：直接把连通数、亏格数、洞数都算出来，对比简化前后这些量是不是一样。但那太慢了，我们一切都希望在不损失精度的前提下尽快算。

这里有一篇不错的论文，方便了我们后来者，它用的是 link condition：每个顶点周围有一圈相邻的元素——相邻的顶点、边、三角形——这叫它的 link。塌边之前先检查：$v_1$ 的 link 和 $v_2$ 的 link 的交集，是否等于边 $v_1 v_2$ 自己的 link。相等，这次折叠就不改变拓扑；不相等，就拒绝。典型的失效场景是：折叠这条边之后会产生非流形的三角形——折叠之前拓扑条件是满足的，折叠之后拓扑变了，就不满足了。通过这个条件，可以比较快速地检验拓扑改没改变。这个点如果你没听说过、想了解细节，可以查 link condition 的论文，或者直接联系我，我给你详细说。

#### 法向翻转检查

折叠之后，不希望面发生翻转。什么是翻转？比如这一组三角形，原来法向都朝向一致——相互的点积都是正的；折叠之后其中某个三角形朝向反了。这样在渲染的时候，尤其是单面渲染，会产生比较差的渲染效果，所以我们经常要避免这种情况。常用的简单 trick：测试新表面那些三角形的法向，跟旧面法向做点积、看夹角，检查有没有发生翻转，用这种策略做一个快速的筛查。当然它并不能完全保证，但这是一个简单、快速的检查方法。

#### 自相交检查：BVH 加速

如果输入模型本身没有穿模（自相交、交叉），我们希望最终输出也没有。为什么？因为穿模同样会让渲染质量很差——尤其是单面渲染的时候，看上去黑乎乎的，不好。当然，如果输入模型已经有穿模了，那确实不好弄，这个不管。

自相交其实分两种情况：一种距离比较远——两块在流形空间上相距很远的区域相交；另一种是近距离的——在临近的 neighborhood 里自己跟自己相交，这种情况一般检查起来会稍微麻烦一点。做法上，可以把每个三角形组织成一个 BVH 这种加速结构，建 AABB 包围盒（bbox）来加速计算，让需要两两 check 的三角形对（pair）的数目大大减少；最粗暴的就是每个三角形 pair 都检查一下有没有真的相交、有没有 overlap。现在也有一些公开的库做这个事情——不过真要把它做好，其实不是那么容易的。

#### 数值鲁棒性检查：包围球兜底

我们做检验的时候，坐标一般都是浮点数，浮点运算有精度问题。前面解顶点位置的时候，由于数值误差，那个点有可能直接飞出去。一个比较粗暴的防止方法：预先定义一个包围球（bounding sphere），限制优化出来的点必须在这个球里面；一旦超出，就说明这个点因为数值误差飞出去了——那肯定是不对的、ugly 的——直接拒绝这个操作。

这就是我列举的几个比较有用、比较常用的有效性检查，是一种相对 cheap 但实用的检验方式。

### 执行之后：更新误差与时间戳

如果这些检查都通过了，接下来就是执行这个简化操作。执行完了之后要注意：它周围的那些三角形都发生了变化；而所有这些三角形面对应的平面也都变了——一个三角形定义一个平面，三个顶点里有一个的位置变了，这个平面就变了。

那怎么办？最原始的论文，就是直接用 $\bar{Q}_1 + \bar{Q}_2$ 表示新顶点的误差，其他不更新。你也可以用新顶点的误差去 update 周围受影响的边；甚至可以完全不 update——不 update 速度更快，但是随着你简化的边数越来越多，它会偏离原来的 surface 越来越远，那个 error 离我们真正想要的 error 就越来越远。所以很多时候我们希望更新一下：重新计算与它相连的、受影响的那些边的简化误差。重新更新一遍，误差更准，最终简化出来的效果更好一点。更新完了，把这些边带着新误差加回优先队列。

这里面还有个小坑：一条边可能被加入了好几次。处理办法是放一个时间戳：每条边维护最新的时间戳，从队列里拿出来的时候对一下时间——如果它不是最新的，说明这条边已经被 collapse 过了、已经不存在了，直接丢掉就行。

> **易错点**：优先队列里的旧记录不会自动消失。一条边被更新重入队之后，旧的那份记录还躺在队列里；不对时间戳，就会把一条已经不存在的边再 collapse 一遍。

这就是整个算法的框架。可以说，几乎所有我觉得比较实用的保纹理简化方法，都遵循这个框架。这个框架虽然简单，但有效、很实用。

### 保住边界：高权重的虚拟平面

还有另外一种情况：模型有边界。最简单的例子是一张正方形的三角网格片：我希望简化完了之后，它还是一个正方形的样子。这明明可以做到——比如我 collapse 这条边——但如果不做任何处理，最终优化出来的新点位置可能跑到别的地方去，形状就发生变化了。很多情况下，我们是希望保持模型边界的。

论文里原始的示意图更直观：一个圆柱，两边开口——这就是它的边界。不做约束地做边折叠，简化完它就成了那种瘪掉的样子；给边加上约束之后，简化完依然很完美。

约束怎么加？其实挺简单的，分三步：

1. 先把模型的边界检测出来，确定哪些边界需要尽量保持；
2. 对每一条边界边加一个虚拟平面。一条边界边必然相邻一个三角形（也就是必然相邻一个平面），让这个虚拟平面跟它真实相邻的那个平面垂直；
3. 每个平面都能算一个 Q，给虚拟平面对应的 Q 负一个很大的权重：如果其他平面的权重都是 1，这个虚拟平面就给 1000。

这样一来，collapse 之后，误差会把这两个点强制拉回这条边界上——这个平面就保住了，边就不会变形。

### 不止三角网格：四边形网格与体网格

到这里，关于三角网格的简化基本讲完了——但还没说其他属性怎么办，那个放在最后讲。先回答一个自然的问题：这种简化方法，能不能用在别的网格上？

**四边形网格。** 可以。不过这里的重点不在于 QEM 本身，而在于四边形网格是有一定规律的：你希望简化完了之后，它仍然是一个四边形网格。看图里这个例子：一个很 dense 的四边形网格，简化一轮，它仍然是四边形网格；再继续简化，仍然是四边形网格——它就一直保持四边形。为什么要费这个劲？因为四边形网格有个好处：比较规则。

有一篇比较经典的论文是这么做的：提取出一个 strip，然后在 strip 上做整体的塌边。我个人觉得，它用对偶网格（dual mesh）来提 strip 其实有点多余——直接开局，从一条边出发，找它的平行边（四边形的对边），再找平行边的平行边，一路找下去，就能找出这个 loop 来。找出来之后，这条 loop 上成对的两个顶点去做 edge collapse——所以它相当于同时做一组 edge collapse。前面三角网格简化的时候，一次只做一条边的折叠；这里一次做一堆边的折叠，每一条被折叠的边看成一个新点（有的时候可能会看成多个点，但没关系），新生成点的位置还是照样用 QEM 的公式：它有前面的那些平面，照样可以算出一个最优点的位置。这是对四边形网格的一个应用，还是挺不错的。

**体网格。** 还可以对体网格做：就是我不仅表面上有网格单元，模型内部也充满了单元。这里列的是六面体网格，其实里面也可以是四面体网格等等多种不同的离散化方式。同样可以提取这种 strip，把一条线的两个端点拉成一个点，照样可以用 QEM 来优化。当然那篇论文没有用 QEM 来优化，我的意思是：QEM 的应用可以很广，它是可以用来做这个事情的。简化效果大家在论文里能看到，这里就简单提一下这方面的应用。

### 不止位置：把颜色、法向、UV 都塞进 QEM

最后说其他属性。输入模型除了位置 $x, y, z$，每个顶点可能还有别的属性：比如颜色 RGB——现在用 AIGC 生成的那些模型，大部分都是把颜色定义在顶点上的，对那种 mesh 做简化怎么办？还有法向，而且一个顶点可能定义好几个法向；还有 UV——我要把纹理映射到 UV 上，怎么办？再或者，我在模型表面定义了一个高度场、一个热度场，whatever 各种属性。做边折叠的时候，这些属性该怎么办？

这篇论文对 QEM 做了一个很简单的扩充。回头看 QEM：它是一个平面公式嘛。每个顶点有很多属性？没关系——把顶点的所有属性全堆着来，弄成一个很长很长的 vector。三点确定一个平面；属性堆在一起，同样可以定义一个（高维空间里的）平面。所以论文的做法就是：你直接往后怼，把那些不同的属性堆在一起，最终它仍然能推导出 QEM 这种表达方式。于是你的整个简化流程、整个操作流程一模一样，计算出来的最优点——连同它的各个属性分量——也一模一样。非常优美。

不过有一点值得说：算出来的分量可能超范围。颜色是有范围的——RGB 在 0 到 255、或者归一化到 0 到 1 之间；但我们的位置是从负无穷到正无穷解出来的，那算出来的颜色也有可能从负无穷到正无穷，这怎么整？可以对它做一个 scale 加 translate：论文里有详细解释，其实很简单，一个线性变换，把它变换回有效值的范围里。法向怎么办？法向要求 $l^2 + m^2 + n^2 = 1$，长度要为一，那就对它做 normalize。UV 也有范围——纹理空间比如是 0 到 1，算出来的 UV 值飞出去了，怎么拉回来？跟颜色一样，做一个 scale 加 translate，拉回来就行。

| 属性 | 天然约束 | 算飞了怎么办 |
| :--- | :--- | :--- |
| 颜色 RGB | 0～255，或归一化到 0～1 | 用 scale + translate 的线性变换拉回有效范围 |
| 法向 | $l^2 + m^2 + n^2 = 1$，长度为 1 | normalize |
| UV | 纹理空间有范围，如 0～1 | 同样用 scale + translate 拉回来 |

结果就是像这样的例子：顶点色的模型，在做简化的时候，能同时很好地保持住颜色。这就是保其他属性——把所有的属性整个纳入到同一个框架中。

### 这些细节，为什么值得抠

这节课我们详细介绍了保纹理的模型减面里最经典、最实用的方法——QEM——具体是怎么 work 的，包括很多论文、很多实际应用讲解、网上讲解都没有介绍到的部分：有效性检查长什么样、误差可以怎么定义、解空间不唯一怎么办、想保持模型边界这种特殊情况怎么处理。这些细节看上去都简单，但在实际使用中，处理不好就会出各种各样很奇葩的结果，所以值得抠。

下节课我们讲不保纹理的模型减面是怎么工作的。那个会复杂一些——它比较"野"，各种不同的方法很多，我也只介绍最实用的。我们下节课再见。

## 不保纹理的模型减面：重新网格化、展 UV 与纹理烘焙
> 对应块：BLK13 | 覆盖分集：P09 | 块标题（分集名）：《9. 几何处理与模型减面之不保纹理的减面算法》

### 先说清楚：什么叫不保纹理的减面

上节课我们讲完了保纹理的减面算法，也就是经典的 QEM 那一套，各方各面的细节都过了一遍。今天这节课是几何处理与模型减面这个模块的第三讲，我们来讨论另外一类同样非常重要的算法——不保纹理的减面算法。

减面这件事本身大家已经很清楚了：把网格的面数降下来。那"不保纹理"是什么意思？比如输入一个模型，它有自己可视化出来的样子、有自己的 UV、有自己的纹理。所谓不保纹理，是说我们在生成面数减少了的新结果时，附着在新模型上的贴图并不是原来输入模型的那张贴图，而是要针对输出结果重新生成一张对应的贴图。

> **定义**：不保纹理的减面算法，就是简化后的模型不复用原模型的 UV 和贴图，而要重新展 UV、重新生成贴图的减面方法。

概念上其实挺容易理解，但实际去做的时候，怎么把这个算法设计出来，有很多因素要考虑。不保持原来的纹理，一方面给算法设计增加了很大的自由度——我们不需要去保持原来模型的 UV；但另一方面，正因为它给了我们极大的自由发挥空间，我们也就需要做很多额外的处理：重新生成 UV、重新展 UV、重新生成贴图，等等。

那这类算法的代价和好处各是什么？缺点很明显：它会生成额外的数据量。我们做减面的主要目的就是减少数据量，结果反而多出来一块新的数据，这对算法的应用并不是好事情。那为什么还会有这样一类算法存在？主要是它可以把面数减到极限：比如原模一万八千多个面，可以减到两百多个——差不多 1% 到 1.5% 的量级，非常少了。

### 整体管线：三步走

不保纹理的减面算法，具体的算法细节、步骤非常多，也非常复杂。但总的来说，我认为比较经典的一个 pipeline 是这样：输入模型，要得到输出结果，需要经过三个步骤。

```text
输入：高模（原模）
     │
     ▼
① 重新网格化   只看点线面，重新生成一张干净的网格
     │
     ▼
② 展 UV        切割 → 参数化 → 装箱，得到 UV 网格
     │
     ▼
③ 纹理烘焙     把原模的外观迁移给低模，生成新贴图
     │
     ▼
输出：低模网格 + UV + 新纹理
```

读图：三步串成一条流水线，每一步的输出就是下一步的输入；原模型的 UV 和贴图过了第一步就不再沿用，最终贴图是第三步新烘焙出来的。

第一步，先对模型做重新网格化。这一步我们只关心网格本身——点、线、面，把它的网格重新生成一遍。第二步，对这个新网格计算 UV、展开 UV。第三大步，有了网格、有了 UV，就根据原模和前两步生成的结果，生成对应的纹理——这个过程就叫烘焙。为啥叫烘焙呢？你把一个高模的信息，通过某种方式转移（transfer）给低模，把纹理转移过去，就叫"烘焙上去"。

每一步其实都对应着很多不同的算法，尤其第一大步和第二大步，算法真的太多太多了。所以这节课我不会像上节课那样聚焦某一个算法的细节，而是从更高层次的 pipeline 角度，阐述几个经典的方法，给大家一个印象：至少理解这个流程是怎么回事、为什么会有这种流程；以后自己去实现、去探索细节的时候，知道从哪里着手。这是我这一讲希望能达到的目的。

### 重新网格化：内容生成总是最难的

先从第一大步开始。这一步也是最复杂、也是最难的一步——在 graphics 里、在几何处理这一块，内容的生成基本上总是最难的。重新网格化相当于你已经有了内容（输入了一个高模），但我们想对它做处理：目的是把面数降下来，同时还要跟原模型相似。这实际上就类似于生成另外一个三维模型，而且我们的要求还挺多：面数要少，等等。这一类方法其实有很多，这里只挑几个非常有限的代表来讲。

#### 输出要满足三件事

什么叫重新网格化？比如输入是一个原模，在这一步里我们不关心它的 UV、不关心它的纹理，只关心这个 mesh——比如输入的模型有五千多个三角形。我们想要的输出，是让它的 mesh 越简单越好。别忘了我们的主要目标：压缩数据，提高渲染效率。

当然不能只盯着面数少，我们还有两个要求。

一是渲染出来的样子要跟原模尽量相似，也就是保住视觉外观（visual appearance）——两个模型渲染出来的图片要尽量相似。

二是输出的网格模型，它的拓扑结构和几何特征要尽量干净、尽量简洁。为什么？因为整个不保纹理的减面是一个管线，这只是第一大步，后面还要展 UV、做纹理烘焙。如果重新网格化的结果有比较好的拓扑和几何性质，就非常有利于后面算法的展开——光展 UV 这一个环节，就有几十种甚至上百种算法，各有优缺点；但总的来说，你给它的网格质量越好、拓扑越干净，展出来在实际应用中就越鲁棒，效果一般也会好一点。

> **结论**：重新网格化要同时做到三件事——面数尽量少、渲染外观尽量相似、拓扑与几何尽量干净。第三条不是洁癖，是在为整条管线铺路。

#### 输入有多脏：拿游戏里的建筑说事

知道了输入和输出，那这一步的挑战在哪？尤其在游戏里，我们拿建筑模型来举例子。实际应用中的这类模型，看上去非常简单——就是简简单单的外轮廓，感觉不是那么复杂的三维模型，非常 simple、非常 nice。但实际上，它的拓扑和几何是非常复杂的。

拿这个模型举例：它有将近六千个三角形。六千其实已经是很少的面数了，但为了游戏玩家有更好的体验，我们还是希望把面数降到更低，渲染的时候更快、更流畅，也能把省下来的计算资源分给其他计算。就是这仅仅六千个左右三角形的模型，它包含 151 个 components——前面提过，components 就是互相分离、互不连接的连接体——这么简单一个模型就有一百多个；另外还有五千多对互相交叉在一起的三角形。一般来说，这种模型都比较 dirty，而且不是流形的（not manifold）。

十几年前、几十年前的很多算法，基本都会对模型做一堆美好的假设：假设它是二流形的、没有自相交、是封闭的，等等。但实际应用中完全不是这样子。美术在制作这种三维模型的时候根本不 care 拓扑，他们最重要的关心是看上去是不是好看、是不是满足他们的制作标准。总而言之，建模的人——美术——的目标，跟我们设计一套自动化算法的要求和目标是很不匹配的；正因为这种不匹配，造成了挑战。还有些模型看上去是一个完整的建筑，实际上里面有大大小小的洞、缝隙等等，都会给自动化算法带来非常多的麻烦。

建筑的例子还有很多：各式各样的建筑，有的不仅有一层外皮，还有多层、上下结构、多孔结构、间隙结构；日式的、中式的、罗马的、中世纪的、现代式的——每种类型的建筑都有各自的复杂度。另外补一句前面没细说的：有的输入模型看起来是三角形的拓扑，但几何上完全面积为零、边长为零；有的模型有很多重复的点、重复的面——你能想象到的各种奇葩的复杂性，实际中都存在。

#### 美术的成本，就是自动化的机会

实际应用中——甚至现在也是这样——美术在创建游戏资产（3D 的、2D 的，游戏里统称美术资产）的时候，经常要花很多时间：不仅是生成原模，还要花很多时间生成低模网格（low poly model）——这正是我们重新网格化这一步的主要目标。他们为什么要花上几周的时间？因为整个游戏开发中，对 3D 资产的处理占的比重非常大。我没有具体的数字，但投入的人力还有物理时间成本非常高、非常之高。这也是自动化算法有强烈现实意义需求的原因。

#### 现有方案实测：基本都不顶用

现在都有什么样的解决方案？工业界：Blender，免费 license，个人开发者用起来没什么门槛；还有 Unreal Engine 5。这两个更多是一个平台，里面集成了各种各样的插件或者他们自己开发的工具。更专业的是 Simplygon 和 InstaLOD 这种：Simplygon 是一家创业公司（瑞典）的产品，2006 年开始做的，2017 年被微软收购，现在是微软的子公司；InstaLOD 是德国的一家创业公司。这两家是专门处理美术资产的——对 3D 资产做各种处理，比如保纹理的减面、不保纹理的减面、重新网格化等等，就是专门干这个事情的。

学术界也有一堆论文，非常多，我这里不一一列举，当然有的想法也很不错。也有一些开源软件，比如 MeshLab，里面有减面；还有 CGAL 这种计算几何处理库，都有相关的重新网格化方法。研究为什么这么多？因为这确实是一个很难的问题。

但实际效果怎么样？我们确实做过测试。输入是两个将近一万面的模型（记号 #T 表示三角形面片数目），拿 KSR、PolyFit、Blender、SPSR 这些不同算法去跑，结果是这样的：有的面数根本没降下来，还把模型破坏得乱七八糟，完全没法用——游戏中对结果的要求还是很高的；有的方法倒是非常简单，但跟原版差距挺大；还有的完全不可用；还有鲁棒性问题，比如会 crash。这里说一下鲁棒是指什么意思：你的程序运行中不崩溃，这就算好的，这就叫鲁棒。

> **结论**：直到现在，这个环节大部分还是通过手工或者交互的方式来做的。

我们跟同事一起做的、去年发在 SIGGRAPH 的一个工作，就可以达到这种效果：输入是那个脏兮兮的建筑模型，输出非常简单；而且因为这种超简模型主要用在相机离得比较远的渲染里，看起来跟高模非常相似。今天我简单介绍这个方法的思路，细节可以通过搜索去看论文；我们也公开了可执行的程序，大家可以试用。

#### 设计原则：先造一个干净的代理网格

设计一个算法，需要考虑我们为什么要设计它、希望用它解决什么问题。我们的方法就是从这个问题的根本要求出发来设计的。

第一，我们希望结果能跟输入的模型视觉上尽量相似——那设计方法的时候就重点考虑这一点。第二，针对前面介绍的各种输入挑战——拓扑复杂、几何脏，还有刚才补的那些奇葩情况（零面积的三角形、零边长的边、大量重复的点面）——我们就想：与其直接对复杂的模型做减面操作（比如上节课讲的边折叠），不如先对这个输入模型计算一个代理网格（proxy mesh）。

> **定义**：proxy mesh（代理网格）是我们先造出来的中间模型，它要满足两条：一，视觉上跟原模相似，从这个视角看、从那个视角看，都跟原版很像；二，clean——拓扑比较干净、三角形尽量少，最好是水密的（watertight）、是流形的，几何上没有自相交这类复杂情况。

先生成这个代理网格，然后再用上节课提到的 QEM 减面方法，通过边折叠来得到低模网格。这就是我们方法的设计原则。

整个方法的 pipeline 是这样：输入高模，第一步先得到一个叫 visual mesh 的东西——它实际上是用 visual hull 的方式对输入模型"切"出来的一个模型，为什么这么叫马上会看到。但 visual mesh 有个问题：它是根据视点、观察的时候把这个模型"看"出来的，而渲染是跟随直线（视线）原则的，凹的地方它就捕捉不到。所以第二步要把凹陷的地方通过布尔运算的方式雕刻出来，叫 carve mesh 生成。到这一步为止，原模的样子就已经出来了，拓扑是干净的，但几何还不行——面数还挺多，还有很多重复的、可以剪掉的。所以第三步再用上节课 QEM 的减面方法对它简化，直到达到用户想要的低模网格。

```text
输入：高模
     │
     ▼
① Visual mesh 生成（visual hull 式的「切」）
     │    选一组观察方向：投影出轮廓 → 拉成扫掠体 → 与当前结果做布尔交
     │    迭代几个视点后，这些视角下的外轮廓与高模一模一样
     ▼
② Carve mesh 生成（雕出凹处）
     │    选平面：把原模沿负方向投影成扫掠体，从当前结果里布尔差掉
     │    从任何视角都看不见的凹槽，在这一步补上
     ▼
③ QEM 边折叠简化（上节课的经典方法，一路减到目标面数）
     │
     ▼
输出：低模网格（拓扑干净、外观相似）
```

读图：三步分别对应"看出轮廓、雕出凹陷、减到目标面数"；前两步都是布尔运算的活，第三步才是真正的减面。

#### Visual mesh：把轮廓从各个视角"看"出来

细节是这样。对于输入的模型，我们先计算它的一个包围盒，从包围盒开始。针对原模，从周围 360 度对它做投影——投影到平面上。平面的计算可以有一定的技巧：比如对原模的面片做平面片的聚类，聚出很多面片方向，然后从中选出一组观察方向。选定之后，从这些视点对三维模型做投影，投影出来就是平面上的一个轮廓（silhouette）。再沿着观察方向对这个平面的样子做 sweeping——把它"拉起来"，从下面往上拉都一样——拉起来之后就是一个体。这个体是封闭的、流形的、不会有自相交，而且是简单的。

每个视点实际上就对应这么一个体。它有什么特点呢？从对应的视角看，它跟原模的样子一模一样——至少外轮廓（silhouette）一模一样。然后我们拿这个扫掠体（swept volume）去跟输入的包围盒做一个布尔交运算；再以交运算的结果为新的起点，从其余的视点继续对 mesh 做投影、再做切割。比如上一次选的是从上往下看的视角，这一次换一个视角，mesh 又被精细化了一次。这么迭代几次、选定几个视角之后，生成的模型从这几个视角看，轮廓就跟高模一模一样了。这基本上就是 visual mesh 的生成。

这里面涉及的操作有几个布尔运算。一个是二维的：把三维模型投影到平面上，要投影出它的轮廓来——这个计算实际上是一个矢量计算，论文里用了一个我觉得用起来还不错的二维几何布尔库。另一个是三维 volume 的布尔交运算：我们要不断地把这几个扫掠体求交，得到越来越精细化的 visual mesh。三维布尔我们用的也是已有的算法和工具，具体细节论文里都有，对这个方法感兴趣的同学可以去看论文。

#### Carve mesh：把看不见的凹处雕出来

这一步的问题在于：如果原模里面有凹陷的地方——比如凹槽——不管你从哪个视角看，都看不到凹的地方，因为渲染走的是直线的视线原则。那怎么办呢？

第二步也挺有意思。同样从原模里面选出一些平面：假设我们知道原模是什么样子，选出一个平面；对这个平面，把原模沿着这个平面的负方向往平面做投影，投影完了也会得到一个扫掠体；然后把前面的 visual mesh 减去这个扫掠体，就把这一块给剪出来了——这是布尔差运算。不断地增加更多平面的扫掠体去做雕琢（carve），细节就慢慢被雕琢出来了。

大家可以看到，前面 visual mesh 的生成和这里 carve mesh 的生成这两步，基本上都涉及同样的两件事：三维模型到二维平面的投影，加上三维体的布尔运算——前者求交，后者做差。

#### 收尾的 QEM，以及"面数该减到多少"

我们最终还是想要那个低模网格。第三步就是用上节课提到的传统 QEM 方法对 carve mesh 做边折叠，通过不断选择合适的边，生成简化的模型。

但有一点要说在前面，这其实是减面算法的一个通用问题、通病：怎么选参数——你希望生成的最终减面结果的面数是多少？这个对自动化的算法来说非常难设计。以往的做法都是让用户指定最终减面的数目，然后生成符合面数的低模网格。缺点是：使用这个算法的用户（一般都是美术）可能并不清楚这个模型能简化到什么程度、简化到什么程度比较好——比如减到 300 面效果还不错，但算法其实减到 250 面效果也很好。这就需要来回地调试，叫 parameter tuning。实际用起来会比较费劲，尤其有的算法你算一次、调一次参数还要计算好久，很不人性化。

所以我们提出了一个很简单的思路：先把模型直接一路减到底——减到底之后，各种面数的结果我们就都有了；然后画一条曲线图，曲线的横轴是面数，每个面数对应一个模型质量——这需要一个模型质量的评估方法（metric）；根据这条曲线算一个 Pareto front（帕累托前沿）的最佳点，让用户从结果里面选。细节大家可以看论文。

#### 效果：拿数据说话

这是针对前面那组建筑数据生成的结果。比如一个非常复杂的中式、日式古建筑模型，右边是我们生成的低模；各种风格都有，比如中世纪——准确说是维京时代——那种用木头和茅草搭建起来的茅草屋模型，可以简化成外观跟原模很像、但又非常简单的样子。

衡量指标有两个：一个是面数；另一个叫 light field distance——它衡量你最终输出的结果在渲染时，跟原模在同一视角渲染下来的差别，数值越小质量越好。从这两个数据来看，我们的方法综合来看是最好的效果。我们也跟商业的和学术界的算法在整个数据集上做了对比：横坐标是面数和 light field distance 共用的，因为它们都是数值越小越好。

重新网格化其实还有一些其他的思路。比如今年我们又有另一个 SIGGRAPH 的工作发表，它不仅仅针对建筑，更加通用，也能生成非常好的效果，大家可以关注一下。

### 展 UV：把三维摊平到贴图空间

整个算法里面，第一大步重新网格化、生成低模网格，完成了最重要、最难的一步。那第二步是做什么？做展 UV。前面我们只是生成了网格模型，但要把纹理信息附着到三维模型表面上去，需要先对三维模型进行一个平面展开的操作。比如一个三维模型，我们希望把它摊到平面上去，使它们有一个映射关系——摊开的这块区域可以叫贴图空间（texture space）。把贴图放在这里，它就可以通过 UV 网格和三维网格的对应关系，映射到三维表面上去。这样我们渲染的时候才能看到带了材质贴图的效果，才有真实感。

#### 输入、输出，以及五条要求

展 UV 的输入基本上就是网格模型（三维的，也可能有二维的）；输出是 UV 网格。计算 UV 网格，实际上就是计算两者之间的映射——有了 UV 网格之后，你就自然而然有了这个映射。因为二维的 UV 网格和三维的网格模型，它们的三角形数目是一一对应的、一样的，只是顶点的 index 可能有所不同——因为里面经常会涉及切割的问题，会把一条边切成两条边。

对结果当然也是有要求的：

| 约束 | 类型 | 要求 |
| :--- | :--- | :--- |
| 不翻转 | 硬约束 | 展开后三角形不能翻面 |
| 不自相交 | 硬约束 | 展开后不能重叠穿插 |
| 切割短 | 软约束 | 切缝的总长越短越好 |
| 扭曲小 | 软约束 | 映射带来的拉伸变形越小越好 |
| 装箱面积小 | 软约束 | patch 在贴图空间里排得越紧凑越好 |

前面两条是硬约束，后面的更多是软约束。展开来说说这些约束背后的门道。

不能有翻转（flip）：三角形翻了之后，一个模型表面的多个区域可能对应到同一块颜色区域，造成一些不必要的 artifacts——所以不能翻，也不能自相交。

切割尽量短：通常来说，一个三维模型是嵌在三维空间里的，它的亏格可能很高，甚至它是封闭的——只要是一个封闭的模型，我们就必须对它进行切割，切割了之后才能把它摊到平面上去。切割的边界长度为什么越短越好？一条切割边在三维模型上是一条边，对应到二维 UV 网格里就成了两条边。纹理图是像素的、离散化的东西，要把它渲染到三维表面上的时候，往往需要跟邻居的像素——或者叫纹理素（texel）——做插值。切割数目多了，往往会造成不连续的情况：两个在三维空间里相连的边，两侧插值出来的纹理颜色往往是不一样的。所以这种切割的地方我们叫"缝"（seam），渲染时经常在那里出现大家不想要的效果。

扭曲尽量小：三维跟二维之间有一个映射关系，我们可以衡量这个映射关系的质量好坏，也就是扭曲。扭曲越小，二维空间中的图像、纹理是什么样子，映射到三维表面上的时候就能保持得越好。扭曲大是什么样？纹理图上一个正正好的三角形，映射到三维表面上变成一个非常狭长的三角形——本来纹理图上那个正三角形内部是比较合理的样式，到了三维空间被拉扯得完全不是你想要的样子。扭曲尽量小，我们制作贴图的时候就会更轻松一些。

装箱面积小：装箱这个事挺简单。前面我们会把 mesh cut 开成一块一块的 patch，而你往往不知道它在纹理空间中应该放在什么位置。装箱的意思就是把这些一块一块的 UV mesh patch 放在一起，又不让它们互相重叠——类似于把它们 pack 起来，越紧致越好。因为越紧致，你的纹理图上浪费的空间就越少：纹理图都是长方形的，那些没被 patch 盖住的白色区域基本都是浪费的——浪费了数据量，因为它们没有任何信息量。

展 UV 这个问题其实有非常多的算法，它本身就可以算作一个管线、一个模块，里面也分几个步骤：先对模型进行切割；切割完了，对切割成的 patch 做参数化，就是到二维平面的展开；展开完了，还要对它进行封装、装配，也就是装箱。这些环节里我自己选了一个我觉得大家理解起来还相对不费劲的工作，它基本上就是"切割 → 参数化 → 装箱"这么一个流程。我们就按这三步来说。

#### 切割：Variational Shape Approximation

切割可以基于 Lloyd 的算法——Variational Shape Approximation（VSA）这个方法。它的过程是这样：先决定要把模型切割成多少个 patch，每个 patch 就是一个连通的区域。一开始我们不知道具体该在哪里切割，就先随机选几个三角形做种子点：如果想切成三块，就选三个三角形当种子。然后基于贪心的方式，从每个种子点往外扩张：比如对某个种子相邻的几个三角形，算"把相邻三角形跟它合并在一起"的误差是多少，把这些都放进一个队列里做排序，然后一个一个去添加、不断地扩张，直到模型里面所有的三角形都被访问完毕。这样模型就完成了一个区域划分。

接着再对每个区域算一个误差——比如算一个区域的平均法向，以及这个法向跟区域里每个三角形法向的差别——根据这个差别信息，去更新、找到新的三角形种子点，然后再重复上面的步骤，直到所谓的收敛。收敛的定义也比较模糊：你可以指定迭代多少次，也可以指定误差降低到什么程度，总之达到一个比较好的分割效果就行。比如输入的模型是一头牛，就用这套迭代策略把它切割开。

这个算法有两点要注意。第一，它需要指定切割的区域个数——VSA、Lloyd 这个方法就是这样的。第二，切割的数目跟模型的复杂程度，以及我们前面讲的那些要求（缝尽量短、扭曲尽量小）往往是互不沟通的——它没有把整个过程作为一个全局优化来打通。这也是非常难的，因为里面涉及拓扑、连续优化等等很多变量，现在还没有方法能把这些都放在一起优化，所以大家往往就把这个问题拆分开来，每一步解决一个小问题。

VSA 这里做了一个设计：切割出来的每个区域，它的 UV 映射误差是能被约束（bound）在一个范围之内的。这样就会造成输入模型里有些区域没有被归类——它们无法被归到任何一个区域，因为只要一归类进去，误差就会很大——于是剩下这些黑色的地方。对这些地方要做 hole filling（洞填补）：要么把它们单独整成一些区域，再跟周围的区域进行合并。合并完了之后，网格模型的切割过程就完成了。

大家别忘了，整个 UV 展开里，切割模型只是第一步；切割完了，还要把每个 patch 摊到二维平面上去。怎么摊非常讲究——关于怎么摊一个网格，至少有几十个不同的算法。

#### 参数化：Tutte embedding 打底，scaffold 保双射

确定了一个 patch 之后，怎么把它插到平面上去？一般是基于一个理论，叫 Tutte embedding。Tutte embedding 是什么意思：如果一个 patch——一个圆盘拓扑的图——它的边界被映射到一个凸的边界上，那么通过 Tutte 这个算法，能保证计算出来的内部点的位置、算出来的这个网格，是没有翻转、没有自相交的。这也是非常重要的一个理论，奠定了绝大多数 UV 参数化算法的基础。

举一个几年前的、我觉得还不错的工作，来说明参数化这一步在干什么。从一个 patch 开始，对它做 Tutte embedding，把它映射到平面上（凸域）。但计算出来的这个参数化是有误差的，而且误差往往很大。所以可以运用一些连续优化的算法来减少这个误差。但减少误差的时候，边界就会变形——来回旋转也好，自由扩张也好（这里是一个示意图，实际中 patch 的形状会非常多样）——就可能造成自相交。自相交对纹理映射、对渲染来说不是我们想要的，我们希望这是一个 bijective 映射——UV 和模型之间是一一映射。

那怎么做呢？这个方法说：我可以加一些三角形，叫 scaffold（脚手架），或者叫 cage；通过保证每个三角形它不翻转，就会使得里面的结果永远不会有自相交。这就是这个方法的核心思路。细节反正也有公开代码，感兴趣的同学可以看原文。

#### 装箱：像拼俄罗斯方块一样排 patch

第三步骤装箱，也有非常多的算法，研究得比较多的叫 bin packing：把每一个 patch 作为一个 bin、当作一个长方形来 pack。这里介绍的这个方法说：可以把每一个不规则的 patch 看成一个长方形，借鉴拼俄罗斯方块的那种思想，设计了一个效果还可以的装箱算法。细节我就不展开了，大家可以去看原文来了解，他们也有公开的代码，想尝试还是比较容易的。

拿几种方法对比过装箱的效果：一种方法、另外一种方法，还有另一个工作的结果。这里我也不是说哪个效果就最好——用的都是它们各自论文发表时的结果。目前来说，这套流程算是比较接近实用的一个管线；要更实用一点，可以直接调用现成开源库（比如 xatlas）里的方法。

### 纹理烘焙：把高模的样子搬到低模上

到了第三大步：有了前面的网格，也有了它的 UV，我们需要对它进行纹理烘焙。烘焙的方法在种类上相对少一些，主要有两大类：一类是基于光投射（ray casting）的，就是投射线的方式；另外一类是基于可微渲染的——这是最近几年刚开始流行起来的一种方法论。我们分别说怎么通过这两种方式，把纹理、或者说整个模型的外观（appearance），迁移过去。

#### 光投射：本质是找对应点

把这件事画成一个二维剖面：黄色的复杂曲面是原模（reference mesh），黑色折线是低模——非常简单，数据量小，就是前面两步得到的结果。

原模上的这些属性——比如每个顶点的颜色、法向，或者其他一些信息（做动画的时候还会用到蒙皮权重等等）——怎么把它们传递到低模网格上去呢？

思路是：把低模网格沿着某个方向往外拉一下，拉出来一个 mesh，它跟低模是一一对应的——拉出来的这个东西叫做 cage，它可以把 reference mesh 整个框住。然后从 cage 出发，朝原来低模网格的方向投射线；射线会跟 reference mesh 有交点，交到哪里，就把那个点的属性赋值过来。因为 cage 上的点跟低模上的点是一一对应的，所以这个方法实际上就是找对应点：找到了对应点，就可以把高模表面上的属性迁移到低模上去了。

```text
      cage（把低模整体向外拉一圈得到，与低模一一对应）
      ═══════════════════════════════════
         │          │          │
         │ 射线      │ 射线     │ 射线        （朝低模方向投）
         ▼          ▼          ▼
            高模（reference mesh）∿∿∿∿∿∿∿
            （射线与高模相交，取交点处的属性）
         │          │          │
         ▼          ▼          ▼
      低模 ━━━━━━━━━━━━━━━━━━━━━━━━
           cage 上的点与低模上的点一一对应，
           交点属性写进低模对应的点 → 完成迁移
```

读图：射线从 cage 出发、穿过低模所在的位置、命中高模；高模交点上的属性，沿着这条"一一对应"的链路落到低模上。

你说找对应点，是不是还有其他算法呢？有的。但为什么这个方法比较流行？它经过了时间的检验，实际应用中大家基本都用这个。为什么都用这个呢？因为低模和高模的几何拓扑往往是非常不一样的，差别非常大；发表论文里那些计算对应点、计算两个 surface 之间 correspondence 的方法，有各种各样的假设，对现实应用中的情况往往不实用。而光投射这个方法非常鲁棒——不管怎么着它不会 crash，总是能找到一个对应的结果；而且它可以非常容易地 GPU 化，全都在 GPU 上实现，速度非常快，秒速出。

#### 可微渲染：把烘焙变成一个优化问题

另外一个思路是可微渲染。这个思路非常有意思，也可以用来做纹理烘焙。可微渲染现在有一系列的工作，这里只提我自己稍微熟悉一点的一个。

什么叫可微渲染？实际上就是把渲染的这个过程，做成一个连续的、可导的过程。为什么要做成这样？因为我们很多的优化问题，如果要做连续优化，就要求目标函数等等是可导的，才能做连续化；可导了，它就会给你一个下降的方向——让目标函数的能量值往下走的方向——这对优化来说比较容易，比较容易找到一个比较好的解。这就是为什么要做可微渲染、要把渲染可微化。可微化之后，参与渲染的各种场景或参数——三维模型的形状、材质（material）、还有灯源的位置等等——就都可以被优化，只要你能把它 formulate 成一个优化问题。

可微渲染的基本概念，用做渲染的同学比较熟悉的 Mitsuba 网站上那张经典示意图来讲最清楚（下面这张字符图就是按它的结构画的）：

```text
    x（渲染参数：模型形状 / 材质 / 灯源位置……）
         │
         ▼   f：渲染函数
         │   （rasterize / ray tracing / volume render ……）
         ▼
    y（输出图片）

    优化回路：
    高模渲染出 y，低模渲染出 y′
    g = ‖y − y′‖   （g 可微 → 得到下降方向 → 反向更新 x）
    本讲的用法：mesh 和 UV 已知，只把贴图当变量优化出来
```

读图：$x$ 是渲染的参数数据，$f$ 表示你用什么样的渲染方式——可以是 rasterize（光栅化），可以是 ray tracing，也可以是 volume render 等等，$y$ 就是输出的图片；渲染过程可导之后，就能沿着目标函数的下降方向反过来调参数。

渲染这个过程可导了之后，我们可以利用它来构建目标函数。比如 $g(y)$：我们的目标是什么？就拿这一讲的内容来说——高模渲染出的图片，和低模渲染出的图片，我希望它们尽量相似。那我的 $g$ 就是两者之差的某种范数：

$$g = \lVert y - y' \rVert$$

whatever 一种 formulation，只要它是可微的，我就可以用它来优化低模的某个变量。什么变量？比如我已经知道它的 mesh、知道它的 UV，我只想优化它的贴图，想把贴图给优化出来——那就可以做到这一点。

这是一篇论文展示的结果：高模和低模，diffuse map、specular map、normal map 等等，都可以 bake 出来——都是优化出来的，因为梯度是可以计算出来的，用可微渲染的方式就可以把它们优化出来。而且因为它是连续优化的方法，有些情况下效果比 ray casting 的方法要好很多——我们验证过。

### 收个尾：两大流程各是什么分量

到这里，不保纹理的模型减面方法就介绍完了。最后对几何处理与模型减面这三节课做一个大概的回顾。

我们主要讲的内容：三维模型的不同表示方式；mesh 这种表达方式及其相关的基本性质——它怎么表示、连接关系是什么样、拓扑什么样子、几何怎么样，以及我们处理这种表示方式时，需要做什么样的数据表示、怎么构建数据结构来帮助我们做相应的计算。然后重点介绍了怎么对 mesh 表达的模型进行简化、进行数据压缩。简化的方法、套路其实有很多种，我的目标不是穷举，而是希望大家掌握减面这一块两个主要的算法流程——保纹理的和不保纹理的——以及经典减面算法的核心思想，比如 QEM。

|  | 保纹理（QEM 一类） | 不保纹理 |
| :--- | :--- | :--- |
| 输入 | 模型网格 + 纹理 + UV | 网格本身（UV、纹理都不用管） |
| 输出 | 减面后的模型 | 低模网格 + 新 UV + 新烘焙贴图 |
| 框架 | 非常简单——太简单了，所以特别经典 | 三步管线，每一步都蛮难（烘焙相对简单些） |
| 鲁棒性 | 非常鲁棒，不太容易出 bug | 最关键看重新网格化之后的网格性质与质量 |
| 现状 | 经时间与实际应用检验的仍是 QEM 一类管线 | 展 UV、烘焙已有实用工具，重新网格化仍是难点 |

保纹理这一套：它的简化框架非常简单——太简单了，所以他特别经典，非常鲁棒，不太容易出 bug。经过时间检验、经过实际应用考验的，还是 QEM 一类的算法管线——这是针对保纹理这个思路来说的。

不保纹理的这一套：非常复杂，往往非常难——把每一步具体实现出来、甚至构思它，都不容易，因为每个步骤其实都蛮难的（纹理烘焙的 ray casting 还算相对简单一些）。它的效果往往非常取决于重新网格化这一步——最关键的就是重新网格化之后，网格的性质和质量。

展 UV 这一块：我们这里只是非常粗略地讲了算法流程，其实还有很多其他工作；但展 UV 已经有实用的工具和算法，在我看来它至少不是一个特别大的难点，有现成的工作可以去解决这个问题。纹理烘焙也一样有现成的工作，两个思路各有优缺点。

最后说两句题外话。今年我们还有一个新的低模 mesh 生成的工作，后面会把论文和可执行程序公开给大家，感兴趣的可以去看。另外，我现在在腾讯，在光子游戏工作室的技术中心做几何处理、可微渲染等相关方向的算法设计和研发，在招实习生——一般需要在读博士，或者有一定的专业背景：熟悉计算机图形学、几何处理相关的基础知识，还要能编程。感兴趣的可以私下联系，联系方式在第一节课 PPT 的个人主页上。
