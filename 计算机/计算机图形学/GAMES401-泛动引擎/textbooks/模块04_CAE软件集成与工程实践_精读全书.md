## 从一根弹簧到 CAE 平台：有限元怎么算，MxSimLab 为什么做
> 对应块：BLK21 | 覆盖分集：P11上 | 块标题（分集名）：《11. 从PeriDyno到CAE软件增量集成开》

这是这门课的最后一节。前面这一大段时间，我们一直围着 PeriDyno 转，把物理仿真引擎的基本算法、CAE 的一些基础理论和知识点都过了一遍。今天要收个尾，把两件事接上：一件是有限元到底怎么算——上节课讲的是弹性力学的理论，那条路一直走到应力与应变的关系，可这个关系怎么变成计算机能算的方程组，中间那一步是有限元方法；另一件是我们在这个引擎之上究竟做了什么，也就是怎么从一个物理仿真引擎，长成一个能用的 CAE 软件平台 MxSimLab。

按原先的安排，这一讲分三块：先补有限元的基本方法，再讲从 PeriDyno 到 MxSimLab 我们具体做了哪些工作，最后拿 MxSimLab 这个软件做介绍和教学。我们从头来。

### 胡克定律之后：把一根弹簧翻译成节点和单元

有限元听着唬人，我拿最笨的例子开场——一根弹簧。

```text
       k
  +--/\/\/\--+
  |          |
 [1]        [2]  --->  F
 U1 = 0     U2
```

左端固定死，右端加一个力 F，弹簧被拉长，伸长量记作 $\Delta$。上节课讲过，只要还处在弹性变形阶段，力和伸长量之间就是线性关系，这条关系叫胡克定律。它在弹性理论里是最基本的一条，描述固体材料受力之后应力与应变之间的关系——也就是上节课说的物理方程，应力和应变之间乘一个线性系数。

落到这根弹簧上，物理方程就具体成这样一行：

$$F = K\Delta$$

K 是弹簧的刚度系数。一行式子，这根弹簧的变形行为就说完了。

问题是，"左端""右端"这种说法不是有限元的语言。端点是弹簧自己的几何特征，是我们用眼睛分的。有限元用另一套东西描述它——节点和单元。这不是为了绕圈子，是为了规范化：物理对象必须先翻译成一套能编号、能批量处理、能递交给程序的符号，后面才谈得上计算。

翻译过来很简单：两个端点，定义成两个节点，左边一号、右边二号；整根弹簧是一个单元。节点上挂两个量，位移和节点力：一号节点有 $U_1$、$F_1$，二号节点有 $U_2$、$F_2$。四个数，这根弹簧的物理状态就描述完了。

> **定义**：节点是有限元里承载未知量的位置，单元是连接节点、携带材料与几何信息的那部分。一个有限元模型就是节点加单元。任何复杂的几何体，划完网格之后都退化成这两样。

有了节点这套描述，方程就能一行一行写出来。二号节点上的力来自弹簧的伸长，而伸长量就是两端位移之差：

$$F_2 = K(U_2 - U_1)$$

再看平衡。整根弹簧处在平衡状态，两个节点上的力加起来必须为零：

$$F_1 + F_2 = 0 \quad\Rightarrow\quad F_1 = -F_2 = K(U_1 - U_2)$$

这个负号不是笔误。$F_1$ 和 $F_2$ 是一对作用力与反作用力，大小一样，方向相反，所以位移项也要反过来减。

两行摆在一起，写成矩阵：

$$\begin{bmatrix} K & -K \\ -K & K \end{bmatrix}\begin{bmatrix} U_1 \\ U_2 \end{bmatrix}=\begin{bmatrix} F_1 \\ F_2 \end{bmatrix}$$

前面那一坨由刚度系数拼出来的矩阵叫刚度矩阵，这个方程叫平衡方程，也叫刚度方程。记成一句话：

$$\mathbf{K}\mathbf{U}=\mathbf{F}$$

> **结论**：不管你以后遇到多复杂的有限元问题，最后都归结成解 $\mathbf{K}\mathbf{U}=\mathbf{F}$ 这一个方程组。差别只在 K 有多大、里面装了什么。

那为什么非得写成矩阵？用一堆带上下标的公式不是一样能写清楚吗？

能写清楚，但落到程序上就不是一回事了。带上下标的公式，人看着都嫌繁琐，从公式到程序中间隔着一层很大的思维转变；而矩阵到程序，几乎是逐一对应的——K 是一个二维数组，U 和 F 是一维数组，循环把乘加做完，方程就解了。有限元之所以天生适合计算机去编程实现，很大程度上就因为它最后长成了这个样子。

我们做算法研究也是这个顺序：一开始用 MATLAB 把算法和推导实现出来、验证清楚，等基本原理和推导都结束了，再把 MATLAB 的程序翻译成 C 或者 Fortran。先求对，再求快；中间那层翻译之所以顺，就是因为两边都是矩阵的语言。

### 两个弹簧串起来：扩充、组装与整体刚度矩阵

一根弹簧说明不了有限元真正的难处。难处不在算，在"多"。

看两根弹簧串起来：

```text
        k1           k2
  +---/\/\/\---+---/\/\/\---+
  |            |            |
 [1]          [2]          [3]
  A            B            C
```

三个端点 A、B、C，编号 1、2、3；两根弹簧分别定义成 1 号单元和 2 号单元。于是这个物理系统在有限元里的描述是：三个节点，两个单元。

> **提示**：这一步就是建模，不是画图，是编号——哪几个节点连成一号单元、哪几个连成二号单元，全部落成数字。编号错了，后面算得再对也没用。

分析的时候不能整体一起上。做法是先拆：对每个单元独立分析，各自建平衡方程，再合并。有限元里"离散—组装"这四个字的全部含义，就在这里。

一号单元只认 1、2 号节点。单看它，就是一个前面算过的单弹簧问题：两个节点上各有位移和节点力，一根弹簧在中间，2×2 的刚度矩阵，形式和前面完全一样。

二号单元只认 2、3 号节点，同样是一个单弹簧问题，同样是 2×2。

2 号节点被两个单元共用，这是新出现的情况。它上面除了两个单元分别给出的内力，还可能挂着一个外力 $F_2$——也就是真正加载在这个点上的载荷。而两个单元在这个点上的内力是一对作用力与反作用力：大小相等，方向相反。

两个单元各自建完平衡方程，都是 2×2 的。现在要把它们合到一个系统里，问题来了：一个 2×2 的矩阵，怎么塞进一个 3×3 的方程组？

答案是先扩充，再相加。

扩充就是把尺寸补到整体规模，补出来的位置全部填零。1 号单元占的是 $U_1$、$U_2$ 这两行两列，所以它落在左上角，第三行第三列整片是零；2 号单元占 $U_2$、$U_3$，落在右下角，第一行第一列整片是零：

$$\tilde{\mathbf{k}}^{(1)}=\begin{bmatrix}k_1&-k_1&0\\-k_1&k_1&0\\0&0&0\end{bmatrix},\qquad \tilde{\mathbf{k}}^{(2)}=\begin{bmatrix}0&0&0\\0&k_2&-k_2\\0&-k_2&k_2\end{bmatrix}$$

填零不是凑数。零的意思是"这个单元跟那个节点没有关系"——1 号单元确实不认识 3 号节点，它对 $U_3$ 的贡献就应该严格为零。

两个都扩充到 3×3 之后，组装就是直接相加，和弹性力学里的叠加原理是一回事：

$$\mathbf{K}=\tilde{\mathbf{k}}^{(1)}+\tilde{\mathbf{k}}^{(2)}=\begin{bmatrix}k_1&-k_1&0\\-k_1&k_1+k_2&-k_2\\0&-k_2&k_2\end{bmatrix}$$

注意中间那个 $k_1+k_2$。它落在 (2,2) 的位置上，因为 2 号节点同时属于两个单元，两个单元都在这个位置上有贡献。这里会不会算重？不会。两个单元在 2 号节点上给出的内力是一对作用力与反作用力，合力恒为零，所以叠加进来的只是刚度，不是力。

> **结论**：有限元的整体思路就两步——先算单个单元，再把它们组装到一起。一根弹簧是这样，一万个单元也是这样。

### 三个方程六个未知量：边界条件与划行划列

整体方程有了，接下来要解。解之前先数一数：三个节点，每个节点一个位移一个力，六个未知量；方程只有三个。

> **易错点**：三个方程解六个未知量，解不出来不是方程写错了，是边界条件还没进来。这是初学有限元最容易卡住的地方——总觉得方程不够，其实是条件没给全。

缺的那一半来自边界条件。上节课讲过，整个系统是有边界条件的，分两类：位移边界条件（哪个节点被约束住、位移是多少）和力的边界条件（哪个节点上加了多大的外力）。

回到这个两端固定的两弹簧系统：A 点和 C 点都被固定住，对应 1 号和 3 号节点，于是

$$U_1=0,\qquad U_3=0$$

两个位移边界条件是白送的。再加上作用在 2 号节点上的外力 $F_2$ 是已知的（这是我们加载的力的边界条件），六个未知量里就只剩 $U_2$、$F_1$、$F_3$ 三个，未知量数终于和方程数对上了。

具体的操作，我用一种很土但很有效的办法——划行划列。既然 $U_1$ 和 $U_3$ 都等于零，方程里凡是乘到它们的项都自动消失，对应就是第一行、第一列、第三行、第三列，全部划掉：

```text
   [ x  -  x ]      x : 与 U1 = 0 / U3 = 0 相关，整行整列删去
   [ -  *  - ]      - : 保留
   [ x  -  x ]      * : 剩下的核心项
```

三阶的方程塌下来，只剩一个含 $U_2$ 的方程：

$$(k_1+k_2)U_2=F_2\quad\Rightarrow\quad U_2=\frac{F_2}{k_1+k_2}$$

三个位移全齐了：$U_1=0$，$U_3=0$，$U_2$ 由上式算出。也就是说，基于节点的描述里那三个位移未知量，到这里全部拿到。

然后是力。把三个位移代回完整的 3×3 方程组，$F_1$ 和 $F_3$ 就出来了——它们是固定端的支反力，是弹簧为了把结构拉住而给出的反力，不是外加的载荷。

到这里，三个节点上的力和位移，六个量全解出来了。

> **提示**：系统一大，3×3 就会变成几万乘几万，方法其实是类似的，也不止一种。划行划列是最直观的一种：约束住哪个自由度，就把对应的行列整片删掉，只解剩下自由的那部分。

有同学说这部分太专业了。确实，这里是有台阶的，而且不止一级：先得理解一根弹簧的力学，传统力学用胡克定律就能算；再上升到 CAE 分析里常用的有限元，把结构划成节点和单元，用有限元的模型来描述；最后把模型算完，把所有节点上的未知量都解出来。台阶是一级一级往上走的，跳不过去，但每一级本身并不高。

好在不管以后多复杂的有限元，基本思路都和这根弹簧一模一样。

### 三个函数撑起一个有限元程序

把上面整套流程落到程序里，模块化程度高得有点出乎意料。先把涉及的变量理清楚：

- 每个弹簧单元由两个节点构成；
- 单元刚度矩阵是 2×2；
- 整体刚度矩阵是 $N\times N$，N 是节点总数——两个弹簧三个节点，所以是 3×3；
- 结构方程还是 $\mathbf{K}\mathbf{U}=\mathbf{F}$。

然后，全部工作只需要三个函数：

| 函数 | 输入 | 输出 | 干什么 |
| :--- | :--- | :--- | :--- |
| 单元刚度矩阵 | 单元刚度系数 K | 2×2 单元刚度矩阵 | 造出小 k |
| 组装 | 小 k、两端节点编号 i 和 j | 更新后的大 K | 定位并累加 |
| 载荷 | 单元刚度矩阵 k、单元位移 u | 单元节点力列阵 | 算 k·u |

第一个函数最省事，因为弹簧单元的刚度矩阵形式是固定的：

$$\mathbf{k}=\begin{bmatrix}k&-k\\-k&k\end{bmatrix}$$

所有单元长得一模一样，只有 k 的取值不同。所以函数只要吃一个刚度系数、吐一个 2×2，就完成了。不同单元无非是把不同的 K 传进去而已。

第二个函数是组装，它要解决的唯一问题是"这块东西该放到大 K 的哪儿"。答案就藏在节点编号里：单元的两个节点是 i 和 j，它的四个格子就分别落在 $(i,i)$、$(i,j)$、$(j,i)$、$(j,j)$。位置是算出来的，不是写死的——真实模型动辄几万、几十万个节点，位置根本不可能手写。前面那个"2×2 扩成 3×3、空位填零再相加"的过程，在这个函数里就是一次下标映射加一次累加。

第三个函数是载荷。$\mathbf{F}=\mathbf{K}\mathbf{U}$，K 是矩阵，U 是列阵，乘出来就是这个单元的节点力列阵。一行代码的事。实际用的时候，它也是放在循环里对每个单元调用一次。

三个函数写完，流程就能跑了：循环所有单元算小 k，循环所有单元把小 k 组装进大 K，引入边界条件划掉被约束的部分，解方程，再回代求力。

> **结论**：这样写出来的程序，不管是一端固定、两端固定，还是三个弹簧、几十个弹簧，函数一行都不用改。变的只有两件事——模型怎么建（节点和单元的对应关系），边界条件有哪些。

这也是我讲这半天最想说的一句：有限元难的不是算，是建模。节点和单元的关系建对，边界条件找准，剩下的事就是这几个函数来回调用。

### 拿 K1=100、K2=200、P=15 走一遍完整流程

换一个具体的系统，把流程完整走一遍。还是两根弹簧串联，但约束和加载换了：左端固定，右端自由，在 3 号节点上加一个力 $P=15$；两根弹簧的刚度系数 $K_1=100$、$K_2=200$。要的东西有四样——整体刚度矩阵、2 号和 3 号节点的位移、1 号节点的支反力、每根弹簧的内力。

第一步，离散。写程序的人都习惯用一张表把模型记下来：

| 单元编号 | 节点 i | 节点 j |
| :--- | :--- | :--- |
| 1 | 1 | 2 |
| 2 | 2 | 3 |

六个数字，一个物理模型就表达完了。这就是有限元的好处：再怎么复杂的几何形状，划完网格之后也是这张表，只是行数多得多。

第二步到第六步，按流程往下走：

```text
  单元刚度矩阵     k1 = f(100) , k2 = f(200)
        |
  造整体矩阵       3x3 全零
        |
  组装             assemble(k1, 1, 2) , assemble(k2, 2, 3)
        |
  边界条件         U1 = 0 , F2 = 0 , F3 = 15
        |
  求解             K\F
        |
  回代             F = K * U
```

组装完的整体刚度矩阵是

$$\mathbf{K}=\begin{bmatrix}100&-100&0\\-100&300&-200\\0&-200&200\end{bmatrix}$$

中间那个 300 就是 $100+200$，两个单元在 2 号节点上重合累加的位置。

边界条件三个：$U_1=0$（左端固定）、$F_2=0$（2 号是系统内部节点，合力为零，没有外力）、$F_3=P=15$（右端加载）。一代进去，剩下的未知量正好三个：$F_1$、$U_2$、$U_3$。

划掉第一行第一列，缩简成 2×2：

$$\begin{bmatrix}300&-200\\-200&200\end{bmatrix}\begin{bmatrix}U_2\\U_3\end{bmatrix}=\begin{bmatrix}0\\15\end{bmatrix}$$

在 MATLAB 里，求解就是一个左除：

```matlab
Ur = K(2:3, 2:3) \ F(2:3);   % 划去第一行第一列后左除
U  = [0; Ur];                % 补回已知的 U1 = 0
F  = K * U;                  % 回代得全部节点力
```

左除 `\` 等价于乘逆再乘，也就是 `inv(K)*F`，两条路结果一样；工程上一般直接用左除，不显式求逆。

数代进去：$U_2=0.15$，$U_3=0.225$。

回代之后 $F_1=100\times 0-100\times 0.15=-15$。负号说明支反力的方向与 P 相反，大小 15，正好把 P 顶住。

弹簧的内力也顺手出来了：1 号单元伸长 $0.15$，力 $100\times 0.15=15$；2 号单元伸长 $0.225-0.15=0.075$，力 $200\times 0.075=15$。串联的两根弹簧内力相同，且与 P 平衡——这个校核能过，说明整条流程没走错。

> **结论**：整个有限元计算就是这六步，多复杂的模型都不换。差别只在单元刚度矩阵怎么算——弹簧是 $K$，杆单元、三角形单元、四边形单元、四面体、六面体各有各的公式。

杆单元、三角形单元、四边形单元、四面体、六面体这些，限于课时就不往下展开了，有兴趣自己往下学。但基本思路和这根弹簧完全一致：离散、扩充、组装、引入边界条件、求解、回代。把这六步吃透，换单元类型只是换第一个函数里的那个矩阵。

### 为什么要把 PeriDyno 变成 CAE 平台

有限元这一块先放一放。上节课到这节课，前后大概花了我们两三个小时，从弹性力学一路铺到有限元的基础，总算是把"有限元大概是怎么实现的"这条路走通了。现在回到这门课更本行的部分——物理仿真引擎，和围绕它的编程。

接下来的问题是：一个物理仿真引擎，为什么要往外走一步，变成一个 CAE 软件？

关键在框架。我们想要的是一个能支撑增量集成的 CAE 软件框架出来——不是再写一个能算的例子，而是搭一套东西，让后面的人可以一段一段往里加。

这个判断是有背景的。CAE 软件的应用领域、它的优点和缺点，前面都讲过；往后看，CAE 软件的开发方向是比较清楚的：智能化、集成化，以及越来越明显的开源、云化和协同化。

- **协同化**：多人、多部门、多工程师之间的软件协同开发。不是一个人闷头写，而是一个团队甚至几个团队在同一个平台上并行推进。
- **多平台、多屏**：手机端、iPad、平板、笔记本、工作站，同一套计算能力要能在这些设备上都用得起来。
- **多物理场**：结构场、电磁场、声场……各种场之间的耦合。用户想要的是一个平台，把不同的场放在一起算，而不是每个场各买一套软件、各导一次数据。
- **交互多元化**：软件的交互形式也要有多种，不能再默认所有人都坐在工作站前敲命令。

还有一层是国家层面的判断。刚颁布的开源工业软件白皮书里，关于 CAE 软件集成框架的那部分分析，我觉得讲得非常正确。它梳理自主 CAE 软件发展的阶段，提到一件事：我们的理论研究基础，其实是比较充足的；真正卡住的，是从理论研究走到产品级工业软件这一段。

这句话正好点中了我们做这件事的理由。理论我们不缺，缺的是把理论变成产品级软件的那一段工程——框架、集成、协同、多平台、多物理场。MxSimLab 要接的，就是这一段。

## 从 PeriDyno 到 MxSimLab：把 CAE 软件的重复劳动交给平台
> 对应块：BLK22 | 覆盖分集：P11下 | 块标题（分集名）：《11. 从PeriDyno到CAE软件增量集成开》

国内做工业软件的人大概都有同一个感受：真正拿得出手的国产工业软件太少，工程上跑的绝大多数还是国外的软件。而一个工业软件要立住，绕不开一个必经的阶段——闭源。走到闭源那一步，要交的作业其实就两块：一块是软件核心代码的开发，一块是把这个软件集成、封装起来。

把这两块拆开看，问题就具体了。核心代码开发是创造性的活，集成封装却往往是重复性的琐碎活。于是很自然会追问一句：有没有一个快速的平台，能帮我们把这件事情做掉？

我们和何晓伟老师一起，依托一个国家计划的支撑，做的就是这么一个增量集成的 CAE 软件。它想解决的是 CAE 行业里一类低价值的重复——很多同学（包括正在上这门课的你）都想动手做一个自己的 CAE 软件，但一想到那些跟自己研究点无关的琐碎工作：搭界面、接文件格式、管数据，就不想重复去做第二遍。你真正想做的只是自己感兴趣的那一段，剩下的完全可以交给平台，这样才谈得上保证软件的高质量发展。

另一个角度是需求的层次。不同任务驱动下，大家对 CAE 软件的学习、开发、应用的需求是不一样的。上了这么几节课之后，很多人心里已经开始"蠢蠢欲动"，想试试自己到底能在 CAE 软件里做点什么。那到底能做什么？按人的处境分，大致是三种。

### 三类人，三种用法

#### 为了学习和科研，想自己搭一套面向行业的 CAE 软件

如果目的是学习和科研，很自然会想做一点软件开发的工作：比如想给某个行业做一套自己的 CAE 软件。那这个时候需要的，是一个能快速集成的平台——因为 CAE 软件本身是分段的：前处理（画网格、加边界条件）、求解、后处理，一段一段。我希望这个平台能帮我把这几段流程快速集成到一起，而不是每一段都从零写。

这里的复用性到底有多强，前面讲过的弹簧系统就是最好的例子。那个系统翻来覆去用的其实就是那么几个函数：一个是算单元刚度矩阵的函数，一个是把单元刚度矩阵组装成整体刚度矩阵的函数，一个是算力的函数。就这三个简单的函数，拼起来就能算一个非常复杂的弹簧系统。

> **结论**：真正被反复复用的东西往往很少，值钱的是"怎么把它们拼起来"。平台的价值就在于把这些函数做成可以拼接的软构件，把拼装这一步变简单。

当然还有一类更轻的诉求：科普性的学习。就是好奇，想尝试自己搭一个仿真流程跑起来看看。这种需求同样需要一个门槛足够低的平台。

#### 手里已经有求解器，缺的是前后处理

CAE 分析由前处理、求解器、后处理三块组成。假设你已经开发出了一个很好的求解器，但没有前处理也没有后处理，怎么办？这时候你需要的平台，是能提供前处理和后处理，让你的求解器插进去，快速完成一个完整 CAE 软件产品的开发。

还有一种更靠里的情况：我手里有很好的算法，想去实现一下——比如前面讲过的某些物理方程的算法、本构方程的算法，或者单元计算的算法——我希望有个平台能帮我快速实现、快速做测试。

#### 有模型，要拿去算的人

工程里的处境常常是反过来的：模型在手，软件没有。比如现在要算一个汽车或者高铁的模型，模型是有的，但得去找一个软件来算。

再一种：同一个模型，我想用不同的软件各算一遍——用开源软件算、用自己开发的软件算、用商业软件算——然后对比它们的计算精度和计算效率。那我就希望有一个平台能把这些软件都集成进来，模型可以很快地在几个软件上分别测试、拿到结果。

再往远看一层：如果我们能提供一个足够好的开源平台，靠大家共同的努力，是不是也有可能在有些场景里替代商业软件？这是做这件事的第三个想法。

### PeriDyno 之上，我们又加了什么

具体怎么实现？围绕着 PeriDyno 来做。前面何晓伟老师已经讲了很多课，这里不再重复它的原理：它是一个开源的增量集成核心框架，主导概念就是拖拽式的增量集成。

我们团队围绕 PeriDyno 和 CAE 仿真的需求，做了几件事：

- 扩充仿真数据域。仿真计算过程中要涉及单元、节点、材料这些数据，得把它们加进 PeriDyno 的数据体系；
- 加入大量 PeriDyno 的 load 节点和 model 节点；
- 基于 PeriDyno 的框架做核心算法的开发与实现，目标是高可复用性；
- 做跨平台、软硬件自适应的工作（这部分比较琐碎，但省不掉）；
- 最终完成 CAE 软件前处理、求解器、后处理这些软构件的开发与集成，形成这一讲讲到的 MxSimLab。

于是它的身份就变了：从一个增量开发的框架，变成一个适用于 CAE 软件开发的开源底座。中间还做了很多面向工程应用的迭代，在很多场景里做过测试和应用验证。里面融进去的算法很多，其中不少跟有限元专业强相关，这里不展开；但正是这些集成，让它能撑住相当复杂的 CAE 仿真分析。

### 四层架构没动，动的是每层里装的东西

MxSimLab 的整体框架跟 PeriDyno 的架构完全一样，还是那四层。

```text
仿真场景层    拖拽节点，搭出完整的 CAE 分析流程
    ↑
load 层       一个个具体功能节点
    ↑
model 层      各类仿真计算功能模块（这里多了仿真算法库）
    ↑
data 层       单元 / 节点 / 材料 等仿真数据（这里扩了 CAE 数据）
```

读图：自下而上是四层。data 层提供数据，model 层把数据算成功能模块，load 层是模块外面那一层可以直接调用的功能节点，最上面的场景层——你把节点拖进去、连起来，就是一条仿真流程。

data 层就是前面讲的那套数据体系，只不过我们把 CAE 仿真需要的很多数据加了进去；model 层是各种仿真计算功能模块的实现；load 层是具体功能的节点。最上面的仿真场景层，则是把整个 CAE 分析——前面讲的各种理论、各种计算流程——分解成一个个节点，然后在场景里把这些节点搭成你需要的流程。

这套分层带来的好处，是 PeriDyno 本来就有的那几个"分离"：

- 仿真计算与渲染分离。计算和渲染是两套独立的管线；
- 仿真与交互分离；
- 仿真与底层分离。

这三条说白了是一件事：界面怎么操作，不影响仿真模块本身；仿真模块怎么算，不绑死在某一种底层实现上；算完的东西怎么画，也走自己那条渲染管线。任何一头要换，另外两头不用跟着改。

正是这些分离，保证了仿真模块的高可复用性。MxSimLab 做的事情，是把 PeriDyno 这几个优势完整继承下来，再集成到自己的平台里。框架整体是 PeriDyno 的，我们只是在其中一块里加了仿真算法库，其余模块层的思想照旧。

### 平台里已经装了什么

整个软件是开源的，代码放在 Git 仓库上，仓库页面有非常详细的说明，一步步教你怎么编译。编译的流程和思路跟 PeriDyno 非常类似，所以这一讲就不再逐条演示怎么编译了。如果觉得编译太麻烦，或者在安装、使用过程中遇到问题，可以扫码加入 MxSimLab 的微信群，主要研发人员都在群里，随时可以交流讨论。

求解计算这一块，平台里同时装了自研的和开源的求解器：

| 求解器 | 来源 | 主要用途 |
| :--- | :--- | :--- |
| 显式动力学求解器 | 本团队自研 | 显式动力学问题 |
| 隐式求解器 | 本团队自研 | 隐式求解（线性静力学这类） |
| 流体求解器 | 本团队自研 | 流体计算 |
| 多物理场求解器 | 本团队自研 | 多物理场耦合 |
| OpenRadioss | 开源（此前闭源，近年才开放） | 汽车碰撞这类显式动力学分析 |
| CalculiX | 开源、成熟 | 通用有限元分析 |
| SU2 | 开源 | 流体计算 |

OpenRadioss 是现在国内非常主流的显式开源求解器，以前是闭源的，后来才开源，做汽车碰撞这类分析很合适；CalculiX 是一个非常成熟的开源有限元软件；SU2 则是流体计算用的。如果你自己手上有想用的求解器，也可以基于这个平台接进来。

之所以敢让你只带一个求解器进来，是因为前处理和后处理的节点我们已经备齐了：画网格、建立有限元模型、读取模型，这些都能在前处理节点里完成。几何文件目前支持 STEP 和 OBJ 两种导入，有兴趣的话还可以接 OCC、IGES 这些开源库，把更多格式的几何文件读进来，导入之后就能直接做 CAE 分析。

此外还有帮助系统；另外还有一个协同系统，这一块还在开发中，目前还不那么完善。

### 界面：一棵节点树，一个场景

软件的界面风格跟 PeriDyno 相比有一定改变——因为要照顾 CAE 工程师习惯的界面；但整体的布局之类，跟 PeriDyno 还是很像的。

界面上有节点树，我们开发的所有节点都放在里面，可以按类别去找：前处理、单元计算、后处理、各种文件系统、材料、各种求解器、渲染，等等。节点树之上还支持比较好的插件式开发：如果你想自己加一个节点进来，可以用插件的形式，也可以像前面基于 PeriDyno 那样直接写代码开发。这两种开发模式跟 PeriDyno 完全一样，这里不重复，重点讲这个软件能做什么功能。

### 走一遍完整算例：从 CAD 模型到云图

先看最标准的一条路——做一次完整的有限元分析。它的起点是前处理，而前处理要解决的核心问题只有一个：把 CAD 模型变成 CAE 模型。

#### 网格：先读 CAD，再选剖分引擎

网格这一块，我们开发的是一个画网格的引擎模块，里面主要就两个节点。

第一个是网格设置节点。它的输入是文件路径——这个文件就是你的 CAD 模型文件；它做的事情是把 CAD 模型传进来，然后让你选择要用的网格剖分引擎。我们这里集成的是一个开源引擎 Gmsh，所以还要指定这个引擎在你机器上的路径。

选好模型文件之后，界面上会提示"几何模型已经导入成功"，模型也就显示出来了。但要注意，这个时候它还只是几何模型，是 CAD 的模型，不是网格。

第二个是网格引擎节点，它负责真正做剖分：把网格设置里那些参数拿过来，喂给剖分引擎去算。

操作上，先指定要用的开源剖分引擎，再选一组网格参数。我们这个是实体模型，所以要画的是体网格；体网格里选四面体网格。其他参数可以先默认不管，真正重要的是网格大小——你打算用多大的网格把模型离散出来。演示里把最大尺寸设成了 6。

> **易错点**：网格尺寸是一个纯粹的权衡，没有"最优值"。尺寸小，离散出来的网格数量就多，占的内存空间大、计算量大，但精度高；尺寸大，算得快，精度就低。选多大，取决于你要的精度和你能付的代价。

参数定完点一次保存，网格这一环就算搭完了。

这里还有一个设计上的考虑：把网格数据集单独输出一下。原因是网格剖分有它的独立性——剖分引擎产出的数据集应该能独立交出去，后面的环节直接把它接进来就行，不必和前面的 CAD 读取绑死。

#### 前处理：材料、截面、单元、工况、载荷、边界

网格有了，接下来是有限元分析的前处理。这里能看出架构的弹性：前处理有两种用法，一种是用一个大的前处理节点，把材料、截面、单元、工况、载荷、边界这些设置全装在里面，一次配完；另一种是拆成一个个小节点（后面再说）。先走大节点这条。

材料这一步，选材料类型——我们这里用的是弹性材料、各向同性的，然后填它的参数：杨氏模量和泊松比。演示里这些数值是随便设的，只为把流程跑通。填完保存，材料就出现在列表里了。

截面这一步的作用，是让求解器认识你的网格"是什么"。网格本身只是一堆单元，求解器不知道它们代表什么，所以我们要创建一个属性，说明它是一个三维实体的截面，再把刚才那个材料赋到这个属性上。

单元这一步，因为网格是四面体的形式，而四面体在计算时有很多种单元计算的形式可选。如果你正好在做单元算法的开发，这里就是你的入口——在这里开发一个单元算法挂进来就行。演示里不动它，默认用四节点的四面体单元（C3D4）来计算。

工况这一步，我们做的是线性静力学分析，所以求解器怎么选之类的都不用管，直接创建一个工况。

然后是载荷和边界。分析的对象不可能是一个完全自由的物体，总得有些地方被固定住，所以我们把模型的两端固定起来：选面，把两端的两个面都选上，加一个边界条件把它们约束住。

载荷则是另一回事：在上面那个表面上加一个集中力，沿 Z 方向，大小 100。

> **提示**：载荷和边界条件经常被混为一谈，其实是两件事——载荷是你施加的力，边界是你限制住的自由度。一个分析里两样都得有，而且要先想清楚"哪里动不了、哪里在受力"。

#### 计算文件与求解

前处理的所有设置，最后要变成求解器能读的东西。这一步由计算文件输出节点完成：它把前处理生成的数据集，转成求解器能读入的计算文件。

连接关系很直白：前处理的一系列设置生成数据集，数据集传进计算文件输出节点，节点吐出计算文件，计算文件再传给求解器；求解器读这个文件，算完输出结果。

演示里用的是自研的隐式求解器，这个算例规模不大，很快就跑完了。结果就是前面那块模型在受这样一个集中载荷之后的求解结果。

求解这一段也是可以整段换掉的：比如不用自研求解器，改用第三方的开源求解器，只要把计算文件的路径接到对应节点上，它照样能算、照样能输出。这一点下面还会展开。

#### 后处理：VTK 解析与云图渲染

求解完之后要能看结果。后处理的查看基本是基于 VTK 文件来做的：求解器算完会得到一系列 VTK 文件，把这些文件传给 VTK 解析节点，解析完再在云图里渲染出来，结果就出现在窗口里了。

把整条链路串起来看，就是 CAE 仿真的标准流程：

```text
CAD 模型（STEP）
      ↓  网格设置：指定模型文件、指定剖分引擎
      ↓  网格引擎：体网格 / 四面体 / 最大尺寸
   网格数据集（单独输出，保持剖分的独立性）
      ↓  前处理：材料 → 截面 → 单元 → 工况 → 载荷 → 边界
   计算文件
      ↓  求解器读入并计算
   VTK 文件
      ↓  VTK 解析
   云图渲染
```

读图：前四个环节（网格设置、网格引擎、前处理的各项设置、计算文件输出）全部属于前处理，中间那一步是求解，后面是后处理。这条链就是"前处理—求解—后处理"三段在节点层面上的展开。

#### 几何模型和网格模型叠在一起，为什么不完全重合

有一个细节值得单独说：把几何模型和网格模型同时显示出来，会发现它们在有些地方并没有完全重合。

这不是显示的问题，而是 CAD 与 CAE 之间本来就存在的误差——网格是对几何的离散近似，曲面被四面体切分之后，边界一定会偏离原来的几何面。你看到的那些缝隙，就是这种近似计算的形式本身。

> **提示**：所以"网格画得对不对"不能只看它像不像，还要看尺寸是否合理；精度和代价的账，从画网格这一步就已经开始算了。

### 把大节点拆成小节点：粒度自己定

刚才那条链用的是一个大前处理节点。但同一个算例也可以做得更细，细到什么程度由你的兴趣决定。

从网格剖分开始就不再用大节点了：网格设置、网格引擎单独拿出来；材料、截面、工况、载荷、边界条件各自独立成节点；计算文件的输出也单独一个；后处理这边，VTK 文件解析和云图渲染也各自独立。然后按"前处理—求解—后处理"重新排一下序，连起来。

```text
前处理
  网格设置 → 网格引擎 → 网格数据集
  材料 → 截面 → 单元 → 工况 → 载荷 → 边界
  计算文件输出
求解
  求解器（自研隐式 / OpenRadioss / CalculiX / SU2 …）
后处理
  VTK 解析 → 云图渲染
```

读图：同一个算例被拆成三组节点，每组内部是一条链，组与组之间用数据集连起来。粒度越细，能替换的点就越多。

每个小节点点进去，里面的窗口跟大节点里对应的那部分设置是一样的——所以拆细并不会多出新的工作量，只是把"一整块"切成了"可单独替换的几块"。

好处就在这里：你在某个节点上开发了自己的功能，就把原来那个删掉，把你的放进去替代。于是同一条流程能同时满足不同的人：

- 只做求解器：前后处理节点全部复用，自己把接口定义好、连起来；
- 只做网格剖分（学图形学的同学往往对这个最感兴趣）：开发自己的剖分引擎，把网格数据往下传给求解器；
- 只做单元算法：在单元那一格换上你自己的实现。

### 接一个开源求解器：OpenRadioss 的接入过程

把开源软件集成进来，套路也是一样的。以 OpenRadioss 为例，需要这么几个节点：

- OpenRadioss 调用节点：我们开发的，用来调用本机安装的 OpenRadioss 求解器；
- 文件输入节点：把计算文件送进这个开源求解器，顾名思义，就是把文件传进来；
- 结果转换节点：OpenRadioss 输出的结果文件不是 VTK 的，所以又单独开发了一个节点，把它的结果转成 VTK；
- 后面就复用现成的 VTK 解析和云图渲染节点。

```text
[文件输入] → [OpenRadioss 调用节点] → [结果转 VTK] → [VTK 解析] → [云图渲染]
```

读图：前三步是这次新接进来的，后两步直接复用平台已有的后处理节点。接入一个新求解器的工作量，基本就压在前三步上。

操作上，先在调用节点里指定本机安装 OpenRadioss 的位置（演示里是手动选的，实际用可以设成默认值），再去文件输入节点选一个要算的文件。演示用的是气囊的算例——文件一传进来，就已经自动调用 OpenRadioss 开始求解了，界面下面会提示"现在用 OpenRadioss 进行求解"。

算完之后，结果由转换节点解析出来。这个算例模拟的是气囊撞击的过程，是一个动态过程：汽车发生碰撞之后，气囊怎么展开，可以在平台里直接看。整个展开、"爆炸"的过程都能放出来。比例自动调整这个功能在这个版本更新时还有点问题，演示里是手动调的——这类小毛病也说明平台还在迭代。

同样的方式可以接 CalculiX，也可以接 SU2 这类流体求解器。你自己想用的求解器也能这么接进来：文件输入、后处理全部复用现成的，你只需要开发一个节点，把求解器调用进来。

### 平台还在长：两种增量方式与 Python 空白节点

目前做增量开发有两条路，前面何晓伟老师讲过：一条是基于代码——复制一个空工程，基于模板去修改；一条是基于插件系统。

团队现在在做更细化的功能。比如加一个空白节点，在这个空白节点里可以直接用 Python 做二次开发：在界面里写 Python，完成整个节点的逻辑——比如解一个方程组，或者算某一个单元。写完就能用，不必回头去动框架那一层。

单元协同这一块，我们团队和何晓伟老师团队也在尽量把它做得更好；软构件复用这些库同样在逐步完善。想用的话，去仓库里把软件下载下来，或者加群交流。
