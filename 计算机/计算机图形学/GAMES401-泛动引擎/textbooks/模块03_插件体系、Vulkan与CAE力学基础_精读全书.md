## 把各种仿真技术串成一台机器：PeriDyno 的插件与蓝图机制
> 对应块：BLK13 | 覆盖分集：P07上 | 块标题（分集名）：《7. PeriDyno插件与功能拓展》

### 这一讲真正要解决的只有一个问题

时间差不多了，我们开始。

这一讲的主题是 PeriDyno 这套系统里的插件机制，以及跟它相关的一些功能。内容会比较散，这一点我先说在前面。但目标其实只有一个：前面我们已经零零散散讲过流体，讲过别的技术，还有一些技术没来得及讲；现在要把这些各种各样的技术串起来，让它们在一个整体框架里协同工作，去搭真正复杂的场景。

在说框架之前，先分清一件事。做仿真，如果针对的只是某个特定的算法，那么有没有框架、有没有引擎，区别其实不大：你自己写一个求解器，跑一个算例，框架在这个环节帮不上太多忙。真正的问题出现在另一种情况下——你需要很多模块相互依赖，需要多人协同开发。这时候，有框架和没框架，差别就出来了：模块怎么配合、接口怎么对齐、谁的改动会不会把别人的东西弄坏，这些都要有个地方管。

这件事不是凭空想出来的，是我们从过去的研究一路做到工程应用，实打实碰出来的。所以这一讲讲的不只是软件设计，也是一段从研究到应用的路。

#### 从理论创新到应用，中间隔着一段很长的路

所有的应用，起点都是理论创新。但起点不等于终点：理论创新最后能不能变成应用，不一定。这中间要解决一大堆问题。

我把它画成三个区域，分别对应研究、研发、应用，合起来是一个完整的流程。而且注意，它不是一条单向流水线，整个过程是迭代的、是闭环的。

```text
        ┌────────────────────┐
        │   研究：原始创新     │  论文 / 代码资产
        └─────────┬──────────┘
                  │ 代码维护、文档注释、依赖升级
                  ▼
        ┌────────────────────┐
        │   研发：工程化改造   │  数据规范 / 接口规范 / 模块改造 / 测试
        └─────────┬──────────┘
                  │ 兼容性改造
                  ▼
        ┌────────────────────┐
        │   应用：真实场景     │  性能 / 稳定性 / 可靠性
        └─────────┬──────────┘
                  │ 使用中暴露新问题
                  └──────────► 回到研究起点
```

读图：三个区域串起来是一个流程，但最后一段冒出来的问题会重新回到研究，于是整个流程首尾相接，成了一条闭环。每一段都有自己的成本，而且成本的性质完全不同。

#### 三个阶段，三种成本

先看研究这一段。对高校、科研院所来说，这一阶段主要是发论文。但论文之外，代码本身也是非常宝贵的资产。现实是什么样？文章发了，代码当时还能用，过一阵子就不知道扔到哪去了，或者根本找不着了。

就算找着了，还有第二个问题：软件系统会随着底层库、各种平台的更新不断演进，需要持续升级换代。长期缺乏维护，整个系统、整个代码最后就跑不起来、用不起来。第三个问题是传承：科研代码相对来说没有那么规范，文档、注释这些东西并不健全。结果是——论文发了，但真正工程性的、代码性的资产，很难传下来。

再看研发这一段。即便代码传下来了，要走到工程应用，还得经历研发：数据规范、接口规范、模块改造，各种测试，让它变得更好用。这一步的麻烦在于，它不单纯是一个工程问题。如果里面涉及核心算法——打个比方，流体算法——纯粹依赖工程改造，或者丢给另外一批工程人员去解决，很多时候并不合适。核心的东西，写它的人不参与，改出来的东西就不对味。所以到底谁来解决问题，本身就是个问题。最理想的情况是工程人员、研发人员和研究人员一起配合。

最后是应用。具体要用，很多时候得到真实场景里去测：性能、稳定性、可靠性，这些指标都得在实际场景里过一遍。用的过程中如果发现新问题，理论上有可能会回到我们一开始的起点——研究。说白了就是又发现了新的问题，需要从研究的角度去解决。

所以整个逻辑是一个闭环，而且需要不同角色参与：研究人员、工程人员、编程人员，还有设计人员。不同角色配合起来，是有协作成本的。而且各阶段的成本性质不一样：

| 阶段 | 主要产出 | 成本的性质 |
| :--- | :--- | :--- |
| 研究 | 论文、算法实现、代码 | 不确定性：选题、调研、实现、对比、撰写、投稿修改，周期长且不可控 |
| 研发 | 可用的模块与接口 | 规范与改造：数据、接口、兼容性、测试 |
| 应用 | 真实场景中的系统 | 实测指标：性能、稳定性、可靠性 |

#### 引擎要压低的是协作成本

每个角色在自己的领域里是专业的。但让研究人员去解决工程问题，很多时候他并不擅长；反过来也一样。所以引擎要解决的核心问题就浮出来了：有没有可能通过引擎，让每个人在自己熟悉的领域里深耕，而不同领域之间的协作，借助引擎和工具变得更方便一些？

这不是说你不可以去别的领域做事。跨领域有个风险：你对那个领域不熟，很可能以为自己挖到了金子，实际上挖的是几块破石头。

所以这一讲的核心，落在 C++ 和蓝图这个概念上。本质就是通过 C++ 跟蓝图的配合，让整个仿真流程更灵活、更好用。这是贯穿全篇的一条线。

### 蓝图是什么，它是怎么长成今天这样

有些人可能对蓝图是什么不太清楚，这里简单讲一下。蓝图是一种可视化的编程界面。如果你以前用过 UE 这类引擎，应该比较熟。它跟 C++ 在某种意义上解决的是同一个问题：都是通过编程的方式去完成某个任务，只不过蓝图是可视化的方式。

这一点很关键：蓝图不是"给不会写程序的人玩的玩具"，它是另一条表达程序逻辑的通道，只是把代码文本换成了图和节点。也正因为是可视化的，它对非计算机专业、非 IT 专业的人会更友好。

#### 从属性面板到节点图

UE 的这套蓝图，不是一开始就长现在这样，它是软件工程不断升级改造、逐步演化过来的。

早期 UE1、UE2 的界面系统，跟传统软件其实比较像：它本质上是一个标签系统——针对某个对象或者某个物体，有一栏属性，有一栏事件。你在面板上改属性、挂事件，就完成了配置。

这种方式最大的问题在哪？很多功能是固化在程序里的，你写程序的时候就得把这些东西事先定制好。后面如果想来点灵活的重组，就比较麻烦。

而很多任务恰恰需要不同的对象、不同的组件相互配合，中间有数据传递、有消息传递。靠一张固定的属性表，这种协作表达不出来，所以这种方式并不太实用。

到了 UE3，开始出现现代蓝图的雏形：先组件化，不同组件之间再通过数据传递、通过图的方式串起来。这时候任务流程就不再是固定的了——你不需要在编程或者研发阶段就把整个流程焊死，等于给后期的应用和设计留出了动态的、可配置的能力。

再到 UE4，就是我们看到的最新蓝图的样子，已经比较方便了。对于一些不太复杂的任务，完全可以不依赖任何 C++ 代码，直接用拖拽式的界面把任务搭建出来。这对非计算机领域的设计人员来说，是很友好的。

不过 UE 这一整套东西本身也相当复杂。你去看它的基础代码，估计没有多少人能把整个代码看一遍，里面包含的东西太多了。

PeriDyno 虽然也需要 C++ 底层，也需要蓝图，但我们不太可能去构造那么复杂的一套蓝图。原因很现实：这样一个庞大的系统，最大的问题是投入——人力和资源投入肯定不会特别稳定。所以我们要解决的是另一个问题：在比较小的维护成本下，把一套类似的系统给大家搭出来。

#### 蓝图到底省掉了什么

有了这套系统之后，蓝图的好处主要在三处。

第一是简化任务流程。原来要用代码一行行描述的流程，现在拖几个节点、连几根线就成型了。

第二是降低研发成本。如果所有任务都依赖编码人员去处理，这是非常吃不消的。对一些比较简单的任务，我们希望通过蓝图把编程人员的压力释放出来。

举个最朴素的例子。我们设计了一个仿真模块，这个模块在不同的参数下有不同的一组计算结果。以往怎么批量跑？

一种办法是写一堆脚本，脚本里读一堆参数，通过脚本运行去批量修改、批量测试。另一种办法是不断去改程序里的那个参数——但 C++ 是编译型语言，每次改完都要重新编译，这个过程的开销比较大。

有了蓝图，这类"改参数、跑一遍、再改参数"的活就不必每次都动 C++ 代码，改节点上的值就行。

第三，也是最重要的一个作用：团队协作。尤其是设计人员和编程人员之间，可以做到无缝衔接。编程人员把底层能力做成节点，设计人员在上层连节点搭流程，两边不用互相等。

### 反射加宏：一套轻量蓝图的两个支点

那么面对这么庞大的一个系统，PeriDyno 是怎么用相对轻量的方式，把这套蓝图构建出来的？

说起来很简单：主要依赖两个东西——反射，和宏。就这两样。

靠这两样东西，从整个框架层面对底层的对象、属性做统一管理。对象怎么造、有哪些属性、属性是什么类型，全都由框架统一收口，界面那边只要查就行。

有了这两个东西，目的也很简单：实现代码运行逻辑和界面运行逻辑的统一。

这话说得有点笼统，得解释一下。代码运行逻辑的功能，肯定远远超过界面运行逻辑——一门通用编程语言能做的事，一套节点图是表达不完的。但我们针对的是仿真任务，仿真任务本身比通用编程更特殊，很多时候它不需要具备通用编程的能力。所以 PeriDyno 是针对仿真这个特定任务做的特定设计，让代码逻辑和界面逻辑看起来差不多一致，而不是追求两者在表达能力上完全对等。

这两个逻辑，换个视角看就更清楚了：

- 代码逻辑，对应的是研发人员、程序员的逻辑；
- 界面逻辑，对应的是用户的逻辑。

我们手上已经有很多仿真算法，后期用的时候，用户可以直接拿这些已有算法去构建各种各样的仿真任务。程序员负责把算法包成节点，用户负责把节点连成场景——两边各自在自己的逻辑里工作，接口在中间对上。这就是"统一"的实际意义，也是后面所有机制服务的目标。

### 一个节点里到底装了什么

#### 从四层架构到 Field

要看懂 C++ 和蓝图是怎么对上的，得先看 PeriDyno 自己的数据结构。第一次课讲过，PeriDyno 有四层架构：

```text
场景图（Scene）
  └─ 节点（Node）        —— 界面上就是节点编辑器里的一个图案
       └─ 模块（Module）
            └─ Field     —— 各种数据
                 ├─ 控制变量
                 ├─ 状态变量
                 ├─ 输入
                 └─ 输出
```

读图：往下是"由什么构成"，顶层是场景，场景里是节点，节点里挂模块，最底层落到 Field 上。Field 按功能分成四类：控制变量、状态变量、输入、输出。整个蓝图对应关系，最后都落在最底下这一层。

拿节点这一层具体看。以创建一个 cube 为例，它在 model 这个库里。创建这么一个对象之后，实际上会生成一个 box。

这个 cube 的控制变量有哪些？

- 边长——box 多大；
- 表面网格类型——想把它剖分成三角网格还是四边形网格；
- 分段数——网格切多细。

除了自己定义的这几个，它还继承了一个父类，叫 parametric model，也就是参数化模型。这个父类里定义了平移、缩放、旋转这些东西。所以你在界面上看到的完整控制变量，是子类自己的加上父类继承下来的一起。

那状态变量又是什么？它是描述这个节点所需要的一个最小状态集合——用来描述这个节点当前是什么样的一组量。

两者的关系是一条单向的链：

```text
控制变量（边长 / 网格类型 / 分段数 / 平移 / 缩放 / 旋转）
        │ 写入并更新
        ▼
状态变量（描述该节点所需的最小状态集合）
        │ 分析
        ▼
节点最终形态 ──► 输出（比如一个标准立方体）
                     ▲
       部分节点的输入 ─┘
```

读图：控制变量是你手上的旋钮，状态变量是节点当前的状态账本，输出是算出来的结果。你调控制变量，它去更新状态变量；再用状态变量一分析，就得到这个节点最终应该是什么样子。

除了状态变量，模型还有一个输出，比如输出一个标准的立方体。有些节点还会有输入——这也是为什么后面的场景里，节点与节点之间能连起来。

#### 界面上的图案与代码里的元素，一一对上

回到界面上。节点对应的就是节点编辑器里的一个图案。这个图案跟 C++ 代码里的各种元素，其实是一一对上的：代码里有哪些控制变量，图案上就有对应的属性；代码里有哪些状态，界面上就有对应的显示。

状态变量在界面右边还有一栏，演示的时候那一栏没显示出来。它会把该节点所有的状态变量都列出来，方便你直接看当前状态。

那么图形界面和 C++ 底层逻辑这两套东西，靠什么统一起来？靠宏定义。这一点先记住，后面讲反射时会看到宏具体是怎么写的。

### 一个场景就是一张有向无环图

一个节点对上容易，换成场景就要复杂一点。

一个场景列表里会包含各种各样的节点，节点之间还有数据传递：上一个节点要把数据传给下一个节点。这些节点和它们之间的连线，构成的是一张有向无环图（DAG）。所有数据流都从前往后流，不会绕回来。

把所有节点组合起来，再把中间的连线算上，对应的就是一个场景。界面右边是图形化的场景图，中间那个视口是它显示出来的效果。

这个场景同样有一份完全一样的 C++ 代码视图。代码量不大，我直接打开代码看。在示例工程那个倒水场景的类里，打开你会发现整个实现不多——因为所有实现并不在 main 函数里，main 只是负责创建这个场景。

#### 倒水场景是怎么搭起来的

这个场景包含哪些要素，我按顺序说一遍。

第一步，创建场景，然后设置重力。这是场景级别的参数。

第二步，创建一个发射器。因为整个效果是流体从上往下流，得先有源头。发射器创建出来之后，要添加到场景里；每个节点同时会有一些属性，比如这个发射器应该放在哪个位置，通过属性去改它的位置。

第三步，发射器后面接一个流体求解器。发射器里创建出来的粒子，要输送到流体求解器里去。这里有一个 `connect` 函数，做的是连接这件事，它的指令跟界面上那根连线一模一样：你在 UI 上从前一个节点连到后一个节点，画出来的那根线，对应的就是代码里的这一次 `connect`。线代表的意思很直白——前一个节点的数据，连入后一个节点。

第四步，流体本身是一个粒子系统，用的正是前面讲过的 SPH 那一套方法。所以要额外加一些辅助模块，把流体渲染出来。

第五步，加边界。后面那几个节点是在创建边界，最后一个节点是流固耦合节点。它要跟表面网格产生耦合作用，所以它需要接入两路东西：一路是流体，另一路是表面网格。

表面网格实际上包含两个：一个是中间那个球的表面网格，还有一个是底下那个平面。这两个东西要先合在一起，再输送到后面的流固耦合节点。

所以后面这一段做的事，说白了就是创建边界：一个平面加一个球，合起来送进流固耦合节点。

```text
发射器 ──粒子──► 流体求解器 ──┬──► 渲染辅助模块（把流体画出来）
                              │
                              └──► 流固耦合节点
                                        ▲
        球表面网格 ──┐                  │
                     ├── 合并 ─────────┘
        平面       ──┘
```

读图：箭头就是 `connect` 建立的数据通道，在界面上表现为一根连线。耦合节点有两路输入——一路来自流体求解器，一路来自合并后的边界表面网格；渲染模块只是挂在流体后面做可视化，不参与耦合计算。

#### 跑起来是什么样

代码讲完，直接跑一遍。

点开始之后，流体从上面的圆形发射器流出来，正好沿着球的那个固壁往下流，最后落到下面的平面上。左边视口里就是可视化之后的效果。

### 反射：让 C++ 在运行时认识自己

前面讲的都是静态视图：场景、节点对应的 C++ 代码跟蓝图到底怎么对上。代码层面的指令跟 UI 层面看到的图案，存在一一对应关系，这个对应关系主要靠反射和一些宏定义实现。接下来就把反射这件事拆开讲。

先给一个概念上的定义。

> **定义**：反射，是程序在运行时检测、查询、修改自身状态的一种能力。

通俗点说：程序跑起来之后，能知道自己有哪些类型、每个类型里有哪些成员、每个成员是什么类型，还能根据一个名字把对象造出来、把值改掉。这套能力在 C++ 里不是白给的，得自己搭。

#### 为什么一个普通的 C++ 类不够用

看一个标准的 C++ 类。这是我们之前定义过的一个基本几何图元——比如一个平面。这个平面主要包含两个数据：一个原点，一个法向。

但如果你只是这么定义一个简单的类，对整个框架来说，它其实是不知道的：它并不知道你这里面有几个数据，也不知道这些数据叫什么、是什么类型。

那按平时的写法，要用这个数据结构怎么办？写 C++ 的人都知道：你必须把它对应的头文件 include 到要用到它的地方。编译器看到了头文件，才知道这个类型长什么样。

问题就出在"必须 include"这件事上。现代软件的功能越来越多，尤其做开源的时候，你很难控制第三方。第三方开发者写了一个类，如果他不告诉你，你根本不知道他写的这个类到底长什么样。你这边没有他的头文件，编译期就一无所知。

而界面那边恰恰需要这个信息。你在 UI 里点一个对象，会弹出属性框；这些属性框要能识别出对象有哪些属性，才能把输入框摆出来。单纯这么定义一个类，肯定做不到。

所以框架必须具备几种能力：

- 知道一个新写的类到底是什么类型；
- 知道这个类里到底包含了哪些变量和方法；
- 支持动态创建对象。

第三条最要命。C++ 里一般用 `new` 来创建对象，但它是编译型语言：你只给它一个类的名称（一个字符串），它是没法创建一个对象的。名字在运行时只是数据，编译器早就不在场了。

这三件事，只有反射能兜住。反射一旦到位，界面上的效果就很自然：

- 要创建一个 cube，只要输入 `cube` 这个字符串，就能把 cube 对应的对象创建出来，加入到节点编辑器里；
- cube 上有边长、分段数、缩放、平移、旋转这些属性，反射能识别到它们，界面就能为这个类生成一个可调节的编辑器；
- 你在这个编辑器里改值，改的就是对象自身的状态。

所以反射不是炫技，它是"界面能操作底层对象"这件事的前提。

#### Object 与那张全局类表

PeriDyno 里所有依赖反射的类，都会继承一个公共的父类，叫 `Object`。

为什么非要有个公共父类？因为 C++ 本身是编译型语言，并不支持反射这个特性。用 Java 会方便很多：Java 是解释型的，运行的时候成员变量、函数都可以动态获取到。C++ 没这个条件，得依赖自己的实现。既然语言不给，就得找一个所有类都能挂上去的地方——那就是一个统一的父类。

所以现在整个系统虽然包含非常多的类，但它们都继承自这个公共父类 `Object`。反射机制就实现在 `Object` 里面。

这样做的好处是责任分得很干净：后面不管你派生出什么类，都不用管反射机制怎么实现，只需要按一定的规则——依赖模板编程的一些特性，加上一些宏定义——把"我这个新类包含哪些信息"告诉父类，剩下的注册、查询都由父类完成。

`Object` 最核心的地方，是它维护了一张 `ClassInfoMap`。

> **定义**：`ClassInfoMap` 是一张从类名到 `ClassInfo` 的映射表，本质是一个 map 结构。每个 `ClassInfo` 里存着这个类的信息，包括它的构造函数。

流程是这样的：你现在新写了一个类，就要调用一次注册函数；注册函数一执行，这张类表里就新增一个对象。于是系统里所有的类，都会统一存在 `Object` 的这个静态结构里。这个结构是全局的。

有了这张全局表，任何地方想创建一个对象，都可以直接查这张表：拿类名找到对应的 `ClassInfo`，从中取出构造函数，把子类构造出来。所以"创建一个对象"这件事，本质上调用的是子类的构造函数，只是这一次调用是由字符串驱动、在运行时发生的。

```text
        程序启动（进入 main 之前）
                  │
                  │ 各子类的静态注册对象依次初始化
                  ▼
        ┌────────────────────────────┐
        │ Object::ClassInfoMap        │  全局静态
        │   "Cube"  ──► ClassInfo     │
        │   "Plane" ──► ClassInfo     │
        │    ...                      │
        └──────────────┬─────────────┘
                       │ 运行时按类名字符串查找
                       ▼
              ClassInfo 里存着构造函数
                       │
                       ▼
              创建出对应的子类对象
```

读图：注册发生在 main 之前，运行期只剩下查表和构造两件事，所以界面那边拿到一个类名字符串，就能把对象造出来。

这张表还有别的讲究。后面你会看到一些原子操作，那是为了解决多线程环境下的异常问题——类表是全局的，多个线程同时读写，就得有保护。

#### 两个宏：声明与实现

`Object` 那边把机制做好了，子类这边要做的，就是"报户口"。报户口靠宏定义，主要是两个：一个声明，一个实现。

声明宏放在头文件里，做的事情是定义一个类信息的静态变量；这个静态变量需要注册到 `Object` 这个父类里。

实现宏（`implement_class` 这一类）做的事情，是创建一个 `ClassInfo` 对象。这个对象创建时传入两样东西：

- 一个是类的名称，也就是 `name`，代表这个类叫什么；
- 另一个是这个类对应的构造函数。

有了这两样，`Object` 就能通过类名的字符串找到构造函数，进而调用子类提供的构造函数，创建出对应的子类对象。

所以对于所有要支持反射的类，头文件里必须 include 这两个宏：一个声明、一个实现。少一个，这个类在类表里就不完整。

这套东西为什么能成立？靠的是 C++ 一个比较特殊的性质：所有的静态变量，都会在进入 `main` 函数之前初始化完。

这一点很关键。你在头文件里定义了那个静态变量，它实际上会在执行代码之前，就去找 `Object` 父类报到，由父类完成注册。等真正运行起来的时候，整个类表已经完整地构造好了，代码里直接就能用。不需要谁在启动时手动遍历一遍、也不用担心"我用到它的时候还没注册"。

> **易错点**：注册是静态变量初始化阶段完成的，不是运行到某一行代码才做的。所以宏必须放在头文件里，而不是随便写进某个函数的实现里——位置不对，注册时机就错了。

有了这一步，`Object` 加两个宏，就把"类"这一层的反射闭合了。

#### 成员变量也要被看见

类注册完了，还有成员变量。

为什么成员变量也要反射？因为控制变量需要 UI 去调整它的属性。UI 得知道这个成员叫什么、是什么类型，才能给你摆一个合适的输入框。所以所有需要暴露给界面的成员变量，也要走反射。

成员变量这一层，靠的是一个叫 `FieldBase` 的父类来完成。它的思想和注册类是一样的：成员变量把自己的信息告诉 `FieldBase`，由它完成注册。

注册一个控制变量，要输入几样东西：

- 类的名称——这个成员属于哪个类；
- 成员变量叫什么；
- 类型——针对特定模块，要说明这个成员是控制变量、参数，还是输入，还是输出；
- `this`——实际上传的是一个 node 的指针；这个指针传进去之后，可以针对整个 node 做一些额外的操作。

所以你需要反射的成员变量，也都是依赖这样的宏定义来完成的。这就是为什么你在 PeriDyno 里会看到好多类似的宏——它们的作用，就是让底层的父类能识别出这个子类到底有哪些成员变量。

> **注意**：这些东西不是定义得越多越好。只需要暴露必须的那些成员变量。有些成员变量只是内部使用，就不需要暴露出来；UI 也不需要去控制所有变量，它只需要控制你对外开放的那些变量。

这里还有一个设计上的细节值得说。这些宏定义的对象也是放在头文件里的，好处是它的构造函数初始化优先级比类内的构造函数更高：所有变量对象在进入构造函数之前，就已经全部创建出来了。

这个顺序带来一个便利：参数会有一个默认值；某个特定的类如果想要改默认值，不需要去动宏，直接在构造函数里把那个值改掉就行。默认值统一给，个别类单独覆盖，两层互不干扰。

到这里，静态视图的两块拼图就齐了：类靠 `Object` 和两个宏注册进类表，成员变量靠 `FieldBase` 和一组宏注册进字段表。界面上的每一个图案、每一个属性框，背后都能在代码里找到对应的注册记录。

### 时间轴上的三个函数与一次回调

前面讲的全是静态视图：一个场景、一个节点，对应的 C++ 代码跟蓝图应该怎么对上。

但仿真还有一个非常重要的维度——时间。

仿真跟 CAD 软件最大的区别在哪？它是一个时间序列。点播放之后，场景里所有元素会动起来。所以除了场景的连接关系、各种参数、各种属性之外，还有两样东西：动态的数据传递（数据流的过程），以及计算模块的执行顺序。界面上看到的运行逻辑，也要跟 C++ 的执行逻辑对上。

#### 播放与重置

界面上有两个按钮：一个是三角形的播放，从头开始，一个时间步一个时间步往前运动；另一个是重置。

重置是什么概念？就是把所有状态变量恢复到它的初始状态。

这个按钮不是摆设。比如场景跑起来之后，你发现出水口的位置不太好，想调一下；调完位置，你得点一下重置——所有节点里的数据恢复到初始状态，然后整个仿真流程重新开始。如果不重置，上一轮算到一半的粒子状态还在，接着往下跑，你看到的就不是新参数下的完整过程。

```text
初始状态 ──播放──► t0 ──► t1 ──► t2 ──► ... ──► tn
   ▲                                              │
   └────────── 重置：所有状态变量回到初始 ──────────┘
```

读图：播放是沿着时间轴一格一格往前走，重置是把时钟拨回原点、所有状态清零，两者配合才能反复试参数。

所以节点里最重要的两个机制就是：重置，和更新。点了播放之后，每个 time step 都会逐步去执行节点里的一些函数。

这里有三个比较重要的函数，它们跟重置一样，都是虚函数：

- `update_states`——每个时间步更新状态；
- `pre_update_states`——更新之前做的处理；
- `post_update_states`——更新之后做的处理。

实现子类的时候，要重载这几个函数，用它们去完成你自己定义的那些状态的更新。

#### 为什么是三个而不是一个

正常来说，只需要一个 `update_states` 就够了。那为什么设计成三个？

主要是为了照顾耦合的场景。耦合场景里，除了仿真流程本身的计算，还有一些数据预处理（以及相应的后处理）。这些预处理很多时候没法给它标准化、流程化——它跟具体的耦合方式绑在一起，每个耦合节点干的事都不一样。这种东西硬塞进标准的更新流程里不合适，就放到 `pre_update_states` 和 `post_update_states` 这两个函数里。

后面演示的流固耦合场景里那个节点，就是按这个模式来操作的：流体和表面网格的数据要先经过它自己的处理，再进入更新，最后再做收尾。

这两个额外的函数有个特点：无论重置还是更新，代价相对都比较大。因为它会去调用各种模块，所有状态都会重新更新一遍。

可有时候我们只想更新局部内容，并不需要点一下重置、把所有数据全改一遍。针对这种需求，PeriDyno 里有一个回调函数的机制，用来做轻量级的、针对个别数据的更新。

#### 回调：只在事件发生的那一刻响

回调是什么概念？看这张图。

```text
注册方                              主程序（持续循环）
  │                                      │
  │  把要执行的操作封装成对象            │
  │  把函数指针存进主程序                │
  └─────────────────────────────────────►│
                                         │ 循环中不做轮询判断
                                         │
        某个特定事件被触发 ──────────────►│
                                         │ 直接调用回调函数
                                         ▼
                                      执行指定操作
```

读图：主程序一直在跑，回调函数的指针事先存在它手里；事件不发生时它什么都不用做，事件一发生就直接调到那段代码。

具体做法是：把一个需要执行的操作函数作为对象，把它的指针存到主程序里头。主程序触发某个事件之后，直接调用这个回调函数，完成特定的功能。

这么做的好处有两个。

第一个是省开销。渲染也好、仿真也好，整个程序一直处在一个不断循环的状态。如果是别的机制，主程序处理的时候要不断去判断"你是不是需要处理这个事件"——每一轮循环都问一遍，就会产生大量冗余开销。回调不一样，它只在触发那一瞬间调用函数，尽可能节约了计算资源。

第二个是解耦。它可以把调用者和被调用者分离开，让被调用者去自定义处理它想处理的行为。主程序不需要知道那段代码具体干什么，它只知道"这件事发生的时候，叫一下这个函数"。

最典型的例子就是游戏设计里的子弹。

把这一路串起来看：反射让类名变成可以创建的对象，宏让成员变量变成界面上的属性框，`connect` 让节点连成场景，三个虚函数让场景在时间轴上动起来，回调则让"只在需要的时候做一点局部的事"成为可能。C++ 写底层、蓝图搭流程，靠的就是这几层机制咬在一起。

## 从回调到插件：PeriDyno 的功能拓展方式
> 对应块：BLK14 | 覆盖分集：P07下 | 块标题（分集名）：《7. PeriDyno插件与功能拓展》

### 偶发事件，以及 field 里那张回调列表

粒子撞上障碍物、布料碰到边界——这类事件在整场仿真里其实非常偶然，它并不是一个每帧都在触发的东西。正因为偶发，它特别适合用回调函数来完成：平时什么都不用做，等它真的发生了，再交给回调去处理。

PeriDyno 里的回调机制，出发点是这样一件事：一个节点里往往会挂很多个控制变量，某个控制变量一旦变了，节点内部的一份数据就要跟着更新。所以每个 field 里都存了一张回调函数列表。你需要它对某个变化做出特定反应，就创建一个回调函数，塞进那个 field 的回调列表里。触发时机主要有两种：数据被改动之后，或者它连接的拓扑关系变了之后。这两类变化一来，后面的回调函数就被逐个调起来，去执行用户想要的行为。

```text
 [事件]  数据被改动 / 连接关系变化
    |
    v
 [Field]  当前值 + 回调函数列表
    |
    v
 依次调用回调
    |
    v
 更新节点内部的派生数据
```

读图说明：回调不改 field 里的那个值，它改的是值背后的东西——节点内部那份由这个值派生出来的数据。

> **定义**：field 是节点上的一个控制变量槽，既装值，也装"值变了该通知谁"。回调列表就挂在它身上，所以任何一次写入或者重新连接都能把回调唤醒。

### 两种写回调的方式

回调主要分两种，一种用成员函数来写，一种用 lambda 来写。

**成员函数回调**，典型例子就是 cube。cube 上有缩放、旋转、平移这些信息，它们一变，内部的表面网格、立方体自己的一堆信息就得重新算一遍。做法是用 `std::bind` 把这个成员函数和节点指针绑在一起，生成一个回调函数，再通过 `attach` 把它挂到每一个你需要它响应的控制变量上。

这里有个必须判断清楚的点：回调到底该挂到哪个 field 上？答案取决于这个函数需要哪些参数。像 cube 那个函数，五个参数它全都要，那就得把这一个回调函数同时塞进五个 field 里；之后这五个里任意一个发生变化，函数都会被调起来，把内部状态重新更新一遍。

**lambda 回调**更灵活一些。典型场景是静态版网格加载：打开一个文件，把文件里的东西载进来。这里写的是一个 lambda：方括号里放个等号 `[=]`，意思是外层现有的值都可以捕获进来；然后把这个 lambda 作为参数传给回调，里面就能直接引用这个类里的各种对象。它实际干的事是拿到一个几何拓扑对象，把文件载进去，再对这个对象做初始化。

> **提示**：这两种写法解决的是同一件事——把"值变了之后要干什么"从节点主逻辑里摘出来，挂到 field 上。区别只在于：成员函数回调要绑定一个节点指针，天然能访问该节点的内部状态；lambda 用捕获列表把需要的东西带进来，写起来更自由，适合一次性的局部操作。

### 回调到底能拿来干什么

两种类型的回调都摆出来了，接下来得回答一个问题：这东西到底能用来干嘛。我举三个实例，都是能直接在界面上跑起来的。

#### 连上了，就把上游的显示关掉

第一个实例是控制可见性。我先打开集成了各个库功能的那个 GUI 插件程序，里面的东西相对多一点。

先在里面创建一个基本的球体，参数可以随手调一下。这个球体可以转成一个体距离场（SDF）。每个节点里其实都带了一个可视化的模块。如果我直接把前面的球连到后面：后面那个节点现在需要输入一张三角网格，球的数据正好能传进去，作为输入把距离场构建出来；后面那个节点本身也带渲染，它会把距离场重新抽成一张表面网格显示出来。

问题就来了：前面那个节点一直处在显示状态，后面那个节点也画出来了，两个东西叠在一起互相遮挡。

我们希望的是——前面连到后面之后，上游那个节点的可视化就消失，只显示下游。针对这个需求，就得在 volume 库下那个 volume generator 类里写一个回调函数。它监听的是"有没有三角面片输进来"：一旦前面有三角面片输入，就顺着这个 field 找到挂在它上面的那个节点，把它的渲染模块关掉。整个回调干的就这一件事，输入一个三角面片，然后把对应节点的显示关闭。

连上之后确实就是前面那个直接隐藏了。再去调后面那个参数、必要时重置一下，场景里剩下的就只有后面那个节点从距离场重构出来的表面网格，初始那张网格已经不显示了。

这种用法当然不限于可见性，同样的位置挂别的事情也一样成立。

#### 把核函数的归一化收到一处

第二个实例来自 SPH。算 SPH 里某个点的物理量，本质是权重求和——每个粒子带一个值，乘上权重函数再加起来，而这里有一个硬性限制：整个权重加起来必须等于一。

满足这个条件有简单粗暴的办法：每次计算的时候，就地重新归一化一遍。这个办法能用，但麻烦在于权重函数在很多代码里都会实现，各处的实现未必一致，对不上就会出问题。那能不能在某一个地方统一做一次归一化，后面用的时候直接拿这个统一归一化之后的结果？可以，还是靠回调。

粒子系统里负责权重求和的那一层——核近似这一块对应的类——就承担这件事。归一化要算一个缩放因子，它由三个参数决定：核函数的作用范围、采样间距，以及核函数的类型。核函数本身五花八门、类型很多，所以类型也必须作为一个参数传进来，不能写死。

这三个参数任意一个变了，缩放因子就得重算。做法就是把同一个成员函数分别 `attach` 到这三个 field 上，谁的值变了就自动调用它，把缩放因子重新算出来，完成对权重函数的归一化。

> **结论**：归一化只写一次、只存在一处，所有调用方拿到的都是同一份结果。这是回调在"数据一致性"上的用法，和前面关显示的用法完全不同，但机制是一个机制。

#### 让 Qt 的属性面板跟上底层数据

第三个实例是界面联动。你选中一个物体或者一个节点，它身上会挂一个坐标架，就是那三个箭头。拖动这个坐标架，你会发现后面属性页里的位置、旋转、缩放全都跟着变——左边怎么拖，右边就怎么跟着动。

界面上看起来只有两部分：左边一栏属性、右边一个三维视图。但实现这件事其实依赖三样东西。

第一样是坐标架本身。它移动之后，需要去设置对应 field 的值——整个物体动了，位置、旋转、缩放这一串值就都得更新。

第二样是这些 field 的值更新之后，怎么让界面知道。整个界面是在 Qt 里实现的，Qt 那边必须能收到"数据变了"这件事，并且知道该怎么刷新自己的属性控件。

第三样是 Qt 侧的属性控件传下去的那个回调。Qt 的 GUI 模块里有很多属性标签，三维向量、整型、浮点型这些都有。点开一个三维向量的属性框，它自己带一个回调函数；这个回调是在 Qt 的界面框架里建好的，然后被传给它所对应的 field。于是 field 一旦发生变化，就会去调用这个由 Qt 传下来的回调。

```text
 拖动坐标架（三个箭头）
        |  写入新值
        v
 Field：位置 / 旋转 / 缩放
        |  值变化 -> 触发回调
        v
 Qt 侧传入的回调  ->  刷新属性面板（int / float / 三维向量组件）
```

读图说明：数据单向流，从三维视图里的操作流向 UI 控件；真正把两端接起来的是 field 上那张回调列表。

Qt 和底层框架确实是两套系统，但依然可以在界面层面完成对接：把跟 Qt 相关的那些功能和函数传到底层框架里，由底层框架来触发回调。这样就能用左边各种控件去做比较方便的交互操作，而不必在三维视图里手拖。

### 为什么要做成插件

回调解决的是节点内部的联动，接下来换个层面：一整个引擎要加新功能，怎么加才不至于把代码搅成一团。答案是插件。

对 C++ 来说，插件这东西拆开看主要就两样：一个整个的框架，加一堆 dll。直观地看非常简单。它要解决的问题也很朴素——把一个复杂的系统拆开，拆成一些基本的、类似积木块的东西，然后用这些积木块再拼起来，重新构建出一个复杂的系统。

为什么非拆不可？因为代码量上去之后——我们这套系统现在的代码量其实已经不少了——如果你每改一处都要在整个系统里重新编译一遍，这个开发成本是相当大的。拆成插件，等于把代码的耦合度降了下来，顺带还有一个现实好处：它比较适合协同开发。不同研发人员各做一部分，最后整合到整个应用框架里，一起去完成复杂的任务。

PeriDyno 的插件系统跟别的插件系统差不太多，也是两部分：框架层面和 plugin 对象。

框架层面在 framework 里，有一个插件管理器，它负责管理里面的每一个 plugin，对应的是一张 plugin 列表。开发者这一侧，则是从 plugin 提供的 entry 基类继承下来，去开发各种不同的插件——针对刚体动力学的、针对粒子系统的、针对 SDF 的，等等。

```text
 Framework
   |
   +-- PluginManager
   |     |
   |     +-- PluginList: [ plugin A ][ plugin B ][ plugin C ] ...
   |
   +-- Plugin（对象层）
         |
         +-- Entry（基类，插件入口）
               |
               +-- 刚体动力学插件
               +-- 粒子系统插件
               +-- SDF / Volume 插件
               +-- 别的自研插件
```

读图说明：管理器只管"有哪些插件"，插件自己负责"提供哪些节点和功能"；两边唯一的契约就是 entry 这个基类。

### 七个原则，落到具体代码上

插件本身就是降低耦合的手段，说到耦合，就绕不开设计模式里的那几条原则。这里我简单提一下。

先说清楚适用对象：如果你只是这套代码的使用者，怎么写其实都无所谓，自己看着舒服就行；但如果你希望成为一名开源软件的贡献者，那你的代码就需要符合一定的约束。这一点是我最近调代码的时候正好撞见一些问题，索性就着这些实际情况说一遍。

一共是七个原则：单一职责、开闭、迪米特法则、接口隔离、依赖倒转、里氏替换、合成复用。抽象地看这七条，你大概不知道它在讲什么——"单一性原则""开闭原则"这些词本身就很抽象。所以下面我不按定义讲，结合具体碰到的情况，一个一个说它到底指什么。

#### 一个类只干一件事

单一职责的意思很直白：一个类只负责一项职责，目的就是把这个类的复杂度压下去。

反例就在刚才演示的那个类里——输入一张三角网格、创建出体（SDF）的那个类。你现在去看它，会发现它多了一个额外的控制变量。一个类需要哪些控制变量，这件事本来就该尽可能少，不需要的就要摘出去。那这个多出来的控制变量是干什么的？是之前测试的时候为了方便加进去的：希望整个 SDF 能动起来，在内部让它沿着某个速度、某个方向不停地运动。

这么设计其实谈不上错，但它跟这个类的初衷相违背。这个类的初衷只有一件事：输入一个三角网格，输出它的有向距离场。让它自己动起来，属于另一件事。

> **易错点**：功能"能跑"和职责"干净"是两回事。测试用的便利代码一旦留在生产类里，后面每个读这个类的人都要多想一层"它为什么自己会动"。

更合理的做法是把这部分移到外面：既然前面输入的是三角网格，那就在外部去驱动这张三角网格运动；网格动完之后，再在后面去更新它新生成的那个 SDF。这样每一段都只干自己的事。

#### 对扩展开放，对修改关闭

开闭原则更抽象，字面意思是"对扩展开放，对修改关闭"。说得直观一点：一个类暴露出来的东西是有区分的——如果你是它的实现人员，那它本来就该允许你去改；但如果你只是别的类、拿它当使用者，那它的内部细节就不该暴露到你面前。

还是拿刚才那个类举例。它里面有一个函数，作用是初始化它内部自己用的一些参数。这个函数你设成 public 也好、设成私有也好，从语法上都成立，但按这条原则，设成 public 就有问题。原因很实在：这个函数对使用者来说，他根本不清楚这东西是干什么用的，也没有理由去调它。理论上就不应该允许外面的类直接调这个函数，因为它是类内部使用的东西。

所以凡是只在类内部使用的数据、函数，就该封装起来，不暴露到外面。对外看，这类函数是关闭的——这就是"对修改关闭"的那半边。

#### 知道得越少越好

迪米特法则和接口隔离，讲的是同一个概念：一个对象对别的对象应该保持最少的了解，也不应该依赖自己用不到的接口。

落到 PeriDyno 里，最典型的一条是：node 对 state 的依赖要尽可能少。一个 node 里可以定义很多不同的量，其中有些是允许用冗余的方式去描述的。比如描述一个立方体，你完全可以定义三条边，也完全可以定义边跟边的乘积——随你怎么定义，都能描述这个立方体。但最好的状态是：你的状态恰好是描述这个 box 的最小集合，那些冗余的变量根本不该出现在里头。

同样的道理也体现在 model 模块上：它对控制变量的依赖、对输入接口的依赖，都要按这个尺度收。

输入接口这件事尤其重要。如果接口有冗余，就会出现有些模块明明用不到某个接口，却还是得带着它；反过来，如果缺了接口，后面整个模块可能直接就没法执行。所以无论是节点还是模块，设计输入接口和输出接口都要非常小心。变化的容忍度也不一样：输出改了相对还好，输入一般来说不能轻易动。

> **注意**：接口是别人依赖你的那部分契约。删掉一个用不到的接口，是清理；改掉一个别人正在用的输入接口，是破坏。

#### 依赖抽象，子类要能顶替

依赖倒转和里氏替换在实践里也是同一个概念：高层模块不应该依赖底层的具体模块。

先看 PeriDyno 的底层拓扑，它是层次化的结构：

```text
 点
  +-- 边
       +-- 三角面片
            +-- 四边形网格
            +-- 四面体网格
```

读图说明：越往下越具体，上层是下层的父类。三角面片一旦作为某个模块的输入类型，那么它下面的四边形网格、六面体网格、四面体网格，只要确实是从三角面片继承下来的，理论上都应该能输入进去。界面里现在也是这么设计的，允许。

这就是里氏替换：你输入的是子类对象，结果也必须正确，跟输入父类对象完全一致、互不影响。

现在的程序里有一层接口判断：所有子类都放行，不是子类、或者是别的类型，就不允许输入。演示里能直接看到这个区别——cube 可以输出两种网格，三角网格和四边形网格，三角网格当然能传进去，四边形网格同样被允许。换成粒子采样器，它输出的是一堆粒子，而粒子比三角网格更靠上、是三角网格的父类，这种就理应不允许。

> **易错点**：方向别弄反。子类对象可以当父类用，反过来不行。把父类对象塞进要求子类的输入口，就是在赌它的额外信息存在——而它并不存在。

#### 能组合就别继承

最后一条是合成复用。这条相对模糊一些，因为实际代码里很多时候边界没那么明确。

它的核心意思就一句：能复用的地方，尽可能不要用继承。

例子在刚体系统里：查找邻域的那一块，本质是做碰撞检测用的，它依赖两个东西——一个是拓扑结构，一个是碰撞检测的类。你完全可以让这个类同时从这两个类继承下来，作为它们的子类去实现，理论上没问题。但这样一来就出现了多重继承，一个类继承多个父类，整个软件系统维护起来的代价会非常大。

所以结论是：需要用到别的模块的时候，如果能用组合的方式，就尽量用组合，不要用派生、继承那套操作。

> **提示**：继承表达的是"是一种"，组合表达的是"有一个"。邻域查找"有一个"拓扑结构、用一套碰撞检测逻辑，它并不是拓扑结构的一种，所以这里本来就该是组合。

另外还有一点值得注意：写继承的时候要尽量减少多继承的场景。一个子类同时继承多个父类，越往下派生，这个子类就越复杂、越不容易维护——这是实际做研发时经常会踩到的地方。

### 一个插件的骨架

原则说完了，回来看插件到底怎么实现。用起来其实挺简单：每一个 plugin 都提供两个接口，一个对应静态库加载，一个对应动态库加载。

各家的算法都写得差不多之后，要做的事情就是给插件做初始化。这个过程也不复杂：从插件入口的 entry 类继承一个子类，在里面实现一个静态的 `instance` 函数——它负责创建出一个静态的插件对象，就这些。

如果这个插件还带 UI，事情多一步：每个插件实际上会对应一套工具架，如果你有自己的自定义工具架，就需要重载那个初始化工具架的函数（名字类似 `initialize…Action`），在里面实现你要的按钮。

每个库的目录里都会有一个 `initialize` 开头的头文件，点开看，本质就是初始化这个插件的那一个类，加上两个 API 接口：`instance` 函数，和初始化工具架的函数。插件能带什么，全在这一个头文件里交代清楚了。

自定义工具架长什么样？比如粒子系统这个插件，上面就加了几个快捷按钮。代码里对应的是：每一个按钮挂一个 lambda，作用是创建一个对象。所以点一下按钮，本质和你在节点编辑器里右键创建一个对象是一回事。

那为什么要把这个动作固化成按钮？因为固化下来可以顺手做额外的操作。比如创建发射器，发射器创建出来是有一个外轮廓的，你可以把外轮廓用边框渲染的模块显示出来——右键创建是做不到这一层的。

插件一旦加载进来，它对应的工具架里的那些按钮就会自动被创建出来，不需要你手动摆。

至于加载的时机：静态加载是在 `main` 函数里显式调用一下它的初始化函数，把插件加载进来；动态加载走的是另一条路，把库拷进插件目录就行，这一点后面单独演示。

### 让界面更好用：标题栏、变量名与端口形状

插件里还挂着一批纯界面层面的功能。它们的定位很清楚：等算法都研发得差不多了，剩下的就是让整个流程更好用，这些扩展就是干这个的。

**标题栏**。有些基本数据类型，你根本不需要给它显示标题栏，那就重载每个节点或者每个模块的 `captionVisible` 函数，由它来控制标题栏的显示和隐藏。

**变量显示名**。现在整个节点系统里，不管是节点还是模块，里边的每一项都预留了自定义的空间。默认的变量名跟你在代码里定义的名字是一致的，这么定的好处是清晰——界面里看到一个变量，你能直接在代码里找到它。但到了最终应用阶段，这个名字就不直观了。所以每个变量的名称都可以改，用 `setSlotName` 完成，比如把标量、矢量改成中文显示。不只是变量名，标题栏、描述信息、节点类型，这些统统可以定制。

**端口形状**。节点主要分两类造型：一种是这种小圆点，一种是钻石型。小圆点对应的是基本数据类型——控制变量、一维数组、二维数组这些；钻石型对应的则是一个节点。

为什么专门设计出钻石型？因为做耦合的时候，一个对象依赖的数据会非常多。比如这里要接入一个粒子系统，它需要连位置信息、速度信息，甚至密度等等，全都要连。真按这样一根根连，整个界面会非常混乱。

```text
 圆点端口        钻石端口
   o               <>
   |               |
 标量/数组       整个节点（含其全部状态）
```

读图说明：钻石端口把一整个节点当成一个对象来传，图上只出现一根连线，节点内部的那些状态变量就不再摊开画了。

所以如果后面那个节点要用到一个主体里的很多状态变量，只需要把整个节点作为一个整体传进去，就算完成接入——图面干净，语义也清楚。

### 用 SDF 捏一个实体，再让流体贴着它走

前面讲的插件系统，最后要落到"能把不同的模块串到一起"这件事上。下面演示三块：实体建模——用 SDF 去生成各种自定义的几何图案；流体；布料。后两块都依赖今天讲的这套插件机制。

整条链路是这样：

```text
 cube + sphere
        |
        v  布尔运算（并）
 融合后的表面网格
        |
        v  体网格生成器
 实体（SDF）
        |
        v  作为边界输入
 流体边界节点  <--  流体  <--  流体求解器  <--  粒子  <--  发射器
        |
        v
 求解推进：流体沿融合后的实体表面受约束
```

读图说明：上半段是建模，产出的是一个实体；下半段是仿真，把实体当作边界吃进去。换成布料场景时，动的只是下半段。

#### 建模：一个 cube 加一个球

打开 GUI 插件那个示例程序，先切到 volume 选项卡。

第一步创建两个标准几何体：一个标准的 cube，一个标准的球。球要调小一点，再往后就变成"一个方块上鼓出一个球"的形状。这两个基本几何体是用来做基于实体的融合操作的。

接着要把表面网格转成体网格：这里用一个体网格生成器，它的输入就是三角网格。体网格的分辨率得改一下，不改的话，分辨率太大，创建出来的质量不太好。

两个体网格都生成之后（这时候流程还没走完，所以画面上暂时什么都没有，索性先把整个流程建完），接下来把它们融合到一起：后面接一个布尔操作节点，这个节点可以针对实体模型做相交、相并、相差等等操作，选项卡里能选。

接上之后再点一下重置，把前面那两个的显示关掉，就能看到球和 box 融合之后的形状了。有了这个形状，接下来就可以跟仿真对接。

#### 流体：发射器、求解器与边界

跟仿真对接，第一步是建几个仿真的基本要素。流体这边需要一个发射器，发射器后面接一个流体求解器，把发射器创建出来的粒子输入到求解器里头。

发射器的位置要调一下：它现在在实体内部，得把它挪到外面去。这样才是从外面发射粒子，让粒子跟物体的边界产生作用。

然后切回 volume 选项卡，那里有一个流体边界节点。它吃两样东西：一个是流体，一个是刚才创建出来的那个实体模型。接上，整个场景就搭完了。

点一下这里的绿色箭头开始运行。你会看到流体撞到边界之后被边界约束住，运动方向随之改变；又因为形状是融合之后的那个形状，流体会沿着这个形状的表面走。

> **提示**：边界节点要的只是"一个流体 + 一个实体"这两类输入，实体具体是 cube 融球还是别的形状，由上游节点决定，边界这一层不需要知道。

#### 布料：同一个实体，换一套求解

换成布料场景，实体模型可以完全不动，只需要把仿真那一块剃掉——把流体相关的节点删了就行。

然后重新搭：想要模拟一块布，同样要先有一个布料求解器，它也需要输入一张三角网格。所以这里创建一个平面，调它的分段数。默认的平面其实只有两个三角面片，分段数调上去之后，平面上就有一系列四边形；这层四边形结构最终会转成三角形，而且它本身就是三角面片的子类，所以可以直接作为输入喂给布料求解器，完成初始化。

布料的数据起来之后，还要把它输入到流体边界节点里的三角网格系统里。这一步的作用是在运动过程中约束这块布料的行为。

把初始的那个物体关掉，再重置一下，布料的数据结构就生成出来了——顶点和边都能看到。这时候场景已经重置完，点开始，布料碰到障碍物就会发生形变。

> **提示**：流体和布料用的是同一个边界节点，只是喂进去的东西不同：流体吃"流体 + 实体"，布料吃"三角网格"。同一个节点复用两次，靠的就是输入类型够宽——只要类型对得上，具体是哪种网格它都接。

### 空工程加一个动态库

前面演示用的都是集成程序，所有库都编在一起，东西自然多。既然这一讲的重点是插件扩展，动态加载还得单独看一眼。

场景是这样的：很多时候你在外面把各种模块开发完，最后需要以插件的形式把它们载进来。这里有一个空工程，专门用来测试动态加载插件——它里边基本不进行任何操作，也几乎不加载任何跟仿真相关的算法。直接打开它是空的：渲染部分因为默认有一些东西，所以还在；但仿真的那些选项卡，一个都没有。

做法很简单：把已经编好的动态库——还是那个粒子系统——拷到插件目录里。再跑起来，粒子系统相关的功能就已经加载进 GUI 了，选项卡跟刚才那个集成界面是类似的。点选项卡里的按钮就能创建对象、搭出类似的场景。

因为这里没有加载建模，也没加载别的，就单纯演示流体：创建一个发射器，输入给流体求解器，把位置调一下，点开始，粒子就从发射器里生成出来了。

> **结论**：你自己自研的库或者算法，也是通过同样的形式导进框架的，导进来之后就能跟别的算法模块和插件配合，拼出更复杂的场景。框架不需要认识你的算法，它只认插件接口。

课讲到这里，剩下的是一道不检查的小作业，有兴趣的话可以做一下：你现在已经实现了某个 UI、某条流程，那就试试把自己的算法模块化，接到这条流程里，看看怎么让它变得更好用一些。

### 答疑：要不要自研引擎，游戏引擎差在哪

课讲完，剩下的时间用来答疑，问得比较集中的是几件与学习路线有关的事。

有人问，想做自研引擎，这是不是计算机专业必学的东西。答案是不一定，得看你处在哪个阶段。如果你只是做一些研究，或者目标就是发论文，其实不一定需要去做自研引擎；但如果你后面想做一些更复杂的应用，那就有可能真的需要它。

还有人问，打算用自研引擎做游戏行不行。这跟我们现在做的东西还不太一样。我们这套主要针对仿真，游戏引擎跟它差别不小——游戏引擎里涉及的物理其实要更简单一些，所以它的重心更多落在物理之外那些需要考虑的内容上。

那想做单机游戏要补哪些东西？最基础的是类似 game 101 这类入门课，加上渲染，编程本身是最基本的。如果现在十八岁，那要补的基础知识还很多；今天讲的这些，比如碰撞算法，已经是比较专的方向了，还到不了那个层次。

至于大学的数学，要看方向。如果只针对游戏开发，主要就是微积分、线性代数，高数那一套可能也要学。游戏里涉及的物理通常不会那么复杂，一些基本的数学差不多就够用。力学方面，大学物理里那些比较简单的力学，有个了解就可以，并不需要连续介质力学——游戏里的刚体之类的系统都是简化过的，里面有很多 trick，物理上并没有那么 serious。

最后补一句关于这套代码本身：PeriDyno 是一个开源系统，里面很多东西也在不断完善，中间某个版本可能会有点小问题，这属于逐步完善过程中的正常现象。

## 脱离 CUDA 之后：Vulkan 与通用并行计算
> 对应块：BLK15 | 覆盖分集：P08上 | 块标题（分集名）：《8. Vulkan编程原理及通用并行计算》

这是这个系列的最后一讲。后面蔡老师还会接着讲工程仿真里的一些内容，所以今天这一讲，你完全可以把它当成前面七次课的一个番外篇。

前面七次课，从 CUDA 到 PeriDyno 引擎，一路下来其实是完整的：怎么用 GPU 做并行、怎么把物理仿真的算法拆到显卡上跑、引擎里那些模块怎么组织，该讲的都讲了。但这条完整的线有一个隐含前提——你手上得有一张 N 卡。

现实里不一定。有些同学现在没有英伟达的显卡，或者因为种种原因用不了 N 卡，那前面课程里讲的那些案例、很多程序，很可能就跑不起来。这就带出一个很实际的问题：如果我们脱离 CUDA，还想做并行仿真相关的并行计算，还能不能做？

第二个原因在 Vulkan 本身。Vulkan 是 2015 年提出、2016 年正式发布的，它提出的初衷，是要把渲染和计算这两件事整合起来，用一套统一的 API 去做。这几年在渲染这一块，大家的常识已经比较多了，也发现 Vulkan 确实有它很多占优势的地方；但在仿真计算领域，用 Vulkan 做的其实不太多。所以很多时候我们对它的能力边界并不清楚——针对仿真计算，它到底能做什么、做到什么程度，这件事没有定论。今天讲的很多内容，正好结合了华为前期做过的一些相关工作，拿出来跟大家做个分享。

先打个预防针：今天讲的很多东西还处在探索过程里，不是一个成熟的解决方案，其实不是的。Vulkan 这门语言、以及它用在仿真这一块，还有很多值得进一步探索的地方；它本身是开源的，后面也会不断完善。

按顺序，今天大概走这么几块：先简单介绍一下 Vulkan，以及通用并行计算的一些概念；然后讲一个比较具体的例子——怎么用 Vulkan 写一个并行计算的程序，这个计算跟渲染完全无关，纯粹是一个通用的并行计算问题；写的过程中你会发现，纯粹用原始的 Vulkan API 去做，其实还是蛮困难的，所以接下来要看，针对「Vulkan 编程太复杂」这个问题，我们怎么去简化、怎么把计算任务的编程复杂度降下来；再往后，因为整个 Vulkan 后端是内嵌在 PeriDyno 这个框架里的，它作为一个跟 CUDA 类似的后端，还要讲一下它怎么跟 PeriDyno 对接；另外还有一些前期各种尝试里踩出来的问题，也正好分享一下；最后是一些简单的案例展示。

### Vulkan 的出身与野心

Vulkan 最早是在 GDC 2015 上被提出来的，正式发布是在 2016 年。

它的上一代主要是 OpenGL——之前大家用得最多的就是它。但 OpenGL 用下来问题不少：多线程环境下有一堆问题；移动平台和 PC 平台还是两套不通的 API；而且 OpenGL 主要还是针对图形渲染，对通用计算这一块的支持比较弱。

所以 Vulkan 设计的初衷，就是把渲染和仿真这两个任务整合到一起，用一个通用的 API 去解决这两个核心任务。它当时被提出的时候，被誉为「OpenGL Next」——下一代的图形接口，也就是未来有可能要替换掉 OpenGL。

不过短期内我估计没那么快，这会是一个漫长的、逐步替换的过程。本质上要看 Vulkan 到底能把 OpenGL 以往那些问题解决到什么程度，另外还牵扯到各种硬件厂商的支持，这些都相关。目标倒是很明确：替换掉 OpenGL，成为新一代的图形接口标准。

这里还有一个特别有意思的点：Vulkan 特别偏底层。直接用 Vulkan 去写各种程序，实践起来非常麻烦、不方便。所以如果你是图形或者仿真计算刚入门，今天讲的内容其实不太适合你——这个时候不适合用 Vulkan 写，更应该拿 CUDA 作为入门的基础。后面会讲，怎么能尽可能把这个复杂度降下来。

### 它凭什么被称为下一代图形接口

既然被认为是下一代的图形 API，它肯定有相对 OpenGL 无法比拟的优势。最直接的几条是这样的。

#### 一套 API 覆盖所有平台

所谓「统一」，针对的是以前 OpenGL 的老毛病：PC 端叫 OpenGL，移动端叫 OpenGL ES，而 OpenGL ES 其实是 OpenGL 的一个子集。两套 API 并存，兼容性实际上还是成问题。

Vulkan 是用一套统一的 API 去解决所有环境的问题，不论是移动端还是 PC 端。好处是它可以兼容各种各样的操作系统——Android 这样的移动平台，或者 Windows、Linux，都用同一套 API。

如果这件事真的行得通，那对写仿真算法的研发人员来说是个利好：你只需要写一套算法，就可以无成本地迁移到任何一个平台上去运行。后期发布、跨平台迁移的时候，都会方便很多。

#### 天生为多线程准备

Vulkan 对整个多线程环境是比较友好的。而以前像 OpenGL 或者 DirectX，它们在设计的时候，主要还是针对单核 CPU 来考虑的——那个年代的硬件形态就是这样，API 的骨架也就定在那儿了。

#### 更靠近硬件的开销与掌控力

因为接口更靠近底层，Vulkan 所有 API 的调度开销相对来说更低。也就是说，同样执行同样的任务，理论上 Vulkan 的效率应该比 OpenGL 要高。

同样因为偏底层，它其实对整个 GPU 拥有更直接的掌控能力——你能决定的事情更多，要担的责任也更多。

### GPU 编程接口的家族谱

要理解 Vulkan 站在什么位置，得先看看这一大家子。GPU 的 API 其实不少，但目的说起来就两个：不是为了做渲染，就是为了做计算（仿真）。Vulkan 特殊一点，它渲染和计算兼顾。整个家族的演进，也是伴随着 GPU 本身的发展走的。

#### 固定管线的 OpenGL

最早是 OpenGL，1992 年提出。当时显卡刚出现，针对游戏、各种三维场景，做一些固定的管线功能。最初它主要是用 C 来写的。

早期 OpenGL 不具备可编程管线。学图形的时候为什么要讲「固定管线」？因为整个流程每一步做什么都是固定的，你只能在它给定的位置上塞数据，改变不了它怎么算。这就是早期图形 API 的特点。

#### DirectX 与着色器的引入

微软后来独立发展出了 DirectX，在 Windows 95 里就把它引入了。微软借助 Windows 的覆盖面，形成了一套独立的标准，所以 DirectX 是平行于 OpenGL、独立发展的一条线。

后来大家希望 API 具备一定的可编程能力。DirectX 9 引入了 HLSL（高阶着色语言），从此像顶点着色器、片元着色器这几个特定阶段，可以由用户自己去设计行为——比如对顶点的属性做一些自定义的计算。让特定阶段具备可编程能力，这是着色器带来的最大变化。

#### 移动端逼出来的 OpenGL ES

OpenGL 最初主要还是针对 PC 平台。到了 2003 年前后，21 世纪初最大的一个变化，就是各种移动设备层出不穷。手机其实也有 GPU，只是性能相对弱一些，但图形能力同样需要兼顾移动设备。于是就发展出了 OpenGL ES——它是 OpenGL 的一个子集，专门用来做移动设备上的图形渲染。

移动端同样需要着色阶段可编程，所以 OpenGL 也引入了自己的着色语言 GLSL。GLSL 和 HLSL 语法很像，很多东西是相通的，但两者的维护主体不一样：OpenGL 这一套由 Khronos Group 这个组织维护，DirectX 那一套由微软维护，语言的迭代方向也就此分开。

#### CUDA 划下的分水岭

07 年之前，图形 API 主要还是以渲染为主。也有过用特定 shader 做模拟的尝试，比如文华老师在 2004 年就做过三维流体的模拟。但总的来说，早期因为各种配套工具、调试工具的缺失，用 GPU 的 API 去写一个比较复杂的仿真算法，代价还是相当大的。

2007 年 CUDA 由英伟达提出来，我认为这是一个里程碑式的节点。因为它重新定义了 GPU：GPU 不是单纯用来做渲染的，它完全可以去做任何跟渲染无关的通用仿真计算任务。这件事之后，GPU 在各种算法训练里的地位一路往上走——今天各种 AI 训练，本质上都建立在「GPU 是通用计算设备」这个前提上。07 年之后，学术界也好、产业界也好，都发生了很大的变化。

CUDA 早期主要还是针对计算的，早期版本（08 年那会儿）只支持 C，后来才逐步加入对 C++ 的支持——具体是哪个版本号我记不太清楚了。发展到现在它已经变得比较好用，所依据的标准也在不断更新，C++17 之类的新特性不断加进来。

但问题也在这儿：CUDA 是英伟达的护城河。对整个行业来说，一套开放的行业标准是缺失的。

#### 迟到的 OpenCL

2009 年提出了 OpenCL，专门针对通用并行计算，算是一个通用计算标准。最早是 Apple 发起的，后来由 Khronos Group 维护。

它里面很多特性跟 CUDA 比较像，唯一不一样的地方是它不做混合编译——shader 和后续的代码是分离的。它同样支持 C 和 C++。但从后来的发展看，从用户角度讲，OpenCL 的用户群体远远少于 CUDA。

#### Metal 与 Vulkan：两条路，一个目标

Metal 是 Apple 在 2014 年开始发展的。苹果也想把图形和计算这两个 API 融合，形成一个统一的图形接口。但 Metal 和 DirectX 一样，主要只针对自家平台——Mac 这些苹果的系统，跨平台能力相对不足。

到 2016 年，Vulkan 发布了，目标还是同一个：把渲染和计算这两件事打通，用一个统一的 API 去处理。Vulkan 最早是 AMD 发起的，后来也由 Khronos Group 维护。

Vulkan 比起 OpenGL、OpenCL 这些，更底层。它会把很多 GPU 硬件的特性直接暴露出来。好处是运用得当的话，性能可以更高；坏处是对编程的人要求同样很高，编程复杂度大幅提升。另外，它的着色端目前还是 C 风格的写法，C++ 的那些特性，比如各种面向对象的封装、继承派生，是支持不了的。

### 语言怎么选：CUDA、OpenCL 还是 Vulkan

单纯做并行计算，其实有很多解决方案：可以用 CUDA，可以用 OpenCL，甚至用 Vulkan 全部重写一遍也没问题。为什么会有这么多标准和 API？一方面是商业上的考量，这个我们不去讨论。对研发人员来说，更该关注的是：针对一个特定的任务，怎么选一个最适合自己的语言。

这里我列了几个方面，以 CUDA、OpenCL、Vulkan 为例，看看它们各自的差异，最后你结合自己的需求去决定。

#### 能不能混合编译

先说清楚混合编译是什么。写过 OpenGL 的话你会发现，设备端（GPU 端）的代码和主机端（用 C++ 写的那部分代码）是分离的，它不是放在一块编译的。

CUDA 支持把这两者放在一起：在一个 `.cu` 后缀的文件里，你可以同时写 C++ 代码和 kernel 代码，nvcc 会帮你把里面不同的代码拆开。这需要编译器层面来协助完成。

好处很直接：代码的编码复杂度能大幅降低，研发算法的效率也就跟着上来了。

OpenCL 和 Vulkan 目前不支持。不支持的直接后果是：你在主机代码里定义了一个数据结构，那设备端代码里还得再维护一份，而且必须保证两边的结构完全一致。这对代码维护是有成本的。

#### 调试工具够不够用

仿真的算法逻辑比较复杂，所以需要各种各样的调试工具来辅助、支撑——比如中间某一步算完，你要能看看它输出的结果对不对。这件事其实很重要。

这一点目前三家都支持，只是用 CUDA 的话会更好用一些。

#### 跨平台能力

如果后期我们写了一份代码，希望能无缝迁移到多个平台上去，那就得看这个 API 本身的跨平台能力。

CUDA 完全依赖英伟达的显卡。如果现在用的是 AMD 的显卡，或者是移动端的设备，很可能根本没有可用的 N 卡，那你以前写的 CUDA 代码就不能直接用。所以从跨平台的角度讲，CUDA 对平台、对硬件的依赖是比较强的。

OpenCL 和 Vulkan 相对好一些，严格讲 Vulkan 最好——它支持的平台从 PC 端到移动端，兼容性更广。

但这也带来一个不好的地方：性能和代码的复杂度，有时候很难折中。而且跨平台兼容做得好，不代表在不同平台上适配时没有差异，依然会有一份额外的工作量要去解决。

#### 语言标准与封装

不同语言支持的 C/C++ 标准不一样。CUDA 和 OpenCL 现在主要是 C 和 C++。

C++ 为什么重要？仿真如果单纯用 C 写，是不是也可以？当然可以。但问题在于，如果不依赖任何封装的特性，整个代码的复杂度会极高。所以从代码简洁的角度讲，支持 C++ 对对象的封装是比较重要的。

Vulkan 目前不支持这些，所以用 Vulkan 的话，很多代码需要退化到 C 的一些规范上。

C++ 还有很重要的一块是模板。模板要解决的是这件事：我们不希望类似的代码写好多份，那样维护成本很高；有模板支持，就可以统一维护一份代码，再用模板的各种技术把维护成本压下来。Vulkan 目前也不支持模板。

把这几条并排放，差别就很清楚了：

| 维度 | CUDA | OpenCL | Vulkan |
| :--- | :--- | :--- | :--- |
| 混合编译 | 支持，`.cu` 里主机代码与 kernel 同文件，由 nvcc 拆分 | 不支持，主机端与设备端代码分离 | 不支持 |
| 调试工具 | 支持，最好用 | 支持 | 支持 |
| 跨平台 | 完全依赖 NVIDIA 显卡 | 较好 | 最好，PC 到移动端 |
| C++ 封装与模板 | 支持 | 支持 | 不支持，设备端退化为 C 风格 |

> **结论**：如果你只是想做一个特定的研究、写特定的算法，用 CUDA 可能是最方便的；一旦要考虑移动端或者跨平台，CUDA 就解决不了你的需求，这时候可以转向 Vulkan，对特定算法做一次重构，生成一份能兼容各个平台的仿真算法。

### 两个数组相加，为什么在 Vulkan 里这么难

既然每种语言都有自己的特点，那我们现在假定选定 Vulkan，要写一个并行计算的程序，该怎么做？

先看不依赖任何封装、直接用原始 API 的情况。任务非常简单：有两个数组 a 和 b，把它们加起来，结果存到数组 c 里。

这个任务用 CUDA 写，很简单。我相信哪怕是一个完全没接触过 GPU 的初学者，花几个小时也能把它写出来，这没有任何问题。

但换成 Vulkan 来写，就是「一言难尽」。针对一个完全的 Vulkan 初学者——或者之前对 GPU 完全没有任何接触的人——如果仅仅想实现这个功能，估计得花很久的时间。

为什么会这么复杂？因为 Vulkan 更偏底层，很多硬件特性直接暴露在外面。CUDA 之所以好写，本质上是它的编译器层面替你做了很多简化的工作；而 Vulkan 的编译器能力相对比较弱，很多时候各种各样的执行流程，需要你自己去指定。

### 对象链：从 instance 到 queue

要写前面那个任务，先得搞清楚 Vulkan 里到底有哪些东西。最顶层是一个 application，往下就进入这一长串对象。

第一步是创建一个 instance。针对不同的任务，你可以创建多个 instance，application 和 instance 是一对多的关系。

有了 instance 之后，因为一台电脑或者一个移动设备上可能有多张显卡，这时候你要选择一张具体的卡——这就是物理设备（physical device），它对应的是真实存在的那块显卡。你要决定在哪个显卡上执行你的计算任务。

物理设备选完之后，真正执行计算的地方是逻辑设备（logical device）。逻辑设备里面有对应的队列，队列主要有三种。

为什么是三种？因为 Vulkan 有两类任务：渲染任务和计算任务。从队列的角度讲，就有图形队列（graphics）、计算队列（compute），另外还有一个 transfer 队列。

transfer 队列主要针对数据拷贝——比如你现在有两个数组，需要把数据在它们之间拷来拷去，就有这么一个独立的队列。

不过要注意：不管是图形队列还是计算队列，实际上都可以同时完成 transfer 的拷贝。这一点在一定程度上简化了整个计算流程，你不必为了拷一份数据特意去排 transfer 队列。

```text
application
    │  一个 application 可对应多个 instance
    ▼
instance
    │
    ▼
physical device          真实的那张显卡
    │
    ▼
logical device           真正执行计算的地方
    │
    ├── graphics queue
    ├── compute queue
    └── transfer queue
```

这张图是自上而下的创建顺序：先有应用，再建 instance，然后从多张卡里选定物理设备，接着建逻辑设备，逻辑设备上挂三种队列。后面那些 buffer、pipeline、command buffer，都是挂在这条链上的对象。

### 命令要自己录：command pool 与 command buffer

有了队列之后，下一步就是创建各种 kernel 函数，然后去执行。

这一步比 CUDA 复杂得多。CUDA 里你可能直接写一个 kernel 函数，编译器帮你转成二进制，完事。Vulkan 里整个逻辑都需要你自己创建：要执行一个计算的管线，首先得分配一个命令池（command pool），池子里会有很多命令缓冲区（command buffer）；你在这些 command buffer 上记录到底要执行哪些命令；计算管线就依赖这些 command buffer 去完成整个计算过程。

再往下，管线的输入也要交代清楚。它需要输入各种各样的数据——比如输入一个 buffer，或者输入一个变量，那你还得额外指定这个 buffer 到底是什么类型、多大。这些都得说明白。

还有很重要的一块是 GPU 上的内存。你在 GPU 上创建的 global memory、local memory 这些，创建出来之后，要指定它代表什么类型，描述符要指定清楚，然后才能传给计算的 API 去执行。

对比 CUDA 就很明显：CUDA 里很多东西是隐藏的。你不选 device，它默认就给你选 0 号；你完全不管其他部分，单独执行一个 kernel，它有一堆默认操作替你兜着。但 Vulkan 的很多地方，需要你显式地把每一部分都指定出来。只有每一步都指定清楚，Vulkan 才能真正去执行你的代码。

把前面这些串起来，那条链大概长这样：

```text
instance
  ↓
physical device（选一张卡）
  ↓
logical device + queue（建好三种队列）
  ↓
分配 GPU 内存：buffer / global memory / local memory
  ↓
写 kernel → 编译成 SPIR-V
  ↓
descriptor set 描述参数
  ↓
pipeline + command buffer（逐条记录命令）
  ↓
提交到队列执行
```

对照前面那个「两个数组相加」，你会看到它其实包含很多步骤。这也是为什么说，原生 Vulkan 的复杂度不在算法本身，而在你必须亲手把这条链条一级一级搭出来。

### 数据怎么上卡：staging buffer

设备初始化完之后，真正要准备的核心其实是两样东西：一是你要准备的数据是什么，二是你的计算程序里那段代码是什么。先看数据。

第一步是在 GPU 的 memory 上把需要的数据分配出来。

这里跟 CUDA 有一个明显的差别。CPU 和 GPU 的数据一般是不能直接互相访问的：我现在有一段 C/C++ 的代码，它没法直接访问 GPU 上的一块数据；反过来也一样，GPU 上的一个 kernel 函数，也没法直接访问 CPU 对应的内存空间。

CUDA 里有拷贝函数，你可以直接把 CPU 的一块数据拷到 GPU，然后 GPU 的代码就能看到这块数据。

Vulkan 不这样。它所有的数据都需要经过一块叫 staging buffer 的存储区中转。这块存储区的特别之处在于：它对 CPU 和对 GPU 都是可见的。所以 CPU 和 GPU 互相打交道的时候，不是两边直接对话，而是要通过 staging buffer 做一次中转。

具体做法是：在 CPU 这边分配一块空间，先映射（map）到 staging buffer 里；staging buffer 对 GPU 来说也能直接访问，但那样效率比较低；所以最好再把它拷到 GPU 的 local memory 里，之后 GPU 的 kernel 访问这块数据就会快得多。

```text
CPU 内存
   │  map
   ▼
staging buffer          CPU 与 GPU 都可见，用于中转
   │  copy
   ▼
GPU local memory        kernel 直接访问，速度更快
   │
   ▼
compute kernel
```

数据从 CPU 出发，先进 staging buffer，再落到 GPU 的 local memory，kernel 只碰最后一段。跳过第二段直接让 kernel 读 staging buffer 也能跑，但那是绕远路。

> **提示**：这是 Vulkan 在分配空间时跟 CUDA 差别最大的地方。CUDA 的拷贝是「一次到位」，Vulkan 则强制你把「中转」这一步显式写出来，也就多了一次映射、一次拷贝的代码。

### kernel 里要交代的三件事

数据备好，第二步就是准备计算的 kernel。kernel 可以用很多种着色语言来写，这里举的例子是用 GLSL 写的。

这个 kernel 里其实要干几件事。

第一，指定输入到底是哪些参数，也就是前面分配的那些 buffer 里，哪几个是输入。两个数组求和存到第三个数组，那就要输入三个 buffer，另外还要一个变量，告诉程序这个数组里一共有多少个元素。

第二，指定 block 的大小。GPU 上的执行是以 block 为单位进行的，所以这个信息必须在 kernel 里交代清楚。

第三，写入口函数。所有 shader 的入口都是一个叫 `main` 的函数。

后面的代码就比较简单了，跟 CUDA 很像：取全局的 ID，然后据此算出自己该处理哪个位置的数据。这个全局 ID 是三维的；如果数组是一维的，那你只要取它的 x 分量，按 x 的大小把对应的数据位置定位出来，就可以开始算了。

### SPIR-V：语言和驱动之间的中间层

kernel 写完还不算完。这份代码直接拿去执行是执行不了的，需要先编译成一个叫 SPIR-V 的中间文件。

SPIR-V 的位置很关键：它是编程语言和底层之间的中转站。它并不是单纯针对 GLSL 或者 HLSL 推出的标准，而是可以把很多种语言都转换成同一种标准的二进制中间文件，然后再拿到各种 GPU 上去执行。

```text
GLSL / HLSL / 其它着色语言
        │  编译
        ▼
SPIR-V（统一的中间二进制）
        │
        ▼
各厂商 GPU 驱动 / 硬件
```

左边是各种语言，右边是各家驱动，中间夹着 SPIR-V。为什么要有这一层？以前左边这些语言直接跟底层的 driver 打交道，工作量很大：你的语言在不断变，driver 也可能在变，两边一变就要做各种适配。有了 SPIR-V 这层标准，无论左边还是右边，都只跟中间这一层打交道，整个流程就简化了很多。

### descriptor set 与两条管线的长短

SPIR-V 有了，接下来要执行 kernel，还得描述清楚它到底有哪些参数——这就是 descriptor set（描述符集）要做的事。

再往后是一整个计算的管线。这里有一张图值得单独说一下，因为这张图很容易让人形成误解。

Vulkan 有两部分任务：一部分是渲染，一部分是计算。渲染这部分的步骤非常多：图里橙色的是一些固定的功能，淡黄色的是一些可编程的 stage；这些可变的 stage 跟计算其实很像，都允许你自己实现一些自定义的函数。

```text
渲染管线（长）
  固定功能阶段
      ↓
  可编程阶段
      ↓
  固定功能阶段
      ↓
  ……（如此交替多轮）
      ↓
  固定功能阶段

计算管线（短）
  可编程阶段（只有一块）
```

看这张图，很容易得出一个印象：渲染这么复杂，计算就只有一块，那计算应该简单得多。这个印象是错的，实际情况正好相反。

渲染的流程之所以长，是因为它把很多数据都给你标准化了。比如转换的时候要输入顶点，那顶点需要哪些数据、需不需要索引、顶点的位置、其他的一些属性，这些都有一套标准，你按这个标准准备数据、跟管线打交道就行。这在很大程度上简化了流程——前提是你的数据套得进这套标准。

计算面向的是通用的计算任务，这时候你没法预见数据结构长什么样。刚体也好、流体也好，里面的数据结构五花八门。计算管线对数据规范其实没有约束，那它能不能适应各种各样的数据接口？这件事是没有定论的。

所以对仿真来说，这反而增加了复杂度。如果你只是写一些简单的 shader，彼此独立，那没有任何问题。但如果我们研发的是一个复杂的物理仿真系统，不同模块之间是需要交互的；数据标准不统一，各个模块之间就没法协同。

这也是后面要讲的内容：怎么利用这个管线，在它的基础上加一些约束，然后把复杂的算法耦合起来。

走到这里，整条流程的落点反而变得很朴素：先把各种 buffer 一个个创建出来。而 buffer 是可以很多的，创建完之后、真正执行之前，怎么把它们组织清楚、怎么让 GPU 知道每一块该拿去干什么，又是一轮新的交代。

这也正是原生 Vulkan 写并行计算的真实手感：难的从来不是那个「两个数组相加」的算法，而是你必须亲手把从 instance 到 command buffer 的整条流水线搭出来，一处不指定，它就什么都不替你猜。

## 用 Vulkan 做通用并行计算：从裸 API 到引擎封装
> 对应块：BLK16 | 覆盖分集：P08下 | 块标题（分集名）：《8. Vulkan编程原理及通用并行计算》

不同的 kernel，依赖的 buffer 是不一样的。这句话本身没什么稀奇，但它把 Vulkan 通用计算里最麻烦的一件事摆到了台面上：shader 只知道自己有几个参数，并不知道这些参数落在显存的哪一块。

于是每一次执行，都得有人在旁边把参数装配好、把计算流程录下来、再推上去跑。这一讲就从这条装配线讲起，一路讲到怎么把它封起来，让写仿真算法的人不必每写一个 kernel 就手工走一遍全流程。

### 描述符与命令缓冲：一次 GPU 计算的装配线

写 shader 的时候，我们只声明"第 0 个参数是一块 float 数组、第 1 个参数是另一块"，函数体里对 a、b、c 做加法。可显存里同时躺着几十块 buffer，GPU 凭什么知道这一次该读哪三块？所以具体执行之前，必须告诉 pipeline：我这次需要哪些 buffer，把它们组合到一起，再输入到 pipeline 里。

这件事由 descriptor set 承担。

> **定义**：descriptor set（描述符集）是一份参数清单，逐条写清楚某个 kernel 的第几个参数指向哪块 buffer、是什么类型、数据多大。一个完整的 kernel 要 n 个参数，就有 n 条描述，合成一个 set。

set 描述清楚之后，整个计算就会按这份描述去读对应的数据：kernel 说需要 n 个，它就按 n 条去找对应的那块数据，然后才真正进入执行计算的过程。

再往里拆，一个计算 pipeline 其实由两部分构成。一部分是 layout，相当于输入参数的描述；另一部分是前面写的 shader，编译成二进制之后，实际上是一段 SPIR-V 的 code。前者说"要什么"，后者说"算什么"，缺一不可。

这两边一摆，关系就出来了：buffer 是一堆，pipeline 也是一堆，彼此多对多。

```text
        Buffer 集合                     Pipeline 集合
   +------------------+           +----------------------+
   |   buffer A       |           |   kernel 1 (SPIR-V)  |
   |   buffer B       |           |   kernel 2 (SPIR-V)  |
   |   buffer C       |           |   kernel 3 (SPIR-V)  |
   |   ...            |           |   ...                |
   +--------+---------+           +----------+-----------+
            |                                |
            +-----------+      +-------------+
                        |      |
                    Descriptor Set
              （按某个 kernel 的形参组合绑定）
                        |
                   Command Buffer
                        |
                      Submit
                        |
                     GPU 执行
```

左边分配一堆 buffer，右边有一堆计算 pipeline；根据某个 pipeline 的需求，组合不同的描述符，把这一组 buffer 交给它，就执行了一个具体的计算任务。同一块 buffer 可以被多个 pipeline 使用，同一个 pipeline 在不同时刻也可以配不同的 buffer——这就是多对多的含义，也是这套东西值得单独抽一层来描述的原因。

描述符备齐，接下来是具体执行，这时候依赖 command pool，相当于一个命令池。池子里最主要的东西是 command buffer：每一次执行都需要一个 command buffer 对象，把这一趟要做的事记下来。

记的内容有四类：

- 描述符：这次输入哪些参数，要描述清楚；
- pipeline：这次需要哪个计算，把它绑定进来；
- 常量：一些需要随命令一起带进去的常量；
- dispatch：block size 到底是多少、总共分成多少个组，用 dispatch 这个 API 指定清楚。

这四类合起来，就构成一个 command buffer。一次执行，等于把参数装配、计算流程、执行完成整个过程都装进去了。

> **易错点**：command buffer 只是"准备"，不是"执行"。录完之后不提交，它什么都不会发生。最后一步是提交（submit）：提交哪个 command buffer，它才会把里面记录的所有命令实际执行一遍。

到这儿，前面那个简单数组相加任务的完整流程就走完了：描述符描述参数，pipeline 提供计算，command buffer 把两者装配成一条条命令，提交之后由 GPU 执行。

### 裸写 Vulkan 的代价

任务很简单，代码非常长。

我写了一个样例，名字叫 vulkan native。之所以专门用这个词，是为了跟后面有个对照：如果不用任何封装、不做任何简化，纯调 Vulkan API 到底要包含哪几个阶段。

```text
创建 Instance
   → 选择 Physical Device
   → 创建 Logical Device
   → 分配 Buffer（CPU 内存 → Staging Buffer → GPU Buffer）
   → 创建描述符相关对象
   → 创建 Descriptor Set 与 Compute Pipeline
   → 录制 Command Buffer
   → 提交执行
```

光是分配 buffer 这一步就已经很复杂了，而且这里边已经用了一些辅助工具，相当于一定程度上简化过。数据要先从 CPU 到 staging buffer，再从 staging buffer 到 GPU buffer。往后还要创建描述符相关的对象，再往后创建 descriptor set 以及计算的 pipeline，最后是 command buffer——把整个需要执行的命令记录下来。

这个样例差不多几百行代码。任务本身只是两个数组相加，纯粹去调 API 就是这个量级，所以写起来比较费劲。感兴趣的话可以自己照着走一遍，感受一下 Vulkan 这套计算过程到底包含哪些部分。

这个程序是我专门为这次课准备的，目的就是看看纯用 Vulkan API 写一个这么简单的程序，开销到底怎么样。写的时候花了好多时间，一方面步骤多，另一方面特别容易出错，整个调试过程也都比较困难。真正费时间的地方也很清楚：shader 那一侧其实是一样的，写起来花不了几分钟；但 host 端要去准备各种对应的流程，非常耗时间。

> **结论**：仿真任务不能这么写。仿真本身就比较复杂，再叠上一层这么复杂的编程，铁定没法做。

### 封装的三条主线

既然这么写不现实，接下来就要降低复杂度。这里的封装不针对渲染，只针对计算任务——让底层那套东西服务特定的计算场景，把整个研发代价压下来。

方向上分三块。

第一块是对象。Vulkan 的对象比较多，要做一定的分类跟封装，把跟仿真算法无关的细节隐藏起来。写算法的人不应该关心 instance 怎么建、设备怎么选。

第二块是调用。实际仿真涉及的 kernel 五花八门，每个 kernel 的参数组合都不一样，所以要想办法简化整个 kernel 调用的方式。

第三块是数据。前面提过，如果对访问数据不做任何约束，不同 kernel 之间的数据协同会非常困难。所以要在数据层面看看有没有可能做一个统一的封装，让各种各样的仿真任务都能共用同一套描述。

### VkSystem、VkContext、VkProgram：把散落的对象收进三个盒子

现在 PeriDyno 集成了 Catalina 这个 Vulkan 后端，在它之上做了一层封装。封装之后的结构大致是这样：

```text
VkSystem
├── Instance 的创建、Physical Device 的选取
├── VkContext
│     └── Logical Device + 各类 Queue
└── VkProgram
      ├── VkDeviceBuffer   大块显存缓冲
      ├── VkUniform        易变、规模小的数据
      └── VkConstant       长期不变的常量（如重力）

VkVariable：上面三类的统一父类
```

整个 Vulkan 底层被抽象成一个 VkSystem 类，它主要管那些跟设备打交道的、一次性的活儿：创建 instance、选取 physical device 等等。逻辑设备以及它的各种 queue，则统一交给 VkContext 管理。设备这一层的状态收在一处，后面所有对象都从这里取，不会散得到处都是。

再往下是 VkProgram，这个类跟 CUDA 的 kernel 函数是对标的。在 CUDA 里写一个 GPU 上可执行的 kernel 函数，对应到 Vulkan 里，等效地就要写一个 VkProgram。

VkProgram 要依赖数据，这些数据被抽象成三类，统一挂在一个父类 VkVariable 下面：

| 类型 | 用途 | 典型场景 |
| :--- | :--- | :--- |
| `VkDeviceBuffer` | 分配一块大的缓存 | 粒子位置、速度这类成规模的数组 |
| `VkUniform` | 易变但规模小的数据 | 几个参数打包后传到 GPU |
| `VkConstant` | 固定或不常变的数据 | 重力这类常量 |

> **提示**：这三类的划分依据不是数据类型，而是"变化的频率和体量"。大块且频繁读写走 buffer，小而易变走 uniform，长期不变走 constant。选错类别不会报错，但会带来不必要的传输开销。

这一层做完，Vulkan 的各种对象就有了统一的去处，编程流程也就被简化下来了。

### 从 CUDA kernel 到 VkProgram

同一个向量求和任务，两边各写一遍，差别就出来了。

#### CUDA 侧：两步走

还是拿前面那个简单的向量求和 kernel 举例。用 CUDA 写，其实就两步。

第一步是声明，函数前面要加 `__global__` 标识符，所有 CUDA 的全局函数都需要这个。第二步是标明这个 kernel 函数到底需要哪些输入，比如三个数组 a、b、c，以及它们分别对应什么类型。函数体里就是一条简单的指令：a 加 b 放到 c 里头。调用的时候有特定的语法。

两步，声明加调用，中间没有别的东西要准备。

#### Vulkan 侧：声明、载入、调用

对标过来，Vulkan 这边引入的就是 VkProgram。它跟 CUDA 那边已经蛮像了，同样包含两部分。

一部分是声明：声明一个函数，写明它需要输入哪些形参。比如输入 float 的数组 a、b、c 三个，还要告诉 kernel 这个数组的长度——长度可以做成一个 constant。

> **提示**：Vulkan 这边的形参是用一组宏定义出来的，不是普通 C++ 的函数签名。声明写完，契约也就定了：想调用这个 kernel，就必须输入四个参数——三个 buffer 加一个 constant 的数。

另一部分是载入。Vulkan 的 shader 代码跟 host 代码是分离的，所以声明之后还有一件事：把 shader 编译出来的 SPIR-V 文件载入进来。载入完成，声明过程才算真正结束。

到了调用的时候，有一个比较快捷的方式，一次调用就把执行也带上。调用之后，其余几个参数跟 CUDA 那边类似：告诉 GPU block size 是多少，这里写的是 128；再对它分组，总数量是 n 个，要分成多少个 group。dispatch 的时候需要这些信息，才能生成对应的命令。后面那几个参数跟声明过程完全一一对应——声明了几个数组，就传几个。

数据层面还有一些别的东西。除了 buffer 和 constant，还可能需要别的结构，因为我们现在做的是二维高度场、三维欧拉网格这类数据，需要额外的数据结构支持。形参层面做了一层统一：底层的 constant 对应 VkConstant 结构，uniform 对应 VkUniform 结构。

比较麻烦的是流体里的邻域列表。它不是一个 buffer，而可能需要几块 buffer 组合到一起，统一去定义这个结构。这一块也可以定义宏，但 Vulkan 跟 C++ 不是混编的，调用过程就没那么方便，所以还在进一步尝试，看有没有可能更简单地处理这个问题。

### 即时、缓存与多程序

VkProgram 的运行机制有两种。

#### 即时模式：每次都重新装配

就是前面看到的那种快捷调用。看它里边的代码，其实分两个过程：首先创建 command buffer，然后提交到 queue 去执行。所以这一个调用，把准备和执行两件事都包含了。

这么做的问题在于：每次都会把实参重新更新一遍。这个动作是有开销的。写仿真算法的时候，经常要循环很多次，每次都重新往里写一遍，实际上存在大量重复的逻辑计算，白白烧掉时间。

#### 缓存模式：录一次，用多次

针对这种任务，还有一种模式，叫缓存模式。记录 command buffer 的时候只记录一次，真正执行的时候重复利用已经记录下来的形参数据，这样就降低了整个执行的代价。

> **提示**：两种模式的分界是"参数变不变"。参数每帧都变，即时模式省心；参数在循环里固定，缓存模式才划算。缓存的代价是你必须保证录制之后形参指向的 buffer 没有被换掉。

#### VkMultiProgram：多个 kernel 进同一个 command buffer

还有一种情况单个 VkProgram 解决不了：仿真任务里的计算往往不是单个 kernel。比如弹性体求解，可能分为好几个 kernel，这几个 kernel 要交替执行。

于是引入 VkMultiProgram。它把不同的 kernel 组合到一起，把不同 program 的执行命令记录进同一个 command buffer。写的时候只需要写一次，同时把各种各样的命令组合到一起。比如调用的时候要循环十次，每次都需要创建一个 dispatch 命令，把这些整个组合到一个 command buffer 之后，再统一执行。

这解决的还是同一个病根：多个 kernel 不断来回切换 command buffer，会导致性能低下。

### 数组相加的完整闭环

按这套方式，最后再写那个数组相加的任务，代码就比较少了。整段程序主要分几块。

第一步，所有程序进来必须有一个 VkSystem，有 instance，并且必须初始化。这个初始化相当于把前面那些事全做完了：physical device 的选取、逻辑设备的生成等等，都不用自己写。

第二步，创建所有的 buffer。这里的接口跟 CUDA 后端是一样的：同一套接口，一个用来分配 CPU 上的内存，另一个因为走的是 Vulkan 后端，直接用 Vulkan API 在 GPU 上开辟出一块。用起来不需要像 native 那样麻烦，可以直接把数据放进去——内部实现其实也用了 staging buffer，只是各种细节被隐藏起来了。

第三步，声明一个 kernel，标明到底需要哪些形参，然后把 shader 的 SPIR-V 文件载入进来，最后执行。

计算完之后把数据拷回来输出。前面的初始化是 0、1、2、3、4……这样线性排下来的，所以这个函数直接运行，会打出 0、2、4、6、8，正好验证了整个计算的正确性。

拿它跟 native 那个程序对照：那边差不多三百多行代码，这边依赖 Catalina 的封装之后，代码复杂度被极大压缩。

> **结论**：Vulkan 的复杂度主要不在 shader，而在 host 端那套装配流程——建对象、分内存、配描述符、录命令。谁的封装把这套流程收掉，谁就把研发成本降下来了。也正因为如此，写复杂算法时这套封装对效率的提升非常明显。

### 与后端解耦：中间层与 GpuBuffer

现在引擎里实际上有两个后端：一个是 CUDA，一个是 ROCm。我们还是希望整个框架跟后端无关——不管接入什么后端，比如前面讲的蓝图系统，都能直接拿起来用。

针对这个需求，引擎架构做了一定调整，主要是 framework 这个库。它定义的是引擎架构，所以把跟 GPU 相关的所有后端的东西都从里面摘了出来，放到 core 或者 topology 里。这样一来，整个架构跟底层就彻底解耦：后面拓展算法也好，增加新的后端数据结构也好，完全不影响引擎框架的调整。

具体做法分两块。

一块是计算。GPU 后端的接口要跟计算后端统一起来，因为框架要能对接，靠的是接口一致。框架识别的是 Field，里面包含很多类，比如变量、数组等等；它并不关注这份数据你是用 CUDA 分配的，还是用 Vulkan API 分配的。所以我们在后端跟引擎框架之间引入了一个中间层，用中间层屏蔽掉底层细节。

```text
        引擎框架（Field：变量、数组，只认接口）
                        ▲
                        │  统一接口
              VkArray / GpuBuffer
             （中间层，屏蔽硬件细节）
                        ▲
          ┌─────────────┴─────────────┐
          │                           │
   CUDA 显存分配               Vulkan Buffer 开辟
```

以数组为例：引擎架构这一段看到的是一个 Field，底层则有 CUDA 的显存分配、Vulkan 的 buffer 开辟这些细节，全部藏在底层，通过 VkArray 这个数据结构用统一的接口暴露给引擎。这样就不会出现"新进来一个后端就要不断调整引擎架构"的局面。

另一块是渲染。引擎有几个任务，一个是计算，另一个是渲染相关的，思路是一样的。现在主要有一个渲染引擎，它不直接跟 Vulkan 后端或者 CUDA 后端打交道，而是利用 GpuBuffer 这么一个中间结构，屏蔽掉底层跟硬件相关的 API 信息。

这层中间结构带来的好处是双向的：往下可以换底层，往上可以换渲染引擎。想用 VTK，想直接用 Vulkan 写，甚至整个仿真计算还沿用原来的 API、渲染换成 Unreal，都可以统一通过 GpuBuffer 打交道，比较方便地做各种拓展。

### Vulkan 的硬伤清单

从目前的感受来讲，Vulkan 还是能做很多各种各样的复杂计算任务。但它主要的问题还是前面提的那一条：研发成本比较高。真正用它，有几个地方要特别注意。

最严重的是对齐。CUDA 那边，编译器应该是默认把对齐问题解决掉了；用 Vulkan 写，这个问题需要研发人员自己解决。

举个例子。创建了一个结构，前面那几个字段都是 16 字节对齐的；后面定义了两个字段，都是 4 字节，再往后还有一个类型，也是 4 字节。这时候如果你不补那块 padding，就会出问题——这块 padding 的主要作用就是对齐。

```text
GPU 端（默认 16 字节对齐）
  偏移 0     前部结构（16 字节）
  偏移 16    字段 1（4 字节）
             字段 2（4 字节）
             c type（4 字节）
             padding（4 字节）     ← 补上这 4 字节，凑满一格
  偏移 32    ────────────────────

CPU 端（紧致排列，省掉 padding）
  偏移 0     前部结构（16 字节）
  偏移 16    字段 1（4 字节）
             字段 2（4 字节）
             c type（4 字节）
  偏移 28    ────────────────────  ← 与 GPU 端错开 4 字节
```

GPU 端是按 16 字节一格往前推的，CPU 端则是紧致排列。如果那个 padding 不填，下一个结构开头的 position 0 就会直接跟到 c type 后头，这时候你把这一整块数据拷到 GPU，两边的偏移对不上，各种数据就会错位。

> **易错点**：这类错误编译期不报，运行起来也不崩，表现是数值莫名其妙不对。凡是 CPU 端结构体要整块拷给 GPU 的，都要按 16 字节对齐逐个字段核对偏移，不能指望编译器替你兜住。

第二个问题是双份代码。Vulkan 不支持混编，CPU 端跟 GPU 端实际上是两套代码。比如一个结构体，做刚体动力学的时候两边内容完全一样，但声明在不同的地方，所以需要定义两个这样的结构。后面要是有新需求、后端要增加一个数据结构，device 端同样也要加一份。相互依赖比较多的时候，很容易出错。

> **结论**：不支持混合编译的 API，对研发大型复杂系统不太适用。

第三个问题是不支持 float 的原子操作。这个对仿真的影响非常大：做刚体碰撞也好，做欧拉流体也好，这个操作都非常关键。没有它，一种替代办法是排序——用排序其实也能解决这个问题，但整个研发成本会变得非常高。

第四个问题是不支持模板。很多代码可能得重复写很多遍，维护起来比较费劲。

第五个问题是厂商差异。不同厂商对 Vulkan 特性的支持五花八门、千差万别。Vulkan 的初衷很美好，是为了解决跨平台；但如果不同芯片、不同厂商支持的标准有差异，那么你虽然只写了一份代码，从 PC 端直接移到移动端也并没有那么容易，很多时候还是要针对不同平台做适配、做优化。

> **结论**：Vulkan 目前更适合对个别的 shader、个别的计算步骤做加速，这种场景下它比较有用；指望它承载整套复杂的仿真系统，代价太高。

### 性能账本：小规模不如 CUDA，大规模才反超

还有一层权衡：性能跟开发效率比较难兼顾。Vulkan 更偏底层，性能比较高，但写起来比较麻烦。具体用的时候就得想清楚，你是要快速把仿真算法搭出来，还是性能优先。

之前做过一些对比。因为 Vulkan 更偏底层，我们拿它跟 CUDA 的 thrust 做比较，发现不同规模下性能表现不太一样。

原因不难理解：创建 pipeline、更新描述符，这些动作本身都有开销。所以当计算规模比较小的时候，Vulkan 虽然更贴近硬件，整个计算的效率反而不如 CUDA——那点固定的装配开销摊不掉。只有规模达到一定程度以上，Vulkan 更偏底层的特性、计算密集度上去之后，它的效率才会超过 CUDA。

我们试过 reduction、scan、排序这些算法，基本都是这个结论。排序相对好一点，因为这个也跟算法本身有关系。

> **结论**：总体上看，Vulkan 的性能应该比 CUDA 更优，但它写一个算法的复杂度更高。真正落地的时候，还是要看你更需要效率还是更需要开发速度。

### 示例工程：发射器、流体求解与蓝图对接

这里搭了一个简单的样例，主要展示两件事：一是渲染跟仿真之间的协同，二是怎么跟前面讲的蓝图系统对上。工程里有一个 `sth` 目录，打开就可以直接跑。

样例纯粹是为了展示，里边还缺不少东西：现在仅仅有一个发射器。场景本身跟之前用 CUDA 写的是一样的——一个发射器，后面跟一个流体修改器；流体求解器现在只写了积分的模块，其他模块还没加。运行起来之后，从发射器生成粒子，粒子经过求解处理，就能看到这个场景。

这个场景简单验证了一件事：从后端对接，到跟蓝图、跟整个引擎的对接，流程是通的。当然功能性还不多，界面上现在也只加了一个发射器和一个求解器。但多创建一个发射器也没问题，可以两个发射器一起生成粒子。这就是解耦带来的好处：在完全不改动引擎架构的前提下，可以拓展各种多后端。

工程里还有一些辅助场景，主要是给想用 Vulkan 写算法的人做参照：点、线、面这些基本渲染模块，用的也是 Vulkan 后端。点渲染我演示过了，面和线框就不一一演示。

> **注意**：这些样例必须选 Vulkan 后端去编译，它才能生成；否则生成出来的还是 CUDA 的版本，看不到 Vulkan 后端的这些样例。

另外还有一些样例没有开源，是之前为了验证"用 Vulkan 做仿真任务到底能做到什么程度"：刚体、水波、弹性体这些都尝试过。至少从目前的角度讲，很多计算任务都能做，只是要看花多少代价去完成。

## 从一场撞车说起：CAE 仿真与有限元离散
> 对应块：BLK17 | 覆盖分集：P09上 | 块标题（分集名）：《9. 工程CAE仿真连续介质力学基础》

同一辆车、同一堵刚性墙、同样不到一秒钟的正面碰撞，被两套完全不同的东西各算了一遍。一套是游戏里的物理引擎：车撞上去、挡风玻璃碎开、车身瘪进去，整个过程实时发生，手按着键盘就能看到结果。另一套是 CAE 软件：算同一场碰撞，画面没那么“游戏”，可你细看它的形变、它的侵入量、它每一处的应力，都是冲着真实去的。

两边算的是同一件物理事实，追求的东西却完全不是一回事。前面几讲的重心一直在图形学那边的物理仿真，这一讲换个视角，从工程那头把同一件事再算一遍：CAE 仿真到底在算什么，它凭什么能替代真实的碰撞实验，以及它最后落到哪一套数学方法上。

### 同一场撞车，两种算法

判断一套仿真站在物理仿真这边还是 CAE 那边，我习惯从三个层面拆：计算精度、计算效率、结果数据量。CAE 还多一道后处理。

**计算精度**比的是同一个东西：计算机模拟出来的物理现象，和做物理实验实测到的数据，能对上多少。碰撞中某个零部件瘪了多少、位移了多远，就是评判的抓手。CAE 这个词前面其实省了两个字——工业 CAE、工程 CAE，它落在工业和工程的场景里，所以精度要求提得很高，要跟真实发生的物理现象尽量吻合，整体上高于物理仿真。

**计算效率**在物理仿真那边是硬指标。游戏里车已经撞毁、玻璃已经碎开，画面必须当场出来，慢半拍就不叫游戏，所以它要求实时。CAE 做不到实时，也没打算实时：车头接触刚性墙到形变结束，可能一秒，甚至只有零点几秒，计算机要算几个小时；早些年一个工况算几天是常事。

**结果数据量**是最容易被忽略的一条。物理仿真要的是给图形渲染用的画面，把现象显示出来就完成任务；CAE 要指导工程设计、支撑优化设计，那就得把变形全过程中每一处的数据都留下来——吸能盒怎么瘪的，每个位置的位移、受力、能量，一个都不能丢。于是短短一秒的仿真，配上几小时甚至几天的计算，产出的是数 TB 乃至上百 TB 的数据。

**后处理**是 CAE 独有的一道工序，把这一大堆数据变成人能读的云图、曲线，后面细说。

| 维度 | 物理仿真 | CAE 仿真 |
| :--- | :--- | :--- |
| 计算精度 | 服务于观感，够像就行 | 与物理实验实测对齐，要求很高 |
| 计算效率 | 必须实时 | 一秒的过程算几小时到几天 |
| 结果数据 | 实时渲染的画面 | 全过程的场数据，数 TB 级 |
| 后处理 | 基本不需要 | 云图、曲线等专门环节 |
| 几何与材料 | 简化模型 | 真实几何建模加真实材料本构 |

> **结论**：CAE 相比物理仿真，精度要求更高，要真实表达物理现象；计算效率一定比不过物理仿真，速度更慢，因为它要算的东西多得多——整个几何模型要真实建模，材料的本质要真实表征；此外它还多出结果数据和后处理两个概念。

### CAE 是什么：从几何模型走到工程决策

CAE 就是 Computer Aided Engineering，计算机辅助工程。它面对的是实际工程问题：汽车碰撞、土木里的塔吊折断、船舶的舰体、航空器的着陆，都是它的地盘。一条完整的链路这样走下来：

```text
几何模型
   │
   ▼
网格模型（离散）
   │
   ▼
载荷与边界条件
   │
   ▼
求解器（固体 / 声学 / 热学 / 光学 / 电磁 / CFD）
   │
   ▼
结果数据
   │
   ▼
后处理（云图 / 流线图 / 矢量图 / 曲线）
```

读图：前四步是前处理加求解，后面两步是结果数据与后处理。注意载荷与边界条件插在求解之前——它决定模型怎么被“驱动”，缺了这一步，再好的网格也只是一个静态的壳。

**几何建模。** CAE 关注的是物理场景里的某一个个体：公路上两车相撞，真正要分析计算的只是那辆车。物理仿真里的几何模型多是 OBJ 这类格式；CAE 里则用 UG、SolidWorks、CATIA 这些工业三维建模软件建出来。

**网格。** 有了几何模型再剖网格，这一步和物理仿真类似。

**边界条件与载荷。** 这是整条链路里最关键的一步：告诉求解器哪些地方受约束、哪些部件能动。空间里六个自由度——x、y、z 三个平动，绕 x、y、z 三个转动——哪些放开、哪些锁死，再由施加的力或速度把车推起来。约束交代不清，算出来的结果就没有意义。

**求解与数据。** CAE 软件跑完，得到一系列仿真数据。这些数据不是拿来看的，是要指导实际产品研发的：工程师基于它们做大量分析、提改进方案。

汽车安全星级就是一个现成的例子。买车时听到的 C-NCAP 五星、四星、三星，背后是设计研发阶段一轮又一轮的 CAE 仿真：碰撞时某处变形量、侵入量偏大，就说明那块要加强，改完再算，直到拿到想要的星级。这就是 CAE 帮工程师找薄弱点、提方案、逼近最佳设计的方式。

公司为什么愿意上 CAE？因为它能替代物理实验。计算精度做到物理实验的 80% 到 90%，就足以指导研发——拿计算机模拟一场碰撞，和真拿一台车去撞，结论对得上，研发周期短了，成本也降了。

> **定义**：CAE 是用计算机辅助求解实际工程问题的一套方法，作用是预测和优化产品的设计与制造性能。

我来自湖南大学整车先进设计制造国家重点实验室，手上的软件更多面向汽车，所以后面举的例子大概率都是车，这一点先说明。

先看它替代了哪些实验。汽车研发里要对车身做抗弯刚度实验、抗扭刚度实验和碰撞实验。这里的车身指的是车壳子——去掉发动机、底盘、轮胎这些驱动系统之后剩下的那副壳。三类实验，CAE 都有对应的仿真去替代：抗弯刚度计算替代抗弯实验，抗扭刚度计算替代抗扭实验，碰撞仿真替代碰撞实验。算完得到的是一张带物理量的云图，比如位移云图，一眼就能看出车身在受扭时哪些地方刚度偏差，工程师据此改进。

设计流程也跟着变了。

```text
传统流程
产品规划 → 产品设计 → 产品研制 → 实验验证 → 生产
                 ↑                    │
                 └──── 不合格则改设计 ──┘

引入 CAE 之后
产品规划 → 产品设计 → CAE 验证与优化 → 产品研制 → 实验验证 → 生产
                            │
                            └── 在计算机里改，不必先做出样件
```

读图：CAE 插在“设计完成”和“研制样件”之间。传统主线的毛病是设计出来的产品不一定一次达标——刚度、强度、模态、疲劳稳定性，哪一项不过关都得靠实验暴露出来，再回头改设计、再试制、再实验。有了 CAE，设计一完成就可以在计算机里验证和优化，发现问题直接改模型，不必每改一处就做一次样件、做一次物理实验。换来的是更短的开发时间、更优的方案、更可靠的质量、更低的成本。

这条路还在往前推。汽车行业里，宝马这类企业已经能用全数字化模型加 CAE 完成车型开发，样件和物理实验可以完全不做——基于数模和 CAE 技术开发出来的产品，本身就符合目标性能要求。CAE 的定位正在从“辅助设计工具”，变成融入正向研发流程、引导设计的一环。

### 一辆车上能算些什么

把汽车上的 CAE 分析摊开，大概是这样一张清单：

| 分析类型 | 它回答的问题 |
| :--- | :--- |
| 环境舒适性 | 空调吹着舒不舒服、隔音好不好、减震降噪行不行 |
| 安全性 | 撞的时候车里的人保不保得住 |
| 人机工程 | 坐姿、方向盘、档把、按钮顺不顺手，会不会和动作轨迹干涉 |
| 结构刚度与强度 | 够不够硬、够不够稳 |
| 模态 | 结构怎么振动，噪声从哪来 |
| 响应与疲劳 | 跑几万公里之后会不会裂 |
| 温度场 | 发动机热不热、散热够不够、零部件是否在可靠温度区间 |
| 振动噪声 | 车厢空腔里哪吵哪静 |
| 空气动力学 | 风阻系数多大，能耗能降多少 |
| 碰撞与冲击 | 侧碰之后车损成什么样 |
| 工艺分析 | 这块钢板冲压会不会裂、会不会起皱 |
| 可靠性 | 整套结构在长期使用中稳不稳 |
| 多学科优化 | 算出来的数据怎么反哺结构设计 |

刚度强度这一条最传统：刚度通俗讲就是它够不够硬，强度就是它够不够稳。模态属于动力学分析，解决的是结构振动和噪声问题——坐在车里，隔音降噪的能力怎么样，看的就是这一层。响应分析则对应到虚拟实验里的疲劳问题。

**虚拟实验**值得单说。它的感觉像玩极品飞车：在一个虚拟场景里开着车在路上跑。但游戏里那种跑，多数还停在物理仿真层面，把车身简单的变形、画面上的现象表达出来就够了。CAE 的虚拟实验更细：同样是让车在路上跑，它不是白跑，它要给出跑完几万公里之后各项性能指标的变化，最典型的是疲劳程度——哪些结构件长期处在振动当中，会不会开裂。为此，整条道路的数据得先拿进来，而且不只是路面图像，路面坑坑洼洼的实际特征都要进模型，车在这样的路面数据上跑，评出来的疲劳结果才可信。

**冲压成型**是另一件容易被忽略的事。车身那些非常漂亮、非常美观的外形，起点是一整块平的钢板，靠两个带造型的模具对压，钢板跟着模具的型面变形，就压出了车身的样子。这个工艺过程也能算：分析结果一片绿，说明当前工艺设计得很好，整车特征都加工得出来；一旦出现别的颜色，尤其是红色，就说明有问题——红色处可能在加工中开裂，因为钢板变形太大，也可能是钢板挤到一起起了皱。

**风阻**关系到燃油经济性和电动车的能耗。要把能耗压下去，就得尽量降低风阻系数，这是 CFD 流体分析的活。物理仿真里常用 SPH 这类方法做流体；工业 CAE 里用得更多的是 FEM、FVM，边界元 BEM 也占一席之地。

**振动噪声**关注的是空腔内部的声场分布：设计出来的这辆车，运行过程中每个位置的噪声怎么分布、哪里小哪里大，据此指导设计。至于**多学科优化设计**，它是 CAE 领域里另一类软件——把各类分析得到的数据反哺回结构优化设计，让前面的计算真正落到结构上。

### 三个问题，和三段式流程

看到这里，CAE 在工业产品开发里的分量已经很清楚了。但作为一个研究者、一个学习者，光知道它能用还不够，得先在心里挂上三个问号：

1. CAE 有没有理论上的缺陷？
2. 它能不能、又是如何模拟出完全真实的情况？
3. 我们该怎么正确认识 CAE，又该怎么正确使用 CAE 软件？

学物理仿真的时候其实也该问同样的问题。带着这三个问号往下走，先看 CAE 分析最基本的流程——就三部分：前处理、求解、后处理。

**前处理**是几何建模、网格剖分、施加载荷和边界条件。建模和剖分前面说过；载荷与边界条件那一步，是把六个自由度里的约束关系交代清楚，再给车施加力或速度让它动起来。

**求解**按物理场分家：固体力学、声学、热学、光学、电磁学，加上 CFD 流体力学，问题不同，用的求解器不同。每一个求解器内部又是一套复杂模块：

```text
                    ┌─ 数值算法与单元计算理论
                    ├─ 材料本构模型
   一个求解器 ──────┼─ 接触算法
                    ├─ 非线性迭代技术
                    ├─ 连接与约束关系
                    ├─ 边界与载荷条件加载
                    └─ 方程组求解 + 并行计算
```

读图：这七块合起来才是一个能算的求解器。材料本构模型负责把“这个对象是钢的、铁的、铝的，还是布料、木头、水泥”表达成数学；接触算法负责检测两个物体有没有碰上；连接与约束负责把上万个零件按零件—部件—整机的层次连起来——一整辆车不能当成一个整体去建，得分开建再连；方程组求解和并行计算决定算得多快，GPU 并行、CPU 并行、多核并行这些在物理仿真里用熟的技术，搬到 CAE 里一样成立。接触算法和非线性迭代这些先放一放，有个印象就行，后面讲力学基础时会碰到。

**后处理**是把求解结果变成人能读的东西——云图、流线图、矢量图、曲线。

看到这个架构，应该能联想到我们的发动引擎 PeriDyno：它也是基于节点的，也是把一个个功能模块拼成一条流程。所以完全可以在 PeriDyno 里做增量式的集成开发，把这样一条 CAE 仿真计算的流程搭出来。CAE 软件和 PeriDyno 之间的关系，大概就是这么个关系。

### 把求解器拆开看

再往里展开，就专业一些了。求解器里排在最前面的三块值得细看一眼：数值算法、单元、材料。

#### 数值算法与 CAD/CAE 一体化

CAE 分析里第一大块是数值算法和单元计算理论。图形学里用得很多的 SPH、MPM 这一类方法，在这里也有一席之地。

另一条思路是 CAD/CAE 一体化。前面那些分析都要先把模型转成特定格式的数据，那能不能直接基于 CAD 模型做 CAE 分析？对应的答案就是等几何分析 IGA，以及边界元 BEM 这一类方法。

#### 单元就是网格

单元这个词听着陌生，其实它等价于物理仿真里的 mesh、网格、片元——把模型切成的那一小片，在有限元里就叫单元。切出来的形状不同，单元就分家：

| 单元类型 | 对应的形状或对象 |
| :--- | :--- |
| 一维单元 | 杆单元、梁单元 |
| 平面单元 | 三角形、四边形 |
| 实体单元 | 四面体、六面体、三棱柱、四棱柱 |
| 板壳单元 | 板、壳这类薄壁构件 |
| 特殊单元 | 刚体单元、弹簧单元 |

刚体单元是把整个模型当成一个刚体，假定它不变形；弹簧单元则是给弹簧仿真准备的专门单元，直接引进模型里参与计算。这两类在通用单元之外各管一摊。

> **提示**：物理仿真说 mesh，有限元说 element，指的是同一个东西在两个语境下的名字——都是连续体被切出来的那一小块。先把这个对应关系记住，后面看有限元模型就不会觉得它是另一套东西。

#### 材料模型：应力与应变之间的那本账

材料模型这块和物理仿真高度一致：线弹性、超弹性、弹塑性，物理仿真里有的那一套，这里都有。区别在于 CAE 会把精度更高的本构模型接进整个分析流程。

它要回答的问题很朴素：这个零件是钢的、铁的、铝的，还是布料、木头、水泥？同样的受力，不同材料给出的反应完全不同，决定这件事的就是材料本构模型。

> **定义**：材料本构模型描述的是应力和应变之间的行为关系——给定一个应变，材料回给你多大的应力，全靠它来表征。

### 顺带回答一个提问：自动驾驶仿真落在哪一层

有同学问到自动驾驶的仿真。这块在 CAE 里主要落在多体动力学这个领域：用 ADAMS 这类软件，把汽车主要的传动部件建成一个多体动力学模型，就能模拟车在路上行驶时的转向、侧倾和稳定性——快速转弯、快速行驶时，结构反应灵不灵敏，车身稳不稳，高速过弯会不会侧翻，都能算出来。这是在设计完传统结构之后还要过的一道关。

再往自动驾驶那一层走，就是多领域协作了。我带本科生做毕业设计时就有类似题目：在道路场景里布置 V2X 传感器，或者用图像识别判断前方有没有障碍物，把障碍物的信息变成一个信号，喂进建好的动力学模型，再由模型驱动汽车执行操作指令，整条自动驾驶的模拟就转起来了。这件事 CAE 技术是能做到的。

### 有限元：够用就好的工程数值方法

CAE 分析里最关键的技术是有限元方法，finite element method，FEM。

> **定义**：有限元方法是用数学近似的方法，对真实的物理系统进行模拟，是求解数学物理方程的一种基本计算方法。它从固体力学起步，随后扩展到流体、热、电磁等领域。

这里有个容易被绕晕的地方。前面说 CAE 的精度要求高于物理仿真，可有限元本身却被称作一种“工程的数值计算方法”。工程数值方法的意思是：它要满足实际工程的需要，就必须有很高的普适性——什么形状、什么材料、什么工况都能算。普适性和精度是要交换的，为了普适，它必然牺牲一部分精度。

拿 1+1 举例。数学上 1+1=2，这是精确解，结果就是真实值。可如果我用一套工程算法去搭个计算流程算 1+1，算出来可能不是 2，而是 1.9999，差了万分之一。这点误差在工程上完全可以用——它能指导实际研发、能满足工程需要，那它就没问题，尽管精度不是百分之百。

> **提示**：不要因为“1.9999 不是 2”就否定有限元。工程仿真追求的是误差可控、结论可用，不是数学上的恒等。真正该警惕的是误差大到改变了设计决策，而不是误差本身存在。

有限元的分析步骤分三段：结构离散化、单元分析、整体分析。先抛出这三个关键词，一个一个来。

### 离散化：把连续体切成能算的小块

离散是第一步，也是最好懂的一步：把原来的连续体切开。

足球就是现成的例子。球面本来是一个连续的圆面，可足球上画满了黑白格子——这一画，连续的表面就被离散成一个个小块了。这个思路古代就有，算圆周率的时候用的就是它。

有限元模型上看得更直接：一个原本整体的刚体模型，用前面讲的四面体单元去切，切成很多小区域，用这些小特征去近似完整的特征，这就是离散。

梯子更能说明问题。真实的梯子由几根木柱和几块踏板构成；到了有限元里，它变成线段加红点。

```text
   真实梯子                     有限元模型

   +---------+                 o----o----o
   |         |        =>       |    |    |
   +---------+                 o----o----o
   |         |                 |    |    |
   +---------+                 o----o----o
```

读图：两个模型看起来很像，实际上是两种东西。真实系统是木柱和踏板，有限元模型里只剩下线段和点——木柱变成了线段，踏板与木柱的连接处变成了点。

每一条黑色线段是一个单元；单元与单元之间靠红色的点连接，那个点叫节点。节点是整个模型的着力点：它能承受载荷，也有自由度——空间里 x、y、z 三个平动，加上绕 x、y、z 的三个转动，一共六个。整个系统的运动，是通过节点被牵引出来的。

自由度还能直接数出来。一个节点六个自由度，两个节点就是十二个自由度，整个模型的规模由此确定。有多少节点、每个节点放开几个自由度，决定了这个模型最终要解多大规模的一个方程组。

> **易错点**：算模型自由度时，是节点数乘以每个节点的自由度数，不是节点数本身。两个节点、每节点六个自由度，得到的是十二个自由度。

一维问题最能看出“分段”这件事：一条线段，按几何离散切成若干段线段，段与段之间就是节点，整条线的行为由这些节点串起来描述。

离散只是第一步。切完之后，每一小块（单元）内部怎么用节点位移去插值出整个单元的变形，是单元分析要干的事；把所有单元按节点拼回一个整体、组装成方程组再求解，是整体分析要干的事。连续介质力学真正登场的地方，就在这两步里。

## 从离散到组装：工程 CAE 仿真的全景
> 对应块：BLK18 | 覆盖分集：P09下 | 块标题（分集名）：《9. 工程CAE仿真连续介质力学基础》

先从一个线段说起。把一根线段看成一个单元，这是最朴素的一维情形。二维呢？拿一个圆、一个椭圆来说，我们照样能做几何离散：把它画成一堆三角形，用一个个三角形的软构件，拼回原来的形状。三维同理，用一个个六面体，把实体离散成若干六面体的集合。

但这里有一件事必须一开始就看清楚：离散后的模型和原来的模型之间是近似关系，不是一对一完全吻合。边界上最明显——我们是用直线去拟合曲边，误差一定存在。这正是有限元的本性：它是一种近似求解技术。

### 离散：用有限个单元逼近连续体

那为什么非要这么切？你们想一想：我不管你这个面多么复杂，是不是都可以用一些或大或小、或多或少的三角形，把你的几何区域铺满、离散掉？这就是它最大的用处——能处理非常复杂的几何问题。

这些基本构件，就是单元。有限元这个名字说白了就是有限个元素，数量有限的单元。

> **定义**：单元是离散几何用的基本构件。有限元就是把连续体切成数量有限的单元，在每个单元上建立方程、求解，再组装回整体——它是近似求解，不是精确解。

单元还有一层好处。原来那个用各种曲线、曲面都很难描述的区域，被换成了若干个相对规则的标准构件；我每次计算，只需要在这个标准构件上建立力学方程、做求解，不必直接面对那个复杂形状。

于是单元内部的分析就形成了一个闭环：

```text
节点位移
   │
   ▼  形函数插值
单元内部各点位移
   │
   ▼  几何关系
单元应变
   │
   ▼  材料本构
单元应力
   │
   ▼  等效分配到节点
节点力
   │
   ▼
新的节点位移
```

读这张图要抓住一点：它是一个循环，不是一个单向流程。节点位移经插值变成单元内各点的位移，再由几何关系算出应变；应变经本构模型换成应力；应力等效分配到节点上成为节点力；节点力又推动下一轮的节点位移。

每一步都不是凭空来的。一个三角形三个节点各自产生位移，整个三角形的形状必然改变——形状改变，就是应变。三个角点一动，内部每一点动多少，靠插值函数算出来。有了应变，本构模型告诉你这种材料会因此产生多大的应力。应力分布在单元内部，要送回节点，才能和外部的载荷、约束放进同一套方程里。

单元算完了，怎么回到整体？假设离散出十个单元，就有十份单元上的力学方程；解完之后要把它们拼起来——这就是组装。具体来说，是从单元刚度矩阵组装出整体刚度矩阵。

拿一个大三角形举例：计算时把它剖成 1 号、2 号、3 号、4 号四个单元，每个单元单独算，算完再全部拼回一个整体。这一步的公式推导放到后面讲具体力学基础时再展开，但思路现在就要立住。

> **结论**：有限元的全部套路就是六个字——先离散，再组装；它交给你的是近似解，不是真值。

### 精度与效率：一对绑在一起的指标

怎么正确认识 CAE？两个指标绕不过去：计算精度和计算效率。

先说精度。CAE 用的是工程数值分析算法，得到的解本身就是近似解。目前很多问题基本实现了从 0 到 1——先能算。像自动驾驶这种很前沿的问题，它也能算。但它毕竟在理论上还有不成熟的地方，在很多场景里，计算精度还是有限的。

再说效率。在 CAE 分析里，计算效率和精度是成正比的：精度要往上提，计算时间就得跟着涨。前面讲离散时说过曲边：如果只用两个单元去逼近一条曲边，误差必然大；要减小误差，就把网格尺寸变小，多加点、多连线，结果就更贴近真实模型。但离散完每个单元都要计算——你增加十个单元，就要多算十次单元的时间量。精度上去了，效率必然下来。

所以它是一把双刃剑，是个矛盾体。

好在实际工程分析里，我们并不要求一定达到百分之百或者 90% 这么高的精度。有时候 70%、80%，在特定的过程中就能满足要求。这一点很关键：CAE 不追求绝对真值，而是在可接受的误差内给出能用的判断。

各类仿真分析的水平大致是这样：

| 分析类型 | 精度 | 效率 |
| :--- | :--- | :--- |
| 静刚度、静强度 | 90% 以上 | 较快 |
| 模态 | — | 快 |
| 疲劳、裂纹 | 约 75% | — |
| 流体、碰撞 | — | 慢 |

空着的地方表示这一类没有给出具体数字。这些数据可能有点老了，但可以做个参考：静刚度、静强度这类静力学分析，精度可以到 90% 以上；疲劳、裂纹这类问题，大概只能到 75%；模态计算比较快；流体、碰撞仿真就慢得多。

> **提示**：看一个 CAE 结果，先问两件事——它算的是哪一类问题，我要求它准到什么程度。脱离这两点谈“准不准”，没有意义。

### CAE 软件为什么难做

CAE 技术离不开 CAE 软件。从 CAD 模型，到 CAE 仿真模型，再到 CAE 性能分析，中间这两步都要靠工业 CAE 软件来完成。

大家做图形学多，接触 CAD 可能更多一点；但 CAE 软件同样重要，而且是国内目前比较缺的一类工业软件。工业软件是个卡脖子问题，这一点大家都知道。现在大概 95% 的 CAE 软件是国外的商业软件，国产的还处在快速发展和起步当中。

#### 从 NASA 的内部工具到商业软件

最早的 CAE 软件是美国 NASA 提出来的。他们最初是为了辅助自己的飞行器、飞机设计研发，做了一些内部工具，后来逐步演化成国际上大名鼎鼎的 NASTRAN。

今天的仿真软件覆盖面非常宽：电池分析、结构优化、多体动力学、机械传动、冲压仿真这些工艺仿真，每个领域都有各自的软件，也都有行业里领头的那个产品。

#### 为什么这门课要接着 PeriDyno 讲 CAE

有两个历史原因。一方面，我和何晓伟老师一直有合作，包括共同承担一些国家项目，做的其实就是自主可控的 CAE 软件产品。另一方面，在共同研发的过程中确实发现，PeriDyno 可以提供一个非常快的 CAE 软件研发、学习和应用的平台。所以物理仿真讲完之后，接着用 PeriDyno 来讲 CAE。

#### 难在学科交叉

CAE 软件为什么难？难在它是复杂的学科交叉，中间有一道很大的技术鸿沟。就拿汽车碰撞仿真来说，要开发这样一套软件，涉及的层面非常多：

- 数学：各种数学计算方法、工程中的数值分析方法、有限元计算；
- 网格：网格剖分；
- 求解：大规模线性方程组的求解；
- 物理：材料、本构等物理学知识；
- 计算机：并行计算、图形学；
- 工程：理解汽车碰撞的实际工况和真实场景。

少一样都做不成。这也是为什么 CAE 的产业覆盖面非常广：从深海到太空，从民用到军工，从小型民企到大型央企，都在用。问题的跨度也大：可能拿它算一个纳米级的器件，也可能算一艘千米级的航母。共性技术是一样的，差别在细节。

#### 三个卡点

我们自己的 CAE 发展，卡点主要有三个。

第一是技术积累相对薄弱。以前有国外软件可用的时候，我们的研究更多集中在算法层面；真正落地到软件产品这个层面的工作，做得相对少。

第二是场景迭代不足。大家都习惯用国外软件，就不愿意用国产软件；国产软件没人用，产品迭代就不足，越迭代不足越不好用——这是一个循环。

第三是人才储备匮乏。不管是我们湖南大学在做 CAE 软件人才培养，还是迈曦软件在招聘 CAD 开发人员，都能感觉到现在 CAE 软件的人才非常匮乏。开这样一门线上课程，也是希望能吸引大家一起学 CAE 相关的知识。

#### 巨头与国产厂商

国际上，CAE 软件基本被几家工业软件巨头垄断：西门子、Altair、MSC、达索、ESI。它们的成长路径很像我们玩过的大鱼吃小鱼——不断并购各种小的 CAE 软件公司，把功能点补进来、把实力壮大起来。因为 CAE 涉及的功能点太多，靠自己一个个做太慢，并购是最快的补充方式。

近几年国产 CAE 发展也很快。比如由湖南大学成果转化成立的迈曦软件，还有十沣、索辰，以及几家起步更早的传统厂商，都是国内比较有代表性的公司和产品。

### 一款 CAE 软件的骨架

如果以后要在 PeriDyno 上开发一款 CAE 软件，它大概由哪些部分组成？从软件架构上讲，大的划分和 CAE 仿真流程是对应的：前处理、求解器、后处理。

```text
        ┌──────────────┐
        │    前处理    │  CAD 建模 / 模型接口 / 网格剖分
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │    求解器    │  隐式 / 显式 / 多体动力学
        └──────┬───────┘
               │
        ┌──────▼───────┐
        │    后处理    │  云图 / 动画渲染
        └──────────────┘

支撑：云计算 · 并行计算 · 数学计算库 · 材料与单元库
```

这张图是骨架：数据从几何与网格进来，经过求解器，最后以云图和动画出来；底下那一层是所有模块共用的支撑。

最核心的几块是：前处理模块、求解器模块、材料与单元库、并行计算模块。

#### 几何：不只是导入

几何前处理模块，首先是把构建好的整体模型——比如一艘船、一辆坦克——通过几何接口导入到 CAE 软件里。现在很多 CAE 软件也支持一些简单的几何建模功能，比如点、线、面的创建。

CAE 的建模能力当然比不上 CAD，相对弱一些，但它不可或缺。原因有两个。一是导入 CAD 模型之后，难免要做几何修补：比如模型上本来有个孔，而在 CAE 分析里这个孔作用不大，就可以生成一个面把它补上。二是很多场景需要全自动分析——从几何分析、网格剖分、计算求解到后处理全部自动完成，这就要求几何建模这一块有足够多的软构件、足够多的功能模块，能做参数驱动的几何建模。

#### 网格：生成之后还要调

从 CAD 模型到 CAE 模型，关键一步是网格剖分。要能生成三角形、四边形、四面体、六面体这些网格。生成完还不算完，还要能调整：网格密度要能改，网格要能拉伸，不需要的网格要能删，本来四个网格要能合并成一个。这些是网格剖分模块的常用功能。

#### 求解器与后处理

求解器要按应用场景分：通用结构的隐式求解器、显式动力学求解器、多体动力学求解器，等等。

后处理则要有强有力的渲染模块支撑——CAE 分析结果最后要变成漂亮的动画和云图，靠的就是它。

再往下是支撑技术：云计算（CAE 计算很耗资源，普通用户要靠云端算力）、并行计算（计算量大）、数学计算库（像 BLAS 这类基础线性代数库，以及各种稀疏矩阵求解库）。

### 隐式分析模块的里子

拿迈曦软件的隐式分析模块来讲。线性分析这一块，支持静强度分析、模态分析等功能；此外还有屈曲分析、惯性释放分析、疲劳分析、随机振动分析这些。

#### 单元类型说的是算法，不是形状

单元类型非常非常多，这里要解释一句：单元类型不仅仅按几何形状划分。

同样是三角形单元，几何形状都是三角形，但计算理论可以不一样：一阶三角形的平面应力单元、二阶三角形的平面应力单元、平面应变单元、二阶的平面应变单元……同样一个三角形，有很多种计算方法。

> **易错点**：在有限元软件里提到“单元”，指的不是形状，而是单元计算的方法。形状只决定它长什么样，阶次和平面应力、平面应变的假设决定它怎么算。

选哪种，要看你实际的工况、应用场景和对计算精度的要求。同一个几何体对应多种计算方法，这是正常的。

#### 材料本构要用实验标定

材料本构是对材料物理性质的模拟。开发本构的过程中，要用标准的 benchmark 来测试。

比如单轴拉伸实验：这个实验可以在物理实验机上完成，做完就得到材料在拉伸过程中的应力—应变曲线。本构模型描述的就是应变和应力之间的关系。我们开发一套数值算法，形成本构模型，再用这个本构模型去模拟同样的单轴拉伸，也能得到一条应力—应变曲线。两条曲线一对比，就知道仿真数据和实验数据是否吻合，从而验证本构模型开发得对不对。

#### 接触：先允许穿透，再把它推开

接触在 CAE 里非常重要，在物理仿真里也非常重要——要模拟真实的物理系统，接触必不可少。但两者的接触有差异。

CAE 分析里，有时候会允许一定的穿透。比如罚函数法：一开始先容许穿透，通过穿透量获取接触力；有了接触力，再对物体施加接触反力，产生反向运动，把它们分开。

物理仿真里，像刚体、粒子法，也会采用类似的思想：先算两个点之间的距离，再由距离算力。思路是类似的。差别在于，CAE 接触对数值稳定性的要求非常高——接触反力产生之后，最终要和内力、外力形成一个合力，对整个物理现象做分析。这个合力一旦不稳，整个求解就崩了。

#### 拓扑优化：把不承力的材料拿掉

拓扑优化是 CAE 里一个非常好用的工具。看一个连杆零件：随着优化过程，有些地方的材料被去掉了。为什么？因为反复计算后可以发现，有些地方产生的位移非常小，说明这部分材料对整个零件的物理性能——比如刚度、强度——影响不大。

那就可以把这部分材料去掉。去掉之后达到什么目的？轻量化。零件质量降下来，重量越轻，成本也越低。这是 CAE 一个非常典型的应用。

### 四边形与三角形的取舍

再往深里做，就是一个研究方向：高精度单元算法。

三角形和四面体单元，一方面几何形状不一样，更重要的是计算精度不一样。四边形单元的计算精度要远高于三角形——一般软件里都是这样。

但四边形有个问题：网格剖分困难，三维里对应的六面体更是如此。你们如果熟悉网格划分就知道，要自动剖出一套规整的四边形、六面体网格是很不容易的。所以前面看到的那些模型，大多是由三角形，或者三角形与四边形混合构成的。

于是就有一个思路：三角形可以自动剖分，那我们能不能把三角形的计算精度提上去，用高精度三角形去替代工程中的四边形？这样既降低了前处理——网格剖分——的时间和难度，又尽量不牺牲精度。这一类单元算法研究想解决的就是这个矛盾。

### 求解器：八成时间花在解方程上

任何 CAE 分析，最后都会归结为解一个方程。在 CAE 里，就是解

$$Ax=b$$

通过求解这个方程得到 $x$，得到我们想要的未知量。因此方程组的求解在 CAE 里极其重要——它经常会占到整个 CAE 分析计算时间的 80% 以上。

所以非常有必要开发高稳定性、高精度的方程组求解器，来提高 CAE 分析的精度和效率。高铁、工程机械、船舶，这些领域都有典型的应用。这一块值得单独展开讲，这里先把分量摆出来：它不是一个可有可无的工具，而是决定整套分析能不能算完、算得准不准的主干。

### 显式分析：为大规模变形而生

隐式之外，还有显式分析模块。它主要算什么？算汽车碰撞那类问题。

汽车碰撞涉及非常大的材料变形。这个时候考虑数值稳定性，一般要采用类似中心差分的思想做显式求解。所以一般 CAE 软件里，隐式模块和显式模块都会有。

比如两个管的碰撞、整个模型的挤压过程，再比如子弹打穿一块平板，这些都是基于显式模块来算的。它同样包含各种单元、各种材料、接触计算模块。

显式里的接触计算比隐式更稳定一些。会涉及点面接触、面面接触、单面接触，还有非常复杂的自接触——你们想一想，一个汽车碰撞过程里涉及的接触现象非常多，各种各样的都有。再就是对连接约束的处理。

#### 为什么显式离不开并行

隐式求解的计算效率其实比较好——把方程组解出来就很快。显式不一样，它是一个迭代计算的过程。算一个汽车碰撞问题，可能要涉及数十万次反复计算迭代，计算时间可能要几天，或者至少一二十个小时。

所以必须用并行计算来提高效率。这就涉及 PeriDyno 的底层架构：它所有底层数据采用 CPU/GPU 混合的方式管理，数据既可以直接在 CPU 上用，也可以在 GPU 上用。这样的框架非常适合做 CAE 里的 GPU 并行计算算法开发。

#### GPU 能带来多少

举个大家都有体会的例子：手机掉到地上，它的损坏程度，研发人员是怎么评估的？就是用 CAE 的显式有限元分析模块，去模拟手机掉在地上的过程。这个过程非常耗时。

如果用 GPU 加速，比如用一块 A100，计算速度可以比商业软件跑 96 核 CPU 还快 1.6 倍。所以 GPU 在 CAE 显式有限元计算里，能力非常强。

我们做过的算例还有更多：汽车碰撞、汽车座椅零部件的碰撞、汽车内饰件的真空成型仿真，还有构件受冲击破坏、冲压成型、零部件受冲击力后的变形——这些都是显式模块模拟的。

### 效率的三条战线

CAE 技术的发展趋势，离不开三个关键词：使用效率、计算效率、迭代效率。看得出来，效率最关键。因为企业里的工程师经常要用 CAE，如果每算一次都要等几天、几个小时，工作效率必然很低。

#### 使用效率：让 CAD 和 CAE 不再分家

使用效率要解决的是 CAE 模型和 CAD 模型相分离的问题。做 CAE 分析，先要把 CAD 模型转成 CAE 模型，这个转换本身就很花时间。

工程设计的梦想，是 CAD 和 CAE 无缝集成——直接基于 CAD 模型做 CAE 分析。现在有不少商业软件在做，也有学者在研究这条路。

#### 计算效率：并行与异构

计算效率大家很熟悉，就是并行计算：用 GPU、用超算，或者用 CPU 加 GPU 的异构平台，把整个 CAE 仿真的计算效率提上去。这也是以后在 CAE 领域，你们学的知识可以更多贡献智慧的地方。

#### 迭代效率：只算改动的那一块

迭代效率是什么？产品设计完之后，用 CAE 分析；分析完改进设计，再分析。这个循环里，迭代效率非常重要。

比如一个车门，改来改去，可能只是增加了一个孔。按以前的做法，整个模型要全部重新算一次，很耗时。如果要迭代 100 次，这个车门就要重复算 100 次。

有没有办法提高？有，叫重分析。基本思路是：如果只改了这一部分，就只对这一部分周边做分析，其他地方不重新分析。这样每次迭代的计算量大幅降低，迭代效率就上去了。

除此之外，还要有更多、更好的单元算法来提高计算精度——这就比较专业了，涉及 CAE 非常核心的计算理论。另外，多物理场耦合，比如力、热的耦合分析，也是未来 CAE 软件要解决的关键问题。

### 在 PeriDyno 上长出国产 CAE

围绕 CPU/GPU 异构并行架构来加速 CAE 软件，我们团队做过一些工作。更往前一步，我们基于 PeriDyno 开发了一套 CAE 软件平台，叫 MxSim。

它要解决的是复杂 CAE 任务的增量开发、集成以及模块复用难题：提供一个平台化的工具，把大家在 CAE 各个领域的专长吸进来，都基于这个平台去实现和构建自己的 CAE 软件。比如你是做算法研究的，可以把算法在平台上快速实现、形成软件，从而测试你的算法对不对。

它完全基于 PeriDyno 开发，底层核心框架就是 PeriDyno；我们在此基础上，把 CAE 的前处理、求解器、后处理做了一系列软构件开发和节点集成。最终形成的界面，操作流程和 PeriDyno 很类似，只是搭建出来的流程面向 CAE 分析，而不仅仅是物理仿真分析。

它也能满足云和多终端的需求：PC、移动端、工业元宇宙里的设备，都可以用。端云协同也是 PeriDyno 很好的一个特性，可以支撑协同式的 CAE 软件开发模式。软件可以在码云上下载，后面课程里再仔细讲。

学完这门课，我也希望大家能基于这个平台，开发出属于自己的 CAE 软件。

把这条线串起来看：从一根线段、一个三角形、一个六面体开始，我们把连续体切成有限个单元；在单元上建立方程、求解，再组装回整体，得到一个近似解。精度和效率互相拉扯，于是有了隐式与显式、有了并行与重分析。这些能力最终要落在一款 CAE 软件的骨架里——前处理、求解器、后处理，加上材料与单元库、并行计算。理解了这条链，再看任何一个 CAE 软件，你都能找到它每个模块在干什么。

## 有限元分析背后的力学原理：从胡克定律到五个基本假设
> 对应块：BLK19 | 覆盖分集：P10上 | 块标题（分集名）：《10. 工程CAE仿真中的有限元分析原理》

### 今天要补的是原理这一段

上周我们讲的是 CAE 软件本身——它能干什么、工业界怎么用它，那一讲更偏科普和介绍。再往前一周，大家已经看到 CAE 技术有非常强的工程分析能力：一个还没造出来的零件，在计算机里就能算出它受多大力、变形多少、会不会断。

那它背后的基本力学原理是什么？这就是今天要补的那一段。而且今天讲的这些，是下一次课的地基：下一讲我会结合 PeriDyno 这个平台，以及我们在它上面继续开发的 MechSim，讲具体怎么用这套平台做 CAE 仿真分析。原理不清楚，工具就只是点按钮。

今天的安排分三块：第一块是有限元分析的作用与地位，这个上一讲已经交代过，我快速过；第二块是有限元分析的力学基础，也就是弹性力学；第三块是在弹性力学的基础上，讲有限元本身的基础。

先说清楚：这一讲理论性会比前两讲强一些。但我尽量用通俗的语言讲，尽量拿工程里能对上号的例子，把这个原理说清楚。

### 有限元在工程软件里的位置

工业软件大致分几大类：CAD 管几何绘图，CAM 是计算机辅助制造，CAE 是计算机辅助工程。CAE 干的事，说白了就是在产品的研发设计过程中，用计算机和数值分析的手段来做建模和性能仿真——东西还没造，先在机器里试一遍。

CAE 软件里的数值计算方法不止一种，但最常见的是有限元分析。有限元最早起源于固体力学，后来迅速扩展到流体、传热、电磁这些领域。我们这门课主要围绕固体力学讲，但你们要知道，往流体、传热、电磁那边去，基本的理论和原理是类似的。

有限元的本质是一种数学近似方法：用数学近似去模拟真实的物理系统。这句话里有两个关键词。一个是"近似"——它求出来的不是精确解，而是工程中的数值解；另一个是"通用"——它能解决非常复杂的工程问题，适用面极广。代价就是精度不是百分之百。这一点要一直记着：有限元给你的答案，永远带着近似的前提。

具体怎么做近似？核心是"单元"这个概念，英文叫 element。

真实的零件是一个连续体，上面有无穷多个点、无穷多个未知量，你没法直接算。有限元的办法是把复杂几何用网格划开——划成三角形、四边形、四面体、六面体，用这些网格去逼近原来的几何形状；然后计算不再针对整个连续体，而是针对每一个单元、每一个网格去做，再用这些单元拼出对真实系统的近似。

> **定义**：所谓有限元模型，就是对真实系统做理想化之后得到的数学抽象。

上一讲我用过一个梯子的例子。左边是一把真实的梯子，右边是它的有限元模型：整把梯子被拆成一根根线段。单元和单元之间靠节点连接，载荷也加在节点上——真实系统受到的力，最终都要落到节点上去。每个节点还有自己的自由度：在三维问题里，就是沿 XYZ 三个方向的平动，加上绕 XYZ 三个轴的转动，一共六个。自由度描述的，是一个物理场响应的特性。

有限元能成立，靠的是一个很巧的思路：用有限种类的标准件，去构造任意复杂的对象。

标准件就是各种单元——杆单元、梁单元、三角形和四边形这样的壳单元、四面体和六面体这样的实体单元。种类是有限的，翻来覆去就这些，但组合起来可以逼近任何复杂的形状。这条路线的两个特征，我在上一讲强调过，这里再说一次，因为它是后面一切的前提：

一是标准化。任何复杂的问题，都先做标准化的分解，分解成一个个标准单元，然后在单元上建模、在单元上计算。二是规范化。整个分析路线是固定的、程式化的，不因人而异。

正因为规范，它才能被写成程序。这也回答了那个问题：为什么有限元能在众多数值分析方法里脱颖而出、发展得这么快？计算机化的能力是非常重要的一个原因。它可以做成标准程序，再拆成一个个模块——前处理模块、求解模块、各种单元模块、本构计算模块——最后拼成一个软件。这种结构非常符合增量式的软件架构和模块化编程的思路。也正因为如此，我们才能用 PeriDyno 这样一个增量集成、开放式的平台来做 CAE 仿真，下一讲你们就会看到它的技术路线有多规整。

整条流程可以这样摆：

```text
真实系统（连续体，未知量无限多）
        │
        │  ① 几何建模（CAD）
        ▼
    CAD 几何模型
        │
        │  ② 网格划分：三角形 / 四边形 / 四面体 / 六面体
        ▼
 有限元模型（有限个单元 + 节点 + 自由度）
        │
        │  ③ 单元级建模与计算
        ▼
   单元方程 ──► 组装成整体方程组
        │
        │  ④ 施加边界条件与载荷，求解
        ▼
  节点位移 ──► 单元应变、应力
        │
        │  ⑤ 后处理显示
        ▼
  工程评价：强度 / 刚度 / 稳定性
```

从 CAD 几何到数学模型，中间是力学求解，最后是后处理显示——这就是 CAE 软件里一直在跑的那条链路。

### 一切从胡克定律说起：弹性与塑性的分界

讲弹性力学，从最简单的定义开始：胡克定律。它说的是一件事——弹性体的变形与外力成正比。

拿弹簧看最直观。一根弹簧受拉就会张开、会伸长，这个伸长量和拉力之间是正比关系。写成式子就是

$$F = k\,\Delta x$$

其中 $F$ 是施加的力，$\Delta x$ 是伸长量，$k$ 是弹性系数，它代表这个弹性体的变形能力。力和变形量之间是线性关系，画出来就是一条过原点的斜直线。

但这条直线只在一定范围内成立。你们小时候有没有玩过弹簧？拿一根弹簧，用很大的力气去扯，扯完之后就发现它回不去了，等于被拉直了。力气小的时候拉一下，一松手它弹回原样；力太大，弹簧拉直，就再也回不到那个样子。

这里面就分出了两个阶段。

弹性变形阶段：力与变形成正比；而且关键是——外力去掉之后，变形可以回到原来的样子，弹簧恢复原状。

塑性变形阶段：力与位移不再是线性关系，可能是个很"随机"的、抖动的曲线；更重要的特征是卸载回不去——力撤掉了，变形留在那里，保持着现在的样子，或者略有变化，反正回不到原样。

> **结论**：判弹性还是塑性，不只看"力与变形是不是成正比"，还要看"卸载后能不能恢复"。前者是过程特征，后者是本质特征。

那为什么我们上来先讲弹性？因为从学习的角度讲，弹性这一段最简单、最规整，也是整个理论体系的入口。塑性的账要难算得多。

### 力、结构与变形：把词汇表立起来

#### 力的三要素与几门力学的分工

力这个概念，你们从初中、高中到大学都学过，但后面所有的推导都绕着它转，所以我们快速过一遍。

力是物体间的一种相互的机械作用。它作用的结果，是使物体的形状或者运动状态发生改变。注意这里其实有两种效应：一种是运动状态改变，那是运动效应，归理论力学研究；另一种是形状改变，那是变形效应，归材料力学、弹性力学研究。

正因为研究对象和假设不同，力学分成了好几门：理论力学、材料力学、结构力学、弹性力学……同样是"力"，在不同假设、不同研究对象下，采用的研究方法是不同的。这一点在后面体会会越来越深。

力有三个要素：大小、方向、作用点。它是有方向的量，所以是矢量，用矢量符号表示。单位是牛顿。

#### 三类研究对象：杆件、薄壁、实体

弹性力学的书里一上来就按几何特征把研究对象分成三类，这个分法很有用，因为它直接决定了你用哪门力学。

| 结构类型 | 几何特征 | 典型例子 | 用什么力学研究 |
| :--- | :--- | :--- | :--- |
| 杆件结构 | 长度远大于横截面尺寸 | 上一讲那把梯子（简化成杆单元） | 材料力学 |
| 薄壁结构 | 两个方向尺寸远大于厚度；平的叫板，曲的叫壳 | 平板、各种壳体 | 弹性力学 |
| 实体结构 | 三个方向尺寸基本相当 | 地基、水坝、挡土墙、变速箱箱体 | 弹性力学 |

杆件结构就是长度远大于横截面积，长比宽、比高都大得多，这时可以把它看成一根杆。薄壁结构的特征是长和宽远大于厚度，它像一块板：面是平的叫板，面是曲的叫壳，两种都归到薄壁结构里。实体结构最直白，三个方向的尺寸差不多大。

#### 杆件的几种基本变形

回到杆件，看它受各种外力会产生什么样的变形。

轴向拉伸或轴向压缩：外力沿着杆的轴向。拉伸时，轴向伸长——这一点谁都知道；但同时一定要注意到，垂直于轴向的横向却在缩小，杆变窄了。反过来，受压时轴向缩短，横向反而变宽。这个"一伸一缩、一缩一伸"的横向效应，后面还会反复出现。

平面弯曲：杆受到弯曲，会随着约束方式、支撑点的不同，产生连续的弯曲变形。实际工况里往往不是单一外力，而是组合受力——比如既有弯曲，中间又受到一个集中力，那就会出现叠加起来的变形形态。

剪切：物体受到两个相对的力，表面上就产生剪切力。材料拉伸试验里那个经典现象就是它：拉伸过程中剪切力起作用，试件最终沿 45 度方向断裂。

扭转：绕着一个轴施加扭矩，杆件被拧转。

这几种基本变形，加上它们的组合，就是杆件力学分析的全部"字母表"。

#### 强度、刚度、稳定性

工程上评价一个构件，常用的三个词——强度、刚度、稳定性——很多人混着用，这里必须分清。

强度，是构件抵抗破坏的能力。一个钩子挂上很重的东西，它会不会断？不断，说明强度够。这就是强度在回答的问题。

刚度，是构件抵抗变形的能力。一个支架上面放一个很重的物体，它断不掉，但会不会被压矮、被压变形？变形太大，就是刚度不够。

> **提示**：强度管"断不断"，刚度管"变不变形"。强度是我有多硬，刚度是我撑得有多稳——一个防的是破坏，一个防的是过量变形。这里的"稳"说的是不变形，和下面单独定义的稳定性不是一回事。

稳定性，是构件保持原有平衡状态的能力。受到外力加载时，它能不能始终维持原来那个平衡状态。这个概念在课程里提得相对少一些，但在细长压杆、薄壳这类问题上它是主角。

在有限元分析里，我们最常做的还是刚度和强度这两类计算。下一讲用软件的时候，你们会反复看到强度分析、刚度分析，还有模态分析。

### 弹性力学研究的是什么

前面铺垫完了，正式进入弹性力学。它到底研究什么？

弹性力学研究的是：弹性体在外界因素——包括外力的作用、温度的变化、边界的约束等等——的影响下，其内部所产生的应力、形变和位移。一个弹性体在外界作用下，内部会产生怎样的应力、形状会发生怎样的变化，这就是它的题目。

所谓弹性体，是只有弹性性质的一种理想物体。它的变形与力成正比；外力撤销之后，变形能够恢复、回到原来的状态。它的性质就是前面讲的那一条：应力和应变之间存在一一对应的关系——没学过应力应变的同学，先把它理解成力和变形之间的一一对应；而且作用去除之后，能回到原来的状态。

研究对象比杆件宽得多：板、壳这样的薄壁结构归它管；土木里的地基、水坝、挡土墙这样的实体结构也归它管；到了工程里就更多了——发动机的机壳、变速箱的箱体、各种汽车的车身，都是实体结构。

这里要说明一个层次差别。上一讲分析楼梯，我是直接用杆单元去简化它的，把一个楼梯转化成几根杆，那是杆件层面的简化。用弹性力学来研究，就会做更精密的处理：不会只当作一维单元，而可能用二维单元、三维单元去分析。

弹性力学的研究任务，可以归成三句话。

第一，分析结构物和构件在弹性阶段的应力和位移。

第二，校核它是否具有所需的强度、刚度和稳定性。

第三，寻求或改进计算方法，采取最优方案去解决安全与经济的矛盾。

我为什么要把"研究任务"这样总结一遍？其实是想让你们再回到上一讲讲过的那个话题：工业仿真和物理仿真的区别。

CAE 仿真里，我们的目的是分析出应力和位移——它受了多大的力、变了多少形。物理仿真里，我们同样能算出力和形状的变化，那也是位移。但工程里我算完之后还有下一步：把这个结果转化成一个评价——它的刚度够不够、强度够不够、稳定性够不够。

物理仿真，在很多场景里——电影、游戏——更多是视觉上、图形上的近似，看着像就行。这里不一样，我们要把它反馈到具体的物理性能上，还要进一步寻求和改进计算方法。

"改进计算方法"这句话什么意思？就是当我分析完，发现刚度不够、强度不够，我一定要回去改。比如我设计完一个结构，算出来刚度太低、达不到预期目标，那就要根据仿真结果改进结构，把强度和刚度提上去。

至于"解决安全与经济的矛盾"，这是计算机仿真非常重要的一个特点，也是它在工程界立足的理由。为什么在汽车行业——我比较熟悉的行业——它的应用这么广泛？因为通过计算机仿真，能拿到一个最优方案，而不需要去做大量的实验，也不需要靠堆一个非常高的安全裕度来保平安。

打个历史的比方。以前在军工里——现在情况也不一样了——造一架飞机、造一辆坦克，其实不太需要 CAE 分析。为什么？坦克这种产物，我不太追求轻量化，也不太追求燃油经济性，它是小批量生产的，我完全可以把结构做得非常扎实，凭工人的经验就做得很扎实，安全和性能肯定够，它不需要考虑经济性。飞机不一样，旋翼飞机要考虑轻量化、要考虑起飞重量，那就必须算。

到了民用产品，就由不得你这么干：既要安全，也要经济性。这个矛盾，靠经验拍脑袋是解决不了的，只能靠计算去找那个最优点。

### 材料力学与弹性力学的分野

这里插一段对比。学工程的同学大多是按"理论力学 → 材料力学 → 弹性力学"这个顺序走过来的，我自己读书时也是先上材料力学、再上弹性力学，材料力学大概是大三、大四的课。两者到底差在哪，值得单独说清楚。

| 对比项 | 材料力学 | 弹性力学 |
| :--- | :--- | :--- |
| 研究对象 | 杆状结构 | 实体结构、薄壁结构 |
| 研究范围 | 弹性阶段，还延伸到塑性阶段、疲劳等问题 | 主要研究弹性阶段 |
| 研究方法 | 对应力分布或变形状态做近似假设 | 从基本假设出发，做精确分析 |
| 结果精度 | 往往是近似的、初等的，只能在特定条件下使用 | 更精确，还可以用来校核材料力学的结果 |

材料力学的做法是：先对应力分布或者变形状态做一些近似的假设，然后推公式。这样得到的结果往往是近似的、初等的，只能在一定的条件下使用。教材里印象最深的就是那张表——列一堆常用结构受某种载荷的情形，你直接代入经验公式，就能算出一个近似结果。够用，但它是在"套表"。

弹性力学不一样。它从基本假设出发，对物体的应力和变形做精确的分析，得到的结果更精确。也正因为更准确，它有时反而被用来校核材料力学算出来的结果。

### 五个基本假设：把问题压成线性

接下来是这一讲最要紧的部分：弹性力学的五个基本假设。

为什么要有假设？因为我们希望用数学工具来研究弹性力学。而真实材料在微观上并不连续，真实的变形过程也复杂得没法直接写方程。所以必须先做理想化，把问题"修剪"成数学能处理的样子。

> **提示**：这五个假设后面会被反复引用。凡是讲到"为什么这里可以这样算"，答案基本都落回这五条上。

#### 连续性假设

连续性假设说的是：从宏观上看，物体是连续的。

在整个物体内部，物理量——应力、应变、位移——都可以表示成坐标的连续函数。比如正应力 $\sigma_x$，它就是坐标 $x$ 的连续函数。

为什么非要假定它连续？因为只有这样，推导时才能用连续和极限的概念，才能用微积分、用微分这些数学工具。如果材料是不连续的，函数就不可导，极限也求不了，方程根本立不起来。

#### 完全弹性假设

完全弹性假设说的是：物体产生变形之后，把外力去除，物体能够完全恢复原形。

它带来一个很强的推论：在温度不变的前提下，物体在任何一个时刻的形状，完全取决于该时刻所受的外力，与它过去所受的历史无关。换句话说，材料没有"记忆"——现在的形状是现在的力造成的，不是前面某一刻的力留下的结果。这一条大家要记住。

这里面其实分两个层次：线弹性阶段和完全弹性阶段，对应的两个材料参数是比例极限和弹性极限。

这个假设最要紧的意义在于：它使得本构方程——描述应力和应变关系的那组方程——是一个线性方程。这为后面用数学工具做计算和推导带来了极大的便利。

实际材料当然不都是理想弹性材料，有脆性的，也有塑性的。但它们在一定范围内都可以用弹性力学来研究。

脆性材料，只要应力没有超过比例极限，还处在下面那段线弹性阶段，就可以近似当成完全弹性体来分析。

塑性材料，只要应力没有超过屈服极限，还在线性阶段，同样可以用弹性力学研究；一旦超过屈服极限、进入塑性变形阶段，就得换塑性力学去分析了。

#### 均匀性假设

均匀性假设说的是：整个物体由同一种材料构成。

比如汽车里的一个变速箱箱体，它是由同一种金属材料做成的。假定它是同一种材料，就保证了物体各个部分具有相同的物理性质，弹性常数——弹性模量和泊松比——不会随着位置、坐标而改变。

这个假设的好处，到后面写程序的时候你会非常直观地看到：那些刚度矩阵之类的矩阵，就可以做模块化的表达。

还有一个更根本的好处：因为整个物体是同一种材料，所以我可以取物体中任意的一小部分来分析，再把分析结果用到整个物体上去。

有同学可能会问：为什么我只算某一个单元，就敢把结果推广到整体？答案就在这条假设上——因为整体是同一种材料。

#### 各向同性假设

各向同性假设说的是：分析对象上的每一个点，在不同的方向上，都具有相同的物理性质和机械性质。

也就是说，一个材料在 X、Y、Z 各个方向上表现一致，弹性模量和泊松比这些弹性常数不随方向而改变。

> **易错点**：均匀性和各向同性最容易混。总结成一句话——均匀性假设的是材料参数不随坐标变化；各向同性假设的是弹性常数不随方向变化。一个管"走到哪都一样"，一个管"朝哪看都一样"。

#### 小变形假设

小变形假设：物体受力之后，所有点的位移都小于物体的原有尺寸。

举个悬臂梁的例子。一根悬臂梁受力后发生一点形状改变，原来在 A 点的位置变到了 A′ 点。这个变形要夸张地画出来才看得清，实际工程里的位移量相对原尺寸是很小的——所有点的位移量都小于物体原有的尺寸。

这条假设换来两个好处。

第一个好处：建立平衡方程时，可以直接用变形之前的尺寸，近似代替变形之后的尺寸，而不产生显著的误差。肯定有误差——尺寸本来是变长了的，我为了简化还用原来的长度去算，当然有偏差；但这个偏差可以接受。

第二个好处：考虑物体变形时，应变和转角的平方项、乘积项这些高阶项，比如 $x^2$、$x \cdot y$，都可以忽略不计。高阶项一扔，弹性力学里的微分方程就变成了线性方程，可以直接求解。

注意这两个好处的方向是一致的：完全弹性假设保证了本构方程是线性的，小变形假设保证了其余那些微分方程也是线性的。整个体系一起线性化。

于是，在连续性、完全弹性、均匀性、各向同性、小变形这五条假设之下，整个弹性力学问题就成功地转化成了一个线性问题。

```text
连续性假设   ┐
完全弹性假设 ├──► 本构方程是线性的
均匀性假设   ┤
各向同性假设 ┤
小变形假设   ┘──► 几何方程、平衡方程线性化
                    │
                    ▼
          弹性力学问题 → 线性问题
                    │
                    ├──► 求解：解线性方程组即可
                    └──► 叠加原理：多组载荷的效应可直接相加
```

图里左边是五条假设，它们合力指向同一个结果：本构方程线性、几何方程与平衡方程线性化。两条线汇到同一个出口——整个问题变成线性问题，再往下分出求解和叠加两个红利。

### 五个假设的回报：叠加原理

线性问题有什么好处？一个是求解上方便，另一个更关键：可以直接使用叠加原理。

叠加原理说的是：在线弹性和小变形的条件下，作用在物体上的几组载荷所产生的应力和变形的总效应，等于单独每组载荷作用效应之和。

举个例子。一个物体同时受三组载荷：外部施加的一个力 $P$、物体内部的体力 $Q$、以及边界上一段非均匀分布的载荷。这三组载荷一起作用，直接求解很麻烦。用叠加原理，就把它拆成三个问题：单独算边界分布力作用下的应力和变形；单独算体力 $Q$ 作用下的应力和变形；单独算外力 $P$ 作用下的应力和变形；最后把三个结果累加起来，就是原来那个复杂受力情况下的总效应。

这个原理后面会反复用到——它是线性体系送给我们的一份大礼。

### 外力、内力与应力

最后一部分是几个基本概念，这些后面会一直用，但我讲快一点。理论课不适合上得太长，时间一久大家注意力就散了，所以挑重点讲，纯概念性的快速过。

#### 外力：体力与面力

外力，是其他物体对研究对象的作用力。研究对象之外的、别的物体给它的力，都算外力。它分两种。

体力，是分布在物体体积内的力，比如重力、惯性力、电磁力。它用单位体积内的力来度量，是矢量，方向沿着力的方向。把它按三个坐标方向分解，合力就是三个分量的平方和再开根号：

$$F = \sqrt{F_x^2 + F_y^2 + F_z^2}$$

方向以沿坐标正向为正。

面力，是分布在物体表面的力，比如流体压力这一类作用在表面上的分布力。它用单位面积上所受到的力来度量，同样按三个方向平方累加再开根号，以指向外法向为正。

> **易错点**：体力和面力都是"集度"——表示的是单位体积、单位面积上的作用力，不是总的合力。所以在考虑平衡条件、做求和的时候，必须乘以相应的体积或者面积。

这一条我自己是踩过坑的。我刚开始学、做课题写有限元程序的时候，人家给了体力和面力的数值，我在计算时就直接把这个物体所受的整体力和面力当成他给的那个值。实际上不是这样：求合力的时候，体力要用单位体积的力乘上体积，面力要用单位面积的力乘上面积，得到的才是合力。这个大家一定要注意。

#### 内力与应力

内力，是物体本身不同部分之间相互作用的力。想象把一个物体切开，截面两边相互作用的那个力，就是内力。它发生在物体内部，是内部不同部分之间的作用。

应力，是截面上单位截面积上的内力。写成式子就是

$$\sigma = \frac{F}{A}$$

力除以面积，得到的就是单位截面积上的内力值。力学里一般用 $\sigma$ 这个符号表示应力。如果这个内力作用在截面的法向——垂直于表面的方向——我们称之为正应力；如果作用在平行于表面的方向上，那是剪应力，用 $\tau$ 表示。

应力比力多了一个要素。力有三要素：大小、方向、作用点；应力除了这三样，还有一个非常重要的东西——作用面。因为它定义在单位面积上，离开面积就无从谈起。

这就带来一个直接后果：同一个点、不同的截面，应力是不同的。

看一个最简单的例子。一根杆两端都受到大小相等、方向相反的力 $N$，那么在中间那个截面上，两侧的力互相抵消，合力为零，那里的应力就是零。但如果只有一端受力，我要分析垂直于轴线的那个截面，正应力就是

$$\sigma = \frac{N}{A}$$

力除以面积，就这么简单。可如果我要分析的是过一个点 P 的斜截面，结果就不一样了：虽然都是过 P 点的截面，方向不同，应力就不同；斜截面上还得把它分解成垂直于斜面的正应力和平行于斜面的剪应力两个分量来看。

到这里，弹性力学的舞台算是搭好了。五个假设把问题压成线性，线性送来叠加原理，而体力、面力、内力、应力这几个量，就是接下来所有方程里要登场的角色。下一讲我们就带着这套东西，去 PeriDyno 和 MechSim 里真正算一个 CAE 分析。

## 从一点到整体：应力、应变与弹性力学的三大方程
> 对应块：BLK20 | 覆盖分集：P10下 | 块标题（分集名）：《10. 工程CAE仿真中的有限元分析原理》

### 为什么要在一点取出一个六面体

先看斜面上那个力 $N$：我们把它沿这个面的法向和切向分开，各分量再除以斜面的面积，就得到一个正应力、一个切应力。这一步本身很朴素，但它立刻逼出一个问题——**同一个点 $P$，过它的不同截面上的应力并不相同**。

那么"$P$ 点的应力状态"到底指什么？它显然不是某一个截面上量出来的那个数，而是能推出所有截面上应力的那套底账。

我们采用的取法是这样的：在 $P$ 点取出一个无穷小的平行六面体，用六面体六个表面上的应力分量来表示 $P$ 点的应力。三条棱分别沿三个坐标轴，长度记作 $dx$、$dy$、$dz$。为什么六面体够用？因为它可以取得任意小，一直小到趋近于 $P$ 点；此时六个面上的应力就趋近于过 $P$ 点、法向分别沿三个坐标轴的那三组平面上的应力。而任意一个斜截面上的力，都可以由这三组平面上的应力通过平衡关系投影出来——底账就是这么记的。

实际分析时，就是在实体结构里取出一个小小的六面体，然后分析包含 $P$ 点的这个微小正六面体。

```text
            ┌─────────────┐
           /│            /│
          / │           / │
         └──┼──────────┘  │
         │  └──────────┼──┘
         │ /           │ /
         │/            │/
         └─────────────┘

   三条棱长：沿 x 为 dx，沿 y 为 dy，沿 z 为 dz
   P 位于六面体中心
```

读图说明：六个面成三对，每一对的两个面外法向相反、互相平行；所谓"分析 $P$ 点的应力状态"，就是把这三对面上的应力都写出来。

### 下标与正负号：应力记号怎么读

我们先盯住一个面。取外法向沿 $y$ 轴的那个侧面，这个面上的应力可以分解成一个正应力和两个切应力：沿面的法向（$y$ 向）的是正应力 $\sigma_y$；沿另外两个坐标方向（$x$、$z$）的各是一个切应力，记作 $\tau_{yx}$ 与 $\tau_{yz}$。

```text
        外法向沿 +y 的面（正面）

        ┌────────────────────────┐
        │                        │
        │      σy  ↑             │   垂直于面，沿 +y
        │      τyx ────→         │   面内，沿 +x
        │                        │
        └────────────────────────┘

        τyz：位于面内，沿 +z 方向（垂直纸面向外）
```

读图说明：一个面上最多站三个分量——一个垂直面的正应力，两个躺在面内的切应力，方向分别沿另外两个坐标轴。

下标的含义是固定的，必须记牢，否则后面的公式一律看不懂：

- 正应力 $\sigma_i$ 的下标 $i$ 是作用面的外法向，同时也是力的方向（正应力垂直于面，两者天然同向）；
- 切应力 $\tau_{ij}$ 的**第一个下标 $i$ 是作用面的外法向，第二个下标 $j$ 是力的指向**。

所以 $\tau_{yx}$ 是"作用在外法向为 $y$ 的面上、指向 $x$ 的切应力"，$\tau_{yz}$ 是同一个面上指向 $z$ 的那一个。$i$、$j$ 各自取 $x$、$y$、$z$，组合起来正好六种：

| 切应力分量 | 作用面的外法向 | 力的指向 |
| :--- | :---: | :---: |
| $\tau_{xy}$ | $x$ | $y$ |
| $\tau_{xz}$ | $x$ | $z$ |
| $\tau_{yx}$ | $y$ | $x$ |
| $\tau_{yz}$ | $y$ | $z$ |
| $\tau_{zx}$ | $z$ | $x$ |
| $\tau_{zy}$ | $z$ | $y$ |

$\sigma_i$ 看起来只有一个下标，其实它本来就该写两个：$\sigma_y$ 完整写出来是 $\sigma_{yy}$——作用面的外法向和力的方向都是 $y$，两个下标相同。这里用的简写约定就是 **Voigt 记号**：两个下标相同的分量只写一个下标。

接下来是正负号。规定是：某个面上的外法线沿坐标轴的正方向，这个面就叫正面，正面上应力沿坐标轴正方向为正、沿负方向为负；外法线沿坐标轴负方向的面叫负面，负面上的正负正好相反。一句话概括——**应力的指向与所在面的外法向同号为正**。所以沿 $x$ 轴正方向的应力取正，沿反方向的取负。

> **易错点**：材料力学对剪应力的正负号另有规定——按剪应力对截面内任意一点的矩是顺时针还是逆时针来定正负，与弹性力学这套"按面法向和力指向"的规则不是一回事。两套体系的符号不能混着用，看不同教材的图时先确认它用的是哪一套。

### 切应力互等：六个独立分量

> **定义**：在受力物体相互垂直的两个表面上，切应力必然成对存在，大小相等，且两者都垂直于这两个平面的交线，方向同时指向交线或同时背离交线。

写成式子就是：

$$\tau_{ij}=\tau_{ji}$$

比如法向为 $z$ 的面上的 $\tau_{zx}$ 与法向为 $x$ 的面上的 $\tau_{xz}$：两者都垂直于 $z$ 面与 $x$ 面的交线；方向上只能"同进同出"——一个指向交线，另一个也必须指向交线；一个背离，另一个也必须背离。绝不会出现一个指向、另一个背离的画法。

两个学科体系在这一点上的画法不同：弹性力学取"大小相等、图上方向同向"的画法，材料力学取"大小相等、图上方向相反"的画法。这不是物理上打架，而是两边取正号的规定不同，导致同一个物理量画出来的箭头方向相反。记住这一条，翻不同书的时候才不会被同一张图绕晕。

有了互等，独立分量就只剩六个：三个正应力 $\sigma_x$、$\sigma_y$、$\sigma_z$，三个切应力 $\tau_{xy}$、$\tau_{yz}$、$\tau_{zx}$。为什么没有 $\tau_{yx}$ 和 $\tau_{zy}$？因为它们分别和 $\tau_{xy}$、$\tau_{yz}$ 相等，写出来是重复的，没必要。

> **结论**：这六个量在 $P$ 点已知，就能求出过该点任何斜面上的正应力和切应力。也就是说，六个分量完全确定了 $P$ 点的应力状态，它们被称为该点的**应力分量**。

一般来说，弹性体里应力各处不同，这些分量并不是常量，而是坐标的函数——$\sigma_x(x,y,z)$、$\tau_{xy}(x,y,z)$，依此类推。在取出的那个微元体上可以把它们当作常量处理；一旦放回整个物体、要描述另一个点，就必须带上坐标。

工程计算里习惯把它们排成一个列阵，三个正应力在前、三个切应力在后：

$$\{\sigma\}=\left[\sigma_x,\ \sigma_y,\ \sigma_z,\ \tau_{xy},\ \tau_{yz},\ \tau_{zx}\right]^{T}$$

后面的几何方程、物理方程都用这个列阵来表示，记住这个排列顺序，矩阵推导时不会错位。

### 位移与应变：把变形写成数学

弹性体受外力之后要变形，形状会改变。问题是怎么把"变了多少"用数学、用公式明确写出来——不能只靠眼睛看它变形。

描述变形有两条路：一条基于点的位移，一条基于线段的长度与夹角变化。两者说的其实是同一件事的两个侧面。

先看位移。物体里任意一点 $A$，它的位置变化在三个坐标轴上各有分量，记作 $u$、$v$、$w$——沿 $x$ 是 $u$，沿 $y$ 是 $v$，沿 $z$ 是 $w$。这个点的新位置就由这三个数确定。

位移分两类，这个区分后面要反复用到：

- **与形状有关的位移**：物体真的变了形，原来的形状变成另一个形状；
- **与形状无关的位移**：刚体位移。物体整体从这儿挪到那儿，$A$ 变成了 $A'$，确实有了位移，但形状一点没变。刚体发生不了形变，它只有位置的改变。

再看线段的变形，它有两种变化：长度的变化与角度的变化。

长度的变化给出**正应变**：任意线段变形后的长度变化量，除以它原来的长度。

$$\varepsilon=\frac{\Delta L}{L}$$

原来长度是 $L$，受力后两端一拉，长度变成 $L+\Delta L$，那么 $\Delta L$ 除以 $L$ 就是这个线段的正应变。它同样沿三个坐标轴各有一个分量，记作 $\varepsilon_x$、$\varepsilon_y$、$\varepsilon_z$。**伸长为正，缩短为负。**

```text
        变形前                            变形后

        P ───────────── A                P' ─────────────── A'
        |<----- L ----->|                |<----- L+ΔL ----->|

                          ΔL
                   ε = ───────────
                           L
```

角度的变化给出**剪应变**：原来成直角的两个线段，受力后夹角不再是 $90^{\circ}$，改变量记作 $\gamma$。

```text
        变形前                          变形后

             B                              B'
             │                              │╲
             │                              │ ╲   β
             │                              │  ╲
             P ─────────  A                P' ──────── A'
                                                  α

        原来 ∠APB = 90°，变形后变为 90° − γxy，且 γxy = α + β
```

读图说明：沿 $x$ 的线段转过 $\alpha$，沿 $y$ 的线段转过 $\beta$，两条边一起贡献了这个直角的改变量，所以 $\gamma_{xy}=\alpha+\beta$。同样有三个分量：$\gamma_{xy}$、$\gamma_{yz}$、$\gamma_{zx}$。

> **提示**：正应变描述"拉长压短"，剪应变描述"直角被掰歪"，两者合起来才能完整刻画一个微元的形状变化。只给正应变，你不知道这个方块是被斜着搓过的。

### 空间问题与平面问题的两种简化

弹性力学的问题按研究对象分两类：**空间问题**与**平面问题**。

实体结构，比如发动机的缸体，是一个空间立体的结构，只能按空间问题分析，三个方向的位移、应变、应力都不能丢。而一些薄壁件、薄板结构，可以简化为平面问题来处理。简化的价值很直接：应变和应力各有六个分量，简化之后只分析面内的那几个，未知量立刻少一大截，手算也好、编程也好都轻得多。

按形状特点简化，有两种方向正好相反的做法：平面应力问题与平面应变问题。

#### 平面应力问题

几何特征是等厚的薄板：一个方向上的尺度远远小于另外两个方向的尺度，这就是前面说过的薄壁结构。

载荷和约束也有配套的要求：体力作用于体内，平行于板的正中面，而且沿板的厚度方向不变化；面力只作用在板的边上，同样平行于中面、沿厚度不变；约束也只作用于板边，平行于中面、沿厚度不变。

受力特点就由此定下来了：外力和约束全部平行于板的平面作用，厚度方向既没有载荷，也不随厚度变化。于是垂直于板面（$z$ 向）的那个正应力、以及 $z$ 面上的两个切应力，全都等于零：

$$\sigma_z=0,\qquad \tau_{zx}=0,\qquad \tau_{zy}=0$$

关键在于它不只在某一个面上成立：因为沿厚度什么都不变，中面上为零的量，整个板厚之内都为零，不必逐点验证。

六个分量划掉三个，剩下的未知量是 $\sigma_x$、$\sigma_y$、$\tau_{xy}$（而 $\tau_{yx}=\tau_{xy}$）。所谓平面应力问题，就是"只剩下 $xy$ 面内的两个正应力加一个切应力"的问题。

#### 平面应变问题

几何特征正好相反：一个很长的等截面柱体，沿 $z$ 方向拉得很长，横截面的形状和面积沿长度不变。

载荷条件也照着这个几何来：体力作用于体内，平行于横截面；面力、约束同样平行于横截面。

为什么这种结构里所有点都没有 $z$ 向位移？因为它很长，任意取一个横截面，两侧的材料是对称的，这个截面就可以看成一个对称面。对称面上的点不能有垂直于该面的位移，否则对称性就被破坏了。于是

$$w=0,\qquad \varepsilon_z=0,\qquad \gamma_{yz}=\gamma_{zx}=0$$

> **易错点**：$\sigma_z$ 在这里并不等于零。$z$ 方向虽然没有位移，但两侧的材料把它夹住了，它照样受力。平面应力是"厚度方向自由、应力为零"，平面应变是"厚度方向被约束、应变为零"，这两句话不能混。

位移只有面内的 $u$、$v$，所以它也被叫作平面位移问题；因为应变跟着位移走，习惯上的名字是**平面应变问题**——应变只发生在面内。

| 对比项 | 平面应力问题 | 平面应变问题 |
| :--- | :--- | :--- |
| 结构特征 | 等厚薄板 | 很长的等截面柱体 |
| 几何条件 | 厚度远小于另两个方向 | 长度远大于截面尺寸 |
| 载荷与约束 | 平行于中面，沿厚度不变 | 平行于横截面 |
| 为零的量 | $\sigma_z$、$\tau_{zx}$、$\tau_{zy}$ | $\varepsilon_z$、$\gamma_{yz}$、$\gamma_{zx}$（即 $w=0$） |
| 保留的未知量 | $\sigma_x$、$\sigma_y$、$\tau_{xy}$ | $\sigma_x$、$\sigma_y$、$\tau_{xy}$、$\sigma_z$ |
| 典型对象 | 板类薄壁结构 | 长柱体类结构 |

```text
   平面应力：等厚薄板              平面应变：很长的等截面柱体

   ┌──────────────────┐          ┌────────────────────────┐
   │   厚度 t 很小     │          │   截面不变，长度很长     │
   └──────────────────┘          └────────────────────────┘

   载荷平行于中面                 载荷平行于横截面
   σz = τzx = τzy = 0            εz = γyz = γzx = 0，但 σz ≠ 0
```

读图说明：左边那块板，厚度方向是自由的；右边那根长柱，厚度方向被两侧材料夹死，所以一个在应力上归零，另一个在应变上归零。

### 平衡方程：从微元受力到微分方程

弹性力学要解的未知量，最后都锁在三类方程里：平衡方程管应力与外力，几何方程管应变与位移，物理方程管应力与应变。它们首尾相接，正好把"位移→应变→应力→外力"这一圈连起来，再配上边界条件才能解。

```text
              位移 u、v、w
                    │
         几何方程    │  微分关系
                    ↓
              应变 ε、γ
                    │
         物理方程    │  代数关系，材料参数 E、μ
                    ↓
              应力 σ、τ
                    │
         平衡方程    │  微分关系 ＋ 边界条件
                    ↓
            位移场与应力场的解
```

读图说明：每一类方程负责链条上的一段，缺哪一段这个闭环都断，方程组也就不封闭。

平衡方程表示的是物体内任何一点微分体的平衡条件。和前面取六面体一样，这里也是取一个微元来做分析，边长 $dx$、$dy$、$dz$，每个表面上都作用着它自己的正应力和切应力。

关键在于面上应力是变化的。设背面（外法向 $-x$）上的正应力是 $\sigma_x$，沿 $x$ 走到正面（外法向 $+x$），走过 $dx$ 之后应力有了一个增量，用偏导写出：

$$\sigma_x\ \longrightarrow\ \sigma_x+\frac{\partial \sigma_x}{\partial x}dx$$

这一步能写出来，靠的是前面两条假设。**连续性假设**：应力可以用连续函数表示，所以才能谈它的增量；**小变形假设**：可以用变形前的尺寸代替变形后的尺寸，面积和力臂都按 $dx$、$dy$、$dz$ 算，不必回头修正。

接下来我们列 $x$ 方向的合力。四个应力分量各乘它作用的面积，再加体力乘体积：

| 力的来源 | 应力（或体力） | 作用的面积／体积 |
| :--- | :---: | :---: |
| 背面（外法向 $-x$）的正应力 | $\sigma_x$ | $dy\,dz$ |
| 正面（外法向 $+x$）的正应力 | $\sigma_x+\dfrac{\partial\sigma_x}{\partial x}dx$ | $dy\,dz$ |
| 底面（外法向 $-y$）的切应力 | $\tau_{yx}$ | $dx\,dz$ |
| 顶面（外法向 $+y$）的切应力 | $\tau_{yx}+\dfrac{\partial\tau_{yx}}{\partial y}dy$ | $dx\,dz$ |
| 体力 | $f_x$ | $dx\,dy\,dz$ |

正应力沿 $x$ 作用，它所在的面的面积是 $dy\,dz$；切应力 $\tau_{yx}$ 躺在法向为 $y$ 的上下底面上，作用面积是 $dx\,dz$。要注意相对的两个面外法向相反，同一个方向上的分量在两边一正一负，所以这四个应力项是相减之后再相加，而不是简单地叠加。

把这些力加起来令其为零，即合力为零，约去公共的微元体积，得到

$$\frac{\partial\sigma_x}{\partial x}+\frac{\partial\tau_{yx}}{\partial y}+f_x=0$$

用同样的思路列 $y$ 方向，得到

$$\frac{\partial\tau_{xy}}{\partial x}+\frac{\partial\sigma_y}{\partial y}+f_y=0$$

还差一个力矩条件。绕 $z$ 轴、对微元中心点取矩：正应力都通过中心点，体力也通过中心点，力臂为零，不产生力矩；真正产生力矩的只有成对的切应力。令合力矩为零，再用小变形假设把微小的增量项去掉，就得到

$$\tau_{xy}=\tau_{yx}$$

这正是切应力互等在微分形式下的来历——前面是从物理上"成对出现、同指向"直接给出，这里是从力矩平衡重新推了一遍，两条路殊途同归。

> **结论**：材料力学、理论力学、弹性力学里都有平衡方程，只是表达方式与研究目标不同。三者之中，弹性力学的平衡条件是最严格的，这一点记住就行。

这里的合并过程不逐项演算，有兴趣的话课后自己动手推一遍，推一次比看十遍管用。

### 斜面上的应力：同一套平衡再用一次

平面问题里还剩一件事：坐标面上的 $\sigma_x$、$\sigma_y$、$\tau_{xy}$ 已知，怎么求任意一个斜截面上的应力？

做法还是取微元，只不过从六面体换成了三角形：微元包含 $x$ 面、$y$ 面和斜的 $n$ 面，两个直角边分别贴在 $x$ 面与 $y$ 面上，斜边就是要求的那个截面。把斜面上的力沿法向和坐标方向分解，用到方向余弦——也就是法线 $n$ 与 $x$、$y$ 轴夹角的余弦，记作 $l$、$m$；再配合斜边的长度，用投影关系把各面上的力换算到同一条斜边上。

计算方法和前面一模一样：斜面上的力乘斜边面积，与 $\sigma_x$ 乘 $x$ 面的投影面积、$\tau_{xy}$ 乘 $y$ 面的投影面积、加上体力乘体积，一起构成平衡条件。写开就是

$$p_x=\sigma_x l+\tau_{yx}m,\qquad p_y=\tau_{xy}l+\sigma_y m$$

其中 $p_x$、$p_y$ 是斜面上那个力 $p$ 沿 $x$、$y$ 的分量。正应力是 $p$ 在法向的投影，切应力是 $p$ 在切向的投影：

$$\sigma_n=p_x l+p_y m,\qquad \tau_n=p_y l-p_x m$$

这就是"六个分量确定一点应力状态"在平面问题里的具体算法。手法没有新东西，仍旧是取微元、列平衡、投影，只是几何形状从六面体缩成了三角形。

### 几何方程：位移能定形变，形变定不了位移

几何方程表达的是一个微分体上形变与位移之间的关系。前面平衡方程管的是"力怎么平衡"，这里换成"变形和位移怎么挂钩"。

取一个微元，$P$、$A$、$B$ 三点构成一个直角形状，$PA$ 沿 $x$ 长 $dx$，$PB$ 沿 $y$ 长 $dy$。变形后 $P$ 移到 $P'$，$x$ 向位移 $u$、$y$ 向位移 $v$；$A$ 也移动，但它离 $P$ 有一个 $dx$，位移里还要多加一份由位置差带来的增量：

$$u_A=u+\frac{\partial u}{\partial x}dx,\qquad v_A=v+\frac{\partial v}{\partial x}dx$$

$PA$ 这条线段的正应变，就是变形后长度减去原长、再除以原长：

$$\varepsilon_x=\frac{\left[dx+\dfrac{\partial u}{\partial x}dx\right]-dx}{dx}=\frac{\partial u}{\partial x}$$

同理，沿 $y$ 的 $PB$ 给出 $\varepsilon_y=\dfrac{\partial v}{\partial y}$。

剪应变是夹角的变化。原来 $\angle APB=90^{\circ}$，变形后 $PA$ 转过 $\alpha$，$PB$ 转过 $\beta$，两者共同把直角掰歪了 $\alpha+\beta$，所以 $\gamma_{xy}=\alpha+\beta$。这两个角都不大，用正切去算：

$$\tan\alpha=\frac{\dfrac{\partial v}{\partial x}dx}{dx+\dfrac{\partial u}{\partial x}dx}\approx\frac{\partial v}{\partial x},\qquad \tan\beta\approx\frac{\partial u}{\partial y}$$

分母里那个 $\dfrac{\partial u}{\partial x}dx$ 相对于 $dx$ 是小量，可以略去；又因为小变形假设下变形量很小，正切值就等于角度值本身。两边一加：

$$\gamma_{xy}=\frac{\partial u}{\partial y}+\frac{\partial v}{\partial x}$$

把平面问题的三个式子摆在一起：

$$\varepsilon_x=\frac{\partial u}{\partial x},\qquad \varepsilon_y=\frac{\partial v}{\partial y},\qquad \gamma_{xy}=\frac{\partial u}{\partial y}+\frac{\partial v}{\partial x}$$

这就是几何方程。它是一组纯几何的、运动学的关系，跟材料是什么、受多大的力都没有关系。

> **结论**：几何方程不是位移与形变之间的充分必要关系。**位移确定，形变完全确定；形变确定，却定不出全部位移**——与形变无关的那部分刚体位移仍然未知，必须靠边界条件才能定下来。

这句话是这一节真正要记住的东西。原因就是前面分过的那两类位移：物体整体平移、转动这类刚体位移不改变任何线段长度与夹角，所以应变里根本不含它的信息；给了一组应变，你可以把形状画出来，却不知道这块东西整体搁在空间的哪个位置、朝哪个方向。补上边界条件，位置和姿态才被钉死。

### 物理方程：广义胡克定律与弹性矩阵

物理方程也叫本构方程，讲的是应力与应变之间的关系，它描述的是材料本身的变形性质。最简单的物理方程就是胡克定律，把它推广到三维应力状态，就是广义胡克定律。

推导靠的是叠加。弹性假设下各方向的效应可以线性叠加，于是 $x$ 方向的应变由三个正应力共同造成：

- $\sigma_x$ 使 $x$ 向伸长 $\dfrac{\sigma_x}{E}$；
- $\sigma_y$ 使 $x$ 向横向收缩 $-\mu\dfrac{\sigma_y}{E}$；
- $\sigma_z$ 使 $x$ 向横向收缩 $-\mu\dfrac{\sigma_z}{E}$。

三项叠加：

$$\varepsilon_x=\frac{1}{E}\left[\sigma_x-\mu\left(\sigma_y+\sigma_z\right)\right]$$

后面两项为什么带负号？因为一个方向受拉，另外两个方向就会缩——横向变形与纵向变形反号，这就是泊松效应。$\varepsilon_y$、$\varepsilon_z$ 把下标轮换一下即可。三个剪应变与切应力之间只差一个系数，形式上更简单：

$$\gamma_{xy}=\frac{\tau_{xy}}{G},\qquad \gamma_{yz}=\frac{\tau_{yz}}{G},\qquad \gamma_{zx}=\frac{\tau_{zx}}{G}$$

这里 $E$ 是弹性模量，$\mu$ 是泊松比，$G$ 是剪切模量。六个式子合在一起就是完整的本构方程。

> **提示**：做有限元分析、给材料模型填参数时，填的就是 $E$ 和 $\mu$——因为本构方程里材料的全部信息都装在这两个数里。

把这些式子整理成矩阵形式，就是编程时天天见到的那两个矩阵：

$$\{\sigma\}=[D]\{\varepsilon\},\qquad \{\varepsilon\}=[C]\{\sigma\}$$

$[D]$ 叫**弹性矩阵**，它的元素只由 $E$ 和 $\mu$ 决定，与坐标无关——材料是连续的，物体内哪一处的材料性质都一样；它也与位移无关，跟变形状态无关，纯粹是材料属性的载体。$[C]$ 叫**柔度矩阵**，和 $[D]$ 互为逆矩阵。

换到平面应力或平面应变问题，$[D]$ 里的元素会不一样，但 $\{\sigma\}=[D]\{\varepsilon\}$ 这个总体形式一字不改。这一点在工程上很有价值，也是有限元程序好写的根本原因之一：结构化编程时模块是同一个，只是喂进去的弹性矩阵不同——一个输入平面应力的 $[D]$，另一个输入平面应变的 $[D]$，程序主体不用动。

除了用 $E$、$\mu$ 表示，也可以改用拉梅系数 $\lambda$ 与 $G$ 来表达，得到等价的另一种形式，矩阵里的系数写法会跟着变。

### 边界条件：力边界与位移边界

前面三类方程描述的都是物体内部的规律，但一个物体摆在空间里，周围的东西还会对它施加作用。这部分必须单独交代清楚。

约定几个说法：研究对象以外的其他物体称为**外界**；研究对象与外界接触的那个面，称为**边界**。边界对研究对象的限制包含三方面——边界的形状、边界上所受的外力、边界给出的位移约束。

对弹性力学来说，边界条件只有两类：

- **力边界** $S_\sigma$：边界上的面力已知；
- **位移边界** $S_u$：边界上的位移已知。

判断一个问题怎么提，先问一句：这个边界上给的是力，还是给的是位移？给力就是力边界，给位移就是位移边界。前面讲几何方程时留下的那个缺口——形变定不出刚体位移——正是靠位移边界补上的：没有它，方程组的解可以整体平移、转动，无穷多组。

边界条件进入求解的方式，和内部方程是同一套：把边界上的应力和应变做分解计算，再融进方程里去。所以在有限元求解程序里，专门有一块模块负责力边界和位移边界的处理——这一块等到讲有限元分析基础和软件编程时再展开。

到这里，弹性力学的描述体系就闭合了：一点处的应力状态由六个分量刻画，变形由位移与应变刻画，内部靠平衡、几何、物理三类方程联系，外部靠力边界与位移边界收口。有限元后面要做的，无非是把这套连续的表达离散到一个个单元上，再把它变成能算的线性代数。
