## 造一个世界：物理仿真与 PeriDyno 引擎架构

### 这门课的定位与排布

这一期是四字头的系列，跟前面几期最大的不同只有一条：以开发为主。我们会设计一系列编程实践，理论不单独占一章，而是穿插在实践里——用到哪一块，就把那一块需要掌握的知识讲掉。理论和实践在这个课里是相互交叉的过程，不是先把理论全部讲完再动手。

401 讲的题目是物理仿真。前面几期，像黄梅老师、胡阳明他们，基础理论其实已经铺过一遍，所以这里不再展开讲那么多仿真相关的技术理论，重心落在实践上，把该掌握的知识融进去。整个课以我们自己研发的那套系统为基础，从第一课开始，一步一步看这个系统怎么搭起来，后面再逐步研发具体的仿真算法。以前完全没接触过也没关系，大纲就是按“从零搭起来”这条路排的。

一共 13 讲：前八讲我讲，后面五讲请湖南大学的蔡文老师来讲。

为什么这么切？因为仿真这个东西，虽然我们做的是图形这个方向，但从大的范畴讲，它在工程领域用得非常多，历史也很悠久。从理论上讲，几百年前各种流体力学之类的力学理论就已经逐步成熟了；计算机出现之后，才逐渐有了数字模拟。所以这门课会有意把图形这边的物理仿真和工程领域的物理仿真放在一起讲。

这两者有差别：图形里的仿真主要还是以视觉效果为主，工程里的仿真更看重精度。差别的根源，说穿了就是计算资源不够时的取舍——资源有限，就得往某一头稍微倾斜一点。但理想情况一定是两者最终融合到一起：既达到工程的精度，又达到图形里那种视觉效果。这是这个课希望建立起来的视角。

前八讲的具体分工是这样的：

- 第一讲，也就是这一讲，讲开源物理引擎的架构。
- 紧接着的两讲，因为仿真的计算量非常之大，所以以 GPU 和 CUDA 编程为基础，讲怎么用并行计算把整个物理计算的过程加速起来；中间会涉及图形学里常用的几何工具、数学原理这些内容。
- 再往后三次针对具体的仿真算法：第四讲是刚体动力学相关的，包括并行编程和一些实践算法；第五讲是 SPH，也就是光滑粒子动力学——SPH 相对来说比较简单，作为一个入门算法，对新入门的同学还是比较友好的；第六讲结合我们自己的一些研究内容来讲。
- 第七、第八讲是扩展内容。这套系统除了算法之外，最终还希望能把自研的算法组合起来做一些有意思的小 app，所以会涉及插件和扩展功能。第八讲还会做一点拓展，讲 Vulkan 编程：CUDA 和 Vulkan 在大的逻辑上其实非常像，但你具体做的时候，因为语言上的差异，实际写代码的手感还是不太一样。
- 后面五讲由蔡文老师讲，从有限元切入，讲怎么基于这个开源系统做后面的应用。

这一讲本身要讲的是：先过大纲，然后讲物理仿真的概述、物理仿真引擎的概述。考虑到不论你现在掌握到什么程度——哪怕完全是小白的程度——都希望这门课能带你入门，所以有些东西一开始会讲得细一些，尤其是一些工具的运用。对新入门的同学来说，搭环境这件事本身就比较困难，所以这一整套流程我会当场演示一遍。最后会讲这套系统的架构，再展示一些仿真实例。

### 适合谁来学，以及不太适合谁

这门课是架在一个开源系统上的，里面会牵涉到方方面面的背景知识。仿真这个方向本身涉及的东西就非常多，所以先把话说在前面：它挑人，不是所有人都适合。

**适合的是这样几类同学。**

第一类，希望有一个能快速上手的科研平台。他不需要去搭太多跟仿真本身不相关的东西，拿到手就能开始做自己的算法。

第二类，对开源平台的不完善有容忍度。整个课基于开源代码，里面会有很多不太完美的地方，比如不少 bug。出了问题之后，愿意自己动手去查、去解决，而不是坐等别人修好。

第三类，想找同方向的人一起做。做仿真这个方向的人其实不太多——图形里面，相比人工智能，做仿真的人还是少得多。通过这门课，希望能遇到一些跟自己方向比较契合的小伙伴，大家可以一起做。

**不适合的也是三类。**

现在尤其搞深度学习的同学，很多人学的不是 C 也不是 C++，对 Python 比较熟；但 C 和 C++ 是编译型语言，对编程能力的要求相对更高。以前没怎么学过的话，上课也好、后面做作业也好，会非常痛苦。

再一类是数学关过不了的。仿真对数学和物理基础的要求相当高，看见公式就头疼的话，学起来会很折磨。

最后一类是想找一个成熟商业解决方案的。这套东西是开源平台，很多地方不完美，抱着“拿来就能用”的预期来，一定会失望。

两边并排放一下，判断起来更直接：

| 适合 | 不适合 |
| :--- | :--- |
| 想要一个能快速上手的科研平台，不必自己搭基础设施 | 没系统学过 C/C++，只熟悉 Python |

### 物理仿真到底在模拟什么

讲背景之前，先把层次放大一点：物理仿真到底是个什么东西？

看我们脚下这颗地球。从最远古的时候开始，那会儿地面上最多的只是一些微生物和低等生物；随着地球不断演变，逐渐发展出一些高级的智能，中间经过恐龙时代，一直到人类的诞生。这一整条线里其实蕴含着两条主线。

一条是地球环境本身在不断变迁，从哲学角度讲，就是我们的物质世界在不断地变化。另一条是智能的出现：智能是长在物质世界基础之上的，受环境影响之后逐步形成，而不同的环境孕育出的智能形态并不一样——水里的可能是鱼这类生物，陆地上是各种哺乳动物，也包括人类。

于是我们的世界笼统地讲分成两块：物质世界与精神世界。

从研究角度看，这两块分别对应两个方向：物质世界对应物理仿真，精神世界对应人工智能。人工智能这几年研究得非常热，但整个人工智能赖以生存的基础，恰恰是物理仿真研究的对象——我们周围的物质环境。

这两个方向各自在研究什么，分得很清楚。

人工智能解决的是精神世界里的那些内容：运动、痛觉、感觉、语言理解、听觉、视觉，这些都是它研究的范畴。物理仿真研究的是我们赖以生存的这个客观世界里的东西，比如海洋、火焰、汽车——这些都是符合物理规律的客观存在，我们要研究它们的物理规律，以及它们的行为特征。

> **定义**：物理仿真，就是用计算机去模拟这些物理介质的力学行为。

按介质分大类，图形学里常见的分法是流体、刚体、柔性体。这是图形这边的分法；到了工程领域，这个分类会分得非常细。无论分得多细，它们都落在物理仿真要研究的范畴里。

### 从游戏穿墙说到黑客帝国

学图形的人，很多最初的动机是喜欢玩游戏。玩着玩着觉得这东西挺有意思，慢慢对图形有了概念，再往下细分，才分成渲染、仿真、几何这些方向。所以讲仿真能干什么，从游戏讲起最直观。

想象一下像《命运二》这样的游戏，如果没有物理仿真，会变成什么样？

场景很简单：玩射击游戏，你往前走，前面有一堵墙。如果你不对它做约束，就会发现玩家直接穿墙穿进去了。对很多玩家来说，这个游戏立刻就显得太假了。物理仿真要做的，就是把真实的力学行为赋予到一个虚拟的世界里：你在虚拟世界里跳一下，不会一下飞到天上（当然这跟具体的游戏设定有关，游戏设定可以调）。说白了，就是把真实物理的那些属性，赋予到一个虚拟世界里去。

游戏里你是以上帝视角看着这一切的。那反过来想一个问题：如果有一天你醒来，有人告诉你，你所在的这个世界其实并不是真实的，你会怎么想？有没有可能，我们自己这个世界，也是一种模拟出来的结果？

这个念头在中西方的科幻作品里出现得非常多，电影里、小说里都有；那部《三体》的电视剧里其实也反映了这样一种思维。假设存在一种更高级的外星生物，整个地球对它来说是一个测试用的训练场，而我们可能只是里面的被试——那我们周围所处的环境，就只是一个模拟出来的结果：它符合某种物理规律，但这个规律是在外面那个更高级生物的试验场里被模拟出来的。

《黑客帝国》讲的正是这样一种哲学。它的故事背景是几十年、几百年之后，地球因为各种各样的原因不再适宜人类生存，机器统治了世界。人类失去了赖以生存的空间，于是机器在一个虚拟世界里，给人类重新造了一个可以活下去的环境。问题来了：怎么让里面的人相信，自己活在一个真实的世界里？

要做到这一点，光把人类精神世界里的 AI 模拟完还不够，必须再造一个跟真实世界一模一样的物理世界。山川河流、空气，这些行为全都要在计算机里模拟出来。用今天的眼光去理解这个设定，它需要什么？需要大量的超级计算机，需要各种各样的算力，把这个世界里涉及的各种物理介质都模拟出来。

这个话头扯得有点远，那就说近一点：我们要造一个哪怕很小的试验场景，也需要各种各样的软件算法，加上硬件设备，才能把场景整个搭起来。

再往细里看一步：前面说的那些不同的力学材质，实际上需要不同的算法去做；把所有这些算法综合起来，在一个系统里搭起来，靠的是什么？靠的就是物理仿真引擎这个概念。

### 物理仿真引擎替我们省掉什么

物理仿真引擎离我们很近，它能干的事可以归成三件。

第一件，给初学者一个技术脚手架。以前可能什么技术都没有，想实践一个算法，根本不知道从哪入手：窗口怎么开、模型怎么读、结果怎么显示，全是从零。有了引擎，基础的框架已经摆在那儿，你只要往里填自己的算法。

第二件，把跟仿真无关的模块替你解决掉。做仿真算法研究的同学，主攻方向是某一种仿真算法，他不想去写渲染，不想去写 UI，也不想碰导入导出这些跟仿真无关的事情。引擎可以把这些跟仿真无关的基础模块全部提供好，你专注在算法上。

第三件，也是大家深有感触的一件：做对比实验。后面研究做多了，审稿人的意见回来，很有可能会出现一种要求——让你跟其他论文的方法做一下对比。这件事对做研究的人来说非常头疼，大部分同学是不愿意做的。但如果这个仿真引擎里已经集成了大量其他算法，事情就变得很容易：直接调用库里现成的算法，把效率、精度这些指标摆在一起比。

> **结论**：仿真引擎提供的是三样东西——入门用的脚手架、与仿真无关的基础设施、以及一个装着大量算法的比较基准。

### 一个引擎长什么样：四层结构

一个仿真引擎通常包含哪些东西？这张架构图这会儿不必全部弄懂，有个大概的意识就行。它的作用主要是把里面涉及的技术模块和技术内容分个类，让条理清楚一些。

以 PeriDyno 这套系统为例，从上到下可以分成几层。

```text
应用层     场景管理 / 模块管理 / UI 与可视化展示
   ▲
   │
核心层     仿真核心算法：有限元 / SPH / 刚体动力学
   ▲
   │
通用层     数据结构 / 图形接口 / 碰撞检测
   ▲
   │
硬件层     CPU / GPU / 内存 / 硬盘 的打交道 API
```

最底下是硬件层，它负责跟 CPU、GPU 打交道，也负责跟数据存储——硬盘和内存——打交道，这一层就是各种打交道的 API。

在这个基础之上是通用层：各种各样的数据结构和通用算法，比如数据库、图形接口、碰撞检测算法。它们的作用是支撑上层的东西——上层的仿真算法也好，交互的算法也好，渲染的算法也好，都建在这一层上。

再往上是核心层。作为一个物理仿真引擎，最核心的部分当然是各式各样的仿真核心算法：有限元的、SPH 的、刚体动力学的，等等。

最上层是管理和展示。我们做研发，不可能所有东西都从基础开始写，上层需要对所有算法进行管理，所以会有场景管理、模块管理这些东西；再加上 UI，因为研发出来的算法总要通过可视化的手段展示出来。

> **注意**：这套分层跟游戏引擎的分层会有一定偏差。原因不在画法，而在于游戏引擎和仿真引擎所面向的对象、所研究的问题本身有差异，架构自然就不一样。

### 上手三步：构建、配置、开发

从拿到源码到跑起来，整个流程可以切成三步：先构建，把系统搭起来；再配置，把源码变成能打开的工程；最后开发，在里面写自己的算法。这套系统目前以 Windows 和 Linux 两个平台为主，用 Mac 的话暂时不太支持，所以下面以 Windows 为例来讲。

每一步依赖的工具不一样，串起来是这样的：

| 阶段 | 要做的事 | 依赖工具 |
| :--- | :--- | :--- |
| 构建 | 把源码完整拉到本地 | Git |
| 配置 | 由源码生成工程文件 | CMake、VS Code |
| 开发 | 编译、调试、写算法 | Visual Studio |

工具的选择跟个人偏好有关系，用别的也完全可以。这里之所以按这一套串一遍，是因为这条流程比较成熟，中间相对而言问题会比较少。开源系统在稳定性方面本来就可能没那么稳，如果换一些新工具，中间完全可能出现一些意想不到的问题。开发环节目前推荐以 Visual Studio 为主，用 CLion 之类的其实问题也不大。

环境方面有几件事得先确认。

整套仿真要依赖 GPU，但这不是绝对的：如果对性能没有要求，完全可以用 CPU，用 C++ 写一些串行代码也能跑。只是推荐用一台有显卡的电脑。系统上 Windows 10 或 Windows 11 都没问题。显卡方面，最新的是四零系列，但这个系列比较贵；想买显卡的同学可以找几个别的系列，性能上有保障，价格又相对可以接受。用 NVIDIA 的显卡做开发，需要额外装 CUDA 的 SDK，这是硬依赖。

> **注意**：其他平台大家可以去试，有问题也可以反馈回来，助教可以帮忙试。但我们确实没有那么多精力把所有的平台都测一遍，所以以文档和讲义里列出的那套配置为准。

### Git：先把代码管起来

要动这套系统，第一个工具是 Git，用来做版本控制。以前没接触过的话可能对它没概念，其实它解决的问题很具体。

#### 它解决的三件事

第一件是版本控制。写代码这件事本身就是不断修改：今天改这块，明天改那块，改着改着就不知道哪一版是对的。Git 会把你每一次的修改都记下来，形成修改记录。万一你在中间某一次改错了，可以直接回退到以前某一个正确的版本。有了这个能力，你才敢不断地迭代、把代码往完善的方向推。

第二件是分支与合并。如果只有你一个人开发一个系统，这个功能意义不大；但我们现在面对的往往是一个大型系统，比如几十个人参与的软件。每个人开发的其实只是里面的一个模块，不同人写的代码需要合并、需要管理，这就得用分支和合并。

第三件是可追踪。多人开发的每一个节点都会被记录下来，中间如果某个研发人员写了一个 bug 进去，你可以定位到这段代码是谁在哪个节点写的，然后逐步把问题定位出来修掉。

> **结论**：Git 本质上是一个给多人研发做协同管理的工具，版本记录、分支并行、责任追溯都建立在同一套提交历史上。

#### 提交与分支长什么样

一张示意图就能看清它在做什么。

```text
c1 ── c2 ── c3 ── c4 ── c5 ──►   master（主版本）
       \
        f1 ── f2 ── f3 ──►     feature（新功能分支）

f3 开发完成后，合并回 master
```

上面那条直线代表主线，也就是一个系统研发的主版本。线上的每一个点，代表一次提交——你可以把它理解成给当前状态做了一次备份。每提交一次就记录一个节点，这个节点会永久留在历史里。后面如果发现出了问题，你可以直接回退到中间任意一个有记录的点，把那个节点的代码恢复出来，再在这个基础上逐步修复后面的错误。

主线上某个节点还可以拉出一条分支。新的研发人员参与进来时，就从你的某个节点分出去，整个研发过程并行进行：新功能的开发不会影响主分支的进度。等新功能开发到某个节点、做完了，再和主分支合并，新功能就进入了主分支，继续往后迭代。

> **提示**：分支不是复制一份代码另存，它只是在历史上多了一个引用。所以在分支上改东西，主分支的代码一动不动。

#### 会用到的几条命令

Git 的命令很多，跟这套系统相关的主要是下面这些。

初始化与克隆：

- `git init`：第一次创建这个工程的时候用。
- `git clone`：大部分时候我们不是从零写，而是基于别人的开源代码做研发，这时要做的是把人家的仓库克隆到本地，再进一步开发。用它的频率远高于 `init`。

克隆有一个参数必须加上：

```bash
git clone --recursive <仓库地址>
```

`--recursive` 不能省。这个仓库里包含很多子模块，不加这个参数，子模块根本拉不下来；而生成工程的时候会因为缺少子模块，导致整个编译不过。

> **易错点**：克隆完发现编译报错、报的是某个第三方库找不到，八成就是当初 clone 时漏了 `--recursive`。补的办法是重新用带参数的 clone 拉一遍，别在残缺的目录上硬修。

日常同步的几条：

- `git remote`：添加远程仓库，本地一个仓可以对应多个远程仓。
- `git fetch`：获取远程仓库的内容。
- `git pull`：把远程仓库的内容同步下来、拉到本地。
- `git push`：把本地的更改推送到远程仓库。
- 分支相关的还有 `git branch` 创建分支、切换分支、`git merge` 合并分支。

Git 的命令确实非常多，我自己其实也不太记得住，所以实际做的时候一般推荐用 GUI 工具。下面演示的大部分操作也是直接在图形界面里点。

#### 在 SmartGit 里走一遍

先看界面的布局，它跟前面讲的那张图是对应的。最左边是所有仓库的列表：克隆下来一个仓，它就会出现在这里；双击一下，下面会展开这个仓的所有分支。右下角是提交记录——这个分支里每一次提交都记着时间点、改了哪些文件；点某个文件，下面会显示修改前和修改后两个视图并排对比，一眼能看出这个文件到底改了哪些内容。中间那块是分支图：黑色那条线是主分支，其他颜色的是从主线分叉出去的新分支，以及合并回来的结果。分叉、合并都在图上一目了然。

下面用一个新建的空仓库走一遍。这个仓里现在什么都没有，只有两个 readme 文件，外加一个 master 分支——它就是这个项目的主版本。

现在假设有一个新的功能模块要开发，而我不希望影响原来的主分支，该怎么做？

第一步，新建一个分支，名字随便取。新分支是从 master 算出来的，所以它此刻的内容跟原来的分支一模一样，区别只在于它处在另一个分叉上。

第二步，注意“当前分支”这个概念。界面上粗体显示的那个分支，就是你当前的工作分支，所有对文件的改动都落在它身上。要让改动不进主分支，就得先切过去——用 checkout，对应的就是 Git 的 `git checkout`。切出来之后，你所有的改动就不会影响原来的 master 了。

第三步，改动并提交。比如现在往里面新加一个 `test.txt`，界面立刻会提示这里有一个更改，是新增了一个文件。改完之后右键提交，提交时有一件事必须做：填一条提交信息，比如 `first commit`，代表这是第一次提交。提交完成，这一次更改就被记录下来了。但要注意，记录完之后，改动依然留在你当前所在的那个分支上。

第四步，验证隔离效果。这时你看目录，`test.txt` 还在；把分支切回 master，这个文件就消失了。这正是因为它所有的更改都在新分支上，对主分支没有任何影响。

第五步，合并。新分支上的改动都做完了，想合进主分支，就选中那个新建的分支，用 merge 命令，按提示选择合并方式，这里选 fast forward。合并完成后，新分支里新增的模块就被引入到主分支里了，再回去看目录，那个文件已经在了。

#### 挂上第二个远程仓

界面上的分支分成两部分：上面是 local branch，也就是你本地的那份；它对应着一个远程仓，就是网页上 GitHub 或者码云上的那个仓。

一个很常见的需求是同时跟多个远程仓同步。比如本地只有一个仓，但远程有两个，我还想推送到另外一个仓里去，这时就要再加一个远程仓：把地址填进去，可能要输一次密码，添加完成。添加完还有一步不能漏——一定要重新拉一下，拉完之后才能看到它里面的所有分支都同步过来。

之后要切换跟踪的分支：点一下跟踪项，会出现两个远程仓，一个是 `origin`，另一个是后来新加的。在这两个之间来回切，就能在不同的仓里做同步。

### 克隆下来之后：目录里都有什么

克隆完成后，本地会得到一个名为 PeriDyno 的目录。进去看，源码是分门别类放好的：

```text
PeriDyno/
├── .git/        版本库，记录临时文件等内容
├── cmake/       创建样例、创建 library 的脚本
├── data/        obj 文件、各种模型文件
├── example/     样例，按 GPU 后端分目录
├── external/    第三方子模块
├── python/      与 C++ 的绑定
├── source/      引擎全部核心库
└── test/        模块测试与单步测试
```

逐个说清楚每个目录是干什么的。

`.git` 是 Git 这个工具自己的目录，用来记录一些临时文件和版本信息。

`cmake` 里放的是我们提供的一些脚本，用来方便地创建样例、创建 library。

`data` 里是各种各样的数据：obj 文件、各种模型文件，都放在这里。

`example` 里是各种各样的样例，现在有三个目录，它们对应的是不同的 GPU 后端：CUDA 的、Vulkan 的，以及 general——各平台通用的那份。

`external` 就是前面反复提到的那个目录：`--recursive` 如果没加，这里面的所有子模块都拉不下来，编译时就因为缺模块而过不去。编译时抱怨找不到某个第三方库，多半就是这个目录里空着。

`python` 是用来跟 C++ 做绑定的，方便从 Python 侧调用引擎。

`source` 是引擎的源码主体，所有跟仿真相关的核心库都在这里：最底层是一个 `core`，最核心的库；此外还有动力学的仿真算法库；有一个 framework，也就是仿真框架；再往后是交互、建模、插件、渲染，各自在自己的文件夹里。

`test` 是测试。为什么要单独留出这么一块？大型系统里代码量非常大、算法模块非常多，一个算法内部往往包含很多步，很多时候需要对每一步做单独的测试，所以这里会有各种各样的模块测试，以及对某个具体步骤的独立测试。

> **结论**：在大型系统里，测试是唯一靠得住的回归手段。代码到了几十万行的规模，某一部分被别人改过之后，你不可能每一行都记得、更不可能靠眼睛把问题看出来；通常的做法就是跑一遍测试样例，看结果对不对，以此反推当前版本的所有模块是不是都还正确。

### 用 CMake 把源码变成能打开的工程

代码拉下来之后，目录里只有一堆源码，没有任何工程文件。这时需要请出第二个工具 CMake，由它把整个系统生成出来。

流程本身很简单：指定源码目录，指定生成目录，然后 configure，再 generate，最后用 Visual Studio 打开工程。整套动作就这么几步。

源码目录怎么确定？就是去找那个根目录——里面会有一个 `CMakeLists.txt`，点进去能看到对 CMake 版本之类的设置，看到这个文件，就能确认它是根目录。把根目录的路径复制到 CMake 的源码目录那一栏。

生成目录要单独设一个。很多人习惯把它跟源码放到同一个目录，但推荐放到一个新的、空的目录里，这样源码和构建产物分开放，整个结构会比较清晰。

> **提示**：源码目录与生成目录分开，工程文件、中间产物、可执行文件全都落在生成目录里。哪天想彻底清一遍，删掉这个目录重配一次就行，源码一点不受影响。

设置好之后点 configure，会弹出一个对话框，里面有两件事要选。

第一件是编译器。这个跟你本地装了什么有关系：装了哪几个版本，它就会列出哪几个。这里选 2019。

第二件是平台。现在的电脑都是 64 位结构，所以这里直接选 x64 就可以。

配置过程会花一点时间，它会按照 CMake 脚本把整个工程配置一遍。中间是有可能报错的，报错就按提示去修。不过这套东西现在基本都调过了，正常情况下一次就能过。

判断成功的标志看输出：出现 `Configuring done`，说明这一轮没有任何问题，配置成功了。一般来说还要多点几次 configure，点到红色的条目消失为止，那才说明彻底没有问题了。

配置通过之后就可以生成工程。

这里有一个地方要格外注意：系统里有很多选项，其中 Qt 这一项，勾上之后会报错。原因不是 Qt 装错了，而是它找不到 Qt 的配置文件——CMake 在默认位置没找到 Qt 的目录。

解决办法是手工把 Qt 的位置指给它：

1. 找到 Qt 的安装目录。我这里是装在 C 盘。
2. 里面会有很多版本，现在推荐用 5.13.2 和 5.14，这两个都可以。
3. 进入对应版本目录，找到 msvc 对应的那个子目录。
4. 进 `lib` 文件夹，再进 `cmake`，再进 `Qt5`。
5. 这个目录里有一个 `Qt5Config.cmake`，把它所在的目录作为 Qt 的路径交给 CMake。

指到这个目录之后，CMake 就能读到 Qt 的配置，Qt 这一项也就能通过了。配置一过，工程生成出来，就可以直接用 Visual Studio 打开，进入开发环节。

## 从一个空窗口开始：PeriDyno 的工程结构与四层架构
> 对应块：BLK02 | 覆盖分集：P01下 | 块标题（分集名）：《1. 物理仿真及PeriDyno开源引擎架构简介》

真正开始用一套引擎，第一步往往不是写算法，而是让它先在你机器上跑起来。这件事听上去没什么技术含量，卡人的地方却全在这里：CMake 配置不过、工程生成不出来、点运行报错，一天就过去了。所以先把这条路走通，再讲这条路通向的那个四层结构。

### 让工程先长出来

流程只有两步：用 CMake 配置，再生成。判断配置成功的标志很直观——界面里那些红色的条目全部消失。红色代表"这一项还没找到"，可能是编译器，可能是某个第三方库，也可能是路径没指对。红的一项都不剩，才轮到点 Generate；只要还留着红的，生成出来的工程一定是残的。

生成完，构建目录里会出现一个以 `.sln` 结尾的文件，这就是 Visual Studio 的解决方案，双击打开。我这边之前在另一个目录里生成过一份，所以直接开现成的；你第一次做，就等它跑完。

打开之后先别急着看代码，看一眼目录结构：

```text
PeriDyno
├── engine/      引擎底层：现有的核心库
├── example/     示例代码：可以直接跑的工程
├── rendering/   渲染相关
└── external/    第三方库（克隆时自动拉取）
```

`engine` 是引擎本体，底层那些库都在里面；`example` 是示例代码，也是最值得先翻的地方——想学这套系统怎么用，找一个最接近你需求的样例改，比从零写 CMakeLists 快得多；渲染相关的内容单独成块；第三方库统一收在 `external`，不用你一个个去下仓库，克隆的时候带上 `--recursive`，子模块会一起拉下来。

接下来做一件很实际的事：新建一个自己的工程。做法不是从零写，而是复制。

在 `example` 下新建一个文件夹，比如叫 `hello`，然后从别的示例里拷一份 CMakeLists 过来——这些脚本彼此之间有很多相通的部分，改比写省事。打开这份脚本，最前面是两样东西：整个工程的名称，和源文件的名称；后面是一串其他配置。

因为是从别处拷来的，工程名会和原来的撞车，所以第一件事就是把名字改成 `hello`，别的先不动。

这份脚本里不只有名字。工程要链接哪些库、源文件放在哪个目录，都写在里面；从示例拷过来，等于白捡一份已经调通的依赖配置。也正因为如此，改完名字之后其余部分可以先放着，先让它跑起来再说。

改完必须重新 Configure、重新 Generate 一遍——**CMake 脚本动过，不重新生成，Visual Studio 里是看不到新工程的**。这一点很容易忘，忘了就会对着旧的解决方案找半天，怀疑自己是不是把文件放错了目录。有时候生成确实成功了，Visual Studio 里还是看不见，关掉重开一次就出来了——它自己没刷新。

重新生成之后，解决方案里会多出一个 `hello` 工程，里面是一个很短的 main：创建一个窗口，别的什么也不干。编译、运行，你会看到一个 GUI 框弹出来——空的，因为还没往里加任何跟仿真有关的东西。

> **提示**：解决方案里有多个工程时，直接点运行会报错，因为 Visual Studio 不知道该启动哪一个。把 `hello` 设为启动项目，再编译运行。

这里还有两个小地方值得说一句。一个是编辑器的高亮：如果 C++ 和 CMake 的语法颜色不对，装对应的插件就行，那只是显示问题，不影响编译。另一个是工程宏：引擎里给了一个 `example` 宏，用它可以把一大段重复的 target 配置压成一行，效果和手写等价，但代码少很多；用这个宏的时候还要补一个参数，告诉它这个工程对应到解决方案里的哪个目录，不然它不知道把新工程挂到哪儿。

首次编译会慢一些，等一两分钟很正常。等窗口真的弹出来，这套工程就算通了。

### 场景要被塞进窗口

窗口是空的，这不是编译错了。那个 main 的职责就是创建界面，别的它一概不管。

要加仿真内容，得从 app 层留的那个接口入手：给界面设置一个场景。整个框架其实只有三块：

```text
界面 GUI
├── 渲染窗口 / 视口   ← 由渲染引擎负责显示
└── 场景 Scene        ← 由使用者提供，可整体替换
```

读图：界面是最外层，里面并排放着渲染窗口和场景。场景自己不负责画，它被交给渲染窗口，渲染引擎用自己的视口去识别这个场景，再把场景里的内容画到界面上。

这里的分工很干净：界面只管窗口和控件，场景只管物理内容，两边唯一的接头就是"设置场景"这个动作。所以换物理内容不用碰界面代码，换界面也不用动场景。

场景可以是刚体仿真，也可以是流体仿真。换一个场景，就换了一整套物理内容，界面和渲染窗口一行都不用改——这是这个结构最直接的好处。

场景内部是四层：

```text
场景 Scene
├── 节点 Node  ────数据────►  节点 Node
│    ├── 模块 Module  ──数据──►  模块 Module
│    ├── 状态变量
│    └── 管线 Pipeline
│
└── 依赖
     ▼
   Field 数据层  ◄──输入──  外部
        │
        └──导出──►  外部
```

读图：场景由节点拼起来，节点之间靠数据传递发生关系；节点内部是若干算法模块，模块之间同样有数据流；节点和模块都站在 Field 这一层上，读它的输入、写它的输出。从上往下数，就是场景、节点、模块、数据这四层。

四层各管什么，可以对着看：

| 层 | 由什么组成 | 主要职责 |
| :--- | :--- | :--- |
| 场景 Scene | 若干节点 | 组织整个仿真世界，提供重置与逐帧推进的入口 |
| 节点 Node | 若干模块、状态变量、管线 | 承载一组状态变量和一条管线，节点之间传数据 |
| 模块 Module | 控制变量、输入、输出 | 实际的算法单元，读输入、写输出 |
| Field 数据层 | 各种类型的数据 | 定义输入输出与状态变量，供上下两层读写 |

数据的流向我们设计了四类：节点到节点、模块到模块，以及模块与外部之间的导入和导出。前两类在内部走，后两类跨出这一层——算完的数据要能导出去看，外面的数据也要能喂进来。

空场景里其实已经带了一批 UI 功能：按住 Ctrl 再配合鼠标左键、中键、右键，可以做缩放、旋转、平移；可以切换相机视角；可以调光照、换背景；还可以打印一些统计信息。这些东西看着是"界面功能"，其实全是给调试准备的——同一个现象，换个角度看，成因常常就露出来了。

### 数据层：Field 存什么、给谁用

数据层的职责很单纯：输入和输出。

#### 四种数据形态

| 数据形态 | 典型内容 | 存储与传递特点 |
| :--- | :--- | :--- |
| 基本类型、向量、矩阵 | `bool`、`int`、`float`、`double`，三维向量，矩阵 | 规模小，CPU 与 GPU 之间可以直接传递 |
| 定长多维数组 | 一维、二维、三维数组，连续的 buffer | 用 `define array` 系列宏定义，二维加 `2d`、三维加 `3d` 后缀 |
| 动态数组 | 长度可变的数组 | 用法接近 C++ 的动态数组，但 CPU 和 GPU 通用，CPU 建好直接传 GPU |
| 实例 instance | 复杂类型的引用 | 本质是一个指针，与 GUI 联动，界面能识别 |

第一类是基本类型：布尔、整型、单精度、双精度，加上三维向量和矩阵。它们的共同点是数据规模小，所以可以直接在 CPU 和 GPU 之间传。这里有两个宏：一个用来定义数据，定义完之后界面里就能识别出这个数据，并且可以直接在界面上改它的值，改的就是场景里那个值；另一个用来定义枚举类型。

第二类是给大数据准备的。像 SPH 流体，粒子数量动辄成千上万，每个粒子带一堆属性，用零散变量存根本不现实，必须有一块连续的存储空间。所以这里提供一维、二维、三维数组，用 `define array` 这一族宏来定义，二维加 `2d` 后缀、三维加 `3d` 后缀。

连续的好处很实际：整块内存可以一次性拷到 GPU，不用为每个元素单独做一次传输；GPU 那边也能按线性地址成块读。

第三类是动态数组。用法和 C++ 里的动态数组很像，好处是它在 CPU 和 GPU 之间是通用的：CPU 里把数据建好，直接传到 GPU，不用为两边各写一套容器。

第四类留给最复杂的类型，我们叫它 instance。你可以把它理解成一个指针，但它和 GUI 是联动的——界面能识别这个类型，也就能把它显示出来、连起来。

#### 三种用途

从用途上看，这些数据分三种：变量、输入输出、状态变量。

> **定义**：状态变量是节点特有的一类数据，用来描述一个物理现象当前处在什么状态——位置、速度、密度，都是这种量。

#### 定义完就能在界面上调

有一个专门演示 Field 的样例，跑起来左边是代码，右边是创建出来的节点。节点下面展示的是它的基本控制变量：一个布尔、一个整型、一个浮点、一个三维向量，正好对应代码里最左边那四个变量。再往下是输入输出：输入定义了一个浮点数组，输出也是一个浮点数组；最后还有一个状态变量，界面里被截断了，看不见全貌。

> **结论**：所有数据类型和 UI 是一一对应的。你定义了什么类型，界面上就长出什么控件，不需要另写一份界面代码。

这个设计值钱的地方在于调参。仿真的很多场景很复杂，你在跑的过程中想动态改一个参数，看看改完之后后续怎么变。没有这套东西，就得改代码、重新编译、重新跑，一轮几分钟，思路早断了；有了它，在界面上直接调就行。

模块那边是同一个道理：有了这些数据之后，定义一个模块只需要说清楚三件事——它需要哪些控制变量、哪些输入、哪些输出。

### 节点与模块：先把输入输出说清楚

#### 一个模块长什么样

模块要定义的东西很少：控制变量、输入、输出。

拿 SPH 的密度计算举例。控制变量是标准密度；输入是位置、邻域位置和邻域粒子 id——算一个粒子的密度，得先知道它邻域里有哪些粒子、这些粒子在哪，再按邻域 id 逐个把密度算出来；输出是密度数组，算完把值写进去。这里有一部分输入是在父类里就定义好的，看一个模块的输入不能只看子类那一段。

#### 节点多出来的三样东西

节点的结构和模块类似，但多出三样。

第一样，可以把整个节点当成一个输入，传给后面的节点。为什么要这么干？有些数据类型很复杂，拆成一个个字段去连线，线会多到界面没法看，显示也冗长；整包传过去，连线数量立刻降下来。

第二样，状态变量。

第三样，管线。管线后面单独讲。

#### 连线时的那道类型闸门

有一个专门测节点之间关系的样例：`source A` 和 `source B` 两个源节点，各输出自己的数据类型，再有一个 `target` 节点接收。打开 log 能看到完整的连接信息；把某条连线断开，日志里就有提示，告诉你是 `source A` 的哪个输出被断开了。

真正的看点是类型判断。`source B` 连不到只接收 `source A` 类型的那个输入上，只有同一种类型才允许连。这不是界面的小脾气，是它在替你挡错。

> **易错点**：连线不是画着好看，它是一次类型检查。研发模块时先把输入输出类型定清楚，不兼容的连接在搭建阶段就被挡住，不会等到运行的时候才把程序搞崩。

### 场景是搭出来的，不是写出来的

模块和节点都齐了，一个场景就能像搭积木一样拼起来。拿流体场景走一遍这个过程。

先建模：创建一个几何的 cube，在它里面生成粒子。粒子出来之后设属性，比如给它一个初始速度。再往后挂仿真计算的节点。跑起来，流体就动起来了。

刚跑起来的时候没有几何边界，所以流体只是自己在流。把几何边界加进来，流体就会和边界发生作用，行为立刻不一样了。

这套流程的价值不在这一场景本身，而在于复用：几何生成、粒子生成、属性设置、仿真计算节点都是现成的模块，搭一个新场景就是换一组参数、换几条连线。基础模块都做完之后，更多场景可以直接在 UI 里搭出来，不用每换一个场景就重写一遍代码。

> **结论**：模块化的回报在这里兑现——场景搭建的成本从"写代码"降到"连模块"。

### 管线：不是队列，是图

> **定义**：管线是一系列功能模块按执行顺序排布出来的执行结构。名字借自图形学里的渲染管线，但在 PeriDyno 里它不是一条线性队列，而是一张图。

#### 两条管线和它们的入口

管线有两条：仿真管线和渲染管线。每一条都有一个入口，入口对应节点里的状态变量——如果是一个流体节点，入口就是速度、位置，以及其他各种场。

这两条管线不是全局各一条，而是挂在节点里：每个节点有自己的仿真管线和渲染管线。场景取一帧时，是逐个节点去驱动它自己那条管线。这也解释了为什么点进一个节点能看到左右两个视图——那是这个节点自带的两条管线。

入口之后接各种模块：可能是仿真计算的模块，也可能是交互的模块。这些模块算完之后，会去更新自己负责的状态变量。

说它是图，是因为一个模块的输入可以来自多个上游，一份输出也可以被多个下游拿去用；执行的先后由数据依赖决定，而不是谁写在前面谁就先跑。

#### tag：只算该算的

模块一多，就有一个必须保证的机制：数据什么时候更新的，要有记录。

我们的做法是给数据打 tag。某个模块把数据写完，记一笔；下游模块在计算前先看上游的数据有没有变——变了才重算，没变就跳过。

省下来的不是一次函数调用，而是整条链：一个模块的输出没变，依赖它的下游全都可以跳过，越靠下游，省得越多。

> **提示**：没有这个机制，每帧所有模块无条件跑一遍，绝大多数计算是重复的，纯属白烧。

#### 模块可以现场拆装

刚体那个 example 最能说明问题。点进节点，里面有两个视图：左边是仿真管线，末端接的是刚体动力学算法，前面几个也是相关的计算模块；右边是渲染管线，接的是渲染算法，作用是辅助显示。

右边那条管线里能看见三样东西：物体的表面网格、触点、触点的法向。对应地，里面有三种渲染模块在干活——一个画触点的法向，一个用点的渲染方式画触点，一个画表面网格。

这些模块可以当场删掉，也可以挂上新的算法模块。之所以叫"管线"，就是因为它里面的模块可以动态配置：删掉不想要的，加上自己写的，显示需求和仿真需求都能现场搭出来。

### 一帧是怎么走完的

仿真管线的运行是一个时序关系，从外到内分四段：场景、节点、管线、模块。

```text
场景 Scene
├── reset()
│     └── 逐级调用节点与模块，全部恢复到初始状态
│
└── take one frame（每帧循环调用）
      └── 节点 Node
           └── 仿真管线
                ├── 模块 1  ──► 更新状态变量
                ├── 模块 2  ──► 更新状态变量
                └── ……
```

读图：`reset` 负责把整棵树拉回初始状态；运行期间，外层循环不断调用"取一帧"，因为仿真是一步一步往前推的。取一帧进去之后，场景调节点，节点调自己的仿真管线，管线里的模块依次更新状态变量，整个场景就这样往前走了一步。

两个入口分开是有道理的：一个管回到起点，一个管往前走一步。同一套搭好的场景可以反复跑——改一个参数、重置、再跑一遍，对比两次结果，这是调仿真最基本的循环。

渲染是同一套骨架：场景 → 节点 → 渲染管线 → 各渲染模块。渲染管线内部的流程是这样：

```text
取出场景里搭好的所有渲染模块
        │
        ▼
   物体渲染 ──► 阴影渲染 ──► 实例渲染 ──► UI 渲染
        │
        ▼
   render target（帧缓存）──► 屏幕
```

读图：引擎先把场景里配置的渲染模块全部取出来，按顺序做物体渲染；然后渲染阴影，再做实例渲染，最后把整个界面也渲染一遍；所有结果都写进 render target，也就是帧缓存，最后显示到屏幕上。

> **结论**：仿真和渲染的调用骨架完全一样，都是场景—节点—管线—模块，差别只在末端挂的是哪一类模块。

### 算法与数据要分开

四层结构为什么要搞这么复杂？目的只有一个：解耦。拆开看是三件事——计算要和数据分离，计算要和渲染分离，交互也要分离。先说第一件。

#### 有限元和粒子，长得不一样但道理相通

看一个有限元的仿真场景。它的拓扑结构是四面体网格；网格之上挂着各种场：位移场、应变场、应力场。场景动起来的时候，算法要做的事就是更新这些量——位移要更新，应力也要更新。

再看一个粒子场景。它也有场：位置、速度、密度、应力，和有限元那边有一部分是重名的。但拓扑结构不一样：SPH 这边整个就是 particle 的基本结构，没有网格。算法上又有相通的地方，比如 Jacobi、Gauss-Seidel、Newton 这些迭代求解的路子，两边都能用。

| | 有限元场景 | 粒子场景 |
| :--- | :--- | :--- |
| 拓扑结构 | 四面体网格 | particle（粒子） |
| 场 | 位移场、应变场、应力场 | 位置、速度、密度、应力 |
| 计算任务 | 运动中更新位移、应力等 | 按邻域更新密度、应力，推进位置与速度 |
| 算法 | Jacobi、Gauss-Seidel、Newton 等迭代 | 同一类迭代方法同样适用 |

把视野再拉远一点，仿真算法非常多：SPH、PBD、MPM、FEM，各有各的适用场景。但它们之间有相通的地方。

一方面，不同的算法可以用相同的数据结构来模拟。SPH 和 PBD、SPH 和 MPM，都依赖 particle——粒子既是 SPH 的载体，也是另外两家的载体。

另一方面，反过来也成立：同一种方法可以跑在不同的拓扑结构上。particle 可以，表面网格可以，体网格也可以，它们都能用 FEM 去算。

这就形成了一对多的关系：算法与拓扑不是一一对应，而是交叉对应。

#### 把拓扑抽象成一层

一对多意味着什么？如果按"算法乘拓扑"两两各写一份实现，就是 M×N 份——M 种算法、N 种拓扑，代码量是乘积，大量重复，根本维护不动。把表示抽象出来之后，算法侧 M 份、拓扑侧 N 份，乘号变成加号；算法越多、拓扑越多，差距越夸张。所以必须把"表示"这件事单独抽出来，做成一套层次化的拓扑结构：

```text
点云（particle）
  └── 边
       └── 三角网格
            └── 四边形网格
                 └── 四面体网格
```

读图：从最简单的点云，到边，到三角网格，再到四边形网格、四面体网格，维度和连接关系逐级变复杂。把它们纳入同一套表示，各种算法依赖的拓扑就有了统一的落脚点。

> **结论**：表示统一之后，不同算法之间要共享数据，只需要在这套表示上做一次映射，不必为每一对算法单独写转换。

#### 写一个仿真算法的三步

有了统一表示，写一个仿真算法的流程就固定成三步。

第一步，创建拓扑结构。可以是点云，也可以是四面体网格，看你的方法需要什么。

第二步，在拓扑上定义场。位置、速度、体积、密度等等。场的定义位置和拓扑是绑定的：如果原来是点云，所有场都定义在点上；如果是四面体网格，有些量定义在四面体的单元上，有些量定义在点上。

第三步，拿拓扑和场做运算。数学上讲，就是梯度、散度、拉普拉斯算子这些；具体形式跟你的离散方式有关，所以不同方法的运算细节会不一样。

落到刚体那个场景的管线里看，左边是数据层：一个拓扑结构，加上质量、位置、速度、角速度这些状态变量；右边接一串算法模块。计算和数据就这么分开了。

> **提示**：分开之后，换算法、加模块，都不用动拓扑和状态变量的定义。同一套拓扑结构，换一组算法模块，就能去模拟不同的现象。

### 渲染不只是为了好看

数据和算法分开之后，还有第二件事：渲染也要和计算分开。为什么值得单独分一层？因为仿真算法最困难的地方不是写出来，是调试。它不像业务代码，断点一打、变量一看就知道哪错了；仿真错起来是一大片数值一起漂，你只能靠猜。

举个最常见的现象：穿模。物体穿过去了，可能是触点没找对，也可能是法向算错了。光盯着数字看不出来，那就把触点和法向画出来——这就是渲染管线要能挂各种模块的原因。

所以渲染这一层在研发期承担的是辅助研发的职责，不只是出图。场景里一穿模，我就把触点和法向显示出来，看看到底是哪个触点没找出来，还是找出来了但方向反了，顺着这条线才能定位到 bug。

这类辅助功能已经集成了一批，都以模块的形式挂在渲染管线里：点、线、面的渲染，实例渲染，半透明，颜色映射。需要哪些就组合哪些，不必为了看一眼中间结果去改渲染器。

### 交互要能定制

还剩最后一件：交互。

打游戏的时候，鼠标、键盘交互是很自然的事。仿真里的交互看着一样，需求却不一样。

同样是鼠标点击：一种场景下，你只是想拾取某个物体，知道"点到了它"；另一种场景下，你要把物体抓住，按住不放拖拽它。这两种行为对物理系统的影响完全不同，而每个开发者想要哪一种，是他自己的事。

所以交互行为必须能定制，做法还是模块化：把交互也做成模块，和仿真模块、渲染模块整合到一起。这样无论在做渲染还是在做仿真，都能调用同一套交互模块。

具体实现上有一个绕不开的动作。鼠标事件发生在二维屏幕空间里，而仿真和渲染都在三维世界空间里，两个坐标系不能直接对话。所以要结合相机参数做一次变换：

```text
屏幕空间：鼠标点击 (x, y)
        │  结合相机参数
        ▼
视锥内的一条射线
        │
        ▼
世界空间：命中的物体 / 世界坐标
```

读图：屏幕上的一个点，对应虚拟世界里视锥上的一小块平面；结合已知的相机参数，这个点可以反推成世界坐标系里的一条射线，射线打到谁，就是点中了谁。

> **易错点**：不做这步变换，直接拿屏幕坐标去改物理量，等于两个坐标系各说各话，表现就是"点哪儿都不对"。

样例里实现的是最朴素的一种：点中某个物体，给它一个冲击，把它推远。要做拖拽，就重载鼠标响应那个模块，再挂进管线，别的地方不用动。

### 多线程：三个 loop 和锁的粒度

仿真、渲染、交互三者要协作，复杂的地方不在单线程。

单线程其实很省心：所有东西顺序执行，先仿真、再渲染、再交互，或者先渲染、再交互、再仿真，都没关系，因为它就是依次调用相应模块。顺序没有那么绝对。

多线程就完全是另一回事了。至少有三个 loop 在跑：

```text
GUI loop
 ├── 收集界面与外设的交互事件
 ├── 分发 ──► 仿真 loop：仿真管线逐帧推进
 └── 分发 ──► 渲染 loop：渲染管线逐帧出图

仿真 loop 写入数据 ──[ 模块级互斥锁 ]── 渲染 loop 读取数据
```

读图：GUI loop 负责收集事件，再把事件分发给仿真和渲染两条线；后两个 loop 各自跑自己的管线。真正麻烦的是最下面那条线——一个在写，一个在读。

第一个问题是不同步。管线和管线跑在不同线程上，时序对不齐，仿真算到一半，渲染可能已经开始取了。

第二个问题是数据量。物理仿真会产生大量动态数据，几十 G 甚至几百 G，而且这些数据还要送给渲染引擎去画。这么大的一块数据，一边写一边读，读写冲突是必然的。

后果分两档：轻一点，显示不对，画面和物理状态对不上；重一点，程序直接崩。

败象具体长什么样：只有一部分模块写完了新值，渲染这时候来取，取到的就是半新半旧的一帧——一部分物体已经在新位置，一部分还停在旧位置。要是恰好读到正在被改写的内存，那就是崩溃。

所以必须引入互斥：仿真在写的时候，渲染不能读；写完了，才能读。

关键在于锁加在哪儿。不能加在整个场景上——场景的开销本来就大，一把大锁扣下去，会频繁卡顿。我们的策略是把锁加在具体的模块上：某个模块正在写，就只锁这一个模块，其他已经准备好的模块照常更新。

> **结论**：锁的粒度决定并行的上限。锁得越细，仿真和渲染越能同时推进；锁得越粗，越安全，也越卡。

### 后端、平台与规模

引擎目前有两个后端：Vulkan 和 CUDA。Vulkan 后端理论上支持移动平台。

构建的时候有一个选项要特别注意，因为默认值不是谁都适用：

| 后端 | 适用场景 | 状态 |
| :--- | :--- | :--- |
| CUDA | 有 NVIDIA GPU 的机器，默认选项 | 最稳定 |
| Vulkan | 移动平台、跨平台 | 理论支持，可能遇到各种问题 |
| 无 GPU | 确实没有可用 GPU 的机器 | 纯 C++ 实现，绕开 GPU |

默认选的是 CUDA。要用移动端，就选 Vulkan；有些同学机器上确实没有 GPU，那就选无 GPU 那一档，全部用 C++ 代码跑。要提醒一句：CUDA 那个版本是最稳定的，另外两个版本确实可能有各种各样的问题。

第三方库不用自己操心。`external` 目录下的东西会在克隆时自动拉下来，前提是加 `--recursive`——这一点前面提过，忘了加就得手动补。

规模上，SPH 在实时条件下最高大概能到 100 万粒子的量级。Mac 那边，只要 Vulkan 后端能跑通，理论上也可以；但其他平台我们确实没怎么测过，有兴趣可以自己测一下。

## 从图形处理器到并行计算：GPU 的硬件架构与 CUDA 编程模型
> 对应块：BLK03 | 覆盖分集：P02上 | 块标题（分集名）：《2. GPU硬件架构简介及CUDA编程基础》

上一周我们主要把这套系统搭起来，大家应该对它有了一个初步的认识。但只要你翻过它的代码就会发现，这套系统里塞满了 GPU 相关的代码和并行的实现——所以这门课绕不开一个问题：怎么用 GPU 来做算法的研发。

这一讲就是来补这块底子的。

### 为什么以 CUDA 为基础

现在 GPU 的后端其实挺多的。CUDA 是一种，OpenCL 是一种，Vulkan、DirectX 这些也都能做，并没有哪一个是唯一解。但总的来说，CUDA 相对最简单，也最容易上手，所以这门课以 CUDA 为基础：先介绍 GPU 的硬件架构，再介绍怎么用 CUDA 这门并行编程语言去实现并行的算法。

具体分这么几块：

- 先讲 GPU 的硬件架构，重点是它和我们以前熟悉的 CPU 到底有哪些差异；
- 再讲基于 GPU 实现算法时，整个编程模型长什么样；
- 然后重点讲两个样例：**归约算法**和**前缀和算法**（scan）。这两个用得极其普遍，你后面写仿真算法，几乎每一个都会牵涉到它们，所以拿这两个最普遍的例子来讲 GPU 编程到底要注意哪些问题；
- 接着讲一下 C++ 模板相关的东西，目的很朴素——让算法更通用；
- 最后讲这两个算法的典型应用场景，看看它们到底能用在哪儿。

分量最重的其实是中间那两个样例算法，前面两块是为它们铺路的。

### 从图形处理器到通用处理器

GPU 硬件架构的发展，这里以 NVIDIA 的架构演进为主线来捋。历史上重要的时间点非常多，但笼统地看可以切成两个阶段：2006 年以前算一个阶段，2006 年以后算另一个。

#### 2006 年以前：为渲染而生的专用芯片

2006 年以前，显卡也叫 GPU，但它主要是在玩游戏的时候做图形渲染用的，本质是一块**专用的图形处理器**。

它里面其实也有可编程的能力——最早是固定管线，后来某些阶段也能写程序——但很多功能仍然是固化的，整个芯片是为图形服务的。所以 2006 年以前这一整段，我们称之为传统 GPU 的时代。

#### Tesla：通用计算的分水岭

2006 年是一个里程碑。NVIDIA 发布了 Tesla 架构，这是一个**通用计算**的架构。

它和以前最大的差别，是把着色器模型、或者说计算模型统一了：同一套计算单元，除了图形渲染之外，还可以拿去算别的任务。以前想拿显卡做一个图形之外的计算，很多硬件是不太方便、甚至根本不支持的；模型统一之后这条路才通。

还有一层差别同样重要，就是**编程方式**。以前在显卡上编程，得写着色语言，比较典型的是 GLSL 和 HLSL，写完像脚本一样发给 GPU，编译完再执行，调试起来非常麻烦。Tesla 架构之后，GPU 直接支持 C 语言编程——对熟悉 C 的人来说，这一步的友好程度是质变。

#### Fermi 之后：大同小异的分化

2010 年 Fermi 架构发布，GPU 的通用计算架构又往前走了一步，也基本成熟了。可以说从这一代起，GPU 完成了从"专用的图形处理器"到"通用计算架构"的演化。

再往后，各家架构大同小异，差别主要体现在细节上：比如 core 的数量，Fermi 一个 SM 里是 32 个，到 Kepler 就变成 192 个；再比如各种性能上的差异。这些数字不重要，它本身只是为兼容不同任务做的调整。

真正值得一提的转折出现在 2016 年之后。过去十几年深度学习发展得非常快，Pascal 架构出来的时候，已经是在特别针对深度学习任务做支持了。再往后的 Volta 架构引入了 **Tensor Core** 这样一个计算单元，本质上是为深度学习服务的；同时它还把传统的 CUDA core 拆开了——以前的 CUDA core 里，整型计算和浮点计算是合在一个单元里的，Volta 之后开始拆。翻到 Ampere 的架构图，这个拆分已经看得很清楚。

Ampere 还有两个特点：一是支持更丰富的数据类型。int 如果是 32 位，那是 4 个字节；但很多时候我们并不需要 32 位的精度，那就可以用半精度浮点，整型也可以用 8 位、4 位甚至 1 位——用更低的精度去换更快的效率。二是 Tensor Core 继续强化，不过那是给深度学习用的，仿真这边目前探索得相对少，还是以常规计算单元为主。

一句话收束：**这些架构上的差别，对我们理解"怎么用 GPU 编程"关系不大**。因为逻辑上的架构，在第一代就已经确定下来了。

### 传统渲染管线：一条固化的流水线

看传统 GPU 的架构，最直观的入口是传统渲染管线。学图形学的一定都学过，它由几个阶段组成，最大的特点是很多功能**固化在硬件里**。

渲染的输入是比较基本的几何单元——离散的点、线段、三角面片。这些图元进来之后：

第一步是**顶点着色器**。它对每个顶点做处理：坐标变换、颜色计算、法向计算，都在顶点这个层面完成。也正因为它是为顶点这一档的事设计的，这个计算单元几乎不可能被拿去干别的计算任务。

第二步是裁剪和背面剔除，把视野之外、以及背朝镜头的图元去掉。

第三步是**片元处理**，也就是图形学里说的光栅化：把输入的点、线、面这些连续图元，转换成一系列像素。屏幕本来就是像素拼出来的，所以必须把连续的东西变成离散的点，再对每个离散点做光照等着色运算。

最后一步，按深度缓存做遮挡剔除，把每个片元送进帧缓存。

```text
顶点数据：点 / 线段 / 三角面片
              │
              ▼
    ┌────────────────────┐
    │     顶点着色器     │  逐顶点：变换 / 颜色 / 法向
    └────────────────────┘
              │
              ▼
       裁剪 · 背面剔除
              │
              ▼
    ┌────────────────────┐
    │       光栅化       │  连续图元 → 离散像素
    └────────────────────┘
              │
              ▼
    ┌────────────────────┐
    │      片元处理      │  逐像素着色
    └────────────────────┘
              │
              ▼
     深度测试 · 遮挡剔除
              │
              ▼
    ┌──────────────────────────┐
    │          帧缓存          │
    │  ├─ z buffer（深度）     │
    │  └─ RGB buffer（颜色）   │
    └──────────────────────────┘
```

整条链路上，每个环节都是硬件固化的专用单元：输入永远是图元，输出永远是帧缓存里的像素，中间不做别的事情。

帧缓存里其实是两个结构：

- **z buffer（深度缓存）**：做片元着色的时候用来体现前后的遮挡关系。有了它，被挡住的片元就不需要再往平面上送。
- **RGB buffer（颜色缓存）**：就是我们看到的那个屏幕。可以把它理解成一张三通道图像，红、绿、蓝三个通道。

从 2006 年以前一直到 Tesla 之前，整条管线就是这样一个固化下来的硬件流程。

问题在哪儿？**很多计算单元只能固化地做某一种特定任务**。而通用计算的任务类型五花八门，一个比较理想的状态应该是：每个计算单元都能按我们的需要去执行特定的任务。顺着这个方向，才逐步演化成今天看到的通用 GPU 架构。

### CPU 与 GPU 的分工：控制单元与计算单元的比例

现在这块通用 GPU 架构，和 CPU 其实非常像。把两者摆在一起看，差别就出来了。

先看 CPU。它主要包含几样东西：

- **计算单元（core）**：最核心的部分，执行指令、做运算都在这里。图中画了四个 core，所以可以多线程执行。
- **控制单元**：指令的控制、数据的存取都要靠它。
- **多级缓存**：L1、L2、L3。CPU 要把数据访问和整体计算的效率做上去，必须靠多级缓存来压低访存延迟。

CPU 的一个关键特征是**计算单元与控制单元基本一一对应**。每个计算单元都有专门的控制单元去协助它，所以它能处理更复杂的任务流、更复杂的逻辑运算。

再看 GPU。同样的元件在它这里变成了一大片：计算单元密密麻麻地铺开，控制单元只有屈指可数的几个，一级、二级缓存照样有，此外还有容量大得多的显存。不一样的地方在于：**控制单元和计算单元不是一一对应的**——一个控制单元要统管十几个计算单元。

```text
CPU：计算单元与控制单元一一对应

 ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │Core│   │Core│   │Core│   │Core│
 └────┘   └────┘   └────┘   └────┘
    │        │        │        │
  ┌─┴┐     ┌─┴┐     ┌─┴┐     ┌─┴┐
  │CU│     │CU│     │CU│     │CU│
  └──┘     └──┘     └──┘     └──┘
    L1 / L2 / L3 多级缓存

GPU：一个控制单元统管一大片计算单元

             ┌───────────────┐
             │   控制单元    │
             └───────┬───────┘
                     │
   ┌────┬────┬────┬──┴─┬────┬────┬────┐
   ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼
 ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
 │SP│ │SP│ │SP│ │SP│ │SP│ │SP│ │SP│ │SP│
 └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
      L1 / L2 缓存 + 大容量显存
```

两张示意图里的元件种类是一样的，变的只是比例：CPU 给每个核都配了一个控制单元，GPU 则用一个控制单元去带一大片计算单元。芯片面积几乎都花在了算力上，代价是控制逻辑被压得很薄。

这个比例直接决定了分工：GPU 的计算单元非常多，但控制逻辑相对 CPU 弱得多，所以它适合**计算密集型**的任务；而大量逻辑判断的活儿，是 CPU 的优势。

GPU 里那一大片计算单元并不是散着的，它们被组织成一个个固定的小集群，这个小集群就叫**流式多处理器**（streaming multiprocessor，SM）。集群里的每一个计算单元，是**流式处理器**（streaming processor，SP），也就是常说的 CUDA core。这套结构是构成一块 GPU 的基础，后面单独拆开看。

### SM 的内部：计算单元、指令收发与存储

不同的 GPU 在 SM 上会有一定差异，因为不同架构要为不同的任务做兼容性调整。但总的来说，从 Tesla 发布之后，大的结构基本就固化下来了。一个 SM 里最重要的几样东西是：

- **多个独立的处理器**。图中画了六个，每一个都可以独立执行运算指令。SP 的数量每个架构不一样，前面说的 Fermi 32 个、Kepler 192 个就是这个数，不用记。
- **指令收发单元**。计算总要先收到指令，这就需要有个地方负责指令的收发与分发。它从 CPU 那里收到一个 kernel 调用之后，把这次调用翻译成 GPU 能识别的指令，再分发到每个 SP 上去执行。
- **寄存器**。每个处理器都有自己的寄存器，用来放运算要用的数据。
- **共享存储**。这是 SM 内所有处理器共享的一块内存。

```text
                   ┌───────────────────────────┐
                   │    指令收发 / 分发单元    │
                   └─────────────┬─────────────┘
                                 │
        ┌─────────┬─────────┬────┴────┬─────────┬─────────┐
        ▼         ▼         ▼         ▼         ▼         ▼
     ┌────┐    ┌────┐    ┌────┐    ┌────┐    ┌────┐    ┌────┐
     │ SP │    │ SP │    │ SP │    │ SP │    │ SP │    │ SP │
     └────┘    └────┘    └────┘    └────┘    └────┘    └────┘
        │         │         │         │         │         │
    [寄存器]  [寄存器]  [寄存器]  [寄存器]  [寄存器]  [寄存器]
        │         │         │         │         │         │
        └─────────┴─────────┴────┬────┴─────────┴─────────┘
                                 │
                    ┌────────────┬────────────┐
                    │      shared memory      │
                    └─────────────────────────┘
```

一个 SM 就是一个自带指令分发、自带私有寄存器、还能共享一小块高速内存的小型计算集群，它是整块 GPU 里最核心的计算单元。

#### SM 里还有什么

以最早发布的 Tesla 架构为例，前面讲的几样东西基本都有，此外还有几处值得单独点一下：

- 图里的 SP 就是 CUDA core，也就是真正执行运算的那些处理器。
- 还有一部分单元专门做数学运算，比如 sin、cos 这类三角函数和特殊函数的运算，走的是特殊函数单元。
- 寄存器的数量其实很小，小到要用字节这个单位去数。这一点跟"内存几个 G"的直觉完全不一样。而且这些寄存器是 SM 里的 core 共用的资源池，某个线程占得太多，就会挤压别的线程能用的寄存器数量。
- 此外还有常量缓存、纹理缓存。
- 还有一个很重要的 **shared memory**。它比寄存器大，但也大不了太多，跟显存比起来小得非常明显。

寄存器和 shared memory 最大的好处是**存取速度非常快**。这一点在讲延迟的时候会变成关键。

#### 整数与浮点拆开之后

Fermi 的 SM 总体结构和 Tesla 差不多，主要多了两处变化。一是指令收发单元变成了两组（以前通常只有一组），指令吞吐能力更强；二是 core 的数量增加了不少。至于 core 内部，每个核主要就包含一个浮点运算单元和一个整型逻辑运算单元。

到了 Ampere，最容易看到的变化就是这两个东西被拆开了。以前 int 和 float 合在一个单元里，叫一个 CUDA core，这就带来一个限制：**它没法同时处理整型和浮点运算**。一个线程在算浮点的时候，如果下一条是整型运算，它就得等。拆成两个独立的计算单元之后，浮点和整型可以同时进行，每个单元的计算能力都能被更充分地利用。

不过 Tensor Core 那套东西是给深度学习准备的，对做仿真的人来说目前用得还不多，真正天天打交道的还是这些常规的整型、浮点单元。所以架构这一路看下来，值得记住的不是某一代多了几个核、多了什么单元，而是一句话：**逻辑架构在第一代就定下来了，后面都是在同一张蓝图上做加减**。

### 三层硬件对三层软件：grid、block、thread

硬件这一侧的组织方式，其实是清清楚楚的三层：一整块 GPU，由一系列 SM 组成；每个 SM 可以独立执行一批任务；具体到每条指令的执行，再落到 SM 里的每个 SP 上。

```text
硬件                              软件
┌────────────────┐
│      GPU       │  ◄──────────►  grid    （一维 / 二维 / 三维）
│  ┌──────────┐  │
│  │    SM    │  │  ◄──────────►  block   （一个 block 交给一个 SM）
│  │  ┌────┐  │  │
│  │  │ SP │  │  │  ◄──────────►  thread  （一个 thread 占一个 SP）
│  │  └────┘  │  │
│  └──────────┘  │
└────────────────┘
```

硬件有几层，编程模型就有几层，而且是一一对应的：grid 里的每个 block 被调度到一个 SM 上，block 里的每个 thread 落在 SM 的一个 SP 上执行。

对应到写代码，思路就是：

- 先针对一个特定任务做**分块**，每一块就是一个 block；
- 所有 block 组成一个 **grid**。grid 可以是一维、二维、三维，取决于你的问题怎么描述；
- block 内部再拆成一个个**线程**，每个线程去执行具体的指令。

grid 的维度为什么不定？因为问题本身就不定。比如做 SPH 的流体粒子模拟，粒子就是一串编号，一维的 grid 就够了；换成欧拉视角的流体，网格是二维甚至三维的，那 grid 就顺着问题做成二维或三维。维度跟着问题的描述走，没有哪个更"正确"。

那为什么一定要分 block？因为 SM 里 core 的数量是有限的。你不可能指望任意大的一个任务进来，直接整块塞进一个 SM 里——这不现实。所以必须按 block 的形式把任务切开，一块一块送进 SM 去执行。

### 从向量加法开始：一个线程算一个元素

概念讲完，落到一个最简单的例子上：输入两个数组，把对应元素逐个相加，结果存到第三个数组 c 里。

在 CPU 上这件事很容易，两行代码就搞定了：

```cpp
for (int i = 0; i < n; ++i)
    c[i] = a[i] + b[i];
```

CPU 是串行的，所以它会从 0 到 1、到 2，一直到 n-1，把每个元素依次处理一遍。效率低在哪儿？这些元素之间**相互独立**：算第 0 个的时候，完全不影响到第 1 个的计算。这种天然并行的活儿，正是 GPU 的主场。

先看一种最简单的情况：数组长度 n 小于 GPU 的 core 数量。这时候你完全可以为每个元素独立分配一个线程，一共分配 n 个线程，每个线程算一个元素——第二个线程就把 a、b 的第二对元素加起来。

CUDA 的核函数写法也围绕这件事展开：函数用 `__global__` 这个特定标识符声明，参数就是那三个数组；启动时按需申请 n 个线程，每个线程用自己的线程编号换算出要处理的下标，把 a、b 对应位置的元素相加写进 c。**一个线程只算一个元素，线程之间不通信**——这是最简单的并行形态。

### warp：GPU 真正的调度单位

上面的前提是 n 比核心数小。真实问题当然不会这么客气：数组长度往往远远超过 core 的数量。这就要引入一个 GPU 特有的概念——**warp**。

一个 SM 里的 core 差不多是 32 个，所以 32 个线程正好和 32 个 core 一一对应，一个 core 跑一个线程。可如果我要 33 个线程呢？多出来的那一个往哪儿放？

答案是把线程**分组**。硬件以 32 个线程为一个 warp 来调度。顺带说一句，一个 block 允许的最大线程数是 1024。

举个例子：假设有 72 个元素要算，以 32 为单元去切，就变成三组：32、32、8。最后一组只有 8 个元素，缺的 24 个硬件会自动补齐，最终线程数总是被凑成 32 的整数倍。这件事发生在 warp 的调度与指令分发单元里：一个 kernel 调用进来之后，它根据你申请的线程数量，按 warp 为单位切块，再逐个把 warp 送到 SM 里执行。

> **提示**：被补齐的那部分 lane 是空转的，它们并不干活，所以写核函数时通常要加一句下标越界判断，避免多出来的线程去访问数组之外的内存。

由此得到一条很实用的建议：**准备数据和分块的时候，尽量让线程数是 warp 大小的整数倍**，比如 32 的 n 倍。否则最后一个 warp 里只有 8 个计算单元在干活，另外 24 个处于闲置状态，这部分算力就白扔了。

### 同一个 warp 顺序执行，不同 warp 乱序

先假设一个 kernel 对应五条指令（编号 0 到 4，具体干什么不用管），整个任务被切成三个 warp。这三个 warp 在 GPU 里是各自独立执行的。

这里有一个必须理解清楚的边界：

- **同一个 warp 内部的指令是顺序执行的**。指令 0 执行完才轮到 1，然后 2、3、4。这是硬性要求——如果 0 还没算就直接执行 1，整个计算结果就是错的。
- **不同 warp 之间是乱序的**，也别指望 warp 0 一定比 warp 1 先跑完。

为什么会乱序？因为每条指令本身都有延迟，而指令之间又是相互独立的。一条指令要等它依赖的数据全部准备好才能执行，不同指令等待的时间长短不一样。于是就会出现这种情形：warp 0 的第一条指令已经算完，第二条要等数据，整个 warp 只能挂着；这时候如果 warp 1 的指令 0 已经就绪，调度器就转去执行 warp 1。

```text
时间 ──────────────────────────────────────────────►

warp 0 : [i0][i1][ 等 i2 所需的数据 ][i2][i3][i4]
warp 1 :       [i0][ 等数据 ][i1][i2][i3][i4]
warp 2 :            [i0][ 等数据 ][i1][i2][i3][i4]
                     ↑
              某条指令的数据还没到，整个 warp 挂起，
              调度器立刻切到另一个已经就绪的 warp
```

三个 warp 的执行节奏彼此错开，谁的数据先到谁就先走一步，看上去就是"乱序"的。

这个机制带来一条铁律：**warp 之间的数据不能相互依赖**。如果 warp 0 要用的数据依赖 warp 1 的结果，轻则计算结果出错，重则整个程序卡死——因为没有任何机制保证 warp 1 一定在 warp 0 之前跑到那一步。

### warp divergence：分支为什么会吃掉一半算力

写算法时通常会有很多分支结构：if/else 一分为二，for 循环，还有嵌套循环。这类结构的特点是在某条指令处分叉，一部分指令被执行、另一部分不执行。

问题在于，一个 warp 里的所有线程是**共用同一条指令流**的。也就是说，不管代码里写成什么样，同一时刻发射给整个 warp 的只能是一条指令。

假设一个 warp 里线程编号是 0 到 31，中间有这么一段：

```cpp
if (tid % 2 == 0)  a = 100;
else               a = 200;
```

对于编号 0 的线程，条件成立，它执行 `a = 100` 这条指令；对于编号 1 的线程，条件不成立，这条指令它不能执行。但由于整个 warp 发射的还是同一条指令，编号 1 的线程必须跟着这条指令"往前走"，只是结果被屏蔽掉，不写回。

后果就是：在 if 这一支里，**有一半线程在空等**。到了 else 那一支，局面反过来——编号 0 进不去 else，编号 1 进去了，于是偶数线程等待、奇数线程运行，同样是一半在空等。

```text
一个 warp 内的 32 条 lane（0 … 31），条件对偶数成立：

if 段    lane ：  0    1    2    3    4    5  …  31
状态      ：     跑   等   跑   等   跑   等 …  等     ← 一半 lane 空转

else 段  lane ：  0    1    2    3    4    5  …  31
状态      ：     等   跑   等   跑   等   跑 …  跑     ← 换另一半空转

按分支把线程分到不同 warp 之后：

warp 0（整条走 if  ）：if 段 32/32 活跃，else 段整段跳过
warp 1（整条走 else）：if 段整段跳过，else 段 32/32 活跃
```

算力就这样被砍掉一半。本来能同时算 32 份，实际只有 16 份在动。

解决办法其实很直接：**让同一个 warp 里的线程走同一个分支**。具体做法是把线程按分支归属分到不同的 warp 里——比如 warp 0 装 0 到 31 号线程，让它们全部走 if 这一支，那么 else 那一整段指令它们都不需要执行，整个 warp **统一跳过**，直接跳到分支之后继续；warp 1 装剩下的线程，全部走 else，那 if 那一段就整段跳过去。

这样一来，每个 warp 内部要执行的指令是一致的：要跳就一起跳，要执行就一起执行，SM 里的计算单元尽可能被填满。这就是降低 warp divergence 最关键的一点——**保证一个 warp 里的计算指令尽可能一致**，从整体上把有效算力提上去。

### 延迟与占用率：SM 什么时候在空转

既然任务已经被切成一堆 warp 轮流执行，怎么保证这个轮流的过程最高效？有两个问题需要解决：一个是刚才讲的 warp divergence，另一个是**延迟的隐藏**。

延迟是什么？不管是做运算还是去取数据，都要消耗一定的时间。这里有一组统计数字，值得记住：

- 一条运算指令，大约 **10 到 20 个时钟周期**；
- 从显存里取一个数据，大约 **400 到 800 个时钟周期**。

两者差了一到两个数量级。所以如果一个算法里有大量取数操作，整个计算就会被取数卡住——**GPU 计算的主要瓶颈在访存，不在算术**。

衡量一个 SM 干活状态好不好的指标叫**占用率**（occupancy）。因为执行是以 warp 为单元、不断往里灌的，最理想的状态是：任何时刻都有 warp 能填满 SM 的计算单元，处理器一直处于工作状态，一刻都不闲置。

但现实是，如果存在大量长延迟操作，就会出现这样的场面：三个 warp 同时进来，第一步都要去取地址，执行到某个阶段之后它们全在等数据，SM 只能干等着，直到这三个 warp 的数据都准备好才能继续往下走。这段时间里计算单元全部闲置，效率掉得非常厉害。

所以提高效率就两条路：**增加可用的 warp 数量**，或者**降低取数的延迟**。后面的优化手段，基本都能归到这两条里。

### 延迟隐藏：把等待的空档用别的 warp 填上

先看一段很短的代码：取线程 id，按 id 去取两个值，然后做一次乘法。

对应到汇编，无非两条 load 把数据搬进寄存器，再一条乘法把它们乘起来。乘法本身的延迟并不高，**最耗时间的是取数那一步**。

为了把这件事讲清楚，我把时间轴画出来。注意：真实延迟是 400 到 800 拍，按这个数画图根本画不下，所以这里假设取一次数只需要 16 个周期。

```text
时间轴（1 格 = 1 个周期；假设取数延迟 16 拍，每个 warp 只有 2 条有效指令）

warp 0 : [取a][取b][······ 等 16 拍 ······][乘][…]
warp 1 :       [取a][取b][······ 等 16 拍 ······][乘][…]
warp 2 :             [取a][取b][······ 等 16 拍 ······][乘][…]
  ⋮
warp 7 :                                              [取a][取b]
                                                         ↑
                                   此刻 warp 0 的数据已经回来，可以接着算
```

warp 0 进来，发出两条取数指令，然后挂起——SM 不会空等，它转去看 warp 1；warp 1 同样是取数、同样挂起；接着是 warp 2、warp 3……一路排到 warp 7。等 warp 7 把取数指令发出去的时候，warp 0 的数据正好回来了，它可以继续执行后面的乘法。

算一下：16 拍延迟，每个 warp 只有 2 条指令的活，所以需要大约 $16 \div 2 = 8$ 个 warp 才能把这个空档填满。这就是**延迟隐藏**——用足够多的 warp 去掩盖中间那段等待。

反过来想就更清楚了。如果这里只有一个 warp，它会执行两条取数指令，然后干等 14 拍。也就是说 16 拍里只有 2 拍在干活，占用率低得可怕。

### GPU 不是天生就快

很多人第一次用 GPU 都会有一个错觉：GPU 一定比 CPU 快。这里必须把概念掰正——**GPU 之所以快，是因为它的核多**，不是因为单个核更强。

如果你要算的问题很小，比如只有几十个、甚至只有几个元素，那点工作量根本摊不开 GPU 的巨大延迟，延迟隐藏机制也无从发挥作用（凑不出足够多的 warp 去填那个空档）。这种规模下，GPU 的运算效率并不比 CPU 快，甚至更慢。

只有当问题的规模、并行的数量上去之后，延迟隐藏才真正生效，效率才逐渐被拉起来。所以"该不该上 GPU"这件事，第一问永远是问题规模够不够大。

围绕延迟隐藏，有几条很实用的配置建议：

- **把 block 的线程数调成 warp 大小的整数倍**，避免最后一个 warp 里有一部分 lane 始终闲置；
- **别让 block 太小**。block 太小，能凑出的 warp 数量就不够，掩盖不住访问 shared memory 和 global memory 时的取数延迟；
- **block 的数量要尽可能远大于 SM 的数量**。SM 之间是可以并行执行不同 block 的，block 太少，就会有一部分 SM 从头到尾都在等活干；
- **针对每张具体的显卡多测几组配置**。影响性能的因素很多，最佳参数没有通用答案，只能实测出来。

这四条都是经验，不是定理。真正可靠的办法是把参数扫一遍。

### 多级存储：把最常用的数据放在离核最近的地方

除了堆 warp 数量，还有另一条路压延迟：用**多级存储结构**，让常用的数据待在离计算单元更近的地方。

GPU 里几种典型的存储器，从最快到最通用：

**寄存器（register）**。每个线程私有、每个 core 私有，是最快的一档。数量很少，但效率极高，用来放临时变量最合适，能显著加速计算。不同架构的寄存器数量不一样，比如 255 个这个量级。要注意它是整个 SM 共享的资源池，某个线程占得多了，别的线程能用的就少。

**局部内存（local memory）**。这是寄存器不够用时的兜底方案。线程需要的寄存器超了，总不能让程序直接跑不起来，于是硬件会分配一部分 local memory 给它。但这个东西并不是一级缓存，它其实是从 global memory 里映射出来的一块，用起来感觉像寄存器，效率却低得多。所以它要**慎用**。

**共享内存（shared memory）**。一个 block 内所有线程共享，数量也不大，但效率非常高。block 内部要交换数据，靠的就是它。

**常量内存（constant memory）**。只读的。因为只读，使用上有局限：必须在编译阶段就把内容分配好。

**纹理内存（texture memory）**。也是只读的，主要用在渲染里。

**全局内存（global memory）**。最通用、用得最多的一种，本质上就是我们说的显存。

| 存储层次 | 作用域 | 特性 | 使用注意 |
| :--- | :--- | :--- | :--- |
| 寄存器 `register` | 每线程私有 | 数量少，效率最高 | 总量是 SM 共享的池子，占多了会挤别人 |
| 局部内存 `local memory` | 每线程私有 | 由 global memory 映射而来，效率低 | 只在寄存器不够时兜底，慎用 |
| 共享内存 `shared memory` | block 内所有线程共享 | 数量不大，效率很高 | block 内协作的主战场 |
| 常量内存 `constant memory` | 全局 | 只读 | 必须在编译阶段分配好 |
| 纹理内存 `texture memory` | 全局 | 只读 | 主要给渲染用 |
| 全局内存 `global memory` | 全局 | 就是显存，最通用 | 用得最多，延迟 400~800 拍 |

这张表的排序逻辑只有一个：越靠近计算单元，容量越小、速度越快。写算法的功夫，很大程度上就是把数据尽量往表的上方放——能塞进寄存器就别放 shared memory，能放 shared memory 就别反复去读 global memory。

到这里，硬件这一侧的图景就基本齐了：三层硬件对应三层软件，warp 是真正的调度单位，warp divergence 和访存延迟是两个吃算力的地方，多级存储是压延迟的手段。接下来就可以拿归约和前缀和这两个算法，看这些道理落到真实代码里是什么样子。

## 显存层次、归约与前缀和：把 GPU 并行算法写对写快
> 对应块：BLK04 | 覆盖分集：P02下 | 块标题（分集名）：《2. GPU硬件架构简介及CUDA编程基础》

上一轮把 GPU 的线程、block、流多处理器这些骨架搭起来了，也点过寄存器、shared memory、global memory 这些名字。名字记下来不算学会——真到了写算法的时候，决定一段代码是快还是慢的，往往不是你怎么算，而是你从哪块内存里取数、取了多少次。所以先把这几块内存横着摆一排，看清各自快多少、能装多少、什么时候还看得见，再拿两个最基础的并行算法——归约和前缀和——把这件事完整演一遍。

### 内存层次：先给快慢排个序

最大的一块是显存，也就是 global memory。它对应的就是显卡上那一颗颗内存颗粒，数量很大，所以用的时候肯定是优先把数据分配在这里——数据总得先有个地方待着。但数据待在这儿，不等于计算就在这儿算：真正跑起来，还要把它用 shared memory、寄存器或者 local memory 再往上搬一层，去加速整个程序。

所以这几块内存摆在一起，代表的就是 GPU 的多级缓存结构。写算法的时候，你要依赖的就是它们各自不同的特性，去尽量发掘能提效的点。

按快慢排，站在最前面的是寄存器，也最好用。它只有一个问题：数量非常少。标准的 `int`、`float`、`double` 这类标量塞进去没问题，可你一旦要定义一个比较大的数组，寄存器这种结构根本不支持数组——编译器会把它挪到 local memory。而 local memory 实际上是映射到 global memory 的，所以这两者的效率差不多，跟寄存器比起来差了大约两个数量级。

shared memory 也很快，而且容量比寄存器大得多。这就给出了一条很实用的判断：

> **结论**：写算法时尽可能用 shared memory。一方面它相对较大，另一方面效率很高，是"容量"和"速度"折中得最好的一块。

| 内存类型 | 相对速度 | 容量 | 典型用途 |
| :--- | :--- | :--- | :--- |
| 寄存器 | 最快（基准） | 极少，只够放标量 | `int`、`float`、`double` 这类临时变量 |
| shared memory | 很快，存取开销约为 global 的百分之一 | 比寄存器大得多 | 需要反复访问的中间数据 |
| local memory | 与 global 相近，比寄存器慢约两个数量级 | 取决于显存 | 寄存器放不下的大数组，自动落到这里 |
| global memory | 慢，延迟开销大 | 最大（整块显存） | 输入输出与常驻的大数据 |

> **提示**：寄存器"最快"是有前提的——前提是数据真的在寄存器里。数组一大，它悄悄落到 local memory，速度立刻掉到跟 global memory 一个档位。很多人写 CUDA 第一次觉得"明明没碰几次 global memory，怎么还是这么慢"，答案往往就在这儿。

### 限定符与可见范围：谁在什么时候看得见

分配哪块内存不是靠猜，CUDA 给了一组标识符，写在变量声明前面：

- 想分配 shared memory，声明前面必须加 `__shared__`；
- global memory 用 `__device__`；
- 常量用 `__constant__`，这是 CUDA 的规范，写法上没有别的选择。

标识符决定"放在哪"，还有一件事决定"谁能看见"：生命周期。

寄存器的生命周期只在线程内有效——每个线程自己一份，出了这个线程就不存在了。local memory 也一样。shared memory 不同，它是整个 block 共享的，block 内所有线程都能看见、都能改。global 和 constant 再往上一层，是整个 application 的，程序里任何地方都能用。

| 内存 | 声明方式 | 可见范围 / 生命周期 |
| :--- | :--- | :--- |
| 寄存器 | 无需限定符，编译器分配 | 单个线程 |
| local memory | 无需限定符，寄存器放不下时自动使用 | 单个线程 |
| shared memory | `__shared__` | 整个 block，block 内所有线程共享 |
| global memory | `__device__` | 整个 application |
| constant memory | `__constant__` | 整个 application |

后面所有的优化，本质上都是在这张表里做取舍：把谁搬到谁那儿，换来的是更大的可见范围，还是更快的存取。

### 归约：n-1 次加法怎么摊成二叉树

第一个算法是归约。输入一个数组，从 a0、a1 一直到 an，输出是把所有元素按某个操作符合并之后的一个值。这个操作符不一定是加法，也可以是求最大值、求最小值——换一个操作符，算出来的就是不同的结果。

CPU 上做这件事很直白：从第一个元素开始，往后逐个相加，一直加到最后一个。整个是一个串行操作。n 个元素只要 n-1 次运算就做完了，写成代码就是一个 for 循环。

那 GPU 上并行性在哪儿？关键在于：这些加法并不是非得按顺序做。最后的目的就是把所有元素加在一起，那我完全可以分组——前两个先算一个值，再逐步把两两的结果算上去，一层一层收缩，最后收到一个值。这个过程其实是一棵二叉树：

```text
第 0 层    a0   a1   a2   a3   a4   a5   a6   a7
            \   /      \   /      \   /      \   /
第 1 层      s0          s1          s2         s3
              \         /              \        /
第 2 层        t0                        t1
                 \                     /
第 3 层                    total
```

图上每一层的每个节点都只依赖它下面两个节点，互相之间没有任何关系，所以同一层的节点完全可以同时算。8 个数进、1 个数出，只需要 3 层，而不是 7 步。

对应到 GPU 代码，最简单的一版是每个线程负责一个数据，然后两两相加：8 个减到 4 个，4 个减到 2 个，2 个减到 1 个。这一版有个前提——数据的数量不超过线程的数量，一个线程正好对一个数据；超了怎么办，后面再说。这里有一个必须交代清楚的细节：每一层真正干活的线程只是一部分——第一层只有一半线程在算，每个线程拿自己的下标 i，去加 i+1 那一个；越往上活着的线程越少，最后只剩一个。

线程号和数组下标不是天然对齐的，中间要做一次换算，也就是偏移。哪一层由哪个线程去算哪一对，全靠这个偏移对上；偏移一旦算错，你会看到结果每次运行都不一样，因为不同线程写到了同一块地方。

这个版本已经能跑了，但它有两个明显的问题，正好对应前面那张内存表：

> **易错点**：直接照搬"一个线程一个数据"的写法，能处理的数据量会被线程总数卡死；而且每次都从 global memory 取数，延迟开销会把并行带来的收益全吃掉。

### 规模超过一个 block：两级归约

先解决第一个问题：数据比线程多。

一个 block 的线程数上限是 1024，超过这个数，问题规模就没法用一个 block 装下。办法很直接：按 block 拆分。拆多大由你自己定，1024 以下都行——512、256、128 都可以，只要不越过上限。

```text
输入数组（长度 N，可能远大于 1024）
+---------+---------+---------+---------+
| block 0 | block 1 | block 2 |   ...   |
+---------+---------+---------+---------+
     |         |         |         |
   SM 0      SM 1      SM 2       ...
     |         |         |         |
  局部规约  局部规约  局部规约    ...
     \         |         /
      +--------+--------+
               |
     第二级：再起一个 block
               |
             total
```

每个 block 被送到一个流多处理器里去做局部规约，各自得到一个局部结果；这些局部结果汇总起来之后，再用一个 block 对它们做一次归约，就得到全局结果。数据量再大，也不过是分几级而已——这套"先局部、再汇总"的结构，是后面所有 GPU 算法共用的骨架。

### 共享内存：把数据搬到近处

第二个问题是延迟。回头看上面那个算法，它一次 shared memory 都没用，所有取地址操作都直接打到 global memory 上——而 global memory 的延迟开销很大，线程大部分时间在等数据，不是在算。

所以要做的第一件事很朴素：把数据搬过来。

```text
global memory :  [ a0  a1  a2  a3  a4  a5  a6  a7 ]   延迟大
                        |
                        |  按线程号整块拷入
                        v
shared memory :  [ a0  a1  a2  a3  a4  a5  a6  a7 ]   block 内可见，快约两个数量级
                        |
                        |  两两求和，逐层收缩
                        v
                  block 局部结果
```

shared memory 里这份数据，可以理解成 global memory 中那一段的一个镜像拷贝。搬完之后，后面所有的两两求和全部在 shared memory 上做。按前面给的数量级，它的存取开销差不多快 100 倍，这一步省下来的就是大量"取数据时干等"的时间。

代码上就是先用 `__shared__` 声明一段共享内存，把传进来的 global 数组按线程号逐个拷进去，再做和前面一样的逐层收缩。

### bank conflict：共享内存的排队规则

shared memory 快，但它有一条自己的规矩，踩上了会比 global memory 还难看。

为了让访问效率高，shared memory 被划分成大小相等的若干块，叫 bank，一共 32 个，编号 0 到 31。这个数量和 warp 是一一对应的——一个 warp 32 个线程，正好一个 bank 一个。

地址是按行铺的：连续的 32 个 32 位字占满第一行，第 0 个地址在 bank 0，第 31 个在 bank 31；再往后的第 32 个地址，又回到 bank 0。

```text
bank:   0    1    2   ...   31  |   0    1    2   ...   31
字地址: 0    1    2   ...   31  |  32   33   34   ...   63
        <---- 第一行 32 个字 ----> <---- 第二行 32 个字 ---->
```

最理想的情况是 32 个线程依次去访问这 32 个不同的 bank：一个线程一个 bank，一条指令就把 32 个数据全取出来，谁也不用等谁。

坏情况是：多个线程落到同一个 bank 里。这时候它们不能同时取，只能排队——第一个线程取完，第二个才能取。原本一条指令并行取 32 个数据，退化成了 32 次串行取数。这就是 bank conflict。

> **定义**：bank conflict 指同一个 warp 内多个线程在同一条指令里访问 shared memory 中同一个 bank 的不同地址，硬件无法一次完成，只能把这几路请求拆成多次执行。

#### 冲突从哪来

拿归约来说，如果按"前后两两成对"去取，warp 里就可能撞上。用 8 个线程的小例子看：地址 0 到 3 落在 bank 0 到 3，地址 4 到 7 又落回 bank 0 到 3。线程 0 要取地址 0 和 1，线程 4 要取地址 4 和 5——地址 0 和地址 4 在同一个 bank 上。

同一时刻两个线程都要那个 bank，就只能排。8 个线程还好，真画满 32 个线程，这种排队会把并行度吃掉一大半。

#### 把配对方式改成对半分

解法出奇地简单：不要让线程 i 去配 i+1，让它去配 `i + blockDim.x / 2`。0 配 4，1 配 5，2 配 6，3 配 7。

这两个地址可能仍然在同一个 bank 上，但它们分属两条不同的指令：第一条指令里，0、1、2、3 号线程各取自己的第一个元素，落在四个不同 bank；第二条指令里，同一批线程再去取 4、5、6、7，又落在四个不同 bank。同一时刻没有任何两个线程抢同一个 bank，冲突就没了。

```text
改之前（i 配 i+1）:
  线程 0 取 [0][1]      线程 4 取 [4][5]
  addr 0 与 addr 4 同 bank  ->  同一指令内排队

改之后（i 配 i+半）:
  第 1 条指令: [0][1][2][3]       -> bank 0 1 2 3
  第 2 条指令: [4][5][6][7]       -> bank 0 1 2 3（已换指令，不算冲突）
```

顺带还捡了一个好处：线程号挨在一起（0、1、2、3），访问的地址也连续，整个 warp 的指令能尽量保持一致，占有率也跟着上去了。

所以这段代码的改动就一句话：以前是按前后两两成对算，现在按 block 对半分，取 `i` 和 `i + blockDim.x / 2`。

### 前缀和：上扫建树，下扫回填

第二个算法是前缀和。输入还是 0 到 n 这一串数，输出稍有不同：每个位置要给出它前面所有元素按同一个操作符合并的结果——a0 就是它自己，a1 是前面的数据跟它做完操作的结果，最后一位则是从头到尾全算一遍。

这个算法比 CUDA 本身还老，是个经典的两阶段做法，一直用到今天。它分两趟。

第一趟自底向上。把每个元素当成二叉树的叶子，两两求和建出内部节点，再往上继续两两求和——和归约的上半程一模一样，最后根节点上就是全部元素的和。

```text
上扫（自底向上，两两求和）
                      [136]
                     /     \
                 [36]       [100]
                /    \      /    \
              ...    ...  ...    ...
              / \    / \   / \    / \
             a0 a1  a2 a3 a4 a5 ... a15
```

图上根是 136，左子树 36，右子树 100，36 + 100 正好 136。到这里为止，每个内部节点存的都是"我这片叶子加起来是多少"。而且整棵树不占新地方——它就在原来那个数组里就地生长，不需要再开一块空间。

第二趟自顶向下，把这些和重新分配下去：

- 根节点先被替换成 0——136 是总和，它不该加到任何一个叶子上去，因为每个位置只要它前面的和；
- 一个节点拿到一个累积值 p 之后，把 p 原样交给左子，把 p 加上"左子原来的和"交给右子。

拿具体数字走一遍：根拿到 0，左子（原来是 36）收到 0，右子（原来是 100）收到 0 + 36 = 36。再往下一层，某个节点从上面接到 36，它的左子原来的和是 42，那右子就收到 36 + 42 = 78。如此一层一层推下去。

```text
下扫（自顶向下）一个节点的改写
  节点收到累积值 36，它的左子和为 42
     左子  <- 36
     右子  <- 36 + 42 = 78
```

走到叶子，每片叶子拿到的就是它前面所有元素的和。所以结果数组的第一位是 0；末位是 120——136 减去末元素自己那一份，正好是 120，而那 136 在下扫第一步就被 0 顶掉，只在上扫时当过临时值。

到这里要说清一个容易含糊的地方：这套两阶段扫描直接产出的，是"不含自己"的前缀和——第 i 位等于它前面所有元素之和，也就是所谓 exclusive scan。要"含自己"的那一版，就在这个结果上把 a_i 自己再并进去。两种形式只差一次合并，但写代码时必须先定死用哪一种，否则后面对不上号。

### 前缀和的两个坑：空转与撞 bank

把上面这套直接搬到 GPU 上，还有两个问题。

第一个是占有率。每一层参与的线程数都减半，越往上闲置的线程越多：底层还好，只有一半在空转，往上就越来越夸张。改法和归约一样——底层不必每个元素配一个线程，隔一个配一个就行：0 号线程处理第 0、1 个数据，1 号线程处理第 2、3 个数据。线程数直接减半，空转的那一半就没了。

第二个还是 bank conflict，而且在前缀和里更麻烦：它是一棵二叉树，越往上互相冲突的可能性越大。

32 个线程的一个 warp 里，线程 0 取地址 0，线程 16 取地址 32，而地址 0 和地址 32 恰好落在同一个 bank 上。前半（0 到 15）在执行的时候，后半（16 到 31）只能等着，等于一半的并行度白扔。

> **易错点**：这类冲突不是"慢一点"，是把本该并行的指令压成串行，代价随冲突路数线性增长。

解法是填充。既然冲突的根源是地址每 32 个字就绕回同一个 bank，那就在每 32 个字后面插一个 32 位的空位——这一格数据是空的，没人用。这样第二行的 32 个地址整体错开一位，地址 32 就落到 bank 1 而不是 bank 0，两个线程各走各的 bank。

```text
不填充（stride = 32）：addr 0 -> bank 0，addr 32 -> bank 0   冲突
填充一位（stride = 33）：addr 0 -> bank 0，addr 33 -> bank 1   错开
```

代码上的表现就是给 shared memory 的索引加一个 offset。CUDA 库里的 scan 实现就是这么处理的，核心就是这一句偏移——想看得更细，可以去翻它里面具体怎么给共享内存加这个量。

### 模板：让 reduce 只写一份

算法写完了，接下来是个工程问题。

我现在针对 `int` 写了一个归约。这时候进来一个 `float` 的数组，也要归约——难道再抄一遍？抄一遍也就算了，更麻烦的是后面：你发现算法效率偏低想改进，那每一份拷贝都得同步改一遍，漏一个就埋一个 bug。

而这些实现里唯一不一样的地方，就是类型。这种"只有类型变、逻辑不变"的重复，正是 C++ 模板要解决的事。

#### 函数模板与类模板

模板的声明以 `template` 开头，后面跟一个类型名（习惯写 `typename T`），再接函数名和参数；函数体里凡是原来写 `int` 的地方，一律换成 `T`。类模板是同一套写法，只是把 `template` 放在类声明前面。

声明只是"写法"，真正生成代码是在调用的时候：编译器看到你传进来的是 `int`、`float` 还是 `double`，会自己做实例化，把对应版本生成出来。这个过程不需要你手工展开。

#### 全特化与偏特化

模板解决不了所有情况。有时候你会碰到某一类需要单独处理的东西：自定义类型，或者某个类型在这套逻辑下需要一套完全不同的实现。

举个向量的例子。一个模板 `Vec<T, dim>`，带两个参数：元素类型和维度。它本身不包含任何数据成员——真正存东西的是特化之后的版本。二维向量只需要 x 和 y，三维向量需要 x、y、z，两者包含的数据都不一样，通用模板没法替你决定。

这就叫特化，分两种：

- 全特化：模板参数全部写死。比如 `Vec<float, 2>`，类型固定 `float`、维度固定 2，所有参数都显式给出，再单独给它一份实现；
- 偏特化：只固定一部分。比如类型仍然留作模板参数 `T`，只把维度固定成 3——对"三维"这一种情况做特殊处理，其他维度还走通用版本。

编译器识别到你写了特化之后，遇到匹配的类型就优先用特化版本，用它替换掉自己默认生成的那个结构。

#### 类型和算子都做成参数

回到归约。模板化之后它需要两个模板参数。

一个类型：可以是 `int`、`float`、`double`，只要在这个类型上"归约"这个操作合法有效就行。另一个是操作符：求和、求积、求最大、求最小，都可以做成一个函数（仿函数）传进来。

代码里所有用到具体类型的地方，全部换成模板参数。调用的时候，编译器按你传入的数组类型和操作符去实例化：传求和就是求和版本，传求最大就是求最大版本。一份实现，覆盖所有组合。

### SPH 邻域查找：连续内存就是性能

前面这些东西在真实场景里怎么用？第一个场景是 SPH 里的邻域查找。

SPH 对每一个点，都要知道它周围到底包含哪些点，把这些点的 id 记下来；后面算压强、算密度都要用到这份邻域表。

用 C++ 最自然的描述方式，就是一个 `vector` 套 `vector`：外层对应粒子数量，每个元素是一个内层 `vector`，装着这个粒子的邻居 id。

这个结构能满足需求，但非常慢——问题出在碎片化。外层 vector 的数据在内存里是连续的，可每个内层 vector 的数据散落在内存的各个段上，彼此不相邻。你去取某个粒子的邻居时，地址一跳，cache 就 miss 一片。

要让 GPU 跑得动，就得把数据摆回一段连续空间里。改成一个扁平的结构：

```text
          粒子 0          粒子 1           粒子 2
ids   : [ n0_0 n0_1 | n1_0 n1_1 | n2_0 n2_1 n2_2 | ... ]
count : [    2          2            3         ... ]   每个粒子有几个邻居
offset: [    0          2            4         ... ]   邻域列表的起始下标
```

中间那条 `ids` 是真正要存的数据，所有粒子的邻居 id 全部挤在一段连续地址里；`count` 记每个粒子有几个邻居；`offset` 记它的邻域列表从哪里开始——相当于 C 里那个指向数组头的指针。

这份结构的构建，正好把前面两个算法都用上了：

1. 先用归约把 `count` 全部加起来，得到总共需要多少空间；
2. 再对 `count` 做一次 exclusive scan，得到每个粒子的起始地址——第 i 个粒子的 offset 就是它前面所有 count 之和；
3. 按总长度分配一整块 `ids`，然后各线程按自己的 offset 往里填。

```text
count : [ 2  2  3 ... ]
scan  : [ 0  2  4 ... ]   <- 每个粒子的起始下标
         |
         v
ids   : [ 粒子0的两个邻居 | 粒子1的两个邻居 | 粒子2的三个邻居 | ... ]
```

一个看起来只是"换个数据结构"的改动，背后是两个并行原语在支撑。

### 包围盒：数据量不够就别上 GPU

第二个场景很小，但很常见：输入一个几何模型或者一堆点，要求它的 bbox。

做法就是拿所有顶点分别求一次最大边界、一次最小边界，两个一夹就是包围盒。用归约，操作符换成 max 和 min，跑两趟。

但这里要说清楚一件事：这个场景不是"一定要上 GPU"。如果数据量本来就小——比如输入进来就是几个点、一个盒子，那你再去算 bbox，CPU 反而更快，光是数据搬到显存再搬回来就不划算。真正值得用 GPU 的，是输入到了 100 万个点甚至更多的时候。

> **提示**：GPU 的收益来自规模。规模不够的时候，它是负优化。

### 去重：排序、标记、扫描、回填

第三个场景是去重：输入一个数组，保留不重复的元素，把重复的删掉。做拓扑更新的时候，这个需求非常常见。

整条流水线是这样的。

第一步排序。升序降序都行，排完相同的元素就挨在一起了。

第二步标记。从左往右扫一遍：第一次出现的元素标 1，已经出现过的标 0。标 1 的位置就是"这个值要保留"。

第三步归约求和。把所有标记加起来，得到的就是不重复元素的个数——也就是最终数组该有多长。

第四步 exclusive scan。对标记数组做一次前缀和，得到每个 1 应该写到哪里。

第五步回填。按扫描给出的地址，把标记为 1 的元素依次写进新数组。

```text
排序后 :  A  A  B  B  B  C  D  D
标记   :  1  0  1  0  0  1  1  0
求和   :  4                       <- 新数组长度
前缀和 :  0  1  1  2  2  2  3  4  <- 每个 1 的写入位置
回填   :  A     B        C  D     <- 新数组
```

这条流水线里，排序之外的两步正好落在前面拆过的两个原语上：求和用归约，定位用 scan。一段看着像"业务逻辑"的代码，底下全是这两样东西在跑。

### 本讲提到的题目

**题干**：开源仓里新开了一个 `homework1` 分支。把它 check out 出来，用 cmake 重新生成一遍，在 `test/` 下面能看到一个样例工程：输入一个比较大的数组，在 CPU 上初始化完，再拷到 GPU；排序那一步已经写好，中间两个算法留空，等你去填。整个工程用 gtest 做校验——如果去重写对了，输出数组的维度应该是 20，也就是 20 个互不相同的元素。现在直接跑，它是不对的，会报错；把两个空填上之后，应该能跑通。顺带练的还有两件事：怎么用 shared memory，怎么划分 block。

**解析**：这两个空就是前面拆过的那两个原语。

求和那一处，注意 block 上限 1024，规模超了要按 block 拆成两级，先出局部结果再汇总；改法上按 `i` 与 `i + blockDim.x / 2` 配对，别让同一个 warp 里两个线程撞同一个 bank。

扫描那一处，exclusive scan 给出的是每个位置"前面有多少个该保留的元素"，也就是它的写入位置，第一位是 0；规模超过一个 block 时，同样要先做块内扫描，再把各块的总量累加到后续块的偏移上。前缀和的树形结构每一层都会减半，越往上空转越多，底层就隔一个元素配一个线程。

两处都要先把数据从 global memory 搬进 `__shared__` 声明的共享内存，再在共享内存上算，否则延迟开销会把并行收益吃掉。

**答案**：这一题不给现成代码——两个算法怎么拆、怎么落到 block 与 shared memory 上，前面已经完整拆过两遍，照着自己写。验收标准只有一个：gtest 全绿，输出长度 20。这题不做检查，纯练手；卡住的时候，回头看归约和前缀和那两节，把图上的每一层对应到线程号上，就通了。

### 矢量与张量：符号先对上几何

#### 矢量代数里的几个乘法

底子是矢量代数和张量分析。这两块前面的课里已经铺过一遍，每个运算直观上代表什么、几何上怎么解释，都讲过，我这里不重复展开。但有一条要反复提醒：看到线性代数的符号，最好顺手在脑子里换成一个图形。

$a + b$ 是平行四边形的那条对角线；$a - b$ 是从 $b$ 的终点指向 $a$ 终点的那一段；点积管的是投影和夹角；叉积 $a \times b$ 算出来是一个新的方向，这个方向跟 $a$、$b$ 都垂直；三重积最常见的身影是平行六面体的体积。符号本身很抽象，一旦能翻译成图形，后面写代码也不容易写反。

这几个运算各自的定律不一样，别默认都能交换。加法和点积是可以交换的；叉积不行，$a \times b$ 和 $b \times a$ 差一个负号；三重积交换两个向量同样会变号。结合律也不是都成立，叉积就不满足。顺序写错了，程序不会报错，只会悄悄给你一个错的结果——这类错最难查。

#### 阶数：从标量一路数到四阶

仿真论文里张量出现得极多，但"张量"是个统称，按阶数分下来其实很朴素：0 阶是标量，1 阶是矢量，2 阶是矩阵。

论文里的写法也有约定：0 阶用小写斜体，$a, b, c, d$；1 阶用粗体小写，代表矢量；2 阶往上就是一个几乘几的二维表。再往上，3 阶、4 阶在做弹性的时候会碰到——应力和应变本身都是 2 阶张量，也就是矩阵，但应力和应变之间那条线性关系，也就是本构关系，要用一个 4 阶张量去写。

阶数怎么理解？就是往某个方向上再挂一维。0 阶没有维度；1 阶挂上一列（或者一行，不同书的约定不一样）；2 阶再挂一维，摊成一张面；3 阶往纵向再叠一层，就成了一个体。所谓高阶张量没什么神秘的，就是一摞矩阵。

#### 爱因斯坦标记法：符号要能直接翻译成 for 循环

论文里习惯用不带下标的整体符号写公式，形式上极其简洁。但这种写法没法直接拿去实现：不管用 C++ 还是 CUDA，最后落到代码里都是项与项之间的乘加。

所以实现的时候要换成爱因斯坦标记法——公式全部带下标。好处是下标直接对应循环：$i$ 是哪一层、$j$ 是哪一层，写 for 循环的时候一目了然，不会写着写着把该求和的维度漏掉。

这里面有一对概念必须分清：

> **定义**：**显式指标**在等式两边都出现，取值固定，左边是 $ij$，右边也必须是 $ij$，不能换。**哑指标**只在等式某一侧出现（前面没出现过），它必须遍历这个方向上的所有取值再求和。

比如 $3 \times 3$ 的张量，哑指标 $k$ 就要取 0、1、2 三个值，对应三项相加。维度变了，遍历的次数跟着变。

这一块内容其实非常深，真要系统学，黄克智老师的《张量分析》值得读。书里的东西比我这里讲的一节多得多，后面要往仿真里钻，张量分析是最底层的一块基础，早晚要补。

#### 论文里那些符号分别是什么运算

我把常见的符号列一遍，目的不是让你们背，而是下次在论文里撞见时不至于完全不认识——至少能反应过来"这是张量里的哪一类运算"，再去翻书就有方向。

下表以二阶张量 $A$、$B$ 为例，所以下标只有 $i$、$j$ 两个：

| 运算 | 下标写法 | 结果的阶 | 换成矩阵运算是什么 |
| :--- | :--- | :--- | :--- |
| 和 / 差 | $A_{ij} \pm B_{ij}$ | 2 阶 | 对应元素相加减 |
| 数乘 | $c\,A_{ij}$ | 2 阶 | 每个元素都乘 $c$ |
| 点积 | $A_{ik} B_{kj}$ | 2 阶 | 矩阵乘法，$k$ 求和 |
| 转置 | $A_{ji}$ | 2 阶 | 行列互换 |
| 双点积（缩并） | $A_{ij} B_{ij}$ | 0 阶 | 全部元素对应相乘再求和 |
| 并矢 | $a_i b_j$ | 2 阶 | 两个向量的外积 |

和差最直观：要算结果的 $ij$ 元素，就拿 $A$ 的 $ij$ 元素加或减 $B$ 的 $ij$ 元素。这里的 $i$、$j$ 是显式指标，两边必须对齐，一个都不能换。数乘同理，标量乘一个张量，等于标量跟张量里每一个元素相乘。

点积是张量里比较特殊的一个，学过线代的人一眼能认出来，这就是矩阵乘法。按 $A \cdot B$ 算 $ij$ 元素，得到的是 $\sum_k A_{ik}B_{kj}$：$i$、$j$ 固定不动，中间那个 $k$ 是哑指标，$3 \times 3$ 的情形就是三项加起来。

转置是把 $i$、$j$ 换个方向。缩并（冒号那个符号）是对两个二阶张量做的，做完变成一个标量——等号左边一个下标都没有，所以 $i$、$j$ 全成了哑指标，所有元素对应相乘再相加。

并矢是把两个一阶张量升成二阶：从 $a$ 里取第 $i$ 个、从 $b$ 里取第 $j$ 个，乘起来填进二阶张量的 $ij$ 位置。粒子法里按邻域去算 shape tensor 的时候，用的就是它。

> **提示**：转置不是二阶张量特有的。三阶张量一样能转置，任取两个下标对调就行：对 $i$、$j$ 转置是 $A_{jik}$，对 $j$、$k$ 转置是 $A_{ikj}$。四阶、五阶同理。有些运算可以原样推广到高维，有些不行，用之前查一下。

这些运算在后面的仿真计算里或多或少都会撞上。现在混个脸熟，将来碰上再翻回来对一眼，或者直接去书里查。

### 图元：表示、代码与参数化

三维空间里常用的图元就那么几类，按维度排下来：

```text
三维几何图元
├─ 点     点、粒子（particle）
├─ 线性   直线 / 射线 / 线段
├─ 面     无穷平面 / 三角形（四边形 = 两个三角形拼起来）
└─ 体     球 / 胶囊 / 四面体 / AABB / OBB
```

每个图元我都按三样东西讲：几何表示是什么、代码里怎么定义、参数化形式长什么样。第三样最有用——后面算距离、算相交，基本都是把"找最近点"翻译成"求参数"。

这几类图元本身都很简单，但再复杂的结构也是它们拼出来的：一个模型是一堆三角形，一个人形是一堆胶囊，一个刚体外面套一个 OBB。所以把每个图元的表示和参数化吃透，后面搭什么都不会心虚。

#### 点与线性结构

点是最好理解的：几何上就是一个位置，代码里就是 $(x, y, z)$，粒子法里的一个 particle 就是一个点。

这里有个问题值得说一句：三维向量本身也是三个 float，为什么还要单独定义一个点的结构？因为 C++ 是封装、面向对象的写法，点参与的运算和向量不一样——向量关心的是加、点乘、叉乘，点关心的是"到别的图元的距离"。单独定义，才好把距离计算这类接口挂在点上。

直线需要两个东西：一个原点和它的一个方向。原点放在哪里其实无所谓，往前挪一点往后挪一点，直线还是那条直线，只是参数值跟着变；方向朝哪头也一样，影响的只是 $t$ 的正负号。

$$x(t) = o + t\,d,\qquad t \in (-\infty, +\infty)$$

两头都能无限延伸，所以 $t$ 取遍整个实数轴。代码里只存原点和方向两个矢量，$t$ 不存——它是计算过程中算出来的中间量。

射线跟直线结构完全一样，唯一区别是只有一半：

$$x(t) = o + t\,d,\qquad t \in [0, +\infty)$$

$t$ 只能从 0 往正方向走，不能到负无穷。这是个人为约定，反过来定也能用，但大家习惯这个方向。数据结构上跟直线一模一样，靠类型区分，不需要把 $t$ 塞进结构里，两个三维矢量就够。

线段稍微不一样。可以按前面那套写：原点 + 方向，$t \in [0, 1]$。但更省事的写法是直接存两个端点 $v_0$、$v_1$，中间任意点用插值表示：

$$x(t) = (1-t)\,v_0 + t\,v_1,\qquad t \in [0, 1]$$

两个权重 $1-t$ 和 $t$ 加起来恒等于 1，这就是"点在两点之间"的代数表达。$t$ 始终被限制在两端之间，超不出去。

三种结构放在一起看，差别只有一处：

| 图元 | 参数化 | $t$ 的范围 | 代码里存什么 |
| :--- | :--- | :--- | :--- |
| 直线 | $o + t\,d$ | $(-\infty, +\infty)$ | 原点、方向 |
| 射线 | $o + t\,d$ | $[0, +\infty)$ | 原点、方向 |
| 线段 | $(1-t)v_0 + t\,v_1$ | $[0, 1]$ | 两个端点 |

> **提示**：正因为只差 $t$ 的范围，后面点到这三种图元的距离可以用同一套代码算，只在最后按类型截断 $t$。

#### 平面与三角形

平面靠两样东西定下来：一个原点当参照，一个法向定朝向。平面有个性质——平面上任意一点跟原点连成的向量，一定跟法向垂直。写成式子：

$$(x - o)\cdot n = 0$$

点积等于 0 就是垂直，这条式子的意思翻译过来就是"$x$ 在平面上"。把点积按分量展开，就变成解析几何里那个熟悉的形式：

$$Ax + By + Cz + D = 0,\qquad (A, B, C) = n,\qquad D = -n \cdot o$$

对照一下就知道，$A$、$B$、$C$ 单独拎出来正好是平面的法向。所以代码里也只存原点和法向，平面上的点 $x$ 是算出来的，不存。后面讲 GJK 的时候会用到这个表示。

三角形是图形学里最核心的图元，渲染到最后全拆成三角形。它的定义就是三个顶点，但有一点必须记牢：顶点有顺序，一般约定逆时针。

> **易错点**：三角形顶点顺序搞反，不只是"法向朝里朝外"的问题。做碰撞检测时正反面判错，物体可能直接穿过去——因为程序要靠表面朝向判断哪一面是外面，穿透判定完全建立在这个基础上。

一个闭合体的表面，所有三角形必须统一顺序，全逆时针或者全顺时针，这样才能一致地判断每个面朝外还是朝里。混着来、一部分逆时针一部分顺时针，后面一定会出错。这条约定对四边形和其他多边形同样适用。

三角形内部的点用两条边参数化。取 $e_0 = v_1 - v_0$、$e_1 = v_2 - v_0$，则

$$x(s, t) = v_0 + s\,e_0 + t\,e_1,\qquad s, t \in [0, 1],\quad s + t \le 1$$

> **提示**：约束不是 $s + t = 1$。等于 1 只能落在一条边上，三角形内部的点满足的是 $s + t \le 1$；写等式就把整个面压缩成一条边了。

按右手法则算一下 $e_0 \times e_1$，得到的法向正好朝外，这一点在判断"哪面是外面"时很有用。代码里它就是三个顶点的数组。

#### 球与胶囊

球只要两个参数：中心点和半径。球内的点满足

$$\|p - c\|^2 < r^2$$

代码里就是一个中心点加一个半径，没有别的。球最大的好处是计算方便——不管求交还是求距离，只要跟中心点算一下就够了。

胶囊在游戏引擎里用得非常多。人体的布娃娃系统，说到底就是一堆胶囊拼出来的骨架。它本质上是一条线段加一个半径：中心线是线段 $v_0 v_1$，表面上任意一点到这条线段的距离都等于半径。

等于把球"拉长"了——球心从一个点换成一条线段，别的规则不变。好处是能表示细长的结构，代价却几乎没涨：算点到胶囊的距离，就是先算点到中心线（线段）的距离，再减半径，前面那套线段距离直接能用。

#### 四面体

四面体在弹性和有限元里很常见，定义就是四个顶点。这里还是那个老问题：顶点编号必须统一。

> **易错点**：编号顺序错了，算出来的体积会是负的。体积一旦为负，后面算压强就会出问题——这类错误不会让程序崩，只会让结果莫名其妙地不对。

四面体也有参数化形式，三个参数 $u, v, w$ 分别对应三条边 $e_0, e_1, e_2$：

$$x(u, v, w) = v_0 + u\,e_0 + v\,e_1 + w\,e_2$$

> **提示**：四面体有四个顶点，重心坐标是四个权重，加起来等于 1；前三个是 $u$、$v$、$w$，剩下那个留给 $v_0$。所以落点在四面体内部的约束是 $u, v, w \in [0, 1]$ 且 $u + v + w \le 1$——取等号时正好落在 $v_1 v_2 v_3$ 那个面上。

#### AABB 与 OBB

这两个是做碰撞检测时最常用的包围盒，后面讲刚体会反复用到。

AABB 只需要两个顶点，最小角和最大角。计算极简，这是它存在的理由：碰撞之前先粗筛一遍，把明显不可能碰上的物体对剔掉，只对剩下的做精确检测。

它的问题是不够紧致。物体斜着放的时候，轴对齐的盒子会空出一大块。OBB 就是冲着这个来的——把 AABB 转个方向，让它贴着物体。

OBB 的定义：一个中心点（跟 AABB 一样），三个互相垂直的单位轴 $u$、$v$、$w$，再加上各方向的半长，也就是中心到对应面的距离。$u$、$v$、$w$ 张成的其实就是一个旋转矩阵，它描述的是"AABB 转过什么角度之后变成了这个 OBB"。

所以结构上它差不多是四个三维向量——中心点加三个轴，半长另存。物体沿着任意朝向摆放时，OBB 都能给出比 AABB 紧得多的包围盒；代价是它比 AABB 多了一层朝向，判定起来没那么干脆。

### 距离计算：先无约束求投影，再按边界截断

图元定义完了，接下来用它们算东西。距离计算的组合非常多，这一讲只讲点到图元：点到点、点到线性结构（直线、射线、线段）、点到平面、点到三角形、点到球。这几个覆盖了前面定义过的全部图元，也是后面真正会用到的。

点到点不用多说，两个坐标相减取模。

剩下的几种有一个共同套路，先记住它，后面每一节都是它的变体：**先不管边界，按无约束的情形求出投影；再根据图元本身的范围，把参数截断**。直线、射线、线段之所以能写成同一套代码，就是因为它们只在 $t$ 的范围上有区别。

#### 点到线性结构

把线性结构统一写成原点 $v_0$ 加方向 $d = v_1 - v_0$。点 $P$ 对应的参数坐标是

$$t = \frac{(P - v_0)\cdot d}{d\cdot d}$$

这就是把 $P - v_0$ 投影到方向 $d$ 上。注意分母是 $d\cdot d$，没有开根号——方向不做归一化。

这个式子怎么来的？所谓最近点，就是让 $P$ 到它的连线跟方向垂直的那一点。写成 $(P - v_0 - t\,d)\cdot d = 0$，解出 $t$ 就是上面那个式子——垂直条件天然把 $t$ 定死了。

> **提示**：这不是偷懒，是刻意的。归一化要多开一次根号，而开根号的代价比加减乘高得多。把"不归一化"贯彻到底，分母补一个 $d\cdot d$，整个计算里就不出现开根号。

拿到 $t$ 之后按图元类型截断：

```text
输入: p、线性结构（原点 v0、方向 d = v1 - v0）
        │
        ▼
  t = (p - v0)·d / (d·d)        ← 方向不归一化
        │
        ▼
  按类型截断 t
        ├─ 直线: 保持原值          t ∈ (-∞, +∞)
        ├─ 射线: max(t, 0)         t ∈ [0, +∞)
        └─ 线段: clamp(t, 0, 1)    t ∈ [0, 1]
        │
        ▼
  q = v0 + t·d    →    distance = |p - q|
```

截断的几何含义很直白：$P$ 投影到 $V_0$ 外侧的时候，离它最近的根本不是投影点，而是端点 $V_0$ 本身，所以把 $t$ 拉回 0；线段同理，超出上界就拉回 1。截断完再算 $|P - q|$，三种图元共用一套代码。

直线不需要任何截断，投影点就是最近点，直接算 $|P - q|$ 就是点到直线的距离。

#### 点到平面

平面是无穷大的，投影点一定落在平面上，所以不需要截断，一路算到底。投影点

$$q = p + \frac{(o - p)\cdot n}{n\cdot n}\,n$$

第二项是从 $p$ 指向投影点的方向向量。$n$ 归一化过的话分母就是 1，不归一化就除以 $n\cdot n$，还是那条避免开根号的原则。

它的来源也很直接：设投影点 $q = p + \lambda n$，要求 $q$ 落在平面上，即 $(q - o)\cdot n = 0$。代进去解出 $\lambda = \dfrac{(o - p)\cdot n}{n\cdot n}$，就是上面那个系数。

这里有一个特殊之处：返回的是有向距离，不是绝对距离。

$$d = \frac{(p - o)\cdot n}{\|n\|}$$

$n$ 指的那一侧为正，背面为负。

> **结论**：绝对距离的取值范围是 $[0, +\infty)$，有向距离是 $(-\infty, +\infty)$。多出来的那个符号，就是用来判断点在哪一面的。

为什么非要这个符号？刚体掉到地面上，光知道"碰上了"不够，还得知道是从哪一面穿进去的、穿了多深。有了符号，穿透方向一目了然，算约束的时候直接可用。要是只有绝对距离，还得再补一次判断，既慢又容易写错。后面的碰撞处理、动力学计算都会依赖这个约定。

#### 点到三角形

三角形是有界的，三条边把它圈住了。投影点完全可能落在三角形外面，所以不能像平面那样一路算到底，必须按落点所在的区域分别处理。

跟平面相比，多出来的就是那两个参数坐标 $s$、$t$——平面没有边界，一个法向就够了，不存在"内部点、边上点、角点"的区分；三角形有边界，落点一旦出界，最近点就得从面上换到边上或者角上，这一步全靠 $s$、$t$ 的值来判断。

这一段的本质是个约束优化：

$$\min_{s,t}\ \|x(s, t) - p\|^2,\qquad x(s, t) = v_0 + s\,e_0 + t\,e_1$$

取平方是为了免掉开根号，最小值的位置不变。

先把约束丢掉，当成无约束问题解。把 $\|x(s,t) - p\|^2$ 展开，得到 $s$、$t$ 的二次式，对 $s$ 和 $t$ 各求一次偏导，令偏导为零，就得到一个二元一次方程组：

$$\begin{cases} a\,s + b\,t = e_0 \cdot (p - v_0) \\ b\,s + c\,t = e_1 \cdot (p - v_0) \end{cases},\qquad a = e_0\cdot e_0,\quad b = e_0\cdot e_1,\quad c = e_1\cdot e_1$$

这没什么新鲜的，就是本科线代里两个方程、两个未知量。极值一定出现在偏导为零的地方；而这个目标函数是二次的，导数为零的点就是极小值点，不会出现鞍点那种情况——这一点可以放心。

解的存在性看系数行列式 $ac - b^2$。$a$ 是 $e_0$ 跟自己的点积，$c$ 是 $e_1$ 跟自己的点积，$ac - b^2 = 0$ 就等价于 $e_0$ 和 $e_1$ 共线。这时候输入的三角形是退化的（三个顶点共线），解不唯一，只能退化成点到线段的距离来计算。

解出来的 $s$、$t$ 是"无约束最优"，可能早就跑到 $[0, 1]$ 外面去了。这一步的目的不是拿最终答案，而是先把落点定位出来，再看它落在哪个区域。

划分的办法是把参数平面按 $s + t = 1$ 这条斜线切成两半：$s + t \le 1$ 的一侧，只可能落在内部和靠近 $v_0$ 的那两条边一带；$s + t > 1$ 的一侧，是越过 $v_1 v_2$ 那条边的地方。之后再按 $s < 0$、$t < 0$ 逐个筛：$s < 0$ 先把范围收到 $v_0$ 附近两个区，再看 $t < 0$，就锁到 $v_0$ 那个角上。落在边区的，最近点在该边上，问题退化成点到线段；落在角区的，最近点就是角点。

参数平面这样切下来一共七个区域——一个面区、三个边区、三个角区。判定落在哪个区，最近点的参数坐标也就定了。三种情形对应三种算法：

| 落点区域 | 最近的特征 | 计算退化成 |
| :--- | :--- | :--- |
| 三角形内部 | 面内的投影点 | 直接算点到该投影点的距离 |
| 某条边的外侧带 | 该边上的最近点 | 点到线段 |
| 某个角点的外侧扇区 | 该角点 | 点到点 |

> **提示**：点 $P$ 和三角形不一定共面。不要先想着"投影到平面上找垂足 $O$"，再拿 $O$ 往下算——多一步平面投影，开销反而更大。直接在参数平面上解这个二维优化，一步到位。

#### 点到球

球最简单：

$$\text{dist}(p) = \|p - c\| - r$$

中心到 $P$ 的距离减掉半径，就是点到球面的距离。

跟平面一样，它返回的也是有向距离：点在球外为正，点在球内为负。碰撞检测和动力学里同样靠这个符号判断有没有穿进去、穿进去多深。这也是球在仿真里好用的原因——一个减法就把距离和内外关系全说清了。

点到这几类图元的距离到这里就齐了：线性结构靠截断 $t$，平面靠投影加符号，三角形靠二维优化加区域判定，球靠中心距减半径。再往下是另一个专题——相交测试。

## 几何距离与相交测试：算法、极端情况与验证场景
> 对应块：BLK06 | 覆盖分集：P03下 | 块标题（分集名）：《3. 计算机图形学常用几何工具及数学原理》

点跟球的距离算完，事情还比较简单。接下来才是真正要花力气的地方：胶囊体、四面体、AABB、OBB，一路下来你会发现它们都在做同一件事——把"点到某个形状的距离"化简成"点到更简单的元素的距离"，而这条化简链的尽头，是线段、平面和坐标轴。再往后是相交测试，那是碰撞检测真正要吃的东西。最后我想带你们把这些算法搭成一个能直接用手拖、能在屏幕上看见交点的场景，因为代码写对了和代码测过了，完全是两回事。

### 点与胶囊体：把球心拉成一条线

胶囊体（capsule）本质上就是对球体的一个拓展：原来球只有一个中心点，现在把这个中心点换成一条中心线。就这么一个改动，形状从一颗球变成了一根两头圆、中间直的火腿肠。

正因为形状是这么来的，点到胶囊体的距离计算可以直接退化：先算点到线段（比如 $v_0v_1$ 这条线段）的距离，再减去半径 $r$。

$$d(P,\ \text{capsule}) = \operatorname{dist}(P,\ \overline{v_0v_1}) - r$$

线段这一块前面已经介绍过了：点到线段上任意一点的距离、线段上离点最近的那个位置，都能很方便地算出来。减掉半径之后得到的是带符号的距离，减出来是负的，说明点已经在胶囊体内部了。

胶囊体之所以在工程里用得这么多，原因有两个。一是计算便宜：它退化成了点到线段的距离，而点到线段是这套几何工具里最便宜的操作之一。二是形状合适：人体、四肢、躯干都是长条形的结构，用一根胶囊体去近似，比用一堆球拼起来省得多。很多游戏引擎里都会大量用到它。

### 点到四面体：用四个面把空间分区

点到四面体的距离，问题形态跟前面的三角形一样：离它最近的点可能落在某一个面上，也可能落在某一条边上，还可能正好是某一个顶点；如果点干脆在四面体内部，它到实体的距离就是零。这几种情况都有可能发生，一个都不能漏。

麻烦的是这些情况怎么写进代码。如果要写 CUDA 的算法，前面已经强调过：尽可能减少分支结构。分支对 CUDA 这种并行计算语言不太友好——同一个 warp 里如果有线程走进不同的分支，其余线程只能等着，很多线程实际上占不满。如果按"先判断最近点是落在边上还是落在面上"这种思路分别独立去算，判断本身就引出了一大堆分支，在 GPU 上非常吃亏。所以这里的目标很明确：把分支降下来。

比较理想的做法，是利用四面体只有四个面这个事实，用这四个面把空间切成几块。

每个面都有一个朝外的法向，它所在的平面把空间分成正侧（法向那一侧）和负侧（法向的反方向）。拿点对四个面分别判一次：

- 如果点在四个面的负侧，那它就在四面体内部；
- 如果点在若干个面的正侧，那它只可能跟这些面有关。

```text
                         ┌── 四个面都在负侧 ──> 内部：算 4 个三角形距离取最小
点 P 相对四面体的四个面 ─┤
                         └── 有若干面在正侧 ──> 只算这些外侧面的三角形距离取最小
```

读图说明：判定的产物不是一个"是/否"，而是"哪几个面在外侧"；后面只需要处理这几个面。

内部的算法很简单：跟四个三角形分别做一次距离计算，取最近的那个，就是点到体表面的最近距离。这里要区分两种口径——如果你要的是"点到这个实体"的距离，内部就是零；但工程上通常更关心"点到表面"的距离，它就是穿透深度。

如果点在某些面的外侧，那就只针对这些外侧的面处理。比如判定下来，点同时处在第一个面和第二个面的外侧，那后面两个面根本不需要算，只需要对这两个面各算一次点到三角形的距离，再取最近的。这样一方面把计算量降下来，另一方面也把分支压下去了。

实际代码也许没有做到最简。为了写得简单直接，它是对四个面分别做了一遍距离计算，然后挑最近的那个。这样也能得到正确结果，唯一的缺点是多算了几步：那些明显在外侧的反面其实可以先剔掉，剔掉之后整个开销还能再降一截。整个逻辑是一个循环，分支结构相对很少，对 CUDA、GPU 来说是比较友好的写法。

> **提示**：判断"正面/负面"一定要用朝外的法向。法向朝外时，负侧就是体内；如果拿到的法向朝里，整套判断会整个反过来，内部会被判成外部。

### AABB 与 OBB：在坐标轴上把距离算完

AABB 的思路跟四面体是一样的，但计算上更简单。为什么更简单？因为它根本不需要算点到平面的距离。AABB 的六个面全都平行于坐标平面，想知道点在哪一侧，比较一个坐标分量就够了：$X$ 坐标比 $x_{\max}$ 还大，就说明点在 $X$ 正方向那个面的外侧，连点积都不用做。

所以算法结构照搬四面体那套——判定点处在哪些面的外侧，只对这些面算距离取最小——但每一步的判定成本降到了常数级，只需要分别对 $X$、$Y$、$Z$ 三个轴各判断一次。这部分就不展开写了，有兴趣可以直接去看源码里的实现。

OBB 跟 AABB 是一回事，本质上就是一个旋转了某个方向的 AABB。做点到 OBB 的距离计算时，一般先把它转回去：构造一个变换矩阵 $T$，$T$ 里包含三个方向向量 $\mathbf{u}$、$\mathbf{v}$、$\mathbf{w}$，再加上一个平移。这是一个齐次坐标下的变换矩阵，作用是把 OBB 所在的坐标架换成标准坐标架。在这个标准坐标系下把它当成 AABB，算完距离或者做完相交测试，再把结果转回 OBB 原来的坐标架。这样整个效率会高不少。

> **提示**：因为 $\mathbf{u}$、$\mathbf{v}$、$\mathbf{w}$ 是正交单位向量，这个变换的逆很好求，不需要真的去做矩阵求逆，转回去的开销同样很低。

有人问过："变换点会不会更快一点？"——这两件事其实是一回事。所谓变换点，就是把顶点分别乘上旋转矩阵，顶点的坐标就变到了标准坐标系下；距离计算里做的正是这件事，只不过被变换的是查询点，而不是盒子的八个顶点。

OBB 在后面做碰撞检测时会反复用到，尤其是宽阶段的粗筛和窄阶段的精确判定。

### 相交测试为什么总归到"线"上

相交测试主要在碰撞检测的场景里用，刚体模拟里会有大量的碰撞检测。一个物体穿透到另一个物体之后，我们要判定它们相交的时刻，还要知道相交的点在哪里——时刻和位置都拿到了，才谈得上把穿透推开、把冲量算对。

复杂的碰撞检测，很多时候可以简化成点跟物体的碰撞。为什么可以这样简化？因为整个过程在时间上是动态的：从这个时刻到下一个时刻，哪怕参与碰撞的只是一个点，它在空间里也连成了一条线段。于是"这个点在运动过程中有没有撞上别人"就变成了"这条线段有没有跟别的几何结构相交"。所以把时间维度加上去之后，大量的连续碰撞检测问题，最终都会退化成线形结构跟基本几何图元（平面、球、三角形、包围盒）的相交问题。这也是我要专门讲线跟这些图元怎么相交的原因。

> **提示**：后面所有推导我都按无限长的直线写，因为公式最干净。换成射线或线段只多一步：算出 $t$ 之后，用 $t$ 的取值范围去截断——射线要求 $t\ge 0$，线段要求 $t\in[0,1]$。这一步放在最后做，不影响交点本身的求解。

### 直线与平面：先处理除零

直线是参数方程：

$$P(t) = O + tD$$

平面是：

$$Ax + By + Cz + D_0 = 0$$

写成点法式就是 $n\cdot P + D_0 = 0$，其中 $n=(A,B,C)$ 是平面的法向。

如果在某个 $t$ 上两者相交，那么这个位置既要满足直线的参数方程，又要满足平面的方程——同一个点，两套方程同时成立。做法就是把直线代进平面：把 $O+tD$ 替换进去，

$$n\cdot(O + tD) + D_0 = 0$$

展开之后按 $x$、$y$、$z$ 三个分量写就是分量的线性组合，跟上面这一行完全等价。整理一下就能解出 $t$：

$$t = -\frac{n\cdot O + D_0}{n\cdot D}$$

代码里对应的就是"$n\cdot O$ 加上常数项，除以 $n\cdot D$，再取负"。

> **提示**：平面方程写成 $Ax+By+Cz+D=0$ 时，最后那个 $D$ 是常数项（本文记作 $D_0$，免得跟方向向量撞名）；直线参数方程里的 $D$ 是方向向量。两个 $D$ 完全不是一回事，写代码时用不同的变量名，读代码时先看清这个符号指的是谁。

这里有一个必须在代码里处理的问题：$D$ 的方向有可能跟平面平行。这时候分母 $n\cdot D$ 等于零——法向和方向互相垂直，点积当然是零。实现时一定要对除零单独处理，否则会直接除出 NaN 或者无穷大，整个结果就废了。

对这种无效值，代码里的处理是返回 0，也就是暂且判定它不发生碰撞。处理方式怎么实现都可以，但要清楚它是有歧义的：如果直线一开始就整个躺在平面内部，那它到底算相交还是不算相交，其实没有唯一答案。这取决于具体应用——有些应用可以假设它处在不发生碰撞的状态，另一些应用可能恰恰需要把它算成碰撞。极端情况的判定策略要按应用来调。

布料仿真里就能看出这个歧义有多实际。假设一条线段正好落在三角形所在的平面上，你判定它相交，那接下来怎么办？你不知道布料的那一层到底在三角形的哪一侧，正面反面都分不清，于是"往上推还是往下推"就没法决定，只能再借助别的信息。反过来，如果你判定它不碰撞，那就先不给力，让它靠别的约束慢慢分离出去，等它明确落到某一侧之后再来判定。两种策略都合理，关键是你要知道自己在哪种策略下写代码。

### 直线与球：一个一元二次方程

线形结构跟球的相交有三种情况：两个交点、一个交点（相切）、没有交点。直观判断很容易：球心到直线的距离小于半径就有两个交点，等于半径正好一个，大于半径就没有。

但碰撞检测不能只判"交不交"，还要找触点，所以必须把位置精确算出来，这就得回到参数形式。球只需要考虑表面，内部不用管——我们要找的是这条线与球面的交点。

球面方程：

$$(P - C)\cdot(P - C) = r^2$$

把 $P = O + tD$ 代入，逐步展开：

$$(O - C + tD)\cdot(O - C + tD) = r^2$$

$$t^2(D\cdot D) + 2t\,D\cdot(O-C) + (O-C)\cdot(O-C) - r^2 = 0$$

这就成了一个关于 $t$ 的一元二次方程 $at^2+bt+c=0$，其中

$$a = D\cdot D,\qquad b = 2D\cdot(O-C),\qquad c = (O-C)\cdot(O-C) - r^2$$

$a$ 就是方向向量跟自己的点积，方向取单位向量时 $a=1$，这就是为什么前面说 $a$ 对应的是 1。$b$、$c$ 都是常量，里面不含 $t$。

判别式 $b^2-4ac$ 决定有几个根：大于 0，两个根不相等，对应两个交点；等于 0，两根重合，对应相切的一个交点；小于 0，没有实根，直线整个从球旁边过去了。我们算的都是实根——复根在几何上没有意义。

$$t_{0,1} = \frac{-b \pm \sqrt{b^2-4ac}}{2a}$$

拿到 $t_0$、$t_1$ 之后还没完。上面的推导是按无限直线做的，换成射线或线段要按范围截断。最典型的例子是射线从球内部往外打：这时候其实只有一个交点，但方程照样给出两个根，其中 $t_0<0$ 的那个必须剔掉，因为它在射线方向上不成立，是直线"反向延长"出去的部分。线段同理，只保留 $t\in[0,1]$ 的根。

### 直线与三角形：三个未知量、三个方程

三角形在布料仿真里用得非常多。做布料的时候，需要判定一个顶点跟一个三角面片、或者跟一条边有没有可能发生穿透，这就依赖线跟三角形的相交检测。

三角形的参数形式用重心坐标写：三个权重 $u,v,w$ 满足 $u+v+w=1$，所以 $w$ 可以直接写成 $1-u-v$，真正独立的未知量只剩两个。于是三角形上的任意一点可以写成

$$P = uV_0 + vV_1 + wV_2 = V_0 + u(V_1-V_0) + v(V_2-V_0)$$

相交点的定义是：直线上存在一个 $t$，使得 $O+tD$ 正好落在这个三角形上。也就是

$$O + tD = V_0 + u(V_1 - V_0) + v(V_2 - V_0)$$

这个式子的意思很直白：直线上那个点和三角形上那个点重合。把右边的项挪到左边整理一下，它就是一个线性方程组——未知量是 $t$、$u$、$v$ 三个，方程数也正好是三个（$x$、$y$、$z$ 各一个）。

三个未知量、三个方程，理想情况下应该有唯一解。线代里学过：$Ax=b$ 有唯一解的条件是 $A$ 满秩，也就是不奇异；否则可能无解，也可能有无穷多解。

这里的系数矩阵由三个向量拼成：方向 $D$，以及三角形的两条边 $V_1-V_0$、$V_2-V_0$。它的行列式就是这三条向量的三重积——前面讲过，三重积代表的是这三条边张成的平行六面体的体积（数值上等于对应四面体体积的六倍）。记

$$S = D\cdot\big((V_1-V_0)\times(V_2-V_0)\big)$$

只要 $S
e 0$，$t,u,v$ 就都有唯一解。用克莱姆法则展开，$t$ 的形式是

$$t = \frac{(V_0 - O)\cdot\big((V_1-V_0)\times(V_2-V_0)\big)}{D\cdot\big((V_1-V_0)\times(V_2-V_0)\big)}$$

分子分母都是三重积，分母跟上面那个行列式是同一个东西。$u$、$v$ 用同一套展开也能拿到，分母还是这个 $S$，只是分子换成另外两组向量的三重积，这里就不逐个写了，自己推一遍会更清楚。拿到 $u$、$v$ 之后按 $u\ge 0$、$v\ge 0$、$u+v\le 1$ 检查一遍，交点才确实落在三角形内部；否则它只是落在三角形所在的平面上，在三角形外面。

真正麻烦的是 $S=0$。这种情况可能有下面几种来源。

第一种，直线的方向跟平面平行。三条向量共面，体积为零，方程不可解，也就是没有交点。这个很好理解：一条平行于三角形所在平面的直线，只要它不在这个平面上，就永远碰不到这个三角形。

第二种，直线整个躺在三角形所在的平面上。这时候方程同样不可解（或者有无穷多解），但"算不算相交"是有歧义的。又回到布料那个例子：你一开始就判定相交，那么布料到底在三角形的上面还是下面根本不知道，往上推还是往下推就无法决定。这种奇异情况必须额外借助别的信息来处理。

第三种，三角形本身退化了。常见于布料质量不好的时候：弹性力不够，三角形塌了，两条边重合成一条，三条向量共面，$S$ 一样是零。这种情况在仿真里一点都不罕见，必须做特殊处理。再极端一点，两条边重合、方向又平行，那就更难办了，几乎没有干净的解，只能靠容差和额外的几何信息去兜。

> **提示**：$S=0$ 只说明"没有唯一解"，不等于"没有交点"。它可能是一个交点都没有（平行），也可能是一整条线都躺在平面上（无穷多解）。这两种情况后续处理完全不同，不能混在一个分支里。

我把这几种特殊情况专门拎出来讲，不是要吓唬人。通用的写法在绝大多数帧上都没问题：网格质量好的时候，按上面那套公式算，结果一定对。怕的是某一帧突然崩了，你回头查半天，最后发现是某个三角形塌了、某个 $S$ 恰好是零，而那里的处理是错的。这类 bug 在仿真里非常难调，因为它是偶发的。

### 直线与包围盒：slabs 与区间求交

AABB 的相交测试在刚体的宽阶段里用得极多。宽阶段的目的不是精确求交，而是提前把明显不可能碰撞的碰撞对剔掉，所以它一定要快。

线跟 AABB 的相交，用的是一套叫 slabs（板）的方法。思路是这样的：AABB 可以看成三个板叠出来的——$X$ 方向两块无限大但有一定厚度的板夹出一个范围，$Y$ 方向同理，$Z$ 方向同理。对每一个板单独去算两个 $t$：线从近端穿进这个板是一个 $t$，从远端穿出是另一个 $t$。这两个 $t$ 就代表在这一个轴向上，线跟盒子"有可能相交"的参数范围。

具体怎么算？以 $X$ 方向为例：

$$t_{0x} = \frac{x_{\min} - O_x}{D_x},\qquad t_{1x} = \frac{x_{\max} - O_x}{D_x}$$

分子是盒子在该轴上的边界减掉原点的对应分量，分母是方向在该轴上的分量。三个分量各算各的，互不干扰。$Y$、$Z$ 同样处理，得到 $[t_{0y},t_{1y}]$、$[t_{0z},t_{1z}]$。

真正的相交范围，是这三个区间的公共重叠部分：

$$t_{\text{enter}} = \max(t_{0x}, t_{0y}, t_{0z}),\qquad t_{\text{exit}} = \min(t_{1x}, t_{1y}, t_{1z})$$

如果 $t_{\text{enter}} \le t_{\text{exit}}$，重叠非空，线确实穿过了盒子，而且这两个值就是进入点和离开点；如果 $t_{\text{enter}} > t_{\text{exit}}$，重叠为空，直接判定不相交。

```text
情况 A：三个区间有公共部分
  X 区间   ├──────────────┤
  Y 区间       ├──────────────────┤
  重叠          ├──────────┤            非空 --> 线穿过盒子的这一段

情况 B：两个区间错开
  X 区间   ├────────┤
  Y 区间                 ├────────┤
  重叠           （空）                 --> 不可能相交，直接退出
```

读图说明：每个轴给出的只是一个必要条件，只有三段同时满足才是真正的相交；任意一段错开，就可以提前判负。

举个具体的例子。先看两条线里的下面那条：它跟 $X$ 板相交的范围是 $t_{0x}$ 到 $t_{1x}$；再考虑 $Y$，得到 $t_{0y}$ 到 $t_{1y}$；两个范围叠在一起，公共的那一段才是有意义的。上面那条线不一样：$X$ 算完、$Y$ 也算完，两段在参数空间里根本不重叠，那就可以断定这条线跟盒子不可能相交，$Z$ 都不用再算。

射线和线段照样是最后截断：射线额外跟 $[0,+\infty)$ 求交，线段额外跟 $[0,1]$ 求交，跟前面那三个区间一起取公共部分。这样算完，不只是知道"交没交"，进入点和离开点的位置也一并拿到了。

> **提示**：跟直线与平面那里的除零是同一个坑。如果某个方向分量 $D_x=0$，$t$ 就算不出来，这时要改判：原点在该轴上的投影落在板的范围内，这个轴就不提供任何约束；落在范围外，则整条线都不可能相交，可以直接返回。

OBB 的相交测试跟距离计算是同一个套路。一种做法是旋转回 AABB 坐标架，算完再转回来。还有一种更简单的做法：OBB 本身就有 $\mathbf{u}$、$\mathbf{v}$、$\mathbf{w}$ 三个方向，直接沿着这三个方向做同样的 slabs 判定——把盒子的半长投影到这三个方向上得到三个区间，再取公共部分。这样连坐标变换都省了，思路跟 AABB 完全一样。

### 距离测试场景：三个节点搭起来

前面讲了这么多算法，其实还欠着一件事：验证。写算法的时候按 general 的情况去写，一般都不会出问题，但是我们常常需要判定它在极端情况下到底 work 不 work。要做到这一点，就得有大量的测试样例，而样例本身并不好构建——很多情况是仿真跑到一半才碰上的，碰上了还很难调。最好的做法是算法一写完，就把各种各样的情况都测一遍，这样后面写复杂算法时才不会因为一个小错误把整个结果带偏。

所以接下来我直接对着代码讲，看看怎么用这个框架方便地搭一个场景，把各种极端情况都测到。先拿点到 OBB 的距离计算开刀。

整个程序有一个交互界面，但如果你去看 main 函数，里面没有一行跟 Qt、跟界面相关的代码——这些都藏在框架里，你不需要管。

场景里要有三个节点：

- 一个代表 OBB 的 cube 节点，cube 是库里自己提供的；
- 一个点节点，用来生成那个被查询的点；
- 一个距离计算节点，吃前两个节点的输出，算出距离。

算完之后还要看得见，所以又挂了两块可视化：两个端点的显示，和中间那条连线的显示——线把 OBB 表面的最近点和查询点连起来，调参数的时候一眼就能看出对不对。

```text
[ PointNode ]  --+
                 +--> [ DistanceNode ] --> [ endpoints + connecting line ]
[ Cube (OBB) ] --+
```

读图说明：前两个节点是数据源，第三个节点吃两路输入做计算，可视化挂在计算节点后面；前一个节点的输出喂给后一个节点的输入，这条"线"就是整个场景的骨架。

有一点前提要先说清楚：如果你想让某个模块能被选中、选中后出现一个 handle 帮你平移、缩放、旋转，那它必须从一个叫 `ParametricModel` 的父类继承下来。这是硬性要求，绕不过去。

#### 点节点是怎么写出来的

定义一个点，代码里包含两部分。一是它参数化的形式：这里定义一个变量，用 `DEFINE_` 宏来声明——这两个都是宏，第一次课讲过宏的用法，声明之后还要把数据喂进去。二是显示：点还得看得见，所以额外定义 `instanceState`，也就是实例的状态。它主要是给可视化用的：定义一个 `PointSet`，在里头创建一个点。构造函数里会额外创建点的可视化模块，把这个点的状态输给可视化模块，点就画出来了。再往下定义的输出，就是喂给后面那个距离计算节点的——前面一更新，后面就实时重算距离。整个结构就这么简单。

具体实现时有两件事必须做。

第一件是重置。点一下 reset，它会重新调用对应的功能，把值重新赋回去。例子里初始化时一直把点放在 $(2,0,0)$，重置就是把 $(2,0,0)$ 再赋一遍，重新初始化，重置就完成了。

第二件是回调。点被拖动之后，距离是在不停重算的，所以这个节点必须感知 handle 什么时候变了，变完立刻更新输出。父类里定义了平移、缩放、旋转三个控制变量，改的就是它们；把回调函数挂到这些变量上，变量一变就重新调用，去更新输出的值和用于可视化的值。

整个过程没有一行跟 UI 相关的代码，按 C++ 的标准写差不多这么几行，就能在节点里把点创建出来。后面那些声明和实现，主要是为了支持 C++ 的反射机制：有了它，你在 UI 菜单里把节点删掉之后，还能重新创建出来继续算。

#### 计算节点与渲染管线

点有了输出，cube 是内置的、直接能输出一个 OBB，接下来就要写那个吃两路输入的计算节点：输入一个点、输入一个 OBB，根据这两个东西算距离。

它要做的事就是重载里头的计算模块：输入一变，就重新算一遍。你会发现真正的计算其实只有一行代码，剩下全是给可视化和交互打辅助的。

计算模块定义好之后，要把它 push 进渲染管线——因为这个模块是挂在渲染管线上的，可视化要靠它。除此之外还额外加了两个模块：一个把两个端点画出来，一个把两点之间的连线画出来。这两个一到位，整个场景必备的东西就齐了，一共三个节点。

#### 把场景连起来

创建流程是固定的：先建一个场景，再建三个节点（点节点、cube 节点、计算节点），然后把前一个节点的输出接到后一个节点的输入上——对应代码里那两条连线。编译之后场景就跑起来了。最后因为这是 Qt 的框架，创建一个 Qt 的 UI，把场景设进去，起一个 main loop，一个能点的测试场景就搭完了。

整套下来两百多行。

#### 极端情况怎么测

有了这个场景，测起来就直观了。刚才说的是把点拉到边上；拉到角点上也没问题，那是最普通的情况。还有一种必须测的是把点放到盒子内部——内部的结果对不对，光看外面是看不出来的，得把渲染的半透明度调一下，让盒子变成半透明，这样内部的线段和计算结果才能看见。点在里面运动的过程中，它跟各个边的关系是各种情况都会出现的，正好一次性看全。

顺带说一句，代码和蓝图是一一对应的：你看到的创建节点、连接节点，跟蓝图里拖出来的东西是同一套东西。用代码写的好处是配置可以预先写好，不用每次点进来都重新搭一遍。

### 相交测试场景：看着交点从一个变成两个

距离计算的场景讲完，相交的场景是同一套搭法。这里测的是一个线段跟一个 OBB 之间的相交结果。

场景里那两个绿色的端点就是线段的两头，另外还有一个 cube。一开始看着不太清楚，把它调成半透明就好办了。

线段穿过盒子的时候，会有两个交点，红色那两个点就是它跟 OBB 相交的位置。线段是可以拖的：拖到外面，可能只剩一个交点；再往外移，交点就消失了。从无交点、到一个交点、到两个交点，全部用交互的方式试一遍，比来来回回写一堆样例省事得多，而且有些情况你写样例还真不一定能覆盖到。

实现跟前面完全一样，不细讲。还是定义一个 segment，然后定义一个用来渲染的数据：线段本质是一个边集，所以定义一个 `EdgeSet`，后面接一个线框渲染模式，把线框画出来；再额外输出一个线段；回调函数照样重载一遍。场景创建还是三个节点，数据连好之后，它会实时地做各种计算。

### 从几何测试到交互：点击方块施加冲量

最后讲一个刚体动力学里的应用，看看前面这些东西到底有什么用。

除了碰撞检测，我们还搭了一个叫 Hit Bricks 的小场景，类似打砖块，本质上就是碰撞检测的演示。刚体下次再讲，这次只看效果。

场景里有很多 cube。我想做的事是：用鼠标在屏幕上点一下，去推动某一个 box。这相当于从屏幕里打了一根射线进去——第一次讲交互的时候就说过，这里所有的交互逻辑，都是把屏幕空间的输入转换到世界坐标系里。所以点一下之后会生成一根射线，射线跟场景里的 OBB 做相交测试，碰到哪个 box，就在那个 box 上施加一个脉冲，顺带把它的速度也调整掉。

实现依赖几样东西。一是刚体场景本身，搭好就行，不细讲。二是一个交互模块：这里写了一个叫 hit 的模块，从鼠标交互的模块继承下来。计算时要用到两份数据——场景里的基本单元（box、球这些离散单元），以及速度，因为施加脉冲之后要改的正是速度。点击响应走 `onEvent`，重载父类的这个函数，拿到鼠标事件。

拿到事件之后，用的就是今天讲的东西：射线跟每一个 box（本质上就是 OBB）做相交检测，检测到了就改它的速度。于是就有了"点一下、推一下"的效果，可以跟场景做一些更有意思的交互。

这个 demo 要说明两件事：一是鼠标交互应该怎么实现；二是今天讲的各种基本几何单元到底落在哪里——它们就是用来做这种功能的。

## 从质点方程到 Linear BVH：刚体动力学与 GPU 并行碰撞检测

从这一讲开始，我们正式进入仿真算法。前面几讲把基础铺完了，有些地方当时讲得比较快，不一定当场吸收得了，所以我们边往下走边回补。但先把我这次的取舍说清楚：不论刚体、流体还是形变体，每个方向上的方法都多得数不过来，全讲一遍既不现实也没意义。所以我侧重的是**共性的技术、地基性的技术**——地基打牢了，你们后面自己做拓展、去读别人的论文会顺得多，也不至于一上来就陷进某个具体方法的技术细节里出不来。

### 质点：最简单的动力学模型

刚体动力学最简化的版本，是质点。质点在现实里并不存在，它是一个抽象的简化模型：有质量，但没有体积、没有形状。没有形状这件事带来一个巨大的好处——**不用考虑旋转**。所以一个质点的运动，需要的物理量少得可怜：质量 $m$、位置 $\boldsymbol{x}$、速度 $\boldsymbol{v}$、加速度 $\boldsymbol{a}$，还有作用在它上面的力 $\boldsymbol{F}$。这些在高中物理里都学过。

有了这些量，接下来要做的只有一件事：让它动起来。核心是牛顿第二定律：

$$\boldsymbol{F} = m\boldsymbol{a}$$

把它落到离散的时间步上，就是两步更新。加速度是力除以质量，乘上时间片就是这段时间里速度的改变量；速度更新完，再拿新速度去推位置：

$$\boldsymbol{v}^{t+\Delta t} = \boldsymbol{v}^{t} + \frac{\boldsymbol{F}}{m}\,\Delta t$$

$$\boldsymbol{x}^{t+\Delta t} = \boldsymbol{x}^{t} + \boldsymbol{v}^{t+\Delta t}\,\Delta t$$

顺序不要搞反：先更新速度，再用**更新后**的速度更新位置。

> **提示**：这套写法里，$\frac{\boldsymbol{F}}{m}$ 就是加速度。整个积分做的事情，无非是"用当前的加速度推下一步的速度，用下一步的速度推下一步的位置"。

于是整个仿真在时间轴上被切成一串离散时刻：$0$、$\Delta t$、$2\Delta t$……初始化时给定三个量——位置、速度、初始的力；之后每一个时刻做一次积分，把状态往前推一格，力在这个过程中也会被不断重新计算和调整。把这些时刻连起来画在空间里，就是一条运动轨迹曲线——在持续的外力作用下，它是一条连续弯折的曲线，这也是最终渲染出来的东西。

> **结论**：连续时间的微分方程，到计算机上一定要变成离散的递推。所谓仿真，就是反复执行这条递推，把一条连续曲线采样成一串状态。

### 刚体：多出来的那一维

刚体的整体思路跟质点一模一样，唯一的复杂化是它多了一个旋转。但你们会发现，旋转和平移这两套概念是一一对应的，几乎可以把质点的表照抄一遍，只换名字：

| 平移 | 转动 | 备注 |
| :--- | :--- | :--- |
| 质量 $m$ | 惯性张量 $\boldsymbol{I}$ | 都衡量"多难被改变" |
| 位置 $\boldsymbol{x}$ | 旋转矩阵 $\boldsymbol{R}$ 或四元数 $q$ | 两者等价，可相互转换 |
| 速度 $\boldsymbol{v}$ | 角速度 $\boldsymbol{\omega}$ | 一阶状态量 |
| 加速度 $\boldsymbol{a}$ | 角加速度 $\boldsymbol{\alpha}$ | 二阶量 |
| 力 $\boldsymbol{F}$ | 扭矩 $\boldsymbol{\tau}$ | 外因 |

质量这一栏要解释一句。质点把质量当成标量就够了，因为质量集中在一点；刚体有形状，质量是分布在形状上的，所以这里用**质量矩阵**来表示，三个平移方向各占一份，写成对角阵就是 $\mathrm{diag}(m,m,m)$。对应到转动，就是**惯性张量**，一个 $3\times3$ 的矩阵。直观理解很朴素：$I$ 越大，改变平移越困难；惯性张量越大，让它转起来、让它停下来都越困难。两者是同一个意思，只是作用在不同的自由度上。

> **易错点**：质量矩阵管"推一下能跑多快"，惯性张量管"拧一下能转多快"。刚体有形状，所以惯性张量的每一个元素都取决于质量怎么分布、分布在哪三个轴上，不是简单把质量抄三遍。

位置在转动空间里的对应物是旋转矩阵，也可以是四元数——两者等效，可以一一互相转换。位置要更新需要速度，姿态要更新需要角速度；速度和角速度要再更新，分别需要平移加速度和角加速度。到这里为止，一切都对得上。但有一个地方不一样，而且是最容易翻车的地方：**平移是线性空间，转动不是。**

在线性空间里，速度就是位置对时间的导数，$\boldsymbol{v} = \dot{\boldsymbol{x}}$，天经地义。可旋转矩阵是正交矩阵，四元数是单位四元数，它们被约束在一个流形上——你不能对它们的九个、四个分量逐个求时间偏导，然后当作角速度用。那样得到的东西不满足"还是旋转"这个约束，物理上是错的。

> **易错点**：旋转的时间导数不能逐元素求。它必须保持正交性，长成 $\dot{\boldsymbol{R}} = [\boldsymbol{\omega}]_\times \boldsymbol{R}$ 这种形式；四元数则是下面要写的两个四元数相乘。这是转动跟平移最本质的差别。

刚体的状态更新，因此分成两半。平移那一半和质点完全一样：外力先更新速度，再更新质心位置。转动那一半形状相似，但每一步都多带一点东西：

$$\boldsymbol{\omega}^{t+\Delta t} = \boldsymbol{\omega}^{t} + \boldsymbol{I}^{-1}\boldsymbol{\tau}\,\Delta t$$

角加速度就是惯性张量的逆乘扭矩，乘上时间片，加到角速度上。然后要把角速度积分成姿态——这一步是整段里看着最诡异的公式，原因就是前面说的非线性：四元数的时间导数需要**两个四元数相乘**。而角速度是三维向量，四元数是四维的，两者没法直接相乘——要给角速度补一个 0，变成 $\boldsymbol{\omega}_q = (0,\omega_x,\omega_y,\omega_z)$，才能跟当前四元数做四元数乘法：

$$\dot{q} = \frac{1}{2}\,\boldsymbol{\omega}_q \otimes q$$

$$q^{t+\Delta t} = \mathrm{normalize}\!\left(q^{t} + \dot{q}\,\Delta t\right)$$

四元数更新完，再回过来把它转成旋转矩阵，姿态就落地了。

还有两个细节，都源于"刚体有形状"这一件事。第一，外力作用在不同点上产生的扭矩不一样，扭矩是力臂叉乘力，$\boldsymbol{\tau} = \boldsymbol{r}\times\boldsymbol{F}$，所以必须结合**当前的姿态**才知道力臂是多少。第二，惯性张量本身也会随姿态变化：物体在体坐标系里的惯性张量是固定的，一旦转起来，换算到世界坐标系就得把旋转带进去，$\boldsymbol{I}_{\text{world}} = \boldsymbol{R}\,\boldsymbol{I}_{\text{body}}\,\boldsymbol{R}^{\top}$。所以更新姿态和更新惯性张量是互相咬合的。

整套东西就这样迭代下去：初始状态 → $\Delta t$ → $2\Delta t$ → ……，一步一个脚印往前推。看着很简单，真正做起来就不简单了。

### 卡住的地方不是积分，是力从哪来

先做个假设：如果不考虑外力，这套系统用任何积分方法都能跑——显式欧拉、隐式欧拉，随便挑，都能给你一条运动曲线。问题在于，**力和扭矩很多时候根本不知道**。它们不是天上掉下来的，得先算出来。场景里有大量刚体的时候，"算出每个刚体受多大力、多大力矩"这件事本身就是整个仿真最大的一块开销。

所以刚体动力学仿真的核心，其实只有一句话：**把力和扭矩算出来**。不同方法在这一步的层面不一样：基于速度的方法（velocity-level）直接算力和扭矩；基于位置的方法（position-level）可能直接去改位置。这是有差别的，但笼统地讲，都可以归到两个阶段。

```text
   上一帧状态
        │
        ▼
  ┌──────────────────────────────────┐
  │ 碰撞检测：到底谁和谁碰上了          │
  │   宽阶段：粗筛出候选 pair           │
  │   窄阶段：算出真实接触点与法向       │
  └───────────────┬──────────────────┘
                  ▼
  ┌──────────────────────────────────┐
  │ 约束求解：在接触点上建立约束并求解    │
  └───────────────┬──────────────────┘
                  ▼
  ┌──────────────────────────────────┐
  │ 积分更新：速度、位置、姿态           │
  └──────────────────────────────────┘
```

读图：宽阶段负责"少算"，窄阶段负责"算准"，约束求解负责"算对"，积分只是最后把结果落到状态上。

第一阶段碰撞检测，内部还要再拆成两步：宽阶段和窄阶段。宽阶段很功利——它不追求精度，只追求**快**，把明显不可能碰上的物体成对剔除掉；筛剩下的潜在候选才交给窄阶段，去算真实的接触点。这就是一个完整的刚体仿真流程。

所以真正麻烦的地方不在方程，而在"谁跟谁发生关系"这件事本身：哪些物体对值得细算，事先是不知道的。成千上万个刚体里，真正相关的那一小部分对，得靠算法自己找出来——这才是 GPU 并行要对付的东西。

### 包围盒：用最便宜的几何体先筛一遍

为什么需要包围盒？想一下场景里的东西：一头牛、一辆车。它们在内存里通常是三角网格，几千上万个三角形。你要是两两直接算，做的是边与边、点与面的相交测试，每一对都要遍历几何单元，开销大到没法看。而绝大多数物体对其实八竿子打不着，根本不值得为它们付这个代价。

所以先套一层代理：给每个物体配一个**运算极便宜**的简单几何体，在代理这一层判断。牛和车的包围盒如果不相交，那么牛身上任何一个点都不可能碰到车——这句话是严格的，不是近似，因为包围盒是"包含"关系。只有包围盒相交了，才值得往下做真正的几何检测。

最常用的是 AABB（axis-aligned bounding box，轴对齐包围盒）：找物体的最小紧致包络，并且强制它的边跟 $X$、$Y$、$Z$ 三个坐标轴对齐。这个"轴对齐"就是它便宜的根本原因——一个 AABB 只需要两个顶点（最小角点和最大角点）就能完整定义，判断相交就是三次坐标区间比较，没有乘法、没有三角函数。

AABB 的毛病也很明确：它必须轴对齐，所以对斜着长的东西不紧致。一片斜放的叶子，沿斜线方向很长，可你只能用横平竖直的盒子去框它，盒子里空出大片没用的区域。包围盒一虚胖，剔除率就掉，窄阶段要多算一堆冤枉对。

要更紧致，就用 OBB（oriented bounding box，有向包围盒）：本质上就是给 AABB 加一个旋转，让盒子顺着物体自己的朝向斜过去。还是那片叶子，现在可以定义一个沿斜线方向的长方体，贴合得多。OBB 特别适合狭长的结构，能明显提高碰撞检测的精度。

第三种也很常见：包围球——取能包含物体的最小球体。这三者的取舍摆在一起看：

| 包围体 | 定义 | 紧致度 | 单次判定开销 |
| :--- | :--- | :--- | :--- |
| AABB | 边与 $X$、$Y$、$Z$ 轴对齐的最小包络 | 一般，斜置物体会虚胖 | 最低，两个顶点即可定义，纯坐标比较 |
| OBB | AABB 再加上一个朝向旋转 | 高，能贴住斜置的狭长物体 | 高于 AABB，要带朝向参与运算 |
| 包围球 | 包含物体的最小球 | 较低 | 高于 AABB |

从计算角度讲，最简单的肯定是 AABB，后面两种都还是有一定计算量的。实际用得最多的也是 AABB，所以下面全部围绕 AABB 来讲空间加速结构。

> **提示**：包围盒只是"代理"，它的判定结果只有两种用处——不相交时**可以确定**内部几何绝不相交，相交时**什么都不能确定**，必须细算。剔除是严格的，保留是有损的，这个不对称性正是整个宽阶段成立的前提。

给每个物体都定义好 AABB 之后，原来的复杂物体就变成了一堆盒子。判断时不再碰里面的几何单元，只碰盒子。牛和车的盒子不相交，就直接判定这一对安全；盒子相交了，才需要往下查它俩到底在哪个点碰上。

于是问题变成：**怎么把"盒子相交"的那些 pair 快速找出来。** 这才是宽阶段真正的算法问题。

### 排序扫描线：CPU 上的经典解法

在 CPU 上，用得最多的方案叫排序扫描线（sweep and prune）。

做法分轴处理，先只看 $X$ 方向。把每个盒子在 $X$ 轴上的区间投影出来，得到一对端点——起点和终点；所有盒子的 $2N$ 个端点扔到一起，按坐标排序。然后从左往右扫一遍，维护一个 **active list**：碰到某个盒子的起点，就把它加进表里；碰到某个盒子的终点，此刻表里所有还活着的起点，都和这个刚结束的盒子在 $X$ 上重叠——它们构成候选对，记下来，然后把这个盒子移出表。

```text
   X 方向投影，按端点排序后从左往右扫描：

   b0: |=========|
   b1:      |============|
   b2:             |==========|

   扫到 b0 起点 → 活动表 = {b0}
   扫到 b1 起点 → 活动表 = {b0, b1}
   扫到 b0 终点 → 表里的 b1 与 b0 重叠，记下 (b0, b1)，移出 b0
   扫到 b2 起点 → 活动表 = {b1, b2}
   扫到 b1 终点 → 记下 (b1, b2)，移出 b1
```

读图：一维扫描只回答"在这一个轴上有没有重叠"。b0 和 b2 在这个轴上根本没碰面，所以不会产生候选对。

一个方向不够。两个物体完全可能在 $X$ 上重叠、在 $Y$ 上隔着老远。所以标准的排扫算法要做三遍：$X$ 一遍、$Y$ 一遍、$Z$ 一遍，最后取交集——只有在三个轴上都重叠的 pair 才是真正的候选对。

这套算法效率很高，复杂度上讲很划算，所以 CPU 引擎里用得很多。Bullet 里就有一个 `btAxisSweep3` 的实现，有兴趣可以去读一读源码。

但它是**CPU 的算法**，搬到 GPU 上不合适。原因有两个，都很硬。

第一，**active list 是个动态结构**。它的长度在扫描过程中不断变化，而且最坏情况会爆炸：假设场景里有一个特别大的物体，跟所有物体都相交，那么从它进入活动表开始，表里就永远挂着它，长度正比于物体总数。GPU 的寄存器、shared memory 都很小，这种不定长、上限还可能很大的结构根本放不进去，也没法在编译期把大小定下来。

第二，**扫描本身是严格串行的**。处理第 $i$ 个端点时，活动表长什么样，完全取决于第 $i-1$ 个端点处理完之后的样子。你没法把 32 个端点分给 32 个线程同时处理——它们读写的是同一份表。

> **易错点**：排序本身在 GPU 上不难，并行排序是很成熟的技术；难的是排序**之后**的扫描。别把"GPU 排序快"误当成"这套算法能上 GPU"。

### 均匀网格：把空间切成格子，让线程互不相干

要在 GPU 上并行，就得换一种不需要动态结构的思路。最常用的是均匀网格。

思路直接得很：分配一个足够大的均匀网格，把整个场景罩住。然后逐个物体去测它跟哪些格点（格子）相交，把物体 ID 记到那些格点上。检测的时候，一个物体只需要查自己占的格子以及相邻格子——落在同一个格子或相邻格子里的物体，才有可能发生碰撞。

它为什么适合 GPU？两点：

- **存储连续**：格点按索引直接算地址，不需要指针跳转，也不需要顺着链表走；
- **计算完全可并行**：每个物体算自己压到哪些格子，是独立的；每个格子里的两两检测，也是独立的。线程之间没有共享状态要协商。

但问题有两个，都很致命。

**负载不均衡。** 想象一个特别小的物体和一头特别大的牛。物体尺寸跟格子差不多的时候还好，一个苹果充其量占四个格子；可牛可能要占几百上千个格子。假设一个线程处理牛、一个线程处理苹果，同一个网格里线程的工作量能差两个数量级。GPU 最怕这个——一个 warp 里的线程要一起走，最慢的那个会把整组拖住。

**存储爆炸。** 物体在空间里的分布往往不均匀。假设特别远的地方也孤零零地放着一个物体，你要用一个网格罩住全部物体，网格就得铺满中间那一大片空区域，绝大部分格子是空的，而空格子照样占显存。

所以均匀网格有它的舒适区：**物体尺寸比较单一、分布比较均匀**的场合。最典型的是封闭容器里的流体模拟，或者刚体颗粒（granular）模拟——容器大小固定，颗粒大小一致，网格铺满容器正好，谁都不浪费。

反过来，场景里大物体小物体混在一起、分布又稀疏辽阔，均匀网格就不合适了。你需要一个"哪里有东西才往哪里细分"的结构。

### 层次化包围盒：只在有东西的地方细分

这里要同时压住两个指标：计算复杂度和存储开销。均匀网格是"致密"的，致密就意味着浪费——没物体的地方也铺着格子。层次化包围盒换了个思路：用一棵自适应的二叉树去划分空间，只在有物体的地方往下分。

先看 CPU 上怎么想这件事。跟均匀网格一样，先分配一个足够大的包围盒，把全部物体装进去。然后开始划分：在中间切一刀，把里面的物体劈成两半，左边一半归节点 $N_1$，右边一半归节点 $N_2$，各自带一个 bounding box。再往下，$N_1$ 里如果还剩两个物体，就再切一刀，分成两个子节点。什么时候停？一个节点里只剩一个物体，就不用再分了，它成为叶子。另一支三个物体的，照样递归。

这样做的存储开销跟物体数量基本成正比——线性，常数也不大：每个内部节点无非存一个 AABB 加两个索引。代价在查询：一次检索要从根往下走，每层做一次盒子相交测试，代价跟树的深度成正比，比均匀网格贵一点。

能不能把这部分开销压下去？关键是**树要尽量平衡**。查找永远从根往下遍历，如果每个叶子的深度都差不多，最坏情况就短，整体效率就高。一棵歪成链的树退化成线性扫描，那还不如直接用均匀网格。

真正的问题不在"怎么分"，而在"怎么**并行地**分"。前面那个过程是自顶向下的：不切开根节点，你不知道子节点在哪；不切开子节点，你不知道孙节点在哪。GPU 上有几千个线程，你不可能让一个线程去建根节点、其余几千个线程干等着，等它建完再一起建下一层——树有十几层，每一层都全设备同步一次，并行度全被同步吃掉。

所以得换方向：**自底向上、一次并行建完**。这就是 Linear BVH 要做的事——它的几块内容是莫顿码、并行构建和并行遍历，核心是头两块：先把这棵树建出来。

### 莫顿码：让内存里的邻居对上空间里的邻居

讲建树之前，得先讲一个看起来跟树没什么关系的东西：莫顿码（Morton code）。

先说为什么需要它。不管均匀网格还是层次结构，最后在显存里都是一维的线性数组——所有东西都要拉平成地址。而 GPU 取数是"一块一块"取的：一个 warp 32 个线程同时发起访问，硬件会把地址相近的数据一次搬进来。如果你的数据在空间上相邻、在内存里也相邻，这 32 次访问大概率落在同一批 cache line 上，miss 很少；反过来，空间上挨着的两个物体在内存里隔着十万八千里，每次访问都是一次 miss，带宽全浪费在搬无关数据上。

所以问题变成：**怎么把一个二维或三维的空间索引映射成一维地址，并且尽量保住"邻近"这个关系？**

先看最朴素的按行存储。二维坐标 $(x,y)$，行主序就是把一整行 $x$ 存完再存下一行。那么 $(0,0)$ 和 $(0,1)$——同一个 $x$、下一行——在内存里隔了整整一行的距离。空间上只差一格，内存上差了 $N$ 个元素。这个连续性很差。

> **提示**：三维时更糟。$z$ 方向差一格，内存里差了一整个平面。

莫顿码的做法是**按位交错**：把 $x$ 的二进制位和 $y$ 的二进制位交替塞进同一个整数里——$x$ 的最低位、$y$ 的最低位、$x$ 的次低位、$y$ 的次低位……一路往上。得到的整数就是莫顿码，也叫 Z-order 码，因为按码值排序之后，遍历顺序在空间上画出来是一条 Z 字形的折线。

效果是：同一个 $2\times2$ 小方块里的四个格点，码值是连续的四个数；$(0,0)$ 之后紧跟的就是同一个小方块里的邻居，然后才跳到相邻的下一个 $2\times2$ 方块。这个性质是分形递归的——小范围邻近，大范围也邻近。

放到刚体这个任务上，过程是这样的。假设场景里有四个三角形，每个落在某个格点上，有自己的 $(x,y)$ 索引，比如其中一个是 $(2,0)$。给每个三角形算出莫顿码，按码值排序。排完之后，顺序跟原来的输入顺序完全不一样了：绿的那个排第一，然后是橙的，再是灰的，最后是棕的。莫顿码是从小到大排列的，这就是排序的结果。

这一步做完，四个三角形被拉平成了一条**空间上有序**的一维序列。这条序列的价值在于，它已经把层次信息编码进去了：莫顿码相同的高位越多，说明它们落在同一个越大的格子里；码值相邻，说明它们在空间上邻近。所以接下来不需要再"切空间、重新分配物体"，直接从这个有序序列上就能把树读出来。

### 从莫顿码直接长出二叉树

建树的过程，本质上是**逐位看前缀**，在第一个发生变化的地方切一刀。

根节点包含全部四个三角形，对应整段有序序列。看最高位：这一位对应 $y$ 的最高位，序列里的取值是 0、1、1、1——在 0 和 1 的交界处切一刀，分成两半：一半只有 1 个三角形（它在空间的另一侧），另一半有 3 个。为什么在这里切？因为 $y$ 的最高位不同，意味着它们根本不在同一个半空间里，必须分开。

接着处理那 3 个三角形。这一位轮到 $x$ 的最高位（交错的下一位），取值是 0、0、1——在第二个 0 和 1 之间切，分成 2 个和 1 个。只剩 1 个的那个节点直接成为叶子，不用再分；2 个的那个继续按位切，直到每个叶子恰好装一个三角形。

```text
[ root : 4 tris ]
   |
   |-- y 最高位 = 0 --> [ leaf : 1 tri ]
   |
   +-- y 最高位 = 1 --> [ inner : 3 tris ]
                             |
                             |-- x 最高位 = 0 --> [ inner : 2 ]
                             |                        |
                             |                        +-- [ leaf ]
                             |                        |
                             |                        +-- [ leaf ]
                             |
                             +-- x 最高位 = 1 --> [ leaf : 1 tri ]
```

读图：每一条分叉都对应莫顿码里的一个比特位，分叉的位置就是这一位第一次由 0 变 1 的地方。树的结构完全由有序的码值决定，不需要再回头去动几何数据。

把分叉处连起来，就是一棵标准的二叉树：根分出两个子节点，内部节点继续各分出两个，最后所有叶子各装一个三角形。这棵树有个正式名字，叫**有序二叉压缩前缀树**。

### 这棵树为什么特别适合 GPU

它的三条性质，每一条都直接对应一个 GPU 上的工程需求。

**第一，节点数是确定的。** 每次划分都是一分为二，所以内部节点数严格等于叶子节点数减一。$N$ 个叶子，就有 $N-1$ 个内部节点，整棵树一共 $2N-1$ 个节点。

> **结论**：整棵树的存储可以在建树之前一次算出来——两个数组，一个长 $N$ 存叶子，一个长 $N-1$ 存内部节点。GPU 最怕运行途中动态扩容，这条性质正好把它绕开。

**第二，节点编号本身就是索引。** 排布有三条约定：

- 内部节点数组的第 0 号固定是根节点。遍历时直接从 0 进去，不用另外存一个根指针；
- 一个节点分裂出的左右两个孩子，就放在这个分裂位的左边和右边，在内部节点数组里是连续的一段；
- 每个内部节点的区间端点一定落在叶子上：它要么是这段区间的起点，要么是终点。因为划分点总是切在某两个相邻叶子之间，所以第 $k$ 个内部节点，就是第 $k$ 个和第 $k+1$ 个叶子之间的那道边界。叶子编号 $0 \sim N-1$，内部节点编号 $0 \sim N-2$，一一对应。

**第三，最长公共前缀可以很快算出来。** 这是并行建树能成立的关键。定义 $\delta_{i,j}$ 为叶子 $i$ 到叶子 $j$ 这一段连续叶子的**最长公共前缀**：从最高位往下逐位比较，第一次出现不同之前，相同的那些位。比如某段的最长公共前缀是 00，就说明这一段里所有码值的高两位都是 00。

> **定义**：$\delta_{i,j}$ 表示排序后第 $i$ 到第 $j$ 个叶子（含两端）的莫顿码的最长公共前缀。它刻画的是这些叶子在空间上"共同属于多大的一个格子"。

然后是最要紧的一条性质：**任意子区间的最长公共前缀，一定不小于包含它的那个大区间的最长公共前缀。** 道理很直白——区间缩小，参与比较的元素变少，能保持一致的位数只会更多，不会更少。

这条性质有什么用？算一个内部节点的最长公共前缀时，不需要把它包含的所有叶子遍历一遍，**只看第一个和最后一个就够了**：首尾两个码值已经把差异拉到最大，中间任何元素都不可能让公共前缀更短。

要是没有这条性质会怎样？算根节点的前缀就得遍历全部 $N$ 个叶子，越往上开销越大——这棵树在 GPU 上根本没法并行构建。所以这一条不是锦上添花，是前提。

### 并行构建：一个内部节点一个线程

有了上面这些，构建思路就清楚了：**从底向上，一个内部节点分配一个线程。** $N-1$ 个内部节点，$N-1$ 个线程，谁也不等谁。

关键在于，每个线程只需要知道自己管哪一段，不需要知道父节点是谁、兄弟是谁、自己处在树的第几层。它只读已经排好序的叶子数组，只写自己那一条记录。这就是"消除对父节点的依赖"——传统自顶向下的建树之所以串行，就是因为子节点必须等父节点算完才知道自己在哪。

每个线程要做三件事。

#### 第一步：确定往哪边搜索

内部节点 $k$ 只知道自己是某段区间的一个端点，但不知道是左端点还是右端点。判定方法是前面那条性质的直接应用：比较它跟**右邻居**、**左邻居**分别组成的两元素区间的最长公共前缀。

- $\delta_{k,\,k+1}$：$k$ 与右邻居组成的两元素区间的最长公共前缀；
- $\delta_{k,\,k-1}$：$k$ 与左邻居组成的两元素区间的最长公共前缀。

这两个值里，**恰好有一个等于父节点的前缀**，另一个**大于**父节点前缀。等于的那一边，邻居已经属于父节点的另一半，也就是出了自己这一支；大于的那一边，邻居还在自己这一支内部。所以"哪一个更大"，直接告诉你区间往哪一边延伸：两个元素分属父节点的左右两个孩子时，它们的公共前缀就停在父节点那一层；而落在同一支里的两个元素，位数还能再往下对。

把两者相减，看符号：

$$d = \delta_{k,\,k+1} - \delta_{k,\,k-1}$$

$d < 0$ 时，说明 $\delta_{k,k+1}$ 是那个更小的值、已经掉到父节点那一档，也就是 $k+1$ 属于父节点的另一半——所以 $k$ 是这段区间的**右端点**，真正的起点在左边，向左搜。反过来 $d > 0$，$k$ 是左端点，终点在右边，向右搜。

> **易错点**：这个符号方向容易记反。判断依据不是"哪边前缀大就往哪边搜"，而是**哪边前缀小，说明那边已经出了自己的区间**。$\delta_{k,k+1}$ 小，意味着右边那个元素已经不在自己这一支里了。

#### 第二步：把区间的另一个端点找出来

方向定了，就沿着这个方向往外扩展。判据还是前缀，而且很干脆：区间还在自己管辖范围内时，你和新拉进来的元素组成的区间，公共前缀一定**大于**父节点的前缀；一旦某个元素进来之后前缀掉到父节点那一档，说明它已经跨出去了。

所以搜索的终止条件是"第一个让前缀不再大于父节点前缀的位置"，它的前一个位置就是区间的另一个端点。

这里能停下来、而且只会停一次，靠的还是前缀的单调性：区间越扩越大，公共前缀只会变短，不会变长。那个"掉档"的边界是唯一确定的，不需要来回试探。

#### 第三步：找到左右子树的分裂点

区间 $[first, last]$ 定下来，这个节点的前缀 $\delta_{first,last}$ 也就定了。接下来要找的是：区间内部从哪个位置开始，码值的这一位变了——那就是左右子树的分界。

判据跟前面一脉相承：左子树内部任意元素与 $first$ 组成的区间，前缀一定**大于** $\delta_{first,last}$；一旦把右子树的元素拉进来，前缀就**正好等于** $\delta_{first,last}$——因为整个区间的公共前缀就只有这么多。所以分裂位就是**第一个让前缀掉到 $\delta_{first,last}$ 的位置**。

三个位置凑齐，这个线程就产出了它该产出的全部东西：自己的区间 $[first,last]$、分裂位、以及两个孩子的位置（分裂位两侧的那两个内部节点索引）。写完退出，不用跟任何人同步。

> **结论**：整个拓扑的构建是完全并行的——每个线程只读叶子数组、只写自己那一条记录，彼此之间没有任何依赖。串行的自顶向下建树，就这样被拆成了一次并行的自底向上扫描。

### AABB 自底向上：两个线程抢同一个父节点

到这里建出来的还只是**索引结构**——谁是谁的孩子、区间怎么分、分裂位在哪。真正用来剔除的 AABB 还没算：不光叶子要有 AABB，每个内部节点也要有，而且内部节点的 AABB 必须是两个孩子 AABB 的并集。

这一步同样是自底向上。先给每个叶子分配一个线程，各自算自己的 AABB。这部分毫无问题：叶子之间完全独立，互不冲突，工作量也均匀。

往上就难受了。父节点的 AABB 必须等两个孩子都算完才能算，而我们的模型是"每个节点一个线程"，于是必然出现两个线程（左孩子和右孩子）都想去算同一个父节点的情况。不管的话，两个线程同时写同一块内存，结果是未定义的；就算结果碰巧对，也是白算一遍。

所以这里需要**互斥**。做法是给每个内部节点挂一个原子计数器（或者一个标志位）：

- 一个线程算完自己的 AABB，先看父节点的两个孩子是不是都好了；
- 没好，说明兄弟还没算完，这个线程直接退出；
- 都好了，它就把父节点的 AABB 算出来，然后接着往上走，去处理祖父节点。

这样一来，每个父节点只会被算一次，而且算它的那个线程手里一定已经握着两个孩子的 AABB。

这里还藏着一个更细的问题。比如某个节点要算自己的 AABB，它依赖左边那支和右边那支；但右边那支的 AABB"还远远没到构建出来的时候"——两支的深度不一样。线程早早地把活干完，就只能空等或者退出，白占一个调度槽。

这也正是前面强调树要尽量平衡的原因：树一旦歪，同一层节点的高度差拉大，自底向上的传播就会卡在某一支上，并行度全泄在这里。

到这里，宽阶段这条链路就通了：包围盒把复杂几何化简成两个顶点，莫顿码把盒子排成空间有序的一维数组，前缀树把这个数组变成可分层遍历的索引，AABB 再从叶子一层层长满整棵树。窄阶段拿到的，就是这棵树筛出来的那一小撮候选对。

## 从层次包围盒到接触约束：刚体动力学并行的整条链路
> 对应块：BLK08 | 覆盖分集：P04下 | 块标题（分集名）：《4. 刚体动力学并行编程与实践》

一棵正在并发构建的 BVH 被涂成了两种颜色。黄色说的是“一个孩子的 AABB 已经知道了，正在等另一个孩子”；灰色说的是“这个节点的事已经有人做完，你可以直接退出”。并行建 BVH 的全部戏剧性就藏在这两种颜色里：谁先到、谁后到、谁该走、谁该接着往上爬。

等根节点的 AABB 一出来，整棵层次化的包围盒结构（Linear BVH）就立住了。后面的一切——查碰撞、生成接触、解约束——都是在这棵树上做的。

### BVH 的并行构建：标记、CAS 与提前退出

先把场景摆清楚。叶子是刚体，每个刚体自己算一个 AABB，这一步天然并行，没什么可讲的。麻烦的是往上合并：一个内部节点的 AABB 等于左右两个孩子 AABB 的并集，可我们并不知道这两个孩子分别由哪个线程处理，更不知道谁先谁后。

这里的关键是换一个问法：**我不需要知道顺序，只需要知道“来过了没有”。**

于是给每个内部节点配一个标记，初值全是 0，意思是“还没有任何线程访问过”。任何处理孩子节点的线程爬到父节点时，先对这个标记做一次原子比较并交换（atomic CAS）：把 0 换成 1，同时拿回旧值。

旧值是 0，说明我是第一个到的。把我这个孩子的 AABB 登记好，然后退出。

旧值是 1，说明已经有人来过了——而那个人只可能是另一个孩子的线程。这时候左右两个孩子的 AABB 都齐了：取出左孩子 ID、右孩子 ID 和它们各自的 AABB，合并成父节点的 AABB，再带着这个结果继续往上一层爬。

```text
              [ root ]  marker = 0
              /        \
         [ P1 ]          [ P2 ]
         /    \          /    \
      [L0]   [L1]     [L2]   [L3]

T0: L0 -> P1    CAS(P1, 0 -> 1) 返回 0
                第一个到达，登记 L0 的 AABB，退出

T1: L1 -> P1    CAS(P1, 0 -> 1) 返回 1
                第二个到达，合并 L0 / L1 的 AABB，
                算出 P1 的 AABB，继续向上
```

T0 和 T1 谁先谁后是完全随机的。先到的那个做完登记就把自己“丢掉”，后到的那个负责真正的合并。所以标记不需要记录是谁来过，只需要记录“来过没有”。

> **结论**：这样走一遍，**每一个内部节点恰好被访问两次**——左孩子那边的线程一次，右孩子那边的线程一次。两次都到齐，它才真正具备算自己 AABB 的条件。逐层往上收敛，最后落在根节点上，整棵结构就建完了。

更上一层会看到另一番景象：有些节点的子树早就被先跑完的线程合并掉了，别的线程爬到这里一看标记已经是 1，什么都不用做，直接退出。这些线程就是被涂灰的那些。所以越往上，活着的线程越少，真正还在爬的只是少数几条链。

> **易错点**：标记只有 0 和 1 两个状态，不是计数器。第二个到达的线程不需要知道第一个是谁——兄弟关系是树的结构定死的，能到这个节点的只可能是我兄弟那边的线程。

有人问：既然只是求并集，直接对所有祖先节点做 `atomicMax` / `atomicMin` 不就行了？

行，但效率不好。这么做等于没有线程会提前退出：每个线程都得从自己的叶子一路算到根，第 0 个线程要爬到根，第 1 个线程也要爬到根。一棵比较平衡的树，底下还压着大量线程在算，上面早就挤在根节点上了，重复计算非常可观。更麻烦的是原子操作本身要排队——同一个节点上 8 个线程同时做原子操作，就得一个一个来，全部做完才能收工。

反过来看 CAS 这套：大量线程处理过一遍就退出了，真正往上爬的只有“第二个到达者”，不太会出现阻塞堆积。物体分布得再密，也只是并集更大，改不了“每个内部节点只被碰两次”这个上限。

### 并行遍历：把递归摊平成一个栈

树建好了，接下来是查询。进来一堆刚体、或者一堆待查的 AABB，我们要知道哪些叶子跟它相交——这就是宽阶段的输出：一批**潜在的**碰撞对。

Linear BVH 的第 0 个元素存的就是根节点，所以查询从索引 0 开始，往下逐层比较包围盒。

最直观的写法是递归：当前节点跟查询框不相交就返回；相交且是叶子，记一对；相交且是内部节点，就对左右孩子各递归一次。

这个写法在 CPU 上写过无数遍，在 GPU 上却不合适。第一是 divergence：同一个 warp 里的线程走了不同分支，硬件只能把两条路都走一遍，效率按分支数往下掉。第二是递归本身的跳入跳出开销——函数调用一层层压栈，在 GPU 上这笔账很贵。

> **结论**：GPU 上要尽量把递归展开成循环，用一个显式的栈去模拟递归的调用栈。

栈放在哪里，是个纯粹的规模问题。规模小，寄存器就够；中等规模，用 shared memory，但要注意别踩 bank conflicts——同一个 bank 上的并发访问会被拆成多次；规模大了，老老实实分配一个数组。

栈里存的是“还没处理的节点索引”。弹一个、判一个，该分裂就把两个孩子压回去，直到栈空。逻辑跟递归完全等价，只是把编译器帮我们管的隐式栈，换成了自己能控制的内存。

### 接触与触点：线接触、面接触统统压成点

宽阶段只回答了“AABB 跟 AABB 撞上了”，具体撞没撞、撞在哪里，都还不知道。窄阶段要回答的就是这三件事：什么是接触、怎么判定、以及接触流形。

先看接触本身。三维空间里笼统地分，接触只有三种：点接触、线接触、面接触。

有意思的地方在于，**程序里的假设跟现实正好相反**。现实里绝大多数是面接触，线接触也有一些，点接触极其罕见——哪怕是一根针扎在物体上，接触处也会产生压力，有压力就必然有一定面积。真正的点没有面积，稍微加一点力压强就趋于无穷，现实里不会出现这种事。所以物理上一切接触最后都是面。

但实现上，线接触和面接触都不好处理。工程上的统一做法是：不管线还是面，全部离散成**触点**。两个盒子贴在一起，真实接触区是一整条线段、甚至一整块面，我们不去直接处理它，而是用若干个点去代表它。

> **定义**：一个独立的触点包含四样东西——位置（在哪里接触）、ID（区分不同的触点）、法线方向（穿透之后往哪个方向分离最快）、穿透深度（决定要施加多大的力、或者校正多远的位置）。

法线这一项值得单说。它不是用来描述几何的，而是给出一个“最快分开”的方向。后面的约束求解里，法线就是那个投影方向，所有相对速度都要往它上面投。

触点这件事还有一个隐蔽的坑：**同一个接触，可以生成出完全不同的触点集合**。一段接触线，你可以取两个端点，也可以取两个对角点，甚至取更多点，都算对。但刚体是随时间演化的，这一帧用一套策略、下一帧换另一套，就会出问题——防穿透本来就不可能一次修干净，总会剩一点残差；如果触点的位置和数量还在帧间跳变，残差就会被新的触点反复激发，仿真表现为抖动、不稳定。

所以选触点生成算法，第一要求不是快，而是**跨帧一致**。这也正是分离轴定理被普遍采用的原因：同样的几何、同样的姿态，它给出的结果是稳定可预期的。

### 分离轴定理：15 根轴都过了才算不相交

分离轴定理的出发点是一句大白话：

> 两个物体没撞上，就一定能找到一条直线从它们中间穿过去；反过来说，只要能找到这样一条直线，这两个物体一定没撞上。

已经穿插在一起的情况，无论怎么画线，都不可能把两个物体分到两侧。

把这句话翻译成计算：选定一个方向 $L$，把两个物体都投影到 $L$ 上，得到两条区间，看区间是否重叠。只要存在**一个**方向能让两条区间分离，就判定不相交。

实际算的时候不用遍历物体上的所有顶点，用中心点和“支持半径”就够了。设两个物体的中心为 $c_0$、$c_1$，沿 $L$ 方向各自最远的角点到中心的投影距离为 $r_0$、$r_1$，则分离条件是

$$\left| (c_0 - c_1) \cdot L \right| > r_0 + r_1$$

中心距在轴上的投影，大于两个物体各自“半宽”之和，两条区间就分开了。反过来，只要这个差小于零，区间就交叠，这根轴分不开它们。

一根轴显然不够。这跟排序是一个道理：某一个方向上判开了，不代表别的方向也安全。二维情况下，每个盒子有两个互相垂直的局部轴 $u$、$v$，两个盒子一共 4 根轴，4 根全判完才能说“不相交”。

三维就麻烦了。每个盒子有 3 根轴，两个盒子 6 根轴——这 6 根还不够。可以构造出这样的姿态：两个盒子斜着靠在一起，某条边跟另一条边离得极近，沿着任何一根面法线方向投影，区间都重叠着；真正能把它们分开的方向，是**垂直于这两条边**的方向。

```text
        盒子 A 的局部轴            盒子 B 的局部轴
          u0, v0, w0                 u1, v1, w1

  面法线轴：  u0  v0  w0   |   u1  v1  w1                共 6 根

  边叉乘轴：  u0 x u1   u0 x v1   u0 x w1
              v0 x u1   v0 x v1   v0 x w1                共 9 根
              w0 x u1   w0 x v1   w0 x w1

                                              合计 15 根
```

3 乘 3 正好是 9，加上面法线的 6 根，一共 **15 根分离轴**。15 根全部判完都不分离，才能断定这两个盒子不相交。

> **易错点**：只判 6 根面法线是二维思维的惯性。三维里“边对边”这种接触姿态必须靠叉乘轴才能分开，漏掉这 9 根，斜着贴在一起的盒子就会被误判成不相交。

计算量的大头是点乘：每根轴都要把顶点或者中心投上去。这里有一个很实用的化简——**把两个物体一起旋转，让左边那个盒子转回与世界坐标轴对齐的姿态**。这样一来，左边盒子的支持半径直接就是它的半长 $x_0$、$y_0$、$z_0$，不需要再做投影；右边那个盒子只需要相对这个新坐标系算一次。点乘的数量一下降下来，整体计算规模能压掉一大截。

### 接触流形：为什么只给一个点，盒子会抖下去

判定完相交，接下来要生成触点。最省事的做法是每次只出一个点，但这么做会出大问题。

想象一个盒子平放在另一个盒子上。如果每次检测只取一个点，这个点落在哪儿是有随机性的——特别平的时候，可能是左下角，也可能是左上、右上、右下。这一帧在左边，下一帧跳到右边，接触力作用的位置就跟着来回摆。盒子支撑不住，抖着抖着就掉下去了。

原因很直接：一个点只能在一个位置提供支撑，四个角轮流被顶一下，等于没有任何一个角被稳定顶住。所以要引入**接触流形**——用一组触点去近似整个接触面，或者接触线。

> **定义**：接触流形就是描述同一对物体之间那片接触区域的一组触点，它们落在同一个接触平面上，位置铺开覆盖整片区域。

流形的算法很多，这里讲最经典的一个：Sutherland-Hodgman 多边形裁剪。

思路是拿一个**裁剪多边形**去裁另一个**被裁剪多边形**，逐条边地裁。每取一条裁剪边，它所在的直线就把平面分成两半：一半保留，一半丢掉。把被裁剪多边形的每条边挨个过一遍：

- 端点在保留侧，这个顶点留下；
- 端点在丢弃侧，这个顶点去掉；
- 这条边跨过了裁剪线，就在交点处**新生成一个顶点**。

```text
      一条裁剪边所在的直线
   ────────────────────────────────
       保留侧           |        丢弃侧
                      |
      P_in ●──────────┼──────────● P_out
                      |  ▲
                      |  新增顶点：边与直线的交点
```

一条边处理完，换下一条裁剪边，继续裁刚才得到的结果。所有裁剪边都过完，剩下的那一个多边形就是交集——它的顶点，就是我们要找的触点。

这里有个必须提前想清楚的问题：裁剪出来的顶点数是**变的**。被裁的多边形可能剩 3 个点，也可能剩 5 个、8 个，具体多少取决于姿态。在 GPU 上，运行时动态分配空间是件很别扭的事。

所以前面反复强调“复杂几何最终都转成基本单元”，落到这里就变现了：四面体、六面体、三角形，这些单元的顶点数是固定的，输出缓冲要开多大，在计算之前就写得出来，一次分配到位，不必在运行时再要内存。

盒子对盒子最多 8 个点。换成更复杂的单元，8 个可能就不够了，但上限依然是可预估的。定长带来的好处，就在这儿。

### 同一个触点，两个速度

触点拿到手，动力学求解就可以开始了。这部分展开会非常多，我们只把最基本的链条走通。

同一个触点，在空间里是一个位置，但在两个刚体眼里是两个不同的相对坐标：在左边刚体的局部坐标系下记作 $r_0$，在右边刚体的局部坐标系下记作 $r_1$。

触点在刚体 $i$ 上的速度，由平动和转动两部分叠加：

$$v_i^{c} = v_i + \omega_i \times r_i$$

两个刚体在同一个位置各算出一个速度，$v_0^{c}$ 和 $v_1^{c}$，相减就是触点的相对速度。把它投影到法线上，得到一个标量：

$$v_n = n \cdot \left( v_0^{c} - v_1^{c} \right)$$

这个标量的符号，直接决定下一步要不要施加力。

| 法向相对速度 | 物理含义 | 处理方式 |
| :--- | :--- | :--- |
| $v_n > 0$ | 下一时刻正在分离 | 不用管，不施加力 |
| $v_n < 0$ | 下一时刻会穿进去 | 必须修正到 0 |
| $v_n = 0$ | 正好贴着一起走 | 临界状态，无需额外修正 |

大于 0 的时候为什么不用管？因为下一步它们本来就是分开的，你再推一把只会让它们弹得更远，纯属多余。小于 0 就必须管了——那是要穿进去的信号。

> **结论**：防穿透在速度层面的目标，就是让**下一时刻**的法向相对速度等于零：

$$J v' = 0$$

$J$ 是 Jacobian，把整个系统的广义速度映射到每个触点的法向相对速度；$v'$ 是待求的新速度。

为什么偏偏是等于零？等于零意味着两个物体贴着一起走，下一时刻既不会穿进去，也不会被弹开。这个“刚好贴着”，正是接触该有的样子。

### 内力不做功：接触力该长什么样

知道目标还不够，还得知道力从哪来、长什么样。

先立一条规矩：**接触力对整个系统来说是内力，内力不做功。**

这不是洁癖。你放一堆盒子在地上，如果内力会做功，能量就会凭空涨出来，过一会儿这堆盒子自己就炸了。仿真里出现莫名其妙的爆炸，往往就是这条底线没守住。

怎么保证不做功？力不能随便取，得取成这个形式：

$$F = J^{T}\lambda$$

$\lambda$ 是每个触点待求的力幅值。代进功率里验一下：

$$F \cdot v = \left( J^{T}\lambda \right)^{T} v = \lambda^{T} \left( J v \right) = 0$$

因为约束本来就要求 $J v = 0$，所以这个力在满足约束的速度上一点功都不做。

> **提示**：$F = J^{T}\lambda$ 不是唯一可行的形式，但它把力限制在 Jacobian 的行空间里——只有这个方向上的分量能真正减小穿透，垂直于它的分量既解决不了问题，又会往系统里灌能量，索性不要。

到这里，我们手上有两组东西。一组是约束 $J v' = 0$，另一组是动量方程，也就是牛顿第二定律：

$$M \dot{v} = F_{ext} + J^{T}\lambda$$

$M$ 是由质量和惯量构成的质量矩阵，$F_{ext}$ 是外力，比如重力。

问题来了：方程数和未知量对不上。$v'$ 不知道，$\lambda$ 也不知道，直接解是解不出来的。

### 消掉未知速度，解出 λ

先把时间离散掉。速度的导数写成一阶差分：

$$M \frac{v' - v}{\Delta t} = F_{ext} + J^{T}\lambda$$

把 $M$ 除过去、$\Delta t$ 乘过去、$v$ 移到右边：

$$v' = v + \Delta t\,M^{-1}F_{ext} + \Delta t\,M^{-1}J^{T}\lambda$$

右边除了 $\lambda$，其余全是已知量：$v$ 是当前速度，$F_{ext}$、$J$、$\Delta t$ 都已知。现在把这个 $v'$ 代进约束 $J v' = 0$：

$$J v + \Delta t\,J M^{-1}F_{ext} + \Delta t\,J M^{-1}J^{T}\lambda = 0$$

把含 $\lambda$ 的项留在左边，剩下的挪到右边：

$$\left( J M^{-1} J^{T} \right)\lambda = -\,\frac{1}{\Delta t} J v - J M^{-1} F_{ext}$$

$v'$ 被彻底消掉了，未知量只剩 $\lambda$。左边是一个稀疏矩阵，右边是一堆已知项——标准的 $A x = b$ 就出来了。

这个 $A = J M^{-1} J^{T}$ 的稀疏结构很规整：一个触点只跟它涉及的那两个刚体耦合，所以每一行只有少数几个非零块。

解它，Jacobi 可以，Gauss-Seidel 可以，共轭梯度也可以。解出 $\lambda$，每个触点的受力大小就都有了，接触力也随之确定：

$$F_{contact} = J^{T}\lambda$$

剩下的就是回代：用新速度更新线速度 $v$ 和角速度 $\omega$，再用它们去更新位置和旋转姿态。到这，一次刚体动力学的求解就走完了。

### 穿透之后：速度级惩罚与位置级修正

上面整套推导有一个隐含前提：触点正好落在表面上。这个前提在实际仿真里经常不成立——物体已经陷进去了。

这时候光把法向相对速度约束到 0 是不够的。两个物体以零相对速度一起陷在墙里，那就永远出不来了。

处理办法分两路。

一条路还在速度层面做。约束的右端不再取 0，而是加一个偏移量 $b$：

$$J v' = b$$

$b$ 代表的是：希望在这一步里，让两个触点沿法线方向分开一段距离所对应的速度。实现上再乘一个 $\beta$（0 到 1 之间）去调强度——取 0 等于完全不起作用，取 1 就是施加到最强。所以穿透不会被一步修干净，而是靠这种惩罚力一点点往外推，视觉上是缓慢分离。

> **提示**：$\beta$ 只在这套速度级修正里出现。0 和 1 是两个极端，实际值在两者之间调，没有一劳永逸的固定取值。

另一条路是位置层面的方法。这几年基于位置的做法做得很多，好处是跳过了“先算力、再由力更新速度和加速度”这一整套流程，直接调整速度甚至位置，对已经穿透的情形更友好。相关内容不少，英伟达那篇基于位置的刚体仿真 paper，以及同一条路线上其他团队的工作，都可以拿来对照。

### 其余约束：摩擦、球窝、活塞、合页

穿透只是约束的一种。刚体系统里还有摩擦，还有各种关节。这些我只点一下、不逐个展开，因为思路是同一套：把约束写成 Jacobian 形式，剩下的流程跟上面完全一样。真正需要单独推的只有 Jacobian 本身怎么算，那部分可以去翻教材。

#### 摩擦：最大能量耗散

两个物体接触之后如果有相对平动，就会产生摩擦。摩擦的约束形式跟法向很像，目标是切向相对速度等于 0——也就是不滑。

为什么目标要设成 0？可以从最大能量耗散的角度理解：摩擦本质上是在耗散能量，而耗散到极致就是两个触点彻底咬住、相对速度归零。所以摩擦的作用，就是尽可能地把这个相对速度往下压。

但这个目标经常达不到。库仑摩擦有一个硬上限：

$$\left| f_t \right| \le \mu f_n$$

切向摩擦力不能超过法向摩擦力乘摩擦系数。所以“等于 0”只是一个期望值，实际能做到的是在库仑锥允许的范围内，尽可能降低相对速度、尽可能多耗散一点能量。

#### 球窝：三个方程锁住位置

球窝关节（ball-and-socket joint）最直观：两个刚体上各取一个参考点，要求这两个点始终重合：

$$x_1 + r_1 = x_2 + r_2$$

三个分量就是三个方程，从六自由度里减掉三个，剩下三个——正好是三个转动自由度。所以球窝允许任意方向转动，但不允许相对平移。

实际做的时候还没完。三个转动自由度本身往往还要额外限制：人的肘关节不可能 180 度、360 度地转。所以工程上会在球窝的基础上再叠角度约束，把转动范围收住。

#### 活塞：两个平动加两个转动约束

活塞（prismatic joint）只保留两个自由度：沿轴 $d$ 平移，以及绕轴 $d$ 转动。

要把别的方向锁死，需要两部分约束。平移部分，垂直于 $d$ 的切平面有两个方向 $n_0$、$n_1$，两个锚点在这两个方向上的相对运动必须固定为零。转动部分，还要约束住另外两个倾斜方向：用上方物体算出来的 $u_1$、$v_1$ 必须始终与 $d$ 正交，否则物体会往这两个方向倒。

算 $d$ 的时候要注意坐标系：锚点和轴先统一到物体坐标里算，再变换出去，不然物体一转，轴的定义就跟着漂了。

#### 合页：五个约束只剩一个自由度

合页（hinge joint）跟活塞很像，转动约束完全一样——也只能绕一个轴转。区别在平移：合页连沿 $d$ 的平移都不允许，三个平动方向全锁住。

所以它一共五个约束：三个平动加两个倾斜，最后只剩一个绕轴转动的自由度。门、窗、单轴铰链，都是这个模型。

| 约束类型 | 保留自由度 | 约束方程数 | 锁住的是什么 |
| :--- | :--- | :--- | :--- |
| 球窝 ball-and-socket | 3（三个转动） | 3 | 两个参考点重合 |
| 活塞 prismatic | 2（沿轴平移 + 绕轴转动） | 4 | 两个切向平动 + 两个倾斜 |
| 合页 hinge | 1（绕轴转动） | 5 | 三个平动 + 两个倾斜 |

> **结论**：这三种基本约束，基本囊括了多体系统里绝大多数的关节类型。更复杂的约束不是另起一套算法，而是把几个基本约束叠在一起组合出来。

### 把结构画出来：两个演示

理论讲完，用两个 demo 把前面的东西跑起来。

#### Linear BVH 的可视化

示例在 `rigid_body` 目录下，界面用 Qt 搭的。打开之后就是一个场景窗口：一边是刚体，另一边能看到那棵层次结构。

代码逻辑跟搭场景的常规流程一致：建场景、把场景设进去、创建刚体动力学求解器、往场景里加基本单元，比如 box、球等等。

差别在于多了一个模块。Linear BVH 的内部结构没法直接拿去渲染，所以先把所有刚体的 AABB 导出来，喂给一个 `ConstructLinearBVH` 类；这个类构建完之后，通过 `getSortedAABB` 接口把内部节点和叶子的 AABB 全部导出成一个数组。

```text
   刚体集合
      |
      |  逐个刚体计算 AABB
      v
   AABB 数组 --> ConstructLinearBVH --> getSortedAABB --> toEdgeSet --> 渲染
                  （建树）             （内部 + 叶子）   （线框数据）
```

数组还不能直接画——AABB 是范围，渲染要的是线框。所以再接一个 `toEdgeSet` 模块，把每个 AABB 转成边的集合，最后交给边框渲染。

跑起来看到的就是一棵标准的二叉树：最外层一个最大的 AABB 把所有物体包住，然后逐层二分，这一拨分到上面、那一拨分到下面，一直到叶子。

因为整条链路都在 GPU 上，输入一变就会重新算 AABB、重建树，所以树是动态更新的。可视化在这里不只是好看——哪一层的包围盒明显不对，一眼就能看出来，比在日志里翻数组快得多。

#### SAT 与接触流形演示

第二个 demo 专门测窄阶段。场景里放两个盒子，默认不透明，看不清楚内部，所以先把材质调成半透明。

调好之后拖动其中一个盒子，就能看到接触流形——不是一个点，是一串点铺在接触面上。想把接触点看得更清楚，可以把盒子本身关掉，剩下的就只有检测出来的那些触点。

缩放、旋转都会跟着重新计算。旋转到某个姿态时，触点正好是 8 个——盒子对盒子来说，8 个点差不多够用了；换成更复杂的结构，8 个未必够。

> **提示**：这里之所以敢把上限卡在 8，是因为 GPU 上的数据结构基本都是定长的，动态长度对 GPU 不友好。用基本几何体去表达复杂结构，不光是效率问题，也是实现难度问题——定长意味着缓冲区大小可以提前算出来。

这两个 demo 对应的是两阶段检测的前半段，另外还有一些刚体碰撞的 demo，可以自己跑。后面还有第二个场景和补充材料。

### 现场问答：工业 mesh 与原子操作

**工业上会直接拿复杂 mesh 做检测吗？**

会。工业里的场景比这里讲的复杂得多，但做法是一致的：不会拿一个任意复杂的网格直接去撞。表面网格会转成三角网格或者四边形网格，体网格会转成四面体、六面体，最后一定是**基本单元与基本单元之间**的碰撞检测。

所以前面那些距离计算、投影、支持半径的工具，放到复杂模型上一样用——它们本来就是为基本几何单元写的通用工具。

**直接用 atomicMax / atomicMin 构建 BVH 行不行？**

行，但不划算。前面算过这笔账：没有提前退出，所有线程都要一路爬到根，重复量随线程数增长；原子操作还要排队，同一节点上并发越多，串行化越严重。CAS 加标记的方案把“谁该退出”这件事提前判掉了，收益就在这里。

**物体分布密集会不会带来更多阻塞？**

在这套方案里不太会。因为大量线程处理完一遍就退出了，往上爬的只是少数第二个到达者，阻塞不会随密度显著增长。

有兴趣的话，完全可以自己搭一个场景、写一个计算模块、调用现成的可视化，去测各种几何体之间的碰撞和刚体动力学。这套东西本身就是给人拆着玩的。

最后说一句整体定位：这些内容刻意停在基础层面，因为一旦陷进某个算法的细节，很容易迷失方向。先把“树怎么建、接触怎么找、约束怎么解”这条主线走通，具体的 Jacobian 推导、具体的求解器实现，再回头逐个补。
