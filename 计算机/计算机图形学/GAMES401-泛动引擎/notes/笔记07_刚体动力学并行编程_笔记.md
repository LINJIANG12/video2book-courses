# 刚体动力学并行编程

## 质点模型与时间积分

* **质点**

    * > **定义**：有质量、没有体积和形状的抽象简化模型，是刚体动力学的最简版本

    * 没有形状带来一个直接好处：不用考虑旋转，状态量只剩质量 $m$、位置 $\boldsymbol{x}$、速度 $\boldsymbol{v}$、加速度 $\boldsymbol{a}$ 与作用力 $\boldsymbol{F}$

    * 运动由牛顿第二定律决定：$\boldsymbol{F}=m\boldsymbol{a}$

* **两步递推更新**

    * 加速度是力除以质量，乘上时间片就是这段时间内速度的改变量：$\boldsymbol{v}^{t+\Delta t}=\boldsymbol{v}^{t}+\dfrac{\boldsymbol{F}}{m}\Delta t$

    * 速度更新完，再用**更新后**的速度推位置：$\boldsymbol{x}^{t+\Delta t}=\boldsymbol{x}^{t}+\boldsymbol{v}^{t+\Delta t}\Delta t$

    * 整个积分做的就是“用当前加速度推下一步速度，用下一步速度推下一步位置”

    * > **易错点**：顺序不能反——先更新速度，再用更新后的速度更新位置

* **离散时间轴**

    * 仿真把时间切成 $0$、$\Delta t$、$2\Delta t$……一串离散时刻，每个时刻做一次积分，把状态往前推一格

    * 初始化时给定位置、速度、初始的力；之后力在每个时刻被不断重新计算与调整

    * 连续时间的微分方程到计算机上一定要变成离散递推；所谓仿真，就是反复执行这条递推，把连续曲线采样成一串状态

    * 持续外力下的运动轨迹是一条连续弯折的曲线，也是最终渲染出来的东西

## 刚体的状态量与姿态积分

### 平动与转动的对应

* **刚体**

    * > **定义**：整体思路与质点一致，唯一的复杂化是多了一个旋转；旋转与平移两套概念一一对应。

    * 几乎可以把质点的表照抄一遍，只换名字

    * 对应关系如下表

| 平移 | 转动 | 对应关系 |
| :--- | :--- | :--- |
| 质量 $m$ | 惯性张量 $\boldsymbol{I}$ | 都衡量“多难被改变” |
| 位置 $\boldsymbol{x}$ | 旋转矩阵 $\boldsymbol{R}$ 或四元数 $q$ | 两者等价，可相互转换 |
| 速度 $\boldsymbol{v}$ | 角速度 $\boldsymbol{\omega}$ | 一阶状态量 |
| 加速度 $\boldsymbol{a}$ | 角加速度 $\boldsymbol{\alpha}$ | 二阶量 |
| 力 $\boldsymbol{F}$ | 扭矩 $\boldsymbol{\tau}$ | 外因 |

* **质量矩阵**

    * 质点把质量当标量就够了，因为质量集中在一点；刚体有形状，质量分布在形状上，所以用质量矩阵表示

    * 三个平移方向各占一份，写成对角阵是 $\mathrm{diag}(m,m,m)$

* **惯性张量**

    * > **定义**：$3\times3$ 矩阵，衡量刚体绕各轴转动有多难被改变，每个元素取决于质量如何分布、分布在哪个轴上

    * 质量越大，改变平移越困难；惯性张量越大，让它转起来、让它停下来都越困难；两者是同一个意思，只是作用在不同的自由度上

    * > **易错点**：惯性张量不是把质量抄三遍；刚体有形状，每个元素都由质量分布决定

### 姿态积分的非线性

* **旋转空间不是线性空间**

    * 平移中速度就是位置对时间的导数，$\boldsymbol{v}=\dot{\boldsymbol{x}}$，天经地义

    * 旋转矩阵是正交矩阵、四元数是单位四元数，它们被约束在一个流形上；不能对九个或四个分量逐个求时间偏导再当作角速度用

    * 逐元素求导得到的东西不满足“还是旋转”这个约束，物理上是错的。

    * 旋转矩阵的导数必须保持正交性，长成 $\dot{\boldsymbol{R}}=[\boldsymbol{\omega}]_\times\boldsymbol{R}$；四元数则是两个四元数相乘

    * > **易错点**：旋转的时间导数不能逐元素求，这是转动与平移最本质的差别

* **四元数姿态积分**

    * 角速度是三维向量、四元数是四维的，两者不能直接相乘；先给角速度补一个 0，变成 $\boldsymbol{\omega}_q=(0,\omega_x,\omega_y,\omega_z)$

    * 四元数导数：$\dot{q}=\dfrac{1}{2}\boldsymbol{\omega}_q\otimes q$

    * 更新后必须归一化：$q^{t+\Delta t}=\mathrm{normalize}\left(q^{t}+\dot{q}\Delta t\right)$，再转回旋转矩阵，姿态就落地了。

* **角速度更新**

    * 角加速度是惯性张量的逆乘扭矩，乘时间片加到角速度上：$\boldsymbol{\omega}^{t+\Delta t}=\boldsymbol{\omega}^{t}+\boldsymbol{I}^{-1}\boldsymbol{\tau}\Delta t$

    * 平移那一半与质点完全相同：外力先更新速度，再更新质心位置；转动那一半形状相似，但每一步都多带补零、四元数乘法与归一化

### 姿态与惯性张量的耦合

* **扭矩依赖当前姿态**

    * 扭矩是力臂叉乘力：$\boldsymbol{\tau}=\boldsymbol{r}\times\boldsymbol{F}$；外力作用在不同点上产生的扭矩不同

    * 必须结合当前姿态才知道力臂 $\boldsymbol{r}$ 是多少

* **惯性张量的世界坐标换算**

    * 物体在体坐标系里的惯性张量是固定的；一旦转起来，换算到世界坐标系要把旋转带进去：$\boldsymbol{I}_{\text{world}}=\boldsymbol{R}\boldsymbol{I}_{\text{body}}\boldsymbol{R}^{\top}$

    * 更新姿态与更新惯性张量互相咬合，整套状态按 $\Delta t$、$2\Delta t$ 一步步迭代

## 仿真主链路

* **真正的困难是力从哪里来**

    * 不考虑外力时，这套系统用任何积分方法都能跑——显式欧拉、隐式欧拉，随便挑，都能给出一条运动曲线

    * 问题在于力和扭矩很多时候根本不知道，得先算出来

    * 场景里有大量刚体时，“算出每个刚体受多大力、多大力矩”本身就是整个仿真最大的一块开销

    * **结论**：刚体动力学仿真的核心只有一句话——把力和扭矩算出来

* **速度级与位置级**

    * 基于速度的方法（velocity-level）直接算力和扭矩；基于位置的方法（position-level）可能直接去改位置

    * 两者层面不同，但笼统都可归到碰撞检测与约束求解这两个阶段；积分只是最后把结果落到状态上

* **三阶段流水线**

    * 上一帧状态先做碰撞检测：宽阶段粗筛出候选 pair，窄阶段算出真实接触点与法向

    * 宽阶段不追求精度，只追求快，把明显不可能碰上的物体成对剔除掉；筛剩下的潜在候选才交给窄阶段

    * 再在接触点上建立约束并求解，最后积分更新速度、位置、姿态

    * 分工：宽阶段负责“少算”，窄阶段负责“算准”，约束求解负责“算对”，积分只是最后把结果落到状态上

    * 真正麻烦的地方不在方程，而在“谁跟谁发生关系”——哪些物体对值得细算，事先不知道，得靠算法从成千上万个刚体里找出来

    ```text
       上一帧状态
            │
            ▼
      ┌──────────────────────────────────┐
      │ 碰撞检测：到底谁和谁碰上了          │
      │   宽阶段：粗筛出候选 pair           │
      │   窄阶段：算出真实接触点与法向       │
      └───────────────┬──────────────────┘
                      ▼
      ┌──────────────────────────────────┐
      │ 约束求解：在接触点上建立约束并求解    │
      └───────────────┬──────────────────┘
                      ▼
      ┌──────────────────────────────────┐
      │ 积分更新：速度、位置、姿态           │
      └──────────────────────────────────┘
    ```

## 包围体

### 包围体的类型

* **轴对齐包围盒（axis-aligned bounding box，AABB）**

    * > **定义**：找物体的最小紧致包络，并强制它的边与 $X$、$Y$、$Z$ 三个坐标轴对齐

    * 一个 AABB 只需要两个顶点（最小角点与最大角点）就能完整定义

    * 相交判定就是三次坐标区间比较，没有乘法、没有三角函数——“轴对齐”正是它便宜的根本原因

    * 毛病是斜置物体不紧致：一片斜放的叶子沿斜线很长，却只能用横平竖直的盒子框，盒子里空出大片区域

* **有向包围盒（oriented bounding box，OBB）**

    * > **定义**：本质上就是给 AABB 加一个旋转，让盒子顺着物体自己的朝向斜过去

    * 还是那片斜放的叶子，可以定义沿斜线方向的长方体，贴合得多

    * 特别适合狭长结构，能明显提高碰撞检测精度；单次判定开销高于 AABB，要带朝向参与运算

* **包围球**

    * > **定义**：取能包含物体的最小球体

    * 紧致度较低，单次判定开销高于 AABB

| 包围体 | 定义 | 紧致度 | 单次判定开销 |
| :--- | :--- | :--- | :--- |
| AABB | 边与 $X$、$Y$、$Z$ 轴对齐的最小包络 | 一般，斜置物体会虚胖 | 最低，两个顶点即可定义，纯坐标比较 |
| OBB | AABB 再加一个朝向旋转 | 高，能贴住斜置的狭长物体 | 高于 AABB，要带朝向参与运算 |
| 包围球 | 包含物体的最小球 | 较低 | 高于 AABB |

* **实际选用**

    * 从计算角度讲最简单的是 AABB，实际用得最多的也是 AABB；空间加速结构通常围绕 AABB 展开

    * OBB 与包围球都有一定计算量，只在需要更紧致时使用

### 剔除的不对称性

* **判定结果只有两种用处**

    * 包围盒不相交时，可以确定内部几何绝不相交——这句话是严格的，不是近似，因为包围盒是“包含”关系

    * 包围盒相交时什么都不能确定，必须往下做真正的几何检测

    * > **提示**：剔除是严格的，保留是有损的；这个不对称性正是整个宽阶段成立的前提

* **为什么不能直接两两算**

    * 场景里的牛、车在内存里通常是三角网格，几千上万个三角形

    * 两两直接算要做边与边、点与面的相交测试，每一对都要遍历几何单元，开销大到没法看

    * 绝大多数物体对其实八竿子打不着，根本不值得为它们付这个代价

## 排序扫描线

* **排序扫描线（sweep and prune）**

    * > **定义**：CPU 上最常用的宽阶段方案——把每个盒子在各轴上的区间投影成端点、排序，再从左往右扫描维护活动表

    * 先只看 $X$ 方向：每个盒子投影出一对端点（起点、终点），所有盒子的 $2N$ 个端点扔到一起按坐标排序

    * 扫到某个盒子的起点就把它加入 active list；扫到某个盒子的终点时，此刻表里所有还活着的起点都与它在 $X$ 上重叠，构成候选对，记下后把该盒子移出

    * CPU 引擎里用得很多，Bullet 的 `btAxisSweep3` 就是这套实现

    * 单轴扫描过程示例

    ```text
       X 方向投影，按端点排序后从左往右扫描：

       b0: |=========|
       b1:      |============|
       b2:             |==========|

       扫到 b0 起点 → 活动表 = {b0}
       扫到 b1 起点 → 活动表 = {b0, b1}
       扫到 b0 终点 → 表里的 b1 与 b0 重叠，记下 (b0, b1)，移出 b0
       扫到 b2 起点 → 活动表 = {b1, b2}
       扫到 b1 终点 → 记下 (b1, b2)，移出 b1
    ```

* **三轴取交集**

    * 一维扫描只回答“在这一个轴上有没有重叠”；两个物体完全可能在 $X$ 上重叠、在 $Y$ 上隔着老远

    * 标准排扫要做三遍：$X$ 一遍、$Y$ 一遍、$Z$ 一遍，最后取交集

    * 只有在三个轴上都重叠的 pair 才是真正的候选对

* **为什么不适合 GPU**

    * active list 是动态结构，长度在扫描过程中不断变化，最坏情况会爆炸：一个特别大的物体与所有物体相交时，从它进入活动表开始表里就永远挂着它，长度正比于物体总数

    * GPU 的寄存器、shared memory 都很小，这种不定长、上限还可能很大的结构根本放不进去，也无法在编译期把大小定下来

    * 扫描本身严格串行：处理第 $i$ 个端点时活动表长什么样，完全取决于第 $i-1$ 个端点处理完之后的样子；没法把 32 个端点分给 32 个线程同时处理

    * > **易错点**：排序本身在 GPU 上不难，并行排序是很成熟的技术；难的是排序**之后**的扫描。别把“GPU 排序快”误当成“这套算法能上 GPU”

## 均匀网格

* **均匀网格**

    * > **定义**：分配一个足够大的均匀网格罩住整个场景，逐个物体测它跟哪些格子相交，把物体 ID 记到那些格点上；检测时只查自身格与相邻格

    * 存储连续：格点按索引直接算地址，不需要指针跳转，也不需要顺着链表走

    * 计算完全可并行：每个物体算自己压到哪些格子是独立的，每个格子里的两两检测也是独立的，线程之间没有共享状态要协商

* **负载不均衡**

    * 苹果尺寸与格子相近时充其量占四个格子；一头牛可能要占几百上千个格子

    * 一个线程处理牛、一个线程处理苹果，同一个网格里线程的工作量能差两个数量级

    * GPU 最怕这个：一个 warp 里的线程要一起走，最慢的那个会把整组拖住

* **存储爆炸**

    * 物体在空间里的分布往往不均匀；特别远的地方孤零零放着一个物体，网格仍要铺满中间那一大片空区域

    * 绝大部分格子是空的，而空格子照样占显存

* **舒适区**

    * 适合物体尺寸比较单一、分布比较均匀的场合

    * 最典型的是封闭容器里的流体模拟，或者刚体颗粒（granular）模拟：容器大小固定、颗粒大小一致，网格铺满容器正好，谁都不浪费

    * 大物体小物体混在一起、分布又稀疏辽阔时，均匀网格不合适；需要“哪里有东西才往哪里细分”的结构

## 层次化包围盒

* **层次化包围盒（Linear BVH）**

    * > **定义**：用一棵自适应的二叉树划分空间，只在有物体的地方往下分；均匀网格是“致密”的，致密就意味着没物体的地方也铺着格子

    * 自顶向下做法：先分配一个足够大的包围盒把全部物体装进去，在中间切一刀把物体劈成两半，左边归一个节点、右边归另一个节点，各自带 bounding box，递归到节点里只剩一个物体

* **存储与查询代价**

    * 存储开销与物体数量基本成正比，线性，常数也不大：每个内部节点无非存一个 AABB 加两个索引

    * 查询从根往下走，每层做一次盒子相交测试，代价与树的深度成正比，比均匀网格贵一点

* **平衡是效率关键**

    * 查找永远从根往下遍历；每个叶子的深度都差不多时最坏情况短，整体效率高

    * 一棵歪成链的树会退化成线性扫描，那还不如直接用均匀网格

* **并行化的障碍**

    * 自顶向下是串行的：不切开根节点就不知道子节点在哪，不切开子节点就不知道孙节点在哪

    * 不能让一个线程建根节点、其余几千个线程干等着，等它建完再一起建下一层；树有十几层，每层一次全设备同步，并行度全被同步吃掉

    * 出路是自底向上、一次并行建完——Linear BVH 要做的事，包含莫顿码、并行构建与并行遍历

## 莫顿码

* **莫顿码（Morton code，Z-order 码）**

    * > **定义**：把多维坐标的二进制位交错塞进同一个整数——$x$ 的最低位、$y$ 的最低位、$x$ 的次低位、$y$ 的次低位，一路往上

    * 按码值排序之后，遍历顺序在空间上画出来是一条 Z 字形折线，所以也叫 Z-order 码

    * 同一个 $2\times2$ 小方块里的四个格点，码值是连续的四个数；$(0,0)$ 之后紧跟同一个小方块里的邻居，然后才跳到相邻的下一个 $2\times2$ 方块

    * 邻近性质是分形递归的：小范围邻近，大范围也邻近

* **动机：让内存邻居对上空间邻居**

    * 不管均匀网格还是层次结构，最后在显存里都是一维线性数组，所有东西都要拉平成地址

    * GPU 取数是“一块一块”取的：一个 warp 32 个线程同时发起访问，硬件把地址相近的数据一次搬进来

    * 空间上相邻、内存里也相邻时，32 次访问大概率落在同一批 cache line 上，miss 很少；反过来，空间挨着的两个物体在内存里隔着十万八千里，每次访问都 miss，带宽全浪费在搬无关数据上

    * 问题本质：把一个二维或三维空间索引映射成一维地址，并且尽量保住“邻近”这个关系

* **行主序为什么不行**

    * 二维按行存储把一整行 $x$ 存完再存下一行；$(0,0)$ 与 $(0,1)$ 同一个 $x$、下一行，空间只差一格，内存里却隔了整整一行（$N$ 个元素）

    * > **提示**：三维更糟——$z$ 方向差一格，内存里差了一整个平面

* **在刚体任务上的用法**

    * 每个三角形落在某个格点上，有自己的 $(x,y)$ 索引；给每个三角形算出莫顿码，按码值排序

    * 排完之后顺序与输入顺序完全不一样，但得到一条空间上有序的一维序列

    * 码值高位相同越多，说明落在同一个越大的格子里；码值相邻说明空间上邻近——层次信息已经编码进这条序列

## 有序二叉压缩前缀树

### 建树规则

* **从莫顿码直接长出树**

    * 建树本质是逐位看前缀，在第一个发生变化的地方切一刀

    * 根节点包含全部元素，对应整段有序序列；看最高位（对应 $y$ 的最高位），序列取值 0、1、1、1，在 0 与 1 的交界处切成 1 个与 3 个

    * 3 个那一支的下一位轮到 $x$ 的最高位，取值 0、0、1，在第二个 0 与 1 之间切成 2 个与 1 个

    * 递归处理每一半，每一条分叉都对应莫顿码里的一个比特位，分叉位置就是这一位第一次由 0 变 1 的地方

    * 只剩一个元素的节点直接成为叶子；树的结构完全由有序码值决定，不需要再回头去动几何数据

    ```text
    [ root : 4 tris ]
       |
       |-- y 最高位 = 0 --> [ leaf : 1 tri ]
       |
       +-- y 最高位 = 1 --> [ inner : 3 tris ]
                                 |
                                 |-- x 最高位 = 0 --> [ inner : 2 ]
                                 |                        |
                                 |                        +-- [ leaf ]
                                 |                        |
                                 |                        +-- [ leaf ]
                                 |
                                 +-- x 最高位 = 1 --> [ leaf : 1 tri ]
    ```

* **有序二叉压缩前缀树**

    * > **定义**：由有序莫顿码逐位分叉得到的标准二叉树，根分出两个子节点，内部节点继续各分出两个，最后所有叶子各装一个元素

    * 每次划分都是一分为二，节点数因此完全确定

### 节点规模与编号

* **节点数确定**

    * 内部节点数严格等于叶子节点数减一：$N$ 个叶子有 $N-1$ 个内部节点，整棵树一共 $2N-1$ 个节点

    * **结论**：整棵树的存储可以在建树之前一次算出来——一个长 $N$ 的数组存叶子，一个长 $N-1$ 的数组存内部节点；GPU 最怕运行途中动态扩容，这条性质正好绕开

* **节点编号本身就是索引**

    * 内部节点数组的第 0 号固定是根节点，遍历时直接从 0 进去，不用另外存根指针

    * 一个节点分裂出的左右两个孩子，就放在这个分裂位的左边和右边，在内部节点数组里是连续的一段

    * 每个内部节点的区间端点一定落在叶子上：它要么是这段区间的起点，要么是终点；划分点总是切在某两个相邻叶子之间

    * 第 $k$ 个内部节点就是第 $k$ 个与第 $k+1$ 个叶子之间的那道边界；叶子编号 $0\sim N-1$，内部节点编号 $0\sim N-2$，一一对应。

### 最长公共前缀

* **最长公共前缀 $\delta_{i,j}$**

    * > **定义**：排序后第 $i$ 到第 $j$ 个叶子（含两端）的莫顿码的最长公共前缀——从最高位往下逐位比较，第一次出现不同之前相同的那些位

    * 它刻画这些叶子在空间上“共同属于多大的一个格子”：例如某段的最长公共前缀是 00，就说明这一段里所有码值的高两位都是 00

    * 任意子区间的最长公共前缀一定不小于包含它的那个大区间——区间缩小、参与比较的元素变少，能保持一致的位数只会更多

* **只看首尾就够**

    * 算一个内部节点的最长公共前缀时，不需要遍历它包含的所有叶子，只看第一个和最后一个就够了。

    * 首尾两个码值已经把差异拉到最大，中间任何元素都不可能让公共前缀更短

    * **结论**：没有这条性质，算根节点的前缀就要遍历全部 $N$ 个叶子，越往上开销越大，这棵树在 GPU 上根本没法并行构建

## 并行建树

### 拓扑构建的线程映射

* **一个内部节点一个线程**

    * 自底向上，一个内部节点分配一个线程：$N-1$ 个内部节点，$N-1$ 个线程，谁也不等谁

    * 每个线程只需要知道自己管哪一段，不需要知道父节点是谁、兄弟是谁、自己处在树的第几层

    * 它只读已经排好序的叶子数组，只写自己那一条记录——这就是“消除对父节点的依赖”；传统自顶向下建树之所以串行，就是因为子节点必须等父节点算完才知道自己在哪

* **第一步：确定往哪边搜索**

    * 内部节点 $k$ 只知道自己是某段区间的一个端点，不知道是左端点还是右端点

    * 比较它与右邻居、左邻居分别组成的两元素区间的最长公共前缀：$\delta_{k,k+1}$ 与 $\delta_{k,k-1}$

    * 这两个值里恰好有一个等于父节点的前缀，另一个大于父节点前缀；等于的那一边，邻居已经属于父节点的另一半（出了自己这一支），大于的那一边，邻居还在自己这一支内部

    * 把两者相减看符号：$d=\delta_{k,k+1}-\delta_{k,k-1}$；$d<0$ 时 $k$ 是这段区间的右端点，真正的起点在左边，向左搜；$d>0$ 时 $k$ 是左端点，终点在右边，向右搜

    * > **易错点**：符号方向容易记反——判断依据不是“哪边前缀大就往哪边搜”，而是**哪边前缀小，说明那边已经出了自己的区间**

* **第二步：把区间的另一个端点找出来**

    * 方向定了就沿这个方向往外扩展，判据还是前缀：区间还在自己管辖范围内时，新拉进来的元素组成的区间公共前缀一定大于父节点的前缀

    * 一旦某个元素进来之后前缀掉到父节点那一档，说明它已经跨出去了。

    * 搜索的终止条件是“第一个让前缀不再大于父节点前缀的位置”，它的前一个位置就是区间的另一个端点

    * 能停下来且只会停一次，靠的是前缀单调性：区间越扩越大，公共前缀只会变短，不会变长；那个“掉档”的边界唯一确定

* **第三步：找到左右子树的分裂点**

    * 区间 $[first,last]$ 定下来，这个节点的前缀 $\delta_{first,last}$ 也就定了。

    * 左子树内部任意元素与 $first$ 组成的区间，前缀一定大于 $\delta_{first,last}$；一旦把右子树的元素拉进来，前缀就正好等于 $\delta_{first,last}$

    * 分裂位就是“第一个让前缀掉到 $\delta_{first,last}$ 的位置”

    * 三个位置凑齐，线程就产出了该产出的全部东西：自己的区间、分裂位、两个孩子的位置；写完退出，不用跟任何人同步

    * **结论**：整个拓扑的构建完全并行——每个线程只读叶子数组、只写自己那一条记录，彼此之间没有任何依赖；串行的自顶向下建树被拆成一次并行的自底向上扫描

### 自底向上的 AABB 合并

* **叶子与内部节点的差别**

    * 建完的还只是索引结构：谁是谁的孩子、区间怎么分、分裂位在哪；真正用来剔除的 AABB 还没算

    * 叶子 AABB 天然并行：每个叶子一个线程，彼此独立、互不冲突，工作量也均匀

    * 内部节点的 AABB 必须是两个孩子 AABB 的并集，必须等两个孩子都算完才能算

* **两个线程抢同一个父节点**

    * 模型是“每个节点一个线程”，左孩子与右孩子必然都想去算同一个父节点

    * 不管的话两个线程同时写同一块内存，结果是未定义的；就算结果碰巧对，也是白算一遍

    * 需要互斥：给每个内部节点挂一个原子计数器或一个标志位

    * 流程：线程算完自己的 AABB，先看父节点的两个孩子是不是都好了；没好，说明兄弟还没算完，直接退出；都好了，就把父节点的 AABB 算出来，再接着往上处理祖父节点

* **标记加原子 CAS**

    * 每个内部节点配一个标记，初值全是 0，意思是“还没有任何线程访问过”

    * 处理孩子节点的线程爬到父节点时，先对标记做一次原子比较并交换（atomic CAS）：把 0 换成 1，同时拿回旧值

    * 旧值是 0：我是第一个到的，把自己这个孩子的 AABB 登记好，然后退出

    * 旧值是 1：已经有人来过了，而那个人只可能是另一个孩子的线程；此时左右两个孩子的 AABB 都齐了，取出左孩子 ID、右孩子 ID 与它们各自的 AABB，合并成父节点的 AABB，再带着结果继续往上一层爬

    ```text
                  [ root ]  marker = 0
                  /        \
             [ P1 ]          [ P2 ]
             /    \          /    \
          [L0]   [L1]     [L2]   [L3]

    T0: L0 -> P1    CAS(P1, 0 -> 1) 返回 0
                    第一个到达，登记 L0 的 AABB，退出

    T1: L1 -> P1    CAS(P1, 0 -> 1) 返回 1
                    第二个到达，合并 L0 / L1 的 AABB，
                    算出 P1 的 AABB，继续向上
    ```

* **每个内部节点恰好被访问两次**

    * 左孩子那边的线程一次，右孩子那边的线程一次；两次都到齐，它才真正具备算自己 AABB 的条件

    * 逐层往上收敛，最后落在根节点上，整棵结构就建完了

    * 越往上活着的线程越少：有些节点的子树早被先跑完的线程合并掉了，别的线程爬到这里一看标记已经是 1，什么都不用做直接退出；真正还在爬的只是少数几条链

    * > **易错点**：标记只有 0 和 1 两个状态，不是计数器；第二个到达的线程不需要知道第一个是谁——兄弟关系由树的结构定死，能到这个节点的只可能是我兄弟那边的线程

* **为什么不用 atomicMax / atomicMin**

    * 直接对所有祖先节点做原子求并集，结果上行得通，但效率不好

    * 等于没有线程会提前退出：每个线程都得从自己的叶子一路算到根，第 0 个线程要爬到根，第 1 个线程也要爬到根

    * 一棵比较平衡的树，底下还压着大量线程在算，上面早就挤在根节点上，重复计算非常可观

    * 原子操作本身还要排队：同一个节点上 8 个线程同时做原子操作，就得一个一个来

    * CAS 方案里大量线程处理过一遍就退出，真正往上爬的只有“第二个到达者”；物体分布再密也只是并集更大，改不了“每个内部节点只被碰两次”这个上限

* **深度不平衡的代价**

    * 某个节点要算自己的 AABB，它依赖左边那支和右边那支，但较深那一支的 AABB 还远远没到构建出来的时候

    * 线程早早把活干完，只能空等或者退出，白占一个调度槽

    * 这就是树要尽量平衡的原因：树一歪，同一层节点的高度差拉大，自底向上的传播就卡在某一支上，并行度全泄在这里

## 并行遍历

* **递归写法与它的代价**

    * 最直观的写法：当前节点与查询框不相交就返回；相交且是叶子，记一对；相交且是内部节点，就对左右孩子各递归一次

    * 问题一：divergence——同一个 warp 里的线程走了不同分支，硬件只能把两条路都走一遍，效率按分支数往下掉

    * 问题二：递归本身的跳入跳出开销——函数调用一层层压栈，在 GPU 上这笔账很贵

    * **结论**：GPU 上要尽量把递归展开成循环，用一个显式的栈去模拟递归的调用栈

* **显式栈的规模分级**

    * 栈里存“还没处理的节点索引”：弹一个、判一个，该分裂就把两个孩子压回去，直到栈空

    * 逻辑与递归完全等价，只是把编译器管理的隐式栈，换成可自行控制的内存

    * 规模小，寄存器就够；中等规模用 shared memory，但要注意别踩 bank conflicts——同一个 bank 上的并发访问会被拆成多次；规模大了就老老实实分配一个数组

* **查询入口**

    * Linear BVH 的第 0 个元素存的就是根节点，查询从索引 0 开始，往下逐层比较包围盒

    * 输出是一批**潜在的**碰撞对，交给窄阶段去算真实接触点

## 接触与触点

* **三种接触**

    * 三维空间里笼统地分，接触只有三种：点接触、线接触、面接触

    * 现实里绝大多数是面接触，线接触也有一些，点接触极其罕见

    * 哪怕一根针扎在物体上，接触处也会产生压力，有压力就必然有一定面积；真正的点没有面积，稍微加一点力压强就趋于无穷

    * 物理上一切接触最后都是面

* **工程做法：线接触与面接触全部离散成触点**

    * 线接触和面接触都不好处理，统一做法是不管线还是面，全部离散成触点

    * 两个盒子贴在一起，真实接触区是一整条线段甚至一整块面，不去直接处理它，而是用若干个点去代表

    * > **定义**：一个独立的触点包含四样东西——位置（在哪里接触）、ID（区分不同的触点）、法线方向（穿透之后往哪个方向分离最快）、穿透深度（决定要施加多大的力、或者校正多远的位置）

    * 法线不是用来描述几何的，而是给出一个“最快分开”的方向；约束求解时，法线就是那个投影方向，所有相对速度都要沿它投影

* **触点生成必须跨帧一致**

    * 同一个接触，可以生成出完全不同的触点集合：一段接触线可以取两个端点，也可以取两个对角点，甚至取更多点，都算对。

    * 刚体是随时间演化的；这一帧用一套策略、下一帧换另一套，就会出问题

    * 防穿透本来就不可能一次修干净，总会剩一点残差；如果触点的位置和数量还在帧间跳变，残差就会被新的触点反复激发，仿真表现为抖动、不稳定

    * > **易错点**：选触点生成算法，第一要求不是快，而是**跨帧一致**；分离轴定理被普遍采用，正是因为同样的几何、同样的姿态下它给出的结果稳定可预期

## 分离轴定理

* **分离轴定理（separating axis theorem，SAT）**

    * > **定义**：两个物体没撞上，就一定能找到一条直线从它们中间穿过去；反过来，只要能找到这样一条直线，这两个物体一定没撞上

    * 已经穿插在一起的情况，无论怎么画线，都不可能把两个物体分到两侧

    * 计算上选定一个方向 $L$，把两个物体都投影到 $L$ 上得到两条区间，看区间是否重叠；只要存在一个方向能让两条区间分离，就判定不相交

* **投影判定公式**

    * 设两个物体的中心为 $c_0$、$c_1$，沿 $L$ 方向各自最远的角点到中心的投影距离为 $r_0$、$r_1$

    * 分离条件：$\left|(c_0-c_1)\cdot L\right|>r_0+r_1$

    * 中心距在轴上的投影大于两个物体各自“半宽”之和，两条区间就分开；反过来这个差小于零，区间就交叠，这根轴分不开它们

    * 实际算的时候不用遍历物体上的所有顶点，用中心点和“支持半径”就够了。

* **轴的数量**

    * 二维：每个盒子有两根互相垂直的局部轴 $u$、$v$，两个盒子一共 4 根轴，4 根全判完才能说“不相交”

    * 三维：每个盒子 3 根面法线轴，两个盒子 6 根——这 6 根还不够

    * 还要加 9 根边叉乘轴：两个盒子各 3 根边，两两叉乘，$3\times3=9$

    * 合计 $6+9=15$ 根分离轴；15 根全部判完都不分离，才能断定两个盒子不相交

    * > **易错点**：只判 6 根面法线是二维思维的惯性；三维里“边对边”这种接触姿态必须靠叉乘轴才能分开，漏掉这 9 根，斜着贴在一起的盒子就会被误判成不相交

* **计算化简**

    * 计算量的大头是点乘：每根轴都要把顶点或者中心投上去

    * 把两个物体一起旋转，让左边那个盒子转回与世界坐标轴对齐的姿态

    * 这样左边盒子的支持半径直接就是它的半长 $x_0$、$y_0$、$z_0$，不需要再做投影；右边那个盒子只需要相对这个新坐标系算一次

    * 点乘数量下降，整体计算规模能压掉一大截

## 接触流形

* **单点接触为什么会抖**

    * 一个盒子平放在另一个盒子上，每次检测只取一个点，这个点落在哪儿是有随机性的——特别平的时候可能是左下角，也可能是左上、右上、右下

    * 这一帧在左边、下一帧跳到右边，接触力作用的位置就跟着来回摆，盒子支撑不住，抖着抖着就掉下去了。

    * 原因很直接：一个点只能在一个位置提供支撑，四个角轮流被顶一下，等于没有任何一个角被稳定顶住

* **接触流形**

    * > **定义**：描述同一对物体之间那片接触区域的一组触点，它们落在同一个接触平面上，位置铺开覆盖整片区域

    * 用一组触点去近似整个接触面或接触线，而不是只给一个点

* **Sutherland-Hodgman 多边形裁剪**

    * 拿一个裁剪多边形去裁另一个被裁剪多边形，逐条边地裁

    * 每取一条裁剪边，它所在的直线就把平面分成两半：一半保留，一半丢掉

    * 被裁剪多边形的每条边挨个过一遍：端点在保留侧则顶点留下；端点在丢弃侧则顶点去掉；这条边跨过裁剪线，就在交点处新生成一个顶点

    * 一条边处理完换下一条裁剪边，继续裁刚才得到的结果；所有裁剪边都过完，剩下的多边形就是交集，它的顶点就是要找的触点

    ```text
          一条裁剪边所在的直线
       ────────────────────────────────
           保留侧           |        丢弃侧
                          |
          P_in ●──────────┼──────────● P_out
                          |  ▲
                          |  新增顶点：边与直线的交点
    ```

* **变长输出与定长基本单元**

    * 裁剪出来的顶点数是变的：可能剩 3 个点，也可能剩 5 个、8 个，取决于姿态

    * GPU 上运行时动态分配空间很别扭；四面体、六面体、三角形这些单元顶点数固定，输出缓冲要开多大在计算之前就写得出来，一次分配到位

    * 盒子对盒子最多 8 个点；换成更复杂的单元，8 个可能不够，但上限依然可预估

    * > **提示**：GPU 上的数据结构基本都是定长的，动态长度对 GPU 不友好；用基本几何体表达复杂结构，不光是效率问题，也是实现难度问题——定长意味着缓冲区大小可以提前算出来

## 触点速度与法向约束

* **同一触点的两个速度**

    * 同一个触点在空间里是一个位置，但在两个刚体眼里是两个不同的相对坐标：在左边刚体的局部坐标系下记作 $r_0$，在右边记作 $r_1$

    * 触点在刚体 $i$ 上的速度由平动与转动两部分叠加：$v_i^{c}=v_i+\omega_i\times r_i$

    * 两个刚体在同一位置各算出一个速度，相减就是触点的相对速度；投影到法线上得到一个标量：$v_n=n\cdot\left(v_0^{c}-v_1^{c}\right)$

* **法向相对速度的符号**

| 法向相对速度 | 物理含义 | 处理方式 |
| :--- | :--- | :--- |
| $v_n>0$ | 下一时刻正在分离 | 不用管，不施加力 |
| $v_n<0$ | 下一时刻会穿进去 | 必须修正到 0 |
| $v_n=0$ | 正好贴着一起走 | 临界状态，无需额外修正 |

* **符号的物理含义**

    * $v_n>0$ 时下一步它们本来就是分开的，再推一把只会让它们弹得更远，纯属多余

    * $v_n<0$ 是要穿进去的信号，必须管

    * $v_n=0$ 时两个物体正好贴着一起走

* **约束目标**

    * **结论**：防穿透在速度层面的目标，就是让**下一时刻**的法向相对速度等于零，即 $Jv'=0$

    * $J$ 是 Jacobian，把整个系统的广义速度映射到每个触点的法向相对速度；$v'$ 是待求的新速度

    * 等于零意味着两个物体贴着一起走：下一时刻既不会穿进去，也不会被弹开；这个“刚好贴着”正是接触该有的样子

## 接触力的形式

* **内力不做功**

    * > **定义**：接触力对整个系统来说是内力，内力不做功

    * 这不是洁癖：放一堆盒子在地上，如果内力会做功，能量就会凭空涨出来，过一会儿这堆盒子自己就炸了。

    * 仿真里出现莫名其妙的爆炸，往往就是这条底线没守住

* **力必须取成 $F=J^{T}\lambda$**

    * $\lambda$ 是每个触点待求的力幅值

    * 代进功率里验：$F\cdot v=(J^{T}\lambda)^{T}v=\lambda^{T}(Jv)=0$

    * 因为约束本来就要求 $Jv=0$，所以这个力在满足约束的速度上一点功都不做

    * > **提示**：$F=J^{T}\lambda$ 不是唯一可行的形式，但它把力限制在 Jacobian 的行空间里——只有这个方向上的分量能真正减小穿透；垂直于它的分量既解决不了问题，又会往系统里灌能量，索性不要

* **动量方程与未知量**

    * 动量方程就是牛顿第二定律：$M\dot{v}=F_{ext}+J^{T}\lambda$

    * $M$ 是由质量和惯量构成的质量矩阵，$F_{ext}$ 是外力，比如重力

    * 手上只有两组东西：约束 $Jv'=0$ 与动量方程；$v'$ 不知道，$\lambda$ 也不知道，方程数和未知量对不上，直接解解不出来

## 约束方程的消元求解

* **时间离散**

    * 速度的导数写成一阶差分：$M\dfrac{v'-v}{\Delta t}=F_{ext}+J^{T}\lambda$

    * 把 $M$ 除过去、$\Delta t$ 乘过去、$v$ 移到右边：$v'=v+\Delta t\,M^{-1}F_{ext}+\Delta t\,M^{-1}J^{T}\lambda$

    * 右边除了 $\lambda$，其余全是已知量：$v$ 是当前速度，$F_{ext}$、$J$、$\Delta t$ 都已知

* **代入约束消元**

    * 把 $v'$ 代进 $Jv'=0$：$Jv+\Delta t\,JM^{-1}F_{ext}+\Delta t\,JM^{-1}J^{T}\lambda=0$

    * 含 $\lambda$ 的项留左边、其余挪右边：$\left(JM^{-1}J^{T}\right)\lambda=-\dfrac{1}{\Delta t}Jv-JM^{-1}F_{ext}$

    * $v'$ 被彻底消掉，未知量只剩 $\lambda$；左边是稀疏矩阵、右边是一堆已知项，标准的 $Ax=b$ 就出来了。

* **稀疏结构与求解**

    * $A=JM^{-1}J^{T}$ 的稀疏结构很规整：一个触点只跟它涉及的那两个刚体耦合，每一行只有少数几个非零块

    * 求解器可选 Jacobi、Gauss-Seidel、共轭梯度

    * 解出 $\lambda$ 后每个触点的受力大小都有了，接触力为 $F_{contact}=J^{T}\lambda$

    * 剩下的就是回代：用新速度更新线速度 $v$ 与角速度 $\omega$，再用它们更新位置和旋转姿态

## 穿透处理

* **速度级偏移**

    * 速度级约束的推导有一个隐含前提：触点正好落在表面上；实际仿真里这个前提经常不成立，物体已经陷进去了。

    * 光把法向相对速度约束到 0 不够：两个物体以零相对速度一起陷在墙里，就永远出不来了。

    * 约束的右端不再取 0，而是加一个偏移量 $b$：$Jv'=b$

    * $b$ 代表希望在这一步里让两个触点沿法线方向分开一段距离所对应的速度

* **$\beta$ 的调节**

    * 实现上再乘一个 $\beta$（0 到 1 之间）去调强度：取 0 等于完全不起作用，取 1 就是施加到最强

    * 穿透不会被一步修干净，而是靠这种惩罚力一点点往外推，视觉上是缓慢分离

    * > **提示**：$\beta$ 只在这套速度级修正里出现；0 和 1 是两个极端，实际值在两者之间调，没有一劳永逸的固定取值

* **位置级方法**

    * 近年基于位置的做法做得很多，好处是跳过“先算力、再由力更新速度和加速度”这一整套流程

    * 直接调整速度甚至位置，对已经穿透的情形更友好

## 关节约束

* **统一套路**

    * 摩擦与各种关节的思路是同一套：把约束写成 Jacobian 形式，剩下流程与接触完全一样

    * 真正需要单独推的只有 Jacobian 本身怎么算

### 摩擦

* **摩擦约束**

    * 两个物体接触之后如果有相对平动，就会产生摩擦；约束形式跟法向很像，目标是切向相对速度等于 0，也就是不滑

    * 目标设成 0 可以从最大能量耗散的角度理解：摩擦本质上在耗散能量，耗散到极致就是两个触点彻底咬住、相对速度归零

* **库仑摩擦上限**

    * 目标经常达不到，因为库仑摩擦有一个硬上限：$|f_t|\le\mu f_n$

    * 切向摩擦力不能超过法向摩擦力乘摩擦系数

    * “等于 0”只是期望值，实际能做到的是在库仑锥允许的范围内尽可能降低相对速度、尽可能多耗散一点能量

### 球窝

* **球窝关节（ball-and-socket joint）**

    * 两个刚体上各取一个参考点，要求这两个点始终重合：$x_1+r_1=x_2+r_2$

    * 三个分量就是三个方程，从六自由度里减掉三个，剩下三个——正好是三个转动自由度

    * 允许任意方向转动，但不允许相对平移

* **角度限制**

    * 三个转动自由度本身往往还要额外限制：人的肘关节不可能 180 度、360 度地转

    * 工程上会在球窝的基础上再叠角度约束，把转动范围收住

### 活塞

* **活塞关节（prismatic joint）**

    * 只保留两个自由度：沿轴 $d$ 平移，以及绕轴 $d$ 转动

    * 平移部分：垂直于 $d$ 的切平面有两个方向 $n_0$、$n_1$，两个锚点在这两个方向上的相对运动必须固定为零

    * 转动部分：用上方物体算出来的 $u_1$、$v_1$ 必须始终与 $d$ 正交，否则物体会往这两个方向倒

    * 一共 4 个约束方程

* **坐标系统一**

    * 算 $d$ 的时候，锚点和轴先统一到物体坐标里算，再变换出去

    * 否则物体一转，轴的定义就跟着漂了

### 合页

* **合页关节（hinge joint）**

    * 转动约束与活塞完全一样：也只能绕一个轴转

    * 区别在平移：合页连沿 $d$ 的平移都不允许，三个平动方向全锁住

    * 一共五个约束：三个平动加两个倾斜，最后只剩一个绕轴转动的自由度

    * 门、窗、单轴铰链都是这个模型

| 约束类型 | 保留自由度 | 约束方程数 | 锁住的是什么 |
| :--- | :--- | :--- | :--- |
| 球窝 | 3（三个转动） | 3 | 两个参考点重合 |
| 活塞 | 2（沿轴平移 + 绕轴转动） | 4 | 两个切向平动 + 两个倾斜 |
| 合页 | 1（绕轴转动） | 5 | 三个平动 + 两个倾斜 |

* **关节类型的组合性**

    * **结论**：这三种基本约束基本囊括了多体系统里绝大多数的关节类型

    * 更复杂的约束不是另起一套算法，而是把几个基本约束叠在一起组合出来

## 可视化与工程实践

* **BVH 导出与渲染链路**

    * 内部结构无法直接渲染：先把所有刚体的 AABB 导出，喂给一个建树类 `ConstructLinearBVH`

    * 构建完之后通过 `getSortedAABB` 接口把内部节点和叶子的 AABB 全部导出成一个数组

    * AABB 是范围、渲染要的是线框，所以再接一个模块把每个 AABB 转成边的集合，最后交给边框渲染

    * 渲染出来是一棵标准的二叉树：最外层一个最大的 AABB 把所有物体包住，然后逐层二分直到叶子

* **动态重建与可视化诊断**

    * 整条链路都在 GPU 上，输入一变就重新算 AABB、重建树，所以树是动态更新的。

    * 可视化不只是好看：哪一层的包围盒明显不对，一眼就能看出来，比在日志里翻数组快得多

* **窄阶段演示**

    * 场景里放两个盒子，默认不透明，先调成半透明才能看清内部

    * 拖动其中一个盒子，能看到接触流形——不是一个点，而是一串点铺在接触面上

    * 缩放、旋转都会跟着重新计算；旋转到某个姿态时，触点正好是 8 个

* **工业复杂 mesh 的处理**

    * 工业场景比基础场景复杂得多，但做法一致：不会拿一个任意复杂的网格直接去撞

    * 表面网格转成三角网格或者四边形网格，体网格转成四面体、六面体，最后一定是**基本单元与基本单元之间**的碰撞检测

    * 距离计算、投影、支持半径这些工具本来就是为基本几何单元写的通用工具，放到复杂模型上一样用

* **atomicMax / atomicMin 的取舍**

    * 可以直接用原子操作构建 BVH，但不划算：没有提前退出，所有线程都要一路爬到根，重复量随线程数增长

    * 原子操作还要排队，同一节点上并发越多，串行化越严重

    * CAS 加标记的方案把“谁该退出”提前判掉了，收益就在这里

* **密集分布是否带来更多阻塞**

    * 在这套方案里不太会：大量线程处理完一遍就退出，往上爬的只是少数“第二个到达者”

    * 阻塞不会随密度显著增长
