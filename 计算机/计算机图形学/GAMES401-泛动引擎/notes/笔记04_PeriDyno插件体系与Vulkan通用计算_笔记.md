# PeriDyno插件体系与Vulkan通用计算

## 从研究到应用的闭环

* **框架真正解决问题的场合**

    * 只针对某个特定算法写求解器、跑单个算例，有没有框架、有没有引擎区别不大，框架在这个环节帮不上太多忙。

    * 需要很多模块相互依赖、多人协同开发时差别才出来：模块怎么配合、接口怎么对齐、谁的改动会不会把别人的东西弄坏，都要有地方统一管。

* **三段流程与闭环**

    * 研究、研发、应用三个区域串成一个流程，但不是单向流水线：应用中发现的新问题会回到研究起点，首尾相接成闭环。

    * 研究段的产出是论文、算法实现与代码；研发段做工程化改造，产出可用的模块与接口；应用段产出真实场景中的系统。

* **各阶段的成本性质**

    * 三个阶段的产出不同，成本性质也完全不同：研究拼不确定性，研发拼规范与改造，应用拼实测指标。

| 阶段 | 主要产出 | 成本的性质 |
| :--- | :--- | :--- |
| 研究 | 论文、算法实现、代码 | 不确定性：选题、调研、实现、对比、撰写、投稿修改，周期长且不可控 |
| 研发 | 可用的模块与接口 | 规范与改造：数据规范、接口规范、兼容性改造、测试 |
| 应用 | 真实场景中的系统 | 实测指标：性能、稳定性、可靠性 |

* **研究段的资产流失**

    * 论文发了、代码当时能用，过一阵就不知道扔到哪去，或者根本找不着。

    * 软件系统随底层库与平台更新不断演进，长期缺乏维护，整个系统最后跑不起来、用不起来。

    * 科研代码文档与注释不健全，真正工程性的代码资产很难传承。

* **研发段的角色问题**

    * 核心算法（如流体算法）纯依赖工程改造、或丢给另一批工程人员解决，很多时候并不合适——写它的人不参与，改出来的东西就不对味。

    * 理想情况是工程人员、研发人员、研究人员一起配合；整个闭环还需要编程人员与设计人员参与，角色之间的协作本身有成本。

* **引擎压低的正是协作成本**

    * 每个角色在自己的领域里是专业的；让研究人员去解决工程问题他并不擅长，反过来也一样。

    * 引擎要回答的是：能否让每个人在自己熟悉的领域深耕，而跨领域的协作借助引擎与工具变得更方便。

    * 跨领域有风险：对那个领域不熟，很可能以为挖到了金子，实际挖的是破石头。

## 蓝图与可视化的程序逻辑

* **蓝图（Blueprint）**

    * > **定义**：一种可视化的编程界面，用图与节点表达程序逻辑；它与 C++ 解决同一个问题——都是通过编程完成某个任务，只是把代码文本换成了图和节点。

    * 它不是"给不会写程序的人玩的玩具"，而是另一条表达程序逻辑的通道；可视化的形式对非计算机、非 IT 专业的人更友好。

* **界面系统的三代形态**

    * 标签系统（UE1、UE2）：针对某个对象一栏属性、一栏事件，在面板上改属性、挂事件即完成配置；功能固化在程序里，写程序时就要预先定制好，后期灵活重组很麻烦。

    * 固定属性表表达不了不同对象、不同组件之间的数据传递与消息传递，而这种配合恰恰是很多任务需要的。

    * 组件化加图（UE3）：先组件化，组件之间再通过数据传递、用图串起来；任务流程不再固定，为后期应用与设计留出动态、可配置的能力。

    * 拖拽式（UE4）：不太复杂的任务可以完全不依赖 C++ 代码，直接用拖拽界面把任务搭出来。

* **蓝图省掉的三样成本**

    * 简化任务流程：原来要一行行代码描述的流程，拖几个节点、连几根线就成型。

    * 降低研发成本：简单任务不必都压在编码人员身上；改参数只改节点上的值，不必动 C++ 再重新编译。

    * 团队协作：编程人员把底层能力做成节点，设计人员在上层连节点搭流程，两边不用互相等。

* **批量试参的旧做法**

    * 写一堆脚本读参数、批量修改与测试；或者反复改程序里的参数，但 C++ 是编译型语言，每次改完都要重新编译，开销较大。

* **轻量化的取舍**

    * UE 整套系统本身相当复杂，基础代码没有多少人能通读一遍；照着做一套同样复杂的东西，人力与资源投入不会特别稳定。

    * 目标因此换成：以比较小的维护成本，搭出一套类似的系统。

* **两条逻辑的分工**

    * 代码运行逻辑对应研发人员、程序员；界面运行逻辑对应用户。

    * 通用编程语言的表达能力远超节点图，一套节点图表达不完；但仿真任务比通用编程更特殊，不需要具备通用编程能力。

    * 目标是让两种逻辑看起来差不多一致，而不是追求表达能力完全对等：程序员负责把算法包成节点，用户负责把节点连成场景，接口在中间对上。

## 四层架构与 Field

* **四层结构**

    * 场景（Scene）→ 节点（Node）→ 模块（Module）→ Field：往下是"由什么构成"，顶层是场景，场景里是节点，节点里挂模块，最底层落到 Field。

    * 节点在界面上就是节点编辑器里的一个图案；Field 按功能分成四类：控制变量、状态变量、输入、输出。

* **控制变量：以 cube 为例**

    * cube 在 model 库里创建，创建后实际生成一个 box。

    * 自身控制变量三个：边长（box 多大）、表面网格类型（剖分成三角网格还是四边形网格）、分段数（网格切多细）。

    * 它继承父类 parametric model（参数化模型），父类定义平移、缩放、旋转；界面上看到的完整控制变量是子类自身与父类继承的合并。

* **状态变量**

    * > **定义**：描述一个节点所需的最小状态集合，即描述该节点当前是什么样的一组量。

    * 控制变量是手上的旋钮，状态变量是节点当前的状态账本，输出是算出来的结果。

* **从控制到输出的单向链**

    * 调控制变量会更新状态变量，用状态变量一分析就得到节点最终形态；模型还会输出一个标准立方体，部分节点另有输入——这正是节点之间能相连的原因。

```text
控制变量（边长 / 网格类型 / 分段数 / 平移 / 缩放 / 旋转）
        │ 写入并更新
        ▼
状态变量（描述该节点所需的最小状态集合）
        │ 分析
        ▼
节点最终形态 ──► 输出（如标准立方体）
                     ▲
       部分节点的输入 ┘
```

* **界面与代码的对应**

    * 代码里有哪些控制变量，图案上就有对应属性；代码里有哪些状态，界面上就有对应显示；状态变量在界面右侧栏统一列出，便于直接查看当前状态。

    * 图形界面与 C++ 底层逻辑靠宏定义统一。

## 场景、节点图与 connect

* **场景是有向无环图（Directed Acyclic Graph，DAG）**

    * 场景列表包含各种节点，节点之间有数据传递；节点与连线构成 DAG，数据流全部从前往后，不会绕回来。

    * 把所有节点与中间连线合起来，对应的就是一个场景；界面右侧是图形化场景图，中间视口是它显示出来的效果。

* **`connect` 的语义**

    * `connect` 做的事与界面上那根连线一模一样：前一个节点的数据连入后一个节点。

    * 代码层面的指令与 UI 层面的图案一一对应，这份对应关系主要靠反射与宏定义实现。

* **倒水场景的组成**

    * 创建场景后设置重力，这是场景级参数。

    * 创建发射器并加入场景，通过属性改它的位置；发射器后接流体求解器，用 `connect` 把粒子送进求解器。

    * 流体是粒子系统，采用 SPH 方法，因此额外挂渲染辅助模块把流体画出来。

    * 创建边界：球的表面网格与底部平面先合并，再送入流固耦合节点；耦合节点有两路输入——一路流体、一路合并后的表面网格。

    * 渲染辅助模块只是挂在流体后面做可视化，不参与耦合计算。

* **代码视图**

    * 场景类里的实现不多，因为所有实现都不在 `main` 里：`main` 只负责创建这个场景。

    * 界面用 Qt 搭建，这个场景在示例工程里可以直接跑。

## 反射机制与全局类表

### 反射的必要性

* **反射（Reflection）**

    * > **定义**：程序在运行时检测、查询、修改自身状态的能力——跑起来之后能知道自己有哪些类型、每个类型有哪些成员、每个成员是什么类型，还能按名字造对象、改值。

    * 这套能力在 C++ 里不是白给的，必须自己搭。

* **缺失反射时的三个障碍**

    * 框架不知道新写的类到底是什么类型。

    * 框架不知道这个类里包含哪些变量和方法。

    * 无法按字符串动态创建对象：`new` 要一个类名，而字符串在运行时只是数据，编译器早已不在场。

* **头文件是根因**

    * C++ 必须把类型对应的头文件 include 到使用处，编译器才知道类型长什么样。

    * 第三方开发者写了一个类，如果他不告诉你，你这边没有头文件，编译期就一无所知；而 UI 点开一个对象要弹属性框，必须识别出对象有哪些属性才能把输入框摆出来。

* **反射到位后的界面效果**

    * 输入 `cube` 这个字符串，就能创建出 cube 对象并加入节点编辑器。

    * 反射能识别边长、分段数、缩放、平移、旋转等属性，界面就能为该类生成可调节编辑器；在编辑器里改值，改的是对象自身的状态。

### Object 与全局类表

* **公共父类 `Object`**

    * 所有依赖反射的类都继承公共父类 `Object`；C++ 是编译型语言、不支持反射，而 Java 是解释型、运行时可动态获取成员变量与函数，C++ 没有这个条件，只能找一个所有类都能挂上去的统一父类。

    * 反射机制实现在 `Object` 里；派生类不必管反射怎么实现，只需按规则（依赖模板编程的一些特性加一些宏定义）把"我这个新类包含哪些信息"告诉父类，注册与查询都由父类完成。

* **`ClassInfoMap`**

    * > **定义**：一张从类名到 `ClassInfo` 的映射表，本质是 map 结构；每个 `ClassInfo` 存着这个类的信息，包括它的构造函数。

    * 新写一个类就调用一次注册函数，类表里新增一个对象；所有类统一存在 `Object` 的这个静态结构里，这个结构是全局的。

    * 任何地方想创建对象都查这张表：拿类名找到 `ClassInfo`，取出构造函数，把子类构造出来；所以创建对象的本质仍是调用子类构造函数，只是由字符串驱动、发生在运行时。

```text
程序启动（进入 main 之前）
        │ 各子类的静态注册对象依次初始化
        ▼
Object::ClassInfoMap        全局静态
  "Cube"  ──► ClassInfo
  "Plane" ──► ClassInfo
        │ 运行时按类名字符串查找
        ▼
ClassInfo 里存着构造函数
        │
        ▼
创建出对应的子类对象
```

* **并发保护**

    * 类表是全局的，多个线程同时读写会出现异常，因此需要原子操作保护。

### 两个宏与注册时机

* **声明宏与实现宏**

    * 声明宏放在头文件里，定义一个类信息的静态变量，该静态变量需要注册到 `Object` 父类。

    * 实现宏（`implement_class` 一类）创建一个 `ClassInfo` 对象，创建时传入两样东西：类的名称 `name`，以及这个类对应的构造函数。

    * 头文件必须同时 include 声明与实现两个宏，少一个，这个类在类表里就不完整。

* **注册发生在进入 `main` 之前**

    * 成立的前提是 C++ 的一个性质：所有静态变量都会在进入 `main` 函数之前初始化完。

    * 子类静态注册对象依次初始化、向 `Object` 报到，等真正运行时整个类表已经完整；不需要谁在启动时手动遍历，也不用担心"用到它时还没注册"。

    * > **易错点**：注册是静态变量初始化阶段完成的，不是运行到某一行代码才做；所以宏必须放在头文件里，随便写进某个函数的实现里，注册时机就错了。

### 成员变量的注册

* **`FieldBase` 与字段表**

    * 控制变量要被 UI 调整，UI 必须知道成员叫什么、是什么类型，才能摆出合适的输入框；所以需要暴露给界面的成员变量也要走反射。

    * 成员变量这一层靠父类 `FieldBase` 完成，思想与注册类相同：成员把自己的信息告诉 `FieldBase`，由它完成注册。

* **注册一个控制变量要提供的四样信息**

    * 所属类的名称。

    * 成员变量叫什么。

    * 类型：针对特定模块说明这个成员是控制变量、参数、输入还是输出。

    * `this`：实际传入的是一个 node 指针，传进去之后可以针对整个 node 做一些额外的操作。

* **暴露范围**

    * > **注意**：不是定义得越多越好，只需要暴露必须的那些成员变量；有些成员只是内部使用就不必暴露，UI 也不需要控制所有变量，只需要控制对外开放的那些。

* **默认值与覆盖**

    * 宏定义的对象也放在头文件里，其构造函数的初始化优先级比类内构造函数更高：所有变量对象在进入构造函数之前就已全部创建。

    * 因此参数会有一个默认值；某个类想改默认值，不必动宏，直接在构造函数里改即可——默认值统一给、个别类单独覆盖，两层互不干扰。

## 时间轴：播放、重置与三个虚函数

### 仿真的时间维度

* **与 CAD 软件的分野**

    * 仿真是一个时间序列：点播放之后，场景里所有元素会动起来。

    * 除场景连接关系、各种参数与属性之外，还有两样东西：动态的数据传递（数据流过程）与计算模块的执行顺序；界面上的运行逻辑也要跟 C++ 的执行逻辑对上。

* **播放与重置**

    * 播放是一个三角形按钮，从头开始，一个时间步一个时间步往前运动。

    * 重置把所有状态变量恢复到初始状态。

    * 重置不是摆设：场景跑起来后发现出水口位置不好，调完位置必须重置，让所有节点的数据回到初始状态、整个流程重新开始；不重置则上一轮算到一半的粒子状态还在，接着往下跑看到的不是新参数下的完整过程。

### 三个虚函数的切分

* **三个函数**

    * `update_states`：每个时间步更新状态。

    * `pre_update_states`：更新之前做的处理。

    * `post_update_states`：更新之后做的处理。

    * 实现子类时重载这几个函数，用它们完成自定义状态的更新；它们与重置一样都是虚函数。

* **为什么不是一个**

    * 正常来说一个 `update_states` 就够了；设计成三个是为了照顾耦合场景。

    * 耦合场景除仿真流程本身的计算外，还有数据预处理与相应的后处理；这些处理无法标准化、流程化，与具体耦合方式绑定，每个耦合节点干的事都不一样，硬塞进标准更新流程不合适。

    * 流固耦合节点就按这个模式：流体与表面网格的数据先经它自己的处理，再进入更新，最后做收尾。

* **两个额外函数的代价**

    * 无论重置还是更新，代价都比较大——它会调用各种模块，所有状态都会重新更新一遍。

    * 只想更新局部内容时，不必点重置改所有数据，用回调机制做轻量级、针对个别数据的更新。

## 回调机制

### 回调的原理与收益

* **回调（Callback）**

    * 做法：把需要执行的操作封装成对象，把它的函数指针存到主程序里；主程序触发某个事件之后，直接调用这个回调函数完成特定功能。

    * 因此主程序不需要知道那段代码具体干什么，它只知道"这件事发生的时候，叫一下这个函数"。

* **两个收益**

    * 省开销：渲染与仿真长期处于循环状态，其他机制每轮都要判断"你是不是需要处理这个事件"，产生大量冗余开销；回调只在触发的那一瞬间调用。

    * 解耦：把调用者与被调用者分离，被调用者自定义它想处理的行为。

* **适配的事件形态**

    * 粒子撞上障碍物、布料碰到边界这类事件在整场仿真里非常偶然，不是每帧都触发，正适合回调：平时什么都不做，真发生了再交给回调处理。

### field 上的回调列表

* **field 的双重角色**

    * > **定义**：field 是节点上的一个控制变量槽，既装值，也装"值变了该通知谁"；回调列表就挂在它身上。

    * 一个节点往往挂很多控制变量，某个控制变量一变，节点内部的一份数据就要跟着更新；需要响应就把回调函数塞进那个 field 的回调列表。

* **两类触发时机**

    * 数据被改动之后。

    * 它连接的拓扑关系变化之后。

    * 这两类变化一来，回调函数被逐个调起来，执行用户想要的行为。

* **回调改的是派生数据**

    * 回调不改 field 里的那个值，它改的是值背后的东西——节点内部由这个值派生出来的数据。

### 两种写法

* **成员函数回调**

    * cube 的缩放、旋转、平移一变，内部的表面网格与立方体自己的一堆信息就得重新算一遍。

    * 做法：用 `std::bind` 把成员函数和节点指针绑在一起生成回调，再通过 `attach` 把它挂到每一个需要响应的控制变量上。

    * 挂到哪些 field 由函数需要哪些参数决定：cube 那个函数五个参数全都要，就把这一个回调同时塞进五个 field，之后任意一个变化都会把它调起来。

* **lambda 回调**

    * 典型场景是静态版网格加载：打开一个文件，把内容载进来，再对几何拓扑对象做初始化。

    * 写法 `[=]`，方括号里放等号表示外层现有的值都可以捕获进来；把这个 lambda 作为参数传给回调，里面就能直接引用类里的各种对象。

* **两种写法的分工**

    * 成员函数回调要绑定节点指针，天然能访问该节点的内部状态。

    * lambda 用捕获列表把需要的东西带进来，写起来更自由，适合一次性的局部操作。

### 三个典型用法

* **控制可见性**

    * 球转成有向距离场（Signed Distance Field，SDF）：上游球节点自带可视化模块，下游节点接收三角网格、构建距离场，再抽成表面网格显示；两个显示叠在一起互相遮挡。

    * 在 volume 库的 volume generator 类里写回调，监听"有没有三角面片输进来"；一旦有输入，顺着这个 field 找到挂在它上面的节点，关闭其渲染模块。

    * 效果：连上之后上游节点直接隐藏，场景只剩下游从距离场重构出来的表面网格。

* **核函数归一化收口**

    * SPH 计算某点的物理量本质是权重求和：每个粒子带一个值，乘权重函数再加起来，硬性限制是整个权重加起来必须等于 1。

    * 就地重新归一化能用，但权重函数在很多代码里都会实现、各处未必一致，对不上就出问题；更好的做法是在一处统一归一化，后面都拿这份结果。

    * 由粒子系统里负责权重求和的核近似对应的类承担；归一化要算一个缩放因子，由三个参数决定：核函数的作用范围、采样间距、核函数的类型。

    * 核函数类型五花八门，必须作为参数传进来、不能写死；把同一个成员函数分别 `attach` 到这三个 field 上，谁的值变了就重算缩放因子。

* **Qt 属性面板联动**

    * 现象：选中物体后拖动它身上的坐标架（三个箭头），属性页里的位置、旋转、缩放全都跟着变。

    * 三样东西：坐标架移动后设置对应 field 的值；field 值更新后要让 Qt 收到"数据变了"并刷新属性控件；Qt 的属性控件（三维向量、整型、浮点型标签）自带回调，由界面框架建好后传给对应 field，field 一变就调用它。

    * 数据单向流：三维视图中的操作 → field → Qt 回调 → 属性面板刷新。

    * Qt 与底层框架是两套系统，把 Qt 相关的功能与函数传进底层框架、由底层触发回调，就能在界面层面完成对接。

## 插件体系

### 插件的构成与动机

* **插件（Plugin）**

    * 对 C++ 来说拆开看主要两样：一个整体的框架，加一堆 dll。

    * 解决的问题很朴素：把复杂系统拆成基本的、类似积木块的东西，再用积木块拼回复杂系统。

* **非拆不可的理由**

    * 代码量上去之后，每改一处都要在整个系统里重新编译一遍，开发成本相当大；拆成插件把耦合度降下来。

    * 适合协同开发：不同研发人员各做一部分，最后整合到整个应用框架里。

* **框架侧与插件侧**

    * 框架层面在 framework 里，有一个插件管理器（PluginManager）管理每一个 plugin，对应的是一张 plugin 列表。

    * 开发者从插件提供的入口基类 Entry 继承，开发各种插件：刚体动力学、粒子系统、SDF、Volume 等。

    * 两边唯一的契约是 Entry 基类：管理器只管"有哪些插件"，插件自己负责"提供哪些节点和功能"。

```text
Framework
  ├── PluginManager
  │     └── PluginList: [ plugin A ][ plugin B ][ plugin C ] ...
  └── Plugin（对象层）
        └── Entry（基类，插件入口）
              ├── 刚体动力学插件
              ├── 粒子系统插件
              ├── SDF / Volume 插件
              └── 其它自研插件
```

### 插件骨架

* **两个加载接口**

    * 每一个 plugin 都提供两个接口：一个对应静态库加载，一个对应动态库加载。

* **初始化要做的事**

    * 从插件入口的 Entry 类继承一个子类。

    * 在子类里实现一个静态的 `instance` 函数，负责创建出一个静态的插件对象。

    * 如果插件带 UI，还要重载初始化工具架的函数（`initialize…Action` 一类），在里面实现想要的按钮。

* **initialize 头文件**

    * 每个库的目录里都有一个 `initialize` 开头的头文件，内容就是初始化这个插件的那一个类，加上两个 API 接口：`instance` 函数与初始化工具架的函数。

    * 插件能带什么，全在这一个头文件里交代清楚。

### 工具架与加载时机

* **工具架按钮**

    * 每个按钮挂一个 lambda，作用是创建一个对象；点按钮与在节点编辑器里右键创建一个对象是一回事。

    * 固化成按钮的价值在于顺手做额外操作：创建发射器时可以用边框渲染模块把它的外轮廓显示出来，右键创建做不到这一层。

    * 插件加载之后，它对应工具架里的按钮会自动创建出来，不需要手动摆。

* **静态加载与动态加载**

    * 静态加载：在 `main` 函数里显式调用一下它的初始化函数，把插件加载进来。

    * 动态加载：把库拷进插件目录即可。

    * 空工程验证：工程里几乎不加载仿真相关算法，打开只有渲染的默认内容，仿真选项卡一个都没有；把粒子系统的动态库拷进插件目录再跑，相关功能与选项卡就加载进 GUI，可以创建对象、搭出类似场景。

    * 自研的库或算法也以同样形式导入框架，导入后能与其他算法模块、插件配合；框架不需要认识算法，只认插件接口。

### 界面层面的扩展

* **标题栏与变量显示名**

    * 有些基本数据类型不需要显示标题栏，重载每个节点或每个模块的 `captionVisible` 函数控制其显示与隐藏。

    * 变量默认名与代码里定义的名字一致，便于在代码里找到它；到最终应用阶段这个名字不直观，可用 `setSlotName` 改成中文等更直观的显示名。

    * 不只是变量名，标题栏、描述信息、节点类型统统可以定制。

* **端口形状**

    * 小圆点端口对应基本数据类型：控制变量、一维数组、二维数组等。

    * 钻石型端口对应一个节点。

    * 为什么需要钻石型：做耦合时一个对象依赖的数据非常多（位置、速度、密度等全都要连），一根根连界面会非常混乱。

    * 把整个节点作为一个整体传进去就算完成接入，图上只出现一根连线，节点内部的状态变量不再摊开画。

```text
 圆点端口        钻石端口
   o               <>
   |               |
 标量/数组       整个节点（含其全部状态）
```

## 七个设计原则

### 原则清单与适用对象

* **七条原则**

    * 单一职责、开闭、迪米特法则、接口隔离、依赖倒转、里氏替换、合成复用。

    * 抽象地看这些原则名称很难理解其具体所指，需要落到具体代码情形逐条对应。

* **适用对象**

    * 只是这套代码的使用者，怎么写都无所谓，自己看着舒服就行。

    * 希望成为开源软件的贡献者，代码就需要符合一定的约束。

### 单一职责与开闭

* **一个类只负责一项职责**

    * 目的很直白：把这个类的复杂度压下去。

    * 反例：输入一张三角网格、创建出体（SDF）的那个类多了一个控制变量，用于测试时让 SDF 沿着某个速度、某个方向不停运动；这个类的初衷只有一件事——输入三角网格、输出它的有向距离场，让它自己动起来属于另一件事。

    * 更合理的做法是把运动移到外面：在外部驱动这张三角网格运动，网格动完之后再更新它新生成的 SDF，每段只干自己的事。

    * > **易错点**：功能"能跑"和职责"干净"是两回事；测试用的便利代码一旦留在生产类里，后面每个读这个类的人都要多想一层"它为什么自己会动"。

* **对扩展开放，对修改关闭**

    * 一个类暴露出来的东西是有区分的：实现人员本来就该允许改，别的类作为使用者则不该看到内部细节。

    * 判断方式：凡是只在类内部使用的数据、函数，就该封装起来、不暴露到外面；对外看这类函数是关闭的，这就是"对修改关闭"的那一半。

    * 实例：类里初始化内部自用参数的函数，设成 public 语法上成立，但使用者根本不清楚它干什么、也没有理由调它，按原则就不该允许外部直接调用。

### 迪米特与接口隔离

* **最少了解、最少依赖**

    * 一个对象对别的对象应保持最少的了解，也不应该依赖自己用不到的接口。

    * node 对 state 的依赖要尽可能少：描述一个立方体可以定义三条边，也可以定义边与边的乘积，都能描述；最好的状态是状态恰好是描述这个 box 的最小集合，冗余变量根本不该出现。

    * model 对控制变量的依赖、对输入接口的依赖，也要按这个尺度收。

* **接口的宽严**

    * 输入接口冗余，会出现有些模块明明用不到某个接口却还是得带着它；缺了接口，后面整个模块可能直接没法执行。

    * 变化的容忍度不同：输出改了相对还好，输入一般不能轻易动。

    * > **注意**：接口是别人依赖你的那部分契约；删掉一个用不到的接口是清理，改掉一个别人正在用的输入接口是破坏。

### 依赖倒转与里氏替换

* **依赖抽象**

    * 高层模块不应该依赖底层的具体模块。

    * 底层拓扑是层次化的：点 → 边 → 三角面片 → 四边形网格 / 四面体网格，越往下越具体，上层是下层的父类。

    * 三角面片一旦作为某个模块的输入类型，从它继承下来的四边形网格、六面体网格、四面体网格理论上都应该能输入；界面里现在的设计允许这样做。

* **子类必须能顶替父类**

    * 里氏替换：输入的是子类对象，结果也必须正确，与输入父类对象完全一致、互不影响。

    * 程序里有一层接口判断：所有子类放行，不是子类或别的类型就不允许输入。

    * 实例对照：cube 可以输出三角网格与四边形网格，两者都能传进三角面片输入口；粒子采样器输出的是一堆粒子，粒子比三角面片更靠上、是它的父类，这种就不允许。

    * > **易错点**：方向别弄反——子类对象可以当父类用，反过来不行；把父类对象塞进要求子类的输入口，是在赌它的额外信息存在，而它并不存在。

### 合成复用

* **能组合就别继承**

    * 核心意思一句：能复用的地方尽可能不要用继承。

    * 例：刚体系统里查找邻域的那一块本质是做碰撞检测，依赖两个东西——拓扑结构与碰撞检测的类；让这个类同时从两者继承理论上没问题，但多重继承让整个软件系统的维护代价变得非常大。

    * 结论：需要用到别的模块时，能用组合就用组合，不要用派生、继承那套操作。

    * > **提示**：继承表达"是一种"，组合表达"有一个"；邻域查找"有一个"拓扑结构、用一套碰撞检测逻辑，它并不是拓扑结构的一种，所以本来就该是组合。

* **少用多继承**

    * 一个子类同时继承多个父类，越往下派生，这个子类越复杂、越不容易维护，这是实际研发里经常踩到的地方。

## SDF 建模与边界节点复用

### 建模与流体接入

* **从几何体到实体**

    * 链路：cube 加 sphere → 布尔运算（并）→ 融合后的表面网格 → 体网格生成器 → 实体（SDF）→ 作为边界输入 → 流体边界节点。

    * 第一步创建两个标准几何体，球调小一点，形成"方块上鼓出一个球"的形状，用来做基于实体的融合操作。

    * 体网格生成器输入三角网格；体网格分辨率要改，不改的话分辨率太大，创建出来的质量不太好。

    * 两个体网格都生成后接布尔操作节点，可做相交、相并、相差；接上后点重置、关掉前面两个的显示，才能看到融合后的形状。

* **基本要素**

    * 发射器后接流体求解器，把发射器创建出来的粒子输入求解器。

    * 发射器位置要调：它现在在实体内部，得挪到外面，才是从外面发射粒子、让粒子与物体边界产生作用。

    * volume 选项卡里的流体边界节点吃两样：一个流体，一个实体模型；接上整个场景就搭完。

* **运行结果**

    * 流体撞到边界之后被约束住，运动方向随之改变；因为形状是融合后的形状，流体会沿着这个形状的表面走。

    * > **提示**：边界节点要的只是"一个流体加一个实体"两类输入，实体具体是什么形状由上游节点决定，边界这一层不需要知道。

### 布料复用同一节点

* **换一套求解**

    * 实体模型完全不动，把流体相关的节点删掉。

    * 布料同样要先有布料求解器，它也需要输入一张三角网格：创建一个平面并调分段数——默认平面只有两个三角面片，分段数调上去之后有一系列四边形，最终转成三角形。

    * 这层四边形结构本身是三角面片的子类，所以可以直接作为输入喂给布料求解器，完成初始化。

* **约束与运行**

    * 布料数据起来后，还要输入到流体边界节点里的三角网格系统，作用是在运动过程中约束这块布料的行为。

    * 把初始物体关掉、重置，布料的数据结构就生成出来，顶点和边都能看到；点开始后布料碰到障碍物发生形变。

    * > **提示**：流体与布料用的是同一个边界节点，只是喂进去的东西不同——流体吃"流体加实体"，布料吃"三角网格"；同一个节点复用两次，靠的是输入类型够宽，类型对得上它都接。

## Vulkan 的出身与代际优势

### 提出与目标

* **时间线**

    * 2015 年在 GDC 上被提出，2016 年正式发布。

    * 上一代主流是 OpenGL。

* **设计初衷**

    * 把渲染与仿真（计算）这两个任务整合到一起，用一个通用的 API 同时解决。

    * 提出时被誉为「OpenGL Next」，即下一代图形接口，目标是替换 OpenGL、成为新一代图形接口标准。

    * 替换会是一个漫长的、逐步进行的过程，取决于 Vulkan 能把 OpenGL 的老问题解决到什么程度，以及各种硬件厂商的支持。

### OpenGL 留下的三个问题

* **多线程**

    * OpenGL 在多线程环境下有一堆问题。

* **平台割裂**

    * 移动平台与 PC 平台是两套不通的 API。

* **计算支持弱**

    * OpenGL 主要针对图形渲染，对通用计算的支持比较弱。

### 三条代际优势

* **一套 API 覆盖所有平台**

    * 以前 PC 端叫 OpenGL、移动端叫 OpenGL ES，而 OpenGL ES 是 OpenGL 的一个子集，两套并存，兼容性实际上还是成问题。

    * Vulkan 用一套统一 API 解决所有环境：Android、Windows、Linux 同一套；写一套算法即可无成本迁移到任何平台，发布与跨平台迁移都方便很多。

* **天生为多线程准备**

    * OpenGL、DirectX 在设计时主要针对单核 CPU，那个年代的硬件形态把 API 的骨架定死了。

    * Vulkan 对整个多线程环境比较友好。

* **更靠近硬件**

    * 接口更靠底层，所有 API 的调度开销相对更低，同样任务理论上效率应比 OpenGL 高。

    * 对 GPU 有更直接的掌控能力：能决定的事情更多，要担的责任也更多。

### 偏底层的代价与未定的边界

* **上手成本**

    * 直接用 Vulkan 写各种程序非常麻烦、不方便；图形或仿真计算刚入门的人不适合以 Vulkan 起步，更应该拿 CUDA 作为入门基础。

    * 着色端目前还是 C 风格写法，C++ 的面向对象封装、继承派生支持不了。

* **能力边界不清楚**

    * 渲染领域对 Vulkan 的常识已经比较多，也发现它有不少占优势的地方；但仿真计算领域用 Vulkan 做的其实不太多，它到底能做什么、做到什么程度没有定论。

    * 相关实践还处在探索过程里，不是成熟解决方案；Vulkan 本身开源，后面会不断完善。

## GPU 编程接口的家族谱

### 两条目的与第一代

* **目的只有两个**

    * GPU 的 API 不少，目的说起来就两个：不是为了做渲染，就是为了做计算（仿真）。

    * Vulkan 特殊一点，渲染与计算兼顾；整个家族的演进伴随 GPU 本身的发展。

* **固定管线的 OpenGL**

    * 1992 年提出，当时显卡刚出现，针对游戏与各种三维场景做固定的管线功能，最初主要用 C 写。

    * 早期不具备可编程管线：整个流程每一步做什么都是固定的，只能在给定位置塞数据，改变不了它怎么算。

### 着色器与移动端

* **DirectX 与 HLSL**

    * 微软独立发展出 DirectX，在 Windows 95 里引入，借助 Windows 的覆盖面形成一套独立标准，与 OpenGL 平行发展。

    * DirectX 9 引入 HLSL（高阶着色语言），顶点着色器、片元着色器等特定阶段可以由用户设计行为。

* **OpenGL ES 与 GLSL**

    * 2003 年前后移动设备层出不穷，手机 GPU 性能较弱但同样要图形能力，于是发展出 OpenGL ES——OpenGL 的一个子集，专门做移动设备上的图形渲染。

    * 移动端同样需要着色阶段可编程，OpenGL 引入了自己的着色语言 GLSL；GLSL 与 HLSL 语法很像、很多相通，但维护主体不同：OpenGL 这一套由 Khronos Group 维护，DirectX 那一套由微软维护，语言迭代方向就此分开。

### 通用计算的分水岭

* **CUDA 重新定义 GPU**

    * 2007 年由英伟达提出，是里程碑式的节点：GPU 不是单纯用来做渲染的，它完全可以做任何与渲染无关的通用仿真计算。

    * 今天各种 AI 训练本质上都建立在"GPU 是通用计算设备"这个前提上；此后学术界与产业界都发生了很大变化。

    * 早期版本（2008 年那会儿）只支持 C，后来才逐步加入 C++，具体版本号长文未说明；所依据的标准不断更新，C++17 之类的新特性不断加进来。

* **此前的 GPU 计算尝试**

    * 2007 年之前图形 API 主要以渲染为主，也有过用特定 shader 做模拟的尝试（2004 年有三维流体模拟）。

    * 但早期配套工具、调试工具缺失，用 GPU 的 API 写一个比较复杂的仿真算法，代价相当大。

* **开放标准的缺位**

    * CUDA 是英伟达的护城河，对整个行业来说一套开放的行业标准是缺失的。

### 之后的四条线

* **OpenCL**

    * 2009 年提出，专门针对通用并行计算，算是一个通用计算标准；最早由 Apple 发起，后来由 Khronos Group 维护。

    * 很多特性跟 CUDA 比较像，唯一不一样的地方是它不做混合编译——shader 与后续代码是分离的；同样支持 C 与 C++。

    * 从用户角度看，OpenCL 的用户群体远远少于 CUDA。

* **Metal**

    * Apple 在 2014 年开始发展，同样想把图形与计算两个 API 融合成一个统一的图形接口。

    * 与 DirectX 一样主要只针对自家平台（Mac 等苹果系统），跨平台能力相对不足。

* **Vulkan**

    * 2016 年发布，目标还是同一个：把渲染与计算打通，用一个统一 API 处理。

    * 最早由 AMD 发起，后来由 Khronos Group 维护。

    * 比 OpenGL、OpenCL 更底层，会把很多 GPU 硬件特性直接暴露出来：运用得当性能可以更高，坏处是对编程的人要求很高、编程复杂度大幅提升。

## 后端选型：CUDA、OpenCL 与 Vulkan

### 混合编译

* **定义与差异**

    * 混合编译指设备端（GPU 端）代码与主机端（用 C++ 写的部分）是否放在一起编译。

    * CUDA 支持：在一个 `.cu` 后缀的文件里可以同时写 C++ 代码和 kernel 代码，nvcc 负责把里面不同的代码拆开，这需要编译器层面协助。

    * 好处是编码复杂度大幅降低，研发算法的效率跟着上来。

* **不支持的代价**

    * OpenCL 与 Vulkan 目前不支持。

    * 主机代码里定义了一个数据结构，设备端代码里还得再维护一份，而且必须保证两边结构完全一致，维护有成本。

### 调试、跨平台与语言标准

* **调试工具**

    * 仿真算法逻辑复杂，需要各种调试工具支撑，比如中间某一步算完要能看输出结果对不对。

    * 三家都支持，只是用 CUDA 会更好用一些。

* **跨平台能力**

    * CUDA 完全依赖英伟达显卡：用 AMD 显卡或移动端设备很可能根本没有可用的 N 卡，已有的 CUDA 代码不能直接用。

    * OpenCL 相对好一些，严格来说 Vulkan 最好——支持的平台从 PC 端到移动端，兼容性更广。

    * 但性能与代码复杂度有时很难折中；跨平台兼容做得好，不代表不同平台适配时没有差异，依然有一份额外工作量。

* **语言标准与封装**

    * CUDA 与 OpenCL 现在主要是 C 和 C++。

    * C++ 重要在封装：仿真单纯用 C 写也可以，但不依赖任何封装特性，整个代码复杂度会极高。

    * 另一块是模板：不希望类似的代码写好多份、维护成本很高，有模板就能统一维护一份；Vulkan 目前不支持模板。

    * Vulkan 不支持 C++ 的这些特性，很多代码需要退化到 C 的一些规范上。

### 对比与结论

* **四个维度的并排对照**

    * 混合编译、调试工具、跨平台、C++ 封装与模板四条并排看，三家差别很清楚。

| 维度 | CUDA | OpenCL | Vulkan |
| :--- | :--- | :--- | :--- |
| 混合编译 | 支持，`.cu` 里主机代码与 kernel 同文件，由 nvcc 拆分 | 不支持，主机端与设备端代码分离 | 不支持 |
| 调试工具 | 支持，最好用 | 支持 | 支持 |
| 跨平台 | 完全依赖 NVIDIA 显卡 | 较好 | 最好，PC 到移动端 |
| C++ 封装与模板 | 支持 | 支持 | 不支持，设备端退化为 C 风格 |

* **研究场景优先 CUDA**

    * 只做特定研究、写特定算法，用 CUDA 可能是最方便的。

* **跨平台场景转 Vulkan**

    * 一旦要考虑移动端或跨平台，CUDA 解决不了，可转向 Vulkan，对特定算法做一次重构，生成一份能兼容各平台的仿真算法。

## 原生 Vulkan 的对象链与执行链

### 数组相加的难度落差

* **任务与落差**

    * 任务是两个数组 a、b 相加，结果存到数组 c。

    * 用 CUDA 写很简单，完全没接触过 GPU 的初学者花几个小时也能写出来。

    * 换成 Vulkan 就"一言难尽"，一个完全的初学者仅实现这个功能，估计得花很久。

* **复杂度来源**

    * Vulkan 更偏底层，很多硬件特性直接暴露在外面。

    * CUDA 之所以好写，本质是编译器层面替你做了很多简化；Vulkan 的编译器能力相对较弱，很多执行流程需要自己指定。

### 对象链

* **从应用到队列**

    * 最顶层是一个 application，往下进入一长串对象。

    * 创建 instance：针对不同任务可以创建多个 instance，application 与 instance 是一对多。

    * 选择物理设备（physical device）：一台电脑或移动设备上可能有多张显卡，要选定真实存在的那一块来执行任务。

    * 逻辑设备（logical device）：真正执行计算的地方，里面有对应的队列。

* **三种队列**

    * 图形队列（graphics）与计算队列（compute）：对应渲染与计算两类任务。

    * transfer 队列：主要针对数据拷贝，比如两个数组之间把数据拷来拷去。

    * 图形队列与计算队列实际上也都可以同时完成 transfer 的拷贝，不必为了拷一份数据特意去排 transfer 队列。

```text
application
    │ 一个 application 可对应多个 instance
    ▼
instance
    ▼
physical device          真实的那张显卡
    ▼
logical device           真正执行计算的地方
    ├── graphics queue
    ├── compute queue
    └── transfer queue
```

### 命令录制与资源描述

* **命令池与命令缓冲区**

    * 要执行一个计算管线（pipeline），首先分配一个命令池（command pool），池子里会有很多命令缓冲区（command buffer）。

    * 在 command buffer 上记录到底要执行哪些命令，计算管线依赖这些 command buffer 完成整个过程。

* **资源与参数都要显式交代**

    * 管线需要输入各种数据：输入一个 buffer 或一个变量时，还要额外指定这个 buffer 到底是什么类型、多大。

    * GPU 上创建的 global memory、local memory 创建之后要指定它代表什么类型，描述符指定清楚，才能传给计算 API 执行。

* **与 CUDA 的默认值差异**

    * CUDA 里很多东西是隐藏的：不选 device 默认给你选 0 号；完全不管其他部分、单独执行一个 kernel，有一堆默认操作替你兜着。

    * Vulkan 很多地方需要显式把每一部分都指定出来，每一步指定清楚才能真正执行。

### 完整链条

* **从 instance 到提交**

    * 整条链自上而下，每一级对象都要自己创建、每一处参数都要自己指定。

```text
instance
  ↓
physical device（选一张卡）
  ↓
logical device + queue（建好三种队列）
  ↓
分配 GPU 内存：buffer / global memory / local memory
  ↓
写 kernel → 编译成 SPIR-V
  ↓
descriptor set 描述参数
  ↓
pipeline + command buffer（逐条记录命令）
  ↓
提交到队列执行
```

* **复杂度不在算法**

    * 两个数组相加实际包含很多步骤；原生 Vulkan 的复杂度不在算法本身，而在必须亲手把这条链条一级一级搭出来。

    * buffer 的数量可以很多，创建完之后、真正执行之前，怎么把它们组织清楚、怎么让 GPU 知道每一块该拿去干什么，又是一轮新的交代。

    * 一处不指定，它就什么都不替你猜。

### kernel 与 SPIR-V

* **kernel 要交代的三件事**

    * 指定输入参数：三个 buffer（a、b、c）外加一个变量，告诉程序数组里一共有多少个元素。

    * 指定 block 大小：GPU 上的执行以 block 为单位。

    * 写入口函数：所有 shader 的入口都是一个叫 `main` 的函数。

    * 函数体跟 CUDA 很像：取全局 ID，据此算出自己该处理哪个位置的数据；全局 ID 是三维的，一维数组只要取它的 x 分量定位。

* **SPIR-V**

    * kernel 写完不能直接执行，必须先编译成 SPIR-V 中间文件。

    * > **定义**：SPIR-V 是编程语言与底层驱动之间的中转站，可以把多种语言都转换成同一种标准的二进制中间文件，再拿到各种 GPU 上执行。

    * 以前各种语言直接跟底层 driver 打交道，语言在变、driver 也在变，两边一变就要做各种适配；有了这一层标准，左右两边都只跟中间层打交道。

### 数据上卡与参数绑定

* **staging buffer**

    * CPU 与 GPU 的数据一般不能直接互访：C/C++ 代码没法直接访问 GPU 上的一块数据，GPU 上的 kernel 也没法直接访问 CPU 的内存空间。

    * CUDA 有拷贝函数可以一次到位；Vulkan 所有数据都要经过一块 staging buffer（中转存储区）中转，它对 CPU 和 GPU 都可见。

    * 做法：CPU 分配一块空间、先映射（map）到 staging buffer；staging buffer 对 GPU 也能直接访问但效率较低，最好再拷到 GPU 的 local memory，kernel 访问就会快得多。

    * 跳过第二段、让 kernel 直接读 staging buffer 也能跑，但那是绕远路。

```text
CPU 内存
   │ map
   ▼
staging buffer          CPU 与 GPU 都可见，用于中转
   │ copy
   ▼
GPU local memory        kernel 直接访问，速度更快
   ▼
compute kernel
```

* **descriptor set**

    * shader 只知道自己有几个参数，不知道这些参数落在显存的哪一块；执行前必须告诉 pipeline 这次需要哪些 buffer。

    * > **定义**：descriptor set 是一份参数清单，逐条写清楚某个 kernel 的第几个参数指向哪块 buffer、是什么类型、数据多大；一个 kernel 要 n 个参数，就有 n 条描述合成一个 set。

    * 计算管线由两部分构成：layout 是输入参数的描述（"要什么"），已写好的 shader 编译成二进制之后是一段 SPIR-V 的 code（"算什么"），缺一不可。

    * buffer 是一堆、pipeline 也是一堆，彼此多对多：同一块 buffer 可以被多个 pipeline 使用，同一个 pipeline 在不同时刻也可以配不同的 buffer。

### command buffer 与提交

* **记录的四个类别**

    * 描述符：这次输入哪些参数。

    * pipeline：这次需要哪个计算，把它绑定进来。

    * 常量：一些需要随命令一起带进去的常量。

    * dispatch：block size 到底是多大、总共分成多少个组。

    * 四类合起来构成一个 command buffer；一次执行等于把参数装配、计算流程、执行都装进去。

* **提交**

    * > **易错点**：command buffer 只是"准备"，不是"执行"；录完之后不提交，它什么都不会发生，最后一步 submit 才会把里面记录的所有命令实际执行一遍。

    * 到这里完整流程走完：描述符描述参数，pipeline 提供计算，command buffer 把两者装配成一条条命令，提交之后由 GPU 执行。

### 渲染管线长、计算管线短

* **两条管线的形态**

    * 渲染这部分的步骤非常多：固定功能阶段与可编程 stage 交替多轮；可变的 stage 跟计算很像，都允许自己实现自定义函数。

    * 计算管线只有一块可编程阶段，很短。

```text
渲染管线（长）
  固定功能阶段
      ↓
  可编程阶段
      ↓
  固定功能阶段
      ↓
  ……（如此交替多轮）
      ↓
  固定功能阶段

计算管线（短）
  可编程阶段（只有一块）
```

* **短不等于简单**

    * > **易错点**：看到渲染这么复杂、计算只有一块，就以为计算简单得多；实际正好相反。

    * 渲染流程长是因为把很多数据标准化了：顶点需要哪些数据、需不需要索引、顶点位置与其他属性都有一套标准，按标准准备数据即可。

    * 计算面向通用任务，没法预见数据结构长什么样，刚体、流体的数据结构五花八门，管线对数据规范其实没有约束；能否适应各种数据接口没有定论。

    * 简单独立 shader 没问题，但复杂物理仿真系统不同模块需要交互，数据标准不统一各模块就没法协同——这正是需要靠约束把复杂算法耦合起来的原因。

## 封装体系：VkSystem、VkContext 与 VkProgram

### 封装的三条主线

* **对象**

    * Vulkan 对象比较多，要做一定的分类与封装，把跟仿真算法无关的细节隐藏起来。

    * 写算法的人不应该关心 instance 怎么建、设备怎么选。

* **调用**

    * 实际仿真涉及的 kernel 五花八门，每个 kernel 的参数组合都不一样。

    * 需要想办法简化整个 kernel 调用的方式。

* **数据**

    * 对访问数据不做任何约束，不同 kernel 之间的数据协同会非常困难。

    * 要在数据层面做统一的封装，让各种仿真任务共用同一套描述。

### 类的分层

* **三个盒子**

    * `VkSystem`：整个 Vulkan 底层被抽象成这个类，管跟设备打交道的、一次性的活——创建 instance、选取 physical device。

    * `VkContext`：逻辑设备以及它的各种 queue 统一交给它管理；设备这一层的状态收在一处，后面所有对象都从这里取，不会散得到处都是。

    * `VkProgram`：跟 CUDA 的 kernel 函数对标；CUDA 里写一个 GPU 可执行的 kernel，Vulkan 里等效地写一个 VkProgram。

    * `VkVariable`：数据三类的统一父类。

```text
VkSystem
├── Instance 的创建、Physical Device 的选取
├── VkContext
│     └── Logical Device + 各类 Queue
└── VkProgram
      ├── VkDeviceBuffer   大块显存缓冲
      ├── VkUniform        易变、规模小的数据
      └── VkConstant       长期不变的常量（如重力）

VkVariable：上面三类的统一父类
```

* **三类数据的划分**

    * 划分依据不是数据类型，而是"变化的频率和体量"：大块且频繁读写走 buffer，小而易变走 uniform，长期不变走 constant。

    * > **提示**：选错类别不会报错，但会带来不必要的传输开销。

| 类型 | 用途 | 典型场景 |
| :--- | :--- | :--- |
| `VkDeviceBuffer` | 分配一块大的缓存 | 粒子位置、速度这类成规模的数组 |
| `VkUniform` | 易变但规模小的数据 | 几个参数打包后传到 GPU |
| `VkConstant` | 固定或不常变的数据 | 重力这类常量 |

### 从 CUDA kernel 到 VkProgram

* **CUDA 侧两步**

    * 声明：函数前面加 `__global__` 标识符，所有 CUDA 的全局函数都需要这个。

    * 标明输入：比如三个数组 a、b、c 及它们分别对应什么类型；函数体就是 a 加 b 放到 c 里，调用时有特定语法。

    * 两步，声明加调用，中间没有别的东西要准备。

* **Vulkan 侧三件事**

    * 声明：声明一个函数，写明需要哪些形参，比如三个 float 数组 a、b、c，再告诉 kernel 数组长度（可以做成 constant）；形参是用一组宏定义出来的，不是普通 C++ 的函数签名。

    * 载入：Vulkan 的 shader 代码与 host 代码分离，声明之后还要把 shader 编译出的 SPIR-V 文件载入进来，载入完成声明过程才算结束。

    * 调用：有一个比较快捷的方式，一次调用就把执行也带上；告诉 GPU block size（示例是 128），以及总数量 n 要分成多少个 group；声明了几个数组就传几个。

* **形参的统一**

    * 底层 constant 对应 `VkConstant` 结构，uniform 对应 `VkUniform` 结构。

    * 二维高度场、三维欧拉网格这类数据还需要额外的数据结构支持。

    * 流体里的邻域列表不是一个 buffer，可能需要几块 buffer 组合起来统一定义结构；可以定义宏，但 Vulkan 与 C++ 不是混编关系，调用没那么方便，还在尝试更简单的处理。

### 三种运行模式

* **即时模式**

    * 快捷调用内部其实是两个过程：先创建 command buffer，再提交到 queue 执行，一个调用把准备与执行都包含。

    * 问题在于每次都会把实参重新更新一遍，这个动作有开销；仿真算法经常循环很多次，每次都重写一遍，存在大量重复的逻辑计算，白白烧掉时间。

* **缓存模式**

    * 记录 command buffer 时只记录一次，真正执行时重复利用已经记录下来的形参数据，降低整个执行的代价。

    * > **提示**：两种模式的分界是"参数变不变"——参数每帧都变，即时模式省心；参数在循环里固定，缓存模式才划算；缓存的代价是必须保证录制之后形参指向的 buffer 没有被换掉。

* **`VkMultiProgram`**

    * 仿真任务里的计算往往不是单个 kernel：比如弹性体求解可能分为好几个 kernel，要交替执行。

    * 它把不同的 kernel 组合到一起，把不同 program 的执行命令记录进同一个 command buffer；写的时候只写一次，同时把各种命令组合到一起。

    * 比如调用时要循环十次、每次创建一个 dispatch 命令，整个组合进一个 command buffer 之后统一执行。

    * 解决的病根相同：多个 kernel 不断来回切换 command buffer 会导致性能低下。

### 数组相加的闭环

* **三步走**

    * 所有程序进来必须有一个 `VkSystem`、有 instance 并初始化；physical device 的选取、逻辑设备的生成都不用自己写。

    * 创建所有 buffer：接口跟 CUDA 后端一样，一个用来分配 CPU 上的内存，另一个走 Vulkan 后端直接在 GPU 上开辟一块；用起来不必像原生那样麻烦，可以直接把数据放进去——内部实现也用了 staging buffer，只是细节被隐藏。

    * 声明 kernel、标明形参、载入 SPIR-V、执行；计算完把数据拷回来输出。

* **验证与对照**

    * 初始化数据是 0、1、2、3、4……这样线性排下来的，直接运行会打出 0、2、4、6、8，正好验证整个计算正确。

    * 与原生 API 的样例对照：那边差不多三百多行代码，依赖封装之后代码复杂度被极大压缩。

    * > **结论**：Vulkan 的复杂度主要不在 shader，而在 host 端那套装配流程——建对象、分内存、配描述符、录命令；谁的封装把这套流程收掉，谁就把研发成本降下来。

## 后端解耦与中间层

### 解耦动机

* **两个后端与一个目标**

    * 引擎里实际上有两个后端：CUDA 与 ROCm。

    * 希望整个框架跟后端无关：不管接入什么后端，上层的蓝图系统都能直接拿起来用。

* **架构调整**

    * framework 定义的是引擎架构，所以把跟 GPU 相关的所有后端内容都从里面摘出来，放到 core 或者 topology 里。

    * 这样整个架构跟底层彻底解耦：后面拓展算法、增加新的后端数据结构，完全不影响引擎框架的调整。

### 计算侧的中间层

* **接口对齐**

    * GPU 后端的接口要跟计算后端统一起来，因为框架要能对接靠的是接口一致。

    * 框架识别的是 Field，里面包含很多类（变量、数组等）；它并不关注这份数据是用 CUDA 分配的，还是用 Vulkan API 分配的。

* **`VkArray` 与 `GpuBuffer`**

    * 在后端与引擎框架之间引入一个中间层，用中间层屏蔽掉底层细节。

    * 引擎架构这一段看到的是一个 Field，底层是 CUDA 的显存分配、Vulkan 的 buffer 开辟，全部藏在底层，通过 `VkArray` 这个数据结构用统一接口暴露给引擎。

    * 效果：不会出现"新进来一个后端就要不断调整引擎架构"的局面。

```text
        引擎框架（Field：变量、数组，只认接口）
                        ▲
                        │ 统一接口
              VkArray / GpuBuffer
             （中间层，屏蔽硬件细节）
                        ▲
          ┌─────────────┴─────────────┐
   CUDA 显存分配               Vulkan Buffer 开辟
```

### 渲染侧的中间层

* **`GpuBuffer` 的定位**

    * 渲染引擎不直接跟 Vulkan 后端或 CUDA 后端打交道，而是利用 `GpuBuffer` 中间结构，屏蔽掉底层与硬件相关的 API 信息。

* **双向可替换**

    * 好处是双向的：往下可以换底层，往上可以换渲染引擎——想用 VTK、想直接用 Vulkan 写，甚至计算沿用原来的 API、渲染换成 Unreal，都可以统一通过 GpuBuffer 打交道。

### 示例工程验证

* **场景与验证目标**

    * 场景跟用 CUDA 写的是一样的：一个发射器，后面跟一个流体修改器；流体求解器目前只写了积分的模块，其他模块还没加。

    * 运行后从发射器生成粒子，粒子经过求解处理；多创建一个发射器也没问题，可以两个发射器一起生成粒子。

    * 验证的是从后端对接，到跟蓝图、跟整个引擎的对接，流程是通的；解耦带来的好处是可以在完全不改动引擎架构的前提下拓展各种多后端。

* **辅助样例**

    * 点、线、面这些基本渲染模块用的也是 Vulkan 后端，作为想用 Vulkan 写算法的人的参照。

    * > **注意**：这些样例必须选 Vulkan 后端去编译才能生成，否则生成出来的还是 CUDA 的版本，看不到 Vulkan 后端的样例。

    * 还有一些没有开源的样例，用于验证"用 Vulkan 做仿真任务到底能做到什么程度"：刚体、水波、弹性体都尝试过，很多计算任务都能做，只是要看花多少代价完成。

## Vulkan 的硬伤清单

### 内存对齐

* **对齐规则**

    * CUDA 那边编译器应该默认把对齐问题解决掉了；用 Vulkan 写，这个问题需要研发人员自己解决。

    * 例：创建了一个结构，前面几个字段都是 16 字节对齐；后面定义两个字段都是 4 字节，再往后还有一个类型也是 4 字节。不补那块 padding 就会出问题，padding 的主要作用就是对齐。

```text
GPU 端（默认 16 字节对齐）
  偏移 0     前部结构（16 字节）
  偏移 16    字段 1（4 字节）
             字段 2（4 字节）
             c type（4 字节）
             padding（4 字节）     ← 补上这 4 字节，凑满一格
  偏移 32    ────────────────────

CPU 端（紧致排列，省掉 padding）
  偏移 0     前部结构（16 字节）
  偏移 16    字段 1（4 字节）
             字段 2（4 字节）
             c type（4 字节）
  偏移 28    ────────────────────  ← 与 GPU 端错开 4 字节
```

* **后果**

    * GPU 端按 16 字节一格往前推，CPU 端是紧致排列；padding 不填，下一个结构开头的 position 0 就会直接跟到 c type 后头。

    * 把这一整块数据拷到 GPU，两边的偏移对不上，各种数据就会错位。

    * > **易错点**：这类错误编译期不报、运行起来也不崩，表现是数值莫名其妙不对；凡是 CPU 端结构体要整块拷给 GPU 的，都要按 16 字节对齐逐个字段核对偏移，不能指望编译器替你兜住。

### 双份代码与语言能力

* **两套代码**

    * Vulkan 不支持混编，CPU 端与 GPU 端实际上是两套代码。

    * 一个结构体两边内容完全一样，却声明在不同的地方，需要定义两个；后端增加一个数据结构，device 端同样也要加一份。

    * 相互依赖比较多的时候，很容易出错。

    * > **结论**：不支持混合编译的 API，对研发大型复杂系统不太适用。

* **float 原子操作**

    * Vulkan 不支持 float 的原子操作，这对仿真影响非常大：刚体碰撞、欧拉流体都非常关键。

    * 替代办法是排序，用排序也能解决这个问题，但整个研发成本会变得非常高。

* **模板**

    * 不支持模板，很多代码可能得重复写很多遍，维护起来比较费劲。

### 厂商差异与适用边界

* **厂商差异**

    * 不同厂商对 Vulkan 特性的支持五花八门、千差万别。

    * Vulkan 的初衷是解决跨平台，但如果不同芯片、不同厂商支持的标准有差异，虽然只写了一份代码，从 PC 端直接移到移动端也并没有那么容易，很多时候还是要针对不同平台做适配、做优化。

* **结论**

    * > **结论**：Vulkan 目前更适合对个别的 shader、个别的计算步骤做加速；指望它承载整套复杂的仿真系统，代价太高。

## 性能账本与适用边界

### 计算规模与性能拐点

* **与 CUDA thrust 的对比**

    * 因为 Vulkan 更偏底层，拿它跟 CUDA 的 thrust 做比较，发现不同规模下性能表现不太一样。

    * 创建 pipeline、更新描述符这些动作本身都有开销；计算规模比较小的时候，虽然 Vulkan 更贴近硬件，整个计算的效率反而不如 CUDA——那点固定的装配开销摊不掉。

    * 只有规模达到一定程度以上、计算密集度上去之后，Vulkan 更偏底层的特性才让它的效率超过 CUDA。

* **算法类型的影响**

    * 试过 reduction、scan、排序这些算法，基本都是这个结论。

    * 排序相对好一点，这跟算法本身也有关系。

    * > **结论**：总体上看 Vulkan 的性能应该比 CUDA 更优，但它写一个算法的复杂度更高；真正落地要看更需要效率还是更需要开发速度。

### 适用范围与学习路径

* **适用范围**

    * 更适合对个别的 shader、个别计算步骤做加速，不适合承载整套复杂仿真系统。

    * 不少仿真计算任务都能做，关键看花多少代价完成。

* **学习门槛**

    * 这套内容不适合初学者：需要先对仿真、对并行计算有一定了解，才能意识到这里真正需要解决哪些问题；没有那层经验，只会觉得步骤繁琐，抓不住繁琐背后的动因。

    * 入门应该直接用 CUDA，Vulkan 作为扩展去了解——除了 CUDA 之外还有哪些 API 能做仿真相关的事、各自要付什么代价。

## 自研引擎与游戏引擎的分野

* **自研引擎是否必修**

    * 不一定，要看所处阶段：只做研究、目标就是发论文，不一定需要做自研引擎；后面想做更复杂的应用，才可能真的需要。

* **游戏引擎的重心**

    * 这套系统主要针对仿真，游戏引擎跟它差别不小：游戏引擎里涉及的物理其实更简单，重心更多落在物理之外需要考虑的内容上。

    * 游戏里的刚体之类的系统都是简化过的，里面有很多 trick，物理上并没有那么严格。

* **入门要补什么**

    * 最基础的是类似 game 101 这类入门课，加上渲染，编程本身是最基本的。

    * 数学主要看方向：针对游戏开发主要是微积分、线性代数，高数那一套可能也要学；游戏里涉及的物理通常不会那么复杂。

    * 力学方面了解大学物理里比较简单的力学即可，并不需要连续介质力学。

* **开源系统的状态**

    * PeriDyno 是一个开源系统，里面很多东西仍在不断完善，中间某个版本可能会有点小问题，属于逐步完善过程中的正常现象。
