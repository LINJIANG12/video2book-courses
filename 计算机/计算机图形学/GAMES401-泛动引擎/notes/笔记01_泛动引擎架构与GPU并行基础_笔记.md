# 泛动引擎架构与GPU并行基础

## 物理仿真与引擎定位

* **物理仿真（Physical Simulation）**

    * > **定义**：用计算机模拟物理介质的力学行为。

    * 研究对象是海洋、火焰、汽车这类符合物理规律的客观介质，关注其物理规律与行为特征。

    * 图形学按介质分为流体、刚体、柔性体三类；工程领域的分类会细得多，但都落在同一研究范畴内。

* **图形仿真与工程仿真**

    * 图形仿真以视觉效果为主，工程仿真更看重精度。

    * 取向差异的根源是计算资源有限时的取舍：资源不够，只能向一头倾斜。

    * 理想状态是二者融合：既达到工程精度，又达到图形所需的视觉效果。

* **物理仿真引擎（Physics Simulation Engine）**

    * 提供技术脚手架：窗口、模型读取、结果显示等基础框架已就位，使用者只需填入算法。

    * 接管与仿真无关的模块：渲染、UI、导入导出由引擎提供，研究者专注算法本身。

    * 充当比较基准：引擎集成大量现成算法，做对比实验时直接调用，比较效率与精度。

## PeriDyno 的四层架构

```text
应用层     场景管理 / 模块管理 / UI 与可视化展示
   ▲
核心层     仿真核心算法：有限元 / SPH / 刚体动力学
   ▲
通用层     数据结构 / 图形接口 / 碰撞检测
   ▲
硬件层     CPU / GPU / 内存 / 硬盘 的打交道 API
```

* **硬件层**

    * 负责与 CPU、GPU 打交道，也负责与内存、硬盘等数据存储打交道。

    * 这一层的实体是各类打交道的 API。

* **通用层**

    * 提供数据结构与通用算法：数据库、图形接口、碰撞检测算法。

    * 上层的仿真算法、交互算法、渲染算法都建在这一层上。

* **核心层**

    * 物理仿真引擎的核心部分，承载有限元、光滑粒子动力学（SPH）、刚体动力学等仿真核心算法。

* **应用层**

    * 对下层所有算法做管理，包括场景管理与模块管理。

    * 提供 UI 与可视化展示，让研发出的算法能被看见。

* **分层的边界**

    * 这套分层与游戏引擎会有偏差；原因不在画法，而在两者面向的对象、研究的问题本身不同，架构自然不一样。

## 工程获取与构建流程

* **上手三步**

    * 构建：把源码完整拉到本地，依赖 Git。

    * 配置：由源码生成工程文件，依赖 CMake 与 VS Code。

    * 开发：编译、调试、写算法，以 Visual Studio 为主；换 CLion 之类问题也不大。

    * 工具可以替换；按这条流程走是因为它成熟、中间问题少，换新工具可能遇到意想不到的问题。

* **运行环境**

    * 平台以 Windows 与 Linux 为主，Windows 10 或 11 均可；Mac 未做支持与实测，Vulkan 后端跑通时理论上可用。

    * 用 NVIDIA 显卡开发必须额外安装 CUDA SDK，这是硬依赖。

    * 整套仿真依赖 GPU，但不是绝对：对性能没有要求时可以完全用 CPU 写串行 C++ 代码。

* **Git**

    * 版本控制：每次修改形成修改记录，改错可回退到某个正确版本。

    * 分支与合并：多人各写一个模块时，并行开发再合并。

    * 可追踪：每个节点都有记录，能定位某段代码是谁在哪个节点写的。

    * 常用命令：`git init`、`git clone`、`git remote`、`git fetch`、`git pull`、`git push`、`git branch`、`git merge`。

* **分支与提交**

    * 主线上的每个点是一次提交，相当于给当前状态做一次备份，节点永久留在历史里。

    * 分支不是复制一份代码另存，只是在历史上多了一个引用；在分支上改东西，主分支代码一动不动。

    * 提交时必须填提交信息；提交后改动仍留在当前分支，切回主分支就看不到。

    * 新功能完成后用 merge 合回主分支，可选 fast forward 方式。

* **克隆**

    * 必须使用 `git clone --recursive <仓库地址>`，子模块才会一起拉下来。

    * 不加 `--recursive`，第三方子模块目录为空，生成工程时会因缺库而编译不过。

    * > **易错点**：克隆后编译报某个第三方库找不到，多半是漏了 `--recursive`；应重新用带参数的 clone 拉一遍，不要在残缺目录上硬修。

* **多远程仓**

    * 一个本地仓可以对应多个远程仓；添加新远程仓后必须重新拉一次，才能看到它里面的所有分支。

    * 在跟踪项里可在 `origin` 与新加的远程仓之间切换，决定向哪个仓同步。

### 目录结构

| 目录 | 内容 |
| :--- | :--- |
| `.git` | Git 自身的版本信息与临时文件 |
| `cmake` | 创建样例、创建 library 的脚本 |
| `data` | obj 文件与各种模型文件 |
| `example` | 样例，按 GPU 后端分为 CUDA、Vulkan、general |
| `external` | 第三方子模块，由克隆时自动拉取 |
| `python` | 与 C++ 的绑定，便于从 Python 侧调用 |
| `source` | 引擎核心库：core、动力学算法库、framework、交互、建模、插件、渲染 |
| `test` | 模块测试与单步测试 |

* **源码主体**

    * `source` 最底层是 `core`，最核心的库；其上依次是动力学仿真算法库、仿真框架 framework，以及交互、建模、插件、渲染各自独立的目录。

    * 生成出的 Visual Studio 解决方案呈现为 `engine`（核心库）、`example`（可直接运行的示例）、`rendering`（渲染）、`external`（第三方库）四块。

* **测试的作用**

    * 大型系统代码量大、算法模块多，一个算法内部又有很多步，因此需要对每一步做单独测试。

    * 测试是大型系统唯一靠得住的回归手段：跑一遍测试样例，用结果反推所有模块是否仍然正确。

### CMake 配置与生成

* **源码目录与生成目录**

    * 源码目录是含 CMake 脚本的根目录，文件里能看到 CMake 版本等设置。

    * 生成目录应新建为空目录，与源码分开；工程文件、中间产物、可执行文件全落在生成目录，清空重配不影响源码。

* **configure**

    * 选择编译器与平台：编译器按本机安装的版本列出（示例选 2019），平台选 x64。

    * 成功标志是输出 `Configuring done`；通常要多次点击 configure，直到红色条目全部消失。

    * 红色条目代表某一项还没找到，可能是编译器、第三方库或路径；还有红色就不能生成。

* **generate 与打开**

    * 生成后构建目录出现 `.sln` 文件，即 Visual Studio 解决方案，双击打开。

    * 勾上 Qt 选项会报错：CMake 在默认位置找不到 Qt 配置；需手工把 Qt 路径指到 `<Qt 版本>/msvc/lib/cmake/Qt5`，该目录含 `Qt5Config.cmake`。

    * 推荐 Qt 5.13.2 或 5.14；路径指对后 Qt 项即可通过。

### 新建工程

* **复制而非从零写**

    * 在 `example` 下新建目录，从其他示例拷一份 CMake 脚本，只改工程名与源文件名。

    * 示例脚本里已写好要链接的库、源文件所在目录，等于白捡一份调通的依赖配置。

    * 示例代码是最值得先翻的地方：找最接近自己需求的样例改，比从零写快得多。

* **重新生成**

    * CMake 脚本改动后必须重新 Configure、重新 Generate，否则 Visual Studio 里看不到新工程。

    * 生成成功但仍看不见时，关掉 Visual Studio 重开一次，让它刷新。

* **运行**

    * 解决方案里有多个工程时直接点运行会报错，因为不知道启动哪一个；把新工程设为启动项目再编译运行。

    * 首次编译较慢，等一两分钟正常；窗口弹出即工程打通。

    * 引擎提供 `example` 宏，可把一大段重复的 target 配置压成一行；用时还要补一个参数，指明工程对应解决方案里的哪个目录。

    * C++ 与 CMake 语法高亮不对只是显示问题，装对应插件即可，不影响编译。

## 场景、节点、模块与数据层

* **框架的三块**

    * 界面 GUI 是最外层，内部并排放置渲染窗口/视口与场景 Scene。

    * 场景不负责画，它被交给渲染窗口，渲染引擎用自己的视口识别场景并画到界面上。

    * 两边唯一的接头是"设置场景"这个动作；换场景不用碰界面代码，换界面也不用动场景。

    * 场景可以是刚体仿真，也可以是流体仿真；换一个场景就换了一整套物理内容。

* **场景的四层**

    * 场景由若干节点拼成，节点之间靠数据传递发生关系；节点内部是若干算法模块，模块之间同样有数据流。

    * 节点与模块都站在 Field 数据层上，读它的输入、写它的输出。

    * 从上往下依次是场景、节点、模块、数据四层。

```text
场景 Scene
├── 节点 Node  ────数据────►  节点 Node
│    ├── 模块 Module  ──数据──►  模块 Module
│    ├── 状态变量
│    └── 管线 Pipeline
│
└── 依赖
     ▼
   Field 数据层  ◄──输入──  外部
        │
        └──导出──►  外部
```

| 层 | 组成 | 职责 |
| :--- | :--- | :--- |
| 场景 Scene | 若干节点 | 组织整个仿真世界，提供重置与逐帧推进的入口 |
| 节点 Node | 若干模块、状态变量、管线 | 承载一组状态变量与一条管线，节点之间传数据 |
| 模块 Module | 控制变量、输入、输出 | 实际算法单元，读输入、写输出 |
| Field 数据层 | 各种类型的数据 | 定义输入输出与状态变量，供上下两层读写 |

* **四类数据流**

    * 节点到节点、模块到模块：在场景内部流动。

    * 模块与外部之间的导入与导出：跨出这一层，算完的数据能导出去看，外面的数据也能喂进来。

* **空场景自带的调试功能**

    * 按住 Ctrl 配合鼠标左键、中键、右键，可做缩放、旋转、平移。

    * 可切换相机视角、调整光照、更换背景、打印统计信息；这些功能都是为调试准备的。

### Field 的四种数据形态

| 数据形态 | 典型内容 | 存储与传递特点 |
| :--- | :--- | :--- |
| 基本类型、向量、矩阵 | `bool`、`int`、`float`、`double`，三维向量，矩阵 | 规模小，CPU 与 GPU 之间可直接传递 |
| 定长多维数组 | 一维、二维、三维数组，连续 buffer | 用 `define array` 系列宏定义，二维加 `2d`、三维加 `3d` 后缀 |
| 动态数组 | 长度可变的数组 | 用法接近 C++ 动态数组，CPU 与 GPU 通用 |
| 实例 instance | 复杂类型的引用 | 本质是指针，与 GUI 联动，界面能识别 |

* **基本类型**

    * 定义数据的宏让界面能识别该数据，可直接在界面上改值，改的就是场景里的值。

    * 另有定义枚举类型的宏。

* **定长多维数组**

    * 面向 SPH 这类粒子数量成千上万、每个粒子带一堆属性的场景；零散变量存不下，必须连续存储。

    * 连续内存可整块一次性拷到 GPU，不必逐元素传输；GPU 也能按线性地址成块读取。

* **动态数组与 instance**

    * 动态数组在 CPU 上建好后可直接传到 GPU，不用为两边各写一套容器。

    * instance 可理解为一个指针，与 GUI 联动，界面能识别、显示并连接它。

* **UI 一一对应**

    * 定义了什么类型，界面上就长出对应控件，不需要另写界面代码。

    * 价值在调参：跑的过程中直接改参数看后续变化，免去改代码、重编译、重跑的一轮等待。

### 模块与节点

* **模块的三要素**

    * 定义一个模块只需说清控制变量、输入、输出三件事。

    * 以 SPH 密度计算为例：控制变量是标准密度；输入是位置、邻域位置、邻域粒子 id；输出是密度数组。

    * 部分输入在父类里就已定义，看模块输入不能只看子类那一段。

* **节点多出的三样**

    * 整个节点可作为输入传给后续节点：复杂类型拆成字段连线会让界面无法辨认，整包传递能大幅减少连线数量。

    * 状态变量。

    * 管线。

* **连线即类型检查**

    * 只有同一种类型才允许连接；类型不符的连接在搭建阶段就被挡住。

    * 日志会记录完整的连接信息；断开某条连线，日志会指出是哪个源节点的哪个输出被断开。

    * > **易错点**：连线不是画着好看，而是一次类型检查；研发模块时先把输入输出类型定清楚，不兼容的连接不会拖到运行时才把程序搞崩。

### 场景的搭建

* **搭建流程**

    * 建模：创建一个几何的 cube，在它里面生成粒子。

    * 粒子出来之后设属性，比如给一个初始速度。

    * 挂上仿真计算节点，跑起来流体就动起来；加入几何边界后，流体与边界发生作用，行为立刻不同。

* **模块化的回报**

    * 几何生成、粒子生成、属性设置、仿真计算节点都是现成模块；搭新场景就是换一组参数、换几条连线。

    * 基础模块都做完之后，更多场景可以直接在 UI 里搭出来，不用每换一个场景就重写一遍代码。

    * 场景搭建的成本从"写代码"降到"连模块"。

### 状态变量与界面

* **状态变量（State Variable）**

    * > **定义**：节点特有的一类数据，用来描述一个物理现象当前处在什么状态。

    * 位置、速度、密度都是状态变量。

* **三种用途**

    * 数据从用途上分为变量、输入输出、状态变量三类。

* **Field 样例的界面映射**

    * 节点下展示基本控制变量：一个布尔、一个整型、一个浮点、一个三维向量，正好对应代码里最左边的四个变量。

    * 再往下是输入输出：输入定义一个浮点数组，输出也是一个浮点数组；最后还有一个状态变量。

## 管线与帧循环

* **管线（Pipeline）**

    * > **定义**：一系列功能模块按执行顺序排布出来的执行结构。

    * 名字借自图形学里的渲染管线，但在引擎里不是线性队列，而是一张图。

    * 一个模块的输入可来自多个上游，一份输出也可被多个下游取用；执行先后由数据依赖决定，而不是谁写在前面谁先跑。

* **两条管线**

    * 每个节点自带仿真管线与渲染管线各一条；场景取一帧时逐个节点驱动它自己的管线。

    * 管线入口对应节点里的状态变量；流体节点的入口是速度、位置以及其他各种场。

    * 入口之后接仿真计算模块或交互模块，模块算完更新自己负责的状态变量。

* **tag**

    * 模块把数据写完记一笔 tag；下游模块计算前先看上游数据有没有变，变了才重算，没变就跳过。

    * 省下的不是一次函数调用，而是整条链：一个模块输出没变，依赖它的下游全可跳过，越靠下游省得越多。

    * 没有 tag 机制，每帧所有模块无条件跑一遍，绝大多数计算是重复的。

### 一帧的执行

```text
场景 Scene
├── reset()
│     └── 逐级调用节点与模块，全部恢复到初始状态
│
└── take one frame（每帧循环调用）
      └── 节点 Node
           └── 仿真管线
                ├── 模块 1  ──► 更新状态变量
                ├── 模块 2  ──► 更新状态变量
                └── ……
```

* **两个入口**

    * `reset` 把整棵树拉回初始状态；取一帧让场景往前推一步。

    * 分开的理由：同一套搭好的场景可以反复跑——改参数、重置、再跑一遍，对比两次结果。

* **逐级驱动**

    * 取一帧时，场景调节点，节点调自己的仿真管线，管线里的模块依次更新状态变量。

* **渲染管线**

    ```text
    取出场景里搭好的所有渲染模块
            │
            ▼
       物体渲染 ──► 阴影渲染 ──► 实例渲染 ──► UI 渲染
            │
            ▼
       render target（帧缓存）──► 屏幕
    ```

    * 顺序为物体渲染、阴影渲染、实例渲染、UI 渲染，结果写入 render target，再显示到屏幕。

    * 仿真与渲染的调用骨架完全一样：场景—节点—管线—模块，差别只在末端挂哪类模块。

### 动态拆装

* **刚体示例的两条管线**

    * 左侧仿真管线末端接刚体动力学算法，前面几个也是相关的计算模块。

    * 右侧渲染管线接渲染算法，用于辅助显示；管线里能看到物体的表面网格、触点、触点法向。

    * 对应三种渲染模块：画触点的法向、用点的渲染方式画触点、画表面网格。

* **现拆现装**

    * 模块可以当场删掉，也可以挂上新的算法模块。

    * 叫"管线"正是因为模块可动态配置：删掉不想要的、加上自己写的，显示需求与仿真需求都能现场搭出来。

## 计算、数据、渲染与交互的分离

* **解耦的三件事**

    * 计算与数据分离。

    * 计算与渲染分离。

    * 交互分离。

* **有限元与粒子**

    * 两者拓扑不同、场有重名，但 Jacobi、Gauss-Seidel、Newton 这类迭代求解路子两边都能用。

| | 有限元场景 | 粒子场景 |
| :--- | :--- | :--- |
| 拓扑结构 | 四面体网格 | particle（粒子） |
| 场 | 位移场、应变场、应力场 | 位置、速度、密度、应力 |
| 计算任务 | 运动中更新位移、应力等 | 按邻域更新密度、应力，推进位置与速度 |
| 算法 | Jacobi、Gauss-Seidel、Newton 等迭代 | 同一类迭代方法同样适用 |

* **算法与拓扑是一对多**

    * 不同算法可共用同一种数据结构：SPH、PBD、MPM 都依赖 particle。

    * 同一种方法可跑在不同拓扑上：particle、表面网格、体网格都能用有限元（FEM）计算。

    * 若按"算法乘拓扑"两两实现，是 M×N 份；把表示抽象出来后，算法侧 M 份、拓扑侧 N 份，乘号变加号。

* **统一的拓扑层次**

    * 把"表示"单独抽出来，做成一套层次化的拓扑结构。

    ```text
    点云（particle）
      └── 边
           └── 三角网格
                └── 四边形网格
                     └── 四面体网格
    ```

    * 从点云到边、三角网格、四边形网格、四面体网格，维度与连接关系逐级变复杂。

    * 表示统一后，不同算法共享数据只需在这套表示上做一次映射，不必为每一对算法单独写转换。

* **写仿真算法的三步**

    * 创建拓扑结构：点云或四面体网格，看方法需要什么。

    * 在拓扑上定义场：位置、速度、体积、密度等；场的定义位置与拓扑绑定——点云上所有场定义在点上，四面体网格上有些量定义在单元、有些定义在点。

    * 拿拓扑与场做运算：数学上是梯度、散度、拉普拉斯算子，具体形式随离散方式不同。

    * 分开之后，换算法、加模块都不用动拓扑与状态变量；同一套拓扑换一组算法模块就能模拟不同现象。

### 渲染承担调试

* **渲染分层的理由**

    * 仿真算法最困难的地方是调试：错起来是一大片数值一起漂，断点与变量看不出问题。

    * 典型现象是穿模：可能是触点没找对，也可能是法向算错；把触点与法向画出来，才能顺着线定位 bug。

* **现成的调试渲染模块**

    * 点、线、面的渲染，实例渲染，半透明，颜色映射，都以模块形式挂在渲染管线里。

    * 需要哪些就组合哪些，不必为了看一眼中间结果去改渲染器。

### 交互的坐标变换

* **交互需要定制**

    * 同样是鼠标点击，一种需求是拾取物体、知道点到了它；另一种是抓住物体、按住拖拽。

    * 两种行为对物理系统的影响完全不同，每个开发者要哪一种由自己决定。

    * 做法是把交互也做成模块，与仿真模块、渲染模块整合，渲染或仿真时都能调用同一套交互模块。

* **屏幕空间到世界空间**

    * 鼠标事件发生在二维屏幕空间，而仿真与渲染都在三维世界空间，两个坐标系不能直接对话。

    ```text
    屏幕空间：鼠标点击 (x, y)
            │  结合相机参数
            ▼
    视锥内的一条射线
            │
            ▼
    世界空间：命中的物体 / 世界坐标
    ```

    * 屏幕上的一个点对应视锥上的一小块平面；结合相机参数可反推成世界坐标系里的一条射线，射线打到谁就是点中了谁。

    * 样例实现的是最朴素的一种：点中物体后给它一个冲击，把它推远；要做拖拽，重载鼠标响应模块再挂进管线，别处不用动。

    * > **易错点**：不做这步变换，直接拿屏幕坐标去改物理量，等于两个坐标系各说各话，表现就是"点哪儿都不对"。

## 多线程与锁

* **三个 loop**

    * GUI loop 收集界面与外设的交互事件，再把事件分发给仿真 loop 与渲染 loop。

    * 仿真 loop 跑仿真管线逐帧推进，渲染 loop 跑渲染管线逐帧出图。

    * 仿真 loop 写数据、渲染 loop 读数据，中间需要模块级互斥锁。

* **读写冲突**

    * 不同步：管线跑在不同线程上，时序对不齐，仿真算到一半渲染可能已经开始取。

    * 数据量大：物理仿真产生大量动态数据，可达几十 G 甚至几百 G，还要送给渲染引擎去画。

    * 轻的后果是显示不对、画面与物理状态对不上；重的后果是程序直接崩溃。

    * 败象是半新半旧的一帧：只有一部分模块写完新值，渲染取到的就是一部分物体在新位置、一部分还在旧位置；若读到正在被改写的内存则崩溃。

* **锁的粒度**

    * 不能把锁加在整个场景上：场景开销本来就大，一把大锁扣下去会频繁卡顿。

    * 锁加在具体模块上：某个模块正在写就只锁这个模块，其他已准备好的模块照常更新。

    * 锁得越细，仿真与渲染越能同时推进；锁得越粗越安全，也越卡。

## 后端与规模

* **后端选择**

    * 引擎有两个后端：CUDA 与 Vulkan；构建时另有"无 GPU"一档，全部用 C++ 实现。

    * 默认选 CUDA；要用移动端选 Vulkan；机器没有 GPU 就选无 GPU 档。

| 后端 | 适用场景 | 状态 |
| :--- | :--- | :--- |
| CUDA | 有 NVIDIA GPU 的机器，默认选项 | 最稳定 |
| Vulkan | 移动平台、跨平台 | 理论支持，可能遇到各种问题 |
| 无 GPU | 确实没有可用 GPU 的机器 | 纯 C++ 实现，绕开 GPU |

* **规模**

    * SPH 在实时条件下最高大约能到 100 万粒子的量级。

    * 不用 GPU 也能跑，只是性能受限：对性能没要求时可以用 CPU 写串行代码。

## GPU 架构与编程接口

* **编程接口的选择**

    * GPU 后端有 CUDA、OpenCL、Vulkan、DirectX 等多种，没有哪一个是唯一解。

    * CUDA 相对最简单、最容易上手，因此作为并行编程的基础。

* **传统 GPU（2006 年以前）**

    * 本质是专用图形处理器，主要为游戏做图形渲染。

    * 有可编程能力（最早是固定管线，某些阶段也能写程序），但很多功能仍固化，整个芯片为图形服务。

    * 在显卡上编程要写 GLSL、HLSL 等着色语言，像脚本一样发给 GPU，编译后执行，调试很麻烦。

* **Tesla（2006）**

    * 发布通用计算架构，是通用计算的分水岭。

    * 统一着色器/计算模型：同一套计算单元除图形渲染外还能算别的任务。

    * 直接支持 C 语言编程，对熟悉 C 的人友好程度是质变。

* **Fermi（2010）及之后**

    * Fermi 让通用计算架构基本成熟，GPU 完成从专用图形处理器到通用计算架构的演化。

    * 之后各家架构大同小异，差别在细节：SM 内 core 数量 Fermi 为 32 个，Kepler 为 192 个；这些数字本身不重要，只是为兼容不同任务做的调整。

* **Volta 与 Ampere**

    * Pascal 已针对深度学习任务做支持。

    * Volta 引入 Tensor Core（为深度学习服务），并把传统 CUDA core 里的整型与浮点计算拆开。

    * Ampere 的拆分更明显；同时支持更丰富的数据类型——不需要 32 位精度时可用半精度浮点，整型可用 8 位、4 位甚至 1 位，用低精度换效率。

    * Tensor Core 继续强化，但主要给深度学习；仿真仍以常规计算单元为主。

* **架构细节的意义**

    * 这些架构差别对"怎么用 GPU 编程"关系不大：逻辑架构在第一代就已经确定，后面都是在同一张蓝图上做加减。

## 传统渲染管线

```text
顶点数据：点 / 线段 / 三角面片
              │
              ▼
         顶点着色器        逐顶点：变换 / 颜色 / 法向
              │
              ▼
       裁剪 · 背面剔除
              │
              ▼
          光栅化          连续图元 → 离散像素
              │
              ▼
         片元处理         逐像素着色
              │
              ▼
     深度测试 · 遮挡剔除
              │
              ▼
          帧缓存
       ├─ z buffer（深度）
       └─ RGB buffer（颜色）
```

* **各阶段职责**

    * 顶点着色器逐顶点做坐标变换、颜色计算、法向计算；它为顶点这一档设计，几乎不可能被拿去干别的计算任务。

    * 裁剪与背面剔除去掉视野之外、背朝镜头的图元。

    * 光栅化把点、线、面等连续图元转换成像素，再对每个离散像素做光照着色。

    * 深度测试按深度缓存做遮挡剔除，最后把片元送进帧缓存。

* **帧缓存**

    * z buffer（深度缓存）体现前后遮挡关系；被挡住的片元不必再往平面上送。

    * RGB buffer（颜色缓存）就是屏幕，可理解为红、绿、蓝三通道图像。

* **固化的局限**

    * 每个环节都是硬件固化的专用单元：输入永远是图元，输出永远是帧缓存里的像素，中间不做别的事。

    * 很多计算单元只能固定做某一种任务，而通用计算的任务类型五花八门，这是向通用 GPU 演化的动因。

## CPU 与 GPU 的分工

```text
CPU：计算单元与控制单元一一对应
 ┌────┐   ┌────┐   ┌────┐   ┌────┐
 │Core│   │Core│   │Core│   │Core│
 └────┘   └────┘   └────┘   └────┘
    │        │        │        │
  ┌─┴┐     ┌─┴┐     ┌─┴┐     ┌─┴┐
  │CU│     │CU│     │CU│     │CU│
  └──┘     └──┘     └──┘     └──┘
    L1 / L2 / L3 多级缓存

GPU：一个控制单元统管一大片计算单元
             ┌───────────────┐
             │   控制单元    │
             └───────┬───────┘
                     │
   ┌────┬────┬────┬──┴─┬────┬────┬────┐
   ▼    ▼    ▼    ▼    ▼    ▼    ▼    ▼
 ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐
 │SP│ │SP│ │SP│ │SP│ │SP│ │SP│ │SP│ │SP│
 └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
      L1 / L2 缓存 + 大容量显存
```

* **CPU 的组成**

    * 计算单元 core 执行指令、做运算；图中四个 core 可以多线程执行。

    * 控制单元负责指令控制与数据存取。

    * 多级缓存 L1、L2、L3 用来压低访存延迟。

    * 关键特征是计算单元与控制单元基本一一对应，因此能处理更复杂的任务流与逻辑运算。

* **GPU 的组成**

    * 计算单元密密麻麻铺开，控制单元只有屈指可数的几个。

    * 同样有一级、二级缓存，还有容量大得多的显存。

    * 控制单元与计算单元不是一一对应：一个控制单元统管十几个计算单元。

* **比例决定分工**

    * 芯片面积几乎都花在算力上，代价是控制逻辑被压得很薄。

    * GPU 计算单元多、控制逻辑弱，适合计算密集型任务；大量逻辑判断是 CPU 的优势。

* **SM 与 SP**

    * 流式多处理器（Streaming Multiprocessor，SM）：GPU 里计算单元被组织成的一个个固定小集群。

    * 流式处理器（Streaming Processor，SP）：SM 集群里的每一个计算单元，也就是常说的 CUDA core。

## SM 的内部结构

```text
                   ┌───────────────────────────┐
                   │    指令收发 / 分发单元    │
                   └─────────────┬─────────────┘
                                 │
        ┌─────────┬─────────┬────┴────┬─────────┬─────────┐
        ▼         ▼         ▼         ▼         ▼         ▼
     ┌────┐    ┌────┐    ┌────┐    ┌────┐    ┌────┐    ┌────┐
     │ SP │    │ SP │    │ SP │    │ SP │    │ SP │    │ SP │
     └────┘    └────┘    └────┘    └────┘    └────┘    └────┘
        │         │         │         │         │         │
    [寄存器]  [寄存器]  [寄存器]  [寄存器]  [寄存器]  [寄存器]
        │         │         │         │         │         │
        └─────────┴─────────┴────┬────┴─────────┴─────────┘
                                 │
                    ┌────────────┬────────────┐
                    │      shared memory      │
                    └─────────────────────────┘
```

* **结构的稳定性**

    * 不同 GPU 的 SM 会有一定差异，因为不同架构要为不同任务做兼容性调整；从 Tesla 之后，大的结构基本固化下来。

* **四类组成部分**

    * 多个独立处理器：每个都能独立执行运算指令；SP 数量随架构不同（Fermi 32 个、Kepler 192 个）。

    * 指令收发单元：从 CPU 收到 kernel 调用后，把它翻译成 GPU 能识别的指令，再分发到每个 SP。

    * 寄存器：每个处理器私有，放运算要用的数据。

    * 共享存储：SM 内所有处理器共享的一块内存。

* **Tesla 的补充**

    * SP 就是 CUDA core，是真正执行运算的处理器。

    * 特殊函数单元负责 sin、cos 这类三角函数与特殊函数运算。

    * 寄存器数量很小，小到用字节数；它是 SM 内 core 共用的资源池，某个线程占多了会挤压别的线程。

    * 还有常量缓存、纹理缓存；shared memory 比寄存器大，但远小于显存。

    * 寄存器与 shared memory 的最大好处是存取速度非常快。

* **Fermi 的变化**

    * 指令收发单元变成两组，指令吞吐能力更强。

    * core 数量明显增加；每个核主要包含一个浮点运算单元和一个整型逻辑运算单元。

* **Ampere 的拆分**

    * 整型与浮点从同一个 CUDA core 里拆成两个独立单元。

    * 拆分前无法同时处理整型与浮点：算浮点时下一条整型指令只能等。

    * 拆分后浮点与整型可同时进行，每个单元的计算能力利用更充分。

## 三层硬件对三层软件

```text
硬件                              软件
┌────────────────┐
│      GPU       │  ◄──────────►  grid    （一维 / 二维 / 三维）
│  ┌──────────┐  │
│  │    SM    │  │  ◄──────────►  block   （一个 block 交给一个 SM）
│  │  ┌────┐  │  │
│  │  │ SP │  │  │  ◄──────────►  thread  （一个 thread 占一个 SP）
│  │  └────┘  │  │
│  └──────────┘  │
└────────────────┘
```

* **一一对应**

    * 一整块 GPU 由一系列 SM 组成，对应 grid；grid 可为一维、二维、三维。

    * 每个 SM 可独立执行一批任务，对应 block：一个 block 被调度到一个 SM。

    * 指令最终落到 SM 里的每个 SP，对应 thread：一个 thread 占一个 SP。

* **为什么分 block**

    * SM 里 core 的数量有限，任意大的任务不可能整块塞进一个 SM。

    * 必须按 block 把任务切开，一块一块送进 SM 执行。

* **grid 维度跟着问题走**

    * SPH 流体粒子就是一串编号，一维 grid 够用。

    * 欧拉视角的流体网格是二维甚至三维，grid 就做成对应维度；没有哪个维度更"正确"。

## 线程与 warp

* **一个线程一个元素**

    * 向量加法在 CPU 上是 `for` 循环逐个处理；这些元素相互独立，是天然并行的活。

    ```cpp
    for (int i = 0; i < n; ++i)
        c[i] = a[i] + b[i];
    ```

    * 数组长度小于 GPU core 数量时，可为每个元素分配一个线程，共 n 个线程，各算一个元素。

    * CUDA 核函数用 `__global__` 声明；启动时申请 n 个线程，每个线程用自己的线程编号换算出下标。

    * 一个线程只算一个元素，线程之间不通信。

* **warp**

    * warp 是 GPU 真正的调度单位，硬件以 32 个线程为一个 warp 调度。

    * 一个 block 允许的最大线程数是 1024。

    * 72 个元素按 32 切分得到 32、32、8 三组；最后一组缺的 24 个由硬件自动补齐，线程数总是 32 的整数倍。

    * 这件事发生在 warp 的调度与指令分发单元：kernel 调用进来后按申请线程数切成 warp，再逐个送入 SM。

* **补齐的代价**

    * 被补齐的 lane 空转，不干活。

    * 核函数通常要加下标越界判断，避免多出来的线程访问数组之外的内存。

    * 准备数据与分块时尽量让线程数是 32 的整数倍，否则最后一个 warp 只有部分 lane 在干活，其余算力白扔。

* **同 warp 顺序，跨 warp 乱序**

    * 同一个 warp 内部指令严格顺序执行，指令 0 完成才轮到 1；否则结果错误。

    * 不同 warp 之间乱序，不能指望 warp 0 一定先于 warp 1 跑完。

    * 乱序的原因是每条指令都有延迟且相互独立：某个 warp 等数据时整体挂起，调度器转去执行已就绪的另一个 warp。

* **warp 之间不能有数据依赖**

    * 若 warp 0 要用 warp 1 的结果，轻则计算错误，重则程序卡死。

    * 没有任何机制保证 warp 1 一定在 warp 0 之前跑到那一步。

---

## warp divergence

* **成因**

    * 一个 warp 里所有线程共用同一条指令流，同一时刻只能发射一条指令。

    * if/else 一类分支处，部分线程条件成立、部分不成立；整个 warp 仍按同一条指令前进，不满足条件的线程结果被屏蔽、不写回。

    ```cpp
    if (tid % 2 == 0)  a = 100;
    else               a = 200;
    ```

    * 若按上式分支：if 段一半线程空等，else 段换成另一半空等。

* **后果**

    * 算力被砍掉一半：本来能同时算 32 份，实际只有 16 份在动。

* **解法**

    * 让同一个 warp 里的线程走同一个分支。

    * 把线程按分支归属分到不同 warp：warp 0 全走 if，else 整段统一跳过；warp 1 全走 else，if 整段跳过。

    * 关键点是保证一个 warp 内的计算指令尽可能一致，从整体上提高有效算力。

---

## 延迟、占用率与延迟隐藏

* **延迟数值**

    * 一条运算指令约 10 到 20 个时钟周期。

    * 从显存取一个数据约 400 到 800 个时钟周期。

    * 两者差一到两个数量级，因此 GPU 计算的主要瓶颈在访存，不在算术。

* **占用率（Occupancy）**

    * 执行以 warp 为单元不断灌入；最理想状态是任何时刻都有 warp 能填满 SM 的计算单元，处理器一刻不闲置。

    * 若存在大量长延迟操作，几个 warp 全在等数据，SM 只能干等，计算单元全部闲置，效率掉得很厉害。

* **延迟隐藏（Latency Hiding）**

    * 做法是用足够多的 warp 掩盖等待：warp 0 发出取数指令后挂起，SM 转去执行 warp 1、2……等它们都发完取数，warp 0 的数据正好回来。

    * 算例：取数延迟 16 拍、每个 warp 只有 2 条有效指令时，需要约 $16 \div 2 = 8$ 个 warp 填满空档。

    * 只有一个 warp 时，16 拍里只有 2 拍在干活，占用率极低。

    * 提高效率只有两条路：增加可用 warp 数量，或降低取数延迟。

* **GPU 不是天生就快**

    * GPU 快是因为核多，不是因为单个核更强。

    * 问题只有几十个甚至几个元素时，工作量摊不开巨大延迟，延迟隐藏凑不出足够 warp，GPU 可能比 CPU 还慢。

    * 判断该不该上 GPU，第一问永远是问题规模够不够大。

* **配置建议**

    * block 线程数调成 warp 大小的整数倍，避免最后一个 warp 有 lane 长期闲置。

    * block 别太小：太小凑不出足够 warp，掩盖不住 shared memory 与 global memory 的取数延迟。

    * block 数量尽可能远大于 SM 数量：SM 之间可并行执行不同 block，block 太少会有一部分 SM 从头等到尾。

    * 针对每张具体显卡多测几组配置；最佳参数没有通用答案，只能实测，这四条都是经验而非定理。

## 多级存储与可见范围

| 存储层次 | 作用域 | 特性 | 使用注意 |
| :--- | :--- | :--- | :--- |
| 寄存器 `register` | 每线程私有 | 数量少，效率最高 | 总量是 SM 共享的池子，占多了挤别人 |
| 局部内存 `local memory` | 每线程私有 | 由 global memory 映射而来，效率低 | 只在寄存器不够时兜底，慎用 |
| 共享内存 `shared memory` | block 内所有线程共享 | 数量不大，效率很高 | block 内协作的主战场 |
| 常量内存 `constant memory` | 全局 | 只读 | 必须在编译阶段分配好 |
| 纹理内存 `texture memory` | 全局 | 只读 | 主要给渲染用 |
| 全局内存 `global memory` | 全局 | 就是显存，最通用 | 用得最多，延迟 400~800 拍 |

* **排序逻辑**

    * 越靠近计算单元，容量越小、速度越快。

    * 写算法的功夫很大一部分是把数据尽量往表的上方放：能进寄存器就别放 shared memory，能放 shared memory 就别反复读 global memory。

* **速度量级**

    * shared memory 的存取开销约为 global memory 的百分之一，容量比寄存器大得多。

    * local memory 与 global memory 效率相近，比寄存器慢约两个数量级。

    * 寄存器数量随架构不同，约 255 个这个量级；它是整个 SM 共享的资源池，某个线程占得多，别的线程能用的就少。

* **限定符**

    * 分配 shared memory，声明前加 `__shared__`。

    * global memory 用 `__device__`。

    * 常量用 `__constant__`。

* **生命周期**

    * 限定符决定变量放在哪，生命周期决定谁能看见：线程内、整个 block，还是整个 application。

| 内存 | 声明方式 | 可见范围 / 生命周期 |
| :--- | :--- | :--- |
| 寄存器 | 无需限定符，编译器分配 | 单个线程 |
| local memory | 无需限定符，寄存器放不下时自动使用 | 单个线程 |
| shared memory | `__shared__` | 整个 block |
| global memory | `__device__` | 整个 application |
| constant memory | `__constant__` | 整个 application |

* **数组落进 local memory**

    * 寄存器只适合放 `int`、`float`、`double` 这类标量，不支持大数组；数组一大，编译器会把它挪到 local memory。

    * local memory 映射自 global memory，速度立刻掉到与 global memory 同一档。

    * > **易错点**：觉得"没碰几次 global memory 却还是很慢"，答案常在数组悄悄落进了 local memory。

## 归约

* **归约（Reduction）**

    * > **定义**：把数组所有元素按某个操作符合并成一个值。

    * 操作符不限于加法，也可是求最大值、求最小值；换操作符得到不同结果。

    * CPU 上从第一个元素逐个加到最后一个，n 个元素需 n-1 次运算，是一个串行循环。

* **并行化**

    * 加法不必按顺序做，可以两两分组、逐层收缩，形成一棵二叉树。

    * 同一层节点只依赖下一层两个节点，彼此无关系，可以同时计算。

    * 8 个数归约只需 3 层，而不是 7 步。

```text
第 0 层    a0   a1   a2   a3   a4   a5   a6   a7
            \   /      \   /      \   /      \   /
第 1 层      s0          s1          s2         s3
              \         /              \        /
第 2 层        t0                        t1
                 \                     /
第 3 层                    total
```

* **第一版实现**

    * 每个线程负责一个数据，两两相加：8 个减到 4 个，4 个减到 2 个，2 个减到 1 个。

    * 前提是数据量不超过线程数，一个线程正好对一个数据。

    * 每一层只有一部分线程干活：第一层一半线程在算，每个线程拿下标 i 去加 i+1；越往上活着的线程越少，最后只剩一个。

    * 线程号与数组下标不天然对齐，中间要做偏移换算；偏移算错会出现结果每次运行都不一样，因为不同线程写到同一块地方。

* **两个问题**

    * 数据量被线程总数卡死。

    * 每次都从 global memory 取数，延迟开销会把并行收益全吃掉。

### 两级归约

* **拆分规则**

    * 一个 block 线程数上限 1024，超过就装不下。

    * 拆多大由自己定，512、256、128 都可以，只要不越过 1024。

* **两级结构**

    * 每个 block 送到一个 SM 做局部规约，得到局部结果；再用一个 block 对局部结果做一次归约，得到全局结果。

    * "先局部、再汇总"是后面所有 GPU 算法共用的骨架；数据量再大也只是多分几级。

### 共享内存加速

* **拷贝**

    * 用 `__shared__` 声明一段共享内存，按线程号把 global 数组整块拷进去。

    * 这份数据可理解为 global memory 中那一段的镜像拷贝。

* **收益**

    * 后续所有两两求和都在 shared memory 上做，存取开销约快 100 倍。

    * 省下的是大量"取数据时干等"的时间。

## bank conflict

* **bank 的布局**

    * shared memory 被划分为 32 个大小相等的 bank，编号 0 到 31，与 warp 的 32 个线程一一对应。

    * 地址按行铺：连续 32 个 32 位字占满一行，第 0 个地址在 bank 0，第 31 个在 bank 31；第 32 个地址又回到 bank 0。

```text
bank:   0    1    2   ...   31  |   0    1    2   ...   31
字地址: 0    1    2   ...   31  |  32   33   34   ...   63
        <---- 第一行 32 个字 ----> <---- 第二行 32 个字 ---->
```

* **理想与坏情况**

    * 理想情况是 32 个线程依次访问 32 个不同 bank，一条指令取完 32 个数据，谁也不用等。

    * 多个线程落到同一个 bank 时只能排队，一条指令并行取 32 个数据退化成 32 次串行取数。

* **bank conflict**

    * > **定义**：同一个 warp 内多个线程在同一条指令里访问 shared memory 中同一个 bank 的不同地址，硬件无法一次完成，只能把请求拆成多次执行。

* **归约里的冲突**

    * 按"前后两两成对"取数会撞 bank：8 个线程时地址 0 到 3 落在 bank 0 到 3，地址 4 到 7 又落回 bank 0 到 3。

    * 线程 0 取地址 0 和 1，线程 4 取地址 4 和 5；地址 0 与地址 4 在同一个 bank，同一时刻只能排队。

* **对半分**

    * 不让线程 i 配 i+1，改配 `i + blockDim.x / 2`：0 配 4，1 配 5，2 配 6，3 配 7。

    * 两个地址可能仍在同一 bank，但分属两条不同指令：第一条指令里各线程取自己的第一个元素，落在不同 bank；第二条指令再取后半，也落在不同 bank。

    * 同一时刻没有两个线程抢同一 bank，冲突消失；附带好处是线程号连续、访问地址也连续，warp 指令更一致。

* **前缀和里的冲突与填充**

    * 32 个线程的 warp 里，线程 0 取地址 0、线程 16 取地址 32，两者恰好同 bank；前半执行时后半只能等，一半并行度白扔。

    * 解法是填充：每 32 个字后插一个 32 位空位，使第二行地址整体错开一位，地址 32 落到 bank 1。

    * 代码表现是给 shared memory 索引加一个 offset，步长从 32 变成 33；CUDA 库的 scan 实现就是这么处理的。

    * > **易错点**：这类冲突不是"慢一点"，而是把本该并行的指令压成串行，代价随冲突路数线性增长。

## 前缀和

* **前缀和（Prefix Sum / Scan）**

    * > **定义**：对每个位置，给出它前面所有元素按同一操作符合并的结果。

    * 按是否包含自身分两种：exclusive scan 不含自己，第 0 位为 0；inclusive scan 含自己，第 0 位是元素自身。

    * 两阶段扫描直接产出的是 exclusive 版本；要 inclusive，就在结果上把 $a_i$ 自己再并进去，只差一次合并。

    * 写代码前必须先定死用哪一种，否则后面对不上号。

    * 这个算法比 CUDA 本身还老，是经典的两阶段做法。

* **上扫**

    * 自底向上，把每个元素当二叉树叶子，两两求和建出内部节点，再逐层向上，根节点就是全部元素之和。

    * 整棵树不占新地方，就在原数组里就地生长。

```text
上扫（自底向上，两两求和）
                      [136]
                     /     \
                 [36]       [100]
                /    \      /    \
              ...    ...  ...    ...
              / \    / \   / \    / \
             a0 a1  a2 a3 a4 a5 ... a15
```

* **下扫**

    * 根节点先替换成 0：总和不该加到任何叶子上，因为每个位置只要它前面的和。

    * 一个节点拿到累积值 p 后，左子收到 p，右子收到 p 加上"左子原来的和"。

    * 例：根给左子 0、右子 0 + 36 = 36；下一层某节点从上面接到 36，左子原和为 42，则右子收到 36 + 42 = 78。

    * 走到叶子，每片叶子拿到的就是它前面所有元素之和；结果首位是 0，末位等于总和减去末元素自身（136 减去末元素那一份得 120）。

* **跨 block 的扫描**

    * 规模超过一个 block 时，先做块内扫描。

    * 再把各块的总量累加到后续块的偏移上。

* **两个坑**

    * 占用率：每一层参与线程数减半，越往上闲置线程越多；改法是底层不必每个元素配一个线程，隔一个配一个——0 号线程处理第 0、1 个数据，1 号线程处理第 2、3 个数据。

    * bank conflict：二叉树越往上冲突可能性越大；解法是前述填充，每 32 个字插一个空位，把步长变成 33。

## 模板

* **函数模板与类模板**

    * 模板声明以 `template` 开头，后跟类型名（习惯写 `typename T`），再接函数名与参数。

    * 函数体里原来写 `int` 的地方一律换成 `T`。

    * 类模板是同一套写法，只是把 `template` 放在类声明前面。

    * 声明只是写法，真正生成代码在调用时：编译器看到传入 `int`、`float` 或 `double`，自行实例化对应版本。

* **全特化与偏特化**

    * 以 `Vec<T, dim>` 为例，模板带两个参数：元素类型与维度；通用模板不包含数据成员，真正存数据的是特化版本。

    * 全特化把模板参数全部写死，例如 `Vec<float, 2>`，类型固定 `float`、维度固定 2，单独给一份实现。

    * 偏特化只固定一部分：类型仍留作模板参数 `T`，只把维度固定成 3，对三维情况特殊处理，其他维度走通用版本。

    * 编译器遇到匹配的类型优先用特化版本，替换掉自己默认生成的结构。

* **归约的参数化**

    * 归约模板化后需要两个模板参数：一个类型，一个操作符。

    * 类型可以是 `int`、`float`、`double`，只要该类型上归约操作合法有效。

    * 操作符可是求和、求积、求最大、求最小，做成函数（仿函数）传入。

    * 代码里所有具体类型都换成模板参数；调用时按数组类型与操作符实例化，一份实现覆盖所有组合。

## 两个原语的组合应用

### SPH 邻域查找

* **问题**

    * SPH 对每个点都要知道周围有哪些点，把邻居 id 记下来；后面算压强、密度都要用这份邻域表。

* **朴素结构的缺陷**

    * 用 `vector` 套 `vector`：外层对应粒子数量，内层装该粒子的邻居 id。

    * 外层数据连续，但每个内层 vector 的数据散落在内存各段；取某个粒子的邻居时地址一跳，cache 就 miss 一片。

* **扁平结构**

    * 把数据摆回一段连续空间：`ids` 存所有邻居 id，`count` 存每个粒子的邻居数，`offset` 存列表起始下标。

    ```text
              粒子 0          粒子 1           粒子 2
    ids   : [ n0_0 n0_1 | n1_0 n1_1 | n2_0 n2_1 n2_2 | ... ]
    count : [    2          2            3         ... ]   每个粒子有几个邻居
    offset: [    0          2            4         ... ]   邻域列表的起始下标
    ```

    * `ids` 把所有粒子的邻居 id 挤在一段连续地址里。

    * `count` 记每个粒子有几个邻居；`offset` 记邻域列表从哪里开始，相当于 C 里指向数组头的指针。

* **构建用到两个原语**

    * 先用归约把 `count` 全部加起来，得到总共需要多少空间。

    * 再对 `count` 做一次 exclusive scan，得到每个粒子的起始地址：第 i 个粒子的 offset 就是它前面所有 count 之和。

    * 按总长度分配一整块 `ids`，各线程按自己的 offset 往里填。

### 包围盒

* **做法**

    * 输入几何模型或一堆点，对所有顶点分别求一次最大边界、一次最小边界，两个一夹就是包围盒。

    * 用归约，操作符换成 max 和 min，跑两趟。

* **适用边界**

    * 数据量小的时候没必要上 GPU：输入只有几个点、一个盒子时，CPU 反而更快，光是搬到显存再搬回来就不划算。

    * 真正值得用 GPU 的是输入到 100 万个点甚至更多的时候。

    * > **提示**：GPU 的收益来自规模，规模不够时它是负优化。

### 去重

* **五步流水线**

    * 排序：升序降序都行，排完相同元素挨在一起。

    * 标记：从左往右扫，第一次出现的元素标 1，已出现过的标 0。

    * 归约求和：把所有标记加起来，得到不重复元素的个数，也就是最终数组长度。

    * exclusive scan：对标记数组做前缀和，得到每个 1 应该写到哪里。

    * 回填：按扫描给出的地址，把标记为 1 的元素依次写进新数组。

```text
排序后 :  A  A  B  B  B  C  D  D
标记   :  1  0  1  0  0  1  1  0
求和   :  4                       <- 新数组长度
前缀和 :  0  1  1  2  2  2  3  4  <- 每个 1 的写入位置
回填   :  A     B        C  D     <- 新数组
```

* **与两个原语的关系**

    * 排序之外，求和用归约、定位用 scan；一段像业务逻辑的代码，底下全是这两个原语在跑。
