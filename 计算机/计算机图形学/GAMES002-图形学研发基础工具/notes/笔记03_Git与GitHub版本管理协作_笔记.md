# Git与GitHub版本管理协作

## 版本控制与 Git 概述

* **版本控制**

    * > **定义**：版本控制帮你搞清楚版本和版本之间文件到底有哪些变化、帮你追溯这些变化，并且在你需要做回溯和对比的时候，替你处理。

    * 没有版本控制时的粗暴做法：为每一轮修改单独准备一个文件（"修改版""最终修改版""最终最终修改版"……）。缺点非常直接：盯着这一串文件名基本得不到信息——不知道两个版本之间到底有什么区别，有时连哪个是最终的最新版都分不清；想追溯自己每次修改、对"到底改了哪些部分"有掌控，靠堆文件很吃力；一旦修改和他人不同步、或出了岔子需要回溯对比，就非常麻烦。

* **Git**

    * > **定义**：一个开源的分布式版本管理系统（软件包），功能就是版本控制，可以非常有效、非常高速地处理从非常小的项目到非常大的项目的版本管理；最初是 Linus 为帮助管理 Linux 内核而开发的开源版本控制软件。

    * 使用心态：Git 功能比较强大，但平时用不到它的所有功能——用一个复杂软件不一定要成为这个软件的专家，只需让它尽可能适合你正在处理的工作、尽可能辅助到手头的事；要学的核心功能其实比较简单。

    * 命令入口：装好后打开命令行输入 `git`，会列出很多子命令（如 `git clone`、`git init`、`git add`）；只要掌握最简单的几种就能完成基本的 git 操作，特别复杂的命令只在分支之间的操作（比如合并）或需要对某些特定操作做微调时才涉及。

* **三种使用形态**

    * **命令行**：在 git 官网下载、直接用命令行运行，是与 git 最直接的交互方式。

    * **git gui**：git 提供的图形化界面，Windows 上下载 git 一般会自带一个。

    * **GitHub Desktop**：通过 GitHub 下载的桌面管理软件，提供图形化界面做 git 操作——和你在网页上打开 GitHub 有点像，只不过它操作的是本地文件。

    * 安装：git 已经是非常知名的包，以 Linux 为例，直接运行安装命令就可以装上。

## Git 的两大功能

### 版本管理

* **git status 报告的三条信息**

    * 当前在哪个分支；

    * 哪些文件已经暂存了、之后就可以做提交（绿色——我修改了这些文件，并且把我的修改保存下来了）；

    * 哪些文件和之前的版本相比已经发生了变化，但这些变化还没有记录下来（红色）。

* **提交即版本**

    * 每个黄色的 commit 都代表一次提交，每个提交可以简单理解为一个版本；每次提交都带一条你在提交时写下的说明注释。

    * 版本和版本之间可以做对比：使用对比功能时，命令行会汇报两个版本之间所有文件的修改——相当于直接对比这两个版本。

    * > **提示**：读对比结果的口诀——版本 A 相对版本 B 新增的部分用绿色显示，版本 A 相对少掉的部分用红色显示。

* **功能概括**

    * 版本管理 = 追踪文件的差异、让你能记录文件版本、自动追踪每个版本的区别。

### 分布式协作

* **多人协作**

    * 同一个代码仓库，可以有不同的人一起协作修改；汇总之后由 git 自动完成合并、提交、修改、覆盖等操作。

* **"分布式"的含义**

    * 不需要存全部的文件——可能每个人手头只存部分的版本；大家把各自的修改汇总到远程一个集中的地方时，git 会自动计算版本之间的差异并完成合并。

## 分支

* **分支（branch）**

    * > **定义**：分支代表一条独立的开发线——可以从开发的主线上分离出来，在不影响主线的情况下同时工作；通俗地说，就是版本历史的"世界线"发生了一次分裂。

    * 版本历史图里的每个圆点都是一次提交，代表所有文件在那一刻的完整状态。

    * 线性历史的版本对比：版本一到版本三的区别，是把"一和二的区别"加上"二和三的区别"组合在一起——历史上可以找到一条修改的线路。

    * 分支与线性历史的区别：从本来一致的版本一分裂出两个节点——两条线基于相同的版本派生，各自演化、互不影响，这两种可能性本身是互斥的。

    * 分支操作：可以创建一个新的分支，也可以切换分支、列出分支、删除分支。

    * 分支可以再分支：打开仓库的 main branch 可以看到一大堆分支、互相之间的关系特别复杂；GitHub 用了一个特别复杂的界面来显示这些分支之间的关系与区别、它们的状态、更新频率、由谁在管理这些更新。

* **分支图示**

    * 每条线都从同一个版本派生出来，各自演化、互不影响：

```text
        o----o----o    <- master 分支（稳定版）
       /
o----o
       \
        o----o----o    <- dev 分支（开发中的功能）
```

* **master / dev 双线维护**

    * 典型用法：master 是稳定版；想新加一些功能时开一个新分支（比如 dev，developer / develop），在这个分支上做特殊修改——这些修改并不会影响 master 分支上的结构，开发者一动手也不会把原来的稳定功能弄坏。

    * 未来某一天，当 dev 分支上的修改已经成熟、稳定、通过测试了，就可以把 dev 分支的所有内容合并到 master 分支里——这就实现了版本管理。

* **版本管理与分支的关系**

    * 版本管理对应分支概念，分支概念对应一系列文件的修改：git 可以管理这些连续的修改，并形成最终的分支。

## 工作区、暂存区、版本库

* **工作区**

    * > **定义**：目录下面这些文件——你在编辑器里打开的、在文件夹里能直接看到的文件就是工作区；是你实际编辑的地方，改动 git 能感知到。

* **版本库**

    * > **定义**：`.git` 这个专用隐藏文件夹，git 把所有信息都存在里面，存版本变化的信息；每次提交一个版本时，把当时工作区所有文件全部存进去——相当于把整个工作区的一个拷贝、一个副本存到这个版本里。

    * V1.0、V1.2 这样一个个版本就构成了版本库，可以随时从版本库中提取历史的代码。

    * `.git` 一般来说看不到：Mac / Linux 上一开头的点文件夹默认隐藏，在命令行输入 `ls -a` 可以看到全部点开头的隐藏文件夹。

* **暂存区**

    * > **定义**：`.git` 里还有一个叫 index 的东西，作为暂存区；针对的是这样一个中间状态——文件已经发生了修改，git 也知道你的文件被修改了，但 git 还没有记录这些修改。暂存区就是让 git 先记住你的修改的地方，所有改动通过 `git add` 存到暂存区中。

    * 两句话定性：它不像版本库——里面只是把你的临时修改保存进去；它也不是工作区——它其实是一个虚拟的概念，追溯的是你的一些文件的改动，而不是实际上存了一份改之前或改之后的文件。

* **三区对照**

| 区域 | 是什么 | 特点 |
| :--- | :--- | :--- |
| 工作区 | 目录里能直接看到的文件 | 你实际编辑的地方，改动 git 能感知到 |
| 暂存区 | `.git` 里的 index | 虚拟的、临时的概念，只记录改动本身，由 `git add` 写入 |
| 版本库 | `.git` 隐藏文件夹 | 存每一次提交的完整快照，可随时提取历史代码 |

* **一条流水线**

    * git 指定一个目录作为工作区，在工作区里生成专用隐藏文件夹 `.git` 作为版本库，`.git` 里的 index 作为暂存区——只要搞清楚这三个概念，基本上就可以明白 git 到底是怎么一回事了。

    * 在工作区里改文件 → `git add` 把改动存进暂存区（git 知道并暂时记录这次修改）→ 攒到一定程度（"应该变成 V1.3 了、可以升级了"）用 `git commit` 把暂存区里的所有修改提交到版本库、形成一个新的版本 → 暂存区清空。

    * 想反悔的时候，再从版本库出发把工作区恢复回去——git 的一切操作都围绕工作区、暂存区、版本库这三个概念展开。

    * > **定义**：`git add` 可以理解为暂时的提交（暂存），`git commit` 可以理解为正式的提交。

## 建仓库与记录修改

* **git init：初始化仓库**

    * 先在想管理的位置新建一个文件夹（如 `mkdir temp`），执行 `git init`：初始化、新建一个 git 工作区——相当于告诉 git"这整个 temp 文件夹下面的所有内容，都是我要关心的"；它会生成一个新的空的 git 仓库，版本文件保存在 `.git` 子文件夹里。

* **git status：查看工作区状态**

    * 空仓库时报告两件事：当前在默认分支 main 上（可以先不用管）；还没有 commit 需要提交——空文件夹没做任何改动、还无法形成版本。中文 git 显示"位于分支 master""尚无提交""没有文件要提交"，是一个意思。

    * 新建一个文件后再看 `git status`：它报告两件事——git 知道这个文件被修改（新建）了；但这些修改 git 还没有暂存、没有记录下来。

* **未跟踪（修改尚未记录）**

    * > **定义**：工作区里文件的内容，和版本库里的记录不符合——空仓库的版本库记录也是空的，只要当前工作区非空，它就会报告"与版本库的记录不符合"，但这个改动并没有被记录。

    * > **易错点**：⚠️ git"知道你改了"和"git 记住了你的修改"是两回事。没有暂存的改动，随着你把文件改回去（比如把新建的文件删掉），这条修改就不存在了——git 不会留下任何痕迹，状态直接回到最初的空状态。

* **git add：把改动存进暂存区**

    * `git add <文件名>`：把这一个文件的改动存进暂存区；执行后再 `git status`，该文件变绿——已经被暂存、这条修改已经被记录、进入暂存区。

    * `git add .`：把所有文件的改动存进暂存区。

    * 暂存之后文件又改了：`git status` 会同时报告两条——暂存区里有一条记录（比如"新建了只有一行的 a.txt"），且暂存区里这条记录和文件当前的状态又不一样（对应暂存之后新加的那一行）。

* **git diff：看距离暂存的变化**

    * `git diff`，或 `git diff <文件名>` 更具体一点：查看"距离这次暂存，文件到底发生了什么变化"；原本一样的地方用普通颜色显示，新增的内容带颜色显示。

    * 注意此时还只是工作区的修改和暂存区的修改——版本库一直是空的，没有提交过任何版本。

## 提交与查看历史

* **git commit：沉淀成一个版本**

    * `git commit -m "<说明>"`：把当前工作区所有文件的一个快照（当前状态）全部记录到版本库里去，作为一个新的版本；以后随时能够和这个版本做比较，或者基于这个版本做一些恢复操作。

    * `-m` 参数后面写一句 message——关于这次提交的注释，相当于每个 commit 下面跟着的那一行说明；一般来说不用写很长，简单讲你到底做了一个什么样的修改。

    * 提交后 git 会告诉你几件事：产生了一个新的 commit，它有一个编号（那一串十六进制的码），说明就是刚才打的那一行；统计当前版本比起上一个版本有哪些变化——几个文件变动、几行新增、几行删减；告诉你新增了哪些文件。

    * 提交之后再查看状态：你和最新的版本已经一致——工作区和版本库的最新版本一致；`git status` 告诉你没有新的东西要提交，working tree 是一个 clean 的状态。

* **git log：查看版本历史**

    * `git log` 列出：这次 commit 的编号、作者是谁、日期是什么，以及关于这个版本的说明；想知道某个版本具体的情况，就根据这个编号进一步查询。

    * > **提示**：`git log` 会打开一个类似 vim 那样的全屏窗口界面，占据命令行当前窗口的全部内容；按 Q 就可以退出。

## 本地常用命令

* **四个"增"命令（最常用）**

| 命令 | 作用 |
| :--- | :--- |
| `git init` | 初始化，新建一个 git 工作区 |
| `git add <文件名>` | 把这一个文件的改动存进暂存区 |
| `git add .` | 把所有文件的改动存进暂存区 |
| `git commit -m "<说明>"` | 提交一个新的版本，并附带上你的说明 |

* **增与删的框架**

    * 这四个命令都对应着你"增加"什么东西：增加一个暂存区的内容，或者增加一个新版本；删减类命令想真正理解其说明的含义，必须先掌握工作区、暂存区、版本库三个概念。

    * 把工作区、版本库都存下来的基本用处：可以看两个区的文件差异；可以看文件的版本历史、所有版本历史；或者逐行地看一个文件的改动。

## 撤销修改与取消跟踪

* **git checkout -- \<文件名\>：恢复单个文件**

    * > **定义**：工作区和上一个版本之间发生了一些改动时，用这条命令把该文件恢复成版本库（最新版本）的状态——从工作区丢弃这次改动。

    * 对已记录的文件：比如给 A.txt 新加了一行，执行后 A.txt 并不会保留新加的那一行——这条命令把 A.txt 整个恢复了回去。

* **git checkout -- .：恢复所有文件**

    * "点"的意思就是"所有文件"：把当前工作区的所有文件，全部恢复成上一个版本的样子；这是最常用的撤销操作。

    * 场景：想针对一个上个版本里压根不存在的文件（比如新加的 B.txt）做 checkout，git 不买账——针对它的 checkout 就用不了；这时最简单的办法是 `git checkout -- .`。

    * > **易错点**：⚠️ checkout 恢复的是"改动"，不是"文件的存在"。它管的是 git 已经有记录的文件；执行后新文件（B.txt、C.txt）还原地待着、原样留在原地——因为 git 从来没见过它们——想让它们消失得用文件系统自己的删除。

* **git rm --cached \<文件名\>：从暂存区删除**

    * 改动有记录（比如进了暂存区）就可以针对它做恢复：把文件加到暂存区之后，用这条命令把它从暂存区里删掉。

    * 执行后它会告诉你把这个东西从暂存区里删掉了；再看 status，又变回没有改动、没有记录的状态——文件本身还在工作区，只是 git 不再跟踪它的改动。

* **删除类命令的使用纪律**

    * git 的删除语句蛮容易混淆：隔了好一段时间不用，很容易不知道该用哪一条；"从什么区里取消掉、删除掉什么东西"——如果不是特别理解暂存区、工作区是什么，你以为是一种效果，实际上是另外一种，这时就会出问题。

    * > **提示**：做 git 的删除操作（特别是删除语句）时，最好先通过搜索弄清这条命令到底有怎样的效果（教程一般会给具体例子让你直观感受），确定能达到想要的效果之后再去执行；不考虑远程协作、只考虑本地自己用的话，最常用的就是前面那四种基本操作——删除类用到时先查后用，别凭感觉敲。

## 忽略无关文件

* **.gitignore：设置 git 不关心哪些文件**

    * > **定义**：一个规则文件，git 会按照里面指定的规则，忽略掉这些无关的文件、不跟踪它们的变化。

    * 场景：新文件一出现 git 都会注意到并提示版本不一致，`git add .` 还会把它一起加进暂存区；但它可能只是你的数据、缓存或别的什么临时文件——不想要 git 跟踪它的变化，这时就需要给 git 设置一个 `.gitignore` 文件。

* **规则写法**

    * 基本上就是一行一条忽略项；git 会从上到下、从前往后扫描这个文件，来确定你到底有哪些文件是不关心的。

    * 直接写一个文件夹名 = 忽略整个该文件夹下的所有内容（比如 lib）。

    * 特殊的星号可以用作正则表达式式的匹配、文件路径的通配：比如所有以 `.egg-info` 结尾的文件夹全部被忽略，所有以 `.egg` 结尾的文件全部被忽略。

    * 前面加一个感叹号是反效果（取反）：典型场景——不想跟踪所有和 download 有关的文件夹，但其中以某个前缀开头的例外是我关心的，就给这一条前面加一个感叹号。

    * > **提示**：按需设置——项目中确实遇到了需要忽略无关文件的情况，再去网上搜索资料、看怎么设置这个规则文件，就可以实现 git 比较方便的忽略。

## Git 与 GitHub 的关系

* **Git 与 GitHub**

    * > **定义**：Git 是一个开源的、人人都可以用的软件，做的是版本控制；GitHub 是一个提供网页服务的网站，基于 Git 给你提供远程存储仓库的服务。两者不是替代关系，而是相辅相成、互相辅助。

    * 两者名字长得很像，但可以说是没有什么关系——完全是两个不一样的东西；GitHub 管理仓库的那些规则、它的版本控制都基于 Git，所以才叫 GitHub；使用上来说，GitHub 并不是 Git 的升级版或替代品。

* **为什么需要远程平台**

    * 本地版本管理难以协作：大家都是线上状态、通过微信这类软件联系，总不能每有一个新版本就把整个项目打包、我发给你、你再发给我。

    * 两条路子：要么你和同事用同一个服务器、可以看到服务器上公共的代码——这其实还是一种"本地"的情况；要么你们没有公共的存储文件系统，要和他人、甚至和网上的开源贡献者分享合作，就需要一个分布式的平台——网站本身给你提供仓库的存储服务，这就是 GitHub。

* **GitHub 提供什么**

    * 把你的仓库存到远程服务器上，它帮你托管这个仓库，并且提供更方便的功能：从文件浏览、分支管理，到一些其他比较复杂的操作，再到开源社区的交互、贡献，都有支持。

    * 类似服务的替代品：国内的 Gitee，另外还有 GitLab。

## 克隆远程仓库

* **git clone：把远程仓库下载到本地**

    * > **定义**：`git clone <网址>` 会把网址对应的那个仓库下载到当前文件夹——这是从网上下载代码到本地最基本的功能。

    * 仓库的下载界面会展示这个仓库 clone 的网址。

* **HTTPS 克隆与 SSH 克隆**

| 对比项 | HTTPS 克隆 | SSH 克隆 |
| :--- | :--- | :--- |
| 克隆条件 | 仓库开源即可，克隆本身不需要权限 | 需要先设置好 SSH key |
| 本地修改 | 可以任意改 | 可以任意改 |
| 推送回远程 | 不行——要检查权限，必须是使用者或协作者，且每次要输用户名密码 | 可以直接推送，无需验证 |
| 适合场景 | 克隆别人的开源仓库 | 自己的仓库、日常推送 |

* **HTTPS 的麻烦出在哪**

    * 把本地的新版本推送到 GitHub 上时需要检查你的权限：你必须要是这个仓库的使用者或者协作者，才有资格把本地的代码交到远程上去。

    * 命令行不像浏览器有一个所谓"登录"的东西，GitHub 每次都会问你——每次都要自己再输一遍用户名和密码，非常麻烦。

* **SSH 的解法**

    * 用 SSH 协议克隆下来的仓库，是直接根据 SSH key 去做权限检查的，这样推送就可以直接进行、无需验证；具体设置网上有非常多的教程，搜一下"GitHub SSH key"就可以。

## 本地与远端同步

* **git fetch：只同步版本库**

    * > **定义**：把我本地的版本库同步成远端的版本库——远程有一个新版本时，用 `git fetch` 把这个新版本加入到我的版本库，但它并不会实际修改我本地的代码。

    * 用途：相当于只是先把它加进来，后续要做一些额外操作、或者做一些对比的时候，可以跟版本库里远端的那个最新版本去对比。

* **git pull：同步并合并**

    * fetch 的进阶版：不仅做了 git fetch 做的事情——把远端的版本库进行同步——还会多做一件事：把远端的最新版本和本地的最新版本做一个合并。

* **git push：本地推上远程**

    * 反方向操作：把本地传到远端；这时你需要有这个仓库的所有权或者使用权。

* **方向图**

```text
fetch / pull ：  GitHub 远程仓库 ─────►  本地仓库
push         ：  本地仓库         ─────►  GitHub 远程仓库
```

## 把本地仓库搬上远程

* **场景与前提**

    * 本地已建好仓库、commit 了一些修改、`git log` 里已经有一个版本历史；想把整个仓库连同版本历史一起打包传到 GitHub 上。

    * 先在网页上直接创建一个空的仓库，就会得到一个链接、一个地址。

* **两条命令**

    * 第一行让本地的这个仓库和远程这个仓库连起来；第二行把本地的这个分支推送到远程上：

```bash
git remote add origin <远程仓库地址>   # 第一行：让本地仓库和远程仓库连起来
git push -u origin <分支名>           # 第二行：把本地的分支推送到远程上
```

    * 之后再在 GitHub 上刷新你的页面，就会发现本地所有的代码已经传上去了。

* **向他人的仓库贡献**

    * 要让本地的修改能同步到远程，需要三步：第一，你需要有这个权限——可能是仓库的所有者交给你的权限；第二，用前面说到的 SSH 协议把它克隆到本地；第三，在本地产生新版本之后，用 `git push` 提交到远端做修改。

    * > **提示**：遇到具体情况——比如你用的不是 GitHub，而是 Gitee、GitLab 这类平台——网上都有具体的教程介绍到底要怎么使用，搜索即可。

## 网页端可视化对比

* **本地对比的麻烦**

    * 命令行对比其实蛮麻烦：首先需要知道一个提交、一个版本的编号，然后用 `git diff` 输入这个编号，开启一个小的界面、列出所有文件的变化；不如可视化的方法直观、清晰。

* **单个提交的详情页**

    * 仓库的提交历史会列出你修改过的所有历史（比如最早有一个提交说明是初始化了整个仓库，最新的提交又有它自己的说明）；想看每一个提交发生了什么，点它右边那个按钮。

    * GitHub 就会给你列出来这些文件之间到底发生了什么：左边列出最基本的详情——哪些文件发生了变化；右边是这些文件里具体发生了什么样的变化，特别是每行的增删，都清楚地列在里面。

    * 相当于本地用 `git log` 加上 `git diff` 来查看的功能，在平台上用更好的可视化方法显示出来。

* **compare：批量比较两个版本**

    * 看单个提交的细节，只能知道这个版本和它的前一个版本之间有什么差别；想比较任意两个版本（比如 4 月 12 号的版本和 3 月 12 号的版本）之间到底有什么差别，就用 compare。

    * 做法：把想比较的两个 commit 的索引（那串代码）的前 6 到 7 位复制过来；网址前面那一段（从 http 到你的仓库名）点进你自己的仓库就会有；然后在网址后面加一个 compare，第一个位置填其中一个版本、第二个位置填另一个版本，中间用两个点连接：

```text
https://github.com/<用户名>/<仓库名>/compare/<版本一>..<版本二>
```

    * 输入这个网址，它会显示正在 comparing changes——比较两个分支、两个版本之间的差异：左边显示旧版本、右边显示新版本；可能有一个非常长的文件修改说明，可以在说明里做筛选，看看哪些文件到底具体发生了改动。

* **没有协作需求也可以用**

    * > **提示**：哪怕没有远程协作的需要，也可以把自己的仓库放到 GitHub 上——不公开、作为一个私人仓库——去利用它的界面做一些可视化或比较；也可以用 GitHub Desktop 这个软件在本地做可视化查看，和网页端的原理类似。

## 合并与冲突

* **git merge：把分支合并回来**

    * > **定义**：支持对不同分支之间进行合并的命令——在同样的版本基础上，把开发分支的内容合并回主线。

    * 用法：在主线分支上，`git merge` 加上这个开发分支的名字，它就会把这两个分支合并起来。

* **自动合并的成败**

    * 这个合并是自动发生的：一般来说，如果你的代码没有一些特殊的问题，基本上这个合并可以自动完成。

    * 能自动合并的情形：对一个文件，只有一个分支修改了它、另一个分支没有修改——这时合并操作很简单，把修改掉的内容应用过来，就完成了合并。

    * 自动合并失败的情形：两个分支同时修改了同一份文件的同一部分内容——git 毕竟不能确定你到底要哪一个文件里的内容。

* **冲突标记与解决**

    * 自动合并失败时，git 会中断这次合并的提交，并告诉你需要自己去选到底要哪个分支的内容；git 会自动在需要你做决定的位置上做标记：

```text
<<<<<<< HEAD
当前分支（分支一）的内容
=======
被合并进来的分支（分支二）的内容
>>>>>>> 分支名
```

    * 标记共五行：第一行是分支一的标记，最后一行是分支二的标记，中间用一大串等号相隔的两个部分，就是两个分支各自的内容。

    * 解决方法：如果觉得上面这个是对的，就把这五行全部换成上面这一行的内容；觉得下面这个对，就把这五行全部换成下面这一行。

    * IDE 辅助：这个标记本身是一个纯文本的界面，但在一些 IDE 里——比如像 VS Code 这样的 IDE，或者一些文本编辑器里——它会给你提供一个按钮：上面有一个勾、下面也有一个勾；点上面就是用上面这个修改结果，点下面就是用下面这个结果，这样就可以完成一个比较简单的冲突合并。

## 学习路径建议

* **先抓核心概念**

    * git 最最重要的概念，就是版本库、工作区、暂存区这三个；基本操作有几类——本地的操作、分支的操作、远端的操作，以及多人协作的操作。

* **入门次序**

    * 对初学者而言，从本地的那四个增加的操作开始学起。

    * 一定要尽量利用图形化的东西——能图形就图形，最好不要在命令行上一直死磕；除非已经逐渐熟练了，可以在命令行上做一些简单、快捷、方便的操作；否则一开始以学习为目的的时候，最好还是利用比较直观的、可视化的东西，来辅助你对工具的使用。

* **心态**

    * git 是一个有一些入门门槛、但同时也确实十分强大的工具——如果你能顺利地使用它、熟练地掌握它，对生产效率会有一个非常大的提升。
