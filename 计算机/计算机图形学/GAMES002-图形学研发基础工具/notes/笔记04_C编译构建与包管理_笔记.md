# C++编译构建与包管理

## 编译型语言与解释型语言

* **编译型语言**

    * > **定义**：必须先经编译器，把代码转换为可执行的二进制文件；C 和 C++ 属于这一类。

* **解释型语言**

    * > **定义**：由解释器实时把代码转化为二进制机器码；Python 属于这一类。

    * 速度更慢，但可能带来意想不到的便捷。

* **编译发生在哪**

    * Windows 上基本用本地 IDE：最原始的大概要数 Dev-C++，后面又有 VS Code、Visual Studio，用本地 IDE 就能把程序编出来。

    * C 和 C++ 也可以远程编译：比如 VS Code 的 SSH 远程功能；服务器上很难打开一个 IDE，往往就通过命令行——输入一个指定的编译器（如 g++），让它编译具体的文件，得到编译结果。

## 构建系统

* **构建系统（build system）**

    * > **定义**：用一份配置文件描述整个项目怎么编译，让它在不同操作系统版本、不同编译器版本下都能顺利构建。

    * 增量编译：每次修改一些代码，它会检查有更新的部分、重新做部分编译，不用每次把整个项目完整地编译打包一遍——这也是构建系统最初的目的之一。

    * 要告诉它三件事：需要生成什么样的目标文件（可以是一个库，也可以是一个可执行文件等）；生成时用到哪些依赖项；生成时用到的具体命令或命令行选项。

* **为什么手动命令行与脚本都不够**

    * 面对的项目往往不是自己写的：要么从网上下载别人的仓库编译出来用，要么把自己写好的发布出去让别人顺利使用——不理清编译配置，你的编译条件和别人的可能完全不一样，文件就没法经过编译。

    * 最原始的编译一行搞定：`g++ main.cc -o main`，指定编译器与源文件，后面还能挂 `-O2` 这类优化级别选项；但要调 OpenGL 这类第三方库时，语句后面挂一大堆选项，就需要配置成具体文件，把当时所有编译选项全部记录下来。

    * 写脚本方案的失效：把命令原封不动放进 bash 脚本虽然便捷，但 g++ 的版本、装的库（如 OpenGL）都依赖执行命令的那台本地机器；换了机器，一模一样的命令行在你这里能运行、到别人那里就没办法运行。

    * 所以对大规模、足够复杂的工程，要把「手动用命令行编译、链接所有代码」改成「用构建系统做一次配置，之后反复使用」。

## make 与 Makefile

* **make**

    * > **定义**：Linux 下最常用的构建系统，编译小项目时非常便捷、能提供非常好的支持。

    * 配置规则繁琐，大项目基本上很难手写 make；实际中往往先用 CMake 生成 make 的配置文件，再用 make 去执行。

* **Makefile**

    * > **定义**：make 的基本配置文件，本质是普通文本文件，里面指定要构建的目标、依赖项和具体命令。

    * 文件名必须一模一样地叫 Makefile，make 才能识别；当前路径下准备好后，命令行直接输入 `make`，make 就会认出它并读取里面所有的配置信息。

* **三段式**

    * > **定义**：Makefile 的基本组成——「目标：依赖项」一行，加一行缩进的生成命令；每个三段式说明某一个 target 文件要怎么生成出来。

    * 依赖不满足时：依赖文件在当前路径找不到，make 会提示依赖没有满足；如果你有其他配置能把它们生成出来，make 会先去把依赖生成好，再去执行生成目标的命令。

    * 两行就是一个 LaTeX 编译的配置；换成编译 C++，target 是可执行文件 main，依赖是 main.cc，命令就是那整句 g++：

```makefile
paper.pdf: paper.tex paper.fig
	pdflatex paper.tex
```

```makefile
main: main.cc
	g++ main.cc -o main
```

* **install 与 clean**

    * 两者是 Makefile 里定义的特殊 target：install 并不是一个要生成的具体文件，而是执行时做一些额外操作——常见的是把需要的文件拷贝到用户的目录下；clean 干的是另一类事。

    * 特殊 target 让 Makefile 的配置非常自由：可以定义编译语句，也可以定义特殊命令，把编译指令和命令组合起来就是一份完善的配置文件。

* **常用命令与选项**

    * `make`：做一次编译。

    * `make install`：把编译完的库、可执行文件全部放到用户可搜索的路径下，之后无论在哪里都能直接从命令行调用。

    * `-j`：希望构建时开多个线程一起并行，用它指定要用的线程或进程数量。

    * `-C`：指定目录——不想在当前目录下找文件、或不想把最终文件生成在当前目录时用，比如新建一个 build 文件夹，让新文件都生成在那里。

* **天花板**

    * make 没有提供太多优化与便利，仅提供「我有什么命令，就把它记录下来」；编译命令特别复杂时 Makefile 也特别复杂——比如调用 OpenGL，一大堆编译选项都得放进 Makefile 里逐个配置。

    * 所以用 C++ 编程基本都用 CMake 做中介：告诉 CMake 要做什么事，CMake 帮忙生成 Makefile，省去繁琐的选项配置。

## CMake 的定位与工作链路

* **CMake**

    * > **定义**：用户需求到 make 之间的中间层——你告诉 CMake 要做什么，它帮你生成 Makefile。

    * > **易错点**：CMake 本身并不是构建系统。它不能直接生成可执行文件，也不能脱离任何构建系统帮你编译——机器上没有 make，CMake 并不能帮你继续编译下去。

    * 一般来说它会生成一个 Makefile，或生成一个 Visual Studio 的解决方案/项目，再用后续真正的构建系统去做进一步的生成。

    * 因为特别方便的跨平台、跨语言能力，CMake 成了用 C++ 基本都会用的配置工具。

    * 整条链路：CMake 只负责把你描述的需求翻译成构建配置，真正动手编译的是最下面一层——

```text
你的需求：要生成什么、依赖什么
        │  写进 CMakeLists.txt
        ▼
    CMake（中间层，不直接编译）
        │  cmake .. 生成构建配置
        ▼
    Makefile（或 VS 解决方案）
        │  make 等真正的构建系统执行命令
        ▼
    可执行文件 / 库
```

* **命令行三段操作**

    * 下载 GitHub 上的项目时一定会见到的操作：第一段创建一个 build 目录；第二段让 CMake 生成 Makefile；第三段让 make 根据 Makefile 执行真正的命令（这个命令行形式还有跨平台的版本，遇到跨平台场景可以再搜索了解）。

```bash
mkdir build
cd build
cmake ..
make
```

    * `cmake ..`：CMake 会识别父目录下它自己的配置文件，识别完之后帮你生成 Makefile；生成完就可以通过 make 去执行。生成的东西都落在 build 目录里：

```text
项目根目录/
├── CMakeLists.txt     ← CMake 的配置文件，写清你的需求
└── build/             ← 新建的生成目录
    ├── Makefile       ← cmake .. 读取上层配置后生成
    └── (可执行文件)   ← make 根据 Makefile 编出来
```

## CMakeLists.txt 配置写法

* **CMakeLists.txt**

    * > **定义**：CMake 的配置文件，角色类似 Makefile；CMake 会在当前目录下识别这个固定名字的文本文件。

    * 里面指定你的 CMake 版本、项目名字，以及要构建的目标——目标叫什么名字、需要什么文件，都可以自定义。

    * 最简单的一个例子，三行分别是：至少要 2.6 版本的 CMake；项目名字叫 hello_world；从 hello.cpp 生成 hello 这个可执行文件——

```cmake
cmake_minimum_required(VERSION 2.6)
project(hello_world)
add_executable(hello hello.cpp)
```

* **与 Makefile 的关键差异**

    * 不需要告诉 CMake 怎么编译 cpp 文件——CMake 自己会决定要怎么编译，而不是需要你告诉它「我要用 g++，加 -O2，再加什么什么选项」。

    * 做 Makefile 的配置一定要关心命令行选项的细节；用 CMake 基本不用操心命令行选项，只需要关心要生成哪些文件、依赖哪些文件、依赖哪些包——这是 CMake 主要方便的地方。

* **脚本能力**

    * 可把 CMake 当作一种非常简单的脚本语言，定义局部变量、全局变量；这些用法基本只在特别大型的 CMake 项目里见到——配置特别复杂、或有多个包的时候。

    * 最常见的场景：指定用的 C++ 版本；指定构建的到底是 debug 还是 release 项目。

    * > **提示**：这些脚本层面的功能一开始不用掌握得特别清楚，后续实际用到了再查资料；语法和常见脚本非常相近，比较容易上手。

## 用 CMake 链接库

* **多文件编译链接**

    * 场景：项目根目录下两个源文件——mysqrt.cpp 定义自己写的平方根函数，main.cpp 定义 main 函数并调用它；把函数定义写到专门的、与函数相关的 cpp 文件里，就形成多个 cpp 文件之间的编译链接关系。

    * 与 hello 例子对比只是简简单单加了两行，就完成了一个库的编译和链接——用 CMake 做库的链接非常方便：

```cmake
cmake_minimum_required(VERSION 2.6)
project(main)

add_library(mysqrt mysqrt.cpp)
add_executable(main main.cpp)
target_link_libraries(main mysqrt)
```

* **三个命令的角色**

    * `add_library`：把 mysqrt.cpp 打包成一个库——打包成库之后就可以去链接它，自己写的平方根函数就能被其他源文件调用。

    * `add_executable`：和前面一样，声明可执行文件的名字，以及它从哪个源文件来。

    * `target_link_libraries`：把可执行文件和需要的库连起来——连起来之后就可以调用它。

* **find_package**

    * > **定义**：在本机搜索已安装的库，把库的地址、依赖选项整理成一组变量，供后续 include 与链接直接使用。

    * 可配合 CMake 的包检索模块（Package Search Module）来查；电脑上有这个库时，命令返回由库的地址、依赖选项形成的变量，直接根据这些变量链接即可。

    * 以 Eigen 为例：直接在命令行里写它的编译选项非常复杂，用 CMake 就很轻松——Eigen 是只有头文件的库，生成的变量就是 Eigen 头文件所在的那个目录，拿这个变量做后续的 include 或链接，整个项目就很简单地把 Eigen 编译进来了：

```cmake
find_package(Eigen3)
include_directories(${EIGEN3_INCLUDE_DIR})
```

## vcpkg 包管理器

* **vcpkg**

    * > **定义**：微软的跨平台 C++ 包管理器：一条命令装包，自动给出 CMake 接入代码，统一管理安装位置，角色类似 Python 的 pip。

* **用法**

    * 在任意位置安装上 vcpkg 之后，在任何一个项目目录下执行 `vcpkg install <包名>`，它就会自动把那个包装起来。

    * 执行完毕 vcpkg 还会告诉你：想在 CMake 里调用这个包应该怎么写——它把这段 CMake 配置代码直接打印出来，复制出来粘贴进自己的 CMake 配置，就可以完成这个包的调用。

    * 不需要关心这个包到底安装在哪，vcpkg 已经帮你管理好；和 pip 一样，都是通过包管理器统一管理所有从第三方装过来的包或库。

## xmake 构建系统

* **xmake**

    * > **定义**：更加现代化的 C/C++ 构建系统——CMake 只是用户需求到 make 之间的一个中间体，xmake 则打包了一大堆内容进去：从 make、到 CMake、到 vcpkg 的所有流程，它都能包下来。

    * 能力：既能完成编译，又能完成项目管理，又能完成包管理，同时还支持管理你的编译器；有自己的官网，官网上有非常丰富的文档。

* **配置文件**

    * 和前两个工具一样需要一个固定名字的配置文件：一个 Lua 脚本，以 xmake 自己定义的语法完成一个目标的编译。

    * 密度对比：脚本里就简简单单四行主要内容，同样这四行翻译成 CMake，要在 CMakeLists.txt 里写出好多好多行——非常容易上手。

* **包管理**

    * 直接在配置文件里加一句 `add_requires`，声明你需要哪个包。

    * 兼容 vcpkg 自己的包管理，也支持你自己构建的包——而不只是第三方的知名包。

* **兼容 Visual Studio**

    * 正常想用 VS 去配置一个 CMake 项目，是要打开一个特殊的 CMake 项目的；xmake 不是这样——通过一条语句把你的项目转化成 VS 项目，打开这个项目的解决方案，Visual Studio 就自动能够运行、能够编译。

* **一条命令运行**

    * `xmake`：命令行里直接说一句，就完成从编译到构建、甚至包安装的一系列事情；它会识别哪些包是没有的、自己去安装，从编译到运行基本全部在这一个命令里完成。

* **写法为什么顺手**

    * 定义 C++ 版本：xmake 里一句非常简单的命令就定义好；CMake 里定义其实有点复杂——往往要上网查怎么定义，而且别把变量名字打错才比较好。增加依赖库的方式也是一行就完成。

    * 搜索源文件的对比：CMake 用 `file(GLOB SRC_FILES src/*.cpp)`——查找所有源文件放进 SRC_FILES 变量，后续用这个变量完成编译，这是老 shell 脚本「一定要先把什么东西放到变量里再继续用」的风格；xmake 跨出了更大的一步，直接用一个函数、函数里指定正则表达式去搜索，可能是更自然的方式。

    * > **易错点**：例子里的 `*` 是 Linux 的路径通配符，它和正则表达式还是有区别的，两者不要混为一谈。

## 三代构建工具对比

| | make | CMake | xmake |
| :--- | :--- | :--- | :--- |
| 它是什么 | 真正的构建系统 | 用户需求到构建系统之间的中间层 | 打包全流程的现代化构建系统 |
| 配置文件 | Makefile | CMakeLists.txt | xmake.lua（Lua 脚本） |
| 命令行选项 | 全部自己写清楚 | 基本不用操心 | 一行命令搞定 |
| 包管理 | — | find_package 搜本机 / 配 vcpkg | add_requires，兼容 vcpkg |
| 典型场景 | 编译小项目非常便捷，大项目难手写 | C/C++ 项目的主流选择 | 一条龙搞定编译与包管理 |

* 演进逻辑：最原始、历史最悠久的是 make；CMake 比 make 跨出一大步——用更少的编译配置完成一个 C/C++ 项目的编译，省了特别多的功夫；再到最近比较新颖的 xmake，集之前各家之大成，兼顾编译和包管理，配置文件写法也非常接近现代人的习惯。

* 结论：经常遇到的、并且需要了解的基本上是 CMake 和 xmake 两种；make 知道它是怎么一回事就行——Makefile 到底要怎么写、语法是什么不用特别仔细关心，现在基本上都不直接写 make，而是用 CMake 或 xmake。

## CMake 与 xmake 的取舍

* **CMake 的定位取决于需求**

    * 不是特别刚需（不需要把自己的仓库打包发布出去）时，基本上不一定要用到它：知道 CMake 是什么、会读会用别人的 CMakeLists，其实已经够了。

    * 要把自己的仓库打包发布出去，那就还是得掌握 CMake：xmake 虽然好用、甚至可以直接拿它作为 C++ 编译的上手工具，但它毕竟不那么流行——要发布自己的东西，基本上还是应该提供一个 CMakeLists。

* **xmake 的短板**

    * 毕竟是一个非常新的东西，很多方面没有像 CMake 那样经过时间的考验、经过各种奇奇怪怪配置的考验，有不少不支持的地方。

    * 编译条件、编译选项特别「非通用」时，xmake 不一定吃得下来——具体要看各自项目的需求情况。

* **怎么选**

    * CMake 和 xmake 都是比较好的选择：xmake 附带把包管理给搞进去了，稍微省力；用 CMake 的话，也可以配上别的包管理系统来用。

* **示例的时效**

    * 上面展示的这些 CMake 例子比较旧；最新的 CMake 到底怎么写，语法估计比以前有所改进，建议根据自己的需求去学——要么 xmake，要么 CMake。

## conda 与 Python 包管理

### Python 侧的特殊性

* **不需要编译**

    * Python 是解释型语言，不需要做编译，直接在解释器上运行就可以，没有那么多复杂的编译过程。

    * 安装 Python 本身的时候，很多东西都已经编译好了——拿到的解释器就是编译好的成品，Python 代码都是直接在解释器上运行。

* **分工差异**

    * 在 C/C++ 里既需要管理包，又需要配置编译环境；在 Python 里只需要管理包就可以。

* **工具面**

    * Python 这边最熟悉的包管理就是 conda、pip 这些。

### conda 基本盘

* **conda**

    * > **定义**：Python 里非常知名的一个包管理和环境管理工具。

    * 基本上做两件事：一件是包管理，另一件是环境的分割——把运行环境分成好几个，每个环境之间安装的包互相不可见，因此也互相不会污染、不会干扰。

* **Miniconda 与 Anaconda**

    * 经常用的两种 conda，功能上基本类似；区别在于 Anaconda 会附带很多科学计算用到的包。

    * Miniconda 特别小、安装特别快，装上之后再去自己决定安装怎样的包；拿到一台 Linux 服务器或一台新电脑要装 conda 环境时，装 Miniconda 是很方便的选择。

* **base 环境**

    * 装好之后，命令行前面会多出一个 base——它就是一个 conda 环境：conda 在默认安装的时候，会提供一个默认的 base 环境。

### conda 与 pip 的日常操作

* **源（channel）**

    * > **定义**：源就是「conda 从哪个网站找包」；要下载一些别人发布的包时，conda 就是到它的 channel 里去找。

    * 动手装包之前一般先配置清华源：不确定现在是不是还必须配，但如果发现默认源不是国内的源，一般来说会很慢，最好还是配一下。

* **命令对照**

| 操作 | conda | pip |
| :--- | :--- | :--- |
| 安装包 | `conda install 包名` | `pip install 包名` |
| 安装指定版本 | `conda install 包名=版本号` | `pip install 包名==版本号` |
| 卸载包 | `conda remove 包名` | `pip uninstall 包名` |
| 列出当前环境的包 | `conda list` | `pip list` |

* **conda clean 与 pip 批量安装**

    * `conda clean`：删除掉那些下载了但是没有用到的 package、清理掉一些文件——常见于电脑实在放不下那么多东西的时候。

    * `pip install -r requirements.txt`：根据 requirements.txt 文件里指定的那些包批量安装，注意要加 `-r` 选项。

    * pip 也有换源的问题：需要到你用户目录下面的一个文件里去改，网上有很多教程。

* **学习成本**

    * conda 和 pip 都是非常简单的两个工具，不像 git 有各种复杂的概念；遇到具体功能再去查也完全来得及。

## 虚拟环境

### 概念与动机

* **虚拟环境**

    * > **定义**：一个目录——里面装着一个特定版本的 Python 解释器，以及一批软件包。

* **为什么需要它**

    * 别人的仓库可能只能在某个特定版本的 Python 下运行：很多语法只跟那个版本配套，或者依赖的一些包最新只发布到了那个版本。

    * numpy、OpenCV 这些包不同版本之间虽然已经尽量在兼容，但还是有差异，有的时候你只希望用其中一个版本。

    * 冲突场景：项目 A 需要某个版本的 Python，项目 B 需要另一个版本的 Python——虚拟环境就是协调这种版本冲突的登场之处。

* **虚拟机式的隔离**

    * 每个环境像一台「虚拟的机器」：一台装着 Python 3.9，再开一台装 Python 3.8。

    * 程序只能看到当前虚拟环境里的解释器和包，不知道你真正的 Python 版本，也不知道其他虚拟环境里安装了什么；一台机器由此可以部署不同版本的 Python，各环境之间互不影响。

```text
一台真实的机器
│
├── 虚拟环境 A：Python 3.9 + 它自己的一批包
├── 虚拟环境 B：Python 3.8 + 另一批包
│
└── 程序只能看到自己所在环境里的解释器和包，
    看不见其他环境，环境之间互相不污染
```

### conda 创建与激活

* **创建工具的选择**

    * 创建虚拟环境，一般来说我们用 conda，而不是用 pip。

* **四条基本命令**

```bash
conda create -n 环境名 python=3.9    # -n：给环境起名，Python 版本在这里一起填
conda create -p 路径 python=3.9      # -p：指定一条路径，把环境的文件放到那里
conda activate 环境名                 # 激活：名字就是自己命名的那一个
conda deactivate                      # 解除激活
```

* **`-n` 与 `-p` 的区别**

    * 区别在于环境的文件存到哪里：`-n` 会把文件存到你的用户目录下——Windows 上可能在 C 盘下面，Linux 上就在 home 目录；那个地方特别挤、而虚拟环境又必须装很多很多文件放不下时，用 `-p` 指定一条路径去放，比如专门把虚拟环境放到 D 盘。

    * 激活方式也不同：`-n` 创建的环境，直接输入它的名字就可以激活；`-p` 创建的环境，要输入它完整的路径名才可以激活。

    * 正常情况下都用 `-n` 来创建；创建完直接 `conda activate` 加名字激活，不需要了就解除激活。

### 接手别人仓库的标准三步

* **requirements.txt**

    * 别人的 Python 仓库里可能带这个文件：它用来告诉你虚拟环境里安装的包的版本。

* **三步流程**

    * 建环境（Python 版本填这个仓库所需要的那个）→ 激活 → 按清单装齐依赖；装完之后就可以正常运行它的项目代码——这其实是一种非常简单的包管理。

```bash
conda create -n 环境名 python=3.9    # 建环境，Python 版本填这个仓库所需要的那个
conda activate 环境名                 # 激活
pip install -r requirements.txt     # 按清单把它的所有依赖项全部装上
```

### conda 与 pip 别混用

* conda 能安装包，pip 也能安装包，但在同一个虚拟环境里又用 conda 装、又用 pip 装，往往会遇到一些冲突的问题——它们有时候还蛮不兼容的。

* 建议只用其中一种：比如只用 conda 安装，或者只用 pip 安装，一个环境认定一种安装工具即可。

* > **易错点**：同一个环境里 conda、pip 混着装包容易出冲突；装包只认定一种工具。

## 性能探查

### 探查的场景与价值

* **场景**

    * 嫌代码太慢：比如渲染什么东西，每次渲染花的时间都太久，想改一个参数再重新渲染看看；反复「改参数、看结果、改参数、看结果」的过程中，程序运行占掉了非常多的时间。

    * 如果能通过代码加速、或知道代码到底慢在哪，从而做时间上的优化，就能给开发、项目的编写和管理提供非常多的便利。

* **为速度花时间的账**

    * 性能探查的终极目的是提高工程迭代的效率；有的时候速度并不是最重要的，但当需要频繁修改程序参数、观察结果时，速度就变得很重要。

    * 一笔账：三天才能搞出一个结果，调参后再花三天看新的结果——不如先花一周时间把程序提速到一天就能出结果，接下来一周就能七天跑七次结果；什么都不做、仍三天出一次，这两周可能就干不了什么事儿了。

### C++ 的 Visual Studio 性能探查器

* **看什么**

    * Visual Studio 自带的性能探查器：用一张表格列出项目里每一个函数占据 CPU 时间的百分比。

* **怎么判读**

    * 根据百分比判断代码最慢的部分在哪里、慢得合不合理：有特别密集的计算，慢是合理的；但如果因为自身过失，写了一个本来应该很快、实际特别慢的循环，通过性能探查就会发现「这个地方比想象的要慢很多」，从而去改进这一块代码——这就是性能探查的主要意义。

### Python 的 cProfile 与可视化

* **cProfile**

    * Python 自带的性能探查工具。

* **配第三方可视化**

    * 再加一个第三方的可视化工具（可以用 pip 来安装），就可以图形化地查看性能结果。

    * 和 Visual Studio 一样，它会把每个函数调用的时间、调用的比例全部列出来，你就知道每个函数具体占用了多少时间。

### 逐行探查

* **逐行探查能力**

    * Python 有一个 C++ 里没有的能力：看每一行性能占用的时间。

    * 原因：Python 毕竟是解释器的语言，每一行是非常分明的，解释器知道现在执行到哪一行；而 C++ 是编译后的一个结果，不能直接知道每行的性能情况——不过它可以推断出来，比如某一条二进制的字节码，到底对应原文件里的哪一行。

    * 总之 Python 能告诉你每一行占用的大概时间。

* **典型案例：从 list 到 set**

    * 逐行看一个函数的占用：第八行占用了 92.9% 的时间——差不多整个程序的九成以上；而那一行只是一个「判断某一个数在不在一个列表里」的语句，本来觉得应该很快执行完，结果占掉了程序绝大部分时间，这就是不合理的点。

    * 分析与改法：这个功能被用得如此频繁，就不应该把它设计成一个列表（list），而应该设计成 set——散列表；改完之后这一句的功能完全一样，但只占用非常少的时间，整个代码的速度大大加快，省下来的就是开发时间。

    * > **提示**：需要频繁判断「在不在里面」的容器，用 set（散列表）而不是 list，两者的查找开销天差地别。

## 高效开发心法

### 读懂别人的 code base

* **起点问题**

    * 先想清楚项目从什么程度出发：是从零出发，还是从 GitHub 上一个已有的仓库出发；针对想实现的功能，应该用什么语言，C++ 还是 Python。

* **第一件事是读懂**

    * 最常见的需求：拿到一个别人已有具体实现、具体仓库的 code base，先把它的仓库读懂，再在上面做一些修改、做一些实验，去发展自己的新方法——读懂别人的代码这一步相当重要。

    * 读懂的手段：利用 IDE——点击一个函数就可以跳转到它的定义；实际去运行它的代码，做一个编译、做一个调试；或者把它放到 Jupyter notebook 里，一句一句地执行，看它的输入输出。

    * 不要把代码当纯文本来读——那样读非常难读；用上 IDE、编译调试工具、自己运行查看输入输出这些现代方法，会事半功倍。

### 起步怎么快怎么来

* **挑开发效率最高的解法**

    * 开始写代码时一定有具体问题——解决某一个点、或加一个功能；同一个问题可能有优雅的解法、也有粗暴的解法，起步阶段建议挑开发效率最高的那个。

* **可视化的例子**

    * C++ 有 OpenGL 这样的可视化方案，Python 也有自己的可视化；但其实可以把东西放到 Chrome 浏览器里，做一些自己的修改或调试，用它控制台的 JavaScript 来做辅助——怎么快怎么来。

* **验证后再整理**

    * Python 起步可以放到 Jupyter notebook 里开发，每个 cell 每个 cell 地执行，而不是把整个脚本文件一块执行下来。

    * 等验证了自己的方法 OK，再把目前的代码整理下来——整理成和原来仓库风格类似、封装好、也比较优雅的状态；起步时高效更好，正确性验证过了再组织成更系统的代码。

### 优化不用太早操心

* 一开始性能好不好、符不符合面向对象的基本原则，可以不用太早关心，特别是优化上的问题——写代码时就太关注优化，会影响开发效率。

* 一开始怎么直接怎么来、先不去关心性能；等把整个问题全部完成、写成代码之后，再回头用性能分析工具去关心效率、做性能的优化。

### 调试占一半时间

* 调试是代码编程中非常重要的地方：可能只有 50% 的时间在写代码，剩下 50% 的时间在调试；debug 永远是最关键的部分。

* 磨刀不误砍柴工：找一个最能直观看到「当前运行到哪里了、当前有哪些变量、怎么样做可交互的调试」的方法，特别是用 IDE——Visual Studio、PyCharm——去做可交互的调试。

* 除非觉得非常非常确定，尽量不要通过肉眼去看文本的代码来做调试。

* 必要时把中间的结果保存下来，和标准的程序去做比较：别人已经有一个标准的实现、或有办法验证自己的结果对不对时，就保存一些中间结果做比较——把问题拆分成一个个小问题，再去逐一做正确性的验证。

### 等待别干耗，参数记下来

* 像深度学习的训练、渲染、物理模拟这类长耗时过程，不要长时间盯着；把这些等待的过程拿去干别的事情，比如边等边开始修改其他的代码。

* 每一次运行时对参数做的微调最好都记录下来——比如每一次的程序到底是怎么能够复现的；这些记录对整体的开发是有帮助的。

### 计划、瓶颈与精力

* 明确自己的计划：判断接下来需要多少实验、需要多少时间，再根据这个判断决定比如有没有必要去优化程序的运行速度。

* 想清楚整个开发过程的瓶颈在哪里、计划是什么，然后平衡好精力和时间——精力和时间是两件非常不一样的事：有时时间充足却没有精力，有时精力充沛却时间来不及。
