# Windows命令行环境与远程开发

## Windows 系统概览

### 操作系统家族树

* **Windows（视窗操作系统家族）**

    * > **定义**：由微软开发、经营、销售的一组**闭源**图形化操作系统——与 Linux 最大的差别就在开源与否；关键词是"家族"：Windows 不是单一的操作系统，而是一整棵系统树。

    * 家族三大分支：**Windows 9x**（最老的一支，95、98……数字就是发布年份）、**Windows IoT**（Internet of Things，旧名 Windows Embedded，装在手表、可穿戴设备甚至眼镜等嵌入式设备上）、**Windows NT**（New Technology，取代 9x 的现代内核）——现在所用的系统全部属于 NT 家族。

    * NT 家族内部分两类：**Windows Server**（服务器线，从老到新有 NT 3.1~4.0、Windows 2000、2003，一直到 2022；科研中不如 Linux Server 常用）与个人电脑线（装在个人电脑上的 Windows，从 XP → 7 → 10 → 11；没有官方名词能概括这一类，可叫 others）。

    * 发展史从图标可窥一斑：1985 年的 Windows 还依附在 DOS 系统上、图标都是字符的；1991 年出现经典四格窗口标志；此后是 2001 年的 XP、Win8、Win10、Win11。

```text
Windows 操作系统家族
├── Windows 9x —— 最老的一支（95、98……数字就是发布年份）
├── Windows IoT —— 旧名 Windows Embedded，装在嵌入式设备上
└── Windows NT（New Technology，取代 9x 的现代内核）
    ├── Windows Server —— 服务器线：NT 3.1~4.0、2000、2003 … 2022
    └── 其他（others）—— 个人电脑线：XP → 7 → 10 → 11
```

### 优势、场景与获取

* **优势**

    * 图形化界面非常强大；用户基数大——基数大意味着基础系统之上开发的软件多，很多东西只支持 Windows，那就不得不用。

    * 硬件兼容、软件兼容都挺强；简单易用，图形界面交互性（interactive）强。

    * 应用场景几乎覆盖一切（almost anything）；图形学日常开发电脑基本都是 Windows——在这个系统上做图形化开发应该是最简单的。

* **深度学习与传统图形学的系统选择**

    * 深度学习用 Linux 更多（要 train）；传统图形学离不开 Windows——做 simulation 基本只会用 Windows，因为没有太多需要 train 的东西。

* **获取途径**

    * 正常买的品牌机自带正版 Windows（买电脑的价钱里已包含）；从零自攒的机器需先购买 Windows、再用启动盘安装，与 Linux 一样。

    * 虚拟机里装 Windows：把程序放到虚拟机里运行就像放在沙盒里——东西带病毒也只破坏虚拟机环境、不影响外面系统；运行来源不确定的程序时更安全。

* **更新节奏**

    * Windows 7 推出一段时间后 XP 停更；Windows 11 推出一段时间后 Windows 7 被完全停更——相当于强制大家更新系统；预计之后也会用 Windows 11 全面取代 Windows 10。

### 图形学开发的语言与库

* **C++ 侧**

    * 个人常用数学库；想写渲染管线这类东西，肯定需要 OpenGL。

* **Python 侧与 Taichi**

    * 需要训练神经网络时 Python 肯定最方便（PyTorch 很好用）；**Taichi（太极）**语言对 Python 支持最好——效率比 Python 高太多、与 C++ 相比可能只稍微慢一点，语法与 Python 很相似：用 C++ 走 GPU 需要手写挺复杂的 CUDA，太极可以直接都在 Python 里写，兼顾效率与开发速度。

## CMD 与 PowerShell

### CMD 与 PowerShell 的关系界定

* **CMD ≠ PowerShell**

    * > **定义**：CMD 与 PowerShell 是两个完全独立、没有任何包含关系的 shell 程序——CMD 不是任何 shell 的子集。

    * 在 PowerShell 里敲 CMD 命令看上去也能用、行为还与 CMD 里非常相似，是因为 PowerShell 的**别名（alias）机制**：它把 PowerShell 的一些指令映射到 CMD 那些简写形式上，调用 CMD 指令时会被自动转化成对应的 PowerShell 指令——只是看上去像子集，实际不是。

    * 从"能干什么"的角度可以说 CMD 被包含于 PowerShell：CMD 能做的事情，几乎所有 PowerShell 都可以干。

* **三条实质差别**

    * PowerShell 的每条命令叫 **commandlet**，每条都是一个小型的命令程序，比 CMD 的命令复杂。

    * 设计理念不同：CMD 本质上只希望你用它干简单的事，比如批处理（一堆文件批量重命名、拷贝）；PowerShell 支持的功能复杂得多，可以说就是一种高级语言——能运行复杂脚本、面向对象（和 Python 一样），CMD 则不是。

    * 信息传递不同：CMD 里指令之间传输信息只靠**字符串**；PowerShell 可以把一个整个的**结构化对象**在指令之间传递。

* **强弱与普及度**

    * PowerShell 比 CMD 强大得多，还支持跨平台和一些可扩展性；唯一"不足"是提出得比 Windows 晚，很早的 Windows 版本不支持它——但没有人才会去用那些系统。

    * CMD 是系统自带的 shell，和系统同时出现，所以哪儿都有它。

### WSL 与 PowerShell 的辨析

* **WSL（Windows Subsystem for Linux，Windows 下的 Linux 子系统）**

    * > **定义**：Windows 下的一个程序，运行之后会模拟出一个 Linux 环境，让你用 Linux 的命令行去操作 Windows 下的文件、资源等。

    * WSL 不是 PowerShell——一个是"Windows 里的 Linux 子系统"，一个是"Windows 自己的 shell"，别混。

### Shell 的启动方式

* **三种启动途径**

    * 开始菜单启动；或 `Win+R` 输入相应的 shell 名称回车。

    * 已打开文件夹、想在这个文件夹里直接开 PowerShell：按住 **Shift** 再右键单击文件夹空白处 → 菜单多出"在此处打开 PowerShell 窗口"——当前路径被直接设定成该文件夹，省得再 cd 一层。

* **安装与使用建议**

    * 电脑上没有 PowerShell 基本不可能；实在需要安装或更新，就先打开 CMD、去官网安装。

    * 建议先启动 CMD 练手——有些命令在 PowerShell 里的行为跟 CMD 里表现的不太一样。

## CMD 用法细则

### 命令格式与路径规则

* **命令行格式**

    * 与 Linux shell 非常相似：第一个单词是命令，后面跟若干参数；每个参数可以是文件名、路径、选项三者之一，文件名用法与 Linux 一样。

* **路径写法**

    * Windows 路径用**反斜杠 `\`** 连接（Linux 用正斜杠 `/`）；建议一律用反斜杠——正斜杠有时可以 work、另一些情况下报错，反斜杠一直都支持。

    * Windows 把磁盘分区直接暴露给用户，分出 C 盘、D 盘、E 盘；路径开头是**盘符**（一个字母加冒号，如 `C:`）——不像 Linux 有统一根目录。

* **选项写法**

    * 选项一般以正斜杠或减号开头，后面一般跟一个字母（也有跟多个字符的情况）；有的选项后面会跟一个有特殊含义的参数，有的选项本身是开关——写上表示打开、没有表示关闭。

    * 示例：`erase /f myfile.txt`——erase 是删除、/f 是强制执行，整条即强制删除该文件。

    * > **易错点** ⚠️：CMD 的 `cd` 没办法直接切换盘符——需要再单独输入一下盘符，才能真正切换到想要的路径。

### 空格与引号的不规律行为

* **echo 的原样输出**

    * `echo hello         world` 不管敲多少个空格都原样不动地输出——echo 后面的所有内容（空格还是非空格字符）都被当成字符串；Linux 里多空格只是参数分隔，输出时 shell 自动在两个参数间加一个空格。

    * > **易错点**：在 echo 里引号不表示"括起来"，会被原样打印——这与大多数指令对引号的处理不一样。

* **引号在路径处正常**

    * `cd "space dir"`：路径里包含空格时加引号没有问题——相当于把路径括到一个子串里；所有 CMD 里涉及路径的地方，路径含空格都可以用引号括起来，唯独 echo 里引号失去含义。

    * 结论：CMD 里每条指令的"协议"、规则不太统一——这是它没有 Linux 好用的重要原因。

* **与 Linux 命令的对应关系**

    * CMD 也支持重定向和管道，与 Linux 一样；每个基本操作基本都能找到功能类似的 Linux 对应指令（删除用 `erase` 或 `del`）——"功能类似"只是类似，并不完全一样。

### 账户类型与权限提升

* **三类账户权限**

| 账户类型 | 能做什么 | 不能做什么 |
| :--- | :--- | :--- |
| 管理员账户 | 最高权限，完全使用计算机并管理其他账户（类似 Linux 的 root） | —— |
| 标准用户账户 | 正常访问计算机、执行程序 | 更改其他用户的设置与系统设置；安装新软件 |
| 来宾账户 | 只适用于临时访问，权限最低 | 更改系统设置；安装应用；访问部分私密文件 |

    * 来宾账户场景：把电脑锁定之后、又想临时给另外一个人用；现在很少用。Microsoft 账户绑定到电脑、且电脑里只有这一个 Microsoft 账户时，基本上就有管理员权限。

    * 日常以标准用户身份使用：双击网上下载的安装程序时弹出的"能不能运行"授权窗口，就是让你以管理员身份授权；账户没有管理员权限时，需要输入管理员的密码才能授权。

* **以管理员身份运行**

    * Windows 里类似 Linux sudo 的提权方式：右键单击 CMD 或 PowerShell → 选"以管理员身份运行"——相当于给了那个程序管理员权限、可以任意操作电脑；任何程序其实都可以这样运行。

    * > **注意**：以管理员身份运行之前，得确认这个程序没有攻击性、不会伤害你的电脑。

### 文件权限：访问控制列表

* **ACL（Access Control List，访问控制列表）**

    * > **定义**：挂在**每个文件**上的清单，记录"有哪些用户可以以哪些权限访问我"——一种 **file-centric（以文件为中心）** 的权限管理方式。

    * 文件权限有两种管理思路：**user-centric（以用户为中心）**——在每个用户底下维护一张"我能以什么权限操作哪些文件"的列表；**file-centric**——为每个文件维护一张"哪些用户能以什么权限访问我"的列表；Windows 采用后者。

    * 查看方式：右键文件 → 属性 → "安全"选项卡——上面的框列出可访问该文件的用户；选中一个用户，下面显示其对应权限（如 users 组只有读取和执行的权限，administrator 是完全控制）。

### 变量与环境变量

* **set：临时变量**

    * 赋值要加 `set` 前缀：`set foo=bar`（Linux 直接 `foo=bar`）；访问在变量名前后各加一个百分号 `%foo%`——把这段字符串替换成变量存的值（Linux 在前面加 `$`）。

    * 删除变量：把赋值号后面的东西放空——`set foo=` 即表示删除。

    * `set` 后面什么都不跟：查看所有环境变量和当前局部变量（类似 Linux 的 set）；`set fo`：查看所有变量名中包含 fo 的变量。

    * set 做的赋值只影响**当前 CMD 窗口**——无论修改 PATH 还是新建变量，关掉 CMD 再启动就都不存在了。

* **PATH 环境变量**

    * 与 Linux 下的 PATH 是一个意思：不加任何路径前缀运行程序时，系统在 PATH 列出的路径里搜索——搜到就运行，搜不到就报错。

    * 追加路径：`set PATH=%PATH%;C:\mytools`——右边 `%PATH%` 先展开成当前值，再在末尾用分号接上新路径；可先 `echo %PATH%` 看现有目录，执行后再 echo 一次验证新路径已接到末尾。

* **setx：永久修改**

    * `setx foo "bar"`——**没有等号**，后面跟两个东西：变量名和用引号括起来的值；默认添加或修改**当前用户的环境变量**。

    * Windows 环境变量分两层：**用户环境变量**（用户之间不共享）与**系统环境变量**（不管登录哪个用户都有）；要修改或添加系统环境变量，后面加一个 `/M` 选项。

    * > **易错点**：setx 没办法永久删除环境变量——CMD 里就没有这种能删除环境变量的指令。

* **图形界面编辑环境变量**

    * 右键"此电脑" → 属性 → "高级系统设置" → "环境变量"：上面是用户变量、下面是系统变量；选中点"编辑"或双击即可修改，新建、删除都有；改 PATH 双击进去可新建、删除、上移、下移。

    * Windows 的设计理念就是尽可能让你用图形化界面解决问题——很多情况下没有必要非用命令行。

### 批处理脚本

* **.bat 文件（batch，批处理文件）**

    * 创建：新建空白文档（默认 .txt 后缀）→ 把后缀改成 .bat；右键 → "编辑"在记事本里写入一系列 CMD 命令，保存退出后**双击即可运行**；也可用 `call` 指令跟一个 .bat 文件运行，或切到该文件所在目录直接输入文件名。

    * > **定义**：可执行判定的本质差异——Linux 判断文件是否可执行是通过**权限位**；Windows 也有类似权限位但不以此为依据，而是看**后缀名**：.exe 默认是可执行文件，.bat 默认是用 CMD 解释器解释的脚本文件。

    * > **易错点** ⚠️：不要把其他类型的文件强行改成 .exe——改完 Windows 真的会把它当可执行文件：双击后系统直接把文件内容的二进制看成计算机执行的代码去运行，结果肯定报错。

* **两行示例：批量创建十个空文件**

```bat
@echo off
for /L %%i in (0,1,5) do (echo. > file%%i.txt & echo. > text%%i.txt)
```

    * `@echo off`：把接下来所有指令的回显提示关掉——此后所有指令无论运行正常与否都是 silent 的（前提是保证每条指令都是对的）；这是 CMD 才有的功能，PowerShell 没有。

    * `for /L %%i in (0,1,5)`：i 从 0 开始、步长 1、到 5 结束——**0 和 5 都包含在内**；do 后面跟想执行的操作，括号里可以有多个操作、之间用 `&` 分开，都会运行。

    * `echo.`（echo 紧跟一个点）表示什么都不输出；配合重定向 `echo. > file%%i.txt`：文件不存在就先创建、再往里输出空内容——即批量创建空文件。

    * 循环变量写成两个百分号 `%%i`，与访问变量的 `%foo%` 写法不同；CMD 脚本也有分支、循环结构，且每一条指令都有返回值。

* **删除与通配符**

    * Windows 里删除用 `erase` 或 `del`（不是 Linux bash 的 rm），配合通配符一把清掉：`erase file* text*`——星号匹配任何串。

* **学 .bat 还是 Python**

    * 不推荐深学 .bat 语法：费时间且有更好的替代——Python 比 PowerShell 还跨平台、几乎所有系统都能跑、功能更强大，科研与深度学习都离不开，一举多得；CMD 记住常用指令即可，更高级的功能写个 Python 脚本方便很多。

## PowerShell 命令体系

### Verb-Noun 命令结构

* **commandlet（动词-名词命令）**

    * > **定义**：PowerShell 每条指令都是一个 commandlet，命名一律是 **Verb-Noun（动词-名词）** 组合——前面是想要执行的动作，后面是执行的对象，可想成一个动名词短语。

    * `Get-Verb`：显示出所有指令的前半部分（verb）及其所属的组：Common、Data、Lifecycle、Diagnostic、Communication、Security、Other——Get 本身就是个 verb。

    * `Get-Command`：输出 PowerShell 里所有内置的指令（数量极多，屏幕刷很久）；如 Register-EngineEvent 也是动名词结构。

    * 可读性优势：CMD 与 Linux shell 用小写字母缩写命名指令、很可能需要查文档才知道意思；PowerShell 的指令一般看一眼就知道大致做什么。

### 帮助、参数与通配符

* **Get-Help 查帮助**

    * 类似 CMD 里的 help 指令：直接回车显示的是 Get-Help 这个指令本身怎么用；`Get-Help Get-Command` 会把 Get-Command 的语法展示出来，还有它的别名——gcm 与 Get-Command 完全等价。

* **带名参数**

    * 命令行格式：第一个词是指令，后面都是 argument；**带名字的参数以减号开头**——类似 C++ 或 Python 里函数的具名参数：给某个名称的参数赋值，就写 `-参数名`、空格后跟值。

    * `Get-Command -Name *-process`：把所有以 -process 结尾的指令显示出来；星号是通配符，匹配任何串、空串也可以。

    * > **提示**：CMD 与 PowerShell 在很多接受字符串输入的地方都支持通配符，有些地方可能还支持正则表达式——通配符让批量操作很方便。

### 对象与类型

* **Get-Member 查看对象**

    * PowerShell 是面向对象的编程语言，像 Python 一样有对象这个概念；`Get-Process | Get-Member` 用**管道**输入——Get-Process 的输出不再像 CMD 那样是 string 字符串，而是一个更高级的对象，Get-Member 把这个对象的信息展示出来。

    * 输出先给 **TypeName**（对象类型，如 System.Diagnostics.Process），再列出该类型所有成员：AliasProperty、Event、Method（类似成员函数、可以调用）、Property 等类别。

* **常见类型**

    * 基础类型：字符串、int、double（整数、小数）、布尔、数组；高级一点的：DateTime（表示时间）、hash table（哈希表）、文件信息和目录信息；**所有 .NET 的类型都支持**——.NET 可理解为一门非常跨平台的语言，可以跑各种各样的程序。

### 别名查询的两个方向

* **别名 → 指令**

    * `Get-Alias -Name gm`：只知道别名、想知道对应的 PowerShell 指令（gm → Get-Member）；Name 是 **positional argument（位置参数）**、排在第一位，`-Name` 一般可以省略，直接 `Get-Alias gm`。

* **指令 → 别名**

    * `Get-Alias -Definition Get-Member`：只知道指令名、想知道它短一点的别名（免得每次打长名）；Definition **不是**位置参数，**不可以省略**。

    * 两个方向输出同样的内容，从中都能获取它的别名叫 gm。

### .ps1 脚本

* **创建与运行**

    * 创建方式与 CMD 相同：新建文本文件、把扩展名改成 .ps1，用文本方式编辑；改完后 Windows 会自动调用 PowerShell 去解释、解析文件里的代码。

    * 代码更接近一门高级语言：大括号、小括号这些符号一目了然；比较运算符是"一个减号接两个字母"，如 `$i -le 5` 表示 i 小于等于 5。

    * > **易错点**：.ps1 不太能双击运行，得用 PowerShell 来跑；且直接输入脚本文件名会报错——不加点杠就等于没有指明路径，系统会从环境变量 PATH 里搜索，而 PATH 里没有当前这个目录；加上 `.\` 前缀才明确指定"就在当前路径下"（与 Linux 同规矩）。

```powershell
.\script.ps1
```

* **学习建议**

    * 想学可参考官方文档；但学 PowerShell 不如学 Python——刚才所有操作用 Python 里一个叫 os 的模块都可以做到。

## 云服务器与 SSH 连接

### 云服务器是什么

* **云服务器（远程服务器）**

    * > **定义**：由服务器供应商提供的远端计算设备，用来做高性能计算——直接通过远程连接来使用这些设备，不需要自己去管理、配置硬件。

    * 图形学、智能科学里最常见的是 **Linux 操作系统的云主机**，硬件配置基本都强大：32GB 以上的内存、多核的 CPU 处理器、常用到的英伟达显卡（做密集的并行计算）。

* **两种来源**

    * 租赁：从腾讯云、百度云、阿里云、华为云这些服务器厂商租，计费方式有按周、按月或者包年之类。

    * 自购：找同样的云服务器厂商，以科研实验室或者个人为单位自行购置服务器并自己维护——放在实验室或工作单位，在家里等地方远程连接。

* **使用形态**

    * 核心意义就是"远程使用"——不需要带着它跑来跑去，有需要随时从远程连接。

    * 很多云服务器**没有图形界面**，需要做终端连接；也有一些提供图形界面、可通过 VNC 服务连接远程桌面——主要面向的场景是无图形界面时的终端使用。

### SSH 连接与验证

* **SSH 连接命令**

    * 云服务器的连接首先通过 SSH 在终端进行：本地打开一个终端（Windows、Mac 都可以开 CMD 或 terminal），现在的电脑一般自带 `ssh` 命令，直接用它做远程连接。

```bash
ssh -p <端口> <用户名>@<服务器地址>
```

    * 三个组成部分：**账号名称 + 服务器地址 + 端口**——租赁或购买云服务器时供应商就会提供；记住这三样，就可以在任意设备（自己的个人电脑、移动的笔记本）上连接。

    * 服务器地址既可以是网址一样的地址，也可以是纯数字的 IP 地址（如 `162.105.x.x` 这样的一串数字）；输入正确密码后连上，命令行提示符从本机的用户名和电脑地址切换成远程服务器的用户名和地址——命令行已经在远程服务器里了。

* **两种验证方式**

    * **密码**：默认方式——输入当时租赁时给的密码。

    * **密钥**：在本地用 SSH 生成一个密钥，以后登录时自动判断有没有这个密钥、这个密钥是否匹配服务器上的一个公钥——匹配就不需要输入密码、自动登录进去。

### 退出连接与进程终止

* **主动退出的三种做法**

    * 在远程终端界面按 `Ctrl+D`；或直接输入 `exit`；或输入 `logout`——都是告诉远程终端"现在要退出了"、执行一个标准的退出过程，之后回到本地命令行，随时可重新连接。

    * 直接把窗口关掉也能退，但不算标准的退出方式——远程终端是"意外地发现"你退出了。

* **被动退出**

    * 远程连接需要一直保持网络连接：登录后闲置太久、把电脑合上、突然没网——过了超时时长连接就会断开，本地收到"远程主机重置了连接"或"远程主机关闭了连接"的信息。

* **退出的关键后果**

    * > **易错点** ⚠️：不管是哪种退出，都会终止终端中**所有的子进程**——终端退出不只是断开连接。

    * 典型痛点：训练神经网络要一天一夜，训练命令是通过远程连接执行的——一旦终端退出（主动退、关窗口、断网超时），远程服务器会终止掉训练过程，不可接受；由此引出终端多路复用。

## 终端多路复用

### 解决什么问题

* **终端多路复用**

    * > **定义**：让关闭远程连接后原有的进程不会中断、可以通过命令再次恢复出来的功能。

    * 附加能力：多个用户实际上可以看到同一个会话（跟别人分享你终端里的一些情况）；可以在单个窗口下进行分屏。

    * 实现载体：Linux 下需要多路复用软件，比如 **tmux** 或 **screen**（Windows 一般通过图形界面的方式来操作终端）。

### tmux 的三层结构

* **会话 / 窗口 / 子窗口**

    * **会话（session）**：顶层容器——连到远程服务器"整个登录进来"的这一层就是一个 session；关闭 session 时，它下面的**所有进程都被关闭**。

    * **窗口（window）**：一个会话里可以开很多窗口，就像浏览器一样；进入 tmux 时默认打开一个编号为 0 的 window（最下面绿色状态栏上有 `0` 标记）。

    * **子窗口（pane）**：在窗口里面做更复杂的分屏功能后出现。

    * 浏览器类比：会话 = 浏览器的整个程序；窗口 = 浏览器里的标签页；子窗口 = 标签页里做的分屏。

```text
tmux
└── 会话（session）…… "整个登录进来"的这一层，关掉它，下面的进程全没
    ├── 窗口 0（window）…… 进入 tmux 时默认打开
    │   └── 子窗口（pane）…… 在窗口里分屏后出现
    ├── 窗口 1 ……
    └── ……
```

### 会话操作命令

* **tmux 常用操作**

    * `tmux new -s test`：新建一个名叫 test 的会话并进入；`tmux ls`：列出全部会话（没有正在运行的会话时会告知）。

    * 组合键规矩：先按 `Ctrl+B` 前缀键——告诉 tmux"你要开始做一些特殊操作了"，再按具体操作：`Ctrl+B s` 选择切换到哪一个会话；`Ctrl+B d` 断开当前的会话。

    * `tmux a -t test`：接入（attach）名叫 test 的会话——断开后随时重新接回来。

    * > **注意**：把系统快捷键设成 `Ctrl+B`（如 Mac 的截屏/录制）会与 tmux 前缀键冲突，需先关掉系统那个快捷键才能正常用 tmux。

* **screen 对应操作**

    * `screen -ls`：列出正在运行的会话——显示会话从什么时间开始运行、状态怎么样（会话可以一直挂着运行很久）。

    * `screen -r`：恢复接入会话——恢复出当时正在运行的那个进程和它的状态（日志还在那里）。

### 终止与断开的区别

* **两种"退出会话"性质完全不同**

| 操作 | 性质 | 会话里的进程 |
| :--- | :--- | :--- |
| `Ctrl+D` | 终止会话 | 被真正终止 |
| `Ctrl+B d` | 断开连接（detach） | 挂到后台，继续运行 |

    * 在 tmux 会话里按 `Ctrl+D` 是**终止**——像终止进程一样，真的把这个窗口终止了；`Ctrl+B d` 是**断开**——把当前会话放到后台去，本机电脑的关机或其他操作不会导致里面的进程断开。

    * 多路复用的本质价值：暂时退出时进程是被**挂起/隐藏到后台**而不是被退出——从而可以在服务器后台运行一些复杂的进程命令，不怕本地电脑关闭。

## 远程文件与程序操作

### 图形化传输工具

* **XFTP 与 WinSCP**

    * 文件传输（本地文件上传到云服务器、反向下载）一般需要通过额外的软件：常见的有 **XFTP** 和 **WinSCP**；这些软件传输用的协议其实都是 **SFTP**——所以可以找到非常多的变种或替代品，选一个顺手的就行。

    * WinSCP 界面：左边显示本地电脑的一个文件夹、右边显示远程电脑的文件夹；把文件从左拖到右、或从右拖到左，就完成传输。

    * 文件的查看、编辑、比较也可以通过这些软件完成，但有时麻烦：查看远程某一个文件，需要先把它下载到本地、再在本地打开。

### 终端文件命令

* **常用查看与统计命令**

| 命令 | 作用 |
| :--- | :--- |
| `ls` | 列出当前目录下都有哪些文件和文件夹 |
| `ls -alF` | 列出详细信息：权限、所有者、创建时间、大小 |
| `find <目录>` | 递归列出目录下所有文件 |
| `grep` | 字符串筛选，比如只保留包含 `txt` 的路径 |
| `du` | 统计目录占用的空间 |
| `cat` | 在命令行里查看文件内容 |

    * `du` 示例：告诉你当前文件夹占了 56G、其中最大的那个文件夹占了 44G；也有统计硬盘剩余空间的命令；`cat` 直接看文件，文件太长可以用后面那条查看命令看。

* **掌握程度定位**

    * 这些复杂文件操作不必完全掌握——它们只是提供便利性：列目录在传输软件里直观可见；统计空间、递归列文件名也可以写 Python 或 C++ 脚本按自己的需求实现；记住它们的场景是"只打开了一个终端、想简单看一下某个目录下有什么"。

    * 文件的编辑、复制、移动、删除、比较会在使用中熟能生巧；用 VS Code 这样的远程控制软件还能更方便地在本地方便地比较文件、比较目录——本节这些是最基本的方法。

### 程序运行与中断

* **运行程序**

    * 进入远程终端后，在命令行里输入一个命令实际上就运行了一个程序（`ls` 本身就是一个程序，Python 命令也是一种程序）。

    * 远程终端里运行的程序一般不能像本地窗口那样"点个关闭"退出：有些复杂的程序需要做**标准的退出**而不是突然关掉——突然关掉程序反应不过来，它的一些日志、一些输出都会中断。

* **中断程序**

    * 一般通过 `Ctrl+C` 中断正在运行的程序：如 `cat` 程序一直运行、占住命令行没法敲别的命令，按 `Ctrl+C` 把它终止掉、回到原来的命令行。

    * 程序卡住了、或因为它特殊处理了 `Ctrl+C` 这个中断信号而按了没反应时，需要用更复杂的 `kill` 命令强制终止——正常来说不应该使用 kill，除非遇到意外状况。

    * > **提示**：中断程序的顺序是先 `Ctrl+C`；`kill` 是兜底手段，只在程序卡住、对 `Ctrl+C` 做了特殊处理这类意外状况下才用。

### 系统状态监控

* **ps aux：瞬时快照**

    * 查看当前机器上所有运行的进程：每个进程告诉你谁在使用、它的 ID 是多少、占用的 CPU 和内存是多少；注意 `ps` 是在输入的瞬间做统计——拿到的是那一刻的快照。

* **top：实时监测**

    * 实时查看 CPU 的变化：每三秒监测一下所有正在运行进程的 CPU 占用、并从高到低排序——像任务管理器；退出可以按 `Ctrl+C`，也可以按 `q`。

* **显卡与内存占用**

    * 有命令可以查看显卡的占用情况（如一张 24G 的显卡已用 500MB）与内存使用情况（如机器有 1T 内存、已用 100G、还有 900G 可以用）。

## 重定向与管道

### 输出重定向

* **重定向 >：覆盖写入**

    * > **定义**：输出重定向（`>`）——把程序本来要打印到屏幕上的输出，改写到指定的文件里；`echo something > apple.txt` 后文件里写的就是那句 something。

    * > **易错点** ⚠️：`>` 的默认行为是**覆盖**——文件旧内容会被整个替换掉；想保留旧内容，别用单个大于号。

* **追加 >>：接在末尾**

    * `echo something >> apple.txt`：在文件末尾追加一句 something，旧内容原封不动。

| 写法 | 行为 | 执行后文件内容 |
| :--- | :--- | :--- |
| `echo apple > apple.txt` | 覆盖：原内容全部丢掉 | 只剩 `apple` |
| `echo something >> apple.txt` | 追加：接在原内容末尾 | `apple` 下面多一行 `something` |

* **典型应用：脚本日志**

    * `python xxx.py > log.txt`：让 Python 跑脚本时把所有输出重定向到一个 log 文件里——跑完打开 log.txt，发生了什么一目了然。

* **输出太长会丢**

    * 终端能显示的内容有上限，往上拉到头就到顶——打印的东西太长，最开头溢出去的部分就丢掉了；希望保存结果时用重定向存成文件：如 `ps aux > apple.txt`，终端上一行不剩、全部存进文件。

    * 也有一些管道操作支持"既显示在终端、也保存到文件"——相当于 `>` 的加强版；输出很长、又想一边跑一边盯着看的时候用它。

### 管道与 grep 筛选

* **管道 |**

    * > **定义**：管道把一个程序的输出，重定向到另一个程序的输入流——与重定向功能相似但更复杂：重定向送进文件，管道送进另一个程序。

```text
程序输出 ──默认──> 屏幕
   │
   ├── 重定向 ──> 保存成一个文件
   └── 管道   ──> 另一个程序的输入流
```

    * `ps aux | grep 用户名`：ps aux 敲下去会出来一个特别复杂、特别长的进程列表，中间的竖线 `|` 把左边 `ps aux` 的输出接到右边 `grep` 的输入上——列出来的所有行都只跟这个用户相关；递归搜索文件时在后面接上这一句管道，结果就只包含所有 jpg 格式的文件。

* **grep 的筛选原理**

    * 单独运行 `grep text`：随手往里输入文本——只要某一行里有 text 这个词，它就把这一行原样输出回来；输入里没有 text，它不会有任何输出（把输入吞掉）。

    * 接到管道里，这个性质就变成对整个输出的筛选：前一个程序的输出，必须包含 grep 规定的那个词才会被重新输出一遍，除此之外都被吞掉。

```text
ps aux 吐出一长串进程行（每行一个进程）
   │
   ▼
grep 用户名：行里含这个词的，原样放行；不含的，悄悄吞掉
   │
   ▼
终端上只剩下你关心的那几行
```

### 返回值与 && 短路

* **程序返回值**

    * 程序跑完没抛出异常、没报错，其实会有一个返回值——就是写 C++ 或 C 程序时 main 函数 return 的那个值；按约定 **0 表示正常返回；一旦不是 0，就说明返回时发生了异常**。

* **&&：短路的成功性检验**

    * `&&` 是逻辑与、而且是**短路**的操作符：一旦前面某个值为 false，后面的所有值都不会再去求值——program1 出现异常（报错），program2 就不会继续运行。

    * 用途：做一个很简单的"成功性检验"——保证前面所有程序都正常运行之后，才去运行接下来的程序。

```bash
program1 && program2
```

## 命令行工作机制

### shell 的中介角色

* **shell**

    * > **定义**：shell 是"我们用户的输入"到"服务器到底要干什么"之间的中介。

    * 一条命令的执行链：终端敲入命令 → 命令传给远程服务器上的 shell → shell 读取命令、判断该干什么（跑一个程序 / 查看所有进程 / 退出登录……）→ shell 告诉具体进程怎么操作、服务器去执行 → 操作结果产生在远程服务器上 → shell 把结果传回你的终端，你看到输出。

```text
你在终端敲入一条命令
   │
   ▼
命令传给远程服务器上的 shell
   │
   ▼
shell 读取命令，判断该干什么
（跑一个程序 / 查看所有进程 / 退出登录……）
   │
   ▼
shell 告诉具体进程怎么操作，服务器去执行
   │
   ▼
操作结果产生在远程服务器上
   │
   ▼
shell 把结果传回你的终端，你看到输出
```

    * 远程服务器场景里实际有两台主机：用户的终端（本地、自己的电脑）与远程服务器（可以运行一些复杂的事情）。

    * shell 这个中介有很多种选择：Windows 常见的有 Windows Terminal、cmd、PowerShell；Linux 上则有 bash、zsh——都是扮演同样角色的常见 shell。

### 命令行参数

* **没有图形界面时的定制入口**

    * 图形界面程序靠窗口、侧边栏、命令选项、文件配置来定制功能（VS Code 就是现成例子）；真正的远程服务器可能就没有这样的图形界面——程序的功能定制**基本都以命令行参数的形式**存在：给一个程序输入一个参数，这个程序就知道你要做什么特殊的定制。

    * 例子：一个复杂的数据处理程序后面跟着一大堆命令行参数——就是这些参数定制了这个程序的各项功能。

* **编程语言里的对应处理**

    * C 和 C++ 的 main 函数本身就带两个参数，专门用来接住并解析这些命令行参数；Python 也有一个默认的库，专门提供命令行参数的处理。

* **历史查找的需求**

    * 一条命令的参数特别复杂时，会希望查找以前使用过的命令行参数——就像浏览器历史一样：收藏过的网页记得住，几天前用过的网页也找得回来；命令行里这个功能由一种特殊的 shell 提供。

## ZSH 配置与使用

### ZSH 与 oh-my-zsh

* **ZSH**

    * > **定义**：一个比较通用、功能也比较强大的 shell，提供命令行历史与自动补全等能力。

    * 历史自动补全体感：输入 `pyt`，它就已经帮你补全成 python 了；再敲一个空格，又能补全到上一句用过的那条 python 命令；按一下右方向键，整条命令全部补上——可以在此基础上再做修改。

    * > **提示**：这套自动补全**不是 ZSH 默认自带**——一个默认的 ZSH 绝对没有这个功能；它来自 oh-my-zsh 里一个名字带 suggestion 字样的插件，相当知名，大多数教程里都能找到。

    * **oh-my-zsh**：ZSH 本身的配置非常复杂，但有人提供了开源的配置方案 oh-my-zsh（GitHub 上有项目主页）；网上能搜到很多资料和中文配置教程，照着那些简单的配置方法就能配起来。

### 快速目录操作

* **Tab 补全文件名**

    * 打前面几个字符、按一下 Tab，它就帮你自动补全成这个目录下的文件名——替代"先 ls 看看要哪个文件夹、再 cd 进去"的老流程（文件夹名字特别长时尤其省事）。

* **公共前缀分流**

    * 目录里两个文件前缀相同（如 mg37、mg42）：输入前三个字母按 Tab，补全到它们**最长的公共前缀** mg；在此基础上想要 37 那个就再输入一个 3 按 Tab，想要 42 就输入一个 4 再按 Tab。

* **逐层路径补全**

    * 目标路径离当前目录特别远、不知道外面一层有什么时：输入 `../` 再按 Tab，把外面那一层目录下的所有目录补全给你看；输一个 o 补全成 output，再按 Tab 看 output 里有什么（补全出 example），再按 Tab 看 example 下面的文件——甚至可以**连按两下 Tab 来做一个选择**。

    * 这种路径自动选择比不上 VS Code 的图形界面操作，但对命令行来说已非常实用；而且要找的东西特别远、藏在几个"犄角旮旯"文件夹里时，命令行反而会比 VS Code 快。

### 状态与属性辅助标注

* **时间与文件颜色**

    * 提示符旁边会标注出当前的时间；ls 里文件颜色不一样，是因为文件属性不一样——比如 zip 压缩包，ZSH 会给它一个特殊的颜色。

* **conda 环境与 git 状态**

    * 用了 Python 虚拟环境（conda：miniconda、anaconda 这类）时，提示符里显示 conda 环境的名字（如 base）；切到某一个环境，这里就改成那个环境对应的名字。

    * 当前文件夹是一个 git 仓库时，会标注 git 状态——显示叉叉，说明当前有一些文件已经被修改掉了；显示一个圈，说明当前文件全部都是最新的、没有被修改过。

## 远程控制工具

### VS Code 远程连接

* **连接流程**

    * 左下角"打开远端窗口"按钮 → 两个选项"连接到主机" / "将当前窗口连接到主机"（两个差不多，点哪个都行）→ 展示已配置好的主机；也可以输入 `ssh username@host -p port` 这样一串命令来添加新的 SSH 主机——username、host、port 就是租服务器时供应商给的三个信息。

    * 连接后提示输入密码——和终端里的操作一模一样；输入密码登上去，左下角会告诉你正在远程服务器上进行编辑；打开命令面板、从里面打开一个终端——这时和你在自己的终端里远程连接到这台服务器是一样的。

* **打开文件夹才算真正开始**

    * 到这一步为止和终端连接还没有区别——VS Code 还不能确定你要在哪个文件目录下工作；再选择一个（远程服务器上的）文件夹去打开，它就把这个文件夹里的所有文件读取出来、列在左边的资源管理器里——过程和本地使用 VS Code 一模一样，只是这些文件实际都在远程服务器上；此后就可以像在自己本地机子上那样在远程服务器上工作。

* **文件操作与扩展**

    * 上传：从本地文件夹把文件拖到左边这一栏；下载：选中文件右键点击"下载"；查看：直接点它——甚至可以同时打开多个终端。

    * 复杂操作（比较两个文件、代码高亮、代码的智能提示）靠扩展：到扩展商店搜索大家常用的插件，安装起来就能用——如装一个 Markdown 查看器插件后，左边原始文本可在右边渲染成排版好的样子；也可以根据自己的需求自己编写扩展。

### Xshell 与 VS Code 对比

* **两个主流远程控制工具**

    * **Xshell**：一款集成式的软件——命令行、文件、程序运行，所有的远程控制它都能做；定位是商用的、专业的付费软件（有没有免费版长文未说明）；本身闭源、没有插件支持，好处可能是自带的一些功能比较强大。

    * **VS Code**：本身只是一个编辑器，里面有各种各样的插件可以支持远程控制；免费，提供一系列插件接口，插件由用户社区群策群力贡献。

* **入门建议**

    * 对初学者、刚希望入门图形学研究、或刚买第一台服务器的人来说，之前那些终端操作都有门槛——一开始先用这种带图形界面的远程控制工具比较好；它基本不需要你做太多学习，不会就搜一下"怎么用 VS Code 做某件事"，或在 VS Code 的社区里做些搜索。

### 图形界面与命令行的取舍

* **能用图形界面就用图形界面**

    * 如果有一个图形界面而不是命令行，肯定是图形界面最方便；除了一些非常特殊的情况——比如在命令行里做一个历史查找，会比图形界面更方便。

    * 不用要求自己"一定要锻炼命令行操作的能力""一定要熟悉 Linux 命令"——当你有图形化界面的时候，肯定就不需要原来那些复杂的东西了。

* **vim 要不要专门学**

    * 有了 VS Code 的远程连接，大部分情况下绝对是在 VS Code 里直接编辑文件更方便；但也一定有一些情况是 vim 更方便的——**不需要**为了那些情况去专门学 vim。

    * 原则：看自己在更高频率下使用的、更得心应手的那个工具，去专门熟悉它，而不是把时间花在命令行上；已经学了 vim 也没关系——多多益善，绝对会带来很多方便。

* **这类知识的学习规律**

    * 没有特别复杂的概念，特点是：某一个点，你知道了之后就一直知道；一开始不知道，就得花些功夫查资料——中文的像 CSDN、菜鸟教程都可以用，也可以去外网查 Stack Overflow 这类英文资料；在使用远程服务器的过程中逐渐就会熟练起来。
