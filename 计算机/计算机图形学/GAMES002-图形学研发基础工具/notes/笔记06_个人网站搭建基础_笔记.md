# 个人网站搭建基础

## 一次网页访问的链路

* **浏览器（Browser）**

    * > **定义**：用户唯一能直接看到的 Web 服务接口——网页渲染出的结果、可点击的按钮、可输入的文本框都在它上面呈现。

    * 用户把操作输入给浏览器，剩下的事全由浏览器内部处理：去真正的服务器上取数据、弄清这个网页长什么样、再渲染到本机屏幕上。

* **请求-响应链路**

    * > **定义**：网页本身部署在服务器上（如百度的网页部署在百度的服务器、高校主页部署在高校自己的服务器），浏览器要显示网页，必须向服务端程序发起请求，获取网页长什么样、有哪些元素。

    * 请求靠一套分层的底层机制完成：先由 TCP 建立连接；TCP 上面一层用 HTTP 协议的格式，把所有请求和响应全部包装起来。

    * 每次操作浏览器默默做三件事：建立 TCP 连接；把要请求的数据打包成 HTTP 格式；通过 TCP 把请求传给服务器。

    * 服务器侧的处理：拿到 URL 后解析"根据这个网址该返回给你什么"，执行处理得到结果，再以同样的方式经过网络传回本地浏览器；浏览器拿到 HTTP 格式的响应后，把对应内容渲染出来。

    * 一次 Web 服务从发起到完成可展开为 11 个步骤，展开的都是这条"浏览器 → 服务器 → 浏览器"链路上的细节；页面加载完成后再点一个按钮（如订阅专栏），会再完整走一遍一模一样的流程。

    * > **易错点**：⚠️ 不要以为网页"加载一次就完事了"。页面上的每一次交互——点一个按钮、提交一次搜索——背后都是一轮完整的"浏览器 → 服务器 → 浏览器"请求-响应。

* **框架与 API 的成熟度**

    * 经过多年的发展，无论用什么语言——C++ 也好、Python 也好——Web 服务都有成熟的框架和 API；不需要做任何非常底层的操作，就能完成一个 Web 服务的提供。

完整骨架：

```text
用户操作（点按钮 / 输入网址 / 填文本框）
        |
        v
     浏 览 器
     建 TCP 连接
     把要请求的数据打包成 HTTP 格式
     通过 TCP 把请求发给服务器
        |
        v    （请求经过网络）
     服 务 器
     拿到 URL，解析"该返回给你什么"
     执行处理，得到结果
        |
        v    （响应沿同样的路传回来）
     浏 览 器
     收到 HTTP 格式的响应，渲染出页面
        |
        v
用户看见网页
```

## 前端

* **前端（Frontend）**

    * > **定义**：用户和浏览器之间的可视化与交互部分——布局、字体大小、按钮的形状颜色等可视化给用户看的东西都属于它。

### 原生方案与语言

* **HTML5 与 CSS3**

    * > **定义**：不引入任何框架、只用浏览器原生功能时的可视化方案，由 HTML5 加 CSS3 两种语言（或者说两种格式）结合在一起组成。

    * HTML 的基本格式是"成对的 tag"：一个开标签，加一个带斜杠的闭标签，两个 tag 中间的部分就是这个 tag 的内容；整个 HTML 基本都用这种方式来组织渲染。

    * 浏览器拿到代码后逐个解析：看到 title 这个 tag，就知道这里要放一行字，而且字体要比较大、可能还要加粗；看到 video 这个 tag，就知道要在这里放一个内嵌的视频，视频的具体参数从后续的属性里得知。

    * 纯手写原生 HTML5 + CSS3 现在已经比较过时，基本没有人直接写；但要做网页的简单前端开发，仍需要认识它们。

    * > **提示**：HTML / CSS 的网上资料很多，菜鸟教程对它们做了系统的讲解。

* **JavaScript 与 TypeScript**

    * 运行在浏览器上的语言，负责浏览器里那些复杂的交互功能。

### 框架与工具链

* **Vue 与 React**

    * > **定义**：真正开发时使用的、最著名的两个前端框架，都有成熟的中文文档。

    * 通过 JavaScript 或 TypeScript，再配合这两种框架之一，就能非常容易地做出像 CSDN 那样的界面。

* **Node.js 与 npm**

    * > **定义**：Web 前端的专用包管理工具组合——Node.js 是一种运行时，npm 是其上的包管理工具，用于管理项目里涉及的依赖库。

    * 使用框架，或者使用别人写好的成熟组件库（里面有 button、slider 等各种各样的 Web 前端组件，不必自己手写一个 button）时，就需要它们来管理这些组件库。

    * 这个角色在其他语言里已经见过：C++ 里是 vcpkg，Python 里是 pip 或 conda——干的是同一件事。

* **Node 版本管理**

    * JavaScript 实际上是运行在某个版本的 Node 上的，而 Node 各个版本之间差异可能比较大，所以需要用专用的工具去管理 Node 的版本。

* **项目构建工具**

    * 构建项目时可能用到模板（比如怎么快速做出一个个人主页），这就有项目构建的专用工具来帮忙。

* **入门路径**

    * 推荐顺序：先了解 HTML 的基本功能，然后了解 CSS，最后在这个基础上去接触 Vue、React 两种框架中的一种，做简单的学习。

## 后端

* **后端（Backend）**

    * > **定义**：服务器自己在幕后做的处理——一些特殊功能、网址的解析都属于它；前端把请求发给后端之后由它接手。

* **服务器（Server）**

    * > **定义**：后端部署的、专门处理请求的程序。

    * 例如在百度上点一下搜索，点击过程就是向服务器发送了一条请求；以 Python 语言为例，有 Flask、Django 这样的专用框架来处理。

* **数据库（Database）**

    * Web 服务更复杂一点时才可能有数据库的需求，按自己的情况具体配置：简单的 Web 应用可以完全不用数据库；有时用一些简单的数据库就够了；也有时需要像 MySQL 这样更复杂的数据库。

## 本地 IP 的 Web 服务

* **本地 IP 的 Web 服务**

    * > **定义**：服务地址部署在本地回环地址上的 Web 服务，只有你这台机子能够看见、能够访问它。

    * 基本上都是为项目开发而服务的；可视化是图形学里非常重要的一环，当远程服务器上没法直接开图形界面、没法直接可视化时，用 Web 服务是非常方便的选择。

### 端口转发

* **端口转发（Port Forwarding）**

    * > **定义**：把部署在远端服务器上的 Web 服务的端口转发到本地，相当于这个服务在你本地完成了一次部署。

    * 典型场景：深度学习代码只能跑在远程服务器上（必须用 VS Code 或命令行远程连接），本地运行不了；服务器上又很难打开一个可视化的图形窗口——两头堵死。解法就是在远端服务器上部署一个 Web 服务，再把它的端口转发到本地。

    * 转发过程 VS Code 在远程连接时会自动帮你完成；转发之后，就可以在本地浏览器里打开交互界面，和远程服务器渲染出来的结果做交互。

### 现成框架

* **Nerfstudio**

    * > **定义**：一个 NeRF 相关的 Python 代码框架，基本功能是把远程服务器上的三维数据显示到本地浏览器上。

    * 在远程端重建出三维场景后，框架已部署好 Web 服务，本地打开浏览器就能拖动整个场景、观察这个场景可视化的情况。

    * 还可以在网页端设置可调整的系数或参数，这些参数会和后端的服务器进行交互——在本地网页上点几个按钮、调整几个数值，就可以操纵远程服务器上的三维资产。

    * 框架按需求和语言选：自己用的是哪门语言，就用这门语言下对应的框架——代码是 Python 就自然用 Python 框架；用 C 或 C++ 开发遇到同样需求，GitHub 上也有很多 C/C++ 的 Web 服务库，直接用它们提供的 API，把远程服务器上的结果放到本地做交互、可视化。

* **Jupyter Notebook**

    * > **定义**：本质上是"把 Web 服务放到本地转发"的一种框架，对 Python 开发人员是熟面孔。

    * 对初学者最主要的好处：能把远程渲染出来的图片直接放到网页里显示——不像之前在命令行里，很难直接查看某一张图片。

    * 提供的方便功能：在网页里编写代码、查看图片，还可以和图片做交互——有一些库能在其中显示可交互的对象（好比一个三维物体），直接在网页里拖动，看到更丰富的可视化结果。

### 最简静态服务

* **python -m http.server**

    * > **定义**：Python 自带模块提供的一行命令，只要装了 Python，输入它就能打开一个非常简单的本地 Web 服务：`python -m http.server 7007`。

    * `http.server` 是 Python 自带的模块，不用装任何东西；`7007` 是指定的端口。

    * 在浏览器里输入这个端口的地址，服务会把 Web 服务根目录（即运行命令时所在的目录）下的所有文件全部列出来——此时就已经成功打开了一个 Web 服务；再点击其中某一个 HTML 文件，就能得到一个全新的网页。

    * 目录下有 index.html 时，按惯例服务会直接解析到它、把它作为首页打开。

    * > **易错点**：⚠️ 纯静态的页面，一行 Python 就能伺候；用框架构建的页面光靠静态文件服务跑不起来，必须配上对应的运行时（如用 Node.js 去运行它）。

## 公网 IP 的 Web 服务

* **公网 IP 的 Web 服务**

    * > **定义**：部署到公网、面向互联网上所有用户的 Web 服务，用于把个人主页、博客，或公司、学校的主页放到网上让所有人看到。

    * 公网上的地址有两种形式：一串数字组成的公网 IP，以及日常见到的网址——域名。

### 完整部署方案

* **四样配置**

    * 域名：需要配置你的域名。

    * HTTPS 证书：需要一个安全的 HTTP 协议时，就需要一张支持 HTTPS 的证书。

    * 专用服务器：需要购买一台。

    * Nginx：用它去配一个端口转发，或者说去代理整个 Web 服务的请求。

* 这套完整配置过于复杂，属于更进阶的内容；对图形学相关的需求而言，更常用的是下面的模板化轻量方案。

### 模板化轻量方案

* **主页模板**

    * > **定义**：GitHub 上一类帮你一键生成网页的库，只需要改动一些非常简单的地方，就可以得到一个自己的主页。

    * 常见的项目主页——上面有很多 demo、有一个 GitHub 的跳转链接、可能还有一些可视化的结果——长得其实都很像，都是用同一类模板生成的。

* **GitHub Pages**

    * > **定义**：GitHub 提供的一种特殊服务，原理是 GitHub 把服务器、域名、证书这一切全都包了。

    * 只需要按照 GitHub Pages 的一些要求，简单配置一下自己的项目信息，就可以完成部署；项目主页、文档主页都可以用这种方式来配置。

    * 这基本上是可能涉及到的公网 IP 的主要应用。

## 本地与公网方案对比

| | 本地 IP 的 Web 服务 | 公网 IP 的 Web 服务 |
| :--- | :--- | :--- |
| 部署在哪 | 本地回环地址 | 公网（数字公网 IP 或网址域名） |
| 谁能访问 | 只有你这台机子 | 互联网上的所有用户 |
| 面向场景 | 开发自己的程序时，靠端口转发完成远程服务器上的可视化 | 个人主页、个人博客、项目主页、项目文档、在线 demo |
| 配置负担 | 几乎没有，端口转发 VS Code 自动完成 | 域名、HTTPS 证书、专用服务器，还要 Nginx 做转发代理 |

* 这两种需求基本涵盖了图形学中涉及到的所有网站配置需求：项目要做一个 demo 放到网上给大家看，用公网 IP；本身是很简单的可视化程序、但在远程服务器上没法直接运行显示，要放到本地浏览器上显示，用本地 IP。

* 大部分时候不需要搞清楚其中的细节，直接用自己使用的那种语言下对应的 Web 服务库，就可以简单地完成；面对复杂的需求，才需要了解具体的 Web 服务原理（前端、后端），甚至学习具体的前端语言、后端语言和框架文档，做整体性的开发。

* **微信小程序实例**

    * 小程序开发相当于一个 Web 服务：涉及界面怎么写、前端怎么显示，以及后端连接一个数据库。

    * 一个实际课题的后端就是用 Python 加 Django 搭的数据库，里面有一些管理员支持的功能；这类项目涉及的前端和后端，比端口转发、静态服务这类例子复杂得多。

## 远程三维数据的网页可视化

* **本地查看三维数据的途径**

    * 常用软件：CloudCompare、MATLAB、Blender；这类软件没有办法在远程服务器上打开。

* **远程查看的两种解法**

    * 下载到本地：把点云等三维文件从服务器上下载下来，用本地的可视化软件打开。

    * 远程起 Web 服务：直接跳过下载这一步，在远程服务器上部署一个 Web 服务，把这个服务转发到本地端口，最后在本地浏览器上打开。

* **3D 高斯**

    * 一种类似点云一样的三维物体对象；有现成代码能够直接在远程服务器上部署一个 Web 服务，部署完点击主页就可以看到它的显示——显示在本地浏览器里打开，并且可以对它做一些交互、查看。

* **普通 mesh 与点云**

    * 有现成库可以完成普通 mesh 或点云的网页可视化；通过一个简单的调用产生端口转发，就可以在本地浏览器里打开一个显示。
