## Git 版本管理入门：从"最终最终修改版"到第一次提交
> 对应块：BLK06 | 覆盖分集：P04上 | 块标题（分集名）：《Git+GitHub》

### 从小组作业的 PPT 说起

先从一个你们多半亲身经历过的场景讲起：小组作业，要共同修改一份 PPT。大家在微信群里互相把自己修改完的文件传到群里，结果就会出现一个情况——群里躺着一堆这样的文件："小组PRE.ppt"、"小组PRE修改版"、"修改版一"、"最终修改版"、"最终最终修改版"……

这就是没有版本控制软件时，我们做共同协作（甚至哪怕只有你自己一个人在反复改一个东西）最粗暴的方式：准备很多很多个文件，这些文件之间各自有一点小修改。它的缺点非常直接：首先从文件名上基本得不到太多信息——盯着这一系列文件，你不知道两个版本之间到底有什么区别，甚至有时候连哪个是最终的最新版都分不清。哪怕只是想追溯自己每次修改的版本、想对"我到底修改了哪些部分"这件事有掌控，靠堆文件也很吃力。而一旦出了岔子——比如你的修改和别人的修改不同步，或者出了错误需要回溯对比——就非常麻烦。

所以我们需要引入 git 这样一个版本控制软件。它做的事情，正是针对上面这些困难的点：

> **定义**：版本控制帮你搞清楚版本和版本之间文件到底有哪些变化；帮你追溯这些变化；并且在你需要做回溯和对比的时候，替你处理。

### Git 是什么，两大功能是什么

git 本身是一个软件包，功能就是版本控制。它是一个开源的分布式版本管理系统，可以非常有效、非常高速地处理从非常小的项目到非常大的项目的版本管理。它的来头也不小：最初是 Linus 为了帮助管理 Linux 内核而开发的一个开源版本控制软件。

这里先给你们一个心理上的宽慰：git 的功能基本上是比较强大的，但我们平时用不到它的所有功能。用一个复杂软件的时候，不一定要成为这个软件的专家——你只需要让它尽可能适合你正在处理的工作、尽可能辅助到你目前手头的事儿，就可以了。我们要学的功能其实比较简单。

git 最大的两个功能，可以简单概括为：第一个是版本管理，第二个是能够允许多个人同时协作，去做版本之间的合并和处理。

#### 版本管理：自动追踪每一处修改

第一个功能是版本管理，核心是自动追踪每个文件的修改。这里有一个命令行控制台的例子：输入 `git status` 这个命令，让它告诉我目前我这个代码仓库——或者说这个代码文件夹——下面的情况是怎么样的。它会告诉你三条信息：

- 第一条，告诉你在哪个分支。分支是之后会学到的概念；
- 第二条，告诉你哪些文件已经暂存了、之后就可以做提交。比如绿色的就是：我已经修改了这些文件，并且我把我的修改保存下来了；
- 第三条，红色的：哪些文件和之前的版本相比已经发生了变化，但这些变化你还没有记录下来。

版本管理还包括追踪每个版本的差异，相当于我们可以人为地定制很多版本出来。每一个黄色的 commit 都代表一次提交，每个提交可以简单理解为一个版本；每次提交都有一个简单的说明，这是你提交的时候写下的注释。版本和版本之间是可以做对比的：比如第一个版本是 10 月 14 号七点，第二个版本是 10 月 14 号 12 点，当你使用 git 的对比功能时，它就会在命令行向你汇报所有文件的修改——相当于直接对比这两个版本。

看对比结果有个简单的口诀：版本 A 相对于版本 B 新增的部分，会用绿色显示出来；版本 A 相对少掉的那一部分，用红色显示出来。

所以 git 的版本管理功能概括下来就是：追踪文件的差异，让你能记录文件版本，并且自动追踪每个版本的区别。

#### 分布式协作：合并交给 git

另一个功能是分布式协作。意思是同一个代码仓库，可以有不同的人一起协作修改。而"分布式"是说，我不需要存全部的文件——可能每个人手头只存部分的版本，最终大家把各自的修改汇总到远程一个集中的地方时，git 就会自动帮你计算你们之间版本的差异，完成一些合并操作，或者提交、修改、覆盖等等的操作。

### 分支：版本历史的"世界线"

git 还有一个分支的概念。它更像是我们的一个"版本"这样的概念，但区别在于：图里的每个小圆点，都代表你的代码所有文件的一个状态。比如这个状态和这个状态之间可能有一些微小的修改，它们分别形成了两个版本——版本一、版本二、版本三。

那版本一和版本三之间的区别怎么对比？实际上是把"一和二的区别"加上"二和三的区别"组合在一起。也就是说，在 git 的版本历史上可以找到一条修改的线路：一开始是一，加了一点东西变成二，再加一点东西变成三。

而分支讲的是另一种情形：我在版本一上做了某一个修改，来到了一个新的节点；同时，版本一又做了另一个修改，来到了另一个节点。相当于从版本一派生出了两个节点，这两个节点对应的就是不同的——你可以叫它世界线也好，或者简单地认为它就是一种分支也好——从本来一致的版本一，分裂出了两种不同的可能性。这两种可能性之间本身是互斥的，因为它们都基于相同的版本，而不像刚才那样是一个线性下来的过程。这就是分支：通俗地理解，就是我们的世界线上发生了一次分裂。最后就会像图里看到的：可以把下面这条分支叫做 dev 分支，把上面这一条分支叫做 master 分支。

```text
            o----o----o      <- master branch (stable version)
           /
    o----o
           \
            o----o----o      <- dev branch (features in development)
```

图中每个圆点都是一次提交，代表所有文件在那一刻的完整状态；两条线都从同一个版本派生出来，各自演化、互不影响。

分支使得我们可以方便地实现这样一个功能：代码有一个稳定版和一个正在开发中的功能。你肯定不希望开发者一动手，原来稳定版的那些功能都没法用了。用 git 来做代码的版本管理，实际能实现的事情就是：同时维护一个 master，它是稳定版；想新加一些功能的时候，开一个新的分支，比如这里开一个 dev 分支——叫开发者或者叫 develop——在这个分支上做一些特殊的修改。这些修改并不会影响到 master 分支上的结构。未来某一天，当我觉得 dev 分支上的修改已经成熟了、稳定了、通过测试了，就可以把 dev 分支的所有内容合并到 master 分支里。这就实现了我们的版本管理。

所以简单来说，版本管理和刚才说到的"追溯文件修改"有一个更大的不同：版本管理对应了分支概念，分支概念对应了一系列文件的修改——我记录了这个修改、这个修改，并且有另一条线路是那几个修改——它可以管理这些连续的修改，并且形成最终的分支。

> **提示**：这里可能还有点抽象，后续我们讲一些更具体的例子。

### 命令行、git gui 与 GitHub Desktop

git 既然是个软件包，我们肯定要有一个使用方法。因为 git 本身是开源的，社区实现了很多种 git 的辅助工具或者图形化的界面。大致有这么几种形态：

- **命令行**：在 git 官网上可以下载、直接用命令行运行的 git，这是和 git 最直接的交互方式；
- **git gui**：git 提供的图形化界面。在 Windows 上下载 git，应该是会自带一个 GUI 的，也就是自带一个图形化界面；
- **GitHub Desktop**：通过 GitHub 下载的一个桌面的管理软件，上面也提供图形化界面，可以让你进行一些 git 操作。它其实就和你在网页上打开 GitHub 有点像，只不过它操作的是你本地的一些文件。

安装上，命令行的 git 有个简单的安装方法，以 Linux 为例：git 已经是一个非常知名的包了，所以基本上直接运行安装命令，就可以把 git 给装上。

装好之后打开命令行，输入 `git`，它会告诉你一些基本的使用方法，列出很多很多的子命令：比如 `git clone`、`git init`、`git add` 这些。大家平时使用过程中可能也遇到过一些子命令。我们这里只要掌握它最简单的几种，就能完成一些基本的 git 操作。有一些比较复杂的命令，我自己平时也基本上不会用到；更复杂的、涉及分支之间的操作（比如合并），或者你需要对 git 的某些特定操作进行一些微调时，才会涉及到那些特别复杂的 git 操作。

### 工作区、暂存区、版本库

在讲那些复杂操作之前，我们可以用一个最简单的、抽象的模型，来介绍一下 git 的原理：为什么 git 能够做文件修改细节的追踪，能够做版本管理？

首先是这样的：git 会指定一个目录作为你的**工作区**——这个工作区里的所有文件，都是我要关心的、需要去追踪修改、需要记录版本的文件。然后 git 会在工作区里生成一个专用的文件夹，这个文件夹一般来说是隐藏的。比如在 Mac 或者 Linux 上，一点开头的文件夹都是默认隐藏的，你一般来说看不到它，但是可以在命令行输入 `ls -a`，看到全部的点开头的隐藏文件夹。这个 `.git` 文件夹就是 git 用的隐藏文件夹，它把所有的信息都存在里面，作为我们的**版本库**，里面会存版本变化的一些信息。而 `.git` 里还会有一个新的文件夹，它叫 index，这个东西是作为我们的**暂存区**。

这里有一个非常重要的概念划分：什么叫工作区、什么叫版本库、什么叫暂存区——只要搞清楚这三个概念，基本上就可以明白 git 到底是怎么一回事了。

> **定义**：**工作区**，指的就是我们这个目录下面的这些文件——相当于你在编辑器里打开的文件，或者说你在文件夹里能直接看到的这些文件，就叫工作区。
>
> **定义**：**版本库**，可以理解为：每次提交一个版本的时候，这个版本把所有工作区文件全部存了进去。想象一下，我有一个 V1.0 的版本，那 V1.0 里可能就有我全部的文件——相当于把整个工作区的一个拷贝、一个副本存到了 V1.0 里；然后我再做一些修改，有了 V1.2，又可以从一个新的版本存进去。V1.0、V1.2 之间就构成了一个版本库，我们可以随时从版本库中提取历史的代码。
>
> **定义**：**暂存区**，针对的是这样一个中间状态：文件已经发生了修改，git 也知道你的文件被修改了，但 git 还没有记录这些修改。暂存区就是我让 git 先记住我的修改的地方——我们做的所有改动，可以通过 `git add` 存到暂存区中。

暂存区有两句话要说清楚：它不像版本库，因为它里面只是把你的临时修改保存到里面去；同时它也不是工作区，因为它其实是一个虚拟的概念——相当于它是追溯你的一些文件的改动，而不是实际上存了一份改之前的文件或者改之后的文件。

| 区域 | 是什么 | 特点 |
| :--- | :--- | :--- |
| 工作区 | 目录里能直接看到的文件 | 你实际编辑的地方，改动 git 能感知到 |
| 暂存区 | `.git` 里的 index | 虚拟的、临时的概念，只记录改动本身，由 `git add` 写入 |
| 版本库 | `.git` 隐藏文件夹 | 存每一次提交的完整快照，可随时提取历史代码 |

整个流程串起来就是：我在工作区里改文件，比如我改了一个文件，把它存到暂存区，git 就知道我修改了这个文件，并且暂时记录下这个文件的改动；当我暂存区里的改动足够多——比如我修改着修改着觉得，我应该变成 V1.3 了、应该可以升级了——就把暂存区里面的所有修改提交到版本库里，形成一个新的版本。于是这些修改就帮助 git 记住了：我从 V1.2 发生了这么多变化，形成了 V1.3。这个时候你会清空你的暂存区，形成你的一个新的版本库。这就是 `git commit` 做的事情。

> **结论**：最基础的两种命令，`git add` 可以理解为暂时的提交（暂存），`git commit` 可以理解为正式的提交。

### 动手建仓库：git init 与 git status

这样讲可能还是非常抽象，我们来看一个真实的例子。比如我打开了桌面上的 GAMES002 文件夹，想在里面做实验。第一步，新建一个文件夹：

```bash
mkdir temp
```

这一句就可以在当前目录下，新建一个名字叫做 temp 的文件夹。有了 temp 这个文件夹之后，我们就可以在里面新建一个 git 工作区了——这一步相当于告诉 git：这整个 temp 文件夹下面的所有内容，都是我要关心的内容。命令是 `git init`：

```bash
git init
```

它会告诉你：我生成了一个新的空的 git 仓库，在这个路径下面，并且版本文件其实保存在 `.git` 这个子文件夹里。我们一般来说是看不到它的——刚才你看这个文件夹里什么都没有，对吧？但其实这个文件夹是存在的。当你 `ls -a` 的时候，就会看到这里有一个 `.git` 文件夹；你甚至可以看看里面有什么东西——一大堆乱七八糟的东西。反正，我们已经初始化了一个新的空的 git 仓库了。

这个时候 `git status` 可以查看当前工作区的状态：

```bash
git status
```

它会告诉你两件事。第一，我们在 main 分支上——这是它的一个默认分支，可以先不用管；第二，还没有 commit 需要提交：毕竟我们是一个空的文件夹，还没做任何改动，还没有办法形成一个版本，所以它告诉你什么东西都不需要提交。如果你用的是中文的 git，它会告诉你"位于分支 master""尚无提交""没有文件要提交"，是一个意思。

### 让 git 记住修改：git add 与 git diff

空仓库看不出什么名堂，我们新建一个文件试试。用上节课学到的命令，往 a.txt 里写入一行内容：

```bash
echo something > a.txt
```

这样会在当前目录生成一个文本文件 a.txt，里面有一行 something。这时候你就会发现，我用的这个终端，提示从一个圈变成了一个叉——从绿色的一个圈变成一个红色的叉。意思就是：你现在的工作区发生改动了。也就是说，git 其实能知道你修改了文件——我这里的行为是新建了一个叫做 a.txt 的文件，git 就知道了。

知道了之后，我们再输入 `git status`，它就会告诉你两件事：首先，git 知道 a.txt 被修改了；其次，这些修改 git 没有去暂存它——git 只是知道修改，还没有把这些修改给记录下来。

> **定义**：什么叫"尚未跟踪"、"修改尚未记录"？就是工作区里文件的内容，和版本库里的记录不符合。我们是一个空的仓库，所以版本库里的记录也是空的；只要当前的工作区非空，它就会告诉你"和版本库的记录不符合"，但这个改动并没有被记录。

这里可以做个小实验。我把 a.txt 删掉，大家看一下：git 的状态又变回一个圈了，`git status` 也会告诉你，回到了一开始的空的状态。这是什么意思呢？因为 git 只能知道你的文件被修改了，但是它没有记录。所以如果你把这个修改恢复回去的话，git 就不会知道——它会发现你现在的工作区，和它知道的上一个版本（也就是它知道的那个全空的状态）是一致的，于是告诉你：当前的工作区和之前 git 知道的那个版本没有变化，一切正常。

> **易错点**：git"知道你改了"和"git 记住了你的修改"是两回事。没有暂存的改动，随着你把文件改回去，这条修改就不存在了——git 不会留下任何痕迹。

那么我们怎么样去跟踪当前改动呢？其实很简单，就是加一句 `git add`。我们再把刚才的 a.txt 给创建出来——这时 git 告诉你，这个东西它是一个未跟踪的修改。我们想要把 a.txt 的出现记下来，就可以用一句：

```bash
git add a.txt
```

右边终端的状态还是一个叉叉——这是因为你目前确实还是修改了，和上一个版本之间还是有差别。但是当你再 `git status` 的时候，它会告诉你：a.txt 变成一个绿色了。绿色的意思就是它已经被暂存了，这条修改已经被记录了，a.txt 现在已经在暂存区里。

接着让 a.txt 再发生变化。原来只有一行，我通过这个语句再给它加一行：

```bash
echo something >> a.txt
```

现在可以看到 a.txt 变成两行的 something 了。这时候你再看 `git status`，它就会告诉你两件事：首先，暂存区里有一条记录——我新建了一个只有一行的 a.txt；其次，暂存区里的这条记录，和现在 a.txt 的状态也不一样，a.txt 又被修改过——对应的就是我在暂存之后新加的那一行。

那如果想看"距离这次暂存的时候，我的 a.txt 到底发生了什么变化"，可以通过 `git diff` 来查看，或者 `git diff a.txt` 可能更具体一点：

```bash
git diff a.txt
```

它会显示一个带颜色的 something，告诉你这里加了一行；原本一样的地方，它就会用普通颜色来显示。读出来就是：第一行 something 是原来就有的、后来也还在；第二行 something 是原来没有的、后来新增的。

到这里大家要注意：我们都只是在做工作区的修改和一个暂存区的修改，还没有记录任何的版本——版本库一直是空的，并且我们没有提交过任何版本。

### 沉淀成一个版本：git commit 与 git log

假设我们现在已经做了一系列改动——比如我现在又加了一行，然后我把新加的这一行给记录下来（再 `git add` 一次），新加的这行确实被记录下来了。这时候假如我说：我已经改好我的代码了，我需要一个新的版本——就可以通过 `git commit` 产生一个提交。

这个提交的意思是：让我当前工作区的所有文件的一个快照——或者说它的当前状态——全部被记录到版本库里去，它会作为一个新的版本出现在版本库里。这样以后，我就随时能够和这个版本去做比较，或者基于这个版本做一些恢复操作。

```bash
git commit -m "新增了 a.txt 这个文件"
```

一般来说 commit 会加一个 `-m` 参数，在后面写一句 message，就是关于这次提交的一个注释——相当于之前看到的每个 commit 下面跟着的那一行说明。这个说明一般来说不用写很长，我们可以简单地讲一下你到底做了一个什么样的修改。

提交之后，git 会告诉你几件事：首先，我产生了一个新的 commit，这个 commit 有一个编号——就是那一串十六进制的码——并且它的说明就是刚才打的那一行；然后它会统计当前的版本比起上一个版本有哪些变化：有几个文件变动，几行新增、几行删减；最后告诉你新增了哪些文件。

这时候我们再查看一下状态：右边终端的状态变成了一个圈，意思是你和最新的版本已经一致了——我们的工作区和版本库的最新版本已经一致了。`git status` 会告诉你没有新的东西要提交，并且 working tree 是一个 clean 的：我和上一个版本是一模一样的，没有任何的修改。

那这个时候我们其实就有一个历史版本了，要怎么去查看这个历史版本呢？最简单的方法就是用 `git log`：

```bash
git log
```

这里有一个简单的 log 信息：首先是你这次 commit 的编号，然后告诉你作者是谁、日期是什么，最后是关于你对这个版本的一个说明。这就是一个简单的查看版本历史的方法。如果我想知道某个版本具体的情况的话，其实是根据这个编号可以进一步的查询。

> **提示**：`git log` 会打开一个类似 vim 那样的全屏窗口的界面，它会占据你命令行当前窗口的全部内容；按 Q 就可以退出。

### 常用命令盘点：四个"增"，一个"删"

最后总结一下。我们把刚才涉及到的功能（其实刚才没有讲到的功能也都列出来了）摆在一起，其中我们经常使用的是前面这四个：

| 命令 | 作用 |
| :--- | :--- |
| `git init` | 初始化，新建一个 git 工作区 |
| `git add <文件名>` | 把这一个文件的改动存进暂存区 |
| `git add .` | 把所有文件的改动存进暂存区 |
| `git commit -m "<说明>"` | 提交一个新的版本，并附带上你的说明 |

这四个其实都对应着你"增加"什么东西：增加一个暂存区的内容，或者增加一个新版本。下面几个命令对应的则是"删减"。想要真正理解删减类命令的说明到底是什么意思，就需要掌握前面讲的三个概念——工作区、暂存区、版本库。

这一讲展开演示的是这一个：

```bash
git checkout -- <文件名>
```

它的意思是：我的工作区和我上一个版本之间发生了一些改动，然后我通过这一条命令，把我工作区的这些改动，恢复到我最新版本的一个状态。

举个例子。我们在仓库里又新建了一大堆文件，比如 b.txt 和 c.txt——而我上一个版本其实只有 a.txt。假设你做了一大堆修改，或者误操作搞了一大堆无关的文件，总之这些 b.txt、c.txt 都是垃圾文件，都不需要它。我想要把工作区的状态恢复成最新版本的状态，就可以用一个 `git checkout --`，后面填一个文件名，意思是把这个文件恢复成上一个版本库的状态。因为 b.txt 在上一个版本库里不存在，所以这个操作会把它直接删掉。

记住这一条就够了：git 的一切操作，都围绕工作区、暂存区、版本库这三个概念展开——改动从工作区经 `git add` 进入暂存区，再经 `git commit` 沉淀为版本库里的一个版本；想反悔的时候，再从版本库出发把工作区恢复回去。

## Git 进阶：撤销、忽略与 GitHub 远程协作
> 对应块：BLK07 | 覆盖分集：P04下 | 块标题（分集名）：《Git+GitHub》

先从一个最常见的"翻车"现场说起：你想把某个文件恢复成上一个版本的样子，敲了 `git checkout 文件名`，结果 Git 不买账——因为这个文件在上一个版本里压根不存在。比如新加的 B.txt，上一个版本里没有它，针对它的 checkout 就用不了。这时候最简单的办法，是加一个点：`git checkout -- .`。

这个点的意思就是"所有文件"。所以这样写，其实是说：把当前工作区的所有文件，全部恢复成上一个版本的样子。

### 撤销修改与取消跟踪

输入这条命令之后，你会发现一个有意思的现象：那两个新文件（B.txt、C.txt）还原地待着，但如果你对 A.txt 做过任何修改，它就会变回去。那这两个文件为什么会留在这里呢？因为 checkout 做的事，是从工作区丢弃掉你的改动——它管的是 Git 已经有记录的文件；B.txt、C.txt 这种新文件 Git 从来没见过，自然原样留在原地。

> **易错点**：`git checkout -- .` 恢复的是"改动"，不是"文件的存在"。未跟踪的新文件它一概不管，想让它们消失得用文件系统自己的删除。

关键是另一头：如果你的改动有记录——比如说进了暂存区——你就可以针对它做恢复。来做个实验：把这两个文件加到暂存区里，现在暂存区里有 B.txt 和 C.txt，那要怎么把它们撤销掉、从暂存区里删除？用这条：

```bash
git rm --cached <文件名>
```

执行后它会告诉你：你把这个东西从暂存区里删掉了。再看 status，它又变回一个没有改动、没有记录的状态——文件本身还在工作区，只是 Git 不再跟踪它的改动。

再看恢复的另一半。恢复到上一个版本的状态之后，假设我们这时又对 A.txt 做了一次修改，比如给它再加一行进去。要把它恢复回去，就是用刚才说的 checkout，加一个文件名：

```bash
git checkout -- A.txt
```

你会发现：虽然刚新加了一行，但 A.txt 并没有变成三行，还是两行——因为这条命令把 A.txt 整个恢复了回去，新加的那一行也一起没了。

这一组命令里，我自己最常用的就是 `git checkout -- .`——把所有修改全部撤销这一个操作。最下面那几条删除语句，我平时用的也不多，而且它们蛮容易混淆的：比如你好久没学 Git 的使用，隔了好一段时间，想做一个类似的删除操作，就很容易不知道该用哪一条。所以一般来说，做 Git 的删除操作时——特别是那些删除语句——最好先确信这条命令到底有怎样的效果。具体效果可以通过搜索来弄清楚，确定它能达到你想要的效果之后，再去执行。因为"从什么区里取消掉什么东西、或者删除掉什么东西"，确实是一个蛮容易混淆的概念：如果你不是特别理解暂存区是什么、工作区是什么，你可能会以为它是一种效果，但实际上它是另外一种，这时就会出问题。像 CSDN 这类教程一般都会给你具体的例子，让你直观感受一下命令的真实效果——查明白再动手，最稳。

> **提示**：不考虑远程协作、只考虑本地自己用的话，最常用的就是前面那四种基本操作；删除类命令用到时先查后用，别凭感觉敲。

那费这么大周章，把工作区、版本库都存下来之后，有什么用呢？基本的用法就是：可以看两个区的文件差异；可以看文件的版本历史、所有版本历史；或者逐行地看一个文件的改动。这些都是比较有用的功能。

### .gitignore：让 Git 忽略无关文件

项目里还有一个经常遇到的功能：你可以设置 Git 到底不关心哪些文件。来举个例子：往 tmp 文件夹下面随便加一个新文件，Git 都会注意到这个新文件的产生，并且告诉你版本不一致了。这时你要是 `git add .`，那不好意思，这个新文件也会被一起加进暂存区。但有时候它仅仅是一个无关的东西——或者是你的数据，或者是你的缓存，或者是别的什么临时文件——我们不想要 Git 跟踪它的变化。这时就需要给 Git 设置一个 `.gitignore` 文件，Git 会按照里面指定的规则，去忽略掉这些无关的文件。

`.gitignore` 长什么样？我找了一个比较知名的代码库的例子，基本上就是一行一条忽略项：直接写一个文件夹名，意思就是忽略整个 lib 文件夹下的所有内容，或者忽略整个某个文件夹下的所有内容；还有一些特殊的星号，可以用作正则表达式式的匹配，或者说文件路径的通配——比如所有以 `.egg-info` 结尾的文件夹，全部被忽略；所有以 `.egg` 结尾的文件，全部被忽略。Git 会从上到下、从前往后扫描这个文件，来确定你到底有哪些文件是不关心的。

还有一些更复杂的规则，比如前面加一个感叹号，其实是反效果。一个典型的场景：我不想跟踪所有和 download 有关的文件夹，但其中有一个例外——以某个前缀开头的 download 文件夹是我关心的——这时就给这一条前面加一个感叹号，它就可以起到这样的效果。基本上大家可以根据自己的需要来：项目中确实遇到了需要忽略无关文件的情况，再去网上搜索资料，看怎么设置这个规则文件，就可以实现 Git 一个比较方便的忽略。

### Git 和 GitHub 到底是什么关系

Git 这边介绍完，我们再来介绍 GitHub。Git 和 GitHub 的关系，我想想，可以说是没有什么关系——虽然它们名字长得很像，但其实是两个完全不一样的东西。Git 是一个开源的、人人都可以用的软件，它做的是版本控制；GitHub 是一个提供了网页服务的网站，它可以给你提供远程存储仓库的服务。只不过 GitHub 基本上是基于 Git 的：它管理仓库的那些规则、它的版本控制，都是基于 Git 的，所以它其实会叫 GitHub 这个名字。但使用上来说，GitHub 并不是一个 Git 的升级版或者替代品；相反，它是一个和 Git 相辅相成、互相辅助的远程的东西。

> **定义**：Git 是做版本控制的开源软件；GitHub 是基于 Git 的、提供远程仓库托管服务的网站。两者不是替代关系，而是相辅相成。

那具体来说是什么情况呢？我们目前的版本管理可能都是在本地：本地建一个文件夹，在里面创建 Git 仓库。但有的时候我们是希望做一些协作的。比如你希望和你的微信好友、或者你的同事一起干活，大家都是线上状态，通过微信这类软件联系——总不能每有一个新版本，就把整个项目打包、我发给你、你再发给我吧？一般来说有两种路子：要么你和同事用同一个服务器，可以看到服务器上公共的代码——这其实还是一种"本地"的情况；要么你们两个没有什么公共的存储文件系统，那么和他人分享合作、甚至和网上的开源贡献者分享合作，就需要一个分布式的平台：网站本身、或者说平台本身，给你提供仓库的存储服务。这个其实就是 GitHub。

类似的服务还有一些替代品，比如国内有 Gitee，另外还有 GitLab，它们都是类似的。这里我们简单以 GitHub 为例来介绍。GitHub 简单来说就是：你可以把你的仓库存到远程服务器上，它帮你托管这个仓库，并且提供一些更加方便的功能——从文件浏览，到分支管理，到一些其他比较复杂的操作，再到开源社区的交互、贡献，它都有支持。

### 从远程下载代码：git clone

经常用到的、最基本的一个功能，就是从网上下载代码到我的本地。GitHub 上有一些开源的仓库，你可以用 `git clone` 把远程仓库下载到本地。仓库的下载界面会展示这个仓库 clone 的网址；在命令行里输一个 `git clone <网址>`，它就会把网址对应的那个仓库，下载到当前文件夹。

clone 有两种方式，可以稍微做一下了解。第一种是用 HTTPS 协议去 clone。它的特点是：只要这个仓库是开源的，你就可以克隆、下载，克隆本身是不需要权限的；下载过来你也可以任意地改它，但是你不能把这个改动提交到 GitHub 上——你本地做了新版本，想把新版本推送到 GitHub 上，这是不行的。因为它需要检查你的权限：你必须要是这个仓库的使用者或者协作者，才有资格把本地的代码交到远程上去。

但这样就很不方便了。假如这个仓库真的是你自己的，你要把本地的新版本上传到远程服务器（也就是 GitHub），每次都要自己再输一遍用户名和密码——毕竟命令行不像浏览器，命令行没有一个所谓"登录"的东西，GitHub 每次都会问你，这就非常麻烦。所以对于自己的仓库，我们就可以用 SSH 协议来克隆。用 SSH 克隆下来的仓库，是直接根据 SSH key 去做权限检查的，这样推送就可以直接进行、无需验证。具体怎么设置，网上有非常多的教程，有需要的话搜一下"GitHub SSH key"就可以。

| 对比项 | HTTPS 克隆 | SSH 克隆 |
| :--- | :--- | :--- |
| 克隆条件 | 仓库开源即可，不需要权限 | 需要先设置好 SSH key |
| 本地修改 | 可以任意改 | 可以任意改 |
| 推送回远程 | 不行——要检查权限，必须是使用者或协作者，且每次要输用户名密码 | 可以直接推送，无需验证 |
| 适合场景 | 克隆别人的开源仓库 | 自己的仓库、日常推送 |

### 本地与远端的通信：fetch、pull、push

接下来是一些涉及本地和远端通信的功能。第一个是 `git fetch`，它是把我本地的版本库，同步成远端的版本库。这是什么意思呢？就是我们只做版本库的一个改动：相当于远程有一个新版本，我可以用 git fetch 把这个新版本加入到我的版本库，但它并不会实际修改我本地的代码。相当于我只是先把它加进来，后续要做一些额外操作、或者做一些对比的时候，我就可以跟我版本库里远端的那个最新版本去对比。

第二个是一个进阶版：`git pull`。它不仅做了 git fetch 做的事情——把远端的版本库进行同步——还会多做一件事：把远端的最新版本和本地的最新版本做一个合并。这个合并具体怎么做的，后面会介绍到。

再就是反方向：你可能有时候需要把本地传到远端，这时用的就是 `git push`。这个时候你需要有这个仓库的所有权或者使用权。

```text
fetch / pull ：  GitHub 远程仓库 ─────►  本地仓库
push         ：  本地仓库 ─────►  GitHub 远程仓库
```

读图：fetch、pull 都是把远程的东西往本地拿——fetch 只把新版本加进版本库、不动工作区的代码，pull 在此基础上还要多做一步合并；push 则是把本地的版本推上远程。

### 把本地仓库搬上 GitHub

就拿刚建的仓库做例子：我在本地建了一个空仓库，加了一些东西，commit 了一些修改，这时 git log 里已经有一个版本历史了。我想把我整个仓库，加上我的版本历史，一起打包传到 GitHub 上，应该怎么做呢？其实比较简单：先在网页上直接创建一个空的仓库，你就会得到一个链接、一个地址；然后在本地通过下面这两行——第一行是说，让本地的这个仓库和远程这个仓库连起来；第二行是说，把本地的这个分支推送到远程上。

```bash
git remote add origin <远程仓库地址>   # 第一行：让本地仓库和远程仓库连起来
git push -u origin <分支名>           # 第二行：把本地的分支推送到远程上
```

这个时候你再在 GitHub 上刷新你的页面，就会发现：你本地的所有代码，已经传上去了。

刚才说的是你亲手创建的仓库。如果这个仓库不是你自己的、是其他人有的，那要让我本地的修改能同步到远程，就需要一些操作：首先，你需要有这个权限——可能是仓库的所有者交给你的权限；第二，你需要用刚才说到的 SSH 协议，把它克隆到本地；第三，在本地产生新版本之后，用 git push 提交到远端做修改。这些就是一些基本的操作了。具体来说，网上有非常多的教程；遇到具体情况——比如你用的不是 GitHub，而是 Gitee、GitLab 这类平台——其实都可以去搜索，会有具体的教程介绍到底要怎么使用。

### 在网页上对比提交：单提交详情与 compare

这里再讲一个我平时会用的东西：GitHub 网页其实是支持 commit 之间的比较的。什么意思呢？我们先看本地怎么做对比——其实是蛮麻烦的：你首先需要知道一个提交、一个版本的编号，然后用 `git diff` 输入这个编号，可以开启一个小的界面，列出你所有的文件的变化。但这种肯定不如可视化的方法直观、清晰，毕竟在命令行操作，还是会有很多不方便、不熟悉的地方。

实际上 GitHub 的网页端，提供了一个 git commit 之间方便的比较，官方也有教程说明。仓库的提交历史会列出你修改过的所有历史：比如最早有一个 3 月 7 号的提交，说明是初始化了整个仓库；最新的这个是 4 月 12 号的提交，又有它自己的说明。想看每一个提交发生了什么，点它右边那个按钮，GitHub 就会给你列出来这些文件之间到底发生了什么：左边列出最基本的详情——哪些文件发生了变化；右边则是这些文件里具体发生了什么样的变化，特别是每行的增删，都清楚地列在里面。这相当于我们本地用 git log 加上 git diff 来查看的功能，在 GitHub 这种平台上，可以用一个更好的可视化方法显示出来。

那如果想批量比较两个版本呢？看单个提交的细节，你能知道这个版本和它的前一个版本之间有什么差别；但如果我想比较 4 月 12 号的版本、和一个 3 月 12 号的版本之间到底有什么差别，就用刚才说到的 compare。做法是：把想比较的两个 commit 的索引——也就是那串代码——的前 6 到 7 位复制过来；网址前面那一段，从 http 到你的仓库名，点进你自己的仓库你就会有；然后在网址后面加一个 compare，第一个位置填其中一个版本，第二个位置填另一个版本，中间用两个点连接：

```text
https://github.com/<用户名>/<仓库名>/compare/<版本一>..<版本二>
```

输入这个网址，它就会告诉你：它正在 comparing changes——在比较两个分支、两个版本之间的差异。左边显示的是 3 月 12 号的版本，右边显示的是 4 月 12 号的版本，我们可以发现这些区别；可能有一个非常长的文件修改的说明，可以在说明里做筛选，看看哪些文件到底具体发生了改动。这样在浏览器里可视化地浏览，会比较直观一点。

总而言之，GitHub 提供了非常多的 Git 可视化的支持，我觉得这个还是蛮好用的。所以有时候，哪怕你没有远程协作的需要，也可以把自己的仓库放到 GitHub 上——哪怕不公开你的仓库，作为一个私人仓库放在你的 GitHub 上——去利用它的界面，做一些可视化或者做一些比较。也可以用 GitHub Desktop 这个软件，在本地做一个可视化的查看，和网页端的原理是类似的。总而言之，GitHub 既可以支持本地和远程仓库之间的上传和下载，也支持这些可视化的操作。

### 分支与合并：git merge 与冲突标记

最后来讲一下 Git 在多人协作上的概念，也就是最开始提到的分支。分支是什么意思呢？

> **定义**：分支代表着一条独立的开发线——你可以从开发的主线上分离出来，在不影响主线的情况下同时工作。

分支有一些操作：我可以创建一个新的分支，也可以切换分支、列出分支、删除分支。看这样一张图：

```text
  feature-A           ●──────●──────●
                     /                \
  main（稳定）  ●───●───────●───────●───●
                     \                \
  feature-B           ●──────●──────●
```

读图：图里这个节点是一个最初的版本；我们在某一个版本的时候发生了一次分裂，分裂出一个新分支，这可能是我想要开发的某一个特殊功能；原来的版本沿着主线一直走——中间这一条是我们的稳定分支，上面这条是开发某个新功能的分支，下面这条又是开发另一个新功能的分支。

这时我们其实会遇到一个需求：这个新分支上的功能已经开发好了，我想要把这些功能合并回主线来，应该怎么做呢？用的就是 `git merge`。git merge 支持对不同分支之间进行合并：在同样的版本基础上，有主线分支、有开发分支；如果你在主线分支上，就 `git merge` 加上这个开发分支的名字，它就会把这两个分支合并起来。

这个合并是自动发生的：一般来说，如果你的代码没有一些特殊的问题，基本上这个合并可以自动完成。但有时候，Git 也不能真正完全没问题的自动合并。什么时候会成功呢？比如我对一个文件，只有其中一个分支修改了它，另一个分支没有修改——这时合并操作很简单，把修改掉的内容应用过来，就完成了合并。但如果你两个分支同时修改了同一份文件的同一部分内容，这时自动合并就会失败——因为 Git 毕竟不能确定你到底要哪一个文件里的内容。

自动合并失败的时候，Git 会中断这次合并的提交，并且告诉你：你需要自己去选，到底要哪个分支的内容。Git 会自动在需要你做决定的位置上做标记，标记的格式是这样：第一行是分支一的标记，最后一行是分支二的标记，中间用一大串等号相隔的两个部分，就是两个分支各自的内容：

```text
<<<<<<< HEAD
当前分支（分支一）的内容
=======
被合并进来的分支（分支二）的内容
>>>>>>> 分支名
```

怎么解决？如果我觉得上面这个是对的，我就把这五行全部换成上面这一行的内容；如果我觉得下面这个是对的，我就把这五行全部换成下面这一行。这个标记本身是一个纯文本的界面，但在一些 IDE 里——比如像 VS Code 这样的 IDE，或者一些文本编辑器里——它会给你提供一个按钮：上面有一个勾，下面也有一个勾；点上面就是用上面这个修改结果，点下面就是用下面这个结果。这样就可以完成一个比较简单的冲突合并。

最后补一个大家自然会想到的问题：一个分支可以再分支吗？肯定是可以的。打开 GitHub 上的一个仓库，点开 main branch，你可以看到上面有一大堆分支，都是大家七手八脚给它弄出来的，会有特别复杂的互相之间的关系。所以 GitHub 用了一个特别复杂的界面，来显示这些分支之间的关系和区别、它们的状态、它们的更新频率是怎么样的、它们是谁在管理这些更新。基本上，分支之间是可以进一步再分支的。

### 怎么学 Git：先图形，后命令行

到这里基本上就是 Git 的全部内容了。这一讲讲的可能还是特别抽象一点，但 Git 确实是一个有一些入门门槛的工具，同时也确实十分强大——如果你能够顺利地使用它、熟练地掌握它，对生产效率会有一个非常大的提升。

总结一下：Git 最最重要的概念，就是版本库、工作区、暂存区这三个；基本操作有几类——本地的操作、分支的操作、远端的操作，以及刚才提到的多人协作的操作。对初学者而言，最重要的建议是：从本地的那四个增加的操作开始学起；然后一定要尽量利用图形化的东西——能图形就图形，最好不要在命令行上一直死磕。除非你已经逐渐熟练了，可以在命令行上做一些简单、快捷、方便的操作；否则一开始以学习为目的的时候，最好还是利用比较直观的、可视化的东西，来辅助你对工具的使用。

## C++ 的编译构建与包管理:make、CMake 与 xmake
> 对应块：BLK08 | 覆盖分集：P05上 | 块标题（分集名）：《编译工具和包管理环境》

Hello hello,大家好,这节课我们来讲编译工具和包管理环境。这两个词分别对应我们平时用的两类语言:比如 C 和 C++,它们需要一个编译工具;而我们用的 Python,或者一些 JavaScript,则需要一些包管理环境。今天的内容,主要就是介绍这两块。

先过一遍大纲。C++ 这边,我们介绍三个编译构建工具:一个是 make;然后是 CMake——这个大家可能用得最多;最后再引申介绍一下 xmake。Python 这边,我们主要介绍 conda 这个包管理工具。C++ 和 Python 都讲完之后,还会做一些延伸展开,比如怎么对我们的程序做性能测试——因为对我来说,这些是我平时可能会用到的一些功能,在这里跟大家分享一下。最后会有一个总结,总结之后介绍今天要布置的作业。

好,那我们就先开始。先把 C++ 的三个构建工具讲透:从一条最原始的编译命令,一路讲到 make、CMake 和 xmake。

### 代码是怎么变成可执行文件的

C 和 C++ 作为编译型语言,我们经常要用到编译器——必须通过编译器,才能把代码转换为可执行的二进制文件。与之相对,另外一些语言叫做解释型语言,Python 就是这种:我们只需要有一个解释器,它实时地把我们的代码转化为二进制的机器码。虽然这样速度更慢了,但是可能会带来意想不到的便捷。

> **定义**：编译型语言(如 C/C++)必须先经编译器,把代码变成可执行的二进制文件;解释型语言(如 Python)由解释器实时把代码转成机器码——速度慢一些,但换来使用上的便捷。

那编译这件事具体发生在哪?在 Windows 电脑上,我们基本上用的都是本地的 IDE 去做编译:最原始的大概要数 Dev-C++,后面又有 VS Code、Visual Studio,用本地 IDE 就能把程序编出来。

其实 C 和 C++ 也可以做远程编译。比如用之前提到过的 VS Code 的 SSH 远程功能,它同样可以完成编译。而在服务器上做编译时,你很难在服务器上打开一个 IDE,所以往往就是通过命令行:输入一个指定的编译器——这里比如用的是 g++——让它去编译一个具体的文件,就能得到编译的结果。

### 为什么还需要构建系统

讲到这儿你可能想问:发展到今天,很多 IDE 都已经支持远程编译了,那为什么我们还要去学怎么配置 make、CMake?

因为我们面对的项目往往不是你自己写的。一方面,我们现在可能想从网上下载一些仓库,把别人的项目编译出来拿过来用;另一方面,也可能是我自己写好了一个东西,想把它发布出来,让别人能顺利地使用它。这个时候,你就必须把编译的所有配置全部理清楚——因为不理清楚的话,你用的编译条件和别人用的编译条件可能完全不一样,你的文件可能就没法经过编译。

先看最简单的情况。最基本的编译,就是指定一个编译器、指定要编译的源文件、再指定一些选项,输入一行就可以完成:

```bash
g++ main.cc -o main
```

后面还可以再挂一些选项,比如 `-O2` 这样的优化级别。但大部分情况下,我们实际遇到的问题都没有这么简单:比如你要调一些额外的库,像 OpenGL 或者类似的第三方库,这条编译语句就会变得特别繁琐——假设这一行后面还挂着一大堆奇奇怪怪的选项,这么长一条命令,就需要给它做一个配置,把你当时所有的编译选项全部记录下来,配置成一个具体的文件。

那最简单的方式是什么?用我们之前学过的知识:写一个脚本,把这条语句写进去。下次想编译项目,直接用 bash 调用这个脚本,就可以完成编译。这样的方式确实非常便捷——当时你怎么敲的命令行,就原封不动地放进脚本里;下次你自己运行,或者别人下载你的仓库之后运行这个脚本,都能完成编译。

但问题也就出在这里:你脚本里的 g++ 是什么版本?那些选项,其实都依赖于你当前运行这条命令的那台本地机器——它装的库、它装的软件的配置。一旦换了机器,比如换了别人的机器:一方面 g++ 的版本跟你不一样,另一方面他可能没有安装 OpenGL 的库,而你这里装了。机器、操作系统层面有各种调用的区别,导致一模一样的命令行,在你这里可以运行,到他那里就没办法运行。所以,简单写成脚本的方式,并不能支撑编译配置这件事。

我们真正需要的,是一个构建系统(build system):我提供一个配置文件,用这套构建系统,就可以在不同的操作系统版本、不同版本的编译器下,都顺利地把整个项目编译下来。

> **定义**：构建系统(build system)——用一份配置文件描述整个项目怎么编译,让它在不同机器、不同编译器版本下都能顺利构建。对大规模、足够复杂的工程,我们都需要把「手动用命令行编译、链接所有代码」的步骤,改成「用构建系统做一次配置,之后反复使用」。

构建系统往往还具备一个很实用的功能:每次修改了一些代码,它会检查有更新的部分,然后重新做部分的编译——相当于不用每次都把整个项目完整地编译打包一遍,这也是构建系统最初的目的之一。

那用户要给它什么呢?拿编译一个 C++(或 C)文件来说,你要告诉构建系统三件事:需要生成什么样的目标文件——它可以是一个库,也可以是一个可执行文件,等等;生成时用到哪些依赖项;以及生成时用到的具体命令或命令行选项。

### make 与 Makefile

前面说了这么多,大家其实都已经见过一个最常用的构建系统——make。它是 Linux 下最常用的构建系统,特点是编译小项目的时候非常便捷,能提供非常好的支持。但是你了解一下 make 的语法、它的配置规则,就会发现它配置起来还是非常繁琐的,所以大项目基本上很难手写 make——实际中我们往往先用 CMake 生成 make 的配置文件,再用 make 去执行。CMake 后面细说,这里先把 make 本身搞明白。

make 的基本配置文件,名字必须一模一样地叫 Makefile,make 才能识别。在当前路径下准备好 Makefile 之后,你在命令行里直接输入 make,make 就会认出这个配置文件,读取里面所有的配置信息。

Makefile 里到底有什么?它其实很简单,就是一个普通的文本文件,里面指定了你要构建的目标、你的依赖项和你的具体命令。每个 Makefile 都由若干个三段式组成,每个三段式告诉你:某一个 target 文件,到底要怎么生成出来。

> **定义**：Makefile 的三段式——「目标: 依赖项」一行,加一行生成命令。依赖文件在当前路径找不到时,make 会提示依赖没有满足;如果你有其他配置能把它们生成出来,make 会先去把依赖生成好,再去执行生成目标的命令。

以下面这个例子为例,这两行说的是一件事:我要构建 paper.pdf。要生成它,首先必须先准备好那两个依赖文件——当前路径下找不到的话,make 就会告诉你依赖没有满足,或者去试图满足这个依赖。具体怎么生成?用的是下面缩进的那行命令:用 pdflatex 从 paper.tex 编出 paper.pdf——这其实就是一个 LaTeX 编译的过程。

```makefile
paper.pdf: paper.tex paper.fig
	pdflatex paper.tex
```

再回到刚才用 g++ 编译的例子,这个 Makefile 怎么写?我们要生成的文件是一个可执行文件 main,所以 target 就是 main,依赖项是 main.cc,生成命令就是那一整句 g++:

```makefile
main: main.cc
	g++ main.cc -o main
```

可以看到,make 从原理上来说还是比较简单的一个东西,它就是简单地帮你把命令打包了一下。以后我想知道 paper.pdf 是怎么生成的,直接找到 Makefile,里面的生成命令全部都列出来了——这样,我们就有了一个最基本的构建系统。

Makefile 里还经常见到 install 和 clean 这两条命令。它们实际上是 Makefile 里定义的一些特殊 target:install 并不是一个具体要生成的文件,而是执行它的时候会做一些额外的操作——常见的操作就是把我们需要的文件拷贝到用户的目录下;clean 干的则是另外一类事。这就使得 Makefile 的配置非常自由:你可以定义编译语句,也可以定义一些特殊的命令,把这些编译指令和命令组合起来,就得到一个比较完善的配置文件。

### make 的日常用法与天花板

碰到一个用 make 的仓库,最常见的用法是这两条:

```bash
make            # 做一次编译
make install    # 把编译完的库、可执行文件放进用户可搜索的路径
```

make install 的意义在于:把编译完的这些库或者可执行文件,全部放到用户可以搜索到的一个路径下,这样无论你在哪里,都可以直接从命令行去调用它们。

另外两个常用选项:如果你希望构建的时候开多个线程一起并行,可以用 `-j` 指定要用的线程或者进程数量;如果你不想在当前目录下找文件、或者不想把最终文件生成在当前目录,可以用 `-C` 指定目录——比如新建一个 build 文件夹,让新的文件都生成在那里。

不过抛开这些常见用法,总体来说,make 还是一个配置起来非常麻烦的事情。因为它其实没有提供太多优化、太多便利,它仅仅提供的是「我有什么命令,就把它记录下来」的功能。也就是说,如果你的编译命令特别特别复杂,那你可以想象,你的 Makefile 也会特别特别复杂。比如要调用 OpenGL 这个库,你会遇到一大堆 OpenGL 的编译选项,这些选项你都得放进 Makefile 里,全部粘贴出来一个个配置,非常麻烦。

所以用 C++ 编程,基本上都是用 CMake 这个工具来作为一个中介:我告诉 CMake 我要做什么事,CMake 帮我生成 Makefile。CMake 来做一个中间层,知道了你的需求之后,帮你省去那些繁琐的 Makefile 选项配置——这个就是 CMake 干的事。

### CMake:帮 make 写配置的中间层

先把 CMake 的定位说清楚:

> **易错点**：CMake 本身并不是构建系统。它不能直接生成可执行文件,你也不能脱离任何构建系统让 CMake 帮你编译——比如你机器上没有 make,CMake 并不能帮你继续编译下去。CMake 一般来说会生成一个 Makefile,或者生成一个 Visual Studio 的解决方案/项目,然后用后续真正的构建系统,去做进一步的生成。

整条链路是这样的:

```text
你的需求:要生成什么、依赖什么
        │  写进 CMakeLists.txt
        ▼
    CMake(中间层,不直接编译)
        │  cmake .. 生成构建配置
        ▼
    Makefile(或 VS 解决方案)
        │  make 等真正的构建系统执行命令
        ▼
    可执行文件 / 库
```

读图:CMake 只负责把你描述的需求翻译成构建配置,真正动手编译的是最下面一层。也正是因为它特别方便的跨平台、跨语言能力,CMake 成了用 C++ 基本都会用的配置工具。

CMake 的命令行用法非常经典:如果你下载过 GitHub 上的一些项目,一定会见过这套操作——在项目目录下新建一个 build 目录,cd 到 build 里,去调用 cmake。CMake 会识别父目录下它自己的配置文件,识别完之后帮你生成 Makefile;生成完 Makefile,我们就可以通过 make 去执行它。所以基本上是三段操作:第一段,创建一个 build 目录;第二段,让 CMake 生成 Makefile;第三段,让 make 根据 Makefile 执行真正的命令。

```bash
mkdir build
cd build
cmake ..
make
```

这时候项目目录大概长这样:

```text
项目根目录/
├── CMakeLists.txt    ← CMake 的配置文件,写清你的需求
└── build/            ← 你新建的生成目录
    ├── Makefile      ← cmake .. 读取上层配置后生成
    └── (可执行文件)   ← make 根据 Makefile 编出来
```

另外,这个命令行形式还有一个跨平台的版本,遇到跨平台的场景时,可以再搜索了解一下。

那么 CMake 到底怎么配置?它的配置文件角色类似 Makefile:CMake 会在当前目录下识别一个叫 CMakeLists.txt 的文本文件,里面指定你的 CMake 版本、你的项目名字,以及你要构建的目标——目标叫什么名字、需要什么文件,都可以自定义。最简单的一个 CMakeLists.txt 长这样:

```cmake
cmake_minimum_required(VERSION 2.6)
project(hello_world)
add_executable(hello hello.cpp)
```

第一行说,至少要 2.6 版本的 CMake;第二行说,项目名字叫 hello_world;最后一行指定,从 hello.cpp 生成 hello 这个可执行文件。

对比 Makefile,它特别简单的一点是:你不需要告诉 CMake 怎么编译 cpp 文件——CMake 自己会决定要怎么编译,而不是需要你去告诉它「我要用 g++,加 -O2,再加什么什么选项」。比较一下:做 Makefile 的配置,你一定要去关心命令行选项的细节;而用 CMake,你可以基本上不用管、不用操心命令行选项,只需要关心我要生成哪些文件、依赖哪些文件、依赖哪些包,不需要针对这些文件或包去定制特别细节的命令行选项——这就是 CMake 主要方便的地方。

当然,CMake 的功能也非常强大。实际上我们可以把 CMake 当作一种非常简单的脚本语言,它可以定义局部变量、全局变量。这些用法基本上只在特别大型的 CMake 项目里见到——比如配置特别复杂、或者有多个包的时候,往往会用到。最常见的场景是:指定我们用的 C++ 版本,或者指定构建的到底是 debug 还是 release 项目。

> **提示**：这些脚本层面的功能,一开始不用掌握得特别清楚,后续实际真用到了再查资料;它的语法和我们之前学过的脚本非常相近,比较容易上手。

### 用 CMake 链接库

接下来重点讲一讲:怎么用 CMake 做多个文件之间的编译链接。假设项目根目录下有两个源文件:一个叫 mysqrt,里面定义了一个我们自己写的平方根函数;一个叫 main,定义了 main 函数,main 函数里会调用这个平方根函数。这是我们经常会遇到的需求:我的 main 文件里并不直接定义函数,而是把函数的定义写到专门的一个、和这个函数相关的 cpp 文件里——这样就形成了多个 cpp 文件之间的编译链接关系。

相应的 CMakeLists.txt 就可以这样写:

```cmake
cmake_minimum_required(VERSION 2.6)
project(main)

add_library(mysqrt mysqrt.cpp)
add_executable(main main.cpp)
target_link_libraries(main mysqrt)
```

第一行指定 CMake 版本,第二行指定项目名称;第三行通过 add_library 这个函数,把 mysqrt.cpp 打包成一个库——打包成库之后,你就可以去链接它,你自己写的这个平方根函数,就可以被其他的源文件调用了;最后再和之前一样,声明可执行文件的名字,以及它从 main.cpp 来。执行完这几步,我们实际上就有了一个 library 和一个可执行文件,这时候就可以去做链接:让你的可执行文件和你需要的这个库连起来——连起来之后,就可以调用它了。

和前面的 hello 例子对比,我们只是简简单单加了两行,就完成了一个库的编译和链接——用 CMake 做库的链接还是非常方便的。

对于第三方库,我们甚至有一些更方便的方法。CMake 有一个特殊命令叫 find_package,它会去搜索你这台电脑上有没有安装某一个库,也可以配合 CMake 的包检索模块(Package Search Module)来查。如果你的电脑上有这个库,命令就会返回相应的库的地址、依赖选项,你直接根据这些地址和依赖选项形成的变量,把它链接起来就行。

> **定义**：find_package——在本机搜索已安装的库,把库的地址、依赖选项整理成一组变量,供后续 include 与链接直接使用。

比如我需要用 Eigen 这个库:直接在命令行里写它的编译选项肯定非常复杂,但用 CMake 来链接就很轻松——首先通过 find_package 直接找到 Eigen 库;找到之后,它会生成变量。因为 Eigen 是只有头文件的库,生成的变量就是 Eigen 头文件所在的那个目录;你用这个变量去做后续的 include、或者做链接,就会发现整个项目非常简单地把 Eigen 编译进来了。

```cmake
find_package(Eigen3)
include_directories(${EIGEN3_INCLUDE_DIR})
```

find_package 找到库之后生成的这些变量,可以帮助你找到文件的包含目录,以及链接库的地址。

### 第三方包管理器 vcpkg

除了在本地系统上做搜索,还可以借助第三方的包管理器,比如 vcpkg——微软的一个跨平台包管理器。以 Windows 为例:在任意位置安装上 vcpkg 之后,在你的任何一个项目目录下面执行 vcpkg install 安装某一个包,它就会自动把那个包装起来;执行完毕之后,vcpkg 还会告诉你:如果想在 CMake 里调用这个包,应该怎么写——它会把这段 CMake 配置代码直接打印出来。你把它复制出来,粘贴到你自己的 CMake 配置里面,就可以完成这个包的调用。

```bash
vcpkg install <包名>
```

而且我们不需要关心这个包到底安装在哪,因为 vcpkg 已经帮你管理好了。如果你熟悉 Python,你会发现它和 pip 有点像:pip install 某一个包,和 vcpkg install 某一个包是类似的——都是通过包管理器,来管理你所有从第三方装过来的包或者库。

> **定义**：vcpkg——微软的跨平台 C++ 包管理器:一条命令装包,自动给出 CMake 接入代码,统一管理安装位置,角色类似 Python 的 pip。

### xmake:一条龙的构建工具

讲完 CMake,我们再提一下 xmake 这个扩展的构建系统。它不像 CMake——CMake 只是用户需求到 make 之间的一个中间体;xmake 自己是一个更加现代化的 C/C++ 构建系统,因为它其实打包了一大堆内容进去:从 make、到 CMake、到 vcpkg 的所有流程,它都能包下来。也就是说,它既能完成编译,又能完成项目管理,又能完成包管理,同时还支持管理你的编译器。它有自己的官网,官网上有非常丰富的文档。

使用上,和前面两个一样,xmake 也需要一个固定名字的配置文件——它是一个 Lua 脚本,以 xmake 自己定义的语法,完成一个目标的编译。比如脚本里就简简单单四行主要内容;但同样这四行,你要是翻译成 CMake,可以在 CMakeLists.txt 里写出好多好多行。所以基本上来说,我个人觉得 xmake 还是一个非常容易上手的编译工具。

它的包管理也非常简单,和 CMake 有点像:直接在配置文件里加一句 `add_requires`,声明你需要哪个包;并且 xmake 兼容 vcpkg 自己的包管理,也支持你自己构建的包——而不只是第三方的知名包。

xmake 还兼容 Visual Studio。正常来讲,我们如果想用 VS 去配置一个 CMake 项目,是要打开一个特殊的 CMake 项目的;但 xmake 不是这样,它可以直接生成一个 VS 项目——通过一条语句,把你的项目转化成 VS 项目,然后你打开这个项目的解决方案,Visual Studio 就自动能够运行、能够编译了。

运行更是傻瓜式的:你在命令行里直接说一句 xmake,它就可以完成从编译到构建、甚至包安装的一系列事情——它会识别哪些包是没有的,自己去安装;从编译到运行,基本上全部在这样一个命令里帮你完成。

```bash
xmake
```

### xmake 的写法为什么更顺手

这里展示一个从我自己的项目里找出来的 xmake 配置文件。你会发现,它的很多操作都用了更加人性化、对用户更友好的一种语法来写。比如在 CMake 里定义 C++ 版本,其实还是有一点复杂的——往往要去网上查一下怎么定义,而且别把变量名字打错才比较好;但在 xmake 里,一句非常简单的命令就可以定义好 C++ 的版本;增加依赖库的方式也是一行就完成。

CMake 这边有一个更有代表性的对比。比如我们要查找 src 这个文件夹下所有的源文件,CMake 的操作长这样:

```cmake
file(GLOB SRC_FILES src/*.cpp)
```

这个操作是什么意思呢?它查找所有的源文件,然后把这些文件放进 SRC_FILES 这个变量里,后续你就可以用这个变量去完成编译。如果你是从「那个年代」过来的人,会觉得这是一件很自然的事情——因为我们之前学的那些 shell 脚本都是这样的:我一定要把什么东西放到变量里,后面就可以继续这样用。但 xmake 在这一点上其实跨出了更大的一步:它可以直接用一个函数,函数里指定我要的正则表达式,xmake 就根据这个正则表达式去搜索——比起 CMake,这可能是一种更加自然的方式。

### 循序渐进:三代构建工具

到这里,C++ 这部分的内容就全部讲完了。回头看,它其实是一个循序渐进的过程:

最原始、历史也最悠久的,是 make 这个工具。从 make 到 CMake,CMake 其实比 make 跨出了一大步——我们可以用更少的编译配置,就完成一个 C 或者 C++ 项目的编译,比 make 省了特别特别多的功夫。再到最近比较新颖的 xmake,它集之前各家之大成,兼顾了你的编译和包管理,同时它的配置文件写法,也非常接近我们现代人(现在大家)的习惯——毕竟我个人觉得,CMake 其实还是有一点反人类的。

| | make | CMake | xmake |
| :--- | :--- | :--- | :--- |
| 它是什么 | 真正的构建系统 | 用户需求到构建系统之间的中间层 | 打包全流程的现代化构建系统 |
| 配置文件 | Makefile | CMakeLists.txt | xmake.lua(Lua 脚本) |
| 命令行选项 | 全部自己写清楚 | 基本不用操心 | 一行命令搞定 |
| 包管理 | — | find_package 搜本机 / 配 vcpkg | add_requires,兼容 vcpkg |
| 典型场景 | 编译小项目非常便捷,大项目难手写 | C/C++ 项目的主流选择 | 一条龙搞定编译与包管理 |

所以总结一下:我们经常遇到的、并且需要了解的,基本上是后面两种——CMake 和 xmake。至于 make 本身,大家知道它是怎么一回事就行了。

## 从 CMake 到 conda：包管理、性能探查与高效开发
> 对应块：BLK09 | 覆盖分集：P05下 | 块标题（分集名）：《编译工具和包管理环境》

先把 C++ 这边的结论收拢一下。对 make，你知道它是一个用来生成、配置系统的 build system，就可以了；至于 Makefile 到底要怎么写、里面的语法是什么，不用特别仔细去关心——因为我们现在基本上都不直接写 make 了，而是用 CMake 或者 xmake。

CMake 的定位，取决于你的需求。如果它对你不是特别刚需——比如你并不需要把自己的仓库打包发布出去——那基本上不一定要用到它：知道 CMake 是什么、会用别人的 CMakeLists，其实已经够了。但如果需要把自己的仓库打包发布出去，那就还是得掌握一下 CMake。原因很直接：xmake 虽然好用，我们甚至可以直接拿它作为 C++ 编译的上手工具，但它毕竟不是那么流行——要把自己的东西发布出去，基本上还是应该提供一个 CMakeLists。

> **结论**：make 知道是干嘛的就行，语法不用背；日常会读、会用别人的 CMakeLists 就够用；要发布自己的仓库，才需要真正掌握 CMake。

期间有两条现场问答值得记下来。有同学指到前面例子里的一个符号——对，那是 Linux 的路径通配符，它和正则表达式还是有区别的，两者不要混为一谈。还有同学说展示的这些 CMake 例子太“古代”了——确实有可能，课件里展示的例子都比较旧；至于最新的 CMake 到底怎么写，我还真不了解，估计语法会比以前有所改进，大家也可以自己去学一学最新的。总之还是建议根据自己的需求去学：要么 xmake，要么 CMake。

xmake 本身，在我具体的使用过程中其实遇到过不少问题：它毕竟是一个非常新的东西，很多方面没有像 CMake 那样经过时间的考验、经过各种奇奇怪怪配置的考验，所以有不少不支持的地方。如果你的编译条件、编译选项特别“非通用”，xmake 不一定吃得下来——具体还是要看各自项目的需求情况。

所以选择就放在这里：CMake 和 xmake，我觉得都是比较好的选择。我个人用 xmake，主要是因为它附带把包管理给搞进去了，感觉稍微省力一点；用 CMake 的话，也可以 CMake 配上别的包管理系统来用。至于 premake，我就不了解了。

### Python 这边：只管包，不用管编译

讲完 C++ 的部分，我们来看 Python 这边的包管理系统。Python 这边大家最熟悉的，可能就是 conda、pip 这些了；其他的其实我也没听说过。

Python 语言和 C++、C 都不一样：它是一种解释型语言，不需要做编译，直接在解释器上运行就可以。所以对 Python 来说，没有那么多复杂的编译过程——实际上你安装 Python 本身的时候，很多东西都已经编译好了：Python 自己的解释器，你拿到的就已经是编译好的成品，不需要再做额外的编译；我们的 Python 代码都是直接在解释器上运行。

这样一来，事情就少了很多：在 C++ 或者 C 里，我们既需要管理包，又需要配置编译环境；而在 Python 里，你可能只需要管理包就可以。

conda 这个东西大家应该都知道——它是 Python 里非常知名的一个包管理和环境管理工具。我们经常用的两种 conda 是 Miniconda 和 Anaconda，这两个基本上功能上类似，只不过 Anaconda 会附带很多科学计算用到的包。

> **提示**：两者功能上没有太多区别；Anaconda 附带一大堆科学计算包，Miniconda 则特别小、装得特别快，装完再按需挑包。

我自己的习惯：比如拿到一台 Linux 服务器，或者一台新电脑，要装一个 conda 环境的话，基本上我的选择都是装 Miniconda——它首先特别小，安装又特别快，装上之后再去自己决定安装怎样的包，是一件比较方便的事情。

装好之后，命令行前面会多出一个 base——上次配置 zsh 的时候，大家可能已经注意到这个点了。这个 base 其实就是一个 conda 环境：conda 在默认安装的时候，会提供一个默认的 base 环境。

所以 conda 基本上做了两件事：一件是包管理，另一件是环境的分割——它会把你的运行环境分成好几个，每个环境之间安装的包互相不可见，因此也互相不会污染、不会干扰。环境分割这件事，到虚拟环境那一节再细说，这里先把包管理这条线走完。

### conda 与 pip 的日常操作

对 conda 来说，动手装包之前，一般要先配置一下清华源。我不确定现在是不是还必须配，但反正如果你发现它的默认源不是国内的源，一般来说会很慢，最好还是配一下。

> **定义**：源（channel）就是“conda 从哪个网站找包”。要下载一些别人发布的包时，conda 就是到它的 channel 里去找；默认的国外 channel 会特别卡，所以一般把它换成国内的源。

设置好源之后，包管理本身非常简单：就像前面讲过的 vcpkg 一样，`conda install` 后面填包的名字，就可以安装这个包；后面再指定它的版本号，就可以安装指定版本的包。conda 和 pip 的常用命令，放到一张表里对比着看：

| 操作 | conda | pip |
| :--- | :--- | :--- |
| 安装包 | `conda install 包名` | `pip install 包名` |
| 安装指定版本 | `conda install 包名=版本号` | `pip install 包名==版本号` |
| 卸载包 | `conda remove 包名` | `pip uninstall 包名` |
| 列出当前环境的包 | `conda list` | `pip list` |

pip 其实也和 conda 很像，上面这些命令两边几乎一模一样。conda 这边还有一个 `conda clean`：删除掉那些你下载了但是没有用到的 package、清理掉一些文件——常见于你的电脑实在放不下那么多东西的时候。pip 那边则有一个很常用的批量安装：`pip install -r requirements.txt`，根据 requirements.txt 这个文件里指定的那些包去安装，要加一个 `-r` 选项，这个用法后面马上还会用到。另外 pip 也有换源的问题，不过它需要到你用户目录下面的一个文件里去改，具体网上有很多教程。

这些功能其实等遇到了再去查，也完全 OK——因为 pip 和 conda 都是非常简单的两个工具，不像我们之前遇到的 git，有各种复杂的概念。conda 和 pip 基本上就非常简单。

### 虚拟环境：给每个项目一套独立的 Python

#### 为什么需要虚拟环境

前面一直 cue 到的概念，这里正式讲：虚拟环境。

> **定义**：虚拟环境就是一个目录——里面装着一个特定版本的 Python 解释器，以及一批软件包。

为什么需要它？比如我希望运行别人的一个仓库，但那个仓库只能在某个特定版本的 Python 下运行——它的很多语法只跟那个版本配套，或者它依赖的一些包最新只发布到了那个版本，种种原因。总而言之，你总会遇到这样的特殊需求：必须指定这个项目要用哪个 Python 版本、要用哪些版本的软件包。

举个最常见的例子：numpy、OpenCV 这些包，不同版本之间虽然已经尽量在兼容，但还是有差异，有的时候你只希望用其中一个版本。于是问题就来了：项目 A 需要某个版本的 Python，项目 B 需要另一个版本的 Python，你怎么去协调这两个版本的冲突？这就是虚拟环境登场的地方。

所谓虚拟环境，有点像虚拟机一样的感觉：你打开了一台“虚拟的机器”，上面装了一个 Python 3.9；再打开另一台虚拟机器，那台机器上装的是 Python 3.8。对你的程序来说，它只能看得到当前虚拟环境里的 Python 版本，不知道你真正的 Python 版本，也不知道其他虚拟环境里安装了什么——它只看得到当前虚拟环境里装的包。这就让你能够在一台机器上部署不同版本的 Python，并且各个虚拟环境之间不会相互影响。

```text
一台真实的机器
│
├── 虚拟环境 A：Python 3.9 + 它自己的一批包
├── 虚拟环境 B：Python 3.8 + 另一批包
│
└── 程序只能看到自己所在环境里的解释器和包，
    看不见其他环境，环境之间互相不污染
```

读图：每个分支就相当于一台“虚拟机”，程序被关在自己的分支里，互相看不见对方装了什么。

#### 用 conda 创建和激活

创建虚拟环境，一般来说我们用 conda，而不是用 pip。最简单的命令是这样：

```bash
conda create -n 环境名 python=3.9    # -n：给环境起个名字，Python 版本也可以在这里一起填
conda create -p 路径 python=3.9      # -p：指定一条路径，把环境的文件放到那里
conda activate 环境名                 # 激活：名字就是你自己命名的那一个
conda deactivate                      # 解除激活
```

`-n` 和 `-p` 的区别，在于这些环境的文件存到哪里去了。`-n` 会把文件存到你的用户目录下——Windows 上可能在 C 盘下面，Linux 上就在 home 目录；有时候那个地方特别挤，而你的虚拟环境又必须装很多很多的文件，放不下了，就用 `-p` 指定一条路径去放——比如我专门把虚拟环境放到 D 盘去，空间上就不那么挤了。

还有一个区别体现在激活上：`-n` 创建的环境，直接输入它的名字就可以激活；`-p` 创建的环境，你要输入它完整的路径名才可以激活。所以正常情况下，我们都是用 `-n` 这种方法来创建环境，创建完之后直接 `conda activate` 加名字激活，不需要了就解除激活。

#### 拿到别人的仓库：标准三步

虚拟环境还有一个很常见的场景。你拿到一个别人的项目，会发现他的 Python 仓库里可能有一个 requirements.txt 文件——这个文件是用来告诉你虚拟环境里安装的包的版本的。

一般来说，拿到一个新的别人的仓库、想运行它的 Python 代码时，要做的就是这几步：

```bash
conda create -n 环境名 python=3.9    # 建环境，Python 版本填这个仓库所需要的那个
conda activate 环境名
pip install -r requirements.txt     # 按清单把它的所有依赖项全部装上
```

装完之后，你就可以正常运行它的项目代码了。这其实是一种非常简单的包管理。

#### conda 和 pip 别混用

还有一件事要提醒：conda 能安装包，pip 也能安装包，但如果你在同一个虚拟环境里又用 conda 装、又用 pip 装，往往会遇到一些冲突的问题——它们有时候还蛮不兼容的。所以建议只用其中一种：比如只用 conda 安装，或者只用 pip 安装。像我个人的话，就都是只用 pip 安装。

> **易错点**：同一个环境里 conda、pip 混着装包容易出冲突；一个环境认定一种安装工具。

到这里，虚拟环境的内容基本就这么多——简单来说，它就是一个稍微复杂一点的包管理系统。conda 和 pip 在网上有非常非常多的资料，遇到什么具体问题，搜索一下就可以。

### 性能探查：你的代码到底慢在哪

最后来讲性能探查。这是一个特别小的部分，当初准备课程大纲的时候，就没把它专门塞成一个模块，所以在这里顺便讲一下。但不管写 C++ 程序还是写 Python 程序，这件事都会遇到——有些同学平时已经在用了，有些同学可能不怎么用，而我个人觉得，它是我经常会用到的一个工具。

场景是这样的：你写了一些代码，嫌它太慢——比如我渲染什么东西，每次渲染花的时间都太久；我想改一个参数，再重新渲染一下看看。就这样反复地改参数、看结果、改参数、看结果，这个过程中你的程序运行占掉了非常多的时间。这时候，如果我们能通过一些代码上的加速，或者能知道这个代码到底慢在哪了，从而去做时间上的优化，就能给我们的开发、给项目的编写和管理提供非常多的便利。

#### C++：Visual Studio 自带的性能探查器

在 C++ 下，我会用 Visual Studio 自带的性能探查器，看我的代码是不是有明显不合理、明显慢的地方。它会用一张表格列出你这个项目里每一个函数占据 CPU 时间的百分比。你根据这个百分比来判断：代码最慢的部分在哪里？它慢得合不合理？如果你有特别密集的计算，慢是合理的；但如果你因为自身的一些过失，写了一个本来应该很快、实际上最后写出来特别慢的循环——通过性能探查你就会发现“这个地方比想象的要慢很多”，从而去改进这一块代码。这就是性能探查的主要意义。

#### Python：cProfile 加可视化

对 Python 来说，我用的是自带的 cProfile，再加上一个第三方的可视化工具——后者也是可以用 pip 来安装的。装好之后，就可以图形化地查看性能结果：和 Visual Studio 一样，它会把每个函数调用的时间、调用的比例全部列出来，你就知道每个函数具体占用了多少时间。

#### 为什么值得为速度花时间

用 C++ 或 Python 的这些性能探查，终极目的都是为了提高我们工程迭代的效率。有的时候速度并不是最重要的；但当你需要频繁地修改程序参数、去观察结果的时候，速度就变得很重要。比如你三天才能搞出一个结果，然后重新调整参数，再去花三天看新的结果——这时候你甚至不如先花一周时间，把程序的速度提高到一天就能出结果：接下来一周，你就能七天跑七次结果。可如果你什么都不做，还是三天出一次结果，那这两周可能就干不了什么事儿了。这就是性能探查的意义所在。

#### 逐行探查：从 list 到 set

Python 除了自带的性能探查，还有一个 C++ 里没有的能力：看每一行性能占用的时间。这是因为 Python 毕竟是解释器的语言，每一行是非常分明的，Python 解释器知道现在执行到哪一行；而 C++ 是编译后的一个结果，它其实不能直接知道每行的性能情况——不过它可以推断出来，比如某一条二进制的字节码，到底对应原文件里的哪一行。总而言之，Python 能告诉你每一行占用的大概时间。

举个例子。我写了一个函数，逐行看它占用的时间，会发现第八行占用了 92.9% 的时间——差不多是整个程序的九成以上。而那一行只是一个“判断某一个数在不在一个列表里”的语句：你本来觉得它应该很快执行完，结果通过性能探查发现它占掉了程序绝大部分的时间，这就是不合理的点。

来分析这个不合理：如果这个功能被用得如此频繁，那你就不应该把它设计成一个列表（list），而应该把它设计成一个 set——一个散列表。改成 set 之后，这一句的功能完全一样，但只占用非常少的时间。把上面那句换成下面那句，你可以想象，整个代码的速度就会大大加快——省下来的就是你的开发时间。

> **提示**：需要频繁判断“在不在里面”的容器，用 set（散列表）而不是 list，两者的查找开销天差地别。

### 高效开发的几条心法

从性能探查引申开来，最后聊聊我们要怎么样高效地做 coding。

#### 从读懂别人的 code base 开始

首先要考虑的是 code base 的准备：你的项目到底要从什么程度出发——是从零出发，还是从 GitHub 上一个已有的仓库出发？针对你想实现的功能，应该用什么语言，C++ 还是 Python？如果是从 GitHub 上的项目出发，又该怎么读别人的代码？这些其实都是要提前想清楚的点。

对我来说，最经常的需求就是：拿到别人的一个 code base——它已经有了一个具体的实现、一个具体的仓库——我先把他的仓库读懂，然后在上面做一些修改、做一些实验，去发展我的新方法。这个时候，第一件事就是读懂别人的代码，这一步其实蛮重要。

读懂的过程中，一定要利用 IDE 这样的功能：点击一个函数，就可以跳转到它的定义；甚至实际去运行它的代码，做一个编译、做一个调试；或者把它放到 Jupyter notebook 里，一句一句地执行，去看它的输入输出。总之，我们不要把代码当纯文本来读——那样读其实是非常难读的；用上这些现代的方法（IDE、编译调试工具、自己运行查看输入输出），其实会事半功倍。

#### 起步时怎么快怎么来，验证后再整理

开始写自己代码的时候，你肯定是有一个具体问题的——比如想解决某一个点，或者想给代码加一个什么功能。在问题的最开始，一定要用最高效的方法：同一个问题可能有多种解决方法，有优雅的解决方法，也有粗暴的解决方法；对起步阶段来说，我建议挑开发效率最高的那个。

比如需要可视化：C++ 当然有 OpenGL 这样的可视化方案，Python 也有它自己的可视化，但你其实可以把东西放到 Chrome 浏览器里，去做一些自己的修改或者调试，用它的控制台的 JavaScript 来做一些辅助——像这种就是怎么快怎么来。Python 的话，一开始可以放到 Jupyter notebook 里去开发，相当于每个 cell 每个 cell 地执行，而不是把整个脚本文件一块执行下来。

等你验证了自己的方法是 OK 的，再把目前的代码整理下来——整理成和原来仓库风格类似、封装好、也比较优雅的状态。起步的时候，高效更好；正确性验证过了，再把它组织成一个更加系统的代码。

#### 优化这件事，不用太早操心

一开始处理问题的时候，性能好不好、符不符合面向对象的基本原则——我们可以不用太早关心这些问题，特别是优化上的问题。因为如果你写代码的时候就太关注优化，其实会影响到你的开发效率。一开始怎么直接怎么来，先不去关心它的性能；等你把整个问题全部完成、写成代码之后，再回头用我们的性能分析工具，去关心它的效率、去做性能的优化。

#### 调试占一半时间，磨刀不误砍柴工

coding 里还有一个很重要的一环：debug，做一个调试。调试是代码编程中非常重要的地方——我们可能只有 50% 的时间在写代码，剩下 50% 的时间在调试。调试也非常有讲究：首先，磨刀不误砍柴工，去找一个最能直观看到“我当前运行到哪里了、当前有哪些变量、怎么样做可交互的调试”的方法；特别是用 IDE——Visual Studio 啦、PyCharm 啦——去做可交互的调试。除非你觉得非常非常确定，否则尽量不要通过肉眼去看文本的代码来做调试。debug 永远是最关键的部分。

必要的时候，我们可以把中间的结果保存下来，和标准的程序去做比较：比如你要实现一个功能，别人已经有一个标准的实现，或者你有办法验证自己的结果是不是对的——这种时候，就可以保存一些中间结果去做比较。简单来说，就是把问题拆分成一个个小问题，再去逐一做正确性的验证。

#### 等待别干耗，参数要记下来

像深度学习这种，不要长时间盯着它的训练过程；渲染这种、物理模拟这种也是一样——不要长时间盯着，把这些等待的过程拿去干别的事情，比如边等边开始修改其他的代码。

另外一个良好习惯：每一次运行的时候，你可能会对参数做一些微调，这些微调你最好都记录下来——比如每一次的程序到底是怎么能够复现的。这些东西如果能记录下来，对整体的开发是有帮助的。

#### 计划、瓶颈，以及精力与时间

最后这条可能更加针对科研一些：我们要明确自己的计划，去判断接下来需要多少实验、需要多少时间，再根据这个判断——比如我们有没有必要去优化程序的运行速度等等。最后就是想清楚整个开发过程的瓶颈在哪里、你的计划是什么，然后平衡好你的精力和时间。

精力和时间其实是两件非常不一样的事情：有时候你可能有充足的时间，但是没有什么精力；有时候你可能精力充沛，但是时间来不及。总而言之，无论做什么，其实都要做好这两件事的平衡。

### 本讲提到的题目

这节课发布作业二，课后会把它传到作业网站上。一共有三道题，加起来 22 分，其中 6 分是选做的；前面的 16 分是前两道题，每道都按语言分 A/B 两个版本——考虑到不是所有人又会 C++ 又会 Python，会 Python 就做 B，只会 C++ 就做 A。这些题涉及的都是本讲讲到的内容。

**题一（A/B 二选一）**

- A（C++）：先写一个 hello world 程序，再为它编写一个 CMakeLists.txt，然后就可以用 CMake 和 make 来完成编译。
- B（Python）：装一个 Miniconda 或者 Anaconda，尝试创建一个新的虚拟环境，用 pip 安装两个指定的包，最后列出这些已安装的包。

> **解析**：A 对应正文开头的结论——现在不直接手写 make，构建交给 CMakeLists，由 CMake 和 make 完成编译；B 就是“虚拟环境”一节的标准流程：`conda create -n` 建环境、`conda activate` 激活、`pip install` 装包、`pip list` 列出。注意正文提醒过：环境里装包只用一种工具。

**题二（A/B 二选一）**

写一个最简单的排序算法，对排序时间做比较，并使用课上介绍的性能分析工具做分析；同样，只会 Python 做 B，只会 C++ 做 A。

> **解析**：对应“性能探查”一节——C++ 用 Visual Studio 自带的性能探查器，看每个函数占据 CPU 时间的百分比；Python 用自带的 cProfile 配第三方可视化工具，还能逐行看时间占用。排序到底慢在哪、占比合不合理，就是这道题要看的东西。

**题三（选做，6 分）**

C++ 侧：用一下 xmake；Python 侧：做一些更复杂的虚拟环境操作。

> **解析**：xmake 的卖点和注意点都在正文开头一节——它把包管理附带进去了，上手省力，但非通用的编译配置它不一定支持；虚拟环境的进阶操作，以“虚拟环境”一节的创建、激活、解除为基础往外扩展即可。
