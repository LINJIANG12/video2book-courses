## 实时全局光照：先把 PRT 讲完（Glossy 物体与小波）
> 对应块：BLK13 | 覆盖分集：P07上 | 块标题（分集名）：《Lecture7 Real-time GLoba》

判断实时渲染质量的好坏，一个重要的标准就是看结果亮不亮。没有全局光照，或者全局光照做得不好，得到的结果自然就会比较暗——全局光照扮演的，就是让整幅图像变得明亮、并且看起来自然的重要角色。它在实时渲染里非常非常重要，这一讲我们就开这个新话题。

这节课的安排：先把上一讲剩下的预计算部分说完。diffuse 物体的预计算和实际快速计算已经讲过，今天补上两块——glossy 物体怎么处理、它为什么值得单独拎出来说；再给大家介绍另外一个基函数，叫做 wavelet，中文叫小波。PRT 说完，我们就正式开始讲实时的全局光照：今天主要讲三维空间中的实时全局光照方法，大概能讲两个——reflective shadow maps（RSM）和 light propagation volumes（LPV）；VXGI 估计今天讲不了，留到下节课开头再补上。下节课还会讲在图像空间上怎么做实时全局光照。

上一讲我们还说过：环境光下的阴影非常难做。今天重新提一句，是因为大家还会发现，这个事情在全局光照中仍然非常难做——全局光照里怎么算间接光照的阴影，会一直是块硬骨头。

### PRT 复盘：预计算的两本账

PRT 预计算的是什么？两部分：一部分是 lighting；另一部分是积分里除了 lighting 以外的所有东西，我们管它叫 light transport。渲染的时候，lighting 乘上 transport、积分起来，在任何一个 shading point 上得到的结果，就是这个 shading point 能看到的最终值。

先把一个词说清楚：我说的 shading point，其实指的就是几何形体的顶点，也就是 vertex。light transport 可以每个顶点计算一份向量。实际运算时有两种做法：一种是 per-vertex shading——每个顶点先运算好、得到 shading result，然后在三角形内部插值；另一种是 per-pixel 或者叫 per-fragment shading——先在三角形内部把 lighting 对应的向量和 transport 对应的向量插值好，然后在中间任何一个像素上算结果。两种都可以；说 shading point 还是说 vertex，其实是一回事。

所以流程就是：每个 vertex 计算它的 light transport，并且投影到 SH 上，得到一个向量；lighting 这边，如果你只用考虑一种光照，那就只用投影一次——投影到每一个 SH 基函数上得到一个数，当然最后合起来就是一个向量。实际运算的过程中，就是一个向量的点乘。

再回顾一下 spherical harmonics 本身。它是一系列基函数，分为不同的阶——从图上看就是分成不同的层、不同的行，每一行表示一个固定的频率；随着行的数量增加，也就是 $l$ 的增加，它能够表示的频率就越来越高。每一种频率下有多少种不同类型的基函数，之前分析过。任何一个二维的函数都可以投影到 SH 上，用一系列加权和来描述；反过来，给定一些 SH 的基函数——比如用前 $n$ 阶，那就总共 $n^2$ 个基函数，也对应 $n^2$ 个系数——就可以恢复出一个原始的函数。当然这算是一个频率截断的恢复：用的阶数越高，越可以表示出原始函数里高频率的内容。

### 同一个推导的两种读法：从点乘到双重求和

上一讲我们是从 rendering equation 出发推 PRT 的：先把 lighting 写成基函数的描述方法，剩下的部分看起来就是把 light transport 投影到基函数上——这是一种理解。今天换个角度：不再考虑先后顺序，直接把 lighting 和 transport 两部分各自展开。

lighting 是关于各个入射方向 $\omega_i$ 的二维函数，把它拆成一系列求和的形式，自然就是对 SH 的前若干阶做个投影；light transport 这边，对 diffuse 的 BRDF 来说它就是一个常数，不用管，剩下的 visibility 仍然是关于 $\omega_i$ 的二维函数，所以同样可以投影到基函数上。为了书写方便，把整个 transport 部分记作 $t$。

两部分都已经写成求和形式了，那是不是就可以把它们在积分里展开？把求和和积分交换一下顺序，就会发现它变成一个双重求和的问题：

$$L_o=\sum_{p=1}^{n}\sum_{q=1}^{n}l_p\,t_q\int_{\Omega}B_p(\omega_i)\,B_q(\omega_i)\,\mathrm d\omega_i$$

每一个求和项里要乘三样东西：两个对应的系数，以及一个积分的值。注意这个积分跟实际的场景没关系——它是两个基函数的 product integral。

现在有一个问题要问大家：这样推导出来的东西，跟上一节课推的不太一样了吧？上一讲我们说，light 和 transport 各自投影到 SH 得到一个向量，渲染时做点乘；向量长度是 $n$——这里的 $n$ 指基函数的个数，不是阶数——点乘是 $O(n)$ 的。怎么这里突然变成对 $p$ 求和、对 $q$ 求和，成了 $n^2$ 的算法？这是个非常严重的问题。

先给一个提示：这两种推导得到的结果肯定是一样的。那为什么看起来是 $O(n^2)$，实则还是 $O(n)$？答案藏在 SH 的一个好性质里。

看这个积分在做什么：一个基函数和另一个基函数乘起来再积分，这不就是"把任意一个函数投影到某个基上"吗？你可以认为 $B_p$ 就是任意一个二维函数，它要投影到 $B_q$ 上，投影出来的系数就是这个积分是多少。而上一讲刚提到 spherical harmonics 本身有正交性。类比三维空间：把 $x$ 轴投影到 $y$ 轴上，得到的结果是多少？零。只有把 $x$ 轴投影到 $x$ 轴，结果才不是零，否则其他都是零。也就是说，只有当 $p$ 和 $q$ 相同、$B_p$ 和 $B_q$ 是同一个基函数的情况下，这个积分结果才会是 1，否则结果就是 0：

$$\int_{\Omega}B_p(\omega)\,B_q(\omega)\,\mathrm d\omega=\begin{cases}1,&p=q\\[2pt]0,&p \neq q\end{cases}$$

所以虽然这看起来是一个 $n\times n$ 的二维求和，但只有 $p=q$ 的时候它才有值，其他时候都不是值——说白了就是你有一个二维的矩阵，但只有矩阵的对角线上有值，那把对角线上的值都算出来就好了。所以这还是 $O(n)$ 的，没有任何问题。

```text
        B1   B2   B3  ...  Bn
  B1  [  1    0    0   ...  0 ]
  B2  [  0    1    0   ...  0 ]
  B3  [  0    0    1   ...  0 ]
  ..  [ ..   ..   ..  ...  .. ]
  Bn  [  0    0    0   ...  1 ]    <- 只有对角线非零，实际要算的只有 n 项
```

读图：双重求和名义上展开出 $n^2$ 项，正交性把非对角线的项全部清零，真正要算的只有对角线上的 $n$ 项，复杂度仍是 $O(n)$。

### Glossy 物体：transport 从向量变成矩阵

这节课的新内容从 glossy 物体开始。diffuse 之前已经处理过了，那 glossy 怎么处理？它有什么和 diffuse 不一样的地方？

区别就在 BRDF 上。diffuse 的 BRDF 是一个常数；glossy 的 BRDF 可就不是常数了——从任何一个方向打进来，它告诉你往哪个方向反射；换个方向打进来，它就往其他方向反射。所以它是一个完整的 4D BRDF：两维是输入方向，两维是输出方向。

麻烦就来了。按之前的办法，lighting 投影到 SH 没问题；但把 light transport 投影到 SH 的时候，就会发现有问题。transport 里的 BRDF 既是 $\omega_i$ 的函数又是 $\mathbf o$ 的函数：只要给一个不同的出射方向 $\mathbf o$，BRDF 的值就不一样。所以对任意一个给定的观察方向 $\mathbf o$，light transport 投影出来的是一组完全不同的向量——不同的 $\mathbf o$ 给你不同的向量，这就麻烦了。换句话说，transport 已经投影到 $\omega_i$ 方向的二维基上了，但向量中间的任何一个元素都不再是一个简单的数 $t_i$，而是一个关于 $\mathbf o$ 的函数。

再给一个直观理解。glossy 物体有一个非常重要的性质：它和视点有关。diffuse 物体，你不管视角怎么旋转，同一个 shading point 看到的都是同一个东西，因为整个 diffuse shading 和视角是无关的；glossy 物体和视角有关，给一个不同的视角，就应该得出一个不同的结果。所以最后得到的 $L_o$ 肯定跟 $\mathbf o$ 有关——不同的观察方向，对应不同的 $L_o$。这也解释了为什么 transport 明明已经投影到 $\omega_i$ 上了，每个系数 $t_i$ 仍然是 $\mathbf o$ 的函数。

那怎么处理？这里就是人们聪明的地方。既然你已经把 4D 的 transport 投影成了一个二维的东西，剩下的这个系数 $t_i$ 虽然是 $\mathbf o$ 的函数，但它现在只是 $\mathbf o$ 的函数了——一个二维的、关于 $\mathbf o$ 的函数。那能不能在 $\mathbf o$ 方向上也把它投影到 spherical harmonics 上去？当然可以，按照这种方式仍然可以把它拆开。

这样一来我们会得到：原来的 light transport 不再是一个向量，而是一个矩阵。说白了就是，给你任何一个 $\mathbf o$，你会得到一串向量；把所有不同 $\mathbf o$ 对应的向量都摆在一块，可不就变成了一个矩阵。

最后的结果也跟着变：出射的 radiance 是往各个不同方向去的，是 $\mathbf o$ 的函数——给任意一个 $\mathbf o$，它都能告诉你往这个方向看的结果，所以最后得到的结果不再是一个数，而是一个关于 $\mathbf o$ 的向量。lighting 那边没有问题，还是关于 $\omega_i$ 的向量。那大家想：一个向量，要乘以一个什么东西，才能得到另外一个向量？——必须是矩阵。从这个角度也能推出来 transport 得是矩阵。

这个 transport matrix 做的事情，基本上就是告诉你：从 $\omega_i$ 方向到 $\mathbf o$ 方向，光是怎么 transport 的。

```text
 diffuse :  lighting 向量 l (n)   ·   transport 向量 t (n)        ->  标量 lo
 glossy  :  lighting 向量 l (n)   ×   transport 矩阵 T (n × n)   ->  向量 lo(o) (n)
```

读图：diffuse 的渲染是一次点乘；glossy 的渲染是同一个 lighting 向量去乘一个矩阵，得到关于出射方向的向量——这正是 glossy 的结果随视角变化的原因。

| 对比项 | Diffuse | Glossy |
| :--- | :--- | :--- |
| BRDF | 常数 | 完整的 4D 函数 |
| transport 投影到 SH 后 | $n$ 维向量，每个元素是一个数 | 每个 $\mathbf o$ 一组向量，合起来是 $n\times n$ 矩阵 |
| 实时渲染操作 | 向量点乘 | 向量乘矩阵 |
| 与视角的关系 | 无关，转视角结果不变 | 有关，不同视角不同结果 |

### 代价、阶数与当年的成绩单

在实际渲染的时候，glossy 的代价立刻就出来了，有两个。一个是存储：任何一个顶点（shading point）都要存一份 transport matrix。原来假如你用 25 个 spherical harmonics 基函数——五阶，$n^2=25$——diffuse 每个顶点存 25 个数；现在要存的就是 625 个，因为它是个矩阵，$25\times25$，非常多了。另一个是计算：存储多了，渲染的时候 glossy 情况就得做向量和矩阵的乘法，这个操作比向量点乘要复杂很多。

那正常情况下人们会用多少个 SH 基函数？通常三阶、四阶、五阶，都是非常低频的情况。三阶用来照亮 diffuse 物体已经足够了；glossy 的话可能需要更多一些高频的东西——大家想，glossy 的 lobe 看起来就比较尖锐、比较高频，所以用得比较多的是四阶、五阶甚至更多。而在科研领域，八阶、十阶都仍然会被认为是非常低频的。

具体算一笔账：如果你选择了用 16 个基函数，diffuse 的渲染计算量就是 16——两个长度为 16 的向量做点乘；glossy 的话，自然就是 16 乘一个 $16\times16$ 的矩阵，最后还得到一个长度 16 的向量。

那 glossy 的 PRT 渲染效果如何？效果还是不错的。这是当年的结果，2003 年前后，或者更早：在整个环境光照下渲染一个这么高质量的 glossy 物体，一个是看起来非常不错，另一个是速度其实也非常不错——毕竟那个年代的硬件都是非常早期的。不过大家看到了一个数字：3.6 fps，很明显比 diffuse 要慢很多，自然是因为计算量大。现在就算你什么都不做，正常实现四阶 SH 描述的 glossy——真正算 16 乘一个 $16\times16$ 的矩阵——我估计 100 fps 是没有任何问题的。

顺手再看一个效果对比：考虑正确的 visibility 差别有多大。左边是不考虑 visibility 的结果——假如 visibility 全是 1，得到的结果不怎么真实。比如这尊佛像脚下这个地方，往上这些方向的光会被它身子挡住，你肯定什么也看不到，它接收不到来自上面的光照，所以这里不该那么亮。考虑了阴影之后，效果就还是不错的。

### 接近镜面时：SH 帮不上忙了

正好有同学问过这么个问题：如果 glossiness 非常大——也就是非常高频——怎么办？像这种情况下，就是 PRT 解决不掉的问题了，这是真的。理论上当然能解决，你可以用非常高阶的 SH 来描述它；但 SH 描述这种非常高频的东西，效果并不好。所以接近镜面反射的情况下，你就不能再采用 spherical harmonics 来作为基函数了——你是可以用一些别的东西来做基函数的。

当时也有同学直接回答说：那种时候直接采样就好了。因为物体本身接近镜面反射的话，你是直接知道它如何反射到其他东西的，这种情况下只需要去做光线追踪（ray tracing）就行了，连预计算都不用做。这倒是可以——不同的解决思路。

### 用光路的语言看清 light transport

接下来看另一件事：如果在做 light transport 的时候，把多次反射——比如佛像自己不同部位之间的互相反射——也都做出来，把它们预计算成 light transport 的一部分，也就是引入所谓 interreflection，同样是可以做的。上一讲没有细说这到底是怎么回事：为什么多次反射、多次 bounce 可以被当做是 light transport 的一部分？这个要怎么理解？

这就得用 GAMES101 里稍微提到过的一点东西了：在讲光子映射（photon mapping）这类更高阶算法的时候，我们提到过对不同路径的分类。这里再多提一句：我们可以用一系列表达式，来描述一整个类型的路径长什么样。

先把材质的词说清楚。正常情况下，特别是在 real-time rendering 里，大家把材质区分成三种：一种叫 diffuse；一种叫 specular，指那种完美镜面式的光滑——一个光线过来之后，它会完美地往镜面反射方向走；还有一种介于中间的，叫 glossy，正常的金属就是这种：你说它像镜子吧，它还有点糊；你说它 diffuse 吧，它又不是。如果要求不怎么严格、不会出现歧义，有时候说 specular 其实就是指 glossy；这里咱们说清楚，单独把 glossy 写出来。

有了这些字母，路径就能写了：

- 光线从光源里出来、直接被我看到：记作 $LE$。L 就是 light，E 就是 eye（眼睛）。
- 直接光照：光从光源出发，打到一个物体上——这个例子里是一个 glossy 的物体——然后被眼睛看到，那就是 $LGE$。对通常的物体来说，中间要么是 D，要么是 G。
- 两次 bounce：图里这把茶壶，壶身上反射出了壶嘴的高光——光线从光源出发，到壶嘴，再到壶身，然后到你的眼睛：$LGGE$。
- 一般情况：光从光源出发，打到任何物体上，可能是 diffuse 可能是 glossy，弹多少次随便——零次、一次、两次、三次——最后到你的眼睛，这就是正常的 light transport。这时候可以借鉴正则表达式的描述方法——大家都学过自动机——写成 $L(D\mid G)^*E$。

> **提示**：正则里的星号本来就表示零次或多次，所以"弹零次"的直接光照也包含在 $L(D\mid G)^*E$ 里。

还有一种很常见的情况：比如光线打到戒指的内壁，或者平常喝牛奶时玻璃杯的内壁——内壁这些东西都比较光滑，我们认为是 specular，非常光滑；它会反过来把光打到地面上。假如光从右上角打到内壁上，再打到地面上，最后再被你看到，这是一种典型的路径，记作 $LSDE$：light 打到 specular，然后被聚焦到 diffuse 物体上，最后被你看到。这种东西就叫做 caustics。

> **定义**：caustics，指 $LSDE$ 型光路形成的光学现象——光经 specular 表面（玻璃杯内壁之类）聚焦到 diffuse 物体上，再进入眼睛。

我之前还吐槽过这件事：把 caustics 翻译成"焦散"非常不合适——都"散"掉了，你还看得见吗？不过没关系，我们就管它叫 caustics。

当然还可以再扩展一点：$LS^*(D\mid G)^*E$，道理是一样的。那为什么要这么写？这样一写大家会发现：光线无论如何都是从 light 出发的——所有这些光路左边反正都是 L；最后被眼睛看到——结尾是 E；中间的所有东西，都是 light transport。

那如果这样一来的话，不管它有多么复杂，我最后要算的，无非就是把整个 light transport 给预计算出来，最后的结果我就都知道了。所以说，任何 light transport 的形式，都可以把它分成 light 和剩下的所有东西。

> **结论**：实际渲染时，只要采用了 PRT 的思路、把 light 和 transport 拆分之后，不管 transport 有多复杂，只要之前预计算了，实际渲染就非常简单——实际跑的时间和 transport 的复杂度无关。预计算的时间当然会越来越多，但渲染的时间跟它无关。

| 路径记号 | 光走了哪条路 | 对应现象 |
| :--- | :--- | :--- |
| $LE$ | 光源出来直接进眼睛 | 直接看到光源 |
| $L(D\mid G)E$ | 弹一次 diffuse 或 glossy 后进眼睛 | 直接光照 |
| $LGGE$ | 光源 → 壶嘴 → 壶身 → 眼睛 | 壶身上映出壶嘴的高光 |
| $LSDE$ | 光源 → 镜面（玻璃杯内壁）→ diffuse（地面）→ 眼睛 | caustics |
| $L(D\mid G)^*E$ | 弹任意多次，最后进眼睛 | 一般的 light transport |

### 预计算任意复杂的 transport：一次"奇怪的渲染"

那 transport 到底怎么算？回到 diffuse 那个例子：把 light transport 投影到 SH 上这个式子，上一讲说过理解方式一——把这个函数和 SH 基函数做了一个 product integral。今天说理解方式二：你看这个公式，看起来像不像 rendering equation？仅仅是把 lighting 这一部分给改成了某种函数——这个函数你管它多么复杂、到底是不是 lighting，你都可以把它当成是 lighting。

所以，如果你要把 light transport 投影到某一个基上——比如说第 16 号基——那其实就相当于：你在用第 16 号基函数当做一种光照，用它来照亮每一个顶点，并且把每一个顶点上照亮的结果给记下来。自然而然，你就会得到一个"好像用这种光照渲染了这个场景"的结果。

对任意复杂的 light transport 都可以这么认为：等于是给定了一个光照——就是 spherical harmonics 的某个基函数——你用它正常渲染出来一个结果。既然是正常的渲染，你有光照、有 rendering equation，那用什么方法都可以解：用 path tracing，用什么方法都可以做得出来。所以无论如何，它是可以做出来的。就把 light transport 的预计算理解成一个渲染过程，只不过这个渲染过程是在一些"奇怪的 lighting"下做的。

另外，投影结果那张图显得尤为奇怪，我把它说明白：红色蓝色是因为用了那种可视化方式——把值显示成红色和蓝色，来表示它是正还是负：红得越厉害表示越正，蓝得越厉害表示越负，黑表示零。仅仅是因为可视化，它看起来才比较奇怪；如果换成平常的可视化方法，那就是用这种光照得到的一张渲染图而已。

而且这不只对 diffuse、glossy 成立，对任意的 BRDF 都行。比如各向异性（anisotropic）的 BRDF：像对着这只鸟的肚子打转摩擦出来的那种效果；中间这个金属算是比较正常的；右边这些看起来就不一样了——它们不止有类似各向异性的结果，还有一个属性叫 spatially varying：不同的位置上，可能拥有完全不同的 BRDF。从这个生锈的壶的角度可以看出来，不同地方的 BRDF 不一样。BRDF 本身是四维的；考虑整个物体的话，不同位置有不同的 BRDF，就意味着它变成了一个六维的函数——两维表示不同的位置，另外四维表示在这个位置上 BRDF 的值。更高维了，但是没关系：只要能够把它表述出来，就肯定有办法用预计算来做。

再看一眼当年的结果：这里突然换了一个光照——只要你预计算过这个光照，都没问题。这里是在旋转 lighting；这里变成了旋转视角。旋转光照和旋转视角都可以得到不错的结果。材质换成 glossy 之后，旋转光照自然会有不同的结果，旋转视角的时候也会有不同的结果——这从壶身上高光的变化可以看得出来。

### SH 的天花板与 PRT 的三笔代价

简单总结一下最早那篇 PRT 论文做的事：它提出了用 spherical harmonics 的基函数来描述 lighting 和 light transport 两部分；diffuse 的情况下，实际渲染过程中每个顶点做一个点乘；glossy 的情况下，每个顶点做一个向量乘以矩阵的操作。

当然它有自己的问题。SH 本身有很多不错的性质，但它有一个不好的性质：基本上只适合用于描述低频的函数。

> **易错点**：注意这个措辞——不是说它不能描述高频。只要你给它足够多的项，它就可以描述高频；而是实际中你给不起那么多项，因此并没有多好的高频表示。是"实际中用不起"，不是"能力上表示不了"。

上节课那个例子大家还记得：就 25 个基函数，去描述一个相当高频的环境光照，一旦恢复出来，基本就不剩什么了。上节课没注意的同学再看一眼：那张图用的可不是 25 个基函数，而是 25 平方个——625 个，也就是二十五阶；前面那张 $n=25$ 个系数的，对应的是五阶。用了那么多个，才能基本恢复出一些高频的东西。也就是说，SH 不太适合做高频。

那 PRT 的好处呢？它可以比较准确地算出整个环境光照下、甚至多次 bounce 下整个场景最终渲染出来的结果，当然也可以考虑到准确的 visibility，这是非常好的。但不好的地方在于它做了一个假设：一旦预计算，就意味着固定住了——既然固定住了，场景就不能再动了，所以是静态场景。甚至材质（BRDF）都预计算好了，就意味着不能在场景中动态地改变材质，这就非常不好。另外一点：你需要大量的预计算数据，这些存储或者别的什么东西，会在实际应用中造成不小的负担。

### 后来者的一串突围路线

既然有这么些问题，之后的人们就研究出了各种各样的方法来试图解决它们。

有科学家研究出了各种各样新型的基函数——SH 有点问题了，咱们用点别的，可以。也有人说：现在预计算的是 lighting 和 light transport 两项，那我能不能预计算更多？比如 lighting 预计算、visibility 也预计算、剩下的 BRDF 什么的也预计算——这样到时候就不再是一个所谓 dot product（两项相乘再积分），而会变成三项相乘再积分，以及会不会有更多项？有相当多的研究在做这个事情。还有人发现，PRT 限制了场景必须静态，这自然不好：有没有什么办法，让我既预计算、又允许场景一定程度上发生一些变化？那就非常好了。还有一系列研究，把 PRT 的思路拿到了复杂材质上，比如半透明的材质，还有头发。

最后一条思路相当重要：有人研究说，预计算确实不错，但也有它不少问题，我们如何能够不预计算、争取把所需要的东西都解析地解出来——当然要经过一些近似——那就非常好了。

从这些 follow-up work 上，大家可以看到一个事情：对科学家来说，最难的是发现问题，而不是解决问题。你看，预计算分明就把场景给冻结住了，可还是有科学家研究出了怎么让场景动起来、同时又能预计算。也就是说，只要有了这么一个问题、说我们争取想办法解决，科学家们总是有办法的。最大的问题在于发现这些问题——特别在 PRT 这篇 paper 之前，人们根本看不到会有这些问题：如果没有引入预计算这么一个概念，这些问题根本不存在，自然也不会有人研究。所以：发现问题总是难的，解决问题总是简单的。

这里有一个典型的例子：咱们在讲 PRT 之前讲的 split sum。环境光照下怎么算 shading——不算 visibility 的情况下？那就是典型的解析方法，当然加了一些预计算的项——就是计算了一张表嘛，二维的一张表，但那就非常轻量级了，基本上可以认为它得到了一个解析解。这样对材质的 shading，用那种方法肯定比 precomputation 要容易很多。正是因为在过去差不多十年、甚至十五年——PRT 出了几年之后——有一些方法渐渐开始考虑用解析的方式来解这些问题而不用预计算，导致 PRT 在过去的十年内并没有那么火。

不过我的一个感觉——我的感觉不一定对——在未来，特别是这段时间 real-time ray tracing 的兴起，很有可能会把 PRT 再重新提出来。看看之后是什么样的情况，我自己也挺感兴趣。

### 课堂问答

- **transport 复杂的情况，预计算时间是不是要变多？** 对，没问题。
- **spatially varying BRDF 怎么得到？** PRT 关注的更多是：各个位置上不同的 BRDF 已经知道了，怎么去计算。至于"怎么得到"，正常情况下人们会用一些可控的噪声来描述——GAMES101 里提到过的 Perlin noise 之类。
- **glossy PRT 里视角方向怎么决定？** 不是"视角方向怎么决定"，而是你首先要预计算：对于每一个视角方向、每一个 $\mathbf o$，你都要预计算一套。有同学说矩阵毕竟不能无限大——说的对。观察方向有可能在整个球面上所有方向都有，你肯定还是得从中选择一些：大家会取一个 grid（网格），在 grid 中间去决定视角方向。只要你决定了一个观察方向，其他的所有东西都要预计算一遍——想一想，这是个非常复杂的过程。
- **预计算结果存成 lightmap 吗？** 有同学可能是把这个和 light baking 混在一块了。这里预计算的维度是非常高的，你不能把它简单当成一个二维的表。
- **光栅化里面怎么做这个事情？** 做不了。正因为做不了，才会有专门做 ray tracing 的硬件。现在是可以了：DXR（DirectX Raytracing）已经可以结合在光栅化里面做实时的 ray tracing。
- **预计算也要写在光栅化里吗？** 不需要。预计算程序跑出来的结果存在比如硬盘等地方，做实时渲染的时候再直接把它读出来——要不怎么叫预计算呢。
- **PRT 在工业界有什么具体应用？** 太多了。一直到现在，电影和游戏里面还都在用这些东西；spherical harmonics lighting 肯定到处都是。
- **预计算可以理解成物理材质的一部分吗？** 可以。
- **RTX 相关的问题？** 关于这块就不再多说了，说得有点远了。

### 小波：另一套基函数

前面说了，在 spherical harmonics 之后，大家研究出了各种各样不同类型的基函数，这块研究出了多么"恐怖"的东西：有各种各样的小波来描述二维函数；还有人找到了一系列数学工具，叫做 zonal harmonics——它和 spherical harmonics 什么关系，咱们不说了；还有一些球面高斯函数（Spherical Gaussian，SG），也是二维的函数，理论上来说不应该管它叫基函数，但还行吧；还有之前说过的徐坤老师做的 piecewise constant 基函数。这都是一系列算是经典的工作。这让我想起差不多十五年前那会儿，MSRA（微软亚洲研究院）做了很多很多跟 PRT 相关的工作，那时候做得非常厉害。

这里简单给大家介绍其中一个：小波。咱们不会详细说——如果大家不学信号处理之类的，可能接触不到这个概念；但它还是挺重要、挺有用的，简单提一下。

小波是一系列基函数。我们谈的是二维小波，就是图上画的那一片。小波有一些和 SH 非常不一样的性质。

第一是定义域。不管 SH 的哪个基函数，都是定义在整个球面上的；小波是定义在一个图像块上的，而且不同的小波定义域还不同——比如第三列整个右半边都没有，第三行整个下半边都没有。图里黑白分明的地方，才是这些小波函数各自的定义域。

第二是取值。图里写着正和负，表示这个值是正的还是负的，有点像 step function，就是类似这样的小波。这里说清楚：小波有很多种，我们说的这种叫哈尔小波（Haar），它有明确的界限；也有一些小波长得非常奇怪。但没关系，就是一系列函数呗，只不过不定义在球面上、定义在一个块上。

我关心的是两件事。第一，给你任何一个函数，肯定也可以把它投影到各个不同的小波基函数上去，这没问题。第二，就是小波和 spherical harmonics 不同的地方了：SH 为什么能比较紧凑地描述一些函数？是因为可以先给它一个阶数——只用前多少阶——就恢复出若干频率的原始函数，通过这种方式来压缩。小波的压缩方式不是这样的：给你任何一个二维函数，投影到所有这些小波基函数上之后，你会发现大量的时候是这样一种情况——很多基函数对应的系数接近零。这就自然而然给了一个非常好的压缩思路：取系数最大的多少个，其他很多接近零的系数就不要了、扔掉。这就是人们所说的 nonlinear approximation（非线性逼近）：通过保留非零的、或者说保留最大的多少个系数，来近似描述、恢复一个原始函数。

它和 SH 相比最大的好处，是支持全频率的表示——低频可以表示，高频也可以表示。那就非常厉害了。

| 对比项 | 球谐 SH | 小波（Haar） |
| :--- | :--- | :--- |
| 定义域 | 整个球面 | 图像块上，且各基函数的定义域不同 |
| 压缩方式 | 按阶截断：只用前若干阶 | 非线性逼近：保留最大的若干个系数 |
| 频率支持 | 实际中基本只适合低频 | 全频率：低频、高频都能表示 |

那小波是定义在平面上的，用来描述球面上的二维函数，不会出现缝吗？正好有同学问到——这就是大家聪明的地方：这时候就自然而然用 cube map 来描述球面上的二维函数了，不再用什么 spherical map 或者别的什么。cube map 就是六个面，每个面都是一张图，都是一个正方形的图。对 cube map 来说，lighting 是六张图，每张图单独做小波变换——所谓小波变换，就是把一张图投影成小波的系数。

小波变换做了件什么事？对任何一张图，它先把高频的信息留在右上、右下、左下这么三个小块里，把稍微低频一点的东西集中到左上；然后左上还可以继续再做小波变换，又把高频的东西留下来，低频的东西放到左上……不断做这样一系列的小波变换下去。大家会发现一个事情：高频的东西好少啊——对于绝大多数地方，它好像都是零。这是非常好的一件事情。

```text
┌────────────────┬────────────────┐
│                │                │
│  低频（左上）  │  高频（右上）  │
│  递归继续分解  │                │
│                │                │
├────────────────┼────────────────┤
│                │                │
│  高频（左下）  │  高频（右下）  │
│                │                │
└────────────────┴────────────────┘
```

读图：一次 Haar 分解把一张图拆成三块高频与一块低频，低频集中在左上、还可以继续递归分解下去；几轮下来，绝大多数系数都接近零，留下的非零值非常少。

有同学说这很像四叉树——说得对，没有问题。

多说一个事情：给任何一张图，用小波变换、然后保留非零的这些值，你会得到一个非常强烈的压缩，压缩质量也会非常不错，又能保证高频。这就是为什么有一种图像格式叫做 JPEG：它用了和小波变换挺像的一个道理——说清楚，不是小波变换，是一种类似于小波变换的变换，叫离散余弦变换（DCT）——先把它投影，然后再取投影出来的非零系数，得到非常强烈的压缩。算是补充一个小知识。

那么后面的东西都一样了，只是把 SH 换成用小波来描述。用小波来描述之后，是不是可以得到一个比较好的结果？还真可以：用相同的存储量，小波可以渲染出非常高频的阴影。高频的阴影，就意味着你对 lighting 的描述把高频的 lighting 信息也给描述下来了。

### 小波基的短板：不支持快速旋转

前面我们刚看过用小波（wavelet）做出来的阴影——那张图的效果是真的好。但正好有同学问到了那个问题：既然小波这么好，是不是就能把别的方法都干掉了？这里必须把话说清楚：在图形学里，不太存在一种方法能够完美地把其他所有方法都干掉的情况。小波就有一个非常严重的问题——**它不支持快速旋转**。

回忆一下我们说过的操作：旋转光照，等于旋转 basis。SH basis 在这一点上性质非常好：一个 basis 旋转之后，还可以用同阶的 basis 来描述。但小波就没有这么好的性质了。你要想旋转一个用小波表示的光照？对不起，只能把它当成一张全新的光照来处理：先解开成比如 $6\times64\times64$ 的一张 cube map，再重新投影到小波上，再取出前若干个系数——绕一大圈回到原点，这就没什么意义了，比较惨。

> **结论**：图形学里没有"一招鲜"的方法。小波表示静态光照非常漂亮，可光照一旦要旋转，就得整个推倒重投影；所有方法都有各自的好处与坏处。

幻灯片那个标题列的，是人们在不同基函数（basis function）上做的研究——注意，这些研究并不是针对"动态场景怎么办"这个问题展开的。这一块我真的不能再多讲了：说句实话，单讲 SH，先不算整个 PRT 系列，就已经可以单独开一门课、讲上非常多节了。

PRT 这套东西实现起来比较难写，工业界用得也不算特别多。大家如果想再深入，去参考 Ravi 的那篇 PRT survey——写得最好的一份。

### 进入新话题前的几个问答

正式开讲实时全局光照之前，把同学们的几个问题一起答了：

- **有没有全局光照的作业？** 作业三就是，但它基于屏幕空间，不是今天要讲的世界空间；等讲到 ray tracing 的时候，会把底下这一套道理讲清楚——那是核心。
- **PRT 算实时全局光照吗？** PRT 能做全局光照，没问题；但我们把它归为"介于 environment lighting 和全局光照之间"的东西。
- **PBR 在光栅化和光线追踪下，计算方式一样吗？** 该是一样的——不管用什么方式，肯定只有一种正确的描述方法；但 PBR 做了一系列简化，在合理的范围内，计算方式会得到简化，结果差不多。
- **信号那套后面还用吗？** 我想了想，后面基本不会再多用了；球谐这块，大家理解它的频率问题就够了。

进度上也放心：就算每节课往后攒一点点，中间该多讲的时候会多讲。全局光照这块比较重要，也许会挤占一部分后面基于物理的材质（shading）的时间——咱们把问题讲清楚就好。

### 实时渲染中"全局光照"的确切含义

新话题：实时的全局光照。全局光照能极大地提升真实感，这一点我们已经反复强调过。这里给大家补一个知识点：下面这幅图，是一篇全局光照 survey paper 的 teaser image。什么叫 teaser image？就是论文开头的那幅大图，用来炫耀自己做的东西——通常大家都会下大力气好好做。

看这幅图：很显然，光照来源于天窗那边。很多东西它直接照不到，但画面里没有任何地方是全黑的——也就是说，光线弹射了很多次，才进到人的眼睛。如果只用光栅化做直接光照，这幅图里很多地方都会是黑的。所以全局光照是非常重要的一个环节，一定得想办法把它做出来，否则很多东西看起来就会觉得不真实。

> **定义**：全局光照 = 直接光照 + 间接光照。

有同学立刻会联想到 GAMES101 里做过的那个 hack——严格说那连近似都算不上，完全是 hack——就是 Blinn-Phong 光照模型里的 ambient 项：它假设任何一个点接收来自四面八方的间接光照都是相同的，最后 shading 的结果和自己的 normal 都没关系，说白了就是往结果上加一点亮度。全局光照能这么 hack 吗？完全不能。就拿刚才那幅图看：书本底下各个地方亮度都不一样；桌面上还有金属球反射出来的 caustics——这些东西完完全全不一样。简单地把最后的结果提升一点亮度，绝对做不到全局光照。它很复杂，这就是我们要得到的结论。

直接光照这一半，我们已经能做得很好了——shadow mapping 这一系列的方法完全可以搞定，之后还会继续讲。剩下的就是间接光照：光线在场景中可以弹射无数多次，弹射越多次越不好解。所以在实时渲染中，人们说"解决全局光照"，实际指的是：

> **结论**：实时渲染要解的"全局光照"，就是比直接光照多一次 bounce 的间接光照（one-bounce indirect）。

数一数这幅示例图：光先在红墙上弹射一次，再在小 box 的左面弹射一次，然后被你看到——光线弹射两次，这就是我们要解决的东西。对它人们当然希望两点：第一，简单，实践起来不麻烦；第二，快速——这非常重要，因为全局光照非常难算，等会儿看 RSM 就知道它为什么难算了。

### 次级光源：一次弹射的间接光照

那这一次的间接光照，应当怎么理解？如果还记得 GAMES101 讲 path tracing 时的那幅图：从 camera 出发打一条光线，打到场景中的一个点 p；p 再往各个不同的方向发射光线——打到光源，那它就接收到直接光照了；打到的不是光源、而是另一个点 q，那么从 q 反射到 p 的这个 radiance，就一样参与 p 点的计算。p 点并不关心这个 radiance 是光源直接来的，还是哪个表面反射来的——从 q 反射过来的 radiance，一样在 p 点参与计算。

而从 q 反射到 p 的 radiance 又是什么呢？就是 q 点本身接收到的直接光照，再反射出来的结果。

再多想一步，就得到一个非常好的结论：q 这些被光线直接照射到的物体表面，可以认为它们在场景中会作为光源出现，用自己反射出来的这些光照再去照亮别人。

> **定义**：一切被直接光照照到的物体表面，都会把自己继续作为光源——给它起个名字，叫次级光源（secondary light source）；真正的光源就叫 primary light source。

回到那幅场景图上做标记。先说清楚一点：直接光照可不代表非黑即白——这个场景的光源是天窗，相当于一个巨大的面光源，所以有的地方会有渐变，没关系，这就是直接光照。整个场景里，比如 p 点在柱子后面，无论如何接收不到任何直接光照；但场景中有很多地方能接收到直接光照——我用一个个小太阳把它们标出来（当然标得非常稀疏）。其实任何一个被照亮的表面 patch，比如书本底下那个地方，都在作为次级光源出现。

那么 p 点是怎么接收到光照的？就是拿所有这些次级光源去照亮 p，得到的结果。特别是考虑 one-bounce 的间接光照：从这些次级光源再照亮物体，中间不再发生额外的弹射——这样得到的，就是一次 bounce 的间接光照；把它和直接光照加起来，不就是 global illumination 了吗？

一句话：被直接光照照亮的物体表面，自己作为光源去照亮别人。这就是我们理解一次弹射间接光照的核心图像。

### Reflective Shadow Maps 的两步走

沿这个思路走的方法，叫 RSM——Reflective Shadow Maps，它就是要渲染出这种间接光照。先问一个问题：我想得到 p 点被次级光源照亮的 shading 结果，需要知道什么？很简单，两件事：

第一，哪些是次级光源？换句话说，哪些物体表面的位置被直接光照照到了、照得有多亮（从 0 到 1）。这个问题肯定有同学立刻就能答上来：shadow map 不就是告诉我们这个信息的吗？先只考虑一个点光源，简单一点——shadow map 相当于从点光源看向场景，我看到什么，什么就是能被照亮的。假如光源是 area light，你甚至可以用 soft shadow mapping 那一类方法，得到不同点的入射光强度。这是没有问题的。

第二，这些被直接照亮的 surface patch，各自对 p 点的贡献是多少？每个小太阳都有可能照亮点 p，把它们的贡献一个个求出来加起来，就是 p 点的间接光照。

这里要把 shadow map 重新理解一遍：shadow map 上的任何一个像素（texel），其实都对应场景中的一小片 patch——它们有自己在场景中的位置和朝向。给你一张 $512\times512$ 的 shadow map，你自然而然就有了 $512\times512$ 个次级光源——每个像素内部，就认为是一个小 patch。

于是要做的事情就是：用这么多理论上的次级光源，去照亮点 p。有同学已经想到问题了：这个计算量是不是非常夸张？没错——但它本该如此。要算一次弹射的间接光照，本来就是个 $N^2$ 的问题：所有 patch 都可能贡献所有其他 patch。所以先想清楚问题本身的形状，再说怎么把它做快。

### 出射方向未知：假设反射物都是 diffuse

补一个细节：每一个次级光源 patch，在生成 shadow map 的时候，我们已经知道它接收到光照的方向（从光源看过来的方向）；只要再固定一个观察方向，就能算出它的 shading 结果。但这里的"观察方向"和平时不太一样：最后你是要用这些次级光源去照亮点 p——相当于**从 p 去观察这些次级光源**，而不是从 camera 去观察。也就是说，patch 的出射方向（往 p 去的方向）对不同的 p 是不一样的，你并不知道它。出射方向不知道，shading 怎么算？这肯定是不能算的。

怎么才能不依赖观察方向呢？这里自然而然产生了一个经典的假设：**所有反射物（reflector）都是 diffuse 的**。只要反射物是 diffuse，那我不管从哪个方向看过去——从 p 看也好、从 camera 看也好——看到的都是一样的东西，问题就解决了。

> **易错点**：这里着重强调"反射物"，就是为了区分——我们**不需要**假设接收物也是 diffuse。被直接照亮的次级光源认为是 diffuse；p 点不要求是 diffuse。

所以这不算一个非常大胆的假设，算是正常的，我觉得问题不是特别大；但如果人们还把这个 reflector 认为可以是 glossy，那就太难了。

### 单个 patch 的贡献：从立体角到面积分

现在正式回答问题二：怎么用这些次级光源去照亮一个 shading point p。先回顾一下 GAMES101 里讲过的一组概念——衡量、准确描述光照属性的辐射度量学：flux（或者叫 power），表示总的能量是多少；单位立体角上对应的能量，叫 intensity（全名 radiant intensity）；单位面积上对应的能量，叫 irradiance；单位立体角、又单位面积上的能量，叫 radiance。这块不管什么时候听都是挺绕的，但待会儿要做的推导倒是相对简单。

| 概念 | 描述的量 |
| :--- | :--- |
| flux / power | 总能量 |
| intensity（radiant intensity） | 单位立体角上的能量 |
| irradiance | 单位面积上的能量 |
| radiance | 单位立体角、单位面积上的能量 |

所有的小 patch 都可能贡献到 p，没关系，先考虑其中一个，把每一个都算出来再加起来就行。考虑一个小的 patch——说小，它是真的小：它是 shadow map 上一个 texel 对应的实际 patch。用它去照亮点 p，要解的就是一个 **area light 下的 rendering equation**。大家应该记得 GAMES101 讲 path tracing 时说过：在 p 点对整个立体角做采样并不好，会浪费很多 sample；不如直接在 light 上采样——用变量替换，把对立体角的积分改写成对光源面积的积分。这个公式本身没有任何特殊的地方，就是 101 的内容：

$$L_o(p,\omega_o)=\int_{A} L_i(p,\omega_{pq})\,f_r(p,\omega_{pq},\omega_o)\,V(p,q)\,\frac{\cos\theta_p\,\cos\theta_q}{\|p-q\|^2}\,\mathrm{d}A_q$$

我们最终想要的，是 p 点的出射结果 $L_o$；其中不知道的，是这个 patch 被直接光照照亮之后、往 p 这个方向会反射出多少 radiance——确切说，就是从 q 到 p 的这个 $L_i$——以及 patch 自身的大小。

如果 patch 比较小——它本来就小——这个积分甚至都不用积了。想想黎曼积分：把区间划分得足够小之后，区间内的积分怎么近似？取区间中间的某一个位置就行了。取 q 为 patch 中心的那个点，反正整个 patch 都比较小，把被积函数在这一点的值算出来——BRDF、visibility、cos 项，这些都是已知的量——最后乘上 patch 的真实面积 $\Delta A_q$，就 OK 了。

### 反射通量：两个数并成一个

剩下的问题就是：怎么把"从 q 反射到 p 的 radiance"准确解出来。反射物（q 那个 patch）既然是 diffuse 的，它的 BRDF 就是一个常数，比如 $\rho/\pi$——咱们之前推导过。注意区分：rendering equation 里写的那个 $f_r(p,\cdot,\cdot)$ 是 **p 点**的 BRDF，它可以是 glossy；这里被假设成常数的，是 **q 点（次级光源）**的 BRDF。

那 patch 反射出去的 radiance 怎么和 BRDF 联系起来？回想 BRDF 的定义：出射的 radiance 除以入射的 irradiance。也就是说，出射 radiance 等于 BRDF 乘以入射 irradiance——这里的"入射"指的是 q 点的入射，也就是直接光照那一下：

$$L_o(q\to p)=f_r(q)\cdot E_q,\qquad E_q=\frac{\Phi_q}{\Delta A_q}$$

其中 $\Phi_q$ 是 q 接收到的入射 flux，$\Delta A_q$ 是 patch 的面积。把这个式子代回到前面的求和里，你会发现一个非常好的性质：**面积消掉了**——黎曼近似里本来要乘一个 $\Delta A_q$，而 irradiance 的定义里正好除了一个 $\Delta A_q$。想知道任何一个 reflector 反射出来的 radiance，直接用它的 BRDF 乘以它接收的 incident flux 就行，而 incident flux 是由光源决定的。

人们平常把 $f_r(q)\cdot\Phi_q$ 叫做 reflected flux（反射通量）——这不算一个多么标准的定义，但没关系。对 RSM 上的任何一个像素，为了得到它反射出去的 radiance，要存的就是 reflected flux 这一个数。对比一下：老老实实存的话，得存 incident radiance 和 patch 面积两个数——incident radiance 从光源方向能知道，$\Delta A$ 因为整个场景怎么投影到 shadow map 上你也知道，两个数也能解决问题；但现在一个数就够，何乐而不为。这是这篇 paper 的一个小优化。

于是，p 点收到的间接光照，就是把每个次级光源的这几项乘起来、求和：

$$L_o(p,\omega_o)\;\approx\;\sum_{q}\;f_r(p,\omega_{pq},\omega_o)\;\bigl[\,f_r(q)\,\Phi_q\,\bigr]\;V(p,q)\;\frac{\cos\theta_p\,\cos\theta_q}{\|p-q\|^2}$$

p 自己的 BRDF 不要求一定是 diffuse——glossy 是完全可以做的，这一点说清楚。

### 可见性：算不了，那就不算

这个公式里还剩两个问题。问题一是那个 V。V 是什么？p 点和 q 点到底能不能互相看见——对应到实际应用里，就是任何一个 reflector（surface patch，也就是次级光源）能不能看到我的 shading point p。

这个问题就很难了。为什么？你总不能对每一个 shading point p，都生成一张 shadow map、去看向之前所有的次级光源吧？所有次级光源都要对所有可能的 shading point 判定贡献——又是一个 $N^2$ 的问题。你不可能直接通过一张 shadow map 得到这个 visibility。

不好算，怎么算呢？那就不算了。RSM 里，人们就不去算次级光源和 shading point 之间的可见性——第二个 pass 里这一项就是被忽略掉的。不考虑这个问题，好像也没有特别大：反正这是间接光照，已经不像直接光照那么高频了。

### 距离衰减：平方，而不是四次方

问题二是分母上的距离。我这边推导出来的，是**平方**——这很好解释：它就是把立体角换成 area measure 时必然要产生的那一项，也就是从 p 到 q 的那一下 foreshortening，没问题。

但论文——就叫 Reflective Shadow Maps 这篇，大家有兴趣可以找来看细节——它的公式分母上，是两个距离的**四次方**。这个我一开始百思不得其解。慎重地考虑了这个事情之后，我得出的结论是：他写错了，真的写错了。错的原因我可以猜到：他无脑地沿用了工业界的一个基本假设——radiance 在传播过程中会有平方衰减，也就是说从 q 发出、到达 p 的时候再除一个距离的平方。这个假设是非常不对的：radiance 沿着一条线传播，本来就不衰减；当初人们做平方衰减的假设，多半就是为了凑上这么一个平方项，结果在这里等于把距离衰减 double count 了一遍。

> **提示**：radiance 沿光线传播（真空、无介质）是不衰减的；随距离平方衰减的是分摊到单位面积上的能量那一系（irradiance）。看到 radiance 再多除一次 $d^2$ 的写法，就要警惕是不是 double count 了。

所以它绝对应该是平方。有兴趣的同学可以自己推导一下，如果觉得我推得不对，欢迎来找我。要真是四次方的话——同学们，我直播吃键盘，怎么样？这个 flag 我立下了。

另外，论文里 p 和 q 是反的：他们把 p 当成照亮 q 的一方。没关系，不影响理解。

### 只用身边的次级光源：投影、采样与权重

到这一步，任何一个次级光源怎么照亮任何一个 shading point，就已经解决了，剩下的是一些工程上的小问题。RSM 的场景里，光源照亮整个场景，shadow map 上每个 texel（论文里标的 $x_1$、$x_2$、$x_{-1}$……）都对应实际物体上的一个 patch；按刚才的公式，它们似乎都应该对 shading point x 有贡献。但有时候，这些东西根本不需要算——你知道它百分之百不会有贡献：

- **从方向上就能看出来。** 以 $x_{-1}$ 为例：shadow map 记录的是桌面，这个 patch 的法线朝上；而它和 shading point 的连线朝另一个方向去——它根本不可能照亮 x。rendering equation 本身就能解释这件事，这里给大家一个形象的说法。
- **从距离上也能看出来。** 贡献经过距离平方那一项，离得非常远的次级光源，贡献本来就已经非常少了。给任何一个 shading point，只找离它足够近的这些次级光源，是不是就 OK 了？这是一个不错的观察。

这个观察会引出一个很不错的技巧，也是这篇论文一个极大的假设：给你一个 shading point，你怎么知道离它比较近的次级光源都在哪、都在 shadow map 的哪？世界坐标下找不好找，那就把 shading point p 投影到 shadow map 上，在它周围一圈的范围内去找——认为 shadow map 上离得近（比如深度也离得近）的，就在世界坐标里离得近。通常情况下这不算不合理，但这确实是一个比较大的假设。

为什么非要这么省？因为每个 shading point 都要把所有 texel 的贡献各算一遍——一个点 $512^2$ 次，这还得了。所以要尽可能减少要算的数量。即便缩小到了周围一圈，范围仍可能不小，那就用聪明的采样办法——跟 PCSS 一个道理：给你一个范围，要做 blocker search、要做 filtering，你不希望把范围内所有 texel 都走一遍，随机采样一些就可以了。至于这篇论文具体的采样方案——哪些地方多采一点、哪些地方少采一点但权重大一点——大家可以大胆想象：离 shading point 对应位置近的地方，采得密一点；离得远的地方，采得疏一点。采得疏，意味着你把很多像素的贡献当成一个了，那这很多像素占据的面积肯定要增大，对应的权重自然就要大一些。都是非常 heuristic 的工业 trick，这里不再多说。

> **提示**：采得疏的地方权重更大——一个样本代表了一大片像素的贡献，面积大了，权重自然要跟上。

不管怎么样，通过这种方式，计算量被压到了（如果我没记错）几百个——400 个吧：对任何一个 shading point，从 RSM 上取大约 400 个 texel 当作次级光源，来照亮它。400 比 $512^2$ 好太多了。

### RSM 的存储清单与实战表现

总结一下：RSM 就是在 shadow map 上多存了点东西。shadow map 本来要存 depth；在此之上：

- **世界坐标**：shading 时要用来判断两个点的实际距离；
- **法线**：反射物（次级光源）的法线，用来算 cos 项；
- **flux**：就是前面的 reflected flux。它跟光源相关、和各个表面的法线都没关系，所以这一通道存下来，看上去就像在做一个很平的 area light shading。

为什么存这几样，前面的公式都已经讲清楚了。

那效果如何？对某些现象，效果是非常好的——特别是**手电筒**。现在的游戏里一旦涉及手电筒，都非常愿意用 RSM。我猜的原因是：手电筒覆盖的范围相对较小，不需要一张很大的 RSM，分辨率就可以压得比较低；分辨率低就意味着快，所以特别适合手电筒这种场景。

效果对比可以看《最后生还者》（The Last of Us）：下一行开启了 RSM，上一行没有——下一行明显更亮。有同学说，好像就亮那么一点点，有什么实际作用吗？有。看天花板：绿的一块，就是藤蔓反射出来的结果。间接光照肯定比直接光照暗很多，但正因为这么一点点细节，整个画面看起来就会好特别多——这是真的，来回切这两张图就能看出来。

不止 The Last of Us：战争机器 4、神秘海域 4，很多游戏都在用 RSM 做手电筒。

### 优点、局限与两个延伸

RSM 的好处，其实一句话就能说清：它就是 shadow map 的流程。

```text
Pass 1  从光源渲染一张 RSM：每个 texel 记录 depth + 世界坐标 + 法线 + flux
Pass 2  从 camera 正常渲染：每个像素就是 shading point p，
        把 p 投影到 RSM，取周围约 400 个 texel 当次级光源，按公式求和
```

第一个 pass 生成一张 RSM；第二个 pass 从眼睛开始看场景，每个像素就是要 shading 的点 p，把各次级光源的贡献算出来加起来。容易实现，这是它的优点。

但问题是非常多的。第一，它会继承 shadow map 自己的所有问题——不管它叫什么 RSM。说清楚，这里的 light 数量指的是直接光源（primary light source）的个数：有多少个直接光源，就得做多少张 shadow map，也就得做多少张 RSM，这就不好了，会越来越慢。第二，可见性没算。反射物到 shading point 之间不做可见性判断，自然而然会造成很多不真实的情况——人眼（或者说我们平常训练出来的大脑）是非常厉害的，看到画面立刻就能分辨出这些结果不自然、不真实，很多情况下就是因为缺了这一块。而且这块是真做不了：想想环境光下怎么对一个 shading point 做阴影——环境光来自四面八方，每个方向都不同，照亮不同的 shading point，又是 $N\times M$ 或者 $N^2$ 级别的问题。实时渲染里这类问题到今天仍然不太好解决。第三，它做了很多不同的假设：反射物必须是 diffuse；"shadow map 上的距离在一定程度上反映实际距离"；还有采样本身——sample 多，效果好但慢；sample 少，快但效果差。写过 PCSS 作业的同学应该已经体会到了，它永远有这么一个 trade-off 在里面。

在这之后，我再补两个点。其一，RSM 把 shadow map 上任何一个小的像素都当成一个 surface patch 来看——这和离线渲染中的一个重要概念非常接近：**virtual point light（VPL）**。更广义一点说，VPL 方法属于一个更大的框架，叫做 **instant radiosity**（即时辐射度，IR）。radiosity 最早不是基于光线追踪的；instant radiosity 引入了 VPL 方法，而且它可以和光线追踪结合得非常好。之后再看到文献里提到 VPL，理解成这种小的 surface patch 或者点光源，都没问题。

其二，图像空间还是三维空间？我们平常说 shadow map 是图像空间（image space）的做法：第一个 pass 就把场景变成了一张图，之后再渲染什么，都从这张图里找信息。RSM 也是一样——经过一次 RSM 生成，需要的所有信息就都有了；第二个 pass 从 camera 正常渲染每个点，就得到结果。按这个说法，它应该算图像空间方法。但我在这里把它归为 3D 空间，是因为我想这么来分类：这种方法不会受到最后 camera pass 可见性的影响——不存在"一开始就记录不到、理论上就会丢失信息"的情况。图像空间方法的问题在于，图像只能记录图像看得到的东西；而 RSM 基本上真正记录到了所有需要的信息。

另外一点，接下来要讲的 LPV 方法，会建立在 RSM 的基础上——今天没时间讲了。下节课我们讲 LPV 和 VXGI，应该会讲得非常快，着重说具体方法怎么做；然后再讲图像空间的方法——名字里带 SS 的就是指屏幕空间（screen space），这类方法还有好多。作业二顺利的话，这周末发布。

## 实时全局光照：LPV、VXGI 与屏幕空间的开端
> 对应块：BLK15 | 覆盖分集：P08上 | 块标题（分集名）：《Lecture8 Real-time GLoba》

上一讲我们把 PRT 收了尾：从 glossy 物体的预计算辐射传输讲到它的代价，又讲了用 wavelet 这种基函数代替 SH 的延伸，好处坏处都摆过一遍；真正的重头戏是 RSM（reflective shadow maps）——它和 shadow map 共享同一个基本思路：shadow map 里看到的东西，自然就是场景中直接会被照亮的部分；而直接被照亮的东西，就可以当作次级光源，在间接光照中反过来去照亮别人。整个实时全局光照，差不多都是沿着这么一条思路来解决的。

这一讲接着往下走：先把 3D 空间（世界空间）里剩下的两个方法 LPV 和 VXGI 补完，然后正式进入屏幕空间的方法，按计划争取把 SSAO 和 SSDO 讲完；屏幕空间的反射（SSR）留到下一讲。

先打个预防针：LPV 和 VXGI 不会像上一讲的 RSM 那样掰开揉碎地讲——不是它们不重要，恰恰相反，而是里面的细节实在太多，我尽量把逻辑讲清楚。听完你很可能还是不知道怎么动手实现，这很正常：3D 空间中的实时全局光照确实是个不小的挑战。之前有同学想在大作业里挑战实现一下 LPV 或 VXGI——没那么容易，自己实现出来跟工业界 demo 的效率差个十倍，是非常正常的事情。

### LPV：在三维网格里传播光

#### 名字里就有思路

LPV，light propagation volumes，光传播体积。这名字起得其实非常好：看到名字基本就能猜出它是个什么思路——volume 是体积，也就是说要在三维空间中传播（propagate）光线，然后拿传播的结果做间接光照。

历史也值得一讲。LPV 最早是在 Cry Engine 3 里引入的，如果没记错，就是为了做 Crysis——中文叫《孤岛危机》，人称"显卡危机"：那个年代这个游戏用了一堆各种各样的新技术，对显卡是非常巨大的挑战，所以人们这么称呼它。LPV 就是其中的一项重要技术，把全局光照做得非常好。它有两个非常好的性质：第一，非常快；第二，质量也非常好。这也正是它存在的意义——之前说过 RSM 有它的问题，LPV 能在一定程度上解决其中一部分。

多说一句这个工作是谁做的：Anton Kaplanyan，超级大神，也是我的合作伙伴。他后来去了 Facebook，我们最近还在讨论合作项目。我和清华合作的那篇 paper——"从直接光照去猜测间接光照"的工作——他特别喜欢，最近好像还在带一个队伍，想从那个工作出发，用神经网络相关的东西继续做全局光照。这个方法后来得到了非常广泛的应用。

#### 物理起点：radiance 沿直线传播不变

LPV 看到的核心问题是这样的：为了做全局光照、做间接光照，我要的其实是一样东西——在任何一个 shading point 上，如果我能立刻知道间接光照打过来时、来自所有不同方向的 radiance 各是多少，我就可以做间接光照了。

这话说了跟没说一样，对吧？这本来就是我自然得知道的事情。但问题一旦被总结成这么一句话，就可以针对性地去解决了：对任何的 shading point，我都能立刻查到它的入射 radiance——这是最好的。那凭什么能"立刻查到"？

LPV 用的是一个关键的物理事实——这不是假设，是物理事实：radiance 在空间中沿直线传播的过程中，是一个不变的量。从这一点开始发出某些 radiance，沿直线到达另外一个位置，这条线上的 radiance 不变。这个概念我们老早之前就在用：path tracing 里从 P 点打出一条线到 Q 点，Q 点接收到的直接光照、沿往 P 点走回来那个出射方向对应的 radiance，就是 P 点接收到的 radiance——我们一直认为沿同一条线它完全一样，没问题。radiometry 那会儿也专门提过这件事。radiance 在传播过程中不会被改变，这就是整个方法的地基。

> **易错点**：有同学联想到"平方衰减"——那是另一个量的事情。intensity 之所以随传播衰减，是因为传播过程中面积不断增大，单位面积上的强度自然就降低了；radiance 跟这个没关系，它本来就是定义在基本一条线上、为描述传输而产生的一个量。

#### 四步流程：生成、注入、传播、渲染

最 high level 地讲，LPV 分成这么几步：先知道哪些点会作为次级光源——这是跟 RSM 一模一样的，即哪些点接收到了直接光照；然后把这些光源放进场景划分好的格子里——不放到格子里，怎么从这个格子传播到其他格子呢；有了起点，就在三维网格中传播 radiance；传播完成，整个场景全覆盖，任何一个位置从任何一个方向来的间接光照 radiance 都知道了，直接拿去渲染。听起来是非常正确的一个思路。

```text
  [直接光照] ──找被照亮的表面──► [次级光源（虚拟光源，可采样缩减）]
        │
        ▼ 注入 injection：把出射 radiance 放进光源所在的 voxel
  [3D 网格]（工业界直接用 3D 纹理）· 每个 voxel 用 2 阶 SH 共 4 个系数
        │
        ▼ 传播 propagation：穿哪个面就交给哪个邻居（6 向），迭代 4~5 次到稳定
        │
        ▼ 渲染：任意 shading point 查所在 voxel 的 SH 入射 radiance，直接用
```

读图：从上到下就是一次完整的 LPV 计算，前三步都是在为最后"任意位置立刻查表"这一步做准备。

**第一步，生成（generation）。** 跟 RSM 一模一样：先把直接光照算好，被直接照亮的物体表面就是次级光源，它们往外发出的 radiance 就是间接光照的来源与起点。上一讲 RSM 的老问题在这里依旧存在——有多少个直接光源，就得做多少次 RSM，这个方法并不解决这个问题。当然，不必要把所有被照亮的表面、所有像素都当成次级光源，可以在其中采样一些，把当做次级光源的表面数量降下来，RSM 里就是这么做的——于是得到一系列虚拟光源，就是示意图里那些小太阳。

**第二步，注入（injection）。** 这一步人家起了个名字，叫注入。场景先要有一个 3D 的格子——3D 的场景切开，切豆腐一样。每个格子叫一个 voxel（体素），类比 texel（纹素）就明白了。工业界的做法是直接用一个三维纹理：纹理不见得一定得是二维的，可以是三维的，没问题；你可以定义任何一个 texel 它对应 3D 空间上哪一个 voxel，这样格子就齐了。然后看任何一个格子内部：里面的虚拟光源朝向可能各不相同，把它们往各个不同方向的 radiance 都算出来、加在一起，就是这个格子往四面八方的 radiance 初始分布。这是个方向上的分布，自然可以压缩——拿什么压？SH。所以又一次看到 spherical harmonics 是非常有用的东西。工业界用了多少 SH 呢？就用了四个，也就是两阶：第一层 1 个、第二层 3 个，就那么多——用四个 SH 基函数表示这么模糊的、大概的一个 radiance 分布。很粗糙。之前推导过，diffuse 物体接收光照至少得按三阶来处理，但工业界很多大胆假设两阶：总共四个数，就可以表示这个格子往四面八方的 radiance 分布初始值。

**第三步，传播（propagation）。** radiance 不是沿直线不变的吗？那就认为它位于格子的中心、往各个不同的方向去。一个格子有六个面：穿过上表面的这些 radiance，很明显都会被它上面这个格子收到；穿过右表面的，都会被右边这个格子收到。原本四面八方都有的分布里，真正朝右的只有右边这么一小块——这块就被右边的格子收下来；朝左的本来就挺少，再穿过左边这个面，就更少了。空间上一个格子会传播到它周围的六个格子里去，贡献直接加起来，接收方照样用 SH 来表示。每个格子都往周围六个格子扩散，不断重复这个操作，直到整个网格稳定下来——这是图形学乃至整个计算机科学都经常用的迭代方法。迭代多少次能变得比较稳定？差不多四五次，是一个非常小的数目。

几个自然的疑问，在这里一并回答：

- 传播时要考虑格子之间的可见性（visibility）吗？不考虑。这和 RSM 是同一个假设，一旦考虑 visibility 就非常难了。
- 斜对角的格子不计算传播吗？不计算。想想斜对角是怎么"穿"过去的：当前这个点先传到它左边的格子，左边这个格子再传到它上面的格子——先往右传、再往上传，跟你直接往右上角传是一样的，没有区别。
- 只往六个面传播，会不会漏？就六个面传播，省得你去考虑 27 个邻居；一个格子可以被周围六个面同时贡献，也可以贡献给周围六个面，是对等的。
- 光在格子间传播时会改变方向吗？不会，光怎么会改变方向呢。不考虑 multi-scale 或 cascade 的概念时，这里也没有 KD-tree 那种层次结构，就是空间中划成几乘几乘几的格子。
- 场景里有雾、云、烟这种 volumetric 的东西怎么办？有雾其实没问题，只不过传播方式会变得不一样——光线不再是直线了。我之前读到过一篇 paper，就用 LPV 的思想来解决云、烟雾里面的光线传输，有人这么做的。

> **提示**：一直迭代下去，最后一定收敛到稳态吗？会。就像往池塘里投一块石头，波纹荡来荡去最终会稳定下来；光线传播没有其他外力，最后肯定会通过这种方式达到一个稳定的状态。

**第四步，渲染。** 传播完成之后，场景中任何一个格子的入射 radiance 都知道了。渲染时对任意 shading point，找到它所在的格子，把这个格子收到的入射 radiance（所有方向、SH 表示）拿出来，自然就可以用它来做渲染了。

最后补两句性质：LPV 不是预计算的方法，它是实时的，每一帧都要把这套计算整个做一遍；每个 voxel 里存的东西，你可以理解成一份 light transport，这么理解没什么问题。

#### light leaking：格子比几何粗的时候

听起来非常美好的方案，会不会有什么问题？从一幅图上就能一目了然。想象一堵墙：它的左半边会被直接光照照亮，然后往四面八方反射——不对，它反射出去肯定是往左边的。这一点咱们说清楚：左半边这个点反射出去的 radiance，绝对不可能照亮右边那堵墙。但是由于你把整个场景分成了格子，注入的时候又把这些所有点发出的 radiance 都当成整个格子上 uniform 的一个分布，于是 P 点的 radiance 会被认为在它所在的格子里处处相同——那它就会照亮自己的背面、照亮格子里的这一整面。棚子的顶明明是朝上的，它怎么可能照亮自己的底下呢？正常情况你应该得到正确的结果，LPV 却给你漏光的结果。这就是 light leaking（漏光），和之前 VSM 出现过的问题如出一辙。

> **结论**：light leaking 的根本原因，是场景里有一段非常细的几何，它的粒度比一个格子还要小——当几何比格子还细时，"格内均匀"的近似必然出错。

那把格子划分得无限小行不行？至少能想到两个问题：第一，存储——3D 空间里格子划得那么细，存储吃不消；第二，做传播的时候要考虑的格子数量更多，计算也会比较慢。那能不能自适应地划分？能，而且工业界会用：用不同分辨率的格子一起做传输和计算，这完全没问题。这种基本方法在实时渲染工业界就叫 cascade；在学术界或者离线渲染，大家管它叫 multi-scale，或者叫 level of detail（LOD），都是一回事——相当于给这些基本设计加一层层次的安排，属于这类方法的标准配置，VXGI 里也有。至于格子一般划多大合适：数量上至少要比像素的数量少一个数量级。

#### 效果与适用边界

看例子。直接光照在不断发生变化的时候，间接光照也会跟着不断发生变化。换成带纹理和最终颜色的场景更直观：一块移动的红布，让它附近的表面都会反射出红色——红布被直接光照照亮，其他地方收到它给出的间接光照，布移到哪里，附近就越来越红。说明 LPV 是一个非常不错的方法：挺稳定，对动态物体的处理也非常好。

不过有一处要较真：glossy 的接收物行不行？之前顺口提过一句"对 glossy 的接收物同样也没有问题"，但认真想一想——voxel 里面的分布既然用 SH 来表示（还只用了两阶），glossy 物体的反射分布一旦进 SH 就会糊掉。所以结论是：LPV 虽然没必要假设反射体是 diffuse 的，但只要用了 SH，基本就得把它当 diffuse reflector 看待。LPV 就认为它只能处理 diffuse。

最后看看现在的游戏在用什么：LPV 还一直在用，没有问题，用得还很多；另外现在还有一些基于 probe 的方法，咱们暂时先不说，我想把它放到后面，跟实时光线追踪放在一块讲。

### VXGI：体素化全局光照

#### 又是体素，思路却反过来

VXGI，voxel global illumination，体素全局照明——又一次出现了体素，场景中又出现了格子这个概念，只不过它和 LPV 是完全不一样的一个思路。先说整体：它仍然是一个两趟（two-pass）的算法。大家会发现实时渲染里很多方法都很喜欢拆成两趟来算——RSM 也是这样；其实真算起来，LPV 算是四趟的算法，比较麻烦，VXGI 基本就是两趟。实时渲染有很多类似的思路：拆分成不同的 pass，每一个 pass 解决不同的问题。

两趟的算法，人们自然要问：它和同样两趟的 RSM 有什么区别？这里提供两个主要的区别。

第一，次级光源的载体从像素换成了体素。RSM 里，次级光源都是每个像素所表示的一些微小的表面；VXGI 里，你的场景是已经完全离散化成一系列的格子。这个非常好理解：把场景理解成一个用乐高堆出来的场景就好了，或者像《我的世界》一样，就是这种场景的表示方法。而且这些格子在这里会用一个所谓的 hierarchy（层级结构）组织成一棵树形结构，有小的有大的：最细的层级是最小的那些格子，分布在物体表面上；再往上做一个层级，格子大一些；同样道理，最后可以建立出来一棵树。

第二，第二趟从 camera 出发。这一点和 LPV 完全不同。LPV 的思路是：考虑任何一个 shading point 要接收到什么样的 radiance，靠传播的方式，从次级光源开始一路传播到不同的 shading point；而且传播在整个场景里只做一次——不管用了多少张 RSM，只要注入完成、传播做完，场景中所有 shading point、任何一个位置接收到的间接光照 radiance 就都知道了。VXGI 不这么干：第二趟从 camera 出发，还是一样去渲染整个场景——好像有一根 camera ray 打到任何一个像素上，根据这个像素本身的材质决定怎么追。比如 glossy 的材质，camera ray 达到一个 glossy 材质，会变成类似一个锥形的东西往外反射；然后看这个锥会相交到场景中哪些已经记录好的体素，这些体素对 shading point 的贡献自然就可以算出来。相当于每个 shading point 都要做一遍所谓的 cone tracing（圆锥追踪）：ray tracing 里你 trace 一根光线，这里对 glossy 的表面你 trace 出来一个锥。这样一想就知道，这个方法肯定比 LPV 要慢——LPV 整个传输只做一遍，这里 cone tracing 每个像素都要做一遍。当然可以优化，之后再说。

#### 第一趟：light pass

第一趟做所谓的 light pass，决定哪些地方、哪些 voxel 会被照亮。还是要从哪些 patch 会被直接照亮开始，这里说得简略一点：你不管拿什么样的方法去做——RSM 也行，别的什么方法都可以——只要你能算直接光照，知道任何一个 patch 的直接光照就行。然后因为这个场景被认为是用 voxel 表示的，对任何一个小格子做和 LPV 注入非常像的事情：记录这个格子里面所有表面反射光照时的分布。

LPV 那里的做法，是认为反射面都是 diffuse、出射是半球形的分布，再用 SH 压缩；VXGI 做了一个比较聪明的做法，可以支持反射物本身也是 glossy 的：一个 voxel 里记录两样东西。一是光源主要从哪些范围来，也就是 incident lighting 的分布，记成一个某种分布、一个 lobe；二是这个 voxel 里面用来反射这些光照的表面们，它们的法线的分布大概是什么样。这样一来，你有输入方向的分布，又有法线大概在哪一个范围内的分布，这两个范围一拼，不管这个格子到底是 glossy 还是 diffuse，都可以直接算出它出射的分布。这自然就比你之前一个格子假设反射面全是 diffuse、再用 SH 压缩，要准得多。

一个小格子可以这么做，把很多小格子的输入方向和法线分布都考虑在一块儿，就相当于可以建立这么一个 hierarchy——这就是第一步，所谓 light pass。有同学问：高层的体素是不是把这些小的体素中间记录的分布都给平均起来？没那么容易——这倒更多是"收集在一块"，不是简单平均。

#### 第二趟：cone tracing

第二趟开始实际考虑渲染：考虑任何一个像素，你知道 camera 的方向，那自然知道，如果这个像素是 glossy 的，这一根 camera ray 就会被反射成一个圆锥，这就是所谓的一个 cone。

最简单、最朴素的方法怎么做？从 shading point 连出一个锥，场景中所有的 voxel 你都判断一下是不是和这么一个圆锥相交，相交的话，就把这个体素对 shading point 的贡献算出来——反正刚才说了，任何一个体素都有光照输入方向的分布，又有法线分布的方向，你肯定可以算出它贡献到任何一个点是多少。但这样是不是会非常慢？而且咱们既然已经建立了一个 hierarchy，何必这么做？

注意一个几何事实：圆锥在传播过程中是越变越大的。一开始它覆盖的空间范围很小，越往后传，覆盖范围就越大。那我干脆根据圆锥离初始点的距离，大概算出它此刻覆盖的范围有多大；然后根据这个范围的大小，直接到之前整个场景 voxel 表示的 hierarchy 上找对应的层级——使得找到的那个层级上的一个块，差不多正好就是圆锥往前走到达这个地方所覆盖的范围。锥传得越远、变得越大，我就在更大的层级上找之前记录好的体素信息，这不就行了吗？这样为了 trace 出哪些体素能对起点的 shading point 有所贡献，二维示意图里只用查四次就差不多了——是个挺轻量级的做法，省去了每次都去查最小的、最细的体素。当然，每一个 shading point 都这么做，还是挺慢的。

有同学问到底要查多少次：刚才说的四次，只是二维示意图上一个随口一说的量级，实际是多少并不知道，取决于 glossy lobe 到底多宽；对 diffuse 来说，圆锥的数量增多了，要查的次数肯定也跟着增多。

#### diffuse 半球的笨办法：一把小圆锥

那马上有同学会问：glossy 的物体，camera ray 打上去反射出去是一个圆锥，那要是 diffuse 呢？这不就出事了吗——camera ray 打到一个 diffuse 物体上，它往四面八方都有反射，难道要反射出一个 180 度的圆锥？那不是场景中所有东西都在里面了吗？

这种情况下，可以把它考虑成一个超大号的圆锥；但是发明这篇 paper 的人们认为，不如用若干个小的圆锥，把整个反射的这么一个巨大的半球给覆盖住，然后每个圆锥的贡献把它加起来就好了，这样算也不错。对这个例子来说是画了八个圆锥，对一个 diffuse 表面，八个圆锥差不多就覆盖了。每个圆锥的中心和大小都是预先分配好的：你要覆盖一个半球，老早就可以算好每个锥应该往不同方向的哪儿去、每一个该多大。

至于圆锥和圆锥中间有缝、彼此之间还会有一些 overlap，这些不准的问题都不大——基本上对 diffuse 来说，完全可以接受。

#### 一对镜像：LPV 与 VXGI 摆在一起看

到这里，VXGI 基本就是这么做的。把它和 LPV 摆在一起看特别清楚——这两个体素方案恰好是一对镜像。

LPV 是把所有次级光源发出的 radiance，先传播到整个场景的任何一个地方去——传播只做一次，之后谁都可以查；但由于它用的格子以及 SH 表示，不怎么准，不过它会比较快。VXGI 则还是一样，把所有次级光源都记录下来，并且记录成一个层次结构；然后对任何一个 shading point，自己去找到底哪些次级光源能够贡献到它，用所谓 cone tracing 的方式。这样一来可以得到一些比较不错的效果，自然而然造成的代价就是会比较慢。

| | LPV | VXGI |
|:---|:---|:---|
| 次级光源的载体 | 体素，出射 radiance 用 2 阶 SH 压缩 | 体素 + hierarchy，记录入射 lobe 与法线分布 |
| 间接光怎么到 shading point | 全场传播一遍，所有位置共享查询结果 | 每个 shading point 自己做 cone tracing 去查 |
| 速度与质量 | 快；格子与 SH 表示粗糙，还会 light leaking | 慢；质量高，做法已经很像 photon mapping |

```text
  Pass 1 · light pass
    直接光照（方法不限，RSM 也行）
      └─ 每个 voxel 记录两个分布：incident lighting 的 lobe + 法线分布
      └─ 两个分布一拼 → 推出出射分布（glossy / diffuse 都行，比 LPV 的全 diffuse + SH 准）
      └─ 小体素逐层收集（不是简单平均）→ hierarchy

  Pass 2 · 从 camera 出发逐像素渲染
      glossy：camera ray 反射成一个锥；锥越传越大，按覆盖范围查对应层级（二维示意约 4 次）
      diffuse：约 8 个预分配的小锥盖住半球，各锥贡献相加
```

读图：第一趟把场景变成一棵"带着光照信息的体素树"，第二趟每个像素自己到这棵树上查自己该收的间接光。

#### 效果、代价与工业落地

NVIDIA 当年放出来过一段官方 demo，看一遍就明白了。从 direct lighting 开始：只有直接光，所以下半部肯定照不亮，完全是黑的。然后看到场景已经被描述成一些 voxel 了——所有表面，原本的那些大的面也都变成了格子；球上还能看到一些 artifact，那是采样造成的，是标准的 pattern。这段视频我记得挺啰嗦的，每一个地方都展示很长时间；其实不太需要去区分这些 voxel 具体描述的都是什么东西，理解成差不多那样就行。接着调另一个光源再照亮场景，用刚才的体素来渲染场景的间接光照，得到的结果看起来非常漂亮——质量非常高，因为体素对场景的表示本身就表示得非常好了。最后把间接光和直接光加在一块，就得到一个看起来非常不错的最终结果。更多的例子，网上可以找到一大堆。

VXGI 的质量在那个年代可以认为是非常不错的，比 LPV 肯定要好；但是由于开销还是大了一点，它的应用受到了一些限制。还有一个更重要的原因，不知道大家想到没有：你要想把一个场景先给体素化，这是一件非常麻烦的事情，很可能是需要预处理的；特别是对于一些动态的物体来说，它动起来，每一帧是不是都要重新体素化？这是非常麻烦的一件事情——你要实时地去体素化，又会非常慢。而且大家也看到了，它的体素是非常小的。这是它比较大的问题。

即便 VXGI 开销很大，后来硬件跟上来了。VXGI 最早应该是发在 2012 年的一篇 paper 上（如果我记得没错）；再后来 PS4 出来了，他们的硬件就比 2012 年的要好很多。我有一个博士学生叫周扬，他在加入我们组之前实现过 VXGI——实现到 PS4 的《蜘蛛侠》游戏里。《蜘蛛侠》那个游戏的全局光照做得特别好，就是因为 VXGI 这个技术做得确实好。VXGI 确实可以得到质量相当高的全局光照。另外一点，它效果好的原因是：它已经非常像我们之前所说的 photon mapping 的方式了，很像离线渲染在做的一些操作——每一个像素都要做一次 tracing，自然而然结果就会好一些。到这里，三维空间中的这批方法就说得差不多了。

### 屏幕空间方法是什么意思

#### 只知道屏幕上看得到的东西

接下来进入屏幕空间（screen space）的方法，目的同样还是做全局光照。那什么是屏幕空间？人们一直这么说，到底指的是哪些限制？我们想一想。

屏幕空间，顾名思义：你所有能够拿到的信息，基本上只有屏幕空间上的——也就是你屏幕上能看到的东西；话说回来，也就是在你做全局光照之前，你在屏幕上能够看到的东西。那做全局光照之前，屏幕上能看到什么？自然只能看到直接光照，这肯定没有问题。

所以屏幕空间的方法指的就是：你仍然还是从 camera 角度渲染这个场景，在做全局光照之前，先得到的这个直接光照结果——这就差不多是屏幕空间方法开始要用到的所有信息了，没有其他的信息了。比如沙发背后是什么？不知道，因为你从 camera 这边看，根本看不到那边是什么。你所有知道的信息基本就是这张图：direct illumination。那你要干嘛呢？相当于是对这张图做一个后期处理、一个图像空间上的操作，然后用各种各样的办法，把全局光照给弄出来。

> **定义**：屏幕空间方法的全部输入，就是"做全局光照之前的那张直接光照画面"；全局光照从这个起点上，用图像空间的后处理手段算出来。

顺带把之前许过的愿还了：我和清华合作的、Anton 特别喜欢的那篇 paper，做的事情很简单——想训练一个神经网络，给你直接光照，你去把间接光照给猜出来，然后把两者加一块得到全局光照。从效果上看好像还是 OK 的。

#### 三个空间的分家

严格意义上来说，可以把这几个概念分一分。RSM 可以把它当做图像空间（image space）——它毕竟很多信息来自于从 light 开始的那一边，你是从 shadow map 里面得到的；马上要说的 SSAO、SSDO 这些，那都叫屏幕空间（screen space）——信息基本上都来自你当前这个屏幕，也没有什么其他的视角；LPV 和 VXGI 自然就是我们刚才说的 3D 空间，或者叫世界空间（world space），一回事。

| 空间 | 代表方法 | 信息来源 |
|:---|:---|:---|
| 图像空间 image space | RSM | 从光源出发，shadow map 里的信息 |
| 屏幕空间 screen space | SSAO、SSDO | 当前屏幕这张直接光照图，没有其他视角 |
| 世界空间 world space | LPV、VXGI | 三维空间中的场景表示 |

做这么一个区分就好：屏幕空间的起点，就认定为直接光照。

### 环境光遮蔽：先建立直观

现在开始说屏幕空间里要做的第一个东西：ambient occlusion，中文叫环境光遮蔽，简称 AO；加上屏幕空间的前缀，总共就叫 SSAO——屏幕空间的环境光遮蔽。那环境光遮蔽是什么鬼？还是老规矩，从历史开始说。

SSAO，又看到了 Crytek。Crytek 是非常夸张、非常厉害的——研究游戏引擎的这帮人可是非常非常厉害。顺便说一句现在的 Unity：虽然它的渲染器本身有点弄不过 Unreal，但在学术界，Unity Research 还是非常猛的，发了很多高质量的文章，所以 Unity 还是挺有未来的。Crytek 发明了 screen space ambient occlusion——如果我没记错，应该是引进在二代里，第三代做的是刚才说的 LPV 那些技术，SSAO 是二代里面就有的功能。

那搞 screen space ambient occlusion 到底要干什么？从对比图上看得比较明白：右边这一列是没有环境光遮蔽的，左边这一列是有环境光遮蔽的。两列直接一对比，立刻可以得到一个直观的感受：环境光遮蔽好像就是把这些物体之间的相对位置标示得更明白了。

> **定义**：环境光遮蔽靠所谓的 contact shadow 起作用——物体和物体接触的时候，你会感觉到它们中间的这些地方会暗一些；正是这些暗部，把物体之间的相对位置交代得更清楚。

## 屏幕空间环境光遮蔽：从渲染方程到 SSAO 与 HBAO
> 对应块：BLK16 | 覆盖分集：P08下 | 块标题（分集名）：《Lecture8 Real-time GLoba》

### 为什么要做环境光遮蔽

我最喜欢这个灯的例子：一盏灯放在物体上，正常情况下你想象一下，它们接触的地方是不是就该有一些阴影？空间站的走廊也是一样的道理——不同的物体相互挨着、离得近，这些东西之间肯定会有一些阴影。环境光遮蔽（ambient occlusion，AO）做的其实就是这么一件事：一系列所谓 contact shadow（接触阴影）共同造成的一种感觉——让物体之间的相对位置感更强。有同学说"立体感"，对，就是这么个意思。

所以为什么要做环境光遮蔽？一个重要理由当然是它能带来这种视觉上的提升，非常好；另一个理由说出来更实在——ambient occlusion 非常非常容易实现。这就是我们做环境光遮蔽的原因，也算是一个简单的定义。

### SSAO 的精确定义与三条假设

那屏幕空间的环境光遮蔽到底是个什么东西？给你一个最精准的定义，分两层说。

环境光遮蔽首先是对全局光照的一个近似。为什么物体和物体接触了、靠着比较近，中间看起来就有阴影？那其实是全局光照造成的——周围的几何挡住了一部分间接光。AO 抓的就是这件事。

"屏幕空间"说的是信息从哪来。我们没有世界空间里那些信息，有的只是屏幕内部的一些东西：还是那个起点——从 camera 看过去，你能看到的所有东西，你能看到的物体、它们的法线、它们的深度，这些都可以得到，因为反正是一趟 camera pass 就能渲染出来的东西。

在这个定义之下，SSAO 有三条关键假设。

第一条：间接光照是常数。给你任何一个 shading point，不通过计算你肯定不知道它的间接光照是什么，那没关系——我们假设间接光照是一个常数：对任何的 shading point、从任何一个方向过来，间接光照都是一个完全相同的数。这个假设对你来说是不是非常熟悉？之前推 Blinn-Phong 着色模型的时候，我们说过一模一样的事：茶杯的背面并没有被直接光照照亮，可它不完全是黑的，那是怎么做的？他认为不管任何一个点，都会接收到来自环境的各种光照——也就是多次反射的这些间接光照——并且任何一点、从任何一个方向接收到的都一样。这样的话最后就得到一个完全平的结果，相当于把整体亮度直接提了一块。

第二条，也是 ambient occlusion 比我们之前那个假设要稍微好一些的地方：不同的 shading point 有不同的 visibility。虽然仍然假设来自四面八方的 incident lighting 是一样的，但不见得所有方向都能接收到这种间接光照——shading point 周围只要有一些各种各样的几何，它就会往各个不同的方向形成遮挡。任何一个 shading point 的 visibility function 本来就是关于方向的函数，往各个方向各有一个可见性；在 AO 里，我们把这个 visibility function 显式地考虑出来了。拿人头模型来说：眼窝这个位置往上看，肯定被眉骨挡住，那从这个方向来的间接光照就接收不到，所以眼窝肯定比额头黑；额头呢，往四面八方看都能看得到。这两个哪个好哪个不好，一眼就能看出来——大家肯定更喜欢 ambient occlusion，因为它少做了"visibility 往各个方向都一样"这个假设。

第三条：物体是 diffuse 的。glossy 这些我不管，就当它是 diffuse 物体来解它的 AO。

顺带补充一点：在一些三维建模软件里，也就是离线渲染里，同样有这种东西。考虑所谓 uniform 的间接光照，不就相当于给你一个模型，拿一个纯白的环境光去渲染直接光照吗？一回事。这种东西在 3D 建模软件里被称作"天光"（skylight），他们就不叫环境光遮蔽了——工业界有各种各样神奇的名字，渲染出来的结果看起来跟 ambient occlusion 一模一样，用来展示一些模型挺好的。

### 从渲染方程推导 AO

AO 的道理本身非常明确：给你任何一个 shading point，往四面八方去看，被挡住的方向接收不到间接光照，没被挡住的就能接到。有的点往左边几个方向全都接收不到、右边都可以；瓶子内部的点几乎往所有方向都被遮挡，只有少数方向能出去——那这一点不就该黑一点，露在外面的点就该亮一点吗？

但为什么说它是对全局光照的近似？这门课我更愿意说得深一点，把它背后的理论讲清楚。不管怎么样，所有这些理论都要从 rendering equation 开始。光照、BRDF、可见性三项乘起来：

$$L_o^{indirect}=\int_{\Omega^+}L_i^{indirect}(\omega_i)\,f_r\,V(\omega_i)\cos\theta_i\,\mathrm{d}\omega_i$$

这里我们还是用之前已经非常熟悉的那个近似——把一个 product integral 中间的某一项拆出去，并且除以一个空的积分做归一化：$f(x)g(x)$ 乘起来积分，把 $f$ 的积分拿出去，底下除一个积分。这门课管它叫 real-time rendering approximation，或者叫 real-time rendering equation。

> **注意**："real-time rendering approximation"（或 real-time rendering equation）这个概念并不存在，是这门课上自己起的名字。平时当黑话用，知道我说的是什么就行；正式场合别这么说。

我要考虑的是任何一点的 visibility，那就把 rendering equation 里的 visibility 拆出去，剩下的是：

$$L_o^{indirect}\approx\frac{\int_{\Omega^+}V(\omega_i)\cos\theta_i\,\mathrm{d}\omega_i}{\int_{\Omega^+}\cos\theta_i\,\mathrm{d}\omega_i}\cdot\int_{\Omega^+}L_i^{indirect}(\omega_i)\,f_r\cos\theta_i\,\mathrm{d}\omega_i$$

拆成了两项，我们一项一项看。

分母这个积分我再清楚不过了：它没积分任何别的东西，就是对整个半球把 $\cos\theta$ 积起来，结果是 $\pi$。微积分忘了的话，把立体角微元拆成 $\sin\theta\,\mathrm{d}\theta\,\mathrm{d}\phi$，再对 $\theta$ 和 $\phi$ 分别积分，就能算出来。在 AO 这个领域，人们给"分子比分母"这一项起了个名字，就叫 $k_A$：

$$k_A=\frac{\int_{\Omega^+}V(\omega_i)\cos\theta_i\,\mathrm{d}\omega_i}{\int_{\Omega^+}\cos\theta_i\,\mathrm{d}\omega_i}\in[0,1]$$

这一项是什么？相当于在任何一个点往四面八方看过去，别的都不管——光照不管、BRDF 不管——只看 visibility，得到按 cos 加权平均的可见性。从 0 到 1，值域非常明确。

> **定义**：$k_A$ 就是 shading point 在上半球上按 cos 加权平均的 visibility，取值 $[0,1]$。

再看另外一项，这项太简单了。这个积分里积的是谁？间接光的入射 radiance——刚才才假设它是常数，跟方向没关系、跟点都没关系，就是一个数 $L_i^{indirect}$；BRDF 呢，又假设了物体是 diffuse，是 $\rho/\pi$，也是个常数。两个常数提出来，积分本身产生一个 $\pi$，$\pi$ 和 $\pi$ 消掉，最后就是 albedo 乘上间接光照强度：

$$L_o^{indirect}=k_A\cdot\rho\cdot L_i^{indirect}$$

间接光照强度你反正也不知道是多少，随便指定一个；diffuse 物体的 albedo 是多少，你也可以随便指定一个。所以右边这一项基本上就是你随便定一个颜色就好了。关键就是前面 $k_A$ 这一项——一个常数乘上平均的 visibility，这就是这个点能得到的间接光照。

这里多说一句。单讲 RTR4 这本书，它关于 AO 讲得极其混乱——工作太多了，前后有很多感觉对不上的东西。我认为直接从 rendering equation 来推导是最对的做法。AO 是什么？一个平均的 visibility，乘上任何一项你给的常数，就这么回事。

### 拆分的本质：求加权平均，以及它何时是准的

既然说到深一层，我们把"拆分"这个操作本身再理解一遍。从一个更通用的角度：把 $f$ 从 $f\cdot g$ 的积分里拆出来、除以空的积分归一化，其实就是求 $f$ 在 $g$ 的 support（$g$ 的覆盖范围）上的平均值，把它拿出来就好了。你甚至可以把之前那些具体的理解都忘掉，就记这一条：给你一个 product integral，把其中一项在它覆盖范围内的平均值拿出来就可以了，没有任何问题。

为什么这就是平均？"加权和除以权重和"是标标准准的加权平均做法，这里不过是连续的写法。写成求和就一目了然：$\sum_i f_i w_i \big/ \sum_i w_i$。归一化还有一个作用：让值不至于发生范围上的变化。visibility 本来是 0 到 1，在一个范围内求平均之后肯定还是 0 到 1——这就是为什么底下要除以 $\pi$，$k_A$ 肯定在 0 到 1 之间。

那这样拆什么时候是准确的？之前说过：一个是 $g$ 的覆盖范围（support）比较小，另一个是 $g$ 比较 smooth，这时候是准的。而对 ambient occlusion 来说，这是百分之百准的——$g$ 是什么？间接光照乘以 BRDF，在 AO 的假设下不就是一个常数吗？$g$ 是常数的情况下，这样做是百分之百准的。也就是说，在"diffuse、间接光照均匀"这两个假设之下，AO 的这个拆分是准确的，不是近似。

### 投影立体角：cos 为什么能和 dω 一起拆

现在我要问大家一个问题：刚才那个拆分，是不是用得不对？按之前 $f(x)g(x)$ 对 $\mathrm{d}x$ 积分的用法，把 $f$ 拆出去之后，分子分母都应该是对同一个 $\mathrm{d}x$ 积分；可这里拆出 $V$ 之后，分子分母积分的都是 $\cos\theta_i\,\mathrm{d}\omega_i$ 这一整块——好像把它当成了一个 $\mathrm{d}$(什么什么) 来用。难道不应该把这两个 cos 都划掉，才是我们之前的用法吗？这样做能对吗？这是我很想让大家琢磨的一个问题。

> **易错点**：AO 拆分式里分子分母的积分测度不是 $\mathrm{d}\omega_i$ 本身，而是 $\cos\theta_i\,\mathrm{d}\omega_i$ 这一整体。

解释它要引入一个概念：投影了的立体角（projected solid angle）。名字听着麻烦，其实一点不麻烦。立体角是什么？单位球上的一块面积。这块面积再乘上 $\cos\theta$——θ 在球面坐标下从北极起算、转到南极是 0 到 180 度——正好是什么？正好等于把这块面积从球上投影到正下方单位圆上得到的面积。所以 $\cos\theta_i\,\mathrm{d}\omega_i$ 有明确定义：它就是一个微分的面积，只不过是单位圆上的面积。

这样一来，刚才那个积分就理解成：$L$、$f_r$、$V$ 这几项在一个单位圆上做积分。原本是"带着 $\cos\theta$、在立体角上积分"，现在变成"不带 $\cos\theta$、在投影立体角上积分"——本质就是一次换元。它同时也告诉你，$\int_{\Omega^+}\cos\theta\,\mathrm{d}\omega$ 为什么积出来是 $\pi$：微分元的物理意义是单位圆上的一小块面积，整个积出来自然就是单位圆的面积，$\pi\times 1^2=\pi$。

有同学问这个拆分操作有没有论文参考——没有哪篇 paper 专门提出这种拆分方法，基本上是一件约定俗成的事情，而且你自己推一下也是对的；也有同学说这就是换元，对，刚才说的就是换元。也别把被积的函数想成非得是"单位圆上的函数"，要记的就一句话：$\cos\theta_i\,\mathrm{d}\omega_i$ 整体等于投影立体角的微分，把它当成一个 $\mathrm{d}$(什么) 就 OK 了。这块如果还是不明白，很可能只是微积分忘了而已，没什么特别难的。

顺带学一个 LaTeX 的细节：积分式里那个 d，直接敲一个 d 字符是不对的——LaTeX 会给你一个斜体的 d，而微积分里微分用的那个 d 是不斜体的，任何正规的印刷品里你都能注意到这一点。正确写法是 `\mathrm{d}`，并且前面最好加一个小空格 `\,`（最小的空格），也就是平时应该写 `\,\mathrm{d}\omega`，这才是非常严谨的写法。来听一节课，顺便学个 LaTeX。

### 换个更简单的推导：把常数直接拿出去

刚才我们是故意把事情说得那么复杂，为了让大家多理解一点知识；其实 SSAO 远远没那么复杂。

间接光照假设成了常数，物体的 BRDF 是 diffuse 也是常数——既然知道这两项都是常数，那干嘛不直接把它们从 rendering equation 里拿出来？拿出来，完了，这就结束了：

$$L_o^{indirect}=L_i^{indirect}\cdot\frac{\rho}{\pi}\cdot\int_{\Omega^+}V(\omega_i)\cos\theta_i\,\mathrm{d}\omega_i$$

间接光照的来源是个常数，拿到积分外面；BRDF 是 diffuse，也拿到积分外面；剩下来的就是对 visibility 乘 cos 的一个积分。

那为什么一开始不这么说？这里要说清楚：这样剩下来的积分，并不是 visibility 的加权平均，因为它缺了底下归一化的那个常数。如果照这么说，大家就会不明白工业界为什么一定要引入 $k_A$ 那么一项、底下要除以一个 $\pi$。当然，从这个式子也可以继续推：里边除一个 $\pi$、外边再乘一个 $\pi$——但那样就理解不到为什么要这么做了。不管怎么样，两种推法得到的结果是一样的。

顺便坚持一个观点：我到现在仍然认为，各种书籍资料在推 AO 的时候非要引入某个中间量、推出来一串 $E$ 等于什么什么什么，毫无必要——你最后要的就是 radiance，要那个中间量干嘛？正因为多绕了这一步，推导里就会多出一个 $\pi$，大家就会觉得这个事情非常麻烦。其实它非常容易：rendering equation，直接把两项常数拿出来，就这么点事。这就是咱们这节课独特的一个推导，希望能好理解一些。

### 屏幕空间怎么算：先把光线限制在半径 R 内

推导完了，想一想还缺哪件事：我说只需要知道加权平均的 visibility，可它怎么算？在世界坐标里，最简单的办法就是 ray tracing——往四面八方真正地追踪光线，把它们的 visibility 加权平均起来，没问题。但在 screen space 上怎么做，这才是关键：AO 的理论有了，现在要对任何一个 shading point，在整个上半球上看有多少方向被挡住、多少没被挡住——特别是在屏幕空间里，这怎么做？

而且就算真的去 trace，也不能无限远。给大家举一个非常极端的例子：给你一个封闭的屋子，那么任何一个 shading point 往任何方向 trace，不管打没打到周围的物体，这光线无论如何最后都出不去这屋子——往任何一个方向肯定都得被遮挡住。这样算出来的 ambient occlusion 会告诉你：到处都是 0，整个屋子全黑。这不出事了吗？

为什么会这样？想象一下：反射光一定都是从有限的距离反射过来的，你不可能用无限的距离去算"能不能 trace 到一个物体"。所以正常人们会限制一个范围：在一定的范围里面 trace 光线——往前走多远、这么一个范围里有没有遮挡——那就够了。否则只要走无限远，那肯定会被挡住；限制范围之后就不一定了，就看这个范围内到底有没有遮挡物。这就解决了"所有光线最终都会被挡住"的问题。

但这样又造成一个新的问题：真正来源于比你考虑的范围更远的间接光照，你就把它忽略掉了、不要了。大家又看到 trade off 了吧：范围大了，所有东西最后肯定都要被挡；范围小了，就自然而然有一部分入射的间接光照被你忽略掉。在 AO 的语境下（反正间接光都当成一样的）这么处理没问题；到后面更精准的方法里，你这样想就不对了。总之，限制一个实际的范围是一个 trade off，通常人们会选一个折中的半径 R。

> **提示**：trace 的最大距离 R 是一个 trade off——R 太大，封闭场景里处处被挡；R 太小，来源更远的间接光被丢掉。

于是问题变成：给定任何一个 shading point，往它上半球各个不同的方向 trace，并且不能 trace 太远，最大半径 R。画在平面上，就是这个范围往外张出一个半圆；半圆内哪个方向有遮挡，那个方向的 visibility 就是 0，其他方向是 1，最后平均起来。对比较凹的物体（比如凹槽的底部），同样考虑一个半圆、一定的范围，往这些方向看哪些能看到、哪些两边看不到——道理非常明确。

### SSAO 的实现：球内撒点，深度图判遮挡

从这里开始，基本就是纯工业界了，大家会开始听到各种各样的 hacks。SSAO 并不从 shading point 往四面八方 trace 光线——screen space 里你知道的只有屏幕上面这些信息，要做 ray tracing 是非常麻烦的一件事。它做了一个超级大胆的做法，分两步。

第一步：在任何 shading point 周围半径 R 的球体内部，随机采样很多的点。说清楚，它并不只采样方向——要采样方向的话，只用球面上不同的点就行了；它是在整个球覆盖的体积内随机撒点。

第二步：判断撒下来的这些点，到底能不能被 shading point 直接看到。在物体内部的点肯定看不到（红点），在物体外部的点看得到（绿点）。可撒的这些点到底哪些在物体内部、哪些在外部？screen space 知道的信息太少了，但无论如何，从 camera 渲染一趟，你一定能知道看到的任何一个点的深度——也就是有一张深度图。

咱们在讲 shadow mapping 的时候就提过这个概念：深度图可以当做场景几何的一种简单近似。camera 往场景方向看，看到的物体表面都被记录成各种不同的深度——每个位置记的都是最浅的深度。判断方法跟 shadow mapping 一模一样：把球里撒的每个点投影到 camera 屏幕上，查这个像素之前记录的深度；如果我这个点的深度比记录的更深，那不就是在物体内部、被挡住了吗——这个点就得是红的；绿点投影过去比记录的最浅深度还要浅，那它一定在物体外部，看得到。

```text
camera pass --> color + depth (深度图: 每个像素记录离 camera 最近的深度)

对每个 shading point:
    在半径 R 的球体积内随机撒 N 个采样点
    每个采样点投影回屏幕像素, 查深度图
        采样点更深 -> 判为物体内部 -> 遮挡 (红点)
        采样点更浅 -> 判为物体外部 -> 可见 (绿点)
    统计红/绿点比例 -> 得到平均 visibility (k_A)

noisy 的 AO 图 --> denoise --> 平滑 AO --> 叠加到直接光照等结果上
```

读图：SSAO 的全部数据流就是"一趟 camera pass 拿深度，球内撒点，投回屏幕比深度，数红绿点"。整套判断就是 shadow mapping 的反向使用。

两个假设一组合，基本都是成立的——前面几个例子里的点都判对了，只有一个点会出问题：这个点在 camera 看到的最浅深度背后，按规则判为"在物体内部、看不到"；结果发现几何在那里拐了个弯（有个尖），这个点其实在外面、能看到。深度只记录最浅的，拐弯的存在你根本不知道，所以这种点会被误判成红点。但这是工业界，就这一点点出问题的话还好，能接受。

### 没有法线的年代：红点过半才算遮挡

还有一个问题。咱们刚才不是说了吗，判断 visibility 应该在法线所在的那半边——rendering equation 的积分范围从来都是上半球，从物体底下打进来的光不可能有贡献，你去判断另外半球干嘛？这个想法完全正确。那为什么 SSAO 要考虑整个球？

因为在 AO 那个时代，你还不能假设 camera 看向整个场景、渲染出来的东西既有深度又有 normal。深度可以有，但不见得渲染出来任何一个点的法线方向你都知道。不知道法线方向，就不知道哪半球该去考虑，是不是出事了？所以它干脆考虑整个球。

考虑整球之后这么补救：正常情况下，如果真的有一个平面，那必然有一半的点在平面底下、肯定看不到，另外一半你能看得到。于是对任何一种几何都做这个假设——撒在整球里的那些点，只有当红点（看不到的点）的个数过半的情况下，才开始考虑 AO 问题。想一想是不是这个道理：红点根本站不满半球的情况（比如点在一个凸起上、几乎所有方向都能看见），是绝对不可能发生 AO 的；只有你肯定可见的那半球里也出现了遮挡，红点才会过半。

红点过半之后，超出"一半"的部分才是真正的遮挡。比如一共撒了 10 个点，9 个是红点：减去 5 个——平面上本来就该看不到的那一半——剩下 4 个点表示这些方向真的被挡住，还有 1 个点没被挡住，那么最后得到的 visibility 自然就是 $1/(4+1)=20\%$。

> **提示**：红点不过半 → 当作没有遮挡；红点过半 → 超出半数的部分才是真实遮挡，visibility = 绿点数 ÷（绿点数 + 超出半数的红点数）。

注意这么做丢了一样东西：没有法线，就不知道 cos 应该怎么加权，所以算出来的只是上半球不同方向 visibility 的一个近似平均，而不是 visibility 和 cos 的加权平均。工业界方法嘛，没有法线的情况下，就只能做到这么好了。

### false occlusion：SSAO 的典型错误

有了 SSAO 和没有 SSAO 的对比一放，效果挺明显，但这幅图真正要说明的是 SSAO 坏在哪。场景是地面上的一个矮石凳，像地铁站里经常能见到的那种。石凳和地面根本不接触，也就是说石凳脚下那一圈地面怎么会有 ambient occlusion？可图里偏偏有——这就是 SSAO 的问题，所谓 false occlusion：不该有的、不自然的遮挡。

原因还是刚才那个机制。比如地板上取一个点，取它周围 3D 空间中的一个球；球里某个采样点投影到 camera 时，查深度图查到的是石凳——离 camera 更近的那个面记录的深度。采样点比它深，就判为"在这个面背后、在物体内部、被挡住"，于是背后的这些点全部都得是红点。这就错误地认为石凳对地板这一点的 AO 有贡献，凭空多出一圈变暗。根子还是那句话：camera 只能记录最前面的表面，它背后到底是什么、挡不挡，其实不知道。

### 采样数量与降噪

那球里到底选多少个 sample？这和 PCSS 是一模一样的问题：一个 shading point 考虑多大范围、这个范围内采多少 sample，作业都已经做过了，知道是什么情况——sample 越多越好，但想要好的速度，就不能用太多的 sample。

办法也一样：用少量的 sample，先得到一张 noisy 的 AO 结果，然后再做一遍 denoise，把这张 AO 糊掉。AO 正常情况下很少单独看——你都是把它加到直接光照或者其他一些东西上面；denoise 之后哪怕还剩一点 noise，一加到其他东西上就差不多了。

### 有法线之后的升级：HBAO

有同学正好提到，法线方向是怎么得到的？你当然可以通过采样相邻的深度纹理来近似一个法线方向，但更多情况下，现代图形学里你去渲染 camera 看到的这一整个场景，怎么可能得不到任何一点的法线信息？开玩笑，现在假设都有。现代实时渲染里你要说只有 depth 没有 normal，那是说不过去的。

那么有法线的情况下，是不是就不需要像 SSAO 那样做那么近似的东西了？你就可以做得相对准确一点：有法线，你就知道应该采样哪半球。做法还是可以用之前 SSAO 那一套，在这个半球内选一些点，直接算它们对应的红点和绿点的比例——可见的 visibility 的一个平均——这就比没有法线、考虑整个球要准。

更进一步，有法线你就可以对不同方向做加权了。我们不是说过吗，站在 shading point 上往四面八方看，看到的 visibility 还要通过 cos 加权一下：cos 肯定是靠近法线方向大、靠近两边小。知道法线了，就可以对不同的方向进行加权，得到一个更准的值。这套有法线的做法就是 HBAO。

HBAO 对 false occlusion 也处理得好一些，用的就是刚才说的那个思路：不再是像 SSAO 那样，认为只要距离近——不管小多少——都算遮挡；它只考虑在一定范围内的遮挡。SSAO 很多边缘的地方出问题，就是因为它不考虑 depth 到底差多远；HBAO 把这个考虑进去，就不会再出现那种非常明显的错误遮挡。总之 HBAO 为什么比 SSAO 要好一些？就是因为它真正考虑了带范围限制的半球这一套考虑方式，自然而然结果就更准。

代价呢？HBAO 要多存一张 normal map——那是要存的，肯定的，因为你要知道任何一个地方的 normal。

把两种方法摆在一起看：

| 对比项 | SSAO | HBAO |
| :--- | :--- | :--- |
| 法线信息 | 不需要（当年假设拿不到） | 需要，G-buffer 多存一张 normal map |
| 采样范围 | 整个球内撒点，红点过半才计遮挡 | 法线所在半球内采样 |
| cos 加权 | 做不到，只是可见性的平均 | 可以按 cos 加权，结果更准 |
| false occlusion | 明显（不看深度差多少） | 只计一定范围内的遮挡，基本消除 |

最后看效果。什么都没有的时候，地铁站就长那样；有 SSAO，哪些地方会看得明显？其实大家已经可以猜到了——接触部分：拐角、柱子底下和地面接触的这些地方，都该有接触阴影，切换过去这些地方确实变暗了。但物体明明离得挺远的地方，SSAO 也会错误地变黑；HBAO 就没有这种非常明显的错误遮挡。

### 半径、阈值与工业实践：几个现实取舍

减小采样的半径，能不能减少 false occlusion？我想了想，既然是 AO，能。但同时你整个的 AO 都会变淡——想象一个极端情况，半径减得特别小，基本上没什么点会有 AO，你这基本就没有 AO 了。所以减少 false occlusion 的同时，也在减少真正的 occlusion，那不是出事了吗？一切东西都还是一个很平衡的东西。

深度差的阈值也一样：一切这些操作都只能说减轻这个问题，或者可能会引入一些其他的问题。有没有更好的设计，留给大家思考——HBAO 这些东西不是还在一直改进吗？HBAO 之后还有各种各样的其他方法，有兴趣的话直接到网上查，就能查到最近大家是怎么做的，但思路还是一样。有同学提的"动态采样半径"，我觉得应该可以，挺有意思的。

这节课的主要目的，是把理论上说清楚：它到底想干嘛、它到底怎么算、该计算的东西到底是什么，而不是"它就这么做"。SSAO 确实就是那么做的，但它背后的这些东西，咱们要把它理解清楚。

最后回答一个技术性问题：AO 作为 GI 的一种，工业界常用吗？太常用了。现在基本上渲染都会有一个 AO；甚至你真正算上了 GI，有时候还会有人再叠一个 AO 在上面，就为了表示物体之间的这种接触感。

### 下讲预告与彩蛋：另一个 SSR

下节课先把 SSDO 说了。刚才 SSAO 假设入射的间接光照各个方向都是一样的，事实上不能这么假设了；SSDO（screen space directional occlusion）就是不这么假设——真正把间接光照该是多少算成多少。SSDO 之后我们讲 screen space reflection（SSR，屏幕空间反射，或者叫屏幕空间光线追踪）；再之后看有没有时间，就开始下一个话题——PBR，所谓材质这块。

最后照例给大家一个彩蛋。一提 SSR，你第一反应想到的可能不是屏幕空间反射，而是阴阳师的 SSR——那是 super super rare，指稀有度。我不是说过我是严重的网瘾大叔嘛，什么游戏都打，阴阳师我也打，而且当年打得很夸张：SSR 全收集，打到间接伤害刚出来那阵子，组了一套间接伤害反击流的阵容去打斗技，打到了全服第 11、世界第 19——截图为证，这是很值得我炫耀的一件事情。重点是，我其实没有氪金，完全靠肝（好像是 30 块人民币；我说我应该算微氪，结果被网易的朋友教育了一顿，说我完全没弄明白什么叫微氪，于是我以后再也不敢说了）。这背后其实跟随机数有关系——抽卡这种东西，随机数多少都会有一些所谓 low discrepancy 的性质，这个性质是可以利用的。不过另外说明一下，虽然斗技打得挺好，但我实力没那么强，那是一个瞬间的动态状态，到最后我还是掉出了 100 名开外。

开始之前先交代个事：大家现在看到的是录播——五一那场直播不是忘了录像，而是硬盘满了，没录进去，有点惨。不过大家真正错过的是一个重大事件：直播吃键盘的环节。正好，今天开课先把这桩公案了结掉。

### 先了结一桩公案：平方还是四次方

还记得前面两节课我做的那个推导吗：RSM 上的任何一个像素，如何对一个 shading point 产生贡献。那个像素本身有一定的面积，对应面积上的积分 $dA$；我们要把原本在 shading point 处对球面立体角的积分，换成对次级光源表面上的积分——这一换，就会引入一个距离的平方。之前讲 path tracing 里 light sampling 的部分，也是这么说的。

当时我看着那篇 paper 的式子立了个 flag：分母底下写的是四次方，我说他写错了，应该是平方——因为我推出来的是平方。今天给大家澄清：他写错了没有？没写错。那我写错了没有？也没写错。

怎么回事？paper 里是四次方不错，可是它的分子上面有向量的点乘——法线和某个向量的点乘。法线咱们通常认为是归一化的，而另外一个向量是直接拿两个点连起来的，并没有归一化，它本身就带着 $x$ 到 $x_p$ 之间的距离。两个点乘各多带上一个这样的距离，分子上就多出了两个距离，于是分母就成了四次方。

$$\frac{\left(\vec{n}_p\cdot\vec{d}\right)\left(\vec{n}_x\cdot\vec{d}\right)}{d^{4}}=\frac{\cos\theta_p\,\cos\theta_x}{d^{2}}$$

左边是 paper 的写法：点乘里的 $\vec{d}$ 是两点间未归一化的向量，长度为 $d$；右边把向量归一化，分子只剩两个纯余弦，分母相应写回平方。这两个式子表示的是完全同一个事情。

所以结论是：谁都没有错，两种写法完全等价。直播吃键盘的环节到此正式结束，以后再见不到我直播吃键盘了。

### 从 SSAO 的大胆假设说起

上一节课我们主要说的是 3D 空间中的实时全局光照，主要是两块：LPV 方法和 VXGI 方法，都非常经典，得到了广泛的应用。然后我们又提到了屏幕空间的一些方法，比如 SSAO。SSAO 之后，就是今天要讲的两个话题：SSDO 和 SSR——前者叫屏幕空间的方向性遮挡（directional occlusion），咱们就这么翻译；后者叫屏幕空间的反射，或者叫屏幕空间的光线追踪。材质本来想这节课捎带讲一点，后来想想还是放到下一节课去说，这节课就把全局光照这块给说完。

SSAO 的基本思想咱们简单回顾一下。它认为：任何一个 shading point，都会接收到从任何一个方向过来的相同的间接光照——就是这么一个假设。那能不能接收到从各个方向来的光照，就取决于在 shading point 周围一个比较小的范围内，往这个方向看过去会不会被挡住。当然，不同的几何有不同的遮挡情况：黄色标出来的是没有被遮挡、能接收到间接光照的方向；有的面只有偏上一点的方向能收到——所以左边会比较亮，右边会比较暗，通过这种方式做出一种近似的全局光照效果。

具体做的时候分两种情况。第一种：如果拿不到 shading point 的法线，那怎么知道该往哪个半球往外看？SSAO 就做一个简单假设——往整个球的所有方向去看，看哪些地方被挡住，这个上节课说得比较详细了。第二种：如果整个场景在屏幕空间上任何一点的法线都知道，那就知道对应的半球是哪一半，在限定的半球、限定的半径范围内，看哪些方向会被挡住。知道法线还有额外的好处：可以根据法线做一个 cos 的衰减——咱们之前推导完公式本来就应该有这一项——还可以考虑遮挡跟距离有一个衰减。这一类改进叫 HBAO，horizon based AO，当然还是 SSAO 这一家的东西。

这里再把那个基本假设强调一遍：从 shading point 往某个方向能不能被看到，我们把它近似成了「从 camera 出发，能不能看得到对应的那个点」——也就是在球面中随机找的那些采样点。这两个并不一致，今天这节课还会看到这个近似会造成的一些问题。

### SSDO 的动机：间接光照其实我们是知道的

SSDO 从名字上看，肯定是对 SSAO 的一个提高，没错吧。它的基本思想是：比起 AO 那种「间接光照到处都一样」的大胆假设，其实我可以考虑得更精准一点。

为什么可以这样？思考一下：我们完全没有必要假设任何一个 shading point 接收到的间接光照都是一样的——有一些信息其实我们已经知道了。能够提供间接光照的，不就是次级光源吗？次级光源的信息，之前讲 RSM 的时候已经说过了：被照亮的这所有像素，本身都可以作为次级光源，为其他的 shading point 提供直接光照。那次级光源提供的直接光照，不就是场景中的间接光照吗？也就是说，间接光照其实是已知的——一定程度上是这个意思。

> **定义**：SSDO，Screen Space Directional Occlusion，屏幕空间的方向性遮挡。它要解决的是怎么把间接光照算出来；而「screen space」意味着所有信息都来自屏幕——被直接光照所照亮的那些像素，本身会成为提供间接光照的次级光源。

也就是说，SSDO 要用直接光照的信息，但不是从 reflective shadow maps 里来的，而是从屏幕里来的：所有次级光源的信息都在屏幕上。

来看看它做出什么效果。最左边是纯粹直接光照的结果，什么都没有；第二幅是 AO 的结果：接触的地方有一些变暗——这张图看起来稍微夸张了一点，有些地方太暗了，但不管怎么样这是 AO 的效果；右边这幅，才是我理解中 SSDO 要做的东西。

跟 AO 怎么对比？AO 可以在接触的地方产生变亮或者变暗，但它做不到 color bleeding。还记得我们之前说想要的效果吗：在 diffuse 的物体上，光线完全可以从一个 diffuse 物体达到另一个物体，再继续传播下去，于是不同颜色的 diffuse 物体会互相照亮对方——蓝色的面上会沾到一点点黄光，黄色的面上同样沾到一点蓝光，地面上也是一样。这样的效果才是我想要的，而不是简单地认为「这一块应该暗一些」。SSDO 是一个更为精准的、能够得到全局光照的方法。

> **提示**：这组对比图截自 SSDO 的 paper，我很想把它当做一个反面教材：论文也好、别的材料也好，编排上尽量不要这么排——二行一列和一行二列才应该是对应的两幅图，第四幅图应该对着下面那幅第四图，中间却隔着第一行第三列的两张图，是非常不合适的布局，挺难看的。之后大家做编排时，吸取一下这篇 paper 暴露的这些问题。

### 两组完全相反的假设

SSDO 具体怎么做？它的做法其实和 path tracing 非常像。在任何一个 shading point 上，我想计算它接收到的光照：path tracing 的做法是随机往某一个方向打一根光线——如果打到了一个物体，比如打到了一个点 $q$，那我就在 $q$ 点算 $q$ 的直接光照，再加上 $q$ 到 $p$ 的贡献，这就是 $p$ 最后收到的间接光照；如果从 $p$ 往外打一根光线什么都没打到，那这个方向上 $p$ 接收的就是直接光照。SSDO 跟 path tracing 是完全一样的思路。

这里面就藏着一个非常神奇的事情：SSAO 和 SSDO 其实是完完全全相反的两个假设。

把 $p$ 上半球里的采样方向分成两类：一组方向从 $p$ 出发打得出去，附近什么都没有；另一组方向往那边看，会被附近的物体挡住。

SSAO 是怎么解读的？它假设任何 shading point 都能接收四面八方来的间接光照：打得出去的这些方向，就认为能收到间接光照；会被物体挡住的那些方向，对 $p$ 来说就接收不到间接光照。

而 path tracing / DO 的解读恰好反过来：打得出去的那些方向，因为达不到任何反射面——间接光照肯定得从另外一个物体反射过来，什么都达不到，就只能打到环境（背景）里去——所以这些方向只有直接光照，没有间接光照；被挡住的那组方向反而打得到附近的物体，那些物体才可能反射光到 $p$ 上，间接光照恰恰是从这里来的。

| 方向的处境 | SSAO 的解读 | SSDO / 路径追踪的解读 |
| :--- | :--- | :--- |
| 打得出去（附近无遮挡） | 有间接光照进来 | 只有直接光照，没有间接光 |
| 被附近物体挡住 | 没有间接光照 | 恰恰是间接光的来源 |

从总结上看，是不是完完全全相反的一个情况？

为什么会这样？因为它们对「间接光照从哪来」的假设不一样。上一节课说过，AO 为什么要把考虑范围限制在一个有限的距离内：要是把范围放开到无限，物体整个放在封闭的盒子里、或者就是室内，那你往任何一个方向看，最终都会被挡住，那不是整个全黑了吗？就不对了。所以 AO 只考虑周围小范围内被挡住的情况，它背后的假设是：来自环境中其他物体的这些间接光照，都是从比较远的地方过来的。DO 里面同样考虑一个小的范围，但在范围之内能打到的那些物体，都会反射出间接光——也就是说，它考虑的是一个小的范围内，间接光对某个 shading point 的影响。

> **结论**：AO 假设间接光照来自非常远的地方，DO 假设间接光照只来自非常近的地方，所以这两者都不完全正确。理论上的正确做法，是把 AO 和 DO 合在一块做：来自近处的 indirect 部分由 DO 捕捉，来自远处的间接光照部分由 AO 捕捉。工业界里不知道有没有人真正这么用，但理论上来说该这样。

从这里也能看到一个明显的局限：DO 能够在一个范围内表示全局光照（间接光照），但它并不能表示远距离的间接光照，所以会造成一些问题，之后再说。这里并没有矛盾，咱们把这个意思说清楚。

### SSDO 的算法：被挡住的方向才有贡献

无论如何，SSDO 肯定是解 rendering equation，跟 path tracing 一样。在任何一个 shading point $p$，往任何一个方向打：

- 如果打不到任何物体——也就是往那个方向可见，$v=1$——这种情况就没有间接光照，来的可能是环境光的直接光照之类，这些咱们不关心；
- 我们关心的是另外一部分：$v=0$ 的情况——打到了某个物体 $q$，从物体 $q$ 反射到物体 $p$ 的这部分入射 radiance，就是所谓间接光照。

所以 SSDO 要关注的就是被挡住的这一块：把这些挡住的面对 shading point 的贡献都算出来、加起来，那就是我们要的间接光照。

那每个被挡住的面贡献怎么算？这件事之前两节课一直在说（讲 RSM 的时候）：我打到的像素代表一个小片，它有多大的面积；假设它是 diffuse 的，那它反射到任何一个 shading point 的 radiance，跟你从 camera 看到它反射出的 radiance 肯定是一样的——因为是 diffuse 嘛。这种情况下，就自然而然可以直接算它的贡献。一个像素对应的小片对 shading point 的贡献，绝对可以算，这样就 ok 了。

核心问题就变成：怎么找到哪些面会被挡住、又会对 shading point $p$ 有贡献。做法和 AO 完全一样：在点 $p$ 考虑它所在的上半球——这里当然假设法线是已知的——并且在这个上半球内撒一些点，然后问：从 $p$ 往 $a$ 方向、$b$ 方向、$c$ 方向、$d$ 方向看，是不是会被挡住？

同样道理，我们仍然不想真正去 trace 一根光线来决定 $p$ 到 $a$、$p$ 到 $b$ 这些方向会不会被挡住，而是做之前那样的假设：$p$ 到 $a$ 能不能被挡住我不管，只管从 camera 到 $a$ 能不能被挡住。这当然还是跟之前 AO 一样是一个非常大胆的假设，但一定程度上挺有效。

具体判定靠深度：渲染场景的时候，肯定会有一个最小深度（深度缓冲）。往 $a$ 方向看，$a$ 在这个物体的壳之后，说明 $p$ 到 $a$ 方向看不见；$b$ 同理，之前记录的深度更浅，$b$ 方向也看不着；$c$ 方向没问题——之前记录的场景深度在那里，$c$ 点在它前面，所以 $p$ 到 $c$ 不会被挡住。如果说我有一个环境光，那我就可以直接从 $p$ 往 $c$ 方向去查这个环境光的值。也就是说，SSDO 在解决间接光照的同时，还要顺便解决来自环境光的直接光照应该怎么做——不过这块我们不怎么关心。

我们关心的是 $a$、$b$、$d$ 这三个点：它们会被打到（判定为被挡），也就是说这三个点会为 $p$ 提供间接光照。这三个点各自都对应了一个小的面片，面片有一定的面积、一定的朝向；假设 $a$、$b$、$d$ 之前的直接光照都已经算好了，那它们分别对 $p$ 的贡献是什么？$b$ 和 $d$ 肯定对 $p$ 有非零的贡献；$a$ 点由于它朝向直接往反方向去了（面片法线背对 $p$），对 $p$ 应该没有贡献。不管怎么样，把 $a$、$b$、$d$ 三个对于 $p$ 点的贡献加起来，就完事了。

所以整个算法很显然：把 $p$ 点上半球所撒的这些点分成两类——往那个方向看不会被场景中的东西挡住的，就没有间接光照，跟 $c$ 没关系；其他被挡住的（$a$、$b$、$d$），把遮挡处的小片当次级光源算贡献，加起来就是间接光照。这么算。

### 相机可见性不等于着色点可见性

这个大胆的假设什么时候会出大问题？上一节课其实就已经提到了：本来想看的是从 $p$ 到 $a$ 这个方向会不会被挡住，实际考虑的却是从 camera 到 $a$——这是两个完全不一样的概念。那这么假设会不会有时候出问题？其实是会的，反例就在告诉大家这里会出什么问题。

反例一，看新的 $a$ 点：从 $p$ 到 $a$ 这个方向完全没有被挡住，但比较倒霉的是，$a$ 的前面正好悬浮了一个物体，从 camera 看过去正好把 $a$ 挡到了。用刚才的判定方法，你会认为：camera 看不到 $a$，那么 $p$ 看向 $a$ 也就会被挡住——这不就判断错了。反例二，$b$ 点：camera 很明显可以看到 $b$（最小深度就记录在那儿），但从 $p$ 往 $b$ 方向看过去，可能会被其他什么东西挡住。也就是说，camera 的 visibility，不能认为是 $p$ 往这个方向上去的 visibility。

> **易错点**：用深度缓冲判遮挡，回答的始终是「camera 能不能看到这个采样点」；而算法真正想问的是「shading point 沿该方向有没有东西」。两种可见性经常凑巧一致，但「采样点前方恰好悬浮遮挡」与「着色点方向上另有遮挡」这两种情形，会把结果正好判反。

大家肯定会问这么一个问题：我原本要判断的就是 $p$ 到 $a$、$p$ 到 $b$；把 camera 换成任何一个别的字母，这些方向的可见性跟 $p$ 到 $a$、$p$ 到 $b$ 肯定不一样。如果想非常精准，那肯定得在场景中打一条真正的光线，从 $p$ 往那个方向上去。那在场景中怎么样去 trace 一根光线？这块就是我们之后要说的 SSR。咱们先回到 SSDO。

### 轻量好用，但天花板在「屏幕空间」

从刚才的计算上看，SSDO 和 SSAO 好像计算量差不多：都是取一个半球、在中间打若干点、根据所谓 camera 的可见性来近似 shading point 对这些方向的可见性。所不同的地方是：当我判定有一些方向会被挡住的时候，不是像 AO 那样简单认为「这个方向看不见东西」，而是计算挡住的那些像素、小片怎么对 shading point 进行贡献——要做额外的一些 shading 计算。所以总体上来说，它仍然是一个非常轻量级的计算方法，得到了一系列不错的广泛应用，质量也非常不错——跟 AO 比，它毕竟做出了间接光照进来，当然是不错了。

那它有没有问题呢？有。首先，它只能表示一个小范围内的全局光照，这是怎么回事，马上继续说。另外，它既然在 shading point 往各个方向的可见性是通过 camera 往这些点的可见性去判断的，那当然不准；不过它毕竟算是考虑了一点次级光源和 shading point 之间的可见性，没考虑那么准，还是不错的。

它真正的大问题在哪？还在 screen space 这个事情上。屏幕空间上节课讲过，要把它理解成一个壳：从 camera 看向场景，不同的像素有一个深度，就等于把场景变成了我在 camera 这个位置往场景方向看所能看到的一层壳；至于壳背后的东西，我都不知道——screen space 记录的都是最浅的深度。这种情况下，就会出现所谓 screen space 丢失信息的问题：丢失什么信息？自然就是在直接能看到的这层壳背后，我什么都不知道。

一个很明显的例子：一个面反射到地板的光。没有旋转的时候，SSDO 非常好，可以把这个面反射到地板的这部分光线算出来，挺好的；旋转了一点之后，多少还剩一点，没问题；但当这个正面旋转到我们看不见的时候，就出问题了——它旋转过去我更看不见了，这部分反射贡献就直接消失。所以 SSDO 有这个问题，而且这是一切 screen space 方法共有的问题：我认为所有信息都是 camera 直接能看到的信息——上面这个小面背后的那个大面，我根本不知道它的存在，就更不可能说它会贡献到地板的 shading。这当然是 SSDO 的问题；不过不管怎么样，整体上来说还是 ok 的。

### 够不着的远处：Cornell Box 反例

还有一个刚才说过的问题要落实：它只能解决一个小范围内的间接光照。全局光照有大量的经典例子，比如 Cornell Box（这里算是一个改版）。先说清楚：这幅图是拿 path tracing 还是 photon mapping 做的？应该是拿 photon mapping 方法做的，它当然能做出完美的全局光照——大家可以看到这个面上会反射出这堵墙来。

那如果要用 SSDO 来做，怎么做？一开始没有反射；我考虑看到的这个点周围的一个范围——这个范围取得再大，也应该覆盖不到右边的绿墙。也就是说，它无论如何不会把绿墙对这个点的贡献考虑进来。所以这里明确指出来：SSDO 只能处理所谓非常小范围内的全局光照或者间接光照。

### SSR：屏幕空间光线追踪才是本质

接下来是屏幕空间的反射。为什么要说这么一个事情？它到底是干什么的、核心问题是什么？在讲这些之前，我更愿意把它理解成 screen space ray tracing——那样写同样是 SSR。其实把「反射」当成它的全部，是挺狭隘的理解，马上说为什么。

SSR 一个正确的理解是：它仍然是一种在实时渲染中实现全局光照的方式。更精准的定义是：它能够做的，是在屏幕空间上做光线追踪。在屏幕空间做光线追踪是什么意思？不需要知道整个场景的三维网格、三角形这些；需要知道的，仍然只是屏幕空间上已有的一些知识。刚才才说过，屏幕空间就相当于认为看到的只是从 camera 过去、场景中存在的那一层壳，这个壳多少能表示一些整个场景的信息。在这么一个壳上，和一根光线做求交——这应该就是所谓 SSR 要做的事情。

但这不是所有的事情，它要解决两个问题：第一，给定任何一根光线和这么一个场景——其实就是在 camera 下能看到的那层壳——怎么做求交，这是很重要的一件事；另外一件事情不能忽略：找到交点之后，还要把最后这种反射的结果给算出来——我要求出交点那个像素对 shading point 的贡献，这要怎么做 shading。这两块肯定都是要算的。

所以，虽然它叫做 screen space reflection，但我不这么认为；我认为它应该叫 screen space ray tracing：我们不限于考虑所谓反射光，考虑的是任何光线和场景这层壳怎么求交。之后还会有更深入的理解。

### 反射本来就是全局光照

可以先看看日常生活中，反射的东西是非常常见的：海景房里光滑的地面，会反射出窗户、牌子、家具这些东西；下雨之后的街道上，也可以看到反射——有灯光，也有建筑物本身。

在这里稍微停一下，说一个事：反射这个事情，本质上来说其实就是全局光照。为什么？大家可以想象：camera ray 达到一个 shading point，比如这个点，它往上反射，正好反射到了一个光源——那就是光源到 shading point、再到你的眼睛，这是直接光照；如果考虑另外一个点，它反射过去到了这栋楼——楼不是光源，它是被别人照亮的——那就是光源到楼的表面、到地面、再到你的眼睛。所以反射本来做的就是全局光照，没有什么特殊的东西。只不过平常人们觉得镜面反射这种东西在游戏里用得比较多，就单独把反射拎出来、当做另外一种效果——其实它就是全局光照，没有任何问题。

游戏里也有现成的对比：同一块地面，加上反射和没加反射的效果。我觉得肯定有很多同学跟我是一个感受：这地板不该有反射吧？工厂里面的地板哪有这么亮的？我觉得右边（不加反射）反而更正常一点。不过作为秀技术来说，左边能做出这种反射效果还是不错的。咱们就不评价哪个更好了，但是反射挺有用的。

### 反射出来的，多半是屏幕上已有的

既然想说屏幕空间的反射，那我们就想把雨后街道这种效果给做出来。假设场景中先没有反射——地面上没有反射出街道这些东西——现在想把反射加进去。那么我问一个问题：为了把反射加进去，我肯定要知道任何一个点它都应该反射到什么东西。

从这幅图上可以发现一个很有意思的现象：底下白色这一块基本都是反射出来的东西，而它反射出来的，其实就是上面红圈圈出来的那一块。也就是说，反射出来的这些东西，绝大多数在屏幕空间中已经有了。

这意味着：如果我在加反射之前就已经把场景渲染出来了，那要把反射加进去，其实不太需要额外的信息，只需要知道反射之前场景中的一些信息就行了。这就是所谓 screen space 的基本思想：认为反射光在很大程度上，反射出来的都是屏幕上已有的东西。当然，这样假设不一定对，之后会说；但绝大部分情况——像这个例子就挺明显——是成立的。

### 镜面、Glossy 与任意方向的光线追踪

那我们就真的来把类似镜面反射的效果做出来。假设场景上面这一部分已经渲染出来了，地面上还没有反射，要把反射加进去。对任何一个像素：我知道观察方向，就肯定知道它的镜面反射方向——做镜面反射的话就是一个方向，从 shading point 往某一个方向去。这里先说清楚：光线的定义肯定是三维的——某一个位置，往某一个方向上去，这是三维的一根光线。我要让它和屏幕空间上我能看到的这层场景壳去求交，求到的那个点，就用那个点当做反射光。这是最粗糙的一个做法，也是最基本的思路。

为了避免大家认为屏幕空间反射就只能做镜面反射，说清楚：它可以做镜面反射——非常完美的镜面，没问题；也可以做有一定 glossy 的材质：刚才那种叫 specular reflection（镜面反射），这种叫 glossy reflection——没有镜面反射那么好，但也不是完全 diffuse。

那 glossy 怎么做？肯定有同学会问：这时 camera 过来，BRDF lobe 反射出来应该是某种 lobe——咱们之前老早就说过 BRDF 是某一种 lobe——这种情况下，取一根反射光线是不是就不够了？得取多少根？答案就是这么做：对于有一定 roughness 的材质，给定入射方向（其实就是观察的方向），出去的这些方向根据 BRDF 的 lobe 来考虑：lobe 越细，可以用越少的光线；lobe 越大——比如像 diffuse 这种——当然就会需要更多的光线。不过没关系，肯定可以做，咱们先不考虑速度什么的，可以做，没问题。

它还能做任何的东西。比如地面不平，不同位置有不同的法线，反射光就会往不同的方向去——也没问题，效果是可以的。甚至来说不要求地面是平面：对任何一种物体，反正只要知道它的几何、知道它的法线，我就可以往任何一个方向去 trace。这正好就是我之前所说的：SSR（或者说镜面反射）可以做任何的光线追踪。能做光线追踪，就能解决任何这种反射问题——比如不同位置有不同的 roughness。

这里给工业界多提一句：工业界有时候会定义一些很奇怪的东西。比如这里叫 smoothness——光滑程度，自然就跟咱们平常说 BRDF 时用的 roughness（粗糙程度）相反了。可以认为这块光滑程度比较高、那块光滑程度比较低。没什么意思。

### 最朴素的做法：一步一步往前走

回到镜面反射这个例子，想一想怎么做。假设还没反射，地面上没有反射；场景中任何一个位置我知道它的法线，这没问题；任何一个点知道它的深度，也没问题——这些作为正常的输入。下面要做的事情就是：对地面上的任何一个像素，都计算出来它反射出来的值是什么，最后再把反射的东西加到之前的场景里面去。这就是最基础的思路。

现在，问题到了最关键的一步：对地面上任何一点，如果它是镜面，它的反射光——一根三维的光线——怎么样描述，我清清楚楚；我现在就想知道，这根反射光会与场景中的哪个像素相交。

最简单的思路是这样：shading point 在这里，从它出发的那条虚线就是反射光；既然是屏幕空间描述场景，camera 在另一头的话，我看到的场景就是最外层那一层壳。我知道有一根光线从这里出发、向斜上方走，我想问它和这个壳相交的点在哪——一目了然。

实践中怎么做？就是在任何一个 shader 里：取一个初始的点，往这个方向每次往前走一点、再走一点，直到走到这层壳所描述的最浅深度的背后——那就说明有交点了。

```text
  沿反射光逐步步进（在 shader 里每步往前走一点）：

  起点  *   场景表面上的一点，从 camera 看过去有确定的深度
  步 1  *   仍在壳之前
  步 2  *   仍在壳之前
  步 3  X   深度第一次落到壳（最浅深度）的背后
            -> 说明光线穿过了表面，交点就在上一步与这一步之间
```

判断的依据始终是深度：光线起点的深度，从 camera 看过去本来就在这层壳之前（起点本来就是场景表面上的一点）；每往前走一步，就拿当前采样点的深度和深度缓冲比一次，一旦某个采样点跨到了壳的背后，就说明光线穿过了表面——交点必然在这最后两步之间。

找到交点，SSR 要解决的两件事里的第一件——求交——就有了最朴素的答案；至于交点那个像素对 shading point 的贡献怎么算，就是 shading 要回答的问题了。

## 屏幕空间光线追踪（SSR）：层级试探与着色
> 对应块：BLK18 | 覆盖分集：P09下 | 块标题（分集名）：《Lecture9 Real-time GLoba》

先接着上一段把求交这件事说完。一根反射光线打出去了，怎么知道它和"场景"交在哪里？沿着光线走，把路上的每个点都过一遍：如果我从 camera 再看这个点，它的深度和我之前看到的场景那层壳的深度相比怎么样？走到这里，它仍然比场景的深度要浅；走到这里，它就比场景的深度要深了——那相交肯定就发生在这中间。说白了，就是用深度来做这么一个可见性判断，跟之前做 SSAO 和 SSDO 一模一样的做法。

> **定义**：屏幕空间方法眼里的"场景"，就是从 camera 能看到的那一层壳（shell）。每个像素只能记录一个深度，所有像素的深度拼起来，就是这层壳。深度值越小，代表离 camera 越近。

### 步长的两难

说到沿光线一步一步往前走，大家肯定马上想到一个问题：这一步步长要取多大？每一次往前走都走多远？

如果步子迈得非常大，完全可能出现这种情况：我"找到"了一个交点，其实光线早就进到壳内部去了——中间真正该有的交点被我一步跨过去了，这肯定不好。反过来，如果步长取得非常小，每次只往前走那么一点点，那判断肯定会非常准；但是计算量就会很大。而且大家注意到，这里只是在 trace 一根反射光线，每个 fragment shader 都要做这样一遍操作，操作就非常麻烦了，代价一下子被放大。

所以步长太大太小都不好。那怎么办？

这里再多说一句：在这种朴素做法里，步长你必须得固定一个定值。因为这里没有 SDF（有向距离场）告诉你"往前走多少是一个安全距离"——没有 SDF 的情况下，你怎么能知道这个信息？你只能盲目地往前试探。这就是为什么必须人为给一个步长。

### 用最小值 Mipmap 给屏幕空间建层次结构

人们是很聪明的，研究出来了一种动态决定步长该有多大的方法。

还是考虑这根反射光线。能观察到一个什么现象呢？咱们这么定义：把"一个像素在场景中描述的大小"算作一格。每次往前走一格，固然是好的、肯定是够准的，但很多时候没有必要——像这一段，往前走四格都不可能和物体相交。如果我能快速拿到"我这一下可以走几格"这个信息，那就非常好了，可以一下跳过好多步。

那谁能告诉我这个信息？不管在什么空间里，第一反应都是我们之前讲过的层次结构：对一个场景建一个 BVH 或者 KD-tree。同样道理，在屏幕空间上建立层次结构，就能让我立刻扔掉、跳过大量不可能相交的像素。

具体怎么做？有一个重要的准备工作：先把场景中间的深度做一份 mipmap。但它跟平常所说的 mipmap 不一样。正常的 mipmap 是一个图像金字塔：最精细的那一层在最底下，往上每一次边长除以二，上一层一个像素是下一层四个像素的平均。这里不一样的地方在于：上一层存的一个像素，不再是下一层四个像素的平均，而是它们的最小值。最小值是什么意思也说清楚：深度越小，代表离场景（离 camera）越近——所以每个上层 texel 存的是它覆盖范围里"最近"的那个深度。

```text
level 2 : [    min of 4 texels   ]
level 1 : [ min of 2 ][ min of 2 ]
level 0 : [ p0 ][ p1 ][ p2 ][ p3 ]
```

读图：上层一格是下层若干格取最小值——level 1 一格管两个像素，level 2 一格管四个；存的是最小值而不是平均值，也就是"离 camera 最近"的深度。

为什么这样做就能换来"能不能跳"的信息？因为这给了一个保守的逻辑：如果一根光线和上层的一个节点（一个 texel）都不可能相交，那它绝对不可能和下层的子节点相交。

拿一维的情况看（mipmap 本来是二维的，反映到一维就是一条线）：第 0 层是 8 个格子，每个像素一格；第 1 层每两个格子合成一个；第 2 层每四个合成一个。第 1 层某个格子的深度，取的是它覆盖的两个第 0 层深度的最小值，而不是取平均——平均会在两者中间，而最小值取到的是更近的那一个。这样就有了一个保守估计：如果光线和第 1 层这一整个蓝色块都不可能相交，那它更不可能和第 0 层的两个子块相交，直接全跳过。这样就可以快速跳过很多格子。

反过来，另一种情况：如果光线和上层一个节点相交了，比如和第 2 层的一个节点相交，那我就知道光线有可能和它的两个子节点——也就是 level 1 上的那两个节点——有交点；再根据光线到底相交在了这块的左边还是右边，我就可以知道应该去看它下面一层的哪一个节点。

所以为什么要做这么一个用最小值定义的深度 mipmap？其实就是对"能看到的壳"做了一个非常非常简单的层次结构，方便地用它来计算：光线在传播过程中到底会相交到哪一个像素上。

### 试探步：在危险的边缘疯狂试探

整个算法的基本思想，我借用篮球上的一个术语来理解，叫试探步。也就是说：我应该往前走多少？先保守一点，往前稍微走那么一点点；走慢点，发现没事，那我就继续往前，走得更快一点，下一步就迈得更大；还没交点，下一步可以迈得更大；而当我什么时候发现"有了一个交点"，我就知道：这时候不应该把步子迈这么大，因为交点可能会出现在更低的一些层上。一句话：在危险的边缘疯狂试探。

拿一维的例子把整个流程完整走一遍。光线从左上往右下打，它和这层壳的真正交点应该落在某个 level 0 的格子上：

1. 先保守。在最精细的 level 0 上往前试探地走一格，拿这个位置的记录深度一比，红线还在上面，没交点。没交点怎么办？胆子大一点。
2. 下一次往前走，我就到 level 1 上走一格——level 1 的一个 texel 表示的是原本两个精细 texel 的最小深度，等于一次走两格。一比，还是没交点。
3. 那就在 level 2 上走一格，一格代表 level 0 的四个格子。走完一比：终于找到交点了！这时候可不能再这么激进、再往前 trace 八个格了——逻辑告诉我，这时候光线是有可能和更精细的格子相交的，必须降层。
4. 光线和 level 2 这一大格的交点在它的右半边，这说明它跟左边那半个格子是没有交点的——直接去考虑右边那个 level 1 的子节点，不用管左边。
5. 到 level 1 这一格一看，还是有交点。行，那我们就更谨慎一点，看是不是该和 level 0 的格子求交了。这里又碰到图形学上经典会出现的一个情况：交点算在左边这个格子还是右边这个格子？咱们就假设它跟左边这个有交点——交点出现在左边，那我就应该在 level 0 上考虑左边这个格子。
6. 到 level 0 一比：没交点。好，又回到刚才的逻辑——你只往前看了一步，而且这一步没交点，那下一次再往前走，就又该升回 level 1 再走一格。
7. level 1 的下一格一比：又有交点，而且交点在它的左半边，于是又降回 level 0 去看它对应的格子——最后找到了交点。算法结束。

什么时候停下来？两个条件：第一，找到了交点（代码里 level 会被暂时置成负的）；第二，在整个屏幕上都找遍了也没有交点——也就是已经走出屏幕了。除了这两种情况都要继续走。

总结到代码上看，是超级简单的事情：任何时候你都知道自己当前在第几层。最开始在最精细的 level 0 往前走一格；根据情况看，没交点，你就大胆一点，下次走两个格子，再下次走四个格子——这其实就是把 level 往前提一级，等于在 level 1 上再走一格、level 2 上再走一格。而如果找到了交点，那我就应该在更精细的一层里继续找交点。

> **易错点**：降层没有那么简单，不是把 level 直接减一就完事。你找到了交点，就知道交点在哪；知道交点在哪，就知道它应该往哪一个子节点里继续找——对应到 2D mipmap 上，绝不会往一个节点的四个子节点分别都去划分，因为你知道精细的那一层会交到哪。

恰恰是这个降层的细节，是工业界实现里最混乱的一步，这里给大家提供一个标准化思路。再多说一句：这一页并不是从那个 SIGGRAPH course 里拿来的——我发现它的实现和它写的有点矛盾，所以我自己给加上了。以刚才的流程为例：已经回到了 mipmap 第 0 层，往前 trace 一下发现没交点，这时一定应该先到 level 1 上、也就是每两个格子形成的一个 node 上去找；在这种情况又发现相交了，才会跟 level 0 上那一个格子去做求交。原来 course 里给的例子中间没有经过这个过程，然而我觉得那样是错的，我这么解释应该才是对的，这样代码也能写得比较干净。

另外，这部分我在直播课里并没有讲得这么细，看过直播的同学建议还是再看一下这一块。说句实话，SSR 的各种算法在网络上是非常非常非常混乱的，我们希望能提供一种应该是没问题的思路。

### 查询起点对不齐怎么办

这套算法其实非常依赖 mipmap 的不同层之间存的最小深度。但我们之前说 mipmap 的时候提过：它可以做范围的查询、正方形的查询，这没问题；但它做不了准确的、起点不在 $2^k$ 边界上的查询。

什么意思？还是拿一维 8 个像素的例子：第 1 层是 4 个 texel，每两格合成一个。如果我现在想问"第 2 格和第 3 格合起来的最小值"——这个范围的起点不在 2 的幂次边界上，mipmap 就做不了这个精确的最小值。硬要的话，只能拿左边格子记录的最小值和右边格子记录的最小值，在中间做一个平均、插值出来。这是个近似，但应该还是 OK 的。

### 快是真的快，问题也全在屏幕空间

说到这儿，回到我们刚才的出发点：hierarchical tracing——我们不希望一次往前走一格，希望一次可以跳好多格。通过这种方法就可以动态决定到底怎么往前跳，快速求出任何一根光线和场景所描述的这层壳的交点。也就是说，我可以把屏幕空间的光线追踪做得非常快，反射应该也可以做得非常好。

当然没有问题，但它会有什么问题？这其实才是我们比较在意的事情。它的问题完全出在 screen space 上。

#### 壳上无物：手指肚反射不出来

最严重的问题看这幅图就非常明显：这么一只手。我们刚才说，screen space 所描述的场景几何，相当于从 camera 能看到的一层壳。我们知道它是一只手，可对于 camera 来说，它怎么可能知道它是一只手？比如手心这块是什么，它完全看不到——它会认为根本不存在。它所记录的整个场景，就是所能看到的最外层的一层壳。

那反射出来的结果就是这样的：手指这个部分，我们知道背后应该有手指肚，但对于 screen space 来说，它只认为外面有一层壳，所以反射出来的就是这么一层壳，底下这块你就看不到手指的指肚——看起来背后就好像没有手掌一样。很有意思的一个几何问题。这个问题说清楚：它跟光线追踪没关系，是我们对场景的理解只到壳为止，是 screen space 的问题。

#### 反射出屏：一道难看的切边

还有一类问题。咱们最早说，反射出来的那些物体都在屏幕里——但它是不是都是对的呢？不完全对。看这个点，看过去反射到这个位置，没问题；但如果这个点稍微偏下一点，它反射过去就出屏幕了，再也找不到相交的几何——我们是屏幕空间，屏幕外面发生任何事情我们都不知道，所以到这儿它什么也反射不出来，画面上就会出现明显的一道 cut。这是非常不希望发生的事情。

所以人们平常做了很多很聪明的做法：根据反射光走的距离做一个衰减——反射光走的距离长了，就认为它基本上反射的东西看不太着了；再把结果虚化掉，这道边界就不那么明显了。

### 着色：把路径追踪整套搬过来

到此为止，光线追踪这块差不多说明白了。但我们刚才说过，SSR 要解决两个问题：第一，你要知道反射光在哪；第二，你要知道怎么样去做 shading。trace 说清了，shading 怎么做？

关键在于：SSR 仅仅是把"光线追踪"这一步，从原本三维空间里光线和 BVH 求交，改成了光线和这层壳求交。也就是说，你之前 path tracing 的任何算法，都是可以直接过来用的。对任何一个 shading point，你看到的 radiance，就是对整个场景对应的半球做一个积分：

$$L_o(\mathrm{p},\omega_o)=\int_{\Omega^+} L_i(\mathrm{p},\omega_i)\,f_r(\mathrm{p},\omega_i,\omega_o)\,\mathrm{d}\omega_i$$

如果你的 BRDF 是一个完全 specular 的 BRDF，那这个 BRDF 就是一个 $\delta$ 函数——我们知道积分里出现一个 delta 函数，积分就没了：不用采样，直接沿着反射方向找到它所达到的那个物体，看它反射过来的 radiance 是多少就行。如果是一般性的 BRDF，有些 glossy 这些，没问题，蒙特卡罗方法多采样几根。不管怎么样，我 trace 到的那些物体反射回来的 radiance，一定就是我这个 p 点接收到的 incident radiance——这是完全正确的理解。

> **注意**：这里仍然需要一个假设——反射物必须是 diffuse。说清楚，不是反射的接收物：地板这些东西完全可以是 glossy、镜面，都没有问题；我们只说"被反射到的东西"得是 diffuse。

为什么呢？因为在屏幕空间中，你看到的那些像素，记录的都是它们反射向 camera 的 radiance；那些像素 q 反射向任意一个 p 点的 radiance 是多少，你并不知道。除非假设这些反射物都是 diffuse 的——那样的话，它反射向 camera 还是反射向任何方向，radiance 都是一样的。

这里给大家留了两个问题，也值得好好思考一下。

第一个问题：任意一点的 shading 这么算，会不会还有我们最早说的那个距离衰减的问题？答案是没有。因为这里你做的是 BRDF sampling：你是在立体角范围内、在 shading point 上做 trace，并没有从某些次级光源上对它的面积做积分、去算任何次级光源对这个 shading point 的贡献——距离平方衰减是那种面积积分才会带来的东西。

第二个问题：那它有没有处理好 shading point 和次级光源之间的可见性？答案是处理得非常好。因为在任何 p 点往任何地方去 trace，你找到的都是第一个能够看到的物体、第一个到达的物体——中间保证不会有看不见的东西，你所考虑的能够对 shading point 有贡献的东西，都是有可见性的。这样说就没有任何问题了。

这其实是离线渲染里值得记下来的一般规律：做 BRDF sampling 的时候，不会有可见性和距离平方衰减这么两个问题；做 light sampling 的时候，一定会出现这两个问题，并且都不好做。

### 现象都是白送的

在 shading 上，SSR 的反射光这些光线是你自己可以随便取的——也就是说你其实做的就是 path tracing。既然做 path tracing，很多现象直接就可以做得到——前提是 shading 做得对。

这里千万注意：shading 可千万不是像之前想的最简单那种——"我 trace 到了一个像素，就把那个颜色拿过来，那就是它反射出来的颜色"。这就不是正确的图形学应该理解的思路。正确的理解是：我 trace 到的那些东西，是 diffuse 的反射物，取它们所能够出射的 radiance。这样，下面这些现象一个都不需要额外操作：

镜面锐利、glossy 模糊。对于镜面来说，反射出来的东西肯定非常锐利；对于一些 glossy 的物体，就是模糊的。这就是不同的 BRDF、不同数量的光线而已，绝对能做。

contact hardening（接触处更"硬"）。看这个物体：爪子这里的反射其实挺清晰的，离远了的翅膀反射出来就不怎么清晰。这是怎么回事？简单做个假设：假如反射物是一个平面。shading point 的 BRDF lobe 是一个往外打的锥，锥的大小由 BRDF 决定。锥在传播过程中越传越大：如果 shading point 离反射物比较远，锥传播到平面上时已经罩住一大片，等于在平均一大范围里所有点对 shading point 的贡献，反射自然糊；如果离得非常近，同样一个锥打过去，只会达到非常小的范围，平均的范围很小，反射就清晰。因为你在用正确的 BRDF 来做这个操作，contact hardening 就是自然而然会有的结果，不会有任何的额外操作。

specular elongation（镜面拉长）。这个现象雨天非常容易看到：特别是雨天坐车的时候，看到红绿灯这些东西，会感觉它们垂直地被拉长了——反射就是上下这么被拉长。解释要用到以前 GAMES101 说过的知识：认为地面是各向同性的——法线分布（normal distribution）跟各个方向都是一样的，类似一个圆。法线分布在一个标准的圆上时，给定一个观察方向，它反射出去的 BRDF lobe 其实就是一个长条的椭圆，上下拉长——所以看到的反射物体也就上下被拉长了。还是强调这么一件事情：这个现象绝对不是一种特殊技巧，你正确考虑了 shading 这一步的 BRDF 项，它就一定会出现，没有什么稀奇的。

最后一点，其实前面已经说了：它完全不挑接受反射的东西是不是平面、本身 normal 是怎么样。我们本来在做的就是 path tracing，对不同点 normal 不一样、几何不一样，那又有什么关系？它只是出射的光线不一样而已。

### 提高的几个方向

#### 重要性采样：光线集中在 lobe 里

一个很显然的提高：既然知道观察方向过来，又知道 BRDF，我就知道反射出去应该是集中的、在 BRDF lobe 这个范围内。那就没有必要均匀地往四面八方随机采样这些光线，只需要用一种 PDF，使得它长得跟这个 lobe 形状一样，让我更倾向于随机选择 lobe 中间的那些方向，把光线分布在 lobe 内。当然，一定要正确地计算 PDF。这一块 GAMES101 之前没有多说，以后开离线渲染的课再好好讲 importance sampling；但思路是很明白的：反射既然都集中在这么一个方向内，你没有必要把它四面八方全部均匀散开。

#### 从镜面到 diffuse：噪声的两极

对于 glossy 的物体多说一句：如果 glossy 到了一定极致，不就变成镜面了吗？给你一个观察方向，它的反射方向完完全全就是一个方向，这样不存在 noise。那什么时候 noise 最大？一个光线进来之后，如果这个物体是 diffuse 的，它就会往四面八方都反射，这时候你需要大量的光线——还记得 VXGI 吗？把整个半球拆成了八个锥去 trace，八个够不够？还不够。所以 diffuse 一定程度上来说挺难的。

但我们之前也提过，diffuse 是最低频的东西，它是 constant——BRDF 决定了你用再复杂的环境光去照亮它，最后结果仍然很糊，这正是我们之前用 SH（球谐）去描述光照的基础。这里就会发现一个非常神奇的现象：什么样的材质最容易？diffuse。什么样的材质又是最难的？还是 diffuse。

#### 空间复用：两条光线当四条用

如果真的有 glossy 的物体，一个 shading point 可能不止要 trace 一条光线，各自到达对应的交点——开销好大呀，怎么办？人们会研究所谓时间和空间上的复用。时间上的复用不再多说，real-time ray tracing 那部分会大量讲；空间上的复用应该怎么做？任何一个 shading point，都可以利用它在屏幕上周围一圈、或者稍微更大一点区域内那些像素 trace 到的信息。

什么意思？比如左边这个点 trace 出来的光线打到了某个点，右边这个 shading point trace 的光线打到了另一个点。那我可以问：这个被左边打到的点，如果它是由右边这个 shading point 产生的反射光打到的，它对右边这个 shading point 的贡献是多少？这可不可以快速弄出来？答案是可以的——我根据这两个点各自对应的 BRDF，来调整"如果这个点是由右边这个点 trace 到的，它的贡献应该是多少"。这样无形之中就增加了 sample 的数量：原本两个点各 trace 一条光线，一共就两条；现在每个 hit point 都可以反过来算它对另一个 shading point 的贡献，就好像原本只 trace 了两条光线，却起到了四条光线的作用。那就非常好了。

这个复用具体怎么做，就相对来说高端一点了，背后要有离线渲染的内功——既然我们这门课先讲实时渲染，很多东西没有办法给大家说得太深，像这么一个话题，之后再补。但 high level 是好理解的：复用其他 pixel trace 到的结果，这肯定是可以的。

#### 先滤波再查询：split sum 的屏幕空间版

之前说 split sum 的时候说过这个道理：对一个环境光，先把它 filter 一遍、预先模糊一遍，之后我只需要在它镜面反射的方向上查一次——就好像在没 filter 的原始环境光上，按真正 glossy 反射的范围查好多次。屏幕空间完全可以照搬：反射物不就是屏幕空间吗？把屏幕空间得到的这张图先做一个模糊，之后再做查询的时候，对 glossy 的面很可能只需要沿着它的 specular 方向去查一次就可以了。非常好的事情。

但这里涉及到一个问题：屏幕空间得到的这么一张图，各个点的深度是不一样的——不像环境光，之前假设过所有不同方向都认为来自无穷远。你肯定不希望做模糊的时候，前景被你糊到背景上去，背景上的颜色也不希望它跑到前景上面来。也就是说这个 filter 不好做，还得考虑深度上的差异。另外，深度本身是不应该被 filter 的吧？深度表示的是任何一个像素它自己对应的深度，你要把前景、背景的深度连续地混合在一块——取个平均——是没有什么物理意义的。

这一系列 filter 怎么做？也就是"整个屏幕最后渲染出来的那张图怎么 filter"，这是之后在实时光线追踪里要说的 joint bilateral filtering，联合双边滤波，挺复杂的一个概念，之后再跟大家说具体怎么做。这里先记住：先 filter 再 query 一次，是一个重要的提高方法。

### 总结：好处、代价，以及这次作业

屏幕空间的 ray tracing 或者叫 reflection，可以很快地做，尤其是 glossy 或者 specular 的反射——这也是之前人们大量用这个技术的时候，画面看起来特别"油"的原因。油，自然就是说这种 glossy 的反射稍微多了些；如果都是 diffuse 的当然就好，但 diffuse 做屏幕空间的 tracing 做起来会比较慢——对任何一个 shading point 都要打出大量的光线往四面八方去。

但其实还是可以的。特别是在现在，实时光线追踪发展起来，可以让人们做非常高效的时间、空间上的一种 filter，使得 diffuse 的这些物体你也可以放心去做 tracing。再多说一句：实时光线追踪本身，是让光线追踪都可以做得比较快；它和屏幕空间 tracing 本质上是一样的——都在解决"快速做光线追踪"这么一个事儿——所以你可以把它们结合到任何最后的 shading 上去。从这个角度上说，如果 RTRT 可以用它的方法去解决 diffuse 物体上面的反射，那么用屏幕空间 tracing 肯定也是可以的。这就是为什么这次作业要做的事情：洞穴里面这些物体都是 diffuse 的，我们就用 SSR 来做整个间接光照，把全局光照给弄出来。

总结一下好处：SSR 效果非常好，速度又比较快；没有那些 exclusion 的问题，也没有 spike——spike 是什么，我只简单说一下，它跟我们之前说的距离平方有一定的关系，这里就不再提了。反正它的好处，就是一切光线追踪能提供的好处。不好的地方：首先 screen space 的问题肯定会出现；另外一点，做 tracing 对于 diffuse 来说是挺难做的——刚才已经说过了。

下节课开始，我们就说 PBR 材质，也就是基于物理渲染中间用到的材质。迪士尼《超能陆战队》里的大白，看起来就像某种塑料——为什么看起来像呢？我们就要研究这些材质到底是怎么回事、它们和光线怎么样作用、特别是在实时渲染中又不能太复杂，应该怎么办。下节课开始说。
