# 高性能计算、物理引擎与课程总结

## 高性能模拟的动机与收益

* **拓扑优化（topology optimization）背景网格案例**

    * 在 1600×2000×3000 的背景网格上解有限元（finite elements）：约 110 亿个 background voxel，其中真正用到的只有约 11 亿——优化出的形状在整个空间里只占一小部分
    * 问题设定：固定鸟嘴一端，在整个表面施加向内的压力，只给有限的材料，求填充方式使抵抗外部压力的能力尽可能好
    * 同等量级此前只有拓扑优化社区用超级计算机做到过：约 500 台机器、8000 个 CPU core 组成的集群；这里靠高性能计算与数值线性代数的加速技巧在单机上完成——那台机器有 512GB 内存、50 余个 CPU core

* **性能工程的收益量级**

    * 把这些技巧用足，一台 server 相当于约 100 台机器来用；优化效果达到一个、两个、三个数量级都是非常正常的。

* **周转时间（turnaround time）**

    * > **定义**：把一个实验从 setup 到运行结束中间的那段时间
    * 一个 simulation 很难一次跑成：跑到 70% out of memory、某个小地方没写好整个 simulator 炸掉、初始条件设得不好要调参、材料参数不行——一个 simulation 跑四五遍、五六遍非常正常，这还算少的。
    * studio 里用 simulator 的 artist 按导演需求来回调整物理参数、初始条件、外力让模拟更有艺术性，每一样都让模拟从头到尾重跑
    * 一个 SPH demo 跑好几天很正常；一个模拟跑五天、来来回回折腾一个月非常正常。人力之外还有机器耗电、维护工程师工资这些 low level 的消耗

## 性能取舍与两条提速路线

* **性能-质量取舍**

    * 给定一天 24 小时，希望粒子数越多越好、网格精度越高越好；但网格精度一高，性能就往下掉——两者此消彼长，给定一个性能水平，没办法不断提高模拟质量

* **两条提速路线**

    * 算法路线：渐近意义上的提高，如 $O(n\log n)$ 的快速排序对 $O(n^2)$ 的插入排序，性能有本质区别
    * 工程路线：讨论性能时默认已选定渐近最优的算法（如 multigrid、共轭梯度 conjugate gradient 这类收敛性非常好的算法），在其之上用更底层的编程技巧，让同样的工作执行得更快

* **MLS-MPM 的 14 倍提速账**

    | 版本 | 相对参考实现的速度 |
    | :--- | :--- |
    | 参考实现（2017 年论文，已做很重的底层优化） | 1× |
    | 同样的算法重新实现一遍 | ≈1× |
    | 同样的算法 + 底层性能优化 | ≈7× |
    | 优化过的传统 MPM 基础上换用 MLS-MPM | ≈14× |

    * 14 倍里 7 倍来自算法（MLS-MPM 本身），另外 7 倍来自底层性能工程（performance engineering）——同样硬件、同样多线程，纯粹比「代码写得好」和「代码写得差」，不是单线程比多线程，也不是 CPU 比 GPU
    * 随便找一个没怎么优化过的程序重写一遍，快 10 倍、20 倍不成问题；参考实现只被优化出 7 倍，因为它本身已经做了很重的优化

* **paper 与 server 的双重标准**

    * 发 paper 不能主打「靠底层性能工程快了 7 倍」——这部分在 paper 里只能是很小一段，reviewer 不珍惜，视之为 messy implementation details；要讲算法上的道理：FLOPs 更少、memory bandwidth 更少
    * 一篇好 paper 不一定是一个好用的 server：一个是学术贡献，一个是工程贡献，标准完全不一样

## 存储器层级与缓存

* **冯·诺依曼架构（von Neumann architecture，1945）**

    * > **定义**：input device + output device + CPU（内含 control unit 与 ALU）+ memory；CPU 不断从 memory 里 fetch 数据、计算、再塞回 memory
    * 讨论性能时可简化到只剩 CPU 和 memory 两个角色，键盘、鼠标、打印机等外部设备一概不管

* **高速缓存（cache，行话记作 `$`）**

    * > **定义**：用比较昂贵的硬件造的快速 memory——cache 容量比较小但访问速度很快；物理内存容量很大但访问速度比较慢
    * cache 里的一个单元大概要用 6 个晶体管去 build，是比较昂贵的设备；CACHE 和 CASH 发音都是 cash，所以行话用 `$` 指代缓存
    * 早期 cache 不是长在 CPU 里的，而是插在主板上、内存和 CPU 之间的独立硬件（cache stick 之类）；现在的 cache 全都塞在 CPU 里面

* **三层缓存与访存路径**

    ```text
    CPU --> L1 --> L2 --> L3 --> memory controller --> main memory
          ~3-4    ~14     ~42                      hundreds of cycles
    ```

    * 访存顺序：信号先查 L1，在就直接返回；不在去问 L2，L2 没有去 L3，L3 还没有才访问 main memory
    * L2 比 L1 容量更大、latency 也更高；每一层延迟都不小——CPU 一个 clock cycle 能做很多事，时间全花在访存上影响非常大

    | 层级 | 典型容量（Intel x86） | 访问延迟（大约） |
    | :--- | :--- | :--- |
    | L1 cache | 32KB（data 与 instruction cache 各 32KB） | 3~4 个时钟周期 |
    | L2 cache | 256KB | 约 14 个时钟周期 |
    | L3 cache（LLC，last level cache） | 每核 1.5~2MB，四核约 8MB | 约 42 个时钟周期 |
    | main memory | 数十 GB 起 | 几百个时钟周期 |

    * 每个 CPU core 有自己私有的 L1 和 L2，所有 core 共享一个 L3；L3 之后是 memory controller，再往后才是 main memory
    * 同一代 CPU（如同为 Skylake）L1、L2 基本没区别，L3 一般每核 1.5~2MB、可能稍微有点区别；具体数字与主频有关

* **CPU 芯片面积的大头不是计算**

    * die（裸片）上踢掉 GPU 与各种外围单元后，很大一块空间被 L3 cache 占据；zoom 进一个 core，L1 data cache 与 L1 instruction cache、memory management 单元、乱序执行（OoO）单元、instruction decode、µcode ROM 都占空间——真正的 execution unit 只占一小部分
    * 摩尔定律「勉强」成立：晶体管数目隔两三年翻一番还能做到（不再是当年的 18 个月），且最近有放缓趋势；2015 年大家还比较乐观，现在画那条曲线会更平一些

## 虚拟内存、页表与 TLB

* **页表（page table）与 TLB（translation lookaside buffer）**

    * 现代体系结构有硬件级的虚拟内存支持：page table 把虚拟内存映射到物理内存，所有访存都要先做一遍虚拟地址到物理地址的转换
    * page table 本身可能比较大、访问它也有 latency，所以给它也做一个 cache——这个叫 TLB，其实也是 cache
    * 查 TLB 和访问物理内存这两步之间有一些并行：大多数情况下只要没有 TLB miss，可以假设 TLB 不存在。

* **内存过度订阅（oversubscription）与按需分配**

    * Linux 上可以用 `mmap` 开虚拟内存：allocate on demand、以 page 为单位——每次摸到一个 page，系统才帮你 allocate 一下
    * 好处是不同程序之间的地址空间通过虚拟内存分离，操作系统用虚拟地址进行保护，很多事情的安全性更高

* **没有内存保护的两个经典事故**

    * 地址空间不分离的年代：C++ 程序 buffer overflow 或数组越界会写到另一个程序里——比如写进打印机进程的打印 buffer，打印机「咦，buffer 里有些东西进来了」就开始打印
    * 早期 GPU 没有内存保护：CUDA 程序数组越界会直接写到屏幕上——数据写进了 framebuffer，显示器刷新时把那段数据刷了出来（花屏）

* **复杂度的代价**

    * CPU 有 cache、TLB 之后高度复杂，反而容易被拿去做特性攻击：Intel CPU 上的 Meltdown、Spectre 两个漏洞，就是东西被设计得更复杂的产物

## 访存局部性与 cache line

* **程序大部分时间花在访存上**

    * 1980 年写程序，做一个加法要三五个周期，时间真的大部分花在计算上；现在 CPU 一个周期可以做三四个加法，而内存随时间的更新（带宽、延迟）赶不上处理器
    * 多线程、vectorization、超标量让 CPU 越来越快，CPU 处理能力与内存供数能力的 gap 越来越大
    * 访存慢在两方面：latency 高（请求一个 cache line，真正给你时已过去很多 clock cycle）、带宽小（每一层带宽逐级减小）；CPU 被 block 在访存上时无事可做，只能停下来等数据

* **局部性（locality）**

    * > **定义**：频繁访问同样的数据、或者相邻数据的程度
    * 空间局部性（spatial locality）：访问相邻的数据（这次 100、下次 101、再下次 102）——顺序访存让 cache 与 TLB 的 miss 都少很多很多
    * 顺序访存还触发 hardware prefetch：CPU 发现程序在连续访存，就把后面的数据（103、104、105…）尽可能提前 fetch 进 cache，等下次要用时数据已经在 cache 里了；hardware prefetching 是 CPU 上的机制，GPU 上没有这玩意儿
    * prefetch 有时是坏的：cache 容量有限，盲目 prefetch 过来的不必要数据会把 cache 里一些有用的数据 flush 掉（有人故意打乱访存节奏让 CPU 不 prefetch，但要搞 work 非常难）
    * 时间局部性（temporal locality）：这次访问 100、下次还访问 100——尽量重用数据；只要中间隔的时间不特别长，100 还在 L1 cache 里（约 4 个周期），最简单可以塞在寄存器里（约 1 个周期，几乎等于没有访存）

* **工作集（working set）**

    * > **定义**：一个 kernel 频繁访问的数据的大小
    * 小于 32KB 就很可能几乎完全 fit 在 L1 cache 里——哪怕随机访存每次也只有约 4 个时钟周期的延迟；L1 塞不下退到 256KB 的 L2，再退到 L3；真落到 main memory 则带宽和延迟都糟糕
    * 优化方向：尽量让数据 reside 在低层级的 cache 里，至少要 in cache（在 L3 里）

* **缓存行（cache line）**

    * > **定义**：cache 的颗粒（粒度）大小——和内存交流不是按 byte，永远以 cache line 为单位
    * CPU 上 cache line 几乎永远都是 64 字节，NVIDIA GPU 是 128 字节，手机 ARM 差不多也是 64 字节——万年不变的参数，可能十几二十年没变过，不用查

* **stride 遍历实验**

    ```cpp
    // 2.56 亿个 int 元素的数组，按 stride 遍历求和。
    for (size_t i = 0; i < N; i += stride) {
        sum += a[i];   // 循环体里做点计算，但总时间与它无关
    }
    ```

    * 实测：stride 取 1、2、4、8、16 时运行时间完全没有变化（尽管循环次数从约 2.56 亿降到 1600 万）；stride 从 16 到 32、从 32 到 64 才各快一点
    * 原因：int 是 4 字节，一条 64 字节的 cache line 装 16 个 int；stride ≤ 16 时每条 line 仍要整条从 main memory fetch 过来；到 stride=32 才终于能跳过一条完整的 cache line，不占 memory bandwidth

    ```text
    one cache line = 64 bytes = 16 int

    stride =  1 : [xxxxxxxxxxxxxxxx]   16/16 used
    stride = 16 : [x               ]   1/16 used, whole line still fetched
    stride = 32 : [x               ][                ]
                  ^ used              ^ untouched: can skip!
    ```

    * > **定义**：这个程序是 memory-bound 程序——运行时间完全由访存决定，和中间做了多少计算没有关系
    * > **易错点**：⚠️ 觉得程序运行速度只和执行的指令数目有关（stride 变成 2、指令数变一半，速度就该翻倍）——完全不是这样，现代计算机上必须考虑访存的因素

## 矩阵乘法的两个陷阱

* **循环顺序：换个顺序快 8 倍**

    ```cpp
    // 程序 A：最内层循环是 k
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            for (int k = 0; k < n; k++)
                c[i][j] += a[i][k] * b[k][j];

    // 程序 B：最内层循环是 j —— 比 A 快了将近 8 倍多
    for (int i = 0; i < n; i++)
        for (int k = 0; k < n; k++)
            for (int j = 0; j < n; j++)
                c[i][j] += a[i][k] * b[k][j];
    ```

    * 程序 B 的便宜：内层 j 变化时 a[i][k] 永远是同一个地址（时间局部性非常好，基本没有 bandwidth 消耗），b[k][j] 访问的是连续内存（空间局部性非常好）——两个数组都占
    * 程序 A 的内层 k 变化时：a[i][k] 恰好是连续访存还不错，但 b[k][j] 的地址步长是一整行，空间局部性非常糟糕，cache 在这种情况下基本不 work

* **陷阱二：n 从 512 改成 513 反而快近 2 倍**

    * 保持原来很慢的循环顺序不动，只把 n 从 512 变成 513——做了更多计算却快了将近 2 倍
    * 原因：n=512 时 cache 上的冲突（aliasing）非常严重，cache 基本上不太 work；n=513 作为 stride 虽然看起来不好，但 cache 勉强还能一定程度上 work（背后是 cache set、cache way 机制）

* **可背结论**

    * 程序的执行时间和计算量有关系，但很多时候关系不是那么大；更大的关系在于程序的缓存到底好不好
    * memory-bound 的程序，把访存结构写好，那它肯定会变快

    * > **易错点**：⚠️ 计算量更大不等于更慢——n=513 做的活更多反而更快，速度不能按指令数主观臆断

* **延伸**

    * 真正优化过的矩阵乘法会用 blocking、unrolling 之类的各种技巧；矩阵乘法是少见的能够达到 compute-bound 的程序
    * > **定义**：compute-bound——瓶颈真的在 CPU 的计算上，而不是在访存上
    * 深入资料：CS:APP（第五章 Optimizing Program Performance，讲怎么通过 engineering 把简单程序变快 10 倍）；What Every Programmer Should Know About Memory（免费，年代稍久但非常有用）

## CPU 微架构与算力账

* **主频墙**

    * GPU 前几年还能每年性能翻一番，最近几年很难做到，只能靠宣称 16 位浮点、8 位甚至 1 位整数运算撑数字；现在 GPU 每年增长 30%~50% 就非常不错，CPU 每年增长 10%~20% 就很不错
    * 核变多以后，每个 core 不可能还保持很高的 frequency——功耗（power）扛不住；总体 FLOPs 在涨，单核性能不涨反降
    * 2004 年买高端 CPU 主频就有 4GHz；现在大部分 CPU 主频 3GHz，加 turbo boost 能到 4GHz——而且核越多 boost 越低：一个核 4GHz、两个核 3.8GHz、四个核可能只有 3.5GHz（散热不行、功耗扛不住）
    * 按当年主频趋势增长下去，到 2030 年 CPU 表面温度就和太阳表面一样了（笑话，但单核提频路线很早就被预言走不通）
    * 出路：multi-threading（多线程）靠 parallelism 提高性能；或者 scale out——多台机器、每台几十个 CPU，变成分布式计算

* **免费午餐已经没了**

    * 过去写一个程序放那儿一年不管，性能自动变快两倍（因为 CPU 快了两倍）；到了 2020 年写个程序放两年不管、不优化，不会变快两倍，可能还会变慢 10%——core 数变多了但每个 core 的性能反而下降
    * 更多时候需要自己去做优化

* **前端：取指与译码（Skylake 为例）**

    * 从 instruction cache 里 fetch instruction，然后 instruction decode 把一个复杂指令转化成若干条 µop（micro-operation，微操作）
    * CISC 与 RISC 之争的和解：Intel 外面用的是复杂指令集，decode 到中间就变成了简单指令集——任何打架最后都会达成和解，落在中间的灰色地带、选一个 sweet spot

* **后端：乱序执行（out-of-order，OoO）引擎**

    * 8 个 port（编号 0 到 7），每个 port 有一定的并行性；decode 出来的 µop 通过寄存器重命名（register renaming）和各种乱序机制分发到各个 port 上执行
    * 一般来说每一个 clock cycle 可以发四五个 µop；中间还有一步 micro-fusion 可以把一些 µop 融合起来
    * integer ALU（整数运算）与浮点的 FMA 单元有两个 port 都能做——一个 clock cycle 里可以发两条 FMA，而且每条还是向量的浮点乘加
    * 乱序执行的含义：指令的执行顺序可以调整——这条卡在访存上了，赶紧把它挂起，先执行后面的不相关指令

* **浮点到底慢不慢**

    * a÷b 是非常复杂的运算，加减乘都比较快。看延迟整数稍快：整数加法 latency 可能只有 1 个周期、一个周期能发 3 条；浮点加法 latency 可能有 3~4 个周期、一个周期发 2 条
    * 整数乘法和浮点乘法的性能其实差不多——「浮点乘法慢 6 倍」是以前的事，现在已经不是了。
    * 向量化（vectorization）：AVX2 一条 vector instruction 可以并行做 8 个浮点数的加法（AVX-512 同理，更宽而已）
    * 融合乘加（FMA，fused multiply-add）：可以以浮点乘法相同的 throughput 运行——一个周期可以发俩浮点乘法、也可以发俩 FMA；代价是 latency 多一个周期，换来一条指令做掉 $a \times b + c$ 这个乘加操作

* **一颗 4.2GHz 四核 i7 的算力账**

    * 每 clock cycle 发 2 条 FMA × 每条 FMA 做 8 个浮点数的乘加（16 次浮点运算）× 4 个 core：$4.2\,\text{GHz} \times 2 \times 16 \times 4 \approx 538\,\text{GFLOPs}$
    * 它每秒能做的浮点运算不是 4.2G 个，而是 538G 个，中间差了 100 多倍——superscalar（每周期发俩指令）× FMA（一次乘加顶两次运算）× SIMD（每条指令 8 个元素）× 4 个核

* **流水线与分支预测**

    * pipelining（流水线）：一条指令从 instruction fetch 开始算，总 latency 可能有十几二十个 clock cycle（真正到计算的加减乘这些简单操作，latency 一般 1 到六七个周期）；流水化后单条指令 latency 变高，但 throughput（吞吐量）变高——superscalar 单位时间能执行的指令变多
    * 代价是硬件设计更复杂：得做 branch prediction（分支预测）
    * 分工：CPU 通过流水线、superscalar、out-of-order 去隐藏访存的 latency；GPU 不做 branch prediction、也不做 out-of-order，通过更大规模的并行去隐藏 latency
    * 深入资料：Intel 的 Architecture Optimization Reference Manual（怎么在 Intel CPU 上写高性能程序，约 700 多页）；WikiChip（各代 architecture 的数据很全）

## 内存带宽与性能上界

* **主存带宽怎么算**

    * Linux 上用 `lshw`（list hardware）列硬件，看内存那一栏的关键几条：channel（通道）数、数据访问位宽、频率
    * 例：双通道 × 64bit（8 字节）× 2.4GHz = 38.4 GB/s——理想情况下的内存访问带宽
    * CPU 的内存带宽一般在 20、30、40 GB/s 这个量级；四条通道可能达到六七十 GB/s
    * cache line size 不写在 main memory 上：只有 cache 上面才有 cache line 这个概念，memory 上其实以 8 字节为一个单位存储

* **memory-bound 程序的理论性能可以直接算出**

    | 操作 | 每个元素的访存量 | 相对耗时 |
    | :--- | :--- | :--- |
    | `asum`（求和） | 读 4 B | 1×，实测约 130 ms |
    | `memset`（全部清零） | 写 4 B | 1×，和 `asum` 消耗一样 |
    | `sscale`（$y_i = a \cdot x_i$） | 读 4 B + 写 4 B | 2× |
    | `sexp`（逐元素指数） | 读 8 B + 写 4 B | 3×，理论上约 390 ms |

    * `asum`：输入 $1024^3$（1G 个浮点元素）要从内存 fetch 4 GB；内存带宽 30 多 GB/s，那么不管怎么优化计算、只要访存是最优的，耗时永远大概是 0.13 秒——实测 130ms，4 GB ÷ 0.126 s = 31.75 GB/s，用到了 89% 的 memory bandwidth
    * `memset` 与 `asum` 访存量一样（一个写、一个读）：写和读对 main memory 没有区别，但对 cache 有很多区别——cache 里有非常复杂的 cache coherency policy（缓存一致性策略）
    * 简单操作可以用到比较高的内存带宽；稍微复杂一点的程序，可能只能用到 20% 的 memory bandwidth、10% 的 peak flops——那就不得了了，很不容易

* **compute-bound 程序有多难写**

    * 常见程序里唯一能真正做成 compute-bound 的是 GEMM——稠密矩阵乘矩阵，而且还得是大矩阵乘大矩阵；其他程序要真正打到 peak flops 非常非常难，能达到 10%~20% 就不得了（GPU 上稍微容易一些，但也没那么容易）
    * 打满 i7 每秒约 0.5 tera flops 的最简单方法：发一坨向量化的 FMA，可以达到 100% 的 peak flops；写一个高度优化过的矩阵乘法同样可以达到
    * 写一个「无意义」的程序去打包 peak flops 就必须写汇编：编译器很容易识别出「你这 FMA 指令啥也没干」直接优化掉
    * 汇编里要发十条 FMA：一个 core 每个周期能发 2 个 FMA、一个 FMA 的 latency 是 5 个时钟周期，要发 $5 \times 2 = 10$ 条才能把 pipeline 全部塞满
    * 普通程序大概能达到 0.1% 的 peak flops；能持续达到 20% 已经非常非常厉害（有人优化大概一个月才到 20%）；写稠密矩阵乘法的话到 20% 比较容易

* **存储器层级与那笔 100 倍的账**

    ```text
    main memory ─── L3 ─── L2 ─── L1 ─── CPU core
                                         └── register file
    （从左往右：容量越来越小，延迟越来越低，带宽越来越高）
    ```

    * 寄存器重命名（register renaming）：你能访问到的向量寄存器可能只有 16~32 个，但物理上其实有更多
    * 账：4 个核、内存总带宽 36 GB/s，平摊下来每个核每秒只能访问 9 GB；而每个 core 每秒能做 134 G flops，若考虑每个 flop 需要 8 个字节的数据，实际需要的带宽是 800 多 GB/s

    ```text
    供给：36 GB/s ÷ 4 核 = 每核 9 GB/s
    需求：134 G flops/s × 8 B/flop ≈ 800 多 GB/s
    差距：约 100 倍
    ```

    * 如果不考虑 locality、没有 data reuse，处理器需要的实际带宽是能提供的约 100 倍——cache 还是个好东西，没有 cache 的话现在的很多程序根本跑不了。

* **体系结构的可背结论**

    * 要写高性能程序就得理解计算机体系结构，而且这件事未来会越来越重要——内存和 CPU 都逐渐停止变得更快了，没有免费午餐，必须通过写高性能的程序才能拿到更高的性能。
    * computation 比 communication 要便宜很多：计算非常便宜，每秒可以做很多很多 flop；但从内存里 fetch 过来的每个 byte 都非常昂贵——memory bandwidth 是一个非常昂贵的资源
    * GPU 在硬件设计上和 CPU 有些差异，但总体来说这些准则是适用的。

* **cache 优化对高级语言有效吗**

    * Python：写 Python 代码的时候不用考虑 cache（语言本身性能较低），但写 Python 解释器的时候得考虑 cache
    * Java：性能没有那么低、还挺好的，这些优化在 Java 上仍然值得做

## SNode：Taichi 的数据布局

* **SNode（structural node，结构节点）**

    * > **定义**：在 Taichi 里，data layout 是被一个树形结构定义的；SNode 就是用来描述这棵树的一个简单语言
    * 种类：root（根节点）、dense、pointer、bitmasked、dynamic 和 place
    * 不管怎么用 SNode 描述数据结构，永远是用 `a[i, j, k]` 这样的语法访问——kernel 写完以后，可以在不改 kernel 代码的情况下通过 SNode 调试数据结构，不断试各种各样的数据结构找出跑得快的。
    * `ti.field`、`ti.Vector.field`、`ti.Matrix.field` 本质上就是 Taichi 的 dense SNode + place 的简写

* **dense SNode：shape 写进树里**

    * 定义 field 时不指定 shape，在 SNode 的结构里去定义它的 shape：

    ```python
    x = ti.field(dtype=ti.f32)          # 定义时不指定 shape
    ti.root.dense(ti.i, 4).place(x)     # 沿 i 方向 4 个元素的容器里放置 x
    ```

    * `ti.root.dense(ti.i, 4)` 创造一个沿 i 方向有 4 个元素的容器，`.place(x)` 往这个容器里放置 x
    * `ti.i`/`ti.j`/`ti.k` 是各方向的下标；Taichi 总共最多支持 8 个下标（要更多可以自己 build 一个 Taichi，一般 8 个完全足够）；`ti.ijkl` 是前四个下标的简写
    * 2D：`ti.root.dense(ti.ij, (4, 2)).place(x)` 和写 `shape=(4, 2)` 是完全一样的；轴的字母本身没有任何特殊含义，j 换成 k 也完全没有关系

* **SOA 与 AOS：同一套访问语法、两种内存排布**

    ```python
    # SOA（structure of arrays）：x 的元素靠在一起、y 的元素靠在一起
    ti.root.dense(ti.i, 4).place(x)
    ti.root.dense(ti.i, 4).place(y)      # 内存排布：x0 x1 x2 x3 y0 y1 y2 y3

    # AOS（array of structures）：x0 和 y0 挨着、x1 和 y1 挨着
    ti.root.dense(ti.i, 4).place(x, y)   # 内存排布：x0 y0 x1 y1 x2 y2 x3 y3
    ```

    * `place(x, y)` 这个写法相当于做了两个 place，是一个简单的语法糖；也可以先取节点 `cell = ti.root.dense(ti.i, 4)`，再 `cell.place(x)`、`cell.place(y)` 或 `cell.place(x, y)`
    * 对用户来说这两者完全没有区别（访问还是 `x[i]`、`y[i]` 这样的语法），但底层的内存排布变了，不同的访问模式下性能会差别非常大
    * 树长什么样，跟你怎么用它完全没有关系——解耦之后可以不断试不同的 data layout，总有一款既适合你的问题、也适合你的机器

* **单个 field 也能玩出多种 layout**

    * row-major（C 的 format，j 方向连续）：`ti.root.dense(ti.ij, (4, 8)).place(a)` 等价 `ti.root.dense(ti.i, 4).dense(ti.j, 8).place(a)`——Taichi 排布数据时以最底层的 SNode 节点为优先，先把它排成连续
    * 2×2 blocking（每个 block 内部连续，block 之间没有保障）：`ti.root.dense(ti.ij, (2, 4)).dense(ti.ij, (2, 2)).place(a)`
    * column-major（i 方向连续，每一列连起来）：`ti.root.dense(ti.i, 1).dense(ti.j, 8).dense(ti.i, 4).place(a)`——先写 `dense(ti.i, 1)` 是为了确保访问时 i 还是第一个轴（`dense(ti.i, 1)` 相当于什么也没做）
    * 三层嵌套：`dense(ti.ij,(1,2)).dense(ti.ij,(2,2)).dense(ti.ij,(2,2)).place(a)`——4×8 先上下分成两个 4×4，再各分成 2×2，小块内部连续；做 Z-index curve 或者 Morton coding，其实就是在做这种各种各样的 nesting
    * 语法糖：`dense(ti.ij, 2)` 等价 `dense(ti.ij, (2, 2))`

* **负下标：place 节点的 offset**

    ```python
    a = ti.field(dtype=ti.f32)
    ti.root.dense(ti.ij, (1024, 1024)).place(a, offset=(-512, -256))
    # 访问范围变为 i ∈ [-512, 511]、j ∈ [-256, 767]
    ```

    * struct-for（如 `for i, j in a`）的范围完全符合偏移后的范围；debug 模式底下越界访问（小于 0 或超过上界）会抛出一个 runtime error
    * 负下标一个最大的用处是很容易实现「无边界的」simulation：原点 (0,0) 不只能往右、往上延伸，也能往左、往下延伸
    * 说是无限其实还是有限的（如只有 −512~511）；配合稀疏数据结构 allocate 一个非常大的 grid，比如 −4096~4096 的，对你来说就相当于没有边界了。
    * > **注意**：只有 place 节点支持 index offset，pointer、dense 这些节点是不支持的。

* **vector field 到底是 AOS 还是 SOA**

    * `ti.Vector.field(2, dtype=ti.f32, shape=(128, 512))` 等效于：

    ```python
    v = ti.Vector.field(2, dtype=ti.f32)
    ti.root.dense(ti.ij, (128, 512)).place(v(0), v(1))   # AOS
    ```

    * `v(0)`、`v(1)` 指这个 vector field 的第 0、1 个子 field，把两个子 field 塞给同一个 place 节点——所以它其实是 AOS：v0 和 v1 里对应下标相同的元素在内存里更加接近
    * 想要 SOA（每一个 component 放在一起）就得 allocate 两个 dense 节点：分别 `place(v(0))`、`place(v(1))`
    * 从 C 语言看两个名字的来历：`struct Particle { float x, y, z; }; Particle particles[8192];` 是 8192 个 structure 组成的一个 array，所以叫 array of structures；把 particle 的 x、y、z 分别开成一个数组则是 structure of arrays
    * 一般来说在 simulation 里图省事会写 AOS，因为它和面向对象的编程比较接近；SOA 相对来说要做的工作复杂一些；Taichi 里两种都可以轻易做到

* **struct-for 也能遍历中间层**

    * 做嵌套的 SNode 时，struct-for 不但可以 iterate over field，还可以 iterate over 中间的 SNode 节点
    * 例：`block = ti.root.dense(ti.ij, 2)`、`block.dense(ti.ij, (2, 4)).place(a)`（合计 4×8）；`for i, j in a` 遍历全网格，`for i, j in block` 则以块为单位做 struct-for，输出 (0,0)、(0,4)、(2,0)、(2,4)

## AOS 与 SOA 的 cache line 账

* **记账前提**

    * 为简化说明，假设 cache line size 是 4 个元素（真实情况可能不止）；AOS 的 linear memory 是 x1 y1 z1 x2 y2 z2、x3 y3 z3… 的排布

* **AOS 的利用率**

    * 顺序访问：访问 x1 时 fetch 一条 cache line，y1、z1、x2 都在这条 line 里——每条 line 都能被 100% 利用，完美
    * 随机访问：约 75%——line 里最后的元素（如 x2）很可能在被再次访问之前这条 line 就已经被踢出去了；好处是每个 particle 的字段在内存里连续，对 random access 比较友好
    * 顺序访问比 SOA 稍差一些：得去做 vector lane shuffling，而且 GPU 上没有 coalesced access

* **SOA 的利用率**

    * 顺序访问：100%——访问 x1、y1、z1 各 fetch 一条 line，到 x2 时就可以复用 x1 那条 line 里的元素；只要是顺序访问，SOA 非常非常棒
    * 随机访问：约 25%——访问 x1、y1、z1 要搞进来三条 line（三个数组各一条）；假设 cache 里只能放 3 条 line，接下来每访问一个新元素都要一进一出，每条 line 只用了 1/4——cache 利用率 25%，程序就得慢 4 倍

* **AOS 与 SOA 对比**

    | 访问模式 | AOS | SOA |
    | :--- | :--- | :--- |
    | 顺序访问 | 利用率 100%，但要做 vector lane shuffling，GPU 上没有 coalesced access | 利用率 100%，最佳 |
    | 随机访问 | 利用率约 75%，比较友好 | 利用率约 25%，非常糟糕（约慢 4 倍） |
    | 粒子要不要排序 | 不需要 | 必须排序，否则一塌糊涂 |

* **MPM 粒子的选型经验**

    * SOA 在 particle 排过序的时候非常非常快；而且 GPU 上如果访问的是对齐的一整条 cache line，可以有 coalesced access——GPU 上的一种访存机制，能让带宽的利用率非常非常高
    * stream 太多要小心：CPU 上 prefetcher 的数目是有限的，不可能二三十条 stream 都给你 prefetch——MPM 里算下来可能相当于有 24 条 stream，那 prefetch 可能就不太 work 了。
    * 随机访问时 SOA 非常 inefficient，AOS 会好很多很多；AOS 即使不去排序随机访问也还可以，SOA 不排序的话性能一塌糊涂
    * 总原则：访问内存的时候尽可能避免 random access——它会带来更多的 cache miss 或者 TLB miss

## 稀疏数据结构

* **空间稀疏（spatial sparsity）**

    * > **定义**：活跃的区域只占整个体积的一小部分，但这一小部分是**集中**的——globally sparse, locally dense
    * 和 general sparsity 不一样：general sparsity 是活跃的 pixel 在空间里随便散着几个、其他都不活跃；spatial sparsity 局部还是 dense 的、有很好的局部性
    * 不活跃的就是空间里的「空气」：不给它分配内存，也不在它身上浪费计算；稀疏和稠密的区别就是——稠密无论用不用都得 allocate，稀疏是用了才 allocate
    * 动机：两坨沙子相撞的模拟，每时每刻占住的 region of interest 都是非常小的一块；直接塞个 512×512×512 的 dense field，memory consumption 非常高，而真正用到的体积只占一小块

* **OpenVDB**

    * 鼎鼎大名、获得了奥斯卡奖的数据结构（颁奖视频值得一看）；支撑（power）了好莱坞很多特效的制作——比如《驯龙高手》里某条龙的体积表示：龙只占整个空间很小一部分，用稀疏结构把没用到的那部分忽略掉
    * 稀疏数据结构一般有好多层级：最外层的 block size 很大——整条龙可能也就几十个顶层 block；zoom 进去有很多 internal nodes，中间节点比顶层小一点；最小的一层是 voxel，它里面用的结构和稠密 SNode 比较像、也是一个树形结构
    * Taichi 的整个数据结构设计，很大程度上受了 VDB 的启发

* **手写稀疏结构难在哪**

    * 要考虑的事情：边界条件、topology、memory management、怎么并行、怎么做负载均衡、怎么消除数据结构的 overhead
    * 理想：90% 的时间在做计算、10% 的时间花在数据结构 overhead 上；现实很骨感：经常是 90% 的时间在做数据结构访问、只有 10% 在做 essential computation，有时甚至 1% 做计算、99% 都在 overhead
    * 开销来源：最顶层的数据结构可能是个 hash table，lookup 一下十几、几十个周期就没了；遍历的时候有各种 cache miss、TLB miss；写的时候还得激活节点、把它从「不关心」的状态转成「关键」状态，要加各种锁

* **pointer SNode**

    * > **定义**：本质上就是一个 dense array，但它的每一个 element 是一个指针；和 dense 的主要区别是 pointer 可以是空的。
    * pointer 可以为空，意味着这棵树不必像 dense 那样是满满的——可以有选择地 populate，有选择地让一些节点长出来；pointer 是做稀疏（sparse）操作最常用的 SNode
    * 典型搭法：pointer 划分块 →（可以再来一层 pointer）→ 最后用一个 dense 收底——dense 是稠密的，它里面的元素不能再有「有的有、有的没」

    ```text
    ti.root
     └── pointer(ti.ij, 2)       # 2×2 的划分，每个 cell 是一个指针：可有值、可空
          └── pointer(ti.ij, 2)  # 底下再来一层 2×2 的 pointer，同样可空
               └── dense(...)    # 最后用 dense 收底
    ```

* **激活与反激活的语义**

    * 一开始稀疏数据结构是完全不 active 的；数据结构完全 active 的情况下，读一个 active cell 返回它的 value，写就直接把 value 写进去
    * 读一个 inactive cell：Taichi **不会**把它设成 active，直接返回 0
    * 写一个 inactive cell：Taichi 会自动把这个 cell 设成 active 并写入这个值——至少得 active 才能有值，而且就算你写的是 0，Taichi 也会把这个 cell 激活
    * sparse struct-for：当 a 是稀疏的时候，Taichi 只帮你 loop over 里面活跃的、有意义的元素，空的直接跳过去

    ```python
    @ti.kernel
    def bump():
        for i, j in a:      # a 是稀疏的：只遍历活跃元素，空的全部自动跳过
            a[i, j] += 1
    ```

    * 不想通过写的方式点亮/灭掉节点，用 `ti.activate` / `ti.deactivate` 显式激活或反激活一个 SNode 的 element；把 cell deactivate 之后 Taichi 会自动帮你做垃圾回收，这些都不用管
    * 激活示例（16×16 网格点亮上三角）：一开始 x 完全不激活，**不能**写 `for i, j in x`——此时循环什么也没干；要用 `for i, j in ti.ndrange(n, n)` 遍历，`if i < j: x[i, j] = 1` 写上去自然就激活；再额外 activate 一个点、deactivate 一个点即可做演示
    * 太极图标 demo（`ti example taichi_sparse`）：好几层嵌套（8×8 里分 4×4、4×4 里再分……最底层是 1×1×1 的 voxel），只把黑色的地方设成激活、白色的不激活；太极转动时每个 cell、每个节点都在不断地被激活和反激活

    * > **易错点**：⚠️ 数据结构全空时 `for i, j in x` 这个循环什么也不干——初始化激活必须用 `ti.ndrange` 遍历后配合写入触发
    * > **易错点**：⚠️ `ti.deactivate` 不会递归处理 children：pointer 自己还有 active children 时直接 deactivate 它，可能会导致 memory leakage；要连根清掉就用 `deactivate_all`——它把 pointer 里面所有的节点全部设成不激活，还会做 zero fill（下次用的时候值就是 0）
    * 在同一个 kernel 里面不要去 activate 和 deactivate 同一个 SNode；一定要这么做就分两个 kernel：一个负责 activate、一个负责 deactivate，否则 Taichi 的 garbage collection 那里会出一点问题
    * leaf node 很少在最底层用一个 pointer：一般是 pointer 指向一个 dense（比如 4×4×4 的 dense 或 bitmasked）——每个 pointer 本身也是 overhead，希望用 dense 去均摊 pointer 的 overhead
    * bitmasked 是另一个常用的 SNode（可以看 unit test 里的各种样例学习）；dynamic 有点像 std::vector，相当于一个动态长度的数组

* **稀疏网格 MPM：几乎不用改的代码**

    * 唯一要改的地方是网格定义：把 `ti.field(..., shape=...)` / `ti.Vector.field(..., shape=...)` 换成 `ti.root.pointer(ti.ij, n)` 先铺一层 block（pointer），pointer 里面再来一个 dense，把 `grid_v` 和 `grid_m` place 进去——kernel 的代码几乎完全不用变

    ```text
    原来：ti.field / ti.Vector.field(..., shape=(n, n)) 直接开稠密网格
    现在：ti.root.pointer(ti.ij, n)   ← 先铺一层 block（pointer）
          └── dense(...)，place 进 grid_v 与 grid_m
    每步 P2G / G2P 之前：deactivate_all()
          —— pointer 下面的所有节点全部反激活并 zero fill，
             下次用的时候值就是 0
    ```

    * 跑起来的效果：只有有粒子的地方才 allocate 这个 grid，灰色的地方就是不 active 的地方；一般在 2D 里用 dense 完全足够，3D 里用 sparse 可能更好一些
    * 3D 实例：100 million（1 亿）个粒子的 MPM 在单个 GPU 上跑，整个模拟下来大概要 8 个小时、每一帧大概 13 秒；grid 用 sparse grid，开了 4096×4096×4096 个 space voxel（实际上用不到那么多，只是开着这么多而已）；代码公开在 taichi_elements 这个库里
    * 用 Taichi 写一个高性能的 MPM solver（还是 sparse grid、而且无边界的）现在大概四五百行代码就可以了。

## 简单性与复杂性

### 简单性为什么好

* **simplicity（简单性）**

    * 构建物理引擎和太极这个项目的十年里，如果只能用一个词概括学到的东西，这个词就是 simplicity
    * 基础教育/本科阶段，学生最重要的事是把考试考过——证明自己**会**某种方法；本科毕业以后去工作、读 PhD 做研究做工程，最重要的能力是证明自己**能找到**好的方法
    * 离开学校、离开考试的环境以后，有两件事会改变：有了自己选择方法的权利；需要与他人合作——往往用哪种方法并不重要，系统性地解决问题才最重要
    * 一天只有 24 个小时——这件事三岁小孩都懂，但真正意识到「自己的时间是有限的」并不容易；姚期智在饭桌上说：聪明的人都是一样聪明的，你不可能指望一个人比你聪明十倍——他不可能长十个脑子；大脑是生物构造，不像微电子里的摩尔定律 18 个月翻一倍，它不会怎么增长、容量就是有限的。
    * 在时间和脑力都非常有限的情况下必须采取的措施：用简单可行的方法，去解决大部分简单的问题——用最少的时间把简单的问题解决了，才会有时间去解决真正复杂的问题
    * 有影响力的创新，往往伴随着复杂性的减少；你觉得新东西复杂，是因为在你接触到它之前，发明它的人已经对它进行了最大程度的简化
    * 借日本文化「不要给他人带来麻烦」的宗旨来体会：要发明一个新的东西，必须让你的用户能够轻易地使用它——造出来的东西必须是简单的。
    * 写了 paper、发明了新算法，但太难以使用、没人能正确使用，能产生的影响（impact）非常有限；写了难以使用、难以读懂的代码，合作时 reviewer 会把它 cut 掉——即使有幸进了最终的代码库，它的维护、测试与正确性也都难以保证

### 复杂性的原罪

* **其他人理解不了，影响力就小**

    * 其他人不见得和你有一样的背景知识，你做的那种东西他们不一定懂——非常复杂的东西没人能懂，产生的影响力就非常小

* **没办法快速失败（fail quickly）**

    * > **定义**：用最小的代价，尽快知道一个方法到底 work 不 work
    * 做科研就知道：99% 的想法都是不 work 的；剩下的 1% 里面，可能有 90% 是被前人尝试过的；真正能 work 的想法，大概只剩千分之一

    ```text
    全部想法（100%）
     ├─ 99% 不 work ─────────► 尽快失败，别恋战，赶紧换下一个
     └─ 1% 勉强有希望
         ├─ 90% 已被前人尝试过 ► 查文献就能排除，别重造轮子
         └─ 约 1‰ 真正能 work ► 只有靠快速失败才抓得住它们
    ```

    * 非常复杂的想法实现起来非常费时间，就很难快速失败：你不知道到底是自己实现错了，还是这个方法本身不行——很难区分到底是方法复杂，还是自己没有实现好，这是复杂方法的原罪

* **更容易出错，错了还查不出来**

    * 复杂方法成分太多，出了错以后很难分析——不知道到底是哪一部分搞错了。
    * 很多非常复杂的 simulation 算法虽然发表在了顶级会议，但随着时间推移很快被大家遗忘：太复杂，没有人能够正确实现
    * 照着一个 paper 实现算法本来就非常难（不给代码的话）：实现了半天发现不 work，到底是 paper 有问题、实现得不对、还是对 paper 的理解有问题？很难知道——甚至可以说不科学，因为你不能证伪它

* **性能优化的前提是简单**

    * > **易错点**：⚠️ 「算法越复杂越快」是个错觉——考虑上体系结构和高性能计算技巧能把算法提高十倍乃至二十倍，但前提条件是算法足够简单
    * 非常复杂的程序，即使知道花很多时间能让它快十倍二十倍，也没人有动力去做——太复杂太烦了；高性能本身就是一个复杂性，人能 handle 的复杂性是有限的：算法本身复杂，剩下的能接受的复杂性就非常小，能用在优化上的脑力就非常少
    * 把 physical solver 搞得非常复杂，编译器也很难优化：编译器遵循规则去分析程序，程序复杂到难以分析，它生成的代码质量也会受影响
    * 最终结果：复杂的数据结构、自适应数据结构、复杂的网格、复杂的数值格式，最后都会败在暴力解法之下
    * > **定义**：暴力解法——稠密数据结构，加上一阶精度的有限元或者 MPM；当然这不绝对（有限元有时还是会用很高的精度），另一条路子是就用一阶精度的单元、把分辨率堆得很高很高——严格意义上可能不太行，但实际情况下往往就不错

### 搞复杂的六个动机

* **总命题**

    * because it's way easier to be complicated than to be simple——搞出复杂的方法，比搞出简单的方法简单多了；对大部分人来说，精力、经验、资源和条件有限时，搞出来的方法往往是复杂的。

* **为了证明自己聪明**

    * 教育里存在「需要通过复杂方法证明自己与众不同」的现象，在学校里或许是好主意；但当你需要和其他人交互时，这几乎永远不是一个好主意
    * 沟通是最难的事情，比写代码难多了——有研究说人的语速一秒钟大概只能传 10 个 bit，传输速率非常低；这就是为什么简单、精炼的方法能够流传得很广
    * 一旦要和他人沟通，就一定要把事情简化、简化、再简化

* **为了展示工作量（show off the amount of work）**

    * 学校里「报告要写五页/十页」会让方法不够复杂的学生想办法把方法搞复杂凑页数；学校更「过程主义」——看的是解决问题的过程，目的是让你学会解决问题的方法
    * 脱离老师、学校与考试的环境后，真正解决实际问题时 who cares 你用什么方法——在合乎道德、合乎逻辑的情况下把问题解决好就行；大部分专家并不需要去 show off 自己的 amount of work

* **为了把错误藏起来**

    * 「做的工作可能有错误，把它搞得非常复杂，就没人能证明我是错的」——说起来很讽刺，但确实有人这么做；这么想的时候已经开始违背科学精神
    * 卡尔·波普尔对科学的定义：科学独一无二之处在于它必须满足可证伪性——如果这个论断是错的，你可以去证明它是错的；把东西搞得既不能被证真、也不能被证伪，就是 not even wrong（连错了都不是），不属于科学讨论的范畴

* **为了和已有工作（prior work）划清界限**

    * 方法非常简单可能被 reviewer 以「和某某 paper 做的一样」拒掉，于是有些同学这边打个补丁、那边打个补丁，使方法看起来和之前不一样
    * 如果目的就是让论文被接收、读个 PhD 尽快毕业，这么做完全可以，也确实有很多人这么做；但如果真希望文章有很大的影响力，最好别这么做——这叫 incremental work（增量性工作），往难听了说就是灌水，很难产生很大的影响力

* **只是懒得简化**

    * 一个想法诞生的过程：往往 20% 的时间在想这个东西、做一个雏形（写上一坨乱七八糟的代码），然后花 80% 的时间去简化它，得到一个最小的、还能工作的代码
    * 只花那 20% 的时间，相当于只用了别人五分之一的时间，得到一个非常复杂的算法——这就是懒得去简化；希望别人能够理解、希望长远有影响力，最好花一点时间去简化你的想法

* **因为观众太宽容（audience being too nice）**

    * 考试时故意写出一大坨显得懂得多，阅卷老师觉得「不知道对错，好歹给个辛苦分」——这纵容了把事情搞复杂的想法，但这种事只会在学校里出现；实际工作中，没有人会 appreciate 你做了很多工作、最后没人能理解这种事情
    * 姚班某老师的规则：如果你的方法非常复杂，我们看了半天也不知道它是对的还是错的，我们会当作错的来处理；如果说你不会，那你就写你不会，我会给你三分——但不要说你不会、还写上一大坨，浪费阅卷人的时间也浪费你自己的时间

### 追求简单的先行者

* **爱因斯坦**

    * 任何事情都应该被搞得 as simple as possible, but not simpler——尽可能地简单，但不能更简单
    * 这是物理学里的一个原则：你得相信这个世界是被一些简单的规律来描述的，要不然你都很难去研究这个世界

* **C++ 之父**

    * 在 CppCon（C++ 的会议）给过很多关于简单性的 talk：make simple tasks simple（用简单的方法解决简单的任务）；being too clever is not clever（表现得太聪明，并不是聪明人的做法）
    * 他很喜欢的例子：调试一个程序比写程序还要难两倍——写程序大部分时间不是花在敲键盘上，而是花在调 bug 上；如果写的时候已经把全部脑力用上了，调试的时候就没法调试了。
    * 别人来接替你的工作、在你的代码上继续工作，本来就比你自己在自己的代码上工作更难；代码写得非常复杂，就只能找一个比自己更聪明的人来接手——但大家都一样聪明，很难找到，最后的结果就是项目自己死了。

* **霍尔（C. A. R. Hoare，1980 年图灵奖得主，快速排序发明人）**

    * 两种软件设计的方法：第一种，使软件足够简单、以至于显然没有错误；第二种，使软件足够复杂、以至于没有明显的错误——第一种方法难得多
    * 他说的第二种就是「打补丁」：这种情况会错打个补丁特殊判断、那种情况会错再打个补丁，最后得到一件满是补丁的衣服——很难说它有没有洞：既难指出它哪里有洞，也不能证明它没有洞

* **2017 年的图灵奖得主**

    * 在 Google 给过 talk《How to Have a Bad Career》（如何毁掉你的职业生涯，说反话），列出毁掉职业生涯的十个做法，其中第二点是 let complexity guide you（让复杂性指导你）
    * 两点：其一，it's easier to be complicated——无论做 research 还是 engineering，打补丁把事情搞复杂永远是简单的方法，而提出简单的想法、把问题解决掉往往是最难的；其二（反讽那种心态）：「如果我的方法很简单，那我怎么能显示出我和同事们的优越性呢？」
    * 往往最伟大的想法，都是很简单的

### 简单性的实战回报

* **ChainQueen（ICRA 2019）**

    * 一开始的目的就是做一个可微分（differentiable）的 MPM solver；做这个项目时还没有自动微分系统，必须手动求导数，求的非常痛苦——求导要用很多链式法则（chain rule），所以把 chain 这个词塞进了项目名
    * 非常好的前提是已经有 MLS-MPM——一个比传统 MPM 简单得多的算法；正因为 MLS-MPM 非常简单，才能在 25 天之内做出一篇 ICRA paper，并且能够正确地把导数推出来
    * 如果是一个非常复杂的 MPM 算法，根本就不会去推它的导数——太难了推不对，人的脑力有限；没有这个简化版的 MPM，后面很多工作都是做不了的。
    * 后来有了自动微分系统 DiffTaichi，目的就是进一步简化可微编程——再也不需要手动推导求导数

* **MGPCG 的 80 分钟**

    * multigrid PCG（MGPCG，多重网格预条件的共轭梯度，用来解线性系统——解泊松方程）流程挺复杂，一般大家都不愿意去实现，因为太难了。
    * 有了太极：只用 80 分钟（git log 里看实现前和实现后两个 commit，差了 80 分钟）、300 行代码把这个算法实现出来；换成 C++ 或者 CUDA，绝对不可能 80 分钟之内写一个 GPU 的 MGPCG
    * 这门课把太极的 idea 再推了一步：大家交的作业里很多都用上了 multigrid——MGPCG 这个算法在中国的物理模拟圈子里，代码可能已经人手一份

    ```text
    很少有人能正确实现
            │  有了太极：80 分钟、300 行代码
            ▼
    我能轻易、正确地实现
            │  这门课把太极的 idea 再推一步
            ▼
    大家都能轻易、正确地实现（作业里很多都用上了）
    ```

    * 一个算法的最终归宿：好的归宿是被大家都能掌握，坏的归宿是被大家都淡忘

## 物理引擎的未来

* **总体判断**

    * 一开始很有雄心的目标是「在计算机里模拟这个世界（simulate the world）」——即使现在最好的物理引擎（各种游戏物理引擎、面向 VFX 的离线物理引擎）也没有实现这一点，好多地方都还做得很不好

* **易用性**

    * 怎么快速、正确地设置参数？物理引擎里这么多拉杆、这么多参数要设置，让艺术家来操作就跟开飞机一样——一脸蒙圈，不知道各个参数怎么设置

* **健壮性**

    * 手稍微抖一下 simulator 就炸：数值不稳定、CFL condition 被违反、本来是对称正定的矩阵变成对称不正定等。
    * 怎么写一个健壮的 physical simulator，其实并没有被很好地解决

* **完备性**

    * 多种材料耦合——真的做到任意多种材料都能耦合了吗？并没有；MPM 里面勉强能够做到一些：固体怎么和刚体耦合、怎么和烟雾耦合，但任意材料之间的耦合到现在也没有很好的解决方案
    * 一定要做到完备性的时候，往往会牺牲许多其他的性质：易用性、健壮性或者真实感

* **真实感**

    * 今年蒋老师有一个 MPM paper 模拟了一块东坡肉，在真实感上又往前推了一步
    * 以前的 MPM，它的 fracture（破碎）是各向同性（isotropic）的；东坡肉肥肉上面有一层皮，撕开时它内部连接得非常好——整层皮一起掉下来
    * > **提示**：各向同性（isotropic）指性质不随方向变化；「整层皮一起撕下来」这个表现，恰恰说明这层皮的破碎是各向异性的。
    * 有没有一个很好的方法能一劳永逸地把真实感的问题解决掉？现在好像还没有；一个 universal 的、性能很高、能模拟各种材料且都很真实的 simulator 是不存在的——只能针对不同的方法，用不同的 simulator 得到不同的真实感、不同的完备性

* **性能与生产力**

    * 现在很多 simulator：real time 就别说了，60 frames per second 做不到，可能 60 seconds per frame（一帧 60 秒）有的时候都不一定能做到——等结果要等很长很长时间
    * 高性能计算、领域特定编程语言和编译器，是必不可少、必须要做的事情
    * 其他待解难题：怎么自动地实现自适应网格；怎么自动地做到多 GPU、多节点的分布式全自动 simulation——特别是要把它和编程语言、编译器结合起来，使得程序员写的还是一个单 GPU/单机的程序，这个问题到现在也没有一个很清晰的 idea
    * 里面还是简单性、简单性、简单性：必须把一个东西搞得非常简单，才有可能去提高它的性能；如果它已经很复杂了，就很难优化

* **Learning 和 Simulation，谁给谁打工**

    * learning for simulation：搞一个神经网络去近似物理模拟器，下次做物理模拟就不用 simulator、用神经网络 evaluate——还需要一段时间的发展；现在的这类论文跟真正的物理模拟器比，既不快、效果又不好
    * 原因：现在的 simulation 是研究偏微分方程的数学家、一代又一代的数值计算专家，加上早期提出 PDE 的物理学家、研究力学的各位同仁，研究了超过 100 年才得到的简单易用且高性能的 solver；想用一个神经网络一劳永逸地替代它，还是有点难
    * 从高性能计算角度算账：MPM 一个粒子占的空间可能是 24 个 byte，一个 time step 用的 FLOPs 可能也就几百到几千个——用这么有限的计算资源去非常精确地 approximate 物理模拟的过程，还是挺难的。
    * simulation for learning：用 simulation 搞一个虚拟环境，在里面训练机器人、无人驾驶这样的任务——降低实验成本；这是非常 reasonable 的，因为得把 simulation 作为信息来源，不能把神经网络作为信息来源
    * 讲者的一家之言：simulation for learning 比 learning for simulation 更有意思一些

## 课程成果与结语

* **课程规模**

    * 世界上第一次用中文开设的物理引擎课；超过 1000 名同学参加（把加入课程微信群的同学算作参加）；播放量 3 万多——十讲平均每讲将近 3000 人次；接近 50 份引擎项目提交——这不是填代码、写三行代码就能提交的作业，是完全开放的项目、耗时非常长，能有 50 份独立完成的作业非常不容易
    * 作业二时间非常紧（不少同学正逢期末考试、工作繁忙），仍有 12 位同学提交，每位获寄一份纪念品（太极茶杯）
    * 太极竞赛（ChinaVR 上）：报名表精简成「一分钟完成报名」——只有四个问题、三个必填；奖项：特等奖 1 个、一等奖 3 个、二等奖 6 个，三等奖和优秀奖若干——基本完成一个合格的提交都会拿到某种奖项
    * 大家掌握的新技能：一门新的编程语言；基于物理的模拟的各种算法；数值线性代数的方法；现代计算机的处理器微架构；类型系统；并行编程、GPU 编程这些高性能计算入门；稀疏数据结构和元编程——后两个是太极的独特功能。

* **太极在课程里的贡献**

    * 第一次做到了：在计算机图形学里，程序能够复制粘贴、直接运行——以前一个程序往往有很多依赖：OpenGL、GLEW、GLFW、CUDA、某些特别的硬件和 GPU，还要问 gcc/MSVC 是什么版本，恨不得把电脑复制一份才能运行
    * 意义是加速知识传播：写代码的人知道代码写出来别人都能运行，动机就更多；使用者复制粘贴后不用配三天环境——太极基本上解决了配环境的问题
    * 大家通过课程和太极快速掌握了讲者当年折腾好久才弄懂的知识——当时没人教、没有资料也没有太极，手写 C++ 很多坑自己亲自踩；这样的知识在全世界能掌握到「能教」程度的人可能不超过 50 个
    * 课程第一次普及了 MGPCG、MLS-MPM 和自动微分相关的算法——这些名词在中国的计算机科学社区里此前相对不常见，这些算法本身都非常简单有效
    * 太极从开课时的 0.6.7 版本到 0.6.27，中间经过了 20 多个版本；每周三、周六定时发布新版本，让大家对版本发布有稳定的预期
    * 助教们的贡献：PLY dumper（把太极里的数据导出到 Blender 这些工具）、修了很多 compiler bug、实现了 ti.field、往论坛输出视频和 GIF 图片

* **讲者的收获**

    * 最大收获是大家交了作业：每天醒来第一件事就是看论坛有没有新作品——发明编程语言还是希望能有人用；把语言搞得非常复杂、没人能用，或许能证明自己 smart，但只是很局限性的 smart；真正有智慧的人做的事，是发明一个工具，让自己的智慧延伸到其他人的大脑里
    * 备课讲课都比设想的难不少：周一到周五有别的事只能周末备课，每个周末都像打仗——原来一周只工作五天是有道理的。
    * 自己懂了不见得能流利地讲出来：要确保别人和你有一样的背景知识、一样的思维方式；很多东西讲课时要解释清楚背后的逻辑，才发现自己其实并没有懂——讲一门课才知道自己在这方面有多无知
    * 工具上的结论：LaTeX 真难用，但公式排版效果还是好——最终用混合方案：讲公式的时候用 LaTeX，其他的东西用 Keynote
    * 麦克风的教训：花四五十美元买的麦克风，讲到第八讲才发现一直对着它的 180 度方位（背面）在说话——0 度的正面才是收音端，背面是降噪的部分（过滤观众那边的噪音）；设计给人前后对称的暗示，但归根结底是自己没看文档

    * 达特茅斯的朱教授：做基于物理的模拟、计算流体力学，也包括机器学习和物理模拟的结合；在 MIT 做 postdoc 期间与讲者一起做了好几个项目，是非常考虑学生、学术水平非常高的教授（读 PhD/master、做 intern 或 visitor 都可以直接发邮件）

    * 讲者读了 PhD 以后非常喜欢扫地：因为扫地可能是生活中唯一一个只要去做了就能成功的事情；积极版的一句话是「努力不一定成功，但是不努力一定不能成功」——只有努力了，才有概率能成功

* **最后三句话**

    * 韩愈《师说》：「是故弟子不必不如师，师不必贤于弟子，闻道有先后，术业有专攻，如是而已」——能讲这门课并不是因为和其他人有什么本质不同，只是 10 年前恰好对这个话题产生了兴趣、花了难以想象的时间在上面；大家花同样多的时间，也可以开自己的这门课
