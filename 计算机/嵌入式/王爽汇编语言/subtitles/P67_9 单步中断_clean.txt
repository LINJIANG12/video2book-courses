# 单步中断与 Debug 调试机制详解

### [00:00] 引言：Debug 中的 T 命令与指令执行流程

在这一节中，我们介绍单步中断。

我们首先从 Debug 工具中的 `T` 命令开始。程序一般的执行顺序是：
1. 取指令；
2. 改变寄存器 $CS$ 和 $IP$ 的值；
3. 执行指令；
4. 执行完当前指令后，再去取下一条指令，依此类推持续执行。

但在 Debug 中，我们观察到它提供了一种单步执行的功能。通过单步执行，每执行完一条指令后，Debug 会显示所有寄存器的当前值，并在此等待用户输入下一步的命令。

那么在 Debug 当中，是通过怎样的机制让 CPU 能够执行完一条指令就停下来呢？这里面一个非常关键的要素在于：**Debug 程序利用了 CPU 提供的单步中断功能**。

而单步中断功能的关键，就在于 CPU 内部的一个标志位——$TF$。

---

### [00:58] 单步执行与断点调试的原理

在使用 `T` 命令的时候，Debug 会将 $TF$ 标志位设为 $1$。只要 $TF$ 标志位为 $1$，CPU 在执行完一条指令之后就会停下来，处于单步中断方式下执行。

在实际的程序设计与处理过程中，单步中断的处理程序也是可以自定义的。通过自定义单步中断处理程序，我们可以利用单步机制去实现一些特殊功能。

事实上，让指令停下来能够做很多事情。例如，在高级语言程序设计中，可以通过一系列调试功能设置断点，让程序停留在某一个位置。程序停下来之后，我们可以观察变量的值，甚至可以修改表达式或变量的值，进而影响程序后续的执行流程。因此，单步执行或让程序暂停的功能，在实际应用中是非常常见的。

---

### [02:03] 关键标志位：TF（陷阱标志）与 IF（中断标志）

要深入理解单步中断的过程和处理方法，必须先了解两个与中断相关的标志寄存器位：

1. **$TF$（Trap Flag，陷阱标志）**
   * 位于标志寄存器（FLAGS）的**第 8 位**。
   * 用于调试时的单步方式操作，负责控制单步执行形式。
   * 当 $TF = 1$ 时，CPU 每执行完一条指令，就会产生一个内部陷阱并停下来，交由系统控制计算机。
   * 当 $TF = 0$ 时，CPU 正常工作，不产生陷阱中断。
   * 因此单步执行的逻辑非常直接：当需要单步执行时，就将 $TF$ 置为 $1$，CPU 的工作便会进入单步执行模式。

2. **$IF$（Interrupt Flag，中断标志）**
   * 位于标志寄存器（FLAGS）的**第 9 位**。
   * 当 $IF = 1$ 时，允许 CPU 响应外部的可屏蔽中断请求。
   * 当 $IF = 0$ 时，关闭并屏蔽外部中断。关于可屏蔽中断，后续课程会进一步展开。

---

### [03:26] 单步中断的处理过程及 TF 置 0 的原因

当 CPU 执行完一条指令后，如果检测到标志寄存器的 $TF$ 位为 $1$，就会引发**单步中断**。单步中断的中断类型码是 **$1$**。

一旦确定了中断类型码，中断处理程序的入口地址就可以在中断向量表中查到。引发中断后，CPU 从中断向量表中获取单步中断处理程序的入口地址，并跳转去执行该处理程序。

将这个过程进一步细化，CPU 响应单步中断的具体步骤如下：
1. 取得中断类型码 $1$；
2. 标志寄存器（FLAGS）入栈保存；
3. 将标志位 $TF = 0$、$IF = 0$；
4. $CS$ 与 $IP$ 寄存器入栈保存；
5. 从中断向量表中读取中断入口地址并写入 $CS$ 和 $IP$。

#### 为什么在进入中断过程时必须将 $TF$ 设置为 0？

单步中断是由 $TF = 1$ 触发的，但进入中断处理流程后，CPU 却立即将 $TF$ 设置为了 $0$。原因在于：

中断处理程序本身也是由一条一条机器指令构成的。如果我们在执行单步中断处理程序之前不将 $TF$ 置为 $0$（即 $TF$ 依然保持为 $1$），那么 CPU 在执行完单步中断处理程序的**第一条指令**后，又会检测到 $TF = 1$，从而再次触发单步中断。

接着，CPU 又会转去重新执行单步中断处理程序的第一条指令。这样一来，整个过程将陷入无限死循环，CPU 将永远只能重复执行单步中断处理程序的第一条指令，无法正常执行后续的处理逻辑。

为了避免这种情况发生，在进入中断处理程序之前，硬件自动将 $TF$ 设置为 $0$。这表明：虽然是因为 $TF = 1$ 才进入中断，但既然已经开始处理单步中断，在处理程序内部就不允许再产生新的单步中断。

> **补充说明**：除了单步中断，在响应其他中断时也会将 $TF$ 清零，这同样是出于类似的考虑。当然，如果进入其他中断例程后，用户确实希望对该中断例程进行单步调试，也可以在例程内部显式地把 $TF$ 重新设置为 $1$。

---

### [06:04] 向量寻址与入口跳转

在将标志位清零并将当前 $CS$、$IP$ 入栈后（便于后续中断返回），CPU 会读取新的中断服务例程入口地址：
* 单步中断的中断类型码为 $1$，因此对应的中断向量表地址偏移为 $1 \times 4 = 4$；
* 偏移地址 $IP$ 从内存 $0000:0004\text{H}$ 处读取；
* 段地址 $CS$ 从内存 $0000:0006\text{H}$（即 $+2$ 的位置）处读取；
* 取出后分别送入 $IP$ 和 $CS$，从而开始执行单步中断处理程序。

---

### [06:46] 特殊情况：不响应中断的指令（设置 SS 寄存器）

在一般情况下，CPU 执行完当前指令后，只要检测到中断请求就会响应并进入中断处理过程。但在某些特殊情况下，即使指令执行完毕且发生了中断条件，CPU 也不会响应。

一个典型的例子就是**向栈段寄存器 $SS$ 传送数据的指令**。

当 CPU 执行完修改 $SS$ 寄存器的指令后，即便当前发生中断（包括 $TF = 1$ 的单步中断），CPU 也绝不会立即响应。

#### 示例分析

在设置堆栈时，我们需要指定栈段寄存器 $SS$ 和栈顶指针 $SP$：

```assembly
mov ax, 1000
mov ss, ax
mov sp, 10
```

如果在 Debug 环境中对上述代码进行单步执行调试：
1. 执行第一条指令：`mov ax, 1000`，单步执行后可以看到寄存器 $AX$ 变为 `1000`；
2. 紧接着要执行的是：`mov ss, ax`；
3. 此时输入 `T` 命令单步执行该指令。

执行后观察状态：
* 执行前当前 $IP$ 为 `1003`，理论上下一步停下来的位置应该是 `mov sp, 10` 所在的偏移地址 `1005`；
* 但实际观察会发现，$IP$ 直接跳到了 `1008`，且寄存器 $SP$ 的值已经直接变成了 `10`。

这意味着：**在执行完 `mov ss, ax` 之后，CPU 并没有停下来，而是紧接着连同下一条指令 `mov sp, 10` 一同执行完毕后才暂停**。换言之，只敲了一次 `T` 命令，CPU 却连续执行了两条指令。

---

### [08:51] 连续设置 SS 与 SP 的底层机制

出现上述现象的原因在于：
$SS$ 和 $SP$ 是联合起来共同指向栈顶的。对栈段寄存器 $SS$ 与栈顶指针寄存器 $SP$ 的设置，必须作为一个原子性的整体连续完成。

如果在修改了 $SS$ 之后、$SP$ 尚未修改完成的瞬间插入了其他指令或发生了中断，CPU 就需要向栈中压入标志寄存器、$CS$ 和 $IP$。而此时 $SS$ 已经改变，$SP$ 却还是旧值，栈顶指针将指向一个错误甚至非法的内存区域，从而引发栈数据破坏、甚至导致系统崩溃。

因此，8086 CPU 在硬件层面上强制要求：**凡是修改堆栈段寄存器 $SS$ 的指令，在其执行完毕后紧接着的下一条指令执行结束之前，CPU 强制禁止响应任何中断（包括单步中断）**。CPU 内部自动忽略 $TF$ 标志的单步中断触发，确保栈设置相关的指令能够连贯执行完毕。

#### 编程规范

在汇编语言程序设计中，以下写法是错误的逻辑结构：

```assembly
mov ax, 1000
mov ss, ax
; 中间插入了其他无关操作
add bx, cx
mov sp, 10
```

虽然这种写法在语法上不会导致编译器报错，但由于人为打断了 $SS$ 与 $SP$ 的连续赋值，如果执行单步调试或发生硬件中断，很容易出现不可预知的错误。在程序设计中，必须杜绝在设置 $SS$ 和设置 $SP$ 之间插入任何其他指令。
