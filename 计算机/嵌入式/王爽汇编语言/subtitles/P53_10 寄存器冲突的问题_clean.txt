# 寄存器冲突问题及其解决方案

### [00:00] 引言与问题引入：字符串转大写的初步方案

在这一节我们介绍寄存器的冲突问题以及它的解决方法。

先看一个例子：我们在编程的时候，将 `data` 段当中的字符串转成大写，以前我们曾经编写过这样的程序。对于这个程序来讲，我们要去给它循环 12 次。循环的程序我们放到一个子程序当中去做——`capital`，在这里边去调用它，然后在这里边通过 `loop` 这个循环去做。

所以在这里边这个 12 非常关键。它作为一个参数传进来以后，有 `si` 这么一个起始地址，有 12 这么一个循环次数，它能够把 `'conversation'` 这样一个字符串逐个地转成大写。这是我们前面曾经看过的一个例子。

---

### [00:46] 引入以 0 结尾的字符串标志

在这里边不禁就要问了：这个 12 是怎么来的？

当然这个 12，我们在编写程序的时候，在这儿一个一个数呗：1、2、3、4、5 一直数到 12。这种方法其实真的是太弱了。为什么呢？这个事情要由人去做，有点可惜。

在这里边我们可以想到在 C 语言里面曾经用过一个 `\0`。`\0` 是什么呢？特殊的一个字符，ASCII 码值为 0 的这样一个字符。那么在这里边能不能够用汇编语言去做呢？当然也是可以的。接下来我们就看这样一个解决方案。

---

### [01:21] 基于 0 标志的子程序设计

我们可以在定义数据的时候，`'conversation'` 后面加一个逗号 `0`，反正它是一个字节型数据。所以在这 12 个字节之后再加一个 0，ASCII 码值为 0 的符号我们在这里边有的。

现在在处理这段字符串的时候，我们就可以看：如果读到的不是 0，我们就去把小写转大写；而如果读到 0 的时候，代表着结束，这个是可以做的。

因此，我们把这个任务可以这样去完成：在一开始的时候，去给它设置数据段，然后去载入它内存的起始地址，然后再去调用 `capital`。所以在这一块来讲，我们设置了字符串的起始地址，然后去调用子程序。

调用的子程序是在这一块。我们可以看到：在调用子程序的时候，首先把 `si` 所指向的那个内存单元当中的字符取出来，放到 `cl` 里面；然后我们把 `ch`，也就是 `cx` 当中的高 8 位赋值为 0。如果在这个时候 `cl` 读到的是 0 的话，和 `ch` 两个一配合，`cx` 就是 0。于是 `jcxz` 的跳转，$cx = 0$ 就成立了，所以它就会跳转到 `ok` 的地方去 `ret` 返回。

```assembly
; 数据段定义（以 0 为结束符）
db 'conversation', 0

; 主程序设置并调用
mov ax, data
mov ds, ax
mov si, 0
call capital

; 子程序 capital 实现
capital:
    mov cl, [si]
    mov ch, 0
    jcxz ok
    and byte ptr [si], 11011111b    ; 小写转换为大写
    inc si
    jmp short capital
ok:
    ret
```

于是我们连起来看一下：只要所读到的是这个 0，它就会返回；而如果在这里边，`cl` 所读到的是这里边的任何一个字符且它不是 0 的时候，该如何去做呢？这个地方不会发生跳转，所以会执行下边的语句，把小写转成大写。然后再把 `si` 增加 1 以后，再跳转到 `capital` 去处理下一个符号。所以这样一个循环是非常容易看到的。

也就是说，我们这个子程序将依次读取每个字符进行检测：
- 如果不是 0（在这 `cx` 得到的值不是 0），它将会去转换；
- 而如果在这里边 `cx` 得到 0 了（`cl` 是 0，`ch` 是 0），那么它就会结束处理。

在这个程序里面我们可以看到，不再需要字符串长度作为参数了。在前面我们没有了这个 12，而是始终根据这个 0、`cx` 是否为 0 去判断它是否结束。所以在这里边我们看到字符串处理的这样一个技巧。

### [03:49] 寄存器冲突问题的提出：多字符串处理

接下来就是我们这一节里面关于寄存器冲突的问题正式闪亮登场了。

我们将从这样一个例子开始。同样还是字符串转大写，但是现在我们可以看到，在数据区给出的字符串是 4 个字符串。

```assembly
datasg segment
    db 'word', 0
    db 'unix', 0
    db 'wind', 0
    db 'good', 0
datasg ends
```

于是这 4 个字符串在处理的时候，我们这样来：在一开始的时候，也还是把这样一个数据区给它设置好。而在这块既然是 4 个字符串，我希望它能够循环 4 次，在这 `cx` 是 4。然后从 `s` 开始去做这样的工作，将来 `loop s` 能够返回来。

我们可以看到对这块来讲，`cx` 决定了这段循环能够循环 4 次，每一次处理一行这样的字符串。而每一次在处理的时候，`bx` 一开始的时候是 0，然后把 0 赋给 `si`，它其实对应的是这段字符串的一个起始地址，然后调用 `capital`。

对 `capital` 的这段我们很熟悉，跟刚才完全是一模一样的。它其实能够去把一个以 0 结束的字符串的小写转成大写。它在干完这个事以后，通过 `ret` 返回来。

要处理下一个字符串的时候，前一个字符串是 5 个字符，下一个也是 5 个字符，所以 `add bx, 5`。所以在 `loop s` 回来以后，`bx` 加 5 以后放到 `si` 里面，传递到这儿的 `si` 就加了 5，我们会去处理下一个字符串、再下一个字符串，这么一直处理下去。

```assembly
; 外层主循环处理 4 个字符串（存在冲突的代码）
    mov ax, datasg
    mov ds, ax
    mov bx, 0

    mov cx, 4
s:  mov si, bx
    call capital
    add bx, 5
    loop s
```

所以在这里边，`cx` 和这儿的 `loop` 决定了对 4 个字符串进行处理。而对每个字符串进行处理的时候，这段代码跟刚才完全是一模一样的：
- 首先把 `si` 所指向的单元的字节放到 `cl` 里面，`ch` 置 0；
- 然后去判断 `cx` 是否为 0：如果是 0 的话，通过 `ok` 返回；如果不是 0 的话，去转大写；
- 最后 `jmp` 再把它跳转回来，处理完一个一个的字符串。

### [06:07] 冲突成因与程序崩溃分析

这个程序好懂，但是这里边一定要告诉大家：

在调用函数之前，`cx` 是作为控制外层循环结构的计数器（循环计数）；而我们看到在 `capital` 当中，它又用作去读入我们的数据、读入字符。

我们可以想一下：当在子程序中 `jcxz` 在退出到达 `ret` 的时候，我们会知道这个 `cx` 已经变成 0 了！我们只要调用一次它，`cx` 就会变成 0。所以当它 `ret` 返回到主程序的时候，其实 `cx` 已经是 0 了。

而 `cx` 已经是 0 以后，到 `loop s` 的时候，我们知道 `loop` 指令是先将 `cx` 减 1，然后再判断 `cx` 的值。那么 $0 - 1$ 会在 `cx` 中产生一个值：

$$\text{cx} = \text{FFFFH}$$

赋了一个 `FFFFH` 这么大的一个数！而这个数对循环来讲是引起灾难了。事实上这个程序如果编译运行的话，是会崩溃的一个程序。

这里边其实就是我们的问题——**冲突**。

`cx` 在调用函数之前我们已经有用了，然后你在子程序里面又给它派了另外一种用场，这不就找茬吗？这就是冲突。所以我们在编写程序的时候，需要把对同一个寄存器有两种用法、并且值产生冲突的问题解决掉。

### [07:48] 常见解决思路的局限性分析

寄存器冲突的问题该如何去解决呢？有两个可能的方案：

#### 方案一：主调程序规避
在编写调用子程序的程序（主程序或其他调用程序）时，要注意看一看子程序里面有没有用到会产生冲突的寄存器。如果有的话，调用的人就自觉点：人家子程序里面用了，我在外层就不用了。

但这会产生这样的问题：调用子程序就会变得很麻烦，必须小心地去检查子程序中是否有将会产生冲突的寄存器。子程序里面用的那些寄存器，我在外边就不能用了。而且在这个时候我们必须要求看到子程序的源码；如果看不到的话，根本不知道它子程序里面到底用了哪些寄存器。

很多子程序我们会做成一个标准的模块，我们知道它是干什么的，不需要知道它怎么干。而现在居然要知道它里边到底用了哪些寄存器，所以这个方案非常难。

#### 方案二：子程序规避
从另外一个角度来讲，在编写子程序的时候，子程序当中不要使用会产生冲突的寄存器。

用这种思路的时候，就需要我们在编写子程序的时候，考虑到谁将会调用它。如果外边调用它的时候已经用了某些寄存器，子程序里面我就不要去用。

其实这个也是相当麻烦的。子程序应该是相对独立的，我现在正在编子程序，还得考虑别的程序在调用的时候可能会用到什么寄存器，这是越想越糟糕的一个事情。在编写子程序的时候，往往无法知道、也不必知道将来的调用情况。我编好的子程序是一个非常独立的东西，我希望编好以后，将来可以在任何地方都能够调用。

所以在这里边，这两种可能的方案基本上都被否定了。

### [09:47] 标准解决方案：栈保护现场

现在提出我们希望的方案是什么呢？
- 在编写调用子程序的程序时（主调程序），**不必关心子程序到底使用了哪些寄存器**；
- 编写子程序的时候，**不必关心调用者使用了哪些寄存器**。

这两者是无关的，并且我们希望它还不会发生寄存器的冲突。

有这样的好事吗？成熟的技术是有的。将来子程序的标准框架将是这样的：
1. **子程序入口处**：把子程序当中使用的寄存器依次入栈（`push`）。在接下来的子程序内容当中看到用哪些寄存器了，把这些寄存器挨个入栈保存就行了。
2. **子程序返回前**：把子程序使用过的寄存器（入栈的寄存器）以相反顺序依次出栈（`pop`）。

通过前边这段操作，把调用者可能使用的寄存器的值进行了保存；在返回之前，再把现场恢复，这不就平安无事了吗？

这就是我们寄存器冲突问题的解决方案。可行的解决方案是：**在子程序的开始，将要用到的所有寄存器的内容都保存到栈中；在子程序返回之前再恢复。** 这个技术非常非常重要。

### [11:11] 完整代码实现与运行过程详解

有了这个以后，我们就看这样一个子程序标准框架用在当前问题的解决当中：

```assembly
datasg segment
    db 'word', 0
    db 'unix', 0
    db 'wind', 0
    db 'good', 0
datasg ends

codesg segment
start:
    mov ax, datasg
    mov ds, ax
    mov bx, 0

    mov cx, 4
s:  mov si, bx
    call capital
    add bx, 5
    loop s

    mov ax, 4c00h
    int 21h

; 子程序 capital（采用寄存器保护的标准框架）
capital:
    push cx         ; 保护现场：依次入栈
    push si

change:
    mov cl, [si]
    mov ch, 0
    jcxz ok
    and byte ptr [si], 11011111b
    inc si
    jmp short change

ok:
    pop si          ; 恢复现场：逆序出栈
    pop cx
    ret

codesg ends
end start
```

由于观察到子程序下边这些地方要用到 `si`、要用到 `cx`，所以在一开始的时候把子程序里面需要用到的寄存器入栈：`push cx`，`push si`。

入栈以后开始去用，这一段就是去做它的大小写转换。如果读到的 `cx` 值为 0，它要退回到 `ok`。到这儿的时候，原先我们是直接 `ret` 的，现在不要忘了，在退出之前按照压栈相反的顺序：
```assembly
pop si
pop cx
ret
```
去把它返回。

当返回到外层主程序的位置之后，`cx` 和 `si` 还保持着当初在调用时候的值：
1. 当外层 `cx` 原先是 4 的时候，我们调用了一次 `capital`；
2. 在子程序退出循环时 `cx` 虽然已经变成了 0，但到了出栈恢复后，出来时 `cx` 仍然恢复成 4；
3. 执行到 `loop s` 时，`cx` 减 1 变成 3，条件满足并跳转回来；
4. 回来以后再次调用 `capital`，`cx` 仍然会被压栈保护。在它出来的时候，不管中间是不是变了，出来时又会恢复成 3。

依此类推，寄存器冲突的问题就彻底解决了。

### [13:18] 总结

在这段内容中，可能看到的问题比较麻烦一些，其实结论是非常简单的：

我们将来编写子程序的时候，就按照这样一个标准的框架，使子程序使用到的寄存器在开始时入栈、在结束前出栈恢复现场，不让它造成冲突就可以了。
