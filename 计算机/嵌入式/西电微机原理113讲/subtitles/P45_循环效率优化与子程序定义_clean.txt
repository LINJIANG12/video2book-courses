### [00:10] 循环程序效率分析与最坏情况

从头看下来，程序是没有问题。但是会出现这样的情况：假如说最坏的情况，一开始 `BX` 全为 0，有无这种可能？有。

如果是这种最坏的情况，CPU 执行这个程序在这儿是不是循环了 16 遍？花了这么多的时间，到最后得到的结果是 0，程序效率很低。

还有一种情况，它可能是 $0000\ 0000\ 0000\ 0010_{(2)}$，循环第一遍得到的结果是 0，循环第二遍得到的结果是 1，后面全都是 0 了。那后面实际上这 14 遍循环是不是没统计出来结果？程序效率都很低。

### [01:10] 循环结构优化：先判定后循环

为了提高程序的效率，我们不妨把结构变一下。变成这么一种方法：

```assembly
        MOV CX, 16      ; 循环次数给 CX
        MOV AX, 0       ; 清零，放统计结果
L2:     CMP BX, 0       ; BX 的值和 0 比较一下，先判定
        JE  EXIT        ; 如果结果为 0（相等），提前退出循环
        SHR BX, 1       ; 把 BX 的值向右移一次
        JNC L1          ; 没进位跳到 L1
        INC AX          ; 有进位，AX 增 1
L1:     LOOP L2         ; CX 减 1，不为 0 则继续循环
EXIT:   MOV AH, 4CH
        INT 21H         ; 程序结束
```

把循环次数给 `CX` 以后，通过 `CMP BX, 0` 将 `BX` 的值和 0 比较一下，先进行判定。如果结果为 0、结果相等，跳到 `EXIT` 退出。跳到这儿如果是程序结束，执行中断 `INT 21H`。

否则，通过 `SHR` 把 `BX` 的值向右移一次。如果没进位（`JNC`），跳到 `L1`；有进位，执行 `INC AX` 增 1。在 `L1` 处执行 `LOOP` 指令让 `CX` 减 1，没减到 0 就跳到 `L2`。

移位后每次高位都会补入 0，移位后的 `BX` 再和 0 比较，如果结果为 0 则提前退出循环，提高了程序效率。

### [02:57] 两种循环结构的对比与设计原则

这种结构显然是**先判定、后循环工作**的一种结构；而前面讲的结构是**先循环工作、后判定**的一种结构，两种结构是不一样的。

在实际的循环程序设计当中，首先要进行分析：你设计的循环程序完成的功能，会不会出现零次循环（一开始就是零次循环）或者提前退出循环的可能？
- 如果有这种可能，为了提高程序的效率，要采用**先判定、后循环工作**的结构；
- 如果没有那种可能，采用的是**先循环工作、后判定**的结构。

但不管哪一种循环结构，循环程序的几大组成部分都在：初始化、循环工作、参数修改以及循环判定。本题的出口判定是由两部分决定的，主要还是在比较指令的判定上。

### [06:12] 一、子程序的概念

了解 8086 汇编语言当中的子程序概念，首先可以类比之前学过的 C 语言当中的函数。

在程序设计当中，程序中经常要完成某一个特定功能。如果每次要完成该功能都去编写一段程序，代码就会重复冗余。为了提高程序的结构化程度，把程序中经常要完成某一特定功能的那段程序定义成一个函数（在 C 语言中）。当程序中需要完成该功能时，直接调用函数即可。

8086 汇编语言同样如此，把程序中经常出现的、完成某一个特定功能的那段程序事先定义成一个子程序。当程序中需要实现该功能时，通过**子程序调用指令**去调用子程序。

在 8086 汇编语言当中，子程序也称为**过程（Procedure）**。定义一个子程序也就是定义一个过程；子程序调用也就是过程调用。

---

### [08:21] 二、子程序的定义

一个子程序或过程如何定义？前面讲过逻辑段的定义是由 `SEGMENT` 伪指令开始、到 `ENDS` 伪指令结束。而过程的定义同样是用伪指令定义的，伪指令助记符是 `PROC`（即英文 Procedure 的缩写，表示过程定义）。

过程定义的基本格式如下：

```assembly
过程名   PROC   [NEAR/FAR]
        ...
        RET
过程名   ENDP
```

- 在 `PROC` 的左边要写上**子程序名（过程名）**。
- 子程序命名遵循的规则与之前学过的标号名、变量名、段名完全一致：**第一个字符必须是字母**。起名时要尽量赋予含义，例如子程序的功能是将结果显示在屏幕上，名字就可以起为 `DISPLAY`，便于程序的阅读和理解。
- 在 `PROC` 伪指令的右边有一个可选参数，用于指定**属性类型**……

### 一、过程类型（NEAR 与 FAR）

关于过程的类型，主要有两种：

1. **段内子程序（NEAR 型）**  
   如果你用 `PROC` 定义的子程序和你 `CALL` 指令所在的那段程序在同一个代码段，这就叫**段内子程序**。段内子程序的类型是 `NEAR` 型（N-E-A-R）。如果是 `NEAR` 型，类型可以缺省（省略不写）。

2. **段间子程序（FAR 型）**  
   如果 `CALL` 指令要调用的子程序和 `CALL` 指令不在同一个代码段，这就叫**段间调用**。该子程序就是**段间子程序**，也就是远程子程序，它的类型是 `FAR` 型。如果是 `FAR` 型，类型不能缺省，必须显式写上 `FAR`。  
   `FAR` 型子程序肯定是用 `SEGMENT` 开始定义一个新的代码段，在这个新的代码段里面去定义子程序。

[01:25]
### 二、过程体与返回指令（RET 与 RETF）

在 `PROC` 伪指令的下方，需要使用具体的指令语句编写程序。能完成某一特定功能的指令语句段，就叫做**子程序体**，或者叫**过程体**。

完成特定功能的过程体编写完毕后，应该写出 `RET` 指令。这是一条指令语句，即子程序返回指令。CPU 执行 `RET` 指令后，就能返回到刚才 `CALL` 调用指令下方紧邻的那一条指令的地址处。

- **段内子程序返回**：直接使用 `RET`。
- **段间（FAR 型）子程序调用与返回**：  
  调用时通常对应远程调用指令：
  ```assembly
  CALL FAR PTR 子程序名
  ```
  其返回指令严格来说应该是 `RETF`。

**说明**：在实际编写中，`RETF` 也可以直接写成 `RET`。原因在于汇编程序在进行汇编时是从上到下逐行翻译的。当汇编程序扫描到 `PROC` 时，便得知一个过程定义开始；而 `PROC` 后面已经指定了类型属性，如果定义为 `FAR` 型，汇编程序就已经记录该过程为 `FAR` 类型。因此，汇编程序在汇编该过程内部的 `RET` 指令时，会自动将其翻译成 `RETF` 对应的机器码。所以 `RETF` 可以直接写成 `RET`。

---

[03:29]
### 三、过程结束伪指令（ENDP）

过程编写完毕后，要使用 `ENDP` 伪指令告诉汇编程序该子程序定义结束。为了指明具体是哪一个子程序结束，在 `ENDP` 的左侧必须写出子程序名。并且，`ENDP` 左侧的子程序名必须与 `PROC` 左侧的子程序名完全保持一致。

---

[04:06]
### 四、子程序定义的要素与属性

子程序定义需要掌握以下三点：

1. **名称一致性**：`PROC` 与 `ENDP` 左边的过程名（即子程序名）必须完全一致。
2. **成对使用**：在实际应用中，`PROC` 与 `ENDP` 必须成对出现，这与段定义（`SEGMENT` / `ENDS`）的规则相同。
3. **过程名的三要素属性**：  
   子程序名一旦通过 `PROC` 完成定义，就具备了与标号相同的三个属性：
   - **段地址属性（SEG）**：过程所在的段基地址。
   - **偏移地址属性（OFFSET，即段内有效地址 EA）**：过程名所具有的段地址和偏移地址，就是该过程中**第一条指令的地址**。简而言之，过程名等价于过程中第一条指令的标号。
   - **类型属性（TYPE）**：即 `NEAR`（近）或 `FAR`（远）。

[06:25]
### 五、主程序与子程序的关系

在实际应用中，我们将程序中反复出现、完成特定功能的那段程序定义为子程序。
- 包含 `CALL` 指令所在的那段程序称为**主程序**（或主调程序）；
- 被调用的子程序称为**被调用程序**。

在实际的工程应用中，**即使完成某一特定功能的一段程序在整个程序中只使用了一次，也尽量将其定义为独立的子程序。**  
这样设计的程序结构是模块化的：各个子程序分别负责独立的功能，整个系统的核心逻辑由子程序模块搭建组合而成。主程序在完成初始化之后，主体部分基本都是连续的 `CALL` 指令，调用下方各个具体的子程序模块。

[07:56]
### 六、程序模块化的优势：便于维护与升级

采用子程序模块化设计带来的核心优势是：**便于程序的维护与升级**。

**实际场景示例**：  
为你给某单位开发的软件系统交付使用一段时间后，对方反馈程序运行稳定，但随着生产需求变化，提出需要新增某项功能：
- **非模块化设计的弊端**：如果原程序未采用子程序模块化，新增功能就需要通读原来冗长复杂的程序段，强行在代码中间插入新逻辑。这不仅编写困难，更致命的是在重新调试时容易出错，往往新功能没调通，反而破坏了原有的老功能。
- **模块化设计的优势**：若前期严格采用子程序模块化，新增功能只需在下方独立设计编写一个新的子程序，并在主程序流程中添加一行对应的 `CALL` 指令即可。新老模块互不干扰，极大提升了程序的可升级性与可维护性。

因此，在实际工程设计中，提倡大家贯彻**程序模块化**的思想。

### 七、模块化的代价：时间开销权衡

程序模块化虽然提升了代码的可读性与工程维护性，但也存在一定的代价——**会额外消耗执行时间**。  
每次调用一个子程序模块，CPU 都必须执行一条 `CALL` 指令（涉及现场保护与地址压栈等操作），执行 `CALL` 需要占用时钟周期；子程序执行完毕返回时，又必须执行 `RET` 指令（涉及出栈返回操作），同样需要消耗时间。这就是以适量的时间开销换取结构清晰度与可维护性。但在整体系统分析中……
