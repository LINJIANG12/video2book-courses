# Redis 持久化与主从复制

## AOF 持久化

### AOF 文件的本质

   * **AOF（Append-Only File，追加文件）**

       * > **定义**：Redis 把接收到的所有写操作命令直接记到一个文件里，该文件就是一份按时间顺序追加的写命令日志。

       * 之所以叫「追加」，是因为它不像 RDB 每次把整个内存从头重写一遍，而是不停往文件末尾追加新命令，文件逐渐累加。

       * 恢复逻辑：读取 AOF 文件，把里面的命令从头开始一条条再执行一遍，数据就回到原来的状态 —— 这就是 AOF 做持久化与恢复的全部原理。

       * 文件里记的是命令本身，不是最终的数据值。

   * **AOF 文件格式**

       * 每条命令按协议格式落盘，行首的数字用于记录长度：`*3` 表示后面跟着 3 个参数，`$3` 表示该参数包含 3 个字符。

       * 执行 `set number 123` 后，AOF 中的记录形如：`*3` / `$3` / `set` / `$6` / `number` / `$3` / `123` —— "set" 长度为 3 写 `$3`，"number" 长度为 6 写 `$6`。

       * 每次新的写命令都会被继续追加到文件末尾，不会覆盖前面的内容。

### 三种刷盘策略

   * **`appendfsync` 刷盘策略**

       * > **定义**：决定 Redis 什么时候把命令写到磁盘的配置项，共三种取值。

       * `always`：主进程接到命令后先操作内存、再立即写 AOF 文件，两个动作一起完成才返回给用户；内存与磁盘同步进行，数据安全性得到绝对保障，性能最差。

       * `everysec`：主进程处理完内存后把命令写入 AOF 缓冲区即返回；每隔一秒把缓冲区中的数据一股脑写入 AOF 文件。若这一秒间隔中间宕机，最多丢失一秒钟内的所有操作。

       * `no`：主进程只把命令写进 AOF 缓冲区，刷盘交给操作系统定期完成，频率往往很低；性能最好，安全性最差。

       * 默认值为 `everysec`。

       * > **易错点**：`no` 策略下操作系统刷盘频率很低，性能虽最好但安全性最差，长文指出「与其用这个模式，还不如用 RDB」，因此这种方案基本没有实用价值。

       * 取舍关系：可靠性与性能不可兼得，必须在两者之间做出抉择。

   * 三种策略的写盘路径对比：

       ```text
       appendfsync always
           主进程:  改内存 ──► 立即写磁盘 ──► 返回用户
                               (每个命令都等)

       appendfsync everysec
           主进程:  改内存 ──► 写入 AOF 缓冲区 ──► 返回用户
                                                 │
                               每 1 秒 ──────────┘
                               缓冲区 ──► 磁盘

       appendfsync no
           主进程:  改内存 ──► 写入 AOF 缓冲区 ──► 返回用户
                                                 │
                               由操作系统决定何时刷盘(频率很低)
       ```

   * **AOF 的开启与验证**

       * AOF 默认是关闭的，需手动开启：`appendonly` 默认值 `no`，改成 `yes` 即开启。

       * 文件名由 `appendfilename` 指定，默认 `appendonly.aof`。

       * 演示 AOF 时需先禁用 RDB：把已有的 `save` 配置注释掉，再加一行 `save ""`。

       * 开启后执行写命令，目录里会生成 AOF 文件；重启 Redis 时日志出现 `DB loaded from append only file`，表示数据从 AOF 文件加载。

       * 停止 Redis 的那一刻会有一次 AOF 数据的再次检查。

## AOF 重写

### 为什么必须重写

   * **命令冗余问题**

       * AOF 只认命令不认结果：对同一个 key 操作 n 次，文件就记录 n 次，例如 `set number 123`、`set name 杰克`、`set number 666` 三条都会被完整记录。

       * 故障恢复时先执行 `number 123` 再执行 `number 666`，前一条没有意义；若最后又来一个 `DEL`，之前所有操作全部失去意义。

       * > **易错点**：RDB 记录的是 key 当前的值（如 `number` 是 666 就只记这一个值），AOF 记录的是一个 key 的多次操作，所以 AOF 文件一定会比 RDB 文件大很多。这是二者在文件体积上的根本区别。

### BGREWRITEAOF

   * **`BGREWRITEAOF`（AOF 重写命令）**

       * > **定义**：对 AOF 文件做重写，尽可能用最少的命令达到相同的效果，从而大幅减小文件体积。

       * 重写方式：抛弃对同一 key 的无意义中间命令，并把多条同类命令合并，例如把 `set name 杰克` 与 `set number 666` 合并成一条 `MSET name 杰克 number 666`。

       * 执行时返回 `Background append only file rewriting`，说明重写在后台异步执行，由独立进程完成。

       * 重写后的文件做了编码/压缩处理，直接用文本编辑器查看会难以辨认，但仍能看到具体的 key 与 value。

       * > **注意**：即便重写过，AOF 文件依然会比 RDB 大。

### 自动触发重写的阈值

   * **两个自动重写配置项**

       * `auto-aof-rewrite-min-size`：监控文件大小，AOF 文件超过 64 MB 自然触发重写。

       * `auto-aof-rewrite-percentage`：监控文件体积变化，相比上一次体积增加了 100%（翻一倍，如 10 MB 变 20 MB）即满足条件并触发重写。

       * 这两项都有默认值，通常无需改动，除非对文件大小有自己的控制要求。

## RDB 与 AOF 的取舍

### 逐维度对照

   * **两种持久化方案对比**

       * 持久化方式：RDB 对整个内存做快照，内存长什么样就写什么样；AOF 只记录命令，每执行一个命令就记一个。

       * 文件体积：RDB 比较小，还可以做文件压缩；AOF 比较大，命令数远远多于数据数。

       * 数据完整性：RDB 不完整，两次备份之间的间隔默认一般超过 60 秒，这 60 秒内出故障就会丢失；AOF 相对完整，默认每秒刷盘一次，最多丢失一秒钟数据。

       * 宕机恢复速度：RDB 较快，存的就是数据，直接加载进内存即可；AOF 较慢，存的是命令，启动后要把所有命令从头到尾执行一遍。

       * 恢复优先级：与 AOF 同时存在时 RDB 让位，AOF 优先被加载用于恢复。

       * 系统资源占用：RDB 占用较多，极限情况下内存要翻倍，fork 过程对 CPU 消耗也大；AOF 相对较少，主要是磁盘 IO 多，但因是异步的，性能受影响有限。

   * **两个概念**

       * 宕机恢复：Redis 挂掉重启后，读取持久化文件来恢复数据的过程。

       * 恢复优先级：同时启用 RDB 与 AOF、两个文件都存在时，Redis 启动以谁为准 —— 以 AOF 优先，原因是 AOF 数据更完整。

### 两者结合使用

   * **RDB 的备份定位**

       * RDB 充当备份角色：把数据备份到磁盘后，还可以拷贝到其他机器、其他机房，形成异地容灾。

       * 若整个机房损毁，只留在本地的 AOF 就废了，而拷贝到别处的 RDB 仍可恢复，因此它起到更强大的故障恢复作用。

       * > **结论**：实际使用时往往把 RDB 与 AOF 结合使用，而不是单独用其中一种；Redis 后续版本有计划把两者合二为一。

   * **按场景选择**

       * 不追求极致数据安全、能容忍数分钟数据丢失的场景，用 RDB 较好，因为速度比较快。

       * 追求数据极致安全的场景，更推荐用 AOF，或者两者结合使用。

## 主从集群与读写分离

### 为什么需要主从

   * **主从集群（master / slave / replica）**

       * > **定义**：由一个主节点 master 与多个从节点组成的 Redis 集群形态；从节点在 Redis 5.0 以前叫 `slave`，之后改叫 `replica`，两者是同一个东西。

       * 动因：单点的 Redis 并发能力有上限，高并发场景下单机无法满足需求，必须形成集群。

       * 之所以做成主从而非传统负载均衡集群，是因为 Redis 应用大多是读多写少的场景，主要压力来自读。

       * 读写分离：写操作访问 master 节点，读操作被分发到各个 slave / replica 节点，一主多从共同承担读请求，读并发能力得到极大提升。

       * > **易错点**：主从集群必须保证客户端访问任何节点都拿到相同结果，因此 master 必须把自己的数据同步给每一个 slave 节点。

### 部署拓扑

   * **一主两从**

       * 最基本的架构也需要三台节点；资源有限时可在一台虚拟机上开启三个 Redis 实例模拟，IP 相同、端口不同 —— 7001 为 master，7002、7003 为 slave。

       * 真实环境下三台机器 IP 不同，端口都可以用 6379。

       * 拓扑示意：

           ```text
                           写请求
                             |
                             v
                   +-----------------------+
                   |    master : 7001      |
                   |  (repl_backlog 在此)  |
                   +-----------------------+
                       /             \
                      v               v
              +--------------+   +--------------+
              | slave : 7002 |   | slave : 7003 |
              +--------------+   +--------------+
                   只读             只读
                    ^               ^
                    +-------+-------+
                            |
                   客户端把读请求分散到两个从节点
           ```

       * 图解：写请求全部打到 7001，读请求在应用层被分发到 7002 和 7003；两个从节点的数据全部由主节点同步而来，天然只读。

### 三个实例的准备

   * **目录与配置**

       * 每台实例需要独立的配置文件与目录，互不干扰；目录以端口命名便于查找：`mkdir -p /tmp/7001 /tmp/7002 /tmp/7003`。

       * 搭建主从时把 `redis.conf` 恢复为「开启 RDB、关闭 AOF」：把 `appendonly` 从 `yes` 改回 `no`，并把 `save ""` 注释掉使 RDB 重新开启。

       * > **提示**：之所以开启 RDB、关闭 AOF，是因为主从全量同步依赖 master 执行 `BGSAVE` 生成 RDB 文件来传输数据。

       * 把 `redis.conf` 分别拷贝到三个目录后，需要把默认端口 6379 改成各自的 7001/7002/7003，并把数据目录 `dir` 从当前目录改成各自的 `/tmp/7001` 之类。

       * 批量替换可用 `sed`：`s` 表示替换、`g` 表示全局，如 `sed -i 's/6379/7001/g; s/^dir .*/dir \/tmp\/7001/' /tmp/7001/redis.conf`；三条 `sed` 也可用 `seq` 生成端口序列配合占位符一条命令批量完成。

   * **`replica-announce-ip`**

       * > **定义**：在配置文件中显式声明本实例对外公布的 IP 地址。

       * 必要性：一台虚拟机往往有多个 IP，若让实例自己去读取，可能读到不一样的 IP 导致集群互通出问题。

       * 写法是在第一行后追加一行：`sed -i "1a replica-announce-ip 192.168.150.101" /tmp/7001/redis.conf`，同样可用 `seq` 配合占位符批量完成。

### 建立主从关系

   * **`REPLICAOF` / `SLAVEOF`**

       * > **定义**：指定当前节点成为谁的从节点，后面跟 master 的 IP 与端口；5.0 以前用 `SLAVEOF`，之后用 `REPLICAOF`，两者等价。

       * 永久方式：在 `redis.conf` 中写 `replicaof <master-ip> <master-port>`，重启后依然生效。

       * 临时方式：用 `redis-cli -p` 连到某台 Redis 上执行同样的 `replicaof` 命令，重启失效。

       * > **易错点**：命令要在「想成为 slave 的那个节点」上执行，而不是在主节点上执行 —— 若想让 B 成为 A 的 slave，就在 B 上执行 `replicaof A的IP A的端口`。

       * 启动实例：开三个 shell 窗口分别执行 `redis-server /tmp/7001/redis.conf` 等，便于同时观察三份日志。

       * 三个实例刚启动时彼此独立，还没有主从关系，必须显式执行上述命令才建立联系。

   * **验证同步结果**

       * `INFO replication` 可查看集群状态：在 7001 上执行会显示角色为 `master`，并列出 7002、7003 两个 slave，状态为 online。

       * 在 7001 上写入后，到 7002、7003 上都能读到相同的值，说明数据同步完成。

       * 从节点上执行写操作会失败，返回 `(error) YOU can't write against a read only replica.`，即副本只读。

       * > **结论**：主节点写、从节点读，天然实现了读写分离。

## 全量同步

### 三个阶段

   * **第一阶段：判断是否第一次**

       * `replicaof` 建立连接后，slave 向 master 发起数据同步请求，并带上自己的 replid 与 offset。

       * master 判断 slave 是不是第一次来：是第一次就把全量数据发过去，不是第一次就「你缺多少给多少」。

       * 在真正发数据之前，master 先把自己的 replid 与 offset 发给 slave，slave 保存下来，作为将来基于数据版本做控制的依据。

       * 第一阶段本质是完成一次初步沟通：确定要不要走全量。

   * **第二阶段：传 RDB 快照**

       * master 执行 `BGSAVE`，由后台独立进程生成 RDB 文件，主进程不受影响、继续处理用户请求。

       * RDB 文件记录了完整的内存信息，生成后发送给从节点；slave 先清空本地数据（`Flushing old data`），再把 RDB 加载进内存（`Loading DB in memory from disk`）。

       * 此阶段结束后 slave 与 master 只是「基本一致」而非完全一致：因为 `BGSAVE` 异步执行期间主进程仍在写入新数据，这些新数据没有进入 RDB。

       * 为补上这段差异，master 主进程会把 RDB 期间收到的新命令记录到名为 `repl_backlog` 的内存缓冲区中。

   * **第三阶段：补发 backlog 命令**

       * master 把 `repl_backlog` 中记录的命令发送给 slave，slave 逐条执行，数据达到完全一致。

       * 此后新命令继续写入 backlog，再由独立进程持续发送给 slave，master 接到一个发一个，两者保持永久一致。

       * 之所以叫「全量同步」，是因为存在生成 RDB 快照并整体发送的过程。

       * > **易错点**：全量同步比较消耗性能 —— 生成 RDB 要把内存数据全量拷贝一遍、写成文件再发过去，速度较慢，因此只在第一次建立连接时才会做。

### replication ID 与 offset

   * **replication ID（replid）**

       * > **定义**：数据集的标记 ID，一致即说明属于同一数据集。

       * 每一个 master 都有自己唯一的 replid，slave 会继承 master 的 replid —— 第一次同步时 master 把自己的 ID 给 slave，此后两者 ID 相同，表示属于同一数据集。

   * **offset（偏移量）**

       * > **定义**：记录在 `repl_backlog` 中的进度位置，随 backlog 中数据量增多而不断增大。

       * slave 每完成一次命令同步也会记录自己的 offset；master 侧 offset 随日志内容增多而变大，slave 侧随同步进度变大。

       * slave 的 offset 一定小于等于 master 的 offset，因为数据是从 master 拷贝过来的：相等表示两者数据完全一样，小于表示 slave 落后于 master、需要更新。

       * 两者合起来标记了「拷贝的是哪一个 master 的数据」以及「拷贝了多少、进度如何」。

   * **slave 同步时必须声明的两个值**

       * 声明 replid：master 据此判断同步是不是从自己这里走的，ID 不一样说明不是从自己这同步的。

       * 声明 offset：master 据此判断进度，相等说明进度一样，不等说明落后需要补数据。

   * **判断「是否第一次」只能看 replid**

       * 不能只看 offset 是否为零：若 slave 的 offset 很大但 ID 与 master 不同，说明它是从别的 master 拷贝的，那个 offset 在本 master 这里毫无意义。

       * > **结论**：判断 slave 是不是第一次来，不能基于 offset，只能基于 ID —— ID 不一样就证明是第一次。

       * 每个 slave 在成为 slave 之前自己也是 master，因此一定会有自己的 replid，第一次与 master 比较时必然不一致。

   * **日志中的体现**

       * slave 侧先尝试 `Trying partial resynchronization`（尝试做局部/增量同步），并带上自己的 replid 与 offset。

       * master 侧若 ID 不匹配则返回 `Partial resynchronization not accepted`，即增量被拒，转而执行全量同步。

       * 随后 master 做 `BGSAVE`、生成并保存 RDB、发送给 slave，slave 侧出现 `Flushing old data` 与 `Loading DB in memory from disk`；后续 backlog 命令的持续发送在日志中不再体现。

## 增量同步

### 触发与判定

   * **增量同步（partial resynchronization）**

       * > **定义**：slave 重启后，只补上它落后于 master 的那一段命令，而不是重新拷贝一份完整 RDB 的同步方式。

       * 典型场景就是从节点重启：不管因故障挂掉还是主动重启，停机期间 master 仍在接收数据，slave 醒来后数据落后，必须补差。

       * 流程：slave 重启后发送 `PSYNC <replid> <offset>`，master 判断带来的 replid 与自己保存的是否一致。

       * replid 不一致（master 手里 replid 为空或对不上）→ 回复 `+FULLRESYNC`，生成 RDB 发给 slave，走全量同步。

       * replid 一致 → 回复 `+CONTINUE`，只发 offset 之后那一段命令，走增量同步。

       * > **提示**：`+CONTINUE` 这一个单词就是增量同步的开关。

       * 判定与走向：

           ```text
              slave 重启
                 │
                 ├─ 向 master 发送 PSYNC <replid> <offset>
                 │
                 ├─ master 判断 replid 与自己保存的是否一致
                 │      ├─ 不一致 ──▶ +FULLRESYNC ──▶ 生成 RDB 发给 slave ──▶ 全量同步
                 │      └─ 一致   ──▶ +CONTINUE    ──▶ 只发 offset 之后那段 ──▶ 增量同步
                 │
                 └─ slave 执行补上的命令 ──▶ 追平 master ──▶ 数据再次一致
           ```

       * 增量同步不是把 backlog 全部内容都发过去，而是从 slave 带来的 offset 位置往后精确截取 —— 这一段才是它挂掉之后产生的数据。

### replication backlog

   * **replication backlog（复制积压缓冲区）**

       * > **定义**：大小固定的数组，本质是 slave 与 master 之间数据差异的缓冲区。

       * 特殊性在于写满后不扩容，而是从 0 重新开始记录、覆盖原有数据，因此可以理解成环形记录方式。

       * 环里跑着两个位置：master 不停写入新命令，最新写入的位置就是 master 的 offset；slave 不断同步，同步到的位置就是 slave 的 offset。

       * 结构示意：

           ```text
              replication backlog（定长环形数组，写满后从 0 重新写）

              ┌──────────────────────────┬───────────────────────┐
              │  已同步（绿色）           │  未同步（红色）         │ ← master offset
              │  覆盖了无所谓             │  覆盖了就只能全量同步   │   （最新写入位置）
              └──────────────────────────┴───────────────────────┘
                               ↑
                        slave 的 offset
           ```

       * 红色那段就是 slave 与 master 的数据差异，即 slave 宕机期间错过的那些数据。

       * offset 会越涨越大但没有关系：只要 slave 一直在同步、跟得上进度，环里真正需要保留的就只有红色一段；绿色部分已被同步过，被覆盖无所谓。

       * > **结论**：只要 slave 与 master 的差距没有超过这个环的存储上限，就永远能从环里找到自己需要的数据，永远能做增量同步。

### 退化成全量同步的条件

   * **超过环的上限**

       * slave 宕机期间 master 继续写入，欠的数据越来越多，逐渐把整个数组撑满；master 不管这些，继续记录并会连红色那段尚未备份的数据一起覆盖。

       * 结果是 slave 的 offset 在环里消失、找不到了，它欠的数据在环中已无备份，只能去 master 的内存里找 —— 这就只能做全量同步。

       * > **结论**：replication backlog 有上限，写满了会覆盖旧数据。若 slave 断开太久，久到它尚未同步的那部分数据也被覆盖（欠的数据超过一圈），从 backlog 里就拿不到完整数据，只能全量同步。

       * > **易错点**：不是「断得久就一定全量同步」，而是「欠的数据超了一圈」才一定全量同步；断开时间只是衡量差距的直观尺度。

       * 这个问题没有办法彻底避免，只能尽可能减小发生的概率。

### 全量同步与增量同步对照

| 对比项 | 全量同步 | 增量同步 |
| :--- | :--- | :--- |
| 触发场景 | 第一次连接；slave 宕机太久 offset 被覆盖 | slave 故障恢复，且 backlog 里还能找到它的 offset |
| 是否生成 RDB | 需要，master 把内存数据生成 RDB 发给 slave | 不需要 RDB，直接读 replication backlog |
| 传输内容 | 完整内存快照 + 后续记在 backlog 里的命令 | 只发 slave 的 offset 之后的那一段命令 |
| 代价 | 高，性能差 | 低 |

## 主从同步的优化

### 提高全量同步的性能

   * **无磁盘复制 `repl-diskless-sync`**

       * > **定义**：master 生成的 RDB 本质是个 IO 流，不把它写进磁盘 IO 流，而是直接写进网络发给 slave，从而省掉一次磁盘读写。

       * 默认值为 `no`，改成 `yes` 即可开启。

       * 常规复制要先在磁盘上写完整份数据（如 10G）再通过网络发送，磁盘读写较慢，效率就低。

       * > **提示**：该配置适用于「磁盘比较慢但网络非常快」的场景；若网络带宽本身不够，发 10G 也很慢，反而可能把网络搞阻塞，必须配合足够的网络带宽。

   * **控制单节点内存上限**

       * 把 slave 单节点的内存上限压得比较低（如控制在 10G、20G 左右，不要太高），RDB 需要传输的数据量就小，磁盘 IO 与网络 IO 都随之减少，性能得到提升。

### 减少全量同步的发生

   * **调大 replication backlog**

       * 增量同步退化成全量是因为环被写满，把 backlog 调大，主从之间允许存在的 offset 差异就越大，发生全量同步的可能性自然降低。

   * **让 slave 宕机后尽快恢复**

       * slave 挂掉后不要长时间不恢复 —— 一躺一小时肯定出问题，要尽快完成故障恢复。

   * **主从从链式结构**

       * > **定义**：让其中一个 slave 去给别的 slave 做数据同步，从而分担 master 同步压力的链式主从结构。

       * 动因：从节点非常多时全都去找 master 做同步，master 压力过大。

       * 实现：某个 slave 执行 `SLAVEOF` 时，IP 与端口指定成另一台 slave 而不是 master，即 slave C 执行 `SLAVEOF <slave A 的 ip> <slave A 的端口>`。

       * 结构示意：

           ```text
                      写 ┌──────────┐
                        ─▶│  master  │◀── 读
                         └────┬─────┘
                              │
                     ┌────────┴────────┐
                     │                 │
                ┌────▼─────┐      ┌────▼─────┐
                │ slave A  │      │ slave B  │
                └────┬─────┘      └──────────┘
                     │
                ┌────▼─────┐
                │ slave C  │
                └──────────┘
           ```

       * 改完后由 slave A 承担给 slave C 同步的职责，master 的压力一下子就轻了。

## 哨兵机制

### 为什么需要哨兵

   * **master 宕机的问题**

       * slave 宕机完全不用担心：它重启后就能从 master 上完成数据同步、恢复数据。

       * master 宕机则不同：即便做了持久化、重启后数据不丢，在宕机期间与数据恢复过程中用户无法执行写操作，集群只能读不能写，可用性下降。

       * 期望的目标是集群对外无感知、一直可用，因此需要持续监控节点状态，一旦发现 master 宕机就立即选一个 slave 作为新 master；旧 master 将来起来后当 slave 即可，这就是主动切换。

       * > **结论**：重启解决的是数据一致，解决不了可用性；真正需要的是一个能持续监控并自动完成切换的角色 —— 哨兵（Sentinel）。

       * 哨兵本身也是一个集群：它是来监控别人的，自己挂了就废了。

### 哨兵的三大作用

   * **监控**

       * 周期性监测每一个节点的状态，掌握集群的健康状态。

   * **自动故障恢复**

       * 若 master 故障，Sentinel 立即将一个 slave 提升为新的 master；故障实例恢复以后也以这个新的 master 为主。

       * slave 宕机时 Sentinel 也会立即去重启这个 slave。

       * 这些动作全部由 Sentinel 自动完成，无需人工介入。

   * **通知**

       * > **结论**：Sentinel 充当 Redis 客户端的服务发现来源。

       * 客户端做了读写分离，需要在主节点写、在从节点读；一旦发生主从切换，地址就变了，而客户端把地址写死并不知道这种变化。

       * 因此客户端找主从地址时不直接去找 Redis 节点，而是去找 Sentinel，由 Sentinel 告诉它主从地址是什么；切换发生时 Sentinel 立即把服务状态变更通知给客户端，客户端随之改变访问地址。

   * 整体结构：

       ```text
             ┌───────────────────────────────────────┐
             │      Sentinel 哨兵集群（自己也是集群）  │
             │      27001        27002        27003   │
             └────────┬────────────┬────────────┬─────┘
                      │  PING      │  PING      │  PING
             ┌────────▼────────────▼────────────▼─────┐
             │        Redis 主从集群（读写分离）         │
             │        master:7001  ──▶  7002 / 7003   │
             └───────────────────────────────────────┘
                           ▲
                           │  主从地址 / 变更通知
                    ┌──────┴────────┐
                    │ RedisTemplate │  ← Java 客户端
                    └───────────────┘
       ```

### 主观下线与客观下线

   * **心跳监测**

       * Sentinel 基于心跳机制监测状态：每隔一秒向集群中的每个实例发送 `PING`，能回 pong 就证明节点 OK。

   * **主观下线（sdown）**

       * > **定义**：单个 Sentinel 发起 PING 后超过一定时间没收到响应，就认为该实例下线 —— 本质只是「我个人认为你下线了」。

       * 超时未响应的原因很多，可能真的挂了，也可能只是网络阻塞导致结果没准时回来，因此单凭一次 ping 不到不能判它下线。

   * **客观下线（odown）**

       * > **定义**：超过指定数量（quorum）的 Sentinel 都认为该实例主观下线，该实例才被判定为客观下线 —— 客观就是事实，事实上下线了。

       * `quorum` 是可配项，一般配成 Sentinel 实例数量的一半；三个 Sentinel 时超过一半即两个，只要两台以上认为你下线，就把你剔除。

       * > **结论**：Sentinel 监测服务状态的方式说到底就是一个投票 —— 大多数人认为你挂了，你就真的挂了。

### 故障转移

   * **哨兵 Leader 选举**

       * 三台 Sentinel 之间地位平等，但最终只需要有一个 Sentinel 去做故障恢复，没必要三个都做，因此要先选出 Leader。

       * 选举机制：谁先发现宕机，谁就能选上。

   * **slave 选主的四条依据**

       * 第一条看断开时间：slave 与 master 断开的时间超过指定值（配置文件里配，不配也有默认值），说明它与 master 断开太久、丢失的数据越多，会被直接排除，不具备选举权。

       * 第二条看优先级 `replica-priority`：默认所有人都是 1，值越小优先级越高；既然默认都一样，默认情况下它不参与区分，也不用管。

       * 第三条看 offset：offset 代表当前 slave 与 master 数据同步的进度，值越大说明数据越新，因此 offset 越大优先级越高。

       * > **结论**：offset 是三条里最关键的，它才是真正衡量一个节点数据是否最新的标准；之所以 offset 排在优先级前面，是为了优先保证数据完整性。

       * 第四条看 run ID：若所有 slave 的 offset 都一样，就比较 slave 的 run ID —— run ID 是 slave 启动那一刻由 Redis 自动生成的，其大小本身不重要，只是取「谁小谁优先级高」作为兜底。

   * **转移执行的三步**

       * 第一步，Leader Sentinel 向选中的 slave 发起 `SLAVEOF NO ONE`，即「别跪了，站起来，永不为奴」，它从 slave 变成 master。

       * 第二步，Leader Sentinel 向其他所有 slave 广播 `SLAVEOF 7002`，告诉它们新主出现、从此以 7002 为主，它们会因此重新做一次全量同步。

       * 第三步，Leader Sentinel 对故障节点执行 `RECONFIG`，强制改写它的配置文件、把它标记为 `slaveof 7002` —— 配置文件一旦被改写，它只要重启就一定会认 7002 为主。

       * 三步走完，所有节点都以新 master 为主，整个主动切换完成。

### 哨兵集群的搭建

   * **实例规划**

       * 三个 Sentinel 部署在同一台机器上，IP 相同，因此需要不同端口：27001、27002、27003。

       * 同时需要三个不同目录 s1、s2、s3 存放各自的配置与运行时数据：`mkdir s1 s2 s3`。

   * **`sentinel.conf` 关键配置**

       * 该文件是自己新建的，不是从 Redis 目录拷贝过来的。

       * `port 27001`：本实例的端口。

       * `sentinel announce-ip 127.0.0.1`：声明本 Sentinel 自己的 IP，避免机器上有多个 IP 引起混乱。

       * `sentinel monitor mymaster 127.0.0.1 7001 2`：声明监控对象 —— `mymaster` 是给集群/主节点起的名字，其后是 master 地址与端口，最后的 `2` 是 quorum 值。

       * `dir s1`：本实例的工作目录。

       * > **提示**：虽然 `sentinel monitor` 只写了 master，但 Sentinel 实际监控的是整个集群 —— 因为在 master 上执行 `INFO replication` 就能拿到所有 slave 的信息。

       * `sentinel.conf` 中还有 slave 与 master 断开的最长超时时间、故障恢复的超时时间两项，不配也有默认值。

       * 写好 s1 的配置后拷贝到 s2、s3，只需分别改掉「端口」和「工作目录」，监控目标与 quorum 值必须完全一样。

   * **启动 Sentinel**

       * 分别 `cd` 到对应目录执行 `redis-server sentinel s1/sentinel.conf`，注意名字是 `redis-server sentinel`，后面指定对应目录下的 sentinel 配置文件。

       * 三个实例跑起来后，Sentinel 已开始监控整个集群：它知道自己在监控 7001、quorum 值是 2，也发现了从节点 7002 和 7003。

   * **一次完整切换的日志链**

       * 让 7001 宕机后，先是标记主观下线（日志 `+sdown`，此时只标记、没有任何动作），各台 Sentinel 陆续都认定主观下线。

       * 达到 quorum 后出现 `+odown`，即客观下线。

       * 接着出现 `+try-failover`，开始故障恢复：三台哨兵先选 Leader（谁先发现宕机谁上，如 `elected-leader: s3`），再由 Leader 在 slave 里选新 master（如 `selected-slave: 7002`）。

       * 然后对 7002 发送 `SLAVEOF NO ONE`，它从一直报连不上变成 `master mode`。

       * 接着把新主信息广播给 7003，7003 执行 `replicaof 7002` 并重新做一次全量同步。

       * 再对故障的 7001 执行 `RECONFIG`，把它标记成 slave。

       * 最后把 7001 重新启动，它会尝试同步，最终成为 7002 的 slave，整个主动切换彻底完成。

       * > **易错点**：观察切换时要同时盯 Redis 与哨兵两侧 —— Redis 侧报 7001 连不上、哨兵侧也报错，这都是正常现象，正是哨兵在发现故障。

## 客户端接入哨兵

### 三步配置

   * **引入依赖**

       * RedisTemplate 的底层依赖 Lettuce 框架实现，关于节点的感知与动态切换底层已全部实现好，只需应用即可。

       * 引入 `spring-boot-starter-data-redis`，它里面会基于 Lettuce 完成 Redis 的各种自动功能。

   * **配 Sentinel 地址**

       * 配的不是 Redis 集群地址，而是 Sentinel 的地址：Sentinel 模式下主从地址可能变更，不能写死，客户端只需知道 Sentinel 地址，将来基于 Sentinel 做服务发现。

       * 配置形如 `spring.redis.sentinel.master: mymaster`（即当初给集群起的名字），`spring.redis.sentinel.nodes` 是集合，列出 `127.0.0.1:27001`、`127.0.0.1:27002`、`127.0.0.1:27003`。

   * **配置读写分离 Bean**

       * 光配地址还不够，还需要保证读写分离：让所有写操作找 master、读操作找 slave。

       * 做法是配一个 `LettuceClientConfigurationBuilderCustomizer` 类型的 Bean，调用 `builder.readFrom(ReadFrom.REPLICA_PREFERRED)`。

       * > **提示**：该接口只有单个方法，可以直接写成 lambda；这个 Bean 可以配在任意一个配置类里。

### `ReadFrom` 的四种取值

| ReadFrom 选项 | 含义 | 适合读写分离吗 |
| :--- | :--- | :--- |
| `MASTER` | 读也从主节点读 | 否 |
| `MASTER_PREFERRED` | 优先从主节点读，主节点不可用了再去读从节点 | 否 |
| `SLAVE` / `REPLICA` | 从 slave（从）节点读取 | 是，但没有兜底 |
| `REPLICA_PREFERRED` | 优先从从节点读，从节点不可用了再去主节点读 | 是，推荐 |

   * 前两个与读写分离相差甚远，不是期望的行为；后两个符合读写分离，带 `PREFERRED` 的多了「从挂了再去主上读」的兜底，因此推荐使用 `REPLICA_PREFERRED`。

   * > **易错点**：`MASTER` 与 `MASTER_PREFERRED` 都不做读写分离；只写了 `sentinel.master: mymaster` 而没配 Lettuce 的 `readFrom`，客户端虽然连上了，但读写分离并没有生效。

### 客户端的工作过程

   * **启动阶段**

       * 第一步找 Sentinel：尝试获取 Sentinel 连接（`trying to get a sentinel connection`），从 27001、27002、27003 中挑中其中一个并连上。

       * 第二步订阅集群状态：以类似订阅的机制（`subscription command`）订阅集群状态，由 Sentinel 把集群信息推给客户端。

       * 第三步拿到拓扑：查询后得到 master 信息（名字 `mymaster`、IP、端口，如 7002）以及一个数组形式的 slave 列表（如 7003、7001）。

       * 第四步建连接：底层维护连接池，不仅连主节点，也会与集群中的每个节点都建立连接。

   * **读写分流**

       * Lettuce 里所有请求都被分成 command，执行 `get` 时 command 类型是查询，请求交给某个从节点（如 7003）处理。

       * 执行 `set` 时 command 类型是写，交给主节点（如 7002）处理。

       * 完整链路：

           ```text
              启动
               └─ 依次连 27001 / 27002 / 27003，挑中其中一个（例：27001）
                    └─ 订阅集群状态（subscription command）
                    └─ 向哨兵查询集群拓扑 → 拿到：
                          master : mymaster → 127.0.0.1:7002
                          slaves : [7003, 7001]
                    └─ 为集群里的每个节点都建连接（底层维护连接池）

              执行 GET → command 类型是 get → 交给某个从节点（7003）处理
              执行 SET → command 类型是 set → 交给 master（7002）处理
           ```

   * **亲历一次故障切换**

       * 把当前主节点（如 7002）弄宕机，哨兵发现后完成主从切换，把主切给 7001，7003 变成 slave；7002 重新启动后又去找 7001，成为它的从节点。

       * 客户端侧日志显示它重新尝试连接集群、重新获取集群信息，解析出的 master 变成 7001，从节点是 7003 与 7002 —— 客户端动态发现了节点的最新信息。

       * 之后再做查询会落到新的从节点（7002），做写操作会落到新的主节点（7001）。

       * > **结论**：主从自动切换、读写分离全部由客户端全自动实现；开发者要做的只有三步 —— 引依赖、配哨兵地址、配读写分离。
