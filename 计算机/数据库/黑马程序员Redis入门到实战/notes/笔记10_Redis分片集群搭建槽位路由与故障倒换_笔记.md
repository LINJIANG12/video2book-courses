# Redis 分片集群：搭建、槽位路由与故障倒换

## 主从集群的两道天花板

* **主从集群的上限**

    * 同步侧的坎：为提高主从同步性能，单节点内存不能设太高；内存占用一大，做 RDB 持久化、做全量同步时大量 IO 会把性能拖下来

    * 结果：单节点能存的数据被压到 10G、20G 量级，海量数据无处可放，这个问题主从集群解决不了。

    * 写入侧的坎：主从集群扛住了高并发读，但写并发高时读写一平衡仍然不够用

* **分片集群（Redis Cluster）**

    * > **定义**：用多个 master 横向拆分数据与写压力、master 之间互相监测并自动完成主从切换的集群形态

    * 定位：主从 + 哨兵解决不了「海量数据存储」和「高并发写」这两件事，都由分片集群来解

## 分片集群的四个结构特征

* 特征一：集群中有多个 master，每个 master 保存不同的数据

    * 不再是主从关系，每个 Redis 都是 master，各存一部分

    * 存储上限取决于 master 节点的数量——理论上可以应对海量数据存储

* 特征二：高并发写不再受限

    * 多个 master 每个都能写，并发写能力随之提升

    * 并发读不下降：每个 master 还能再挂多个 slave，于是同时具备主从集群的全部特性——读走 slave、写走 master

* 特征三：master 之间通过 Gossip 协议互相监测

    * 多个 master 都认为某节点主观下线，就把它标记为客观下线，随时可以做主从切换

    * 以前做主从切换需要哨兵，现在不需要：master 之间互相起到了哨兵的作用

* 特征四：客户端可以连接集群中的任意一个节点

    * 因为节点之间会自动路由，把请求送到正确的节点上去

    * 结论：不再需要哨兵机制，却具备哨兵机制的所有功能

```text
                    客户端（连任意一个节点即可）
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
            [7001]        [7002]        [7003]      master，各存不同数据
            [8001]        [8002]        [8003]      各自挂一个 slave
                └─────────────┼─────────────┘
                        Gossip 互相监测
                 （故障判定、主从切换，不再需要哨兵）
```

## 集群搭建：三主三从六个实例

### 端口规划与目录准备

* 规划：一主一从、三组三从，一共六个实例

| 端口 | 角色 |
| :--- | :--- |
| 7001、7002、7003 | master |
| 8001、8002、8003 | slave |

* 目录准备

    * 先建六个目录，目录与端口一一对应

    * > **易错点**：以前旧的目录一定要先删掉再重建，旧配置可能会产生干扰

* 配置文件

    * 集群相关配置要重新写一份，不能用原来的

### 关键配置项

```ini
# 开启集群功能，默认是关闭的
cluster-enabled yes

# 集群配置文件的存放位置
cluster-config-file nodes.conf

# 集群心跳的超时时间：互相做心跳超过 5 秒没有心跳，就认为你是疑似宕机
cluster-node-timeout 5000

dir /tmp/7001
bind 0.0.0.0

# 守护进程，默认是 no。改成 yes 之后不往控制台打印日志，持续后台运行
daemonize yes

# 声明主从实例的 ip 地址
replicaof 127.0.0.1 6379

# 保护模式，改成 no，将来就不做用户密码之类的校验
protected-mode no

# 数据库数量，默认一共 16 个，我们用不了那么多，一个就够
databases 1

# 后台运行后控制台看不到日志了，想看日志就指定日志位置
logfile /tmp/7001/redis.log
```

* `cluster-enabled`

    * 开启集群功能，默认是关闭的

* `cluster-config-file nodes.conf`

    * 只需指明存放位置，不需要自己维护

    * 该文件由集群内部自动维护，是只读的

    * 位置对应各自目录：在 7001 就是 7001，在 7002 就是 7002，将来要跟着改

* `cluster-node-timeout 5000`

    * 集群心跳超时时间，单位是毫秒

    * 判定：互相做心跳超过 5 秒没有心跳，就认为该节点疑似宕机

* `daemonize yes`

    * 改成 yes 后不往控制台打印日志，持续后台运行

    * 因为是后台启动，不再需要开六个终端窗口，可以一键启动

* `databases 1`

    * 集群下用不了 16 个库，一个就够

* `protected-mode no`

    * 关掉保护模式，将来不做用户密码之类的校验

### 一键拷贝、一键换端口、一键启动

* 一键拷贝到六个目录

```bash
cat /tmp/redis.conf | tee /tmp/{7001,7002,7003,8001,8002,8003}/redis.conf
```

* 一键把默认端口 6379 替换成各自端口

```bash
for i in 7001 7002 7003 8001 8002 8003; do
  sed -i "s/6379/$i/g" /tmp/$i/redis.conf
done
```

* 一键启动六个实例

```bash
for i in 7001 7002 7003 8001 8002 8003; do
  redis-server /tmp/$i/redis.conf
done
```

* 关闭方式：用 Redis 客户端执行 `shutdown` 命令

### 启动后的真实状态

* 用 `ps -ef | grep redis` 可以看到六个 Redis 全部启动

* 此刻六个实例**还没有联系起来**

    * 配置文件里没有指定集群中谁跟谁有联系

    * 所以每个人都是一个独立的集群，处于未互联状态

    * 真正把它们捏成一个集群，靠下一步的创建命令

## 创建集群与查看状态

### create 命令

```bash
redis-cli --cluster create --cluster-replicas 1 \
  192.168.150.101:7001 192.168.150.101:7002 192.168.150.101:7003 \
  192.168.150.101:8001 192.168.150.101:8002 192.168.150.101:8003
```

* `--cluster-replicas 1`

    * 含义是副本数量，一主一从即一个副本，所以取 1

    * 命令后面跟的是集群中所有节点的 IP 和端口

* 创建过程

    * 先给出一个计划供确认：谁做 master、谁做 slave

    * 输入 `yes` 回车后开始建集群，看到 `All nodes agree` 说明所有节点都同意，集群创建成功

* > **易错点**：⚠️ Redis 判断六个节点谁主谁从的依据是副本数——replicas 为 1 意味着主从比例 1:1 各占一半，6 ÷ 2 = 3，所以主节点占三个，**前三个是主、后三个是从**

* 集群操作命令总入口

    * `redis-cli --cluster help` 可以看到集群操作的所有命令

    * 已知命令：`create`（创建集群）、`rebalance`、`add-node`（添加节点）、`del-node`（删除节点）、`info`（查看节点状态）、`reshard`（重新分片）

    * > **提示**：命令不要死记硬背，通过帮助文档去查看和使用

### 查看集群状态

```bash
redis-cli -p 7001 cluster nodes
```

* 输出包含每个节点的角色（master / slave）与其主从对应关系

* 输出中有一列 `slots`，即每个 master 的**散列插槽**

## 散列插槽

### 槽的划分与分配

* **散列插槽（hash slot）**

    * > **定义**：Redis 把每一个 master 映射到 0 至 16383 共 16384 个插槽上，用槽来标记数据的归属

    * 数值：槽编号范围 0 ~ 16383，总数 16384

    * 分配：集群创建时把 16384 个槽分给每个节点一部分，各节点槽数相加正好 16384

| 节点 | 分配到的插槽 | 数量 |
| :--- | :--- | :--- |
| 7001 | 0 ~ 5460 | 5461 |
| 7002 | 5461 ~ 10922 | 5462 |
| 7003 | 10923 ~ 16383 | 5461 |

* 为什么要有插槽

    * 提出问题：`set number 123` 该存到哪个 master？

    * 若随便挑一个（如 7002）存进去，将来取的时候无从知道它在 7002，就找不到了。

    * 插槽就是为了解决「数据存到哪个节点、将来从哪里取」这个问题

### key 的有效部分与槽位计算

* **有效部分**

    * 判定规则一：key 里带了大括号，且大括号内部至少包含一个字符——大括号里边的内容就是有效部分

    * 判定规则二：key 里不含大括号——整个 key 就是有效部分

    * 例：`number` 无大括号，有效部分是整个 `number`；`{itcast}number` 的有效部分是 `itcast`

* 槽位计算公式

    * 先对有效部分做 **CRC16** 算法算出哈希值，再对 16384 取模

    * 任何数字对 16384 取模，结果一定落在 0 ~ 16383 之间，刚好落在插槽范围内

$$slot = CRC16(\text{有效部分}) \bmod 16384$$

* 三步流程

    * 第一步：创建集群时，把 16384 个槽分配到每个节点

    * 第二步：存取一个 key 时，根据 key 的有效部分计算哈希值，再用哈希值算出插槽值

    * 第三步：插槽值算出来，就能判断这个槽在哪个节点上，从而找到对应的数据

### 重定向

* 连接方式

```bash
redis-cli -c -p 7001
```

* > **易错点**：⚠️ 集群模式下连接参数**不仅仅要加 `-p`，一定要加 `-c`**；`-c` 代表 cluster 集群模式，务必加上

* **重定向（MOVED）**

    * > **定义**：操作的 key 经槽位计算后不属于当前连接的节点时，节点返回 `MOVED` 把请求引到正确节点

    * 现象：`(error) MOVED 15495 127.0.0.1:7003`——key `a` 算出的插槽值是 15495，落在 7003 上，于是重定向到 7003

    * 反向同理：`get number` 算得插槽 2765，落在 0~5460 区间，对应 7001，又被带回 7001

    * 边界：长文只演示了 `MOVED` 这一种重定向，未说明 `ASK`

* 结论

    * 操作任意一个 key 都会先算插槽值、再判断在哪个节点、再完成一次请求路由（重定向）

    * 这正是「访问集群中任意一个节点都没问题」的原因——每个节点都能实现这种重定向

### 数据绑定插槽而非节点

* **key 与插槽绑定**

    * 规则：Redis 中数据的 key 不是与 master 节点绑定，而是与插槽绑定

    * 原因：主节点可能宕机，也可能因集群扩容/缩容而增删；节点一旦删除或宕机，其上的数据会跟着丢

    * 解法：数据与插槽绑定后，节点宕机时可把该节点对应的插槽转移到活着的节点上；集群扩容时也可以把插槽转移出去

    * 结论：**数据跟着插槽走**，因此永远能找到数据所在的位置

## 让同一类数据落在同一个节点

* 需求与动机

    * 需求：把同一类数据固定保存在同一个实例上（如所有手机存一个节点、空调存另一个节点）

    * 动机：将来按类查询时可以在同一节点内查完，避免请求重定向——重定向要重新建立连接，性能上一定有一定损耗

* 实现思路

    * 数据落在哪个实例取决于插槽值，所以只要同一类数据算出的插槽一样，就一定会存在同一个实例上

    * 要让插槽一样，就得让这批 key 的**有效部分一样**

    * 做法：给同一类数据的 key 加上共同的大括号，例如用商品类型 id 作为有效部分

```text
{商品类型id}商品id
```

* 验证

    * 原本 `number` 在 7001 上，改成 `SET {a}number xx` 后有效部分变成 `a`

    * `a` 算出的插槽是 15495，于是 `{a}number` 跳到 7003

    * 结论：想控制某一类数据存到指定实例，可以通过控制有效部分来实现

## 集群伸缩

### add-node：新增节点

```bash
redis-cli --cluster add-node <新节点IP:端口> <集群中已存在的节点IP:端口>
```

* 两组参数

    * `new_host` / `new_port`：新节点的 IP 和端口

    * `existing_host` / `existing_port`：集群中已经存在的节点 IP 和端口

    * > **提示**：为什么加新节点还要给旧节点地址——添加一个节点必须通知集群中的每一个角色，所以得先联系上这个集群；命令通过该地址联系上集群，才能把新节点信息通知给每个节点

* 可选选项（默认都不加）

    * 不加：新增节点默认就是一个 master

    * `--cluster-slave`：新增节点一出生就是 slave

    * `--cluster-master-id`：指定 master 的 id，生下来就是指定那个 master 的 slave；每个实例都有一个 id

### 案例：新增 master 7004 并装入数据

* 难点定位

    * 加节点本身不难，难的是往新节点里存数据

    * `number` 的插槽算出来是 2765、在 7001 上；要让 `number` 存到 7004，就必须把 7001 的一部分插槽分给 7004

    * 核心是**插槽的分配问题**

* 步骤一：起一个 7004 实例

```bash
sed -i "s/6379/7004/g" /tmp/7004/redis.conf
redis-server /tmp/7004/redis.conf
```

* 步骤二：加入集群

```bash
redis-cli --cluster add-node 192.168.150.101:7004 192.168.150.101:7001
```

* 加入后的状态

    * `cluster nodes` 里能看到 7004

    * 但 7004 上**没有任何插槽**：7001 有 0~5460、7002 有、7003 也有，7004 一片空白

    * 不分配插槽的话，新增的这个节点就没有意义

### reshard：重新分片

```bash
redis-cli --cluster reshard 192.168.150.101:7001
```

* 参数：指定集群中任意一个节点的 IP 和端口即可

* 交互式问答

```text
How many slots do you want to move?            3000
Enter the node ID of the receiving node:      <7004 的 id>
Enter the node ID of the source node:         <7001 的 id>
Do you want to proceed with the proposed reshard plan? (yes/no)
```

* 各项含义

    * 移动多少插槽：本例 `number` 的槽是 2765，把 7001 上的 0~2765 移过去可以，直接移 3000 个也可以。

    * receiving（接收方）：填 7004 的 id

    * source（数据源节点）：从 7001 拷贝，填 7001 的 id

    * 输入完敲 `done` 表示结束，剩下没填的都不动

    * 最后再确认一次，回 `yes` 开始迁移，从 7001 一口气把 3000 个插槽搬到 7004

* 迁移结果

    * 再看 `cluster nodes`，7004 上现在是 0~2999，2765 必然在其中

    * 连 7001 执行 `get number` 会自动切到 7004，`set number 10` 随之成功

    * 原因：**把插槽移过去了，数据是跟着插槽走的**

* > **结论**：集群伸缩的重点就是两个命令——`add-node` 和 `reshard`

* 删除节点：`redis-cli --cluster help` 中提供 `del-node`，可自行按帮助文档实现

## 自动故障转移

* **自动故障转移**

    * > **定义**：master 掉线后，集群自动把它的 slave 提升为 master 的过程

    * 前提：分片集群没有哨兵，但依然具备故障转移能力

* 触发与状态变化（以 7002 为例）

```bash
redis-cli -p 7002 shutdown
```

```text
          redis-cli -p 7002 shutdown
                        │
                        ▼
  7002:  master  ──►  disconnected  ──►  fail（心跳监测判定失败）
                        │
                        ▼
  8003:  slave   ──►  master          （奴隶翻身做主人）
  7002:  重新启动 ──►  slave           （退成小弟）
```

* 观察要点

    * 先是 `disconnected`（失去连接），等待一会儿后变成 `fail`（彻底失败）

    * 与此同时 8003 由 slave 升为 master，7002 变成小弟

    * 把 7002 重新 `redis-server /tmp/7002/redis.conf` 启动，启动那一刻它就是 slave

    * 结论：整个过程不需要哨兵，Redis 集群自动完成主从切换

* 三步机制

    * 第一步：某一个主节点失去连接

    * 第二步：其他节点对它做心跳监测，发现失去连接后把它标记成 fail 状态

    * 第三步：标记为 fail 后选出新的主——因为每个主只有一个从，直接找出来即可，不需要复杂的选举

## 手动故障转移

* **手动故障转移**

    * > **定义**：在目标 slave 上执行 `CLUSTER FAILOVER`，主动让该 slave 替换其 master 的过程

    * 用途：集群里某台 master 机器老旧或需要维护时，先起一个性能更好的新节点成为它的 slave，再手动让新节点替换旧 master，实现一台机器的**无感知升级**

    * 与自动转移的区别：自动转移是被动的，宕机了才去选新主；手动转移是有目的性的迁移，用于服务升级或数据迁移

* 执行位置：必须在**那个新的 slave 节点上**执行 `CLUSTER FAILOVER`，替换的是它所对应的 master

### 默认流程五步

```text
  在 slave(8001) 上执行 CLUSTER FAILOVER
                  │
                  ▼
  ① slave 向 master 发消息："我要替换你了"
                  │
                  ▼
  ② master 拒绝客户端的一切请求
     （"我要下岗了"，凡是进来的请求全部阻塞，避免消息丢失）
                  │
                  ▼
  ③ master 把当前的 offset 返回给 slave
     （"我的数据已经最新到这个位置了，你看看跟我一不一样"）
                  │
                  ▼
  ④ slave 与 master 之间检查 offset 是否一致
     不一致就赶紧同步，直到完全一致
                  │
                  ▼
  ⑤ 完成转移：slave 变 master，master 变 slave
                  │
                  ▼
  新 master 向集群中每个节点发广播："我是新 master"
  原来的 master 收到消息，知道同步和转移都结束了，
  才敢转为一个 slave，开始处理 slave 该干的事
```

* 每一步的理由

    * 第 ② 步：master 不接新命令，才能保证数据不会被新写入搅乱

    * 第 ④ 步：master 已告知「数据最新到这个位置」，slave 若不一致就得先同步，同步完成后两者数据才完全一致

* 收尾

    * slave 把自己标记为 master，然后向集群中每一个节点发广播

    * 集群中其它节点收到消息后，以后就跟新 master 交互

    * 原 master 收到广播，知道同步和转移都结束了，才转为 slave

### FORCE 与 TAKEOVER

* `FORCE`

    * 含义：强制，省略对 offset 的校验，跳过与数据一致性有关的几步

    * 行为：上来就通知「我要替换你了」，不管数据一样不一样，直接开始替换

* `TAKEOVER`

    * 含义：直接接管，是最暴力的一种

    * 行为：忽略数据一致性、忽略 master 状态和其他 master 的意见，前面几步都不做，直接执行第 ⑤ 步——把自己标记成 master 并通知集群

* > **易错点**：虽然可以用 `FORCE` 或 `TAKEOVER` 强制替换，但**一般不推荐**，通常用默认缺省即可。

* 演示

```bash
redis-cli -p 7002
CLUSTER FAILOVER
```

    * 执行后 7002 变成 master，之前顶上来的 8003 变回 slave，切换一瞬间完成

## 分片集群的 Java 访问

* 接入方式

    * RedisTemplate 已集成分片集群，同样基于 Lettuce 实现，Redis 里的功能它全都能用

    * 用法与哨兵模式基本一致，三步：引入 Redis 的 starter 依赖、配置集群地址、配置读写分离

* 与哨兵模式的唯一差别

    * 哨兵模式配的是**哨兵的地址**

    * 分片集群配的是**集群中每个节点自己的地址**——因为分片集群里没有哨兵这个角色

```yaml
spring:
  data:
    redis:
      cluster:
        # 分片集群没有哨兵，这里要把每个节点都配进来
        nodes:
          - 127.0.0.1:7001
          - 127.0.0.1:7002
          - 127.0.0.1:7003
          - 127.0.0.1:8001
          - 127.0.0.1:8002
          - 127.0.0.1:8003
```

* 验证结论

    * 读写分离生效：查 `number`（该 key 在 7001 上），日志显示 GET 请求没有走 7001，而是走到 8002；8002 的角色是 slave，其 master id 与 7001 相同，数据等价，从 8002 读没有问题

    * 插槽自动路由生效：写 `set number` 落到 7001，写 `set a 666`（`a` 落在 7003）落到 7003

```text
读：get number  → number 落在 7001，而 7001 的从节点是 8002，实际读的是 8002
写：set number  → 7001
写：set a 666   → 7003
```

    * 综合结论：节点间的动态切换、插槽的自动路由、读写分离全部由客户端自动实现

## 多级缓存的由来

### 缓存的作用与单机上限

* 缓存的三项作用

    * 减轻对数据库的压力

    * 缩短服务的响应时间

    * 从而提高整个服务的并发能力

* 为什么还要多级缓存

    * Redis 单机并发已经很高，但仍有上限

    * 像淘宝、京东、12306 这类网站，并发量往往能达到亿级以上的流量，仅靠一个 Redis 满足不了。

### 传统缓存的两个瓶颈

```text
用户请求
   │
   ▼
Tomcat 服务器        ← 瓶颈：Tomcat 的并发能力其实不如 Redis
   │ 先查
   ▼
Redis 缓存 ──命中──► 直接返回
   │ 未命中
   ▼
数据库               ← 缓存失效或宕机时，全部请求直接压到这里
```

* 瓶颈一：请求要经过 Tomcat 处理

    * 用户请求进 Tomcat，再由 Tomcat 去查 Redis 缓存

    * Tomcat 本身的并发能力不如 Redis，因此 Tomcat 成为整个业务的瓶颈

* 瓶颈二：Redis 缓存有过期的可能

    * Redis 有淘汰策略；部分缓存失效、或缓存直接挂掉时，所有请求直接打到数据库

    * > **易错点**：⚠️ 传统缓存把「缓存失效」这件事完全押在 Redis 一层身上，它一旦过期或宕机，数据库就是裸奔的。

### 多级缓存的分层

* **多级缓存**

    * > **定义**：充分利用请求处理的每一个环节都加上缓存，从而减轻数据库压力、提升性能。

```text
浏览器 / App
   │
   │  ① 浏览器客户端缓存：静态资源没变化就返回 304，浏览器直接渲染本地数据
   │     非静态数据 ↓
   ▼
Nginx
   │
   │  ② Nginx 本地缓存：命中直接返回，不过 Tomcat；未命中 ↓
   ▼
Redis
   │
   │  ③ Redis 缓存：命中直接返回；未命中 ↓
   ▼
Tomcat
   │
   │  ④ Tomcat 进程缓存（JVM 进程内）：命中就不访问数据库；未命中 ↓
   ▼
数据库
```

* ① 浏览器客户端缓存

    * 浏览器把服务器返回的静态资源缓存在本地

    * 再次访问时服务器只检查数据有没有变化，没变化直接返回 304 状态码，不返回数据；浏览器看到 304 就直接渲染本地数据

    * 数值：对一个页面而言，90% 的请求都是这种可缓存的静态资源请求，因此响应速度大幅提升

* ② Nginx 本地缓存

    * Nginx 不再只做反向代理，而是在内部形成第二级缓存；Nginx 也可以像 Tomcat 一样编写业务逻辑，把数据缓存在本地

    * 命中直接返回，压根到不了 Tomcat

    * 未命中时也不绕 Tomcat：既然要在 Nginx 里编程，就直接在 Nginx 里查 Redis——查 Redis 的动作从 Tomcat 搬到了 Nginx，Tomcat 压根不参与。

* ③ Redis 缓存

    * 老熟人：命中直接返回，未命中才到达 Tomcat

* ④ Tomcat 进程缓存

    * 在服务器内部用类似 Map 的形式形成进程缓存（实际不会用 Map，会用更高级的东西），请求先读本地缓存，命中就不访问数据库

* 两个问题如何被解决

    * 大多数请求被 Nginx 处理，不过 Tomcat，Tomcat 不再成为系统瓶颈

    * Redis 缓存失效时还有 Tomcat 进程缓存作缓冲，不会直接打到数据库，何况前面还有好几层缓存

### 部署形态与学习范围

* 部署结构

```text
浏览器 / App
      │
      ▼
Nginx 反向代理（只做静态资源 + 负载均衡）
      │  把请求负载均衡到下面任意一个业务节点
      ▼
  ┌───┴───────┐
  ▼           ▼
Nginx 节点1  Nginx 节点2      ← 用 Lua 写业务，带本地缓存
  └───┬───────┘
      ▼
 Redis 集群
      │ 未命中
      ▼
 Tomcat 集群（进程缓存）
      │ 未命中
      ▼
    数据库
```

* 名分区别

    * 前面那台 Nginx 是纯反向代理（静态资源 + 负载均衡）

    * 后面那几台是要写业务的多级缓存节点，即「Nginx 业务集群」

* 压力转移

    * 所有压力集中到 Nginx，Nginx 不再是单纯的反向代理服务器，而是在内部编写业务访问的真正对外服务

    * 因此 Nginx 业务集群需要部署成集群来应对更高并发；Redis、Tomcat、MySQL 也都可以做成集群

* 服务端开发要掌握的四块知识

    * JVM 进程缓存——在 Tomcat 内部编写进程缓存

    * Nginx 编程——在 Nginx 内部写业务，要学一门新语言 Lua

    * 多级缓存实现——把 Nginx 本地缓存、Redis 缓存、Tomcat 缓存串起来

    * 缓存同步策略——数据库与缓存之间还要做同步

### 商品表与库存表为什么要分开

| 表 | 内容 |
| :--- | :--- |
| `tb_item`（商品表） | 商品 id、标题名称、价格、图片、品牌分类等基本信息，一共 5 条数据 |
| `item_stock`（库存表） | id、库存、销量，就三个字段，id 与商品表对应 |

* 现实背景

    * 一个商品的数据非常多：除基本信息外还有详细介绍、规格参数、包装、售后保障、用户评价，往往需要 N 多张表保存

* 分离的两个理由

    * 数据解耦：一张表数据太多、字段太多，查询效率会比较低

    * 为缓存考虑：若所有数据在一张表里，缓存的就是一条包含商品完整信息的数据；其中任意一个字段（如经常变化的库存）被修改，整条数据作废、整个商品缓存失效，缓存失效频率过高

    * 分开之后：经常修改的和不经常修改的各成一张表、各成一个缓存，库存改了只影响库存那份缓存，其他缓存不受影响

    * > **结论**：数据分离要做细，这既是数据库表的设计，也是后面缓存设计能跑得动的前提

### 静态页面与 Nginx 反向代理

* 页面定位

    * Ajax 查询将来走多级缓存流程：先查 Nginx 本地缓存，未命中查 Redis，再未命中查 Tomcat

* Nginx 运行

    * > **提示**：Nginx 运行时千万不要放在中文目录下，路径也不要出现空格

    * 启动：`start nginx`；浏览器直接访问 `localhost`（不要加任何端口），看到欢迎页即启动成功

* 反向代理配置

    * Ajax 请求地址是 `localhost/api/item/1001`，没有加端口，因此发到 80 端口，即当前的 Nginx 服务器

    * 该请求被 Nginx 的 `location /api/` 拦截，反向代理到 `nginx_cluster`（即 Nginx 业务集群），由它完成后续的多级缓存处理

```nginx
upstream nginx_cluster {
    server 192.168.150.101:8001;
    # 第二台机器的地址，按自己的实际情况补充
}

server {
    listen 80;
    # 以 /api/ 开头的请求，反向代理到 Nginx 业务集群
    location /api/ {
        proxy_pass http://nginx_cluster;
    }
}
```

    * 配置里的两个地址是虚拟机 IP 加对应端口，这两台服务当前并不存在，所以页面 Ajax 会报错

## 进程缓存与分布式缓存

* **分布式缓存（Redis）**

    * > **定义**：独立于 Tomcat 之外、可在集群间共享的缓存，如 Redis

    * 优势：不管 10 台还是 100 台 Tomcat 都共享一份；Redis 本身能搭集群，存储容量可以非常大；哨兵机制与主从模式提供更好的可靠性

    * 劣势：Tomcat 访问它必然发起网络请求，带来额外网络开销，性能受制于网络、存在网络延时

* **进程本地缓存（JVM 进程缓存）**

    * > **定义**：存放在 Tomcat 进程内部的缓存，如用 HashMap 存数据、下次直接从 Map 读

    * 优势：本地内存直读，不用网络请求，速度更快

    * 劣势：不能共享（每台一份、数据冗余）、容量上限就是当前 Tomcat 的 JVM 堆内存且不能占完、进程重启或服务宕机数据就丢

| 对比维度 | Redis 分布式缓存 | JVM 进程缓存 |
| :--- | :--- | :--- |
| 存放位置 | 独立于 Tomcat 之外 | Tomcat 进程内的堆内存 |
| 多实例共享 | 可以，10 台还是 100 台共用一份 | 不可以，每台各自一份，数据冗余 |
| 存储容量 | 能搭集群，容量可以非常大 | 上限就是当前 Tomcat 的 JVM 堆内存，而且你也不能一个人占完，否则程序运行就有问题了 |
| 可靠性 | 哨兵、主从模式能提供更好的可靠性 | 进程重启或服务宕机，数据就丢了 |
| 访问性能 | 要走网络，受网络延时影响 | 本地内存直读，更快 |

* > **结论**：进程本地缓存是作为 Redis 缓存的**补充**来使用的——Redis 未命中时再去看进程缓存；企业开发中两者结合使用

## Caffeine

* **Caffeine**

    * > **定义**：基于 Java 开发、可提供近乎最佳命中率的高性能本地缓存库，Spring 内部很多时候也会用到它

    * 官方读写测试（读写比例约 3:1）中对比的对象有：`ConcurrentHashMap`（JDK 自带）、Guava（Google 的库）、Ehcache、Infinispan 等；其中表现最好的是 Caffeine

### 基本 API

* 构建缓存对象

```java
Cache<String, String> cache = Caffeine.newBuilder().build();
```

    * `Caffeine.newBuilder()` 是工厂模式获取工厂，再用 `build` 构建出缓存对象

    * 缓存对象上有两个泛型，就是 key 和 value，这一点跟 Map 很像

* 存与取

```java
// 存：key 是 gf，value 是我女朋友
cache.put("gf", "迪丽热巴");

String gf = cache.getIfPresent("gf");   // 迪丽热巴
```

    * `put(key, value)`：跟 Map 一样

    * `getIfPresent(key)`：「如果有我就取」，没有则返回 null

* `get(key, Function)`：日常用得最多的取法

```java
// key 存在：查出来返回；key 不存在：执行 Function，返回值写入缓存并返回
String defaultGf = cache.get("default:gf", key -> {
    // 真实场景在这里查数据库；demo 里就直接返回一个假数据
    return "柳岩";
});
System.out.println(defaultGf);   // 柳岩
```

    * 语义：先按 key 查缓存；未命中就执行第二个参数这个函数（里面写查询数据库的业务逻辑）；把数据库结果写入缓存并作为结果返回

    * 价值：查缓存、判断是否命中、未命中查数据库、查完写入缓存这一整套事情，一个方法全做了。

### 驱逐策略

* 三种驱逐策略

| 策略 | 配置 | 含义 |
| :--- | :--- | :--- |
| 基于容量驱逐 | `maximumSize` | 设置缓存上限，一旦超过阈值就做内存清理，清理时采用 LRU 策略（最近最少使用），跟 Redis 一样 |
| 基于时间驱逐 | `expireAfterWrite` | 在写入之后开始计时，如 `Duration.ofSeconds(10)` 即 10 秒；写入超过 10 秒以后如果没有人访问，就把它清除 |
| 基于引用驱逐 | 软引用 / 弱引用 | 利用 Java 的垃圾回收机制，把 key/value 配成软引用或弱引用，没被引用的对象可被回收 |

* > **提示**：基于引用的方式官方交代性能太差、不建议使用，一般用前两种就够

* 基于容量示例

```java
Cache<String, String> cache = Caffeine.newBuilder()
        .maximumSize(1)   // 我的缓存最大值只能存一个
        .build();

// 我有三个女朋友，全往里面存
cache.put("gf1", "迪丽热巴");
cache.put("gf2", "杨幂");
cache.put("gf3", "赵丽颖");
```

    * 现象：上限为 1 却三个都进去了

    * 原因：驱逐需要时间——直接运行完 JVM 就退出了，根本没机会驱逐；稍微休眠、给一点空闲时间后再看，前两个 key 就被清理掉，只剩最后一个

* 基于时间示例

```java
Cache<String, String> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofSeconds(1))  // 写入之后清除，时间 1 秒
        .build();

cache.put("gf", "柳岩");
System.out.println(cache.getIfPresent("gf"));   // 柳岩

Thread.sleep(1200);
System.out.println(cache.getIfPresent("gf"));   // null
```

* > **易错点**：⚠️ 跟 Redis 一样，Caffeine 的缓存驱逐**不是立即驱逐**——超过上限后只是做一个标记，一般在下一次读写操作时、或在空闲时间才真正清理

* 企业开发用法

    * 开发过程中把缓存提前定义好，做成静态工具类或非静态工具类都行

    * 把这个 `Cache` 对外暴露，让别人使用它、往里边做数据读取
