# 商户查询缓存：缓存更新策略与三大问题

## 缓存是什么

### 缓存的本质

   * **缓存（Cache）**

       * > **定义**：数据交换的缓冲区，是存储数据的临时地方，读写性能较高。

       * 引入缓存的动因：CPU 运算能力远超内存与磁盘的读写能力，而 CPU 做任何运算都必须先把数据读到寄存器，数据读写能力成为整机性能瓶颈。

       * 解法是在 CPU 内部加缓存，把经常读写的数据放进去，高速运算时直接从缓存取，不必每次都从内存和磁盘读。

       * 衡量 CPU 强弱的一项标准是 CPU 缓存的大小——缓存越大，能缓存的数据越多，处理性能越好。

### Web 开发中的缓存层次

   * 请求从外到内流经每一层，每一层都可以加缓存：

       * **浏览器缓存**：缓存 CSS、JS、图片等不变的静态资源，无需每次加载，降低网络延迟、提高页面响应速度。

       * **应用层缓存**：在 Tomcat（Java 应用）一侧建缓存，一般用 Redis 而不是自建 Map，因为 Redis 读写延迟往往在微秒级别。

       * **数据库缓存**：索引数据缓存进内存，按索引查询时在内存里快速检索，不必每次读写磁盘。

   * > **易错点**：数据最终查找还是要落到磁盘，做复杂排序、表关联这类运算还会用到 CPU，因此数据库最终仍会访问 CPU 与磁盘，这一层又会用到 CPU 多级缓存与磁盘，甚至还能建读写缓存。

### 缓存的收益

   * **降低后端负载**：请求进入 Tomcat 后直接在缓存查到并返回，不必查数据库，避免慢 SQL 与磁盘读写给数据库带来的压力。

   * **提高读写效率、降低响应时间**：数据库读写往往是磁盘读写，耗时较长；Redis 这类缓存读写延迟在微秒级别，等待时间大幅缩短，从而能应对更高的并发请求。

### 缓存的成本

   * **一致性成本**：数据同时存在于数据库与缓存，数据库改了而缓存不知道，用户读到旧数据；重大数据不一致会带来严重问题。解决一致性还要写非常复杂的业务编码，过程中又会引出缓存穿透、击穿等一连串问题，开发与后期维护成本都很高。

   * **运维成本**：为避免缓存雪崩、保证缓存高可用，缓存往往要搭成集群，集群的部署与维护带来额外人力成本与硬件成本。

   * **开发成本**：加了缓存以后代码明显变复杂。

   * > **注意**：是否用缓存要看收益能否弥补成本；中小型企业刚起步、用户量不大时不用缓存也能应对日常请求，没有必要引入这些成本。

### 缓存的工作模型

   * 加缓存之前：客户端请求全部直达数据库，数据库查询后返回给客户端。

   * 加缓存等于在客户端与数据库之间加了一层中间层：

       ```text
       客户端 ──► Redis ──► 命中 ──────────► 直接返回给客户端
                     │
                     └─► 未命中 ──► 数据库 ──► 结果返回给客户端
                                       └──────► 同时写回 Redis（下次就能命中）
       ```

   * 未命中必须把数据库结果写回 Redis，否则下次请求依然未命中；随着请求数据越来越多，Redis 缓存的数据越多、命中率越高，这才形成良性工作模型。

   * > **结论**：整个流程的关键点只有两个——一开始从 Redis 查；Redis 未命中时查数据库并把数据写入 Redis。

## 给商户查询加缓存

### 业务流程

   * 接口 `/api/shop/{id}` 是按 id 查询商户详情的入口，业务逻辑不能写在 Controller 里，要下沉到 Service，Controller 只做 `return shopService.queryShopById(id)`。

   * 加缓存后的步骤：提交店铺 id → 先查 Redis → 命中则直接返回 → 未命中则查数据库 → 数据库中不存在说明 id 传错，返回错误 → 数据库中存在则先写入 Redis 再返回。

   * 原实现直接调 MyBatis-Plus 的 `IService.getById`，拿到 Wrapper 后走 select，等于直接查库，没有任何缓存。

### 数据结构与 key 设计

   * 缓存的是商铺对象，Hash 完全可用；采用 String（`opsForValue()`）演示，把对象转成 JSON 字符串存储。

   * key 必须确保唯一：每个店铺都有唯一 id，因此以店铺 id 作为 key 是合适的选择。

   * key 一定要拼前缀再跟 id：`cache:shop:` + id，提取成常量 `CACHE_SHOP_KEY` 放到 Redis 常量类里。

   * value 是店铺的 JSON 字符串，读取时要反序列化成 Java 对象。

### 实现要点

   * 命中判断要用 `StrUtil.isNotBlank(shopJson)`：拿到的是 JSON 字符串，若为空还去做反序列化会出现空指针异常。

   * 查完数据库要判断是否存在，不存在返回 `Result.fail("店铺不存在")`；也可以返回 OK 放空，取决于与前端的约定。

   * 写入用 `JSONUtil.toJsonStr(shop)`，读出用 `JSONUtil.toBean(shopJson, Shop.class)`。

   * 验证缓存是否生效的办法：清空 IDEA 日志后重新访问，看控制台是否还有 `select ... from tb_shop`；优惠券的 SQL 与店铺无关，不算数。

### 课后练习：店铺类型查询加缓存

   * 目标接口 `/api/shopTypeList` 对应首页店铺类型展示，数据不怎么变化，非常适合做缓存。

   * 与店铺查询的差别在于返回值是**集合**而不是单个对象。

   * 一切 Java 对象最终都能转成 JSON 字符串，集合也不例外，所以用 String 类型可以；也可以选择 List 类型。

## 缓存更新策略

### 三种策略

   * **内存淘汰**

       * 原本是 Redis 用来解决内存不足的机制，Redis 基于内存存储、内存有限，往往设置上限，数据越来越多时触发淘汰策略清出空间。

       * 默认开启、不用管，淘汰策略可自行配置（长文未展开具体策略）。

       * 一致性：内存不足时淘汰掉数据，用户再查就会未命中、回源数据库并写回缓存，一定程度上能达成一致。

       * > **易错点** ⚠️：淘汰哪部分数据、什么时候淘汰都不可控，内存一直充足时数据可能很长时间不被淘汰，用户每次查到的都是旧数据，一致性差；好处是维护成本几乎为零。

   * **超时剔除**

       * 利用 `EXPIRE` 命令给 key 加过期时间，到期 Redis 自动删除，下次查询未命中就会更新缓存。

       * 一致性强弱取决于 TTL 长短：设 30 分钟更新频率不错，设一天更新频率就低，是人为可控的。

       * 不是强一致而是最终一致：TTL 期间数据库若发生变化，两边依然不一致；但一致性好于内存淘汰，维护成本也只是加一个过期时间。

   * **主动更新**

       * 自己编写业务逻辑，修改数据库的同时把缓存也改掉。

       * 一致性比较好，但不是"完全保证一致"——没有任何人能确保程序一定健康运行。

       * 成本高：原来只写数据库，现在还要同步处理缓存，业务编码复杂、维护成本高。

   * | 策略 | 一致性 | 维护成本 | 关键点 |
     | :--- | :--- | :--- | :--- |
     | 内存淘汰 | 差，不可控 | 几乎为零 | Redis 自带，淘汰哪部分、何时淘汰我们不知道 |
     | 超时剔除 | 一般，最终一致 | 低 | 给 key 设 TTL，时长短则更新频率高 |
     | 主动更新 | 很好 | 高 | 改库的同时改缓存，需自己编码 |

### 主动更新的三种模式

   * **Cache Aside**

       * 人工编码，自己写代码在更新数据库的同时更新缓存，对应 `@Cacheable` 这类注解的使用方式。

       * 调用者要自己写代码、稍微复杂，但可以人为控制，可控性最高。

   * **Write Through**

       * 把缓存与数据库整合成一个服务，对外透明，调用者不用管底层用的是什么。

       * 服务内部同时处理缓存与数据库，能保证两者同时成功或同时失败，由它维护一致性；调用者无需关心一致性问题。

       * 代价：维护这样一个服务比较复杂，市面上现成的不好找，开发成本高。

   * **Write Behind（写回）**

       * 调用者明确地只操作缓存，增删改查全部在缓存里做，不处理数据库、不处理一致性。

       * 由一个独立线程异步地把缓存数据持久化到数据库来保证一致，写入是异步的、隔一段时间执行一次。

       * 好处是可合并写：两次异步更新之间对同一个 key 做了 $n$ 次更新，只有最后一次有效，只需把最后一次结果写入数据库；十次写操作也可能被合并成一次批处理，效率提升明显。

       * 代价：要实时监控缓存变更的异步任务本身复杂；一致性难保证，异步未触发期间数据库与缓存完全不一致；缓存多为内存存储，一旦宕机数据丢失，可靠性也有问题。

   * | 模式 | 调用者做什么 | 一致性由谁保证 | 代价 |
     | :--- | :--- | :--- | :--- |
     | Cache Aside（`@Cacheable`） | 自己写代码，更新数据库时同步处理缓存 | 调用者自己 | 代码复杂，但可控性最高 |
     | Write Through | 只调一个服务 | 服务内部同时处理缓存与数据库，保证同时成功或失败 | 要维护这样一个服务，现成的不好找，开发成本高 |
     | Write Behind（写回） | 只操作缓存 | 独立线程异步批量持久化 | 一致性难保证，缓存宕机会丢数据 |

   * > **结论**：三种模式里企业用得最多的是 Cache Aside；后两种实现复杂、也找不到较好的第三方组件。

### Cache Aside 的三件事：更新还是删除

   * 两种做法：更新缓存是数据库做什么更新、缓存也做什么更新；删除缓存是更新数据库后直接把缓存删掉。

   * 更新缓存的问题：对数据库做上百次操作就要对缓存做上百次操作，若期间无人查询（写多读少），这 $n$ 次修改全是无效写。

   * 删除缓存等于延迟加载：更新 100 次其实只删一次就够，期间无人访问就不更新，什么时候有人访问什么时候更新。

   * > **结论**：删除缓存写频率更低、有效更新更多，一般选择删除缓存而不是更新缓存。

   * 补充：采用更新缓存的方案还会有较大的线程安全问题，这也是不选它的原因之一。

### Cache Aside 的三件事：原子性

   * 必须保证"更新数据库"与"删除缓存"同时成功或同时失败。

   * 单体系统：缓存与数据库在同一个项目、甚至同一个方法里，做成事务即可，利用事务特性保证同时成功和失败。

   * 分布式系统：缓存操作与数据库操作可能是两个不同服务，必须借助 TCC 这类分布式事务方案保证原子性。

   * > **注意**：原子性保证不了，关于先后顺序的分析就都没有意义。

### Cache Aside 的三件事：线程安全

   * **先删缓存，再更新数据库**（正常情况）

       * 初始缓存与数据库都是 10：线程先删缓存，再更新数据库为 20；此后任何人来查询都会未命中、查库拿到 20 并写回 20，两者一致。

   * **先删缓存，再更新数据库**（异常情况）

       ```text
       初始：缓存 = 10，数据库 = 10

       时刻   线程A（更新：先删缓存，再更新数据库）   线程B（查询）
       ─────────────────────────────────────────────────────────────
        t1    删除缓存
        t2                                          缓存未命中
        t3                                          查数据库 → 拿到 10（旧值）
        t4                                          把 10 写回缓存
        t5    更新数据库 → 20
        t6    结束

       结果：缓存 = 10，数据库 = 20   →   不一致
       ```

       * 发生概率较高：删缓存很快，更新数据库要组织数据且是写操作、很慢，而查询线程查缓存、写缓存都在微秒级别，很容易插在这两者之间执行。

   * **先写数据库，再删缓存**（正常情况）

       * 先把数据库改成 20 再删缓存，此后任何人查询都会未命中、查库拿到 20 并写回 20，保持一致。

   * **先写数据库，再删缓存**（异常情况）

       ```text
       初始：缓存 = 10，数据库 = 10

       时刻   线程A（更新：先写数据库，再删缓存）    线程B（查询）
       ─────────────────────────────────────────────────────────────
        t1    更新数据库 → 20
        t2                                          恰好缓存失效 → 未命中
        t3                                          查数据库 → 拿到 10（旧值）
        t4    删除缓存（本来就没有，删了等于没删）
        t5    结束
        t6                                          把 10 写回缓存

       结果：缓存 = 10，数据库 = 20   →   仍然不一致
       ```

       * 发生概率极低，要同时满足三个巧合：两个线程并行；查询时缓存恰好失效（比如时间到了）；恰好在查完数据库、写缓存这个微秒级的窗口内，另一个线程完成了慢得多的数据库更新与删缓存。

       * 缓存速度远高于数据库，数据库更新操作不太可能比缓存操作还快。

   * > **结论**：两种顺序都可能出问题，但先写数据库再删缓存的概率极低；万一发生，写缓存时加超时时间兜底，旧数据过一段时间也会被清除。

### 缓存最佳实践

   * 低一致性需求（长久不发生变化的数据，如店铺类型）：用自带的内存淘汰机制即可，实在不放心再加超时时间。

   * 高一致性需求（如店铺详情、优惠券）：必须做主动更新，并以超时剔除作为兜底，万一主动更新失败，超时后仍能清除脏数据。

   * 主动更新选 Cache Aside，并且：删除缓存而不是更新缓存；单体用事务、分布式用分布式事务保证原子性；顺序上先写数据库再删缓存。

   * 读侧流程不变，但**写缓存时必须设置超时时间**作为兜底方案。

   * 最终落地形态：

       ```text
       【查询】
         请求 ──▶ 查缓存 ──命中──────────────▶ 直接返回
                        └─未命中─▶ 查数据库 ──▶ 写回缓存 ──▶ 返回

       【修改】
         请求 ──▶ 改数据库 ──▶ 删缓存
       ```

## 双写一致的代码落地

### 查询时补 TTL

   * 改动只有一处：写入缓存的同时设置过期时间。

       ```java
       String key = SHOP_CACHE_KEY + id;
       redisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_TTL, TimeUnit.MINUTES);
       ```

   * > **易错点** ⚠️：方法最后的时间单位参数千万别漏，只写 `set(key, value, 30)` 时 Redis 认的是秒，30 秒就过期，和想要的半小时差了六十倍。

   * TTL 提取成常量放到 `RedisConstants`：`SHOP_CACHE_KEY = "shop:"`、`CACHE_TTL = 30L`（单位分钟，业务含义就是这条缓存的有效期）。

### 更新时下沉到 Service 并删缓存

   * 原 `updateShop` 直接调 MyBatis-Plus 的 `updateById`，一行更新完，根本没有缓存什么事；缓存逻辑放不进 Controller，必须先把更新下沉到 Service，Controller 只剩 `shopService.update(shop)`。

   * 实现要点：

       * key 用与写入时同一个前缀拼店铺 id，id 只能从传入的 `shop` 对象里 `getId()` 取。

       * id 必须判空：id 不存在时拼 key 会出问题，判空直接返回 `Result.fail("店铺id不能为空")`，根本不做任何更新。

       * 整个方法加 `@Transactional` 做成统一事务，删除缓存抛异常时事务跟着回滚。

```java
@Override
@Transactional
public Result update(Shop shop) {
    if (shop.getId() == null) {
        return Result.fail("店铺id不能为空");
    }
    updateById(shop);
    String key = SHOP_CACHE_KEY + shop.getId();
    redisTemplate.delete(key);
    return Result.ok();
}
```

   * 单体项目里数据库操作与缓存操作在同一个方法中，用事务就能控制原子性；分布式系统下删缓存可能是另一个系统通过 MQ 异步通知完成，要借助 TCC 这类方案保证强一致。

### 验证方式

   * 验证 TTL：缓存里已有数据时会走命中，看不出效果，要先清空 Redis 让它重走 miss 路径，触发 `select ... from tb_shop`；再打开 Redis 客户端能看到 key 旁显示 `TTL 1775`，而设置的总量是 `1800` 秒。

   * 验证更新：更新动作由管理端发起，用户端页面点不出来，要借 Postman 发 `PUT 8081/shop`；返回 `200 OK`、控制台出现 update、数据库里店铺名已变，而 Redis 里的 key 消失了。

   * 用户再次刷新时查到的一定是最新数据，同时缓存被重建，Redis 里重新出现新值。

## 缓存穿透

### 成因与危害

   * > **定义**：**缓存穿透**是指客户端请求的数据在缓存中和数据库中都不存在的情况。

   * 既然两边都不存在，就永远不可能建立缓存，只要有人请求就一定会到达数据库。

       ```text
           客户端              Redis                 数据库
             |                  |                      |
             |-- 请求 id ------>|  没有这个 key        |
             |                  |----- 查询 --------->|
             |                  |<---- 也不存在 ------|
             |<-- 返回空 -------|                      |
             |                  |                      |
             |-- 再请求一次 --->|  还是没有            |
             |                  |----- 查询 --------->|  <-- 每次请求都落到库
             |<-- 返回空 -------|                      |
       ```

   * 危害：不怀好意的人构造无数个不存在的 id 并发请求，这些请求全部打到数据库，很可能把数据库搞垮。

### 缓存空对象

   * 思路：Redis 没有、数据库也没有时，把空值也缓存进 Redis，下次再来就能命中，尽管命中的是 null，也不会再请求数据库。

   * 优点：简单粗暴，实现代码非常容易。

   * 缺点一，额外的内存消耗：随便传的 id 都被缓存起来，Redis 里会堆积垃圾。

       * 对策是给 null 加一个较短的 TTL，比如五分钟甚至约两分钟；两分钟内对恶意请求有保护作用，到期后垃圾数据自动清除。

   * 缺点二，短期不一致：请求某个不存在的 id 后缓存了 null，此时真的插入了这条数据，用户查到 null 而实际存在，只有 TTL 过期后才能查到最新数据。

       * 对策一是控制好 TTL 时长，把不一致期压到足够短；对策二是新增数据时主动把这条数据插入缓存、覆盖之前的 null。

### 布隆过滤器

   * > **定义**：**布隆过滤器（Bloom Filter）**是一种算法，在客户端与 Redis 之间加一层前置拦截。

       ```text
         客户端 ──> 布隆过滤器 ──> Redis ──> 数据库
                        │              │          │
               判定不存在：直接拒绝    未命中      查不到
               判定存在：才放行 ────> 才继续往下走
       ```

   * 判定不存在就直接拒绝、不给往下走的机会；判定存在才去 Redis 查，后续逻辑与原来完全一致，仅仅多了一个前置过滤。

   * 原理：它就是一个 bit 数组，存的是二进制位；并不真的把数据存进去，而是把数据用某种**哈希算法**算出哈希值，再转成二进制位保存，判定时看对应位置是 0 还是 1。

   * > **易错点** ⚠️：这种存在与否是概率上的统计，不是百分之百准确——说不存在时是真的不存在，说存在时却不一定真存在，因此布隆过滤器本身仍有一定的穿透风险。

   * 优点：内存占用少，只是用二进制位的形式保存数据，不用缓存大量空数据。

   * 缺点：实现相对复杂；存在误判可能。

   * > **提示**：Redis 的 **bitmap（位图）** 是布隆过滤器最典型的实现载体，Redis 自带这种方式可以简化开发。

   * > **结论**：实际开发中选择缓存空对象来解决缓存穿透。

### 穿透保护的代码改动

   * 改动一：数据库中不存在时，除了返回错误，还要把空值（空字符串）写进 Redis，有效期用单独的短常量 `CACHE_NULL_TTL = 2L`（分钟），不能像真实数据那样给 30 分钟。

       ```java
       Shop shop = queryShopById(id);
       if (shop == null) {
           redisTemplate.opsForValue().set(SHOP_CACHE_KEY + id, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
           return Result.fail("店铺不存在");
       }
       ```

   * 改动二：命中之后还要再判一次命中的是不是空值。`StrUtil.isNotBlank` 只有在真正有字符串时才为 true，null、空字符串、纯空白都为 false，所以命中空串会往下走、会去查数据库，必须拦住。

```java
String json = redisTemplate.opsForValue().get(key);
if (StrUtil.isNotBlank(json)) {
    shop = JSONUtil.toBean(json, Shop.class);
    if (shop != null) {
        return Result.ok(shop);
    }
    return Result.fail("店铺不存在");
}
```

   * 命中分支里判 `shop != null` 就够了：前面已经排除了有值的情况，剩下只有 null 与空字符串两种，既然不等于 null 就一定是空字符串。

   * | 命中情况 | Redis 里是什么 | 怎么处理 |
     | :--- | :--- | :--- |
     | 命中真实数据 | 商铺的 JSON | 直接返回商铺信息 |
     | 命中空值 | 空字符串 | 直接返回错误，不查数据库 |
     | 什么都没命中 | null | 去查数据库 |

   * 验证：查一个不存在的 id（如 0 号），第一次日志里有 `select ... from tb_shop`；清空日志再查一次就没有 SQL 了，Redis 里出现了 `shop:0` 这个空值 key。

### 主动防御

   * 以上两种属于被动弥补，还可以主动防范。

   * **增加 id 的复杂度、加强基础格式校验**：避免别人猜到 id 的规律；真正的 id 要有格式规范（长度、前缀、规律性），接到 id 后先做格式校验，不符合规范（如"0"）的直接拒绝。

   * **加强用户权限管理**：不是任何人都能访问服务，比如要求先登录。

   * **限流**：对用户做访问频率限制；对热点参数做限流；对空值参数也可以做限流，避免给数据库带来额外压力。

## 缓存雪崩

### 成因

   * > **定义**：**缓存雪崩**是指在同一时段内有大量的缓存 key 同时失效，或者 Redis 服务直接宕机，导致大量请求到达数据库、带来巨大压力的情况。

   * 正常情况：大部分请求在 Redis 直接返回，只有少数未命中落到数据库。

   * 情况一，大量 key 同时过期：一瞬间几万甚至几十万的 key 一起失效，这些请求全部打到数据库，可能导致数据库压力过大而宕机。

       ```text
       情况一：大量 key 同时过期

         客户端 ──几乎所有请求──> Redis（大批 key 同时失效）
                                      │
                                      └──────> 数据库   ← 压力剧增，可能宕机
       ```

   * 情况二，Redis 服务直接宕机（更严重、更可怕）：所有 key 都无法访问，接收到的一切请求都会访问数据库，等于数据库裸奔、回到原始状态。

       ```text
       情况二：Redis 服务直接宕机

         客户端 ──所有请求────> Redis（服务不可用，无法访问）
                                   │
                                   └──────> 数据库   ← 等于数据库裸奔
       ```

### 让 TTL 散开

   * 针对 key 同时失效：根因是它们的 TTL 一起到期，因此给不同的 key 的 TTL 添加一个随机值。

   * 典型场景是缓存预热批量导入：同一时刻导入、TTL 设成同一个值，将来很可能一起过期。

   * 解法：TTL 后面跟一个随机数，比如 30 分钟有效期后跟 1~5 的随机数，有效期就在 30~35 分钟之间波动，把过期时间分散到一个时间段内。

       ```java
       redisTemplate.opsForValue().set(key, value, CACHE_TTL + RandomUtil.randomInt(1, 5), TimeUnit.MINUTES);
       ```

### 提高 Redis 高可用

   * 针对宕机：首先要尽可能避免 Redis 宕机，提高整个 Redis 的高可用性，必须借助 Redis 集群与哨兵机制。

   * 哨兵做服务监控：搭建 Redis 集群形成主从，主宕机后哨兵自动从从机中选一个替代原来的主，确保 Redis 一直能对外提供服务。

   * 主从还能做数据同步，主宕机时从上仍有数据，不会导致数据丢失。

   * > **注意**：确保高可用用的是哨兵、集群这样的方案，不是主从。

### 降级限流与多级缓存

   * 降级限流策略：出现整个机房挂掉、整个 Redis 集群都完蛋这类不可抗事故时，提前做好容错处理，发现 Redis 故障就及时服务降级，比如快速失败、拒绝服务，而不是继续把请求压到数据库上，牺牲部分服务来保护数据库健康。

   * 多级缓存：浏览器缓存一般只缓存静态数据，动态数据可以在反向代理服务器 Nginx 层面做缓存，再往下还有 JVM 本地缓存，最后才是数据库。

       ```text
         浏览器(静态缓存) ──> Nginx(代理层缓存) ──> JVM 本地缓存 ──> Redis ──> 数据库
       ```

   * Redis 这一环崩了，还有很多别的缓存可以弥补，从而有效避免雪崩导致的问题。

   * 多级缓存方案常用于大型互联网电商项目（如商品详情）来应对高并发。

## 缓存击穿

### 成因

   * 击穿的原因往往是一些**热点 key**，热点要满足两个特点：**高并发**，以及**缓存的重建时间比较长**。

   * 重建时间长意味着重建过程中缓存不存在，又因为它高并发，这段时间内无数请求查不到缓存都会去查数据库，数据库承受巨大压力甚至宕机。

   * 要解决的核心问题：热点 key 重建的时候，不要有无数的线程进来。

### 互斥锁方案

   * 思路：重建时加锁，只能有一个线程重建，其他线程等待；实现简单粗暴，但等待会带来性能下降，还有死锁风险。

   * > **结论**：击穿的解法本质是在"缓存未命中"和"查数据库重建"之间插一道闸门，把成千上万并发请求挡在数据库外面，只放一个进去。

### 逻辑过期方案

   * 思路：逻辑过期甚至可以永不过期，不过期就不需要重建，不需要重建自然不会给数据库带来压力。

   * 永远都是旧数据也不行，所以要加一个逻辑过期时间：每次查到数据后判断这个 key 是否已过期、需要更新，是则再去更新。

   * 多个线程都判断出需要更新时仍有问题，所以还要加互斥锁；但为避免退化成等待方案，抢到锁后**不是自己去更新，而是开启一个独立的线程去做更新**。

   * 在独立线程更新缓存的这段时间内，其他所有线程不用等，直接查到什么就用什么（用旧数据），从而解决等待导致的性能下降与死锁问题。

   * 代价：正因为不用等、查到什么用什么，拿到的很可能是旧数据，实际存在一段时间的不一致。

### 两方案的取舍

   * | 方案 | 等待行为 | 一致性 | 风险 |
     | :--- | :--- | :--- | :--- |
     | 互斥锁 | 抢不到锁的线程休眠后重试，直到拿到数据 | 拿到的是重建后的新数据 | 等待导致性能下降，有死锁风险 |
     | 逻辑过期 | 抢不到锁直接返回旧数据，不等 | 重建完成前返回的是旧数据 | 一段时间内的不一致 |

## 互斥锁的实现

### 这把锁不是 synchronized

   * `synchronized` 与 `ReentrantLock` 是"等待式互斥"，语义是没拿到锁就一直排队等。

   * 击穿方案需要的是"没拿到就走开、稍后再来"：拿到锁去重建，没拿到锁先歇一会儿再来，执行逻辑要自己定义。

   * > **易错点** ⚠️：语义对不上，工具就选错了，不能使用等待式锁。

### SET NX 原语

   * `SET NX` 的含义是 `Set the value of a key only if the key does not exist`——当且仅当 key 不存在时才赋值，key 已存在就不执行。

       ```text
       set nx lock 1
       "1"        ← 第一个人的返回值：1，代表成功

       set nx lock 2
       "0"        ← 换个人来，还是想给这把锁换个值

       set nx lock 3
       "0"        ← 再来一个人

       get lock
       "1"        ← 值依然是原来那个 1，谁也没能改掉它
       ```

   * 并发数百上千个线程同时执行 `SET NX`，只有第一个人成功写入，其他人拿到的都是 0（失败），天然实现了"只有一个人成功"的互斥。

   * > **结论**：这事实上就是后期要讲的分布式锁的基本原理，真正的分布式锁会比这个复杂很多。

### 释放锁与有效期

   * 获取锁是给 key 赋值，释放锁就是把这把锁删掉（`delete`），删掉后其他人再执行 `SET NX` 就能成功。

   * 必须给锁加有效期：程序出问题迟迟不释放时，到期锁会自动释放，避免永远打不开的死锁；比如设 10 秒，而业务执行一般在一秒以内。

   * > **易错点** ⚠️：只写 `SET NX` 不写过期时间，等于留下了一把可能永远打不开的锁；有效期是必须项，不是优化项。

### tryLock 与 unlock

```java
private Boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", 10L, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}

public void unlock(String key) {
    stringRedisTemplate.delete(key);
}
```

   * `SET NX` 是 string 的操作，用 `opsForValue()`；Spring 里 NX 起的名字叫 `setIfAbsent`（ifAbsent 即"如果不存在"），找不到叫 `setNx` 的方法，而且这个方法可以直接带过期时间。

   * 锁的 value 随意，传 "1" 即可；有效期要比正常业务执行时长一些，长个十倍二十倍，避免异常情况。

   * 命令行返回的是 0 和 1，Spring 已转成 `Boolean`。

   * > **易错点**：`Boolean` 是包装类型，直接 return 会触发自动拆箱，一旦拿到 null 就是 NPE，必须走 `BooleanUtil.isTrue(...)` 这类判空转换。

### queryWithMutex 的流程

```text
前端提交 shopId
      │
      ▼
 查询 Redis 缓存
      │
 ┌────┴────┐
 │         │
命中     未命中
 │         │
直接     命中空值？──是──► 返回 null（穿透方案的结果）
返回       │
 │        └──否──► 尝试获取互斥锁 lock:shopId
 │                    │
 │              ┌─────┴─────┐
 │            失败          成功
 │              │             │
 │          休眠 50ms     查询数据库
 │        递归回查询处    写入 Redis
 │              │        释放锁（finally）
 │              │             │
 └──────────────┴──────┬──────┘
                       ▼
                    返回结果
```

   * 未命中之后还要再切一刀：命中空值是穿透方案留下的痕迹，直接返回 null；只有缓存里真的一无所有才进入击穿处理流程。

   * 锁的 key 不能用缓存的 key，要单独拼，如 `"lock:" + id`，每个店铺有自己的一把锁。

   * 获取锁失败：休眠一会儿后重试，重试就是重新执行整个查询动作，用递归回到方法开头；休眠时间不要太长，先试 50ms，因为不确定别人重建要花多久。

```java
String lockKey = "lock:" + id;
Boolean isLock = tryLock(lockKey);
if (!isLock) {
    Thread.sleep(50);
    return queryWithMutex(id);
}
```

   * 获取锁成功：查数据库、写 Redis，释放锁必须放在 `finally` 里，保证抛异常时也执行。

       ```java
       try {
           Shop shop = shopMapper.selectById(id);
           redisTemplate.opsForValue().set(cacheKey, JSONUtil.toJsonStr(shop));
           return shop;
       } catch (InterruptedException e) {
           throw e;
       } finally {
           unlock(lockKey);
       }
       ```

   * `Thread.sleep` 抛的是受检异常 `InterruptedException`，必须声明抛出或 try-catch 后往外抛。

   * 返回值可能为 null，可以在调用侧判空后 `return Result.fail("店铺不存在")`，反馈更友好。

   * 复用已有代码：把之前的穿透方案封装成 `queryWithPassThrough`，返回 `Shop`、内部不再返回 `Result`，保留下来便于参考。

### 压测与结论

   * 热点 key 要满足高并发与重建时间久两个条件；本地数据库太快、重建一瞬间就结束，不容易复现并发冲突，测试时要在代码里主动 `Thread.sleep(200)` 模拟重建延时。

       * > **提示**：本地环境跑出来"没问题"不能证明锁没问题；在测试代码里主动加延迟，等于把生产的极端情况搬到本地。

   * 用 JMeter 模拟高并发：

       * | 测试项 | 取值 |
         | :--- | :--- |
         | 线程数 | 1000 |
         | 持续时间 | 5 秒 |
         | 请求地址 | `localhost:8081/shop/1` |
         | QPS | 约 200 |
         | 数据库查询触发次数 | 1 次 |

   * 结果：1000 个线程在 5 秒内执行完毕、全部成功，QPS 约 200，而控制台里数据库查询只触发了一次，说明只有一个人进来了，互斥锁方案成立。

## 逻辑过期的实现

### 逻辑过期是什么

   * 逻辑过期不是真正的过期：存储数据到 Redis 时额外添加一个过期时间字段，而 key **本身不设 TTL**。

   * 过期时间不由 Redis 控制，而由程序员自己判断是否过期，因此 key 可以认为是永久有效。

   * > **注意**：向 Redis set 这个数据时并没有添加 TTL，真正的过期时间是代码里控制的逻辑过期时间。

### 命中判断反过来了

   * 这个方案里缓存查询理论上不会未命中：key 不会过期，一旦添加进缓存就应永久存在，除非活动结束人工删除；热点 key 往往就是参加活动的商品，会提前加入缓存并设好逻辑过期时间。

   * 查到缓存不存在只能说明这个商品不在活动当中、不是热点 key；为健壮性还是判断一下命中，真的未命中直接返回空，不用去做击穿、穿透的处理。

   * 核心逻辑是默认它命中，命中后判断有没有逻辑过期：

       * **未过期**：数据可用，直接返回给前端。

       * **已过期**：需要重建，先尝试获取互斥锁。

           * 获取失败：说明之前已经有人在更新了，佛系处理，不等，直接先把旧的返回，性能较好。

           * 获取成功：开启一个独立线程去做重建，自己同样先把旧数据返回；独立线程查数据库、写回 Redis 并设置新的逻辑过期时间、释放锁。

```text
前端提交 shopId
      |
      v
 stringRedisTemplate.opsForValue().get(CACHE_SHOP_KEY + id)
      |
      v
   缓存是否存在？
    | 否                    | 是
    v                       v
 直接返回 null      反序列化为 RedisData
                             |
                             v
                   expireTime 与当前时间比较
                        未过期 | 已过期
                           |       |
                           v       v
                    直接返回店铺  tryLock(LOCK_SHOP_KEY + id)
                              成功 | 失败
                                |     |
                                v     v
                       开启独立线程   不等待，直接返回旧数据
                       重建缓存
                                |
                                v
                    查数据库 → 写入 Redis（设置逻辑过期时间）
                                |
                                v
                        释放锁（写在 finally 里）
                                |
                                v
                    返回店铺信息（可能已是逻辑过期数据）
```

### 逻辑过期字段挂在哪儿

   * 两种方式：

       * 定义 `RedisData`，里面放 `LocalDateTime expireTime`，让 `Shop` 继承 `RedisData` 把属性带过来——简单，但要修改源代码，有侵入性。

       * 在 `RedisData` 里再放一个 `Object data`，自己既带过期时间又带数据——对原来的实体完全不做修改，是万能的存储数据的对象。

   * 演示采用第二种，存进 Redis 的数据形如：

       ```json
       {
         "data": { /* 店铺信息 Shop */ },
         "expireTime": "2026-10-03T15:30:00"
       }
       ```

### 热点数据预热

   * 热点数据的缓存需要提前导入，实际开发中可能由后台管理系统把热点数据提前加入缓存，这里用单元测试做缓存预设。

       ```java
       private void saveShopToRedis(Long shopId, long expireSeconds) {
           Shop shop = getById(shopId);
           RedisData redisData = new RedisData();
           redisData.setData(shop);
           redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));
           stringRedisTemplate.opsForValue()
                   .set(CACHE_SHOP_KEY + shopId, JSONUtil.toJsonStr(redisData));
       }
       ```

   * 逻辑过期时间由调用方传 `long expireSeconds`，内部用 `LocalDateTime.now().plusSeconds(expireSeconds)` 计算；写进去的不是 shop 而是 `RedisData`。

   * 单元测试里调 `shopService.saveShopToRedis(1L, 10L)`（方法改成 public），Redis 里就出现一条带 `data` 与 `expireTime` 的数据。

### 反序列化的两层

   * 反序列化成的类型是 `RedisData`，不能写成 `Shop`——Redis 里存的是 `RedisData`，真正的店铺信息藏在 `data` 里面。

   * `data` 取出后是 `Object`：序列化时 `data` 字段声明的就是 `Object`，反序列化拿不到具体类型，只能给通用对象类型。

       * > **提示**：Java 反序列化要靠目标类型的字节码映射字段，泛型擦除加上字段声明为 `Object`，框架无法确定要还原成什么，只能退回最通用的对象类型；所以工具类里不能把类型写死成店铺。

   * 把 `data` 再转一次即可，`toBean` 也能接受对象类型：

       ```java
       RedisData redisData = JSONUtil.toBean(shopJson, RedisData.class);
       Shop shop = JSONUtil.toBean(JSONUtil.parseObj(redisData.getData()), Shop.class);
       LocalDateTime expireTime = redisData.getExpireTime();
       ```

### 过期判断

```java
if (expireTime.isAfter(LocalDateTime.now())) {
    return shop;      // 未过期，直接返回旧店铺
}
// isBefore 则说明已经过期了，需要重建缓存
```

### 抢锁与独立线程重建

   * 锁 key 常量：`LOCK_SHOP_KEY`，锁过期时间 `LOCK_SHOP_TTL` 设 30 秒或 10 秒就够，不要太长。

   * 用线程池而不是自己 `new Thread()`：

       ```java
       private static final ExecutorService CACHE_REBUILD_EXECUTOR =
               Executors.newFixedThreadPool(10);

       if (isLock) {
           try {
               CACHE_REBUILD_EXECUTOR.submit(() -> {
                   Thread.sleep(200);
                   this.saveShopToRedis(id, 30L);
                   return null;
               });
           } finally {
               unlock(lockKey);
           }
       }
       return shop;
       ```

   * 缓存重建就是重新查数据库再写回缓存，直接复用 `saveShopToRedis`。

   * 实际过期时间应设 30 分钟，测试时设 30 秒或 20 秒以便观察重建效果；重建里加 `Thread.sleep(200)` 是为了模拟缓存延迟，延迟越长越容易出现线程安全问题。

   * 释放锁用 `try-catch Throwable` 加 `finally` 完成，不释放别人下次就进不来。

   * > **结论**：无论获取锁成功还是失败，最终都要返回店铺信息，只不过成功了要多干一件事（开启独立线程）；返回的这个店铺信息其实是个过期的数据。

### 压测与结论

   * Redis 清空后，单元测试插入的那条数据设置的逻辑过期时间只有 10 秒、理论上早该过期，但它依然还在 Redis 里——这就是逻辑过期：物理上没有 TTL，可以认为是永久存在，逻辑上已过期。

   * 一致性测试：先把数据库里的"102 茶餐厅"改成"103 茶餐厅"，让数据库与缓存不一致。

   * JMeter 用 100 个线程、1 秒执行完，QPS 约 100（1000 个太多，JMeter 结果面板写不下会覆盖前面的结果）。

   * 结果：一开始查到的都是旧的"102 茶餐厅"，到 47、48 左右变成"103"——因为重建延迟是 200ms，第一次请求触发重建，200ms 后更新完成，之后的请求才查到最新数据，存在一段时间的不一致。

   * 日志里数据库最后只执行了一条 SQL，证明并发是安全的、只会有一次重建，但一致性确实存在问题。

## 缓存工具类的封装

### 四个方法

   * | 方法 | 它做什么 | 搭档 |
     | :--- | :--- | :--- |
     | `set` | 把任意 Java 对象序列化为 JSON 字符串，存在 String 类型的 key 上，并设置 TTL 过期时间 | 与 `queryWithPassThrough` 配对，解决缓存穿透 |
     | `setWithLogicalExpire` | 和它类似，最大的区别是不设 TTL，而是设置逻辑过期时间 | 与 `queryWithLogicalExpire` 配对，解决缓存击穿 |
     | `queryWithPassThrough` | 给个 key 帮你查，把查到的结果反序列化为指定的类型，并利用缓存空值解决穿透，未命中就去查数据库 | — |
     | `queryWithLogicalExpire` | 与上面基本一致，区别是最后利用逻辑过期解决缓存击穿 | — |

   * 为什么 `set` 要接受任意对象：不能要求调用方传字符串，序列化动作交给工具类，对调用方做简化。

   * 为什么取的时候必须指定类型：工具类并不知道要操作的数据是什么类型，存的时候是任意类型、取的时候也是任意的就没法反序列化，所以要求使用时指定类型。

### 两个存的方法

   * 工具类叫 `CacheClient`，加 `@Component` 交给 Spring 维护，加 `@Slf4j` 便于记录日志；`StringRedisTemplate` 用构造函数注入，字段可定义成 `final`。

```java
public void set(String key, Object value, long time, TimeUnit unit) {
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(value), time, unit);
}

public void setWithLogicalExpire(String key, Object value, long time, TimeUnit unit) {
    RedisData redisData = new RedisData();
    redisData.setData(value);
    redisData.setExpireTime(LocalDateTime.now().plus(unit.toSeconds(time)));
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(redisData));
}
```

   * `StringRedisTemplate` 要求 String 类型，直接传 `Object` 会报错，必须先用 `JSONUtil.toJsonStr` 序列化。

   * 过期时间参数模仿 Spring 的 API 风格：先时间值、再时间单位 `TimeUnit`。

   * `setWithLogicalExpire` 参数列表与 `set` 完全一样，只是实现不同：把 value 封装进 `RedisData` 再存，就带上逻辑过期了。

   * 传进来的 `time` 带单位、不能假定是秒，要用 `TimeUnit.toSeconds()` 转换；既然 value 已封装进 `RedisData`，写 Redis 时就不该再序列化 value，而要写 `RedisData`。

### 泛型：返回值与 id 都不确定

   * 返回类型不能是 `Shop`（那是具体业务），用泛型 `R`（return），由调用方传 `Class<R>` 告诉真实类型，做泛型的推断。

   * 除了 id 还要有 key 前缀 `keyPrefix`——id 是查数据库用的，查 Redis 还要前缀拼 id 才是真正的 key。

   * id 也不一定是 Long，同样用泛型，再定义一个 `ID`；类头就是 `public class CacheClient<R, ID>`。

### 数据库查询交给调用者

   * 工具类不可能知道各个业务的数据库怎么查，这段逻辑交给调用者，由调用方把查询逻辑传递进来。

   * > **定义**：这段逻辑有参数（id）、有返回值（R），是有参有返回值的函数，Java 中对应的就是 `Function`。

   * 参数名 `dbFallback`，意为数据库降级的后备逻辑：先查 Redis，Redis 失败才走它。

```java
public R queryWithPassThrough(String keyPrefix, ID id, Class<R> type,
                              Function<ID, R> dbFallback, long time, TimeUnit unit) {
    String key = keyPrefix + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, type);
    }
    if (json != null) {
        return null;
    }
    R r = dbFallback.apply(id);
    if (r == null) {
        stringRedisTemplate.opsForValue().set(key, "", time, unit);
        return null;
    }
    this.set(key, r, time, unit);
    return r;
}
```

   * 第 3 步写成 `json != null` 的原因：存空值存的是空（等于 null），所以 json 不为 null 时只剩下"空"这一种情况。

   * 时间与单位不能写死，由调用方传入，否则所有缓存都被迫用同一个时间；写入时直接复用已封装的 `this.set(...)`。

### queryWithLogicalExpire

```java
public R queryWithLogicalExpire(String keyPrefix, ID id, Class<R> type,
                                Function<ID, R> dbFallback, long time, TimeUnit unit) {
    String key = keyPrefix + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isBlank(json)) {
        return null;
    }
    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    R r = JSONUtil.toBean(JSONUtil.parseObj(redisData.getData()), type);
    LocalDateTime expireTime = redisData.getExpireTime();
    if (expireTime.isAfter(LocalDateTime.now())) {
        return r;
    }
    String lockKey = LOCK_KEY_PREFIX + id;
    if (tryLock(lockKey)) {
        try {
            CACHE_REBUILD_EXECUTOR.submit(() -> {
                try {
                    Thread.sleep(200);
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
                R newR = dbFallback.apply(id);
                this.setWithLogicalExpire(key, newR, time, unit);
                return null;
            });
        } finally {
            unlock(lockKey);
        }
    }
    return r;
}
```

   * 两个查询方法的参数列表完全一样；重建缓存其实是两个步骤——先查数据库，再写 Redis。

### 调用侧的样子

```java
@Resource
private CacheClient<Shop, Long> cacheClient;

@Override
public Shop queryShopWithPassThrough(Long id) {
    return cacheClient.queryWithPassThrough(
            CACHE_SHOP_KEY, id, Shop.class,
            id2 -> getById(id2),
            CACHE_SHOP_TTL, TimeUnit.MINUTES);
}

@Override
public Shop queryShopWithLogicalExpire(Long id) {
    return cacheClient.queryWithLogicalExpire(
            CACHE_SHOP_KEY, id, Shop.class,
            id2 -> getById(id2),
            20, TimeUnit.SECONDS);
}
```

   * 传递数据库查询逻辑用 Lambda `id2 -> getById(id2)`，也可用方法引用 `Shop::getById`；工具类里 apply 时执行的其实就是 `getById`。

   * 改造后业务类里不再需要线程池、`tryLock`、`unlock`，这些一并挪进工具类。

   * 逻辑过期方案必须先预热才能测：用单元测试注入 `CacheClient`，`getById` 拿到数据后调 `cacheClient.setWithLogicalExpire(CACHE_SHOP_KEY + 1, shop, 10, TimeUnit.SECONDS)`，时间设短一点便于观察重建。

   * 验证：查不存在的 id 第一次会存空值、日志里有一条 SQL，之后狂刷都不再查询；逻辑过期方案用 100 线程跑完，日志里数据库只执行了一次，说明工具类同样解决了击穿。

### 封装里最难的两处

   * 一是返回值类型与 id 类型都不确定，要善于利用泛型，由调用者告知真实类型从而做出泛型推断。

   * 二是封装查询逻辑要牵扯数据库查询而工具类并不知道怎么查，解法是让调用者把这段逻辑以函数形式传进来，用到函数式编程；因为有参有返回值，正好对应 `Function`。
