# 秒杀异步化与 Redis 消息队列

## 同步秒杀流程与性能瓶颈

* **秒杀下单**

    * > **定义**：接口接收一个 `voucherId`，业务核心只有两件事——扣减该优惠券的库存、把用户抢购的优惠券信息写入订单完成创建。

    * 条件：因为是秒杀业务，额外加两条限制——库存绝对不能出现超卖，必须判断库存是否充足；一个用户对一张优惠券只能下一单，即一人一单。

    * 机理：查询优惠券（读数据库）→ 判断秒杀时间与库存是否充足 → 尝试获取分布式锁 → 查询订单判断一人一单（读数据库）→ 扣减库存（写数据库）→ 创建订单（写数据库）→ 释放锁。

    * 规则：整条链路串行执行，一个环节执行完再执行下一个，请求总耗时等于每一步耗时之和。

* **同步秒杀的性能瓶颈**

    * 条件：查询优惠券、查询订单、扣减库存、创建订单四步全部访问数据库。

    * 机理：数据库本身并发能力较差，扣库存与创建订单还是写操作，为避免并发安全问题又加了分布式锁，三者叠加导致耗时长、并发能力弱。

    * 数值：改造前压测（1000 个已登录用户的 token、券库存 200）最小耗时 126 ms，最大 800 多 ms，平均 400 多 ms，吞吐量 1000/s。

    * 边界：吞吐量随并发量升高只会越来越低。

    * > **提示**：压测耗时波动大的原因是压测工具的并发并非一次性发出全部请求，而是一开始少、后来越来越多，CPU 需要在多个线程之间来回切换，导致单个请求的处理耗时增加。

## 异步秒杀思路

### 把业务拆成前台与后厨

* **购买资格判断**

    * > **定义**：判断这个人能不能买，依据是库存够不够、这个人买没买过。

    * 边界：耗时短，对应饭店里前台小姐姐接待顾客、点餐、收钱。

* **真正下单**

    * > **定义**：扣减库存与创建订单，是真正落库的动作。

    * 边界：耗时长，是对数据库的写操作，对应饭店里后厨做饭。

* **拆分后怎么"交给两个人"**

    * 机理：执行代码的是线程，把两块业务交给两个线程即可——主线程判断购买资格，判断通过后再由独立线程处理耗时较久的减库存与下单。

    * 边界：用户不必等待后厨，拿到结果即可离开，单位时间内能接待的请求数大幅提高。

### 资格判断搬进 Redis

* **为什么用 Redis 做资格判断**

    * 条件：拆分后前台仍需访问数据库，性能依旧受数据库限制。

    * 结论：把优惠券信息、订单信息缓存到 Redis，把秒杀资格判断放到 Redis 里做，主线程进来先找 Redis 完成判断，判断完前台工作即结束。

* **异步必须是独立线程，不是同步调用**

    * > **易错点**：不能"调完 Redis 再去调扣库存下单"，那样又变成串行一条龙，性能没有增加反而降低；这里必须开独立线程执行。

* **写库的时效性要求**

    * 规则：返回订单 id 的那一刻秒杀业务已经结束，用户已可拿 id 去付款，因此何时把优惠券信息、用户信息写入数据库完成下单减库存没有那么重要，完全可以按照数据库能承受的频率去写。

    * 边界：想提高写库性能可以多开几个线程，或把单条写改成批量写。

### 队列与返回的订单 id

* **队列里存什么**

    * 机理：有资格时先记录优惠券信息、用户信息（谁买了什么），再记录订单 id（相当于叫号），把这些存进一个队列；将来开启独立线程读取队列里的信息完成下单，相当于后厨墙上贴的点餐列表。

* **订单 id 的两个作用**

    * 规则：一方面用户可以拿这个订单 id 去付款，另一方面拿到 id 就代表真的抢单成功。

    * 边界：此时真正的订单还没创建，但后续会确保它一定会被创建。

* **异步化带来的收益**

    * 结论：一方面缩短了秒杀业务流程、大大提高并发能力，另一方面减轻了数据库压力。

## 秒杀资格数据在 Redis 中的组织

### 库存：普通 String

* **库存 key**

    * 规则：库存只是一个数值，用普通 string 结构即可，key 为 `seckill:stock:` 加优惠券 id，value 为库存值。

    * 判断方式：做库存判断时看这个值是否大于零，大于零代表库存充足。

    * > **易错点**：判断用户确实有购买资格之后，必须把 Redis 里的库存值减一（预减库存）；否则值永远不变，库存判断形同虚设。

### 一人一单：必须是 Set

* **订单 key**

    * 规则：在 Redis 里记录当前优惠券被哪些用户购买过，用 Set 集合保存用户 id，key 为 `seckill:orders:` 加优惠券 id。

    * 条件：选 Set 是因为要同时满足两点——一个 key 里能保存很多值（集合），且用户 id 不能重复（唯一性）。

    * 判断方式：用户再来时判断其 id 在该集合里是否存在，存在即重复下单，拒绝购买。

    ```text
    seckill:stock:9     (String)  100          ← 9 号券的库存
    seckill:orders:9   (Set)     {5, 12, 88}  ← 买过 9 号券的用户 id
    ```

### 资格判断的五步与返回值

* **判断流程**

    * 规则：一先判断库存是否充足（值是否大于零），不足则返回 `1`；二判断一人一单（用户 id 是否在集合中），存在则返回 `2`；三扣减库存（不是真正扣数据库，而是把 Redis 里的值减一）；四把用户 id 存入该优惠券的集合，作为下一次判断的依据；五返回 `0` 代表有购买资格。

    * 条件：对 Redis 的判断步骤多、流程长，必须确保这段流程的原子性，因此用 Lua 脚本实现，不需要写 Java 代码。

| 返回值 | 含义 | 后续处理 |
| :--- | :--- | :--- |
| `0` | 有购买资格 | 保存订单信息入队，返回订单 id |
| `1` | 库存不足 | 返回异常信息 |
| `2` | 重复下单 | 返回异常信息 |

* **新增秒杀券时写入库存**

    * 机理：新增秒杀优惠券的同时，把库存信息一并保存到 Redis，用 `stringRedisTemplate.opsForValue().set(SECKILL_STOCK_KEY + voucher.getId(), voucher.getStock().toString())`。

    * 边界：不需要配置过期时间，库存可以永久保存在 Redis，将来需要移除该券信息时手动删除即可。

    * 提示：key 前缀与订单 key 都定义到 Redis 常量类中，如 `SECKILL_STOCK_KEY`。

## Lua 脚本实现资格判断

### 参数列表与 key 拼装

* **脚本参数**

    * 规则：只有两个 ARGV 参数，没有 KEYS——`ARGV[1]` 是优惠券 id，`ARGV[2]` 是用户 id。

    * 机理：优惠券 id 不是 key 只是一个 id，所以在脚本里拼接出 key 即可；订单集合的 key 同样由优惠券 id 拼出，只是前缀不同，无需再传第三个参数。

    ```lua
    local voucherId = ARGV[1]
    local userId    = ARGV[2]

    local stockKey = 'seckill:stock:'  .. voucherId
    local orderKey = 'seckill:orders:' .. voucherId
    ```

    * > **易错点**：Lua 里拼接字符串不是用加号，而是用两个点 `..`。

### 脚本逻辑

* **五段逻辑**

    * 规则：取库存值判断、判断用户是否下单、扣减库存、保存用户 id、返回成功，共三个出口。

    ```lua
    -- 3.1 判断库存是否充足
    if tonumber(redis.call('get', stockKey)) <= 0 then
        return 1
    end

    -- 3.2 判断用户是否下单
    if redis.call('sismember', orderKey, userId) == 1 then
        return 2
    end

    -- 3.3 扣减库存（incrby 是加，加 -1 就是减一）
    redis.call('incrby', stockKey, -1)

    -- 3.4 保存用户 id 到订单集合
    redis.call('sadd', orderKey, userId)

    -- 3.5 抢购成功
    return 0
    ```

    * > **易错点**：Redis 存取拿到的都是 string，`get` 的结果不能直接与数字比较，必须先 `tonumber` 转成数值再比较。

    * 规则：判断成员用 `SISMEMBER`，存在返回 `1`、不存在返回 `0`；下单时改用 `SADD` 把用户 id 加入集合。

    * 规则：库存是 string 结构，扣减用 `incrby` 加 `-1` 实现减一。

    * > **提示**：脚本有三个出口，成功那一支千万别漏掉——漏了 `return 0`，Java 侧会把所有情况都当成失败。

### Java 侧执行脚本

* **加载与执行**

    * 机理：用静态代码块加载脚本，`DefaultRedisScript<Long>` 指定结果类型为 `Long`，脚本位置用 `ClassPathResource("seckill.lua")`。

    * 规则：调用 `stringRedisTemplate.execute(script, keys, args...)`，第二个参数是 key 集合——该脚本没有 KEYS，要传 `Collections.emptyList()` 而不是 `null`；第三个参数起是 ARGV，依次传优惠券 id 与用户 id 的字符串形式。

    * > **易错点**：`execute` 的第二个参数千万不要传 `null`，要传 `Collections.emptyList()`。

    ```java
    private static final DefaultRedisScript<Long> seckillScript;

    static {
        seckillScript = new DefaultRedisScript<>();
        seckillScript.setLocation(new ClassPathResource("seckill.lua"));
        seckillScript.setResultType(Long.class);
    }
    ```

    ```java
    Long result = stringRedisTemplate.execute(
            seckillScript,
            Collections.emptyList(),
            voucherId.toString(),
            userId.toString()
    );

    int r = result.intValue();
    if (r != 0) {
        if (r == 1) {
            throw new RuntimeException("库存不足！");
        } else {
            throw new RuntimeException("不能重复下单！");
        }
    }

    long orderId = idWorker.nextId(RedisConstants.ORDER_KEY);
    return orderId;
    ```

    * 规则：结果不为零即无资格，为 `1` 抛库存不足，其余（即 `2`）抛不能重复下单；为零则生成订单 id（id 算法前缀为 `order`）并返回。

    * > **提示**：先打通资格判断再补队列部分，这叫分批测试——一次全写完出 bug 无法定位。

* **资格判断改造后的性能**

    * 数值：最小耗时 24 ms（原 126 ms），最大 559 ms（原 800 多 ms），平均 176 ms（原 400 多 ms），吞吐量 1500/s（原 1000/s）。

    * 边界：若 Redis、数据库部署在同一台机器上，CPU 压力较大；真实环境资源分离部署时性能还会更好。

## 用阻塞队列实现异步下单

### 队列与入队

* **阻塞队列（BlockingQueue）**

    * > **定义**：当一个线程尝试从队列获取元素而队列中没有元素时，该线程被阻塞，直到队列中有元素才被唤醒并获取元素。

    * 条件：订单不是一直都有——有人下单才有，没人下单就没有，所以用阻塞队列刚刚好。

    * 数值：元素类型为 `VoucherOrder`，实现选最简单的 `ArrayBlockingQueue`，初始化大小给 `1024 * 1024`。

    * > **注意**：队列长度不能给得太大，太大会消耗过多内存，要给一个适当的值。

    * 规则：调用 `offer` 方法把封装好的订单信息存入队列，抢单流程即完成。

* **VoucherOrder 封装的内容**

    * 规则：订单 id、用户 id、优惠券 id 三项。

### 线程池与线程任务

* **线程池**

    * 规则：创建名为秒杀订单处理器的线程池，用 `Executors.newSingleThreadExecutor()` 取单线程即可——处理订单速度不需要特别快，慢慢处理即可。

* **线程任务**

    * 规则：任务是一个实现 `Runnable` 的类（如 `VoucherOrderHandler`），`run` 方法里 `while (true)` 死循环，先 `orderQueue.take()` 取订单，再调用 `handleVoucherOrder` 创建订单。

    * > **提示**：`while (true)` 不会给 CPU 带来巨大负担，因为没有元素时 `take()` 会卡在那里，有元素才能往下走。

    * 边界：取订单与处理订单的异常只需记录日志，不向外返回——异步处理没有前端可返回。

* **任务何时启动**

    * 条件：用户一旦开始秒杀就会往队列里加订单，因此任务必须在类初始化之后就开始运行。

    * 规则：定义 `init` 方法并加 `@PostConstruct` 注解，表示当前类初始化完毕后执行，在方法里 `submit` 提交该任务。

### 异步化后的代码改动

* **用户 id 不能再从 ThreadLocal 取**

    * 条件：处理订单的是线程池里的全新子线程，不是主线程，`ThreadLocal` 与线程绑定，子线程取不到用户。

    * 规则：用户 id 必须从 `VoucherOrder` 里取（`order.getUserId()`），不能再走 `UserHolder`。

    * > **易错点**：`UserHolder.getUser().getId()` 在子线程里拿到的是空值。

    ```java
    // ✘ 子线程里拿不到，ThreadLocal 是跟线程绑定的
    Long userId = UserHolder.getUser().getId();

    // ✔ 订单是谁抢的就从订单里取
    Long userId = order.getUserId();
    ```

* **事务代理对象要在主线程提前获取**

    * 机理：`TransactionSynchronizationManager` 底层同样通过 `ThreadLocal` 获取，子线程里拿不到事务代理对象，事务无法生效。

    * 规则：只能在主线程里提前获取代理对象（`SpringUtil.getBean(VoucherOrderService.class)`），再交给后续线程使用。

    * 边界：两种传递手段都可以——把代理对象传进队列，或放到当前类的成员变量里，子线程取现成的代理对象。

* **createVoucherOrder 的改造**

    * 规则：入参由 `Long voucherId` 改为整个 `VoucherOrder` 对象；方法内部不再重新 `new` 订单对象，直接用现成的 `order`；返回值由 `Long` 改为 `void`，接口也一并改成 `void`。

    * 边界：异步执行后任何 `return` 都没有意义，判断失败记日志即可。

* **兜底判断**

    * 条件：理论上一人一单与库存判断在 Lua 里已做过，子线程里再做加锁与判断几乎不可能触发。

    * 规则：仍然保留加锁、一人一单判断、库存判断，作为一种兜底，以防万一 Lua 判断出现意外。

### 改造后的实测

* **单请求**

    * 数值：拿到订单 id，响应时间约 20 ms；同一用户再次请求提示不能重复下单。

* **压测**

    * 数值：平均响应时间 216 ms，最小值 17 ms。

    * 边界：平均值比只做资格判断时略高，是因为异步下单本身要占用 CPU；但相比最早的同步处理（平均四五百毫秒）仍有极大提升，且受限于单机性能。

## 阻塞队列方案的两个问题

### 内存限制

* **问题机理**

    * 条件：使用的是 JDK 的阻塞队列，占用的是 JVM 内存。

    * 规则：不加以限制时，高并发下会创建无数订单对象放入队列，可能导致内存溢出；因此创建时要设置队列长度上限。

    * 边界：队列一旦存满，再有新订单就塞不进去了。

### 数据安全

* **两类不一致**

    * 规则：基于内存保存订单信息，服务突然宕机则内存中所有订单信息全部丢失——用户已被告知成功并可付款，后台却没有订单数据。

    * 规则：线程从队列取出一个订单任务后若发生异常未执行成功，该任务已从队列移除、以后再也不会执行，任务等于丢失。

* **结论**

    * 两种情形都会导致数据不一致，解决这两个问题的最佳方案是使用消息队列。

## 消息队列

### 三个角色与 message broker

* **消息队列（message queue）**

    * > **定义**：字面意思是存放消息的队列；最简单的消息队列模型至少包含三个角色——生产者、消息队列、消费者，消息队列负责存储和管理消息。

    * 边界：它要做的事远不止存储，因此与其称消息队列，不如称消息的代理（message broker）——像快递公司一样负责揽件、运输保管、投递。

    ```text
      ┌────────────┐    发送消息    ┌────────────────┐    消费消息   ┌────────────┐
      │   生产者    │ ───────────▶ │    消息队列      │ ───────────▶ │   消费者    │
      │ （秒杀下单） │              │  message broker │              │ （独立线程） │
      └────────────┘              └────────────────┘              └────────────┘
                                        │
                                  揽件 · 运输保管 · 投递
    ```

* **快递柜类比**

    * 机理：没有快递柜时，快递员送货上门要等收件人，消费者上班惦记、回去又没人，两头难受；有了快递柜，快递员十分钟投完一上午的货，消费者收到短信后有空再取，零压力。

    * 结论：快递柜把"投递"与"取件"在时间上彻底解开，这正是消息队列解除耦合的直观体现。

* **秒杀套用该模型**

    * 机理：有人抢购时先判断购买资格，有资格不写数据库，而是把订单相关信息写入队列（相当于发一条消息）；另开独立线程作为消费者，不断从队列取消息完成下单写库。

    * 结论：抢单业务与写库业务分离、变成异步操作、解除耦合——抢单侧不写库并发能力大大提高，数据库侧可按自己节奏慢慢取单写入。

### 消息队列与阻塞队列的差异

* **两点不同**

    * 规则：消息队列是 JVM 以外的独立服务，不受 JVM 内存限制，解决了内存限制问题。

    * 规则：消息队列不只是存储数据，还要确保数据安全——存入的消息要做持久化，服务宕机或重启数据不丢；消息投递给消费者后要求消费者确认，未确认的消息依然留在队列中，下次会再投递，直到成功，即确保消息至少被消费一次。

    ```text
                JVM 阻塞队列          消息队列
      存储位置        JVM 进程内存          JVM 以外的独立服务
      内存上限        受 JVM 内存限制        不受 JVM 内存限制
      宕机 / 重启    队列中数据全部丢失      持久化，数据不丢
      异常中断        任务出队后即丢失        未确认的消息重新投递
      角色定位        一个数据容器            message broker：揽件 · 运输保管 · 投递
    ```

* **选型成本**

    * 边界：市面成熟的消息队列（如 RocketMQ、RabbitMQ、Kafka）需要额外搭建服务、学习新技术，有一定成本。

    * 结论：若已搭建 Redis 集群，可直接利用 Redis 实现消息队列，无需额外搭建服务。

### Redis 实现消息队列的三种方式

* **List**

    * 机理：利用双向链表模拟阻塞队列。

    * 边界：简单，但消息取出即消失，只能单消费者消费。

* **Pub/Sub**

    * 机理：发布订阅，`pub` 是 publish、`sub` 是 subscribe，一种典型的消息队列模型。

    * 边界：功能并不够完善。

* **Stream**

    * 机理：Redis 5.0 推出的最新模型。

    * 边界：相对比较完善，功能非常强大。

## 基于 List 的消息队列

### 用双向链表模拟队列

* **入口与出口不在同一侧**

    * 条件：队列要求先进先出，入口和出口不能在一起。

    * 规则：双向链表可在左侧或右侧操作，因此用 `LPUSH` 配 `RPOP`，或 `RPUSH` 配 `LPOP`——从左侧存、从右侧取（或反过来），自然实现先进先出。

    * > **易错点**：出队口和入队口若在同一侧，就成了栈（先入后出），不再是队列。

### 阻塞取消息

* **为什么需要 B 系列命令**

    * 条件：Java 代码要循环不断获取消息，取完之后希望卡住等待，实现阻塞队列效果。

    * 规则：`LPOP`/`RPOP` 是非阻塞的，没有消息时直接返回 nil；必须用带 `B`（block，阻塞）的 `BLPOP`/`BRPOP` 代替。

    * 数值：`BRPOP q1 20` 表示阻塞式地从队尾取，最多等 20 秒。

    * 机理：`pop` 是 remove-and-get，既取走元素又把它从队列移除，移除后别人就看不到了。

### List 方案的优缺点

* **优点**

    * 规则：存储在 Redis 中，不受 JVM 内存上限限制，解决了内存限制问题。

    * 规则：Redis 支持持久化，服务宕机、重启数据依然在，解决了数据安全问题。

    * 规则：它是队列，先进先出按顺序来，可以保证消息的有序性。

* **缺点**

    * 规则：消息丢失躲不掉——`pop` 是 remove-and-get，消息一旦取走就从队列移除，消费者取到后没来得及处理就挂掉，其他消费者再也拿不到。

    * 规则：只支持单消费者——一条消息被一个人拿走就从队列移除，无法实现一条消息被多个消费者消费。

| 维度 | 结论 |
| :--- | :--- |
| 内存上限 | 存储在 Redis，不受 JVM 内存上限限制 |
| 数据安全 | Redis 支持持久化，宕机重启数据依然在 |
| 消息有序性 | 队列先进先出，顺序有保证 |
| 消息丢失 | 躲不掉，`pop` 是 remove-and-get，拿到即出队 |
| 消费模型 | 只能单消费者，一条消息被拿走即从队列移除 |

## Pub/Sub 发布订阅

### 频道模型

* **Pub/Sub**

    * > **定义**：`publish` 发布与 `subscribe` 订阅的缩写，Redis 2.0 之后引入，基于「频道」这一订阅机制：一个消费者可以订阅一个或多个 channel，生产者每向某个 channel 发消息，所有订阅了该频道的消费者都会收到。

    * 机理：相当于订报纸——你告诉邮局要看体育频道，就收到体育那份；别人订财经频道，收到的是另一份。

* **与 List 的差别**

    * 规则：List 模式下一个生产者只能把消息发给一个消费者；Pub/Sub 模式下一个生产者可以发送消息给多个消费者。

    * 边界：不同生产者往相同频道发消息也可以，因此它是多生产、多消费。

### 命令与通配符

* **三个常用命令**

    * 规则：`SUBSCRIBE channel [channel ...]` 订阅一个或多个频道，可一次跟多个。

    * 规则：`PUBLISH channel message` 向某个频道发送一条消息。

    * 规则：`PSUBSCRIBE pattern [pattern ...]` 按通配符订阅，一条命令等于订阅了匹配该格式的所有频道。

    ```bash
    SUBSCRIBE channel [channel ...]   # 订阅一个或多个频道
    PUBLISH channel message           # 向某个频道发送一条消息
    PSUBSCRIBE pattern [pattern ...]  # 按通配符订阅频道
    ```

* **三种通配符**

    * 规则：`?` 代表一个字符。

    * 规则：`*` 代表零个或多个字符。

    * 规则：`[…]` 代表中括号内指定的字符之一。

| 通配符 | 含义 | 例子 |
| :--- | :--- | :--- |
| `?` | 一个字符 | `h?llo` 可以是 `hello`，也可以是 `hxllo` |
| `*` | 零个或多个字符 | `h*llo` 可以是 `hllo`（零个）、`hello`、`hellooooo`（多个） |
| `[…]` | 中括号内指定的字符之一 | `h[ae]llo` 匹配 `hello` 或 `hallo`，但不匹配 `hillo` |

### 消息分发

* **精确订阅与通配订阅**

    * 规则：消费者一 `SUBSCRIBE order.q1` 精确订阅，消费者二 `PSUBSCRIBE order.*` 通配订阅，`*` 是零个或多个，消费者二订阅的范围包含了消费者一订阅的频道。

    * 数值：往 `order.q1` 发消息，返回值为 `2`，两个消费者都收到；往 `order.q2` 发消息，返回值为 `1`，只有通配订阅的消费者二收到。

    * 边界：订阅命令执行后客户端会卡住等待读消息，这种模式天生就是阻塞式的。

### 三个缺点

* **不支持数据持久化**

    * 根源：List 本质是链表、本来用于数据存储，因此支持持久化；Pub/Sub 本身设计出来就是做消息发送的，发消息时若没有任何人订阅该频道，这条消息直接丢失。

    * 数值：消费者全部停掉后再 `PUBLISH`，返回值为 `0`，表示没有任何人收到、消息丢了；此时再把消费者启动也毫无意义。

    * 边界：连消息丢失都谈不上，因为它压根就不保存。

* **消息堆积有上限**

    * 机理：有消费者监听时消息会缓存在消费者客户端那里，客户端缓冲空间有上限，超出就丢。

    * 边界：消费者处理一条消息耗时一秒、这一秒内又来了十几条消息，这些消息全堆在客户端缓冲区。

* **安全性没有保障**

    * 规则：发完没人收直接丢，服务重启、宕机数据也没有了。

    * 结论：如果对可靠性要求较高，不建议使用 Pub/Sub，还不如使用 List。

## Stream 数据类型

* **Stream**

    * > **定义**：Redis 5.0 之后引入的全新数据类型，和 String、List、Sorted Set、Hash 类似是用来做数据存储的，因此支持数据持久化。

    * 边界：它是专门为消息队列设计的数据类型，提供的命令与功能非常适合做消息队列，是 Redis 里功能最完善的消息队列。

### XADD 发送消息

* **XADD 的参数**

    * 规则：完整格式为 `XADD key [NOMKSTREAM] [MAXLEN [~|=] count] [ID id] field value [field value ...]`。

    * 规则：`key` 是队列名称；`NOMKSTREAM` 表示队列不存在时不自动创建（默认自动创建，一般不用管）；`MAXLEN` 设置队列中最大消息数量，超过且一直无人消费时旧消息会被剔除，不给值即不设上限。

    * 规则：`field value` 是消息体，一个键值对称为一个 entry，一条消息可以包含多个 entry（多个键值对）。

    ```bash
    XADD key [NOMKSTREAM] [MAXLEN [~|=] count] [ID id] field value [field value ...]
    ```

    * 数值：最简用法 `XADD s1 * k1 v1`，`*` 表示 id 由 Redis 自动创建，执行后立即返回自动生成的唯一 ID；`XLEN s1` 查队列中消息条数。

### 消息 ID

* **ID 的组成**

    * 规则：ID 由两部分组成、中间是短横——前半部分是毫秒时间戳，后半部分是递增的数字。

    * 规则：同一毫秒内添加的消息前半段相同、后半段不断递增；不同毫秒添加的毫秒值不同、后半段从 `0` 开始。

    * 边界：ID 非常重要，Stream 底层会基于 ID 形成树的结构方便查询消息；建议一律用 `*` 让 Redis 自动生成。

    ```text
    1650000000000-0     ← 某一毫秒的第 1 条
    1650000000000-1     ← 同一毫秒内继续递增
    1650000000000-2
    1650000001000-0     ← 到了下一毫秒，序号归零
    ```

### XREAD 读取消息

* **XREAD 的参数**

    * 规则：完整格式为 `XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]`。

    * 规则：`COUNT` 是一次最多读多少条；不给 `BLOCK` 就是不阻塞（有消息直接返回、没有返回空），给了 `BLOCK` 没消息就等待，等待时长给 `0` 表示永久等待。

    * 规则：`STREAMS key … id …` 是一个整体，key 可以指定多个，即同时监听多个队列；id 表示从第几个消息开始读。

    * 数值：起始 id 有两个特殊值——`0`（严格说是 `0-0`）代表从队列第一条消息开始读，`$` 代表从最新的一条（队列最后一条）开始读，一般指定 `$` 一直往后读最新。

    * > **提示**：Stream 里一条消息读完了不会删除，它永久存在于队列中，什么时候想读都可以来读。

* **阻塞读取的写法**

    * 机理：`XREAD COUNT 1 BLOCK 2000 STREAMS s1 $` 最长等两秒，期间另一客户端 `XADD` 一条新消息则立即收到。

    * 规则：命令只有两种结果——等待期内来了新消息返回内容，超过时长返回空；因此循环里判断是否为空，为空 `continue` 进入下一轮，不为空则处理消息，处理完再回来，如此永远监听消息。

### 单消费模式的特点

* **四条特点**

    * 规则：消息可回溯——读完不消失，永久保存在队列中，随时回去看。

    * 规则：消息可以被多个消费者读取——消息不消失，张三读完李四也能读。

    * 规则：消息可以阻塞读取，可以写出循环一直读。

    * 规则：消息有漏读的风险。

### 漏读风险

* **漏读的成因**

    * 条件：把起始 ID 指定为 `$` 代表读取最新消息，即队列中的最后一条。

    * 机理：消费者读到某条消息后进入处理，处理期间生产者连发多条新消息；处理完进入下一轮时 `$` 只给最后一条，中间几条被永久跳过。

    * > **易错点**：单消费模式下用 `$` 循环监听，中间的消息会被永久漏读，这种方式看起来很完美但并不可靠。

    ```text
    t0  队列 s1 = [ k3 ]
        消费者 XREAD ... $  ->  读到 k3，开始 handleMessage()
        （处理过程中，生产方连发 k4、k5、k6）
    t1  队列 s1 = [ k3, k4, k5, k6 ]
        消费者处理完，进入下一轮
        消费者 XREAD ... $  ->  只拿到 k6
        k4、k5 被跳过
    ```

    * 结论：以上属于 Stream 的单消费者玩法；解决漏读要靠消费者组。

## 消费者组

### 消费者组的三个关键机制

* **消费者组（consumer group）**

    * > **定义**：把多个消费者划分到一个组中，共同监听同一个队列。

* **消息分流**

    * 规则：队列中的消息会分流给组内不同消费者，而不是重复消费，从而加快消息处理速度。

    * 边界：同一组内的消费者之间是竞争关系，凡是进入该组的消息大家都可以去抢，一定程度上可避免消息堆积。

    * 例外：若就是想让一条消息被多个消费者消费，加多个消费者组即可。

* **消息标识**

    * 规则：消费者组会维护一个标识，记录最后一个被处理的消息。

    * > **注意**：这里记录的不是最新的消息，而是最后一个被处理的消息。

    * 机理：像书里夹的书签——消费者故障、宕机或处理期间来了很多新消息都没关系，凭这个标识就知道上次读到哪，下次接着读，确保每一条消息都会被消费，绝对不会漏。

* **消息确认**

    * 规则：消费者获取消息后消息处于 pending（待处理）状态并保存到 pending list；处理完要通过 `XACK` 确认，Redis 才把它标记为已处理并从 pending list 移除。

    * 机理：拿到消息后若宕机，消息不会消失而是留在 pending list；恢复后到该列表里查看，把上次没处理完的消息接着处理完即可。

    * 结论：消息确认机制确保只要拿到了消息就至少会消费它一次，不会出现拿到不消费的情况。

### 创建与管理消费者组

* **XGROUP CREATE**

    * 规则：格式为 `XGROUP CREATE key groupname id [MKSTREAM]`；`key` 是队列名，`groupname` 是组名，`id` 决定该组从哪儿开始监听。

    * 规则：起始 id 给 `$` 表示从队列创建那一刻开始、即最新的（最后一个）消息开始；给 `0` 表示从队列第一个消息开始、从头消费。

    * 边界：队列中没有消息，或队列中已有很多消息而那些消息不想消费，选 `$`；队列中已有消息还需要重新消费一遍，选 `0`。

    * 规则：`MKSTREAM` 表示创建消费者组时若队列不存在则自动创建队列；不给的话队列不存在就无法创建组。

    * 结论：`XGROUP CREATE` 加上 `MKSTREAM`，一条命令完成两个动作——建队列加建组。

* **组的其他子命令**

    * 规则：`XGROUP DESTROY` 删除消费者组，`XGROUP CREATECONSUMER` 给组里添加消费者，`XGROUP DELCONSUMER` 删除消费者。

    * 边界：一般不需要手动添加消费者——从组中指定一个消费者并监听消息时，若该消费者不存在会自动创建。

### XREADGROUP 与起始 ID

* **XREADGROUP 的参数**

    * 规则：格式为 `XREADGROUP GROUP group consumer [COUNT count] [BLOCK milliseconds] [NOACK] STREAMS key [key ...] id [id ...]`。

    * 规则：`group` 是组名，`consumer` 是消费者名称（不存在会自动创建）；`COUNT` 是查询数量；不给 `BLOCK` 为非阻塞（查不到返回空），给了值则等待指定毫秒数。

    * 规则：`NOACK` 表示不需要消费者确认，消息投递给消费者那一刻就自动确认，根本不会进入 pending list。

    * > **易错点**：`NOACK` 一般不要配置——给了它，拿到消息后挂掉，消息又没进 pending list，将来根本不知道哪条消息失败了，消息就丢了。

* **起始 ID 的含义**

    * > **定义**：在 `XREADGROUP` 里，`>` 代表从下一个未消费的消息开始。

    * > **易错点**：`>` 是从下一个未消费的消息开始，不是从最新消息开始；组内会维护标记记录上一次消费的是哪一条，指定 `>` 就从标记的下一个消息开始读，确保所有消息都会被消费。

    * 规则：除 `>` 以外的 ID（如 `0`）含义变为读 pending list 中已经获取但未确认的消息；给 `0` 就读 pending list 第一条，消费并确认后该条被移除，下次给 `0` 读到的就是新的第一条未确认消息。

    * 结论：正常情况下给 `>` 读未消费消息；出现异常时去 pending list 里读拿到了但未处理的消息。

### 组内消息分流

* **分流演示**

    * 规则：组内某消费者连续读到 `k1`、`k2` 后，另一消费者来读拿到的是 `k3` 而不是 `k1`。

    * 机理：一个组内只有一个标记，不管是谁消费的，只要消费到那里就标记起来；下一个消费者不论是谁，都从标记的下一条开始。

## 消息确认与 pending list

### XACK

* **XACK**

    * > **定义**：`XACK key group id [id ...]`，把一个待处理的消息标记为已正确处理的消息，使其从 pending list 移除。

    * 规则：`key` 是队列名称，`group` 是组名称，后面指定要确认哪条消息的 ID，可以一次确认多条。

    * 数值：`XACK s1 g1 k1id k2id k3id k4id k5id` 返回 `5`，说明五条消息全部确认掉。

    * 边界：读了很多消息却从未确认是不行的——读一条一定要确认一条，代表正常处理了。

### XPENDING

* **XPENDING**

    * 规则：格式为 `XPENDING key group [[IDLE min-idle-time] start end count [consumer]]`。

    * 规则：`IDLE min-idle-time` 是空闲时间，即获取消息到确认之前的这段时间，给 `5000` 表示只要空闲超过 5000 ms 的消息。

    * 规则：`start` 与 `end` 是 ID 范围，`-` 表示最小、`+` 表示最大；`count` 是获取数量；`consumer` 指定查哪个消费者的 pending list。

    * 边界：每个消费者都有自己的 pending list。

    * 数值：不给空闲时间、最小到最大取十条、不指定消费者，即 `XPENDING s1 g1 - + 10`，返回 pending list 中所有未确认消息。

* **重读 pending list 里的消息**

    * 规则：把 `XREADGROUP` 里的 `>` 改成 `0`，读到的是 pending list 中的第一条消息，可再次处理；处理成功后再 `XACK` 确认，pending list 即清空。

### 正常与异常交织的处理流程

* **流程要点**

    * 规则：正常情况下用 `>` 获取所有未消费消息，处理完 `XACK` 确认；确认过程中出现异常（Java 里表现为抛出异常被 catch），消息进入 pending list，此时把最后那个 ID 从 `>` 改成 `0`，转去取 pending list 里的异常消息，处理完确认掉，再改回 `>` 恢复正常。

    * 规则：内层循环取不到消息才跳出——出了异常 pending list 里一定有消息，第一次肯定取得到；处理成功确认后消息被移除，下次就取不到，于是跳出内层循环回到外层。

    * 边界：内层处理又抛异常则 `continue` 再次去 pending list 取，一直循环直到该消息处理成功为止。

    * 边界：若反复几千次都不成功，可以人工介入并告警。

    ```text
    读取：XREADGROUP ... STREAMS s1 >
                  |
           拿到消息了吗？
          no ──────┴────── yes
          │                │
     continue          处理消息
                          │
              ┌───────────┴───────────┐
              │                       │
           成功                  抛出异常
              │                       │
           XACK              消息滞留 pending list
              │                       │
       回到外层循环      读取：... STREAMS s1 0
                                      │
                               拿到消息了吗？
                          no ──────┴────── yes
                              │                │
                        跳出内层循环        重新处理
                        回到外层循环              │
                                            成功 / 再次异常
                                                │
                                           XACK / continue
    ```

    * 结论：正常情况下一定确认、异常情况下去 pending list 再读再确认，可以确保消息至少被消费一次。

## 三种模式对比与选型

* **List 模式**

    * 规则：利用 List 数据结构模拟消息队列，本身是数据存储模式，因此支持持久化；`BLPOP`、`BRPOP`、`BLMPOP` 支持阻塞读取。

    * 边界：存储上限是 Redis 对 List 的内存上限，但可以有多个消费者同时取，堆积问题有办法缓解。

    * 边界：没有消息确认机制——它本身不是消息队列，取完就移除，后续处理一概不管；因此也不支持回溯。

* **Pub/Sub 模式**

    * 规则：不支持持久化，服务重启、宕机都会导致数据丢失；阻塞读取支持（订阅端阻塞）。

    * 边界：消息堆积能力最差，本身没有存储能力，消息最多在消费者端做缓冲且空间非常有限；没有消息确认机制，发出去没人收直接丢弃；不支持回溯。

    * 结论：三种里功能最差劲。

* **Stream 模式**

    * 规则：消息持久化、阻塞读取都支持；堆积受队列长度上限约束，不设上限时可存空间较多，且可用消费者组分流加快处理、减少堆积。

    * 规则：有消息确认机制（`XACK` 加 pending list，确保至少消费一次）；消息支持回溯。

| 能力 | List | Pub/Sub | Stream |
| :--- | :--- | :--- | :--- |
| 数据持久化 | 支持 | 不支持 | 支持 |
| 阻塞读取 | 支持（`BLPOP`/`BRPOP`） | 支持（订阅端阻塞） | 支持（`XREAD` 的 `BLOCK`） |
| 消息堆积 | 受 List 内存上限约束，多消费者取可缓解 | 最差，仅消费者端有限缓冲 | 受队列长度上限约束，消费者组可分流 |
| 消息确认 | 无 | 无 | 有（`XACK` + pending list） |
| 消息回溯 | 不支持（取出即移除） | 不支持 | 支持 |
| 漏读风险 | 无 | 无（但会丢消息） | 单消费 `$` 有，消费者组无 |

* **消费者组的额外收益**

    * 规则：具备 `XREAD` 单消费模式的所有优点并弥补其缺点——消息可回溯（别的组可以来拿）、组内消费者竞争提高处理速度避免堆积、可阻塞式循环读取避免 `while` 盲等、没有消息漏读风险、有消息确认机制确保至少消费一次。

* **选型建议**

    * 结论：在 Redis 三种消息队列里推荐使用 Stream 模式。

    * > **提示**：业务庞大、对消息队列要求更严格时应使用更专业的消息队列（如 RabbitMQ、RocketMQ），原因是 Stream 的持久化依赖 Redis 自身持久化、仍有丢失风险；确认机制只支持消费者确认而不支持生产者确认（生产者发消息过程中丢失无法处理）；消息的事务机制、多消费者下的消息有序性等问题也需要更强大的消息队列支持。

    * 边界：中小型企业对队列要求不多时，Stream 已能满足业务需要。

## 用 Stream 重做异步秒杀

### 建立队列与消费者组

* **建队列的时机**

    * 条件：队列只需要在一开始创建一次，创建完再也不用管，没必要专门写一段 Java 代码，直接用命令行创建。

    * 规则：创建用 `XGROUP CREATE stream.orders g1 0 MKSTREAM`——`stream.orders` 是队列名，`g1` 是消费者组名，`0` 是起始 ID（全新队列可以从零开始读），`MKSTREAM` 表示队列不存在时自动创建。

### Lua 脚本内直接发消息

* **为什么在脚本里发消息**

    * 机理：消息里必须带上订单信息（`voucherId`、`userId`、`orderId`），既然这些信息脚本里都有，直接在脚本里发消息可以让 Java 代码要做的事更少，还少一次 Java 与 Redis 之间的往返。

* **脚本的改造**

    * 规则：参数由两个增加到三个——`ARGV[1]` 优惠券 id、`ARGV[2]` 用户 id、`ARGV[3]` 订单 id。

    * 规则：在原来判断成功即 `return 0` 的地方，先加一个发消息的动作。

    ```lua
    local voucherId = ARGV[1]
    local userId    = ARGV[2]
    local orderId   = ARGV[3]

    redis.call('xadd', 'stream.orders', '*',
        'userId',    ARGV[2],
        'voucherId', ARGV[1],
        'id',        ARGV[3])
    ```

    * > **注意**：`XADD` 的参数顺序是先队列名，再消息 ID（`*` 表示由 Redis 生成），再后面一堆 key-value 对。

* **订单字段命名**

    * 规则：消息里订单 id 的 key 建议直接叫 `id` 而不是 `orderId`——订单实体 `VoucherOrder` 里的成员变量本来就叫 `id`，保持一致将来往对象里存更方便。

    * 结论：脚本执行完且结果为 OK，就同时代表两件事已完成——用户有购买资格，消息也已发出；业务侧只要判断结果 OK 就可以直接返回。

### Java 侧调用脚本

* **传参的改动**

    * 规则：订单 id 要提前生成，挪到执行脚本之前（与获取用户放在一起），作为第三个参数传入。

    * > **易错点**：Lua 脚本里的参数都是字符串，Long 类型的订单 id 要通过 `String.valueOf` 转成字符串再传，忘了这一步脚本直接报错。

    ```java
    execute(LUA_SCRIPT,
            Keys.empty(),
            String.valueOf(voucherId),
            String.valueOf(userId),
            String.valueOf(orderId));
    ```

### 消费者线程读取消息

* **读取命令**

    * 规则：完整命令为 `XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS stream.orders >`——`GROUP g1 c1` 说明读取的是哪个组、消费者叫什么；`COUNT 1` 读一条；`BLOCK 2000` 没消息最多等两秒；`STREAMS` 后跟队列名与读取标识。

    * > **注意**：最后的 `>` 代表读取最近一条未消费的消息；另一个标识 `$` 代表最新的消息，对应 `ReadOffset.latest()`，这里要的是 `>`。

    * 边界：消费者名字可以写死成 `c1`，将来应该配到配置文件里——启动多节点时消费者名字应各不相同才不冲突。

* **Java 里的三段对应关系**

    * 规则：RedisTemplate 把 Stream 操作封装在 `opsForStream` 里，它没有单独的 read group，而是统一的 `read`，参数分成三段理解。

    * > **易错点**：`Consumer` 要引 Spring 的那个（`org.springframework.data.redis.connection.stream.Consumer`），不是 Lettuce 里的，找错类编译不过。

    * 规则：读取选项用 `StreamReadOptions.empty().count(1).block(...)`，`block` 接收 `Duration`（周期，可带天、小时、毫秒、秒、纳秒等单位），这里给 `Duration.ofSeconds(2)`。

    * 规则：偏移量用 `StreamOffset.create(Q_NAME, ReadOffset.lastConsumed())`，`lastConsumed()` 就是 `>`，`latest()` 是 `$`。

| 命令里的这一段 | 对应的 Java 类 | 填法 |
| :--- | :--- | :--- |
| `GROUP g1 c1` | `Consumer` | `Consumer.from("g1", "c1")` |
| `COUNT 1 BLOCK 2000` | `StreamReadOptions` | `StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2))` |
| `STREAMS stream.orders >` | `StreamOffset` | `StreamOffset.create(Q_NAME, ReadOffset.lastConsumed())` |

    ```java
    List<MapRecord<String, Object, Object>> messages = stringRedisTemplate.opsForStream().read(
            Consumer.from(GROUP, CONSUMER),
            StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
            StreamOffset.create(Q_NAME, ReadOffset.lastConsumed()));

    if (messages == null || messages.isEmpty()) {
        // 没有消息，继续下一次循环
        continue;
    }
    ```

    * > **提示**：返回结果是 List，因为 `count` 不一定是一，可能是多条；所以要判断集合有没有数据，为空就 `continue` 再来一次。

### 解析消息与确认

* **MapRecord 的结构**

    * 机理：取到的是 `MapRecord`，底层就是一个 Map——`record.getId()` 是消息 ID，`record.getValue()` 是键值对的集合。

    * 规则：`XADD` 发的是 `key value key value` 形式，这里的 key 恰好就是订单类的三个成员变量，value 是对应值，所以返回的是 Map 形式。

* **Map 还原成订单对象**

    * 规则：用 `BeanUtil.toBean(map, VoucherOrder.class, true)` 把 Map 转成订单对象，第三个参数表示出错是否忽略，给 `true` 即忽略。

    ```java
    MapRecord<String, Object, Object> record = messages.get(0);
    Map<Object, Object> map = record.getValue();

    VoucherOrder order = BeanUtil.toBean(map, VoucherOrder.class, true);
    orderService.createOrder(order);
    ```

    * 边界：明确只读一条时，直接按角标取第 0 位即可。

* **ACK 确认**

    * 规则：确认用 `opsForStream().acknowledge(Q_NAME, GROUP, record.getId())`，三个参数分别是队列名、组名、消息 ID；消息 ID 直接从前面那个 record 里取。

    * 机理：告诉 Redis 哪条消息已处理完，它就把该消息从 pending 列表中确认掉。

### pending list 的处理

* **handlePendingList 的三处不同**

    * 规则：不再需要 `block` 阻塞——这个循环本身就是不停地取 pending 列表，阻塞在这里没有意义。

    * 规则：结束标识不再是 `>` 而是 `0`——传 `0` 时读的不是消息队列而是 pending list；`ReadOffset` 里只有 `$` 和 `>`，这里自己传 `"0"` 即可。

    * 规则：读到空是 `break` 而不是 `continue`。

    ```java
    private void handlePendingList() {
        while (true) {
            List<MapRecord<String, Object, Object>> messages = stringRedisTemplate.opsForStream().read(
                    Consumer.from(GROUP, CONSUMER),
                    StreamReadOptions.empty().count(1),                    // ① 不需要 block
                    StreamOffset.create(Q_NAME, ReadOffset.from("0")));    // ② 标识是 0
            if (messages == null || messages.isEmpty()) {
                break;                                                    // ③ 读到空是 break
            }
            MapRecord<String, Object, Object> record = messages.get(0);
            Map<Object, Object> map = record.getValue();
            VoucherOrder order = BeanUtil.toBean(map, VoucherOrder.class, true);
            orderService.createOrder(order);
            stringRedisTemplate.opsForStream().acknowledge(Q_NAME, GROUP, record.getId());
        }
    }
    ```

    * > **易错点**：pending list 里读不到消息说明没有异常消息了，此时应该 `break` 跳出循环回到外层继续处理正常消息；写成 `continue` 会空转。

* **处理 pending list 时又抛异常**

    * 规则：不需要递归调用自己——抛异常后打印日志并直接结束，又会进入下一次循环再次取到。

    * 边界：担心循环太频繁，可以稍微休眠一下（如 20 ms 或 50 ms）降低执行频率。

* **整体流程**

    * 规则：循环开头读取队列（标识 `>`、阻塞 2000 ms）；没有消息 `continue`；有消息则解析、创建订单、`XACK`；处理中抛异常且不确认则消息留在 pending list，进入 catch 调用 `handlePendingList()`；该方法以标识 `0`、不阻塞地读 pending list，读到就解析下单确认，读不到就 `break`，直到 pending list 清空。

    * 结论：这样可以确保异常的订单一定能够得到处理。

### 验证与压测

* **启动阶段的典型故障**

    * > **易错点**：启动即报队列或组不存在，常见原因是 Java 里的队列名变量写反了——一个变量名写错就什么都找不到，消息队列找不到自然报错。

* **功能验证**

    * 规则：下单成功后数据库订单表新增一条、库存扣一条，Redis 里库存扣一条、订单集合加一条；再点几次会提示下单失败，这是一人一单校验在起作用。

* **压测结果**

    * 数值：最小耗时 12 ms，最大 565 ms，平均耗时 110 ms。

    * 结论：订单没有出现超卖，订单数量刚好等于库存数量（201 条），Redis 库存减到零——既保证了不超卖、订单不超出，效率也相当不错。
