# Redis 底层数据结构与内存编码

## 原理篇的知识版图

* 原理篇分四大部分：数据结构、网络模型、通信协议、内存策略
    * 数据结构：深入源码看 String、Hash、List、Set 等类型的底层实现，涉及动态字符串、哈希表、压缩列表、快速列表、跳表等。
    * 网络模型：解答 Redis 是单线程还是多线程、单线程为何性能强，涉及五种 IO 模型与 select、poll、epoll
    * 通信协议：客户端与服务端之间的协议标准，最终用 Java 代码写一个 Redis 客户端与之通信
    * 内存策略：内存淘汰与内存回收，涉及 LRU、LFU 算法的底层差别
* 第一章的路线：先讲底层数据结构，再讲 RedisObject，最后分析 String、Hash、List、Set、SortedSet 如何基于上述结构实现

## 为什么 Redis 要自建字符串

### C 语言字符串的三个问题

* 获取长度要做运算：底层是字符数组，取长度要么用数组长度减一，要么遍历计数到结束标识，时间复杂度可达 $O(n)$
* 非二进制安全：以 `\0` 作为结束标识，字符数组中若出现 `\0`，读取到一半就被认为字符串结束
* 不可修改：双引号声明的字符串是字面值，保存在常量池，不能改其中某个字符，拼接要重新申请内存

### Redis 里万物皆可视为字符串

* key 一定是字符串
* String 的 value 是字符串；List、Set、SortedSet 存的是一个一个字符串，即字符串集合
* Hash 的 field 与 value 同样都是字符串
* > **结论**：Redis 里所有数据最终都会构建成 SDS

## 简单动态字符串 SDS

### 结构

* **简单动态字符串（Simple Dynamic String，SDS）**
    * > **定义**：Redis 自建的字符串结构，本质是结构体，由描述信息的 header 与保存数据的 body 两部分组成
    * `len`：buf 中已保存字符串的字节数
    * `alloc`：buf 申请的总字节数
    * `flags`：SDS 头的类型，单字节
    * `buf[]`：字符数组，保存真实数据，其申请多大、存什么、到哪结束全由 SDS 自己控制

```c
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;
    uint8_t alloc;
    unsigned char flags;
    char buf[];
};
```

* > **注意**：`len` 与 `alloc` 都不包含结束标识 `\0`；SDS 仍会在末尾带 `\0`，但只是为了兼容 C 语言，读取时不以它为准

### 五种头

* `sdshdr8` 的容量上限
    * `len` 与 `alloc` 各占 8 个比特位，最大值 $2^8 - 1 = 255$
    * 再去掉一个结束标识，`sdshdr8` 实际能保存的字符串是 254 字节
* Redis 定义了五种头：`sdshdr5`、`sdshdr8`、`sdshdr16`、`sdshdr32`、`sdshdr64`
    * 对应的 flags 值为 0、1、2、3、4
    * `sdshdr5` 已弃用，实际最小的就是 `sdshdr8`
    * `sdshdr16` 最大 $2^{16}-1 = 65535$，`sdshdr32` 最大 $2^{32}-1$
* 不统一用 64 位头的原因
    * 统一用 64 位则 `len`、`alloc` 各占 8 字节，头部开销过大
    * 执行 set 时大多数 key 不超过 255 字节，`sdshdr8` 最常用，头只占 1 字节

### 读法与二进制安全

* SDS 读取字符串以 `len` 为准：从起始位置读满 `len` 个字节即结束，中间有 `\0` 也继续读
* 由此获得二进制安全：不会出现读到一半被 `\0` 截断的情况
* 取长度不用遍历也不用运算，时间复杂度 $O(1)$

### 内存预分配

* > **定义**：内存预分配指 SDS 扩容时申请的内存大于实际使用量，以此减少内存分配次数
* 扩容规则
    * 新字符串小于 1 兆：新空间 = 扩展后字符串长度 × 2 + 1
    * 新字符串超过 1 兆：新空间 = 扩展后字符串长度 + 1 兆 + 1，不再翻倍
    * 加 1 是结束标识；`alloc` 记录的值不含结束标识
* 为什么要预分配
    * 申请内存要从用户态切换到内核态走一遍流程，非常消耗资源
    * 多申请一部分后，后续追加内容未超出预分配额度时就不必再次申请内存
* > **易错点**：`alloc` 与真正申请到的字节数差 1。例如 "hi,Amy" 是 6 字节，新空间是 $6 \times 2 + 1 = 13$，而 `alloc` 记的是 12

### SDS 的四条优势

* 获取字符串长度的时间复杂度是 $O(1)$
* 支持动态扩容
* 通过内存预分配减少内存分配次数
* 二进制安全，理论上可以保存任意字节数据

* > **提示**：SDS 能存图片、音频转成的字节，但不推荐这么做——Redis 基于内存，存大对象太浪费

## 整数集合 IntSet

### 结构与三种编码

* **整数集合（IntSet）**
    * > **定义**：Redis 中 Set 的一种实现方式，底层是整数数组，可看作一个特殊的整数数组
    * `encoding`：编码方式，占 4 字节
    * `length`：元素个数
    * `contents[]`：整数数组，保存元素，只能存整数

* 三种编码
    * `INTSET_ENC_INT16`：16 位、2 字节，有符号，范围 -32768 到 32767
    * `INTSET_ENC_INT32`：32 位、4 字节
    * `INTSET_ENC_INT64`：64 位、8 字节

* > **易错点**：`contents` 声明成 `int8_t` 并不表示元素只占一个字节。IntSet 不依赖 C 语言的数组函数，增删改查全部自己实现，元素真正占几个字节由 `encoding` 决定，`contents` 只是指向首元素地址的指针

* 元素默认按升序保存，Redis 保证元素的唯一性与有序性

### 统一编码与寻址

* 统一编码格式的目的：方便基于数组角标快速定位元素
* 寻址公式

$$\text{元素地址} = \text{起始地址} + \text{index} \times \text{每个元素的大小}$$

* > **注意**：`index` 表示元素与起始地址之间间隔了几个元素，这就是数组角标从 0 开始的原因；若角标从 1 开始，每次寻址都要多做一次减法，性能下降
* 头部固定开销：`encoding` 与 `length` 各 4 字节，头共 8 字节
    * 例：3 个元素、编码 INT16 时，contents 为 $2 \times 3 = 6$ 字节，整个 IntSet 占 $4 + 4 + 6 = 14$ 字节

### 动态升级

* > **定义**：当待插入元素超出当前编码范围时，IntSet 自动升级到合适的编码，所有元素统一按新编码重新保存

* 升级流程
    * 判断新元素落在哪个范围，确定新编码
    * 按新编码与元素个数重算并申请内存：`(原元素个数 + 1) × 新编码字节数`
    * 倒序把旧元素拷贝到扩容后的正确位置
    * 把新元素放入队首或队尾
    * 更新 `encoding` 与 `length`

* 必须倒序拷贝的原因
    * 正序拷贝时，扩容后的元素会覆盖后面尚未拷贝的旧元素数据
    * 倒序从最后一个元素开始搬，其后是空闲空间，不会覆盖任何有效数据

* 新元素的落点由正负决定
    * 新元素为负数：一定比所有元素小，放队首，`prepend = 1`，所有旧元素角标整体后移一位
    * 新元素为正数：一定比所有元素大，放队尾，`prepend = 0`，旧元素角标不变

* > **提示**：升级过程中元素角标不变，变的是每个元素占用的字节数

### 有序性靠二分查找保证

* `intsetSearch` 采用二分查找定位插入位置
    * 集合为空：直接返回 0 号位
    * 比最大元素还大：直接插最后；比最小元素还小：直接插最前
    * 否则二分：`mid = (min + max)` 右移一位，比较 `mid` 位置的元素与待插值，逐步收缩区间
* 查找命中则阻止插入（Set 元素唯一）；未命中则返回位置，用 `intsetMoveTail` 把该位置之后的元素整体后移一位再插入

### 适用边界

* 优势：数字小时用 16 位两字节存储，数据大时才升级，节省内存；二分查找保证查询效率
* 劣势：数据越多查询性能越差；作为数组需要连续内存空间，元素过多时不易一次性申请到
* > **结论**：IntSet 适合数据量不多的场景

## 字典 Dict

### 哈希表 DictHT

* **哈希表（dict hash table，dictHT）**
    * > **定义**：dict 底层的哈希表，本质是一个存放 dictEntry 指针的数组
    * `table`：二级指针，数组里保存的是指向 entry 的指针，而不是 entry 本身
    * `size`：数组有多少个格子
    * `sizeMask`：size 的掩码，值恒等于 size - 1
    * `used`：当前 entry 的个数

* > **注意**：`size` 永远等于 2 的 n 次方，只可能是 4、8、16 这类值，不会出现 5 或 6

* > **易错点**：`used` 可以大于 `size`——哈希冲突的元素会挂在同一角标形成链表

### 哈希节点 DictEntry

* `key`：键，一般是字符串，指向一个 SDS
* `v`：联合体，值可以是 `uint64_t`、`int64_t`、`double` 或 `void*`，四者只能取其一，不能同时成立
* `next`：指向下一个 entry 的指针，用于把冲突元素串成单向链表
* > **提示**：dict 的 key 与 value 类型都不确定；key 通常只是字符串，一个 SDS 指针足够，所以 key 不做成联合体

### 下标计算

* 计算方式：`index = hash & sizeMask`，与 `hash % size` 效果完全相同

* 与运算等价于求余的原因
    * size 是 2 的 n 次方，二进制是 1 后跟 n 个 0，减一后低 n 位全是 1
    * 与 0 做与运算必为 0，高位被抹掉；与 1 做与运算保持原值，余数被完整取出
    * 二进制中不足 size 的低 n 位，恰好就是 size 的余数

```text
  size     = ... 1 0 0        (= 4)    2 的 n 次方所在的那一位
  sizeMask = ... 0 1 1        (= 3)    2 的 n 次方以下，低 n 位全是 1

  hash     = 1 0 1 1 0 1 0 1  (= 181)
                      └─┬─┘
                    低 2 位 = 01 = 1        ← 181 % 4 = 1

  hash & 3 = 0 0 0 0 0 0 0 1  (= 1)        ← 与 181 % 4 完全相同
```

* > **提示**：size 必须是 2 的 n 次方、sizeMask 必须是 2 的 n 次方减一，这两条约束是绑在一起的。

### 插入与冲突处理

* 新建的 dict 数组初始化为 4 个格子，`size = 4`，`sizeMask = 3`
* 冲突处理：新 entry 占据该角标位置，旧的 entry 指针挂到新 entry 的 `next` 上
* > **注意**：新元素永远插在链表头部——头插只需改两个指针，尾插要先遍历到链表末尾

### 字典本体

* **字典（dictionary，dict）**
    * `type`：字典类型（dictType），不同场景可以使用不同的哈希函数
    * `ht[2]`：两张哈希表
    * `rehashidx`：rehash 进度，默认 -1，表示没有在 rehash
    * `pauseRehash`：rehash 是否处于暂停状态
* > **注意**：一般情况下只用 `ht[0]`，`ht[1]` 平时为 NULL，仅在 rehash 时启用

### 负载因子与伸缩时机

* **负载因子（load factor）**

$$\text{load factor} = \frac{\text{used}}{\text{size}}$$

* 扩容时机（每次新增时检查）
    * 负载因子 ≥ 1，且服务器没有在执行 BGSAVE、BGREWRITEAOF 这类后台命令
    * 负载因子 ≥ 5 时强制执行，不论是否有后台命令在运行
* 后台进程期间不扩容的原因
    * 这类后台进程 CPU 占用高、IO 读写多，此时做 rehash 很可能导致主进程被阻塞
    * 源码用 `dict_can_resize` 控制：后台命令执行时置 0，执行结束置 1
* 收缩时机（每次删除时检查）
    * 负载因子 < 0.1，且 `size > 4` 才收缩
    * `size` 已经等于初始大小 4 时不再收缩
    * 源码判据写成 `(used * 100 / size) < 10`，两边同除 100 即负载因子 < 0.1

### 对齐到 2 的 n 次方

* 初始化、扩容、收缩最终都走 `dictExpand`，收缩的 `dictResize` 内部仍调 `dictExpand`
* 传入的 size 由 `_dictNextPower` 对齐：从 4 起不断乘 2，找到第一个不小于传入值的 2 的 n 次方
    * 传入值 ≤ 4 直接返回 4；传入值 ≥ LONG_MAX 返回 LONG_MAX
* > **易错点**：扩容传的是 `used + 1`，但数组不会真的扩成 `used + 1`。例如 size 为 4、元素 5 个，传进去的是 6，最终 size 是 8
* `_dictExpand` 的两个前置检查
    * 正在 rehash 则直接返回
    * `ht->used > size` 则报错返回：这与让 size 大于 used 的目的相冲突

### rehash 与渐进式 rehash

* > **定义**：rehash 是把旧哈希表中的每个 key 按新的 sizeMask 重新计算索引、插入新哈希表的过程
* 为什么必须 rehash
    * 新表的 size 与 sizeMask 一定与旧表不同，而算角标要跟 sizeMask 做与运算
    * 拿着旧角标去新表查会查不到，所以每个 key 都要重算索引
* 新表先赋给 `ht[1]` 的原因
    * `ht[0]` 里是旧数据，新表先放进 `ht[1]`，再把 `ht[0]` 的数据逐个搬过去
    * 初始化场景（`ht[0]->table == NULL`）下新表直接赋给 `ht[0]`，不触发 rehash

* **渐进式 rehash**
    * > **定义**：把一次性的全量迁移拆成很多次，每次只迁移一个角标上的链表
    * 动因：数百万元素一次性 rehash 要几秒甚至更久，期间主线程被阻塞，新命令无法处理
    * 执行方式：每次增删改查时判断 `rehashidx > -1`，成立就迁移 `ht[0]->table[rehashidx]` 这一条链表，然后 `rehashidx++`
    * `rehashidx` 就是旧表的数组角标，从 0 开始逐个前进
    * 收尾：全部迁完后把 `ht[1]` 赋给 `ht[0]`，`ht[1]` 置 NULL，释放旧内存，`rehashidx` 置 -1

* > **提示**：每次只迁一个角标上的链表，数据量很小——某个角标挂太多元素早就触发扩容了。

### 迁移期间的操作落点

| 操作 | 查哪几张表 | 原因 |
| :--- | :--- | :--- |
| 新增 | 只进 `ht[1]`，不去旧表找 | 数据本来就要往新表搬，没必要在旧表白找一趟 |
| 查询 | 先 `ht[0]`，找不到再查 `ht[1]` | 元素要么在旧表要么在新表，不会两边都有 |
| 修改 | 同查询，先定位到再改 | 先找得到，才谈得上改 |
| 删除 | 同查询，找到即删 | 同一个道理 |

* > **结论**：新增只进 `ht[1]`，保证 `ht[0]` 只减不增，直到全部迁移完成

### dict 伸缩全景

| 场景 | 触发时机 | 目标 size | 新表先放哪 |
| :--- | :--- | :--- | :--- |
| 初始化 | 新建字典，`ht[0]->table` 为 NULL | 固定 4 | 直接给 `ht[0]` |
| 扩容 | 新增时 `used >= size` 且 `dict_can_resize` 为真 | 第一个 ≥ `used + 1` 的 2 的 n 次方 | 先进 `ht[1]` |
| 强制扩容 | 新增时 `used >= 5 × size`，不论后台进程 | 第一个 ≥ `used + 1` 的 2 的 n 次方 | 先进 `ht[1]` |
| 收缩 | 删除时负载因子 < 0.1 且 `size > 4` | 第一个 ≥ `used` 的 2 的 n 次方，不低于 4 | 先进 `ht[1]` |

* 与 Java HashMap 思路一致：数组加链表解决哈希冲突；区别是 Redis 用单向链表，没有红黑树

## 压缩列表 ZipList

### 设计动机

* dict 大量使用指针：数组里是指向 entry 的指针，entry 之间也靠指针成链
    * 一个指针一般占 8 字节
    * 内存不连续易产生碎片，指针本身也吃掉大量内存
* **压缩列表（ZipList）**
    * > **定义**：一整片连续内存的数据结构，可以看作一种特殊的双端链表，完全没有指针却具备双端链表的特性
    * 可以从头或尾任意一端压入、弹出
    * 支持从头到尾与从尾到头的正向、逆向遍历
    * 头尾增删复杂度是 $O(1)$

* > **易错点**：这里的"压缩"不是数据压缩，而是紧凑编码——用尽可能少的字节把值存下来

### 整体布局

| 字段 | 含义 | 字节数 | 取值范围 |
| :--- | :--- | ---: | :--- |
| `zlbytes` | 压缩列表占用的总字节数 | 4 | 无符号 32 位整数，最大 $2^{32}-1$ |
| `zltail` | 尾节点相对起始地址的偏移量 | 4 | 无符号 32 位整数，最大 $2^{32}-1$ |
| `zllen` | entry 节点的个数 | 2 | 最大 $2^{16}-1 = 65535$ |
| `entry` | 节点，个数与长度都可变 | 不定 | — |
| `zend` | 结束标识 | 1 | 固定 `0xFF` |

```text
 +----------+----------+---------+---------------------+--------+
 |  zlbytes |   zltail |  zllen  |       entries       |  zend  |
 |    4 B   |    4 B   |   2 B   |  length is variable |   1 B  |
 +----------+----------+---------+---------------------+--------+

       <-- 11 B header -->   head entry ... tail entry    fixed 0xFF
```

* 头尾固定开销共 11 字节（4 + 4 + 2 + 1）
* `zltail` 的作用：起始地址加上 `zltail` 即得尾节点起始地址，从而支持从尾部操作
* > **易错点**：`zlbytes` 与 `zltail` 存的是字节数，值可能到几千几百万，所以给 4 字节；`zllen` 只存个数，2 字节够用——前提是不要在单个 key 里塞过多数据
* > **注意**：元素个数超过 65535 时 `zllen` 记录不了，真实个数必须自己遍历计算，又是一笔额外开销

### entry 的三段式

```text
 +-------------------------+------------------+---------------------+
 | previous entry length   |     encoding     |       content       |
 |      1 B or 5 B         |  1 B / 2 B / 5 B |    real value data  |
 +-------------------------+------------------+---------------------+
```

* **previous_entry_length**
    * 记录前一个节点的长度，第一个节点的前驱长度记为 0
    * 前一个节点长度 < 254：用 1 字节保存
    * 前一个节点长度 ≥ 254：用 5 字节保存，第一字节固定 `0xFE`，后 4 字节才是真实长度
    * 254 能当分水岭，是因为它刚好能塞进一个字节的上限
* **encoding**
    * 记录 `content` 的数据类型（字符串或整数）以及 `content` 的长度
    * 自身长度为 1、2 或 5 字节，由编码方式决定
* **content**
    * 真实数据，长度不定，由 encoding 中记录的长度决定
* 整个节点长度 = `previous_entry_length` 字节数 + `encoding` 字节数 + `content` 字节数
* > **提示**：entry 长度不固定正是省内存的关键——值大占字节多、值小占字节少，不会让 1 也占 8 字节

### 遍历与寻址

```text
   起始地址
      |
      v
 +-------+-------+-------+-------+
 |entry 0|entry 1|entry 2|entry N|      一整片连续内存
 +-------+-------+-------+-------+
 |<--L0-->|<--L1-->|<--L2-->|<--LN-->|

 正向：next(Ei) = addr(Ei) + 总长度(Ei)
 逆向：prev(Ei) = addr(Ei) - previous_entry_len(Ei)
```

* 前进就是"当前地址加长度"，后退就是"当前地址减长度"，两者都只需一次加减法
* 与链表的对比
    * 链表每个节点要保存前驱与后继两个指针，共 16 字节
    * ZipList 记录长度最少 1 字节、最多 5 字节，能达到同样的寻址效果

### 小端字节序

* `encoding` 与 `previous_entry_length` 都采用小端字节序存储
* > **定义**：小端字节序按计算机的习惯从低位向高位保存，低地址处先放低位字节
* 例：十六进制 `0x1234` 中 `12` 是高位字节、`34` 是低位字节，小端序下先存 `34` 再存 `12`
* > **提示**：小端字节序只影响一个多字节数值内部的字节摆放顺序，不改变字段之间的先后顺序

### 字符串的 encoding

| `encoding` 开头 | `encoding` 总长度 | 用于记录长度的位数 | `content` 长度上限 |
| :--- | ---: | ---: | :--- |
| `00` | 1 字节 | 剩余 $8-2=6$ 位 | $2^6-1=63$ 字节 |
| `01` | 2 字节 | 剩余 $16-2=14$ 位 | $2^{14}-1=16383$ 字节 |
| `10` | 5 字节 | 后 4 字节共 32 位 | 可表示到 $2^{32}$ |

* 高两位是类型标识：`00`、`01`、`10` 都表示字符串，同时决定 encoding 自身占几字节
* > **提示**：一般情况下前两种编码就够用，第三种要到几百兆甚至上 GB 才用得上，早已违背 Redis 最佳实践

### 整数的 encoding

* 两个二进制位共四种情况，`00`、`01`、`10` 已给字符串，整数只能是 `11` 开头

| `encoding` | 含义 | `content` 占用字节数 |
| :--- | :--- | ---: |
| `1100 0000` | 16 位整数 | 2 字节 |
| `1101 0000` | 32 位整数 | 4 字节 |
| `1110 0000` | 64 位整数 | 8 字节 |
| `1111 xxxx` | 4 位立即数 | 0（不存在 content） |

* 整数类型有限、最大 8 字节，所以整数编码固定 1 字节，且不再记录长度——看到编码就知道 content 占几字节

### 4 位立即数

* 以 `1111` 开头，后 4 个比特位直接记录数值本身，不再需要 `content`
* 可用编码值范围是 `0001` 到 `1101`（即 1 到 13），因为 `0000`、`1110`、`1111` 已被占用
* > **易错点**：4 位立即数没有 `content`，数值直接存在 encoding 里；存入的编码值比真实值大 1，还原真实值必须减 1
* 实际能表示的范围是 0 到 12

### 编码实例

* 存字符串 `ab` 与 `bc`
    * 每个 entry 4 字节：前驱长度 1 字节 + encoding 1 字节 + 内容 2 字节
    * `ab` 的 encoding 是 `00` 加 `000010`，即 `00000010` = `0x02`
    * `bc` 的前驱长度是 `0x04`，因为前一个 entry 整整占 4 字节
    * 列表总字节数 $4+4+2+4+4+1 = 19$，`zlbytes` 记 19（`0x13`），`zltail` 是 $4+4+2+4 = 14$，`zllen` 是 2，`zend` 是 `0xFF`

```text
 offset   0       4       8      10      14      18   19
         +-------+-------+-------+-------+-------+-----+
         |zlbytes|zltail |zllen  |entry  |entry  |zend |
         |  19   |  14   |  2    | "ab"  | "bc"  |0xFF |
         +-------+-------+-------+-------+-------+-----+
           4 B     4 B     2 B     4 B     4 B     1 B

   0x13 00 00 00 | 0x0E 00 00 00 | 0x02 00 | 00 02 61 62 | 04 02 62 63 | FF
   <- zlbytes ->  <-  zltail  ->  <-zllen->  <-  "ab"  ->  <-  "bc"  ->  <-zend->
```

* 存数字 2 与 5
    * 都在 0 到 12 范围内，用 4 位立即数编码，无 `content`，每个 entry 只占 2 字节
    * 实际值 2 的编码值是 3 → `1111 0011` = `0xF3`
    * 实际值 5 的编码值是 6 → `1111 0110` = `0xF6`
    * 列表总字节数 $4+4+2+2+2+1 = 15$，`zlbytes` 记 15（`0x0F`），`zltail` 是 $4+4+2+2 = 12$，`zllen` 是 2

```text
   0x0F 00 00 00 | 0x0C 00 00 00 | 0x02 00 | 00 F3 | 02 F6 | FF
   <- zlbytes ->  <-  zltail  ->  <-zllen->  <- 2 ->  <- 5 ->  <-zend->
```

### 连锁更新

* > **定义**：ZipList 在特殊情况下产生的连续多次空间扩展操作，称为连锁更新
* 触发过程
    * 存在 n 个连续的、长度都在 250 ~ 253 之间的 entry，刚好卡在 254 边缘
    * 在它们之前插入一个长度 ≥ 254 的新 entry
    * 后一个 entry 的 `previous_entry_length` 从 1 字节扩成 5 字节，自身长度 +4 变成 254
    * 254 又让再后面一个 entry 的记录超限，于是再 +4，一个传一个，整串全部跟着扩

* 代价
    * ZipList 是连续内存，多申请 4 字节意味着后面所有数据都要后移
    * 空间不足时要申请新内存并把整段数据搬过去，频繁产生内存申请、销毁与数据迁移
    * 内存申请与销毁牵扯内核态切换，对性能影响很大

* > **易错点**：连锁更新在新增节点和删除节点时都可能被触发，不只是插入时才有

* 发生概率与现状
    * 触发条件苛刻，需要连续多个长度恰在 250 ~ 253 之间的 entry，概率极低
    * Redis 作者并未解决该问题
    * 新版引入的 **listpack（紧凑列表）** 目前只在 stream 结构底层使用，list、set 等常见结构仍用 ziplist

### ZipList 的边界

* 优点：不用指针，内存占用低；内存连续，读写效率高于真正的链表
* 缺点：只能逐个遍历，节点过多时按值查找线性劣化；连续内存太大时不易申请到；存在连锁更新的可能。
* > **提示**：头尾两端增删是 $O(1)$，按值查找中间节点要逐个 entry 遍历——这是两个不同操作，并不矛盾

## 快速列表 QuickList

### 设计思路

* ziplist 的问题：数据量过大时，一次性申请大片连续内存的效率很低
* **快速列表（QuickList）**
    * > **定义**：Redis 3.2 之后引入的双端链表，链表中每一个节点都是一个 ziplist
    * 限制单个 ziplist 的大小，避免大块连续内存的申请问题
    * 用多个 ziplist 分片存储解决存储上限问题，再用链表把分片串起来便于管理与查找

```text
  head ◄────► Node1 ◄────► Node2 ◄────► Node3 ◄────► Node4 ◄────► tail
                │            │            │            │
              zl│          zl│          zl│          zl│
                ▼            ▼            ▼            ▼
           [ziplist]    [ziplist]    [ziplist]    [ziplist]
```

* > **结论**：QuickList 兼具链表与 ziplist 两者的优势

| | 链表 | ziplist |
| :--- | :--- | :--- |
| 优势 | 内存不用连续，理论上存储上限无限 | 内存占用少、碎片少，是连续空间 |
| 劣势 | 占用内存过多，内存碎片比较多 | 能存的数据量比较有限 |

### list-max-ziplist-size

* 配置项 `list-max-ziplist-size` 控制每个 ziplist 的大小，值可正可负
    * 正值：限制 ziplist 里的 entry 个数
    * 负值：限制 ziplist 总的占用内存大小

| 配置值 | 每个 ziplist 的内存上限 |
| :--- | :--- |
| `-1` | 不超过 4 KB |
| `-2` | 不超过 8 KB（默认值） |
| `-3` | 不超过 16 KB |
| `-4` | 不超过 32 KB |
| `-5` | 不超过 64 KB |

* > **提示**：限制个数不如限制内存——限制 1000 个 entry 时，若每个 entry 都很大，最终内存依然很大，推荐用负数形式

### list-compress-depth

* 配置项 `list-compress-depth` 控制压缩深度，取值 0 到 4
    * 链表访问多集中在首尾，中间节点访问频率低，所以只压中间

| 配置值 | 含义 |
| :--- | :--- |
| `0` | 都不压缩（默认值） |
| `1` | 首尾各 1 个节点不压缩，其他全压 |
| `2` | 首尾各 2 个节点不压缩，其他全压 |
| `3` | 首尾各 3 个节点不压缩，其他全压 |
| `4` | 首尾各 4 个节点不压缩，其他全压 |

* > **易错点**：`0` 不代表全部压缩，而是代表都不压缩；正数才表示不压缩的节点个数

### 两个结构体

* `quicklist` 的字段

| 字段 | 含义 |
| :--- | :--- |
| `head` / `tail` | 指向链表头和尾，支持双向遍历 |
| `count` | 所有 ziplist 中 entry 的总数 |
| `len` | ziplist 的个数 |
| `fill` | 每个 ziplist 的大小上限，默认 -2 |
| `compress` | 压缩深度，默认 0 |

* > **易错点**：`count` 与 `len` 完全不同——10 个节点就是 10 个 ziplist，即 `len = 10`；所有 ziplist 内 entry 的累加值才是 `count`

* `quicklistNode` 的字段

| 字段 | 含义 |
| :--- | :--- |
| `prev` | 前向指针 |
| `next` | 后向指针 |
| `zl` | 指向该节点对应的 ziplist |
| `sz` | 当前 ziplist 占用的字节数 |
| `count` | 当前 ziplist 的 entry 个数 |
| `encoding` | 编码方式：ziplist 模式，还是用 LZF 压缩 |
| `container` | 容器类型，目前只有 ziplist 一种，其余是为将来预留 |
| `recompress` | 标记当前节点有没有被解压缩过 |

* 压缩后的节点仍是一个 ziplist，只是换成了压缩形态，读取时要先解压缩

## 跳表 SkipList

### 设计思路

* 传统链表查中间慢的原因：指针跨度恒为 1，只能一个一个遍历
* **跳表（SkipList）**
    * > **定义**：本质仍是链表，但元素按升序排列，且允许一个节点包含多个跨度不同的指针
    * 节点同时保存 score 与 ele，通过多级指针提升查询效率
* 层级与跨度
    * 最底层是一级指针，跨度都是 1，即原始链表
    * 越往上跨度越大，二级、三级指针跨度递增

```text
   level 2:  1 ──────────────► 10 ──────────────► 20 ──► 25
   level 1:  1 ────► 5 ────► 10 ────► 15 ──► 20 ──► 25
   level 0:  1 ─► 5 ─► 10 ─► 15 ─► 20 ─► 25     ← 原始链表，跨度都是 1
```

* 最多允许 32 级指针
    * 若每级跨度呈倍数递增，32 级指针的跨度约为 $2^{31}$
    * 允许存储的元素数量可达 $2^{32}$
* > **结论**：跳表增删改查效率与红黑树基本一致，但实现比红黑树简单得多，所以 Redis 用它做有序数据存储

### 两个结构体

* `zskiplist` 的字段
    * `header`、`tail`：头尾节点指针
    * `length`：节点数量
    * `level`：最大索引层级，列表越长层级可能越多，决定查询从第几层开始
* `zskiplistNode` 的字段

| 字段 | 含义 |
| :--- | :--- |
| `ele`（sds） | 真正保存的数据，是字符串 |
| `score`（double） | 得分，用来做排序和查找，相当于索引 |
| `backward` | 前向指针，可以倒着查 |
| `level[]` | 多级指针数组，每项是一个 `zskiplistLevel` |

* > **提示**：多级指针做成数组而不是写死，是因为不同节点的层数可能不同
* `zskiplistLevel` 的两个字段
    * `forward`：真正的指针，指向下一个节点，但不一定是紧挨着的那个
    * `span`：跨度，表示该指针跨越了多少个元素

### 查找与排序

* 查找方式：从最高层出发，拿目标 score 与后继节点的 score 比较，更大就往后走，更小就降一层继续比较
* > **提示**：每一级指针指向的都是另一个 zskiplistNode，而不是 level 数组本身
* 节点按 score 升序排列
* > **注意**：score 相同时按 element 做字典排序
* 节点层数由 Redis 底层函数生成，虽称随机，实则是按算法推测较合适的层数

## RedisObject

### 五个字段

* **Redis 对象（redisObject，robj）**
    * > **定义**：Redis 中任意数据类型的键与值最终都会被封装成的统一结构体

```c
typedef struct redisObject {
    unsigned type:4;       /* 类型：4 个比特位 */
    unsigned encoding:4;   /* 编码：4 个比特位 */
    unsigned lru:LRU_BITS; /* LRU：24 个比特位 */
    int refcount;          /* 引用计数 */
    void *ptr;             /* 指向实际数据的指针 */
} robj;
```

| 字段 | 位数 / 字节 | 含义 |
| :--- | :--- | :--- |
| `type` | 4 bit | 对象类型，预定义值为 0~4，对应 String、List、Set、Sorted Set、Hash |
| `encoding` | 4 bit | 对象底层使用的编码 |
| `lru` | 24 bit | 最近一次被访问的时间，供内存回收使用 |
| `refcount` | 4 字节 | 引用计数 |
| `ptr` | 一般 8 字节 | 指向真实数据的指针，void 类型，可以指向任意东西 |

* `refcount`：对象每被引用一次加一，每释放一次引用减一，减到零时证明无人引用，内存被回收
* 头部开销：`type` + `encoding` + `lru` 共 32 位即 4 字节，加 `refcount` 4 字节、`ptr` 8 字节，共 16 字节，这还不含 ptr 指向的那片内存
* > **结论**：每个 String 都要一个对象头，10 个字符串就是 160 字节的头部开销；存成一个 List 只需 16 字节头部。大量数据推荐用集合形式存储

### 十一种编码

| 编码 | 含义 | 状态 |
| :--- | :--- | :--- |
| `RAW` | SDS 动态字符串的其中一种编码 | 在用 |
| `INT` | 字符串的一种编码，同时也是整数类型的编码 | 在用 |
| `EMBSTR` | 字符串的一种编码 | 在用 |
| `HT` | hashtable 哈希表，底层就是 dict 字典 | 在用 |
| `ZIPLIST` | 压缩列表 | 在用 |
| `INTSET` | 整数集合 | 在用 |
| `SKIPLIST` | 跳表 | 在用 |
| `QUICKLIST` | 快速列表 | 在用 |
| `STREAM` | 最新引入的一种编码 | 在用，尚未使用 |
| `ZIPMAP` | 压缩映射 | 已经废弃 |
| `LINKEDLIST` | 双端链表，早期 Redis 会用到 | 已经废弃 |

* > **提示**：光 String 就占了三种编码：`INT`、`EMBSTR`、`RAW`

### 类型与编码的对应

| 数据类型 | 底层编码 |
| :--- | :--- |
| String | `INT`、`EMBSTR`、`RAW` 三种 |
| List | 3.2 以前是 `LINKEDLIST` 和 `ZIPLIST`；3.2 以后弃用，变成 `QUICKLIST` |
| Set | `INTSET` 和 `HT` 两种 |
| Sorted Set | `ZIPLIST`、`SKIPLIST`、`HT` 三种 |
| Hash | `HT` 和 `ZIPLIST` |

* > **提示**：Bitmap、HyperLogLog 底层就是 String，只是 String 的一种用法；Geo 底层是 Sorted Set，都不是新的数据类型

## String 的三种编码

### raw

* > **定义**：redisObject 头与 SDS 是两片独立的内存空间，中间靠 ptr 指针相连
* 创建时要申请两次内存（先 object 再 SDS），释放同样是两次
* 取到 object 之后想读 SDS 还要多一次指针寻址
* > **注意**：raw 编码下 SDS 字符串不允许超过 512 MB；这是上限，不代表应该真存这么大，太大就是 big key 问题
* SDS 自身构成：头信息（`len`、`alloc`、`flags`）+ 字符串本体 + 结束标识 `\0`

### embstr

* > **定义**：redisObject 头与 SDS 是一段连续内存空间，只需申请一次内存、释放一次
* 触发条件：SDS 字符串小于 44 字节
* 44 这个阈值的由来
    * 44 字节用 `sdshdr8`：`len` 1 字节 + `alloc` 1 字节 + `flags` 1 字节，头共 3 字节
    * 加结束标识 1 字节、字符串本体 44 字节，共 48 字节
    * 再加 redisObject 头 16 字节，合计 64 字节
    * 内存分配算法 jemalloc 按 $2^n$ 粒度分配，64 恰好是一个分片大小，不会产生内存碎片

| 组成部分 | 字节数 | 说明 |
| :--- | ---: | :--- |
| `sdshdr8.len` | 1 | 44 用一个字节就装得下 |
| `sdshdr8.alloc` | 1 | 申请的字节数 |
| `sdshdr8.flags` | 1 | 标记头类型 |
| 空字符 `'\0'` | 1 | SDS 的结束标识 |
| 字符串本体 | 44 | 待存储的内容 |
| redisObject 头 | 16 | 固定开销 |
| **合计** | **64** | |

* > **结论**：使用 String 时尽可能不要让字符串超过 44 字节，否则转成 raw，效率不如 embstr

### int

* > **定义**：把整数值直接存放在 redisObject 的 ptr 指针位置，不再有 SDS
* 触发条件：存储的字符串是整数值，且大小在 long max（Java 里 long 类型的最大值）范围内
* 原理：任意整数最多占 8 字节，而指针位置刚好 8 字节，完全放得下
* > **结论**：int 是三种编码中最节省内存的一种

### 用命令观察编码切换

```redis
127.0.0.1:6379> set name jack
OK
127.0.0.1:6379> object encoding name
"embstr"
```

* `jack` 是字符串且小于 44 字节，编码是 `embstr`
* 把值凑到 44 字节仍是 `embstr`；再多加一个字符凑够 45 字节，编码变为 `raw`
* `set age 123` 之后 `object encoding age` 返回 `int`，因为 123 是数字

## List 的编码

### 从需求反推

* List 最擅长首尾操作
    * `LPUSH` / `RPUSH` 从左侧或右侧插入，`LPOP` / `RPOP` 从左或右弹出
    * 从队首依次插入 e1、e2、e3 时，最后插入的在最前，看到顺序是 e1、e2、e3
    * 从队尾依次插入则按插入顺序排列
* 双向链表支持首尾操作，但节点内存独立、靠指针相连，占内存多且易产生碎片
* ziplist 省内存，但要申请连续内存，存储上限低
* **quicklist** 是链表与 ziplist 的结合
    * 首先仍是链表，支持双端访问
    * 链表中的每个节点不是一个普通节点，而是一个 ziplist
    * 单个 ziplist 存不下就多来几个，用链表串起来
* > **结论**：最近几个版本的 Redis 中，List 采用的都是 quicklist 编码

### 一次 LPUSH 的创建链路

* List 命令实现在 `t_list.c`，`lpush` 底层调用 `pushGenericCommand`
* **`pushGenericCommand`**
    * > **定义**：执行 push 操作的通用命令函数，通过 `where` 参数决定插到队首（HEAD）还是队尾（TAIL）
    * 参数 `xx`：为 true 时只有 key 已存在才执行 push，不存在直接结束；一般不传即为 false，此时 key 不存在会自动创建 list
* 客户端对象 `c` 与 `argv`
    * 客户端与服务端建立连接后被封装成 client 对象
    * 命令按空格切成 n 段放进 `argv` 数组，如 `LPUSH key v1 v2` 中 `argv[0]` 是命令、`argv[1]` 是 key、`argv[2]` 起才是 value
* 关键步骤
    * 元素大小校验：从 `c->argv[2]` 遍历到 `c->argc`，逐个取元素长度与配置上限比较；上限约为 $2^{32}$（会减 1024），基本可认为无限制，但元素最好小于 64 字节
    * `lookupKeyWrite(c->db, c->argv[1])`：`c->db` 是当前客户端访问的库（0 到 15），按库与 key 查找，返回的是 redisObject
    * `checkType(o, LIST)`：比较 redisObject 的 `type` 与期望类型，不相等直接报错返回
    * 对象为空且 `xx` 为 false 时调用 `createQuicklistObject` 创建
* > **注意**：Redis 内部万物皆对象，list 也是一个 redisObject，本质是指针指向一个 quicklist
* `createQuicklistObject` 内部
    * 先创建并初始化 quicklist 本身，拿到指向起始地址的指针
    * 再 `createObject` 创建 redisObject，两个参数分别是数据类型与真实数据指针
    * > **易错点**：`createObject` 初始化的是泛型编码，不对，所以要手动把编码重置成 `quicklist`
    * 最后对 quicklist 做一次 `setOptions`，写入 `list-max-ziplist-size`（默认 -2，即 8 KB）与压缩深度（默认 0，不压缩）

## Set 的编码

### 三个特征与选型的理由

* 不保证元素有序性，插入顺序与实际保存顺序都可能不一致
* 保证元素唯一性，已存在就不插入
* 支持交集、并集、差集
* > **结论**：`sadd`、`sismember`、`sinter` 底层都在判断元素是否存在，这类判断执行得非常频繁，所以 Set 需要高效的随机查询
* 跳表不合适：跳表元素有序、按 score 排序且要求数值，而 Set 不保证有序、元素也不一定是数值
* 唯一选择是哈希表，即 dict

### ht 编码下如何存单列

* 用 dict 的 key 保存 Set 的元素，value 统一给成 NULL
* > **提示**：与 Java 的 HashSet 复用 HashMap 的 key 是同一个道理

### intset 编码

* dict 的弊端：数组里是指向 dictEntry 的指针，每个 entry 都是独立内存空间，碎片化且指针多，内存占用高
* 触发条件：Set 中存储的所有数据都是整数，且元素数量不超过 `set-max-intset-entries`
* intset 底层可看作变长数组，按升序保存
    * 升序才能用二分查找快速查询，效率有保障
    * 插入前先查存在性，已存在就不存，唯一性得到保证
    * 作为数组是连续内存空间，比较省内存
* 代价：数据类型只能是整数，元素数量过多时查询效率会下降

### 编码转换

* 创建时的选择：`setTypeCreate`
    * value 的 sds 能解析成 long long → `createIntsetObject`：初始化 intset，`createObject(OBJ_SET, ptr)`，再把编码改成 intset
    * 不能 → `createSetObject`：初始化 dict，`createObject(OBJ_SET, ptr)`，最后把编码改成 ht
* > **注意**：intset 编码不是永久性的，两个条件任一被违背就转 ht；每次插入新元素都会检查，转换发生在 `setTypeMaybeConvert`
* 两条触发线
    * 待插入的 value 不是整数 → 先 `setTypeConvert(o, HT)` 转成 ht，再用哈希表的 add 插入
    * value 是整数 → 先 `intsetAdd` 插入，成功后再取服务器的 `set-max-intset-entries`，`intsetLen(intset) > max` 同样转 ht
* `set-max-intset-entries` 默认 512，可 `CONFIG GET` 查看、`CONFIG SET` 修改，也可改配置文件；该值超过 $2^{30}$ 时会被截成 $2^{30}$
* > **提示**：不建议把 `set-max-intset-entries` 调得太大，太大查询性能会受影响
* 转换实例：intset 中有 10、20、50（`encoding` 为 `int16`），插入字符串 `m1` 后新建 dict，四个 entry 的 key 分别是 10、20、50、m1，value 全为 NULL，redisObject 的 ptr 改指 dict，编码改为 ht

## Sorted Set 的编码

### 三个特征

* 每个元素包含 score 与 member 两部分，`ZADD z1 10 m1 20 m2 30 m3` 一次添加三组
* 根据 score 排序，值越小排名越靠前
* member 必须唯一，重复添加时新 score 会覆盖旧的。
* 要能根据 member 反查 score（`ZSCORE z1 m1`）

* > **提示**：ziplist 是压缩列表，zskiplist 是跳表，两者名字极易混淆，代码和配置项里不能混

### 为什么是 dict 加跳表

| 结构 | 可排序 | 键值存储 | 键唯一且能按 member 查 score |
| :--- | :--- | :--- | :--- |
| intset | ✓ 默认升序 | ✗ 只存整数 | ✗ |
| 跳表 zskiplist | ✓ | ✓ score + element | ✗ 只能按 score 查，按 member 查只能遍历 |
| dict 哈希表 | ✗ | ✓ | ✓ |

* 跳表查询时是拿 score 做大小判断，不能按 member 查 score，硬查只能把整表当普通列表遍历
* dict 能按键做哈希运算快速定位、能保证键唯一，但本身没有排序能力
* > **结论**：zset 同时用两种结构——dict 负责键值存储与键唯一性查询，zskiplist 负责排序与范围查询

### SKIPLIST 编码的内存布局

* zset 结构体维护两个指针：一个指向 dict，另一个指向 zskiplist
* 创建流程
    * 申请 zset 内存，创建 dict 赋给 `zs->dict`，创建跳表赋给 `zs->zsl`
    * 调用 `createObject`：`type = ZSET`，`ptr = zs`，`encoding = SKIPLIST`
* > **注意**：底层虽然有两种结构，但 `encoding` 只能写一个，所以写的是 SKIPLIST
* dict 中 key 保存 member、value 保存 score，拿 member 做哈希运算即可快速定位 score
* 跳表中每个节点保存 ele（即 member）与 score，按 score 升序，查第一名、最后一名与范围都很快
* > **易错点**：dict 和跳表各自存了一份 member 与 score，数据是重复存储的，再加上大量指针和链表，内存占用很高

### ziplist 编码

* 数据量不多时哈希表和跳表的性能优势并不明显，遍历与哈希查差别不大，因此改用省内存的 ziplist
* 两个使用条件
    * 元素数量不超过 `zset-max-ziplist-entries`，默认 128
    * 元素大小不超过 `zset-max-ziplist-value`，默认 64 字节
* > **注意**：一般不建议改这两个值，数据量再大 ziplist 性能会明显下降

* 初始化时的编码选择
    * `zset_max_ziplist_entries == 0` → 元素数量永远不可能小于阈值，等于禁用 ziplist，改用 dict + 跳表
    * 从 `c->argv` 取出的待插入元素长度超过 64 字节 → 用默认编码 dict + 跳表
    * 否则 → 使用 ziplist 编码
* 两个创建函数的区别
    * `createZsetZiplistObject`：底层没有 zset 这一层，redisObject 的 ptr 直接指向 ziplist，`encoding = ZIPLIST`
    * `createZsetObject`：ptr 指向 zset 对象，`encoding = SKIPLIST`

```text
  redisObject
 ┌──────────────────────────────────────┐
 │ type     : ZSET                       │
 │ encoding : ZIPLIST                    │
 │ ptr ───────────────┐                  │
 └────────────────────┼──────────────────┘
                      ▼
      ziplist（连续内存，内部没有任何指针）
   ┌────────┬───────┬──────┬───────┬───────┬──────┐
   │ <zl>   │ m1    │ 10   │ m2    │ 20    │ m3 … │ <zt>
   │ 头节点 │member │score │member │score  │      │ 尾节点
   └────────┴───────┴──────┴───────┴───────┴──────┘
                └─ 第 1 组 ─┘ └─ 第 2 组 ─┘
```

### ziplist 如何模拟键值对与排序

* ziplist 本身没有键值对概念、也没有排序能力，全靠业务逻辑模拟
* 把 member 与 score 紧挨着存进两个相邻 entry，每两个 entry 作为一组
* 插入时自己做排序：值越小越靠前，值越大越靠后
* 按 member 查 score 就从头遍历，找到 member 后它下一个就是 score
* > **结论**：数据量小时以节省内存为主要目标用 ziplist，数据量大时转成 dict + 跳表，牺牲内存换时间

### 编码转换

* `zsetAdd` 中的检查顺序
    * 当前编码已是 SKIPLIST → 已是最终编码，不用转换，直接添加
    * 当前编码是 ZIPLIST → 先 `zzlFind` 查元素是否已存在。
        * 已存在 → 不能重复添加，只更新 score
        * 不存在 → 才判断要不要转换
* 三个转换条件，任一触发就 `zsetConvert` 转成 SKIPLIST
    * 当前元素个数 + 1 > max entries
    * 新元素大小 > max value（64 字节）
    * 兜底：整个 ziplist 的总大小超上限
* > **提示**：判断的是"当前元素个数 + 1"，因为元素添进去之后数量一定会加一，判的是加以以后的情况

## Hash 的编码

### 与 ZSet 的异同

* 相同点：都是键值对存储，都要根据键找值，都要求键唯一
    * `ZSCORE z1 m1` 是根据 member 查 score，`HGET user name` 是根据 field 查 value
* 差别一：zset 的值必须是数字（要做排序），Hash 的 field 与 value 可以是字符串也可以是数值，没有格式要求
* 差别二：zset 要按 score 排序，Hash 不需要排序
* > **结论**：Hash 的编码可以参考 zset，只需把跟排序有关的跳表去掉

### ziplist 编码

* 数据量较少时默认使用 ziplist，相邻两个 entry 分别保存 field 与 value，每两个 entry 作为一组
* `createHashObject` 的流程：先申请一个 ziplist 拿回指针，再创建 redisObject，`type = HASH`，`ptr` 指向该 ziplist，`encoding = ZIPLIST`
* > **结论**：Hash 初始化时的默认编码就是 ziplist

### 转成 HT 的两个条件

| 条件 | 配置 | 默认值 |
| :--- | :--- | ---: |
| 元素数量超过阈值 | `hash-max-ziplist-entries` | 512 |
| field 或 value 任一超过阈值 | `hash-max-ziplist-value` | 64 字节 |

* 转成 HT 后 ptr 指向 dict，encoding 改为 HT，不再需要跳表
* 阈值比 zset 大（512 对 128）的原因：Hash 不用排序，五百多个元素用 ziplist 遍历效率仍可接受

### 源码里的分工

* `hsetCommand` 是执行 HSET 命令的函数；凡以 Command 结尾的函数都是执行 Redis 命令的函数
* **`hashTypeLookupKeyForOrCreate`**
    * > **定义**：把查找与创建合二为一的函数，先尝试找，找不到就创建
    * 流程：`lookupKeyWrite(c->db, key)` → 检查 o 是不是 Hash 类型，不是直接 return → 为空则 `createHashObject` 并 `dbAdd` 建立 key 与对象的映射 → 回到主流程再检查一次 o 是否为 NULL，仍为 NULL 说明 key 类型不正确，直接结束
* `hashTypeTryConversion`：只检查元素大小
    * 先判断 o 的 encoding 是不是 ZIPLIST，不是就结束（本来就不是 ziplist 没什么可转）
    * `for (i = start; i <= end; i++)` 遍历 `argv`：`start` 为 2，因为 0 是命令名、1 是 key，都无关；`end` 是 argv 数组长度减一
    * 逐个元素：不是 SDS 就结束；是 SDS 则用 `sdslen` 取字节数，超过 64 字节就转码成哈希表
    * 没超标的把单个元素大小累加起来，循环结束再看总大小是否超标，超标同样转 HT
* `hashTypeSet`：插入并检查元素数量
    * `ziplistIndex(0)` 取头节点指针；为 NULL 说明 ziplist 一个元素都没有，是全新 ziplist，直接加
    * 不为 NULL 则 `ziplistFind` 查 field 是否已存在。
        * 没找到 → 新增：先 push field 再 push value，两者紧挨着
        * 找到了 → `update = 1`（1 代表修改、0 代表新增），执行 replace 覆盖
    * 插入完成后用 `hashTypeLength` 检查元素长度是否超出 max entries，超出就转成哈希表
* > **易错点**：转码前不做数量检查——那时元素还没真正插入，且 field 已存在时插入只是修改，ziplist 长度不会变，所以数量检查只能放在真正插入之后

### 调参建议

* `hash-max-ziplist-entries` 与 `hash-max-ziplist-value` 都可用 `config get` 查看、`config set` 修改，也可改配置文件
* > **提示**：一般 512 和 64 就够了，一定要调也不建议超过 1000——ziplist 太大既影响性能，连续内存也不好申请

### ZSet 与 Hash 阈值对照

| | ZSet | Hash |
| :--- | :--- | :--- |
| 小数据编码 | ziplist | ziplist |
| 大数据编码 | dict + zskiplist | dict（不需要跳表） |
| 元素数量阈值 | `zset-max-ziplist-entries` = 128 | `hash-max-ziplist-entries` = 512 |
| 元素大小阈值 | `zset-max-ziplist-value` = 64 字节 | `hash-max-ziplist-value` = 64 字节 |
| 需要排序吗 | 需要，按 score | 不需要 |
