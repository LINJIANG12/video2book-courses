# Redis 最佳实践：键值设计、批处理与服务端调优

## 键值设计

### key 的格式与长度

* **分段式 key**

    * > **定义**：以冒号分隔、按「业务名:数据名:ID」分段组织的命名方式。

    * 规则：第一段是业务名称，第二段是数据名称，最后是 ID。

    * 边界：不强制三段，业务复杂或可能出现重复时可以再加更多段。

* **长度与字符约束**

    * 数值：整个 key 最好不要超过 44 字节，超过时把部分段的单词做简写。

    * 禁止：绝对不要包含特殊字符。

### value 的选型与过期

* **value 选型原则**

    * 规则：一定要选择合适的数据结构，不能什么数据都往 String 里塞。

    * 规则：遇到较大的数据要做合理拆分，拒绝 BigKey。

    * > **易错点**：不要因为说了 String 不好就全改成 Hash，Hash 也不是万能的；Hash 里的 entry 数量也要有上限，最好不要超过 1000。

* **过期时间**

    * 规则：不太重要的数据都应该设置过期时间，到期后自动剔除，将来要用再重新写入。

    * > **易错点**：不设过期时间等于什么都往 Redis 里扔且扔完不管，Redis 也不是垃圾桶，塞满之后就再也写不进去了。

## BigKey 的判定

### 判定维度与安全上限

* **BigKey**

    * > **定义**：占用内存很大的 key；判定不看单一指标，而是「元素大小」与「元素数量」两个维度的综合结果。

    * 规则：单值类型（String）只看大小，集合类型主要看元素数量，两个维度都极端的最严重。

    * 数值：String 类型理论上限 512 MB，但到 5 MB 就已经是超级大的 key，不允许出现。

    * 数值：List、Set 这类集合的成员数达到 1 万个即被认定为 BigKey。

    * 数值：Hash 只有 1000 个 entry、但每个成员很大、合计 100 MB（乃至 10 MB）也算非常大。

| 类型 | 判定方式 | 安全上限 | 超过之后 |
| :--- | :--- | :--- | :--- |
| String | 看 value 大小（`STRLEN`） | 不超过 10 KB | 认定为 BigKey |
| 集合类型 | 看元素个数（`LLEN`/`HLEN`/`SCARD` 等） | 元素数小于 1000 | 认定为 BigKey |

### 怎么量出一个 key 多大

* **MEMORY USAGE**

    * 命令：`MEMORY USAGE key` 直接报出该 key 占用的字节数，集合类型同样适用。

    * > **易错点**：不推荐在生产上使用，因为它对 CPU 的使用率比较高。

* **用长度代替精确内存**

    * 规则：真正决定是不是 BigKey 的是 value 那一块，所以 String 看 `STRLEN`、集合类型只看元素个数即可，不一定非要用 `MEMORY USAGE`。

    * 命令对应：`LLEN`（List）、`HLEN`（Hash）、`SCARD`（Set）、`ZCARD`（Sorted Set）取成员个数。

    * 数值示例：`MEMORY USAGE name` 报 54 字节，而 `STRLEN name` 只有 4（两个汉字在 UTF-8 下各 2 字节），其余约 50 字节是 key 本身加上 key-value 整体的 Redis 数据结构元信息开销。

```bash
STRLEN name
LPUSH l2 a b
LLEN l2
MEMORY USAGE name
```

## BigKey 的危害

### 网络阻塞

* 条件：BigKey 体积特别大，一个 key 就可能占 5 MB，只要很小的 QPS 就足以把带宽占满。

* 数值示例：QPS 20 × 5 MB = 100 MB，把整台物理机 100 MB 的带宽吃干净。

* 边界：危害不止于 Redis，同一台物理机上部署的其他应用也全都无法请求网络。

```text
       客户端                                 Redis 所在物理机
   GET bigkey, QPS = 20                     整台机器带宽一共 100MB
           │                                        │
           └──────── 20 × 5MB = 100MB ──────────────►│
                                            一个 BigKey 就把 100MB 吃干净
                                            → 其他所有业务请求全都进不来
```

### 数据倾斜

* 机理：集群数据分片的最小单位是 key，插槽由 Redis 自动均衡分配，各节点插槽数量与 key 数量基本一致，但带 BigKey 的那几台机器数据量会明显超过其他机器。

* 后果：内存使用率远高于其他节点，要解决就不得不手动对插槽做重新分配，给运维平白增加麻烦。

### 主线程阻塞

* 条件：大型集合（如 1 万元素的 Sorted Set）与另一个 Set 做交集、并集或排序运算非常耗时，而 Redis 是单线程的，这段时间内其他请求无法被处理。

* 机理：BigKey 写入需要序列化、读取需要反序列化，数据量大时对 CPU 使用率也非常高，CPU 被占满后同机部署的其他应用同样受影响。

* > **结论**：三重灾难的共同点是损害不止于 Redis 自己，会沿着网络带宽、节点内存、主线程 CPU 一路扩散到整台物理机上的其他业务，所以 BigKey 必须找到并干掉。

## BigKey 的发现

### redis-cli --bigkeys

* 命令：`redis-cli -a 密码 --bigkeys`。

    * > **易错点**：`redis-cli` 本身是客户端命令，不能在 Redis 控制台里运行，必须打开一个全新的命令行窗口带参数执行。

* 输出：扫描全部 key 后给出每种数据类型的 Top One（占用内存最多的第一名），例如扫出 27 个 key、最大 List 3 个元素、最大 Hash 801 个元素、最大字符串 120 万字节、最大 Stream 1380 个元素、最大 Set 680 个元素。

* > **易错点**：只能看到第一名，第二名及以后看不到；第一名未必是 BigKey（如最大的 List 只有 3 个元素），第二名却有可能是，所以统计不完整，只能作基本参考。

### 自定义 SCAN 扫描

* **SCAN**

    * > **定义**：借助迭代器逐个扫描所有 key 的命令，一次只扫一小部分，不占用 Redis 主线程、不会导致阻塞。

    * 规则：扫描时指定游标 cursor，第一次给 0；下次以上一次返回的游标继续；游标回到 0 时证明全部扫描完毕。

    * > **易错点**：⚠️ 扫描不能使用 `KEYS *`，它一下子把所有 key 全取出来，数据量大时可能耗时几十秒甚至更久，期间主线程被阻塞，生产环境禁止使用。

```text
      cursor = 0
           │
           ▼
      ┌─────────┐   返回 (nextCursor, keys)
      │  SCAN   │──────────────────────┐
      └─────────┘                      │
           │                           ▼
   nextCursor != 0 ?        对这一批 key 逐个判断长度
           │                    超过阈值就打印出来
           ├── 是 ──► cursor = nextCursor，回到 SCAN
           │
           └── 否（nextCursor == 0）──► 全部扫描完毕
```

* 判定方式：拿到 key 后先 `type` 判断类型，再取长度与阈值比较，而不是用 `MEMORY USAGE` 精确算内存（那样 CPU 消耗太大）；即自定义编码 + `SCAN` 扫描 + 用长度判断。

* 数值：示例阈值取 String 10 × 1024（10 KB）、集合 500。

* 运行结果示例：找出 `k1`（String，120 万字节）、某订单 Set（680 元素）、另一 Set（500 元素）、两个 Hash（650 与 801 元素），第一名第二名都能拿到。

* 优势：凡符合 BigKey 的通通能扫出来，结果比 `--bigkeys` 完整。

* > **注意**：即便基于游标也不建议放到主节点执行，有主从时应放到从节点执行。

### 离线分析与网络监控

* **redis-rdb-tools**

    * 机制：解析 RDB 文件做离线分析，对 Redis 本身没有任何性能损耗。

    * 边界：因为是离线分析，时效性上有差异，拿到的不是最新的；运行环境为 Python，需要自行安装运行环境。

    * > **提示**：这种方式相对比较推荐。

* **网络监控告警**

    * 机制：监控进出 Redis 的网络数据，判断哪一次查询返回的数据特别大，从而找出 BigKey 并及时告警。

    * 边界：自己搭建实现更复杂；使用云服务时控制台里可直接定位，但要付出更高的成本。

## BigKey 的删除

### 拆而不是丢

* 规则：找到 BigKey 后要把它拆掉，但不是说这部分数据不要了，而是拆分后重新存储，把 BigKey 打散成不大的 key。

* 原因：像数十万元素的 Sorted Set 直接 `DEL` 耗时非常久，会导致主线程阻塞，删都不敢乱删。

### Redis 4.0 以后：UNLINK

* **UNLINK**

    * > **定义**：异步删除 key 的命令。

    * 机理：不用主线程，而是用一个额外的线程去删除；先把它标记成已删除即可，因此不会阻塞主线程。

    * 现象：`UNLINK name` 之后 `GET name` 已经拿不到值，但后台仍在异步删。

### Redis 4.0 以前：扫描 + 逐字段删

* 规则：key 大是因为元素多，那就先删元素而不是直接删 key——把所有字段删完之后它就不是 BigKey 了。

* 命令：Hash 用 `HDEL` 删除一个或多个字段；遍历集合用 `HSCAN`（Hash）、`SSCAN`（Set）、`ZSCAN`（Sorted Set），用法与 `SCAN` 完全一致，指定 key 加游标即可。

```text
        一个巨大的哈希（数十万元素）
                 │
                 │  直接 DEL → 主线程阻塞数十秒  ✗
                 ▼
        HSCAN key cursor  ──►  取出一批 field
                 │
                 ├──► HDEL key field1 field2 ...
                 │
           cursor != 0 ? ──是──► 继续 HSCAN
                 │
                 └──否（所有字段都删完了）
                              │
                              ▼
                      此时它已不是 BigKey
                      直接 DEL key 即可  ✓
```

## 数据结构选型

### 存储对象的三种方式

* **JSON 字符串**

    * 优点：实现简单，对象与 JSON 的序列化/反序列化方案非常成熟，不用考虑太多数据类型问题。

    * 缺点：数据耦合在一起，想改或删其中某一个字段做不到，只能把整个字符串重新覆盖，不够灵活。

* **字段打散成多个 key**

    * 优点：可以灵活访问任意字段。

    * 缺点：每存一个 key-value 都要保存大量元信息（key 的元信息、value 的元信息、底层字典信息等），key 越多无效数据越多，额外内存占用大——存一个数字 123 最终占了 48 字节就是元信息导致的。

    * 缺点：没有办法做统一控制，想拿一个对象的全部字段只能一条一条取。

* **哈希结构**

    * 优点：value 又是一个哈希，字段可任意单独访问，灵活性与打散方案一致。

    * 优点：底层采用 ziplist 压缩链表，对内存占用非常小，兼具省内存与灵活性。

    * 缺点：代码相对复杂，需要把对象转成哈希 Map，转换时要考虑对象的数据类型转换；但有工具类帮忙就不算问题。

| 存储方式 | 优点 | 缺点 |
| :--- | :--- | :--- |
| JSON 字符串 | 实现简单，序列化方案成熟 | 字段耦合，改/删一个字段要重写整个字符串 |
| 字段打散成多个 key | 可灵活访问任意字段 | key 暴涨导致元信息开销大；没法一次性拿全部字段 |
| 哈希结构 | 字段可单独访问 + ziplist 压缩省内存 | 代码稍复杂，需把对象转成 Map |

* > **结论**：存储对象时推荐使用哈希类型的数据结构。

### 哈希的 ziplist 条件与配置

* **entry**

    * > **定义**：哈希里一个 field-value 键值对就叫一个 entry。

    * 条件：当哈希里 entry 数量超过 500 时，它就会改用哈希表而不是 ziplist，因此不再有内存上的优势。

    * 数值：100 万 entry 的哈希最终占用 62.23 MB。

* **hash-max-ziplist-entries**

    * 命令：`CONFIG GET hash-max-ziplist-entries` 默认 500；`CONFIG SET hash-max-ziplist-entries 1000` 即可调整，动态修改不需要重启，重启后失效。

    * > **易错点**：可以调，但不要调到 100 万——集合类型 key 的元素个数上限是 1000，调到 100 万等于往一个 key 里塞 100 万组 entry，妥妥的 BigKey，得不偿失；这个值可以调，但不要超过 1000。

### 100 万字段大哈希的三种结局

* **不动它**

    * 结果：entry 数 100 万远超 500，用哈希表、不再用 ziplist，内存 62.23 MB，且本身就是一个 BigKey。

* **拆成 100 万个 String**

    * 结果：BigKey 问题确实解决了，变成 100 万个 key。

    * 代价：String 底层没有内存优化，每个 key 都有大量元信息，100 万数据最终占 77.54 MB，比不动它更惨。

    * 代价：想批量获取数据也拿不到，只能一个一个按 key 取。

* **拆成 1 万个小哈希**

    * 规则：把 `ID / 100` 的值作为 key，把 `ID % 100` 的结果作为 field；任何数对 100 取余的结果永远是 0 到 99。

    * 结果：100 万数据变成 1 万个 key，每个 key 里刚好 100 个 entry，没有超过默认的 500 上限，既利用了哈希的优势又把 key 打散了。

    * 数值：最终内存占用约 24 MB，远小于前两种方案。

    * > **提示**：打散不一定用 100，用 500、1000 也可以，只要小于 entry 的上限就行。

```text
   id     0  1  2  ...  99 | 100 101 ... 199 | 200 ... 299 | ... | 999900 ... 999999
   id/100 0  0  0      0  |   1   1       1  |   2       2 | ... |    9999 ...   9999
   id%100 0  1  2     99  |   0   1      99  |   0      99 | ... |       0 ...      99
   key        hash:0      |      hash:1      |    hash:2   | ... |        hash:9999
                  ↓                ↓              ↓                        ↓
             100 个 entry     100 个 entry    100 个 entry             100 个 entry
```

### 10 万级实测对照

| key 前缀 | 数据形态 | key 数量 | 内存占用 |
| :--- | :--- | :--- | :--- |
| `test:str` | 每个 key-value 拆成独立 string | 10 万 | 7.69 MB |
| `test:big_hash` | 全部塞进一个哈希 | 1 | 6 MB 多 |
| `test:small_hash` | 按 100 条拆成小哈希 | 1000 | 1.85 MB |

* 规则：String 本身在内存上没有太多优化，每个 key 都要存很多元信息，用得越多无效数据越多；Hash、Set、Sorted Set 使用了 ziplist 这类压缩结构，内存上更有优势。

* 边界：String 也不是一无是处，验证码这类存储时间短、空间占用小的临时信息用 String 没什么问题。

* > **结论**：没有最好的数据结构，只有最合适的数据结构，要根据实际情况分析。

## 批处理

### 为什么需要批处理

* 单条命令耗时构成：1 次网络往返耗时 + 1 次命令执行耗时（网络传输相当于在路上走，命令执行相当于卸货）。

* 数值：Redis 并发可达 5 万/秒，即单次执行耗时约 $\frac{1}{50000}$ 秒，换算约 20 微秒；而网络传输往往毫秒级（示例 ping 平均 5 ms；按光纤中 20 万 km/s 计算，1000 km 往返即 0.01 秒 = 10 ms，还未计网络拥堵）。

* > **结论**：网络传输是毫秒级、命令执行是微秒级，两者差好几个数量级，执行命令的时间相对于网络传输时间几乎可以忽略不计。

* 数值：逐条 `SET` 导入 10 万条耗时 40 多秒，时间主要花在网络耗时上。

* 批处理耗时构成：1 次网络往返 + n 次命令执行，比逐条执行少了 n − 1 次网络传输耗时。

### MSET

* **MSET**

    * > **定义**：一次处理多个 key-value 键值对的原生批处理命令。

    * 规则：`MSET` 后面永远是一串 key value key value，中间不需要任何分隔符。

    * 用法：Jedis 的 `mset` 要的是一个数组，数组中紧挨着的两个元素分别是 key 和 value；所以 2000 长度的数组保存的是 1000 组键值对。

    * 分批技巧：用 `i % 1000` 得到 0~999，左移一位（乘 2）得到偶数下标 0、2、4…1998 存 key，下标 +1 的奇数位存 value；当 `i % 1000 == 0` 时说明这一批 1000 组已填满，就 `mset` 发出去。

    * 数值：每批 1000 组，10 万条耗时 182 ms。

* > **易错点**：一次批处理千万不要传输太多命令——一次多发送确实能减少运输次数、提高效率，但一次压得太多把带宽占满、网络阻塞，反而变慢，得不偿失。

* 边界：MSET 只能处理 String；HMSET 只能操作 Hash 且 key 不能变；SADD（Set）、ZADD（Sorted Set）也是一次性插多个 member 但 key 不能变，变的仅仅是 field 或 member。

| 命令 | 能处理的数据结构 | key 能否变化 |
| :--- | :--- | :--- |
| `MSET` | String | 可以，一批多个 key |
| `HMSET` | Hash | 不可以，只能一个 key |
| `SADD` | Set | 不可以，只能一个 key |
| `ZADD` | Sorted Set | 不可以，只能一个 key |

### Pipeline

* **Pipeline**

    * > **定义**：把很多命令塞到一个管道里、一次性传过去的批处理方案。

    * 能力：允许传任意命令（`set`、`hset`、`lpush`、`sadd`、`zadd` 等），Redis 里的一切命令都能做，且 key 不用约束、随便命名。

    * 用法：Jedis 用 `jedis.pipelined()` 拿到管道，循环中 `pipeline.set(...)` 写入，`pipeline.sync()` 把它发出去并清空管道里的数据。

    * 数值：每 1000 条 sync 一次，10 万条耗时 294 ms / 248 ms。

    * 边界：Spring Data Redis 里对应的批处理叫 `executePipelined`。

```java
Jedis jedis = new Jedis("127.0.0.1", 6379);
Pipeline pipeline = jedis.pipelined();
for (int i = 0; i < 100000; i++) {
    pipeline.set("test:" + i, "value");
    if (i % 1000 == 0) {
        pipeline.sync();      // 发出去，同时清空管道里的数据
    }
}
```

### Pipeline 与 MSET 的差异与选型

* 差异一：MSET 只能操作部分数据类型且对 key 有约束；pipeline 可以任意命令组合、key 自定义，应对复杂数据类型或复杂需求时用 pipeline。

* 差异二：MSET 是 Redis 内置操作，多组 key 和 value 会作为一个原子性操作一次性执行完，中间不会有其他命令插队；pipeline 的一组命令一起发到 Redis，但不一定一起执行。

* 机理：pipeline 命令在传输过程中其他客户端也可以向 Redis 发命令，到达后进入队列排队，Redis 线程依次出队执行，因此可能被别人的命令插队，实际执行时长比预期长一些——这就是 pipeline 比 MSET 稍慢的原因。

* 选型：有「所有命令必须连着执行、中间不能有间隔」的原则性需求时用 MSET；没办法用 MSET 时用 pipeline。

* > **易错点**：⚠️ pipeline 的一批命令不具备原子性，不要以为它们是一起执行的，它们是按一定顺序先后执行的。

## 集群模式下的批处理

### 为什么必须落在同一个槽位

* 规则：`MSET`、`PIPELINE` 这样的批处理需要在一次请求中携带很多命令，如果 Redis 是集群，这些命令的多个 key 必须落在一个槽位中，否则执行失败。

* 机理：集群共 16384 个槽位分配到不同节点，key 按槽位值落到对应节点；一次携带上千条命令时算出的槽位值很可能不同，要保存到不同节点就需要很多个连接，那就不是批处理的语义了。

* 现象：`MSET name jack age 21 sex mu` 报 `(error) CROSSSLOT Keys in request don't hash to the same slot`；pipeline 同样无法执行。

### 四种方案

* **串行命令**

    * 做法：for 循环依次执行每一条命令，等于放弃批处理。

    * 耗时：n 次网络耗时 + n 次命令耗时。

    * 边界：实现最简单，但耗时太久，强烈不推荐。

* **串行 slot**

    * 做法：先计算每条命令 key 的槽位，槽位相同的放进一个集合作为一组，组内用 pipeline 或 MSET 做批处理，组与组之间串行执行。

    * 耗时：m 次网络往返 + n 次命令执行，取决于计算出来的槽位数量 m（如 1000 条命令落在 10 个槽位就是 10 次网络传输）。

    * 边界：极端情况下 1000 条命令算出 1000 个不同槽位，耗时退化为串行命令，但这种情况几乎不可能发生；slot 越多耗时越久，实现也稍复杂。

* **并行 slot**

    * 做法：同样按槽位分组，但组与组之间不是串行等待，而是开 N 个线程一起发请求。

    * 耗时：虽然是 N 次传输，但因为是一起发生的，网络耗时仍相当于一次网络往返；命令执行耗时不变。

    * 边界：槽位过多需要开启过多线程并行执行，仍有性能损耗，实现也更复杂。

    * > **结论**：推荐并行 slot——性能上相对 hash tag 有一定损耗但可接受，而且不会产生数据倾斜。

* **hash tag（哈希标签）**

    * > **定义**：key 中的一对花括号 `{}`，花括号里的部分才是计算槽位时使用的有效部分。

    * 示例：`SET name jack` 用整个 name 参与运算算槽位；`SET {a}name jack` 只用花括号里的 `a` 去算槽位。

    * 机理：给批处理的每个 key 都指定相同的花括号内容，hash tag 一样则算出的槽位一定相同，批处理就能执行。

    * 性能：正常批处理的性能（一次网络往返 + N 次命令执行），还不需要开启多线程，性能最好。

    * > **易错点**：把 1 万个 key 都设置成相同槽位，等于全扔到同一个节点上，该节点数据量会比别的节点多很多，这就是数据倾斜，所以不推荐。

### 客户端实现差异

* **JedisCluster**

    * 现象：`jedisCluster.mset("name","jack","age","21","sex","mu")` 直接报错，说明 Jedis 的 cluster 默认并没有解决集群下的批处理问题。

    * 做法：只能自己按串行 slot 或并行 slot 实现——用自定义工具类计算 key 的槽位，放进 `Map<Integer, Map<String,String>>`（外层 key 为槽位值，value 为该槽位下所有 entry），再遍历每一组组装成数组 `mset` 出去。

* **Spring Data Redis（Lettuce）**

    * 现象：`restTemplate.opsForValue().multiSet(map)` 在集群下直接可用，代码与非集群完全一样。

    * 机理：底层 Lettuce 的集群 `multiSet` 第一件事就是 `slotHashPartition`（分区），按 map 里 key 的槽位把相同的放进一个集合，再遍历各组做 multiSet。

    * 判定：该 `multiSet` 返回的是 `Future`，即异步执行（底层基于线程、NIO 模式），所以它做的是异步的 slot，也就是并行 slot。

    * > **结论**：实现集群批处理强烈建议用 Spring 提供的工具类，不要自己实现；坚持用 Jedis 就只能自己实现分组方案。

## 持久化配置

### 缓存与重要数据分离

* 建议：用来做缓存的 Redis 实例尽量不要开启持久化功能——缓存的目的是提高查询效率，缓存临时消失后再查一次就回来了，安全性要求没那么高。

* 部署：把缓存相关业务放到一个单独的实例、不开持久化；把分布式锁、库存、订单流水等安全要求高的业务放到独立实例并开启持久化。

* 选型：尽可能使用 AOF，关闭 RDB。

    * RDB 优点：持久化文件小、重启加载速度非常快。

    * RDB 缺点：数据安全性差——频率不高，两次 RDB 往往间隔 60 秒甚至更长，期间所有命令都可能丢失。

    * RDB 无法靠提频补救：后台采用 fork 机制，虽基于 Copy On Write，但内存较大时耗时非常久，且需要大量磁盘 IO，执行起来对性能影响非常大。

    * AOF 优点：每秒刷盘机制，最多丢失这一秒钟左右的数据；代价是生成的 AOF 文件体积较大，但在可接受范围内。

* > **提示**：RDB 更适合用来做数据备份——可以定期手动执行一次 `BGSAVE`，把得到的 RDB 文件作为永久备份放着兜底；不要频繁做，而且不要在主节点做，最好找从节点把影响降到最低。

### AOF rewrite 阈值

* 机理：AOF 文件体积较大，会频繁做 BG rewrite；重写时要计算哪些命令需要重写（CPU 压力大），过程中也需要大量磁盘 IO，做得太频繁对性能有影响。

* 配置：`auto-aof-rewrite-percentage 100`——Redis 记录上一次 AOF 文件大小，当前文件超过它达到 100%（体积翻倍）就触发 rewrite。

* 配置：`auto-aof-rewrite-min-size 64mb`——文件大小在 64 MB 以内不会做任何 rewrite。

* 规则：通过调整百分比值或体积值来控制 rewrite 的频率。

```conf
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
no-appendfsync-on-rewrite no
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

### no-appendfsync-on-rewrite

* 机理：主线程收到写命令后，一方面写入内存，一方面把命令写进 AOF 缓冲区（保存最近 1 秒内的所有命令），由独立线程每隔 1 秒 fsync 刷盘；主线程会检查刷盘耗时，小于 2 秒直接返回，超过 2 秒则认为出问题、阻塞等待直到刷盘结束，期间无法接受新命令。

* 背景：BG rewrite 或主从全量同步时的 fork 都会产生大量磁盘 IO，拖慢 AOF 每秒刷盘，进而导致主线程阻塞。

* 配置：改成 `yes` 后，Redis 在后台做 BG rewrite 或 RDB fork 期间停止 AOF 持久化，请求写完内存直接结束，性能得到保障。

| 取值 | 行为 | 代价 |
| :--- | :--- | :--- |
| `no`（默认） | rewrite/fork 期间照常 fsync | 可能因磁盘争抢导致 fsync 变慢，主线程阻塞 |
| `yes` | rewrite/fork 期间不做 fsync | 期间的数据没有持久化，可能丢失 |

* 边界：更在意数据安全性就配 `no`，担心 fsync 阻塞主线程、更追求性能就配 `yes`。

### 部署建议

* 内存预留：Redis 实例所在物理机一定要预留足够内存应对 fork 和 rewrite；fork 极致情况下内存可能翻倍（如 Redis 里 6 G 变成 12 G）。

* 单实例上限：单个 Redis 实例内存不要太大，建议 4 G 到 8 G 之间，采用单机多实例部署。

    * 原因：单个实例内存越大，将来建立主从后从节点做 fork、同步时需要同步的数据越多、压力越大；控制内存可以提高 fork 速度、减少主从同步与数据迁移的压力。

* > **提示**：不建议把 Redis 部署到 CPU 密集型应用所在的机器上（如 Elasticsearch，搜索运算与数据聚合对 CPU 消耗很高）；也不建议与高磁盘负载的应用部署在一起（如数据库、消息队列），因为 rewrite 与 AOF 刷盘都需要大量磁盘读写。

## 慢查询

### 定义与危害

* **慢查询**

    * > **定义**：在 Redis 里执行耗时超过了某个阈值的命令。

    * 边界：虽然名字叫慢查询，但不管命令是 set 还是 get，只要超时就叫慢查询。

* 危害：Redis 单线程执行命令，所有命令进入队列排队依次执行；正在执行的是慢查询时，后面的命令全在队列里排队，很可能因等待超时而报错，导致主线程阻塞、性能下降，甚至出现业务故障。

### 两个必须调的配置

* **slowlog-log-slower-than**

    * 含义：慢查询的阈值，单位是微秒，默认 10000（即 10 ms）。

    * 建议调小：Redis 平常执行命令一般在微秒级、约 50 微秒，10 ms 的阈值下大多数请求都不会被记录；建议调到 1000 微秒或再小一点。

* **slowlog-max-len**

    * 含义：慢查询日志 slowlog 的长度，默认 128，最多记录 128 条。

    * 建议：可以稍微调大，但不要无限调大，否则会造成过多内存占用。

* 修改方式：`CONFIG GET` / `CONFIG SET` 动态修改（重启后失效），或写进 `redis.conf` 永久生效。

* > **提示**：慢查询日志要及时发现、及时处理，不能一直堆积在那里。

### 定位命令

* `SLOWLOG LEN`：查看慢查询日志的长度。

* `SLOWLOG GET`：读取慢查询日志。

* `SLOWLOG RESET`：清空慢查询日志。

* `SLOWLOG GET` 输出字段依次是：慢查询日志编号（每条日志的唯一编号）、时间戳（什么时候查询的）、耗时（微秒）、慢查询对应的命令（如 `KEYS *`）、发起客户端的 IP 和端口、客户端名称（需自己配，未配则为空）。

### 两类根因

* 命令本身的问题：像 `KEYS *` 天生具有慢查询潜质，只要用了肯定是慢查询，应该想办法禁用它、不让大家使用。

* 数据结构不合理：比如一个 Hash 里有数万元素再对它做运算就会慢查询，这种情况往往是产生了 big key，应该选择更合适的数据结构、拒绝 big key。

* > **提示**：桌面客户端的「服务器信息」能直接展示每秒查询率、客户端数量、内存占用、网络输入/输出、键的总量，并提供慢查询日志视图（展示什么时间发的、什么命令）。

## 服务端安全

### SSH 免密登录与攻击链路

* **免密登录原理**

    * 机制：利用 SSH 的非对称加密生成公钥与私钥，公钥放服务器、私钥留本地，登录时双方用公私钥做加密认证，认证通过即视为可信任用户、允许访问。

    * 前提：公钥信息必须保存在服务器上才行；不知道服务器账号密码的人没法把公钥放进去，这种情况下服务器是安全的。

* **authorized_keys**

    * > **定义**：`root/.ssh` 目录下存放「已经授权的密钥」的文件名，把公钥重命名为它放上去，就等于得到了这台服务器的认可。

* 漏洞利用步骤：

    * 攻击者本地把整套公钥写进一个文件（如 `tt`）。

    * `cat tt | redis-cli -h 目标IP set crack`，利用管道把文件内容作为 value 塞进目标 Redis 的某个 key（key 名叫什么都无所谓）。

    * `CONFIG SET dir /root/.ssh` 把持久化目录改到 `/root/.ssh`；`CONFIG SET dbfilename authorized_keys` 把 RDB 文件名改成 `authorized_keys`。

    * 执行 `SAVE` 触发 RDB 持久化，目标机上生成 `/root/.ssh/authorized_keys`，文件内容就是 Redis 里的所有数据，其中包含那条公钥。

    * 攻击者手持私钥执行 `ssh root@目标IP`，免密登录成功。

* 要害：Redis 自己有把数据写到任意目录、任意文件名的能力，攻击者恰好能用一个管道把公钥伪装成普通业务数据送进去。

### 漏洞成立的三个前提

* 能直接连上：Redis 默认绑定 `0.0.0.0`，全世界任何人只要知道 IP 都能访问；且默认情况下没有密码限制。

* 能在 Redis 里使用 `CONFIG SET` 去修改持久化目录和持久化文件名称。

* Redis 具备写入本地目录的权限：因为是以 root 账号启动的，Redis 才具备了 root 权限、才能往 root 目录写文件。

* > **易错点**：只说「Redis 没有设置密码」还少说了更致命的几点——Redis 暴露到了公网上、Redis 里有 `CONFIG SET` 命令，并且是以 root 账号权限运行的。

### 加固措施

* 设置密码：不能裸奔；而且密码一定要超级复杂，因为 Redis 响应速度是微秒级，天然方便黑客不断试值做暴力破解。

* 禁止在线上使用的危险命令：`CONFIG SET`（可以修改系统配置）、`FLUSHDB` / `FLUSHALL`（清空数据库）、`KEYS`（天生慢查询体质，一用主线程就堵死）。

* **rename-command**

    * > **定义**：给命令改名的配置，可把危险命令改成一长串只有运维人员记得住的名字，别人不知道就没法用。

    * 彻底禁用：把名字置空，如 `rename-command config ""`，置空意味着这个命令以后再也不能用。

    * 生效方式：编辑 `redis.conf` 中的 `rename-command` 后需要重启 Redis（`systemctl restart redis`）。

* 限制网卡：`bind` 默认 `127.0.0.1`，改成 `0.0.0.0` 意味着任何人都能访问、非常危险；建议绑定局域网那张网卡，只让公司内网互相访问，或者 Redis 所在的服务器干脆不开外网。

* 开启防火墙：不开防火墙等于整个服务器在裸奔。

* 不要使用 root 账号启动 Redis：建立独立账号单独启动，去掉往 `/root/.ssh` 写文件的权限。

* 尽量不要使用默认端口：默认 6379 全天下都知道，换成例如 6388 之类没人知道的端口。

## 内存划分与内存配置

### 三类内存

* **数据内存**

    * 地位：Redis 内存最主要的部分，平常保存的各种键值信息都在这里。

    * 问题一：bigkey，由写入时数据结构选择不恰当或业务分配不恰当导致。

    * 问题二：内存碎片。

        * 机理：底层采用 jemalloc 内存分配策略，会提前界定 8、16、32、48 等多种大小（不是严格按 2 的 n 次方，有自己的一套 size 区间）；存 10 字节数据时 8 不够、只能分配 16 字节，多给的 6 字节就是没人使用的碎片。

        * 解决：重启 Redis 时碎片会被回收，定期重启即可。

        * > **易错点**：不能把所有服务器暴力全停掉，应按主从或集群分批重启，在确保 Redis 可用的前提下做。

* **进程内存**

    * > **定义**：Redis 主进程本身运行时需要分配的内存，用来运行代码、保存常量等，就像 Java 代码跑起来需要内存空间一样。

    * 数值：大小往往固定，一般几兆，不会有太大波动；内存占用过高时基本不用考虑这里。

* **缓冲区内存**

    * 组成：客户端缓冲区、AOF 缓冲区、复制缓冲区等。

    * 特性：受客户端操作影响，波动比较大，是将来出现内存占用过高时需要重点分析的一块。

```text
Redis 内存
├── 数据内存      ← 主要部分，存各种 key-value
│    ├── bigkey       数据结构选得不恰当 / 业务分配不恰当
│    └── 内存碎片     分配器按区间切分，多给你的那几个字节
├── 进程内存      ← 主进程运行时分配：跑代码、存常量
│    └── 一般只有几兆，固定，不会大波动
└── 缓冲区内存    ← 受客户端操作影响，波动最大
     ├── 复制缓冲区   repl-backlog buffer（有上限，默认 1 兆）
     ├── AOF 缓冲区   （无上限，但缓存的数据量很小）
     └── 客户端缓冲区  ← 重点盯的就是它
          ├── 输入缓冲区（固定上限 1G，不能配）
          └── 输出缓冲区（可配，normal 默认 0 0 0 ＝ 无上限）
```

### 内存查看命令

* `INFO memory`：查看服务端内存相关的所有指标。

* `MEMORY USAGE <key>`：查看某一个 key 的内存占用。

* `MEMORY STATUS`：统计整个 Redis 里不同模块的内存占用。

* `MEMORY DOCTOR`：自带的内存诊断策略，帮你判断内存有什么问题。

* `MEMORY PURGE`：清除一些数据。

* > **易错点**：这两个命令展开的结果有很多重复项，不要把它们当成两套不同的东西。

| 指标（`INFO memory` / `MEMORY STATUS`） | 含义 | 对应哪块内存 |
| :--- | :--- | :--- |
| `used_memory` / `total.allocated` | 当前使用的总内存 | —— |
| `used_memory_peak` / `peak.allocated` | Redis 进程自启动以来的内存峰值 | —— |
| `used_memory_startup` / `startup.allocated` | Redis 刚启动时初始化的内存 | 进程内存 |
| `repl_backlog_size` / `replication.backlog` | 复制缓冲区的大小 | 缓冲区内存 |
| 各客户端类型 / `clients.normal`、`clients.slave` | 输入、输出缓冲区 | 缓冲区内存 |
| 更下面若干项 | 数据库数据量、纯业务数据内存大小 | 数据内存 |

* > **提示**：`peak` 是峰值、`total` 是当前值，肯定会有波动，峰值往往比当前值大一点。

* 处置阈值：内存使用率达到 90% 以上就需要警惕，必须赶紧找到内存占用过高的原因并解决。

### 复制缓冲区与 AOF 缓冲区

* **复制缓冲区（repl-backlog buffer）**

    * 作用一：主节点制作 RDB 期间过来的新命令先放进这个 buffer，RDB 发给从节点后再把 buffer 里的数据发过去，从节点数据才完整。

    * 作用二：记录增量复制的偏移量——从节点有自己的 offset，小于主节点 offset 时做增量复制；差得太多导致 buffer 被占满就只能做全量复制。

    * 数值：默认 1 兆，通过配置文件里的 `repl-backlog-size` 设置；可以调得稍微大一点。

    * 边界：有上限，一般情况下不用担心它波动。

* **AOF 缓冲区**

    * 用途一：AOF 每秒刷一次盘，这一秒内的命令就放在这个缓冲区里，再由线程一次性刷出去。

    * 用途二：`BGREWRITEAOF` 过程中有部分数据需要缓存起来，也放在这个缓冲区。

    * 边界：没有上限，但保存的只是 AOF 过程中的命令，数据量不多且 AOF 刷写速度很快，基本不会导致内存巨大波动。

### 客户端缓冲区

* **输入缓冲区**

    * 作用：缓存客户端发过来的命令。

    * 数值：最大值 1 G，固定不能配，不用担心溢出。

    * 溢出场景：主线程因慢查询被长期阻塞，无数命令涌进来来不及处理、堆积超过 1 G（可能性非常小）。

    * 后果：超过 1 G 说明 Redis 完全忙不过来，会直接断开客户端连接、不再接收任何客户端命令。

* **输出缓冲区**

    * 作用：缓存要返回给客户端的结果。

    * 配置：`client-output-buffer-limit class hard-limit soft-limit soft-seconds`。

    * 参数含义：`class` 客户端缓冲区的类型；`hard limit` 硬限制，一旦触发链接直接断开（谁满了就把谁断开）；`soft limit` 软限制，不是一到上限就断开；`soft seconds` 软限制的观察时长，到了上限并持续这么久才断开。

    * 三种客户端类型：普通客户端（Java 代码建立的普通连接）、主从复制客户端 `replica`、发布订阅客户端 `pubsub`；不同类型可以配不同的限制。

    * 数值：普通客户端默认 `client-output-buffer-limit normal 0 0 0`，也就是没有上限。

    * > **易错点**：⚠️ 没有上限非常危险——如果请求查的都是 bigkey（一个 key 占几百兆）而 QPS 又有几千，很可能直接把内存占满。

    * 变满的原因：返回的数据量太多、客户端来不及处理；常见成因是查了 bigkey，或开启了 `MONITOR`（只监控不处理，大量请求涌入也会撑满）。

    * 预防：尽可能避免 bigkey；带宽确实不够时适当增加 Redis 所在物理机的带宽；更重要的是尽快找到相关业务做业务限流。

    * 边界：`replica` 客户端和 `pubsub` 客户端都有上限，不用担心它们导致内存溢出。

* **CLIENT LIST**

    * 作用：查看当前连接到 Redis 的所有客户端及每个客户端的详细信息，用来定位具体是哪个客户端缓冲区溢出。

    * 关键字段：`id` 客户端 id、`addr` 客户端 IP 和端口、`age` 建立连接多久了、`idle` 空闲了多久、`flags` 客户端类型、`obl` 输出缓冲区长度、`oll` 输出缓冲区列表、`omem` 该客户端输出缓冲区占用的总内存。

    * 判定：输出缓冲区有问题时 `omem` 会大于 0 且非常大，看这个值就能鉴别客户端是否溢出。

    * > **提示**：最佳方案是写脚本不断获取客户端相关信息做监控，发现参数异常赶紧揪出来并发告警，后台再定位相关业务处理。

## 集群还是主从

### 集群的六个问题

| 问题 | 一句话说明 |
| :--- | :--- |
| 完整性 | 插槽全覆盖要求下，任意几个槽不可用，整个集群就停止对外服务 |
| 带宽 | 节点靠互相 ping 判活，节点越多每次 ping 携带的信息越大 |
| 数据倾斜 | bigkey、相同 hash tag 的批处理会让部分节点负担过重 |
| 客户端性能 | 客户端要做节点选择、读写分离判断、插槽判断，有额外开销 |
| 兼容性 | `MGET`、`PIPELINE` 等批处理命令在集群模式下无法直接运行 |
| Lua 与事务 | 多命令要落在同一节点，跨槽就无法执行 |

### 完整性

* **cluster-require-full-coverage**

    * 默认 `yes`：插槽必须全覆盖，16384 个插槽中任意几个不可用，整个集群都不对外服务。

    * 现象：五节点集群里干掉一对主从后，在存活的节点上执行 `SET name jack` 报 `(error) CLUSTERDOWN The cluster is down`，明明还有节点活着也不让用。

    * 改成 `no`：不需要全覆盖，部分插槽出现问题时集群依然可用。

    * 边界：改成 `no` 后，插槽值落在健康节点上的命令可用（示例 `SET name jack` 成功），落在不健康节点上的仍会被目标节点拒绝。

    * > **易错点**：⚠️ 注意改的是 `/tmp` 目录下的集群配置文件，不在普通实例的目录里；改完需要删掉各节点的目录与配置文件，重新创建并启动集群。

```conf
# 默认配置
cluster-require-full-coverage yes

# 改成
cluster-require-full-coverage no
```

* > **结论**：牺牲一部分数据完整性，换取整个集群继续可用——部分槽坏了只影响部分业务，还可以做熔断、降级；整个不可用则所有业务都废了，所以不建议配成 `yes`。

### 带宽

* 机理：集群模式中没有哨兵，节点是否健康完全靠节点之间互相 ping 判断；每一次 ping 都会带上集群的插槽信息以及各个节点的状态信息。

* 数值：十个节点时每次 ping 的信息量大约 1 KB；节点达到成千上万时，一次 ping 可能占用数兆甚至数十兆、数百兆的带宽，光 ping 就把带宽占完，请求进不来。

* 途径一：避免大的集群，节点数最好小于 1000（其实 1000 都多，越少越好）；业务再大也应该拆成小业务，每个业务用一个小的独立集群。

* 途径二：避免在单个物理机中运行太多 Redis 实例，一般部署十个左右就差不多；同一台机上实例越多，ping 消耗的带宽成倍增加。

* 途径三：配合合适的 `cluster-node-timeout`——它是集群节点之间故障检测的超时时间，ping 的时间间隔约为它的一半；值越大 ping 频率越低、带宽占用越小，但故障发现与恢复的速度变慢、集群可用性降低。

    * > **易错点**：这个值不是越大越好，也不是越小越好，应该在实际实践中检测节点数量与带宽够不够用，再适当调整。

### 其余四个问题

* 数据倾斜：出现 bigkey，或者做集群批处理时使用了相同的 hash tag，都会导致数据倾斜，部分节点负担过重、部分节点负担较少。

* 客户端性能：一旦做了集群，客户端（Jedis 或 Lettuce）访问时都要做节点选择、读写分离判断、插槽判断，势必带来额外开销。

* 兼容性：`MGET`、`PIPELINE` 等批处理命令在集群模式下无法正常运行，因为无法保证多个 key 落到同一个槽，只能在客户端按 slot 拆分处理；程序员实现起来复杂，即便实现了业务性能也受影响。

* Lua 与事务：Lua 和事务都在保证多个命令执行的原子性，既然是多个命令，对应的 key 若不在同一个节点的插槽上就无法执行，因此集群模式下没法运行 Lua 和事务。

### 取舍结论

* 结论：在满足业务需求的情况下，能不用集群还是不要用的好。

* 依据：单体 Redis 已经能够达到万级别的 QPS，业务与数据优化得好可能达到好几万；全国百分之八九十的公司 QPS 根本达不到数万，完全能够满足需求。

* 替代：单体 Redis 也可以建立主从，可用性不错；再加上哨兵机制，可用性与并发能力都能达到。

* > **结论**：单体或主从能够满足业务需求时，能使用主从尽量主从，不要去做集群，得不偿失。
