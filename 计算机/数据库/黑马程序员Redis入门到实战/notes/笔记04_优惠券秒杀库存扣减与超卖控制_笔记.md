# 优惠券秒杀：库存扣减与超卖控制

## 券的两种命运与两张表

秒杀业务里的商品就是优惠券（代金券），券本身分两类，两类券的发放方式完全不同，后面的秒杀逻辑只对其中一类生效。

### 平价券与特价券

* **平价券**

    * > **定义**：折扣小、可以无限量发放的普通代金券，谁想买都能买。

    * 例子：47.5 抵 50，约等于九五折；因为价格便宜、折扣小，可以大量发放，不需要抢。

    * 落库位置：只落在 `tb_voucher` 表里，没有库存字段，所以任意用户都可以随意购买。

* **特价券（秒杀券）**

    * > **定义**：折扣力度大、有库存上限、且只在限定时间段内开放的券，需要先到先得地抢购。

    * 例子：80 抵 100，八折；库存 100 张，卖完即止。

    * 它同时具备「券的基本信息」和「售卖规则」两部分，因此要落到两张表里。

    * > **注意**：普通券不需要秒杀，秒杀下单接口针对的是特价券。

### tb_voucher：券是什么

* **tb_voucher**

    * > **定义**：记录券基本信息的表，普通券和秒杀券都在这张表里，用 `type` 区分。

    * `shop_id`：发放这张券的店铺 id，券一定跟店铺有关联。

    * `name` / `sub_title`：券的标题与副标题，标题描述面额（例如 100 块的还是 50 块的）。

    * `rules`：使用规则，可以写多条，例如什么时间能使用、可以叠加多少张。

    * `pay_value`：支付金额，即实际要付的钱；47.5 抵 50 里的 47.5。

    * `actual_value`：实际抵用金额；47.5 抵 50 里的 50。这两个字段合起来就是折扣。

    * `type`：券类型，普通券 0，秒杀券 1。

    * `status`：上架、下架、过期三种状态。

    * `create_time` / `update_time`：通用字段。

* **status 的三态语义**

    * > **定义**：描述一张券从被创建到失效的生命周期。

    * 刚添加时理论上应是下架状态；管理员检验、审核通过后才可以上架；审核不通过就不上架；将来不想再用可以让它处于过期状态。

### tb_voucher_seckill：这张券作为秒杀券的售卖规则

* **tb_voucher_seckill**

    * > **定义**：秒杀券的拓展表，核心只多出三样东西——库存、生效时间、失效时间。

    * 主键是 `voucher_id`，且**不自增**：因为秒杀券首先是一张券，它已经具备 `tb_voucher` 的全部信息，`tb_voucher_seckill` 只是它的拓展表，主键直接取 `tb_voucher` 的 id。

    * `stock`：库存上限。

    * 生效时间 / 失效时间：只有在有效时间范围内才允许抢购，不能随时抢。

    * `create_time` / `update_time`：通用字段。

* **两张表的绑定关系**

    * `tb_voucher` 里既有秒杀券也有非秒杀券，靠 `type` 的 0 / 1 区分；`tb_voucher_seckill` 里的一行对应 `tb_voucher` 里的一条记录。

```text
tb_voucher     券的基本信息，普通券和秒杀券都在这张表
  id │ shop_id │ name │ sub_title │ rules │ pay_value
  actual_value │ type │ status │ create_time │ update_time
        ▲
        │  voucher_id 取的就是这张表的 id，秒杀券不单独自增
        │
tb_voucher_seckill     秒杀券多出来的部分
  voucher_id │ stock │ 生效时间 │ 失效时间
  create_time │ update_time
```

### 新增一张秒杀券

* **新增接口**

    * `POST /voucher/seckill`，参数为一个 `@RequestBody VoucherDTO`。

    * 请求体除了券的基本字段，还带上秒杀券的核心三件套：库存、开始时间、结束时间。

    * 实现一次性写两张表：先新增普通券，再新增秒杀券。

* **请求体示例与单位陷阱**

```json
{
  "shopId": 1,
  "name": "100元的代金券",
  "subTitle": "周一到周五可用",
  "rules": "全场通用，无需预约",
  "payValue": 8000,
  "actualValue": 10000,
  "type": 1,
  "stock": 100,
  "beginTime": "2025-01-26T00:00:00",
  "endTime": "2025-01-26T14:00:00"
}
```

* **秒杀券特有的填写规则**

    * `type` 必须填 1，表示这是一张特价券／秒杀券。

    * `stock` 填库存数量，例如 100。

    * `beginTime` / `endTime` 设定可抢购的时间窗口，窗口外不允许购买。

    * > **易错点** ⚠️：数据库里 `pay_value` 和 `actual_value` 的单位是**分**，不是元；以分为单位是为了避免出现小数。所以 JSON 里的 8000 抵 10000，实际是 80 元抵 100 元。

    * > **提示**：新增成功后两张表通过 id 关联，新券 id 在 `tb_voucher` 与 `tb_voucher_seckill` 中一致，将来这份接口应当由后台管理界面调用。

## 秒杀下单链路

### 一个动作组：下单 + 扣库存

* **秒杀下单接口**

    * `POST /voucher-order/seckill/{id}`，路径里的 id 是要抢的那张券的 id。

    * 返回值是当前订单的 id；订单 id 必须返回给前端，前端才能拿它去获取支付链接、完成支付。

* **订单落库**

    * > **定义**：无论普通券还是特价券，下单购买都要生成订单数据并写入 `tb_voucher_order`。

    * 表内记录下单用户、购买的券、付款方式、订单状态等信息。

    * 新建时不必指定全部字段：支付方式、支付金额、创建时间、更新时间都有默认值。

    * 必须手写的只有三个字段：订单 id、用户 id（user_id）、券 id（voucher_id）。

* **订单 id 与用户 id 的来源**

    * 订单 id 用分布式 id 生成器 `RedisIdWorker` 生成，调用 `nextId("order")` 得到全局唯一 id。

    * 用户 id 从 `UserHolder` 获取——登录拦截器已经把用户放进去，从中取用户再取 id。

    * 券 id 就是前端传来的路径参数。

### 必须先判断再动手

* **两项前置判断**

    * 秒杀时间：券上有开始时间和结束时间，只有在这个时间段内才能参与，否则就是过期或超时的请求。

    * 库存是否充足：一共就 100 个库存，卖完不能再减，库存不足不允许下单。

    * > **注意**：判断顺序是「先时间、后库存」，时间不合法时库存判断没有意义；而时间与库存都要先查到券的信息才谈得上判断，所以查询必须排在最前面。

* **整体流程**

```text
  前端提交优惠券 id
        │
        ▼
  ① 查询优惠券信息 ──────► 拿到 开始时间 / 结束时间 / 库存
        │
        ▼
  ② 判断秒杀时间 ───────► 还没开始 / 已经结束 → 返回异常
        │
        ▼
  ③ 判断库存 ────────────► 库存不足 → 返回异常
        │
        ▼
  ④ 扣减库存
     UPDATE tb_voucher_seckill SET stock = stock - 1 WHERE voucher_id = ?
        │
        ├── 更新失败 ──────► 返回异常
        ▼
  ⑤ 创建订单 ────────────► 写入 tb_voucher_order
        │
        ▼
  ⑥ 返回订单 id ─────────► 前端凭它去获取支付链接
```

* **时间的比较方式**

    * 判断未开始：取 `beginTime` 与当前时间比较，若 `beginTime.isAfter(LocalDateTime.now())` 成立，说明开始时间还在当前时间之后，返回「秒杀尚未开始」。

    * 判断已结束：取 `endTime` 与当前时间比较，若 `endTime.isBefore(LocalDateTime.now())` 成立，说明结束时间已在当前时间之前，返回「秒杀已结束」。

* **库存是否充足的判定**

    * > **定义**：秒杀场景下库存只要大于 0 就算充足，即 `stock < 1` 时判定为库存不足。

* **扣减库存的写法**

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1
WHERE voucher_id = #{voucherId}
```

* **update 返回值的兜底作用**

    * 扣减会返回一个 boolean，代表本次更新有没有成功；失败一般也是库存不足，返回错误信息即可。

    * > **结论**：前面的库存判断检查的是「查出来那一刻」的库存，update 的影响行数才是「真正扣减那一刻」的结论，这一层是必要兜底。

    * > **易错点**：where 条件里的字段是 `voucher_id`（下划线形式），写条件前应与秒杀表的主键名核对。

### 完整实现与事务

* **查询该注入哪个 Service**

    * > **提示**：要查的是秒杀时间和库存，这些信息在秒杀券里而不在普通券里；实体类有 `Voucher` 与 `VoucherSeckill` 两个，对应的 Service 也有两个，此处应注入秒杀券的 Service。

    * 由于 `tb_voucher_seckill` 与 `tb_voucher` 共享 id，用秒杀券 Service 的 `getById(voucherId)` 查询没有问题。

* **参考实现**

```java
@Override
@Transactional
public Long seckillVoucher(Long voucherId) {
    // ① 查询优惠券信息
    VoucherSeckill voucher = voucherSeckillService.getById(voucherId);

    // ② 判断秒杀时间：未开始 or 已结束
    if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
        throw new BadRequestException("秒杀尚未开始！");
    }
    if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
        throw new BadRequestException("秒杀已结束！");
    }

    // ③ 判断库存
    if (voucher.getStock() < 1) {
        throw new BadRequestException("库存不足！");
    }

    // ④ 扣减库存
    boolean ok = voucherSeckillService.update(
            Wrappers.lambdaUpdate(VoucherSeckill.class)
                    .setSql("stock = stock - 1")
                    .eq(VoucherSeckill::getVoucherId, voucherId));
    if (!ok) {
        throw new BadRequestException("库存不足！");
    }

    // ⑤ 创建订单
    VoucherOrder order = new VoucherOrder();
    order.setId(redisIdWorker.nextId("order"));
    order.setUserId(UserHolder.getUser().getId());
    order.setVoucherId(voucherId);
    voucherOrderService.save(order);

    // ⑥ 返回订单 id
    return order.getId();
}
```

* **事务边界**

    * > **易错点**：这个方法同时做了新增订单和扣减库存两张表的写操作，必须加 `@Transactional`；不加事务一旦中途出问题就无法回滚。

    * > **提示**：调试时可以在 Redis 里把登录 token 的 TTL 改成永不过期（例如将 1791 改为持久化），避免反复登录打断测试。

## 库存超卖

### 压测复现

* **构造方式**

    * 用 JMeter 配置 200 个线程，请求 `localhost/voucher-order/seckill/7`，即 200 个用户同时请求同一张券。

    * 测试前把库存改回 100 并清空已有订单，预期只生成 100 个订单、恰好一半失败。

* **实测结果**

    * 聚合报告异常比例 45%，失败者全部报库存不足——失败比例低于预期的一半，本身已经是异常信号。

    * 数据库中库存变为 **-9**，订单数量为 **109**。

    * > **结论**：100 件库存卖出了 109 件，库存出现负数、订单也多出 9 条，这就是库存超卖。秒杀商品往往价值高而售价低，超卖会给商家带来巨大损失，是不可接受的。

* ** ⚠️ 不可接受的理由**

    * > **易错点**：语气可以说重一点——库存超卖在秒杀场景下极易出现，但它属于必须杜绝的问题，不能因为「只是多了几件」而容忍。

### 超卖的成因：查询与扣减之间的交叉

* **串行执行时的正确表现**

    * 线程一先查询，得到 stock = 1；判断 `stock > 0` 成立；扣减后库存变成 0。

    * 随后线程二查询得到 stock = 0，判断不成立，返回库存不足。最终库存 = 0，正确。

```text
【串行执行】库存只剩 1

线程一                            线程二
  │ 查询 -> stock = 1               │
  │ 判断 stock > 0，成立            │
  │ 扣减 stock: 1 -> 0              │
  │ 下单完成                        │
  │                                 │ 查询 -> stock = 0
  │                                 │ 判断不成立，返回「库存不足」

最终库存 = 0，正确
```

* **交叉执行时的超卖**

    * 线程一查询得到 stock = 1，尚未扣减时线程二切换进来查询，得到的同样是 1。

    * 线程一判断成立、扣减，库存 1 → 0；线程二拿自己先前查到的 1 判断同样成立，于是再扣一次，库存 0 → -1。

    * > **结论**：只要在线程一完成扣减之前有任意多个线程进来做查询，它们都会认为库存充足并都去扣减，库存最终必然超卖。

```text
【交叉执行】库存只剩 1

线程一                            线程二
  │ 查询 -> stock = 1               │
  │                                 │ 查询 -> stock = 1   <-- 也读到 1
  │ 判断 stock > 0，成立            │
  │ 扣减 stock: 1 -> 0              │
  │                                 │ 判断 stock > 0，也成立
  │                                 │ 扣减 stock: 0 -> -1

最终库存 = -1，超卖
```

### 并发安全问题的本质

* **并发安全问题**

    * > **定义**：多个线程操作同一份共享资源，且操作资源的代码有好几行，在这几行执行的中间多个线程互相穿插，从而产生错误结果。

    * 落到本例：共享资源是库存，代码是「查询 → 判断 → 扣减」三步，穿插发生在查询之后、扣减之前。

    * > **结论**：只要存在「先查后改」的多步操作序列，且没有任何互斥措施，高并发下必然出现穿插，这不是偶发而是放大——线程越多穿插机会越多。

## 悲观锁与乐观锁

* **两类锁的共同点**

    * > **定义**：悲观锁和乐观锁并不是某一把真正的锁，而是两种被设计出来的**理念**，用来应对同一个并发安全问题。

### 悲观锁

* **悲观锁（Pessimistic Lock）**

    * > **定义**：认为线程安全问题一定会发生，因此在操作数据之前先获取锁，强制线程串行执行。

    * 机理：既然并发有安全问题，那就不要并发——一个执行完另一个再执行。

    * 代价：不管多少线程都只能排队，性能并不好，高并发场景不太适合。

    * 代表实现：JDK 的 `synchronized`、`Lock`，以及数据库里的互斥锁。

### 乐观锁

* **乐观锁（Optimistic Lock）**

    * > **定义**：认为线程安全问题不一定发生，因此根本不加锁，而是在**更新数据的那一刻**判断之前有没有别的线程改过这份数据。

    * 判断依据：把自己查询到的值与库中当前值对比；一致则认为没人改过，放心修改；不一致则认为有安全问题，重试或报错。

    * 优势：因为不加锁、只在更新时加一次判断，性能比悲观锁好很多。

    * 关键点：整套方案的成败在于「怎么知道更新时别人有没有改过」。

* **选型理由**

    * > **提示**：多数情况下并不会真的发生穿插，为了极少数情况把所有线程都串行化显然不划算，这正是乐观锁的存在理由。

### 两者对照

| | 悲观锁 | 乐观锁 |
| :--- | :--- | :--- |
| 基本假设 | 认为线程安全问题**一定会**发生 | 认为线程安全问题**不一定**发生 |
| 做法 | 加同步锁让线程串行执行，确保同一时刻只有一个线程修改资源 | 不加锁，在更新时判断之前有没有人也来更新了；没有就更新，有就取消更新 |
| 优点 | 实现简单粗暴 | 不加锁，性能相对较好 |
| 缺点 | 必定串行执行，性能受影响 | 基于数据变更判断，容易出现「数据被改过但其实还能改」的误判，**成功率太低** |

## 乐观锁的两种落地方案

### 版本号法

* **版本号法**

    * > **定义**：给数据增加一个版本字段，每次修改都让版本号加一，通过版本号是否变化来判断数据有没有被修改过。

    * 查询阶段：除了查业务字段（库存），还要把版本号一起查出来。

    * 更新阶段：除了改业务字段，必须同时 `version = version + 1`；where 条件里加上「version 等于我查到的那个版本」。

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1,
    version = version + 1
WHERE id = #{id}
  AND version = #{version}
```

* **拦截过程**

    * 线程一查到库存 1、版本 1，更新时 where `id = 10 AND version = 1` 匹配成功，库存变 0、版本变 2。

    * 线程二也查到版本 1，执行同样语句时库中版本已是 2，where 条件不成立，更新失败，不扣库存也不下单。

    * > **结论**：「有没有更新成功」通过 update 的返回值即可判定，这正是扣减步骤要用 boolean 兜一层的原因。

```text
  线程一                              线程二
    │ 查询 stock=1, version=1           │
    │                                   │ 查询 stock=1, version=1
    │ UPDATE SET stock=0, version=2      │
    │ WHERE id=10 AND version=1         │   <-- 匹配，更新成功
    │                                   │
    │                                   │ UPDATE SET stock=0, version=2
    │                                   │ WHERE id=10 AND version=1
    │                                   │ <-- version 已是 2，条件不成立
    │                                   │ <-- 更新失败，不扣库存，不下单
```

### CAS 法

* **CAS（compare-and-swap，比较并交换）**

    * > **定义**：不额外引入版本号，直接用业务字段本身的变化来充当「版本」，先比较再修改。

    * 简化依据：版本号法里「查版本 + 每次改版本」的动作，与库存场景里「查库存 + 每次改库存」的动作完全重合，因此可以让库存自己充当版本号。

    * 用法：查询时只查库存；更新时要求 where 里的库存等于我查到的库存，条件成立才扣减。

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1
WHERE id = #{id}
  AND stock = #{stock}
```

* **拦截过程**

    * 两个线程都查到 stock = 1，线程一执行 `WHERE id = 10 AND stock = 1` 匹配成功，库存变成 0。

    * 线程二再执行时库中库存已是 0，条件 `stock = 1` 不成立，扣减动作不执行。

* **两种方案的取舍**

| | 版本号法 | CAS 法 |
| :--- | :--- | :--- |
| 判别字段 | 额外维护的 version 字段 | 业务字段本身（本例为 stock） |
| 每次更新要改 | 业务字段 + version | 只改业务字段 |
| 查询要查 | 业务字段 + version | 只查业务字段 |
| 适用 | 通用，应用最广泛 | 库存这类「本就要查、本就要改」的字段，加版本号属于多余 |

* **本例选型**

    * 库存场景下添加版本号显然是多余的，直接用库存判断即可，所以采用 CAS 法。

## CAS 落地：从 89% 失败率到预期的一半

### 在 where 里带上查到的库存

* **落地写法**

```java
// 扣减库存：乐观锁方案
boolean ok = voucherMapper.update(null, Wrappers.<Voucher>lambdaUpdate()
        .set(Voucher::getStock, voucher.getStock() - 1)  // set 赋值：stock = stock - 1
        .eq(Voucher::getId, voucher.getId())             // where 条件一：id = ?
        .eq(Voucher::getStock, voucher.getStock()));     // where 条件二：stock = 我查到的 stock
```

```sql
UPDATE voucher
SET stock = stock - 1
WHERE id = ?
  AND stock = ?;   -- 我查到的那个 stock
```

* **要点**

    * > **结论**：把「我更新的时候你还在不在」这件事塞进 SQL 的 where 条件，让数据库替我们判断；全程一把锁都没加，线程却是安全的。

    * 两个 `eq` 分别对应 `id` 与 `stock` 两个 where 条件，只要更新时的库存值等于查询时的库存值，就说明期间没人改过。

### ⚠️ 89% 失败率的成因

* **压测现象**

    * 测试前还原数据：清空所有订单，库存改回 100；JMeter 仍是 200 线程对 100 库存。

    * 聚合报告失败比例 **89%**；数据库中库存没有超卖，只卖出 20 件，订单约 20 条。

    * > **易错点**：200 人抢 100 件，正常的失败率应在 50% 左右；89% 说明失败被人为放大。

* **根因：所有线程读到同一个库存**

    * 库存还剩 100 时有大量线程同时涌入，因为没加锁它们并行执行，全部在「查询」这一步读到 stock = 100。

    * 执行 UPDATE 时，只有第一个线程把 100 改成 99；其余线程 where 里的 `stock = 100` 已经对不上，一行都改不动，全部失败。

```text
  并行的 100 个线程，全都读到 stock = 100
  ┌──────────────────────────────────────────────────────┐
  │  T1    T2    T3    T4    T5   ...              T100 │
  │   │     │     │     │     │                        │
  │  查    查    查    查    查                       查   │
  │ 100   100   100   100   100                      100 │
  └───┴─────┴─────┴─────┴─────┴────────────────────────┘
                          │
                          ▼
          执行 UPDATE ... WHERE id = ? AND stock = ?
                          │
          ┌───────────────┴────────────────┐
          ▼                                ▼
  WHERE stock = 100 成立            WHERE stock = 100 不成立
  stock: 100 → 99                    库里的值已经变成 99 了
  成功 1 个，更新 1 行                失败 99 个，更新 0 行
```

* **本质**

    * > **结论**：这些线程「太小心」了——只要发现数据被改过就认为有安全问题。但库存被改过并不等于不安全：库存还剩 99 时剩下的请求完全可以成功。这里发生了并发修改，却没有业务上的安全问题。

### 改进：只要求库存大于零

* **改进思路**

    * > **定义**：不再要求更新时的库存与查询时一致，只要求库存大于 0 即可扣减。

    * 理由：库存只要大于零，是 100 还是 57 都无所谓，随便减都没问题；不大于零才真该失败。

* **改动点**

    * 把第二个 `eq` 换成 `gt`（大于），并且右边不再是查到的值，而是 0。

```java
// 扣减库存：只判断库存大于零
boolean ok = voucherMapper.update(null, Wrappers.<Voucher>lambdaUpdate()
        .set(Voucher::getStock, voucher.getStock() - 1)
        .eq(Voucher::getId, voucher.getId())
        .gt(Voucher::getStock, 0));
```

* **复测结果**

    * 数据还原为库存 100、订单清空，JMeter 清空后重跑。

    * 聚合报告失败比例 **50%**，达到预期；数据库中库存恰好为 0，订单恰好 100 条。

    * > **结论**：库存没有超卖，订单数刚好等于库存数，且失败全部源于库存真正耗尽，超卖问题被解决。

### 提高成功率的其他方案

* **分段锁（分批加锁）**

    * > **定义**：把一份资源拆成多份分别加锁，从而缩小每次锁定的资源范围、提高成功率。

    * 举例：100 件库存拆到十张表，每张 10 件，用户去多张表里分别抢，成功率相当于提高十倍。

    * > **提示**：这种思想在 `ConcurrentHashMap` 里用过；它的实质是不再一次性锁定全部 100 个资源，而是每次只锁其中十个。

* **乐观锁的局限**

    * > **注意**：最终选用乐观锁并不代表它完美——它毕竟还要访问数据库，对数据库压力很大。真正的高并发秒杀场景，仅靠乐观锁远远不够，链路还需继续优化。

## 一人一单

### 需求成因与判定方式

* **一人一单**

    * > **定义**：同一张优惠券，同一个用户只能下一单。

    * 业务动机：秒杀券是赔本引流，目的是吸引更多用户进店体验并通过口碑传播；若 100 张订单全是同一个用户买的（等于黄牛包圆），活动就起不到宣传效果。

    * 判定方式：以 `user_id` 和 `voucher_id` 做联合查询，存在记录说明该用户已购买，不允许再下单。

    * > **注意**：不能简单给订单表加唯一主键，因为它已经有自己的主键了，只能靠查询 count 判断。

* **插入位置与执行顺序**

    * 新流程：判断秒杀时间 → 判断库存 → **按用户 id 与券 id 查询订单数** → 扣减库存 → 创建订单。

    * > **易错点**：顺序要调整，把扣减库存放到后面，做到「先判断、先下单、再扣库存」；如果先减了库存再去判断失败，前面的减库存就毫无意义。

### 先查后判拦不住并发

* **初步实现**

```java
// 一人一单：判断当前用户是否已经下过单
Long count = orderService.query(new OrderWrapper()
        .eq("user_id", userId)          // 条件一：user_id = 当前登录用户
        .eq("voucher_id", voucherId));  // 条件二：voucher_id = 当前优惠券
if (count != null && count > 0) {
    // 大于零证明至少有一条记录，说明这个用户已经下过单了
    return Result.fail("该用户已经购买过了");
}
```

* **要点**

    * 不需要查出具体数据，只查数量即可；count 大于零即代表至少下过一单。（无需判断等于 1。）

* **压测构造与结果**

    * JMeter 仍发 200 个请求，但在请求头里统一加上同一个 `authorization`（登录 token），因此服务端识别出的 200 个请求属于同一个用户。

    * 预期库存减 1 剩 99、订单只有 1 条；实测库存确实 99，但订单出现了 **10 条**，且 `user_id`、`voucher_id` 完全相同。

    * > **结论**：并发下一个用户仍下了多单，问题比之前轻（此前是同一用户包圆 100 单），但依然存在。

* **成因**

    * > **定义**：与库存超卖同源——先查询、再判断、最后写入，多线程穿插使得所有线程在查询阶段都拿到了同一个结果（count = 0）。

    * 数据库中原本没有订单时，100 个线程并发执行查询，查到的都是 0，判断全部不成立，于是接连插入 N 条订单。

### 改用悲观锁包住查询到下单

* **为何不能用乐观锁**

    * > **易错点**：乐观锁是在**更新**数据时使用的手段；一人一单这里是**新增（插入）**数据，数据压根不存在，无法判断「有没有被修改过」，要判断的是「是否存在」。因此这里只能走悲观方案。

* **加锁范围**

    * > **定义**：从「查询订单」开始，到「判断订单是否存在」，再到「扣减库存、创建订单」，这一整段逻辑整体加悲观锁。

    * 做法是把这段逻辑抽成一个方法（例如 `createVoucherOrder`），在其中用 `synchronized` 包裹。

    * `@Transactional` 也要跟着挪到这个方法上——加锁范围本质是写库范围（扣库存 + 创建订单），前面的查询不需要加锁。

* **锁对象不能是 this**

    * > **易错点** ⚠️：不建议把 `synchronized` 加在方法上——那样锁的范围变成整个方法、锁对象是 `this`，任何用户来了都要抢同一把锁，整个方法串行，性能很差。

    * 一人一单只要求**同一个用户**内部串行；张三和李四互不干扰，完全不需要同一把锁。

    * 因此应锁当前用户：改成同步代码块，手动指定锁对象为用户 id 转成的字符串。

### 锁对象必须取 userId.intern()

* **toString 为什么不行**

    * 每个请求进来拿到的都是一个全新的 id 对象；对象变了锁就变了，达不到锁定同一用户的目的。

    * `Long.toString()` 底层调用的是新建一个字符串的静态方法，每调一次都是全新字符串对象——即使 id 一直是 5，每次的锁对象仍然不同。

* **intern 的作用**

    * > **定义**：`String.intern()` 返回字符串在常量池中的规范表示——去字符串常量池里找值相同的那个字符串的引用返回。

    * 效果：只要值相同（例如都是 5），无论存在多少个字符串实例，`intern()` 返回的引用永远相同，从而保证「值相同 → 锁对象相同」。

    * > **提示**：这是把「值相同」翻译成「对象相同」的手段，正是这一步的关键点。

```java
String lockKey = userId.toString().intern();  // 值相同 -> 锁对象相同
synchronized (lockKey) {
    // 查询出订单 -> 判断订单是否存在 -> 扣减库存 -> 创建订单
}
```

* **收益**

    * 不同用户用不同的锁，锁定的资源范围变小，性能得到提升。

### 锁必须在事务提交之后释放

* **方法内部加锁的漏洞**

    * 方法执行的大致次序是：方法内开启并执行 → 获取锁 → 查询 → 减库存 → 创建订单 → **离开同步块释放锁** → 方法返回后由 Spring 提交事务。

    * 隐患：锁释放后事务尚未提交，此时其他线程进来查询订单，刚新增的订单可能还没写进数据库，照样查不到，于是重复下单。

* **正确做法**

    * > **易错点** ⚠️：把 `synchronized` 挪出方法体，放到调用处包住整个函数调用（先在外层取到 userId 并上锁，再调 `createVoucherOrder`）。

    * > **结论**：唯一安全的次序是「先获取锁 → 事务提交 → 再释放锁」。函数执行完毕意味着事务已提交、订单已入库，此时释放锁，后来的线程一定查得到订单。

### 让事务真正生效：AopContext

* **this 调用导致事务失效**

    * 事务生效的前提是 Spring 对当前类做了动态代理，由代理对象来做事务处理。

    * 在类的内部直接调用 `createVoucherOrder(voucherId)`（省略了 `this`），拿到的是目标对象而非代理对象，因此没有事务功能——这是 Spring 事务失效的典型情形之一。

* **解决方案**

```java
// 拿到当前对象的代理对象（与事务有关的那个代理）
IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
proxy.createVoucherOrder(voucherId);   // 用代理对象去调，而不是 this
```

    * `AopContext.currentProxy()` 拿到当前对象的代理对象，返回值为 `Object`，需要强转成对应接口类型；被调方法必须在 `IVoucherOrderService` 接口中声明，否则无法基于接口调用。

    * **依赖**：底层依赖 aspectj，需要引入 aspectj 依赖。

    * **注解**：启动类加 `@EnableAspectJAutoProxy(exposeProxy = true)`；`exposeProxy` 默认为 `false`，不暴露时 `AopContext.currentProxy()` 取不到代理对象。

* **两个必须同时守住的要点**

    * > **结论**：一是释放锁的时机必须在事务提交之后，二是内层方法的事务必须真正生效；两者缺一，一人一单都会再次失效。

### 复测结果

* **验证**

    * 清理数据：订单清空、库存改回 100；JMeter 清空结果后跑 200 线程同一 token 的请求。

    * 聚合报告失败比例 **99.5%**；数据库中库存 99（只减 1）、订单 1 条。

    * > **结论**：一人一单问题解决；方案同样是加锁，但这次用悲观锁，并通过选取用户 id 这种特殊锁对象缩小了锁定范围，在一定程度上提升了性能。

## 集群下本地锁失效

### 用两份实例模拟一个集群

* **构造方式**

    * 在 IDEA 里 `Ctrl+D` 复制当前启动项，得到一份**新的启动配置**；每份新配置底层会启一台独立的 Tomcat，从而模拟多台机器。

    * 需要覆盖端口避免冲突：在新启动项的 JVM 参数里加 `-Dserver.port=8082`，覆盖配置文件中的端口，另一台保持 8081。

    * 以此方式继续复制即可得到三节点、四节点集群。

* **单机与集群的差别**

    * > **定义**：本项目虽然是单体项目，但为应对高并发会把同一个项目部署到多台机器形成负载均衡集群；而 `synchronized` 只在单个 JVM 内有效，集群模式下就会出问题。

### nginx 反向代理与负载均衡

* **配置**

```nginx
upstream backend {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}

server {
    listen 8080;

    location /api {
        proxy_pass http://backend;
    }
}
```

* **要点**

    * Nginx 监听 8080，把 `/api` 路径反向代理到 upstream；upstream 里列出多个节点，需要更多节点时继续复制并改对应 IP 和端口。

    * 改完配置必须执行 `nginx -s reload` 重新加载才能生效。

    * 默认采用**轮询**的负载均衡规则。

    * 访问方式：请求打到 8080（Nginx），由它分发到 8081 / 8082；连刷两次 list 接口即可在两个节点各看到一次请求日志，证明负载生效。

### 复现：同用户两个请求同时进了锁

* **构造过程**

    * 在 `synchronized` 加锁处打断点，用同一个用户的 `authorization` 头，对同一个券 id 通过 Nginx 连发两次秒杀下单请求。

    * > **易错点**：两个服务都进到了断点里，两边用户 id 都是 5——明明有锁，却因为请求被负载均衡分到了两台机器而双双拿到锁。

    * 继续在查询处打断点放行，两个查询得到的 count 都是 0；全部放行后两者都去扣库存、都创建订单，订单表出现 2 条记录。

    * > **结论**：集群模式下虽然用了 `synchronized`，却没有锁住，并发安全问题再次出现。

### JVM 的锁跨不过进程

* **单体下的锁原理**

    * > **定义**：JVM 内部靠维护一把**锁的监视器对象**实现互斥；本例拿来当锁的是字符串常量池里 userId 对应的那个字符串。

    * 同一个 JVM 内，id 值相同就意味着永远是同一个监视器对象。线程一获取成功后监视器记录线程一，线程二再来获取时发现已被占用，只能等待；等线程一释放后才能进入，此时再查订单必定存在，于是不会插入。

    * 未加锁时则会出现查询与插入交叉：线程一查到不存在、线程二也查到不存在，随后两者都插入，同一笔订单被插入两次。

```text
      线程-1                        线程-2
        │                             │
     查询订单                          │
        │ …… 发现不存在                 │
        ├──────────────┐               │
        │              │            查询订单
        │              │               │ …… 也是不存在
        │              ├───────────────┤
        │              │               │
     插入新订单                    插入新订单
        │                             │
        └────► 订单被插入了两次 ◄───────┘
                        │
                并发安全问题！
```

* **集群下监视器不再唯一**

    * 一次新的部署就是一个全新的 Tomcat，也就是一个全新的 JVM；两套 JVM 各有自己的堆栈与方法区，因此也各有自己的字符串常量池。

    * userId 同样是 5，但 JVM2 生成的锁监视器与 JVM1 的监视器不是同一个对象；线程三走自己的监视器时它是空的，于是也获取成功。

    * > **结论**：集群或分布式系统下存在多个 JVM，每个 JVM 内都有自己的一把锁，于是每个 JVM 都能有一个线程拿到锁而并行运行，安全问题由此产生。

```text
        单体：一个 JVM                    集群：两个 JVM
  ┌───────────────────────────┐    ┌───────────────────────────┐
  │  字符串常量池              │    │  字符串常量池              │
  │    "5" ──► 锁监视器 M      │    │    "5" ──► 锁监视器 M'     │
  └─────────────▲─────────────┘    └─────────────▲─────────────┘
                │                                │
        线程一 拿到 ✓                   线程三 拿到 ✓
        线程二 等待 ✓                   线程四 等待 ✓
                                            ↑
                             本该被挡住，却被放行了
```

* **留给下一环的缺口**

    * 集群若部署十台二十台，就意味着并行运行的线程至少有十个同时获得者，安全问题成倍放大。

    * 出路：必须让多个 JVM 共用同一把锁。这样的锁 JVM 不提供，需要自己实现，也就是跨 JVM、跨进程的分布式锁。
