# Redis 内存回收与淘汰策略

## 内存淘汰（Eviction）与它的触发时机

   * **内存淘汰策略（Eviction Policy）**

       * > **定义**：当 Redis 的内存使用达到设置的阈值时，由 Redis 主动挑选一部分 key 进行删除，与 key 是否过期无关

       * 触发前提：内存不够用了，只能靠删 key 腾空间；此时不再关心 key 有没有到期

       * 适用背景：数据量太大、写入持续不断，即使把过期 key 全部删干净，内存依然顶到上限

   * **检查内存的时机**

       * > **结论**：客户端执行任何命令时，都要先检查内存够不够，不够就清理

       * 检查点挂在命令执行流程上：命令解析完成、真正执行之前，在 `processCommand` 里做各项检查

       * `processCommand` 的常规检查包含权限校验等，其中一项就是服务器内存上限检查

       * 不采用"等到内存溢出那一刻再处理"，因为那时已经晚了

---

## processCommand 到 performEviction 的路径

   * **淘汰的两个前置条件**

       * 条件一：配置了 `server.maxmemory`（内存上限）；没配就等于内存没有上限，不做任何清理

       * 条件二：当前没有在执行 LUA 脚本；正在跑脚本时跑去删 key，很可能导致脚本出问题

       * 两个条件都满足，才尝试进行内存清理，执行 `performEviction` 做驱逐

   * **performEviction 的执行结果**

       * 返回成功：内存腾出来了，继续执行客户端命令

       * 返回 fail：说明应该清理但清理失败，即内存确实不够，Redis 报 out of memory（OOM）错误

       * 报 OOM 之后直接 reject 掉该命令，不再执行

   * **整条路径**

       * 代码化描述

           ```text
           客户端命令
               |
               v
           [ 命令解析 ]
               |
               v
           processCommand  —— 执行真正命令之前的各种检查
               |
               +-- 权限等常规检查
               |
               +-- 配了 maxmemory 吗？
               |       +-- 没有 -> 内存没有上限 -> 不做任何清理
               |
               +-- 当前正在执行 LUA 脚本吗？
               |       +-- 是 -> 跳过（脚本执行中途删 key 会让脚本出问题）
               |
               +-- 两个条件都成立 -> 执行 performEviction() 尝试淘汰
                        |
                        +-- 返回成功 -> 内存腾出来了 -> 继续执行命令
                        |
                        +-- 返回 fail -> 内存确实不够 -> 报 OOM -> reject 该命令
           ```

## 八种淘汰策略的命名规律

   * **策略总数与配置方式**

       * `performEviction` 内部支持八种不同策略

       * 配置方式：在配置文件中设置 `maxmemory-policy`，值改成想要的策略即可

   * **`noeviction`**

       * 含义：不淘汰任何 key，内存不足时不允许写新数据，直接报错

       * 事实上默认就是这种策略

   * **名字拆成两段：前缀 + 后缀**

       * 后缀两两相同，说明属于同一类算法、用的是同一种挑法

       * 前缀不同，决定去哪个字典里挑

       * 排布

           ```text
           allkeys-random      volatile-random
           allkeys-lru         volatile-lru
           allkeys-lfu         volatile-lfu
           ```

   * **前缀：决定淘汰范围**

       * `allkeys`：在全体 key 里挑，来源是 `redisDB` 结构里的 `dict` 字典，该字典存储 Redis 中的所有 key

       * `volatile`：在设置了过期时间的 key 里挑，来源是 `redisDB` 里的 `expires` 字典，该字典保存带过期时间的 key

       * > **结论**：两个前缀唯一的含义差别就是挑选位置——一个在所有 key 里挑，一个在有过期时间的 key 里挑

   * **后缀：真正的算法**

       * 剥掉前缀后，八种策略只剩四种算法

       * 四种算法的挑选对象

           | 算法 | 挑谁 | 直觉 |
           | :--- | :--- | :--- |
           | `ttl` | 剩余 TTL 最小的 | 都快不行了，直接送一程 |
           | `random` | 随手蒙一个 | 不知道该挑谁，挑到谁是谁 |
           | `lru` | 最久没被访问的 | 这么长时间没人访问，还要它干嘛 |
           | `lfu` | 被访问次数最少的 | 几乎没人访问，优先淘汰 |

       * 随机策略基本不会有人使用，太随意

## LRU 与 LFU 的差别

   * **LRU（Least Recently Used）**

       * > **定义**：最少最近使用，看的是 key 最近一次被访问的时间

       * 判定方式：用当前时间减最后一次访问时间，得到"多久没有被访问"，该值越大越优先淘汰

       * 要找的是最近使用时间最小的那个 key

       * > **易错点** ⚠️：不要翻译成"最近最少使用"，原文是 Least Recently，Least 是"最少"

   * **LFU（Least Frequently Used）**

       * > **定义**：最少频率使用，统计的是 key 被访问的次数（频率）

       * 判定方式：访问频率越高，将来被淘汰的概率越小；频率很低、几乎没人访问的优先淘汰

       * > **提示**：真正被叫做"最近最少使用"的反而是 LFU，LRU 叫"最少最近使用"，两者差异很大

   * **两者对照**

       * LRU 看时间：最近一次访问离现在多久

       * LFU 看频率：一段时间内被访问了多少次

## redisObject 的 24 比特统计字段

   * **字段位置与长度**

       * Redis 中存储的所有键值最终都被封装成 `redisObject` 对象

       * `redisObject` 的属性包括类型（string / list / set / hash 等）、`encoding` 编码方式、引用计数、指向真实数据的指针

       * 关键字段是 `LRU`，长度 **24 个比特位**，用来记录 LRU 值和 LFU 值

       * 记的东西随配置的策略不同而不同

   * **配成 LRU 时**

       * 记录以**秒**为单位的最近一次访问时间

       * 长度只有 24 比特位，所以只能按秒记

       * 用当前时间减该时间，差值越大越优先淘汰

   * **配成 LFU 时：24 位分两段**

       * 高 16 位：最近一次访问时间，以**分钟**为单位（16 位太小，只能按分钟记）

       * 低 8 位：逻辑访问次数，取值 0 ~ 255

       * 位划分

           ```text
            24 bit LRU 字段（配 LFU 时）
            +--------------------+------------+
            |  高 16 bit         |  低 8 bit  |
            +--------------------+------------+
            | 最近一次访问时间   | 逻辑访问次数|
            |   （以分钟为单位） |  (0 ~ 255) |
            +--------------------+------------+
           ```

   * **为什么叫"逻辑"访问次数**

       * 8 个比特位最大才 255，不可能真按 255 次封顶去记真实访问次数

       * 高并发业务下单个 key 被访问成千上万次是常态，8 位装不下

       * 所以记的不是真实访问次数，而是**逻辑访问次数**，用它代替访问频率

## 逻辑访问次数的累加算法

   * **累加的四个动作**

       * 第一步：生成一个 0~1 之间的随机数，记作 $R$

       * 第二步：拿旧的逻辑访问次数乘以 LFU 因子（默认值 **10**），再加 1，作为分母

       * 第三步：用 1 除以该分母得到 $P$，该值一定小于 1

       * 第四步：比较 $R$ 与 $P$，$R < P$ 时计数器加一

   * **公式**

       $$
       P = \frac{1}{\text{old\_count} \times \text{lfu\_factor} + 1}, \quad \text{lfu\_factor} 默认 = 10
       $$

       $$
       \text{count}' = \begin{cases} \text{count} + 1, & R < P \\ \text{count}, & R \ge P \end{cases}
       $$

   * **举例推演**

       * 旧次数为 0 时：$0 \times 10 + 1 = 1$，$P = 1 \div 1 = 1$，$R$ 必小于 1，计数器一定加一，即第一次访问一定加一

       * 旧次数为 1 时：$1 \times 10 + 1 = 11$，$P = 1 \div 11 < 0.1$，$R < P$ 的概率大幅降低，计数器不一定加一

   * **累加的性质**

       * 除第一次必然加一外，后续访问不一定累加，会隔一段时间才累加一次，取决于概率

       * 访问次数越多，分母越大，$P$ 越小，$R < P$ 的概率越小，累加可能性越来越低：一开始概率高，后来概率越来越低

       * 记录的是概率性的次数，不准确；但只要访问次数足够多，这个值仍会越来越大

       * 上限判断：超过 255 就取 255

       * > **结论**：用 8 个比特位就能量化反映一个 key 的访问频率——虽不准确，但访问频率越高值越大，这就够了

## 逻辑访问次数的衰减

   * **为什么要衰减**

       * 反例场景：某 key 早期被频繁访问，逻辑访问次数已达最大值 255，随后一年无人访问

       * 若不衰减，该 key 的计数永远是最大值、永不淘汰，这不合理

   * **衰减算法**

       * 用当前时间（分钟）减去高 16 位记录的上次访问时间（分钟），得到以分钟为单位的间隔

       * 用该间隔除以 `lfu-decay-time`（衰减周期，默认 **1** 分钟）

       * 即距离上次访问隔了多少分钟，计数器就减几；最低为 0，不会为负

       * 超过 255 分钟没被访问过，计数器恢复成 0

   * **衰减公式**

       $$
       \text{decay} = \left\lfloor \frac{\text{当前时间(分钟)} - \text{上次访问时间(分钟)}}{\text{lfu-decay-time}} \right\rfloor, \quad \text{count} = \max(0, \text{count} - \text{decay})
       $$

   * **参数可调**

       * LFU 因子与衰减周期都可以通过配置文件配置

       * 也可以通过命令行 `config set` 配置

   * **两者记录内容的对照**

       * LRU 算法：24 位记最近一次访问时间

       * LFU 算法：高 16 位记时间（分钟），低 8 位记逻辑访问次数（相当于频率）

## 淘汰池（Eviction Pool）

   * **为什么需要淘汰池**

       * Redis 中可能有数百万 key，逐个拿来做 TTL / LRU / LFU 比较并排序，一次淘汰的耗时会非常恐怖，不可行

       * Redis 采用的不是严格意义上的真正 LRU，而是整了一个池子做驱逐淘汰

   * **样本法**

       * 池子一开始是空的

       * 从数据库里挑一些样本放进池子，在池子内统一比较：谁快到期了、谁空闲太久了

       * 不是随便找一个，而是找一堆再统一比较谁最该被淘汰

       * 准确率不如全量遍历，但可以接受；性能更好，抽样本即可

   * **候选 key 的来源**

       * Redis 有 0 ~ 15 共 16 个库，先拿到一个库，再从该库里挑 key

       * 挑法是随机挑选样本，一次挑 `maxmemory-samples` 个，默认值 **5**

       * 挑出来的 5 个不一定都进池子：没设超时时间的 key、经常被访问的 key 不该被淘汰，需要按标准筛选

## idle time：三种算法的统一排序标准

   * **为什么要统一**

       * 不同策略有不同筛选标准，若各写一套逻辑，策略增加时代码会越来越麻烦

       * 统一办法：池子按 key 的某一个值做**升序排列**，值越大的优先淘汰（倒着来）

       * 统一后流程固定：key 放进去 → 升序排列 → 从尾部倒着找，找到的就是最该被淘汰的那个

       * 排序模式统一（升序找最大），"按什么排序"由各算法个性化决定

   * **三种算法的 idle time 算式**

       * LRU：用当前时间减去最近一次访问时间，得到空闲时间；空闲越久越该淘汰，符合升序淘汰逻辑

       * LFU：用 LFU 最大值 255 减去逻辑访问次数；频率越小，减完的值越大，越该淘汰

       * TTL：用最大时间减去剩余 TTL；剩余时间越少，减完的值越大，越该淘汰

       * > **注意**：TTL 这里要用 long 的最大值 `LONG_MAX` 去减剩余时间

       * 三种算式

           | 策略 | 算式 | 结果的含义 |
           | :--- | :--- | :--- |
           | `allkeys-lru` / `volatile-lru` | `当前时间 - 最近一次访问时间` | 真正空闲了多久 |
           | `allkeys-lfu` / `volatile-lfu` | `255 - 逻辑访问次数` | 离"最不常用"还差多少 |
           | `volatile-ttl` | `LONG_MAX - 剩余TTL` | 离"最长寿命"还差多少 |

       * 三种算式都保证：idle time 越大，越应该被淘汰

       * > **提示**：只有 LRU 那条才是真正的空闲时间，另外两条不是；统一叫 idle time 纯粹是为了代码上统一

## 入池筛选与倒序删除

   * **候选 key 凭什么进池子**

       * 算完 idle time 不等于能进池子，池子还要做一次判断，不是什么 key 都能放

       * 本质是"比烂"：拿自己的 idle time 跟池子里最小的那个比

       * 池子没满：直接放进来

       * 池子满了：自己的 idle time 必须比池子里至少一个的 idle time 更大，才说明更烂、更该被淘汰，可以把最小的那个挤出去、自己进来

       * 筛选过程

           ```text
           淘汰池（按 idle time 升序）
           +----+------+--------+-----------+---------+
           | k1 | k2   | k3      | ...       | kN      |   <- 最右边 idle time 最大
           +----+------+--------+-----------+---------+      最该被淘汰
             ^
             | 最小值

           新候选 key 来了：
              池子没满  -> 直接放进来
              池子满了  -> 算自己的 idle time
                           比池子里最小的那几个还大吗？
                              |-- 否 -> 比它们都干净，不该淘汰 -> 丢弃
                              |-- 是 -> 比它们更烂 -> 把最小的那个挤出去，自己进来
           ```

       * 样本里的 5 个 key 逐个这样判断，直到全部处理完

   * **多库循环**

       * 一个库处理完，还要看有没有下一个库，有就循环回去继续处理，直到 16 个库都处理完

       * > **提示**：一般建议只使用 0 号库，少很多次循环，效果更好

   * **删除与外层循环**

       * 从池子里删除时按**倒序**删：idle time 值越大越该删

       * 每次删掉一个就检查释放的内存是否够；够了就结束，不够就回到流程上方再看一次策略、再删一个，如此循环

       * 每循环一次都会往池子里再放一批 key，并与池中已有 key 比较：idle time 小的被淘汰出池，值较大的被保留

       * 循环次数越多，池中存放的 key 越接近 idle time 最大的那些 key，越接近真正的 LRU 算法，准确率越来越高

       * 因此不必担心样本法的准确率问题

## performEviction 的整体流程

   * **流程的三个判断**

       * 先判断内存是否充足：已用内存没达到最大值就说明充足，函数直接结束

       * 内存不充足时判断策略是否为 `noeviction`：是则直接结束，由上层报错

       * 不是 `noeviction` 时判断前缀是 `allkeys` 还是 `volatile`：`allkeys` 走 db 的 `dict` 淘汰，`volatile` 走 db 的 `expires` 淘汰，从不同地方挑

   * **随即开始真正淘汰**

       * 随机模式最简单：直接从库里随便挑一个删掉，再判断释放的内存是否满足需要；不够就回到上方再判断、再删，循环到删够为止

       * 非随机模式（LRU / LFU / TTL）的共同点：都要取出 key 的 TTL 值、LRU 值或 LFU 值来做比较

   * **随机与采样类策略的流程差异**

       * 随机：挑一个就删，删完判内存，不够则重来

       * LRU / LFU / TTL：先抽样本进淘汰池，按 idle time 升序排好后倒序挑最大的删

## 内存回收全景

   * **两种回收策略**

       * 内存过期策略：给 key 设置过期时间，到期后想办法删掉

       * 内存淘汰策略：key 都没过期但内存已达到上限时采用

   * **过期策略的两种删除方式**

       * **惰性删除**：访问某个 key 的那一刻检查是否过期，过期就删除

       * **周期性删除**：Redis 内部有定期任务，每隔一段时间尝试清理一部分过期的 key

   * **内存淘汰策略的八种构成**

       * `noeviction`：不做驱逐，内存不足直接报错

       * 其余七种：两个随机（`allkeys-random`、`volatile-random`）、两个 LRU、两个 LFU、一个 `volatile-ttl`

       * 之所以两两成对：既可以从所有 key 里淘汰，也可以从有过期时间的 key 里淘汰

       * 关键是把 TTL、LRU、LFU 三个算法各自以什么为标准弄清楚

   * **淘汰策略速查**

       | 策略 | 淘汰范围 | 挑谁 |
       | :--- | :--- | :--- |
       | `noeviction`（默认） | 不淘汰 | 不删任何 key，内存不足时直接报 OOM 并拒绝写入 |
       | `volatile-ttl` | 设了 TTL 的 key | 剩余 TTL 最小的 |
       | `allkeys-random` | 所有 key | 随机的 |
       | `volatile-random` | 设了 TTL 的 key | 随机的 |
       | `allkeys-lru` | 所有 key | 空闲时间最长的（最近最少使用） |
       | `volatile-lru` | 设了 TTL 的 key | 空闲时间最长的（最近最少使用） |
       | `allkeys-lfu` | 所有 key | 逻辑访问次数最小的（最少频率使用） |
       | `volatile-lfu` | 设了 TTL 的 key | 逻辑访问次数最小的（最少频率使用） |

   * **相关配置项**

       | 配置项 | 默认值 | 作用 |
       | :--- | :--- | :--- |
       | `maxmemory` | 0（不限制） | 内存上限，超过就触发淘汰 |
       | `maxmemory-policy` | `noeviction` | 淘汰策略 |
       | `maxmemory-samples` | 5 | 每个库随机抽取多少个候选 key 进淘汰池 |
       | `lfu-decay-time` | 1（分钟） | 逻辑访问次数的衰减周期 |
