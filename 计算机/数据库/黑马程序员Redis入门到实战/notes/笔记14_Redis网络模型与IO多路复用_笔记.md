# Redis 网络模型与 IO 多路复用

## 用户空间与内核空间

### 用户应用为什么碰不到硬件

* **系统调用接口**

    * > **定义**：内核在设备驱动之上形成内存管理、进程管理、文件系统管理、网络管理，再往上一层封装出对外提供的接口，用户应用与它的依赖库只能调用这些接口间接访问硬件。

    * 用户应用（MySQL / Redis 等）无法直接访问计算机硬件（CPU、内存、网卡、磁盘等），必须经由发行版这层壳去访问内核，再由内核操作硬件。

    * 不同发行版（如 openEuler、CentOS）只是包在 Linux 外面的壳，内部内核都是 Linux。

    * 内核需要先有各个设备的驱动，才能在其基础上形成对内存、进程、文件系统和网络的管理能力。

### 为什么要隔离

* **寻址空间**

    * > **定义**：内核与用户应用都无法直接访问物理内存，只能分配不同的虚拟内存空间并映射到物理内存；访问时使用的虚拟地址是一个从零开始的无符号整数，最大值取决于 CPU 的地址总线和寄存器带宽。

    * 32 位系统的带宽一般是 32，地址最大值为 $2^{32}-1$，寻址范围从 `0x00000000` 到 `0xFFFFFFFF`。

    * 内存地址的每一个值代表一个存储单元，也就是一个字节；$2^{32}$ 个地址即 $2^{32}$ 个字节，即 4GB，这就是 32 位系统寻址空间最多 4GB 的原因。

    * 32 位进程中，低位的 3GB 划分为**用户空间**，高位的 1GB 划分为**内核空间**。

```text
32 位进程的完整寻址空间：0x00000000 ~ 0xFFFFFFFF

0x00000000                                          0xFFFFFFFF
┌───────────────────────────────────┬───────────────────┐
│          用户空间   3GB            │   内核空间  1GB   │
│          低位地址                  │   高位地址         │
│          只能执行 R3 指令          │   可执行 R0 指令  │
└───────────────────────────────────┴───────────────────┘
```

* **隔离的动因**

    * 内核本质也是应用，运行时同样要消耗 CPU、内存等设备资源（例如系统启动后什么都不干也会占用数 GB 内存和百分之十几的 CPU）。

    * 用户应用也在消耗这些资源；不加以限制、让用户应用随意操作资源，就可能导致冲突甚至整个系统崩溃。

    * 因此必须把用户应用与内核隔离开。

### 指令权限等级

* **R0 与 R3**

    * > **定义**：CPU 把指令按风险等级划分为 R0 到 R3 四级，R3 风险最低、任何用户应用都可访问，R0 风险最高、属于系统级指令。

    * Linux 没有划分那么多级别，只用了两级：3 代表最低，0 代表风险等级最高（Windows 则划分了完整的四个等级）。

    * 用户空间里能执行的仅仅是 R3 级别的命令，不能直接调用系统资源，必须通过内核提供的接口访问。

    * 内核空间可以执行所有特权命令、R0 级别的命令，可以调用一切系统资源。

* > **易错点**：内存隔离和权限隔离是两回事。切地址空间解决的是「你碰不到我的内存」，切指令等级解决的是「你发不出我的指令」。少任何一层，隔离都不成立。

### 用户态与内核态

* **状态切换**

    * > **定义**：进程运行在用户空间时称为**用户态**，运行在内核空间时称为**内核态**；进程因业务需要执行特权命令、调用系统资源，会在两种状态之间来回切换。

    * 一般情况下用户应用运行在用户空间，内核应用运行在内核空间。

    * IO 读写涉及磁盘访问或网卡访问，都会触碰系统硬件，因此一定会涉及内核态。

### 一次读写的边界跨越

* **两级缓冲区**

    * 用户空间有读写缓冲区，作用等同于用户 IO 流里的缓冲流：写先写进缓冲区再一次性写出，读先读到缓冲区。

    * 内核空间也有缓冲区，主要起缓存作用：读一次之后数据缓存在内核，下次再读若有则可直接返回。

```text
用户空间                                    内核空间
┌──────────────┐   系统调用   ┌───────────────────────┐
│  用户缓冲区   │ ◄─────────► │   内核缓冲区（缓存）   │
└──────┬───────┘             └───────────┬───────────┘
       │                                     │
    业务处理                          磁盘 / 网卡
```

* **写流程**

    * 先在用户态完成业务处理，把数据写入用户缓冲区。

    * 要写往磁盘或网卡必须切换到内核态；此时内核空间里并没有要写的数据，必须先把用户缓冲区的数据拷贝到内核缓冲区，再由内核缓冲区写入磁盘/网卡。

* **读流程**

    * 用户态发起读请求（系统调用）进入内核态，内核先判断有没有数据。

    * 没有数据就要等待：读磁盘要先寻址，读网卡要等网络上别人的数据传过来。

    * 数据到达后从磁盘或网卡读入内核缓冲区，此时才算「数据就绪」。

    * 处理数据与系统硬件无关、需在用户空间运行，因此要把内核缓冲区的数据拷贝回用户缓冲区，再在用户空间做处理。

* **影响 IO 效率的两个核心点**

    * 数据的无效等待：别人没有数据来的时候只能白等。

    * 缓冲区的数据拷贝：内核空间往用户空间、用户空间往内核空间来回拷贝。

    * Linux 的五种 IO 模型都是针对这两个点在做优化。

## Linux 的五种 IO 模型

### 读数据的两个阶段

* **两阶段划分**

    * 阶段一：用户等待数据就绪，即等硬件设备把数据送到内核缓冲区（磁盘寻址完成并读入内核缓冲区，才算数据准备好）。

    * 阶段二：把内核缓冲区的数据拷贝/读取到用户缓冲区（用户空间）。

    * 不同 IO 模型的差别，就在这两个阶段的处理方式上。

* **五种模型与两阶段对照**

    | 模型 | 阶段一：等待数据就绪 | 阶段二：拷贝数据到用户空间 |
    | :--- | :--- | :--- |
    | 阻塞 IO | 阻塞等待 | 阻塞 |
    | 非阻塞 IO | 不阻塞，立即返回失败 | 阻塞 |
    | IO 多路复用 | 阻塞等待，但一次监听 N 个 fd | 阻塞 |

* **五种模型的名单**

    * 阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO、异步 IO。

### 阻塞 IO

* **阻塞 IO（blocking IO）**

    * > **定义**：两个阶段用户进程全程处于阻塞等待状态。

    * 用户应用调用 `recvfrom` 尝试读数据，只有该函数返回结果才算结束，否则用户进程一直等待。

    * 内核检查发现没有数据时有两种处理方案：立即返回「没有数据」的失败信息，或者等到有数据为止；阻塞 IO 采用后者，不返回失败而是等待。

    * 等待数据就绪（磁盘或其他硬件设备的数据读到内核缓冲区）后，再将内核数据拷贝到用户空间，返回 OK 给用户进程。

    * 在返回 OK 之前的数据等待阶段与数据拷贝阶段，用户进程全程什么都干不了。

### 非阻塞 IO

* **非阻塞 IO（non-blocking IO）**

    * > **定义**：阶段一不等待，内核发现没有数据时立即返回失败信息；阶段二的数据拷贝过程依然是阻塞状态。

    * 用户应用锲而不舍地反复调用 `recvfrom`；内核在后台把硬件数据读入内核缓冲区需要时间，这期间用户应用不断来问「就绪了吗」。

    * 这种不停地问称为**盲轮询**或**盲等**。

    * 直到某一刻数据真正到达内核缓冲区，这一次就不再报错，而是把数据从内核缓冲区拷贝到用户缓冲区，返回 OK。

    * > **结论**：相比阻塞 IO，非阻塞 IO 并没有提升进程性能——用户进程除了不停地问，什么也没干，最终还是要等到数据就绪；反而因为不断让 CPU 执行命令，导致 CPU 使用率暴增，某种程度上可能还不如阻塞 IO。

    * 某些特殊场景下不得不使用非阻塞 IO：IO 多路复用必须结合非阻塞 IO，才能有更好的性能表现。

### 信号驱动 IO

* **信号驱动 IO（signal-driven IO）**

    * > **定义**：用户进程调用 `sigaction` 向内核指定一个 fd 并绑定一个信号处理函数，然后立即结束、不用阻塞等待；fd 有数据时内核递交信号给用户进程，由已注册的信号处理函数得知数据就绪。

    * 阶段一非阻塞：注册完信号处理函数就可以去干别的事（例如处理其他客户端请求）；阶段二调用 `recvfrom` 读数据、即从内核空间拷贝到用户空间的过程依然阻塞。

    * 与非阻塞 IO 的区别：非阻塞 IO 是不停询问「准备好了吗」，用户进程虽不阻塞但做的是无用功；信号驱动 IO 是注册完就去忙正事，数据就绪了再来通知，是真正的非阻塞。

* **信号驱动 IO 的两个缺点**

    * 大量 IO 操作时信号非常多、并发非常高，无数信号提交给用户进程后会放进队列依次处理，信号过多可能导致信号队列溢出、部分信号丢失。

    * 不断传递信号需要频繁地将信号从内核空间拷贝到用户空间，性能受到影响。

    * 因此在并发场景下存在问题，使用不多。

### 异步 IO

* **异步 IO（asynchronous IO）**

    * > **定义**：不调用 `recvfrom`，而是调用 `aio_read` 通知内核「我想读哪个 fd、读到哪里去」，随后立即返回并去干别的事；内核监听 fd、等待就绪、被唤醒后把数据直接从内核拷贝到用户空间，全部办完再来通知成功。

    * 它不是「就绪了就通知」，而是「就绪了先别急，我把所有事都办完再来通知」。

    * 两个阶段都是非阻塞，用户进程都不用管。

* **异步 IO 的代价**

    * 高并发下不停地处理请求、不停地交 `aio_read` 给内核，内核里积累的 IO 读写任务越来越多；IO 读写效率较低，每增加一次任务都可能有大量内存消耗，很可能导致整个系统因内存占用过多而崩溃。

    * 使用异步 IO 必须做好对并发访问的**限流**。

    * 回调函数的机制使代码实现复杂度高很多。

    * 不如 IO 多路复用使用广泛：IO 多路复用并发能力也很好，实现起来相对简单。

## IO 多路复用

### 基本思想

* **文件描述符（file descriptor，fd）**

    * > **定义**：一个从零开始递增的无符号整数，每一个数字代表一个文件描述符，用来关联 Linux 中的一个文件。

    * Linux 中一切皆文件：硬盘中的普通文件或视频、键盘鼠标等硬件设备都可以看作文件，因而都有自己的 fd。

    * 网络套接字 socket 也有 fd，每一个客户端与服务器建立联系都有对应的 socket 和对应的 fd。

* **IO 多路复用（IO multiplexing）**

    * > **定义**：利用单个线程同时监听多个 fd，并且在某个 fd 可读或可写时得到通知，从而避免无效等待、充分利用 CPU 资源。

    * **复用的就是线程**：一个线程监听 N 个 fd，这个线程相当于服务员，每个客户端 socket 对应的 fd 相当于顾客。

```text
【排队模式：阻塞 / 非阻塞】
   顾客 A（还在纠结）──┐
   顾客 B（早就想好了）─┼──► 收银台（单个服务员）──► 后厨
   顾客 C（早就想好了）─┘        A 没想好 ⇒ B、C 全卡住
                                  ⇒ 无效等待

【叫号模式：IO 多路复用】
   顾客 A（还在纠结，没人会来打扰）
   顾客 B ──按铃──┐
   顾客 C ──按铃──┴──► 服务员同时盯着所有人，谁按铃就先服务谁
```

### 为什么不排队就够了

* **阻塞与非阻塞的共同短板**

    * 两者在阶段一都是调用 `recvfrom` 尝试读数据，区别只在没数据时怎么处理：阻塞 IO 让进程阻塞，非阻塞 IO 让 CPU 空转。

    * 无论阻塞还是空转，都不能充分发挥 CPU 的作用，即没有干正事。

* **单线程排队下的连锁等待**

    * 服务端单线程接收客户端 socket 请求时，很多客户端 socket 只能排队、一次处理一个。

    * 正在处理的 socket 若数据未就绪（不可读或不可写），整个线程阻塞等待，队列中的其他 socket 都要跟着等，哪怕其中有些数据早已就绪。

    * 增加线程（对应「增加服务员」）早期确实能提升效率，但线程越多 CPU 上下文切换开销越大，性能可能不增反降，还要付出更多资源开销。

### select 形式的完整流程

* **为什么要先 select 再 recvfrom**

    * 调用 `recvfrom` 那一刻并不知道目标 fd 有没有数据就绪，没就绪就不得不阻塞等待；因此要先弄清哪些 fd 就绪，再去调 `recvfrom`。

    * `select` 内部可以接收多个 fd：把每个客户端 socket 对应的 fd 都传给 `select`，由内核检查这些 fd 是否有任意一个就绪，只要有一个或多个就绪就直接返回结果。

```text
用户态                              内核态
  │                                    │
  │  ① select(多个 fd) ────────────────►│
  │                                    │ 检查这些 fd
  │                                    │ 全部未就绪 ⇒ 稍等（不可避免的等待）
  │                                    │ 任一/多个就绪 ⇒ 返回就绪结果
  │  ◄────────────── 返回（就绪了）      │
  │                                    │
  │  ② recvfrom(fd1) ─────────────────►│ 此时 fd1 必有数据，直接拷贝
  │  ③ recvfrom(fd2) ─────────────────►│
  │  …… 循环读完所有就绪的 fd           │
  │                                    │
  │  ④ 再回到 ①，监听下一批             │
```

* **等待的性质**

    * 所有 fd 都没就绪时的等待是不得不的等待，不算无效等待；等待期间由后台进程监听这些 fd，一旦有任意 fd 就绪就返回。

    * 拿到返回值后调 `recvfrom` 时可以明确知道该 fd 一定有数据，一进来就拷贝、不用阻塞。

    * 就绪的可能是多个 fd，所以要循环读完所有就绪的 fd，之后再回头调 `select` 监听下一批。

### 与阻塞 IO 的差别

* **差别所在**

    * 两种模型在阶段一等待 fd 就绪、阶段二数据拷贝时，用户进程都是阻塞的。

    * 阻塞 IO 调 `recvfrom` 只能监听某一个 fd，等到这个 fd 就绪才往下处理；当前 fd 没就绪不代表其他 fd 没就绪，此时其他 fd 已就绪也只能在队列里等着，这种等待是无效等待。

    * `select` 模式一次传多个 fd 进去，只要有任意一个就绪就立刻知道结果并去处理，不会因为一个顾客没想好而让所有人跟着等。

* **通知机制的代际差异**

    * > **结论**：`select` 和 `poll` 只会通知用户进程「有 fd 就绪」，但根本不确定是谁，所以用户进程只能逐个遍历 fd 来找；`epoll` 则会在通知的同时把已经就绪的 fd 写到用户空间，用户直接看到是哪几个就绪，直接处理即可。

    * 集体模式比喻：每张桌子上一个开关，连到服务员面前唯一的一个灯泡，任何人按下灯都亮，但服务员不知道是谁，只能挨个问。

    * 升级后的通知方案（epoll）：按钮直接连到服务员面前的计算机，按下就显示具体是几号桌。

## select

### 函数声明与五个参数

* **`int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds, struct timeval *timeout)`**

    * 一句话概括作用：监听多个 fd 组成的集合，下面传的参数全都跟这个 fd 集合有关。

* **`nfds`：遍历上限**

    * 值往往是要监听的 fd 集合中最大的那个 fd 再加一，告诉内核遍历到它就已经到上限，不用再往后遍历。

    * > **易错点**：`nfds` 是「最大 fd + 1」，不是「fd 的个数」。数量和编号是两回事，传错了内核会少扫或者白扫一段。

* **三个 `fd_set*`：按事件分类**

    * Linux 把一个 fd 上可能发生的事件分成三类：可读事件、可写事件、异常事件，对应读、写、异常三个 fd 集合。

    * 刚建立连接、正在发送请求的客户端 fd 要放进读事件的 `fd_set`；已经处理完请求、正等待响应的客户端 socket 对应的 fd 要放进写事件的 `fd_set`。

    * 调用时一定要把对应的 fd 放到对应的集合当中，把事件区分开。

* **`timeout`：三种取值**

    * 传 `NULL`：永不超时，等到某一个或多个 fd 就绪为止。

    * 传 `0`：不阻塞等待，不管调用那一刻有没有就绪都立即返回，返回就绪的 fd 数量，没有就返回零。

    * 传大于零的值：具体超时时间；超时仍无就绪也返回，返回值同样是零。

    * > **提示**：返回零有两种完全不同的含义，一种是你传了 0 主动轮询，一种是你等超时了但没人来。想知道是哪种，得自己看自己传的是什么。

### fd_set：用比特位省出来的集合

* **结构体定义**

```c
#define __FD_SETSIZE  1024
#define __NFDBITS    (8 * sizeof (long))      /* 32 */

typedef struct {
    unsigned long fd_mask[__FD_SETSIZE / __NFDBITS];   /* 1024 / 32 = 32 */
} fd_set;
```

    * `fd_mask` 的真实类型是 `long int`，在 C 语言里占四个字节，即 32 个比特位。

    * 32 位平台上 `$1024 \div 32 = 32$` 个元素，每个元素 32 个比特位，$32 \times 32 = 1024$ 个比特位。

    * > **提示**：64 位 Linux 上 `long` 是 8 字节，`__NFDBITS` 变成 64，`__FD_SETSIZE / __NFDBITS` 算出来是 16 个元素，16 × 64 依然是 1024 个比特位。结论不变：**`fd_set` 始终只能表示 1024 个 fd**。

* **按比特位保存 fd**

    * 初始化时每一个比特位都被置为零；**第几个比特位代表的 fd 就是几**，值为 1 表示监听、0 表示不监听。

```text
bit index :   0    1    2    3    4    5    6    7
fd number :  -    1    2    3    4    5    6    7
bit value :   0    1    0    0    1    0    0    0
```

    * 上例表示监听 fd = 1、2、5：分别把第 1、第 2、第 5 个比特位置成 1。

    * 用 bit 的 0 或 1 代替真正的 fd 值，可以大大节省内存空间。

### select 的执行流程

* **一次 select 走一遍**

```text
USER SPACE                            KERNEL SPACE
-----------                           ------------
build fd_set:
  bit1=1 (fd=1)
  bit2=1 (fd=2)
  bit5=1 (fd=5)
      |
      |  select(6, &rfds, 0, 0, 3s)
      |  ---- copy in : 1st copy -------
      +------------------------------->  scan fd 0..5
                                             |
                                    all blocked?
                                     /            \
                              yes /              \ no
                                 v                v
                            sleep & wait      return count
                            (woken up by fd=1)
                                 |
      <--------------------------+  rewrite bits:
      |  <---- copy back: 2nd ---+    ready fd  -> 1
      |                           |    others    -> 0
      |
 return value = 1  (ready count)
 scan fd_set again in USER space
      -> find fd=1 -> read(fd)
```

    * 内核从最低位开始遍历到 `nfds` 给定的上限为止，检查被标记的 fd 是否就绪。

    * 一个都没就绪就去休眠等待，等待期间后台一直在监听，任意一个 fd 可读就把它唤醒，然后**再遍历一遍**做「rewrite bits」：就绪的保留成 1、没就绪的改成 0。

    * 返回值告诉用户现在有几个就绪：一个就绪返回 1，五个就绪返回 5。

* > **易错点**：select 只是反馈了「有几个就绪了」，并没有把真正就绪的结果告诉用户，用户空间里根本不知道具体是谁就绪了。它在背后还有一个隐含操作：会把这个 fd 集合的结果**再拷贝回用户空间**，覆盖用户空间里那个 fd 集合。

* > **结论**：`fd_set` 这种设计虽然一定程度上节省了内存，但没办法直观地告诉用户进程**谁就绪了**——用户每次读数据前都得先遍历找到对应的 fd 才行。这也是 select 模式性能相对比较差的直接原因。

### select 留下的三个坑

* **坑一：每次调用两次内存拷贝**

    * 每执行一次 select，都要把 fd_set 从用户空间拷贝到内核空间，select 结束后还要再次拷贝回用户空间，即两次用户态内核态切换、两次内存拷贝。

    * select 不是只执行一次，处理完下一轮还要再执行，循环往复每一次都有这样的拷贝。

* **坑二：无法得知具体是哪个 fd 就绪**

    * 根源是 fd_set 的比特位结构：结果虽然传回来了，但不知道哪个就绪，不得不一个一个遍历。

* **坑三：能监听的 fd 数量只有 1024**

    * 被数组大小这个在源码里写死的常量限制，要改就得修改源码重新编译。

    * 随着互联网并发量暴增，1024 已完全不够用，实际能处理的客户端请求量比这个还要小。

## poll

### 函数声明与 pollfd 结构体

* **`int poll(struct pollfd *fds, nfds_t nfds, int timeout)`**

    * 第一个参数 `fds` 带星号，是一个数组，数组里装的是需要监听的文件描述符的集合，数组大小没有上限、没有固定，可以随便定义。

    * 第二个参数 `nfds` 代表数组中元素的个数，第三个 `timeout` 是超时时间。

    * 与 select 的差别：select 传三个集合（读、写、异常），poll 简化了参数，不划分事件集合，全部放在一个数组里。

* **`struct pollfd` 的三个属性**

```c
struct pollfd {
    int   fd;       /* the fd to watch            */
    short events;   /* the event(s) we care about  */
    short revents;  /* the event(s) actually seen */
};

enum poll_event {
    POLLIN,     /* data can be read        */
    POLLOUT,    /* data can be written     */
    POLLERR,    /* error condition         */
    POLLNVAL    /* fd not open             */
};
```

    * `fd`：要监听的 fd 的值；poll 吸取了教训，没有用二进制位表示 fd，而是直接保存 fd 的值。

    * `events`：要监听的事件类型，pollfd 里既含 fd 的值也含事件类型，各种事件类型的 fd 放在同一个数组里传过去；事件类型预定义好，相比 select 更丰富（`POLLIN` 可读、`POLLOUT` 可写、`POLLERR` 错误、`POLLNVAL` fd 未打开）。

    * `revents`：「real events」，代表真正发生的事件类型。

    * > **注意**：调用时创建多个 `struct pollfd` 形成数组传进去，但**只需要指定 `fd` 和 `events`**（我要做什么事情），不需要指定 `revents`；内核监听过程中发现事件就绪就把就绪的事件类型回填到 `revents`，若等到超时都没有任何事件发生则把它改成零，代表没发生任何事件，然后把整个数组返回。

### poll 的执行流程

* **一次 poll 走一遍**

```text
USER SPACE                          KERNEL SPACE
-----------                         ------------
pollfd[] = { {fd=3,ev=IN,rv=0},
             {fd=5,ev=OUT,rv=0} }
      |
      |  poll(fds, 2, timeout)
      |  ---- copy in --------------->  convert to linked list
      |                                   scan -> ready?
                                             |
                        +--------------------+--+
                        | no -> wait/timeout |  |
                        +--------------------+--+
      <-------------------------------------+  copy whole array back
      |                                        (ready AND not-ready)
pollfd[] -> scan it myself to find who is ready
```

    * 第一步创建 pollfd 数组，数组大小可自定义，理论上能监听的 fd 数量没有上限。

    * 调用时把 pollfd 数组拷贝到内核空间——同样有一次从用户空间到内核空间的拷贝；拷过去后内核把它转成链表存储，理论上可以无限存储。

    * 内核遍历这些 fd 判断是否就绪；有就绪就返回，没就绪同样要等待，等待仍没就绪则可能超时。

    * 最终一定返回结果：没有任何就绪返回零，有就绪返回具体的就绪数量。

    * poll 返回的也只是就绪的数量，并没有把具体谁就绪返回出来；背后同样把内核空间中处理好的 pollfd 数组拷贝回用户空间。

    * 用户进程还要判断结果是否大于零，大于零代表有就绪，必须遍历 pollfd 数组才能找到就绪的 fd。

### 换汤不换药

* **三大问题逐条对照**

    | select 的三大问题 | poll 解决了吗 |
    | :--- | :--- |
    | 每次调用都要把 fd 集合从用户空间拷到内核，处理完再拷回来 | 没解决，poll 同样是这么做的 |
    | 返回时只给就绪数量，还得遍历整个集合去找 | 没解决，poll 依然要遍历整个数组 |
    | fd 数量被 1024 卡死 | **解决了**，poll 用的是数组 + 链表，理论上没有上限 |

* **为什么没有巨大性能提升**

    * poll 唯一的改进就是增加了能够监听的 fd 的数量。

    * 每次调用都要遍历所有 fd 判断有没有就绪，给的 fd 值非常大时遍历消耗也越多，fd 非常多时反而性能下降。

    * 虽然 Linux 有这种模式，但基本上没有人去使用它。

## epoll

### epoll_create：内核里的 eventpoll

* **`int epoll_create(int size)`**

    * 执行时会在内核里创建一个叫 `eventpoll` 的结构体，创建完返回一个句柄 **epfd**。

    * epfd 可以看作 eventpoll 的唯一标识：每一个 epfd 指向一个唯一的 eventpoll；每调一次 `epoll_create` 就创建一个新的 eventpoll，这样的对象可以有很多个。

* **`struct eventpoll` 的两个关键属性**

```c
struct eventpoll {
    /* rbr stores the fds we are watching */
    struct rb_root   rbr;        /* red-black tree: ALL watched fds   */
    struct list_head rdllist;    /* ready list:    ONLY ready fds     */
    /* ... plus callback/wait-queue bookkeeping ... */
};
```

    * **rbr 是一棵红黑树**，里面每一个节点就是一个要监听的 fd；fd 是从零开始递增的有序整数，适合用红黑树来记。

    * **rdllist 是一个链表**，里面记录的是就绪的 fd。

    * 即：红黑树记录**所有**的 fd，链表记录**已就绪、有事件**的那部分 fd。

```text
USER SPACE                         KERNEL SPACE
-----------                        ------------
epoll_create()
     |  ---- returns epfd -------->  struct eventpoll
     |                               +-----------------------+
     |                               | rbr     : rb-tree    | <- all watched fds
     |                               | rdllist : ready list | <- ready fds only
     |                               +-----------------------+
     |                                     ^
     |  epoll_ctl(epfd, ADD, fd, ev) ------+  insert node + attach callback
     v
 epoll_wait(epfd, events[], max, timeout)
     |                                     ^
     |  events[] is EMPTY on entry ---------+  only READY fds copied back
     v
 events[] now holds exactly the ready fds
 -> no scan, no filtering needed
```

### epoll_ctl：往红黑树上挂回调

* **`int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event)`**

```c
#define EPOLL_CTL_ADD  1   /* insert fd into rb-tree   */
#define EPOLL_CTL_DEL  2   /* remove fd from rb-tree   */
#define EPOLL_CTL_MOD  3   /* change the event mask    */
```

    * 只具备 select 功能的一部分：select 的功能是「监听」+「等待就绪」，`epoll_ctl` 只做**添加 fd 去监听**，不会在那里等待就绪。

* **四个参数**

    * `epfd`：eventpoll 的句柄，据此知道要把当前 fd 添加到哪一个 eventpoll 上。

    * `op`：执行的操作，增（`EPOLL_CTL_ADD` 把 fd 添加到红黑树）、删（`EPOLL_CTL_DEL` 不再监听）、改（`EPOLL_CTL_MOD` 修改某个 fd 要监听的事件类型）；初始化时先做增。

    * `fd`：要监听的具体 fd 的值。

    * `event`：要监听的事件类型（读事件、写事件还是其他）。

* **回调函数 epoll_callback**

    * 添加 fd 的同时，会给每一个要监听的 fd 及其事件类型添加一个名为 `epoll_callback` 的 callback 函数。

    * 该回调在 fd 对应事件就绪时自动触发，业务逻辑极其简单：**一旦触发，就把对应的 fd 添加到 rdllist 就绪链表中**。

    * > **结论**：`epoll_ctl` 只负责添加 fd 进来，动作非常快、一瞬间就结束，它**不做任何等待**。

### epoll_wait：那个空数组

* **`int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout)`**

    * 它等于 select / poll 功能的另外一半：`epoll_ctl` 做前一半（添加 fd 去监听），`epoll_wait` 做后一半（等待 fd 就绪）。

* **四个参数**

    * `epfd`：要监听哪个 epoll 上的这些 fd。

    * `events`：一个**空数组**，这是与 select 的非常大的不同——要监听的 fd 已经在 `epoll_ctl` 里加过了，这里只需创建一片空的内存空间，传进去的仅仅是指向这片空间的指针，里边什么数据都没有。

    * `maxevents`：这个空数组所能允许的最大空间，内核将来要往里写数据，得告诉它别写超了。

    * `timeout`：超时时间，`-1` 永不超时，`0` 代表不等、没有就直接结束，也可以是大于零的具体时间。

* **检查的是就绪链表，不是红黑树**

    * 红黑树随着程序运行会越挂越多，遍历它性能可想而知，所以内核直接检查就绪列表。

    * 就绪列表中有元素就直接返回；没有就等 `timeout` 设定的时间，这段时间内有就绪也会被唤醒；这段时间结束仍无就绪，一样返回零。

    * 返回的是就绪元素的数量，例如两个 fd 就绪就返回二。

* > **易错点**：返回的只是数量，用户进程怎么知道谁就绪了？这时传进来的那个空数组就派上用场了——内核把就绪链表里的元素拷贝到用户空间的这个数组，用户进程就知道谁就绪了。

* **与 select / poll 的关键区分**

    * select / poll 拷回用户空间的是**所有的 fd**，不管就绪还是没就绪，用户进程不得不遍历、逐个判断。

    * epoll 拷贝过去的**仅仅是已经就绪的 fd**，用户进程**所见即所得**，不需要再自己筛选，遍历的只是就绪的 fd。

### 三大问题是怎么被解决的

* **问题一：拷贝**

    | select 做的两件事 | epoll 里的归属 | 调用频率 |
    | :--- | :--- | :--- |
    | 把 fd 拷进内核去监听 | `epoll_ctl` | 每个 fd 只需要一次 |
    | 等待这些 fd 就绪 | `epoll_wait` | 循环里每次都要调 |

    * 巧妙之处是把 select 函数的功能拆开了：监听一个新 fd 时执行一次 `epoll_ctl` 就够，以后循环处理事件时只循环执行 `epoll_wait`，不用再把 fd 拷进内核，减少了无数次 fd 数据的拷贝。

    * 回拷方向：select / poll 每次要把内核中所有的 fd 都拷回用户空间，epoll 只拷贝就绪的 fd，拷贝数量少很多。

    * 综合看是**大大减少了拷贝的次数**（每个 fd 只用拷一次），也**大大减少了拷贝的数量**（每次只拷就绪的，未就绪不用管）。

* **问题二：不知道谁就绪**

    * epoll 返回的同样是就绪 fd 的数量，但拷过去的仅仅是就绪的，拿到数组中的每一个 fd 都可以确保它一定就绪，不用再去遍历和判断。

* **问题三：fd 的数量**

    * select 因位图设计最多监听 1024 个 fd。

    * poll 虽然改成链表、允许监听的 fd 数量没有上限，但**这只是理论上没有上限**：所有要监听的 fd 串在一条链表上，数量极多时链表超级长，每遍历一次耗时非常久，实际受限于性能只能有限增加，是**伪无限**。

    * epoll 把每个 fd 放到红黑树上，红黑树理论上支持的数量是无限的；即便真要遍历，红黑树的增删改查性能不会随元素数量增加而有太大波动，性能基本稳定，不会因 fd 过多而影响性能，是**真无限**。

    * > **结论**：epoll 基于红黑树保存要监听的 fd，理论上没有上限且增删改查性能非常高，不会因为 fd 数量增加而产生显著下降；每个 fd 只需执行一次 `epoll_ctl` 就能上树，以后每次 `epoll_wait` 不用再传任何参数；内核只把就绪的 fd 拷贝到用户空间，用户立刻就知道谁就绪、谁没就绪。

### 三种实现摆在一起

| 维度 | select | poll | epoll |
| :--- | :--- | :--- | :--- |
| fd 集合的结构 | `fd_set` 位图，写死 1024 bit | `pollfd` 数组，内核转成链表 | 红黑树存全部 + 就绪链表 |
| 每次调用的拷贝 | 进一次、全部回一次 | 进一次、全部回一次 | 每个 fd 只进一次，只回就绪的 |
| 返回给用户的数组 | 全部 fd（就绪的置 1，未就绪置 0） | 全部 fd（含未发生的 `revents`） | **只有就绪的 fd** |
| 用户要不要自己遍历 | 要，且遍历全部 | 要，且遍历全部 | 不用遍历，按数组处理即可 |
| fd 数量 | 固定 1024 | 理论无限、实际受链表遍历限制（伪无限） | 真无限，且不影响性能 |
| 实践中是否用得多 | 少 | 基本没人用 | 高性能框架基本都用它 |

* **范围边界**

    * 这里讲的仅仅是 **Linux 平台**上的三种实现；Windows、macOS 对 IO 多路复用也有自己的实现。

    * epoll 模式完胜，现在一些高性能的网络框架基本都基于 epoll 模式实现。

## epoll 的事件通知机制

### LT 与 ET 的两种脾气

* **LT（level trigger，水平触发）**

    * > **定义**：数据可读时会**重复**得到多次通知，每一次调用 `epoll_wait` 都会告知这个 fd 就绪，直到把 fd 中所有数据都处理完为止。

    * 这是 epoll 中的**默认模式**。

* **ET（edge trigger，边沿触发）**

    * > **定义**：fd 就绪时第一次调用 `epoll_wait` 会通知，但重复调用就不再通知——只通知一次，不管 fd 中的数据是不是已经被处理掉。

* **2KB 数据的例子**

```text
kernel buffer :  [ 2 KB data ]

LT   epoll_wait -> NOTIFY -> read 1KB -> 1KB left
     epoll_wait -> NOTIFY -> read 1KB -> 0 left
     epoll_wait -> no data, no more NOTIFY

ET   epoll_wait -> NOTIFY -> read 1KB -> 1KB left
     epoll_wait -> already notified, SILENCE  (forever)
```

    * 客户端 socket 的 fd 注册到 epoll 实例后发来 2KB 数据，调 `epoll_wait` 得到通知；读数据不可能一次读完，先读 1KB 后再次调 `epoll_wait`，此时差异出现。

    * > **结论**：LT 循环往复直到把所有数据读完；ET 第一次通知完就再也没动静，剩下的 1KB 再也没有机会被处理。

### 就绪链表里发生了什么

* **拷贝前先断开**

    * `epoll_wait` 一方面返回有几个就绪，另一方面把就绪的 fd 拷贝到用户空间；但**在拷贝之前**，它会先把这些 fd 从就绪链表中断开（移除指针），因为它认为你要去处理了，然后再完成拷贝。

* **随后的模式检查**

```text
 fd ready
    |
    v
[ ready list ] <-----------------------------------------------+
    |                                                          |
    |  epoll_wait: copy events out to user space                |
    |  (before copying: unlink these fds from the ready list)   |
    v                                                          |
 check the trigger mode                                         |
    |                                                          |
 +--+------------+                                            |
 |  LT           |  ET                                        |
 |  still has    |  done. they are gone,                     |
 |  data ?       |  never notified again                      |
 +--+------------+                                            |
    |                                                          |
    +-- YES: link them back into the ready list ---------------+
```

    * **ET 模式**：移除后就结束了，就绪队列里再也没有它们，下一次调 `epoll_wait` 时就绪列表是空的，得不到通知。

    * **LT 模式**：内核发现用的是 LT 且这俩 fd 还有数据，就**再次把它们添加回就绪链表**，下一次调 `epoll_wait` 还会再拷贝给你，从而实现重复读取。

### 用 ET 就得自己把数据读干净

* **方案一：手动把 fd 加回就绪列表**

```text
Route 1: link the fds back by hand

  epoll_wait -> NOTIFY -> read 1KB -> still 1KB ?
                                        |
                               epoll_ctl(MOD) on those fds
                               (kernel checks: really ready?)
                                        |
                          linked back into the ready list
                                        |
  epoll_wait -> NOTIFY -> read the rest -> done
```

    * 调用 `epoll_ctl` 做「修改」动作，修改 fd 上的一个状态；`epoll_ctl` 会检查该 fd 是不是真有就绪的事件、有没有对应的数据，有就再次把它添加回就绪队列。

    * LT 是内核自动帮你重新添加回去，ET 需要手动添加。

    * > **注意**：每次手动加回后再循环调 `epoll_wait`，就要重复地通知、再一次做内存拷贝，**等同于返回成 LT 模式**，这种重复通知对性能影响很大。

* **方案二：一次通知里循环读到空**

```text
Route 2: drain it in one single notification

  epoll_wait -> NOTIFY -> enter the loop
                                       |
           +------------------------ read(fd, .., NONBLOCK)
           |                            |
           |             +--------------+--------------+
           |             |                             |
       got data                     EAGAIN : nothing left
           |                             |
     keep reading                    break the loop
           |                             |
           +-------> back to the top      done
```

    * 既然每个 fd 就绪时只通知一次，就在这一次通知中用 `while` 循环反复读，直到把 fd 数据读完。

    * > **易错点**：循环里**千万不能用阻塞 IO 的模式来读**。阻塞 IO 读到 fd 里已经没有数据时不会返回错误，而是一直卡在那里等到下一次再来数据，整个循环出不来、整个进程被阻塞。

    * 必须采用非阻塞 IO：有数据就返回，没数据也返回，只是返回一个标识（`EAGAIN`）告诉你没有了，据此跳出循环，避免循环读取导致的阻塞。

    * > **提示**：这两种方案本质上都是在补 ET 故意留下的窟窿——ET 只保证「状态发生变化时通知你一次」，至于你有没有把数据处理干净，它从此再也不管。

### LT 的两个包袱

* **重复通知的开销**

    * LT 是重复通知，每次调 `epoll_wait` 只要 fd 还有数据就一直通知，看起来能确保数据彻底读完，但这种重复通知（以及随之的重复拷贝）对效率和性能都有影响。

* **惊群现象**

    * > **定义**：N 个不同的进程都监听了当前 epoll 实例中的某一个 fd 并都在调用 `epoll_wait`，该 fd 就绪后把**所有**监听它的进程都唤醒，即一个 fd 就绪、所有进程都被唤醒。

    * 成因：LT 模式下任何一个进程通知完成后，这个 fd **还会存在在列表当中**，于是所有监听它的进程最终都会被通知到。

    * 真正处理时可能前一两个进程就已把 fd 的数据处理完，后续被唤醒的进程没有必要被唤醒。

    * ET 模式不会出现这个问题：第一次通知完直接移除，后续进程不会得到通知。

* **LT 与 ET 对照**

    | 对比维度 | LT（水平触发，默认模式） | ET（边沿触发） |
    | :--- | :--- | :--- |
    | 通知次数 | 只要 fd 还有数据，就反复通知 | 只在就绪状态变化时通知一次 |
    | 惊群 | 可能出现惊群现象 | 不会 |
    | 把数据读干净 | 内核自动放回就绪链表，天然支持分批读 | 手动 `epoll_ctl` 加回，或非阻塞循环读到空 |
    | 实现复杂度 | 简单 | 相对复杂 |
    | 性能 | 有重复通知与重复拷贝的开销 | 更好 |

* **选型**

    * LT 实现简单，但可能有性能问题和惊群问题；ET 实现相对复杂，但没有这些问题、性能更好。

    * 对这点性能不太在意就用默认的 LT 模式，否则建议使用 ET。

    * > **结论**：ET 避免了 LT 可能出现的惊群现象，且可以结合非阻塞 IO 去读数据，虽然实现比 LT 复杂一点，但性能上会更好。

## 基于 epoll 的 Web 服务流程

### 内核空间那一半

* **epoll 实例的内部构成**

    * 红黑树：每一个通过 `epoll_ctl` 注册的 fd。

    * 就绪链表：当前已就绪的 fd。

    * `epoll_callback`：注册时绑定，fd 一就绪就立即触发，把该 fd 放进就绪链表。

    * `epoll_wait`：扫描就绪链表，把事件拷贝出来。

### 用户空间那一半

* **完整流程**

```text
=========================== KERNEL SPACE ==========================
  red-black tree : every fd registered through epoll_ctl
  ready list     : fds that are currently ready

  epoll_callback : bound at registration time; fired as soon as
                   its fd becomes ready, which puts the fd into
                   the ready list

  epoll_wait     : scan the ready list, copy the events out
=================================================================

----------------------------- USER SPACE -------------------------
  1. epoll_create()              -> get the instance above
  2. init the server socket      -> ssfd (server socket fd)
  3. epoll_ctl(ADD, ssfd, EPOLLIN, epoll_callback)
        |
        v
  4. epoll_wait()
        |
        +--> returns 0   : nothing is ready, loop back to 4
        |
        +--> returns n>0 : go on, dispatch every ready event
                              |
                              +-- EPOLLIN  and  data.fd == ssfd ?
                              |     YES -> accept() -> client fd
                              |            epoll_ctl(ADD, cfd, ..)
                              |            loop back to 4
                              |
                              +-- EPOLLIN  on a normal client fd ?
                              |     YES -> read the request
                              |            run the business
                              |            write the response
                              |            loop back to 4
                              |
                              +-- error / other events ?
                                    YES -> write an error response
                                           loop back to 4
==================================================================
```

    * 第一步 `epoll_create()` 创建 epoll 实例，本质是在内核里准备红黑树（记录要监听的 fd）和链表（记录就绪的 fd）。

    * 第二步初始化 server socket：Web 服务基于 TCP 协议，服务端就是一个 server socket，它在 Linux 内部同样被看成文件，因此有自己的 fd，称为 **ssfd**。

    * 第三步用 `epoll_ctl`（`EPOLL_CTL_ADD`）把 ssfd 添加到红黑树，同时给它绑定回调函数 `epoll_callback`。

    * 第四步 `epoll_wait()`：检查就绪列表有没有元素，有就直接返回；没有就等待指定的时间，期间有 fd 就绪会被唤醒并返回；始终没有就绪则返回 0。

* **返回值必须为 0 判断**

    * 执行完 `epoll_wait` 必须判断当前有没有就绪（返回值是否为 0）；没有就绪就二话不说重新执行 `epoll_wait`，循环不停地执行直到就绪。

* **事件分派的三条分支**

    * server socket 只有一种情况会就绪：**有客户端在向它申请连接**，此时它上面产生的是读事件。

    * 判断事件类型为 `EPOLLIN` 后再判断是谁可读：是 ssfd 可读，证明真的有客户端要连接，调用 `accept` 接收客户端 socket，得到客户端 fd，再通过 `epoll_ctl` 把它注册到红黑树并绑定回调，继续 wait。

    * 不是 ssfd 而是普通客户端 socket 可读，代表有请求参数来了：读取请求参数、处理业务、把响应结果写到客户端 socket。

    * 执行过程中出错时可能不是读事件而是异常事件，此时也要给客户端写响应，写的就是异常信息。

* **整体抽象与注意点**

    * 整体就是「接收事件 → 把事件派发给不同的业务去处理 → 处理事件」：事件无非是客户端连接事件、客户端数据可读、异常三种。

    * > **注意**：流程图上半部分执行的所有业务都属于内核空间，下半部分是在用户空间执行的。

    * Redis 底层就是基于这种 epoll 模型，Redis 本身也是一个 TCP 服务端，与这里的流程基本差不多。

## 同步与异步的判定

### 判定标准

* **看的是第二阶段**

    * > **定义**：在 IO 操作里判断同步还是异步，标准是**数据从内核空间到用户空间的拷贝过程**，也就是第二阶段到底是阻塞还是非阻塞。

    * 阶段一是等待数据就绪，阶段二是从内核空间拷贝到用户空间。

* **五种模型两阶段对照**

    | IO 模型 | 一阶段：等待数据就绪 | 二阶段：从内核拷贝到用户空间 |
    | :--- | :--- | :--- |
    | 阻塞 IO | 阻塞，一直阻塞直到完成为止 | 阻塞 |
    | 非阻塞 IO | 非阻塞（不停地轮询，其实是在做无用功） | 阻塞 |
    | IO 多路复用 | 阻塞（等待 fd 就绪） | 阻塞（真正去读数据） |
    | 信号驱动 IO | 非阻塞（靠信号通知） | 阻塞（数据拷贝依然要等） |
    | 异步 IO | 非阻塞 | 非阻塞 |

* > **结论**：只有异步 IO 的二阶段是非阻塞的，所以只有它才能称之为异步 IO。

* > **易错点**：在 IO 当中，同步、异步并不是跟阻塞、非阻塞有强关系。阻塞 IO 和非阻塞 IO 本质都属于同步 IO，千万不要把同步异步跟阻塞非阻塞混为一谈。

* **使用现状**

    * 目前使用相对较多的是 IO 多路复用，少数情况下也会用到异步 IO。

## Redis 的线程模型

### Redis 是单线程还是多线程

* **先反问，再作答**

    * > **定义**：标准答法是先反问对方——讨论的是 Redis 的**核心业务处理部分**（命令处理部分），还是**整个 Redis**。

    * 讨论核心业务处理部分（命令处理部分）：**单线程**。

    * 讨论整个 Redis：**多线程**。

* **多线程是怎么进来的**

    * Redis 4.0 就已经引入多线程，主要用于处理耗时较长的任务，特别是后台进程：直接删除 big key 可能导致主线程阻塞、耗时很久，因此采用异步删除——先标记成删除，后台用一个线程慢慢删，`UNLINK` 命令就是如此。

    * 4.0 时除了命令处理，整个网络模型也都是单线程；因为底层采用 IO 多路复用机制，性能非常好，即便单机模式也能做到每秒数万的并发。

    * 服务器可以做到 16 核、32 核甚至 64 核，单线程无法充分利用高性能硬件；搭建集群会引发其他问题，不是最佳方案。

    * Redis 6.0 在**核心网络模型**中引入多线程，对原来的 IO 多路复用整体机制做了些小改变，提高了对整个 CPU 的利用率；但核心部分即命令处理依然是单线程。

    * > **提示**：把每个层次讲清楚——哪里是单线程、哪里是多线程，比直接甩一个答案要严谨得多。

### 为什么坚持使用单线程

* **原因一：Redis 的瓶颈不在执行速度**

    * 抛开持久化不谈，Redis 是**纯内存的操作**，执行速度非常快，延迟可以做到微秒级别。

    * 它的瓶颈从来不是执行速度，而是**网络的延时**；因此开启更多线程并不会带来非常大的性能提升。

    * 「Redis 为什么运行得那么快」的最重要原因就是纯内存操作，IO 多路复用之类只是细微的提升。

* **原因二：多线程带来上下文切换与内存代价**

    * 引入多线程反而会导致过多的上下文切换（在单核情况下尤其明显）：CPU 需要在多个线程之间切换，线程越多切换频率越高。

    * 线程也会带来额外的内存消耗，有可能反而导致性能下降。

    * 即便 6.0 引入了多线程，线程数也往往跟 CPU 的核数相对应，最多也就是核数的 1~2 倍，以尽量减少上下文切换。

* **原因三：线程安全与改造代价**

    * 单线程时所有命令依次执行，一直是线程安全的，加减之类的操作不用考虑风险。

    * 一旦基于多线程做命令操作，就不得不考虑线程安全、做并发控制，整个代码复杂度非常高，性能也会大打折扣，还会与老的 Redis 版本产生兼容性问题。

* > **结论**：即便已经在网络处理这一块加了一些线程，命令处理部分依然是单线程的。
