# 分布式锁：原理、实现陷阱与 Redisson

## 分布式锁的定义与基本特性

* **分布式锁（Distributed Lock）**

    * > **定义**：满足「多进程可见」与「互斥」两个条件的锁。

    * 多进程可见是首要条件：所有 JVM 进程都必须看得见同一个锁监视器。

    * 互斥是难点：不管谁来访问，只能有一个人拿到，其他人都得失败。

    * 起因：`synchronized` 依赖 JVM 内部的锁监视器，只能保证单个 JVM 内部多线程之间的互斥；有几个 JVM 就有几个锁监视器，各锁各的，互不相识。

    * 集群下的表现：两个进程同时进来，两把锁各放行一个线程，互斥根本没发生，一人一单被穿。

    * 解决方向：放弃 JVM 内部的锁监视器，让多个 JVM 都去盯着同一个外部监视器。

### 五个基本特性

* **多进程可见**

    * 判定方式：只要位于 JVM 外部、所有 JVM 进程都能看得见即成立。

    * 边界：Redis、MySQL 都能满足，这条基本不用操心。

* **互斥**

    * 规则：无论谁来访问，只能有一个线程拿到锁，其余一律失败。

* **高可用**

    * 规则：大多数情况下获取锁的动作都应该成功；获取锁经常出问题会拖累业务，得不偿失。

* **高并发 / 高性能**

    * 机理：加锁使线程串行执行、性能本就下降，若获取锁这个动作本身还很慢就是雪上加霜，因此获取锁必须高性能。

* **安全性**

    * 边界：要能扛住异常——拿到锁还没释放时服务宕机，锁必须还有出路，不能产生死锁。

### 功能性特征

* **可选特征**

    * 可不可重入、获取锁是阻塞还是非阻塞、是公平锁还是非公平锁等，可满足也可不满足。

    * 核心对比维度只有四个：怎么实现互斥、互斥逻辑有什么差异、怎么保证高可用和高性能、安全性如何。

## 三种实现方案的差异

### 基于 MySQL

* **互斥来源**

    * 白拿数据库的事务机制：执行写操作时数据库自动分配互斥锁，事务之间自然互斥，只有一个能执行。

    * 流程：业务执行前先向 MySQL 申请锁 → 执行业务 → 提交事务即释放锁；业务抛异常则事务自动回滚，锁随之释放。

* **可用性**

    * 取决于 MySQL 本身，支持主从模式，可用性不错。

* **性能**

    * 完全受限于 MySQL 性能，与 Redis 相比有差距，比较一般。

* **安全性**

    * 好：系统崩溃、连接断开后锁自动释放，数据也回滚，无需额外考虑。

### 基于 Redis

* **互斥来源**

    * `SETNX` 天然互斥：只有 key 不存在时才能 set 成功，已存在则失败；无数线程对同一个 key 执行 `SETNX`，只能有一个成功。

    * 释放锁：把 key 删掉，其他人就能获取。

* **可用性**

    * 不止支持主从，还支持集群模式，可靠有保障。

* **性能**

    * 远好于 MySQL，非常好。

* **安全性**

    * 最弱：`SETNX` 写入的 key 不会自己消失，服务宕机后没有人执行删除，锁永远得不到释放，产生类似死锁的效果。

    * 兜底办法：利用 Redis 的 key 过期机制，在 `SETNX` 的同时加上过期时间。

    * 遗留问题：过期时间太长，无效等待时间多；太短，业务没执行完锁就释放。

### 基于 ZooKeeper

* **互斥来源**

    * 利用数据节点机制：节点具备唯一性和有序性，还可创建临时节点。

    * 有序性做法：多个线程都去创建节点，节点 ID 单调递增，约定 ID 最小者获取锁成功；最小者只有一个，互斥成立。

    * 唯一性做法：大家都去创建同名节点，也只有一个人能创建成功；一般还是用有序性。

    * 释放锁：删掉自己的节点，另一个人自然变成最小者并拿到锁。

* **可用性**

    * 天生支持集群，可用性很好。

* **性能**

    * 相对较差：ZooKeeper 集群强调强一致性，主从数据同步要消耗时间。

* **安全性**

    * 很好：创建的往往是临时节点，服务宕机、连接断开后节点自动删除，锁随之释放。

### 四个维度对比

| 方案 | 互斥原理 | 可用性 | 性能 | 安全性 |
| :--- | :--- | :--- | :--- | :--- |
| MySQL | 借助事务机制，写操作时数据库自动加互斥锁；提交事务即释放，异常自动回滚 | 依赖 MySQL 本身，支持主从，可用性不错 | 受限于 MySQL 性能，比 Redis 有差距，比较一般 | 好：系统崩溃、连接断开后锁自动释放，数据回滚 |
| Redis | `SETNX` 只有 key 不存在时才设置成功，天然互斥；删 key 释放 | 不止主从，还支持集群模式，可靠有保障 | 远好于 MySQL，非常好 | 最弱：`SETNX` 写入的 key 不会自己消失，只能靠 key 过期机制兜底 |
| ZooKeeper | 借助数据节点机制，节点唯一、有序、可临时创建；约定序号最小者持锁 | 天生支持集群，可用性很好 | 强一致性导致主从同步耗时间，相对比 Redis 差 | 很好：临时节点在连接断开后自动删除 |

* **选型结论**

    * 安全性角度：ZooKeeper 与 MySQL 原理基本类似，都比 Redis 强，Redis 只能靠超时机制兜底。

    * 可用性与性能角度：Redis 非常好。

    * 因此本教程选择基于 Redis 实现分布式锁。

## Redis 分布式锁的最小闭环

### 获取与释放

* **基本命令**

    * 获取锁：`SETNX lock 线程标识`，返回 1 成功；再有人执行同样的 `SETNX` 返回 0，互斥生效。

    * 释放锁：`DEL lock`；删掉之后 `SETNX` 又能成功。

* **理想与现实的差距**

    * 理想情况：`SETNX` 成功 → 执行业务 → `DEL` 释放。

    * 风险：拿到锁后服务宕机、来不及执行 `DEL`，释放动作永远得不到执行，锁永远存在，业务陷入死锁。

### 超时释放

* **机制**

    * 用 `EXPIRE` 给锁添加超时时间，到期自动删除，服务宕机也能释放锁。

    * > **注意**：时间不能设置太短，万一业务还没执行完就释放也会出问题；一般稍微长一点，比如十秒钟，比实际业务执行时间长一点。

    * > **易错点** ⚠️：`SETNX` 与 `EXPIRE` 是两步，若在两者之间宕机，锁依然无法释放；必须保证「获取锁」与「添加过期时间」要么都成功、要么都失败。

### SET NX EX 的原子性

* **一条命令搞定**

    * `SET` 支持 `EX`（秒）、`PX`（毫秒）指定过期时间，再跟上 `NX`（与 `SETNX` 效果相同，数据不存在才能 set）。

    * 最终写法：`SET lock 线程标识 NX EX 10`，重复的 set 无效果，过期后再 set 又能成功。

    * 结论：把 `NX` 与过期时间合并进一条 `SET`，两步变一步，成为原子操作。

### 非阻塞式获取

* **机制**

    * 只执行一次，成功返回 `true`、失败返回 `false`，不再尝试、不阻塞等待。

* **选它的原因**

    * 阻塞式对 CPU 有一定浪费。

    * 阻塞式实现起来相对麻烦。

* **完整流程**

    * 尝试获取锁执行 `SET key value NX EX <时间>`，返回值只有 `OK` 与 `nil` 两种。

    * `nil` 代表失败（之前已有人执行过），`OK` 代表成功，可执行业务逻辑。

    * 业务执行完执行 `DEL` 释放锁。

    * 因为有 `EX`，获取锁成功后若服务宕机，锁会自动释放，避免死锁。

## 第一版实现

### 锁接口与类骨架

* **接口定义**

    * 标准锁接口 `ILock` 只有两个方法：`tryLock(String name, Long timeoutSec)` 与 `unlock(String name)`。

    * 之所以叫「尝试」获取锁：非阻塞模式只试一次，成功返回 `true`、失败返回 `false`，不重试也不阻塞等待。

    * `timeoutSec` 就是 `SET ... EX` 里的那个 `EX` 时间。

* **类的构成**

    * 成员：`StringRedisTemplate`，获取锁与释放锁都要用它执行 Redis 命令，通过构造函数注入。

    * 常量：`KEY_PREFIX` 值为 `lock:`，给锁加统一前缀。

    * > **注意**：锁的名称不能写死。写死意味着任何业务都用同一把锁，正确做法是让锁名与业务有关，由使用者传入。

### tryLock

* **四要素**

    * NX 的由来：必须调用 `setIfAbsent`，`absent` 即缺席，只有不存在时才执行，等价于 `NX`。

    * EX 的由来：`setIfAbsent` 的重载方法传时间参数，单位写 `TimeUnit.SECONDS` 即为秒。

    * key 的构成：`KEY_PREFIX` 拼接业务名称。

    * value 的构成：线程标识，用 `Thread.currentThread().getId()` 取线程 id，一个 JVM 内部线程 id 一般不重复。

* **返回值处理**

    * `SET NX EX` 的返回值是 `OK` / `nil`，Spring 封装后已直接返回布尔值。

    * > **易错点** ⚠️：返回类型是基本类型而值是包装类，直接返回会发生自动拆箱，值为 `null` 时空指针。应写成 `Boolean.TRUE.equals(success)`，用常量调用 `equals`，`true`/`false`/`null` 分别得到 `true`/`false`/`false`。

### unlock

* **第一版写法**

    * 直接 `stringRedisTemplate.delete(key)`，key 为前缀加锁名，然后返回 `true`。

    * > **提示**：这一版是「上来就删」，不管锁在不在、是不是自己的；存进去的线程标识在这一版还没被用上。

### 接入下单业务

* **锁的范围**

    * 只写业务名（如 `order`）意味着凡是来下单的业务都会被锁住；实际要锁定的是用户，应拼接用户 id，写成 `order:` + 用户 id。

    * 好处：锁定范围是用户 id，冲突范围较小，并发效率过得去。

* **调用骨架**

    * 创建锁对象 `new SimpleRedisLock(stringRedisTemplate)`，锁名与业务相关。

    * `Boolean isLock = lock.tryLock(lockName, 1200L)`，做反向判断 `if (!isLock)` 直接返回失败，避免嵌套。

    * 失败处理：直接返回「一个人只允许下一单」，不重试——并发重复的抢购请求本就是非法请求。

    * 业务逻辑必须包在 try-catch-finally 中，释放锁放进 `finally`，异常与否都要释放。

* **超时时间的取值**

    * 与业务耗时有关：下单业务耗时约 500ms 时可设 5 秒；为便于打断点调试可给较长的值。

* **实测结果**

    * 两个进程访问同一台 Redis、锁名相同，只有一个拿到锁（`isLock` 分别得到 `true` 与 `false`），另一个被拒绝。

    * Redis 里只记录了一个线程标识，同一用户争抢时只能有一个线程持锁。

## 误删锁问题

### 成因

* **时间线上的两个要害**

    * 业务阻塞过久，超过了 `EX` 设定的超时时间，锁被提前自动释放，别人趁虚而入拿到锁。

    * 原持有线程醒来后不辨身份直接 `DEL`，删掉的是别人的锁。

    * 后果：新持锁者毫不知情仍在跑业务，第三个线程也能获取成功，两个线程同时执行，线程安全问题再次出现。

    * > **结论**：最根本的原因是释放锁时把别人的锁给删了；解决办法是在释放锁时判断锁的标识是否一致。

### 线程标识的设计

* **为什么不能只用线程 id**

    * 线程 id 是 JVM 内部递增的数字，多个 JVM 各自维护一套从 1 开始递增的数字，集群下两个 JVM 之间 ID 冲突概率相当高。

    * > **易错点** ⚠️：线程 ID 只在单个 JVM 内唯一，跨 JVM 会重复；集群部署下拿它当锁的所有者标识，等于没加锁。

* **正确构成**

    * UUID 区分不同的服务（不同的 JVM），线程 ID 区分不同的线程，两者拼接。

    * 效果：不同线程的标识一定不一样，相同线程的标识一定一样。

    * 写法：`ID_PREFIX = IdUtil.fastUUID().toString(true) + ":"`，Hutool 的 `fastUUID()` 传 `true` 去掉 UUID 默认带的横线，末尾拼冒号隔开线程 ID。

### 释放前的比对

* **判定方式**

      1. 用**同一个 key** 取出锁里的标识（`opsForValue().get()`）。

      2. 与自己的 `ID_PREFIX + 线程id` 比较；一致才删除，不一致什么都不做。

    * > **结论**：改进点只有一个——释放锁之前先判断再释放；不一致代表锁早就不是自己的，不用管。

* **实测表现**

    * 模拟锁超时过期后，另一个实例拿到锁，锁里的标识换人；前者走到释放时两个标识肉眼可见对不上，不删，锁安然无恙。

    * 后者业务跑完再释放，两个标识完全一致，锁被真正删除。

## 判断与删除之间的缝隙

### GC 阻塞造成的误删

* **缝隙在哪**

    * 判断锁标识与释放锁是两个动作，两者之间仍可能阻塞。

    * 阻塞来源不是业务，而是 JVM 的垃圾回收：GC 会阻塞所有代码。

    * 后果链：判断通过 → Full GC 阻塞 → 锁超时被 Redis 自动删除 → 别人拿到锁 → GC 结束 → 直接 `DEL`，删掉别人的锁 → 第三个线程趁虚而入。

    * 关键：判断已经执行过了，线程认为锁还是自己的，不会再判断一次，直接执行释放。

    * > **易错点** ⚠️：加了标识判断 ≠ 安全。只要判断和删除之间存在时间缝隙，缝隙里锁就可能易主。

### 原子性要求

* **规则**

    * 判断锁标识的动作与释放锁的动作必须成为原子性操作，一起执行，中间不能出现间隔。

## 用 Lua 脚本保证原子性

### 为什么不选 Redis 事务

* **Redis 事务的性质**

    * Redis 确实有事务，但与 MySQL 事务差别很大：能保证原子性，却给不出完整的一致性保证。

    * 更关键的是，事务内的多个操作是**批处理**、最终一次性执行，执行查询时拿不到中间结果，无法做到「先查询、再判断、再释放」。

| 方案 | 能否把「判断 + 释放」合成一个动作 | 结论 |
| :--- | :--- | :--- |
| Redis 事务（MULTI/EXEC） | 不能。事务内命令是批处理、最终一次性执行，查询时拿不到中间结果 | 排除 |
| 事务 + WATCH 乐观锁 | 理论上可行，靠版本号校验「期间无人修改」 | 复杂，不推荐 |
| Lua 脚本 | 能。脚本执行期间不会被插入其他命令 | 采用 |

* **Lua 脚本的作用**

    * 在一个脚本中编写多条 Redis 命令，Redis 一次性执行，确保这些命令的原子性，执行过程中不会有其他命令插进来。

### Lua 语法要点

* **语言特点**

    * 弱类型，变量用 `local` 声明，不需要声明 `int` 之类，与 JS 很像。

    * 函数声明 `function 函数名(参数列表)`，没有大括号，用 `end` 代表结束。

    * 流程控制 `if ... then ... end`，同样没有大括号。

    * > **提示**：`if` 成立与不成立各自都需要一个 `end` 收尾，写的时候最容易少写一个。

    * 注释用 `--`。

    * 数组角标**从 1 开始**，取第一个元素写 `KEYS[1]`。

### redis.call

* **调用方式**

    * Redis 提供内置函数 `redis.call`，可理解为「对象.函数」，括号里传命令的每一个单词。

    * 规则：Redis 命令用空格隔开，脚本里把每个单词作为字符串参数、用逗号隔开——一个空格对应一个参数。

```lua
redis.call('set', 'name', 'Jack')
local name = redis.call('get', 'name')
```

    * 多条命令依次书写即可，返回值可用 `local` 变量接收，最终用 `return` 返回。

### eval 与参数

* **命令格式**

    * `eval <script> <numkeys> <key...> <arg...>`，脚本本质是一个字符串，用双引号引起来，里面的字符串参数用单引号避免冲突。

    * `numkeys` 是 key 类型参数的个数：指定 1 表示后面紧跟着的那一个是 key 类型参数，再往后的都是其他参数。

    * 无参脚本写 `eval "return redis.call('set','name','杰克')" 0`，最后的 0 就是参数数量。

* **为什么要分两类参数**

    * Redis 是 key-value 结构，命令一般都要指定 key，而且像 `MSET` 这类命令可以有多个 key，所以必须显式指定 key 的个数才能区分。

* **KEYS 与 ARGV**

    * key 类型参数放进 `KEYS` 数组，其他参数放进 `ARGV` 数组，脚本里按下标取用。

    * 动态脚本写法：`return redis.call('set', KEYS[1], ARGV[1])`，后面跟 `1` 表示 key 类型参数只有一个。

    * > **提示**：脚本可理解成一个函数，全部写死则拓展性差；允许传参后，同一份脚本可以给不同的 key 赋不同的值。

### 释放锁脚本

* **编写顺序**

    * > **提示**：先不要考虑 `KEYS`、`ARGV`，先把脚本的整体流程写出来，最后再把该动态的地方替换成参数。

    * 流程：取锁中的线程标识 → 与当前线程标识比较 → 一致则 `del` 并 `return` 结果，不一致则 `return 0`。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

    * 参数含义：`KEYS[1]` 是锁的 key（如 `lock:order:5`），`ARGV[1]` 是线程标识。

    * 返回值：`del` 成功返回 1 代表释放成功，0 代表失败。

### 用 Java 执行脚本

* **提前加载脚本**

    * 不建议在代码里把脚本写死（`new DefaultRedisScript(脚本字符串, Long.class)` 属于硬编码），应放到类路径下的脚本文件，用 `ClassPathResource` 指定。

    * 用 `static final` 常量加静态代码块初始化：类一加载脚本就初始化完成，不用每次释放锁都读文件产生 IO。

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;

static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```

* **execute 与 eval 的对应**

    * 第一个参数 `script` 对应 `eval` 的 `script`。

    * 第二个参数 `List<String> keys` 对应 `key...`，key 可以有多个所以用集合；`numkeys` 不需要传，keys 集合的元素个数就是 key 数量。

    * 第三个参数 `Object... args` 对应 `arg...`，是可变参数。

```java
stringRedisTemplate.execute(
        UNLOCK_SCRIPT,
        Collections.singletonList(LOCK_KEY),
        ID_PREFIX + Thread.currentThread().getId()
);
```

    * 单元素集合可用 `Collections.singletonList` 生成。

    * 返回值不用关心：释放成功就成功；没成功说明锁已被别人删掉或已超时释放，无所谓。

    * > **结论**：释放锁从两行代码变成一行，更重要的是这一行调的是 Lua 脚本，判断与删除在脚本中执行，满足原子性。

## 完整的自定义方案

### 获取锁

* `SET NX EX`：`NX` 实现互斥，确保只有一个线程能拿到锁；`EX` 是兜底方案，防止服务宕机导致锁无法释放。

### 释放锁

* 先判断线程标识是不是自己，一致才释放，不一致不删，防止误删。

* 采用 Lua 脚本确保原子性，避免多线程下因阻塞导致的误删。

### 这把锁具备的性质

* **互斥性**：只有拿到锁的那个线程能进临界区，多线程下可见性也满足。

* **安全性**：有超时释放，可以避免死锁。

* **原子性**：Lua 脚本保证判断和删除是一个动作，避免误删。

* **高可用与高并发**：可以满足；Redis 可以做集群（主从或其他集群模式），不会因宕机导致锁失效。

## 自定义锁的四个短板

### 不可重入

* **可重入锁（Reentrant Lock）**

    * > **定义**：同一个线程可以多次获取同一把锁。

    * 死锁场景：方法 A 获取锁后调用方法 B，B 又要获取同一把锁；`NX` 保证一把锁只能有一个持有者，B 获取失败并等待释放，而锁要等 A 结束才释放、A 又在等 B 返回，于是自己把自己锁死。

### 不可重试（不可阻塞）

* 现有实现是非阻塞式：尝试获取失败立即返回 `false`，没有重试机制。

* 期望：锁被别人占有时等一等再试，成功后仍可执行业务；一旦失败就立即失败、撒手不管，在很多场景下不可接受。

### 超时释放

* Lua 脚本解决的是「超时之后误删了别人的锁」，管不了「超时本身」带来的业务风险。

* 时间太短：业务还没执行完锁就释放，业务执行过程中其他人也可能进来。

* 时间太长：出现故障后很长一段时间大家都在等锁自动释放，锁的阻塞周期过长。

* > **易错点**：误删问题和超时问题是两码事。

### 主从一致性

* **主从模式**

    * 读写分离：一个主节点多个从节点，写操作访问主节点，读操作访问从节点；主节点把数据同步给所有从节点。

    * 主节点宕机后可从从节点中选出一个作为新主，可用性更强。

* **失效链**

    * 线程在主节点 `set` 写入锁标识 → 同步延迟，写操作还没到从节点 → 主节点突然宕机 → 从节点中选出新主 → 新主身上没有这个锁标识 → 其他线程趁虚而入也拿到锁 → 多个线程同时认为自己持锁。

* **概率**

    * 出现概率比较低，主从同步延时往往极低，可在毫秒级别甚至更低。

### 这四个问题的性质

* 要么发生概率极低，要么视业务而定（有的业务需要，有的不需要），都是**功能上的拓展点**，不是必须实现。

* 不实现也能用：大多数场景不需要重入与重试；用单节点就不存在主从一致性问题。

* 但要实现起来很繁琐，因此不推荐亲自实现，应使用成熟框架。

## Redisson

### 定位

* **Redisson**

    * 官方概念：在 Redis 基础上实现的 Java 驻内存数据网格（in-Memory Data Grid）。

    * 通俗理解：在 Redis 基础上实现的**分布式工具集合**，分布式系统下要用到的各种工具它都有，分布式锁只是其中一个子集。

* **分布式锁家族**

    * 包含可重入锁、公平锁、联锁、红锁、读写锁、信号量等，功能完善。

    * 对应关系：重入用可重入锁解决；可阻塞在可重入锁里同样有解决；超时问题、主从同步问题也都能在这里找到方案。

    * > **结论**：企业环境下没有必要自己实现锁，直接使用该开源框架即可；自己实现一遍的价值在于明白原理，利于面试与问题调试。

## 可重入锁的原理

### 借鉴 ReentrantLock

* **JDK 中的做法**

    * 获取锁时若发现锁已有人，会判断是不是自己（同一个线程）；是自己则允许获取，并用一个**计数器**记录重入次数。

    * 获取时次数累加，释放时次数减一。

* **分布式下的改造**

    * 不仅要记录获取锁的线程，还要记录重入的次数，每拿一次加一。

### Hash 结构

* **为什么 String 不够**

    * String 是简单 key-value，装不下「线程标识 + 重入次数」两样东西。

* **哈希结构（Hash）**

    * key 位置记录**锁的名称**，field 位置记录**线程标识**，value 位置记录**重复次数**。

```text
key          field          value
┌────────┐   ┌──────────┐   ┌──────┐
│  lock   │ → │  线程标识 │ → │  次数 │
└────────┘   └──────────┘   └──────┘
```

    * 代价：Hash 里没有 `NX`、`EX` 这样的组合命令，只能把原来的逻辑拆开——先判断锁存不存在，再手动设置过期时间。

### 获取锁流程

* **三个分支**

```text
                  tryLock()
                      │
             ┌────────┴────────┐
          锁不存在           锁已存在
       （EXISTS 返回 0）      │
        我是第一个来的         │
          │                   │
HSET lock <线程标识> 1   HEXISTS lock <线程标识>
（次数初始化为 1）                   │
PEXPIRE lock <释放时间>     ┌────────┴────────┐
          │                1（是我的）    0（别人的锁）
          │                  │                │
   HINCRBY +1          不是我的，重试也没意义
   PEXPIRE 重置有效期        │
          │                   │
     return 1              return 0
   获取成功                获取失败
```

    * 锁不存在：`HSET` 把次数**初始化为 1**，并 `PEXPIRE` 设置有效期。

    * 锁已存在但标识是自己：次数加一，**并重置有效期**——`method1` 执行中已消耗了一部分锁的时间，重置才能让内层方法有充足时间。

    * 锁已存在且标识是别人：直接获取失败，返回 0。

### 释放锁流程

* **为什么不能在内层直接删**

    * 内层方法结束不代表整个业务结束，返回后外层方法的剩余业务还要执行；此时删锁会让其他线程进来，可能发生并发安全问题。

    * > **易错点** ⚠️：可重入锁在内部被调用的方法里释放锁时**不能直接删除锁**，只能把重入次数减一。

* **怎么判断走到最外层**

    * 获取锁与释放锁成对出现，加了多少次就一定会减多少次，走到最外层时重入次数**一定会被减成零**。

    * 每次释放锁时先把次数减一，再判断是否为零：为零证明已到最外层，可以放心删除锁；不为零说明还有别的业务在跑，重置有效期并交给其他业务处理。

### 获取与释放脚本

* **参数**：`KEYS[1]` 锁名称，`ARGV[1]` 线程标识，`ARGV[2]` 锁的释放时间（获取过程中要设置有效期，所以多这一个参数）。

* **获取锁脚本**

```lua
-- 1.判断锁是否存在
if redis.call('exists', KEYS[1]) == 0 then
    redis.call('hset', KEYS[1], ARGV[1], 1)    -- 线程标识 + 次数初始化为 1
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 设置有效期
    return 1
end;

-- 2.锁已存在，判断锁标识是不是自己的
if redis.call('hexists', KEYS[1], ARGV[1]) == 1 then
    redis.call('hincrby', KEYS[1], ARGV[1], 1)  -- 重入次数 +1
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 重置有效期
    return 1
end;

-- 3.锁标识不是自己的，获取失败
return 0;
```

* **释放锁脚本**

```lua
-- 1.判断锁标识是不是自己
if redis.call('hexists', KEYS[1], ARGV[1]) == 0 then
    return nil;                                 -- 锁早就释放了（可能超时），不用管
end;

-- 2.是自己的，重入次数 -1
local counter = redis.call('hincrby', KEYS[1], ARGV[1], -1);

-- 3.判断减完之后是否还大于 0
if counter > 0 then
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 还在内层，重置有效期
    return nil;
end;

-- 4.已经小于等于零，走到最外层，真正释放
redis.call('del', KEYS[1]);
redis.call('publish', ARGV[1], 1);             -- 发消息通知锁已释放
return nil;
```

* **为什么必须用脚本**：流程复杂、步骤多，不可能再用 Java 代码实现，必须靠 Lua 脚本确保获取锁与释放锁的原子性。

* **实测表现**：外层获取成功后 Redis 里值为 1；进入内层再获取，值变成 2；内层释放，值减一但锁未删除；回到外层再释放，锁消失。

* **源码印证**：Redisson 的 `tryLockInner` 与 `unlockInner` 就是这两段脚本，脚本以字符串形式直接写死在源码里。

    * 源码里锁不存在时用的是 `hincrby`：不存在时会自动创建，与 `HSET` 效果一样。

    * `leaseTime` 未传时为 `-1`，走默认值；传了就用传入的值，最终都进到同一个方法。

## 锁重试

### tryLock 的三个参数

| 参数 | 含义 | 不传会怎样 |
| :--- | :--- | :--- |
| `waitTime` | 获取锁的**最大等待时长** | 只尝试一次，失败立即返回 `false` |
| `leaseTime` | 锁**自动失效释放的时间** | 取默认值 30 秒，同时**开启 WatchDog 续约** |
| `unit` | 上面两个时间的时间单位 | 必传 |

* **waitTime**

    * > **定义**：`waitTime` 一给，这把锁就从「一次性的」变成「可重试的锁」。

    * 一旦给了 `waitTime`，第一次获取失败就不会立刻返回，而是在等待时间内不断尝试；时间走完还没拿到才返回 `false`。

    * 传入后先把等待时间换算成毫秒——后续所有时间运算都按毫秒做。

### 返回值的巧思

* **加锁脚本的返回**

    * 获取成功返回 **`null`**。

    * 获取失败返回一个结果——脚本里执行了 `PTTL`，返回这把锁的**剩余有效期**。

    * `PTTL` 与 `TTL` 效果类似，都是取指定 key 的剩余有效期，区别是 `TTL` 以秒为单位、`PTTL` 以毫秒为单位；因为整体按毫秒运算所以用 `PTTL`。

* **异步结果**

    * 加锁是异步函数，命令发出去不代表结果拿到了，所以结果封装在 `Future` 里；外面紧跟 `get()` 阻塞等待，拿到的 `long` 就是剩余有效期。

### 订阅与信号量

* **第一次等待：不能立即重试**

    * 刚失败说明锁在别人手里、对方业务还没跑完，立刻再试大概率还是失败，只会白白增加 CPU 负担。

    * 做法是 `subscribe`，订阅别人释放锁的信号；`unlock` 的释放脚本在 `DEL` 之后有一行 `publish`，订阅的就是这条通知。

* **之后的等待：信号量**

    * 等的方式是等 `Future`：`future.await`，**只等剩余的最大等待时间**，指定时间内完成返回 `true`，否则 `false`。

    * 返回 `false`（超时）：先取消订阅，然后返回 `false`。

    * 返回 `true`（收到释放通知）：**又算一次时间**，用当前时间减之前的时间得到这一段等待的耗时，再用剩余时间减一次，得到真正的剩余等待时间；小于等于零同样 `return false`。

    * 获取信号时的等待时长分两种：

        * 锁的剩余有效期（`ttl`）小于剩余等待时间 → 只等 `ttl`，对方一释放立刻醒。

        * `ttl` 大于剩余等待时间 → 只等剩余等待时间，因为到期对方还没释放，等下去也没意义。

* **时间的严谨性**

    * 每一段耗时都要重新扣一次：先扣「获取锁这一段」的耗时，再扣「等待这一段」的耗时。

    * > **易错点**：如果获取锁消耗的时间太长，把 `waitTime` 整个耗完了，直接 `return false`；只有减完之后还大于零才可以继续尝试。

* **重试循环**

    * 形成「尝试 → 等待 → 尝试 → 等待」的循环：要么最终拿到锁，要么超时返回 `false`。

    * > **结论**：最巧妙之处是利用消息订阅 + 信号量的机制，而不是无休止的盲等（`while true`）；采用等待唤醒方案，不会无效等待，对 CPU 友好。

    * 底层用的是 Redis 的发布订阅（Publish/Subscribe，Pub/Sub）机制。

## WatchDog 续约

### 触发条件

* **看门狗（WatchDog）**

    * > **定义**：加锁成功后开启一个定时任务，每隔一段时间重置锁的超时时间，业务跑多久就续多久。

    * 解决的问题：确保锁是因为业务执行完才释放，而不是因为阻塞而释放。

* **回调逻辑**

```java
future.whenComplete((res, e) -> {
    if (e != null) {
        return;                       // 中间有问题了，什么都不做
    }
    if (res == null) {                // res == null 才是加锁成功
        scheduleExpirationRenewal(threadId);
    }
});
```

    * > **易错点** ⚠️：`whenComplete` 这段逻辑**只有 `leaseTime == -1` 时才会走到**；自己传了 `leaseTime` 就不会走看门狗逻辑，锁到期就是到期。

### 续约任务的组织

* **静态 Map**

    * `EXPIRATION_RENEWAL_MAP` 是 `static final` 的 `ConcurrentHashMap`，`RedissonLock` 类的所有实例都能看到它。

    * key 是 `entryName`，也就是**当前锁的名称**（`new` 锁时传进去的名字）；一把锁对应一个 entry，互不重复。

* **重入时如何保证唯一**

    * 用 `putIfAbsent`：第一次来 entry 不存在，放入全新 entry 并返回它；重入时 `putIfAbsent` 不执行，返回的是之前第一个线程创建的旧 entry。

    * 效果：不管这把锁被重入几次，拿到的永远是同一个 entry。

    * 新旧 entry 都会做 `addThreadId`——不同线程不可能拿到同一把锁，所以一定是同一线程多次获取，本质是重入。

    * 只有第一次来（拿到新 entry）才会多做一个 `renew` 动作；旧 entry 里已经有定时任务，重入只是补进线程 id。

### 续约周期

* **关键数值**

    * `leaseTime` 传 `-1` 时，取看门狗默认超时 `getLockWatchdogTimeout()` = `30 * 1000`，即 **30 秒**，赋给 `internalLockLeaseTime`。

    * 延时任务的延时是 `internalLockLeaseTime / 3`，即 **10 秒**；10 秒后任务才执行。

* **自循环**

```text
scheduleExpirationRenewal(threadId)          ← 只有加锁成功时触发一次
        │
        ├─ EXPIRATION_RENEWAL_MAP.putIfAbsent(锁名, new entry)
        │     首次 → 放入新 entry，才继续往下开启续约任务
        │     重入 → 拿回旧 entry，只把线程 id 塞进去
        ▼
renewExpiration()  ──► scheduleTimeoutTask(延时 = 30s / 3 = 10s)
        │
        ▼  10 秒后执行
续约脚本：① 判断锁是否仍是当前线程持有的   ② 是 → PEXPIRE 重置为 30 秒
        │
        ▼
执行完又调回自己 ──► 再挂一个 10 秒的延时任务 ──► 再等 10 秒 ──► …
```

    * 续约脚本做两件事：先判断锁是不是当前这个线程拿的，是则执行 `PEXPIRE` 重新设置有效期，相当于满血复活、重新开始计时。

    * 因为执行完又调自己，锁一开始设成 30 秒，过 10 秒又设成 30 秒，如此往复，有效期无限重置、永不过期。

### 取消续约

* **时机**：锁被释放时，`unlockInner` 成功后执行 `cancelExpirationRenewal`。

* **步骤**：先从静态 Map 里按锁名取出 entry → `deleteThreadId` 删掉线程 id → 取出 `Timeout` 定时任务并 `cancel` → 从 Map 里 `remove` 掉这个 entry。

* **释放锁成功后的两件事**

    * 发送释放锁的消息：等待重试的人还在等这个信号，收到后才能再次争抢。

    * 取消 WatchDog：定时任务是循环往复执行的，不取消就会无休止地执行。

## 主从一致性与 MultiLock

### 主从一致性问题

* **起因**

    * 单节点 Redis 一旦故障，所有依赖它的业务（包括分布式锁）都会出问题，核心业务不允许这种情况。

    * 主从模式做读写分离提高可用性：主节点处理写操作，从节点处理读操作，主节点不断把数据同步给从节点。

* **失效链**

```text
   Java 应用                主节点                从节点
        │                      │                      │
        │ SET lock:thread1     │                      │
        │ NX EX 30 ───────────►│                      │
        │                      │ 保存锁标识            │
        │                      ├──── 数据同步 ───────►│
        │                      │    （同步中……）      │
        │                      │ ✖ 宕机，同步尚未完成  │
        │                      │                      │ 从节点上没有锁标识

  哨兵监控到主节点宕机 → 客户端连接断开 → 从从节点中选出一个作为新主节点

  Java 应用再访问新主节点：锁已经没有了，锁失效 → 其他线程也能获取成功
```

### MultiLock 的思路

* **连锁（MultiLock）**

    * 思路：既然主从关系是导致一致性问题的原因，就干脆不要主从——所有节点都变成独立的 Redis 节点，相互之间没有任何主从关系，都可以做读写。

    * 获取方式随之改变：必须**依次向多个 Redis 节点都去获取锁**，不管三个还是五个节点，全部都保存了锁标识才算获取成功。

* **效果**

    * 没有主从，就没有主从一致性问题。

    * 可用性：一个节点宕机，只要其他节点还存活着，锁依然有效；可用性还可以随节点增多而提高。

    * 也可以给这些节点再建立主从关系提高可用性：即使某个从节点没完成同步就被提升为新主、被一个线程趁虚而入拿到锁，其他节点仍然拿不到，最终还是失败。

    * > **结论**：只要不是所有节点都出问题，其他线程就不可能拿到锁，不会出现锁失效。

### MultiLock 的获取循环

* **组装**

    * `RLock multiLock = client1.getMultiLock(lock1, lock2, lock3);`，参数是可变参数，接收多个 lock。

    * 用哪个 client 调用没有区别——进去是 `new` 出来的，甚至自己 `new` 都行。

    * 传进来的数组会被转成集合存进成员变量 `locks`；获取时依次遍历每一把锁都尝试获取，都成功才算成功。

* **循环要点**

    * `failedLocksLimit`（获取失败的锁的限制）值为 **0**：只有「已获取数量等于锁的总数量」时 `locks.size() - acquiredLocks.size()` 才为 0 才 break，也就是**只有把所有锁都拿到了才能结束循环**。

    * 获取成功 → 放进 `acquiredLocks`，并扣减本轮已耗时；剩余时间小于等于 0 时，先把已拿到的锁全部 `unlock` 再 `return false`。

    * 时间耗尽前 `return false` 之前，一定先把 `acquiredLocks` 里已拿到的锁全部释放——已经失败了，前面拿到的锁就不能再拿着，否则别人拿不了。

    * 重试时是「从第一把锁开始」：先清空 `acquiredLocks`，把迭代器指针复位到第一把，再来一次完整的循环。

    * 拿到所有锁后 `return true`；超时则最终返回 `false`。

* **leaseTime 的处理**

    * 若传了 `leaseTime` 且 `waitTime != -1`（要重试），重试时不会用原来的释放时间，而是用 **`waitTime × 2`** 代替。

    * 原因：重试可能耗时较久，释放时间小于等待时间的话，还没重试完锁就过期了。

    * 若 `waitTime == -1`（只想获取一次、不重试），就用传入的释放时间。

* **实测表现（三个独立节点）**

    * 获取连锁锁成功，三个节点上分别多出一把锁，后面那个数字就是重入次数。

    * 再重入一次，三边的数字都从 1 变成 2——连锁中每一个独立的锁都是可重入锁，只是把三把联合起来分别获取。

    * 释放一次，三边都从 2 变回 1；再释放一次，三个节点上的锁全部消失。

### 统一有效期

* **为什么要再 PEXPIRE 一遍**

    * 依次获取时，第一把获取的锁获取后**立即开始倒计时**，最后一把锁才**刚开始倒计时**；同一集合内多把锁的剩余有效期不一致，可能出现有些释放了有些没释放。

    * 做法：所有锁都拿到后、`return true` 之前，遍历已拿到的每一把锁执行 `PEXPIRE`，重新设置有效期，确保大家的有效期一致。

* **适用条件**

    * 只有 `leaseTime != -1` 时才需要；`leaseTime == -1` 时会触发看门狗，所有锁的有效期都会自动续约，无需处理。

    * > **提示**：释放时间不建议设置，让它走 WatchDog。

## 三类锁的选型对比

| 方案 | 可重入 | 获取失败重试 | 锁超时释放 | 主要问题 |
| :--- | :--- | :--- | :--- | :--- |
| 不可重入的 Redis 分布式锁（自己写的） | 不支持 | 不支持 | 到期自动释放，业务没跑完就有风险 | 实现简单、大多数场景实用；但不适合有重入需求、重试需求，或安全性要求较高的业务 |
| Redisson 可重入锁 | 支持（Hash 记录线程标识 + 重复次数） | 支持（发布订阅 + 信号量） | WatchDog 不断续约，除非服务宕机 | 主从一致性引起的锁失效 |
| Redisson MultiLock 连锁 | 支持 | 支持 | WatchDog 不断续约 | 成本较高——最少三个独立节点，五个以上更好；可再加主从提高可用性，但成本更高、实现更复杂 |

* **自定义不可重入锁**

    * 原理：利用 `SET NX` 的互斥性，`EX` 设置过期时间避免死锁，释放锁时判断线程标识避免误删。

    * 缺陷：不可重入、无法重试，锁超时有自动释放的风险。

    * 适用：实现简单，大多数场景下实用；不适合有重入需求、重试需求或安全性要求较高的场景。

* **Redisson 可重入锁**

    * 用哈希结构记录线程标识和重入次数实现可重入；用 WatchDog 延续剩余时间、不断续约，确保锁不会因自动超时而释放（除非服务宕机）；用信号量 + 发布订阅控制重试，等待唤醒方案不会无效等待，对 CPU 友好。

    * 缺陷：主从一致性引起的锁失效。

* **MultiLock 连锁**

    * 多个独立的 Redis 节点、节点之间无主从关系，不会因主从一致导致锁失效；获取时要在所有节点都获取成功才算成功，可看成多个可重入锁的集合。

    * 缺点：成本较高，最少三个独立节点（五个以上更好），给节点再建主从会进一步提高成本与复杂度。

    * 优点：**是所有方案里最安全的一种**。

* **遗留影响**

    * 加入各种锁后，秒杀业务的性能会受到巨大影响，后续还需要进一步优化。
