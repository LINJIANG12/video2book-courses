# 多级缓存架构与缓存同步

## JVM 进程缓存

### 缓存库的划分与声明

* **进程缓存（JVM 进程缓存）**

    * > **定义**：运行在 Tomcat 内部、保存在 Java 进程内存里的本地缓存，命中时不再访问数据库。

    * 商品与库存必须各用一份缓存库，不能往同一份缓存里塞两种数据。

    * 缓存库要在项目启动时就初始化好，声明成 Spring 容器里的 Bean，业务要用时都从里面读写。

    * key 取实体的 id，商品的 id 是 `Long` 类型，所以缓存泛型是 `Cache<Long, Item>`；库存为 `Cache<Long, ItemStock>`。

    * 需求给定的参数为：初始容量 100，最大容量 10000，超出后按淘汰策略清理。

* **Caffeine 构建器参数**

    * 通过 `Caffeine.newBuilder()` 创建构建器，`build()` 完成构建，`build` 之前可以追加各种参数。

    * `initialCapacity(100)` 设初始容量，`maximumSize(10_000)` 设上限；`10_000` 中的下划线只是数字分隔符，编译后仍是 10000。

```java
@Configuration
public class CacheConfig {

    @Bean
    public Cache<Long, Item> itemCache() {
        return Caffeine.newBuilder()
                .initialCapacity(100)
                .maximumSize(10_000)
                .build();
    }

    @Bean
    public Cache<Long, ItemStock> stockCache() {
        return Caffeine.newBuilder()
                .initialCapacity(100)
                .maximumSize(10_000)
                .build();
    }
}
```

### 查询业务的缓存化改造

* **`get(key, Function)`**

    * > **定义**：一个 API 顶掉整段"先查缓存、未命中再查数据库"的 if-else。

    * 第一个参数是 key（就是商品的 id），第二个参数是 Lambda 形式的备选方案——缓存未命中时执行它去查数据库。

    * Lambda 里的参数名与外层 id 不能重名，需要重新命名；它拿到的值就是外面传进来的那个 id。

```java
@GetMapping("item/{id}")
public Item queryItemById(@PathVariable Long id) {
    return itemCache.get(id, key -> {
        Item item = itemService.queryById(key);
        return item;
    });
}

@GetMapping("stock/{id}")
public ItemStock queryStockById(@PathVariable Long id) {
    return stockCache.get(id, key -> itemService.queryStockById(key));
}
```

### 进程缓存的验证方式

* 验证手段是看 SQL 日志：清空日志后首次访问接口会产生一条 SQL，说明走了数据库；再次刷新没有日志，说明走的是缓存。

* > **结论**：第一次查询走数据库并把数据放入缓存，之后一直走缓存。

## Lua 语言基础

### Lua 的定位与运行

* **Lua**

    * > **定义**：用 C 语言编写、以源代码形式开放的轻量小巧脚本语言，设计目的是嵌入应用程序。

    * 常被用在游戏开发中编写插件实现拓展（例如魔兽世界的插件）。

    * 与 Web 服务的对应关系：Tomcat 用 Java 写业务，Nginx 用 Lua 写业务。

    * CentOS 系统自带 Lua，无需额外安装；执行用 `lua 文件名`，也可以直接输入 `lua` 进入交互控制台做语法试验。

    * Lua 不需要编译，可直接运行；字符串可用双引号也可用单引号；语句末尾不需要加分号。

### 数据类型

* **nil**

    * > **定义**：代表无效、等于没有，类似 Java 的 null，但同时还能代表 false。

    * `nil` 在条件判断中代表假；`not nil` 代表 true。

* **boolean / number / string / function / table**

    * `boolean`：true 或 false，与 Java 相同。

    * `number`：数值类型，不区分整数与小数，统一用 number 表示。

    * `string`：字符串，单双引号均可。

    * `function`：函数本身也是一种数据类型，可以声明函数类型的变量并把它传递，C 与 Lua 之间可以互相引用函数。

    * `table`：key-value 结构，既可以当 map 也可以当数组；key 是数字时表现为数组，key 是字符串时表现为 map。

* **`type()`**

    * > **定义**：判断并返回变量数据类型的函数，返回值本身是字符串。

    * `type('hello')` 得 `string`，`type(1)` 得 `number`，`type(true)` 得 `boolean`，`type(print)` 得 `function`。

### 变量声明与访问

* **变量声明**

    * 声明时不需要指定数据类型，写法是 `local` + 变量名 + 值；`local` 表示局部变量，作用域仅限当前代码块。

    * 不写 `local` 就是全局变量，后续代码块中依然可以访问。

    * 字符串拼接用两个点 `..`。

```lua
local str = 'hello'
local age = 21
local flag = true
local nothing = nil

local arr = {"hello", "world", "java"}
local map = {name='jack', age=21}

local str1 = 'hello' .. 'world'
```

* **table 的两种访问方式**

    * 数组用角标访问，且角标**从 1 开始**，`arr[1]` 取到第一个元素。

    * > **易错点**：Lua 数组没有下标 0，取 `arr[0]` 得到的是 nil。

    * key 为字符串的 table 可用 `map['name']` 取，也可用 `map.name` 这种点语法取。

    * Java 里 List 与 Map 是两个东西，Lua 把它们抹平成一个 table；判断某种写法能不能用时先想底层是不是 table。

* **遍历**

    * 数组用 `ipairs`，table 用 `pairs`；两者都把元素解析成一对 key-value。

    * 循环体的开始是 `do`、结束是 `end`，不是大括号。

    * `print` 可以用逗号隔开多个值一起打印。

```lua
for index, value in ipairs(arr) do
    print(index, value)
end

for key, value in pairs(map) do
    print(key, value)
end
```

### 函数与条件控制

* **函数定义**

    * 语法为 `function` + 函数名 + 参数列表 + 函数体 + `end`，可以有 `return` 也可以没有；可以用 `local function` 限定为局部。

    * 作用是把重复代码封装复用，例如把打印数组的循环收成 `printArr(arr)`。

* **条件控制**

    * 语法为 `if` + 布尔表达式 + 函数体 + `end`，多条件判断写 `elseif`。

    * 比较运算（大于、小于、大于等于、小于等于）与 Java 差别不大。

    * 逻辑运算不用符号而用英文单词：`and` 是与，`or` 是或，`not` 是非。

    * 判空写法是 `if not arr then`：传进来的 nil 代表 false，取反后为 true，进入分支打印错误信息并 `return`。

```lua
local function printArr(arr)
    if not arr then
        print('数组不能为空')
        return
    end

    for key, value in ipairs(arr) do
        print(value)
    end
end
```

## OpenResty

### OpenResty 是什么

* **OpenResty**

    * > **定义**：基于 Nginx 的高性能 Web 平台，为 Nginx 做了定制并提供大量精良的 Lua 语言库和第三方模块。

    * 基于这些插件可以编写自定义业务逻辑，实现动态的 Web 服务。

    * OpenResty 的可执行文件本质就是 Nginx；`bin` 目录下的 `openresty` 是指向 `nginx` 可执行文件的软链接。

* **目录结构**

    * `lualib`：OpenResty 提供的第三方 Lua 模块，操作 Redis、MySQL 的插件都在里面。

    * `nginx/conf`：默认的 `nginx.conf`；`nginx/html` 默认站点页面；另有 `logs`、`sbin`。

```text
/usr/local/openresty
├── bin/          可执行文件目录（openresty 是软链接，指向 nginx）
├── lualib/       OpenResty 提供的第三方 Lua 模块
├── nginx/
│   ├── conf/     里面是 nginx.conf 默认配置文件
│   ├── html/     默认站点页面
│   ├── logs/
│   └── sbin/
└── ...
```

### 安装、配置与启动

* 安装步骤：安装依赖库 → 用 `yum config-manager` 添加仓库地址 → 安装 OpenResty 本体、管理插件与管理工具（管理工具用于下载第三方 Lua 模块）。

    * > **提示**：`config-manager` 报错说明机器上没有 `yum-utils`，先装 `yum-utils` 再执行。

* 安装目录是 `/usr/local/openresty`；安装过程需要联网下载依赖库。

* 配置环境变量要修改 `/etc/profile` 把 Nginx 目录配进 PATH，再 `source /etc/profile` 生效。

* 启动用 `nginx`，重新加载用 `nginx -s reload`，停止用 `nginx -s stop`；启动后可见一个 master 主进程与一个 worker 工作进程。

* 默认的 `nginx.conf` 注释非常多，做法是用去掉注释的简化版配置替换；示例端口为 8081，访问后看到 "Welcome to OpenResty" 欢迎页即安装成功。

### 加载 Lua 模块与 C 模块

* 访问 Redis、MySQL、Tomcat 之前必须先加载 OpenResty 的工具模块，配置放在 `nginx.conf` 的 `http` 块下，属于固定写法。

```nginx
http {
    lua_package_path /usr/local/openresty/lualib/?.lua;;
    lua_package_cpath /usr/local/openresty/lualib/?.so;;
}
```

    * `lua_package_path` 对应 Lua 函数模块（`.lua`），`lua_package_cpath` 对应 C 函数模块（`.so`），路径值就是 OpenResty 的安装目录。

## OpenResty 接收请求

### location 与 Lua 文件的分工

* `location` 负责拦路径，相当于 Controller；`content_by_lua_file` 指定的 Lua 文件负责写业务，相当于 Service。

* `default_type application/json` 声明默认响应类型，Lua 文件返回 JSON，页面拿到即可渲染。

```nginx
server {
    listen 8081;
    server_name localhost;

    location /api/item {
        default_type application/json;
        content_by_lua_file /lua/item.lua;
    }
}
```

* **ngx.say**

    * > **定义**：把结果写回浏览器的函数，相当于 Java 里的 `response.print`。

    * > **易错点**：返回 JSON 字符串时必须用单引号包住 Lua 字符串，否则与 JSON 内部的双引号冲突。

```lua
ngx.say('{"id":1001,"title":"26寸曲面屏","price":199}')
```

* Lua 文件建在 Nginx 目录下的 `lua` 目录中，改完配置与文件都要 `nginx -s reload`。

### 请求参数的获取

* **路径占位符**

    * 唯一需要正则表达式的参数类型：`location ~ /api/item/(\d+)`，波浪线表示后面是正则匹配，`~` 两边都要留空格。

    * 括号是正则的分组；`\d` 匹配数字，`+` 表示至少一个字符，商品 id 是 long 型所以这样写。

    * 被路径正则匹配到的参数会存进 `ngx.var` 数组，按顺序取用角标，第一个分组就是 `ngx.var[1]`。

* **其余四类参数**

    * > **易错点**：波浪线两边都要留空格，别写成 `~/api/item`。

| 参数类型 | 获取方式 | 返回值 |
| :--- | :--- | :--- |
| 路径占位符 | `ngx.var[1]` | 匹配到的字符串 |
| 请求头 | `ngx.req.get_headers()` | table |
| GET 请求参数（`?a=1`） | `ngx.req.get_uri_args()` | table |
| POST 表单参数 | `ngx.req.read_body()` + `ngx.req.get_post_args()` | table |
| JSON 请求体 | `ngx.req.read_body()` + `ngx.req.get_body_data()` | 原始 JSON 字符串 |

    * 请求头与 GET 参数都是 key-value 结构，所以返回值用 table 封装。

    * POST 表单与 JSON 请求体都要先 `read_body` 读取并解析请求体，再取参数；JSON 走 `get_body_data` 得到的是 JSON 字符串本身。

* 拿到 id 后用两个点拼进返回结果，结果就不再是写死的，而是随请求 id 动态变化。

```lua
local id = ngx.var[1]
ngx.say('{"id":' .. id .. ',"title":"26寸曲面屏","price":199}')
```

## 向 Tomcat 发起请求

### ngx.location.capture

* **ngx.location.capture（capture）**

    * > **定义**：在 OpenResty 内部发起一个 HTTP 请求的 API，名字意为捕获一个请求。

    * 第一个参数是请求路径，第二个参数是 table：请求方式（GET 用 `ngx.HTTP_GET`）、GET 参数用 `args`、POST 参数用 `body`，两者按请求方式二选一。

    * 返回值是 response 对象，含 `status` 状态码、`header` 响应头、`body` 响应体；业务关心的只有 `body`，而 `body` 是 JSON 字符串。

    * > **易错点**：`capture` 发出的请求不带 IP 和端口，因此不会发到任何外部地址，而是被 Nginx 自己接住。

### 用反向代理把请求送出去

* 发给自己的请求要靠反向代理转发出去：新增一个 `location /item`，`proxy_pass` 指向 Tomcat 的 IP 与端口。

* 路径前缀取 `item`，因为查商品与查库存的 Controller 路径都以 `item` 开头。

* 从虚拟机访问 Windows 上的 Tomcat：不管虚拟地址是什么，取前三位并把最后一位换成 1 就是 Windows 地址（如 `192.168.150.101` 对应 `192.168.150.1`）。

    * > **注意**：前提是防火墙必须关闭，否则访问不到 Windows 上的服务。

```nginx
location /item {
    proxy_pass http://192.168.150.1:8081;
}
```

### 通用工具模块

* 放在 `/usr/local/openresty/lualib` 下的 `.lua` 文件会被 `lua_package_path` 自动加载，里面定义的函数也就成为通用工具。

* 引用方式是 `require`，返回的是导出时那个 table；函数也是变量，可以用变量接收，也可以写成 `local readHttp = common.readHttp`。

    * > **提示**：`require` 后面跟文件名；若目标文件在子目录下，必须带上目录名。

```lua
-- common.lua
local function readHttp(path, params)
    local resp = ngx.location.capture(path, {
        method = ngx.HTTP_GET,
        args   = params
    })

    if not resp then
        ngx.log(ngx.ERR, "http not found, path: ", path, ", params: ", params)
        ngx.exit(500)
    end

    return resp.body
end

local m = {}

m.readHttp = readHttp

return m
```

    * 路径 `path` 与参数 `params` 都由调用方传入，方式固定为 GET；查不到时 response 是 nil，取反后进入分支记日志并 `ngx.exit(500)`。

    * `ngx.log` 记日志、`ngx.ERR` 是错误级别、`ngx.exit` 退出。

### cjson 的序列化与反序列化

* **cjson**

    * > **定义**：OpenResty 提供的 JSON 处理库，`require("cjson")` 引入。

    * `encode` 序列化，把 table 变成 JSON；`decode` 反序列化，把 JSON 字符串变成 table。

    * JSON 无法直接做数据拼装，必须先转成 table 才能操作：把库存表查到的 `stock`、`sold` 填进商品 table，再序列化回 JSON 返回。

```lua
local item  = cjson.decode(itemJson)
local stock = cjson.decode(stockJson)

item.stock = stock.stock
item.sold  = stock.sold

ngx.say(cjson.encode(item))
```

    * 查商品与查库存的调用路径分别是 `item` 拼 id、`item/stock` 拼 id，没有问号参数时第二个参数传 `nil`。

## Tomcat 集群负载均衡

### 轮询与进程缓存的矛盾

* 生产中 Tomcat 一定是集群，需要定义 `upstream` 形成集群，反向代理的目标从写死的 IP 改成集群名称。

* 默认负载均衡规则是轮询，而**进程缓存不能共享**：8081 上建的缓存 8082 上没有，下一次请求被轮询到 8082 就又要查一遍数据库。

* 结果是每台 Tomcat 都要冗余保存一份缓存，既占额外空间，命中率也低。

* 要让 JVM 进程缓存有意义，必须让同一个商品 id 永远落到同一台服务器。

### hash $request_uri

* **hash $request_uri**

    * > **定义**：对请求路径做哈希运算，再对服务器数量取模，据此选择目标服务器的负载均衡算法。

    * 路径不变则哈希值不变，永远访问同一台服务器，进程缓存持续命中；路径（id）变了哈希值就变，自然换到另一台，仍然起到负载均衡作用。

```nginx
upstream tomcat_cluster {
    hash $request_uri;
    server 192.168.150.1:8081;
    server 192.168.150.1:8082;
}

location /item {
    proxy_pass http://tomcat_cluster;
}
```

    * 起两台 Tomcat 的做法是复制一份启动配置、改名并把 `server.port` 改成 8082。

    * 验证方式：反复访问同一个 id，只有被哈希选中的那台产生首次查询日志，之后再无任何日志；换成另一个 id 才切到另一台并建立它自己的缓存。

    * > **结论**：同一个商品 id 必须永远落到同一台服务器，否则每台都缓存一份，既浪费空间，命中率又上不去。

## Redis 缓存预热

### 冷启动与预热

* **冷启动**

    * > **定义**：服务刚启动、缓存还是空的那段时间里，大量请求同时穿透缓存直打数据库，导致数据库压力骤增甚至不可用。

* **缓存预热**

    * > **定义**：项目启动时提前把数据放进缓存，把"第一次查询才去查库"这件事挪到启动阶段提前做完。

    * 预热内容由热点数据决定：真实项目中借助大数据统计出热点名单，只把热点数据放进 Redis；演示时把数据库中的全部商品与库存数据都放进去。

    * 数据库的数据量远大于 Redis 容量，全量放入不现实。

### 用 InitializingBean 挂到启动时刻

* **InitializingBean**

    * > **定义**：Spring 提供的接口，实现后在 bean 创建完成且成员变量注入完成后执行其 `afterPropertiesSet()` 方法。

    * bean 本来就在项目启动时创建，把预热逻辑写进 `afterPropertiesSet()`，就等于项目一启动就预热。

    * 类上加 `@Component` 才能被 Spring 管理并注入容器。

    * > **易错点**：实现了 `InitializingBean` 就必须实现 `afterPropertiesSet()`，方法名写错或漏写都是坑。

* 预热三步：查数据 → 序列化成 JSON → 写进 Redis。

* Redis 环境用 Docker 启动：`docker run --name redis -p 6379:6379 -d redis redis-server --appendonly yes`，`--appendonly yes` 用日志方式做持久化。

* 接入 Redis 两步：引 `spring-boot-starter-data-redis` 依赖；配置 `spring.redis.host` 为虚拟机地址、端口 6379。

### 序列化与 key 前缀

* **ObjectMapper**

    * > **定义**：Jackson 提供的工具类，`writeValueAsString(对象)` 把对象写成 JSON 字符串；通常定义为静态常量当工具用。

* 写入用 `redisTemplate.opsForValue().set(key, json)`。

* key 必须带前缀：商品与库存的 id 相同，若直接用 id 当 key 两边会撞车冲突。

```java
redisTemplate.opsForValue().set("item:id:" + item.getId(), json);      // 商品缓存
redisTemplate.opsForValue().set("stock:id:" + stock.getId(), json);    // 库存缓存
```

```text
item:id:1003   -->  {"id":1003,"title":"xxxx","price":1999}    商品基本信息
stock:id:1003  -->  {"id":1003,"stock":99}                     商品库存
```

    * 库存侧改用库存 Service，遍历、序列化、写缓存的套路与商品一致，只是 key 前缀换成 `stock:id:`。

    * 验证：项目启动那一刻控制台就有查询日志，商品与库存各查到五条；打开 Redis 客户端能看到两批 key。

## OpenResty 操作 Redis

### resty.redis 与连接

* 引入方式是 `require("resty.redis")`；库名称带点是因为 `redis.lua` 不在 `lualib` 根目录而在 `resty` 子目录下，所以要写成"目录名.文件名"。

* `redis:new()` 是 Lua 的面向对象写法，相当于构造函数，创建出的对象才能拿去用。

* `red:set_timeouts(1000, 1000, 1000)` 设置三个超时时间，单位都是毫秒，从左到右依次是建立连接超时、发送请求超时、响应结果超时。

### 连接池与"关闭"

* **set_keepalive**

    * > **定义**：把连接保持住放回连接池，而不是真正关闭；示例里最大空闲时间 10000 毫秒（10 秒）、连接池大小 100。

    * 每次请求创建连接、用完又释放，性能较差，所以连接应放在连接池里复用。

    * 十秒内没人用才真正关掉；十秒内一直在用就不关。

    * 返回两个值 `ok` 与 `err`：失败时 `ok` 为 nil，取反为 true 正好进 `if` 分支记日志。

```lua
local function close_redis(red)
    local idle_timeout = 10000   -- 10 秒
    local pool_size = 100

    local ok, err = red:set_keepalive(idle_timeout, pool_size)
    if not ok then
        ngx.log(ngx.ERR, "redis 连接释放失败：", err)
    end
end
```

* `close_redis` 只在 `read_redis` 内部调用，不用对外暴露；暴露的写法与 HTTP 工具一致，在 common 的 table 上加一个属性即可（`M.read_redis = read_redis`）。

### 读数据与两种空结果

* `red:get(key)` 只支持最简单的 key-value（string 类型）读取，map 之类没有封装。

* 返回值要区分两种情况，含义完全不同：

    * `if not res`：`res` 为 nil，说明这次查询**失败了**。

    * `res == false`：查询**成功了**，只是没查到，很可能是 key 根本不存在。

    * > **易错点**：nil 是查询失败，false 是查询成功但数据为空，必须分开判断，否则排错会被带偏。

```lua
local function read_redis(ip, port, key)
    local ok, err = red:connect(ip, port)
    if not ok then
        ngx.log(ngx.ERR, "redis 连接失败：", err)
        return
    end

    local res, err = red:get(key)
    if not res then
        ngx.log(ngx.ERR, "redis 查询失败：", err)
    elseif res == false then
        ngx.log(ngx.ERR, "redis 查询数据为空，key 不存在：", key)
    else
        close_redis(red)
        return res
    end
end
```

### 先 Redis 再 HTTP

* **read_data**

    * > **定义**：把"查一个 key，没查到再查 HTTP"这串几乎一样的逻辑收成的函数，商品与库存共用。

    * 参数有 key、path、param；ip 与端口写死为 `127.0.0.1:6379`，因为 Lua 跑在 OpenResty 里而 Redis 也在同一台虚拟机上。

    * 日志必须带上失败的 key，否则线上查不到时无法定位是哪件商品出了问题。

```lua
local function read_data(key, path, param)
    local resp = read_redis("127.0.0.1", 6379, key)
    if not resp then
        ngx.log(ngx.ERR, "redis 查询失败，key：", key, "，尝试查询 http")
        resp = read_http(path, param)
    end
    return resp
end
```

* 验证办法：把两台 Tomcat 都停掉，页面仍能查出数据，就证明走的是 Redis 而不是 Tomcat。

## OpenResty 本地缓存

### lua_shared_dict

* **lua_shared_dict（共享词典）**

    * > **定义**：在 `nginx.conf` 的 `http` 块下声明的一块共享内存，供同一个 nginx 实例内的多个 worker 进程共享数据。

    * Nginx 通常是一个 master 加多个 worker，worker 负责处理用户请求且彼此可以共享数据。

    * > **注意**：这种共享只在一个 nginx 实例内部成立，部署多台 OpenResty 时它们之间无法共享。

```nginx
http {
    lua_shared_dict item_cache 150m;
}
```

    * 两个参数：词典名称（可自定义，如 `item_cache`）与大小（示例给 150m，因为机器内存不大所以给小一点）。

* 取对象用 `ngx.shared` 加词典名称：`local item_cache = ngx.shared.item_cache`；这一行写在业务 Lua 文件里，不是写在工具模块里。

* `set(key, value, 时间)` 存数据，第三个参数是超时秒数，到点自动删除以免越存越多；`get(key)` 取数据。

    * > **提示**：第三个参数给 0 代表永不过期。

```lua
item_cache:set(key, value, 1000)   -- 存 1000 秒后自动过期
item_cache:get(key)                 -- 取的时候只给 key 就行
```

### 三级查询与回填

* 顺序是：本地缓存 → Redis → Tomcat，命中任何一级即返回。

* 查到数据后**必须写回本地缓存**，否则本地缓存永远没有数据，共享词典等于白开；哪怕数据来自 Redis 也要写一份并设过期时间。

* > **易错点**：有效期不能写死在函数体里，商品与库存的合理有效期完全不同，要做成 `expire` 参数传进来。

```lua
local item_cache = ngx.shared.item_cache

local function read_data(key, path, param, expire)
    local value = item_cache:get(key)
    if not value then
        ngx.log(ngx.ERR, "本地缓存查询失败，尝试查询 redis，key：", key)
        value = read_redis("127.0.0.1", 6379, key)
        if not value then
            ngx.log(ngx.ERR, "redis 查询失败，尝试查询 http，key：", key)
            value = read_http(path, param)
        end
        item_cache:set(key, value, expire)
    end
    return value
end
```

* 排错时看日志：`cd` 到 OpenResty 的 nginx 目录，`tail -f logs/error.log`。

    * > **易错点**：`ngx.log` 的第一个参数必须是日志级别 `ngx.ERR`，漏写会直接报错；正确写法是 `ngx.log(ngx.ERR, "本地缓存查询失败...")`。

### 有效期怎么定

* 商品基本信息配 30 分钟（1800 秒），库存配 1 分钟（60 秒）。

```lua
local itemData = read_data(itemKey, path, param, 1800)
local stockData = read_data(stockKey, path, param, 60)
```

* 商品基本信息、描述、规格参数上架后基本不变，有效期可以设长；库存变化频率高，有效期要尽可能短。

* Nginx 本地缓存的更新策略是**到期更新**，到期之前数据变了它不知道，所以特别敏感的数据根本不要往里存。

    * 普通商品库存差一分钟影响不大，可以存；秒杀商品的库存不要往里加。

* 验证命中：第一次请求本地缓存必然失败（本来就是空的），日志出现"先查本地缓存失败，然后查 Redis"；再刷新无日志即说明走了本地缓存。

    * 把 Redis 里某商品的 key 删掉后仍能正常返回且响应极快（约 6ms），是因为 nginx 里还留着本地缓存。

## 缓存同步策略

### 三种常见策略

| 策略 | 怎么做 | 优势 | 不足 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 有效期（被动同步） | 只给缓存设计有效期，到期自动删除，下次查询自然拿到新数据 | 简单、方便，等于根本不用做同步 | 时效性差：到期之前数据库改了，缓存根本不知道 | 更新频率较低、时效性要求较低的业务 |
| 同步双写 | 数据库写和缓存写放进同一个事务 | 时效性非常强，基本能做到强一致 | 代码侵入、耦合度高，缓存点越多业务代码越臃肿 | 对一致性、时效性要求比较高的缓存场景 |
| 异步通知 | 改库后发一条消息/事件，通知缓存自己去更新 | 低耦合、代码侵入少，一条通知可被多个缓存服务消费 | 时效性比同步双写差一些 | 时效性要求没那么高、且有多个服务需要同步 |

### 有效期与同步双写

* 有效期方式属于被动同步，OpenResty 本地缓存用的就是这种；时效性指数据库与缓存同步之间存在的时差。

* 商品数据可按变化频率拆分：库存、价格这种经常变化的单独保存并用别的方式同步，不怎么变的数据用过期方式同步。

* 同步双写把数据库写与缓存写放进同一个事务，要么都成功要么都失败，时效性非常强、基本强一致。

    * 代价是代码侵入耦合度高：新增商品业务里硬塞一段更新缓存逻辑，缓存点多了业务代码会变臃肿。

### 异步通知与 Canal 的取舍

* 异步通知不直接改缓存，而是发一条消息通知各缓存自行更新；可用 MQ 实现，延迟常在毫秒级别且可靠性较强。

* 缺点是不确定对方何时收到、何时改完，时效性比同步双写差；适合有多个服务需要同步的场景，大多数缓存都能用这种方案。

* **Canal**

    * > **定义**：阿里巴巴旗下基于 Java 开发的开源项目，作用是监控数据库变更、提供增量数据的订阅和消费；名字意为水道、管道。

    * 与 MQ 方案的差别：发 MQ 消息仍要在商品服务里加代码，而 Canal 方案下商品服务照旧写数据库、一行代码都不用改，改完即结束。

    * 优势是**零侵入、零耦合**，且时效性与效率都比 MQ 方式更好。

```text
     商品服务：照旧写 MySQL，一行代码都不用改
                     |
                     v
                  MySQL
                     |  binlog 变化
                     v
                  Canal      监听数据库变化
                     |
                     v
              缓存服务：收到通知 --> 更新缓存
```

## Canal 的部署

### MySQL 主从同步

* Master 执行增删改时写入 binlog（二进制日志文件），里面记的是 binary log events，即执行的那些业务 SQL。

* Slave 开一个 I/O 线程不断读 binlog 并放进 relay log（中继日志），再由 SQL 线程重放这些操作，两边数据因此一致。

* 开启方式：修改 `my.cnf`，加两行后 `docker restart mysql`。

```ini
[mysqld]
log-bin=mysql-bin
binlog-do-db=黑马
```

    * `log-bin` 指定 binlog 的存放位置与名称，`mysql-bin` 可自定义；`binlog-do-db` 指定监控哪一个数据库。

    * > **易错点**：别一上来就全库记录，只记录业务数据所在的那个库，否则会记录大量无关库。

    * 重启后 data 目录出现 `mysql-bin.0001`，`mysql-bin` 是起的名字、`.0001` 是文件编号，编号会随文件增多逐渐增大。

* 给从库设置权限：创建名为 `canal` 的新用户、授权、刷新权限。

* `SHOW MASTER STATUS` 查看主从状态，`File` 是 binlog 名称、`Position` 是日志偏移量。

    * > **提示**：从库的 position 小于主库就说明还有新日志要获取，这一点类似 Redis 主从同步里的 offset，用来确定主从数据差异。

### 安装 Canal 容器

* 先建 Docker 网络并把 MySQL 加进去，安装 Canal 时也加入同一网络，两者即可互通；同一网络内的 Docker 容器可以用容器名互访。

```bash
docker network create 黑马
docker network connect 黑马 mysql
```

* 用 `docker load -i <镜像文件>` 加载 Canal 镜像，再用 `docker run` 启动，关键参数如下。

| 参数 | 作用 | 取值 |
| :--- | :--- | :--- |
| `-p` | 端口映射 | Canal 客户端要连上来的端口 |
| `--name` | 容器名称 | `canal` |
| `destination` | Canal 的集群名称 | `黑马` |
| `mysql master 地址` | 主节点地址 | `mysql:3306` |
| 用户名 / 密码 | 做数据同步时的用户名、密码等 | 创建用户时已经备好 |
| 数据库/表过滤 | 监听哪个库 | 只监听 `黑马` 库下所有的表 |
| `network` | 加入哪个 Docker 网络 | `黑马` |

    * 主节点地址写 `mysql:3306` 而不是 IP，是因为 Canal 与 MySQL 在同一 Docker 网络里。

    * 库表过滤支持 `黑马.tb_item`、`黑马.*` 这类语法，用来描述监听哪个库、哪些表。

* 验证：`docker logs -f canal` 看启动成功字样；`docker exec -it canal bash` 进入容器后 `tail -f canal-server/logs/canal.log` 看运行情况。

    * 另有一个以 destination 命名的日志，里面会显示尝试连接 `mysql:3306`、执行 `find start position` 找到 `mysql-bin.0001` 并开始同步，看到这些即安装成功。

## Canal 的 Java 客户端

### 依赖与自动装配

* 官方原生客户端写起来比较麻烦，实际用的是第三方开源的 `canal-spring-boot-starter`（groupId `top.java.two`，版本 `1.2.1-Release`）。

* 引入依赖后即可实现自动装配，只需再配上 Canal 的地址与 `destination`；`destination` 必须与安装 Canal 时的集群名称一致。

```yaml
canal:
  server: 192.168.150.101:11111
  destination: 黑马
```

### EntryHandler 与监听三个方法

* **EntryHandler**

    * > **定义**：Canal 客户端用来接收数据库变更的接口，实现后由增、改、删三个方法分别接住对应变化。

    * 类上加 `@CanalTable("tb_item")` 声明监听哪张表，泛型指定表对应的实体类；变化时把那一行封装成该实体对象传进方法。

    * 类上加 `@Component` 注册成 Bean。

* 监听到新增就把新数据写进 Redis，监听到更新就把更新后的数据放进 Redis，监听到删除就把 Redis 里的删掉。

* > **易错点**：更新顺序别弄反——本地缓存效率更高，先操作本地再操作 Redis；删除同理，先操作本地。

```java
@Component
@CanalTable("tb_item")
public class ItemHandler implements EntryHandler<Item> {

    @Autowired
    private CacheHandler cacheHandler;

    @Override
    public void insert(Item item) {
        CACHE.put(item.getId(), item);
        cacheHandler.saveItem(item);
    }

    @Override
    public void update(Item item) {
        CACHE.put(item.getId(), item);
        cacheHandler.saveItem(item);
    }

    @Override
    public void delete(Item item) {
        CACHE.invalidate(item.getId());
        cacheHandler.deleteItemById(item.getId());
    }
}
```

* JVM 进程缓存的操作更简单：`put( id, item)` 写入，`invalidate(id)` 清除。

* Redis 操作封装成两个方法：写入用 `opsForValue().set` 并先把对象序列化成 JSON，删除用 `delete` 传 id。

```java
public void saveItem(Item item) {
    try {
        stringRedisTemplate.opsForValue()
                .set("item:" + item.getId(), objectMapper.writeValueAsString(item));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}

public void deleteItemById(Long id) {
    stringRedisTemplate.delete("item:" + id);
}
```

    * 客户端封装里的 key 写作 `item:` + id；预热与 Lua 查询侧用的是 `item:id:` + id 与 `stock:id:` + id，两处写法不同，长文未进一步说明。

### 实体类的三个注解

* Canal 底层不依赖 MyBatis，需要靠注解标记实体类与表中字段的映射关系。

    * `@Id`：标记与数据库主键关联的字段。

    * `@Column`：声明字段对应的列名，只在属性名与列名真的对不上时才需要。

    * `@Transient`：标记不属于当前表的字段，将来会被忽略。

* > **提示**：绝大多数字段不用写注解——驼峰属性（`updateTime`）与下划线列名（`update_time`）能自动对应，通常只给 id 标 `@Id` 即可。

* 库存与销量属于库存表而非商品表，放在商品实体里是为了做数据封装，因此加 `@Transient` 标记。

* 验证：服务启动后持续收到消息说明 Java 代码已与 Canal 建立连接；改掉 1001 的价格与尺寸后，浏览器与 Redis 客户端里都能立刻看到新值。

## 多级缓存全貌

### 完整查询链路

* 页面是 `item.html`，放在 Nginx 上；Nginx 既是静态资源服务器又是反向代理服务器，本身不处理业务，只做转发。

* 浏览器渲染时发现缺数据，发 ajax 请求查数据，Nginx 把请求代理给 OpenResty 集群。

* OpenResty 上做了本地缓存（shared dict），请求到达后先查；命中直接返回，未命中再查 Redis；Redis 未命中再查 Tomcat 集群。

* Tomcat 集群内部也做了 JVM 进程缓存，先查进程缓存，命中直接返回，未命中才查数据库。

```text
 浏览器
   │  ① 打开页面 item.html
   ▼
 Nginx（静态资源服务器 + 反向代理，不处理业务）
   │  ② 页面缺数据，ajax 请求 /item/1001
   ▼
 OpenResty 集群   ← 按 id 哈希路由，同一个 id 永远落同一台
   │  ③ 先查本地 shared dict
   │        命中 → 直接返回
   │        未命中 ↓
   │  ④ 查 Redis
   │        命中 → 直接返回
   │        未命中 ↓
   ▼
 Tomcat 集群     ← 同样按 id 哈希路由
   │  ⑤ 先查 JVM 进程缓存
   │        命中 → 直接返回
   │        未命中 ↓
   ▼
 MySQL
```

* 大多数情况走缓存，极少数情况才走数据库。

### 两处按 id 哈希的路由

* 本地共享词典的数据只能在当前 Nginx 进程内使用，多台 OpenResty 之间内存不共享：在 A 台缓存了 1001，下次负载均衡到 B 台就看不到。

* 因此 Nginx 反向代理到 OpenResty 时也要按商品 id 路由，把多个 OpenResty 地址配上去并把算法改成基于请求 url 的哈希，同一个 id 永远访问同一台，url（id）变了才换台。

* OpenResty 向 Tomcat 做负载均衡时同样按商品 id 做哈希路由，只是目标地址换成 Tomcat 的地址。

    * > **结论**：凡是不共享的缓存，想让命中率高就必须保证同一个商品永远访问到它。

### 各层的同步策略

| 缓存层 | 同步策略 | 适合放什么数据 |
| :--- | :--- | :--- |
| Nginx（OpenResty 本地缓存） | 超时同步：过期时间到期自动删除，下次再查就变成新数据了 | 更新频率较低的通用数据，比如商品当中大多数不怎么变的字段 |
| Redis + Tomcat 进程缓存 | Canal 监听 MySQL 变更，通知 Java 客户端立即更新 | 任意类型的数据，尤其是变化频率较高、实时性要求较强的数据 |

* > **易错点**：变化频率较高、对实时性要求较强的数据，不建议放到 OpenResty 里做过期缓存。

* Canal 一旦监听到数据库修改就立即通知 Java 客户端，客户端立即更新 Redis 与本地进程缓存，从而保住一致性。

## Redis 键值设计

### key 的基本格式与三个好处

* 建议格式：以冒号隔开的几段，第一部分是业务名称，第二部分是数据名称，最后是数据的 id；长度不超过 44 个字节，且不要包含特殊字符。

```text
login:user:10
```

    * `login` 是业务名称，`user` 是数据名称代表存的是用户信息，`10` 是 id 代表 10 号用户。

* 好处一，可读性强：了解格式的人看到 key 就知道它是哪个业务、什么数据、哪一条。

* 好处二，避免 key 冲突：不同业务共用同一台 Redis 时数据都存在一起，若都直接用 id 当 key 会互相覆盖；加了业务名与数据名作前缀，同业务不同数据类型即使 id 一样也不冲突。

* 好处三，方便管理：Redis 桌面客户端会以冒号做层级，前缀相同的 key 出现在同一目录下，便于批量查看与批量删除。

```text
Redis 桌面客户端里看到的层级
└── login
    ├── login:user:10
    ├── login:user:11
    └── login:user:12
```

### 为什么卡在 44 个字节

* 原因一，省内存：一个 key 省十几个字节，1 亿个 key 省下的内存相当可观；在满足可读性与避免冲突的前提下能短就短，`user` 可以简写成 `u` 或 `uid`。

* 原因二，字符编码：key 底层都是 string，而 string 的底层编码分 `int`、`embstr`、`raw` 三种，用 `object encoding` 命令可以查看某个 key 的底层编码。

    * `int`：字符串内容全是数值时采用，直接当数字存储，占用空间小很多。

    * `embstr`：非数值时采用，存储为一段连续空间，编码更紧凑、占用内存更小，前提是字符串长度小于 44 字节。

    * `raw`：超过 44 字节后转为此模式，内存空间不连续、用指针指向另一段空间存放 SDS 内容，访问性能受影响并可能产生内存碎片，占用比 `embstr` 高。

```bash
set number 123
type number
object encoding number

set name jack
object encoding name
```

* > **结论**：把字符串长度控制在 44 个字节以内，它自然就使用 `embstr` 编码，从而提高内存使用率、减少内存碎片。

* > **易错点**：44 字节是 Redis 6 点几版本的 `embstr` 上限；Redis 3 点几版本（低于 4）的这个上限是 39 字节。

* 实践验证：`set name jack` 的编码是 `embstr`；把 name 加长到正好 44 字节仍是 `embstr`；再加一个字节凑到 45 字节就变成 `raw`。
