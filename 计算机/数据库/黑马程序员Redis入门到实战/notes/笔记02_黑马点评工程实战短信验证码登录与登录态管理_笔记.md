# 黑马点评工程实战：短信验证码登录与登录态管理

## 黑马点评项目定位与 Redis 落地路径

### 项目是什么

* **黑马点评**
    * > **定义**：一个类大众点评的、以社交平台为核心的轻电商项目，用来把 Redis 的企业应用姿势整体走一遍。
    * 选它的理由：社交类项目里 Redis 的应用场景非常丰富，同时里面还塞进了电商业务场景，社交加电商的组合能把 Redis 的各种数据结构、各种应用姿势覆盖到。
    * 学习取向：整套内容不只讲原理，更重要的是把核心代码都实现出来，以实际项目代码的形式讲解功能。

### 五个业务板块对应的 Redis 技术

* **短信登录**：核心包含两件事——短信验证码的保存、登录信息的保存。
* **商户查询缓存**：站点有各类商户信息，对其查询建立缓存可大大提高效率；重点不是缓存是什么，而是企业缓存使用的各种技巧，以及缓存雪崩、穿透、击穿等问题与解决方案。
* **达人探店**：以博客形式发布图文内容，他人可点赞评论，由此产生点赞列表与点赞排行榜，这两部分恰好用 List 与 Sorted Set；重点在两种结构实现排行榜的差异以及各自的应用场景。
* **优惠券秒杀**：点评不卖商品而是卖券（如 4.5 折、5 折），特价券要做秒杀；会用到 Redis 计数器、Lua 脚本、分布式锁、阻塞队列。
* **好友关注**：互相关注、取关、共同关注等用到 Set；地理坐标相关的搜索用到 GEO 结构，GEO 放在实战阶段讲是因为它贴合实际、理解起来更容易。
* **用户签到与在线统计**：用到 BitMap 与 HyperLogLog；原因是亿级用户下把每一天的信息都记录下来数据量非常恐怖，这两种特殊结构能实现基本统计且占用内存非常小。

### 部署形态与水平扩展

* 不采用微服务：核心目标是学 Redis 的用法，不想把 Java 代码搞得太复杂而影响注意力与学习效果。
* 单体但前后端分离：前端与后端分别部署而非揉在一起往一处扔，这是现在企业开发的标准做法；后端部署在 Tomcat 上，开发阶段用开发工具打开就行，前端部署在 Nginx 上。
* 水平扩展能力：单台 Tomcat 扛不住时可以再多部署几台，形成负载均衡的集群。
* 集群带来的代价：一旦步入集群，就存在集群间的数据共享问题，比如"用户的登录信息存在哪一台"。

## 短信登录的三段主干流程

### 发送验证码的顺序是死的

* 用户提交手机号后不要急着发，第一步是校验手机号是否合法，校验失败就让他重来。
* 校验通过第二步才生成验证码。
* 第三步必须先把验证码保存到本地，因为将来要拿它做登录校验。
* 第四步才真正把验证码发出去。
* > **结论**：整条顺序是校验手机号 → 生成验证码 → 保存验证码 → 发送验证码，最容易搞错的是"保存"与"发送"这两步的先后，必须**先保存再发送**；反过来的话用户在保存之前就提交了验证码，服务端手里是空的。

### 校验验证码顺带完成注册

* 用户把手机号与收到的验证码一起提交到后台。
* 先比验证码：把提交的验证码与上一步保存的验证码做比较，不一样就拒绝让他重来，一样才能往下走。
* 验证码一致还不能证明可以登录，因为手机号尚未验证，还要根据手机号查询用户信息。
* 查得到用户：证明手机号是正确的，直接登录。
* 查不到用户：证明这是第一次访问，给他注册成一个新用户，把手机号等基本信息写入数据库，等于一种快捷注册。
* 登录与注册合在同一个流程里完成；流程的最后一定要保存用户信息，供后续业务使用。

### 登录状态校验与 ThreadLocal

* 校验基于 Cookie：登录凭证保存在浏览器的 Cookie 中，用户访问时一定会携带自己的 session id。
* 判定(session)：session 里没有用户就拦截请求不许访问，有用户就说明曾经登录过，放行。
* 校验不能白做：后续业务一定会用到当前登录用户的信息，所以要把它缓存起来方便后续使用，缓存的位置一般是 ThreadLocal。
* **ThreadLocal**
    * > **定义**：线程域对象，它把数据保存在每一个线程的内部，在线程内部创建一个 Map 来保存。
    * 为什么需要它：每一个请求到达服务端都是独立的线程，如果直接把用户存进本地变量，会出现多线程并发修改的安全问题。
    * 效果：每个线程都有自己独立的存储空间，每个请求来了都有自己的空间，相互之间没有干扰，后续所有业务都能从中取出自己的用户信息。

```text
          浏览器
            │  发起请求，自动携带 Cookie 中的 session id
            ▼
      服务端校验登录状态
            │
     ┌──────┴───────┐
     ▼              ▼
  查不到用户      查得到用户
     │              │
     ▼              ├──► 放行
  直接拦截请求        │
  （不许访问）        └──► 把用户信息缓存进 ThreadLocal
                          │
                  每个线程内部一个独立 Map
                  线程之间互不干扰
                          │
                          ▼
              后续业务直接从 ThreadLocal
              取出当前登录用户的信息
```

## 发送验证码接口的实现

### 接口约定

* 请求方式 `POST`，路径 `/user/code`，请求参数是 `phone`（手机号），没有返回值。
* 路径里的 `api` 是用来标识当前请求发往 Tomcat 服务的前缀，会被自动过滤掉，真正的请求路径是后面的部分。
* Controller 只做转发，业务逻辑下沉到 service 的 `sendCode` 方法里。

### 五个步骤

* 校验手机号：调用 `RegexUtils.isPhoneInvalid(phone)` 判断是否无效，成立就返回 `Result.error("手机号格式错误")`。
* 生成验证码：用 Hutool 的 `RandomUtil.randomNumbers(6)` 生成长度为六位的随机数字。
* 保存验证码：目的是为了将来登录时可以据此校验，所以要先保存再发送。
* 发送验证码：真实发送要调用第三方短信平台，实现较复杂且不是重点，此处用 `log.debug("发送短信验证码成功：{}", code)` 记录日志来模拟。
* 返回结果：没有具体返回值，直接调用 `Result.ok()` 表示成功。

### 工具与统一结果对象

* `RegexPatterns` 里定义了手机号、邮箱等各种正则；`RegexUtils` 是针对手机号的校验工具。
* **Result**
    * > **定义**：自定义的业务结果对象，含 `success`（是否成功）、`errorMsg`（异常时返回）、`object`（成功时返回）。
    * 它有一个静态方法 `ok()` 代表成功；失败就直接 `return Result.error(...)` 返回错误信息。
* > **易错点**：发送短信这一步是模拟的、不是真发；真实开发中替换成调用短信服务即可，一般公司里都会有独立的服务专门负责发送验证码。

## 登录与注册合二为一

### 登录接口的形态

* 请求方式 `POST`，路径 `/user/login`，参数不再是 URL 上拼接的形式，而是 JSON 风格的请求体，字段是 `code` 与 `phone`。
* **@RequestBody**
    * > **定义**：Spring MVC 中用来接收 JSON 风格请求体、并把它反序列化成对象的注解。
    * 没有它后端拿到的是一个空的请求体；加上之后 Spring 会自动把 JSON 转成 `UserLoginForm` 对象。
* **UserLoginForm**：含 `phone`、`code`、`password` 三个字段；`password` 的存在是因为登录框同时支持"验证码登录"与"密码登录"两种模式，本次只用手机号登录模式，所以不用管它。
* 参数有两类来源：取验证码用的是 session，取 `phone` 和 `code` 则是从 `loginForm` 里拿的请求参数。

### 校验手机号与验证码

* > **易错点**：手机号为什么要再校验一遍？发送短信与登录是两个不同的请求，每个请求都要做独立的校验；发短信时填了正确的手机号、登录时填错是完全可能的。
* 从 session 取缓存验证码：`(String) request.getSession().getAttribute(CACHE_CODE)`。
* > **易错点**：不要像第一遍那样把 `"code"` 这种字面量直接写进 `getAttribute`，散落在代码里的字符串常量叫**魔法值**；正确做法是定义成常量放到专门的地方，例如 `CACHE_CODE` 代表缓存起来的 code。
* 先判 `cacheCode == null`：等于 null 说明这个手机号从来没有发过验证码、或者验证码已经过期，两种情况都是错，直接返回错误信息。
* 不为 null 再用 `cacheCode.toString().equals(code)` 比对，不一致就返回错误。
* 反向写法的意义：先写错误分支直接 `return`，剩下的才是正常流程；如果全部用正向校验，外层判不为 null、里面再判一致、一致里面再判下一步，if 越套越深会形成"菱形"代码，反向写可以避免嵌套、更优雅。

### 用 MyBatis-Plus 查用户

* 依据：用户表的 `phone` 字段加了 `unique` 索引，手机号是唯一的，按手机号查要么没有、要么只能查到一个。
* 手写的话等价于 `SELECT * FROM tb_user WHERE phone = ?`，用 MyBatis-Plus 则不需要自己写这条 SQL。
* 链式写法：`lambdaQuery().eq(User::getPhone, phone).one()`。
    * `lambdaQuery()` 等价于 `SELECT * FROM tb_user`，它之所以知道表名，是因为实体类上有 `@TableName` 注解。
    * `.eq(...)` 是等值条件——字段等于哪个值；后面还有一大批对应各种 SQL 关键字的条件方法。
    * 返回值按查几条决定：查多个返回集合，查一个用 `one`，直接得到 `user`。
* 这些方法之所以能直接用，是因为 service 继承的 `IService` 由 MyBatis-Plus 提供，并且已经告诉了它实体类与 Mapper 分别是什么。

### 创建新用户

* 触发条件：查到的 `user == null` 时调用 `createUserWithPhone(phone)` 创建。
* > **结论**：真正要填的只有 `phone` 和一个随机昵称；验证码不是用户的属性，密码可以置空让他以后自己配，头像给默认头像，时间不用管。
* 昵称生成：`SystemConstants.USER_NAME_PREFIX + RandomUtil.randomString(10)`，加统一前缀是为了让随机用户名看起来不那么混乱，前缀常量直接取自系统常量类。
* 入库使用 MyBatis-Plus 提供的保存能力，把 `user` 交给它即可。
* 方法必须把创建好的用户 `return` 回来：不确定走的是查到还是新建的分支，但两条分支结束后都必须要有一个有值的 `user`。
* > **提示**：这一步不需要返回登录凭证，因为访问 Tomcat 时 id 已自动写进 cookie，之后请求会带着它过来；这句话在登录态搬到 Redis 之后就不成立了。

## 登录校验：拦截器与线程隔离

### 为什么是拦截器

* 背景：项目中 Controller 非常多，很多业务都需要校验登录，不可能在每个 Controller 里各写一遍校验逻辑。
* **拦截器**：Spring MVC 中可以在所有 Controller 执行之前执行的东西；用户请求不再能直接访问 Controller，全部先过拦截器，由它判断该不该放行。
* **HandlerInterceptor** 的三个方法：`preHandle`（Controller 执行之前）、`postHandle`（Controller 执行之后）、`afterCompletion`（视图渲染之后、返回给用户之前）。
* 只需实现两个：进 Controller 之前做登录校验，业务执行完毕后再销毁用户信息以避免内存泄漏。

### UserHolder 与 ThreadLocal 的配合

* 拦截器里拿到用户信息后保存到 ThreadLocal，Controller 再从 ThreadLocal 里取出，完成跨层传递。
* 传递过程要注意线程安全：每个进入 Tomcat 的请求都是独立的线程，Tomcat 会在线程内开辟内存空间保存用户，不同请求访问不同 Controller 也各有独立线程，互不干扰。
* **UserHolder**：utils 里已准备好的类，内部定义了静态 ThreadLocal 常量、泛型是 `User`，提供 `saveUser`、`getUser`、`removeUser` 三个静态方法。
* 保存时需要强转一下，因为 ThreadLocal 那边声明的类型是 `Object`。
* > **提示**：保存不需要 key 之类的东西，因为它保存在当前线程里面。

### LoginInterceptor 的判定逻辑

* 先获取 session，再从 session 里取出登录时存进去的用户（key 就叫 `USER`）并强转成 `User`。
* 用户为 null → 给出失败标识后 `return false` 拦截；用户存在 → `UserHolder.saveUser(user)` 后 `return true` 放行。
* `return false` 表示拦截，`return true` 表示放行。
* 拦截时最好给个不同的标识：可以直接抛异常让上层知道原因，也可以温柔一点返回状态码。
* **401**：Unauthorized（未授权），用来告诉调用方这次请求是被登录校验拦下来的。
* 在 `afterCompletion` 中调用 `UserHolder.removeUser()` 移除用户，避免内存泄漏。

### 注册拦截器与放行路径

* **MvcConfig**：实现 `WebMvcConfigurer` 代表这是一个 MVC 相关配置，加 `@Configuration` 注解，实现 `addInterceptors` 方法，用 `registry.addInterceptor(...)` 添加拦截器。
* 不能默认拦截一切：很多路径不需要拦截，盲目拦截一切会带来不必要的问题，通过 `excludePathPatterns` 排除不需要拦截的路径，它是可变参数可以填多个值。
* 必须排除 `/user/code` 与 `/user/login`：发送验证码与登录注册本身就不应该被拦截。
* 需要拦截的是取当前登录用户、登出、用户详情这类与登录态有关的接口。

| Controller | 路径特征 | 为什么放行 |
| :--- | :--- | :--- |
| 查热点博客 | `/blog/hot` | 跟登录用户无关 |
| 店铺 | `/shop/**` | 店铺基本没什么需要拦的，登录不登录都能查 |
| 店铺类型 | `/shop/type/**` | 店铺类型跟登录没关系，不登录就不让看不合理 |
| 上传 | `/upload` | 一般要登录才能做，测试时也可以先放行 |
| 优惠券 | `/voucher` | 不登录也不可能不让查优惠券 |

* > **结论**：这里直接用 `/**` 放行了所有以 `/shop` 开头的请求；实际开发中要根据需求逐个决定哪些进拦截、哪些进放行。

### 获取当前登录用户

* `/user/me` 的作用就是查询当前登录用户的信息，它能返回用户就说明登录校验成功。
* 该请求会带上 cookie，其中 `JSESSIONID` 就是登录凭证。
* 实现只有一行：`Result.success(UserHolder.getUser())` —— 拦截器已经把用户放进了 UserHolder，Controller 直接取即可。

## 存储粒度与脱敏

### UserDTO 与属性拷贝

* 问题现象：`/user/me` 把创建时间、头像、id、昵称、密码、手机号、更新时间全部返回了；但查询当前登录用户只要返回 id、昵称、头像就够了，时间、密码、电话这些敏感信息没有必要返回，存在泄露风险。
* 根因链条：`me` 把 UserHolder 里取到的东西二话不说整个返回 → 拦截器二话不说把整个对象存了进去 → 源头是登录时从数据库查出后就整个存进了 Tomcat 的内存空间。
* > **定义**：这是一个**存储粒度**的问题——存得越完整将来使用越方便，但会带来内存压力过大，还可能把敏感信息返回到前端。
* **UserDTO**：只含 `id`、`nickName`、`icon` 三个字段的 DTO；实现登录功能时先把 `user` 转成它再存。
* 转换用 Hutool 的 `BeanUtil.copyProperties(user, UserDTO.class)`：传入数据源对象与目标类型，它会自动把 user 的所有属性拷进 UserDTO 并创建出对象返回，返回值就是那个 DTO。
* > **易错点**：改成存 DTO 之后，拦截器里取出来的自然也是 DTO 类型，此时 `UserHolder` 会因为它里面要的是 `User` 而报错；必须把泛型改成 `UserDTO`，`getUser()` 的返回值随之变化，所有用到它的地方都要手动改一遍。
* > **结论**：降低存储粒度既能避免返回敏感信息，又能减少对内存的占用。

## Session 不共享问题

### 现象与成因

* > **定义**：多台 Tomcat 无法共享私人存储空间的问题——请求被切换到不同的 Tomcat 上时，在其他 Tomcat 里是看不到数据的。
* 触发场景：系统虽然是单体架构，但为了应对并发一定要具备水平扩展能力；一旦形成负载均衡集群，请求进入 Nginx 后会在多台 Tomcat 之间做轮询。
* 具体表现：第一次请求（发验证码或登录）被均衡到 Tomcat 1，验证码与用户信息都存在它的 session 空间里；第二次请求（登录或校验）被均衡到 Tomcat 2，它去自己的 session 里找就是空的。
* 用户感知：明明输对了却被告知"验证码错误"，或者前一秒刚登录完却被告知"没有登录"，体验非常差。

```text
                Nginx / Ingress（负载均衡，轮询）
                              |
            +-----------------+-----------------+
            |                                   |
            v                                   v
    +---------------+                   +---------------+
    |   Tomcat 1    |                   |   Tomcat 2    |
    |---------------|                   |---------------|
    | session 空间  |                   | session 空间  |
    |  code=123321  |                   |   （空的）    |
    |  user=...     |                   |               |
    +---------------+                   +---------------+

第一次请求（发验证码）  -> 被负载均衡到 Tomcat 1
第二次请求（登录/校验）-> 被负载均衡到 Tomcat 2
Tomcat 2 去自己的 session 里找 code -> 找不到
-> "验证码错误" / "没登录"
```

### Tomcat 之间互拷为什么不行

* 早期做法：多台 Tomcat 之间做一些配置，让它们互相实现数据拷贝，看上去问题就解决了。
* 否定的第一个理由：好多台 Tomcat 保存相同的数据、互相拷贝，是内存空间的浪费。
* 否定的第二个理由：拷贝需要时间，在这个延迟之内有人来访问，依然会出现数据不一致。
* > **结论**：这套方案退出之后没有得到广泛的使用和认可，因此被 PASS 掉。

### 替代 Session 需要满足的条件

| 要求 | 为什么必须有 |
| :--- | :--- |
| 数据共享 | 正是因为不共享才导致了问题；共享后多个 Tomcat 能看到相同的数据，也就不会出现数据丢失 |
| 内存存储 | 读写效率高。登录校验这类操作访问频率非常高，读写性能差就难以满足高并发需求 |
| key-value 结构 | 存验证码时 key 是 code、value 是验证码值；存用户时 key 是 user、value 是用户。替代方案也应该是这个样子 |

* Redis 为什么正中下怀：它首先是在 Tomcat 以外的存储方案，任何一台 Tomcat 都能访问到，不会出现数据丢失；它是内存存储，读写延时基本上在微秒级别；它本身就是 key-value 类型。
* > **结论**：code 与 user 都可以以 key-value 的形式存进 Redis 来替代 session；但简单地往 Redis 里存还不够，业务流程上还有细节要处理。

## Redis 数据结构选型

### 验证码：String

* 选择依据：验证码就是一个普通的、六位长度的数字，没有什么特殊结构，用最简单的 String 结构就 OK。

### 用户对象：String 与 Hash

| | String（JSON 字符串） | Hash（field-value） |
| :--- | :--- | :--- |
| 存法 | 把 Java 对象序列化成 JSON 字符串整体保存 | value 是一个哈希，可以理解成 map，把对象里每一个字段作为 field 和 value 拆开保存 |
| 加字段 | 不行，把整条干掉重新插入一条 | 没问题，直接加一个 field |
| 改单个字段 | 不行，只能把这条干掉重来 | 没问题，只针对这个 field 操作 |
| 内存占用 | 多。包含大括号、冒号、引号等，数据越长符号越多 | 少。只需要保存数据本身 |
| 直观性 | 好 | 一般 |

* 本质差别：String 这种 JSON 串看起来直观，但把整个数据变成一个串，字段与字段之间耦合在一个整体里；Hash 每个字段彼此独立，可以针对单个字段做增删改查。
* > **结论**：如果对内存不是很在意、数据量也不大，用 String 相对直观方便也是 OK 的；从优化角度考虑**推荐使用 Hash**，本案例选择 Hash 结构保存用户信息。

## Redis 的 Key 设计

### 两个基本要求

* 要求一 唯一性：Redis 是大家都在往里存的共享内存空间，如果不同手机号都拿 `code` 当 key，就会互相覆盖，验证码丢失导致很多人对不上。
* 要求二 可携带：session 那套方案里不用考虑"怎么取"——浏览器一来就创建 session、自动把 session id 写进 cookie、以后每次带着它来取；换成 Redis 之后没有人帮你维护 session id，必须让客户端能拿着某个信息把值取回来。
* > **结论**：key 一方面要考虑唯一性，另一方面要考虑将来客户端能够携带这个 key 来获取数据。

### 验证码 key：手机号加业务前缀

* 不能用随机 code 当 Redis 的 key：每个请求在 Tomcat 内部有独立线程，用 `code` 互不干扰；但 Redis 是共享空间，不同手机号都用 `code` 就会覆盖。
* 改用手机号：每个手机号都有自己的唯一 key 不会冲突，而且用户登录时正好提交手机号，可以拿着它原样拼出同一个 key 把验证码取回来比对；保存时用的不是手机号就取不出来。
* 必须加业务前缀：Redis 是大家共用的空间，别的业务也可能用手机号当 key，加前缀让 key 有层次感才能区分开，形式为 `login:code:` + 手机号。

```text
login:code:13800000000
└──┬──┘ └──────┬─────┘
  业务前缀     手机号
```

### 用户 key：随机 token

* 手机号也可以，但一般不太推荐。
* **token**：随机字符串，一般用 UUID 生成；以它为 key 保存用户信息，同时它本身就是新的登录凭证。
* 为什么不能再用手机号：token 要返回给前端保存在浏览器里，用手机号会有泄露风险。
* 凭证机制的改变：session 方案下 Tomcat 会自动把 session id 写进浏览器 cookie 并带回来；改成 token 之后 Tomcat 不会自动写，只能手动把 token 通过响应体返回给客户端。
* 前端侧的配合：登录请求成功后把 token 存进浏览器的 `sessionStorage`；公共脚本里有一个 axios 的拦截器，每次发请求时都会从 `sessionStorage` 取出 token，放进名为 `Authorization` 的请求头，于是所有 axios 请求都携带它。
* 服务端针对性地从这个请求头取值，就能拿到 token、进而完成登录验证。

## 写入 Redis 的实现细节

### 验证码的写入

* 注入 Spring Data 提供的 `StringRedisTemplate`，把原来写 session 的那行删掉换成写 Redis。
* 写法：`opsForValue().set(LOGIN_CODE_KEY + phone, code, LOGIN_CODE_TTL, TimeUnit.MINUTES)`。
* > **结论**：存的每一个 key 都必须设有效期。不设的话，只要有登录注册发生 Redis 里就多一条数据，有人一直点就存了无数条且永远不删除，终有一天 Redis 会被占满。
* 取值的变化：从 Redis 取出来的直接就是 `String`（因为 `StringRedisTemplate` 的 key、value 全都是字符串），不再是 `Object`，校验时直接 `equals`，不需要 `toString()`。

### TTL 的两种传法

| 写法 | 传什么 | 直观含义 |
| :--- | :--- | :--- |
| `set(key, value, timeout, unit)` | 数值 + `TimeUnit` | 传 `2` 配 `TimeUnit.MINUTES` 就是两分钟 |
| `set(key, value, duration)` | 一个 `Duration` 对象 | `Duration.ofMinutes(2)`，单位直接写在对象里 |

* 第一种有点类似于 `SET key value EX 120`，`EX` 就是有效期、单位是秒，120 秒就是两分钟。
* 验证码这里设两分钟（五分钟也行），对应短信里常见的"该验证码两分钟内有效"。

### 常量抽取

* `"login:code:"` 与 `2L` 这种字面量最好都定义成常量：万一将来取的时候 key 写错了就查不到数据。
* 常量清单：`LOGIN_CODE_KEY = "login:code:"`、`LOGIN_CODE_TTL = 2L`（分钟）、`LOGIN_USER_KEY = "login:user:"`、`LOGIN_USER_TTL = 30L`（分钟）。
* token 的 key 也一样要加前缀，表明这是登录业务里存的用户信息，叫 `login:user:` 或 `login:token:` 都行，只要能表明含义。

### token 生成与哈希写入

* token 生成：`UUID.fastUUID().toString(true)`，用的是 Hutool 的 UUID 而不是 JDK 自带的那个；`true` 是 `isSimple` 的意思，表示不带中划线，不带参数默认就是带中划线的那种。
* 必须用 `putAll` 而不是 `put`：`put` 接受一个 key、一个哈希 key、一个 value，一次只能存一个字段；对象有多个字段就得调多次、跟服务器做多次交互。`putAll` 后面跟一个 Map，一次就把全部字段写进去。
* 对象转 Map：先 `BeanUtil.copyBean(user, UserDTO.class)` 得到 DTO，再 `BeanUtil.beanToMap(userDTO)` 得到 Map，把这个 Map 交给 `putAll` 即可。

### Hash 写入不能带 TTL

* > **易错点**：`putAll` 只有 key 和 map 两个参数、没有 TTL 的位置，`opsForHash()` 存数据时不允许设置有效期；只能先存，存完再单独补一次 `expire`。
* 补刀写法：`stringRedisTemplate.expire(tokenKey, LOGIN_USER_TTL, TimeUnit.MINUTES)`；这个 key 与写入时用的是同一个，抽成一个变量就不用写两次。
* 用户信息也要设有效期：登录用户越来越多、数据比验证码还大，不清理 Redis 也会被放满。
* TTL 定为 30 分钟：如果 30 分钟不做任何操作，登录状态其实就已经失去意义了。

## StringRedisTemplate 的类型约束

### 报错与根因

* 现象：改完重启后提交登录，服务端报异常；日志是类型转换异常——long 不能转化为 string，定位在把 userMap 往 Redis 写的那一步。
* 排查：Map 里只有 `id` 是 Long 类型，也就是 Long 类型的 id 无法存入 Redis。
* > **结论**：这是 Redis serializer 的报错。`StringRedisTemplate` 的特点是要求 key 和 value 都必须是 String 结构，所以存进去的 Map 里每一个值都得是 String。
* > **提示**：碰到错误不要着急，而是去仔细分析可能产生问题的原因在哪里。

### 两种修法

* 修法一（笨办法）：不用工具类，自己 new 一个 Map，把字段名作为 key、把字段值转成字符串作为 value 逐项塞进去。
* 修法二（推荐）：用 `CopyOptions` 做自定义拷贝。
* **CopyOptions**
    * > **定义**：数据拷贝时的选项对象，允许对拷贝出来的 key 和 value 做自定义。
    * 用法：`BeanUtil.beanToMap(userDTO, new HashMap<>(), CopyOptions.create()...)` —— 先传对象，再传一个空的 HashMap，最后传拷贝选项。
    * `setIgnoreNullValue(true)`：忽略空的值。
    * `setFieldValueEditor`：字段值修改器，接收一个 `Function`，两个参数分别是 `fieldName` 与 `fieldValue`，返回值是修改后的字段值；写成 `fieldValue.toString()` 就把所有字段值都转成了字符串。

## 登录态续期

### 固定 30 分钟过期的问题

* 期望的语义：不是到 30 分钟就结束，而是只要用户不停地访问，有效期就一直是 30 分钟；只有超过 30 分钟不访问，才把登录状态剔除。
* 实际实现：从登录那一刻开始算，不管用户有没有在访问，30 分钟后一定会被 Redis 剔除。
* 结论：只要用户在不断地访问，就要不断地去更新 Redis 中 token 的有效期。

### 续期思路放在拦截器里

* 所有请求进来都要经过登录拦截器的拦截与校验，通过校验就证明两件事：他是个登录用户，并且他在活跃地访问。
* 于是可以在原有校验逻辑上追加一步：更新 token 的有效期。这样持续访问时 token 永不过期，只有完全不触发拦截器的情况下，超过 30 分钟这个 key 才会被移除。
* 判断用户是否在访问这个问题的答案就在拦截器里——能否感知到这次请求。

### 改造后的单个拦截器

* 步骤依次为：取 `authorization` 请求头 → `StrUtil.isBlank(token)` 判空、为空则设置 401 并拦截 → 拼出 tokenKey → `opsForHash().entries(tokenKey)` 取回整个 Map → `userMap.isEmpty()` 则设置 401 并拦截 → `BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false)` 转回 DTO → 存入 ThreadLocal → `expire` 刷新有效期 → 放行。
* `entries` 与 `get` 的区别：`get` 只能取出某个 key 里的一个字段，而 `entries` 接受一个 key 并返回 Map，把整个哈希结构的多个字段一次性反馈回来。
* 不必判 null：`entries` 方法内部会做判断，如果为 null 会返回空 Map，所以直接判断 `isEmpty` 就行。
* `fillBeanWithMap` 的三个参数：用哪个 map、用哪个 bean（这里 new 一个 `UserDTO`）、是否忽略转换过程中的错误（给 false，有异常就抛出来）。

### 拦截器里为什么不能用 @Resource

* 原因：这个类的对象是我们自己手动 new 出来的，不是通过 `@Component` 这类注解由 Spring 创建的；由 Spring 创建的对象才会被依赖注入，手动创建的没有人为你注入，因此 `@Autowired`、`@Resource` 都不可用。
* 解法：利用构造函数注入，由使用它的地方把 `StringRedisTemplate` 传进来。
* 注入链条：配置类带 `@Configuration`，所以它本身由 Spring 构建，可以在里面用 `@Resource` 拿到 `StringRedisTemplate`，再在手动 new 拦截器时把它放进构造函数。
* 后续形态：两个拦截器也可以注册为 Spring 组件，在配置类里用 `@Resource` 直接取用。

### 单拦截器方案为什么不够

* 病根：这个拦截器拦的是需要做登录校验的路径，不是一切路径。
* 具体表现：用户一直访问首页、商户详情页这类不需要登录也能看的页面时，拦截器不生效、也不刷新有效期。
* 后果：30 分钟之后，尽管用户一直在访问，登录状态依然消失，这是一个不太合理的点。

### 双拦截器方案

```text
                  一次请求进来
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│ RefreshTokenInterceptor                                 │
│   addPathPatterns("/**")  拦截一切路径，order 小 → 先执行 │
│                                                         │
│   ① 取请求头 authorization                              │
│   ② token 为空？→ 不拦截，直接 return true              │
│   ③ opsForHash().entries(tokenKey) 取用户               │
│   ④ 为空？→ 不拦截，直接 return true                    │
│   ⑤ Map → UserDTO → UserHolder.save()                  │
│   ⑥ expire(tokenKey, 30, MINUTES)  刷新有效期           │
│   ⑦ return true（这个拦截器永远不拦人）                  │
└─────────────────────────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│ LoginInterceptor                                        │
│   addPathPatterns("/user/**")  只拦需登录的路径          │
│   order 大 → 后执行                                     │
│                                                         │
│   ① UserHolder.getUser() == null？                      │
│   ② 是 → response.setStatus(401) + return false         │
│   ③ 否 → return true                                    │
└─────────────────────────────────────────────────────────┘
                        │
                        ▼
                Controller 业务方法
```

* **RefreshTokenInterceptor**：由原拦截器复制改名而来，拦截一切路径，负责取 token、查用户、存 ThreadLocal、刷新有效期；它**永不拦截**——token 为空或 Redis 里查不到用户时都直接 `return true` 放行。
* **LoginInterceptor**（瘦身后）：不再需要 `StringRedisTemplate`，唯一要做的是判断 `UserHolder.getUser()` 是否为 null，为 null 就设置 401 并 `return false`，否则 `return true`。
* 职责划分：第一个的核心工作是得到用户、保存起来并刷新，第二个的核心动作才是做登录拦截。
* 顺序要求：必须让刷新的先执行，它把用户放进 ThreadLocal 之后，第二个拦截器才能据此判断。
* **order**：注册拦截器时会被注册成一个 `InterceptorRegistration`，其中的 `order` 就是执行顺序；值越小优先级越高，值越大执行优先级反而越低。
* 默认行为：所有拦截器的 order 默认都是 0，都是 0 的情况下按添加顺序执行，所以只要把要后执行的先添加也行。
* 推荐配置：给刷新的 order 调小（1）、给 LoginInterceptor 的 order 调大（2），确保刷新的先执行、登录的后执行。
* `addPathPatterns("/**")` 不写也可以，默认就是 `/**`。

### 验证结果

* Redis 客户端里看到用户信息已保存，有效期是 1800 秒（30 分钟）。
* 访问需要登录的接口后，TTL 被重置成 1780。
* 只刷新首页（这个请求只访问店铺类型、没有经过登录拦截）之后，TTL 同样被重置。
* > **结论**：不管访问的是需要登录还是不需要登录的页面，只要访问了都能触发 token 有效期的更新，每刷新一次 TTL 都被重置。

## Redis 存储规范

### 落地时的五个维度

| 维度 | 要求 | 原因 |
| :--- | :--- | :--- |
| 数据类型 | 简单数据如验证码用 String；复杂对象用 Hash | Hash 存储空间占用更小，还能对单个字段做修改，更灵活 |
| key 唯一性 | 必须能保证不撞车 | 手机号天然唯一；用户信息用随机 UUID |
| key 含义 | 要方便下一次能更快更方便地找到它 | 加上 `login:code:` / `login:user:` 这样的业务前缀 |
| 有效期 | 一定要设 | 避免数据在 Redis 里存储过长时间，占用过多内存 |
| 存储粒度 | 不必存完整用户信息 | 去掉敏感数据，只保存页面真正需要的不太敏感的数据，还能节省内存空间 |

* 三条必须跟着改的事：单纯把数据存入 Redis 还不够，**key 的设计、数据结构的选择、以及登录凭证怎么从服务端交到客户端手上**，这三件事都要一起改。
* 最容易忽略的一条是存储粒度：真正存进 Redis 的并不是完整的用户信息，而是把其中的敏感数据去掉后、只保留页面需要的那一部分。
