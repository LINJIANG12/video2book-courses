## 秒杀优化：把下单拆成前台和后厨
> 对应块：BLK20 | 覆盖分集：P69-P70 | 块标题（分集名）：《实战篇-22.秒杀优化-异步秒杀思路》

前面几个小节，我们已经把优惠券的秒杀下单功能做出来了。秒杀这条路走到这里，接下来该干什么？继续优化秒杀业务，进一步提高它的性能。

不过时间一长，我估计不少人对秒杀的业务流程已经开始模糊了。所以先别急着往下走——我们把这条流程重新捋一遍。因为接下来所有的优化，毛病都要从这条流程里找。

### 先回顾一遍秒杀下单

秒杀接口接收一个 `voucherId`，也就是当前这个用户正在抢购的优惠券的 id。业务核心就两件事：扣减这个优惠券的库存，以及把用户抢购的优惠券信息写入订单，完成订单的创建。

只不过因为是秒杀业务，所以要多加一些业务限制：

> **易错点**：一是库存绝对不能出现超卖，必须判断库存是否充足；二是一个用户对一张优惠券只能下一单，也就是一人一单。

也正因为这两条限制，整个业务一下子变得复杂起来了。

要想判断优惠券的库存，你得先查询优惠券吧，这一步肯定是访问数据库的。查到优惠券以后，判断一下秒杀的时间，判断一下库存是否充足；如果不足，直接报错，避免超卖。如果充足，我们再去尝试下单。

接下来就是对一人一单的判断。一人一单怎么判断呢？其实就是看一看数据库里有没有这个订单。但是可能存在并发安全问题，所以我们利用了分布式锁：先尝试去获取锁，获取成功再去做判断；判断的时候就是拿用户 id 和券的 id 去查订单，查完以后看一看存不存在，如果已经存在了就证明他买过了，那肯定拒绝他；如果没买过，那才可以继续在这个时候放心大胆地去扣减库存、创建订单。最后业务结束，释放锁，整个流程也就完成了。

```text
前端 ──> Nginx ──> Tomcat
                            │
                            ▼
                    ┌───────────────────────────────┐
                    │ Tomcat 内的秒杀业务流程        │
                    │ ① 查询优惠券 → 判断库存  [读] │
                    │ ② 分布式锁，加锁             │
                    │ ③ 查询订单 → 一人一单    [读] │
                    │ ④ 扣减库存               [写] │
                    │ ⑤ 创建订单               [写] │
                    │ ⑥ 释放锁                     │
                    └───────────────────────────────┘
```

读图：一条请求走完 Nginx 进入 Tomcat，四步数据库操作全都在锁里串着跑完。

回头看，虽然整体业务非常复杂，核心其实就两点：

> **定义**：一是购买资格的判断——这个人能不能买，依据是库存够不够、这个人买没买过；二是真正下单——扣库存和创建订单。

而性能的问题恰恰出在这里，因为这两部分里全都有大量的数据库操作。

### 跑一次压测，看看现在到底有多慢

要测高并发，不能用一个用户或者两个用户去糊弄，我提前准备了 1000 个用户，都已经登录过了，token 也提前准备好了；数据库里秒杀券的库存改成了 200，订单表也清空了。接下来就是用这 1000 个 token 去发起请求。

打开 JMeter，这里是 1000 个请求。以前登录 token 是写死在请求头里的，现在没有写死了，改成了引用变量 `${token}`。这个变量从哪来呢？用 CSV Data Set Config 去读取课件资料里的 token 文件（`token.txt`），一行一个 token，变量名就叫 `token`。JMeter 会逐行读取并复制给这个变量，于是我们每次发起请求都能使用不同的请求头。

跑完看聚合报告：最小耗时 126 ms，最大八百多毫秒，平均耗时竟然达到了四百多毫秒，吞吐量 1000/s。

> **提示**：为什么这里的波动这么大？因为 JMeter 模拟的并发并不是真的一次性发了 1000 个请求，它是一开始少、后来越来越多。随着并发量越来越高，CPU 需要在多个线程之间来回切换，就会导致某一个请求处理的耗时增加。

吞吐量 1000/s 看着好像还可以？其实随着并发越来越高，这个值只会越来越低。总之，我们这个业务是比较慢的，接下来必须优化。

### 慢在哪：四步数据库操作串成了一条龙

先回到 PPT 把流程再过一遍。前端发起请求到达我们的 Nginx，Nginx 把请求负载均衡到 Tomcat，而 Tomcat 内部业务流程是这样一个串行的过程：

```text
前端 ──> Nginx ──> Tomcat
                            │
                            ▼
              执行 seckill.lua（资格判断全在 Redis）
                            │
         ┌──────────────────┴──────────────────┐
         │                                     │
    结果 != 0                              结果 == 0
         │                                     │
  返回异常，请求结束                订单信息放进阻塞队列
                                                │
                                                ▼
                                     后厨线程异步消费
                                                │
                                  扣库存 + 创建订单（写数据库）
```

整个流程是串行执行的，一个执行完再往下执行，所以整个请求的耗时就是每一步耗时之和。

而更麻烦的是，查询优惠券、查询订单、扣减库存、创建订单这四步全部要走数据库。数据库的并发能力本身就是比较差的，更何况扣库存和创建订单还是对数据库的写操作；另外为了避免安全问题，我们这里还加了分布式锁。整个业务的性能可想而知——耗时长，并发能力弱。

举个小例子，一看就明白。

我现在开了一个饭店，成本有限，就请了一个人，一个小姐姐。她既负责接待顾客，又要做饭。

```text
【改造前】一个人一条龙

  顾客 ──> 接待 / 点餐 / 收钱 ──> 做菜 ──> 端给顾客
                耗时短           耗时很长

  一个人负责完整的一条龙，总耗时 = 所有环节耗时之和
  单位时间内能接待的顾客自然就少了，后面排队的等不及就走了
```

顾客来了，她首先去接待、点餐、收钱，记录一下；然后到后厨帮这个顾客把菜做好，做好了再端给顾客，流程结束。她一个人负责了一条龙的完整服务，所以接待顾客的业务流程，就是整个流程所有环节之和。因为做饭其实比较耗时，所以接待一个顾客的总时间就变长了，处理一个顾客要耗这么久，单位时间内能接待的顾客数量是不是就少了，工作效率变得极低，后面排队的顾客等不及干脆就走了。这些都不是我们希望看到的。

那该怎么解决呢？大家都能想到——我再请一个人不就行了。小姐姐在前面负责接待顾客，后面再请一个后厨来做饭。

```text
【改造后】前台接待 + 后厨做饭

  顾客 ──> 小姐姐：接待 / 点餐 / 收钱 ──> "旁边请，下一位"
                       │
                       └─> 小票（几号、点了什么）─> 后厨按单做菜 ──> 叫号 ──> 顾客
```

顾客来了，小姐姐先接待、点餐、付钱、把信息记录下来，交给后厨，后厨慢慢去做——到这一步小姐姐的工作已经结束了，顾客坐旁边等着，下一位继续重复这个过程。

那顾客越来越多，怎么分得清谁点了什么、谁先到谁后到？所以点餐以后要给顾客一张小票，上面记录你是几号、吃了什么、点了什么。但这个信息不仅仅是给顾客一份，给后厨也有一份——后厨那里有一个点餐列表贴在墙上，厨师就按照点餐的顺序依次去做，将来做完了以后叫号，是谁的谁来拿。

所以你看：因为点餐收钱这一块业务耗时比较短，就分给了小姐姐去做；而做饭的业务，就交给另外一个人——后厨去做。因此小姐姐的工作效率大大提高，这个饭店处理顾客的速度也提升了，单位时间内能够接待更多的顾客。

同理，咱们这个业务是不是也可以参考这种模式，把它分成两部分：

| 拆出来的两块 | 对应饭店里的谁 | 特点 |
| --- | --- | --- |
| 判断库存是否充足、判断一人一单 | 小姐姐接待顾客 | 耗时短 |
| 扣库存、创建订单 | 后厨做饭 | 耗时长，是对数据库的写操作 |

那在 Java 代码里怎么"交给两个人"呢？执行代码的不是人，是线程。也就是说，我们只需要把这两块交给两个线程就行了。

### 资格判断搬进 Redis，订单进队列

请求进来以后，主线程做的事情就是判断用户的购买资格。如果他有购买资格，我们再开启一个独立的线程，去处理耗时较久的减库存和下单操作——相当于后厨。这样咱们这个业务的效率是不是也就大大提升了？

当然，为了更进一步地提高性能，除了把它分离成两块以外，我们还要尽可能提高"秒杀资格判断"这部分业务本身的效率。因为它现在依然要去查询数据库，所以性能依然会受到数据库的限制。

那我们知道相比于数据库，什么东西的性能更好？没错，就是 Redis。

所以在这里我们完全可以将优惠券信息、订单信息缓存到 Redis 当中，然后把对于秒杀资格的判断放到 Redis 里去做。主线程进来以后，首先就去找我们的 Redis 完成对于秒杀资格的判断，这部分判断完，就代表小姐姐的工作都完成了，其实可以结束了；如果发现他有资格，我们再去执行后续的减库存下单操作就 OK 了。

但是有个坑必须点出来：

> **易错点**：不能"调完 Redis 再去调扣库存下单这部分业务"。那这样一来不就又变成串联成一条龙了吗？性能其实没有增加，反而降低了。所以这里不能是同步调用，而必须开独立线程去执行。

那问题来了：我怎么知道该执行谁呢？给哪个用户去创建订单？之前讲过，人家点餐完了得有小票，记住是谁、点了什么。我们这里也要记录谁买了什么东西，并且还要返回一个编号给用户，将来他可以依据这个去完成付款等后续操作。

所以进到这里要做的第一件事情，其实是记录一下优惠券信息、用户信息——也就是谁买了什么，然后再去记录订单的 id，就相当于是那个叫号：你是几号。然后把这些信息存储到一个队列里。将来我们就可以开启一个独立的线程，去读取这个队列里面的信息，完成下单，相当于后厨里墙上的那个点餐列表。

我们返回给用户的就是这个订单 id，它有两个作用：

> **结论**：一方面用户可以拿这个订单 id 去付款；另一方面他拿到 id 就代表他真的抢单成功了。当然虽然此时真正的订单还没创建，但是将来我们会确保它一定会创建。

于是我们接收用户请求以后的业务流程就变成：进来直接判断秒杀资格，而且这个判断是在 Redis 里做的；做完以后只需要把它保存到队列里，就结束了。整个业务流程是不是变短了？而且因为是基于 Redis，所以性能可以得到极大的提升，整个业务的吞吐能力、并发能力都可以大大提高。

什么时候再做下单和减库存的逻辑呢？我们只需要开启一个独立的线程，去读取提前保存好的这些用户信息、优惠券信息，就可以完成异步的数据库写操作了。

而且在我们返回订单 id 给用户的那一刻，其实秒杀业务已经结束了，用户已经可以拿着这个 id 去付款了。

> **提示**：所以我们什么时候将优惠券信息、用户信息写入数据库里完成下单减库存，其实就没有那么重要了——时效性上的要求就没那么高了，完全可以按照数据库能够承受的频率去写入。当然如果你想提高写库时的性能，不妨多开几个线程，甚至是把单个的写变成批量的写。

正是因为我们把这种同步的写数据库操作变成了异步操作，一方面缩短了秒杀业务的流程，大大提高了秒杀业务的并发；另一方面还减轻了数据库的压力。可以说是一举多得，是一种非常好的方案。

### Redis 里存什么：库存 String，一人一单 Set

难点来了：如何在 Redis 里完成对于秒杀库存的判断，以及一人一单的判断？

答案的前提是——我们肯定需要把优惠券的库存信息以及有关的订单信息缓存到 Redis 当中。那这里就有一个问题：我们应该选择什么样的数据结构来保存这两个信息？

#### 库存：普通 String 就够

库存比较简单，它就是一个数值，所以我们只需要一个普通的 string 结构就行了，key 就是优惠券的 id，value 就是库存的值。将来做库存判断的时候，其实就是看一下这个值是不是大于零，如果大于零那就代表库存充足，我们就可以去做后续的业务了。

但大家一定要注意：

> **易错点**：当我们判断用户确实有购买资格之后，这个库存值一定要减一，相当于我们要在 Redis 里提前预减库存。否则这个值永远不变，那岂不是永远都是库存充足了？这样库存判断就形同虚设。

#### 一人一单：必须是 Set

要实现一人一单功能，就需要在 Redis 里记录当前这个优惠券被哪些用户购买过。以后再有用户来，只需要判断他是否存在，存在就证明他购买过，那就不能再买了。

什么样的数据结构比较适合保存购买过这个优惠券的用户信息？我们可以想一想需要满足的两点：

1. 一张优惠券库存很多，将来购买的用户也会很多，所以要能在一个 key 里保存很多值，也就是一个集合；
2. 一人一单意味着保存在这个优惠券里面的用户 id 是肯定不能重复的，要保证唯一性。

什么样的集合具有唯一性呢？答案就很明显了——就是 Set 集合。Set 可以确保元素的唯一性，并且可以在一个 key 里保存多个值。

```text
seckill:stock:9     (String)  100          ← 9 号券的库存
seckill:orders:9   (Set)     {5, 12, 88}  ← 买过 9 号券的用户 id
```

将来当有用户来抢购的时候，只需要在这个 set 里记录用户的 id，再有更多用户来，也是依次记录就行了。当然如果有用户重复地来购买，比如说 2 号用户，我们判断发现在这个集合里已经存在了，那肯定就不允许购买，它代表他是重复购买。这样一人一单的功能就实现了。

现在我们一起把整个流程梳理一下：

1. 一上来先判断库存是否充足，就是看一下这个值是否大于零；如果库存不足，返回 `1` 代表库存不足，业务结束；
2. 如果库存充足，再判断一人一单，看这个用户在这个集合里是否存在；如果存在，代表重复下单，返回 `2`；
3. 如果不存在，说明他没下过单，有购买资格，就可以去扣减库存——注意这不是真正去数据库扣，而是把 Redis 里这个值减一；
4. 别忘了还要把用户 id 存入这个优惠券的集合里，这样可以作为下一次再来判断时的一个依据；
5. 返回 `0`，代表有购买资格。

| 返回值 | 含义 | 后续处理 |
| --- | --- | --- |
| `0` | 有购买资格 | 保存订单信息入队，返回订单 id |
| `1` | 库存不足 | 返回异常信息 |
| `2` | 重复下单 | 返回异常信息 |

但是，因为对 Redis 的判断有很多个，业务流程比较长，而我们必须确保这一段流程执行时的一个原子性。用什么东西可以确保代码执行的原子性？

> **结论**：Lua 脚本。所以这部分内容将来完全不需要写 Java 代码，直接用 Lua 脚本来实现就行了。

那么将来在 Tomcat 里面，进入用户请求以后要干的事情是什么？上来先调用这个 Lua 脚本，根据 Lua 脚本执行的结果是 `0`、`1` 还是 `2` 来做后续判断。如果不是 `0`，代表就是失败的情况，可能是一，可能是二，这个时候返回一个错误信息就行了，然后结束。如果说是 `0`，证明你有购买资格，我们就需要把优惠券 id、用户 id、订单 id 这些信息首先保存在一个队列里——这就相当于是小票，谁购买了什么东西，还有你的编号是什么——保存下来，方便将来我们的异步线程去执行它，完成真正的下单。其次，我们还需要返回一个订单的 id，也就是那个号，给用户。

到这里，基于 Redis 的秒杀业务流程就分析完毕了。我们可以看到在这个版本当中，接收用户请求以后核心要做的事情仅仅是判断一下用户有没有购买资格：没资格就报错，有资格就返回一个 id 给他。而耗时较久的扣库存、创建订单等等核心的数据库写操作，并没有在我们这个流程当中出现。更何况我们判断用户购买资格也是在 Redis 里通过脚本来执行的。可以说整个业务流程变得非常短，而且执行的性能又非常好，因此整个业务的耗时非常短，可以想象的是，这套实现方案的并发能力就会变得非常高。

### 把库存写进 Redis：新增秒杀券的时候

这节课的需求已经提前列出来了，一共四个：

- 新增秒杀优惠券的同时，把优惠券的信息保存到 Redis；
- 基于脚本判断秒杀库存、一人一单，决定用户是否抢购成功；
- 下单信息放到阻塞队列；
- 异步执行下单。

先看第一个。分析的时候我们已经说过了，要在 Redis 里完成秒杀资格的判断，而资格判断第一个要判断的就是库存，所以我们需要在新增秒杀优惠券的同时，把这个优惠券的库存信息也写到 Redis 里。至于第二个有关购买这个优惠券的用户信息，那肯定是在秒杀的过程当中添加的，所以现在不需要去考虑。

打开 IDEA，首先我们找到有关优惠券添加的业务，在 `VoucherController` 里面，这个就是新增秒杀优惠券的业务。我们跟进去可以看到，它做了两件事情：因为优惠券有两张表，一张 `voucher` 表，一张 `seckill_voucher` 表，所以先保存优惠券信息，再去保存秒杀相关的信息。当然这两个都是往数据库里写，现在我们要多做一件事，就是把它写到 Redis 里——把秒杀的这个库存保存到 Redis 当中。

因此我们需要先注入 `StringRedisTemplate`，通过 `@Resource` 拿到它。接下来就可以用 `opsForValue()` 的 `set` 命令存了。保存库存只需要一个简单的 string 结构就行了，所以完全够用。

那 key 怎么保存？我们之前也分析过了，key 就是当前这个优惠券的 id，当然最好加上一些前缀，比如 `seckill:stock` 代表库存，后面跟上的就是优惠券的 id，也就是 `voucher.getId()`；而它的值就是优惠券的库存，通过 `voucher.getStock()` 获取。写数据库的时候是个数字，所以把它转成字符串就行了。

```java
@Resource
private StringRedisTemplate stringRedisTemplate;

// 保存优惠券信息到数据库
// 保存秒杀信息到数据库
// 保存秒杀库存到 Redis
stringRedisTemplate.opsForValue().set(
        RedisConstants.SECKILL_STOCK_KEY + voucher.getId(),
        voucher.getStock().toString()
);
```

> **提示**：这里我们不需要去配置过期时间。库存可以永久保存到 Redis 当中，除非将来我们需要去移除这个券信息的时候，我们再手动把它删除就行了，所以这块就不去设置有效期。

另外，这里这个 key 最好跟以前一样，都定义到 Redis 的常量当中。我们以前是不是有个 Redis 常量类？在这我们把以前的复制一份，粘贴一下，然后在这里写上值、名字改一下就行——这里对应的就是 `SECKILL_STOCK_KEY`。这样回到代码里就可以直接用这个静态常量了，会显得更加优雅一点。

保存秒杀库存到 Redis 这个业务就完成了。下面做个测试：打开 service 重启一下，重启完成后打开 Postman，点击这个添加秒杀券的接口——以前就准备好了的——在这去添加一个新的秒杀券，时间我们配得长一点，好几个月的有效期，这样测试起来比较方便。发起请求走，你看一下下边返回了一个 `9`，这个其实是秒杀券的一个 id。

打开数据库看一下，`seckill_voucher` 里是不是多了一个 9 号券，库存是 100。然后我们再看 Redis，打开客户端刷新一下，可以看到有一个 `seckill:stock:9`，这个 9 就是对应的 id，它的值是 100。添加秒杀券的这个功能就完成了，第一个需求搞定。

### 用 Lua 脚本完成资格判断

第二个需求是基于脚本判断秒杀库存、一人一单，决定用户是否抢购成功。这块之前已经分析过了，整个流程全部都是用 Lua 脚本来实现的，所以下面先把这个 Lua 脚本写一下。

Lua 脚本的编写相信大家现在还比较陌生，没关系，我们按照这样一个流程来：第一，先想一想我们在写整个 Lua 脚本的时候，这里面会用到哪些参数，也就是参数列表。

进来脚本以后，首先要判断的就是库存是否充足。那我要判断库存是否充足，是不是得去读取 Redis 当中的这个 key，然后来判断这个值是否大于零？因此我必须知道这个 key 的前缀是固定的，而优惠券的 id 是动态变化的，那我认为第一个参数其实就是优惠券的 id。

为什么从 `ARGV` 去取呢？因为它不是一个 key，它只是一个 id，在脚本里把 id 拼接出来得到 key 就好了。

第二个参数是用户 id。判断完库存以后，判断用户是否下单，依据就是看这个用户 id 在将来的那个 set 集合里是否存在。而至于 set 集合的 key，其实将来也是以优惠券的 id 作为 key，只是前缀会有变化，所以不用再传第三个参数了。

后面的扣库存、存用户、返回结果都只是逻辑判断和返回，没有别的参数了。所以说到这里其实就是两个参数、两个数据：

```lua
-- 1. 参数列表
-- 1.1 优惠券id
local voucherId = ARGV[1]
-- 1.2 用户id
local userId = ARGV[2]

-- 2. 定义数据key
-- 2.1 库存key
local stockKey = 'seckill:stock:' .. voucherId
-- 2.2 订单key
local orderKey = 'seckill:orders:' .. voucherId
```

> **易错点**：在 Lua 脚本里拼接字符串不是用加号，是用两个点 `..`。

订单 key 虽然咱们现在还没有写过，但这里可以参考库存的结构：同样是秒杀前缀，只不过这里保存的不是库存，而是有关订单的信息——准确来讲保存的是用户 id。key 是优惠券 id，value 是一个 set 集合，里面保存的就是购买了这个优惠券的所有用户 id 形成的一个集合。

接下来就是业务逻辑，先判断库存是否充足，其实就是取出这个 stock key 的结果，看它是否小于等于零；小于等于零代表没有了、用完了。

> **易错点**：这里我就不卖关子了，直接告诉大家。我们在 Redis 里做存或者取操作，拿到的都是 string 类型，所以调用 `get` 得到的其实也是一个字符串，而字符串是没有办法跟数字做比较的。所以在这里最好先把它转成数字，调用一个函数叫 `tonumber`，把这个值传进去，它就会帮我们把字符串转成数值类型，然后再去做比较。

判断用户是否下单，可以用 set 集合里面的一个命令来判断一个元素是不是这个集合的成员——`SISMEMBER`。很多同学可能忘了，我带着大家来回顾一下。打开一个 Redis 客户端，通过 `help` 看一下 set 相关的命令，也有很多。判断一个给定的值是不是当前这个 set 集合的成员，我们可以用 `SISMEMBER`。

```text
SADD k1 u1
(integer) 1

SISMEMBER k1 u1
(integer) 1

SISMEMBER k1 u2
(integer) 0
```

看到规律了吧：存在返回 `1`，不存在返回 `0`。将来我们会把用户 id 存在这个 set 集合里，那判断一个用户有没有下单，其实就是看当前用户 id 是否在这个集合里存在。

回到脚本里：

```lua
-- 3. 业务逻辑
-- 3.1 判断库存是否充足
if tonumber(redis.call('get', stockKey)) <= 0 then
    -- 库存不足
    return 1
end

-- 3.2 判断用户是否下单
if redis.call('sismember', orderKey, userId) == 1 then
    -- 重复下单
    return 2
end

-- 3.3 扣减库存（incrby 是加，加 -1 就是减一）
redis.call('incrby', stockKey, -1)

-- 3.4 保存用户id到订单集合
redis.call('sadd', orderKey, userId)

-- 3.5 抢购成功
return 0
```

扣库存这块要注意：库存现在是一个 string 结构，直接用 decrby 是不行的，得用 `incrby`，`incrby` 是加的意思，那加 `-1` 是不是就减一了？下单其实就是把这个用户 id 添加到 order key 里，这块就不能用 `sismember` 了，而是用刚才演示过的 `sadd` 添加进去，这样下一次同一个用户再来的时候，判断的时候它就存在了。

如果代码能走到 `3.1` 判断之后的位置，证明库存是充足的，也没有下过单、是第一次来，就可以完成扣库存和保存用户 id 的逻辑了。

> **提示**：整个脚本有三个出口，成功那一支千万别漏掉——成功要返回 `0`，前面忘了写的话资格判断的 Java 侧就会全当成失败。

### 在 Java 里执行脚本并返回订单号

脚本写完了只是第一步，我们还需要在 Java 代码里执行这个脚本。找到之前那个秒杀下单的业务去做改造：不再是用 Java 代码来判断秒杀资格，而是去调用这个 Lua 脚本。原来那段用 Java 判断的代码先注掉留着，剩下的代码大家以后可以自己看一看；下面真正下单的那部分我们先删掉，等实现异步的时候再补回来。

执行脚本这块可以参考之前写分布式锁的代码——那时候我们是用一个静态代码块来加载脚本的，这块同样是参考它来做，把那段复制过来粘贴一下，改个名字就行。我们这块是秒杀脚本，脚本名字也改成 `seckill.lua`：

```java
private static final DefaultRedisScript<Long> seckillScript;

static {
    seckillScript = new DefaultRedisScript<>();
    seckillScript.setLocation(new ClassPathResource("seckill.lua"));
    seckillScript.setResultType(Long.class);
}
```

有了这个脚本就可以执行它了。执行脚本我们要用到 `RedisTemplate`，直接拿到它，调用里面的 `execute` 方法，这个咱们之前讲过。调用的时候需要传三个参数：

1. 第一个参数就是我们的脚本；
2. 第二个是它里面所需要的 key。但是大家可以注意到，我们刚才写这个脚本的时候，这里是没有 KEYS 类型参数的，只有两个 ARGV，也就是其他类型的参数，所以 KEYS 的个数为零。这个地方要的是一个集合，这里不是传 null，而是利用工具类 `Collections` 传一个 `emptyList()`，代表空集合；
3. 第三个是 args，也就是其他类型的参数。我们这个脚本里其实有两个：优惠券 id 和用户 id，把这两个传过去就 OK 了。

用户 id 我们可以通过 `UserHolder` 去 `getUser()`，然后 `getId()` 就拿到了。所以代码是：

```java
Long result = stringRedisTemplate.execute(
        seckillScript,
        Collections.emptyList(),
        voucherId.toString(),
        userId.toString()
);

int r = result.intValue();
if (r != 0) {
    // 没有购买资格
    if (r == 1) {
        // 库存不足
        throw new RuntimeException("库存不足！");
    } else {
        // 不能重复下单
        throw new RuntimeException("不能重复下单！");
    }
}

// TODO 保存订单信息到阻塞队列

// 返回订单id
long orderId = idWorker.nextId(RedisConstants.ORDER_KEY);
return orderId;
```

> **易错点**：`execute` 的第二个参数千万不要传 `null`，要传 `Collections.emptyList()`。

结果有三种情况：`1` 代表库存不足，`2` 代表重复下单，`0` 代表成功、也就是有资格。所以我们判断一下结果是否为零，不为零就是有问题。而不等于零还分两种情况：一就是库存不足，剩下的就是不能重复下单了，所以这里要返回不同类型的异常。

如果走到后面，代表就肯定是零了，有购买资格。那有购买资格就要把它保存到阻塞队列当中，后续就可以基于这个队列异步完成下单的业务了。但是写阻塞队列会麻烦一点，我们先不着急，先在这里 TODO 一个"保存订单信息到阻塞队列"，我们先测一下购买资格的判断能不能成功，然后再去实现队列的保存。

> **提示**：这叫做分批测试。你一下全写完了去测，万一出了 bug 你也不知道问题在哪，所以先 TODO 一下，通一段再往下走。

放到阻塞队列里需要订单 id。我们有自己的 id 算法 `IdWorker`，调用它里面的 `nextId`，然后把 key 传进去，key 前缀就是 `order`，得到订单 id 后最后返回。到这里其实我们业务的前半部分——判断购买资格——就做完了，就差往队列里放以及异步执行了。

现在先测一下这一部分。重启一下，这次就启动一台做测试就行了，不去启动多台了。启动完毕后打开 Postman，通过这个来测一下：刚才我们的券的 id 是 `9`，所以把这里改成 `9`，然后发起请求。你看，这里是不是得到了一个订单 id，证明这次下单是成功了；我们再来一次，直接提示不能重复下单，说明咱们这个逻辑没什么问题。

看一下数据库，因为我们还没做数据库的写操作，所以这块没什么变化，还是以前的样子。然后我们看 Redis——现在整套流程都是基于 Redis 做的，刷新一下：首先库存是不是减了一个，订单是不是加了一条，是 5 号用户来添加的。再打开 Postman 来发一次，还是不能重复下单，也就是同一个用户不能一直下单；这时候 Redis 里库存大家可以看到还是 99，没有问题。这说明整个流程是 OK 的。

那这个改造对性能到底有多大影响？现在其实就差一个往阻塞队列里放，那个对性能其实没有什么影响，所以我们直接测一下当前情况下的性能。先把库存恢复一下，比如改成 200 个库存，库存多一点好。打开 JMeter，找到这个 app 请求，首先把参数改成 9 号券，然后先把以前的结果清空，执行。

## 秒杀异步下单与 Redis 消息队列
> 对应块：BLK21 | 覆盖分集：P71-P73 | 块标题（分集名）：《实战篇-24.秒杀优化-基于阻塞队列实现秒杀异步》

### 抢单成功之后，订单先别急着落库

上一节课我们已经把秒杀优化的前两个需求做完了：优惠券的库存信息存进 Redis，然后在 Redis 里用 Lua 脚本完成秒杀资格的判断——先看库存是否充足，再看你有没有下过单。库存充足，并且你从来没下过单，就证明你有购买资格，这时候我们**立即**返回一个订单 id，告诉你抢单成功了。

到这里，抢单的任务是不是就结束了？整个流程非常短，响应时间自然也就很短，整个业务的并发能力也增强了。

但是呢，到这里为止并没有真正下单，只是告诉用户说你现在成功了。

那什么时候去完成下单？

就在这个地方——我们会把抢单成功的用户 id、他抢的这张优惠券的 id，以及相关的订单 id，全部封装一下，放到一个队列里。这个队列里放的就是所有等待下单的订单信息。然后我们会开启一个线程，异步地去执行，不断从队列里拿到订单信息完成下单。这样下单就不会影响到整个业务的耗时了。这个也是我们业务性能提升的关键。

> **结论**：秒杀优化的核心思路就是把同步下单改为异步下单。一部分负责判断抢购资格，发现有资格立即结束、告诉用户成功；至于耗时较久的下单部分，异步去完成。

### 阻塞队列：接得住"时有时无"的订单

那下单信息包括什么呢？订单 id、用户 id、还有我们的优惠券 id，这些都需要封装起来。怎么封装呢？可以参考我们以前下单的那段业务代码，其实非常简单，就是 `new` 出来一个 `VoucherOrder` 对象，然后把这几个信息一个一个放进去，不就完了吗。

> **提示**：真正下单的动作先别着急。数据准备好了，但我们不是马上去下单，而是先把它放到阻塞队列里去。

那问题来了，我们这里没有阻塞队列呀。要往阻塞队列里放，是不是得先创建一个？

### 阻塞队列到底"阻塞"在哪

阻塞队列就叫 `BlockingQueue`，它有一个特点：当一个线程尝试从这个队列里获取元素的时候，如果队列里没有元素，那么这个线程就会被阻塞，直到队列中有元素它才会被唤醒，并且获取元素。

你想，我们的订单也不是一直会有吧——有人下单才会有，没人下单就没有。所以在这儿用阻塞队列刚刚好。

我们阻塞队列里面装的元素的类型呢，就是这个 `VoucherOrder` 类型，名字就叫 `orderQueue` 吧，就是订单相关的队列。然后 `new` 一个什么呢？因为 `BlockingQueue` 有很多很多的实现，这里我们可以选择最简单的 `ArrayBlockingQueue`，就是利用数组实现的一个队列。所有队列需要指定一下初始化的大小，也就是说这个队列的长度是多少。这里我们给个 `1024 * 1024` 吧。

> **注意**：这个值不能给得太大，给得太大容易消耗过多内存，所以这块要给一个适当的值。

有了阻塞队列以后，下面就好办了，我们只需要调用它的 `offer` 方法，就能够把我们的订单信息存到阻塞队列里去了。到这儿，抢单的流程其实就算是完成了。

### 另起一个线程去慢慢下单

接下来要做的就是异步的下单了。我们说过，异步下单就是开启独立线程，不断地执行线程任务，任务就是从队列里取出订单去下单。所以这里我们要准备两个东西：第一是线程池，第二是一个线程任务。

线程池比较好办，我们以前应该也都用过。我们这里创建一个线程池，名字呢就叫秒杀订单处理器，专门用来做秒杀订单的处理。这里其实线程池我们也可以用静态常量，`static final`，小驼峰改成大写。它的值通过 `Executors` 的静态方法来获取，`newSingleThreadExecutor`，获取一个单线程的。因为在这里处理订单，它的速度也不需要特别快，所以说我们给一个线程就行了，你慢慢去处理就完了。

线程任务其实就是一个 `Runnable`。怎么去创建呢？可以用匿名的方式，也可以直接写一个类，比如说就叫 `VoucherOrderHandler`，让它实现 `Runnable`。这样我们就有现成的任务了嘛。虽然这个任务方法里面还没有东西，但是最起码任务先有了，将来再去执行我们的业务逻辑。

什么时候执行这个任务呢？肯定是在用户秒杀抢购之前就开始吧。因为用户一旦开始秒杀，就会向我们的阻塞队列里添加新的订单，那我们这个任务就应该去取出这里的订单信息了，所以它必须在这之前去执行。事实上我们这个项目只要一启动，用户随时都可能来抢购，所以说我们这个任务是不是应该在我们这个类初始化之后就应该赶紧运行？

怎么样让我们这个类一初始化就来执行这个任务呢？这里我们可以利用 Spring 提供的一个注解来做。我们先定义一个方法叫 `init`，加上 `@PostConstruct` 注解。这个注解代表的含义就是说在当前类初始化完毕以后来去执行。在这个方法执行什么呢？我用它去 `submit` 提交这个任务。

因此呢，我们这个对象 `VoucherOrderServiceImpl` 一旦初始化完毕，就可以执行了，一执行这个 `run` 方法任务就开始跑了。

那在 `run` 方法里我要干什么？很简单，你就是不断地从队列取嘛，上来就 `while (true)` 死循环。死循环里两步：第一步获取队列中的订单信息，第二步就是去创建订单。

```java
public class VoucherOrderHandler implements Runnable {

    @Override
    public void run() {
        while (true) {
            try {
                // take 是阻塞方法：获取队列中的头部元素（第一个元素），
                // 如果没有则一直等待，直到有元素可用为止
                VoucherOrder order = orderQueue.take();
                handleVoucherOrder(order);
            } catch (InterruptedException e) {
                // 处理订单出异常，为什么异常了不知道，记一笔日志就完了
                log.error("处理订单异常", e);
            }
        }
    }
}
```

> **提示**：尽管我这里写的是 `while (true)`，但是你不用担心它会对我们的 CPU 带来巨大负担。因为一旦发现没有元素就会卡在这里，有元素才能往下走。

创建订单会复杂一点，我们在这定义一个函数，比如说叫 `handleVoucherOrder`，把取出来的订单传进去。这个方法我们把它创建到 Service 这个外部类里面，在这边去处理订单。

### 异步化之后，代码要跟着改哪些地方

那处理的流程其实跟我们之前这段逻辑比较像——就是之前在上面做判断，判断完了以后开始做处理，处理的话你就要去获取用户信息、创建锁对象。这一对呀，所以我们跟这段逻辑基本上是一致的，我们按照这个流程复制一下来做。

但是复制完了以后呢，这块有一些问题我们需要改进。

#### 用户 id：UserHolder 在子线程里是空的

首先第一个，在这个地方创建锁对象需要用户 id。这个用户 id 我们不能再从 `UserHolder` 里去取了。因为你现在是一个多线程，从线程池里获取的一个全新的线程，不是主线程去做的，所以这个时候你从 `ThreadLocal` 里想去取这个用户，是取不到的。

所以这里我们只能从 `VoucherOrder` 里去取用户 id。

> **易错点**：这个地方大家一定要去注意。获取用户不能再走 `UserHolder`，必须从 `VoucherOrder` 里拿。

```java
// ✘ 子线程里拿不到，ThreadLocal 是跟线程绑定的
Long userId = UserHolder.getUser().getId();

// ✔ 订单是谁抢的就从订单里取
Long userId = order.getUserId();
```

然后我们再去创建这个锁对象，锁对象有了以后再去获取锁，然后判断这个锁是否成功。

那这个判断如果说失败，这个地方也不要去返回什么东西了，因为咱们现在是异步处理，不用返回给前端了，所以现在 `return` 任何东西都是没有意义的，通过一个 `error` 记录一下日志就行了。

而且呢，在这个地方的话，我们其实理论上讲不用加锁也 OK 啊，因为什么？因为我们已经在 Lua 里做了这种判断了，对不对？在这个地方有时候为什么又要加一次锁呢？其实就是为了做一个兜底，以防万一——万一 Lua 出了问题没有判断成功的，虽然这种可能性几乎没有，但是该做的判断咱们还是做一下。

#### 事务代理对象：主线程拿好了再传下去

然后在这个地方要去获取这个代理对象，去调用 `createVoucherOrder` 函数。

那么这个地方需要注意一下，获取事务代理对象在这里是拿不到的。

为什么拿不到呢？同样是这个原理。大家点进去 `TransactionSynchronizationManager` 看一下，它的底层也是通过 `ThreadLocal` 去获取的。

那么我们现在这个处理业务是基于一个子线程去做的，你是一个子线程，而不是主线程，那么作为一个子线程，你是没有办法从 `ThreadLocal` 里取出你想要的东西的，所以这个地方其实是拿不到的。

那我们现在想要让这个事务生效，该怎么办呢？只能这么做了——我们把这个事务对象提前获取，你只能提前获取。在这获取是不行的，在主线程获取。主线程是谁呢？主线程就是一进来做秒杀的时候，走到这一步的时候，基本意味着可以去做处理了，在这个时候我们去拿到这个代理对象是没问题的。

在秒杀主流程里加一步获取代理对象，然后放到队列里，后续就可以去处理了。在哪获取了以后，你的这个代理对象是不是应该让我们的后续线程能够拿到啊？那现在有两种手段：第一种就是把它也传到这个队列里；还有一种就是把它放到我们的成员变量的位置。两种手段都是 OK 的。比如说我给他就放到这里吧，在这个地方我们放一个成员变量，然后在这儿给他做一个初始化。现在就等于把代理对象放到当前这个类里边了，那这个时候我们在子线程去取的时候，其实就是拿到一个现成的代理对象了，不用临时获取了。

```java
public class VoucherOrderServiceImpl implements VoucherOrderService {

    // 事务代理对象必须在主线程里拿！子线程的 ThreadLocal 是空的，拿不到
    private VoucherOrderService vcService;

    @PostConstruct
    public void init() {
        ORDER_EXECUTOR.submit(new VoucherOrderHandler());
    }

    public Long seckillVoucher(Long voucherId) {
        // 1. 执行 Lua 脚本，判断购买资格，无资格直接结束
        // 2. 封装 VoucherOrder：订单 id、用户 id、优惠券 id
        // 3. 走到这里说明有资格，可以放队列了，这时候取代理对象没问题
        vcService = SpringUtil.getBean(VoucherOrderService.class);

        // 4. 放到阻塞队列，后续由异步线程处理
        orderQueue.offer(order);

        // 5. 立即返回订单 id，真正的落库交给异步线程
        return orderId;
    }

    private static class VoucherOrderHandler implements Runnable {
        @Override
        public void run() {
            while (true) {
                try {
                    VoucherOrder order = orderQueue.take();
                    // 用主线程提前塞进来的这个现成代理对象，子线程里不用再获取
                    vcService.handleVoucherOrder(order);
                } catch (InterruptedException e) {
                    log.error("处理订单异常", e);
                }
            }
        }
    }
}
```

#### createVoucherOrder：订单现成，直接用

然后我们去调用这个 `createVoucherOrder` 函数，这地方同样需要注意的是，在原本这个函数里面，它其实是有一个重新创建订单的动作的。我们现在是不是不需要这个创建订单的动作了？现在你可以在原有这个函数的基础上做改造，没问题的。

也就是说，你首先第一个，你传的不再是 `voucherId` 了，传的是整个订单对象，这是第一个改变。第二个就是，你那个订单的对象不用再重新创建了。

所以你现在就需要对当前这个业务去做改造，改造的时候变量名改成 `order`：`voucherOrder` 改成 `order`，然后去重写一下。原来这个方法里面他要重新创建订单，现在根本不用重新创建了，直接用这个 `order` 就完了，因为 `order` 是现成的嘛。

这个地方也不需要返回 id 了，因为我们现在这个业务都是异步执行的了，不需要返回给前端任何东西了，直接 `void` 就可以了。那这样我们那个接口也要改，接口都返回成 `void`。

```java
// 改造前：传 voucherId，内部自己 new VoucherOrder，最后返回新生成的订单 id
public Long createVoucherOrder(Long voucherId)

// 改造后：整个 order 已经现成了，直接用；也不用再返回 id
public void createVoucherOrder(VoucherOrder order)
```

现在这个流程其实是 OK 的。我进来以后第一步就去执行，执行的时候我就调 `createVoucherOrder` 去创建订单。就进到这个函数里以后，首先是开启事务，然后开始执行。那么这个用户 id 就不能通过 `UserHolder` 获取了，刚才说过原因了，因为你是异步的，你是一个子线程，所以你需要从 `VoucherOrder` 里去取。

同样呢，你下边的话也不需要去做返回了。首先是不太可能出现重复，对吧？但是呢为了以防万一，咱们也给他记个日志就行了，然后再往下扣库存。扣库存这里同样道理，不太可能出现库存不足，因为 Redis 里已经做了判断了，但是以防万一，咱们还是做一个判断，做个输出就好了。再往下的话就是创建订单。

到这呢整段逻辑其实就已经完成了，这是最新的创建订单的逻辑：一样一人一单进来做一个判断，然后做库存判断，然后去创建订单——就省去了自己手动创建订单的过程，跟以前那个代码相比。

到这里呢，咱们整个代码的改造其实就 OK 了。

### 全流程串一遍

现在任何人来调用我们的创建订单的逻辑，我们首先会调用 Lua 脚本去判断这个用户有没有购买资格、库存是否充足。经过 Lua 脚本执行，根据这个结果我们就能得到它有没有购买资格。

如果说没有购买资格，这里直接就结束了。如果有购买资格呢，我们不是直接下单，而是将这个订单创建出来，扔到阻塞队列里去，然后就结束了。所以我们的业务到这其实就直接结束了，用户直接得到结果了，告诉他说下单成功——理论上讲他已经有购买资格了，对不对。

放到阻塞队列之后，接下来要执行的就是异步下单。这个任务我们认为应该百分之百能够成功，因为库存也是足的，用户也没下过单。那么这个任务我们认为应该百分之百能够成功，队列里的订单任务就由线程池不断取出然后去创建。

创建的流程是干什么的呢？首先一样要去获取锁，这个地方同样还是为了保证并发安全。事实上尽管不太可能出现并发安全问题，因为已经做过判断了，这里不可能出现重复，但是咱们这里还是做了，就是做一种兜底，以防万一。所以还是去获取锁什么的，事实上这段不做也没问题啊。然后拿到锁以后去创建订单，创建订单的话就是之前的逻辑，无非就是在这里做判断一人一单、减库存；创建订单这块不用创建了，因为前面已经创建好了。

```text
【改造前：同步下单】

   用户请求
      │
      ▼
  ① Lua 脚本判断购买资格
      │
      ▼
  ② 加锁 → 一人一单判断 → 扣库存
      │
      ▼
  ③ 开启事务 → 写订单表 → 提交事务
      │
      ▼
  返回订单 id
      ↑
   这整条链路用户都要等：最快 100 多 ms，平均 400 多 ms


【改造后：异步下单】

   用户请求
      │
      ▼
  ① Lua 脚本判断购买资格（库存充足？是否已下单？）
      │
      ├──── 无资格 ────▶ 直接返回失败，流程结束
      │
      ▼ 有资格
  ② 封装 VoucherOrder（订单 id + 用户 id + 优惠券 id）
      │
      ▼
  ③ 放进阻塞队列 ─────────────────┐
      │                           │
      ▼                           │
  立即返回订单 id（~20ms）         │
                                  ▼
                     ┌──────────────────────────────┐
                     │  独立线程（单线程池 + Runnable）│
                     │  while (true) {              │
                     │      orderQueue.take()       │
                     │      加锁 → 一人一单 → 扣库存   │
                     │      开启事务 → 写订单表       │
                     │  }                          │
                     └──────────────────────────────┘
```

读图要点：用户这条链路只跑到"放进队列"就断了，后面那一大段耗时的事全部搬到旁路的线程里；两条链路之间唯一的交接物就是队列里的那个 `VoucherOrder`。

### 秒杀优化思路回顾，以及它留下的两个问题

那我们回到 PPT。这节课呢我们实现了异步下单的功能，到这儿呢，其实对于秒杀的初步优化就结束了。我们一起来回顾一下秒杀优化的思路是什么。

秒杀优化的思路就是变同步下单为异步下单。什么叫同步下单啊？就是说来了以后我判断你有没有资格，有资格呢我就立即去下单。但因为下单、扣库存啊等等这些业务要加各种各样的事务或者是锁，就导致了这一系列的业务全部执行完，它的耗时就会非常地久，最低耗时都能达到 100 多毫秒甚至 200ms，然后平均耗时就达到了 400 多毫秒。

而我们现在的思路是什么呢？就是尽可能地去简化这个业务，然后把业务分成两部分。一部分是对于抢购资格的判断，如果发现你有资格，立即就结束，告诉用户说下单成功。至于耗时较久的下单部分，我们可以异步去完成——这就是我们的思路。

两个动作：首先是利用 Redis 完成库存余量、还有已下单的判断，也就是购买资格的判断，如果发现有资格直接结束，这样响应时间就变短了。然后至于下单、减库存这些耗时较久的任务呢，我们可以把它放到阻塞队列里，然后利用独立线程异步去下单。

那这种模式呢虽然提升了秒杀业务的性能，但是呢它也存在一些问题。不知道大家能不能想到啊，可以把自己的想法打在弹幕上。

#### 内存限制问题

关键点就在于，我们使用的是 JDK 里面的阻塞队列，而这个阻塞队列它使用的是 JVM 的内存。如果说不加以限制，在高并发的情况下，可能就会有无数的订单对象需要去创建，并且放到队列里，这里可能会导致我们内存溢出。

所以我们在创建阻塞队列的时候，是不是设置了一个队列的长度、一个上限？但是同学们思考一下，那如果说这个队列里面的东西存满了呢？再有新的订单需要往里面塞，是不是就塞不进去了呀？

所以这就是我们现在这个秒杀存在的第一个问题——内存限制的问题。

#### 数据安全问题

第二个问题呢是数据安全的问题。现在我们是基于内存来保存这些订单信息的，如果说我们的服务突然宕机了，那内存里的所有的这些订单信息是不是都丢失了呀？用户已经完成下单了，你告诉人家成功、让人家付款了，结果我们后台根本没有相关订单数据，这样一来不就出现了数据不一致的情况了吗？

还有一种情况是这样子的：比如说我们现在有一个线程，从队列里取出了一个订单任务要去执行，可惜啊，就在此时发生了严重的事故，比如说出现了什么异常之类的。那这样一来这个任务有没有执行？没有吧。而任务一旦取出来，队列里就没有了，也就是说以后再也不会执行了——这不就等于这个任务丢失了吗？那再一次出现了不一致的情况吧。

所以以上这两种都会导致数据的安全问题。

### 认识消息队列

那这两个问题又该怎么解决呢？最佳的方案就是使用消息队列。

当然有很多同学可能没有接触过消息队列，别着急，这节课呢我们就带大家花几分钟时间先了解一下什么是消息队列。

#### 三个角色，和一个更贴切的名字

消息队列的英文名称叫 message queue，字面意思就是存放消息的队列。因为队列我们都知道是一种数据结构嘛，就是来存东西的，存什么？存消息。

而一个最简单的消息队列模型，至少要包含三个角色，分别是生产者、消息队列和消费者。消息队列负责存储和管理消息。

注意了，虽然字面来讲是做存储，但其实一个消息队列他要干的事情远远不止于此。所以与其称它为消息队列啊，不如称它为消息的代理，message broker。

```text
      ┌────────────┐    发送消息    ┌────────────────┐    消费消息   ┌────────────┐
      │   生产者    │ ───────────▶ │    消息队列      │ ───────────▶ │   消费者    │
      │ （秒杀下单） │              │  message broker │              │ （独立线程） │
      └────────────┘              └────────────────┘              └────────────┘
                                          │
                                    揽件 · 运输保管 · 投递
```

读图要点：消息队列站在中间，它不是一个单纯的"存东西的容器"，它扮演的是快递公司的角色——当有人要寄件的时候，快递公司要去揽件，然后要运输保管这个快递，当然最终还要去投递，所以它的工作是非常复杂的。

#### 从快递柜说起

当然如果大家对于快递公司内部的工作流程不太熟悉，没关系，咱们也可以把这个流程简化一下：你可以把它理解成这个队列就是个快递柜。快递柜大家都见过，就是用来存放快递的。那这个人呢你就可以理解成投快递的快递员，这个就是我们我们去取快递。

现在的快递员寄件呢，都不再是投送到我们家门口了，而是都是往快递柜一扔就结束了。

那现在呢我问问大家，大家觉得应不应该有快递柜？把你们的答案打在弹幕上，让我看看。相信啊，作为消费者的我们，肯定都会认为啊，不应该有快递柜，所有快递员都应该送货上门，是不是啊？但是呢你听我给你分析一下。

现在假设有一个快递员真的来投递了，结果是没有快递柜，他就送货上门了。但是你正在公司上班啊，他给你打了个电话说"我到你这了，你快点下来拿快递"。结果呢，你不在呀，怎么办呀？把快递放门口吧，你不放心，不安全，万一被人拿走了。但是让你现在赶回去吧，你正在工作，这怎么办呢？你给快递员说："你要不等我一下吧，等我下班了回去拿。"那个快递员，你说他等不等你？他如果等你的话，这一等就是一天，这时间就浪费了。那如果不等你的话，这一趟不就白跑了，而且还可能面临你的投诉，下次再来呢，有可能你还不在。

所以你看，我们的快递员比较难受，工作效率低下，头一个快递都得等一天。而我们的消费者呢也不好过啊：快递给你送上门的时候你在公司上班，你回家了呢人家快递员又没时间；你在公司上班的时候接到这个快递员的电话呀，整个人就一直想着这个事，快递放家里你不担心不安全，回去嘛老板又不同意，你这个工作呀，都没办法专心做。你看看是不是两头都不好收啊？

而有了快递柜就不一样了。有了快递柜，快递员可以把快递投送到快递柜去，早上花上十分钟的时间，就把一个上午所有的货全部投出去。而作为消费者呢，你在公司里上班不急，只要你收到了短信，什么时候有空什么时候去快递柜拿就行了，没有压力。

```text
   【没有快递柜】
        ┌──────────┐    打电话等你    ┌──────────┐
        │  快递员   │ ──────────────▶ │  消费者   │
        └──────────┘   一天？白跑？   └──────────┘
          快递员：放门口不安全 / 干等浪费 / 不等被投诉
          消费者：上班惦记 / 请假被拒 / 回去没人 → 两头难受


   【有了快递柜】
          ┌──────────┐   投递    ┌──────────┐   有空再取   ┌──────────┐
          │  快递员   │ ───────▶ │  快递柜   │ ───────────▶ │  消费者   │
          └──────────┘           │(消息队列) │             └──────────┘
          十分钟投完一上午的货      └──────────┘            零压力
              ◀──────────── 解除耦合 ────────────▶
```

读图要点：快递柜把"投递"和"取件"在时间上彻底解开了，快递员不必等、消费者不必赶，这正是消息队列解除耦合的直观体现。

那我们的秒杀是不是也是一样的？当有人来抢购我们的商品时，我们不着急去真正下单，我们可以先判断他有没有购买的资格。如果有购买资格，这个时候不要去写数据库，而是把我们的订单相关信息写到队列里去，相当于是发了一条消息。而这个时候我们开启一个独立的线程，作为一个消费者，让他不断地从队列里获取消息，真正地去完成下单、去写这个数据库。

这样呢，我们秒杀抢单的这个业务，就与真正写数据库的业务分离了，变成异步操作了，解除了耦合。那秒杀这一块呢因为不用写数据库，它的并发能力是大大提高；而数据库这一块呢，它可以按照自己的节奏慢慢去取订单去写，它没有感受到很大的压力啊，不用担心数据库扛不住的问题。是不是完美解决了？

### 消息队列和阻塞队列到底差在哪

但有的同学会说了：你这个时候把阻塞队列替换成消息队列，不是一样的吗？你这里有订单了扔到队列里去，听起来确实是类似的。

但是这里有两点不同。第一呢，消息队列是在 JVM 以外的一个独立服务，所以它不受 JVM 内存的限制，这就解决了我们第一个问题。第二呢，消息队列不仅仅是做数据存储，它还要干什么？要确保我们的数据安全。也就是说你存进消息队列里的所有消息，它要去做持久化，这样呢不管是服务宕机还是重启，数据不会丢失。而且啊，它要在消息投递给消费者以后，要求消费者做消息的确认；如果消息没有确认，那么这个消息就会在队列当中依然存在，下一次呢会再投递给消费者，让他继续处理，直到成功为止——也就是确保消息至少被消费一次。

所以这就是一个完美的消息队列应该达成的目标了，这也是它与传统的阻塞队列的区别。

```text
                JVM 阻塞队列          消息队列
  存储位置        JVM 进程内存          JVM 以外的独立服务
  内存上限        受 JVM 内存限制        不受 JVM 内存限制
  宕机 / 重启    队列中数据全部丢失      持久化，数据不丢
  异常中断        任务出队后即丢失        未确认的消息重新投递
  角色定位        一个数据容器            message broker：揽件 · 运输保管 · 投递
```

那到哪里去找这样的消息队列呢？现在市面上其实有很多这样的消息队列，比如说 RocketMQ、RabbitMQ、Kafka 等等。大家如果想完整地学习消息队列的有关知识，在这里我推荐大家学习我们在 B 站上的另一个课程：搜索"Spring Cloud"，排第一个的黑马程序员课程，就是微服务技术栈的完整课程，那它里边就包含了有关 MQ 的一些知识，包括 MQ 的基础知识和高级知识，大家可以去学习一下。

好，那我们言归正传。这是我们市面上提供的各种各样的消息队列，不过上述这些消息队列都需要去额外搭建一些服务，去学习另外的一些技术，那么它是有一定的成本的。对于一些小型的企业来讲，肯定是成本越低越好，对不对？比如说我们现在已经搭建了一套 Redis 集群了，Redis 在开发的时候是不可或缺的吧。那这个时候我们能不能利用 Redis 直接解决这个问题呢？

答案是可以的。因为在 Redis 里面也提供了三种不同的方式来实现消息队列，这样你就没有必要额外去搭建别的一些服务、学习别的技术了，直接利用 Redis 搞定了。

```text
  Redis 实现消息队列的三种方式

  ┌────────────┬────────────────────────────────┬──────────────────────────┐
  │   方式     │              原理               │          特点            │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │   List     │ 利用双向链表模拟阻塞队列         │ 简单，但消息取出即消失，   │
  │            │                                │ 只能单消费者消费           │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │  Pub/Sub   │ 发布订阅：PUBLISH / SUBSCRIBE   │ 典型的消息队列模型，       │
  │            │                                │ 但功能并不够完善           │
  ├────────────┼────────────────────────────────┼──────────────────────────┤
  │  Stream    │ Redis 5.0 推出的最新模型         │ 相对比较完善，功能非常强大 │
  └────────────┴────────────────────────────────┴──────────────────────────┘
```

`pub` 就是 publish，`sub` 就是 subscribe，订阅的意思，也就是发布订阅，这是一种典型的消息队列模型。近几节课我们就会依次给大家介绍这三种不同方式实现消息队列的原理和优缺点。

### 用 List 模拟消息队列

我们知道 Redis 的 List 结构是一个双向链表，而消息队列却是一个队列。因此要想利用 List 实现消息队列，就必须利用链表模拟出队列的效果。

#### 入口和出口不在同一侧

那队列效果有什么样的要求呢？我们其实在 Redis 的入门篇里已经给大家总结过了——队列就像我们喝酒喝多了要去上厕所一样，先进的要先出，所以"喝"和"出"不是一个口。入口和出口不在一起，这样实现出来的自然就是队列了。

我们的双向链表可以在左侧或者右侧去做操作，那入口出口不在一起，就是说你存的时候从左侧存，取的时候从右侧取，或者反过来都是 OK 的。所以我们可以利用 `LPUSH` 结合 `RPOP` 命令，或者是 `RPUSH` 结合 `LPOP` 命令。因为 `push` 就是往里面去存，`pop` 就是取。

比方说现在我们用 `LPUSH` 就是从左边存。现在呢我们存一个消息 1，再存一个消息 2，那么它其实就是一个有序的。那这样呢我们再从右侧去取的时候，利用 `RPOP` 的时候，我们首先取到的就是第一个存进去的 message 1，是不是就实现了先进先出的效果？哎就符合了队列的要求了。

```text
   LPUSH q1 1                LPUSH q1 2              BRPOP q1 20
        │                        │                        │
        ▼                        ▼                        ▼
   ┌─────┬─────┐           ┌─────┬─────┬─────┐        取走的是 1
   │  1  │     │    ───▶   │  2  │  1  │     │   ◀──────────────
   └─────┴─────┘           └─────┴─────┴─────┘           取出后队列变成
        ▲                                                  ┌─────┬─────┐
        └────── 入口（LPUSH）                    出口 ────▶ │  2  │     │
                          （RPOP / BRPOP 从右侧取）          └─────┴─────┘
```

读图要点：左侧进、右侧出，先进先出；如果出队口和入队口是同一个方向，那就成了栈，先入后出，那就不是队列了。

#### BRPOP 把阻塞补回来

不过呀，大家需要注意的是，我们的 Java 代码将来去获取消息的时候，肯定是要循环不断地去获取的。那如果有消息了，我把它取出来；如果我把这里面消息都取完了，我再去取的时候会怎么样啊？

那我们的期望应该是：当我们再去获取的时候，如果没有消息，是不是应该卡在那里，或者讲阻塞在那里，等待到有消息了你再给我。也就是说实现一种阻塞队列的效果。

但是呢，我们的 `LPOP` 和 `RPOP` 这两个命令可无法做到阻塞式，也就是说它是非阻塞式的。当没有消息的时候，如果你去获取，它会直接返回 nil。所以要想实现阻塞队列，我们必须用 `BLPOP` 和 `BRPOP` 来代替这两个命令。那这两个命令的作用呢？其实就是带了一个 B，block，也是阻塞。

下面我们来演示一下。我们打开控制台，我提前准备好了两个控制台窗口，首先我们先去建立一下 Redis 连接，通过 `redis-cli`，然后输入密码 `123321` 就可以了。

我们先看一下帮助文档，通过 `HELP` 看一下这个 List 结构的一些常见命令。第一个呢就是这个 `RPOP`，它就是 "Remove and get the last element in list"，也就是说我移除并且获取列表的最后一个元素。所以说它不仅仅是把元素拿走了，而且还把它从队列中移除了，那它一旦移除了以后，别人还能不能看啊？就不能了。但是呢它没有阻塞效果。

我们再来看一下 `BRPOP`，这里也说了，移除并且获取最后一个元素，或者会阻塞等待，直到有一个元素可用为止。所以呢它就是带有阻塞效果的这种方式。

来，不废话，下面我们演示一下。首先呢我们在消费者这里去做一个监听，通过 `BRPOP` 监听一个名为 `q1` 的队列，然后指定一个监听的阻塞时间吧——不能无限制地去等待嘛，对不对？比如说等 20 秒，20 秒等不到我就结束。然后我们在这一侧呢，我们就往里面存元素。存元素我们就要用 `LPUSH`，就是入口出口不在同一侧嘛。

```text
  # 1. 连接 Redis
  redis-cli
  AUTH 123321

  # 2. 看命令帮助
  HELP

  # 3. 【消费者窗口】阻塞式地从队尾取，最多等 20 秒
  BRPOP q1 20

  # 4. 【生产者窗口】消息从左侧入队
  LPUSH q1 1
  LPUSH q1 2
```

我们看这边是不是立马拿到了一个元素了？那这个时候我们里面其实还有一个元素 2，那我如果再次来获取，是不是立马就拿到了？因为有元素嘛。但是如果你再次获取，它又卡住了，又没有元素了——这就是所谓的 `BRPOP`。

那利用这个 `BRPOP` 或者是 `BLPOP` 结合我们的 `LPUSH`，我们其实就能实现阻塞队列的效果了，对不对？有元素我就取，没元素我就等。

### List 方案的优点，和它躲不掉的两个硬伤

那大家也能够看出来了，其实这种方式就是利用了 Redis 里面的 List 来模拟了 JDK 里面的阻塞队列。那相比于 JDK 的对象，它有什么好处呢？

首先它是在 JVM 以外的独立的存储，那它不依赖于 JVM 内存，所以他不用担心存储上限的一个问题。第二数据安全，我们的 Redis 是支持数据持久化的，所以一旦数据存储到队列里，我们完成了持久化，数据就不会丢失了，哪怕你宕机也好，数据是不是依然还在。所以从这一点讲，安全性是不是会比 JVM 里面的阻塞队列要好。

所以说呢它可以认为是一个基本满足了消息队列里边需求的这样一个模式了。但是呢，它并不是完美的。我们来总结一下基于 List 结构的这个方案，它有什么样的优缺点呢？

| 维度 | 结论 |
| :--- | :--- |
| 内存上限 | 存储在 Redis，不受 JVM 内存上限的限制，解决了之前的内存限制问题 |
| 数据安全 | Redis 支持持久化，服务宕机、重启数据依然在，解决了之前的数据安全问题 |
| 消息有序性 | 它是个队列，先进先出按顺序来，这一点做到了 |
| 消息丢失 | ✘ 躲不掉，`pop` 是 remove-and-get，拿到即出队 |
| 消费模型 | ✘ 只能单消费者，一条消息被拿走就从队列里移除 |

它的优点就是：第一利用 Redis 存储，不受 JVM 内存上限，限制了之前的内存限制的问题；第二持久化，数据安全性有保障；另外它还可以保证消息的有序性，毕竟它是个队列嘛，先进先出是按照顺序来的，这一点它做到了。

那缺点是什么呢？

**第一个缺点是消息丢失的问题。** 我们知道这个 `pop` 命令它是 remove and get，也就是会把它直接从队里移除。消息一旦取走了，你自己拿走了，但是你没处理，结果你自己挂了，那这个时候其他消费者能不能拿到？拿不到，所以就出现了丢失的情况，这个情况是没有办法避免的。

举个数：现在假设说我从 Redis 的队列里取到了一条消息，取出来以后，如果还没来得及处理，我就挂掉了或者出现异常了，那这个消息是不是就丢失了？其他消费者能不能拿到？拿不到，所以就出现了丢失的情况。

**第二个缺点是它也只是这种单消费者。** 什么意思呢？就是我发送的消息，一旦有一个人拿走了，就从队列移除了，其他的消费者还能不能拿就拿不到了。也就是它没有办法实现一条消息被很多人消费的这样的需求。有的时候我们是会有这样的需求，但是在这里 List 结构就不支持。

这就是基于 List 结构的消息队列的两个缺点。

## Redis 的三种消息队列：Pub/Sub、Stream 单消费与消费者组
> 对应块：BLK22 | 覆盖分集：P74-P76 | 块标题（分集名）：《实战篇-27.Redis消息队列-PubSub实》

上一节我们拿 List 做了一个简易消息队列，能阻塞地取消息、能持久化，够用。但它有个绕不开的短板：**一条消息只能被一个消费者拿走**。生产者发出去，谁先 `POP` 到就是谁的，第二个消费者连残影都看不到。

今天我们把 Redis 里三种做消息队列的模型一次讲完：先看第二种 Pub/Sub 怎么做到多消费者，再看第三种 Stream——它先是单消费模式，然后升级成消费者组，把单消费模式留下的漏读坑一个个堵上。

---

### Pub/Sub：像订报纸一样的发布订阅

Pub/Sub 是两个单词的缩写，`publish` 发布、`subscribe` 订阅，Redis 2.0 之后引入的这种消息传递模型。

> **定义**：Pub/Sub 基于「频道」这一订阅机制。一个消费者可以订阅一个或多个 channel（频道），生产者每向某个 channel 发消息，所有订阅了这个频道的消费者都会收到。

怎么理解这个模型？**就相当于你订报纸**。你告诉邮局"我要看体育频道"，邮局给你送来了一份；别人订的是财经频道，收到的就是另一份内容。频道是什么？频道就是频道——你喜欢收听哪个频道，你订阅一下，将来生产者每当向这个 channel 发消息，所有的订阅者都能收到相关消息。

这里和 List 的差别一下就显出来了：**List 模式下，一个生产者可以把消息发给一个消费者；Pub/Sub 模式下，一个生产者可以发送消息给多个消费者。**

#### 最常用的三个命令

```bash
SUBSCRIBE channel [channel ...]   # 订阅一个或多个频道
PUBLISH channel message           # 向某个频道发送一条消息
PSUBSCRIBE pattern [pattern ...]  # 按通配符订阅频道
```

`SUBSCRIBE` 后面跟的 `channel` 就是频道名称，可以一次跟多个，也就是说你可以同时订阅多个频道；不同消费者可以订阅相同频道，也可以订阅不同频道。

`PUBLISH` 顾名思义就是发送，向一个 channel 发送一条消息。

`PSUBSCRIBE` 是新东西，`p` 就是 `pattern`。订阅的时候后面跟的不再是频道名称，而是 **pattern 通配符**——订阅的是跟通配符格式匹配的所有频道，所以一条命令就等于订阅了多个频道。

Redis 官网上对通配符给出了明确说明，一共三种：

| 通配符 | 含义 | 例子 |
| --- | --- | --- |
| `?` | 一个字符 | `h?llo` 可以是 `hello`，也可以是 `hxllo` |
| `*` | 零个或多个字符 | `h*llo` 可以是 `hllo`（零个），也可以是 `hello`、`hellooooo`（多个） |
| `[…]` | 中括号内指定的字符之一 | `h[ae]llo` 是 `hello` 或 `hxllo`，但不是 `hillo` |

顺手在官网上查命令的时候别只翻命令列表——Stream 那块官网还专门写了一篇英文教程（Redis Streams），想深入了解 Stream 底层实现和用法的，到时候用谷歌翻译一下自己看就行。

#### 一张图看懂消息怎么分发

消费者一用 `SUBSCRIBE order.q1` 精确订阅，消费者二用 `PSUBSCRIBE order.*` 订阅所有以 `order` 开头的频道——`*` 是零个或多个，所以消费者二订阅的范围**包含了**消费者一订阅的那个频道。

```text
                    PUBLISH message1
                            |
                            v
                  +-------------------+
                  |     order.q1      |
                  +-------------------+
                      /            \
     SUBSCRIBE order.q1        PSUBSCRIBE order.*
             |                          |
     +---------------+          +---------------+
     |   消费者 1     |          |   消费者 2     |
     +---------------+          +---------------+
```

读图：生产者往 `order.q1` 发一条消息，精确订阅的消费者一收到，通配订阅的消费者二也收到——**两个人都能拿到**。

那如果生产者是发到 `order.q2` 呢？

```text
                    PUBLISH message2
                            |
                            v
                  +-------------------+
                  |     order.q2      |
                  +-------------------+
                            |
                     ( 无人精确订阅 )
                            x
                     消息当场丢弃，无人可补
```

`order.q2` 符合 `order.*`，但不符合 `order.q1`，所以**只有消费者二收到**。

> **结论**：Pub/Sub 这种模式非常灵活——一条消息既可以被多个消费者拿到，也可以只被某某一个消费者拿到。这就是它相比 List 结构的优势之处。而且不同生产者往相同频道发消息也是可以的，所以它是**多生产、多消费**的。

#### 亲手演示一遍

打开三个控制台，上面一个是生产者，下面两个是消费者。

消费者一：`SUBSCRIBE order.q1`，消费者二：`PSUBSCRIBE order.*`。执行完你会发现两边都**卡在那里不动了**——`Reading message...`，正在等着要读消息。**这种模式天生就是阻塞式的。**

然后生产者这边发消息：

```bash
# 情况一：发到 order.q1
PUBLISH order.q1 hello
```

两边同时收到，返回值是 `2`，说明有两个接收者。因为 `order.q1` 既符合消费者一的 `order.q1`，也符合消费者二的 `order.*`。

```bash
# 情况二：发到 order.q2
PUBLISH order.q2 hello2
```

这次只有消费者二收到，返回值是 `1`，因为 `order.q2` 符合 `*` 但不符合 `order.q1`。

#### 三个要命的缺点

优点说完，该说代价了。Pub/Sub 的缺点**比较多**。

**第一，不支持数据持久化。** 为什么 List 支持、Pub/Sub 不支持？因为 List 本质上根本不是一个消息队列，它就是一个链表，目的本来是做数据存储，只不过我们把它当成消息队列来用了。而 Redis 里所有拿来做数据存储的数据结构都支持持久化。Pub/Sub 本身设计出来就是用来做消息发送的，因此当你发一条消息时——**如果这个消息没有任何人订阅，这个频道没有别人订阅，这条消息直接就丢失了。**

```bash
# 两个消费者都停掉之后
PUBLISH order.q1 hello     # 返回值 0
PUBLISH order.q2 hello2    # 返回值 0
```

返回 `0` 就是"没有任何人收到，这条消息丢了"。这时候你哪怕再把消费者启动起来，也没有任何意义了——消息已经没了。你再用 `PSUBSCRIBE order.*` 去搜，搜不到，以前发的不算了。

有人收就收，没人收直接完了，不要了。**所以这是它最大的问题，连消息丢失都谈不上，因为它压根就不保存。**

**第二，正因为不保存，消息堆积有上限。** 这怎么还能堆积？不是说不保存在内存中吗？是不在 Redis 中保存——当有消费者在监听时，消息会缓存在**消费者客户端**那里。如果消费者处理一条消息要耗时一秒，这一秒内又来了十几条消息，这些消息全都缓存在客户端，而客户端这个缓冲空间是有上限的，超出了就丢。

**第三，安全性没有保障。** 发完了没人收直接丢，服务重启、宕机数据也没了。

> **结论**：如果对可靠性要求较高，不建议使用 Pub/Sub 这种消息队列，还不如老老实实用我们的 List。那有没有更加完美的消息队列模型呢？有。

---

### Stream：专门为消息队列设计的数据类型

有。这就是 Redis 5.0 之后引入的全新数据类型——**注意了，是一种新的数据类型**，和之前讲的 String、List、Sorted Set、Hash 类似，是用来做数据存储的，**所以它支持数据持久化，数据安全这一块是绝对有保障的**。

而且它和 List 有本质区别：这种数据类型是专门为消息队列设计的，它提供的命令、各种功能非常适合做消息队列，可以说是 Redis 里提供的**功能最完善的消息队列**。

到官网上找到 Streams，这一堆就是 Stream 有关的全部命令，非常多。但最核心的其实就两件事：消息的**发送**和**读取**。发送就是往队列里添一条消息，读取就是读一条消息。

#### 往队列里添消息：XADD

XADD 的参数列表非常长，我们逐个拆开看：

```bash
XADD key [NOMKSTREAM] [MAXLEN [~|=] count] [ID id] field value [field value ...]
```

- `key`：我们这个队列的名称，你想往哪个队列里填就填哪个，没什么好解释的。
- `[NOMKSTREAM]`：队列不存在时要不要自动创建。`MK` 就是 `make` 创建的意思，默认是自动创建；你要是给了 `NOMKSTREAM`，那就是不创建。中括号括起来的都是可选参数，所以一般情况下这个完全不用管。
- `[MAXLEN … count]`：`max` 就是最大长度，设置的是消息队列中最大的消息数量。假如设成 `1000`，将来存消息超过 1000 条、又一直没有消费者处理，一些旧的消息就会被剔除掉。不给值就是说不设置上限。
- `[ID id]`：指定消息的唯一 ID。ID 就是**标识**，每一条消息都要有自己的唯一标识。Stream 底层会基于这个 ID 形成一个树的结构，方便将来查询消息，所以 ID 非常重要。给 `*` 就是由 Redis 自动生成，你不用管；当然也可以自己指定。

  自己指定的话一定要遵循格式：ID 由两部分组成，中间是个杠，**前半部分是毫秒时间戳，后半部分是递增的数字**。

  ```text
  1650000000000-0     ← 某一毫秒的第 1 条
  1650000000000-1     ← 同一毫秒内继续递增
  1650000000000-2
  1650000001000-0     ← 到了下一毫秒，序号归零
  ```

  同一个毫秒内添加的消息，前边时间戳一样、后边数字不断递增；不同毫秒添加的，毫秒值不一样，后边就是 `0`。我建议大家都用 `*`，让 Redis 自动生成。

- `field value`：这就是存到消息里边的消息体。消息体被称为 **entry**，一个键值对称之为一个 entry。也就是说一条消息 ID 里面可以包含**多个 entry**，也就是多个键值对。

可选参数太多，所以最简的用法就是这样：

```bash
# key 是队列名，* 表示 id 由 Redis 自动创建，后面是消息体
XADD s1 * k1 v1
```

执行完它会**立即**返回一个 ID，这就是 Redis 帮你自动生成的这条消息的唯一标识。然后我们可以查一下队列里有多少条消息：

```bash
XLEN s1
```

返回 `1`，说明队列里现在只有一条消息，消息发出去了。

#### 读消息：XREAD

```bash
XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]
```

`COUNT` 顾名思义就是一次最多读多少条，可以一次读多条也可以一次读一条。

`BLOCK` 代表阻塞。**如果你不给它，就是不阻塞**——读取时有消息就直接返回，没有消息就返回空。**给了 `BLOCK` 就不一样了**：有消息就返回，没消息就等着。后面跟的 milliseconds 是毫秒数，指定等待时长；**如果等待时长给 `0`，那就是永久等待，一直等下去。**

`STREAMS key … id …` 这两个是一个整体，意思是"你要读取的是哪一个 Stream、哪一个队列当中的消息"。这里的 key 就是队列名称，而且**可以指定多个**，也就是我可以同时监听多个队列。

后面这个 id，就是"我从第几个消息开始读"。有两个特殊的值：

- `0`（严格说是 `0-0`）：代表我从这个队列中的**第一条**消息开始读；
- `$`：**从最新的一条消息开始**，也就是队列当中最后一条。

一般情况我们就指定 `$`，读最新的，一直往后读。

#### 阻塞读取：把消费者写出来

有了阻塞功能，Java 代码就可以这样写了。我们开两个消费者，先在消费者一上试：

```bash
XREAD COUNT 1 STREAMS s1 0
```

读到了 `k1 v1`。那消费者二能不能也去读一次？**能。** 同一个消息可以读两次，两个消费者都能读。我再到消费者一这里读一次——**还能读到**。

> **提示**：在 Stream 这种数据类型里，一条消息你读完了**不会删除**，它是永久存在于队列中的，你什么时候想读都可以来读，随时都行。

那么想读最新消息呢：

```bash
XREAD COUNT 1 STREAMS s1 $
```

没有返回内容。因为现在队列中的消息你都读过了，没有新消息。

那想**等待**最新消息怎么办？就得用阻塞的方式了：

```bash
XREAD COUNT 1 BLOCK 2000 STREAMS s1 $
```

最长等两秒。这时另外一个人发一条消息 `XADD s1 * k2 v2`——下边立马就收到了。这就是阻塞读取。

有了阻塞功能，代码就能这么写（伪代码）：

```java
while (true) {
    // 最多阻塞两秒，读最新消息
    Object[] message = redisTemplate.execute("XREAD COUNT 1 BLOCK 2000 STREAMS s1 $");
    if (message == null) {
        // 两秒已过还没有新消息，continue 下一轮循环
        continue;
    }
    // 拿到了就往下走，处理消息
    handleMessage(message);
}
```

这一条命令执行只有两种结果：要么两秒内来了新消息，这里有消息内容；要么超过两秒还没来，返回空。所以判断一下是否为空，为空就 `continue` 继续下一轮，不为空就处理消息，处理完再回来继续——这样就可以**永远监听我们的消息**。

#### 单消费模式最大的坑：漏读

但是！我要告诉大家，我们这个 read 方法有个小小的 bug。

问题出在把起始 ID 指定为 `$` 代表读取最新消息。什么是最新？就是队列当中的最后一条消息。

```text
t0  队列 s1 = [ k3 ]
    消费者 XREAD ... $  ->  读到 k3，开始 handleMessage()

    （处理过程中，生产方连发 k4、k5、k6）
        消费者线程正卡在 handleMessage 里，什么也没读

t1  队列 s1 = [ k3, k4, k5, k6 ]
    消费者处理完，进入下一轮
    消费者 XREAD ... $  ->  只拿到 k6

    k4、k5 呢？它们不是还在队列里吗？
    不在于 $ 只给你最后一条 —— 它们被跳过了。
```

我当场演示给你们看：先发一条 `k3 v3`，消费者确实读到了；但就在它处理的过程中，我连发了好几条 `k4 v4`、`k5 v5`，一下发了好几条。等它处理完进入下一轮，我再读取一次——**读不到**。中间这三条不在了。只有我再发新消息，它才能再看到新消息。

> **易错点**：单消费模式下用 `$` 循环监听，**中间的消息会被永久漏读**。这种方式看起来很完美，但它是不可靠的。

所以我们总结一下 Stream 单消费模式的几个特点：

1. **消息可回溯**：消息读完了不消失，永久保存在队列中，随时想看随时回去看。这是它的一个优势。
2. **消息可以被多个消费者读取**：因为消息不消失，谁都可以来读。张三读完了，李四也能读。
3. **消息可以阻塞读取**：这样我们就可以写出循环一直去读。
4. **消息有漏读的风险**：处理消息的过程中来了新消息我看不到，只能看到最后一条最新的那一条。

> **结论**：以上是 Stream 的基本玩法，属于**单消费者的玩法**。那如何解决消息漏读的问题？有没有更好的消息读取方案？靠消费者组。

---

### 消费者组：把漏读的坑彻底堵上

上一节课我们已经学习了 Stream 消息队列的单消费模式，在这种模式当中，如果我们利用 `$` 符号循环去获取队列中的消息，**有可能会出现漏掉消息的情况**。所以这节课我们继续学习一个新的消费模式，叫做消费者组，看一看能否解决这个问题。

消费者组的英文叫 `consumer group`，顾名思义，就是把多个消费者划分到一个组当中去，监听同一个队列。它有三个关键机制。

#### 消费者组的三个关键机制

**第一个是消息分流。** 队列中的消息会分流给组内的不同消费者，而不是重复消费，从而加快消息处理的速度。也就是说多个消费者只要在**一个组里**，他们之间就是一个**竞争关系**，凡是进入这个组的消息大家都可以去抢——这样处理消息的速度是不是就大大加快了，从一定程度上可以避免消息堆积的问题。

有同学问了：如果我就是想让这个消息被多个消费者消费怎么办？很简单，你只需要加多个消费者组就好了。

**第二个是消息标识。** 消费者组会维护一个标识，记录**最后一个被处理的消息**。

> **注意**：这里记录的不是最新的消息，而是**最后一个被处理的消息**。

就像我们看书的时候还夹了一个书签儿——我看到哪里了，这样下一次我再翻开这本书的时候，是不是立马就能找到，接着读？我们这里这个标识也是如此。如果消费者真的出现了故障或者宕机，或者在我处理的过程中又来了很多新消息，都没关系，因为有这个标识，我就能知道我上次读到哪了，下一次就可以接着读，这样就可以确保每一个消息都会被消费，**绝对不会出现漏掉消息的情况**。单消费时漏消息的这个问题，是不是就得到解决了？

**第三个是消息确认。** 消费者在获取消息以后，消息会处于一个 **pending 状态**，`pending` 翻译过来就是"待处理"的意思，并且会保存到一个 `pending list` 列表当中，可以认为就是一个未完成的消息。而当我们处理完了消息以后，还需要通过 `XACK` 命令来确认——当我拿到消息以后还不算完，我得处理完了，还得告诉 Redis 说"哎这事我给你办好了"，那 Redis 一旦看到你把消息处理完成了，它才会把这个消息标记成已处理，然后从这个 pending list 里移除。

这有什么用？**它可以解决消息丢失的问题。** 以前咱们讲过的消息队列模式当中，如果我们拿到这条消息但没来得及处理我就挂了，这个消息是不是就丢失了。但在这里不会：假设我现在拿到了一个消息，这个消息会处于 pending 待处理状态；如果此时出现故障比如宕机，那么这个消息**并不会消失**，而是会处于一个待处理状态待在这个列表里。下一次当我恢复以后，我只需要来到这个列表里看一看，这里面有的消息就是我上一次没处理完的消息，那我接着把它处理完了不就好了吗。

所以这个消息确认机制就可以确保：**只要我拿到了，那我至少会消费它一次**，绝对不会出现消息拿到了不消费的情况。

结合以上三个特征，还有之前讲的 Stream 本身的一些特点（比如可回溯等等），我们可以发现：**基于消费者组模型的 Stream 消息队列，可以说是一个功能非常完善的消息队列。**

#### 创建消费者组

和组有关的命令都以 `XGROUP` 打头，创建消费者组的是 `XGROUP CREATE`：

```bash
XGROUP CREATE key groupname id [MKSTREAM]
```

- `key`：我们这个队列的名称，你要在哪个队列里创建消费者组。
- `groupname`：组的名称。
- `id`：这个组监听消息时从哪儿开始监听。`$` 是从队列创建那一刻开始、也就是最新的（最后一个）消息开始；`0` 代表队列中的第一个消息，从头开始。

  我的建议是：创建这个组的时候，**如果队列中没有消息，或者队列中已经有很多消息而那些消息你又不想消费**，那你可以选择 `$`；**如果队列中已有的消息你还需要重新消费一遍**，那你就选择 `0`。这两个都是 OK 的。

- `[MKSTREAM]`：和 XADD 里说的一样，`MK` 就是创建 Stream、也就是我们的队列。创建消费者组时如果队列不存在，要不要创建？你给了就是自动创建；不给的话，当队列不存在时它就无法创建消费者组了。

来实际创建一下，我们之前不是有个队列 `s1` 吗：

```bash
XGROUP CREATE s1 g1 0
```

我们这个组就从 `0` 开始，也就是说这个队列中已经存在的消息我也要消费。这个消费者组就创建好了。

既然有创建，那当然也该有删除，这些指令同样以 `XGROUP` 打头，只不过后边的指令不一样：

| 子命令 | 作用 |
| --- | --- |
| `XGROUP CREATE` | 创建消费者组 |
| `XGROUP DESTROY` | 删除消费者组 |
| `XGROUP CREATECONSUMER` | 给组里面添加一个消费者（后面跟 consumer name） |
| `XGROUP DELCONSUMER` | 删除消费者 |

但一般情况下我们并不需要自己去添加消费者。因为当我们从这个组当中指定一个消费者并监听消息的时候，如果它发现这个消费者不存在，它就会**自动帮我们创建出来**。所以并不需要手动去创建。

#### 从组内消费：XREADGROUP

创建好了以后，该怎么样监听消息呢？从消费者组内读取消息叫 `XREADGROUP`——我们以前单消费的时候叫 `XREAD`，现在从组内消费就是 `XREADGROUP`。

```bash
XREADGROUP GROUP group consumer [COUNT count] [BLOCK milliseconds] [NOACK] STREAMS key [key ...] id [id ...]
```

除了前面 `GROUP` 往后这一段，后面的参数跟我们原来单消费时是一样的。多出来的是这几个：

- `group`：顾名思义你是从组消费，那你告诉我你组是谁呀。
- `consumer`：你是哪个消费者呀，你得有一个自己的名称。不存在会自动创建，所以我们将来不用手动去创建消费者。
- `COUNT`：指定我查询的数量，比如给 `1` 就是我一次查一个。
- `BLOCK`：阻塞。不给就是非阻塞——查到了我就返回，查不到我就返回空；给了值它就会等待，后面的 milliseconds 就是我们等待的毫秒值。
- `NOACK`：我们有个消息确认机制，拿到消息以后处理完了一定要确认。但如果你这里给了 `NOACK`，代表**不用消费者确认了**，消息投递给消费者那一刻就自动确认，它根本不会进入 pending list。

  > **易错点**：`NOACK` 这个参数一般不建议大家去设置，都不要配就行。你想想：给了 `NOACK`，我们拿到了消息，结果我挂了，这个消息又没有进 pending list，将来是不是就出问题了？消息就丢了——因为压根不知道到底哪个消息失败了。

- `STREAMS key … id …`：最后一个 id，也就是起始 ID，**这个参数和单消费时不一样**。

##### 起始 ID：大写号和其他

单消费时可以给 `$`，这里**不是 `$` 了**。这里给什么呢？给 **`>`**。

> **定义**：在 `XREADGROUP` 里，`>` 代表**从下一个未消费的消息开始**。

> **易错点**：注意了，`>` 是从**下一个未消费的消息**开始，**不是从最新消息开始**。因为消费者组内会维护一个标记，记录上一次消费的是哪一个消息，因此当我们指定 `>` 时，它就会从那个标记的下一个消息开始读，确保所有消息都会被消费。**所以我建议大家使用 `>`。**

那除了 `>` 以外的 ID 呢？它们的含义不再是"下一个未消费消息"，而是**读 pending list 中已经获取了但未确认的消息**。

比如给 `0`，就是从这个 pending list 当中的第一个消息开始。我给 `0`，从 pending list 里读一个，消费了并且确认，那 pending list 里是不是就少一个？我下一次还给 `0`，是不是还是读到第一个未确认的？但跟上一个已经不一样了——之前那个已消费的已经从 pending list 里移除了。所以我永远给 `0`，是不是就可以一直读取 pending list 中未确认的消息，直到把 pending list 中的所有消息都处理完为止。

所以：**正常情况下给 `>` 读那些未消费的消息；如果出现了异常情况，我们再去 pending list 里读那些拿到了但未处理的消息。** 这就是我们这个 ID 配置的一个技巧。

##### 演示：谁消费谁

我们这个 `s1` 队列里已经有六条消息了，从 `k1` 一直到 `k6`。消费者一来读：

```bash
XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS s1 >
```

消费者名称随便给一个就行，反正不存在它也会帮我们自动创建。因为组内一条消息都没消费过，所以这次读到的一定是队列中的第一条消息 `k1 v1`。再来一次 → `k2 v2`。

现在消费者二也来读，这次把消费者名字改成 `c2`：

```bash
XREADGROUP GROUP g1 c2 COUNT 1 BLOCK 2000 STREAMS s1 >
```

它读到的是 `k3 v3`——**不是 k1**。

为什么？因为**在一个组内其实只有一个标记**，不管是谁消费的，只要消费到那里了，我就给你标记起来。消费者一消费了 k2，我标记起来，那么下一个消费者不管是谁，只要来消费，一定是从下一个消息、也就是 k3 开始。所以消费者二再来一次，得到的一定是 k4；这时候消费者一再读，一定是 k5。

#### 确认消息：XACK 与 pending list

好，但是大家别忘了——我们现在读了这么多消息，有没有确认过呀？**没有吧。这可不行。** 我们说过要读一个消息，一定要确认一个消息，代表你正常处理了。

确认用什么命令呢？`XACK`。我们可以通过 help 看一下：

```bash
XACK key group id [id ...]
```

`key` 就是队列名称，`group` 就是组名称，然后指定一个 id 代表你要确认哪一条消息——**mark a pending message as correctly processed**，把一个待处理的消息标记为已正确处理的消息，这样它就会从 pending list 里移除。

来试一下：

```bash
XACK s1 g1 k1id k2id k3id k4id k5id
```

返回 `5`，说明这五条消息全部都确认掉了。

那有正常情况就有异常情况。比如我现在处理了一条消息 `k6`，**但是我出现故障了**——我拿到了一条消息 k6，结果我挂了，这条消息也没有执行 `XACK`。我们说了，它一定会进入 pending list。

##### 查看 pending list：XPENDING

这个命令叫做 `XPENDING`，参数还比较多，我们去官网看一下：

```bash
XPENDING key group [[IDLE min-idle-time] start end count [consumer]]
```

- `key`：队列名称；`group`：组的名称。
- `[IDLE min-idle-time]`：叫**空闲时间**，意思是获取消息以后到确认之前的这段时间。比如你给一个 `5000`，也就是说空闲时间超过 5000ms 以上的消息你才要，别的就不要了。
- `start` 和 `end`：起始范围。pending list 里边有很多很多消息，你告诉我你想获取的最小的那个 ID 和最大的 ID 是什么。官网给的例子里用的是 `-` 和 `+`，`-` 就是最小、`+` 就是最大，即最小到最大所有的 ID 我都要。
- `count`：你要获取的数量。
- `consumer`：你要获取哪个消费者的 pending list——**每个消费者都有自己的 pending list。**

我们回到控制台试一下，不给空闲时间，最小到最大取十个，消费者不指定：

```bash
XPENDING s1 g1 - + 10
```

返回的就是我们 pending list 中所有的未确认消息。现在就一条，因为我们总共只有一条消息没确认，别的都确认了。

##### 把 pending list 里的消息再读出来

怎么去读取 pending list 里的消息呢？其实前面讲过了：**当我们去读这条消息的时候，把 `>` 改成 `0` 或者改成任意都行。** 改成 `0`，它代表的含义就是读取 pending list 中的第一条消息。

试一下，是不是又一次拿到 k6 了？这样我就可以再次去处理这条消息。如果这次真的处理成功了，我是不是就可以去 `XACK` 确认这条消息了？确认成功。这时候我们再一次想去 pending list 里取，是不是就取不到了——说明所有的未确认消息、或者说异常消息，全部处理完成了。

#### 正常与异常交织的完整流程

把刚才命令行里走了一遍的东西合起来，这其实就是将来处理消息的一个完整流程：

```text
     读取：XREADGROUP ... STREAMS s1 >
                    |
             拿到消息了吗？
            no ──────┴────── yes
            │                │
       continue          处理消息
                            │
                ┌───────────┴───────────┐
                │                       │
             成功                  抛出异常
                │                       │
             XACK              消息滞留 pending list
                │                       │
                v                       v
         回到外层循环      读取：... STREAMS s1 0
                                        │
                                 拿到消息了吗？
                            no ──────┴────── yes
                                │                │
                          跳出内层循环        重新处理
                          回到外层循环              │
                                              成功 / 再次异常
                                                  │
                                             XACK / continue
```

读图：**正常**情况下，我们先用 `>` 的方式获取所有未消费的消息，拿到以后处理，处理完以后确认。**在确认的过程中如果出现了异常**，这个消息就会进入 pending list——在 Java 代码中体现出来的就是我们抛出了异常、被 catch 到了。这时你就不能放任不管，而是把最后的那个 ID 从 `>` 改成 `0`，这样就不再是取未消费消息了，而是取所有出现异常的消息，在 pending list 里的消息。把 pending list 里的消息拿出来处理，处理完成后确认掉，pending list 是不是就清空了？这时候再回头改成 `>` 去获取未消费消息，是不是又回归正常了？

现在整个队列当中的所有消息是不是全部处理完了？那这时候如果我再次用 `>` 这种方式阻塞两秒钟去读，还有没有消息？没有了。它就会阻塞，等两秒，两秒以后还没有消息，返回空，就结束了。

#### 落到 Java 代码里的写法

刚才呢我们是基于命令行的方式演示了一下如何正确地处理消息，但这个流程因为是命令行方式，比较抽象，转换成 Java 代码以后又会变成什么样子呢？我提前准备好了一段伪代码，我们一起来看：

```java
// 外层：循环往复地获取消费者组中的消息
while (true) {
    // 读取组 g1，指定消费者名称，读一条，阻塞两秒，起始 ID 是 >
    Object[] message = executeXREADGROUP("GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS s1 >");

    // 为空说明现在没有消息，继续下一次循环等待就行了
    if (message == null) {
        continue;
    }

    try {
        // 拿到消息肯定去处理
        handleMessage(message);
        // 处理的过程中如果没有问题，完成了一定要做 ACK，
        // 消息就会从 pending list 里移除
        executeXACK("s1 g1 " + messageId);
    } catch (Exception e) {
        // 抛出了异常，因为没有做 ACK，
        // 消息依然留在 pending list 当中，这时候我们就去处理 pending list
        while (true) {
            // 注意：这一次读取，把 > 替换成了 0，
            // 代表读取的是 pending list 里边出现了问题的消息
            Object[] pendingMessage = executeXREADGROUP("GROUP g1 c1 COUNT 1 STREAMS s1 0");

            // 取不到了，说明处理完了，跳出内层循环回到外层
            if (pendingMessage == null) {
                break;
            }

            try {
                handleMessage(pendingMessage);
                // 处理成功了，确认之后消息就被移除了
                executeXACK("s1 g1 " + pendingMessageId);
                break;
            } catch (Exception ex) {
                // 这次处理又抛异常，它依然是未确认、依然在 pending list 里，
                // continue 再循环一次去 pending list 里取
                continue;
            }
        }
    }
}
```

这里有个细节我特意留了注释：**内层循环取不到消息才会跳出去**。因为你出了异常，pending list 里一定有消息，所以第一次肯定取得到；处理成功了确认掉、消息被移除，下一次就取不到了，于是跳出内层循环，回到外层循环继续正常流程。但如果这次处理又抛异常了，`continue` 再次去 pending list 取，因为这次处理又出异常，它依然是未确认、依然在 pending list 里——**这个循环就会一直循环一直循环，直到这个消息处理成功为止。**

有人说了，我就是不成功，试了几千次都不成功，再怎么办？这个时候你其实可以人工介入了，可以去告警。如果这个消息出现长久的问题，你就可以警告了，也是没问题的。

所以大家可以想象的是，基于这样一种模式——正常情况下我一定确认，异常情况下我再去 pending list 读一次、再确认——**可以确保我们消息至少被消费一次**。

### 三种模式怎么选

到这里，Redis 的三种消息队列我们全部讲完了，做一个总结和回顾。三种分别是 List、Pub/Sub 和 Stream 模式。

**List 模式**，其实就是利用 List 这种数据结构去模拟消息队列，从而实现消息队列效果的。因为它本身就是一种数据存储的模式，所以它是支持持久化的；阻塞读取它也是支持的，它里面有 `BLPOP`、`BRPOP` 和 `BLMPOP` 都是支持阻塞的。它的存储上限其实就是 Redis 对于 List 这种数据结构的内存上限，不过因为 List 可以有多个消费者同时去取，处理速度还是可以的，所以堆积这一块还是有办法去解决的。**消息确认机制它没有**——因为它本身不是一个消息队列，它只是用来做数据存储的，你拿了以后你怎么处理它都不管，反正你拿完它就移除掉了。正因为此，它的**回溯也是不支持的**。

**Pub/Sub 模式**，其实还不如我们的 List。首先不支持持久化，数据丢了就是丢了，服务重启、宕机都会导致数据丢失。那阻塞读取呢倒还好，它还是支持的，因为它本身是发布订阅这种形式嘛。消息堆积这一块它就更差了，因为它本身没有存储能力，直接就是一个通道帮你把消息发过去的，消息呢最多是在消费者这里做一个缓冲，而这个缓冲的空间也是非常有限的。消息确认机制没有，消息你发出去以后如果没有人收直接就扔了不管了，回溯也不支持。**功能是最差劲的。**

**Stream 模式**，基本上各种功能都有。消息持久化没问题，消息阻塞读取也 OK，消息堆积也不用太担心，最多的是受限于队列长度——如果你队列不设上限，其实能够存储的空间还是比较多的。并且因为它可以利用多消费者去消费（消费者组），所以消息处理速度也非常快，尽可能地去减少堆积。消息确认机制也是有的，利用这种 ACK 的方式、再利用 pending list 确保消息至少被消费一次。消息也是支持回溯的。**可以说它的功能非常非常强大。**

| 能力 | List | Pub/Sub | Stream |
| --- | --- | --- | --- |
| 数据持久化 | 支持 | 不支持 | 支持 |
| 阻塞读取 | 支持（`BLPOP`/`BRPOP`） | 支持（订阅端阻塞） | 支持（`XREAD` 的 `BLOCK`） |
| 消息堆积 | 受 List 内存上限约束，多消费者取可缓解 | 最差，仅消费者端有限缓冲 | 受队列长度上限约束，消费者组可分流 |
| 消息确认 | 无 | 无 | 有（`XACK` + pending list） |
| 消息回溯 | 不支持（取出即移除） | 不支持 | 支持 |
| 漏读风险 | 无 | 无（但会丢消息） | 单消费 `$` 有，消费者组无 |

消费者组模式还可以再单独总结一下：它**肯定具备 XREAD 单消费模式的所有优点，并且还弥补了它的一些缺点**——消息可回溯（别的组可以来拿；同一组内的消费者之间是**竞争关系**，好几个人一起抢，处理速度肯定快，可以避免消息堆积）、可以阻塞式地循环读取以避免 `while` 的盲等、没有消息漏读的风险（因为组内会标记上一次消费到哪里了）、还有消息确认机制确保消息至少得消费一次。

> **结论**：如果说我们要在 Redis 这三种消息队列里选一种，我肯定推荐大家使用 **Stream** 这种模式。

> **提示**：但是如果你们公司的业务比较庞大，对于消息队列的要求更加严格，那我建议还是使用更加专业的消息队列，比如 RabbitMQ、RocketMQ 等等。这是因为：我们的 Stream 虽然支持消息的持久化，但这种持久化是依赖于 Redis 本身持久化的，而 Redis 的持久化其实也不能保证万无一失，还是有丢失风险的；而且我们的这种消息确认机制只支持消费者的确认机制，而不支持生产者确认机制——那如果生产者在发消息的过程中丢失了，又该怎么办呢？另外还有消息的事务机制、在多消费者下的消息有序性等等，这些问题都需要更强大的消息队列去支持。

不过如果我们是一些中小型的企业，对队列的要求并没有那么多，事实上 Stream 已经能够满足我们的业务需要了。

理论上的东西我们就说到这里。下节课我们就带着大家利用 Java 代码，来实现一下基于 Stream 消息队列的**异步秒杀**。那我们下节课再见。

## 用 Stream 队列重做异步秒杀，顺便开一个新功能
> 对应块：BLK23 | 覆盖分集：P77-P78 | 块标题（分集名）：《实战篇-30.Redis消息队列-基于Strea》

之前咱们做异步下单，用的是阻塞队列：Lua 脚本只负责判断抢购资格，判断通过以后，Java 代码再拿着订单信息往阻塞队列里塞。

这次换成 Stream，我一开始想的是"不就换个容器呗"，但写着写着发现有个地方可以做得更好——发消息这件事本身，就可以直接塞进 Lua 脚本里干完。Java 代码要做的事情一下少了一大半，还少了一次 Java 和 Redis 之间的往返。

所以这一篇干两件事：把秒杀从阻塞队列完整改造成基于 Stream 的异步秒杀，然后把下一个新功能「达人探店」的第一小节写完。

---

### 先把队列和消费者组建起来

需求很简单，就一条：创建一个 Stream 类型的队列，名字就叫 `stream.orders`。

> **提示**：这个名称没什么特殊的，纯粹是为了方便我们看出来它跟哪个业务有关。大家完全可以根据自己的业务去命名。

这里有个要先想清楚的问题：这个队列是用 Java 代码创建，还是用命令行创建？

答案是命令行。队列只需要在一开始的时候创建一次，创建完就再也不用管了，没必要为此专门写一段 Java。所以直接打开控制台，一条命令搞定。

创建队列用的是 `XGROUP`，它是专门用来操作消费者组的。我们这里不只要建队列，还要建组——将来我们是按组消费的。

```bash
XGROUP CREATE stream.orders g1 0 MKSTREAM
```

别忘了后面的 `MKSTREAM` 参数，这个参数的意思是：创建消费者组的时候，如果队列不存在，它会自动帮我们把队列和组一起创建了。

> **结论**：`XGROUP CREATE` 加上 `MKSTREAM`，一条命令完成两个动作——建队列 + 建组。

参数逐个看：

- `stream.orders`：队列名称，就是我们刚才说的那个；
- `g1`：消费者组名称，这里就叫 g1；
- `0`：起始 ID。咱们这个队列是全新的，消息一条都没有，完全可以从零开始读；
- `MKSTREAM`：队列不存在就自动建。

执行完，队列和消费者组就都创建好了。接下来就可以放心去写代码。

---

### 让 Lua 脚本顺手把消息发出去

改造点有两处：Lua 脚本本身，以及调用它的业务代码。

#### 脚本要多接一个订单 id

之前的 Java 代码调这个 Lua 脚本，只传优惠券 id 和用户 id 两个参数，脚本判断有没有抢购资格。现在要往 Stream 里发消息了，消息里必须带上订单的信息，而订单信息是三个东西：`voucherId`、`userId`、`orderId`。

那问题来了——为什么不在 Lua 脚本里直接发这条消息？这样 Java 代码要做的事情更少，还少了一次 Java 和 Redis 之间的交互，效率不是更高吗。

所以说，向 Stream 队列发消息这件事，我们直接就在 Lua 脚本里做了。

先加参数。原来是 vuId、userId 两个，现在在末尾再加一个订单 id 变成三个：

```lua
local voucherId = ARGV[1]
local userId    = ARGV[2]
local orderId   = ARGV[3]
```

然后在判断有资格的地方（原来是判断成功就 `return 0`），加一个发消息的动作：

```lua
redis.call('xadd', 'stream.orders', '*',
    'userId',    ARGV[2],
    'voucherId', ARGV[1],
    'id',        ARGV[3])
```

`XADD` 的参数顺序要记住：**先队列名，再消息 ID，再后面一堆 key-value 对**。

我们的消息 ID 是不确定的，由 Redis 帮我们生成，所以这里直接写 `*`；再往后就是 `k1 v1 k2 v2` 这样的键值对。

#### 消息里那个订单字段，名字建议就直接叫 id

写到最后那个订单 id 的 key 时，我给大家一个建议：不要叫 `orderId`，直接就叫 `id`。

为什么呢？我们有一个实体类叫 `VoucherOrder`，代表我们的订单。将来传这些信息的目的，不就是为了创建订单吗。而在订单里，它的 id 本来就叫 `id`。

我们现在就叫 `id` 的话，将来往这个对象里存的时候是不是很方便？因为跟成员变量名称是完全一致的。

所以这个脚本里，我建议大家把 `orderId` 这个字段改成 `id`。这样三组参数就都传进去了。

#### Java 侧跟着改：订单 id 提前挪到脚本之前

回到秒杀业务逻辑，因为目前那段代码还是把订单信息写入阻塞队列的，这一段要改造。做法很简单：把旧代码注释掉保留，然后在新代码的基础上改。

第一步，获取用户，没问题。紧接着执行脚本——脚本这边首先有变化了。

原来我们传两个参数，现在得传三个，除了优惠券 id 和用户 id，还有一个订单 id。那订单 id 在获取的时候是在下边的，现在需要把它挪走，挪到上面来，跟获取用户放在一起。拿到订单 id 以后，直接作为第三个参数传进去。

还有一个细节：

```java
execute(LUA_SCRIPT,
        Keys.empty(),
        String.valueOf(voucherId),
        String.valueOf(orderId),
        String.valueOf(userId));
```

> **易错点**：Lua 脚本里的参数都是字符串，所以 Long 类型的订单 id 要通过 `String.valueOf` 转成字符串再传。忘了这一步，脚本直接报错。

这样脚本就执行完了。它现在做的事情有两件：一是判断你的购买资格，二是把订单信息发送到消息队列。

所以我们可以认为这段脚本执行完（且结果是 OK），就代表两件事已经同时完成了：用户有购买资格，消息也已经发出去了。

那咱们的业务逻辑只要判断结果是 OK 的，是不是就可以直接往下走、直接返回了？后面还需要做那一堆动作吗？不需要了吧。

你看，业务是不是比以前简单了？因为事情都在脚本里完成了。执行效率上来讲，也比以前更强。到这儿，秒杀的基本流程就改造完成了。

### 消费者线程：从阻塞队列换成 Stream 读消息

改完发起方，还差另一半。到现在为止你只是实现了"判断资格 + 发消息"，紧接着你还得去收消息，对吧。怎么收？在项目启动时开启一个线程任务，获取队列中的消息去完成下单。

我们项目一启动时其实已经有一个线程任务了，但它目前做的事情是从阻塞队列里取东西。现在我们已经不再需要阻塞队列了，这一段逻辑直接把旧代码注释掉，重新写。

#### 整体的数据流向

```text
  用户请求
   │
   ▼
VoucherOrderServiceImpl.seckill()
   │  先生成 orderId
   │  执行 Lua 脚本（voucherId / userId / orderId）
   ▼
[Redis] Lua 脚本内原子完成
   │  · 判断抢购资格
   │  · XADD stream.orders * 写入订单信息
   ▼
[Stream] stream.orders
   │
   │  XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000
   │  STREAMS stream.orders >
   ▼
消费者线程（项目启动时开启）
   │  解析消息 → 创建订单 → ACK
   │  中途抛异常 → 不 ACK → 消息留在 pending list
   ▼
MySQL 订单表
```

这一段流程可能有点陌生，我们可以参考一下之前写的那个伪代码：进来以后循环 → 长时间监听队列获取消息 → 判断是否有消息 → 没有就继续下一次 → 有就处理（也就是下单）→ 处理成功以后做 ACK 确认。确认没问题，这条消息就彻底处理完了，不会再来了。

那如果抛了异常呢？一旦抛异常，这条消息就是未确认状态，未确认的消息就会进入 pending 列表。所以在异常当中，我们就去 pending 列表里取。

这就是整体流程。

#### 命令拆开看

获取队列中的订单消息，用的是 `XREADGROUP` 命令。完整长这样：

```bash
XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS stream.orders >
```

一段一段拆开：

- `GROUP g1 c1`：先告诉 Redis 你读取的是哪个组，比如我是 g1 组；然后是你的消费者叫什么名字，比如 c1。
- `COUNT 1`：你要读多少条消息，我读一条。
- `BLOCK 2000`：读的时候要不要阻塞，阻塞多久。两秒钟的意思是——读的时候如果没有消息，我就等，最多等两秒钟，超过就直接返回结束，返回一个空。
- `STREAMS stream.orders >`：告诉它读的是哪个 Stream 队列，队列名后面是读取标识。

> **注意**：最后这个 `>` 代表读取最近一条未消费的消息。另一个标识 `$` 代表的是最新的消息，用的是 `ReadOffset.latest()`。咱们要的是 `>`。

消费者名字这里我们先写死成 `c1`。将来应该是配到配置文件里的，因为启动多节点的话，消费者名字应该有多个，这样才不冲突。

#### Java 里这三个片段各对应一个类

如果用命令，上面一条就完了。但我们现在要用 Java 代码。RedisTemplate 已经把 Stream 的所有操作都封装到了对应的操作对象里——之前玩字符串是 `opsForValue`，哈希是 `opsForHash`，Set 是 `opsForSet`，那玩 Stream 流其实就是 `opsForStream`。

它里面没有单独提供 read group，而是直接给了一个 `read`，但这个 read 的参数非常多，我们得把它看成三段来理解：

| 命令里的这一段 | 对应的 Java 类 | 我们填什么 |
| --- | --- | --- |
| `GROUP g1 c1` | `Consumer` | `Consumer.from("g1", "c1")` |
| `COUNT 1 BLOCK 2000` | `StreamReadOptions` | `StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2))` |
| `STREAMS stream.orders >` | `StreamOffset` | `StreamOffset.create(Q_NAME, ReadOffset.lastConsumed())` |

消费者这块有个小细节容易绕：它并没有写成 `readGroup`，参数里先传的就是 consumer。组其实是消费者的一部分信息，所以在这里统一叫 Consumer 了，组的名称作为消费者的名称一起传进去。`Consumer` 还有一个静态方法叫 `from`，把 group 和 name 传给它就行了——g1 是组，c1 是消费者名，这俩参数刚好对住。

> **易错点**：`Consumer` 要找 Spring 相关的那个（`org.springframework.data.redis.connection.stream.Consumer`），不是 Lettuce 里的。找错了类就编译不过。

读取选项这块，我们首先用 `empty()` 创建一个空的读取选项，紧接着再指定：`count(1)` 我读一个，`block(...)` 阻塞多长时间。

这里要注意，阻塞时间接收的是 `Duration`，它叫"周期"，里面可以传很多带有时间单位的值——天、小时、毫秒、秒、纳秒等等都可以。在这里我们肯定是秒，那就写最多等两秒。

最后一段是队列名加读取标识，它叫 `StreamOffset`，就是偏移量，也就是你读取的位置。它有一个 `create` 方法帮我们创建，第一个要指定的是 Stream，也就是你的队列名称。队列名我们可以提前在外面定义成常量：

```java
private static final String Q_NAME = "stream.orders";
```

第二个参数是读取标识，就是说你读到哪里。这里同样是有枚举的 `ReadOffset`：`lastConsumed()` 就是我们刚才说的 `>`，代表最近一条未消费的消息；`latest()` 是 `$`，代表最新的消息。我们肯定选前者。它是静态常量，指向的确实是这个大括号大于号。当然如果你不想用它，也可以自己 new 一个，也没问题的。

#### 返回的是 List，要判断有没有读到

到这，read 需要的信息就全部指定出来了，就可以拿结果了。这个结果返回的是一个 List。

> **提示**：为什么返回的是 List？因为你的 count 值不一定是一，可能是 1，可能是 2，可能是多个。返回 List 就是为了表示"我可能读到多条"。所以我们在这个地方就需要判断它是否获取成功，也就是判断这个集合有没有数据。

```java
List<MapRecord<String, Object, Object>> messages = stringRedisTemplate.opsForStream().read(
        Consumer.from(GROUP, CONSUMER),
        StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
        StreamOffset.create(Q_NAME, ReadOffset.lastConsumed()));

if (messages == null || messages.isEmpty()) {
    // 没有消息，继续下一次循环
    continue;
}
```

如果为空，就证明这次读取失败了，那我们干什么？继续下一次循环，`continue`，我再来读一次，看有没有。

代码能走到这，就证明消息是有的，说明有订单要处理，我们就可以去处理这个订单了。但是要处理订单，我是不是得先把它从 list 里取出来？所以这个地方其实要多一步，就是去解析消息中的订单信息。

它是个 list，那就按照角标取。虽然这里是个例子，但我明确知道我只设置读一条，所以我直接取 0 位就好了。

#### 把 Map 还原成 VoucherOrder

大家会注意到，我们取到的是一个 `MapRecord`。为什么是 MapRecord？因为底层就是一个 Map。这个 record 的第一个东西就是消息的 ID——我们知道 Stream 消息队列里发的消息都会有 id。

那它后面为什么还有键值对形式呢？这是跟我们发的消息格式有关。我们用 XADD 发消息的时候，发的不就是键值对格式吗：`key value key value key value`。这里的 key 恰好就是我们 `VoucherOrder` 类的三个成员变量，value 就是对应的值。所以它返回的就是这样一种 Map 形式，它封装了一下。

- `record.getId()` 得到的就是消息 ID；
- `record.getValue()` 拿到的就是那个键值对的集合，所以是个 Map。

我们现在要做的就是把这个 Map 转成我们的订单对象。怎么转呢？我们 Hutool 工具类里有个 `BeanUtil.toBean(Map, Class, boolean)`，把 Map 给他，再给他一个对象——我们要转的对象是 `VoucherOrder`，然后告诉他如果出错了怎么办，出错要不要忽略，那我们就忽略，直接传 `true`：

```java
MapRecord<String, Object, Object> record = messages.get(0);
Map<Object, Object> map = record.getValue();

VoucherOrder order = BeanUtil.toBean(map, VoucherOrder.class, true);
orderService.createOrder(order);
```

拿到 order，完成下单不就 OK 了吗？

#### 处理完必须 ACK

最后还要去做订单确认。确认用的是我们之前讲过的 `XACK` 命令，这里边要传三个参数：第一个是队列名字 `stream.orders`，然后是你是哪个组，我们这里是 g1，最后是这个消息的 ID。也就是说你是哪一条消息已经被处理完了——你告诉它，它就会把这个消息从队列中移除（从 pending 列表中确认掉）。

用 Java 来表示，同样是用 RedisTemplate 的 `opsForStream`，这里边有一个叫 `acknowledge` 的函数，传三个参数：

```java
stringRedisTemplate.opsForStream().acknowledge(Q_NAME, GROUP, record.getId());
```

key 就是队列名，我们已经定义常量 `Q_NAME` 了；组叫 g1；消息 ID 我们可以直接从前面那个 record 里去取，`record.getId()` 就是消息 ID。

到这里，正常的处理流程就完整了：获取消息 → 判断有没有拿到 → 没拿到就继续获取 → 拿到了就处理、下单 → 下单完成之后 ACK 确认，搞定。

### 处理到一半抛异常的消息：pending list

上面讲的是正常情况。那还有出异常的情况呢？

一旦在处理消息的过程中抛了异常，我们要干什么？消息一旦异常，它就不会被 ACK 确认；没有被确认的消息其实就会进入 pending list。紧接着我们应该按照这个逻辑，去 pending list 里尝试取出来，然后再次去做处理。

所以在这儿我们可以封装一个方法，叫 `handlePendingList`，再次来处理这种异常的消息。就在当前这个内部类里创建它。

怎么做？流程其实很简单，跟上面那个 `while` 循环非常像：循环进来以后尝试去处理，处理的过程中判断一下这个消息有没有，没有的话就结束，有的话就继续。既然这么像，我们完全可以把那段代码抠一份放下来，然后改。

要改三个地方：

```java
private void handlePendingList() {
    while (true) {
        List<MapRecord<String, Object, Object>> messages = stringRedisTemplate.opsForStream().read(
                Consumer.from(GROUP, CONSUMER),
                StreamReadOptions.empty().count(1),           // ① 不需要 block
                StreamOffset.create(Q_NAME, ReadOffset.from("0"))); // ② 标识是 0
        // ③ 读到空要 break，不是 continue
        if (messages == null || messages.isEmpty()) {
            break;
        }
        MapRecord<String, Object, Object> record = messages.get(0);
        Map<Object, Object> map = record.getValue();
        VoucherOrder order = BeanUtil.toBean(map, VoucherOrder.class, true);
        orderService.createOrder(order);
        stringRedisTemplate.opsForStream().acknowledge(Q_NAME, GROUP, record.getId());
    }
}
```

逐条说清楚为什么：

- **不再需要 block 阻塞**。这个循环本身就是不停地取 pending 列表，阻塞在这里没有意义；
- **结束标识不再是 `>`，而是 `0`**。因为传 0 的时候，读的就不是消息队列了，而是 pending list。`StreamOffset.create` 里如果没有现成的标识（`ReadOffset` 里只有 `$` 和 `>`），我们就自己传，直接传 0 就行；
- **读到空是 `break`，不是 `continue`**。

第三条特别容易搞错。pending list 里的订单信息就是那些出现异常的消息。要是这里没读到，说明 pending list 里没有异常消息了——那还需要下一次循环吗？完全不需要了。你都没了，我还继续什么？应该是结束循环才对，`break` 跳出。这样结束了就会执行外面的逻辑，继续去处理正常的消息。

那如果这里边有消息，就按照正常逻辑去解析、得到订单、然后去处理订单，确认这一步跟以前一样，不变。

#### 处理 pending list 时又抛异常了，怎么办？

这个时候我是不是要调自己？调自己是不是就递归了？完全不需要。

同学们想想看，你一旦抛了异常，我这边就这样打印一下，然后直接结束，结束以后是不是又会进入下一次循环？又会去取，还是能够取得到的。所以这个地方不用去做递归。

但是你这里一抛异常又来一次死循环、又抛一层，是不是太频繁了？如果你担心这个太频繁，你可以稍微在这儿给它休眠一下，比如休眠 20ms 或者 50ms 都可以，这样我们执行的频率就没有那么高了。

#### 整个业务流程串起来

上面是代码，现在把整体流程串一遍。

```text
while (true)
   │
   ▼
读 stream.orders（标识 > ，阻塞 2000ms）
   │
   ├─ 没有消息 ──► continue（下次再来，反正会阻塞两秒）
   │
   └─ 有消息 ────► 解析消息 → 创建订单 → ACK
                   │
                   └─ 抛异常且不 ACK ──► 消息留在 pending list
                                         │
                                         ▼
                                         catch 中调用 handlePendingList()
                                         读 pending list（标识 0，不阻塞）
                                         │
                                         ├─ 没有异常消息 ──► break（彻底结束）
                                         │
                                         └─ 有异常消息 ────► 解析 → 下单 → ACK
                                                             │
                                                             └─► 回到循环开头，一直读到 pending list 清空
```

我一上来，尝试从消息队列中读取消息。可能有可能没有消息，没有的话我就直接结束，进行下一次循环，再读一次。如果有消息，说明现在有订单要处理，那我就去解析里面的订单信息，完成下单，然后 ACK 确认。成功之后再来下一次循环，又去取，取到了就处理，取不到就继续下一次，就这样循环往复。这是正常逻辑。

而且取不到这里还会阻塞两秒钟，所以你不用担心太频繁的问题。

那如果我在处理消息的过程中抛出了异常，导致没有确认，这条消息就进入 pending list，于是就进入 catch，在 catch 里边我们 `handlePendingList()`。

进来以后我们会首先从 pending list 里读，所以它的读取标识是 0。这个读的时候它也有可能读到，也可能读不到——如果说上面真的抛了异常了，理论上讲这里一定能读到。读到了我就往下处理：解析消息、处理下单、最后确认，这是不变的。

如果这个消息被我处理完了，我再进行下一次循环，我来读的时候是不是就没有异常消息了？没有异常消息，我干什么？`break` 跳出。到这儿异常处理就结束了。

如果这次处理的过程中又抛了异常，那也只是暂停了一下，防止太频繁，然后又重复循环，再来读、再来处理，直到 pending list 里面的所有异常消息全部处理完成为止。

> **结论**：这样是不是就可以确保异常的订单一定能够得到处理？没错吧。

### 回头看：秒杀这条链上 Redis 都干了什么

在整个秒杀的过程当中，我们利用 Redis 到底做了哪些事情？这也是整个项目的一个大纲。

首先是库存超卖的问题，一开始是基于乐观锁的方式解决的。

后来又学习了一人一单的问题，在解决一人一单的时候利用到了分布式锁。这一块我们讲解了大量利用 Redis 实现分布式锁的基本原理，并且学习了一个框架 Redisson，也研究了它的原理，利用分布式锁去解决在集群模式下的一人一单的安全问题。

然后我们又对 Redis 的秒杀做了个优化，也就是把这种同步的秒杀变成异步：在 Redis 当中完成对于秒杀资格的判断，也就是库存和一人一单的限制判断，然后把任务放到阻塞队列里，利用阻塞队列实现异步下单。这里用到了 Lua 脚本，还有我们的阻塞队列。

再然后我们学习了 Redis 里面的消息队列——List、Pub/Sub 和 Stream。最后我们利用 Stream 这种消息队列代替了阻塞队列，实现了真正的基于队列的异步秒杀。

除此之外，还包括库存啊、订单这些数据的缓存，也就是订单流水的缓存，还有分布式锁、超卖问题的解决方案、Lua 脚本等等。

可见 Redis 在整个秒杀业务当中扮演的角色是非常重要的。整个秒杀这部分的内容就全部讲完了。

### 达人探店：从一篇"人均3000"的笔记开始

接下来我们来实现一个新的功能，叫达人探店。

达人可以理解成是现在的网红，大多数都是小姐姐。探店呢，就是到店里边去试一下。比如到了饭店里去试吃，点了几个菜，菜品上来以后先不着急，摆上一个优雅的姿势，拍几张照片，再配上一行文字：

> 生活不仅要有眼前的苟且，还有诗和远方。
> 人均3000的菜品啊，你值得拥有。

你看看，不仅仅显得很有诗意，而且还能秀一下优越感。但是讲白了，这就是给店家做的一些营销广告。小姐姐好不好看，那是一目了然的；但是饭店好不好吃，你得试了才知道。所以我们看到这些评价，你也不要当真。

当然，该实现的功能我们还是得实现。

这一章会有三个小节：第一小节是发布探店笔记，把你拍的照片还有相关的文字发出去，让别人查看；第二小节是点赞功能，有人看了你的笔记觉得挺满意的，不管是对店铺满意还是对发文章的小姐姐满意，都可以点赞，点赞多了说不定你就上热搜了；第三小节是点赞的排行榜功能。

我们先来实现第一个小节，发布探店笔记。

探店笔记类似我们以往的这种评价，但是它比评价更丰富，因为它图文结合嘛，更加容易吸引看官的目光。

#### 笔记背后有两张表

对应的表有两张。

第一张叫 `tb_blog`，也就是探店笔记表，里面包含了笔记的标题、文字、图片等等各种详细信息。上边是达人拍的各种图片，下边是他所描述的一些文字。

第二张叫 `tb_blog_comments`，就是评价表。达人小姐姐发了自己的靓照，那这个时候作为一名绅士，我们是不是应该不吝自己的赞美之词，去评价一下？这个评论表就是来保存这些评价信息的。

在发布探店图文这一块，我们只关注第一张表，评价暂时不用去管。

`tb_blog` 表的结构是这样的：第一个字段是 `id`，主键；第二个是 `shopId`，也就是这条笔记是跟哪个商户有关系的；第三个是 `userId`，就是谁发的这篇笔记；第四个是标题；第五个是照片，照片最多不超过九张，多张的话以逗号隔开，所以它是一个字段，里面包含了多张图片；再往下 `content` 是探店的文字描述；然后还有两个，一个是点赞的数量，一个是评论的数量——点赞了不一定会评论，所以这两个是分开计数的；最后是 `createTime` 和 `updateTime`，创建时间和更新时间。

> **结论**：这里边最核心的、跟笔记有关的信息，其实就是标题、图片和内容，还有跟哪个店铺有关。

#### 上传照片与保存笔记，是两个请求

前端怎么做呢？在首页点击最下方的这个加号按钮，就会弹出一个新的页面，在这个页面里去发布一个新的笔记。可以看到最上面是照片，然后是标题，再往下是内容，也就是文字描述——核心的这三个东西全都有了；再往下选择一下关联哪个商户，这样点击发布其实就发出去了。

不过有一点需要特别注意：**在这里上传照片和发布笔记，这两个功能是分离的。**

为什么呢？因为上传照片这个功能，不仅仅是发笔记的时候有这个需求，其他业务也有这个需求，所以上传照片是一个独立的功能。

点击上传照片的时候，它其实会先发出一个请求实现上传，而这个上传成功以后，它会返回这张图片的地址——也就是上传之后的可访问的一个地址。那么这个地址将来就会作为这个表单的参数，在发布笔记的时候一起提交到后台。

也就是说，我们发笔记的时候这个地方提交的就不是照片本身了，而是上传成功之后的那个图片地址。所以在你点发布的时候，这就是另外的一个请求了。

这两个接口其实我们都已经实现好了，因为跟 Redis 没什么关系，就是基本的增删改查，所以我们就不用大家自己去写了。

#### 图片要传到你的 nginx 站点目录

先看第一个接口 `uploadImg`。它会接收我们的图片，然后把它保存。按照道理，企业里面一般会把它保存到一个文件服务器，但是呢我们这里不关注上传本身，我们只关注跟 Redis 有关的，所以这块就简化了一下，直接把它保存到本地了。

保存本地也不是随便保存的，你得保存到你的前端服务器上，是不是这样？一来将来我们才能直接保存完了就能访问。

我们前端的服务器是放在哪呢？放在 nginx 上的，站点目录里面——那就是我们这个网站所有的图片了。所以你将来是不是应该保存在这里。

> **注意**：在这个地方我们会有一个叫做 `imageUploadDir` 的文件上传地址配置。这个地址现在写的这个位置显然是不对的，我们需要把它改成我们自己本机上真实存在的路径——找到你自己前端所在的那个目录（nginx 站点目录下），因为每个同学放的位置都不一样，所以把这个值当成字符串，拿到那边 Ctrl+V 复制一下，地址就更换成功了。

这样一来，当我们去上传的时候，它就会上传到这个 nginx 的目录下了，将来再去访问的时候才能够正确地访问到这张图片。

#### 保存笔记其实只差一个 userId

第二个接口叫 `saveBlog`，也已经写好了。我们打开 `BlogController`，第一个接口就是它，接收你提交的一个博客，然后呢获取登录用户的信息，把用户信息放进去。

为什么只要拿到用户就可以去保存了呢？因为一个博客里面最核心的几个东西是什么？是不是就是店铺 id、用户 id，然后就是我们的标题、图片和内容。这几个里面，店铺 id、标题、图片和内容已经从前端提交过来了，那只差用户 id 了，对不对？所以这块就可以直接保存。

这块业务非常简单。

#### 亲手发一条出来

把服务重启一下，打开浏览器测试。

点击这个加号，可以看到它会弹到这样的一个页面里来，需要我们去发布一个新的笔记。

我们首先上传照片，在这里我提前准备好了一些素材，点击上传，大家看是不是就上传了。上传成功以后，图片就落到了 nginx 那个目录里，它会生成一个文件夹地址和一个全新的文件名称。打开对应的目录，是不是有一张图片？变成大图标看，是不是上传成功了。

我们还可以上传多张，都可以上传好几张，这边也可以滑动去看。

然后填标题，我们随便填一下，就叫"人均3000的菜品啊，你值得拥有"。下边文字我们也准备好素材了，直接粘贴过来。然后关联一个商户，商户的话我们就随便选一个吧，比如就选一个新白鹿。

好，然后点击发布。大家可以看到是不是发布成功了？而且发布完了以后，它会跳到我的个人主页，在我的个人主页的笔记里，就能看到我刚刚发布的这个笔记了。

然后我们去首页看一下，在首页滚到最下边，其实也可以看到我刚刚发布的这个，因为它没有任何的点赞，所以它排在最后。

再去数据库看一下，刷新，是不是有刚刚插入的这一条博客信息？好，到这里呢我们就已经实现了发布探店图文的这个功能了。
