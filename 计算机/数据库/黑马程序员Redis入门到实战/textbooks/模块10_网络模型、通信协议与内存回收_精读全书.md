## Redis 网络模型：从用户空间与内核空间一路讲到 IO 多路复用
> 对应块：BLK48 | 覆盖分集：P160-P163 | 块标题（分集名）：《原理篇-16.Redis网络模型-用户空间与内核》

接下来我们进入第二章，学习 Redis 的网络模型。这一章会分成八个小节。

第一节先简单介绍一下用户空间和内核空间的概念——因为我们要学网络模型，一定得先知道 Linux 有各种不同的 IO 模型；而要想知道这些 IO 模型，你就得先弄明白用户空间和内核空间。紧接着我们就可以去学习 Linux 的五种不同 IO 模型：阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO 和异步 IO。最后，我们再带着大家去看 Redis 底层到底采用了哪一种 Linux 的 IO 模型，以及它对它做了什么样的封装。

### 用户应用为什么不能直接操作硬件

服务器大多采用的是 Linux 系统，所以这里我们也以 Linux 为例。

大家会看到两个不同的 Linux 发行版，比如 openEuler 和 CentOS。发行版可以看作是在 Linux 上面包了一层壳，但不管是什么发行版，它们的内部，也就是它们的内核，其实都是 Linux。我们在这个基础上安装的一些用户应用，比如 MySQL、Redis，它们其实没有办法直接去访问我们的计算机硬件，所以它们会基于这个壳去访问我们的内核，然后再基于这个内核去操作计算机硬件。

我们把这个流程再进一步细化一下。计算机硬件主要包括 CPU、内存、网卡等等各种各样的设备。内核是可以操作硬件的，但它也需要有各个设备的驱动；在设备驱动的基础上，它就可以形成对内存的管理、进程的管理、文件系统的管理、网络管理等等。最后，我们要想让用户应用来访问，就必须在这些能力之上封装一些接口——系统调用的接口，对外提供。这样用户应用，包括它的一些依赖库，就可以调用这些接口，从而间接地实现对硬件设备的访问。

```text
   用户应用（MySQL / Redis / ...）
            │
            │  无法直接访问硬件
            ▼
   发行版（shell）
            │
            ▼
     ┌──────────────────────────────┐
     │           内核空间            │
     │  内存管理 / 进程管理 /        │
     │  文件系统管理 / 网络管理      │
     │   ↑        建立在设备驱动之上 │
     └──────────────┬───────────────┘
                    │  系统调用接口对外提供
                    ▼
        硬件：CPU、内存、网卡、磁盘 ...
```

> **定义**：设备驱动是内核与具体硬件之间的那层翻译——内核通过它去管理内存、进程、文件和网络管理；再往上一层，才是对外暴露的系统调用接口。

### 为什么要隔离：内核自己也在吃资源

这里有一个问题：我们的内核本质其实也是应用，对不对？它在运行的过程中，是不是也需要一些 CPU 的资源、内存的资源？

你比如说我们的 Windows 系统，启动以后什么都不干，内存是不是就要占去四五个 G，CPU 要占去 10% 甚至 20%？为什么呀？因为这个系统本身它要消耗一定的 CPU、内存等等各种各样的设备资源。

那么我们的用户应用是不是也在消耗这些资源呀？如果说我们不加以任何的限制，让用户应用随意地去操作我们各种各样的资源，是不是很有可能导致一些冲突，甚至让整个系统就崩溃了？因此，我们需要把用户的这些应用隔离开——跟谁隔离开？跟内核隔离开，避免用户应用冲突导致内核崩溃。

### 怎么隔离：先切寻址空间

怎么样实现这种隔离呢？首先就是把寻址空间做隔离，把进程的寻址空间分成两部分：内核空间和用户空间。

那什么叫寻址空间呢？无论是我们的内核也好，还是用户应用也好，其实都没有办法直接访问物理内存，而是只能分配不同的虚拟内存空间，映射到不同的物理内存。那么应用或者内核再去访问虚拟内存空间的时候，其实需要一个对应的虚拟地址。这个地址是一个无符号的整数，从零开始，它的最大值取决于我们 CPU 的地址总线和寄存器的带宽。

比如说一个 32 位的系统，它的带宽一般是 32，因此地址的最大值就是二的 32 次方减一，也就是 $2^{32}-1$，它寻址的范围就是从 `0x00000000` 到 `0xFFFFFFFF` 这么一段空间——这个空间就是所谓的寻址空间了。而内存地址的每一个值，代表的其实就是一个存储单元，也就是一个字节。所以 $2^{32}$ 这么大的虚拟空间，它最多代表的其实就是 $2^{32}$ 个字节，也就是 4GB。这也就是为什么一个 32 位系统的寻址空间最多就是 4GB 的原因。

```text
 32 位进程的完整寻址空间：0x00000000 ~ 0xFFFFFFFF

 0x00000000                                          0xFFFFFFFF
 ┌───────────────────────────────────┬───────────────────┐
 │          用户空间   3GB            │   内核空间  1GB   │
 │          低位地址                  │   高位地址         │
 │          只能执行 R3 指令          │   可执行 R0 指令  │
 └───────────────────────────────────┴───────────────────┘
```

这么一大片就代表完整的一个 32 位系统的寻址空间：从零开始一直到 `0xFFFFFFFF`，这里总共是八个 f，每两个为一个字节，所以总共是四个字节，也就是 32 位——它就是内存地址的最大值了。`0x00000000` 是最小值，整个空间就是寻址空间，其中每一个值代表一个存储单元，也就是一个字节，总共就是 4GB。

现在我们把这 4GB 里的低位 3GB 称之为用户空间，高位的 1GB 划分成内核空间。这样一来，我们就把用户应用和内核应用在内存上做了一个划分。

### 怎么隔离：再切指令权限

内存上做了划分，但这还不够，我们还需要在系统权限上也做一些划分。

因为我们 CPU 运行的各种各样的命令里边，有一些命令它的风险等级比较低，有一些呢比较高。所以 CPU 其实会把各种各样的指令划分成四个不同的风险等级，从 R0 直到 R3。其中 R3 是风险等级最低的，我们的任何的用户应用其实都可以访问；而 R0 是风险等级最高的，也就是一些系统级的一些指令了。

在 Windows 这样的系统里，指令就划分成了这样四个等级。但我们的 Linux 系统里就没有划分那么多级别了，它其实就两个：零和三。三代表最低，零代表风险等级最高。

于是就有了这样的约束：**用户空间里能够执行的仅仅是 R3 级别的这些命令**，也就是说它不能直接调用系统资源，它必须通过内核提供的这个接口才能访问系统资源。而内核空间则不一样，内核空间它里边可以去执行所有的特权命令、R0 级别的命令，也就是说它可以去调用一切系统资源。

> **易错点**：内存隔离和权限隔离是两回事。切地址空间解决的是"你碰不到我的内存"，切指令等级解决的是"你发不出我的指令"。少任何一层，隔离都不成立。

### 用户态与内核态：一个进程的身份切换

一般情况下，用户的应用往往都是运行在用户空间的，而内核的应用一般都是运行在内核空间的。

但是呢，我们讲一个进程，它在执行的过程中，因为业务比较多，可能会去执行一些普通的命令，但也有可能需要去执行一些特权命令、调用系统资源。因此，我们的进程就会在用户空间和内核空间之间去做一种切换：当一个进程运行在用户空间的时候，我们把它称为用户态；当它运行在内核空间的时候，我们就把它称之为内核态。所以我们的进程很有可能在两个状态之间去做切换。

那这个切换的流程具体是什么样子的呢？我们以 IO 读写为例来说明。因为 IO 读写会涉及到磁盘的访问或者网卡的访问——磁盘访问就是读写到磁盘，网卡访问其实就是网络的读写了——这里都会涉及到对系统硬件的访问，所以它们都会涉及到系统资源、涉及到内核态。

### 一次读写要跨几次边界

为了提高效率，我们在用户空间和内核空间里其实都会加入读写的缓冲区。

用户空间的缓冲区比较好理解：我们在 IO 流里都讲过有这种缓冲流，对不对？我们写数据的时候是先写到缓冲区里，然后一次性地写出去；读数据也一样，你先读到缓冲区。所以说这里的缓冲区就可以理解成我们用户 IO 流的这种缓冲区。

内核空间里它也有缓冲区，这个主要是起一个缓存的作用。比方说你去内核里读数据的时候，它可以缓存在这里，下一次再读的时候，如果有就可以直接返回了。

```text
用户空间                                    内核空间
┌──────────────┐   系统调用   ┌───────────────────────┐
│  用户缓冲区   │ ◄─────────► │   内核缓冲区（缓存）   │
└──────┬───────┘             └───────────┬───────────┘
       │                                     │
    业务处理                          磁盘 / 网卡
```

现在我们拿一个进程来走一遍。它一开始在做一些简单的字符串处理、做一些运算，这些命令都属于一些基本应用，只需要运行在用户空间是不是就可以了？

但是呢，等这些运算完了以后，比如说他要把数据写出到我们的磁盘，那么他就需要调用我们的内核。怎么去调呢？首先在写的时候，我们先写到这个缓冲区——写好数据以后，接着你要往磁盘写，你就必须得切换到内核。切换到内核了以后，内核空间里其实是没有你要写的数据的，所以就没法写嘛。因此在真正要想写到磁盘的时候，你必须先把用户空间缓冲区里的数据拷贝到内核的这个缓冲区，然后再把我们这个缓冲区里的数据写入我们的磁盘。

我们读其实也是一样。比如说我现在用户空间要去发起的命令，要去读数据，那么一开始我发起读请求，这个请求到达内核空间以后，内核空间它会先去判断一下有没有数据。

如果说你现在要读的是磁盘，那首先磁盘是不是要先去寻址，所以在这个过程中你要干什么？你要等待。那如果说你读的不是磁盘，你读的是网卡，那网卡是别人从网络传的数据过来，对不对？如果现在数据还没传过来，你是不是也要等待？

所以当你发现一个读请求的时候，首先是要等——等数据到达。好，数据有了以后，接下来是可以读了：如果是读磁盘，那就是直接从磁盘读取；如果是读网卡，那就要从网卡读取，读到哪里去？同样要先读取到我们的这个缓冲区里去。读到缓冲区了，代表数据是不是已经就绪了。

数据就绪了以后，接下来我们读数据的目的肯定要做处理，对不对？所以处理数据跟我们的系统硬件没什么关系，它需要在用户空间去运行。那用户空间里现在没数据怎么办？那么就需要把缓冲数据拷贝回我们的用户空间，然后你就可以在用户空间里去执行那些简单的、对数据的处理操作了。

```text
【写】
 用户态：业务处理完成
   └─► 写入用户缓冲区 ──系统调用──► 内核态
                                          └─► 拷贝到内核缓冲区 ──► 写入磁盘/网卡

【读】
 用户态：发起读请求 ──系统调用──► 内核态
                                          └─► 检查数据：没有？那就等
                                          └─► 从磁盘/网卡读入内核缓冲区（数据就绪）
   ◄── 拷贝到用户缓冲区 ──────────┘
   └─► 处理数据
```

到这里，IO 在用户空间和内核空间之间切换的整体流程我们就分析完了。

### 服务器视角：一次请求的完整往返

如果我们把整台 Linux 服务当成咱们的一台服务器，把刚才这里的硬件设备假想成我们的网卡，那刚才分析的读写流程，就是一个服务器在跟用户客户端进行交互的流程。

比如说现在客户端已经跟我们当前这台服务器建立连接了，然后呢准备发请求给我们。那我们在这里做 read，其实就是在读客户端的请求；然后呢客户端请求在发送的过程中，我们就在这里等待——等客户端请求到达了我们的网卡，然后我们其实就去网卡读取数据。读取数据以后会先读到我们的内核的缓冲区，然后再读到我们的用户缓冲区，接下来就是在我们用户空间里做业务处理了。

那么业务处理完了以后，我们是不是还要把数据写回去？先写到我们的缓冲区，再拷贝到内核缓冲区，然后再写到网卡。唉，这就是一个外部服务与客户端的交互流程。

```text
   客户端            内核态（网卡 / 内核缓冲区）       用户态（进程）
     │                       │                            │
     │  请求 ────────────────►│                            │
     │                       │   等待数据到达               │
     │                       │────► 数据进入内核缓冲区      │
     │                       │────► 拷贝到用户缓冲区 ─────►│
     │                       │                            │  业务处理
     │  ◄────────────────────│◄─── 写入用户缓冲区 ─────────┤
     │                       │────► 拷贝到内核缓冲区       │
     │                       │────► 写回网卡              │
```

大家可以看到，在整个过程中是不是就涉及到了各种各样的状态切换呀。其实影响我们 IO 效率的最主要的原因，大家通过这个图也就能够看出来了：第一个是在这个地方需要有数据的等待，别人没有数据来的时候，你就在这白等，这是一个效率的浪费；第二个原因是在数据的拷贝，你需要从内核空间往我们用户空间拷贝，还需要从用户空间往内核空间拷贝，这种来回的拷贝也是非常影响性能的。

所以呢，我们要想去提高 IO 的效率，核心的两个点：第一个就是想办法减少这种无效的等待，第二个就是减少用户态和内核态之间的这种缓冲区的数据拷贝。

> **结论**：我们后边要学的 Linux 五种不同的 IO 模型，其实都是针对这两个点在做优化的。那么它们到底是如何针对这两个点做优化的，我们后面逐个来看。

### 五种 IO 模型与读数据的两个阶段

有一本神书叫做《UNIX 网络编程》，这本书就把不同的处理方案归纳成了五种 IO 模型，分别是阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO 和异步 IO。

在具体展开之前，我们先回顾一下 IO 读取数据的流程。当我们的用户应用想要去读取硬件设备上的数据时，不管你是要读磁盘还是读网卡，你是没有权限直接去操作的，所以你必须得去调用内核对外提供的指令或者函数。

当我们去调用的时候，如果现在数据还没有准备好，你就必须等待数据就绪。什么时候数据就绪了呢？比如说我们的磁盘寻址完成了，并且将磁盘中的数据读取到内核缓冲区了，这个时候才算是数据准备好了。数据就绪之后，我们就可以将内核缓冲区的数据读取到我们的用户缓冲区。

在这里，等待数据就绪，最核心的就是在等这个硬件设备把数据到达我们的内核缓冲区。因此，数据读取的整个流程我们可以理解成两部分：一部分是用户去等待我们的数据就绪，等待数据到达内核缓冲区；第二部分是将内核中的数据拷贝或者说读取到我们的用户空间去。

而我们不同的 IO 模型，它的差别就是在这两个阶段处理上的一个差别。

| 模型 | 阶段一：等待数据就绪 | 阶段二：拷贝数据到用户空间 |
| --- | --- | --- |
| 阻塞 IO | 阻塞等待 | 阻塞 |
| 非阻塞 IO | 不阻塞，立即返回失败 | 阻塞 |
| IO 多路复用 | 阻塞等待，但一次监听 N 个 fd | 阻塞 |

信号驱动 IO 和异步 IO 也在这五种的名单里，不过本块我们先把上面这三种讲透。

### 阻塞 IO

阻塞 IO 从名字就能看出来，也就是说他在这两个阶段都是一个阻塞等待的状态，谁阻塞等待呢？用户。

那这幅图我们画的不是用户空间和内核空间，画的是用户进程和内核——他们分别在干什么事情，处于什么状态。

比如说我们的用户应用一开始需要去调用内核的这样的命令或者函数，比如说 `recvfrom` 尝试去读数据，那只有这个函数返回结果了，我们才算结束，否则呢用户进程就会一直等待。

那么现在你去调这个函数的时候，我们的内核就会去检查有没有数据。那现在呢发现没有数据，其实内核有两种处理方案：第一种就是立即返回结果，告诉你没有数据了，你一边凉快去吧；还有一种呢就是——没数据是吧，我等一会儿，等到有数据为止。那这个到底怎么处理呢？就取决于你的 IO 模型了。

你现在是阻塞 IO，意思就是没数据是吧，没数据我也等。所以我们的内核就不会返回一个失败的信息，而是说等一等——好，那么他就会在这儿等什么？等待数据就绪，直到我们将磁盘或者是其他硬件设备的数据读取到内核的缓冲区，才算是等待结束，数据就绪。而后呢，我们再将内核中的数据拷贝到用户空间，然后返回一个 OK 的结果给我们的用户进程。那么用户进程一看到哦，返回了，那么就可以去处理了。

在返回 OK 之前，也就是这两个阶段——数据等待阶段和数据拷贝阶段——我们的用户进程全程都处于一个阻塞等待的状态，两阶段都是阻塞状态的，所以说这种模式被称之为阻塞 IO。

> **结论**：阻塞 IO 的问题是显而易见的——用户进程在这两个阶段全程什么都干不了。大家可以想象这种模式它的性能如何？肯定是不怎么样。所以后续就有了更多别的 IO 模型了。

### 非阻塞 IO

非阻塞 IO 从名字上就能看出来，它跟阻塞 IO 相比就是不阻塞的吧。我们知道在阻塞 IO 当中我们去调 `recvfrom` 函数的时候，如果内核发现没有数据，这里我们当时说了有两种嘛：一种处理就是直接报错，另外一种处理就是我没数据，我等等等到有数据为止。阻塞 IO 采用的就是等待模式。

那非阻塞 IO 显然是不阻塞，那显然是不能等，所以如果没有数据，它不等待，而是会立即返回结果。

所以大家看到这个地方，用户应用去调用 `recvfrom` 的时候，内核一看，说没有数据，它不等，而是会立即返回一个失败的信息。但是呢，我们的用户应用啊也算是锲而不舍——你没数据是吧？那我再调一次。诶，这回你有数据了吗？哦你还没有是吧？那我再调一次。

注意了，在这个过程中，内核它在后台肯定会尝试将我们硬件设备上的数据读取到内核缓冲区吧？但是这个肯定需要时间吧？所以在这一段时间内啊，我们的用户应用它就会不断来问你：诶，你好了吗？你好了吗？你就绪了吗？哎，不停地问啊。但是他不用阻塞，他只不过是要不停地问而已。

直到某一刻，数据真的就绪了，已经到达了我们的内核缓冲区了，好，那么这次就不再报错了，而是呢尝试把数据从内核缓冲区拷贝到用户缓冲区，接下来呢就可以返回一个 OK 的结果给用户了。

那大家可以发现在这里的两个阶段：一阶段我们非阻塞 IO 去调 `recvfrom` 的时候，并没有阻塞，而是立即返回一个失败的信息，对不对？而在二阶段的时候呢，我们去调用，如果数据就绪了，它需要去拷贝数据，在拷贝的过程中，其实我们的进程是不是处于一个阻塞状态的啊？没错啊。

> **结论**：非阻塞 IO 在一阶段等待数据就绪的时候是非阻塞的，但在二阶段的数据拷贝的时候依然是阻塞状态。

那么大家觉得这种模式相比于阻塞 IO，性能上有没有提升啊？

事实上啊，我们这种非阻塞 IO 看起来花里胡哨的是吧，其实啊没什么用。你想啊，我阻塞 IO 我调用 `recvfrom` 的时候，如果没数据，我是等到有数据然后去拷贝，在这个过程中我们用户进程啥都没干，就等。好，你非阻塞 IO 当我发现没有数据的时候，你报一个错给我，我又问你有没有数据，你再报错给我，我再问。那么除了问，你的用户进程还干了别的事了吗？也没有干吧？所以说有什么用呢？你不还是要等到数据就绪为止吗？

在整个过程当中，我们的用户进程除了不停地问——这种不停地问，叫**盲轮询**或者叫**盲等**。出了这种机制之外，它并没有提升整个我们这个进程的性能。相反，因为你在不停地问，你要不断地去让 CPU 去执行一些命令，反而会导致 CPU 的使用率暴增。所以呢，非阻塞 IO 其实在某种程度上来讲，可能还不如我们的阻塞 IO 啊。

那有同学会说了，那这个非阻塞 IO 有什么用啊？

虽然看起来非阻塞 IO 在性能上并不比阻塞 IO 有什么太大的提升，但是在某些特殊场景下，你不得不使用非阻塞 IO，而且呢可能还会带来更好的一些提升。比如说我们下节课要学习的 IO 多路复用，那么它就必须得结合非阻塞 IO，才能有更好的性能表现。

### IO 多路复用

接下来我们学习第三种 IO 模型——IO 多路复用。这个名字可以说是如雷贯耳，无论是在面试当中，还是我们平常开发过程中都听到过它。只要是一些高性能的网络框架，底层都绕不开 IO 多路复用。这一节我们就来看一看，它相比于阻塞 IO 和非阻塞 IO 主要是胜在哪里、差异在哪里。

#### 两种老办法，都没让 CPU 干正事

首先呢我们知道阻塞 IO 或者是非阻塞 IO，它们在第一阶段数据等待阶段，其实都是在调这个 `recvfrom` 函数尝试来读数据，差别就是在调用函数时，如果没有数据时该怎么处理。如果说在调用 `recvfrom` 时恰好没有数据，那对于阻塞 IO 来讲，他要做的事情就是让进程阻塞；而对非阻塞 IO 来讲，它虽然不阻塞，但是呢它会让 CPU 去做空转。但无论是阻塞或者是空转，都不能够充分地去发挥 CPU 的作用，就是没有干正事啊——这就是这两种模式它性能不太好的一个原因了。

而如果恰好你调用这个 `recvfrom` 的时候，它有数据，那还好，那我们就直接去读数据就好了，这个没什么问题。

但是你怎么能保证我们调用 `recvfrom` 的时候，它就真的刚好有数据？那就比如说吧，我们现在假设是一个服务端，然后我们接收客户端 socket 的请求。我调这个 `recvfrom` 就是尝试从客户端 socket 里去读取数据。

那如果说现在我们有很多很多的 socket 请求都来了，但是我们是一个单线程的情况，那么这很多的客户端 socket 是不是就要去排队？我只能一次处理其中的一个。给它的，如果说我正在处理的这个 socket 它恰好没有就绪，也就数据不可读或者是不可写，那现在整个线程是不是就要去阻塞等待了？而在这个队列当中的其他的 socket，他是不是也都要跟着等？甚至有可能这些其他 socket 有一些数据人家已经就绪了，但是没办法，只能等，一个一个的等。所以说呢整个性能它就比较差了。

#### 一个段子：把快餐店变成慢餐店

当然了啊，我在这儿说这个 socket 啊，很多同学脑海里还是没有办法出现一个画面。那好了，我给大家准备了一个段子，这个段子讲的是快餐店点餐的一个故事。通过这个故事，相信大家就能更加体会到这种单线程阻塞导致的性能的问题。

我平时呢经常会愿意去快餐店吃饭，就特别讨厌店里的一种人，就是那种点餐特别慢的人，他会活活把一个快餐店变成慢餐店。

我有一次去一个面馆点餐，不知道为啥哈，排在我前面那个哥们儿，轮到他点餐的时候，就跟个傻子一样，就往那一站："你们这都有啥吃的？"服务员说："我们这个都是面，菜单都在上面，您看一下。"那个酸辣笋尖面啊，来一份酸辣笋尖面是吗？不是——那里面都有啥呀？哦——那里面主要就是笋尖儿还有面啊。笋尖儿那就算了吧，呃……那你呃我看一下，那你给我来一个，你给我来一个那个什么吧。你给我来一个那个，哦，下面也有啊。

好，同学们，视频看完了。不愧是脱口秀天花板啊，把一个有选择困难症的客户，他的形象啊表现得栩栩如生，活活把一个快餐店变成了慢餐店是吧。

#### 点餐的两步，就是 IO 读取的两步

但是呢大家也别光顾着看笑话是吧，关键要从里面去分析我们这个阻塞 IO 它的问题。

这里描述的这个快餐店，他的点餐模式不像现在很多都是用手机扫二维码点餐了，它属于比较传统的模式。这种点餐模式呢，在现在依然还有很多的快餐店就是这么做。那他的点餐模式是这样子的：首先你得有一个这个收银台嘛，然后我们所有的客户都会排着队到这个收银台这里依次来点餐。

所以呢，点餐的步骤就要分成两步了。第一步啊，就是这个顾客他要去思考自己该吃什么，那这个思考肯定会花一定的时间嘛，在他思考完成之前，我们是没有办法点餐的。这就就像我们 IO 去读数据，如果说数据还没有到达内核缓冲区，你就必须等，等待数据就绪。

那顾客如果想好了呢？我们服务员是不是就可以把他想点的东西输入这个设备，然后呢这个设备就会把信息传到我们后厨，后厨是不是就可以去做餐了。这就像我们数据一旦就绪了，就可以把数据从内核拷贝到用户缓冲区，完成读取数据的流程了。所以你看，这个点餐的两步跟我们 IO 读取的两步是不是几乎是一样的。

但是呢，现在假设我们这个用户他有选择困难症，他想"我该吃啥呀"，酸辣笋尖还是那啥呀，想半天在这纠结。那在他纠结的这个过程当中，就相当于说数据没有就绪吗？那我们的服务员也只能在这干等着，对不对。这种等待其实就类似于阻塞 IO。

那就别说了——你为什么不用非阻塞？我们知道非阻塞模式其实就是不断地询问你，对不对？你问你，你是想好了吗？没想好是吧？你要不要吃酸笋尖啊？要不要吃鱼香肉丝面啊？要不要吃酸麻辣豆腐面啊？就一直问。你这样一直问他，可能会让这个顾客更加心烦意乱，反而效率是不是更低了？

所以非阻塞 IO 有没有去提升整个性能？没有。

#### 加服务员：老路走不通

那么在这个客户想的这个过程中，不仅仅服务员要等，后续所有人是不是也跟着等了？哪怕是早就已经准备好了、自己想点什么了，是不是也没有办法点餐啊？因为要排着队嘛。所以啊这个点餐的效率可想而知就比较差了。

这就像是我们现在这个 socket 一样，有很多客户端 socket 都在排着队等待处理。第一个 socket 如果数据未就绪，那大家呢都得跟着等，不管后边的 socket 有没有就绪。那这样的等待就是无效等待。所以不管你是阻塞还是非阻塞 IO，那么这种方式它的效率都是非常低的。

那么我们该怎么样去提升这个效率呢？在早期啊，提升性能的方案非常简单，就是增加服务员。你可以回忆一下肯德基在 10 年前的时候是什么时候做的？一个长长的收银台，有好几个收银机，是不是好几个服务员啊？这样大家就不是排成一队了，是不是可以排成两队或者三队呀？每增加一个服务员，理论上讲排的队——这个点餐的效率是不是要提升一倍啊？

那这种处理方案呢，其实就有点像是 IO 当中的这种多线程。在多线程这种方案啊，虽然在一开始确实能够增加效率，我增加两个服务员、三个服务员，那点餐效率肯定高了呀。但是服务员越多，你得开更多的工资，开销也大了。那对于我们多线程来讲也是如此：一个线程的时候，我们 CPU 可以专门来处理它；但是如果你有多个线程，CPU 就要在多个线程之间做上下文的切换，那这种上下文切换本身的开销也是非常大的。所以呢，随着线程越来越多，很有可能你将来的性能不增反降。所以这并不是一种很好的方案啊。

#### 不排队：一个人盯一屋子

那还有什么方案可以提高效率？我们还是拿这个点餐为例来说明，在这我给大家说一招。

比如说我们可以这么做：就是不让这些人排队了。谁想好了要吃什么了，那么你就去叫服务员就行。也就是说大家各自坐在一个桌子上，对吧？你就想"我想好了，我要吃什么了"，我直接呼叫服务员，然后点餐就完了。这种方案是不是也是可行的？

那这个时候呢，我们的服务员就可以同时去监听多个客户。谁准备好了，我就去找谁；没想好的人呢，你就在旁边想，我也不在你身上浪费时间，我去处理想好的人。是不是就没有这种无效的等待了？

那对应到我们 IO 处理当中呢？比如说现在有很多个客户端 socket 都连到了我们的服务器，但是呢有一些数据就绪了，有一些没有就绪。这个时候如果你是排队处理的话，如果第一个人刚好队列对手的这个他是数据没有就绪的，那是不是后边的人都在等着？这不行。那现在的做法是什么？就是这些 socket 不要排队了，然后呢我们用这个线程去监听所有 socket，任意有一个 socket 数据就绪了，我就赶紧去处理一下。那这样一来是不是就减少了这种无效等待？那我们的 IO 效率是不是也会大大地提升？

```text
【排队模式：阻塞 / 非阻塞】
   顾客 A（还在纠结）──┐
   顾客 B（早就想好了）─┼──► 收银台（单个服务员）──► 后厨
   顾客 C（早就想好了）─┘        A 没想好 ⇒ B、C 全卡住
                                  ⇒ 无效等待

【叫号模式：IO 多路复用】
   顾客 A（还在纠结，没人会来打扰）
   顾客 B ──按铃──┐
   顾客 C ──按铃──┴──► 服务员同时盯着所有人，谁按铃就先服务谁
```

#### 文件描述符：为什么能同时盯多个 socket

但是呢现在问题来了：我们的用户进程怎么知道你这个内核数据有没有就绪？我怎么知道你的 socket 是不是就绪的？

那要解决这个问题，就不得不提到我们 Linux 内部的一个东西，叫做**文件描述符**（file descriptor，简称 fd）——以后一说 fd 你就知道是文件描述符了。它是一个从零开始递增的无符号整数，每一个数字就代表一个文件描述符，用来关联 Linux 中的一个文件。

而在 Linux 当中呢，一切皆文件。比如说你硬盘中的一个普通的文件或者视频，甚至于一个硬件设备，你说你键盘鼠标都可以看作是文件。那这样一来，他们是不是都可以有自己对应的文件描述符？当然这也包括我们刚才说的网络套接字 socket。那接下来我们每一个客户端跟我们建立联系时，是不是都有一个对应的 socket？是不是都有一个对应的文件描述符？

那这个有什么用呢？一旦有了这个东西，我们刚才所说的用一个线程来监听多个客户端 socket，这种方式就可以实现了。

> **定义**：**IO 多路复用**就是利用单个线程同时监听多个 fd，并且在某个 fd 可读或可写时得到通知，从而避免无效等待、充分利用 CPU 资源。

也就是说你将来每个 socket 不都是一个 fd 吗？我就用一个线程来监听你 N 个 fd，这就是 IO 多路复用。**复用的就是线程**，用一个线程进行多个。那这个线程就相当于是服务员，然后呢这些 fd——每一个客户端 socket 对应的 fd，就相当于是顾客。就是一个服务员同时盯着多个顾客，没问题吧？

#### select 的完整流程

那这边呢，它具体的流程是这样子的。

首先用户应用一上来，他调的是 `select` 函数，不再是 `recvfrom`。我们知道 `recvfrom` 是直接尝试去读数据的，它要读的目标就是具体的某一个 fd。但是你在调这个函数那一刻，你知不知道这个 fd 它数据有没有就绪？你不知道吧？所以如果你去调那一刻没有就绪，那你就不得不阻塞等待。我们必须得先弄清楚到底是哪些 fd 就绪了——也就是说去监听这些 fd，一旦 fd 就绪了，我们再去调用 `recvfrom`。

那么因此呢，我们现在还不能去调用它，我们现在调的是谁？`select`。`select` 函数呢，它的内部可以接收多个 fd。也就是说，我们可以把每一个客户端 socket 对应的 fd 都传给这个 `select` 函数，然后呢它就传到内核去了。那么内核就可以去检查——你要监听的这些多个 fd，它有没有任何一个是就绪的？只要有任意一个或者多个就绪，那么它就会直接返回这个结果，告诉你说数据就绪了。

那如果说我这 N 个 fd 都没有就绪呢？其实这种概率比较低，这么多年下来一个都不就绪那也太夸张了，对不对？但是万一呢？万一真的所有的 fd 都没就绪呢？别着急，那在这里会稍微等一会儿。在这个等待的过程中啊，它其实就会有一个后台的进程去监听这些 fd，一旦有任意的一个 fd 就绪或者多个 fd 就绪，那么它就会返回结果了。

那么在这个等待的过程中，我们用户进程那就不得不去阻塞等待了，等到有 fd 就绪。这个等待是不可避免的，因为所有 fd 都没有数据，那没有办法，只能等——那这个也不算是无效的等待，对不对？

那么接下来一旦有一个或多个就绪，我们拿到这个返回值了，知道可读了，那么接下来我们就可以去调 `recvfrom`。而且我在调的过程中，我可以明确地知道我要读的这个 fd 它一定是有序的，它一定是有数据的，对不对？我肯定不用阻塞，所以我一进来我就开始拷贝数据，然后结束就行了。

当然啊，因为这里就绪是有可能是多个 fd 就需要……因此在这里其实是要循环啊：读完一个 fd 了，再来读下一个，也一直调一直调，直到把所有就绪的 fd 读完为止。好，等所有的都就绪了，我再回头再来调 `select`，在监听下一批。就这样一直去处理，直到把所有的连接都处理完成。

```text
用户态                              内核态
  │                                    │
  │  ① select(多个 fd) ────────────────►│
  │                                    │ 检查这些 fd
  │                                    │ 全部未就绪 ⇒ 稍等（不可避免的等待）
  │                                    │ 任一/多个就绪 ⇒ 返回就绪结果
  │  ◄────────────── 返回（就绪了）      │
  │                                    │
  │  ② recvfrom(fd1) ─────────────────►│ 此时 fd1 必有数据，直接拷贝
  │  ③ recvfrom(fd2) ─────────────────►│
  │  …… 循环读完所有就绪的 fd           │
  │                                    │
  │  ④ 再回到 ①，监听下一批             │
```

#### 它跟阻塞 IO 到底差在哪

那么大家可以发现，在 IO 多路复用这种模型当中，它的阶段一等待 fd 就绪的时候，其实我们的用户进程是不是也是阻塞的？阶段二数据拷贝呢？同样是阻塞。

那有的会说你这种模式跟我们刚才的阻塞 IO 模式又有什么差别呢？

诶，你不要忘了：阻塞 IO 模式调的是 `recvfrom`，产生了阻塞，而 `recvfrom` 它只能监听某一个 fd，直到这个 fd 就绪我才去往下处理。但是啊你去调的这个 fd 它没有就绪，不代表其他 fd 没有就绪，对不对？所以呢这个时候，你等待当前 fd 就绪的时候，如果其他 fd 已经就绪了，你这种等待是无效的等待——你完全可以去处理其他人啊。所以呢它的效率比较低。

而 `select` 模式则不同：`select` 模式是一次性传多个 fd 进去，然后只要有任意一个行了，我们就立马知道结果了，我就赶紧去处理就行了。这就相当于我们刚才讲的餐厅服务员嘛——我这个服务员在这里一次性监听 N 个顾客，只要有任意一个顾客说"哎我准备好了，我要点了"，你就赶紧去处理，他不会因为说有一个顾客等在那里了，结果呢导致所有人都去等。

因此呢，这种模式它的效率肯定是比阻塞 IO 要高很多的。这就是 IO 多路复用它的一个基本的思想。

#### select、poll 与 epoll：灯泡还是计算机

当然啊，这只是基本的一个思路。真正在实现 IO 多路复用的时候，它其实还有很多种不同的实现方式。在我们的 Linux 系统当中，IO 多路复用的实现常见的有三种：第一种就是 `select` 模式，第二种是 `poll`，第三种是 `epoll`。

那么这三种模式又有什么差别呢？在这里呢我们同样是拿这个点餐的案例来讲。

IO 多路复用是一个服务员监听 N 个客户，对不对？所以呢现在大家不用排队了，那怎么监听呢？这里有两种。

**第一种，集体模式。** 就相当于是每个顾客他们都坐在自己的桌子面前吧，那我给每个桌子上都安一个开关，这个开关会连到我们服务员面前的一个灯泡上。那任意有一个人，比如说他想好了要吃什么了，那他就可以去按那个开关，那么一按就会通知服务员，服务员面前的这个灯它就亮了。我们的服务员是不是就知道说有客户就绪了，要点餐了？

但是呢这里有一个问题：因为我们服务员面前就这一个灯，任何一个人按了他都会亮，那就导致了当灯亮的时候，我们的服务员不知道到底是谁就绪了。那他要做的事情是什么？那就是一个一个的过去——诶，是你要点了吗？不是是吧？你要点吗？不是是吧？一个一个问，直到找到真正要点餐的客户为止。所以这是最早期的 IO 多路复用实现的方案了，也就是 `select` 和 `poll` 他们的实现方案。那这种方案中大家也能看到它的弊端：就是这种通知的机制不太好，我不知道是谁，我得一个一个遍历。

```text
select / poll：开关 ──► 灯泡（服务员面前只有一个）
   1 号桌 ──┐
   2 号桌 ──┼──►  灯亮了  ──►  服务员挨个问：
   3 号桌 ──┘                      "是你吗？" —— 不是
                                   "你要点吗？" —— 不是
                                   ……  直到找到真正就绪的那一位

epoll：按钮 ──► 直接写入计算机（就绪 fd 列表）
   1 号桌 ──┐
   2 号桌 ──┼──►  就绪列表 = [ fd2, fd3 ]
   3 号桌 ──┘                      ──►  直接处理 fd2、fd3
```

**第二种，升级后的通知方案。** 后来那个系统就升级了一种新的通知方案，就是 `epoll`。那他的思路是什么呢？那就比较简单了：就是大家面前的这个按钮，不再是控制这个灯泡了，有可能是直接控制这个服务员面前的计算机，然后你按这个按钮，直接会在计算机上显示出具体是几号桌就行了。那这样一来，我们服务员是不是能快速找到就绪的这个人，然后去给他点餐就行了。

这就是 `select`、`poll` 和 `epoll` 之间的一个差异了。

> **结论**：`select` 和 `poll` 只会通知用户进程"有 fd 就绪"，但是根本不确定是谁，所以用户进程只能是逐个遍历 fd 来圈；而 `epoll` 则会在通知用户进程就绪的同时，把已经就绪的 fd 写到用户空间里去，那用户直接就看到了"是这几个哥们就绪了"，直接处理就行了。

当然这是从大的方面来讲，事实上从细节上 `select`、`poll` 和 `epoll` 还有很多不同之处。所以呢，我们下一节会带着大家逐一地去学习 `select`、`poll` 和 `epoll` 这三种模式底层实现的源码，看一看它们的差异主要在哪里。

## IO 多路复用的三种实现：select、poll 与 epoll
> 对应块：BLK49 | 覆盖分集：P164-P166 | 块标题（分集名）：《原理篇-20.Redis网络模型-IO多路复用之》

从这节课开始，我们正式来学习 IO 多路复用的多种实现方案。

第一个登场的是 **select**，它是 Linux 中最早的一种 IO 多路复用实现方案。然后是 **poll**，它针对 select 做了些简单改进，但性能提升并不明显。最后是 **epoll**，它对前两者做了一个巨大的改造，性能相比之下提升得非常明显。

这三个方案我会一个一个拆开，把它们的函数声明、数据结构和执行流程全都走一遍，再回头看看每一代到底解决了上一代的哪些毛病、又留下了哪些毛病。

### select：Linux 上最早的那一版

#### 五个参数各管什么

先看 select 的声明：

```c
int select(int nfds,
           fd_set *readfds,
           fd_set *writefds,
           fd_set *exceptfds,
           struct timeval *timeout);
```

一句话概括它的作用：**监听多个 fd 组成的集合**。所以下面传的一堆参数，全都是跟这个 fd 集合有关的。

**第一个参数 `nfds`**。它的值往往是我们要监听的这个 fd 集合当中最大的那个 fd 再加一。我们知道 fd 的值是无符号整数，从零开始不断递增，那么这多个 fd 一定会有一个最大值。把这个值传进去，就是告诉内核：你在遍历这些 fd 的时候，当遍历到它的时候已经到了上限，不用再往后遍历了。所以传的是**最大 fd 的值加一**，它是一个遍历 fd 时的上限。

> **易错点**：`nfds` 是「最大 fd + 1」，不是「fd 的个数」。数量和编号是两回事，传错了内核会少扫或者白扫一段。

**第二、三、四个参数是三个 `fd_set*`**。顾名思义就是 fd 的集合，但你一定会疑惑：怎么会有**三个**？

因为 Linux 把一个 fd 上可能发生的事件分成了这么三类：IO 要么读、要么写、要么发生异常。所以将来的事件可能就是这三种：可读事件、可写事件和异常事件。

有一些 fd 我们只关心它有没有数据可读，有一些我们关心的是它可不可写。所以将来我们把这些 fd 传给内核的时候，你得**给它分类**：现在有一个客户端刚刚建立连接、正在发送请求，那它肯定要放进读事件的 fd_set 里；而另外一个客户端 socket 已经请求处理完了、正等待去响应，那对应的 fd 就应该放进写事件的 fd_set 里。所以调用 select 的时候，一定要把对应的 fd 放到对应的集合当中，把事件区分开。

**最后一个参数 `timeout`**，也就是超时时间：调用 select 的时候需要等待这些 fd 就绪，那到底要等多久？这个只有三种情况：

- 传 `NULL`：代表永不超时。也就是我这个 select 要去等待，等到某一个或多个 fd 就绪为止——你不结束我就一直等下去，等到海枯石烂、天长地久。
- 传 `0`：代表不阻塞等待。不管我调用 select 的那一刻有没有就绪，我都会立即返回，返回就绪的 fd 的数量，没有就是返回零。
- 传大于零的值：那就是一个具体的超时时间。如果没有任何 fd 就绪，我就等这个固定的时间；如果超过时间依然没有就绪，此时也会返回，返回值同样是零，告诉它没有就绪。

> **提示**：返回零有两种完全不同的含义，一种是你传了 0 主动轮询，一种是你等超时了但没人来。想知道到底是哪种，得自己看自己传的是什么。

#### fd_set：一个用比特位省下来的集合

接下来是最关键的部分：**fd_set 的结构非常特殊**。

```c
#define __FD_SETSIZE  1024
#define __NFDBITS    (8 * sizeof (long))      /* 32 */

typedef struct {
    unsigned long fd_mask[__FD_SETSIZE / __NFDBITS];   /* 1024 / 32 = 32 */
} fd_set;
```

我们一层一层往下看。

`fd_set` 是一个结构体，结构体里有一个属性 `fd_mask`，类型是数组。数组的元素个数由两个常量算出来：第一个常量是 `__FD_SETSIZE`，值是 **1024**；第二个常量是 `__NFDBITS`，值是 **32**。那么 $1024 \div 32 = 32$，也就是说这个数组的元素个数是 32。

那是不是说 fd_set 集合里最多只能装 32 个 fd？**并不是。**

注意看这个属性的类型，它叫 `fd_mask`——又是没见过的东西，别着急，往上看，它又是一个别名，真实类型是一个 `long int`，也就是一个整数，在 C 语言里占四个字节，四个字节就是 32 个比特位。

也就是说，`fd_set` 这个数组的元素个数是 32，而每一个元素的长度是 32 个比特位，$32 \times 32 = 1024$ 个比特位。

> **提示**：这里我一直强调「比特位」是有原因的。上面 $1024 \div 32 = 32$ 的推导是按 32 位平台算的；64 位 Linux 上 `long` 是 8 字节，`__NFDBITS` 变成 64，`__FD_SETSIZE / __NFDBITS` 算出来是 16 个元素，16 × 64 依然是 1024 个比特位。结论不变：**`fd_set` 始终只能表示 1024 个 fd**。

`fd_set` 在保存 fd 的时候是**按比特位保存**的，每一个 bit 代表一个 fd。虽然数组是 32 个元素，但我不是按元素存的，是按比特位存的，那我有 1024 个比特位，将来就能保存 1024 个 fd。

具体怎么保存？我们用八个比特位来演示（真实的 1024 个太多了，画不下）：

```text
bit index :   0    1    2    3    4    5    6    7
fd number :  -    1    2    3    4    5    6    7
bit value :   0    1    0    0    1    0    0    0
```

在我们初始化 fd_set 的那一刻，每一个比特位都会被初始化为零。现在假设要监听的 fd 值分别是 1、2、5，那它是这样保存的：

- 要监听 fd = 1，就去找 1 号比特位，把这个值置成 1；
- 要监听 fd = 2，就找第 2 个比特位，置成 1；
- 要监听 fd = 5，就找第 5 个比特位，置成 1。

也就是说，**第几个比特位代表的 fd 就是几**，值是 1 就是监听，是 0 就是不监听。

有些同学问我：1024 个比特位是不是就能实现监听 1024 个 fd 啊？你看看这种方案就非常巧妙——它用 bit 的 0 或 1 来代替了真正的 fd 的值，是不是可以大大节省内存空间。

#### 走一遍 select 的完整流程

接下来我们通过流程图来梳理一下 select 这种方式的执行过程。

```text
USER SPACE                            KERNEL SPACE
-----------                           ------------
build fd_set:
  bit1=1 (fd=1)
  bit2=1 (fd=2)
  bit5=1 (fd=5)
      |
      |  select(6, &rfds, 0, 0, 3s)
      |  ---- copy in : 1st copy -------
      +------------------------------->  scan fd 0..5
                                             |
                                    all blocked?
                                     /            \
                              yes /              \ no
                                 v                v
                            sleep & wait      return count
                            (woken up by fd=1)
                                 |
      <--------------------------+  rewrite bits:
      |  <---- copy back: 2nd ---+    ready fd  -> 1
      |                           |    others    -> 0
      |
 return value = 1  (ready count)
 scan fd_set again in USER space
      -> find fd=1 -> read(fd)
```

读图顺序：先把 `fd_set` 造好并传进内核（**第一次拷贝**），内核从最低位开始遍历到 `nfds` 给定的上限为止，检查被标记的 fd 是否就绪。假设这次一个都没就绪，那就去休眠等待；等待过程中后台一直在监听，只要任意一个 fd 可读，就把我唤醒，然后**再遍历一遍**，把就绪的保留成 1、没就绪的改成 0，也就是第二张图里那个「rewrite bits」的动作。

最后 select 会返回一个值，告诉用户现在有几个就绪了——一个就绪返回 1，五个就绪返回 5。

> **易错点**：但是有一点要注意，**select 只是反馈了「有几个就绪了」，并没有把真正就绪的结果告诉用户**。用户空间里根本不知道具体是谁就绪了。所以 select 在背后还有一个隐含的操作：会把这个 fd 集合的结果**再拷贝回用户空间**，覆盖用户空间里那个 fd 集合。

等到用户进程真正去读数据的时候，它只能自己在遍历一遍，找到那些标记为 1 的 fd，再去读取其中的数据。

> **结论**：成也萧何，败也萧何。`fd_set` 这种设计虽然一定程度上节省了内存，但它没有办法直观地告诉用户进程**谁就绪了**——用户每次读数据前都得先遍历找到对应的 fd 才行。这也是 select 模式性能相对比较差的一个直接原因。

这一次执行完、数据处理完毕以后，下一次就可以从第一步继续开始：再一次把要添加的 fd 放到 fd_set 里面，然后执行 select，然后再次去进行监听，然后再次等待就绪，然后再次处理数据，以此类推，不断地循环往复，处理各种各样的读写数据。

#### select 留下的三个坑

我们一起来分析一下，这种模式总共有哪些缺点。其实刚才在分析的过程中已经提到过几点，我在这里给大家总结好了。

**第一个坑：每一次执行 select，都要发生两次用户态和内核态之间的内存拷贝。**

每执行一次 select，都需要将 fd_set 从用户空间拷贝到内核空间，而 select 结束以后还要再次拷贝回用户空间。你看我们每次调 select，得先把要监听的 fd 传过来，完成一次拷贝；等我们处理完了、检测完了，还要把结果再拷贝回去。也就是说，每执行一次 select 就会有两次用户态和内核态的切换、两次这种内存的拷贝。

而 select 并不是只执行一次——刚才我们说了，每一次执行完，下一次又要执行 select，再次去监听。也就是说它会循环往复不停地执行，每一次都会有这样的拷贝。所以这也是影响 select 性能的一个非常重要的原因。

**第二个坑：select 无法得知具体是哪个 fd 就绪了。**

这个原因刚才说过了，就是因为 fd_set 集合的结构是这种比特位的形式。虽然我把结果传回去了，但你不知道这里边哪个就绪，你不得不一个一个遍历，直到找到就绪的为止。

**第三个坑：fd_set 能够监听的 fd 数量比较少，只有 1024。**

还是被这个数组给限制了，这个数组里边的大小是一个常量，直接在源码里写死的。你要想改变这个值，你得去修改源码，然后去重新编译——这不是我们一般人能去做的。

所以我们一般情况下认为 select 模式能够监听的 fd 数量是固定的。这个值看起来好像挺大的，但是现在随着互联网企业的发展，并发量可以说是暴增。以前可能 1024 还够看，现在啊完全都不够用了。也就是说，你并行能够处理的这种文件的数量只能是 1024，那你能处理的客户端请求量可能比这个还要小，完全是不够用的。

正因为此，我们的 Linux 在升级迭代的过程中也提出了很多新的 IO 多路复用实现方案，比如 poll 和 epoll。

### poll：换了骨架，毛病还在

#### 函数声明与 pollfd 结构体

poll 相对于 select 做了一些简单的改进，不过它的性能提升也不是特别明显。

```c
int poll(struct pollfd *fds, nfds_t nfds, int timeout);

struct pollfd {
    int   fd;       /* the fd to watch            */
    short events;   /* the event(s) we care about  */
    short revents;  /* the event(s) actually seen */
};

enum poll_event {
    POLLIN,     /* data can be read        */
    POLLOUT,    /* data can be written     */
    POLLERR,    /* error condition         */
    POLLNVAL    /* fd not open             */
};
```

**第一个参数是 `struct pollfd *fds`**，带星号，说明是一个数组，数组里装的就是我们需要监听的这些文件描述符的集合。这个数组的大小没有上限、没有固定，你可以随便定义。

**第二个参数 `nfds`**，代表数组中元素的个数。**第三个是超时时间**。

这两个参数跟我们之前 select 当中传递的参数基本上差不多。差别在于：fd 集合在 select 模式当中我们传了三个集合，分成读事件集合、写事件集合还有一个异常集合；但是在 poll 函数中它就简化了，参数变少了，因为它没有去划分不同事件集合，而是全部放在一个数组当中了。

那问题来了——将来内核怎么知道你要监听哪种事件呢？这里的关键就在于数组中元素的类型。

数组中的元素叫 `struct pollfd`，它也是一个结构体，里面分成三个属性：

- **`fd`**：也就是我们要监听的那个 fd 的值。你看这一次它就吸取了教训，没有用二进制位去表示 fd，而是直接把 fd 的值保存在这里了。
- **`events`**：要监听的事件类型。也就是说在 poll 模式当中，这个 pollfd 里既包含了 fd 的值，也包含了事件的类型，它可以是读、写、各种类型都行。因此各种事件类型的 fd，其实是放到了一个数组中传过去了。事件类型已经预定义好了，相比较 select 模式，它的事件类型会更丰富一些，上面的枚举里我只是列举了其中的一部分。
- **`revents`**：叫「real events」，代表真正发生的事件类型。

> **注意**：调用 poll 的时候，我们创建多个 `struct pollfd` 形成数组传进去，但**只需要指定 `fd` 和 `events`**——也就是「我要做什么事情」，而不需要指定 `revents`，因为你现在也不知道有没有发生。传进内核以后，内核监听的过程中如果发现事件有就绪的情况，就会把就绪的事件类型回填到 `revents` 里；如果等到超时时间过了都还没有发生任何的事件（也就是没有就绪），那这个值就改成零，代表没有发生任何事件，然后把整个数组再返回给我们。这样一来我们其实就能够知道这个 fd 有没有发生事件、发生了什么事件了。

#### 走一遍 poll 的流程

第一步，你肯定要去创建这个 pollfd 的数组，数组中放的就是我们要监听的所有 fd 的信息。数组大小是可以自定义的，所以理论上讲我们这里能监听的 fd 数量是没有上限的。

数组创建好了就可以去调 poll 函数了，调用的时候会把 pollfd 里的数组拷贝到内核空间——**注意了，这里同样会有一次从用户空间到内核空间的拷贝**。拷过去以后，内核会把它转成一个链表去存储，所以理论上讲存进去以后是没有上限的，可以无限存储。

执行完以后内核就可以去遍历这些 fd，判断它有没有就绪。跟 select 一样，如果有就绪了就返回，如果没有就绪它同样需要去做一个等待；如果说等待还是没有就绪，那就可能会超时。不管怎么样，最后一定会返回一个结果：如果最终没有任何就绪，返回的就是零，代表就绪了零个；如果有就绪就会返回具体的就绪的数量。

```text
USER SPACE                          KERNEL SPACE
-----------                         ------------
pollfd[] = { {fd=3,ev=IN,rv=0},
             {fd=5,ev=OUT,rv=0} }
      |
      |  poll(fds, 2, timeout)
      |  ---- copy in --------------->  convert to linked list
      |                                   scan -> ready?
                                             |
                        +--------------------+--+
                        | no -> wait/timeout |  |
                        +--------------------+--+
      <-------------------------------------+  copy whole array back
      |                                        (ready AND not-ready)
pollfd[] -> scan it myself to find who is ready
```

同学们注意到了吧，**这里 poll 函数返回的也只是就绪的数量**，它没有把我们具体谁就绪返回出来。在背后，它同样也会把内核空间中处理好的这个 pollfd 数组拷贝回用户空间，这样用户空间里这个数组其实就有了所有 fd 实际发生的事件类型（当然也可能没发生）。

但是具体是哪一个我们也不清楚，因此返回结果以后，用户进程还要判断一下结果是否大于零，大于零代表有就绪的，那么它必须要遍历 pollfd 的数组，才能找到就绪的 fd。

#### 换汤不换药

从这一点来讲，跟 select 模式相比是不是没有改进？我们之前讲 select 模式有三大问题，现在一个一个对一遍：

| select 的三大问题 | poll 解决了吗 |
| --- | --- |
| 每次调用都要把 fd 集合从用户空间拷到内核，处理完再拷回来 | 没解决，poll 同样是这么做的 |
| 返回时只给就绪数量，还得遍历整个集合去找 | 没解决，poll 依然要遍历整个数组 |
| fd 数量被 1024 卡死 | **解决了**，poll 用的是数组 + 链表，理论上没有上限 |

所以 poll 唯一的改进，就是**增加了能够监听的 fd 的数量**。

那这会不会带来巨大的性能提升呢？**并不会。**

你想，每一次调用 poll 函数的时候，我们都需要去遍历所有的 fd 判断有没有就绪。那如果我们给的 fd 值非常非常大，这样来其实你遍历的过程消耗是不是也会越多？所以有可能你给的 fd 值非常非常多的时候，反而性能还会下降。

所以这种模式就是**换汤不换药**。虽然说 Linux 有这种模式，但基本上没有人去使用它。

### epoll：把 select 拆成两半

epoll 是对 select 和 poll 的一个巨大的改进，它的性能相比于前两种模式有非常大的提升。我们就来看看它为什么在性能上会有这么大的改变。

#### epoll_create：拿到一个 eventpoll

epoll 模式中提供了三个不同的函数。第一个是 `epoll_create`，它在执行的时候会在内核里创建一个叫 `eventpoll` 的结构体：

```c
int epoll_create(int size);

struct eventpoll {
    /* rbr stores the fds we are watching */
    struct rb_root   rbr;        /* red-black tree: ALL watched fds   */
    struct list_head rdllist;    /* ready list:    ONLY ready fds     */
    /* ... plus callback/wait-queue bookkeeping ... */
};
```

这个结构体里面有两个非常重要的属性：一个叫 **rbr**，一个叫 **rdllist**。

- **rbr 是一棵红黑树**，它里边的每一个节点就是一个要监听的 fd。我们知道 fd 是一个无符号的整数，从零开始不断递增，那既然是一个有序的整数，我们是不是可以用红黑树来记住它。
- **rdllist 是一个链表**，它里面记录的是就绪的 fd。

也就是说，**红黑树里记录的是所有的 fd，而链表里记录的是已经就绪、有事件的那部分 fd**。

```text
USER SPACE                         KERNEL SPACE
-----------                        ------------
epoll_create()
     |  ---- returns epfd -------->  struct eventpoll
     |                               +-----------------------+
     |                               | rbr     : rb-tree    | <- all watched fds
     |                               | rdllist : ready list | <- ready fds only
     |                               +-----------------------+
     |                                     ^
     |  epoll_ctl(epfd, ADD, fd, ev) ------+  insert node + attach callback
     v
 epoll_wait(epfd, events[], max, timeout)
     |                                     ^
     |  events[] is EMPTY on entry ---------+  only READY fds copied back
     v
 events[] now holds exactly the ready fds
 -> no scan, no filtering needed
```

epoll_create 创建完 eventpoll 实例以后，会返回一个对应的句柄叫 **epfd**，它可以看作 eventpoll 的唯一标识：每一个 epfd 就指向一个唯一的 eventpoll。每调一次 epoll_create 就会创建一个新的 eventpoll，像这样的对象其实可以有很多很多个——所以这个 fd 就是它的唯一标识。

#### epoll_ctl：往红黑树上挂一个回调

接下来我们就要去监听 fd 了，这时候会调用第二个函数 `epoll_ctl`。

```c
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);

#define EPOLL_CTL_ADD  1   /* insert fd into rb-tree   */
#define EPOLL_CTL_DEL  2   /* remove fd from rb-tree   */
#define EPOLL_CTL_MOD  3   /* change the event mask    */
```

跟我们之前讲的 select 或者 poll 相比，它的功能其实只具备 select 功能的一部分。因为不是全部。

select 里面它的功能是什么？**第一是监听，第二是等待就绪**。那么 epoll_ctl 的作用是把一个 fd 添加到我们的 eventpoll 里面去，也就是监听一个 fd——它只做添加，**可不会在那里等待你就绪**。

它有四个参数：

- **`epfd`**：这就是我们刚刚讲的那个 eventpoll 的句柄。根据它我就知道要把当前这个 fd 添加到哪一个 eventpoll 上面去。
- **`op`**：代表执行的操作。这里可以执行增、删、改三种不同的操作。增，顾名思义就是把当前指定的 fd 添加到对应的红黑树上（红黑树是用来记录所有要监听的 fd 的）；删，就是这个 fd 我不想再监听了，我就可以把它删掉；还可以执行 MOD 也就是修改，比如我想修改某一个 fd 想监听事件的类型，同样也可以去做。所以 epoll_ctl 可以做增删改三种操作，初始化的时候我们肯定是先去做增，把我们要监听的 fd 给它添加到这个树上去。
- **`fd`**：你要进行监听的具体 fd 的值，它是多少，根据这个值我们才能给你添加到这个树上去。比如这里我们添加了一堆，相当于监听了 3、5、6、7、8、9 这几个不同的 fd。
- **`event`**：要监听的对应的事件类型。也就是说，你现在监听这个 fd，只监听它的读事件、写事件还是其他事件，你要在这里指定一下事件类型。epoll 的事件类型有很多种，这里我们就不再赘述了。

那类型指定了以后他会干什么？在这里我们不仅仅会把多个 fd 添加到这棵红黑树上，而且**会给每一个对应的要监听的 fd 以及它的事件类型添加一个 callback 函数**，名字叫 `epoll_callback`。这个 callback 函数会在 fd 对应事件就绪时自动触发，所以它这种机制就是一种回调的机制，也就相当于是监听嘛。

这个回调函数里边的业务逻辑极其简单：**一旦我触发了，那我就把我对应的那个 fd 添加到 rdllist 这个就绪链表里**。也就是说，每一个 fd 都挂了一个回调事件，每当就绪了回调就被触发，一触发就把它添加到这个列表当中去了，相当于把就绪的 fd 记录下来了。

> **结论**：`epoll_ctl` 只负责添加 fd 进来，所以这个动作也是非常快的，一瞬间就结束了。它**不做任何等待**。

#### epoll_wait：那个空数组终于派上用场

现在监听已经听好了，回调函数也都已经设置好了，那我接下来是不是应该去等待它就绪了。所以第三步要做的就是 `epoll_wait`——它等于 select 还有 poll 这个功能的另外一半。epoll_ctl 做的是前一半（添加 fd 到我们这里去做监听），epoll_wait 做的是后一半（等待我们的 fd 就绪）。

```c
int epoll_wait(int epfd, struct epoll_event *events,
               int maxevents, int timeout);
```

- **`epfd`**：同样是那个 eventpoll 句，也就是说我要去监听的是哪个 epoll 上的这些 fd。
- **`events`**：加上星号，注意了，它是一个数组，而且**这个数组是一个空的数组**。这是跟之前 select 模式非常大的不同：之前在 select 里边我们调用 select 或者 poll 的时候，是不是要传一个 fd 的数组，把要监听的 fd 全传进去？但是因为我们现在已经在 epoll_ctl 里把要监听的 fd 添加进去了，所以当我们调 epoll_wait 的时候，就不需要了。所以在这个地方它只是指定了一个空数组，也就是说在这里创建一片空的内存空间，我这里的这个值仅仅是一个指向这个空间的指针，里边什么数据都没有。
- **`maxevents`**：你这个空数组所能允许的最大的空间。你得告诉我们的内核，因为内核将来要向这里面去写数据，所以你得告诉他你这空间最大有多大，别写超了。
- **`timeout`**：超时时间。`-1` 就是永不超时；`0` 代表我不等，如果没有就直接结束；也可以是大于零的一个具体的时间，比如 1、2、3。

那有人会问，你为什么要去把这个空的数组传进去？**这个大家别着急，等一会儿我再给大家去说。**

当我们去执行 epoll_wait 的时候，我们的内核首先会去检查一下——**检查什么？注意了，这里不是去检查这棵红黑树**。因为这棵红黑树随着这个程序运行的累加，它上面所要监听的 fd 的数量是不是会越来越多，如果去遍历它的话，那性能可想而知。

所以他会去检查谁呢？内核会**直接去检查这个就绪列表**。因为一旦就绪了，callback 是不是会把它添加过来？所以我不需要检查红黑树，我直接检查这个就绪链表，看这个列表中有没有元素。如果有，咱们就直接返回了；如果没有，就等一会儿（那个 timeout 设定的时间），然后看一看在这段时间内有没有就绪。如果说在这段时间内还是没有就绪，那我们还是一样返回零，告诉它没有任何就绪的。

但是如果这个时候比如说有两个 fd 就绪了，那么此时就会触发这两个 fd 节点的 callback，一旦触发就会把它俩添加到这个就绪的列表当中。所以此时我们的 epoll_wait 函数就发现了，说这个就绪列表中已经有元素了是吧，行，那二话不说就返回结果，返回的是就绪的元素的数量。这里就绪了两个，就返回二。

> **易错点**：那有人说不对呀，你只返回数量，我的用户进程怎么知道谁就绪了呢？

**这个时候刚刚传递的这个空数组就派上用场了。**你不是把空数组地址传给我了吗？数组是空的，它干什么用的？就是用来接收这些就绪的 fd 的。就绪的 fd 已经放到了这个就绪链表当中了，那我完全可以把链表的这两个元素拷贝到用户空间的这个数组当中去，这样一来用户进程就知道谁就绪了。

这里一定要跟我们之前的 select 和 poll 模式做一个区分：

- **之前在 select 或 poll 模式当中**，拷贝到用户空间的是**所有的 fd**，不管就绪的还是没就绪的，所以你的用户进程不得不遍历，一个一个判断谁就绪了。
- **但是在 epoll 模式当中**，我们拷贝过去的**仅仅是已经就绪的 fd**，因此作为用户进程来讲，**所见即所得**：我看到哪个 fd，就知道它是就绪了，不需要再去自己筛选。

我们遍历的仅仅是就绪的 fd，相比于 select 要去遍历所有 fd，性能上来讲是不是有大大的提升——这就是 epoll 模式中一个非常大的改变。

#### 三大问题是怎么被解决的

讲完流程，我们回过头来看看：epoll 到底解决了 select 或 poll 的哪些问题。

**第一个问题：拷贝。**

select 模式中的第一大问题，就是每一次调用 select 都需要把要监听的 fd 集合拷贝到内核，而每一次还要把结果拷贝回用户空间。

在 epoll 模式当中，这就是它的一个巧妙之处了：**我们把 select 函数的功能拆分开了**。

| select 做的两件事 | epoll 里的归属 | 调用频率 |
| --- | --- | --- |
| 把 fd 拷进内核去监听 | `epoll_ctl` | 每个 fd 只需要一次 |
| 等待这些 fd 就绪 | `epoll_wait` | 循环里每次都要调 |

同学们思考一下，将来我们再去循环执行的过程中，我们要监听一个新的 fd 时，其实执行一次 `epoll_ctl` 把它加进去就完了。在以后的循环过程当中，我还需不需要再一次去执行 `epoll_ctl` 完成这个添加的动作了？**不需要了吧**——因为你添加一次这个树上就有了，它又不会删，所以它一直在这里。

所以说 epoll_ctl 这个函数，相对于每一个 fd 来讲，它只需要去执行一次、拷贝一次就完了。以后循环处理事件的过程中，都是循环地执行 `epoll_wait`，而 epoll_wait 只需要去等待就行了，它不需要去把 fd 往这边拷贝。相比于 select 模式和 poll 模式，是不是减少了无数次的这种 fd 数据的拷贝？

第二，再来看把结果向用户空间拷贝的这个过程。在 select 模式和 poll 模式当中，我们每一次要把内核中所有的 fd 都拷贝回用户空间，管它就绪的还是没就绪的。但是在 epoll 模式中，我们**只拷贝了就绪的这些 fd**。虽然每一次 wait 以后结果也要完成拷贝，但是我们的拷贝数量相比较于 select 和 poll，是不是都少了很多？

综合来讲，epoll 模式第一是**大大减少了拷贝的次数**（循环执行 wait 的过程中不用再拷贝 fd 了，每个 fd 只用拷贝一次），第二是**大大减少了拷贝的数量**（每一次只需要去拷贝就绪的 fd，未就绪的不用管）。

**第二个问题：不知道谁就绪。**

在 select 模式当中执行完 select，返回的是就绪的 fd 的数量，而拷贝到用户那里的是所有的 fd，你并不知道哪些是就绪的，你不得不一个一个遍历。

但是在 epoll 模式当中，虽然我们返回的也是就绪的 fd 的数量，但我拷过去的仅仅是就绪的，所以你不用自己去遍历和判断了。你拿到这个数组中的每一个 fd，可以确保它一定是就绪的。所以第二个问题是不是也解决了——你不用遍历所有 fd 了，只要拿着一部分 fd 就可以了。

**第三个问题：fd 的数量。**

select 模式当中因为它的位图设计，`fd_set` 最多能监听 1024 个 fd。poll 模式虽然改成了链表，允许监听 fd 的数量没有上限，**但这只是理论上没有上限**。因为它的底层设计是链表，你所有要监听的 fd 都串在一起，如果 fd 数量非常非常多，将来这个链表就超级无敌长，那你每遍历一次要花费的时间是不是也非常久？所以它其实虽然理论上是无限，但实际上受限于性能，它不可能加很多，只能是一个有限的增加。**它是伪无限。**

而 epoll 模式当中，我们从用户空间添加过来的每一个 fd 都会放到红黑树上。红黑树理论上能够支持的数量是不是无限的？再看遍历性能：假设真的要去遍历这棵红黑树，我们知道红黑树的增删改查性能不会随着树上元素数量的增加而有太大波动，也就是说它的性能基本上是稳定的。所以哪怕我真的增加了很多很多，将来真的要去遍历，会不会有太大的性能上的影响呀？**不会。**

所以这种 fd 监听数量的增加才是**真**的增加：允许你的 fd 非常非常多，而且是真的允许，不会导致监听的 fd 过多而影响性能。相比较于 select 模式和 poll 模式，epoll 模式是真的可以监听尽可能多的 fd。

> **结论**：epoll 模式基于红黑树来保存要监听的 fd，理论上没有上限，而且增删改查性能非常高，不会因为 fd 数量增加而产生显著下降——**真无限，不是伪无限**。每个 fd 只需要执行一次 `epoll_ctl` 就能添加到红黑树去，以后每次 `epoll_wait` 不用再传任何参数，不用重复地把 fd 拷贝到内核空间；本质上就是把 select 函数的功能分成两份，把执行频率较高的 `epoll_wait`（等待和监听）以及执行频率较低的添加 fd 拆分开了。最后，内核只把就绪的 fd 拷贝到用户空间，用户就不用去遍历所有 fd 了，立刻就能知道到底谁就绪、谁没就绪。

### 三种方案摆在一起看

到这里，IO 多路复用的原理以及三种实现方案的优缺点就全部分析完了，可以看到 **epoll 模式是完胜**。所以现在一些高性能的网络框架当中，基本上都是基于这种 epoll 模式来去实现的。

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 集合的结构 | `fd_set` 位图，写死 1024 bit | `pollfd` 数组，内核转成链表 | 红黑树存全部 + 就绪链表 |
| 每次调用的拷贝 | 进一次、全部回一次 | 进一次、全部回一次 | 每个 fd 只进一次，只回就绪的 |
| 返回给用户的数组 | 全部 fd（就绪的置 1，未就绪置 0） | 全部 fd（含未发生的 `revents`） | **只有就绪的 fd** |
| 用户要不要自己遍历 | 要，且遍历全部 | 要，且遍历全部 | 不用遍历，按数组处理即可 |
| fd 数量 | 固定 1024 | 理论无限、实际受链表遍历限制（伪无限） | 真无限，且不影响性能 |
| 实践中是否用得多 | 少 | 基本没人用 | 高性能框架基本都用它 |

最后补一句我们这次的范围：我们现在讲的仅仅是 **Linux 平台**上面的三种实现。事实上 Windows、macOS 上它们对于 IO 多路复用也会有自己的实现，这里就不在我们的课程中去讲了，大家如果有兴趣也可以自己去查看一下、学习一下。

## epoll 事件通知机制与 Redis 的单线程选择
> 对应块：BLK50 | 覆盖分集：P167-P170 | 块标题（分集名）：《原理篇-23.Redis网络模型-epoll的E》

前面几节课，我们把 select、poll、epoll 一个个拆开看，知道 epoll 靠的是内核里的一个实例，替我们同时盯着成千上万个 fd。但盯住只是第一步——**它凭什么告诉我们"哪个 fd 好了"？**

这就是 IO 多路复用的最后一块拼图：事件通知机制。

先说清楚它是什么。其实就是当我们去调用 `epoll_wait` 的时候，如果说我们对应的 epoll 实例上它的一些 fd 就绪了，比如说啊有数据可读了，那么我们就可以得到对应的这个事件的通知。

而这个通知的模式，有两种。一种叫 level trigger，简称 LT；另外一种叫 edge trigger，简称 ET。

### 就绪通知的两种脾气：LT 与 ET

LT 是这样定义的：数据可读时会**重复**得到多次通知。也就是说每一次你调用 `epoll_wait`，它都会告诉你说"这个 fd 就绪了"，直到你把 fd 中所有数据都处理完为止。这也是 epoll 中的**默认模式**。

ET 则不同。fd 就绪的时候，你第一次调用 `epoll_wait`，它会通知你说就绪；但是如果你重复地去调用，它就不会再去通知你了——也就是说只通知一次，不管你 fd 中的数据是不是已经被处理掉了。

这么说可能还是有点抽象。我们来举一个具体的例子。

现在假设有一个客户端的 socket，它对应的 fd 已经注册到了我们的 epoll 实例上。这时它发送了 2KB 的数据，那么意味着现在 fd 已经有数据可读了。此时如果我们去调用 `epoll_wait`，那肯定就会得到通知，说这个 fd 就绪了，然后我们就可以去读数据。

而读数据的时候，我们不可能一次性把所有数据都读完。所以这里假如说我们分批去读，先读了一 KB 的数据，这样一次数据的处理其实就完成了。但是因为没有读完，所以我们还要再重复。重复到哪了呢？再次调用 `epoll_wait`，再问一下：诶，你有没有准备好？有没有数据啊？那么这个时候就会有差异了。

```text
  kernel buffer :  [ 2 KB data ]

  LT   epoll_wait -> NOTIFY -> read 1KB -> 1KB left
       epoll_wait -> NOTIFY -> read 1KB -> 0 left
       epoll_wait -> no data, no more NOTIFY

  ET   epoll_wait -> NOTIFY -> read 1KB -> 1KB left
       epoll_wait -> already notified, SILENCE  (forever)
```

> **结论**：LT 循环往复，直到把所有数据读完为止。ET 呢，第一次通知完就再也没动静了，那剩下的这 1KB 是不是再也没有机会被处理了？这就是 LT 和 ET 的差别。

ET 那边为什么这么绝情？讲师当时是这么吐槽的：已经通知过一次了，你自己没有处理完，怪谁呢？给你机会，你不中用啊——机会是不等人的，你错过了，那肯定就不会再通知你了，对不对？

### 就绪链表里到底发生了什么

那么为什么会出现这种差异呢？我们还是通过之前讲的 epoll 实例内存图来给大家分析一下。

现在呢，这里的 event 实例已经初始化完成了。我们假设现在有很多 fd 正在被监听，然后呢，现在有几个 fd 就绪了。那此时这些就绪的 fd 就会被添加到就绪链表当中。

现在假如我们调用 `epoll_wait`，那么我们就需要去通知用户说这个 fd 就绪了，对不对。我们当时讲过，一方面是要返回一个结果，告诉它有几个就绪了；另一方面是要把就绪的 fd 拷贝到用户空间去。

但是啊，我们之前只是**假说**要拷贝，其实在这背后他还要做一个动作。

**在拷贝之前，它会将这两个 fd 从就绪链表当中给它断开**，也就是说把那个指针给它移除。因为它认为你要去处理了，所以就先移除掉了，然后再去完成这个拷贝的动作。

那这个时候我们的用户是不是就可以去处理这个数据？但是呢，假设说我们现在数据没有处理完，只处理了 1KB，那么这两个 fd 其实还有数据。所以这个时候我们的内核其实还要多做一件事情。

做什么事情呢？**他要做一次检查，检查你当前采用的模式是 LT 还是 ET。**

```text
   fd ready
      |
      v
  [ ready list ] <-----------------------------------------------+
      |                                                          |
      |  epoll_wait: copy events out to user space                |
      |  (before copying: unlink these fds from the ready list)   |
      v                                                          |
   check the trigger mode                                         |
      |                                                          |
   +--+------------+                                            |
   |  LT           |  ET                                        |
   |  still has    |  done. they are gone,                     |
   |  data ?       |  never notified again                      |
   +--+------------+                                            |
      |                                                          |
      +-- YES: link them back into the ready list ---------------+
```

分两种情况：

- **如果是 ET 模式**，那结束了，这两个干掉了，这个就绪队列里再也没有你们了。所以你下一次再来调 `epoll_wait` 的时候，就绪列表中其实是空的了，所以你得不到通知了。
- **如果我们是 LT 模式**，那内核一看：哦，你用的 LT 是吧，而且这俩还有数据啊？那不行，那我不能给你删了。所以它会**把它再次添加回就绪链表当中**。这样下一次你再来调 `epoll_wait`，它一看这里有，是不是还会再拷贝给你啊？这样就可以实现重复的读取了。

这就是 LT 和 ET 在内部实现上的一些差异。

### 想用 ET，就得自己把数据读干净

讲到这儿呢，有同学就会说了：那你这个 ET 模式感觉没啥用啊，每次读取都会残留数据，导致这个读不到啊。

这是因为我们现在采用的读取方式啊，其实更适合 LT。那如果说我们现在想要使用 ET 模式，在读取方式上我们可以做一些改变，来解决这个残留数据的问题。这里有两种方案可以解决。

#### 方案一：手动把 fd 加回就绪列表

刚才我们说了，LT 模式它是在拷贝完了以后，要把这两个重新添加回就绪队列；而 ET 则是拷贝完了直接把它干掉了，也就不会再添加回去了，对不对。

那既然如此，那我们再想了：我用了 ET 模式内核不帮我们重新添加回就绪队列，**我们能不能手动添加呢？** 答案是可以的。

什么意思呢？也就是说我第一次调用 `epoll_wait`，我发现 fd 里有数据，然后我读了一 KB，是不是还剩一 KB？也就是说呀我还得再调一次 `epoll_wait`，再来读取一次这个 fd 中的数据才能够读完。但问题是在你第一次调用那一刻，这两个就绪的 fd 已经从就绪列表中移除了，也就是说我们现在如果再找一次，是不是就得不到通知了。

因此呢，我们必须在第一次读完数据之后，如果还有数据的情况下，**手动地把这两个 fd 再添加回这个就绪列表中**。

怎么添加呢？在这儿呢我们去调用一个叫 `epoll_ctl` 的函数。那 `epoll_ctl` 我们之前讲过，它的作用其实就是去增删改查 epoll 实例上面对应的 fd。在这里呢我们其实可以去尝试做这个"修改"的动作，修改这个 fd 上的一个状态。那当我们去做修改时，`epoll_ctl` 会检查一下对应的 fd 是不是真的还有一些就绪的事件、有没有对应的数据。如果有，它就会再次将这两个 fd 添加回就绪队列，也就等于是手动把它加回去了。

那既然手动加回去了，那下一次我们再重复调用 `epoll_wait` 的时候，是不是又会得到通知了？

```text
  Route 1: link the fds back by hand

    epoll_wait -> NOTIFY -> read 1KB -> still 1KB ?
                                          |
                                 epoll_ctl(MOD) on those fds
                                 (kernel checks: really ready?)
                                          |
                            linked back into the ready list
                                          |
    epoll_wait -> NOTIFY -> read the rest -> done
```

那既然手动加回去了，LT 是人家内核自动帮你重新添加回去；那么 ET 模式下呢，你可能需要去手动添加。而且呢，每一次手动添加回去以后，我们再去循环调用 `epoll_wait` 的时候，它就要重复地再去通知你，再一次做这种内存的拷贝——**那就等同于返回成 LT 模式了**。那么这种重复的通知对于性能其实是会有很大影响的。

#### 方案二：一次通知里循环读到空

当然如果你不想用这种方案，还有一种办法。那就是在读数据的时候——既然每一个 fd 它就绪时你只通知我一次，那我为什么不在**这一次通知中**把数据全部读完呢？

我一次只能读 1KB，对不对？那我如果循环读呢？我在这写个 while(true) 是吧，循环地尝试从这个 fd 里读出去，直到把 fd 数据读完为止，然后我就不用再重复了嘛，一次性读完。

但是呢，大家需要注意哦——如果你在这个 while 循环里不停地读数据，**你千万不能用阻塞 IO 的模式来读**。

为什么呢？如果你采用阻塞 IO 的模式去读，你想啊：我先读了一 KB，然后循环里又读一 KB，紧接着我又来读，因为你要持续地读直到没有为止，对不对。但是阻塞 IO 它有一个问题，就是如果读到 fd 里已经没有数据了，它不是会返回一个错误，而是会**一直卡在这里等**，一直等一直等一直等，等到下一次再来数据为止。

这样一来等于什么？等于我们的第四步就陷入这个循环出不来了，那么整个进程就被阻塞了。

```text
  Route 2: drain it in one single notification

    epoll_wait -> NOTIFY -> enter the loop
                                         |
             +------------------------ read(fd, .., NONBLOCK)
             |                            |
             |             +--------------+--------------+
             |             |                             |
         got data                     EAGAIN : nothing left
             |                             |
       keep reading                    break the loop
             |                             |
             +-------> back to the top      done
```

因此啊，如果你想在一次通知中把所有数据处理完，**你一定要采用非阻塞 IO**：我读的时候如果有数据就返回，如果没数据它也返回，只不过会返回一个标识告诉你说没有了。那当我判断没有的时候，我是不是可以跳出循环？这样是不是就避免了这种循环读取导致的阻塞了。

好，所以说呢，ET 模式可以通过两种不同的方案来去解决这个数据读取的问题。因此它跟 LT 相比，除了在实现上复杂一点，最终都能够实现对于 fd 数据的读取。

> **提示**：这两种方案本质上都是在补 ET 故意留下的窟窿——ET 只保证"状态发生变化时通知你一次"，至于你有没有把数据处理干净，它从此再也不管。

### LT 的两个包袱

那有的同学会说了：你这个这么复杂，我为什么要用呢？我就用 LT 不就好了？

在这里呢，就不得不提到 LT 模式它所存在的几个问题。

#### 重复通知的开销

因为这个 LT 啊，它是一种**重复通知**，也就是说我每一次来调用 `epoll_wait`，只要这个 fd 还有数据，它就一直通知一直通知，对不对？

看起来能够确保这个数据能够彻底读完，但是同时这种重复的通知啊，对于效率、或者说对于性能都是会有影响的。这是 LT 的第一个问题。

#### 惊群现象

第二个问题啊，是 LT 可能会出现一种**惊群**的现象。

什么叫惊群现象呢？我们假设说现在有 N 个不同的进程，他们都监听到了当前 epoll 实例中的某一个 fd，并且呢他们都在调用 `epoll_wait`，尝试去获取就绪的 fd。结果是呢，这个 fd 真的就绪了，然后就会去通知我们的进程。

那现在，LT 模式当中任何的一个进程，它通知完成以后，其实这个 fd **还会存在在列表当中**。这也就导致了所有监听这个 fd 的进程是不是最后都会被通知到——也就是说**一个 fd 就绪，所有的进程都会被唤醒**。这其实就是一种惊群的现象。

而真正在处理的时候呢，可能前面的一两个进程就已经能够把 fd 的所有数据处理完了，那后续这些被唤醒的进程是不是就没有必要去被唤醒了？

然而 ET 模式就不会出现这个问题啊。因为 ET 模式中第一次通知完，它直接移除了，后续的进程就不会得到通知。

| 对比维度 | LT（水平触发，默认模式） | ET（边沿触发） |
| --- | --- | --- |
| 通知次数 | 只要 fd 还有数据，就反复通知 | 只在就绪状态变化时通知一次 |
| 惊群 | 可能出现惊群现象 | 不会 |
| 把数据读干净 | 内核自动放回就绪链表，天然支持分批读 | 手动 `epoll_ctl` 加回，或非阻塞循环读到空 |
| 实现复杂度 | 简单 | 相对复杂 |
| 性能 | 有重复通知与重复拷贝的开销 | 更好 |

所以综上所述，LT 模式虽然实现起来更简单，但是它可能会存在性能上的问题以及惊群的问题；ET 模式呢虽然实现起来相对复杂，但是却没有这样的问题，相对来讲性能会更好一点。

所以说呢，其实我们可以根据自己的需求：如果你对这一点的性能不太在意，那你就可以用默认的 LT 模式；否则，我们还是建议大家使用 ET。

> **结论**：ET 模式避免了 LT 模式可能出现的惊群现象，并且我们可以利用 ET 模式结合非阻塞 IO 去读数据，虽然实现起来相比 LT 会复杂一点，但是性能上来讲会更好一点。

### 拆开一个基于 epoll 的 Web 服务

接下来我们带着大家分析一下：基于 epoll 模式实现一个 Web 服务，它的运行流程应该是什么样子的。

在这里没有代码，我们通过流程图的形式给大家分析。

```text
=========================== KERNEL SPACE ==========================
  red-black tree : every fd registered through epoll_ctl
  ready list     : fds that are currently ready

  epoll_callback : bound at registration time; fired as soon as
                   its fd becomes ready, which puts the fd into
                   the ready list

  epoll_wait     : scan the ready list, copy the events out
=================================================================

----------------------------- USER SPACE -------------------------
  1. epoll_create()              -> get the instance above
  2. init the server socket      -> ssfd (server socket fd)
  3. epoll_ctl(ADD, ssfd, EPOLLIN, epoll_callback)
        |
        v
  4. epoll_wait()
        |
        +--> returns 0   : nothing is ready, loop back to 4
        |
        +--> returns n>0 : go on, dispatch every ready event
                              |
                              +-- EPOLLIN  and  data.fd == ssfd ?
                              |     YES -> accept() -> client fd
                              |            epoll_ctl(ADD, cfd, ..)
                              |            loop back to 4
                              |
                              +-- EPOLLIN  on a normal client fd ?
                              |     YES -> read the request
                              |            run the business
                              |            write the response
                              |            loop back to 4
                              |
                              +-- error / other events ?
                                    YES -> write an error response
                                           loop back to 4
==================================================================
```

读图说明：上半部分全部在内核空间执行——红黑树管"在听谁"，就绪链表管"谁好了"，`epoll_wait` 只负责从链表上取事件；下半部分在用户空间，从建实例、注册、等待一直到事件分派，全是用户进程自己在转。

现在我们把这个流程一步步走一遍。

服务端在启动以后，首先就要基于 `epoll_create` 去创建一个 epoll 的实例。当我们去创建这个 epoll 实例的时候，我们当时讲过，其实它的本质就是在内核里边去准备了两个东西：**第一个是红黑树**，用来记录要监听的那些 fd；**第二个是一个链表**，用来记录就绪的 fd。那么等这个事情做完，准备工作就完成了。

接下来我们就可以去初始化这个 server socket 了。因为我们这里是一个外部服务，而 Web 服务都是基于 TCP 协议的——在 TCP 协议里，服务端就是一个 server socket。那 server socket 它在 Linux 内部同样也会被看成是一个文件，所以说他也有自己的文件描述符，也就是 fd。在这里呢，它叫 server socket 的 fd，所以我们把它记住是 **ssfd**。

那么接下来 fd 有了，我们就需要把它注册到这一个 epoll 实例上了。那么注册我们用的是哪个命令啊？是不是叫 `epoll_ctl`？没错。那只要指定这个 ctl 的类型是新增（`EPOLL_CTL_ADD`），它就会将我们这个 fd 添加到这个红黑树上去了。

同时啊还要做一件事情，就是给添加到红黑树上的 fd 绑定一个回调函数，回调函数的名字叫 `epoll_callback`。这个回调函数一旦就绪就会立即执行，而就绪的 fd 会被挂进就绪链表——所以这个链表记录的其实就是就绪的 fd。

到这里其实我们监听的动作就完成了。下一步我们要做的事情就是去等待它就绪了。那这次是哪个命令啊？是不是叫 `epoll_wait`？`epoll_wait` 就是等待 fd 就绪，它其实做的事情就是会去检查我们的就绪列表，看看这些列表上有没有元素。如果有，那就直接返回了；如果没有呢，那他就会等待指定的时间，就是你这里传参数传了多少秒，它就等待多少秒。如果在等待的这段时间内有 fd 就绪，那么同样它也会被唤醒，然后读取到这些就绪的 fd 并且返回。当然如果等到最后它都没有任何 fd 就绪，那只能是返回一个 0，告诉我们的用户进程就是这个没有就绪。

因此呢，我们执行 `epoll_wait` 以后，**必须判断一下当前结果有没有就绪**，也就是说这个返回值是不是 0。那因此它的结果有两种嘛：要么有，要么没有，对不对。那如果没有呢，二话不说，直接就重新执行 `epoll_wait`，循环不停地执行，直到就绪为止。

那么同学们，什么时候我们的这个 fd 会就绪啊？作为 server socket 来讲，**只有一种情况它会就绪，就是有客户端在向它申请连接**。因为 server socket 它的唯一目的就是接收客户端请求嘛。所以一旦有任何客户端的 socket 尝试着跟它建立连接，这个时候它上面就会产生 fd 的事件了，而且是读事件。

不过随着我们这个程序的运行，将来呢，我们这个 epoll 实例上监听的 fd 也越来越多，事件的类型啊也会越来越多。所以说呢，这个 fd 就绪以后，我们其实应该去判断一下当前事件的类型到底是什么。那如果我们的结果是 `EPOLLIN`，那就代表它真的是一个读事件，对不对。那么读事件是在读谁呢？是不是来读我们当前的这个 ssfd？如果是，那才证明是有客户端连上来；如果不是，那就是有其他的事情。所以在这个地方呢，我们还要再判断一个，就是当前是有事件，是谁可读了呀？是 ssfd，那就是 server socket 可读，那就证明真的是客户端要连接了，那就要去调用 `accept` 接收客户端的 socket。

那一旦接收到了客户端 socket，我们就得到了客户端 socket 对应的这个 fd 了。那接下来我们是不是应该监听这个 fd？所以说呢，又要执行 `epoll_ctl`，把它注册到我们的红黑树上去，当然还要注册回调函数。接着我们就继续去 wait。那如果再有客户端连上来，是不是又重复这个流程啊？那于是呢，这个过程就不断重复不断重复。随着这个时间的推移，连接到我们 server socket 上的客户端越来越多，我们监听的 fd 是不是也越来越多。

那么接下来，客户端可能就要去发请求给我们了啊。那客户端发请求过来以后，也就意味着有请求参数，是不是也会触发 fd 事件啊？而且也是读事件。当然这个地方呢，读的可能性还是有两种啊：有可能是 ssfd 可读，那是新客户端来了；当然也有可能不是。如果不是，那就证明当前要读的是一个普通的客户端 socket，代表他有请求参数来了。那此时我们就应该去读取它里面的请求参数，然后呢去处理这个业务。等业务处理完，咱们是不是可以去返回这个响应结果了？直接写到客户端 socket 里，响应就结束了。到这儿呢，其实一个 Web 服务的整体流程就算是完了。

当然了，我们在执行过程也不可能完全一帆风顺啊，在执行的过程中很有可能也会出错。那么出错的时候可能就不是读事件了，而是一些异常事件。如果这个地方是 error 之类的各种各样的异常，那么我们其实也应该返回给客户端，也要给他写响应，但是这个响应该写的可能就是异常信息了。

那么从整体来看啊，其实我们利用 epoll 来实现一个 Web 服务，就是利用我们 IO 多路复用的机制来实现对于事件的监听。不管是什么样的事件来了以后，我们呢只要去分门别类地去处理就行了。那事件无非就这么几种：要么就是客户端连接的事件，要么呢就是客户端数据可读，要么呀就是异常。客户端连接事件来了，我们就建立新连接并且监听就完了；客户端请求来了，那是读事件，我们就读出请求并行处理，并且返回就完了；如果是一个异常，同样去返回。

所以啊，其实就是一个接收事件，然后把事件做派发，派发给不同的业务去处理，最后处理事件这样一个过程。

> **注意**：在整个流程当中，其实我们画这个图也不是随便乱画的。可以看到在上半部分，其实执行的所有的业务都属于是在内核空间去执行，而下半部分这些呢，是在我们的用户空间去执行的。

好，那分析这个其实是为了让大家对于 epoll 的流程有一个更清晰的了解，也同时是为了我们后去讲解 Redis 的网络模型做准备的。因为 Redis 的底层啊，其实就是基于这种 epoll 模型，而 Redis 本身其实也就是一个 TCP 的服务端，就类似于我们的 Web 服务。那大家可以想象一下，将来我们的 Redis 到底是做了些什么事，基本上就跟这个流程是差不多的。

### 剩下的两种 IO 模型

截至目前为止，我们已经学习了 Linux 5 种 IO 模型中的前三种，特别是 IO 多路复用啊，这种模式呢因为比较高效，而且呢在现在可以说使用的频率是最高的，所以我们在这块花费了大量的时间去学习，特别是其中的这种 epoll 的模式。

那最后还有两种 IO 模型啊，信号驱动 IO 和异步 IO，那么这两种使用的相对来讲就少很多了，所以在这里呢我们带大家快速地过一下。

#### 信号驱动 IO

用户进程一上来，他同样调的不是 `recvfrom`，而是一个叫 `sigaction` 的指令。那么这个指令啊，一上来就会向内核当中去指定一个 fd，并且向其绑定一个信号处理的函数，然后呢立即结束，也就是说他不用阻塞等待。

那么如果这个时候没有数据，没关系，内核呢会帮我们去监听。那如果这个 fd 有数据了，就会被唤醒，并且呢递交一个信号给我们的用户进程。那么我们之前注册的那个信号处理的函数，是不是就可以去处理这个信号，知道说有数据就绪了。

而在整个过程中，我们用户进程可以去干别的事情啊，根本不用去阻塞等待。那拿到信号了以后，证明现在有数据就绪了，我们的用户进程去调用 `recvfrom` 去读取数据。那读取数据的过程，也就是从内核空间拷贝到用户空间的这个过程，那还是要去等待的啊。那等读取完成啊，我们再去完成数据处理就 OK 了。

所以从这可以看到啊，在信号驱动 IO 当中：

- **一阶段**因为仅仅是注册了一个信号处理的函数，所以呢它是非阻塞的。他可以去干别的事情，比如说我们可以去处理其他的客户端请求，所以说呢它的性能相对来讲是比较好的。
- **二阶段**读数据的阶段依然是阻塞的。

那这种呢，跟我们之前的非阻塞 IO 大家要区分开：非阻塞 IO 一阶段也是非阻塞、二阶段阻塞，一样。但是啊，不一样。

那非阻塞 IO 它采用的方式是什么？是不停地去询问："你准备好了吗？你准备好了吗？"事实上我们的用户进程，它虽然是不用阻塞的，但它其实做的是无用功。

而我们在这里呢，我们只是注册了一个处理函数，我就不用管了，我就可以做正事去了，忙别的事去了，处理其他的客户端请求，直到你数据就绪了你再来通知我。因此呢这种模式啊，其实才是真正的这种非阻塞，相比于之前的非阻塞 IO，它的性能会更好一点。

那有同学就要说了：这种模式这么好，为什么我们不用这种，而是用 IO 多路复用之类的东西呢？这是因为啊，这种模式它也存在一些缺点。

**第一**，如果我们现在有大量的 IO 操作，也就是说现在信号是不是非常非常的多、并发非常高，那么无数的信号提交给我们的用户进程，这个时候它会放到一个队列里边依次去处理。那如果说信号过多，可能会导致这个信号队列溢出，那可能部分信号就丢失了。

**另外**，在不断地传递信号过程中，就需要频繁地将信号从内核空间拷贝到用户空间，那么这个时候其实性能也是会受到影响。

所以综上所述啊，这种模式它其实在并发的场景下，还是会存在一定的问题的，因此呢使用的也不是很多。

#### 异步 IO

下面呢我们再来看一下最后一种 IO 模型啊，异步 IO。

你同样来看这幅图，你会发现异步 IO 更神奇啊——它在这里**根本就没有调用 `recvfrom` 那个函数**，也就是没有调用那个数据拷贝的函数。它是怎么做的？

它上来调了个叫 `aio_read` 的调用。这个调用啊是通知内核：我想读哪个 fd，然后读到哪里去，好，不管了，然后直接就结束了，返回一个 ok，然后他就干别的事去了。然后我们的内核会去监听 fd，然后等待就绪，然后被唤醒，当数据直接从内核拷贝到用户空间，再来通知你：好，成功了。

你看了吗？他不是说就绪了就通知你哦，他是就绪了——别着急，我把所有事都办完了再来通知你。是不是一个全方位一条龙服务的保姆？你啥都不用干，你只要通知我就行了，剩下的事我全部搞定，再来通知你。相当于我们这是领导在给这个下属指派任务，所有任务都是他做的，最后功劳是我们这个领导的，对不对？是这样一种模式。

这种模式听起来是不是非常爽啊？完全地实现了一个非阻塞，不管是一阶段还是二阶段，用户进程都不用管啊。听起来非常爽，对不对？那为什么我们不去使用这种模式呢？

这种模式确实非常优秀，但是它也同样会存在那么一两个问题。

什么问题呢？因为用户进程不用阻塞，那他干什么去？他是不会去处理新的用户请求。那新的用户请求来了以后，是不是又要调 `aio_read` 去通知内核去完成数据拷贝？

那这样一来，在高并发的情况下，同学们先看看是不是啊：不停地处理请求，不停地交给内核去处理。相当于这个领导啊，不管这个下属的死活，我一直给你安排任务，一直安排任务。那么这样一来，我们的内核里积累的这样的 IO 读写的任务是不是会越来越多？因为 IO 读写的效率是比较低的嘛。所以说呢，这里具体的任务越来越多越来越多，而每增加一次任务，可能就会有大量的这种内存的一些消耗。那么如果在高并发情况下，很有可能导致整个系统啊，因为内存占用过多出现崩溃的现象。

所以呢，你要使用异步 IO，你必须做好什么？你必须做好对于这种并发访问的**限流**，那一定要去做这种限流的工作啊。再加上这里这种回调函数的机制，它实现起来的代码的复杂度是不是就高很多了。

所以啊，不是异步 IO 不优秀啊，只是我们刚才讲了两个点：就是你要去控制它的并发，让它实现起来相对比较繁琐。所以说呢，这种模式其实也有使用，但是呢就不如我们之前讲的 IO 多路复用——它的并发能力也很好，然后实现起来相对也比较简单，使用得更加广泛一些。

### 同步与异步，到底怎么判

最后让我们去做一个这样的总结啊。异步 IO 在最后两个阶段它都是非阻塞的。相比于以前，我们之前讲了总共五种嘛，只有最后一种 IO 是叫异步 IO，前面的都没有叫这个名字，对不对？

那么这里就有一个问题了：**什么是同步？什么是异步呢？**

在 IO 操作里面判断同步还是异步，它的判断标准是——**从数据从内核空间到用户空间的这个拷贝的过程**。

我们讲 IO 读的时候不是分两步吗？第一步是不是等待数据就绪呀？第二步是不是从内核空间拷贝到用户空间呀？好，两个阶段。那我们判断同步与否，就是看这个拷贝的过程，也就是第二阶段到底是阻塞的还是非阻塞。

| IO 模型 | 一阶段：等待数据就绪 | 二阶段：从内核拷贝到用户空间 |
| --- | --- | --- |
| 阻塞 IO | 阻塞，一直阻塞直到完成为止 | 阻塞 |
| 非阻塞 IO | 非阻塞（不停地轮询，其实是在做无用功） | 阻塞 |
| IO 多路复用 | 阻塞（等待 fd 就绪） | 阻塞（真正去读数据） |
| 信号驱动 IO | 非阻塞（靠信号通知） | 阻塞（数据拷贝依然要等） |
| 异步 IO | 非阻塞 | 非阻塞 |

所以综上所述啊，**只有异步 IO 的二阶段是非阻塞的，所以只有它才能称之为异步 IO**。

> **易错点**：在 IO 当中，同步、异步并不是跟阻塞、非阻塞有这种强的关系。阻塞 IO 或者是非阻塞 IO，本质都属于同步 IO。千万不要把同步异步跟阻塞非阻塞混为一谈。

目前在使用的相对较多的就是 IO 多路复用，在少数情况下也会用到这种异步 IO。

### Redis 是单线程还是多线程

经过前面这么多节的铺垫，我们终于来到了最后一小节 Redis 网络模型。那这一节啊，我们就会一起来分析一下 Redis 它到底使用了我们 Linux 中的哪一种网络模型，又对它做了什么样的一些封装和改变。

不过在这之前，我们还要先弄清楚两个问题——也是两个热点的面试题。

第一个，Redis 到底是单线程还是多线程？这个问题相信很多同学可能脑海中有那么一点印象，但是大部分同学的答案应该都不太准确。在这里我给大家一个标准的答案。

如果说我们面试官问你 Redis 是单线程还是多线程，那你就反问他了：**咱们现在讨论的是 Redis 的核心的业务处理部分，还是说整个 Redis？** 你就问问他啊。

然后呢你就说了：如果你想讨论的是 Redis 的核心业务部分，也就是命令处理部分，那我明确地告诉你就是**单线程**；如果咱们聊的是整个 Redis，那么答案就是**多线程**。你看看这是不是显得咱们这个回答非常的严谨。

那你可能会好奇：这里为什么会有这么多细节？其实是因为 Redis 它在不同版本迭代的过程中，引入了一些新的东西。

在最早的 4.0 的时候啊，其实就已经引入了多线程了。那那个时候引入多线程呢，主要是处理一些耗时较长的一些任务，特别是一些后台的进程。比方说我们以前讲过，对于一些 big key 啊，我们直接去删除它的话，可能就会导致主线程阻塞，耗时非常久。那因此呢，这个时候往往会采用一种异步删除——先把它标记成删除，然后后台用一个线程慢慢去删它。比如说我们这个 `UNLINK` 命令其实就是这样子的。

所以呢，从那个时候开始，在 Redis 内部其实已经有多线程了。当然了它的核心部分也就是命令处理部分，其实还是主线程。

不仅仅如此啊，其实那个时候，除了命令处理以外，它的整个网络模型都是单线程的。但是尽管它是单线程，因为它的底层采用了我们 IO 多路复用的机制，所以说呢它的性能啊可以说是非常的好，即便是在单机模式下，也能够做到每秒钟数万的这样的一个并发。那因此呢，在很长一段时间内啊，Redis 都是基于这种单线程模式，核心网络模型也都是单线程的，只有在一些边缘任务时才会用多线程。

但是呢，这种情况持续了一段时间啊。随着我们业务的发展，然后呢各种硬件设备也不断地去提升，那我们的服务器往往可以做到 16 核、32 核甚至 64 核甚至更多，所以硬件性能也是越来越强。那我们的 Redis 如果还是采用单线程，就没有办法充分地去利用这种高性能的硬件设备。

有些会说了，那我们可以做集群呢？没错，在早期确实是这么做的。但是我们知道搭建集群是不是会引发一些其他的问题啊，所以说呀这并不是一种最佳的方案。

那于是呢，到了 Redis 6.0 的时候，作者终于引入了多线程。**在它的核心的网络模型当中**，也就是说对原来的这种 IO 多路复用的整体机制做了一些小小的改变，然后呢让它加入了多线程的部分，提高了对于整个 CPU 的一个利用率。但是尽管如此，它的核心部分也就是命令处理这一块，依然是单线程的。

> **结论**：当面试官问你 Redis 到底是单线程还是多线程的时候，你一定要给他问清楚我们现在讨论的是哪一部分。如果你能把每一个层次讲得这么清楚，到底哪里是单线程、哪里是多线程，相信面试官对你绝对会刮目相看的。

### 为什么偏偏要用单线程

那么这个时候他的下一个问题就来了，他会接着问你说：那为什么 Redis 的作者要坚持去使用单线程，而且使用了这么长时间？同学们可以思考一下为什么。

核心的原因有这么几个。

**第一，抛开持久化不谈，Redis 它是一个纯内存的操作。** 因此呢它的执行速度可以说是非常快，所以呢它的瓶颈从来都不是我们执行的一个速度，而是**网络的延时**。那因此呢你开启更多的线程，其实并不会带来非常大的一个性能的提升啊。

而且还有面试官问你"为什么 Redis 运行得那么快"啊，很多人都会说很多理由，什么 IO 多路复用什么的。其实我跟你讲，这些都是次要的。最最重要的原因就是因为它是纯内存操作，这种内存操作速度太快了，它的延迟可以做到微秒级别。正因为此，它的性能才如此的好。至于什么 IO 多路复用什么的，那些只是一些细微的提升。

**第二，我们如果引入了多线程，其实啊反而会导致过多的上下文的切换**——当然这是指在单核的情况下啊。因为我们的 CPU 需要在多个线程之间去做切换，你开的线程越多，那么它需要切换的频率也越高。而且呢线程也会带来额外的一些内存的消耗，所以说啊，有可能反而导致性能下降。

即便在现在 Redis 6.0 当中引入了多线程，但是呢它的线程数往往也是跟我们 CPU 的核数相对应的啊，最多也就是它的 1~2 倍。所以我们要尽可能地减少多线程导致的这种上下文的切换。

**第三，引入多线程还会面临线程安全的问题。** 在之前我们采用单线程，那这个时候所有的命令都是依次执行的，所以我们一直说它是线程安全的。我们在执行命令的时候，特别是一些这种加呀减呀这样的操作，它不是自动自检吗，那这些操作往往都是线程安全的，你不用去考虑风险。

但是一旦引入多线程，如果我们基于多线程去做这种命令的操作，那么你就不得不考虑线程的安全啊，要去做这种并发的控制，那整个代码的复杂度就会非常的高啊，那么性能也会大打折扣。而且呢，跟以前老的 Redis 版本之间，还会有一个兼容性的问题。

所以综上所述啊，Redis 即便是到了现在，即便它已经在网络模型上引入了多线程，但是对命令处理这部分它依然是单线程的。

> **结论**：综上所述的三点原因，Redis 就是要选择单线程。即便现在命令的处理也是单线程，只是在网络处理这一块儿加了一些线程。

### I/O 多路复用有多种实现，Redis 给它封了一层

Redis 是一个单线程的程序，这是大家都知道的。但服务器上那么多客户端连进来，它凭什么一个线程还能干得动？

靠的是 I/O 多路复用。

> **定义**：I/O 多路复用的思路是，一个线程同时盯着成千上万个 fd，只要其中有一个（或某几个）可读、可写，就把注意力挪过去处理，其余的一律不管。线程从"忙等"变成了"等通知"，CPU 的利用率自然就上来了。

这个技术咱们不陌生，之前都讲过有好几种实现：

| 实现 | 适用环境 |
| --- | --- |
| `epoll` | 我们 Linux 系统下的实现方案 |
| `poll` | 在另一些操作系统上作为底层的实现方案 |
| `kqueue` | Unix 系统及其衍生版本的事情，比如我们的 macOS 底层就是它 |
| `select` | 一个跨平台的方案，基本上大部分操作系统都支持 |

这几个都是各操作系统自己提供的、专门做多路复用的系统调用。

麻烦就麻烦在：我们做企业应用的时候，不一定就使用 Linux；不同的操作系统，对于 I/O 多路复用的实现方案还不太一样。你不能指望一段代码在 Linux 上调 `epoll_wait`，换到 macOS 上还能这么调。

所以 Redis 在这些不同实现方案的基础上，做了**二次封装**。

大家现在在源码里看到的 `ae_epoll.c`、`ae_kqueue.c`、`ae_select.c` 这样的文件，就是 Redis 在对应实现方案基础上做的封装，然后对外暴露了统一的 API。有点像咱们 Java 中那种接口的感觉——它们有统一的 API 接口。

这个封装层在 `ae.c` 里面。它会对你当前运行的这个系统环境去做一个判断，然后声明几个对应的变量：

- `have_epoll`：你当前环境里是否支持 `epoll`；
- `have_kqueue`：你是否支持 `kqueue`；
- 剩下的几个依此类推。

一个一个做判断，如果你支持这个了，那我就引入这个对应的文件；如果你支持的是 `epoll`，我就引入对应的 `epoll` 那个文件，以此类推；如果全都不支持，那我就选 `select` 文件。

```text
        Redis 业务代码
              │  只认这三个 API，不管底下是谁
              ▼
   ┌──────────────────────────────────────┐
   │   ae.c  编译期判断当前操作系统环境      │
   │   have_epoll / have_kqueue / have_poll│
   └──────────────────────────────────────┘
        │            │            │
        ▼            ▼            ▼
   ae_epoll.c    ae_kqueue.c   ae_select.c
   ae_poll.c    ae_kqueue_poll.c
        │            │            │
        └────────────┴────────────┘
                     ▼
     真正的 epoll_wait / kqueue / poll / select 系统调用
```

读图说明：上面那一层是 Redis 自己的抽象，下面一层才是各操作系统真正的实现。引入哪个文件，将来调用对应 API 的时候就触发哪个文件里的函数——有点像一个接口的多种重载实现而已。

> **结论**：不管最终选中哪个实现，API 不会变。这就是二次封装的全部意义：让上层代码对操作系统差异无感知。

### ae 的三个核心 API

我们打开 `ae_epoll.c` 和 `ae_select.c` 对比一下，会发现里面有一堆 API，但核心的就那么几个，而且不同实现之间**基本上没有什么太大的变化**。

我们以 `epoll` 为例，把这三个 API 和它背后的东西对起来：

| Redis 统一的 API | 对应 epoll 的哪个函数 | 作用 |
| --- | --- | --- |
| `aeApiCreate()` | `epoll_create()` | 在内核里创建一个实例：一棵红黑树记录所有要监听的 fd，另一条链表记录就绪的 fd |
| `aeApiAddEvent(fd, event)` | `epoll_ctl()` | 添加事件：把某个 fd 挂到实例上，监听它的读事件或者写事件 |
| `aeApiPoll(timeout)` | `epoll_wait()` | 等待。参数是超时时间，等到某个 fd 就绪就返回，返回值是就绪 fd 的数量 |

一个一个说。

`aeApiCreate` 就是 `epoll_create`，作用是在我们的内核中去创建一个 epoll 实例。一个是红黑树，记录所有要监听的 fd；另外一个是链表，记录就绪的 fd。

> **提示**：红黑树是「我要盯着谁」，链表是「谁已经准备好了」。这棵红黑树是 epoll 高效的根基——它让"往一个有几万个 fd 的集合里增删查"这件事维持在 $O(\log n)$，而不是每次都得把整个数组扫一遍。

`aeApiAddEvent` 顾名思义就是添加一个事件：你要添加要监听的某一个 fd 对应的读事件或者写事件。这个动作有点像我们之前讲的 `epoll_ctl`。后面跟上的指令类型应该是 `AE` 的类型，也就是做新增。它的作用就是注册一个 fd 到我们的 epoll 实例上去。所以 `AE_` 的 `A` 就是"add 新增"，等同于 `epoll_ctl` 的 `ADD`。删除也是等于这个命令，只不过后面的指令改成 `DEL` 了。

`aeApiPoll` 就非常关键了。后面跟上了一个 timeout value，就是超时时间。它的作用有点像我们之前讲的 `epoll_wait`，或者 `select`、`poll`——去做等待，等待我们的 fd 就绪，并且返回一个结果。

> **易错点**：这三个名字一定要记住名字本身，不是记 `epoll_create`。因为将来你在 Redis 源码里到处走的都是 `aeApiXxx`，看到 `aeApiCreate` 你要立刻知道它等价于 `epoll_create`。

### 三个 API 串起来，就是一条完整的链路

我担心有部分同学已经忘了，所以提前给大家准备好了一张流程图。就是用 `epoll` 的方式模拟一个服务器——Redis 不就是个服务器吗——所以等一会儿它干的事情跟这个流程很像。

```text
  server 启动
      │
      ├─(1) aeApiCreate()
      │        └─► 内核里建好一棵红黑树 + 一条就绪链表
      │
      ├─(2) 创建 server socket
      │        └─► 拿到 server fd（我们叫它 ss fd）
      │        └─ aeApiAddEvent(server fd, 读事件)
      │              └─► 从此 server fd 可读 = 有客户端连上来了
      │
      └─(3) aeApiPoll(timeout)
                │
                ├── server fd 就绪 ──► 有新客户端连上来
                │        ├─ accept() 拿到客户端 socket fd
                │        └─ aeApiAddEvent(客户端 fd, 读事件)
                │              └─► 从此客户端 fd 可读 = 它发请求来了
                │
                └── 客户端 fd 就绪 ──► 客户端发来请求
                         ├─ 读请求、解析请求、执行命令
                         ├─ 结果写进客户端的输出缓冲区并排队
                         └─ 客户端 fd 可写 ──► 把结果真的写回去
```

读图说明：整张图就三步——建实例、注册 fd、等就绪。第三步是循环的，永远在等。

一步一步顺着走。

服务器启动以后首先要干什么？**创建实例**。于是我们在内核里创建一棵红黑树来记录所有要监听的 fd，再创建一条链表用来记录就绪的 fd。这一步在 Redis 里就是调 `aeApiCreate`。

然后我们要准备去接收客户端的请求，那就需要创建一个 server socket，得到一个对应的 fd，我们称之为 server socket fd。**凡是有客户端连接，将来这个 server fd 就会可读**——这就是"有读事件了"。当然我们还得先把这个 fd 监听起来，所以就会调用 `epoll_ctl` 去监听当前这个 fd，对应到 Redis 里就是 `aeApiAddEvent`，把它添加进去。一旦添加进去，当前这个 server socket 不就被监听起来了？

接下来是不是要等待就绪？我们用的是 `epoll_wait`，对应到 Redis 这边就是 `aeApiPoll`。

什么时候就绪？就是当有客户端来连我们的时候。一旦客户端连上我们了，就绪了，我们就可以去判断一下当前的事件类型——是不是读事件？因为只有当前这个 server socket 可读才是连接。

如果是读事件，当前 server socket 可读，那代表的就是当前真的是有新的客户端连上来了。那我们是不是就要去接受他的请求，并且得到对应的 socket fd，然后是不是监听这个客户端的 socket？

经过这样的一个循环，连上来的客户端越来越多，被监听的 fd 是不是就越来越多？以后呢，事件也会越来越多。这个时候就绪的就不一定是我们的 server socket 了——有可能就是客户端 socket 可读。客户端可读，我们就处理对应的请求参数，然后去写入响应。

> **结论**：所以整体流程简单讲就是：监听 server socket、监听客户端 socket，然后监听里面发生的各种事。server socket 的事就是监听新客户端并再次监听；普通客户端的事就是去读取请求、处理响应。对应的 API 就是 `aeApiCreate`、`aeApiAddEvent` 和 `aeApiPoll`，核心就是这几个。

### 走进源码：初始化阶段做的三件事

整体思路分析完了，我们来看一下真正的 Redis 实现是不是这个样子。

首先要找到真正的实现，你必须找到 Redis 服务启动的入口。Redis 服务启动的入口在一个叫 `server.c` 的文件里，这个文件里面有一个 `main` 函数。C 语言跟咱们 Java 很像，`main` 函数作为整个服务的入口，也就是说 Redis 一启动，首先就会执行它。

那么这个 `main` 函数里干的事情非常多，代码非常的"变态"。我们打开 VS Code 看一下就会发现，`main` 函数底下干的事情是不是超级多。所以咱不可能带大家一行一行去分析——这样一来咱们整个就懵逼了，源码大家肯定看懵。所以我截取了核心的代码片段给大家来看。

第一个叫 `initServer`，就是在初始化服务。按照我们刚刚给大家分析的思路，初始化服务应该干什么？是不是应该去创建这个 epoll 实例，然后去准备创建 server socket 去监听？应该做这个初始化的动作。

这个源码也是非常非常多，我们也是截了片段，核心的就这么几个：

```c
/* initServer() 的核心三步 */
createEventLoop();      /* 创建事件循环 */
listenToPort(...);      /* 创建 server socket */
createSocketAcceptHandler();  /* 监听 + 绑定处理器 */
```

**第一步是 `createEventLoop`，创建事件循环。**

其实这里的 event loop——事件循环——就等同于我们讲的那个 epoll 实例，就是所谓的 epoll 实例，只不过在 Redis 里把它叫 event loop。大家以后记住：**event loop 就是 epoll 实例，也就是 I/O 多路复用的这个程序**。

它底下调的就是 `aeApiCreate`，也就是我们刚刚讲的那个创建 epoll 实例，等同于 `epoll_create`。这一步执行完，I/O 多路复用程序就创建好了。也就是说在内核里面，如果以 epoll 为例的话，已经有一个红黑树和一个链表准备好了。

**第二步是 `listenToPort`。**

> **易错点**：这个名字有点误导——它不是"监听端口"的意思，本质就是创建 server socket。

创建 server socket 是不是要去指定 IP 和端口？所以这里有两个参数：第一个参数就是端口，第二个就是 IP 地址。

端口是读取的 `server.port`，也就是我们配置文件里面能够配的那个端口，它默认是 `6379`。IP 地址同样也是我们可以在配置文件里配的——咱们之前是不是有一个那个 `bind` 去监听不同的 IP 地址？如果你不配，默认就是 `127.0.0.1`，也就是只监听本地的这个地址。

这一行代码执行完毕，server socket 就创建出来了，并且对应的 fd 我们也得到了。

**第三步是 `createSocketAcceptHandler`。**

这名字有点长，它创建一个"socket 接收的处理器"。这什么玩意儿啊？我问问大家，我们监听 server socket 以后要干什么事？是不是要等待它就绪；如果它就绪了，那代表什么？是不是代表有客户端连上来了；如果有客户端连上来了，我们要干什么？我们是不是要去 `accept` 接收客户端 socket——对不对。

所以它这个地方起了个名字叫 `createSocketAcceptHandler`，就是"socket 接收的处理器"，专门处理 server socket 上面的事件。虽然我们这里没有带大家去看这个函数的源码，但是仅仅从名字上我们就能看出来，他这里是要给我们 server socket 上边发生的事件设置一个处理器。

那他至少要干两件事吧：第一是去监听 server socket；第二是提前配置好，一旦 server socket 发生了什么事，要去做好对应的处理。确实如此。

它内部就干了这么两件事。第一，调用 `aeApiAddEvent`，这个函数咱们之前是不是说过？就是去添加一个对应的 fd 到 event loop 上，实现对他的监听。这里添加的是 `server.ipfd`，是不是就是我们 server socket 对应的那个 fd？把它添加到 event loop 上，就开始对他做监听了。第一件事就完成了。

第二，一旦监听了以后，将来真的发生的事件是不是要去处理好？它帮你设置好了一个对应的处理器，叫做 `acceptTcpHandler`，也就是接收 TCP 请求的这样的一个处理器。因此将来一旦我们的 server socket 上有了事件，自然就会有对应的函数来处理了。

> **提示**：这里有一个思想转变。以前我们是把 fd 注册上去，等将来真的发生事件了再临时去写处理的代码；但 Redis 不是这样——它是**提前把处理的代码写好**，等于一种回调。我先定义在这里，将来你真的发生了，直接调就行了。

对照我们刚才那幅图：第一步 `createEventLoop` 其实底层就是 `aeApiCreate`，在这里创建 epoll 实例；第二步 `listenToPort` 就是在创建 server socket 并得到它对应的 fd；第三步 `createSocketAcceptHandler` 干了两件事，一件是把它监听起来，相当于 `epoll_ctl` 注册到实例上，另一件是把将来的准备工作做好——一旦 server socket 发生一个事件就绪，我们就用处理器来处理。

对照那幅图里 server fd 可读这块框起来的内容，问问自己需要干哪些事情？很简单，就两件事：第一调用 `accept` 接收客户端 socket，第二把它对应的 fd 注册到我们的实例上。这么一推测，将来我们的 `acceptTcpHandler` 做的事情，其实就可以认为是这两件事。

走到这里，三步走完：实例创建完了，server socket 创建完了，监听也监完了，处理器也提前定义好了。就差它就绪了——对不对。前半部分就搞定了。接下来应该做的事情，是不是就是去做 `epoll_wait` 等待就绪，一旦就绪了直接调这个函数处理就行了。

### before sleep：真正 wait 之前的那点准备

但我们往下看源码，发现它并没有这么做。它调了一个叫 `aeSetBeforeSleepEventHandler` 的这么个玩意儿。

什么叫 before sleep 呀？按照道理讲，在我们监听已经注册好了以后，下一步就要调 `wait` 了，对不对。当我们去调 `wait` 的时候，万一现在没有 fd 就绪，我们的线程会干嘛？哎，就会进行一个休眠等待——等待 fd 事件嘛，一旦 fd 就绪我们才会被唤醒。所以在调 `epoll_wait` 的时候，其实就等于是 sleep 了。

那它这个地方起了个名叫 before sleep，也就是在你调 `wait` 之前。因为你调了很有可能就 sleep 了，所以在你 sleep 之前，它要做一些准备工作。这里就定义了一个函数叫 `beforeSleep`。

那 `beforeSleep` 干了什么事？咱先不管，咱先知道就是：当他在调 `wait` 之前，他要在这先处理一下，调一个这个东西。

好，这是我们注册了 before sleep。那到这为止其实只是做好了准备工作，对不对？还没有开始去做 wait，也就是说还没有去等待 fd。这是在什么时候做的呢？好回到 `main` 函数，初始化准备工作做好了，也就是初始化。接下来 `aeMain` 才开始真正地去等待 fd。我们跟进去看一下。

在 `aeMain` 里边，一上来有一个叫 event loop stop 的变量，值默认是零。然后 while 循环的时候，会判断它的 stop 就停止嘛。停止线是零，零就是 false，那代表不用停；不用停，not stop 就是 true。所以这里就可以理解成 `while true`，就是循环不断地处理，不断处理不断处理事件——处理本来就是循环的嘛。

```c
/* aeMain() */
void aeMain(aeEventLoop *eventLoop) {
    int stop = 0;                 /* 默认 0 == false，代表不用停 */
    while (!stop) {
        aeProcessEvents(eventLoop, AE_ALL_EVENTS | AE_CALL_BEFORE_SLEEP);
    }
}
```

接下来调了一个函数叫 `aeProcessEvents`，顾名思义处理事件。它内部是怎么处理的呢？你可以猜一猜，它应该就是去等待 fd 就绪，对不对。

进来以后你一眼就能看到这么一个代码，叫 `aeApiPoll`。我们之前讲过，等同于 `epoll_wait`，也就是说它在这个里边就是来去等待 fd 就绪啊。也就是说相当于是一个循环：我调一下，就绪了吗？就绪了我就处理，处理完了我再循环再调，不停地处理。

```c
/* aeProcessEvents() 的骨架 */
void aeProcessEvents(aeEventLoop *eventLoop, int flags) {
    /* 第一步：wait 之前先做准备 */
    if (flags & AE_CALL_BEFORE_SLEEP) {
        void (*func)(void) = eventLoop->beforeSleep;
        if (func) func();
    }

    /* 第二步：真正去等待，返回就绪 fd 的数量 */
    numevents = aeApiPoll(eventLoop, timeout, ...);

    /* 第三步：numevents == 0 表示没有就绪，本轮直接跳过 */
    for (i = 0; i < numevents; i++) {
        /* 调用这个事件对应的处理器（回调函数） */
    }
}
```

`aeApiPoll` 是在去等待，也就是有可能要休眠，于是在休眠之前先调了 before sleep——所以我刚才说过了，在真正 wait 休眠之前，一定会先调这个。

至于它干什么咱先不管，反正它要做，对吧。然后呢再去执行 `aeApiPoll`，也就是去做这个 wait，等待 fd 就绪。它会返回一个结果，这个结果就是**就绪的 fd 的数量**。如果是零，就是没有就绪；如果是大于零，就代表有就绪。所以它返回来以后，我们接下来要去遍历看看它里面有没有。如果没有，这里是不是就直接结束了？for 循环就直接跳过了嘛。如果是大于零，那这里自然就会遍历已经就绪的 fd。

到现在为止，咱们这里其实只注册了一个 fd，就是 server socket。也就是说如果这里真的就绪了，是不是就是我们的 server socket 就绪？那它就绪以后干什么？这块代码我没给大家贴，因为它非常复杂，但是我可以告诉大家，这里面做的事情就是**调用这个事件对应的处理器**——你看这个处理器是不是就是回调函数？

我们之前是不是刚好注册了不同的事件、有不同的处理器啊。目前只有一个处理器：`acceptTcpHandler`。也就是说当我们的 server socket 就绪了，这个处理器就会被调用了。

### 三类事件，三个处理器

现在同学们对照流程图，我们把整个流程完整捋一遍，然后回到源码去看，你会发现源码好懂多了。

#### 接收连接：acceptTcpHandler

一旦 server socket 就绪，我们要干的事情有两件事：第一接收客户端请求，得到他的 socket fd；第二把这个 fd 注册上去，再一次开始监听。

那这样一来，随着这个循环，我们 event loop 里边监听的 fd 是不是也会越来越多啊？一开始只有 server socket 一个被监听，随着客户端接收的越来越多，被监听的 fd 越来越多。

我们来看 `acceptTcpHandler` 里面的代码。第一步 accept 接收，接收完了得到了一个 fd——这就是客户端 socket 的 fd。

客户端 socket fd 拿到了以后，咱是不是要去监听他？所以紧跟着这里再往下，首先创建了 `connection`——`connection` 是一种封装和抽象，代表客户端对应的连接。然后这里面会有一个叫 `connSetReadHandler`。

这个函数呢，跟我们之前讲的 `createSocketAcceptHandler` 类似。它们都会做一件事情，就是去注册一个 fd 到我们的实例里。只不过在刚才那边，它注册的是我们的这个 server socket；而在这儿他要注册的自然就是我们这里的客户端的 socket。

主要看这个地方，它传递的是 `connection`，但是你看上面他已经把客户端 socket 的 fd 赋值给 connection 了，所以这里边传递进去的 connection 就是传递进去我们客户端的 fd。

`setReadHandler` 就是读处理器。那什么叫读处理器？将来我在这个地方要去监听客户端 socket 发生的事。客户端 socket 发生的事是不是就是它发请求过来了嘛——它发请求过来了，我是不是要去处理他的请求？处理请求就是要去读数据，所以叫读处理器。

从名字就能看出来它要干两件事：第一是去监听客户端 socket fd；第二是一旦客户端 socket 发生的事件，我们用一个处理器去处理它。

所以它底层就是两件事：`aeApiAddEvent` 把我们客户端 fd 注册上去，并且还绑定了一个读处理器 `readQueryFromClient`。顾名思义，读取查询请求从哪读？从这个客户端里读。

到这为止，我们有几个处理器了？是不是有两个处理器了。

> **易错点**：这两个都是处理读事件的处理器，一定别搞混——一个处理的是 server socket 上的读事件，一个是处理客户端 socket 上的读事件。

| 处理器 | 它处理的是哪个 fd 上的读事件 |
| --- | --- |
| `acceptTcpHandler` | server socket 上的读事件 |
| `readQueryFromClient` | 客户端 socket 上的读事件 |

#### 读取请求：readQueryFromClient

客户端 socket 可读做的事情就是读取请求数据，并且写响应。那这块代码非常非常长，我们慢慢地来看。

首先一上来 `connGetData`，这个地方返回了一个叫 `c`，这个 client 咱们不是第一次见了吧？之前咱们就说过：每一个客户端 socket，只要跟我们的服务器连接，那么 Redis 就会把它封装成一个 client 实例。这个 client 里面包含了客户端的所有信息，甚至包括客户端的请求信息——你发了什么样的命令过来啊，`set name` 等，只要你发过来了，全部都在这个 client 里。

我们先拿到它，拿到以后注意注意了，干了件事：这里去得到了一个长度，`c->querybuf`，client c 的 query buffer。这是一个查询缓冲区。然后做了件事叫 `connRead`，就是读、从哪读、从这个 connection 里去读，读什么？读数据到 query buffer。因为客户端传过来的请求其实是在这个 connection 里面，我们需要把它读取过来，然后去做处理。

所以一上来先会把数据读取到一个 query buffer 的缓冲区里。

> **提示**：这个叫什么？这叫做输入缓冲区。我们在讲 Redis 高级篇的时候大家提到过，在 Redis 内部给客户端有输入缓冲区，也有输出缓冲区。那么这里这个 query buffer 就是输入缓冲区，它是用来缓存客户端请求参数的。

这还不够，下边我们是不是要去处理这个请求参数啊。你要知道我们读过来的其实是一个一个的字节。比如说你传了一个命令叫 `set name 胡歌`，这在我们看来是字符串，但它传递的时候是以字节形式传递的，所以你读成字节放到缓冲区了。那你将来是不是还要去解析它？

所以再往下 `processInputBuffer`，就是在处理缓冲区中的字节：把它转成字符串，以空格的形式给它隔开，封装成一个一个的 sds 对象，保存到 argv 数组。

`set name 胡歌` 到这儿就会变成三个 sds 字符串存在这个数组里——一个 `set`，一个 `name`，一个 `胡歌`。这个咱们之前是不是提到过？数组中放的就是所有的命令参数。

一旦把命令解析出来了，接下来是不是就可以处理命令了。到这为止，他把对应的这个流程我们用图表示一下：

```text
 conn  --read-->  querybuf  --parse-->  argv[]  --exec-->  processCommand
               (input buffer)            (3 x sds)   |
                                                  +-- lookupCommand : name -> command func
                                                  +-- cmd->proc()    : really execute it
                                                  +-- addReply()     : result -> output buffer
```

读图说明：左边是网络里的字节，中间是缓冲区和解析出来的 argv，右边才是命令查找、执行和回结果。

到哪儿了？就跟到这个函数里来了，叫 `processCommand`。处理，怎么处理呢？处理命令你得先找到这个命令，对不对，叫 `lookupCommand`，寻找客户端的命令。

怎么寻找的？你要知道前端传过来的仅仅是一个 sds 字符串吗？`set name 胡歌`。那么第一个 `set` 字符串就是我们要执行的命令。我们要根据它传过来的那个 `set` 这个字符串，找到对应的可执行的这个函数。

所以这里有个 `lookupCommand`。找的时候大家看，它从 argv 数组里去找 0 号。`set` 是不是就是数组的 0 号？就是这个命令的名称字符串。根据名称字符串去找对应的命令。

这上哪找去？不知道大家有没有印象，其实之前我们带大家看过。我们打开 VS Code，随便找一个数据类型，比如说 string 类型，我往下翻一翻，这里应该是有 string。大家看 string 类型的内部，这里有很多很多的函数啊。有 `getCommand`，然后下面还有 `setCommand`——这些是不是我们以前学过的命令？

大家有没有发现，**每一个命令都有一个对应的函数**，就是什么什么 command。其实在 Redis 内部，所有的命令都有对应的 command 函数，由对应的函数去处理对应的命令。那么这些函数肯定要跟对应的这个名称做成一个映射关系。这个映射关系其实就被放到了一个字典当中：字典的 key 就是对应的命令的名称，字典的值就是对应的 command 函数。

因此呢当我们调 `lookupCommand` 的时候，它根据这个命令的名称，是不是就找到了对应的 command 函数，就这个 `cmd`。

再往下是不是就可以去执行这个函数了。所以这个 `cmd->proc` 就是 process 的缩写啊，就是在执行这个 command 函数。比如说我们现在是执行 ping 命令，那找到的是 `pingCommand`，这个 `pingCommand->proc` 就是在去执行这个 ping 命令。我们知道 ping 命令执行完返回的是不是 PONG？当然如果你是 set，set 完了以后返回的应该是 OK 吧。反正不同的命令都会有不同的响应。

所以执行完了以后，将来也许返回这个结果给用户。所以处理命令呢，它分三步：**第一步是找命令，第二步是执行命令，第三步就是把结果返回回去**。最后这里的 `addReply` 就是在返回一个响应结果。reply 什么意思？回复，就是把回复结果添加回去。

#### 输出响应：结果先不进 socket

你比如说这里如果你执行了 ping，那要返回 pong。大家可以看到这里有一个叫 `shared` 的常量，sds 常量，然后就把这个东西写回给客户端了。

但是具体往哪写呢？跟进来，`addReply` 往哪写吗？跟进来以后，这里首先是 `addReplyToBuffer`。这里又没有直接写，没有写到他的 socket，而是先写到缓冲区了。这个缓冲区是 `c->buf`，也就是说还是我们的 client 里面的 buf。那么写完以后，这个结果有可能成功也有可能不成功。为什么呢？因为缓冲区的大小是有上限的。

如果 `c->buf` 这个缓冲区已经被写满了，那么这里会报错，它会不往这个 buf 里写了，而是换到一个叫 `c->reply` 的链表当中。因为链表理论上讲是没有上限的，而 buffer 它是一个字节数组，它是有上限的。

> **定义**：所以说呢在这个地方它会有两种不同的缓冲区：一个叫 `c->buf`，一个叫 `c->reply`，它们都在我们的客户端里面，是**输出缓冲区**。

因此我们在 `addReply` 里，它不是真的把数据写给了客户端 socket，仅仅是把这个结果写到了 buf 或者 reply 这个缓冲区，写到哪个取决于你的大小。

那问题来了——你写到缓冲区了，什么时候写给客户端 socket 呢？好，紧跟着再往下：

`listAddNodeHead`，那这个地方做了一个添加。把谁添加进去了？把 `c` 添加到了一个叫 `server.clients_pending_write` 的东西里。这是什么？大家看这是一个队列，它是服务器里边定义好的一个队列，固定的。那么这个队列现在其实是空的。它是用来存放什么？存放那些**等待被写**的客户端的。

因为现在响应结果是不是已经放到客户端缓冲区去了，所以将来这个客户端其实已经可以把数据输出了。但是别着急，先不着急输出，先给你排个队，扔到这个队列里面去。那随着处理的请求越来越多、处理的客户端越来越多，这样待写出的客户端是不是也越来越多？他们都会排在这个队列当中。

到这 `readQueryFromClient` 这个函数就结束了。也就是说，其实结果到这为止——写出了没有？没写。同学们，没写出。

```c
/* readQueryFromClient() 的骨架 */
void readQueryFromClient(connection *conn) {
    client *c = connGetData(conn);

    connRead(c->conn, c->querybuf, ...);  /* 请求字节 --> 输入缓冲区 */
    processInputBuffer(c);                 /* 字节 --> sds --> argv[] */
    processCommand(c);                    /* 找命令 -> 执行 -> 生成响应 */
}

void processCommand(client *c) {
    lookupCommand(c->argv, c->argc);      /* argv[0] --> command 函数 */
    c->cmd->proc(c);                      /* 真正执行命令 */
    addReply(c, ...);                     /* 结果进输出缓冲区 */
}

void addReply(client *c, robj *obj) {
    if (!addReplyToBuffer(c, obj)) {
        /* buf 写满了 --> 不往 buf 写，改挂到 c->reply 链表 */
        addReplyToList(c, obj);
    }
    listAddNodeHead(server.clients_pending_write, c);  /* 排队，还没写出去 */
}
```

### before sleep 里的一把钥匙：给客户端绑定写处理器

什么时候写呢？咱们一直有一个东西没给大家分析——`beforeSleep`。

`beforeSleep` 这个函数它会帮助我们去写。它会定义一个迭代器叫 `listGetIterator`，这是缩写，就是迭代器的意思。那么这个迭代器的指针 next 首先指向的是这个 `server.clients_pending_write` 的头指针。它不是队列嘛，里面存放的是不是待写出的客户端呀？现在有一个迭代器，它指向了我们这个头，然后迭代的方向是从头往后迭代。

所以他就会一个一个从这个队里取出待写的这些客户端，然后 while 循环啊，如果有就取出来。取出来以后注意看啊，取出来以后直接做了一件事：`connSetWriteHandler`。

同学们，这样的命令我们已经不是第一次看到了吧。之前在我们 server socket 注册的时候，是不是有一个 `createSocketAcceptHandler`，设置了一个处理器；后来在我们去接收到客户端请求、拿到客户端 fd 的时候，我们又设置了一个 `readQueryFromClient`。

那在这儿呢，又来了一个 set handler。那像这样的函数，我们知道它底层都会做两件事：一件事是去监听 fd，另一件事是设置这个 fd 对应的处理器。

> **易错点**：这里有个特别容易搞错的地方。我们之前已经监听过客户端 socket fd 了，怎么这里又监听了？因为之前指定的事件是**读**事件，也就是客户端 socket 可读，代表它有请求来了。但在这里我们要监听的是客户端 socket 的**写**事件。

因为现在有很多的客户端都在这排着队等待输出，要把这些缓冲区的数据写回到客户端 socket 里去。因此 `setWriteHandler` 就是给我们所有的客户端 socket 都绑定一个写处理器，这个写处理器的名字叫 `sendReplyToClient`。

```c
/* beforeSleep() 里的骨架 */
void beforeSleep(aeEventLoop *eventLoop) {
    listIter *li;
    client *c;

    /* 迭代器指向 server.clients_pending_write 的表头，从头往后遍历 */
    li = listGetIterator(server.clients_pending_write, LIST_START);
    while ((c = listNext(li)) != NULL) {
        connSetWriteHandler(c, sendReplyToClient);   /* 绑定写处理器 */
    }
    listReleaseIterator(li);
}
```

那么也就是说，现在我们的客户端 socket不仅仅会监听他读，是不是也会监听它的写事件呀。那如果说他可写了，现在触发就绪，那么就会找到我们对应的处理器了——`sendReplyToClient`。那么他就会真正地帮助我们，把这些客户端当中这个缓冲区的数据给它取出来，然后一个一个地写到客户端的 socket。那么客户端就拿到结果了。

> **结论**：至此整个流程就形成闭环了。第一次客户端来的时候我们去接受他的请求，这时候它是个读事件，我们交给读处理器来处理。读事件里边我们去解析它里面的请求参数，并且变成 Redis 命令，然后去执行，把结果写回到客户端缓冲区。接下来就会去触发写事件，写事件交给写处理器，写处理器会把准备好的数据写回给客户端——闭环。

```text
   客户端 connect
        │
        ▼
   server fd 可读  ──► acceptTcpHandler ──► accept + 注册客户端 fd
        │
   客户端 fd 可读  ──► readQueryFromClient
        │                read -> querybuf -> parse -> exec
        │                addReply -> output buffer -> pending queue
        │                beforeSleep -> connSetWriteHandler
        ▼
   客户端 fd 可写  ──► sendReplyToClient ──► buffer 写回 socket
        │
        ▼
   客户端拿到结果
```

读图说明：从连接到出结果，走的正是同一对 fd 在"可读"和"可写"两个事件上的来回切换。

那么到这里其实我们整个流程是不是就形成闭环了？那么看起来啊似乎整个流程有些复杂，对不对？其实呢你要是把它看得整体一点、看得简单一点，那么这里什么 `beforeSleep`、什么 `aeApiXxx` 你都不用管它。

整体来讲就是一个 **I/O 多路复用，再加上一个事件派发**。为什么呢？因为我在这里其实就是不断地去监听：监听 server socket、监听客户端 socket，给你们过来一口我都来监听。监听完了以后呢，然后你这个事件有很多嘛，事件有哪几种呢？有三种：

| 事件类型 | 派发给哪个处理器 | 这个处理器干什么 |
| --- | --- | --- |
| server socket 可读 | `acceptTcpHandler` | 接收新客户端请求，拿到 fd 并注册到 event loop 上 |
| 客户端 socket 可读 | `readQueryFromClient` | 把请求参数读到输入缓冲区、解析成命令并执行，结果放到输出缓冲区、等待排队输出，并通过 `beforeSleep` 触发写事件 |
| 客户端 socket 可写 | `sendReplyToClient` | 把输出缓冲区里的数据一个一个写到客户端 socket |

所以整个 Redis 的网络模型，就是一个 I/O 多路复用加事件派发的这样一种机制。

> **结论**：大家只要牢记这幅图，在你的脑海中对这幅图形成一个印象，相信你一定能够给面试官讲清楚 Redis 网络模型的整个流程。如果你能把这个讲出来，那你在面试官心目中的印象一定是加分的。

### 单线程的瓶颈：不在命令执行，在两次网络 I/O

当然，以上说的都是单线程的模型。在 Redis 6 以后，又引入了多线程的模型，想要去进一步地提升 Redis 的性能。

那么现在我们要思考一下：在当前这个模型下，出现性能瓶颈的地方是在哪里？

**是 I/O 多路复用的机制吗？** 哎不是。因为这里只是接收你的请求，然后去注册事件而已，所以它这里非常的速度非常快，效率非常高，没什么问题。

**是我们接收应答吗？** 也不是。接收应答也就是去注册一下。

**是我们的命令处理吗？** 哎同学们，命令处理要干什么？命令处理首先第一步要从客户端连接里去读 socket，读出对应的请求；读完了以后呢，还要解析它，把它变成 Redis 的命令。这个过程牵扯到了 I/O。那么读 socket，它的这个速度就会受到网络的影响、带宽的影响等等，所以效率相对会低一点。这是我们现在单线程模型中的其中一个瓶颈：可能你这里在读，我们主线程在那儿等，等你把它读出来，然后才能去继续执行命令。

**那么执行命令这里是瓶颈吗？** 我们 Redis 执行命令都是纯内存操作，那么它的一个速度可以说是非常的高。我们之前说过，执行的时候长一般是在微秒级别，所以它根本就不是瓶颈。

然后执行完了命令，把结果放到缓冲区里，这个是一个缓存操作，速度也很快，没什么问题。然后去排队好，那么这里也不是问题。

那再接着呢，触发写事件，交给写处理器，往哪写呀？往客户端 socket 里写。这里又一次会出现网络 I/O 的操作，也就是要写向客户端 socket，又是网络操作。那么它又会受到网络带宽、受到网络的状态等等各方面的影响，因此呢这里它又是一个瓶颈。因为我们刚才说过了，网络的操作都会相对来讲比较慢一点，网络延迟会比较高。

> **结论**：在传统的单线程模型下，真正会影响性能的并不是我们命令的处理，以及这个 I/O 多路复用的这种事件监听，而是 **I/O**。大家记住，影响性能呢永远是 I/O，对吧。大家数据库里也一样，MySQL 里边影响性能呢就是对磁盘的读写，那这里也就是网络读写。

### Redis 6 的多线程：只动这两块

为了解决这个问题，Redis 引入多线程。其实正是在这两块引入多线程，哪两块？**一个是命令解析，一个是响应结果的输出。**

```text
  Redis 6 之前
  ----------------------------------------------
  主线程 |  read+parse  |  execute  |  write   |
         ^  网络 I/O，瓶颈  ^ 很快    ^ 网络 I/O，瓶颈

  Redis 6 之后
  ----------------------------------------------
            +-- IO thread 1 --+
            +-- IO thread 2 --+  read + parse (in parallel)
  主线程    +-- IO thread N --+  write to client (in parallel)
            |  execute        |  由主线程逐个串行执行
  ----------------------------------------------
```

读图说明：多线程接管的是两头——读进来的解析和写出去的发送；中间真正执行命令的那一步，始终牢牢握在主线程手里。

先看命令解析这一块。首先客户端 socket 来了以后，注册什么的就不说了。假如说现在客户端可读，在高并发的情况下，会有无数的请求过来，是不是都等待着读？那这个时候是读事件非常的多。

然后如果我们一个一个去读，单线程的情况下可能就忙不过来了，于是呢我们就会在这个地方开启多线程。然后我们的主线程会以**轮询**的形式，把多个不同的客户端分发给不同的线程，由他们去并行的读取 socket 中的数据、解析其中的数据转换成命令，然后找到对应的命令。

那么真正执行命令的时候呢？还是由我们的主线程他一个人去执行。所以多线程它主要是用来去读取客户端 socket 中的数据，解析其中的数据转换成命令，是这样一个耗时较久的过程。

一旦处理完了以后，我们的主线程就开始执行命令了，那么命令依然是一个个执行啊——也就是说它是线程安全的、串行执行的。

然后放到缓冲区，好，就没啥事了。紧接着一旦触发了写事件要往外写，但这里又好使，因为它会考虑到这个网络的一个情况，那么此时又会开启多线程。反正你这里排着队等着写，那么开启多线程，由他们从这个队里去取，取完以后去写，是不是也没问题。

所以说呢，这两块多线程可以大幅地提高我们 Redis 对于客户端处理的速度，减少因为网络 I/O 导致的这种性能的影响。

> **结论**：虽然说单次请求的响应时间没有缩短，但是整体的吞吐量相对于单线程模式还是有不少的提升的。

### RESP：客户端和服务端之间那套共同的规范

下面进入 Redis 通信协议这一章。这一章我们会分成两个小节：第一小节先认识一下 RESP 这种通信协议的基本规范；第二小节会带着大家基于这个协议去模拟一个 Redis 的客户端，尝试跟 Redis 的服务端进行交互。现在我们先认识协议。

我们知道 Redis 是一个 C/S 架构的软件，这里的 C/S 指的就是客户端 Client 以及服务端 Server。比如说我们安装一个 Redis 并且把它启动起来，那个就是我们的服务端；然后我们通过命令行的 redis-cli，或者通过 Java 的这种客户端 Jedis，或者我们的桌面客户端——比如我们之前用的这个 RDM——这些都算是 Redis 的客户端。

虽然这些客户端它们的形式不一样，但是呢它们其实跟我们 Redis 通信的时候，基本的流程都是一样的，一般都分成两步：第一步就是客户端向服务端发送一条命令；第二步就是服务端接收到了这个命令，它会去解析它，然后去执行它，最后返回一个结果。

我们上一讲讲 Redis 网络模型的时候，其实主要讲的就是第二部分：在服务器端我们去接收这个命令，在接收到命令了以后，我们要把它读取到一个缓冲区。接下来有一个非常关键的一步，就是去解析这个缓冲区中的命令信息，然后把它转换成对应的命令去执行。也就是说，在这个地方是不是会有一个解析的动作呀。

那如果说客户端向服务端发命令的时候一顿乱发，没有任何的章法，那么我们服务端去解析的时候，是不是很有可能解析不出来？那就没有办法执行。然后我们执行完了以后要返回结果给客户端，客户端是不是要去解析这个结果？那如果我们返回结果的时候也是没有章法的，随便乱发的，那这个时候客户端拿到这结果以后他看得懂吗？是不是也看不懂。

> **结论**：所以啊，无论是客户端向服务端发送的命令，还是服务端返回给客户端的结果，是不是都应该遵循一种规范？只有这样，客户端和服务端之间进行交互的时候，互相才能看得明白对方发了什么信息。那这种规范就是通信协议。

Redis 里采用的呀，就是这个 **RESP 协议**，也就是 Redis Serialization Protocol，Redis 序列化协议。

这个协议在 Redis 1.2 版本的时候就已经引入了，不过呢当时还没有特别的标准，所以在 2.0 时代的时候，已经将我们的协议给定成了标准，那么当时呢就称之为 **RESP2**。这个版本的协议一直延续并且使用至今。然后到了 Redis 的 6 版本中，才把这个协议二的版本升级成了三的版本。

这一次升级啊有非常大的一个变化，可以说这个三协议的版本相对于二来讲，它们之间是不太兼容的。而且呢在 RESP3 里面增加了很多各种不同的数据类型，并且它可以支持 Redis 6 里面的一个新特性，叫**客户端缓存**，但是 RESP2 就不行。

所以呢这种协议它其实变化确实是非常的大。不过呀虽然这个协议非常强大，但是因为这种兼容性的问题，所以说在 Redis 6 版本中，默认情况下使用的依然是 2 版本的协议，也就是 RESP2。因此我们在学习的过程中，我们学的依然是 RESP2 这个版本的协议。

### 简单字符串与错误：最基础的单行格式

在 RESP 协议中规定了五种不同的数据类型。不管是客户端发送的命令，还是服务端返回的响应结果，只要是传输的数据，它都必须是这五种数据类型中的一种。

为了去区分这些不同的数据类型，我们传输的这个数据的**首个字节**，就拿来作为不同数据类型的标识了。

| 类型 | 首字节 | 完整格式 | 一句话说明 |
| --- | --- | --- | --- |
| 简单字符串 Simple String | `+` | `+<字符串>\r
` | 结尾换行是结束标志，内容里不能出现 `\r
` |
| 错误 Error | `-` | `-<异常类型> <详细信息>\r
` | 只有服务端响应时才会出现 |
| 整数 Integer | `:` | `:<数字>\r
` | 中间跟的是数字格式的字符串 |
| 多行字符串 Bulk String | `$` | `$<字节长度>\r
<字符串内容>\r
` | 按长度读，二进制安全 |
| 数组 Array | `*` | `*<元素个数>\r
<元素>...` | 元素类型任意，甚至可以嵌套自己 |

**第一种是简单字符串。** 它的首个字节呢就是加号，那因此只要你看到加号，你就知道说我现在读的就是一个单行字符串了。那么加号的后边跟上的就是字符串本身的内容，而最后呢会有一个 `\r
`，它代表的就是一个换行符。

比如我们要返回一个 OK，那它对应的结构就是这样：

```text
+OK\r\n
```

> **易错点**：那它为什么叫单行字符串呢？刚才我们讲了这个 `\r
` 是结束标识，所以当你看到单行字符串加号的时候，你读取这个数据的过程是这么读的：一直读，一直读，直到碰到 `\r
` 我就结束。在这之前呢，就是我要读的这个字符串。

那这样就会有一个问题啊：如果说我的这个字符串它本身比较特殊，里边包含了 `\r
`，也就是说这个字符串可能会分好几行，它本身里面带了 `\r
`。此时如果说我们直接从加号开始读，读到第一个 `\r
` 你就认为结束了，哎那么就出问题了——因为其实它没结束，它有很长的一截。所以呢这个时候我们就只能读取到部分数据了。

> **结论**：因此单行字符串是不允许在字符串里出现换行符这种特殊字符的。所以我们也可以认为单行字符串它是**二进制不安全**的，它只能是普通字符串。

它最常见是用在哪里呢？就是服务端返回的这个结果。我们服务端经常会返回这种简单字符串，比如 OK，它不可能有特殊字符；或者是我们发给客户端的 ping，客户端返回给我们一个 PONG，那这个 PONG 是不是也都是普通字符串呀？所以他们都是这种加号开头这种格式。

**第二种数据类型叫做 Error，也就是错误。** 什么时候会有这种数据类型呢？就是当我们客户端去调服务端时，如果服务端执行过程中出现了错误，它就会返回一个 error 这样的数据。

所以这种数据类型一般情况下，**它仅仅是服务端响应的时候才会出现**——也就是我们客户端发请求的时候会不会发这种？那肯定不会，这个要注意。

那么这种 error 呢，它的首个字节呢不是加号，而是减号。剩下的呢跟简单字符串是一样的，也就是说它也是以 `\r
` 结尾，然后中间呢同样是字符串。区别在于它中间的这个字符串是异常信息。

```text
-ERR unknown command 'hset'\r\n
```

前面的这个 error 是异常的类型，中间是个空格，后面就是异常的详细信息。那这里的异常类型啊，除了 ERR 以外还会有很多别的——Redis 内部其实把异常分得非常多种。所以说呢，如果我们将来自己写客户端来解析这个 error 的时候，完全可以根据不同的异常类型去做出不同的处理。

**第三种是数值类型。** 数值类型它的首字节呢是冒号，然后后面跟上的是数字格式的字符串，最后也是 `\r
` 结尾。

```text
:1\r\n
```

同学们看到这儿，你会发现它也是跟单行字符串或者是错误一样，是不是他们格式基本上都是一致的？首字节不一样，我首字节是冒号，后面跟上的是字符串，只不过这个字符串的格式是数值。所以这三种类型，他们的整体格式上没有什么太大的差别。

---

### 多行字符串：用长度换二进制安全

**第四种叫做多行字符串。** 它的首字节呢是 `$`，也就是看到它，你就知道我们是一个多行的字符串。

那为什么它叫多行字符串？刚才那个叫单行——我们刚说过了，单行字符串是以这个 `\r
` 作为结束标识的。我们在读的时候，会从加号往后读，读到第一个 `\r
` 就代表结束。那因此呢，如果这个字符串的内部本身包含 `\r
`，那你读到一半就结束了，这显然是有问题的。

所以我们讲单行字符串，它是不允许在字符串里出现换行符的。那多行字符串，也就意味着它允许你在字符串的内部本身含有换行符这种特殊字符，允许你有好几行。

那这个时候如果我们看到 `$` 了，我们往后读，我们还能不能以 `\r
` 换行符作为结束标识？显然不行吧。那么我们怎么知道我把这个字符串读完了呢？

> **提示**：这里可以参考之前讲的那个 SDS 的结构。它为了确保二进制安全，采用了特殊的读取方式：不是以这个结束标识作为字符串的结束，而是去记录字符串的长度——你占了多少个字节，那我就读多少个字节，不管你中间是什么。所以这就能确保字符串二进制安全。

那因此呢我们这个地方也是如此，它需要去记录两部分：第一是当前这个字符串的长度，第二就是字符串本身。那么你在读的时候，就不用担心字符串中间出现特殊字符了。它的格式是这样子的，我们举个例子：

```text
$5\r\n
hello\r\n
```

一开始是 `$` 标记，我是一个多行字符串；后面紧跟的这个 `5` 就是字符串占用的字节大小。比方说我后面跟的是个 `hello`，是不是占五个字节，所以我这里就是 `5`。我这个长度标识完了，后面的 `\r
` 代表记录长度的部分要结束了；再往下就是真正的字符串部分，也就是这里的 `hello`。

那么你这个字符串中间你出现了特殊字符，比如说你包含 `\r
` 没有任何关系。因为什么？它前面记录长度是 5 了，因此你在读这部分内容的时候，你千万不要说我读到 `\r
` 就结束，而是它标识 5 你就读五个字节，代表结束。

前面这个 `5` 是用来标识字符串的字节大小的。它如果是正数的时候，就是字节大小。它还会有两种特殊值，用来标识一些特殊情况：如果它的值为零，那就代表它是个空字符串；如果它是 `-1` 呢，则代表这个字符串根本就不存在——也就是你找的这个东西，可能我根据 key 去找，根本就不存在，所以呢这个地方就会变成 `-1`。

```text
空字符串:        $0\r\n\r\n
字符串不存在:    $-1\r\n
```

所以这两种情况你可以都认为是没有。那么我们将来如果要去解析这个多行字符串的时候，就需要去判断了：这里的长度到底是什么？如果是零和 -1，咱是不是就不用处理了？如果是正整数，我们再去处理。

---

### 数组：可以套自己

最后一种叫做数组。数组顾名思义就是它里边其实是可以存储多种类型的，对不对。

它的首个字节是 `*`，标记说我是一个数组，后面跟上的是数组元素的个数。比如说我跟了 `5`，那代表我数组里有五个元素。那么它的元素的类型是什么呢？它的元素可以是上面这四种中的任意一种，甚至可以是它自己本身，也就是还是数组——可以嵌套，所以它的类型是不确定的。

好，我们举个例子。比方说啊在这个地方，因为它比较长，我故意给它换了个行，让大家看清晰一点：

```text
*3\r\n
$3\r\n
set\r\n
$4\r\n
name\r\n
$6\r\n
胡歌\r\n
```

首先 `*` 开头，那我们就知道了，我现在这个是数组；后面跟了 `3`，那我就知道我这数组的元素个数是三。既然数组元素个数是三，那往下我就读三个数据。我先读第一个，结果发现是 `$` 符——那 `$` 符我们一看就知道是多行字符串，多行字符串长度是三，往后读发现哦是 `set`。然后呢再往下又读到一个 `$` 符，啊我又知道这又是一个新的多行字符串，那么它的长度是 4，值呢是 `name`。

再往下第三个元素啊，它的长度是六。怎么是六字节啊？因为它是中文啊——我们知道中文在 UTF-8 中是不是占三字节，两个字最后六字节了。

> **易错点**：这里的长度是**字节数**，不是字符数。中文一个字在 UTF-8 里就是 3 个字节，所以这里必须写 6。如果按字符数写成 2，客户端读出来的数据就会缺一截。

其实在这个地方，我是故意准备了这么一套数据。大家看第一个字符串是 `set`，第二个字符串是 `name`，那么我这个数组中装的是不是恰好是一个 Redis 命令啊？`SET name 胡歌`。事实上啊，将来我们的客户端在向服务端发请求的时候，你的命令就是这种格式的数组格式——当然我们这里因为是要发命令，所以都是字符串。

但是我们刚刚说了，数组中的元素可以是任意类型，不一定是字符串。你比如说这里这个数组的元素个数是三，但是它的第一个元素是一个数字，而它的第二个元素是个多行字符串，而它的第 N 个元素竟然又是一个 `*`，也就是数组——数组嵌套了：

```text
*3\r\n
:1\r\n
$5\r\n
hello\r\n
*2\r\n
$1\r\n
h\r\n
$2\r\n
hi\r\n
```

最外层这个数组有三个元素：第一个是整数 `1`；第二个是长度为 5 的多行字符串 `hello`；第三个又是一个 `*` 开头的数组，数组里包含两个元素，第一个是 `h`，第二个是 `hi`。

到这儿呢，我们就把 RESP 协议当中的五种数据类型给大家分析清楚了。

---

### 谁发什么，谁回什么

那么我们将来呢，客户端在向服务端发送命令的时候，我们的命令往往都会分成几段嘛，所以多数情况下我们发送的命令都是**数组格式**，而且数组中往往都是字符串。

而服务端响应的数据格式却会多种多样、五花八门：

| 我们做的操作 | 返回的可能是哪种 RESP 类型 |
| --- | --- |
| 执行 `SET` | 简单字符串，比如 `+OK\r
` |
| 服务端执行出错 | 错误，比如 `-ERR ...\r
` |
| 执行 `INCR` | 整数，比如 `:1\r
` |
| 执行 `GET` | 多行字符串，为了确保二进制安全 |
| 执行 `MGET` | 数组，因为有多个不同的结果 |

所以啊，我们的响应结果这五种都有可能；而我们发请求啊，一般发的就是数组。

## 手撸 RESP 客户端，再看 Redis 如何回收过期 Key
> 对应块：BLK52 | 覆盖分集：P173-P174 | 块标题（分集名）：《原理篇-29.Redis通信协议-基于Socke》

这一节课，我要用 Java 代码，参考 RESP 协议，自己去模拟一个 Redis 客户端——向 Redis 发起请求，再把它的响应解析出来。

IDEA 里我已经准备好了一个全新的项目。注意啊，这不是一个 Maven 项目，就是一个最普通的 Java 项目，除了 JDK 什么都没有。所以我们等于完全自己动手，基于 JDK 来编写。

### 从零起步：连接、收发、释放

现在我们要去跟 Redis 交互，那就要用到 TCP 协议。客户端这边是 `Socket`，Redis 那边是 `Server Socket`：

```text
┌──────────────────┐       ┌──────────────────┐
│   我们的客户端   │ --TCP--│   Redis 服务端   │
│     Socket       │       │   ServerSocket   │
└──────────────────┘       └──────────────────┘
```

所以我们做的第一件事，其实就是跟 Redis 建立连接。连接建立完了以后，理论上就可以向它发请求了。

但是这里大家要注意一个细节：我们用 TCP 怎么发请求呢？要去获取 Socket 里面的**输出流**；那将来要去读响应呢？就要去获取它的**输入流**。

> **提示**：我的建议是在这里就把两条流提前拿到手，这样后面用的时候直接用就可以了，不用再重新获取。

所以整个流程先理一遍，就这么三段：

```text
① 建连接   new Socket(host, port)
② 收发     输出流 → 发一条 SET       输入流 → 读回响应
③ 释放     finally 里关掉 reader / writer / socket
```

#### Socket 之外，先把两条流拿到手

建连接的代码本身很短，`Socket` 需要两个参数，一个 `host` 一个 `port`，也就是你要连的目标的 IP 和端口。我的目标就是我的虚拟机：

```java
String host = "192.168.6.101";   // 虚拟机的 IP 地址
int port = 6379;                 // Redis 端口
```

> **注意**：真实当中如果你要自己定一个客户端，这两个东西最好是**可配置**的，不要写死在代码里。这里我就把它定义成参数。

这里其实会有一个异常，我们等会肯定要给他抛出去——因为等一会我们要去做连接的释放。这个异常要往外抛，`catch` 块可以一直穿到 `main` 这个位置，然后我们会得到一个 `Socket`。

那这个 `Socket` 应该放哪儿呢？为了将来我们能把它释放掉，一般是放在 `finally` 里的，所以你最好把它放到外边去、放到成员变量的位置去：

```java
private static Socket s;
```

这样一来连接就建立起来了。连接建立以后，还要去拿输出流和输入流。

#### 输出流：为什么不直接用字节流

先看输出流。我们将来要利用它去发送请求，所以在这里我**不建议直接用字节流**——字节流输出的时候会比较麻烦，它只能输出字节。所以我们用一个字符流来代替，用 `PrintWriter`。

`PrintWriter` 有什么好处呢？它可以帮助我们直接**按行输出**，这样你就不用自己去输出换行符了。

> **定义**：`PrintWriter` 内部接收的其实还是字节流，所以你要么直接用它，要么自己定义一个转换流，比如 `OutputStreamWriter`，把字节流传给它，再把编码指定上——我们这里统一用字符集 UTF-8。

所以输出流这样拿：

```java
PrintWriter writer = new PrintWriter(
        new OutputStreamWriter(s.getOutputStream(), StandardCharsets.UTF_8));
```

#### 输入流：按行读很方便，但有个坑

与此类似，我们还可以整一个 `Reader`。字符流这边对应的就是 `BufferedReader`，它的好处是可以按行读——上面那个是按行写，这个是按行读。

那我们为什么非要整这种流呢？因为我们的结果都带有换行符，如果利用 `BufferedReader` 去读的话，是不是会方便很多？

```java
BufferedReader reader = new BufferedReader(
        new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8));
```

但是这个地方我要给大家说明一下：**虽然我们利用字符流去写没什么问题，但是你用字符流去读其实是不太合适的。**

理论上讲这里应该去用字节流读。虽然我们讲响应里有很多的换行符，但是你不要忘了，我们之前讲过多行字符串，它是**二进制安全**的。如果你用字符流 `readLine()` 的话，那就是一行一行读，很有可能读不全。所以最佳的方式是用字节读。

但是呢这个地方太麻烦了，为了省事儿，咱们这就先用字符流了。你明白这个道理就行了。因为这是 IO 读取的问题了，跟我们核心跑的有点偏了——我们的核心是什么？弄清楚这个协议就行了。感兴趣的同学可以自己下去用字节流写一下。

#### 释放连接：收尾必须在 finally 里

输出流输入流全部定义完毕之后，最后是释放连接。只要它们不为 `null`，我们就可以释放掉：比如这个 `reader` 如果不等于 `null`，就可以调用 `reader.close()`；同理 `writer` 也可以释放掉，还有 `socket` 都可以释放掉。

释放过程中有可能有异常，所以这个地方还要抛异常。这里我们就不去处理这个异常了，仅仅打印一下就完了。

到这里架子就搭起来了，`main` 大致长这样：

```java
public class RedisClient {

    private static Socket s;
    private static PrintWriter writer;
    private static BufferedReader reader;

    public static void main(String[] args) throws IOException {
        String host = "192.168.6.101";
        int port = 6379;

        // 建连接
        s = new Socket(host, port);

        // 拿流
        writer = new PrintWriter(
                new OutputStreamWriter(s.getOutputStream(), StandardCharsets.UTF_8));
        reader = new BufferedReader(
                new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8));

        // 中间：发请求、解析响应
        sendRequest();
        System.out.println(handleResponse());

        // 释放
        try {
            if (reader != null) reader.close();
            if (writer != null) writer.close();
            if (s != null) s.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }

    private static void sendRequest() throws IOException { }

    private static Object handleResponse() throws IOException { return null; }
}
```

发请求和解析响应的逻辑会比较复杂，这个地方我们暂时把它封装到两个函数里：`sendRequest` 代表发请求，`handleResponse` 代表解析响应。`handleResponse` 返回一个结果，这个结果是不确定的，所以用一个 `Object` 接收，然后打印一下就完了。

架子看起来没什么问题，跑一下试试，OK，架子达成了。下边就是真正去实现发请求和解析响应这个动作。

### 按 RESP 格式把 SET 发出去

发什么请求呢？我们刚才举了个例子，所以说呢我们这个地方先写死好了——就发一个 `SET`。

协议长什么样？我提前已经截好图了，在这里大家可以看到，你要去发一个 `set name 胡歌`。这里边其实包含了多个字符串，所以说呢它其实是一个数组，数组中的每一段都是一个字符串：

```text
*3\r\n
$3\r\n
set\r\n
$4\r\n
name\r\n
$6\r\n
胡歌\r\n
```

挨个拆开看：

- `*3` 中的 `3` 代表数组的元素个数是 3——你不是三段吗，每一段都是一个字符串；
- `$` 代表多行字符串，因为字符串里有可能会有特殊字符；
- `$3` 后面跟的是第一串字符串，它的字节大小是 3，而 `set` 刚好三个字节；
- `$4` 代表下一个字符串的长度是 4，那么内容就是 `name`；
- `$6` 代表下一个字符串长度是六个字节，对应的就是 `胡歌`。

所以接下来我们就可以按照这个形式去把它输出就行了。那怎么输出呢？

这个地方我故意地把每一个换行都写成了一行，为什么呢？这样方便我们等一会儿去输出啊——因为我们这个字符流带有 `println` 功能，它就是打印一行，它会自带一个换行符。那因此我们其实不用管这个 `\r
` 的，我们直接管前边这一串是不是就行了。

```java
writer.println("*3");
writer.println("$3");
writer.println("set");
writer.println("$4");
writer.println("name");
writer.println("$6");
writer.println("胡歌");

// 最后给他刷出去
writer.flush();
```

> **易错点**：千万不要忘了刷新啊，一定要 `writer.flush()`。这样呢，其实一个命令就真正地给发到我们的 Redis 去了。

这里你一定要搞清楚：前两行 `*3` 和 `$3` 合起来代表的是**一个字符串**，只不过它代表的是「3 个元素的数组」，不是一个普通字符串。

#### 让 sendRequest 通用起来

发完了以后，我们是不是还要去解析它的响应结果？那放到最后再说。我们先回到这个发送函数——现在它是写死的，肯定不合适，我们要改造它。

你们有没有发现这里有规律？什么规律？除了一开始这个数组以外，接下来其实就是：**你的命令分成几段，你就循环几次；先输长度，再输内容。** 全是这样。你的命令有三段，那我就这样弄三次就行。

那我们可不可以让别人把命令传给我？传字符串，传几个都行，随便几个——**可变参数**。

> **结论**：数组大小不是死的，它取决于数组元素的个数；元素长度也不是死的，它是**字符串本身的字节大小**。所以循环体内永远是「先写长度，再写内容」，一份代码就够了。

```java
private static void sendRequest(String... args) throws IOException {
    writer.println("*" + args.length);
    for (String arg : args) {
        writer.println("$" + arg.getBytes(StandardCharsets.UTF_8).length);
        writer.println(arg);
    }
    writer.flush();
}
```

这里你一定要区分清楚：这里的**长度不是字符串的长度，是它转成字节之后的字节大小**。字符串长度不一定等于字节的大小——你传 `胡歌`，字符串长度是 2，字节大小是 6。

这样一来你不管传几个命令，我是不是都能接收。现在 `sendRequest` 就是万能的了。

### 解析响应：五种首字节标识一个都不能少

那么解析响应结果怎么解析呢？它可能有**五种情况**，因为 RESP 有五种数据类型。虽然我们自己知道，执行完 `set` 返回的结果可能就是个 `OK`，但是我们现在要写的时候得是通用的，你不确定，所以这五种都有可能，你得在这个地方自己判断好。

那我们怎么去做这个判断呢？我们知道这五种不同的数据类型，它的标识是不是在**首字节**？所以我要做的第一件事情应该是什么？是不是读取首字节。也就是判断这个数据类型的标识，去做这个事情啊。

那怎么去读取首字节呢？我们现在是个字符流——这正是我前面说「应该用字节流读」的原因了，因为这里都是按字节去判断的。但好在什么呢，我们现在用的这种特殊字符，它的一个字符就是一个字节，所以说我们可以简化一下：`BufferedReader` 直接 `read()`，读单个字符啊，刚好现在一个字符就一个字节，利用它去读到的就是这个前缀，也就是数据类型。

```java
char prefix = (char) reader.read();
switch (prefix) {
    case '+': ...
    case '-': ...
    case ':': ...
    case '$': ...
    case '*': ...
    default: ...
}
```

这么多种情况，就不要用 `if else` 了，建议大家用 `switch` 去做判断。

> **易错点**：字符不能用双引号，要用单引号。另外，像这种单字符的协议标识，最好把它定义成一个**字符常量**，放在一个单独的常量类里。像我们现在这样直接写死，其实是不太好的，就很容易出现写错的这种情况。`default` 那支表示你不是上面五种任意一种，那我这里就给你抛一个异常，提示未知类型或者数据格式不正确。

#### 加、减、冒号：三种一次读完的简单类型

`+`、`-`、`:` 这几种非常简单，为什么呢？

- `+` 就是单行字符串，那我直接读到这一行不就完了吗？用 `readLine()` 读一行就完了，甚至可以直接 `return`，不需要去干别的了。这就是单行字符串的好处。
- `-` 其实跟它一样，只不过它里面装的是异常信息。也是读一行，只不过这里不是 `return`，而是抛出——异常的信息就是这一行的内容，把异常信息给抛出去就行了。
- `:` 稍微复杂一点，它是数字。那数字我们除了要读了以外，还要把它解析成数字。所以在这里我们首先要 `readLine()` 读这一行，然后还要把它转成整数。

> **结论**：返回成 `int` 还是 `long` 呢？建议返回 `long`，因为 `int` 有可能太小了，万一人家超过了你的最大值怎么办呢。把字符串扔进 `Long.parseLong()`，它会自动帮我们去转成 `long` 型返回。

```java
case '+':
    return reader.readLine();
case '-':
    throw new RuntimeException(reader.readLine());
case ':':
    return Long.parseLong(reader.readLine());
```

#### 美元符：先读长度，再决定读什么

再然后就是 `$` 了，这种就比较复杂。`$` 这种格式呢，它**要先读的是后面这个字符串的长度**，所以说呢这个地方会复杂一点，多行字符串嘛，先读长度，读数据。

那为什么直接 `readLine()` 就可以读到长度了呢？因为在这个地方，这个 `$` 前缀其实已经被 `read()` 拿走了，所以你现在只剩 `$` 后面的内容了，而 `readLine()` 读到的刚好是那个长度数字。

那长度最好是整形，而不是像现在这样一个字符串，所以通过 `Integer.parseInt` 去做一个处理，得到这个长度。这个长度有多种情况，只有三种：

- **$-1**：代表不存在，那就 `return null`；
- **$0**：代表它是个空字符串，**这两个是不一样的**；
- **正数**：代表当前字符串的长度。

> **注意**：既然是二进制安全的，那这里正确的做法应该是——读 N 个**字节**作为结果，这样一来万一中间有换行符它也没关系。但是呢读字节就很麻烦了，因为我们现在已经没有字节流了，我们现在已经转成字符流了，就没有办法再读字节了。

所以说啊这个地方就很麻烦。我们就不读字节了，这里我们假设什么呢？我们假设**没有特殊字符**，所以只读一行就完了。这个地方是简化了啊，偷懒了啊，都偷懒了。理论上讲不应该这样。大家有兴趣的可以下去自己用字节流去实现这个读的过程。

因为只要不出现特殊字符，我们其实读一行也是没问题的嘛——中间没有换行符的话，我们这一段也能把它读完。

```java
case '$':
    int len = Integer.parseInt(reader.readLine());
    if (len < 0) return null;
    if (len == 0) return "";
    // 偷懒：假设没有特殊字符，直接读一行
    return reader.readLine();
```

#### 星号：数组靠递归读回来

只剩下最后一种就是数组了。数组是最麻烦的，所以我们把它单独抽成一个方法也可以，读数组的话，第一件事同样是先获取数组中**有几个元素**。

`*` 后面的那一行 `readLine()` 就能读到数组的元素个数了，同样通过 `Integer.parseInt` 处理一下。元素大小也做个整型的判断：

- 小于等于 0，就直接 `return null`，代表没有任何东西；
- 大于 0，就代表有元素，我们是不是就可以去读元素了。

那读元素怎么读呢？我们刚才讲了要 `for` 循环遍历。你这个 `len` 比如说是三，我是不是要读三个元素？遍历从 0 到 3。

关键在这儿：**这每一个元素都是一个完整的数据**，它可以是加号的、减号的、冒号的，是不是也可以是多行字符串，甚至还可以是数组。也就是说数组中的每一个元素，都可能会有以上五种情况。

那不就等于我又要执行这个流程了？我现在想去读一个元素，是不是要再调那个 `handleResponse` 方法就可以了？如果我现在再调一次，他是不是就相当于又读了一个元素？那我循环三次是不是就把三个元素都读完了？

每循环一次读到的是一个元素，而数组是有多个元素的，所以我需要定义一个集合来接收到多个元素，最后把这个集合返回就行了。这里其实就等于是一个**递归**了，这里实现了一个递归调用。

> **提示**：`handleResponse` 读出来的元素类型是不确定的，所以集合要用 `List<Object>`。

```java
case '*':
    int size = Integer.parseInt(reader.readLine());
    if (size <= 0) return null;
    List<Object> list = new ArrayList<>(size);
    for (int i = 0; i < size; i++) {
        list.add(handleResponse());   // 递归：每个元素再来一遍五种判断
    }
    return list;
default:
    throw new RuntimeException("未知类型，数据格式不正确");
```

到这我们就把解析响应的代码给写完了，咱们试一下，执行一下。

### 跑一遍：先授权，再执行

诶，这里报了一个异常。什么异常呢？——**没有权限访问**。

为啥没有权限访问呀？还记得我们的 Redis 是不是设了个密码呀？所以报 `NOAUTH Authentication required`。

我打开一个 Redis 客户端验证一下：这里我把它清理一下，退出重连以后，我直接来 `set name 123`，是不是同样报的这个错，`NOAUTH Authentication required`。跟我刚才这里报的错是不是一模一样？这证明我们刚才写的这个响应解析是不是没问题——我们刚才解析的**正是一个异常**。没问题，成功了。

但是那我如果想要获取权限怎么办？我得输入密码。输密码怎么输？`auth 123321`，有了权限了。我再来 `set name 胡歌`，是不是就能 set 了？这就有权限了。

所以你要通过这种方式。也就是说我们回来也就意味着，你在发这个请求的时候，你得发俩请求：你得先授权，要发 `auth 123321`，再发 `set name`。这尴尬了是吧，太尴尬了——因为我们现在定义的这个发请求的代码是写死的，也就是说现在咱们只能发这个 `set`，现在还发不了别的，是不是啊？

那现在呢，同学们我们就可以先授权、再发请求、再解析了。注意你**解析得解析多次**，你不能只解析一次——因为你这次发完请求有一个响应，上面那个发完是不是也有响应啊？你会有多次响应啊。

```java
sendRequest("auth", "123321");
System.out.println(handleResponse());

sendRequest("set", "name", "胡歌");
System.out.println(handleResponse());
```

好，我们来试一下。你看俩都是 `OK` 吗？他们都成功了。

那我试试 `get`——你别光让我 `set`，不让我 `get`！`get name` 只需要一个参数就行，然后我得到的结果我们打印一下。再走一次，诶，怎么样啊？

那我多来两个行不行啊，我来个 `MGET`。`MGET` 我就可以传好几个 key，传 `name`、再传个 `number`，再传个 `message`，我传多个，我去取。那我打开控制台，我先 set 几个：`set number 123`，然后 `set message hello`。好，那我现在就有三个 key 了，回来我们看一下能不能一次性全取出来——怎么样？是不是全取出来了，`name`、`number` 还有 `message`。

这就是发送请求、解析响应的全部代码了。我们基于 RESP 协议实现了对 Redis 客户端的一个模拟。当然，这还是一个比较初级的模拟，毕竟命令都需要自己手写，但是已经很不错了。下一步就是进一步地去做抽象，把这些命令进行常量化，这样将来就可以直接调命令，而不是像这样写字符串。

### 过期删除之一：Redis 怎么知道一个 Key 过期了

接下来我们进入一个新的章节：Redis 的内存策略。

我们知道 Redis 之所以性能这么好，最重要的一个原因就是它的所有操作都是基于内存来去完成的。但是我们之前也说过，单节点的 Redis 它的内存啊不能设得太大——因为我们将来去做持久化或者是主从同步的时候，都需要去操作大量的数据，性能就会有一定的影响。

因此呢我们一般都会在配置文件里去修改配置，设置一下 Redis 的最大的内存。那它既然有了最大内存，那就很有可能随着我们使用内存越来越多，会达到这个极限值。那这个时候如果我们再要去存，不就存不了了吗？那该怎么办？

所以说呢在我们 Redis 里面，就提供了两种不同的策略来避免内存达到这个上限。第一种策略叫**过期策略**，第二种呢就是**内存淘汰**。我们呢先来学习第一种。

内存过期其实我们不陌生，之前我们玩过 `EXPIRE` 命令，它可以给 Redis 中的 key 设置一个 TTL，也叫存活时间。假设我先存一对键值 `SET 胡歌 内蒙古`，然后呢就给这个 key 配一个过期时间，长度为 5。那这个时候如果你在 5 秒钟内去访问，还是能够看得到的；但是如果超过了这个 TTL 存活时间，你再来访问，那么你得到的就是一个空内容，那也就是说这个 key 已经不存在了，那么它所对应的内存肯定也就被回收了。

我们以前学习缓存的时候给大家提到过，其实我们在向 Redis 里写入数据的时候，特别是缓存的时候，最好都配上一个过期时间。那这样就可以尽可能地把一些不需要的赶紧给他干掉，避免这种无效的数据过多地占用 Redis 内存，从而起到一个节省内存的作用。

不过呀，我们之前仅仅是应用这种过期策略，我们知道我配了以后它就能够移除、能够节省内存，**但是我们从来没有认真思考过它背后的原理**。所以呢这节课我们其实就是要探讨一下它背后是怎么实现的。

那这里必然会面临两个问题：

- **第一个问题**：Redis 是怎么知道有一个 key 是否过期的？我们 Redis 当中有数十万甚至数百万的 key，它怎么知道哪个过期、哪个没过期呢？那个过期时间具体是多长，它怎么知道的呀？
- **第二个问题**：那如果真的它过期了，那什么时候把它删掉了呢？是立刻就删掉了吗？

#### 两个字典：一个记数据，一个记时间

那我们先来看第一个问题——Redis 怎么知道一个 key 有没有过期？要想弄清楚这个问题，我们必须得认真研究一下 Redis 数据库的底层结构。

在这里我已经给大家贴好了一个代码片段，这个就是 Redis 数据库，大家看 `redisDb` 的结构。可以看到 `redisDb` 是一个结构体。我们知道在 Redis 当中，它可以有从 0 到 15、默认 16 个这样的库，那么每一个库其实就是一个这样的 `redisDb` 结构体。

它里面的属性非常多，我们首先来看第一个属性，叫 `dict`，它的类型也是 `dict`。那么 `dict` 这种数据结构我们不陌生啊，其实可以把它看作是一个哈希表，因为它里面其实就是键值对的存储模式。我们的 Redis 本身它就是一种 key-value 的数据结构，只不过 value 的类型有很多种，但是不管你是什么类型，它的 key 和 value 最终都是一个 `redisObject`，只不过类型不同。因此呢我们这里采用一种字典的模式——字典不刚好存键值对吗？是不是恰好可以来保存 Redis 当中所有的这些 key 键值了。

> **注意**：`dict` 里边它的这个键值存的不是真正的 key 本身。我们知道 key 和 value 其实都是 `redisObject`，所以字典里其实只要存这个 `redisObject` 对应的**内存地址的指针**就行了。

但是呢，紧跟着往下大家会发现这里又多出来很多属性，而且这些属性都是 `dict` 类型的。那有点意思是吧——明明一个字典就能够保存 Redis 中所有的键值了，怎么这里又整一堆呀？

大家可以看到这里它们的名称啊很特殊：什么 `blocking keys`，什么 `ready keys`，什么 `watch` 的 key。其实啊这里面就是用来记录那些具有一些特殊功能的一些 key 的。比方说我们要去做 Redis 事务里面，可能会用乐观锁去监视一些 key，那么就可以保存到 watched keys 里面；或者说你这里有一个 key 是指一种阻塞式的操作，那么它等待它的结果，就可以放到 blocked keys。所以下边这些其实都是一些特殊功能性的。

**特别需要注意的就是这个叫 `expires`**。从名字就能听出来了，`expire` 是什么？是不是过期的意思呀。

```text
redisDb（0 号库）
│
├─ id = 0                          数据库标识，0~15
│
├─ dict  ── 键空间 keyspace
│    保存库里【所有】key-value
│      key  : 指向 redisObject 的指针（如 name）
│      value: 指向 redisObject 的指针（如 "胡歌"）
│
└─ expires
     只保存【设置了 TTL】的 key
       key  : 和上面 dict 的 key 一致
       value: 一个数字，存活时间（TTL）
```

那么这个字典里边保存的就是我们的过期时间。它也是键值对嘛，它的键就跟我们上边这个 `dict` 的键一样，就是我们 Redis 当中的 key；而它的值却不是 value，而是这个 key 所对应的 TTL 存活时间。那因为不同的 key 它的过期时间不一样，所以呢两者之间刚好形成一个键值对的映射关系，那我放到这个字典里，是不是恰好。

这样一来，我们 Redis 想要知道某一个 key 的过期时间的时候，其实很简单——只要找到这个字典，然后根据 key 来查询，是不是就知道它的过期时间了？从而就能知道他有没有过期了。

> **易错点**：并不是每一个 key 都有过期时间。所以呢，上边这个 `dict` 它里边保存的是 Redis 当中**所有**的键值对的信息；而下边这个 `dict expires` 它里面保存的仅仅是**设置了过期时间的那些 key**。因此呢，`expires` 里面的元素个数应该是小于等于 `dict`。

看两个字典的作用就一目了然了：

| key | `dict`（keyspace，一定有） | `expires`（设了 TTL 才有） |
| --- | --- | --- |
| `name`（设了 5s） | 有 → 指向字符串对象 | 有 → 存活时间 5000 |
| `age`（没设过期时间） | 有 → 指向字符串对象 | **没有** |

那当我们向 Redis 里 `set` 一个键值对的时候，如果你没有给它设置过期时间，它就只存在于第一个字典当中；如果说你设置了，那它就会在这两个里都存在。

再往下的这些属性啊，都是一些功能性的属性了：这个 `id` 代表数据库的标识，0 到 15；然后下面这个其实是记录我们 Redis 当中所有这些过期 key 可以对应的**平均 TTL 时间**。这些都是做统计用的，现在我们不用去管它。所以它最核心的就是两个。

> **结论**：Redis 如何判断一个 key 是否过期？太简单了——就是在 Redis 数据库里包含两个不同的字典，一个字典记录 key-value 键值信息，另外一个记录的是 key 和存活时间这一对信息。如果我们想知道一个 key 有没有过期，很简单，我们只需要拿这个 key 去这里查，查询到对应的这个条目，然后加以判断就 OK 了。

### 惰性删除：访问的时候顺手判一下

那这个时候呢我们就会面临到第二个问题了：我现在知道一个 key 过期了，我是不是立即把它删除了？

所谓的「立即删除」啊，就是说当我们判断一个 key 它到期的那一刻，必须赶紧给他干掉，不能有任何的延时。那要想实现这种立即删除，我们必须**监视每一个 key**，给每一个 key 去设置一个定时器，然后做判断，在它到期那一刻立刻干掉。

如果说我们的 key 比较少，那还好。但是如果我们可以非常的多，达到数十万甚至数百万，那么这些 key 如果我们都给他设置这样一个定时器，其实对于我们的 CPU 会有非常大的一个压力，这样一来呢就会严重影响到 Redis 服务本身的一个性能，所以说呢这个是没有办法接受的。

因此呢，我们在实际应用当中，Redis 采用的并不是立即删除，而是**惰性删除或者周期删除**。

#### 惰性删除：挂在查 key 的那一刻

那什么叫惰性删除呢？顾名思义啊，就是不是在它到期以后立即删除，而是当你**访问它**的时候，我们再来判断一下它有没有到期，如果到期了我再删。

那什么时候我们要访问一个 key 啊？无非就是**增删改查**的时候。不管增删改查的任何一种操作，我们都应该去检查一下这个 key 有没有过期。

但是呢，不管你是做增删改查的哪一种，我们是不是得**先找到这个 key**，然后再去检查它呀？那么因此呢，这个判断其实就是在查到一个 key 的时候去做的判断。

这里我提了一个代码的片段。我们查找一个 key，那可能是用来做写，也可能是用来做读，所以这个代码片段里就有两个函数，一个叫 `lookupKeyRead`，一个叫 `lookupKeyWrite`。但是呢这两个函数它们有个共同的特点——可以看到在这里都可以执行一个函数，叫 `expireIfNeeded`，下边也是。只有在检查完了过期以后没问题，才可以去真正去找这个 key 并返回。

> **结论**：这就是不管你任何时候增删改查的任意一种操作，只要你来访问，我们都可以去做这个检查。

那 `expireIfNeeded` 干了什么事呢？在这里对应的代码大家可以看一下，其实这个代码很简单——就是判断一下这个 key 是不是已经过期了，如果是把它 `delete` 掉，这就是所谓的惰性删除。

那这个判断是怎么判断的呢？其实就很简单了。我们去那个 `expires` 字典里查一查，然后去进行一个时间的判断就 OK 了。

#### 惰性删除的漏洞：没人访问就永远不删

但是呢这里存在一个问题。同学们想一想啊，假如说有一个 key 已经过期了，但是很长很长的时间一直没有人来访问他，那这个时候这个 key 会不会被删除？

显然不会吧。因为只有访问了才会检查嘛，我不访问就不检查，就放在那里。那如果说我们有很多很多 key 都过期了，但是再也没有人访问了，假如说极端情况下，那这些 key 是不是永远不可能被删除？

所以呢对应删除啊，它可能就存在这样一种问题。那为了解决这个问题呢，Redis 里又引入了另外一个，就是**周期删除**。

### 周期删除：一个定时任务，两种模式

顾名思义，它不是说你访问了我再来删啊，而是一个**定时的任务**，周期性地去抽样部分过期的 key，然后执行删除操作。

> **注意**：这个定时任务啊，他不是说我们要整很多很多、给每个 key 都整一个，**总共就一个定时任务**。它也不是说我把数据库里的 key 全部检查一遍——那数百万上千万的 key 我怎么检查得过来。但是**抽样**，也就是说定时去抽一批出来看一看，你们有没有过期，如果过期了给你删除掉。而且这种抽样会随着这个任务的时间的推移，不断地去遍历数据库中不同的 key，直到把所有的 key 都遍历一遍。所以说呢我们可以确保，一个 key 只要你是过期了，早晚有一天你都会被抽到，那么早晚都会把你删掉，不会出现因为一个 key 长时间没人访问，它再也不删除的这种情况。

这个周期检查的任务它分成两种。第一种呢，是在我们 Redis **初始化**的时候会设置一个定时任务，这个定时任务他所执行的任务叫 `serverCron`，那么他们会按照 `server.hz`（也就是赫兹的意思）这样的一个频率来去执行抽样删除的这个动作。

在 `initServer` 这个代码当中有一个片段：`createTimeEvent`，就是创建了一个定时器。那么这个定时器呢，它执行的时间是在 1ms 以后——因为第一次初始化嘛，就会立即先去执行一次。然后呢他执行的任务是 `serverCron`。

那 `serverCron` 长什么样呢？它里面可以做很多很多事情，最后它会返回一个结果：

$$\text{下次执行间隔} = 1000 \div \text{server.hz} = 1000 \div 10 = 100\ \text{ms}$$

这个就是赫兹，默认是十，那 $1000 \div 10$ 是不是 100 啊？也就是说这个东西最终返回值是 100，一般就是下一次执行的这个间隔。那因此 `serverCron` 除了一开始初始化的时候会立即执行以外，后期呢其实就是**每隔 100ms 执行一次**。当然这个值取决于 `server.hz`，而 `server.hz` 值是可以配置的。

它在 `serverCron` 里干的事情非常多，我这里罗列了两个：第一个就是 `get` 这个 `clock`——clock 就是时钟的意思啊，然后 get 完了以后还要把它 `set` 回去，`set` 给 `server.eloClock`。这个 `clock` 你可以理解成是我们 Redis 服务器内部维护的一个时钟，这个时钟的值它记录的是我们的一个**微秒**为单位的一个值，它每隔一个周期——也就是每隔一个 100ms——会记录一次，所以这个值会不断地变、不断地变，代表的就是当前时间。

这个动作干什么事呢？有什么用呢？大家别着急，我们后面会讲啊，现在你先记住它有一个时钟会一直记住这个当前时间。

然后下边有一个 `databasesCron`，那么这个就是真正去执行对数据库的一个清理的动作了。`databasesCron` 里面干的事呢，大家可以看到它调了一个函数，叫做 `activeExpireCycle`，就是**激活一个清理的循环**。为什么叫循环呢？因为它是个清理的动作，这个函数的内部那会有一个循环，不停地做、不停地做，不是说我做一次就完了。

#### slow 模式：低频，但可以慢慢干

具体清理的流程我到时候再给大家讲，现在大家知道有这么一种模式就行了。我们当前采用的是 `slow` 模式，就是采用 `slow` 模式去做这个清理。

`slow` 模式的执行频率受 `server.hz` 影响，默认是 10，也就是**一秒最多执行十次**，每个执行周期就是 100ms。但是啊，这 100ms 并不是说我们就全部拿来去做清理 key 的这个任务——事实上真正执行这个清理的任务，它的耗时**不能够超过周期的 25%**：

$$\text{单次清理时长上限} = \text{周期} \times 25\% = 100\ \text{ms} \times 0.25 = 25\ \text{ms}$$

那剩下的时间你是什么都不能做的。也就是说我们刚才说过那个 while 循环吗，循环到了我们 `serverCron` 的时候，一判断啊，这个时间还没到啊——可能就是你 25ms 刚结束，剩下这段时间我们就不会做任何事情啊，就直接跳过它。可以确保什么呢？它的执行频率相对来讲是固定的，就是不要超过这个每秒十次，然后呢不会对我们的主线程造成太多影响了啊。这是他的一个执行频率和执行时长，这块大家要搞清楚。

那接下来呢，他执行的时候到底做了什么事呢？

首先会**遍历我们整个 db**。事实上我们 `redisDb` 可能会有 0 到 15 中 16 个 db 嘛，所以这里其实一个一个遍历。我们说过他随着任务的推进，会把所有的库都遍历一遍。遍历 db 的过程中，每一个 db 它的内部就是一个字典，我们知道字典其实就是一个哈希表嘛，它里面会有一个数组，那么他会去遍历这个数组中的**所有的 bucket**。

> **定义**：这个 bucket 怎么理解呢？你可以理解成就是那个哈希表数组的每一个**角标**，因为每一个角标上都是一个链表，而这个链表可能会比较长。

所以呢他会**分批**遍历一个 bucket，也就是数组角标的一个位置。那这个角标的位置，等于是你当前遍历的进度啊，那他这个进度呢会记录下来，记录到我们的一个 Redis 的全局变量当中。这样一来我们下次再执行这个任务的时候，可以接着去执行。那按照这样一个思路，他是不是就可以一点一点地，直到把所有的数据库都遍历一遍、所有的 bucket 都遍历一遍为止？所以这是他执行的一个流程啊，可以确保最终所有的 key 都能够被抽样到。

```text
遍历 16 个 db
  └─ 遍历字典数组里的 bucket（数组角标）
       ├─ 从 bucket 里抽 key，不够 20 个就换下一个 bucket
       ├─ 逐个判断是否过期，过期的删掉，没过期的跳过
       ├─ 耗时 >= 25ms ？      ──是──► 结束
       ├─ 过期比例 <= 10% ？   ──是──► 结束
       └─ 都不满足 ──► 再抽一轮，循环重复
```

好，遍历到 bucket 了以后呢，我们就从这里面去找 **20 个 key**，如果这个 bucket 不足，我们再去找下一个 bucket，直到凑够 20 个为止。然后呢去判断这 20 个 key 它有没有过期的 key，如果有过期了就把它干掉，如果没有过期就跳过。

那等 20 个抽完了以后呢？我们先来看一下这执行的一个总的时长有没有超过 25ms 啊。理论上讲其实你做 20 个非常快，不会超过 25ms，很快就执行完了。

执行完了以后呢，这个时候会做一次判断，判断什么呢？判断当前**过期的 key 它的比例有没有超过 10%**。因为呢我们在去抽取的过程中，他在后台会有一个不断的**全局统计**，去统计当前这个过期的 key 有多少、总的 key 有多少，看这个比例。

> **结论**：你其实删了一部分以后，那么这个过期 key 的比例其实就低了一些了——你删得越多，过期 key 的比例也就越低。

那如果这个比例呢它**小于 10%** 了，那就代表什么？过期的 key 就很少，我再去做这个抽样就感觉没什么意义了，可能我抽了半天也没抽到，是不是？所以说呢他认为得不偿失。如果低于 10% 了就不做了，就结束了。但是如果说你这个比例**大于 10%**，也就是说时间还没到——其实一次循环可能就是多少微秒——那如果这个时间没到，并且呢你这个过期 key 的比例还比较大，那它就会再次抽样。

但是如果说时间没到啊，这个比例已经小于 10% 了，他也会提前结束。也就是说这个 `slow` 模式它是**最多 25ms**，不是每次都 25ms，快的时候可能就多少毫秒，甚至多少微秒就结束了。

好但是呢还有一种情况，就是你时间已经超了——时间超了，哪怕你只遍历了一次，我也不再遍历了。**所以这两个条件都要达到**，他才会继续去遍历、重复这个抽的过程，然后再这样循环循环一直重复，直到这个条件不成立为止，然后就结束。这样就是一次 `slow` 模式的一个执行了。

执行完了以后，接下来的这一段时间剩余时间啊，在到达下一个周期之前，它就不会再执行了，每次都会跳过它。这是 `slow` 模式。

#### fast 模式：高频，但一碰就走

那么第二种模式呢就是 `fast` 模式，跟它相比，它们执行的**业务流程是一样的**——同样也是遍历 db、遍历每个 bucket，然后去抽样判断有没有过期，然后呢执行完了以后，同样要做这个时间的判断以及这个比例的判断。那他们的差别在哪里呢？差别就在于**执行的这个周期和它的这个执行的时长**上的差别。

| 对比项 | `slow` 模式 | `fast` 模式 |
| --- | --- | --- |
| 挂在哪儿 | 定时任务 `serverCron` | 事件循环每轮的 `beforeSleep` |
| 执行间隔 | 每 100ms 一次（受 `server.hz` 影响，默认 10） | 每次循环都来，但两次间隔**不得小于 2ms** |
| 单次时长上限 | 不超过 **25ms**（周期的 25%） | 不超过 **1ms** |
| 提前结束条件 | 耗时 ≥ 25ms 或过期比例 ≤ 10% | 耗时 ≥ 1ms 或过期比例 ≤ 10% |
| 清理力度 | 一次多抽点，清理更彻底 | 每次轻一点，抽到即止 |

你可以看到啊，这里同样也是遍历 db、遍历每个 bucket，然后去抽样判断是有没有过期，执行完了以后同样要做这个时间的一个判断以及这个比例的判断。那么差异就是在这个时间上了。

**第一个**就是间隔不能低于 2ms——上面是每次不低于 100ms，这是不低于 2ms。那也就是说我们 `fast` 模式每次执行完，都要判断上一次执行跟这次执行的间隔有没有超过 2ms，如果不足 2ms 他就直接跳过，确保这个频率是这样的。

**第二个**呢，就是执行清理的时间要求更严格，不要超过 1ms。所以我刚才讲了，这一次清理不可能达到 1ms 的耗时，会非常快。那如果说我们一次就完了，时间还没有超过 1ms，并且这个过期 key 的比例依然超过 10%，他就可以再循环一次、再进行一次，有可能 1ms 内可以进行多次，那是有这个可能性的。但是呢如果这两个条件任意一个不满足，同样也会结束。

所以这种 `fast` 模式它的执行频率会相对高一点，但是执行的时长会非常的短，所以呢不会对我们的主线程造成太多的阻塞。

#### 为什么要这么分：回到事件循环里看

很多同学可能对于 `beforeSleep`、`aeMain` 这几个代码具体执行的时机啊，可能有点模糊了，这我带着大家简单回顾一下：

```text
initServer()
  建 server socket、建事件循环、注册事件源、注册定时任务 serverCron
        │
        ▼
aeMain()  ── while (true) 不断转
        │
        ├─► beforeSleep()   ──► activeExpireCycle(FAST)
        │       每轮都跑，单次不超过 1ms
        │
        ├─► aeApiPoll()     ──► 等事件就绪 → 处理 IO（执行 Redis 命令）
        │
        └─► serverCron()    ──► activeExpireCycle(SLOW)
                先判断"到点没"，默认 100ms 一次，到了才跑，最多 25ms
```

我们的 Redis 服务已启动，首先就会先调 `initServer`，完成各种各样的注册。比如说 server socket 给他创建出来，然后我们的这个事件处理器——就是那个 `aeEventLoop` 给他创建出来，然后把 sources 给他注册上去，也就开始监听。这是初始化要干的事，当然也创建了这个定时任务。

接下来呢就会去真正去执行一个函数叫 `aeMain`，`aeMain` 里面就要去开启事件循环了啊，它是个 `while (true)` 不断执行。那在这个不断执行的过程中，他首先会调 `beforeSleep` 这个函数，然后呢再去调这个 `aeApiPoll`——这个就等于是在 `epoll_wait` 等待事件就绪，如果事件就绪了就开始处理 IO 事件，也就是实现我们之前说的对于 Redis 命令的处理，读写各种操作在这边做。

最后呢会去执行这个 `serverCron`，也就是这个定时清理。但是啊，除了我们第一次 `serverCron` 是在初始化后 1ms 直接执行以外，以后每一次 `serverCron` 它执行完都会返回一个时间，也就是 1000 除以这个赫兹，默认就是 100ms，这个时间就是下一次执行的时间。那因此呢，它其实当循环执行到这个地方，它会检查一下这个时间到了没有，如果没到这个 `serverCron` 是不会被调用的。

你要知道这个循环它的频率其实是非常非常高的，可能我们 1ms 就能够循环一次，甚至于快的时候可能几十微秒、几百微秒就循环一次。那如果说我每次循环二话不说直接调用 `serverCron` 的话，那它的执行频率是不是就变得非常高了啊？所以说呢在这里每一次执行前其实要先检查时间，确保 `serverCron` 每隔 100ms 执行一次。

> **结论**：而这个 `fast` 模式则不同。`fast` 模式它每次来就会调，那么这个 while 循环的频率是多少，它执行的频率也就是多少啊。

为什么他要这么设定呢？因为 `fast` 模式它其实执行的速度是非常快的，清理速度也是非常快的，它大概的耗时时间啊都会控制在 1ms 以内。而我们的 `slow` 模式则不然，`slow` 模式它有可能会耗时几十毫秒。

那同学们，我们这个外循环其实是有一个线程——也就是主线程来做的。那如果说我们执行到这里的时候直接耗时几十毫秒，每一次都来执行，每一次到这里都要卡几十毫秒，那也就意味着我们 Redis 的主线程它的执行效率是不是就会受到大大的影响。

那因此呢他这里的 `slow` 模式并不是每次都执行，是每隔 100ms 才执行一次，那在中间的这些循环它都不执行啊，这样可以避免我们的整个线程被 `slow` 模式阻塞。所以呢 `slow` 模式属于是一种什么？**低频、长时长的清理**，那它的清理效果会更好一点，会清理更多的 key。而 `fast` 模式属于是一种**高频、少量清理**，每次我清理一点，每次轻一点，耗时时间非常的短，最长不超过 1ms，一般可能也就非常非常快，可能几百微秒、几十微秒就结束了。

这是这两种清理它的一个特点啊，所以这两种的场景是不一样的。但是最终就是为了保证在不阻塞主线程的情况下，尽可能多地去清理一些过期的 key。

### 把整条链子串起来

那最后我们就做个总结。Redis 它这个过期策略啊，分成两大块：**第一块就是去记录这个过期时间，第二块就是判断和删除的逻辑。**

记录呢，是通过 Redis 数据库底层的一个 `expires` 字典，字典的 key 就是我们 Redis 里面的每一个 key，字典的值就是具体的 TTL 存活时间。那这样一来我们要想知道 key 有没有过期，其实就是来这个字典查他的 TTL，然后做实际上的判断就 OK 了。

但是呢它过期了以后**并不会立即删除**，它采用的是惰性删除和定期删除。对应删除就是：每一次我来访问这个 key 的时候，不管是对它做增删改查哪一种操作，只要你访问了，都需要先找这个 key，找到 key 的时候，我们就顺带判断一下它有没有过期时间，以及有没有过期，如果有就把它删掉，所以这种就称之为**惰性**。

> **易错点**：但仅仅靠它不够。因为仅仅靠它的话，如果一个 key 过期了，再也没有人访问了，那么这个 key 就不会被删除了，永远不会被删除，就会有一定的风险啊。所以为了避免这个问题，他又引入了**定期清理**。

定期清理呢，其实就是不断地去循环遍历我们数据库中的每一个 key，然后就每一次只抽一部分啊，然后呢进行一个判断，如果有我这就去清理掉。随着这个任务往后的推进，那我们整个数据库都会被检查一遍啊，凡是过期的肯定都会被干掉。虽然经过这两种模式就能够确保那些过期的 key 早晚都能被删除了。

但是呢这个定期清理它又分成两种，一种 `slow` 模式，一种 `fast` 模式。`slow` 模式呢就是属于低频的，频率也不超过十，每次执行不超过 25ms。而 `fast` 模式属于高频的，但它的频率不是固定的——最低不能够低于 2ms，也就是说你可以大于 2ms，但不能小于 2ms这个间隔。然后呢每次执行的时长不超过 1ms，可以说执行速度非常快，属于是一种快速清理，避免对于我们整个线程造成太多的阻塞。

到这里，过期策略我们就说到这里了。

## Redis 内存淘汰：什么时候删、删哪些、怎么删
> 对应块：BLK53 | 覆盖分集：P175 | 块标题（分集名）：《原理篇-31.Redis内存回收-内存淘汰策略》

上节课我们学了过期策略——把 Redis 里已经过期的 key 剔除掉。但你有没有想过，在一些非常庞大的项目里，光靠删过期的 key 根本不够用？

数据量太大、写入又一直在持续，不断有新的数据往 Redis 里塞，那可能把过期的 key 删得干干净净，内存照样还是顶到了上限。这时候该怎么办？那就得靠**内存淘汰策略**了。

> **定义**：内存淘汰策略就是——当 Redis 的内存使用达到我们设置的阈值时，它主动挑选一部分 key 进行删除。注意这一次不是"你过期了我才删"，它不管你过不过期：没办法了，我已经不够用了，我一定要去删。

但这么一搞，马上就冒出两个问题，也就是我们这一讲要一条条啃下来的：

1. Redis 到底在**什么时候**去检查内存够不够？
2. 检查发现不够了，我去**挑哪些 key** 来删？总不能随便删吧——把一些热点 key 删了，那不就出问题了。

---

### 第一个问题：什么时候检查内存

先说第一个问题。在整个使用过程中，任何一个时刻，只要不断有数据写入，都有可能让内存溢出。真要等到溢出那一刻再处理，那已经晚了。所以 Redis 干脆一刀切：

> **结论**：只要你来访问我了，执行任何命令的时候，我都要检查检查内存够不够。只要不够，我就去清理。

这个检查点就挂在命令的执行流程上。Redis 接到客户端命令以后，先解析命令，解析完再执行，执行就是进到 `processCommand` 里。而在这个函数里，在真正执行命令之前，它会做各种各样的检查——你有没有权限啊，等等，当然也包括对服务器内存上限的检查。

这里有两个前置条件得满足，才会往下走：

- **你配了 `server.maxmemory`**。就是刚刚给大家提到过的内存上限配置。如果没配，那就意味着内存没有上限，那自然就不需要清理；
- **当前没有在执行 LUA 脚本**。万一你正在跑一段 LUA 脚本，我跑去删 key，很有可能导致这个脚本出问题。

两个条件都满足，就尝试进行内存清理，会去执行 `performEviction` 这个函数，也就是执行驱逐、去淘汰一部分内存。这个执行结果可能成功，也可能失败。如果结果等于 fail，那就代表——我应该清理内存，但清理失败了，那自然就是内存不够，于是 Redis 会报一个 out of memory 的错误。报了这个错之后，他会直接 reject 掉你的命令：不帮你执行了。内存都不够了，我还执行个鬼啊。

整个路径画出来就是这样：

```text
客户端命令
    |
    v
[ 命令解析 ]
    |
    v
processCommand  —— 执行真正命令之前的各种检查
    |
    +-- 权限等常规检查
    |
    +-- 配了 maxmemory 吗？
    |       +-- 没有 -> 内存没有上限 -> 不做任何清理
    |
    +-- 当前正在执行 LUA 脚本吗？
    |       +-- 是 -> 跳过（脚本执行中途删 key 会让脚本出问题）
    |
    +-- 两个条件都成立 -> 执行 performEviction() 尝试淘汰
             |
             +-- 返回成功 -> 内存腾出来了 -> 继续执行命令
             |
             +-- 返回 fail -> 内存确实不够 -> 报 OOM -> reject 该命令
```

第一个问题就这样解决了：**在任何命令执行之前，检查内存并尝试淘汰一部分内存。**

---

### 第二个问题：八种策略，拆开名字看

第二个问题，淘汰的时候到底该淘汰哪一部分。不能随便淘汰，你得有一定的策略。`performEviction` 这个函数内部支持**八种不同的策略**，我们一个一个来看。

第一个 `noeviction`，叫做不淘汰任何 key。管你内存够不够，我一个都不删，我全都要。这种情况下如果内存不足，它就不允许写新数据，直接报错。**事实上默认就是这种策略。**

修改方式是找到配置文件，在里边配置 `maxmemory-policy`，把值调成任意你想要的就行。

剩下的七种，我们先把名字拆开看，名字一拆，规律就出来了。

#### 前缀决定去哪个字典里挑

第二个策略叫 `volatile-ttl`，它是**对设置了 TTL 的 key 进行淘汰**，具体淘汰哪一部分呢？它会去比较剩余的 TTL 值，这个值越小，就说明你剩余的存活时间越短——你都已经快不行了，那我干脆送你一程，直接给你淘汰算了。这就是第二种策略：在快过期的 key 里进行淘汰。

接下来你会发现，这六个策略的名字两两相同：

```text
allkeys-random      volatile-random
allkeys-lru         volatile-lru
allkeys-lfu         volatile-lfu
```

后缀两两一样，意味着它们其实是一类算法，用的是同一种挑法；不一样的是前面那个**前缀**。

前缀 `allkeys`，顾名思义就是全体 key——在所有 key 里进行淘汰。什么叫"所有 key"？还记得我们的 `redisDB` 这个数据结构里有一个字典叫做 `dict` 吗？它里边存储的就是 Redis 中所有的 key。所以凡是以 `allkeys` 开头的，就是在 db 的这个 dict 字典中挑，对所有 key 挑选要淘汰的。

而以 `volatile` 为前缀的呢？它去找那些**有过期时间的 key**，也就是 db 里的另一个字典——`expires`，这个字典里保存的就是带有过期时间的 key。

> **结论**：这两个前缀唯一的含义差别，就是挑选的位置不一样。一个是在所有 key 里挑，一个是在有过期时间的 key 里挑。

#### 后缀才是真正的算法

剥掉前缀之后，八种策略其实只剩四种算法：

| 算法 | 挑谁 | 直觉 |
| --- | --- | --- |
| `ttl` | 剩余 TTL 最小的 | 你都快不行了，直接送你一程 |
| `random` | 随手蒙一个 | 我实在不知道该挑谁了，干脆蒙着眼睛挑，挑到谁是谁 |
| `lru` | 最久没被访问的 | 你都这么长时间没人访问了，我还要你干嘛 |
| `lfu` | 被访问次数最少的 | 几乎没有人访问它，优先淘汰 |

随机显然不会有人去使用，太随意了。那我们就只要弄清楚 LRU 和 LFU 它俩的差别，所有的算法咱不就都清楚了？

#### LRU 和 LFU：一个看时间，一个看频率

这两个是最容易混淆的，因为名字就差一个字母，一个 L 一个 F。

`LRU` 叫 **Least Recently Used**，翻译过来是**最少最近使用**。

> **易错点**：千万不要翻译成"最近最少使用"。很多人会这么翻，这是不对的。你看人家原文写的是 Least Recently，Least 就是"最少"的意思。最近使用就是你最近一次访问的那个时间；"最少最近使用"就是看你最近使用的那个时间越小，我越优先淘汰——因为他会用当前时间减最后一次访问的时间，也就是"你多久没有被访问了"，这个值越大，代表你没被访问的时间越长，你都这么长时间没人访问你了，我还要你干嘛，是不是就可以淘汰掉了。**所以要找的是那个最近使用时间最小的 key。**

`LFU` 叫 **Least Frequently Used**，就是**最少频率使用**，统计的是访问次数。频率不就是次数的意思吗？一个 key 被访问的频率越高，将来被淘汰的概率越小；被访问的频率非常低、几乎没有人访问的，就优先淘汰。

> **提示**：其实真正被叫做"最近最少使用"的反而是 LFU，它看的是使用频率较少；最上面那个 LRU 叫的是"最少最近使用"。这两个是有很大差异的，别混。

---

### Redis 怎么知道这些信息：redisObject 里那 24 个比特

问题就来了。四种算法里，随机不用我们管，TTL 这个时间我们是不是已经记录到 `expires` 字典当中了？每个 key 的过期时间都很容易知道，所以这个也不用你去管。

但是 LRU 和 LFU 有问题啊。统计"最少最近使用"，我必须得知道每一个 key 最近一次被访问的时间是什么；LFU 更麻烦，我必须得知道每一个 key 被访问的频率。这我怎么知道？

所以要弄清楚淘汰策略，就得先弄清楚 Redis 是怎么统计一个 key 最近访问的时间、以及最近访问的频率的。这就跟我们的 Redis 结构有关了——`redisObject`。

Redis 里面存储的所有键值，最后都被封装成了 redisObject 对象。这个对象里有好几个属性：第一个是它的类型，你是字符串还是 list、set 还是哈希，就在这里记录；第二个是 `encoding`，就是你的编码方式；然后是引用计数，这个指针指向真实数据。这些都不说了。

> **提示**：这里面最关键的是 `LRU` 这个字段。它的长度是 **24 个比特位**。之前咱们提到过，但没有解释它的作用——它就是用来记录 LRU 和 LFU 值的。

注意是根据你配的策略不同，它记的东西就不一样。

- **如果你配的是 LRU**，它记录的就是**以秒为单位的最近一次访问的时间**。因为它的长度只有 24 个比特位，所以这个地方记的是以秒为单位。将来就拿当前时间减这个时间，看这个时间差，差越大你就越优先淘汰。
- **如果配的是 LFU**，它要记的是频率，所以就比较特殊了。

#### 配 LFU 时，24 位怎么分

配成 LFU 的时候，它会把这 24 个比特位分成两部分：

```text
 24 bit LRU 字段（配 LFU 时）
 +--------------------+------------+
 |  高 16 bit         |  低 8 bit  |
 +--------------------+------------+
 | 最近一次访问时间   | 逻辑访问次数|
 |   （以分钟为单位） |  (0 ~ 255) |
 +--------------------+------------+
```

高 16 位记录你最近一次访问的时间，只不过这里是以**分钟**为单位——16 个比特位实在是太小了，只能以分钟为单位。低 8 位记录访问次数。

这个低 8 位有个说法叫**逻辑访问次数**。为什么呢？因为如果真的是记录访问次数，你想象一下，8 个比特位最大才 255，难道一个 key 总共只能访问 200 次啊？这不可能。在一个高并发的业务场景下，一个 key 被访问成千上万次都是可能的，只有 8 位你怎么去记这个次数？

所以这里记的不是真实的访问次数，而是**逻辑访问次数**，用它来代替访问频率。

#### 逻辑访问次数怎么加：一套概率算法

那这个逻辑访问次数是怎么算出来的？注意了，这里有一套算法。当一个 key 被访问的时候，它会做这么几个动作：

1. 生成一个 0~1 之间的随机数，记作 $R$；
2. 拿旧的逻辑访问次数乘以一个 **LFU 因子**（默认值是 **10**），然后加 1，用这个结果作为分母；
3. 用 1 除以这个数，得到 $P$——这个值一定小于 1；
4. 把 $R$ 和 $P$ 做比较，$R$ 会不会小于 $P$？如果小于，计数器加一。

写成公式就是：

$$
P = \frac{1}{\text{old\_count} \times \text{lfu\_factor} + 1}, \quad \text{lfu\_factor} 默认 = 10
$$

$$
\text{count}' = \begin{cases} \text{count} + 1, & R < P \\ \text{count}, & R \ge P \end{cases}
$$

举个例子。假设旧的次数是零，那么 $0 \times 10 = 0$，$0 + 1 = 1$，$1 \div 1 = 1$，也就是说 $P$ 的值是 1。$R$ 是一个 0~1 之间的随机数，肯定小于 1，所以这个时候计数器一定会加一。也就是说，只要你是第一次来，计数器一定会加一，加一以后你的次数就变成一次了。

下一次再来的话呢？$1 \times 10 = 10$，加 1 变成 11，$1 \div 11$ 还不到 0.1。那这个时候再用 $R$ 去跟 $P$ 比的话，$R$ 要想小于 $P$ 的概率就低很多了，计数器就不一定能加一了。

所以我们现在不停地访问同一个 key，除了第一次一定会加一以外，后续你再访问时计数器**不一定会累加**，它会隔一段时间累加一次，取决于这个概率。而且你访问的次数越多，分母的值越大，$P$ 的值就越小，$R$ 小于 $P$ 的概率也越小，计数器累加的可能性就越来越低。一开始概率高，后来概率越来越低。

所以它记录的不再是一个准确的次数，而是一个**概率性的次数**。但不管怎么说，不管概率再低，它一定还是有概率的，所以只要你访问的次数足够多，这个值也会越来越大。不过它最大不会超过 255，他会做一个判断，如果超过了就是 255。

> **结论**：通过这套算法，我们用 8 个比特位就能量化地反映出一个 key 的访问频率——虽然不准确，但确实随着访问频率越高，这个值也会越大。这就够了。

#### 逻辑访问次数还要衰减

但是这里还有一个问题。我们假设有一个 key，它一开始被频繁地访问，以至于逻辑访问次数已经达到了最大值 255。紧接着一年的时间就没有人访问它，那这个 key 难道说逻辑访问次数永远是最大、永远不淘汰吗？这不合理吧，你都一年没访问了。

所以逻辑访问次数它不仅仅会累加，它还会**衰减**，会随时间衰减。那怎么衰减呢？

它有一个算法：每次来访问的时候，用你上一次访问时间的间隔。高 16 位不是记录了以分钟为单位的最近一次访问时间吗？那我用当前时间（以分钟为单位）减去上一次访问的时间，得到的就是间隔（以分钟为单位）。然后用这个间隔除以 `lfu-decay-time`，也就是衰减的一个周期，默认是 1 分钟。

也就是说，距离上一次访问隔了多少分钟，计数器就减几。如果你已经超过 255 分钟没有访问过了，那这个 key 对应的计数器就会恢复成零。当然不可能小于零，最低也是零。

写成公式：

$$
\text{decay} = \left\lfloor \frac{\text{当前时间(分钟)} - \text{上次访问时间(分钟)}}{\text{lfu-decay-time}} \right\rfloor, \quad \text{count} = \max(0, \text{count} - \text{decay})
$$

这个 LFU 因子和这个衰减周期，都是可以通过配置文件去配的，也可以通过命令行 `config set` 去配，都没问题。

好，到这儿我们就把 LRU 和 LFU 的统计方式弄清楚了：都是在这个 24 位的字段里，算法不同，记的东西不同。**LRU 算法记的是最近一次访问时间；LFU 算法记的是两部分，高 16 位是时间，低 8 位是逻辑访问次数，相当于是频率。**

### 怎么触发：performEviction 的执行流程

几种策略分析完了，我们去看一看刚才讲的 `performEviction` 这个函数底层的实现。

但是这个函数底层的实现非常复杂：从 512 行一直到 700 多行，中间有 200 多行，你还别提这里面还调了很多很多方法，随便跟进去一个，又是 100 多行。真要跟着代码一行行看，大家肯定就看晕了。我们直接看它整体执行的流程图。

一上来，它首先会判断一下内存是否充足，也就是看一下当前已经使用的内存有没有达到内存最大值。如果没有达到，那就没问题，内存充足，这个函数就结束了，不用管了。

如果判断内存不够了，那它就要去尝试进行驱逐。尝试驱逐的时候，它会先判断你的策略是不是 `noeviction`——我们知道 noeviction 代表的是不驱逐，而是直接报错。所以如果你的策略是 noeviction，那不好意思，直接结束，将来你那边不就报错了吗。

如果你不是 noeviction，那你就是有淘汰策略了。别着急，我们知道不管是随机还是 LRU 还是 LFU，是不是都要去判断：你是从所有 key 里淘汰，还是从有过期时间的 key 里淘汰。所以紧接着它要判断：你这里是 `allkeys` 还是 `volatile`？如果是 allkeys，将来就要走 db dict 淘汰；如果是 volatile，那就要走 db expires 淘汰。你要从不同的地方去挑，所以这里要做一次判断。

判断完了以后，接下来就要开始真正尝试做淘汰了。你的策略有好多种：随机、LRU、LFU、TTL。**随机是最简单的**，先看随机：如果你是随机模式，那就二话不说，直接从库里随便挑一个，找完以后直接删。删完以后判断一下已经释放的内存是否满足需要释放的内存——你不能说我删一个就完了；如果删完了发现释放的还不够，才会再上来一次进行判断、再进行删除，就这样循环，直到删得足够了为止。

好，够了就结束，随机策略就讲完了。

再往上，如果你不是 random，你就可能是 LRU、LFU、TTL 这三种。这三种有一个共同的特点：**要去判断你的 key 的值**——你的 TTL 值、LRU 值或者 LFU 值，要拿来做比较。

那这里就有一个问题了。我们的 Redis 中有那么多的 key，比如说有数百万的 key，难道说我一个一个地给它们排个序，然后进行比较？同学们觉得这可能吗？如果把 Redis 中数百万的 key 一个拿过来，按照 TTL 做个比较，那这一次淘汰所消耗的时间简直太恐怖了。所以不可能。

那怎么办？这里就要讲到一个技巧了。

### eviction pool：用样本近似 LRU

在 Redis 里，它采用的其实不是严格的真正的 LRU。真正的 LRU 你是不是应该一个一个比较？它采用的办法是整了一个池子，叫做 **eviction pool**，用来做驱逐和淘汰的一个淘汰池。

这个池子一开始是空的。我们现在想找出一些要淘汰的 key，又不想去遍历所有的 key，那怎么办？就从这些数据库里挑一些样本，把这些样本放到这个池子里，然后整体再去做一个比较——看看哪一个的存活时间已经到期了，或者哪一个空闲时间太久了，然后去做淘汰。

这样一来，我们其实采用的是一种**样本法**：不是我在 Redis 里随便找一个，而是找一堆，找了一堆以后统一再去比较谁最应该被淘汰。虽然准确率肯定不如把所有 key 都遍历一遍，但准确率还是可以的接受，而且这种方式性能比较好，你不用担心说我要整个遍历一遍，抽一下样本就 OK 了。

#### 候选 key 从哪儿来

池子是空的，接下来就应该往池子里添加一些带淘汰的 key 了。那去哪找呢？当然是去数据库了。Redis 里面不是有 0~15 总共 16 个库吗，所以这里先拿到一个库，再从这个库里去挑一些 key。

这个库里有那么多 key，调到哪个呢？这个地方会去**随机挑选一些样本**。随机挑多少个呢？这里边有一个默认值叫 `maxmemory-samples`，这个值默认是 **5**，也就是说我一次性先从这个库里挑五个。

但这五个 key 是不是一定会扔到池子里去？并不一定。我们现在要找的是那些待淘汰的 key，并不是说所有的 key 都应该被淘汰。比如有一个 key 人家根本就没有设置超时时间，或者说这个 key 经常被访问，你淘汰它干嘛？所以这里有一个标准要做筛选。接下来等于是选秀：选出一部分再往池子里放。那怎么选呢？不同的策略，选的方式还不一样，所以接下来要根据不同的策略去运行不同的筛选标准。

#### 三种算法怎么统一成一套淘汰逻辑

但是这里其实有一个问题，同学们你思考一下：如果我们不同的 key 有不同的筛选标准，将来往池子里放的时候，判断的标准也不一样，这里就会出现一个问题——不同标准你要写一套不同的逻辑，将来你要写的逻辑是不是也越来越多？现在是三种不同的策略，那如果有第四种、第五种、第六种呢，你是不是有无数种策略要写？这样一来我们这个代码就实现起来太麻烦了。

所以为了解决这个问题，我们必须统一这个淘汰池的淘汰标准。那我们这个池子是怎么淘汰的？标准是什么呢？

**我们这个池子会按照 key 其中的某一个值做升序排列，排列完了以后值越大的优先淘汰，也就是倒着来。**

再说一遍：这个池子将来会按照某种方式去做一个升序排列，排列以后值越大的越先淘汰。这样一来，淘汰的逻辑就是固定的了——把 key 放进去，升序排列，排列完了以后倒着从里边找，找到的就是最应该被淘汰的那个。所以流程就变成一致的了。

那现在问题来了：**按什么顺序排列？** 这个是没有办法统一的，你不同算法，这个标准肯定不一样。就是说淘汰的模式是一样的——升序找最大的——但是按什么排序，这个可以根据算法来变。这样一来我们就把能统一的都统一了，不能统一的就个性化就行。

那么我们举个例子，以 LRU 为例。LRU 看的是你最近一次使用的时间，最近一次使用的时间越小，代表你太久没访问了，越应该被淘汰。哎，这不对呀——我们这个池子要求是升序越大越应该淘汰，你这最近一次时间越小越应该淘汰，那不就废了吗？

所以 Redis 做了一件事：**用当前时间减去 LRU**。当前时间减去你最近一次的访问时间，得到的是什么？得到的是你空闲、没有被访问的时间。你没有被访问的时间越大，是不是就越应该被淘汰？符合了升序淘汰的策略。所以当你的内存策略是 LRU 的时候，它就会用当前时间减去你的 LRU 最近一次访问时间，得到空闲时间，称之为叫 **idle time**，然后按照这个来做升序排列。

那 LFU 呢？LFU 是按频率的，LFU 里有个计数器可以看作是统计的频率。但是我们知道频率越小代表访问次数越少，越应该被淘汰，那又不符合升序的逻辑了。所以他又做了一件事情：**用 LFU 的最大值 255 去减 LFU**。频率越小，减完以后的值越大，越应该被淘汰，符合流程了。

那 TTL 呢？TTL 代表的是剩余存活时间，剩余存活时间越小越应该被淘汰，也不符合升序逻辑。所以他又做了一件事情：用最大的这个时间减去 TTL 的值。最大时间其实就是 long 的最大值——**注意要用 long 的最大值减你剩下的时间**。你剩的时间越少，你的这个减的结果就越大，越应该被淘汰，很合理吧。

三种算法，三个不同的计算逻辑，但不管怎么计算，最终都能符合"按升序排列，最大的先淘汰"这样一个策略。为了统一，Redis 把这个计算出来的结果统一都叫空闲时间 idle time。

> **提示**：其实只有中间的这个才是真正的空闲时间，剩下两个都不是。这么叫纯粹是为了代码上统一，这一点别搞混。

三种算法对应的 idle time 算式就是：

| 策略 | 算式 | 结果的含义 |
| --- | --- | --- |
| `allkeys-lru` / `volatile-lru` | `当前时间 - 最近一次访问时间` | 真正空闲了多久 |
| `allkeys-lfu` / `volatile-lfu` | `255 - 逻辑访问次数` | 离"最不常用"还差多少 |
| `volatile-ttl` | `LONG_MAX - 剩余TTL` | 离"最长寿命"还差多少 |

三种算式都能保证：**idle time 越大，越应该被淘汰。**

#### 候选 key 凭什么进得去池子

那算完了 idle time 是不是就可以往里边扔了呢？**不是啊。** 我这个池子还要对你放进来这个 key 做一个判断，不是什么人都能往这放。

你想呀，如果我这个池子已经满了，还能不能往里面放？一定要看，要比一比谁应该被淘汰，谁最应该被淘汰——这相当于是在**比烂**。你不都是有自己的 idle time 吗？我这里边是按升序排列的，你就比一比你的这个 idle time，是不是比我这里边最小的那个还要小。

- 池子没满：那你随便，直接放进来；
- 池子满了：你的 idle time 一定要比这里边至少一个的 idle time 要大，才代表你比别人更烂、更应该被淘汰，你就可以把最小的那个挤出去，你自己就能进来了。

```text
淘汰池（按 idle time 升序）
+----+------+--------+-----------+---------+
| k1 | k2   | k3      | ...       | kN      |   <- 最右边 idle time 最大
+----+------+--------+-----------+---------+      最该被淘汰
  ^
  | 最小值

新候选 key 来了：
   池子没满  -> 直接放进来
   池子满了  -> 算自己的 idle time
                比池子里最小的那几个还大吗？
                   |-- 否 -> 比它们都干净，不该淘汰 -> 丢弃
                   |-- 是 -> 比它们更烂 -> 把最小的那个挤出去，自己进来
```

样本中有五个 key，那就一个一个地这样判断，直到全部处理完为止。

#### 倒序往外删，循环到内存够用

存完了只代表一个数据库处理完了。0 到 15 十六个库，一个处理完了，有没有下一个？有的话就循环回去再来处理，直到把这 16 个库都处理完为止。

> **提示**：所以一般情况下我们建议大家只使用 0 号库。你只使用 0 号库的情况下，是不是就少了很多次循环，会更好一点。

经过这一顿操作，我们是不是就挑选了一部分的 key 扔到这个池子里了？扔到池子里以后，接下来就可以从池子里去删除了。

**删的时候怎么删？倒序。** 刚说过，值越大越应该删。挑一个出来，然后删掉，删掉以后看一看现在内存释放得够不够。够了那就结束；不够就回头重来，再看内存策略，再往上跳一次，再删一个，就这样循环。经过这种循环就能够不断地去删除 key，直到足够我们使用为止。

而且在我们这个执行循环的过程当中，我们每循环一次都会向这个池子里放一部分的 key，而且是跟池子里的比较以后往里面去放。每一次比较的过程中，就会把那些剩余时间小的给他淘汰掉，也就是把他从池子里拿走，而值较大的呢则会被保留下来。这样一来池子里放的就是那些 idle time 值最大的 key。

可能一开始我们挑的样本还不够准确，那随着循环次数越来越多、执行得越来越多，我们可以肯定的是，这个池子里边将来存放的 key 一定是越来越接近于 idle time 最大的那些 key，也就是说它会跟真正的 LRU 算法越来越接近，准确率也越来越高。

所以我们其实不用担心挑样本这种方式在准确率这一块有什么问题。

### 内存回收全景：过期删除与内存淘汰

最后做个总结。Redis 是可以设置内存上限的，为了避免内存到达上限，它里边有两种不同的策略。

**一个是内存过期**：设置一个 key 的过期时间，到期以后我们就可以想办法把它删掉。删的时候策略有两种——一种是**惰性删除**，指当你访问的那一刻，我检查一下有没有过期，过期了就删除；另一种是**周期性的删除**，在 Redis 内部有定期的任务，每隔一段时间它就会去尝试清理一部分过期的 key。这就是所谓的过期策略。

但这种策略只能把那些过期的 key 删掉。如果说这些 key 都没过期，而 Redis 内存又已经达到上限了，又该怎么办？这个时候就会采用**内存淘汰策略**。

内存淘汰策略有八种：

- 一种是 `noeviction`，也就是不做驱逐，将来如果内存不足，那就直接报错；
- 还有七种：两个随机的（`allkeys-random`、`volatile-random`）、两个 LRU、两个 LFU 和一个 `volatile-ttl`。

之所以是两个，就是因为它可以从所有 key 里淘汰，也可以从有过期时间的 key 里淘汰。

所以大家关键的，就是要把 **TTL、LRU、LFU** 这三个算法究竟以什么为标准弄清楚就可以了。

### 淘汰策略速查

| 策略 | 淘汰范围 | 挑谁 |
| --- | --- | --- |
| `noeviction`（默认） | 不淘汰 | 不删任何 key，内存不足时直接报 OOM 并拒绝写入 |
| `volatile-ttl` | 设了 TTL 的 key | 剩余 TTL 最小的 |
| `allkeys-random` | 所有 key | 随机的 |
| `volatile-random` | 设了 TTL 的 key | 随机的 |
| `allkeys-lru` | 所有 key | 空闲时间最长的（最近最少使用） |
| `volatile-lru` | 设了 TTL 的 key | 空闲时间最长的（最近最少使用） |
| `allkeys-lfu` | 所有 key | 逻辑访问次数最小的（最少频率使用） |
| `volatile-lfu` | 设了 TTL 的 key | 逻辑访问次数最小的（最少频率使用） |

相关配置项：

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `maxmemory` | 0（不限制） | 内存上限，超过就触发淘汰 |
| `maxmemory-policy` | `noeviction` | 淘汰策略 |
| `maxmemory-samples` | 5 | 每个库随机抽取多少个候选 key 进淘汰池 |
| `lfu-decay-time` | 1（分钟） | 逻辑访问次数的衰减周期 |
