## Redis 分片集群：横向拆分与故障倒换
> 对应块：BLK33 | 覆盖分集：P108-P111 | 块标题（分集名）：《高级篇-分布式缓存-13-Redis分片集群-搭》

### 主从集群的天花板，卡在哪

前面两章我们学了主从集群和哨兵机制。主从集群能应对**高并发读**，但它有两个绕不过去的坎。

第一个坎在同步上。为了提高主从同步的性能，单个节点的内存设置不能设得太高。内存占用一多，做 RDB 持久化、做全量同步的时候，大量 IO 就会把性能拖下来一截。

这就尴尬了：如果单节点内存上限压到只能存 10G、20G，那海量数据往哪儿放？这个问题主从集群解决不了。

第二个坎在写上。主从集群把读扛住了，可如果**写并发**也很高呢？读写一平衡，还是不够用。

这两个问题，都得靠 Redis 的**分片集群**来解决。这一章我们就把集群搭起来，把散列插槽的原理摸透，再基于散列插槽做集群的伸缩和故障转移。最后还是要用我们的 RestTemplate 去访问分片集群。

### 分片集群的四个特征

分片集群不是"更大的主从集群"，它的结构变了，所以它能同时解决上面两个问题。

```text
                    客户端（连任意一个节点即可）
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
            [7001]        [7002]        [7003]      master，各存不同数据
            [8001]        [8002]        [8003]      各自挂一个 slave
                └─────────────┼─────────────┘
                        Gossip 互相监测
                 （故障判定、主从切换，不再需要哨兵）
```

**第一，集群里有多个 master，每个 master 保存不同的数据。** 我们不再是主从关系了，我每一个 Redis 都是 master。你这保存了 20G，我这 20G，咱仨合在一起是不是就 60G 了。所以数据存储的上限，其实取决于你 master 节点的数量——理论上就能应对海量数据存储。

**第二，高并发写也没问题。** 因为我有多个 master，每个 master 都可以写，并发写的能力自然也就提升了。

有同学会问：你这样并发读的能力不就下降了吗？没关系，**每个 master 还可以再支持多个 slave**。也就是说每一个 master 本身还能形成主从关系，再挂 slave。它就同时具备了主从集群的全部特性：既能高并发读在 slave 上，又能高并发写在 master 上。

**第三，master 之间互相监测。** 通过 Gossip 协议互相做检测，相当于彼此之间起了哨兵的效果——如果多个 master 都认为它主观下线，那也会把它变成客观下线，随时可以做主从切换。所以以前你做主从需要哨兵，现在不需要了，master 之间就互相起到了哨兵的作用。

**第四，客户端连任意一个节点都行。** 这么多机器又没哨兵，Redis 客户端该访问谁呢？事实上客户端可以访问集群中的任意一个节点，因为节点之间会自动路由，把你的请求送到正确的节点上去。所以不再需要哨兵机制，却具备哨兵机制的所有功能。

### 搭建：三主三从的六个实例

搭法还是参考配套资料里的 Redis 集群那一节。跟着 PPT 上的结构，一组两主两从的话总共要九个节点，太多了。我们退一步用**一主一从**、三组三从，一共六个实例：

| 端口 | 角色 |
| --- | --- |
| 7001、7002、7003 | master |
| 8001、8002、8003 | slave |

#### 目录与配置文件

先准备六个目录。**以前旧的目录一定要先删掉**，旧配置可能会产生干扰，再创建新的目录。

配置文件也要重新写一份，因为里面会有集群相关的配置。下面是需要改动的关键项：

```ini
# 开启集群功能，默认是关闭的
cluster-enabled yes

# 集群配置文件的存放位置
cluster-config-file nodes.conf

# 集群心跳的超时时间：互相做心跳超过 5 秒没有心跳，就认为你是疑似宕机
cluster-node-timeout 5000

dir /tmp/7001
bind 0.0.0.0

# 守护进程，默认是 no。改成 yes 之后不往控制台打印日志，持续后台运行
daemonize yes

# 声明主从实例的 ip 地址
replicaof 127.0.0.1 6379

# 保护模式，改成 no，将来就不做用户密码之类的校验
protected-mode no

# 数据库数量，默认一共 16 个，我们用不了那么多，一个就够
databases 1

# 后台运行后控制台看不到日志了，想看日志就指定日志位置
logfile /tmp/7001/redis.log
```

> **提示**：`cluster-config-file` 指向的那个集群配置文件**不用你管**。它是由集群内部自动维护的，只读的，你只需要指明它在哪个位置就行，将来 Redis 自己会维护好。位置自然对应各自的目录——你在 7001 就是 `7001`，在 7002 就是 `7002`，这个将来是要改的。

```bash
vi /tmp/redis.conf
```

#### 一键拷贝，一键替换端口

文件写好之后，要拷到这六个目录里去。你可以一个一个拷，也可以用管道做一键拷贝：

```bash
cat /tmp/redis.conf | tee /tmp/{7001,7002,7003,8001,8002,8003}/redis.conf
```

拷过去还没完。文件里的端口还是默认的 6379，得批量替换成各自的端口：

```bash
for i in 7001 7002 7003 8001 8002 8003; do
  sed -i "s/6379/$i/g" /tmp/$i/redis.conf
done
```

手动去改六个文件就太麻烦了，Linux 上这些命令还是非常好用的。

因为这一次是**后台启动**，不再是前台了，所以我们不需要开六个窗口，可以一键启动：

```bash
for i in 7001 7002 7003 8001 8002 8003; do
  redis-server /tmp/$i/redis.conf
done
```

#### 启动之后：六个人互不相识

用 `ps -ef | grep redis` 看一眼，六个 Redis 全部启动起来了。

但这六个**还没有联系起来**。因为我们并没有在配置文件里指定集群中谁跟谁有联系，所以此刻它们每个人都是一个独立的集群，还处于未形成互联的状态。真正把它们捏成一个集群，是下一步的事。

（顺带一提：以后要关闭的话，本质上就是用 Redis 客户端执行 `shutdown` 命令。这里先不关，我们直接往下建集群。）

### 建集群与查状态

集群的创建有两种方式：一种是 5.0 之前的版本，一种是 5.0 之后的版本。早期要靠一个独立的工具包来实现，需要你去安装；现在已经集成了 `redis-cli`，可以直接用。我们用的是 6.2.4，所以用第二种方式。

在控制台里敲一下 `redis-cli --cluster help`，就能看到集群操作的**所有命令**：`create` 创建集群、`rebalance`、`add-node` 添加节点、`del-node` 删除节点等等。

建集群的命令是：

```bash
redis-cli --cluster create --cluster-replicas 1 \
  192.168.150.101:7001 192.168.150.101:7002 192.168.150.101:7003 \
  192.168.150.101:8001 192.168.150.101:8002 192.168.150.101:8003
```

`--cluster-replicas` 就是集群的副本数量。我们的做法是一主一从、一个主一个副本，所以 replicas 是 1。后面跟的就是集群中所有节点的 IP 和端口，一共六个实例。

> **易错点**：Redis 怎么知道这六个里面哪些是主、哪些是从？判断依据就在副本数上：replicas 是 1，那 master 肯定也是一组 1 个，一主一从加起来等于 2，也就是主从比例 1:1 各占一半。现在总共六个节点，6 ÷ 2 = 3，说明主节点占三个——**因此前三个是主，后三个是从**。

运行之后它会先把计划打给你看：7001、7002、7003 作为 master，8001、8002、8003 作为 slave，然后问你这配置行不行。你觉得 OK 就输入 `yes` 回车，它就尝试建立集群了。看到 `All nodes agree` 也就说明所有节点都同意了，集群创建成功。

查状态非常简单：

```bash
redis-cli -p 7001 cluster nodes
```

出来一大串，8001 是 slave，7001 是 master，8002 是 slave，7003 是 master，所有信息都有了。

这里边有一个比较特殊的东西，就是上面看到的 **`slots`（插槽）**——这就是每个 master 的**散列插槽**。我们在下一节展开。

### 散列插槽：数据为什么不绑节点

#### 先把 16384 个槽分下去

Redis 会把每一个 master 都映射到 0 至 16383、共 16384 个插槽上去。这一列一万多个插槽，集群创建时会分配给每个节点一部分：

| 节点 | 分配到的插槽 | 数量 |
| --- | --- | --- |
| 7001 | 0 ~ 5460 | 5461 |
| 7002 | 5461 ~ 10922 | 5462 |
| 7003 | 10923 ~ 16383 | 5461 |

每个人分一部分，加在一起正好就是 16384 个。

那为什么要做这样一个插槽呢？我们想象一下：现在我要存储一个数据到集群里面，比如说我要 `set number 123`，这个数据应该存到哪一个 master 上？既然每个 master 都可以存数据，存哪一个好？

如果随便挑一个，比如存到 7002，那将来取的时候你怎么知道它在 7002？你是不是就找不到了。**插槽就是来解决这个问题的。**

#### key 怎么算出自己的槽

Redis 当中数据的 key，不是跟 master 节点绑定的，而是**与插槽绑定**的。

具体怎么算？它会先找到 key 的**有效部分**，分两种情况：

- **key 里带了大括号**，并且大括号内部至少包含一个字符——那么大括号里边的内容就是有效部分；
- **key 里不含大括号**——那整个 key 就是有效部分。

比如 `set number 123`，`number` 里面没有大括号，所以整个 key 就是有效部分，将来就根据 `number` 这个字符串来计算插槽。但如果 key 是 `{itcast}number`，那有效部分就是 `itcast`，计算插槽时按 `itcast` 来算。

拿到有效部分之后，用 **CRC16 算法**算出一个哈希值，再**对 16384 取模**：

$$
slot = CRC16(\text{有效部分}) \bmod 16384
$$

你想啊，任何一个数字对 16384 取模，结果是不是一定在 0 ~ 16383 之间，刚好落在插槽范围内。这个结果就是 slot 值。既然每个节点有一部分 slot 值，那我就可以判断你的 slot 值落在哪个节点上——那不就知道应该存在哪个节点了吗？

我们可以连上去实测一下感受一下重定向：

```bash
redis-cli -c -p 7001
```

> **易错点**：在集群模式下，连接参数里**不仅仅要加 `-p`，一定要加一个 `-c`**。`-c` 代表 cluster，就是集群模式，务必加上，切记。

进去之后执行 `set number 123`，和以前做的一模一样。接着 `set a 1`，你就会注意到有一个变化：

```text
(error) MOVED 15495 127.0.0.1:7003
```

这是**重定向**。说明 key `a` 计算出的插槽值是 15495，而 15495 在 7003 上，所以它就重定向到 7003 去了。这时候再 `get a`，就能拿到了，因为你现在已经在 7003 里了。

那 `number` 呢？显然不在 7003。`get number` 同样会被重定向，只不过这次指向 slot 2765，2765 落在 0~5460 之间，对应的就是 7001，于是又被带回了 7001。

所以你操作任意一个 key 的时候，它都会先计算插槽值，再判断你在哪个节点，然后完成一次请求的路由，也就是重定向。这也解释了为什么"访问集群中的任意一个节点都没问题"——它都能实现这种重定向。

整个流程就这么三步：

1. 创建集群时，把 16384 个槽分配到每个节点；
2. 存取一个 key 时，根据 key 的有效部分计算哈希值，再用哈希值算出插槽值；
3. 插槽值算出来，就能判断这个槽在哪个节点上，从而找到对应的数据。

#### 绕开节点绑定插槽，是宕机救命的

那为什么 key 要跟插槽绑定，而不是跟节点绑定？

正因为我们的 Redis 主节点是**可能出现宕机**的，或者是集群扩容增加了节点，或者是集群伸缩删除了节点，都有可能。如果一个节点被删除了或者宕机了，它上面的数据是不是也跟着丢了？

而如果数据是跟插槽绑定的，那么当节点宕机时，我们可以把**这个节点对应的插槽转移到活着的节点**上去；集群扩容时，我们也可以把插槽进行转移。这样**数据跟着插槽走**，就永远都能找到数据所在的位置。这就是 Redis 要把数据跟插槽绑定的原因。

### 让同一类数据待在同一个节点

明白了插槽之后，大家思考一个问题：如果我想将**同一类数据固定地保存在同一个实例**上，我该怎么办？

举个例子。比方说我们的商品，有手机、有空调、有洗衣机等等。我希望所有的手机在 Redis 里存的时候放到一个节点，空调放另外一个节点——就是说相同的商品放到同一个节点上。

**为什么呢？** 因为将来如果有用户去搜手机，我们去 Redis 里查的时候，是不是可以在同一个节点查，避免出现这种请求重定向。请求重定向是不是要重新建立连接，它的性能上一定会有一定的损耗。

怎么实现呢？既然"计算一个 key 到底存在哪个实例"看的是插槽，那么只要同一类数据——比如同一类商品——算出来的插槽是一样的，就一定会存在同一个实例上。

那我怎么让这一类商品算出来的插槽一样呢？**说明它们的 key 的有效部分得是一样的。** 怎么让有效部分一样？给同一类商品的 key 加上一个**共同的大括号**。

比方说我们把**商品类型的 id 作为有效部分**，后面再加上商品 id 作为完整的 key：

```text
{商品类型id}商品id
```

这样在计算插槽值时，就根据类型 id 来计算了。同一类商品算出来的有效部分一样、插槽一样，就都能存到同一个 Redis 实例上了。

我们验证一下。之前 `number` 一直都在 7001 上。这次给它加一个有效部分 `a`：

```text
SET {a}number xx
```

现在存的这个 key 已经不是 `number` 了，是 `{a}number`，有效部分是 `a`。所以它会跳到哪个节点？跟 `a` 一样的嘛——算出来 15495，跳到 7003 上去了。

所以如果你要去控制某一类数据，让它保存到你指定的实例上，你就可以通过这种**控制有效部分**的方式来实现。

### 扩容：把 7004 拉进来，还得让它吃到数据

作为一个分片集群，其中有一个非常重要的功能就是**做集群的伸缩**，也就是你这个集群必须得能够动态地增加节点或者移除节点。

`redis-cli --cluster` 里提供了非常多的命令，可以用 `create` 创建节点，也可以用 `info` 查看节点状态，或者用 `add-node` 添加节点。集群伸缩其实就是添加或者移除节点。

#### add-node 的两组参数

添加节点的命令叫 `add-node`，参数是这样的：

```bash
redis-cli --cluster add-node <新节点IP:端口> <集群中已存在的节点IP:端口>
```

首先是 `new_host` 和 `new_port`，顾名思义就是新节点的 IP 和端口——你不是要添加一个新节点吗，那总得告诉我它的 IP 和端口吧。

但是你会发现，除了新节点和端口以外，还有一个 `existing_host` 和 `existing_port`，也就是**已经存在的**主机 IP 和端口。什么叫"已经存在的"？就是集群中已经有的。

> **提示**：为什么我添加新节点，还要知道旧节点的 IP 端口？因为你向集群中添加一个节点，你是不是得通知集群中的每一个角色？那你是不是得**先联系上这个集群**？这里告诉你集群中已经存在的一个 IP 和端口，我们这个命令就可以联系上集群，从而把这个新节点的信息通知给集群中的每一个节点，这样才算真正添加好。所以它需要两部分参数。

后面还可以加一些选项：`--cluster-slave` 和 `--cluster-master-id`，这两个默认是没有加的。不加这两个参数，新增的节点默认就是一个 **master**；如果你加了 `--cluster-slave`，它就会变成一个从节点，一出生就是个 slave。而且你还可以去指定这个 master id 是谁——每一个实例都有一个 id，你只要指定了，生下来就是 slave，而且能指定它是**谁的** slave。

#### 案例：新增 master 7004，把 number 10 送过去

案例要求是这样的：让我们向集群中加一个新的 master 节点，并且向其中去存储 `number = 10`。

听起来好像很简单，就是加个节点对不对？但这里却暗含玄机。

添加新节点很简单，用刚才看到的 `add-node` 就行，而且新增的是一个 master，不加任何选项就行了。**难点是要存一个 `number = 10`**。我们刚才测试的时候，`number` 的插槽算出来是在 7001 上面的。现在你新增了一个 master，比如叫 7004，你想让 `number` 存到 7004 上——那就意味着你是不是要把 7001 的插槽分配到 7004 上去？你不然这怎么存得过去呢？

所以这里边比较难的点，在于**插槽的分配问题**。

先把这 7004 跑起来。创建目录，把配置文件拷一份到 7004 目录下，把里面的端口都改成 7004：

```bash
sed -i "s/6379/7004/g" /tmp/7004/redis.conf
redis-server /tmp/7004/redis.conf
```

用 `ps -ef | grep redis` 确认一下是不是成功启动了。但它目前还没有成为集群的一个节点，我们需要通过 `add-node` 把它加进来：

```bash
redis-cli --cluster add-node 192.168.150.101:7004 192.168.150.101:7001
```

这时候 7004 就已经成功加入集群当中了。在 `cluster nodes` 里我们可以看到 7004 这个节点了，7001、7002、7003 也没问题。但是 7004 上**有没有任何的插槽**？没有。7001 有 0~5460，7002 有，7003 也有，就 7004 是一片空白。

那我们现在要 `set number`，让 number 到 7004，是不是要把 7001 上面那一部分插槽分配到 7004 上面去？连上 7001 `get number` 一下，我们查到它对应的插槽是 2765。也就是说，**只要我把这 2765 号插槽分配到 7004 这个节点，是不是就能够让 number 存到 7004 这个键上去？** 不然你新增的这个节点不是就没有任何意义了。

#### reshard：把插槽连着数据一起搬过去

怎么分配插槽呢？在 `redis-cli --cluster` 的帮助文档里找一个叫 `reshard` 的命令，这就是重新分配：

```bash
redis-cli --cluster reshard 192.168.150.101:7001
```

指定一个集群中任意一个节点的 IP 和端口就行。它接下来会一项一项问你：

```text
How many slots do you want to move?            3000
Enter the node ID of the receiving node:      <7004 的 id>
Enter the node ID of the source node:         <7001 的 id>
Do you want to proceed with the proposed reshard plan? (yes/no)
```

逐条来说：

- **你想移动多少插槽**：number 的插槽是 2765，我们把 7001 上面的 0~2765 直接移过去也可以，或者直接移 3000 个也可以。这个是移动的插槽的数量。
- **谁接收这部分插槽**：`receiving` 是接收，那就是 7004，把 7004 的 id 复制过来。
- **source 从哪里作为数据源去拷贝**：从 7001 拷贝，所以填 7001 的 id。
- 输入完这些之后敲 `done` 表示结束，剩下没填的都不动了。

然后它会再确认一次要不要把这 3000 个插槽移过去，你回 `yes`，它就开始移了，从 7001 一口气把这 3000 个插槽全搬到 7004。

迁移完再看 `cluster nodes`，7004 上面现在是 0~2999，2765 肯定在里面。现在连上 7001，`get number`，它给我自动切到 7004 上去了；`set number 10` 也就能成功了。这时候 number 已经存在于 7004 这个节点上了——**因为你是把插槽移过去了，数据是跟着插槽走的**。

> **结论**：这个案例的重点就两个命令，一个是 `add-node`，一个是 `reshard`。
>
> 命令大家不要死记硬背，切记了——通过帮助文档去查看和使用。

### 自动故障转移：master 掉线，slave 顶上去

前面我们提过，分片集群虽然没有哨兵，但它也具备故障转移的功能。这一节我们就来验证一下。

我们尝试让其中一个 master 宕机，看一看会发生什么。先说明一下状态：之前我已经把 7004 那个节点从集群里删除了，现在的 master 依然是 7001、7002、7003。

我用一个 `watch` 的方式去监控整个集群状态，然后新开一个窗口：上面监控集群状态，下面让某一个节点停机。比如我要让 7002 这个 master 宕机：

```bash
redis-cli -p 7002 shutdown
```

注意观察这个节点的状态变化：

```text
          redis-cli -p 7002 shutdown
                        │
                        ▼
  7002:  master  ──►  disconnected  ──►  fail（心跳监测判定失败）
                        │
                        ▼
  8003:  slave   ──►  master          （奴隶翻身做主人）
  7002:  重新启动 ──►  slave           （退成小弟）
```

它先是 `disconnected`，失去连接；等待一会儿，就变成了 `fail`，彻底失败。而 8003 这个节点升为主了，这个奴隶翻身做主人了，7002 就变成了一个小弟。

现在把 7002 重新启动起来：

```bash
redis-server /tmp/7002/redis.conf
```

在启动那一刻，它就变成了 slave，所以自动切换就实现了。你可以看到，**我们并不需要哨兵**，Redis 集群自动就具备这种主从的故障切换。

整个过程发生了这么几步：

1. 某一个主节点失去连接；
2. 其他节点对它做心跳监测，发现这哥们失去连接后，把它标记成失败状态，也就是 fail；
3. 标记为 fail 之后，要选一个新的主出来。其实这个地方不用"选"，因为我们每个主只有一个从，直接找出来就行了。

这就是**自动故障转移**。

### 手动故障转移：为了换机器、搞升级

自动转移是被动的——它宕机了，我们才去选一个新的主。但有的时候我们需要做**手动故障转移**。

为什么要做手动故障转移呢？比如说现在集群里边 7001 这个节点是个 master，但是它的机器可能有些老旧了，或者需要做维护了。这时候怎么办呢？

我们可以启动一个新的节点，这个节点性能比较好，然后让它成为 7001 的 slave，然后**手动地**让这个新的节点去替换 7001，实现故障转移。这样是不是就可以实现一台机器的无感知升级了？这种就叫**手动故障转移**。

怎么做呢？做法是这样的：首先你肯定要有一个新的 slave 节点，然后需要在**那个新的 slave 节点上**执行 `CLUSTER FAILOVER` 命令。如果你在这个 slave 节点上执行了 `CLUSTER FAILOVER`，那么这个 slave 对应的 master 就会被替换——它会成为新的主，而那个对应的 master 会成为一个 slave。那你是不是就可以让这个 slave 停机了？就这么一个过程。

#### 五步走完一次角色对调

它的流程是这样的。现在 7001 是 master，8001 是 slave，我想让 8001 替换 7001：

```text
  在 slave(8001) 上执行 CLUSTER FAILOVER
                  │
                  ▼
  ① slave 向 master 发消息："我要替换你了"
                  │
                  ▼
  ② master 拒绝客户端的一切请求
     （"我要下岗了"，凡是进来的请求全部阻塞，避免消息丢失）
                  │
                  ▼
  ③ master 把当前的 offset 返回给 slave
     （"我的数据已经最新到这个位置了，你看看跟我一不一样"）
                  │
                  ▼
  ④ slave 与 master 之间检查 offset 是否一致
     不一致就赶紧同步，直到完全一致
                  │
                  ▼
  ⑤ 完成转移：slave 变 master，master 变 slave
                  │
                  ▼
  新 master 向集群中每个节点发广播："我是新 master"
  原来的 master 收到消息，知道同步和转移都结束了，
  才敢转为一个 slave，开始处理 slave 该干的事
```

每一步都说清楚为什么：

- 第 ② 步 master 为什么要拒绝一切客户端请求？因为 master 不接新命令了，才能保证数据不会被新写入搅乱。
- 第 ④ 步为什么必须校验 offset？因为 master 已经把"数据最新到这个位置"告诉 slave 了，如果不一样，slave 得先同步。同步完成了，slave 和 master 数据才完全一致。

这个过程执行完毕以后，slave 把自己标记为一个 master，然后就开始发广播，通知集群中的每一个节点。集群中的节点收到消息以后，以后就跟它交互了。

这个 `CLUSTER FAILOVER` 命令其实还有几个参数。缺省什么都不写时，默认参数就是按上面这个流程一步一步执行。

#### FORCE 和 TAKEOVER：两档更暴力的力度

一个是 **`FORCE`**，强制的意思，就是省略了对 offset 的校验——也就是跳过前面跟数据一致性有关的那几步，上来就通知"我要替换你了"，也不管数据一样不一样，直接开始替换。这种情况就比较暴力了。

还有一个更暴力的，叫 **`TAKEOVER`**，就是我直接接管你了。它直接执行第 ⑤ 步：忽略数据一致性，忽略 master 状态和其他 master 的意见，前面几步都不做，上来就把自己标记成 master，通知集群中的其他人，直接把他干掉。所以属于是最暴力的一种。

> **易错点**：如果你想直接强制替换，可能会用 `FORCE` 或 `TAKEOVER`，但**一般是不推荐的**，一般就用默认缺省就可以了。

我们演示一下：在 slave 7002 这个从节点上执行手动故障转移，让它夺回 master 的地位（刚才 7002 被我们弄宕机、变成 slave 了，现在让它恢复一下）：

```bash
redis-cli -p 7002
CLUSTER FAILOVER
```

注意观察状态：702 变成 master 了，之前那个 8003 就变成 slave 了。就一瞬间，切换就完成了。

> **结论**：自动故障转移是为了避免一个服务突然宕机而引起的数据损失；而手动故障转移是我们有目的性地去做的一种迁移，用来做服务的升级或者数据迁移。

### 分片集群的 Java 访问：和哨兵只差一步配置

RedisTemplate 里面已经集成了分片集群，而且它同样是基于 Lettuce 实现的，Redis 里的功能它全都能用。所以用法跟前面学的哨兵模式基本一致，还是老三步：

1. 引入 Redis 的 starter 依赖；
2. 配置分片集群的地址；
3. 配置读写分离。

第一和第三步咱在哨兵那会儿已经做过了，差别就出在第二步。哨兵里配的是**哨兵的地址**，分片集群里配的是**集群中每个节点自己的地址**——因为分片集群里压根就没有哨兵这个角色。

```yaml
spring:
  data:
    redis:
      cluster:
        # 分片集群没有哨兵，这里要把每个节点都配进来
        nodes:
          - 127.0.0.1:7001
          - 127.0.0.1:7002
          - 127.0.0.1:7003
          - 127.0.0.1:8001
          - 127.0.0.1:8002
          - 127.0.0.1:8003
```

也就是说 7001、7002、7003 和 8001、8002、8003 六个全配进来就 OK 了。改完配置把项目启动起来，清空日志，我们来验证两件事。

**第一件：读写分离是不是真的生效了。**

在浏览器里查一个 `number`，查到了 10。这个 key 我记得是在 7001 上的，我们去日志里翻一下这个 GET 请求——它没有走 7001，而是走到了 8002 这个从节点。这不就证明读写分离生效了：查询都是走从节点的。

8002 是不是 7001 的从节点？打开控制台看一眼就知道——8002 的角色是 slave，它记录的 master id 和 7001 是同一个。既然 `number` 在 7001 上，那也就等于在 8002 上，从 8002 读没有任何问题。

**第二件：插槽的自动路由是不是也生效了。**

再执行一个 SET 写 `number`，这个肯定得去 7001，日志里一翻果然是 7001。换一个 key 再来：`set a 666`，这个 `a` 落在 7003，日志里就是 7003。

```text
读：get number  → number 落在 7001，而 7001 的从节点是 8002，实际读的是 8002
写：set number  → 7001
写：set a 666   → 7003
```

所以节点间的动态切换、插槽的自动路由、读写分离，全部都实现了。

> **结论**：分片集群的 Java 访问跟哨兵玩法一模一样——第一步引依赖，第二步配地址，只不过地址从"哨兵地址"换成了"集群节点地址"，第三步同样配读写分离。这是唯一的差别。

### 亿级流量下，Redis 单机为什么还不够

有同学会问：Redis 各种各样的知识我都已经学过了，缓存也学了，我自认为已经精通了，还有什么知识需要我学？

我们捋一捋缓存的作用：**减轻对数据库的压力、缩短服务的响应时间、从而提高整个服务的并发能力**。这三件事 Redis 都在干，而且 Redis 单机的并发其实已经很高了。

但是呢，它依然有自己的上限。随着互联网的发展，用户体量越来越大，特别是像淘宝、京东、12306 这样的网站，它的并发量往往能达到**亿级以上的流量**。这个时候仅仅靠一个 Redis 能满足高并发需求吗？显然不行。

我们今天要学的**多级缓存**，正是为了去应对这样亿级流量的并发。

### 传统缓存卡在哪两个地方

先回顾一下传统缓存的流程，以及它存在的问题。

```text
用户请求
   │
   ▼
Tomcat 服务器        ← 瓶颈：Tomcat 的并发能力其实不如 Redis
   │ 先查
   ▼
Redis 缓存 ──命中──► 直接返回
   │ 未命中
   ▼
数据库               ← 缓存失效或宕机时，全部请求直接压到这里
```

读图很直观：用户请求先到达 Tomcat，Tomcat 优先查 Redis，命中直接返回，未命中才去访问数据库。这样绝大多数请求都被 Redis 处理了，只有少数才会到达数据库，数据库压力大大减少。

但它有两个绕不过去的问题。

**第一，请求要经过 Tomcat 处理，Tomcat 的性能成了限制整个系统的瓶颈。** 用户请求依然要进 Tomcat，再由 Tomcat 去查 Redis 缓存。我们知道 Tomcat 本身的并发能力其实是不如 Redis 的，那在整个流程当中，谁成为了整个业务的瓶颈？是不是 Tomcat 呀。

**第二，Redis 缓存有过期的可能。** Redis 有淘汰策略，对吧。当部分缓存失效时，或者干脆这个缓存直接挂了，那么所有请求就直接打到了数据库——那不是"不会"对数据库产生巨大的冲击，而是一定会。

> **易错点**：传统缓存把"缓存失效"这件事完全押在了 Redis 一层身上。它一旦过期或宕机，数据库就是裸奔的。

### 多级缓存：把请求链路上每一段都用起来

多级缓存简单来讲就是：**充分利用请求处理的每一个环节，都给它加上缓存**，从而减轻数据库压力、提升性能。

具体是什么意思呢？我们沿着一个用户请求的完整链路走一遍。

```text
浏览器 / App
   │
   │  ① 浏览器客户端缓存：静态资源没变化就返回 304，浏览器直接渲染本地数据
   │     非静态数据 ↓
   ▼
Nginx
   │
   │  ② Nginx 本地缓存：命中直接返回，不过 Tomcat；未命中 ↓
   ▼
Redis
   │
   │  ③ Redis 缓存：命中直接返回；未命中 ↓
   ▼
Tomcat
   │
   │  ④ Tomcat 进程缓存（JVM 进程内）：命中就不访问数据库；未命中 ↓
   ▼
数据库
```

**① 浏览器客户端缓存。** 我们的浏览器其实是可以把服务器返回的静态资源缓存在本地的。下次再去访问这些静态资源的时候，服务器只要检查一下数据有没有变化；没有变化就直接返回 304 状态码，不用返回数据了。浏览器一看，304，说明本地有，那就直接把本地数据渲染出来，用户马上就能看到。这就减少了大量的数据传输，从而提高渲染和响应的速度。而事实上，对于一个页面来讲，**90% 的请求都是这种可以缓存起来的静态资源请求**——你想一下，响应速度是不是大大提升了？

**② Nginx 本地缓存。** 对于一些非静态的数据，那就不得不访问到服务器端了。请求到达我们的 Nginx——以前的 Nginx 只做反向代理，现在我们在它内部形成第二级缓存。因为 Nginx 同样可以像 Tomcat 一样去编写业务逻辑，我们就可以把数据缓存在 Nginx 本地。用户请求来了以后先看缓存有没有，有就直接返回，压根就到不了 Tomcat，响应速度是不是快了很多？

当然也有本地缓存没命中的情况。那这时候要去查 Tomcat 吗？哎不是——既然都要在 Nginx 编程了，那就直接写到底呗，干嘛还绕 Tomcat，直接在 Nginx 查 Redis。注意了，**Redis 以前是在 Tomcat 干的查，现在是在 Nginx 查**，压根就不需要到 Tomcat，Tomcat 压根就不参与，那它的压力是不是大减轻？

**③ Redis 缓存。** 到这一步就是老熟人了。命中直接返回，未命中才到达我们逃不掉的 Tomcat。

**④ Tomcat 进程缓存。** 到 Tomcat 以后是不是直接访问数据库呢？也不是。在这我们形成第四级缓存，叫 Tomcat 进程缓存——我们在服务器内部利用比如说类似 Map 这样的形式形成一个进程缓存。当然实际上我们不会用 Map，会用更高级的一些东西来实现它。请求到达以后先去读本地缓存，这个进程缓存如果命中了直接就返回，也就不用去访问数据库了。

通过这样层层的缓存，就把之前说的两个问题都解决了：

- 第一，大多数请求其实都被 Nginx 处理了，不用过 Tomcat，Tomcat 的压力大大减轻，它就不会成为整个系统的瓶颈了；
- 第二，当 Redis 缓存失效时，我们还有 Tomcat 的进程缓存作为一个缓冲，从而不会直接打到数据库，避免了对数据库的冲击。更何况前面还有好几层缓存呢。

那这个时候所有压力集中到哪儿了呢？集中到 Nginx。我们需要在 Nginx 的内部去实现业务访问的编写，也就是说 Nginx 此时不再只是一个反向代理服务器了，它变成了一个真正的对外服务，在里面写业务逻辑。因此将来这个 Nginx 需要部署成一个集群，才能应对更高的并发。我们还可以再准备一个单独的 Nginx 专门用来做反向代理——请求到了它以后，它再反向代理到多个编写本地缓存业务的 Nginx 服务器，然后再往后去访问 Redis、Tomcat。当然了，Redis、Tomcat、MySQL 也都可以做成集群。

```text
浏览器 / App
      │
      ▼
Nginx 反向代理（只做静态资源 + 负载均衡）
      │  把请求负载均衡到下面任意一个业务节点
      ▼
  ┌───┴───────┐
  ▼           ▼
Nginx 节点1  Nginx 节点2      ← 用 Lua 写业务，带本地缓存
  └───┬───────┘
      ▼
 Redis 集群
      │ 未命中
      ▼
 Tomcat 集群（进程缓存）
      │ 未命中
      ▼
    数据库
```

读这张部署图要抓住一个名分：前面那台 Nginx 和后面那几台 Nginx 已经不是同一个角色了。前面那台是纯反向代理，后面那几台是要写业务的多级缓存节点——就是所谓的"Nginx 业务集群"。

那么，作为服务端开发人员，我们关注的其实是从 Nginx 开始往后的这部分内容。这里我们需要学的知识有这么几处：

```text

2. Nginx 编程     —— 在 Nginx 内部写业务，要学一门新语言：Lua

4. 缓存同步策略   —— 缓存实现了也别忘了，数据库与缓存之间还要做同步
```

### 商品和库存为什么分成两张表

导入完刷新一下，两张表：

| 表 | 内容 |
| --- | --- |
| `tb_item`（商品表） | 商品 id、标题名称、价格、图片、品牌分类等基本信息，一共 5 条数据 |
| `item_stock`（库存表） | id、库存、销量，就三个字段，id 和商品表是对应关系 |

它俩其实可以看作是一张表。那为什么这个地方做了分离呢？

事实上一个商品的数据是非常多的，不只是大家现在看到的标题名称这些，还有库存销量，还有商品的介绍。大家去京东买过东西吧？随便找一个商品点进去看看，除了上面这些基本信息以外，下面是不是还有非常复杂的一些详细介绍信息、规格参数、包装、售后保障、用户评价——这些信息非常的多，往往就需要有 N 多张表去保存，而不是一张表。当然你说你用一张表也能存，一定是能存，但为什么要把它分离呢？大家思考一下。

**一方面是数据解耦。** 一张表数据太多了、字段太多了，查询效率是不是会比较低？

**另一方面是为缓存考虑。** 将来我们要给这些数据加缓存。如果所有数据全在一张表里，那缓存的就是一条包含商品完整信息的数据。一旦这条数据里边的任意一个字段做了修改——比如库存，因为库存经常性地会变化嘛——结果整个商品的缓存是不是全都失效了？因为你是一条数据，一旦数据发生修改，整条数据都要作废，那整个缓存失效的频率是不是太高了？而缓存经常性地未命中，其实是不好的。

所以我们把数据分离：经常修改的、不经常修改的，都给它分开，形成好几张表，将来就是好几个不同的缓存。库存这部分数据改了，它这部分缓存过期了，其他缓存不受影响。

> **结论**：数据分离要做细。这既是数据库表的设计，也是后面缓存设计能跑得动的前提。

同学们能理解啥意思吗？也就是说现在这个 Ajax 请求被这个反向代理服务器拿到了，那他拿到以后不能处理对不对，他需要把它代理到我们后台那个叫"Nginx 业务集群"里去，然后由 Nginx 业务集群完成后续的多级缓存处理。所以我们现在需要在这个反向代理服务器里完成反向代理的配置——反向代理的配置大家以前也都学过，这里已经给大家做好了。

```nginx
upstream nginx_cluster {
    server 192.168.150.101:8001;
    # 第二台机器的地址，按自己的实际情况补充
}

server {
    listen 80;
    # 以 /api/ 开头的请求，反向代理到 Nginx 业务集群
    location /api/ {
        proxy_pass http://nginx_cluster;
    }
}
```

`nginx_cluster` 其实就是我们刚刚聊的那个 Nginx 业务集群。这个集群将来做什么？做 Nginx 的本地缓存、做 Redis 缓存、做 Tomcat 缓存、查询等等，就是做这些多级缓存的活儿。所以将来这个集群里面的 Nginx 是要写业务的。

### 进程缓存和分布式缓存：一对互补的拼图

分布式缓存大家已经不陌生了，我们用的 Redis 就属于分布式缓存。为什么叫分布式呢？因为它往往用在集群的环境下。比如说我们有 N 台 Tomcat，每一台都要访问这个缓存，那我们就可以用 Redis 缓存。因为 Redis 缓存是独立于 Tomcat 之外的，所以不管你是 10 台还是 100台 Tomcat，它们都可以共享 Redis 缓存——这也是分布式缓存的一个巨大优势：**可以在集群间共享**。而且因为 Redis 本身也能搭建集群，所以它的存储容量其实可以非常非常大；Redis 的哨兵机制、它的主从模式也可以提供更好的可靠性。所以在一些大型的项目当中，对于数据存储要求较高的，往往都会使用 Redis。

但是呢，它也有一些缺点。因为 Redis 毕竟是独立于 Tomcat 之外的，那 Tomcat 要访问 Redis 时，必然要向 Redis 发起网络请求，所以需要带来额外的一些网络开销，它的性能也会受制于网络，存在网络延时。

进程本地缓存这个概念我们以前没有专门提过，但其实大家也都用过。比如说你整一个 HashMap 放在那里，把数据存到这个 Map 里，下次要读的时候直接从 Map 里读——这本身就是一种缓存。本地缓存相对 Redis 有一些优点：它在本地直接读本地内存，不用通过网络进行请求，所以速度更快。当然，也正是因为这个原因，它也带来了一些缺点：

| 对比维度 | Redis 分布式缓存 | JVM 进程缓存 |
| --- | --- | --- |
| 存放位置 | 独立于 Tomcat 之外 | Tomcat 进程内的堆内存 |
| 多实例共享 | 可以，10 台还是 100 台共用一份 | 不可以，每台各自一份，数据冗余 |
| 存储容量 | 能搭集群，容量可以非常大 | 上限就是当前 Tomcat 的 JVM 堆内存，而且你也不能一个人占完，否则程序运行就有问题了 |
| 可靠性 | 哨兵、主从模式能提供更好的可靠性 | 进程重启或服务宕机，数据就丢了 |
| 访问性能 | 要走网络，受网络延时影响 | 本地内存直读，更快 |

所以可以看到，进程缓存它的性能更好，但是可靠性、容量都比较差，也无法共享；而 Redis 缓存呢，在这些方面有着巨大的优势，但是性能相比进程缓存来讲存在一定的差异。

> **结论**：进程本地缓存其实是作为 Redis 缓存的一种**补充**来使用——当 Redis 缓存未命中时，我们再去看一下进程缓存。所以企业开发中，肯定是两者结合去使用的。

### Caffeine：先把本地缓存这件工具认识清楚

本地缓存我们使用 **Caffeine** 这个库来实现。这个单词翻译过来就是"咖啡因"，它基于 Java 开发，可以提供近乎最佳命中率的、高性能的本地缓存库，Spring 内部很多时候也会用到这个库。

下面这个是官方给出的一个测试，是读写测试，读写的比例大概是 3:1 的样子：

| 对比对象 | 是什么 |
| --- | --- |
| Caffeine | 蓝色块，最牛的就是它 |
| `ConcurrentHashMap` | JDK 里自带的那个 |
| Guava | Google 的一个库 |
| Ehcache | 另一个缓存库 |
| Infinispan | 以及等等各种各样的缓存库 |

你可以说最牛的就是这个 Caffeine，所以我们目前基本上都是使用这个库。它的官方网站在 GitHub 上，Wiki 里面有它的官方文档说明：各种各样的说明下面就有缓存的用法，如何去添加数据、如何去清除一个数据、如何去刷新缓存、如何做各种各样的运算统计，都有。有兴趣的同学也可以自己去看看这份官方文档，还有它的性能测试。

那怎么去使用它呢？我们就不去看官方的这个文档了，回到我们的 demo 一起看。

#### 基本 API：查不到就让函数去加载

首先是 `Caffeine.newBuilder()`，这个一看就知道了，是一个工厂模式获取一个工厂，然后再利用这个工厂 `build` 去构建出一个缓存对象。这个对象上有两个泛型，其实就是它的 key 和 value，这一点跟我们的 Map 很像。

得到缓存对象以后，就可以去存和取数据了。存怎么存呢？`cache.put`，是不是跟我们的 Map 更像了？key 后面跟上 value。

```java
Cache<String, String> cache = Caffeine.newBuilder().build();

// 存：key 是 gf，value 是我女朋友
cache.put("gf", "迪丽热巴");
```

那怎么取出来呢？我们还可以利用 `cache.getIfPresent` 去取。这个方法名就是"如果有我就取"，那如果没有呢？它会返回一个 null，那你就可以答应他了。

```java
String gf = cache.getIfPresent("gf");
System.out.println(gf);   // 迪丽热巴
```

但这种取法其实并不是我们用得最多的。你想啊，我们日常写缓存，是先查缓存；如果未命中，就要查数据库，然后把数据库查出来的数据再写到缓存里边，把结果返回给用户，是不是这样子？

所以 Caffeine 提供了这样一个方法叫 `cache.get`：`get` 的时候你传第一个参数 key，它帮你去缓存里取；如果缓存未命中，你再传第二个参数——第二个参数是一个 `Function`（大家可以看到 Lambda 表达式，它代表的是一个函数），这个函数里面你要写的就是查询数据库的业务逻辑，然后把数据库的结果返回。

综合来讲这个函数的意思就是：我先帮你根据这个 key 查缓存；如果缓存未命中，我就来执行你第二个参数这个函数，你去数据库查嘛，查完以后把结果给我；给我以后呢，我会帮你把这个结果存入我们的缓存里，并且把结果返回给用户。

```java
// key 存在：查出来返回；key 不存在：执行 Function，返回值写入缓存并返回
String defaultGf = cache.get("default:gf", key -> {
    // 真实场景在这里查数据库；demo 里就直接返回一个假数据
    return "柳岩";
});
System.out.println(defaultGf);   // 柳岩
```

也就是说，这一个方法把咱们以前写缓存要做的那一堆事儿全做了：查缓存、判断有没有命中、没命中查数据库、查询数据库写入缓存，全做完了，是不是非常方便。这就是 Caffeine 的基本篇。

我们把这个单元测试运行一下，可以看到它绿了：第一个 `gf` 查到的是迪丽热巴，第二个 `default:gf` 是柳岩——因为缓存里不存在这个 key，走的是我们写的那个假数据。

#### 驱逐策略：容量、时间与引用

缓存的存和取很简单，对吧？但是如果缓存不停地往里面存，终有一天可能会把缓存填满。所以作为一个缓存来讲，它一定得有一个过期、或者讲缓存的驱逐策略：什么情况下我要把一些缓存清理一下？

Caffeine 里面提供了三种缓存的驱逐策略：

| 策略 | 配置 | 含义 |
| --- | --- | --- |
| 基于容量驱逐 | `maximumSize` | 设置一个缓存的上限，比如最大值为一，就是我最多存一个 key；一旦超过上限意味着达到阈值了，就可以做内存清理，清理时采用 **LRU 策略**，跟 Redis 一样，最近最少使用 |
| 基于时间驱逐 | `expireAfterWrite` | 在写入之后开始计时，比如 `Duration.ofSeconds(10)` 就是 10 秒钟；写入超过 10 秒以后，如果没有人访问了，就会把它清除 |
| 基于引用驱逐 | 软引用 / 弱引用 | Java 里有垃圾回收机制，一个对象没人引用就可以被回收；Caffeine 底层可以基于软引用或弱引用来配置它的 key/value，利用 GC 机制来回收它里边的数据 |

基于引用的这种方式，官方有交代说是**性能太差、不建议使用**，所以一般情况下我们基于前两种就 OK 了。

> **易错点**：跟 Redis 一样，Caffeine 的缓存驱逐策略并不是立即驱逐的。当你超过缓存上限以后，它只是给你做一个标记；什么时候驱逐呢？一般是在你下一次做读写操作时，或者是在空闲时间——就是我闲了没啥事干了，去做一下这个驱逐。所以它不是一种立即清除。

我们做个测试感受一下。基于上限的这个：

```java
Cache<String, String> cache = Caffeine.newBuilder()
        .maximumSize(1)   // 我的缓存最大值只能存一个
        .build();

// 我有三个女朋友，全往里面存
cache.put("gf1", "迪丽热巴");
cache.put("gf2", "杨幂");
cache.put("gf3", "赵丽颖");
```

问题来了：最大上限为一，怎么三个都进去了？这就是因为**它驱逐需要时间**——你直接运行完，JVM 就退出了，它根本就没机会在这儿驱逐。你可以稍微让它休眠一下，给它一定的空闲时间再来尝试。你看这一次，前两个 key 是不是就被清理掉了，只剩下最后一个 key 了。这就是按缓存上限去做清理。

按时间清理的：

```java
Cache<String, String> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofSeconds(1))  // 写入之后清除，时间 1 秒
        .build();

cache.put("gf", "柳岩");
System.out.println(cache.getIfPresent("gf"));   // 柳岩

Thread.sleep(1200);
System.out.println(cache.getIfPresent("gf"));   // null
```

第一次打印出来是柳岩，第二次打印是 null，那也就说明缓存确实是被清掉了。这就是按照时间清理。

最后是企业开发中的用法：你可以在开发的过程中把缓存提前定义好，放到一个地方，定义成一个静态的工具类也好，非静态的工具类也好都行；接下来把这个 `Cache` 对外暴露，让别人去使用它、往里边做数据读取就行了。

## 把缓存写进进程：Caffeine 落地与 Nginx 业务底座的起步
> 对应块：BLK35 | 覆盖分集：P117-P121 | 块标题（分集名）：《高级篇-多级缓存-05-JVM进程缓存-实现进程》

上一节课我们把 Caffeine 这个库的基本用法过了一遍，那这节课就顺理成章：拿它来实现商品查询的 JVM 进程缓存。

但这一块的内容不止于此。等进程缓存落地，我们就要正式换战场了——从 Tomcat 里的 Java 代码，挪到 Nginx 里的 Lua 代码。所以这节课实际走了两段：先把上一节的 Caffeine 收尾落地，再把 Lua 这门语言和 OpenResty 这个底座准备好。

### 商品与库存，各自一份进程缓存

需求先摆在这：在根据 id 查询商品的接口上加一个缓存，缓存没命中就去查数据库；根据 id 查询库存的接口同样加一个。另外这个缓存的**初始大小是 100，上限是 1 万**，超出就按淘汰策略清理。

这里有个点得先拎出来说：缓存库我们**不要把它混在一起**。商品一个缓存库，库存一个缓存库，是两份，不是一份里塞两种数据。

> **结论**：缓存库最好在一开始就初始化好，放在那里，然后所有业务要用的时候都从里面做读和写。所以我们要把这两个缓存提前声明成 Bean，放进 Spring 的容器里去。

既然要声明 Bean，那就得写个配置类。我们新建一个类，名字叫 `CacheConfig` 之类的，加一个 `@Configuration` 注解，在里面声明 Bean。

泛型怎么定？把商品存到缓存里，一般情况下肯定是基于商品的 id 作为 key——看一眼我们的实体类，它的 id 是 `Long` 类型，所以缓存的 key 直接用 `Long`；值不用说了，肯定是 `Item` 对象。这个缓存我们起名 `itemCache`。库存那个同理，key 还是 `Long`，值是 `ItemStock`，起名 `stockCache`。

构建的过程我们之前已经演示过了：通过 Caffeine 这个类在它里面 new 一个 builder（构建器），然后 build 就构建出来了。**但在 build 的过程中，我们可以加很多很多的参数**，比如初始容量、上限这些。

```java
@Configuration
public class CacheConfig {

    @Bean
    public Cache<Long, Item> itemCache() {
        return Caffeine.newBuilder()
                .initialCapacity(100)
                .maximumSize(10_000)
                .build();
    }

    @Bean
    public Cache<Long, ItemStock> stockCache() {
        return Caffeine.newBuilder()
                .initialCapacity(100)
                .maximumSize(10_000)
                .build();
    }
}
```

`10_000` 里面那个下划线其实就是个分隔符，让你方便去读，编译出来还是一万。这个缓存我们起名叫 itemCache，另一个叫 stockCache，代表库存的缓存，这两个缓存的大小和初始化值都是一样的。

到这里两个缓存就定义好了。定义好了以后，接下来就可以实现业务了。

### 一个 get 调用顶掉一整段 if-else

我们的业务要求是什么？**是在查询的时候去添加缓存**，对不对。所以我们找到 Controller——两个查询业务不就在这吗，一个是根据 id 查商品，一个是根据 id 查库存，给它俩加上缓存就 OK 了。

先把刚才的两个缓存对象注入进来。它们的类型就是缓存类型，只不过泛型不同：key 是 `Long`，一个是 `Item`，一个是 `ItemStock`。

然后我们就可以到查询业务里去做修改了。这里其实我们之前讲过，**有一个 API 可以自动实现"优先查缓存，缓存未命中再查数据库"**。所以这里我们直接调那个 API，名字叫 `get`，作用对象是 itemCache。第一个参数就是商品的 id；**第二个参数是你的备选方案**——如果根据 id 去读缓存没读到怎么办？是不是查数据库啊，所以备选方案就是这一段业务逻辑。

```java
@GetMapping("item/{id}")
public Item queryItemById(@PathVariable Long id) {
    // 优先按 id 查缓存，未命中再按 id 查数据库
    return itemCache.get(id, key -> {
        Item item = itemService.queryById(key);
        return item;
    });
}

@GetMapping("stock/{id}")
public ItemStock queryStockById(@PathVariable Long id) {
    // 同理，库存走自己的那份缓存
    return stockCache.get(id, key -> itemService.queryStockById(key));
}
```

这里有个细节值得留意：**Lambda 表达式里的 key 其实就是我们外面传进来的那个 id**，因为 key 就是 id 嘛，第一个参数其实是一样的。只不过因为是 Lambda 表达式，我们得把参数重新命名一下，不然跟外面那个就冲突了。

拿到结果以后直接 return 就可以了，原来那段"先查缓存、再查数据库"的业务就可以删掉了。库存那边与此类似——stockCache 点 get，第一个参数是 id，未命中就把 key 作为参数传进去执行对应的查询业务。

到这里两个业务就写完了，缓存就加入进来了。

### 拿 SQL 日志证明缓存真的生效了

光写完不算数，我们得验证。重启服务，打开浏览器访问一下这两个接口，先清空日志。

第一次访问查商品的接口，商品查到了。这时候我们回到 IDEA，可以看到在这儿啊是**有一条 SQL 语句的**，查的是 `1001`。这就说明这一次它是真的走了数据库。

我们把日志清空，回浏览器再刷新一次，再回到 IDEA——有日志吗？没有吧。这就证明这次查询**没有走数据库，走的是缓存**。

库存这边一模一样：第一次查，产生了一条 SQL，证明走的数据库；清空日志，再刷新，刷新了两三次，回到 IDEA 依然没有任何日志，证明依然走的是缓存。

> **结论**：第一次查询时会走数据库，把数据放入缓存当中；以后就可以直接走缓存，而不再去查数据库了。这就证明我们的 JVM 进程缓存实现了。

### 换到 Nginx 写业务，就得多学一门语言

到这里，Tomcat 这一侧算是齐了。但整个多级缓存框架还差最后一块。

到目前为止我们已经做好的部分：Nginx 反向代理、数据库、Tomcat 服务，以及上一节课实现的 Tomcat 内部的进程缓存。接下来要做的，是 **Nginx 的业务集群，在它里面实现本地缓存**；本地缓存未命中查 Redis，Redis 未命中查 Tomcat——这样的业务。

问题就来了：**这一部分业务是在 Nginx 的业务集群里实现的，等于要通过 Nginx 来做业务编码，而不再是利用 Tomcat 做编码了。**

以前我们利用 Tomcat 做编码，用的是 Java 语言去写业务逻辑。那在 Nginx 内部，它用什么去写业务逻辑呢？它就要用到一种新的语言，那这个语言叫做 Lua。

你可以这么理解：

| Web 服务 | 写业务用的语言 |
| --- | --- |
| Tomcat | Java |
| Nginx | Lua |

Nginx 对应于 Tomcat，都属于是一个 Web 服务；Java 和 Lua 就是对应的开发语言。这么来讲，大家应该能明白 Lua 到底是什么了吧——**它就是一个开发的语言**。

把整条链路摆在一起，缺的那一环就很清楚了：

```text
        浏览器
          │  http 请求
          ▼
┌───────────────────────────────┐
│  Nginx 反向代理               │  ← 已完成
└───────────────────────────────┘
          │  代理转发
          ▼
┌───────────────────────────────┐
│  Nginx 业务集群                │  ← 本章之后用 Lua 编码
│   ① 本地缓存（Lua 实现）      │
└───────────────────────────────┘
          │  本地缓存未命中
          ▼
        Redis
          │  Redis 未命中
          ▼
┌───────────────────────────────┐
│  Tomcat 服务                   │  ← 进程缓存已完成（本节第一部分）
│   ② JVM 进程缓存（Caffeine）   │
└───────────────────────────────┘
          │  进程缓存未命中
          ▼
        MySQL
```

读图：越靠上的缓存越快、越"热"，命中就越省事；本节我们刚落地的是第 ② 级，第 ① 级要等换到 Nginx 那一侧才能写。

所以我们这一章主要就是来学习一下 Lua 的语法：先简单了解它的基本用法，然后学习一门语言的基本流程——变量、循环、条件控制、函数等等。这里我们学习的并不是完整的 Lua 语法，**只是 Lua 中最常用的、在我们后边会用到的一些知识**。

### Hello World 三十秒上手

先看这门语言本身。Lua 是一个轻量小巧的**脚本语言**。脚本语言咱们也不是第一次接触了，以前学的 JS 是吧，还有现在比较流行的 Python。什么样的语言算脚本语言？一般特点就是比较小巧、比较轻量级。

Lua 底层是用 C 语言编写的，并以**源代码形式开放**。那它设计的目的是什么呢？为了**嵌入应用程序当中**。基本上大多数用 C 语言开发的程序，只要它开放了对应的接口，都可以基于 Lua 进行一个嵌入。

> **结论**：Lua 经常被用在游戏开发当中。比如之前比较流行的魔兽世界，在它里面就可以用 Lua 去编写一些插件，实现一些拓展功能。

而我们的 Nginx 也是用 C 语言编写的，它也开放了一些接口，因此它就允许你基于 Lua 进行一些拓展，那你就能够去实现一些业务功能了。这就是我们今天要换到 Nginx 上面写业务的技术前提。

Lua 有自己的官方网站，上面有 Documentation（文档）。当然如果你是第一次使用 Lua，还是需要去做一些安装的，它需要有一个运行环境，官网的 Get Started 会教你怎样去安装。Mac 就按照上面那种方式；如果是 Linux 系统，可以用源码安装，下载、解压，然后编译安装就可以了还是比较简单的。

那我们需不需要去安装呢？**不需要。**因为在我们的 CentOS 系统里面已经自带了 Lua 了，所以可以直接去用。

那怎么去使用 Lua 做开发呢？我们在 Linux 虚拟机里面任意目录下先新建一个文件 `hello.lua`——这就像咱们写 Java 文件一样嘛。然后往里面加一行内容：

```lua
print("Hello World")
```

这不就是一个典型的 Hello World 快速入门嘛。以前我们 Java 里面写的是 `System.out.println`，而这里是直接 `print`，**说明 Lua 的语言更加简单**。这里边是一个字符串 `"Hello World"`，它的字符串可以用双引号，也可以用单引号，这一点跟我们的 JS 里面非常像。

写完保存，怎么去运行呢？它不需要编译，可以直接运行，通过 `lua hello.lua` 就能直接运行这个 Lua 文件了。

我们在控制台里 `vi hello.lua`，用 print 打印，单引号也行双引号也行：

```lua
print('Hello World')
```

注意啊，**这里不需要加分号**。保存，然后用 `lua hello.lua` 去运行，控制台就成功打印出了 Hello World。

另外还有一种方式：直接输入 `lua` 就能进入 Lua 的交互控制台，在那儿你可以随时输入、编写你想运行的一些命令，不用每次都去改文件、保存、运行。这一招在做语法试验的时候特别好用。

### Lua 的数据类型：nil 也是假，table 既表又数组

聊到变量，一定离不开数据类型。Lua 提供的类型其实非常丰富，我们一个个看。

**nil**，跟 Java 中的 null 有一点相似，因为它们代表的都是无效，也就等于没有。但区别在于——**nil 在 Lua 语言当中，它还可以代表 false**，也就是说直接 `if nil`，它就代表一个假。

**boolean**，布尔类型，可以是 true 也可以是 false，这个跟 Java 很像。

**number**，数值类型。它其实并没有详细区分整数啊、小数啊，**统一都用 number 来表示**，整数也好，小数也好，都叫 number。

**string**，字符串，可以用双引号，也可以用单引号，这个之前是不是提到过了。

**function**，函数，用 C 和 Lua 编写的函数。这里有个有意思的点：C 和 Lua 之间其实是可以相互去做一些引用的，也就意味着在 Lua 语言当中，**函数本身也是一种类型**。那是不是也可以声明一个函数类型的变量？接下来是不是可以把这个变量去传递呀？这一点跟我们 Java 有比较大的一个差异，跟 JS 很像。

**table**，这个 table 在它这里的描述是叫"数组"，但我觉得把它理解成咱们 Java 中的 map 可能更接近一点。因为 Java 中的 map 是 key-value 结构，table 同样是 key-value 结构。

那它既可以表示 map，也可以表示数组，为什么呢？因为当你表示数组的时候，那 key 无非就是数字嘛，1、2、3、4 这样。当你的 key 是字符串的时候，那它不就变成了一个 map 了吗？所以这就是 Lua 中比较特殊的一个 table 类型。

### type()：让运行时自己报出类型

那我们怎么去判断一个变量它到底是什么类型呢？这里有一个函数叫做 `type`，作用就是来判断一个变量的数据类型。

我们来看这个例子。`print` 我们见过了，打印的内容之前是 Hello World 这个字符串；但这次打印的是 `type('hello')`。其实意思就是——我打印的是 `type` 这个函数的运行结果。我们知道 `type` 是用来测这个变量的数据类型的，测的是 Hello World 这个字符串的类型，那因此 `type` 的结果是不是一定是字符串啊？哎，就是 `string`。

同理，`type(1)` 的结果一定是 `number`，所以打印的时候咱看到的就是 `number`。所以它其实是打印 `type` 这个函数的结果。

我们打开控制台来演示一下，直接进 `lua` 控制台，不用改文件：

```lua
print(type('hello'))   --> string
print(type(1))         --> number
print(type(true))      --> boolean
```

那如果我想知道布尔类型的类型呢？比如 `true` 的类型，你看是不是 boolean？

那我问一下大家：**如果我这么写呢？**

```lua
print(type(print))
```

好像有点套娃的感觉。大家猜测一下返回值应该是什么？应该是 `function`。因为你打印的是什么？打印的是 print 的类型，print 是函数嘛，所以这个函数类型。

这就是我们这个 `type` 函数的一个作用了。

### 声明与取值：local、数组与 map

那么我们怎么去声明一个具体类型的变量呢？通过这个大家能够看出来一点——**在声明变量的时候，并不需要指定数据的类型**，但是 Java 里面是需要指定的对吧，那这里就没有。声明方式是直接 `local` 后面跟变量名，再跟变量的值。`local` 代表的就是一个局部变量的意思。

```lua
local str = 'hello'
local age = 21
local flag = true
local nothing = nil

local arr = {"hello", "world", "java"}
local map = {name='jack', age=21}
```

字符串可以用双引号，数值直接给数，布尔比较特殊。这里比较特殊的是这两个：

`arr` 其实是一个数组。大家看这个数字的描述方式，一个大括号里面一个元素、两个元素、三个元素就行了。

而 `map` 呢，它的写法是 `name` 等于 `jack`，`age` 等于 `21`，是不是典型的 key-value 结构？跟我们 Java 中的 map有点像，**但是他声明的时候不用 new，直接大括号就行了**，所以它比较方便。

但我们讲，Lua 中其实**没有 map 和数组这两种类型**，它其实都是叫 table。只不过区别在于——`map` 其实只不过是 key 是一个字符串的 table，只不过这个字符串我们不用加引号，直接写就行了；而对于 `arr` 来讲，它其实就是一个 key 为索引 1、2、3、4 的 table。所以这两个其实都是 table。

> **提示**：Java 的集合是分家子的——`List` 是 `List`，`Map` 是 `Map`；Lua 把它们抹平成了一个 `table`。后面判断一个值能不能用某种写法访问时，先想它底层是不是 table。

字符串还有个小操作：在 Lua 中字符串拼接是用**两个点**来拼接的。

```lua
local str1 = 'hello' .. 'world'
print(str1)   --> helloworld
```

这里有两个字符串拼接的坑容易踩。第一个是：`local` 声明的变量，作用域仅限当前代码块内，**如果只在声明语句后写一行结束，后面就没办法再访问了**。第二个是，如果想让变量成为全局的，**直接不写 `local`**，比如演示全局数组时：

```lua
arr = {"hello", "world", "java"}
```

说明这是全局的，全局变量在后续代码块中依然可以访问。

那我们怎么样去访问一个 table 中的元素呢？

对于数组来讲，**直接跟上角标就行了**，就是 `arr` 中括号里面跟角标。但是区别在于——**这个角标是从一开始的**。比如我访问 `hello` 我就写 `arr[1]`，而不是 `arr[0]`，它是没有零的。

> **易错点**：Lua 数组下标从 1 开始，没有 0。这一点切记，别写错了。如果你取 `arr[0]`，求出来的就是 nil——因为 nil 代表的是无效，也就是没有。

而如果说你要访问的是这种 key 是字符串的 map，那么有两种访问方式。第一种就是跟上面数组类似，中括号里面跟上 key 的名称，而这个 key 是 `name`，你就写中括号 `name`；还有一种做法呢，是类似于咱们 Java 中面向对象的那种玩法，什么什么点——就是 `map.name` 就能取到这个 name，`map.age` 就能取到这个年龄。

我们在控制台里来实际走一遍：声明一个字符串 `str = 'hello'`，再拼一个 `str1 = 'hello' .. 'world'`，打印出来就是拼在一起的效果。然后声明数组 `arr = {"hello","world","java"}`，取 `arr[0]` 就出问题了——求出来是 nil，代表无效；取 `arr[1]` 就没问题，取到的是 hello。再声明一个 table，`map = {name='jack', age=21}`，我可以通过 `map['name']` 去取，也可以通过 `map.name` 去取，两个都可以。

到这里，Lua 的变量声明就演示好了。

### 遍历：ipairs 管数组，pairs 管 table

但是像这样取 map，其实是一个一个取，对不对？那我们肯定会有一些需求，是要去循环地取 map 或者数组，这这时候该怎么办呢？

如果你的变量是一个数组，你想去循环去取的话，就可以用到一个 for 循环了。

```lua
for index, value in ipairs(arr) do
    print(index, value)
end
```

for 循环比较特殊，它是一个叫 for 什么什么 in 什么什么，然后来了个 `do`。**注意这里不是大括号，是 `do` 和 `end`**，`do` 代表这个 for 循环的开始，`end` 代表 for 循环的结束。

那这里的 `ipairs` 表达式代表什么呢？就是说 `ipairs(arr)` 就是指我要解析这个数组。

为什么叫 pair 呢？因为解析的时候形成的是**一对**什么东西呢？就是键值对。第一个就是 key，也就是所谓的键；第二个就是 value 值。只不过区别在于，它是个数组，数组的键其实就是索引，所以这里我用了一个 `index` 来表示。`index` 就是角标，`value` 就是对应的值。这两个其实是变量名，你可以随便写。所以 `pair` 其实就把数组变成这种键值对解析出来了。

那同样呢，如果是 table，也是类似：

```lua
for key, value in pairs(map) do
    print(key, value)
end
```

一样从 `pairs(map)` 里面把键值对解析出来。但是你看这边用的是 `pairs`，上面用的是 `ipairs`，**因为你上面是个数组，下边是一个 table，这俩还是有点差别的，所以用了不同的函数**。一个是 ipairs，一个是 pairs。

> **提示**：这个 for 语法有点像 Vue 里边那个什么什么 in 什么什么啊这种语法，看过 Vue 的话应该会很熟悉。

我们打开控制台来演示一下，因为遍历相对复杂一点，我们在文件里写：

```lua
local arr = {"java", "lua", "python"}
local map = {name='jack', age=21}

for index, value in ipairs(arr) do
    print(index, value)
end

for key, value in pairs(map) do
    print(key, value)
end
```

**注意这个打印函数是可以用逗号隔开多个值的**，它会把这俩一起打印。

保存运行，大家可以看到打印出来的是 `1 java`、`2 lua`、`3 python`，下边是 `name jack`、`age 21`。你看数组它的 key 是不是 1、2、3 啊？这样 table 的遍历我们也就学完了。

简单回顾一下这一节：数据类型有字符串、数值、布尔、nil，还有 table；声明方式就是用 `local` 代表局部变量，然后变量名再跟上变量值就 OK 了；数组和 map 的访问方式可以用角标访问，table 的话也可以用 key 来访问，都可以。而循环呢，是用一个 for 循环要结合两个函数——一个叫 ipairs，一个叫 pairs，来对 map 或者数组做一个解析，然后再去遍历里面的 key、value。

### 把打印数组这件重复事收进函数

接下来继续学习 Lua 的语法，这一节我们学习函数和条件控制。

先说函数。**函数的作用是非常重要的**，因为它可以把一些代码进行一个封装，简化我们的开发，避免重复代码。

在这里呢，函数的语法是 `function` 来去声明的，这一点跟 JS 很像。`function` 后边跟上函数的名称，然后再跟上参数的列表。同样啊，在我们的 Lua 中是没有大括号的，所以它的参数列表后边直接就可以去编写函数体了。在函数体写完了以后，也可以用 `return` 返回，也可以不返回，最后由 `end` 代表函数的结束。

下边给大家举了个例子：这里就把打印数组的这个语法给封装成了一个函数。因为打印数组挺麻烦的嘛，所以在这呢你看它又来了个 `printArr` 的函数，而这个函数呢，它接收一个数组，然后通过 for 循环遍历、通过 ipairs，在 for 循环遍历的过程中把结果给它打印出来了。

那我们是不是也可以参考这个来封装一个函数呢？我们打开控制台编辑这个文件，可以在这里封装一个函数来打印数组：

```lua
local function printArr(arr)
    for key, value in ipairs(arr) do
        print(value)
    end
end

local arr = {"java", "lua", "python"}
local arr2 = {100, 200, 300}

printArr(arr)
printArr(arr2)
```

我们通过 `local function` 起名字，叫做 printArr，代表打印数组，我接收一个数组，然后接着就可以去编写函数体，函数结束写 `end` 就可以了。

那么在这里边呢，我们就可以去写这个 for 循环了——接受一个 key，再接受一个 value，然后 `in ipairs`，把 arr 拿过来，然后 `do`，然后呢里面有 print，我们就打印 value 就可以了，然后 `end`。这样呢我们的一个函数就声明好了，这行的作用就是专门打印数组。

这样以后如果你还要打印数组的时候，你就没有必要自己再去写了吧？也就是说上面这个 for 循环其实就没有必要了，我们就可以把它给删掉了。现在我要打印这个 arr，我就可以直接写 `printArr(arr)` 把它传进去，他就能帮我打印了；再来一个数组 `arr2 = {100, 200, 300}`，直接 `printArr(arr2)`。你看这样我们在打印的时候就非常方便，就不用自己去写这一堆了。

这就是封装和抽取的一个作用，代码可复用。保存运行，大家可以看到 `java lua python`、`1 2 3`，是不是都成功循环输出了？

### 健壮性来自条件控制，而逻辑词不是符号

但是呢，我们封装函数，在函数内部的业务还要考虑一些健壮性，对不对？

人家给你传了一个数组，你去遍历打印，那万一人家传的是一个 nil 呢？是不是有可能会出现类似于空指针之类的这种情况？怎么办呢？所以我们往往还需要做一些逻辑判断，也就是**条件控制**嘛。

在 Lua 中，条件控制跟 Java 也是比较相似的，同样是 `if else`。只不过这里没有大括号，同样是 `end`——`if` 代表大括号开始，`end` 代表大括号的结束。然后它其实也会有 `if elseif elseif` 这样的语句，只不过我们在这里并没有给大家示例，其实这里只要写成 elseif 就可以了，也是可以去进行多个逻辑条件的判断的。

这里与 Java 中啊，还有一个非常大的区别在于**这个布尔表达式**。我们知道布尔表达式里边往往是来做逻辑运算、布尔运算的，比如说大于、小于、大于等于、小于等于这些判断，这块判断跟 Java 中没什么太大差别。

但是呢，当你做一些逻辑运算——与、或、非的时候，就有差别了。因为在我们的 Lua 中，与或非**不是用符号，而是用英文单词**：`and` 代表与，`or` 代表或，`not` 代表非。

比如说两个条件 a 和 b，那么 `a and b` 那就是与，`a or b` 就是或，那如果是 `not` 就是非。所以如果有一个条件为 a，那么 `not a` 那也就是非 a 的意思啊。

> **提示**：这里有一个点需要特别注意——我们知道 nil 代表的是 false，那么 `not nil` 代表的是什么？哎没错，代表就是 true。

那明白了这个条件控制以后，我们通过一个案例来演示一下：让我们自定义一个函数可以打印 table，那么当参数为 nil 时，打印错误信息。也就是说，这里等于是你这个函数还有一个什么功能？是不是带一个条件控制功能——如果人家传的是 nil 了，你报错"传的不是那样"；人家在正常打印，是吧？

好那我们来做一个测试。我们其实已经定义好了一个打印数组的函数了，那在这里呢，我们就对这个打印数组的函数做一个修改吧，加入一个新的业务逻辑——做什么业务逻辑呢？做个条件控制，`if` 里面写条件语句，就判这个 `arr` 是否为 nil。

那我们知道 nil 代表是 false，如果这么写是不是就"如果它是 false 的话"？这是不是就不成立了？对不对。所以我在这里要**取反** `not nil`，是不是叫 `not nil` 啊？我们知道 nil 我们知道代表是 false，那 `not nil` 就是取反，代表的就是 true 了。

那也就是说如果你给我传了一个 nil，那到这里呢，nil 代表 false，取反代表 true，是不是就可以进入到我这个 if 业务逻辑当中了？那我发现你给我传的是个 nil 了，进到我业务逻辑了，我要干什么？我是不是得给你打印错误信息啊。按照我们的需求，所以在这我就给你 print，比如说"数组不能为空"啊，然后提示一下你对吧。然后呢我再给你 return，return 就结束了嘛，内容结束，我就不再往下走了，然后 `end` 我这个 if 逻辑就结束了。

```lua
local function printArr(arr)
    if not arr then
        print('数组不能为空')
        return
    end

    for key, value in ipairs(arr) do
        print(value)
    end
end

local arr = {"java", "lua", "python"}
local arr2 = {100, 200, 300}

printArr(arr)
printArr(arr2)
printArr(nil)
```

这样呢，一旦你传的内容进入这个 if 当中，自然就会报错了；那如果你传的是数组，我再往下去做打印。

大家看，前边这两个数组就正常打印了，打印到第三个时就说了"数组不能为空"，好，证明我们的条件控制生效了。

> **结论**：这一节主要就是学习了两个点。第一个点是如何去自定义一个函数语法，就是 `function` 跟函数名和参数列表、那里边写函数体；第二个呢是做条件控制，`if` 加布尔表达式。这个表达式里比较特殊的在于这个与或非，特别是这个非要是用 `not`——所以如果一个值是 false，那么 `not false` 就代表 true 了。

当然，这些业务逻辑的编写，还要依赖于一些其他的组件，这些组件呢我们会用到一个名为 OpenResty 的工具来帮我们实现。所以我们这一章，其实就是利用 OpenResty 来完成这个多级缓存业务的编写。这一部分的东西会比较多一点，我们要先安装这个 OpenResty，然后带大家去简单地应用一下它；接下来就是利用它去实现请求参数的获取、Tomcat 查询、Redis 的这种查询、Nginx 本地缓存等等这一系列的功能。

## 在 OpenResty 上写业务：从假数据到 Tomcat 集群负载均衡
> 对应块：BLK36 | 覆盖分集：P122-P126 | 块标题（分集名）：《高级篇-多级缓存-10-多级缓存-OpenRes》

### 一个还在报错的商品详情页

先打开浏览器看商品详情页 `item.html`。这页面上确实发起了请求——请求的是 `/api/item/1001`，这就是商品的 id——只不过这个请求报错了，所以页面现在渲染的是一份假数据。

将来我们要干的事就一件：接下这个请求，把真实数据返回好。

那这个请求现在是谁接住的？你看它打到的是 `localhost`，本机的 Nginx。上节课我们在当前这台 Windows 电脑上准备好了一个 Nginx 服务，`/api/` 下的 `item.html` 这些页面都在里面。但是 Nginx 本身没有业务能力，它只会转发；而上节课我们装的 OpenResty 才有。所以这个请求应该交给 OpenResty 去处理。

我们上节课已经配置过了：

```nginx
upstream openresty_cluster {
    server 192.168.150.101:8081;
}

server {
    listen 80;
    location /api/item {
        proxy_pass http://openresty_cluster;
    }
}
```

`location /api/item` 一命中，这个地址就被拦截到了，接着反向代理到了 OpenResty 集群。集群在哪？`192.168.150.101:8081`——这个地址就是我们的虚拟机，端口 8081 也正是我们刚才部署 OpenResty 的地址。所以准确来讲，这里配的就是 OpenResty 业务集群的地址，将来它可以形成一个集群，查 Redis、查缓存这些业务都写在里面。

```text
        浏览器（Windows）
   localhost/item.html  ──▶ 发起 /api/item/1001
          │
          ▼
   ┌───────────────────────────────┐
   │  本机 Nginx（Windows:80）      │  只做转发，没有业务
   └───────────────────────────────┘
          │  location /api/item
          │  proxy_pass → openresty_cluster
          ▼
   ┌─────────────────────────────────────────┐
   │  OpenResty 业务集群                      │
   │  虚拟机 192.168.150.101:8081            │
   │    Nginx 内核 → lua/item.lua             │
   │  将来：查 Redis、查本地缓存、查 Tomcat    │
   └─────────────────────────────────────────┘
```

图要这么读：页面请求先落在本机 Nginx，由它按 `location` 转发给 OpenResty 业务集群；真正写业务的地方是集群里的 Lua 文件。

那 OpenResty 该怎么接这个请求？这节课我们用一个快速入门把它走通，案例就是商品详情页的查询。

### 让 OpenResty 接下这个请求

接请求我们都熟，无非就是写个 `location`，路径只要跟页面请求路径一致就行了。但接完请求之后要写业务逻辑，那就不一样了——以前接收到请求是交给反向代理去处理，这里我们要交给一个 Lua 文件去处理。

```text
   浏览器请求 /api/item/1001
              │
              ▼
   ┌──────────────────────────┐
   │   location /api/item     │  ◀── 相当于 Controller：拦下这个路径
   └──────────────────────────┘
              │  content_by_lua_file
              ▼
   ┌──────────────────────────┐
   │   /lua/item.lua          │  ◀── 相当于 Service：写业务逻辑
   │   ngx.say(...)           │
   └──────────────────────────┘
              │  JSON
              ▼
          浏览器拿到数据
```

这张图就是整个多级缓存里 OpenResty 部分的样子：一个 `location` 负责拦路径，一个 Lua 文件负责干活，最后把结果吐回去。

#### 先加载工具模块

真正写业务之前，前面还得有这么一段，它放在 `nginx.conf` 的 `http` 下边：

```nginx
http {
    lua_package_path /usr/local/openresty/lualib/?.lua;;
    lua_package_cpath /usr/local/openresty/lualib/?.so;;
}
```

这两行是干什么的？是在加载 OpenResty 的工具模块。我们知道 OpenResty 对 Nginx 做了扩展，加了很多工具模块，这些模块你必须先把它加载进来才能用——你要访问 Redis、访问 MySQL、访问 Tomcat，都得用到这些东西。

怎么加载的呢？其实就是指定了两个 `path`。`path` 就是路径嘛，一个 `path` 对应 Lua 的函数模块，一个对应 C 的函数模块；路径值就是我们之前 OpenResty 的安装目录 `/usr/local/openresty/`，以 `.lua` 结尾的是 Lua 模块，以 `.so` 结尾的是 C 模块。所以这两行是固定写法。

这两行大家肯定记不住，手写是不可能的。好在安装 OpenResty 的文档最下边已经给大家准备好了，直接 `Ctrl+C` 拷一份，粘贴到刚才那个编辑器里就完事了。这两个模块就加载好了。

#### 用 location 把请求交给 Lua 文件

接下来还要去监听浏览器的那个请求，地址就是 `location /api/item`。监听到这个请求以后要做两件事：第一个，声明 `default_type`，我的默认响应类型是 `application/json`；第二个，声明我的响应结果由谁决定——由哪个 Lua 文件决定。

```nginx
server {
    listen 8081;
    server_name localhost;

    location /api/item {
        default_type application/json;
        content_by_lua_file /lua/item.lua;
    }
}
```

`content_by_lua_file` 的意思就是：我的内容是由一个 Lua 文件来决定的。哪个文件？`/lua/item.lua`。这个文件的执行结果就是我的响应结果。

那这个文件最后返回的是什么类型？上面已经用 `default_type` 声明成 `application/json` 了，意思是将来我的文件里返回一个 JSON，页面拿到了就 OK。

在这个 Lua 文件里我们就能写业务了——利用 Lua 的语法，利用 OpenResty 提供的工具，实现查 Redis、查缓存等等各种各样的业务。这不就实现业务逻辑的编写了吗？就有点像我们的 Controller 拦到路径了，然后在这写业务，那这就相当于是 Service 了嘛。

#### 第一个 Lua 文件：先把假数据返回出去

关键是这个文件现在还没有，得先建。Lua 文件到哪儿去找？它会去你的 Nginx 所在的目录去找。所以要在 Nginx 目录里新建一个 `lua` 目录，然后 `touch lua/item.lua`，刷新一下就能看到 `lua` 目录里有个 `item.lua` 文件了。

现在把它打开，业务怎么写？这节课我们先不着急写业务，就实现一个最简单的：OpenResty 接收到请求以后，直接返回一段假数据就行了。返回假数据我不会返回呀，怎么返回呢？就这么写：

```lua
ngx.say('{"id":1001,"title":"26寸曲面屏","price":199}')
```

就一行。`ngx.say` 里边传的是个字符串，Lua 的字符串，里面是一个 JSON 风格的。那这里的 `ngx.say` 是什么东西呢？它就相当于是我们 Java 里面那个 `response.print`，利用我们的 response 把结果写到浏览器。这里边你就传你想返回的结果就行了。这是不是很简单。

那这个假数据从何而来？打开浏览器，从 `item.html` 的 Vue 里 `root` 那儿能看到一份商品的假数据，我把它 `Ctrl+C` 拷一份过来就行。

> **易错点**：这里必须用**单引号**包字符串，不然会跟 JSON 里的双引号产生冲突。

拷过来之后我们可以随便改点东西，让它跟页面产生一些差异，比如尺寸我从 21 寸改成 26 寸，价格从 179 改成 199，这样我跟页面就有差异了。

好了，现在 OpenResty 已经可以监听这个请求了，业务也写完了——你一来我就给你返回好。跑之前别忘了重新加载：`nginx -s reload`。

打开浏览器，Network 清理一下，刷新页面。你看结果已经出来了，标题变成了 26 寸，价格也变成 199，跟我们预期的一样；再看页面的请求，状态码变成了 200，证明查询成功了，是由我们的 OpenResty 返回的数据，完整的 JSON 数据都来了。

这样，OpenResty 的快速入门就实现了。

> **结论**：回顾一下这个套路——编写一个 `server` 监听端口，然后写一个 `location` 监听路径。以前匹配到路径以后去做反向代理，这里匹配到以后是交给 Lua 文件去处理，然后 Lua 文件里再写自己的业务逻辑。所以理解的时候，你可以就把这一段路径理解成我们的 Controller，拦到以后交给一个 Service 去处理，而那个 Lua 文件就可以理解成是一个 Service，这就比较好理解了。

> **提示**：别忘了那两行加载 Lua 模块和 C 模块的配置。

### 拿到请求参数：五种参数怎么取

刚才我们返回的是假数据，id 是写死的 1001。但将来我们肯定不能返回假数据，一定会根据请求不同去查询不同的商品数据。这就有一个问题了：你必须得想办法拿到不同请求的参数。

这里我把 OpenResty 里各种不同类型的请求参数以及对应的获取 API 整理成了一个表格，可以看到请求参数分成了五种：路径占位符，也就是在路径里拼了一个参数；第二类是从请求头里获取参数；第三类是 GET 请求参数，也就是拼在这个路径上问号什么什么的那种；第四类是 POST 这种 form 表单的参数；最后一类就是 JSON 的参数。

#### 路径占位符：唯一需要正则的那个

路径占位符是最复杂的，因为它不是常规参数，它需要利用正则表达式。

我们现在的业务是 `/api/item/1001`，你敢说这是路径占位符吧？所以等一会儿就用路径占位符这种方式来获取。

看这个正则：`/api/item/(\d+)`。写路径匹配的时候大家注意看，以前是 `location` 直接 `/` 什么什么，那在这儿呢多了一个**波浪线**。这个波浪线代表的就是说：后边跟的是正则表达式匹配。前面这一段是精确匹配的 `/api/item`，因为这部分我们不关心嘛，而后边才是真正的正则表达式。

注意看这个括号，括号呢是对正则表达式做一个分组，这是第一组。这一组它的语法是 `\d`，`\` 就是转义字符，`d` 代表所有的数字。因为我们的 id 是 long 型，所以用 `\d` 代表一切数字。`+` 代表至少一个字符，但因为你是数值，你至少得有一个字符嘛，所以用加号；那也可以有多个，比如 1001 有 4 位，你就能被我这个 `\d` 给匹配到了。

匹配到了以后，下边就交给这个 Lua 文件去处理了。但是这个匹配到的这段表达式的值放到哪里去了呢？凡是被路径匹配到的参数，都会存在一个名为 `ngx.var` 的数组当中。那如果你的路径中有多个正则表达式，将来就会匹配到多个值，数组中也会有多个；如果你有一个，这里就一个。我们知道取数组中的元素是用角标来取的嘛，从一开始，所以我想取这个表达式的值，是不是 `ngx.var[1]` 就可以了？

所以 location 要改成这样：

```nginx
location ~ /api/item/(\d+) {
    default_type application/json;
    content_by_lua_file /lua/item.lua;
}
```

> **易错点**：波浪线两边都要留空格，`~ /api/item/(\d+)`，别写成 `~/api/item`。

回到 `item.lua`，先获取路径参数：

```lua
local id = ngx.var[1]
```

然后把这个 id 拼接进返回结果。现在 id 是写死的，我们把它干掉，这里要做拼接。Lua 里拼接是用两个点来拼接的，把前面这段字符串拼起来再来两个点，中间带上 id，再来两个点拼后边的字符串，这样就拼接完成了。

```lua
ngx.say('{"id":' .. id .. ',"title":"26寸曲面屏","price":199}')
```

保存、`nginx -s reload`、回浏览器刷新。好像没什么变化？我们把地址改成 1002 诶——打开这个请求看返回值，里面 id 也是 1002 吧？再来 1003，结果是不是变成了 003 了？那证明我们确实是拿到了请求 id，并且拼接进结果中了，结果就不再是死的而是动态的了。

#### 其余四种：一个比一个省事

| 参数类型 | 获取方式 | 返回值 |
| --- | --- | --- |
| 路径占位符 | `ngx.var[1]` | 匹配到的字符串 |
| 请求头 | `ngx.req.get_headers()` | table |
| GET 请求参数（`?a=1`） | `ngx.req.get_uri_args()` | table |
| POST 表单参数 | `ngx.req.read_body()` + `ngx.req.get_post_args()` | table |
| JSON 请求体 | `ngx.req.read_body()` + `ngx.req.get_body_data()` | 原始 JSON 字符串 |

请求头就简单很多了，不需要正则表达式了。`ngx.req` 里的 `req` 就是 `request` 的缩写，代表请求。`get_headers` 获取请求头，那它的返回值是一个 table。为什么呢？因为请求头它有多个，是 key-value 结构，那 key 和结果是用 table 来封装，非常完美。

如果是 GET 请求，并且用问号拼接这种参数，那就很简单，用 `ngx.req.get_uri_args()`，`args` 不就是参数的意思吗，它就能获取了，返回也是一个 table，key-value 的格式。

如果是 POST 表单呢，这里改成 `ngx.req.get_post_args()`，这一系列的大家看是不是就非常接近了。那区别在于，POST 请求在前边要多做一个事情，就是要 `read_body`，先让我们的 OpenResty 帮你去读取请求体，做一个解析，解析完了才能去获取里面的参数。

那最后一种 JSON 风格的参数呢？同样是先读 body、再取参数，这里不再是 `get_post_args` 了，而是 `get_body_data`。因为你是一个 JSON，所以 `get_body_data` 的返回值直接就是 JSON 字符串类型。

我们这个业务是路径占位符，就用它。感兴趣的也可以参考这个表格里的 API 介绍，去尝试一下其他四种。

### 有 id 了，下一步才是查数据

先回头看一眼多级缓存的整体架构。目前 Nginx 反向代理服务器已经准备好了，在这儿去接收前端的请求，然后转到 OpenResty；服务端也准备好了，并且编写了进程缓存；OpenResty 也搭好了。

那 OpenResty 接收到这个请求以后要查数据，从哪儿查？按照我们的逻辑肯定是先查缓存，缓存没有了再查 Tomcat。但是——我们的缓存数据又从何而来？你是不是得查了 Tomcat 以后，把它给的数据存到缓存里去。

所以现在先不着急实现缓存，本地缓存和 Redis 都不做，我们先实现对 Tomcat 的查询，将来再把查到的数据放到缓存里去。

```text
       浏览器
          │
          ▼
       Nginx
          │
          ▼
      OpenResty  ──┬──▶  ① 查 Redis        ← 这节课先不做
                    │
                    └──▶  ② 查 Tomcat      ← 这节课先做这个
                              │
                              └──▶  查出来的数据，再回填进 Redis
```

这张图是多级缓存里数据流的顺序问题：读的时候按 ①② 顺序走，写的时候反过来——数据必须先从 Tomcat 查出来，才有东西可以回填给 Redis。所以第一步只能是 Tomcat。

这里有一个需要特别注意的地方：OpenResty 所在的服务器是我们的虚拟机，而我们的 Tomcat 是在 Windows 上，他俩的 IP 地址是不一样的。我们的虚拟机地址是 `192.168.150.101`，Windows 电脑是另外一个地址，所以你将来在发请求的时候，一定要找到正确的地址。

这里有一个比较便捷的方式，适用于所有人的虚拟机，大家记住了：**不管你的虚拟地址是什么，你只要管它的前三位就行了，然后把最后一位替换成一，一定得到的就是你的 Windows 电脑地址**。`192.168.150.101` 对应的就是 `192.168.150.1`。

> **注意**：当然前提是你的防火墙得关闭，不然你一定访问不到你的 Windows 电脑。

#### capture 发出去的请求，发到了哪儿

我们这个案例的需求有四个：第一个是获取请求参数中的 id，也就是商品 id，这件事咱们已经做过了；那么第二和第三呢，是根据 id 向 Tomcat 发请求，查商品和库存。

为什么这里要分成两个查询呢？大家还记不记得我们数据库里的表是分成了两张表，一个商品表，还有一个库存表。而且打开 IDEA，事实上在我们的 Controller 里边有一个是查商品的业务，还有一个是不是查库存的业务。当然了，这两个请求它们的路径前缀是一样的，都是 `item`。

所以等一会儿要发两次请求、查两份数据。但是这两个数据查完以后，最终页面需要的是什么数据呢？我们打开浏览器看一下，页面需要的数据不仅仅包含商品的基本信息，还包含了商品的库存，还有销量——那些都是库存表中的数据。也就是说最终我们还是要把两张表的数据整合在一起返回。

回到 PPT，这个需求又多了一步：还要把结果组装封装为 JSON 返回。所以需求可以分成两步来做，第一步是查询，第二步是数据的封装。

那查询应该怎么做？这里有一个 API，名字叫 `ngx.location.capture`。

```lua
ngx.location.capture(uri, options)
```

`capture` 就是捕获的意思，捕获一个请求。这里有两个参数：第一个参数是请求的路径，也就是你向哪里发请求；第二个参数是一个 table，这个 table 里有多个信息，包括第一，请求的方式，这里是 GET；第二，请求的参数，`args` 它适合于 GET 请求来传递；再往下一个叫 `body`，它是 POST 请求传递的。这两个你不要都传——如果你是 GET 就选第一种，如果是 POST 就选第二种。

返回值是一个叫 `response` 的对象，里面包含三个属性：`status` 显示状态码，一个叫 `header` 响应头，还有一个是 `body` 响应体。那显然我们关心的仅仅就是响应体。

我们向 Tomcat 开始发请求，TomCat 开始返回的数据是什么结果呀？是不是商品的一个 JSON 结构啊，所以得到的应该是一个 JSON 的字符串。大家注意，`response.body` 是 JSON 的字符串。

但是不知道大家有没有注意到一点：**我们发请求的地址应该是有 IP、有端口，再加上请求的路径**，但是你看这个示例里边只有路径，没有 IP 也没有端口。那问题来了，你这个请求发到哪里去了？

这里非常关键。这个请求不包含 IP 和端口，所以这个请求没有发到任何一个地方，而是被 Nginx 自己监听到了。

> **易错点**：`ngx.location.capture` 发出的请求不带 IP 和端口，默认会被 OpenResty 自己接住，发不出去。

这不行啊，因为我们最终的目的是发给 Tomcat。这个请求最终一定要发现 Tomcat 所在的 IP 和端口。那怎么办？现在被 Nginx 自己拿到了怎么办？那大家不要忘了，我们 Nginx 是不是有反向代理的功能？既然这个请求被自己拦截到了，那我再把这个请求反向代理到 Tomcat 的 IP 地址和端口上，是不是就 OK 了？

#### 用反向代理把它送到 Tomcat

说那怎么代理？太简单了，这么写就可以：

```nginx
location /item {
    proxy_pass http://192.168.150.1:8081;
}
```

这个写法大家应该都认识。那为什么监听 `/item` 这个路径？因为你既然是向这个路径发请求，你的请求是不是就被我监听到了，然后我反向代理到这样一个 IP 和端口。

大家注意，这个 IP 可不是虚拟机 IP，最后一段是 1，这是我们 Windows 的 IP；`8081` 是我们 Tomcat 服务的端口。这样一来，等于这个请求就发到我们的 IDEA 里 Tomcat 服务去了，就能够接收到你这个请求了。当然这里有一个注意事项：防火墙一定要关闭。

那到底监听什么路径呢？我们打开 IDEA，在 Tomcat 里我们接受请求是不是以 `item` 开头的？不管是查最终的商品还是查库存，都是 `item` 开头。所以我们在这个地方监听的也应该是以 `item` 开头吧。

于是 `nginx.conf` 里就多加一个 `location`，凡是 `/item` 请求一定会到达我们的 Tomcat。

好了，反向代理搞定了。那以后咱们只要调这个 capture API，请求是 `item` 开头，是不是一定能到达 Tomcat？所以以后咱们可以放心地使用这套 API 了。

#### 把这段请求封装成通用工具

这套 API 我们既然经常要使用，咱们可不可以把这个发请求的代码封装成一个函数呢？最起码咱们要用两次吧——刚才讲了，查商品要用一次，查库存要用一次。那这也是值得封装成一个函数。

那放哪里去呢？大家看，`/usr/local/openresty/lualib` 这个目录不知道大家还有没有印象。打开编辑器，还记得吗？这个不就是我们之前配置的加载 Lua 模块的那个配置嘛——你看这个地址 `/usr/local/openresty/lualib/?.lua`，是不是指这个目录下的一切、后缀名为 `.lua` 的文件都会被加载。

那同学们想想看，我们在这个目录里定义一个 `.lua` 文件，是不是也一定会被加载？我们在这个文件里定义的函数，是不是也一定能够被加载？这不就可以变成通用的工具了吗？所以这里叫 `common.lua`。

这个 `common.lua` 里写了什么呢？

```lua
-- common.lua
local function readHttp(path, params)
    local resp = ngx.location.capture(path, {
        method = ngx.HTTP_GET,
        args   = params
    })

    if not resp then
        ngx.log(ngx.ERR, "http not found, path: ", path, ", params: ", params)
        ngx.exit(500)
    end

    return resp.body
end

local m = {}

m.readHttp = readHttp

return m
```

我一段段说。

因为是封装函数，我们刚才发请求的时候要指定一个路径、要指定一个参数，这两部分都不能写死，所以路径让你传参 `path`，参数呢同样让你传参 `params`。进来以后我这里就默认你是 GET 请求了——通过 `ngx.location.capture`，你的路径是什么我就用什么，方法我写死为 `ngx.HTTP_GET`，请求参数 `args` 用你传给我的参数。那这样我就把这个 GET 请求给封装起来了，你只要调我就能查到结果。

那结果是个 `response`，对不对。这个 response 有可能查到，也有可能没查到。查询失败，我们返回的都是一个 `nil`——`nil` 我们讲过是什么，它是不是代表一个 `false` 呀？所以如果查失败了，这个地方你得到的就是 `nil`，那你得到 nil 之后我取反是不是就是 true，为 true 就意味着你失败了。

失败以后大家看，这里我就记录一下错误信息。`ngx.log` 是利用这个 `ngx` 去记日志，`ngx.ERR` 是记录错误信息，这里说了 http not found，也就是这个 API 查询失败了——路径和参数都给你记下来了，然后通过 `ngx.exit` 退出。

那如果查成功了呢？我就 `return resp.body`。刚才我们讲过，这个 body 是不是那个 JSON 的字符串呢？那这样是不是就把 JSON 结果返回给我们这个函数的结果了。

最后我们还把这个函数放到一个 table 里，这个 table 的名字叫 `m`，然后把 `m` return 了。这种语法其实等于什么呀？把当前这里边的东西封装成一个整体，返回了。注意看它不是把函数 return 啊，它是把这个对象 return。那将来凡是拿到 `common.lua` 这个文件的人，就能拿到这个 `m`；拿到这个 `m` 了，就能得到 `m` 里边的这个 `readHttp` 函数，就能够使用了。这就把工具给导出了。

那这个函数比较长，大家肯定写不出来。好在我们安装 OpenResty 的文档的最后一部分已经准备了一个 `common.lua`，大家拷贝一下就行。而为了让日志看起来更舒服一点，我们可以把里面的英文改成中文，比如改成「http查询失败」，这样更方便我们去阅读这个日志。

> **结论**：在 OpenResty 里发起一个 HTTP 请求，主要是两个步骤。首先，利用 `ngx.location.capture` 这个 API 去发请求，指定请求路径、请求方式和请求的参数；注意你发出的请求其实是被 Nginx 自己捕获了的，所以还需要编写一个反向代理，把发起的这个请求拦截下来，代理到你的目标服务器（比如 Tomcat）。将来只要你保证你的请求路径是这个前缀，就都能到达目标服务器了。同时我们还学会了如何封装一个工具类，只要把它放到对应目录下、能够被 OpenResty 加载，将来它就是一个通用的工具模块了。

### 用工具查商品和库存

上一节课我们已经封装好了 `common.lua`，放到 `/usr/local/openresty/lualib` 包下。这个目录默认情况下就会被 OpenResty 去读取，所以这个 `common.lua` 已经默认被加载到我们的 OpenResty 里边的函数库中去了。那个时候任何人只要引用了它，就能够去使用我们这个工具函数。

具体该怎么去用？这节课我们一起去看一下。

#### require 引入，再取出函数

在 `item.lua` 里，我们现在返回的还是假数据，接下来要做的事情就不再是返回假数据了，而是要返回真实数据。这些数据从何而来？是不是要查询出来。所以这里我们需要去查询商品信息，当然还要查询库存信息，因为我们商品和库存是分离的嘛。

这个查询是不是就要用到我们刚才说的那个 `common` 库？那怎么用呢？这里跟我们的 Java 很像，就是一个导包的意思。

```lua
local common = require("common")
local readHttp = common.readHttp
```

怎么导呢？这里需要用一个变量来接收，比如我就叫 `common`，这个变量可以随便起名字。语法叫 `require`，`require` 就是引用的意思，后面跟的是这个文件的名字，我们的文件名就叫 `common`。

这里不能随便写哦，打开这个小控制台，你看到我们这个文件名是不是就叫 `common`？所以我们在 `require` 的时候直接写了这个文件的名字。那如果说你要导的那个是在某个目录下，这里有一个什么文件，你还必须带上目录名。因为我们是直接在 `lualib` 下，所以可以直接写文件名。

好了，`common` 引进来了。那么 `common` 里边是一个 table，大家看导出的是不是一个 table？这个 table 里是不是有个叫 `readHttp` 的函数？所以我在 `item.lua` 这边拿了 `common`，其实就是刚才那边导出的那个 table，所以我要从里边拿到那个函数。函数也是个变量，也可以接收，所以这里可以用变量来接收，比如 `readHttp`。那它其实是 table 里面的一个属性，我们知道 table 的属性是不是可以用点的方式来读取，那这样我就拿到那个 `readHttp` 函数了。

拿到函数以后，那你就可以放心大胆地去调用了吧？我们知道发 HTTP 请求得到的是一个 JSON 数据。我们先打开浏览器访问一下 `localhost:8081`，这是我们那个 Tomcat 服务啊，这是不是查商品？查库存呢是 `/item/stock`。所以这个时候我们只要向这两个地址发请求，是不是就能查询了？

```lua
local id = ngx.var[1]

-- 查询商品
local itemJson = readHttp("item" .. id, nil)
-- 查询库存
local stockJson = readHttp("item/stock" .. id, nil)

ngx.say(itemJson)
```

这里呢我们拿的是个 JSON 数据，所以要去接收。第一个参数是你请求的路径，第二个参数是你的实际参数。那我们的请求路径是什么呢？如果查商品，路径就是 `item` 后面跟上 1001 这个 id，但这个 id 不能写死，要根据参数来传递——这不是有 id 嘛，所以这叫拼接，拼接是不是有两个点来拼接，这样就有了这个完整的路径了。

但这个路径后面有没有问号参数？没有吧，所以第二个参数我们是不需要的，我们没有参数，所以这里给 `nil` 代表无参。

`reload` 之后回浏览器刷新：商品有变化了，1003 是牛仔裤，1004 是鞋子，1005 是拉拉裤，所有的商品都能正确查询了。但是大家看销量和库存有没有？没有吧？那说明你的数据还不完整。

#### JSON 没法拼装，得先变成 table

那事实上呢，如果这里再有第三张、第四张、第五张表需要查，你是不是都需要把它拼接起来？比如再有商品描述啊什么之类的，都需要往这儿拼。所以这里边最终需要的是完整数据。

那我们该怎么样完成这个数据的拼接呢？现在你是个 JSON，JSON 是无法去做数据拼装的，你就除非把它转换成 Lua 中的对象——不是对象，而是 table 结构。只要转成这样，我们才能去操作 table、往里面加数据。

那怎么样实现从 JSON 到这个 table 的转换呢？这里又要用到一个工具包，名字叫 `cjson`，这也是 OpenResty 里提供好的一个库。用法也非常的简单：

```lua
local cjson = require("cjson")
```

第一步就是 `require "cjson"`，不是导入嘛，这里边要跟的是文件名。现在打开 Shell 控制台，你看一下在 `common.lua` 的目录底下是不是有一个叫 `cjson` 的？那我们现在只要把文件名指定，是不是就能把这个模块导入了。

导入 `cjson` 以后怎么用呢？如果你要做序列化，就是把 table 变 JSON，你用 `encode`；如果你要反序列化，把 JSON 字符串转 table，就用 `decode`。很简单，`encode`、`decode` 就能实现了。

那我在这儿呢，我需要把商品反序列化成一个 table，那我就可以调用 cjson 了。当然前提得先导入一下：

```lua
local cjson = require("cjson")
```

那么接下来我要去调用 cjson 的函数，获取商品信息了：

```lua
-- 反序列化：把 json 字符串变成 table
local item  = cjson.decode(itemJson)
local stock = cjson.decode(stockJson)

-- 组合数据：其实就是把库存的数据放到商品里面去
item.stock = stock.stock
item.sold  = stock.sold

-- 商品已经变成 table 了，不再是 json，所以还得再序列化回去
ngx.say(cjson.encode(item))
```

怎么组合呢？其实就是把库存的数据放到商品里面去嘛。那商品里面有两个没有？一个是 `stock`，没有，对吧，那就从 `stock` 里面去取 `stock`；还有一个是销量，`sold` 没有，对吧，那就从 `stock` 里去取这个 `sold`，因为库存里是有这两个值的嘛，就可以取出来。

注意这里不用 `get`，啊，不是咱们 Java 了，这是 Lua，Lua 里面可以直接用点来取就行了。那这样库存的值就填到商品里面去了。

填完以后，我们是不是还要把商品返回啊？但是现在商品已经变成什么？是不是已经变成一个 table 了，不再是 JSON 了，所以你还得序列化，把 item 序列化为 JSON 再返回，那这次要调的就不是 `decode` 而是 `encode` 了。那这样整个逻辑就实现了对 JSON 的处理。

`reload`，回浏览器刷新。这时候我们来看一下，1005 里边有没有销量和库存？是不是有了。那这样我们这个页面上库存也能够正常显示了。

> **结论**：到这里我们实现了两个功能。一是通用工具模块的使用，类似于 Java 的导包，利用 `require` 去引入、用一个变量接收，然后调这个函数去发送请求，得到 JSON；二是数据组装，这里用到了新工具 `cjson`，它可以实现对 JSON 数据的序列化和反序列化——序列化就是把 table 变 JSON，反序列化就是反过来把 JSON 变成 table。有了它，我们就能把数据组装好，最终返回给前端页面。

### 一台 Tomcat 不够：按商品 id 负载均衡

#### 轮询为什么会让进程缓存失效

刚才那个案例里边，Tomcat 其实只有一台。但是在实际生产中，Tomcat 的一定是一个集群吧？所以你的 OpenResty 再去发送这个请求的时候，你必须得对多台 Tomcat 实现一个负载均衡。比方说我这里有 8081、8082 两台 Tomcat，你这里就要配置那个负载均衡了。

负载均衡本身并不难，我们之前是不是也都讲过呀？只需要定义一个 `upstream`，比如说叫 `tomcat_cluster`，那这样就形成了一个 Tomcat 集群了嘛。然后在里边把每一台 Tomcat 的 IP 和端口都定义出来。将来我们的 OpenResty 其实底层也就是 Nginx，它就会对这个列表中的每一台机器去做一个轮询的负载均衡。

```text
                  轮询：item/1001 → 8081
   OpenResty ─────────────────────▶  8081  ✔ 有 JVM 进程缓存
        │                            命中，性能非常好
        │
        └─────────────────────▶  8082  ✘ 没有缓存 → 又得查一遍数据库
                  轮询：item/1001 → 8082
```

当然了啊，你之前那个反向代理是不是要改一下了？我们之前那个反向代理目的地指向的是 8081，写死了。那你现在既然有集群了，这就不能写死了，是不是应该写成集群名称。

那问题就来了。像这样访问下去，性能能好得了吗？我给你算一笔账。

请求被负载均衡挑到了一台，跳到了 8081，那这个时候你的请求就会到达 8081，然后去查数据库，查完数据库以后还会形成一个 JVM 的进程缓存，保存再 8081 这一台服务器上。这时缓存有了以后，如果下次再来查 8081，是不是可以直接读取缓存，不用查数据库了？性能是不是就非常好了。

但是啊非常可惜的是，进程缓存是不能共享的。8081 有这个缓存，8082 有没有？没有。而我们的负载均衡的规则是什么？是轮询。所以你现在访问 item/1001，再访问一次的话，因为它就必然走到 8082，那你的缓存就没有生效了。那这样一来，如果我这里不是两台 Tomcat，再有第三台、第四台，那接下来我再访问是不是都不会生效啊？除非每个服务都放了一遍，那这样一来我这个缓存就需要在多台 Tomcat 上去冗余地保存——第一个是占用了额外的空间，第二呢这个缓存的命中率啊，也有点惨。这不是我们想看到的。

所以如果说我想让 1001 这个商品，第一次查询完以后永远都有缓存，我必须得做到什么呢？我必须得让 `item/1001` 这个请求每次都指向同一台服务器，这样是不是才能够保证这个缓存一直生效。也就是说，同一个 id 的商品永远指向同一台服务器。假如说你又来了一个 item/1002，那我再让你指向下一个服务器；再来一个 1003，我再指向下一个服务器。那么不同商品访问到不一样的服务器，当然也可以是一样；然后相同商品的同一个 id，永远访问同一个服务器。这样是不是可以保证缓存永远命中，你的 JVM 进程缓存才有意义。

但是能做到吗？我们现在是轮询，肯定做不到吧，怎么办？是不是需要修改我们 Nginx 的负载均衡算法了。

#### hash $request_uri

在 Nginx 里，有这么一种负载均衡算法，叫做 `hash $request_uri`。那这个什么意思呢？

`request_uri` 就是你的请求路径。比方说我访问 `/item/1001`，那么这里的 `request_uri` 指的就是这个路径。而哈希的意思就是对这个路径做哈希运算，比方说用一种哈希算法进行运算，得到了一个数值，这个数值比如说是 1001 啊，举个例子。

```text
   路径 /item/1001
          │
          ▼
    ┌───────────┐   哈希算法
    │  hash 计算 │ ──────────▶ 得到一个数值（举例：1001）
    └───────────┘
          │
          ▼
   对服务器数量取模（假设 2 台）
   1001 % 2 = 1  →  数组下标 1  →  8081
```

那这个时候得到一个哈希值了以后再干嘛呢？再对 Tomcat 服务器的数量取模，或者说讲取余吧。比如说我数量是二，我就对二去取。那如果我对二取的话，1001 对二取余的结果是不是就是 1 啊？那按照这个数组，数组从一开始，那是不是永远分到 8081。

OK，只要你的请求路径没有变，你永远得到的哈希值是一样的，那你永远访问同一台服务器。那如果你的路径变了，变成了 item/1002，访问到这个 id 为 1002 的商品了，那么它的哈希值变了，那它的服务器是不是也会变。这样是不是就能起到负载均衡的效果了，并且可以确保的是，只要你路径不变，你的服务器地址也不会变，那我们的 JVM 缓存就能够一直命中了。

那下面我们就参考这个来实现一下。打开编辑器找到我们的 `nginx.conf`，现在我们是写死了这个代理的目标地址，那接下来我们就要改了，不能写死。我们需要在上面定义一个 `upstream` 集群，然后呢起个名字，比如说就叫 `tomcat_cluster`，然后在这里边去定一个哈希算法，算法呢是基于 `request_uri` 来去进行运算的，然后是两个地址，这一个是 8082，再来一个我们假设说有两个，那就这么写。

```nginx
upstream tomcat_cluster {
    hash $request_uri;
    server 192.168.150.1:8081;
    server 192.168.150.1:8082;
}

location /item {
    proxy_pass http://tomcat_cluster;
}
```

那来这儿呢就不能再去写 IP 地址了，一定要写成这个 `tomcat_cluster`，这样一个我们声明的这个集群就 OK 了，这样就实现了基于 URL 地址的负载均衡。

下面我们去测试一下。首先找到 Shell 控制台，把 Nginx 做一个 `reload`。然后呢我们再回到 Tomcat，我们需要启动两台 Tomcat 服务。在 IDEA 的编辑配置里，启动两台我们给大家讲过吗？只需要把 `application` 拷贝一份，然后起名字叫 `application2`，把端口改一下，`server.port` 等于 8082，这样我们就能够启动两个 Tomcat 了。你看会有两个 service 出来了，我把这两个都启动一下，这两台服务都已经成功启动了。我们把日志清空。

那下面我们就去访问一下。先访问这个 id 为 1001 的，我们刷新，走，访问成功。这时候我们去 IDEA 看一眼，发现他其实这个算法负载均衡到了 8082。那说明他的算法跟我们想象的可能有些差异，对吧？但是呢最起码他确实是找到了，并且发起了一次请求，是 8082 这台机器啊。

我们把日志清空，注意 8081 并没有收到请求。我们再来访问一次，打开浏览器刷新。如果说按照轮询，是不是就要找到 8081 了？那么 8081 没有缓存，是不是就再查一次？我们打开 IDEA 看一下，8081 有没有请求？是不是没有？说明还是走的 8082。8082 有缓存，所以说是不是就不用再查了？你看你的 JVM 进程缓存是不是就生效了。

其实呢我们回到浏览器，不管你访问 10 次还是 100 次，只要你 id 没有变，那么它的路由一定是路由到同一台服务。回到 IDEA，你看一直是 8082，这里什么都没有，对不对？除非你换了一个 id。你看现在我访问 1002，你换了一个 id，这时候你再去打开这个 id，看是不是都跑到另外一台服务器上去了？是不是就实现了负载均衡了，而这台服务器上呢它也建立了缓存。所以你再回到浏览器去狂刷，不管你刷多少次，你再回到 IDEA，它绝对不会有日志，说明缓存是不是一直都命中了。

那这样，不管是任何一个商品，只要第一次访问完，它都会有缓存存在，那就达到了我们最终的目的了。

> **结论**：这就是对多台 Tomcat 的一个负载均衡，并且能够确保进程缓存永远生效。前提很简单——同一个商品 id 必须永远落到同一台服务器上，否则每台都缓存一份，既浪费空间，命中率又上不去。

## 多级缓存最后一哆嗦：Redis 预热、OpenResty 本地缓存与缓存同步
> 对应块：BLK37 | 覆盖分集：P127-P130 | 块标题（分集名）：《高级篇-多级缓存-15-多级缓存-Redis缓存》

上一节课我们打通了 OpenResty 到 Tomcat 集群的这一段：请求从 OpenResty 出来以后，按 URL 路径做负载均衡打到 Tomcat 集群的任意一台，Tomcat 进程内的 JVM 本地缓存才能一直生效——不然请求在集群里乱窜，缓存命中率就没了。

但是按照我们最初对多级缓存的设想，请求到达 OpenResty 之后**不能直接去查 Tomcat**，应该先查 Redis，Redis 缓存没命中的时候再回落 Tomcat。这一节就把 Redis 这一级插进去。

不过插缓存会带出一个绕不过去的问题，还是先从这个问题说起。

### 冷启动会把数据库打崩，所以要做缓存预热

一个服务刚刚启动的时候，Redis 里是空的，一行数据都没有。这时候如果所有商品请求一起涌进来，每一件商品在第一次查询时都得去查数据库，查到之后再回填缓存——数据库会瞬间承受巨大的压力，严重的话直接崩。这就是**冷启动**问题。

> **定义**：冷启动，指服务刚启动、缓存还是空的这段时间内，大量请求同时穿透缓存直打数据库，导致数据库压力骤增甚至不可用。

所以一般企业里都会做**缓存预热**：项目启动的时候，我提前把数据放进缓存里；等用户来查的时候，缓存里已经有了，不用再临时去查数据库。一句话，预热就是把"第一次查询才去查库"这件事挪到启动阶段提前做完。

#### 预热该往里放什么数据

问题紧接着就来了：如果我把数据库里**所有**数据都提前放进缓存，这不现实。数据库的数据肯定是非常非常多的，远远超过 Redis 的容量。那到底放什么进去？

实际开发中往往会借助大数据统计的技术，先记录清楚到底哪些数据属于热点数据，做预热的时候只把热点数据放进 Redis 就行了。

> **结论**：真实项目里，预热的范围由"热点数据"决定；课程里没有大数据统计这套东西，所以我们直接把数据库里的所有商品、库存数据全放进去，作为预热演示。落到生产环境，你要结合负责离线统计的团队产出的热点名单来放。

#### 用 InitializingBean 把预热挂到项目启动那一刻

环境先搭起来。装 Redis 用的还是老熟人 Docker：

```bash
docker run --name redis -p 6379:6379 -d redis redis-server --appendonly yes
```

`-p` 做端口映射，`-d` 后台运行，最后的 `--appendonly yes` 我们之前讲过，就是用日志的方式做数据持久化。跑起来之后 Redis 服务就起来了，再开一个客户端连上去，一开始当然什么都没有。

接下来要在微服务里跟 Redis 建立连接，两步：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```yaml
spring:
  redis:
    host: 192.168.150.101
    port: 6379
    # 其余保持默认即可
```

`host` 填我们虚拟机的地址。

那预热这件事在什么时候做？答案是项目启动的时候。Spring 里正好有一个接口专门干这个：

```java
@Component
public class RedisHandler implements InitializingBean {

    private final RedisTemplate<String, String> redisTemplate;
    private final IItemService itemService;
    private final IStockService stockService;

    @Override
    public void afterPropertiesSet() {
        // 这个 bean 一创建完、成员变量注入完成，这个方法就会执行
        // 而 bean 是在项目启动时就创建的，所以预热也就跑在启动阶段
    }
}
```

> **提示**：`@Component` 让这个类被 Spring 管理并注入容器；`InitializingBean` 接口规定必须实现 `afterPropertiesSet()` 方法。这个方法的执行时机是"当前 bean 创建之后、并且成员变量都完成注入之后"。既然 bean 本来就是项目启动时创建的，那把初始化缓存的逻辑写在这个方法里，就等于实现了"项目一启动就做预热"。

> **易错点**：凡是实现了 `InitializingBean`，就必须老老实实实现 `afterPropertiesSet()`，这个方法名写错、漏写都是坑。

预热的步骤其实就三步：**查数据 → 序列化成 JSON → 写进 Redis**。这里要注意，商品缓存和库存缓存是两种缓存，应该分开来做，我们先做商品相关的。

#### 序列化成 JSON，并且给 key 加前缀

数据最终要存进 Redis，肯定得存成 JSON 字符串。这件事 Spring 里已经有现成工具了，就是 Jackson 的 `ObjectMapper`，定义成一个静态常量当工具用：

```java
private static final ObjectMapper MAPPER = new ObjectMapper();

String json = MAPPER.writeValueAsString(item);
```

`writeValueAsString` 就是把一个对象写成字符串，返回值就是 JSON 文本。有人以前可能没见过这个类，这里算是正式认识一下。

拿到 JSON 之后就往 Redis 里放，用最简单的那种 key 结构：

```java
redisTemplate.opsForValue().set(key, json);
```

那么 key 用什么？很多同学第一反应就是：把 id 往这一放不就完了。**但你千万别忘了，除了商品，库存是不是也要做缓存？** 而商品和库存它们俩的 id 是一样的。你要是直接拿 id 当 key，这两边的数据直接就撞车了，Redis 的 key 会冲突。

所以在 Redis 里，key 一定要**带前缀**，不能直接就是 id：

```java
redisTemplate.opsForValue().set("item:id:" + item.getId(), json);      // 商品缓存
redisTemplate.opsForValue().set("stock:id:" + stock.getId(), json);    // 库存缓存
```

```text
item:id:1003   -->  {"id":1003,"title":"xxxx","price":1999}    商品基本信息
stock:id:1003  -->  {"id":1003,"stock":99}                     商品库存
```

看到前缀就知道这条缓存是跟什么有关的，后面查的时候也完全按这套 key 来对。库存那边不用 `itemService`，改用 `stockService`，返回值的自然是库存对象，遍历、序列化、写缓存的套路一模一样，只是 key 换成 `stock:id:` 开头的，两个就彻底分开了。

跑一下验证：随便启动一个实例，比如 8081 端口那个。项目启动的那一刻控制台就已经有查询日志了——第一个查的是商品，查到五条；第二个查的是库存，也查到五条。这批数据此时已经被写进 Redis 了，打开 Redis 客户端刷新一下，商品和库存的 key 全都在。预热就成了。

### 让 OpenResty 先查 Redis

预热做好了，接下来就该让 OpenResty 真正去查 Redis 了。这里有个绕不开的问题：**OpenResty 怎么操作 Redis？**

好在 OpenResty 本身就提供了一个 Redis 的函数库，引入就能用，跟我们之前用 `cjson` 的感觉是一模一样的。

#### 导库：为什么是 resty.redis

```lua
local redis = require("resty.redis")
```

`require` 大家都熟，导入嘛，后面跟的是库名称。这里库名称比较特殊，是 `resty.redis`，那个点是从哪来的？我们打开 shell 控制台看一下就明白了。

之前读的是 `lua/lib` 目录下的 `cjson`、`common` 这些库，它们直接就在这个目录里，所以 `require` 的时候直接写文件名就行了。但 Redis 不在根目录，它在 `resty` 目录下，有一个叫 `redis.lua` 的文件。所以你 require 的时候得先写目录名，再写文件名——这就是 `resty.redis` 的来历。Lua 里导函数库就是这个语法。

导进来之后就能用了，而使用的方式有点特殊：

```lua
local red = redis:new()
```

`redis:new()` 这种写法其实是**创建对象**，这是 Lua 里面的面向对象写法，相当于构造函数。`new` 出来的对象就能拿去用了。这一块我们之前没有讲过，属于是顺手补上。

拿到对象第一件事是设置超时时间：

```lua
red:set_timeouts(1000, 1000, 1000)
```

这三个超时时间的单位都是**毫秒**，从左到右分别代表：建立连接的超时时间、发送请求的超时时间、以及响应给我结果的超时时间。

#### close_redis 这个名字有点骗人，其实是把连接放回池子

有了对象就能读写了，但读写完我们是不是还得把 Redis 连接释放掉？我们在下边封装了一个函数叫 `close_redis`，顾名思义就是"关闭 Redis"。

但是这个"关闭"不是真的关闭。你想啊，每次来一个请求就创建连接，操作完又释放，创建加释放其实是性能比较差的。所以一般来说，像这种连接最好是放在**连接池**里的。

虽然我方法名叫 `close`，但你看看它里面干了什么事：

```lua
local function close_redis(red)
    -- 连接池的最大空闲时间，单位毫秒
    local idle_timeout = 10000   -- 10 秒
    -- 连接池大小
    local pool_size = 100

    local ok, err = red:set_keepalive(idle_timeout, pool_size)
    if not ok then
        ngx.log(ngx.ERR, "redis 连接释放失败：", err)
    end
end
```

`set_keepalive` 的意思就是"保持连接"，把最大空闲时间和池子大小一起指定进去。空闲时间这里给 10000，也就是十秒钟：将来这个连接在池子里放那儿，十秒内没人用，我再给你真正地关掉；十秒内你一直在用，我就不关。

这个函数有两个返回值：`ok` 和 `err`。`err` 是异常的消息，等于是 Java 里的那个错误消息；`ok` 才是结果。成功就返回 ok，失败的话这里的 ok 其实是 nil——nil 就代表 false，而 `not nil` 取反之后代表 true，正好进到 `if` 里。我在里面打印一行日志，说放到 Redis 连接失败了，把错误消息展示出来，这样将来排查错误方便。

#### 读数据：nil 和 false 是完全不同的两回事

接下来看怎么利用 Redis 读取数据。我们封装了第二个函数 `read_redis`，三个参数：ip、端口、你要查询的那个 key。

```lua
local function read_redis(ip, port, key)
    local ok, err = red:connect(ip, port)
    if not ok then
        ngx.log(ngx.ERR, "redis 连接失败：", err)
        return
    end

    local res, err = red:get(key)
    if not res then
        ngx.log(ngx.ERR, "redis 查询失败：", err)
    elseif res == false then
        ngx.log(ngx.ERR, "redis 查询数据为空，key 不存在：", key)
    else
        close_redis(red)   -- 其实是放回连接池
        return res
    end
end
```

连接这一步还是那两个返回值，前面解释过一遍了：异常就记日志直接返回，没有异常就往下走真正读写数据。这里只封装了读，所以直接调 `get` 方法，把 key 给你直接读。**注意，它只能读最简单的 key-value、string 这种类型的数据**，map 什么的我这里没有封装。

真正要注意的是读完之后这个判断。返回值同样有异常和结果两个，但结果可能为 nil，也可能为 false：

- `if not res` —— `res` 为 nil，说明这次查询**失败了**；
- `res == false` —— 查询**成功了**，只不过没查到而已，很可能就是这个 key 根本不存在，所以报一个"查询数据为空"。

> **易错点**：`nil` 是查询失败，`false` 是查询成功但数据为空，这两种情况含义完全不同，一定要分开判断，不然排错的时候会被带偏。

上面那个是报错，这个是为空，两个不是一回事。如果这两个判断都跳过了，证明我们是真真切切查到数据了，那就把 Redis 连接释放掉——其实就是放回连接池——然后 return 这个结果。

这两个函数我们统一封装到之前那个 `common.lua` 里。这里我就不逐行念了，大家对着文档写就行，反正就两个函数。最后只把 `read_redis` 暴露出去，`close_redis` 不用暴露——它在 `read_redis` 内部调用就够了。暴露的写法和之前暴露 HTTP 那边是一样的，在 common 里定义一个新属性就行。

```lua
M.read_redis = read_redis
```

将来在 `item.lua` 里想用就很简单，一行导入：

```lua
local read_redis = common.read_redis
```

### 查询链路改造：先 Redis，再 HTTP

有了读 Redis 的函数，商品查询的逻辑就得改了：**先查 Redis，Redis 未命中再查 HTTP**。跟上一节课那个只有一级的顺序相比，多了一层。

问题是商品要改、库存也要改，一共两份。而且这两份代码的形状几乎一模一样——都是"查一个 key，没查到再查 HTTP"。与其复制两遍，不如把它封装成一个函数，就叫 `read_data`。

#### 封装 read_data

```lua
local read_redis = common.read_redis

local function read_data(key, path, param)
    -- 1. 优先查 Redis
    local resp = read_redis("127.0.0.1", 6379, key)
    if not resp then
        ngx.log(ngx.ERR, "redis 查询失败，key：", key, "，尝试查询 http")
        -- 2. Redis 没查到，去查 Tomcat
        resp = read_http(path, param)
    end
    return resp
end
```

参数有三个。ip 和端口不用你传了，我直接帮你写死；`key` 至少得告诉我，不然不知道查什么；查 HTTP 的时候需要 `path` 和 `param`，这两个也得传进来。逻辑本身特别简单：先调 `read_redis`，如果没查到（为 nil），就记一条日志，然后转去 `read_http`。

> **提示**：这里 ip 和端口为什么可以直接写 `127.0.0.1:6379`？因为这段 Lua 代码是在 OpenResty 里跑的，而 OpenResty 和 Redis 都在虚拟机里面，他俩是在一起的，所以 `127.0.0.1` 就代表本地。

这个日志我建议认真写。将来线上真出现查不到的情况，你看到这条日志，就知道是哪个 key 失败了——也就是到底哪一件商品失败了。光写一句"redis 查询失败"等于没写。

下面调用它的地方也不用再直接调 `read_http` 了，改成调 `read_data`，只是参数多了一个 key。key 我们继续沿用预热时定下的那套命名规则：

```lua
-- 商品：item:id: + 真正的 id
local itemKey = "item:id:" .. id
local itemData = read_data(itemKey, path, param)

-- 库存：key 前面要加上 stock
local stockKey = "stock:id:" .. id
local stockData = read_data(stockKey, path, param)
```

这样查询商品和查询库存就都默认"先 Redis，未命中再 Tomcat"了。

#### 验证：把 Tomcat 停掉再说

代码写完先 reload 一下，然后打开浏览器刷新，查询是成功的。但这还不能说明 Redis 真的生效了——万一它悄悄走了 Tomcat 呢？

验证办法简单粗暴：**把 Tomcat 的两个服务都停掉**。以前 OpenResty 是靠它们才能查数据，现在停了，如果页面还能正常查出来，那就证明它走的是 Redis 路径。

实际测下来，商品 1003、1004 都没问题。这就足以证明链路通了：**OpenResty → Redis**，Redis 未命中才回落 Tomcat。这一节的全部内容就是 OpenResty 提供的 `resty.redis` 模块，引入它、设置连接池封装释放、再建立连接读数据，API 我都封装提供好了，大家会用这几个函数就行。

### OpenResty 本地缓存：lua_shared_dict

经过前面几节课，多级缓存里已经完成了绝大部分功能：Tomcat 集群里 JVM 进程内的缓存、OpenResty 到 Tomcat 的负载均衡远程调用、先 Redis 再 Tomcat 的查询顺序、OpenResty 本身的搭建——现在就差最后一哆嗦，**在 OpenResty 里加一层本地缓存**。

最终这条链路应该是这样的：

```text
                  浏览器请求
                       |
                       v
        +-----------------------------------+
        |          OpenResty                |
        |  ① ngx.shared 本地缓存           |---- 命中 ---> 直接返回
        +-----------------------------------+
                       | 未命中
                       v
        +-----------------------------------+
        |  ② Redis  item:id:1003          |---- 命中 ---> 回填本地缓存 ---> 返回
        +-----------------------------------+
                       | 未命中
                       v
        +-----------------------------------+
        |  ③ Tomcat 集群（JVM 进程内缓存）|---- 返回后回填本地缓存
        +-----------------------------------+
```

也就是：请求进 OpenResty，先查本地缓存；本地未命中查 Redis；Redis 未命中再查 Tomcat。

#### 声明共享词典，并拿到缓存对象

nginx 里面通常有一个 master 进程和多个 worker 进程，多个 worker 负责处理用户请求，而它们之间**可以共享数据**，其实就等于一种共享内存。

> **注意**：这种共享只在**一个 nginx 实例内部**成立。你要是部署了多台 OpenResty，它们之间是没法共享的。

开启的方法很简单，在 `nginx.conf` 的 `http` 块下面加一行配置：

```nginx
http {
    lua_shared_dict item_cache 150m;
}
```

这条配置叫 `lua_shared_dict`，就是 lua 的共享词典。后面跟两个参数：第一个是共享词典的名称，名字可以随便起，我这里叫 `item_cache`，就是商品缓存；第二个是它的大小，我给了 150M，因为我们机器内存本身不大，就给小一点。

开启之后就能用了，API 也非常简单：

```lua
local item_cache = ngx.shared.item_cache
```

通过 `ngx.shared` 加上你起的这个名称，就拿到了这个本地缓存对象。拿到之后可以调它的 `set` 方法往里面存数据，调 `get` 方法从里面取数据。

`set` 的时候有三个参数：key、value，还有一个时间。

```lua
item_cache:set(key, value, 1000)   -- 存 1000 秒后自动过期
item_cache:get(key)                 -- 取的时候只给 key 就行
```

`key` 就是存进去的键，没什么好解释的。第三个参数是超时时间：比如我存 1000 秒，那 1000 秒以后这个数据就自动删除了。这样可以避免缓存越存越多这种问题。

> **提示**：如果第三个参数给的是 0，代表**永不过期**。

导入这一行写在 `item.lua` 里，不是写在 `common.lua` 里——因为最终的业务逻辑是在 `item.lua` 里写的。

#### 三级查询改造，以及一定要回填

拿到了对象，接下来就是在查询商品的时候优先查本地缓存。我们把 `read_data` 再改一次，从两级变成三级：

```lua
local item_cache = ngx.shared.item_cache

local function read_data(key, path, param, expire)
    -- ① 先查本地缓存
    local value = item_cache:get(key)
    if not value then
        ngx.log(ngx.ERR, "本地缓存查询失败，尝试查询 redis，key：", key)
        -- ② 本地未命中，查 Redis
        value = read_redis("127.0.0.1", 6379, key)
        if not value then
            ngx.log(ngx.ERR, "redis 查询失败，尝试查询 http，key：", key)
            -- ③ Redis 也没命中，才去查 Tomcat
            value = read_http(path, param)
        end
        -- 查到数据一定要写回本地缓存，不然下一次来还是照样穿透
        item_cache:set(key, value, expire)
    end
    return value
end
```

查询只是一方面，**查询成功以后必须把数据写回本地缓存**，不然本地缓存的数据从何而来？这一步很容易漏，漏了就等于白开这个共享词典。所以哪怕数据是从 Redis 拿到的，也得往本地缓存里写一份并设置过期时间，下一次请求就可以直接从本地读了。

> **易错点**：`item_cache:set()` 里的有效期不能写死在函数体里。商品和库存的合理有效期完全不一样，所以把它做成一个 `expire` 参数传进来。

于是两个业务调用点的参数也跟着变了：

```lua
-- 商品基本信息：半小时
local itemData = read_data(itemKey, path, param, 1800)
-- 库存：一分钟
local stockData = read_data(stockKey, path, param, 60)
```

#### 有效期到底该定多久

我们给商品基本信息配的是 **30 分钟（1800 秒）**，库存配的是 **1 分钟（60 秒）**。为什么不一样？

因为商品的基本信息属于是常年不怎么变的数据——商品的基本信息、商品的描述信息、商品的规格参数这些，基本上架以后就不怎么变了，所以有效期可以设置长一点。而像库存这种相对敏感的数据，变化的频率比较高，有效期就要尽可能设短一点。

再往前推一步：**特别敏感的数据，你压根就不要往 nginx 里存**。因为 nginx 本地缓存的更新策略是**到期更新**，万一数据在到期之前就变了呢？它是不晓得的。所以如果数据特别敏感，干脆就不要加这层缓存。

库存这里之所以还能加，是因为我们这个商品的库存就算有一分钟的差异也不会差太多。**但秒杀商品的库存就不要往里加了。**

#### 报错现场：日志少写了一个 ngx.ERR

改完 reload 一下，打开浏览器刷新——**报错了**。别慌，这类问题最快的定位方式是看日志。我们 cd 到 `/usr/local/openresty/nginx` 目录，`tail -f logs/error.log` 一路跟着。

错误信息很明确：`read_data` 函数的第 15 行，出错的地方是这个 `log`。打开编辑器一看，还真是——**记录日志的时候漏写了错误级别**。

```lua
-- 错误写法
ngx.log("本地缓存查询失败...")

-- 正确写法：第一个参数是日志级别
ngx.log(ngx.ERR, "本地缓存查询失败...")
```

`ngx.log` 的第一个参数得先写 `ngx.ERR`，然后才能拼后面的字符串。你回头看我们之前的那些工具类，是不是全都是先 `ngx.ERR` 再加字符串的？就是这样，这次少写了。补上，重新 reload，再刷新，一切正常。

#### 怎么确认本地缓存真的命中了

修完之后再看一眼日志，这次日志里会告诉你：我先查了本地缓存，失败了，于是去查了 Redis。因为**第一次请求本地缓存一定会失败**——它本来就是空的。

那我再刷新一次，会不会还失败？我们回到控制台看日志，没有了。**没有日志，说明这次走的就是本地缓存。**

再往后还有个更暴力的验证：如果访问的商品在本地缓存里没有了，日志又会重新出现"先查本地缓存失败，然后查 Redis"。而当我们把 Redis 里商品 1003 的 key 直接删掉，再去访问 1003——**页面照常正常，而且响应速度非常快，6ms 一瞬间就查出来了**。为什么？因为 nginx 里还留着本地缓存呢。

到这里，nginx 本地缓存就算做完了。总结也就两步：第一步通过 `lua_shared_dict` 指令开启共享词典，指定名称和大小；第二步封装函数使用它，`get` 取、`set` 存。逻辑上改成先查本地缓存、未命中再查 Redis、Redis 未命中再查 HTTP，把最终结果放进本地缓存，这样下一次请求就会优先读本地缓存。

### 缓存同步：数据库和缓存怎么保持一致

现在多级缓存架构已经完整了，查询性能大幅提升。但缓存这东西在提高性能的同时，也带来了**一致性问题**：比如数据库发生了修改，这时候如果你的缓存依然是旧的数据，两者不就产生不一致了吗？

这不是我们希望看到的。如何保证数据库与缓存数据的一致性，就是这一章要解决的问题。这一章先带大家了解几种常见的缓存同步策略，然后再实现其中的一种。

#### 三种常见策略先摆在一起

| 策略 | 怎么做 | 优势 | 不足 | 适用场景 |
| --- | --- | --- | --- | --- |
| 有效期（被动同步） | 只给缓存设计有效期，到期自动删除，下次查询自然拿到新数据 | 简单、方便，等于根本不用做同步 | 时效性差：到期之前数据库改了，缓存根本不知道 | 更新频率较低、时效性要求较低的业务 |
| 同步双写 | 数据库写和缓存写放进同一个事务 | 时效性非常强，基本能做到强一致 | 代码侵入、耦合度高，缓存点越多业务代码越臃肿 | 对一致性、时效性要求比较高的缓存场景 |
| 异步通知 | 改库后发一条消息/事件，通知缓存自己去更新 | 低耦合、代码侵入少，一条通知可被多个缓存服务消费 | 时效性比同步双写差一些 | 时效性要求没那么高、且有多个服务需要同步 |

#### 靠有效期：最简单，也最迟钝

第一种是通过**有效期**来控制缓存同步。这其实是一种被动的缓存同步：因为给缓存设计了有效期，让它到期以后自动删除，你下次再来查的时候，缓存不就更新了吗？

事实上我们的 OpenResty 本地缓存用的就是这种方式。

它最大的优势就是简单、方便——因为等于是没有做同步，你只要设置一个过期时间就够了。但缺点也很明显：**时效性比较差**。什么叫时效性？就是数据库与缓存同步之间会存在的那个时差。因为你是到期了才去删，在到期之前数据库发生了什么修改，你知不知道？显然不知道。那么这样缓存与数据库就不一致了。

所以它适用的场景是那种更新频率较低、时效性要求也较低的业务。比方说商品里有基本信息、库存信息、价格信息、描述信息、规格信息等等，将来我们把这些数据都分离出来，经常变化的比如库存或者价格，就可以单独保存，用别的方式去做同步；而其他一些不怎么变的数据，就可以用这种过期的方式做同步。

#### 同步双写：一致，但代码会变重

第二种叫**同步双写**。什么意思呢？就是把数据库的写操作和缓存的写操作变成一种同步的操作，放到**一个事务**当中。

比方说我现在做一个新增商品的业务，在新增商品的业务代码后面，紧跟一个新增数据到缓存的业务，然后形成一个事务——两个都成功，要么都成功，要么都失败。这样就能确保数据库修改的同时，缓存也一定会被修改。

它的时效性是非常强的，缓存与数据库基本可以做到强一致。

但缺点是**代码侵入耦合度比较高**。你想啊，我明明是一个新增商品的业务，结果在里面硬塞了一段更新缓存的逻辑。而且你将来如果缓存不止一个地方，好多地方都有缓存，那你这个新增商品、修改商品的业务里是不是要加好多好多逻辑？所以代码侵入是比较多的。

它适合的场景，就是你对一致性、时效性要求比较高的这种缓存场景，才会去用它。

#### 异步通知：发条消息就行

第三种叫**异步通知**。你在修改数据库时想要修改缓存，但是**不直接去改**，而是发送一条消息通知：我告诉你们这些个缓存，你们赶紧都给我改好。至于你什么时候改，我不管了，我通知到位就行了——这就是异步。

这种通知可以利用我们以前学习的 MQ 来实现。

它的优点是**低耦合**：我去做商品增删改查的时候，不用去加好多好多业务逻辑了，只发一条通知。而且我发的这一条通知，是不是可以被多个缓存服务都收到？这就是它的一大优势，代码侵入比较少，耦合度也比较低。

它也有缺点：因为我是做完增删改以后才发事件通知，那这个通知你到底有没有收到？你收到了以后什么时候完成修改？哇，这就不清楚了。所以时效性相对于同步双写来讲要差一些。

不过大家放心，我们现在的 MQ，比如我们今天会学到的 RabbitMQ、RocketMQ 等等，它们往往时效性本身就很强——这边发消息，那边立马就收到，延迟往往是在**毫秒级别**，而且消息的可靠性也比较强。具体怎么能保证 MQ 的可靠性，大家可以关注后面的课程。

所以在这样的前提下，异步通知的时效性其实也就没有那么差了。现在来讲还是不错的。但是相比同步双写，它还是要差一点。

因此它适合的场景，往往是**对时效性要求没有那么高，而且你有好多服务需要同步**的情况。事实上我们大多数缓存，都可以用这种异步通知方案来实现。

#### 为什么这一章最后落到 canal

异步通知可以用 MQ 来做，这个是我们比较熟知的：做商品的增删改查，我就写数据库，写完了以后发一条消息，好，我的业务就结束了。至于你那边缓存什么时候监听、什么时候修改，我就不管了。

但我们今天要学的是**另外一种**：发 MQ 消息，其实还要在商品服务里做一些代码的修改，对吧？至少你还要发一条消息。而 canal 方案是基于 **canal 这个库来监听 MySQL 数据库的变化**——修改商品的业务根本不用改，还是以前的逻辑，来了以后就写数据库，写完结束。

```text
     商品服务：照旧写 MySQL，一行代码都不用改
                     |
                     v
                  MySQL
                     |  binlog 变化
                     v
                  Canal      监听数据库变化
                     |
                     v
              缓存服务：收到通知 --> 更新缓存
```

发现数据库变了以后，直接通知缓存服务完成更新。

这样是不是可以做到代码零侵入？你的商品服务去做商品修改，根本感知不到说有人在监听着。所以这种方案相对来讲侵入性更低，零侵入、没有任何耦合。而且它的时效性其实比 MQ 这种方式要更好一点，效率也比较高。

> **结论**：三种常见的缓存同步策略——靠有效期自动过期、同步双写、异步通知。多级缓存里本地缓存用的是第一种，接下来要用 canal 来实现第三种。

## Canal 缓存同步与 Redis 键值设计
> 对应块：BLK38 | 覆盖分集：P131-P135 | 块标题（分集名）：《高级篇-多级缓存-19-缓存同步-安装Canal》

上节课我们把缓存同步的策略过了一遍，选定了用 Canal 来做这件事。这节课就实打实地把它装起来——装完之后，Java 侧怎么接住它传来的变化、怎么顺着它去改缓存，再把整条多级缓存的链路和同步策略串一遍看看。最后我们进入 Redis 最佳实践的第一章：键值设计。

### Canal 是什么：把自己伪装成一个从库

先认识一下这个名字。Canal 的英文就是这么写的，音标念出来，它的翻译过来就是**水道、管道**。它是阿里巴巴旗下的一款开源项目，基于 Java 开发，作用是**监控数据库的变更，提供增量数据的订阅和消费**。它的 GitHub 地址课件里给了，想翻源码的自己去瞅一眼。

#### 先复习 MySQL 主从同步

可能很多人对 MySQL 主从同步不太了解，这里我们简单介绍一下，因为 Canal 的原理就架在这上面。

大家看这幅图：

```text
        业务 SQL
           |
           v
  +-----------------+
  |     Master      |   ① 增删改时写入 binlog events
  |    （主节点）    | -------------------------------+
  +-----------------+                                |
           ^                                        v
           |                          +----------------------------+
           |                          |          binlog            |
           |                          |   （二进制日志文件）        |
           |                          +----------------------------+
           |                                        |
           |                   ② I/O 线程不断读取     v
           |                          +----------------------------+
           |                          |        relay log          |
           |                          |      （中继日志）         |
           |                          +----------------------------+
           |                                        |
           |                   ③ SQL 线程重放这些操作  v
           |                          +----------------------------+
           |                          |          Slave            |
           +--------------------------|         （从节点）          |
          ④ 两边数据一致               +----------------------------+
```

读图：Master 只干一件事——你执行了增删改，它就把这件事记进 binary log，里面记的东西叫 binary log events，说白了就是你执行的那些业务 SQL。Slave 呢，开一个 I/O 线程不断去读这个日志文件，读过来放进 relay log（中继日志）里；然后再有一个 SQL 线程，去重放日志里执行的这些操作。

你那边做了增，我这边照样做增；你那边做了改，我这边也做改。也就是说主节点做了哪些 SQL，我这边也照着做一遍，那这两个库的数据是不是一定就一致了。这就是 MySQL 主从同步的原理。

#### Canal 干的事，就是"假扮"一个 slave

那这跟 Canal 又有什么关系呢？

Canal 的原理就是**把自己伪装成 MySQL 的一个 slave 节点**。待会儿我们的 MySQL 开启主从同步、生成 binlog，Canal 就不断去读这个 binlog。这样每当你做了一次增删改，它是不是立刻就知道了？知道了以后，就可以把这个消息通知给各种各样的下游服务——比如 Elasticsearch、比如你的 MQ，或者是我们的 Redis——去完成数据同步。

> **结论**：要用 Canal，就得先实现 MySQL 的主从同步。所以它的部署相对会麻烦一点，这麻烦是躲不掉的，咱们老老实实一步步走。

### 部署 Canal：照着文档一步步来

安装其实没什么技巧，大家只需要参考这个流程一步一步做就行了。我们来看第一步。

#### 开启 MySQL 主从同步

开启主从需要去改 MySQL 的配置文件。好在之前刚好做过 MySQL 容器的挂载，把配置文件挂载到了宿主机目录下，所以这个地方要改就非常简单了。

改什么内容呢？去修改 `my.cnf`，往里加两行就够了：

```ini
[mysqld]
log-bin=mysql-bin
binlog-do-db=黑马
```

- 第一行是告诉 MySQL，binary log 的存放位置以及名称。后面跟的 `mysql-bin` 就是这份 binlog 的名字，这个名字你可以自己随便起，我这里是起的这个名字。
- 再往下这个 `binlog-do-db`，指定的是你的这份 binlog 监控的是哪一个数据库。

> **易错点**：别一上来就全库记录。我们打开 MySQL 客户端看一眼，里面有好多个库，但我们的数据是放在 `黑马` 这个库里的，所以 binlog 只记住这一个库就行了。否则将来你记录过很多无关的库，就有点多余了。

改完之后记住这两个东西，然后去控制台操作一下。复制一个终端，`cd` 到 `/tmp/mysql` 下面，这里能看到几个东西，其中 `config` 目录里就是我们的 `my.cnf`：

```bash
cd /tmp/mysql
vi config/my.cnf
```

进去把上面那两行加上，保存一下，然后去重启你的 MySQL：

```bash
docker restart mysql
```

重启完成以后大家注意来看一下 data 目录，里面是不是出现了一个 `mysql-bin.0001` 这样的文件？`mysql-bin` 就是我们刚刚起的那个 binlog 的名字，那 `.0001` 是文件的编号。那么这个二进制 binlog 文件会越来越多、越来越多，所以它的编号也会越来越大，`001`、`002`、`003` 逐渐增大，就是这么个意思。

那么修改完成以后，MySQL 其实已经可以去用了。但是主从同步还需要去给从库设置一个权限。这里其实就是在给从库设置权限：创建了一个全新的用户，叫做 `canal`。我们找到文档里的 MySQL 客户端，新建一个查询，执行这段逻辑——创建新用户、授权、刷新权限，就这么三行。执行完成以后点开用户列表，是不是能够看到一个名为 `canal` 的用户？这样就证明你的 MySQL 用户添加成功了。

回到文档，重启完以后通过 `SHOW MASTER STATUS` 查看主从状态：

```sql
SHOW MASTER STATUS;
```

可以看到这里边有这样的信息。其中 `File` 就是 binlog 的名称，`Position` 是它里面那个 log 的偏移量，再往后还能看到对应的数据库名称，叫 `黑马`。

> **提示**：当 MySQL 在做主从同步的时候，它需要知道主库的 position 位置。如果从库的 position 和主库的 position 不一样、小于主库的 position，那就证明你有新的一些 log 需要去获取了。这个有点像我们 Redis 主从同步里面那个 offset，用来确定从库与主库之间的数据差异。

到这里，主从同步就已经成功开启了。

#### 把 MySQL 和 Canal 拉进同一个 Docker 网络

主从同步开启只是第一步，第二步还要安装 Canal。这里我们需要先创建一个 Docker 的网络，然后让 MySQL 跟 Canal 将来在同一个网络里：

```bash
docker network create 黑马
docker network connect 黑马 mysql
```

网络的名字是 `黑马`，容器叫 `mysql`，这样我们的 MySQL 容器就加入这个网络了。下边我们安装 Canal 的时候也加入这个网络，两者是不是就互通了？

#### 跑起 Canal 容器

安装 Canal 需要先去加载 Canal 的镜像。镜像在课件资料里已经给大家提供了，找到它，通过 `docker load` 加载到我们的镜像里面就行了：

```bash
docker load -i <canal 镜像文件>
docker images
```

运行 Canal 的命令是 `docker run`，参数大致是这么几类：

| 参数 | 作用 | 我们的取值 |
| --- | --- | --- |
| `-p` | 端口映射 | Canal 客户端要连上来的端口 |
| `--name` | 容器名称 | `canal` |
| `destination` | Canal 的集群名称 | `黑马` |
| `mysql master 地址` | 主节点地址 | `mysql:3306` |
| 用户名 / 密码 | 做数据同步时的用户名、密码等 | 创建用户时已经备好 |
| 数据库/表过滤 | 监听哪个库 | 只监听 `黑马` 库下所有的表 |
| `network` | 加入哪个 Docker 网络 | `黑马` |

这里面的环境变量非常多，其中有这么几个是比较关键的。

第一个是 `destination`，它是 Canal 的一个集群名称——Canal 是可以做集群的，这也是给这个集群起个名字，也就是说我们当前的 Canal 就叫 `黑马`，是这个集群下的。

再往下是对应的 MySQL 主节点地址。大家看它叫 `master`，就是你主节点的地址，将来 Canal 要联系 Master、要做主从同步，所以你得知道主节点地址。这里我有一个地方没写 IP，而是写的是 `mysql:3306`。为什么？因为我们的 Canal 跟 MySQL 在同一个网络里，而 Docker 容器在同一个网络时，是可以用**容器名**互相访问的，所以我这里直接写成 `mysql`。

再往下是做数据同步时的用户名、密码、编码等等。这些信息我们刚才在创建用户的时候是不是已经创建好了，所以已经不用再去操心了，直接配上就行了。

这里还有一个比较关键的是数据库过滤：将来 Canal 监听主从同步时监听哪个库。因为我们的主从同步只开启了 `黑马` 这个库，所以这里只监听 `黑马` 这个库。这个就是 `黑马` 这个库下的所有的表，就这么个意思。当然这块其实它有一种语法，`黑马.tb_item`、`黑马.*` 等等，这些语法就是用来描述你要进行哪个库、什么表的。最后一个就是镜像名称，我们把这个命令复制一下就可以去运行了。

#### 确认它真的连上了 MySQL

运行起来以后，先看看日志：

```bash
docker logs -f canal
```

看到表示启动成功的字样，就说明容器起来了。

那启动成功了以后，我们怎么知道 Canal 有没有跟 MySQL 建立连接呢？进入容器内部看一下：

```bash
docker exec -it canal bash
ll
tail -f canal-server/logs/canal.log
```

里面是不是有一个 canal 的目录，通过 `tail -f` 跟上一个 canal 的运行日志文件就能看到它的运行情况——可以看到 Canal 运行是没什么问题的。

然后这里除了 canal 的运行日志以外，还会有一个其他的运行日志，就是 `黑马` 下边的一个 log。在这个运行日志里面就会有这么一段信息了：它会尝试去连接谁呢？连接这个 `mysql:3306`。连接了以后呢，它还会尝试去做 `find start position`，去找什么呢？找主从同步那个 binlog 的偏移量 position。找到了以后就开始去同步那个日志了——那么找到了 `mysql-bin.0001` 嘛，我们刚才是不是看到过有这个文件？接下来就开始做同步了。

到这，就证明 Canal 的安装就成功了。

### 在 Java 端接住这些变化

上一节课我们已经安装好了 Canal，并且让它监听了 MySQL 的变化。那我们接到变化以后，肯定要去更新我们的缓存，这个又该怎么去做呢？

Canal 提供了各种语言的客户端，当然包括我们的 Java 语言客户端。将来在我们的 Tomcat 服务里就需要去编写 Canal 的客户端。它在监听到 MySQL 的数据变化时，会去通知我们的客户端——那也就是给 Java 代码。我们的客户端接收到这样的通知以后，自然就应该去更新 Redis 了，对不对？

所以接下来要做的事情，就是在 Tomcat 里编写客户端监听变化、修改 Redis。但官方原生提供的这个客户端写起来是比较麻烦复杂的，这儿我给大家推荐了一个第三方开源的 Canal 的 starter，这个是跟 Spring Boot 整合的，用起来极其方便，拿来就能用了。

#### 引依赖，配上自动装配

怎么用呢？第一步需要引入一个依赖，这个依赖的名字叫 `canal-spring-boot-starter`，它的 groupId 是 `top.java.two`，版本是 `1.2.1-Release`：

```xml
<dependency>
    <groupId>top.java.two</groupId>
    <artifactId>canal-spring-boot-starter</artifactId>
    <version>1.2.1-Release</version>
</dependency>
```

引了这个依赖以后，你就可以实现 Canal 的自动装配了。剩下的事情就是告诉它 Canal 的 IP 地址和端口号，以及 Canal 的 `destination`（集群名称）。这里的名称啊，一定要跟我们安装 Canal 时的名称保持一致——你看我们安装文档里 `destination` 是不是 `黑马`？对，一模一样。所以在配置文件里配的这两个东西就够了：

```yaml
canal:
  server: 192.168.150.101:11111
  destination: 黑马
```

这两件事做完，Canal 就实现自动装配了。下面我们把这两件事做一下：找到 pom 文件引入依赖，然后配置 application 配置文件。到这儿 Canal 的配置就完成了。那接下来又该怎么样去监听 Canal 呢？

#### EntryHandler：表名、实体类、增删改三个方法

监听需要我们编写一个类，并且实现一个接口，这个接口的名字叫 `EntryHandler`。

在这个 `EntryHandler` 里边，首先你需要去加一个注解，叫 `@CanalTable`。因为你这个 handler 将来是处理数据库变化的，当数据库变化时，你是不是要知道？但是数据库有那么多张表，哪张表变化了你需要知道，所以在这儿通过 `@CanalTable` 是声明表的，也就是说我要监听哪一张表。比如黑马这个库里的 `tb_item` 这张表发生变化了，那么我们就能够感知到了。

感知到了以后干什么呢？这里要指定一个泛型 `Item`，这个泛型是表对应的实体类。那么将来我们监听到这张表中的数据发生变化时，它就会把变化的那一行数据封装成这个实体对象，然后传给我们。

那传递在哪里呢？这个 `EntryHandler` 接口里有三个方法需要我们实现，分别是增、改和删。当数据库发生增删改时，它就会把对应的那一行数据封装成 item 对象，然后传递给对应的这三个方法。那这样来你就能拿到对应的那些数据了吧，你就可以去做你想做的事了：比如说监听到新增了，那我是不是把新增的这个数据写到 Redis 里去？监听到更新了，那我是不是把更新后的数据放到 Redis 里去？监听到删除了，我是不是把 Redis 的删掉就行了？

好，这就是我们 Canal 监听的一个基本语法。

#### 给实体类打上三个注解

但是这里有一个问题了：Canal 怎么知道该如何把数据库表中的数据变成 Item 实体类？

当然有些人说了，这还不简单吗，我们 MyBatis 不是这么搞的吗？是，那是 MyBatis 底层实现的。而 Canal 底层并不依赖于 MyBatis，所以它得知道怎么把表中的数据转成实体类。那所以我们需要给这个实体类加一些 Canal 内部用到的一些注解，来标记实体类与表中字段的映射关系。

需要加哪些注解呢？三个你可能会用到的：

- **`@Id`**：标记我们这个类里边跟数据库主键进行关联的那个字段。
- **`@Column`**：声明字段对应的列的名称。
- **`@Transient`**：标记不属于表中的字段。

这里面的门道是这样的：如果说是主键，给它标一下 `@Id` 就行了。非主键的其他字段，其实你不用加任何注解——除非你这个字段名称与数据库的列名不一致。名称不一致的时候，它就没有办法根据属性名去推断了，对吧？那你需要加一个 `@Column` 注解。如果名称一致，比如 `updateTime` 这种，你就不用去加了，它属于驼峰，它可以自动转换。所以大多数字段我们都不用加注解，也就是给 id 标记一下就行了。

另外还有一种比较特殊的，像库存和销量，其实它们并不属于商品表，它们属于库存表，我们把它放在这里呢，其实就是为了将来做数据封装。所以这两个字段属于非当前表的字段，我们加了一个 `@Transient` 注解，来标记它不属于表中的字段，将来它就会忽略掉了。

> **提示**：绝大多数字段其实是不用写注解的。驼峰命名的属性（`updateTime`）和下划线的列名（`update_time`）能自动对应上，只有名字真的对不上的时候才需要 `@Column`。

#### 封装 Redis 的写入删除，再实现三个方法

接下来我们就来实现这个过程。首先找到 Item 实体类，把主键字段上标一个 `@Id` 就可以了；对于那些不属于这张表的字段，可以加 `@Transient`，将来它就会忽略了。到这儿我们就把实体类准备好了。

下边还要去编写那个 handler。我们再来写一个 Canal 的类，比如叫 `ItemHandler`，实现 `EntryHandler` 接口，泛型就是刚刚我们写好的那个 Item 类，加 `@Component` 注册成一个 Bean，再加上 `@CanalTable("tb_item")` 声明表：

```java
@Component
@CanalTable("tb_item")
public class ItemHandler implements EntryHandler<Item> {

    // 本地 JVM 进程缓存：key 为 Long，value 为 Item
    // （就是我们之前写的那个缓存，记作 CACHE）

    @Autowired
    private CacheHandler cacheHandler;

    @Override
    public void insert(Item item) {
        // 本地缓存效率更高，先操作本地，再操作 Redis
        CACHE.put(item.getId(), item);
        cacheHandler.saveItem(item);
    }

    @Override
    public void update(Item item) {
        CACHE.put(item.getId(), item);
        cacheHandler.saveItem(item);
    }

    @Override
    public void delete(Item item) {
        CACHE.invalidate(item.getId());
        cacheHandler.deleteItemById(item.getId());
    }
}
```

> **易错点**：更新顺序别弄反了。本地缓存放在前面，因为本地缓存效率更高，先操作本地再操作 Redis。删除也是同样的道理，先操作本地的。

那这三个方法里头的 Redis 操作怎么写呢？这里我建议大家都把它给封装到我们之前写的那个 `CacheHandler` 里，那这样一来你就不需要在这里去写 Redis 的相关操作了，直接调 `CacheHandler` 对应的 API 就行了。这里边其实就俩，一个是写，一个是删。写的时候要传 item 对象；删的时候只要传 id 是不是就够了？我们只要根据 id 删就行了。

所以在 `CacheHandler` 里边我们可以去定义这么两个方法：

```java
public void saveItem(Item item) {
    try {
        // 调用 redisTemplate.opsForValue().set，把 item 序列化成 json 往里面写
        stringRedisTemplate.opsForValue()
                .set("item:" + item.getId(), objectMapper.writeValueAsString(item));
    } catch (JsonProcessingException e) {
        throw new RuntimeException(e);
    }
}

public void deleteItemById(Long id) {
    stringRedisTemplate.delete("item:" + id);
}
```

`opsForValue().set` 这行我们之前不是写过吗，就这一行，只不过这个 json 数据从何而来？是不是需要把 item 序列化成 json 往里面写。那我们可以把这个序列化的动作也给他拿过来，你看这样通过两步走，是不是就实现了这个数据写入了。这里有一个异常，我们可以把它给串起来，然后给他转换一下抛出就可以了。这样呢，一个新增逻辑就搞定了。

删除 likewise：`deleteItemById` 你只要给我传 id 就可以了。同样用 redisTemplate，然后这里直接调 delete，把 k 传进来就可以了，而这个 k 就是用 id 作为 k，拼接 id 就这样可以了。增和删的逻辑就封装好了。那么在刚才的监听的逻辑里，我们就可以直接使用了。

对于 JVM 的进程缓存来讲就更加简单了。JVM 进程缓存我们也是有的，就叫 CACHE，key 是 Long 值，值是 Item。拿到它以后，你就可以操作它进行缓存了：`put` 以 id 作为 key，item 本身作为值，是不是就写进去了。删除呢通过 `invalidate`，`invalidate` 就是清除的意思，同样是 `item.getId()`，基于 id 都清除，行了。

到这里，我们就把监听 Canal 的业务逻辑写完了。

好，回到 PPT，我们做一个简单的总结。这节课我们主要学习了 Canal 客户端的一个监听语法：

### 多级缓存全貌与数据同步

在课程最后，我们来总结一下我们这套多级缓存架构。

首先我们是有一个页面 `item.html`，放在了我们的 Nginx 这台服务器上，它的主要作用就是一个静态资源服务器和反向代理服务器。静态资源放在它上面，当用户通过浏览器来请求它的时候，它就可以把这个页面返回给用户。而用户的浏览器在渲染的时候发现缺少数据，就会发送 ajax 请求来查询数据。

Nginx 这台反向代理服务器呢，它不会去处理业务，它只是做反向代理，所以它会把请求代理给我们的 OpenResty 集群。当然了，我们在课程中只搭建了一台 OpenResty，事实上你搭建成集群无非就是多整两台机器，再多部署一下就好了。

那我们在 OpenResty 上不仅仅是做了集群，更重要的是还做了本地缓存。请求到达以后，想要去查询商品信息，它会优先从本地那个 shared dict（共享词典）上面去查一查，看有没有数据，如果有是不是就直接返回了。

但是呢，这个本地共享词典的数据它只能在当前 Nginx 进程内使用。所以如果我们真的部署成一个 OpenResty 集群，他们之间的内存是不共享的，这里我们就会面临一个问题：当我来查询 1001 的时候，如果说我在 8081 上做了缓存，那下一次负载均衡到 8082 的时候，可能就看不到数据了，对不对？

所以我们需要在 Nginx 反向代理到 OpenResty 的时候，也去针对商品的 id 去做路由，同一个 id 永远让他访问到同一个 OpenResty 实例，这样它的缓存就能一直生效。这里就需要有一个负载均衡的配置，这个配置需要把多个 OpenResty 的地址配上去，同时改变负载均衡算法，不再是轮询，而是基于请求的 url 地址做哈希。那这样将来 url 地址只要不变，请求的就永远是同一台；地址变了——其实或者讲 id 变了——那么就会换到另外一台。这部分我虽然没做，大家可以参考着去实现一下。

而在 OpenResty 查询本地缓存未命中的情况下，它会去查询 Redis 缓存，这里我们就会讲到 OpenResty 操作 Redis 的一些 api，然后查询缓存，如果命中了就直接返回了；如果未命中，那么它就会去查询我们的 Tomcat。同样 Tomcat 我们也做了集群，这里呢你也要做负载均衡，并且 Tomcat 内部也做了进程缓存，把商品信息缓存在本地。这个缓存也是不共享的——凡是这种不共享的缓存，你想要命中率高，你就必须得保证同一个商品永远访问到它。所以同样在这个地方，我们的 OpenResty 在向 Tomcat 做负载均衡的时候，也需要根据商品的 id 去做一个哈希运算做路由。同样是一个哈希，只不过请求的目标地址不再是我们的地址了，而是 Tomcat 的地址，这样同一个商品它肯定能落到同一个 Tomcat。

在 Tomcat 查询的时候，先查进程缓存，如果进程缓存命中了，那就直接返回；如果未命中，我们再去查数据库。

```text
 浏览器
   │  ① 打开页面 item.html
   ▼
 Nginx（静态资源服务器 + 反向代理，不处理业务）
   │  ② 页面缺数据，ajax 请求 /item/1001
   ▼
 OpenResty 集群   ← 按 id 哈希路由，同一个 id 永远落同一台
   │  ③ 先查本地 shared dict
   │        命中 → 直接返回
   │        未命中 ↓
   │  ④ 查 Redis
   │        命中 → 直接返回
   │        未命中 ↓
   ▼
 Tomcat 集群     ← 同样按 id 哈希路由
   │  ⑤ 先查 JVM 进程缓存
   │        命中 → 直接返回
   │        未命中 ↓
   ▼
 MySQL
```

读图：这就是查缓存的主链路。本地缓存一级、Redis 一级，加上 Tomcat 开的进程缓存，就形成了多级缓存的效果。大多数情况下都会走缓存，极少数情况下才会去走我们的数据库。

那多级缓存形成了以后，就会面临一个问题，就是数据同步的问题。比如说现在 MySQL 的数据发生了修改，那么我们的 Redis 数据、本地进程缓存和 Nginx 缓存啊都需要做同步。

这里同步呢，我们实现了有多种策略：

| 缓存层 | 同步策略 | 适合放什么数据 |
| --- | --- | --- |
| Nginx（OpenResty 本地缓存） | 超时同步：过期时间到期自动删除，下次再查就变成新数据了 | 更新频率较低的通用数据，比如商品当中大多数不怎么变的字段 |
| Redis + Tomcat 进程缓存 | Canal 监听 MySQL 变更，通知 Java 客户端立即更新 | 任意类型的数据，尤其是变化频率较高、实时性要求较强的数据 |

> **易错点**：变化频率较高的、对实时性要求较强的数据，就不建议放到 OpenResty 里面去做这种过期缓存了。

那对于 Redis 和 Tomcat 进程缓存，它们就可以放任意类型的数据了。这个时候要想更新、时效性比较强，怎么办呢？这里我们采用了这个 Canal 监听 MySQL 的这种方式。每当你对数据库做了修改，我们的 Canal 就能立即得到这个通知，然后呢，它再去通知我们编写好的这个 Java 客户端，而我们的客户端就会去立即更新 Redis、立即更新本地进程缓存，从而确保我们的缓存与数据库保持一致性好。

那这个就是我们整个多级缓存的一个架构了。

### 键值设计：让 key 优雅一点

下面我们进入第一章，Redis 的键值设计。这一章我们会分成三个小节：第一节我们来看一看 key 的设计，怎么样让一个 key 它看起来更加的优雅；第二节我们会了解一下 big key 它的常见问题以及对应的解决方案；最后我们再来看一看 value 的一个设计，怎么样才能选择一个更加适当的数据类型的 value。好，那我们下面呢现在就进入第一节，看一看 key 的一个设计。

#### 基本格式与三个好处

Redis 的 key 是可以自定义的，但是啊我建议大家遵循下面的几个约定。

首先要遵循基本的格式。这里可以看到 key 是以冒号隔开的几段，每一段包含的含义不同：第一部分呢，建议是使用业务名称；第二部分呢，建议是数据名称；最后一部分是数据的 id。然后呢，长度不要超过 44 个字节，而且呢不要包含特殊字符。

其实最后一点是非常好理解的，不仅仅是我们 Redis 里的 key，我们以前也讲过，你起名字的时候啊，最好的都不要包含特殊字符，避免出现一些 bug。这一点不用太多解释，只不过第一块名称的分段啊相对抽象一些，所以在这里我给大家举个例子。

比如说我们的登录页登录完了，我们肯定要保存用户信息，那这时候我们的 key 就可以这么来设计：

```text
login:user:10
```

首先第一段呢是 `login`，然后冒号再跟上 `user`，再冒号跟上 `10`。那这样就是以冒号分割的这种成段的形式了。在这一点，`login` 自然就是我们的业务名称，那么 `user` 呢对应的就是数据的名称，代表我将来存入的是用户信息，最后的 `10` 就是 id 了，存的是 10 号这个用户。好，这就是我们这个 key 的一个设计了，就遵循了前面这个格式。

那为什么要这样来设计呢？

**第一，可读性强。** 任何人只要了解我们的格式，看到这个 key 一目了然，就能知道你这个 key 的作用了呀——你不就是登录业务吗？里面存的用户信息，10 号用户，对不对？所以这种分段的设计，它的可读性就是很强。

**第二，避免 key 的冲突。** 在这里啊，我们没有直接使用用户的 id 作为 key。你想啊，在我们的开发当中，不同的业务如果说大家使用的是同一台 Redis 的话，那最终我们的数据都是存储在一起的。这个时候你的业务使用了用户 id 作为 key，那其他的业务是不是也有可能要使用用户 id 啊？这个时候大家如果都直接把 id 作为 key，是不是会产生冲突？数据有可能会互相覆盖，产生错乱。而现在呢我们不仅仅使用了 id，在前边还加上了业务名称、数据名称作为前缀，那这样不同业务都使用了用户 id 的情况下，是不会出现冲突啊；相同业务啊，不同数据类型的时候，哪怕 id 一样，是不是也不会冲突啊？从而避免了各种 key 冲突的可能性。

**第三，方便管理。** 在这里我们以冒号隔开，大家知道在 Redis 的桌面客户端里，我们发现当你以冒号隔开时，这些 key 就会出现层级结构。只要前缀一样的 key 啊，就会出现在同一个目录里。我们以前存储的一些 Redis key，所有跟登录有关的 k 都保存在这个 `login` 这个文件夹的下面，这是我们桌面客户端给我们展现出的这种层级的结构。那将来我要想统一管理跟登录有关的 key，我只需要在这里，比如想删除卡号就删掉了，所以就非常方便了。

```text
Redis 桌面客户端里看到的层级
└── login
    ├── login:user:10
    ├── login:user:11
    └── login:user:12
```

读图：前缀相同的 key 会被归到同一个目录下，按目录批量查看、批量删除就很容易。

#### 为什么长度要卡在 44 个字节

那么长度为什么要不超过 44 个字节呢？

首先第一点，长度越小，我们 key 占用的空间是不是越小啊。大家不要小看这十几个字节啊，你想想看，如果一个 key 我们能节省十几个字节，如果我有 1 亿个 key 呢，这节省的内存是不是相当可观了？所以说我们的 key 在设计的时候，在满足了可读性、避免 key 冲突的前提下，应该是能有多短就尽可能有多短。你看这里的 `user` 我们是不是可以简写为 `u`，代表用户的意思是不是也没问题？或者 `uid` 也可以。也就是说这些单词有的时候我们是可以做到简写的，尽可能缩短它的长度，节省内存空间。

第二呢，是因为字符编码的问题。我们的 key 啊其实底层都是 string 类型，但是 string 类型它的底层的编码呀，又分了三种：`int`、`embstr`、`raw`。

那这里的 `int` 呢，是我们这个字符串的内容它如果全都是数值的情况下，这个时候它就会采用 int 编码，把字符串啊直接当成一个数字去进行存储了。这样呢，占用的空间呀就会小很多。

而如果你不是数值，那这个时候我们的 string 类型去存储的时候，就会采用这种 `embstr` 的模式。这种模式的话呢，我们在后期讲解底层数据结构的时候再和大家聊，现在你只要知道它是一种特殊的编码方式就行了。

而 `embstr` 和 `raw` 这两种在存储 SDS 的时候不一样。`embstr` 呢它在存储的时候啊，是一段连续空间，也就是说它的编码会更加紧凑，占用的内存量会更小一点。但是呢它有一个前提，就是你这个字符串它的长度必须小于 44 个字节。如果超过了 44 个字节，那么它就会转为使用这个 `raw` 模式进行存储啊。

在 `raw` 模式当中啊，它的内存空间不是连续的，而是采用了一个指针指向了另外的一段空间，在这个空间里去存储这个 SDS 的内容，也就是字符串的内容。那这样一来呢，空间不连续，访问的时候性能肯定会有受到一定的影响，还有可能会产生一些内存的碎片。所以呢它的内存占用了就会比 `embstr` 要高一点啊。

> **结论**：为了提高内存的使用率、减少这种内存碎片，我们推荐大家使用 `embstr` 的编码。但是呢这个不是我们能控制的，对不对？我们能控制的是什么呢？就是把字符串的长度缩小到 44 个字节以内，它自然就会使用 `embstr` 的编码了。

那下边我们给大家演示一下这三种编码。我们打开控制台，在这个地方呢我们随便来一个，比如说 `set` 一个 `number` 叫 `123`：

```bash
set number 123
type number
object encoding number
```

`123` 这个其实就是一个数值，对不对？这时候我们首先通过 `type` 来看一下，它确实是 string 类型吧。但是我们通过另外一个命令叫 `object encoding`，这个命令可以帮我们看一下某一个 key 的底层编码，你会发现也是 int 啊，数值编码的，所以它的存储空间是占用非常小的。

那我们再来试一个普通字符串，比如说 `set` 一个 `name`，我的名字叫 jack：

```bash
set name jack
object encoding name
```

这个时候我们再来看一下 `object encoding name`，你发现它的底层是 `embstr` 啊。那它的类型是 string 类型，编码是 `embstr`。

好，那这个时候我们把这个 `name` 给加长一点，长到多少呢？我们刚才说了，长到 44 个字节：

```bash
# 继续给 name 加长，长到正好 44 个字节
object encoding name
```

先看 type 是不是还是 string，再看它的 encoding，是不是还是 `embstr`？刚好 44 个字节吧。好，再加一个字节：

```bash
# 再加一个字节，凑够 45 个字节
object encoding name
```

注意了，走 45 个字节了。现在我们再来看一下它的 encoding，是不是变成 `raw` 了？raw 模式啊。

> **易错点**：所以说 44 个字节是它 `embstr` 的一个上限。当然了，这个是因为我们当前使用的 Redis 版本是六点多的版本。如果你们公司里使用的 Redis 的版本是低于四点的、就是三点多的 Redis 啊，它的这个 `embstr` 的限制是 39 个字节。所以这里大家要注意一下，它的上限是不一样的。我们现在是 44 个字节。

好，那这就是我们 key 设计啊，大家需要注意的一些事情了，还有就是它的一个设计的原理。行吧，那咱们这节课的内容就到这里。
