## 跟着黑马点评，把 Redis 用进真实业务
> 对应块：BLK06 | 覆盖分集：P24-P27 | 块标题（分集名）：《实战篇-01.Redis企业实战课程介绍》

### 会增删改查，不等于会用 Redis

上一章我们把 Redis 各种数据结构过了一遍，也把对应的常用命令和 Spring Data Redis 提供的 API 学了一遍。现在回头看，你能对 Redis 做数据的增删改查了。

但问题也就来了：**到底该在哪里应用 Redis？在企业开发过程中又该怎么用它？**

这里边有各种各样的姿势等着我们去解锁。正所谓光说不练假把式，只讲原理是练不出真本事的。为了让大家能快速解锁 Redis 企业应用的各种姿势，我们换一种学法——用一个案例把大家带着走一遍。

这个案例叫**黑马点评**，你可以理解成大家平常用到的**大众点评**，它是一个以社交平台为核心的**轻电商项目**。

> **提示**：为什么偏偏选它？因为社交类项目里 Redis 的应用场景非常丰富，同时里面还塞进了一些电商业务场景——社交加电商的组合，能把 Redis 的各种数据结构、各种应用姿势玩了个遍。跟着它走一遍，Redis 的企业应用姿势基本就解锁了。

### 五个业务点，把 Redis 的各种姿势走一遍

黑马点评的业务我们分几块来做，每一块都对应一批 Redis 的实战场景。

#### 短信登录

短信登录大家都不陌生，现在的 App 基本都是这种模式。它的核心会包含两件事：**短信验证码的保存**，还有**登录信息的保存**。这两样东西往哪儿放，后面你会看到 Redis 天生就是干这个的。

#### 商户查询缓存

点评网站一定会有各种各样的商户信息，这些信息的查询建立缓存，就可以大大提高效率。

这部分的重点不是"缓存是个啥"，而是**企业缓存使用的各种技巧**，以及缓存使用过程中产生的各种问题——比如缓存雪崩、穿透、击穿等等，以及它们的解决方案。

而且我们当然不会只讲原理，会带着大家写代码，把各种解决方案一个个实现出来。

#### 达人探店

这个功能可以理解成一个博客。比如我们去了哪儿吃了饭，或者玩儿了，在那边拍了一些照片、写了一些感想，就以这种博客的形式把它发出来。其他的用户可以给你点赞，也可以给你做一些评论。

这个时候自然就会出现**点赞列表**、**点赞排行榜**等等这些功能。而这两部分功能，恰好可以用到 List、Sorted Set 这样的结构。

通过这一部分，我们会重点介绍 **List 和 Sorted Set 实现排行榜的差异**，以及具体的应用场景——什么情况下该用哪一种。

#### 优惠券秒杀

虽然说是一个社交型的网站，但它也会有一些轻电商业务，优惠券就是其中之一。

点评网站呢，我们不是卖一些商品的，**我们卖的是券**。像什么 4.5 折、5 折之类的这种券，一些特价券往往就要去做秒杀。

秒杀可以说是电商的核心业务了，只要是聊电商就离不开秒杀，而秒杀一定离不开 Redis。这里面自然就会用到 Redis 的计数器、Lua 脚本、分布式锁、阻塞队列等等各种各样的功能，含金量非常的大。

#### 好友关注

社交网站肯定离不开的就是关注，包括互相关注、取关、共同关注等等这样的功能。它会用到的就是 Redis 里的 Set 集合这样的结构。

而且这个功能跟我们的地理坐标有关。Redis 里边提供了 GEO 这样的地理数据结构，可以解决这种根据地理坐标进行搜索的功能。

我们在 Redis 入门当中没有学习这种数据结构，放到实战里面去讲——因为它贴合实际，大家理解起来会更容易。

#### 用户签到与在线统计

我们还会学习用户签到，以及像在线统计这样一些统计类型的业务功能。

这两部分同样会用到一些比较特殊的数据结构——**BitMap** 和 **HyperLogLog**。

> **提示**：为什么要用这些？因为随着用户规模越来越多、越来越庞大，比如说你达到数以千万计、数以亿计的用户。像用户签到功能，如果说我们把每一天登录的用户信息都给它记录下来，那产生的数据量是非常恐怖的。怎么解决这个问题？BitMap 或者 HyperLogLog 这样的功能就可以实现一个基本的统计功能，而且它所占用的内存非常小。所以这两个特殊的数据结构，我们也放在实战阶段去学习，大家理解起来会更加方便一点。

### 先把环境搭起来

短信登录这个功能我们会分成四个小节来实现。第一个部分，先去导入黑马点评的项目——主要是它里面的一些 SQL 文件和一些基础代码，用来搭建咱们的项目运行环境，搭好之后我们就可以编写自己的功能了。后面几节再分析登录功能存在的问题，最终利用 Redis 解决它，并且实现一下**集群模式**下的登录功能。

#### 单体项目，前后端分离

先说明一下，我们这个项目**不会采用微服务的方式**。因为我们的核心是学习 Redis 的用法，我们不想把 Java 代码搞得太复杂，影响大家的注意力和学习效果。如果大家对微服务有兴趣，可以去 B 站上搜索"史上最全的 Spring Cloud 教程"，也是我讲的，可以去看一看。

在这儿我们就是一个单体的项目了。尽管是单体项目，但我们采用的结构是**前后端分离**的模式：我们会把前端与后端分别去部署，而不是全部揉在一起往它们开始那儿一扔。

后端将来肯定是部署在 Tomcat 上的，当然现在我们开发阶段用 IDEA 把项目打开，去完成后续的开发和部署就 OK 了。而前端呢，我们会把它部署在 Nginx 服务器上——这也是现在企业开发的一个标准做法。

```text
     移动端 / PC 端浏览器
              │
              │  ① 先向 Nginx 请求页面，拿到静态资源
              ▼
        Nginx（端口 8080）   ← 前端代码 + 静态资源
              │
              │  ② 页面通过 Ajax 向服务端请求数据
              ▼
      后端服务 Tomcat（8081）
              │
        ┌─────┴─────┐
        ▼           ▼
    MySQL 集群   Redis 集群
        │           │
        └─────┬─────┘
              │  ③ 查询到的数据返回给前端，前端完成渲染
              ▼
     移动端 / PC 端浏览器
```

读图说明：用户第一次访问时拿到的是 Nginx 里的静态页面，真正的数据是页面渲染完之后再通过 Ajax 回来取的，数据可能来自 MySQL 集群，也可能来自 Redis 集群。

不过呢，尽管我们是一个单体式的项目，将来还是要考虑到整个项目的并发能力的。所以我们的项目一定要具备**水平扩展**的能力。

什么意思呢？就是说我们这个项目部署到 Tomcat 上以后，将来如果单台 Tomcat 扛不住压力，我们还可以做一个水平的扩展，形成一个集群负载均衡的集群，在多台 Tomcat 上都来部署我们的代码。

```text
             集群入口 / 负载均衡
           ┌────────┴────────┐
           ▼                 ▼
      Tomcat-1           Tomcat-2   ···   Tomcat-N
           │                 │               │
           └────────┬────────┴───────────────┘
                    ▼
          MySQL 集群  /  Redis 集群

  一旦步入集群，将来就会存在集群间的数据共享问题
```

读图说明：多台 Tomcat 部署同一份代码，压力扛不住就继续加机器；但一旦成了集群，"用户登录信息存在哪一台"这类数据共享问题就冒出来了。这些问题的解决方案，我们会在后面讲。

所以将来我们部署的时候，就要分成两部分了：一部分是后端，一部分是前端。

#### 后端：从 IDEA 里跑起来

后端是黑马点评这个项目，我已经在开源资料里给大家准备好了源码，是一个**半成品**——我们后续还要继续做二次开发。

所以你需要把它复制到你的 IDEA 的工作空间，然后用 IDEA 打开它，后续继续对它做开发就行了。

> **提示**：这里有个习惯问题。很多同学从网上下载到我们这个东西以后，随便扔到一个地方就开始用 IDEA 打开、开发了，这其实是不好的习惯。你最好在电脑上专门准备一个文件夹，用来放你 IDEA 里面的各种各样的代码，这样管理起来也很方便。另外这个目录里最好不要出现**中文、特殊字符**，避免出现一些莫名其妙的问题。

先看它的 `pom.xml`，这里边就是项目的依赖：

| 依赖 | 干什么用 |
| --- | --- |
| `spring-data-redis` + `commons-pool2` | 入门当中已经讲过的 Redis 基本 API 和它的连接池 |
| 外部 starter | 外部项目必备的 |
| MySQL 依赖 | 数据库访问 |
| Lombok | 提供一些方便的注解 |
| 单元测试 | — |
| MyBatis-Plus | 实现单表增删改查的简化，非常好用；没用过的同学也不用担心，百度一下，使用方法非常简单 |
| Hutool 工具包 | 各种各样的一些工具类：JSON 处理的、字符串工具类、数字工具类、日期工具类等等，简直是个万能的包，很好用 |

再看代码结构。`resources` 这里边有两部分：一部分是 mapper 文件，这里我简单写了两个；其实我们这里的每一个表结构都会对应一个实体类，一个对应的实体类和对应的 Mapper，那有 Mapper 自然就会对应到 Mapper 的 XML 文件，用来编写一些复杂的业务 SQL。因为我们用了 MyBatis-Plus，所以很多单表增删改查我们其实就不用写了，对于一些复杂的才需要 mapper 文件。

再往下，`yml` 文件里边是整个项目的配置：

- **服务端口**采用 `8081`；
- **数据库连接池配置**：数据库名字叫黑马点评，用户名密码是 `root` / `123456`；如果你跟我不一样，切记一定要去修改；

### 短信登录到底是怎么一步步走完的

环境已经搭好了，我们自然就要去完成功能了。

登录大家不陌生，但是短信登录啊，可能很多同学并没有做过。它必然包括短信的发送，然后才是基于短信验证码的登录，最后是对登录状态的一个校验。所以在这里我们会分成三块来给大家讲解这个登录的流程，然后再去动手写代码。

#### 发送短信验证码：先校验，再保存，最后才发

当用户要去利用手机号做短信登录的时候，肯定得先给他发一个验证码过去。所以用户会提交自己的手机号码，我们的服务端接收到这个手机号以后要干什么？

**别着急去发。** 首先我们要去验证一下用户的手机号是不是合法的——他如果填个错的，你怎么发呢？先校验，校验成功了以后我们再去发；如果校验失败，那二话不说是不是让他重来。

校验成功，校验通过了该干嘛呢？发验证码之前一定要先有一个验证码吧？所以我们要先去**生成验证码**。

生成验证码以后呢，我们就可以发送了吗？

**不要着急。** 我们想啊，短信验证码发送完了，将来的目的是为了让用户去做登录；我们是不是得校验验证码呀？所以说呀，你需要把这个验证码保存在本地，将来他在做登录的时候，你才能做验证。

所以说在这里啊，我们要对验证码做个保存。而后你就可以放心大胆地给用户发送短信验证码了。

> **结论**：整条发送流程的顺序是死的——**校验手机号 → 生成验证码 → 保存验证码 → 发送验证码**。这个顺序里最容易搞错的就是"保存"和"发送"这两步——先保存，再发送。反过来的话，用户在你保存之前就提交了验证码，你手里是空的。

#### 校验验证码，顺带把注册也做了

用户收到这个验证码以后，是不是就可以去做登录或者注册了？又该怎么做呢？

首先第一步，他肯定要把自己的手机号和收到的验证码提交到后台。那后台就要去验证他提交的这两个数据了。首先呢要验证的是它的验证码——怎么验证呢？把他提交的这个验证码，跟上一步保存的那个验证码做一个比较。

比较完有两种结果：

- **不一样**：证明验证码是错误的，那肯定要拒绝他，让他重来；
- **一样**：说明验证码填写的是正确的。

但能证明说他就可以登录了吗？**不行**，因为手机号是不是还没有验证啊。

那怎么验证手机号呢？我们是不是可以去数据库里查呀。所以下一步要做的事情，就是**根据手机号去查询用户的信息**。

根据手机号去查询用户信息，还会得到两种情况：有可能查到，有可能没查到。所以这里我们要对查询到的用户做个判断，看他是不是存在的。

- **不存在**：证明这个人是第一次来访问，数据库里没有这个手机号。那这个时候我们其实要干什么呢？是要去给他注册成一个新用户。也就是说，**登录和注册其实是在一个流程里完成的**；
- **存在**：那很好办，证明他这个手机号也是正确的，是不是就可以去做登录了。

可以登录了之后干什么呢？**登录一定要保存用户信息**，对不对？

所以流程走到这里，如果这个用户不存在，我们就创建一个全新的用户，把手机号之类的基本信息填充一下，把它写入到数据库当中。那这样一来这个用户是不是就存在了呀——**等于是一种快捷注册**。到这里，短信验证码的登录和注册功能就结束了，登录和注册合而为一了。

#### 登录状态怎么校验

最后，如果用户真的登录成功了，那以后他访问我们的时候，访问一些关键的接口的时候，是不是都需要去校验登录状态啊？

那将来用户来访问我们的时候，怎么继续做这个校验呢？是**基于 Cookie 的**，保存在浏览器的 Cookie 当中。所以说当用户来访问我们的时候，他一定会携带上自己的 session id。

那这个时候，我们只需要判断一下这个 session 有没有用户，就能够知道他是否登录了：

- 如果判断发现没有用户，那我是不是等于直接就拦截他的请求就行了啊；
- 如果判断发现有用户，说明这个哥们儿是曾经登录过的，那放行呗，他登过肯定是要放行的。

但是大家思考一下啊，我这个登录刚才的校验不能白校验。因为在后续的业务当中，他一定会用到当前登录的这个用户的信息。既然如此，我为什么不把这个用户的信息给它缓存起来呢，方便后续的业务来使用它。

缓存哪里呢？我们一般情况下会把登录用户缓存在 **ThreadLocal** 当中。那这样一来，后续的业务就可以直接从 ThreadLocal 里获取用户。

ThreadLocal 大家以前有没有听说过呢？它其实就是一个线程域对象。在我们的业务当中，每一个请求到达服务端，它都会是一个独立的线程。如果说我们没有用 ThreadLocal，而是直接把这个用户保存到一个本地变量，那就可能会出现**多线程并发修改的一个安全问题**。

而 ThreadLocal 呢，它会将这个数据保存在每一个线程的内部，在线程内部创建一个 Map 来保存。那这样一来，每个线程都有自己独立的存储空间，每一个请求来了以后是不是都会有自己的空间？相互之间没有干扰。那然后我们再去放行，后续的所有的业务都可以从这里面去取出自己的用户信息。

这就是基于 session 的一个登录状态的校验了。

```text
            浏览器
              │  发起请求，自动携带 Cookie 中的 session id
              ▼
        服务端校验登录状态
              │
     ┌────────┴─────────┐
     ▼                  ▼
 查不到用户          查得到用户
     │                  │
     ▼                  ├──► 放行
 直接拦截请求            │
 （不许访问）             └──► 把用户信息缓存进 ThreadLocal
                                │
                        每个线程内部一个独立 Map
                        线程之间互不干扰
                                │
                                ▼
                    后续业务直接从 ThreadLocal
                    取出当前登录用户的信息
```

读图说明：session id 解决的是"你是谁"，ThreadLocal 解决的是"这条业务链路上怎么随手拿到你"——后者正是登录校验不能白做的原因。

以上这三个流程我们说完了。下一节课，我们就基于这个流程动手实践，来实现这个登录功能。

#### 五个步骤依次落地

业务流程我们上节课已经分析过了，落到代码上就是五个步骤：**校验手机号、生成验证码、保存验证码、发送验证码，最后返回结果**。

**第一步，校验手机号。** 校验手机号呢是比较简单的，其实就是看一下这个手机号它是否符合手机号的那个规范，13 开头、什么什么之类的，对吧。

这个校验呢一般是要用正则表达式去做的。不过这里呢大家不需要自己去写正则表达式，因为我给大家提供的这个 `utils` 包下已经准备好了正则表达式的一个工具了：一个叫 `RegexPatterns`，里面定义了手机号码、邮箱啊等等各种各样的一些正则表达式，你看这个手机正则表达式写的是挺专业的；对的，还有一个 `RegexUtils`，它呢其实就是对正则针对手机号码的一个校验。

你看这个方法叫 `isPhoneInvalid`，什么意思呢？是否是无效的数据格式啊，**它是取反向的一个校验**。

那我们回到 service 里，直接去调用 `RegexUtils.isPhoneInvalid(phone)`，问它是否无效，然后做一个判断：`if` 成立，就代表是无效的手机号码，那我肯定要报错。报错怎么报？直接 `return` 就行了，返回 `Result.error("手机号格式错误")`，这就来一个 fail 告诉他说手机号格式错误就行了。

这里呢，`Result` 是我们自己定义的一个对象，它可以代表一个业务结果：里边有 `success` 标识，代表是否成功；还有 `errorMsg`，如果异常的话返回它；还有 `object`，成功的时候返回它。所以这是一个通用的结果对象，里面有一个静态方法叫 `ok()`，代表是成功。

**第二步，生成验证码。** 手机号正确了，我们就可以给他发验证码了，但发得先生成，对不对。

生成验证码一般是什么呢？一般是一个长度为六位的一个数字。这块呢我们可以用一个随机生成器来生成。这块我们要用到之前引入的那个 Hutool 工具类，它里面有个叫 `RandomUtil` 的。Hutool 简直就是个百宝箱，里边啥都有，它里面可以帮我们随机生成——那么 `randomNumbers` 就是随机数字，我们可以来一个比如说 6，那代表生成的就是一个六位的随机数字，用它来做一个验证码，是不是非常的方便呀。

大家还是要善于去利用这种第三方的工具包啊，确实能给我们节省很多的时间。

**第三步，保存验证码。** 验证码有了，这个就简单了，大家应该都还有印象吧，前面学过的那个写法是不是就可以了。然后呢这块我们给它起个名字叫 `code`，然后就把这个 `code` 保存起来。

为什么要先保存呢？因为将来用户登录的时候，我们是不是就可以利用保存起来的这个验证码进行校验了。所以呢，**要先保存，然后再发送**。

**第四步，发送验证码。** 这个呢我们就暂时先不做了。为什么呢？因为发送验证码你要去调用第三方的一些平台，比如说阿里云的这种短信平台去实现，那么实现起来呢稍微会有一些复杂，而那不是我们讲解的重点。所以呢这块我们就跳过了，我们就写个假的。

那怎么写假的呢？我们来个日志记录一下，就假设说我们发成功了：`log.debug("发送短信验证码成功：{}", code)`，记一下发送短信验证码成功，把这个 `code` 也给它记录下来，就好了。

> **易错点**：这个地方大家注意，我们是**模拟的，不是真的发**。那么你在真实开发中，你替换一下就 OK 了。一般呢，发送验证码在公司里都会有一个独立的服务去做，你只需要调那个服务就行了。

**第五步，返回结果。** 他返回值呢没什么返回值啊，所以说我们可以不用去处理，直接返回 `OK` 就行了，返回空就行了。这里调用 `Result` 里面那个静态方法 `ok()` 来代表成功，因为这里没有返回值，就不用返回具体的东西了。

好，这就是整体的流程。

## 用短信验证码登录：注册即登录，再到 Redis 接管 Session
> 对应块：BLK07 | 覆盖分集：P28-P32 | 块标题（分集名）：《实战篇-05.短信登录-实现短信验证码登录和注册》

上一节课我们已经把短信验证码发到用户手机上了。用户收到短信，验证码一填，点登录——按理说，登录这件事就该在这儿收尾。可现实是：点完登录，页面一闪，又弹回登录页，还是那个"你没登录"的样子。

问题出在哪？这一整块内容就是从这儿开始，一步步把这个窟窿补上的，最后再把整个登录态从单机内存搬到 Redis 里去。我们先把请求发出去看看。

### 登录接口长什么样

先别急着写代码，回到浏览器确认一下请求到底长什么样。随便输一个验证码，比如 `123321`，点登录。

第一件事就会拦住你：提示先确认已阅读用户协议，得先勾上才能继续。这不是什么技术细节，就是前端的一个校验，勾完再点一次登录——接口提示"功能未完成"。注意，重点不是这个提示，而是**请求确实发出去了**。点开 Network 看这条请求：

- 请求方式 `POST`
- 路径 `/user/login`
- 参数不再是 URL 上那种 `a=1&b=2` 的拼接形式了，而是一个 JSON 风格的请求体
- 请求体里就两个字段：`code` 和 `phone`

跟我们之前在 PPT 上看到的一模一样。到这一步，接口的形状算是确认下来了。

回到代码里，`UserController` 中我们上节课实现的是 `sendCode`，这节课来实现登录 `login`。方法上的东西跟 `sendCode` 一样，路径 `/user/login`、方式 `POST`，唯独特殊在一个地方：

```java
@PostMapping("/login")
public Result login(@RequestBody UserLoginForm loginForm) {
    return userService.login(loginForm);
}
```

这里有个 `@RequestBody`。前端提交的是 JSON 风格的数据，JSON 要在后端被接收，靠的就是这个注解——没有它，后端拿到的是一个空的请求体。加上它之后，Spring 会自动把 JSON 反序列化成一个 `UserLoginForm` 对象。

点进 `UserLoginForm` 看一看，里面有三个字段：`phone`、`code`，还有一个 `password`。密码是怎么回事？我们回浏览器看一眼就明白了——登录框那里除了"验证码登录"，还有"密码登录"这个选项。也就是说这个表单既支持手机号登录，也支持密码登录，两种都支持。

> **提示**：我们这次只用手机号登录模式，所以 `password` 不用管，只关心 `phone` 和 `code` 两个参数。

还有一个地方值得注意：`login` 方法的参数里其实是**两部分**。一部分是"表单参数"，另一部分是"请求参数"。这个区分后面会一直用得上——取验证码的时候用的是 session，那是表单参数；取 `phone` 和 `code` 的时候是从 `loginForm` 里拿的，那是请求参数。

至于业务逻辑，我们不放 Controller 里做，还是老规矩，扔给 service：

```java
return userService.login(loginForm);
```

参数原样传过去，Controller 这边就到头了。

### 登录注册二合一：把流程写进注释

`UserServiceImpl` 里 `login` 方法还没实现，先用 IDE 生成，然后我们回头看之前定义的那个流程图——**短信验证码登录其实是"登录"和"注册"两部分合在一起的**。

为什么？因为当用户输入手机号，我们验证发现这个手机号在数据库里压根不存在，那就立即给他创建一个用户。这样的用户就不用再走一遍繁琐的注册流程了，注册是登录的副产品。

所以这块是登录注册二合一。我们按这个流程先把注释写出来，写完注释，代码基本就自己长出来了：

**第一步，校验手机号和验证码。**

> **易错点**：这里为什么要把手机号再校验一遍？发送短信的时候不是已经校验过一次了吗？
>
> 这是两个不同的请求，每一个请求都要做独立的校验。他发短信的时候填了一个正确的手机号，但登录的时候填了一个错的，有没有可能？所以这个手机号格式，我们一定要再校验一次。

手机号校验我们前面已经做过一遍了，这里就不废话了——直接复制过来就行。当然，如果你觉得这个动作太麻烦，用一些基于注解的校验框插件来做校验也是没问题的。

**第二步，校验验证码。** 这个比手机号复杂一点，需要拿缓存里的验证码跟表单提交的验证码做一个比较。

**第三步，如果验证码一致，拿手机号去数据库里查对应的用户。**

**第四步，判断用户是否存在。** 用户有两种情况——不存在，或者存在：

- 不存在：创建全新的用户，保存到用户表
- 存在：那就简单了，用现成的

> **提示**：仔细看流程图会注意到，不存在这一条分支是个"支线"，而且创建完用户之后还要写回数据库。存在这一条，虽然不用创建，但用户本来就有一条记录。也就是说，**不管存在还是不存在，最终都要拿到一个 `user` 对象**。所以 `createUserWithPhone` 这个方法不能"创建完就完了"，必须把创建好的用户返回给我。这样不管走哪个分支，`user` 都确保有值。

走到这一步，登录其实就完成了。流程图从这头到那头一条直线走下来，旁边的分支我们把它定义到方法里面去了，主流程会清晰很多。

### 校验手机号与验证码：魔法值和反向判断

验证码校验的代码，我们把它一段段拆开看。

先是取缓存里的验证码，从 session 里取：

```java
String cacheCode = (String) request.getSession().getAttribute(CACHE_CODE);
```

看到 `CACHE_CODE` 这个常量名了没有？

> **易错点**：这里我故意提醒一下。像 `getAttribute` 里面的 `"code"` 这样的字符串常量，最好不要像我第一遍那样直接把字面量写进去。这种写在代码里到处散落的字符串常量，其实有个名字，叫**魔法值**。正确做法是把它定义成一个常量值放到一个专门的地方去。我们给它起名叫 `CACHE_CODE`，代表这是缓存起来的 code。

接着从 `loginForm` 里取出前端提交的 `code`，然后两者做比较。

这里有一个关键的分支写法，先判断缓存里的验证码是否为 `null`：

```java
if (cacheCode == null) {
    // 从来没发过验证码，或者验证码已经过期了
    return Result.error("验证码无效，请重新获取");
}
```

如果等于 `null`，就证明这个手机号**从来没有发过验证码，或者验证码已经过期了**——无论哪一种，都是错，直接报错。

不为 `null` 的话，用 `cacheCode.toString().equals(code)` 做比较。两者一致，放行；不一致，报错。

```java
if (!cacheCode.toString().equals(code)) {
    return Result.error("验证码错误");
}
```

> **提示**：注意上面这两段的写法都是"反过来"的——先写错误的情况直接 `return` 掉，剩下的才是正常流程。为什么要这么写？
>
> 因为这种校验我们不需要 if 嵌套。假如全用正向校验：外层 if 判断不为 null，里面再 if 判断一致，一致里面还要再 if 做下一步，越套越深，最后形成那种"菱形"的代码，一层一层越来越深。这种反向的写法可以避免 if 嵌套越来越深，看起来会更优雅一些。

验证码校验完毕，意味着什么？意味着手机号格式是对的，而且这个验证码确实是你自己申请的。全部验证通过，下一步就是看你这个手机号对应的用户是谁了。

### 查用户：MyBatis-Plus 的条件构造

去哪儿查？当然是数据库。

我们先打开 `tb__user` 表看一眼。这张表存的就是用户的基本字段：手机号码、密码、昵称、头像、时间。这里最关键的就是手机号——因为我们就是根据手机号登录的，而手机号是唯一的，所以字段下面加了 `unique` 索引。也就是说，根据手机号查，**肯定只能查到一个，要么没有**。

如果手写 SQL，其实非常简单：

```sql
SELECT * FROM tb__user WHERE phone = ?
```

但我们现在不需要自己写这条 SQL，因为项目里用的是 MyBatis-Plus。很多同学可能没用过，不要紧，我说一下它能干什么：它可以非常简单地帮我们实现单表增删改查。

具体怎么用？看 `UserService` 里的调用——这个方法之所以能直接用，是因为 `UserService` 继承的 `IService` 是 MyBatis-Plus 提供的。我们还告诉了它我们的实体类是什么、我们的 Mapper 是什么，它就可以自动帮我们去查了。

```java
User user = userService.lambdaQuery()
        .eq(User::getPhone, loginForm.getPhone())
        .one();
```

拆开看这三步：

- `lambdaQuery()` 等价于前面那半句 `SELECT * FROM tb__user`，它之所以知道表名叫 `tb__user`，是因为实体类上有 `@TableName` 注解
- 紧跟着写条件就行了。`.eq(...)` 就是等值条件——字段 `phone` 等于什么值，值就是我们从表单里取出来的那个手机号。方法后面有一大堆各种条件，都是 SQL 语句对应的那些关键字
- 返回值要看查几个：查多个返回 `list`，得到的是一个集合；查一个就用 `one`，返回值就是一个 `user`

就这么简单。到这一步，我们已经根据手机号码查到用户了。MyBatis-Plus 非常好用。

### 创建新用户：真正要填的只有两个字段

查完了，用户还不一定有值——有可能是新用户嘛。所以这里还要做一个判断。

```java
if (user == null) {
    user = createUserWithPhone(loginForm.getPhone());
}
```

创建新用户该怎么创建？要注意，用户这儿只提供了手机号和验证码，**验证码不是用户的属性，手机号才是**。那我在这儿要创建，是不是等于凭空创造？

我们回头看看整个 `User` 类，最关键的就是 `phone`，其他字段——密码什么的都不重要。人家刚创建，密码是不是可以置空？他后面可以自己配。头像没有，就给个默认头像。时间不用管。昵称没有怎么办？给他来个随机的就行了。

> **结论**：所以这里真正要填的就是 `phone` 和一个随机的昵称，其他不用管。

那就把它定义成一个方法 `createUserWithPhone`，根据手机号创建用户，把 `phone` 给他，剩下的事在这个方法里做。方法很简单，直接 `new` 一个出来：

```java
private User createUserWithPhone(String phone) {
    User user = new User();
    user.setPhone(phone);
    user.setNickName(SystemConstants.USER_NAME_PREFIX + RandomUtil.randomString(10));
    userMapper.insert(user);
    return user;
}
```

随机昵称怎么生成？可以用我们之前讲过的 `RandomUtil`，随机来一个字符串，长度你自己定义，十位二十位都行。

但是——纯随机的用户名看起来很混乱。所以最好给它加一个统一的前缀，拼一下，看起来更统一一点。比如叫 `user`，就是"随机用户名"。

> **提示**：事实上你去注册一些网站，比如京东之类的，如果直接用手机号注册，他都会给你生成一个有规律的随机用户名，大众点评之类的也都是这样。我们这里其实就是有一个统一的前缀。当然这个前缀你叫 `user` 可以，叫"黑马点评"是不是也可以，随意。

另外前缀这么写在代码里也不太优雅，最好也给他定义成一个常量。我们工程里其实有一个 `SystemConstants` 系统常量类，已经定义好了前缀常量，直接 `Ctrl+C`、`Ctrl+V` 过来即可。你看这个代码的逼格是不是就上了一个档次了，优雅、专业。

保存用户又要用 MyBatis-Plus 提供的功能了，这里有个方法叫 `save`，你把 `user` 给它，它就帮你保存，然后把保存好的用户返回就行。

回到上面那个 `if`：`user` 现在不管是从数据库查到的，还是临时创建的，都有值了。到这里登录其实就完成了。

> **提示**：有同学会问，这里不需要返回一个登录凭证吗？答案是不需要。因为你访问 Tomcat 的时候，这个 id 就已经自动写到你的 cookie 当中了，你以后请求会带着这个 id 过来。所以这里不需要返回登录凭证。
>
> 先记住这句话——等到最后我们把登录态搬到 Redis 里的时候，它会不成立。

### 登录成功了，页面为什么还显示未登录

代码写完了，重启服务，回到浏览器实测一遍。

输入刚才那个手机号 `13456789001`，点发送验证码。我们这里是假发，所以直接把这个码从控制台 copy 出来粘回浏览器，勾上用户协议，点登录。

一看列表接口：成功，一闪而过。但是——**怎么又弹回来了？**

先确认一下服务端的日志：它确实做了一次查询，查的结果是零，用户没查到；没查到就新增一个用户。我们去数据库里看 `tb__user`，刷新，最下边确实多了一个全新的用户。说明流程是正常的，登录应该也是 OK 的。

那为什么浏览器又跳回登录页？**因为我们还没有做登录校验功能。**

我们现在只做了两件事：发送短信验证码、短信登录和注册。校验功能还没做。所以这里要想让它成功，是不是还得去做登录校验？这个其实就是一个动作。

刚才那一下应该是返回了一个异常的信息。我们下节课就来实现登录校验。到这儿，登录流程本身算是完成了。

### 登录校验：拦截器与 ThreadLocal 的配合

#### 用拦截器统一做校验

前面两节课我们实现了发送短信验证码和基于短信验证码登录。可页面依然认为我们没有登录，为什么？因为登录校验没做。这节课就来做。

登录校验本质上就是这样的一个请求：`/user/me`，它就是来查询当前登录的用户信息。如果它能给你返回用户，登录校验就算是成功了。

这个请求会带上 cookie，因为前面讲过登录凭证——你看这幅图，前面这个 cookie 后面跟着的 `JSESSIONID`，这不正是你的登录凭证吗？如果带着这个信息到了服务端，服务端只需要判断一下这个用户是否存在，有就证明登录成功，把用户返回给前端，就 OK 了。

听起来是不是很简单？但事实上这么做有些问题。大家想一下，在我们整个黑马点评服务里有很多很多 Controller。刚才讲的 `/user/me` 登录校验是 `UserController` 里的，前端会向 `UserController` 发请求，你在它对应的业务里编写这一堆登录校验的业务逻辑，完成了。但是随着业务开发，越来越多的业务都需要校验用户登录。难道你在每一个 Controller 里都来写这一堆业务逻辑吗？有些麻烦了。

有没有更方便的方案？有。在我们的 Spring MVC 中有一个东西，它可以在**所有 Controller 执行之前**去做——**拦截器**。

有了拦截器以后，用户请求就不再能直接访问 Controller，所有请求都必须先经过拦截器，再由拦截器判断该不该放行，让你到达 Controller。这样一来所有的 Controller 都不用再写这种校验，全部由拦截器来做，很方便吧。

但这里还存在一个小小的问题：拦截器确实能帮我们实现登录校验，可是校验完了以后，在后续业务当中，人家是需要这个用户信息的——你在这儿校验时是拿到了，那 Controller 怎么拿到？所以我们需要有一种方案，把拦截器里拦截得到的用户信息传递到 Controller 里面去。

#### 用 ThreadLocal 把用户传给 Controller

而且在传递的过程中要注意线程安全问题。

我们前面提到过有个东西叫 `ThreadLocal`。在拦截器里拦截到用户信息以后，可以把它保存在 `ThreadLocal` 里。因为 `ThreadLocal` 是一个线程内部对象，每一个进入 Tomcat 的请求都是一个独立的线程，Tomcat 就会在线程内给你开辟一个内存空间去保存对应的用户——这样每个线程相互不干扰。

```text
 浏览器 --Cookie: JSESSIONID--> Tomcat
                                   |
                                   v
                         +---------------------+
                         |   LoginInterceptor  |
                         |     preHandle()     |
                         +---------------------+
                                   |
                  读 session 取 user <-- 登录时已经写过 user
                        |              |
                     没 user        有 user
                        |              |
                 401 + return false   |
                                       v
                                 [ ThreadLocal ]
                              (每个请求一个线程，
                               线程之间互不干扰)
                                       |
                                       v
                              Controller 业务方法
                              UserHolder.getUser()
                                       |
                                       v
                              afterCompletion()
                              UserHolder.removeUser()
```

有的请求访问这个 Controller，有的访问那个 Controller，或者说不同的用户访问这个 Controller——这个时候都会有独立线程，大家都有自己的用户信息，互不干扰。到了 Controller 以后，再从 `ThreadLocal` 里取出用户，是不是就 OK 了？我们基于这种方式来实现整个登录校验的流程。

具体落地的时候，我们不用自己去写 `ThreadLocal` 了。在我们的 `utils` 里已经有一个叫 `UserHolder` 的类，点进去看，它里面定义了一个静态的 `ThreadLocal` 常量，泛型是 `User`，也就是说它专门来处理 `User`。里面定义了三个方法：

- `saveUser`：你把 `user` 给我，我帮你存进去
- `getUser`：帮你从 `ThreadLocal` 里取
- `removeUser`：移除

都是静态方法，所以在 `LoginInterceptor` 里直接调用 `UserHolder.saveUser(...)` 就可以了。保存的时候需要强转一下，因为那边声明的类型是 `Object`。

> **提示**：有同学问，保存的时候不需要什么 key 之类的吗？不需要，它是保存在当前线程里面的。如果你对 `ThreadLocal` 的实现原理有疑问，可以去网上搜索一下，看一看就明白是什么意思了。

拦截器要实现 `HandlerInterceptor` 接口，里面有三个方法：

- `preHandle`：前置拦截，在 Controller 执行之前
- `postHandle`：在 Controller 执行之后
- `afterCompletion`：在视图渲染之后、返回给用户之前

我们只实现两个方法就 OK 了。因为在进 Controller 之前肯定要做登录校验，最后用户业务执行完毕，我们还要去销毁对应的用户信息，避免内存泄漏。

```java
public class LoginInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 1. 获取 session
        HttpSession session = request.getSession();
        // 2. 获取 session 中的用户信息（登录时存进去的，key 就叫 USER）
        User user = (User) session.getAttribute("USER");
        // 3. 判断用户是否存在
        if (user == null) {
            // 拦截之后最好给他一些不同的标识，告诉他这个失败了
            response.setStatus(401);
            return false;
        }
        // 4. 保存用户信息到 ThreadLocal
        UserHolder.saveUser(user);
        // 5. 放行
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        // 移除用户，避免内存泄漏
        UserHolder.removeUser();
    }
}
```

`return false` 就是拦截，`return true` 就是放行。

> **注意**：拦截以后最好给他一些不同的标识，告诉他这个失败了。最简单的做法就是直接抛异常，前面自然就拿到这个异常，也知道什么原因了。当然你也可以温柔一点，返回一些状态码，比如 `response.setStatus(401)`，401 就是 Unauthorized——未授权的意思。这样其实就拦截下来了。

到这里，整个前置的拦截就写完了。

### 注册拦截器：哪些要拦，哪些要放行

拦截器写好了，其实它还没有生效。要想让拦截器生效，我们还需要去配置拦截器。

在 `config` 里新建一个 `MvcConfig`，让它实现 `WebMvcConfigurer`，代表的就是一个 MVC 相关的配置。加上 `@Configuration` 注解，然后实现一个叫 `addInterceptors` 的方法，顾名思义就是添加拦截器。添加拦截器可以利用 `registry`——这个是拦截器的注册器，用它的 `addInterceptor` 添加 `LoginInterceptor`。

```java
@Configuration
public class MvcConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginInterceptor())
                .excludePathPatterns(
                        "/user/code",
                        "/user/login",
                        ...
                );
    }
}
```

拦截器配进来以后，你还要去配置拦截哪些路径。你要知道不是所有的路径都需要被拦截，对不对？有很多路径是不需要拦截的。如果说你二话不说拦截一切、默认就拦截一切，那可能就会带来一些不必要的问题。所以我们通过 `excludePathPatterns` 来排除一些不需要拦截的路径，它是可变参数，你可以填多个不同的值。

那要排除哪些？

先看 `UserController`。发送短信验证码和登录注册，这两个本身就不应该被拦截。而登出、`me` 这两个是要做登录校验的，肯定需要拦截，还有 `info` 这些也是需要拦截的。所以我们要把 `code` 和 `login` 这两个功能给它排除，对应的路径就是 `/user/code` 和 `/user/login`。

然后还有其他的 Controller 也需要做一些排除，也就是**放行**：

| Controller | 路径特征 | 为什么放行 |
| --- | --- | --- |
| `BlogController` 查热点博客 | `/blog/hot` | 跟登录用户无关 |
| 店铺 | `/shop/**` | 店铺基本没什么需要拦的，登录不登录都能查 |
| 店铺类型 | `/shop/type/**` | 店铺类型跟登录有什么关系？你不登录就不让我看了吗？不合理 |
| 上传 | `/upload` | 一般要登录才能做，但测试时也可以先放行 |
| 优惠券 | `/voucher` | 你不登录，难道就不让我查优惠券吗？不可能 |

注意 `BlogController` 里那些从后端取用户信息的接口，显然是需要被拦截的；而查热点博客的那个接口就不需要。

> **结论**：这里我们直接用 `/**` 放行了所有以 `/shop` 开头的请求。实际开发中，你要根据实际需求，哪些要拦就配到拦截里，哪些先放行就配到放行里面，这样会比较好一点。这里我们简化一点，先把拦截部分需要的配好就可以了。

配完之后我们的工作还没做完。因为拦截器做完的只是"拦截登录用户并保存到 `ThreadLocal`"这一步。放行以后请求还会到我们的 Controller，Controller 还要完成剩余的业务逻辑。

比方说我们刚才做的登录校验，用的是那个叫 `/user/me` 的接口。这个接口最终还需要把当前登录的用户信息返回到前端，所以这个接口我们还没做。

这个功能太简单了——因为我们在拦截器里已经把用户放到了 `UserHolder` 里面，所以在这个地方只需要从 `UserHolder` 里取出来就行：

```java
@GetMapping("/me")
public Result me() {
    return Result.success(UserHolder.getUser());
}
```

重启测试一下。先重放一下 `/user/me` 这个接口——直接返回 `401`，未授权，报错，符合预期。然后再走一遍手机号 `13456789001` 登录：发验证码、回来粘贴、点登录、确认协议，成功。再看列表接口，已经有我们这个随机生成的用户名了，用户信息都成功返回了。说明整个登录校验 OK 了。

### 敏感信息：把存储粒度降下来

上节课我们实现了登录拦截的校验功能，不过这个功能有一点小问题，不知道大家发现了没有——**返回的信息有点多**。

看这个 `/user/me` 的返回：创建时间、用户头像、id、昵称、密码、手机号、更新时间，全都在里面。但我们查询当前登录用户的时候，其实只要返回用户的 id、昵称、头像就够了。像时间、密码、电话这些敏感信息有没有必要返回？没有，这其实是有泄露风险的。

为什么我们把这一堆信息都给返回来了？打开代码看一下：`me` 方法从 `UserHolder` 里拿到用户以后，二话不说就返回了。说明从 `UserHolder` 里取出来的信息是一个**完整的用户信息**。那这个信息又从哪儿来的？是我们当时做的拦截器，二话不说就扔进去了。

再往上游追一层：Tomcat 的内存空间。你在这里面存的信息越多，对整个服务来讲压力就越大。所以这里边存那么多不相关的、不重要的信息，有没有必要？没有。

那好，是谁给内存存信息的？**是我们做 login 的时候**——从数据库里查出来，二话不说就整个存进去了。找到源头了。

> **定义**：这其实就是一个**存储粒度**的问题。存储得越完整，将来使用起来肯定越方便，但是带来的问题就是内存压力过大，还有可能把敏感信息返回到前端。

怎么改正？我们只返回一些基本的信息就够了，就是 id、昵称、头像等等。

所以专门定义了一个 DTO，叫 `UserDTO`，里面就三个字段：`id`、`nickName`、`icon`。在实现登录功能的时候，先把 `user` 转成 `UserDTO`。

怎么转？笨办法就是 `new` 一个新的对象，然后手动一个一个地把 `user` 的信息存进去，就完了。但这里我们有一个工具类——`BeanUtil`，也是 `hutool` 里面的工具类，它里面有个方法叫 `copyProperties`，意思是拷贝属性。

```java
UserDTO dto = BeanUtil.copyProperties(user, UserDTO.class);
```

把数据源给他——数据源就是 `user`；再把目标告诉他。目标你可以改成具体的一个对象，比如 `new` 出个 `UserDTO`，你也可以改成一个 class 字节码，比如我告诉他"我就要 `UserDTO`"。

这个时候它会干一件什么事情呢？它会自动帮我们把 `user` 当中的所有属性拷贝到 `UserDTO` 当中，而且给你创建出一个对象出来。所以这个方法的返回值就是 DTO。

于是我这里存的就是一个 DTO 对象了。

> **易错点**：这里存的是 DTO，那从拦截器里取出来的这个肯定也是 DTO 类型了——因为它也是从 login 那边存进去的。这时候你的 `UserHolder` 就报错了，因为它里面要的是 `User`。所以你要把 `UserHolder` 里的泛型改成 `UserDTO`，相应地 `getUser()` 的返回值也变成了 `UserDTO`。而且 `getUser()` 这个方法在很多地方都有用，这些地方都要手动改掉。

全部改掉之后，`UserHolder` 里存进去的就是 `UserDTO` 了，`me` 方法取出来的也是 DTO，返回到前端的数据自然就没那么多了。

重启，刷新，重新登录一次。看查到的用户信息，是不是就只剩下三个字段了？

> **结论**：这样就能够避免返回敏感信息，而且能够减少对于内存的占用。到这里，整个登录流程就实现了。

### Session 不共享：水平扩展带来的新问题

前面三节课，实现起来并不复杂，但是它有一个比较致命的问题——**Session 共享的问题**。

什么叫 Session 共享问题？是指多台 Tomcat 无法共享私人存储空间这样一个问题。当请求被切换到不同的 Tomcat 上去，在其他 Tomcat 里是看不到的。

看这幅图，这是我们系统之前的架构图。虽然我们的系统是一个单体式的架构，但是这一台 Tomcat 将来为了应对并发，肯定还是要做水平扩展的，部署多个形成负载均衡的集群。一旦形成负载均衡的集群，请求进入 Nginx，它会在多台 Tomcat 之间做一个轮询。

```text
                    Nginx / Ingress（负载均衡，轮询）
                                  |
                +-----------------+-----------------+
                |                                   |
                v                                   v
        +---------------+                   +---------------+
        |   Tomcat 1    |                   |   Tomcat 2    |
        |---------------|                   |---------------|
        | session 空间  |                   | session 空间  |
        |  code=123321  |                   |   （空的）    |
        |  user=...     |                   |               |
        +---------------+                   +---------------+

  第一次请求（发验证码）  -> 被负载均衡到 Tomcat 1
  第二次请求（登录/校验）-> 被负载均衡到 Tomcat 2
  Tomcat 2 去自己的 session 里找 code -> 找不到
  -> "验证码错误" / "没登录"
```

现在每一个 Tomcat 都有自己独立的 session 空间。假设用户请求来了以后，第一次被负载均衡到了 Tomcat 1，这时候假如我们做的是发送验证码，或者是登录的功能，那么它的验证码也好、用户信息也好，是不是都保存到了这台 Tomcat 里面去了？

紧接着用户第二次来做登录、或者做其他功能的时候，被负载均衡到了第二台 Tomcat。当他要获取验证码，或者获取用户信息的时候——**是不是空的呀？**

这就是 Session 不共享带来的问题。这时候你会告诉他说验证码错——人家明明输的是对的；或者说告诉他没有登录——这不扯了吗？我前一秒钟刚登录完。

那个时候给用户带来的体验就非常差了。

### 解法：为什么是 Redis

#### Tomcat 之间互拷为什么不行

怎么解决这个问题呢？解决方案听起来很简单：Tomcat 的 Session 可不可以共享？

事实上在早期，Tomcat 为了解决这个问题——也就是多台 Tomcat 之间只要做好一些配置，它们之间互相可以互相实现一个数据拷贝。那这么说起来的话，这问题不就解决了吗？

**但并不行。** 为什么？因为数据拷贝有这么几个问题：

- 第一，好多台 Tomcat 保存相同的数据，大家互相拷贝，是不是一种**内存空间的浪费**？
- 第二，我们把数据拷贝的时候，它需要有一个时间的延迟。那么如果在这个延迟之内有人来访问，是不是依然会有一个数据不一致的情况？

所以这种方案退出了以后，并没有得到广泛的使用和认可，因此这种方案就 PASS 了。

#### Redis 恰好卡在这三个条件上

那我们该怎么办呢？替代 Session 的方案需要满足三个条件：

| 要求 | 为什么必须有 |
| --- | --- |
| 数据共享 | 正是因为不共享才导致了刚才的问题，共享了多个 Tomcat 就能看到相同的数据，也就不会出现数据丢失 |
| 内存存储 | 读写效率高。登录校验这类访问频率非常高，读写性能差就难以满足高并发需求 |
| key-value 结构 | 存 code 时 key 是 code、value 是对应的 code 值；存 user 时 key 是 user、value 是 user。这种存取方案非常方便，替代方案也应该是这个样子 |

同学们思考一下，有没有什么东西能同时满足这三个点？答案是不是就呼之欲出了——正是我们的 Redis。

```text
改造前：状态存在单机内存里
  浏览器 --Cookie--> Nginx --> [随机一台 Tomcat] --> 本地 session

改造后：状态集中存到外部内存，任何一台 Tomcat 都能读
  浏览器 --Cookie--> Nginx --> [任意一台 Tomcat] --> Redis
                                          (key = 随机 token)
```

因为 Redis 首先是在 Tomcat 以外的一个存储方案，所以任何一台 Tomcat 都能访问到 Redis。你存在 Redis 里的数据，任何一台 Tomcat 都能够看得见，就不会出现数据丢失的情况，这是第一个。第二，内存存储，Redis 是内存存储，而且性能非常强，读写延时基本上在微秒级别。第三，key-value 结构，这不废话吗，我们之前讲 Redis 的时候就讲过，它是一个 key-value 类型的。

正中了 Redis 的下怀。所以我们把 code 也好、user 也好，都可以以 key-value 的形式存储在 Redis 当中，来替代我们的 Session。

不过是不是说简单地用 Redis 我们的登录就实现了？**其实里边还有一些细节上的东西**，我们在下节课介绍业务流程上的变化。

### 验证码存进 Redis：结构和 Key 都要重设计

先看发送短信验证码。整体来讲这个流程没什么大的变化：提交手机号校验、生成验证码，只不过在保存的时候，现在要保存到 Redis 当中了。

但这里有两个问题。

**第一个问题：选哪种数据结构？**

Redis 的 value 类型有很多种，保存验证码的时候得考虑选择哪种结构。答案是 **String**——因为我们的验证码就是个普通的、六位长度的数字，这样的东西没有什么特殊结构，用最简单的 String 结构就 OK 了。

**第二个问题：key 是什么？**

> **易错点**：这里很多人第一反应是：我们不是用 `code` 作为 k 吗，那在这儿也用 `code` 作为 k 不就好了？
>
> **非常可惜，不能这样。**

为什么？发请求的时候，每一个请求在 Tomcat 内部都有一个独立的线程，Tomcat 内部维护了很多很多的线程。不同浏览器携带不同手机号来的时候，它们**都用 `code` 作为 k，互相之间不干扰，是不是没问题？**

而我们的 Redis 不一样。Redis 是一个**共享的内存空间**，不管是谁来发请求，在我们服务端是不是只有一个 Redis？大家都在往这个里面去存。如果你这个手机号来的时候用 `code` 做 key，我又来个手机号，又用 `code` 做 key，那么不同的手机号都用 `code` 做 key，互相是不是就覆盖了呀？那么这个验证码将来是不是就丢失了很多，那肯定会有很多人对不上。

所以我们必须确保：**每一个不同的手机号来做验证时，保存的 k 都得是不一样的。**

那怎么样才能确保这一点？既然每一个手机号都要有自己的、不一样的 k，那我干脆就用手机号作为 key 不就好了吗？以手机号为 k 来保存验证码，后面跟着手机号，存储验证码就行了。

这么做不仅仅帮我们确保每个手机号都有自己唯一的 k、不会冲突，其实还有第二个好处。

> **提示**：在 Session 那套方案里，我们是不用考虑"怎么取"这个问题的。浏览器发请求来了，我就给浏览器创建一个新的 session；如果说 session 存在，我们就不用去创建，直接用，它就会自动形成 `session id` 写到用户浏览器的 cookie 里。以后每次请求就会带着 cookie、带着 session id，帮我们去取出数据。所以你不用考虑取的问题。
>
> **但现在不一样了**，我们现在用的是 Redis，没有人帮我们维护什么 session id 之类的。你以手机号为 k 存进去了，将来人家去做登录的时候，客户端还得带着这个信息来取，才能验证。

你看一下我们在做登录的时候，用户刚好提交的是什么？手机号和验证码。这样一来我们去校验的时候，就可以基于手机号为 k 从 Redis 里读取到这个验证码，然后跟他提交的验证码做比较就行了。如果说你在保存的时候用的不是手机号，那这边你是不是就取不出来了？

> **结论**：所以这是我们设计的一个技巧。**key 一方面要考虑唯一性，另一方面要考虑将来客户端能够携带这个 key 来获取数据。**

### 用户信息存进 Redis：String 还是 Hash

拿到验证码、完成了对验证码的校验之后，就可以去查询用户、用户是否存在。如果存在，就去保存用户——而保存到 Redis。

既然是保存在 Redis 里，同样要去考虑两个问题，跟刚才一模一样：第一是数据类型的选择，第二是 key 的设计。

先看数据类型。保存验证码时我们用的是 String，因为验证码就是个六位长度的数字。但这里保存的是一个用户对象，保存对象应该选哪种数据结构？

我们以前学过的 string、hash 等等，大家觉得应该用哪种？可能很多同学已经不太记得了，我帮大家回忆一下。当我们要在 Redis 里保存单个对象时，比较常见的有两种方式：

| | String（JSON 字符串） | Hash（field-value） |
| --- | --- | --- |
| 存法 | 把 Java 对象序列化成 JSON 字符串整体保存 | value 是一个哈希，可以理解成 map，又是一组 key-value，把对象里每一个字段都作为 field 和 value 拆开保存 |
| 加字段 | 不行，把整条干掉，重新插入一条 | 没问题，直接加一个 field |
| 改单个字段 | 不行，只能把这条干掉重来 | 没问题，只针对这个 field 操作 |
| 内存占用 | 多。里面包含大括号、冒号、引号等等，数据越长符号越多，有额外的数据存储 | 少。只需要保存数据本身 |
| 直观性 | 好 | 一般 |

这就是 String 和 Hash 最大的差别。String 这种 JSON 字符串的格式看起来比较直观，但是他把整个数据变成一个串了，**字段与字段之间是耦合在一个整体**。而 Hash 结构每个字段是独立的，所以它可以针对单个字段做 CRUD——比如我现在觉得少了两个字段，加个字段没问题；或者说我想修改这个 field 的值没问题。

但像 JSON 就不行了，你要改就只能把这条干掉，重新插入一条；或者你想加个字段，也是不行，把这个干掉，重新插入一个。所以我们的 Hash 结构对于单个字段去做增删改查的时候会更方便、更加灵活。

其次，它的内存占用会更少一点。因为 Hash 结构只需要保存数据本身就可以了，而我们的 JSON 呢，你看这里面还会有这种 JSON 串的格式，什么大括号、冒号、引号等等，数据越长，里面包含的这种符号是不是也越多呀，会多一些额外的数据存储。

所以大家觉得我们应该用哪种？

> **结论**：如果说你对内存不是很在意，而且数据量也不是很大，那其实用 String 相对来讲比较直观、也比较方便，也是 OK 的。但是如果从优化的角度去考虑，**推荐大家使用 Hash 这种模式**。在我们这个案例当中，我们会选择 Hash 结构来保存用户信息。大家也可以自己尝试用 String 结构来实现一下。

### Key 的两个要求，以及 token 怎么交到前端

保存用户信息，key 怎么设计？和保存验证码一样，key 第一要保证唯一——每一个手机号都是唯一的；第二，要保证客户端将来能够携带这个 key，方便从 Redis 里取出这个值。

这个地方我们可以用什么呢？有的时候我们也用手机号，用手机号当然也可以，不过**一般不太推荐**，为什么等一会儿解释。

一般情况下，建议大家使用一个**随机的 token 作为 key** 去存储用户数据。什么叫随机 token？其实就是随机字符串，比如你可以用 UUID 来生成，然后这边就保存用户信息就可以了。这样就满足了 key 的第一个要求——唯一性。

第二个要求呢？将来客户端要非常方便地基于这个 key 去提取到数据，进行登录校验。

之前我们是怎么做登录校验的？把 `session id` 写到浏览器的 cookie 里，每次请求带着 cookie 就带着 session id 来了，从而找到用户。也就是说，**这里的 `session id` 就是你的登录凭证**，基于 id 找用户。这个东西是由 Tomcat 给我们维护的。

但是现在我们已经不用这套东西了，登录凭证就不再是 session id 了。那我们的登录凭证现在应该是什么？

既然你是以 token 为 key 来存储用户信息的，那显然这里的 token 就是登录凭证。也就是说，以后用户再来访问，我们是要带着这个 token 作为凭证的。

但问题来了：**这个 token，Tomcat 会帮我们自动写到浏览器上去吗？** 不会。

所以我们只能怎么办？自己手动把这个 token 返回给前端。也就是说我们这个流程变了：你保存完了，你要把这个生成的 token 返回给客户端；客户端把这个信息保存下来——这里的客户端其实就是浏览器。那这样一来，以后每次请求他就可以携带这个 token，我们的服务器看到他拿了这个 token，就可以基于这个 token 从 Redis 里获取用户信息，拿到用户信息我就可以判断了，剩下流程就不变。

> **结论**：我们这个地方返回 token 到前端，其实就是为了确保前端能够拿到这个登录凭证，以后每次根据它来取。这就满足了 key 的第二个要求。**设计 Redis 数据存取的时候，一定要注意 key 的这两个要求：唯一性，以及方便将来去携带并且提取数据。**

那前端是怎么做到每次请求都携带这个 token 的？来看一下前端的代码。

在登录页面里，登录是用一个 axios 请求来做的。在这个请求的响应里面，`data` 其实就是我们要返回到前端的登录凭证 token。这个 token 会把它保存在 `sessionStorage` 里——`sessionStorage` 是浏览器的一种存储方式，它就把它保存起来了。

然后以后每次请求要携带，怎么做呢？在 `common.js` 里还有这么一点逻辑：从 `sessionStorage` 里得到这个 token，下边是一个 **axios 的拦截器**，它会在每次发请求的时候执行这段逻辑，把这个 token 作为这个**请求头**放进去，这个头的名字叫 `Authorization`。

这样一来就可以确保以后凡是有 axios 发起的请求，也就是所有的 axios 请求，都会携带 `Authorization` 这个头，也就是 token。那咱们将来在服务端就可以获取 `Authorization` 这个请求头，从而拿到 token，从而去实现对于登录的一个验证了。

这就引出了最后一个问题：**我们为什么这个 token 不能使用手机号？**

你想啊，如果我们把手机号作为这个 k 去保存，将来返回到前端、直接保存在浏览器里，会有泄露的风险。所以这个地方不能使用手机号。

> **结论**：至此，实现登录这个业务流程上的一些变化就分析完了。简单地把数据存入 Redis 还不够，**key 的设计、数据结构的选择、以及登录凭证怎么从服务端交到客户端手上**，这三件事都要跟着改。接下来就是动手把这套逻辑实现掉。

**第一题**：短信验证码保存到 Redis，应该选择哪种数据结构？

**答案**：String。依据在《验证码存进 Redis：结构和 Key 都要重设计》——验证码就是个普通的六位长度数字，没有什么特殊结构，用最简单的 String 就够了。

**第二题**：保存一个用户对象，应该选择哪种数据结构？

**答案**：Hash 结构。依据在《用户信息存进 Redis：String 还是 Hash》——JSON 字符串会把所有字段耦合成一个整体，改一个字段就得整条删除重插；Hash 每个字段独立，可以针对单个字段做增删改查，而且只保存数据本身，内存开销更小。当然，如果数据量不大又对内存不敏感，String 直观、方便，也是可以的，只是从优化的角度推荐 Hash。

**第三题**：有没有什么东西能同时满足"数据共享、内存存储、key-value 结构"这三个条件？

**答案**：Redis。依据在《解法：为什么是 Redis》——它在 Tomcat 之外所以能共享、是内存存储且读写延时在微秒级、本身就是 key-value 类型。"多台 Tomcat 互拷数据"这个看似现成的方案，第一个因为重复存储浪费内存，第二个因为拷贝存在延迟窗口、窗口内依然会数据不一致，所以被 PASS 掉了。

## 把登录状态搬进 Redis：短信登录的改造与登录态续期
> 对应块：BLK08 | 覆盖分集：P33-P34 | 块标题（分集名）：《实战篇-10.短信登录-基于Redis实现短信登》

上节课我们把短信登录的流程在纸上推了一遍，这节课就动手改代码，把验证码和登录用户都搬进 Redis。

改动集中在两个业务上：一个是**发送短信验证码**，一个是**登录注册**。发送验证码这块其实只有一处变化——保存验证码的地方；登录这块要动的多，`login` 方法里几乎每一行都得改。

先把改造之后的样子摆出来，后面所有细节都挂在这张图上：

```text
                        发送验证码
浏览器 ──POST /user/sendCode(phone)──▶ UserController
                                             │
                                             ▼
                                       StringRedisTemplate
                                             │
                                             ▼
                    ┌──────────────────────────────────────────┐
                    │ SET login:code:13800000000 572934         │
                    │     EX 120            （验证码 2 分钟有效） │
                    └──────────────────────────────────────────┘

                        登录 / 注册
浏览器 ──POST /user/login(phone, code)──▶ UserController
                                             │
   ① GET  login:code:phone        ── 取回验证码并比对
   ② 查库 / 落库                   ── 没有就注册
   ③ 生成 token（UUID.fastUUID）
   ④ HSET login:user:token  {...} ── 用户对象以 Hash 存
   ⑤ EXPIRE login:user:token 30 MIN
   ⑥ 把 token 通过响应体返回给前端 ─────────────┐
                                                ▼
浏览器把 token 放进请求头 authorization ──▶ 后端拦截器据此识别登录态
```

### 验证码存进 Redis

先注入 Spring Data 提供的 `StringRedisTemplate`。因为我们在构建项目的时候就已经完成了 Redis 的配置，所以这个地方直接拿来用就行，不用废话。

```java
@Resource
private StringRedisTemplate stringRedisTemplate;
```

原来那行保存到 Session 的代码直接删掉，换成：

```java
@Override
public void sendCode(String phone) {
    // 生成验证码（这一步本次不改）

    // 改造前：session.setAttribute("code", code);  ← 删掉
    // 改造后：
    stringRedisTemplate.opsForValue().set(
            RedisConstants.LOGIN_CODE_KEY + phone,
            code,
            RedisConstants.LOGIN_CODE_TTL,
            TimeUnit.MINUTES);
}
```

这里有两个参数值得停下来看一眼。

#### key 不再是随机 code，而是手机号

发送的时候，key 不再用那个随机生成的 code，而是直接以手机号为 key——因为这里本来就有现成的手机号了，不用白不用。

这样改有个直接好处：每个手机号天然对应唯一一个 key，等用户点登录的时候，我们拿着他提交上来的手机号就能原样拼出同一个 key，把验证码取回来做比对。如果 key 还是那个随机 code，登录的时候压根不知道它是什么，也就无从校验了。

#### 一定要加业务前缀

到这儿代码其实已经能跑了，但还有一点必须处理：给 key 加个前缀。

Redis 是一个大家共用的大空间，别人也往里存东西。如果大家都直接把手机号当 key，很可能别的业务也是这么干的，一撞车就冲突了。所以前面最好加一个业务前缀，让 key 有层次感。

我们的业务是登录，用来做 code 校验，那就可以叫 `login:code:`，后面再跟手机号：

```text
login:code:13800000000
└──┬──┘ └──────┬─────┘
  业务前缀     手机号
```

这样 key 就跟别人区分开了。

#### 验证码必须带有效期

以前做短信登录注册，验证码上是不是都写着"该验证码五分钟内有效"或者"两分钟内有效"？为什么一定要加这个限制？

你想，如果不加限制，这个东西往 Redis 一存就不管了。以后每当有人登录或注册需要验证码，Redis 里都会多一条数据。要是有人闲着没事干一直在那狂点，Redis 里岂不是存了无数条数据，而且永远不删除——终于有一天，你的 Redis 就被占满了。

所以我们存的每一个 key 都必须设有效期。这里我们设两分钟，当然五分钟也行。

#### 两种传 TTL 的写法

`set` 的参数列表里就能传有效期，两种方式：

| 写法 | 传什么 | 直观含义 |
| --- | --- | --- |
| `set(key, value, timeout, unit)` | 数值 + `TimeUnit` | 传 `2` 配 `TimeUnit.MINUTES`，就是两分钟 |
| `set(key, value, duration)` | 一个 `Duration` 对象 | `Duration.ofMinutes(2)`，单位直接写在 `Duration` 里 |

第一种有点类似于我们 Redis 里的 `SET key value EX 120`，`EX` 就是有效期，单位是秒，120 秒其实就是两分钟。

#### 把 key 和 TTL 都抽成常量

像 `"login:code:"` 和 `2L` 这种东西，最好都定义成常量。这样写看起来有点 low，万一将来去取的时候这个 key 写错了怎么办呢？所以我们一般都有一个工具类专门定义 Redis 相关的常量。

打开 `util` 里的 `RedisConstants`：

```java
public class RedisConstants {
    public static final String LOGIN_CODE_KEY = "login:code:";
    public static final Long LOGIN_CODE_TTL = 2L;      // 单位：分钟
    public static final String LOGIN_USER_KEY = "login:user:";
    public static final Long LOGIN_USER_TTL = 30L;    // 单位：分钟
}
```

把 key 定义出来再改成大写——逼格不就出来了。粘贴导包回到业务代码里，你看整个代码是不是就优雅很多了。

到这里，发送短信验证码的逻辑就结束了。

### 登录注册：把用户信息也存进 Redis

接下来是短信登录和注册。这个功能在 `login` 方法里，业务逻辑比较复杂，需要改动的东西也比较多。整条链路是：

```text
前端提交手机号 → 校验手机号 → 从 Redis 取验证码并校验
    → 通过则查询用户 → 判断存在与否
        ├── 不存在：创建
        └── 存在  ：直接用
              ↓
        保存用户到 Redis，并把 token 返回给前端
```

第一处变化就是验证码校验：以前从 Session 取，现在改成从 Redis 取。取出来之后直接就是 `String`，不再是 `Object`——因为 `StringRedisTemplate` 的 key 和 value 全都是字符串——所以校验时直接用 `equals` 就行了，`toString()` 没必要。

真正麻烦的是保存用户这段。要考虑的东西比较多：

1. 生成一个 token，作为登录令牌；
2. 把 User 对象转成 Map 去存储，因为我们采用的是哈希结构；
3. 把数据保存到 Redis；
4. 把 token 返回给客户端。

这四件事一件一件来。

#### 生成 token：用 Hutool 的 UUID

token 将来要作为 Redis 的 key，建议用 UUID 来生成，因为比较简单。注意 UUID 有两个，一个是 JDK 自带的，一个是 Hutool 提供的，我们用下面这个 Hutool 的。

```java
String token = UUID.fastUUID().toString(true);
```

`toString(true)` 里的 `true` 是 `isSimple` 的意思：不带中划线，随便一段连着的字符串；不带参数默认就是带中划线的那个。

> **提示**：token 的 key 最好也加前缀，还是那个道理，不能直接裸存。你这里是登录业务、里面存的是用户信息，叫 `login:user:` 行，`login:token:` 也行，只要能表明含义就行。

#### 为什么用 Hash，为什么必须用 putAll

存的时候用哈希结构，这次不再用 String 了。用 `stringRedisTemplate.opsForHash()`。

`put` 有三个重载，最简单那个接受一个 key、一个哈希 key、一个 value：

```java
stringRedisTemplate.opsForHash().put(tokenKey, "id", userDTO.getId().toString());
```

但这里要注意：`user` 里可能有多个字段，那就意味着有多个 hash key 和多个 value。一个 `put` 只能存一个字段，多个字段是不是就得调多次？那这样其实就不太好了，等于是你要跟服务器做多次交互。

所以我们推荐用 `putAll`。它是一个 key 后面跟一个 Map，而 Map 本身就是一个哈希，里头可以存好几个键值对。这样一来只要我们能把 UserDTO 转成一个 Map，不管它有三个字段还是五个字段，都可以一次性 put 进 Redis：

```java
stringRedisTemplate.opsForHash().putAll(tokenKey, userMap);
```

那怎么把 User 转成 Map？继续用 Hutool 的 `BeanUtil`，它有个方法叫 `beanToMap`，作用就是把一个 Bean 变成一个 Map：

```java
UserDTO userDTO = BeanUtil.copyBean(user, UserDTO.class);
Map<String, Object> userMap = BeanUtil.beanToMap(userDTO);
```

返回值正是一个 Map。有了它，存的时候就可以放心大胆地存了。

#### 用户信息同样要设有效期

等等——写到这儿业务其实还没完成。我要给大家提示一个小小的问题。

我们现在把用户信息直接扔到 Redis 里去了。用户登录完扔进去，好；如果登录用户越来越多，扔到 Redis 里的数据是不是也越来越多？加以时日，Redis 是不是也可能会被放满？跟刚才存 code 一模一样的问题，而且用户信息反而比 code 还大。

所以这里也要给这个 token 设置一个有效期。一段时间以后我们把它从内存里清掉，就可以避免内存占用过多。

**那这个时间是多长合适呢？** 同学们大家思考一下，可以打在公屏上。

答案是 30 分钟。因为如果你 30 分钟不去管它、不去做任何的操作，那登录状态其实就已经失去意义了。

不过这里有个坑：**`opsForHash()` 存数据的时候，是不允许设置有效期的。**

> **易错点**：`putAll` 只有 key 和 map 两个参数，没有 TTL 的位置。只能先存，存完了再单独给它设置有效期。

存完之后直接用 `expire` 就行。这个命令跟我们的方法名是一样的，前面跟上 key，这个 key 就是上面那个 key，两个是一样的。当然了，你也可以在外面把它抽成一个变量，这样就不用写两次了。

```java
String tokenKey = RedisConstants.LOGIN_USER_KEY + token;
stringRedisTemplate.opsForHash().putAll(tokenKey, userMap);

// Hash 结构没法在写入时带 TTL，存完再补一刀
stringRedisTemplate.expire(tokenKey, RedisConstants.LOGIN_USER_TTL, TimeUnit.MINUTES);
```

这两个常量的名字也要改一下：既然现在存的是用户了，就叫 `LOGIN_USER_KEY` 和 `LOGIN_USER_TTL`，TTL 是 `30L`，单位 `MINUTES`。回到代码里替换掉，至此业务完成。

### 30 分钟到了就掉登录态，这个设计有问题

看着好像齐了，但还有一个小小的问题，我提示一下。

我们给 token 设的是 30 分钟有效期，对吧。可是它有一个前提大家想想：**它不是到了 30 分钟就结束了，只要你不停地访问我，我的有效期就一直是 30 分钟；只有你超过 30 分钟不访问我，我才会把你的登录状态给剔除。**

这才是我们想要的效果。但我们现在是怎么做的呢？是从登录那一刻开始算，只要过了 30 分钟，Redis 就会把你剔除，没了。不管用户有没有在访问，将来 30 分钟一定会被踢掉——那这就不行了啊。

所以我们应该做到：**只要用户在不断地访问我们，就不断地去更新 Redis 中 token 的有效期。**

可问题来了：**我怎么知道用户有没有访问我？我怎么知道用户什么时候访问？**

### 思路就在拦截器里

我们之前是不是有这么一个东西——登录拦截校验？可以认为，我们所有的请求进来以后，都要经过拦截器的拦截和校验。

那么只要经过了这个校验，就证明两件事：第一，他是个登录的用户；第二，他在活跃着，在访问着我们。

既然满足了这两个条件，我是不是就可以去更新一下 Redis 里 token 的有效期？这样一来，只要登录用户不停地访问，我们就不断更新有效期，Redis 里这个 token 就永远不会过期；而只有用户什么操作都不干、不触发拦截器的情况下，超过 30 分钟这个 key 才会被移除。

所以，等一会儿我们去改那个"校验登录状态"的业务逻辑时，应该在原有逻辑的基础上，**添加一个更新 token 有效期的逻辑**。

### 改写 LoginInterceptor

登录的相关业务我们是写在拦截器里的，`LoginInterceptor`。这个拦截器里要做的事情比较多，我们一件一件捋。

```java
public class LoginInterceptor implements HandlerInterceptor {

    private StringRedisTemplate stringRedisTemplate;

    public LoginInterceptor(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // ① 改：token 现在在请求头里
        String token = request.getHeader("authorization");

        // ② token 为空就没必要去取了，直接拦
        if (StrUtil.isBlank(token)) {
            response.setStatus(401);
            return false;
        }

        // ③ 改：以 token 为 k，从 Redis 的哈希结构中取回整个 Map
        String tokenKey = RedisConstants.LOGIN_USER_KEY + token;
        Map<Object, Object> userMap = stringRedisTemplate.opsForHash().entries(tokenKey);

        // ④ 用户不存在，照样拦截
        if (userMap.isEmpty()) {
            response.setStatus(401);
            return false;
        }

        // ⑤ 改：哈希数据（Map）转回 UserDTO
        UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);

        // ⑥ 存到 ThreadLocal，供后续 Controller 业务使用
        UserHolder.save(userDTO);

        // ⑦ 改：刷新 token 的有效期
        stringRedisTemplate.expire(tokenKey, RedisConstants.LOGIN_USER_TTL, TimeUnit.MINUTES);

        // ⑧ 放行
        return true;
    }
}
```

几个地方要展开说。

**关于请求头**。token 是在请求头里的，我们看前端代码的时候见过，名字叫 `authorization`。请求头从 `request` 里拿，`request.getHeader("authorization")` 就完事了。

**关于 `entries`**。之前用 `get` 只能取出某一个 key 里的一个字段，而我们想取的是这个哈希里边的所有键值对，所以这里要用 `entries`，它接受一个 key，返回值是一个 Map，把整个哈希结构的多个字段一次性反馈给我们。

**关于判空**。这里不用判 null，因为 `entries` 方法内部会做判断——如果为 null，它会给你返回空 Map。所以直接判断 `isEmpty` 就行了。

**关于 `fillBeanWithMap`**。把对象转 Map 用的是 `BeanUtil`，转回来还是要用 `BeanUtil`，但方法名不再是 `beanToMap` 了，而是反过来叫 `fillBeanWithMap`，也就是用一个 map 来填充 Bean。它有三个参数：用哪个 map、用哪个 bean（我们 new 一个 `UserDTO`）、要不要忽略转换过程中的错误。肯定不忽略，给个 false，有异常你就给我抛出来就行了。

只有转换成了 UserDTO，我们才可以把它存到 ThreadLocal，然后完成放行。

### 拦截器里为什么不能注入 @Resource

等等，这块的注入有个讲究。

这里的注入我们不能用 `@Autowired`、`@Resource`，只能用构造函数来传。

**为什么？** 因为这个类的对象是我们自己手动 new 出来的，它不是通过 `@Component` 这些注解构建出来的——也就是说这个类的对象不是由 Spring 创建的，是手动创建的。那么由 Spring 创建的对象，它能帮你做依赖注入；我们自己手动创建对象，没有人帮你做依赖注入，因此你没有办法使用 `@Resource` 等等这样的注解了。

那怎么办？利用构造函数注入。**谁来帮我们注入呢？那就看是谁用了它。**

```text
Spring 容器
   ├─ 构建 UserController / UserService（@RestController、@Service）
   │      └─ 这些类里 @Autowired / @Resource 都能用，因为是 Spring 建的
   │
   └─ 构建 WebMvcConfig（带 @Configuration 注解）
          └─ 类带 @Configuration → 这个类将来由 Spring 构建
                 └─ 所以可以在这里用 @Resource 拿到 StringRedisTemplate
                        └─ 再手动 new 拦截器，把 template 传进构造函数
```

当初我们就是在 `MvcConfig` 的拦截器里用到它的，当时那个地方直接报错了。所以我们需要在这儿把它注进去——`WebMvcConfig` 加了 `@Configuration` 注解，说明这个类将来由 Spring 来构建，那就可以在这儿利用 `@Resource` 注解获取 `StringRedisTemplate`，然后拿着它往构造函数里一放，整个类就 OK 了。

这个技巧大家也要注意，学习一下。

### 联调报错：Long 类型的 id 转不成 String

改完重启测试。浏览器输手机号、发送验证码，打开 Redis 桌面客户端看一眼——`login:code:` 里存的 `572934` 和页面上收到的一模一样，说明数据确实存进去了。

回到浏览器输验证码点登录，一提交——**服务器异常**。

回去翻日志，是一个类型转换异常：`long 不能转化为 string`。定位到 `UserService` 的登录方法，是在把 userMap 往 Redis 写的时候报错的。

那我们的 userMap 里什么是 Long 类型的？userMap 其实来自于 UserDTO，而 DTO 里其实只有 id 是 Long 类型。也就是说，我们这个 Long 类型的 id 无法存储到 Redis 里面去，就报了这个错。

**这是 Redis serializer 的报错。** 为什么会有 long 转 string 的错误？我们使用的 `StringRedisTemplate` 记得吧，它有一个特点：**它要求你所有的 key 也好、value 也好，都必须是 String 结构。** 而我们把数据转成 Map 的时候，那个字段 id 是 Long 类型，所以就出现这个问题了。

> **结论**：`StringRedisTemplate` 只吃字符串。存进去的 Map 里，key 和 value 都得是 String 结构。

那这个问题该怎么办？也就是说，我们在把对象转成 Map 的时候，得确保这里边每一个值都以 String 的形式存储。

#### 修法一：笨办法

不用工具类了，自己 new 一个 Map，把对象里的字段名作为 key，把字段值转成字符串作为 value。也是一种办法。

#### 修法二：用 CopyOptions 自定义

这个工具是可以自定义的。默认情况下你的值是什么数据类型就用什么类型，但它允许你做自定义，哪个呢？`CopyOptions`。它就是做数据拷贝时的一个选项，允许你对 key 和 value 做自定义。

```java
Map<String, Object> userMap = BeanUtil.beanToMap(
        userDTO,
        new HashMap<>(),
        CopyOptions.create()
                .setIgnoreNullValue(true)
                .setFieldValueEditor((fieldName, fieldValue) -> fieldValue.toString()));
```

我再说一遍它怎么用。先传对象，再传一个 Map，我们 new 一个空的 HashMap，然后传第三个参数 `CopyOptions`。

`CopyOptions.create()` 创建出来是默认的，我们要自定义它，后面允许你做各种各样的 set：

- `setIgnoreNullValue(true)`：忽略空的值，空的值它就会被忽略掉；
- `setFieldValueEditor`：对字段值的一个修改器，它允许你去修改字段值。

`setFieldValueEditor` 接收的是一个 `Function`，这个函数里面有两个参数加一个返回值。那两个参数分别就是**字段名 fieldName** 和**字段值 fieldValue**，返回值是你修改后的字段值。

我们要的是什么？同学们，我们只需要字段值要字符串就行了，`fieldValue.toString()` 是不是就 OK 了。这样我们其实就自己对字段的值做了修改，也就是说所有的值都转成字符串，哪怕它原来是 Long 也转成字符串，那刚才那个错误就不会出现了。

> **提示**：碰到错误不要着急，而是去仔细分析一下可能产生问题的原因在哪里。

重启再试，这次登录成功了。打开 Redis 客户端刷新一下：`login:code:` 里存着验证码，`login:user:` 里 token 是一串 UUID，值是以 key-value 形式存的——哈希结构。再打开浏览器看请求，`/user/me` 这个请求的 request header 里确实带着 `authorization`，值就是我们看到的那个 token。这样后台才能验证 token、验证他有没有登录。

至此整个登录流程完全按我们期待的方式运行了。

### 这一章真正想让你记住的几条

回到 PPT 总结一下。

改造点其实就那么几个：

- **发送验证码**时把验证码存进 Redis。需要注意的就是它的 key——我们用手机号。第一，保证每个手机号都有自己唯一的 key；第二，保证将来用户再登录时能基于手机号取到这个验证码，从而实现验证。
- **登录时保存用户**，对 key 也做了调整。首先要保证唯一，用了一个 UUID；其次要保证将来前端能拿过来做登录校验，所以我们还把 token 返回给了用户、保存到浏览器里。这样浏览器将来才能携带这个 token 来访问我们，从而实现登录效果。

由此也告诉我们：**在使用 Redis 存储数据的时候，key 的规范是很重要的。**

具体到规范，一共这么几条：

| 维度 | 要求 | 原因 |
| --- | --- | --- |
| 数据类型 | 简单数据如验证码用 String；复杂对象用 Hash | Hash 存储空间占用更小，还能对单个字段做修改，更灵活 |
| key 唯一性 | 必须能保证不撞车 | 手机号天然唯一；用户信息用随机 UUID |
| key 含义 | 要方便下一次能更快更方便地找到它 | 加上 `login:code:` / `login:user:` 这样的业务前缀 |
| 有效期 | 一定要设 | 避免数据在 Redis 里存储过长时间，占用过多内存 |
| 存储粒度 | 不必存完整用户信息 | 去掉敏感数据，只保存页面真正需要的不太敏感的数据，还能节省内存空间 |

最后一条尤其容易被忽略。我们实际存的时候并没有把完整的用户信息塞进去，而是把 user 信息里的一些敏感数据去掉了，只留不太敏感的、页面需要的那部分。所以**存储的粒度是非常重要的**。

顺便说，这节课我们把 Redis 的 String 和 Hash 这两种结构都练了一遍。企业在用 Redis 的时候大概就是这些细节和注意事项，希望对大家有帮助。

### 换一个拦截器：让所有请求都能续期

经过前面几节课的努力，我们终于实现了基于 Redis 的短信登录功能。不过细心的同学可能发现了：我们这个登录还有一点小小的问题，大家跟我一起来分析。

#### 病根：拦截器并不拦一切路径

我们这个登录功能是基于拦截器做校验的。用户请求进入拦截器以后，我们会尝试去获取请求头中的 token；如果他之前登录过，头里一定会有 token。然后我们根据 token 到 Redis 里查询对应的用户信息，查了以后对用户做判断：不存在就拦截，存在就继续，把它保存到 ThreadLocal 当中，方便后续的 Controller 业务使用。保存完我们还做了一件事，就是去刷新 token 的有效期。

为什么刷新？因为 Redis 里这个 token 的有效期是 30 分钟，如果不刷新，用户 30 分钟后可能就失去登录状态了，这个就不太友好。所以每当用户来访问我们都刷新一次，确保只要用户一直在操作，他这个登录态就不会消失。最后放行就可以了。

**但是我们现在的逻辑，能不能真正达成"只要用户一直在访问就不会过期"呢？还不太行。**

为什么？因为这个拦截器它拦截的路径不是一切路径啊。它拦的是那些需要做登录校验的路径，比如我们的 `/user/**`，再比如将来用户的下单、支付等等这样一些对用户信息有需求的路径。但它不是拦截一切。

这就导致：如果用户一直访问的是不需要登录的页面——举个例子，我们的首页、商户的详情页，这些都是不需要登录就能看的——那么这个拦截器就不生效，它就不会去刷新。

那接下来如果说 30 分钟以后，尽管用户一直在访问，用户的登录状态是不是也消失了？所以这是一个不太合理的点。

#### 解法：再加一个拦截器，拦一切路径

针对这个点我们可以这么来做：**在原有这个拦截器的基础上，再加一个新的拦截器。**

```text
                一次请求进来
                      │
                      ▼
┌─────────────────────────────────────────────────────────┐
│ RefreshTokenInterceptor                                  │
│   addPathPatterns("/**")   拦截一切路径，order 小 → 先执行 │
│                                                         │
│   ① 取请求头 authorization                              │
│   ② token 为空？→ 不拦截，直接 return true              │
│   ③ opsForHash().entries(tokenKey) 取用户               │
│   ④ 为空？→ 不拦截，直接 return true                    │
│   ⑤ Map → UserDTO → UserHolder.save()                  │
│   ⑥ expire(tokenKey, 30, MINUTES)  刷新有效期          │
│   ⑦ return true（这个拦截器永远不拦人）                 │
└─────────────────────────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────┐
│ LoginInterceptor                                         │
│   addPathPatterns("/user/**")  只拦需登录的路径           │
│   order 大 → 后执行                                     │
│                                                         │
│   ① UserHolder.getUser() == null？                      │
│   ② 是 → response.setStatus(401) + return false         │
│   ③ 否 → return true                                    │
└─────────────────────────────────────────────────────────┘
                      │
                      ▼
              Controller 业务方法
```

因为我们的第二个拦截器拦的是需要登录的那些路径，而不是所有的路径，所以没有办法给所有的请求都做刷新。那新加的这个拦截器，我就让它拦截一切路径，所有请求都会经过我。我是不是可以在这个拦截器里来做刷新 token 有效期的这个动作？

在这里获取 token、获取 Redis 中的用户。当然了，有人说：你这个查的时候万一不存在怎么办？不存在我不管。只要它存在，我就给它保存到 ThreadLocal，做刷新的动作——**也就是说我这里不做拦截。我这个拦截器虽然拦截一切路径，但它唯一的目的其实就是保存 ThreadLocal 和刷新的动作。**

那拦截的动作在哪做呢？在第二个拦截器里。

#### RefreshTokenInterceptor：复制一份，改掉拦截

实操上就是复制原来的拦截器一份，名字叫 `RefreshTokenInterceptor`。在这个拦截器里我们要完成大部分的业务功能：包括获取请求中的 token。当然这个**不用做拦截**，如果发现为空，直接结束就行了，放行，`return true` 就可以了。

往下拿到 token，从 Redis 里获取这个用户。获取完用户判断如果为空，同样不要拦截，而是直接放行。

再往下走就是去把用户转成 DTO，然后给它保存到 ThreadLocal，然后去刷新有效期，然后也是放行。

```java
public class RefreshTokenInterceptor implements HandlerInterceptor {

    private StringRedisTemplate stringRedisTemplate;

    public RefreshTokenInterceptor(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String token = request.getHeader("authorization");
        if (StrUtil.isBlank(token)) {
            return true;                       // 没登录，不拦，放行
        }

        String tokenKey = RedisConstants.LOGIN_USER_KEY + token;
        Map<Object, Object> userMap = stringRedisTemplate.opsForHash().entries(tokenKey);
        if (userMap.isEmpty()) {
            return true;                       // 没有这个用户，也不拦，放行
        }

        UserDTO userDTO = BeanUtil.fillBeanWithMap(userMap, new UserDTO(), false);
        UserHolder.save(userDTO);

        stringRedisTemplate.expire(tokenKey, RedisConstants.LOGIN_USER_TTL, TimeUnit.MINUTES);
        return true;                           // 永不拦截
    }
}
```

#### LoginInterceptor 瘦身成一行判断

再看之前的那个拦截器，它就不用这么复杂了。因为前边那个拦截器已经把所有的事情都做完了，它唯一要做的事情就是判断要不要做这个拦截。

其实依据是什么？依据就是 ThreadLocal 中是否有我们的这个用户。如果有，这里就放行；没有，就拦截就可以了。

```java
public class LoginInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        User user = UserHolder.getUser();
        if (user == null) {                    // 没有 → 未登录
            response.setStatus(401);
            return false;                      // 拦截
        }
        return true;                           // 有用户 → 放行
    }
}
```

这里我们不再需要 `RedisTemplate` 了，因为有关 token 获取、刷新、用户存储那块代码，全部都交给刷新的这个来去执行了。所以这块只是做判断有没有用户，其他动作全部放到刷新拦截器里。

两个拦截器各司其职：**第一个的核心工作就是得到用户、保存起来并刷新；第二个的核心动作才是做登录拦截。**

#### 注册与执行顺序

接下来配置这两个拦截器。到 `WebMvcConfig` 里，`LoginInterceptor` 需要的 `redisTemplate` 删掉——它不再需要了；然后把新的 `RefreshTokenInterceptor` 加进来。

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    @Resource
    private LoginInterceptor loginInterceptor;

    @Resource
    private RefreshTokenInterceptor refreshTokenInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 登录拦截器：只拦部分需要登录的请求，且必须后执行
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/user/**")
                .order(2);

        // 刷新拦截器：拦所有请求，且必须先执行
        registry.addInterceptor(refreshTokenInterceptor)
                .addPathPatterns("/**")
                .order(1);
    }
}
```

`addPathPatterns("/**")` 不写其实也可以，默认就是 `/**`，如果不放心你还可以显式加上。

那这里有个坑：**我们希望的是 refresh 先执行**，因为只有它先执行了、拿到了我们的用户保存到 ThreadLocal，第二个拦截器才能去做拦截的判断。也就是说这两个其实是有先后顺序的。

怎么控制执行顺序？我们添加拦截器的时候，这个拦截器会被注册成一个叫 `InterceptorRegistration` 的东西，注册器里面有一个 `order`，就是执行顺序。

默认情况下所有拦截器的 order 都是 0，都是 0 的情况下按添加顺序执行。所以简单来说，只要把要后执行的先添加就行。但如果你想控制得严谨一点，可以给 refresh 的 order 调得小一点，给 LoginInterceptor 的 order 调得大一点——**值越大，执行优先级反而越低；越小，优先级越高。** 这样就能确保刷新的先执行、登录的后执行。

### 验证：连首页刷新都能续期

重启测试。浏览器登录进去，打开 Redis 客户端看登录信息：保存下来了，有效期是 1800 秒，也就是 30 分钟。

现在过了一段时间，我们来看看到底会不会触发续期。先在浏览器刷新页面——它要访问 `/user/me`，这个请求需要获取当前登录用户，肯定会触发刷新。回到 Redis 客户端一看，TTL 变成 1780 了，被重置了。

再试一个：**访问首页**。首页其实是没有对用户的一次访问的，它只访问了店铺类型，这个请求是没有做登录拦截的。在首页上刷新，回到 Redis 客户端——**一样被重置了**。

这就说明：不管我们现在访问的是需要登录的还是不需要登录的页面，只要你访问了都能够触发对这个用户登录 token 有效期的更新。每当你刷新一次，这里的 TTL 都会被重置。

至此，登录状态刷新的功能就完美解决了。思路其实就是两个拦截器：**一个负责专门刷新，一个负责拦截。**

## 商户查询缓存：从"什么是缓存"到缓存更新策略
> 对应块：BLK09 | 覆盖分集：P35-P38 | 块标题（分集名）：《实战篇-商户查询缓存-01.什么是缓存》

这一章我们进入 Redis 企业实战的第二个部分——商户查询的缓存。我会借"查询商户"这样一个真实的业务，带大家把企业里缓存怎么用、有哪些坑、怎么解决，一个一个过一遍。

这一章的路线是这样的：先搞明白什么是缓存，以及它带来的收益和成本；然后动手写代码，看怎么给业务加 Redis 缓存；接着讲用缓存过程中的数据同步问题，也就是缓存更新策略，以及穿透、击穿、雪崩这些常见问题对应的思路和代码；最后我们再动手封装一个缓存工具类，把这些解决方案打包起来，方便后期直接用。

### 缓存到底是什么

> **定义**：缓存（Cache）就是数据交换的缓冲区，它是存储数据的临时地方，**读写性能较高**。

注意了，画重点了，敲黑板了——读写性能较高。这也是为什么缓存会被用作数据交换的缓冲区：性能好。就这么朴素的一条。

比较典型的例子就是我们自己的计算机。大家知道计算机主要构造就是 CPU、内存、磁盘。CPU 的运算能力到现在已经发展得非常厉害了，远远超过了内存和磁盘读写数据的能力。

问题就出在这儿：**CPU 所做的任何运算，都需要先从内存或者磁盘里读到数据，放到自己的寄存器，才可以做运算。** 数据读写能力远远低于 CPU 的运算能力，计算机的整体性能就被卡在这儿了。

```text
                    ┌─────────────────────┐
                    │   CPU 寄存器         │  ← 真正参与运算的地方
                    └──────────▲──────────┘
                       读写数据 │
        ┌───────────────────┴───────────────────┐
        │        CPU Cache（多级缓存）            │  读写快、容量小
        └────────┬───────────────────────┬────────┘
      ┌──────────┴─────────┐   ┌─────────┴────────┐
      │       内存          │   │       磁盘        │  读写慢、容量大
      └────────────────────┘   └──────────────────┘
```

解决办法就是：人们在 CPU 内部添加了一个缓存，把经常需要读写的数据放进 CPU 缓存里。做高速运算的时候，就不必每次都等半天从内存和磁盘里把数据读过来，而是直接从缓存里拿。这样 CPU 的运算能力是不是就充分释放出来了？

> **提示**：所以衡量一个 CPU 强不强的一项标准，就是 CPU 缓存的大小——缓存越大，能缓存的数据自然越多，处理性能也就越好。这就是缓存使用的一个最典型的场景。

### Web 开发里到处都能加缓存

在 Web 应用开发过程中，缓存同样离不开。我们从一个外部应用的请求流进来往下看，每一层都可以加缓存。

**浏览器缓存。** 用户通过浏览器向我们发起请求，浏览器首先就可以建立缓存。最常见的就是页面的静态资源——我们访问一个页面，页面里有很多 CSS、JS 和图片，这些东西一般是不变的，浏览器可以把它们缓存在本地，这样无需每次访问都去加载，能大大降低网络延迟、提高页面响应速度。

**应用层缓存。** 在浏览器缓存中未命中的数据会到我们的 Tomcat，也就是我们编写的 Java 应用里。而在这里，我们还可以添加应用层的缓存。所谓应用层缓存，简单来说就是创建一个 Map，把从数据库查到的数据放进这个 Map，下次来了直接从 Map 里读给你，减少对数据库的查询、提升效率。

当然，一般情况下我们不用 Map 来做缓存，而是用我们学过的 Redis。为什么？因为 Redis 本身的读写能力非常强、速度非常快，读写延迟往往在微秒级别，用它作为应用层的缓存再合适不过。

**数据库缓存。** 当缓存未命中、请求依然落到数据库时，数据库层面也可以添加缓存。举个例子，我们的索引——MySQL 数据库它是一个聚簇索引，会给 id 创建索引，这些索引数据就可以被缓存起来，这样当我们根据索引查询时，就能在内存里快速检索得到结果，而不用每次都去读写磁盘，效率也会大大提升。

```text
浏览器 ──► Tomcat（Java 应用）──► 数据库 ──► 磁盘 / CPU
  │              │                  │
浏览器缓存    应用层缓存           数据库索引缓存
（静态资源）  （Redis，微秒级）    （内存中的索引页）
```

> **易错点**：数据最终查找还是要落到磁盘。做复杂排序、表关联这类运算，还会用到 CPU，所以最终数据库还是会去访问 CPU 和磁盘。到了这一层，用到的又回到我们前面提到的 CPU 多级缓存以及磁盘，甚至还可以建立读写缓存。

所以你看，整个 Web 开发的每一个阶段都可以添加缓存，缓存的应用场景非常丰富。

### 缓存是双刃剑：收益与成本

但是！缓存不能乱用。任何东西都是双刃剑，有得必有失。你引入缓存以后，它在给你带来好处的同时，也一定会带来一些成本。我们就基于 Web 应用开发来分析一下，在外围应用当中添加缓存，它的作用和代价分别是什么。

**收益之一：降低后端的负载。** 以前请求进入 Tomcat 之后，第一件事就是查数据库。而数据库因为要做磁盘读写，相对来讲效率比较低，导致整个业务延迟比较高，特别是一些复杂的业务 SQL，查询起来就更慢了，会给数据库带来比较大的压力。有了缓存之后，请求进入 Tomcat 直接在缓存里查到数据返回给前端，不用查数据库，后端压力就大大降低了。

**收益之二：提高读写效率、降低响应时间。** 前面说了，数据库的读写往往是磁盘读写，耗时比较长。而像 Redis 这样的缓存，读写延迟往往在微秒级别，等待时间大大缩短，读写效率大大提高——这就意味着我们能够应对更高的并发请求。所以在一些用户量比较大、并发比较高的业务里，使用缓存就能解决这样的高并发问题。

但是，使用缓存也会带来成本。

**成本之一：数据一致性成本。** 我们的数据本来保存在数据库里，现在你把它缓存了一份放到内存里（Redis），用户查询时优先查 Redis 来减轻数据库压力。但如果数据库的数据发生了变化，而 Redis 里还是旧数据，这时候用户再来读，读到的就是旧数据，两者产生了不一致。如果是一些比较重要的数据，不一致甚至可能带来比较严重的问题。

而且为了解决一致性问题，会给代码维护带来极大的成本：你在解决一致性问题的过程中，需要有非常复杂的业务编码，而且在缓存一致性处理过程中，还会冒出缓存穿透、击穿等等一系列问题。为了解决这些问题，代码复杂度会提高很多，以后开发和维护起来成本也就越来越高。

**成本之二：运维成本。** 为了避免缓存雪崩这样的问题、为了保证缓存的高可用，缓存往往需要搭建成集群模式。而缓存集群的部署和维护，会带来额外的人力成本，还有集群部署过程中的硬件成本。

> **结论**：任何东西都是双刃剑，有得必有失。所以一个企业在开发过程中做选择时，你要去评估——使用缓存带来的这些好处，能不能弥补它带来的这些成本。如果不能，那我觉得不用也罢。特别是一些中小型企业，刚刚起步、用户量也不大，这时候你不用缓存其实也能够应对日常的用户请求，那就没有必要去做这些事情。

### 缓存工作的模型

要想知道添加缓存具体该怎么做，你首先得明白缓存工作的一个模型。

没有添加缓存的时候，客户端向服务器发起的请求都会直接打到数据库，数据库查询数据以后再返回给客户端。添加缓存，就等于是在客户端与数据库之间添加了一个中间层。

```text
【加缓存之前】
客户端 ─────────────────────────────► 数据库 ──► 返回给客户端
         所有请求都落到数据库（一条又粗又大的箭头）

【加缓存之后】
客户端 ──► Redis ──► 命中 ──────────► 直接返回给客户端
            │
            └─► 未命中 ──► 数据库 ──► 结果返回给客户端
                              └──────► 同时写回 Redis（下次就能命中）
```

你看，这样一来，真正能够到达数据库的请求是不是就非常少了？原来是一个又粗又大的箭头，现在变细了。

但是我们不能满足于这个就完了。你想，如果到这就结束了，那么在 Redis 中未命中的数据，下一次是不是依然是未命中？所以如果 Redis 未命中、查了数据库，我们应该把查到的数据写回 Redis 当中，这样下一次再来查询这个数据的时候是不是就可以命中了？随着用户请求的数据越来越多，Redis 当中缓存的数据也越来越多，Redis 的命中率越来越高——这才形成了一个良性的工作模型。

### 给商户查询加上缓存

有了模型，我们回到真实的业务上。我们打开浏览器看首页，顶部是商户的类型列表，随便选一个"美食"，看到的就是美食有关的商户；再随便选一个，比如"茶餐厅"，这边就是茶餐厅这个商户的详情数据了。

这些数据都是由 `/api/shop/{id}` 这个请求查到的，后面那个 id 就是当前商户的 id——这是一个根据 id 查询商户详情的接口。你可以看得到，它查询到的数据还是挺多的，所以我们要做的事情就是：给这个接口添加缓存，提高它的查询性能。

先看现状。接口在跟 shop 有关的 Controller 里，第一个就是根据 id 查询商品信息：

```java
@GetMapping("/{id}")
public Result<Shop> queryShopById(Long id) {
    return Result.ok(shopService.getById(id));
}
```

拿到 id 以后直接调了 ShopService 的 `getById`，而这个方法是 IService 接口提供的——IService 是 MyBatis-Plus 给我们提供的接口，在它里边拿到 Wrapper 以后直接调了 select 方法，等于是直接走了数据库。

现在我们要做的就是给这个业务添加 Redis 缓存。

#### 业务流程该放在哪里

这个业务肯定不能在 Controller 里写，业务流程相对比较多。我们直接 `return shopService.queryShopById(id)`，把 id 传进去，这样就把整个业务搬到 Service 里去做了。

具体怎么做？在接口里先把方法创建出来，然后找到它的实现类，再用 IDEA 的快捷键生成对应的实现方法，然后在这儿完成整个查询和缓存的流程。

参考前面那个模型，商户查询的业务流程就变成了这样：

- 请求提交了店铺 id，先尝试从 Redis 里查缓存；
- 判断是否存在，存在就直接返回，这一种比较简单；
- 不存在就复杂了：先根据 id 查询数据库；
- 查数据库又分两种情况：不存在，说明用户提交的 id 是错的，直接返回错误；存在，则需要先把数据写入 Redis，然后再返回。

复杂了一些，但也就这样。

#### 选择数据结构与 key 设计

从 Redis 查询缓存，我们可以拿到 `StringRedisTemplate`，在这里用 `@Resource` 注入一下，拿到了它在下边就可以去查询了。

这回我们要选择一个数据结构。因为缓存的是商铺，它肯定是一个对象。那你选什么呢？很多同学就会说了：选哈希对不对？没错，选哈希完全可以，因为之前我们演示的时候都是用哈希来演示的。这里我们采用 String 来演示，每一种结构我们都给大家演示一下，所以这里我们选择 `opsForValue()`。

取的时候就用 `get`，用 `get` 的时候就要去指定这个 key 了。那么这个 key 我们要一起来商量一下：key 的选择要确保唯一。那你现在查的店铺，每一个店铺都有自己唯一的 key，对不对？你觉得店铺的什么东西是唯一的？是不是这个 id？所以在这个地方我们直接以店铺 id 作为 key，是很合适的一个选择。

当然了，一定要拼成一个前缀，然后再跟上 id，以这样的形式。那这个前缀用什么呢？一般的 cache 你就跟上 cache，后面跟上说你的 cache 是谁、是什么东西。我们是店铺 shop，那后面跟上 id，这样不就 OK 了。

所以我们得到的 key 就是一个字符串，我们可以认为是 shop 的一个 JSON 字符串。那这样的话我们就需要把这个字符串再反序列化成我们的 Java 对象才行。

#### 实现代码

```java
public interface ShopService extends IService<Shop> {

    /**
     * 根据 id 查询商铺
     */
    Shop queryShopById(Long id);
}
```

```java
@Service
public class ShopServiceImpl extends ServiceImpl<ShopMapper, Shop> implements ShopService {

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    @Override
    public Shop queryShopById(Long id) {
        // 1.查询redis缓存
        String shopJson = stringRedisTemplate.opsForValue().get(CACHE_SHOP_KEY + id);

        // 2.判断是否命中
        if (StrUtil.isNotBlank(shopJson)) {
            // 3.命中，直接返回
            return JSONUtil.toBean(shopJson, Shop.class);
        }

        // 4.未命中，查询数据库
        Shop shop = getById(id);

        // 5.判断数据库中是否存在
        if (shop == null) {
            return null;
        }

        // 6.写入redis缓存
        stringRedisTemplate.opsForValue().set(CACHE_SHOP_KEY + id, JSONUtil.toJsonStr(shop));

        // 7.返回
        return shop;
    }
}
```

这里有几处细节值得专门说一下。

第一，返回之前一定要先判断它是否为空。为什么？因为我们拿到的是 JSON 字符串，如果为空去做反序列化处理，可能就会出现空指针异常。所以这块我们用 `StrUtil.isNotBlank` 做个判断：不为空就直接返回，返回之前需要把它转成 Java 对象，所以用 `JSONUtil.toBean` 把 shopJson 传进去，然后告诉它类型是什么，`Shop.class`，这样就拿到了 Shop 的结果。

第二，查完数据库以后也要判断存在不存在。如果不存在，直接返回错误就可以了，比如返回 `Result.fail` 告诉前端"店铺不存在"。当然也可以返回 OK 放空也行，这个是基于你和前端的一个约定。

第三，value 是什么？value 就是把这个 shop 转成 JSON 形式存进去，所以又要用 `JSONUtil.toJsonStr` 把 shop 放进去。这样我们的 Redis 里就一定会有这样一条店铺的信息了，下次再来查就可以直接命中返回了。

第四，同样的，像这个地方的这个字符串，我们也可以把它提取成一个常量，放到 Redis 的常量类里：

```java
public class MRedisConstant {
    public static final String CACHE_SHOP_KEY = "cache:shop:";
}
```

然后 `Ctrl + C` 回到刚才的业务逻辑里，把字符串替换掉，导一下包，这样就很优雅了。

#### 跑起来验证一下

我们重启一下，打开浏览器直接刷新就能测试。

查询成功，但你会看到这次查询的耗时还是比较久的，耗时了一秒多钟。

我们来看一下 Redis：刷新一下，`cache:shop` 是不是已经查到了？这个数据已经缓存进来了。这个时候我们再刷新一次——你看，这次查询速度是不是就快了很多？

那怎么证明数据库真的不查了？同学们，如果我们的缓存生效了，理论上讲数据库是不是就不应该再查询了。我们来验证一下：把 IDEA 里的日志清空，打开浏览器重新访问。你可能就会说了：怎么还有一些 SQL 语句？

> **结论**：整个流程的关键点就两个——一开始要从 Redis 查；在 Redis 未命中的情况下，需要去查数据库，并且把数据写入 Redis。大家注意这两点就够了。

### 课后练习：给店铺类型查询也加缓存

在上节课我给店铺查询的业务添加了 Redis 缓存，这里给大家留一个作业，检验一下大家是不是真正掌握了缓存的添加功能。

我们要求：给店铺的类型查询业务添加缓存。

在网站的首页上会有一个店铺类型的展示，它对应的接口就是 `/api/shopTypeList`。事实上这个接口在很多地方都会用到，因为店铺的类型经常性地要拿来做一些过滤，所以这个接口还是很常用的。而它对应的这些数据，往往是不怎么变化的一些数据，所以这一块是非常适合做成一个缓存的。

这里需要注意什么呢？我们之前做的业务返回值是一个对象，而这个地方的返回值你会发现它是一个**集合**。所以你做这道题的时候，需要慎重地去选择缓存的数据类型。

### 缓存更新策略

我们已经给商户查询的业务添加了缓存，大大降低了对于数据库的负载压力。不过就像我们之前说过的，缓存是一个双刃剑，它在带来好处的同时，也引入了一些问题。

首先是**缓存的一致性问题**。因为我们把数据同时保存在缓存与数据库当中，如果我们对数据库数据做了一些修改，缓存并不知道、也不会去更新，于是用户来查询的时候，查到的就是缓存中的旧数据，与数据库不一致——这在很多业务场景下是不允许的。

所以这一节我们要学习**缓存的更新策略**，正是为了解决这个问题。企业里常见的缓存更新策略主要有三种。

#### 内存淘汰

内存淘汰这种机制，其实原本是 Redis 用来解决内存不足的问题的。我们知道 Redis 是基于内存存储的，内存不像磁盘，它是有限的、比较珍贵的，往往会设置一个上限。那么如果说我们存储的数据越来越多，终究可能导致内存不足，于是 Redis 里面就会有一个内存的淘汰机制。这个机制我们可以自己去配置，它有好几种不同的策略，后边讲 Redis 原理的时候会再提。

但不管怎么样，当内存不足的时候，它就会触发这种策略，把一部分数据淘汰掉，这样就可以清空一段空间去存储新的数据。

这种机制默认就是开启的，不用我们管，所以我们不用去考虑 Redis 内存不足的问题。当然了，我们还是要尽可能节省内存空间的使用。

那它能不能保证数据一致性呢？在一定程度上是可以的。你想，当内存不足时它把一部分数据淘汰了，这部分数据在 Redis 里没有了，用户来查询这部分数据时，按照我们以前写的业务逻辑，未命中就会去查询数据库，然后把数据库的数据写入缓存——是不是就一致了？

> **易错点**：但是这种一致性首先不是我们能控制的。淘汰的时候它淘汰的是哪一部分数据、什么时候淘汰，我们都不知道。很有可能很长一段时间这些数据都不会被淘汰，因为内存一直都很充足。那这些不被淘汰的数据每次来查询，查到的都是旧数据，就无法保证一致性了。所以它的一致性是比较差的，也不是我们能控制的。不过它的好处是维护成本几乎等于无，因为你根本不用管，全部都用 Redis 自己去控制。

#### 超时剔除

超时剔除相对于内存淘汰来讲就会稍微好一点，因为它会利用 Redis 里面的 `EXPIRE` 命令给我们的数据添加一条过期时间，这个时间到期以后，Redis 会自动把数据删除。数据一旦删除，下一次用户来查未命中，是不是就会更新缓存了，从而确保一致性。

它的一致性强弱，其实取决于你设置这个时间的长短。如果你设置得短一点，比如说 30 分钟，那更新频率其实还是不错的；如果你设置得长一点，比如一天，那更新频率相对就会低一点。所以这个一致性是我们可以控制的。

> **提示**：当然，它也不是完全的一致。比如你设置 30 分钟，如果在这 30 分钟内数据库发生了变化，此时 Redis 数据与数据库数据还是不一致的。所以它不是一种强的一致，是一种最终的一致，一致性比较一般，但肯定好于内存淘汰机制。

从维护成本上来考虑，这种成本也不高、比较低，因为你只需要在原来设置缓存的那个逻辑上，添加一个过期时间就行了，还是比较简单的。

#### 主动更新

主动更新，简单来讲就是我们自己编写业务逻辑，每当我们要去修改数据库数据的同时，我们就去把缓存也给他改了，这样两者不就能够确保一致了吗？

> **注意**：它的一致性相对来讲是比较"好"的，注意我说的是好，而不是"完全保证一致"——因为没有任何人能确保你的程序一定是健康运行的，总会有一些意外。

但是它的成本比较高。为什么？因为你需要自己编码。原来只是写数据库，更新一下就行了；现在你还需要在更新数据库的同时对缓存也作出更新，所以业务编码比较复杂，维护成本比较高。

那该怎么选择呢？其实就看业务场景了。

**低一致性需求的场景**，什么样的数据是低一致性的？就是长久就不发生变化。你想我们之前讲的那个店铺类型的查询，就是首页顶部的那个，店铺的类型——美食、娱乐、运动、KTV，你说这些东西它会变吗？会，但变化的频率可以认为是极低。这时候我们完全可以采用默认的内存淘汰机制，实在不放心，你再加个超时时间就行了。

**高一致性需求的场景**，那你就要保证它的一致性尽可能好，这时候肯定要采用主动更新。但主动更新也不是百分之百能保证，所以以防万一，我们也可以加上一个超时剔除做一个兜底：万一主动更新失败了，将来超时的时候还可以把它干掉，也能保证一致性。所以往往以这个为兜底，两者结合去使用。高一致性的需求，比如我们的店铺详情、优惠券的一些缓存，其实都可以使用这种方案。

| 策略 | 一致性 | 维护成本 | 关键点 |
| --- | --- | --- | --- |
| 内存淘汰 | 差，不可控 | 几乎为零 | Redis 自带，淘汰哪部分、何时淘汰我们不知道 |
| 超时剔除 | 一般，最终一致 | 低 | 给 key 设 TTL，时长短则更新频率高 |
| 主动更新 | 很好 | 高 | 改库的同时改缓存，需自己编码 |

### 主动更新的三种模式

刚才说了，主动更新方案是最复杂的，那它到底复杂在哪里呢？我们来看一下它在企业里的三种常见模式。

**第一种是 Cache Aside**，也就是我们平时用 `@Cacheable` 这类注解自己编码的方式。简单来讲就是人工编码，我们自己写代码，更新数据库的同时把缓存也给它更新了。这种方式我们需要自己写一些代码，对于调用者来讲可能会稍微有些复杂，但是你是可以人为去控制它的。

**第二种叫 Write Through**。它是将我们的缓存与数据库整合成一个服务。这个服务你不要管它底层到底用的是什么，对外来讲它就是一个透明的服务。因为这个服务内部同时处理了缓存和数据库，所以它是可以保证两者的处理同时成功和失败的，由它来维护两者的一致性。也就是说，我们作为调用者只需要说"我今天要新增个数据了"，它可以保证你缓存里有、数据库里也有，所以你都不用管了，直接调就行了。调用者无需关心一致性问题，我们作为调用者是不是就非常简单了？这是它相对于方案一的一个好处。

当然它最大的问题是什么呢？维护这样一个服务是比较复杂的。市面上你想找到一个现成的这样的服务，可能也不太好找，所以你去开发起来成本还是挺高的。

**第三种叫 Write Behind**，也叫写回。这种模式与方案二有类似之处，它们的作用都是为了简化调用者的开发，调用者无需关心一致性。

区别在于：我们的一致性，方案二是由服务来控制的，调用者不知道自己到底是操作的缓存还是数据库，对外是透明的；而作为方案三的写回模式，我们的调用者明确地知道——**我只操作缓存**。注意了，我只操作缓存，我不关心数据库，我也不需要去处理数据库，我不需要处理一致性，我的增删改查全部在缓存里做。

那么谁来保证一致性呢？有一个独立线程，异步地将缓存数据持久化到数据库，保证一致。也就是说，你单独地去操作增删改查，全部在缓存里做，这样一来缓存的数据是不是最新，而数据库的还是旧的数据。好，现在有一个线程，及时地去看一看缓存里有没有变化，如果有，他就在帮我们把缓存数据写到数据库里去。原来有这个线程去做，你不用管，而且这个写是异步的，它会隔一段时间去执行一次。

那这样做有什么好处呢？比方说我们在缓存里做了十次写操作，而这十次结束以后，刚好轮到了异步更新的动作，那么他会把这十个操作合并成一次写操作往数据库里去写，做一个批处理——这样是不是就可以把多次对数据库的写合并成一次写了？效率肯定有大的提升。

而且还有一种特殊的情况：在两次异步更新之间，如果我们对缓存中的某一个 key 做了 $n$ 次更新，事实上只有最后一次更新有效，对不对？那我们在做一波更新的时候，只需要把最后一次的结果写入数据库就 OK 了。所以这就是我们这种异步机制的一个好处，效率比较高。

但它最大的问题是什么呢？第一，你要维护这样的一个异步任务是复杂的，你需要实时地监控缓存中数据的变更。其次，我们这个地方的一致性是难以保证的。你想我们先操作缓存，然后异步更新；如果我缓存已经执行了上百次操作了，这个时候还没有触发这个异步的更新，那么在这一段时间内，我们的缓存数据跟数据库完全是不一致的。而且如果此时缓存出现宕机——缓存大多数是内存存储的，一旦宕机数据丢失了，那这个时候就等于这段数据完全丢失了。所以它的一致性和可靠性都会存在一定的问题。

| 模式 | 调用者做什么 | 一致性由谁保证 | 代价 |
| --- | --- | --- | --- |
| Cache Aside（`@Cacheable`） | 自己写代码，更新数据库时同步处理缓存 | 调用者自己 | 代码复杂，但可控性最高 |
| Write Through | 只调一个服务 | 服务内部同时处理缓存与数据库，保证同时成功或失败 | 要维护这样一个服务，现成的不好找，开发成本高 |
| Write Behind（写回） | 只操作缓存 | 独立线程异步批量持久化 | 一致性难保证，缓存宕机会丢数据 |

> **结论**：综上所述，尽管方案一需要我们的调用者自己编码、相对来讲可控性更高一点，因此一般情况下我们在企业里用得最多的正是这个方案——Cache Aside。

### Cache Aside 要想清楚的三件事

Cache Aside 需要我们的开发者自己去编码，因此在编码的过程当中，我们还是需要去考虑几个问题。

#### 更新缓存还是删除缓存

第一个问题：既然我们需要在更新数据库的同时去更新缓存，那这个地方就有两种——一种更新，一种删除。

更新就不用多解释了吧：你数据库做了什么样的更新，我们的缓存也做什么样的更新。删除是什么意思呢？你对数据库做了更新，我不更新缓存，我是直接删缓存。

这两个会带来什么样的差异呢？你想，因为更新缓存是每次更新数据库都更新缓存，如果我对数据库做了上百次操作，那么我就需要对缓存也做上百次操作。但如果在这上百次操作的过程当中，没有任何一个人来做查询，也就是写多读少，那这个时候你对缓存做的 $n$ 次修改是不是都是无效的？

而删除操作则不存在这个问题。为什么？因为我更新数据库时让缓存失效、把它删了就好。我更新了 100 次，其实只删一次是不是就够了？而在这 100 次之间如果没有任何人来访问，我也不会去更新缓存；什么时候有人来访问了，什么时候我去更新缓存——这样是不是等于是一种延迟加载的模式？

> **结论**：因此这种方案写的频率更低，有效更新会更多。所以我们一般会选择删除缓存这个方案，而不是更新缓存。

#### 原子性：事务与分布式事务

第二个问题：更新数据库的同时要去删缓存，你需要确保"更新数据库"与"删除缓存"这两个操作同时成功或失败，也就是保证两个操作的原子性。如果说我更新数据库的时候，删缓存这件事失败了，那这不就没有意义了吗？

怎么保证同时成功失败呢？**如果是一个单体系统**，就像我们现在这个案例都是单体系统，缓存和数据库在一个项目当中，甚至于我们是在一个方法里，我们可不可以把它做成一个事务？可以。所以我们利用事务本身的这种特性，就能保证同时成功和失败。

**但如果是一个分布式系统**，我们的缓存操作和数据库操作很有可能是两个不同的服务，那你怎么保证这两个东西的一致性呢？这个就不得不用到类似于 TCC 这样的分布式事务方案了。有同学可能不知道什么叫分布式事务，如果有兴趣或者有疑问，可以去 B 站上搜索一下我讲解的另外一门 Spring Cloud 微服务课程，史上最全的微服务课程，里面可以讲到全套的微服务各种问题及解决方案，包括了分布式事务的解决方案。

最后还要考虑一个线程安全的问题。我们在操作的时候，因为有缓存操作、数据库操作两个操作，那么在多线程并发的情况下，这两个操作之间可能会有多个线程同时穿插执行，这时候谁先谁后就带来了不一样的线程安全问题。先删缓存、再更新数据库，还是先写数据库、再删缓存，其实都 OK，具体选哪一个我们需要对比之后再来看。

#### 线程安全之一：先删缓存，再更新数据库

先看正常情况。假设缓存和数据库里初始化时都是 10，有两个线程并发执行。我们知道线程的执行顺序往往是无法控制的，CPU 在这之间去做切换，你也不知道它会限制谁。

假设线程一要来更新缓存，按第一种方法，它先删缓存，把 10 删掉了；然后更新数据库，把数据库更新成 20。到这儿线程一的操作其实就结束了。结束后不管是谁、任意一个人只要来查询，都会出现一个情况：缓存没了，未命中。未命中他会干什么？是不是要查数据库，这时候数据库值是几？是不是 20，所以他此时得到的是 20，得到 20 以后再把数据写到缓存，写进去的还是 20。所以这个时候两者是一致的。

好，我们再来讨论异常情况。现在缓存和数据库都是 10，异常情况是指在线程一执行的过程中，另外一个线程它也进来执行了——因为我们没有加锁，所以他们是可以并行执行的。

```text
初始：缓存 = 10，数据库 = 10

时刻   线程A（更新：先删缓存，再更新数据库）   线程B（查询）
─────────────────────────────────────────────────────────────
 t1    删除缓存
 t2                                          缓存未命中
 t3                                          查数据库 → 拿到 10（旧值）
 t4                                          把 10 写回缓存
 t5    更新数据库 → 20
 t6    结束

结果：缓存 = 10，数据库 = 20   →   不一致
```

线程一先删了缓存，缓存没了，接着它要去更新——但因为更新的业务比较复杂，所以这个时候谁趁虚而入呢？线程二趁虚而入，它去查询。因为这边把缓存删了，它来查询的时候缓存显然是未命中的，未命中它就会查数据库。那因为它是趁虚而入的，此时数据库还没有完全更新，所以依然是旧的值，他查到的就是旧的 10。紧接着他就去写入缓存，写的是不是这个旧的 10？他写完了。

这个时候线程一终于开始执行这个更新的操作了，把值改成 20，于是数据库数据就与缓存数据产生了不一致的情况。

那这种线程安全问题发生的概率高不高呢？其实还是挺高的。为什么？因为你是删缓存、更新数据库——删缓存很快，但是更新数据库的动作是不是很慢？你首先要组织数据，然后去更新，而且这是个写操作。而线程二干什么呢？线程二查询缓存未命中，然后直接把数据写回缓存；写缓存因为写的是 Redis，写操作往往是非常快的，微秒级别的。所以它跟写数据库相比更快，查也很快、写也很快，那么这个操作很有可能就在他俩之间执行。所以这种情况发生的概率还是挺高的。

#### 线程安全之二：先写数据库，再删缓存

我们再来看第二种方案。这次先假设线程二来完成更新，他的操作是先数据库再删缓存。

先看正常情况。现在更新数据库，把值改成 20，更新完数据库后去删缓存，缓存一删就没有了。这时不管谁、任意一个人只要来查询，都会触发缓存的同步——因为未命中、未命中都要去查，他查到的不就是更新好的数据库数据了吗？也就是 20。那他去写缓存的时候，缓存里的自然也就是 20，保持一致了。当然这是正常情况，两个线程穿插的情况有可能，我们下边再来看看异常的情况。

```text
初始：缓存 = 10，数据库 = 10

时刻   线程A（更新：先写数据库，再删缓存）    线程B（查询）
─────────────────────────────────────────────────────────────
 t1    更新数据库 → 20
 t2                                          恰好缓存失效 → 未命中
 t3                                          查数据库 → 拿到 10（旧值）
 t4    删除缓存（本来就没有，删了等于没删）
 t5    结束
 t6                                          把 10 写回缓存

结果：缓存 = 10，数据库 = 20   →   仍然不一致
```

这种情况发生的可能性高不高呢？大家思考一下，它发生要这么几个条件：首先两个线程并行执行；其次线程二来查询的时候恰好缓存失效了——比如有可能是缓存时间到了；然后呢，恰好失效的同时，他查完了数据库要去写缓存。注意咯，是查完数据库写缓存，写缓存的操作往往是不是微秒级别的？就在这个微秒的范围内，突然来了一个线程，他先去更新数据库。同学们更新数据库的速度往往是比较慢的，更新完了以后，尤其是删缓存——然后才轮到这哥们儿写。

大家想象一下，在这一个微秒甚至非常短的时间内，要完成这么多数据库的写操作，可能性高不高？显然不高。因为缓存的速度是远远高于数据库的，你不太可能你的数据库更新操作竟然比我的缓存操作还要快。

所以这个可能性是比较低的，要同时满足这样三个巧合。而方案一我们刚才分析过，它出现的可能性是比较高的。

> **结论**：这两种方案都有可能发生线程安全问题，但是方案二相对来讲出现的可能性更低——但也不是完全没有，这个概率可以认为是极低、几乎不太可能发生。可是一旦发生了怎么办？将来加上一个超时时间就行了：我们在写缓存数据的时候加上一个时间，万一我写了旧数据，没关系嘛，过一段时间是不是也会清除。

所以从线程安全的概率角度来分析，最终胜出的就是方案二——先操作数据库再删缓存这种方式。

### 缓存最佳实践

我们把缓存同步策略全部讲完了，最后做一个总结：缓存更新策略的最佳实践方案。

我们讲了低一致性和高一致性两种场景，总共三种策略——内存淘汰、超时剔除和主动更新。

- 对于**低一致性**，一般我们用自带的淘汰机制就行了，最多再加一个超时时间；
- 对于**高一致性**要求，我们就必须去做主动更新，并且辅以超时剔除作为兜底，因为只有这样才能在发生意外的时候保证数据的恢复；
- 主动更新的三种模式里，后两种实现起来相对复杂，而且也找不到比较好的第三方组件，所以一般情况下企业里选择都是 Cache Aside。

而 Cache Aside 我们又讲了好多问题要考虑：

**更新还是删除缓存？** 删除更好，因为更新有太多的无效写操作了。

**如何保证原子性？** 单体系统天生就是原子系统，利用事务；分布式系统可以利用分布式事务方案，保证原子性——同时成功、同时失败。

**线程安全问题怎么保证？** 我们选择的是先写数据库、再删缓存，因为它的线程安全问题发生概率最低。

所以最终我们的方案就确定下来了：**当我们要去写的时候，我们先写数据库再删缓存，这种发生线程安全问题的可能性最低。** 这是写的时候。那我们在读的时候呢？读的时候跟以前来讲变化不大：读就是去看一下缓存有没有缓存，如果有直接返回；没有就查数据库，查完数据库以后还要把它写回到缓存里。但是要注意这个区别了——**写缓存的时候要设置一个超时时间，作为兜底方案。**

这就是我们最终的缓存最佳实践方案了。

## 商铺查询缓存：双写一致、穿透与雪崩

动手的目标也很小——就是给查询商铺的缓存把这两条策略真写进去：

- 更新的时候，先改数据库，再删缓存。

### 双写一致：查询补超时，更新删缓存

#### 查询时补上过期时间

先看查询业务。我们原来的逻辑是：判断缓存有没有命中，命中直接返回；没命中就去查数据库，然后把数据库结果写入缓存。这一版的改动只有一处——**写入缓存的同时设置超时时间**。

```java
// 查询店铺
Shop shop = queryShopById(id);
if (shop == null) {
    return Result.fail("店铺不存在");
}

// 写入Redis，同时设置过期时间
String key = SHOP_CACHE_KEY + id;
redisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_TTL, TimeUnit.MINUTES);

// 返回
return Result.ok(shop);
```

> **提示**：那个 `30` 和 `TimeUnit.MINUTES` 就是超时剔除的抓手。方法最后那个时间单位参数千万别漏，只写 `set(key, value, 30)` 的话，Redis 认的是**秒**，30 秒就过期了，和你想要的半小时差了六十倍。

至于这个 30 分钟，它在业务里的含义就是这条缓存的 **TTL（有效期）**。既然它是个业务上反复要用的值，就别在方法里写死了，提取成常量放到我们的 `RedisConstants` 里：

```java
public class RedisConstants {
    public static final String SHOP_CACHE_KEY = "shop:";
    // 缓存有效期，30分钟
    public static final Long CACHE_TTL = 30L;
}
```

回到查询方法里直接引用常量即可。第一块需求，查询业务的改造就完成了。

#### 更新时把逻辑下沉到 Service

第二块需求在更新侧。我们现在的 `updateShop` 是什么样子呢？它直接调用 MyBatis-Plus 提供的 `updateById` 方法，一行就更新完了，**根本没有缓存什么事**。

问题在于：缓存逻辑放不到 Controller 里。所以要先把更新这件事从 Controller 下沉到 Service 层，Controller 只负责调用 `shopService.update(...)`，具体的实现到实现类里补上。

这个更新方法要做的事情，我们早就分析过了，就两步：**先更新数据库，再删除缓存**。更新数据库，直接调 `updateById`；删除缓存，用 `StringRedisTemplate` 把 key 删掉。

这里有两个细节必须处理：

**第一，key 怎么拼。** 删除用的 key，和我们写入缓存时用的 key 是同一个——就是一个前缀后面拼上店铺的 id。而这个 id 只能从传入的 `shop` 对象里 `getId()` 出来。

**第二，id 可能为空。** 你想，如果 id 根本不存在，你这么去拼 key 是不是就出问题了？所以拼之前必须对 id 判空，判空直接返回错误，提示"店铺id不能为空"，这种情况下我们根本不去做任何更新。

**第三，事务。** 删除缓存的过程中如果抛了异常，将来我们这块的事务是不是要跟着回滚？所以整个方法必须是一个统一的事务，加一个 `@Transactional`。

```java
@Override
@Transactional
public Result update(Shop shop) {
    if (shop.getId() == null) {
        // 店铺id不能为空
        return Result.fail("店铺id不能为空");
    }

    // 1. 更新数据库
    updateById(shop);

    // 2. 删除缓存
    String key = SHOP_CACHE_KEY + shop.getId();
    redisTemplate.delete(key);

    // 3. 返回
    return Result.ok();
}
```

Controller 那边 correspondingly 就只剩下调用了：

```java
@PutMapping("/shop")
public Result updateShop(@RequestBody Shop shop) {
    return shopService.update(shop);
}
```

> **结论**：我们现在是一个单体项目，数据库操作和缓存操作都在**同一个方法**里，所以用事务就能控制住它们的原子性，缓存的同步更新就这么直接实现了。

但如果你做的是**分布式系统**，这块就麻烦一点了：你这边更新完数据库，删缓存这个动作可能根本不是你来做的，而是另外一个系统通过 MQ 异步通知对方去完成。这时候想保证两边的一致性，就必须借助于我们之前讲过的方案，比如 TCC 这样的，才能保证强一致性。

#### 跑一遍：缓存建了、删了、又重建了

功能写完了，我们重启、清空日志，实测一遍。

**第一件事，验证 TTL 有没有真的写进去。**

打开浏览器访问"101 茶餐厅"。注意，此刻缓存里其实已经有数据了（我们之前跑过），所以走的是缓存命中，IDEA 里只看到对 mocha（优惠券）的查询，对店铺根本没有查询。

那怎么验证新加的过期时间？很简单：**先把 Redis 里的缓存全清空**，让它重新走一次 miss 的路径。浏览器里刷新，这次能看到 IDEA 里触发了 `select ... from tb_shop ...` 的 SQL，说明确实回源查库了。

这时候打开 Redis 客户端刷新，你会看到 key 旁边有个 `TTL 1775`，而我们设置的总量是 `1800` 秒。

> **结论**：`TTL 1775 / 1800` 就证明过期时间确实写进去了，超时剔除这块已经触发了。

**第二件事，验证更新会不会带动缓存。**

更新这个动作一般是由管理端发起的，而我们现在浏览器里看的是面向用户的端，不是商家后台，所以页面上点不出这个更新操作，只能借 Postman 这样的工具。

在 Postman 里我们已经准备好一条请求：`PUT 8081/shop`，参数就是刚才那个 101 茶餐厅的店铺信息。随便改一改，把"101 茶 3 厅"改成"102 茶 3 厅"，点 Send。

这边拿到 `200 OK`，说明更新成功了。切回 IDEA，能看到 `updateById` 被调用了，下面跟着一条 update 操作，证明更新确实执行了。接着去数据库里校验：`tb_shop` 表刷新，店铺名变成了"102 茶 3 厅"。

再打开 Redis 刷新——**没有了**。

这就是我们定的策略：数据发生更新的时候，把缓存移除。此时如果有用户在浏览器里再次刷新，他看到的**一定是最新的"102 茶 3 厅"**，而且这个时候缓存会被重建。

回到 Redis 再刷新一下，值变成了"102 茶 3 厅"。缓存重建完成。

> **结论**：每当数据库发生更新，缓存会被移除；用户再去查询就能查到最新数据。数据库与缓存的数据同步，到此就打通了。

### 缓存穿透：两边都查不到的请求

前面几节课我们讲的是企业使用缓存的基本用法和最佳实践，接下来进入难点和热点问题。这些问题面试的时候也经常碰到，很多同学可能都听说过——缓存穿透、雪崩、击穿等等。

先看穿透。

> **定义**：**缓存穿透**是指客户端请求的数据，在缓存中和数据库中都不存在的一种情况。

既然两边都不存在，那它永远就不可能建立缓存。只要有人来请求，它就一定会到达我们的数据库。用图来表示会更直观一些：

```text
    客户端              Redis                 数据库
      |                  |                      |
      |-- 请求 id ------>|  没有这个 key        |
      |                  |----- 查询 --------->|
      |                  |<---- 也不存在 ------|
      |<-- 返回空 -------|                      |
      |                  |                      |
      |-- 再请求一次 --->|  还是没有            |
      |                  |----- 查询 --------->|  <-- 每次请求都落到库
      |<-- 返回空 -------|                      |
```

读一下这张图：客户端传了一个 id过来，Redis 里根本没有，我们就不得不去查数据库，结果数据库里也不存在——这哥们传的 id 有可能是他自己瞎编的。数据库只能返回一个空给他。可他一看是空，他又来请求，那又请求是不是又是空？最终**每一次请求都会到达数据库**。

如果是一个不怀好意的人，他构造无数个不存在的 id 并发地来请求，这些请求就全部打到数据库上，很有可能就把我们的数据库搞垮了。这就是缓存穿透带来的危害。

怎么解决？企业里最常见的就两种方案。

#### 缓存空对象

第一种叫**缓存空对象**，它是一种简单粗暴的处理方案。思路是这样的：

你来请求我，我这里 Redis 里没有，然后我去数据库，数据库也没有。好，为了让你不再请求我，那我就把这个空的值缓存到 Redis 里。也就是说，你请求的这个 id 我数据库里根本没有，我也给你缓存起来。那么下次你再来的时候，我是不是就能命中了？尽管命中的是个 null，是不是也命中了？这样你是不是就不会请求我的数据库了？

它的**最大优点就是简单**——无非就是不存在的时候我把 null 写进去呗，实现起来代码非常容易。

缺点也比较明显。

**第一，额外的内存消耗。** 我随便传了一个 id，结果你给我缓存起来了；我编各种各样的 id 都不存在，你都给它缓存起来了。你在 Redis 里缓存了很多很多这样的垃圾，是不是？

不过针对这个问题其实也能解决：**缓存 null 的时候给它加一个 TTL**，设置一个比较短的 TTL，比如五分钟甚至约两分钟。两分钟一到，这个东西是不是就清掉了？在我们这两分钟内它的缓存是有效的，能对恶意请求起到一定的保护作用；同时它有效期也不长，这些垃圾数据过段时间就会清除，也不会带来特别大的内存消耗。

**第二，可能存在短期的不一致性。** 你想，现在用户请求了一个 id，这个 id 刚好不存在，我们给他设置了 null。就在此时，我们真的给这个 id 插入了一条商铺的数据——这个时候数据库里已经有了，但是我们却缓存了一个 null。用户来查询查到是 null，而实际上是存在的，这是不是就出现不一致了？只有当这个 TTL 过期以后，用户才能查到最新的数据。

针对这个问题，只要控制好 TTL 的时间，在一定程度上是可以缓解的——不一致的时期只要足够短，其实也是可以接受的。当然如果你实在是无法接受这个不一致，也可以这么做：**当我们新增一条数据的时候，主动地把这条数据插入缓存中，覆盖之前那个 null**，是不是也能解决。

好，这就是缓存空对象的优缺点。

#### 布隆过滤器

第二个解决方案叫**布隆过滤器**。准确来讲它其实是一种算法，它的原则跟缓存空对象完全不一样。

它的做法是：**在客户端与 Redis 之间，又加入了一层拦截，叫做布隆过滤器。**

```text
  客户端 ──> 布隆过滤器 ──> Redis ──> 数据库
                 │              │          │
        判定不存在：直接拒绝    未命中      查不到
        判定存在：才放行 ────> 才继续往下走
```

读一下这张图：用户请求来了，不是上来就去查，先去找布隆过滤器问一问，这个数据存在还是不存在。**如果不存在，直接拒绝，就不给你机会往下走了**；如果布隆过滤器告诉你说存在，它才会去 Redis 里查询，后面的逻辑跟以前一模一样——Redis 里有就直接返回，没有就查数据库，数据库有就缓存到 Redis 并返回。

也就是说后续逻辑不变，仅仅是在前面加了一个前置的过滤。

有同学会问了：**布隆过滤器它怎么知道我这个数据有还是没有呢？难道它里面存储了数据库中的所有数据吗？**

不是的。那如果这样，我们不是就多余存储了很多数据了吗？

布隆过滤器的原理其实可以简单理解成：**它就是一个 bit 数组，里面存的就是二进制位。** 当我们要去判断数据库中的数据是否存在时，并不是真的把数据存到布隆过滤器里，而是把这些数据基于某一种**哈希算法**计算出哈希值，然后再将这些哈希值转化为二进制位，保存到布隆过滤器里，就是对应的这种零一的形式。

而后我们去判断数据是否存在时，其实就是判断对应的那个位置是零还是一，以此来判断数据是否存在。

> **易错点**：这种"存在与否"是一种**概率上的统计**，它并不是百分之百准确的。当布隆过滤器说不存在的时候，那是真的不存在；但当它告诉你存在的时候，其实那就不一定是存在的。

所以你想想看，如果我现在来请求布隆过滤器，它告诉我这个数据存在，放心了；然后我去 Redis 结果没发现；然后我又去数据库，结果又没发现——那是不是**又一次出现穿透**了？所以布隆过滤器还是有一定的穿透风险的。

它的**优点是内存占用少**。因为它不用像之前那样缓存大量的空数据，只是用一个二进制位的形式保存数据，空间占用非常小。

> **提示**：Redis 的 **bitmap（位图）** 就是布隆过滤器最典型的实现载体，后面讲 bitmap 的时候会把具体原理展开，这里先大概了解就行。

它的**缺点**有两个：一是实现起来相对复杂，如果你想自己去实现布隆过滤器，其实还真的挺麻烦的；好在我们 Redis 里其实提供了 bitmap 这种方式，它是自带的一种布隆过滤器的实现，可以帮助我们简化开发。二是存在误判的可能，也就是我们刚刚聊过的，不一定准确。

所以在我们实际开发过程中，会选择**缓存空对象**这种方案来解决缓存穿透问题。

### 给查询商铺加上穿透保护

方案选定了，这节课我们动手实践，给查询商铺的业务加上缓存穿透的保护。

在业务流程上，我们会有什么样的变化？来看一眼原来的完整流程：

1. 前端提交店铺 id 去查询；
2. 先从 Redis 里查，命中就直接返回；
3. 未命中就去查数据库，数据库里如果有，就先把它写到 Redis 里，然后再返回给数据库。

第 3 步这里，就出现了穿透的风险了。

要解决缓存穿透，也就是在**数据库里不存在**的时候我们要做什么修改？是不是应该把这个空的值也给它写到 Redis 里去？这样下次再来的时候，就能够读到 Redis 里的这个空值了。

到这就结束了吗？没有。你既然把空值写到 Redis 了，就会导致一个问题——当我们从 Redis 命中时，**你命中的就不一定是商铺信息了，还有可能是空**。所以命中以后，是不是还要对这个结果做一个判断？判断一下命中的是不是空：命中的如果不是空，那代表是商铺，我就可以返回商铺信息；但命中的如果是空，咱们是不是等于直接返回空就行了？

所以在这块我们有两个地方需要变化：

- 一个是**商铺在数据库里不存在的情况下**，要把它写的 Redis；
- 另一个是**缓存命中以后**，看一看命中的是什么。

#### 查不到时，把空串写进 Redis

先改写入这一部分。查询店铺，如果说不存在，我们之前是直接返回了一个错误信息；那么现在我们不仅仅要返回错误信息，还要**将空值写 Redis**，然后再去返回错误信息。

写 Redis 的代码跟之前基本上一致，变化在于：写进去的不是那么一串东西了，而是个空——空字符串就行了。而且**有效期不能像真实数据设置那么长**，真实数据当初设计的是 30 分钟；下面我们给它重新写一个短一点的，专门叫 `CACHE_NULL_TTL`，就是空值的有效期，比如设置成两分钟或者三分钟都可以。

```java
// 查询店铺
Shop shop = queryShopById(id);
if (shop == null) {
    // 缓存空值
    String key = SHOP_CACHE_KEY + id;
    redisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);

    // 返回错误信息
    return Result.fail("店铺不存在");
}
```

常量这边也加一个：

```java
// 空值缓存有效期，2分钟
public static final Long CACHE_NULL_TTL = 2L;
```

这样一来，下一次来查询的时候，如果还是查询这个 id，它其实就能够命中了——但命中的**不是店铺数据，而是个空字符串**。

#### 命中之后，再判一次是不是空

这就要求我们在读取侧多做一个判断。我们通过 `StrUtil.isNotBlank` 来判断的时候，它分这么几种情况：**只有在真正里面有字符串的时候才是 true**，剩下的 null、空字符串，还有纯空白这类，都属于是 false。

所以同学们想想看，也就意味着**只有是有商铺数据的情况下它才是 true**。我们这个空字符串是不是也是 false呀？所以 `isNotBlank` 是肯定不成立的，它会往下走——但是往下走它就去查数据库去了。那不行，我们还要再多判断一个什么？**判断一下空值，命中的是否是空值。**

如果是空值，我们是不是还要去返回一个结果，而不能是查数据库？所以在这里加一个 `if`：

```java
// 1. 查Redis
String key = SHOP_CACHE_KEY + id;
String json = redisTemplate.opsForValue().get(key);
Shop shop;

// 2. 命中非空数据，直接返回
if (StrUtil.isNotBlank(json)) {
    shop = JSONUtil.toBean(json, Shop.class);
    if (shop != null) {
        return Result.ok(shop);
    }

    // 命中空值，直接返回错误
    return Result.fail("店铺不存在");
}

// 3. 未命中，查询数据库
shop = queryShopById(id);
if (shop == null) {
    // 缓存空值
    redisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
    return Result.fail("店铺不存在");
}

// 4. 写入Redis
redisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), CACHE_TTL, TimeUnit.MINUTES);

// 5. 返回
return Result.ok(shop);
```

这里的关键判断条件是 `shop != null`。因为前面已经判断过有值的情况了，所以下边其实只有两种情况：**要么是 null，要么是空字符串**。既然不等于 null，那就一定是空字符串了——所以直接返回一个错误信息，说"店铺不存在"就可以了。

于是整个逻辑就齐了：

| 命中情况 | Redis 里是什么 | 怎么处理 |
| --- | --- | --- |
| 命中真实数据 | 商铺的 JSON | 直接返回商铺信息 |
| 命中空值 | 空字符串 | 直接返回错误，不查数据库 |
| 什么都没命中 | null | 去查数据库 |

这样是不是就可以解决缓存穿透的一个问题了？

#### 跑一遍：第二次查询没有 SQL

逻辑写完，重启测试。

打开浏览器先查一个存在的数据，比如刚才那个 101 茶餐厅。当然是命中的，没问题。

现在我查询一个**不存在**的数据试一试，比如查一个 0 号 id——同学们，根本没有，对不对。走完之后我们打开数据库看一下：这块其实是有一个查询店铺的 SQL 语句的，`select ... from tb_shop`，有这样的一次请求。

那现在把这个日志清空，**再查一次** 0 号 id，然后回到 IDEA——你看这次有查询没有？没有。

> **结论**：这说明我们的请求根本没有到达数据库，也就是没有给数据库带来任何请求压力。

为什么？因为我们在 Redis 里建立了空值。打开 Redis 客户端刷新一下，这里边就有两个 key 了，其中一个是 `shop:0`，这个 0 号其实就是空。那是不是就解决缓存穿透的问题了？

回过头再做一个总结。**缓存穿透产生的原因**是什么？就是因为用户查询的这个数据，在缓存当中和数据库中都不存在，这样一来这样的请求一定会到我们的数据库，就会给数据库带来非常大的压力。

**解决方案**我们上课提到两种：一种是缓存 null 值，一种是布隆过滤。我们采用的是缓存 null 的方式，把 null 值缓存下来，下次再请求的时候就会命中 Redis 了，尽管命中的是一个 null，但至少命中了，不会对数据库带来压力。这种方式优点是简单、粗暴，缺点是会带来额外的一些内存存储压力，还有短暂的一些不一致性。

布隆过滤基于的是一种特殊的算法，对数据做一种统计，判断一下存在不存在——存在就让你往后走，不存在就不让你往后走。但是这种判断它的准确性不能保证，有一定的误差，并且实现起来相对有一些复杂，所以我们并没有采用这种方案。

### 穿透不只能被动补，还能主动防

但是我们的缓存穿透啊，不是说仅仅能依靠这两种方案去解决。这两种啊，其实属于是一种**被动的方案**，你想办法去弥补，对吧。

那么事实上，我们也可以**主动地**采取一些措施来解决。

**一是可以增加 id 的复杂度**，避免让别人猜到你 id 的一些规律。那这样一来，他就不太容易输入一些自己编的 id 了。id 有复杂度、有了一定的规律性，你就可以去加强这种基础的参数格式校验。比方说你看刚才我们在浏览器输的是不是有个"0"？你像 0 这样的 id 不可能存在对不对。而且我们别的 id 是 1、2、3，其实这种 id 都是不太好的——真正的 id 一定要有一定的格式的规范，比如说长度我们都保证它在十位或者是二十位，然后前面用什么样的方式去弥补，然后又有什么样的一些规律性。

这个时候我们接到这个 id 以后，就可以做一些基础的格式校验，看它是否符合我们 id 的规范，像"0"这种不符合的，是不是可以直接就 pass 掉了？主动地做好这种防范，而不是被动的等待。

**二是可以加强用户权限的管理**。不是说任何人都能去访问我们的服务，比如说要求你先登录；登录以后，我们还可以对用户去做**限流**——什么样的用户可以访问，这样的一个用户访问我们的时候，它有什么样的一个频率的限制。而且我们还可以对一些**热点参数**做限流，比如说有些商品访问的就是多，我们是不是也可以去做限流；对于一些这种空值的参数，我们也可以去做一些限流。这样就可以避免对数据库带来额外压力。

虽然我们这里并没有去操作，但是这些都可以去做。

### 缓存雪崩：集体过期与 Redis 宕机

上节课我们解决了缓存穿透的问题，接着来分析缓存雪崩。

> **定义**：**缓存雪崩**是指在同一时段内有大量的缓存 key 同时失效，或者 Redis 服务直接宕机，导致大量请求到达数据库、带来巨大压力的情况。

听名字就知道了，那肯定是发生了比较严重的事故了。我们同样以图的方式来演示，会比较清晰。

正常情况下是这样的：

```text
  客户端 ──┬── 大部分请求 ──> Redis ──> 直接返回
           │
           └── 少数未命中 ──> 数据库
```

可是呢，如果说突然之间大量的 key 都失效了——比方说这些 key 都过期了，一瞬间几万甚至几十万的 key 都过期了，那么这些请求是不是都会直接打到我们的数据库？这个时候是不是就可能导致数据库压力过大而出现服务宕机。

```text
情况一：大量 key 同时过期

  客户端 ──几乎所有请求──> Redis（大批 key 同时失效）
                               │
                               └──────> 数据库   ← 压力剧增，可能宕机
```

第二种情况呢是**更可怕**的。刚才仅仅是部分 key 过期了，而第二种情况是 **Redis 服务直接宕机**了。

```text
情况二：Redis 服务直接宕机

  客户端 ──所有请求────> Redis（服务不可用，无法访问）
                            │
                            └──────> 数据库   ← 等于数据库裸奔
```

比方说现在这是我们的 Redis，突然之间它挂了。它挂了以后，客户端再来访问，是不是所有的 key 都可以认为是失效了、都无法访问了？那也就意味着它接收到的一切请求都会访问到数据库，就等于是**裸奔**了，是原始状态了。那这个时候数据库肯定完蛋。

所以这两种情况相比较起来，宕机这种情况更严重一点。那我们该怎么解决呢？它有这么几个解决方案。

#### 让 TTL 散开

第一个是针对 **key 同时失效**这个问题。key 同时失效，肯定是因为它们的 TTL 一起到期了。为了避免它们的 TTL 一起到期，我们可以**给不同的 key 添加一个 TTL 的随机值**。

这是什么意思呢？平常做缓存预热的时候，我们可能提前把数据库中的数据导入到缓存当中，那就是**批量地导入**的。在批量导入的过程中，因为是同一时刻导入的，它们的 TTL 设置的是同一个值，很有可能将来时间一到，所有的都一起过期了，那就会出现雪崩。

为了解决这个问题，在做缓存预热、批量导入数据的时候，我们可以给这个 TTL 的后边跟上一个随机数。比如说我们的时间是 30 分钟有效期，然后我在后面跟上一个 1~5 之间的随机数，那么它的有效期是不是就会在 30~35 分钟之间波动了？当然你也可以扩大这个随机数，这样的话就可以让这些 key 过期的时间分散在一个时间段内了，而不是一起失效。

```java
// 批量预热时，为每个 key 打散过期时间
redisTemplate.opsForValue().set(key, value, CACHE_TTL + RandomUtil.randomInt(1, 5), TimeUnit.MINUTES);
```

这就是解决思路，非常简单，谁都会做。

#### 集群与哨兵挡住宕机

第二个，Redis 宕机导致的才是问题最严重的。那针对这个问题该怎么解决呢？

首先我们肯定是要**尽可能地避免 Redis 的宕机**，也就是提高整个 Redis 的**高可用性**。要想提高高可用性，我们就必须借助于 Redis 的集群、Redis 的哨兵机制。

Redis 哨兵可以实现一种服务的监控：比如说我们先搭建 Redis 集群，形成主从；如果说有一台机器宕机了，比如主宕机了，哨兵可以自动地从从机里面选出来一个，去替代原来的主，这样就可以确保 Redis 一直能够正常地对外提供服务。而且我们的主从还可以实现一种数据的同步，如果说主宕机了，从上面还会有数据，也不会导致数据的丢失。所以这样就可以在很大程度上保证我们 Redis 的高可用性。

> **提示**：有同学会问，这个集群应该怎么做呀，我们没学过。别着急，在后面 Redis 的高级课程当中，我们就会给大家讲解 Redis 各种各样的集群怎么去用、用的时候有什么技巧。大家继续关注，一定能 get 到这些技能。

#### 降级限流与多级缓存

第三个，我们还可以给**缓存业务添加一些降级和限流的策略**。

比方说出现了一些人们无法抗拒的超级严重的事故——我这整个服务器挂了，好吧，整个机房挂了，结果是我的整个 Redis 全部完蛋了，整个集群都完蛋了。那你这个可用性怎么保证？此时我们就可以给服务添加一些降级、限流的策略。

也就是说，**提前做好一些容错处理**：当我们发现 Redis 出现故障时，我们应该及时地去做服务降级，比如说**快速失败、拒绝服务**，而不是把请求继续压到我们的数据库上去。这样做的话，其实就可以保护我们的数据库了——牺牲部分服务，但最终保护了我们整个数据库的健康。

> **提示**：限流、隔离、降级这套怎么来做，我这也没展开过。在 B 站上搜索 **spring cloud**，找到黑马程序员提供的"史上最全的 Spring Cloud 微服务"课程，那里边有全套的微服务安全保护措施，限流降级全都有。

最后，我们还可以**给业务添加多级缓存**。何为多级缓存呢？举个例子。我们最开始讲，缓存的使用场景是多种多样的——浏览器是可以添加缓存的，但浏览器的缓存一般缓存的是**静态的数据**，而对于一些需要从数据库查询的**动态数据**是无法做缓存的。那么对于这部分，我们还可以在**反向代理服务器 Nginx 层面**去做缓存。

```text
  浏览器(静态缓存) ──> Nginx(代理层缓存) ──> JVM 本地缓存 ──> Redis ──> 数据库
```

Nginx 缓存未命中了，再去找我们的 Redis；Redis 为空再到达 JVM，我们还可以在 JVM 内部建立本地缓存；最后才是数据库。就是在多个层面建立缓存，这样 Redis 这一环崩了，还有很多别的缓存可以去弥补。

> **结论**：这就好比我这个防弹衣我穿了五件，你一枪打了我一件，我还有两件三件四件是吧，我这一层一层的。所以通过多级缓存的方式，就可以有效地避免这种雪崩导致的问题了。

这种多级缓存方案往往在一些大型的互联网电商项目里会有用到，比如京东的商品详情，他们都会去添加这种多级缓存，从而应对这种高并发。

## 缓存击穿：用 SET NX 互斥锁把重建风暴关在门外
> 对应块：BLK11 | 覆盖分集：P43-P44 | 块标题（分集名）：《实战篇-商户查询缓存-09.缓存击穿问题及解决方》

好，有同学问，能不能动手把缓存击穿的解决方案写一遍？安排上——上一节我们已经分析过缓存击穿问题和它的两种解决方案，这一节我们就直接上手：先看业务流程到底哪一步变了，再把互斥锁一层层封装出来，最后拿压测工具检验一下这把锁到底靠不靠谱。

还是老规矩，业务场景还是之前查询店铺的那个接口。

### 未命中之后，多了一道"能不能拿到锁"的判断

前端呢还是会提交这个商铺的 id 到我们的服务端，服务端肯定还是先查缓存，缓存查询完了以后判断一下它是否命中，根据是否命中再去做下一步的处理。

命中那就二话不说返回数据到前端，是不是就 ok 了呀。但如果未命中呢，这个地方就复杂了。

以前我们未命中，直接就去查数据库了对吧。但是现在呢，为了解决这个击穿的问题，我们还需要判断一下——**能不能拿到锁**，拿到锁了以后才可以去执行，对不对。

```text
前端提交 shopId
      │
      ▼
 查询 Redis 缓存
      │
 ┌────┴────┐
 │         │
命中     未命中
 │         │
直接     命中空值？──是──► 返回 null（穿透方案的结果）
返回       │
 │        └──否──► 尝试获取互斥锁 lock:shopId
 │                    │
 │              ┌─────┴─────┐
 │            失败          成功
 │              │             │
 │          休眠 50ms     查询数据库
 │        递归回查询处    写入 Redis
 │              │        释放锁（finally）
 │              │             │
 └──────────────┴──────┬──────┘
                       ▼
                    返回结果
```

读图：整条链路只有一个出口，就是把数据返回给前端；所有分岔都集中在"未命中"之后。而"未命中"又被再切一刀——切出的第一条是穿透方案留下的痕迹（缓存里存的是空值），直接返回 null 就结束了；只有第二条，也就是缓存里真的一无所有，才会进入击穿的处理流程。

没拿到锁，意味着等于是有别的人正在执行重建的动作了，那么这个时候你就不应该继续往下执行了。你该干什么呢？休眠一会，然后重新尝试查询，看看别人是不是已经更新好了。

拿到锁，证明你是第一个尝试做这个动作的人，那你就可以放心大胆地去执行缓存重建了：去数据库里查询，查完了以后将这个查到的数据写到 Redis 里，最后再去释放这个锁——释放锁别人下次才能够进来，对吧。做完就可以返回结果了。

这就是我们整个基于互斥锁方案的完整业务流程。

> **结论**：击穿的解法，本质上是在"缓存未命中"和"查数据库重建"之间插了一道闸门，把成千上万并发的请求挡在数据库外面，只放一个进去。

### 这把锁不是 synchronize

不过在这个地方有一个非常关键的点，就是锁。

那么这个锁呢，它不是我们平常用的那个锁。我们平常用 `synchronized` 或者用 `Lock`，那个锁呢，你拿到锁了你可以执行，没拿到锁你是不是要一直等待。

而我们当前这块呢，拿到锁和不拿到锁，它的一个执行逻辑是要我们自己去自定义的：拿到锁我去重建，没拿到锁我先歇一会儿再来。所以呢我们不能使用那种方式了，那我们要采用一个自定义的这种锁。

> **易错点**：`synchronized` 和 `ReentrantLock` 是"等待式互斥"，语义是"没拿到就一直排队等"；击穿方案需要的是"没拿到就走开、稍后再来"。语义对不上，工具就选错了。

### SET NX：Redis 里现成的互斥原语

那么用什么方式来实现这种自定义的互斥锁呢？

所谓的这种互斥锁呀，也就是说在多个线程并行执行的时候，只能有一个人成功，其他人失败，对不对。那么大家思考一下，在我们以前所学的这些知识里，有没有什么东西能够达成这样的一个效果？

有的。其实呢，在我们以前学习 Redis 的 string 数据类型的时候，它里边啊就有一个命令，跟这个效果是非常接近的。什么命令呢？`SET NX`。我们一起来看一下 `help set nx`，你看这个命令它的一个解释：

```text
Set the value of a key only if the key does not exist
```

就是说我们给一个 key 赋值，当且仅当这个 key 不存在的时候去执行；那如果 key 存在，是不是就不执行了。

那它为什么能做到互斥呢？来，我们一起演示一下。

```text
set nx lock 1
"1"        ← 第一个人的返回值：1，代表成功

set nx lock 2
"0"        ← 换个人来，还是想给这把锁换个值

set nx lock 3
"0"        ← 再来一个人

get lock
"1"        ← 值依然是原来那个 1，谁也没能改掉它
```

我们可以看到这个时候呢返回值是个一，这个返回值代表的就是成功。我们看一下是不是已经成功了，没错吧。好，这时候又有一个人还想来 set，那他来改一下这个值，我们再看一下啊，他的返回值是零啊；你再来一个人，好，都是零。

这时候 lock 的值有没有发生改变呢？没有，依然是原来那个值。

这这就告诉我们什么了？`SET NX` 其实啊是在 key 不存在的时候才能往里面写，key 如果已经存在了，是无法写的。那么如果现在并发的有数百上千的线程一起来执行 `SET NX` 操作，同学们思考一下，那是不是只有第一个人能够成功啊？他成功写入以后，其他线程再来执行 `SET NX`，得到的一定是一个零，也就是失败的结果。

没错吧，是不是就类似于我们讲的互斥？只有一个人成功，其他人都失败了。这就是我们自己所设计的一个方案。

> **结论**：`SET NX` 用一条原子命令就把"只有一个人成功"这件事天然保证了。这事实上也是我们后期要讲到的分布式锁的一个基本原理，当然真正的分布式锁会比这个复杂很多，这里我们先简单使用一下。

### 释放锁就是删 key，但有效期不能省

那么获取锁我们明白了，用这个命令就可以。那释放锁呢？

你获取锁是给它赋值，那释放锁其实非常简单，就是你把这个锁删掉不就好了吗？你把它删掉了，这时候再有其他人来执行 `SET NX` 操作的时候，是不是就能成功了。所以释放锁就是删除，获取锁就是给它赋值。

当然了，这里会有一种意外的情况啊。比如说我们用 `SET NX` 设置了一把锁，设置完了以后呢，因为某种原因你的程序出问题了，最后呢迟迟没有人去执行这个删除或者释放的动作，那将来是不是很有可能这把锁就永远不会释放了？

所以说呢，我们在利用 `SET NX` 设置锁的时候，往往会给它加一个有效期，比如说设置有效期为十秒钟。然后呢，一般我们的业务执行都在一秒钟以内嘛。那么在这个业务执行的过程中，如果正常释放没什么好说的；万一因为某种异常导致我的服务出现故障了，它永远不释放了，将来十秒钟到达，是不是锁还会自动释放呀？

所以说呢，我们再去设置这把锁的时候，也会给它设置一个有效期啊，来做这种兜底，避免锁呢就是因为某种原因得不到释放，产生死锁。

> **易错点**：只写 `SET NX` 不写过期时间，等于留下了一把可能永远打不开的锁。有效期是必须项，不是优化项。

到这里呢，其实我们就简单给大家介绍一下这种互斥锁的实现的基本思路啊，这跟真正的分布式锁还会有一定的差距，不过呢这里我们先暂时先这么去做。

### 把两个动作先封装成方法

在真正来去写这个业务之前啊，我们先去声明两个方法，分别来代表获取锁和释放锁，这样呢等一会儿我们使用起来是不是就比较方便了。

#### tryLock：尝试获取锁

我们在这个地方定义一个方法，它的返回值是一个 `Boolean`，代表成功与否。

```java
private Boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", 10L, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}
```

这里边呢我们其实就是去执行 `SET NX`。锁其实就是 Redis 里存的一个 key 对吧，所以说这个 key 呢由我们的使用者传给我们，我们就不在这写死了。

我们通过 `StringRedisTemplate` 操作，`SET NX` 是 string 的操作啊，所以这里要选择 `opsForValue`，然后调用它里边的一个方法叫 `set`。这里有个坑：你这两个 set 想找 `setNx` 是找不到的，它的 `NX` 呢起了个名字叫 `ifAbsent`，因为这个单词的意思就是"如果存在"的意思。并且大家可以看到它在后面是可以设置这个过期时间的吧，所以说我们直接用这一个命令就能搞定了。

先传 key，再传值——值其实随意啊，在目前来讲我们就随意传个 1 好了。然后呢我们再去设置这个有效期。有效期的设置啊跟你的业务有关，一般你正常你的业务执行时长是多少，你这个锁的有效期啊就比它长一些，长个十倍二十倍的，避免这种异常情况嘛。比方说这里我们就设置十秒钟吧，单位就是 seconds。

那么这里就拿到了一个结果。这个结果呢在我们命令行里面是零和一啊，在这呢 Spring 帮我们转换成了 `Boolean`，所以说它其实就是一个最终结果。然后我们需要把这个结果转成基本类型返回。

**在这里大家千万不要直接返回。** 如果你直接把这个 flag 返回，它是会做拆箱的，那么在拆箱的过程中是有可能出现空指针的。

所以说这里建议大家使用一个工具类啊，就是我们的 `BooleanUtil`，它是 Hutool 里面的。它呢可以帮助你做判断啊，`isTrue`、`isFalse`；或者是呢他也可以直接给你做拆箱，知道吧，都是比较方便的。就用 `isTrue` 返回这个 flag 就可以了。这样我们的 `tryLock` 函数就定义完成了。

> **易错点**：`Boolean` 是包装类型，直接 return 会触发自动拆箱，一旦拿到 null 就是 NPE。必须走 `BooleanUtil.isTrue(...)` 这类判空转换。

#### unlock：释放锁

释放锁我们这也分析过了，其实就是把锁删掉吧，所以说这块就不需要什么返回值了，直接就是 `unlock`。key 点告诉我，然后呢我帮你去释放，也就是删除 `StringRedisTemplate` 的一个 `delete`，然后呢在这里边呢我们把 id 传进去，就能实现一个删除的操作了。

```java
public void unlock(String key) {
    stringRedisTemplate.delete(key);
}
```

好，这样呢 `tryLock` 和 `unlock` 也就是获取锁、释放锁的代码，我们就完成了。

### 改造原有代码：先把穿透版本封装起来

那么接下来呢，我们就可以开始修改我们的业务逻辑了。

现在这个代码呢是我们之前写的缓存穿透的一个解决方案，这个逻辑啊我们先给它封装起来，就不要去删除了。那我们呢把它 Ctrl+C，然后在下面呢给他写一个方法，返回值呢是一个 `Shop`——你查的是店铺信息嘛；然后名字呢就叫做 `queryWithPassThrough`，`PassThrough` 代表这个缓存穿透，然后呢传递给我们的肯定是这个店铺的 id 嘛。

这种逻辑呢，因为我们最终返回的是一个对象，所以说呢他这块目前返回的那种 `ok` 什么的，我们都把它改掉，直接返回 shop 就 ok 了，是吧。当然这块的话可以直接这样返回。然后往下啊，这里如果不等于 null 也返回错了，就返回一个 null 就可以了，对吧；然后呢再往下这里也都一样，就不报错，咱们都是返回空，或者是数据本身。

那这样我们就把缓存穿透的代码给封装了，这样防止以后咱们的这个代码丢失，以后同学们也可以参考。那也就是说呢，如果要去实现缓存穿透，事实上吧我们只需要调这个方法拿到这个结果，是不是就好像穿梭的实现一样？那这样就比较方便了。

那这个代码呢我们也不删，好，在这写一下"缓存穿透"注释，那么就可以调这个 `queryWithPassThrough`，把这个 id 传进去，然后得到一个 `Shop`，然后呢就 ok 了。

这是一部分。

### queryShopWithMutex：照着流程图改写

下面我们要做的是什么？我们是不是解决缓存击穿啊，用互斥锁解决。

那我们再定义一个函数，这个函数呢我们可以在缓存穿透的基础上去写，所以这两段逻辑可能会非常像。好，我们起名字叫 `queryWithMutex` 吧——mutex 就是互斥锁的意思。然后呢我们来修改这段逻辑，整体修改的业务逻辑啊，肯定是要参考我们刚才那幅图的，对不对。

首先我们一步一步来，拿到店铺 id，也就是他，然后呢从 Redis 里查询缓存，也就查这个；查完了以后呢要去判断一下是否命中啊，也就是这部分。这个判断呢如果命中直接返回，你看 `isNotBlank` 是不是就命中了？命中就直接返回了。

如果未命中呢，这块呢其实是判断空值，这是我们那个穿透的方案对吧。如果说是空值，我们其实在 Redis 里存了空，所以这块呢代表是查到的是一个穿透的结果，所以直接返回 null。

那么再往下走到这才是真正的未命中，对不对啊，也就是既没有命中数据，也没有命中那个空值啊，就是什么都没有。未命中的情况下，我们就要尝试去获取互斥锁了，对不对。所以从这开始啊，业务逻辑就发生变化了，就跟以前不一样了。

而缓存重建的整个流程里面就比较复杂，不是一步两步能搞定的啊。第一个呢是做这个获取互斥锁，完了以后还要判断有没有成功对吧。那这个结果有两个，一个是成功，一个是失败。

#### 获取锁与失败重试

获取互斥锁呢，我们刚才已经封装了一个函数了，叫 `tryLock`，对不对，所以直接调就完了。那这里的 key 用什么呢？

**这个地方千万不要用前面这个 key 啊。** 前面这个 key 是缓存的 key，我们这里是锁的 key，它可以跟缓存的 key 不是同一个啊。我们起名叫 `lockKey` 吧。这个缓存的 key 的话呢我们可以这么做啊，也就是自己拼接一下，跟以前一样；那首先有个前缀嘛，比如说是叫 `lock`，代表锁的是谁的 lock 呢，是这个店铺，后面跟上店铺的 id，这样每一个店铺是不是都有自己的一个锁就行了。

```java
String lockKey = "lock:" + id;
Boolean isLock = tryLock(lockKey);

if (!isLock) {
    // 获取锁失败，休眠后重试
    Thread.sleep(50);
    // 重试：重新执行查询动作
    return queryWithMutex(id);
}
```

`tryLock` 以后它其实是有一个返回值的啊，`isLock` 有没有获取成功。下面的是不是判断了？那这个是不是"获取成功"的意思？对吧，那我们这个地方要先判断失败，因为失败更简单嘛，失败是直接就返回了重试了，对吧。所以说呢我们取反，这就代表失败。

失败了以后，首先是休眠。休眠我们通过 `Thread.sleep` 就行了吧，这个没什么难度啊。那么休眠的话不要休眠太长，因为你并不确定啊，别人重建到底会花费多长时间，所以我们呢先试一下，所以这块你去买个 50ms 试一试，然后再去看看有没有，万一成了呢，对吧？所以说这块的时间短一点。

然后往下，休眠完了以后是不是还要重试？重试是什么意思？重试就是重新来执行这个查询的动作。我们看这个流程图，重试是不是又重新回到了查询的这个动作，查询是不是从这儿开始了，所以等于是不是又重头回到这个方法了？所以同学们其实就是在这儿是不是得递归就行了？对吗，做递归，重来一次。好，等于是循环一直执行，直到要么这块获取锁成功了，要么就是上边拿到了返回值。

> **提示**：`Thread.sleep` 抛的是 `InterruptedException`，受检异常必须处理掉——要么向上声明抛出，要么 try-catch 后往外抛，这里先留着，等会儿再解决。

#### 重建与释放锁

如果这一块啊递归直接 return 了，等于是这块没有成立，那就是获取锁成功，往下走，查数据库，存一个 Redis 值，全部结束，接下来是不是要释放互斥锁了？

释放互斥锁的动作呢其实比较简单，也就是 `unlock` 把那个 `lockKey` 一传，这是不是就释放了。

不过我们前面还有个异常没处理啊。那我认为呢，你获取锁啊，还有整个释放锁这个逻辑啊，是不是应该给他实现一个 `try-finally`，因为抛异常的情况下，你也要执行 unlock，对不对。所以说呢这块要放到 finally 里去写啊。我们在这里呢给他来一个大的一个 try，catch 一下，然后 catch 这个异常呢我们就不去做处理了，直接往外抛就行了，因为这是一个打断的异常，不用管。然后呢 finally 在最终函数里我们去做释放，对吧。

```java
// 获取锁成功，进行缓存重建
try {
    // 根据id查询数据库
    Shop shop = shopMapper.selectById(id);
    // 写入redis
    redisTemplate.opsForValue().set(cacheKey, JSONUtil.toJsonStr(shop));
    return shop;
} catch (InterruptedException e) {
    // 打断型异常，直接往外抛
    throw e;
} finally {
    // 释放锁
    unlock(lockKey);
}
```

那在这个地方就得十分严谨了啊。这样呢，我们这个逻辑才算是一个比较严谨的一个业务逻辑，对吧。这就搞定了啊。

#### 返回值为 null 时的友好处理

好，那么我们定义的这个方法，它的一个返回值是有可能为 null 的对吧。但是呢我们在上面得到这个结果的时候，并没有对这个 null 值啊去做一个判断，那么这里呢当然你这么做也行，前端呢有可能拿到数据，有可能拿到 null。

但是如果你想反馈得友好一点啊，你其实可以在这里对 shop 的结果做一个判断，如果他是 null 的情况下，那么你就 return 一个 fail，代表一个失败，告诉他说你这个店铺不存在，好就 ok 了。

```java
Shop shop = queryWithMutex(id);
if (shop == null) {
    return Result.fail("店铺不存在");
}
```

那这样的话呢，我们这个功能算是基本上完成了。

下面呢我们就可以做测试了啊。不过呢在做测试的时候，大家要注意一下了。

我们当时讨论的时候讲过啊，我们的热点 key 它要满足两个条件：第一就是高并发；那么第二呢，就是缓存重建的时间比较久。重建时间越久，发生线程并发安全问题的可能性是不是越高？

## 用逻辑过期解决缓存击穿
> 对应块：BLK12 | 覆盖分集：P45-P46 | 块标题（分集名）：《实战篇-商户查询缓存-11.利用逻辑过期解决缓存》

上节课我们已经基于互斥锁的方式解决了缓存击穿，这节课我们再来看第二种方案——**逻辑过期**。

顾名思义，逻辑过期不是真正的过期。它要求我们在存储数据到 Redis 的时候，额外添加一个过期时间的字段，而这个 key 本身**不设 TTL**。所以它的过期时间不由 Redis 控制，而是由我们程序员自己去判断是否过期。

这样一来，业务上就会复杂很多。所以我们先把整个业务流程上的变化看清楚，再动手。

### 命中判断整个反过来了

先想清楚一件反直觉的事：这个方案里，缓存查询**理论上不会未命中**。

为什么？因为 key 不会过期，一旦添加进缓存，就应该永久存在，除非活动结束我们人工删除。而热点 key 往往就是参加活动的一些商品，我们会给它们提前加入缓存，在那个时候就已经设置好了逻辑过期时间。也就是说，所有热点 key 都会提前添加好，并且一直存在到活动结束。

所以查缓存的时候，其实可以不用判断它有没有命中。如果真的查到这个缓存不存在，那只能说明一个问题：这个商品不在活动当中，不是一个热点 key。

不过为了健壮性考虑，我们还是判断一下它有没有命中。如果真的未命中，也不用去做击穿啊、穿透啊这样的一些解决方案，直接给它返回空就行了。

核心逻辑其实是**默认它命中了**。命中的情况下，需要判断的是它有没有逻辑过期，结果就两种：

- **未过期**：没什么好说的，数据可用，直接返回给前端。
- **已过期**：说明需要重新加载，需要做缓存重建。但我们不能说谁来了都可以重建，所以这里要有一个争抢，跟上节课一样先尝试去获取互斥锁。

获取失败意味着在你之前已经有人尝试更新缓存了，那你就不用管了。而且逻辑过期这种方法属于比较"佛系"的，它看到有人去处理了就不管了，也**不是等待**，而是直接先把旧的返回，这样性能会比较好。

获取成功的人，需要去执行缓存重建，但也不是自己去执行，而是**开启一个独立的线程**用这个线程去做重建。他自己也是一样，先把旧数据返回着用，我不着急，由你这个独立线程去查询数据库，查到了以后写进 Redis 并设置一下逻辑过期时间，然后释放掉这个锁就可以了。

```text
前端提交 shopId
      |
      v
 stringRedisTemplate.opsForValue().get(CACHE_SHOP_KEY + id)
      |
      v
   缓存是否存在？
    | 否                    | 是
    v                       v
 直接返回 null      反序列化为 RedisData
                             |
                             v
                   expireTime 与当前时间比较
                        未过期 | 已过期
                           |       |
                           v       v
                    直接返回店铺  tryLock(LOCK_SHOP_KEY + id)
                              成功 | 失败
                                |     |
                                v     v
                       开启独立线程   不等待，直接返回旧数据
                       重建缓存
                                |
                                v
                    查数据库 → 写入 Redis（设置逻辑过期时间）
                                |
                                v
                        释放锁（写在 finally 里）
                                |
                                v
                    返回店铺信息（可能已是逻辑过期数据）
```

跟之前那个方案比较大的差别就在这儿——流程确实复杂了一些。

### 逻辑过期时间该挂在哪儿

那么第一个要解决的问题是：我们把数据写入 Redis 的时候，要设置一个逻辑过期时间，这个时间怎么样添加到数据里边去？

举例来说，我们现在写进 Redis 的是店铺信息，就是个 `Shop`。而 `Shop` 本身是没有逻辑过期这个字段的，所以要怎么办？

当然有同学会说，直接在 `Shop` 里加一个逻辑过期时间呀。当然可以了，但这种方案不够友好，因为你对原来的代码和业务逻辑做了修改，这样其实是不太推荐的。

这里其实有两种思路。

**第一种**：先定义一个对象，比如叫 `RedisData`，在里面定义一个成员变量，类型是 `LocalDateTime`，名字叫 `expireTime`，这个就是我们设置的逻辑过期时间。那么我们的 `Shop` 想要具备这个属性怎么办？大家就能想到了——让 `Shop` 继承 `RedisData`，不就把这个属性自然带过来了吗。这种方案很简单，但还是需要去修改源代码、修改我们的 `Shop`，所以还是有一定的侵入性。

**第二种**：在 `RedisData` 里边再加一个 `Object` 类型的属性叫 `data`。也就是说，`RedisData` 自己带有过期时间，并且里面带有数据，而这个数据就是你想存进 Redis 的东西——现在是 shop，将来要存别的实体也可以，所以它是一个**万能的存储数据的对象**。这种方案就完全不需要对原来的实体做任何修改。

两种都可以，我们给大家演示第二种，因为这种会稍微复杂一点，继承会更简单一点。我们用的也是这种。

那么我们将来存储 Redis 的数据是长这个样子的，你可以理解成这样：

```json
{
  "data": { /* 店铺信息 Shop */ },
  "expireTime": "2026-10-03T15:30:00"
}
```

这个 `data` 就是我们原来的店铺信息，`expireTime` 就是那个过期时间。

### 热点数据要提前预热

第二，像这种热点数据，它的缓存是需要我们提前导入进去的。实际开发中你可能会有一个后台管理系统，把某些热点数据提前在后台添加到缓存当中。

所以我们这儿会基于一个**单元测试**的方式，把我们的店铺数据加入缓存，等于是提前做一个缓存的预设。我们在 `ShopServiceImpl` 里先写这样一个方法：

```java
private void saveShopToRedis(Long shopId, long expireSeconds) {
    // 1. 查询店铺数据
    Shop shop = getById(shopId);

    // 2. 封装逻辑过期时间
    RedisData redisData = new RedisData();
    redisData.setData(shop);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));

    // 3. 写入 Redis
    stringRedisTemplate.opsForValue()
            .set(CACHE_SHOP_KEY + shopId, JSONUtil.toJsonStr(redisData));
}
```

几个地方要说清楚：

- 逻辑过期时间你自己定义就行，30 分钟、多长时间其实都可以。所以我们把它设计成由调用方传一个 `long expireSeconds` 进来，内部 `LocalDateTime.now().plusSeconds(expireSeconds)`，也就是在当前时间基础上加多少秒。
- 这次不再是把 `shop` 写进去了，而是写 `RedisData`，因为它里面同时包含了 shop 和过期时间。
- 通过 JSON 工具类转一下再放进去就可以了。

> **注意**：我们向 Redis 里 set 这个数据的时候，并没有给它添加 TTL 过期时间。这样这个 key 就可以认为是永久有效了，它的真正过期时间就是由我们控制的这个逻辑过期时间。

我们通过单元测试来测一下，看是不是真的能够把数据写入 Redis：

```java
@Resource
private ShopServiceImpl shopService;

@Test
void saveShop() {
    shopService.saveShopToRedis(1L, 10L);
}
```

方法改成 `public`，传一个 id，比如查 1 号店铺，过期时间我们随便给一个，比如 10 秒钟，方便测试。

执行完打开 Redis 客户端刷新，确实存进了一条数据。这个数据格式上边是一个大的对象，里面有两个属性：一个是 `data`，就是我们原来的店铺信息；一个是 `expireTime`，就是过期时间，完全符合我们的预期。这样我们就把店铺数据带逻辑过期时间写入 Redis 这件事做完了，数据预热也完成了。

### 照着流程改造查询方法

下面我们才真正去解决缓存击穿。先把之前缓存穿透的那段代码复制一份过来，改名成 `queryShopWithLogicalExpire`，然后照着流程图改造。

#### 哪些判断可以拿掉

从头往上来看，这一块变化会比较大。因为我们不用去考虑缓存穿透的问题了，所以像存空值那些逻辑就没有了，判断空值那块也不需要了。

- 前端提交 id，没问题。
- 查完 Redis 判断是否命中，**未命中直接返回 null** 就行了。这里 `if (StrUtil.isBlank(shopJson)) return null;` 改一下就完事。
- 复杂的是命中之后：你要判断是否过期，那你总得先把店铺数据取出来看一下过期字段，看是否超过了当前时间，对不对。所以**从命中分支开始代码就复杂了**。

流程是这样走的：命中 → 反序列化成 `RedisData` → 判断是否过期 → 未过期就直接返回店铺信息 → 已过期则缓存重建。

#### 反序列化的两层，以及类型是谁给的

先说反序列化，这里有个细节容易搞错。

拿到 JSON 字符串以后，反序列化成的类型应该是 `RedisData`，**不能写成 `Shop`**。别忘了我们打开 Redis 客户端看到的是什么——存的是 `RedisData`，里面有 `data` 和 `expireTime`，真正的店铺信息藏在 `data` 里面。

那 `data` 取出来是个 `Object`，这是什么？因为我们没有把类型写死，序列化时 `data` 字段声明的就是 `Object`，反序列化拿不到具体类型，就只能给你一个通用的对象类型。

> **提示**：Java 的反序列化要靠目标类型的字节码信息来映射字段。泛型擦除 + 字段声明为 `Object`，框架就无法确定你到底要还原成什么，只能退回到最通用的对象类型。所以我们在工具类里**不能把类型写死成店铺**——万一以后还有别的东西要缓存呢。

解决办法是把 `data` 再转一次。JSON 工具类的 `toBean` 除了接受 JSON 字符串，也可以接受对象类型，我们把 `data` 交给他，再告诉他实际类型是店铺，他就能返回店铺给你了。

```java
// 先反序列化成 RedisData
RedisData redisData = JSONUtil.toBean(shopJson, RedisData.class);
// 再把 data 转成真正的店铺
Shop shop = JSONUtil.toBean(JSONUtil.parseObj(redisData.getData()), Shop.class);

// 顺便取出过期时间
LocalDateTime expireTime = redisData.getExpireTime();
```

顺带说一句，这里其实两步有点多余，你完全可以把第二步放到位替代掉第一步的转换。拿到店铺和过期时间以后，就可以判断有没有过期了。

#### 判断过期，一个 isAfter 就够了

```java
LocalDateTime expireTime = redisData.getExpireTime();
if (expireTime.isAfter(LocalDateTime.now())) {
    // 未过期，直接返回旧店铺
    return shop;
}
// isBefore 则说明已经过期了，需要重建缓存
```

过期时间在当前时间之后，说明还没过期；在它之前，说明已经过期了。就这么点事。

#### 抢锁重建

走到这就证明它过期了，需要重建缓存。重建缓存首先要获取互斥锁，跟之前那套逻辑不一样的地方就在这儿。

先定义一个 `lockKey`，就是前面有个前缀 `lock`，然后 `shop`，后面拼上店铺的 id。这串东西我们会多次使用，所以应该定义成常量——找到 `RedisConstants`，加一个 `LOCK_SHOP_KEY`。锁其实也会有一个过期时间，我们同样定义一个 `LOCK_SHOP_TTL`，这个是 30 秒，或者 10 秒就够了，不要太长。

有了这两个以后，我们就可以利用 `tryLock(lockKey)` 拿到加锁的结果：

```java
String lockKey = LOCK_SHOP_KEY + id;
boolean isLock = tryLock(lockKey);
```

如果你获取成功，就要开启独立线程去做缓存重建。

> **提示**：我的建议是大家用一个线程池去做，不要自己去 `new Thread()`，那样性能不太好，经常创建和销毁。

所以我们在这里定义一个 `private static final ExecutorService`，起个名字叫 `CACHE_REBUILD_EXECUTOR`，里面 `Executors.newFixedThreadPool(10)`，十个线程玩一玩就够了。有了线程池，开启独立线程就是 `submit` 一个任务，写成 Lambda 表达式的形式。

那缓存重建到底干什么呢？说白了就是重新查询一下数据库，重新把它写到缓存里。我们刚才是不是定义过这样一个方法？查询、封装逻辑过期时间、写 Redis——对，就是 `saveShopToRedis`，这不就是重建吗？直接用它就完了。

```java
private static final ExecutorService CACHE_REBUILD_EXECUTOR =
        Executors.newFixedThreadPool(10);

if (isLock) {
    try {
        CACHE_REBUILD_EXECUTOR.submit(() -> {
            // 模拟重建耗时
            Thread.sleep(200);
            // 重新查询数据库并写回 Redis
            this.saveShopToRedis(id, 30L);
            return null;
        });
    } finally {
        unlock(lockKey);
    }
}
return shop;
```

关于过期时间：准确来讲应该是 30 分钟，但为了等一会儿测试，我们先设成 30 秒或者 20 秒。为什么？因为我们期待的是缓存过期后能立刻触发缓存重建，这样方便我们观察效果。实际中你应该设置成 30 分钟。

重建完缓存不要忘了一个非常重要的动作，就是**释放锁**。你不释放的话，下次别人是不是就进不来了？所以这块一定要有个释放锁的动作。这里用 `try-catch Throwable`，在 `finally` 里完成锁的释放。

另外，重建缓存我们为了模拟"缓存有一定延迟"，可以在里面休眠一下，`Thread.sleep(200)`，让延迟达到 200ms。延迟越长，将来越容易出现线程安全问题，所以我们在这直接给它整上。

最后要注意：**无论获取锁成功还是失败，最终都要返回店铺信息**，只不过成功了以后要多干一件事，就是开启独立线程。而返回的这个店铺信息，其实是个**过期**的商品信息。

### 压测：并发是安全的，但牺牲了一致性

现在整个流程写完了，我们去做个测试。

先把 Redis 清空一下。当时单元测试已经插入过一条数据，而且设置的逻辑过期时间比较短，大概 10 秒钟，理论上早该过期了。但你可以看到它依然还在 Redis 里——**这就是逻辑过期**：我们并没有真的给它设置 TTL，所以从物理上它可以理解成是永久存在的，但从逻辑上它已经过期了。等一会代码运行起来，一判断逻辑过期，就该走缓存重建了。

我们要测两件事：

- 高并发下会不会大家一起都来做重建，也就是**并发的安全问题**；
- 之前讨论过的**一致性问题**——在缓存重建完成之前，查询得到的是旧数据还是新数据。

为了测一致性，我们先去把数据库改一下。现在这个餐厅的名字叫"102 茶餐厅"，我们打开数据库把它改成"103 茶餐厅"，这样数据库就跟缓存里面的数据不一致了。

然后用 JMeter 做测试。1000 个太多了，JMeter 的结果面板写不下，它会把前面的结果覆盖掉，所以我们整 100 个就行了，让它 1 秒钟执行完，这样 QPS 大概也在 100 左右，也足够高。

运行结果：一开始查到的都是旧的"102 茶餐厅"，后面到 47、48 左右那一段的时候变成了"103"。为什么是那个时间点？因为我们设置的重建延迟是 200ms，从第一次请求开始它触发重建，到 200ms 之后更新完成，后来的新请求就能查到最新数据了。

所以你会看到它会有**一段时间的不一致**，后边才一致。

那我们到底执行了多少次重建呢？打开日志看一下，数据库最后只执行了一条 SQL，可以证明我们的并发是安全的，只会有一次重建。但数据的一致性确实会存在一定的问题。

至此，我们就实现了基于逻辑过期的方式解决缓存击穿问题。实现起来相对来讲逻辑会比较复杂一点。

### 封装成工具类

经过前面几节课的学习，我们已经解决了缓存使用过程中的各种问题。但是你也发现了，无论是解决缓存穿透还是解决缓存击穿，它们的代码逻辑都挺复杂的。如果每次开发都去写这些逻辑，开发成本还是挺高的。

所以我们将来一定会将这些解决方案封装成工具。不过封装的时候其实还会碰到不少问题需要解决，这里我给大家演示一下工具封装的时候会有一些什么样的使用技巧。

我们并不是真正封装一个完整的工具类，只是以几个方法为例，去演示一下中间可能存在的一些亟待解决的思路。要求封装四个方法：

| 方法 | 它做什么 | 搭档 |
| --- | --- | --- |
| `set` | 把任意 Java 对象序列化为 JSON 字符串，存在 String 类型的 key 上，并设置 TTL 过期时间 | 与下面第 3 个方法配对，解决缓存穿透 |
| `setWithLogicalExpire` | 和它类似，最大的区别是不设 TTL，而是设置逻辑过期时间 | 与下面第 4 个方法配对，解决缓存击穿 |
| `queryWithPassThrough` | 给个 key 帮你查，但要把查到的结果**反序列化为指定的类型**；反序列化过程中还要利用缓存空值解决缓存穿透，未命中就去查数据库 | — |
| `queryWithLogicalExpire` | 和上面基本一致，唯一的区别是最后它来解决缓存击穿，利用逻辑过期来解决 | — |

这里有两个点值得单独说：

**为什么 set 要接受任意对象？** 不能要求人家传字符串了，人家传任意对象都可以，那这个序列化的动作就交给工具类去做，对调用方做一个简化。

**为什么 get 必须指定类型？** 因为你封装的这个工具类再去操作的时候，它并不知道你要操作的这个数据是什么类型。不像我们明确知道我们刚才的业务都是在做店铺的查询、是 `Shop`。存的时候是任意类型，取的时候也是任意的——那任意的话我怎么反序列化呢？没法反序列化。所以要求这个方法在使用的时候，你去指定这个类型，然后我帮你做反序列化。

### 两个存的方法

新建一个工具类叫 `CacheClient`，因为我们那是专门处理缓存的，其他的不好处理。加一个 `@Component` 注解，这样将来就由 Spring 维护了；再加一个 `@Slf4j`，将来我们可以在工具类里做一些日志记录之类的操作。

工具类肯定需要用到 `StringRedisTemplate`，先把它拿进来。这里我们基于构造函数去注入它，当然用 `@Resource` 注解也都没有问题。用构造函数注入会有提示说你最好把这个字段定义成 `final` 的，其实也可以避免无效的一些修改。

先定 `set`。它接收 key 和 value，value 因为是任意类型，所以我直接用 `Object`。这样写的话这个存的动作它就没有过期时间了，但我们的需求中要求你是要带上这个过期时间的。所以还要加过期时间，我们可以模拟 Spring 那种玩法，先是一个时间值，然后再加上一个时间单位 `TimeUnit`，这样的话我们基本上就跟 Spring 的那个 API 基本一致了。

然后直接调 `opsForValue().set()`，会发现**报错了**。因为 `StringRedisTemplate` 要求是 String 类型，而你这里是一个 `Object`。所以这块少了一件事，就是需要把这个对象序列化为 JSON 字符串。工具类就要把这种复杂的活儿都包下来——用户传的时候传任意类型，那么序列化动作就交给我们来做了。

```java
@Component
@Slf4j
public class CacheClient<R, ID> {

    private final StringRedisTemplate stringRedisTemplate;

    public CacheClient(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    /**
     * 存储数据，设置 TTL 过期时间
     */
    public void set(String key, Object value, long time, TimeUnit unit) {
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(value), time, unit);
    }

    /**
     * 存储数据，设置逻辑过期时间
     */
    public void setWithLogicalExpire(String key, Object value, long time, TimeUnit unit) {
        RedisData redisData = new RedisData();
        redisData.setData(value);
        redisData.setExpireTime(LocalDateTime.now().plus(unit.toSeconds(time)));
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(redisData));
    }
}
```

`setWithLogicalExpire` 和它类似，区别在于它是逻辑过期，所以它的**参数列表可以认为是完全一样的**，无非就是实现不同。

那逻辑过期怎么去做呢？所谓的逻辑过期，就是在存数据的时候给数据里加上一个逻辑过期的字段。而我们怎么给逻辑过期加字段呢？这个类是别人传给我们的值，我们没有办法确定它里面有没有过期字段，所以我们还是整一个 `RedisData` 对象嘛，它里边有过期时间，也有这个数据，这样一来不就带上时间了？

> **结论**：我们只需要把这个 `value` 封装到 `RedisData` 里去存，就带上逻辑过期了。

过期时间是在当前时间基础上加上这个时间就可以了。这里有个细节：`time` 传进来是**带单位**的，你并不能确定它是秒，所以这块要把这个东西做个转换，利用 `TimeUnit` 里面的功能 `toSeconds()` 把 `time` 传给他，他就能转成秒。

那既然我们已经封装好了逻辑过期的时间，而且这个 `value` 值也都封装到了 `RedisData` 里，那我们就**不应该再去把 `value` 序列化写到 Redis** 了，应该是把 `RedisData` 写到我们的 Redis 当中。

### 两个取的方法

这两个方法我们其实以前都写过，所以封装的时候我们可以把以前的代码拷过来，在这个基础上去做改造就行了。

#### 泛型：返回值和 id 都不确定

先说改造点。

**第一，返回值肯定不能是 `Shop`**，因为你定义的是工具，你返回的应该是任意类型，这里是不确定的。返回一个类型不确定的时候我们用什么？没错，用泛型。

那要用泛型，你得先定义泛型才能使用。我定一个 `R`，R 代表 return——返回值。我不确定这个类型，那我将来真实的类型是什么？等你告诉我。你不告诉我怎么知道是什么，对不对？所以在这个地方，将来一定会有一个 `Class`，就是你的具体类型，你告诉我你是什么类型，然后我将来就给你返回这个对应的类型，这叫**泛型的推断**。

**第二，除了 id 还要有 key 前缀。** `id` 是干什么的？是根据 id 查数据库时会用到的。那我们要去 Redis 查，是不是还要有前面这一部分？前缀拼上 id 才得到真正的 key。所以这俩都得告诉。

**第三，`id` 一定是 Long 类型吗？** 不一定。我们现在这个店铺恰好是 Long，那将来人家传的一定是 Long 吗？不确定，所以这个地方你不能写死。也就是说 id 的类型也不确定，类型不确定全部用泛型，所以我们再定义一个泛型 `ID`。泛型的名称可以随便定义，故意的，就叫 `ID`。

于是类头上就是 `public class CacheClient<R, ID>`。k、id、类型都有了，那就可以放心大胆去做了。

#### queryWithPassThrough

```java
public R queryWithPassThrough(String keyPrefix, ID id, Class<R> type,
                              Function<ID, R> dbFallback, long time, TimeUnit unit) {
    String key = keyPrefix + id;

    // 1. 从 Redis 查询 JSON
    String json = stringRedisTemplate.opsForValue().get(key);

    // 2. 判断是否存在，存在则反序列化为指定类型
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, type);
    }

    // 3. 不存在，判断是否是空值（解决缓存穿透）
    if (json != null) {
        return null;
    }

    // 4. 数据库查询
    R r = dbFallback.apply(id);

    // 5. 写入 Redis
    if (r == null) {
        stringRedisTemplate.opsForValue().set(key, "", time, unit);
        return null;
    }
    this.set(key, r, time, unit);
    return r;
}
```

返回的时候你直接 `return`，你返回的肯定就是 R 类型，所以反序列化的 `type` 直接传进来就可以了，这就是泛型的这种玩法。

至于第 3 步为什么是 `json != null`：我们当时存空值存的是空，等于 null，所以 `json` 不为 null 的情况下只剩下"空"这种情况了。

#### 数据库查询这段逻辑，交给调用者

然后问题又来了——第 4 步去数据库查，最终我要返回的可不是 `Shop`，最终返回的肯定也是 R。但我怎么去查数据呢？我们知不知道？怎么可能知道！

你查 shop 的时候有 shop 的数据库查询方法，查 user 的时候是不是有 user 的方法。你查 Redis 里的数据方案是不是不一样，你查数据库的方法是不是也不一样。所以这块你根本不可能知道是什么，怎么办？

像这种情况下，这段逻辑我们不知道，我就不想写了，**交给调用者**。调用我们的人他肯定知道数据库要怎么做，所以我们要求他把这段逻辑传递给我就可以了。

那我们现在要传递的是什么？是一段逻辑——数据库查询的逻辑。那数据库查询逻辑其实不就是一段函数吗？函数式编程就可以传递这种函数。

> **定义**：传递函数有什么样的特点呢？它有参数——参数就是 id；它有返回值——返回值是 R。所以它是一个**有参有返回值的函数**，而 Java 中有参有返回值的函数就叫 `Function`。

`Function` 有两个泛型，一个是参数的类型，一个是返回值的类型。我们在这里可以起名叫 `dbFallback`，也就是数据库的一个降级的逻辑。什么意思呢？就是我先去查 Redis，Redis 失败了才走它，等于是个后备的逻辑，所以叫 fallback。

定义好了以后，将来别人把这种逻辑传递给我就行了，我这里就可以直接调它，调它里面的 `apply` 方法，把 id 传给他就行了。我们现在等于是在做函数式编程了：由别人给我们传这种函数逻辑，我们去执行查数据库。

查完得到这个数据以后，我们就判断是否为空。如果等于 null，就存空值进去；如果不等于 null，就把它写进 Redis。写的时候注意，这个时间应该是人家传的时间，而不是你在这里写死——你把时间写死了，难道所有的缓存都是这个时间吗？不一定。所以这块你也应该有参数传进来，参数列表还得再加两个参数，加的就是这个时间和单位。

那有了这个以后，你再写的时候是不是就可以直接用了？记不记得刚才我们写过一个 `set`？直接调 `this.set(key, value, time, unit)` 就可以了，不用自己再去写一遍。最后返回值肯定是 R 嘛。一个方法就这么封装好了。

#### queryWithLogicalExpire

还是一样的道理，我们去分析。

返回值不能是 shop，不确定，用泛型，先定义泛型然后使用泛型，R 就有了。然后是我们的 `ID`，再接下来还有 key，需要有一个 `String` 的 `keyPrefix`，将来的 key 就是用它拼出来的。再然后去查，查到是个 JSON 没问题，然后判断这个 JSON，如果不为空，将来要去做反序列化——反序列化得到的类型不再是店铺类型，因为我们不知道谁调用我们，所以将来是不是要传那个 `Class<R>`？然后泛型是 R，就是你具体的类型，你得告诉我。

这样一来我们再往下走的时候，查的这个地方就不用写死了，用它，我得到的就是 R，你给定的是什么，我查的就是什么。

查完以后做逻辑过期判断：如果说这个数据未过期，直接返回；如果已过期就往下走，去抢锁，锁了以后再往下走，这是不是要去重建缓存？

> **提示**：重建缓存其实是两个步骤——先查数据库，然后再写 Redis，这就是所谓的重建缓存。

查数据库的逻辑我们现在肯定不知道怎么查，交给别人，告诉我怎么查数据库。查数据库肯定需要有 id，所以我们需要有一个 `Function<ID, R>` 的 `dbFallback`，参数就是 id，返回值就是 R。那 id 的类型需要定义出来，而且它不一定是 Long 的，同样是泛型。这样呢就是一个 `dbFallback` 了，去 apply 一下 id，就得到了这个 r 这个数据。

得到数据以后是不是把它写 Redis 里？写 Redis 是要带逻辑过期时间的一个写，我们之前封装了一个 `setWithLogicalExpire`，那不正好用上了吗？还有 value 就是 r，然后就是时间。这个 `time` 和 `unit` 我们也不能写死，同样是由调用者传给我们，所以这块它也需要这两个字段。

所以你会发现，这两个方法的参数列表是完全一样的。最后返回 R 就行了。

```java
public R queryWithLogicalExpire(String keyPrefix, ID id, Class<R> type,
                                 Function<ID, R> dbFallback, long time, TimeUnit unit) {
    String key = keyPrefix + id;

    String json = stringRedisTemplate.opsForValue().get(key);
    if (StrUtil.isBlank(json)) {
        return null;
    }

    // 反序列化为 RedisData，再取出真实数据
    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    R r = JSONUtil.toBean(JSONUtil.parseObj(redisData.getData()), type);
    LocalDateTime expireTime = redisData.getExpireTime();

    // 未过期，直接返回
    if (expireTime.isAfter(LocalDateTime.now())) {
        return r;
    }

    // 已过期，尝试获取互斥锁，进行缓存重建
    String lockKey = LOCK_KEY_PREFIX + id;
    if (tryLock(lockKey)) {
        try {
            CACHE_REBUILD_EXECUTOR.submit(() -> {
                try {
                    Thread.sleep(200);
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
                // 查数据库
                R newR = dbFallback.apply(id);
                // 写入 Redis
                this.setWithLogicalExpire(key, newR, time, unit);
                return null;
            });
        } finally {
            unlock(lockKey);
        }
    }

    return r;
}
```

### 用起来是什么样

函数封装好了，怎么用？回去改造 `ShopServiceImpl`。

先看穿透。之前的方法我们先不用了，改成用工具类里面的方法，先把 `CacheClient` 注进来。

```java
@Resource
private CacheClient<Shop, Long> cacheClient;

@Override
public Shop queryShopWithPassThrough(Long id) {
    return cacheClient.queryWithPassThrough(
            CACHE_SHOP_KEY,
            id,
            Shop.class,
            id2 -> getById(id2),
            CACHE_SHOP_TTL,
            TimeUnit.MINUTES);
}
```

参数一个一个对：key 前缀就是 `CACHE_SHOP_KEY`，id 就是 id，类型是 `Shop.class`，如果缓存查询失败了要查数据库，这就是一段查询数据库的函数，而且这个函数的参数也就是这个 id 是 Long 类型的，那么它的返回值就是你要查的这个结果，这里其实就是 `Shop`。

那用 Lambda 表达式来代替的话就是 `id2 -> getById(id2)`。当然你也可以再简写一点，因为参数是 id，值就是它，那你不就是 `getById` 吗，所以写成 `Shop::getById` 这种方法引用的形式效果也是一模一样的。这就传递了一段函数过去，将来工具类里面去 apply 的时候，其实就是在执行 `getById`，就得到那个数据库的数据，也就是 shop 了。

最后是过期的时间和单位，这个时间我们以前是有的，`CACHE_SHOP_TTL` 还有 `TimeUnit.MINUTES`。

到这儿代码就写完了。也就是说我们以后再做缓存穿透的时候，就是这一行代码就搞定了，下面那一堆代码——判断空值、查数据库、写 Redis——都不再需要了。而且任意类型的对象都能使用我这个工具类，而不是只有 shop。

我们先测一下：重启、清空、打开浏览器访问一个不存在 id 的店铺。第一次来查的时候肯定是要去做缓存重建的，也就是存储空值进去。打开日志可以看到这是一条查询 id 为零的 SQL，因为它不存在，所以我们插了一个空值进去，解决这个穿透。

这时候打开浏览器再狂刷几次，不管你刷多少次，其实它都不会再去查询了，日志里还是之前那一条，没有更多的查询语句了。所以缓存穿透问题依然是得到解决的，我们的工具类没有问题。

那击穿是不是也就很简单了？就算我们用的是 `queryWithLogicalExpire`，我们可以把这个代码拷过去封装成工具类，代码其实就大同小异了，难度上就不大了。

当然，因为我们在使用逻辑过期的过程中还用到了线程池，所以线程池我们也可以拿过来，那业务类里这边就不需要了，直接给干掉就行了。然后因为这边还需要 `tryLock` 和 `unlock`，所以锁的这两个方法也拿过来。

改造的道理完全一样，返回值泛型、ID 泛型、`keyPrefix`、`Class<R> type`……到这儿 `queryWithLogicalExpire` 也就完成了。

```java
@Override
public Shop queryShopWithLogicalExpire(Long id) {
    return cacheClient.queryWithLogicalExpire(
            CACHE_SHOP_KEY,
            id,
            Shop.class,
            id2 -> getById(id2),
            20,
            TimeUnit.SECONDS);
}
```

当然，如果想测试缓存击穿，这个时间你可以调短一点，比如十秒或者二十秒，这样我们可以很快让它过期，方便我们去看看效果；想演示带有一定的延迟，也可以在这传的时候加个延迟时间就行了。

但不要忘了一件事情：**我们的缓存还需要先提前加载到 Redis 里**，将来它才能去查询逻辑过期时间。如果今天没有预热，你是没有办法测的。所以我们需要用单元测试在这里提前把数据存进去：注入工具类 `CacheClient`，先从 `shopService` 里 `getById` 把数据拿到，然后调用 `cacheClient.setWithLogicalExpire`，把逻辑过期的时间插入进去，key 就是 `CACHE_SHOP_KEY` 拼上 1，值就是 shop，过期时间短一点，来个 10 秒钟，这样可以很快让它过期，方便我们测试缓存重建。

```java
@Test
void saveShop() {
    Shop shop = shopService.getById(1L);
    cacheClient.setWithLogicalExpire(CACHE_SHOP_KEY + 1, shop, 10, TimeUnit.SECONDS);
}
```

执行一下存储完成，然后把项目重启。重启的过程中我们去 Redis 看一眼，刷新，现在存进去的这个数据已经带上了逻辑过期的时间了。我们稍微等待大概十秒钟，那么这个东西应该就会过期了。

然后再去测试击穿，还是利用 JMeter。先把以前的结果清空，还是 100 个线程，运行一下，很快就运行完了，这边全是绿的，应该是成功了。然后打开日志看有没有做数据缓存重建、重建了多少次——可以看到这里只执行了一次，说明缓存重建这块并没有发生线程安全问题。也就是说，工具类的缓存击穿问题也是能够成功得到解决的。

### 封装里最难的两个地方

最后我们回头看一下这个工具类，整个工具类里边比较难点的地方其实在哪里？

**第一个难点，是查询的时候返回值类型不确定，id 类型也不确定。** 要善于去利用泛型，在数据类型不确定的情况下去指定对应的类型，然后由调用者告诉我们真实的类型是什么，从而做出泛型的推断。

**第二个难点，是我们封装这段查询逻辑的时候要牵扯到数据库查询，而数据库查询本身我们并不知道该怎么查。** 所以我们的做法就是，由调用我们的人告诉我们数据库该怎么查。查数据库因为是一段函数，所以这里我们要求他传的也是一个函数，这里就用到了函数式编程。而这个函数呢，因为是根据 id 查、返回出一个结果，所以它是有参有返回值的，正对应了我们 Java 的 `Function`，利用 `Function` 指定这个参数和返回值类型，由对方调用的时候传递给我们就行了。而我们在调用的时候，传递的其实就是这个 `getById`，根据 id 查询的这样一个业务，这样在工具类里面就可以调用它，从而实现数据库查询，从而实现这样一个工具类的封装。

这就是一个小小的技巧。

### 缓存这一章，我们学了什么

先从认识缓存说起，这块我们主要讲了三个点。

#### 缓存的作用与代价

> **定义**：缓存就是一种具备高效读写能力的数据暂存区。它可以把数据暂存起来，因为读写能力比较强，所以查询和写入的效率都高，同时也减轻了对我们后端的压力——说白了就是降低后端负载、提高响应速度。

但加了缓存不是免费的。它带来的成本主要三点：

| 成本 | 具体是什么 |
| --- | --- |
| 开发成本 | 加了缓存以后代码明显变复杂了，这一点讲到后面大家自己就有感觉 |
| 运维成本 | Redis 为了保证高可用，将来要做集群，这些集群的部署会给运维带来很多麻烦；而且部署大量集群还需要机器，是实打实的经济成本 |
| 一致性成本 | 数据库和缓存里都有数据，怎么保证两者数据一致？这就是我们传说中的**双写一致性**问题 |

> **结论**：一致性这一条不是一句"注意一下"就能打发的，它要靠缓存更新的策略来维护，后面专门讲。

#### 添加缓存：先查缓存，再查数据库

基本模型很简单，查询数据的时候优先查缓存，缓存未命中再去查数据库。

```text
查询请求
    │
    ▼
┌────────────┐
│  先查缓存  │ ──命中──────────────▶ 直接返回
└──────┬─────┘
       │ 未命中
       ▼
┌────────────┐
│  查数据库  │
└──────┬─────┘
       │ 把结果写回
       ▼
┌────────────┐
│  回写缓存  │ ──▶ 返回结果
└────────────┘
```

读图就明白：缓存命中是一步返回，没命中要跑一趟数据库再回填，保证下一次能命中。

后来我们发现这个模型问题挺多，所以后面几节全是在解决它。

#### 缓存更新：三种策略各有用武之地

缓存更新解决的就是前面说的双写一致性。三种策略：

**内存淘汰**。这是 Redis 自带的机制，默认采用 LRU 的方式，当然我们也可以自己配各种不同的策略。当 Redis 内存不足的时候，它会把部分数据淘汰掉，清出空间来存新的数据。用这种方式可以一定程度上保证数据得到更新。

问题在于——它更新的时间、周期都是不可控的，所以一致性比较差。但好处是简单，你不用管。

**过期淘汰**。利用过期命令给我们的 key 指定 TTL 过期时间，到期以后自动清除。一旦清除了缓存，下次再查询自然就会查数据库、得到最新数据了。

这种方案可以人为控制 TTL 时间，从而保证更新频率，比内存淘汰的一致性好一些，但还不是强一致。而且在 TTL 过期之前的这一段时间里，如果数据库发生变更，还是会出现不一致的情况。它自己也有问题，后期我们专门讲过怎么解决。

**主动更新**。写代码的时候，主动地在更新数据库的同时，把缓存也更新了。

那怎么选？我的建议很直接：一般业务需求的情况下，用内存淘汰加过期淘汰这种方式就行了，因为它比较简单；对于一些数据有高一致性需求的，再去用主动更新，而且要**主动更新为主、过期淘汰兜底**——因为主动更新也不能百分之百保证一致，万一出了问题，还有一个过期的策略能兜一下。

#### 主动更新里，为什么最终选了 Cache Aside

主动更新常见的方案有三种：Cache Aside、Read Through 和 Write Behind。后两种虽然都挺优秀，但实现起来相对比较复杂，而且最后一种 Write Behind 的一致性还比较差。所以我们一般不选后两种，都选第一种 Cache Aside。

Cache Aside 是由调用者自己在更新数据库的同时去更新缓存。但它实现起来要回答几个问题。

**第一个问题：更新缓存，还是删除缓存？**

选"更新缓存"，意味着每次更新数据库都要更新缓存。如果用户根本不查、只是在更新，那你就产生了很多无效的更新。

至于线程安全——这里我特意留了个坑，没有给大家分析。你可以自己去想一想：采用更新缓存的方案，会有很大的线程安全问题。这也是我们不选更新缓存的一个原因。

选"删除缓存"就干净多了。第一，没有无效的更新——我更新完数据库只是删缓存，我不更新；它什么时候更新呢？当用户查的时候再更新，没有人查我就不更新。第二，它的线程安全问题出现的概率相对比较低，而且我们还可以去控制它。

**第二个问题：先操作数据库，还是先操作缓存？**

先操作数据库、再操作缓存，安全性相对较高，出现问题的概率比较低；先删缓存再操作数据库，安全问题出现的概率会相对高一点。

所以最终我们选的是：**先更新数据库，再删缓存**。

> **注意**：这里是有前提的——这两个操作必须确保原子性。单体系统我们利用事务机制，分布式系统就利用分布式事务机制来确保整体原子性，要么都成功，要么都失败。原子性保证不了，上面那些分析就全白扯。

最终落地的实践长这样：

```text
【查询】
  请求 ──▶ 查缓存 ──命中──────────────▶ 直接返回
                 └─未命中─▶ 查数据库 ──▶ 写回缓存 ──▶ 返回

【修改】
  请求 ──▶ 改数据库 ──▶ 删缓存
```

先改数据库再删缓存，确保两者的最终一致性。

#### 缓存穿透：查的东西压根就不存在

穿透产生的原因很朴素：用户查询的数据，在缓存和数据库中都没有。既然都没有，那就永远不可能有缓存，永远只能查数据库。那些不怀好意的人不停地访问这样的数据，你的数据库就要承受巨大压力。

两种常见方案。

**缓存空对象**——简单粗暴。你来查，不存在？那我就给你放个空的进去，下次来我就照样给你返回空。这样缓存就有了，就不会查数据库。

优点是简单、方便。缺点是带来额外的内存消耗，毕竟空值是真存进去了；而且会有一定数据不一致的情况——比方说你一开始没有，后来有了，而你存的还是那个空值，这不就又不一致了。

**布隆过滤**——利用布隆过滤的算法，在进入 Redis 之前先判断存不存在。不存在，根本不给你往后访问的机会。它是在前置去做拦截的。

它的问题是实现起来比较复杂，而且还有误判的可能——布隆过滤采用的是一种统计的、基于二进制位的方式，不一定百分之百准确。

所以从这个角度考虑，我们一般选择缓存空对象，因为它比较简单、实现起来也方便。虽然有额外的内存消耗，但可以通过设置过期时间的方式去弥补。

当然还有一些别的方案我们以前也聊过：做好基础的数据格式校验，如果 ID 不符合我们的规范——比如传了个零——就应该直接拒绝，而不是让它往下访问；做用户权限的校验；对热点参数做一些限流。这些都是可以做的。

#### 缓存雪崩：两种原因，两条对策

雪崩的原因主要有两个。

一个是 **key 过期导致的**。无数的 key、非常非常多同时到期，虽然单个 key 的访问量不大，但因为过期的太多，加起来访问量就大了，就会给数据库带来成批的压力。

另一个是 **Redis 直接挂了**。Redis 一挂，请求肯定直接打到数据库上。

这两种情况都可能把数据库整卡住。解决方案就针对这两个点。

针对**同时过期**：给过期时间加上随机值，让它们的过期时间不一样，就不会同时过期了。

针对**宕机**：首先要建立集群——注意是哨兵、集群这样的方案，不是主从——以此确保高可用。另外还可以给缓存业务添加限流、降级、隔离的策略。隔离和降级的意思是：Redis 失败的时候，它不会直接就打到数据库，而是有可能做一个降级、快速失败，避免业务继续往后进行，这样就给数据库带来了保护措施。

另外我们还可以利用**多级缓存**的方案。从请求进入浏览器发出，一直到最后到服务端，这整个流程当中添加多种不同的缓存：一个不行，总有另外一个缓存吧，总不可能所有缓存都挂了。通过这种方案一级一级地拦，从而保证整个后端的安全。

#### 缓存击穿：热点的 key 被大家一起重建

击穿的原因往往是一些热点的 key。热点要满足两个特点：**高并发**，以及**缓存的重建时间比较长**。

因为重建时间比较长，在它重建的过程当中缓存是不存在的；又因为它时间比较长，这一段时间内无数的请求就会涌进来；再加上它高并发，这些请求查不到缓存，都会去查数据库，于是数据库承受巨大压力，甚至出现宕机的情况。

要解决的就是：热点 key 在重建的时候，不要有无数的线程进来。

**第一种方案是加锁**。重建的时候我加个锁，只能一个线程来重建，其他线程等待。思路非常简单粗暴，优点是实现简单。但它会带来一些别的问题：因为你要等，等待就有性能的下降，并且还有死锁的风险。

**第二种方案是逻辑过期**。逻辑过期就是我们甚至可以永不过期——不过期就不需要重建，不需要重建自然就不会给数据库带来压力了。

但永远都是旧数据也不行，所以我们要加一个逻辑过期时间：每次查到数据以后，判断这个 key 是不是已经过期了、需要更新，如果是我们再去更新。

那如果这时候有 N 多的线程都来判断，发现都要更新，不还是有问题吗？所以还要加互斥锁。可加了互斥锁，不就跟之前一样了吗？

所以为了避免这个问题：加了互斥锁之后，**不是自己去更新，而是开启一个独立的线程去做更新**。在这个独立线程更新缓存的这段时间内，其他所有的线程不用等，而是直接查到什么就用什么——用旧的数据。这样就解决了等待导致的性能下降和死锁的问题。

不过也正是因为这个问题，因为你不用等、查到什么就用什么，那很有可能你拿到的就是旧数据，实际上会有这样的一种不一致的情况发生。

最后我们还带着大家封装了一个工具类。封装的时候主要用了 Java 提供的**函数式编程**这种思想：把数据库查询"传递"给我们的工具类，从而实现任意数据的数据库查询、缓存的同步策略都给他加进去。这是一个小技巧。

> **提示**：以上是 Redis 缓存常见的一些使用技巧和解决方案。除此之外还有一些多级缓存、Redis 缓存集群这样的高级知识点，我们会在 Redis 的高级课程里继续讲，紧跟课程、不要半途而废，学完以后绝对会带来巨大的收获。

### 订单表为什么放弃了自增主键

先看业务。在整个黑马点评业务里，唯一的商品就是优惠券。用户去抢购优惠券，抢购时自然就要生成订单，订单保存在 `tb_voucher_order` 这张表里——voucher 就是优惠券，order 就是订单。

打开数据库看这张表，字段并不算多：

- **用户的 ID**：谁来购买的，要记录下来；
- **代金券的 ID**（voucherId）：谁购买的、购买了什么；
- **支付方式**：将来要去支付，得记录一下支付方式；
- **状态**：订单刚创建时默认是未支付；支付了变成已支付；拿到店里去把这张券用掉了，变成已核销；下了单没支付直接取消，就是已取消；付了款没去用直接退款，就会出现退款中和已退款；
- **对应的时间**：创建时间、支付时间、核销时间、退款时间等等。

> **易错点**：需要特别注意的是主键——它并没有采用自增长。像我们之前的店铺表，用的就是 auto_increment 自增 ID。为什么订单表不用自增长？

**ID 的规律太明显**。订单编号 ID 将来是要发送给用户的，用户在我的订单列表里能看到每一个订单的编号，所以这个 ID 会暴露给用户。如果 ID 的规律性太明显，用户就能根据 ID 猜测到信息。比方说我今天下了一单，ID 是 10；第二天同一时刻我又下一单，ID 竟然是 100。那我就知道了——昨天一整天你们这个商城总共才下了 90 单。这不就暴露信息给用户了吗？

**受单表数据量限制**。订单的特点就是数据量非常大：用户只要产生购买行为，就会不停产生新订单。网站做到一定的规模，用户量达到数百万，每天都会产生数十万甚至近百万的订单，一年下来可能达到数千万，两年三年四年，是不是会达到数亿甚至数十亿？单张表显然保存不了这么多数据，那就必须分表。

可如果每张表都采用自增长，会出现什么问题？MySQL 的自增长是每张表各自计算的，每张表都从一开始增。多张表的自增 ID 是不是一定会出现重复？

而订单 ID 还有一个特点：**不应该重复**。从业务角度考虑，将来会有一些售后服务，用户会拿着订单来问我们"我这个订单怎么样了"。如果 ID 是重复的，将来不就会出问题了吗？

所以订单有两个特点：第一数据量大，第二 ID 需要唯一性。但是当我们把表拆开、出现这种分布式存储的时候，它就会违背这个唯一性。这就必然要用到我们今天要讲的**全局 ID 生成器**。

---

### 全局唯一 ID：五条硬要求

> **定义**：全局 ID 生成器，是一种在分布式系统下用来生成全局唯一 ID 的工具。关键在于"全局"两个字——在同一个业务下，不管你的分布式系统将来有多少个服务、多少个节点，这个业务下面又分成了多少张不同的表，最终只要你用这个 ID 生成器得到的 ID，它一定是当前业务内唯一的，不会出现冲突。当然了，不同业务之间即便冲突了，也没有什么关系。

因为它经常是用在这种分布式系统下，所以也被称为**分布式 ID**。我们虽然是个单体项目，但考虑到数据量将来可能也会很大，所以用它也是没有问题的。

这样的全局 ID 需要满足五个特性：

| 特性 | 含义 | 为什么不能妥协 |
| --- | --- | --- |
| 唯一性 | 绝不能和别的订单 ID 冲突 | 冲突了将来就会产生纠纷 |
| 高可用 | 你任何时候来找我，我都能给出正确的 ID | 你不能让我来找你，结果你挂了，别的业务都没法运行了 |
| 高性能 | 不只要正确，生成速度还要足够快 | 生成一个 ID 要耗几秒钟，别的业务都被你拖慢了，整体性能都下降 |
| 递增 | 单调的，不断变大 | 不一定非要像数据库那样 1、2、3、4 紧挨着增高，但整体一定要逐渐变大——这样有利于数据库创建索引，提高插入速度 |
| 安全性 | 规律性不能太明显 | 别让别人能够猜到你的其他订单 ID |

那 Redis 能不能满足这五条？没错，我们之前其实给大家提到过了——Redis 的 String 数据结构里边是有一种自增特性的，有一个 `INCR` 的命令。

#### Redis 凭什么满足前四条

- **唯一性**：Redis 是独立于数据库之外的。不管你数据库有几张表，或者说你有几个不同的数据库，但是 Redis 它只有一个。当所有人都来访问 Redis 的时候，它的自增一定是唯一的，不会存在说多个自增的情况。
- **高可用**：这就更不用提了。Redis 后面我们会去讲集群方案、主从方案、哨兵方案，这些方案是不是可以确保它的高可用。
- **高性能**：高性能就更不用提了，Redis 就是以性能著称的，它比数据库的性能要好太多太多了。
- **递增**：Redis 也是采用自增方案的，1、2、3、4 这样自增，所以它肯定能够保证整体的单调递增性。

**麻烦的是安全性。** 如果说我们直接采用 Redis 的那种 1、2、3、4、5、6 和我们数据库一样，那这个时候它就不存在安全性了，因为太容易猜测出规律来。

所以在利用 Redis 的 `INCR` 实现全局唯一 ID 时，我们不能直接把 Redis 的自增数值拿来当作 ID。那怎么办呢？给它拼接一点别的信息，让它的规律性不那么明显。怎么拼接？这就引出了整个方案的核心结构。

#### 三段式：符号位 + 时间戳 + 序列号

为了提高数据库的一个性能，我们的 ID 会采用数值类型——说直白点就是 Java 里的 `long`，然后直接插入数据库。因为数值类型在数据库里占用空间更小、建立索引更方便、速度会更快。

Java 的 long 占用 8 个字节，也就是 64 个比特位。我们把它这样安排：

```text
       63    62 ........ 32     31 ........ 0
       ┌───┬─────────────────┬─────────────────┐
       │ 0 │      时间戳      │      序列号      │
       │   │  （31 bit 秒）   │ （32 bit 自增）  │
       └───┴─────────────────┴─────────────────┘
         1          31                32
```

**符号位**（bit 63）永远是 0，代表我们的 ID 永远是正数。

**中间的 31 个比特位是时间戳**。这个时间戳是用来增加 ID 复杂性的，不是单纯的 Redis 自增了，它带上了一个时间。为什么是 31 位？因为我们将来会以秒为单位——定一个初始时间，比如从 2000 年 1 月 1 号开始算一下当前你下单这一刻的时间，与那个时间的时间差是多少秒，把这个秒数记录下来。而 31 位代表的是 21 亿多，算下来这个秒数大概能支持 69 年，69 年都用不完，那完全够了。

**最后 32 个比特位是序列号**，里面放的就是 Redis 自增的那个值了，从一开始自增。

有人会问：如果我一秒钟下了多个单呢？那你的时间戳不就重复了吗？没关系，**时间冲突的情况下，靠后面这部分 32 个比特位的序列号来区分**——它里面就是 Redis 自增的值，从一开始自增，当年份时间重复的时候，这里就是不同的。那么理论上讲，我们支持一秒钟内 $2^{32}$ 个订单量。当然实际上不可能那么高，像淘宝也就是每秒几十万的订单量，而且仅仅是在双 11 时刻，平常的话你最多也就是几千。所以完全够用了。

这么拼下来，三个特性同时成立：

- **唯一**：时间不同，时间戳就不一样；时间相同，序列号不一样。所以整体一定是唯一的。
- **单调递增**：时间是越来越大的，序列号也是越来越大的。
- **安全**：整体复杂度高了很多了，不再是简单的自增，所以在规律上就不容易被别人猜到了。

综上所述，我们利用 Redis 就能够满足全局唯一 ID 的五个特性。当然 Redis 并不是全局唯一 ID 的唯一实现方案，还有很多别的方案，我们这里讲的是基于 Redis 的方案。

#### 序列号的 key：为什么不能永远用同一个

这里有一个非常容易忽略的细节，也是实现时最容易想当然的地方。

自增需要一个 key。不同业务肯定有不同的 key——大家不能都去用同一个自增——所以这里需要一个前缀来区分不同的业务，这个参数可以理解成业务的前缀，比如订单业务你就传一个 `order`，其他业务传其他的。

那 key 是不是 `icr:order` 这样，到这儿就结束了？**不行。**

假如订单业务永远只采用一个 key 来自增，不管是经历了 1 年、2 年还是 8 年，永远是同一个 key。随着业务逐渐发展，订单越来越多，这个自增的值是不是也会越来越大？而 Redis 单个 key 的自增，它对应的这个数值是有一个上限的——上限是多少呢？是 $2^{64}$。虽然说这个值已经非常非常大了，但它也是有一个上限的。

而且你不要忘了，我们的 key 策略里真正用来记录序列号的只有 32 个比特位。Redis 是 64 比特位，超过 64 位很难，但超过 32 位还是有可能的。如果序列号这部分超过了 32 位，是不是就存不下了？

所以我们不能说永远使用同一个 key，哪怕同一个业务也不能永远使用同一个 key，否则真的有可能会超过这个上限。

**办法就是：在业务前缀的后边拼上一个日期。** 比如说我们拼上 `20220910` 这样一个时间戳，那它代表的就是 9 月 10 号这一天。当我们下单的时候，只要是 9 月 10 号这一天下的单，就以这个 key 去做自增 1、2、3、4、5；而当到了第二天 9 月 11 号时，你再去下单，又开始是一个新的 key 了，从一开始递增。

也就是说，这个 key 里自增的上限，其实就是这一天下单的量。那同学们想一想，一天下单的量会不会达到 $2^{32}$ 这么大？不可能，因为这个值都有几十亿这么大了。

这样做还有一个好处：将来如果我想统计这一天总共下了多少单，直接看对应日期的那个 key 的值就行了，统计效果非常好。

> **结论**：所以我们采用的方案是拼接日期字符串——每一天下单采用一个相同的 key，不同天下单就是不同的 key。这样做有两个好处：一是避免超过 32 位的上限，二是方便统计。

那么将来想统计月、统计年怎么办？你也不需要以月为单位重新去生成 key。因为我们知道在 Redis 里面，你的 key 用冒号分割之后是分层级的、是年月的。想统计月，我就统计以月为前缀的所有的 key，把它们的值累加，就得到这个月的订单量；想统计年，就是以年为前缀统计，它里面包含了所有的 key 的值。所以将来我们想去做统计就太简单了。

因此建议大家以日期、精确到"天"为单位作为 key。

### 动手写一个 RedisIdWorker

策略分析完了，我们直接动手实践。

在 `utils` 包下定义一个类，起个名字叫 `RedisIdWorker`，也就是一个基于 Redis 的 ID 生成器。给它定义成一个 `@Component`，也就是 Spring 的一个 Bean，方便我们后续去使用。里面定义一个方法，返回值是 `long`——因为按照我们之前的策略，最终生成的 ID 是一个 64 位的数字，那就是对应了 Java 的 long。方法名就叫 `nextId`。

它接收一个参数，我把它取名为 `keyPrefix`。为什么要这样一个参数？我们的生成策略是基于 Redis 的自增长，而 Redis 自增长肯定需要有一个 key，然后对应的值不断自增。不同业务肯定有不同的 key，大家不能都去用同一个自增。所以这里我们需要有一个前缀来区分不同的业务——比如说我们订单业务你可以传一个 `order` 过来，其他的业务你可以传其他的过来。

参考前面那幅三段式的图：符号位不用去管，只要最终我们生成的 ID 是一个正数就 OK 了。所以我们的核心工作就是去准备后两部分，一个时间戳、一个序列号。然后把它们拼接起来返回，这个方法的核心业务也就出来了：**第一，想办法生成时间戳；第二，想办法生成序列号；第三，把这两部分拼接起来返回。**

#### 时间戳：从一个固定起点算起的秒数

时间戳是一个 31 位的数字，单位是秒。它的值是要有一个基础的日期作为开始时间的，说直白点就是用当前时间减去那个开始时间，得到那个秒数，等于是从起始时间开始隔了多少秒。

所以我们在这个类里最好记录一个初始值。可以先写一个私有方法生成这个初始时间，借用 `LocalDateTime` 这个工具类，调一个 `of` 方法——`of` 方法可以让我们去指定这个年月日，所以在这个地方我们直接来 2022 年 1 月 1 号，零点分零秒。这样就得到了一个具体的时间。拿到它的时间戳很简单，`toEpochSecond` 就可以了。

这里涉及到时区 `ZoneOffset`，我们选 UTC。这样就得到一个具体的时间戳，我们运行一下，把这个值记录下来：`private static final`，肯定是个 long 了，起个名字叫 `beginTimestamp`，这个初始时间值就是它。

要计算当前时间戳就非常简单了——用当前时间减去这个值就 OK。获取当前时间其实就是利用 `LocalDateTime.now()`，它里面有一个 `toEpochSecond` 这样的函数调用，它得到的就是当前的秒数。那么将来我们只需要用这个秒数减去 `beginTimestamp`，就得到了时间戳。

```java
private static final long beginTimestamp = LocalDateTime
        .of(2022, 1, 1, 0, 0, 0)
        .toEpochSecond(ZoneOffset.UTC);

// 当前时间戳 = 当前秒数 - 起始秒数
long timestamp = LocalDateTime.now().toEpochSecond(ZoneOffset.UTC) - beginTimestamp;
```

#### 序列号：一天一个 key 的自增

序列号我们是利用 Redis 的自增长，所以在这里需要注入 Redis，用我们的 `StringRedisTemplate` 工具就可以了。这里你利用 `@Resource` 也可以，利用构造函数注入也可以，都是没问题的。

自增长我们用的是字符串结构，所以要调 `opsForValue()`，然后调用它的 `increment` 方法，这就是自增，默认是一次自增 1，就 1、2、3、4 就可以了。

在自增的时候你需要指定一个 key，也就是我们刚刚讲的，不同的业务有不同的 key，不能大家都一样。然后呢在这个 key 前面我们还可以拼一个标识，比如叫 `icr`，就是 increment 的缩写，表示它是自动 ID，是哪个业务的自动 ID，把业务拼上。

**但到这儿还不行**，为什么？因为这意味着整个订单业务永远采用的是同一个 key 来做自增长——不管你的订单业务是经历了 1 年、2 年还是 8 年，永远是同一个 key。上面说过，这样会有上限的问题。

所以在业务前缀的后边，我们再拼上当天日期。而且当然不能写死，我们必须先获取当前的日期、精确到天，然后再去做这个自增的动作，分两步。

得到当天日期其实很简单，用 `LocalDateTime.now()` 的 `format` 方法做格式化，用 `DateTimeFormatter.ofPattern` 自己定义这个格式化方式，`yyyy-MM-dd`，这样就得到了今天的日期，把它拼接在后面就可以了，这就是我们日期 key 的一个字符串了。

```java
String day = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy-MM-dd"));
String key = "icr:" + keyPrefix + ":" + day;
long count = stringRedisTemplate.opsForValue().increment(key);
```

这里有两点要留意。

**第一，自增的结果要用基本类型 long，不要用包装类**，因为等一会我们要做位运算。

**第二，IDE 在这个地方会报空指针的警告，这个你不用管，忽略就行了。** 为什么？因为自动拆箱的过程中可能会有空指针。事实上这里不会出现空指针——如果我们的 key 根本不存在，也就是新的一天到来的第一个单，这个不存在不会导致空指针；如果 key 不存在，Redis 会自动帮你创建这个 key，然后从零开始嘛，加一之后不就是 1 吗。所以说你根本不用担心空指针的问题。

#### 拼接：移位加或运算

现在序列号也有了，日期也有了，下一步要干的事情就是：把这两个东西拼接起来，形成最终的格式然后返回。

有的人很简单呀，前面时间戳、后边序列号，这俩用的字符串拼一下不就完了吗？是的，简单来讲是这么做可以。

但你别忘了我们的返回值是 `long`。如果你把他俩拼接成字符串，那你的返回值就是字符串了，对不对。所以我们是要以数字的形式去做拼接，也就是数字的高位是这个时间戳、低位是序列号。那这种拼接又该怎么做呢？

就要借助于**位运算**了。

你可以这么来理解：时间戳现在是在最低位，而我们需要让它把低位让出来，往前挪，挪到高位去。那怎么去做？序列号占 32 位，因此我们让时间戳的值向左移动 32 位。这就相当于把位置给空出来了——原来在最低位的时间戳往左移动了 32 位，剩下的这空出来的 32 位其实全部以零补充了。

```text
timestamp << COUNT_BITS        时间戳挪到高位，低 32 位空出来（全 0）

  ... ... ... ... | 0000 0000 0000 0000 0000 0000 0000 0000
                     └────── 32 位空位（全 0）──────┘

再 | count                     用或运算把 count 原样填进去

  ... ... ... ... | 0000 0000 0000 0000 0000 0000 0000 1111
                     └──────── count = 15 ────────┘
```

那怎么把 count 填进去？现在移上去以后，低位全部都是零，我们只要把 count 值填充到这一部分就行了。而这个填充我们可以采用**或运算**。

为什么或运算就可以去填充？你想，或运算是什么？一个为真就为真，对不对。现在这里都是零，而 count 的值它可能为零、可能为一，我们希望的是不管 count 的值是零还是一，都直接填在这里。那你看，现在是 0 或 0 得到 0，0 或 1 得 1。换言之，这里都是零的情况下我们用或运算，count 值是 1 这里就会是 1，count 值是 0 就是 0。也就是说 count 值是什么，将来就保留什么，这样是不是就能够实现这个拼接的效果？

**先向左移，把位置空出来；然后或，原样不动保留下来。** 这就是我们最终的运算方案。

还有一个细节：这个 32 最好不要在代码里写死，它是序列号的长度，现在是 32，那将来万一我们算法有变化，这个就有可能不是 32 了。所以也建议把它定义成一个常量，`int` 就行了，它代表的就是 count 这个位数的 base。

```java
private static final int COUNT_BITS = 32;

public long nextId(String keyPrefix) {
    long timestamp = LocalDateTime.now().toEpochSecond(ZoneOffset.UTC) - beginTimestamp;
    String day = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy-MM-dd"));
    String key = "icr:" + keyPrefix + ":" + day;
    long count = stringRedisTemplate.opsForValue().increment(key);
    return (timestamp << COUNT_BITS) | count;
}
```

到这里，ID 生成器的算法就初步实现了。

#### 用单元测试看看它长什么样

下面来测试一下。注入刚刚我们定义的 `RedisIdWorker`，测两件事：并发情况下生成 ID 的性能，还有生成 ID 的值的情况。

我们准备一个线程池，写一个简单一点的，不用搞太复杂，直接 `ExecutorService` 的 `newFixedThreadPool`，比如给 500 个线程。我们的任务是什么？每个线程来了都去生成 100 个 ID，并且把它打印一下——用 `Runnable` 来定义任务，`for` 循环生成 100 个，调用 `redisIdWorker.nextId("order")` 去生成，拿到这个 ID 打印一下，打印完了以后这个任务其实也就结束了。

然后我们把这个任务提交 500 次，或者说 300 次，提交的时候还是用 `for` 循环。这样任务就被提交了 300 次，300 × 100 就是 3 万个 ID。我们看一下它要花多长时间执行完，所以去记个时：在任务开始的时候记个时，任务结束再记个时。

但大家要注意，**因为我们使用的线程池是异步的，所以直接这么计时是没有意义的**。是不是要等它执行完再去计时？这里我们借助于 `CountDownLatch` 来做。我们明明知道是 300 个任务，每一个新任务执行完毕就执行一下这个 countDown 动作，每一个任务 countDown 一次，300 个线程就是 countDown 300 次。等到最后调用 `await`，等待所有的 countDown 结束为止，然后我们再去记录这个结束时间，打印出来，它的值就是用结束时间减去开始时间。

```java
@Test
void testIdWorker() throws InterruptedException {
    ExecutorService es = Executors.newFixedThreadPool(500);
    CountDownLatch latch = new CountDownLatch(300);
    Runnable task = () -> {
        for (int i = 0; i < 100; i++) {
            System.out.println(redisIdWorker.nextId("order"));
        }
        latch.countDown();
    };
    long begin = System.currentTimeMillis();
    for (int i = 0; i < 300; i++) {
        es.submit(task);
    }
    latch.await();
    long end = System.currentTimeMillis();
    System.out.println("time = " + (end - begin));
}
```

跑一遍，任务已经结束了。这里得到了非常多的 ID 的值，可以看到各不相同，并不会出现重复。

只不过这是十进制，我们看不出它的一个构造，是不是跟我们所预期的一样？我们可以利用数学的工具，把它转成二进制的形式——打开 Windows 自带的计算器，把那个值给它粘过来。

我们来看：

- 低 32 位显然就是那个 32 位的计数器；
- 再往前就是时间戳了。因为是以秒为单位，而且目前这个值还比较小，所以时间戳只占用了三个字节（24 位），再往前就是 0；
- 再看下一个相邻的 ID。因为我们这个打印是多线程打印的，所以它乱序了，我们找到相邻的两个一对比：计数器确实是增了一，而前面整体是不变的——说明同一秒钟内生成的 ID，它的前缀应该是一样的。

这就完全符合我们之前推测的规律：后半部分计数器不断递增，前半部分是时间戳，同一秒钟内生成的前缀一样。

再看整批：这些 ID 的高位前缀总共就变化了两次，说明我们总共大概也就花费了两秒钟。这里之所以显示是三秒，应该是因为还有打印以及其他各种各样的一些时间花费，其实真正地生成 ID 可能也就是两秒钟以内就生成了 3 万个左右。

剩下多少个 ID 呢？我们去 Redis 里看一下。刷新一下，可以看到生成到 3 万个了，自增长到了 3 万。也就是说，我们在两秒钟左右的时间生成了 3 万个 ID，每秒钟还是能生成 1 万多的，还是可以的对不对。尽管我的电脑性能并不是特别好，但是可以看到效率还是不错的。这个还没有达到它的上限，其实它还可以更高的。

### 全局唯一 ID 的其他几种解法

我们回到那张总结的表。事实上升成全局唯一 ID 的策略还有很多种别的：

**UUID** 是大家非常熟悉的一种方案了，直接利用 JDK 自带的 UUID 工具类就能够生成。但这种生成策略生成的是一个 16 进制的一长串数值，因为是 16 进制，所以它返回的结果其实是个**字符串结构**，并且也不是这种单调递增的特性。因此虽然可以做，但是并不够友好，没有满足我们之前所说的那些特性，所以这种方案用的比较少。

**Snowflake 雪花算法** 也是世界知名的一种全局 ID 生成策略，它采用的同样是一个 long 类型的 64 位数字。有兴趣的同学可以去百度一下看一看它的原理，你会发现跟我们这个还是有一些接近的。只不过它的自增采用的是当前机器内部维护的，所以它需要维护一个机器 ID；而我们用的是 Redis，不管是任何的分布式系统，它都是用 Redis 作为自增，所以它不需要维护机器 ID，结构上更简单一点。雪花算法也是一个非常不错的算法，它不依赖于 Redis，所以说性能上来讲，理论上会比 Redis 要更好一点。但是它也有自己的缺点，就是对于时钟依赖比较高，如果时间不准确，可能会出现一些异常的问题。

**数据库自增**——我们刚才不是说数据库自增不行吗，这怎么还说还能用数据库自增呢？这是因为我们在这儿用数据库自增，不是说我们在新增这个订单表的时候把订单的 ID 设置成自增，而是单独整一张表，这张表专门用来做自增。这样一来，不管你的订单表是十张表还是八张表，它们的 ID 其实还不是自增的，它们的 ID 从哪来？从那个专门用来做自增的那张表拿去获取。等于是这 N 张表用的是同一个表的自增，这样的话其实就可以实现这样的一个唯一效果了。

你可以把它理解成什么呢？就是 Redis 自增的**数据库版**——它不再是用 Redis 字段，而是用数据库的某一张特定的表的自增来代替 Redis 的自增。原理上来讲跟 Redis 的很像，但是从性能的角度来考虑，数据库的自增肯定不如 Redis 的自增性能更好。所以企业在去使用数据库自增的时候，往往会采取一些方案，比如说批量地去获取 ID，然后缓存到内存里再使用，这样也可以一定程度上提高它的性能。

对比一下这几种方案：

| 方案 | 生成结果 | 单调递增 | 依赖 | 短板 |
| --- | --- | --- | --- | --- |
| Redis 自增 + 时间戳 | 64 位数字 | 是 | Redis | 依赖 Redis 的高可用 |
| UUID | 16 进制字符串 | 否 | 无 | 返回字符串、不单调，对数据库不友好 |
| Snowflake 雪花 | 64 位数字 | 是 | 本机时钟 | 需要维护机器 ID，对时钟依赖高 |
| 独立自增表 | 数字 | 是 | 数据库 | 性能不如 Redis 自增，要批量取号 + 本地缓存 |

后面这三种方案在企业里都有去应用，同学们可以自己去百度一下，研究一下这些方案它的一些不同点。

最后回到我们这个基于 Redis 自增的策略，核心大家需要注意的就是：**整体结构是时间戳加自增 ID**；而在 Redis 保存这个 key 的时候，有一个需要注意的事项——**我们是每天一个 key**，它有两个优势，第一是方便统计每天的订单量、每月订单量和每年订单量，第二是可以限定这个 key 自增的值不会太大，以至于超过我们存储的上限。另外它的结构就是移位加计数器的方式。

我们这个全局 ID 的 Redis 方案就讲完了，这也是我们 Redis 应用当中比较常见的一种应用场景了。
