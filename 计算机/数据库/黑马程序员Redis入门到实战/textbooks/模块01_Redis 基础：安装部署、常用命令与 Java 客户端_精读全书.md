### Redis 是个键值型的数据库

Redis 是一个键值型的数据库。很多同学应该是第一次接触这个概念，简单来讲，Redis 内存中的数据都是键值对的格式——key、value。

比方说我们现在要存储一个用户信息。作为用户信息来讲，它里边的这些字段，还有字段的值，其实就是键值，对不对？比如说我们的用户有 id、有 name、有 age，把它拆开一个一个存，那就形成键值对了。

只不过呢，以这样一种方式去存储，数据显得比较松散——因为这本质是一个用户，我们却把它打散了，作为一个一个的键值对去存储了。

因此在多数情况下，我们并不会直接这样拆分地去存。那我们可以干什么呢？我们可以把一个用户的多个字段组装成一个 **JSON 的字符串**作为 value 去存，那么这时候它的 key 其实就是用户的 id。此时它其实也是一个 key-value 结构，只不过这个 value 变成了一个更长的、稍微复杂一点的 JSON 字符串，但它依然是字符串。

> **定义**：键值型数据库——内存中的数据以 key-value 对的形式组织。key 用来定位，value 就是这条数据本身。

当然，这里的值除了可以是字符串以外，还可以是一些其他更复杂的结构，比如 List、有序的集合、无序的集合，甚至哈希表等等。所以 Redis 的 value 结构是非常丰富的，可以满足我们各种各样的需求——这也是 Redis 在企业里现在使用得比较多、非常重要的一个原因：**功能丰富**。

从这里我们就能够看出来了，Redis 这样的一个数据库，它的结构与传统的 MySQL 数据库有比较大的差异：**它没有表，也没有约束，存的都是键值对。**

而像这样一种库，我们其实有一种称呼，它就是一种 **NoSQL 的数据库**。

### 认识 NoSQL：先把名字里的字母捋清

下面我们进入第一章“初始 Redis”的第一小节，认识 NoSQL。这一章我们有三个小节：第一小节了解 NoSQL 数据库与传统的关系型数据库有什么差别和联系；第二小节了解 Redis 的一些发展过程以及它的一些特征，看一看它为什么这么受欢迎；第三小节我们就会去动手实践，带大家安装和使用一下 Redis。

NoSQL 我们比较陌生，但与它相对的 SQL 我们就比较熟悉了——SQL 代表的就是关系型数据库。

这里插一段名字的闲话，缓一缓：SQL 这三个字母其实是三个单词的缩写——**Structured Query Language**。这个单词正确的念法应该是念首字母 S-Q-L，但这么念太长了，所以为了简化，在国内就流行着按字母念成 MySQL。但事实上，因为它是一门国外的语言，有历史的原因，它最早期的简写其实是 **SEQUEL**，后来才被叫作 SQL。无论是 SQL、MySQL 还是 SEQUEL，其实只要能够表达对应的意思就 OK 了，叫什么都无所谓，你爱叫什么叫什么。

好，我们言归正传。SQL 代表的是关系型数据库，那 NoSQL 在英文上来理解，它加了一个 No，我们是不是可以翻译成“非”的意思？所以我们一般把它叫做**非关系型数据库**。当然，也有人会把它翻译成 not only，也就是“不仅仅是数据库”。

不管是哪种翻译，想表达的意思都是：这种 NoSQL 与传统的 SQL 其实是有一些差异的，当然也有联系——毕竟它们都属于是数据库。而数据库最终的目的，一定是数据的增删改查。无非是在**数据存储的方式**上，以及**做数据增删改查的方式**上，有一些差异。

> **注意**：说 NoSQL“非结构化”，并不是说它完全没有约束。约束强不强，取决于你用的是哪一种 NoSQL 数据库。下面会具体讲到。

### 结构化与非结构化

两者之间的第一个差异，体现在这个字母 **S** 上。S 是英文单词 Structure 的缩写，也就是**结构化**。

存入关系型数据库的数据，都是结构化的数据。翻译一下就是：这些数据都要有固定的一些格式的要求。那这些要求是怎么定义的呢？就是我们以前所学的表，以及表的约束了。

比如说，我现在要存一个用户信息，那我们就需要有一张用户表。这张表里定义了必须有三个字段：id、name 和 age。并且我们还可以给 id 加约束，比如给 id 加上**主键约束**；给 name 加上 **unique 唯一约束**，那它就不能重复了；我们再给 age 加上一个 **unsigned 无符号约束**，那它的值就不能为负。除此之外，我们还可以定义数据类型、数据长度等等的约束：比如 id 定义成 BIGINT，长度在 20 以内；这个 name 定义成 VARCHAR，长度在 32 以内；age 因为值较小，我可以定成 INT，长度在 3 以内——这样呢可以节省一定的内存空间。

这些约束一旦定义好了，我们的表的结构就固定了。将来我们插入表中的所有数据，都要严格地遵循这些约定，而且数据库也会对你插入的数据做校验，如果不符合这些约定，自然就会报错，不允许你做插入。这就是所谓的**结构化**。

而且呢，表的结构一般是不建议随便去修改的，你最好在项目设计之初就把它定义好。因为什么呢？一旦你将来数据插入得较多，比如说达到上千万的规模，这时候你修改表中的某个字段，可能带来的影响是非常巨大的——可能会导致这张表被锁表很长一段时间不可用。而且因为表跟业务有关联，所以将来表变了，业务有可能也要跟着变。这样带来的影响啊，太大了。这也是结构化数据带来的一个问题了：**一般不建议对它的结构做修改。**

与它相对的，NoSQL 数据库存储的就是一种非结构化的数据，它对于数据的结构并没有非常严格的这种约束。

### 四种常见的 NoSQL 形态

常见的 NoSQL 类型有那么四种。

**第一种，就是我们最常见的 Redis 这种键值型的 NoSQL 数据库。** 这个我们之前已经简单了解过了：它的 key 是可以自定义的，你想叫什么都行啊。比如我的 key 想叫 id 行，没问题啊，name、age 也都可以——这样其实就等于把这一行数据作为键值的形式存进去了。当然了，这么存一般不太建议去做。我们也可以把 key 就定义成用户的 id 值，value 定义成一长串 JSON 的字符串，是不是也没问题？这种键值型，它对于 key 的约束就没有那么强，你可以自定义；对于 value 类型，同样你也可以自定义。那么约束相对来讲就会小很多。

**第二种，document 文档型。** 所谓的文档型，就是把我们的数据封装成一条文档存进去，一条一条的就对应这里的一行数据。那这里的一条数据它是用 JSON 的风格去存储的，所以代表一个文档；再来一条就又是一个新的 JSON，就是一个新的文档。

这种类型跟关系型数据库的差异在于：这个 JSON 文档，首先字段是可以任意的，对吧？我插入一条有 id、name、age；我再插入一条，我完全可以叫别的，我叫 id、我叫 username 也是没问题的。所以它的字段约束就非常的松散，没有强的约束。

**第三种，列类型（宽列模型）。** 典型代表是 HBase。

**第四种，图类型。** 什么叫图类型数据库呢？就是存入这个数据库的每一个数据，都可以看到成一个节点。比如我存取了一个人的信息，那么他就是一个节点。那为什么是节点呢？因为人和人之间是不是会有联系——比如张三是李四的老师，他们两个之间就是一个师生关系；然后李四是王二的朋友，那么这个就是朋友关系。这样，每一个数据都是一个节点，节点与节点之间有联系，那这种数据就叫图。

当然这种我们用的非常少，因为我们一般不做社交的 App 嘛，所以这种用的比较少。

那这些是常见的 NoSQL 的一些数据库。但是不管是哪一种，大家可以看到它们的数据结构其实都没有严格的要求，相对来讲都比较松散。而且将来你说我再去修改数据结构行不行？没问题，它也允许你对这里面比如说这个字段，我加一个或者少一个都是可以的，影响相对较小的。

这就是关系型与非关系型的第一个差异。

### 数据之间要不要关联

除了对数据有结构上的要求以外，关系型数据库之所以叫“关系”型，那就是数据与数据之间往往是有关联的。

比如说这里有一张 user 表，这里再来一张表叫商品表。现在来看，这两张表是没有关系的，对吧。但是呢，现在我来了一个订单表——订单表里边要记录是谁下的单：用户 id，还要记录下单买了什么商品：商品 id。那么这个时候，关系就建立起来了。我们的 order 表里面记录用户，所以它保留了用户的 id，那么这个时候用户 id 就可以理解成一个**外键**，它关联到了用户表里面的 id——哦，原来是张三买的。然后呢，他的商品 id 对应的就是商品表中的 id，也是外键关联了这张表的一行数据——证明说张三买了“荣耀 6”这样一个商品。

你看，表和表之间的关系是不是就建立起来了？通过什么建立的？通过外键。这种外键关系一旦建立，那么将来比如说我要删除一个用户，或者删除一个商品，他就不允许你这么做，因为他会觉得：哦，这个商品现在在其他表里有关联。所以我们的数据库就会去维护这些关系，它会去检查。

并且呢，这种关联有一个好处：**节省数据存储空间。** 我的订单里关联的用户，我不是把用户信息完整地保存在这里，而是只关联一个 id 就 OK 了。

好，这就是所谓的**关系型**（Relational）。那么 NoSQL 库呢，它就是一种非关系型的，它的数据与数据之间没有直接地去维护一个关联，比如说不存在外键。

关系型这边长这样：订单表靠两个外键把用户表和商品表连了起来，删除时被数据库拦下来检查的，也是这些外键。

```text
  ┌──────────┐  ── id ──  ┌──────────┐  ── id ──  ┌──────────┐
  │ user 表  │  ── id ──  │ order 表 │  ── id ──  │ 商品表   │
  │ (主键)   │            │ user_id  │            │ (主键)   │
  └──────────┘            │ goods_id │            └──────────┘
                          │ (外键)   │
                          └──────────┘
```

那 NoSQL 里我想维护“一个用户下了多少单”“每个单里面有什么商品”，怎么维护呢？它比较常见的一种方式，就是用这种 JSON 的嵌套形式来描述：文档本身代表一个用户，用户下面挂一个 orders 数组，数组的每一项是一个订单，每个订单有自己的 id，还有对应的商品 item，而 item 里面记录的就是对应的商品信息。这样就把一个用户下了几个单、每个单里边是什么商品都记录下来了。

这种描述呢，因为它首先我们讲了**没有表**，对吧？那么也没有表和表之间的这种外键关系，它是一种嵌套形式。所以呢，它的第一个特点就是：**没有关联**。

那第二呢，好，这个数据存储有一个缺点，就是**重复**。张三买了荣耀 6，那么李四可不可以也买？那当然了，等于你这个文档是不是存储多份，在多个用户里面？

当然也有同学会说了，那你为什么不像刚才那样，这里也只记录一个 id 呢？记录一个 item id 就可以了，然后我单独再来存一个文档，是商品，然后它俩不就有关系了吗？

这样做也行。但是呢，这个关系啊，就要**靠程序员自己通过业务逻辑去维护了**，因为数据库本身不会帮你维护表和表之间的关联。所以它是一种非关联的、或者说叫无关联的这种数据。

### 查询方式的差别

第三个差异，体现在这个**查询**（Query）上。

我们的关系数据库采用的是 SQL 查询，SQL 的查询就是说它有一个查询的语法。那什么样的语法呢？比如说我要查询用户表里边根据 id 来查，那么就有这样一条语句：

```sql
SELECT 字段 FROM 表 WHERE 条件
```

它的格式是固定的，语法也是固定的。那这样做有什么好处呢？因为它的语法是固定的，所以只要是关系型数据库，是不是都能够使用相同的语句进行查询？不管你是 MySQL 数据库、Oracle 数据库还是其他的，那么他都可以使用相同的语句去查询。这就是它的查询语句语法固定的一个好处了。

那么相对应的呢，NoSQL 库它的查询是非 SQL 查询，也就是说没有这样的固定的语法，格式不统一。

那在 Redis 里边呢，它在 Redis 里的查询，语法是这样子的：

```text
GET key
```

`GET` 后面跟上的这个是一个 key，key 就是一个字符串。这里其实就指“用户 1”的意思——一个命令就够了。

那么除了 Redis 以外，我们讲了还有一些其他的 NoSQL 的库，对吧？比如说大家没学过，我举个例子：MongoDB。

```javascript
db.user.find({ id: 1 })
```

这个查询看起来像是调了一个函数，是吧？那么 `db` 代表数据库，`user` 代表表，`find` 代表找，找什么呢？括号里面是参数，参数里面传了一个 id，冒号 1 就是查 id 为 1 的用户，这样一种查询语法。

那如果说我不是 MongoDB，我就是一些其他的，比如 ElasticSearch，这种库呢？它的查询语法又变了，它变成了一种 HTTP 的请求、RESTful 的请求：

```text
GET /users/1
```

那么请求的路径后面跟上 `users`，它代表的是这个库；后面的一位，代表的就是 id。那么它代表的效果就跟前面这效果是一样的。

所以你看，在 NoSQL 库中，它没有统一标准：有一些呢是命令，有一些呢看起来像函数，还有一些啊是一个请求。

那么这种方式它的优点是什么呢？首先啊，你可以看到 Redis 这种调用，直接用一个命令就可以了，非常的简单；那么 MongoDB，它调用呢是基于一种函数形式的调用，这种对于程序员来讲也相对比较熟悉。所以说呢，他们这些风格使用起来相对简单，没有复杂的语法需要去学习。

那么当然了，它的缺点就是不统一，每一个不同的库要学不同的语法。

### 事务与一致性

第四个差异呢，体现在这个**事务**上。

我们知道呀，在关系型数据库当中，我们做数据的增删改的时候，往往会有事务的一个需求。那么事务必须满足 **ACID** 的特性——原子性、一致性和隔离性等等这样一些特性。而我们的关系数据库啊，无论是 MySQL 还是 Oracle，它底层都可以帮助我们去实现 ACID 的特性。所以呢，我们可以认为所有的关系数据库都是满足 ACID 的。

而我们的 NoSQL 数据库呢——Redis、MongoDB、ElasticSearch——那么这些数据库呢，它要么呢是没有事务的，要么呢无法满足事务的强一致性，只能做一些基本的一致性。所以呢，这些 NoSQL 数据库就无法满足 ACID，或者说无法全部满足。那么我们把它称之为就是 **BASE**，基本的一种满足。那么这个 BASE 理论呢，大家如果有兴趣，也可以自己去研究一下。

> **结论**：如果说你对于数据的安全性要求较高，要满足 ACID，那么这个时候你就应该优先选择关系数据库，而不是 NoSQL 这种数据库。

### 四个差异摆在一张表里

以上呢就是我们 SQL 与 NoSQL 最常见的一些差异，这里我们做一个总结：

| 对比维度 | 关系型数据库（SQL） | 非关系型数据库（NoSQL） |
| --- | --- | --- |
| 数据结构 | 结构化：有固定的表结构与约束 | 非结构化：常见四种形态——键值型（Redis）、文档型（MongoDB、ElasticSearch）、宽列型（HBase）、图类型（Neo4j） |
| 数据关联性 | 有关联，靠外键由数据库维护 | 无关联，关联关系要靠程序员用业务逻辑自己维护 |
| 查询方式 | 基于 SQL 语句，语法严格且通用，MySQL、Oracle 通用 | 语法不统一：有的像命令（Redis）、有的像函数（MongoDB）、有的像请求（ElasticSearch） |
| 事务 | 满足 ACID | 不一定能满足，或只做到 BASE（基本/最终一致性，甚至可能无法保证一致性） |

当然了，也不是说只有这些差异。

### 还有两处差别：存储方式与扩展性

**从存储方式来讲**，我们的关系型数据库大多采用的是磁盘存储。比如说我们 MySQL、Oracle，是不是都存储在我们的磁盘上的？虽然它有缓存，但是核心数据都是在磁盘上的。而我们的 NoSQL 数据库，大多数呢，它们的数据都是在内存存储的，比如 Redis。

那内存存储的好处是什么呢？就是**性能**，查询的性能非常的高。所以说呢，在对性能要求较高的情况下，你都可以去使用这种 NoSQL 数据库。

**从扩展性上来讲**，我们的关系型数据库它是一种**垂直方式**。什么意思呢？就是说关系型数据库在设计数据库之初，可能就没有考虑到这种分布式的数据分片的需求。所以当我们去存储数据到关系型数据库的时候，它呢都是存储在本机，那么影响它性能的就是本机这台机器的性能，你只能是提升这个机器的性能来提升它的能力。

虽然说像 MySQL 它是支持这种主从的，但是主从仅仅是提升了什么呢？机器的数量提升了，读写啊的性能，但是你并不能提升数据存储的量——因为你主和从存储的数据是一模一样的，对吧？数据存储的总量没有变，只不过是做了备份而已。

那与此对应的，我们的 NoSQL 数据库呢，无论是 Redis 也好，还是我们的 ElasticSearch 也好，它们在设计之初，就已经考虑到了数据拆分的一个需求。因此呢，它们在插入数据的时候，往往都会基于这个数据的 id 或者一个唯一的标识去做一个哈希运算，然后根据哈希运算的结果，去判断这个数据到底应该存储在哪一个不同的节点上，从而实现数据的一个拆分。那么天然的就支持这种**水平的扩展**。

```text
   关系型：垂直扩展 —— 只能给这一台升配
   ┌────────┐
   │ 数据库 │
   └────────┘
        ▲
   加 CPU / 加内存
   （主从只是备份，数据存储总量并不变）

   非关系型：水平扩展 —— 加节点就行
   ┌────┐    ┌────┐    ┌────┐
   │ N1 │    │ N2 │    │ N3 │
   └────┘    └────┘    └────┘
     插入时基于 id 或唯一标识做哈希运算，
     哈希结果决定这条数据落在哪个节点上
```

我们的 NoSQL 库在扩展的时候，其实是非常轻松就能实现的。虽然说我们的 MySQL 默认情况下是不支持这种水平扩展的，但是你也可以基于第三方的一些组件来实现数据库的分库。当然了，一旦引入了第三方的组件，肯定会对性能上造成一些影响，并且在开发的时候需要考虑的问题也会更多，复杂度就增加了。不像我们的 NoSQL 库里边像 Redis 和 ElasticSearch 啊，他们天然地支持，那么开发难度上还有性能上都不会有特别大的影响，所以会更好一点。

### 该选关系型还是非关系型

综上所述，什么情况下我们该选择关系数据库，什么情况下我们该选择非关系型数据库呢？

如果说呀你的业务数据结构相对固定，将来不会怎么变更的；或者说呢，你的业务对安全性要求较高、对一致性要求较高的，那么建议使用关系数据库。比如说我们去下一个订单，那么订单数据就是属于安全性要求较高的数据呀，我肯定要用关系数据库去存储。当然，为了提升查询性能，我们可以冗余地把部分订单数据放到 NoSQL 数据库里去，提升它的查询效率，对吧？所以两者结合使用。

那因此呢，我们的 NoSQL 库往往就是运用在一些数据结构不固定、经常可能会有一些灵活变更，而你对于一致性和 ACID 要求不高，但对于性能要求较高的场景下去使用。

在实际开发中啊，要根据自己的需求灵活地去选择好了。

## 把 Redis 装起来、连上去，然后开始敲命令
> 对应块：BLK02 | 覆盖分集：P05-P09 | 块标题（分集名）：《基础篇-04.初识Redis-安装Redis及启》

装 Redis 之前，先回答一个问题：**装在哪台机器上？**

### 为什么一定装在 Linux 上

我们在课件资料里准备了一份文档，Redis 的安装说明，详细的安装步骤它全都有。打开它之前先把这份文档的前提说清楚——它是基于 **Linux 服务器**来讲解的。

为什么非要 Linux？理由只有两条，但都很硬。

第一，大多数企业在做项目部署的时候，用的都是 Linux 服务器。你以后上班真正天天打交道的是它，不是 Windows。

第二条更干脆：**Redis 的作者根本就没有编写 Windows 版的 Redis**。

> **易错点**：所以你在网上找到的那些 Windows 版 Redis，其实并不是官方提供的，而是由微软自己编译出来的。

综合这两条，所以我们选择用 Linux 服务器来部署。Linux 服务器的版本我们选 CentOS 7，建议大家跟我保持一致。

Redis 的官网大家也可以点开看看，下载点和安装说明文档都有，最新版本是 6.2.6。它那个网站是全英文的，速度还有点慢，有兴趣的可以自己进去翻一翻——不过下面要用到的安装包，我已经给大家下载好了，直接用就行。

### 从零装起 Redis

#### 先准备一台虚拟机

装 Redis 之前，第一步肯定是准备一台虚拟机，然后把安装包传上去，在里面安装就可以了。

有的同学用的是云服务器。云服务器不是不行，但有两个麻烦：一是网速是一个考验；二是它的安全性设置也多，比如说防火墙也不能关，操作起来反而更麻烦。

> **提示**：因此建议大家跟我一样都准备一台虚拟机，在本地操作会方便一点。

#### 装 gcc 依赖

要安装 Redis，第一步是要安装它的依赖。因为 Redis 是基于 C 语言编写的，所以我们必须先安装它的 gcc 依赖。

打开控制台，粘贴命令回车，剩下就是耐心等待：

```bash
yum install -y gcc
```

经过一段时间，依赖就安装好了。接下来回到文档，进入第二步。

#### 上传安装包并解压

文档里说明得很清楚：把 6.2.6 的安装包上传到 `/usr/local/src` 目录下。这个目录一般情况下都是用来放安装文件的。

```bash
cd /usr/local/src
tar -zxvf redis-6.2.6.tar.gz
```

上传时找到控制台进到这个目录，把安装包拖进来，然后对它做解压。看到解压成功，就说明这一步完成了。

#### 编译安装，然后去验货

解压以后，我们还需要进入 Redis 的安装目录：

```bash
cd redis-6.2.6
```

进来以后，运行 `make && make install`——`make` 是编译，`make install` 是安装：

```bash
make && make install
```

又是一段耐心的等待。跑完之后怎么知道有没有安装成功？文档里写着：安装完成以后，默认的安装路径是在 `/usr/local/bin` 目录下。我们进到这个目录里检查一下：

```bash
cd /usr/local/bin
ls
```

这个目录下确实多了很多文件，其中比较重要的有三个：

| 文件 | 作用 |
| --- | --- |
| `redis-server` | Redis 的服务端，运行这个脚本就能启动了 |
| `redis-cli` | Redis 的命令行客户端，我们比较常用 |
| `redis-sentinel` | Redis 的哨兵 |

> **结论**：看到这三个文件在，就证明我们这个安装其实是已经成功的。

而且这些命令已经加入了环境变量，你不用待在当前目录下，在任意地方都可以直接运行。判断方法也很直观：敲 `redis-server` 打到一半按 `Tab` 键，如果能自动补全，就证明它已经在环境变量里了。

顺便说一下，Redis 的官网上除了下载，还有三个地方值得逛：

- **Commands**：Redis 的相关命令，包含了 Redis 的所有命令，这里面每个命令是干什么的、有什么作用都会给你讲解。这是**最官方、最准确的文档**，也是学习 Redis 最重要的途径。
- **Clients**：官方提供的各种语言的客户端。
- **Documentation**：官方提供的一些帮助文档，比如所有命令的列表、pipeline 管道模式、发布订阅等等，都是一些相对高级的使用方式，有些同学也可以去看一看。

### 三种启动方式

装好了，那怎么样运行呢？Redis 一共有三种启动方式，我们一种一种来。

#### 直接启动：前台运行，关掉窗口服务就停了

最简单来讲，直接运行这个命令就 OK 了：

```bash
redis-server
```

回车之后，它会弹出一个这样的界面——这个其实就是 Redis 的一个日志界面了：版本是 6.2.6，端口是 6379，还有这次的进程 ID、官方网站，以及一个 Redis 的 logo。看到这个界面，说明 Redis 启动就成功了。

但是有的同学要问了：**我怎么连接这个 Redis 呢？**

不好意思，现在连不了。因为这个界面大家可以看到它并没有停止，它是一直卡在这里的。这种启动方式呢叫做**前台启动**——你想去建立连接，必须重新打开一个窗口，重新去建立连接；那如果当前窗口我把它关掉，Redis 也就被停止了。

> **易错点**：所以这种方式是一个不友好的方式，咱总不可能把这个界面天天挂在这里，对不对？

#### 指定配置文件启动：后台跑起来

那我们怎么样才能让它后台启动呢？就必须去修改 Redis 的配置文件，并且指定配置文件启动。

配置文件的默认位置就在 Redis 的安装目录下，有一个 `redis.conf`。修改这个文件之前，最好提前把它做一个备份——万一你修改错了，将来还能有一个文件让你去恢复：

```bash
cp redis.conf redis.conf.bck
```

这就是把这个文件拷贝了一份。备份完了，接下来就可以放心大胆地来修改 `redis.conf`。这个文件里面的东西非常多，文档里列出的可修改内容很多很多，但我们最关键的目前就这么几项（下一节详说）。

修改完了配置以后，怎么样启动并且指定配置文件呢？要想在启动的时候指定配置文件，只需要在命令后面跟上配置文件的名称就可以了。因为我们就是在 `redis.conf` 所在的目录下运行的，所以这里就省去了全路径，而是直接写文件名称：

```bash
redis-server redis.conf
```

可以看到这次启动以后，**没有任何的日志输出**，因为它已经变成后台运行了。那怎么知道我们有没有运行呢？通过 `ps -ef` 看一下：

```bash
ps -ef | grep redis
```

可以看到已经有一个进程在运行了。如果你要把它停止，就可以用 `kill` 命令把这个进程杀死，就能把它停掉了。

> **结论**：这是 Redis 启动的第二种方式，基于配置文件来启动。

#### 写 systemd 服务：开机自启

以上这几种方式去启动，其实都比较麻烦。那我们能不能让 Redis 将来做到开机自启呢？是可以的。

要想 Redis 开机自启，我们需要自己编写一个系统服务文件，把 Redis 加入到操作系统的服务当中，这样以后它就能开机自启了。

怎么做呢？按照文档，首先新建一个服务文件。新建好了以后，**内容大家不要自己去写**，最好是拷贝——文档里已经准备好了我编写好的这一份 Redis 服务文件。

> **注意**：这一份文件里最关键的就是启动命令那一行。它前面是 `redis-server` 的安装位置，后面是配置文件的目录，它就会用这个命令去启动并且指定这个配置文件了。大致长这样：

```text
ExecStart=/usr/local/bin/redis-server /usr/local/redis-6.2.6/redis.conf
```

有了这个文件以后，我们还要让它生效：

```bash
vim /etc/systemd/system/redis.service     # 新建并粘贴文档中准备好的服务文件内容
systemctl daemon-reload                    # 重新加载我们的服务
```

有了这个服务以后，它还没有开机自启——它只是被 systemd 系统管理了。现在我们可以通过 `systemctl` 来控制 Redis：

| 命令 | 作用 |
| --- | --- |
| `systemctl start redis` | 启动 Redis |
| `systemctl stop redis` | 停止 Redis |
| `systemctl restart redis` | 重启 Redis |
| `systemctl status redis` | 查看 Redis 的运行状态 |
| `systemctl enable redis` | 设置开机自启 |

`start` 之后可以看到它是 `running` 正在运行状态，通过 `stop` 可以停止 Redis，通过 `restart` 可以重启 Redis。`stop` 之后你看状态是不是变成 `dead` 死亡状态了——你看是不是非常地方便？

怎么样开机自启呢？通过 `systemctl enable redis`，这样一来我们的 Redis 就是开机自启了。开启以后我们再把它启动一下，`ps -ef` 看一下——Redis 已经起来了，启动的时候用的是 `redis-server` 这个命令，监听的端口是 6379，没问题。

至此，Redis 的三种启动方式我们就介绍完了。

### 配置文件里最该动的那几行

`redis.conf` 里可以修改的内容很多很多，但我们目前最关键的就那么几项。

#### 必改的三项

| 配置项 | 默认值 | 改成 | 说明 |
| --- | --- | --- | --- |
| `bind` | `127.0.0.1` | `0.0.0.0` | 端口**监听的地址**，不是允许访问的地址 |
| `daemonize` | `no` | `yes` | 是否以守护进程在后台运行 |
| `requirepass` | 注释状态 | 你的密码 | 访问 Redis 的密码 |

先说 `bind`。它默认是 `127.0.0.1`，它其实是指**端口监听的一个地址**——注意，是监听的地址，不能说是允许访问的地址，应该是监听的地址。监听 `127.0.0.1` 意味着什么？意味着只有本地的访问它才允许，从外界访问呢都会被拒绝。

那我现在把它改成了 `0.0.0.0`，就意味着在任意的 IP 地址都能访问这台 Redis。因为我们现在处于测试阶段，建议大家改成这个；将来在生产环境下，肯定还是用默认值。

在配置文件里改的时候是这样：把默认的 `127.0.0.1` 那一行**注释掉**，再加一个新的 `0.0.0.0` 进去，这样它就可以在任意地方访问了。

再往下找，还有一个 `protected-mode`（保护模式）。这个我们先不用管它，它是开启着的，密码的校验等等操作 Redis 会替我们去做。

第二个是守护进程 `daemonize`。刚才讲的那个不友好的前台运行方式，控制的就是它——默认值是一个 `no`，我们把它改成一个 `yes`，它就变成守护进程了，就在后台运行了。

> **提示**：找起来如果比较不好找，建议大家用搜索的方式。在 vim 里输入 `/daemonize` 就能直接定位过去。

第三个是密码，`requirepass`，默认是注释掉的。我们既然把 Redis 改成了任意人都能访问，如果在**没有密码**的情况下，那不就裸奔了吗？这个时候任何人都能访问你的 Redis，它是有风险的。

> **注意**：因为 Redis 可能有一些命令会有一些漏洞，如果任何人都能访问，它可能在你电脑上跑一些脚本，这是很危险的——有可能你的电脑就会变成肉鸡了，或者变成矿机了。

所以为了避免这种情况的发生，我们一定要给 Redis 设置一个密码。这个密码你可以随便改一个，比如说我就叫 `123321`。

#### 顺带可以看的几项

除了上面这三个配置，我们还有一些其他的配置，大家也可以配，当然也可以不配。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `port` | `6379` | 一般就用默认就行了，除非你的端口被占用了 |
| `dir` | `.` | 工作目录，`.` 代表当前目录 |
| `databases` | `16` | 数据库数量，编号从 0 到 15 |
| `maxmemory` | 不限 | 最大可用内存，比如 `512mb` |
| `logfile` | 空 | 日志文件，默认不记录日志 |

`dir` 这个要给大家记住：默认的 `.` 代表当前的意思，就是你在哪里启动或者运行 Redis 命令，哪里就是你的工作目录。比方说我刚才就是在 Redis 的安装目录下运行的，所以我产生的工作目录就是当前目录，也就是 Redis 安装目录。

`databases` 是数据库的数量，默认是 16，代表它有 16 个库，编号是从 0 到 15。那如果你把它改成了 1，就代表将来只用一个库。

> **易错点**：这也是 Redis 与 MySQL 不一样的一个地方。MySQL 的数据库是可以随便创建的，但 Redis 的库是固定的，是它自己给你创建好的。当然数量你可以控制，到底是 16 个还是 1 个，可以在 1 到 16 之间做出一个选择，编号是 0 到 15。

`maxmemory` 可以设置 Redis 的最大可用内存，比如写成 `512mb`，就是说我只允许使用 512M。

`logfile` 是 Redis 的日志文件，默认为空，也就是不记录日志。将来如果出了错误，你也不知道是什么原因啊。所以我们可以给他指定一个日志文件名称，比如我们就加个日志吧，叫 `redis.log`，这样方便大家调出去看一下我们的日志。找到 `logfile` 这个配置项，默认是空的，我们起个名字保存，配置文件就修改完毕了。

> **注意**：这个日志文件啊，他是**写了文件名，没有写路径**。那么这个日志文件会产生在哪里呢？就会产生在 `dir` 也就是当前这个位置。那也就是运行 Redis 命令时的那个目录。这俩结合，才是真正的存储的地方。

### 用 redis-cli 连上 Redis

上一节课我们已经带着大家安装了 Redis，并且把它跑起来了。但是我们该如何去访问 Redis 呢？

Redis 给我们提供了一些客户端，让我们去操作它，一共有三种：命令行客户端，也就是通过命令的方式进行交互；图形化界面的客户端；还有编程方式，也就是各种不同语言的客户端。

这里我们先讲前两种，第三种放到最后去讲。

命令行客户端在安装 Redis 的那一刻就已经安装好了，也就是 `redis-cli`。我们当时是安装到了 `/usr/local/bin` 目录下，你可以在这个目录下看到 `redis-cli`，它就是 Redis 的命令行客户端。

#### 语法与常用选项

它的使用语法是这样的：

```bash
redis-cli [option] [command]
```

`option` 是选项，常见的就是这三个：

| 选项 | 含义 | 不指定时的默认值 |
| --- | --- | --- |
| `-h` | 指定 Redis 的 IP 地址 | `127.0.0.1`，代表本机 |
| `-p` | 指定端口 | `6379`，正是 Redis 的默认端口 |
| `-a` | 设置访问 Redis 时的密码 | 无 |

这些选项你都可以不指定，不指定就是默认；如果指定了，它就会按照你指定的去连接。

连接完了以后，你还可以指定 `command`，代表是命令。前面的选项是让你连上 Redis，连上之后我要干什么事啊，就可以指定一些命令。

但一般情况下 `command` 我们都不用输入，因为我们希望的是先连上。如果你不输，连上以后它会进入一个持续的交互式控制台，不断的是什么呢？你可以输入命令，它给你返回，输入命令，返回，这样会比较方便。

#### 带密码的两种连法

我们到控制台测试一下：

```bash
redis-cli -h 127.0.0.1 -p 6379
```

`-h` 后面跟上 IP 地址，第一种我可以写 `127`，那不写是不是也一样？也可以写我的 IP，我这台虚拟机的 IP 是 `192.168.15.101`，那也能连到我这台机器。`-p` 后面跟端口 6379，我们刚才走的就是默认的，所以输不输其实都 OK。

这个密码呢我先不着急输入，我先回车。诶，连上了吧？现在我来打个 `ping`——它是跟 Redis 打招呼的一个方式：

```text
127.0.0.1:6379> ping
(error) NOAUTH Authentication required.
```

它说 `NOAUTH Authentication required.`，就是说你没有权限。为什么呀？因为需要密码。

那怎么办呢？第一种方式就是刚才我们看到的，在连接时加一个 `-a` 参数：

```bash
redis-cli -h 127.0.0.1 -p 6379 -a 123321
```

加上以后，你看这一次他就成功进来了。我们再来 ping 它一下，跟打乒乓球一样是吧，证明我们已经能够正常连接了，心跳是通过了。

但是呢，它有一个警告，说是**你利用 `-a` 参数来指定密码太危险了**，让你换种方式。

那么换什么方式呢？第二种方式：我不在连接时指定密码，连上了以后，通过 `auth` 命令来指定用户名和密码。因为我们没有用户名，只有密码，所以可以直接写密码就行了：

```text
127.0.0.1:6379> auth 123321
OK
127.0.0.1:6379> ping
PONG
```

大家看校验成功，这时候我再来 ping，是不是也可以 pong。这就是 `redis-cli` 连接的两种方式。

#### 连上之后随便敲敲

连上了以后呢，你在这里面各种乒乓打起来，也可以去操作它，做一些增删改查之类的都是可以的。比如我先 `set` 一个：

```text
127.0.0.1:6379> set name 杰克
OK
127.0.0.1:6379> set age 21
OK
```

虽然大家还没正式学，但我们可以先用一下。其实就是在 Redis 里存了一个键值对，key 是 `name`，值呢是 `杰克`。当然你也可以 `set` 一个 `number` 或者 `age` 等于 21，好，都存进去了。

那我要取呢？我们还可以用 `get` 命令：

```text
127.0.0.1:6379> get name
"杰克"
127.0.0.1:6379> get age
"21"
```

取到了名字、取到了年龄，都是没问题的。这就是 Redis 命令行客户端的使用。

在连接设置里面：

- **连接名称**是随意的，你随便起名字就行了，比如说我叫 SLS7；
- **IP 地址**这里才是真正填 IP 地址的地方，填我虚拟机的 `192.168.15.101`；
- 这里还有**填密码**的地方，如果你不填密码的话，你看是连不上的，我们填一下 `123321`。

连接成功，点击确定，点击连接——你看是不是连上了？

连上以后，它就显示了 16 个库，从 0 到 15。这个我们之前介绍过，Redis 默认就有 16 个库，而且它的**库的名字是固定的，你不能改**，你只能去配置库的数量。

现在的 0 号库点进去，可以看到里面就已经有刚才存进去的两个 key 了，一个 `name` 一个值。那有的同学要问了，我想往 1 号库里存该怎么办？点击它就切到 1 号库了，但是 1 号库里什么都没有。你可以在这里面自己新建，我在这里新建一个 `name`，我叫 rose，你看是不是也存进去了。

> **结论**：因为呢这两个是不同的库，所以它俩的 key 尽管是一样的，但值呢是互相不干扰的。

那如果我想在命令行客户端里去找到那个库呢？我们可以通过 `select`：

```text
127.0.0.1:6379> select 1
OK
127.0.0.1:6379> get name
"rose"
127.0.0.1:6379> select 0
OK
127.0.0.1:6379> get name
"杰克"
```

这是在命令行中选择库，而在图形化界面里选择更方便一点。

> **提示**：所以日常情况下，建议大家使用图形化界面，因为它很方便。但是如果是初学 Redis、想要学习 Redis 里面的命令，还是建议大家通过命令行，因为在命令行里可以让你更加熟悉每一个命令。

### Redis 里到底装了什么

接下来我们进入 Redis 常见命令这一章。这一章里，我们会分成七个小节：首先介绍一下 Redis 里面常见的一些数据结构，而后就是针对这些数据结构的一些命令了。

Redis 是一个键值型的数据库，这个我们已经说过很多次了，key、value。

```text
        key  ──▶  value
                 │
                 ├── 基本类型：底层就是这些真实结构
                 │     ├── String       普通字符串
                 │     ├── Hash         哈希表
                 │     ├── List         有序集合（本质是链表）
                 │     ├── Set          无序集合，不能重复
                 │     └── Sorted Set   有序、可排序的集合，不能重复
                 │
                 └── 特殊类型：在基本类型的基础上做了特殊处理
                       ├── GEO           地理坐标（经度、纬度）
                       ├── Map           按 value 存取
                       └── HyperLogLog   基数统计
```

这张图把 Redis 的值分成了两拨。

#### 五种基本类型

一般情况下，Redis 的 key 就是一个 String 字符串，而它的值的类型却是多种多样、五花八门——光列出来的就有八种之多，而这还不是全部。其中比较常见的就是前面的五种了，我们称它为**基本类型**：

| 类型 | 值是什么 | 特点 |
| --- | --- | --- |
| String | 普通字符串 | 最基础的值类型 |
| Hash | 哈希表 | 值不是一个普通字符串，这里用字符串的形式来描述，但本质其实是个哈希表 |
| List | 有序集合 | 本质是一个链表 |
| Set | 无序集合 | 不能重复 |
| Sorted Set | 有序集合 | 可排序的集合，当然也不能重复 |

#### 三种特殊类型

后面的这三种，我们称为**特殊类型**：

- `GEO` 其实呢是一个地理坐标，你看到它存的是经度和纬度；
- `Map` 是一种特殊的按 value 去进行存储的方式；
- `HyperLogLog` 也是一种特殊的按 value 去进行存储的方式。

它们往往用到一些特殊的数据统计。

> **结论**：为什么称上面的是基本类型？就是这样的原因——下面这三种的底层本质其实都是字符串，只不过是在基本类型的基础上做了一些特殊的处理，用来实现特殊的功能，所以说我们称它们为特殊类型。

在 Redis 里，除了这八种以外，其实还有很多其他的一些类型，用来实现其他特殊的一些功能，比方说消息队列等等。那这些呢我们后面也都会给大家讲。可以说啊，Redis 里面提供的所有数据类型，在咱们的课程中全部都有，绝对是做到知识足够全面。

不过啊这里就会有两个问题了：如此之多不同的数据类型，它们的操作肯定会有差异。

- 第一个问题就是：**我该怎么操作**这些不同的数据类型？
- 第二个问题就是：这么多的数据类型，它们的功能肯定也不一样，**我该在什么时候去使用哪一种数据类型**呢？

这其实就是怎么用和什么时候用的问题。按照学习规律啊，我们肯定是先弄懂怎么用，只有我们把这些数据类型给它弄懂了、弄透彻了，知道该怎么去用了，接下来我们再去分析什么时候用，是不是就更容易理解了？

所以我们的课程也是这么安排的。在第一阶段也就是我们的基础篇当中，我们会先学习这些数据结构对应的操作，把每种数据结构的操作给它弄熟，把它的特征给他弄透；而在第二阶段实战篇当中，我们会结合真实的项目，带着项目需求去分析一下，在不同的需求场景下我到底该使用哪一种数据类型。

> **提示**：我觉得呢，带着需求去分析，肯定比我直白地告诉你该什么时候用要好很多。另外这三种特殊类型啊，因为它们的功能比较特殊，使用场景往往比较单一，所以我们会在实战篇当中一起来学习它们的操作和使用场景。

### 命令怎么查：help 才是关键

接下来在整个课程里，我们先来学习这五种基本类型的操作。而 Redis 提供的操作往往都是命令行——那要学习命令行，肯定要去查看帮助文档。

官网上有一个 Commands 页面，之前我们已经带大家看过了，里面有 Redis 常见的所有的命令。但你会发现这里有一个说明，叫 `Filter by group`，也就是根据组去做一个分类和过滤。

- `all` 就是所有的命令；
- 你选 `string`，意思就是过滤出 String 这个数据结构的命令，下边这些呢就是 String 相关的命令；
- 那如果我想看跟哈希表有关的，我就可以去找 Hash，看到的就是跟这种结构有关的命令。

> **结论**：所以你可以看到，在 Redis 里面所有的命令，它都是分组的。我们在学习的时候呢，也是分组去学习，一组一组地来就 OK 了。

除了官方网站以外，在我们的命令行里也能看到这些帮助文档。打开控制台，我们先输一个 `help`：

```text
127.0.0.1:6379> help
```

它在 help 里面会告诉你：这里是获取帮助的，关于 Redis 命令的帮助怎么获取呢？有个 `@` 后面跟上 group 代表组。比如说：

- `help @generic` 代表通用的，它是不分数据结构的，就是所有数据结构都可以通用的一些指令；
- `help @string` 就是 String 类型的；
- 再有 List、Set、Sorted Set、Hash……你看这些所有常见的结构它都是有的，非常的丰富。

我们随便看一个吧，比如 String：

```text
127.0.0.1:6379> help @string
```

这里会告诉你命令的名称、命令的一个参数、说明命令的一个摘要，还有从什么版本开始。当然没有官方文档那么详细，官方的浏览器里介绍得更加详细一点。

所以呢，不管是在官网上还是在命令行里都能看得到。

> **提示**：建议大家在学习的时候啊，不是死记硬背，而是参考文档学习——将来忘了也没关系，我只要会查是不就 OK 了？这些命令呢，也不是说谁就能完全记住，除非是你天天在用，否则的话你肯定或多或少就会忘掉一些。忘了没关系，关键是要学会通过查询的方式自己去使用。

### 五个通用命令

下面我们一起来学习一下 Redis 的通用命令。之前也说过，通用命令是对任何的数据类型都可以适用的一些命令。

在官网上，它就是放在 `generic` 这一组下的，很多很多。而在命令行里，通过 `help @generic` 同样能看到很多很多的命令，它们的使用方式也非常的多。

那么如此多的命令，我们怎么去记住它呢？

答案是不用去记。只要你会用帮助文档 `help`，随时都是可以来查的，没有必要去记忆。另外呢，这里边虽然很多，但是最常用的呀其实就那么几个。下面我们就来看几个。

#### keys：查得爽，但生产环境别用

第一个命令是 `keys` 啊，它的作用呢是查看符合模板的所有 key。

那这个命令具体怎么使用呢？大家要想知道某一个命令的使用方式的话，有两种方式：第一种就是利用 `help` 后面跟上这个命令的名称。比如我要知道 `keys` 的用法，`help keys`：

```text
127.0.0.1:6379> help keys
KEYS pattern
summary: Find all keys matching the given pattern.
group: generic
```

`pattern` 代表模板，意思就是找到所有的符合指定模板的这样的一个 key。那这个模板呢有点像一种匹配的表达式——注意，**它不是正则**，它就是一种 Redis 内置的表达式。

在这个表达式里面一般是用通配符来用：`star` 就代表所有。凡是符合要求的 key 都会返回给你。官方文档里还举了几个例子：比如说以 `star` 开头的就是匹配所有；中间是 `star` 一个 `name` 一个 `star` 的，那凡是符合这个要求的都可以返回；还有后边跟上问号的，`?` 代表应该是一个字符，所以它就返回了这个值。`star` 代表多个，`?` 代表就是一个。

我们也来演示一下。先通过 `help` 看一下，然后使用它——在我敲到一半的时候按 `Tab` 键，它是能自动补全的，这个是非常强大的一个功能，并且你看还有提示，告诉你后面要跟一个 `pattern` 模板：

```text
127.0.0.1:6379> keys *
1) "age"
2) "name"
127.0.0.1:6379> keys a*
1) "age"
```

`star` 代表所有、任意的，所以它就匹配到了所有的 key——不管你 Redis 里存 100 个还是 1 万个还是 10 万个、100 万个，都能查出来。

> **易错点**：这个命令呢，你通过它的用法就能看出来，它既然是基于这种通配符去搜索，那么它底层一定是有一种模糊查询的机制。那同学们想一想，它的效率高不高？肯定不高。

事实上呢，当 Redis 的数据量达到一定的规模时，比如说达到了数百万、上千万甚至更多时，你用这种模糊的匹配查询，往往会给服务器带来巨大的负担——这个搜索可能会搜很长时间。

> **注意**：又因为 Redis 是单线程的，那么在它搜索的这一段时间内，它就无法执行其他的命令，那么等于是整个 Redis 的服务就被阻塞了。

所以在生产环境下，是**不建议大家使用 `keys` 去查询**的。当然了，如果说你们的 Redis 是一个集群模式，有主有从，那我在从节点上我去做这个命令行不行呢？那倒也还可以。**千万不要在主节点去做**，因为会阻塞所有的请求。

#### del：删一个，也删一批

第二个命令呢是 `del`，`del` 呢是删除一个指定的 key。

那这个该怎么去用呢？就不废话了，同样用帮助文档看一下呗，`help del`：

```text
127.0.0.1:6379> help del
DEL key [key ...]
summary: Delete a key.
group: generic
```

摘要就是删除一个 key。上面呢可以看到跟的参数就是 key，你要删谁，你就跟上谁呗。同时你可以看到后面有个中括号，这个的意思是它可以接受多个 key——你传一个我就删一个，你传多个了我就删多个。

比如说我们现在来删除一下 `name`，这个时候我们再去查看的时候，你就会发现就剩下 `age` 了，说明 `name` 是被删掉了。这就是删一个。

那如果我要删多个呢？你就跟多个 key 就行了。我们先准备几个 key，这里我们用一个命令叫做 `mset`（后面我们再给大家介绍），它的作用就是批量地往里面插入。你可以看到它是 key、value 这样的形式：

```text
127.0.0.1:6379> mset k1 v1 k2 v2 k3 v3
OK
127.0.0.1:6379> keys *
1) "age"
2) "k1"
3) "k2"
4) "k3"
```

`k1`、`k2`、`k3` 都插入进去了。那么现在呢，我们通过 `del` 来做一个批量的删除：

```text
127.0.0.1:6379> del k1 k2 k3 k4
(integer) 3
```

> **结论**：你会发现它的返回值是 3，这是什么意思呢？它的返回值代表的就是删除的 key 的数量。因为只有三个 key 存在，`k4` 是不存在的，所以返回值是 3。

你想之前我们删 `name` 的时候，返回值是 1，因为只有一个 `name`。所以呢，这个删除它的返回值代表的就是删除的数量，可以删一个，也可以删多个。

#### exists：存在是 1，不存在是 0

判断完了，我们再下一个是 `exists`，是判断一个 key 是否存在。

回到命令行，相信大家应该轻车熟路了吧：首先用 `help` 来查看帮助文档：

```text
127.0.0.1:6379> help exists
EXISTS key [key ...]
summary: Determine if a key exists.
group: generic
```

判断一个 key 是否存在。这里呢 `exists` 后面跟的是 key，也可以跟一个或多个嘛：

```text
127.0.0.1:6379> exists age
(integer) 1
127.0.0.1:6379> exists name
(integer) 0
```

想看 `age` 存不存在，返回值是 1；想看 `name` 存不存在，返回 0，因为 `name` 已经不存在了。这个判断还是挺好用的。

#### expire 与 ttl：给内存上保险

再下一个是 `expire`，是给一个 key 设置有效期，有效期到期时，该 key 会被自动删除。

那么为什么 Redis 要有这样一个命令呢？给大家解释一下。因为 Redis 是基于内存存储的，同学们想象一下，我们把很多很多的数据保存在内存当中，如果说呀永远是往里面插入，而从来不去管删除的动作、不去清理它，那么假以时日，Redis 里面存储的数据也越来越多，总有一天内存可能会被占满，对不对？

所以为了解决这个问题，Redis 给我们提供了一个 `expire` 命令，我们可以用它来给 key 设置有效期。比如说我存了一个数据进去，根据业务需求，比如说这个业务我是一个短信的验证码——我们知道验证码一般的存在时间可能就是五分钟，那我就设置五分钟有效期，到期以后自动删除。这样一来是不是可以节省 Redis 的内存空间？

跟它类似的，或者说合作使用的另外一个命令叫 `ttl`，它是查看一个 key 的剩余有效期。

好，下面呢我们就来试一下这两个命令。同样大家也可以通过 `help` 来查看 `expire` 命令：

```text
127.0.0.1:6379> help expire
EXPIRE key seconds
set a key's time to live in seconds
```

`time to live` 就是存活时间，简称 TTL。后面跟上两个参数：一个是 key，给谁设置有效期；`seconds` 是秒，设置多长时间，单位是秒。

那我就可以通过 `expire` 给一个值设置一个有效期为 20 秒钟。那这个时候我怎么查看它的剩余有效期呢？刚才说了 `ttl` 对不对：

```text
127.0.0.1:6379> expire age 20
(integer) 1
127.0.0.1:6379> ttl age
(integer) 9
127.0.0.1:6379> ttl age
(integer) 7
127.0.0.1:6379> ttl age
(integer) 5
```

它在倒着数：7、5、4、3、2、1、0，最后变成 -2。

这 -2 是什么意思呢？来看一下，我们发现整个 Redis 里面已经没有任何的数据了，`empty`，没有任何数据。证明 `age` 是不是已经被自动删除了。

```text
127.0.0.1:6379> ttl age
(integer) -2
```

那么如果说我们直接存了一个 key，比如说 `name` 杰克、`age` 18，但是我并没有利用 `expire` 给他设置有效期，那他这个时候的存活时间是多长呢？我们来看一下，发现是 -1。

| `TTL` 返回值 | 含义 |
| --- | --- |
| `-2` | key 已经不存在了，说明它是被自动删除的 |
| `-1` | key 存在，但永久有效，不会被自动删除 |
| `0` 及以上 | 距离过期还剩多少秒 |

> **结论**：一般情况下，建议大家在往 Redis 里存入数据时，最好都设置一个有效期。

好，那 Redis 里面比较常用的一些通用命令就介绍完毕了，我们总共讲了这么五个：

| 命令 | 作用 | 要点 |
| --- | --- | --- |
| `keys` | 按通配符模板查看 key | 一般用 `keys star` 查看所有，但因效率问题不建议在生产环境使用 |
| `del` | 删除一个或多个指定的 key | 返回值是实际删除的 key 的数量 |
| `exists` | 判断一个 key 是否存在 | 存在返回 1，不存在返回 0 |
| `expire` | 给一个 key 设置有效期 | 单位是秒，有效期到期后 key 会被自动删除 |
| `ttl` | 查看一个 key 的剩余有效期 | 返回 -2 表示已被删除，-1 表示永久有效 |

> **承前启后**：上一节讲完「把 Redis 装起来、连上去，然后开始敲命令」，下一节接着讲「Redis 常用数据类型：String、Hash 与 List 的命令与用法」。

## Redis 常用数据类型：String、Hash 与 List 的命令与用法
> 对应块：BLK03 | 覆盖分集：P10-P13 | 块标题（分集名）：《基础篇-09.Redis命令-String类型》

Redis 是一个键值型的数据库，只不过它的"值"的类型五花八门、各种各样。我们先从最简单的 String 讲起，再把 Hash、List 也过一遍——这三块正好构成了日常开发里用得最多的数据结构。

### String 看起来是字符串，底层却是字节数组

String 的值就是最简单的字符串，所以它可以认为是 Redis 里最简单的一种数据类型，用起来也非常简单方便。但是呢，都是字符串，它表现出来的形式上还是会有一些差异。

举个例子，假设我有三组键值对：

| 看起来的样子 | 值的类型 |
| --- | --- |
| `hello world` | 普通字符串 |
| `10` | 整型 |
| `2.5` | 浮点型 |

第一组的值是一个 `hello world`，字母，那不就是普通字符串吗？第二组是一个 `10`，尽管它也是个字符串，但是看起来的样子是一个数字。第三个是 `2.5`，同样如此，它是一个浮点数。

那么 Redis 在做数据存储的时候，这几个都是字符串，所以底层呢肯定都是用**字节数组**去存储的。只不过为了节省空间，数值类型的字符串在做编码的时候会不同——它会把数字直接转为二进制的形式作为字节去存储。这样一来，一个字节就能表示很大的数字了，所以会更节省空间。而字符串呢，只能是把字符转成对应的字节码然后再去存储，相对来讲占用内存更多一点。

> **结论**：String 的表现形式不一样、底层编码不一样，但本质都是字节数组。

> **提示**：如果你愿意的话，甚至于你可以把一张图片编译成字节，存到 String 类型里面。里面的内容有多少，你往里面存多少都是可以的。但是它的最大上限不能超过 **512 MB**，所以一般情况下我们也不会往 String 里面存储太多的数据。我刚才说存个图片那只是开个玩笑，一般不会这么去做，最多存一个图片的地址。

也就是说，操作命令上基本都是一样的——不管你是哪一种，什么数字之类的，只是底层编码不同。

### String 的存取：单个与批量

#### SET 与 GET：一次一个，天然带修改

`SET` 其实我们刚才在演示的时候已经演示过了，就是往 Redis 里添加或者修改一个 String 类型的键值对。

为什么叫"添加或者修改"？就是说如果你第一次执行 `SET`，它不存在，那就添加；如果已经存在了，那就变成修改。

```text
SET key value [EX seconds] [NX]
```

大家也可以通过帮助文档，在控制台通过 `help` 看一下这个 `SET` 命令。它会告诉你 `SET key value`，key、value 就是键值对，存进去的就是普通的 String 类型；如果 key 已经存在了，将来就是修改。后面这些呢是一些可选的参数，现在咱们先不管它。

```text
> SET name rose
OK
> GET name
"rose"
> SET name 杰克
OK
> GET name
"杰克"
```

你发现值是不是就被覆盖掉了？所以说增或者改，对吧。

跟 `SET` 对应的，`GET` 自然就是取了。

#### MSET 与 MGET：一次一批

`MSET` 是一个批量的添加。我们刚才 `SET` 是一次添加一组 key 和 value，`MSET` 呢就是批量地添加 key 和 value。

```text
MSET key value [key value ...]
```

来我们看一下 help，你可以看到了，它这个地方接收的不是一个 key 了，这里还可以继续 key1 value1、key2 value2、key3 value3，也就是批量的一种新增。

与此对应的，我们的 `MGET` 当然就是一个批量的获取了——你给我传多个 key，然后呢我一次性把它都返回给你。

```text
> MSET name 杰克 age 18 k1 v1 k2 v2
OK
> MGET name age k1 k2
1) "杰克"
2) "18"
3) "v1"
4) "v2"
```

那么它就会把每一个 key 对应的值都返回给你。它的返回值啊是多个值形成的一个数组，在 Redis 里面多个值形成数组，就可以这样 `1 2 3 4 5` 这样一种形式返回。

### 数值类型独有的自增自减

除了基本的存取以外，既然 Redis 在存储这个数字的时候它的编码不同，所以对于数值类型啊，它就有一些特殊功能了——自增啊、自减呀等等这样的功能。

#### INCR 与 INCRBY：整数，步长可以自己定

`INCR` 是让一个整型的 key 自增一。

```text
> INCR age
(integer) 19
> GET age
"19"
> INCR age
(integer) 20
> INCR age
(integer) 21
```

它的返回值是个 integer，那也就是说它的值其实已经增了一了。你可以看到每执行一次，它值是不是就加一，这就叫自增。

除了 `INCR` 以外，还有 `INCRBY`。`INCRBY` 的意思是让一个整型的 key 自增，但是可以自己指定步长。什么叫指定步长？默认情况下 `INCR` 是自增一，那你可以自己指定这个步长的值，让它每次增更多。

```text
INCRBY key increment
```

`INCRBY` 后面跟两个参数，一个参数是 key，一个参数是增长的数量。

```text
> INCRBY age 2
(integer) 23
> INCRBY age 2
(integer) 25
> INCRBY age 2
(integer) 27
```

这就是每次加二。

那如果说我让它自减，我该怎么办？OK，你可以把这个值改成负数——你把值改成负数，它不就自减了吗？所以 `INCRBY` 可以实现一个自减的效果。

> **提示**：当然了，事实上它有一个专门的命令叫自减，叫 `DECR`。但是在我们一般使用的时候，其实你都用 `INCR` 就行了，只不过给成正负就完了。

#### INCRBYFLOAT：浮点数，必须指定增量

刚才讲的是整数的自增长，那对于浮点数呢，它有一个叫 `INCRBYFLOAT`。

`INCRBYFLOAT` 是让浮点型的数字去做增长。但是浮点型到底增长多少，它不是按一次增一，你必须指定一个数字，让我增多少。

```text
INCRBYFLOAT key increment
```

```text
> SET score 10.1
OK
> INCRBYFLOAT score 0.5
"10.6"
> INCRBYFLOAT score 0.5
"11.1"
> INCRBYFLOAT score 0.5
"11.6"
```

大家来看这个是不是每次都增长指定的步长。

> **结论**：浮点数没有默认增长，必须指定这个增长的步长。

### SET NX 与 SET EX：两个组合命令

最后的这两个呢，一个叫 `SET NX`，一个叫 `SET EX`，这里也给大家翻译一下是什么意思。

#### SET NX：只有真正的新增才生效

`SET NX` 是添加一个 String 类型的键值对，前提是这个 key 不存在，否则不执行。

它的 help 写得很清楚：`Set the value of a key, only if the key does not exist`。如果一个 key 不存在，我才添加；如果存在呢，那我自然就不添加了呗。

所以这个才是真正的新增功能，它只有新增效果。

```text
> SETNX name 李四
(integer) 0
> GET name
"杰克"
> SETNX name2 李四
(integer) 1
> GET name2
"李四"
```

现在呢我们这里已经有了很多很多 key 了，比如说这里 `name` 已经有值了，我再来 `SETNX name`，想给他再来个值，比如叫做李四。你会发现返回值是零，`GET` 一下内部值有没有发生改变，没有吧，依然是杰克。但是如果我添加一个不存在的新 key `name2`，你发现这次返回值为 1，`GET name2` 就能够拿到了。

这就是说啊，当我们存储的 key 不存在时，我才能插入成功；存在，我就插入失败。

> **易错点**：`SET NX` 其实是个组合命令——先是 `SET`，再加一个 `NX`。你看我们在 `SET` 的时候，后面可以跟很多很多参数，我们都会帮助文档看一下，其中就有一个参数是 `NX`。所以当我们 `SET name 王五 NX` 的时候，其实就跟 `SETNX` 的效果是一样的。

#### SET EX：添加的同时把有效期也设上

这个 `EX` 代表的是效果，还是有效期？——是有效期。

还记得通用命令里那个设置有效期的命令吗？它的作用就是设置一个 key 的有效期。比如说我给它一个 10，那么代表这个 key 有效期就是十秒，然后这个元气（倒计时）会自动减少，当它降到零的时候，这个 key 是不是就会被移除了？我们讲过还有这么一个效果，等于删除了。

```text
EXPIRE key seconds
PEXPIRE key milliseconds
```

> **提示**：`EXPIRE` 的时间单位是**秒**，`PEXPIRE` 的时间单位是**毫秒**，这两个千万别记混。

但这个 `EXPIRE` 呢，是在 key 已经存在的情况下操作的。那么 `SET EX` 的作用就是我添加一个 key，并且设置有效期，等于是把添加和有效期的动作合二为一了——添加 `name`，然后设置有效期，比如有效期为十。

```text
SETEX key seconds value
```

```text
> SETEX name 10 杰克
OK
> TTL name
(integer) 10
```

你看一下这个内容，它同样会有一个倒计时。所以 `SET EX` 也是组合命令，哪两个组合？一是 `SET`，二呢是 `EXPIRE`。

它同样也可以在后面加 `EX` 来指定，这个效果跟 `SETEX` 是一样的。

### 把 String 命令分组记

这一堆命令啊，大家可以分组的形式去记忆。

| 分组 | 命令 | 说明 |
| --- | --- | --- |
| 基本存取 | `SET`、`GET`、`MSET`、`MGET` | 单个增、单个查、批量增、批量查；增的操作具备修改功能，存在就是修改、不存在就是新增，所以增改查都有 |
| 数值操作 | `INCR`、`INCRBY`、`INCRBYFLOAT`、`DECR` | 专门操作数值类型，做自增或自减 |
| 组合命令 | `SET NX`、`SET EX` | 前者只在不存在的时候才加，后者是添加的同时设置有效期 |

至于删除呢，删除是我们上一节讲的 `DEL` 命令，它是通用命令，不属于 String 专属。

所以呢，大家分组的方式去学习和记忆，那就更容易掌握 String 相关的这些命令了。至于其他一些命令呢，大家也不需要死记硬背，只要会通过 `help` 帮助去查看相关命令就 OK 了。

### 没有 table，key 靠冒号分出层级

Redis 是键值型的数据库，因此它的键啊一定有一个要求，就是**唯一**。所以我们大多数情况下，都会以数据的 id 来作为 key 形成唯一标识。

那么这里呢就会存在一个问题了——因为 Redis 里并没有像 MySQL 中的 table 这样的概念，所以它没有表，所有数据都是存在一起的。那这个时候我们该如何区分不同类型数据的 key 呢？

比如说我们现在要存储用户，还有商品，都给它写 Redis，而我用户呢有一个 id 呢是一，那我有一个商品的 id 恰好也是一，那么这两个的 id 是一样的。如果说都存 Redis 里，岂不是产生了冲突。大家思考一下这个问题该怎么解决？

相信很多同学都能想到了：**我们完全可以在这个 id 的基础上，拼接一些其他的字符串**，这样就能区分。

但是这个拼接也不是随意拼接的。在 Redis 里边，它的 key 允许多个单词拼在一起形成层级结构，然后这个单词之间用冒号去隔开。

```text
项目名:业务名:数据类型:唯一标识
```

这个格式不是固定的，这是我举的例子。如果说在公司里你们有自己的 key 的标准，你可以按照你们的标准去做。

#### 拿黑马项目举例

现在假设我的项目名叫黑马，那我有 `user` 和 `product` 两种不同类型的数据。那现在因为我没有业务啊，这个业务我就不管了，那我们的 key 就可以这么来定义。

比方说我现在要存用户，那我就可以用黑马代表项目名，`user` 代表类型，然后后面的 1 其实就是他的 id 了。那商品也就是类似的，`黑马:product:1`。

这样呢，我的 key 就形成一种层级关系了，说明他们俩是一个项目的，只不过一个是 user，一个是商品。

#### 值放什么：把 Java 对象序列化成 JSON

现在 key 定义好了以后，它的值是什么呢？我们知道用户也好、商品也好，在我们的项目中往往都是一个 Java 类或者 Java 对象。这样的对象该怎么存储到这个值的位置呢？

上一节我们讲 String 的时候其实提到过，String 的值是字符串。Java 对象虽然不是字符串，但是它完全可以序列化成 JSON 的风格来存储。就像比方说我们 `user 1`，那么 id 为 1 的这个用户啊，他有很多的信息，最终我用了一个 JSON 字符串的形式去存储——你 Java 对象里面有多少字段，这里边就有多少字段就可以了。那同样道理，商品也是，我们也可以把它序列化为 JSON 字符串去存储。

```text
> SET 黑马:user:1 <粘贴课前资料里准备好的 JSON 串>
OK
> SET 黑马:user:2 <粘贴 id 为 2 的用户的 JSON 串>
OK
> SET 黑马:product:1 <粘贴"小米 11"的 JSON 串>
OK
> SET 黑马:product:2 <粘贴"荣耀 60"的 JSON 串>
OK
```

这个串儿在这写就太麻烦了，我在课前资料里提前给大家准备好了一个 JSON 串的文档，打开一看呢就有两个用户和两个商品。我们先复制一个用户 id 为 1 的杰克，回到控制台粘贴回车——一个用户就塞进去了；再来看看 `黑马:user:2`，id 为 2 的，同样去粘贴他的 JSON 字符串，两个存进去了；再来 `黑马:product:1`，这一次的类型就不是用户了，而是商品，同样 id 为一，因为它俩的前缀不同，所以这个时候就不会产生冲突。

目前我们就存储了两个用户、两个商品了。现在呢我们看一下 `KEYS *`，能够看到我刚刚新插入的这些数据，没错吧——四个 key。但是呢从这里并不能看到有什么特殊之处，就是四个 key 嘛，只不过可以长一点。

别急，我们通过图形界面客户端来看一下，在这儿我点下刷新，大家发现多出来一个叫"黑马"的。同学们，我们什么时候有插入一个"黑马"的 key 吗？没有吧，黑马是我们 key 的前缀。我们点进去，你发现它里面有两个 `product` 和 `user`；再点，`user` 里面有一和二，`product` 有一和二。

```text
黑马                        ← 项目名（key 的前缀，从未单独插入）
├── user                   ← 数据类型
│   ├── 1   ──────────►   id 为 1 的用户的 JSON 串
│   └── 2   ──────────►   id 为 2 的用户的 JSON 串
└── product
    ├── 1   ──────────►   "小米 11" 的 JSON 串
    └── 2   ──────────►   "荣耀 60" 的 JSON 串
```

你看我们以冒号隔开，这个 key 是不是很自然地形成层级结构了：黑马作为第一层，而 `product`、`user` 代表第二层，所有的商品都放在 `product` 下边，所有的用户放在 `user` 下面，是不是很自然地就把数据给分离了，形成了层级结构。这时候我们存取的 JSON 字符串看起来就很舒服。

> **结论**：这种 key 的层级存储，它可以避免 id 相同时的这种冲突，并且让我们的数据分离看起来比较优雅。这是我们使用 Redis 时的一个最佳实践——key 最好都用这样的方式隔开。

这不仅仅适用于 String 类型，我们学的其他的数据类型，它的 key 都可以用这种方式去做成层级的模式。

### Hash 类型：把 JSON 串拆成一个个字段

之前呢我们一再强调，Redis 呀是键值型的数据库，它的值的类型多种多样、五花八门。在 String 类型当中，它的值就是普通字符串；而哈希类型的值呢，则是一个**无序字典**。

很多同学可能不理解"无序字典"啊，其实呢就是一个哈希表，就跟我们 Java 中的 `HashMap` 呀比较类似。当然有一些差异，我们在后续的原理篇当中讲底层数据结构的时候你就明白了，现在呢你先把它当成一个 `HashMap`。

#### 为什么用字符串存对象那么别扭

上一节中我们已经讲到了，String 结构它的值是字符串，所以当我们要表示一个 Java 对象时——它比较复杂的一个数据结构——我们只能把它序列化成 JSON 字符串以后去存。

这种存储方式啊，有一个最大的弊端：**因为你存取的是一个字符串，里边不管是有两个字段还是十个字段，它都是一个字符串。** 现在你想单独对某个字段做修改，是无法进行修改的——要么你把整个字符串覆盖掉，要么呢你只能是删掉重来。

那么作为哈希结构呢，它的 key 跟我们 String 类型没什么差异，主要是 value。那么它的 value 不再是一个字符串了，它的 value 又分成两部分：一部分叫 `field`，或者也有人称它为哈希 key；另外一部分是 value。

```text
String 类型（value = 一个字符串）
    key  ───────────────►  "id=1, name=杰克, age=20, ..."

Hash 类型（value = 一个哈希表，又是一层 key-value 结构）
    key  ───────────────►  ┌────────────┬──────────┐
                           │   field    │  value   │
                           ├────────────┼──────────┤
                           │   name     │   Lucy   │
                           │   age      │   17     │
                           └────────────┴──────────┘
```

那么我们就不需要再用 JSON 字符串来表示一个用户了，我们可以把一个用户里边的 name、age 等等给它拆开，变成独立的这样的字段值。你有十个字段，我这里呢这个 `user:1` 这个 key 里面就可以有十个 field。

这样呢我们就能把每个字段独立去表示了。那么你想要单独修改某一个字段的时候，对于其他字段来讲没有任何影响。所以这就是哈希结构相对于字符串结构它的优势了——它更加的灵活。

#### 命令就是前面的 SET 加个 H

Hash 的常见命令呢，我们可以对照着 String 类型的命令去做一个学习。在 String 里面我们讲过 `SET`、`GET`，你会发现啊，把所有这些个命令前面加上 H，它就变成了哈希操作的命令了。

那我们以 `HSET` 为例。`SET` 存的时候呢给个 key，在 String 里面给个 value 就结束了，对吧。但是呢因为哈希类型它多了一个 field——来看刚才这幅图，哈系结构因为多出了 field 这样一个东西，所以在它的命令当中又多了一个 field。

那么你在存的时候，你第一要告诉我 key，第二要告诉我你存的是哪个 field，第三再告诉我值。那如果我要存 `name`，那么这个地方的 field 就是 `name`。

```text
HSET key field value
```

```text
> HSET 黑马:user:3 name Lucy
(integer) 1
> HSET 黑马:user:3 age 21
(integer) 1
> HGET 黑马:user:3 name
"Lucy"
```

你看这样呢我就存进去了一组这样的字段和值了。那现在我要再存一个呢，我还可以利用 `HSET`，但是呢这次你就不要讲 name 了，这次你来个 age、21。你看我的 key 是同一个 key，也就是在同一个 key 里，我是不是插入了两个不同的 field。

打开图形化客户端来看一下，刷新一下 id 为 3 的这个。你看他的这个结构表现出来的，是不是跟图上画的这种很相似的？也就是说他的这个 key 里边存的这个 value 啊，又是一个 key-value 结构——哈希结构。其实它这个标注的 key，其实就是 field：`name`、`age`、`Lucy`、`21`。

那现在我想单独对一个值做修改可不可以？答案是可以的。那我只需要再做一次 `HSET` 就可以了。

```text
> HSET 黑马:user:3 age 17
(integer) 0
> HGET 黑马:user:3 age
"17"
```

所以它是允许你针对单个字段的修改，很方便。

那 `MGET` 呢？哎你也不能说光给个 key 就行了，你除了 key 以外，你还告诉我你要获取的是哪一个字段。那 `HMSET` 顾名思义批量的一种新增，也就是我在给 key 赋值的时候，我可以指定多个字段值；那 `HMGET` 自然就是批量地去获取了。

```text
HMSET key field value [field value ...]
HMGET key field [field ...]
```

```text
> HMSET 黑马:user:4 name 韩梅梅
OK
> HMSET 黑马:user:4 name lily age 20 sex man
OK
> HMGET 黑马:user:4 name age sex
1) "lily"
2) "20"
3) "man"
```

哎我又存了一个 id 为 4 的用户，它的名字叫韩梅梅。那 `HMSET` 呢，它其实可以存多组字段名、字段值——刚才存了一组，现在我还可以存多组，我可以存多组走。

打开图形化客户端刷新 id 为四的这个，你看是不是有 name、age 和性别就都有了。

> **结论**：你在这里可以看到，我们的哈希结构再一次证明了一点——我们的 Redis 结构是松散的，它没有说要求你必须得是什么样子的，我这边多一个字段是没问题的。

#### 想一次全拿：HGETALL、HKEYS、HVALUES

除了这样的基本的存取以外呢，它这里还有一个叫 `HGETALL`。`HGETALL` 是获取一个哈希类型的 key 中的所有的字段名和字段值。

那刚才是一个一个取，或者说你要自己手动地指定这个 field。那万一 field 很多，比如有十个，我不想一个一个指定，我想都拿到怎么办？那么就用这个 `HGETALL`。

```text
> HGETALL 黑马:user:4
1) "name"
2) "lily"
3) "age"
4) "20"
5) "sex"
6) "man"
```

你看这次只需要知道 key 就行了，不需要知道字段。它呢就把这个 key 下所有的字段名和字段值依次返回——一个 key、一个 value，一个 key、一个 value，这样一个格式紧挨着这样去返回的。

再有了 `HKEYS`，这个是获取一个 key 中所有的字段；那么 `HVALUES` 呢，是获取 key 中所有的 value。

```text
> HKEYS 黑马:user:4
1) "name"
2) "age"
3) "sex"
> HVALUES 黑马:user:4
1) "lily"
2) "20"
3) "man"
```

这三个你可以理解成我们 Java `HashMap` 里面的什么呢：`HGETALL` 返回的是不是所有的 entry 键值对；`HKEYS` 呢，是 `HashMap` 里的 keys 部分，获取所有的字段名、所有的 key；`HVALUES` 是获取所有的值。效果是类似的。

这些操作啊，就跟我们的 `HashMap` 操作真的非常接近，所以大家呢这样关联学习，其实记忆起来就不难了。

#### 字段也能自增，还有 HSETNX

哈希里边也支持自增长。`HINCRBY`、`INCRBYFLOAT` 不就是自增吗，只不过加了 H，是让哈希类型的一个 key 的字段去增长，比如说年龄。

```text
> HINCRBY 黑马:user:4 age 2
(integer) 22
> HINCRBY 黑马:user:4 age 2
(integer) 24
> HINCRBY 黑马:user:4 age 2
(integer) 26
```

原来是 20，现在是不是变 22 了。当然你给成负数的话，它也是没问题的，这就变成自减了。

那么哈希里面也有 `SET NX` 操作了，`HSETNX`，跟我们 String 类型的 `SETNX` 一样：同样是判断值是否存在，值不存在了我再执行，如果已经存在了，我就不执行了。

> **易错点**：但是这次判断的不是 key，判断的是某一个 field 是否存在。

```text
> HSETNX 黑马:user:4 sex woman
(integer) 0
> HSETNX 黑马:user:3 sex woman
(integer) 1
> HGETALL 黑马:user:3
1) "name"
2) "Lucy"
3) "age"
4) "17"
5) "sex"
6) "woman"
```

现在我给用户 4 `HSETNX` 一个 sex 字段——不好意思，他已经有性别了是吧，你总能给他变性吧——看到没有，返回值是零，不允许。但是你给 id 为三的用户加行不行？这个用户是没有性别的，现在是可以加的，返回值是一。

所以呢，`HSETNX` 跟 String 的 `SET NX` 效果是类似的，只不过呢他判断的是某个字段是否存在，而 String 判断的是当前 key 是否存在。

> **结论**：Hash 类型的常见命令你就把它当成咱们 Java 里边那个 `Map` 去操作就行了。

### List 类型：一条能两头走的有序链

与前面讲的两种类型类似啊，不同数据类型的差异，主要就是在值的数据结构不同：像 String 类型呢，它的值就是普通字符串；Hash 类型呢它的值是一个哈希表；而这节课我们要学的 List 类型，它的值自然也就是一个类似的集合了。

这个 List 呢，给我们 Java 中的 `LinkedList` 的比较类似啊，因为它的底层可以看作是一个双向链表的结构。当然实际结构会更复杂一点，我们同样会在后边的原理篇当中给大家去讲解。

那么双向链表的最大的一个特点，就是它可以支持正向检索和反向检索，从头到尾或者从尾到头都是可以的。所以呢，它跟我们 Java 中的 `LinkedList` 的特征基本是类似的：

- **有序**——这个跟插入的顺序是有关系的；
- **元素可以重复**——因为它不会去检查元素是否是一致；
- **插入和删除速度快**——这个是必然的，所有的链表插入和删除都会比较快，因为插入和删除只是改变了链表中节点的指向啊；
- **查询速度相对差一些**——比传统的那种数组类型会稍微地差一点，因为它只能通过逐个节点遍历的方式进行查询。

好，这 Redis 这个 List 也都基本上是这样子的。那么具体我们什么情况下可以使用这种类似的结构？比较常见的就是用来保存一些**对顺序有要求的数据**。

举个例子：你的朋友圈里面点赞，有不同的人来点赞，那么点赞完了，这些人是不是会有一个列表形式展示出来？谁先点赞、谁后点赞都会有一个顺序。还有评论也是如此，他都是有序的，谁先评论的、谁后评论的。那这种呢都可以用一个 List 去保存。

#### PUSH 和 POP：左边还是右边

我们来看一下它的命令。这里的命令呢大家可以简单看一下，`LPUSH`、`RPUSH`、`LPOP`、`RPOP`，整体呢是比较接近的。核心操作就是两个：一个是 `PUSH`，一个是 `POP`——`PUSH` 是插入，`POP` 呢是移除并返回，等于是就是获取了。

那为什么会有 `LPUSH` 和 `RPUSH` 呢？这个其实就是队首和队尾的一个区别了。`L` 就是 left，就是左侧，可以理解成是队首；`R` 是右侧，可以理解成是队尾。也就是说，它在这里其实是把一个链表看成了一个队列，一个有头有尾的这样一个结构。

```text
最初：  [ a , b ]      左侧是队首，右侧是队尾

LPUSH c  →  [ c , a , b ]          从左边插，新元素跑到最左边
LPUSH d  →  [ d , c , a , b ]
RPUSH e  →  [ d , c , a , b , e ]  从右边插，新元素跑到最右边

LPOP     →  取出 d（最左边那个）
RPOP     →  取出 e（最右边那个）
```

同学们可以思考一下，现在我插入一个元素叫 c，那么 c 这个元素是会在 a 的前边，还是跑到 b 的后边去了？因为是左侧插入啊，所以它肯定是在 a 的前边。**它不会说，因为 c 是比 b 后一个字母，所以跑到后边去——不会这样的。它是跟你插入的位置有关的。**

那如果我现在再 `LPUSH` 一个新的元素 d，同学们觉得 d 元素会在哪里？没错，他是在 c 的前面。那如果是 `RPUSH` 呢？那么恰好相反，`RPUSH` 它就不是往队首了，是从右侧，那就是队尾插入；这个时候如果我插入一个元素 e，那么 e 会出现在 b 的后面。

所以呢，从右侧插入的就在最右边，从左侧插入的就在最左边。那 `POP` 是取，`LPOP` 呢是从左边取；那现在我从最左边取一个元素，取到的是谁？自然就是 d 这个元素。那我如果是从 `RPOP`，从右侧去取，取到的自然就是 e 这个元素。

> **提示**：大家呢不需要去死记硬背，在你的脑海中你只要存储这样一个画面就行了——你把队列中元素简单在脑海中想象一下这个列表的样子，然后呢 `LPUSH` 就从左边插，`RPUSH` 就从右边插，你大概就能够知道我到时候存进去的是谁、取出来是谁了。

#### 按角标取一段：LRANGE

除此之外呢还有一个 `LRANGE`，`LRANGE` 是一个范围的获取，返回一段角标范围内的所有元素。

```text
LRANGE key start stop
```

它第一个是指定 key，就是获取哪一个列表，然后呢再指定 start 开始、end 结束就行了。比如说 `LRANGE key 1 2`，也就是取角标 1~2 之间的，那么自然取得的就是这部分。

```text
> LPUSH users 1 2 3
(integer) 3
```

我推进去 1、2、3 那三个元素，推进去以后它的顺序是什么样子的？打开图形界面客户端来看一下，刷新到 users——它的顺序是 3 2 1。为什么这样子？因为啊不管你推了几个元素，它其实就是按照顺序地先推 1 号，那么 1 此时是在最左边；再推 2 号，那么 2 就跑到 1 的左边去了，因为你是 L 不是吗；那么接着 3，3 是不是就跑到了最左侧了。

那如果现在是 `RPUSH` 呢？那他自然就反过来了，它会从这个右侧去推。来了个 4 5 6，推了三个元素，那么这三个元素呢自然就会排到右侧去——从右侧先推 4，再推 5，再推 6。

那 `POP` 是取，对不对？我们来试一下。

```text
> LPOP users 1
"3"
> RPOP users 1
"6"
> LRANGE users 1 2
1) "1"
2) "4"
```

`LPOP` 取一个，最左边是不是 3？那是不是就拿到 3 了。注意这个 `POP` 同时还会把元素给移除，所以回到图形化界面你会发现 3 是不是没了。那我现在 `RPOP`，我取的应该就是谁？是不是 6。那用 `LRANGE` 来取呢，我们取 1 到 2，看一下实际返回的是 1 和 4。为什么？因为 0 号、1 号、2 号嘛，所以从 1 开始取，2 结束，就取到了这两个。

> **易错点**：大家不要看前面这个编号啊，前面这个编号不是角标，它是从 0、1、2、3、4 这样子的。

#### 阻塞式获取：BLPOP 与 BRPOP

那我们刚才还讲了，有一个叫 `BLPOP` 和 `BRPOP` 这样的命令。它跟 `LPOP`、`RPOP` 有点类似，区别呢又加了一个 `B`，那么这个 `B` 代表的是阻塞（block）。

就是说它跟 `LPOP`、`RPOP` 的效果是一样的，都是取一个、从左取一个、从右取。区别在于：`LPOP` 和 `RPOP` 当列表中没有任何元素时，你去取，它会直接返回一个 nil，直接返回的内容告诉你没有。但是如果是 `BLPOP`、`BRPOP` 这两个，它就不会，它会等待一段时间，有点像阻塞队列的效果。

```text
BLPOP key [key ...] timeout
BRPOP key [key ...] timeout
```

我们来试一下，打开控制台，这里我把这个控制台复制一个，好，我现在有两个控制台，这边我也通过 redis-cli 连接上，然后输入一下密码。

接下来呢我这边通过 `BLPOP` 来尝试获取元素。这里我故意少传一个参数——它的第一个参数是 key，第二个参数是 timeout 时间。意思就是说我等，但我不能无限等吧？万一你这队列里永远没有元素，难道我等到海枯石烂吗？这不行啊，还得有一个超时时间。这个时间单位是秒啊，我写 10 就是 10 秒，我写 100 就是 100 秒，也就是说我等 100 秒钟啊，等不到，我就结束了。

```text
> BLPOP users
(error) ERR wrong number of arguments for 'blpop' command
> BLPOP users 10
```

你看它是不是卡到这里了？哎，这就是阻塞的意思。那现在你在另一个客户端里，你再来去执行一个命令，比如说 `LPUSH users 1 2 杰克`，插入一个元素。这个时候我们赶紧回去，我发现这边是不是拿到了杰克？看到了吧。

所以说呢，它的 `POP` 就是阻塞，并且还告诉你了啊，花了多长时间才拿到。这就是所谓的阻塞式获取。

### 用 List 模拟栈、队列和阻塞队列

最后我们一起来思考这么几个问题：第一，如何利用 List 这个结构模拟一个栈？第二，如何用 List 模拟一个队列？第三，怎么模拟阻塞队列？

我们现在说的是栈和队列。栈呢我们知道它的特点是什么？是不是先进后出；那么队列先进先出。

那怎么样才能实现这样的效果呢？事实上呢，咱们那个开始播课啊最早的时候，毕老师给大家举过一个例子，我觉得非常的贴切，也非常容易去记。

**先进后出**，这像什么呢？就像是你去喝酒喝大了，然后呢吐了。你想你喝酒喝了很多，你先喝进去的是不是已经消化了？最后喝进去的，如果你吐了，是不是先吐出来？是不是有点像先进后出？所以呢，喝酒吐了啊就是栈。

**队列**呢，就是你喝酒喝多了但是没吐，但是你喝的有点撑，你要去上个厕所排出来，是不是啊？那么这个时候呢就是先进先出了——因为你先喝进去的先消化，是不是就先排出来了。

好，那么这个跟我们当前这个有什么关系呢？大家思考：**如果你是喝酒喝吐了，是栈**，那你喝是用嘴巴喝，吐也是用嘴巴吐，是不是同一个口？所以栈的特点是什么？就是入口和出口在一起。

那么队列呢？哎我们刚才讲了，是不是那个喝酒喝多了去上厕所排出去了——你喝是从嘴巴喝的，排是从下边排的，不是一个口吧？所以呢，入口和出口不在一起。那么这就是栈和队列了。

道理太简单了。我们想实现一个栈，只要入口出口在同一边就行了。

```text
栈（先进后出）：入口与出口在同一侧
    LPUSH  +  LPOP        （都用左边）
    RPUSH  +  RPOP        （都用右边）

队列（先进先出）：入口与出口在不同侧
    LPUSH  +  RPOP        （左进右出）
    RPUSH  +  LPOP        （右进左出）

阻塞队列：先得是队列，再把"取"的那一步换成阻塞版本
    LPUSH  +  BRPOP
    RPUSH  +  BLPOP
```

只要在同一边就是栈，只要不在同一边就是队列。至于阻塞队列又是怎么回事呢？阻塞队列首先是什么？哎首先是队列，然后是什么？是阻塞。那因此呢，它的时候其实就是：首先你要保证入口和出口在不同边，是个队列；其次呢，取的时候不要用传统的 `POP`，而是要用 `BLPOP` 和 `BRPOP`。这样是不是就是阻塞队列了？

### 本讲提到的题目

#### 怎么用 List 模拟一个栈

**题干**：Redis 的 List 是一个双向链表，如何只用 List 模拟一个栈？

**答案**：栈的要求是先进后出、入口与出口在同一边。所以只要入和出都走同一侧即可——`LPUSH` 配 `LPOP`，或者 `RPUSH` 配 `RPOP`。本讲正文"用 List 模拟栈、队列和阻塞队列"里的分析就出自这个理由：栈的特征是入口和出口在一起（就像喝酒用嘴巴喝、用嘴巴吐，是同一个口）。

#### 怎么用 List 模拟一个队列

**题干**：如何用 List 模拟一个先进先出的队列？

**答案**：入和出走不同的两侧——`LPUSH` 存、`RPOP` 取，或者反过来 `RPUSH` 存、`LPOP` 取。这样元素就会按照写入的顺序依次被取出。

#### 怎么模拟阻塞队列

**题干**：在队列的基础上，怎么再加上"阻塞"的能力？

**答案**：分两步。先按队列的要求保证入口和出口在不同边；然后把取的那一步从 `LPOP`/`RPOP` 换成 `BLPOP`/`BRPOP`。区别在于列表为空时，前者立刻返回 nil，后者会一直等到有元素进来或者超时时间耗尽为止。

## Set、SortedSet 与 Redis 的 Java 客户端
> 对应块：BLK04 | 覆盖分集：P14-P18 | 块标题（分集名）：《基础篇-13.Redis命令-Set类型》

前面几种数据类型大家都学过了，set 类型该怎么用，其实也能想象到。但有一件事跟前面记住的那几种**一定不一样**——它的数据结构。

### Set 底层：一个 value 恒为 null 的哈希表

set 类型有点像咱们 Java 中的 HashSet。HashSet 的底层是由 HashMap 实现的，所以我们 Redis 的这种 set 结构，也可以看作是一个 **value 为 null 的哈希表**。

既然是哈希表，底层肯定还是一个哈希表，只不过这一次我们不关心它的 value 了，只关心它的 k。这一下，它就变成了一个 set。

```text
   insert "tom"
        │
        │   ① hash("tom") → 算出插入角标
        │   ② 按角标落进哈希表，value 恒为 null
        ▼
   ┌───────────────────────┐
   │  k = "tom"  →  null   │   同一个 k 再来一次 → 互相覆盖
   └───────────────────────┘
        │
        └── 存储顺序与插入顺序无关  → 无序
            走哈希表查找，复杂度低 → 查得快
```

有了这个底子，它和 Java 的 Set 特征也比较类似：

- **无序**：每一个插入的元素都会用 hash 算法来计算它插入的角标，因此数据的存储顺序与我们插入的顺序无关；
- **元素不可重复**：相同元素会互相覆盖，这一点跟 HashSet 很像；
- **查找速度比较快**：根据哈希表来做查找，时间复杂度是比较低的，所以速度非常快；
- **比 Java 的 Set 多了一些功能**：Redis 的 Set 支持交集、并集、差集等等特殊的功能。

> **提示**：最后这一条才是 Set 类型的价值所在。好友列表、共同好友、关注列表……这些用集合运算来做非常方便。所以在实际的开发中，特别是在一些交流型的、社交型的应用当中，Set 的使用还是比较广泛的。

### Set 的两类命令

上面这些特征落到命令上，正好分成两部分：一部分是对单个集合的操作，另一部分是多个集合之间的操作。

#### 单个集合的增删查

| 命令 | 作用 | 参数说明 |
| --- | --- | --- |
| `SADD key member [member ...]` | 往集合中添加元素 | `key` 是集合名称，`member` 是要插入的元素；省略号说明它可以一次插一个，也可以一次性插多个 |
| `SREM key member [member ...]` | 移除元素（remove 的缩写） | 同样支持移除一个或多个，先指定集合名称 `key`，再指定具体元素 |
| `SCARD key` | 返回集合中元素的总的个数 | 就是一个计数 |
| `SISMEMBER key member` | 判断这个元素在不在当前集合里 | `key` 代表指定的集合，`member` 是待判断的元素；有点像 Java 里那个 `contains` |
| `SMEMBERS key` | 返回集合中的所有元素 | 我所有的成员 |

打开控制台，我们把这几个命令过一遍：

```text
SADD s1 a              # 添加一个元素
SADD s1 b c d          # 也可以一次性加三个
SMEMBERS s1            # a  b  c  d
SREM s1 a              # 删掉 a
SISMEMBER s1 a         # 0  —— 没有了
SISMEMBER s1 b         # 1  —— 还有
SCARD s1               # 3
```

你看，一个集合的增、删、判、查、数，就这几个命令，全在这儿了。

#### 多个集合之间的交集、差集、并集

刚才说过，Set 还支持多个集合之间的交互操作，比如交集并集等等。

```text
   s1 = { a, b, c }        s2 = { b, c, d }

   SINTER   交集   s1 ∩ s2   =  { b, c }         两边都有的
   SDIFF    差集   s1 - s2   =  { a }            s1 里有、s2 里没有的
   SUNION   并集   s1 ∪ s2   =  { a, b, c, d }  合在一起，重复元素只记一次
```

`SINTER` 接受 `key1 key2` 这样的参数，很直白，求的就是两个集合的交集。这个例子我们一眼就能看出来是 b、c；但是如果集合比较复杂、元素比较多的时候，你肯定是用命令来求更方便。

`SDIFF` 这个我们接触得比较少一点，它代表的是**差距**——`S1`、`S2` 的差距，就是看 `S1` 里有、`S2` 里没有的。在这个例子里就是元素 a。

`SUNION` 就更简单了，把所有元素合并在一起。但你要知道 set 是不能重复的，所以当所有元素组合在一起的时候，重复元素只会记录一次，最终的元素个数就是 a、b、c、d。

> **易错点**：`SDIFF` 的第一个 key 是被减数。同样两个集合，`SDIFF s1 s2` 和 `SDIFF s2 s1` 算的是两回事，把 key 的顺序写反，结果就反了。

### 好友列表案例

我们通过一个案例把上面这几个命令都练习一遍。案例是这样的：将下列数据用 Redis 的 Set 集合来存储——有一个张三，李四；张三的好友有李四、王五、赵六；李四的好友有王五、麻子、二狗。

我们把这些数据添加进去。这里我们就不写汉字了，写汉字的话比较麻烦，还容易写错。张三我们用 `zs`，李四用 `ls`：

```text
SADD zs lisi wangwu zhaoliu
SADD ls wangwu mazi ergou
```

现在可以认为是两个人的好友列表就有了。围绕它有这么几个功能：

| 需求 | 用哪条命令 |
| --- | --- |
| 计算张三有几个好友 | `SCARD zs` |
| 计算张三和李四的共同好友 | `SINTER zs ls` |
| 哪些人是张三的好友，却不是李四的 | `SDIFF zs ls` |
| 张三和李四的好友总共有哪些人 | `SUNION zs ls` |
| 判断李四是否是张三的好友 | `SISMEMBER zs lisi` |
| 判断张三是否是李四的好友 | `SISMEMBER ls zs` |

一个一个走。`SCARD zs` 返回 3，就是张三有三个好友。`SINTER zs ls` 求交集，共同好友是王五。`SDIFF zs ls` 求差距，在张三那有、在李四里却没有的，一看有两个：李四和赵六，说明张三的好友列表里有这两个人，而李四的好友列表里没有他们。`SUNION zs ls` 求并集，总共五个人。

最后两条就有意思了。判断李四是否是张三的好友，就是在 `zs` 这个集合里查有没有李四这个人，结果是有的。可再判断张三是否是李四的好友——诶，这个有点意思了，李四张三，是不是李四的好友张三啊？结果发现**不是**。

哦，张三的好友有李四，但李四的好友里没有张三。说明啊，这个朋友关系有点儿故事，对不对。

然后结果李四一气之下，最后把李四从张三的好友列表中删除，那就要用 `SREM` 了：

```text
SREM zs lisi
SMEMBERS zs     # 里面已经没有李四了
```

到这儿，Set 集合中的所有命令我们就算练习了一遍了，同时呢我们也发现了，张三和李四是表面朋友，对不对。

### SortedSet：给每个元素带上分数

从名字来看，SortedSet 首先呢它是一个 set，也就是集合；同时呢它是一个 sorted set，也就是可排序的集合。

那我想问问大家呀，在 Java 当中有没有哪一种 set 集合是可排序的？我们 Java 中有一种叫做 TreeSet 的类型，正是一种可排序的集合吧。

#### 底层：跳表管排序，哈希表管查分

那么我们 SortedSet 它的底层数据结构到底是什么样子呢？

跟我们的 TreeSet 啊，从功能上来讲有点相似，都是可排序的，并且是 set 集合，元素唯一等等。但是呢，底层数据结构上的差别其实是蛮大的。因为我们的 TreeSet 底层是**红黑树**实现的，而我们 SortedSet 却不是啊。另外呢，我们在排序的时候 TreeSet 需要你**定义排序方法**，而我们 Redis SortedSet 它的底层排序，是根据一个**固定的 score 值**来排序的。也就是说，我们在向 SortedSet 中存储元素时要带上一个 score 得分，那这样一来，它就能帮我们根据得分去排序了。

那么它底层的存储呢，有一个跳表和一个哈希表：

```text
                     ZADD key score member ...
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
   ┌────────────────────────┐    ┌────────────────────────┐
   │   skip list            │    │   hash table           │
   │  按 score 维护顺序     │    │  key   = member        │
   │  TopN 走这里           │    │  value = score         │
   └────────────────────────┘    └────────────────────────┘
              │                               │
              └──── 负责排序                  └──── 负责按元素查分
```

跳表的作用是用来做排序的；哈希表呢其实就是最基本的结构了，k 是我们的元素，这样来实现了 set 的效果，值呢是对应的 score 分数。

> **定义**：SortedSet = Set + score。每个成员都带一个分数，排序就按这个分数来。

因此它具备的特性有这么几个：第一是可排序；第二元素不能重复，毕竟它是个 set 嘛；第三查询速度快，因为它有哈希表，所以查询速度比较快，再加上跳表，它还可以完成一种排序的功能，并且跳表也可以增加查询的速度。

也正因为 SortedSet 具备这样的排序功能，并且查询效率也非常高，所以它经常被用来实现像排行榜这样的功能，比如 TopN、Top10 这样的效果。

#### 命令清单，以及那个 REV 后缀

这个地方的命令有点多，但是有很多的命令都是似曾相识的。

| 命令 | 作用 | 说明 |
| --- | --- | --- |
| `ZADD key score member [score member ...]` | 新增元素 | 除了 key 和 member，还要带上一个分数。**分数在前、元素在后**，后面可以串很多组，可以一起批量添加 |
| `ZREM key member` | 移除元素 | 跟上节的 `SREM` 一个套路，给个元素我帮你删了就完了 |
| `ZSCORE key member` | 查询分数 | 每个元素都带分数，想查某个元素的分数就用它 |
| `ZRANK key member` | 获取排名 | 因为有排序功能，排序默认是根据分数来排的，有排序自然就有排名 |
| `ZCARD key` | 获取元素总个数 | 跟上节的 `SCARD` 一样，就是一个计数 |
| `ZCOUNT key min max` | 统计**分数区间**内的个数 | 比方说一个班级，统计 60 分以下的不及格人数，或者 90 分以上优秀的人数 |
| `ZINCRBY key increment member` | 分数自增/自减 | `key` 是集合名称，`increment` 是自增或自减的值，`member` 是具体的某一个元素 |
| `ZRANGE key start stop` | 按**排名区间**取元素 | 先按 score 排序，然后获取指定排名范围内的元素，角标从 0 开始 |
| `ZRANGEBYSCORE key min max` | 按**分数区间**取元素 | min/max 就是分数的最小值最大值，返回区间之间的所有元素 |

这里有两个地方特别容易搞错，我再点一遍。刚才 `ZCOUNT` 查的是**数量**，`ZRANGE` 是获取**具体的元素**——同样给了 min 和 max，一个按分数值取范围，一个按排名范围取范围。

比方说 `ZRANGE` 我给的是 `0~9`，那就是按得分排序以后，去取排名在前十名的元素，因为角标是从零开始的；如果我给的是 `0~4`，那自然取的就是前五名 Top5 的元素了，它**是按照名次去取范围的**。而 `ZCOUNT` 呢，是按照分数值去取范围。

那如果说我想按分数值取范围、要具体的元素呢？那就要用 `ZRANGEBYSCORE`，它给的 min 和 max 自然就是分数的最小值最大值，返回的就是在这个分数区间之间的所有元素。

> **易错点**：`ZRANGE` 和 `ZRANGEBYSCORE` 长得像，拿的东西完全不同——前者的 min/max 是**名次角标**，后者的 min/max 是**分数值**。计数那边也一样，`ZCARD` 是全量个数，`ZCOUNT` 才是按分数区间统计。

> **注意**：我们刚才讲的所有的这些排名，默认都是**升序**的排名，按分数升序。那如果说我们要降序排名，就需要在这条命令的 `Z` 后面添加 `REV`。

那什么叫在 `Z` 的后面呢？我举个例子。刚才的 `ZRANGE` 是排序对吧，那我加上 reverse 就是 `Z` 后面加上 `rev`，`ZREVRANGE`，那么它就是一个降序了；再比如 `ZRANK`，这里默认是升序的，如果加上 rev，也就是 `ZREVRANK`，那么它就是一个降序了。

这里因为篇幅关系我并没有把它们都罗列出来，我们可以回到控制台通过 `help` 看一下。这个 SortedSet 在这里面有很多很多命令，我们罗列的只是其中的一小部分。比如说你看这个 `ZREVRANK`，它这个地方就是判断这个 index，也就是你的那个排名顺序嘛、角标啊。那么 `WITHSCORES` 呢，在排在这个得分排序的情况下，from high to low，从高到低，是不是降序的。OK，这就是 `rev` 的一个意思啊。

基本上呢，大部分有排名有关的命令都支持这个 `rev`。

### 排行榜案例：七个人的成绩

下面我们通过一个案例来演示这里边的这些命令。我这个案例里面基本上包含了几乎所有命令的使用。

首先我们需要将一些学生的得分存入 SortedSet 当中——这里边有一堆的学生，每个学生后面跟着的是他的分数。那这个时候你要把他们批量加进去，等一会是不是用 add 命令啊。

```text
ZADD stu 85 jack 89 lucy 82 rose 95 tom 78 jerry 92 amy 76 miles
```

注意添加的时候，我们在这个地方先指定一个 key，比如说叫 `stu`，s t u s 代表学生。后面 `score` 是分数，`member` 是元素，也就是说**它是分数在前、元素在后**，并且后面可以添多组，是一个链、是一个点点省略的，所以我们可以一起添加、批量添加下来。总共有七个。

打开桌面客户端刷新一下，大家看这个 `stu` 是不是已经进来了。并且大家有没有发现，这个图形化界面客户端默认展示出来的数据啊，就是一个升序的，你看 76、78、82、85、89——也就是说我们刚才讲的吧，它其实会自动给你做排序啊。我们插入的是乱的，它排，它取出来的是排好序的。

下面我们一个一个来做这些功能。

**删除 tom。** 删除 tom 这里要用 remove 命令了，先指定 `key`，再 `member`。这里的 k 就是集合名称，member 就是这个元素本身。

```text
ZREM stu tom
```

再打开桌面客户端一看，原来是七个，tom 在最后嘛，没了，他就成功了吧。

**获取 rose 同学的排名。** 这个就跟排名有关了。那我们知道在分数里面一般排名是从高到低排，虽然这里没说啊，但是这是学校排名的一个一般的默认的排序方式吧，所以说我们就默认是降序了。我们获取排名用的是一个叫 `rank`，但是又因为是倒序啊，我们要加上那个 `rev`。我们把这两个命令都试一下啊：

```text
ZRANK stu rose       # (integer) 2
ZREVRANK stu rose    # (integer) 3
```

第一个它返回了一个 2。那为什么返回二呢？我们打开我们的图形化界面，那这里默认就是升序，在这个升序的列表当中，我们可以看到 rose 是不是在第 3 号啊。但是呢它返回的这个排名啊，是从零开始的 0、1、2，所以说是不是就返回了二了。

那如果是降序呢？是不是应该从这边开始 0、1、2、3。我们来试一下 `ZREVRANK stu rose`，那么这一次得到的是不是 3 啊？那就证明我们刚才说的是正确的。

> **结论**：获取排名的方式就是这样。如果说你的功能真的涉及排名，你一定要在获取排名之后加个一，别让它从零开始，因为他们习惯是从一开始。这样才是正确的排名。

**查询 80 分以下总共有几个学生。** 这个其实就是在查在一定范围内的元素的个数了。那这不就是 card 吗？card 是获取所有元素个数对吧。那我现在先用 card 试一下：

```text
ZCARD stu            # (integer) 6
```

而 count 就是统计在一定范围内了，你看最小值最大值在一定范围内的。我们现在什么范围？80 分以下，所以说呢我们就可以通过 count，key 呢是 `stu`，最小值 0，最大值 80。因为不可能有零分以下的分数嘛。

```text
ZCOUNT stu 0 80      # (integer) 2
```

统计出来两个人。那通过图形界面客户端看一下，80 分以下不是两个人吗？76、78，`miles` 和 `jerry`，对不对，说明这个 count 是正确的啊。你想统计 90 分以上的，那你是不是就 90 往上就行了，大于 90，如果你满分 100 就小于 100 就可以了。

**给 amy 同学加两分。** 加分的话呢，我们这里其实等于是一个自增操作吗，`INCRBY` 是不是啊。对了我们用它就行了。

```text
ZINCRBY stu 2 amy     # 92 → 94
```

后面跟 key `stu`，带跟要增多少哦，加两分，增 2，member 给谁加，给 amy 加。那么变成了 94，因为它原来是 92 分呢。你看这个是不是就变成了增分的一个功能了。当然你减分也行，你只要把 2 改成负的不就减分了啊，这是修改分数。

**查出成绩在前三名的所有同学。** 也就是找出班级里的前三名呗，发个奖什么的。那这个查的就不是数量、不是统计数量了，而是具体的元素，所以要用 range 了。那 range 它就是按照 score 排序以后，这个 min、max 是它的角标范围啊，0、1、2、3。

但是呢你要注意的是，这个 range 默认是升序。我们要查出前三名是不是应该倒序过来的，所以呢我们要用 reverse range。我们把两个都用一下试一下：

```text
ZRANGE stu 0 2        # 后三名：miles、jerry、rose
ZREVRANGE stu 0 2     # 前三名：amy、lucy、jack
```

你看的是 miles、jerry 和 rose，我们打开图形化界面，是不是 miles、jerry 和 rose，后三名啊。那前三名的话呢就要倒过来，最小值加上 `ZREVRANGE`，那么这个呢就是倒序了：amy 第一名，lucy 第二名，jack 第三名吧。哎，这就是获取按照什么排名的这个顺序来获取了。

**查出成绩 80 分以下的所有同学。** 你注意了，count 是查 80 分以下的数量、统计数量，而要查同学，那是不是要统计出具体的人了？那么这个时候就只能用 range，因为 range 是查元素的，card 是查数量的。那 range 这里不是按排名了，是按分数，所以就是 range by score：

```text
ZRANGEBYSCORE stu 0 80    # miles、jerry
```

80 分以下啊，那我们就用 0~80 呗。来控制台，`ZRANGEBYSCORE` 后面加 key 的话呢就是 `stu`，值从 0 到 80。所以你可以对比一下他跟我们刚才那个 count 相比，唯一的区别——你看都是 0~80，区别就是这里是 count，这里是不是用 range by score。返回的是 miles 和 jerry，80 分以下两个人啊。回到界面打开验证一下，是这两个人吧。

到这儿了，我们就把这里所有的功能演示了一遍了，基本上这个命令是不是全部都用到了，它就可以非常方便地实现这样的数据统计。

### Java 客户端怎么选

经过前面两章的学习，我们已经基本了解了 Redis 常见的五种数据结构，以及每种结构它的常见命令和基本的用法。不过呀，最终我们实现一些业务，肯定还要用代码的方式来实现。而 Redis 的官网啊，给我们提供了各种编程语言的客户端供我们去使用。

作为 Java 程序员，我们将来关注的肯定是它的 Java 语言的客户端。这个呢是它的客户端网站，我已经提前打开了。大家可以看到这里有很多的语言。你看在这里呢它有一个说明啊，他说是我们推荐你使用的客户端啊，都会标记一个新，也就是说每一种不同的语言，它都会有一个标记带有新的，是他比较推荐你去使用的。那我们就点入 Java 客户端来看一下，大家可以看到在 Java 客户端里面的排名的前三个的都带有新，都是推荐你使用的。而这个小点呢，表明这个客户端最近也都持续的在去做更新。

那么我们到底该使用这三个中的哪一个呢？

#### Jedis：命令名即方法名

第一个我们叫 Jedis，其实呢就是 Java Redis 的一个组成单词。那这个客户端最大的特点是什么呢？就是它里面的方法都是以 Redis 的命令作为方法名称的。比方说我们 Redis 命令里有一个命令叫 `SET`，那它里面对应的就有一个方法叫 `set`；你有一个 get，它就有一个方法叫 get；你有一个叫 mset，它就有一个方法叫 mset。

所以说呢，以命令作为方法名称，我们的学习成本就比较低，基本上命令你知道了，方法你也会了，你就会操作了。简单实用，这是它最大的优势。正因为此呢，Jedis 在刚刚推出就得到了很多广泛的使用啊，可以认为在最开始啊，是使用最多的一种客户端了，包括现在也依然有很多公司在使用。

但是它有一个小小的弊端啊，那就是 Jedis 实例是线程不安全的。也就是说你创建一个 Jedis 的实例，多线程并发运行的时候啊，是有线程安全问题的。所以呢在多线程使用时，必须为每一个线程创建独立的连接，那么就必须得使用连接池的方式来去使用了。

#### Lettuce：基于 Netty 的响应式客户端

那么第二个客户端呢叫 Lettuce。它的一个特征是什么呢？就是它底层的一个实现啊，跟其他的不一样，它是基于 Netty 来实现的。我们知道 Netty 是一个高性能的网络编程框架，那么它底层的支持这种同步啊或者是异步的这种连接，并且这是这种响应式编程的一种方式，这也是现在比较流行的、在 Spring 里边啊也特别推荐大家使用的一种方式。

而且呢它是线程安全的，并且啊它对于 Redis 的哨兵模式、集群模式啊都有非常好的支持。所以呢这种模式呢，它最大的特点啊可以说是跟 Spring 的现在这种编程模式结合的是比较好。而且这种响应式编程、异步编程它的吞吐能力也比较高一点，因此在 Spring 官方啊，默认其实兼容的就是这个 Lettuce 客户端。

#### Redisson：把单机工具搬进分布式

那么最后一种呢叫 Redisson。这客户端的特点啊，不在于对 Redis 的基本操作，而是在于它底层是基于 Redis 实现了一系列的一些工具。什么样的工具呢？分布式的、可伸缩的 Java 工具。

你比如说我们 Java 里是不是有 map 啊、集合吗？我们 Java 里是不是有队列啊，还有锁，还有一些信号量啊，还有一些原子整形等等这样的一些基本类。这类呢可以保证我们什么呢？平常使用的时候做数据存储也好，做一些线程控制也好，是不是非常方便。

但是呢这些东西它们有一个特点，就是它们是**单机的**。如果是在分布式环境下，它们往往就失去作用了。而我们的 Redisson 呢，就是基于 Redis 重新实现了这一系列的东西，以至于它们可以在分布式环境下，同样能够使用。那因此呢如果说啊，你在分布式环境下使用这些功能有这样的需求啊，那你就可以不用自己造轮子了，而是直接使用 Redisson。

| 客户端 | 最大特点 | 什么时候会选它 |
| --- | --- | --- |
| **Jedis** | 方法名就是 Redis 命令名（`set` → `set`），学习成本低 | 常规业务逻辑，简单直接，至今仍有很多公司在用。但它实例线程不安全，多线程必须配连接池 |
| **Lettuce** | 基于 Netty，同步/异步、响应式编程 | 与 Spring 现在的编程模型结合得好、吞吐高，Spring 官方默认兼容的客户端 |
| **Redisson** | 基于 Redis 重写了一批分布式的 Java 工具（Map、队列、锁、信号量、原子整形……） | 需要在分布式环境下使用这些能力时，不用自己造轮子 |

一般作为普通的使用 Redis 来实现一些业务逻辑，那用 Jedis 或者 Lettuce，这两种会相对方便一点。那我们这两种是不是都应该掌握呀？没错啊。

不过呀，我们并不会让大家一个一个的去学习这三种，因为啊我们 Spring 最擅长的事情就是什么呀？整合。那后面呢我们会学习这个 Spring Data Redis，它可以啊、底层可以兼容 Jedis 和 Lettuce，也就是说他定义了一套 API，这套 API 底层既可以用 Jedis 实现，也可以用 Lettuce 实现。那么这样一来，学习了它，等于这两个是不是就都会了呀。所以我们后期会去学习 Spring Data Redis。

那当然也有很多的企业啊，他并没有尝试用 Spring 这一套 API 啊，他还是喜欢用那种旧的啊、Jedis 那一套啊。刚才说了，因为这一套它的命令跟方法名嘛，学习成本低嘛。所以说呢我们把这里的原生 API 也会讲一下，然后我们再学习 Spring Data Redis。那也就是说我们后续的课程的安排啊，就是两部分啊：Jedis、Spring Data Redis。那至于 Redisson 呢，我们会在后期学习分布式锁的时候，再去给大家介绍一下它的使用方式。

### Jedis 快速入门

Jedis 客户端使用起来非常的简单。这个呢是它的官方网站，官网呢也给出了一个快速入门的 demo。这里我们就先来演示一下这个 demo。

首先呢我们去创建一个 maven 工程，选 Maven，起名字叫 `jedis-demo`，改包名 `com.heima.jedis.demo`，finish。然后呢我们需要做的事情啊，总共有四步啊。

#### 引入依赖与建立连接

第一步呢我们需要引入一个 Jedis 的依赖啊。它的名字是叫 jedis，然后它的 groupId 是 redis.clients，下面是他的版本 3.7.x。这些呢都在官网上能够看到的。大家也不需要自己去手敲，你看在下边它这里使用说明上是不是就有这个依赖。第二步呢我们最好引一个单元测试，因为等一会呢我们要基于单元测试去测一下刚才的一些方法，我们用 JUnit 啊，artifactId 是 junit-jupiter。

```xml
<dependencies>
    <dependency>
        <groupId>redis.clients</groupId>
        <artifactId>jedis</artifactId>
        <version>3.7.0</version>
    </dependency>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.10.0</version>
        <scope>test</scope>
    </dependency>

```

引完依赖以后呢，第二步是要去建立一个连接。所谓的建立连接呢其实就是 `new` 这个 Jedis，然后在 new Jedis 对象的过程当中，这里指定了一个 ip 地址，这是我的虚拟机 ip 啊。那如果你 ip 跟我不一样，这里应该改成你自己的 Redis 的 ip 地址，后边当然是端口号了。那么这样呢其实就有点像什么呀，有点像我们那个 `redis-cli -h` 和 `-p` 对吧。

那么这两个指定以后只是建立连接，还没有密码，所以还要利用 `auth` 设置这个密码，那这样你才有了访问它的权利。然后呢我们还可以利用 `select` 选择一个库，如果你不选择的话，默认其实也是 0 号库，总共有 16 个库嘛，你自己选好。

我们这里呢用了一个 `@BeforeAll`，这是我们单元测试的一种语法，提前先把这个对象给它 new 出来。

```java
package com.heima.jedis;

import org.junit.jupiter.api.AfterAll;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.Test;
import redis.clients.jedis.Jedis;

public class JedisTest {

    private static Jedis jedis;

    @BeforeAll
    static void setUp() {
        // 第二步：建立连接
        jedis = new Jedis("192.168.150.101", 6379);
        jedis.auth("123321");
        jedis.select(0);
    }
}
```

#### String 与 Hash 的读写

连接建立了以后呢，第三步我们就可以操作它了。我们用 String 先来操作一下吧——String 我们讲过存叫什么命令？`set`，取 `get`。你看这里跟 set 有关的命令我们都讲过的，`setex`、`setnx` 啊，这是不是我们以前都学过的这些命令，这都可以用啊。

方法名就是命令名，这是 Jedis 最大的特点。你看我要执行一个 set 的时候，那我就接着点 set，然后给 key 给 value，这就像我们在命令行里输入 `SET name 杰克` 一样的。那我取的时候就是 `get`。那么 set 的时候呢和 get 的时候，我们这里其实都可以得到一个结果，就像我们在控制台执行 set 啊、name 啊、杰克，我们就能得到一个结果，OK 告诉你是不是成功了对吧；那你 get name 的时候得到的是什么？是不是就是杰克本身。

```java
@Test
void testString() {
    String result = jedis.set("name", "杰克");
    System.out.println("set 结果：" + result);

    String value = jedis.get("name");
    System.out.println("get 结果：" + value);
}
```

那同学们我们大家想想看，如果现在操作的是哈希呢？哈希类型呢，那是不是类似呀？

所以大家看 `hset` 的时候，你可以传一个 key 啊，然后可以传字段、字段值——字段名、字段值这传一个啊。那如果你有多个，是不是还可以 `hmset` 呀？那 `hmset` 的时候传一个 k，然后传一堆的这个 field 和 value，那他这里让你用一个 map 啊，那 map 里是不是可以传一堆的 key、value，都是可以的。

```java
@Test
void testHash() {
    // 存：先来个简单的 hset，一个 key 塞两个字段
    jedis.hset("user1", "name", "杰克");
    jedis.hset("user1", "age", "21");

    // 取：hget 是一个字段一个字段取；hgetall 一次性把整个 map 取出来
    Map<String, String> all = jedis.hgetAll("user1");
    System.out.println(all);   // {age=21, name=杰克}
}
```

这里他要求填字符串，那咱们就用字符串。执行完大家可以看到最终是不是取到了这个内容——杰克、21。我们在客户端界面里来看一眼，在这刷新，好，这里 user1 确实是存进去了，没问题吧。

好，这就是 Jedis 的一个使用了，其他的命令我就不一一演示了。因为你想嘛，它所有操作都是基于这个命令名称嘛，所以方法名就是命令名，你还有什么好说的呀？你就直接看命令就行了嘛。

#### 释放资源

那成功了以后呢，最后我们还要释放资源。释放资源其实就是 `close` 关闭吗，当然这里做了健壮性的判断。

```java
@AfterAll
static void tearDown() {
    if (jedis != null) {
        jedis.close();
    }
}
```

为什么做判断呢？因为如果在这里已经抛异常了，直接走到这的话，如果你直接关，是不是有可能有空指针的风险？

总共四步啊，我们一起回顾一下：

1. 第一步是引入一个 Jedis 的依赖；
2. 第二步建立一个连接，指定 ip、端口、密码啊，然后去选择一个库；
3. 第三步使用这个 Jedis 去操作，方法名就是命令名；
4. 第四步呢释放资源——这个千万不能忘了好吧。

### Jedis 连接池

上一节课呢，我们已经学习了 Jedis 的一个基本用法了。但是呢我们也提到过 Jedis 呀，它本身是线程不安全的。如果说在多线程的环境下，并发的去访问、大家都来去使用这类 Jedis 的话，是有可能出现线程安全问题的。因此呢在并发的环境下，一定要给每一个线程创建独立的这个对象。

那此时呢，最好的方案是使用连接池。因为啊，频繁的创建和销毁 Jedis 对象，是有很大的一个性能损耗的啊。那这里的官方啊也基于 Apache Commons Pool 来实现了 Jedis 连接池，所以呢下面呢我们就来介绍一下这里的连接池用法。

连接池的使用本身并不复杂。我们定义一个工具类，叫 `JedisConnectionFactory`。在这个工具类里面呢，首先有一个静态的成员变量叫 `JedisPool`，也就是 Jedis 的连接池。而这个 pool 的对象呢，我们是通过**静态代码块**来给它初始化的。

```java
package com.heima.jedis.util;

import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPool;
import redis.clients.jedis.JedisPoolConfig;

import java.time.Duration;

public class JedisConnectionFactory {

    private static final JedisPool JPL;

    static {
        // 先配置连接池
        JedisPoolConfig poolConfig = new JedisPoolConfig();
        poolConfig.setMaxTotal(8);
        poolConfig.setMaxIdle(8);
        poolConfig.setMinIdle(0);
        poolConfig.setMaxWait(Duration.ofMillis(1000));

        // 再创建连接池对象，池配置 + 连接参数
        JPL = new JedisPool(poolConfig, "192.168.150.101", 6379, 1000, "123321");
    }

    public static Jedis getJedis() {
        return JPL.getResource();
    }
}
```

这里呢先把这个 config 对象传进来，config 是做池的配置的，然后呢是 ip、端口啊、一个超时时间还有一个密码。那么等于是 pool 这个构造函数里传的是连接的一些参数；而我们前边的这个 config 存在啊，是池的一些参数——一个连接池无非就是配置最大连接、最大空闲连接、最小空闲连接等等信息嘛。所以说呢我们把池配好，然后把连接参数配好，那么连接池不就创建出来了吗？

最后呢我们还提供了一个静态方法，方便我们去获取 Jedis 的对象，其实就是从这个 pool 里面去 `get`。那这样一来呢，任何的人只要调用这个工具类的 `getJedis` 方法，就能拿到 Jedis 对象，每次都是从池子里去获取，用完了呀也会还回去，这样就可以避免频繁的创建和销毁这些对象了。

```text
   线程 A ─┐
   线程 B ─┼─►  JedisConnectionFactory.getJedis()
   线程 C ─┘                 │
                            ▼
                     +--------------+
                     |   JedisPool  |   静态成员，JVM 里就一个
                     +--------------+
                            │
             getResource() │ 借出
                            ▼
                     业务里用 jedis
                            │
                   jedis.close()
                            │
           returnResource() │ 归还（注意：不是销毁）
                            ▼
                     +--------------+
                     |   JedisPool  |   连接又回到了池子里
                     +--------------+
```

连接池里可以配置的参数还是比较多的，比较常见的有这么几个：

| 参数 | 含义 | 这里给的值 |
| --- | --- | --- |
| `maxTotal` | 最大连接数，池里最多允许创建这么多个连接，再多就不行了 | 8 |
| `maxIdle` | 最大空闲连接。即便没有人来访问，池子里最多也可以预备这么多个连接；一旦有人来了我就可以直接用，不用再临时去创建 | 8 |
| `minIdle` | 最小空闲连接。超过一段时间如果一直没有人访问，这些空闲连接就会被释放，直到达到这个数为止。当然你也可以把它调大一点，常备一些连接 | 0 |
| `maxWait` | 连接池里没有连接可用的时候，我们最多等多长时间。默认值是 -1，也就是没有连接时无限制等待，一直等到有新的空闲连接为止 | 1000ms，超时就报错 |

好，这样呢就把池子配好了，连接池也创建出来了。最后呢就是提供一个静态方法了，和刚才类似一样啊，叫 `getJedis`，那么当有人调的时候呢，我们就调 `JedisPool.getResource()`。

现在呢我们回到刚才的单元测试啊，在这个单元测试里边呢，之前我们是通过 new 的方式，现在还需要 new 吗？唉，不需要了吧。

```java
@BeforeAll
static void setUp() {
    // jedis = new Jedis("192.168.150.101", 6379);
    // jedis.auth("123321");
    // jedis.select(0);

    jedis = JedisConnectionFactory.getJedis();
}
```

那么最后呢释放资源呢这个动作啊，我们虽然还是 `close`，但是大家进去看，当它判断你有连接池的时候啊，它其实底层就不会真的 close 了，而是归还，`returnResource` 就归还。所以说了，等于把连接还回去啊，连接还到连接池里了，而不是把它销毁了啊。这样呢我们就实现了 Jedis 的一个使用了。我们可以再测一下——好，你可以看到依然是绿的，没有问题吧。

## RedisTemplate 精读：Spring Data Redis 的封装、序列化与取舍
> 对应块：BLK05 | 覆盖分集：P19-P23 | 块标题（分集名）：《基础篇-18.Redis的Java客户端-认识S》

前面我们学过了第一种 Java 客户端 Jedis——方法名就是命令名，`set` 对应 `SET`，`get` 对应 `GET`，一一对应，写起来很爽。今天来看第二种 Java 客户端：Spring Data Redis。

它比 Jedis 抽象了一层，也顺手替我们解决了一个 Jedis 解决不了的问题：**往 Redis 里存 Java 对象**。这一个知识点，会在后面引出这一讲最值得掰开揉碎的部分——序列化器的选择，以及两种方案背后的取舍。

### Spring Data Redis 是怎么来的

先看它的前缀：`spring-data`。`data` 是 Spring 里专门做数据操作的模块。你以前有没有接触过？在 Spring 官网的 Spring Data 模块下，会看到非常多各种各样的操作：

- JDBC、JPA
- MongoDB、Cassandra
- Solr、Elasticsearch、Neo4j 等等

这些全是常见的数据库操作，全都属于 Spring Data 这一个模块。Spring Data Redis 就是其中之一，它里面封装的东西，自然就是对 Redis 的各种操作。

版本方面，目前最新的应该是 2.6，发布日期是 2021 年 11 月 12 号，官方支持到 2022 年 11 月 12 号，也就是一年左右的时间，所以这个版本能放心用很长时间。不过企业里用的往往不会这么新，一般会落后一点，比如 2.3、2.4 等等，但整体使用上的差异并不是很大。

> **提示**：新版本不等于生产版本。企业卡在 2.3、2.4 上是常态，别为了追新而追新。

### 它替我们做了什么

回到这张幻灯片，先说它的几个特征。

#### 整合，而不是造轮子

Spring 从来不重复造轮子，它做的都是**整合**。

> **易错点**：注意哦，是整合，不是抄袭。把别人的东西拿过来再封装——这在 Spring 那儿叫整合，不叫抄袭。

Spring Data Redis 的底层整合了 **Lettuce** 和 **Jedis** 这两个客户端，之前咱们都提过。而且要整合就应该提供一套统一的标准，所以 Spring 提供了一个 `RedisTemplate` 这样的类。这跟我们以前学的 JDBC 是一模一样的思路：Spring 提供了 `JdbcTemplate` 来封装对数据库的各种操作，那 `RedisTemplate` 就是封装了对 Redis 的各种操作的 API。

底层的实现由 Lettuce 和 Jedis 来完成，两者都可以。

```text
        你的 Service 代码
               │
               ▼
    ┌────────────────────────┐
    │     RedisTemplate      │  统一 API，按数据结构分组
    └────────────────────────┘
        │                 │
        ▼                 ▼
   Lettuce 驱动       Jedis 驱动        （二选一，默认 Lettuce）
        └────────┬────────┘
                 ▼
       commons-pool2 连接池
                 ▼
            Redis 服务端
```

#### 在封装之上做的额外支持

它不光是转发，还额外做了很多东西的支持：

- 对发布订阅模型的支持
- 对哨兵的支持
- 对集群的支持
- 基于 Lettuce 实现的**响应式编程**支持——如果你要结合 Spring Web Flux 做响应式编程，用它再好不过了

#### 序列化与反序列化支持

这个是什么意思？我们回顾一下上一节课讲的 Jedis 代码，在 JS（Java）里我们去做 `set` 的时候，看一下它参数的类型，key 和 value 大家看都是什么呀？

字符串类型，要么是字节数组。我们讲过，Redis 的底层的编码都是字节数组，无非就是编码的格式不一样。所以它要么是字符串，要么是字节。

那如果我现在有一个 Java 对象需要存呢？它这里显然存不进去，对不对？

Jedis 也是如此——你看它的参数全是字符串。所以如果你要存的是一个复杂的 Java 对象，**你就必须手动对它做序列化，变成字符串或者变成字节**。

而 Spring Data Redis 天生内部就支持基于 JDK、或者 Jackson、或者字符串、或者其他对象对它做这种序列化——也就是把这些东西变成字节或字符串，然后写进 Redis 里。它还能支持**反序列化**，也就是把 Redis 里读到的这些字节再变成我们 Java 里面的一些对象或者字符串。

> **定义**：**序列化** = Java 对象 → 字节（写进去）；**反序列化** = Redis 里的字节 → Java 对象（读出来）。

有了这样一个支持，我们去做数据存取的时候就非常方便。

#### 基于 Redis 的 Redis Collection

它还支持基于 Redis 的 Redis Collection——所谓的 Redis Collection，其实就是我们 JDK 里面的各种各样的集合，只不过我们基于 Redis 重新实现了一下这些集合，比如队列啊、链表啊等等。

为什么要重新实现呢？因为基于 Redis 的这种实现是**分布式的、跨系统**的。所以 Spring Data Redis 里也对这些做了重新的实现。

### opsForXxx：把几百个命令拆成五组

现在来看具体怎么用。核心就是 `RedisTemplate`，里面封装了一系列 API。这个 API 的封装是有规律的——它不像 Jedis 那样，方法名就是命令名称。

Jedis 里面 Redis 有上百个数百个命令，那里边就封装了上百个不同的方法供你使用，所以说学习成本相对较低，**但是这个类就显得比较臃肿了**，里面东西特别多。

Redis 官方对我们的命令其实是做了分组的：有通用的命令，有专门操作字符串的、专门操作哈希的、专门操作 List 的、专门操作 Set 的命令。我们的 `RedisTemplate` 也做了这件事。

它的内部提供了一系列 API，这些 API 的名字都是 `opsFor` 开头的，返回值都是对应的 **Operation 对象**：

| 调用 | 拿到的对象 | 对应的数据结构 |
| --- | --- | --- |
| `opsForValue()` | `ValueOperations` | 字符串 |
| `opsForHash()` | `HashOperations` | 哈希 |
| `opsForList()` | `ListOperations` | List |
| `opsForSet()` | `SetOperations` | Set |
| `opsForZSet()` | `ZSetOperations` | Sorted Set |

比如我调了 `redisTemplate.opsForValue()`，就能拿到一个 `ValueOperations` 对象；我调了 `opsForHash()`，拿到的就是 `HashOperations` 对象。而 `ValueOperations` 里面封装的，就是对于字符串的各种操作；`HashOperations` 里封装的，就是对哈希类型的各种操作。

也就是说，它利用这种**对象封装**的形式，把不同数据类型的方法封装到了不同对象里面。将来我们操作的时候各司其职，就显得没有那么臃肿了——这就是 `RedisTemplate` 里面的设计思想。

至于 `RedisTemplate` 这个类本身，里面封装的是一些通用的、或者说一些比较特殊的命令，就直接利用它去调用好了。

### 快速入门：三步跑通

接下来动手实践，基于 Spring Boot 来使用——因为 Spring Boot 已经默认整合了 Spring Data Redis，并且做了自动装配，我们用起来会极其方便。

#### 第一步：引入依赖

项目直接基于 Spring Initializr 创建一个 Spring Boot 项目，起名 `redis-demo`（或者 `spring-data-redis-demo` 也行）。版本这里他给的是最新的 2.6，我选个 2.5。依赖勾选一下 Lombok，还有 Spring Data Redis。

Finish 之后打开 pom 文件，你会发现它已经自动把 `spring-boot-starter-data-redis` 引入了——它其实就是 Spring Data Redis 跟 Spring Boot 的一个整合包。这里边有一些多余的东西，比如 Maven 的配置、`.gitignore` 等等，不需要的话可以直接删掉，看起来会比较清爽一点。

项目搭建就完成了：`main` 函数已经帮你创建好了，单元测试也已经创建好了，properties 文件也有。用不习惯的话可以改成 `.yml` 或 `.yaml` 都行。

回到幻灯片，正式的第一步是引入依赖，一共要引两个：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-pool2</artifactId>
</dependency>
```

第一个是 Spring Boot 对 Redis 的整合；第二个是连接池 `commons-pool2`，因为不管是 Jedis 也好，还是我们的 Lettuce 也好，底层都会基于它来实现连接池效果。

#### 第二步：配置连接信息

Spring Boot 自动装配的好处就是我们不用去写编码了。上节课我们 Jedis 的那个连接池代码其实还是有些复杂的，但是现在你根本不用管了。你要做的事情，就是打开你的配置文件，在里面写上这么一段信息就行了：

```yaml
spring:
  redis:
    host: 192.168.150.101
    port: 6379
    password: 123321
    database: 0
    lettuce:
      pool:
        max-active: 8
        max-idle: 8
        min-idle: 0
        max-wait: 1000ms
```

你看，IP 地址、端口号、密码，下面就是连接池的信息，是不是非常简单。

> **提示**：记不住配置项也没关系，在配置文件里输入 `spring.redis`，所有的提示就都有了，照着写就行。

这里有两件事必须点一下。

第一，地址不记得了不要紧，`host`、`port`、`password`、`database` 都是上面那样。`database` 大家看默认就是 0 号库。

第二，也是个**易错点**——紧接着呢还有 Redis 的连接池配置。这个连接池配置里**有两套**：一套是 Jedis 连接池，一套是 Lettuce 连接池。其实这里就是在选择：你到底用的是哪一种实现，用 Jedis 还是用 Lettuce。如果你要选择 Jedis 的实现，**还需要在 pom 文件里额外引入 Jedis 的相关依赖**，因为 Spring 默认使用的是 Lettuce。

我们来看一下 Maven 里的 dependencies，这个 `spring-boot-starter-data-redis` 里面默认引入的就是 Lettuce 客户端，所以默认是它。如果你想用 Jedis，得单独自己去引入相关依赖。

好，所以这个地方我们选择 `lettuce`。

```yaml
    lettuce:
      pool:
        max-active: 8
        max-idle: 8
        min-idle: 0
        max-wait: 1000ms
```

`max-active` 是最大连接数，这里是 8；`max-idle` 是最大空闲连接；`min-idle` 是最小空闲连接；还有一个 `max-wait` 等待时长，比如 1000ms，它其实就是一个等待时间。

> **易错点**：同学们你注意了，**你一定要手动配置 `lettuce.pool`，连接池配置才会生效**，否则它是不会生效的。别写完代码发现还是默认连接池，然后跑来问是不是 Lettuce 的问题。

#### 第三步：注入并写测试

依赖引入了、配置配好了，就可以放心大胆地写代码了。直接 `@Autowired` 注入就行——自动装配嘛，那肯定这些类都不用我们创建了，拿来就用。

我们之前讲过，它里面有不同的操作，`opsForValue()` 拿的就是 String 类型的操作。那 String 里面是不是要做 `set` 操作呀？你看 `set(key, value)`；String 里面是不是有 `get` 操作呀？`get(key)` 得到的就是 value。是不是很舒服。

```java
@SpringBootTest
class RedisTemplateTest {

    @Autowired
    private RedisTemplate<String, Object> template;

    @Test
    void testString() {
        // 写入一条指定数据
        template.opsForValue().set("name", "胡歌");

        // 获取数据
        String name = (String) template.opsForValue().get("name");
        System.out.println(name);
    }
}
```

> **提示**：这里的 key 和 value **并没有要求你传字符串**——你传字符串也好，传 Object 也好，它都可以接受。因为我们讲过，它底层有一个自动的序列化机制帮你去处理这个事情。这一点还是非常强大的。

运行一下，绿了，那就证明我们这个插入已经成功了。

所以整个流程就四步：**引入依赖 → 编写配置 → 注入 RedisTemplate → 写测试**。在使用时需要注意的就是，它里面包含了五种不同的操作，分到了五个不同的对象里面，你调用对应的 API 或者对应的对象来执行对应的操作就 OK 了。

### 序列化之谜：明明存的是"胡歌"，怎么读出"杰克"

好，现在到这节课最精彩的部分。

上一节课我们往 Redis 里写入了一个 `name`，值是"胡歌"。这节课我打开图形界面客户端，连接进来，`GET name`——怎么是"杰克"呢？

我不信，我再 set 一次，我改成 rose，再来看一下，是 rose 吧。我现在给他覆盖一下，走。我们再来 get 一下，而取出来的却是 rose。

这不大变活人了吗？到底发生了什么？

我们通过 `keys *` 来看一下。大家会发现，我这里边有一个叫 `name` 的 key，对不对？但是你往下翻，还有一个"这样的" key——看到这个 key 最后有个内容了吗？我来 get 一下，得到了这么一串东西。看不懂吧？那我告诉你，这就是"胡歌"。

哦，他被**剁碎了**。

#### 跟着断点走一遍

为什么呢？这就要说到序列化。我们的 `RedisTemplate` 的 `set` 方法接收的参数**并不是字符串，而是 Object**。这个是之前给大家讲过的，Spring Data Redis 的一个特殊功能，它可以接收任何类型的对象，然后帮我们把它转成 Redis 可以处理的字节。

在进入 `set` 方法之前，你传进来的值就已经被"装饰"成字节了。我们跟着断点 debug 走一遍：

```text
   template.opsForValue().set("name", "胡歌")
            │
            ▼
   RedisTemplate.set()          参数是 Object，不是 String
            │  key 与 value 双双都要过序列化
            ▼
   valueSerializer.serialize()  取的就是值序列化器（默认为 JDK 的）
            │
            ▼
   JdkSerializationRedisSerializer.serialize()
            │
            ▼
   SerializationUtils → JDK 序列化
     └─ new ByteArrayOutputStream()   缓冲
     └─ new ObjectOutputStream(buf)
     └─ oos.writeObject(obj)           把 Java 对象转成字节
            │
            ▼
      byte[]  ──────►  写进 Redis 的就是这坨字节
```

可以看到，`RedisTemplate` 里获取 `valueSerializer` 这个值序列化器，然后进入 JDK 的序列化；JDK 的底层序列化用的是 `ObjectOutputStream`，外面套一层 `ByteArrayOutputStream` 当缓冲；这个流的作用就是把 Java 对象转成字节，转成字节以后再写入 Redis。

#### 那四个序列化器

那么有人说你怎么知道的？大家来看，点到 `RedisTemplate` 里，它有四个东西：

| 序列化器 | 管的是谁 |
| --- | --- |
| `keySerializer` | key 的序列化器 |
| `valueSerializer` | value 的序列化器 |
| `hashKeySerializer` | 哈希结构里面的字段名 |
| `hashValueSerializer` | 哈希结构里面的字段值 |

我们利用 `RedisTemplate` 存入的一切数据，最终都会利用这四个东西，取决于你的数据结构。如果你是普通字符串，用前俩就行了。

而这两个东西现在都是 null，谁给它们做初始化呢？在这个地方，它会给它创建一个默认的序列化器，而默认序列化器就是 **JDK 的序列化器**。在你没有给这几个值进行定义的情况下，它就会走这个默认的 JDK 序列化器。

> **结论**：所以 JDK 序列化器会把你的 **key** 和 **value** 一起序列化成字节。key 也被序列化，这才是"明明写了 name 却找不到 name"的真正原因。

#### JDK 序列化的两大罪状

这种方式有什么问题吗？有问题，而且是两个很要命的问题。

**第一，可读性差。** 如果我不说，这都剁碎了，谁认得出来。而且还会出现一些 bug——我们明明 `set name`，我以为我把 `name` 改了，结果 `name` 没改，我是 set 了一个新的东西进去了。就是因为你的 key 也被序列化了。

**第二，内存占用较大。** 我明明就是一个 name，结果你给我弄这么长，占用的空间实在是太大了。

所以我们希望的是：**我写的是什么，你就存什么，所见即所得**，多好。

### 改掉序列化器：key 用 String，value 用 Jackson

那怎么才能做到这一点呢？，我们就必须去改变 `RedisTemplate` 的序列化方式了。也就是说，我们需要去改变它里面的序列化对象，不要用默认的了。

它有哪些实现呢？

| 序列化器 | 干什么的 | 用在哪 |
| --- | --- | --- |
| `JdkSerializationRedisSerializer` | JDK 默认序列化，内部走 `ObjectOutputStream` | 最不好用的一种，我们不希望用它 |
| `StringRedisSerializer` | 专门用来处理字符串 | key、hashKey |
| `GenericJackson2JsonRedisSerializer` | 把对象转成 JSON 字符串 | value、hashValue |

先看第二个 `StringRedisSerializer`——它是专门用来处理字符串的。因为我们知道，字符串要想转成字节写入 Redis，其实只需要简单地 `getBytes` 就行了，没必要利用 JDK 去序列化吧？所以它做的事情就是 `getBytes`，只不过底层的编码你可以控制，是 UTF-8 还是什么别的。

> **提示**：如果你的 key 和你的哈希 key 都是字符串的情况下，是不是可以用它？一般情况下我们的 key 是字符串，只有值可能是对象，所以 key 一般就用它。

那我们的 value 呢？如果 value 有可能是对象，那么建议你使用 `GenericJackson2JsonRedisSerializer`，也就是转 JSON 字符串的这样一种序列化工具。

所以也就是说：**我们的 key 一般用字符串类型，我们的值一般用这种 JSON 序列化类型。**

#### 写一个 RedisConfig

`RedisTemplate` 是允许你修改它的，所以只要把它改了不就行了吗。

这里我定义了一个 Bean 叫 `redisTemplate`，泛型是 `<String, Object>`——也就是我们默认了永远我的 key 是 String，只是 value 是 Object。先把它 new 出来，`RedisTemplate` 需要连接工厂，所以连接工厂先注入进来，然后再塞进去，然后就可以开始设置序列化工具了。

```java
@Configuration
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory connectionFactory) {
        RedisTemplate<String, Object> tm = new RedisTemplate<>();

        // 连接工厂不需要我们自己创建，Spring Boot 会自动创建，注入进来即可
        tm.setConnectionFactory(connectionFactory);

        // key 与 hashKey 用字符串序列化器
        tm.setKeySerializer(RedisSerializer.string());
        tm.setHashKeySerializer(RedisSerializer.string());

        // value 与 hashValue 用 JSON 序列化器
        tm.setValueSerializer(new GenericJackson2JsonRedisSerializer());
        tm.setHashValueSerializer(new GenericJackson2JsonRedisSerializer());

        return tm;
    }
}
```

这里用的是 `RedisSerializer.string()`——它返回的就是一个以 UTF-8 作为编码的 `StringRedisSerializer` 常量，用它我们就会比较方便一点，不用自己去 new 了。

#### 踩坑：缺少 Jackson 依赖

回到单元测试，我们把注入的地方加个泛型 `<String, Object>`，也就是我的 key 一定是字符串，值呢是 Object，随便。然后存数据、测试代码。

好，这里报了个错。我们看一下，它说这个类没有找到，失败了，缺少一个类。你看它是不是缺少了这个 Jackson 处理的工具类？

这是因为呢，我们要用 JSON 处理，是不是得引入 JSON 处理的依赖啊？

> **提示**：这其实在告诉我们什么呀？**碰到问题的时候，你应该及时根据异常的信息来判断异常产生的原因。** 这个地方就是因为缺少了一个依赖造成的。

那我们就去 pom 文件里引入 Jackson 依赖。

这个 JSON 依赖呢，其实平常开发的时候是不需要自己去引的。因为平常我们开发的时候用了 Spring MVC，而 Spring Boot 会自带这个 Jackson 的依赖，那么它就会自动引入了，不用我们去操心。这个地方呢，因为我们没有引入 Spring MVC，所以这个依赖是需要手动引入的。

引完再跑——绿了。我们打开图形界面的客户端，再看一下，`name` 是不是成功写入了"胡歌"？

> **结论**：`name` 终于是个干干净净的普通字符串了。**所见即所得**，在客户端里能直接看出存的是什么。

### Jackson 的魔法，和它的代价

那么这个时候我们来验证一下，如果我写的一个对象，他能不能帮我们也去做序列化呢？我们来试一下。

我们新建一个类，`pojo` 包下的，就叫 `User`。给 `User` 加两个属性，一个是 `name`，一个是 `Integer` 的 `age`。给它加一个 `@Data` 注解，这样它就有了 get/set 方法，然后给这个类添加构造函数，一个无参构造和一个有参构造。

```java
@Data
public class User {

    private String name;
    private Integer age;

    public User() {
    }

    public User(String name, Integer age) {
        this.name = name;
        this.age = age;
    }
}
```

接下来我们编写单元测试，这次我们保存一个用户对象到 Redis：

```java
@Test
void testSaveUser() {
    template.opsForValue().set("user:100", new User("胡歌", 21));
}

@Test
void testGetUser() {
    // 取出来的是一个 Object，但我们明确知道自己存取的就是一个 User 对象，
    // 所以完全可以在这里来一个强转
    User user = (User) template.opsForValue().get("user:100");
    System.out.println(user);
}
```

运行一下，绿了，可以看到这里成功打印出了用户的信息，说明这个强转是没有问题的。

我们去看图形界面客户端，找到刚才存的那个 `user:100`。我们发现呢，这里面是不是存入了一个 User 对象了，而且是 **JSON 风格的**——没错，它自动化地帮我们把对象转成了 JSON 写入了这一边。

并且最神奇的是，当我们去获取结果的时候，它还能自动地帮我们反序列化成 User 对象了。存的时候存 User 它帮你转 JSON，取的时候它还帮你把 JSON 反序列化成 Java 对象。

#### 它怎么做到反序列化的？

这个时候我们来看一下刚才图形界面里面的内容。事实上在写入 JSON 的同时，它还帮我们写出了这样一个 `class` 的一个属性，那么对应的就是这个 User 类的字节码名称。

这是因为有这样一条属性，所以它在反序列化的时候，才能读取到我们对应的字节码（就是类的名称），然后帮我们把这个 JSON 反序列化为对应的 User。

是不是非常的神奇？

#### 可是这个 class 属性，是要收费的

但是啊，它却存在一个小小的问题。我们在上一节课里写入的那个 `user` 对象，你会发现这个 User 对象不仅仅写了对象本身的属性哦，还**夹带了点私货**——它把这个 User 类的字节码也写进去了。

那么这样一来会带来一个什么问题呢？你看啊，这个字节码本身占用的内存空间，**甚至比我的这个数据本身还要长**。你想想看，每一个对象我都存了这么多额外的多余的信息，与我业务无关的信息。那如果说我有成百上千上万的对象，是不是会多余占用非常多的空间呀？那么在我们的一些大型的项目当中，数百万、上千万的这样一个对象需要去存储，那么这个时候就会浪费太多空间，无法接受。

有人说了：我可不可以不存这个对象进去？不存这个 class 进去，行不行？

为什么呢？因为我们要实现自动的序列化和反序列化，它就必须知道这个东西。序列化的时候还好说，我直接把对象转字符串写就行了；但是**反序列化的时候，它怎么知道你这个 JSON 串要转成哪个类型的对象呢？** 如果你不记录 class，是不是就没有办法知道？那就没有办法实现自动的反序列化。

所以呢，这个东西是实现自动序列化必不可少的。

> **结论**：class 字段是自动反序列化的**前提**，二者绑定：有它，才有便利；没它，就没有便利，但省内存。

那因此如果你想节省内存空间，这个东西还能不能要？

不能要。

那如果不能要，那就不能实现自动的序列化和反序列化了。那为了节省内存空间，我们**并不会使用 JSON 的序列化器来处理 value，而是统一使用字符串序列化器**——也就是我们上节课的那个 key 的处理方案，`RedisSerializer.string()`。

那么那个序列化器呢，它要求什么要求？只能处理字符串，用 `getBytes` 来处理吧。

那因此我们呢，就只能存储 String 类型的 key 和 value 了。也就是说 key 和 value 都是字符串，不能再存 Java 对象了。

那我真的要存 Java 对象的时候怎么办？那你就不得不**手动地来完成序列化和反序列化**了。

### StringRedisTemplate：省掉配置，多写两行代码

看一下这幅图。这是我们的 Redis，现在我有一个 User 的类，它有一个对象需要往 Redis 里存。

```text
      User 对象
          │
          │  MAPPER.writeValueAsString(user)
          │  ← 手动序列化，不再往里夹带 class
          ▼
   JSON 字符串  ──────────────────►  Redis
   （key 也是纯字符串）               │
                                      │  stringTemplate.opsForValue().get("user:200")
                                      ▼
                                JSON 字符串
                                      │
                                      │  MAPPER.readValue(json, User.class)
                                      │  ← 手动反序列化
                                      ▼
                                   User 对象
```

这个时候呢没有人帮你自动处理了，你需要手动地来序列化。我们在序列化的时候，就不需要把那个字节码写进去了，我就只是这个类本身的属性就可以了，然后把它调用 `set` 方法写入 Redis。

那么当我们要读取数据的时候呢？唉，那我读出来的是这样一个 JSON 字符串，它里面**没有字节码，没有字节码，就没有人帮你自动处理**，那么你要手动来处理啊。因为程序员自己知道我取出来的是哪个类型，我是不是就可以转成对应的类型了。

相当于什么呢？代码上是不是复杂了？我们加两个手动处理的动作。但是呢，哎，就解决了刚才那个内存占用的问题了。

#### 好消息：不用你重新定义

不过呀，这里还有一点需要注意的是：既然说了我们要统一使用字符串序列化，也就是说我们原来那个 `RedisTemplate` 是不是需要重新地定义成用字符串序列化器才可以啊？也就是说还需要重新地定义 `RedisTemplate`，对不对？

那么这个地方呢，告诉大家一个好消息：**不用你重新定义。** 因为 Spring 提供了一个叫 `StringRedisTemplate` 的类，那么这个类它的 key 和 value 的序列化方式默认就是字符串方式。

也就是说，**你不用再去定义 `RedisTemplate` 了**，也就省了一个那个复杂的配置了，直接用它就可以了。

那以前写的那一堆东西其实是不是不需要了啊？因为有默认的了，这个以后你就可以直接干掉就行了。

#### 代码只是多了一步

```java
@SpringBootTest
class RedisStringTemplateTest {

    @Autowired
    private StringRedisTemplate stringTemplate;

    private static final ObjectMapper MAPPER = new ObjectMapper();

    @Test
    void testSaveObject() throws JsonProcessingException {
        // 先创建对象
        User user = new User("胡歌", 21);

        // 对象是不能往 Redis 里直接写的，所以手动序列化成 JSON 字符串
        String json = MAPPER.writeValueAsString(user);

        stringTemplate.opsForValue().set("user:200", json);
    }

    @Test
    void testGetObject() throws JsonProcessingException {
        // 这回取的时候你也别强转了，强转不了，
        // 因为它默认取出来一定是一个 JSON 字符串
        String json = stringTemplate.opsForValue().get("user:200");

        // 手动告诉它类型，这个 JSON 串请当成 User 来解析
        User user = MAPPER.readValue(json, User.class);
        System.out.println(user);
    }
}
```

这里用到了一个东西叫 `ObjectMapper`，它是一个 JSON 的工具，就跟大家以前可能接触过的一些 FastJSON 这样的东西一样，它的作用就是把一个对象转成 JSON。如果没有学过 `ObjectMapper`，同学也可以使用你自己熟悉的 JSON 序列化工具，比如 FastJSON。`ObjectMapper` 是 Spring MVC 里面默认使用的 JSON 处理工具，所以我就用它了。

> **易错点**：注意 key 是 `user:200`，存进去的也必须用 `user:200` 去取。

对比一下与原来相比，其实就是多了一个手动处理的过程：以前是**自动**的，现在需要**手动**告诉它字节码。

#### 效果对比

运行一下，OK 它绿了，可以看到成功取得了这个用户。然后我们打开图形界面客户端，刷新一下 `200`——你看，存进去的是不是一个非常**清纯的**、**优雅的** JSON 字符串？与原来那个相比，是不是少了很多东西？内存空间上是不是节省了很多？

这就是手动处理 JSON 的方案。虽然代码上与原来相比多了这么点东西，但是同学们思考一下，事实上将来如果我们把这个 JSON 的处理封装成工具类，这段代码是不是也可以省掉了。

> **结论**：因此呢，这种处理方案是我个人比较推荐使用的一种方案。

#### 两种方案，怎么选

我们 `RedisTemplate` 的序列化有两种实现方案：

| | 方案一：自定义 `RedisTemplate` + `GenericJackson2JsonRedisSerializer` | 方案二：使用 `StringRedisTemplate` |
| --- | --- | --- |
| 写 | 直接 `set` 对象 | 先 `ObjectMapper.writeValueAsString` 转 JSON 再 `set` |
| 读 | 直接 `get`，自动反序列化 | 先 `get` 拿 String，再 `readValue` 转对象 |
| 内存 | 会占用额外空间，去记录那个类的字节码 | 纯 JSON 字符串，省空间 |
| 配置 | 需要自己写 `RedisConfig` | 省去了自定义的过程，不用定义 `RedisTemplate` |

方案一在做 JSON 的序列化和反序列化的时候，就会自动帮我们处理，不用你管；但它的弊端是会占用额外的内存空间去记录那个类的字节码。

方案二省去了自定义的过程；另外它麻烦的点在于，每次存数据的时候需要手动把对象序列化为 JSON，而每次读数据的时候需要手动地去做数据的反序列化。

那么两个呢有优点有缺点，**没有最好的啊**，你需要根据自己的需求，或者说你自己的喜好去选择。

### 哈希：opsForHash 其实就是 Java 的 HashMap

最后补充一个小知识点。因为之前我们讲解的所有 `RedisTemplate` 的使用，操作的都是字符串结构，对吧？所以下面我们再来写一个小测试，测试一下哈希结构的用法。

在 `RedisTemplate` 里，所有的操作都是由 `ops` 来获取的，`opsForValue()` 获取的是字符串操作，那 `opsForHash()` 拿到的自然就是跟哈希有关的操作了。

哈希里边我们可以做的是什么呢？就是一个 key 对应多个字段和值（field、value）。在这里边呢，我们的命令是叫 `HSET`，但是你会发现它**没有这样的方法名**——也就是说在我们的 Spring 里面，它并不是以命令名作为方法名的。

它叫什么？它叫 `put`。

它为什么叫 put 呢？因为啊，在它认为你这里玩的是哈希表——哈希表不就是 Java 的 HashMap 吗？那我干脆就用 `put` 是不是更容易接受一点。

那么它里面需要指定一个 key，然后再指定一个哈希 key 和 value，这就相当于是 **key field value**。没错吧？

而这里的 `putAll` 呢，就有点像那个 `HMSET`，指定一个 key 和多个字段值，字段值形成一个 Map。

```java
@Test
void testHash() {
    // 相当于 HSET key field value
    stringTemplate.opsForHash().put("user:400", "name", "胡歌");
    stringTemplate.opsForHash().put("user:400", "age", "21");

    // 相当于 HMSET key field value...
    Map<String, String> map = new HashMap<>();
    map.put("name", "胡歌");
    map.put("age", "21");
    stringTemplate.opsForHash().putAll("user:400", map);

    // 取一个字段
    Object name = stringTemplate.opsForHash().get("user:400", "name");

    // 取所有的键值对，相当于 Java 的 entrySet
    Map<Object, Object> result = stringTemplate.opsForHash().entries("user:400");
    System.out.println(result);

    // 取所有的 key、所有的 value
    stringTemplate.opsForHash().keys("user:400");
    stringTemplate.opsForHash().values("user:400");
}
```

取的时候大家看一下：`get` 就是取一个字段。那你说我想取好多怎么办？这里有个叫 `entries`，你看是不是跟 Java 的哈希 Map 很像？实际上 Java 叫 `entrySet`，它这里也叫 `entries`，拿到的就是所有的键值对。那么还有什么 `keys` 拿到所有的 key，还有 `values` 拿所有的值，确实是跟 Java 里面非常的相似吧。

运行一下，绿了，可以看到这里确实是拿到了这个 Map 的结果。我们去图形界面刷新一下 `400`，看是不是这样一个字段结构。

所以呢这个使用的效果，跟我们的 JDBC 也好，还是其他的好也好，都没什么太大差别啊。API 上呢更接近于 Java 的这种编程习惯，所以说这个就看你个人的喜好了。

那么其他的结构——Set、Sorted Set，我就再也不一一演示了。其实大家可以自己摸索一下，或者是参考一下官方的文档还是比较容易掌握的。
