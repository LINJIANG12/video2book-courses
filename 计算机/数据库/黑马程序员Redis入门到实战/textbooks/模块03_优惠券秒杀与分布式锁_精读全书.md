## 优惠券秒杀：从加一张券，到库存超卖
> 对应块：BLK14 | 覆盖分集：P50-P52 | 块标题（分集名）：《实战篇-03.优惠券秒杀-添加优惠券》

上节课我们已经把下单时 id 的唯一性问题解决了。id 不再重复，下一步就很自然了——实现优惠券的秒杀下单。

不过在说下单之前，我们得先把"券"这个东西看清楚一点。因为在黑马点评里，商品就是优惠券（也可以叫代金券），而券分两种：一种平平无奇，一种是要抢的。搞清楚这两种券的区别，后面的秒杀逻辑才有来龙去脉。

### 平价券和特价券，两种命运

网站上的第一张券是 47.5 抵 50，等于打了个九五折。这种券叫平价券，折扣小、价格便宜，所以可以大量发放，谁想买就买，跟给你发张传单没什么区别。

第二张券是 80 抵 100，八折。这就属于特价券了。折扣一下拉到这个程度，就不能随便发放了——你看它是有库存限制的，就 100 张，卖完就没了。所以它需要大家去抢购，先到先得；而且它也不是随时都能抢的，它还有时间的限制，只在某个时间段里开放。

> **结论**：普通券不用去秒杀，特价券才是需要秒杀的。我们接下来讲的秒杀下单，针对的就是这种特价券。普通券没什么好聊的。

这两种券落到数据库上是两张表，一张 `tb_voucher`，一张 `tb_voucher_seckill`。`voucher` 就是优惠券、代金券的意思，`tb_voucher` 里放的是普通的代金券，也就是没有特价的那种。

### 优惠券表与秒杀券表

#### tb_voucher：一张券的基本信息

打开数据库看 `tb_voucher`，第一个主键就不说了。往下：

| 字段 | 含义 |
| --- | --- |
| `shop_id` | 店铺 id。你这个券肯定是跟店铺有关联的，是哪个店铺发放代金券，得记录他的 id |
| `name` | 券的标题，你是一个多少钱的代金券，100 块的还是 50 块的 |
| `sub_title` | 副标题，一些描述 |
| `rules` | 使用规则。规则可以有很多，比如什么时间能够使用、可以叠加多少张使用等等 |
| `pay_value` | 支付金额。47.5 抵 50 里面，这个 47.5 就是它 |
| `actual_value` | 实际金额，也就是抵掉的金额。47.5 抵 50 里面，这个 50 就是它 |
| `type` | 券的类型：普通券是 0，秒杀券是 1 |
| `status` | 状态：上架、下架、过期三种 |
| `create_time` / `update_time` | 通用字段，没什么好聊的 |

`pay_value` 和 `actual_value` 这两个字段其实就是你的折扣。

> **提示**：`status` 这三个状态要想清楚。一个券理论上刚刚添加，它应该是一个下架状态；管理员去检验、审核通过，才可以给它上架去使用；如果觉得你的券有问题，就可以不去上架了。将来如果这个券不想再用了，我也可以让它处于一个过期状态。

注意这张表里面并没有库存。所以它其实也可以理解成是平价券——任意的人都可以来购买，随意购买。

#### tb_voucher_seckill：多出来的库存和时间

第二张表叫 `tb_voucher_seckill`，秒杀券。这张表的主键非常特殊，叫 `voucher_id`，而且没有自增长。

为什么主键不自增、还取了一个优惠券的名字？因为秒杀券它首先是一个券，对不对？它具备 `tb_voucher` 中的所有信息，除此以外，又因为它是个秒杀券，所以它又多了一些别的信息。

于是我们是不是可以这么认为：`tb_voucher` 里边既有秒杀券，也有非秒杀券，所以它里面有两种标识（0 和 1）；而 `tb_voucher_seckill` 里的这一行，将来在 `tb_voucher` 表中会对应一条信息，等于是一个拓展字段。

拓展出来的是什么字段呢？`stock`，因为秒杀券要有库存上限；然后是创建时间和更新时间，这俩就是基本的，没什么好说的。关键还有一个生效时间和失效时间——这个券什么时候可以开始抢，什么时候结束抢。它不能随时都能抢，在有效时间范围内才可以抢购。

所以这张表核心就是三样东西：库存和时间。

```text
tb_voucher     券的基本信息，普通券和秒杀券都在这张表
  id │ shop_id │ name │ sub_title │ rules │ pay_value
  actual_value │ type │ status │ create_time │ update_time
        ▲
        │  voucher_id 取的就是这张表的 id，秒杀券不单独自增
        │
tb_voucher_seckill     秒杀券多出来的部分
  voucher_id │ stock │ 生效时间 │ 失效时间
  create_time │ update_time
```

读图：上面那张表描述"券是什么"，下面那张表描述"这张券作为秒杀券的售卖规则"。两张表靠一个 id 绑在一起。

### 手动添加一张秒杀券

两张券讲完了，我们看一下现状：目前普通券里其实是有一张的，但是秒杀券里一张都没有。所以我们得去添加一些券，才能做测试。

打开浏览器看 103 茶餐厅这个店铺，现在是没有任何秒杀券的，只有这种普通的代金券。怎么添加呢？回到 PPT 上，我们其实提供了一个接口，是用来添加秒杀优惠券的。

```text
VoucherController
  POST /voucher/seckill
  参数：@RequestBody VoucherDTO
```

我们只需要调用这个接口，它就能帮我们新增这张优惠券。

打开代码，找到 `VoucherController`。这个秒杀功能里面，虽然看起来只接收了 `VoucherDTO` 这一个对象，其实往下翻你会发现，它还会带上库存、开始时间和结束时间——它把秒杀券的核心的这三个字段都带上了。因此你提交的时候这几个都提交了，最终在实现这个业务的时候，它就会帮你第一新增普通券，第二新增这个秒杀券，两张表的信息都会帮你去新增。

好，这个业务就看完了，下面我们就去添加一个。打开 Postman。

> **提示**：这里理论上讲将来是从后台管理的接口里、后台管理的一个界面里添加的，所以现在我们直接利用 Postman 来添加。

Postman 里有一个"添加秒杀券"的业务，我提前已经写好了：`/voucher/seckill`，POST，请求体是准备好的 JSON。

```json
{
  "shopId": 1,
  "name": "100元的代金券",
  "subTitle": "周一到周五可用",
  "rules": "全场通用，无需预约",
  "payValue": 8000,
  "actualValue": 10000,
  "type": 1,
  "stock": 100,
  "beginTime": "2025-01-26T00:00:00",
  "endTime": "2025-01-26T14:00:00"
}
```

这里有几个地方要停下来看一眼。

第一，关联的店铺我这里准备的是 2，我们改成 1 号店铺，就是刚才那个茶餐厅。

第二，特价券周末就不让你用了，所以副标题写的是"周一到周五可用"，规则是"全场通用，无需预约"。

> **易错点**：注意这两个数怎么是 8000 抵 1 万呢？这两个其实是它的单位。我们在数据库里，这两个值的单位是**分**。以分为单位可以避免出现小数。所以 8000 其实就是 80 块钱，抵的是 100。

第三，`type` 填 1，也就是一个特价券、秒杀券。`stock` 是 100。

第四，开始时间和结束时间你可以随便做一个设置，那都是没问题的。比如设置到 1 月 26 号到 1 月 26 号的下午两点，这一期间都可以去购买；或者可以设置到 24 点。

发送一下，返回确实是新增成功了。去数据库里刷新一下：确实有一个券，而且这边也会有一张券，生成的新券 id 是 7，对应到这边也是 7，所以他俩是有关联的，这边库存是 100。秒杀券添加成功了。

回到浏览器再刷新一下，可以看到多了一张券。好了，这张券已经准备好了，已经可以开始去做抢购了。

现在点击抢购，它说你要先登录。我登录一下 13456789001，发送一个验证码，然后去 Redis 里刷新找到这个验证码，填进去，确认用户协议，登录成功。

回到店铺，就这一张券了。现在点抢购，它说"功能尚未完成"。但是最起码这个接口我们看到了，所以下一步要做的事情很简单——来实现这个接口，完成下单的功能。

我们可以看到这个接口的使用方式是 POST，路径叫 `/voucher-order/seckill`，也就是优惠券订单的秒杀，后面跟上的这个 7 就是当前券的 id，就是你要抢的是哪一个券。

> **结论**：接收到这些信息以后，就可以去对应的券去下单，扣除对应的库存，完成整个秒杀的过程。返回值是当前订单的 id——订单 id 一定要返回给前端，前端才可以去支付。

### 秒杀下单：一张订单，两个动作

既然是下单，你要做的事情自然就是去创建一个订单。当然不要忘了，最终还要去把对应的库存给扣了。下单、扣库存，这是一套动作。

下单下到哪里去呢？看数据库，其实就是我们之前那个 `tb_voucher_order` 表。不管是普通代金券还是特价券，最终下单购买都需要生成订单数据，然后放到这张表里面去。这里面记录的是下单的用户、购买了哪一张券、付款方式、订单状态等等这些信息。

> **提示**：这些信息在刚刚创建的时候并不需要全部指定出来。支付方式有默认值，支付金额有默认值，创建时间、更新时间也都有默认值。所以我们一开始只要指定订单的 id、用户 id 和券 id 就够了。别的不用管了。

那下单扣库存这个功能这么复杂，肯定不能写在 Controller 里，我们放到 Service 里。在 Controller 里需要注意 `VoucherOrderService`，调用它里面的方法来实现秒杀，方法名是 `seckillVoucher`，把 voucherId 传进去就行了。实现类里照着流程写就行。

### 先判断，再动手

这个秒杀下单的功能有两点需求需要我们注意。

第一，你需要判断这个秒杀是否开始或者结束了。因为我们这个秒杀里边会有两个字段，一个是开始时间，一个是结束时间，只有在这个时间段内你才能去参与秒杀，过了这个时间段就不允许你参加了，等于是你是一个过期的或者超时的请求。

另外还要对库存做判断。你要减库存，我不能说谁来了我都减吧——我就这 100 个，卖完了怎么办呢？所以如果库存不足也是不允许下单的。

这两个点是我们一定要去做判断的。

整体的流程大概是这样的：前端提交优惠券 id 过来，我们拿到 id 以后，不要上来先去下单，要先去做判断，看条件是否成立。而你要判断秒杀有没有开始或者结束、库存够不够，你是不是得先拿到这个优惠券的信息才行？

```text
  前端提交优惠券 id
        │
        ▼
  ① 查询优惠券信息 ──────► 拿到 开始时间 / 结束时间 / 库存
        │
        ▼
  ② 判断秒杀时间 ───────► 还没开始 / 已经结束 → 返回异常
        │
        ▼
  ③ 判断库存 ────────────► 库存不足 → 返回异常
        │
        ▼
  ④ 扣减库存
     UPDATE tb_voucher_seckill SET stock = stock - 1 WHERE voucher_id = ?
        │
        ├── 更新失败 ──────► 返回异常
        ▼
  ⑤ 创建订单 ────────────► 写入 tb_voucher_order
        │
        ▼
  ⑥ 返回订单 id ─────────► 前端凭它去获取支付链接
```

读图：查询在最前面，是因为后面两个判断都依赖查出来的数据；时间判断在库存判断之前，因为时间不合法的话库存根本没有意义。

把每一步再展开说一遍。查出来以后，我得到了优惠券里面的时间和库存，就可以做判断了。我先判断时间对不对——有没有开始，或者是不是结束了？如果还没开始，那证明什么？你来早了呗，不知道你从哪知道的，请求就发来了，这不允许的，所以直接返回一个异常就行了。结束也一样。

但如果是已经开始的，那就代表你是一个正常的请求，而且是在合理的时间来的，我接下来是不是可以考虑去减库存了？但减库存的前提是库存要充足，所以在这儿还要再做一个判断，就是库存是否充足。如果库存充足没问题，我们就可以去执行下面的动作了；如果库存不足那就无法下单呗，证明东西被抢完了，同样是返回错误信息。

库存充足自然就是去扣减库存，库存扣完了我们还要完成下单的动作，别忘了我们还要去向 `tb_voucher_order` 表里插入这个订单。创建完了就可以返回订单信息，也就是它的 id 给前端，前端将来就可以拿这个 id 去获取支付的链接，然后用户去做支付。

这就是我们整体的一个业务流程了。

### 把流程写成代码

先解决查询优惠券这一步。这个查询我们就要用到优惠券对应的 Service 了，根据 id 去查。我们需要注入 `IVoucherSeckillService`。

> **提示**：这里要注入哪个 Service，值得想一下。我们要查的是秒杀的时间，还有库存，那么这些信息其实是在秒杀券里面，而不是在普通券里边。我们的实体类里其实就有两种：`Voucher` 和 `VoucherSeckill`，对应的 Service 也有两个。既然要查的是秒杀相关信息，就应该用秒杀券的 Service。事实上它与 `Voucher` 表是共享 id 的，所以说用这个来查是没有问题的。

直接调它的 `getById`，把 voucherId 传进去，就能拿到优惠券的信息了。

拿到信息以后，判断有没有开始，其实就是把它里面那个时间取出来。是否开始就取那个开始时间，也就是 `beginTime`，拿这个时间和当前时间去做一个比较。如果开始时间是大于我们当前时间的，那证明就没有开始——大于就是 `isAfter`。因为你的开始时间还是在当前时间之后嘛，那不就是未开始。未开始我们就可以返回一个错误信息了，比如"秒杀尚未开始"。

然后再往下判断是否结束，是不是一个道理？这次取的是结束时间，这次就不是 `isAfter` 了，是 `isBefore`。结束时间在当前时间之前，那不代表已经结束了嘛，所以这个地方就是"秒杀已结束"。

如果时间都没问题，往下判断库存。库存就是我们这个券里面的 `stock` 字段。什么叫充足？秒杀嘛，一人一单，只要大于 0 是不是就是充足的。我们判断一下它是不是小于 1，如果是小于 1，那就代表库存不足了，同样返回错误信息。

这样各种判断就做完了。判断全部成功，我们就可以去执行真正的业务逻辑了。

扣减库存其实简单，无非就是把我们的秒杀库存值减一就行了。所以我们可以执行它里面的 `update` 语句，手写 SQL，也就是这个 stock 值等于 stock 减一，在原来基础上减一；然后它的 where 条件就是 id，voucher_id 等于我们传递的这个 voucherId。

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1
WHERE voucher_id = #{voucherId}
```

> **易错点**：这个地方是 `voucher_id`，下划线 id。去看一下秒杀表里面的主键，是不是下划线 id？千万别搞错了啊。

扣减库存它最后还会返回一个结果，一个 boolean，代表你当前这一次更新有没有成功。如果 success 取反，那代表没成功，更新失败、扣减失败。一般的原因可能也是库存不足，所以我们也可以返回"库存不足"。

> **结论**：这个返回值是一层兜底。前面已经判断过库存了，但那是"查出来的时候"的库存；update 影响行数才是"真正扣减那一刻"的结论。

然后就可以去下单了，创建订单其实就是往订单表里面新增一条数据。订单表 `tb_voucher_order` 这个类虽然大家没见过，但表我们之前是见过的。这张表主要记录的是用户的 id、券的 id、支付方式、订单状态等等。订单状态初始化有默认值，支付方式也有默认值，这些我们都不用管，其实我们只用管三个：订单的 id、用户 id 和代金券 id。

订单 id 我们当时计划的是用 id 生成器去生成的，所以我们在这里需要注入之前写的 `RedisIdWorker`，利用它去获取一个全局唯一 id，调用 `nextId` 传一个 key，比如就叫 `order`，得到我们的订单 id。用户 id 我们可以通过 `UserHolder` 获取，我们是写了一个登录拦截器，从它里面就能取得用户，从而取到用户的 id。最后代金券的 id 就是参数传给我们的，这是最简单的，直接把 id 传给它就行了。

现在订单所需要的参数全部准备齐了，接下来就是把这个订单写入数据库，用当前的 `save` 就行了，把订单对象扔进去。

最终要返回的是订单的 id，也就是这个地方生成的，那么这样返回不就行了。当然，这个要放到 `result` 里，所以这个地方要拿 Map 做个包装，这样返回就行。

整个方法写完了：

```java
@Override
@Transactional
public Long seckillVoucher(Long voucherId) {
    // ① 查询优惠券信息
    VoucherSeckill voucher = voucherSeckillService.getById(voucherId);

    // ② 判断秒杀时间：未开始 or 已结束
    if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
        throw new BadRequestException("秒杀尚未开始！");
    }
    if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
        throw new BadRequestException("秒杀已结束！");
    }

    // ③ 判断库存
    if (voucher.getStock() < 1) {
        throw new BadRequestException("库存不足！");
    }

    // ④ 扣减库存
    boolean ok = voucherSeckillService.update(
            Wrappers.lambdaUpdate(VoucherSeckill.class)
                    .set(VoucherSeckill::getStock, VoucherSeckill::getStock - 1)
                    .eq(VoucherSeckill::getVoucherId, voucherId));
    if (!ok) {
        throw new BadRequestException("库存不足！");
    }

    // ⑤ 创建订单
    VoucherOrder order = new VoucherOrder();
    order.setId(redisIdWorker.nextId("order"));
    order.setUserId(UserHolder.getUser().getId());
    order.setVoucherId(voucherId);
    voucherOrderService.save(order);

    // ⑥ 返回订单 id
    return order.getId();
}
```

> **易错点**：这里面牵扯了订单的新增，还有库存的扣减，等于是有两张表的操作。像这种情况下最好加上事务 `@Transactional`。加了事务的话一旦出现问题，它可以及时回滚；如果你不加事务的话，出现问题都无法回滚了。

### 200 个线程一起抢：库存超卖

上一次测试我们是在页面上自己点击的，这跟真实的秒杀场景还是有很大差异。因为真实的秒杀场景下，肯定有无数的用户一起来去抢购、一起去点那个按钮，所以在一瞬间的并发量可能会达到每秒钟数百甚至上千上万个。那在这种情况下，我们这个接口还能不能正常工作呢？

要想模拟高并发的场景，肯定要用到 JMeter。我们打开提前配置好的脚本：这里配了 200 个线程，也就是说代表 200 个用户同时来向我们发起请求，请求地址是 `localhost/voucher-order/seckill/7`，跟之前测试的接口是一致的。

看一下数据库的现状：订单只有一个，是之前测试的时候下的；优惠券库存目前是 99。我们把库存改成 100，顺便把这个订单也删掉，方便我们看效果。这样一来 200 个用户并发来请求，我们有 100 个券，我们希望只卖出 100 个，理论上讲应该只生成 100 个订单。这是我们所预期的。

来运行一下，一瞬间就运行完了。看结果：有一些是成功的，拿到了 id；那当然肯定还会有一些失败的，库存不足。从聚合报告来看，这个地方的异常比例是 45%，也就是说有 45% 的人失败了。

> **结论**：按我们的预期应该是一半失败才对——只有 100 个库存，200 个人嘛，应该一半失败。那证明失败的好像没有达到一半。

去数据库看一下，库存刷新一下：`-9`。库存是不是出现了负数啊？再看这张表，订单的数量是 109。同学们发现问题了吗？

在高并发的场景下：第一，我们的库存是不是出现了超卖啊？我们只能卖 100 件，但实际上却卖出了 109 件，因为出现了 -9；而且订单数量本来也应该只有 100，却出现了 109。也就是多出来那些，说明我们这个库存多卖了很多。

这在秒杀场景下是很容易出现的一个问题，但也是不可接受的一个问题。如果说秒杀的商品是一个非常珍贵的商品，或者说它的价值非常高，而且它卖的又很便宜，这时候可能会给商家带来巨大的损失，所以这肯定是不允许的。

### 超卖是怎么发生的

我们为什么会出现这个问题呢？回到代码里看一下：我们对于库存的判断是在这一块做的。首先我们去查询优惠券，查到券了以后判断这个券的库存是否充足。如果说充足，我们就去扣减；如果不足，就报错。先查询，再判断，然后去减——这就是我们的一个逻辑。

那这个逻辑怎么就出现问题了呢？我们拿库存来分析。假设现在库存就剩下 1 个了，然后高度并发的情况下，有很多很多线程来执行。假如说我这里有两个线程。

在正常情况下，我们的线程是按顺序去执行的。线程一先来执行下单逻辑：首先他要先查询，查询完了才能判断，查询库存，因为库存是 1，所以他查到的结果就是这个 1。查到了以后要去干什么呢？要去判断库存是否足够，这里判断是大于 0，大于 0 代表足够，就可以去扣减。现在明显 1 是大于 0 的，所以它要执行扣减的动作，库存就从 1 变成了 0，这个下单的逻辑就走完了。此时线程二来查询的时候，查到的自然就是 0，它去判断库存是否充足，一看不行，不满足，那就报错了。这是正常逻辑，一个执行完再执行另一个。

```text
【串行执行】库存只剩 1

线程一                            线程二
  │ 查询 -> stock = 1               │
  │ 判断 stock > 0，成立            │
  │ 扣减 stock: 1 -> 0              │
  │ 下单完成                        │
  │                                 │ 查询 -> stock = 0
  │                                 │ 判断不成立，返回「库存不足」

最终库存 = 0，正确
```

但是高并发的情况恰恰相反，你无法控制顺序。线程一和线程二能这么友好地说"你认为我在执行吗"？不一定，它还可能出现一种情况，就是交叉执行。

也就是说，线程一现在执行查询库存的动作，他查到的可能是 1，这个时候他本来应该去判断去了；就在此时线程二也进来了，在线程一尚未扣减库存之前，他进来了，好多线程切换，那他也去查了，查的也是 1。也就是说这两个线程查到的都是 1。此时轮到了线程一去扣减，他判断 1 大于 0 执行扣减，库存就从 1 变成了 0。而线程二做判断的时候，因为它是在线程一扣减之前查询的，所以它拿这个 1 来判断结果也是大于 0，所以它也执行了扣减的动作，于是库存就从 0 变成了 -1。

```text
【交叉执行】库存只剩 1

线程一                            线程二
  │ 查询 -> stock = 1               │
  │                                 │ 查询 -> stock = 1   <-- 也读到 1
  │ 判断 stock > 0，成立            │
  │ 扣减 stock: 1 -> 0              │
  │                                 │ 判断 stock > 0，也成立
  │                                 │ 扣减 stock: 0 -> -1

最终库存 = -1，超卖
```

同学们想象一下，我们这里只模拟了两个线程。如果在同一时刻有无数的线程，比如我们这次模拟的 200 个，那更多线程来，是不是都是同样的道理？只要在线程一扣减之前，有无数的线程进来做查询，他们都会认为库存充足，都会去做扣减，最终库存就会出现超卖。

> **结论**：这就是所谓的并发安全问题——多个线程在操作共享的资源，并且操作资源的代码有好几行，那么在这几行代码执行的中间，多个线程互相穿插就出现安全问题了。

### 加锁：悲观锁还是乐观锁

针对这样的多线程并发安全问题怎么解决？相信每个同学都能想到答案——答案可以打在公屏上。是不是采用锁的方案啊？没错，加锁。

但是加锁还是有很多不同的诀窍、很多不同的姿势。不知道大家有没有听说过两种锁：一种叫悲观锁，一种叫乐观锁。

> **定义**：悲观锁和乐观锁并不是一种真正的锁，它们只是两种所设计出来的理念。

悲观锁认为线程安全问题一定会发生，所以说它会在执行数据库操作之前先获取锁，确保线程串行执行。如果我们做到线程是串行执行的，是不是就不会出现安全问题了？是这样子的。所以这就是悲观锁的一个设计思想：既然多线程并发有安全问题，那你就不要并发了呀，我执行完了你再执行。

正因为此，悲观锁的性能并不是很好，因为你不管有多少线程，都只能是一个一个地去执行，在高并发场景下并不是很适合。比如说我们 JDK 里面提供的 `synchronized`、`Lock`，其实都属于悲观锁；还有我们数据库里面的这种互斥的锁，它也属于悲观锁。

乐观锁就恰好相反了，它属于乐天派，它认为线程安全问题不一定会发生，所以它根本就不加锁。

有的会说了：我加锁？我怎么保证这个线程安全呀？乐观锁认为，这种线程安全问题发生的可能性其实是比较低的，多数情况下是不会发生的，你没有必要上来就加锁。你看我们刚才分析，是不是在极少数情况下才会出现这个问题？而你为了这极少数的情况，把大多数的、所有的线程都让它串行了，这显然是不太好的。所以乐观锁就说了：既然大多数情况下都不发生安全问题，那我就不锁了，大家都来吧。

那它怎么保证这个安全呢？它会在线程对数据做更新时才去做判断：判断在我之前有没有别的线程来做数据的修改。

什么意思呢？比方说我现在查到一个库存，查到库存以后我是不是要去更新这个库存？好，在更新库存之前，我判断一下有没有别人修改库存看一看、对比对比。如果改了，跟我之前查的不一样了，那不就说明有人改了吗？那我就认为有安全问题了，我就重试或者报错。但是如果在我尝试去修改的时候，我一看数据跟我之前差不多、没有变化，那我认为安全，我可以放心地修改。

> **结论**：因为乐观锁不用去加锁，而是在更新时才有个判断，因此它的性能会比悲观锁好很多。

但是它的关键点在哪里？它的关键点就是在于：我怎么知道在我更新的时候别人有没有来做修改？这个判断是不是成为了关键呀？那乐观锁怎么去实现这种判断呢？这就是我们接下来要去研究的重点了。

悲观锁这种方案比较简单，相信大家都会加锁这种方式，所以我们就不去演示了，我们就演示乐观锁这种方案。

### 版本号法

乐观锁的关键，刚才说了，是判断我之前查询到的数据有没有被修改过。那怎么判断呢？常见的方式有两种。

第一种叫版本号法，这种方案是应用最广泛的，也是最普遍的。它的原理是什么呢？我们还是拿刚才的库存为例，在我们的数据库表里边有 id 字段，有库存字段，还有很多别的字段，现在我们先不管。

所谓的版本号法，就是给数据加上一个版本。那么在多线程并发的时候，基于版本号来去判断有没有被修改过。每当数据要做一次修改，版本号就会加一，也就是说这个版本是在不断变化的，每一次修改版本就会变化一次。那我想要判断一个数据有没有被修改过，其实就是判断它的版本号有没有变化，是不是就 OK 了？

具体怎么去做呢？我们来看一下。首先现在假设有两个线程，线程一和线程二。有了版本号以后，线程一去查询的时候，它做查询就不仅仅是查库存了，它还要把版本号也查出来。现在线程一查库存和版本号，查到的是库存 1、版本 1。紧接着它本来应该去减去了，但就在此时另外一个线程插入进来了，这时候是不是就出现了并发的这种问题？好，线程二也去查询，同样查询这两个字段，它查到的也是库存 1、版本 1。

紧接着又切到了线程一，线程一要去扣减库存了，判断库存 1 大于 0，是要扣减。以前要是扣减是不是直接减就完了？现在不行。版本号每次修改之后都要加一，所以他在做扣减库存的时候，不仅仅要修改库存，还要修改版本号。

其次，我在修改时，乐观锁的方案是什么？是在修改的时候判断一下之前查询到的数据有没有被修改过。我之前查到的数据是不是库存和版本？那我就要判断一下我这个版本有没有被修改过，所以他最终的一个语句是这样的（我写了个伪代码）：

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1,
    version = version + 1
WHERE id = #{id}
  AND version = #{version}
```

`SET stock = stock - 1` 是要减库存，`version = version + 1` 是必备操作，任何一次修改都要版本加一。where 条件是 `id` 等于 10，就是我更新 voucher_id 为 10 的这一条数据。但是我加了一个 and 条件：`version` 必须等于 1。为什么？因为判断之前查询到的数据有没有被修改，我之前查的 version 是不是 1，所以我在 where 条件里这个 version 就要求必须等于 1。

如果我执行这条 SQL 语句时 version 值依然等于 1，说明跟我之前查到的一样，说明在我这个查询和这个减两者之间没有人修改过我的数据，我是不是就可以放心大胆地去减了呢？

```text
  线程一                              线程二
    │ 查询 stock=1, version=1           │
    │                                   │ 查询 stock=1, version=1
    │ UPDATE SET stock=0, version=2      │
    │ WHERE id=10 AND version=1         │   <-- 匹配，更新成功
    │                                   │
    │                                   │ UPDATE SET stock=0, version=2
    │                                   │ WHERE id=10 AND version=1
    │                                   │ <-- version 已是 2，条件不成立
    │                                   │ <-- 更新失败，不扣库存，不下单
```

读图：线程二的条件不成立，所以它不会执行这条语句，也就不会超卖。而我们怎么知道它没执行？看 update 的返回值就行——这就是前面扣减库存那一步为什么要拿 boolean 再兜一层。

线程二发现 `version` 是 2 而不是我查的 1，说明在我之前有人修改了，那线程二就知道我们的数据不安全了，这个 where 条件不成立，就不会执行。这样是不是就不会发生安全问题了？就不会超卖。这就是乐观锁的实现方案之一——版本号法。

### CAS：拿库存本身当版本号

乐观锁的第二种方案，是在版本号法的基础上做了一些简化。怎么简化呢？

大家看版本号法，其实是用版本来标识数据有没有变化。怎么知道有没有变化呢？首先要查询的时候要把版本查出来；其次更新的时候，每次除了更新数据以外，版本也要跟着更新。既然每次更新都要更新版本，那我如果查到的版本和我更新时的版本一致，就证明没有人更新，对不对？

但是大家看一下我们当前的业务：我们每次业务其实在查版本的同时，库存是必查的，更新的同时库存也是必更新的。这个库存跟版本所做的事情是不是一样的？既然如此，我为什么不用库存来代替版本呢？

我在查询的时候把库存查出来，然后我在更新的时候，判断一下当前的这个库存跟我之前查到的库存是不是一样的。如果一样，不就同样能够证明没有人修改过吗？所以我们这个方案是不是就能够简化了，也就是用数据本身有没有变化来去判断我们这个线程是否安全。

> **定义**：这种方案称为 CAS（compare-and-swap，比较并交换），先比较 compare，再 set 修改。

也就是说我们不再有版本号了。开始查的时候只查库存就行了。比方说这两个线程去查库存都是 1。查到了以后判断库存 1 大于 0，那是在扣减，扣减怎么扣减呢？

```sql
UPDATE tb_voucher_seckill
SET stock = stock - 1
WHERE id = #{id}
  AND stock = #{stock}
```

注意 and。因为没有版本了，我们用库存来代替版本，所以我要求在我更新的这一刻，这个库存值一定要跟我查询的库存值一样。我查询的库存是 1，那么这里的 stock 值必须等于 1。于是我拿着这个去判断：`id` 是 10 吗？库存是 1 吗？是的，满足，满足我就减，库存变成了 0。

这个时候线程二也来执行扣减的动作了，他判断一下 1 大于 0，他就开始扣减，他也执行这条语句，`set stock = stock - 1 where id = 10 and stock = ?`。那么这个 `stock` 值是不是要等于他查询到的 stock 值？当他查询到的是 1，所以这个条件也必须是 1。他拿这两个条件去判断，发现不成立，所以这个扣减动作不会执行。于是线程安全问题是不是也没有发生？

所以它其实就是利用库存来代替了版本号，这就是 CAS——比较这个数据有没有发生变化。

> **结论**：以上两种方案思想是一样的，只不过一个用版本号，一个没有用版本号。解决思路我们先聊到这里，下节课就动手实践，用这种乐观锁来解决库存超卖的问题。

## 优惠券秒杀：乐观锁、一人一单，以及集群下那道拦不住的锁
> 对应块：BLK15 | 覆盖分集：P53-P55 | 块标题（分集名）：《实战篇-06.优惠券秒杀-乐观锁解决超卖》

上节课我们把解决并发安全的两条路都摊开讲了：悲观锁和乐观锁。悲观锁大家都熟，乐观锁大多数同学没怎么接触过。这节课我们就拿乐观锁这把刀，真刀真枪地切进秒杀业务里去。

改完代码我第一件事是跑压测：200 个线程抢 100 个库存，结果聚合报告上失败率高到 89%。可数据库里一翻——库存才只卖出 20 件，订单也只有 20 条出头。安全是安全了，可这生意根本没法做。这中间到底发生了什么，是这一讲最值得掰开了揉碎了讲的地方。

### 乐观锁解决超卖

#### 给扣减加一个条件

先回到代码。原来那段业务逻辑再熟悉不过：一上来去查询优惠券，查询完了以后对库存去做一个判断，判断完了以后去扣减库存。

按照我们之前分析的，所谓的乐观锁方案，其实就是在**执行扣减的这一刻去加上一个条件**——判断什么？判断我更新时的这个库存值，与我查询到的库存值是不是同一个。如果是，证明在我之前没人修改过，我就可以放心大胆地修改了。

所以我需要在 where 条件里去添加一个对 stock 值的判断，它的值就是我查到的值。我查到的值是不是就是这个 stock 值呢？所以加上这样一条就可以了。

```java
// 扣减库存：乐观锁方案
boolean ok = voucherMapper.update(null, Wrappers.<Voucher>lambdaUpdate()
        .set(Voucher::getStock, voucher.getStock() - 1)  // set 赋值：stock = stock - 1
        .eq(Voucher::getId, voucher.getId())             // where 条件一：id = ?
        .eq(Voucher::getStock, voucher.getStock()));     // where 条件二：stock = 我查到的 stock
```

对应的 SQL 就是：

```sql
UPDATE voucher
SET stock = stock - 1
WHERE id = ?
  AND stock = ?;   -- 我查到的那个 stock
```

这里给大家解释一下：上面的 `set` 就是赋值，把这个 stock 等于 stock 减一；下面这两个 `eq` 就是 where 条件，一个判断 id 等于什么，另一个判断 stock 等于什么。只要我在更新时这个 where 条件里的库存值，等于我查询到的库存值，那证明我上面那个判断是没有问题的，证明在我之前没有人修改过，我放心大胆地扣，是不是就没问题？

> **结论**：所以我们现在这样去写，线程一定是安全的——注意，我们一把锁都没有加。这就是乐观锁：不加锁，把"我更新的时候你还在不在"这件事，塞进 SQL 的 where 条件里让数据库替我们判断。

顺带把选型说清楚。乐观锁的落地方式我们讲过两种：一种是版本号法，还有一种是直接的 CAS 法。那鉴于我们这里是库存场景，去添加版本号显然是多余的，我们可以直接用库存来判断，所以我们采用这种 CAS 法。

#### 89% 的失败率从哪来

改完先别急着下结论，测一测。测试之前老规矩，先把数据库数据还原：打开数据库，把所有的订单数据都删掉，再到优惠券表里把库存改回 100，保存。

数据库现在还原了——库存又是 100，订单是空的。我们打开 JMeter，还是刚才这个测试，线程数量依然是 200，200 个人同时来访问，100 个库存。执行完毕，我们来看聚合报告。

**失败比例 89%。**

> **易错点**：我们有 200 个人、100 个库存，按照我们分析的正常情况，50% 的失败率才是比较正常的。现在是 89%，说明失败的人大大增加了。

我们再来看一下结果数。你可以看到一上来就有"库存不足"，然后是成功的、库存不足的。诶，为什么这么多失败呢？我们去看一下数据库——在这里刷新，库存并没有超卖，只卖出了 20 件；订单呢，也是 20、21 件左右。所以说没有超卖，安全问题是不是解决了。

可为什么出现了很多失败的情况？我还没卖完，结果这些人就结束了，这怎么回事？

回到 PPT 上给大家分析一下。现在假设库存还剩 100，也就是刚开始卖，然后有无数的线程都涌入进来了，又因为我没加锁，那这些线程就并行执行：

```text
  并行的 100 个线程，全都读到 stock = 100
  ┌──────────────────────────────────────────────────────┐
  │  T1    T2    T3    T4    T5   ...              T100 │
  │   │     │     │     │     │                        │
  │  查    查    查    查    查                       查   │
  │ 100   100   100   100   100                      100 │
  └───┴─────┴─────┴─────┴─────┴────────────────────────┘
                          │
                          ▼
          执行 UPDATE ... WHERE id = ? AND stock = ?
                          │
          ┌───────────────┴────────────────┐
          ▼                                ▼
  WHERE stock = 100 成立            WHERE stock = 100 不成立
  stock: 100 → 99                    库里的值已经变成 99 了
  成功 1 个，更新 1 行                失败 99 个，更新 0 行
```

（读图：所有线程都在"查询"这一步读到同一个 100；真正执行 UPDATE 时，只有第一个把 100 改成 99，后面的 where 一对不上，一行都改不动。）

只剩下一个线程会去执行更新的动作，它判断库存是否大于零，是；然后 where 条件里的库存得等于 100，也成立，于是它减掉一点，库存从 100 变成 99，它成功了。

现在其他剩下的 99 个线程来执行这个 SQL 语句的时候，他们判断这个库存值是不是也得等于 100——但已经变成 99 了，是不是全部失败了。这剩下的 99 个线程都会认为：在我之前有人改过了，那我不能犯错误对吧，我就取消。于是你会发现失败率大大提高。

但是我们从业务角度来考虑啊：我现在还剩 99 个库存，剩下的 99 个人是不是真的要失败啊？不是，这 99 个人完全可以成功啊，对不对？那你为什么失败了？

**因为他太小心了。** 他觉得只要有人改了就有安全问题。其实没有啊，这里是产生了并发修改，但没有业务上的安全问题，对不对？因为作为库存来讲，只要大于零就行了，不是说我改的时候别人不能改。

#### 只要库存大于零

> **结论**：这就是我们乐观锁方案的一个问题——成功率太低。

那因此呢，我们完全可以对这个乐观锁方案做一个简单的改进。什么改进呢？回到 IDEA 里，在这个地方解决这个失败率高的问题。我们的思路有很多种，库存这一块有一个非常简单的方案：我们不再判断库存是否与我查到的相等了，我们只要判断库存大于零，是不是就 OK 了？

同学们思考一下，只要库存是大于零的，我管你是多少呢？我随便减是不是都没问题？只要库存不是大于零的，那我就失败。这样是不是就 OK 了？所以说我们完全没有必要非得判断说必须得一模一样，是不是。

因此呢，我们把这个 `eq` 改成 `gt`（大于的意思），那这个值就不再是我查到的值，是零就行了。

```java
// 扣减库存：只判断库存大于零
boolean ok = voucherMapper.update(null, Wrappers.<Voucher>lambdaUpdate()
        .set(Voucher::getStock, voucher.getStock() - 1)
        .eq(Voucher::getId, voucher.getId())
        .gt(Voucher::getStock, 0));
```

重启完成。我们先打开数据库，把数据恢复成 100，订单全选删除；然后打开 JMeter，清空所有的数据，重新运行。

运行完成，我们来看一下报告——**失败比例 50%**，完美达到我们的预期是吧。那我们看一下数据库：库存恰好是零，订单呢恰好是 100。大家可以看到库存并没有超卖，而且订单是不是也恰好刚好是 100 个呀，而且成功的比例也是刚刚好，就是说没有因为某种特别的原因导致失败，就是库存没了才失败的。

所以呢，现在我们是不是就完美解决了这个库存的超卖问题了？

#### 悲观锁还是乐观锁

好，我们回到 PPT 做一个总结。本节课我们解决的是线程并发安全问题，也就是超卖的问题。那解决这样的问题呢，方案可以使用悲观锁，也可以使用乐观锁。

| | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 基本假设 | 认为线程安全问题**一定会**发生 | 认为线程安全问题**不一定**发生 |
| 做法 | 加同步锁，让线程串行执行，确保同一时刻只会有一个线程修改资源 | 不加锁，在更新的时候再判断一下：在我更新之前有没有人也来更新了；没有就放心大胆地更新，有就取消更新 |
| 优点 | 实现起来简单粗暴 | 正因为不加锁，性能相对来讲是比较好的 |
| 缺点 | 必定是串行执行，性能会有一定的影响 | 基于数据变更来判断。像库存这种，我们查到的数据不一样、但其实并没有超卖，是完全可以减的，却因为乐观锁只要判断数据被修改了就不许减，**成功率太低** |

这个缺点要再说透一点：由 1000 个人来去执行这个减的动作，如果他们查到的库存都是一样的，理论上讲是没问题的，是 OK 的；但是实际上他们都会失败，只有一个人成功。

那成功率太低的问题怎么去解决呢？我们给大家讲了一个方案——因为库存比较特殊，其实只要大于零就行，所以不再判断数据与查询的时候是否一致了，而是仅仅要求大于零就 OK 了，也就是 where 条件里添加上库存大于零就行了。

那么除了这种方案以外呢，还有一些其他的方案。比如说有些场景里它不是库存，它只能通过数据有没有变化来去判断是否安全，那这种情况下也可以提高成功率。我们还可以采用这种分批加锁的方案，或者讲分段锁的方案：也就是说，我们可以把数据类的资源分成几份。比如说我的库存总共是 100，我可以把这 100 的库存分到十张表当中，每个表里边库存量是 10，然后用户在抢的时候呢，可以去多张表里面分别去抢。那这样一来的话，我的成功率就相当于同时有十个去抢，成功率是不是提高了十倍？

> **提示**：这种分段锁的思想，其实在 `ConcurrentHashMap` 里面是不是有用到过？它就可以解决成功率低的问题。分段锁的方案相当于是什么？每次锁定的资源少啊，不再是一下把 100 个资源全锁定，只锁这十个资源。

> **结论**：以上呢就是超卖这个问题了。通过这个问题呢，我们其实主要是给大家讲解了各种不同的锁的一个使用场景。那大家可以根据自己实际工程中的需求，去判断到底应该使用哪种。虽然我们最终选择了乐观锁，但并不是说乐观锁就是完美的了——因为他毕竟还要去访问数据库，对数据库的压力还是非常大的。所以在真正的秒杀场景下，特别是像淘宝、京东这样的高并发场景下，仅仅使用乐观锁还是不够的。所以我们接下来还要继续对秒杀的这种方案进行优化，进一步地提高它的性能。

### 一人一单

#### 活动不能被一个人吃光

好同学们，在上一节课呢我们已经利用乐观锁的方式解决了优惠券秒杀时的一个库存超卖问题。这节课呢我们会给秒杀业务添加一个新的需求，叫做**一人一单**。

什么意思呢？同一个优惠券，一个用户只能下一单。

为什么要有这样一个需求呢？大家思考一下。像这样的秒杀券、特价券，他的优惠力度非常的大，那这种券的目的是什么？商家明明是赔本的，为什么要这么做啊？他的目的只有一个，就是利用这样的券，吸引更多的用户来我们店铺里去体验。体验了以后，如果口碑好，它是不是就可以被传播出去，引更多的用户来啊？这才是目的。

但是我们打开数据库一看，在当前情况下，我们订单表里面的这 100 张订单竟然都是同一个用户买的，也就是说这 100 个券全部被一个人买走了。那这不是黄牛是什么呀？等于做了个活动，就这一个人享受了，别人都享受不了，是不是就起不到宣传效果了？所以这不行，我们必须要求同一个用户对于同一个券只能下一单。

那怎么实现？思路非常简单：同一个用户只能下一单，也就是在这张表当中，同一个 `user_id` 和 `voucher_id` 是不是应该做到唯一。

我们不是给这个表加唯一主键吗？也不行，因为它已经有主键了，对不对？那我们的做法其实很简单，就是判断一下——当一个用户来了，我们判断一下当前用户 id（好比如说 5）、当前这个 voucherId（7）在这个库里是否存在。如果存在，证明这个用户是不是已经下过一单了，那我们是不是就不允许他下单就行了。所以简单来讲就是做一个查询，根据用户 id 和 voucherId 查询，如果存在了，就不让他下单。

回到 PPT 上分析一下这个思路。之前我们的思路是：来了以后直接判断秒杀有没有开始、库存是否充足，充足就直接让他减库存下单去了。现在不行，现在要多加一个判断，看一下这个用户是否已经下过单了。因此这块如果库存充足，我们要先去做一次查询，根据优惠券 id 和用户 id 要做一个联合的查询。如果根据这两个作为条件查询存在，那说明这个人已经下过单了，给他返回一个异常就行了；如果不存在，我们才允许他去做后续的动作。

> **易错点**：顺便把顺序也调一下——这个扣减库存动作我们放到后面去。要先判断、先下单，再去做扣减库存。因为你要是已经减过了再判断是不是失败了，那就太没有意义了。

#### 先查后判，为什么还是拦不住

代码上就是多插这么一段：

```java
// 一人一单：判断当前用户是否已经下过单
Long count = orderService.query(new OrderWrapper()
        .eq("user_id", userId)          // 条件一：user_id = 当前登录用户
        .eq("voucher_id", voucherId));  // 条件二：voucher_id = 当前优惠券
if (count != null && count > 0) {
    // 大于零证明至少有一条记录，说明这个用户已经下过单了
    return Result.fail("该用户已经购买过了");
}
```

这里不需要查出具体的数据，只要查 count 数量就可以了，所以 count 值我们用一个基本类型接收。如果这个 count 值它等于 1 或者讲大于零吧——我们不用判断等于 1，大于零就证明它的存在。至少有一条说明这个用户是不是至少下过一单，那不行，证明下过了，用户已经购买过了，不允许下单了，所以 return 一个 fail 告诉他说该用户已经购买过了。如果它小于等于零，证明他从来没买过，我们才允许他去创建订单，完成后续的动作。

单看这个逻辑是没毛病的。那我们重启，跑一遍测试。

这里先说明一下测试的构造：虽然我们设置的线程数是 200、发了 200 个请求，但是我们在发请求的时候，添加了一个请求头，在头里面添加了一个 `authorization`，也就是我们登录的那个 token。所以这 200 个请求用的是同一个 token，真正到了服务端识别出来的是同一个用户。那我们虽然发了 200 个请求，但同一个用户按照我们之前的业务需求应该是只能下一单对吧，所以现在我们就要测试一下，看看真正能下多少单。

我们运行一下。很快业务就执行完毕了，看报告，失败的比例还是挺高的。然后我们打开数据库——既然我们只希望下一单，那这 100 库存应该减掉一，还剩 99。刷新，没问题。我们看一下订单，十个单。

> **结论**：那说明什么？说明这个用户还是下了多单。大家看 `user_id`、`voucher_id` 是不是一模一样。我们刚才虽然在代码当中做了一人一单的业务逻辑的判断，但是问题依然存在；只是没有像以前那么严重了，以前是一个用户下了 100 单，现在下十单。

那问题出在哪？我们一起来分析一下。对于一人一单的判断：如果你是第一次来，那我拿这个查询结果一定是零，这个判断就不成立，是不是就往下走、去下单了？如果你不是第一次来，你这个地方查到的一定就是一个大于零的值，那这个时候往下走，他肯定走到这个地方，一判断大于零，是不是就失败了？所以说逻辑是正常的。

现在是怎么了呢？大家思考一下，其实这个问题跟我们库存判断的逻辑是不是一样的道理——先查询、再判断、判断完了去减。因为呢你是一个多线程并发操作，这个时候就会出现多个线程穿插执行的情况。我们当时是不是出现了库存超卖的问题？一人一单也是如此。

现在呢假设说我们的数据库里根本就没有订单，有 100 个线程都来执行这个逻辑，大家都来做查询，那查的是不是都是零？也就是说现在没有任何一个人去做插入，大家都是做查询。并发的情况下都是零，是不是都判断不成立、都往下走？于是就插入了 N 条订单。能理解这个意思吧？所以说还是并发安全问题，多线程来操作都往里面去插入，你这个判断就出现问题了。

#### 锁住查询、判断与下单

那针对这个问题，我们是不是已经有经验了呀？上节课解决我们的库存超卖，我们已经讲了加锁，要么乐观锁，要么用悲观锁。

但是乐观锁的方案我们之前讲过了，是在**更新**数据的时候去用的。但是我们这个地方是干什么？我们是在**插入**数据、新增。所以你不能说我判断一下我这数据有没有被修改过——没有办法判断，因为它根本不存在，对不对？所以我们要判断的是什么？我们这个地方要判断的是**是否存在**，而不是有没有被修改过。我们没有办法去用乐观锁方案了，我们只能是悲观方案。也就是说我们需要给这段代码加 `synchronized` 这样的锁。给谁加？从查询出订单、到判断订单、到新增订单，这一整段逻辑，给它加上悲观锁。

那我们怎么写？我们需要把这一段逻辑给它做一个封装，从查询开始封装（因为你最终要返回 result 嘛），一直到创建订单这个位置。

顺便把事务也挪过去。我们这个加锁的范围其实是更新数据库的一个范围，也就是说减库存操作和创建订单操作，而不是整个方法，因为前面这部分是查询，不用加锁。所以呢我们把 `@Transactional` 也放到这个方法上。那这样呢我们这个方法就是带上事务的，并且是线程安全的。

不过呢需要大家注意的是，**我不建议大家把 `synchronized` 加在方法上**。因为你在方法上锁，范围是什么？你锁的范围就变成了整个方法，而且锁的对象是 `this`，也就意味着不管是任何一个用户来了，是不是都要加这个锁，而且大家是同一把锁，也就意味着我的整个方法就是串行执行了。同学们，这个性能是不是很差了？

但是大家思考一下，所谓的一人一单，是同一个用户来了，我们才去判断他这个并发安全问题。如果不是同一用户啊，一个是张三，一个是李四，需不需要去加锁？不需要，大可各做各的就行了。

那因此呢，我认为这个地方加的锁不应该是这个 service、不应该是 `this`，而是什么？而是当前用户——我们可以**用用户 id 地去加锁**。这样的话，我们是不是可以去把锁的范围缩小了？也就是说同一个用户我加一把锁，不同用户加不同锁，也就是把锁定的资源范围减小了，对不对？

所以我们可以不用 `synchronized` 方法这种方法了，我们用 `synchronized` 关键字，然后在这里锁自己指定的对象——userId，userId 要转成字符串，把剩下的代码给它括起来，做个同步代码块就行了。

#### 锁对象要用 userId.intern()

不过呀，这里还要再给大家强调一点。这里的 userId 转字符串，我们期望的是什么？id 值一样的，它作为一把锁，对不对？

> **易错点**：但你要知道，你每一个请求来，这个 id 对象是不是都是一个全新的 id 对象？因此对象变了，锁就变了，这不行。我们要求的是值一样。

那 `toString()` 就能保证它是按照值来加锁的吗？我们看一下——其实在这个 `toString` 方法里面，底层调用的是 Long 的一个静态方法，在它的内部其实是 new 了一个字符串。那也就是说我们在刚才那个代码里边，每调一次 `toString`，是不是也是一个全新的字符串对象？这个锁对象是不是还会再变？哪怕你 id 是一样的，比如说你 id 一直是 5，但是你每次来虽然都是 5，但每次都是个全新的对象，还是不行。

那怎么办？所以这个地方呢我们要调用一个字符串的方法，叫做 `intern()`。这个 `intern` 方法的作用是返回字符串的规范表示。什么叫规范表示？就是去字符串常量池里去找一找，跟你值一样的那个字符串的地址返回给你，或者是它的引用发给你。那这样一来，如果你的值是 5，不管你有了多少个字符串，只要你的值是一样的，那最终返回的结果永远是一样。所以这样可以确保：当用户 id 的值一样时，锁就一样。这样呢我们就锁的是当前用户了，而不同的用户呢就不会被锁定，整体的锁定范围变小了，那性能就会得到很大的提升了。

```java
String lockKey = userId.toString().intern();  // 值相同 -> 锁对象相同
synchronized (lockKey) {
    // 查询出订单 -> 判断订单是否存在 -> 扣减库存 -> 创建订单
}
```

> **提示**：`String.intern()` 返回的是字符串在常量池中的规范表示（同一个值只对应一个引用）——这是把"值相同"翻译成"对象相同"的手段，也是这一步真正的考点。

#### 锁必须在事务提交之后释放

那到这里我们这个代码还没有结束，大家思考一下。我们现在呢是在方法内部来去加的锁。之前我们 `synchronized` 加在方法上的话，是不是对整个方法加锁？现在在方法内部加锁就会存在一个问题。

比方说我们现在这里开启事务开始执行，执行了之后呢，我们获取锁、获取了锁以后，我开始做这个查询；查询完了以后减库存、提交订单；提交订单完了以后，我先释放锁，才会提交事务，对不对？因为这个事务是被我们 Spring 管理的，所以这个事务的提交，它是在我们方法执行完以后由 Spring 做的。那么这个时候，其实锁在这个大括号结束了以后已经释放了。那同学们，锁释放了意味着其他线程是不是已经可以进来了？而此时因为事务尚未提交，如果有其他线程进来去查询订单的话，那刚刚新增的这个订单很有可能还没有写入数据库——因为你没提交——所以他再去查询的时候依然不存在，是不是有可能出现并发安全问题？

那么因此我们这个锁，它锁定的范围有点小了。它应该是把这整个函数锁起来，那这样一来，应该是事务提交之后我们再去释放锁，对不对？

那你说那怎么办呢？你这个 `synchronized` 加在方法内部，其实就不合适了，大家要注意这个范围了。那要加在哪里呢？我们把这段锁删掉，我们应该是加在这个函数的外面，把整个函数锁起来，在这个地方去加锁。那当然了，你在这个地方加锁的对象是 userId 嘛，所以说你需要在外边去获取这个用户 id，然后上锁，对吧，这么来做才是 OK 的。

你想啊，现在我们这么做是**先获取锁**，再进入 `createVoucherOrder` 这个函数，去完成这个下单操作。好，那等我这个函数执行完，说明什么？说明我这个新的订单是不是一定是已经写入数据库了，因为事务提交了嘛。那等我这块事务提交完，我再来释放锁。也就是说，我释放的这一刻，我可以确保数据库里已经有订单了。那此时再有其他线程来，他再去完成这个业务的时候，你去查这个订单，那订单肯定存在了，你就不会重复下单了，对不对？

> **结论**：所以呢，我们只有"先获取锁 → 提交事务 → 再释放锁"这样一个操作，才能确保我们这个操作是安全的。

#### 让事务生效：AopContext 拿代理对象

线程安全，是不是意味着这个业务现在就能够按照我们所想的方式实现了呢？诶，细心的同学可能就发现了，这里还存在一个事务的问题。

我们在这里呢是对当前的 `createVoucherOrder` 函数加了事务，没有给外边这个函数加。而外面这个函数在调用的时候是这样调用的——那这种调用其实是用 `this` 调的，对不对？就省去了一个 `this`。

那么这种调用的话呢，这个 `this` 拿的是谁呢？是当前的这个 `VoucherOrderServiceImpl` 对象，而不是它的代理对象。我们知道事务要想生效，其实是因为我们 Spring 对当前这个类做了动态代理，拿到了他的代理对象，用它来做的事务处理。那现在你这个 `this` 其实指向的是非代理对象，也就是目标对象，所以它是没有事务功能的，对不对？这个是我们讲 Spring 事务失效的几种可能性之一嘛，那这就是一种可能性。

怎么解决？其实在这个地方的话，我们也需要去拿到这个事务代理的对象才可以。这里呢我们可以借助一个 API 啊，叫做 `AopContext`，利用它里面的 `currentProxy` 方法，那么就能够拿到当前对象的代理对象了，我们称之为 proxy。那当前对象是谁呀？其实就是这个 `IVoucherOrderService` 这个接口，是它的一个代理对象。所以说呢我们这里就用这个来接收就可以了，然后呢给他做个强转——它返回的是 `Object`，但我们知道肯定是这个玩意儿对吧，那我们就拿到了当前代理对象了。

```java
// 拿到当前对象的代理对象（与事务有关的那个代理）
IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
proxy.createVoucherOrder(voucherId);   // 用代理对象去调，而不是 this
```

这个时候呢，我们用代理对象来去调这个 `createVoucherOrder` 函数，而不是用 `this`，那么你就会被 Spring 管理了，因为这个代理上是有 Spring 创建的嘛，所以它是带有事务的一个函数。那现在不生效的原因是什么呢？因为这个接口里是不存在这个函数的，我们现在是在实现类里做的对吧，所以说你把这个函数也给它创建一下，创建到我们的 `IVoucherOrderService` 里。那现在接口里有了，我们才能够基于接口去调用嘛，那现在我们这个事务就能够生效了。

当然了，你要这么去做，还需要做两件事啊。

首先是我们要添加一个依赖。因为这么做了以后，它其实底层会用一个 aspectj 的依赖，所以我们需要把 aspectj 引进来啊，这是一种动态代理的模式嘛。

然后还有启动类要添加一个注解去暴露这个代理对象。`@EnableAspectJAutoProxy` 里面有一个叫 `exposeProxy`，这个值默认是 `false`。大家看到没有？暴露这个代理对象默认是不暴露的，不暴露的话，你去获取是获取不到的，这个地方要把它改成 `true` 就能暴露了。那我们再回到当前这个实现类这里，一旦暴露了以后，你这样就能够拿到代理对象了。什么代理对象啊？其实就是跟事务有关的代理对象，然后再去掉就没问题了。

> **结论**：现在呢我们就能确保这个事务生效了，并且是获取锁之后才去创建的事务，事务提交了以后我才会释放锁，这样就会避免刚才我们说的、因为事务没提交就释放锁的这种安全问题。这两个点是大家需要注意的：释放锁的时机，以及这个事务是否生效。

#### 复测：库存 99，订单 1

好，现在我们把这个业务改造完毕，重启一下，然后去做一个测试。在重启的过程当中我们先去把数据库数据清理一下，打开数据库，把订单清空，然后呢库存再次改成 100。

然后我们去做 JMeter 测试，先清空所有的数据，然后运行。很快运行完毕。聚合报告里面失败的比例 **99.5%**，可以说非常的高。然后呢我们去看一下数据库——我们期望这里是只减一个，99，没问题；我们期望订单只有一个，没问题。

好，到这儿我们是不是就解决了一人一单的问题了？解决方案同样是加锁，那这次我们用的是悲观锁。只不过呢我们采用了啊一种特殊的锁对象，也就是用户 id，来减小锁资源锁定的范围，从而呢在一定程度上提高了它的性能。

### 集群下的锁失效

#### 用两份实例模拟一个集群

刚才呢我们已经演示了秒杀下单的一人一单的功能，并且基于 `synchronized` 的锁解决了一人一单的并发安全问题。不过呀，这种解决方案啊，它仅仅适合在单机情况下使用。我们的项目虽然是一个单体项目，但是我们将来可能会面临非常高的并发，这个时候呢我们就会把这一个项目部署到多个机器，从而形成一个负载均衡的集群。而在集群模式下，我们的 `synchronized` 就会受到挑战了啊，就会出现一些问题。所以呢这节课我们就会来演示一下，在集群模式下它所存在的问题，以及问题产生的原因。

那在这里呢我们要去模拟一个集群。怎么办呢？我们可以利用 IDEA 提供的功能，去把我们这个项目启动两次，就是把 App 给我们这个项目去启动两次，端口设置成不一样的，比如说 8081 和 8082，从而模拟一个集群效果。当然你也可以启动三台四台啊，我们以两台为例。

怎么做呢？在 IDEA 里找到我们之前的一个项目启动项，我们这个地方呢按一下 `Ctrl+D`，它会弹出一个新的窗口，作用呢就是把当前的这个启动项拷贝了一份——注意啊，这**是一个新的启动项**。每创建一个新的启动项、新的启动配置，那么将来的 Spring Boot 或者讲 IDEA 底层就会给我们整两台 Tomcat，分别启动，就可以模拟两台机器了。

但是呢如果说你直接这么启动的话，将来端口就会有冲突。所以在这里我们需要配置一下这个 JVM 参数，把端口给覆盖掉：通过一个 `-Dserver.port=8082`，通过这个来去覆盖我们 application.yml 里面配的那个端口，然后点击 Apply。大家就会发现这里会多出来一个，对不对？那现在呢我们把这两个给它重启，那么现在我们就形成了一个集群了，两个节点形成的集群。如果参考这种方式你继续去复制，就会出现三个节点集群、四个节点集群，对不对？虽然少，但是也是一个集群。

那当然，其中两台以后呢，将来我们还需要利用 Nginx 对它做一个负载均衡、反向代理。这样一来的话，当用户去访问 Nginx 的时候，其实就是在访问这两台服务器，就模拟了一个真实将来部署的一个环境了。

#### nginx 做反向代理与负载均衡

我们还要做一件事情：回到 Nginx，我们要利用 Nginx 对这两个节点去做一个反向代理、负载均衡。我们需要去修改 Nginx 目录下的 config 目录下的 `nginx.conf` 文件来实现这个负载均衡。

这个文件里边呢，其实我提前已经写好了一些配置。现在呢我们 Nginx 监听的是 8080 这个端口，然后监听到 8080 端口了以后，监听的路径是 `/api`，监听到它了以后会反向代理到这个 upstream。这个 upstream 呢在下面写着，它其实就是一个负载均衡的多个节点，上面有个 8081，下面这个注释我们把它打开，8082。当然了，如果你想要更多，你就继续复制就行了，然后改对应的 IP 和端口。

```nginx
upstream backend {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
}

server {
    listen 8080;

    location /api {
        proxy_pass http://backend;
    }
}
```

那它就能够实现什么呢？当你访问 Nginx 的那一刻，它就会反向代理到这两个节点上去，默认采用的就是轮询的负载均衡规则。那这样他们两个就都能够被访问到了。好，改完配置以后需要重新加载，通过 `nginx -s reload` 就能够重新加载我们 Nginx 的配置文件，那它就生效了。

那怎么知道我们的负载均衡生效了呢？我们先把日志清空一下，然后打开浏览器。我提前准备好了一个接口：访问的是 8080/api。注意这个端口——8081 和 8082 才是我们这两台服务，8080 是我们的 Nginx。Nginx 监听 8080 以后呢，就把 `/api` 这个路径代理到 upstream，upstream 呢就会负载均衡到 8081 和 8082，所以说我们访问 8080，其实就是在访问这两个节点。

我访问的是 voucher/list，就是查询优惠券这个接口。我们去刷新一次，发起了一次请求，然后再刷新一次，又发起了一次请求。然后打开 IDEA，大家可以看到在 8081 和 8082 这两个节点上是不是各有一次请求？说明现在这两个节点是不是都被访问到了，也就是说他们其实已经有了这样的一个负载均衡的效果。

#### 断点里两个请求都进来了

接下来呢我们就去测试优惠券下单。我们打开数据库，现在这里其实是有一条有效订单的，我们把这个订单先给它干掉；然后呢这边是库存，库存现在是 99，我们也给它恢复成 100。

好，接下来我们去做测试了。我们先打个断点——找到我们刚才这个实现类，在我们加锁的地方打，注意看 `synchronized` 加锁，现在我们在这打断点。我们让同一个用户发起两次请求。那理论上讲，同一个用户这里是不是会有一个并发锁的控制，只能有一个进来？

我们打开 PostMan，在这个地方我提前准备好了两个请求。这里有一个用户的这个 authorization 头，然后呢这边我们也用这个，那也就是说现在我们这俩是不是同一个用户？同一个用户。同一个优惠券的 id 是 7。那现在呢我们用它来发两个请求——大家注意到啊，我这两个接口都是访问的 `8080/api/voucher-order/seckill?id=7`，就是秒杀下单那个接口，然后呢都是这个 id 为 7 的优惠券，然后呢用户是同一个用户。

好，我们去发这个请求，然后第二个也发个请求。现在是不是一下发了两个请求？那大家发现没有，现在这两边是不是都进到这个断点里了？

> **易错点**：同学们，我这儿可是有锁。现在用户 id 为 5，这边这个哥们用户 id 同样是 5，是不是两个服务都收到请求了？这是因为负载均衡对不对？然后他们两个的用户 id 是一样的，竟然没锁住，都进来了。

那同学们如果都进来了，这就又有问题了。我如果放行，他们此时去做查询会造成什么后果？我们在查询这个位置打断点，是不是去查的时候得到这个结果都是 count 为零？你看，是不是都是零。那么这两个线程都进来了、都查到 count 为零，然后我如果再都放行，这俩是不是都会去扣库存、都会去创建订单？放行。

我们刷新一下订单表——两个订单，是不是两个？那这就说明了什么？同学们，这就说明了我们又一次出现了并发的安全问题。在集群模式下，虽然我们用了 `synchronized`，发现锁住了没有？没有锁住吧，这俩都进去了。

#### 为什么 JVM 的锁跨不过进程

为什么产生了问题？我们回到 PPT 上看一下。

先来看在正常情况下我们之前是怎么做的。之前我们是不是单体项目？我们假设把这个灰色的框当成我们的一个单体项目，启动以后，其中有一个线程来查询订单；然后这个时候呢查完了以后，他去判断一下这个订单是否存在。如果说不存在，他就会去插入这个新订单。他执行完了以后，另外一个线程来查询，查询完了以后，因为这边已经插入了，所以说这个查询他再去判断的时候肯定是存在的，是不是就报错了，无法插入。这是正常串行执行的情况。

那现在呢在多线程并发的情况下，在没有加锁的情况下，而他不可能每一次都是这么正常的串行执行，它可能会出现交叉执行的情况：

```text
      线程-1                        线程-2
        │                             │
     查询订单                          │
        │ …… 发现不存在                 │
        ├──────────────┐               │
        │              │            查询订单
        │              │               │ …… 也是不存在
        │              ├───────────────┤
        │              │               │
     插入新订单                    插入新订单
        │                             │
        └────► 订单被插入了两次 ◄───────┘
                        │
                并发安全问题！
```

（读图：两个线程的"查询"与"插入"交叉在一起，两个查询都落在了插入之前，于是两笔插入都成立。）

一旦出现交叉执行：线程一查询订单，发现不存在；线程二也来查询，也是不存在；好，紧接着线程一和线程二都去插入新订单，那么这个订单是不是就被插入了两次——这就是线程安全问题产生的原因。

后来我们干了什么事？后来我们加了锁，对不对。也就是一个线程来了以后，必须先获取锁，拿到锁了以后才可以去执行查询订单这个动作，还有判断的动作。假如说他拿到以后去执行，成功了，然后去插入新订单，然后呢去释放锁。此时另外一个线程他也想要来获取锁，但是因为这把锁在这一时刻被线程一拿到了，所以线程二是拿不到的，他会失败。失败会干什么？根据 `synchronized` 的原理，他会等待锁释放，等了很长很长时间，这边释放了，他终于是不是可以获取成功了，然后才能执行。那你这个时候再去执行查询，那边已经插入了，你再来查是不是已经存在了，那么这个地方就会报错了，不会插入。是不是就确保了串行执行了啊——这是我们理想的情况。

那现在发生了什么呢？现在我们不再是一台机器，是多台。

大家要知道的是，在当前这一个 JVM 的内部，锁的原理是什么？其实是在我们 JVM 内部维护了一个**锁的监视器对象**。那么这个监视器对象我们用的什么？用的就是 userId 的那个字符串，是不是在我们的常量池里边。那么在这个 JVM 内部，它维护了这一个池子。那当 id 相同的情况下，他们是不是永远是同一把锁？也就是锁的监视器是同一个。所以说呢无论是线程一也好，还是线程二也好，他们来获取锁的时候，当线程一来获取锁的时候，那么锁计时器就会记录线程一的这个名称，在这里。那么线程二再来获取的时候呢，他一看说不行，这已经有了，那他还能获取吗？不能，就不能了。这就是它的一个原理。

但是呢当我们做集群部署的时候，一个新的部署就意味着这是一个全新的 Tomcat，那就意味着这是一个全新的 JVM，也就是说有两套 JVM。那两个 JVM 是不是有各自的堆栈啊、各种方法区之类的？所以说呢我们的 JVM2，它也会有自己的常量池啊。所以呢他用 userId 作为锁的时候，它的监视器对象啊，就会有一个全新的锁监视器了，跟 JVM1 的那个监视器是不是同一个呀？

那现在当我们的线程三来获取锁的时候，他走的是自己的这个监视器，那这个监视器显然是空的呀——他那边已经有了，在这边没有——所以呢他也能获取成功，对不对？当然了，线程四肯定还是失败的，这没问题。

```text
        单体：一个 JVM                    集群：两个 JVM
  ┌───────────────────────────┐    ┌───────────────────────────┐
  │  字符串常量池              │    │  字符串常量池              │
  │    "5" ──► 锁监视器 M      │    │    "5" ──► 锁监视器 M'     │
  └─────────────▲─────────────┘    └─────────────▲─────────────┘
                │                                │
        线程一 拿到 ✓                   线程三 拿到 ✓
        线程二 等待 ✓                   线程四 等待 ✓
                                            ↑
                             本该被挡住，却被放行了
```

（读图：左右两个 JVM 各有自己的字符串常量池，userId 的值都是 5，但"5"对应的锁监视器根本不是同一个对象，于是线程一和线程三在彼此看不见的情况下都拿到了锁。）

也就是说，我们这个 `synchronized` 在当前 JVM 的内部可以监视到这些线程实现互斥；但是呢如果你有多个 JVM，就会有多个锁监视器，是不是每一个 JVM 内部都会有一个线程是成功的？如果我们将来集群比如说部署了十台、二十台，也就意味着并行的至少会有十个线程是同时在运行的，那不就又一次出现了线程安全问题了？

> **结论**：所以产生安全问题的原因是什么？在集群模式下，或者有一些是在分布式的系统下，有多个 JVM 的存在，每个 JVM 里都有自己的锁，导致了每一个锁都可以有一个线程获取，于是就出现了并行运行，那么就可能出现安全问题。

那要想解决这个问题，我们必须得想办法——让多个 JVM 只能使用同一把锁。对不对？那么这样的锁可不是我们 JVM 里面提供的，需要我们自己去实现。

在下节课我们就来讲一讲这种跨 JVM 的、或者讲跨进程的锁。下节课我们再见。

## 集群模式下挡不住的并发：用 Redis 实现一把分布式锁
> 对应块：BLK16 | 覆盖分集：P56-P59 | 块标题（分集名）：《实战篇-09.分布式锁-基本原理和不同实现方式对》

### synchronized 出了集群就失效了

上节课我们演示过一件事：在集群模式下，`synchronized` 加的锁失效了。

原因其实很直白。`synchronized` 依赖的是 JVM 内部的锁监视器，它只能保证**单个 JVM 内部**多个线程之间的互斥。有几个 JVM 就有几个锁监视器，大家各锁各的，互不相识。

```text
        JVM 1                          JVM 2
  ┌───────────────┐              ┌───────────────┐
  │ 线程1 ──┐     │              │     ┌── 线程3 │
  │ 线程2 ──┴─> 锁监视器          │ 锁监视器 <─┴── 线程4 │
  └───────────────┘              └───────────────┘
        一把锁                          又一把锁
   只在本 JVM 内有效                只在本 JVM 内有效

  两个进程同时进来 → 两把锁各放行一个线程 → 互斥根本没发生
```

读图：两个 JVM 各有一把自己的锁，线程1 和线程3 眼里对方根本不存在，所以它们会同时"拿到锁"、同时执行业务，一人一单就穿了。

那怎么解决？既然 JVM 内部的锁监视器管不了跨进程，那就别再用它了。我们必须**让多个 JVM 都去盯着同一个监视器**——一个在 JVM 之外、所有 JVM 进程都能看见的东西。

### 分布式锁的原理：让所有进程盯着同一把锁

```text
        JVM 1                JVM 2                JVM 3
      ┌────────┐          ┌────────┐          ┌────────┐
      │ 线程1  │          │ 线程2  │          │ 线程4  │
      └────┬───┘          └───┬────┘          └───┬────┘
           └──────────────────┼──────────────────┘
                              ↓
                   ┌─────────────────────────┐
                   │    外部锁监视器           │
                   │  key: lock:order:5      │
                   │  value: 线程标识         │
                   └─────────────────────────┘
                              ↑
        无论哪个 JVM 的线程，都来这里抢；只有一个能抢到
```

读图：三个 JVM 的线程最终都指向同一个外部监视器，谁先抢到谁持有，其他线程一律失败并等待。

我们拿下单这个场景完整走一遍。假设线程1 先拿到锁，它开始执行业务——查一下订单存不存在，不存在，它是第一个来的，肯定不存在，那就插入一条新订单。业务做完释放锁。

线程3 这时来抢锁。它是在 JVM 2 内部的线程，跟线程1 用的是同一个监视器，而监视器里已经被线程1 持有了，所以它必然获取失败。失败了就只能等待，不停地等。

等线程1 干完活把锁删掉，线程3 终于拿到锁。它去查订单，这时候线程1 已经插进去了，一定能查到。查到就代表订单存在，存在就不能再插，于是报错。

问题就被挡在业务逻辑内部了，一人一单守住了。而且不管来的是 JVM 内部的线程2，还是另一个 JVM 的线程4，只要线程1 持着锁，它们去抢全都是失败、全都要阻塞等待，跟线程3 一模一样。

> **定义**：分布式锁就是满足"多进程可见"（首要条件，一定要所有 JVM 都看得见）+"互斥"（只有一个线程能拿到锁）的锁。

### 一个合格的分布式锁要满足什么

上面那两个是核心，除此之外还有三个基本特性，加起来一共五个。

**多进程可见。** 这一条其实非常容易做到。所谓多进程可见，就是多个 JVM 都能看到它。用 Redis 行不行？行，只要在 JVM 外部，基本都能做到。用 MySQL 行不行？也行，它同样是所有 JVM 进程都能看得见的。所以这条基本不用操心。

**互斥。** 难点在这儿。不管谁来访问，只能有一个人拿到，其他人都得失败。

**高可用。** 大多数情况下我来获取锁，你都应该是成功的。你不能说获取锁这个动作经常出问题，结果业务也跟着出问题，那就得不偿失了。

**高并发 / 高性能。** 加锁本身就会影响业务性能——加了锁以后线程变成串行执行，性能是下降的。如果获取锁这个动作本身还很慢，那不就雪上加霜了吗？所以获取锁这个动作必须做到高性能。

**安全性。** 获取锁的时候要能扛住异常情况。比如我拿到锁、还没释放、我挂了怎么办？将来这把锁怎么办？会不会产生死锁？这些都是要考虑的。

除了这五个核心的，还有一些**功能性特征**，你可以满足也可以不满足：可不可重入，获取锁时是阻塞的还是非阻塞的，是公平锁还是非公平锁等等。这些不是重点，我们不展开讨论。

我们核心要对比的是：不同的分布式锁实现方案，它们**是怎么实现互斥的**、**互斥逻辑有什么差异**、**怎么保证高可用和高性能**、**安全性如何**。

### 三种实现方案的差异

实现分布式锁的种类很多，但比较常见的就是这么三大类：基于 MySQL 这样的数据库，基于 Redis 这样的缓存，以及基于 ZooKeeper。它们在互斥、可用性、性能、安全性这四个维度上，表现差别很大。

#### 基于 MySQL：白拿数据库的事务机制

互斥怎么来的？MySQL 或者其他数据库都具备**事务机制**。在执行写操作的时候，数据库会自动帮你分配一个互斥的锁，事务之间自然就是互斥的，只有一个能执行。

所以完全可以白嫖这个特性：业务执行前，先去 MySQL 里申请一把锁，然后执行我们的业务，业务执行完提交事务，锁就释放了。业务抛异常呢？事务会自动回滚，锁也跟着释放了。获取和释放都非常省事。

**可用性**取决于 MySQL 本身的可用性。MySQL 支持主从模式，所以可用性还是不错的。

**性能**就完全受限于 MySQL 的性能了。MySQL 的性能跟 Redis 相比肯定还是有差距的，所以它的性能属于比较一般，不能说好，但也不是很差。

**安全性**其实是可以的。系统一旦崩溃，连接断开以后，锁会自动释放，数据也会回滚，这个问题不用考虑。

#### 基于 Redis：SETNX 天然互斥

这个方式我们以前介绍过，用的就是 `SETNX` 这个互斥命令。

`SETNX` 的意思是，往 Redis 里 set 一个数据的时候，**只有数据不存在时才能 set 成功**；如果已经存在了，那就失败。如果有无数个线程都来执行 `SETNX`，并且 key 是同一个 key，那肯定只能有一个人成功，其他人都失败——互斥就实现了。

将来要释放锁也很简单，只要把这个 key 删了，其他人就能获取了。

**可用性**不用担心，Redis 不仅仅只是主从，它还支持集群模式，可用性是能够得到保障的。

**性能**更不用讲了，Redis 的性能是远远好于 MySQL 的，所以它实现分布式锁的性能也是非常好的。

**安全性**就不行了。我们 `SETNX` 成功后，一旦我的服务出现故障，锁能不能得到释放？不行。因为 `SETNX` 只是在 Redis 里设置了一个 key，服务宕机了，将来没有人去执行删除的动作，这个 key 就一直在那里，锁永远得不到释放，其他人也都拿不到锁——这就产生了类似死锁的效果。

为了应对这个问题，我们必须在 `SETNX` 获取锁的时候想个办法：将来一旦出现故障，锁也能自动释放。办法就是利用 **Redis 的 key 过期机制**——在 `SETNX` 获取锁的同时给它加上一个过期时间，将来一旦服务出现故障、没人手动释放，到期以后锁也会自动释放。

不过这个过期时间设置多长是个问题：太长的话，锁的无效等待时间会比较多；太短的话，万一业务还没执行完锁就释放了。所以这种方式做安全性能保证是可以的，但还需要去完善。具体怎么解决，我们在后面讲。

#### 基于 ZooKeeper：有序节点定胜负

ZooKeeper 实现锁，用的是它内部的数据节点机制。ZooKeeper 里可以创建数据节点，而节点具备**唯一性**和**有序性**，另外还可以创建**临时节点**。

怎么用有序性实现互斥呢？很多线程都去 ZooKeeper 创建节点，这样每一个节点的 ID 就是单调递增的。我们约定：**ID 最小的那个算获取锁成功**。最小的是不是只有一个？那不就实现互斥了。

当然你也可以利用唯一性：大家都去创建同名节点，也只有一个人能创建成功。一般情况下我们还是用有序性来做。

释放锁也很简单：将来你把节点删掉，你就不是最小的了，另外一个人自然变成最小的，它就获得锁了。

**可用性**也不错，因为 ZooKeeper 天生就是支持集群的。

**性能**相对要差一些。因为 ZooKeeper 的集群强调**强一致性**，这种强一致性会导致主从之间做数据同步，去消耗一定的时间。

**安全性**做得很好。因为它创建的往往就是临时节点，一旦出现故障，比如服务宕机、连接断开，节点会自动释放掉，锁也就等于释放了，这块儿不用去考虑。

#### 四个维度拉个表

| 方案 | 互斥原理 | 可用性 | 性能 | 安全性 |
| --- | --- | --- | --- | --- |
| MySQL | 借助事务机制，执行写操作时数据库自动加互斥锁；提交事务即释放，异常自动回滚 | 依赖 MySQL 本身，支持主从，可用性不错 | 受限于 MySQL 性能，比 Redis 有差距，比较一般 | 好：系统崩溃、连接断开后锁自动释放，数据回滚 |
| Redis | `SETNX` 只有 key 不存在时才设置成功，天然互斥；删 key 释放 | 不止主从，还支持集群模式，可靠有保障 | 远好于 MySQL，非常好 | 最弱：`SETNX` 写入的 key 不会自己消失，只能靠 key 过期机制兜底 |
| ZooKeeper | 借助数据节点机制，节点唯一、有序、可临时创建；约定序号最小者持锁 | 天生支持集群，可用性很好 | 强一致性导致主从同步耗时间，相对比 Redis 差 | 很好：临时节点在连接断开后自动删除 |

> **结论**：从安全性角度看，ZooKeeper 和 MySQL 的原理基本类似，都比较好，比 Redis 要强一些——Redis 只能利用超时机制来兜底；但从可用性和性能上看，Redis 非常好。所以这个教程我们选择基于 Redis 来实现分布式锁。MySQL 和 ZooKeeper 的其他实现方式，大家有兴趣可以自己去网上看一看原理。

### Redis 方案的完整实现思路

思路分析完了，接下来动手实现。实现一个分布式锁，肯定要实现两个基本方法：**获取锁**和**释放锁**。

#### 获取与释放的最小闭环

先在客户端里试一下。我们打开一个客户端，执行：

```text
SETNX lock thread1
```

返回 1，说明设置成功了。现在假如再有一个人来执行同样的 `SETNX`，返回的是 0，也就是说同一个锁只有一个人能执行，其他人执行不了——这就是互斥的效果。

释放锁就一个 `DEL`：

```text
DEL lock
```

删掉之后你再执行 `SETNX`，大家发现就成功了。所以获取锁是 `SETNX`，释放锁是 `DEL`，这就是最基本的方法。

不过这里要注意，这是**理想情况**：我获取到锁，执行 `SETNX` 成功，然后执行业务，最后 `DEL` 释放锁。但你思考一下，如果我拿到锁之后服务就宕机了，还没来得及执行 `DEL`，整个服务就没了——这个释放锁的动作永远得不到执行，锁永远存在，其他线程也进不来，整个业务就处于死锁状态。

#### 服务宕机了，谁来帮我删锁

为了解决这个问题，我们要给它加一个**超时释放机制**：如果服务宕机了，长时间没人操作，就让那个锁自动过期。讲白了就是在添加锁的时候给它添加一个超时时间——这就是所谓的超时释放，用的命令是 `EXPIRE`。一旦给锁加上了过期时间，到期就会被自动删除。

```text
SETNX lock thread1
EXPIRE lock 5
TTL lock        # 返回 2
TTL lock        # 返回 1
TTL lock        # key 已经不存在了
```

你看，过期时间到了，`lock` 就被自动删除了。这就解决了异常情况下锁的释放问题——服务挂了没关系，我们有超时自动释放。

> **注意**：这个时间不能设置太短。万一业务还没执行完你就释放了，是不是也有问题？所以一般是稍微长一点，比如十秒钟，比你的实际业务执行时间要长一点。

#### 两步之间，还藏着一个窗口

加超时时间是为了避免服务宕机导致锁无法释放。但同学们再思考一下，有没有这样一种可能性：**我执行 `SETNX` 成功了，还没来得及执行 `EXPIRE`，就已经宕机了**。宕机发生在这两个命令之间，是不是依然没有办法释放？

所以说我们必须保证 `SETNX` 获取锁的动作和添加过期时间这两者，**要么都成功，要么都失败，要具备原子性**。

那怎么做？看一下 Redis 提供的 `SET` 命令，它可以跟上很多参数：

```text
HELP SET
```

可以看到除了可以指定 key 和 value 以外，还可以通过 `EX` 指定一个以秒为单位的过期时间，`PX` 是以毫秒为单位；后面还可以跟上 `NX`，它跟 `SETNX` 效果一样，也就是当数据不存在的时候才能 set，存在就不能 set。

于是我们可以在一条 `SET` 命令里，通过设置参数，同时实现 `NX` 和过期时间的效果，这就是一个原子操作了：

```text
SET lock thread1 NX EX 10    # 返回 OK
SET lock thread1 NX EX 10    # 返回 nil
TTL lock                     # 返回 -2，证明已经过期
SET lock thread1 NX EX 10    # 过期之后再 set，又返回 OK 了
```

看到没有，重复的 set 就没有效果了；因为加了 `EX` 所以有过期时间；一旦过期，再有人来 set 又可以成功了。所以利用这条命令，我们就把 `NX` + `EX` 变成了一个原子操作。

所以最终我们不是分两步来做，而是把两步合成一步：

```text
获取锁：SET lock 线程标识 NX EX <过期时间>
释放锁：DEL lock
```

#### 为什么选非阻塞

到这儿其实已经能实现分布式锁了，但还有一个小问题要讨论：**获取锁的结果要么成功要么失败，那失败了以后我们该怎么做？**

在 JUC 里提供的锁其实有两种机制：一种是失败了它会阻塞等待，等到有人释放锁为止，也就是说是一种**阻塞式**的获取；还有一种就是**非阻塞式**的获取，我尝试获取锁，如果获取失败了，我立即结束返回一个结果，而不是一直尝试、一直等待。

我们这里会实现一个**非阻塞机制**。原因有两个：第一，阻塞式对于 CPU 是有一定浪费的；第二，阻塞式实现起来相对会麻烦一点。

所以我们用一种非阻塞式的方式：这个操作只执行一次，根据它反馈的结果，如果成功就返回 `true`，如果失败就返回 `false`，然后我就不再尝试了。

整个流程总结一下就是：一个线程来了以后，首先尝试获取锁，执行的命令就是 `SET key value NX EX <时间>`；执行完之后我们看返回值，只有两种结果，一种 `OK`，一种 `nil`。如果是 `nil`，代表失败，说明在你之前已经有人执行过这个操作了，我们认为获取锁失败；如果是 `OK`，证明获取锁成功，他就可以去执行自己的业务逻辑。业务执行完，我们再去执行释放锁操作，执行的就是 `DEL`。

同时因为我们添加了这个 `EX`，所以在获取锁成功以后、在这一段执行业务的时间里，如果出现了服务宕机，锁会自动释放，从而避免了死锁的发生。

### 动手实现第一版 SimpleRedisLock

这一版是初级版本，后续我们还会继续升级和拓展，让它变得更加完善。

#### 先把锁接口定出来

需求是让我们定义一个类，实现一个锁接口，利用 Redis 实现分布式锁功能。这个接口其实就是一个标准的锁接口 `ILock`，里面有两个方法：一个是 `tryLock`，一个是 `unlock`，也就是获取锁和释放锁。

```java
public interface ILock {

    Boolean tryLock(String name, Long timeoutSec);

    Boolean unlock(String name);
}
```

为什么这个方法叫**尝试**获取锁？因为我们采用的是非阻塞模式：我只试过一次，如果成功了返回 `true` 代表成功；如果失败了就返回 `false` 代表失败，我不会去不断重试，也不会阻塞等待。

另外在获取锁的时候还需要指定一个超时时间 `timeoutSec`。它其实就是我们前面 `SET ... EX` 里面的那个 `EX` 时间。

`unlock` 我已经给大家实现好了，接下来就是去定义一个类，起个名字比如 `SimpleRedisLock`，让它去实现 `ILock`，把这两个方法填上。

#### 搭好类的骨架

这两个方法的逻辑其实一点都不难：获取锁就是 `SET` 加上 `NX` 和 `EX`，释放锁就是 `DEL`。但是不管是哪一个操作，你都需要拿到 `StringRedisTemplate`，因为只有拿到了它我们才能执行这些 Redis 操作。

```java
public class SimpleRedisLock implements ILock {

    private static final String KEY_PREFIX = "lock:";

    private final StringRedisTemplate stringRedisTemplate;

    public SimpleRedisLock(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }
}
```

两个构造参数是要用户传递给我们的，所以需要用构造函数给它赋值；`KEY_PREFIX` 是常量，不用管。

然后这里有个重点要提醒你：**锁的名称你不能在这儿给它写死**。

你要是写死了，就意味着不管任何一个业务来获取锁的时候，用的都是同一把锁，这肯定是不对的。我们希望的是不同的业务有不同的锁，所以锁的名称应该跟业务有关，由使用的人反馈或者说传递给我们。

当然你也可以给锁加一个统一前缀，让它看起来更专业一点，比如我们定义一个 `static final` 的 `KEY_PREFIX`，值就叫 `lock:`。

#### tryLock：把 SET NX EX 翻成代码

`tryLock` 的业务逻辑这块儿其实没有任何难度，直接调用 `StringRedisTemplate` 的 `opsForValue()`——`value` 就是字符串操作，`SET` 就是字符串操作。

```java
@Override
public Boolean tryLock(String name, Long timeoutSec) {
    // 1. 构造锁的 key：统一前缀 + 业务名称
    String key = KEY_PREFIX + name;

    // 2. 构造 value：记录是哪个线程拿到锁了
    Long threadId = Thread.currentThread().getId();
    String threadIdentifier = threadId + "";

    // 3. 执行 SET key value NX EX timeoutSec
    Boolean success = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, threadIdentifier, timeoutSec, TimeUnit.SECONDS);

    return Boolean.TRUE.equals(success);
}
```

这里的关键点有这么几个。

**第一，NX 怎么来的。** 因为要同时有 `NX` 和 `EX`，所以必须使用 `setIfAbsent`。这个名字很直白——`absent` 就是缺席，只有不存在的时候我才执行，那不就是 `NX` 吗。

**第二，EX 怎么来的。** `setIfAbsent` 这个重载方法后面要传时间参数，最后一个单位写 `TimeUnit.SECONDS` 就是秒，直接把 `timeoutSec` 传进去就行。

**第三，key 和 value 分别放什么。** key 前面说过了，用前缀拼接上业务名称，两者拼接就行。value 就比较特殊了，它要加上线程的标识，告诉我说是哪个线程拿到锁了。我们测试的时候用的是线程 id，比如 `thread1`、`31` 这样的。你在这里最好带上一个标识。

获取当前线程标识很简单，直接通过 `Thread.currentThread()` 然后去 `get`。这里你可以 `getName()` 代表线程名称，当然你也可以 `getId()`——这个就是现成的唯一的 id，一个 JVM 内部这些线程的 id 一般是不会重复的。我们这里就用线程 id。

**第四，返回值的处理，这里有个坑。**

我们业务逻辑里执行 `SET NX EX` 之后，返回值是 `OK` 成功、`nil` 失败。但我们这个接口要求返回布尔值，而事实上 Spring 在给我们封装这个函数的时候，它已经帮我们对结果做了判断，你不用自己去判断 `OK` 和 `nil` 了，它直接用布尔值返回了。

但是你注意了，**你直接返回这里会有一个自动拆箱的过程**。这里是个包装类，返回类型是基本类型，所以它有个拆箱的过程。而只要有自动拆箱，就可能会有安全风险：万一这个哥们儿是个 `null` 呢？你一拆箱是不是就空指针了？

所以我建议大家在这儿调用它的一个 `equals` 去做一个判断，用一个常量去调用：`Boolean.TRUE.equals(success)`。因为这是个常量，它肯定不是 `null`。利用它的 `equals` 判断——如果你是 `true`，我这就是返回 `true`；如果你是 `false`，我肯定返回 `false`；如果你是 `null`，返回的也是 `false`。这样就可以避免空指针的风险了。

> **易错点**：做自动拆箱的时候，一定要注意空指针的可能性，做好这种判断。

#### unlock：DEL 就够了

释放锁的动作更简单了，我们当时说的不就是 `DEL` 就完了吗。直接调用 `stringRedisTemplate.opsForValue().delete(key)`，给我一个 key 就行了，而这个 key 我们可以跟前面一样，用前缀加上锁名。

```java
@Override
public Boolean unlock(String name) {
    String key = KEY_PREFIX + name;
    stringRedisTemplate.opsForValue().delete(key);
    return true;
}
```

> **提示**：这里先记一笔——这一版释放锁是"上来就删"，不管这个锁还在不在、是不是自己的，统统删掉。前面存进去的那个线程标识在这一版里其实还没被用上，先别急，后面马上就会知道它是为了什么。

#### 把锁接进下单业务

获取锁、释放锁的动作全部搞定，接下来就可以做测试了。怎么测？肯定是来测我们那个一人一单。

之前这里我们是采用 `synchronized` 来做锁的，现在我们不这么做了，我们需要自己来创建锁对象、自己解锁。所以我们把之前那段代码给它干掉，改为在这里创建锁对象，然后去获取锁。

```java
@Resource
private StringRedisTemplate stringRedisTemplate;

@Override
public Long createVoucherOrder(Long voucherId, Long userId, Integer requestCount) {
    // 1. 查询优惠券信息 ...

    // 2. 库存扣减（数据库条件更新）...

    // 3. 创建订单 ...
}
```

创建锁对象就是 `new SimpleRedisLock(stringRedisTemplate)`，需要传一个参数：**锁的名称**。

锁的名称一般跟你的业务有关、有标识。我们这个是下单的业务，所以可以叫 `order`。但这里除了叫业务名之外，还有一点必须注意——**我们锁的范围**。

如果你就写 `order`，意味着凡是来下单的业务都会被锁住。但我们之前提到过，我们锁定的范围其实是**用户**：同一个用户我们才要加限制，不同用户无所谓。所以这个地方锁的范围应该是用户，应该拼接上那个用户的 id，把这俩合在一起作为锁的对象：

```java
String lockName = "order:" + userId;

Boolean isLock = lock.tryLock(lockName, 1200L);

// 获取锁失败
if (!isLock) {
    // 告诉前端：一个人只允许下一单，不允许重复下单
    return fail;
}

// 获取锁成功
try {
    // 3. 一人一单判断：查询数据库，看这个用户有没有下过单
    // 4. 创建订单
    return orderId;
} catch (Exception e) {
    throw new RuntimeException(e);
} finally {
    // 释放锁
    lock.unlock(lockName);
}
```

这里有几个点要展开说。

**锁的范围小了，并发效率才不错。** 因为锁定范围是用户 id，所以跟刚才单机版一样，冲突范围较小，并发效率是过得去的。

**超时时间跟业务耗时有关。** 我们下单业务的耗时大概是 500ms，那超时时间可以设置成 5 秒钟。只要执行不超过 5 秒，最终肯定能执行完。但这里因为要做测试、要打断点，会耗费比较长的时间，所以代码里我给个长一点的 `1200L`，这样等会儿打断点也不用担心打到一半超时。

**这里只是尝试获取，不一定能成功，所以必须判断。** 判断是否获取锁成功，写成 `if (!isLock)` 这样的反向判断。为什么建议反着写？因为如果我写成功，按这个结构是不是要嵌套？嵌套的话就很容易出现一些问题，嵌套的逻辑代码看起来不够优雅。

那获取失败我们干什么呢？一般情况下要么是报错直接返回错误信息，要么就是重试。我们这个业务是一个并发的下单业务，目的是避免一个用户重复下单——现在有个人开了挂，一下子发过来了无数的请求要来抢，其中有一个请求获取锁成功了，其他线程都失败了，你觉得我应该让他重试吗？显然不应该，因为这本来就是非法的请求。

所以我们采用比较简单的一个方案：你既然获取锁失败了，代表现在是在并发地处理同一个用户的多个请求，那我肯定阻止你。直接 `return fail`，告诉他说一个人只允许下一单、不允许重复下单就行了。

**业务逻辑必须包在 try-catch-finally 里。** 这段逻辑执行过程中有可能有异常，我们要把它捕获起来；将来一旦出现了异常我们再去释放锁，不出现异常是不是也要释放锁？所以释放锁要放到 `finally` 里去做。现在是手动释放了，不再是 `synchronized` 自动释放，通过 `lock.unlock` 来做释放。

相比以前 `synchronized` 是不是会复杂一点？因为你有了一个手动创建锁、手动释放锁的过程了。

#### 开两台服务实测一下

代码完成了，我们再测试一次。在获取锁成功的地方打一个断点，把它启动起来——我们照旧启动两个，模拟两台服务器。

之前那轮测试里，这两个是独立的两个进程，每个进程内都会有自己的锁对象，所以并发访问时两个进程就有两把锁，以至于出现并发安全问题。现在我们就来测一下：一旦我们换成了自定义的 Redis 锁，它还会不会有这个并发安全漏洞。

测试前先把数据库里的数据清理一下，库存也恢复一下。然后依然用 Postman 分别发两个请求。

回来你看，两个请求都停在断点上了，但你会发现第一个这边得到的是 `isLock = true`，而第二个请求的 `isLock` 值却是 `false`。这就证明现在其实只有一个人获取锁成功了。

为什么？因为我们虽然有两个进程，但他们都是去同一台 Redis 机器上获取锁，而且获取锁的名称是一样的。这时候我们去 Redis 里刷新看一下：他们在获取锁的时候，这个地方会记录这个用户 id，会记录当前线程。因为是同一个用户你来争抢，所以只能有一个线程的锁拿到，另外一个线程是拿不到的。

只要锁只有一把，你就不会出现同时执行这种情况。所以第一个哥们往下走就能成功，然后去执行下面的业务；第二个哥们就不行了，往下走直接就失败了，然后不允许重复下单。所以我们在 Postman 里得到的结果也是一个成功、一个失败。

我们回忆一下这版分布式锁的原理，其实就很简单：一开始获取锁就是利用 `SET NX` 来实现互斥效果，当锁的名称是一样的时候（同一个用户），他们去执行 `SETNX` 的时候只有一个人能成功，实现互斥；同时我们用了 `EX`，也就是后面这个时间，来确保万一没有正常释放，将来锁可以超时自动释放。如果说正常情况下，我们其实手动释放锁会执行 `DELETE` 把它手动删除掉。

这就是分布式锁的第一版本的实现思路。

### 第一版还差一口气：会误删别人的锁

这一版的实现方式非常简单，在大多数情况下这个锁都能够正常工作。但在一些极端情况下，它依然会存在一些问题。我们来分析一下它可能存在什么样的问题。

我先准备了一条时间线，把它理解成一把锁的持有周期。

```text
时间  ──────────────────────────────────────────────────────────────►

   线程一（蓝）                 线程二（紫）                线程三
      │                            │                          │
 t1   │─ SET NX 成功，拿到锁        │                          │
 t2   │─ 执行业务（下单）           │                          │
 t3   │─ 业务阻塞，卡住 ⚠            │─ SET NX 成功，拿到锁      │
 t4   │  超过 EX 设定的超时时间      │─ 执行业务（下单）         │
 t5   │  锁被自动过期释放 ⚠          │                          │
 t6   │  业务醒来，准备 DEL          │─ 业务进行中…             │
 t7   │─ DEL lock  ← 删掉的其实是线程二的锁 ⚠                      │
      │                            │  锁没了，但它并不知道     │
 t8   │                            │                    │─ SET NX 成功
 t9   │                            │                    │─ 业务执行中
      │                    ┈┈┈ 此时线程二、线程三 同时在跑 ⚠
```

读图：线程一的业务阻塞太久，超过了我们设置的超时时间，锁在 t5 就被自动释放了，这时候线程二趁虚而入拿到锁。线程一在 t7 醒来，业务完成了，它二话不说上来直接一个 `DEL`——删掉的其实是线程二的锁。线程二对此一无所知，它还在执行自己的业务。与此同时线程三发现锁没了，也能获取成功，于是线程二和线程三就同时在跑，并行执行的情况又出现了，线程安全问题有可能再次发生。

我们分析一下这种极端情况产生的原因。

**第一**，因为业务阻塞，导致了我们这个锁被提前释放了。别忘了，我们获取锁的时候有一个 `EX` 超时时间，它就是一个兜底方案，避免因为没有人释放锁而卡住。虽然我们设了超时时间，但是如果说这个业务阻塞得太久，以至于都超过这个超时时间了，那这个时候是不是也会触发这个锁的超时释放？也就是说业务还没完呢，它提前释放了。

**第二**，当线程一醒过来以后，这个时候的锁已经不是线程一的锁，而是线程二的锁了。但是线程一二话不说，上来就把别人的锁给删了。

这个场景像什么呢？你到点放学了，去自行车棚里，想推自己的自行车。你当然得先开锁，你在这儿开了半天发现打不开，于是你一气之下拿了一个大钳子，直接把锁给剪断了。剪断了以后抬头一看——不是自己的车。你这个锁就弄错了啊，你把别人的锁给剪了。

所以这里归根结底要发生安全问题的、最重要的原因就是：**线程一在释放锁的时候，把别人的锁给删了**。

那要想解决这个问题该怎么办呢？关键在于——**释放锁的时候要做判断**。

你释放锁的时候不要那么着急，先看一眼这个锁是不是你的了，你有没有资格去释放。所以我们要在释放锁的时候做一个判断：**判断一下锁的标识是否一致**。

什么意思呢？当你醒了以后要去释放锁的时候，你要看一看这个锁里面存的这个标识，跟你当前线程是否一样。

大家别忘了，我们之前去获取锁的时候，是不是存了一个线程标识进去？你看一下我们之前获取锁的时候存的那个东西，是不是就成了一个现成的、早就铺好的路。

```text
  释放锁前的判断

      GET lock:order:5
            │
            ▼
     "1 12345"        ← 存的是获取锁时的线程标识
            │
            ▼
     标识 == 当前线程？
        ├── 是 ──> DEL lock:order:5    （安全释放）
        └── 否 ──> 什么都不做            （锁早就不是我的了）
```

如果发现不一样——比如说当前锁里的标识是紫色的、我是蓝的，那肯定不行，那我就什么都不做。标识代表不一致，我就不做任何操作，这样一来是不是就避免误删别人的锁了？

再往后看，线程二也一样。他去执行自己的业务时，因为线程一没有删他的锁，他这把锁依然存在，因此线程二就可以正常地、不受干扰地去执行，不会存在刚才那种情况。那么当线程二执行业务完了以后去释放锁的时候，他也要做这个动作——**任何一次释放锁，我们以后都要做这个判断，检查锁标识**。因为这个地方锁依然是紫色的，跟它一致，所以标识一样，那就没事，他就可以正常地去释放锁了，于是再发一次请求去做释放锁，它的那把锁就被释放掉了，那么此时线程三才能够去获取锁、去执行自己的业务。

这样一来，是不是就避免了这个问题的发生？

> **结论**：解决这个问题的关键就是在释放锁时做一个判断。所以我们这个业务流程与原来相比会有一些变化——以前上来就释放锁，现在不行了。第一，在获取锁的时候要把线程的标识存进去（我们之前存的是线程 id，反正不管怎么样，你要存一个标识进去）；第二，在执行完业务要释放锁的时候，一定要判断一下这个标识是不是自己的，是自己的你才能释放，如果不是你也不能释放——其实这个时候就代表你的锁早就没了，你就不用管就行了。

这就是我们刚才那个分布式锁所存在的问题，以及对应的解决方案了。下一节课我们就动手实践，去改造一下我们这个分布式锁。

## Redis 分布式锁：从"别删错锁"到"删锁这件事本身是原子的"
> 对应块：BLK17 | 覆盖分集：P60-P63 | 块标题（分集名）：《实战篇-13.分布式锁-解决Redis分布式锁误》

我们上一轮把分布式锁版本一的问题翻了个底朝天：一旦某个线程业务超时、锁自己过期释放了，另一个线程趁虚而入拿到锁，这时候第一个线程跑回来执行 `DEL`，删掉的却是**别人**的锁。于是并发问题又一次上演。

这一轮我们要做三件事：先给锁装上身份证把误删挡住；再把这个"挡住了"的版本拿到极端条件下试炼一次，发现它照样会错；最后用 Lua 脚本把判断和释放焊死在一个动作里，把它做成一个相对完善、生产可用的分布式锁。

### 锁上的身份证：线程标识

#### 为什么线程 ID 单独用还不够

思路本身很朴素，两个要点：

- 获取锁的时候，把**当前线程的标识**一起存进去；
- 释放锁的时候，先把存进去的标识取出来跟自己的比一下，一致——是我的，我才删；不一致——不是我的，我碰都不碰。

看起来闭环了。但需求里让我们存的不是裸的线程 ID，而是一个 **UUID**。为什么？

我们之前用的那个线程 ID，其实就是 `Thread.currentThread().getId()`，它在 JVM 内部是一个**递增的数字**：123、456 这样依次往上加。这在单机上没问题，可一旦我们跑在集群模式下——大家想想看，多个 JVM 各自都维护着自己那一套从 1 开始递增的数字，那么两个 JVM 之间出现 ID 冲突的概率相当高。

> **易错点**：线程 ID 只在单个 JVM 内唯一，跨 JVM 会重复。集群部署下拿它当锁的所有者标识，等于没加锁。

所以光靠线程 ID 不够，我们还得让不同的 JVM 之间产生差异。怎么产生？两个思路凑到一块儿就完事了：

- **UUID 区分不同的服务，也就是不同的 JVM**；
- **线程 ID 区分不同的线程**。

两者结合，就能保证：**不同线程的标识一定不一样，相同线程的标识一定一样**。这就是我们最终要存的那个标识。

#### 改造锁的实现

注意改造范围——业务代码一行都不用动，要改的是**锁的实现**。所以改动只有两处：获取锁的地方，标识要写得复杂一点；释放锁的地方，要多做一次判断。

标识怎么拼？给线程标识加个前缀就行，这样在 Redis 里一眼就能看出格式：

```java
private static final String ID_PREFIX = IdUtil.fastUUID().toString(true) + ":";
```

这里用 Hutool 工具类里的 `fastUUID()`，比我们自己造要方便。它可以传一个 `true`，把 UUID 里那些横线去掉——注意了，UUID 默认是**带**横线的，去掉之后更紧凑。最后拼一个冒号，因为后面还要接线程 ID，用冒号隔开就够了。

于是获取锁的时候：

```java
private static final String LOCK_KEY = "lock:order:" + userId;
String threadId = ID_PREFIX + Thread.currentThread().getId();
// setIfAbsent(key, value, timeout) 对应 SET key value NX EX ttl
stringRedisTemplate.opsForValue().setIfAbsent(LOCK_KEY, threadId, LOCK_TTL);
```

存进去的 value 就是 `UUID:线程ID` 这样一串字符串。

释放锁这边就要多一步了：先把锁里的标识取出来。取的时候必须用**同一个 key**，不然取的就不是这把锁了；用 `opsForValue().get()`，拿到的就是锁里那个 ID。

```java
String threadId = ID_PREFIX + Thread.currentThread().getId();
String lockId = stringRedisTemplate.opsForValue().get(LOCK_KEY);
if (threadId.equals(lockId)) {
    // 是我的锁，才删
    stringRedisTemplate.delete(LOCK_KEY);
}
```

一致就删，不一致就什么都不做。到这儿释放锁的逻辑就写完了。

### 把改造后的锁跑一遍

代码写完必须验证，不然都是心里有底。我们去下单的那条业务链路上打两个断点：一个打在获取锁的地方，一个打在释放锁的地方，然后 debug 启动。

跑之前先清数据：库存恢复成 100，订单表里那条删掉。然后用 Postman 发两个请求，让两个实例都进来。

流程是这样：

```text
t0  8081  获取锁成功，Redis 里 lock:order:5 = "uuidA:31"
t1  我们手动删掉这个 key，模拟"锁超时过期"
t2  8082  获取锁成功，Redis 里 lock:order:5 = "uuidB:42"   ← 换人了
t3  8081  走到释放锁：自己的标识 "uuidA:31" vs 锁里的 "uuidB:42"
t4  不一致 → 不删。锁还在 Redis 里
t5  8082  业务跑完走释放锁：两个标识完全一致 → 删掉。锁消失
```

在 IDEA 里单步跟进去的时候，8081 会先算出自己的线程标识，再从 Redis 里 GET 出锁里的标识，两个值肉眼可见地对不上。它就知道这锁已经不是自己的了——那显然不能删啊。于是直接往下走，锁安然无恙。

等 8082 执行完业务去释放，它先拿自己的标识、再拿锁里的标识，两个完全一样，所以它可以删。回到 Redis 一看，锁这才真正消失。

> **结论**：加线程标识 + 释放前比对标识，这套机制确实把"误删别人的锁"挡住了，整个分布式锁健壮了一大截。改进的点就是一个——释放锁之前先判断，再释放。

### 判断通过了，为什么还是会删错锁

#### GC 卡在中间的那一刻

刚才那次测试是**正常情况**下的测试，大多数时候它确实能好好工作。但在某些极端条件下，它依然会出问题。

我们把锁的整个生命周期摊开来看。线程一上来申请锁，因为只有它自己，所以肯定能拿到，然后开始执行自己的业务。假设这次业务**没有阻塞**，顺利执行完，紧接着要去释放锁。释放锁要先判断锁标识——锁是他自己的嘛，这个判断肯定是成功的，返回 OK。

**注意了，判断锁标识和释放锁，是两个动作。**

那它凭什么会在中间出问题呢？判断完了直接释放，中间又没有别的代码，怎么会阻塞？

还真有可能。大家想想 JVM 里有个什么东西——**垃圾回收**。当我们的 JVM 做 GC 的时候，它会阻塞我们所有的代码。所以这个时候就产生了阻塞——不是因为你的业务阻塞，是因为 JVM 本身产生阻塞，是有这种可能性的。

那一旦阻塞了，故事就往下走了：

```text
时刻 t0   线程1  SET lock:1 uuid:1 NX EX 30   →  拿到锁
时刻 t1   线程1  业务执行完毕
时刻 t2   线程1  GET lock:1 → "uuid:1"        （判断通过！）
     ⋯⋯⋯  JVM 触发 Full GC，线程1 被阻塞  ⋯⋯⋯
时刻 t3   锁超时到期，Redis 自动删除 lock:1
时刻 t4   线程2  SET lock:1 uuid:2 NX EX 30   →  成功，开始跑业务
时刻 t5   GC 结束，线程1 恢复运行
时刻 t6   线程1  直接执行 DEL lock:1          →  ✗ 删掉了线程2的锁
时刻 t7   线程3  趁虚而入，获取锁成功，又一次并发问题
```

关键在 t6：**因为判断在 t2 就已经执行过了，线程1 认为锁还是自己的，它不会再判断一次，直接执行释放。**可事实上锁已经不是它的了。于是又误删一次，紧接着线程三趁虚而入，同类型的并发问题又一次发生。

> **易错点**：加了标识判断 ≠ 安全。只要判断和删除之间存在时间缝隙，缝隙里锁就可能易主。

#### 原子性：判断和释放必须是一个动作

那这一次产生的原因是什么？我们明明做了判断了呀，为什么又出问题？

就是因为**判断锁标识和释放锁是两个动作，而这两个动作之间产生了阻塞**。

所以要想避免这个问题，我们必须确保：**判断锁标识的动作和释放锁的动作，得成为一个原子性的操作**——也就是说一起执行，中间不能出现间隔。那问题来了，怎么样保证两个动作的原子性呢？

### 为什么最后选了 Lua 脚本

我一聊到原子性，很多同学可能就想到事务了。那 Redis 它到底有没有事务呢？

**答案是有的。**不过这个事务跟大家所了解的 MySQL 事务是有很大差别的。Redis 的事务首先能保证原子性，但没办法像 MySQL 那样给你一套完整的一致性保证；更关键的是，它这个事务里面的多个操作其实是一个**批处理**，是在最终一次性去执行的。

这意味着什么呢？你没有办法说"我先去查询，然后判断，再去释放"，因为你做这个查询动作的时候其实是拿不到结果的——它是最终一次性执行的。所以你没办法把它们俩放进一个事务当中。

理论上你只能利用 Redis 里面的**乐观锁**去做一些判断，确保在我释放的时候没有人去修改。但这种做法复杂很多，所以我们**不建议大家这么做**。

那用什么？在 Redis 里面可以用 Lua 脚本。

这里我们推荐大家使用 Lua 脚本去做。这个 Lua 脚本，其实就是在一个脚本当中编写多条 Redis 命令，把多条命令做到一个脚本当中。Redis 去执行的时候就会一次性去执行它们，确保这些命令的原子性——它们在执行过程中，就不会有其他的命令插入进来了。这样一来，问题不就解决了吗。

> **结论**：判断标识与释放锁必须原子执行。实现上推荐 Lua 脚本，不推荐 Redis 事务 + 乐观锁。

| 方案 | 能不能把"判断 + 释放"合成一个动作 | 结论 |
| --- | --- | --- |
| Redis 事务（MULTI/EXEC） | 不能。事务内命令是批处理、最终一次性执行，查询时拿不到中间结果 | 排除 |
| 事务 + WATCH 乐观锁 | 理论上可行，靠版本号校验"期间无人修改" | 复杂，不推荐 |
| Lua 脚本 | 能。脚本执行期间不会被插入其他命令 | 本讲采用 |

#### 为什么叫 Lua

因为编写这个脚本，用到的是一个叫做 Lua 的编程语言。我们学的 Java 也是编程语言，对不对。

有的人会说：我 Java 还没学明白呢，你现在又让我整个 Lua，是不是啊？

**不用急啊。**事实上我们并不需要去真正熟练精通这个 Lua 语言，你只需要懂它的一些基本语法就行了。因为我们要做的事情很简单，无非就是去查询一下，然后判断一下是否一样，就是类似于这样的。所以其实是比较简单的。

这里给大家找了一份 Lua 的简单入门教程，需要的时候去查一下就行：

- 它提供了 `print` 这个打印函数，跟我们 Java 的 `System.out` 是不是差不多的意思；
- 它也有各种不同的数据类型，也会有变量；
- 变量声明的时候有一个 `local` 来声明，代表是一个**局部变量**。也就是说它其实是**弱类型**的，不需要声明什么 `int` 之类的，这一点跟 JS 很像；
- 函数声明的时候也是跟 JS 很像，`function 函数名(参数列表)`；
- 需要注意的是，它这个函数是**没有大括号的**，像我们 JS 和 Java 都是有大括号的，而它这里仅仅是一个 `end` 代表结束。

当然这里面还会有一些像流程控制，比如说 `if else`，`if` 里面同样写条件，然后条件下边呢也是没有大括号，是 `then` 和 `end`。所以这就是它与我们 JS 或者 Java 的一个差别了。

在这里大家不需要去死记硬背。就是说当我们去写脚本的时候，你用到一个什么东西，你来这儿查一下，然后参考着去写不就行了。这些其实都比较简单，没有特别好说的。

> **提示**：Lua 的条件分支用 `if ... then ... end`，没有大括号；`if` 成立和 `if` 不成立都各自需要一个 `end` 收尾，写的时候最容易少写一个。

#### redis.call：从 Lua 里调 Redis

真正重点的不是语法，而是我们要做的事情——**利用 Lua 语言编写脚本，去调用 Redis**。用 Java 调 Redis 我们很熟悉，用 Spring 提供的 `RedisTemplate` 就可以了。那 Lua 又该怎么去调 Redis？

Redis 官方给我们提供了一个内置的函数，方便我们去调用 Redis。什么函数呢？`redis.call`。

这个你就把它理解成 Java 的面向对象：前面那个 `redis` 就是提供了一个对象，第一个 `call` 其实就是在调这个 `call` 函数，括号里传的就是函数的参数。是不是挺简单的？

这个参数大家可以看到有很多——什么命令名称、什么 key、什么其他参数，其实看起来挺复杂的。我给大家解释一下，你就明白了。

比方说我们现在要执行 `set name Jack`，这不就是一条 Redis 命令吗？那这条命令如果是用这个函数来执行的话，就是这样子：

```lua
redis.call('set', 'name', 'Jack')
```

你看，我们的命令是 `set name Jack`，它传参是不是也是这样？我们的命令是用空格隔开的，它其实就是把命令里面的每一个单词，作为一个参数、用引号引起来作为字符串，然后用逗号隔开。**一个空格隔起来就是一个参数**。很容易吧？

让同学们思考一下：如果我要做 `get name`，我该怎么做啊？你可以想一想，可以把答案打在公屏上。

其实应该是什么呀：`redis.call('get', 'name')`，是不是就 OK 了？非常简单。

这就是脚本了。当然我们讲脚本里面写什么，是想写一堆的命令，最终实现一个复杂业务逻辑。所以刚才这种就是简单的一个命令。那如果我们要写多个呢？比如说我先 set 再 get，我就可以这么写：

```lua
redis.call('set', 'name', '杰克')
local name = redis.call('get', 'name')
```

这样就取出了这个 name 的值了吧。取完以后我们还可以拿一个变量来接收——刚才我们看过，声明变量是不是用 `local`？`local name = ...` 就是去接收。你看这些语法跟我们 JS 也好、Java 也好，是不是非常地像？

拿到变量以后，最终我要把结果返回，我干嘛？我可以 `return`。当然你说我取出来了，我想判断结果是不是一致，可不可以用 `if` 啊？当然可以了。所以基本上跟我们其他语言的判断、查询是没什么太大差别的，还是挺简单的。

### 执行脚本：eval 与参数

脚本写好了，又该怎么样去执行这个脚本呢？

Redis 里面提供了一个命令来执行脚本，这个命令的名字叫 `eval`。`eval` 后面跟上 `script`，这个 script 就是脚本，然后再往后跟的是一些参数。

```text
eval <script> <numkeys> <key...> <arg...>
```

什么意思呢？就是我们这个脚本里面是**可以传参的**，当然你也可以不传参。我们先来个不传参的看一下。

比方说我现在要执行这个脚本——`redis.call('set', 'name', '杰克')`，刚才说过了，是不是就执行这个 `set name 杰克` 这个命令啊？那么这样的一个脚本我要去执行的时候，我就可以这么写：

```text
eval "return redis.call('set','name','杰克')" 0
```

这个脚本大家看用一个双引号引起来了啊，因为脚本本质上就是一个字符串，所以用一对双引号把它引起来，代表这就是脚本的内容。在这儿我们执行的是 `redis.call`，但是执行完了，我还是把结果 `return` 了，将来这个结果就会展示出来给我们看，所以这块是这么来写的。当然外边的这个引号用了双引号，里边就要用单引号，避免这个冲突嘛。

那执行脚本后面又跟了一个什么？跟了个 **0**。这个 0 就是参数的数量。

为什么我这里给了 0？因为我这里这个脚本当中没有任何参数，是写死的，就是 `set name 杰克`，这里边全部写死的常量。

> **提示**：脚本可以理解成一个函数，里面有一堆代码。如果全部写死，将来脚本的拓展性就很差——比如我这个脚本将来就只能是 `set name 杰克`。而如果允许传参，把"杰克"做成一个占位符，我们就可以给这个内容赋不同的值，脚本的拓展性立刻就上来了。

再进一步，如果我连 name 都可以传参，那将来我们是不是就可以给不同的 key 赋不同的值，脚本的拓展性是不是更进一步增强了？所以我们的脚本可以传参，也可以不传参，传参是不是更好一点，拓展性是不是更强一点？

好，现在我们先来演示一下不带传参的这种。我们还是通过这个 `eval` 去执行这个脚本，脚本的内容跟刚才 PPT 上一样，我们通过 `return` 先返回这个结果，然后是 `redis.call`，在 `call` 里面去传参，执行的是 `set`，它的 name 它的值我们给成"杰克"。好，然后呢到这脚本是不是就写完了？

脚本写完了以后问你脚本有多少个参数啊？零参数，无参的。然后执行一下，你看它返回了个 OK。那这个 name 有没有 set 进去呢？我们看一眼——是不是有？值是不是"杰克"呀？没问题。

这就是执行脚本，无参脚本的情况。但是这样的脚本它写死了，只能执行这样的一个命令，显然不是我们所希望的。那我们将来希望的脚本，一定是能够执行更复杂的、并且拓展性更强的一些命令，也就是**带参数**的。

#### 带参脚本：KEYS 与 ARGV

带参数该怎么去写呢？大家首先要知道的是，Redis 里面的参数它分两类：一类是 key 类型的参数，比如说这个 `name`；另一类就是其他参数了，比如说这个"杰克"。

为什么呢？因为在 Redis 里面它的结构不就是 key-value 结构吗？所以说我们在执行命令的时候，一般情况下都是要指定这个 key 的，所以它有一个叫 key 的类型的参数。另外就是其他参数。

那这里为什么要指定 key 类型的参数的个数？让大家的思考一下。首先呢，在 Redis 里边命令啊有很多种，而且有很多命令它是可以传多个 key 的。比方说我们来看一个 `MSET`，我们 `help` 一下：`MSET` 可以传 key、value，key、value，是不是可传多组？那这样来这个命令是不是有多个 key？

那我们如果脚本里面是这样的一个脚本，那将来这个 key 是不是可以有多个？所以回到 PPT 上，这个地方 key 的个数可能是有多个。既然 key 有多个，其他参数是不是也可以有多个？那我怎么知道哪些是 key 类型的，哪些是其他类型的？所以呢，他在这个地方让你指定 **key 类型的参数个数**。

比方说我这指定的是 1，那就代表着再往后紧跟着的这一个就是 key 类型的参数；如果指定 2，那往后跟着的两个就是 key 类型的参数，再往后跟着的就是其他参数了。这就是他这里这个参数的一个概念。

那新的问题来了：如果我真的在后边传了很多个 key、很多个其他参数，那这些参数我在脚本里怎么获取呢？在脚本当中我是不是得有一个占位符去取这类的参数？

在 Redis 里面，它会把你后边的这些参数分成两类：key 类型的和其他类型的。那么 key 类型的参数，因为有多个，会放到一个 `KEYS` 的数组里，而其他参数会放在一个 `ARGV` 数组里面。这个 `KEYS` 和 `ARGV` 其实就是数组名称。既然把参数放到两个不同的数组当中了，那我在脚本里是不是可以去取数组里面的内容啊？

比方说现在我们还是这个 `set` 命令，但是这个 key、value 我都不写死，我都是去取数组中的参数：

```lua
return redis.call('set', KEYS[1], ARGV[1])
```

`set` 里面这个 key 我就没有写死了，而是从 KEYS 里去取。那取的时候因为它是数组嘛，我就取**中括号 1**——取数组中的第一个。

有的说了，第一个不是零吗？这就是 Lua 语言与其他语言的不同之处了：**在 Lua 语言里，数组的角标是从一开始的**，所以我这个中括号 1 就是取数组中的第一个。那 `ARGV[1]` 就是取其他参数这个 ARGV 数组中的第一个。

那紧跟着我们这个脚本后面跟一个 1 代表什么？脚本里面 key 类型的参数只有一个，因此紧跟着的这一个就是 key 类型的参数。这个是脚本参数的个数，是 1；那紧跟着后面的这个 `name` 就是 key 的参数，它放到 KEYS 数组里，因此当脚本执行的时候，它就会取到这个 name。同理这个"杰克"放到 ARGV 数组里了，所以脚本执行的时候，自然就会取到这个数值作为这个 value。

这就是我们这个带参数脚本的一个语法了。那这样的一个脚本，将来你就可以随便传不同的参数，它就可以给不同的 key 赋不同的值了，这是个**动态的脚本**。

我们也来试验一下：通过 `eval` 后面跟上脚本，跟刚才一样，这句话我们还 `return`，然后 `redis.call`，那么这个地方同样是 `set`，然后紧接着 `set` 的时候我不写死了，我说 `KEYS[1]`、`ARGV[1]`。这样我这个脚本的内容就写好了。脚本内容写好了以后，我要告诉他 key 的数量啊——我 key 就是一个，key 是什么呢？比方说我还是来 `name`；值呢？指我这次来一个"杰克"。

执行一下这个脚本，key 对应这个 name，ARGV 也对应这个"杰克"。我们来看一下返回 OK，我们来看一下 name 值变成什么了？是不是变成"杰克"了？

那么还可以。因为脚本是动态的嘛，所以我后面传参我可以随便传是吧？我再传一个"黑黑"，我们再来 `get` 一次，看是不是就变"黑黑"了？所以这样的脚本是不是就具备了拓展性了？它的值是可以变化的，那当然 key 肯定也可以变化。

好，这就是我们 Redis Lua 脚本的一个基本用法了。所以我们一般写的都是带参数脚本。

### 把释放锁写成 Lua 脚本

这些基本的语法弄明白以后，同学们我们一起来思考一下：现在呢我们要做基于 Redis 的分布式锁嘛，那这个锁的业务流程呢我们刚才已经做过一遍了，非常简单——

就是先获取锁中的线程标识，然后拿这个标识去跟当前线程标识去做一个比较，看是否一致。如果一致咱就去释放锁；如果不一致，什么都不做。

那现在呢我们就来把这一段用 Lua 脚本去编写一下。咱先不着急去执行这个脚本，我们先去把这个脚本给写出来。

> **提示**：写脚本的时候你先不要考虑什么 `ARGV`、`KEYS` 之类的。你先想清楚这个脚本它的**整体流程是什么**，把流程写出来，最后再把该动态的地方替换成参数。

首先，大家在写脚本的时候，先想整体流程。第一步，获取锁中的线程标识——获取锁中的线程标识其实就是去 `get` 呗。`get` 的时候，`get` 要传个 key，这样是不是就得到 value 了？

但是这个 key 我们能不能写死？**肯定不能写死**。将来不同的业务锁是不是会有变化？所以这个 key 不能写死，它应该是个变量。我们先记录一下：首先我们要得到这个锁的一个 key，这个 key 我们先用一个变量来声明啊，`local`，比如说叫 `key`，那它的值将来是动态的，对不对？我们现在先写死。比方说我们锁的 key 一般格式是这样：`lock:order:5`，先 lock，然后后面是 order，然后再往后是不是用户 id，比如说是 5，这样我们就把这个锁的 key 先用一个变量记录下来了。

> **提示**：这个 `--` 就是这个脚本里面的注释，写的时候可以带上。

那么有了这个 key 以后，我们想获取锁中的线程标识，是不是就很简化了？其实就是执行一个 `get` 命令，`get` 这个 key 是不是就开了。那我们要在脚本里执行，我们该怎么执行？我们通过 `redis.call` 去执行，然后 `get`，`get` 这个 key，把这个 key 作为一个变量传进来就可以了。那得到的结果我们可以用一个变量来接收，线程中的标识我们叫 `id`。

拿了以后我要干什么？我要把这个标识与当前线程标识去比较。那当前线程标识是什么？能不能写死？**不能**，将来是动态变化的，所以这个将来也是一个参数。当前线程标识，不同的线程来执行我这个脚本的时候有不同的标识，所以它也不能在脚本里写死，需要去传过来，我们叫 `threadId` 吧。那这个 id 的格式是什么格式呢？我们之前也讲过了，它是一个 UUID 跟上一个线程 id，是这样一个格式。

那这个 id 有了，这个 threadId 也有了，我可以干什么了？是不是可以比较了——比较这个线程标识与这个锁中的标识是否一致。

`if id == threadId`，这跟 Java 写法一样吗？然后它不是大括号，它是 `then ... end`。然后呢，如果成立，如果一致，肯定释放啊。释放锁就是执行一个什么命令？是不是 `del`？当然我们在脚本里不能写 `del`，我们叫 `redis.call`，那这个 `call` 里面执行的是什么命令？`del` 命令，删谁？删这个 key 就可以了。执行的结果我们是不是可以把它 `return` 掉？然后呢 `if` 结束。

如果 `if` 成立咱们去释放，`return` 是这个结果；那如果不成立呢？我们可以 `return` 一个 **0**。我们知道删除成功是 `return` 1 嘛，这样的话 1 代表成功，0 是不是代表失败？

到这里就结束了，这就是我们的脚本。

但是呢我们还要考虑的是，我们的脚本不能写死是吧？我们的 key 和 threadId 将来是动态的，你不能写死。不能写死就是传参呗。所以呢我们这里的 key 其实就是 key 类型的参数，我们讲了 key 类型的参数是放在 KEYS 数组里，是不是 `KEYS[1]`，中括号 1 取到了；而这个 threadId 就是其他参数嘛，因为它不是 key，它只是一个比较用的东西，所以说它就是放到了 ARGV 数组当中。

那这样一来咱们这个脚本是不是就是动态的了？再往后如果我们要简化这个脚本的话，同学们看，既然这个 KEYS 在下边都要用，我们是不是也可以把它直接这样写？也可以。那 ARGV 如果要去替换它们，是不是就在这儿替换它就行了？这样我们的脚本是不是就简化一点？

来，我们来看一下 PPT 里其实给大家写好了这个脚本，我们可以比较一下我们写的这个跟它对比一下，其实整体来讲是差不多的。我们这里是先取，取完了以后再比较；其实放到这个 `if` 里头的话，是不是就跟他一样了。然后 `return` 那个 `del`，然后呢这个 `return 0`。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

这就是我们释放锁这个 Lua 脚本了。到这里呢这个 Lua 脚本的编写方式我们就讲完了。当然了我们也去亲自把这个释放锁的脚本给写出来了。

但是脚本写完了是一回事啊，等一会儿我们还要去改造咱们的 Java 代码，让它去执行这个脚本。那具体怎么用 Java 代码来执行这样的脚本呢，我们下节课继续来分析。

### 用 Java 执行脚本

上一节课我们已经学习了 Redis Lua 脚本的语法，并且还去编写了一个释放锁的 Lua 脚本，确保在释放锁时，判断锁标识以及释放锁这两个动作的原子性。那这样呢我们的释放锁就变得更加健壮了。

但是啊，脚本写好了，我们又该怎么样去执行它呢？这节课呢我们就一起来研究一下。

需求上给我们提示了：要想利用 Java 代码来执行这个 Lua 脚本，只需要调用 `RedisTemplate` 里面的 `execute` 方法就可以了。这个方法接收三个参数，分别是 `script`（也就是脚本）、`keys` 和 `args`。

我们可以结合那个 `eval` 命令去看这个方法。对应关系非常简单：

| `eval` 命令里的部分 | `execute()` 对应参数 | 说明 |
| --- | --- | --- |
| `script` | 第一个参数 | 脚本内容本身 |
| `numkeys` | 不需要传 | 因为 keys 集合的元素个数就是 key 的数量 |
| `key...` | 第二个参数 `List<String> keys` | key 类型参数可以有多个，所以用集合 |
| `arg...` | 第三个参数 `Object... args` | 可变参数，其实就是数组 |

所以呢这个函数跟我们的 `eval` 命令是这样一个对应关系的，非常的简单。

#### 提前把脚本加载好

下面我们一起来基于这个 API 改造一下我们之前的分布式锁。我们打开 IDEA，首先找到我们的锁，这是我们那个释放锁的一个代码，等一会儿我们就要对这个代码做一个改造了——不再是自己去做这些动作了，而是去执行 Lua 脚本。

我们先把原来那段代码做掉，然后在这儿给他重新来一个，这段代码等一会我们就基于 Lua 脚本去执行。脚本该怎么样去调用呢？刚才说了，是不是那个 `execute`？

这个脚本啊，我们**不建议大家直接在代码中给他写死**。因为你把他写死到这里的话，将来如果我们需要对这个脚本做一些调整的时候，就非常的不方便了。所以我们把它写到一个文件当中。我们在这里直接新建一个 lua 脚本，起个名字叫 `unlock.lua`，也就是释放锁的意思。然后我们在这儿上去写那个脚本。这个脚本我们就不再重复写了，因为之前已经写过一遍了。

看整体流程：判断取出来的这个线程标识，与我们传进去的标识是否一致；如果一致就可以释放锁，然后就结束了。就这么个代码。在这个脚本当中，它的返回值是 0 或者 1，其实就是一个数值类型。这里的 KEYS 其实就是我们传取的锁的名称，也就是锁的那个 key；而这里的 ARGV 其实就是线程标识。所以等一会我们去传这两个参数。

那整个脚本我们就准备好了。接下来呢就是去调用这个脚本了。怎么指定这个脚本呢？我们可以调用它的一个 `setLocation` 方法，设置这个脚本它的位置。这里边接收的是个 `Resource`，其实就是资源的意思。在这儿我们可以使用 Spring 里面提供的 `ClassPathResource`，也就是在 classpath 下的一些资源，他默认就会去 classpath 下找。我们文件是放在这个 resources 下的，那是不是就是 classpath呀？因此我们可以直接指定这个文件名称，直接指定 `unlock.lua`，因为他会去找，直接找到这个文件就 OK 了。

然后我们还可以去配一下它的返回类型 `setResultType`，比如说我们是 Long 类型，就可以告诉他是 `Long.class`。

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;

static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```

这里有个问题：既然是静态的，所以说我们肯定是在静态代码块里去给他做这个初始化。那 `new DefaultRedisScript` 的时候，它的构造函数里边可以接收这个字符串类型的脚本，也就是把这串脚本当成字符串直接传进来。那这种模式的话就相当于是硬编码了啊，我们还是不建议这么做，我们还是放文件里，将来去修改下来比较方便，所以说这块就不用去管它了。

```java
UNLOCK_SCRIPT = new DefaultRedisScript("return redis.call('set','name','杰克')", Long.class);
```

> **提示**：顺便说一个性能上的事——我们是**每次释放锁的时候**去读这个文件，还是**提前**把这个文件读取好？显然要提前读取好。如果你每次执行都去读文件，那就要产生 IO 流，其实效果并不好，性能肯定很差。所以建议大家提前把脚本定义好。因为我用的是静态常量和静态代码块，这个类一加载，这个脚本就已经初始化完成了，这样就不用每次释放锁都加载，性能就会好很多。

#### 一行调用搞定释放锁

好，那在执行的时候我们就可以直接调用这个 script 了。我们是 `UNLOCK_SCRIPT`，第一个参数是不是搞定了？紧接着呢要指定 key 和 arg。

那么这个 key 和 arg 我们刚才在脚本里已经研究过了：`KEYS` 就是我们 Redis 里这个锁的 key，而这个 arg 其实就是线程的标识。所以在这儿呢我们需要指定这个锁的 key。锁的 key 其实就是前缀加 name，其实这个很简单。但你不能直接往那儿放，因为它要的是个集合，你这传过来是个字符串，所以我们需要把这个字符串放到集合里去。

那在这儿怎么办呢？我们用一个工具 `Collections`，它里面有个叫 `singletonList`，就是单元素的集合一个意思。那这样的话就简单直接生成一个集合，元素往里面一扔就行了。好，这是第二个参数；而最后一个参数呢就是 arg，就是我们要传的这个线程标识了。那线程的标识怎么来？`ID_PREFIX` 加当前线程 id 就行了。

```java
stringRedisTemplate.execute(
        UNLOCK_SCRIPT,
        Collections.singletonList(LOCK_KEY),
        ID_PREFIX + Thread.currentThread().getId()
);
```

这里呢我们不用去管返回值了。释放锁嘛，如果执行成功那就成功；如果最后没有成功，说明锁已经被别人删掉了，或者已经超时释放了，是不是也无所谓了。所以这块我们就不关心返回值了。

好，那大家来看我们这个释放锁的代码到现在是不是就变成**一行代码**了？

那之前为什么出现线程安全问题？就是因为它是两行代码，一个查询、一个判断，然后再释放。但如果判断完成以后、释放锁之前出现了一个阻塞，然后超时释放，是不是就出现误删的情况了？

那么现在呢它变成一行代码了，当然更重要的是：**我们这一行代码调的是 Lua 脚本，判断和删除是在脚本中执行的，是能够满足原子性的。**

### 回到生产可用：完整方案与验证

先测一遍。服务重启，日志清空，数据恢复（订单删掉、库存恢复 100），Postman 发两次请求。

```text
t0  8081  获取锁成功，Redis 里 lock:order:5 = "uuidA:31"
t1  我们手动删掉这个 key，模拟"锁超时过期"
t2  8082  获取锁成功，Redis 里锁的标识已经变成 "uuidB:42"
t3  8081  走到释放锁：这一行是一段脚本，由 Redis 保证原子性
t4  判断不通过 → 锁还在，"锁没有误删"成立
t5  8082  执行完业务去释放：判断通过 → 锁被删除
```

跟进去你会看到，这段释放逻辑现在是一段脚本，这段脚本是由我们的 Redis 帮我们执行的，它会保证这个判断和删除逻辑的原子性，所以就不会出现"判断的时候还好好的、删除的时候锁已经换人了"这种情况。8081 直接放行，其实这个锁并不会被删除——回到 Redis 一看，锁还在，因为它不是自己的。再回到 8082，他自己删除这把锁的时候，因为锁是他自己的，所以他可以删，回到 Redis 打开，显示无法打开，说明这把锁已经被删除了。

这样呢我们其实就验证了我们这个 Lua 脚本确实可以保证锁不误删，同时因为 Lua 脚本的原子性，所以也就不会出现这种线程安全的漏洞了。

来，我们把这套方案做个总结。

**获取锁**的时候，我们采用的是 `SET NX EX` 的方式。`NX` 的目的是互斥，确保只有一个线程能拿到锁；`EX` 呢是一个兜底方案，防止将来因为服务宕机导致锁无法释放。

**释放锁**的时候，我们采用的是先判断线程标识是不是自己，一致的证明是我的，我才释放锁，不一致我就不删，防止误删；并且呢我们还采用了 Lua 脚本，确保它的原子性，避免在多线程的情况下因为阻塞导致的误删。

那这个分布式锁它有什么样的一些特性呢？

- **互斥性**：只有拿到锁的那个线程能进临界区，多线程下可见性也满足；
- **安全性**：因为我们有超时释放，可以避免死锁；
- **原子性**：Lua 脚本保证判断和删除是一个动作，避免了误删问题；
- **高可用性、高并发性**：这个也可以满足。因为我们现在还没学集群，Redis 是可以做集群的，比如说做成主从或者其他集群模式，那么这样就不会因为宕机而导致锁失效。

所以呢到现在为止，我们这个锁已经是一个相对完善的分布式锁了。当然，相对完善，那证明什么呀？它是不是还有进步的空间呢？它还有哪些问题、还可以继续学、拓展和升级呢？我们下节课继续来分析。

> **承前启后**：上一节讲完「Redis 分布式锁：从"别删错锁"到"删锁这件事本身是原子的"」，下一节接着讲「分布式锁的四个短板，与 Redisson 的可重入锁原理」。

## 分布式锁的四个短板，与 Redisson 的可重入锁原理
> 对应块：BLK18 | 覆盖分集：P64-P66 | 块标题（分集名）：《实战篇-17.分布式锁-Redisson功能介绍》

经过前面几节课的努力，我们已经实现了一个**生产可用的、基于 Redis 的分布式锁**。不过呢，这把锁还有一些进步的空间啊——当然，这是高情商的说法。换言之，这个锁还存在一些问题，对吧。

什么问题呢？这节课我们一个一个拆开来看。

### 先算算旧锁欠下的四笔账

#### 不可重入：A 调 B，A 被自己锁死了

第一个是不可重入的问题。这个概念大家应该也听说过，你在 JUC 里面就有可重入锁的说法，`ReentrantLock`，对吧。

> **定义**：可重入，就是指**同一个线程可以多次获取同一把锁**。

比方说我有一个方法 A，方法 A 里要去获取锁，然后执行业务的中途要调方法 B。那在这种情况下，如果你的锁是不可重入的——我在方法 A 里已经获取了锁，等我去调方法 B 的时候，它又想获取这同一把锁，显然是过不去的。此时它就会去等待锁的释放。

而所谓等不到释放，是因为方法 A 还没执行完，它还在调 B 啊。于是就出现死锁了：

```text
线程 T1 执行 methodA
  │
  ├─ tryLock()  ──►  获取成功，锁归 T1
  │
  └─ 调用 methodB()
       │
       └─ tryLock()  ──►  失败：NX 保证一把锁只能有一个持有者
            │
            └─ 等待锁被释放 …
                     ▲
                     │  可锁要等 methodA 结束才会被释放
                     │  而 methodA 又在等 methodB 返回
                     │
                  methodB  ✗  永远等不到
       ==>  死锁：自己把自己锁死了
```

所以在这样的场景下，我们是要求锁可重入的。这是第一个问题。

#### 不可阻塞：一次失败就撒手不管

第二个问题呢，是不可阻塞的问题。我们之前实现的这个锁，它是一种**非阻塞式**的：去尝试获取锁，如果失败会立即返回 `false`，没有重试机制。

但是呢，在很多业务下，我们不能说立即失败啊。我们希望的是什么呢？我去拿锁的时候，如果这个锁现在被别人占有了，我等一等、我再试啊，如果最后成功了，那我再去执行业务。所以你不能说我一旦失败，就立即失败了，撒手不管了，这样在很多场景下是不可接受的。所以有些时候，我们需要这个锁是阻塞的，或者说可重试的。

#### 超时释放：太短太长都是坑

第三个点是超时释放问题。虽然我们之前利用判断锁标识、用 Lua 脚本，已经解决了因为超时释放导致的**误删**问题，不过呢，超时这种情况还是有可能会发生的——虽然不会导致误伤，但是也会有一些其他的隐患产生。所以超时释放这个问题，我们还是要想办法去解决。

那问题出在哪呢？

- 如果你把这个时间**设置得太短**：我的业务还没有执行完，锁就释放了，那这样一来，等于我的业务执行过程中，其他人也有可能来执行业务。这就是一个风险。
- 如果你**设置得太长**：将来我出现了故障以后，很长一段时间大家都在等待锁自动释放，那么我们这个锁的阻塞周期就过长了。

所以这是一个矛盾，我们也需要去解决。

> **易错点**：误删问题和超时问题是两码事。Lua 脚本解决的是"超时之后误删了别人的锁"，它管不了"超时本身"带来的业务风险。

#### 主从一致性：锁可能凭空消失

最后一个问题，就是主从的一致性问题。

主从这个概念很多同学可能没听说过，因为 Redis 的集群我们还没讲，在后面的高级篇中我们会去学习。这里先简单介绍一下。

所谓的主从模式，你也可以理解成读写分离模式。也就是说 Redis 会有一个主节点和多个从节点：当我们去执行**写操作**的时候，我们去访问主节点；当我们执行**读操作**的时候，我们去访问从节点。当然主节点需要把自己的数据同步给所有的从节点，保证主和从的数据是一致的。

这样我们就可以在多个节点上去完成读的操作，提高我们整个服务的并发能力和高可用性。而且如果主节点宕机了，我们还可以从从节点中选出一个作为新的主，这样整个集群的可用性就更强了。

但是呢，**主从之间的数据同步是有延迟的**。所以在极端情况下，可能发生这样一种情况：

```text
时间轴 →
  │
  │  T1 线程在【主节点】执行 set lock 1，锁标识写入成功
  │  （set 是写操作，主节点本地已生效）
  │
  │  ⏳ 同步延迟：这个写操作还没到从节点
  │
  │  ⚡ 主节点突然宕机
  │
  └─> 从从节点中选出一个作为新主
      └─ 新主身上【没有】这个锁标识
          └─ T2 线程趁虚而入，拿到锁
              ==>  此刻 T1 和 T2 同时认为自己持锁，并发安全出问题
```

其他线程是不是可以趁虚而入，去拿到锁？这时候其实就等于是有多个线程拿到锁了。所以呢，可能在极端情况下会出现安全问题。

当然它出现的概率比较低，因为主从同步的延时往往是极低的，它往往可以在毫秒级别甚至更低。

#### 这四笔账，一定要自己还吗？

所以呢，我们以上说的这四个问题，要么发生的概率极低，要么就是说了我们不一定有这样的需求——有些业务上需要，有些业务下不需要。所以这些个点都是一个**功能上的拓展点**，不是说必须得实现的。不实现我们也能够用，其实大多数场景下，我们之前实现的那个锁就已经够用了。大多数情况下我们可能不需要去做重入，也不需要去重试；超时释放一般情况下也不会去……那就极端刚好出现超时的情况吧；而主从一致性，如果我用单节点，其实就不存在一致性问题，对不对。

但如果说你对于锁的要求很高，你有这样的需求，你就必须想办法去解决它们了。

而要解决这几个问题，可就麻烦了啊：不可重入这个还好说，我们借鉴 `ReentrantLock` 的一个实现，去修改我们的分布式锁的实现就行了；对于可重试、超时释放、主从一致性问题，要解决起来就相对麻烦，整个实现起来也很繁琐。

> **结论**：不推荐大家亲自去实现，而是去找一找有没有成熟的框架来帮助我们。事实上就有这样的东西——这节课要给大家介绍的这个组件，它的名字叫 **Redisson**。

### Redisson：Redis 之上的分布式工具集

Redisson 是一个在 Redis 基础上实现的 **Java 驻内存数据网格**（in-Memory Data Grid），这是官方给出的概念。

那么说句人话，它的意思是什么呢？它是一个在 Redis 基础上实现的一个**分布式工具的集合**——也就是说在分布式系统下要用到的各种各样的工具，它都有，包括分布式锁。所以分布式锁只是它的一个子集。

这是它的官方网站。官方首页上的 Wiki 里有个简单的介绍，大家下去可以自己看一看。你可以看到它里面包含的功能非常非常多：分布式对象、分布式集合、分布式锁，分布式锁是其中一块功能，可以说是非常非常地丰富。

再看分布式锁里边，它又包含了啊各种各样不同的锁，像可重入锁、公平锁、联锁、红锁等等，还有读写锁、信号量等等，功能非常完善。

> **结论**：我们刚才所想到的那几个问题——重入，用可重入锁就能解决；可阻塞，可重入锁里面同样也有解决；超时问题、主从同步问题，这些同样在这里都能够找到解决方案。

所以呢，大家在企业环境下，其实没有必要自己去实现锁。我们之前的讲解，其实是让大家明白分布式锁的原理——因为在有的时候，面试的时候还是会去问到的。如果你懂了原理，将来的话，无论是面试还是你自己工作过程中出现问题，都更有利于你去学习和调试，对吧。

我们推荐大家以后使用分布式锁的时候，直接使用这个开源的框架就可以了。

### 可重入锁的原理

前面我们聊过，咱们自定义的分布式锁有一个缺陷，就是无法实现可重入，而 Redisson 它就可以做到。那这是为什么呢？这节课我们就一起来研究一下。

#### 先看看原来的流程卡在哪

咱们自定义的分布式锁采用的是 Redis **String** 数据类型，也就是简单的 key-value。整个获取锁的流程是这样子的：在一开始尝试获取锁，其实就是执行这个 `set` 命令，当然要加上 `NX` 和 `EX` 参数。

- `NX` 的目的就是实现一个**互斥**，满足分布式锁的基本要求。
- 同时呢，在获取锁的时候，我们要存入这个线程的标识，其目的就是将来在释放锁的时候做判断，**避免误删**——只有锁是自己的才去做这个删除。

那么这样的一个流程，为什么不能重入呢？我们一起来看一个 demo。

首先我们会创建一个锁的对象，然后有一个测试方法 `method1`；在 `method1` 里会首先尝试获取锁，获取失败就报错，成功的话就调用 `method2`；而在 `method2` 里又一次尝试获取锁。`method1` 调 `method2`，所以他们两个是在**一个线程**里的，那一个线程连续两次去获取锁——这其实就是锁的重入了。

那我们来看一下，如果按照我们这个流程，它能不能实现重入：

1. 首先 `method1` 尝试获取锁，按我们这里就会去 `set` 这个锁名称以及锁标识进去。在这里就是 `lock` 以及比如说这个线程名叫 `tid1`，我们把它存进去了。
2. 接下来往下执行，调用 `method2`。那么 `method2` 又一次尝试获取锁，那么又要执行这个 `set lock tid1`。
3. 那因为这里加了 `NX` 的参数，也就是说**只有第一个人能成功**。这里已经有值了，所以 `method2` 执行出来的时候，一定是失败的。

所以说呢，我们就没有办法实现重入了。

#### 借鉴 ReentrantLock：多记一个计数

那怎么样解决这个问题呢？要想实现可重入锁，我们可以参考 JDK 里边提供的那个 `ReentrantLock` 的原理。

> **提示**：如果大家不知道 JUC 的 `ReentrantLock` 原理，建议去 B 站上搜一下我们黑马程序员的《Java 并发编程》课程，你搜"Java 并发编程"排第一的那个，UP 主就是黑马程序员。那个并发课程里其实就有讲到 `ReentrantLock` 的原理。

他为什么能实现可重入呢？这里简单说一下：所谓的可重入，无非就是在获取锁的时候，当我判断这个锁已经有人的情况下，我会看一下**是不是我自己**，也就是说是不是同一个线程。如果是同一个线程的话，我也会让他获取锁。但是呢，他在这里要多做一件事，就是有一个**计数器**，去记录你重入的次数——你总共获取了几次。那么你在 `tryAcquire` 获取锁的时候，这个次数会去累加，不断加一；而将来你再去 `release` 释放锁的时候，这个次数会减一。

这就是可重入的一个基本原理。那因此呢，我们再去实现的时候，也可以参考它。也就意味着我们其实不仅仅要在锁里边去记录获取锁的线程，还要去记录这个线程它的重复次数、总共拿了几次，每拿一次次数就加一。

#### String 装不下两个人，改用 Hash

现在呢，我们既要记录线程标识，又要记录重复的次数，那这样一来，我们的这个 **String 类型的结构显然就不行了吧**。什么样的数据结构可以满足在一个 key 里存储两个东西？

可以使用哈希结构。因为哈希结构它的 value 里面是不是可以又分成两个，一个 field、一个 value。那这个时候我们就可以：在 key 的位置记录**锁的名称**，然后在 field 的位置去记录**线程标识**，在 value 位置记录这个锁的**重复次数**。

```text
key          field          value
┌────────┐   ┌──────────┐   ┌──────┐
│  lock   │ → │  线程标识 │ → │  次数 │
└────────┘   └──────────┘   └──────┘

例：HGETALL lock
1) "lock"
2) 1) "tid1"
   2) "2"        ← 重入了 2 次
```

#### 获取锁：三个分支，两条成功路

比方说我们创建锁对象，然后去 `tryLock`，那么第一次来的时候，在这里我们会记录这个线程标识，并且把这个次数**重置为 1**，因为他是第一个来的嘛。好，然后往下走。

接下来调用 `method2`，而在 `method2` 里又一次尝试获取锁。那么他首先要做的肯定是看一看这个锁是不是有人了。这个锁已经有人了，这个时候**不代表失败**，还要再判断一下——获取锁的这个线程是不是我自己呀？因为 `method1` 调 `method2`，所以他俩是在一个线程里的，这个标识肯定是一样的呀。标识一样怎么办？只需要把重复的次数加一就可以了，代表我是第二次获取锁了。以此类推，如果再有重复，那就继续累加三、四。

这样就好了，`method2` 拿到锁了，已经重入了，是不是可以执行自己的业务了呀。

那么问题来了：以前我们是用 String，命令是 `set NX EX`，其中 `NX` 是来判断锁是否存在、实现互斥，而 `EX` 是设置过期时间。但是现在我们用的是哈希结构，**哈希结构里可没有这样的组合命令**，没有 `NX` 这样的东西。所以我们只能把之前那个逻辑给它拆开——先判断锁存不存在，再手动来设置过期时间。

那这个流程就会变化了：

```text
                      tryLock()
                          │
                 ┌────────┴────────┐
              锁不存在           锁已存在
           （EXISTS 返回 0）      │
            我是第一个来的         │
              │                   │
    HSET lock <线程标识> 1   HEXISTS lock <线程标识>
    （次数初始化为 1）                   │
    PEXPIRE lock <释放时间>     ┌────────┴────────┐
              │                1（是我的）    0（别人的锁）
              │                  │                │
    HINCRBY +1 不是我的，重试也没意义
    PEXPIRE 重置有效期              │
              │                   │
         return 1              return 0
       获取成功                获取失败
```

这里有两个点要特别留意：

- 锁不存在时，`HSET` 把次数**初始化为 1**，因为这是第一次获取。
- 锁已存在但**标识是自己**时，除了次数加一，还要**重置一下有效期**。因为在 `method1` 执行的过程中，可能已经消耗了一部分锁的时间了，所以在这儿最好重置一下，让 `method2` 有充足的时间去执行自己的业务。

到这儿，其实就完成了一次锁的重入了。

#### 释放锁：什么时候才敢真删

那等 `method2` 执行完自己的业务，是不是就可以去释放锁了呀？

释放锁的时候，以前我们是先判断锁是不是自己的，如果是，我们再去删，避免误删。这里呢其实也是类似，首先肯定也得先判断锁是不是自己的。如果说这个锁根本就不是你的，那证明什么？证明你这个锁已经释放了，可能是超时了，对不对。那这种情况下你就不要管了。

但是如果这个锁是自己的，那么我们就要去释放了。当然这个释放不是上来就删——能不能像以前一样，先判断标识是自己，然后接下来直接删除？**答案是不能啊。**

想一想：如果我在 `method2` 里直接把这个锁删了，你要知道，`method2` 结束并不代表整个业务结束吧？因为 `method2` 出来以后，还要去执行 `method1` 的剩余业务。虽然我们这没写，但是很有可能在真实场景下是有其他业务的。那也就是说，在 `method1` 业务尚未执行完的时候，`method2` 直接就把锁给删了，那么此时是不是就有其他线程可以进来了？是不是就有可能发生一些并发的安全问题了？

> **易错点**：可重入锁在内部被调用的方法里，释放锁时**不能直接删除锁**，只能把重入次数减一。

那问题来了：我们什么时候才能释放锁、真的把这个锁删掉呢？肯定是当我们所有的业务都执行完，走到最外层的这个方法，它在结束释放时才能删除。

但问题又来了：我们怎么知道这个业务释放的时候，是不是已经到最外层了呢？

让我思考一下。我们每次获取锁这个重复次数就会加一，而每次释放锁这个值会减一；但是在方法当中，获取锁和释放锁都是**成对出现**的，也就是说，你加了多少次，将来释放锁的时候就一定会减多少次。那当方法走到最外层时，这个重复次数的值**一定会被减成零**，对不对？

比方说现在 `method2` 在释放锁时，这个值已经减了一，他业务结束了，走到了 `method1`——`method1` 就是最外层。那此时又一次释放锁，那么又减一次，它的值就变成了零。

所以说，我们每一次在释放锁的时候，除了要去把重复次数减一以外，还应该判断一下这个值是不是已经为零了。如果已经是零了，那就证明我已经到了最外层的这个方法了，也就是说没有其他业务需要执行了，此时你就可以放心大胆地把这个锁删除了。如果不是零，证明啊，还有别的业务，那么你就不要管了，交给其他业务去处理就行了。

这就是我们可重入锁的最终原理了——我们利用**哈希结构代替了 String 结构**，不仅仅存储线程标识，还存储了可重入的次数。

#### Lua 脚本：把整套流程按成原子操作

大家可以看到，无论是获取锁还是释放锁，跟以前相比，是不是就复杂很多了？而且这个地方代码有多个步骤，所以说像这样的逻辑，咱不可能再用 Java 代码去实现了——那这套东西一定要采用 **Lua 脚本**来确保获取锁和释放锁的原子性。

那这个 Lua 脚本又该怎么写呢？带着大家简单来看一看，我们就不一个一个去写了，流程跟刚才讲的差不多。

首先是三个参数：这里的 `KEYS[1]` 就是我们锁的名称，就叫 `lock`；`ARGV[1]` 就是线程的标识；`ARGV[2]` 是锁的释放时间——跟之前相比要多这样一个参数，为什么需要释放时间呢？因为在获取锁的过程当中，我们要去设置有效期，所以说这个也作为参数之一了。

**获取锁脚本**：

```lua
-- KEYS[1]  锁名称
-- ARGV[1]  线程标识
-- ARGV[2]  锁的释放时间

-- 1.判断锁是否存在
if redis.call('exists', KEYS[1]) == 0 then
    -- 锁不存在，说明你是第一个来的，可以放心大胆地获取
    redis.call('hset', KEYS[1], ARGV[1], 1)    -- 线程标识 + 次数初始化为 1
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 设置有效期
    return 1                                    -- 获取成功
end;

-- 2.锁已存在，判断锁标识是不是自己的
if redis.call('hexists', KEYS[1], ARGV[1]) == 1 then
    -- 是自己的，说明是重入
    redis.call('hincrby', KEYS[1], ARGV[1], 1)  -- 重入次数 +1
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 重置有效期
    return 1                                    -- 重入成功
end;

-- 3.锁标识不是自己的，跟你没有任何关系，获取失败
return 0;
```

所以在这整个流程里边，返回 `1` 的就是成功了，返回 `0` 就是失败。

**释放锁脚本**：

```lua
-- KEYS[1]  锁名称
-- ARGV[1]  线程标识
-- ARGV[2]  锁的释放时间

-- 1.判断锁标识是不是自己
if redis.call('hexists', KEYS[1], ARGV[1]) == 0 then
    -- 不是自己的，说明锁早就已经释放掉了（可能是超时了），不用管
    return nil;
end;

-- 2.是自己的，重入次数 -1
local counter = redis.call('hincrby', KEYS[1], ARGV[1], -1);

-- 3.判断减完之后是否还大于 0
if counter > 0 then
    -- 证明现在还不在最外层，还有内层业务在跑
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 重置有效期，给后续业务留够时间
    return nil;
end;

-- 4.已经小于等于零，说明走到了最外层，锁可以真正释放了
redis.call('del', KEYS[1]);                     -- 删除锁
redis.call('publish', ARGV[1], 1);             -- 发一条消息，通知大家这个锁我释放了
return nil;
```

> **提示**：最后那句 `publish` 是干什么的？后面我们会讲——它其实是发了一条消息，也就是去通知大家这个锁我释放了。

#### 跑一遍：那个值从 1 变成 2，再回到 0

光看脚本还是有点抽象，我们打开 IDEA 跑一下。这里我提前准备好了一个单元测试，是 Redisson 提供的一个锁。在 `method1` 当中我会尝试获取锁，获取失败就结束，成功就调 `method2`；在 `method2` 里再次获取锁，然后执行业务，最后释放锁——这就是一个可重入的 demo。下面我们打上断点走 debug。

- 放行到获取锁成功，返回 `true`，对吧。我们打开桌面客户端刷新一下，因为我们的锁名称起的是 `order`，可以看到这里边有一个 key，这个就是那个锁的标识；后面呢是一个 value，值为一——**就是重复次数为一嘛**。
- 然后往下走，进入 `method2`，又一次获取锁，你看又是 `true`，对不对？那这个时候我们再来刷新一下 Redis，大家看**值是不是变成二了**？也就是说重入次数加了一。没问题。
- 再往下走，释放锁。那么释放锁以后重置次数应该会减一，对不对？我们再来看一下。嗯，**没有真的删除，是减一**。
- 然后出来以后又回到了 `method1`，在 `method1` 里往下走也会去释放锁。那么这次释放锁，再刷新——是不是就没有了？说明这个锁被删除了。

所以这就是我们刚刚分析的那个逻辑啊，通过重复次数来记录这个可重入锁。整个流程也就是按照我们刚才分析的：先获取锁 1，然后获取锁 2，执行业务 2，释放锁 2，执行业务 1，释放锁 1，就是这样一个重复的流程。

#### 回到源码：Redisson 就是这么写的

那我们的 Redisson 是不是这么实现的呢？我们跟踪一下源码来看一下。

在 `tryLock` 里，我们往下跟找到它的实现类。这里我们采用的是最普通的 `RLock`。进到 `get` 里面有个 `tryLock`，我们根据这个再深入进去，看到这里呢 `tryAcquireOnceAsync`，那在这里他会先判断这个 `leaseTime` 是否等于 `-1`。这个 `leaseTime` 就是我们之前讲过的锁自动释放的时间，这里其实我们是没有传的，在没传的情况下大家可以看到他给的是一个 `-1`，所以说在进入这个方法以后啊，他去判断的时候这个地方肯定不成立，那于是呢就会往下走，走到这行，那这一行呢他会去 `tryLockInner`，也就是尝试获取锁。

锁的这两个逻辑是一样的，只不过呢，如果说你给了释放时间，他就会用你给的那个值；如果说你没给，他会走一个默认值。所以最终呢，都是会进到这个方法。

进到 `tryLockInner` 里面，大家就会看到这里有一段逻辑，这段逻辑就是一个 Lua 脚本。我们可以看到 Redisson 是把这个脚本**通过字符串直接写死的**，不需要像我们之前那样通过一个文件——这种方式其实也可以。那这段脚本大家如果仔细去看，跟我们刚刚 PPT 上的脚本就是一样的：

- 首先判断锁是否存在。如果等于零代表不存在，不存在怎么办呀？当然是去获取锁了。他在这个地方是直接 `hincrby` 了，也就是自增一。因为如果你不存在，它会自动帮你创建，所以跟那个 `HSET` 的效果是一样的；紧接着设置过期时间，然后结束。
- 那如果存在呢？存在也不要紧，我判断一下这个锁是不是自己，等于一代表是自己。是自己怎么办？同样是加一，然后设过期时间，然后结束。

这两个就是获取锁成功的情况，其他情况就是失败了。

那释放锁呢？释放锁走的是 `unlock`，我们跟进去。`unlock` 会调到 `unlockAsync`，我们继续跟入，同样找到 `RedissonLock` 里面。大家可以看到同样有一段 Lua 脚本，这段脚本就是我们刚刚分析的那一段：首先一样先判断锁是不是自己的，如果等于零，就是不存在，那就直接结束了——因为这种就是说锁早就已经释放了，你就不用管了。

然后让它锁的次数减一，你看 `hincrby` 然后 `-1`，这就是减一的意思。减完了以后啊，判断一下锁重入次数是不是零：如果大于零，证明好我们现在还不在最下层，怎么办？重置有效期；否则就说明已经小于等于零了，说明这个锁可以释放了，这里就执行了个 `del` 删除它。这里还执行了一个 `publish`——这个是干什么的？后面我们会讲，它其实是发了一条消息，也就是去通知大家这个锁我释放了。

好，到这儿呢，Redisson 可重入锁的这个原理我们就分析完毕了，获取锁和释放锁的整个流程，通过这幅图就给大家讲述完毕了。其核心就是利用一个哈希结构，去记录获取锁的线程以及重入的次数，与 JDK 里面 `ReentrantLock` 的原理是一致的。

### 本讲提到的题目

#### 题目一：选一个装得下两样东西的数据结构

**题干**：现在我们既要记录线程标识，又要记录重复的次数，那我们的这个 String 类型的结构显然就不行了吧？什么样的数据结构可以满足在一个 key 里存储两个东西？

**答案**：哈希结构（Hash）。key 位置记录锁的名称，field 位置记录线程标识，value 位置记录这个锁的重复次数。

**解析**：见"String 装不下两个人，改用 Hash"一节。原因是 Hash 的 value 本身还可以再分成 field 和 value 两层，天然就能在一把 key 下挂多个"字段—数值"。

#### 题目二：释放锁时能不能像以前一样直接删

**题干**：`method2` 业务执行完了准备释放锁，能不能像以前一样，先判断一下锁标识是不是自己，是的话就我，然后接下来直接删除？能不能这么做？

**答案**：不能。

**解析**：`method2` 结束并不代表整个业务结束，`method2` 返回后还要去执行 `method1` 的剩余业务。虽然 demo 里没写，但真实场景下很可能还有其他业务。如果在 `method1` 业务尚未执行完时就直接删锁，其他线程就能进来，可能发生并发安全问题。

#### 题目三：怎么知道已经走到最外层了

**题干**：我们每次释放锁时把次数减一，那么我们怎么知道这个业务释放的时候，是不是已经到最外层了呢？什么时候才能真正删除这个锁？

**答案**：判断重入次数减完之后是不是已经为 0。

**解析**：在方法当中，获取锁和释放锁都是成对出现的——加了多少次，将来释放锁时就一定会减多少次。所以当方法走到最外层时，这个重复次数的值一定会被减成零。因此每一次释放锁时，除了把重复次数减一，还应该判断这个值是不是已经为零了：为零就证明已经到了最外层、没有其他业务需要执行，此时可以放心大胆地删除锁；不是零就说明还有别的业务在跑，重置一下有效期就交给其他业务去处理。

## Redisson 分布式锁：锁重试、WatchDog 与连锁锁
> 对应块：BLK19 | 覆盖分集：P67-P68 | 块标题（分集名）：《实战篇-20.分布式锁-Redisson的锁重试》

### 上一节课留下的三个坑

上一节课我们把自定义分布式锁"不可重入"的原因分析了一遍，也弄明白了 Redisson 是怎么用哈希结构把可重入做出来的。可重入只解决了三个问题里的一个，我们自己写的那把锁还剩两个坑摆在那儿。

第一个是**不可重试**。我们现在是尝试一次，失败就直接结束了，压根儿没有"再来一次"这种机制。

第二个是**超时释放**。锁总得设个过期时间，不然进程一挂锁就永远卡死。可一旦业务执行得比较长，或者被阻塞了，锁自己就到期被干掉了，此时业务还没跑完，别的线程反倒能拿到锁——安全上就出事了。

第三个是**数据一致性问题**。

> **结论**：Redisson 正好就是来解决这三个问题的。这一节我们把它的源码跟一遍，看看它到底怎么做的。

跟源码之前，先把 `tryLock` 这个方法看明白——这三个问题的答案，全都藏在它那三个参数里。

### tryLock 的三个参数

之前我们的代码里 `tryLock` 都是空参调用，我们就知道它其实有重载版本，参数一共三个：

| 参数 | 含义 | 不传会怎样 |
| --- | --- | --- |
| `waitTime` | 获取锁的**最大等待时长** | 只尝试一次，失败立即返回 `false` |
| `leaseTime` | 锁**自动失效释放的时间** | 取默认值 30 秒，同时**开启 WatchDog 续约** |
| `unit` | 上面两个时间的时间单位 | 必传 |

第一个参数是关键。**一旦你给了 `waitTime`，第一次获取失败之后它就不会立刻返回了**，而是在这个等待时间内不断地去尝试；只有等到时间走完还没拿到，才会返回一个 `false`。

> **定义**：`waitTime` 一给，这把锁就从"一次性的"变成了"可重试的锁"。

第二个参数 `leaseTime` 是锁自动失效释放的时间；第三个是时间单位。

因为我们要研究的就是重试机制，所以等待时间这里是必传的；`leaseTime` 你不传其实无所谓，它有默认值。我们这里就传两个参数：

```java
tryLock(1, TimeUnit.SECONDS)   // 最长等 1 秒；1 秒还拿不到，我不等了
```

跟进去看：第一个参数就是等待时间，第二个 `leaseTime` 因为没传，给的是 `-1`，第三个是时间单位。

再往下，它先把等待时间换算成毫秒——**后续所有的时间运算都是按毫秒做的**——然后取当前时间、取线程 id（这个 id 将来就是锁里的线程标识，非常重要），然后 `tryAcquire` 进去执行真正的获取逻辑。

### 重试：不是盲等，是等一个信号

#### 返回值里藏着一个关键设计

`tryAcquire` 里执行的是我们上节课分析过的那段加锁 Lua 脚本：

- 锁不存在 → 记录线程标识，重复次数加一；
- 锁存在且是自己持有的 → 重复次数加一；
- 否则 → 获取失败。

注意它返回的东西：

- **获取成功返回 `null`**；
- **获取失败返回的反而是一个结果**——脚本里执行了 `PTTL`，返回的是这把锁的剩余有效期。

`PTTL` 和我们以前讲的 `TTL` 效果类似，都是取指定 key 的剩余有效期，只不过 `TTL` 以秒为单位，`PTTL` 以毫秒为单位。因为整个代码都是按毫秒做运算的，所以这里用的是 `PTTL`。

```text
tryAcquire：执行加锁 Lua 脚本
     │
     ├── 返回 null ──────► 加锁成功 ──► 注册 WatchDog 续约 ──► 返回
     │
     └── 返回 PTTL（对方锁的剩余有效期）─► 加锁失败
              │
              ├─ 剩余等待时间 -= 本轮尝试消耗的耗时
              ├─ 剩余等待时间 <= 0 ? ── 是 ──► return false
              │
              └─ 还没超时，那就先 subscribe 订阅"别人释放锁"的信号
                       │
                       ├─ 等待期内收到通知 ──► 重新 tryAcquire
                       │                            │
                       │                            ├─ 拿到锁 ──► 返回成功
                       │                            └─ 还没拿到，剩余时间 <= 0 ──► return false
                       │
                       └─ 等待期内没收到通知 ──► cancel 订阅 ──► return false
```

读图顺序就是一次失败之后的完整走向：**拿到结果 → 判断时间还够不够 → 不够就返回 false，够就等信号 → 收到信号才去重试**。中间那两步时间校验都不是多余的，后面还会再遇到一次。

#### 第一次等待：订阅 + 限时等待

这段代码里拿到的结果是封装在一个 `Future` 里面的。为什么？因为加锁那步是个异步函数（`tryLockAsync`），函数执行完只代表命令发出去了，结果拿没拿到还不清楚，所以是个 `Future`，最终返回的也是它。外面紧跟一个 `get()`，阻塞等待结果，拿到的 `long` 就是剩余有效期。

结果回到最外层，只有两种可能：等于 `null` 代表成功，直接返回；不等于 `null` 代表失败，那就得重试。

但重试之前，先要用当前时间减去最初记下的时间，算出"获取锁这一段消耗了多久"，再用最大等待时间减去这个耗时，得到**剩余等待时间**。这一步必须做，因为获取锁本身是要走网络、跑脚本的，耗时是真金白银。

> **易错点**：如果获取锁消耗的时间太长，把 `waitTime` 整个耗完了，直接 `return false`；只有减完之后还大于零，才可以继续尝试。

那接下来能不能立刻就再试一次？

**不能。** 想想你这边刚刚才失败，那锁现在是别人拿着呢，人家业务还没跑完、没释放。你现在立刻再试，大概率还是失败，除了白白增加 CPU 负担，没有任何意义。

所以这里不能立即尝试，它做的是 `subscribe`——**订阅别人释放锁的信号**。将来真的有人释放了锁，是不是应该发个消息过来，然后它就知道了。

这个订阅不是凭空来的。上一节课我们讲过 `unlock` 的释放脚本，脚本在真正删锁（`DEL`）之后，有一行 `publish`，就是发布一条消息通知。而这里 `subscribe` 订阅的就是这个通知。两边一对上，释放成功它就真能收到。

那具体什么时候收到是不确定的，怎么办？

#### 之后的每一次等待：信号量

这里也返回 `Future`，通过 `future.await` 去等这个结果。它等多久呢？

**只等剩余的最大等待时间。** 如果在指定时间内这个 `Future` 完成就返回 `true`，否则返回 `false`。不是无限制地等。

- 返回 `false`（超时了）：那就没什么好等的了。先**取消订阅**——我都超时了，还订阅干什么，没有意义了——然后返回 `false`。
- 返回 `true`（在时间内收到了释放通知）：`if` 不成立，往下走。这里**又算了一次时间**：用当前时间减之前的时间，得到这一段等待消耗了多久，再用剩余时间减一次，得到现在真正的剩余等待时间。如果它已经小于等于零，也 `return false`。

> **提示**：这个时间运算非常严谨，每等一轮就要重新扣一次，不然累积几次下来就超时了。

如果还有剩余，那**终于可以去尝试了**——这就是第一次重试。重试完又是成功或失败，失败就再判断剩余时间，不够就直接失败，够就再等一次。

这里又用到 `Future`，做的事和 `await` 很像，但机制不同：**这里用的是信号量的方案**。外面释放锁的人会释放一个信号，这边就尝试去获取信号；获取的时候也有一个最大等待时间，指定时间内没拿到返回 `false`，拿到了返回 `true`。

那我到底等多长时间呢？两种情况：

- **锁的剩余有效期（`ttl`）小于我的剩余等待时间**：说明在我等待的时间之内它就已经释放了，那没必要再等了，等 `ttl` 那么久，对方一释放我立刻醒；
- **`ttl` 大于剩余等待时间**：那就只等剩余等待时间。因为它一旦到期对方还没释放，我等下去也没意义了。

不管哪种情况，反正最后都要等。等完之后不管哪个先到期，我醒了，先看时间：如果是因为对方锁到期才醒的，那我的等待时间肯定还没到，往下继续；如果时间到了小于零，这时候直接返回 `false` 失败。但**如果时间还很充足，`while` 又进来，再一次尝试、循环这个过程**。

于是形成了一个"尝试 → 等待 → 尝试 → 等待"的循环：要么我最终拿到锁，要么我超时了，最终返回 `false`。

> **结论**：这里设计得最巧妙的地方，就是**它利用了消息订阅 + 信号量的机制，而不是无休止的盲等**。无休止的盲等就是 `while true` 一直尝试、没有这种"到点就醒"的机制，那样对 CPU 是一种浪费。现在是"我等你释放了，我再来尝试；释放了，我再尝试"，对 CPU 就比较友好了。

至此第一个问题——锁重试——就解决了。**只要你给了 `waitTime`，Redisson 的锁就是可重试的。**

### WatchDog：让锁的有效期一直续下去

第二个问题是超时释放。我现在获取成功了，有一个剩余有效期；万一业务阻塞了，`ttl` 到期被别人拿去锁了，那不就出安全问题了。

所以必须**确保锁是因为我业务执行完才释放，不能是因为阻塞而释放**。

解决办法就藏在 `tryAcquire` 里那段我们刚才没看的代码：

```java
// 加锁成功后 future 完成时挂上去的回调（两个参数就是真实的结果：剩余有效期和异常）
future.whenComplete((res, e) -> {
    if (e != null) {
        return;                       // 中间有问题了，什么都不做
    }
    if (res == null) {                // res == null 才是加锁成功
        scheduleExpirationRenewal(threadId);   // 这时候才去解决有效期的问题
    }
});
```

> **易错点**：`whenComplete` 这段逻辑**只有 `leaseTime == -1` 时才会走到**。如果你自己传了 `leaseTime`，就不会走这套看门狗逻辑，锁到期就是到期。这一点非常容易踩坑，一定要记住。

#### 续约任务挂在哪儿

`scheduleExpirationRenewal` 翻译过来就是"调度一个过期时间的续约任务"。跟进去看，它先创建一个 `ExpirationEntry`，然后放进一个 `Map` 里：

- 这个 `Map` 是 `ConcurrentHashMap`，而且是 `static final` 的；
- key 是 `entryName`，而 `entryName` 就是**当前锁的名称**（我们 `new` 一个锁的时候传进去的那个名字）；
- 因为这个 Map 是静态的，所以 `RedissonLock` 类的**所有实例都能看到它**。

这里要特别想一下：一个锁类将来会创建出很多锁的实例，因为不同的业务会创建不同的锁；每个实例都有自己的名字。所以它们在这个 Map 里都会有各自唯一的 key 和唯一的 entry，**一把锁对应一个 entry，互不重复**。

那怎么保证不重复？用的是 `putIfAbsent`：

- **第一次来**的时候，这个 entry 肯定不存在，走 `putIfAbsent` 把一个全新的 entry 放进去，返回值就是新建的这个 entry；
- **如果是重入**（第二次、第三次），`putIfAbsent` 不会执行，返回值是那个旧的 entry，也就是之前第一个线程创建的那个。

> **结论**：这就保证了**不管这把锁被重入了几次，将来拿到的永远是同一个 entry**。这个静态 Map 起的就是这个效果——保证同一把锁只对应一个 entry。

然后呢，把线程 id 加进去。因为不同的线程不可能拿到同一把锁，所以这里一定是**同一个线程多次来获取**，本质是一种重入。新的、旧的 entry 都会做这个 `addThreadId` 的动作。

**只有第一次来的时候，才会多做一个 `renew` 的动作**——就是续约、更新有效期。

#### 十秒一次，递归下去

再跟进 `renewExpiration`：

```java
private void renewExpiration() {
    ExpirationEntry entry = EXPIRATION_RENEWAL_MAP.get(getEntryName());   // 先从 map 里拿到 entry
    if (entry == null) return;

    Long threadId = entry.getFirstThreadId();
    if (threadId != null) {
        // 一个任务 + 一个延时 + 时间单位：这个延时任务在 delay 到期后才执行
        Timeout task = scheduleTimeoutTask(() -> {
            ExpirationEntry ent = EXPIRATION_RENEWAL_MAP.get(getEntryName());
            Long id = ent.getFirstThreadId();
            if (id != null) {
                renewExpiration(id, ent);      // 刷新有效期
            }
        }, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);

        entry.setTimeoutTask(task);            // 最后把这个任务放到 entry 里
    }
}
```

这里有个关键数字。`internalLockLeaseTime` 是内部的锁释放时间，我们之前把 `leaseTime` 传的是 `-1`，获取锁的时候它取了看门狗的默认超时时间——`getLockWatchdogTimeout()`，值是 `30 * 1000`，也就是 **30 秒**——作为默认的释放时间，最终赋给了 `internalLockLeaseTime`。

那么延时的这段时间是多久？**`internalLockLeaseTime / 3`，也就是 30 ÷ 3 = 10 秒。10 秒钟后这个任务才得以执行。**

10 秒钟之后干什么呢？它从 Map 里取出 entry，从里面取出线程 id，然后调用刷新有效期的函数。里面是一段脚本，做两件事：

1. 先判断这个锁是不是当前这个线程拿的；
2. 是的话，就执行 `PEXPIRE` 重新设置一下有效期。

`PEXPIRE` 一执行，有效期就重置了，相当于**满血复活，重新开始计时**。这一段脚本就是来重置锁的有效期的。

关键的地方来了——**这个延时任务执行完之后，它调的 `renewExpiration` 又是自己**：

```text
scheduleExpirationRenewal(threadId)          ← 只有加锁成功时触发一次
        │
        ├─ EXPIRATION_RENEWAL_MAP.putIfAbsent(锁名, new entry)
        │     首次 → 放入新 entry，才继续往下开启续约任务
        │     重入 → 拿回旧 entry，它里面已经有定时任务了，只把线程 id 塞进去即可
        ▼
renewExpiration()  ──► scheduleTimeoutTask(延时 = internalLockLeaseTime / 3 = 30s / 3 = 10s)
        │
        ▼  10 秒后执行
续约脚本：① 判断锁是否仍是当前线程持有的   ② 是 → PEXPIRE 重置为 30 秒
        │
        ▼
执行完又调回自己 ──► 再挂一个 10 秒的延时任务 ──► 再等 10 秒 ──► …
        │
        └──► 如此往复：锁的有效期被无限重置，永不过期
```

读图就是一条自循环的链：**开启一次 → 每 10 秒重置一次有效期 → 跑完再开启下一次**。所以锁一开始设成 30，过了 10 秒我又把它设成 30，又过 10 秒又设成 30，所以它就永不过期。

这也解释了刚才那个问题：为什么重入的时候拿到旧 entry 就不用再调 `scheduleExpirationRenewal` 了？因为**旧 entry 里已经有那个定时任务了**，它本来就在持续执行，重入只是把线程 id 补进去而已；只有新的 entry 才需要真正去开启。

#### 释放锁时怎么把它收回来

那问题来了：**什么时候才能释放呢？什么时候这个任务才取消？**

自然是在锁被释放的时候。再回到释放锁的逻辑：`unlockInner` 返回一个 `Future`，在它成功之后会执行 `cancelExpirationRenewal`，也就是取消这个更新任务。

怎么取消的？

```java
protected void cancelExpirationRenewal(Long threadId) {
    ExpirationEntry entry = EXPIRATION_RENEWAL_MAP.get(getEntryName());
    if (entry != null) {
        if (threadId != null) {
            entry.deleteThreadId(threadId);      // 先把线程 id 干掉
        }
        Timeout timeout = entry.getTimeoutTask();
        if (timeout != null) {
            timeout.cancel();                    // 再取出定时任务，取消掉
        }
        EXPIRATION_RENEWAL_MAP.remove(getEntryName());   // 最后把 entry 也干掉
    }
}
```

你看这个 Map 的作用是不是就体现出来了？它是静态的，取的时候**根据锁的名称来取**，所以每一把锁都有自己独立的 entry 和独立的定时任务，这里取到的就是当前这把锁的那一个。

线程 id 删掉、定时任务取消、entry 移除——到这儿整个定时任务删得干干净净，锁的释放也就彻底完成了。

> **结论**：所谓看门狗，简单讲就是**每隔一段时间去重置一次有效期**。业务跑多久，它就续多久。

### 把获取锁和释放锁的完整流程串一遍

回过头把两条主线捋一遍。

**加锁**这边的骨架是这样：

```text
tryAcquireAsync
   │
   ├─ 等待时间统一换算成毫秒，取当前时间、线程 id
   │
   ├─ 加锁 Lua 脚本  ──►  返回 null = 成功 / PTTL = 剩余有效期
   │
   ├─ 成功分支：注册 whenComplete → scheduleExpirationRenewal
   │              （仅当 leaseTime == -1 才有 WatchDog）
   │
   └─ 失败分支：剩余等待时间 - 耗时
                 ├─ <= 0 → return false
                 └─ > 0  → 等一个释放信号（第一次订阅，之后用信号量）
                              ├─ 超时 → return false
                              └─ 收到 → 剩余等待时间再扣一次
                                         ├─ <= 0 → return false
                                         └─ > 0  → 回到 tryAcquire，循环
```

**释放锁**这边就简单多了：上来直接执行释放脚本，一般都会成功。也不排除真的因为某种原因超时了，但这种情况发生的概率极低，所以还是做个判断：如果失败了，也不用多做什么，因为失败大概率就是超时导致锁已经释放了，这时不用管就行，最多记个异常然后结束。

如果释放成功，接下来要做两件事：

1. **发送释放锁的消息**——那些重试获取锁失败的人还在等这个信号呢，收到你的信号，人家才可以再次去争抢这把锁；
2. **取消 WatchDog**——之前定义的定时任务是循环往复一直执行的，不取消它就还在，所以一定要取消掉，避免它无休止地执行。

到这里，Redisson 定时更新锁有效期的流程就分析完了。

### 三个问题对照着再过一遍

- **可重入**：基于哈希结构实现，替代了我们原来用的 String 结构。哈希能保存两个东西，所以它就记录了线程标识和重入次数。每次获取锁的时候先判断锁是否存在——不存在就直接获取；已经存在也不代表获取就失败了，如果发现线程标识就是当前线程，那代表可以再次获取，只需要把重复次数加一。将来释放锁的时候，每释放一次重复次数就减一，一直减到零，就证明走到了最外层、所有业务都结束了，才真正去释放锁。这跟我们 JDK 里面提供的 `ReentrantLock` 原理基本一致。
- **获取失败重试**：基于信号量、`subscribe` 订阅这些功能。第一次尝试失败以后，它不是立即失败，而是去做一个等待，等的是"释放锁"这个消息，利用的是 Redis 里的 Pub/Sub 机制；而获取成功的线程在释放锁时会发送这样一条消息，被我们捕获到。拿到消息以后重新获取锁，如果又失败就继续等、再重试。当然这个重试也不是无限制的，它会有一个等待时间，超过就不重试了。因为采用的是这种等待唤醒的方案，所以并不会过多地占用 CPU，效率上来讲还是比较不错的。
- **锁超时释放**：基于 WatchDog 看门狗机制。加锁成功以后开启一个定时任务，每隔一段时间去重置锁的超时时间，也就是重新 `PEXPIRE` 一遍，这样锁的生存时间就会重新计时、满血复活。

至于最后一个——主从一致性问题——我们放到下一节单独讲。

### 主从一致性：锁会凭空消失

前面所有案例我们用的都是单节点 Redis。不妨思考一下：**如果这一台 Redis 发生了故障，会引发什么样的问题？**

可以想象，我们所有依赖 Redis 的业务是不是都会出问题，包括我们的分布式锁。在一些核心业务当中，这样的情况肯定是不允许发生的。

所以为了提高 Redis 的可用性，实际应用当中往往会搭建 Redis 的**主从模式**。所谓主从，就是由多台 Redis 组成，只不过角色不同：一台作为主节点，剩下的作为从节点。它们的职责也不一样，往往做**读写分离**——主节点处理所有对 Redis 的写操作（比如增删改），从节点只负责处理读操作。

那问题来了：既然主节点处理写操作，所有的数据都在主节点里，**从节点没有数据，怎么处理读请求呢？**

所以主从之间需要做数据同步，主节点会不断把自己的数据同步给从节点，确保两边数据一致。但是毕竟不在同一台机器上，主从之间会有一定的延迟，所以这个同步也存在一定的延时——尽管这个延时很短，但它确实存在。我们所说的主从一致性问题，正是因为这样的延时而导致的。

```text
   Java 应用                主节点                从节点
        │                      │                      │
        │ SET lock:thread1     │                      │
        │ NX EX 30 ───────────►│                      │
        │                      │ 保存锁标识            │
        │                      ├──── 数据同步 ───────►│
        │                      │    （同步中……）      │
        │                      │                      │
        │                      │ ✖ 宕机，同步尚未完成  │
        │                      │                      │ 从节点上没有锁标识

  哨兵监控到主节点宕机 → 客户端连接断开 → 从两个从节点中选出一个作为新的主节点

  Java 应用再访问这个新主节点时，就会发现：  锁已经没有了，也就是锁失效了
  此时再有其他线程来获取锁，也能获取成功 →  出现并发安全问题
```

读图就是一句话：**锁写进了主节点，还没同步到从节点，主节点就挂了；新主节点上根本没有这把锁，于是锁凭空消失**。

那 Redisson 是怎么解决的呢？它的思路非常"简单粗暴"：

> **既然主从关系是导致一致性问题发生的原因，那干脆我就不要主从了呗。**

所有节点都变成独立的 Redis 节点，相互之间没有任何主从关系，都可以去做读写。那么获取锁的方式就变了：以前只需要找到 master 节点，在它里面获取锁就行了；现在必须**依次向多个 Redis 节点都去获取锁**。不管你是三个节点还是五个节点，必须依次都获取锁、都保存了这个锁的标识，才算是你获取锁成功。

这时会不会有安全问题呢？

- 因为没有主从，所以不会有主从一致性问题；
- 可用性上，现在真的有一个节点宕机了，Redisson 可不可用？还是可用的。因为你宕机了，还有俩节点呢，只要这两个节点还存活着，锁依然有效。而且**这个可用性不会随着节点的增多而越来越高**——如果你觉得三个不够，可以加五个节点。

所以我们不仅解决了主从一致性问题，也保证了可用性。

如果你还想让可用性更强一点，比如挂一个就少一台，怎么办？没关系，我们**也可以给这里的节点去建立主从关系**，让它们做主从同步。

那加了主从同步以后会不会出现安全问题呢？其实不会。假设真有一个节点发生了宕机，刚好没有完成同步，也就是说这个从节点上没有锁的标识，它会被提升为新的主节点。此时有一个线程趁虚而入想要来获取锁，能不能获取成功？答案是不能——因为只有**每一个节点都拿到锁**才算成功，现在尽管有一个节点是空的，你能在它这拿到锁，但其他两个节点能不能拿到？拿不到吧，所以最终还是失败的。

> **结论**：只要没有任意一个节点在存活着，其他线程就不可能拿到锁，就不会出现锁失效的问题。

这样一套方案保留了主从同步机制，确保了整个集群的高可用性，同时也避免了主从一致性引发的锁失效问题。这套方案在 Redis 里面有个名字叫 **MultiLock**——也就是连锁，把多个独立的锁联合在一起，变成一个联合起来的锁。

使用它的时候是比较灵活的：你可以就弄几个独立节点、不建主从关系，也可以建立主从关系让可用性变得更强。

### MultiLock：每个节点都得拿到锁

#### 三个独立节点，跑一遍看看

接下来我们测试的时候就不去做主从了，因为这样太复杂了，需要的节点太多了，就得六个了。我们就整**三个独立节点**来测这个连锁。

我提前已经用虚拟机搭好了三个 Redis 节点并建立好连接：第一个是最早搭建的那个 6379，往下还有一个 6380 和 6381，这两个是新的、提前准备好的。接下来就用这三个独立的节点形成一个连锁。

配置上要做的事情很简单：找到 `RedissonConfig`，把原来那个（端口 6379 的）复制一份、粘贴两份。三个 Bean 的类型一样，但**名字必须不一样**，分别叫 2 和 3，端口是 6380 和 6381。

```java
@Bean
public RedissonClient redissonClient2() {
    Config config = new Config();
    config.useSingleServer().setAddress("redis://127.0.0.1:6380");   // 新装的节点没配密码
    return Redisson.create(config);
}

@Bean
public RedissonClient redissonClient3() {
    Config config = new Config();
    config.useSingleServer().setAddress("redis://127.0.0.1:6381");
    return Redisson.create(config);
}
```

接下来是单元测试里的写法。有了三个 client，就可以分别获取三个独立的锁，名字改成 `lock1`、`lock2`、`lock3`，分别用 client 1、2、3 去获取。

然后才是真正去创建连锁——这个连锁叫 `MultiLock`，创建方式有多种，给大家看最简单的：

```java
RLock multiLock = client1.getMultiLock(lock1, lock2, lock3);
```

`getMultiLock` 的参数列表里是个**可变参数**，接收了多个 lock，把这三个 lock 依次给它放进去就可以了，它就自动帮我们把这三个连在一起变成连锁了。

有同学会问：你这里为什么用 `client1` 来调，而不是用 client2、client3 去 `get` 呢？

跟进去你会发现这里是 `new` 的。那我去调的时候不管用谁调，最终都是 `new` 一个——甚至于我自己 `new` 都行。所以其实用哪个 client 来调**没有区别**。

传进来的可变参数我们知道是数组，数组传进来以后跟进去可以发现，它被转变成了一个集合，一起添加到成员变量 `locks` 里去了。也就是说我们的多个独立的锁都被收进这个集合了。**按照连锁的原理，将来它在获取锁时，就应该依次把这个集合里边的每一把锁都尝试去获取一遍，都成功了才算成功。**

拿到连锁锁以后，它的使用方式跟以前没有区别，这代码都不用动，直接就可以。

跑起来验证一下：加锁那行返回的是 `true`，说明获取连锁锁成功了。打开 Redis 客户端一看，**三个节点上分别多出来一把锁**，前面是标识、后面那个数字就是锁的重入次数。再进到方法里获取锁一次，又成功了，这时候三边的数字**都变成了 2**，说明是第二次重入——可以看出连锁中的每一个独立的锁都是可重入锁，与之前的实现没什么差别，只不过把三个联合起来分别去获取而已。

释放锁也一样：第一次释放，重入次数减一，三边都从 2 变回 1；再释放一次，回到 Redis 里看，**三个节点上的锁都没有了**，说明这把锁被真的释放掉了。

> **结论**：所谓的连锁就是多个独立的锁，而每一个独立的锁，跟我们之前讲的原理一模一样。

#### MultiLock 里那点门道

跟源码的时候这次我们直接跟 `MultiLock` 的 `tryLock`。这里第一个是等待时间，第二个是时间单位，**释放时间我们没传，没传就是 `-1`**。

跟进去发现，这跟以前有一些差别了。一上来这一段在判断你有没有传 `leaseTime`：

- 如果 `leaseTime != -1`（你传了），再判断 `waitTime` 是不是 `-1`：
  - `waitTime == -1` 说明你只想获取一次，也就是不重试，那你的释放时间是多久我就用多久；
  - `waitTime != -1` 说明你想要去做重试（获取失败我要重试）。那重试的时候他不会用你原来的释放时间了，而是会用 **`waitTime × 2` 来代替**。

为什么？因为**重试可能耗时较久，万一你的释放时间小于等待时间，那我还没重试完锁你就过期了，这不有问题吗。**

我们这儿传的是 `-1`，这块条件不成立，不管它，继续往下。

往下走会先获取当前时间，然后有个 `remainTime`，剩余时间，初始化是 `-1`；如果 `waitTime != -1`，它就会用 `waitTime` 来代替 `remainTime`，也就是说 `remainTime` 就是剩余的等待时间。

再有一个叫 `calcWaitTime` 的方法，计算锁的等待时间。跟着这个方法进去，你会发现它原封不动就返回了——也就是说，**锁的等待时间和剩余等待时间其实是一样的**。

再往下有一个 `failedLocksLimit`，获取失败的锁的一个限制。跟进去一看，值是 **0**。这东西有什么用，等会儿你就知道了。

然后这里有一个集合叫 `acquiredLocks`，acquired 是"已获取的"，所以这个集合里保存的是获取成功的锁。刚创建出来肯定是空的。

接下来开始 `for` 循环遍历 `locks`，遍历每一个独立的锁。进来以后就开始去获取了——因为有两种：如果没传 `waitTime`，其实就尝试一次，走的是空参的 `tryLock`，就是一次不重试；如果传了 `waitTime`，就走带重试的那个 `tryLock`，把等待时间和释放时间都传进去。这两个源码我们之前都跟踪过了，就不再赘述。

不管怎么样，最终你会得到一个结果，是**布尔值**，`true` 或 `false`，代表获取成功或者失败。

```text
for (lock : locks)                       ← locks 就是那几把独立的锁
        │
        ├─ 获取成功 ──► 放进 acquiredLocks
        │                  │
        │                  └─ remainTime -= 本轮已耗时
        │                       └─ <= 0 ──► 先把已拿到的锁全部 unlock，再 return false
        │
        └─ 获取失败
              │
              ├─ locks.size() - acquiredLocks.size() == failedLocksLimit(0) ?
              │     3 - 0 = 3 ≠ 0，不成立；只有已获取数量等于锁的总数量，减完才是 0，才 break
              │     换言之：**只有把所有锁都拿到了，才能结束循环**
              │
              └─ 剩余等待时间耗尽？
                    ├─ 是 ──► 先把已拿到的锁全部 unlock
                    │          ├─ waitTime == -1 ──► 不想做重试，直接 return false
                    │          └─ 还要重试 ──► 清空 acquiredLocks，迭代器指针复位到第一把，重新 for 一轮
                    └─ 否 ──► 继续往下走
```

读图要点两条。第一条：**时间耗尽前 `return false` 之前，一定先把 `acquiredLocks` 里已经拿到的锁全部 `unlock` 掉**——你已经失败了，前面拿到的锁就不能再拿着了，因为拿着别人就拿不了了，干脆释放掉算了。

第二条：**重试的时候是"从第一把锁开始"，不是接着上一把往下试**。因为重试要从头再来，所以代码里先把已经拿到的清空（不管你拿到了几把，哪怕一把都没拿到也给你清空），然后把迭代器指针往前拨回第一个，接着又是一次完整的 `for` 循环。

这样循环往复：**要么我把所有的锁都拿到结束（`for` 循环结束，`return true`），要么就是我超时了最终返回 `false`**。跟之前分析单把锁的重试是不是差不多。

#### 为什么要再 PEXPIRE 一遍

等所有的锁都拿到了，最终肯定要 `return true`。但是在 `return` 之前，它还有一段业务逻辑：**判断这个 `leaseTime` 是不是等于 `-1`。**

我们之前是没传的，是 `-1`，所以这个 `if` 不成立，直接往下走了。但是**假设你传了 `leaseTime`**，那就意味着你需要自己指定锁的释放时间，在这种情况下它会去遍历已经拿到的每一把锁，给它执行 `PEXPIRE`，给每一个锁都重新设置一下有效期。

为什么要做这件事？

我们获取锁的时候有多个 Redis 节点，要依次获取：第一把获取的锁，在获取之后**立即就开始倒计时了**；而最后一把锁是**刚开始倒计时**。也就是说在这个集合内的多把锁里，**第一把的剩余有效期一定会比最后一把的剩余有效期要短一些**。

这样就有可能会出现一个问题：有些释放了，有些没释放。

那为了避免这个问题发生，他在 `return true` 之前干的事情就是：**等所有锁都拿完了，再重新给每一把锁都配一下有效期，确保大家的有效期是一样的。**

> **提示**：为什么只有在 `leaseTime != -1` 的时候才需要做这件事？因为当 `leaseTime == -1` 的时候会触发**看门狗机制**，而有了看门狗机制，所有锁的有效期都会自动去续约，因此这里就不需要你处理了。

所以说我们建议大家，**这个释放时间就不要设置了，让它走 WatchDog**。

### 收个尾：三类锁怎么选

分布式锁这个章节我们总共讲了三大类锁，串起来对比一下：

| 方案 | 可重入 | 获取失败重试 | 锁超时释放 | 主要问题 |
| --- | --- | --- | --- | --- |
| 不可重入的 Redis 分布式锁（自己写的） | 不支持 | 不支持 | 到期自动释放，业务没跑完就有风险 | 实现简单、大多数场景实用；但不适合有重入需求、重试需求，或安全性要求较高的业务 |
| Redisson 可重入锁 | 支持（Hash 记录线程标识 + 重复次数） | 支持（发布订阅 + 信号量） | WatchDog 不断续约，除非服务宕机 | 主从一致性引起的锁失效 |
| Redisson MultiLock 连锁 | 支持 | 支持 | WatchDog 不断续约 | 成本较高——最少得三个独立节点，五个以上更好；可以再加主从提高可用性，但成本更高、实现更复杂 |

具体说说：

**第一种是自己自定义的不可重入锁**，原理是利用 `SET NX` 的互斥性，然后用 `EX` 设置过期时间避免死锁，释放锁的时候去判断线程标识避免误删。缺陷就是不可重入、无法实现重试，而且锁超时可能会有自动释放的风险。但它实现方式非常简单，在大多数场景下还是比较实用的，只不过对于有重入需求、重试需求，或者安全性要求较高的业务场景就不太适合了。

**第二种是 Redisson 的可重入锁**，利用哈希结构记录线程标识和重复次数来实现可重入；再利用 WatchDog 延续锁的剩余时间，不断重新续约，确保这个锁不会因为自动超时而释放（除非是服务宕机）；最后利用信号量 + 发布订阅来控制重试机制，采用等待唤醒的方案，不会无效等待，所以 CPU 这块是比较友好的，性能等各方面都还是不错的。但它的缺陷就是主从一致性引起的锁失效问题。

**第三种是 MultiLock 连锁**：利用多个独立的 Redis 节点，节点之间没有主从关系，就不会因为主从一致导致锁失效；但获取的时候不是只获取一次，而是要在所有节点都获取成功才算成功，你可以把它看成多个可重入锁的集合。它的缺点就比较明显了——**成本比较高**，最少得三个独立节点（当然大于三个、比如五个以上会更好），而且也可以给节点再建主从关系来提高可用性，只不过成本会更高、实现起来更复杂。但是，它**是所有方案里最安全的一种**。

到这里分布式锁的所有知识就讲完了。之前我们也用 Redisson 的分布式锁代替了自定义分布式锁，实现了"一人一单"，测试也没有什么问题，到这里整个秒杀相关的业务就做完了。

但是，正是因为我们加入了各种各样的锁，秒杀业务的性能也会受到巨大的影响。所以后续我们还需要对秒杀的业务做进一步的优化，从而提升它的性能。具体怎么做，我们会在接下来的课程里继续学习。
