## 数据库安全：谁能进来，谁能看，谁还能留下痕迹
> 对应块：BLK13 | 覆盖分集：P11 | 块标题（分集名）：《数据库第4章 数据库的安全性》

### 先把第四章放回数据库的地图里

先别急着背 `GRANT`，我们把这门课的知识地图再摆一次。

数据库课程的前几章，沿着一条很清楚的线往前走：第一章讲概述，关系数据库和关系代数，第三章讲 SQL。到第四章，我们才把 SQL 语言里还剩下的那一块补上。

SQL 语言有三个方面的功能。数据的定义，用 DDL；数据的操作，主要是 DML；数据的控制，用 DCL。前面的章节已经处理了数据库模式、表、索引、视图如何创建、删除和修改，也在第三章集中讲了 `INSERT`、`UPDATE`、`DELETE`、`SELECT`。现在回头看，剩下的就是“数据怎么控制”。

而“数据的控制”又分成两件事：数据库的安全性，以及数据库的完整性。这正好是第四章和第五章要接上的位置。前面五章走完，才进入后面的数据库设计。

所以第四章不是孤零零地讲一堆安全术语。它要回答的是：数据库已经建起来了，表也已经有了，谁可以进来？谁能看哪些数据？谁能改哪些列？什么时候改？改过之后又能不能查到痕迹？

这一章的篇幅其实不长，内容也不多。我们可以把重点先抓住：

- 安全性问题可能从什么地方来；
- 安全性控制是怎样一层一层建立起来的；
- `GRANT` 和 `REVOKE` 怎么把权限送出去、收回来；
- 强制存取控制怎样用敏感度标记做决定；
- 视图、审计、加密分别在什么地方补上控制。

如果考试一定要从这一章出题，最值得留意的是 SQL 里的授权和收回，也就是 `GRANT`、`REVOKE`；审计也有可能被考。安全性概述可以帮助我们理解问题，但它不是这一章最集中的考点。数据加密在这一门课里不算重点。

### 安全问题先问清楚：它到底从哪里来

#### 主观破坏和客观故障，都是安全问题

“数据库安全”听起来像是防止黑客，其实不只如此。

第一类，是有人主动想要破坏数据库：改数据、删数据、泄露数据、篡改数据，甚至绕过正常的管理规则去做这些事。

第二类，是硬件或者软件出了故障。硬盘坏了，机器坏了，原本保存的数据丢了，这当然也是数据库安全要面对的问题。

所以，安全性不是只盯着“恶意用户”这一种人。人的主观破坏是一条来源，软硬件的客观故障也是一条来源。把两条来源都看见，后面的控制思路才不会只盯着密码。

#### 个人端、互联网、服务器，每一个环节都可能出问题

我们先看一张通用的三层架构图。这里把一台电脑看作单一的客户端，手机、iPad、电脑都算客户端。

```text
个人客户端：手机 / iPad / 电脑
              │
              │ 公开互联网
              │ TCP/IP 分组交换
              ▼
        Web server（网页服务器）
        网址、导航、邮件等
              │
              ▼
    Application server（应用服务器）
    处理观看、输入、弹幕、投币等交互
              │
              ▼
       Database server（数据库服务器）
              实际数据库
```

取数据的时候，路径大致反过来。你点开一个视频主页，再点进某一集，网页服务器和应用服务器把交互一路处理完，最后数据从数据库服务器返回来。

这张图不是数据库教材里的原图，但我很喜欢用它建立感觉：安全问题不只发生在数据库文件本身。个人客户端可能泄露密码，硬件和软件可能坏掉；数据经过公开互联网时，包会被拆分、加表头、分组传播；后端服务器同样可能遭受攻击。

服务器性能高，并不代表它天然安全。常见的攻击思路之一是 DOS，也就是 Denial of-Service，拒绝服务：如果服务器的访问量承受不住，就把它压垮。如果服务器本身比较 robust、比较能扛，还可以虚拟出多个分布式 IP 地址，同时访问一个目标，这就成了 DDOS，也就是 Distributed Denial-of-Service。核心仍然是让访问量超过它能承受的范围。

> **结论**：安全问题的范围，要沿着“客户端—网络—服务器—数据库”整条路径去找，不能只盯着数据库服务器。

#### 企业数据管理架构里，数据库也不是孤立的一格

再看企业端常见的数据管理架构：

```text
信息源 / 历史数据 / POS 机 / 网页实时数据 / 外部导流数据
                              │
                              │ 提取、转换、加载
                              ▼
                         Data warehouse
                              │
                    备份；生成 metadata
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
          Data mart                       Data mart
        职能部门的数据集                  职能部门的数据集
              │                               │
              └───────────────┬───────────────┘
                              ▼
                 application interface / middleware
                              │
                              ▼
             数据可视化、数据挖掘、在线实时分析
                        以及其他 application
```

原始数据可以把它想成图书馆里的书，`metadata` 就是图书馆的索引。数据先进入数据仓库，再按不同职能部门形成数据集市，也就是更小的数据集合，最后通过应用接口或中间件提供给可视化、挖掘、在线实时分析等应用。

如果数据库出了安全问题，不能只问“用户有没有输对密码”，还要问：数据在数据仓库里有没有被不当访问？数据集市之间的数据有没有被拿错？应用接口有没有把不该暴露的东西传出去？

这正是从整体架构看安全，而不是把数据库当成一台孤零零的机器。

### 两套安全标准：TCSEC 与 CC

#### 不安全因素：越权、泄露、脆弱的环境

数据库安全概述里，最先列出的不安全因素并不复杂：

- 非授权用户对数据库进行恶意存取和破坏；
- 数据库中的敏感数据被泄露；
- 安全环境本身比较脆弱。

它们看起来像三个短语，实际上对应了完全不同的控制方向。第一种要防越权，第二种要防数据暴露，第三种要靠整个运行环境和保护机制一起支撑。

#### TCSEC：从 D 往 A 逐级提高

数据库安全标准里，最早的一套是 1985 年美国国防部颁布的 DoD 可信计算机系统评估准则，通常简称 TCSEC，也叫 DoD85。它的基本思路是给安全等级分层，再按照系统达到的等级来判断它处在什么保护水平。

TCSEC 使用 A、B、C、D 四个大等级，细分为 A1、B3、B2、B1、C2、C1、D。

| 等级 | 课程中对应的名称 | 这条线要记住的含义 |
| --- | --- | --- |
| A1 | Verified design | 验证设计，保护级别最高 |
| B3 | Security domains | 安全域 |
| B2 | Structured protection | 结构化保护 |
| B1 | Labels | 标记性保护 |
| C2 | Controlled access protection | 受控的存取保护 |
| C1 | Discretionary security protection | 自主安全保护 |
| D | Minimal protection | 最小保护，等级最低 |

从 D 往上走，保护越来越强。A 最高，D 最低。B1 的 `labels` 这个词尤其要记住，因为后面强制存取控制会直接用到“敏感度标记”。

这里不要把整套等级表当成一大串要背的名词。真正要抓住的是：TCSEC 按 A、B、C、D 划分，A 最高、D 最低；而“验证设计”已经可以对数据库的框架进行结构性验证，所以处在最高层。

#### CC：从 1 往 7 逐级提高

另一套标准是 CC，也就是 Common Criteria。逐字稿里提到，1993 年左右，几个标准开始联合，试图解决原标准中概念和技术上的差异，形成 Common Criteria。它是后来演化出来的标准，现在行业里通常更多地使用 CC。

CC 的评估等级是 1 到 7，等级逐级上升，7 最高，1 最低。它从功能测试、结构测试，一直发展到形式化的验证、设计和测试。

因此，如果只需要记住两套标准的关系和方向，可以这样收束：

```text
TCSEC：最早的数据库安全标准，按 A / B / C / D 划分
        A 最高，D 最低

CC：后来演化出来的标准，按 1 / 2 / 3 / 4 / 5 / 6 / 7 划分
    7 最高，1 最低
```

不要被名称的差异绕进去。TCSEC 的 ABCD 和 CC 的 1234567，是两套不同的等级体系；先分清是谁，再记方向。

### 安全控制不是一件事：从身份到审计的链条

#### 非法使用不只有一种样子

非法使用数据库，至少可以分成几种情形。

一种是编写合法程序，绕过原本的授权机制，直接执行非授权操作。另一种是编写应用程序，借着应用程序去做本来没有被允许的操作。还有一种更隐蔽：通过多次合法的查询，从数据库已有数据里推导出保密数据。

我们可以用一个很直观的例子理解最后一种。某个人虽然没有直接拿到一个单位的核心数据，但如果他知道一些零散的信息，比如 X1、X2、X3，就可能通过合法的查询把核心内容推导出来。结果虽然没有“越权读取一个文件”，但敏感信息仍然泄露了。

所以“所有操作都合法”不一定意味着“所有结果都安全”。这也是为什么要考虑推理控制。

#### 每一级都有自己的保护任务

数据库管理系统不是孤零零地立在那里，它运行在操作系统之上，实际数据又要落在存储上。理解安全控制时，可以把这条层次关系画出来：

```text
用户
  │
  │ 用户标识与识别：你是谁？
  ▼
数据库管理系统（DBMS）
  │ SQL 检查、权限检查、推理控制等
  ▼
操作系统（OS）
  │ 负责 0/1 与磁盘存储之间的具体映射
  ▼
实际数据
  └─ 数据本身也需要得到保护
```

用户端的用户标识与识别是第一道门；DBMS 负责数据库层面的保护；操作系统还要负责它所掌握的底层存储保护；数据实际存放的位置也不能完全裸放着。

在更细一点的安全控制模型里，身份鉴别之后，系统还要处理 SQL 操作和推理控制，再进入强制存取控制和自主存取控制。真正到了数据层，系统不一定还能阻止已经获得合法身份的人，但可以加上审计日志，记录他做过什么。

可以把完整思路记成下面这条链：

```text
用户提出访问请求
        │
        ▼
身份鉴别：用户名、密码等是否通过？
        │
        ▼
SQL 与推理控制：这条操作是否允许？结果会不会推出保密信息？
        │
        ▼
自主存取控制（DAC）与强制存取控制（MAC）
        │
        ▼
数据层执行或拒绝
        │
        └── 全过程由审计日志留下记录
```

图里的重点不是死背两个访问控制的先后顺序，而是记住：身份、SQL 规则、DAC、MAC、数据执行和审计，分别在链条上承担不同任务。

#### 用户身份鉴别：先把“你是谁”问清楚

用户身份鉴别就是我们熟悉的那些办法：静态口令、密码、动态口令、U 盾、短信验证码、生物特征识别，比如指纹和人脸，还有智能卡识别。

这一部分和课程中 SQL 控制的重点相比，了解含义即可。我们不需要在这里展开每一种识别设备，但要知道，数据库安全的第一步始终是把用户身份和后续权限对应起来。

> **定义**：用户权限先被定义出来，再登记到数据字典里。用户登录或访问时，系统根据其身份和权限做合法性检查，允许的范围就通过，被拒绝的操作也就在这里被挡住。

#### 存取控制的两种门：DAC 与 MAC

常用的存取控制方法有两类。

一类是自主存取控制，叫 Discretionary Access Control，简称 DAC。另一类是强制存取控制，叫 Mandatory Access Control，简称 MAC。

它们在前面那套 TCSEC 等级里对应的位置不同：DAC 对应 C2，MAC 对应 B1。因为 B 比 C 高，所以 MAC 的保密级别更高。

| 对比 | 自主存取控制 DAC | 强制存取控制 MAC |
| --- | --- | --- |
| 英文全称 | Discretionary Access Control | Mandatory Access Control |
| 对应等级 | C2 | B1 |
| 决定方式 | 权限拥有者可以授予、收回 | 由制度化的密级规则决定 |
| 典型直觉 | “我可以把成绩读给你，但暂时不给你改成绩的权限” | “你的身份等级和文件密级不匹配，就不能操作” |
| 课程中的场景 | 期末录成绩时开放写入窗口 | 给人和文件都标 TS、S、C、P 等级 |

举个 DAC 的例子。老师可以把成绩单的查询权限给学生，但是不必一直给学生修改 `grade` 这一列的权限。成绩录入期间，老师再把更新权限放出来；过了这个时间窗口，再把权限收回去。于是“看得到”和“改得了”被拆开了。

这正是 `GRANT` 和 `REVOKE` 要完成的事情，也是这一章最需要练熟的 SQL 部分。

### GRANT：把权限送到谁手里

#### 语句的骨架

`GRANT` 的标准骨架可以先记成：

```sql
GRANT <权限列表>
ON [对象类型] <对象名>
TO <用户>[, ...] [WITH GRANT OPTION];
```

逐字稿里反复出现的记号就是 `GRANT ... ON ... TO ...`，最后还可以加 `WITH GRANT OPTION`。

它可以作用于很多对象：模式、基本表、视图、索引都可以。涉及数据操作时，增加、删除、修改、查询这些权限也可以设置；针对某一个属性列，还可以只授权某一列。

发出授权的人可以是管理员、对象的创建者，或者已经拥有这个权限的人。接受授权的人可以是一个，也可以是多个；写成 `PUBLIC`，表示全体用户。

#### `WITH GRANT OPTION`：权限到谁那里停

`WITH GRANT OPTION` 决定收到的用户能不能继续把这个权限传播出去。

比如老师把成绩单表的 `INSERT` 权限给学委。如果不加这个选项，权限到学委这里就停了。学委不能把“录成绩”的权限再传给别人。

如果加上：

```sql
GRANT INSERT ON TABLE SC TO U5 WITH GRANT OPTION;
```

那么 U5 收到 `INSERT` 权限后，就可以继续把这个权限授给别人。它不是把数据直接给了 U5，而是把“授予这项权限的能力”一并交给了 U5。

反过来，如果没有写 `WITH GRANT OPTION`：

```sql
GRANT INSERT ON TABLE SC TO U7;
```

U7 就只能使用自己收到的权限，不能再往下传。

> **易错点**：`WITH GRANT OPTION` 传递的不是一份孤立的权限记录，而是一种继续授权的能力。没有这个选项，权限传播链就在接收者这里停止。

#### 七个例子，走一遍授权传播

先把最基本的写法放在一起看：

```sql
GRANT SELECT ON TABLE STUDENT TO U1;

GRANT ALL PRIVILEGES ON TABLE STUDENT, COURSE TO U2, U3;

GRANT SELECT ON TABLE SC TO PUBLIC;

GRANT UPDATE(Sno), SELECT ON TABLE STUDENT TO U4;

GRANT INSERT ON TABLE SC TO U5 WITH GRANT OPTION;
```

逐句解释：

- 第一句把查询学生表的权限给 U1。
- 第二句把 `STUDENT` 和 `COURSE` 两张表的全部权限给 U2、U3，表名和用户都用逗号隔开。
- 第三句把查询成绩单的权限给全体用户。
- 第四句给 U4 查询学生表和修改学生学号的权限。这里 `Sno` 就是被单独限制的属性列；如果不写列名，更新权限就针对整张表，写了列名，U4 只能更新这一列。
- 第五句把成绩单表的 `INSERT` 权限给 U5，并允许 U5 再授权。

接下来让 U5 把权限传出去：

```sql
GRANT INSERT ON TABLE SC TO U6 WITH GRANT OPTION;

GRANT INSERT ON TABLE SC TO U7;
```

U5 因为有 `WITH GRANT OPTION`，可以把 `INSERT` 给 U6；U6 收到后也有再授权的能力，所以可以把 `INSERT` 给 U7；U7 没有 `WITH GRANT OPTION`，传播到此为止。

如果 U5 后来想把权限再传回自己，形成一个圈，这是不允许的。权限可以沿着链向下传播，但不能转成环。

这七个小例子跑完之后，系统后台会保存一张权限传播表。它至少要记录：谁把权限给谁、对哪张表或哪一列、给了什么操作、接收者能不能继续传播。课程中是为了讲清楚而把这张表画出来；实际系统会在后台维护对应的授权信息。

| 授权路径 | 对象与操作 | 能否继续传播 |
| --- | --- | --- |
| DBA → U5 | `SC` 表的 `INSERT` | 可以，U5 有 `WITH GRANT OPTION` |
| U5 → U6 | `SC` 表的 `INSERT` | 可以，U6 有 `WITH GRANT OPTION` |
| U6 → U7 | `SC` 表的 `INSERT` | 不可以，U7 没有该选项 |

### REVOKE：把已经送出去的权限收回来

#### `ON ... FROM ...` 是收回的方向

有授权，就要有收回。`GRANT` 的方向是 `ON ... TO ...`，对应的 `REVOKE` 就是 `ON ... FROM ...`。

基本骨架是：

```sql
REVOKE <权限列表>
ON [对象类型] <对象名>
FROM <用户>[, ...]
[CASCADE | RESTRICT];
```

`CASCADE` 和 `RESTRICT` 的差别，发生在被收回的权限已经继续传播出去的时候。

#### `CASCADE` 与 `RESTRICT`：连坐，还是先停下

假设 U5 把 `SC` 表的 `INSERT` 给了 U6，U6 又给了 U7。现在要收回 U5 的权限。

使用 `CASCADE`，就表示把从 U5 这条传播链继续传出去的权限一起收回。前面例子里的 U6、U7 都会跟着被删掉。

使用 `RESTRICT`，系统不会直接让收回操作完成，而是提示你：U5 已经把权限传给别人了，后面还有依赖它的授权。你必须先把下游的 U6、U7 处理干净，系统才允许收回 U5 的权限。

```text
U5 ──INSERT──> U6 ──INSERT──> U7

REVOKE ... FROM U5 CASCADE
    └─ U5、U6、U7 的相关权限一起收回

REVOKE ... FROM U5 RESTRICT
    └─ 先要求处理 U6、U7，再收回 U5
```

课程中给出的收回例子包括：

```sql
REVOKE UPDATE(Sno) ON TABLE Student FROM U4;

REVOKE SELECT ON TABLE SC FROM PUBLIC;

REVOKE INSERT ON TABLE SC FROM U5 CASCADE;
```

第一句收回 U4 对 `Student` 表学号列的更新权限；第二句把成绩单的查询权限从全体用户那里收回；第三句把 U5 对 `SC` 的 `INSERT` 权限收回，并把它传播到 U6、U7 的相关授权一起收回。

于是前面那张传播表里，从 U5 开始的链就消失了。权限不是只在你发出 `GRANT` 的那一刻有用；只要对象、列、操作、用户都还匹配，它就会在授权链上一直存在，直到被 `REVOKE` 收掉。

> **结论**：`GRANT` 和 `REVOKE` 很灵活，可以针对对象、属性列和操作进行授权，也可以针对一个或多个用户收回。灵活性正是“自主”这个词的来源。

### 用户身份与角色：别把一百个名字写成一百遍

#### `CREATE USER` 时的三类身份

`CREATE USER` 用来创建用户。创建时，用户就可以带有不同的初始身份；课程把常见的三类归成 `CONNECT`、`RESOURCE` 和 `DBA`。

| 身份 | 课程中的权限范围 | 用学校来理解 |
| --- | --- | --- |
| `CONNECT` | 可以连接数据库，不能创建用户、模式或基本表 | 普通同学 |
| `RESOURCE` | 可以创建基本表和视图，不能创建数据库模式，也不能创建新用户 | 需要建表、录成绩的教师 |
| `DBA` | 可以创建新用户、模式、基本表，几乎什么都能做 | 数据库管理员 |

如果没有指定创建新用户的权限，默认就是 `CONNECT`。它的意思很直白：可以登录数据库，但不能因为登录了，就获得创建更多数据库对象的能力。

`RESOURCE` 比 `CONNECT` 高一级，适合需要创建基本表和视图的用户；但它仍然不能动数据库的整体框架，也不能创建新用户。把它放到学校场景里，就是老师可能需要做表、录成绩，却不能随意改变教务处数据库的框架。

`DBA` 是最高的身份，可以创建用户、模式和基本表，可以做各种事情。你可以把它理解成数据库系统里的超级用户。

这里不必死记整张权限表，真正需要掌握的是：先创建用户，再根据用户的实际身份分配 `CONNECT`、`RESOURCE` 或 `DBA`；之后还可以用 `GRANT` 和 `REVOKE` 对具体权限继续授权和收回。

#### 角色：一组用户的集合

如果没有角色，给一个班的一百个同学发成绩单查询权限，就得把一百个用户名逐个写到 `TO` 后面。名字一长，授权和收回都很麻烦。

角色解决的就是这个问题。它是一个虚拟概念，可以看成用户集合：

```text
学生角色
  ├── 100 个同学
  ├── 后来加入的第 101 个同学
  └── 其他班需要同样权限的同学
```

先创建角色，再把权限授给角色，最后把角色授给用户。集合里的用户就一次性具备角色上的权限；以后新增符合这个角色的人，也只需要把新用户加入角色，不必重新写一遍所有对象和操作。

一个完整的最小例子是：

```sql
CREATE ROLE R1;

GRANT SELECT, UPDATE, INSERT ON TABLE Student TO R1;

GRANT R1 TO U1, U2, U3;
```

`R1` 拥有学生表的查询、更新、插入权限。把 `R1` 授给 U1、U2、U3 后，这三个用户就同时获得这些权限。给一百个人也是同样的逻辑。

收回时也一样，不用把一百个人逐个处理。逐字稿里用“把王平从群里踢出去”作比喻：

```sql
REVOKE R1 FROM 王平;
```

这不是只删除一个人的某一条零散记录，而是让他不再通过这个角色获得相应权限。

#### 修改角色，不用先描述旧状态

SQL 是一种高度非过程化的语言。你不需要先告诉系统“角色原来是什么样，再把它改成什么样”。直接用 `GRANT` 增加权限，用 `REVOKE` 收回权限就行。

```sql
GRANT DELETE ON TABLE Student TO R1;

REVOKE SELECT ON TABLE Student FROM R1;
```

第一句给 `R1` 增加删除学生表数据的权限；第二句把 `R1` 对学生表的查询权限收回来。角色权限的修改，本质上还是前面那两组语句。

#### `WITH ADMIN OPTION`：角色也可以继续发展成员

角色上的权限如果要继续传播给其他用户，使用 `WITH ADMIN OPTION`。它和 `WITH GRANT OPTION` 是同一种思路，只是作用对象不同：

- `WITH GRANT OPTION`：用户收到的是对象权限，并且可以继续授权；
- `WITH ADMIN OPTION`：用户收到的是角色，并且可以继续把角色发展给别人。

可以把角色想成一个微信群。老师把“建立和维护这个群”的能力交给班长，班长再把成员管理能力交给小组长；`WITH ADMIN OPTION` 就是允许这种角色继续向下传播。

角色授权、角色收回、角色权限增加、角色权限删除，核心仍然没有跳出：

```text
GRANT ... ON ... TO ...
REVOKE ... ON ... FROM ...
```

### 强制存取控制：让标记替你做决定

#### 给人和文件都贴上密级

强制存取控制通常用于政府和军事部门，标准做法是敏感度标记，也就是前面 TCSEC 里的 `label`。

我们把人分为主体，把文件分成客体。主体有自己的 `clearance level`，也就是人的许可证级别；客体有自己的 `classification label`，也就是文件的密级标记。

课程中给出的四个等级从高到低是：

```text
TS：Top Secret，绝密
S ：Secret，秘密
C ：Confidential，机密
P ：Public，公开

TS ≥ S ≥ C ≥ P
```

人和文件都贴上这四级标签之后，系统就能进行强制的等级比较。它不是看谁在当前操作中“想不想给”，而是看制度和标记本身是否允许。

#### 两条规则：读和写的方向不一样

强制存取控制有两条规则：

```text
读：主体许可证级别 ≥ 客体文件密级

写：主体许可证级别 ≤ 客体文件密级
```

第一条容易理解。一个 TS 级员工当然可以读 S、C、P 级的文件；一个 P 级员工不能因为文件存在，就去读 TS 级文件。

第二条看起来反直觉：为什么写文件时，人的级别要“小于等于”文件密级？我们用一个航天科工的程序员例子来想。

很多工程师分别编写代码、制作小零件，但通常不会让每个人都知道，某段代码或某个零件最终会被放进哪一个模块，更不会让它进入整个飞船时承担什么用途。假设某个低等级员工只能接触很低密级的工作，他可以把自己编出来的东西提交到更高等级的文件中，却不能把更高等级文件的内容读回来。

这样，材料可以向更高的密级流转，秘密却不会因为提交过程自动流回低等级人员手里。

```text
低等级主体 ──写入──> 高等级文件
低等级主体 ──不能读──> 高等级文件
```

这就是强制存取控制强调规范和密级的原因。数据本身带有密级，复制时标记不可拆分，不能因为复制了一份，就把密级标签拆掉。

> **易错点**：写权限不是“级别越高越能随便写”。在本课程的规则里，主体许可证级别要小于等于客体密级；这正是保密场景和普通文件编辑直觉不同的地方。

#### DAC 与 MAC 合起来，才形成完整控制

DAC 更像权限拥有者作出的灵活决定：这个表谁能查、谁能改、什么时候开放。MAC 则把人和对象的密级固定下来，由规则直接判断。

因此，一个访问请求不能只看“SQL 语法写对没有”，还要通过 DAC 和 MAC 两道访问控制检查。语法、语义、权限和身份等级，都可能成为请求被拒绝的原因。

这也解释了为什么课程会把 `GRANT`、`REVOKE` 放在 DAC 这一节：它们把权限灵活地送给一个用户、多个用户、全体用户，或者一个角色；而 MAC 则用敏感度标记在更高的制度层面约束访问。

### 视图：把不该看的列挡在门外

#### 先投影，再授权

视图之所以能够帮助控制安全性，是因为它可以把基本表中的部分数据投影出来，再对这个受控的结果授权。

比如一个基本表里有很多数据，但我们只想给财务处的老师看其中某两列。与其把基本表整个交出去，不如先只把这两列形成视图，然后给这个视图设置查询权限。拿不到视图背后的完整基本表，自然也就看不到未授权的部分。

课程中的例子是建立一个“计算机系学生”的视图：把 `Student` 表中计算机专业对应的行选出来，形成一个新的视图。它基于一个表筛选行和列，所以属于行列子集视图。

```text
Student 基本表：包含完整数据
          │
          │ 选择计算机专业，并只保留需要的列
          ▼
CS_Student 视图
          │
          ├── 王平：查询权限
          └── 张明：所有操作权限
```

视图定义出来以后，使用方式可以和表类似。我们可以直接对视图做 `GRANT` 和 `REVOKE`，而不是先把底层基本表交出去。

所以视图能做到的是“部分的数据安全性控制”：它可以限制用户从哪个入口看到哪些数据，但不能把它当成完整的替代品。基础表、其他视图、角色和其他访问路径，仍然要一起考虑。

### 审计：阻止不了的人，至少留下痕迹

#### 审计日志就是把操作写成日记

审计做的事情很直接：把用户对数据库的操作，像写日记一样写进 `auditing log`。

一个老师登录教务处数据库，登录这件事记下来；他找到某个班的成绩单，执行 `SELECT`，记下来；修改成绩单的某些数据，执行 `UPDATE`，也记下来；最后退出系统，再记下来。这样回头追查时，至少知道是谁、在什么时候、做过什么。

审计当然费时间和空间。要把所有操作都记下来，不可能完全没有成本。但它有一个很实际的作用：身份鉴别、`GRANT`/`REVOKE` 的自主存取控制、强制存取控制都通过以后，如果这个人仍然做了不该做的事，或者问题来自内部，系统已经不一定能阻止他，却还能留下证据。

例如成绩单被改了，系统可以查出：

- 是哪个用户进入了数据库；
- 他查看过什么；
- 他执行了什么修改操作；
- 修改前是什么，修改后是什么；
- 必要时据此把数据改回去。

> **结论**：审计不是用来代替权限控制的“最后一道密码”，而是权限控制已经无法阻止时的事后补救和追责手段。

#### 审计可以按事件、权限、语句和对象设置

审计事件不只一种粒度：

- 可以审计服务器事件，例如用户连接服务器；
- 可以审计系统权限；
- 可以审计某类语句；
- 也可以只针对特定模式中的特定对象。

并不是所有查询都必须审计。课程里说，查成绩单这类操作按道理可以不做那么细的记录；更节省时间、空间的做法，是只针对成绩单中 `grade` 这一列的更新操作设置审计。这样审计范围更小，性能代价也更容易控制。

#### `AUDIT` 与 `NOAUDIT`

对 `SC` 表的结构修改和数据进行修改，可以分别设置审计；取消时使用 `NOAUDIT`。课程中围绕这两个命令的思路可以写成：

```sql
AUDIT ALTER ON SC;

AUDIT INSERT, UPDATE, DELETE ON SC;
```

取消时对应使用：

```sql
NOAUDIT ALTER ON SC;

NOAUDIT INSERT, UPDATE, DELETE ON SC;
```

第一组关注表结构，第二组关注数据变化。这里要注意，审计的具体范围可以根据要保护的对象和操作来选择，并不是说所有操作都必须写日志。

审计会在数据库恢复部分再次出现。到那里还会结合数据库故障、恢复和证据追踪继续讲。这一章先把它的位置记住：身份鉴别和访问控制试图把不允许的操作挡在门外；审计负责在门已经被绕过之后，尽可能把过程留下来。

### 加密：明文不该在路上裸奔

#### 从明文到密文：先约定算法

加密的基本思想，是用一定算法把原始数据的明文转换成不能直接识别的密文。

课程用一串数字举了一个最简单的例子。发送方和接收方先约定：发送时把数字乘以 2 再减去 1；收到后先加 1，再除以 2。

设原文是 $x$，发送的密文是 $y$：

$$
y=2x-1
$$

接收方拿到 $y$ 后恢复：

$$
x=\frac{y+1}{2}
$$

如果数据在传播过程中被截获，截获者看到的只是按算法处理后的格式；除非他知道双方约定的算法，否则不能直接认出原文。

#### 存储加密和传输加密

从前面那张系统架构图看，加密至少有两个位置。

第一类是存储加密。数据存在硬盘或其他存储位置时，可以在明文和密文之间转换，避免数据以原始形式直接暴露。

第二类是传输加密。数据要经过公开互联网，也可能在服务器内部的网络中传播，因此传播过程本身也要保护。

TCP/IP 会把文件切割、加表头、装入分组之后再传播。课程在七层网络模型中提到数据链路层，也提到链路加密；除此之外还有端到端加密，也就是从发送端加密，到接收端再解密。

#### 建立可信连接的过程

可以把一次可信传输记成五步：

```text
创建可信连接
      │
      ▼
确认双方端点的可靠性
      │
      ▼
协商加密算法和密钥
      │
      ▼
以密文形式传递可信数据
      │
      ▼
关闭可信连接
```

确认双方端点可靠性时，课程提到 CA 和 certificate，也就是数字证书。早些年使用网页付款时，点完付款后常会经历几秒钟的等待，就是在验证付款机构、银行机构之间的证书关系。没有问题，才表明双方身份可信，付款流程才可以继续。

密钥部分还会涉及公钥和私钥；数据在网络中传输时以密文形式出现。这里不必把所有密码学展开，我们先把加密在本章中的位置认出来：它保护的是数据的存储形态和传播过程，而访问控制保护的是“谁可以对什么数据做什么操作”。

此外，推理控制、隐蔽信道和数据隐私保护，本章也提到了这些安全问题，但这里不对它们另起一套没有讲过的细节。知道它们属于数据库安全的其他保护方向即可。

### 把整条安全链串起来

现在再回到开头那张图，数据库安全就不是一句“设置密码”能概括的了。

安全问题有两类来源：人为主观地想改、删、泄露、篡改数据，以及软硬件故障造成数据丢失。个人端、公开互联网、Web 服务器、应用服务器、数据库服务器，企业端的数据仓库和数据集市，每一个节点和传播环节都可能成为问题发生的位置。

标准上，TCSEC 用 A、B、C、D 划分，A 最高、D 最低；CC 用 1 到 7 划分，7 最高、1 最低。TCSEC 是较早的一套，CC 是后来演化出来的标准。

控制上，先做用户身份鉴别，再经过 SQL 与推理控制等检查；自主存取控制用 `GRANT`、`REVOKE` 灵活地管理对象、列和操作权限，强制存取控制用 `TS`、`S`、`C`、`P` 等敏感度标记比较人和文件的密级。视图可以把基本表的一部分投影出来，审计在控制已经无法阻止操作时留下痕迹，加密则保护数据的存储和传播。

所以安全不是某一个点，而是一条链：

```text
确认身份
  → 判断是否允许这项访问
  → 限制能看到、能改的对象和列
  → 对高密级对象执行强制规则
  → 在数据层执行操作
  → 需要时把全过程写入审计日志
```

再往下一章，我们会转向数据库的完整性：用户完整性、参照完整性和实体完整性，以及它们从 SQL 语句角度如何进行控制。这里先把边界记住：安全性主要问“谁能做什么”，完整性继续问“数据本身是否始终满足应该满足的条件”。

> **承前启后**：上一节讲完「数据库安全：谁能进来，谁能看，谁还能留下痕迹」，下一节接着讲「让数据符合语义：数据库完整性」。

## 让数据符合语义：数据库完整性
> 对应块：BLK14 | 覆盖分集：P12 | 块标题（分集名）：《数据库第5章 数据库完整性（第一部分：实体完整性》

“学号必须唯一”“性别只能取男或女”“年龄要在规定范围内”——数据一进入数据库，能不能放进来、能不能这样改、能不能删掉，都不是“看着差不多就行”，而要遵守事先定好的规则。

这就是数据库完整性。它要回答的是：数据库里什么样的数据合乎语义、什么样的操作允许发生。第五章看起来有许多小节，真正要抓住的并不复杂：现实世界有实体、属性、联系，数据库也从这三者入手；相应地，完整性主要有三类——实体完整性、参照完整性和用户定义的完整性。再往后，则是把这三类规则落实为 SQL 定义、命名、删除与修改。

这一章和第四章讲的安全性不是一回事。安全性关心的是防止数据被破坏、防止非法存取；完整性关心的是已经进入数据库的数据是否符合业务含义，以及一条操作是否违反规则。两者合起来，构成数据库管理系统在控制方面的主要内容。

> **定义**：数据库完整性是数据库在定义、操作和控制过程中必须遵守的规则，目标是保证数据的正确性与相容性。

规则写出来还不算完，数据库管理系统至少要做到三件事：

| 必须具备的能力 | 意味着什么 |
| :--- | :--- |
| 给出约束机制 | 能用 SQL 把规则写出来，例如 `UNIQUE`、`NOT NULL`。 |
| 验证约束 | 数据写入或修改时，能判断它是否违反规则。 |
| 处理违约 | 真的违反了约束时，能拒绝或按约定处理，而不是把不合规则的数据放进去。 |

### 实体完整性：主属性不能取空值

实体完整性只有一句必须记住的话：**主属性不能取空值**。

选课表是最典型的例子。表中有学号 `Sno`、课程编号 `Cno` 和成绩 `Grade`，学号与课程编号构成共同主码，它们就是这里的主属性。假设允许空值，会出现什么？

- 学号为空、课程编号为 1、成绩为 90，这门课是谁选的？
- 学号为 1、课程编号为空、成绩为 90，学生选了哪门课？
- 学号为 1、课程编号为 1、成绩为空，至少还能解释为“选了这门课但还没有成绩”；可把学号或课程编号置空，这个元组就失去了最基本的意义。

所以，“空”不是随便什么都能往里塞的。主码所标识的实体必须有明确的身份；身份字段一旦空了，实体本身就无法被准确识别。

在 SQL 中，实体完整性主要通过主码来定义。这里有一个很实用的写法建议：**主码、外码以及针对整张表的约束，统一写在表定义的末尾；只针对某一列的要求，写在该列的数据类型之后。**

这样写不是为了形式好看，而是为了避免把不同层次的要求混在一起。像选课表这样的共同主码，只能作为表级约束写在末尾；不能拆成“学号列写一个 `PRIMARY KEY`、课程编号列再写一个 `PRIMARY KEY`”，那样表达的是两个独立主码，而不是 `(Sno, Cno)` 共同构成一个主码。

主码本身已经隐含了两项要求：非空且唯一。因此，在已经声明主码的列上再重复写 `NOT NULL` 没有必要。表定义得清楚，既方便自己看，也方便别人维护。

### 参照完整性：有关联的表必须一起看

实体完整性管的是“这个实体是谁”；参照完整性管的是“这个实体与另一个表中的对象有没有对应关系”。

它对应现实世界中的“联系”。如果一个表中的外码指向另一个表的主码，那么两边就不能各说各话：更新时要一起更新，删除时也要一起删除，不能让被引用的数据消失了，留下一些找不到源头的记录。

在前面一直使用的选课表中，`Sno` 要参照学生表的学号，`Cno` 要参照课程表的课程编号。因此，SC 表的共同主码仍是 `(Sno, Cno)`；其中的 `Sno` 是外码，连接 `Student(Sno)`，其中的 `Cno` 也是外码，连接课程表对应的 `Cno`。常见的标准写法就是：

```text
PRIMARY KEY (Sno, Cno)
FOREIGN KEY (Sno) REFERENCES Student (Sno)
FOREIGN KEY (Cno) REFERENCES Course (Cno)
```

这里要注意，`Sno` 和 `Cno` 在 SC 表里是共同主码的组成部分，但它们同时还承担外码的作用。主码和外码并不互相排斥：一个属性可以既是本表主码的一部分，又引用另一个表中的主码。

#### 参照完整性什么时候会被破坏

把两个表关联起来以后，对被参照表和参照表做增、删、改，都有可能破坏对应关系。最稳妥的判断方法，是沿着“插入/修改的一方是否还找得到被参照对象”和“被参照对象被删除/修改后，引用它的一方是否仍然存在”这两条线去检查。

具体到 SC 表和 Student 表：

- 向 SC 表增加一行，但该行的 `Sno` 在学生表中根本找不到：新增的选课记录指向了不存在的学生。
- 修改 SC 表某行的 `Sno`，改成学生表中没有的学号：原来的联系被改断了。
- 删除学生表中的一行，但 SC 表中仍保留这个学生的选课记录：留下来的记录失去了被参照对象。
- 修改学生表中某位学生的学号，却没有同步修改 SC 表：这个学生原有的选课记录仍指向旧学号。

一张表插入、删除、修改，另一张表也有插入、删除、修改；两边一组合，正好是这四种最需要警惕的破坏情形。不必死记硬背，但必须知道：**两张表既然建立了参照关系，任何一边动起来，都可能影响到另一边。**

#### 三种违约处理方式

发现破坏参照完整性的操作时，可以选择以下三种处理方式：

| 处理方式 | SQL 写法 | 含义 |
| :--- | :--- | :--- |
| 拒绝执行 | `NO ACTION` | 不允许这次操作造成不一致。 |
| 级联操作 | `CASCADE` | 删除或修改被参照的数据时，把相联系的引用数据一起删除或修改。 |
| 设为空值 | `SET NULL` | 把引用了被删除或被修改对象的那些外码列置空。 |

拒绝执行最简单，也最不容易意外破坏数据。级联操作强调“要更新一起更新，要删除一起删除”。设为空值则适合表达“原来的联系已经没有了，当前暂未建立新联系”的情况。

例如，假设专业表中编号为 12 的专业被删除。采用 `SET NULL` 后，学生表中专业号为 12 的学生的专业列就应被设为空，表示这个学生目前专业待定，需要重新分配，而不是还挂在一个已经不存在的专业上。

这就是为什么定义外码时，不能只写“它引用了谁”，还要考虑：**当被引用的数据消失或改变时，这个外码允许不允许变空？** 这本身就是参照完整性规则的一部分。

在 SC 表中，可以在两个外码定义后分别补充参照动作。例如，学号外码后面跟着：

```text
FOREIGN KEY (Sno) REFERENCES Student (Sno)
ON DELETE CASCADE
ON UPDATE CASCADE
```

它的意思很直接：如果对 SC 表产生与学号相联系的删除操作，就级联删除；产生与学号相联系的更新操作，就级联更新。课程编号外码也可以独立指定自己的动作，比如删除时 `NO ACTION`，更新时 `CASCADE`。也就是说，**每个外码都可以有自己的参照处理规则，不必把两个外码绑成同一种行为。**

> **易错点**：`ON DELETE` 和 `ON UPDATE` 分别处理删除与更新，不能把“更新成绩”误当成“删除选课记录”。删掉 SC 中一行和改掉 SC 中成绩的值，是两种不同操作，可以配置不同策略。

### 用户定义的完整性：把业务规则写进表定义

实体完整性和参照完整性有非常明确的核心语义；用户定义的完整性则留给具体业务。某个学校规定学分只能是 1、2、3、4，某个系统规定性别只能填男或女，另一张表要求工资与扣除项满足特定关系——这些规则要根据实际情况自行确定。

它既可以限制一个属性列，也可以同时限制多个属性列。

- 限制单个属性列的要求，写在列定义之后。
- 涉及多个属性列、对一条元组中多个值之间关系的整体要求，写在表定义的末尾。

最常见的列级要求无非三类：非空、唯一，以及用 `CHECK` 写自定义条件。

`NOT NULL` 表示不允许空值；`UNIQUE` 表示取值唯一。它们前面的“主码、列唯一”等要求并不难，难的是把“这一列必须满足什么表达式”写清楚。

#### CHECK：把自定义条件写成表达式

`CHECK` 后面的括号中写判断条件，条件成立才允许数据进入。

学生表的性别列只允许取“男”或“女”，可以写成：

```text
CHECK (Ssex IN ('男', '女'))
```

这里，`IN` 后面列出允许的两个常量，`Ssex` 的取值必须落在它们之中。年龄要求落在一个区间内，可以使用 `BETWEEN ... AND ...`；需要按字符串模式匹配姓名时，还可以使用 `LIKE` 和通配符。

成绩的 `Grade` 列已经用 `SMALLINT` 限定为整数，但整数不等于合法成绩。成绩必须在 0 到 100 之间，还要额外写：

```text
CHECK (Grade >= 0 AND Grade <= 100)
```

也可以写成 `BETWEEN 0 AND 100` 的形式。`SMALLINT` 只解决“是不是整数”，`CHECK` 才解决“这个整数是不是允许的成绩”。数据类型约束和业务约束，各管各的，不能互相替代。

对于“性别是男时，姓名不能以 `Ms.` 开头”这样的要求，只看一个属性列就不够了，因为判断同时依赖 `Ssex` 和 `Sname`。它应当写在表定义的末尾，作为表级检查条件。口述的标准条件是：

```text
CHECK (Ssex = '女' OR Sname NOT LIKE 'Ms.%')
```

当性别为“女”时，条件成立；当性别为“男”时，就必须满足姓名不以 `Ms.` 开头。百分号 `%` 是可以代表任意长度内容的通配符，下划线 `_` 则对应一个字符位置。姓名的长度事先不确定，就不能把“像 `Ms.` 开头的部分”写死；这正是通配符存在的理由。

所以，写约束时不要先问“这是不是 `CHECK`”，而要先问：**判断只依赖一个属性，还是依赖这条元组中多个属性之间的组合关系？** 前者紧跟列写，后者放到表末尾。

#### 一个跨列约束的例子

教师表中可以设置一个很直观的整体规则：每位教师的应发工资不能低于 30000 元。假定工资列是 `Salary`，扣除项列是 `Deduct`，并且扣除项按负数记录，那么“应发工资”就是 `Salary + Deduct`，对应检查条件为：

```text
CHECK (Salary + Deduct >= 30000)
```

这个例子特别能说明“检查的是整条记录，而不是某一个格子”。单独输入 `Salary = 30000` 不一定有问题，单独输入一个负的扣除项也各自可能满足数据类型要求；只有把两个值放在一起，才知道应发工资是否达标。数据库执行检查时也是这样：填完相关数据，条件不满足就报错，要求修改。

> **结论**：用户定义的完整性并不神秘。它就是把本应由业务规定、却不能只靠应用层口头提醒的规则，前移到数据库表定义中，让数据库自己守住底线。

### 给完整性约束起名字

前面讲过很多完整性条件，常见写法可以省略约束名；这一节要看的是更标准、也更适合较大程序维护的写法：

```text
CONSTRAINT 约束名 完整性约束条件
```

约束条件可以是 `NOT NULL`、`UNIQUE`、`PRIMARY KEY`、`FOREIGN KEY`、`CHECK` 等。命名之后，后续删除或修改约束时，就能直接说“我要改哪一个”，而不必把复杂的条件再完整写一遍。

例如，在学生表中，针对学号的范围检查可以命名为 `C1`，姓名非空命名为 `C2`，年龄小于 30 命名为 `C3`，性别只能取男或女命名为 `C4`，学号主码再单独命名为 `student_key`。这些名字只是标识约束的标签；真正决定行为的是后面的条件。

写的时候仍然要坚持位置原则：

- 紧跟在某个列定义之后的约束，是针对这一列的要求。
- 写在整张表末尾的主码、外码或 `CHECK`，是针对整张表的要求。
- 多列共同参与的判断，不能伪装成某一列的列级约束。

起名不是为了把一行简单的 `NOT NULL` 写得更长，而是为了后续能精确管理。别人看程序时，也更容易知道一条约束管什么。

### 约束的删除与修改

完整性约束不是写完就永远不能动。业务规则变了，数据库规则也要跟着变；这时使用的是 `ALTER TABLE`，因为对表结构的增加、删除和修改，本质上属于 DDL 操作。

删除已经命名的约束，核心写法是：

```sql
ALTER TABLE Student
DROP CONSTRAINT C4;
```

比如，删掉 `C4`，就是删掉先前命名为 `C4` 的那条约束。若没有起名，遇到复杂约束时就难以用这种简洁方式精确指定目标，这正是命名子句的实际价值。

要修改一条约束，不必追求一条语句“就地变形”。最简单、也最不容易留下旧规则残留的办法是：**先删除旧约束，再添加新约束。** 例如，把年龄限制从“小于 30”改成“小于 40”，先删掉原来的 `C3`，再以同一个名字或新名字添加新的 `C3` 即可。涉及其他条件时也一样。

> **结论**：修改完整性约束，就是修改游戏的规则。先删旧规则，再加新规则，往往比研究怎样直接修改更省事，也更清楚。

### 把三类规则与 SQL 对起来

这一章看似涉及很多定义、例子和写法，真正必须装进脑子的对应关系却很整齐：

| 完整性类别 | 核心思想 | SQL 中依靠什么实现 |
| :--- | :--- | :--- |
| 实体完整性 | 主属性不能取空值 | 主码 `PRIMARY KEY`。 |
| 参照完整性 | 有外码指向主码的两张表，更新、删除要互相参照 | 外码 `FOREIGN KEY` 与 `REFERENCES`，以及对应的 `ON DELETE`、`ON UPDATE` 动作。 |
| 用户定义的完整性 | 按实际业务，对列或整行提出要求 | `NOT NULL`、`UNIQUE`、`CHECK`；需要维护时使用 `CONSTRAINT`、`ALTER TABLE`。 |

写表定义时，再把位置规则与这套对应关系合起来：

1. 先逐列写数据类型和列级要求。
2. 再在表末尾写共同主码、外码及它们各自的参照动作。
3. 涉及多个列的整体业务要求，也写在表末尾的 `CHECK` 中。
4. 复杂约束尽量命名；规则变化时，用 `ALTER TABLE` 先删再加。

考试如果只出一道“表定义加完整性约束条件”的题，最值得练熟的就是学生表和选课表这类定义。它们能把共同主码、外码、级联动作、`CHECK`、列级与表级条件区分开，还能把 `LIKE` 的通配符一起考到。表面上可能只值五分，实际却把好几个知识点黏在了一起。

到这里，数据库完整性的主线就很清楚了：实体靠主码守住身份，参照关系靠外码守住联系，业务边界靠自定义约束守住语义；而所有规则，都应该尽量在数据库中用 SQL 明确表达、清楚命名，并能用 `ALTER TABLE` 随业务变化有序地删除和重建。

## 数据库完整性中的断言与触发器：从判断到行动
> 对应块：BLK15 | 覆盖分集：P13 | 块标题（分集名）：《数据库第5章 数据库完整性（第二部分：断言和触发》

先把一个容易混淆的问题摆到台面上：数据库发现数据不合要求时，究竟只能把操作拒绝掉，还是还可以进一步替我们做点什么？

前面讲过的实体完整性、参照完整性和用户定义完整性，主要是在某一个列、某几个列或者某一个表上设置基本限制。比如，性别列只允许填“男”或“女”，可以用 `CHECK` 完成；再比如工资的两个列之间需要满足某种运算关系，也可以交给 `CHECK`。这些当然有用，但它们更像一道一道的基础门槛，控制能力也是比较基础的。

可是在真实的管理场景里，门槛往往不是一道，而是会牵动多张表、数数和业务条件；有时候，数据库发现问题以后还不能简单地拒绝，还要自动修正，或者把变化过程留下来。这个缺口，正好由断言和触发器补上。

> **结论**：基础约束、断言和触发器是逐级递进的三种控制手段。`CHECK` 负责基础限制，断言负责复杂条件下的“停住”，触发器则在事件发生、条件满足之后继续执行动作。

### 完整性控制的三层递进

举三个场景就很清楚了。数据库这门课最多允许 60 个同学选，超过人数就不能继续选；某个老师填入的工资低于 30000 时，系统自动把它改成 30000；老师修改某个同学的成绩后，系统自动生成一张记录表，保存修改前和修改后的成绩。

第一类问题，关键在于“满足某个复杂条件时，不允许这次操作继续”。第二类和第三类则更进一步：系统不只是判断，还要反应。前者偏向阻止，后者偏向自动处理和留痕。

| 控制手段 | 适合表达的要求 | 发生问题时的主要结果 |
| --- | --- | --- |
| `CHECK` 等基础约束 | 某列、某几列或某个表的基本限制 | 拒绝不符合条件的操作 |
| 断言 | 涉及多表、聚集运算或更一般的条件 | 只要条件不为真，就拒绝相关操作 |
| 触发器 | 事件、条件、动作的组合 | 事件发生后按条件执行过程或动作 |

所以不能把它们理解成互相割裂的三个名词。它们都在回答同一个问题：人对数据库中的数据和信息有哪些限制、框定和执行要求？只是表达这些要求的能力逐步增强。

### 断言：让复杂条件成为一票否决

> **定义**：断言是 SQL 中用 `CREATE ASSERTION` 指定的一般性完整性约束。它可以涉及多个关系，也可以包含聚集操作这样的复杂条件。

断言创建以后，凡是对断言涉及的关系进行操作，数据库系统都会检查这个断言。任何会让断言条件变成假值的操作，都会被拒绝执行。这里先抓住“条件必须为真”这个核心，不要一上来就被复杂的例子吓住。

#### 断言的写法

断言的标准骨架很简单：

```sql
CREATE ASSERTION <断言名>
CHECK (<约束条件>);
```

`CREATE ASSERTION` 表示创建断言，后面给出断言的名字，再由 `CHECK` 子句写出约束内容。`CHECK` 里面的表达式和 `WHERE` 子句里的表达式类似：条件为真，操作可以继续；条件为假，操作就停下来。

名字可以自己取，但不要随手写成 `a`、`b`、`c`。代码不一定是只写给自己看的，别人也可能要读它，还要据此理解数据库的管理规则。一个清楚的命名可以让人一眼看出：这是断言、针对哪张表、限制的是什么对象、限制的数量是多少。比如先看出 `ASSE`，再看 `SC`、`DATABASE`、`NUMBER` 这些部分，意思就很容易连起来。

> **提示**：断言的名字不仅是为了语法完整，也是为了让数据库规则具备可读性；后面删除断言时，名字也直接决定了你能不能准确找到它。

#### 限制数据库这门课的选课人数

先看一个最具体的例子：数据库这门课最多只能有 60 个同学选。

这件事不是只看 `SC` 表里的一个字段就够了。课程名称在 `Course` 表里，选课记录在 `SC` 表里，而且限制条件针对的是课程名称为“数据库”的那一门课。因此，子查询需要同时使用 `SC` 和 `Course`，先写连接条件，再写课程名称的筛选条件：

```sql
CREATE ASSERTION ASSE_SC_DATABASE_NUMBER
CHECK (
    60 >= (
        SELECT COUNT(*)
        FROM SC, Course
        WHERE SC.Cno = Course.Cno
          AND Course.Cname = '数据库'
    )
);
```

这里的 `COUNT(*)` 就是一个数数问题：把 `SC` 和 `Course` 按课程编号接起来，只留下课程名称为“数据库”的记录，再数一数选课记录有多少条。多表查询里，连接条件一定要先明确；否则两个表直接放在一起，不能表达我们要找的那门课。

断言检查的就是这个子查询的结果。当前选课人数不超过 60 时，`60 >= 选课人数` 为真，选课可以照常执行。等到第 61 个同学要选这门课时，条件变成 `60 >= 61`，结果为假，数据库便把这次程序停下来。放到教务处的场景里，就是这个同学暂时选不进去了。

这里要注意，单门课程的限制和所有课程的限制不是同一件事。前者只需要筛出课程名为“数据库”的一组记录；后者需要对每一门课分别检查，不能只数整张 `SC` 表。

#### 每一门课程都最多 60 人

如果要求变成“每一门课程最多 60 个同学选”，就不能再只盯着课程名为“数据库”的那一门课了。此时要做的是分组：对 `SC` 表按课程编号 `Cno` 分组，让 `COUNT(*)` 分别作用于每一个课程组。

```sql
CREATE ASSERTION ASSE_SC_CNUMBER_NUMBER
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno
    )
);
```

这段 SQL 的意思要顺着读：不分组时，聚集函数作用于整个结果；按 `Cno` 分组以后，聚集函数就分别作用于每一个组。假设分组后的统计结果是 30、20、50，那么 `60 >= ALL (...)` 要求这一列中的每一个数都不超过 60。只要某一门课的人数超过 60，整个断言条件就不再成立。

所以，断言真正有用的地方，并不是把一个常数改写成一个更复杂的表达式，而是可以把“多个关系和聚集结果必须满足什么条件”整体交给数据库检查。

#### 每一学期、每一门课程都最多 60 人

再把条件扩展一步：每一学期、每一门课程都最多 60 人。

原来的 `SC` 表只有学号、课程编号和成绩，并没有学期信息。课程名称也不在这张表里。先把 `Term` 加到 `SC` 表中：

```sql
ALTER TABLE SC ADD Term DATE;
```

如果这个字段不能为空，可以继续加上 `NOT NULL`。完成这个结构补充以后，断言就要同时按课程编号和学期分组：

```sql
CREATE ASSERTION ASSE_SC_CNUMBER_TERM_NUMBER
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno, Term
    )
);
```

现在每一组代表“同一学期、同一门课程”的选课记录。数据库会分别统计每个组合的人数，再要求每一组都不超过 60。这个例子很清楚地说明，断言的检查对象可以随着表结构和业务条件一起扩展。

#### 删除断言与选择工具

删除断言使用：

```sql
DROP ASSERTION <断言名>;
```

删除时直接使用创建时给出的名字，所以前面为什么反复强调名字要清楚，这里就体现出来了。断言越复杂，系统在检测和维护它时的开销越高，这一点也要纳入考虑。

以后遇到“满足什么条件时，数据库就停住、不让操作继续”的要求，可以优先想到断言；针对某一个表的某几列做基本限制，则先用 `CHECK`。但如果要求不只是拒绝，而是自动修改、自动记录，或者在操作前后取两个值进行比较，就已经不是断言能完成的工作了。

### 触发器：把事件变成动作

> **定义**：触发器是定义在关系表上的、由事件驱动的特殊过程。事件发生的某个时刻，数据库可以先检查条件，再执行预先安排的动作。

触发器保存在数据库服务器中。数据流进来时，服务器会自动检查并激活相应的触发器。任何用户对表进行增加、删除或修改操作，都可能激活对应的触发器。触发器因此可以做比 `CHECK` 和断言更复杂、更精细的检查与操作。

这里最重要的思维转换是：断言主要回答“这个条件还能不能成立”，触发器还要回答“条件成立以后，数据库接下来要做什么”。如果没有触发动作，或者触发动作失败，条件判断本身就没有完成；这个差别正是能力递进的关键。

可以把触发器压缩成三个词：event、condition、action。也就是事件、条件、动作。

```text
增加、删除或修改
        |
        v
     事件发生
        |
        v
   检查 WHEN 条件
      /       \
    真         假
     |          |
  执行动作    不执行动作
```

读图时不要把它理解成一个脱离数据库的流程图：事件必须落在某个关系表上，条件要针对这次操作中的新旧值，条件为真时才执行过程块或对存储过程的调用。

#### 先看懂触发器的语法骨架

把讲过的部件放到一起，可以先写成下面这个骨架：

```sql
CREATE TRIGGER <触发器名>
{BEFORE | AFTER} <触发事件> ON <基本表>
[REFERENCING
    [NEW ROW | NEW TABLE] AS <新值变量>
    [OLD ROW | OLD TABLE] AS <旧值变量>]
[FOR EACH {ROW | STATEMENT}]
[WHEN <触发条件>]
<触发动作体>;
```

`CREATE TRIGGER` 后面是触发器名字。`BEFORE` 和 `AFTER` 指定触发时机，`ON` 后面是发生变化的表。触发事件可以是 `INSERT`、`DELETE`、`UPDATE`，也可以是这些事件的组合。

`REFERENCING` 用来引入新值和旧值。行级触发器里，可以写 `NEW ROW` 和 `OLD ROW`；语句级触发器里，也可以用 `NEW TABLE` 把事件完成后的新表交给一个变量。名字本身只是名字，重要的是它代表事件之前还是事件之后的数据。

可以把它们想成两个“碗”。旧碗接住操作之前的值，新碗接住操作之后的值。这个碗不一定只装一个数，也可以装一个字段、一行元组，甚至一张表。不要被 `ROW`、`TABLE` 这些外形限制住，重点是分清“旧值”和“新值”。

`FOR EACH ROW` 表示对每一行处理，`FOR EACH STATEMENT` 表示对整条语句处理。`WHEN` 后面写触发条件；如果条件为真，触发动作体才执行。动作体可以是一个匿名的过程块，也可以调用已经创建好的存储过程。这里可以先把动作体理解成一段 SQL 过程代码，过程块和存储过程的具体内容留到后面学习。

#### BEFORE、AFTER 以及行列范围

`AFTER` 是在事件执行之后触发。比如成绩已经被改成新值，再把修改前后的成绩记录下来，这就是 `AFTER UPDATE` 的思路。

`BEFORE` 不是说老师还没有敲键盘，也不是说数据还没有进入计算机。它指的是数据已经进入计算机之后，在内存中真正执行更新之前，数据库先检查并处理这一行。这里的“之前”是数据库执行过程里的“之前”，不是键盘输入动作之前。这个地方特别容易搞错，一定要把输入界面和数据库执行过程分开。

`UPDATE OF Grade` 可以把事件进一步缩小到某一列。普通的 `UPDATE ON SC` 表示成绩单这张表发生更新时触发；写成 `UPDATE OF Grade ON SC`，就表示关注的动作是对 `Grade` 这一列动手脚。如果只是更新别的列，就没有必要让这个专门检查成绩变化的触发器跟着执行。

行级和语句级的差别，可以用一个直接的例子体会。假设 `teacher` 表有 1000 行，现在执行一条语句，把所有老师的专业都改成 5 号专业：

- `FOR EACH STATEMENT` 时，这条语句执行完，语句级触发器动作一次；
- `FOR EACH ROW` 时，1000 行都要分别处理，触发器就可能执行 1000 次。

所以看到 `FOR EACH ROW`，就要想到“逐行”；看到 `FOR EACH STATEMENT`，就要想到“整条语句完成后处理一次”。

`WHEN` 是可选的触发条件。条件为真才执行动作，条件为假就不执行；如果省略 `WHEN`，那么事件一激活，动作就立即执行。`new` 和 `old` 主要在行级触发器中使用，因为只有针对具体一行时，才适合拿这一行的新旧值做比较。语句级触发器处理的是语句结束后的整体结果，不能把它当成某一行的新旧记录来使用。

如果动作体执行失败，触发器的事件就会终止执行，目标对象或触发器影响的其他对象也不发生变化。这里要把“触发动作”与原来的数据操作看成有联系的一步，而不是动作失败后原来的修改还照旧留下。

#### 触发器的使用边界

有几条规则一定要记住。

- 触发器必须由表的拥有者创建。连上了一个数据库，并不等于可以在任意表上创建触发器。
- 触发器名可以包含模式名，也可以不包含；但同一个数据库框架下，触发器名字要唯一。触发器和它所依附的表要处于同一个模式。
- 触发器只能定义在基本表上，不能定义在视图上。视图是虚表，基本表的数据发生变化时，触发器才会被激活。
- 触发事件可以是 `INSERT`、`DELETE`、`UPDATE`，也可以是它们的组合；如果只关心某一列，就用 `UPDATE OF` 缩小范围。
- 不同数据库产品的触发器语法可能不同。SQL Server、MySQL、DB2、Kingbase 的写法可能存在差异，实际使用时先看所用软件的说明书，不要把某一种产品的语法直接当成所有产品都完全一致。

#### 成绩大幅修改时留下审计记录

现在看第一个完整的触发器例子：当成绩单表 `SC` 的 `Grade` 属性被修改，而且新分数比旧分数增加了 10% 时，把这次修改记录下来。记录里要有学号、课程编号、旧成绩和新成绩，教务处之后可以根据记录询问老师：原来为什么给这个分，为什么这次一下改得这么高？

逐字稿给出了触发器名 `SC_T`，但没有报出记录表及其四个字段的具体名称。下面保留这些位置为占位符，不凭空补写；`OLD ROW`、`NEW ROW`、`FOR EACH ROW` 和新旧成绩的比较方式则是原样保留的。

```sql
CREATE TRIGGER SC_T
AFTER UPDATE OF Grade ON SC
REFERENCING
    OLD ROW AS OldTuple
    NEW ROW AS NewTuple
FOR EACH ROW
WHEN NewTuple.Grade >= 1.1 * OldTuple.Grade
INSERT INTO <成绩变化记录表>
    (<学号>, <课程编号>, <旧成绩>, <新成绩>)
VALUES
    (OldTuple.Sno, OldTuple.Cno, OldTuple.Grade, NewTuple.Grade);
```

读这段定义时，不要只盯着 `CREATE TRIGGER`，要顺着事件、条件、动作走一遍。`AFTER UPDATE OF Grade ON SC` 表示成绩已经更新，而且关注的是 `Grade` 列。`OldTuple` 接住旧行，`NewTuple` 接住新行；`Tuple` 这里是元组的意思，不是泛泛地指一张表。

`NewTuple.Grade >= 1.1 * OldTuple.Grade` 是触发条件。新成绩至少达到旧成绩的 1.1 倍，就相当于增加了 10% 或更多。条件为真时，`INSERT INTO ... VALUES ...` 把学号、课程编号、旧成绩和新成绩取出来，写入记录表。学号和课程编号在改成绩时不变，所以可以从旧行或新行中取；旧成绩来自 `OldTuple.Grade`，新成绩来自 `NewTuple.Grade`。

这个例子正好说明了为什么 `CHECK` 和断言还不够。`CHECK` 不能自然地拿到修改前和修改后的两个值；断言可以发现修改幅度超过 10% 后把操作停掉，却不能在操作之外再把这次变化写入另一张表。触发器既有新旧值，又能把记录插入新表，所以它能完成这种审计动作。

#### 统计插入后学生表的新行数

第二个例子换成 `Student` 表。要求每次对 `Student` 执行插入后，把数量记录到 `insert_log`。这里不再指定某一列，因此使用 `INSERT ON Student`，不写 `OF`；用 `FOR EACH STATEMENT`，把 `NEW TABLE` 作为 `delta` 引入，再读取这张新表并计数。

```sql
CREATE TRIGGER <触发器名>
AFTER INSERT ON Student
REFERENCING NEW TABLE AS delta
FOR EACH STATEMENT
INSERT INTO insert_log
SELECT COUNT(*) FROM delta;
```

这里不要被 `NEW` 这个词限制住。成绩例子里，变量接的是一行；学生插入例子里，变量接的是一张表。它们都只是在区分事件之后和事件之前的值。这个例子没有插入前的行需要逐行比较，所以重点是取得事件完成后的新表，不需要构造旧行和新行的成对比较。

按给出的计数方式，`delta` 是操作后的学生表。假设原来有 50 名学生，一次插入后变成 70 名，那么这一次写入 `insert_log` 的是 70；下一次再插入 10 名，表变成 80 名，就写入 80。

> **易错点**：这里按 `COUNT(*) FROM delta` 读到的是操作完成后新表的行数。50 变 70 时记录 70，70 变 80 时记录 80，不应擅自把它改写成“只记录本次新增的 20 和 10”。原始例子给出的就是读取新表并计数。

行级和语句级的差别在这里也很明显：成绩例子是 `FOR EACH ROW`，需要对具体一行的新旧成绩做比较；学生插入例子是 `FOR EACH STATEMENT`，把整次插入后的新表作为一个整体来处理。

#### 在更新前自动修正教授工资

最后看 `BEFORE` 的行级触发器。给 `teacher` 表设置一个要求：如果职称是教授，而新工资低于 4 万，就在真正更新之前自动改成 4 万。

```sql
CREATE TRIGGER <触发器名>
BEFORE INSERT OR UPDATE OF Salary ON teacher
FOR EACH ROW
BEGIN
    IF new.job = '教授' AND new.salary < 40000 THEN
        new.salary := 40000;
    END IF;
END;
```

这里的事件是插入或更新 `Salary`，时机是 `BEFORE`，范围是 `FOR EACH ROW`。因为动作只需要检查传入的新记录，不需要把旧记录拿来比较，所以不写 `REFERENCING` 中的新旧变量；这不是语法上每次都必须写，而是要根据需求决定。

`BEGIN` 和 `END` 之间是过程块。`IF` 先判断新行的职称和新工资：只有职称为“教授”并且新工资小于 4 万时，才执行 `new.salary := 40000`。这里的 `:=` 表示赋值，把 4 万赋给新工资。数据库在内存中真正完成更新之前，就把新值调整好，因此最后更新进去的是 4 万，而不是仍然保留一个低于 4 万的值。

这个例子和断言的差别非常关键。断言可以发现工资低于 4 万，然后把这次输入拦住；它不能替用户把值改成 4 万。触发器的事件—条件—动作结构可以在更新前执行赋值，所以“自动补齐”只能由触发器完成。

### 触发器如何激活与删除

触发器的激活首先取决于事件：发生了 `INSERT`、`DELETE` 或 `UPDATE`，才有可能激活对应触发器。一个表上如果定义了多个触发器，执行顺序是先执行 `BEFORE` 类的，再执行 SQL 语句，最后执行 `AFTER` 类的。也就是先在执行前处理，再执行数据操作本身，最后在执行后处理。

删除触发器使用创建时给出的名字：

```sql
DROP TRIGGER <触发器名> ON Student;
```

只有已经创建的触发器才能删除，也只有具备相应权限的用户才能删除。这里没有像 `ALTER` 那样的修改语句，不是因为触发器永远不能改，而是因为触发器牵涉事件、条件、范围和动作，修改起来比较复杂；需要改变定义时，直接删除再重新创建一个，往往更清楚。

### 把三种机制放回数据库整体

到这里，数据库完整性这条线就完整了。数据库管理系统里的数据问题可以分成数据定义 DDL、数据操作 DML 和数据控制 DCL。前面关于 DDL 和 DML 的内容，加上这里讲的数据控制，共同构成了数据库管理的基本框架。

在完整性这个主题里，规则、约束和限制回答的是“什么可以做，什么不可以做；如果不可以，应该怎样处理”。前面先用实体完整性、参照完整性和用户定义完整性建立基本限制；遇到涉及多表、聚集结果或更一般条件的限制，就用断言；需要“事件发生后，条件满足时自动执行动作”，就用触发器。

所以，断言的关键是 `CHECK`：条件为真就允许，条件为假就拒绝。触发器的关键则是 event、condition、action：发生了什么事，满足了什么条件，数据库就做什么事。前者把复杂控制推进到“能不能做”，后者进一步推进到“做完之后如何响应”。这才是从基础完整性一路走到断言、再走到触发器的完整逻辑。
