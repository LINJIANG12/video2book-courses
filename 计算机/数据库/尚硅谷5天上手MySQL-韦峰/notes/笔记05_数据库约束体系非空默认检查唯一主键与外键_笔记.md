# 数据库约束体系：非空、默认、检查、唯一、主键与外键

## 约束的分类与查看

* **约束（Constraint）**
    * > **定义**：加在表上的具体限制，用来保证存入的数据符合设定好的规矩。
    * 列级别约束一列一列地管，实体级别（行级别）约束必须把本行的数据和其他行比较才成立。
    * 检查约束虽然可以写在列后边，本质上属于表级别，它针对表内的数据做统一检查。
    * 主键约束与外键约束是同一层级的概念：一个保证主键数据正确，一个保证外键数据正确。
    * 主外键约束又可以叫参照约束、引用约束、外键约束、多表约束，名字不同指的是同一件事。

* **约束的层级**

    ```text
    约束
    ├── 列级别约束（一列一列地管）
    │   ├── 非空约束   NOT NULL
    │   └── 默认值约束 DEFAULT
    ├── 检查约束       CHECK
    └── 实体级别约束（行与行之间比）
        ├── 唯一约束   UNIQUE
        ├── 主键       概念：区分一行不重复的列
        └── 主键约束   PRIMARY KEY
    ```

    * 自增长约束 `AUTO_INCREMENT` 收尾了实体级别这一支，讲完它，域约束与实体约束就全部结束，再往外才是多表的主外键约束。

* **`DESC` 能看见什么**
    * `DESC 表名` 能看出列能不能为空、列类型、默认值，以及这一列是不是一个索引。
    * 检查约束这一类 `DESC` 是看不见的，得去查 MySQL 自带的 `information_schema` 库里存放约束信息的那张表。
    * 查询时用 `table_schema` 指定自己的库、用 `table_name` 指定表名，回车后能看到约束名与 `type`。
    * `type` 叫 `CHECK` 的就是检查约束，属于强制生效的那一类。

    ```sql
    SELECT * FROM information_schema.table_constraints
    WHERE table_schema = '库名' AND table_name = '表名';
    ```

* **约束名的规则**
    * 建唯一约束时不指定名字，约束名默认就是它的列名。
    * 建检查约束不指定名字时，数据库给的默认名称是 `表名_chk_序号`。
    * 自己指定的约束名只要求在同一个表内不重复。

## 非空与默认值约束

* **非空约束（NOT NULL）**
    * > **定义**：列级别约束，限定该列不接受 `NULL`。
    * 给标了非空的列硬塞一个 `NULL`，报的是 `Column 'age' cannot be null`。
    * 拦下这次插入的是非空约束，数据库不会回头去找这一列的默认值替补。
    * 非空约束的添加方式与默认值约束相同：建表时写在列后，建表后用 `ALTER TABLE ... MODIFY` 修改。

* **默认值约束的三个特点**
    * > **定义**：给某个列添加一个默认值的约束，当不往这一列插值的时候就走这个默认值，关键字是 `DEFAULT`。
    * 默认值不能加在唯一列和主键列上，其他列都可以，且建表时可以一次给多列加。
    * 唯一列本来就要求值不重复，不插时默认值每次都相同，天然冲突；主键列同样要求不能重复。
    * 插入数据时没有显式赋值，就会走默认值。
    * 默认值的类型必须和列的类型匹配，整数列配整数默认值，字符串列配字符串默认值。

* **建表加、改表加与删除**
    * 建表时在列的后边直接写 `DEFAULT`，这一列已有非空约束也可以继续叠加。
    * 建表后补上用 `ALTER TABLE 表名 MODIFY 列 类型 DEFAULT 默认值`。
    * 删除是把 `DEFAULT` 去掉再 `MODIFY` 一次，执行后 `DESC` 的 Default 栏就空了。

    ```sql
    CREATE TABLE emp2 (
      name varchar(20) DEFAULT '二狗子',
      age  int NOT NULL
    );

    ALTER TABLE emp2 MODIFY age int DEFAULT 48;
    ALTER TABLE emp2 MODIFY name varchar(20);
    ```

    * 建完表先 `DESC` 一次，`name` 可以为空且 Default 栏是"二狗子"，`age` 不能为空但没有默认值。
    * 只写 `name` 插一行时，`age` 查出来是 48，说明没有主动赋值就走默认值。
    * 给 `age` 执行 `MODIFY age int DEFAULT 48` 之后再 `DESC`，`age` 变成可以为空，原来那个非空约束被整个覆盖掉了。
    * 改成 `MODIFY age int NOT NULL DEFAULT 48` 之后，`age` 才同时既不能为空又带默认值。

* **`MODIFY` 的覆盖语义**
    * > **注意**：`MODIFY` 是把这个列的定义整个重写一遍，不是往原来那上面再叠一层。
    * 这一次没有写出来的原有约束（`NOT NULL`、`DEFAULT`）都按"没写"处理。
    * 所以 `MODIFY` 之后，非空和默认值这两项要一起写全，否则等于把非空弄丢了。

* **什么时候才走默认值**
    * 默认值只在**没有显式赋值**的时候生效。
    * 显式写入 `NULL` 也算赋值，所以 `INSERT INTO emp2(age, name) VALUES (20, NULL)` 之后 `name` 就是 `NULL`，不走默认值。
    * 同一行里别的列给了值，不影响没提到的那一列走默认值。
    * 某一列同时是 `NOT NULL` 时硬塞 `NULL`，插入直接失败，拦它的是非空约束而不是默认值。

## 检查约束

* **检查约束的三个特点**
    * > **定义**：限制某一个字段的值是否符合自定义的要求，语法是 `CHECK` 后边写一个表达式。
    * MySQL 5.7 相关版本虽然认识 `CHECK` 关键字，但解析完就丢掉了、没有实际效果，到 8.0.16 以后它才真正开始工作。
    * 它是万能约束，内部可以写表达式，靠表达式实现任何想做的检查工作，关键在表达式怎么写。
    * 表达式的典型用途之一是限定取值集合，比如要求性别这一列必须是男或者女。
    * 表达式的另一个典型用途是限定取值区间，比如年龄必须在 18 到 35 岁之间才能查出这个值。
    * 不推荐用检查约束，因为它偏业务性，把业务性的检查都交给数据库会让数据库压力很大。
    * 建议做程序级别的限制，在代码中控制好数据，符合就插入、不符合就不插入，别把这些检查工作交给数据库。

* **写在列后还是表级单写**
    * 建表时可以放在列的后边，也可以不放在列的后边、单独写一个，两者之间要用逗号隔开。
    * 它属于表级别的约束，写在括号里就会专门触发对表达式的检查。
    * 建表后添加用 `ALTER TABLE 表名 ADD CONSTRAINT 约束名 CHECK (检查表达式)`。
    * 表达式可以指向一列也可以指向多列，所以这种约束不是针对某一列，而是针对表内的数据做统一检查。

    ```sql
    CREATE TABLE emp3 (
      gender char(1),
      check (gender in ('男', '女')),
      age int
    );

    ALTER TABLE emp3 ADD CONSTRAINT emp3_age_check CHECK (age >= 48);
    ```

    * `IN` 代表两者之间的"或"的关系，值在这个范围内才可以。
    * `CHECK` 前面一定要写逗号，跟前面的列隔开。
    * 起个约束名时用 `CONSTRAINT` 加名字即可，本例用的是 `emp3_age_check`。
    * 建表时加的那条没起名，性别填"人妖"报的是 `Data too long for column 'gender'`，超的是 `char(1)` 的长度，不是检查约束拦的。
    * 换成"妖"仍然报错，因为"妖"不在检查约束的范围内，这时才能看出检查约束确实生效。

* **查约束与删约束**
    * 删除用 `ALTER TABLE 表名 DROP CONSTRAINT 约束名`，注意这里不是 `MODIFY`。
    * 约束名记不住时，用 `information_schema` 的查询语句查出来即可。
    * 删掉 `emp3_chk_1` 之后再查，这张表就只剩一个 CHECK 约束了。
    * 约束不在之后，再插一条性别"妖"、年龄给合规值的数据这回能保存。

    ```sql
    ALTER TABLE emp3 DROP CONSTRAINT emp3_chk_1;
    ```

## 唯一约束

* **行级别约束的含义**
    * > **定义**：限制某一个字段的值是唯一的，关键字是 `UNIQUE`。
    * 它与前面几个约束有本质区别：需要对比其他行的数据才能知道自己是不是唯一，这才是行级别的约束。
    * 典型场景是手机号：手机号可以为空，但要填写的时候必须唯一。

* **三个特点**
    * 允许一张表中有多个列各自唯一，也可以把多个列组成一个联合的。
    * 联合唯一的判定是这些列的综合值不重复：1 号班级的 1 号学生行，1 号班级的 2 号学生也行，但不能让两个"1 号班级 + 1 号学生"同时存在。
    * 唯一约束允许为空，而且允许有多个空值，因为空不算重复。
    * 建唯一约束时不指定名字，约束名默认就是它的列名。

* **单列唯一与联合唯一**
    * 直接在字段后边写 `UNIQUE` 或 `UNIQUE KEY` 都行；`unique` 和 `primary` 都是索引，索引就是 K，写不写 K 都可以。
    * 单着写在列后边，指的就是这一列单独唯一。
    * 在括号里单独写时，前边的 `CONSTRAINT` 约束名可以省略，省略就默认用列名。
    * 括号里可以写一个列，也可以写个逗号再写另外一个列，多列即为联合唯一。
    * 联合唯一必须用括号里这种写法，列后单写只能是单打独斗的单列唯一。

    ```sql
    CREATE TABLE emp4 (
      name  varchar(20),
      phone varchar(11) UNIQUE
    );

    CREATE TABLE emp7 (
      phone     varchar(11) UNIQUE,
      class_no  int,
      stu_no    int,
      CONSTRAINT emp7_class_stu UNIQUE KEY (class_no, stu_no)
    );
    ```

    * `DESC` 能看见有一个单独的 `unique` 和一个组合的 `unique`，但具体名字看不太清楚。
    * 用 `information_schema` 的查询语句能查出来：`phone` 那条是一个唯一约束，另一条约束名就是自己起的那个，它是联合的。

* **组合验证与多个空值**
    * `(NULL, NULL)` 可以保存，`(1, 2)` 也可以保存，只要组合不重复就行。
    * 再插一条一模一样的 `(1, 2)`，组合重复了，直接报错。
    * 能塞进两个都为空的行，原因就是"空不算重复"。

    ```sql
    INSERT INTO emp7 (class_no, stu_no) VALUES (NULL, NULL);
    INSERT INTO emp7 (class_no, stu_no) VALUES (1, 2);
    INSERT INTO emp7 (class_no, stu_no) VALUES (1, 2);
    ```

* **建表后添加与删除**
    * `ALTER TABLE 表名 ADD CONSTRAINT 约束名 UNIQUE KEY (列)`，后边可以写一个列或者多列，多列代表组合唯一。
    * 指定了名称就用这个名称，不再是默认列名。
    * 删除用 `ALTER TABLE 表名 DROP CONSTRAINT 约束名`。
    * 把 `name` 列变成唯一又删掉之后再查一遍，联合的那条还在，没有动到。

    ```sql
    ALTER TABLE emp7 ADD CONSTRAINT emp7_name UNIQUE KEY (name);
    ALTER TABLE emp7 DROP CONSTRAINT emp7_name;
    ```

## 主键

* **从整行重复说起**
    * > **定义**：主键就是用来区分一行数据的那一列，它不为空且唯一。
    * 班里出现同名、同龄、同性的两个学生时，人可以靠长相区分，数据库不知道谁高谁矮，从数据角度这两条完全相同。
    * 数据库里如果存在所有列都相同的重复数据，后续操作全部失效：删掉其中一个会把两条都删掉，修改也无从下手。
    * 解题思路是保证表中至少有一列不重复，只要有一列不重复，整行就永远不会重复。
    * 学生有学号、员工有员工编号、人还有身份证号，这些都是区分个体的最终标识。

* **自然主键与自定义主键**
    * **自定义主键**：人为创造的一列，专门用来做主键，使命就是永远不为空且不重复，例如学号、身份证号。
    * **自然主键**：不是人为创造的、实体本身自带的属性列，例如 name、age 这类在当前环境下也唯一且不为空的列，人的 DNA、瞳孔、牙齿的轮廓也算。
    * 身份证号看起来像自带属性，但它是别人给编的一个码，并不是人本身的特性，所以它属于自定义主键。
    * 开发中全部推荐自定义主键，因为当下感觉唯一的东西，你并不能保证它未来永远唯一。
    * 用现有属性列做主键，这一列后期不能随意修改，主键不能改，改它相当于改了标识。

    > **易错点**：用现有的某个属性列作主键，这一列将同时承载两个使命——第一，它本身是实体的属性；第二，它还是个主键。

* **主键的常见细节**
    * 一张表只能有一个主键——加引号的重点是"只能有一个主键"而不是"只能有一个主键列"。
    * 主键分单一主键和复合主键，多列组合当主键也仍然是一个主键，不能有两个标识。
    * 主键列的类型可以是任意类型，数字也好、字符串也好都行，只要满足唯一且不为空。
    * 命名上一般采用 identity（标识）的缩写，即某某 `id`、`xxx_id`，但没有强制要求，叫什么都行。
    * 创建主键约束以后会创建一个主键索引，根据主键查会提升查询效率。

    > **注意**：正因如此，推荐每张表都必须要有主键，至多它也只能有一个。

## 主键约束

* **概念与机制的分界**
    * > **定义**：主键约束是针对主键列施加的数据约束和限制，确保主键列不会出现错误的数据。
    * 表里确实有主键时，如果不加约束，插入一个空值没有任何惩罚手段，表里只有口头概念。
    * 主键约束规定主键值必须唯一且不为空，谁要插入空值和重复的值，就给他抛异常。
    * 它只针对主键列；主键是概念、主键约束是保障机制，这是两个概念。
    * 类比：大熊猫是国宝只是说了句话，没有法律法规保护时谁都能上去打两下，主键约束就是那部法律法规。

* **两个问答**
    * 主键列不一定要添加主键约束，只要真的能保证它唯一且不为空，那就可以不用加约束。
    * 没有主键约束它也仍然叫主键，只不过这个主键数据不安全，数据库层面没有任何惩罚手段来拦。
    * 主键的成立条件只有一条——这一列真实地做到了唯一且不为空。

* **添加与删除**
    * 建表时单列主键直接加 `PRIMARY KEY` 写在列后边。
    * 建表时在表级写 `PRIMARY KEY (列)`，一个列或多个列都行，可以做组合主键。
    * 建表后用 `ALTER TABLE 表名 ADD PRIMARY KEY (列)` 补上，单列多列都可以。
    * 删除用 `ALTER TABLE 表名 DROP PRIMARY KEY`，不用写约束名。

    ```sql
    CREATE TABLE emp8 (
      eid  int PRIMARY KEY,
      name varchar(20),
      age  int
    );

    CREATE TABLE emp8 (
      eid  int,
      name varchar(20),
      age  int,
      PRIMARY KEY (eid)
    );

    ALTER TABLE emp8 ADD PRIMARY KEY (eid);
    ALTER TABLE emp8 DROP PRIMARY KEY;
    ```

    > **注意**：`DROP PRIMARY KEY` 不需要写约束名，因为一个表只有一个主键约束，数据库知道该删的是谁；而 `UNIQUE` 这些可能建了多个，才需要靠约束名来区分。

## 自增长约束

* **定义与动机**
    * > **定义**：限定某个整数类型的列，在插入数据时不需要显式赋值，它的值会自动增长，关键字是 `AUTO_INCREMENT`。
    * 没有它时，每次插数据都得考虑整数型主键 `id` 填什么，既要保证这个值没被用过，又要让它按某种顺序往下走。
    * 并发一上来，谁也不知道刚才那条到底用了哪个号，维护起来很苦恼。
    * 加上它以后只管填 `age` 和 `phone`，`id` 自动按之前的最大值加 1 往下长，这一列永远不重复。
    * 好处是解放双手、不用自己维护主键值，同时顺带保证了主键值唯一，它其实是 `PRIMARY KEY` 的好基友。

* **三条硬性规矩**
    * 添加位置：自增长只能加在主键列或者唯一约束列上，普通列加不了。
    * 数量限制：每个表只能有一个自增长约束，而且绝大部分情况下它都加在主键列上。
    * 类型限制：被限制的列必须是整数类型，字符串可能很长不会长，总不能靠 a、b、c、d、e 这样排下去。

* **插入时的四种写法**
    * 只写 `ename` 压根不提 `eid`，自动增长，取最大值 +1。
    * `eid` 写 `0`，照样自动增长。
    * `eid` 写 `NULL`，照样自动增长。
    * `eid` 写 `10`、`11` 这样的具体值，就插 10、11，不受自增长支配。

    | 插入时对 eid 怎么写 | 结果 |
    | :--- | :--- |
    | 只写 `ename`，压根不提 eid | 自动增长，取最大值 +1 |
    | eid 写 `0` | 照样自动增长 |
    | eid 写 `NULL` | 照样自动增长 |
    | eid 写 `10`、`11` 这样的具体值 | 就插 10、11，不受自增长支配 |

    > **易错点**：只有"不指定、指定 0、指定空"这三种情况才会触发自增长，一旦指定了值，数据库就听你的，插什么就是什么。

* **只记最大值**
    * 手工插过 10、11 之后，再执行一次不指定 `eid` 的插入，是从 12、13 开始而不是从 5、6 开始。
    * 删掉这几行再插入，仍然是从 14 开始，删了也不回头。
    * 中间空缺不填有两个原因：一是填空缺更麻烦，它得记住哪些值有、哪些值没有，每来一个新号都要跳着判断一次。
    * 另一个原因是真要"从头开始重新算"，还可能算出两条数据撞同一个 ID，直接重复了。
    * 它只记最大值这一个数，每次基于最大值往下长。

    ```text
    insert 指定 1、2             -> 1, 2
    insert 指定 0、NULL          -> 3, 4
    insert 指定 10、11           -> 10, 11   (5~9 空着，不补)
    insert 不指定 eid            -> 12, 13   (从最大值往下长)
    delete 掉这几行再 insert     -> 14       (删了也不回头)
    ```

* **建表加、改表加与删除**
    * 建表时在主键后边、或者在 `UNIQUE KEY` 后边写一个 `AUTO_INCREMENT`。
    * 建表后补上用 `ALTER TABLE emp10 MODIFY eid INT AUTO_INCREMENT`。
    * 删除把 `AUTO_INCREMENT` 去掉即可，原来的属性被覆盖掉，而主键列依然存在。

    ```sql
    CREATE TABLE emp9 (
        eid INT PRIMARY KEY AUTO_INCREMENT,
        ename VARCHAR(20)
    );

    ALTER TABLE emp10 MODIFY eid INT AUTO_INCREMENT;
    ALTER TABLE emp10 MODIFY eid INT;
    ```

* **与默认值的差别**
    * `DESC emp9` 之后，`eid` 那一行的 `PRI` 表示主键，在扩展信息那一列会出现 `auto_increment`。
    * 改表加自增长时不需要再写 `PRIMARY KEY` 或 `UNIQUE KEY`，它也不会覆盖你原有的主键或唯一约束。
    * 它只是在后边追加一个 `AUTO_INCREMENT`，这跟默认值、非空不一样，那些是会覆盖的。

## 外键

* **外键的定义**
    * > **定义**：外键指的是引用或者参照其他表主键列的那一列，它在自己这张表里就是个非主键的普通列。
    * 因为它是"外面的键"，所以叫外键。
    * 分数表里的分数是隶属于某一个学生的，那个指向学生信息的列就是外键。
    * 外键的取值范围应该在主键值的范围之内，写一个不存在的值，这条数据本身就错了。

    ```text
    [主表] student 学生表
      sid(主键)| sname
      ---------+--------
      1        | 二狗子
      2        | 德华
      3        | 蛋蛋
      ^
      | 分数表的 sid 列引用这里的 sid
    [子表] score 分数表
      cid(主键)| 分数 | 学科   | sid(外键)
      ---------+-------+-------+----------
      1        | 88   | Java  | 1
      2        | 90   | Java  | 1
      3        | 60   | MySQL | 4         <- 学生表里根本没有 sid = 4
    ```

    * 分数表自己的 `cid` 是主键，指向学生表 `sid` 的那一列是外键。
    * 二狗子的编号是 1，分数表里引用的也是 1，再叠加学科刚好是 Java，才拆出"二狗子 Java 考了 88 分"。
    * 90 分虽然也是 Java 的，但对应的是同一个人另一条记录。

* **外键与外键约束是两件事**
    * > **定义**：外键约束指的是外键应该引用主键的值，如果不添加这个约束，就可能出现错误数据。
    * 不加外键约束时，`sid` 那里写个 4 照样不报错。
    * 加了外键约束之后，插入 4 直接就报错了，因为主键里压根没有这个值。
    * 外键是一个列，外键约束是保证这个列数据正确的一种限制。
    * 外键约束跟主键约束是一个层级的概念：一个保证主键数据正确，一个保证外键数据正确。

    > **提示**：就算没加外键约束，它也依然是外键，这层关系你心里得知道，但最好还是加上。

* **外键的数量与主子表**
    * 一张表里可以有 $N$ 个外键，因为一张表完全可以关联很多其他表的数据。
    * 被引用的那张表叫主表（学生表），含有外键的那张表叫子表（分数表）。
    * 主子表是相对的，今天学生是主表，明天学生可能去引用别人，它自己就成了子表，看表关系时都是两两考虑。
    * 这给建表指点了顺序：先建主表，再建子表，不然你的子表引用谁去。

* **类型的对应**
    * 外键既然要引用主键，类型就应该和主键的类型对应，不能瞎搞。
    * 列名可以不同，命名不同也不影响关系，因为谁引用了谁程序员自己心里是清楚的。
    * 但最好相同，至少一眼能看出来。

* **有主外键不等于有外键约束**
    * MySQL 是关系型数据库，数据按类别存到对应的表中，表与表之间通过主外键建立数据之间的关系。
    * 关系型数据库里的"关系"指的就是主外键关系。
    * 两张表之间有主外键关系，就代表它们的数据互相关联，可以用水平连接查询的方式把两张表的数据查到一张表里去。
    * 有主外键就行，不一定非得有外键约束。

* **主表删不动了**
    * 学生表的 `sid` 一旦被别人引用了，就不能像以前那样随便删、随便改了。
    * 想删学生表里 `sid = 1` 这条，结果发现 1 已经被分数表引用好几次了，这时候就删不掉。
    * 默认情况下，只要有主外键约束，删除主表数据时如果子表存在引用，就会删除失败。
    * 想删有三条路：创建约束的时候指定允许删除；先把子表数据删掉再删主表；干脆把这个主外键约束干掉。

## 外键约束

* **加约束的三个前提**
    * 得有两张表。
    * 先建主表，再建子表。
    * 这个约束是加在子表里的，因为是子表去引用主表，只要有外键的表就是子表。
    * `DESC` 子表能看到 `PRIMARY KEY` 下面多了一条 `foreign key` 约束。
    * `DESC` 主表看不见外键，因为外键住在子表里，主表那边只有主键。

* **建表时加**
    * 约束写在字段列表最后，用逗号与前面的列隔开。

    ```sql
    CREATE TABLE student1 (
        sid INT PRIMARY KEY AUTO_INCREMENT,
        sname VARCHAR(20)
    );

    CREATE TABLE score1 (
        cid INT PRIMARY KEY AUTO_INCREMENT,
        number INT,
        sid INT,
        CONSTRAINT s_s_1_fk FOREIGN KEY (sid) REFERENCES student1(sid)
    );
    ```

    * 整行语法是 `CONSTRAINT 约束名 FOREIGN KEY (外键列名) REFERENCES 主表名(主键列名)`。
    * `constraint` 后面起个约束名，`fk` 是 foreign key 的缩写，随便起，只要不重复就行。
    * `foreign key` 后面括号里写当前子表里那个外键列的名字，两边都叫 `sid`。
    * `reference`（拼写别错）后面写主表名，括号里写主表的主键名。

* **建完表再补**
    * `ALTER TABLE score2 ADD CONSTRAINT 约束名 FOREIGN KEY (外键列) REFERENCES 主表名(主键列)`，与建表时那一行一模一样，粘过来改个名字就行。
    * 一定要加分号，否则语句会被连在一起执行，直接报错。

    ```sql
    ALTER TABLE score2 ADD CONSTRAINT s_s_2_fk FOREIGN KEY (sid) REFERENCES student2(sid);
    ```

* **删除要删两样**
    * 删约束用 `ALTER TABLE score2 DROP FOREIGN KEY 约束名`；主键能只写 `PRIMARY KEY` 是因为一个表只有一个，外键可能有多个，所以必须指定约束名。
    * 外键会主动创建一个外键索引，先用 `SHOW INDEX` 查出来，结果里的 `Key_name` 就是索引名。
    * 结果里 `sid` 那一行说明有个以 `sid` 为键的外键索引，再把它删掉。

    ```sql
    ALTER TABLE score2 DROP FOREIGN KEY s_s_2_fk;
    SHOW INDEX FROM score2;
    ALTER TABLE score2 DROP INDEX s_s_2_fk;
    ```

    > **提示**：有些版本删约束的时候会顺带把索引删干净，有些删不干净，老老实实两步手动删才能保证删得干净；索引是额外辅助的一种数据结构，留着就是白占地方。

## 级联动作

* **级联的定义与由来**
    * > **定义**：级联动作指的是对主表的数据进行修改或者删除时，子表如何做出响应。
    * 添加外键时可以设置动作，默认值就是：删除或修改主表数据时，如果子表有引用，就报错，不让你删。
    * 只有关键词涉及 `UPDATE` 和 `DELETE`，添加查询的时候是没有级联动作的。
    * 名字来自古代的连坐：一个人犯了事被判诛九族，其他人因为被连坐而遭殃，逻辑与主表改动子表跟着动是一样的。

* **四个可选值**

    | 值 | 主表 update / delete 时子表的响应 |
    | :--- | :--- |
    | `CASCADE` | 同步过去：主表改了子表跟着改，主表删了子表跟着删 |
    | `SET NULL` | 主表删了不连带删子表，只把子表里那个外键列置空 |
    | `NO ACTION` / `RESTRICT` | 子表什么都不做，但只要子表有引用就抛异常；默认值就是 `RESTRICT` |
    | `SET DEFAULT` | 给子表的外键列设一个默认值（有些驱动不识别，知道一下就行） |

    * `NO ACTION` 和 `RESTRICT` 效果基本一样。
    * `CASCADE` 最狠，一旦设上，主表那边一删，子表相关的记录同步删，甚至不知道数据去哪了。
    * 表里可以设置的这几类动作只针对主表的更新和删除，不涉及查询。

* **建议的设法**
    * `ON UPDATE CASCADE`：父数据更新，子数据自动跟着更新，比如父表 `sid` 从 1 变成 5，子表里所有引用 1 的行自动改成 5。
    * `ON DELETE RESTRICT` 走默认值：父数据删除时先检查，子表有引用就不让删。
    * 删除**不要**设成 `CASCADE`，太暴力了，实际业务里删主表数据之前得先提示一下子表有没有引用，人家同意了再删。

    ```sql
    CONSTRAINT 外键约束名 FOREIGN KEY (子表外键名) REFERENCES 主表名(主键名)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
    ```

    * 级联动作写在约束的最后，可以写 `ON UPDATE` 一个、`ON DELETE` 一个。
    * 建表的时候能写，建完表 `ALTER TABLE ... ADD CONSTRAINT` 也能写。
    * 不写就走默认值。

* **孤儿数据**
    * 万一真删了主表、子表还留着引用，那条数据就成了孤儿数据，是没人认领的数据。
    * 设成 `RESTRICT` 正好逼着你走一遍"确认子表引用再删"的正常业务流程。

## 拆表与多表关系

* **一张综合表的代价**
    * 不分表时搞一张大表同时记录学生信息和分数，学生信息会在多行里反复出现。
    * 都不用考虑主键重复的问题，光看数据就已经很乱了——大量冗余，而且展示得乱。

    ```text
      name   |age| 科目 | 分数
      -------+---+------+-----
      德华   |18 | MySQL| 88
      德华   |18 | Java | 90
      德华   |18 | MySQL| 77
      二狗子 |20 | Java | 66
    ```

    * 解法是拆：学生还单独存在学生表里，另外专门创建一张分数表，分数表里有分数的 id、具体分数和一个 `sid`。
    * 分数里通过存储学生的主键产生关联，这个主键在分数表里就叫它的外键。
    * 图里课程的名也没了是对的，课程后期也会独立创建一张表，分数表再去引用课程那张表。

    ```text
      学生表(主表)    分数表(子表)
      sid| name       sid| 科目 | 分数
      ---+ -------    ---+ -----+ ----
      1  | 德华       1  | MySQL| 88
      2  | 二狗子     1  | Java | 90
      3  | 蛋蛋       1  | MySQL| 77
      .  | ...        2  | Java | 66
    ```

* **拆表之后的三重好处**
    * 提高查询效率：混在一起时只想查学生信息也得把分数带着，分表后单查学生、单查分数都行，要联查就用多表查询。
    * 防止数据冗余，这是最核心的一点，八门课程的话德华得出现八次，数据重复得有多厉害。
    * 方便数据的更新和维护：不分表时改德华的名字要改所有出现的地方，分表之后通过主键引用，改这边那边自然就更新了（只要不改主键）。

* **多表关系的要点**
    * MySQL 是关系型数据库，数据按类别存储到对应的表结构中，一个项目里有成百上千个表是正常的。
    * 表和表之间通过主外键建立数据关系；所谓"表关系"，指的其实是表中数据的关系。
    * 拆表存储可以减少数据冗余，并提高查询和操作效率。
    * 正因为拆了表，不仅要会单表查询语法，还必须掌握多表的关联查询语法。
    * 关系型数据库的表结构需要提前创建，做数据操作之前要先学 DDL，创建表时通过分析数据之间的关系添加合理的约束和限制。

## 约束相关的面试题

* **建不建外键约束有什么区别**
    * 对查询、对是不是主外键关系没什么区别，建了只是语法层面多一层数据校验和保证。
    * 它是一种数据保证机制，而且就算没建外键约束，它依然是主外键关系。

* **建外键约束对查询有影响吗**
    * 有影响，但影响的是效率不是正确性。
    * 有了外键约束，数据库要做额外的关联检查和连接动作，查询效率会降低。

* **设计中为什么不想让字段是 null**
    * 不好比较：大于、小于、等于这些运算符可以比较数值类型、字符串类型、时间类型，但 `NULL` 比较不了。
    * 列里要是有 null，判断它是否等于某个值还得改用 `IS NULL` 或 `IS NOT NULL`，同一个"等于"动作要换不同符号，很麻烦。
    * 站在更高一点看，为 null 会影响索引效果，索引像图书目录能提高查询效果，但有 null 会打折扣。
    * 所以建表时建议把非空约束加好。

* **加了 `AUTO_INCREMENT`，字段是从 1 开始吗**
    * 答案不完全对，第一次添加、而且之前没手动插过值时，它就是从 1 开始。
    * 如果主动插过值就不一样，比如第一条手动给了 5，下次就从 6 开始。
    * 它会记录当前表中的最大值，每次在最大值基础上加，而且就算删除了也不会回头。

* **每个表都能随便选存储引擎吗**
    * 存储引擎是真实完成表数据操作的那部分功能的一个集合，MySQL 不同版本提供了不同的存储引擎，表和库都可以设置，没设置就走默认的。
    * 只要加了外键约束，存储引擎就不能随意选了，因为外键约束不能跨存储引擎使用。
    * 假设两张表一个是 A 引擎、一个是 B 引擎，它们之间建立外键约束是联不到一起去的。
    * 所以有外键约束不行，没有则每张表都能独立设置。

* **创建库时会给表添加完备的约束吗**
    * 真实场景下一般只加一些单表约束：非空约束、默认值约束、主键约束、自增长约束。
    * 这些是辅助在插入、更新数据时减少出错的手段。
    * 真实开发中一般不加外键和级联动作，加了它有时候会影响你整个表结构，你可能不知道这个数据哪去了，它就被级联删掉了，没经过你的手处理数据就没了，业务流程你也可能不清晰。
    * 阿里巴巴提供的 Java 开发手册里，强制要求不得使用外键以及级联，一切相关概念应该在应用内解决：想保证数据正确性，就在程序里用代码做校验和连接；想做级联删除，也请在程序里自己写代码做连表删除。

    > **提示**：所以答案是会加单表约束，外键约束一般场景不加。
