# 事务、权限管理与数据备份还原

## 事务与自动提交

* **自动提交（autocommit）**
    * > **定义**：事务默认就是自动提交的，每一条语句自己就独立待在一个事务中。
    * 语句执行成功，事务立刻自动提交；语句写错执行报错，这条语句就不会生效，数据还是原样。
    * 用 `mysql -u 账号 -p 密码` 登录进来的那一刻，默认都是自动提交。
* **事务（Transaction）**
    * > **定义**：把多条语句装进同一个事务里，让它们要么一起生效，要么一起不生效。
    * 存在理由：转账的加钱与减钱在自动提交下各自成为一个事务、加钱成功就加钱、减钱失败就减钱，两边互不干扰，钱就凭空多出来了。
    * 目标是把这些步骤焊成一个整体，绝不出现只成一半的局面。

## 手动控制事务

### 开关与语句收尾

* **SET autocommit**
    * > **定义**：修改 MySQL 系统变量 `autocommit` 的开关，把自动提交关掉，改成由自己决定何时提交。
    * 关闭写法 `SET autocommit = false;`，等价写法是 `SET autocommit = 0;`。
    * 恢复写法 `SET autocommit = true;`，等价写法是 `SET autocommit = 1;`。
* **关闭之后的行为**
    * 写一条也好、写 N 条也好，都不再自动提交，也不会立刻改变数据库的数据。
    * 无论单条还是多条，写完都必须主动调 `COMMIT` 或者 `ROLLBACK` 来收尾，事务才算真正执行完。
* **COMMIT 与 ROLLBACK 的选择**
    * 只要不报错就 `COMMIT`，如果报错就 `ROLLBACK`，二选一。
    * 调 `COMMIT` 数据才真的改；调 `ROLLBACK` 就代表回到这个事务之前的状态，事务同样结束。
    * 写进 Java 代码是同一套逻辑：把整段语句执行放进 `try-catch` 块，捕获到异常就 `ROLLBACK`，没异常就 `COMMIT`。

        ```sql
        SET autocommit = false;          -- 先关自动提交

        UPDATE t_员工表 SET salary = 10000 WHERE name = '孙宏亮';
        UPDATE t_员工表 SET salary = 8000  WHERE name = '周小胖';
        -- ……想写几条写几条

        COMMIT;                          -- 不报错就 commit
        -- ROLLBACK;                     -- 报错就 rollback，二选一
        ```

* **SHOW VARIABLES LIKE 'autocommit'**
    * > **定义**：用 `SHOW VARIABLES LIKE` 关键字查 MySQL 的系统变量，关键字加上 `autocommit` 就能看到当前是自动还是手动。
    * > **易错点** ⚠️：这条是查系统变量的，不是 `SELECT`，这两个词长得像，千万别混。

### 有效范围与演示环境

* **有效期只有一个连接**
    * 设置之后只要这个黑窗口不关闭，它就一直是 `false`；窗口一关再打开就是一个新连接，得重新设置一遍。
    * Java 里连接一次、设置一次只对这次连接有效，下次再连接还得重新设置。
    * > **易错点**：新建连接时 `autocommit` 一律是默认值（自动提交），所以每建一个新连接都要主动设置一次；不是新建连接的话，设置一遍就够了。
* **演示要用 CMD**
    * 小海豚在写完语句、点执行时，会在背后自动提交事务，关掉窗口都没用，看到的结果永远是「自动提交」的效果。
    * 演示手动提交要统一转到 CMD，用纯命令行的方式，不加任何额外工具的参与。

## 独立事务空间与回滚边界

* **START TRANSACTION**
    * > **定义**：在当前会话正在执行的 SQL 语句之上又浮动地升一层，单独划出一块独立的事务空间。
    * 无论现在是自动提交模式还是手动提交模式，都能用这条命令硬生生开出一个独立事务。
    * 空间里可以写若干条 SQL 语句，写完再主动提交或者回滚。
    * 空间内的语句和外层的语句互不干扰；想再开一个，重复写一遍 `START TRANSACTION` 就行。

        ```text
        ┌─────────────────────────────────────────┐
        │  外层：当前会话正在执行的 SQL 语句        │
        │        （可能本身就是自动提交）          │
        │                                         │
        │  ┌───────────────────────────────────┐  │
        │  │  START TRANSACTION;  ← 独立事务空间 │  │
        │  │  UPDATE ...;                      │  │
        │  │  UPDATE ...;    和外层的语句       │  │
        │  │  UPDATE ...;    互不干扰          │  │
        │  │  COMMIT; / ROLLBACK;              │  │
        │  └───────────────────────────────────┘  │
        └─────────────────────────────────────────┘
        ```

* **DDL 的回滚边界**
    * 事务只能针对数据的删除、修改、插入有影响，管不了 DDL（把表删了、删一个库这类语句）。
    * 先开启事务、中间做操作、最后 `ROLLBACK`，对 DDL 没有作用，删了就是删了。
    * > **易错点** ⚠️：`DDL` 不支持事务，或者说事务不支持 `DDL` 语句的回滚，加上 `ROLLBACK` 也回归不了。
    * 边界对照：误删除数据可以用 binlog 日志去回滚，那是可以回滚的，但事务回滚不了。

## 隔离级别

### 隔离性的强弱阶梯

* **隔离性（Isolation，缩写 I）**
    * > **定义**：一个事务内部的操作和使用权，对并发的其他事务来说是隔离性的；并发执行、多人同时操作同一个库表时，各个事务之间互相不干扰。
    * 好处是避免了事务之间的干扰，而真干扰了会产生一些数据上的问题。
* **隔离级别阶梯**
    * 隔离性有强有弱：桌上画一道三八线属于弱隔离（手能伸过来拿走铅笔橡皮），垒一道书墙更强，两张书桌之间垒一道砖墙最强。
    * 隔离性越高，两个事务之间的数据干扰程度越低，但性能也必然受影响。

        ```text
                隔离性弱  ──────────────▶  隔离性强

           三八线        书墙              砖墙
            │            │                │
          干扰多        干扰少           几乎无干扰
          性能高        性能中            性能低
        ```

    * 规律：隔离级别越高，数据一致性越好、数据越安全，但性能越弱，所以不一定隔离级别越高越好。

### 四个隔离级别与默认选择

| 隔离级别 | 中文名 | 脏读 | 不可重复读 | 幻读 | 谁拿它当默认 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `READ UNCOMMITTED` | 读未提交 | 可能发生 | 可能发生 | 可能发生 | — |
| `READ COMMITTED` | 读已提交 | 不会 | 可能发生 | 可能发生 | Oracle |
| `REPEATABLE READ` | 可重复读 | 不会 | 不会 | 很小概率 | MySQL |
| `SERIALIZABLE` | 串行化 | 不会 | 不会 | 不会 | — |

* **读未提交**
    * 最低的级别，相当于画了一道线，虽然有隔离性，但脏读、不可重复读以及幻读都可能发生。
* **读已提交**
    * 是 Oracle 的默认隔离级别，不会发生脏读，但可能会发生不可重复读以及幻读。
* **可重复读**
    * 是 MySQL 的默认隔离级别，避免了脏读，也不会发生不可重复读，很小概率下可能发生幻读。
* **串行化（序列化）**
    * 避免了脏读、不可重复读和幻读，也就是避免了所有的问题。
* **为什么不都用最高的级别**
    * 三个并发问题里只有脏读是真正的数据错误，剩下两个并不是错误，它们只是不符合事务四个特性中的一致性。
    * 推论：开发中也建议把隔离级别改成第二个 `READ COMMITTED`，只要避免脏读即可，性能比 `REPEATABLE READ` 更好。

### 隔离级别的查看与修改

* **SELECT @@transaction_isolation**
    * > **定义**：查看当前会话的隔离级别，MySQL 默认返回 `REPEATABLE-READ`。
* **SET TRANSACTION ISOLATION LEVEL** 〈隔离级别〉
    * > **定义**：修改隔离级别，后面填 `READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE` 里的任意一个。
    * 结论：是不是真的互不干扰、干扰到什么程度，决定权在隔离级别手里，不在「隔离性」这个词手里；隔离性只给方向，具体强弱由级别定。

### 串行化的表现与代价

* **没有并发，只有排队**
    * 串行化的含义就是没有并发了，并行变成串行，只能一个一个来。
    * 一侧的事务未提交时，另一侧的 `SELECT` 回车之后不执行、不出结果，必须等前者提交后才返回。

        ```text
        张三窗口（事务A）                      李四窗口（事务B）
        START TRANSACTION;                    START TRANSACTION;
        UPDATE ...;
        COMMIT; ──────────────────▶          SELECT * FROM t_bank;
                                               └─▶ 一直挂着，不出结果
                                                  必须等 A 提交后才返回
        ```

    * 它的解决根本就是把并发变成串行，两个事务不能再同时进行数据库操作，所以不会发生任何并发问题。
* **开发中用不了**
    * 例如注册用户功能只能一个个来注册，第 10000 个人要等前 9999 个人注册完毕才能注册，用了相当于把程序弄废。
    * 存在即合理，确实有应用场景：做秒杀功能为了防止商品超卖可以设成串行化；共享单车的押金几千万用户只能一个一个退，做不到这么干。
    * 结论：开发中不推荐用串行化，推荐 `READ COMMITTED`，它是性能和数据安全性之间最均衡的一个选择。

## 三个并发问题

### 脏读（Dirty Read）

* **本质**
    * 一个事务读取了另外一个事务未提交的数据，加粗的关键词就是「未提交」。
    * 两个事务同时发生，一个事务开启事务并操作了数据还没提交，另一个事务就读上了，看到不该看的东西。
* **为什么算真正的数据错误**
    * 因为对方可能数据回滚，人家回滚以后你看见的东西就是错误的。
    * 所以脏读读到的东西不一定是真实的数据，这是三个问题里唯一的真正错误。
    * 因此大家都避开了把隔离级别设成读未提交。

### 不可重复读（Non-repeatable Read）

* **本质**
    * 一个事务读取了另外一个事务提交的修改数据，注意是「已提交的修改数据」。
    * 场景：你进来时读这个数是 10000，你啥也没干，再读突然变成 12000，因为另外的事务真的加了 2000 并提交了。
* **为什么不算数据错误**
    * 对方真的已经把数据提交了、真的改变数据库了，只是你这次事务读到了。
    * 12000 这个数据本身没错，只是不符合一致性原则——一个事务中没有做修改，数据无缘无故从 10000 变成 12000，前后不一致。
* **分水岭与例子**
    * 与脏读的分水岭就在「未提交」和「已提交」这四个字。
    * 生活例子：财务在统计报销总额的周期内，员工来说金额应是 180 而不是 80。正确答案确实是 180，问题在于统计周期正中间不能让人知道，等统计完再增减 100 就好了。
    * 正确做法是事务期间读不到，等事务结束、开启下一个事务再读得到，这才绕开了不可重复读。

### 幻读（Phantom Read）

* **本质**
    * 一个事务读取了另外一个事务新增或者删除的记录，记录数不一样了，也有人叫虚读。
    * 读着读着突然间多了一条数据或者少了一条数据。
* **与不可重复读的分工**
    * 之前读到的「修改」是不可重复读；「新增或删除导致记录数变化」是幻读。
    * 生活例子：财务做账途中有人说「我忘了报这个月」，对方此前根本没提交过，这是新插入的数据，属于幻读。
* **算不算错误与发生概率**
    * 它读到的同样是提交的数据，所以也是一种数据正确的情况，本质上不是数据错误，就是不符合前后一致性原则。
    * 在 `REPEATABLE READ` 下基本也很小概率能发生，多次试验下来大约四个千八百回能出现一回。

### 并发问题的现场复现

* **银行表与并发场景**
    * 建表 `t_bank`，只有银行卡账号 `account` 和金额 `money` 两列，初始插入张三 10000、李四 10000。
    * 场景是张三欠李四一千块钱，还钱就是张三减一千、李四加一千；开两个 CMD 窗口各当一人，同时连接同一个库，先各自查当前隔离级别，两边都是 `repeatable read`。

        ```sql
        CREATE TABLE t_bank (
            account VARCHAR(20),   -- 银行卡账号
            money   INT            -- 金额
        );

        INSERT INTO t_bank VALUES ('张三', 10000);
        INSERT INTO t_bank VALUES ('李四', 10000);
        ```

* **降到读未提交复现脏读**
    * 两边都 `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;` 再各自 `START TRANSACTION;`。
    * 李四先查是 10000；张三给李四加 1000、给自己减 1000，李四再查变成了 11000，随后张三执行 `ROLLBACK`，李四第二天再查还是 10000。

        ```text
        时间轴     李四窗口                                        张三窗口
         t1      START TRANSACTION;
         t2      SELECT ... WHERE account='李四';  → 10000
                                                            START TRANSACTION;
         t3                                                     UPDATE ... '李四' +1000
         t4                                                     UPDATE ... '张三' -1000
         t5      SELECT ... WHERE account='李四';  → 11000
                 "四哥真到账了，欠条撕了"              ROLLBACK;  ← 全部作废
         t6      第二天再查 → 还是 10000
                 "昨天明明已经还我了，那 1000 块钱呢？"
        ```

    * 李四不会去质疑张三，因为他确实看到过 11000，这正是读到了别人未提交数据的后果。
* **提到读已提交复现不可重复读**
    * 两边都 `SET TRANSACTION ISOLATION LEVEL READ COMMITTED;` 再各自开事务。
    * 李四先查是 10000；张三加 1000 减 1000 后李四立刻查不到，因为读不到未提交数据、避免了脏读；等张三真的 `COMMIT` 之后，李四再查变成了 11000。

        ```text
        时间轴     李四窗口                                       张三窗口
         t1      START TRANSACTION;
         t2      SELECT ... '李四'  → 10000
                                                            START TRANSACTION;
         t2~t3   （读不到，未提交）    UPDATE '李四' +1000;
                                        UPDATE '张三' -1000;
         t4                                                     COMMIT;   ← 真提交了
         t5      SELECT ... '李四'  → 11000
        ```

    * 这个 11000 的数据是对的，但不符合一致性原则，这就是不可重复读。
* **提到可重复读检查幻读**
    * 两边都设成 `REPEATABLE READ` 后照老套路验一遍：两边开事务，李四先查是 11000，张三减 1000 加 1000 后 `COMMIT`，李四再读还是 11000，多试几遍仍是 11000，说明避免了不可重复读。
    * 验幻读时李四改查全部人 `SELECT * FROM t_bank;`，张三走新增而非修改，`INSERT INTO t_bank VALUES ('王五', 998);` 提交前李四必然读不到（读到就成了脏读），提交后如果读得到就是幻读，读不到说明该级别也避免了它。
    * 结论：MySQL 的默认级别基本把上面三个问题全解决了。

## 权限管理

### 权限控制的粒度与权限类型

* **三个级别**
    * 库级别：把哪个库让他可以操作。
    * 表级别：哪个表可以单独让他操作。
    * 特定的数据操作级别：对表上的数据赋予增删改查的动作。
* **权限类型**
    * 增删改查四个关键字，代表特定的数据操作。
    * `CREATE`、`DROP` 指的是对库表有没有创建和删除的权限，属于库表级别。
    * `GRANT` 指的是赋予权限本身——默认都用 root 这个超级管理员账号赋权，但给某个账号赋了这个权限，他也能去给别的账号赋权。
    * `ALL` 代表所有的权限。
* **管理周期**
    * 权限控制体现在四个操作上：创建用户、赋予权限、回收权限、删除用户。
    * 周期刚好对应一名员工从入职到离职：入职建账号、按项目需要给权限、离职前回收权限避免删库跑路、离职后删用户。

### 创建用户

* **CREATE USER**
    * > **定义**：通过 `CREATE USER` 写账号、在哪个主机可以访问、最后写密码，就完成建号。

        ```sql
        CREATE USER '赵伟峰'@'localhost' IDENTIFIED BY '密码';
        ```

    * 三个片段分别是建账号、用户名、来自哪台机器、用什么方式验证身份、密码，用户名和密码都放在单引号里，密码明文写。

        ```text
        CREATE USER   '小赵'   @   '%'   IDENTIFIED BY   '123456';
             │          │       │           │              │
             │          │       │           │              └─ 密码
             │          │       │           └───────────────── 用什么方式验证身份
             │          │       └───────────────────────────── 来自哪台机器
             │          └───────────────────────────────────── 用户名
             └──────────────────────────────────────────────── 建账号
        ```

    * `@` 是分隔符，斜杠后面那个百分号就是「任意主机」。
* **账号能登录不等于有权限**
    * 用 `mysql -u 小赵 -p123456` 确实能登录成功，但跑 `SHOW DATABASES` 只能列出自带的系统库，其他库一个都看不见，因为没给权限。
    * 结论：`CREATE USER` 只解决了「你是谁」，没解决「你能干什么」。
    * > **注意**：把密码明着写在 `-p` 后面纯粹是为了演示方便，正式环境别这么干。

### 主机部分决定使用范围

| 写法 | 含义 |
| :--- | :--- |
| `localhost` | 只能是本机访问 |
| `1.1.1.1` | 固定 IP，只能从这台机器访问 |
| `%` | 任何主机都可以访问 |

* **字段含义**
    * 这个字段指的是账号的使用范围：在同一台电脑上用客户端连本机的 MySQL，可以写成 `localhost`。
    * 换成另一台电脑（比如地址 `1.1.1.1`）来连这台 MySQL 就连不上了，因为之前设置的是 `localhost`，账号的使用范围只能在本机。
* **前后必须一致**
    * 创建用户时主机地址怎么写，`GRANT` 和 `REVOKE` 里就得怎么写；创建时写百分号，那里就不能写 `localhost`，写了不生效。

### 赋予权限

* **GRANT**
    * > **定义**：赋予权限的关键字，`grant` 就是「赋予」的意思。

        ```sql
        GRANT   SELECT   ON   test08_other.*   TO   '小赵'@'%';
          │       │       │        │            │       │
          │       │       │        │            │       └─ 来自哪台机器，% = 哪都能来
          │       │       │        │            └───────── 给谁
          │       │       │        └──────────────────────  作用到哪张表
          │       │       └───────────────────────────────  作用范围
          │       └───────────────────────────────────────  授什么权
          └───────────────────────────────────────────────  授权
        ```

    * 完整骨架是 `GRANT 权限列表 ON 数据库.表名 TO '账号'@'主机';`，可以给一个权限也可以给多个，多个之间用逗号隔开。
    * `ON` 后面写具体表名就是精确到那一张表，写星号 `*` 就是这个库里所有表；所有库所有表就写 `*.*`。

        ```sql
        GRANT SELECT, INSERT ON test08_other.* TO '赵伟峰'@'%';
        GRANT ALL ON *.* TO '赵伟峰'@'%';
        ```

    * > **易错点** ⚠️：地址位置的通配符是 `%`，库表位置的通配符是 `*`，这两个别搞反——百分号管「从哪台机器来」，星号管「哪个库哪张表」。
    * > **易错点**：命令里写的是 `GRANT`，不是「GRINT」。
* **权限是一项一项给的**
    * 只给 `SELECT` 就只能查，`DELETE FROM t_bank;` 会报没有执行删除的权限；再补一条 `GRANT INSERT ON test08_other.* TO '小赵'@'%';` 才能插；从头到尾没给过的 `DELETE` 永远都是错的。
    * > **注意**：权限是存在服务端内存里的，给完权限别急着在另一个窗口试，得刷新一下或者干脆退出重连一次。
    * 常用权限关键字还有 `CREATE`、`DROP`（库表创建和删除）、`ALL`（所有权限）。

### 查看用户与权限

* **SELECT user, host FROM mysql.user;**
    * > **定义**：查询用户利用的是 MySQL 自带的 `mysql` 库里的 `user` 表，用它查出有哪些账号、每个账号对应的主机是什么。
* **SHOW GRANTS FOR '赵伟峰'@'%';**
    * > **定义**：查某个账号具体有什么权限。

### 回收与删除用户

* **REVOKE**
    * > **定义**：回收权限用 `REVOKE`，做法跟 `GRANT` 几乎一样，权限写一个或写多个都行，写 `ALL` 就是回收全部权限。

        ```sql
        REVOKE INSERT, SELECT ON test08_other.* FROM '赵伟峰'@'%';
        REVOKE SELECT ON test08_other.* FROM '小赵'@'%';
        ```

    * 区分点只有一个：赋予是 `TO`（给谁），回收是 `FROM`（从谁那里回收）。
    * 回收完同样要退出重连，再查就连查询权限都没了。
* **DROP USER**
    * > **定义**：删除用户，直接写用户名即可，用于离职销号。

        ```sql
        DROP USER '赵伟峰';
        DROP USER '小赵'@'%';
        ```

    * > **易错点**：后面必须写完整的 `'用户名'@'主机'`，只敲用户名服务器会直接回一句「没有这个用户」；写对了之后让该账号退出再登录，会连登录都登不上，提示密码错误。
* **四个命令速记**
    * 创建用户 `CREATE USER`，赋予权限 `GRANT`，回收权限 `REVOKE`，删除用户 `DROP USER`，查用户查 `mysql.user` 表，查权限 `SHOW GRANTS`。

## 数据备份与还原

### 备份的意义

* **备份还原**
    * > **定义**：把你的数据导成一个外部文件存起来，等以后出问题了再通过这个外部文件把数据还原回来。
    * 备份文件不能和数据库放在同一台机器上，否则机器着火时备份也一起烧毁了。
* **三个用途**
    * 灾难性恢复：主机出各种问题，通过备份的数据进行还原。
    * 数据迁移：系统升级了、数据库版本升级了，数据可以迁过去。
    * 数据的复制：拿生产数据在别处复一份。
    * 典型用法：把生产环境的数据备份成文件传到本地，再在本地数据库里导进去，就能用真实数据做测试。
    * 结论：备份的意义并不是为了容灾，也可能是为了数据迁移，以及更好地进行开发和测试。

### 全量备份 mysqldump

* **全量备份**
    * > **定义**：不考虑什么时间点，把某一个库、或某库中某些表的全部内容（表结构 + 表数据）一次性导出到一个外部文件。
    * 备份完的文件可以传到任何位置，需要的时候再拿它做还原。
* **mysqldump**
    * > **注意**：它不是 MySQL 命令，是装 MySQL 自带的一个可执行工具，而且已经配到环境变量里，所以要用 CMD 执行，不是连到 MySQL 里执行。

        ```bash
        # 备份单库中的某一张表
        mysqldump -u root -p 库名 表名 > D:\xxx.sql

        # 备份单库中的所有表
        mysqldump -u root -p 库名 > D:\xxx.sql
        ```

    * 直接写库名、不写表名就会把这一个库里所有表的结构和表数据全导出去。
    * 备份出来的文件一般叫 `.sql`；密码直接写在命令行里会冒一条 warning，它推荐回车之后再输密码。
    * > **易错点**：想写密码就得紧贴着写，`-p` 和密码之间不能有空格，`-p 123456` 是无效的。
    * 导出的内容是建表语句加一条条 `INSERT` 语句，备份的从来不只有数据，表结构是一起被导出来的。

### 还原

* **mysql < 文件**
    * > **定义**：还原用 `mysql` 客户端，跟备份正好反着——备份是 `>` 重定向到文件，还原是 `<` 把文件喂给 `mysql`，选项只有 `-u`、`-p`、库名这几个。

        ```bash
        mysql -uroot -p 库名 < D:\xxx.sql
        ```

* **还原前必须先建库**
    * `mysqldump` 导出的脚本里只有 `CREATE TABLE` 和 `INSERT`，没有 `CREATE DATABASE`，所以得提前先建好一个空库（`CREATE DATABASE test08;`），再退出登录执行还原命令。
    * 还原完刷新，库有了、表有了、表里的数据也全拿过来了。
    * > **易错点**：跨环境还原，两边的 MySQL 版本必须一致，8.2 对 8.1、8.0 对 5.7 都是还原不了的。

## binlog 日志

### binlog 是什么

* **binlog（二进制日志）**
    * > **定义**：MySQL 的二进制日志，会记录所有数据库增删改查相关的操作，同时也会包括执行时间，可用于误删除数据的恢复、增量复制、数据同步。
    * 打个比方：客户端发来一条 SQL，MySQL 执行并落盘，就像古装片里掌柜记下一条账（`Write_rows, Pos=xxx`）；晚上对账发现数目不对，就回去看账本。
    * 默认情况下它就是开启的。
* **找回误删数据的本质**
    * 找回误删数据的第一步是先看有没有及时备份，没有的话就用 binlog 日志把数据找回来。
    * 结论：不是「把删掉的东西变回来」，而是把那条删除命令从序列里挑出来不执行，其余命令原样再跑一遍；把所有命令原样再执行一遍，数据照样是被删掉的。
    * 真实误删恢复挺麻烦的，误删数据有七八条还散落在不同日志文件里的话，得一段一段地切。

### 配置与文件命名

* **配置文件位置**
    * 位置在 MySQL 的安装配置文件里，Windows 上是安装目录（如 `C:\Program Files\MySQL\MySQL Server 8.2`）下的 `my.ini`，用记事本打开都行。
    * > **注意**：`Program Files` 是个隐藏文件夹，得在文件夹选项里把它显示出来。
    * 往下找到 `[mysqld]` 这一段，段名是 `mysqld`，这个 `d` 千万别漏了，写错了配置就不生效。
* **两处 binlog 相关配置**
    * 日志的名字，默认名是主机名（电脑的名字），建议改一个好认的。
    * 日志的存放位置，默认缓存在安装目录下的 `data` 文件夹里，这个位置用默认的就行。

        ```ini
        [mysqld]
        log-bin = my_log_bin
        ```

* **文件名规则**

        ```text
           my_log_bin.000001        my_log_bin.000002        my_log_bin.000003
                  │                       │                       │
             FLUSH LOGS 之前          FLUSH LOGS 之后         再切一刀
             建库、建表、插数据        删除 + 后续的操作         ……
           后缀是六位序号，前五位是零，从 000001 开始
        ```

    * 到 `data` 目录下能同时看到改名前的老文件，因为默认那一份是以主机名命名的。
    * > **注意**：这些是二进制文件，不是文本文件，用记事本这类工具根本看不了，得用专门的工具去看。

### 造两段日志

* **RESET MASTER**
    * > **定义**：把原有的 binlog 日志文件清空，相当于一切从零开始记。
    * 结论：这一条会把之前所有日志都清掉，执行完原来那个 000002 被删掉，只留下一个 000001，而且这个 000001 里面一条命令都没有，纯粹就是新建了一个空文件。
* **FLUSH LOGS**
    * > **定义**：只是创建一个新的日志文件，执行完就会出现 `my_log_bin.000002`，后续所有操作都自动记录到这个新文件里。

        ```sql
        RESET MASTER;

        CREATE DATABASE test08_blog;
        USE test08_blog;
        CREATE TABLE table_01 (id INT, name VARCHAR(20));   -- 就 id、name 两列
        INSERT INTO table_01 VALUES (1, '二狗子');
        INSERT INTO table_01 VALUES (2, '驴蛋蛋');

        FLUSH LOGS;
        ```

    * 分好文件之后的结构如下，000002 里记的是先 `DELETE` 掉 `id = 2` 那条（驴蛋蛋就这么没了），再插一条 `id = 3` 的数据，然后 `SELECT *` 查一下这个表，接着又插一条 `id = 4` 的数据。

        ```text
           RESET MASTER 之后
                  │
                  ▼
           my_log_bin.000001  ──  CREATE DATABASE test08_blog
           （一个空文件起步）        USE test08_blog
                                    CREATE TABLE table_01 (id, name)
                                    INSERT 二狗子、驴蛋蛋
                                  ── FLUSH LOGS 从这里切一刀 ──
           my_log_bin.000002  ──  DELETE  id = 2       ← 驴蛋蛋没了
                                    INSERT  id = 3
                                    SELECT *
                                    INSERT  id = 4
        ```

* **恢复目标**
    * 目标很明确：把中间那条被误删的驴蛋蛋找回来。

### 查看日志文件与事件清单

* **两条 SHOW 命令**

        | 命令 | 作用 |
        | :--- | :--- |
        | `SHOW BINARY LOGS;` | 列出当前所有 binlog 文件及其大小（表格形式） |
        | `SHOW BINLOG EVENTS;` | 查看日志文件里记录了哪些命令的清单 |

    * 执行 `SHOW BINARY LOGS;` 能看到 `my_log_bin.000001` 和 `my_log_bin.000002` 两个文件，前面是名字，后面是 Size，每切一次日志它就涨一截。

        ```sql
        SHOW BINARY LOGS;

        SHOW BINLOG EVENTS;                                  -- 默认看第一个
        SHOW BINLOG EVENTS IN 'my_log_bin.000002';           -- 指定看第二个
        ```

    * > **注意**：这里看的是命令清单，不是命令细节；清单就是把完整日志里的关键字截出来给你看。
    * 000001 的清单里全是建库、建表、插入数据这类命令，最后还有一条开启新日志的记录；000002 里就清爽多了，一条 `Delete_rows`、一条插入 `Write_rows`（位置 391）、另一条插入（位置 706），一目了然。
* **清单字段**

        ```text
          事件类型        对应的操作        Pos          End_log_pos     Server_id
         ─────────────────────────────────────────────────────────────────────────
          Query           创建表结构        507          5xx             1
          Write_rows      往表里写数据      ...          ...             1
          Delete_rows     删除数据          391          441             1
                                       ↑            ↑
                                  命令开始坐标   命令结束坐标
        ```

    * `Pos` 是这条命令开始的坐标，`End_log_pos` 是它结束的坐标，`Server_id` 表明这条来自哪个 MySQL 服务。
    * 读懂事件类型这一列、大概看出干了啥就够了，但位置信息必须记住——下一步恢复数据全靠它。
    * 只想看某条之后的几条也支持：`SHOW BINLOG EVENTS IN 'my_log_bin.000002' FROM 391 LIMIT 2 OFFSET 0;`，`FROM` 是从哪个坐标开始查，`LIMIT` 写查几条，`OFFSET` 写 0 表示从这个坐标开始算，效果与分页关键字一致。

### mysqlbinlog 工具

* **两个作用**
    * 第一个作用是查看 binlog 日志的内容细节：`mysqlbinlog -v my_log_bin.000002`，写一个 `-v` 是详细，写两个 `-vv` 信息更多。
    * 跟 `SHOW BINLOG EVENTS` 的区别是：那个看的是被截取过关键字的清单，这个看的是具体的内部内容。
    * 第二个作用（真正的重点）是把 binlog 日志文件导成 SQL 脚本，而且能指定从哪个位置导、到哪个位置停，用的就是清单里看过的 `Pos`。
* **使用前提**
    * 它跟 `mysqldump` 一样是装完 MySQL 就自带的工具，不是 MySQL 的一个 SQL 命令。
    * > **提示**：得在 CMD 里执行，跟 `mysql -u ... -p` 那个连接不是一回事；而且它默认读的是当前目录下的文件，所以执行前先把 CMD 定位到 `data` 目录，命令里就能直接写相对文件名了。

### 导出三段脚本并还原

* **掐掉删除，两头分开导**
    * 那条 `DELETE` 的 `Pos` 是 391，`End_log_pos` 是 441，也就是说 391 是它的起点，441 就是删除之后下一条事件的起点。

        ```bash
        # ① 000001 里没有删除，整段导出，一个位置都不用指定
        mysqlbinlog my_log_bin.000001 > D:\bin001.sql

        # ② 000002 导出到删除之前为止，在 391 停
        mysqlbinlog --stop-position=391 my_log_bin.000002 > D:\bin002.sql

        # ③ 000002 从删除之后开始，441 起
        mysqlbinlog --start-position=441 my_log_bin.000002 > D:\bin003.sql
        ```

    * `--stop-position` 是「到哪停」，`--start-position` 是「从哪开始」；常用的其实就这两个。
    * 结论：之所以是三个脚本，第一个是完整的 000001，第二个是 000002 里删除之前的部分，第三个是 000002 里删除之后的部分；中间那条 `DELETE` 两头都不带，天然就被跳过了。

        ```text
           误删之前的完整操作序列
           ├─ CREATE DATABASE test08_blog
           ├─ CREATE TABLE table_01
           ├─ INSERT 二狗子
           ├─ INSERT 驴蛋蛋
           ├─ DELETE 驴蛋蛋   ← 丢掉这一条，不导出
           ├─ INSERT 391
           ├─ SELECT *
           └─ INSERT 706
                │
                │  掐掉 DELETE，两头分开导
                ▼
           bin001.sql   ← 000001 整段
           bin002.sql   ← 000002 开头 … 391
           bin003.sql   ← 000002 441 … 末尾
                │
                ▼
           三个脚本依次执行 ──►  驴蛋蛋回来了
        ```

    * > **易错点**：文件名里的分隔符是下划线不是中划线，`my_log_bin` 写成 `my-blog-bin` 会直接给一个 `No such file`。
    * > **注意**：导 002 的时候它会报一条 warning（没有指定销毁时间之类的），不用管，那只是警告不是错误。
* **执行还原**
    * 先 `mysql -uroot -p < D:\bin001.sql`，会报不能创建 `test08_blog` 因为它已存在——这个报错恰好说明 `mysqlbinlog` 导出的脚本是自带 `CREATE DATABASE` 语句的。
    * 这一点跟 `mysqldump` 完全不同：`mysqldump` 只给建表和插入，所以还原前得自己先建库；而 binlog 脚本自带建库，所以目标库必须先不存在，把整个库删掉即可。
    * 三个脚本依次执行完，库表结构就有了、`table_01` 里是二狗子和驴蛋蛋，驴蛋蛋找回来了。
* **位置参数的另一种用法**
    * 从某个时间节点开始截取到剩下的日志文件，拿它做一个增量更新也是可以的。
