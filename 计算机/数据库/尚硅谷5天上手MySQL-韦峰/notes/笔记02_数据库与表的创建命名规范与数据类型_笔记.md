# 数据库与表的创建、命名规范与数据类型

## 一条数据进库的四道关

* **四步流程**

    ```text
      第①步  创建数据库     库是最大的容器，没库数据无处安放
      第②步  明确字段清单   字段没理清，第③步根本无从下手
      第③步  创建表         字段名 + 类型 + 约束，容器正式成型
      第④步  插入数据       往容器里放货

      第①②③步：造容器、管容器  →  DDL
      第④步：往容器里放货        →  DML
    ```

    * 建表之前必须先明确这类数据应该有哪些字段，不明确字段就无法建表
    * 容器都没有，谈不上往容器里放数据，所以必须先学 DDL

## 数据定义语言

* **数据定义语言（Data Definition Language，DDL）**

    * > **定义**：定义和管理数据库结构的语言
    * 结构包含库、表，以及后期可扩展的索引、视图等，这些对象的创建、删除、修改都归 DDL 管
    * 本阶段重点是对库和表的行为操作
    * > **易错点**：⚠️ DDL 不涉及对数据相关的操作，它玩的是容器，关注的是数据结构和元数据

* **三个关键字**

    * `CREATE` —— 创建，完成库、表、索引等的创建
    * `ALTER` —— 修改，完成库、表以及列的修改
    * `DROP` —— 删除，极其危险的关键字，完成库、表、索引相关的删除

## 命名规定与命名的规范

* **规定与规范是两回事**

    * > **定义**：规定是不能这么做，这么做了相当于报错，类似生活中的法律，不能触犯
    * 规范是这么做会更好，不这么做也不会报错，类似生活中的道德约束
    * 学习顺序是先弄清规定确保不犯错，再弄清规范怎么做更好

* **标识符的五条规定**

    * 命名长度不得超过 30 个字符
    * 只能包含大写字母、小写字母、0 到 9 以及下划线，除了这 63 个字符其他都不能包含
    * 不能用数字开头
    * 数据库、表、字段这些名称中间不能包含空格
    * 名字不能重复：同一 MySQL 管理系统中库名不能重复，同一库中表不能重复，同一表中字段也不能重复
        * A 库和 B 库中各有一个叫 `student` 的表没问题，但 A 库中不能出现两个 `student` 表
        * 字段重复后根本不知道操作的到底是哪一列
    * 必须保证名称没有使用保留字、关键字，等同于 Java 里不能把属性命名为 `class`
    * 坚决要用关键字时（如订单表叫 `order`），用两个反引号包裹：`\`order\``
        * 后续对该表操作时，插入数据、读取数据、指定表都要记得加这对反引号
        * 结论：加反引号关键字也能用，但不建议
    * > **易错点**：⚠️ 把查询关键字放在名字前面（如 `select`），开发工具会误认为它就是一个关键字，直接报错

    | 名称 | 判定 | 原因 |
    | :--- | :--- | :--- |
    | `user_account` | 可以 | 英文，没超 30 字符 |
    | `product_name` | 可以 | 用下划线连接 |
    | `user__Name` | 可以 | 两个下划线，中间加一个大写字母 |
    | `user account` | 不可以 | 中间包含了空格 |
    | `user-account` | 不可以 | 中间用了特殊符号（连字符）拼接 |
    | `select` | 不可以 | 使用了 select 关键字 |
    | `123user` | 不可以 | 使用数字开头 |

* **阿里巴巴规范手册中的三条通用要求**

    * 注释要清晰简洁：注释是为了描述这段代码的，读注释不看代码就该知道它干什么
        * 注释写得很乱又不简洁，建议干脆别写，因为它已经成了一个错误的指南
    * 库、表、列名应该使用小写：这不是强制规定，用大写也行，但建议小写
        * 很多开发工具会自动把关键字识别成大写，名称写小写正好把它们区分开
        * 某个名称写完莫名其妙变成大写，就证明它被写成关键字了
        * 多个词拼接推荐用下划线，这种形式叫蛇形命名法（snake_case）；驼峰式可以用但不推荐
    * 库、表、列应简洁明了且具有描述性：别用拼音，不行就找个翻译软件翻译

* **库、表、列各自的命名依据**

    * 库：跟应用程序一致，一个应用对应一个库，Java 项目名不要写成大驼峰，全小写加下划线即可。
    * 表：遵循业务，一个库中有很多表，表对应支付任务、配置等具体业务；只有一层写成单层也没问题
    * 列：遵循实体属性，类似 Java 的属性命名，如 `product_name`、`product_price`、`customer_id`
    * > **提示**：表命名相当于类命名，列命名相当于属性命名，只不过用下划线拼接而不是驼峰式
    * 表名写三层有点冗余，`user_account_table`、`order_detail_table` 后面的 `table` 都可以省略

    | 对象 | 命名依据 | 标准写法 | 例子 |
    | :--- | :--- | :--- | :--- |
    | 库 | 对应的应用程序 | 小写 + 下划线 | `my_project` |
    | 表 | 对应的业务 | 小写 + 下划线 | `user_account`、`order_detail`、`product_catalog` |
    | 列 | 实体属性 | 小写 + 下划线 | `customer_id`、`product_price` |

## 库管理语句

### 创建数据库

* **五条创建语法**

    * `CREATE DATABASE 数据库名;` —— 直接建库，不指定字符集和排序方式，走 MySQL 默认值
        * `CREATE` 后必须跟 `DATABASE`，因为 `CREATE` 也能创建表，要指明创建方向
        * 关键字忽略大小写，空格隔开跟数据库名，分号结尾
    * `CREATE DATABASE IF NOT EXISTS 数据库名;` —— 不存在就创建，已存在也不报错，推荐使用这种
    * `CREATE DATABASE 数据库名 CHARACTER SET 字符集;` —— 只指定字符集
    * `CREATE DATABASE 数据库名 COLLATE 排序方式;` —— 只指定排序方式
    * `CREATE DATABASE 数据库名 CHARACTER SET 字符集 COLLATE 排序规则;` —— 两者同时指定，不分先后
    * 字符集和排序方式是可选的；只指定字符集而没指定排序方式时，排序方式走 MySQL 默认值

* **字符集（character set）**

    * > **定义**：字符与底层存储字节之间的对应关系，也就是我们常说的编码格式
    * 字符最终都用字节存储，选错字符集就会出现乱码；要存中文一般选 UTF 系列
    * `utf8` 一个字符占 3 字节，存储位数少、有些符号找不到会乱码，是 5.7 与 5 系列的默认字符集，不推荐
    * `utf8mb4` 一个字符占 4 字节，存储宽度更广，基本覆盖所有中文相关内容、表情符号也能存，是 MySQL 8 的默认字符集，推荐
    * 加 `mb3` 后缀是因为早期 `utf8` 这个名称已经被占用了。

* **排序规则（collation）**

    * > **定义**：在字符集的基础上决定字符之间如何进行比较
    * `ai` 表示大小写不敏感，`as` 表示大小写敏感，`ci` / `cs` 表示比较时是否忽略大小写
    * MySQL 8 默认 `utf8mb4` + `utf8mb4_0900_ai_ci`，即四个字节存字符且忽略大小写
    * 业务上对大小写敏感时，把排序规则换成 `as_cs`

    | 排序规则 | 含义 | `'apple' = 'Apple'` 的结果 |
    | :--- | :--- | :--- |
    | `utf8mb4_0900_ai_ci` | 大小写不敏感 | 判定为真，值为 1 |
    | `utf8mb4_0900_as_cs` | 大小写敏感 | 判定为假，值为 0 |

* **两者必须成套出现**

    * 一句话钉死：字符集决定会不会乱码，排序规则决定字符如何对比
    * 查看当前配置：`SHOW VARIABLES LIKE 'character_set_database';` 与 `SHOW VARIABLES LIKE 'collation_database';`
    * > **易错点**：⚠️ 建库写 `CHARACTER SET utf8 COLLATE utf8mb4_0900_as_cs` 会报错，因为 `utf8` 等同于 `utf8mb3`，与 `utf8mb4` 不是一套，排序规则必须在对应的字符集下设置
    * 改正写法：`CREATE DATABASE IF NOT EXISTS ddl_d1 CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;`
    * 修改排序规则同理，当前库是 `utf8mb4` 才能选 `utf8mb4` 系的排序规则。

### 查看、切换、修改与删除

* **查看**

    * `SHOW DATABASES;` —— 查看 MySQL 中所有库，用的是复数形式 `DATABASES`
    * `SELECT DATABASE();` —— 查看当前使用的库，这是一个函数，带一对小括号
    * `SHOW TABLES FROM 数据库名;` —— 查看某个数据库下的所有表
    * `SHOW CREATE DATABASE 数据库名;` —— 查看当初创建该库的完整建库语句与字符集配置

* **切换**

    * `USE 数据库名;` —— 选中数据库，对数据操作前必须先选中库，第一件事就是执行它
    * 要切换到其他库就再执行一次；同一时刻只能有一个库处于被选中的激活状态

* **修改**

    * `ALTER DATABASE 数据库名 CHARACTER SET 字符集;`
    * `ALTER DATABASE 数据库名 COLLATE 排序方式;`
    * `ALTER DATABASE 数据库名 CHARACTER SET 字符集 COLLATE 排序方式;`
    * 一般把字符集写在前面，因为排序方式依赖于字符集
    * > **易错点**：⚠️ 数据库没有修改名称的指令，可视化工具的改名功能底层也是把旧库备份导出、创建新库导入数据、再删旧库

* **删除**

    * `DROP DATABASE 数据库名;`
    * `DROP DATABASE IF EXISTS 数据库名;` —— 先判断存在再删除，不存在也不报错
    * > **易错点**：创建时是 `IF NOT EXISTS`（不存在才创建），删除时是 `IF EXISTS`（存在才能删除），这里边没有 `NOT`
    * > **注意**：真实项目里库名是手敲出来的，删库前一定要拿眼睛再核对一遍名字

## 建表语法

### 括号内外与列的骨架

* **完整骨架**

    ```text
      CREATE TABLE [IF NOT EXISTS] 表名
      (
          列名1  列类型1  [列约束1]  [COMMENT '列注释1'],
          列名2  列类型2  [列约束2]  [COMMENT '列注释2'],
          ...
          列名N  列类型N  [列约束N]  [COMMENT '列注释N']   ← 最后一列后面不加逗号
      )
      [表选项：字符集 / 排序规则 / 表注释]                 ← 括号外才是表级别的描述
    ```

    * 括号内部放列的信息，括号外部才是表级别的描述，这一层内外关系最容易被忽略
    * 方括号是可选的意思，不要真的写方括号

* **必写三样与可选的那些**

    * 必写：表名、列名、列类型；列名与类型之间用空格隔开，列与列之间用逗号隔开
    * 可选：列约束，如 `NOT NULL`、`AUTO_INCREMENT`；约束是对数据做限制的语法，可以加一个也可以不加 n 个
    * 可选：列注释 `COMMENT '列注释'`，描述该列的含义
    * 括号外：表级约束如 `PRIMARY KEY (post_id)`，以及表描述符如 `ENGINE`、`DEFAULT CHARSET`、表级 `COMMENT`
    * 表不指定字符集就选用所在库的字符集
    * 表描述符要写就在括号后加 `key=value`，多组用空格隔开
    * 推荐给表和列都加注释，这样读起来更清晰，接手的人靠注释能看懂表和字段的含义

* **完整示例**

    ```sql
    CREATE TABLE IF NOT EXISTS `post` (
        `post_id` INT NOT NULL AUTO_INCREMENT,
        `title` VARCHAR(255) NOT NULL COMMENT '帖子标题',
        `content` TEXT NOT NULL,
        PRIMARY KEY (`post_id`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='论坛帖子表';
    ```

* **四条注意事项**

    * 列名和列类型必须填写，其他都是可选的；配合关键字、括号、逗号一起写
    * 推荐 `CREATE TABLE IF NOT EXISTS 表名 (...)` 的优雅写法，避免表已存在导致程序运行中报错
    * 注释不是必须的但很有必要，且一定要保证注释描述是清晰的
    * > **易错点**：列之间用逗号隔开且逗号一定是英文的；最后一列末尾加逗号会直接报错
    * > **结论**：表名对标业务，列名对标属性，这两项按 SQL 的命名规定和规范来填
    * `DEFAULT CHARSET = utf8mb4` 中等号紧跟关键字，写法固定
    * > **提示**：注释内容在 MySQL 里双引号单引号都能用，但推荐单引号，这才是 MySQL 的语法规则，Java 的习惯别混进来

### 在线图书管理系统建库建表

* **建库并切换**

    ```sql
    CREATE DATABASE IF NOT EXISTS books_labs
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_general_ci;

    USE books_labs;
    ```

    * 字符集要显式写出来，不要图省事用默认值，避免不同版本的默认字符集不一样
    * 排序方式名字末尾的 `ci` 表示不区分大小写
    * 建完必须 `USE` 切过去，后面创建的表才落在这个库里

* **建表并解读三列**

    ```sql
    CREATE TABLE IF NOT EXISTS books
    (
        book_name   VARCHAR(20)  COMMENT '图书名',
        book_price  DOUBLE(4, 1) COMMENT '图书价格',
        book_number INT          COMMENT '图书数量'
    ) DEFAULT CHARSET = utf8mb4 COMMENT = '图书表';
    ```

    * `book_name VARCHAR(20)` —— `VARCHAR` 是短字符串类型，20 是最大长度 20 个字符，超过报错
    * `book_price DOUBLE(4, 1)` —— `DOUBLE` 是浮点类型，4、1 表示总共四位、其中一位是小数，整数部分只能占三位
    * `book_number INT` —— `INT` 是整数类型
    * 验证：`SHOW TABLES FROM books_labs;`

## 整数类型

### 种类、标准与方言

* **整数类型**

    * 支持的类型有 `TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT`、`BIGINT`
    * `INT` 有两种写法，写成 `INT` 或 `INTEGER` 是同一个东西
    * > **结论**：标准 SQL 中只有 `INT`、`INTEGER`、`SMALLINT` 是标准的；`TINYINT`、`MEDIUMINT`、`BIGINT` 属于方言，是标准不支持、由 MySQL 单独扩展出来的。

* **由存储字节推值范围**

    * 1 字节是 8 位，n 字节的类型能表示 $2^{8n}$ 个不同的值，后边的范围不用背，从存储字节就能算出来
    * 无符号取 $0 \sim 2^{8n} - 1$；有符号把这个范围对半分，一半负一半正，正的那半算上零

    | 类型 | 存储空间 | 无符号最大值 | 有符号范围 |
    | :--- | :--- | :--- | :--- |
    | `TINYINT` | 1 字节 | $2^8 - 1 = 255$ | $-128 \sim 127$ |
    | `SMALLINT` | 2 字节 | $2^{16} - 1 = 65535$ | $-32768 \sim 32767$ |
    | `MEDIUMINT` | 3 字节 | $2^{24} - 1 = 16777215$ | $-8388608 \sim 8388607$ |
    | `INT` / `INTEGER` | 4 字节 | $2^{32} - 1$ | $-2^{31} \sim 2^{31} - 1$ |
    | `BIGINT` | 8 字节 | $2^{64} - 1$ | $-2^{63} \sim 2^{63} - 1$ |

    * `SMALLINT` 的范围与 Java 的 `short` 一致，`INT` 对标 `int`，`BIGINT` 对标 `long`，`MEDIUMINT` 在 Java 里没有对应类型

### UNSIGNED 无符号修饰符

* **加与不加的差别**

    * 什么都不写默认就是有符号，既有负值也有正值，`TINYINT` 是 $-128 \sim 127$，超出范围会报错
    * 类型后面加 `UNSIGNED` 就是无符号，负号那一半的范围去掉挪到正值那边，`TINYINT` 变成 $0 \sim 255$
    * `UN` 是"没有"、`SIGNED` 是"符号"，这个组合是固定的。
    * > **易错点**：⚠️ `UNSIGNED` 只能跟着数字类型用，并且要紧贴着数值类型后边写，二者是一一组合，要写就一起写
    * 浮点类型的 `UNSIGNED` 跟整数不同：范围 $-1 \sim 1$ 加了之后只变成 $0 \sim 1$，不会像整数那样迁移到 $0 \sim 2$
    * > **结论**：浮点类型加不加 `UNSIGNED` 没什么意义，它不节约空间，只是把负值那一部分砍掉了。

### 怎么选

* **两条选型逻辑**

    * 范围必须能覆盖要存的数据值范围，否则会报错
    * 在范围符合的前提下选占有空间最小的那个
    * 范围不确定时（如学号、编号）建议尽量选大的，宁可多占点空间也不能报错

## 浮点与定点类型

### FLOAT 与 DOUBLE

* **浮点类型**

    * `FLOAT` 占 4 字节是单精度，`DOUBLE` 占 8 字节是双精度，跟 Java 一样
    * 声明后需要加括号，`FLOAT(M, D)`、`DOUBLE(M, D)`
    * M 指的是所有位置的总长度，整数位加小数位之和，小数点不算在里面；D 指的是小数位数
    * `FLOAT(5, 2)` 最大只能装 `999.99`，M 减 D 得到整数部分只能写三位

    | 类型 | 存储空间 | M 最大值 | D 最大值 |
    | :--- | :--- | :--- | :--- |
    | `FLOAT` | 4 字节 | 24 | 8 |
    | `DOUBLE` | 8 字节 | 53 | 30 |

* **超范围时的表现**

    * `height FLOAT(4, 1) UNSIGNED COMMENT '身高，保留小数点一位，多位四舍五入'`
    * 身高 `180.565` 存进这一列不会报错，多出的一位会四舍五入向前进一位，最终存 `180.6`

* **为什么不推荐**

    * 从 MySQL 8.0.17 版本开始就不推荐使用 `FLOAT` 和 `DOUBLE`
    * 原因是它们采用二进制存储表示法，底层存二进制、转十进制时可能出现精度失准，比如除一个数莫名其妙多出好几轮小数点
    * 精度要求不高时（身高、体重）用它没问题；存现金、货币、价格用它就太不合理了。

### DECIMAL 定点数

* **定点数（DECIMAL）**

    * > **定义**：绝对精度的十进制数据类型，底层采用十进制存储和转换，不会损失精度
    * 标注货币和商品价格用它
    * 写法与 `FLOAT`、`DOUBLE` 一样是 `DECIMAL(M, D)`，M 最大 65 位、D 最大 30 位
    * 存储空间是动态计算的，根据传入的数据值算；不同 MySQL 版本的计算公式有区别
    * `emp_salary DECIMAL(8, 1)` 表示小数点后保留一位、前面是七位，最大 999 万；不够可以把 M 加大成 `DECIMAL(11, 1)`
    * D 可以写成 0，代表没有小数位、全是整数位
    * 多出一位也会四舍五入向前进位
    * > **结论**：精度要求不高用 `FLOAT`、`DOUBLE` 按范围选；跟钱有关、差一分钱都不行的（工资、商品价格）建议用 `DECIMAL`

## 短字符类型

### CHAR 固定长度

* **定长字符（CHAR）**

    * > **定义**：固定长度类型，一旦声明就固定占有对应空间，实际数据小于长度限制时用空格补满
    * 可以加最大长度限制 M，超过会报错；M 最多 255，一列最多只能存 255 个字符
    * 声明时可以不写 M，不写就等于 `CHAR(1)`，即 $M=1$
    * 占用空间与编码格式有关，空间 = M × 字节比，`utf8mb4` 下声明 255 就是 $255 \times 4$
    * 适用场景：固定长度且 M 小于等于 255，比如性别 `CHAR(1)`、手机号 `CHAR(11)`
    * > **结论**：它不需要伸缩运算，性能相对于 `VARCHAR` 会好一些

    ```text
      声明：name CHAR(5)
      插入：A

      最终存储：[A][ ][ ][ ][ ]      ← 右侧补空格，永远占满 5 个字符
    ```

### VARCHAR 可变长度

* **变长字符（VARCHAR）**

    * > **定义**：可变、可伸缩的字符串类型，会根据内容伸缩最终存储空间
    * 声明时必须指定最大长度 M，不指定会直接报错
    * 理论上没有类型自带的最大限制，但受一行数据最多 65535 字节的硬限制
    * 占用空间 = 实际长度 × 字节比 **+ 1**；`CHAR` 的空间 = M × 字节比
    * 那额外的 1 个字节是用来记录该列是否为空的，`VARCHAR` 可能真为空而 `CHAR` 会自动补全
    * 适用场景：短文本但长度不确定，比如姓名、地址、个人签名、描述信息

* **补空格只发生在存储时，检索时另有一套规则**

    * `CHAR` 存的时候补齐尾部空格，查的时候自动去掉尾部空格，把原始数据还给你
    * `VARCHAR` 不做任何填充和压缩，存啥就是啥、取啥就是啥，自己加的空格读出来也带
    * 版本差异：MySQL 4.0 以下 `VARCHAR(20)` 的 20 是 20 个字节限制；4.x 版里 `utf8mb4` 指一个字符占 3 字节，20 字节只能放 6 个字符（$6 \times 3 = 18$，$7 \times 3 = 21$ 超了）
    * MySQL 5.0 以后 M 改成了字符限制，写 20 就是 20 个字符，占几个字节由编码格式自己运算

* **同一份数据、两种占法（`latin1` 单字节字符集）**

    | 插入的数据 | `CHAR(4)` 实际存储 | 占用字节 | `VARCHAR(4)` 实际存储 | 占用字节 |
    | :--- | :--- | :--- | :--- | :--- |
    | 空字符串 | 补 4 个空格 | 4 | 空 | $0 \times 1 + 1 = 1$ |
    | `AB` | `AB` + 2 个空格 | 4 | `AB` | $2 \times 1 + 1 = 3$ |
    | `ABCD` | `ABCD`，不补 | 4 | `ABCD` | $4 \times 1 + 1 = 5$ |

    * `CHAR(4)` 无论插空串、`AB` 还是 `ABCD` 始终都是 4 字节，补的空格也占位
    * 换成 `utf8mb4` 后：`CHAR(4)` 三种情况都是 $4 \times 4 = 16$ 字节；`VARCHAR(4)` 分别是 $0 \times 4 + 1 = 1$、$2 \times 4 + 1 = 9$、$4 \times 4 + 1 = 17$ 字节

## TEXT 大文本类型

* **大文本（TEXT）**

    * 声明时不需要指定长度，`TEXT` 类型单列最大只能放 65535
    * > **易错点**：⚠️ 这个 65535 是该类型单列自身的类型限制，跟当前行没关系；它最大的特点正是不占用一行 65535 的空间限制
    * 家族包含 `TINYTEXT`、`TEXT`、`MEDIUMTEXT`、`LONGTEXT` 四个，都可伸缩可变，和 `VARCHAR` 一样，放一小段就只占一个文本对应的字节
    * `LONGTEXT` 最大 4GB，绝对够存文本，用的时候只写列名加类型即可。

* **VARCHAR 的 M 能写多大**

    * 一行数据的空间上限是 65535 字节，减掉 1 字节的 `VARCHAR` 长度标识，内容可用 65534 字节
    * `utf8mb4` 一个字符占 4 字节，$65534 \div 4 = 16383.5$，带小数说明 16384 装不下，所以 M 最大是 16383
    * 一行有两个 `VARCHAR` 列时合起来也受 65535 限制，写 `VARCHAR(16000)` 加 `VARCHAR(384)` 会报 `Too large`
    * 把 M 调小或换成 `mb3`、`latin` 等小字符集是"看起来能行其实不合理"：M 是按业务需求设的，换字符集会乱码
    * MySQL 报错信息会提示 `You have to change some columns to TEXT or BLOBs.`，把其中一列改成 `TEXT` 就不占这一行的限制，创建即可通过

* **为什么不推荐 TEXT**

    * `TEXT` 性能不太好，大文本每次读写都消耗性能
    * 推荐做法：把大文本存成文件放到磁盘某个位置，库里只用 `CHAR`、`VARCHAR` 记录文件地址，程序读到地址后用 IO 流去读文件

## 时间类型

### 五种类型

* **时间类型**

    * 标准 SQL 提供了 5 种常用时间类型，区别只在格式、存储空间、值范围
    * > **结论**：设置好时间类型字段后，插数据就按字符串插入，加单引号并按它内部的时间格式写；把时间理解成一个特殊格式的字符串即可。

    | 类型 | 字节 | 格式 | 备注 |
    | :--- | :--- | :--- | :--- |
    | `YEAR` | 1 | 4 位的年或 2 位的年 | 两位年换算见下 |
    | `TIME` | 3 | 时分秒，冒号分隔 | 顾名思义就是时间 |
    | `DATE` | 3 | 年-月-日，中划线分隔 | 所谓日期 |
    | `DATETIME` | 8 | 年-月-日 时:分:秒 | `DATE` 加 `TIME` 的整合，值范围更大 |
    | `TIMESTAMP` | 4 | 同 `DATETIME` | 值范围 1970 ~ 2038 |

    * `TIMESTAMP` 是格林威治时间那一套，格式和 `DATETIME` 一样但只占 4 字节；在有效时间范围内想去表示时间，`TIMESTAMP` 更合适
    * `YEAR` 的两位年对应关系反直觉：`00` ~ `69` 代表 2000 ~ 2069 年，`70` ~ `99` 代表 1970 ~ 1999 年
    * 不推荐用两位格式，用两位还得自己在脑子里做一次转换，推荐四位，值范围更广、表达更清晰
    * > **提示**：`YEAR` 插入时既可以用字符串 `'09'` 也可以直接写数值 `09`，其他时间类型只能放字符串

### 自动维护时间的两个约束

* **两个时间戳约束**

    * `DEFAULT CURRENT_TIMESTAMP` —— 插入时赋予默认的 `CURRENT_TIMESTAMP`
    * `ON UPDATE CURRENT_TIMESTAMP` —— 更新时把它设置为该次更新的时间
    * 只想在更新时维护时间，就只写 `ON UPDATE CURRENT_TIMESTAMP`，不带 `DEFAULT CURRENT_TIMESTAMP`
    * 主动插入的时间优先于默认值

    ```sql
    CREATE TABLE t2 (
        name VARCHAR(20),
        regist_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '插入会自动维护时间',
        update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '插入维护时间，且修改数据也自动更新时间'
    );
    ```

* **版本差异**

    * > **易错点**：⚠️ 低版本 MySQL 中 `TIMESTAMP` 会自动维护时间（自动插入或自动更新），新版本没有这个自动维护功能，有的版本有、有的没有
    * 稳妥做法是按语法自己加 `DEFAULT CURRENT_TIMESTAMP`、`ON UPDATE CURRENT_TIMESTAMP` 约束
    * 建表前先分析每个字段的类型、相关约束和格式，再落到语句上

## 数据类型总账与选型原则

* **四个方向一张总账**

    | 方向 | 具体类型 |
    | :--- | :--- |
    | 整型 | `TINYINT`、`SMALLINT`、`INT`、`BIGINT` |
    | 浮点型 | `FLOAT`（单精度）、`DOUBLE`（双精度）、`DECIMAL`（精度更高） |
    | 字符串 | `VARCHAR`、`CHAR`、`TEXT` |
    | 日期时间 | `YEAR`、`TIME`、`DATE`、`DATETIME`、`TIMESTAMP` |

    * 此外还有很多其他特殊类型以及 JSON 类型
    * `CHAR`、`VARCHAR` 都有长度限制，受一行 65535 字节约束；想要更大的字符用 `TEXT`，它不算进一行的最大值限制，理论上可以超越 65535 字节，最大到 4GB

* **两条选型原则**

    * 第一原则是保证数据不要超越值范围、先不要报错，第二原则才是节约存储空间
    * 范围确定时选符合范围且占有空间最小的类型；年龄用 `TINYINT` 就够（$-128 \sim 127$），觉得不够可加无符号变成 $0 \sim 255$
    * 范围不确定时直接上最大的整型类型 `BIGINT`，因为编号会无限自增长，长到多大不确定，宁可多占空间也不能报错

* **学生表逐字段选型**

    * 建库切库：`CREATE DATABASE book_libs CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;` 然后 `USE book_libs;`

    | 字段 | 选型 | 为什么 |
    | :--- | :--- | :--- |
    | 学生姓名 | `VARCHAR(10)` | 有两字、三字、四字的，长度不确定，用可变字符串 |
    | 性别 | `CHAR` | 只有男和女两种，不指定长度默认就是一个字符 |
    | 年龄 | `TINYINT UNSIGNED` | 是整数且没有负值，加无符号把 $-128$ 转到正值方向变成 $0 \sim 255$ |
    | 身高 | `DOUBLE(4,1)` | 都在两米左右，记到小数点后一位；4、1 表示一共四位、其中一位是小数 |
    | 生日 | `DATE` | 一般只记哪年哪月哪日，不记时分秒 |
    | 注册日期 | `TIMESTAMP` + `DEFAULT CURRENT_TIMESTAMP` | 第一次插入那一刻就是注册日期，要自动维护 |
    | 更新日期 | `TIMESTAMP` + `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | 第一次插入算第一次更新，以后每次更新都要跟着改 |

    ```sql
    CREATE TABLE student (
        stu_name     VARCHAR(10) COMMENT '学生的姓名',
        stu_sex      CHAR        COMMENT '学生的性别，男和女',
        stu_age      TINYINT UNSIGNED COMMENT '年龄，0 到 255',
        stu_height   DOUBLE(4,1) COMMENT '身高',
        stu_birthday DATE        COMMENT '生日',
        stu_regist   TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '注册日期，插入的时候自动维护',
        stu_update   TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新日期，插入和更新自动维护时间'
    );
    ```

## 表的修改

* **统一的 ALTER TABLE 前缀**

    * > **提示**：修改表常用的关键字是 `ALTER`，所有语句的前置部分都是 `ALTER TABLE 表名`，真正区分动作的是后面那个动词
    * 修改表分两个方向：修改表中的列（添加、删除、改名、改类型），以及修改表名

* **列的操作**

    * `ALTER TABLE 表名 ADD 列名 类型 [FIRST | AFTER 已有列名];` —— 添加一列，末尾两个可选关键字决定加在某列之前还是之后
    * `ALTER TABLE 表名 DROP 列名;` —— 删除一列，`DROP` 后直接写列名
    * `ALTER TABLE 表名 CHANGE 原列名 新列名 新类型 [FIRST | AFTER 已有列名];` —— 改列名，顺带可以改类型，类型不变就把原类型写上
    * `ALTER TABLE 表名 MODIFY 列名 新类型 [FIRST | AFTER 已有列名];` —— 只改类型不改名字
    * `CHANGE` 像理了新发型染成红色，别人一看就发现，是外在的修改；`MODIFY` 像最近健身有八块腹肌但大冬天不能露，是内在的修改
    * `ADD` 不指定位置时，新列自动加在最后一个位置

* **改表名与查结构**

    * `ALTER TABLE 表名 RENAME TO 新表名;` —— 中间的 `TO` 可以省略，一般就写 `RENAME 新表名`
    * `DESC 表名;` —— 查看表中字段，字段展示的顺序就是当初创建时的顺序
    * `SHOW TABLES;` —— 查看当前库中有哪些表，用来确认改名结果

* **员工表从建表到改到位**

    ```sql
    CREATE TABLE emp (
        emp_id INT,
        last_name  VARCHAR(50),
        first_name VARCHAR(50),
        mobile     VARCHAR(25),
        `code`     INT,
        job_title  VARCHAR(50),
        birth_date DATE,
        note       VARCHAR(255),
        sex        CHAR(5)
    );
    ```

    * `code` 是保留关键字但可以使用，可视化工具会误识别成关键字，加一对反引号即可。
    * 国内手机号 11 位，`VARCHAR(25)` 有余量；`sex` 先按要求写 `CHAR(5)`，待会儿再改
    * 把 `mobile` 移到 `code` 之后，类型不变，只用位置关键字 `AFTER`：`ALTER TABLE emp MODIFY mobile VARCHAR(25) AFTER \`code\`;`
    * 把 `birth_date` 改名为 `birthday`，外在的改变用 `CHANGE`：`ALTER TABLE emp CHANGE birth_date birthday DATE;`
    * 把 `sex` 改成 `CHAR(1)`，内在的改变用 `MODIFY`：`ALTER TABLE emp MODIFY sex CHAR;`（`CHAR` 不写长度默认就是一个字符）
    * 删除 `note` 列：`ALTER TABLE emp DROP note;`
    * 新增一列：`ALTER TABLE emp ADD new_column VARCHAR(100);`
    * 改表名：`ALTER TABLE emp RENAME emp_info;`，然后 `SHOW TABLES;` 确认

## 表的删除与清空

* **两条都不能回滚**

    * > **注意**：删除表和清空表都无法回滚，一旦真清空了或表被删了，后期数据拿不回来、表也找不回，除非程序有对应的备份系统

* **`DROP TABLE`**

    ```sql
    DROP TABLE IF EXISTS 表名1, 表名2, 表名3;
    ```

    * 中间的 `IF EXISTS` 表示先判断表是否存在再删，不加也可以。
    * 表名用逗号隔开可以一次删除多个表
    * 它把表连同表结构全部删掉

* **`TRUNCATE TABLE`**

    ```sql
    TRUNCATE TABLE 表名;
    ```

    * 把表中的数据全部清空，表结构保留
    * 如果表中有自增主键，`TRUNCATE` 会把主键的最大值记录一起清掉，相当于清清白白地删除所有数据和关联数据
