# 多表关系与多表查询：连接、自连接与子查询

## 表关系的本质

### 多表关系是一堆两两关系

    * **表关系（table relationship）**
        * > **定义**：表关系指的是表中数据行之间的关系，是行跟行对应出来的关系。
        * 表自己不会有关系，关系是数据挤出来的。
        * 项目里哪怕有 100 张表，落到"分析表关系"这一步，永远是两两之间去分析。
        * A 与 B 之间是一种关系，A 与 C 之间可能就换了一种关系，所以不存在"100 张表搅在一块儿谈关系"这回事。

    * **三种具体关系**
        * 一对一：两个表之间每行数据至多对应对方一行，也可以不对应，例如员工与员工的唯一档案。
        * 一对多：A 表的一行关联 B 表的一行到至多多行，B 表每行至多对应 A 表一行，例如作者与文章。
        * 多对多：两张表的记录都可以对应对方的多条数据，例如学生与课程。

        ```text
        【一对一】  emp.eid  ⇄  profile.eid
                    （主表）    （子表：外键 + UNIQUE，同一个 emp.eid 最多命中一行档案）

        【一对多】  article.author_id  ──▶  author.id
                    （子表：外键，可重复）      （主表：同一个 author.id 可以命中多篇文章）

        【多对多】  sc.s_id  ──▶  student.s_id      关系是间接的，全靠中间表 sc
                    sc.c_id  ──▶  course.c_id         撑起来，sc 里的一行就等于
                                                          「某个学生选了某门课」这一件事
        ```

    * **双向视角**
        * 表关系一定要双向看：一对多拆开看是"一对多"，反着看就是"多对一"，合起来统一叫一对多。
        * 问"作者和文章是什么关系"之前得先把视角摆清楚——作者看文章是多，文章看作者是一。

    * **主外键（primary key / foreign key）**
        * 只要有表关系，就一定有主外键；一对一、一对多、多对多全都是主外键撑起来的。
        * 判断一段关系的唯一标准分两步：先看两张表之间有没有主外键，再看这个外键能不能重复。

### 拆表的动因是冷热数据分离

    * **数据冗余（redundancy）**
        * 冗余指一个学生对应多个分数，学生信息不得不在表里出现多次。
        * 一对一解决不了冗余：二狗子只有一个地址，这种"一对"写在同一张表里完全没问题，一点都不冗余。

    * **冷数据与热数据**
        * 冷数据是很少用的数据，热数据是经常要查询的数据。
        * 不拆表时每次查询都会把这些列全查出来，或者都在这些列的基础上做查询，带着不要的列会降低查询效率。
        * 一对一的真正意义是把冷热数据分别存储到两张表，或者三张、四张表都行；查热数据只查小表，查询频次高效率就高，两个都想查就把两张表关联起来。
        * QQ、微信的"基本信息"与"详细信息"分开存储，关系正是一对一。

## 三种关系的建表语法

### 一对一：外键唯一

    * **外键唯一**
        * 一对一的最终特点是一条员工至多对应一条档案数据，一条档案也至多对应一条员工数据。
        * 只要子表的外键出现一次、至多出现一次，就是一对一。

    * **两种约束方案**
        * 方案一：档案表保留自己的主键，外键列上加 `UNIQUE` 唯一约束。
        * 方案二：档案表干脆不要自己的主键，让 `eid` 既是外键又是主键；加了主键约束的值非空且唯一，一样是一对一。
        * `CONSTRAINT` 关键字可以省略。

        ```sql
        -- 主表：员工表。姓名、年龄、性别放这里
        CREATE TABLE emp (
          eid    INT PRIMARY KEY,
          name   VARCHAR(20),
          age    INT,
          gender CHAR(1)
        );

        -- 方案一：档案表有自己的主键，外键列加 UNIQUE
        CREATE TABLE profile1 (
          id      INT PRIMARY KEY AUTO_INCREMENT,
          eid     INT UNIQUE,                              -- 外键 + 唯一 → 至多一条
          address VARCHAR(50),
          level   VARCHAR(20),
          CONSTRAINT fk_profile1_eid FOREIGN KEY (eid) REFERENCES emp(eid)
        );

        -- 方案二：eid 既是外键又是主键，不用 AUTO_INCREMENT
        CREATE TABLE profile2 (
          eid     INT PRIMARY KEY,                         -- 同时是外键
          address VARCHAR(50),
          level   VARCHAR(20),
          CONSTRAINT fk_profile2_eid FOREIGN KEY (eid) REFERENCES emp(eid)
        );
        ```

        * > **易错点**：方案二里千万别再顺手写 `AUTO_INCREMENT`。那个值是引用对方主键来的，不是自己长出来的；方案一里的 `id` 才是自增的。

    * **关系的可视化验证**
        * Navicat 社区版免费；升级到企业版可以把两个表拖进去，它会直接告诉你这是一对一还是一对多、关系建没建成功。
        * 不升级的话，插两条相同外键的数据互相引用，插入被拦下就说明唯一约束生效。

### 一对多：外键可重复

    * **外键可重复**
        * 一对一与一对多的唯一区别就卡在外键上：一对一外键必须唯一，一对多外键可以出现多次。
        * 一对多的表里一定会有一个单独的主键，外键正常加一个外键约束、不加任何限制，一对多就成立。

        ```sql
        -- 主表：作者
        CREATE TABLE author (
          id     INT PRIMARY KEY AUTO_INCREMENT,
          name   VARCHAR(20),
          age    INT,
          gender CHAR(1)
        );

        -- 子表：文章。文章自己也有主键，这一条一定要记住
        CREATE TABLE article (
          id        INT PRIMARY KEY AUTO_INCREMENT,        -- 文章自己的主键
          title     VARCHAR(50),
          author_id INT,                                  -- 外键，刻意不加 UNIQUE
          CONSTRAINT fk_article_author FOREIGN KEY (author_id) REFERENCES author(id)
        );
        ```

    * **一对多解决冗余**
        * 文章表里那个外键把同一个作者主键引用了多遍，作者在表里出现多次是正常的。
        * 一对多存在的意义就是拆表存在的意义：解决数据冗余，以及提高数据操作效率。
        * 只要发现一个实体有对应多个子元素，那就得完成表的拆分。

### 多对多：中间表间接引用

    * **外键无处安放**
        * 在课程表里加 `s_id` 只能引用一个学生，加在学生表上的 `c_id` 也只能引用一门课，所以外键加在哪一边都不行。
        * 分析出两个实体是多对多时，必须额外建一张中间表，没有第二种走法。

    * **中间表建法**
        * 中间表里可以包含两个外键：一个跟学生表，一个跟课程表，数据靠这种间接引用连起来。
        * 两个主表必须先创建好，否则中间表的外键会报错。

        ```sql
        CREATE TABLE student (
          s_id INT PRIMARY KEY,
          name VARCHAR(20)
        );

        CREATE TABLE course (
          c_id INT PRIMARY KEY,
          name VARCHAR(20)
        );

        -- 中间表：两个外键，谁都不许加 UNIQUE
        CREATE TABLE sc (
          s_id INT,
          c_id INT,
          CONSTRAINT fk_sc_student FOREIGN KEY (s_id) REFERENCES student(s_id),
          CONSTRAINT fk_sc_course  FOREIGN KEY (c_id)  REFERENCES course(c_id)
        );

        INSERT INTO student VALUES (1,'二狗子'), (2,'驴蛋蛋');
        INSERT INTO course  VALUES (1,'Java-常老师'), (2,'H5-马老师');
        INSERT INTO sc VALUES (1,1), (1,2), (2,1), (2,2);
        ```

        * `sc` 里的一行就等于"某个学生选了某门课"这一件事，四行合起来的意思是这两位学生都上过两位老师的课。
        * 多对多在查询时天然就是三张表的查询：学生先关联中间表，再通过中间表关联课程表。

        * > **易错点**：中间表的外键列上绝对不能加唯一约束。加了唯一就退化成"一个学生只能选一门课"，既不是多对多也不是一对一，是把多对多硬生生压扁了。

    * **三步口诀**
        * 第一，把两个主表先创建好。
        * 第二，创建中间表，中间表至少包含两个主表的外键。
        * 第三，中间表的外键上不添加唯一性约束。

### 三种关系的分野

    * **约束对照**

        | 关系 | 外键能否重复 | 维护手段 | 是否解决冗余 |
        | :--- | :---: | :--- | :---: |
        | 一对一 | 不能 | 外键加 `UNIQUE`，或直接让外键兼任主键 | 否，为冷热数据分离 |
        | 一对多 | 能 | 外键不加唯一约束，子表另设主键 | 是 |
        | 多对多 | 两个外键都不能 | 必须建中间表间接撑起关系 | 是 |

    * **判定口诀**
        * 一对一 = 外键唯一；一对多 = 外键可重复、子表另设主键；多对多 = 外键无处安放、必须由中间表间接撑起来。
        * 把外键的约束情况看一眼，答案就出来了。

## 垂直合并：UNION 与 UNION ALL

### 两个关键字的去重差异

    * **UNION**
        * > **定义**：把多个结果集上下摞在一起形成一个结果集的垂直合并关键字，会去掉重复行。

    * **UNION ALL**
        * 不会去掉重复行，不管重不重复都原样合并。

    * **示例与行数**
        * A 表是 `1/AA、2/BB、3/CC`，B 表是 `4/AA、2/BB、3/CC`；`2/BB` 和 `3/CC` 两行在两个结果集里一模一样。

        | 关键字 | 重复行怎么处理 | 3 行 + 3 行的结果 |
        | :--- | :--- | :---: |
        | `UNION` | 相同行只保留一份 | 4 行 |
        | `UNION ALL` | 相同行原样保留 | 6 行 |

        ```sql
        SELECT a_id, a_name FROM a
        UNION
        SELECT b_id, b_name FROM b;
        ```

        ```text
        ┌──────┬────────┐
        │ 来源 │ a_name │      上面 3 行来自 A 表，下面 3 行来自 B 表
        ├──────┼────────┤      列名以在上的结果集（A）为准
        │ A    │ AA     │
        │ A    │ BB     │      UNION      → BB、CC 跟下面重复，去掉 → 4 行
        │ A    │ CC     │      UNION ALL  → 原样全摞上          → 6 行
        ├──────┼────────┤
        │ B    │ AA     │
        │ B    │ BB     │
        │ B    │ CC     │
        └──────┴────────┘
        ```

        * 谁在上、谁在下都无所谓，在上的那个结果集最后会成为虚拟表的列名。
        * 连着写三遍查询、中间都用 `UNION ALL`，$3 \times 3 = 9$ 条。

### 合并的三条硬要求

    * **列数和类型一一对应**
        * 上面是三列下面三列，上面第一个是字符串下面也得是字符串，不然它怎么对到一起。

    * **不要求主外键关系**
        * 垂直合并不涉及行与行之间的关联，什么驴唇不对马嘴都能合到一块儿去，只要列数和类型对应上就行。

    * **重复数据的认定标准**
        * 认定是一行中的所有列值都重复才算重复行；上面三列、下面三列，其中只有两列重复的不算。

### 适用场景

    * **合并多个相似的表**
        * 电子商务网站里电子产品、服饰、家居各存各的表，最终首页展示时分别查一个结果再合并成一个结果集。

    * **统计不同数据源的数据**
        * 用户数据可能来自注册页面也可能来自访问日志，最后合并展示同样用 `UNION`、`UNION ALL`。

    * **与连接查询的分野**
        * 垂直合并不要求两表之间有关系；水平合并要求两表必须有关系、必须有主外键。
        * 开发中只要是关联展示不同表的数据，绝大部分情况下都是水平合并，连接查询是必须掌握的。

## 水平合并：连接查询的门槛

### 笛卡尔积是连接查询的底层原理

    * **连接查询的硬要求**
        * 水平合并要求两个表必须存在关系、必须得有主外键，因为两边各有一条数据是靠主外键的值进行引用才连成一行的。
        * 连接查询的本质是抓"两个表的主外键相等"这个条件。

    * **笛卡尔积（Cartesian product）**
        * > **定义**：不加主外键相等条件时，数据库把两个表的所有数据行互相拼接一遍的合并方式。
        * 它只保证"里面一定有正确数据"，但一定也混着错误数据。
        * 行数 = 左表行数 × 右表行数。员工表 27 条、部门表 6 条，连接后是 $6 \times 27 = 162$ 条。
        * 最后正是靠"主外键相等"这个条件才能从笛卡尔积里恢复出正确的数据。

    * **连接查询是拆表逼出来的**
        * 关系型数据库分表存储，但展示时经常要联合展示，员工名字要、员工部门名称也要。
        * 内连接、外连接、自然连接三大类，本质差距并不特别大，掌握内连接和外连接的区别就行。

### 标准语法与非标准语法

    * **标准语法**

        ```sql
        SELECT 列
        FROM 表1 AS 别名
        INNER JOIN 表2 AS 别名
          ON 表1别名.主键 = 表2别名.外键;
        ```

        * `INNER` 可以省略，但写的时候不要加方括号，课件上的方括号只是"可以不写"的意思。
        * 光有 `JOIN` 不够，它只是把所有行拼接一次；`ON` 后面跟的正是"两个表中主外键相等"这一句。
        * `ON` 只能跟在 `JOIN` 这种关键字后面，它后面一般就是主外键相等。

    * **非标准语法**

        ```sql
        SELECT 列
        FROM 表1 别名, 表2 别名
        WHERE 表1别名.主键 = 表2别名.外键;
        ```

        * 这是 MySQL 的方言，在其他数据库里不支持；非标准语法写起来更顺手，标准语法更通用。
        * 用法是第一个表起、第二个表起，用逗号隔开再加一个表，第三张、第四张表继续逗号隔开。

    * **两种语法对照**

        | 项目 | 标准语法 | 非标准语法 |
        | :--- | :--- | :--- |
        | 表怎么拼 | `表1 别名 inner join 表2 别名` | `from 表1 别名, 表2 别名` |
        | 主外键相等写在哪 | `on e.did = d.did` | `where e.did = d.did` |
        | 额外条件写在哪 | `where` 后面 | 继续用 `and` 接在 `where` 后面 |
        | 底层原理 | 全连接一遍 | 全连接一遍 |

    * **写法取向**
        * 两种语法在 MySQL 里效果完全一致，非标准语法可以拿来理解原理，真正写代码推荐用标准的那一套，毕竟它在哪都支持。

### 列名限定与表别名

    * **同名列问题**
        * 多表查询时 `SELECT` 位置和指定条件的位置都不能随便写列名，列名重名时 MySQL 会报"不知道这个 `name` 到底是谁的"。
        * 解决办法是对列的操作都写 `表名.列名`；直接写列名的前提是保证它不是重复列名。

    * **表别名**
        * 表名一般很长，每次写很麻烦，所以多表操作时一般都会给表起别名，用短别名带出列名。
        * 语法有两种：`FROM employee e` 和 `FROM employee AS e`。
        * 起完别名之后，列就写成 `别名.列名`。

### 多表连接的规律

    * **多表查询是伪命题**
        * 所谓的多表查询本质上就是多个两表查询：三张表就是两个两表查询。
        * 每次写连接查询只需要关注当下的表关系：关联下一张表是谁、下一张表关联的又是谁，无限往后写。

    * **条件条数**
        * 有 $N$ 张表，至少有 $N-1$ 对主外键相等条件；100 张表是 99 对，1 万张表是 9999 对。
        * 岗位跟部门没有直接关系，岗位也是跟员工关联的，所以三表查询要查员工和部门、员工和岗位两组关系。

        ```text
        -- 标准语法
        表1 join 表2 on 主外键1 join 表3 on 主外键2 ... where 其他条件

        -- 非标准语法
        from 表1, 表2, 表3 ... where 主外键1 and 主外键2 ... and 其他条件
        ```

    * **关键字顺序**
        * 多表查询只是把内连接和外连接的语法加进 `SELECT ... FROM` 中间一段，后面的关键字顺序不变。
        * 拼接完以后分组、分页这些高级查询照干不误。

        ```text
        SELECT  列1, 列2, ...
        FROM    表1 别名
                [INNER|LEFT|RIGHT JOIN 表N 别名 ON 主外键相等] ...
        WHERE   其他条件
        GROUP BY ...
        HAVING  ...
        ORDER BY ...
        LIMIT   ...
        ```

### 实战用的三张表

    * **表关系**
        * 部门表 6 条，岗位表 12 条，员工表 27 条；三个数字用来算笛卡尔积。
        * 员工表里存在两个外键，分别引用岗位和部门相关的信息，所以员工表是子表，部门表和岗位表是主表。

        ```text
                t_department                t_job
                部门表 6条                  岗位表 12条
                did  ← 主键                jid  ← 主键
                dname                     jname
                描述                       描述
                ▲                          ▲
                │                          │
           t_emp.did(外键)           t_emp.job_id(外键)
                │                          │
                └──────────┬─────────────┘
                           ▼
                      t_emp  员工表(子表, 27条)
                      eid / ename / did / job_id
        ```

        ```sql
        CREATE TABLE t_department (
            did     INT PRIMARY KEY,
            dname   VARCHAR(20),
            descr   VARCHAR(100)
        );

        CREATE TABLE t_job (
            jid     INT PRIMARY KEY,
            jname   VARCHAR(20),
            descr   VARCHAR(100)
        );

        CREATE TABLE t_emp (
            eid     INT PRIMARY KEY,
            ename   VARCHAR(20),
            job_id  INT,
            did     INT,
            FOREIGN KEY (job_id) REFERENCES t_job(jid),
            FOREIGN KEY (did)    REFERENCES t_department(did)
        );
        ```

## 内连接

### INNER JOIN 配 ON

    * **内连接（inner join）**
        * > **定义**：一种将多个表水平连接到一起的语法，要求两个被合并的表之间必须存在主外键相等的条件才能进行合并。
        * 把学生和对应的分数正确地水平拼接到一个结果集，就是内连接的典型效果。
        * 内连接查询到的结果要求两个表中必须存在相同的主外键，对方的引用为空就拿不到。

    * **标准写法**

        ```sql
        select e.eid, e.ename, e.did, d.dname
        from t_emp e
        inner join t_department d
        on e.did = d.did;
        ```

        * `on` 就是连接查询放主外键相等的关键字，用来筛选笛卡尔积。
        * `on` 后面能加其他条件，当前阶段只要记住加主外键就行。

    * **非标准写法**

        ```sql
        select e.eid, e.ename, e.did, d.dname
        from t_emp e, t_department d
        where e.did = d.did;
        ```

### 附加条件与关键字省略

    * **INNER 可省**
        * 标准语法中的 `inner` 可以省略，`inner join` 等同于 `join`，它们都属于内连接。

        ```sql
        select e.eid, e.ename, e.did, d.dname
        from t_emp e
        join t_department d
        on e.did = d.did
        where e.eid > 10;
        ```

    * **额外条件照常加**
        * 非标准语法里主外键相等和筛选条件之间是 `and` 的关系。

        ```sql
        select e.eid, e.ename, e.did, d.dname
        from t_emp e, t_department d
        where e.did = d.did
          and e.eid > 10;
        ```

    * **三表内连接**

        ```sql
        select e.eid, e.ename, e.did, d.dname, e.job_id, j.jname
        from t_emp e
        inner join t_department d
        on e.did = d.did
        inner join t_job j
        on e.job_id = j.jid
        where e.eid > 10;
        ```

        * 四张表就继续 `inner join`，五张表也是继续 `inner join`。

### 内连接查不到无引用方

    * **匹配不到就消失**
        * > **结论**：内连接查询的结果要求两个表中必须都存在主外键匹配才能查到。
        * 27 个员工里 27 号周芷若的 `did` 为空，代表她没有部门，用内连接查从 1 号查到李红就没有她了。

## 外连接

### 逻辑主表

    * **外连接（outer join）**
        * > **定义**：会返回所有符合的行——既返回两个表中主外键相等的行，也返回未匹配的行。
        * 未匹配指可以指定一个表为逻辑主表，那就算这个表没有被引用或者没有外键，它也会全部返回。
        * 逻辑主表那一侧的行照样查出来，另一侧置空；置空的位置可以用 `IFNULL` 兜一个值，比如"未分配"。

    * **LEFT 与 RIGHT 指定逻辑主表**
        * 左和右指的就是指定左侧和右侧哪个表为逻辑主表。
        * 逻辑主表放第一位用左外连接，以它为主；逻辑主表放后面、想查到它就得写成 `RIGHT`。
        * `LEFT` 和 `RIGHT` 就是用来指定哪个是逻辑主表的。
        * 想查周芷若、部门表放前面时左外连接查不到，只能写右外连接。

    * **关键字省略**
        * 外连接的 `OUTER` 可以省略，`LEFT OUTER JOIN`、`LEFT JOIN`、`RIGHT OUTER JOIN`、`RIGHT JOIN` 效果一致。
        * 只写一个 `JOIN` 就是内连接，加上 `LEFT` 和 `RIGHT` 就是外连接。

### 语法与必须加 ON

    * **外连接语法**

        ```text
        表1 别名 LEFT|RIGHT OUTER JOIN 表2 别名 ON 主外键相等
        ```

    * **ON 是强制项**
        * 外连接不写 `ON` 会直接语法报错。

        ```sql
        SELECT *
        FROM t_emp e
        LEFT JOIN t_department d
        ON e.did = d.did
        WHERE e.eid > 10;
        ```

        * > **易错点**：外连接必须添加主外键相等条件，不加直接报错误代码 1064，代表语法有问题；内连接是建议加，不加就出笛卡尔积。

    * **内外连接对比**

        | 项目 | 内连接 | 外连接 |
        | :--- | :--- | :--- |
        | 关键字 | `JOIN` / `INNER JOIN` | `LEFT JOIN` / `RIGHT JOIN`（`OUTER` 可省） |
        | 判定规则 | 公平的：两边主外键都得有且相等 | 不公平的：可指定一张逻辑主表，它的数据一定全返回 |
        | 对方没有外键的行 | 查不到 | 逻辑主表那侧的行照样查出来，另一侧置空 |
        | 能省的写法 | `INNER` 可省 | `OUTER` 可省 |
        | 加不加分隔条件 | 建议加，不加就出笛卡尔积 | 必须加，不加直接语法报错 |

### 连接的连续性

    * **主表放第一位**
        * 一旦选定逻辑主表就把它放在第一位，第一个连接用左外连接，后续全都是左外连接。
        * 中途改成右外连接或内连接，相当于第一个左外连接就没意义了。
        * 剩下的一张表关联第三张时本来也可能是空关联，用内连接会让表 1 的数据又查不到。

    * **三表外连接写法**

        ```sql
        SELECT e.eid, e.ename, e.did, d.dname, e.job_id, j.jname
        FROM t_emp e
        LEFT JOIN t_department d
        ON e.did = d.did
        LEFT JOIN t_job j
        ON e.job_id = j.jid
        WHERE e.eid > 10;
        ```

        * 有外连接以后正常写 `ON` 主外键相等，其他条件加在 `WHERE` 后面。
        * 表一定要起别名，否则 `j.jname` 这种写法根本无从下手。

    * **结论落点**
        * 只要第一个是逻辑主表，剩下的就都是左连接，闭眼写即可。

### 该用内连接还是外连接

    * **需求：展示有员工和员工的岗位信息**
        * 有些员工是新入职还没分配岗位，用内连接的话该用户在结果中查不到。
        * 用外连接并以员工表为逻辑主表，没有岗位的员工也会查出来，只是岗位位置为空，可以用 `IFNULL` 约定成"未分配岗位"。

    * **需求：展示费用名和费用值的整合信息**
        * 取暖费有费用项但没有值，内连接会要求两张表主外键匹配上，最终取暖费查不出来。
        * 这就形成一个死循环：要加取暖费得有值才能查出来，而不显示出来又没法加。
        * 所以以费用项为逻辑主表做外连接，费用项没有值时也照样显示，后续有加号可以动态加值。

    * **出现率判断**
        * 开发中有很多表都是逻辑主表，即使没有被引用数据也应该展示，所以外连接的登场率比内连接更高。
        * 学生与分数表同理：没来考试的学生用内连接就不会上榜，用外连接查出来分数为空，`IFNULL` 等于 0 即可。

## 自然连接

### 自动匹配同名列

    * **自然连接（natural join）**
        * > **定义**：自动找到两个表中命名相同的列并自动判定相等，从而达到内外连接的效果并省略 `ON` 后面的主外键相等公式。
        * `NATURAL JOIN` 代表自然内连接；`NATURAL` 后边加 `LEFT` 或 `RIGHT` 代表自然外连接。
        * 要求两个表的主外键命名相同才能用。

    * **自然外连接**
        * 想查周芷若就加上 `LEFT`，以员工为逻辑主表进行查询。

        ```sql
        SELECT e.eid, e.ename, e.did, d.dname
        FROM t_emp e
        NATURAL JOIN t_department d;
        ```

    * **不太稳妥**
        * 自然连接效果就是内外连接的同样效果，只是语法简化；但如果两表中除主外键外还有同名列，它也会自动判定相等，数据就会出错。

### USING 优化

    * **USING 指定列名**
        * 自然连接后面还可以加 `USING`，指定主外键列名，且主外键列名得相同，这样就只判定指定的列，其他相同列不判定。
        * 但这么做比直接写 `JOIN` 后面跟 `ON` 更麻烦、更不直观，了解即可，它并不是什么特殊功能，只是一个语法。

### 命名不同时失效

    * **列名对不上就退化成笛卡尔积**
        * 员工表的外键叫 `job_id`，岗位表的主键叫 `jid`，命名不同，`NATURAL JOIN` 找不到。

        ```sql
        SELECT e.eid, e.ename, e.job_id, j.jname
        FROM t_emp e
        NATURAL JOIN t_job j;
        ```

        * 结果行数一下子涨了很多，就是两张表的行数直接相乘。

        * > **易错点**：就算加 `USING` 也不行，命名不同用它也白搭；用自然连接的前提是主外键命名必须相同，而且其他列要不同，其他列相同可以用 `USING` 指定。

## 自连接

### 一个表用多次

    * **自连接（self join）**
        * > **定义**：一个表与自身进行数据连接的操作，在查询里给同一个表起不同的别名，表示它的两个不同实例，再把这两个实例连接起来。
        * 自连接不是语法，只是一种特殊的使用场景；它说的还是内连接、外连接、自然连接这几句话。
        * 适用条件只有一句：你要查的那个关联数据，躺在同一张表的其他行里。
        * 实现手段有两条：照样用内/外/自然连接，并且照例给别名。
        * 自连接不等于自然连接，一个是场景，一个是语法。

    * **表里的引用关系**
        * 员工表里有员工编号，也有经理编号 `mid`，`mid` 指向的同样是这张员工表里的某个行——领导也是员工，只不过是另一行。
        * 孙洪亮的领导编号是 1，而 1 就是孙洪亮自己；何金的领导是 1，即孙洪亮；邓超远的领导是 7 即贾宝玉，贾宝玉的领导又是 1 即孙洪亮。
        * 明明只有一行数据，行与行之间却互相引用起来了，这就是自连接场景。

    * **为什么一行不够用**
        * 查员工的编号、姓名、领导编号是一次普通的单表查询，这三样东西这一行里全都有。
        * 再加领导的姓名就麻烦在：这一行里只有领导的编号，没有领导的姓名，只能拿编号当条件回到员工表再关联一次。
        * 判断标准：只要发现你要关联的数据在同一个表里的其他行，用的就是自连接。

### 语法与等号方向

    * **同一个表两个名字**
        * 第一份当员工表，第二份当领导的表；员工那一份叫 `e1`，领导那一份叫 `e2`。

        ```text
           e1  员工表                    e2  员工表（复用一份，当领导的表用）
           eid  ename  mid              eid  ename
            1   孙洪亮   1               1   孙洪亮
            5   陈浩     7  ───────────> 7   贾宝玉
                              ▲
                e1.mid  =  e2.eid
        ```

        ```sql
        select e1.eid, e1.ename, e1.mid, e2.ename
        from t_emp e1
        left join t_emp e2
        on e1.mid = e2.eid
        where e1.eid = 5;
        ```

    * **用左外连接的原因**
        * 即使我没领导也照样把我查出来，表 2 那边匹配不上，`e2` 的列全是 `NULL`，行还是自己的行。

    * **等号方向**
        * 抓住之后表 2 的 `ename` 就不一样了，它是领导的姓名。
        * 自连接说到底就是抓住主外键哪个相等就行。

        * > **易错点**：等号的方向千万不能反，必须写 `e1.mid = e2.eid`。写成 `e1.eid = e2.mid` 就变成"我的经理等于他的经理"了。正确的说法是我的经理编号等于对面那个人的员工编号。

### 复用多次

    * **查领导的领导**
        * 同一个表能用两次就能用三次、用 $n$ 次，连接思路完全一样，只是链路多接一节。

        ```text
           e1 员工表                   e2 领导表                    e3 领导的领导表
           eid  ename  mid             eid  ename  mid              eid  ename
            5   陈浩     7   ─────────> 7   贾宝玉    1  ─────────> 1   孙洪亮
                              ▲                      ▲
                e1.mid  =  e2.eid          e2.mid  =  e3.eid
        ```

        ```sql
        select e1.eid, e1.ename, e1.mid,
               e2.ename, e2.mid,
               e3.ename
        from t_emp e1
        left join t_emp e2
        on e1.mid = e2.eid
        left join t_emp e3
        on e2.mid = e3.eid
        where e1.eid = 5;
        ```

    * **自连接的固定套路**
        * 要查的列顺着链路加：`e1.eid`、`e1.ename`、`e1.mid`，然后 `e2.ename`、`e2.mid`，最后 `e3.ename`。
        * 再往上找一层就复用四次，套路一模一样，是固定化的公式。

    * **同型练习题**
        * 查收入超过其经理的员工：员工表有 `id`、`name`、`salary` 和 `managerId`，Sam 和 Max 没有领导编号说明他们就是领导。
        * 解法是典型自连接，连接键依旧是"我的 `managerId` 等于对面的 `id`"，连成一行后在里面比较两个 `salary`。

## 子查询

### 定义与四类

    * **子查询（subquery，也叫嵌套查询）**
        * > **定义**：在一个 SQL 语句中，嵌套了另外一个完整的 select 语句。
        * 子查询不只出现在 `SELECT` 里，`INSERT`、`UPDATE`、`DELETE` 语句中都可以嵌套。
        * 典型思路是两步：先用一条 select 加聚合函数算出结果，再把算出来的东西加个括号当成条件值。

    * **四类划分**

        | 类别 | 返回结果形状 | 典型用途 | 配套关键字 |
        | :--- | :--- | :--- | :--- |
        | 标量子查询 | 单行单列 | 做判定条件、过滤，或作为表达式里的一个值 | 无，直接当值用 |
        | 行子查询 | 一行多列 | 更新、插入数据的值，或整体比较 | `=` 或 `IN`（多列要加括号整体比） |
        | 列子查询 | 多行单列 | 条件比较 | `IN` / `NOT IN` / `ANY` / `ALL` |
        | 表子查询 | 多行多列 | 一般不做条件，用作连接的虚表 | 正常外连接，记得起别名 |

    * **一句话各归其位**
        * 标量子查询是一个值，用起来像常量；行子查询是一行几个值，只能整体比。
        * 列子查询是一列好几个值，得靠 `IN`、`ANY`、`ALL` 判；表子查询是好几行好几列，没法比大小，只能当表用。

### 标量子查询

    * **单值当普通值用**
        * > **定义**：子查询的结果是单行单列，也就是一个单独的值。
        * 这个值有三个去处：作为判定条件、作为过滤条件、作为 select 列表里的一部分。
        * 当它是个条件值的时候，一般一次只加一个额外的条件。

    * **条件位置：查研发部门的所有员工**
        * 员工表里只有部门 `did` 没有部门名称，条件拿不到，所以用两步子查询：先由部门名称查 `did`，再用这个 `did` 查员工。

        ```sql
        SELECT *
        FROM t_emp
        WHERE did = (
            SELECT did
            FROM t_department
            WHERE dname = '研发部'
        );
        ```

        * 括号就代表内部要先执行一个查询，把第一步整条粘进来，注意别把分号也粘上。

    * **表达式位置：部门平均工资减去公司平均工资**
        * 题目里出现"每个"两个字就是典型的分组查询；只要你分组，`SELECT` 位置就只允许查分组字段和聚合函数，别的不许写。

        ```sql
        SELECT did,
               AVG(salary),
               AVG(salary) - (SELECT AVG(salary) FROM t_emp) AS diff
        FROM t_emp
        GROUP BY did;
        ```

        * 因为是单行单列，所以可以直接当一个普通值扔到减法算式的右边，大于、小于、等于随便比，等号赋值、减法加法都行。

### 行子查询

    * **一行多列得整体比**
        * > **定义**：子查询返回一行，但返回了多个列。
        * 查和白鹭性别和部门相同的员工信息，子查询返回的正是白鹭的 `gender` 和 `did`。
        * 做法是把多个列用括号括起来，当成一个整体去比，这个位置一定要一一对应上。

        ```sql
        SELECT *
        FROM t_emp
        WHERE (gender, did) = (
            SELECT gender, did
            FROM t_emp
            WHERE ename = '白鹭'
        );
        ```

        * 除了等号，用 `IN` 也可以，`IN` 同样能承担多列之间的整体等于判定。
        * 想排除掉白鹭本人，再补一个 `AND` 就行。

    * **转换成若干个标量子查询**
        * 记不住整体比较就拆开：先查白鹭的性别，再查白鹭的部门，这变成了两个标量子查询。

        ```sql
        SELECT *
        FROM t_emp
        WHERE gender = (SELECT gender FROM t_emp WHERE ename = '白鹭')
          AND did   = (SELECT did   FROM t_emp WHERE ename = '白鹭');
        ```

    * **不必死记分类**
        * 查询里嵌查询、更新里嵌查询、删除里嵌查询，都能查得出来，语法灵活掌握了就行。

### 列子查询

    * **多行单列靠关键字判**
        * > **定义**：子查询返回多行单列，可以通俗理解成查出来的结果是多个值。
        * 返回多个值时，比较必须加 `IN`、`NOT IN`，或者 `ANY`、`ALL`。
        * `IN` 表示"在其中"，等价于"是他或者是他"；`NOT IN` 表示"不在其中"。

    * **与白鹭、谢吉娜同部门**

        ```sql
        SELECT *
        FROM t_emp
        WHERE did IN (
            SELECT did
            FROM t_emp
            WHERE ename IN ('谢吉娜', '白鹭')
        );
        ```

        * 这两人可能在一个部门（退化成标量子查询）也可能在两个（是列子查询），查出来是 2 和 5。
        * 两个值是一起给你的，不能拆开查；换 `NOT IN` 就查不同部门的。

        * > **易错点**：多值场景下用等号会直接报错，因为等号只能等于单值。解法是在等号后边、子查询括号的前面加上 `ANY` 或 `ALL`。

    * **ANY 与 ALL 的差别**
        * `ANY` 代表任意一个值，作用等于 `IN`，满足其中任意一个都行，等价于比他们里的最小值大。
        * `ALL` 代表所有值，判定的是"且"的关系。

        ```sql
        SELECT *
        FROM t_emp
        WHERE salary > ALL (
            SELECT salary
            FROM t_emp
            WHERE ename IN ('白鹭', '李思羽', '黄冰茹')
        );
        ```

        * 题目要的是三个人都比，所以必须写 `ALL`；`IN` 和 `NOT IN` 管的是"等于"的场景，要比大小就得用 `ANY` 或 `ALL`。

    * **用聚合函数收成单值**
        * `MAX` 返回的是单行单列，是标量子查询，可以当普通值直接放进去，不用加 `ANY` 和 `ALL`。

        ```sql
        SELECT * FROM t_emp WHERE salary > (
            SELECT MAX(salary) FROM t_emp WHERE ename IN ('白鹭', '李思羽', '黄冰茹')
        );
        ```

    * **归口结论**
        * 列子查询拿来做等于用 `IN` / `NOT IN`，拿来做大于小于加 `ANY`（任意一个）或 `ALL`（所有）。
        * 这四种关键字本质上都可以用聚合函数收成单值，绕开多值。

### 表子查询

    * **多行多列当虚表连**
        * > **定义**：子查询返回多行多列，这种结果既做不了条件也做不了值，一般作为一个虚拟的中间表来用。
        * 查所有部门的编号、名称以及部门的平均工资：部门表里没有平均工资，平均工资是员工表分组查询算出来的。
        * 所以不是简单的"部门表连接员工表"，而是员工表先分组查出结果，查出来以后再跟部门表连接。

        ```sql
        SELECT d.did, d.dname, tmp.avs
        FROM t_department d
        LEFT JOIN (
            SELECT did, AVG(salary) avs
            FROM t_emp
            GROUP BY did
        ) tmp
        ON d.did = tmp.did;
        ```

    * **三个注意点**
        * 用 `LEFT JOIN` 左外连接，部门表是逻辑主表，就算这个部门一个员工都没有它也照样出来，平均工资算作 0。
        * 括号里查出来的这个结果集一定要起别名，否则后期没法取列，得写成 `tmp.avs`。
        * 有外连接以后正常写 `ON` 主外键相等，别名已起好就直接取 `avs`，不用再算。

    * **何时会遇到**
        * 当你发现你要查的数据还得再经过一次查询才能拿到时，就先查出一个虚表；表里直接有的数据肯定直接关联原表。

## 嵌套子查询在修改、删除与插入语句中的写法

### UPDATE 跨表改

    * **案例：把测试部门所有人的薪资改为原来的 1.5 倍**
        * 改的是员工表，要先由部门名称查出部门 `did` 再去改，所以子查询写在 `WHERE` 右边。

        ```sql
        UPDATE t_employee
        SET    salary = salary * 1.5
        WHERE  did = (
            SELECT did
            FROM   t_department
            WHERE  d_name = '测试部'
        );
        ```

        * `salary = salary * 1.5` 里右边的 `salary` 代表取到原有的值再乘 1.5。
        * 执行完影响行数是 0：测试部的 `did` 确实是 6，可员工表里压根就没有 `did` 为 6 的人；换成研发部再执行才改中四五条。

    * **案例：把没有部门的员工改为测试部**
        * 单行单列的标量子查询可以出现在任何需要"值"的位置上，写在 `SET` 右边同样可以。

        ```sql
        UPDATE t_employee
        SET    did = (
            SELECT did
            FROM   t_department
            WHERE  d_name = '测试部'
        )
        WHERE  did IS NULL;
        ```

        * > **易错点**：空不能用等于号比，必须用 `IS NULL`。`did = NULL` 判断的永远是"未知"，一行都命中不了。

### 同表嵌套与 1093

    * **案例：把李冰冰的薪资改成孙红梅的薪资**

        ```sql
        UPDATE t_employee
        SET    salary = (
            SELECT salary
            FROM   t_employee
            WHERE  name = '孙红梅'
        )
        WHERE  name = '李冰冰';
        ```

        * 查孙红梅的薪资出来是 1 万 3500，李冰冰是 2 万多，改过去相当于给她降工资。
        * 一执行报 1093，不让改。

    * **报错的机理**
        * 前两个案例都是「部门表 ↔ 员工表」两张不同的表之间做修改，只涉及查询；这个案例是员工表与员工表之间，直接嵌套就出问题。
        * `UPDATE` 占用了员工表这张对象的引用，下方内部又要查询员工表，又是一次引用，相当于**一个对象被两个位置同时做了地址引用**。
        * 其中一个引用没释放，两个人都占着，这时候任何一方都不能直接改——你改了别人怎么用。这是 MySQL 为安全性提供的保护机制。

    * **解法：再套一层**
        * 让内层那个只查询先把值算出来，执行完以后把员工表的引用释放掉。

        ```sql
        UPDATE t_employee
        SET    salary = (
            SELECT salary
            FROM   (
                SELECT salary
                FROM   t_employee
                WHERE  name = '孙红梅'
            ) AS tmp
        )
        WHERE  name = '李冰冰';
        ```

        ```text
        朴素写法：同一张表被两个位置同时引用

            UPDATE t_employee          -->  占用 t_employee
                  |
                  +-- SET salary = ( SELECT salary FROM t_employee  )
                                                 ^
                                                 +-- 又来一次，还是同一张表
                  |
                  +-- WHERE name = '李冰冰'
              同一张表既被读又被改  =>  1093

        套一层：内层先算完，结果交给 tmp，原表的引用顺手释放

            UPDATE t_employee          -->  占用 t_employee
                  |
                  +-- SET salary = ( SELECT salary FROM ( SELECT salary FROM t_employee
                                                       WHERE name = '孙红梅'
                                                     ) AS tmp
                                 )
                  |
                  +-- WHERE name = '李冰冰'
                     内层执行完毕，salary 落在 tmp 上，t_employee 的读取到此结束

              外层表 + 临时表 = 两张表  =>  可以改
        ```

        * 内层 `SELECT` 先跑完并把结果甩给 `tmp`，`t_employee` 的读取引用随之结束，等外层真正下手写的时候那张表已经没人跟它抢了。
        * 修正的思路是在内层子查询外面再套一层只查询，结果交给 `tmp`，最终修改的是外层表和临时表之间的关系。

### DELETE 跨表删

    * **删除嵌套子查询的定位**
        * 删除嵌套同样很简单，只不过也会面临跟修改一样的问题：删除的时候不能是同一张表，解决方案与嵌套修改的解法一致。

    * **案例一：删除测试部门的员工数据（两张表，可直接嵌套）**

        ```sql
        DELETE FROM t_employee
        WHERE  did = (
            SELECT did
            FROM   t_department
            WHERE  d_name = '测试部'
        );
        ```

        * 两步走：先由部门名称查出部门 `did`（测试部是 6），再在员工表中按 `did` 删除员工数据。
        * 执行完毕后被删掉的那位是周周——她原本没有部门，嵌套修改的案例已把她的 `did` 改成了 6，这回终于被删掉。

    * **案例二：删除与李冰冰同部门的员工（同表，会撞上 1093）**

        ```sql
        DELETE FROM t_employee
        WHERE  did = (
            SELECT did
            FROM   t_employee
            WHERE  name = '李冰冰'
        );
        ```

        * 两步依然清楚：先查李冰冰对应的部门 `did`（是 1），再按这个 `did` 删掉该部门的其他员工。
        * 但外层和内层是同一张表、又查又删，MySQL 的保护机制直接拦下来，报的还是 1093。

    * **解法与嵌套修改完全一致**

        ```sql
        DELETE FROM t_employee
        WHERE  did = (
            SELECT did
            FROM   (
                SELECT did
                FROM   t_employee
                WHERE  name = '李冰冰'
            ) AS tmp
        );
        ```

        * 思路是"里面不直接拿员工表了，先查出一个虚拟结果表"，让内层先执行完、外层表与临时表之间的关系去操作。
        * > **易错点**：每个由查询产生的虚拟表**必须起自己的别名**；`TMP` 这个别名是可以把 `as` 省略掉写的，但名字不能省。
        * 执行完提示 15 行受影响，刷新后 1 号 id 的部门整批被删掉了。

### INSERT 复制结构与数据

    * **嵌套查询的最后一章讲三件事**
        * 标题起得并不十分准确，实际内容包含三个场景：一是通过复制其他表的结构创建一个表；二是把其他表的数据插到我们这个表里（用 insert 嵌套）；三是创建一张模仿其他表的表并把它内部的数据一并复制过来。

    * **只复制表结构**

        ```sql
        CREATE TABLE t_employee_1 LIKE t_employee;
        ```

        * `LIKE` 关键字参照已经存在的表，创建一个表结构相同的新表，但里面没有数据。

    * **搬运数据**

        ```sql
        INSERT INTO t_employee_1 SELECT * FROM t_employee;
        ```

        * 这个位置**不写 `values`**，也不写 `values` 加后面那些东西，直接写 `select 星 from 谁`。
        * 后边还可以再加 `where` 条件，加了代表只拿部分数据，不写就代表把所有数据都插进来。

    * **结构与数据二合一**

        ```sql
        CREATE TABLE t_employee_2 AS SELECT * FROM t_employee;
        ```

        * `AS` 后边参照把上面那句 `select` 粘过来，创建表的同时数据和表结构全部参照这个表。

    * **四类嵌套子查询的收束**
        * 嵌套子查询一共四种场景——`select` 嵌套、`update` 嵌套、`insert` 嵌套、`delete` 嵌套，到这里全部讲完，多表查询也讲完了。
        * 回顾全景：垂直连接、水平连接，水平连接里又分成内连接、外连接、自然连接，再加上这四种嵌套子查询。

## 多表查询综合实战

### 三张表与中间表

    * **表结构**
        * 学生表有学生 id、名字、年龄、性别；课程表有对应 id 以及课程的名字；分数表有一个分数，也知道这个分数属于哪门课、哪个学生。
        * 分数表是典型的中间表，两列外键分别把学生和课程挂上，课程和学生之间是"多对多"的关系。

        ```text
           student(student_id PK)          course(course_id PK)
                  |                                 |
                  | student_id                     | course_id
                  v                                 v
                score(student_id, course_id, score)

             分数表两个外键：student_id 指向学生表，course_id 指向课程表
        ```

    * **数据基线**
        * 数据是三名学生（爱丽丝、鲍勃、查理）、三门课（数学、物理、化学）、七条分数记录。

### 保主表：左连接

    * **查每名学生的姓名、年龄、所选课程的名称以及对应的成绩**
        * 题目强调"如果学生没有选择课程，那成绩为空"，也就是没选课的学生也得查出来，只是成绩为空。
        * 这句话在告诉你学生表是逻辑主表，要用左连接，学生放最左边，剩下的都是左连接。

        ```sql
        SELECT STU.name,
               STU.age,
               COU.course_name,
               SC.score
        FROM   student STU
        LEFT JOIN score  SC  ON STU.student_id = SC.student_id
        LEFT JOIN course COU ON SC.course_id  = COU.course_id;
        ```

        * 做法是先通过学生表关联分数表，占用中间表之后再去关联课程表。

    * **别名要写全**
        * 别名少写一个字母执行就报列不存在；三张表的别名必须各自独立，不能互相顶替。

### NOT IN 与 DISTINCT

    * **查没有选择任何课程的学生姓名**
        * 目标是查学生姓名而条件是"没选课"，做法就是先查没选课学生的 id，再拿 id 去查姓名。

        ```sql
        SELECT name
        FROM   student
        WHERE  student_id NOT IN (
            SELECT DISTINCT student_id FROM score
        );
        ```

    * **判定依据**
        * 课程表里包含所有课程，跟学生选不选没关系；学生表里是所有学生信息，选不选课都有。
        * 真正该看的是分数表：只要在分数表里出现过的都选过课了，反之没出现的就是没选课。

    * **DISTINCT 的作用**
        * 这些 id 有没有必要重复出现没有必要，出现 1、2、3 就行；一人选两三门课出现多次也只证明他选过。
        * `DISTINCT` 这个关键字可以把后边的一列或者多列值去重。

        * > **易错点**：这里子查询返回的是多个值，不能用 `=` 比，要用 `IN` / `NOT IN`（或者 `ANY` / `ALL`）。放过 `IN` 执行一次三位学生全列出来，证明所有学生都选过课，但这题的答案得加个 `not`。

### 分组筛选与 HAVING

    * **查平均分高于全体平均分的课程**
        * 先查所有学生的平均成绩，一共七条分数，平均成绩是 86 分。
        * 再按学科分组算平均分，起学科 id 分组字段和平均分。

        ```sql
        SELECT course_id AS cid,
               AVG(score) AS cav
        FROM   score
        GROUP BY course_id
        HAVING AVG(score) > (SELECT AVG(score) FROM score);
        ```

        * 分完组以后再筛选用 `HAVING`，它是跟 `GROUP BY` 搭配、专门做分组后筛选的，后边可以直接复用这些字段。
        * 括号里是查总体平均分的标量子查询，返回单值，可以直接参与比较（比较符号、算术运算都行）。
        * 执行下来只有 01 学科那行显示出来，它的平均分 89 高于整体的 86，其余几门都低。

    * **分组后筛选的工具**
        * `HAVING` 跟 `GROUP BY` 搭配、专门做分组后筛选，后边可以直接复用分组字段和聚合结果。
        * 先分组再筛选用 `HAVING`，而不是 `WHERE`。

### 连接后再分组排序

    * **查每名学生选课的平均成绩并降序排列**
        * 单表版本按学生编号分组，1 号学生考的是 101、102 两门学科，平均成绩就是 85 加 78 再除以 2。

        ```sql
        SELECT student_id AS gid,
               AVG(score) AS avg_score
        FROM   score
        GROUP BY student_id
        ORDER BY avg_score DESC;
        ```

        * 执行完是 3 号学生分最高，然后 2 号、1 号；降序就是从大到小，写 `DESC` 就可以了。

    * **要出姓名就得先连接**
        * 分数表里只有学生 id 没有姓名，所以先把学生表和分数表做一次水平连接，再拿名字分组、再排序。

        ```sql
        SELECT STU.name,
               AVG(SC.score) AS avg_score
        FROM   score  SC
        JOIN   student STU ON SC.student_id = STU.student_id
        GROUP BY STU.name
        ORDER BY avg_score DESC;
        ```

    * **可复用结论**
        * `GROUP BY` 后边算出来的这些数据，在 `ORDER BY`、`LIMIT`、`HAVING` 后边都是可以直接使用的。
        * 写完连接后该加 `where`、`GROUP BY`、`ORDER BY` 就照常加。

    * **延伸**
        * 单表版本与多表版本道理完全一样；用子查询做出来的这些题也可以研究能不能换成连接查询来实现。

## 收官预告：事务概念

### 事务是什么、有什么用

    * **事务（Transaction）**
        * > **定义**：一套操作命令的**有序集合**，一个不可分割的工作单位。
        * 它是一个有序的容器，内部可以装多条我们写的 SQL 语句。
        * 事务中单个命令不会立即改变数据库的数据；当全部执行成功，可以统一进行数据的更新；当有任意命令失败，可以进行状态的回滚。
        * 组成只有三段：事务的开始、事务的结束，开始与结束中间写多条命令，它们就在一个事务中。

    * **两个核心作用**
        * 第一，为数据库操作序列提供一个从失败中恢复到正常状态的方法——语句执行错了没关系，它不会部分修改数据库，会大家一起回到之前的状态，等于给了容错的机会。
        * 第二，当多个应用并发访问数据库时，可以防止彼此之间的操作互不干扰。
        * 收益是本质上的：事务把多条原本单独执行的语句装进一个不可分割的单位，让它们统一成功或者统一失败。

    * **什么时候需要加事务**

        * 生活化的例子：高考前偷偷逃课上网被父母抓住，父母不会当场开打，而是撂一句"你给我等着"——因为打完可能影响考试心情，考好了父母又找不回场面。所以这两件相关的事（挨打与高考）会互相影响、彼此结果绑定，必须整成一件事统一决策；这类事情必须放进一个事务里。
        * 程序里的例子是转账：加钱与减钱是两个修改动作，一共可能出现加钱成功减钱失败、加钱失败减钱成功等四种状态，其中只有「加钱成功且减钱成功」一种是业务成功的，其余三种都不应该单独进行数据修改。
        * 把「发起者减钱」和「接收者加钱」这两条 SQL 放进同一个事务，就能避免出现"银行卡里无缘无故多出很多钱"的局面。
        * > **结论**：只要一个业务中包含两条或者以上的修改数据操作，就应该加到事务中；后续开发场景下甚至会把所有业务层的方法全部加上事务，不管一条两条一律都加。事务是开发中必备的一个技术点。

### ACID 四大特性

    * **原子性（Atomicity）**
        * > **定义**：在早期物理学版本中，原子是最小不可分割的一个单位；事务中的操作要么都发生，要么都不发生。
        * 以转账为例，不能把加钱和减钱中的任何一个动作剥离出这个事务——剥离出去这个事务就没有意义了，它已经是最基本的业务单位，不能再拆。

    * **一致性（Consistency）**
        * > **定义**：事务内部的这些动作要么全成功、要么全失败；换一种理解是数据的总状态前后一致。
        * 举例：我银行卡有 1000 块、你银行卡也有 1000 块，转账 500 之后我变 500、你变 1500，加起来还是 2000，跟之前一样；失败的话两人都不动，还是 2000。
        * 有人会拿"扣手续费导致总额少了"来较劲——那跟一致性没关系。

    * **隔离性（Isolation）**
        * > **定义**：同一个数据库的表可以被多个客户端访问，这些访问之间各自是独立事务，事务与事务之间互相不受干扰。
        * 具体表现是：他做了什么你看不见，只有他提交以后你才能看见（隔离级别的强弱后续单独展开讲）。

    * **持久性（Durability）**
        * > **定义**：事务一旦真的提交了，就真的会改变数据库、真的生效；如果没提交，就真的不修改数据库。
        * 最终它一定会真的去改变数据库的数据状态，是持久性的改变。
