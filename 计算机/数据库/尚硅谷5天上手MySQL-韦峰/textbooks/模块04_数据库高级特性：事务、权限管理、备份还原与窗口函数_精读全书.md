## 事务怎么手动控制、隔离级别怎么定，以及权限怎么管
> 对应块：BLK19 | 覆盖分集：P94-P98 | 块标题（分集名）：《94-数据库高级和新特性-事务实现方案1手动提交》

先把一个特别容易忽略的事情摆到台面上。

前面我们写过的那些 `update`、`insert`、`delete`，语句末尾敲个分号回车，数据就真真切切变掉了。你有没有想过：**这条语句到底是在哪一刻落地的？**是它执行完就落地，还是还差一步？

答案是：在 MySQL 里，事务**默认就是自动提交的**——每一条语句自己就独立待在一个事务中。语句执行成功，事务立刻自动提交；语句写错了执行报错，这条语句就不会生效，数据还是原样。你不用写任何东西，数据库替你把提交这件事做了，而且做得又快又勤快。

所以你想想，为什么我们随手写错一条 `update`，数据居然没乱？因为那条错语句压根没落下去。

那既然如此，事务还有存在的必要吗？有。我们的目标非常明确：**把多条语句装进同一个事务里，让它们要么一起生效，要么一起不生效。**

### 为什么非得多条语句一起装进一个事务

还是拿转账说事。

转账这件事拆开看无非两个动作：给张三加钱，给李四减钱。如果你不管它，自动提交机制会老老实实地让每条语句各自成为一个事务、加钱成功就加钱、减钱失败就减钱，两边**互不干扰**。

麻烦就出在这个"互不干扰"上：

```text
   加钱（事务A）              减钱（事务B）
        │                          │
        ▼                          ▼
   成功 → 数据改了             失败 → 数据没改
        │                          │
        └──── 钱凭空多出来了 ───────┘
```

加钱那一路已经落库了，减钱那一路没落库，账就对不上了。我们要做的，是把这两步**焊成一个整体**——要么都成，要么都不成，绝不出现只成一半的局面。

那就开工。这一节先讲第一种实现方案：手动提交。

### 方案一：关掉自动提交，改成手动提交

你现在不是自动提交吗？每条语句都得自己提交一下。既然不想要这个自动的，那就把开关关掉，改成我说了算。

关闭的方式是设置一个 MySQL 的系统变量，把 `autocommit` 置为 `false` 或者 `0`：

```sql
SET autocommit = false;   -- 或者 SET autocommit = 0;
```

关掉之后再写 SQL——你写一条也好，写 N 条也好，它都不再自动提交，也不会立刻改变数据库的数据。写完之后，必须由你主动调 `COMMIT` 或者 `ROLLBACK` 来收尾。单条想单条过、想改个东西，也一样得调；多条就一起调，调完之后它们才算真正在这个事务里执行完。想恢复原来的自动提交，同样一条命令的事：

```sql
SET autocommit = true;    -- 或者 SET autocommit = 1;
```

那怎么确认现在到底是自动还是手动？用 `SHOW VARIABLES LIKE` 这个关键字去查 MySQL 的系统变量，关键字加上 `autocommit` 就能看到了。

> **提示**：`SHOW VARIABLES LIKE 'autocommit';` 是查系统变量的，不是 `SELECT`。这两个词长得像，千万别混。

完整流程就三步，记住这个顺序就够了：

```sql
SET autocommit = false;          -- 先关自动提交

UPDATE t_员工表 SET salary = 10000 WHERE name = '孙宏亮';
UPDATE t_员工表 SET salary = 8000  WHERE name = '周小胖';
-- ……想写几条写几条

COMMIT;                          -- 不报错就 commit
-- ROLLBACK;                     -- 报错就 rollback，二选一
```

那么到底调哪个？简单到不能再简单：**只要不报错就 `COMMIT`，如果报错就 `ROLLBACK`。**后期写到 Java 代码里也是同一套逻辑——把整段语句执行放进 `try-catch` 块，捕获到异常就 `ROLLBACK`，没异常就 `COMMIT`。事务这块的语法本身真的很简单，大家可以多去练练。

#### 这个设置的有效期，只有一个连接

这是个小注意事项，但特别容易忘：**`SET autocommit = false` 的有效期是"一个连接"。**

回忆一下我们之前讲过怎么登录 MySQL，`mysql -u 账号 -p 密码`，登录进来的那一刻默认都是自动提交。你设置完之后，只要这个黑窗口不关闭，它就一直是 `false`；等你把黑窗口一关、再打开，那就是一个**新连接**了，得重新设置一遍。

在 Java 里连接数据库也是同样的道理：你连接一次、设置一次，这次有效；下次再连接，还得重新设置。

> **易错点**：新建连接时，`autocommit` 一律是默认值（自动提交）。所以每建一个新连接，都要主动设置一次；不是新建连接的话，设置一遍就够了。

#### 演示时千万不要用小海豚

这一点我得专门强调，因为这是新手最容易踩的坑：**演示事务千万别用小海豚。**

小海豚这个工具在写完语句、点执行的时候，它会帮你在背后自动提交事务——你关掉窗口都没用，它已经帮你主动提交了。那你看到的结果永远是"自动提交"的效果，根本演示不出手动提交的过程。

所以我们统一转到 CMD，用纯命令行的方式，不加任何额外工具的参与，去演示这个过程。

#### 完整走一遍

先准备数据。建一个库 `test08_other`，再把员工表和之前的数据都放进来。

```sql
CREATE DATABASE test08_other;
USE test08_other;
```

打开员工表看一眼，记下孙宏亮现在是 28000，一会要改的就是他。

然后进 CMD：

```sql
mysql -u root -p
```

登录之后切库：

```sql
USE test08_other;
```

进来第一件事，先看看我们是不是自动提交：

```sql
SHOW VARIABLES LIKE 'autocommit';
```

这回记住，当前这个黑窗口一关，下次再开就又变回自动提交了——每一次新建连接都会走默认值。改掉它：

```sql
SET autocommit = false;
SHOW VARIABLES LIKE 'autocommit';   -- 再查一遍，已经变成关闭状态了
```

现在把孙宏亮的工资改成 10000（28000 太高了）：

```sql
UPDATE t_员工表 SET salary = 10000 WHERE name = '孙宏亮';
```

回车看到"影响 1 行"。但这时候你到小海豚里刷新孙宏亮这条记录——**工资还是 28000，没变。**

为什么？因为事务的作用就是**不会立即改变数据**。只有当你最后主动调了 `COMMIT` 或者 `ROLLBACK`，二选一，这个事务才真正结束。你调 `COMMIT`，数据才真的改；你调 `ROLLBACK`，就代表回到这个事务之前的状态，还是 28000，事务同样结束。

再改一次，这回收尾：

```sql
UPDATE t_员工表 SET salary = 10000 WHERE name = '孙宏亮';
COMMIT;
```

刷新，工资变成 10000。事务这套操作就齐了。

### 方案二：start transaction 开启独立事务

第二种方案叫**开启一个独立的事务**。它跟自动提交、手动提交都没关系——不管你现在是哪种模式，都能用一条命令硬生生开出一个独立事务来。

这条命令是 `START TRANSACTION`。它到底什么意思？设想你现在正在跑一串 SQL 语句，这次操作可能是一个事务，也可能不是。`START TRANSACTION` 一执行，相当于在这一切之上**又浮动地升了一层**，单独划出一块空间：

```text
┌─────────────────────────────────────────┐
│  外层：当前会话正在执行的 SQL 语句        │
│        （可能本身就是自动提交）          │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │  START TRANSACTION;  ← 独立事务空间 │  │
│  │  UPDATE ...;                      │  │
│  │  UPDATE ...;    和外层的语句       │  │
│  │  UPDATE ...;    互不干扰          │  │
│  │  COMMIT; / ROLLBACK;              │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

在这块空间里你可以写若干条 SQL 语句，写完再主动提交或者回滚。它不但在自动提交模式下能用，在手动提交模式下依然也能用。

演示的时候还是老规矩，先退出去手動提交模式——把连接退掉，把窗口关掉，重新打开一个 CMD，再连一次 MySQL。重新连上之后你再查 `autocommit`，它果然又回到自动提交了，这就是"每次新建连接都走默认值"。

然后在自动提交模式下，照样能开独立事务：

```sql
USE test08_other;

START TRANSACTION;                            -- 独立开启事务

UPDATE t_员工表 SET salary = 10000 WHERE name = '孙宏亮';
-- 后面还能再写多条

SELECT * FROM t_员工表 WHERE name = '孙宏亮'; -- 还是 28000
COMMIT;                                       -- 这句话才真的把事务结束掉
```

下次想再开一个，重复写一遍 `START TRANSACTION` 就行。

#### 事务并不能回滚一切

说完语法必须提一个注意事项：**事务并不能回滚一切。**

你做数据库操作的时候得注意，比如我们的 DDL 语句就不支持事务。什么叫 DDL？你把一个表删了、你删了一个库等等这些语句。它不受事务管——你想先开启事务、中间做点操作，最后 `ROLLBACK`，没用的，管不了；事务只能针对数据的删除、修改、插入有影响，管不了 DDL。

你删了 DDL，该跑路还得跑路，别让人抓住，老板抓住把你腿给你打折了，你回不了。

不过大家也不用怕，因为我们在新特性里还会讲一个关于数据还原的东西——误删除数据了怎么办，如何用 binlog（运行日志）去回滚，那个是可以回滚的。但**事务是回滚不了的**。

> **易错点**：`DDL` 不支持事务，或者说事务不支持 `DDL` 语句的回滚。你加上 `ROLLBACK` 也回归不了，切记。

### 什么是事务的隔离性

概念讲完了，我们单独来说说事务的四个特性里的一个：**I，隔离性**。这是一个热门的面试题，我们来把它讲透。

先看这句话——**一个事务内部的操作和使用权，对并发的其他事务来说是隔离性的**。也就是说在并发执行的时候、多人同时操作同一个库表的时候，各个事务之间是互相不干扰的。这就叫隔离性。

打个比方你立刻就懂了。你和你的同桌，为了防止文具互相搞混，你会怎么做？画一道线，或者挡一个板。产生隔离性了。好处也很直白：互相的数据不干扰。

```text
一个客户端访问数据库  ──▶  一个事务
再有客户端访问数据库  ──▶  一个事务
再有客户端访问数据库  ──▶  一个事务
     ……
         N 个客户端并发访问同一个库表
              =  N 个事务
         事务之间靠「隔离性」互不干扰
```

隔离性的好处就在这儿：它避免了事务之间的干扰。那真干扰了又如何？没关系，一会儿会介绍——干扰了可能会产生一些数据上的问题。

#### 隔离性有强有弱

知道什么是隔离性以后，接下来说**隔离级别**。隔离性有强有弱，分为不同的级别。还是拿同桌说：你俩为了防止文具、书本拿乱，可以先在桌上画一道三八线，这也是隔离性；但这种隔离比较弱，因为他手真的能伸过来把你的铅笔橡皮拿走。你想再提高一点，就在桌上垒一道书墙，他够不着了；觉得还不安全，就干脆在两张书桌中间垒一道砖墙。

```text
        隔离性弱  ──────────────▶  隔离性强

   三八线        书墙              砖墙
    │            │                │
  干扰多        干扰少           几乎无干扰
  性能高        性能中            性能低
```

隔离性越高，两个事务之间的数据干扰程度越低；但性能也必然受影响——你垒墙、划线，哪个更快？当然是划线了。

所以隔离级别一共有四种，各自有各自能避免的问题。

| 隔离级别 | 中文名 | 脏读 | 不可重复读 | 幻读 | 谁拿它当默认 |
| --- | --- | --- | --- | --- | --- |
| `READ UNCOMMITTED` | 读未提交 | 可能发生 | 可能发生 | 可能发生 | — |
| `READ COMMITTED` | 读已提交 | 不会 | 可能发生 | 可能发生 | Oracle |
| `REPEATABLE READ` | 可重复读 | 不会 | 不会 | 很小概率 | MySQL |
| `SERIALIZABLE` | 串行化 | 不会 | 不会 | 不会 | — |

- **读未提交**，最低的级别，相当于画了一道线。这种隔离级别下，虽然说有隔离性，但它可能会发生各种问题，脏读、不可重复读以及幻读都可能发生。具体什么问题先不用管，这种隔离级别太低了，事务之间可能会出现数据上的三个问题。想解决就往上提高。
- **读已提交**，是 **Oracle 的默认隔离级别**。Oracle 是关系型数据库行业的标杆，它选的是这个级别。这个级别不会发生脏读，但可能会发生不可重复读以及幻读。
- **可重复读**，是 **MySQL 的默认隔离级别**。所以第一个面试题就出现了：**MySQL 默认隔离级别是什么？记住，就是第三个 `REPEATABLE READ`。**它避免了脏读，也不会发生不可重复读，最后很小概率下可能会发生幻读。
- **串行化**，也叫序列化。之前讲电流的时候有并流、并行还有串行，这就是串行的意思。它避免了脏读、不可重复读，还有幻读——避免了所有的问题。

那问题来了：**为什么大家不把隔离级别都设成最后一个，非得 Oracle 用第二个、我们用第三个呢？**

原因在我讲这三个问题的时候已经埋下了：三个问题里，**只有脏读是真正的数据错误**，剩下俩并不是错误，它们只是不符合事务的那四个特性、只是不符合一致性而已。

记住这个规律：**隔离级别越往下越高，隔离级别越高，数据一致性就越好、数据越安全，但性能就越弱。**所以不一定是隔离级别越高越好。

我给大家举个例子，这个例子我在课上经常举。我在北京工作，印象特别深：只要北京一开什么大型的会议，我都不用看新闻我就知道。怎么看？你去坐地铁，你只要看地铁门口那个安检就知道了——只要排长队，长长地排成很多条龙，那肯定是开什么大会了。为什么？一开大会安检级别就提高了，每个人到安检点都给你浑身摸一遍，甚至耳孔里边的都看看有没有藏什么东西。安检级别越高，检查得越仔细，而进去的人的效率越慢。平时没有开什么会的时候，你兜里边装个炸弹都能混进去，因为他也不咋好好检查你。

你看，这种场景下人进得快、效率高，但安全上是不是有问题？所以**隔离级别没有说越高越好**——越高数据确实越安全，性能却越差。我们要选一个合适的隔离级别。

这就是为什么 MySQL 选第三个、Oracle 选第二个。Oracle 的性能会比我们好一些。

### 三个并发问题到底怎么回事

说完了级别，我们来看看脏读、不可重复读、幻读这三个问题究竟是什么，有没有必要非要把隔离级别设得比第二个更高——只要避免脏读就行了，那另外两个可以发生，它们到底算不算真正的错误呢。

#### 脏读

脏读很简单：**一个事务读取了另外一个事务未提交的数据。**这句话一定记住，加粗的就是"未提交"。

什么意思呢？两个事务同时发生，另外一个事务开启事务以后操作了一个数据，**他还没提交呢，你就读上了**。这就叫脏读——读到人家未提交的数据，看到不该看的东西。

这算错误吗？很明显的错误。为什么？因为对方可能数据回滚。人家回滚了以后，你看见的东西就是错误的。**所以脏读读到的东西不一定是真实的数据，脏读是一种真正的错误。**

所以你发现大家都避开了把隔离级别设成第一个，因为它可能发生脏读。

#### 不可重复读

先给个结论：不可重复读和幻读这两点**都不是数据上的错误，它们只是不符合一致性原则而已**。

一致性是什么意思？我们讲事务有个一致性，就是说前后的总状态要一致。一个事务内部不符合这个原则，但数据本身并没有错。

不可重复读指的是：**一个事务读取了另外一个事务提交的修改数据。**注意啊，是"已提交的修改数据"——A 事务读到了 B 事务提交的修改数据，这就叫不可重复读。

但数据错了吗？没错。为什么？因为他真的已经把这个数据提交了，他已经真的改变数据库了，只不过你这次事务读到了。

举个例子。你进来的时候读这个数是 10000，你啥也没干呢，它变成 12000 了，突然间就变成 12000——这种问题就叫不可重复读。

那为什么变成 12000 呢？因为有另外的事务真的做了修改，加了 2000，并且把这个事务提交了，你才能读得到。首先，这个 12000 的数据是没错误的，这只是不符合一致性原则——我一个事务中没有做修改，数据无缘无故从 10000 变成 12000，前后不一致。

> **易错点**：不可重复读是"读取了另一个事务**已提交**的**修改**数据"。它和脏读的分水岭，就在于"未提交"和"已提交"这四个字。

有的同学到这儿还不太理解，我再举个例子，你就懂了。

假如你是公司的财务，你在做这个月的报销，做到马上要结尾了，马上要统计结束了。这个时候有一个员工过来了，跟你说："张工，我那个账我整错了，我那报销金额我写的是 80，但不对，我应该报销 180，因为当时打车我忘了那个打车净额，我记错了，应该是 180。"

那现在你思考一个问题：**首先，你应该给人报销 80 还是 180？**答案肯定是 180，因为他真的就花了 180。

但是各位，你这个财务得烦死了。为什么呢？因为他现在正在一个统计周期内。你就算有真实要修改的数据，**你不要让我现在知道**，等我统计完了再说好不好？我先把整体金额算完了，算完以后最后你再说"我那个错了没关系，我在增减金额再加 100 或减 100"是不是就可以了。你偏要在周期正中间去说，我不好去改。我这个统计结束以后你再跟我说，不就完事了。

这个时候就相当于这种叫不可重复读——**在我的事务期间内，读到另外一个事务修改的数据。**其实我应该咋办呢？我应该读不到。等我事务结束以后，我开启下一个事务，我再读得到。这就叫做不可重复读。

#### 幻读

幻读（也有人叫虚读）也很好理解：**一个事务读取了另外一个事务新增或者删除的记录，记录数不一样了。**

之前读到的**修改**叫不可重复读；**虚读、幻读**代表的是，你读着读着突然间多了一条数据，或者少了一条数据——突然间出现了，这叫做幻读。

这也是一种数据正确吗？是的，因为它读到的同样是提交的数据。

还是拿刚才报销的例子。还是张工，你正做着做着账，做到过程中，你突然发现有个人说了："哎呀，我忘了一个事儿，我这个月还没报销呢，你把我的东西赶紧加上。"注意，他并不是之前给你提交过的，他都没提交过，这一次他想临时的再去加他自己——这叫做**新插入**的数据，那这就叫做幻读。而上面那个是已存在的修改数据，就是不可重复读。

所以下边这两种，本质上都不是数据错误，就是不符合前后的一致性原则。

**所以这就是 Oracle 的高明之处了。**Oracle 用了第二个级别，它避免了脏读，可能会发生不可重复读或者幻读——这两个人家说不算错误。但是呢，我的性能比 `REPEATABLE READ` 高。所以其实我们在开发中也建议把我们的隔离级别改成第二个，只要避免脏读就可以了。

### 隔离级别的查看和修改

语法非常简单，两条命令。

查看隔离级别：

```sql
SELECT @@transaction_isolation;
```

MySQL 默认返回的就是 `REPEATABLE-READ`。

修改隔离级别：

```sql
SET TRANSACTION ISOLATION LEVEL  <隔离级别>;
```

后面填 `READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE` 里的任意一个就行。

记住：**是不是真的互不干扰、干扰到什么程度，决定权在隔离级别手里，不在"隔离性"这个词手里。**隔离性只是给了你一个方向，具体强弱强弱是隔离级别定的。

### 开两个窗口，把三个问题现场跑一遍

光说不练假把式。我们准备一张银行表，把上面说的三个问题一个一个演示出来。

#### 准备一张银行表

这个表很简单，就叫银行表，里面有一个银行卡账号，还有一个金额：

```sql
USE test08_other;

CREATE TABLE t_bank (
    account VARCHAR(20),   -- 银行卡账号
    money   INT            -- 金额
);

INSERT INTO t_bank VALUES ('张三', 10000);
INSERT INTO t_bank VALUES ('李四', 10000);
```

我们的场景很简单：**张三欠李四一千块钱。**还钱就是张三减一千，李四加一千，是不是就完事了。

打开两个 CMD 窗口，一个当张三，一个当李四，两个人同时连接到同一个库，模拟并发场景。先各自登录、切换库：

```sql
mysql -u root -p
USE test08_other;
```

然后各自查一下当前默认的隔离级别：

```sql
SELECT @@transaction_isolation;   -- 两边都是 repeatable read
```

#### 演示脏读

想演示脏读，得把隔离级别降到最低：

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;   -- 两边都设
```

这个隔离级别最低，防御性比较差，大家互相之间都没有那么高的警惕性。

演示开始。张三说："兄弟四哥，我今天还你 1000 块钱，有钱了。"还钱的话，两个人都开一个事务：

```sql
START TRANSACTION;   -- 两边都开
```

李四先留个心眼，先查查自己有多少钱，"他还我 1000，我是不是有 11000 了呢"：

```sql
SELECT * FROM t_bank WHERE account = '李四';   -- 10000，行
```

行，那就还钱吧。张三的操作是：给对方加 1000，再给自己减 1000：

```sql
UPDATE t_bank SET money = money + 1000 WHERE account = '李四';
UPDATE t_bank SET money = money - 1000 WHERE account = '张三';
```

这时候张三跟李四说："四哥，我全给你打过去了，你查查对不对。"

李四一查——真的多了 1000 块钱。那按理说这事就成了，他把账号跟张三说一声，张三就把欠条撕了，张三最后正常提交。这哥们要是不搞事，这事就没啥问题了。

**但这哥们搞了个事：他执行了 `ROLLBACK`。**

一回滚，前面那两个动作全部失效。李四读到的那个 11000，是张三一个**未提交**的数据。

```text
时间轴     李四窗口                                        张三窗口
 t1      START TRANSACTION;
 t2      SELECT ... WHERE account='李四';  → 10000
                                                        START TRANSACTION;
 t3                                                     UPDATE ... '李四' +1000
 t4                                                     UPDATE ... '张三' -1000
 t5      SELECT ... WHERE account='李四';  → 11000
         "四哥真到账了，欠条撕了"              ROLLBACK;  ← 全部作废
 t6      第二天再查 → 还是 10000
         "昨天明明已经还我了，那 1000 块钱呢？"
```

这时候你想想，李四这 1000 块钱还会有吗？不会。他隔天再查银行卡，发现自己还是 10000。他会去质疑张三吗？**不会**，因为他确实看到过 11000。但确实是这哥们捣的鬼——因为你读到了他一个未提交的数据。**这就叫脏读。**

脏读是真正的数据错误。

#### 演示不可重复读

把隔离级别往上提一提，提到第二个级别：

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- 两边都设
```

这回级别提高了，李四"变聪明了，吃了六核桃了"。张三说："四哥，我再还你钱，我再骗你一把，看能不能骗成功。"

先查一下，确认自己有 10000。然后又是老套路——两边各自开事务：

```sql
START TRANSACTION;   -- 两边都开
```

李四先查：

```sql
SELECT * FROM t_bank WHERE account = '李四';   -- 10000
```

张三照样先给他加 1000，再给自己减 1000，然后喊一声："四哥我又给你还钱了，你查一下。"

李四一查——**查不到了。**

为什么？因为你"吃了核桃"，隔离级别提高了，你读不到他未提交的数据，避免了脏读。李四说："不对呀三儿，这一次的数据我没读到，我没有看到 1000 块钱啊。"

张三这回没法子了，他必须**真的提交**。一提交，这才行。

按理说，拿一致性来说，我们这一个事务中不应该读到——因为你进来是 10000，你啥也没干，你后面还是应该是 10000 才对。但这次我们再读一遍，发现变成了 11000。就是你读到了对方提交的一个修改数据。

**这个数据是对的，但不符合一致性原则，这就叫不可重复读。**

```text
时间轴     李四窗口                                       张三窗口
 t1      START TRANSACTION;
 t2      SELECT ... '李四'  → 10000
                                                        START TRANSACTION;
 t2~t3   （读不到，未提交）    UPDATE '李四' +1000;
                                UPDATE '张三' -1000;
 t4                                                   COMMIT;   ← 真提交了
 t5      SELECT ... '李四'  → 11000
```

#### 演示幻读

再把级别提到第三个——`REPEATABLE READ`，MySQL 的默认级别：

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- 两边都设
```

第三个级别能避免刚才的脏读和不可重复读。照着老样子验一遍：两边开事务，李四先查——11000；张三减 1000、加 1000，然后 `COMMIT`；李四再读——**还是 11000**。你多试几遍，还是 11000。这就说明它避免了不可重复读。

**但是，第三个隔离级别其实基本来说也很小概率能发生幻读。**我试过很多回，基本就是四个千八百回能出现一回。

那幻读长什么样？这回李四不查李四了，**他查全部人**：

```sql
SELECT * FROM t_bank;   -- 两个人：张三、李四
```

张三这回不走修改了，**插一条新数据**（不删除，写插入）：

```sql
START TRANSACTION;
INSERT INTO t_bank VALUES ('王五', 998);
```

这时候李四再读，肯定还是读不到——为什么？因为要是读到了，那不就成了我们前面说的脏读了吗，对不对。

所以张三这回提交：

```sql
COMMIT;
```

这时候李四的做法是：**如果能读到，这叫虚读、幻读；如果读不到，那说明这个级别也避免了它。**你多试两遍，基本是四个千八百遍里可能抽出来一次。

所以 `REPEATABLE READ` 基本也避免了幻读。大家想演示幻读的话，用其他隔离级别去演示就行了。最后李四再 `COMMIT` 一下，下回他就能读到王五了。

**结论：MySQL 的默认级别，基本就把上面这三个问题全解决了。**

#### 串行化是怎么"彻底"解决并发问题的

最后一个级别，为什么说它能解决所有并发问题？它不是口头说说，我们来看清楚。

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- 两边都设
```

这个单词是真不好拼。设完级别，两边都开事务：

```sql
START TRANSACTION;   -- 两边都开
```

李四这边执行一条查询：

```sql
SELECT * FROM t_bank WHERE account = '李四';
```

**回车之后不执行。**不是卡住了，程序还活着，是它不给你出结果。

为什么？因为你是串行化。所谓的串行化就是：之前各位是能并发的，能并发执行多个事务；有了串行化以后，这个含义指的就是**没有并发了**，并行变成了串行，只能一个一个来。那当然就没有并发问题了。

```text
张三窗口（事务A）                      李四窗口（事务B）
START TRANSACTION;                    START TRANSACTION;
UPDATE ...;
COMMIT; ──────────────────▶          SELECT * FROM t_bank;
                                       └─▶ 一直挂着，不出结果
                                          必须等 A 提交后才返回
```

所以它的解决根本，就是把之前的并发变成串行、并行变成串行，一个一个来——你就不谈并发的问题了，也没有之前两个事务能同时进行数据库操作了，这肯定不会发生任何并发问题。

**但是性能是不是也太低了？**

这让我想起很早之前听过的一个段子。疫情期间，某个国家发现了一个新冠病例，这怎么彻底解决呢？把新冠病例给埋了——把人给埋起来。那不是彻底解决了吗，是不是？这很彻底。

串行化是怎么"彻底"解决并发问题的呢？就是把之前的并发变成串行，一个一个来，不谈并发问题了。

那开发中能不能用呢？**肯定用不了。**你用它，你知道会产生什么后果吗？举个例子，假如你有个注册用户的功能，那只能一个个来注册。假如你是第 10000 个人，你只能等到前 9999 个人注册完毕以后，你才能注册。那这个东西你用不了，用了相当于把自己程序弄废了。

但是，它存在即合理，确实有它的应用场景。**如果你做了一个秒杀功能，为了防止商品超卖，你可以把它设置成串行化**，最终进来的东西都一个一个处理。当然其实有些公司也是这么做的。我最早有一个叫 OFO 还是什么，就是那个共享单车，他们有押金，那押金是怎么退呢？只能一个一个退。那咋办呢？你只要把数据库搞成串行化，那你就一个一个退了，对吧？你有几千万用户，你最后一个用户你得退到啥时候呢？猴年马月是吧。

> **结论**：开发中不推荐用串行化。我们推荐还是第二个级别——`READ COMMITTED`，它是性能和数据安全性之间最均衡的一个选择。

到这里，事务这块就讲完了。重点有三个：**第一是它的概念；第二是什么场景下需要添加事务，以及事务的添加语法；第三是要理解隔离级别和对应的问题。**第三点是道面试题，但基本来说不需要我们去实际设置什么。

### 用户权限管理

接下来进入第二小章节，讲讲用户权限的控制。这块我们先做个简单的介绍和理解。

#### 什么是权限控制

MySQL 使用权限控制来**限制用户对库、表以及数据的操作访问权限**。

大家想一个问题。举个例子，假如你现在是你们公司的一个领导，公司新招了一个成员，他也要对我们的公共库进行一些操作。这回得由谁给他创建账号？由我们领导去创建。创建完账号以后呢，他的账号并不是对所有的库都能进行操作的，你得去赋予他对哪个库、哪个表能进行什么样的相关操作。

**这就叫权限控制。**权限控制是你到后期当上领导以后，需要给员工进行操作的一项必备工作。

那我们的权限控制基本可以分为三个级别：第一个是**库的级别**，第二个是**表的级别**，第三个是**特定的数据操作级别**。就是把哪个库让他可以操作、哪个表可以单独让他操作、最后对表上的数据赋予增删改查的动作。可以说这个权限控得已经非常细了。

基本权限一共就这几大类。前四大类是**增删改查**四个关键字，代表特定的数据操作；下面的 `CREATE`、`DROP` 指的是对库表有没有创建和删除的权限，那是库表级别的；还有两个特殊权限：第一个是 `GRANT`，指的是你赋予这个用户权限，他也能去给别的用户赋予权限（默认我们都用 root 这个超级管理员账号去赋予权限，但如果给某个账号赋予了这个权限，他也能去给其他账号赋予权限了）；最后一个 `ALL` 代表的是所有的权限。

#### 权限管理的完整生命周期

MySQL 的权限控制具体体现在几个操作上。第一个是**创建用户**，第二个是**赋予权限**，第三个是**回收权限**，还有一个是**删除用户**。

大家能感受到，这几个操作的周期刚好是一名员工从入职到离职的整个过程：员工入职了，你是不是得给人创建一个账号；创完了以后，你是不是得给人家一些相关的、他操作项目所需的权限。你会注意到，随着时间增长，这家伙天天出去打电话、鬼鬼祟祟的，可能要离职了，你是不是得赶紧把权限给他回收，避免他删库跑路；完毕以后你发现他真的离职了，你可以把他的用户直接删掉。这几个我们都要去学习一下。

##### 创建用户

创建用户很简单，通过 `CREATE USER` 写账号、在哪个主机可以访问、最后密码就可以了：

```sql
CREATE USER '赵伟峰'@'localhost' IDENTIFIED BY '密码';
```

这里边的账号和密码没什么好说的，但很多同学对**主机**这块不太理解，我简单解释一下。

我们有一台电脑，这电脑里边装了 MySQL，还装了小海豚这个客户端。其实我就是在同一台电脑中用小海豚连接的这个 MySQL。那这时候假如我创建一个账号，比如就创建赵伟峰这个账号，那这个时候我就可以把后边这个值写成 `localhost`——这个含义就是我在本机上用这个账号。

但是呢，如果有一天，这台电脑我现在是在家放着呢，有一天我去公司了，公司是另外一台电脑。假设公司电脑地址我随便写一个是 `1.1.1.1`，我在公司里边装了一个小海豚，我也期望用赵伟峰这个账号去连我家里边这台电脑上面的 MySQL——这次你就连不上了。因为之前你设置的是 `localhost`，这个账号的使用范围只能在本机使用，你在其他的 IP 地址上就使不了。

**所以这个字段指的是你账号的使用范围。**主机部分可以这么写：

| 写法 | 含义 |
| --- | --- |
| `localhost` | 只能是本机访问 |
| `1.1.1.1` | 固定 IP，只能从这台机器访问 |
| `%` | 任何主机都可以访问 |

如果想在任何位置都可以访问，就写一个百分号，`'账号'@'%'`，这个百分号的含义代表是任何主机都可以访问。

##### 赋予权限

赋予权限的关键字叫 `GRANT`，`grant` 就是"赋予"的意思：

```sql
GRANT 权限列表 ON 数据库.表名 TO '账号'@'主机';
```

可以给一个权限（那就是全部了），也可以给多个权限，多个权限之间用逗号隔开就可以了。最后 `TO` 哪个账号以及哪个对应的地址——**这里有个坑**：你创建用户的时候主机地址怎么写的，这里就得怎么写。创建时写的百分号，这儿就不能写 `localhost` 了，写了不生效。

`ON` 后边的库名表名这里给大家说一下：如果是所有库所有表，可以用通配符 `*`——星号代表"全部"；某一个库的所有表，就写库名，表这块写 `*` 就行。

```sql
GRANT SELECT, INSERT ON test08_other.* TO '赵伟峰'@'%';
GRANT ALL ON *.* TO '赵伟峰'@'%';
```

> **易错点**：**地址位置的通配符是 `%`，库表位置的通配符是 `*`**，这两个别搞反了。上面那个百分号管的是"从哪台机器来"，星号管的是"哪个库哪张表"。

##### 查看用户和权限

先查用户。查询用户是利用 MySQL 自带的一个表，就是 `mysql` 库里的 `user` 表：

```sql
SELECT user, host FROM mysql.user;
```

查到你有哪些账号、每个账号对应的主机是什么。查完之后，想看某个账号具体有什么权限，就用这一条：

```sql
SHOW GRANTS FOR '赵伟峰'@'%';
```

##### 回收权限

回收权限就是 `REVOKE`，跟刚刚的 `GRANT` 做法一样，权限写一个或者写多个都行，写 `ALL` 就是回收全部权限：

```sql
REVOKE INSERT, SELECT ON test08_other.* FROM '赵伟峰'@'%';
```

语法跟 `GRANT` 长得几乎一样，大家就记一个区分点：**赋予是 `TO`——给谁；回收是 `FROM`——从谁那里回收。**

##### 删除用户

最后是删除用户。他要跑路，给他删掉：

```sql
DROP USER '赵伟峰';
```

直接写用户名就行了，不用再写什么主机地址，全删了。

到这里，权限操作相关的几个命令就齐了：创建用户用 `CREATE USER`，赋予权限用 `GRANT`，回收权限用 `REVOKE`，删除用户用 `DROP USER`，查用户查 `mysql.user` 表，查权限用 `SHOW GRANTS`。这些具体的演示，我们放到下一节里一个一个来。

> **承前启后**：上一节讲完「事务怎么手动控制、隔离级别怎么定，以及权限怎么管」，下一节接着讲「权限、备份与 binlog：数据库的三道防线」。

## 权限、备份与 binlog：数据库的三道防线
> 对应块：BLK20 | 覆盖分集：P99-P102 | 块标题（分集名）：《99-数据库高级和新特性-用户权限管理实践》

打开两个 CMD 窗口，我们挨个演示——这一段的演示就是这么开场的。

有权限的那一方，用超级管理员 root，他是什么权限都有的；另一个窗口，是咱们待会儿要建出来的"小赵"。这轮演示就围绕小赵走完一遍：建号、给权限、试边界、收权限、最后销号。走完这一圈，我们再把话头往大了说：数据备份到底是为了什么，误删了又没备份该怎么办。

### 先给一个人开小灶：权限从建号到销号

#### 建号成功，权限还是零

想创建账号，你得先有一个有权限的人，所以第一个窗口用 `mysql -u root -p` 登录 root。现在我在 root 这边想创建"赵伟峰"这个账号——算了，太麻烦，就叫它小赵吧。

```sql
CREATE USER '小赵'@'%' IDENTIFIED BY '123456';
```

这句话其实就三段，拆开看：

```text
CREATE USER   '小赵'   @   '%'   IDENTIFIED BY   '123456';
     │          │       │           │              │
     │          │       │           │              └─ 密码
     │          │       │           └───────────────── 用什么方式验证身份
     │          │       └───────────────────────────── 来自哪台机器
     │          └───────────────────────────────────── 用户名
     └──────────────────────────────────────────────── 建账号
```

`'小赵'@'%'` 里的 `@` 是分隔符，斜杠后面那个百分号就是"任意主机"——写 `%` 表示它在任何位置都能访问；写成具体的 IP 或主机名，就只放行从那儿来的连接。用户名和密码都放在单引号里，密码明文写。

账号建好，小赵当然以为这就能用了。切到第二个窗口：

```bash
mysql -u 小赵 -p123456
```

> **提示**：这里把密码明着写在 `-p` 后面纯粹是为了演示方便，正式环境别这么干。

回车，确实登录成功了。可你一跑 `SHOW DATABASES` 就发现不对——能列出来的只有 MySQL 自带的系统库，其他库一个都看不见。别的库其实都在，只是**他没给你权限**。

> **结论**：账号能登录 ≠ 有权限。`CREATE USER` 只解决了"你是谁"，没解决"你能干什么"。

#### 给一点、试边界、再收回去

那就给他一点。先给 `test08_other` 这个库下所有表的查看权限，查看权限就是 `SELECT`：

```sql
GRANT   SELECT   ON   test08_other.*   TO   '小赵'@'%';
  │       │       │        │            │       │
  │       │       │        │            │       └─ 来自哪台机器，% = 哪都能来
  │       │       │        │            └───────── 给谁
  │       │       │        └──────────────────────  作用到哪张表
  │       │       └───────────────────────────────  作用范围
  │       └───────────────────────────────────────  授什么权
  └───────────────────────────────────────────────  授权
```

`ON` 后面的层级要说清楚：写具体的表名就是精确到那一张表，写星号 `*` 就是这个库里所有的表。末尾打分号，权限就给出去了。

> **易错点**：命令里说的 `GRANT` 是拼写，不是"GRINT"。

不过给完权限别急着在小赵窗口里试——**权限是存在服务端内存里的，得刷新一下，或者干脆退出重连一次**。退出重连之后再 `USE test08_other;` 一 `SHOW TABLES;`，那两张表就都露出来了。跟着 `SELECT * FROM t_bank;` 也能查出数据了。

那能查，能不能删？我在小赵窗口里手欠一下：

```sql
DELETE FROM t_bank;
```

回车——报错，说我没有执行这个删除命令的权限。这就对了："新入职的我只能让你看数据，我还能让你删数据吗？"

随着时间深入，发现这小伙还挺可靠，那就再给他加一条插入权限，道理完全一样：

```sql
GRANT INSERT ON test08_other.* TO '小赵'@'%';
```

这回插入又报错了——别慌，还是那个老问题，**权限没刷新**。退出重连之后再执行 `INSERT INTO t_bank VALUES ( ... );` 就成了；而 `DELETE` 试了还是没权限。

> **结论**：权限是一项一项给的。只给 `SELECT`，那就只能查；再补一个 `INSERT`，才能插；从头到尾没给过的 `DELETE`，永远都是错的。

现在我不想要他查看了，想把查看权限**回收**掉。回收用 `REVOKE`：

```sql
REVOKE SELECT ON test08_other.* FROM '小赵'@'%';
```

回收完退出重连，再 `SELECT * FROM t_bank;`——这回连查询权限都没了。

> **易错点**：`GRANT` 结尾是 `TO`（给谁），`REVOKE` 结尾是 `FROM`（从谁那里收回），这两个别写反。

最后一天他天天打电话要面试、要跑路，形势不对，那就把这个人删了。删用户用 `DROP USER`，而且后面必须写完整的 `'用户名'@'主机'`——我第一次只敲了用户名，服务器直接回一句"没有这个用户"：

```sql
DROP USER '小赵'@'%';
```

改对了之后，让小赵退出再登录，这回连登录都登不上去了，密码错误——因为已经没有小抄的用户了。

到这儿这轮"给人开小灶"就完整走了一遍：建号 → 给 → 试 → 补 → 收 → 销。接下来换话题，讲数据的备份和还原。

### 备份到底是为了什么

所谓备份还原，一句话：把你的数据导成一个外部文件存起来，等以后当有问题了，再通过这个外部文件把数据还原回来。

那这个东西做这事儿干什么？**很多事情就是你得往好的方向做，但是你得做好最坏的打算。** 你有没有一种可能——你那台跑数据库的机器着火了，数据全烧毁了。这时候你才发现备份也没用，因为你备份也备份在那台电脑上。那就别备份到那台电脑啊，你换台电脑备份呢？

所以备份还原的意义，我给大家总结了几点，它并不是单纯"备份"的问题：

- **灾难性恢复**：主机出各种问题，通过备份的数据进行还原；
- **数据迁移**：系统升级了、数据库版本升级了，数据可以迁过去；
- **数据的复制**：拿生产数据在别处复一份。

举个例子。假设我们有一个生产环境上的数据库，真实上线的那种；我本地也想用真实数据做测试。可你不能直接连生产库干啊，那怎么把真实数据拿到本地？你把生产环境的数据备份成一份文件，传到本地，再在本地数据库里导进去——这不就等于把生产上的数据拿到手了。

> **结论**：备份的意义并不是为了容灾，也可能是为了数据的迁移，以及更好地进行开发和测试。

### 全量备份：mysqldump 一条命令

先讲最简单的：全量备份。所谓全量，就是把某一个库，或者某一个库中的某些表，备份到一个外部文件里。

"全量"指的是**不考虑什么时间点**——就只要这个库和表的东西，全部的内容都给我备份出去。备份完这个文件可以传到任何位置，需要的时候再拿它做还原。

用的工具叫 `mysqldump`。这里要特别强调一下：

> **注意**：`mysqldump` 不是 MySQL 命令，它是装 MySQL 自带的一个可执行工具，而且已经配到环境变量里了。所以执行它得用 CMD，不是连到 MySQL 里执行。

命令很简单：

```bash
# 备份单库中的某一张表
mysqldump -u root -p 库名 表名 > D:\xxx.sql

# 备份单库中的所有表
mysqldump -u root -p 库名 > D:\xxx.sql
```

要备份整个库，直接写库名、不写表名就行了，它会把这一个库里所有表的结构和表数据全导出去。

> **结论**：备份的从来不只有数据——建表语句（表结构）是一起被导出来的。

演示一下。我们现在有个 `test08_other` 库，想把这个库中所有表全部备份出去：

```bash
mysqldump -uroot -ptest08_other > D:\test08.sql
```

一般备份出来的文件都叫 `.sql`，所以最后那个文件名带扩展名。回车之后它会冒一条 warning，原因是密码直接写在命令行里了——它推荐你别写在这，回车之后再输密码。

> **易错点**：想写密码就得**紧贴着写**，`-p` 和密码之间不能有空格，`-p 123456` 是无效的。

备份完打开 D 盘就能看到这个文件了。打开看看里面是啥——它备份的东西一点不高端：建表语句给你导出来了，数据呢，被变成了一条条 `INSERT` 语句。那你说什么叫还原？你只要把这些命令整体再执行一遍，不就相当于创建好库、创建好表、又创建插入数据了吗？

> **结论**：`mysqldump` 导出的脚本里**只有 `CREATE TABLE` 和 `INSERT`，没有 `CREATE DATABASE`**。所以还原之前，你得自己先把目标库建好。

那怎么还原？用 `mysql` 客户端：

```bash
mysql -uroot -p 库名 < D:\xxx.sql
```

跟备份正好反着：备份是 `>` 重定向到文件，还原是 `<` 把文件喂给 `mysql`。选项也少，就 `-u`、`-p`、库名这几个。

因为脚本里没有创建库的语句，所以得提前先建好一个空库：

```sql
CREATE DATABASE test08;
```

建好之后这个库里啥都没有，退出登录，再执行上面那条还原命令。回车之后刷新一下——库有了、表有了、表里的数据也全拿过来了。

> **易错点**：跨环境还原，两边的 MySQL 版本必须一致。他用 8.2 你用 8.1，他用 8.0 你用 5.7，那都是还原不了的。大家一定记住这件事。

> **定义**：**全量备份** —— 不考虑时间点，把某一个库、或某库中某些表的全部内容（表结构 + 表数据）一次性导出到一个外部文件。

### 误删了还没有备份：binlog 就是 MySQL 的账本

现在换一个场景，这个场景比备份更让人心慌：开发中一不小心把数据库的数据给删除了，怎么办？而且开发中也没有备份机制，数据也没有备份。

这时候是不慌不慌——应该很慌。我能想到最早之前接触过一个学员，去了一个不小的公司，最后误操作把数据都删了。删了以后你猜他第一反应是干啥的？第一反应就想提桶跑路。跑不了的，你往哪跑。

所以误删数据了怎么办？两步：第一，先看公司有没有及时备份，有的话通过备份文件就能找回数据；第二，**就算没有备份也没关系**，我们可以用一个叫 binlog 的日志把数据找回来。

那什么是 binlog？**MySQL 的二进制日志，它会记录所有数据库增删改查相关的操作，同时也会包括执行时间。** 我们可以利用 binlog 日志进行误删除数据的恢复，以及增量复制、数据同步等等。

`binlog` 这个词不太理解的话，我打个比方。大家看古装片应该都见过这个场景：侠客进了一个酒庄，跟小二说"小二啊，上等的牛肉二斤，再来一坛女儿红"；小二就去上菜了。这个柜台上一般还有个掌柜，掌柜在干嘛呢？掌柜也在记账——今天来了一桌客人，点什么菜，是不是得记下这个账。

```text
        古装片里的酒庄                        MySQL
   ┌───────────────────────┐          ┌───────────────────────┐
   │  侠客报菜名             │          │  客户端发来一条 SQL    │
   │  "上等牛肉二斤、        │          │  INSERT INTO ...       │
   │   一坛女儿红"           │          │                       │
   │          ↓             │          │          ↓            │
   │  小二照单上菜            │          │  MySQL 执行并落盘       │
   │          ↓             │          │          ↓            │
   │  掌柜记一笔账           │          │  binlog 记下一条 event │
   │  "三号桌，牛肉二斤"     │          │  Write_rows, Pos=xxx   │
   └───────────────────────┘          └───────────────────────┘
    晚上对账：柜上银子还剩 12 两         误删了：翻账本找到那条 DELETE
    为何剩 12 两？→ 回去看账本          跳过它，前后照跑，数据就回来了
```

这个记账有什么用？晚上可以用账本复盘。假如今天收了账，柜上银子还剩 12 两，那为什么剩 12 两？因为记账记录了每一个操作的过程。

**binlog 日志，其实就是 MySQL 的一个账本**，它记录了每次数据库的操作。所以就算你误删除了数据，也别怕——你可以把前面的命令再执行一遍，把这条命令跳过，把后边的命令再执行一遍，数据就找回来了。

> **结论**：找回误删数据的本质，不是"把删掉的东西变回来"，而是**把那条删除命令从序列里挑出来不执行，其余命令原样再跑一遍**。binlog 就是那本账。

### 找到 binlog：配置、文件名与两条 SHOW 命令

#### 先确认它开着，知道它叫什么、在哪儿

要用 binlog 恢复，第一步是开启 binlog 支持。好在默认情况下它就是开启的，问题不大。

它的位置在 MySQL 的安装配置文件里。以 Windows 为例，在 `C:\Program Files\MySQL\MySQL Server 8.2` 目录下——注意 `Program Files` 是个隐藏文件夹，你得在文件夹选项里把它显示出来。里面是 `my.ini`，用记事本打开都行。

打开之后往下找，找到 `[mysqld]` 这一段（是 `mysqld`，这个 `d` 千万别漏了，写错了配置就不生效）。

底下有两处跟 binlog 相关的配置要认：

- 一个是**日志的名字**，默认名是主机名（就是你电脑的名字），建议改一个好认的；
- 另一个是**日志的存放位置**，默认缓存在安装目录下的 `data` 文件夹里，这个位置用默认的就行。

```ini
[mysqld]
log-bin = my_log_bin
```

文件名规则是这样的：

```text
   my_log_bin.000001        my_log_bin.000002        my_log_bin.000003
          │                       │                       │
     FLUSH LOGS 之前          FLUSH LOGS 之后         再切一刀
     建库、建表、插数据        删除 + 后续的操作         ……
   后缀是六位序号，前五位是零，从 000001 开始
```

到 `data` 目录下打开就能看到这些文件了——你在那儿还能同时看到改名前的老文件，因为默认那一份是以主机名命名的。

> **注意**：这些文件是二进制文件，**不是文本文件**，用记事本这类工具根本看不了，得用专门的工具去看。这个我们第一步就说到了，一会儿再讲用哪个工具。

#### 造两段日志，把"删除"夹在中间

要演示找回数据，得先造一批数据出来。这一步的整个结构是**刻意设计**的：

```text
   RESET MASTER 之后
          │
          ▼
   my_log_bin.000001  ──  CREATE DATABASE test08_blog
   （一个空文件起步）        USE test08_blog
                            CREATE TABLE table_01 (id, name)
                            INSERT 二狗子、驴蛋蛋
                          ── FLUSH LOGS 从这里切一刀 ──
   my_log_bin.000002  ──  DELETE  id = 2       ← 驴蛋蛋没了
                            INSERT  id = 3
                            SELECT *
                            INSERT  id = 4
```

具体第一步，先来一条命令把原有的 binlog 日志文件清空：

```sql
RESET MASTER;
```

> **结论**：这一条会把之前所有日志都清掉。执行完，原来那个 000002 被删掉，只留下一个 000001——而且这个 000001 里面一条命令都没有，纯粹就是新建了一个空文件。相当于一切从零开始记。

然后在 000001 里建库、建表、插两条数据（二狗子和驴蛋蛋）：

```sql
CREATE DATABASE test08_blog;
USE test08_blog;
CREATE TABLE table_01 (id INT, name VARCHAR(20));   -- 就 id、name 两列
INSERT INTO table_01 VALUES (1, '二狗子');
INSERT INTO table_01 VALUES (2, '驴蛋蛋');
```

写完这批，再来一条：

```sql
FLUSH LOGS;
```

> **结论**：`FLUSH LOGS` 只是创建一个新的日志文件。执行完就会出现 `my_log_bin.000002`，后续所有操作都自动记录到这个新文件里。

000002 里记的是这么几件事：先 `DELETE` 掉 `id = 2` 那条（驴蛋蛋就这么没了），再插一条 `id = 3` 的数据，然后 `SELECT *` 查一下这个表，接着又插一条 `id = 4` 的数据。

我们的目标就很明确了：**把中间那条被误删的驴蛋蛋找回来**。

> **提示**：为什么非要整两个日志文件，不整一个？——增加点难度嘛，对不对。

#### 两条 SHOW 命令读清单和坐标

那怎么知道到底有哪些日志文件、每个文件里记了哪些命令呢？笨办法就是去 `data` 目录里翻，但我给大家两条命令，一条比一条省事：

| 命令 | 作用 |
| --- | --- |
| `SHOW BINARY LOGS;` | 列出当前所有 binlog 文件及其大小（表格形式） |
| `SHOW BINLOG EVENTS;` | 查看日志文件里记录了哪些命令的**清单** |

```sql
SHOW BINARY LOGS;
```

执行完能看到两个文件：`my_log_bin.000001` 和 `my_log_bin.000002`。前面是名字，后面是 Size——每切一次日志，它就涨一截。

要看某个具体文件里都有啥：

```sql
SHOW BINLOG EVENTS;                                  -- 默认看第一个
SHOW BINLOG EVENTS IN 'my_log_bin.000002';           -- 指定看第二个
```

> **注意**：这里看的是**命令清单**，不是命令细节。清单就是把完整日志里的关键字截出来给你看。

000001 的清单里全是建库、建表、插入数据这类命令，最后还有一条开启新日志的记录。000002 里就清爽多了：一条 `DELETE`（删数据）、一条 `INSERT` 值 391、一条 `INSERT` 值 706，一目了然。

清单里每一行后面还跟着一串位置信息，这几个字段一定要认：

```text
  事件类型        对应的操作        Pos          End_log_pos     Server_id
 ─────────────────────────────────────────────────────────────────────────
  Query           创建表结构        507          5xx             1
  Write_rows      往表里写数据      ...          ...             1
  Delete_rows     删除数据          391          441             1
                                   ↑            ↑
                              命令开始坐标   命令结束坐标
```

`Pos` 是这条命令开始的坐标（对照清单你就能看出来，比如那条创建表结构的命令是从 507 这个位置开始的）；`End_log_pos` 是它结束的坐标；`Server_id` 表明这条来自哪个 MySQL 服务。

你只要大概能读懂事件类型这一列、能看出后边大概干了啥就够了。但**位置信息必须记住**——下一步恢复数据，全靠它。

> **提示**：不想看全部、只看某条之后的几条，也是支持的：

```sql
SHOW BINLOG EVENTS IN 'my_log_bin.000002' FROM 391 LIMIT 2 OFFSET 0;
```

`FROM 391` 就是从 391 这个坐标开始查；`LIMIT` 写要查几条；`OFFSET` 写 0，表示就从这个坐标开始算——跟分页里的关键字是一个效果。查出来正好是那条删除后面的那几条。

### 用 mysqlbinlog 跳过删除，把数据找回来

#### 思路：不是"恢复"，是把命令重新归位

先想一个问题：什么叫误删除数据恢复？它跟日志文件到底有什么关系？

就拿刚刚的例子：那条删除命令，前面有建库、建表、插入数据等一堆命令，后面也还有一堆命令，这一整套加起来才是完整的操作。现在我突然发现那条删除是误操作、我不想执行它——那怎么找回数据？

这里要特别提醒一句：**把所有命令原样再执行一遍，数据照样是被删掉的。** 所以真正要做的是把命令重新归位：

```text
   误删之前的完整操作序列
   ├─ CREATE DATABASE test08_blog
   ├─ CREATE TABLE table_01
   ├─ INSERT 二狗子
   ├─ INSERT 驴蛋蛋
   ├─ DELETE 驴蛋蛋   ← 丢掉这一条，不导出
   ├─ INSERT 391
   ├─ SELECT *
   └─ INSERT 706
        │
        │  掐掉 DELETE，两头分开导
        ▼
   bin001.sql   ← 000001 整段
   bin002.sql   ← 000002 开头 … 391
   bin003.sql   ← 000002 441 … 末尾
        │
        ▼
   三个脚本依次执行 ──►  驴蛋蛋回来了
```

所以你挑出来的是这么几样：删除之前的其他命令全部；那条删除命令——肯定不挑，我就要它丢掉；再把删除之后剩下的命令也拿过来，因为后面可能还有插入数据等别的操作。最后把这些东西拼成一个 SQL 脚本，执行一遍，误删的数据就回来了。

> **结论**：所谓的"找回数据"，就是让那条删除命令不执行，剩下的所有命令再执行一遍。

#### 工具：mysqlbinlog，不是 SQL 命令

这里要用一个工具叫 `mysqlbinlog`。它跟 `mysqldump` 一样，是装完 MySQL 就自带的工具，**不是 MySQL 的一个 SQL 命令**。它有两个作用。

第一个作用，是能查看 binlog 日志的**内容细节**：

```bash
mysqlbinlog -v my_log_bin.000002
```

写一个 `-v` 是详细，写两个（`-vv`）信息更多。跟前面 `SHOW BINLOG EVENTS` 的区别在于：那个看的是被截取过关键字的清单，这个看的是具体的内部内容。不过这个平时没什么意义，知道怎么用就行。

> **提示**：`mysqlbinlog` 和 `mysqldump` 一样，得**在 CMD 里执行**，跟 `mysql -u ... -p` 那个连接不是一回事。而且它默认读的是当前目录下的文件，所以执行前先把 CMD 定位到 `data` 目录，命令里就能直接写相对文件名了。

第二个作用，才是真正的重点：**把 binlog 日志文件导成 SQL 脚本，而且能指定从哪个位置导、到哪个位置停。** 我们在清单里看过的那个 `Pos`，就是干这个用的。

#### 导出：三个脚本，掐头去尾避开那条 DELETE

先把坐标摆出来。用 `SHOW BINLOG EVENTS IN 'my_log_bin.000002'` 查一下就知道：那条 `DELETE` 的 `Pos` 是 391，它的 `End_log_pos` 是 441——也就是说，391 是它的起点，441 就是删除之后下一条事件的起点。

然后分三段导出：

```bash
# ① 000001 里没有删除，整段导出，一个位置都不用指定
mysqlbinlog my_log_bin.000001 > D:\bin001.sql

# ② 000002 导出到删除之前为止，在 391 停
mysqlbinlog --stop-position=391 my_log_bin.000002 > D:\bin002.sql

# ③ 000002 从删除之后开始，441 起
mysqlbinlog --start-position=441 my_log_bin.000002 > D:\bin003.sql
```

`--stop-position` 是"到哪停"，`--start-position` 是"从哪开始"。参数挺多的，但常用的其实就这两个，其他的你记不住也没关系。

> **易错点**：文件名里的分隔符是**下划线**，不是中划线。`my_log_bin` 写成 `my-blog-bin` 会直接给你一个 `No such file`。我现场就踩了这个坑——都到误删除数据的时候了，这一步你得比平时更细一点。

> **注意**：导 002 的时候它会报一条 warning（没有指定销毁时间之类的），不用管，那只是警告不是错误。

> **结论**：为什么是三个脚本？第一个是完整的 000001；第二个是 000002 里删除之前的部分；第三个是 000002 里删除之后的部分。中间那条 DELETE 两头都不带，天然就被跳过了。

真实的误删恢复啊，其实挺麻烦的，并不像我们想象中那么简单。假如说你误删除的数据有七八条，还散落在不同的日志文件里，那你就得一段一段地切。但至少能找回。

#### 收尾：依次执行，驴蛋蛋回来了

打开 D 盘，三个脚本都躺在这儿了。先拿第一个试试，直接执行：

```bash
mysql -uroot -p < D:\bin001.sql
```

结果报错：不能创建 `test08_blog`，因为它已经存在。

> **结论**：这个报错恰好说明了一件事——`mysqlbinlog` 导出的脚本是**自带 `CREATE DATABASE` 语句的**。这一点跟 `mysqldump` 完全不同：`mysqldump` 只给建表和插入，所以还原前得自己先建库；而 binlog 脚本自带建库，所以目标库必须先不存在。

那就把整个库删掉，再依次执行这三个脚本。第一个执行完，库表结构就有了，`table_01` 里是二狗子和驴蛋蛋；接着执行删除之前的那一段和删除之后的那一段，最后一刷新——驴蛋蛋找回来了。

> **结论**：整个过程说白了就是用 `mysqlbinlog` 把日志文件里删除步骤的前后两段分别导成脚本，再把它们恢复还原一遍。就是把删除那一步跳过去了。

这套 `start-position` / `stop-position` 还能干别的：假如我从今天这个时间节点开始，截取到剩下的日志文件，拿它做一个增量更新也都是可以的。

> **承前启后**：上一节讲完「权限、备份与 binlog：数据库的三道防线」，下一节接着讲「窗口函数与十道综合查询」。

## 窗口函数与十道综合查询
> 对应块：BLK21 | 覆盖分集：P103-P106 | 块标题（分集名）：《103-数据库高级和新特性-窗口函数概述和理解示》

接下来这一节，讲 MySQL 8 以后的两个非常重要的新特性，先讲第一个：窗口函数。

窗口函数这个概念并不是 MySQL 专有的，其他数据库中很多都支持，只不过 MySQL 一直到 8 以后才支持。

### 窗口函数到底解决什么问题

先不用急着弄明白它是什么，先弄清楚它能干什么。它的作用就是：**允许你在结果集上执行聚合、分析、排序这些相关操作的同时，不改变结果的行数。**

这句话什么意思？之前讲过单行函数和多行函数，多行函数当时只讲了聚合函数，当然还有很多别的。只要你一旦用上多行函数，返回的结果就不能是多条了，它会直接帮你压成一条。也就是说，聚合这类多行函数只能单独使用，没办法跟正常要查的列混在一起。

有了窗口函数就不一样了：你在查单条数据的时候，可以顺带把多行函数的结果也带出来。它不会把所有数据压缩成一行，而是把这个结果分散到各个单行里去体现。大家现在可能还不太理解，没关系，我们通过练习做一遍就懂了。

```text
  聚合函数：多行 → 一行
    10 行明细 ──AVG(price)──▶ 1 个值
    还想同时查 id、name、price？不行，只能 GROUP BY 之后取分组列

  窗口函数：多行 → 每行都挂一份
    10 行明细 ──AVG(price) OVER()──▶ 还是 10 行，每行后面挂着同一个平均值
    id、name、price 一条都不少，行数也一条不多
```

窗口函数应用的场景就是多行函数。除了之前讲的聚合函数，像平均值、最大值这些，还有几个比较重要的多行函数：

- **序号函数**：获取数据的排列序号、第几名。假如有一张分数表，想查出考试分数排在第几名，就靠它，最后能造出一个序号列；
- **分布函数**：你的分数在排名的位置是前百分之多少还是后百分之多少；
- **前后函数**：取当前行的前 n 行或后 n 行的数据；
- **首尾函数**：取第一行或者最后一行的数据。

这些多行函数，加上之前学的聚合函数，都可以额外去应用窗口函数。

> **提示**：窗口函数有点像一层**包装和加工**——它自己不改变数据的粒度，只是把多行函数算出来的结果，"加工"进每一行单行数据里。

具体怎么写？语法就这么点东西：先加一个多行函数，后面加一个 `OVER` 就可以了。只要加上这一段，多行函数就可以在单行中去显示。

```sql
多行函数() OVER (PARTITION BY 列名 ORDER BY 列名 DESC/ASC)
```

括号里现在是空的也行，后面也可以先声明一个窗口然后复用，这个稍后单独解释。

### 搭一张商品表，把窗口函数跑起来

光说没用，我们建表跑一遍。打开客户端，先准备一个商品表 `goods`，里面是 id、类别、商品名、价格，另外还有库存、上架时间这些字段，先把测试数据插进来。

第一个需求：查询所有商品的编号、名称、价格、类别，以及**整体的平均价格**。

先写正常的单表查询，返回的当然是多条：

```sql
SELECT id, name, price, category FROM goods;
```

那整体平均价格怎么查？之前做过，就是：

```sql
SELECT AVG(price) FROM goods;
```

聚合函数是对整体统计，返回一条数据。现在问题就来了：前面的查询返回多条，聚合返回一条，而需求是**既要前面的单条数据，又想要一个整体平均值**——这俩是矛盾的。真要直接拼一起：

```sql
SELECT id, name, price, category, AVG(price) FROM goods;
```

这样会报错。因为一旦用了 `AVG()`，还想查其他列，那被查的列只能是分组列，或者是聚合函数本身，放不了多个普通列。

这时候就该窗口函数出场了，只要在后面加上 `OVER()` 就行，括号里什么都不用写。**这句话的含义就是：把这个值分散到多个行中。**

```sql
SELECT id, name, price, category, AVG(price) OVER() FROM goods;
```

执行一下，整体的平均价格就出来了。整体算完之后，每一行都会体现它。

再来一个新需求：查询商品编号、价格、类别，以及**该商品所属类别对应的平均价格**，而不是整体平均价格。这里还是聚合函数，只不过不是算整体，而是算类别对应的平均值：

```sql
SELECT id, name, price, category, AVG(price) OVER(PARTITION BY category) FROM goods;
```

执行结果：按类别分组后，女装/女士精品这一组算出来是 121，户外用品那一组是 593。它会按照当前商品对应的类别去分组，所以 `PARTITION BY` 其实就是**分组统计**。

```text
  整体平均价：AVG(price) OVER ()
    id  name   price  category   平均价
     …    …      …     女装        121      ← 每行都挂同一个整体平均值
     …    …      …     户外        121

  类别平均价：AVG(price) OVER (PARTITION BY category)
    id  name   price  category   平均价
     …    …      …     女装        121      ← 女装这一组自己的平均
     …    …      …     户外        593      ← 户外这一组自己的平均
```

`ORDER BY` 也很好理解：如果你还想在最终结果里按类别的价钱做倒序或者正序排列，就再在后面加 `ORDER BY 列名 DESC` 或者 `ASC`。至此窗口函数的基本概念就齐了。

> **易错点**：`PARTITION BY` 决定"分组统计"的口径，`ORDER BY` 决定"组内怎么排"。求类别平均价只需要前者；一旦再加 `ORDER BY price DESC`，序号函数、排名的含义就跟着变了。

### 序号函数：ROW_NUMBER、RANK 与 DENSE_RANK

第一个讲序号函数。所谓序号函数，就是把条数按照某一指标进行排序、造出一个序号列。

第一个是 `ROW_NUMBER()`，用于对数据进行排序。需求是：查询商品表中每个商品在**分类下**按价格降序的序号。也就是把这些商品在各自的类别里从 1 排下去，户外用品也自己从 1 排下去，按类别范围内的序号来，同时还要考虑价格降序。

还是先写基础查询：

```sql
SELECT id, category, name, price FROM goods;
```

接下来想排序，写上：

```sql
SELECT ROW_NUMBER() OVER() AS num, id, category, name, price FROM goods;
```

如果直接写 `OVER()`，代表对**整体**数据排序，序号就是 1 到 10，跟 ID 是一样的。

现在需求是按类别排序，也就是按类别分组、排类别组里面的序号：

```sql
SELECT ROW_NUMBER() OVER(PARTITION BY category) AS num, id, category, name, price FROM goods;
```

执行之后就是按照组排下去的序号。接着要求按价格降序，从大到小，在后面加上 `ORDER BY`：

```sql
SELECT ROW_NUMBER() OVER(PARTITION BY category ORDER BY price DESC) AS num,
       id, category, name, price
FROM goods;
```

这样 ID 为 6 的商品价格最高，就排在第 1，这就是 `ROW_NUMBER()` 的用法。**不管价格是否相同，它都是按照连续的序号排下来的。**

有了序号就有用武之地了。下一个需求：查询每个商品分类下价格最高的三种商品。把刚才那条查所有分类内排序的查询当成一个中间表，最外层筛选出序号小于等于 3 即可：

```sql
SELECT * FROM (
    SELECT ROW_NUMBER() OVER(PARTITION BY category ORDER BY price DESC) AS num,
           id, category, name, price
    FROM goods
) AS t
WHERE num <= 3;
```

这就相当于查出了每个商品分类里面排名前三的商品。

> **提示**：这个"先算出带序号的中间结果，再在外面筛 `num <= 3`"的套子，后面还会再遇到一次。记住它，是因为窗口函数算出来的那一列，在当前这层查询的 `WHERE` 里是**用不了**的。

接下来是 `RANK()`。`RANK()` 排序会**跳过重复序号**：如果有价格相同的，比如第二名并列有两个，后面跳过的就直接是第四名。这就像平时考试排名——第一名有一人，第二名有三人并列，那后面就没有第三名和第四名了，直接从第五名开始。

用法就是把函数换成 `RANK()`：

```sql
SELECT RANK() OVER(PARTITION BY category ORDER BY price DESC) AS num,
       id, category, name, price
FROM goods;
```

如果只看其中一个类别，排序结果就是 1、2、2、4：因为有两个都是 2，所以跳过了 3，直接到 4。

而 `DENSE_RANK()` 则是连续的，即便有并列第二，后面紧跟着还是第三，排序就是 1、2、2、3。

| 函数 | 排序列出现并列时 | 并列第二时的排序结果 |
| --- | --- | --- |
| `ROW_NUMBER()` | 不管价格是否相同，一律连续编号 | 1、2、3、4、5、6 |
| `RANK()` | 并列共享名次，后续名次跳过 | 1、2、2、4 |
| `DENSE_RANK()` | 并列共享名次，后续名次紧跟 | 1、2、2、3 |

**到底用哪个，就看你想不想"占位"**：要严格的前 N 名就用 `ROW_NUMBER()`（并列也各占一个名额），要"和第几名同分"的名次就用 `RANK()` / `DENSE_RANK()`。

### 分布函数与窗口的复用

接下来看分布函数，主要看 `PERCENT_RANK()`。分布函数指的是**在范围内的百分比**，它的值在 0 到 1 之间。

假如考试有四个人的分数：80 分、90 分、100 分、70 分。那 100 分的值是多少？公式是：

$$\frac{\text{rank} - 1}{\text{rows} - 1}$$

按排名来说，100 分排第一名，$(1 - 1) / (\text{rows} - 1) = 0$，所以 100 分是 0，是最靠前的。90 分排第二名，$(2 - 1) / (4 - 1) = 1/3 \approx 0.33$。它算的就是你在整批数据里的分布范围。

来看具体的 SQL：查询货物表中女装类别下商品的 RANK 值及百分比分布。

```sql
SELECT
    id, category, name, price,
    RANK()      OVER w AS rk,
    PERCENT_RANK() OVER w AS pr
FROM goods
WHERE category = '女装/女士精品'
WINDOW w AS (PARTITION BY category ORDER BY price DESC);
```

第一位是 0；第二高价格这一组总共 6 个数，$(2 - 1) / (6 - 1) = 1 / 5 = 0.2$；接着是 0.6、0.8、1。这就计算出了分布的范围值，**值越小，证明越靠前**。

| 名次 rank | 公式 (rank-1)/(rows-1) | 百分比分布 |
| --- | --- | --- |
| 1 | (1-1)/(6-1) | 0 |
| 2 | (2-1)/(6-1) | 0.2 |
| 4 | (4-1)/(6-1) | 0.6 |
| 5 | (5-1)/(6-1) | 0.8 |
| 6 | (6-1)/(6-1) | 1 |

> **注意**：0.2 之后直接跳到 0.6，不是 0.4——因为第二名有并列，`RANK()` 把名次跳到了 4。分子里的 `rank` 用的是 `RANK()` 的名次，所以 `PERCENT_RANK()` 和 `RANK()` 一定要成对使用。

这里还顺便用到了**第二种语法：窗口的复用**。如果两个窗口函数的 `OVER` 里面的写法完全一样，写两遍太冗余，就可以复用：在最后面声明一个 `WINDOW w AS (PARTITION BY ... ORDER BY ...)`，然后在前面直接写 `OVER w` 就可以了。这就是窗口定义的复用。

### 前后函数与首尾函数

除了分布函数，还有前后函数。前后函数顾名思义：返回当前行的前 $n$ 行数据，或者返回当前行的后 $n$ 行数据。

需求：查询货物信息表中前一个商品价格与当前商品价格的差。不仅要查当前的价格，还要查跟上一个商品的价格差。

```sql
SELECT
    id, category, name, price,
    LAG(price, 1) OVER w               AS pre_price,
    price - LAG(price, 1) OVER w       AS diff_price
FROM goods
WINDOW w AS (PARTITION BY category ORDER BY price ASC);
```

`LAG(price, 1)` 里，第一个参数代表要获取哪个字段的值，第二个参数 1 代表前一个，写 2 就代表前两行。如果没有前一行就是 `NULL`。这就是用来取某一列的前几行值。

同理，`LEAD()` 则是取后几行的值。

还有首尾函数：`FIRST_VALUE()` 和 `LAST_VALUE()`，分别代表取第一行的值和最后一行的值。按照价格排序查询第一个商品的价格信息，就是使用 `FIRST_VALUE()`。

到这儿窗口函数就讲完了。**大家一定要把讲到的这几个例子亲自练一遍**，光看是记不住的。

### 实战前的四张表

课程最后，迎来一个数据库的综合实战练习，用它来检验一下掌握情况。一共准备了四张表：员工表、部门表、薪资表以及经理表。

先看字段：

- **员工表 employees**：员工 ID、员工姓名（分成 `first_name` 和 `last_name` 两列）、所属部门 ID；
- **部门表 departments**：部门 ID、部门名称；
- **薪资表 salaries**：员工 ID（主外键）、员工对应的薪水；
- **经理表 managers**：经理 ID、部门 ID，代表这个部门的经理是谁。

```text
  employees                          departments
  ├ employee_id  员工 ID               ├ department_id    部门 ID
  ├ first_name                          └ department_name  部门名称
  ├ last_name
  └ department_id ──────────────────────────────┐
        │                                        │ department_id
        │ employee_id                           │
        ▼                                        ▼
  salaries                            managers
  └ salary  薪水                       ├ manager_id     经理 ID
                                          └ department_id 部门 ID
                                                │
                                                └─► manager_id 回到 employees
                                                   查这个经理本人的姓名
```

> **结论**：`managers.manager_id` 看起来是"经理 ID"，但它**本质上是经理这个人的员工 ID**。所以经理的姓名不在 managers 表里，得拿它回到 employees 表去拼 —— 这是后面第二道题的钥匙。

先执行建库建表语句，执行完毕后熟悉一下表结构。然后我们一道一道来。

### 实战的前五题

#### 每个部门的平均工资

需求是显示部门信息以及部门的平均工资。

先分析需要查哪些表。很明显，只有员工才有薪水，所谓"部门的平均薪资"，实际上是**员工按部门分组后的平均薪资**。所以数据来自 employees 和 salaries 两张表。

语法上有两个要点：第一，要用多表连接查询，把员工表作为逻辑主表；第二，要算部门的平均工资，就得再加分组查询——而分组查询只能查分组字段和聚合函数。

```sql
SELECT
    e.department_id,
    AVG(s.salary) AS avg_salary
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
GROUP BY e.department_id;
```

这样就查出了每个部门的平均工资。如果还想要部门的名称，就再 `LEFT JOIN` 一次部门表：

```sql
SELECT
    d.department_name,
    AVG(s.salary) AS avg_salary
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
LEFT JOIN departments d ON e.department_id = d.department_id
GROUP BY d.department_name;
```

执行之后就查出了各个部门的平均工资。由于用的是左外连接，没有分配部门的员工对应的平均薪资也能统计出来。第一题就这么完了。

#### 每个部门的经理姓名与部门人数

第二道题比较难，我们来看看怎么查。

需求是：查出每个部门的经理的姓名，以及他管理的部门的员工的数量。

**这里有一条很好用的经验：只要需求里出现"每"这个字，一般都会涉及分组。** 因为以什么为单位，它就"每"嘛。所以先不想员工数，先只查每个部门以及部门对应的经理名称。

那这个怎么查？回头看 managers 表：一号部门的经理是谁？是 id=1。这个 1 虽然叫经理 ID，但它同时也是经理的员工 ID。也就是说，**一号部门的经理，其实就是员工表里编号为 1 的那个人**，他那 `first_name` 和 `last_name` 合到一起，就是一号部门经理的名字。

所以会涉及到三张表联查：拿部门表去关联经理表，再拿经理表的 `manager_id` 去关联员工表的员工 ID。先查前两步：

```sql
SELECT *
FROM departments d
LEFT JOIN managers m ON d.department_id = m.department_id
LEFT JOIN employees e1 ON e1.employee_id = m.manager_id;
```

到这里，已经查出了"部门 + 部门对应的经理"。

那接下来要查这个部门对应的员工怎么办？**再拿员工表连接一遍**——员工表里有 `department_id`，再去连一次，就知道这个部门里有哪些员工了：

```sql
LEFT JOIN employees e2 ON e2.department_id = d.department_id
```

> **注意**：这里 `managers` 只用了一次，但**`employees` 用了两次**——`e1` 是当"经理"用的，`e2` 是当"普通员工"用的。同一张表在一个查询里可以起多个别名，各司其职。

现在要出最终结果了：查每个部门、部门的经理名字，以及该部门人数。

经理的名字由 `first_name` 和 `last_name` 两列组成，我们学过字符函数 `CONCAT`，把两个字符串拼到一起就是它：

```sql
SELECT
    d.department_name,
    CONCAT(e1.first_name, e1.last_name) AS manager_name,
    COUNT(1)                            AS num
FROM departments d
LEFT JOIN managers  m  ON d.department_id = m.department_id
LEFT JOIN employees e1 ON e1.employee_id = m.manager_id
LEFT JOIN employees e2 ON e2.department_id = d.department_id
GROUP BY d.department_name, CONCAT(e1.first_name, e1.last_name);
```

`COUNT(1)` 就是一个部门的人数。

不过第一次跑出来的数是有点瑕疵的，我们现场 debug 一下。盯着 `manager_name` 这一列看——**同一个部门的经理名字怎么都不一样呢？** 顺着往回找，明白了：拼名字的时候两个参数都写成了 `e1.first_name`，等于把每个员工自己的名字拼了两遍。改回 `first_name`、`last_name` 之后，一号部门 3 个，二号部门 2 个，就对上了。

> **易错点**：`CONCAT` 的参数写错，名字就拼错，名字一错，分组就跟着错——因为分组是按这个表达式来的。这个 bug 特别隐蔽，因为 SQL 不会报错，只会给你一个"看起来挺像那么回事"的错误数字。

还有同学会问：既然同一个部门的经理是一样的，那 `department_name` 和 `manager_name` 数值上完全相同，我拿一个分不就行了吗？我们试一下，只 `GROUP BY d.department_name` —— 果然报错，说 `manager_name` 不能用。

原因还是那句老话：**一旦分组，SELECT 里就只能查分组字段和聚合函数。** 所以这两个值虽然相同，只要你想在结果里 `SELECT` 它们，就必须两个都写进 `GROUP BY`，哪怕写两遍是多余的，也得写。记住了吗？

#### 没有分配部门的员工数量

这题是送分题。需求是罗列出没有分配部门的员工数量，本质上就是一个 `NULL` 判断，单表查询直接写：

```sql
SELECT COUNT(*)
FROM employees
WHERE department_id IS NULL;
```

> **易错点**：空值不能用等于号判断，`NULL = NULL` 的结果是 `UNKNOWN` 而不是 `TRUE`，要写 `IS NULL`。

#### 每个部门的员工数量与平均工资

需求是查出每个部门员工的数量以及该部门的平均工资。这个对我们来说就简单了。

先想数据来自哪：员工表里有部门，能查部门人数，但没有工资，所以还是拿员工表关联一下工资表，关联完再做一个聚合函数。这个写法比较简单，问题是肯定还是要分组。

先查所有数据看看：

```sql
SELECT *
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
```

查到了之后，再做聚合就完事了。按部门分：

```sql
SELECT
    e.department_id,
    AVG(s.salary) AS avg_salary,
    COUNT(1)      AS num
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
GROUP BY e.department_id;
```

一分组就只能查分组字段 `department_id` 和聚合函数，所以要查的东西只能往 `AVG(s.salary)`、`COUNT(1)` 里塞。执行一下，效果就出来了。

#### 每个员工的姓名与薪资等级

第五题：查询每个员工的姓名以及他的薪资等级。

题目里说的是薪资等级，但员工表只有姓名和部门 ID，哪来的薪资等级？往下看条件就明白了：**低于平均工资的是低档，高于平均工资的是高档。**

那我要查的列就清楚了：员工 ID、姓名（`first_name` + `last_name`）、还有薪水等级。薪水等级要跟什么比？跟平均薪水比。

那这里就要用到之前讲过的**流程控制语句 `CASE WHEN`**。但这里有个细节大家一定要知道：我们要拿每个员工的信息，同时还要比较**平均薪水**。平均薪水可不是闹着玩的，它是聚合函数；按理说聚合函数只能单独使用。可如果想在每条记录里都拿到聚合函数，还记得怎么做吗？

**对，最后讲的窗口函数。** 这里需要窗口函数加上流程控制。如果你理解了这一点，那就好写了。

先把前置的东西写出来：

```sql
SELECT *
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id;
```

要先查到员工和薪水，然后要啥就拿啥：员工 ID `e.employee_id`，员工名用 `CONCAT(e.first_name, e.last_name)` 拼出来，再把薪水 `s.salary` 也查出来。接下来是薪水等级，用 `CASE WHEN`，把整体的平均薪水套上窗口函数：

```sql
SELECT
    e.employee_id,
    CONCAT(e.first_name, e.last_name) AS name,
    s.salary,
    CASE
        WHEN s.salary < AVG(s.salary) OVER() THEN '低档'
        ELSE '高档'
    END AS salary_level
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id;
```

`CASE` 有两种写法，一种是在 `WHEN` 里面直接带条件，一种是先写一列再比。这里用的是前者：工资小于平均薪水就 `THEN` 一个"低档"；剩下的不用再写 `THEN` 了，用 `ELSE` 兜底就行，叫"高档"。

`END` 这里要注意：如果你把 `CASE` 整体当一个值用，后面就不用写列名了；如果想让它作为结果里的一列，就在 `END` 后面 `AS` 一个列名，这里我们叫 `salary_level`。

> **注意**：这里用的是 `ELSE` 兜底，所以工资正好等于平均值的人也会被算进"高档"这一档。如果业务上要把相等的情况单独拎出来，就把 `ELSE` 换成一个显式的 `WHEN s.salary > 平均值`，剩下的再兜底。

再说 `AVG(s.salary)`：平均值谁都会写，`AVG(salary)` 就行了。但它是聚合函数，没有办法直接这么用。想用怎么办？**你得用窗口函数才能用，加上 `OVER()`。** 虽然这里既没有分组也没有 `ORDER BY`，但你也要加窗口函数，否则就是用不了。忘了就回头看看窗口函数那节。

> **易错点**：`CASE` 表达式后面要跟一个逗号，漏了逗号会直接报语法错，就在 `case` 附近。

跑一下，低高档别就查出来了。先练到这儿，休息一会儿。

### 实战的后五题

休息完了，我们来"绝杀"后五题，还是一条条来看。

#### 薪资排名前十的员工

需求：查出薪资排名前十的员工信息。

这个又是基本连表查询，员工表和薪资表，因为员工表里没有薪水。排前十，那肯定要有排序，按薪水的倒序 `DESC`，最后拿前十个，用 `LIMIT` 去切割——这就练到了高级查询的处理。

```sql
SELECT *
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
ORDER BY s.salary DESC
LIMIT 10;
```

写完 `JOIN` 以后，后边该有的高级处理还是得有：排序就写 `ORDER BY`，取前十个就写 `LIMIT 10`。语法是完全正确的，虽然数据一共没十条。

如果只想拿前三名，就把 `LIMIT 10` 改成 `LIMIT 3`；如果想拿薪资第二多的，那就 `LIMIT 1, 1`——跳过 1 个，再取 1 个。

#### 至少有两名员工的部门

需求：查出至少有两名员工的部门。也就是按部门分组，最终这个部门的员工数量要不少于 2。

先看条件放在哪。条件我们已经讲过有 `WHERE`、`ON`，现在是第三个了：**`HAVING`**。

- `ON` 里一般放主表与外键表的连接条件；
- `WHERE` 是**分组前**的条件；
- `HAVING` 紧跟着 `GROUP BY`，做的是**分组后**的条件。

这道题显然是分组后条件——分组以后你才知道哪个部门有几名员工，对吧？

先写正常部分，按 `department_id` 分组，一分组就只能查分组字段和每组中的聚合函数了：

```sql
SELECT
    e.department_id,
    COUNT(1) AS num
FROM employees e
GROUP BY e.department_id;
```

先执行一下，看看每个部门的员工数量。查出来以后要过滤，注意 `num` 不用再写一遍，它可以在 `HAVING` 里直接复用：

```sql
SELECT
    e.department_id,
    COUNT(1) AS num
FROM employees e
GROUP BY e.department_id
HAVING num >= 2;
```

> **提示**：`WHERE` 和 `HAVING` 的本质区别是**执行的时机**——`WHERE` 是拿到原始行的时候就过滤掉，`HAVING` 是分组、把每组压成一行之后再判断。凡是需要先聚合才知道结果的条件（"数量大于 N"、"平均工资低于 X"），就只能放 `HAVING`。

#### 排除经理后的部门平均薪资

需求：查出每个部门的平均薪资，但是要**排除经理**。

查平均工资这件事我们已经写过好几次了，先把之前那条粘过来改改——正常分组、正常算 `AVG`，只是人数不求了：

```sql
SELECT
    e.department_id,
    AVG(s.salary) AS avg_salary
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
GROUP BY e.department_id;
```

问题在于：员工表里是不是也有经理？他不想算进平均里。那这个"排除经理"是分组前还是分组后的条件？很明显是**分组前**——就是在分组之前把经理排除掉，再分组、再算平均。

那就在前面加个 `WHERE` 呗。`WHERE` 怎么写？其实很简单：**员工的 ID 不能等于经理的 ID**。假如经理是 1，就不能等于 1；经理是 2，不能等于 2；经理是 3，不能等于 3。

但这里要注意，**经理可不止一个**——三个部门就有三个经理，不能等于多个值。等于多值我们用 `IN`，那不等于多值用啥？`NOT IN`。

那经理的编号从哪来？从 managers 表里，它有个 `manager_id`，既是经理的编号，也是员工的编号。所以这里要套一个子查询：

```sql
SELECT
    e.department_id,
    AVG(s.salary) AS avg_salary
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id
WHERE e.employee_id NOT IN (SELECT manager_id FROM managers)
GROUP BY e.department_id;
```

`SELECT manager_id FROM managers` 单独执行一下，就是所有经理的员工编号；连完之后排除掉，再分组，查出来的就是每个部门去掉经理之后的平均工资了。这里稍微嵌套了一个子查询，仅此而已。

#### 部门内部的工资排名

需求：查出每个部门的姓名、薪水以及该部门内部的工资排名。

这个我们会了，工资排名是 `RANK` 系列。但排名是**多行函数**，那它得配合谁使用？配合窗口函数才行。

要不然你想一下：又查部门、又查薪水、又要查它的排名，直接写肯定查不出来，你得配合窗口函数。

先把部门员工的姓名和薪水查出来：

```sql
SELECT
    e.first_name,
    s.salary,
    e.department_id
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id;
```

这里有个小细节：员工表里员工名是分成 `first_name`、`last_name` 两列的，**根本没有一个叫 name 的列**。老外这套表就是这样，麻烦在这儿，我们就直接取 `first_name`，不做整合了，不影响排名。

然后在查列的位置加一个逗号，把排名写出来。`RANK()` 后面加 `OVER`，是窗口函数。`OVER` 后面什么都不加的话，排的是**整体**排名；我们这里要的是**部门内部**的排名，所以要 `PARTITION BY` 部门 ID，再按薪水 `ORDER BY` 从大到小：

```sql
SELECT
    e.first_name,
    s.salary,
    e.department_id,
    RANK() OVER (PARTITION BY e.department_id ORDER BY s.salary DESC) AS num
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id;
```

执行一下：每个人在部门中的排名，第一个是 1，然后是 1、2、3，薪水从高到低；二号部门那个是 1，三号部门那个也是 1。这就完毕了。

> **结论**：窗口函数的排序要分成两层看——`PARTITION BY` 决定"**在谁的范围内**排"，`ORDER BY` 决定"**按什么**排"。两个一起给，才是完整的排名语义。

#### 部门里薪水最低的员工

需求：查出每个部门薪水最低的员工的工资。

这个也简单，而且我觉得也得用排名，只不过这个排名是**正序**排名。正序的话第 1 名就是薪水最低的那个了。

先把刚才那条复用一遍，把 `DESC` 改成 `ASC`：

```sql
SELECT
    e.first_name,
    s.salary,
    e.department_id,
    RANK() OVER (PARTITION BY e.department_id ORDER BY s.salary ASC) AS num
FROM employees e
LEFT JOIN salaries s ON e.employee_id = s.employee_id;
```

一走大家就发现了：**这里边只要谁是 1，谁就是最低的。**

那有人说，那不就简单了，写个别名 `num`，直接 `WHERE num = 1` 不就完了吗？来，试一下——**写不了。** 报错了，说没有这个列。

> **易错点**：这是关键字执行顺序的问题。逻辑上是从 `FROM` 开始，紧跟着 `WHERE`，**最后**才是 `SELECT`。而窗口函数算出来的那一列，是在 `SELECT` 这个阶段才产生的，所以你在同层的 `WHERE` 里根本用不到它。

那怎么办？发挥一下聪明头脑吧——把这个结果**括起来，当成一个临时表**：

```sql
SELECT *
FROM (
    SELECT
        e.first_name,
        s.salary,
        e.department_id,
        RANK() OVER (PARTITION BY e.department_id ORDER BY s.salary ASC) AS num
    FROM employees e
    LEFT JOIN salaries s ON e.employee_id = s.employee_id
) AS tmp
WHERE tmp.num = 1;
```

这样就能用了。

> **结论**：为啥还要套一层？就是因为**你直接查的时候，这个查询里产生的列，在你当前这层查询中没法用**。套一层之后，里面先把结果算完、赋给这个临时表 `tmp`，外层这一回 `from` 找得到 `tmp`，而 `from` 是执行顺序在 `where` 之前的，所以外层的 `WHERE` 就能用里边的列了。你比我早了，这个 `WHERE` 自然就能引用它。

前面查"每个分类下价格最高的三种商品"用的是同一个套路，都是把带窗口函数的结果当成一张临时表，再在外层过滤。这样我们就查出了每个部门工资最低的员工的信息。
