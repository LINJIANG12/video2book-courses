### 数据库到底在解决什么问题

#### 先看看我们今天是怎么存数据的

先问大家一个问题。你每天基本刷的软件：回家刷抖音，给小哥哥、小姐姐们点个赞、刷个收藏；打开 B 站，搜一下尚硅谷的课程，去学一些开源课程。**这些程序里呈现的数据，都存储在哪个位置呢？**

我们先拿现有的存储手段来试，看它到底能不能存得住。

**第一种：程序的运行变量。** 拿 Java 举例，Java 的运行变量其实支持丰富的类型，字符串、整数、集合类型、自定义类型，完全有能力存储程序展示的这些内容。但这种方式行不行呢？行不通。因为所谓运行变量，是把数据存在程序运行的内存里，程序一终止，运行变量立即被释放，而且它根本没有主动的持久化手段，不会把变量持久化到本地磁盘中。下次你再打开程序，数据已经丢了。

> **易错点**：内存 ≠ 存储。程序变量看起来"在电脑里"，但它随进程生死，进程一死数据就没了，这是数据丢失的直接原因。

**第二种：本地文件 + I/O 流。** 我在本地创建一个文本文件，在程序中用 I/O 流对这个文件做操作。这下数据不丢了吧？确实不丢了，但又冒出新问题：**本地的文本文件它没有格式。** 对整个文本做读取、替换、删除，那是可以实现的；但如果你想对整个文本的局部进行条件化查询、条件化修改、条件化更新，用起来就非常麻烦，因为它没有格式。

**第三种：数据库。** 上面两种方案，一个持久性差，一个没有格式。而真正开发中，程序里的这些数据都是用数据库来存储的。数据库能同时规避上面两种缺点——它既是一种持久化存储手段，又是有格式的，因此方便对数据进行读、写、删、改等操作。

#### 数据库是干什么的

先给一个总的说法：**数据库是按照数据结构来组织、存储和管理数据的仓库。** 到这一步你大致理解它是一个存储数据的仓库就可以了。

教科书式的定义是：数据库是一个**长期存储在计算机内、有组织、可共享、统一管理的大量数据的集合（文件）**。可初学者读到这个定义往往还是有点迷糊，所以我把它的特点拆开，挨个讲透。

#### 三个特点：长期、有组织、可共享

**第一，数据库本质上是磁盘中的文件，或者运行内存中的一段数据。** 拿我们接下来要讲的 MySQL 举例：MySQL 会在我们的磁盘中创建一个它指定格式的文件，最终在这个格式化的文件里完成数据存储。

**第二，它是一种长期存储手段。** 注意，"长期"这个词跟位置、跟存储介质没关系，不是说它一定存在磁盘里。长期指的是：只要你不主动删除，存在数据库中的数据永远不应该丢失。

**第三，它是有组织的。** 所谓有组织，指的是数据库在存数据时，内部是有格式地存储。有了格式，才方便对数据进行读、写、删、改等操作。

那问题来了：为什么有格式、有组织就方便操作？我打个大家都经历过的比方。

北京下雪了，而且北京年年下雪。只要一下雪，学校就要组织学生扫雪。大家知道学生都是按照班级划分的：去年校长安排五年级的学员扫雪，今年校长为了公平，说今年五年级不用扫了，由六年级学员来扫。大家想想，校长就是根据"班级"这个组织结构去调动学员的——**有组织，是不是就方便查找学员了？** 数据库就是这个道理。

**第四，它还是可共享的。** 存在数据库中的数据，只要你赋予对方账号，或者开放他的主机访问权限，他就可以访问。所以它是一种可共享的存储手段。

> **定义**：综合起来，数据库就是一个**长期存储、且有格式、可共享**的文件或一段数据。

### 关系型与非关系型：一字之差

#### "关系"这两个字到底指什么

数据库根据数据的**存储结构**不同，分为两大类：一类叫非关系型数据库，一类叫关系型数据库。很明显，差别就是一个有关系、一个没关系。

我们把"关系"这个词拆开看。关系指的是两个事物之间的联系——比如我和我媳妇是夫妻关系。放到数据库里，关系指的不是人，是**数据**。

- **非关系型数据库**：它可以存多份数据，但数据和数据之间**不能建立关联**，每个数据都是独立的。
- **关系型数据库**：它也可以创建多份，只不过这些数据之间**可以建立某种关系**。

这就是两种数据库本质上的区别：能不能建立数据之间的关系。至于建立关系有什么好处，下一节我们细化再说。

再说底层。非关系型数据库到目前为止**没有一个统一标准**——不同的非关系型产品，内部存储结构可能完全不同：有的用键值，类似于 Map 这种 Key-Value 形式，比如 Redis；有的用文档；有的用 JSON。但不管怎么存，数据和数据之间都是没有关系的。而且正因为没有关系、每个数据都截然一身，它的性能相对来说会更好。

关系型数据库则已经有了统一的存储标准：**所有关系型数据库都是将数据按照类别存储**——数据先分好类，每个类别存到对应的一个容器里，这个容器叫**表**；表和表之间可以建立关联，最终能进行关联操作。但因为数据和数据之间有关联，它的性能相对来说一般。

举个例子：我们要存学生和学生的分数。关系型数据库可以存两个表，最终能查询"某个学生和他关联的分数"，能做关联查询；而非关系型数据库做不到这件事。

#### 非关系型的三个特点

**灵活的数据类型。** 所谓的灵活，指的是它内部的存储结构其实是多样化的——你可以根据你想要的数据结构，选择对应的非关系型数据库。它没有统一标准，各有各的存法。

**无固定的表结构。** 它本身内部就没有"表"这一说。你想存数据，比如存键值对，直接设置一个 Key 和 Value 就行了，不需要像关系型数据库那样提前声明好表结构。随时存、随时用，不需要做前置工作。

**高性能。** 还是那句话：截然一身，没有任何藕断丝连，所以它的性能相对来说会更高一些。

#### 关系型的四个特点

**数据结构化模型。** 它内部是有固定结构的，就是用表存储。你可以把它理解成你平时做的表格：想做表格存储之前，是不是得先提前规定好表内的表头是什么东西？所以关系型数据库需要你提前做一些前置准备工作——先设计好表名、表头等等。

**支持事务。** 事务后面会详细讲。大概意思是：某些语句执行出错了，它可以帮你进行数据回滚。比如我给你转账，转账到一半突然因为网络失败了，那钱不能丢吧？事务就会把钱回滚到我之前的状态，把钱还给我，就是这种感觉。

**支持关联查询。** 因为数据和数据之间有联系，所以它可以查出学生关联的分数、分数关联的课程等等，支持非常丰富的查询语句。

**数据一致性。** 它可以加一些所谓的"约束"概念，来保证数据的正确性和一致性。

> **结论**：两句话记住这两类数据库的分工——**关系型数据库适用于强一致性和复杂查询的场景，它好用**；**非关系型数据库就是灵活和性能会更好一些**。

#### 小孩才做选择：开发中到底用哪个

既然知道了特点，问题就来了：在开发中到底选哪种数据库？

先问第一个问题——开发中哪个数据库用得多一些？这个问题我不太好回答，但我换个问法，你可能就知道答案了。**两个帅哥或者两个美女同时要跟你交朋友，你要如何选择？** 有人说"我选他""我选她"，大家注意，小孩才做选择呢，大人是我全要。

我们从头到尾没有说数据库是水和火的关系，它俩没有说不兼容。所谓的关系型和非关系型是可以兼容的。所以在真正的开发场景下，一般用**混合模式**：两者都用，都利用它们的特点来进行数据存储。

具体分工是：程序的主体数据，一般存储在关系型数据库里，**以它为主**；程序的缓存数据和高并发这类数据，存储在非关系型数据库里，**以它为辅**。两者皆用。

最后明确一下：本门课程要讲的是一个**关系型数据库**。当然，如果你想学一些非关系型数据库，可以去看看尚硅谷的其他课程，那边也有讲解。

### ER 模型：关系型数据库到底怎么存数据

只有了解了关系型数据库的存储和设计规则，我们才能方便地去做后面关于数据和容器的操作。这套规则可以总结成一个东西，叫 **ER 模型**。

#### E 是实体，R 是关系

ER 模型里的字母是这么来的：

- **E 是 Entity 的缩写，代表"实体"**。关系型数据库会将一类数据存储到一张表中——它表达的是"数据按类别存在表中"这件事。
- **R 是 Relationship，代表"关系"**。它指的是这些表和表之间可以建立某种关系，最终我们能通过关系进行关联操作。

还是用学生和分数的例子。我们把学生和分数这两类数据，在关系型数据库里存到两个表中，然后让表和表之间建立关系，最后就能查询"学生和他关联的分数"，也能查询"这个分数是哪个学生考的"。这就是关系型数据库存储规则的总结，也就是 ER 模型。

#### 四个存储单位：库、表、列、行

ER 模型内部有哪些单位？给你一个完整答案：**库、表、列、行。**

```text
库  ── 关系型数据库中最大的存储单位（库里可能还不装具体数据，
│       它下面还有别的容器）
 └── 表 ── 每一类数据最终存储到一个表里，表要存到库中
      ├── 列 ── 表的特性列，定义表中如何存储。
      │         例如学生表要存什么属性：姓名、年龄……
      │         列是最小的存储单位
      └── 行 ── 在表里形成的一行数据，
                一行数据其实代表一条记录、一个实体
```

说到这儿，可能有同学会恍然大悟：**这不就是我们平时操作的表格吗？**

没错，大家完全可以把关系型数据库的内部存储结构，抽象成我们用的 Excel 表格，本质来说它们俩的结构是一致的。逐个对照着看：

| Excel 表格 | 关系型数据库 | 说明 |
| --- | --- | --- |
| 整个表格文件 | 库 | 最大存储单位 |
| 工作表（页） | 表 | 一类数据的集合，类似 Java 里的"类" |
| 列 | 列 | 描述这一类数据要存哪些属性，类似 Java 对象的属性；最小存储单位 |
| 行 | 行 | 一个具体的实体，类似 Java 中的"对象" |

对照着理解就顺了：去 Excel 存数据，第一步是不是要先创建一个表格文件？整个文件就相当于库。第二步，文件里可以创建多个页，每个页相当于一个表，存的是对应类别数据的集合。第三步，表里要有列这样的特性，来标注你到底要存哪些属性，这是最小的存储单位。第四步，我们真正操作数据时——我要删除数据，我是删除列吗？我要查询数据，我是查列吗？都不是，**我们操作的基本单位是行**，一行代表一个实体，一个具体的对象。

> **结论**：ER 模型最终总结出来的单位就是这四个——**库是最大的存储单位，表是一类数据的集合，列标注要存的属性，行代表一个实体**。在脑子里把这四个单位抽象一下，后面学起来就顺了。

### 数据库管理系统：仓库里还得有个管理员

#### 仓库和仓库管理员

先想一个生活中的概念——**仓库**。仓库也能帮我们完成货物的存储。

但我们得想一个问题：仓库中的这些货物，会不会自动走上货架，或者走下货架呢？很明显，它不会。它需要有一个类似**仓库管理员**的角色，帮我们完成对仓库中货物的管理。**仓库管理员加上仓库，才等于一个动态的仓库，二者缺一不可。**

反推回数据库。数据库本身就是一个磁盘中的文件，或者是运行内存中的一段数据，它本身是**静态**的，里面的数据也不会长腿跑出来。所以我们也需要安装一个在当前电脑中、类似仓库管理员角色的软件，最终帮我们完成数据库中数据的操作。这个软件、这个系统，就叫**数据库管理系统**，我们简称为 **DBMS**。

> **定义**：数据库管理系统是操作和管理数据库的大型软件。用户最终通过数据库管理系统，完成对数据库中数据的操作。

它们俩合二为一，才是一个完整的数据库，少一个都不行。所以我们操作数据的路径永远是：先操作数据库管理系统，间接达到对数据库中数据的操作，**而不能直接去操作数据库文件**。这就是我们为什么必须准备一个数据库管理系统。

#### 常见的四款关系型数据库管理系统

关系型数据库常见的管理系统有这么几个，我先罗列几个。

| 管理系统 | 出身 | 擅长 | 费用 |
| --- | --- | --- | --- |
| Oracle | 行业绝对一哥，很多关系型管理系统的标准都是参照它定义的 | 大型项目；性能优异 | 企业使用需要收费，而且相当昂贵 |
| MySQL | 最早由瑞典公司开发，后被 Oracle 收购，与 Oracle 同属甲骨文 | 中小型项目；性能也不差 | 企业使用有免费的开源版本 |
| DB2 | IBM 的知名产品，IBM 生态圈的一环 | 金融项目、大型项目；数据恢复与数据安全管理更全一些 | 需要认证收费，价格也不便宜 |
| SQLite | 小型嵌入式数据库，跟生活贴得最近 | 移动端 App、智能家居、智能眼镜等小型设备 | 企业免费 |

逐个再强调一下。**Oracle** 是被业界认为最成功、性能最好的关系型管理系统，但它的第三个标签也是最重要的标签是：企业使用需要收费，而且这个 money 还很昂贵。**MySQL** 是 Oracle 的小弟，性能也不差，比较适合中小型项目，而且企业有免费版本。**DB2** 是 IBM 产品生态的一环——有时候你用了 IBM 的硬件服务器，它就要求你配 DB2；它比较适合金融项目或大型项目，内部的数据恢复、安全管理更全面，同样需要认证收费。**SQLite** 稍微有点特别，它比较小型，一般应用于移动端，我们手机里那些 App 用的数据库就是 SQLite，智能家居、移动设备、智能眼镜里存数据也都可以用它。

这里边我们介绍了两款收费产品、两款免费产品，大家先有个大概印象。

#### 站在老板的角度来选

知道这几款明星产品以后，到底如何选择呢？我们还得换个维度——因为我们学习它，就是为了在工作中去使用，得找一个在国内或者国际上使用率排名靠前的。

看市场使用率排行，前两位基本就是 Oracle 和 MySQL：一张图里 Oracle 是第一，另一张图里 MySQL 是第一，两个交叉着排第一、第二。所以从市场使用率来说，MySQL 和 Oracle 的使用率是比较高的。

到这儿，很多同学会说：用 Oracle，Oracle 性能好、行业大哥，就用它！这回我们得替老板琢磨琢磨。**假如你是个老板，你选谁？** 你不是打工者。这回你可能就不会说 Oracle 了，因为它收费，能理解吗？

一般在公认的一些一线大厂，比如阿里、百度、腾讯等等，他们都有自己的数据库产品，不会去用 Oracle 这种收费产品。而用第三方收费产品的，基本都是一些中小型公司——中小型公司一定是把成本放在第一位。所以在国内，Oracle 并不是首选，MySQL 才是首选。

还有一个维度：甲骨文公司的市值现在是 3100 多亿美元，折合人民币 21000 亿，21000 个小目标而已（2023 年的数据），全年销售了大约 500 亿的营销额。从这张营销图上能看到，美洲和欧洲等地区占比都比较高，而亚太地区只有 66 亿，而且还在呈现下降的姿态。这间接说明：亚太地区的软件用得其实也不少，但对收费产品的贡献比较少——**我们对性能可能没有那么极致的要求。**

> **结论**：通过综合考量，推荐用 MySQL。现在的企业开发中，MySQL 确实是绝对的主流，所以我们这门课要安装的、最后要学的，就是它。

#### 到底装 5.7 还是 8.0

要装 MySQL，得先说清楚装哪个版本。MySQL 这个软件有点特殊：**它长期维护两个稳定版本**，一个 5.7 系列，一个 8.0 系列，两个版本并行更新迭代。正常软件一般都是更新到 1、2、3 就把前面的版本丢掉了，MySQL 不这样。

很多同学看到这，一定会在公屏或留言区问："我们公司用的是 5.7。" 大家注意，你公司用的版本跟授课还是有点区别的。**我们讲肯定要讲新版本**，讲的是一个趋势和方向，而且一般新版本都会向下兼容。何况官网已经给出了解释：8 版本相对于 5.7 做了许多改进和更新，包括性能、安全以及一些新的特性。

还有一个最关键的点——**这些可能打不动老板，但下面这个一定能说明他必须要更新了**：Oracle 在政策上已经于 **2023 年 10 月 25 日结束了对 MySQL 5.7 的更新**。后期 MySQL 这条线就断了，"断"指的是它不再做功能更新了，它作为一个末期版本、维护版本，后期只会维护一些 bug，新的功能、新的特性不再在这个版本上做任何研发和进展。所以官方强烈建议所有 5.7 的用户尽快迁移到 8.0。

顺便说个彩蛋。MySQL 的版本号按理说应该 1、2、3、4、5 这样排下去，我们现在讲到了 5.7，那是不是应该有 6 和 7？它偏偏没有 6 和 7 两个大版本，从 5 系列直接跳到 8 系列——**它想表达的就是 8 相对 5 系列做了一个很大的跨越，中间版本跳跃更新，体现它的更新力度更大**。所以无论从哪个方向看，我们都更推荐 8 系列。

> **结论**：8.0 是我们学习的首选，也是后期开发的首选。本课程使用的是**最新最稳定版本**，官方标注为 GA（General Availability，即最新最稳定版本），具体版本号是 **8.2.0**。

最后交代一下我的安装环境。我要给大家演示 Windows 和 Mac 两套安装：Windows 我用的是 Win10 系统；Mac 这个电脑可能稍微有点老，是 2018 年的，用的还是 Intel 芯片，不是 M 芯片——大家不用笑话我。如果你们用的是 Win11 或者是 M 芯片，步骤肯定没差别，可能一些细节稍微有点差别，但整体步骤都是类似的。

### 在 Windows 上把 MySQL 装起来

在动手之前，先把整个 MySQL 安装过程整理到了一个 Markdown 教案里，它存在物料的"课件/安装"这个文件夹下，一共有三个教案，分别讲 Windows 版本安装过程、Mac 版本安装过程，以及安装过程中可能发生的一些问题及解决方案。

我的习惯是：**先打开第三个"常见问题和解决方案"，确保我们没有类似的问题，再去做 Windows 安装。** 这个教案里一共讲了七个小点：第一个是卸载的问题——如果你之前装过其它版本，按这个过程卸载就完事了；第二个是安装失败可能发生的问题；第三个是初始化失败的问题；下方还有连接等等一些相关的问题。

#### 先排雷：两个最容易卡住的地方

七个小点里，1、4、5、6、7 放到以后再说，咱们先把 2 和 3 说清楚——这是安装过程中最容易卡住的地方。

**第二点：安装 MySQL 需要电脑里具备一些其它的环境包，缺少了就会报错。** 比如你双击 MySQL 以后弹出一个窗口，报错缺少 .NET Framework 这个包，那你就打开对应的地址下载安装就可以了。还可能缺 C++ 的包，或者缺 DLL 文件——只要报了对应的问题，去下载再安装就行。记住这个规律：**缺什么补什么。**

**第三点：安装完毕以后要初始化 MySQL，服务启动不起来。** 如果安装完毕以后服务起不来，**只有一个原因**——你的电脑用户名是中文的。电脑用户名是中文，它也会在电脑中创建一个对应的存储文件夹，而这个文件夹也是中文的。MySQL 在识别中文的时候可能出现乱码，所以它无法在你的当前用户文件夹下去初始化一些内容，于是就报错。解决办法很简单：把电脑的用户名改成英文就可以了。

> **易错点**：安装到最后"Execute"失败，别怀疑安装包有问题，90% 是中文用户名导致的。先改名，再回头重新安装。

#### 双击安装：默认模式一路 Next

软件就在下发的资料里有个"软件"文件夹，里面分 Mac 和 Windows，点开对应的系统就有了。我们点开 Windows，这里边有一个 MySQL 的可执行文件，是 MSI 格式的 8.2.0 版本，安装它就可以了。

安装过程大致就几步，我们一边走一边说：

第一步，**双击安装包**，正常点 Next。这一步代表你是否同意认证——"我同意"，你不同意也下一步不了。

第二步，选择你要如何安装、是否自定义。我们选第一个，用它的默认模式安装就可以了，然后点 Install。

这里有个细节要说明：它会问你选择什么版本，因为我们下载的可执行文件里只有一个 MySQL 服务，没有什么其他工具，所以这一步你都不用选择，直接下一步就搞定。点完 Install 稍等一会儿，安装就结束了。

**就这么简单。到这儿，"安装"这件事本身已经完成了**——注意，这只是在课件四步里的第一步。

#### 初始化配置：三个必须记住的东西

接下来进入第二步，MySQL 的一些初始化配置：服务在后台占哪个端口号、初始化账号密码是什么，我们一步一步往下走。

**第一件事：端口号。** 页面会问你这个 MySQL 服务在后台占的端口号是多少。这个一定要记住，默认就是 **3306**。它可以改，但是**不建议改**——因为后期其他软件连接 MySQL 的时候，默认就找 3306 这个端口号去找 MySQL 程序。

**第二件事：账号和密码。** 页面上下有两个区域，大家听我说清楚。上方指的是超级管理员账号，你要给它配置密码；**超级管理员账号固定就叫 `root`**，所以下面两个配置框是 root 的密码和重复密码——**两遍都是密码，账号固定就是 root**。它会提示你这个密码有点弱，弱就弱，无所谓，好记就行。下方指的是你要不要添加其他非超级管理员账号，我们先不添加，等后期学到了相关命令，在 MySQL 里面用命令添加。前期我们用 root 账号和对应密码操作就可以了。

**第三件事：服务名。** 这一步指的是 MySQL 的服务名，大家一定要记住，因为**后期我们可以通过 Windows 下的 DOS 命令去启动 MySQL 服务，就是根据这个服务名来的**。叫什么都无所谓，你只要记住它是什么就行，而且**它区分大小写**。我之前装过，所以这次就叫 82，避免跟之前装过的服务名重复导致安装失败。安装完我会把服务名截个图定在这儿；我可能跟你不同，但你自己要知道。

服务名之后的几步就不用管了：初始化数据在哪个位置，正常；要不要创建什么数据，也正常。直接往下走。

最后是**正式初始化 MySQL 服务**：点一下 Execute，它会把这几步一步一步帮你搞定。**只要 Start server 这一步成功了，就证明我们 MySQL 安装成功了**；如果这一步失败了，就回到前面说的——电脑用户名可能是中文，先改成英文，再回头重新安装。点 Execute 执行，稍等，这一步有快有慢，跟电脑性能有关系。等它跑完，显示全部完毕，那 8.2.0 就安装成功了。接下来点 Next，点 Finish 就可以了。

> **结论**：整个安装配置过程，有三个主要注意点要记住——**端口号 3306**（后期连接要用）、**服务名是什么**（后期要靠它启动 MySQL）、**超级管理员账号固定是 root**（密码写两遍，记住初始化的密码）。前期建议别玩花活，密码设得稍微简单点，不然忘了改起来非常麻烦。

#### 怎么开启、怎么关闭这个服务

装完之后还有一个必会的操作：MySQL 这个服务怎么关、怎么开。

大家注意，MySQL 不像其他可视化工具那样在桌面上有一个可执行文件，**它是一个后台服务**。它的开和关有两种方案。

**第一种，可视化方式。** 点开你的电脑，右键点"管理"，在这里能看见我们电脑所有服务。找到"服务"，找到我们刚刚起的那个 MySQL 服务名——MySQL 以 M 开头，你点到这个位置以后按 M，它会快速切换定位到 `MySQL82`。怎么证明这个服务是不是正在运行呢？看状态就知道了：**默认 MySQL 服务是开机自启动的**，所以它装完就是开启状态。如果暂时不用数据库，你可以右键把它停止，这完全没问题；想用的时候，再右键启动。

> **注意**：在你要进行数据库操作之前，一定要先把 MySQL 这个服务启动，否则你是无法进行数据库操作的。

**第二种，命令方式。** 打开命令行工具 `cmd`。这里有个关键点：**右键要用管理员身份运行**，否则你没有对这个服务操作的权限。Windows 下对服务操作的命令就是 `net`，这是固定的；开启是 `start`，停止是 `stop`。格式是：`net` + 空格 + `stop`（或 `start`）+ 空格 + 服务名。

先把它停掉：

```cmd
net stop MySQL82
```

再把它开起来：

```cmd
net start MySQL82
```

服务名是区分大小写的，写错了是没反应的。

### 让 mysql 命令到处都能用

初始化做完，最后还有一个小点：**MySQL 实际上会自动配到环境变量里**，我们得确认一下到底配成功了没有。

#### 验证：输入 mysql 看看它认不认得你

先确保你的服务是启动的，然后在命令行里输入一个 `mysql` 就够了。

如果它报"不是内部或外部命令"这类提示，你就知道了——**这说明 MySQL 没有配到环境变量 Path 中**。原因也很清楚：Path 决定系统去哪里找可执行文件，MySQL 的可执行文件不在 Path 指到的文件夹里，它当然认不出来。

那如果配好了会是什么样？你会看到 MySQL 的连接提示和输入提示符，但这说明另一件事：**在 cmd 里敲 `mysql` 本身是不需要管理员权限的，只有启动和停止服务才需要管理员权限。** 我们没输入账号密码，所以它现在是在等你输。

#### 两种配法，我推荐第二种

配环境变量的本质，就是把 MySQL 的 `bin` 目录挂到系统能找到的地方。默认安装位置在 C 盘：

```text
MYSQL_HOME  =  C:\Program Files\MySQL          （MySQL 整个文件夹）

然后在系统环境变量 Path 中追加一项：
    %MYSQL_HOME%\bin
```

有两种配法。

**第一种，也是很多人直接在 Path 里写完整路径**，直接把 `C:\Program Files\MySQL\MySQL Server 8.2\bin` 整个粘进 Path。能用，但不推荐。

**第二种，就是我教大家的这种，更专业一点**：第一步，在系统环境变量（下方的"系统变量"，任何用户都可以使用）里新建一个变量，名字叫 `MYSQL_HOME`，值就是 MySQL 整个文件夹的地址，相当于我们在电脑中声明了一个变量叫 `MYSQL_HOME`。第二步，双击打开 Path，新建一项，写上 `%MYSQL_HOME%\bin`。

这里的关键是两个百分号，它代表"引用其他变量"，引用的就是你刚刚声明的 `MYSQL_HOME`。所以这一行等价于 MYSQL_HOME 的完整路径加上 `\bin`，**等同于写了一个完整的路径**。

> **为什么推荐第二种**：后期万一你换了这个安装位置，你只要改 `MYSQL_HOME` 一个值就行了，Path 那一行完全不用动。写成完整路径的话，换位置就得去改 Path 里那一长串，容易漏、容易错。

还有一个细节要提醒：我的电脑上打开 Path 是自动分行的，自动分成不同的行；但有些同学打开以后它是这样的一串，中间用分号连着。**如果你的是一串，记得在前面补一个分号，再继续写 `%MYSQL_HOME%\bin`。**

配完之后点"确定""确定"，然后**把那个黑色的 cmd 窗口关掉**——它缓存的还是上次的变量值，窗口不关不生效。重新打开一个 `cmd`，这次**不用**管理员权限，输入 `mysql`。只要不再报"不是内部或外部命令"，就证明环境变量配好了。

到这里我们把整件事串一遍：第一，先安装；安装完做初始化；第三，掌握用可视化方式或者命令开启和关闭 MySQL 服务；最后，服务开启状态下，用 `mysql` 命令确认环境变量已经配置完毕。如果报"不是内部或外部命令"，那就是环境变量有问题——声明一个 `MYSQL_HOME` 等于 MySQL 整个文件夹的地址，再在 Path 里追加 `%MYSQL_HOME%\bin`，就完成了配置。

这就是 Windows 下的 MySQL 安装。千里之行，始于足下，接下来我们正式开启 MySQL 的学习之旅。

### 在 Mac 上把 MySQL 装起来

先说结论：Mac 下装 MySQL 反而比 Windows 简单。资料里就两样东西——一个 Mac 下的安装可执行软件，一个 Mac 下的安装教程。打开教程，三步走：

1. 完成 MySQL 的安装；
2. MySQL 服务如何启动和停止；
3. 配置 Mac 下的环境变量。

我们一步一步来。

#### 双击可执行文件，一路下一步

双击可执行文件，按提示一路下一步就行。真正要注意的是配密码那一步。

> **易错点**：Mac 下 root 密码有长度和大小写的要求，不像 Windows 下可以随意配置。

安装向导的流程大概是这样：双击，系统弹出窗口问你要不要允许，允许；然后是介绍页，继续；接着是许可认证协议，你没有"不同意"这个选项，拖到最下面点继续，它还会再问一遍是否同意，同意；再往下是安装类型，这一步大家听我说，位置不用改，用它默认安装的位置就可以了，这样我们在配置环境变量的时候找的软件位置都是统一的。一路安装，中间要输入自己电脑的账号密码。

装完软件，安装包会自动接着做 MySQL 相关的 Configuration 配置，这一段才是关键。

#### 两个配置，决定你以后用哪种登录方式

第一个配置是选密码策略，走默认值就可以了。它为什么给两份？因为 MySQL 5.7 和 8 版本的加密方式不同：选上方是 8 版本的加密方式；选下方，等于虽然我用的是 MySQL 8 的软件，但我还选择 5.7 的加密方式。我们推荐 8 的，就用默认值。

第二个配置是输入超级管理员 root 账号对应的密码，它要求至少是 8 位，里面包含大小字符。大家自己设置就可以了，只要设置成功以后，Finish 就可以点了。

> **提示**：不要搞得太复杂，省得自己记不住，后面改密码比较麻烦。

设置完点 Finish，这一步是指直接让它去初始化我们的 MySQL 服务，可能还要再输一次当前电脑的登录密码。到这，MySQL 就算装好了。Mac 下的安装无非就是装软件 + 配个密码，就这么简单。

#### 服务是自动开的，但你得知道怎么关

MySQL 服务在你 Mac 电脑打开以后是自动开启的，所以真正要学的是怎么关它。点开系统「设置」，在设置里会多出一个 MySQL 选项，这一块直接体现你 MySQL 服务现在是否在运行：绿色的代表服务正在运行。如果你想停止，点 Stop；停止以后这边变成 Start，再点 Start 就可以开起来了。

下方还有一个 Uninstall，代表你要把 MySQL 后期卸载，点这个按钮就可以。

> **结论**：做数据库操作之前，只要确保这个服务是绿的就是开启状态就可以了。

#### 配环境变量：先找到 bin 在哪

装完了，怎么用命令行操作？打开终端，输入 `mysql` 回车。如果报这个命令没有被识别，证明 MySQL 虽然安装成功了，但是没有配到 Mac 的环境变量下。那我们就把环境变量配上。

配之前先说几个基础知识点。

Mac 的默认环境变量文件，是在当前用户下一个叫 `.bash_profile` 的文件，它是个隐藏文件。怎么确认自己在不在当前用户文件夹下？输入 `pwd` 看一下当前路径——如果这就是你账号对应的文件夹，环境变量文件其实就在这里。如果说我进到其他文件夹了，没在当前用户的文件夹下，那你先回到当前用户的文件夹，很简单，直接 `cd` 就可以了，前面有个小飘号（`~`）就代表你回到了当前用户文件夹。

```bash
pwd
```

回到家目录以后，咱们 `ls -a`，`-a` 代表是查看隐藏文件，回车。这里边大家跟我一起找一下，有一个叫 `.bash_profile` 的文件。这里边配的就是整个 Mac 下的环境变量，所以我们只要把 MySQL 安装的软件 `bin` 的路径配到这里就可以了。

那 MySQL 到底安装到哪了呢？大家注意，默认我们没有改变位置，它是安装到 `/usr/local` 在这个下方。大家看，记住前面要加斜杠，这是绝对路径。进来以后咱们 `ls`，看到这里边发现是不是多了一个 `mysql`？`cd mysql` 下再 `ls`，它有一个叫 `bin` 的文件夹；`cd bin` 进去以后，咱们发现这里边有一个可执行文件叫 `mysql`。

`pwd` 一下，路径就齐了：

```text
/usr/local/mysql/bin
```

其实我们只需要把这个地址配到刚刚说的当前用户下 `.bash_profile` 那个环境变量下就可以了。如果大家不清晰，资料下方有环境变量对应的教案，教我们怎么配置。

#### 用 vim 把路径塞进 PATH

先 `cd` 回家目录，`ls` 查看未隐藏文件，加个 `ls -a` 就可以了，确保在这个文件夹下有 `.bash_profile`。最后用编辑命令去打开它，有一个叫 `vim` 的文本编辑器命令：

```bash
vim .bash_profile
```

进到这里边注意，这里面就是我们的环境变量。我们找到一个叫 `PATH` 的环境变量，只需要把我们刚刚那个安装的 MySQL 的 `bin` 文件夹地址配到这里就可以了。大家发现 `PATH` 里面其实有很多变量，而变量之间用的是冒号隔开，那同样我们也在写之前用冒号给它隔开就可以了。

现在用 `vim` 进到编辑命令以后，大家注意，先按 `i` 进到编辑模式——不按 `i` 你现在写不了东西。进到编辑模式以后，我们写出我们 MySQL 对应的地址，中间加个冒号：

```text
/usr/local/mysql/bin:
```

这就代表我们把 MySQL 的环境变量对应地址配到环境变量中了。当然如果说你改变了安装位置，这里写你指定的位置也可以。

> **注意**：这个地址加在 `PATH` 的前、后都行，但分割前后一定要加个冒号，大家记住。

写完按 `Esc` 退出编辑模式，再按 `Shift` 加冒号，写 `wq`，这相当于是把当前的文件进行保存并且退出就可以了。我之前做的这一系列操作都是 Vim 编辑器的相关操作，如果大家不熟悉，同样可以看教案的步骤写就可以了。

最后还差一步，让环境变量立即生效，只需要 `source` 去指定你环境变量的这个文件名：

```bash
source .bash_profile
```

回车，环境变量就配好了。但前提记住，`source .` 它指的是找到当前文件夹下的这个文件，如果说你不在你当前的用户文件夹下，那这个可能会报找不到文件，你要先回到当前的用户文件夹下，才执行以下命令，记住了吗？

现在我们再去输入 `mysql`，咱们可以用一下 `--version` 看一下 MySQL 的版本：

```bash
mysql --version
```

大家发现这个版本就能识别到了，也相当于识别到了 MySQL 命令，证明 MySQL 就安装成功了。

回头看，我给大家解释一下我们做了几件事情。第一件事情是安装，安装里面无非有个注意事项，就是在配置密码的时候是 8 位。第二步是 MySQL 服务的开启、关闭，只要打开电脑设置、找到下方的 MySQL，我们就可以在这个位置停止或者开启服务。第三步是在命令操作的时候发现它不识别 MySQL 命令，证明我们没有配置环境变量；打开当前登录用户的家文件夹（就是飘号 `~` 这个地址）下的 `.bash_profile`，把 MySQL 的地址加进 `PATH` 就行，最后再用 `source` 让它生效，整个环境变量就配置完毕了。

### 找不到界面，MySQL 到底怎么操作

第二小节我们已经完成了 MySQL 管理系统的安装，接下来讲对 MySQL 这类关系型管理系统进行操作的指令——SQL 指令，它的概念和作用。

先给大家引导一下为什么要学 SQL 指令。第一个我们要理解的是，如何去操作 MySQL 这类的应用。正等着我们大干一场对数据库操作的时候，我们发现我们连入口都没有。因为 MySQL 这类它是一个服务，没有像我们之前玩的那些游戏那样有些用户界面可以点点点。那我们到底该怎么操作它？

#### 软件分两大类：GUI 与后台服务

从操作角度来说，软件可以分成两大类。

第一类就是我们玩的《英雄联盟》《魔兽世界》，或者是你聊的 QQ、微信，它们都有用户界面。只要有手，我们就可以通过控制鼠标、键盘完成对应用或者软件的操作，R 闪、盲视野反杀，是不是都可以简单地完成？这一类我们称为图形用户界面类的应用，叫 GUI，它有界面。我们平时用的、现代用的大部分都是这类。

除了这类，还有像 MySQL 这个类型的。其实我们可能会很苦恼，MySQL 要怎么操作呢？大家首先要知道，MySQL 这类它只是后台的一个服务，就是默默地在后台这运行着，有它，但是它没有可视化操作界面。这类应用我们称为无用户界面或者后台服务类的应用。这一类的应用操作起来肯定不能通过鼠标点点点，因为你没有点的地方。它需要你输入一段特定的文本指令、或者一段命令跟它进行交互，来完成这个操作。

我在命令行里演示一下。这边我已经登录到了 MySQL（后边会细讲，现在这不重要），在下方我输入了一个指令：

```sql
show databases;
```

这个肯定不是我瞎写的，这肯定是固定的要求这么写。它就相当于跟 MySQL 进行交互，告诉 MySQL 去给我展示一下你到底有哪些数据库。或者我可以再写一个指令：

```sql
use mysql;
```

回车，我们发现有个 `mysql` 这个库，那这时我可以通过 `use` 去使用这个库。库里面是不是有表啊？我还可以再输出：

```sql
show tables;
```

就能查看我们库下有哪些表。重点不在命令本身，我们只要知道这一类的应用，你需要输入某一种指令完成跟它的交互，最后它会给我返回结果。这类就叫命令行界面的应用，或者是后台服务的应用。

所以说，我们要想跟 MySQL 交互，我们必须去学某种指令。这个指令我们其实就叫某一种文本指令，它就叫结构化查询语句，或者叫结构化查询指令，简称 SQL 命令、SQL 语句、SQL 指令，都可以。也就是说，SQL 指令其实就是操作 MySQL 软件的一套基本命令。

#### SQL 为什么能通吃所有关系型数据库

为什么叫 SQL 呢？它是这三个单词的缩写，翻译过来叫结构化查询语言。

SQL 指令最早是被美国国家标准局定义为关系型数据库的美国标准。也就是说，SQL 这个指令你学完了以后，是可以操作所有关系型数据库的，而非关系型数据库你是操作不了的。最后它被国际化标准组织采纳为国际标准的关系型数据库的标准语句。也就是说最终我们可以使用这个 SQL 指令操作所有的关系型数据库了。

这里要把几个东西分清楚：

```text
                SQL 指令
                   │
                   ▼
        数据库管理系统（DBMS）
    MySQL / Oracle / DB2 / SQLite ...
                   │
                   ▼
             数据库（DB）
```

我们是通过数据库管理系统完成对数据库的操作。但是如果你想对数据库管理系统进行操作，你得给它输入一段指令，这个指令是什么呢？就是我们所说的 SQL 指令。

所以，虽然我们的课程叫做 MySQL，但 MySQL 在上一小节已经完成了整体安装，它已经成为过去式了。其实剩下的我们就在讲整个 SQL 指令：到底有哪些 SQL 指令，可以对数据库进行怎么操作，这才是我们课程的重点。

我们只要学到 SQL 指令以后，就可以对 Oracle、MySQL、DB2、SQLite 等等这类关系型数据库统统进行操作，进而达到对数据库进行操作的目的。

#### 普通话和方言：SQL 也有方言

中国这么大，肯定也有很多方言。SQL 指令对应的是不同的关系管理系统，它其实也可能有方言的概念。

> **提示**：作为东北人，我有义务和必要去推广一下东北的部分方言。大家注意，我教大家几个东北的友好问候的方言。一共是八句，只要这一个八句话你要会了，在东北你可以畅通无阻了，到哪都是朋友。举个例子，假如说你走在大街上，你不小心碰了别人一下，那别人就瞅着你呗，完了你可以用这句话去回复他，你说"你瞅啥"，就代表咱们可能见面打招呼"你好啊"这种感觉。对方一定会这么说，"瞅你咋地"，他说"你也号"。最后你跟他说了啥，就说"找削啊"，这句话就是"吃了吗"。最终你俩就能成为好朋友。

所谓的意思就是说，我们东北有方言，你们各地也有方言。SQL 虽然是标准，它支持所有的数据库，但是大家记住一个事，SQL 它也是有方言的。我们上课讲的是标准 SQL，所有关系管理系统它都支持；但是不同的关系管理系统它可能也有方言。

本次我们课程主要讲的就是标准的 SQL 语句，我讲的东西这都支持；但是，我也会讲 MySQL 的相关的一些特性方言。但是讲到方言的时候我会告诉你，我说这是方言，那你知道它只有 MySQL 去支持，而其他数据库不支持。

> **结论**：要想对 MySQL 这类关系管理系统进行操作，我们必须学 SQL 语句。SQL 语句有标准和方言，标准是支持所有关系管理系统的，而方言指的是特定某个关系管理系统单独支持的。既然我们要用了 MySQL 这个软件，所以我们学的就是标准的 SQL 语句以及 MySQL 相关的方言。

### SQL 语句怎么分类，该按什么顺序学

这就好比学 Java 一样。Java 分为 Java SE、Java ME 和 Java EE，我们知道应该先学习 Java SE，再学 Java ME 或者 EE。当我们了解了这个语言的分类和每个类别的特点以后，就知道应该如何按顺序去学习。SQL 语句完全同理。

SQL 语句内部的命令是非常庞大的，很多很多，用东北话说就是老鼻子多了。如果说你上来直接去搞，基本你是搞得很乱，而且一头雾水。SQL 语句内部是有分类的，我们应该按照正确的每个类别的作用的顺序去学习。

#### 容器得先立起来：数据定义语句 DDL

大家想象一个问题，你想对数据库进行操作，你的第一步应该先干什么？有人说我要插入数据，或者我要查询数据、修改数据、删除数据。

> 这四个动作——增、删、改、查，一定是你最终要做的目标，但一定不是你最初的目标。

你想想，你要对数据进行插入，前期关系型数据库内部是有容器的，是需要你提前规定好的：库、表、行、列。那你是不是要先把这些容器先创建好？学生表、分数表是不是要创建好？所以第一步我认为，我们应该做的事情是先完成数据库相关的容器的创建、修改和删除的工作。这里边当然包含库的创建、表的创建，还有列的修改等等相关的动作。

这一类的语句就叫做数据定义语句，简称 DDL。DDL 里边包含的是关于容器的创建、删除和修改相关的指令和命令，这是我们学习的时候第一步要学的事情。

#### 只有容器没有数据也不行：数据操纵语句 DML

DDL 掌握了以后，容器是没有问题了。容器没问题以后，接下来你要干什么？有人说我查询，那也不太合适，只有容器没有数据也不行。

第二个我们要讲的就是数据操纵语句，简称 DML。它包含了对数据的添加、修改以及删除这三个动作。DML 不会影响我们的表和库等相关的结构，它只是对表中数据进行增、删、改相关的动作。

#### 有了数据再查：DQL，最复杂也最核心

有了表也有了数据，接下来你就可以大大方方地进行查询、展示了。第三个我们基本要学的就是 DQL，叫数据查询语句。这里边它只包含一个功能叫查询，会根据你的表去查询到结果。

但大家记住，查询语句不管你怎么查，你查出花来，你也不会影响表中的数据，更不会影响整个表结构。大家不要看查询语句只有一个查询功能，但它是最复杂的。因为你查询的条件、单表、多表非常多样化，所以查询语句是最复杂的，它也是我们本门课程的重点核心。

#### 拔高的部分：DCL 和 TCL

这三个搞定以后，其实还有两个，这就包含我们所说的数据控制和事务控制。这两个大家现在也不用了解，后面我们会讲。它指的就是对数据库的一个高级维护，相当于失败以后会做回滚，还有一个就是创建一些账号，可以对数据库访问权限进行控制等等相关的动作。这其实就是一些扩展和拔高了。上面是基础，下方是扩展和拔高。

| 分类 | 中文名 | 管什么 | 学习位置 |
| --- | --- | --- | --- |
| DDL | 数据定义语句 | 库、表、列等容器的创建、修改、删除 | 第一步，必学 |
| DML | 数据操纵语句 | 表中数据的添加、修改、删除 | 第二步，必学 |
| DQL | 数据查询语句 | 查询 | 第三步，最复杂，课程核心 |
| DCL | 数据控制语句 | 创建账号、控制访问权限 | 扩展拔高 |
| TCL | 事务控制语句 | 事务与失败回滚 | 扩展拔高 |

> **结论**：学习顺序就是先 DDL，保证对表、容器能进行操作；再 DML，保证能把数据插到数据库中、修改和删除；再 DQL，指的是对数据查询，虽然它只有一个功能，但是它是重点和核心，也是最复杂的。下方就是扩展 TCL 和 DCL 这两个，它俩谁先谁后倒没有任何顺序了。这就是我们整个 SQL 语句的分类，以及我们应该如何学习。

### 在哪写 SQL，以及怎么连上去

在正式学习 SQL 语句之前，我们先去讲几个关于 SQL 语句的基本操作。这里边主要包含：第一，我们要知道在什么位置去编写或输入 SQL 语句；第二，一些基本的 SQL 指令，包括连接、退出和版本号查询以及注释等等。

#### 黑窗口就是我们的编辑区

现阶段如果我们想跟 MySQL 进行沟通、或者去传递 SQL 语句，需要用的工具是命令窗口、黑窗口，如果你是 Mac 电脑就是终端。在这个基础上，我们才能去编写 SQL 语句。

第一步你一定要保证一个点：打开右键「管理」，点开「服务」，找到「服务」，搜一下 MySQL 服务，要确保 MySQL 的服务是正在启动状态。

启动好了以后，第二步我们要打开 cmd 咱们的黑窗口「命令提示符」这个应用，Mac 就打开终端。打开了以后，我们就可以通过这个应用去连接到对应的 MySQL 服务，连接到以后也可以在这个位置向 MySQL 去传递 SQL 指令。

> **定义**：现在的黑窗口就相当于是我们编辑 SQL 指令的一个编辑区和编辑工具，这样去理解就可以了。

#### 连接参数：必写两个，可省三个

怎么连接？我们要找 MySQL 这个软件，这里边需要输入一些核心参数。

第一个我们要先写的就是 `mysql`，这是固定的，相当于调用 MySQL 的可执行文件，后边要跟的是空格。

| 参数 | 含义 | 必填 | 写法要点 |
| --- | --- | --- | --- |
| `-u` | 要登录的账号用户名 | 必填 | 用户名紧贴 `-u` 或写空格都行 |
| `-p` | 该账号的密码 | 必填 | 密码必须紧贴 `-p`，不能写空格 |
| `-h` | MySQL 服务所在主机的 IP 地址 | 可省略 | 同一台电脑时默认本机 |
| `-P` | MySQL 软件的端口号 | 可省略 | 大写 P，默认 3306 |
| 库名 | 直接连接到的库 | 可省略 | 不写相当于连接所有库 |

`-h` 之所以要存在，是因为 MySQL 连接软件也没说非得装到当前的电脑中，它也可以装到其他电脑中，只要通过 IP 地址就可以进行连接。`-P`（大写 P）就是端口号，找到 IP 地址以后，想找到一个软件我们还得知道它所在的位置，也就是端口号。默认的就是 3306，我们在当初安装的时候，如果你没改它就是 3306。

`-h` 和 `-P` 什么场景下可以省略呢？如果这个软件装在了和 cmd 这个黑窗口是同一台电脑中，并且端口号你没改、是 3306，那这两个就不用写，它默认就找本机 3306 这个软件。所以这两个你可以改，也可以不改。

在最后其实还可以写一个数据库名。如果你写了数据库名，指的是我直接连接到某一个库；如果你不写数据库名，相当于是连接到所有库，最终你可以选择使用哪个库。所以数据库名也可以省略。

> **结论**：这里边必须写的只有 `-u` 和 `-p`，剩下的这三个都是可以省略的。

#### 密码别明着写

第一种连接方法，打开窗口以后输入：

```bash
mysql -uroot -proot
```

注意空格。`-u` 我们账号是 `root`，`-p` 必须紧贴着，我的密码也是 `root`。当然这个账号其实可以贴着也可以不贴着，而密码必须紧贴着 `-p`。回车，这样是不是就可以连接上了？

第二种连接方法，我直接给它保留下记录：

```bash
mysql -u root -p root -h 127.0.0.1 -P 3306
```

这回我给它空格，`-p` 后面还是 `root`，再下方 `-h` 我们在本机写 `127.0.0.1`，当然你这儿也可以不加空格，这都没问题；再下方 `-P 3306`，我也加空格。这样也可以指定。但其实你这么指定的效果跟你上方不指定效果是一样的，因为默认就连接本地和 3306。当然还有一些场景，后边你还可以写一个库名——假如这里边有库叫 `mysql`，那这个时候你就直接连接到 `mysql` 这个库了。

但是这么写都有一个弊端。因为我们账号你写出来去体现也行，但密码如果直接在这儿写上，在开发中你周围有同事，你刚跟你同事闹点矛盾，同事一眼撇到你的密码了，记住你的密码了，那他有没有可能趁你上厕所登录你的数据库删库并且跑路呢？当然他删你库，你跑路。

> **易错点**：所以我们这个密码不建议明着写。

怎么做呢？可以这么写：

```bash
mysql -u root -p
```

我只写上 `-p`，后边其他写不写跟这个没关系。这回你 `p` 后边不写密码，当然你也可以继续有 `-h 127.0.0.1`，这样写是没问题的。如果你不写密码，当你按回车的时候它会提示你，让你去输密码，这个时候你再输入的密码就是隐式密码了。

> **提示**：我建议大家在连接的时候，`-p` 后边不要写密码，回车以后再输密码。

连接完毕以后注意，前面就会变成 `mysql>`，在这个中就可以写我们所谓的 SQL 命令了。后期我们学的所有 SQL 命令都可以在此处进行编写。

#### 三个基本命令：版本、注释、退出

先看一个最基本的命令，查看我们 MySQL 的版本。查版本有一个 SQL 指令：

```sql
select version();
```

这是一个固定的指令，查看 MySQL 版本。但是大家注意，我不加分号，我直接回车，我回车了很多遍，它也不执行。

> **易错点**：MySQL 中是以分号判定你这个语句是否结束的。如果你不加分号，它认为你没结束，你可以继续再写，它会追加到之前的命令中。但如果你想结束去执行，你必须要加分号。所以大家注意，千万别忘了分号，而且这个分号大家仔细看，应该是英文的分号。

紧接着下边一回车，这就查到了版本了。

然后是注释。你不能瞎写——如果你瞎写，加个英文分号，它会说不认识这个指令，不是一个正确的 SQL 指令。当然如果说你想写描述的话语，这叫注释，不执行的。MySQL 里有三种注释方案：

- `#` 开头的单行注释；
- `-- ` 开头的注释，但注意 `-- ` 后边必须加空格，否则它也不识别；
- `/* */` 包围的多行注释。

举例，假如我想加个注释，写个 `#`，写什么呢？写"SQL 指令"，就一回车，它也是成功的，它不会真正执行，它代表是一个注释的含义。这几种大家都可以去试试。

最后是退出连接。很自然，有个退出命令 `exit`。退出命令稍微有点特殊，它可以不用加分号，就直接执行了，因为最后一个关键字了，也没有其他的命令了，所以它可以省略分号。回车，说了个 `Bye`，这就已经相当于是退出了 MySQL 的一个连接。

到这里我们知道怎么连接、在哪个位置怎么写 SQL 语句了。连接与退出这个大家要去多试一试。

### 换掉黑窗口：可视化工具怎么选

接下来我们要进行第一章节的最后一个小节：去安装一个编写 SQL 语句的可视化工具。

到现在为止我们应该知道，我们用的是结构化查询语句，也就是 SQL 指令，能完成对数据库管理系统的操作，这指的是关系型数据库管理系统，而间接地去达到对数据库的操作。这个流程大家应该是没有问题的。

那么 SQL 语句写在哪呢？现在的 SQL 语句我们写到黑窗口，在这个工具中去编写 SQL 语句，而 Mac 是写在终端中。但是我想给大家去吐槽一个事情：命令行窗口、黑窗口太不好用了。

1. **它没有 SQL 提示**。你在写的时候只能自己硬写，没有提示，也不能去识别你是不是写对和错了。
2. **它不能备份**。在命令行窗口中写了很多条 SQL 语句，想把写的过程中备份发给大家，备份不了，没这能力。
3. **它不方便粘贴**。SQL 语句在黑窗口里面粘贴也比较麻烦。
4. **它不能批量执行**，只能单条语句单条语句执行。
5. **它不能可视化**。在这里边查出的结果也好，或者你想看你的库，都是一个非常丑的可视化界面，它没有一个美化界面。

总之后这玩意不好用。

> **结论**：到目前为止大家应该知道我要干啥了。我就是想把它给替换了，换一个更好的工具，这个工具替代的是黑窗口，进而去在里面能更好去编写我们的 SQL 语句。

市面上这些可视化工具其实有很多很多。

**SQLyog**——我们亲切地称它为小海豚，因为它的 logo 跟 MySQL 是一样的。我也推荐大家去安装这个 SQLyog。当然它也有收费版和免费版，它的免费版功能也比较弱，它的免费版也没有代码提示能力。但是，我用它我就看中这一观点，它没有代码提示和补全能力。

#### 界面分区：四个区域要认出来

这就是我们小海豚的可视化界面。我把它最大化，给大家分几个区域去看。

#### 写一条、执行、保存

写 SQL 语句怎么写呢？很简单，就来此处写：

```sql

```

这个我们建议还是加个分号，这个就搞定了。搞定以后大家发现这个工具有好处，它会识别你的关键字，会变成大写蓝色等。

第二种方案，假如我写了两条 `SELECT VERSION();`，但我只想执行其中某一条怎么办呢？那你第一步就选中它。选中了以后，不要点第二个了，就点第一个，这叫**执行查询**，执行你选中的。最后也是这个值。当然你也可以选中两条，也是可以的，这个都是没有任何问题的。

> **结论**：批量那个按钮指的是把这里边的所有 SQL 语句全部执行，而另一个位置实际上就是执行我选中的。

这个就是我们整个小海豚，很明显比 CMD 会好用很多。

## 一条数据是怎么进到数据库里的
> 对应块：BLK03 | 覆盖分集：P14-P20 | 块标题（分集名）：《14-数据定义篇-一条数据的存储过程》

### 先想清楚：一条数据要过几道关

数据库的准备工作已经全部搞定了，接下来正式进入 DDL 这部分。但在敲第一条语句之前，我们先退一步，想一个特别朴素的问题：

**一条数据，到底是怎么进到数据库里的？它大概要经历哪些过程？**

把大象装冰箱分三步，我们把一条数据装进数据库，得过四道关：

```text
  一条数据 → 数据库

  第①步  创建数据库
          库是最大的容器；没库，数据无处安放
          CREATE DATABASE 数据库名;
                    │
                    ▼
  第②步  明确要存哪些字段
          字段清单没理清，第三步根本无从下手
                    │
                    ▼
  第③步  创建表
          字段名 + 类型 + 约束，容器正式成型
          CREATE TABLE 表名 ( 列名 类型, ... );
                    │
                    ▼
  第④步  插入数据
          往容器里放东西——从这一步起，就不是 DDL 的地盘了

  ─────────────────────────────────────────
  前三步：造容器、管容器   →  DDL
  第四步：往容器里放货     →  DML
```

注意第二步：创建表之前，**先要明确存的这类数据应该有哪些字段**。不明确字段，你根本没法去创建表。我们平常说的数据操作都是由这四步组成，而前三步就是**数据定义语言**。

它主要是完成容器相关的操作——库管理和表管理。所以我们一定得先学它，容器都没有，谈什么往里面放数据。

DDL 这一部分我们分四小节来过：

- 先把 DDL 的作用和内部关键字再强调一遍，让大家重新清晰一下；
- 在写 SQL 之前，先把自己的命名行为规范起来，后期整体会顺很多；
- 开始讲容器的操作，主要是库管理的语句怎么写；
- 最后讲表管理的语句。

### DDL 是什么，以及它的三个关键字

大概理解了流程之后，我们系统介绍一下这个概念。

老说 DDL，它是怎么来的？**Data Definition Language**，数据定义语言，三个单词缩写而成。它的主要作用是**定义和管理数据库的结构**。

这个"结构"里包含什么？包含我们要讲的库、表，以及后期可以优化扩展学习的索引、视图等等。这些对象的创建、删除、修改，全都在 DDL 里实现。创建一个库、删除一个库、修改库，创建表、修改表、删除表，它都能搞定。我们本次重点学习的，就是对库和表的行为操作。

还要理解一点：**DDL 不涉及对数据相关的操作。** 换句话说，DDL 不是玩数据的，它是玩容器的。当然也要理解——你要真把库删了，库里面的数据也就跟着没了，那也得跑路。它专注的是对容器的操作，关注的是对**数据结构和元数据**的操作，这就是 DDL。

至于它内部到底有哪些关键字，学 SQL 语句其实就像学 Java 一样，记它的关键语法和关键字。DDL 一共有三个关键字，大家记住就可以了：

- 第一个叫 `CREATE`，单词的含义就是创建。用这个关键字，最终可以完成库、表、索引等的创建。
- 第二个叫 `ALTER`，翻译过来是修改的意思，指的是可以用它去完成我们库、表等等相关的修改，以及列的修改。
- 还有一个叫 `DROP`，一个极其危险的关键字——删除。可以用它去完成库、表、索引相关的删除。

先大概了解这三个。后期在学的时候，我们都以这个关键字去引发、触发对应的动作。这就是 DDL 的一个介绍。

### 规定和规范，根本不是一回事

在正式编写 SQL 之前，我们还有一项准备工作：**SQL 语句的命名的规定和规范**。

大家很多都是第一次接触 SQL 语句，我希望你们能使用最标准的 SQL 命名规范，编写出漂亮的 SQL 语句。等出去了工作，让别人一看一夸："这小伙子、小姑娘真棒。"

首先要澄清一点：**"规定"和"规范"是两个词，也是完全不同的意思。**

- **规定**指的是不能这么做。要是这么做了，相当于报错，类似于生活中的**法律**，是不能触犯的。
- **规范**指的是怎么做会更好。如果不这么做，也不会报错，它类似于生活中的**道德约束**。

举个例子：假如我去坐公交车，来了一个老头，我非常有道德，在没有座位的情况下可以让老头骑我脑门上，证明我这么做会更好；当然如果说我有座位，老头来了，我不给老头让座，这个东西我认为也不会有法律去触犯或者惩罚我。这就是规范。

了解了这层区别，下面先讲规定——确保大家先不犯错；再讲规范——怎么做会更好。

#### 标识符的五条规定

先介绍标识符，也就是这些容器的名称的命名规定。一共五条，必须围绕这个用法。

**第一条，命名长度不得超过 30 个字符。** 命名不要太长，一般情况下很少会超过这个点。

**第二条，命名只能包含大写的字母、小写的字母、0 到 9 以及下划线。** 除了这 63 个字符，其他都不能包含。而且它跟 Java 一样，**不能用数字开头**——这一点大家一定要记住。

**第三条，数据库、表、字段这些名称中间不能包含空格。**

**第四，名字不能重复。** 在同一个 MySQL 管理系统中，库名不能重复；在同一个库中，表不能重复；在同一个表中，字段也不能重复。

这条要展开说清楚它的层级关系。假如我有 A 库和 B 库，两个库中都有一个叫 `student` 的表，这是没问题的；但如果在 A 库中，不能出现两个 `student` 表。字段也一样——一旦重复了，你根本不知道操作的到底是哪一列。

**第五条，必须保证名称没有使用保留字、关键字。** 也就是说在命名的时候，不要去用数据库已有的那些关键字当作表名和容器名。这其实跟 Java 一个道理：在 Java 中定义一个属性，能不能叫 `class`？当然不行。

那如果我坚决要用关键字呢？举个例子，有一个订单表，订单就叫 `order`。可 `order` 除了"订单"的意思，它在数据库里还指的是排序关键字。怎么办？在这个容器的名称上加着重符号——**两个反引号包裹起来**：

```sql
`order`
```

这样它就不识别为关键字了。后期如果想对这个表进行操作，**在用的时候也要记得，插入数据、读取数据、指定表的时候都要加这个反引号**。

> **结论**：只要非得用关键字，不能直接用，加反引号的话关键字也是能用的——但是不建议。

看一下哪些命名是可以的，哪些是不可以的。

```sql
-- 可以
user_account                 英文，没超 30 字符
product_name                 用下划线连接
user__Name                   两个下划线，中间加一个大写字母

-- 不可以（会直接报错）
user account                 中间包含了空格
user-account                 中间用了特殊符号（连字符）拼接
select                       使用了 select 关键字
123user                      使用数字开头
```

`select` 那一行特别值得留意：把查询关键字放在名字前面，开发工具会误认为它就是一个关键字，所以会报错。上面这五条是硬规定，是不能打破的。

#### 比"不报错"更好的做法

规定讲完了，我们现在知道了：这些东西可以这么叫。但**它到底好不好**？后期创建库、表、列的时候该怎么叫，我心里边好像仍然没有一个标准。

为什么会出现这种情况？因为我们现在只知道**规定**——它只能告诉我们不能这么做，其实并不知道**规范**应该要怎么做更好。只知道规定但不知道规范，就没有标准。

这套规范来自国内非常知名的**阿里巴巴规范手册**。基本上国内的 Java 开发都围绕阿里巴巴这套规范手册进行命名、定义变量。这里边它也做了 SQL 的规范，来确保效率、安全性和可维护性。

规范中到底说了什么？第一点跟命名无关，但特别重要：**如果加了注释，注释是为了描述这段代码的，我们通过读取注释，不看代码就知道它干什么。** 所以一定要保证注释的描述是清晰、而且简洁的。如果注释写得很乱又不简洁，建议干脆别写——因为它已经成了一个错误的指南。

第二点，库、表、列名**应该使用小写**。注意，这个"应该"不是强制规定，用大写其实也行，但建议小写。为什么？因为很多开发工具会把关键字自动识别成大写，名称是小写，这样就把它区分出来了。反过来说，如果某个名称你写完之后莫名其妙变成了大写，那就证明它被写成关键字了。

而且，如果有多个词进行拼接，**推荐使用下划线**。这种命名形式叫**蛇形命名法（snake_case）**。不推荐使用 Java 中的驼峰式——可以用，但不推荐。

总结出来就一句：**命名用小写，如果多个单词之间用下划线拼接，这样最标准。**

第三点，库、表、列应该**简洁明了，具有描述性**。这跟 Java 中类似，起这些变量名一定是有描述性的。别瞎搞，也别用拼音，实在不行找个翻译软件翻译一下。

#### 库、表、列该怎么命名

上面三条是通用的，具体到库、表、列，我们逐个说。

**库的命名**应该跟应用程序是一致的。后期一个应用对应的是一个库，所以建议库跟程序对应。举个例子，如果有一个 Java 项目名，在数据库里不建议写成大驼峰，把它们都变成小写，两个单词之间用下划线连接就可以了。

**表的命名**最好遵循的是业务。表对应的是某个业务，一个库中有很多表，表对应的应该是业务——例如支付任务、强制项目，还有一些配置等等，可以用业务的名称去命名表。当然也没说必须是两层，如果只有一层，写成单层也是没问题的。

**列的命名**要遵循的是实体属性，因为列要装具体的某一个属性值，它代表的应该跟属性是一致的。它有点像 Java 中的属性命名，比如 `product_name`、`product_price`、`customer_id` 等等。

> **提示**：表命名相当于类命名，列命名相当于属性命名，只不过不是驼峰式，而是用下划线进行拼接。

| 对象 | 命名依据 | 标准写法 | 例子 |
|---|---|---|---|
| 库 | 对应的应用程序 | 小写 + 下划线 | `my_project` |
| 表 | 对应的业务 | 小写 + 下划线 | `user_account`、`order_detail`、`product_catalog` |
| 列 | 实体属性 | 小写 + 下划线 | `customer_id`、`product_price` |

这里有个细节要提醒：表的命名写三层是可以的，但注意，后面其实有点**冗余**。比如 `user_account_table` 后面的 `table` 就可以不用加了，`order_detail_table` 的 `table` 也没必要——省略一下更简短一些。

这就是规范性的命名。大家把这个好好掌握一下，后期我们就按照这个规定和规范统一标准命名。

### 建库：把字符集和排序规则一起交代清楚

讲完 SQL 命名规定和规范，接下来正式去学习数据库定义语言之对应的**库管理**。

对库的管理无非包含几个方向：库的创建、库的删除，还有库的修改和查看。因为 SQL 指令特别多，我们一个方向一个方向慢慢去磨、慢慢去学。先说创建。

在创建数据库的时候，首先需要明确一个事情：**只需要用对应的关键字，加上指定要创建数据库的名称就可以了。** 这是必需的、必须指定的，只有数据库名。除此之外，还可以在创建的时候去指定字符集和排序方式——如果对它们不太了解，没关系，我们稍后就介绍。字符集和排序方式是**可选的**，不指定的话，库就会选用 MySQL 提供的默认字符集和排序方式。

创建库一共有几个相关的命令，我们一个一个看。

**第一个：直接创建一个库**，不指定字符集和排序方式，也就是选用 MySQL 默认的。语法非常简单，DDL 创建的关键字叫 `CREATE`，后面紧跟一个空格，要跟一个 `DATABASE`。

```sql
CREATE DATABASE 数据库名;
```

为什么要跟一个 `DATABASE`，不直接 `CREATE` 数据库呢？因为 `CREATE` 不仅能创建库，后期它也能创建表，所以要指定创建的方向是什么。

写的时候是忽略大小写的，大小写都无所谓。空格隔开跟数据库名，分号结尾，特别简单。

**第二个：创建并且判断。** 第一个稍微有个弊端，如果创建的库存在，它会报错。第二种是一种更优雅的创建方式：

```sql
CREATE DATABASE IF NOT EXISTS 数据库名;
```

如果这个数据库不存在，我就创建；如果已经存在，也别报错，我就不创建。这种判断能避免库重复时出错。**推荐使用第二种。**

**第三个和第四个：在创建库的过程中指定字符集或者排序方式。**

```sql
CREATE DATABASE 数据库名 CHARACTER SET 字符集;
```

```sql
CREATE DATABASE 数据库名 COLLATE 排序方式;
```

这两个当然也都可以加上 `IF NOT EXISTS`。如果指定了字符集而没指定排序方式，那它的排序方式还走 MySQL 的默认值。

这是**单向指定**。如果想双向指定该怎么办？也很简单：

```sql
CREATE DATABASE 数据库名 CHARACTER SET 字符集 COLLATE 排序规则;
```

它俩不分先后，只要把它们都写上，代表既创建了一个库，同时自己指定了字符集和排序规则。

#### 字符集决定会不会乱码

语法大概知道了，可字符集和排序规则到底是什么呢？

**所谓的字符集就是我们常说的编码格式。** 我们存储的这些字符，最终都是用字节存储的；字符集指的就是字符和底层存储的字节如何进行对应。我们要选择一个正确的字符集，否则就会出现常说的乱码问题。

如果想使用中文，一般选用国际上知名的编码格式，即 UTF 系列，它内部可以进行中文的存储和映射。在 MySQL 中常见的字符集有两个：

| 字符集 | 一个字符占几个字节 | 覆盖能力 | 建议 |
|---|---|---|---|
| `utf8` | 3 字节 | 存不下全部中文符号，有些符号找不到就乱码 | 不推荐 |
| `utf8mb4` | 4 字节 | 存储宽度更广，基本覆盖所有中文相关内容，表情符号也能存 | MySQL 8 默认，推荐 |

这里面的来龙去脉值得说清楚。`utf8` 是 MySQL 早期版本的默认字符集，如果用的是 5.7 或 5 系列版本，默认字符集就是 `utf8`。它用三个字节存一个字符——只有三个字节，存储的位数少一些，有些符号找不到，于是就出现乱码，所以**不推荐使用 `utf8`**。

随着 MySQL 的更新，现在用的是 8 系列版本，现在的默认字符集叫做 `utf8mb4`。为什么加个 `mb3` 的后缀？**因为早期把 `utf8` 这个名称占用了**，更新之后只能叫 `utf8mb4`。`utf8mb4` 指的是用四个字节去映射和存储字符，存储的宽度更广。

#### 排序规则决定字符怎么比

排序规则是在字符集的基础上，决定字符之间**如何进行比较**的。

例如数据库里存了一个小写的 `a` 和一个大写的 `A`，我们用等号去比较判断：

| 排序规则 | 含义 | `'apple' = 'Apple'` 的结果 |
|---|---|---|
| `utf8mb4_0900_ai_ci` | 大小写不敏感 | 判定为真，值为 1 |
| `utf8mb4_0900_as_cs` | 大小写敏感 | 判定为假，值为 0 |

```text
  字符集   =  字符怎么变成字节     →  决定"会不会乱码"
  排序规则 =  字符之间怎么比较    →  决定"a 和 A 等不等于"

  MySQL 8 的默认值是 utf8mb4 + utf8mb4_0900_ai_ci
  也就是：四个字节存字符，且忽略大小写
```

在 MySQL 8 系列版本中，默认选用的是第一种，即不区分大小写。后期在查询数据做对比时，大小写是被忽略的，判定为相等。如果业务需求对大小写敏感，就可以把排序规则换成 `as_cs`。

#### 两者必须成套出现

这两个概念很容易记混，一句话钉死它：**字符集决定是否乱码，排序规则决定字符如何对比。**

如果想查看当前配置，可以通过指令 `SHOW VARIABLES LIKE ...` 来查看字符集和当前数据库的排序规则：

```sql
SHOW VARIABLES LIKE 'character_set_database';
SHOW VARIABLES LIKE 'collation_database';
```

我们来做个实战小练习：创建一个名为 `ddl_d1` 的库，指定字符集为 `utf8`，排序方式指定为大小写敏感的 `utf8mb4_0900_as_cs`：

```sql
CREATE DATABASE IF NOT EXISTS ddl_d1 CHARACTER SET utf8 COLLATE utf8mb4_0900_as_cs;
```

执行后会报错，提示排序规则不能在该字符集中使用。

> **易错点**：因为写的是 `utf8`，它等同于 `utf8mb3`，与 `utf8mb4` 不是一套，**排序规则必须在对应的字符集下设置**。

所以必须选用 `utf8mb4`：

```sql
CREATE DATABASE IF NOT EXISTS ddl_d1 CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;
```

执行成功，刷新连接后数据库就创建完成了。

至此，建库的语法我们回顾一遍——先是 `CREATE` 关键字加 `DATABASE`，然后判断并创建、单独指定字符集、单独指定排序方式、或者两者同时指定：

```sql
CREATE DATABASE 数据库名称;
CREATE DATABASE IF NOT EXISTS 数据库名;
CREATE DATABASE 数据库名 CHARACTER SET 字符集;
CREATE DATABASE 数据库名 COLLATE 排序方式;
CREATE DATABASE 数据库名 CHARACTER SET 字符集 COLLATE 排序方式;
```

### 看库、切库：四个必须会的小语句

接下来讲数据库的查看和使用，这一部分语句不多，但全都是天天要用的。

```sql
SHOW DATABASES;
```

查看 MySQL 中的所有库。注意这里用的是**复数**形式 `DATABASES`——因为库有多个。

```sql
SELECT DATABASE();
```

查看当前使用的数据库。注意这是一个**函数**，带一对小括号。MySQL 中可以有很多数据库，对数据进行操作的前提是必须先选中一个库，那怎么知道现在选中的是哪个库呢？就靠它。

```sql
SHOW TABLES FROM 数据库名;
```

查看某个数据库下的所有表。

```sql
SHOW CREATE DATABASE 数据库名;
```

查看当初创建该数据库时的那条完整建库语句。

```sql
USE 数据库名;
```

选中数据库，也就是切换数据库。在对数据进行操作之前，**必须先选中库**，第一件事就是执行 `USE 数据库名;`。如果要切换到其他库，再次执行一次即可。同时，**只能有一个库处于被选中的激活状态**。

在客户端工具里我们过一遍：`SHOW DATABASES;` 下方结果会把现有的库全部罗列出来；`SELECT DATABASE();` 返回当前所在的库，执行 `USE mysql;` 切换之后，再查一次返回的就是 `mysql`；`SHOW TABLES FROM mysql;` 可以查看该库下的所有表；`SHOW CREATE DATABASE ddl_d1;` 能看到当初创建该库时的完整 DDL 语句与字符集配置。

### 改库、删库，以及那个不能改的名字

修改和删除数据库的相关指令，先说修改。

**修改数据库只能修改字符集和排序方式，不能直接修改数据库的名称。** MySQL 没有提供直接重命名数据库的语法。如果某些可视化工具提供了修改库名的功能，那它的底层做法无非就是：将旧库备份导出，创建新库导入数据，再将旧库删除。

修改字符集的关键字就是 DDL 中的 `ALTER`：

```sql
ALTER DATABASE 数据库名 CHARACTER SET 字符集;
ALTER DATABASE 数据库名 COLLATE 排序方式;
ALTER DATABASE 数据库名 CHARACTER SET 字符集 COLLATE 排序方式;
```

一般把字符集写在前面，因为排序方式依赖于字符集。

> **易错点**：数据库中**没有修改名称的指令**。如果想改名字，需要先备份数据，删除旧库，创建新库并指定新名字，再恢复数据。

接下来是删除。删除数据库是一个极其危险的操作，必须三思而后行。删除方式有两种：

```sql
DROP DATABASE 数据库名;
```

以及带判断条件的优雅删除：

```sql
DROP DATABASE IF EXISTS 数据库名;
```

第二种会先判断该数据库是否存在，存在则删除，不存在也不会报错。

这里有一个细节特别容易搞混，大家注意：当初我们在创建的时候有一个 `IF NOT EXISTS`，代表不存在才创建；而删除这边是 `IF EXISTS`——**你有、存在，才能删除，这里边没有 `NOT`**。后面跟数据库名就可以了。

> **注意**：删除是一个危险命令，一定要确认、明确再操作。如果没确认，可别擅自做这个事，跑路犯不上。

### 光说不练假把式：完整跑一遍库管理

俗话说光说不练假把式。库管理的命令虽然不多，但也不少。接下来我们通过一个实战场景来检验一下你是否真的掌握了。

场景一共五个，我们在控制台上实现一遍。

**第一个，创建一个博客平台的库，指定字符集。** 它要支持多语言存储，说白了就是要选择一个更宽度的字符集，选用的是 `utf8mb4`；排序规则选默认方式就可以了：

```sql
CREATE DATABASE IF NOT EXISTS blog_platform CHARACTER SET = utf8mb4;
```

建议大家要加 `IF NOT EXISTS`——如果不存在我创建，防止已经存在了导致这条命令报错。有人说我们现在用的是 8.2.0，不写不就可以了吗？**现在不写确实是可以的**，但是为了考虑我们能兼容更多的平台和版本，只要有这种显式的要求，你就要把它写上。

执行一遍，数据库就创建好了。刷新一下，是不是就有了？

**第二个，查看当前库的字符集和排序规则。** 那你就先切换一下：

```sql
USE blog_platform;
```

切换成功之后，用我们记过的两条变量查询：

```sql
SHOW VARIABLES LIKE 'character_set_database';
SHOW VARIABLES LIKE 'collation_database';
```

字符集查出来是 `utf8mb4`；排序规则查出来是默认值 `_ai_ci`，也就是忽略大小写。

**第三个，修改排序规则。** 后续发展中我们决定，书名英文有大写有小写，想区分大小写，要改一下对应的排序规则。这个很简单，修改用 `ALTER`：

```sql
ALTER DATABASE blog_platform COLLATE utf8mb4_as_cs;
```

哪个库就叫 `blog_platform`，最后 `COLLATE` 下方写上你要指定的排序规则就可以了。大家注意，你在指定之前，**排序规则其实跟我们的字符集是配套的**。因为我们前边是 `utf8mb4`，所以说你可以选它；如果你是 `utf8`，那是选不了它的。

**第四个，再查看一次修改后的字符集和排序规则**，确认已经变成 `_as_cs` 了，搞定。

**第五个，项目凉凉了，删库跑路：**

```sql
DROP DATABASE IF EXISTS blog_platform;
```

建议加一个判断。最后 `IF EXISTS`，如果它存在我再删除。选中执行，完毕。

不过这里我们现场翻车了一次——完事以后执行 `SHOW DATABASES;`，发现这个库怎么没删成功？来对比一下，`blog_platform`，果然是名字写错了，敲成了 `plat`。命令本身肯定不能错，是手滑了。刷新，这回再看，库里没有了，列表里也没有了。最后再 `SHOW DATABASES;` 一下，已经没有这个库了。

整个流程就练完了。大家按照我这种思路把它自己练一遍——注意最后这一步，真实项目里库名是手敲出来的，**删库前一定要拿眼睛再核对一遍名字**。

### 表管理：一条语句造出一个容器

接下来我们进入数据库定义语言的最后一小节，关于表的管理。

在讲表管理之前，先提前给大家打个预防针：**表的管理语法一定是会比库管理复杂很多**，而且我们平时对表的操作也会更多一些。

同样，表也分创建、修改、查看以及删除，我们一项一项说明。先说创建。

#### 建库和建表，难度不是一个量级

在创建之前我们需要理解几个东西：**创建库和创建表有什么不同？**

大家知道，创建库就好比我们在计算机里创建了一个 Excel 表格**文件**——其实我们只需要指定文件的名字或者字符集就可以了，它就这么简单。

但大家想个问题：如果你要创建表，那不就相当于我们在这个文件内创建一个**表格**吗？表格除了写名字、字符集等等，我认为它还有好多东西要写——例如表里边有哪些字段，字段都叫什么名，这个名字又有什么类型等等。

所以创建表的时候，一般需要指定表名、字符集、以及表中的字段（也就是所谓的列）和列的类型等等，还要加一些其他的描述符。它的语法会很复杂。

那么 MySQL 是怎么把创建表的这么多元化、复杂的这些内容，混合到一个语句中去的呢？这个语句长什么样呢？

不要急，我们一点点去拆解它。

#### 一个建表语句，逐段读给你看

```sql
CREATE TABLE `post` (
    `post_id` INT NOT NULL AUTO_INCREMENT,
    `title` VARCHAR(255) NOT NULL COMMENT '帖子标题',
    `content` TEXT NOT NULL,
    PRIMARY KEY (`post_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='论坛帖子表';
```

大家跟着我简单读一读。首先 `CREATE TABLE`，很明显这是关键字。紫色的都是关键字。创建一个表叫什么呢？叫 `post`，这个就是表名了。到这为止是表名，而表名后边跟了一个括号。

大家发现了吗？括号里边可以先不说，**括号后边又跟了一堆的东西**，那一堆就是对表的一些描述——例如说它用的是哪个存储引擎，以及表的字符集、表的一个注释等等。而在表的括号内部，写的就是列相关的东西了。

第一个它有叫 `post_id` 的这一列——这就相当于我们给列起名字，这个是什么类型呢？`INT`，是个整数类型，后边加一些描述符等等；逗号隔开，这是另外一列，叫 `title`；是什么类型？是这个类型；最后加一些描述，加个 `COMMENT`，这也是注释的意思。下方同样逗号隔开就好。

总而言之，大致我能看懂这个表中有几列，类型也大致能看懂——但是这个语法还是稍有点乱，对不对？没关系，我们一点点去总结。

#### 必写的三样，和可写的那些

第一步。大家看到这是一个建表的完整语句，我们把它拆成骨架看：

```text
  ┌──────────────┬─────────────────────────┬────────────────┐
  │ ① 表名       │ post                    │ 必须           │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ② 列名       │ post_id / title        │ 必须，逗号隔开 │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ③ 类型       │ INT / VARCHAR(255)     │ 必须           │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ④ 列约束     │ NOT NULL / AUTO_INC    │ 可选           │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ⑤ 列注释     │ COMMENT '帖子标题'     │ 可选，强烈建议 │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ⑥ 表级约束   │ PRIMARY KEY (post_id)  │ 可选           │
  ├──────────────┼─────────────────────────┼────────────────┤
  │ ⑦ 表描述符   │ ENGINE / DEFAULT CHARSET │ 可选，一般不写 │
  └──────────────┴─────────────────────────┴────────────────┘
```

逐条说清楚：

**第一个必须指定的要素是表名。** 把 `post` 这个位置换成我们自己的表名就可以了。

**第二，往后走，我们发现这中间有很多列，那些列名都是自定义的**，后期由我们自行指定就可以了，这也是必须要写的——要指定有哪些列。列和列之间，大家看，是不是用**逗号**隔开的。

**第三点大家注意，这有什么 `INT`、`VARCHAR` 等等，这些东西最终都会变成类型。** 你的列存什么类型，也是需要我们显式地指定的，而且必须指定。这三点是创建表时必须指定的，**只要这三个指定了，其他的都可以不写**。单不单纯？

下面还有很多，我们整理一下。

**列后面的约束。** 有人说约束不太懂，后边我们会专门讲，但这里我大概给大家说一说。**约束是对我们数据进行一些限制的语法。** 假如说我这有一个手机号，手机号你可以不填、可以没有，但你要填了必须唯一；还有身份证号，你必须都得填，且唯一。在这里边可以加一个或者 n 个。这些东西也可以加，也可以不加。

**列后面的 `COMMENT`**，这就是我们每个列的一个注释、一个描述，它代表什么含义。而 `) ENGINE=...` 后面的那个 `COMMENT`，这就是表的一个注释。

**再往前的表描述符。** 大家回头看一下，`COMMENT` 之前这一段，指的是表的一些描述符——例如它是哪个存储引擎，以及表的字符集格式等等。当然表可以不指定字符集，不指定就选用库的字符集。一般表也都不写这些东西，听我说，都不写；第一个选择存储引擎也都不写。但你要知道如果想写怎么写呢？就在后边直接加 `key=value`，多组直接空格隔开，`key=value` 空格 `key=value` 就可以了。

> **结论**：整个表的骨架就是——`CREATE TABLE 表名`，加个括号，写**列名、类型**，逗号隔开，列名、类型，逗号，列名、类型；每列类型后边可以加一些约束或者加注释，这些前期都可以不写；最后括号隔开以后，是表的一些约束限制，再加个表注释，就完事了。

然后是那几个带 `COMMENT` 的东西——虽然它们是可选的，**但是我们推荐大家在创建表的时候都给表还有列加上注释**，这样我们在读的时候就更清晰：这个表、这个字段是什么含义。

单不单纯？也就是说，有一天我们也不保证在哪家公司呆很久。假如我们离职了，我们希望我们的后人来了以后能看见这个表它是代表什么含义，看得更清楚——根据这个注释。

单不单纯？有人说了，我都离职了，管他干啥呀。**前人栽树，后人乘凉嘛。** 你想想你去新公司，人家有注释，你是不是开心呢？同理心嘛。

最后我们把表创建语法再补充完整。除了刚才那种创建方式，还有一种更优雅的语法：**后边都不变，只需要在前面加个 `IF NOT EXISTS`**。

```sql
CREATE TABLE IF NOT EXISTS 表名 (
    列名 类型,
    列名 类型
);
```

大家应该能理解了，我们创建库的时候 `CREATE DATABASE IF NOT EXISTS ...` 也加了这句话。数据库中一个库中表是不能重复的，所以如果直接创建、表已存在，它会报错，因此**建议加上这个 `IF NOT EXISTS`**。顺便再提一句：方括号是可选的意思，**不要真的写方括号**。

那我们再强调几个注意事项：

- **第一个**，必须要写的只有表名、列名和类型。当然要配合关键字、括号、逗号，这肯定要写。
- **第二个**，表在创建的时候推荐使用 `IF NOT EXISTS` 这种优雅的方式创建，避免我们程序在运行过程中报错。
- **第三个**，就是注释这个玩意儿。约束这些东西我们后边会讲，其实也可以不加；但**注释虽然不是必须的，却是很有必要的**。我建议大家把注释都加上。而且还有一个注意事项——**你们在写的时候，一定要保证注释描述是清晰的**。
- **最后还有一个小细节**：如果你写了多个列，列名、类型，列名、类型——注意列之间要用逗号隔开，**而且逗号一定是英文的**。

这就搞定了。大家回忆一下：这就相当于我们平时在电脑中创建了一个表格，这个表格叫什么就相当于我们的表名；表中创建几个列，就相当于一列、两列、三列、四列；这个列存什么类型呢？代表你指定的后边类型的指定。列的一些注释描述是用 `COMMENT` 去描述的，当然还有一些约束限制也是在括号里写的。

这就是整个创建表的一个语法。大家把这里好好记记，下一节课我们先利用这些语法简单做个实战。

### 本讲提到的题目

**题一：综合实战——博客平台建库流程**

> 创建一个博客平台的数据库，要求支持多语言存储。完成后依次完成查看当前库的字符集与排序规则、把排序规则改为区分大小写、再查看一次确认修改结果，最后项目放弃，删库跑路。

**解析与答案：**

1. 创建库。要支持多语言存储，就得选更宽度的字符集 `utf8mb4`，排序规则用默认即可：
   ```sql
   CREATE DATABASE IF NOT EXISTS blog_platform CHARACTER SET = utf8mb4;
   ```
2. 先切库，再查两个系统变量：
   ```sql
   USE blog_platform;
   SHOW VARIABLES LIKE 'character_set_database';
   SHOW VARIABLES LIKE 'collation_database';
   ```
   预期结果：字符集为 `utf8mb4`，排序规则为默认的 `_ai_ci`（忽略大小写）。
3. 改排序规则为大小写敏感：
   ```sql
   ALTER DATABASE blog_platform COLLATE utf8mb4_as_cs;
   ```
4. 重复第 2 步的两条查询，确认排序规则已变为 `_as_cs`。
5. 删库跑路：
   ```sql
   DROP DATABASE IF EXISTS blog_platform;
   SHOW DATABASES;
   ```

本题的坑在第 3 步：排序规则必须与字符集配套。当前库字符集是 `utf8mb4`，所以只能用 `utf8mb4` 系的排序规则；若字符集是 `utf8`（即 `utf8mb3`），这条 `ALTER` 会直接报错。

**题二：建库时指定字符集与排序规则**

> 创建一个名为 `ddl_d1` 的数据库，指定字符集为 `utf8`，排序方式为大小写敏感的 `utf8mb4_0900_as_cs`。

**解析与答案：** 按题面直接写会报错——`utf8` 等同于 `utf8mb3`，与 `utf8mb4` 不是一套，排序规则不能在该字符集中使用。改正办法是把字符集换成 `utf8mb4`：

```sql
CREATE DATABASE IF NOT EXISTS ddl_d1 CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs;
```

这道题考察的就是"字符集与排序规则必须成套出现"这一点，面试和实际开发中都经常被追问。

## 建表语法、实战与常用数据类型
> 对应块：BLK04 | 覆盖分集：P21-P24 | 块标题（分集名）：《21-数据定义篇-表创建实战练习》

创建表的基本语法讲完了，先别急着往下走。停一下，把这套语法在脑子里过一遍，然后我们动手实战一次，看看大家是不是真的把它掌握住了。

练完创建表，还有一个绕不开的问题：语法里那个"列类型"到底能填什么？这正是我们接下来要系统拆开的东西。

### 建表语法：括号里放列，括号外放表描述

先来回忆一下 `CREATE TABLE` 的结构长什么样——你可以在脑子里默写，也可以在公屏上打一遍，第一个关键字当然是 `CREATE`，后面跟 `TABLE`，再往后是表名。

但这只是一种写法。你还可以在中间加一个 `IF NOT EXISTS`，表示"表不存在才创建"。

表名写完，是一个括号。**这个括号内部放的是列的信息，括号外部才是表级别的描述**——比如字符集、排序规则，还有表注释。这一点最容易被忽略，一定要把内外分清楚。

括号里面，每一列的结构是：

```text
CREATE TABLE [IF NOT EXISTS] 表名
(
    列名1   列类型1   [列约束1]   [COMMENT '列注释1'],
    列名2   列类型2   [列约束2]   [COMMENT '列注释2'],
    ...
    列名N   列类型N   [列约束N]   [COMMENT '列注释N']   ← 最后一列后面不加逗号
)
[表选项：字符集 / 排序规则 / 表注释]                    ← 括号外才是表级别的描述
```

列里面，**必写的是列名和类型，两者用空格隔开**。除此之外还可以有列的约束、列的注释。列与列之间用逗号隔开，下一列接着往上写，可以有很多列。

> **易错点**：最后一列切记千万不要加逗号，加了直接报错。最后一列省略逗号，直接跟右括号结尾就可以了。

那么，创建表语法一共有四个注意事项，记住这四条基本不会出事：

1. **列名和列类型是必须填写的**，其他都是可选的；
2. **推荐使用 `IF NOT EXISTS` 这个语法**；
3. **注释不是必须的，但很有必要**。前期大家写的时候，尽量用最标准的方式去创建；
4. **列之间用逗号隔开，最后一列不要逗号**。

> **结论**：表名对标的是**业务**，列名对标的是**属性**。这两项按 SQL 的命名规定和规范来填就行。

### 实战：在线图书管理系统

实战有两个场景：第一，创建"在线图书管理系统"的库，并且要选择对应的字符集和排序方式；第二，在库中创建一张 `books` 表，这张表需要手动设置字符集、加上注释内容，并且在表里创建指定的三列。三列的类型我已经给定了，大家自己再补一个注释就行。

切到客户端，我们一步一步来。

#### 建库并切换到它

先创建库。`CREATE` 之后别写错了，这里是 `DATABASE`，不是 `TABLE`；后面跟上 `IF NOT EXISTS`，这是标准写法。

```sql
CREATE DATABASE IF NOT EXISTS books_labs
DEFAULT CHARACTER SET utf8mb4
COLLATE utf8mb4_general_ci;
```

字符集我们要**显式写出来**，不要图省事用默认值——避免不同版本的默认字符集不一样。`utf8mb4` 是字符集，后面这个排序方式是**不区分大小写**的（名字末尾的 `ci` 就是这个意思）。

库建好了，别忘了**切换到这个库**：

```sql
USE books_labs;
```

只有切过来，后面创建的表才会落在这个库中。执行完在客户端的数据库列表刷新一下就能看到它了，列表没自动刷新没关系。

#### 建表 books，并解读那三列

接下来建表。`CREATE TABLE IF NOT EXISTS books`，中间是列的信息，后面是表级别的描述。

**这里要注意**：如果你不设置编码格式，它默认走的就是库的编码格式；想显式写出来，就用 `CHARSET`——`CHARSET` 后面紧跟等号，写 `= utf8mb4`，这是固定的语法格式，记住它就行。

之后推荐给表加个注释，注释叫 `COMMENT`，挨着写，中间加空格。

> **提示**：注释内容在 MySQL 里可以用双引号，也可以用单引号，**推荐用单引号**，这才是 MySQL 的语法规则。Java 里我们习惯用双引号标注字符串字面量，两个东西别混了。

```sql
CREATE TABLE IF NOT EXISTS books
(
    book_name   VARCHAR(20)  COMMENT '图书名',
    book_price  DOUBLE(4, 1) COMMENT '图书价格',
    book_number INT          COMMENT '图书数量'
) DEFAULT CHARSET = utf8mb4 COMMENT = '图书表';
```

题目要求的三个列，类型是给定的，我们逐个看一遍它到底意味着什么：

- `book_name VARCHAR(20)`——`VARCHAR` 是短字符串类型，后边的 `20` 翻译过来是**最大长度 20 个字符**，超过会报错。注释写"图书名"。
- `book_price DOUBLE(4, 1)`——明显是图书价格。`DOUBLE` 是浮点类型，括号里的 `4,1` 表示**总共四位，其中一位是小数**，所以整数部分只能占三位。注释写"图书价格"。
- `book_number INT`——图书的数量，`INT` 是整数类型。注释写"图书数量"。

三列写完，最后一列后面**千万别加逗号**，加了直接报错。然后收尾一个分号。

写完别急着敲回车，先验证一下有没有创建成功。点开客户端的数据库列表，展开 `books_labs`，`books` 就在里面了。或者直接敲一条命令，查看某个库下的全部表：

```sql
SHOW TABLES FROM books_labs;
```

> **结论**：这个案例掌握以后，你就能掌握基本的创建表语法了。类型具体有哪些、约束是什么概念，后面会详细讲；前期把基本语法掌握住就可以了。

### 整数类型：五种写法与它们各自的边界

创建表有三项是前期必须填写的：表名、列名、还有类型。前两项按命名规范填就行，那第三项"类型"到底怎么选？

大家可以先自己想一想：假如领导让你统计一个员工，建一张表，里面有姓名、年龄、性别、身高、工资、生日、入职日期……你在脑子里把这张表构建出来，会发现**常用的数据类型其实就那么几种**：姓名和性别是字符串，年龄是整数，身高是浮点，工资是更精准的浮点，生日和入职日期是日期类型。

所以 MySQL 提供的类型并不复杂。常见的就是**整数、浮点、定数、字符串、日期**这几类；此外还有很多其他特殊类型以及 JSON 类型，但那些我们课程里用得少，就不多讲了——想了解的可以自己点开官方文档下面的类型列表看一看。

#### MySQL 提供了哪些整数类型

MySQL 支持的整数类型有以下几种：`TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT` 以及 `BIGINT`。

这里有个小细节：`INT` 这里边有两个写法，写成 `INT` 或者写成 `INTEGER` 都可以，它俩是同一个东西。

还有一个概念要分清楚。在**标准 SQL** 中，只有 `INT`、`INTEGER` 和 `SMALLINT` 是标准的；而我们接下来要讲的 MySQL 里的 `TINYINT`、`MEDIUMINT`、`BIGINT`，这三种属于**方言**——标准不支持，是 MySQL 单独扩展出来的。这一点大家要记住。

#### 从存储字节推值范围

那为什么它要提供这么多整数类型呢？道理和 Java 一样——Java 里也提供了很多整数类型（byte、short、long、int），因为不同的整数类型，它**范围不同，占有空间大小也不同**。我们最终用的时候，只要选择一个合适的范围就可以了。

先看存储空间，再看值范围，你会发现**后边的范围不用背，从存储字节就能自己算出来**：

| 类型 | 存储空间 | 无符号最大值 | 有符号范围 |
| :--- | :--- | :--- | :--- |
| `TINYINT` | 1 字节 | $2^8 - 1 = 255$ | $-128 \sim 127$ |
| `SMALLINT` | 2 字节 | $2^{16} - 1 = 65535$ | $-32768 \sim 32767$ |
| `MEDIUMINT` | 3 字节 | $2^{24} - 1 = 16777215$ | $-8388608 \sim 8388607$ |
| `INT` / `INTEGER` | 4 字节 | $2^{32} - 1$ | $-2^{31} \sim 2^{31} - 1$ |
| `BIGINT` | 8 字节 | $2^{64} - 1$ | $-2^{63} \sim 2^{63} - 1$ |

算法就是这么简单：一个字节是 8 位，所以 1 字节类型能表示 $2^8$ 个不同的值。

- **无符号**的情况下（就是没有负号），取值是 $0 \sim 2^{8n} - 1$。所以 `TINYINT` 是 0 到 255，256 才是最大值，算一个零是 255；
- **有符号**的情况下，就是把这个范围**对半分**，一半是负的、一半是正的，正的那半算上零。所以 `TINYINT` 就是 $-128 \sim 127$，`SMALLINT` 是 $-32768 \sim 32767$。

顺着这个规律往下推：`MEDIUMINT` 占 3 个字节，就是 $2^{24}$，无符号到 16777215，有符号就正半分；`INT` 占 4 个字节，就跟 Java 的 `int` 一样；最大的 `BIGINT` 占 8 个字节，$8 \times 8 = 64$ 位，无符号是 $2^{64} - 1$，有符号就是 $-2^{63} \sim 2^{63} - 1$。

> **提示**：`SMALLINT` 的范围跟 Java 的 `short` 是一致的；`BIGINT` 对标的是 Java 的 `long`；`INT` 对标 Java 的 `int`。`MEDIUMINT` 在 Java 里没有对应的参考类型。

#### 有符号与无符号

说到这儿，肯定还有人蒙：什么叫"无符号"，什么叫"有符号"？

有一个修饰符叫 `UNSIGNED`，这个修饰符的意思就代表着**无符号**。

假如你声明一个 `age` 列，等于 `TINYINT`，不写任何别的东西——**默认它就是有符号的**，代表它有负号也有正值，采用的范围是 $-128 \sim 127$。你不能超过这个存储范围，超了会报错。

那有人说，我这个年龄也不可能活成负值啊，怎么办？我想全要成正值，怎么弄？

很简单，再加一个修饰符 `UNSIGNED`。"UN"代表"没有"，`SIGNED`代表"符号"，这是固定的。它要**跟在数值类型之后**，代表我这个范围没有负号。**没有负号，就把负号那一半的范围去掉，挪到正值那边去**，所以范围变成了 $0 \sim 255$。

总结一下：

- 什么都不写 → **有符号**，从负数开始到正数；
- 类型后面加 `UNSIGNED` → **无符号**，从 0 开始一直到最大值。

> **易错点**：`UNSIGNED` 只能跟着**数字类型**用，并且要**紧贴着数值类型后边写**，它俩相当于一一组合，要写就一起写，别拆开放。

#### 怎么选：范围先满足，再省空间

选数据类型主要考虑两点：

1. **它的范围是否符合**——要保证范围能覆盖你要存的数据的值范围，否则会报错；
2. 在范围符合的前提下，**选占有空间最小的那个**，这样相当于节省空间。

举个例子：假如要声明一个年龄，选哪个比较合适？我认为选 `TINYINT` 会合适一些——它符合年龄的实际情况，人也活不到 255 岁，而且占用空间小。

你说我用 `INT` 行不行？当然也行，`INT` 的范围更大，也能存下你的年龄；但是 `INT` 固定就占 4 个字节，占有的空间会更大一些。

反过来还有一种情况：如果**范围不确定**，比如一个学号，可能很大也可能很小，咱们不确定。那这个时候如果你要不确定，**建议尽量选大的**，因为宁可多占点空间，也不能报错。

### 浮点与定点：M、D 和精度的取舍

整数讲完了，我们介绍数值类型中的另一个方向——**浮点类型**。

什么叫浮点？就是在声明的时候可以写小数点的数。比如你的身高 1 米 85 点 6，这个点后面的小数点是整数类型存储不了的。

#### float 与 double

浮点类型它也有两个：一个是 `FLOAT`，一个是 `DOUBLE`，跟 Java 中一样，一个是单精度，一个是双精度。`FLOAT` 占有 4 字节空间，`DOUBLE` 占有 8 字节空间。

它们俩在声明的时候跟整数类型有点不同：**声明以后，后边需要加个括号，括号里分别写一个 M 和 D**。

- **M** 指的是所有位置的总长度——整数和小数位的长度之和，小数点不算在里面。比如我有个 1.1，它现在是两位，一位整数一位小数，点不算；
- **D** 指的是小数位数。

这两个是对你这个数值类型的一个限制。举个例子，假如我写个 `FLOAT(5, 2)`，这代表着我这个 `FLOAT` 类型最大只能装 `999.99`。M 是 5，指的是我整个数一共是五位；D 是 2，指的是小数点后边一共是两位；那 5 减 2，说明最终整数部分也只能写三位。相当于是对这个也有个长度限制。

它俩的 M 范围也不一样：

| 类型 | 存储空间 | M 最大值 | D 最大值 |
| :--- | :--- | :--- | :--- |
| `FLOAT` | 4 字节 | 24 | 8 |
| `DOUBLE` | 8 字节 | 53 | 30 |

`FLOAT` 的 M 最大是 24，也就是最多能存放 24 位，小数后边最多放 8 位；`DOUBLE` 的 M 最大是 53，一共是 53 位，小数后边最多 30 位。

举个例子，声明一个身高：

```sql
height FLOAT(4, 1) UNSIGNED COMMENT '身高，保留小数点一位，多位四舍五入'
```

`FLOAT(4, 1)` 里边的 4 代表着我身高一共要写四位，其中一位是小数位，单位是厘米，这样是不是就够装了。`UNSIGNED` 代表我无负号，不能填负值。注释就写清楚：它会保留小数点一位，如果多位会四舍五入。

这是个什么效果呢？假如我的身高是 `180.565`，存进这一列里，**它不会报错**，因为没有超出范围；它会把最后多出来的那一位四舍五入向前进一位，最终存到数据库里的值是 `180.6`——5 进 1 变成 6，就是这个意思。

#### 浮点上的 UNSIGNED：砍掉负值，但不迁移

还有一点要注意：他们俩也支持加 `UNSIGNED`，也有负值和正值。

但**它跟整数类型不同**。举个例子：假设它原来的范围是负一到正一，如果你加了一个无符号（不要负值），那**整数**会从负一到正一变成 0 到 2；而**它不会变**，还是 0 到 1。

也就是说，**浮点类型不会做负值向正值的迁移**。

> **结论**：所以说加不加 `UNSIGNED`，在浮点类型里边是没什么意义的。它也不会节约空间，它只是把负值那一部分给砍掉了而已。

#### 为什么不推荐 float 和 double

其实从 MySQL 8.0.17 版本开始，就**已经不推荐大家使用 `FLOAT` 和 `DOUBLE`** 了。

为什么呢？因为我们知道在 Java 中其实就面临这个问题：`double` 和 `float` 采用的是二进制存储表示法，它在底层是用二进制存储，最终你要转成十进制的时候，**可能出现精度失准的问题**——你除一个数，它莫名其妙地多了好几轮小数点，这就是因为它内部要做二进制和十进制的转换。

所以：**如果精度要求不高**，比如你存个身高，那肯定是没问题的；但**如果你存的是现金、货币、价格，用它就太不合理了**。

那有人就问了：你不推荐它，你讲它干啥呀？当然，如果精度要求不高，它是可以用的。精度要求高不推荐用，那到底推荐用什么？没关系，我们接着走——**定点数**。

#### DECIMAL：绝对精度的十进制类型

定点数类型是一个精度更高的数据类型，它是**绝对精度的十进制数据类型**。它底层采用的就是十进制进行存储和转换，所以**不会损失精度**。如果你想标注货币和商品价格，用它就可以了。

它的用法跟 `FLOAT` 和 `DOUBLE` 是一样的，叫 `DECIMAL`，写作 `DECIMAL(M, D)`。

它的存储空间是**动态计算**的——根据你传入的数据值来计算存储字节数。**大概了解一下就可以了**，不给你讲具体的公式，因为不同的 MySQL 版本，计算公式和方式是有区别的。

它的 M 最大是 65 位，D 最大是 30 位。反正纯数字，肯定够用了。

举个例子，假如我想存薪水：

```sql
emp_salary DECIMAL(8, 1)  -- 小数点后边保留一位，前面是七位
```

`(8, 1)` 里 8 代表小数点后边保留一位、前面是七位，那么最大就是 999 万，我觉得已经够了。如果不够，你可以在前面加数字，比如 `DECIMAL(11, 1)`。

而且它后边如果多出一位、有两位，也会进行**四舍五入向前进位**。

另外还有一个点：你在写的过程中，**可以把 D 写成 0**。D 写成 0 就代表没有小数位，全是整数位。

> **结论**：怎么选就一句话。**精度要求不高**——身高、体重这种，差个零点几厘米那玩意儿不算事儿——用 `FLOAT` 和 `DOUBLE`，根据你的范围去选；**精度要求特别高**——差一分钱都不行，说白了就是跟钱有关的东西，工资、商品价格——建议用 `DECIMAL`。它精度更高，占有空间当然也可能大一些。

### 短字符类型：CHAR 与 VARCHAR

接下来是数据库中**最重要的数据类型：字符串**。

在数据库中，我们可以用 `CHAR` 和 `VARCHAR` 两个类型来表达一个短字符类型。它们俩有什么区别？我简单给大家介绍一下。

#### CHAR 固定长度

`CHAR` 在声明的时候，**可以加一个最大长度限制 M**，它会限制这一列输入的最大字符串长度，超过了会报错。

而 `CHAR` 的特点是**它是固定长度**的：一旦你声明一个 `CHAR` 并约定最大长度，哪怕你实际插入的数据小于这个长度，**它也会占有最大长度的空间，剩下的用空格去补充**。

举个例子。假如我声明一个 `name`，用的是 `CHAR`，写的 M 是 5，代表着我这个 name 是一个字符串类型，而且最大长度不能超过 5。那在插入数据的时候，假如我插入一个名字，就叫一个 `A`，存储的时候是怎么处理的？

因为 `CHAR` 是固定长度，最终在存储的时候，它会这么做：把 `A` 写上，然后在**右侧补四个空格**来占满五个空间。

```text
声明：name CHAR(5)
插入：A

最终存储：[A][ ][ ][ ][ ]      ← 右侧补空格，永远占满 5 个字符
```

所以它的固定长度一定等于你声明的最大限制长度。而且这个 M 最多是 255，**一列最多只能存放 255 个字符**。

那它占有的空间多大呢？这就**跟我们的编码格式有关系了**。举个例子，我们的编码格式是 `utf8mb4`，指一个字符占 4 个字节，那最终你写了 255，那就是 $255 \times 4$；如果你声明的是 5，那就是 $5 \times 4$。

**什么时候用它？**你去琢磨琢磨这个空间就好了。比如想存一个性别，男和女，它只有男和女，没有人妖八，长度固定，那就写成 `CHAR(1)`；再比如手机号，大家都是 11 位，那你肯定 `CHAR(11)`。

> **结论**：固定长度、且 M 小于等于 255 的，可以用 `CHAR` 来存。它的性能相对于 `VARCHAR` 来说会好一些，因为它不需要伸缩。

#### VARCHAR 可变长度

`VARCHAR` 在声明的时候，**是必须要指定一个最大长度限制 M 的**，不指定会直接报错。

它是一个**可变的、可伸缩的字符串**。我还是举个例子：假如我也有个 `name`，这回写的类型是 `VARCHAR(5)`，指的是最大只能存 5 个字符串，不能超过，超过会报错。那这时我也插入了一个字符，它能存吗？最终在内存里会怎么存？

**它会自动伸缩，最终只存这一个字符。**所以它是一个可变长度的、会根据你内容伸缩最终存储空间的类型。

那 `VARCHAR` 的 M 最大限制是多少？**理论上说没有最大限制**，你可以随便写多大都行。但是因为 MySQL 有一条规定和限制——**一行数据最多不能超过 65535 个字节**。

也就是说，就算一个表里边只有一个 `VARCHAR` 列，你这一列存放的数据也不能超过 65535 个字节。还是拿 `utf8mb4` 举例，一个字符 4 个字节，那这个 M 值就不能超过 $65535 \div 4$ 向下取整的数，不是整除的结果。你超过了以后，最终会超过整行的数据限制。当然你写的时候可以写得比较大，但真实存的时候不能超过这个字符长度就可以了。

那它的空间怎么算呢？还是 `utf8mb4`，**它也要乘以 4**。比如我写了一个字符，就等于 $1 \times 4$。

**为什么还要加一个 1 呢？**

因为 `VARCHAR` 类型它**可能为空**。而 `CHAR` 类型永远不会为空，因为它会自己自动补全；而 `VARCHAR` 类型如果你真的不传值，它真的可能为空。所以这额外的 1 个字节，是用来记录这一列**是否为空**的。

> **结论**：`CHAR` 的空间 = M × 字节比；`VARCHAR` 的空间 = 实际长度 × 字节比 **+ 1**。

一个可以总结成这么一句话：**一个是固定长度，一个是可变长度**。上边类似数组，下边类似我们的 Java 集合，是这种感觉。

#### 同一份数据，两种占法

有个地方特别容易被忽略，就是**补空格这件事只发生在存储的时候，检索的时候还有另一套规则**：

- `CHAR`：存的时候补齐尾部空格，**查的时候会自动去掉尾部空格**，把原始数据还给你。所以你不用担心插 `AAA` 读出来变成 `AAA␣␣`；
- `VARCHAR`：它不会对你数据做任何填充和压缩，**你存啥就是啥，你取啥就是啥**。比如你自己存的时候加了两个空格，那读的时候你也会拿到带这两个空格的值。

再来一个版本上的区别，大家了解就行。我们现在讲的 MySQL 是 8 版本。如果你用的是 4 以下版本，之前声明 `VARCHAR(20)`，这个 20 **不是 20 个字符的大小限制，而是 20 个字节**。比如你用 `utf8mb4`（4.x 版本里指的是一个字符占 3 个字节），那这个列就只能放 6 个字符，因为 6 × 3 = 18，放 7 个就是 7 × 3 = 21，超了放不下。

而 **5.0 以后做了改版**，把 `VARCHAR` 的 M 变成了**字符限制**：这里边写 20，指的就是 20 个字符。

下面这张存储对比图，我把同样的数据分别塞进 `CHAR(4)` 和 `VARCHAR(4)`，字符集用的是**单字节的字符集 `latin1`**（一个字符就是一个字节，只存得下英文 ABCD 那些东西，存不了中文）：

| 插入的数据 | `CHAR(4)` 实际存储 | 占用字节 | `VARCHAR(4)` 实际存储 | 占用字节 |
| :--- | :--- | :--- | :--- | :--- |
| 空字符串 | 补 4 个空格 | 4 | 空 | $0 \times 1 + 1 = 1$ |
| `AB` | `AB` + 2 个空格 | 4 | `AB` | $2 \times 1 + 1 = 3$ |
| `ABCD` | `ABCD`，不补 | 4 | `ABCD` | $4 \times 1 + 1 = 5$ |

先看 `VARCHAR(4)` 这一列：插空字符串的时候，`M` 相当于等于 0，它不乘 1，所以内容部分一个字节都不占，但**所有的 `VARCHAR` 字段都需要有一个字节来记录你是否为空**，所以最终还是占 1 个字节；放 `AB` 就是 2 个字节再加 1，等于 3；放 `ABCD` 就是 $4 + 1 = 5$。

再换到 `CHAR(4)`：不管你插的是空、是 `AB` 还是 `ABCD`，**它始终都是 4 个字节**——因为你在 latin1 下边一个字符占一个字节，补的空格也是占位的。

看出这俩的区别了吗？那如果换成 `utf8mb4`，这几个值分别是多少？下面就当一道题交给大家。

### 本讲提到的题目

#### 练习：创建在线图书管理系统

**题干**：创建一个库，选择对应的字符集和排序方式；然后在库中创建 `books` 表，表中手动设置字符集并加注释，表中包含指定的三个列——列的类型已经给定，注释自己补。

**答案**：

```sql
CREATE DATABASE IF NOT EXISTS books_labs
DEFAULT CHARACTER SET utf8mb4
COLLATE utf8mb4_general_ci;

USE books_labs;

CREATE TABLE IF NOT EXISTS books
(
    book_name   VARCHAR(20)  COMMENT '图书名',
    book_price  DOUBLE(4, 1) COMMENT '图书价格',
    book_number INT          COMMENT '图书数量'
) DEFAULT CHARSET = utf8mb4 COMMENT = '图书表';
```

**解析**：三个易错点都在建表语法那节——字符集要显式写、注释内容用单引号、**最后一列 `book_number` 后面绝对不能加逗号**。建完切到库里，用 `SHOW TABLES FROM books_labs;` 验证。`VARCHAR(20)` 的 20 是 20 个**字符**（5.0 之后），`DOUBLE(4, 1)` 是总共 4 位、其中 1 位小数。

#### 练习：给年龄和学号选类型

**题干**：库里创建一张 `t1` 表，包含年龄和学号两个列。年龄你能活成负数吗？学号的范围不确定，请分别选类型。

**答案**：

```sql
CREATE TABLE t1
(
    age  TINYINT UNSIGNED  COMMENT '年龄',
    sno  BIGINT  UNSIGNED  COMMENT '学号'
);
```

**解析**：年龄选 `TINYINT`——人活不到 255 岁，范围够用且空间最小；不可能有负值，所以加 `UNSIGNED`，范围变成 $0 \sim 255$。学号**范围不确定，这时候建议尽量选大的**，宁可多占点空间也不能报错，所以选 `BIGINT`，同样没有负号加 `UNSIGNED`。选型就两条逻辑：**第一范围要覆盖住数据，否则报错；第二范围够的前提下，选占有空间最小的**。

#### 思考题：换成 utf8mb4 会怎样

**题干**：上面那张对比图用的字符集是单字节的 `latin1`。假如编码换成 `utf8mb4`（一个字符占 4 个字节），同样声明 `CHAR(4)` 和 `VARCHAR(4)`，插入空字符串、`AB`、`ABCD`，它们分别占多少字节？

**答案**：

| 插入的数据 | `CHAR(4)` | `VARCHAR(4)` |
| :--- | :--- | :--- |
| 空字符串 | 16 字节 | $0 \times 4 + 1 = 1$ 字节 |
| `AB` | 16 字节 | $2 \times 4 + 1 = 9$ 字节 |
| `ABCD` | 16 字节 | $4 \times 4 + 1 = 17$ 字节 |

**解析**：直接套前面那两条公式就行——`CHAR` 固定长度，空间 = M × 字节比，$4 \times 4 = 16$，**不管你插多短，它都是 16 字节**；`VARCHAR` 可变长度，空间 = 实际长度 × 字节比 **+ 1**（那个 1 用来记录是否为空），所以插空串是 1、插 `AB` 是 9、插 `ABCD` 是 17。同一份数据，`CHAR` 稳如泰山，`VARCHAR` 跟着内容伸缩，这就是它们最本质的差别。

> 对应块：BLK05 | 覆盖分集：P25-P29 | 块标题（分集名）：《25-数据定义篇-字符类型深思和总结》

### 字符串类型：CHAR、VARCHAR 与 TEXT

字符串类型是所有类型里最"复杂"的，也最值得停下来想一想。咱们先把它总结一遍，这一节要解决两件事：`VARCHAR` 的 `M` 到底最大能写多少，以及一旦写不进去该怎么办。

#### 先给两种字符串贴个标签

我们常用的字符串类型就两个：`CHAR` 和 `VARCHAR`。

`CHAR` 是**固定长度类型**。一旦声明，就固定占有对应的空间。你存的时候就算少于这个长度限制，它也会去填充满。而且各位，`CHAR` 的 `M` 最大为 255。

`VARCHAR` 是**可变长度类型**。一旦声明，可以插入小于它的长度，而且它会自动伸缩。

> **注意**：`VARCHAR` 的 `M` 其实没有"类型自带"的最大限制，但 `M` 所占的空间不能超过一行的最大限制——65535 字节。这笔账我们待会儿亲手算一遍。

那最终用谁？还得给它们打个标签：

> **结论**：`CHAR` 性能较好，因为它不需要做运算，所以性能会好一些；`VARCHAR` 性能一般，因为它内部需要做这种伸缩运算。

#### `CHAR` 的两个细节

第一，`CHAR` 在声明的时候**可以不写 `M`**。写一个 `CHAR` 类型，它就等于 `CHAR(1)`，也就是 $M=1$。

第二，如果声明了最大长度限制，而输入的文本小于长度限制，它会在**右侧补空格**。比如 `CHAR(5)` 里插入 `abc`，最终存进数据库的是 `abc` 后面带两个空格，占满 5 个字符空间，所以它每次都是固定的。

```text
插入：  'abc'    →  实际入库  'abc  '   (右侧补空格，占满 5 个)
读取：  'abc  '  →  程序拿到  'abc'     (右侧空格被自动去掉)
```

补进去的时候补了空格，读出来的时候 MySQL 又会自动把右侧空格去掉——因为它知道这些空格是自己补的，给到你也没意义。

> **提示**：`VARCHAR` 恰好相反，它是**识别空格**的，你插入空格，读出来也是有空格的。

#### `VARCHAR` 的两个细节，以及一段历史

第一，`VARCHAR` 在声明的时候是**必须写 `M` 限制**的，不写直接报错。

第二，这段历史值得回看一眼。在 MySQL 4.0 以下版本，你写 `VARCHAR(20)`，这个 20 是什么呢？是 **20 个字节**限制。也就是说我只是约定这个字符串空间不能超过 20 个字节，但具体能存几个字符，还得根据你的编码格式进行运算：假如我们用的是 `utf8mb3`，那最多你只能存 6 个字符，因为你不能存 7 个，7 乘 3 就等于 21 了。这个长度不但不是固定的，还跟你的编码格式绑在一起，它不太好用。

MySQL 5.0 以后做了改版，这回改成 20 代表**20 个字符**限制。这回就更清晰了：不管你是什么编码格式，我都占 20 个字符，最终占几个字节空间，由你的编码格式自己运算。

#### `M` 能写多大：把 65535 这笔账算清楚

`CHAR` 的 `M` 封顶 255，我们来演示 `VARCHAR` 的上限。咱们建一张表：

```sql
CREATE TABLE t1 (
    name1 VARCHAR(16384)
);
```

表名就起个 `t1`。为了大家清晰点，我把字符集显式设置成 `utf8mb4`。大家记住，如果不写就走数据库的默认值，它也是这个字符集。用之前那个库 `ddl_d1`，没有的话随便创建个库就可以了。

先看这笔账。第一个前提大家要知道：MySQL 中一行数据最大的占有空间是 65535 字节。现在这一行里只有一个 `name1` 列，证明 `name1` 能占的最大空间就是 65535，不能比它大，声明的时候也就不能比它大。

第二个前提：`VARCHAR` 类型默认会用一个字节的数据去表示是否为空，这个字节也算在里面。所以真正能给内容用的字节是多少呢？$65535 - 1 = 65534$。

最后，我们用的字符集 `utf8mb4` 代表一个字符占 4 个字节：

$$\frac{65534}{4} = 16383.5$$

算出来是个带小数点的数，这就说明 16384 肯定装不下。所以它最大的限制应该是 **16383**，这个 `M` 值最大就是 16383。

```text
一行的空间上限：65535 字节
──────────────────────────────────────────
  行总预算                          65535 字节
  - VARCHAR 长度标识（是否为 NULL）      1 字节
  ------------------------------------------
  真正能给内容用的                  65534 字节

  utf8mb4：1 个字符 = 4 字节
  65534 / 4 = 16383.5     ← 带小数，说明 16384 装不下
  向下取整  →  M 最大 = 16383
```

我们照着算的写一下：先写个 16384，卡一下这个点。执行一下——果然不能这么创建，它说超过了这个值，最大只能是 16383，跟我们理解和运算的完全一样。

再换个写法试试：给两个列，一列 16000，一列 384。大家思考个问题，这么一执行能不能创建成功？可以在公屏上互动一下。答案很显然，也是不行的。因为我们强调的是**一行**数据不能超过，现在一行有两个列，两个合起来也不能超过 65535 字节。执行一下，它直接说 `Too large`，太大了。

#### 预算超了怎么办：两个不合理的办法，和一个正解

先说两个"看起来能行、其实不合理"的办法。

**方案一：把 `M` 值调小。** 确实能解决，但不合理。因为我们设置的 `M` 值不是玩、不是闹，是根据我们的需求去设置的。既然业务上需要这么大，那我只能这么设置；你让我调小，数据就设置不去了，那我还是报错吧——那数据库不是废了吗。

**方案二：把字符集换掉。** `mb4` 占 4 个字节，你可以写 `mb3`，或者写 `latin`，它是不是就占一个字节？一个字符占的字节小了，保留的字符数自然就多了。但这答案一样不合理：你为什么选这个字符集？就是因为它满足我们程序显示字符的效果，它不会出现乱码。如果换了字符集乱码了，那不是得不偿失吗。

那到底怎么解决？这里我要说一句：MySQL 这个东西非常智能，它给我们报错的同时，一般都会在错误后边给我们提供解决方案。我们把错误再好好去读读——前面说我们太大了、限制是 65535，这些我们都能理解；**最后一句话**才是重点：

```text
You have to change some columns to TEXT or BLOBs.
```

它的建议就是：你可以把某些列改成 `TEXT` 或者是 `BLOB` 就可以了。

为什么要这么做？因为上面有一句话我们之前没有给它说完：**MySQL 中一行数据最大的占有空间限制是 65535，但 `TEXT` 和 `BLOB` 这两个类型的列不占用这个 65535 限制**，它属于法外狂徒。所以你把其中一列改成对应类型，相当于它不占这个限制，数据就过了。

这两个类型一个是文本，一个是二进制。二进制我们课程不讲，所以主要先说文本类型：把字符串列改成 `TEXT` 就行，改成 `TEXT` 之后不占用一行的限制，最终解除 65535 的危机就可以了。随便改哪一列都行。改完我们再执行一下，创建成功了。

#### `TEXT` 家族与最终选型

既然话已经说到这儿了，都已经提到 `TEXT` 了，那不介绍是不合理啊。真正的字符串其实是三种：`CHAR`、`VARCHAR`，还有一个就是 `TEXT`——大文本类型。它在声明的时候不需要指定长度，它是有固定的大小限制的：`TEXT` 类型最大的单列只能放 65535。

> **易错点**：这个 65535 指的是**这个类型单列它自己的类型限制**，跟你当前行是没关系的。而且它最大的特点，是**不占用一行的最大限制空间**。

`TEXT` 还有几个兄弟，我们统一去说一下：它包括 4 个类型——`TINYTEXT`、`TEXT`、`MEDIUMTEXT`、`LONGTEXT`。这 4 个类型注意，它们都是可伸缩可变的，其实跟 `VARCHAR` 是一样的。你放一小段，我就自己伸缩，只占一个文本对应的字节，但我最大是 65535 字节。

这 4 个里面能盛放文本最多的就是 `LONGTEXT`。它的限制转成可读性是 4GB，4 个 G 的文本。你想想，4 个 G 的文本，这一列能存多少数据了？把整个国家博物馆的书转成文本存好几个，是不是都能存得下？所以我们这个是绝对够存文本的。它们在用的时候只需要写一个列名，之后加上属性类型就可以了。大家记住它们各自的大小限制就可以了。

大文本我们一笔带过。最终总结一下，有这三个文本（或者说字符串），到底怎么用呢？

> **结论**：
> - 短文本且**固定长度**，用 `CHAR` 就行，性能最好，比如性别和手机号；
> - 短文本但**长度不确定**，用 `VARCHAR`。比如名字，有人叫赵四，有人的名字有 6 个字叫尼古拉斯·赵四，长度不确定，那你就写 `VARCHAR`，写最大值，写 10、20 都行，它会自动伸缩。还有存地址、个人签名、一些描述信息等等，都可以用 `VARCHAR` 去存；
> - 真碰见更大的文本、超越了 65535，其实我们**不推荐使用 `TEXT`**。

为什么不推荐 `TEXT`？因为 `TEXT` 这个东西性能不太好，而且如果你直接往数据库里面存大文本，每次从数据库里读和写都是比较消耗性能的。那我们推荐怎么办？如果有太大的文本，你可以把大文本存到一个文本文件中，最后把文本文件放到磁盘的某一个位置。放到磁盘以后，你是不是有一个文本文件地址？接下来在数据库里面用 `CHAR` 和 `VARCHAR` 去记录文本文件的地址就可以了。记录完地址以后，下次你在程序中根据数据库读到了文本文件地址，再用 IO 流就可以去读取这个文本文件，一般都是这么操作，避免直接在数据库里面存较大的数据，让我们的性能变得更差一些。

好，到这儿为止我们就把所有文本类型都介绍好了。大家要记住，文本类型有三种：`CHAR`、`VARCHAR` 以及 `TEXT`，它们的特点需要简单思考一下。

### 时间类型：五种格式，其实就是特殊字符串

介绍完数据库的字符串类型，接下来介绍数据库的时间类型。时间类型在数据库存储过程中也是经常会需要的。举个例子，假设我们有个用户表，用户的生日那就应该是时间类型；还有这条数据的插入时间，或者来记录一下这条数据的更改时间等等，它们都是时间类型。

在标准的 SQL 语句中，它给我们提供了 5 种常用的时间类型，一会我们细化。这 5 种类型的区别就是**格式不同、所占的存储空间不同、值范围不同**，仅此而已。

> **结论**：当我们设置好时间类型的字段以后，插数据的时候，你就**按照字符串插入**就可以了，加单引号，只是按照它内部的时间格式插入即可。或者换个理解——**你可以把时间理解成一个特殊格式的字符串**，就 OK 了。

#### 五种类型：格式、字节与取值

| 类型 | 字节 | 格式 | 备注 |
| --- | --- | --- | --- |
| `YEAR` | 1 | 4 位的年或 2 位的年 | 两位年的换算见下文 |
| `TIME` | 3 | `时分秒`，冒号分隔 | 顾名思义就是时间 |
| `DATE` | 3 | `年-月-日`，中划线分隔 | 所谓日期 |
| `DATETIME` | 8 | `年-月-日 时:分:秒` | `DATE` 加 `TIME` 的整合，值范围更大 |
| `TIMESTAMP` | 4 | 同 `DATETIME` | 值范围 1970 ~ 2038 |

`TIME` 顾名思义就是一个时间，它占 3 个字节，格式用冒号去隔开，是时分秒这种格式。

`DATE` 所谓的日期，它有年月日，中间用一个中划线分隔，它也占 3 个字节。

`DATETIME` 顾名思义，它是 `DATE` 加 `TIME` 的一个整合，占 8 个字节，它内部是由日期加空格加对应的时分秒组成的。

除此之外还有一个 `TIMESTAMP`。大家发现一个问题：`TIMESTAMP` 也是来表达日期加时间的，但跟 `DATETIME` 不同。第一，它占有的空间字节会更小一些；第二，它的时间格式跟之前是一样的；但还有第三点——**它们的值范围是不同的**。`TIMESTAMP` 就是我们常说的格林威治时间那一套，它的时间范围是 1970 年到 2038 年；而 `DATETIME` 存储空间大，它的时间范围也会更大一些。这里可以根据我们的程序需求进行选择，一般来说在有效时间范围内想去表示它，选 `TIMESTAMP` 更合适，因为它占有的空间更小。

#### `YEAR` 的两位年：`00-69` 与 `70-99`

`YEAR` 它可以允许用两位表达，就是 00 到 99 来表达年限。但是它的对应关系有点反直觉：

| 写成的两位值 | 实际代表的年份 |
| --- | --- |
| `00` ~ `69` | 2000 年 ~ 2069 年 |
| `70` ~ `99` | 1970 年 ~ 1999 年 |

说到这儿大家应该就明白了：记这个两位年份，你发现如果用两位，你还要自己在脑子里做一次时间格式的转换，对不对？所以我们在真正的开发中**不推荐用两位的格式**，还是推荐写成四位的时间格式，这样它的值范围会更广一些，表达也更清晰。

> **提示**：`YEAR` 有点特殊，年份在插入的时候既可以用字符串 ` '09' `，也可以直接写数值 `09`，这么写也行的，因为两位年中间没有特殊的格式。而其他时间类型就只能放字符串了：想写 `10:10:10` 就按 `TIME` 的格式写，生日是 2000 年 10 月 10 号就按 `DATE` 的格式写，都得加引号。

#### 让时间自己动：两个时间戳约束

如果说我们有这样两个需求：假设我插一条数据，就想去读取我当前的时间自动给我插入，我不想维护；或者我想更新一条数据，想它自动去变成更新的时间——那这时候需要我们做一些额外的设置。

`DATETIME` 和 `TIMESTAMP` 后面加这两段东西就行了，相当于是一个约束和限制：

- `DEFAULT CURRENT_TIMESTAMP`：代表是一个默认的，默认什么呢？默认 `CURRENT_TIMESTAMP`。插入的时候，就给它赋予默认时间。
- `ON UPDATE CURRENT_TIMESTAMP`：就是说当更新的时候，也给它设置为更新的那个节点的时间。

只要写好这两个约束，大家在插入数据和更新数据的时候就不用去维护这个时间字段，它会自动插入时间。当然，你如果要主动地插入时间了，那还是以你主动插入的时间为主。

第二种情况，假如说我只想在插入的时候去维护一个时间。举个例子，假如说有一个用户信息数据，里面有字段来记录这条数据的创建时间，插入的时候记录一下就可以了，后续更改这个字段是不需要更改的——那大家只需要加一个 `DEFAULT CURRENT_TIMESTAMP` 就可以了。

#### 亲手建一张带自动时间的表

光说不练不行，我们来建一张 `t2` 表。还是一样先选中 `ddl_db` 库，然后：

```sql
CREATE TABLE t2 (
    name VARCHAR(20),
    regist_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '插入会自动维护时间',
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '插入维护时间，且修改数据也自动更新时间'
);
```

逐列拆开看：

- `name VARCHAR(20)`，随便一个字符串字段。
- `regist_time`：注册时间要的是年月日时分秒，那你就写个 `DATETIME`；如果想要一个插入默认时间，就写 `DEFAULT CURRENT_TIMESTAMP`。
- `update_time`：这里我们依然可以用 `TIMESTAMP`，它也支持这套语法。如果它想插入有时间且更新有时间，你就把上面那句话先加进来，加完以后在下方再加一个 `ON UPDATE CURRENT_TIMESTAMP`就可以了。

到这里这个表就创建好了。在这儿给大家留一个小疑问：**假如说有没有一种可能，我们有某一个字段，在插入的时候不需要它帮我们维护时间，但是后期更新的时候需要它自动帮我们维护时间呢？** 大家思考一下，如果有这种场景，这个语法应该怎么写呢？可以把它敲在公屏上。

### 数据类型总账与选型原则

类型介绍得有点多了，我们来做一个总结。

#### 四个方向，一张总账

我们大概介绍了一共是四个方向，第一个方向是整型，第二个是浮点型，第三是字符串，第四是日期类型。这四个大类型基本就涵盖了我们平时在创建表的时候需要的这些列字段类型。当然我们介绍的并不是全部，如果大家有什么其他的特殊类型，也可以建议去官网查一下全部类型。

| 方向 | 具体类型 |
| --- | --- |
| 整型 | `TINYINT`、`SMALLINT`、`INT`、`BIGINT` |
| 浮点型 | `FLOAT`（单精度）、`DOUBLE`（双精度）、`DECIMAL`（精度更高） |
| 字符串 | `VARCHAR`、`CHAR`、`TEXT` |
| 日期时间 | `YEAR`、`TIME`、`DATE`、`DATETIME`、`TIMESTAMP` |

整型我们介绍了四种，它们占有的空间不同，值范围不同，这是它们的特点。浮点型除了 `FLOAT`、`DOUBLE` 之外，还有一个精度更高的叫 `DECIMAL`，这个同样根据需求进行对应选择——假如说你设计的是金钱、更精细的数据，用 `DECIMAL`；假如说设计的是身高，用 `FLOAT`、`DOUBLE` 其实都是可以的。

字符串这块的细节上一节已经讲透了：`VARCHAR` 和 `CHAR` 它俩一个可变长度、一个固定长度，但这两个都有一个长度限制，碍于我们一行数据的最大长度限制是 65535 字节，它是有限制的。那如果你想要更大的字符，怎么办？你可以用 `TEXT`——它相当于不会算为一行内的一个最大值限制，所以理论上它可以超越 65535 字节，最大的可以设置到 4GB。大家想个问题，银行某一个数据库中某个字段存了一个 4GB 的字符，你得存多大一个字符？其实理论上说都已经绝对够用了。

> **易错点**：这里有一个必须强调的点。在**一些低版本的 MySQL** 中，`TIMESTAMP` 这个类型它会自动去维护时间，包括自动插入或者自动更新维护时间。但这个自动更新时间的功能其实并不稳，在**一些新版本的 MySQL** 中，它是没有自动维护功能的。所以这不是一个特定的行为——有的版本有，有的版本没有。大家如果在用 `TIMESTAMP` 或者 `DATETIME` 的时候想自动维护时间，还是按照我们说过的语法，自己在后边加相关的约束去实现，这样会更加稳妥一些。

#### 范围确定时：选最省空间的那个

第一条选型原则：如果大家在确定值类型和值范围的时候，就选**符合这个范围且占有空间最小**的类型，来节约我们数据库占有的整体空间大小。

举个例子，假如我想存一个年龄，那大家就要思考用什么类型了。一定是整数，对吧，它是个整数，你不能用浮点。第二，年龄的值范围大家想想——每个人也就活那么一两百岁，最多活三五百岁，是不是都够了，也活不到那么大是吧？其实用 `TINYINT` 就够了，`TINYINT` 它的值是 -128 到 127，应该是够用是吧。如果大家觉得可能不够用，可以加一个叫**无符号**，把负值部分转移到正数部分，也就是 0 到 255，是不是也是可以搞定这个事的。

#### 范围不确定时：直接上最大的

第二条选型原则：如果大家发现**不确定值范围**的时候，怎么办？假如说我有一个字段叫编号，这个编号到底能大到什么程度我不确定，但我知道它是个整数。那这个时候你会选哪种呢？大家可以在公屏上打出你认为编号应该选哪种整型类型会更合适一些。

答案是 `BIGINT`。为什么？

> **结论**：我们数据库的**第一原则是保证数据不要超越值范围，先不要报错；第二原则才是去节约我们的存储空间**。编号是无限自增长的，长长长，长到多大我也不确定，那你就用最大的整型类型去存储它。就算超越了最大的整型类型，那我们也无能为力了；但在它这种场景下，我们能确保它不会出现过大地超出值范围这个问题。如果你用 `TINYINT`，那就太容易发生了。

#### 动手：为学生表的每个字段挑类型

我们来做个小练习。场景是：创建一个图书库，图书库叫 `book_libs`，字符集是 `utf8mb4`，排序方式是一个忽略大小写敏感的 `COLLATE`。然后在这个库里创建一个学生表，存储借书的学生信息，包含学生的姓名、年龄、身高、生日以及注册时间和更新时间等等这些属性。我们一起来分析分析，这些属性应该用什么样的数据类型会更加方便一些。

先建库，再切进去：

```sql
CREATE DATABASE book_libs CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE book_libs;
```

注意这两个关键字：`CHARACTER SET` 声明字符集，后面紧跟的 `COLLATE utf8mb4_0900_ai_ci` 是它的比较规则（忽略大小写敏感），我们之前已经写过多遍了。执行完刷新一下，库就创建好了。

然后我们逐个字段分析该怎么选：

| 字段 | 选型 | 为什么 |
| --- | --- | --- |
| 学生姓名 | `VARCHAR(10)` | 咱有俩字的、有仨字的、有四个字的，长度不确定，所以是可变字符串。中国人的字符我见过姓名最多的就是尼古拉斯·赵四，就七个字，给 10 个我觉得就够用了 |
| 性别 | `CHAR` | 中国就两种，男和女，一个字符就够用了；`CHAR` 不指定长度默认就是一个字符 |
| 年龄 | `TINYINT UNSIGNED` | 是整数，且年龄没有负值；加无符号就把 -128 转到正值方向，变成 0 到 255 |
| 身高 | `DOUBLE(4,1)` | 大家都是两米左右，一般记录到小数点后一位；`4,1` 表示一共四位、其中一位是小数，也就是整数位是三位的厘米数 |
| 生日 | `DATE` | 一般记的就是哪年哪月哪日，不记时分秒 |
| 注册日期 | `TIMESTAMP` + `DEFAULT CURRENT_TIMESTAMP` | 第一次往数据库里插入数据的那一刻就是注册日期，要自动维护 |
| 更新日期 | `TIMESTAMP` + `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | 第一次插入算第一次更新，以后每次更新都要跟着改 |

对应的建表语句：

```sql
CREATE TABLE student (
    stu_name     VARCHAR(10) COMMENT '学生的姓名',
    stu_sex      CHAR        COMMENT '学生的性别，男和女',
    stu_age      TINYINT UNSIGNED COMMENT '年龄，0 到 255',
    stu_height   DOUBLE(4,1) COMMENT '身高',
    stu_birthday DATE        COMMENT '生日',
    stu_regist   TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '注册日期，插入的时候自动维护',
    stu_update   TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新日期，插入和更新自动维护时间'
);
```

注册日期和更新日期这两个字段要注意：它们都是一个详细的时间，要年月日时分秒；而且注册日期指的是你第一次往数据库里插入数据时的那一刻，更新日期是第一次插入算第一次更新、以后每次更新它要跟着去改。所以这两个都要"写日期类型 + 加相关约束"，类型我们都可以用 `TIMESTAMP`，没毛病。

这里也给大家一个建议：以后大家去创建表的时候，可以**先去分析一下对应的类型，有没有相关的约束、格式**等等，然后再落到语句上。写起来其实就是 `CREATE` 关键字、表就是 `TABLE`、表名 `student`、左括号放相关的列、右括号收工。

### 表的修改：一切从 ALTER TABLE 开始

创建表讲完，接下来介绍最后两个表操作：修改表和删除表。

修改表主要分为两个方向：第一个方向是修改表中的**字段，也就是列**，比如说修改表添加一列、删除一列，或者修改某一列的名字或者类型；第二个方向是修改**表的名称**。我们一个个来看。

> **提示**：修改表在 DDL 里面常用的关键字是 `ALTER`。下面所有语句的前置部分都是 `ALTER TABLE 表名`，真正区分动作的是后面那个动词。

#### 添加、删除与移动一列

**添加一列**：

```sql
ALTER TABLE 表名 ADD 列名 类型 [FIRST | AFTER 已有列名];
```

`ADD` 后面跟的就是列名和对应的类型。末尾还有两个可选关键字，第一个是 `FIRST`，第二个是 `AFTER`——它们指的是在指定一个列名，是在原有表中的某一列之前还是之后添加新的列。

**删除一列**：

```sql
ALTER TABLE 表名 DROP 列名;
```

用 `DROP`，后面直接写列名就可以了。这就是列的操作、列名的操作，大家记一下。

#### `CHANGE` 与 `MODIFY`：外在的改与内在的改

**改列名**用 `CHANGE`：

```sql
ALTER TABLE 表名 CHANGE 原列名 新列名 新类型 [FIRST | AFTER 已有列名];
```

这里要写原列名、要改变的新列名，接着还要写一个对应的类型。也就是说，**在修改列名的时候，其实也是可以修改类型的**；如果类型不变，就把原类型写上就可以了。后面同样可以加 `FIRST` 或者 `AFTER`，指定改到某一列的前面或后面。

**只改类型不改名字**用 `MODIFY`：

```sql
ALTER TABLE 表名 MODIFY 列名 新类型 [FIRST | AFTER 已有列名];
```

`MODIFY` 这个关键字大家注意。我来打个比方：`CHANGE` 这种修改，就像是你去理了一个新的发型，染成了红色，别人一看就能看得到，就是一种**外在修改**的感觉；而 `MODIFY` 这个词它指的是一种**内在修改**，你最近健身了，有八块腹肌，但大冬天的也不能露着腹肌，属于内在，但其实你也是有改变的。它后面写的是原列名、新的类型，同时也可以指定到某列的前后。

#### 改表名

这个就比较简单了：

```sql
ALTER TABLE 表名 RENAME TO 新表名;
```

中间有个关键字是 `TO`，其实 `TO` 是可以省略的，我们一般就写 `RENAME 新表名`，这样就可以了。

以上都是修改表的相关操作。大家也发现了，它们的**前置关键字全都是 `ALTER TABLE 表名`**。

### 表的删除与清空：两条都不能回滚

讲删除语法之前，先知道一件很重要的事：**删除表和清空表的操作都是无法回滚的**。也就是说一旦你把表真的清空了，那后期想拿到表中的数据你就拿不到了，或者表想找回你也找不到了，除非你的程序有对应的备份系统。所以大家一定要慎重、慎重。

#### `DROP TABLE`：把表连结构一起带走

```sql
DROP TABLE IF EXISTS 表名1, 表名2, 表名3;
```

中间可以加个 `IF EXISTS`——这个之前我们在创建库、判断库的时候也用过，就是在删除一个表的时候先判断它是否存在，当然这个也可以不加。最后再写表名，逗号隔开可以写多个表名，可以一下删除多个表。

#### `TRUNCATE TABLE`：只清数据，顺带清掉自增记录

```sql
TRUNCATE TABLE 表名;
```

这个指的是我想把表中的数据全部给清空，但是**表结构还保留**。对比一下：第一个 `DROP TABLE` 是把表和表结构全部给删掉；第二个是把表中的数据全部清空，和表相关联的数据我也给清空。

关联数据这块后边我们会讲。举个眼前的例子：假如我后期表中有主键，可以加一个相关的配置，让那个主键自增长，从 1、2、3、4、5、6、7、8 一直往后长。如果我要用 `TRUNCATE` 这种去删除的话，它也会把表中主键的最大值记录一起删掉。也就是说，它是清清白白地删除一个表中的所有数据和关联的数据。

所以这两个表的相关删除操作你记住：第一个是删除表结构，第二个是清空表数据，**它们都是无法回滚的**。

### 员工表实战：从建表到改到位

到这为止，所有表的创建、修改和删除操作我们都已经讲完了。数据定义篇的难点大家注意，其实就是**数据类型那一块偏多**。接下来我们对讲过的表操作做一个综合的练习。

案例要求分两步：第一步创建一个员工表，表中有指定的这些字段；第二步按要求去修改表。完整的建表语句和六条修改语句，咱们一个一个走过。

先建表，语法我们已经很熟了：

```sql
CREATE TABLE emp (
    emp_id INT,
    last_name  VARCHAR(50),
    first_name VARCHAR(50),
    mobile     VARCHAR(25),
    `code`     INT,
    job_title  VARCHAR(50),
    birth_date DATE,
    note       VARCHAR(255),
    sex        CHAR(5)
);
```

几个细节顺带说一下。`mobile` 是手机号，要求给的是 `VARCHAR(25)`，其实在国内 11 位手机号是不是就够了。`code` 这个列名，Navicat 里会被误识别成关键字，但它其实是一个保留关键字、是可以使用的；如果大家觉得这么显示不好看，可以加一对飘号（反引号），它也是 `code` 的意思。最后那个 `sex` 要求给的是 `CHAR(5)`，其实我们知道性别写的时候 `CHAR(1)` 更合适，但咱们先按要求写成 `CHAR(5)`，待会儿再改。

在改之前，我再教大家一个命令：

```sql
DESC emp;
```

加上表名，我们能看见这个表中的字段展示。大家发现，这个字段展示的顺序，其实就是当初我们创建的时候它的顺序——第一个是员工编号等等。

现在按要求开始改。

**把 `mobile` 字段移到 `code` 字段之后。** 其他名字和类型都不改变。有人说我也没讲过专门挪列位置的命令是吧？但我们讲过修改表名、修改表的类型，对不对？那我们能不能利用修改类型来实现？只不过类型还是原类型，最后后边再加一个位置关键字 `AFTER`，挪到所谓的 `code` 后边，不就完了？

```sql
ALTER TABLE emp MODIFY mobile VARCHAR(25) AFTER `code`;
```

改成了什么类型？它的原类型还是 `VARCHAR(25)`，一点没变；这会儿我们想换的只是位置。位置的关键字写的是 `AFTER`——在谁之后？`code` 之后。这里飘号加不加都行，加了只是让显示效果变成小写，不加大写一样也能识别。执行完毕以后，我们再 `DESC` 一下，大家发现这个 `mobile` 是不是挪到它的后边了？

**把 `birth_date` 改成全写的 `birthday`。** 这不就是修改列名吗？外在的改变用 `CHANGE`，内在的改变才用 `MODIFY`：

```sql
ALTER TABLE emp CHANGE birth_date birthday DATE;
```

后面的类型没发生变化，那咱们就写原来的 `DATE` 类型。执行完以后，同样执行一下 `DESC`，看我们的表结构——生日是不是已经改完毕了？

**把 `sex` 改成 `CHAR(1)`。** 我们前期创建这个字段的时候就知道，在中国没有人妖，就是一个字符男女，那现在就可以改成 `CHAR(1)`；其实 `CHAR` 不写也默认是一个字符：

```sql
ALTER TABLE emp MODIFY sex CHAR;
```

执行完毕以后再 `DESC` 一下，看我们的这个 `sex` 是不是变成一个字符了？不写，默认就是一个字符。

**删除 `note` 这一列。** 前面还一样，只是关键字换成了 `DROP`：

```sql
ALTER TABLE emp DROP note;
```

别忘了写表名——哪个表，得写清楚。执行完再看一下，这个就搞定了。

**新增一列 `new_column VARCHAR(100)`。** 新增列没有指定在哪个位置，那就正常去新增：

```sql
ALTER TABLE emp ADD new_column VARCHAR(100);
```

执行完毕以后我们一样 `DESC` 一下，大家发现新增的列，它**自动加在了最后一个位置**。

**把表名改成 `emp_info`。** `TO` 可以省略：

```sql
ALTER TABLE emp RENAME emp_info;
```

改完以后我们看一看表名：

```sql
SHOW TABLES;
```

这是查看我们当前库中有哪些表——是不是改成对应的 `emp_info` 这个名字了？

到这为止，关于表和库的所有操作我们都已经讲完了。大家在这一章数据定义篇需要掌握的，我再给你捋一遍：第一是**库**的创建、库的修改、库的删除，以及库的切换和使用等等；第二是**表**的创建，创建的时候表的列的类型如何指定，以及修改表、删除表、清空表等等这些相关的操作。大家把这个练习练好了，后边我们还会继续强化练习。

### 本讲提到的题目

#### 只想在更新时自动维护时间，语法怎么写

**题干**：建 `t2` 表的时候留了个疑问——假如某一个字段，在插入的时候不需要它帮我们维护时间，但后期更新的时候需要它自动帮我们维护时间，这种场景应该怎么写？

**答案**：只写 `ON UPDATE CURRENT_TIMESTAMP`，不带 `DEFAULT CURRENT_TIMESTAMP`。

```sql
字段名 TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**解析**：`ON UPDATE CURRENT_TIMESTAMP` 是独立于默认值之外的约束，前面建 `update_time` 那一列时我们已经演示过它的作用——更新的时候自动把字段设成当前时间。`DEFAULT CURRENT_TIMESTAMP` 只负责插入时赋值，跟它是两回事；把插入这一环去掉、只留下 `ON UPDATE`，就正好满足"插入时不维护、更新时才维护"。

#### 员工表综合练习

**题干**：先创建一个员工表（字段与类型按上面那张表的要求），然后依次完成六个修改——把 `mobile` 移到 `code` 之后；把 `birth_date` 改名全写为 `birthday`；把 `sex` 改成 `CHAR(1)`；删除 `note` 列；新增 `new_column VARCHAR(100)`；把表名改为 `emp_info`。

**答案**：建表语句与六条 `ALTER` 语句见上文《员工表实战》一节；做完后用 `DESC emp;` 逐条自检列名、类型与顺序，最后用 `SHOW TABLES;` 确认改名结果。
