## 数据的规矩：默认值、检查、唯一与主键约束
> 对应块：BLK13 | 覆盖分集：P60-P64 | 块标题（分集名）：《60-数据库约束篇-默认值约束实战》

非空约束讲完了。接下来是列级别的第二道约束——默认值约束。这一段往下，默认值、检查、唯一，再到主键和主键约束，我们把数据库里最常用的一批"规矩"一次收齐。

### 默认值约束：不赋值时它替你填

顾名思义，默认值约束就是给某个列添加一个默认值的约束。关键在于——当你不往这一列插值的时候，它就走这个默认值。

语法非常简单，关键字叫 `DEFAULT`，写完以后后边跟一个对应的默认值就行了。

#### 三个要记牢的特点

第一，默认值不能添加到唯一或者主键上，其他列都是可以的。建表加约束时可以加多列，但唯独不能加在唯一列和主键列上。大家这点一定要记住。为什么？人家都唯一了，你还加个默认值——不插的时候默认值每次都是相同的，这不明显是冲突吗。主键列也一样，主键本来就是要求不能重复的。

第二，插入数据的时候如果没有显式地赋值，那就会走默认值。你没有主动给它赋值，它就走默认值。这里先埋一个伏笔：假如我插入空值，会不会走默认值？空算不算值？这个我们待会儿亲手试。

第三，添加默认值约束时，这个默认值一定要和列的类型匹配好。假设我有两个列，一个是性别，一个是年龄，假如我想给年龄加个默认值，那我写的默认值一定得是一个整数类型；同样的，如果我这有个字符串类型，那你加的默认值就也得是一个字符串。

#### 建表时加、修改表加，怎么删

添加的方式跟非空约束是一样的。

第一种，创建表的时候添加，直接在列的后边加个 `DEFAULT` 就可以了。如果这个列还有非空约束，可以继续再加，没问题，后边写个默认值就完事了。

第二种，创建表以后修改，`ALTER TABLE` 某个表，`MODIFY` 某一列，最后加个 `DEFAULT`。

删除也很简单，还是 `ALTER TABLE` 表名，改这一列，把 `DEFAULT` 去掉就完事了。

```sql
-- 建表时加
CREATE TABLE emp2 (
  name varchar(20) DEFAULT '二狗子',
  age  int NOT NULL
);

-- 建表后加
ALTER TABLE emp2 MODIFY age int DEFAULT 48;

-- 去掉默认值
ALTER TABLE emp2 MODIFY name varchar(20);
```

> **易错点**：`MODIFY` 后边可以加多个约束，但它不是累加，是覆盖。原来的列要是非空，你修改的时候只加一个默认值，那就把非空给弄丢了——默认就变成允许为空了。所以 `MODIFY` 之后，非空和默认值这两项都要写全。

#### emp2 上手：改列是覆盖，不是累加

光听不踏实，我们建个 `emp2` 试。`name varchar(20)` 给个默认值 `'二狗子'`（咱就起个俗点的名儿），`age int` 加 `NOT NULL`：

```sql
CREATE TABLE emp2 (
  name varchar(20) DEFAULT '二狗子',
  age  int NOT NULL
);
```

`DESC emp2` 一看：`name` 可以为空，Default 那一栏是"二狗子"；`age` 不能为空，但没有默认值。

接下来走修改表这条路。假设我们给 `age` 加个默认值 48：

```sql
ALTER TABLE emp2 MODIFY age int DEFAULT 48;
```

执行完再 `DESC` 一次，你会发现事情不妙——`age` 变成可以为空了。因为我这条语句里没写 `not null`，原来那个非空约束被整个覆盖掉了。

那要是非空还想留着怎么办？很简单，两项都加上：

```sql
ALTER TABLE emp2 MODIFY age int NOT NULL DEFAULT 48;
```

这回再执行，`age` 就既是不能为空、又有默认值了。

> **结论**：`MODIFY` 是把这个列的定义整个重写一遍，不是往原来那上面再叠一层。原有的非空、默认值，凡是这回没写的，都按"没写"处理。

#### 到底什么时候才会走默认值

表建好了，插数据看看。

第一种，我只写 `name`：

```sql
INSERT INTO emp2(name) VALUES ('张三');
SELECT * FROM emp2;
```

`age` 查出来是 48。我根本没有主动去插 `age`，它自己走了默认值。

第二种，我给 `name` 主动赋个空：

```sql
INSERT INTO emp2(age, name) VALUES (20, NULL);
```

这一条 `name` 就是 NULL，**没有**走默认值。

为什么？这里边得解释清楚：默认值是在**没有显式赋值**的时候生效的。你写了 `NULL`，那也是赋值，是主动赋值，所以它不走默认值。记住这一条，后面就不容易错。

那有人要问：如果 `age` 也加了 `not null`，硬给它塞一个 `NULL` 会怎样？来试：

```sql
INSERT INTO emp2(age) VALUES (NULL);
```

报的还是 `Column 'age' cannot be null`。它也不会回头去找默认值，直接插入失败——拦它的是非空约束。

好，最后把默认值删掉：

```sql
ALTER TABLE emp2 MODIFY name varchar(20);
```

再 `DESC` 一看，Default 那一栏已经空了。默认值怎么加、什么时候会触发、怎么删，到这儿就齐了。

### 检查约束：能塞表达式的万能约束

列级别的最后一个约束，检查约束。它的作用很简单：限制某一个字段的值是否符合我们自定义的要求。

比如要求性别这一列必须是男或者女——当然按数据类型，枚举类型也能指定，但这一边我可以用检查约束来实现。再比如年龄必须在 18 到 35 岁之间，才能查出这个值。这就是检查约束。

语法就是 `CHECK` 后边写个对应的表达式。

#### 三个特点，第三条是给开发泼冷水

第一，检查约束不是哪个版本都支持的。MySQL 5.7 相关的版本里虽然认识 `CHECK` 这个关键字，但它是解析完就丢掉了，没有实际效果；到 8.0.16 以后它才真正开始工作。

第二，检查约束是一个万能约束。它内部可以写表达式，可以写表达式来实现你任何你想做的检查工作。所以你主要看表达式要怎么写。

第三，这句话得给咱们泼一盆冷水：**不推荐用检查约束**。为什么？因为检查约束有点偏业务性了。你得把这些业务性的检查工作都交给数据库，数据库的压力很大呀，我压力很大，它要崩溃了，是不是？

所以建议是：如果想进行数据检查，建议做程序级别的限制，就是在你的代码中控制好这个数据，符合了你就插入，不符合呢你就不插入。别把这些检查工作交给数据库。

> **提示**：当然，万一你公司就是要用，那你就用，只是别忘了这条道理——检查是能做的，代价是你得自己扛着。别把所有的压力都压到数据库身上。

#### 加在哪儿：列后面，还是表级单写

创建表时添加，语法是 `CREATE TABLE`，写完列名之后注意：检查约束其实可以放在列的后边，但也可以不放在列的后边，你可以单独放一个。注意那个位置放完以后，逗号要隔开。检查约束属于表级别约束，写在括号里，它就会专门去触发检查你这个表达式的值。

第二种方式，创建表以后修改：

```sql
ALTER TABLE 表名 ADD CONSTRAINT 约束名 CHECK (检查表达式);
```

这里 `CONSTRAINT` 代表约束的意思，再写个约束名，给检查约束起个名，最后再写 `CHECK` 就可以了。

大家能发现，其实这个在写的时候也没有指定这个检查约束到底要添加到哪个列上。因为检查约束的表达式里边可以指向一列，也可以指向多列，所以它并不是针对于某一列，而是针对表内的数据做统一检查的。

> **注意**：加约束名的时候，这个约束名是自定义的，只要在一个表内不能重复就可以了。

删除是 `ALTER TABLE ... DROP CONSTRAINT 约束名`。注意啊，不是 `MODIFY` 了。名字记不住，往下有一节专门讲怎么查。

#### 怎么查：DESC 看不见的那些

之前那些非空、默认值，我们直接用 `DESC` 就能看到：能不能为空、类型、默认值，以及后面会说的它是不是一个索引。但检查约束这一类，`DESC` 是看不见的。

那约束怎么看呢？有一句 SQL：

```sql
SELECT * FROM information_schema.table_constraints
WHERE table_schema = '库名' AND table_name = '表名';
```

这句话啥意思呢？`SELECT` 是查询，后边 `FROM` 的这个 `information_schema` 代表一个库里边的某一张表，也就是说这个库表是固定的，这个库里专门存的就是 MySQL 的约束信息。当初装 MySQL 自带的一个库，它里边的表有一个对应约束的表，专门存着我们当前所有的约束。

下面 `WHERE` 条件里有个 `table_schema`，这个可以放我们自己的库，要查哪个库下边的；再放一个 `and table_name` 是哪个表名。

把库名和表名一填，一回车就能看出来。哪个约束、是什么约束类型，`type` 叫 CHECK 就是检查约束，是那种强制生效的；最后约束名也有了。第二个约束大家看见它不叫咱们起的那个名，它叫 `emp3_chk_1`——这个就是数据库自己给的默认名称，`表明_CHK_序号`。

#### emp3 上手与删除

还是建个员工表 `emp3`，两列：`gender` 性别、`age` 年龄。我要求性别必须是男或者女，年龄必须大于等于 48，写两个检查约束。

先在创建表的时候加一个：

```sql
CREATE TABLE emp3 (
  gender char(1),
  check (gender in ('男', '女')),
  age int
);
```

`IN` 就是代表它俩之间的"或"的关系，值在这个范围内才可以。注意这个 `CHECK` 前面一定要写逗号，跟前面的列隔开。

第二个我留着后期改：

```sql
ALTER TABLE emp3 ADD CONSTRAINT emp3_age_check CHECK (age >= 48);
```

这个写法稍微有点特别，不是 `MODIFY`，是 `ADD CONSTRAINT`。`CONSTRAINT` 这个单词的意义叫约束，加约束；`ADD` 就是加。起个约束名不要重复，我这里写的是 `emp3_age_check`。

执行完，用上面那句查 `information_schema` 的 SQL 一查，`emp3` 底下就能看到两个 CHECK 约束。

插数据验证一下。先插一条对的：性别填"男"，年龄给一个大于等于 48 的数，刷新保存，没问题。

接着我故意找茬：性别填"人妖"，年龄还是给一个合规的值。一执行，报错了——`Data too long for column 'gender'`，人妖超过我们 `char(1)` 的长度了。那就换一个，换成"妖"，再刷新，还是报错：因为"妖"不在这个检查约束的范围内。大家能看出来吗，检查约束是生效的。

那最后假如我想把这个检查约束删掉，怎么删？还记得吗，`ALTER TABLE`，也是修改表，修改的是 `emp3`，这回是 `DROP CONSTRAINT`，后边写这个约束名。那约束名叫啥？各位你记不住，就把它一执行下去，用前面那个查询语句查一下就知道了。我们 emp3 对应的约束名，是表名后边跟固定的 CHK，杠 1：

```sql
ALTER TABLE emp3 DROP CONSTRAINT emp3_chk_1;
```

执行一下，是不是删掉了？删掉以后再去查一下这个表中的约束，是不是就只剩一个了。这时候我再插一条性别"妖"的数据（年龄照旧给合规值），这回能保存了——因为 gender 上那个检查约束已经去掉了。

到这里，检查约束怎么写、怎么加、怎么查、怎么删就都过了一遍。

### 唯一约束：得跟别的行比一比

刚刚我们已经完成了列级别的约束介绍，接下来讲行级别、也就是实体之间的约束，这部分一共有三个：唯一、主键、主键约束。

```text
约束
├── 列级别约束（一列一列地管）
│   ├── 非空约束   NOT NULL
│   └── 默认值约束 DEFAULT
├── 检查约束       CHECK
└── 实体级别约束（行与行之间比）
    ├── 唯一约束   UNIQUE
    ├── 主键       概念：区分一行不重复的列
    └── 主键约束   PRIMARY KEY
```

图里前三样是刚收尾的列级别部分；检查约束虽然能写在列后边，本质上是表级的。真正需要行与行之间比较的，是下面这一支。

先说唯一。什么是唯一？这个可能就不用说了吧——你有一个还是俩？俩那就重复了，不唯一。这里边就可以限制某一个字段的值是唯一的。

那唯一跟前面几个约束有个本质区别：你需要对比其他行相关的数据，才能知道你是不是唯一。这才叫做行级别的约束——行和行之间要进行比较。

举个例子：这里有手机号，手机号可以为空，但是大家如果要填写的时候，必须要唯一。那这个时候大家可以用一个关键字叫 `UNIQUE` 就可以了。

#### 三个特点

第一，`UNIQUE` 允许一个表中有多个列是唯一的，或者是可以把多个列组成一个联合的。举个好理解的例子：假如有个班级有个学号，班级可以重复，学号呢你也可以重复，但班级和学号这俩不能一起重复。假如 1 号班级有 1 号学生，行；1 号班级有 2 号学生，行；但你不能出现两个"1 号班级 + 1 号学生"，那就不正常了。

所以它可以做一个组合唯一性：把多个列组合到一起，它们的综合值不重复。

第二，唯一约束是允许为空的，而且允许有多个空值。空不算重复，这个大家知道。

第三，如果创建唯一约束时不指定名字，它的约束名默认就是它的列名。之前默认值那些约束不是这样，但唯一约束的名字就是列名。

#### 建表时的几种写法

第一种方案非常简单，直接在我们的字段后边加个 `UNIQUE` 就可以了。加 `UNIQUE` 或者加 `UNIQUE KEY` 也都行——`unique` 和 `primary` 它们都是索引，索引就是 K，写 K 也可以不写。但如果你是单着在列后边写，指的就是这一列是一个唯一的限制。

第二种写法，在括号里单独去写。它前边的 `CONSTRAINT` 约束名是可以省略的，不写这个约束名就是默认用列名；但如果你要指定名称，后边跟 `UNIQUE KEY` 就可以了，代表 `UNIQUE KEY` 就要在括号里边去指定，可以指定其中的一个列；当然其实这里边你可以写个逗号，再写另外一个列，这里边可以写多列。

这种写法可以做联合唯一——假如说有两列，它俩合并在一起，或者三个列合并在一起作为一个唯一，那你就得用这种方法写。如果你用上一种写法，它只能是单打独斗的感觉，每个是一个单独的列。

```sql
-- 单列唯一
CREATE TABLE emp4 (
  name  varchar(20),
  phone varchar(11) UNIQUE
);

-- 联合唯一：class_no 和 stu_no 合起来才唯一
CREATE TABLE emp7 (
  phone     varchar(11) UNIQUE,
  class_no  int,
  stu_no    int,
  CONSTRAINT emp7_class_stu UNIQUE KEY (class_no, stu_no)
);
```

#### emp7 上手：组合唯一与多个空值

看约束有几种看法。第一种用 `DESC`，能看见有个 `unique`，一个是单独的、一个是组合的，但具体名字看不太清楚。第二种用之前那个查 `information_schema` 的 SQL 粘一份过来：查出来 `phone` 那条是一个唯一约束，另一条约束名就是我们自己起的那个，而它俩是一个联合、组合的。

那插数据看看效果。先插一条，两个值都为空——可以保存。再插一条 `1`、`2`——也可以保存。为什么？因为他们俩的组合只要唯一就行。再插一条一模一样的 `1`、`2`——这回组合重复了，那就不行了，直接报错。

```sql
INSERT INTO emp7 (class_no, stu_no) VALUES (NULL, NULL);  -- 可以
INSERT INTO emp7 (class_no, stu_no) VALUES (1, 2);         -- 可以
INSERT INTO emp7 (class_no, stu_no) VALUES (1, 2);         -- 报错：组合重复
```

> **结论**：唯一约束可以指定单列，也可以指定多列组合唯一。之所以能塞进两个都为空的行，是因为"空不算重复"。

#### 建表后加、删

创建表以后修改也一样简单，`ALTER TABLE 表名 ADD CONSTRAINT 约束名 UNIQUE KEY (列)`，后边可以写一个列或者多列，多列代表组合唯一。删除还是 `ALTER TABLE 表名 DROP CONSTRAINT 约束名`，跟我们之前一样。约束名要是记不住，还是用之前那个 SQL 查一下；不过大家注意，默认情况下它就叫列名。

比如我们把 emp7 里的 `name` 变成唯一的：

```sql
ALTER TABLE emp7 ADD CONSTRAINT emp7_name UNIQUE KEY (name);
```

因为你指定了名称，这回就用这个名称了，不再是默认列名。删也就一句：

```sql
ALTER TABLE emp7 DROP CONSTRAINT emp7_name;
```

删完再查一遍，name 的那条没了，联合的那条还在，没动到。唯一约束就讲到这。

### 主键：数据库靠什么认出两条一模一样的记录

接下来介绍实体约束里一个非常重要的概念，叫主键。我们会分两节讲：先说什么是主键，再专门讲什么是主键约束，把两个概念清晰起来。

先说场景。大家想想我们在班级，上学期间会不会出现这样一件事：班级里边有两个学生，同名，年龄也相同，性别也相同——是不是经常有这种情况。假设我们班里俩学生都叫二狗子，都是 18 岁，都是男。

这种场景，作为讲课老师是好区分的。因为虽然姓名这些属性相同，但一般外观长相不可能完全相同，对不对？有高的有低的，高的我就说大二狗子，低的叫小二狗子；如果胖呢叫胖二狗子，瘦的叫瘦二狗子。老是可以在外观上进行区分。

但是大家思考一个问题：那如果把学生的数据录入数据库，我们会出现什么场景？数据库里边他的 name、age、性别是完全相同的。数据库会不会知道他们谁高谁低、谁矮谁胖呢？它是不知道的。数据库只是站在数据角度来说，那这两条数据对数据库来说就是完全相同的。

这就犯了一个最大的忌讳：**如果说数据库里边存在这种重复数据，所有列都相同，那我们将无法做后续的操作**。

举个例子：假如说你把其中一个二狗子删掉，你能不能删？你没法删，对吧，俩一删俩都删掉了。修改也没法修改，等等。

那怎么解决这个问题呢？思路是这样的：第一，我们要保证一点，在任何情况下，表中行数据至少得有一列是不重复的，来避免整行数据重复。那么只要有一列不重复，那这整行是不是永远就不重复了。那么这一列如果能确保这个表中的数据都不重复，那我就称它为主键列，或者主键。

> **定义**：主键就是用来区分一行数据的那一列——它不为空，且唯一。举例：学生有学号、员工有员工编号、我们还有身份证号，这些都是区分我们每个人的一个最终标识。它防止其他属性相同，但主键一定不重复。主键也是这一行数据的标识。

那在这个表里加主键是什么样呢？原来有 name、age、性别，我再加一列学号，分别是 1 和 2，这样我就可以根据序号进行区分了。这个学号就称作主键列。

#### 自定义主键和自然主键

主键分类一共是两种。

一种叫自定义主键。像我们的学号，其实就是自定义主键。什么是自定义主键？就是人为创造的一列，专门用来做主键。它的使命就是永远不为空且不重复，来保证一行数据的唯一性。例如学号、身份证号等等。

大家想想，是不是就自定义主键？但有些同学老跟我犟，说身份证号不是自然主键，是自定义主键。大家想一个问题：谁出生的时候拿这个身份证出来？谁出生的时候第一时间告诉自己的父母，我的身份证号是啥？这不都是别人给我们编的一个码吗？这不是我们本身的特性，对不对。

第二种叫自然主键。什么意思呢？它并不是人为创造的，就是本身实体自带的一个属性列。假如你的学生表里边有 name、age、性别这些属性列，这个属性在当前环境下也是唯一且不为空的，它也可以做主键。假如说你本身有一个属性列，人的 DNA、瞳孔、牙齿的轮廓等等，它们也是人人都有、且不重复、且不为空，那它们其实也是可以做主键的。

> **易错点**：如果你用现有的某个属性列作为主键，那这一列将承载两个使命——第一，它本身就是一个实体的属性；第二，它还是个主键。

那要说哪个好呢？很多同学可能会说自然主键，因为这样的话我本身就要有这一列，我也不用额外创建列了，对不对。但是大家听我说，开发中我们全部推荐的是用自定义主键——人为造一个列，而不用现有的列。为什么？

第一，很多东西在当下你感觉是它是唯一的，但是你能保证它未来永远是唯一的吗？
第二，如果这个属性把它作为主键，那后期你是不能随意修改的。主键是不能改的，改路径相当于改了标识。那这个列万一真的需要修改怎么办呢？

所以说我们不用自然主键，就用自定义主键，大家记住了吗。

#### 几个容易记错的细节

第一，主键的数量问题。记住一张表只能有一个主键——这一点要加上引号，并不是一个列，只能有一个主键。

第二，主键分单一主键和复合主键。就像刚刚讲 `UNIQUE` 似的，你可以把一个列当作主键，或者多列的组合当作主键。但是就算多个列组合当主键，它也是一个主键，记住了，你不能有两个标识。

第三，主键列的类型可以是任意类型，只要满足唯一且不为空就可以了。数字也好、字符串也好，都可以。

第四，主键命名的问题。一般主键采用 identity 这个单词的缩写，也就是一个标识的缩写，一般叫某某 id、某某_id 等等。但是没有强制要求。假如我的主键叫二狗子、驴蛋蛋、狗剩子行不行？行行行，任意类型行行行，只要不重复且不为空就可以了。

第五，大家在创建主键约束以后，它会创建一个主键索引。什么意思呢？只要有了主键和主键约束，最后你的查询效率会提升——你根据主键查，它会提升查询效率。索引这块我们不细讲，但是记住：所以我们推荐每个表中都必须要有主键，至多它也只能有一个。

来简单总结一下。什么是主键？主键就是咱们一个区分一行不重复的列，永远唯一且不为空，它来标识这个不重复的列。然后主键分为自然主键和自定义主键，最终我们推荐自定义主键，例如我们的学号、员工编号以及身份证号——不是谁出生的时候就带着一个身份证的，对吧。

### 主键约束：给主键配上那部"法律法规"

刚刚我们已经介绍了什么是主键，那什么是主键约束呢？就拿学号这一列来说：我们知道它是主键，而且它是一个自定义主键，那我们要保证这个学号列唯一且不为空，用它来区分学员的不同。

但大家想一个问题：现在呢你就算创建一个表里边有个学号，那请问真的能保证唯一且不会空吗？假如我要插一个空值，你有没有什么办法，或者有没有什么惩罚的手段呢？答案是没有的。

表里边确实是有主键，但是他现在没有什么限制和约束，只有口头的一些概念。那怎么办？要给主键加个叫主键约束。

什么叫约束呢？约束能保证我们的这个主键列是唯一且不为空的，它就是一个限制、具体的限制。大家能理解吗。

举个例子。假如说啊我们国家说了，说大熊猫是国宝，它只是说了一句话：大熊猫是国宝，不能杀不能吃，不能打不能骂。好，这么说完了。但是各位，没有相应的法律法规去保护这个大熊猫，说白了这不就是谁都能上去打他两嘴巴子，也没什么惩罚。那大家想想问题，是不是你去动物园看大熊猫，都得先给他搂两下子。

那这时候是不行的。那怎么办？国家要出一个法律法规，就说谁碰大熊猫一下，我就啵啵 BIU BIU。这个大家能理解这意思吧。这各位，那就相当于主键约束，相当于就是对主键保护的一种法律法规。最后呢有了它以后，它规定什么呢？它就规定主键值必须唯一且不为空。谁要插入的空值和重复的值，我就给你抛异常。

> **结论**：主键 = 主键 + 主键约束，才是一个完整的主键。当然了，没有主键约束，它也叫主键——它也是国宝，是这个意思。主键约束是来保护主键数据的正确性的：主键是保证一行不重复的列，主键列应该唯一且不为空，这只是一个口号；但真正怎么能保证这一点呢？要加主键约束，它是针对主键列的数据约束和限制，确保主键列不会出现错误的数据。注意啊，它只是针对主键列。这是两个概念。

最后我问大家两个小问题：主键列一定要添加主键约束吗？没有主键约束，还叫不叫主键呢？

答案：第一，主键列不一定要添加主键约束，只要你真的能保证它唯一且不为空，那就可以不用加约束。第二，没有主键约束它也是主键，只不过这个主键数据不安全。大家记住这句话：主键是主键，主键约束是主键约束。主键和主键约束就好比卧龙凤雏，现在来说他俩肯定是一起出现的，卧龙三步之内必有凤雏。

#### 怎么加、怎么删

添加也分两种。第一种是建表添加，特别简单。如果说你单列作为主键，直接加个 `PRIMARY KEY` 就可以了。如果你组合咋办？我建议用第二种，就是之前像 `UNIQUE KEY` 是一样的，写个 `PRIMARY KEY`，起个列名，一个列逗号隔开或者多个列，可以做一个组合的主键。

创建表以后修改主键也很简单：

```sql
ALTER TABLE 表名 ADD PRIMARY KEY (列);
```

单个列或者多列都可以，作为组合主键或者单个主键。

删除更简单：

```sql
ALTER TABLE 表名 DROP PRIMARY KEY;
```

大家看，这里边删除跟之前不一样。之前的删除还要写一个 `CONSTRAINT`，还可以加个约束名，这不用写，不用写约束名。大家思考一下，为什么这里不用写约束名呢？因为主键只有一个，它知道删的是谁。你之前为什么要写？因为之前的 `UNIQUE` 也好，其他也好，它可能有多个。

#### emp8 上手

```sql
-- 方式一：建表时，单列主键直接写在列后边
CREATE TABLE emp8 (
  eid  int PRIMARY KEY,
  name varchar(20),
  age  int
);

-- 方式二：建表时，表级写，一个列或多个列都行
CREATE TABLE emp8 (
  eid  int,
  name varchar(20),
  age  int,
  PRIMARY KEY (eid)
);

-- 建表以后加
ALTER TABLE emp8 ADD PRIMARY KEY (eid);

-- 删除
ALTER TABLE emp8 DROP PRIMARY KEY;
```

`eid` 这列的类型你写啥都行，int、字符串都可以，只要不重复且不为空就行。大家注意 `DROP PRIMARY KEY` 这里边它不需要写主键约束的名，因为一个表只有一个主键约束，它就知道该删哪一个。

好，这就是我们关于主键和主键约束的概念，和它相关的语法。

### 本讲提到的题目

**题目一**：主键列一定要添加主键约束吗？

解析：主键约束是保护主键的手段，不是主键本身。主键的成立条件只有一条——这一列真实地做到了唯一且不为空。

答案：不一定要加。只要你真的能保证它唯一且不为空，那就可以不用加约束。

**题目二**：没有主键约束，还叫不叫主键？

解析：主键是一个概念——一列不为空且唯一、用来区分一行数据；主键约束是保障机制。

答案：也叫主键。只不过这个主键数据不安全——它只是个口号，数据库层面没有任何惩罚手段来拦你。

**题目三**：为什么删除主键约束 `DROP PRIMARY KEY` 不用写约束名，而 `DROP CONSTRAINT` 要写？

解析：约束名是用来在多个同类约束中定位目标的。

答案：因为主键在一张表里至多一个，目标唯一，数据库知道该删的是谁；而 `UNIQUE` 这些可能建了多个，才需要靠约束名来区分。

## 把约束收到底：自增长、外键与拆表之由

行级约束讲到最后一个，自增长。讲完它，域约束和实体约束就全部结束了；再往外走是多表约束，我们统一叫它主外键约束。名字很多——参照约束、引用约束、外键约束、多表约束都能叫，但说的是同一件事。

这一整段其实是一条线：先解决"主键值谁维护"，再解决"两张表怎么互相认得"，最后回到最朴素的问题——表到底该不该拆、怎么拆。约束讲完，六个面试题把这块知识点收个口，然后我们进到多表关系这一章。

### 自增长：把主键值交给数据库

#### 没有它，id 成了你的活

先说场景。现在有一张表，三列：`id`、`age`、`phone`。`id` 是主键，而且是整数类型。

每次插数据，你都得考虑 `id` 该填什么。`age` 和 `phone` 好说，照着真实数据填就是了。可 `id` 呢？你得保证这个值没被用过，不能重复，而且还得让它按某种顺序往下走。这时候维护起来就很苦恼——特别是并发一上来，谁也不知道刚才那条到底用了哪个号。

给 `id` 这一列加上自增长约束，事情就简单了。你每次只管 `age` 和 `phone`，`id` 自动按之前的最大值加 1 往下长，这一列永远不重复。

> **定义**：自增长约束是限定某个整数类型的列，在插入数据时不需要显式赋值，它的值会自动增长。语法关键字叫 `AUTO_INCREMENT`。

好处就两条：解放双手，不用自己维护主键值；顺带保证了主键值唯一。它其实就是 `PRIMARY KEY` 的好基友。

#### 三条硬性规矩

这三条一定要记住。

**第一，添加位置。** 自增长只能加在主键列或者唯一约束列上，普通列加不了。

**第二，数量限制。** 每个表只能有一个自增长约束。而且绝大部分情况下，它都加在主键列上。

**第三，类型限制。** 被自增长约束限制的列必须是整数类型。字符串怎么办？你的字符串可能很长，它不会长；总不能是 a、b、c、d、e 这么排下去吧。所以只能要求整数。

至于插入时怎么配合，还有几种情况：

| 插入时对 eid 怎么写 | 结果 |
| --- | --- |
| 只写 `ename`，压根不提 eid | 自动增长，取最大值 +1 |
| eid 写 `0` | 照样自动增长 |
| eid 写 `NULL` | 照样自动增长 |
| eid 写 `10`、`11` 这样的具体值 | 就插 10、11，不受自增长支配 |

> **易错点**：只有"不指定、指定 0、指定空"这三种情况才会触发自增长。你一旦指定了值，数据库就听你的，插什么就是什么。

#### 语法：建表加、改表加、拿掉

第一种，建表的时候直接加。在主键后边，或者在 `UNIQUE KEY` 后边写一个 `AUTO_INCREMENT` 就行：

```sql
CREATE TABLE emp9 (
    eid INT PRIMARY KEY AUTO_INCREMENT,
    ename VARCHAR(20)
);
```

执行完用 `DESC emp9` 就能看见——`eid` 那一行的 `PRI` 表示主键，在扩展信息那一列会出现 `auto_increment`，说明加上了。

第二种，表建完之后再补上。又回到 `MODIFY` 了：

```sql
ALTER TABLE emp10 MODIFY eid INT AUTO_INCREMENT;
```

这里有个特点特别容易搞错：**不需要再写 `PRIMARY KEY` 或者 `UNIQUE KEY`，它也不会覆盖你原有的主键或唯一约束**。它只是在后边追加一个 `AUTO_INCREMENT`。这跟默认值、非空可不一样，那些是会覆盖的。执行完再 `DESC` 一次，`auto_increment` 就出现了。

第三种，删除。更简单，把 `AUTO_INCREMENT` 去掉即可：

```sql
ALTER TABLE emp10 MODIFY eid INT;
```

原来那个 `AUTO_INCREMENT` 被覆盖掉了，而主键列依然存在。

#### 插入时的四种写法与"只记最大值"

现在 `emp9` 有主键、也有自增长了，我们插点数据看看：

```sql
INSERT INTO emp9 (ename) VALUES ('二狗子'), ('驴蛋蛋');
```

执行完刷新表结构，从 1 开始长。

你当然也可以管它。在插的时候把这张表复制一份，eid 那列写 0，刷新一下——从 3、4 开始；写 NULL，同样从 3、4 开始。

再往下，你如果自己赋值，写个 10、11，刷新就是 10 和 11，不顺着长。这时我抛个问题给大家：**这时候我再执行一次"不指定 eid"的插入，它是从 5、6 开始，还是从 10、11 开始？**

做个实验就知道了——结果是从 12、13 开始。

```text
insert 指定 1、2             -> 1, 2
insert 指定 0、NULL          -> 3, 4
insert 指定 10、11           -> 10, 11   (5~9 空着，不补)
insert 不指定 eid            -> 12, 13   (从最大值往下长)
delete 掉这几行再 insert     -> 14       (删了也不回头)
```

为什么中间的空缺不填？两个原因。一是填空缺更麻烦——它得记住哪些值有、哪些值没有，每来一个新号都要跳着判断一次；二是真要"从头开始重新算"，还可能算出两条数据撞同一个 ID，直接重复了。它只记最大值这一个数，每次基于最大值往下长。

> **结论**：MySQL 会记录这张表自增长的最大值，每次都在最大值基础上增长，就算删除也不会回退。这一条记住就够了。

### 外键：分数凭什么说这是二狗子的分

#### 二狗子 Java 考了多少分

现在有两张表。一张学生表，一张分数表。

学生表里是学生的编号、姓名、年龄、性别；分数表里有分数自己的编号、分数、学科，还有个 `sid`。这个 `sid` 是干什么的？分数是隶属于某一个学生的，所以它指向的当然是学生的信息。

我问大家一个问题：**二狗子 Java 考了多少分？** 答案是 88。有人问，为什么不是 90？90 分也是 Java 的呀。因为二狗子的编号是 1，而分数表里引用的也是 1——这一行的 sid 参照的正是学生表里 sid=1 那位，也就是二狗子本人，学科又刚好是 Java，这就拆出来了。

```text
[主表] student 学生表
  sid(主键)| sname   
  ---------+ --------
  1        | 二狗子  
  2        | 德华    
  3        | 蛋蛋    
       ^
       |  分数表的 sid 列引用这里的 sid
[子表] score 分数表
  cid(主键)| 分数  | 学科   | sid(外键)
  ---------+ ------+ -------+ ---------
  1        | 88    | Java   | 1        
  2        | 90    | Java   | 1        
  3        | 60    | MySQL  | 4         <- 学生表里根本没有 sid = 4
```

由此得出一个概念：分数表的 `sid` 和学生表的 `sid` 之间存在引用关系——分数的 `sid` 是去引用、参照学生表 `sid` 这个值的。你不能瞎写，写一个不存在的值，那就出问题了。

学生表的 `sid` 叫主键，分数表自己的 `cid` 也叫主键。那分数表里这个 `sid` 叫啥？叫**外键**。

#### 外键和外键约束，是两件事

> **定义**：外键指的是引用或者参照其他表主键列的那一列。它在你自己这张表里就是个非主键的普通列，但它参照着别的主表的主键值——因为它是"外面的键"，所以叫外键。

外键的取值范围应该在主键值的范围之内。上面那张图里 sid 写 1、2 都有人，写 4 就出问题了。于是我问：那 60 分是谁考的？对应的值是 4，学生表里没有这个人，说明这条数据本身就错了。

那怎么保证外键值正确？这就是外键约束登场的地方。

> **定义**：外键约束指的是，外键应该引用主键的值；如果不添加约束，就可能出现错误数据。比如 sid 那里写个 4，它照样不报错。加了外键约束之后，插入 4 的时候直接就报错了，因为主键里压根没有这个值。

所以要分清两个概念：什么是外键（一个列），外键约束是什么（保证这个列数据正确的一种限制）。外键约束跟主键约束是一个层级的概念——主键约束保证主键数据正确，外键约束保证外键数据正确。

> **提示**：就算没加外键约束，**它也依然是外键**，你心里得知道这层关系在。但最好还是加上。

到这儿很多同学会冒出来一句：阿里巴巴的规范手册里，好像不建议在数据库上加外键关系。这话不假，后面我们会讲到，加了外键关系会降低数据库的查询效率。但按标准语法来说，为了数据正确性，还是加上为好。

#### 主表、子表，以及先建谁

几个细节必须捋清。

**外键的数量。** 一张表里可以有 $N$ 个外键。因为一张表完全可以关联很多其他表的数据。

**主表和子表。** 被引用的那张表叫主表（学生表），含有外键的那张表叫子表（分数表）。这里有个现实用处：它给我们指点了建表的顺序——**先建主表，再建子表**。不然你的子表引用谁去？

而且主子表是相对的。今天学生是主表，明天学生可能去引用别人，它自己就成了子表。我们看表关系的时候，都是两两考虑。

**类型必须一致。** 外键类型不能瞎搞。既然要引用主键，外键就应该和主键的类型对应。列名可以不同——命名不同也不影响关系，因为谁引用了谁，程序员自己心里是清楚的——但最好相同，至少一眼能看出来。

#### 主外键关系是横向连接的前提

主外键关系是一个非常重要的关系。官方说法是这么回事，我们翻译成人话：

MySQL 是关系型数据库，数据按类别存到对应的表中。而表和表之间，可以通过主外键建立数据之间的关系。关系型数据库里的"关系"，指的就是主外键关系。两张表之间有主外键关系，就代表它们的数据互相关联，我们就能用**水平连接查询**的方式，把两张表的数据查到一张表里去。

> **结论**：外键有关系，才能进行水平查询。这句话记住，后面讲多表联查全靠它。

但请注意——**有主外键就行，不一定非得有外键约束**。

#### 有了主外键，主表就删不动了

还有一个影响特别容易被忽略。

学生表的 `sid` 一旦被别人引用了，你就不能像以前那样随便删、随便改了。举个例子：你想删学生表里 sid=1 这条，结果发现 1 已经被分数表引用好几次了，这时候就删不掉。

> **结论**：默认情况下，只要有主外键约束，删除主表数据时，如果子表存在引用，就会删除失败。

想删怎么办？三条路：一是创建约束的时候指定允许删除；二是先把子表数据删掉，再删主表；三是干脆把这个主外键约束干掉。

### 外键约束的增与删

#### 建表时加

加之前先明确三点：第一，得有两张表；第二，先建主表，再建子表；第三，**这个约束是加在子表里的**，因为是子表去引用主表。只要有外键的表就是子表。

看代码。先建主表：

```sql
CREATE TABLE student1 (
    sid INT PRIMARY KEY AUTO_INCREMENT,
    sname VARCHAR(20)
);
```

再建子表，在字段列表最后用逗号隔开，写约束：

```sql
CREATE TABLE score1 (
    cid INT PRIMARY KEY AUTO_INCREMENT,
    number INT,
    sid INT,
    CONSTRAINT s_s_1_fk FOREIGN KEY (sid) REFERENCES student1(sid)
);
```

拆开看这一行：

```sql
CONSTRAINT 约束名 FOREIGN KEY (外键列名) REFERENCES 主表名(主键列名)
```

`constraint` 后面起个约束名，`fk` 是 foreign key 的缩写，随便起，只要不重复就行；`foreign key` 后面括号里写**当前子表里那个外键列的名字**，这里两边都叫 `sid`；`reference`（拼写别错）后面写主表名，括号里写主表的主键名。

`DESC score1` 之后，你会看到 `PRIMARY KEY` 下面多了一条 `foreign key` 约束。再 `DESC student1`——**看不见外键**，因为外键住在子表里，主表那边只有主键。

#### 建完表再补

跟之前一样，也可以后期修改：

```sql
ALTER TABLE score2 ADD CONSTRAINT s_s_2_fk FOREIGN KEY (sid) REFERENCES student2(sid);
```

跟前面建表时写的那一坨一模一样，粘过来改个名字就行。有个小提醒：**一定要加分号**，否则语句会被连在一起执行，直接报错。

#### 删除得删两样

删除稍微有点麻烦，因为外键除了约束本身，还牵涉到索引。**删约束的同时，索引也得删干净。**

第一步，删约束。跟删主键不一样——主键一个表只有一个，写 `primary key` 就完事；外键可能有多个，所以必须指定约束名：

```sql
ALTER TABLE score2 DROP FOREIGN KEY s_s_2_fk;
```

第二步，删索引。外键会主动创建一个外键索引，先查出来：

```sql
SHOW INDEX FROM score2;
```

结果里 `Key_name` 就是索引名，sid 那一行说明有个以 sid 为键的外键索引。然后：

```sql
ALTER TABLE score2 DROP INDEX s_s_2_fk;
```

> **提示**：有些版本删约束的时候会顺带把索引删干净，有些删不干净。建议还是老老实实两步手动删，保证删得干净。索引是额外辅助的一种数据结构，留着就是白占地方。

### 级联动作：给"动主表"定规矩

#### 从诛九族说起

先说场景。学生表里有 sid=1、sid=2；分数表里引用的 sid 全是 1。这时候你想删学生表里 sid=1 那条——删不了，被引用了。但 sid=2 呢？能删，因为没人引用你。

为什么会这样？因为添加外键时可以设置动作，而默认值就是：删除或修改主表数据时，如果子表有引用，就报错，不让你删。

这类动作设置就叫**级联**。

> **定义**：级联动作指的是——对主表的数据进行修改或者删除时，子表如何做出响应。

注意，只有关键词涉及 update 和 delete。你添加查询的时候是没有级联动作的。

那"级联"这俩字怎么来的？有点像古代的连坐。一个人犯了事，比如欺君罔上、骗了皇上，皇上定个罪叫诛九族——九族都找出来杀掉，连隔壁的狗都不放过。其他人为什么被杀？因为被连坐了。现在我们说的级联设置，是主表数据改或者删的时候，子表跟着怎么动，逻辑是一样的。

#### 四个可选值

| 值 | 主表 update / delete 时子表的响应 |
| --- | --- |
| `CASCADE` | 同步过去：主表改了子表跟着改，主表删了子表跟着删 |
| `SET NULL` | 主表删了不连带删子表，只把子表里那个外键列置空 |
| `NO ACTION` / `RESTRICT` | 子表什么都不做，但只要子表有引用就抛异常；默认值就是 `RESTRICT` |
| `SET DEFAULT` | 给子表的外键列设一个默认值（有些驱动不识别，知道一下就行） |

`NO ACTION` 和 `RESTRICT` 效果基本一样。`CASCADE` 最狠，一旦设上，主表那边一删，子表相关的记录同步删——你甚至不知道数据去哪了。

#### 我建议这么设

第一条：`ON UPDATE CASCADE`。父数据更新，子数据自动跟着更新。比如父表 sid 从 1 变成 5，子表里所有引用 1 的行自动改成 5。

第二条：`ON DELETE RESTRICT`，走默认值。父数据删除时先检查，子表有引用就不让删。

> **结论**：删除**不要**设成 `CASCADE`，太暴力了。实际业务里，删主表数据之前你得先提示一下子表有没有引用，人家同意了再删——这本来就是正常的业务流程。设成 `RESTRICT`，逼着你走一遍这个确认过程。

万一真删了主表、子表还留着引用，那条数据就成了**孤儿数据**——小白菜啊，地里黄啊，两三岁啊没了爹娘，它就是没人认领的数据。

语法上，它写在约束的最后，可以写 update 一个、delete 一个：

```sql
CONSTRAINT 外键约束名 FOREIGN KEY (子表外键名) REFERENCES 主表名(主键名)
    ON UPDATE CASCADE
    ON DELETE RESTRICT
```

建表的时候能写，建完表 `ALTER TABLE ... ADD CONSTRAINT` 也能写。不写就走默认值。

### 面试里关于约束的六个问题

约束讲完了，我们把这块知识点用六个题收个口。这六个问题我按顺序过一遍。

**建不建外键约束有什么区别？** 其实对于查询、对于是不是主外键关系，没什么区别。建了外键约束，只是在语法层面上多了一层数据校验和保证，它是一种数据保证机制。而且就算没建外键约束，它依然是主外键关系。

**建外键约束对查询有影响吗？** 上面那句"对查询没区别"，第二问要补一句：有影响，但影响的是效率，不是正确性。有了外键约束，数据库要做额外的关联检查和连接动作，查询效率会降低。

**设计中为什么不想让字段是 null？** 两个原因。第一，不好比较。大于、小于、等于这些运算符可以比较数值类型、字符串类型、时间类型，但 `NULL` 比较不了。列里要是有 null，判断它是否等于某个值，还得改用 `IS NULL` 或 `IS NOT NULL`。同样一个"等于"动作要换不同符号，很麻烦。第二，站在更高一点看，如果为 null，查询效率不高，它会影响索引效果——索引这东西就像图书目录，能提高查询效果，但有 null 会打折扣。所以建表时建议把非空约束加好。

**加了 `AUTO_INCREMENT`，这个字段是从 1 开始吗？** 答案不完全对。第一次添加、而且你之前没手动插过值，它就是从 1 开始。但如果你自己主动插过值，比如第一条手动给了 5，下次就从 6 开始。记住前面那条结论：它会记录当前表中的最大值，每次在最大值基础上加，而且**就算删除了也不会回头**。

**每个表都能随便选存储引擎吗？** 先说什么是存储引擎。打个比方：汽车里得有个发动机，汽车靠发动机驱动完成行走，最终虽然有轮子，但一切力量来源都是发动机。存储引擎就是真实完成表数据操作的那部分功能的一个集合。MySQL 不同版本提供了不同的存储引擎，表和库都可以设置，没设置就走默认的。这题不是想问有哪些引擎，是想问你**能不能随意选**：只要你加了外键约束，存储引擎就不能随意选了，因为**外键约束不能跨存储引擎使用**。假设两张表一个是 A 引擎、一个是 B 引擎，它们之间建立外键约束是联不到一起去的。所以：有外键约束——不行；没有——当然可以，每张表都独立设置。

**创建库的时候，你会给表添加完备的约束吗？** 说实话回答可能会伤一部分同学的心——学了这么多天约束，后期可能用不太多。真实场景下，我们一般只加一些**单表约束**：非空约束、默认值约束、主键约束、自增长约束。这些是辅助我们在插入、更新数据时减少出错的手段。但真实开发中，一般不加外键（主外键）和级联动作。比如连表删除这些，不会做。因为一旦加上外键和级联，它有时候会影响你整个表结构——你可能不知道这个数据哪去了，它就被级联删掉了，没经过你的手处理，数据就没了。业务流程你也可能不清晰。

> **结论**：阿里巴巴提供的 Java 开发手册里，强制要求不得使用外键以及级联，一切相关概念应该在应用内解决。你想保证数据正确性，在你的程序里用代码做校验和连接就行；你想做级联删除，也请在程序里自己写代码做连表删除。所以答案是：会加单表约束，外键约束一般场景不加。

约束这块就到此为止了。而约束讲完，其实也引出了一个非常重要的概念——主外键、多表关系。从下一章开始，我们正式进入多表查询。

### 多表关系：为什么非得拆表

#### 四步学习路线

在学多表查询之前，先把思路理顺。我们的目标一定是多表查询，但在查询之前到底要干什么事？我把它分成四大步。

第一步，理解为什么数据要拆表存储。为什么我一个项目会有成百上千个表？两个表直接搞定不是更简单吗？第二，理解完拆表以后，要分析这些表之间到底存在哪些关系。第三，通过分析表关系，知道数据库需要预先创建表结构，那这些表关系靠什么样的语法才能真正维系住——也就是建表时要加哪些约束和限制。第四，理解了这三点之后，再去学多表查询的语法有哪些，最后做一个超级综合的实战。

这一章只解前三步：为啥拆表、多表关系、以及表关系的语法限制。

#### 一张综合表的代价

举个最简单的例子。数据库里要存一个学生实体，学生有 `id`、`name`、`age`。那创建一张学生表存进去就行了，存三名同学：德华、二狗子、蛋蛋。存完没有争议。

现在问题来了：不光要存学生信息，还要存分数。期末考试，每个学生会有多条分数——德华考了 MySQL 和 Java。

不分表其实也很简单。搞一张大表，综合表，在里面同时记录学生信息和学生分数：

```text
  name  | age| 科目 | 分数
  ------+ ---+ -----+ ----
  德华  | 18 | MySQL| 88  
  德华  | 18 | Java | 90  
  德华  | 18 | MySQL| 77  
  二狗子| 20 | Java | 66  
```

一眼就能看出来问题：**学生的信息出现了多次**。你都不用考虑主键重复的问题，光看数据就已经很乱了——大量冗余，而且展示得乱。

怎么解决？很简单，拆！拆拆拆！分分分！分成两个表：学生还单独存在学生表里，另外专门创建一张分数表。分数表里有分数的 id、具体分数，还有一个 sid。这不就是上节课刚讲过的经典主外键关系吗？分数里通过存储学生的主键，这个主键就叫它的外键，最终跟学生表的数据产生关联。

```text
  学生表(主表)         分数表(子表)
  sid| name            sid| 科目 | 分数
  ---+ ------          ---+ -----+ ----
  1  | 德华            1  | MySQL| 88  
  2  | 二狗子          1  | Java | 90  
  3  | 蛋蛋            1  | MySQL| 77  
  .  | ...             2  | Java | 66  
```

这样数据就没有冗余了，查询的时候两个表联查一下，用多表查询的语法就完事了。

细心的同学可能发现，图里课程的名也没了。这是对的——课程后期也会独立创建一张表，分数表再去引用课程那张表，两边之间同样是一个引用关系。现在先只展示两个表。

> **结论**：在开发中，我们都会把数据按照类别分别存储。这就是拆表。

#### 拆表之后的三重好处

**第一，提高查询效率。** 混在一起的时候，假如我只想查学生信息，不好意思，你也得把分数带着；只想查分数，也得把学生带着。只有都查，那混在一张表里才有存在的必要。分表以后，单查学生、单查分数都行，要联查就用下一章的多表查询——效率自然更高。

**第二，防止数据冗余。这是最核心的一点。** 德华出现一次不算问题，那要是八门课程，德华得出现八次，数据重复得有多厉害。

**第三，方便数据的更新和维护。** 不分表的时候，你想改德华的名字，改一个位置不够，所有出现德华的地方都得改。二狗子同理。这就是数据冗余带来的麻烦——改数据不能只改一个位置。分表之后，你想改德华就怎么改怎么改（只要不改主键），因为我是通过主键引用的，你这边改了德华的信息，那边引用过去自然就更新了。

#### 多表关系记这四条

把这一章的概念捋一下，记住四条就够。

**第一，MySQL 是关系型数据库，数据按类别存储到对应的表结构中。** 正因为是按类别拆开存，一个项目里有成百上千个表是正常的。

**第二，表和表之间通过主外键建立数据关系。** 这里一定要理解——所谓"表关系"，指的其实是**表中数据的关系**。下一章讲多表查询时，怎么才能把两张表的结果水平拼到一起？前提就是你得有主外键。没主外键、没关系，你查什么查？

**第三，拆表存储可以减少数据冗余，并提高查询和操作效率。**

**第四，正因为拆了表，我们不仅要会单表查询语法，还必须掌握多表的关联查询语法。** 这就是你要学多表查询的原因——表都拆开了，你光会单表查不够。

最后补一句：关系型数据库中，表结构是需要提前创建的。在做数据操作之前，你得先学 DDL——怎么创建库、怎么创建表。而在创建表的时候，你还要通过分析数据之间的关系（后面会讲多表具体有几种关系），添加合理的约束和限制，来保证表里只存储符合这个关系的数据。

### 本讲提到的题目

#### 概念题

**二狗子 Java 考了多少分？** 答：88 分。姓名并不出现在分数表里，是靠 sid=1 引用到学生表才确定的；90 分虽然也是 Java，但对应的是同一个人另一条记录，靠这条 sid 定位到的是分数表第一行。

**分数表里那条 60 分是谁考的？** 答：谁都考不了，是条错数据。它 sid=4，而学生表里根本没有 sid=4。这正是外键约束要拦下来的。

#### 动手验证题

**手工插过 10、11 之后，再执行一次不指定 eid 的插入，从几开始？** 答：12、13。`AUTO_INCREMENT` 只记录最大值，每次在最大值基础上加 1，中间 5 到 9 的空缺不会回头补。同理，删掉这些行再插入，还是从 14 开始。

#### 面试题

**建不建外键约束有什么区别？** 答：只差一层数据校验与保证，不影响是否构成主外键关系；没有外键约束，它依然是主外键。

**建外键约束对查询效率有影响吗？** 答：有，会降低效率，因为它带来额外的关联检查和连接动作。

**设计中为什么不希望字段为 null？** 答：一是 `NULL` 比较不了，等值判断得改用 `IS NULL` / `IS NOT NULL`，麻烦；二是为 null 会影响索引效果，拉低查询效率。

**加了 `AUTO_INCREMENT`，字段是从 1 开始吗？** 答：只在你从未手动指定过值时才是。它记录当前最大值，每次在最大值上 +1，删除后不回退。

**每张表都能任选存储引擎吗？** 答：不能一概而论。**外键不能跨存储引擎使用**，所以有外键约束时相关表必须同一引擎；没有外键约束时，每张表都能独立设置。

**创建库时会给表添加完备的约束吗？** 答：不会。只加单表约束（非空、默认值、主键、自增长）；外键约束和级联动作在真实开发中一般不加，阿里巴巴规范手册也强制要求外键及级联在应用内解决。

## 多表关系与多表查询:三种关系怎么建,又怎么查
> 对应块：BLK15 | 覆盖分集：P71-P77 | 块标题（分集名）：《71-数据库多表关系篇-多表具体关系分析》

### "多表关系"这四个字,得先抠明白

先把标题抠一遍,这两个括号是整块内容的地基。

第一个括号,单引号里的"多"字底下加了个"两"。为什么要加?因为**"多表关系"这个说法本身就是个伪命题**。你项目里哪怕有 100 张表,真落到"分析表关系"这一步,永远是**两两之间**去分析。假如 A 和 B 之间是一种关系,A 和 C 之间可能就换了一种关系。所以多表关系从来不是 100 张表搅在一块儿谈关系,而是一堆两两之间的关系。

第二个括号,"表"字后面加了个"数据"。

> **定义**:表关系指的是**表中数据行之间的关系**,是行跟行对应出来的关系。表是一个一个的表,表跟表之间哪来的关系?表自己不会有关系,关系是数据挤出来的。这一点一定要理解。

这两句先立住,后面所有的建表语法、所有的查询语法,全是在这两句上搭的。

标题下方列出来的具体关系一共三种,而且每一种的"人话翻译"都很短,我给你一句一句拆开。

**一对一**。两个表之间,每行数据都对应唯一的对应关系。听着有点绕,翻译过来就是:我的一行数据对应它的一行数据,它的一行数据也对应我的一行数据,至多对一行,也可以不对应,反正最多一行。典型的例子是员工和员工的唯一档案——一个员工实体,一个档案实体,一对一。

**一对多**。一个表里的行关联了另一个表的多行数据,反过来只能关联一行。也就是 A 可能关联 B 的一行到至多多行,但 B 至多只对应 A 的一行。例子是作者和文章:一个作者能写多篇文章,每一篇文章只对应一个作者。

**多对多**。两张表的记录都可以对应对方的多条数据。例子是学生和课程:一个学生能选多门课,一门课也能被多个学生选,双方都是"对多",合起来就是多对多。

```text
【一对一】  emp.eid  ⇄  profile.eid
            （主表）    （子表：外键 + UNIQUE，同一个 emp.eid 最多命中一行档案）

【一对多】  article.author_id  ──▶  author.id
            （子表：外键，可重复）      （主表：同一个 author.id 可以命中多篇文章）

【多对多】  sc.s_id  ──▶  student.s_id      关系是间接的，全靠中间表 sc
            sc.c_id  ──▶  course.c_id         撑起来，sc 里的一行就等于
                                              「某个学生选了某门课」这一件事
```

> **结论**:表关系一定要**双向看**。一对多拆开看是"一对多",反着看就是"多对一";多对多就是两个方向都是对多。所以你问"作者和文章是什么关系",得先把视角摆清楚——作者看文章是多,文章看作者是一,合起来统一就叫一对多。记住"双向"这一条,后面判断少一半的错。

以上是我们大致分析出的表关系。接下来挨个系统地介绍,一个一个落到建表语法上。

### 一对一:为了把冷数据挪到一边去

先看例子。还是员工和员工唯一档案:把员工的**姓名、年龄、性别**存在一张表里,把**地址、级别**这些东西拆到另一张表。关系怎么建立?员工表里放的是**主键**,档案表里带一个**外键**,指向员工表的主键。数据靠主外键,一下就关联上了。

只要这个外键**出现一次、至多出现一次**,不就是一对一了吗?

所以一对一的最终特点就一句话:一条员工至多对应一条档案数据,一条档案也至多对应一条员工数据。

#### 一对一拆表,不是为了消灭冗余

这里有个特别容易想歪的地方,先掰过来:**一对一这种表结构,解决不了数据冗余问题**。你们想,二狗子只有一个地址,那"一对"这种关系本来写在同一张表里也完全没问题,一点都不冗余。前面说的数据冗余指的是什么?是一个学生对应多个分数,没办法,学生就得出现多次。而一对一是只对应一,压根不冗余。

所以一对一的本质不是来解决数据冗余的。那它存在的意义是什么?

#### 真正的动机:冷热数据分离

一张表里通常会同时有**冷数据**和**热数据**。什么叫冷数据?就是很少用的数据,像冷宫一样,很冷,妃子被打入冷宫,皇上就肯定不待见了;热数据就是经常要查询的数据。

举个例子。假如我们不拆表,就把员工信息合在一起变成一张表。平时我们只用**姓名、年龄、性别**这三个字段,而地址和级别基本只在展示详细信息的时候才拿出来。那问题来了:在一张表里,你每次查询是不是都把这些列全查出来?或者都在这些列的基础上做查询?你既然不要,每次都带着它,显然就会**降低查询效率**。

所以一对一的真正意义是:把一张表中的**冷热数据分别存储到两张表,或者三张表、四张表都行**。最终一张表存热数据,一些表存冷数据。想查热数据就查这张表,想查冷数据就查那张表,热数据的查询频次高,效率就高;如果两个都想查,两张表一关联也就出来了。

> **提示**:这个道理生活里天天见。你用 QQ、用微信,都有"基本信息",再点开还有"详细信息",它们为什么要分开写?很可能就是存在了多张表里,而它们之间的关系,恰恰就是一对一。

#### 怎么用约束把它维护住

一句话:**一对一就是外键唯一**。那怎么保证唯一?两种方案,都在子表的**外键**上下功夫。

第一种(在档案表里正常保留自己的主键):外键那一列上加一个 `UNIQUE` 唯一约束,这就形成了一对一。

第二种(档案表干脆不要自己的主键):直接让这个 `eid` 既是外键又是主键,给它加 `PRIMARY KEY` 约束。因为一旦加了主键约束,这个值就**非空且唯一**,一样能是一对一。

```sql
-- 主表：员工表。姓名、年龄、性别放这里
CREATE TABLE emp (
  eid    INT PRIMARY KEY,
  name   VARCHAR(20),
  age    INT,
  gender CHAR(1)
);

-- 方案二：档案表有自己的主键，外键列加 UNIQUE
CREATE TABLE profile1 (
  id      INT PRIMARY KEY AUTO_INCREMENT,
  eid     INT UNIQUE,                              -- 外键 + 唯一 → 至多一条
  address VARCHAR(50),
  level   VARCHAR(20),
  CONSTRAINT fk_profile1_eid FOREIGN KEY (eid) REFERENCES emp(eid)
);

-- 方案一：eid 既是外键又是主键，不用 AUTO_INCREMENT，
-- 因为值不是自己长出来的，是引用对方 emp.eid 的
CREATE TABLE profile2 (
  eid     INT PRIMARY KEY,                         -- 同时是外键
  address VARCHAR(50),
  level   VARCHAR(20),
  CONSTRAINT fk_profile2_eid FOREIGN KEY (eid) REFERENCES emp(eid)
);
```

对比一下:方案二里 `profile1` 有自己的 `id` 主键,`eid` 只挂一个 `UNIQUE`;方案一里 `profile2` 干脆没有 `id`,`eid` 直接兼职主键和外键。两种都能把 emp 和 profile 维护成一对一。`emp` 引用不了第二条同号档案,你插两条相同的 `eid` 试试,直接给你拦下来。

> **易错点**:方案一里千万别再顺手写 `AUTO_INCREMENT`。那个值是引用对方主键来的,不是自己长的。方案二里的 `id` 才是自增的。

配套工具也说一下:我们用的是 Navicat 社区版,免费的。想直观看表关系,升级到企业版之后有个功能,点开可以把两个表拖进去,它会直接告诉你这是一对一还是一对多、关系建没建成功。课上就不升级了,它要钱;不升级的话,自己插两条数据互相引用试一下,一样能验证。

### 一对多:外键能重复,这才是治冗余的那味药

一对多就简单了。还是作者和文章表:一个作者可以对应多篇文章。二狗子这边对应了一篇文章,没问题;驴蛋蛋写了两篇文章。为什么能写两篇?**因为在文章表里,那个外键把驴蛋蛋的主键引用了两遍**。

> **结论**:只要有表关系,就一定有主外键。一对一、一对多、多对多,全都是主外键撑起来的,这一点先刻在脑子里。

那一对一和一对多的**唯一区别**是什么?就卡在外键上:

- **一对一**:外键必须唯一,加 `UNIQUE` 约束,或者干脆把外键当主键。
- **一对多**:外键**可以出现多次**,不能加唯一约束,外键也不能当主键。

所以一对多的表里,一定会有一个**单独的主键**,外键就正常加一个外键约束,什么都不加限制,一对多就成立了。最终特点还是一个作者对应多条文章,一个文章只对应一个作者。

这一节还有两个小细节得说清楚。

第一,**一对多关系能解决数据冗余问题**吗?能。回头看那张表,驴蛋蛋是不是出现多次了?这完全是可以的、正常的。一对多存在的意义,就是拆表存在的意义:**解决数据冗余,以及提高数据操作效率**。只要大家发现一个实体有对应多个子元素,那就得完成表的拆分,记住了吗?

第二,维护方式极其简单:正常添加外键约束,**只要保证外键不加唯一约束**,就是一对多。

```sql
-- 主表：作者
CREATE TABLE author (
  id     INT PRIMARY KEY AUTO_INCREMENT,
  name   VARCHAR(20),
  age    INT,
  gender CHAR(1)
);

-- 子表：文章。文章自己也有主键，这一条一定要记住
CREATE TABLE article (
  id        INT PRIMARY KEY AUTO_INCREMENT,        -- 文章自己的主键
  title     VARCHAR(50),
  author_id INT,                                  -- 外键，刻意不加 UNIQUE
  CONSTRAINT fk_article_author FOREIGN KEY (author_id) REFERENCES author(id)
);
```

`author` 是主表,是被引用的那一个;`article` 是子表,带着外键往上指。外键不加任何限制,驴蛋蛋的文章想写几篇写几篇。在 Navicat 里把这两张表建完、刷新一下关系视图,一对多的关系就出来了。

### 多对多:一张表装不下,那就再加一张

多对多先看例子:学生和课程。学生表里有二狗子和蛋蛋,`s_id` 是它的主键;课程表里有 Java 和 H5,Java 是常老师教的,H5 是马老师教的,`c_id` 也是主键。这两张表的数据之间就是多对多。

那问题来了——大家想一下,**这个外键到底加在学生表上,还是加在课程表上?**

想明白了没有:**谁加都不行**。假如我在课程表里加,我只能加一个 `s_id`,那我只能引用一个学生,我引用不了多个;加在学生表上,一个 `c_id` 也只能引用一门课。所以这个外键根本无处安放。

怎么办?**多对多的表,必须额外再创建一个中间表**。如果分析出两个实体是多对多的关系,那就一定要额外建一张中间表,这是必须做的,没有第二种走法。

中间表里可以包含**两个外键**:一个跟学生表,一个跟课程表。最终数据通过这种**间接引用**的关系连起来。

```sql
-- 两个主表，先建好，否则中间表的外键会报错
CREATE TABLE student (
  s_id INT PRIMARY KEY,
  name VARCHAR(20)
);

CREATE TABLE course (
  c_id INT PRIMARY KEY,
  name VARCHAR(20)
);

-- 中间表：两个外键，谁都不许加 UNIQUE
CREATE TABLE sc (
  s_id INT,
  c_id INT,
  CONSTRAINT fk_sc_student FOREIGN KEY (s_id) REFERENCES student(s_id),
  CONSTRAINT fk_sc_course  FOREIGN KEY (c_id)  REFERENCES course(c_id)
);

INSERT INTO student VALUES (1,'二狗子'), (2,'驴蛋蛋');
INSERT INTO course  VALUES (1,'Java-常老师'), (2,'H5-马老师');
INSERT INTO sc VALUES (1,1), (1,2), (2,1), (2,2);
```

对着这四行数据看一遍就明白了。二狗子(`s_id=1`)上过常老师的 Java 课,就是 `(1,1)`;驴蛋蛋(`s_id=2`)既选了马老师的课(`2,2`),也选了常老师的课(`2,1`)——四行合起来,意思就是**他俩都上过两位老师的课**。

> **易错点**:中间表的外键列上**绝对不能加唯一约束**。加了唯一,就退化成"一个学生只能选一门课"了,那既不是多对多,也不是一对一,是把多对多硬生生压扁了。

另外提醒一句,`CONSTRAINT` 这个关键字是**可以省略**的,前面讲外键约束的时候说过。

多对多记住三步就行:第一,把两个主表先创建好;第二,创建中间表,中间表至少包含两个主表的外键;第三,中间表的外键上不添加唯一性约束。这就搞定了。

至于中间表以后怎么用?这里先埋个伏笔:等到多表查询那一块,查"某个学生以及他关联的课程"这件事,如果是多对多,那就是**三张表查询**——学生先关联中间表,再通过中间表关联课程表,最终完成表关系的查询。

到这里,多表关系、为什么拆表、到底有几种关系、关系维护的具体语法和细节,就全过完了。下面进入多表查询。

### 多表查询:先合成一张表,再当单表查

先说清楚接下来要走到哪儿。这一章是整个课程的高潮和重点部分,一共分五个小节:第一小节回顾 DQL、顺便理解多表查询到底要做哪些事;第二、三、四小节讲具体的语法;第五小节做章节综合实战。

#### DQL 回顾,以及多表查询到底要干什么

DQL 的语法当时分成两大类:**单表查询**和**多表查询**。单表查询我们已经学完了——基于一张真实表作为数据源,用查询语法得到一张我们想要的虚拟表,也叫结果集。用到的有 `SELECT` 关键字、`WHERE` 条件、运算符、单行函数和多行函数等等,这些都学过了。

那多表查询到底要干哪些事呢?先回答一个关键问题:**之前学过的单表查询语法,在多表里还能不能适用?**答案是能。多表查询只是在单表的基础上做了一点额外扩展。

多表查询的目标是:数据源来自多张真实表。但这里有个特别容易搞反的地方——**第一步不是写查询语法,而是想方设法把这些多张表的数据用合并语法先合并成一张表**。合并成一张表以后,再拿单表查询语句去查,最终查到我们的虚拟表。

所以说白了,多表查询的前置知识,只多了一个东西:**一个合并语法而已**。之前讲的那些单表操作在这里依然可用,额外要学的就是"怎么把它们合起来"。这就是多表查询最核心的重点。

#### 合并的两个方向:垂直与水平

两个数据合起来能怎么合?打个比方:你手里有两块正方形积木,怎么合成一块?很明显,水平合或者垂直合,都行。

**垂直合并**,就是把两个结果**上下摞在一起**,形成一个结果集。语法关键字是 `UNION` 和 `UNION ALL`,主要作用就是把多个表的结果汇总在一起,统一返回。它**不要求两个表之间存在关系,不要求有主外键**——因为它压根不管数据行之间怎么关联,它只是把结果摞到一块儿去。

**水平合并**,就是把两个表的结果**左右连到一起**,这叫**连接查询**。它要求两个表**必须有关系,必须得有主外键**。为什么必须?你想啊,两边各有一条数据,凭什么它们能连成一行?它们是**靠着主外键的值进行引用**才连上的,没有主外键,那就是瞎连。

哪一个更重要?毫无疑问是**水平合并**。因为关系型数据库的特点就是数据按类别分表存储,最终我们要做的是关联查询,把数据合并到一个结果里去,而"合并到一个结果"指的就是行与行之间要产生关联。

> **结论**:多表查询就两种合并语法——垂直合并(`UNION` / `UNION ALL`)和水平合并(连接查询)。垂直合并的应用场景是:我在百度搜一个关键字"美食",结果列表里第一个可能来自网站推荐,第二个来自视频资源,第三个是图片资源,最后一个是百度百科。现实里这些资源存在不同的库里、不同的表里,不可能塞进同一张表,但我一搜就把它们变成**一个结果列表**返回了,靠的就是 `UNION` 或者 `UNION ALL`。

水平合并的例子更常见:我们为了防数据冗余,把员工信息和部门信息拆成了员工表和部门表。现在有个需求,既要展示员工信息,又要展示员工所属部门的名称信息。这份数据来自两张表,怎么办?就是把两张表**水平连接**,按照数据正确地连起来。所以在开发中,只要是关联展示不同表的数据,绝大部分情况下都是水平合并,连接查询这个语法是必须掌握的。

### 垂直合并:UNION 与 UNION ALL

垂直合并比较简单,是多表查询的一道开胃菜。语法就两个关键字:`UNION` 和 `UNION ALL`。

#### 两个关键字差在哪

`UNION` 会**去掉重复行**。什么叫重复行?所有数据都重复,那最终它会去重。

`UNION ALL` **不会去掉重复行**,不管你重不重复,原样合并。

| 关键字 | 重复行怎么处理 | 下面这个例子跑出来的行数 |
| --- | :---: | ---: |
| `UNION` | 相同行只保留一份 | 3 行 + 3 行 → **4 行** |
| `UNION ALL` | 相同行原样保留 | 3 行 + 3 行 → **6 行** |

示例里 A 表是 `1/AA、2/BB、3/CC`,B 表是 `4/AA、2/BB、3/CC`。`2/BB` 和 `3/CC` 这两行在两个结果集里一模一样,所以 `UNION` 会把它们各去掉一份,3 + 3 变成 4。

#### 三条注意事项

**第一,合并的两个结果集之间,列数和类型一定要一一对应。**你上面是三列,下面三列;上面第一个是字符串,下面也得是字符串。不然它怎么对到一起?

**第二,它不要求两个表或两个结果集之间存在主外键关系。**因为垂直合并不涉及行与行之间的关联。什么驴唇不对马嘴都能合到一块儿去,只要列数和类型对应上就行。

**第三,什么叫"重复数据"?**认定是**一行中的所有列值都重复**才算重复行。上面三列、下面三列,其中只有两列重复的,不算;三列全重复了,`UNION` 才会给你去掉。

#### 什么时候用得上

**合并多个相似的表。**比如一个电子商务网站,不同的数据库里存着不同类型的商品信息,电子产品、服饰、家居各存各的表,每种商品类别一张表。最终在网站首页展示的时候,你总不能摆三个列表吧?那就从电子产品表查一个结果,服装表查一个,家居表查一个,最后用 `UNION` 或 `UNION ALL` 按业务需求合并成一个结果集,完事。

**统计不同数据源的数据。**一个网站的用户数据可能来自注册页面,也可能来自访问日志,最后合并展示,同样用 `UNION`、`UNION ALL`。

总结成一句:它主要解决的就是**你想做结果汇总**的时候,来自不同结果集的数据想汇总到一起、一起返回,用这两个关键字就够。

#### 上手合一把

先准备库和表:

```sql
CREATE DATABASE IF NOT EXISTS 07_multi_dql;
USE 07_multi_dql;

CREATE TABLE a (
  a_id   INT,
  a_name VARCHAR(20)
);

CREATE TABLE b (
  b_id   INT,
  b_name VARCHAR(20)
);

INSERT INTO a VALUES (1,'AA'), (2,'BB'), (3,'CC');
INSERT INTO b VALUES (4,'AA'), (2,'BB'), (3,'CC');
```

注意:A 表是 `1/AA、2/BB、3/CC`,B 表是 `4/AA、2/BB、3/CC`。这里面**是有重复数据的**。

去重复合并,写法特别简单,就是先查 A,再查 B,中间把分号打开,加个 `UNION` 就行了:

```sql
SELECT a_id, a_name FROM a
UNION
SELECT b_id, b_name FROM b;
```

谁在上、谁在下都无所谓,**在上的那个结果集,最后会成为虚拟表的列名**。执行完你会得到四条:

```text
┌──────┬────────┐
│ 来源 │ a_name │      上面 3 行来自 A 表，下面 3 行来自 B 表
├──────┼────────┤      列名以在上的结果集（A）为准
│ A    │ AA     │
│ A    │ BB     │      UNION      → BB、CC 跟下面重复，去掉 → 4 行
│ A    │ CC     │      UNION ALL  → 原样全摞上          → 6 行
├──────┼────────┤
│ B    │ AA     │
│ B    │ BB     │
│ B    │ CC     │
└──────┴────────┘
```

BB 和 CC 这两行重复被去掉了,所以是 4 条。要是不去重复,连着写三遍查询,中间都用 `UNION ALL`:

```sql
SELECT a_id, a_name FROM a
UNION ALL
SELECT b_id, b_name FROM b
UNION ALL
SELECT b_id, b_name FROM b;
```

3 × 3 = **9 条**。这就是最朴素的垂直合并语法,加个关键字一连就完事。

### 水平连接查询:唯一的门槛是主外键

垂直合并简单到近乎送分,所以我们真正的正菜在这儿:水平连接查询。

先回顾效果:两个或者多个表,利用水平合并语法把数据水平合并。这跟垂直合并最大的区别是,**两个表的行数据会产生关联**,所以它有硬要求——**两个表必须存在关系,才能进行水平合并**,也就是必须得有主外键。

#### 为什么一定得有主外键

这里边有两条要点,你把这两条捏住了,连接查询这一块就通了一半。

**第一,连接查询的本质是抓"两个表的主外键相等"这个条件。**你说"我这有条数据,她那也有条数据",怎么保证这两条能连成一行?最终它抓的就是主外键相等。就这一条。

**第二,如果不加这个判定条件会怎样?**后面我会讲得更细,先给你个预告:不加的话,数据库会把两个表的所有数据用**笛卡尔积**的方式全部合并一遍,里面肯定有错数据,最后正是靠"主外键相等"这个条件才能恢复出正确的数据。所以为了保证连接正确,所有的连接语法都会去判定主外键相等。

水平合并的语法大致分三大类:**内连接、外连接、自然连接**。现在先大致知道就行,你记不住也正常,而且这三种语法虽然名字唬人,本质差距并不特别大。

#### 连接查询是拆表逼出来的

我们为什么要学连接查询?原因很简单,它是**拆表的一个产物**。

关系型数据库讲究的就是:所有数据都按照类别存在对应的表里,表与表之间通过主外键产生关联,存储是**分表存储**。但你想,展示的时候很多时候是要**联合展示**的——员工名字要、员工部门名称也要。怎么联合展示?就得用水平连接语法,把它们查询到同一个结果中,水平拼接在一起,最终返回给前端。

至于那三种语法,你完全不用迷茫、害怕,只要掌握**内连接和外连接的区别**就行了,其余的基本都差不多。

### 内连接:两种写法,一个都不能少

内连接的定位,一句话就能说清:它就是一种将多个表水平连接到一起的语法。它相对外连接来说,主要的特点是**要求两个被合并的表之间必须存在主外键相等的条件,才能进行合并**。

这句话你现在记不住没关系,等讲完外连接我对比着再强调一遍。这里先把两种语法记住。

#### 标准语法:INNER JOIN 配 ON

```sql
SELECT 列
FROM 表1 AS 别名
INNER JOIN 表2 AS 别名
  ON 表1别名.主键 = 表2别名.外键;
```

拆开看。`SELECT ... FROM` 就是老熟人,从哪个表查、查哪列,都跟单表一模一样;表 1 后面用 `INNER JOIN` 接上表 2,`INNER` 是"内"、`JOIN` 是"连接",合起来就是把两个表的结果水平连到一起。

`INNER` 可以省略——课件上它加方括号,意思是**你写的时候可以不写**,但**写的时候不要加方括号**,这两个坑别踩。

还有一点,光有 `JOIN` 还不够。它只是把两个表的所有行全部拼接一次,就是一个**笛卡尔积**的问题,把内部的所有组合都排了一遍,数据不一定对。要保证数据对,就得在 `INNER JOIN` 后面加一个 `ON` 条件,`ON` 后面跟的正是"两个表中主外键相等"这一句,取到正确的拼接行,完事。

> **提示**:`ON` 只能跟在 `JOIN` 这种关键字后面,它后面一般就是主外键相等。

还有个细节你可能已经注意到了:标准语法里我们写列名的时候,写的不是光秃秃的列名,而是**`表名.列名`**。为什么?因为现在查的数据来自两张表,而一般情况下两张表的主外键命名都相同。你不写表名直接写列名,MySQL 根本不知道你判定的是哪张表的列。所以在多表查询时,对列的操作一般都要用 `表名.` 来指明这个列具体属于哪张表,防止重名的时候说不清楚。

#### 非标准语法:逗号加 WHERE

```sql
SELECT 列
FROM 表1 别名, 表2 别名
WHERE 表1别名.主键 = 表2别名.外键;
```

这个更像 MySQL 的一个**方言**:在 MySQL 里支持,在其他数据库里不支持。打个比方,你就当它是你老家的方言——你在老家跟人聊天的时候很少说普通话,说方言,因为更顺嘴。所以非标准语法在 MySQL 里写起来更顺手,而标准语法更通用。

用法特别简单:第一个表起,第二个表起,后面跟 `SELECT * FROM` 一样,只不过单表的时候写一个表名,多表的时候**用逗号隔开再加一个表**。要是有第三张表,再加逗号加表,第四张也一样。条件呢?`JOIN` 后面加 `ON`,普通非标准语法就是在 `WHERE` 后面正常写主外键相等,否则你拿到的也是错误数据。

#### 三个必须记住的细节

**第一,两种语法在 MySQL 里效果完全一致,但我们推荐使用标准语法。**非标准语法可以拿来理解原理,但真正写代码用标准的那一套,毕竟它在哪都支持。

**第二,为了避免错误的数据行连接,我们必须添加主外键相等的条件。**所有的连接查询,后面都要加主外键相等。这话为什么这么重要?咱们把机理说透。

所谓连接查询,表 1、表 2 本质上就是**把所有行互相都拼接一次**,这个问题就叫**笛卡尔积**。它只保证"里面一定有正确数据",但**一定也混着错误数据**。举个例子:A 表有 3 条,B 表有 4 条,连接完之后得到多少条?**12 条**,它全给你合并一遍。

它有点像小时候数学课上那个九九乘法表、加法表,把两个数字、九个数字之间的加减全给你拼到一起,最后你想要哪个都能找得到。连接查询也是一样,它会把两个表中的所有行数据都拼到一起,你要的那个肯定在里面。但**有些行不是它俩该连到一起的,也被连上了**,这就是经典的**笛卡尔积(笛卡尔乘积)问题**。

怎么解决?加上主外键相等。拼接的时候,只有主外键相等的那几条才是正确数据。所以用 `JOIN` 就在 `ON` 后面加,用非标准语法就在 `WHERE` 后面加。

**第三,多表查询要处理同名列的问题。**单表的时候你写列名随便写没问题,多表就不行了。前面 `SELECT` 的位置、后面指定条件的位置,都不能随便写列名。万一这个列名它要重呢?比如你在查的时候这个位置搞了一个 `name`,那 `name` 在表 1、表 2 里可能都存在,MySQL 就会报错:不知道这个 `name` 到底是谁的。

解决办法很简单:多表操作时,对列的操作都写**`表名.列名`**,防止不确定它是哪张表的列。当然,列名你也能直接写,但前提是**你保证这个列名不是重复的列名**;保证不了,老老实实写 `表名.列名`。

但这又带出一个新麻烦:表名一般都很长,每次写它很麻烦。怎么办?**表也起别名啊。**表起别名的语法有两种:

```sql
FROM   employee e          -- 表名 空格 别名
FROM   employee AS e       -- 表名 AS 别名
```

比如之前用的员工表 `t_employee`,后面给它 `AS` 个名字,叫个 `e` 就行。起完别名之后,列就写成**`别名.列名`**,是不是方便多了?所以我们在多表操作的时候,**一般都会给表起别名**,就是为了用短别名带出列名。

最后再把内连接总结一遍:内连接可以把多个表的数据行**正确地水平拼接到一个结果集**中,比如查询"学生和学生对应的分数",那就是水平拼接。它还有一个特点——**内连接查询到的结果,要求两个表中必须存在相同的主外键**,这一点等讲完外连接我们再强调一遍。

具体的演示和实战留到下一节,这几条语法先记牢。

### 本讲提到的题目

#### 题目

在生活中举出三个案例,三对实体分别构成**一对一、一对多、多对多**的关系。

#### 解析与答案

判断的唯一标准还是那两句:先看两张表之间**有没有主外键**,再看这个外键**能不能重复**。

**一对一**——**员工与员工的唯一档案**。员工表里是姓名、年龄、性别,档案表里是地址、级别,档案表的外键指向员工表主键,而且这个外键加了 `UNIQUE`,至多命中一行。生活里的等价例子是 **QQ / 微信的基本信息与详细信息**:点开就能看到的是基本信息,再点进去才是详细信息,它们存了多张表,关系是一对一。之所以要拆,是因为**冷热数据分离**,想查热数据就只查小的那张表,查询效率才高。

**一对多**——**作者与文章**。一个作者能写多篇文章,每篇文章只对应一个作者,文章表里的外键把同一个作者主键引用了多遍,压根没加唯一约束。换成工作场景就是**员工与部门**:为了防冗余把员工表和部门表拆开,`S1001` 这个员工的部门 ID 引用的是 `D1001`,同一个部门可以命中很多个员工。这就是一对多存在的意义——**一个实体有多个子元素,就该拆表**,既解决冗余,又提高操作效率。

**多对多**——**学生与课程**。一个学生选多门课,一门课被多个学生选,两边都是"对多"。这个例子里外键在学生表和课程表里**都放不下**,所以必须额外建一张**中间表** `sc`,它挂两个外键(`s_id`、`c_id`),而且两个外键都不能加唯一约束。`sc` 里的一行,就是"某个学生选了某门课"这一件事本身。多对多在查询时也最麻烦:它天然就是**三张表的查询**,学生关联中间表,再通过中间表关联课程表。

> **结论**:三个案例的分野全在外键上。一对一 = 外键唯一(加 `UNIQUE` 或直接当主键);一对多 = 外键可重复,子表另设主键;多对多 = 外键无处安放,必须由中间表间接撑起来。判断的时候,把外键的约束情况看一眼,答案就出来了。

## 多表连接实战：内连接、外连接与自然连接
> 对应块：BLK16 | 覆盖分集：P78-P83 | 块标题（分集名）：《78-数据库多表查询篇-内连接双表实战》

介绍完内连接的查询语法和特点，接下来我们具体做个实战。

动手之前先把料备齐——三张表，五个场景。从双表内连接一路练到三表，再从内连接走到外连接，最后看一眼自然连接这个"省事但不稳妥"的写法。中间我还提前埋了一个小问题，等到外连接那一节再拆开。

### 先把三张表备好

我们准备三张表用于查询：一张部门表，一张岗位表，还有一张员工表。

部门表三个字段——部门的编号 `did`、名称 `dname`，以及简介；岗位表三个字段——岗位编号 `jid`、名称 `jname`，以及简介；员工表里是员工的基本信息。关键的地方在于：员工表里面引用了岗位，在下方又引用了部门。也就是说，员工表相对来说是子表，这里边存在两个外键，分别引用了岗位和部门相关的信息。

```text
        t_department                t_job
        部门表 6条                  岗位表 12条
        did  ← 主键                jid  ← 主键
        dname                     jname
        描述                       描述
        ▲                          ▲
        │                          │
   t_emp.did(外键)           t_emp.job_id(外键)
        │                          │
        └──────────┬─────────────┘
                   ▼
              t_emp  员工表(子表, 27条)
              eid / ename / did / job_id
```

读图：两条箭头都从 `t_emp` 出发——员工表通过 `did` 指向部门表、通过 `job_id` 指向岗位表。所以 `t_emp` 是子表，`t_department` 和 `t_job` 是主表，我们一会儿要做多表查询，找的就是这两条主外键关系。

表结构和数据在下发的资料里，打开 `07_DQL_多表` 这个 SQL 文件就能看到，在第三个模块中。第一个是部门表，`did`、`dname` 以及描述，一共 6 条部门数据；第二个是岗位表，`jid`、`jname` 以及它的描述，一共 12 条；最后是员工表，员工有 `eid`，通过 `job_id` 以及 `did` 来引用岗位和部门相关的编号，一共 27 条。

部门 6 条，岗位 12 条，员工 27 条。三个数字先记住，等会儿算笛卡尔积要用。

```sql
-- t_department：部门表
CREATE TABLE t_department (
    did     INT PRIMARY KEY,
    dname   VARCHAR(20),
    descr   VARCHAR(100)
);

-- t_job：岗位表
CREATE TABLE t_job (
    jid     INT PRIMARY KEY,
    jname   VARCHAR(20),
    descr   VARCHAR(100)
);

-- t_emp：员工表，两个外键分别指向岗位和部门
CREATE TABLE t_emp (
    eid     INT PRIMARY KEY,
    ename   VARCHAR(20),
    job_id  INT,
    did     INT,
    FOREIGN KEY (job_id) REFERENCES t_job(jid),
    FOREIGN KEY (did)    REFERENCES t_department(did)
);
```

大家把这几张表执行一下。数据准备好以后，我们在下方做查询练习，一共五个场景。

### 先别写条件，看看连接到底干了什么

我们先看第一个场景：演示基本查询语法，以及演示笛卡尔积的问题。这次我们故意不添加主外键相等条件，专门演示连接查询的实现原理——它到底是怎样实现的。

看需求：**查询员工的编号、姓名，以及所处的部门编号和部门名称。**

在分析表查询结果的时候大家会发现，前面的员工编号以及部门编号，其实在员工单张表中就可以拿到，编号、姓名以及部门编号都是有的。但是这次多要了一个部门名称，这在员工表里就没有了。部门名称就在我们的部门表中，也就是 `dname`。

想要在一条结果中展示两个表中的数据，这很明显就要做多表查询了。而且这次应该做的是**水平多表查询**——把两张表拼到一行。

做水平多表查询之前，一定要分析一下它们有没有关系。答案是有的：两张表中存在主外键，`did` 是部门表的主键，而在员工表中的 `did` 是外键，那我们就可以做到这个事情。

具体怎么写，我们分两种语法。

第一种是标准语法：

```text
表1 别名 inner join 表2 别名 on 主外键相等
```

其中 `inner` 可以省略。

第二种是非标准语法：

```text
from 表1 别名, 表2 别名 where 主外键相等
```

也就是把 `inner join` 换成逗号，把 `on` 变成 `where`。

我们一一进行展示。首先写标准语法，先不加主外键，先不加 `on` 条件：

```sql
select
    e.eid,
    e.ename,
    e.did
from t_emp e
inner join t_department d;
```

先看连接语法是怎么实现的，就是把所有的行都拼接到一起。如果写成 `select *` 执行一下，前面到 `did` 为止都是员工的信息，后边一行中已经把部门拼接到一起了。所以取的时候，可以这样写：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e
inner join t_department d;
```

这样就相当于把每行中想要的列筛选出来了。

但这个数据到底对不对呢？我们把 `d.did` 也查一下：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.did,
    d.dname
from t_emp e
inner join t_department d;
```

执行后大家会发现这个数据并不对。孙洪亮是一号部门的，但一号部门是研发部，不是财务部；可是结果里面也有财务部，这是为什么呢？

这就是我们说的一个经典问题。我们所谓的连接查询，就是将所有的行都拼接一遍，拼接成一张单表。现在没有做筛选，所以如果要筛选就要加主外键。大家理解完以后，这叫做**笛卡尔积原理**——但它同时也是连接查询的原理：把所有可能都拼接一遍，里面肯定有对的，也一定会有错的。

是不是都拼接了一遍？我们可以算一下，通过聚合函数查询总条数：

```sql
select count(1)
from t_emp e
inner join t_department d;
```

员工一共有 27 条数据，部门一共有 6 条，结果应该等于 $6 \times 27 = 162$ 条数据。执行一下，结果确实是 162。

> **结论**：所谓的连接查询就是全都拼接一遍，这就产生了笛卡尔积。行数 = 左表行数 × 右表行数。

接下来我们再用非标准语法实现一遍，非常简单：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e, t_department d;
```

只需要把 `from` 后的 `inner join` 去掉，两张表加逗号隔开即可。它用的底层原理也是内连接，全连接一遍，执行也能查出同样的结果。

| | 标准语法 | 非标准语法 |
|---|---|---|
| 表怎么拼 | `表1 别名 inner join 表2 别名` | `from 表1 别名, 表2 别名` |
| 主外键相等写在哪 | `on e.did = d.did` | `where e.did = d.did` |
| 额外条件写在哪 | `where` 后面 | 继续用 `and` 接在 `where` 后面 |
| 底层原理 | 全连接一遍 | 全连接一遍 |

这是第一种，我们演示了语法的基本使用，但现在存在一个问题，就是笛卡尔积。

### 主外键相等，是唯一的正确条件

怎么能去掉这个问题，拿到正确的数据呢？其实大家通过数据看一下就知道了。

孙洪亮不是财务部的，排除掉；孙洪亮是研发部的，保留。孙洪亮也不是测试部、市场部、后勤部、人事部。何进不是财务部的，排除掉；何进是研发部的，保留。再往下看，黄西蒙是市场部的。

到底什么样的数据是对的呢？在笛卡尔积全都拼接一遍之后，对的数据的特点非常明显——那就是**主外键相等的记录**。

> **结论**：条件唯一，就是主外键相等才是正确的连接数据。这 6 个部门就是研发部、市场部、后勤部、人事部、测试部、财务部。

如果想要获取正确的数据该怎么办？我们来看第二种写法。

用标准写法，在后边加一个 `on` 即可。`on` 就是连接查询放主外键相等的关键字，用来筛选笛卡尔积：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e
inner join t_department d
on e.did = d.did;
```

加上主外键相等，就能拿到正确的数据了。执行看一下，这次拿到的就是正确的数据。

如果用非标准语法怎么写？非标准语法不用加 `on`，直接加 `where` 就行了：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e, t_department d
where e.did = d.did;
```

这样就搞定了。

做个小总结：如果想获取正确数据，需要添加主外键相等条件，这是唯一的要求。只要用连接查询，至少要加这个要求——`join` 这种标准语法在 `on` 后面添加主外键，`表1, 表2` 这种非标准语法在 `where` 后面添加主外键相等。加上主外键以后才能保证连接正确。

至于 `on` 后面能不能加其他条件，其实能加。但是当前阶段大家只要记住 `on` 后面加主外键就行，加其他条件的情况等讲到项目实战时再去介绍。

### `inner` 能省，额外条件照常加

第三、第四个场景放在一起讲。

先看第三个：`inner join` 优化的概念。其实也很简单，标准语法中的 `inner` 是可以省略的：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e
join t_department d
on e.did = d.did;
```

这也相当于内连接，结果是一样的。也就是说，`inner join` 等同于 `join`，它们都属于内连接，`inner` 是可以省略的。

看第四个场景：如果想加一些额外条件该怎么办？

现在我们是查所有员工，如果有个需求是查询编号大于 10 的员工所处的部门编号以及部门名称，这就多了一个额外条件。如果有条件，直接正常添加就行。

非标准语法中有 `where`，在 `where` 后面已经加了一个条件，可以再接一个条件：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e, t_department d
where e.did = d.did
  and e.eid > 10;
```

主外键相等和我们的筛选条件之间是 `and` 的关系：既要满足主外键相等，又要满足员工编号大于 10。

如果用标准语法，也是可以加 `where` 的：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname
from t_emp e
join t_department d
on e.did = d.did
where e.eid > 10;
```

执行查询，结果就是从编号大于 10 的员工开始了。

总结一下：如果有额外的条件，即非主外键相等条件，两种语法都正常添加 `where` 即可。**多表查询就是先把表结果进行拼接，最后依然正常使用查询语法。** 拼接完了以后，分组、分页这些高级查询的活儿一样照干不误。

### 三张表怎么连：多表查询是个伪命题

接下来介绍第五种场景，多表之间的查询。刚才只讲了两表之间的查询，那如果是多张表呢？

其实只要讲到三张表就够了。需求是：**查询编号大于 10 的员工的员工编号、姓名、所处的部门编号以及对应的岗位编号和岗位名称。**

员工表里面的信息我们知道，部门表的信息也知道，现在还要连接岗位表，这三张表要连在一起进行展示。这里需要明确一点：**岗位跟部门没有直接关系，岗位也是跟员工关联的。** 所以这个查询要做的事情，就是查员工和部门，以及员工和岗位，把它们的结果都拼到一起。

多表查询其实是一个伪命题——所谓的多表查询，本质上就是多个两表查询。两张表就是一个两表查询；三张表，其实就是两个两表查询。每次在写连接查询的时候，只需要关注当下的表关系即可：关联下一张表是谁，下一张表关联的又是谁，无限往后写就行了。

先写前边已经掌握的部分：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.did,
    d.dname,
    e.job_id
from t_emp e
inner join t_department d
on e.did = d.did;
```

这一步查询查出了两张表的关系。两张表执行完后，相当于产生了一张虚拟表。如果还想要岗位名称，继续连接即可。写完一套 `inner join ... on` 以后，在后边继续添加 `inner join`，其中 `inner` 可以省略：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname,
    e.job_id,
    j.jname
from t_emp e
inner join t_department d
on e.did = d.did
inner join t_job j
on e.job_id = j.jid;
```

这里边的 `job_id` 是来自于员工表 `e`，它是外键；岗位表 `t_job` 别名为 `j`，它的主键是 `jid`。这样就完成了三张表的查询。

如果还需要加条件，在最后加上 `where` 即可：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname,
    e.job_id,
    j.jname
from t_emp e
inner join t_department d
on e.did = d.did
inner join t_job j
on e.job_id = j.jid
where e.eid > 10;
```

执行后就查出来了。如果是四张表，就继续 `inner join`；五张表也是继续 `inner join`。写完以后如果有额外条件，最后该加 `where` 加 `where`。

如果用非标准语法怎么写？那就更简单了：

```sql
select
    e.eid,
    e.ename,
    e.did,
    d.dname,
    e.job_id,
    j.jname
from t_emp e, t_department d, t_job j
where e.did = d.did
  and e.job_id = j.jid
  and e.eid > 10;
```

在 `from` 后面把表一、表二、表三用逗号隔开列出来。在 `where` 后面，首先把两对主外键相等条件用 `and` 连接好，如果有其他条件，继续使用 `and` 追加。

我们来做个总结。有三张表，至少有两对主外键相等条件，中间是 `and` 的关系；如果有 $N$ 张表，至少有 $N-1$ 对主外键相等条件。语法结构是：

```text
-- 标准语法
表1 join 表2 on 主外键1 join 表3 on 主外键2 ... where 其他条件

-- 非标准语法
from 表1, 表2, 表3 ... where 主外键1 and 主外键2 ... and 其他条件
```

掌握了规律以后，多表查询非常简单。

### 内连接查不到的那个人

在这部分内容结束之前，提前预告一个下节讲外连接时的小问题。回到最简单的两表查询：

```sql
select *
from t_emp e
inner join t_department d
on e.did = d.did;
```

这是查询所有员工及其关联的部门信息。我们一共有 27 个员工，但其中有一个叫周芷若的第 27 号员工，她的 `did` 为空，代表她没有部门。我们用内连接查的时候介绍过，它要求双方必须都具备主外键对应关系才能查到。执行查询后会发现，从 1 号查到了李红，确实没有查到周芷若。

> **定义**：内连接查询的结果要求两个表中必须都存在主外键匹配才能查到。如果用内连接查，现在是没有周芷若这条数据的。

这就是内连接的特点以及相关语法。

### 外连接：用 LEFT 和 RIGHT 指定逻辑主表

介绍完内连接以后，接下来我们介绍外连接。只要把内连接搞懂了，外连接基本也能拿下。

外连接和内连接有什么区别呢？用白话来说，刚才我们发现查数据的时候没有周芷若的数据，因为她没有部门，所以没有查到；而如果用外连接的话，就可以查到周芷若的数据。说白了，区别就在于**能不能把没有对应部门的周芷若给查出来**。

那么我们来看看，到底啥是外连接？

外连接是一种多表查询的一种方式，这不用说了。与内连接不同的是，外连接会返回所有符合的行——也就是说，外连接会返回两个表中主外键相等的行，同时也会返回未匹配的行。这个所谓未匹配，指的就是你可以指定一个表为逻辑主表，那就算这个表没有被引用或者没有外键，它也会全部返回。

最终外连接分为左外和右外。这个左和右，指的就是指定左侧和右侧哪个表为逻辑主表。刚才我们说有一个员工还有一个部门，我想要查到员工里面的周芷若怎么办？你就可以通过方向指定员工表为逻辑主表，那最终的结果它就会查到员工的信息；而部门的位置没有，怎么办？它就会置空。

语法大家听我说，第一个就是这个位置，它只不过多了一个 `LEFT` 或者 `RIGHT`。它没有非标准语法，它都是标准语法。在输出外连接的时候，它后面多了一个叫 `OUTER`——之前是不是叫 `INNER` 啊？那这个 `OUTER` 是可以省略的。也就是说 `LEFT OUTER JOIN`、`LEFT JOIN`、`RIGHT JOIN` 都是外连接，而直接写 `INNER JOIN` 或者 `JOIN` 就是内连接，剩下其他都一样。

> **结论**：`LEFT` 和 `RIGHT` 是用来指定哪个是逻辑主表的。如果 `LEFT`，左边那个就是逻辑主表；如果 `RIGHT`，右边那个就是逻辑主表。

之后我们来说说细节。第一个细节就是内外连接的区别：内连接只有满足匹配条件的行数才会返回，也就是说两个表中必须存在主外键值、且这个值相等才会返回——它得判定主外键值相等且两值都得有才能返回。而外连接可以通过左右来指定一个表为逻辑主表，逻辑主表的数据一定会查到，那就算它没有外键或者没有被引用，我也能够查到。

第二个细节，内外连接的语法都可以优化：外连接可以省略 `OUTER`，内连接可以省略 `INNER`。外连接写 `RIGHT OUTER JOIN` 其实跟 `LEFT JOIN`、`RIGHT JOIN` 效果是一样的；而如果单纯只写一个 `JOIN`，那就是内连接。大家前期容易弄混的就是区分不好内外连接，记住：**只写一个 `JOIN` 就是内连接，加上 `RIGHT` 和 `LEFT` 就是外连接。**

| | 内连接 | 外连接 |
|---|---|---|
| 关键字 | `JOIN` / `INNER JOIN` | `LEFT JOIN` / `RIGHT JOIN`（`OUTER` 可省） |
| 判定规则 | 公平的：两边主外键都得有且相等 | 不公平的：可指定一张逻辑主表，它的数据一定全返回 |
| 对方没有外键的行 | 查不到 | 逻辑主表那侧的行照样查出来，另一侧置空 |
| 能省的写法 | `INNER` 可省 | `OUTER` 可省 |
| 加不加分隔条件 | 建议加，不加就出笛卡尔积 | **必须**加，不加直接语法报错 |

### 逻辑主表放第一位，后面全是左外连接

第三个细节是连接的连续性，这算是一个小技巧，提前给大家说。

只要在开发中一旦你写了 `join`，找到一个逻辑主表，建议大家把这个逻辑主表放在第一位。既然它为逻辑主表，它就是第一个——第一个用左外连接，是不是以它为主啊？而后续你都不用思考了，后续全都是左外连接。

大家思考个问题：第一个为逻辑主表，跟第二个表查出这个数据，如果剩下你变成了右外连接或者内连接，那相当于第一个左外连接是不是就没有意义了？

> **结论**：开发中是有规律的，一旦选择了左外连接，后续全是左外连接，也都不用思考，没有什么内外连接混合用的这种思维或这种场景。

### 该用内连接还是外连接：两个需求

说完以后大家也可能不太理解内外连接的区别，我们来看一个场景，给大家演示一下。首先思考一下，以下两种需求到底是用内连接还是用外连接？

**第一个需求：展示有员工和员工的岗位信息。**

它们分别来自于两个表。但是这里边听我说，我们员工有些可能是新入职，还没有给他分配岗位。那我们无非就是拿员工表去连接岗位表做连表查询——是用内连接查还是外连接查呢？大家可以在公屏上互动一下。

假如说用内连接，第一个用户他没有分配岗位。记住，那这个用户数据在结果中就查不到，你只能查到管理员这个账号以及管理员对应的这个岗位信息。因为内连接你如果对方的引用为空，它是拿不到的，展示的时候那只会有一个管理员这一个数据。内连接会出现这个场景。

但如果用外连接就不同了。外连接就算我把用户表指定为逻辑主表，那就算他没有岗位，那它也会查到用户和岗位数据，只不过岗位数据这个位置为什么呢？为空。但是我们可以跟前端约定一下：如果你发现岗位为空的话，那你给它写个啥？未分配岗位。给它起个别名、起个别的值就可以了，`IFNULL` 是不是起个值就可以了。

所以这个需求我们用的是外连接，以员工表为逻辑主表做外连接。

**第二个需求：展示费用名和费用值的整合信息。**

这个需求是我们后面要做的一个项目练习——搞一个公寓项目，公寓有一些费用信息，它分两个表：一个是费用名的表，停车费、网费；还有一个费用值的表。名和值用一个正常的连表查询俩一连到一起就行了，但这次是用外连接还是内连接呢？

大家思考问题，如果用内连接会出现什么问题？举个例子，假如说这个值能加也能减，假如说取暖费这个值我现在一个没加呢，是空的——我有取暖费这个项目名的表，但值的表里边没有数据。如果你用内连接去弄，它要求两张表里有主外键、最终匹配上，那最终取暖费你也查不到，展示的时候就不会有取暖费这个信息。

那大家说这会不会有问题啊？如果连取暖费这个项都没有，那后续怎么加值啊？那这不会出现一个特别尴尬的问题吗？就是说我要加取暖费，但是取暖费内连接你查不来，我要加那你得先有值才能查出来，但是你不给我显示出来我怎么能加呀？**这不就形成了一个死循环吗？**

所以这时也依然得用外连接，而且以费用项为逻辑主表去连接对应的费用值。那就算费用项没有费用值，这个位置也依然要显示什么？取暖费。结果写完取暖费以后，这个位置虽然是空的，但是后续有加号你可以动态加值啊。如果用内连接，取暖费都不显示，是不是啊？

那通过这两个说明，大家其实能感受到，你说开发中到底是内连接用的多还是外连接用的多呢？这里边我可以给大家下一个定论：**99.9999%，比黄金还纯，六个 9，一般用的都是外连接比较多。**

原因就是开发中有很多表都是逻辑主表的，就算没有被引用数据它也应该去展示。所以最终我们下个总结：其实在开发中绝大部分情况都是有逻辑主表的，而存在逻辑主表就要使用外连接，所以说外连接的登场率会比内连接稍微会更高一点。

好，这就是我们总结的所谓外连接的常用语法。我们先不做它的练习，先把语法总结出来：

```text
表1 别名 LEFT|RIGHT OUTER JOIN 表2 别名 ON 主外键相等
```

它的连接作用和效果和内连接一致，不同点就是这个所谓的外连接可以通过 `LEFT` 或者 `RIGHT` 来指定一个为逻辑主表，逻辑主表的数据一定会显示全。大家想要都显示全就可以用外连接。

几个注意事项收个尾：第一，还是效果问题，内连接必须存在主外键且主外键相等才会查到，而外连接可以指定一个逻辑主表，它一定会显示全。第二，外连接的 `OUTER` 可以省略，`LEFT JOIN` 等同于 `LEFT OUTER JOIN`；区分内外连接更简单，只要有 `LEFT`、`RIGHT` 就是外连接，没有就是内连接。第三，如果有逻辑主表，就将逻辑主表放在第一位，放在第一位以后它一定是外连接，而且后续一定都是左外连接，`LEFT JOIN`、`LEFT JOIN`，你就不用琢磨了，这是固定的规律。

### 三张表外连接实战

讲完外连接的概念以后，我们通过几个场景也来讲讲外连接的细节。第一个场景，查询员工的编号、姓名以及所属的岗位编号和岗位名称，展示一下笛卡尔积的问题——不过在外连接里，外连接它不能出现笛卡尔积的问题，但咱们可以试一下。

需求是查询**所有员工**。听我说，它有一个要求是所有员工——他想要谁呢？他是想要周芷若的，所有员工包含谁？包括这个周芷若。周芷若没有部门，你也得给人家查出来。那这时候大家注意，我们得用外连接，以谁为主？以员工表为主。

那写法就是先写个星号：

```sql
SELECT *
FROM t_emp e
LEFT JOIN t_department d
```

那假如说我不写 `ON` 看行不行？大家发现是不是语法报错呀？

> **易错点**：外连接必须添加主外键相等条件。你不加它直接报错，报一个错误代码 1064，代表语法有问题。

所以这个位置写的时候你必须得怎么写呢？一样：

```sql
ON e.did = d.did
```

好，这样呢就查到我们所有数据了。我就没有指定列啊，查的是所有列。大家发现，最终咱们主要看后边——周芷若是不是也查到了？只不过她的部门没有。

那如果我写 `e.eid`、`e.ename`，之后 `d.dname` 这几列，最后一查，大家可能会发现周芷若最终是为空啊，因为你是以她为逻辑主表，就算没有对应的引用或者没有对方的引用也能查到。这就是外连接和内连接的主要区别，就差周芷若。

那之后说没有怎么办呢？你可以用我们之前讲过的一个函数叫 `IFNULL`，如果为空咱们可以说一个"暂时未分配"，配上 `IFNULL` 就行了。

下边展示是不是"未分配"啊？就可以了。

那啥时候用右外连接呢？很简单。你想一个问题，这个位置假如我放在了后边——好，我第一个放的是部门表，现在放的是员工表，但是呢你不管放在哪个位置，是不是员工表还是逻辑主表？你要周芷若啊。那这时候大家想个问题，如果你这块用的是左外连接，你能不能查到周芷若呢？

答案是查不到的，因为部门里面是没有周芷若对应的部门信息的，她没有引用部门。所以如果你想查到，只能写成右外连接，`RIGHT`。还是依然找到你的逻辑主表，以它为主就可以了。大家一定要记住，`RIGHT` 和 `LEFT` 就是用来指定哪个是逻辑主表的。

第二，正确的查询我们已经演示了。大家注意啊，你不能——就是外连接是必须要加主外键的。加工中有条件怎么办呢？有条件你正常加呗，给它 `ON` 写完以后，有条件你正常加：

```sql
WHERE e.eid > 10
```

是不是这意思啊？执行一下，这样正常就有条件了，还跟之前一样。

接下来，三张表以后怎么办呢？这规律还是和以前一样，但我先教大家一个小技巧：**建议大家先找到这个逻辑主表，把逻辑主表放在第一位，后续都是 `LEFT JOIN`。**

大家想一个问题，假如说我们有个连续性的 $N$ 张表，1、2、3，三张表，就是我关联它，它关联我，我关联它，我是不是要做这个连表查询啊？而最终我发现什么呢？发现第一张表是逻辑主表，就是它的数据一定是存在的，就算后面没有引用它也是存在的。那你用不了内连接，是不是得用外连接？

你把逻辑主表放第一位，就是说假如这是表 1、表 2、表 3、表 4，你这么写：写一个第一，`FROM 表1 LEFT JOIN 表2`，你看，`LEFT` 是不是以它为逻辑主表？后面加 `ON`，主等外。是不是搞定了？这第一搞定了。

那大家思考问题，这两个表查的结果是没问题的。那关联第三张表以后，下边用什么呢？也就是说我查的数据里面可能还是有一行是空关联 2，2 肯定关联不了 3，就你空肯定关联不了 3 了，是吧？那我关联 3 的时候这块能不能用内连接呢？假如我不用外连接，我用内连接 `JOIN 3 ON` 主等外——如果你要是这么做的话，那证明第一个这个连接出的结果，表 1 里面有的数据，在这里边你因为用内连接又是公平法则了，又查不到了。

> **结论**：只要第一个用了左外连接，后续一定都是它，闭眼就写，都是左外连接。3 就是 `LEFT JOIN 3 ON 主 = 外`，4 就是 `LEFT JOIN 4 ON 主 = 外`。

现在我们这个需求就是查询员工编号、部门、岗位。这个东西大家注意，闭眼就写呗。怎么写？大于 10 我们先加上，这正常加是吧？把它先写一个，把逻辑主表放在第一位，粘过来放在第一位；之后把部门表放在第二位，`LEFT JOIN` 是不是搞定了？完毕以后下方我们后续再写啥：

```sql
SELECT
    e.eid,
    e.ename,
    e.did,
    d.dname,
    e.job_id,
    j.jname
FROM t_emp e
LEFT JOIN t_department d
ON e.did = d.did
LEFT JOIN t_job j
ON e.job_id = j.jid
WHERE e.eid > 10;
```

主外相等，就完事了。说后续还是 `LEFT JOIN`，记住了吗？所以只要有逻辑主表，那后续基本都定了。完之后再加个 `j.jname` 就搞定了。

诶？`j` 没起别名——表是不是得起别名啊。表名一定要起别名，不然 `j.jname` 这种写法根本无从下手。

看结果，有人说这个"未分配"为什么这里还有成员呢？因为大家听我说，我们这个表稍微有点奇怪：并不是说我第一个表连接第二个表、第二个表连接第三个表，而是我第一个表同时连接第二个表和第三个表。所以就是我没有部门，但是我有岗位，所以这是能查到的。大家能理解吗？好嘞，这就是外连接怎么用，跟内连接一样，只不过你要理解外连接和内连接的区别是什么。

### 内外连接总账

我们把这个简单做个总结。

**第一点**，内连接、外连接大家在用的时候，它都需要判定主外键相等来去掉笛卡尔积的问题啊，这都是一样的。只不过就是内连接不强制要求，外连接是必须要要求的。

**第二点**，内连接它属于公平的查询法则——双方都得满足主外键相等，才能够拿到这个最终的结果。而外连接就是不公平了，它可以通过一个左和右来指定一方为逻辑主表，就算逻辑主表中没有对方的引用数据，它也会查到全部。

我再给大家说一个场景，举个例子。假如说我们有一个学生表和学生的一个考试分数表，最终我们要两表查询来展示学生以及学生的分数。假如说你用内连接，那就是谁考试了、分数表里面才会有他的分数，他也能查到。举个例子，假如说张三、二狗子那天拉肚子了，没来考试——学生表里面有他，分数表里面没有。那大家想想，一罗列榜的时候，那是不是就没有二狗子这个学生的名字？如果用内连接的话，这样不好。

那这时候怎么办呢？你可以用外连接。如果二狗子没来考试，只不过他查出来以后他的分数为空，空可以写个 `IFNULL` 等于 0，是不是就完事了？

**第三点**，一般情况下呢，外连接的主外键条件加在 `ON` 后边，其他条件我们加在 `WHERE` 后边就可以了。如果有逻辑主表，建议将逻辑主表放在最左侧、第一位，之后后置都可以使用左外连接。

**第四点**，多表联合查询的时候，主外键关联的条件是 $n-1$：你有 100 张表是 99 对主外键相等，有 1 万张表是 9999 对，其实都是两两进行考虑的。

有完多表以后，多表的关键字顺序怎么写呢？我这边虽然没给大家讲怎么切割、`HAVING`、`GROUP BY` 等等，最终的语法还是一样：之前我们写 `SELECT ... FROM` 完事了，现在只不过后边可以加一些单表——就是加一些这个内连接和外连接的语法。加了以后呢，后边 `WHERE`、`GROUP BY`、`HAVING`、`ORDER BY`、`LIMIT` 这些关键字还按之前的顺序去写就行了。

也就是说，我们刚刚只学的部分，只是在中间这个部分做一下结果集的一个连接。

```text
SELECT  列1, 列2, ...
FROM    表1 别名
        [INNER|LEFT|RIGHT JOIN 表N 别名 ON 主外键相等] ...
WHERE   其他条件
GROUP BY ...
HAVING  ...
ORDER BY ...
LIMIT   ...
```

好，这就是我们的内连接、外连接的一个总结。

### 自然连接：自动匹配同名列的省事写法

接下来我们介绍第三种连接语法，叫自然连接。

自然连接是一种内连接和外连接的一种升级版本。它会自动找到两个表中命名相同的列，并且自动判定——相当于你用这种连接语法，就不用写这个 `ON` 后边主外键相等的这个公式了。

这么一说呢，其实自然连接还是比较靠谱的是吧？但是在开发中，自然连接用的还是比较少。因为它的效果也就是内连接和外连接的同样效果，只不过语法稍微简化一些。但大家思考个问题啊，**你能保证两个表中除了主外键，其他列都不相同吗？** 如果说两表中除了主外键，其他列名还有相同，那它也会自动判定相等，那这样的话数据就会出现错误了。这就是自然连接的特点，既有优势也有缺点。

先看语法。它首先加一个 `NATURAL`，就是自然的意思。`NATURAL JOIN` 代表自然内连接；如果 `NATURAL` 后边加 `LEFT` 或者 `RIGHT`，代表自然外连接。也就是说它能达到内连接和外连接的效果，最终它省了什么？省略了 `ON` 的效果。

> **定义**：自然内连接 `NATURAL JOIN`；自然外连接 `NATURAL LEFT JOIN` / `NATURAL RIGHT JOIN`。作用是达到内外连接的效果，并自动查找主外键相等。

它的要求是：两个表只有主外键命名相同，你就可以用，它是方便的，最终相当于省略了 `ON` 后边的主等外。但是你也得保证一点：**其他的列命名不能相同**，要不这样它数据就会出现错误。

有两个细节需要讨论。

第一，自然连接其实等于外连接加内连接的效果，只不过语法上展示而已。但大家要记住，它不太稳妥——如果其他列命名相同，它也会判定等于，会产生错误数据。

第二，自然连接其实它也可以做一个优化。在写的时候，它也可以在后边加关键字叫 `USING`，在这里边指定叫什么呢？叫主外键列名，而且主外键列名得相同。这样的话它就会判定指定的这个主外键列判定相等，其他相同列就不判定了。但是大家想想这么做是不是也挺麻烦的？那还不如跟写一个 `JOIN` 后边写个 `ON` 写个主外键相等更直观一些。所以我们了解一下自然连接就行了，它并不是一个什么特殊的功能，只是一个语法而已。

接下来我们来用一用。第一，查一下所有部门员工的编号以及部门，就是员工姓名以及部门编号和所谓的部门名称。用内连接查一下：

```sql
SELECT e.eid, e.ename, e.did, d.dname
FROM t_emp e
NATURAL JOIN t_department d;
```

大家注意，这里边省略了什么呢？省略了 `ON`。因为刚好这个表中的 `ON` 后面的主外键命名相同，它会自动查找。结果大家都找到了。

但这个能找到，有一个它是有问题的。大家看，假如说我们再做一个额外练习，这有一个员工表，接下来我想查员工以及员工的职位。大家看，职位表里边的主键叫 `jid`，而员工表里边的外键叫 `job_id`，那这回它就找不到了：

```sql
SELECT e.eid, e.ename, e.job_id, j.jname
FROM t_emp e
NATURAL JOIN t_job j;
```

员工表关联我们的岗位表。大家注意，这个时候就要有问题了——你发现数量一下子涨了这么多，是两张表的行数直接相乘，因为这个时候它虽然省略了 `ON`，但是我的主外键命名不同，它找不到。

> **易错点**：就算你加 `USING` 也不行，它命名不同。所以用 `NATURAL` 这种自然连接的语法，前提是主外键命名必须相同，而且其他列要不同。如果其他列要相同你可以用 `USING` 指定，但是主外键如果要是完全不同，那根本用它也白搭。

接下来用一下自然外连接。这个粘过来以后就是，我现在想查一下周芷若，那就用一个什么？在这个位置加个 `LEFT`，以员工为逻辑主表进行查询就行了。一走，我们来看，周芷若是不是就出来了？就这样。所以这就是我们说的自然连接。

## 自连接与子查询：把一张表用两次，把查询嵌进查询
> 对应块：BLK17 | 覆盖分集：P84-P88 | 块标题（分集名）：《84-数据库多表查询篇-自连接语法》

介绍完自然连接，我们接着讲自连接。开讲之前先给大家强调一点，可能很多人心里第一反应是"自连接是不是又是一套新语法"——**自连接它并不是语法，它只是一种特殊的使用场景**。这一句你记住了，后面所有内容就都通了。

先把账算清楚。到今天为止我们一共讲了三种连接：内连接、外连接、自然连接。这三个听起来是三种语法，但落到效果上其实只有两种，就是内和外两种；自然连接本质上是对它们俩的一层优化和封装。顺便说一句，这封装优化得也一般，只能说省了点手写 `ON` 条件的功夫。

而自连接没有那个"然"字，它不是第四种语法。它说的还是内连接、外连接、自然连接这几句话，只不过换了一个用法的场景。

到这儿，垂直和水平方向的多表查询语法就算讲完了。接下来我们正式进第四章：子查询，也叫嵌套查询。

### 自连接不是新语法，是一张表用多次

自连接指的是：在数据库中，一个表与自身进行数据的一个连接操作。做法是在查询里给同一个表起不同的别名，表示它的两个不同实例，再把这两个实例连接起来。

> **定义**：自连接 = 单张表被多次使用的场景；实现手段依然是内连接、外连接或自然连接。

一句话概括自连接的适用条件：**你要查的那个关联数据，躺在同一张表的其他行里**。

一个表里存在数据的引用关系——同一行里的某一列，引用了这张表里另外某一行。这种时候你就得上自连接。打个最常见的比方：员工表里有员工编号，也有领导编号，而领导编号指向的同样是这张员工表里的某个行。领导也是员工，只不过是另一行。

#### 先看一眼表里真实的引用关系

我们打开员工表，挑三列看：员工的名字、员工的编号、`mid`——也就是这个员工的经理编号。

`mid` 这个值引用的是谁？就在这张表里。

- 孙洪亮的领导是谁？编号是 1，而 1 就是孙洪亮自己。也就是说这个哥们自己的领导是自己，大领导。
- 何金的领导是 1，也就是孙洪亮。同一张表的另一行。
- 邓超远的领导是 7，7 是贾宝玉；贾宝玉的领导又是 1，是孙洪亮。

看出来了吗？表里明明只有一行数据，行与行之间却互相引用起来了。这种场景，就是自连接。

#### 为什么一行不够用

现在对比两个查询，你就明白自连接到底解决什么了。

**第一种：查询员工的编号、姓名、领导编号。** 这不是自连接，这就是一次普普通通的单表查询。因为你要的三样东西，这一行里全都有。

**第二种：查询员工的编号、姓名、领导的编号，以及领导的姓名。** 麻烦就出在这儿了——这一行里只有领导的**编号**，没有领导的**姓名**。

那怎么才能把姓名查出来？只能拿这个编号当条件，再回到员工表里，把它当成一次"员工的编号"再关联一次，把对应行查出来。既然一张表不够用，那就把它用两次。这，就是自连接。

所以判断标准你记这一句就够了：**只要发现你要关联的数据在同一个表里的其他行，用的就是自连接。**

最后提前打个招呼：自连接这种场景，就像你平时学的那些设计模式，什么单例模式、工厂模式——我教了你这个场景具体怎么写，以后不管碰到哪个自连接需求，代码结构都是那一个。是固定化的公式，不用每次重新想。

#### 语法：同一个表，两个名字

我们先看图。正经多表查询你肯定是"表 1 关联表 2"，表 1 是逻辑主表；自连接不一样，是同一张员工表复制出来复用两遍：

- 第一份当**员工表**；
- 第二份当**领导的表**。

```text
   e1  员工表                    e2  员工表（复用一份，当领导的表用）
   eid  ename  mid              eid  ename
    1   孙洪亮   1               1   孙洪亮
    5   陈浩     7  ───────────> 7   贾宝玉
                      ▲
        e1.mid  =  e2.eid
```

正常查表 1 的 `eid`、`ename`，再查表 1 的 `mid`，到这儿就完了。但 `mid` 只有一个编号，领导的具体信息它没有。所以要再关联第二份表，拿 `mid` 去关联表 2 的**员工编号 `eid`**——因为你的领导编号，本质上就是人家作为"员工"的那个编号。

抓住之后，表 2 的 `ename` 就不一样了，它是**领导的姓名**。

> **易错点**：等号的方向千万不能反。必须写 `e1.mid = e2.eid`。要是写成 `e1.eid = e2.mid`，那意思就变成"我的经理等于他的经理"了，这显然不对。正确的说法是：**我的经理编号，等于对面那个人的员工编号**。

给两份表起名：员工那一份叫 `e1`，领导那一份叫 `e2`。语法简单得不像话：

```sql
select *
from t_emp e1
left join t_emp e2
on e1.mid = e2.eid
```

`left join` 是左连接。意思很直白：即使我没领导，也照样把我查出来——表 2 那边匹配不上，`e2` 的列全是 `NULL`，行还是你的行。

要查什么列也顺手定下来：员工 ID 用 `e1.eid`，员工名字用 `e1.ename`，经理 ID 用 `e1.mid`，领导的名字用 `e2.ename`。四列一摆，谁是谁的领导就全清楚了。

后面要加条件就正常加。比如"查询 5 号员工的编号、姓名以及领导的编号、领导姓名"，加个 `where` 就行，注意谁是员工——`e1` 当的是员工，所以是 `e1.eid` 等于 5：

```sql
select e1.eid, e1.ename, e1.mid, e2.ename
from t_emp e1
left join t_emp e2
on e1.mid = e2.eid
where e1.eid = 5;
```

整个自连接说到底就一句话：**抓住主外键哪个相等就行。**

#### 复用多次：查领导的领导

上面是两次复用，已经是一个完整的需求了。但你马上会想到第二个需求：查询 5 号员工的编号、姓名，领导的编号、姓名，以及**领导的领导的编号和姓名**。

同一个表能用两次，就能用三次、用 n 次。图上就是三份：

```text
   e1 员工表                   e2 领导表                    e3 领导的领导表
   eid  ename  mid             eid  ename  mid              eid  ename
    5   陈浩     7   ─────────> 7   贾宝玉    1  ─────────> 1   孙洪亮
                      ▲                      ▲
        e1.mid  =  e2.eid          e2.mid  =  e3.eid
```

连接的思路完全一样，只是链路多接一节：

- `e1.mid = e2.eid`：员工的经理编号，去对上领导那一行的员工编号；
- `e2.mid = e3.eid`：领导自己也有领导，拿领导的 `mid` 再去对上第三份表的员工编号。

要查的列也就顺着链路加：`e1.eid`、`e1.ename`、`e1.mid`，然后 `e2.ename`、`e2.mid`，最后 `e3.ename`——全齐了。

```sql
select e1.eid, e1.ename, e1.mid,
       e2.ename, e2.mid,
       e3.ename
from t_emp e1
left join t_emp e2
on e1.mid = e2.eid
left join t_emp e3
on e2.mid = e3.eid
where e1.eid = 5;
```

跑一下：5 号陈浩的领导是 7 贾宝玉，贾宝玉的领导是 1 孙洪亮。数据对得上。

那要是再往上找一层"员工领导的领导的领导"呢？复用四次就行了，套路一模一样。

> **结论**：自连接不是新语法，是一种"一个表连接自己、实现多表查询"的特殊场景——一个表用多次，查到想要的数据，可以理解为自产自销。判断依据只有一条：数据引用落在同一个表的其他行；实现依据有两条：照样用内/外/自然连接，并且照例给别名。**自连接 ≠ 自然连接，一个是场景，一个是语法，两码事。**

### 子查询：一条语句里嵌一条查询

垂直和水平的多表查询到此讲完，我们开始正式接触子查询。

子查询的定义特别短：**在一个 SQL 语句中，嵌套了另外一个完整的 select 语句。** 语句之间形成嵌套，而被嵌套进去的，是一条 select 语句。

举个最典型的例子：查询大于平均分的信息。

思路是两步——先用一条 select 加 `AVG` 聚合函数算出平均分，再把算出来的东西加个括号，当成条件值去查分数表，比它大就行。因为中间那条 select 被塞进了外层语句里，它就是子查询。

```text
   外层语句：SELECT * FROM t_分数表 WHERE score > ( ... )
                                              │
                                              └── 内层语句（先算）：
                                                  SELECT AVG(score) FROM t_分数表
                                                  —— 返回 1 个值，比如 78.5
   拿这个值回到外层：SELECT * FROM t_分数表 WHERE score > 78.5
```

> **提示**：子查询不只出现在 select 里。任何语句中都可以嵌套——`INSERT`、`UPDATE`、`DELETE` 都行。只要被嵌套进去的内容是一条 select 语句，就称作子查询。比如下面这条 `UPDATE`，就是把 5 号学生的分数改成平均分：

```sql
UPDATE t_学生表
SET score = (SELECT AVG(score) FROM t_学生表)
WHERE id = 5;
```

### 子查询分四类

为了方便记忆，我们把子查询分成四类。先说句实在话：**这个分类有点适得其反，分类以后反倒不好记了**。不过每类都有固定的特点、固定的用法和固定的关键字，尽量记一记。真记不住也没关系，等会儿我们一个一个上手。

| 类别 | 返回结果形状 | 典型用途 | 配套关键字 |
| --- | --- | --- | --- |
| 标量子查询 | 单行单列 | 做判定条件、过滤，或作为表达式里的一个值 | 无，直接当值用 |
| 行子查询 | 一行多列 | 更新、插入数据的值，或整体比较 | `=` 或 `IN`（多列要加括号整体比） |
| 列子查询 | 多行单列 | 条件比较 | `IN` / `NOT IN` / `ANY` / `ALL` |
| 表子查询 | 多行多列 | 一般不做条件，用作连接的虚表 | 正常外连接，记得起别名 |

一句话各归其位：标量子查询是"一个值"，用起来像常量；行子查询是"一行几个值"，只能整体比；列子查询是"一列好几个值"，得靠 `IN`、`ANY`、`ALL` 判；表子查询是"好几行好几列"，没法比大小，只能当表用。

下面我们按顺序把四类挨个练一遍。先在 `SELECT` 里嵌套，这四种场景一个一个实现给你看。

### 标量子查询：一个值，当普通值用

标量子查询就是子查询的结果是**单行单列**，也就是一个单个的值。你查出来的平均分就是一个值，那就是标量子查询。

一般情况下，这个值有三个去处：作为判定条件、作为过滤条件、或者作为 select 列表里的一部分。当它是个条件值的时候，一般一次只加一个额外的条件。

#### 条件位置：查研发部门的所有员工

需求是"查询研发部门的所有的员工信息"。我们把它拆开看：条件是研发部门，查询结果是员工信息。

问题来了——员工表里只有一个部门 `did`，没有部门名称。这个条件你手上根本拿不到。

所以这题明显是子查询。做法就是分成两步：

**第一步**，根据部门名称查部门的 ID：

```sql
SELECT did FROM t_department WHERE dname = '研发部';
```

这条一执行，就能拿到研发部对应的 ID。

**第二步**，根据这个 ID 查对应的员工信息：

```sql
SELECT * FROM t_emp WHERE did = 1;
```

相对而言这就查到了部门 1 的所有员工。但这个 `1` 是写死的，我们要让它由上面的查询结果带出来。于是回到第一步那条语句，加个括号——**括号就代表内部要先执行一个查询**，把第一步整条粘进来，注意别把分号也粘上：

```sql
SELECT *
FROM t_emp
WHERE did = (
    SELECT did
    FROM t_department
    WHERE dname = '研发部'
);
```

最终它会先执行括号里的，拿到 `did` 这一个值，再拿这个单值当条件，和外层的 `did` 做比较，就查到了研发部的所有员工。

> **结论**：子查询其实不复杂，它就是把查询的步骤拆开分类，再嵌套到一起。

#### 表达式位置：部门平均工资减去公司平均工资

第二个练习是"查询每个部门的平均工资和公司的平均工资的差"。这个有点意思，我们分两头看。

先看公司平均工资。员工不都是公司的吗？把 `salary` 这一列求个平均值就完事了：

```sql
SELECT AVG(salary) FROM t_emp;
```

再看部门平均工资。员工表里有各个部门的 `did`，而题目里出现了"每个"这两个字——**只要听到"每个"，就是典型的分组查询**。按部门分组，再算组内平均工资：

```sql
SELECT did, AVG(salary) FROM t_emp GROUP BY did;
```

这个语法是固定的：只要你分组，`SELECT` 位置就只允许查分组字段和聚合函数，别的不许写。跑完你就有了公司一共有多少组、每组的平均工资是多少。

现在把两个数一减，就出来了。所以在后面加个逗号，减去一个"整个公司的平均工资"：

```sql
SELECT did,
       AVG(salary),
       AVG(salary) - (SELECT AVG(salary) FROM t_emp) AS diff
FROM t_emp
GROUP BY did;
```

写个括号，子查询往里一放。因为它是单行单列，所以可以直接当一个普通值，扔到减法算式的右边——大于、小于、等于随便比，等号赋值、减法加法也都行。

这一类就讲完了：在查询里套查询，结果是单行单列，就可以名正言顺地当成一个值用。

### 行子查询：一行多列，得整体比

行子查询的形状是**一行多列**：子查询返回一行，但返回了多个列。

需求是"查询和白鹭性别和部门相同的员工信息"。我们先在员工表里定位白鹭：按 `ename` 查到他的性别 `gender` 和部门 `did`。返回的正是单行多列。

接下来第二步是查和白鹭信息相同的其他员工。这里的问题是：外层的 `WHERE` 拿谁比？

按理说拆开比就行了，但**行子查询的特点就是整体比较**。做法是把多个列用括号括起来，当成一个整体去比：

```sql
SELECT *
FROM t_emp
WHERE (gender, did) = (
    SELECT gender, did
    FROM t_emp
    WHERE ename = '白鹭'
);
```

括号的含义是：`gender` 等于子查询查出的 `gender`，并且 `did` 等于子查询查出的 `did`，**这个位置一定要一一对应上**。想排除掉白鹭本人，再补一个 `AND` 就行。

注意：这里除了等号，用 `IN` 也是可以的——`IN` 同样能承担多列之间的整体等于判定。

> **结论**：碰到行子查询（单行多列），一律用括号把多列括起来，配合 `IN` 或者等号，跟子查询的整体结果比。

不过如果实在记不住整体比较这个写法，也有一个转换思路：**把行子查询拆成若干个标量子查询**。就拿白鹭来说，部门和性别可以分开查——先查白鹭的性别，再查白鹭的部门，这就变成了两个标量子查询：

```sql
SELECT *
FROM t_emp
WHERE gender = (SELECT gender FROM t_emp WHERE ename = '白鹭')
  AND did   = (SELECT did   FROM t_emp WHERE ename = '白鹭');
```

所以其实也不用特意去记什么行子、标子、列子，把语法灵活掌握了就行：查询里嵌查询、更新里嵌查询、删除里嵌查询，都能查得出来。

### 列子查询：多行单列，IN 和 ANY、ALL

列子查询返回的是**多行单列**，也可以通俗理解成：查出来的结果是多个值。

多个值怎么比较？这就是关键了。如果返回的是多个值，比较的时候必须加上 `IN`、`NOT IN`，或者 `ANY`、`ALL`。

#### 与白鹭、谢吉娜同部门

需求是"查询与白鹭和谢吉娜同部门的员工姓名和电话"。

第一步，先查这两个人所属的部门编号 `did`。他们俩可能在一个部门，也可能在两个——如果是一个，那就退化成标量子查询了；如果是两个，就是列子查询，说白了就是有多个值。

```sql
SELECT did FROM t_emp WHERE ename = '谢吉娜' OR ename = '白鹭';
```

这句没问题。也可以这么写：

```sql
SELECT did FROM t_emp WHERE ename IN ('谢吉娜', '白鹭');
```

一个列名等于多个值，中间用 `IN` 串起来，表示"是他或者是他"，跟上面那句完全等价。查出来是 2 和 5。

第二步，查 2 和 5 这两个部门的员工信息。这两个值是一起给你的，你不能拆开查。第一个处理方案还是 `IN`：

```sql
SELECT *
FROM t_emp
WHERE did IN (
    SELECT did
    FROM t_emp
    WHERE ename IN ('谢吉娜', '白鹭')
);
```

把上面那句整个拿过来塞进括号就行。在这个范围内就是 `IN`，查出来就是跟那两个人同部门的员工。要查**不同**部门的呢？把 `IN` 换成 `NOT IN`，不在 2 和 5 里面，完事。

那如果手底下只有一个列，却又不想用 `IN` 呢？

```sql
SELECT * FROM t_emp WHERE did = (
    SELECT did FROM t_emp WHERE ename IN ('谢吉娜', '白鹭')
);
```

这句执行会直接报错。为什么？因为**等号只能等于单值，也就是标量子查询**。现在子查询返回了两行，没法"等于"。

> **易错点**：多值场景下等号直接报错，这是列子查询最常踩的坑。解法就是在等号后边、子查询括号的前面，加上 `ANY` 或 `ALL`。

- `ANY` 代表任意一个值，作用等于 `IN`——满足其中任意一个都行。
- `ALL` 代表所有值，判定的是"且"的关系。

#### 工资比他们三个都高

第二道练习：查询工资比白鹭、李思羽、黄冰茹三个人都要高的员工信息。

第一步，先查他们三个的工资：

```sql
SELECT salary FROM t_emp WHERE ename IN ('白鹭', '李思羽', '黄冰茹');
```

查出来三行数据、单列的值。

第二步，比他们的工资都大。`IN` 和 `NOT IN` 管的是"等于"的场景，这回我们要用大于，那就得上 `ANY` 或 `ALL`：

```sql
SELECT *
FROM t_emp
WHERE salary > ALL (
    SELECT salary
    FROM t_emp
    WHERE ename IN ('白鹭', '李思羽', '黄冰茹')
);
```

理解一下差别：加 `ANY` 是"比他们**任意一个**大就行"，效果等同于比他们里的**最小值**大；加 `ALL` 是"比他们**所有**人都大"。题目要的是三个人都比，所以必须写 `ALL`。

这一题也能转。列子查询可以转成标量子查询——"比他们三个都高"，那就大于其中的最大值：

```sql
SELECT * FROM t_emp WHERE salary > (
    SELECT MAX(salary) FROM t_emp WHERE ename IN ('白鹭', '李思羽', '黄冰茹')
);
```

`MAX` 返回的是单行单列，是标量子查询，可以当一个普通值直接放进去，不用加 `ANY` 和 `ALL`。效果跟上面那句完全一样。

> **结论**：列子查询（单列多行、多个值）拿来做等于，用 `IN` / `NOT IN`；拿来做大于小于，加 `ANY`（任意一个）或 `ALL`（所有）。而这四种关键字，本质上都可以用聚合函数收成单值，绕开多值。

### 表子查询：多行多列，当虚表连

最后一种是表子查询，名字不太好听。它的返回结果是**多行多列**。

这种结果既做不了条件也做不了值——你总不能拿一个多行多列的东西去"大于"谁。所以它一般作为一个**虚拟的中间表**来用。

需求是"查询所有部门的编号、名称以及部门的平均工资"。

我们打开部门表看看：部门表里只有部门编号和名称，**没有平均工资**。想让一行把这些都展示出来，就得做水平结果集拼接，把两部分接在一起。

- 第一部分来自部门表：部门编号、名称。
- 第二部分"平均工资"来自哪里？来自员工表。但员工表里也没有现成的"部门平均工资"这一列，它是**靠员工表做分组查询算出来的**。

所以这不是一次简单的"部门表连接员工表"，而是**员工表先分组查出结果，查出来以后再跟部门表连接**。这个位置上的东西，就是一个表子查询。

**步骤一**，在员工表上加分组查询，把部门平均工资查出来：

```sql
SELECT did, AVG(salary) avs FROM t_emp GROUP BY did;
```

得到部门编号和部门平均工资两列。这个结果集就可以当成一张虚拟表，去跟部门表做主外键连接。

**步骤二**，查部门的信息和平均工资，子查询是多行多列，当虚表用，正常连接：

```sql
SELECT d.did, d.dname, tmp.avs
FROM t_department d
LEFT JOIN (
    SELECT did, AVG(salary) avs
    FROM t_emp
    GROUP BY did
) tmp
ON d.did = tmp.did;
```

这里有三个点要注意：

- 用的是 `LEFT JOIN` 左外连接，部门表是逻辑主表。**就算这个部门一个员工都没有，它也照样出来**，平均工资算作 0。
- 括号里查出来的这个结果集，**一定要给它起个别名**。不起别名，后期你怎么去取这个表里的列？比如取平均工资这一列，你得写成 `tmp.avs`。
- 有外连接以后正常写 `ON`，主外键相等：`d.did = tmp.did`。查询列表就是 `d.did`、`d.dname`，加上 `tmp.avs`——别名叫 `avs` 了，所以这里直接取 `avs`，不用再算。

跑一下，每个部门的平均工资就都出来了。

> **结论**：子查询是多行多列时，绝大部分情况下都当虚表用——正常把它当一张表来连接，但别忘了起别名。什么时候会遇到这种场景？**当你发现你要查的数据，还得再经过一次查询才能拿到时**，就先查出一个虚表。如果表里直接就有，那肯定直接关联原表了，根本不需要子查询。

到这里，查询语句里嵌套的子查询就讲完了。

题面给的数据是这样的：

- 1 号员工工资 7000，他的领导是 3 号 Sam；

## 把子查询写进 update、delete 和 insert，收尾多表查询，再认识事务
> 对应块：BLK18 | 覆盖分集：P89-P93 | 块标题（分集名）：《89-数据库多表查询篇-update嵌套子查询以》

update 语句里也能塞子查询，而且下边一连就是三个案例。除了案例本身，这三个案例还顺带把一个坑暴露出来了——同表嵌套的问题以及它的解决方案。

跟前面 select 嵌套的套路完全一样：要么两张表之间互相打秋风，要么在同一张表上自己跟自己较劲。前者顺畅，后者就要绕个弯。

### update 里的子查询：两张表之间的搬运

第一个案例，**将测试部门的所有人的薪资改为原来的 1.5 倍**。

怎么做？大家想想，我们要改的是测试部门的薪资，已知部门名称是"测试部"，最后是不是要根据部门名称查出对应的 id，再去员工表里根据部门 id 修改 salary？行，那分两步。

步骤一很简单，它就是一个标量子查询：查测试部门对应的部门 id。

```sql
-- 步骤一：查测试部门对应的部门 id
SELECT did
FROM   t_department
WHERE  d_name = '测试部';
```

出来一个 6。

步骤二，根据这个部门 id 修改员工表的薪资。

```sql
-- 步骤二：把该部门所有人的薪资改为原来的 1.5 倍
UPDATE t_employee
SET    salary = salary * 1.5
WHERE  did = (
    SELECT did
    FROM   t_department
    WHERE  d_name = '测试部'
);
```

`salary = salary * 1.5` 里，右边的 `salary` 代表取到原有的值再乘 1.5，这跟我们在讲修改语句时学过的是一回事。`WHERE` 后面的括号把它一嵌套就可以了——这就是两张不同表之间做修改的一个子查询。

执行完一看，**影响行数是 0**。查了才知道，测试部的 `did` 确实是 6，可员工表里压根就没有 `did` 为 6 的人；1 号部门是研发部，孙宏亮他们几个在这儿呢。

把部门换成研发部再执行，这回四五条改中了，点开表一看，之前 2 万 8 的工资真涨成了 1.5 倍。

> **提示**：子查询查出来是单行单列，它就是"部门 id"这么一个值，可以直接当常量放在 `=` 右边。这一点你只要记住一次，后面几个案例就都是它的翻版。

第二个案例，**将没有部门的员工改为测试部**。具体是谁呢，是周周——他这个员工记录里的 `did` 是空的，现在要给他改成测试部门。

第一步还是那句话：先查测试部门对应的 `did`。因为你改完以后是要给周周设置一个 `did` 啊，你得先根据测试部门查出这个 `did` 来。

第二步还是修改语句：

```sql
UPDATE t_employee
SET    did = (
    SELECT did
    FROM   t_department
    WHERE  d_name = '测试部'
)
WHERE  did IS NULL;
```

执行完，周周那个位置的 `did` 已经变成 6 了。

注意这个位置你查出来的是单行单列，是标量子查询，它可以出现在任何需要"值"的位置上——写在 `WHERE` 右边可以，写在 `SET` 右边同样可以。

> **易错点**：空不能用等于号比，必须用 `IS NULL`。`did = NULL` 判断的永远是"未知"，一行都命中不了。

这两个案例相对来说都比较简单。

### 同表嵌套：1093 错误和它的解法

第三个案例开始有坑了：**把李冰冰的薪资改成孙红梅的薪资**。

步骤一：查孙红梅的薪资。这大家应该很简单。

```sql
SELECT salary
FROM   t_employee
WHERE  name = '孙红梅';
```

出来 1 万 3500。再看李冰冰多少——冰冰是 2 万多。那这一下改过去，相当于给她降工资了。

步骤二，按理说应该也简单：

```sql
UPDATE t_employee
SET    salary = (
    SELECT salary
    FROM   t_employee
    WHERE  name = '孙红梅'
)
WHERE  name = '李冰冰';
```

一执行——**1093**，不让改。

为什么？特别好理解。你就想象成 `UPDATE` 占用了员工表这张"对象"的引用，下方内部又要查询员工表，又是一次引用。他俩谁先谁后呢？相当于内部是先把值取出来，你再去获取。这就是一个对象被两个位置同时做了地址引用——其中一个引用没释放，两个人都占着，这时候任何一方都不能直接改。你改了，别人拿什么用？

这是一种 MySQL 为安全性提供的保护机制。

那这个东西就没法解决了吗？我现在就想这么做咋办？有办法。人是很聪明的，他是这样做的——**让内层先执行完，执行完以后把这个员工表的引用释放掉**。怎么释放？再套一层。

```sql
UPDATE t_employee
SET    salary = (
    SELECT salary
    FROM   (
        SELECT salary
        FROM   t_employee
        WHERE  name = '孙红梅'
    ) AS tmp
)
WHERE  name = '李冰冰';
```

看这个语法：我在内层子查询的外面又套了一层子查询，内层把 `salary` 查到以后，结果就交给了 `tmp`；这一层相当于执行完毕了，等于把这个值放给了临时表。而最终我们修改的，是外层表和临时表之间的关系。现在变成几张表了？变成两张表。

```text
朴素写法：同一张表被两个位置同时引用

    UPDATE t_employee          -->  占用 t_employee
          |
          +-- SET salary = ( SELECT salary FROM t_employee  )
                                             ^
                                             +-- 又来一次，还是同一张表
          |
          +-- WHERE name = '李冰冰'
      同一张表既被读又被改  =>  1093

套一层：内层先算完，结果交给 tmp，原表的引用顺手释放

    UPDATE t_employee          -->  占用 t_employee
          |
          +-- SET salary = ( SELECT salary FROM ( SELECT salary FROM t_employee
                                                   WHERE name = '孙红梅'
                                                 ) AS tmp
                               )
          |
          +-- WHERE name = '李冰冰'
             内层执行完毕，salary 落在 tmp 上，t_employee 的读取到此结束

      外层表 + 临时表 = 两张表  =>  可以改
```

读图说明：上面那半张图里，`t_employee` 同时是"被读的对象"和"被改的对象"，MySQL 直接拒绝；下面这半张图里，内层 `SELECT` 先跑完并把结果甩给 `tmp`，`t_employee` 的读取引用随之结束，等外层真正下手写的时候，那张表已经没人跟它抢了。

刷新一看，李冰冰的工资真改过来了。

> **结论**：同表嵌套的解法其实只有一条——把内层这个只查询再嵌套一层只查询，释放原有表的引用即可。太巧妙了。

至此，修改相关的嵌套语法就讲完了。

### delete 里的子查询：删两张表，还是删自己

刚呢我们已经完成了修改嵌套子查询，下面再说说删除嵌套子查询。其实它也很简单，只不过**也会面临跟修改同样的问题：删除的时候你不能是同一张表**。那解决方案呢？上一节课的方案是一模一样的。

接下来我们来做一下这两个练习。

#### 删除测试部门的员工：两张表之间的搬运

第一个呢，**将测试部门的员工数据删除**。这个相对来说比较简单，因为它是两张表。

步骤一，我们先根据部门名称查询部门 id：

```sql
SELECT did
FROM   t_department
WHERE  d_name = '测试部';
```

这个是 6 吧。

步骤二，我们在员工表中完成删除，根据部门 id 删除员工数据：

```sql
DELETE FROM t_employee
WHERE  did = (
    SELECT did
    FROM   t_department
    WHERE  d_name = '测试部'
);
```

括号里一放就 OK 了。执行一下，刷新——这回周周终于没了。

#### 删除李冰冰同部门的员工：又是 1093，还是那层套壳

第二个，**要删除跟员工表中李冰冰同一个部门的员工记录**。这个大家注意哈，他查的数据和删除数据都是员工表，是吧？那么面临什么问题呢？

首先我们还是老样子，步骤一先分步分清楚：步骤一先查询李冰冰对应的这个部门 id 编号；步骤二我们再删除李冰冰部门的其他员工。

```sql
SELECT did
FROM   t_employee
WHERE  name = '李冰冰';
```

这一查查出李冰冰对应的部门是 1。那最后呢要删除：

```sql
DELETE FROM t_employee
WHERE  did = (
    SELECT did
    FROM   t_employee
    WHERE  name = '李冰冰'
);
```

但是各位现在呢其实我们应该知道，**这又面临着一个问题：外层和内层是同一个表，也就是说双方占有同一个表的引用。** 那这个时候呢 MySQL 的保护机制是不让这么操作的，对吧？你说你又查又删除，你说到底我是让你删，还是让你要不要你塞啊，对不对？

我们来正常执行一下，看中不中来。看着，是不是还是报 1093 的问题啊？

那怎么解决啊？跟上方是一样的，我们还是去多套一层嵌套。说白了就说我不用这里边不是拿员工表了，我做一个啥呢？我查你的 `did` 完了呢，从……先执行，做一个虚拟结果表，连带 `tmp` 吧。

```sql
DELETE FROM t_employee
WHERE  did = (
    SELECT did
    FROM   (
        SELECT did
        FROM   t_employee
        WHERE  name = '李冰冰'
    ) AS tmp
);
```

好，完事。那最终的下方那我就跟我没关系了。

> **易错点**：这里有个报错容易让人卡住——每个虚拟产生的表啊，必须要起一个自己的名字。别名是必须得有自己的名字的。这起个别名啊，`tmp`，**可以省略 `as`**。

执行一下，这回忘了啥——你看这个位置说，这个每个虚拟产生的表必须要起一个自己的名字，别名是必须得有自己的名字。执行下好，那这样就 15 行受影响，最终员工表是不是就删了？来刷新哦，一号 id 的部门都删掉了。

所以解决方案跟上方还是一样的——那就这就是嵌套子查询的问题。

### insert 里的子查询：结构、数据，一步到位

这个标题叫得不是特别准，这一章其实主要讲三件事：第一，如何通过复制其他表的结构创建一个表；第二，如何把其他表的数据插到我们这个表中——这个可能得用 insert 嵌套；第三，如何模仿其他表创建表，并且复制其他表的内部数据。

**第一件事，复制表结构。** 现在我们有一个员工表 `t_employee`，我想创建一个新表，期望它的表结构跟 `t_employee` 一样。如果平时创建，你就自己手动写呗，DUANG DUANG 一大堆，比较麻烦。但是我教大家一个快捷方式：

```sql
CREATE TABLE t_employee_1 LIKE t_employee;
```

`LIKE` 用这个关键字，像谁呢，像我们下边那个已经存在的表。这样他就会创建一个表结构相同的新表。刷新一下有了，点开表你发现结构是不是相同啊？但是——**只复制表结构这句话，它没有数据**。

**第二件事，搬运数据。** 假如我想把 `t_employee` 里的数据再插到我这里边怎么办？这就可以用 insert 嵌套了。

```sql
INSERT INTO t_employee_1 SELECT * FROM t_employee;
```

这个位置不要写 `values`，也不要写 `values` 加后面那些东西，直接写 `select 星 from 谁`。当然这个表后边你还可以再加 `where` 条件——加 `where` 条件代表你不拿全部数据，拿部分数据；不写就代表把所有数据都给你插进来。

执行完再刷新，这样是不是好了？这就完成了一个表的复制。

**第三件事，二合一。** 但大家注意哈，这么做呢还有点麻烦，我教大家一个二合一的方法——创建表并且复制对方表的数据：

```sql
CREATE TABLE t_employee_2 AS SELECT * FROM t_employee;
```

`AS` 后边参照谁呢，参照我们把上面那句 `select` 粘过来。注意哈，这个写法就代表创建一个表，同时里边的数据和表结构全部参照这个表。执行完刷新就有了。

所以大家听我说，这就是我们如何用嵌套完成数据之间的互相绑定、表之间的一个迁移。大家把这个记一下。

到这里嵌套子查询就讲完了，多表查询也算讲完了。回忆一下我们都讲了什么：之前讲了垂直连接、水平连接，水平连接里边又分成了内连接、外连接、自然连接等等；刚才我们又讲了嵌套查询的四种场景——select 嵌套、update 嵌套、insert 嵌套、delete 嵌套。课上这些案例大家统一练一下。

### 多表查询阶段收官：四道题

语法讲完了不代表你会用。你们可能只是基本掌握，用起来那肯定还是要费劲的。所以还是那句话——SQL 语句的学习必须得是学练结合。咱们做一个阶段性的小练习，这次只练四道题（先说五道，又改口"是四道哈"），这四道题先不要看答案自己走一遍，能写出来，这阶段性的练习就是成功。

先分析表关系。一共准备了三张表：学生表、课程表、分数表。学生表里有学生 id、名字、年龄、性别；课程表里有对应的 id 以及课程的名字；分数表里有一个分数，同时它也会知道这个分数是哪个课程的、哪个学生的——是不是有两个外键？

```text
   student(student_id PK)          course(course_id PK)
          |                                 |
          | student_id                     | course_id
          v                                 v
        score(student_id, course_id, score)

     分数表两个外键：student_id 指向学生表，course_id 指向课程表
```

读图说明：分数表是典型的中间表，两列外键分别把学生和课程挂上，课程和学生之间是"多对多"的关系。

往表里放数据：学生表插入三名学生，分别是爱丽丝、鲍勃和查理；课程表建三门课，数学、物理、化学；分数表执行七条分数信息。

#### 查每名学生的姓名、年龄、课程名和成绩

**查询每名学生的姓名、年龄、所选课程的名称以及对应的成绩；如果学生没有选课，则成绩为空。**

你看他要的数据：姓名和年龄来自学生表，课程名称来自课程表，对应的成绩来自分数表。最后他强调的那句话在教我们什么呢？——**如果学生没有选择课程，那成绩为空。** 也就是就算学生人家没选课，你也得把人家给查出来，只不过人家的成绩为空。

这句话在教我们：**学生表是逻辑主表**。这里应用的应该是左连接查询，一会儿我把学生放在最左边，剩下的都是左连接。

做法就是通过学生表关联分数表——注意分数表是中间表，占用分数表之后再去关联课程表，那最终不就都有了。

```sql
SELECT STU.name,
       STU.age,
       COU.course_name,
       SC.score
FROM   student STU
LEFT JOIN score  SC  ON STU.student_id = SC.student_id
LEFT JOIN course COU ON SC.course_id  = COU.course_id;
```

> **结论**：只要第一个是逻辑主表，剩下的就都是左连接。

连完了以后，最终要啥就写清楚：学生的 `name`、`age`，课程的 `course_name`，分数表的 `score`。执行一下全出来了。

现场写的时候我可闹了笑话：把别名 `SC` 写成了 `S`，少写一个字母，一执行就报列不存在；改过来还是错，盯着屏幕直念叨"这不是 student，这是 STU，这是学生啊"。三号代码八个 bug。改完再一戳，这回总不错不了吧——成了。

#### 查没有选任何课程的学生

**查询没有选择任何课程的学生姓名。**

这题一听我都不用想，它肯定是子查询好实现。为什么？因为大家想想，他的目标是查学生姓名，但他的条件是"没有选择任何课程的学生"。那我们的做法无非就是先查出没选课学生的 id，查出来以后再拿着这个 id 去查学生姓名。这不就一个经典的子查询吗。

那大家想一个问题：啥算学生没选课呢？你说看哪个表——看课程表还是看学生表？

都不看。因为课程表里边是包含所有课程，跟学生选不选没关系；学生表里边是所有学生信息，选不选课，学生信息都有。他其实看的是**分数表**。

你看分数表里有 1 号学生、2 号学生、3 号学生、1 号学生、2 号学生、3 号学生——1 号学生选了两门课，所以有两个成绩；2 号学生两门，两个成绩；3 号学生三门，三个成绩。这证明只要在分数表里出现过的，都选过课了；那反之，没出现的就是没选课。

那怎么做呢？我查不了没选的，但我能查选的。我只要不在这个范围内，是不是就搞定了。

第一步，先查所有选过课的学生 id：

```sql
SELECT DISTINCT student_id FROM score;
```

这里边面临一个问题：这些 id 有没有必要重复出现啊？没必要。你只要出现 1、2、3 就行了，如果重复出现一遍，证明你选了就得了呗，也没说你选两门课、三门课，对不对。那怎么能不让它重复出现呢？当然我们讲过一个去重复的关键字，大家有印象吗？叫 `DISTINCT`。这个关键字可以把我们后边的一列或者多列值去重。

第二步，查不在这个范围内的学生：

```sql
SELECT name
FROM   student
WHERE  student_id NOT IN (
    SELECT DISTINCT student_id FROM score
);
```

> **易错点**：这里子查询返回的是多个值，不能用 `=` 比，要用 `IN` / `NOT IN`（或者 `ANY` / `ALL`）。`IN` 是"在其中"，`NOT IN` 是"不在其中"。这里放过 `IN` 执行一次，三位学生全列出来了——这就证明所有学生都选过课；但这个题的答案得加个 `not`，它也是对的，代表没有。

#### 查平均分高于全体平均分的课程

**查询每门课程的平均成绩，并罗列出平均成绩高于所有学生平均成绩的课程。**

这又是一个子查询，很明显，为什么？因为这个条件也需要查。做法三步。

第一步，先查所有学生的平均成绩。

```sql
SELECT AVG(score) FROM score;   -- 86
```

这应该很简单，从分数表归来，把它们送到平均值就行。一共七条分数，平均成绩 86 分，还挺高。

第二步，查询每个学科的平均成绩。你分数表全查学科的时候，注意这里边是不是有个 course id——01 学科、02 学科、03 学科，这个跟人没关系，是不是按照学科分组算平均分啊？那就是说这个要分组，给它 `GROUP BY` 一下。根据学科分组，我就可以起一个学科 id 分组字段，以及平均分，给它起个名叫做 `cav`。

```sql
SELECT course_id AS cid,
       AVG(score) AS cav
FROM   score
GROUP BY course_id;
```

第三步，分完组以后再筛选。我要的是这些平均分要大于整体的平均分。分完组以后再筛选，用啥呢？是不是用那个 `HAVING`？`HAVING` 是跟 `GROUP BY` 搭配、专门用来做分组后筛选的，而且后边是可以复用我们这些字段的。

```sql
SELECT course_id AS cid,
       AVG(score) AS cav
FROM   score
GROUP BY course_id
HAVING AVG(score) > (SELECT AVG(score) FROM score);
```

括号里就是我们刚刚写的查总体平均分那句，它是个单值，叫标量子查询——单值做个简单比较、符号运算都是可以的。

执行下来，只有 01 学科那行显示出来了，它 89，整体平均分 86，其余几门都低。这说明什么？说明 01 这个学科老师讲得比别的科好呗。

#### 查每名学生选课的平均成绩

**查询每名学生选课的平均成绩，并且按照平均成绩的降序排序。**

我问大家一个问题：1 号学生的平均成绩是多少？他考的是 101、102 两门学科，那他的平均成绩就等于 85 加 78 再除以 2。

做法又是分组，只不过这回根据学生编号分组：

```sql
SELECT student_id AS gid,
       AVG(score) AS avg_score
FROM   score
GROUP BY student_id
ORDER BY avg_score DESC;
```

分组以后还要排个序，`ORDER BY`。降序就是从大到小，写 `DESC` 就可以了。执行完：3 号学生分最高，然后 2 号、1 号。

> **提示**：`GROUP BY` 后边算出来的这些数据，在 `ORDER BY`、`LIMIT`、`GROUP BY`、`HAVING` 后边都是可以直接使用的。

但是这么做有问题。假如我不拿学生 id 分组，我要查学生的姓名，怎么办？你看我们现在分数表里边只有这个学生的 id，没有学生的姓名。

其实这个做法很简单——我们相当于加了一点难度：把数据做一个水平的连接，把学生表和分数表连完了以后再做高级处理，分组、排序等等。

```sql
SELECT STU.name,
       AVG(SC.score) AS avg_score
FROM   score  SC
JOIN   student STU ON SC.student_id = STU.student_id
GROUP BY STU.name
ORDER BY avg_score DESC;
```

先连接一下拿到了学生姓名，再拿名字分组，这样查的时候就能查到哪个学生的平均分是多少了。其实跟上方是一样的——一个单表，一个多表。

这四道题大家可以反复再练两遍。练的过程可以去思考一个问题：我们现在用的这些所谓的子查询，能不能换成连接查询去实现？这些东西都可以去研究研究。

### 事务：一个不可分割的工作单位

接下来进入课程的第八章，数据库的高级和新特性。这一章一共分四个小节：第一，数据库中极为重要的概念——事务，以及事务的具体操作命令；第二，用户权限控制管理，以后出去当组长了，怎么给组员创建账号分配权限；第三，数据库的备份和还原，讲数据怎么备份容灾、数据怎么传递，以及如果误删数据了怎么用日志做回滚，避免删完数据提桶跑路；第四，MySQL 8 这个版本的两个新特性。

我们先进入第一个小节。这个概念特别重要，需要大家掌握。

#### 它是什么，又有什么用

> **定义**：事务是一套操作命令的有序集合，是一个不可分割的工作单位。

先不看"事务"这俩字，光看这句话。它是一个什么？它是一个集合，是一个容器，是一个有序的容器，内部可以装一套操作数据的命令——也就是这个集合中装的是我们写的多条 SQL 语句，这就叫做一个事务。

以前这些语句是单独执行的，现在装到一个事务里一起执行，这就是这个概念。

再往下读它的作用：

- 事务中单个命令不会立即改变数据库的数据；
- 当全部执行成功，可以统一进行数据的更新；
- 当有任意命令失败，可以进行状态的回滚。

读到这我稍微有个感觉了。什么意思呢？就是事务内部有多个命令，这些命令单独执行的时候都不会进行数据的修改；只有全部成功了，我们才判定事务成功，才会统一修改。反之有任意一条失败，我们判定事务失败，可以进行状态的一个回滚——把数据回到修改之前的一种状态。

> **结论**：这个作用不就是当我们有操作失败的时候，给我们一种数据回滚的机会，或者一个容错的机会吗。

事务的组成是由事务的开始和事务的结束，中间可以写多条命令，那它们就在一个事务中。

```text
    事务开始
       |
       +-- 命令 1
       +-- 命令 2          中间可以写多条命令
       +-- 命令 3          一条两条、三条四条、100 条都行
       |
    事务结束
       |
   +---+---+
   |       |
   v       v
 都成功   都失败
统一更新  回到修改
数据库   之前的状态
```

读图说明：这是一个有序集合，要么大家都成功、要么就都失败，中间夹的那几条命令不允许有"一半执行了一半没执行"的状态。

再总结一下事务的两个作用。第一个作用，**为数据库操作序列提供一个从失败中恢复到正常状态的方法**。你报错了、语句执行错了没关系，它不会部分修改数据库，会大家一起回到之前的状态。第二个作用，**当多个应用并发访问数据库时，可以防止彼此之间的操作互不干扰**。后期的数据库可能被多个客户端同时访问，互相在修改数据的时候互不影响。

这是事务的两个核心作用，先大概记下。

#### 什么时候该加事务：两个真实场景

我给大家通过真实的场景来说一说，到底啥时候需要加事务。举两个例子。

**一个生活里的场景，一个非常可怕的场景。**

临近期末考试、高考的最后，你偷偷逃课出去上网吧，被父母当场抓住。大家，这是一听到就挺渗人的，比恐怖故事还恐怖。

但大家想想会发生什么。如果你是高考之前被抓住，你放心，你不会挨打。为什么？都高考了，父母打了你，万一影响你考试心情怎么办？还有一个问题，万一打了你，万一你高考考得又很好，那父母又怎么找回这个场面呢？

所以现在面临两个事情：第一是打你，第二是高考，这两件事有点相关。一般这时候父母都会给你撂一句狠话，就说你给我等着啊——这话含义就比较大了：你要考好，那便是晴天；你要考不好，男女混合双打加上出血流血 buff 一起往上干。

那这个时候大家想一个问题，他就不会立即打你吧，他会等到高考结束以后再决定是否收拾你。那我就认为逃学上网和高考临近，这两件事情就是一个完整的事务。只有两个条件都触发了，最终才能整体打你，或者是整体放过你。

> **结论**：两件相关的事情，彼此影响、结果互相牵连，就应该加到一个事务中。

**再看一个程序里的案例：转账。**

转账业务其实很简单，我给你转钱，那就是我减钱，你加钱。所以转账业务会涉及到两个修改动作，一个加钱一个减钱。

那大家思考一个问题：如果我们不考虑错误的场景，肯定是成功的，我减钱成功，你加钱成功。但各位可能面临一些问题啊——假如我想给你转一个亿，一个小目标，但我银行卡里边只有三块七，那能不能你加钱成功了、我减钱不成功呢？是不是也可能有这种场景？

所以大家想想，我们一共有几种状态呢：

| 加钱（接收方） | 减钱（发起方） | 业务结果 | 允许吗 |
| :--- | :--- | :--- | :--- |
| 成功 | 成功 | 成功 | 允许，两边都成了 |
| 成功 | 失败 | 失败 | 不允许，银行卡里会无缘无故多出很多钱 |
| 失败 | 成功 | 失败 | 不允许，光扣钱不加钱，银行不干 |
| 失败 | 失败 | 失败 | 允许，反正是彻底啥也没干 |

虽然说只有两个动作，最终它们发生的可能性有四种，其中只有一种是成功的，剩下的都不应该单独地进行数据的修改。

那如果说你是单独去执行这两条 SQL 语句，你是控制不了的。真出现加钱成功、减钱失败这个结果，最终就是银行卡中无缘无故多了很多钱。这个肯定是不行的。

所以我们应该把发起者减钱、接收者加钱这两个 SQL 语句的动作放到一个事务中。都成功了，OK，我就整体执行；如果有任意失败，我判断失败，咱们回到之前的状态。是不是就可以了。

> **结论**：只要一个业务中包含两条或者以上的修改数据操作，就应该加到事务中。或者更有甚者，在我们后期开发场景下，我们会把所有的业务层的方法全部加上事务——不管你是一条两条，我都加上，是这样一个状态。所以事务是我们一个必须要使用的一种技术点。

#### ACID：把前面的理解抽象成四个点

面试经常会问事务的 ACID。所谓的 ACID，就是把我们刚刚理解的思路和概念，抽象成了四个小节点。

**A 原子性（Atomicity）**。什么叫原子？在早期的物理版本中，原子是最小不可分割的一个单位。那放到事务里说，事务是一个不可分割的单位，事务中的操作要么都发生，要么都不发生。举个转账的例子，里边有加钱减钱，你不能把加钱和减钱的任何一个动作剥离出这个事务；如果剥离出去，这个事务就没有意义了。事务是一个最基本的业务单位，就不能再拆了。

**C 一致性（Consistency）**。这个理解有两种状态，但两种都是有关系的。第一种状态就是事务内部的这些动作，加钱减钱全成功就都成功，失败就都失败。还有一种见解思路也一样，就是整体的数据总状态前后一致。举个例子：我银行卡有 1000 块，你银行卡里边也有 1000 块；如果都成功了，假如给你转 500，我变成 500，你变成 1500，那咱们加起来还是 2000，跟我之前还是一样的；如果我失败了，我不动你不动，还是 2000。所以说就是前后总状态一致。

这时候有些同学可能跟我较劲说："那不对，老师你有 1000 我有 1000，转成功了呢，我变成 500，你变成 1500。"那差两块呢？我说为啥呀，他说扣手续费了啊。那这可不算哈，这跟一致性没关系。

**I 隔离性（Isolation）**。这个稍后我们会单独再讲。隔离性指的就是：我们在开发中，同一个数据库的表可以被多个客户端访问，那这个时候他们访问之间都是一个独立的事务，事务和事务之间互相不受干扰。他做了什么事你看不见，只有他提交以后你才能看得见。这是一个避免干扰的机制。

**D 持久性（Durability）**。这个其实很好理解。所谓的事务，持久性指的就是：一旦它真的有个提交动作、真的提交了，代表就要修改了、成功了，那它真的会改变数据库；但要是没提交，它就真的不改数据库。所以最终它会真的去改变数据库的一个数据状态，持久改变。

> **结论**：把上面四条再拧一把——事务可以把多个动作组成一个不可分割的单位，最后统一成功或者统一失败。那到底什么时候需要加事务呢？记住这句话：**只要一个业务包含两条以上的修改语句，就应该加事务**。所以说事务是开发中必备的一个技术点。

### 本讲提到的题目

多表查询这一阶段收官时留了四道练习题，题目是当场给出来的，要求不看答案自己先走一遍。表结构就是前面那三张：`student`（`student_id`、`name`、`age`、`sex`）、`course`（`course_id`、`course_name`）、`score`（`student_id`、`course_id`、`score`），学生是爱丽丝、鲍勃、查理，课程是数学、物理、化学，分数表七条记录。

**题目一：查询每名学生的姓名、年龄、所选课程的名称以及对应的成绩；如果学生没有选课，则成绩为空。**

答案：

```sql
SELECT STU.name,
       STU.age,
       COU.course_name,
       SC.score
FROM   student STU
LEFT JOIN score  SC  ON STU.student_id = SC.student_id
LEFT JOIN course COU ON SC.course_id  = COU.course_id;
```

解析见《查每名学生的姓名、年龄、课程名和成绩》。关键在于最后那句强调——没选课的学生也得查出来，只不过成绩为空。既然要保住主表的人，就必须用左连接；而且只要第一个是逻辑主表，剩下的连接全都是左连接，分数表是中间表，它再去连课程表。

**题目二：查询没有选择任何课程的学生姓名。**

答案：

```sql
SELECT name
FROM   student
WHERE  student_id NOT IN (
    SELECT DISTINCT student_id FROM score
);
```

解析见《查没有选任何课程的学生》。两个要点：一是"没选课"这件事只能从分数表判断，课程表和学生表都看不出来——凡是在分数表里出现过的学生，就证明他选过课了；二是 `DISTINCT` 是为了去掉重复的 `student_id`，一个人选两门课出现两次没有意义，证明他选过就够了。

**题目三：查询每门课程的平均成绩，并罗列出平均成绩高于所有学生平均成绩的课程。**

答案：

```sql
SELECT course_id AS cid,
       AVG(score) AS cav
FROM   score
GROUP BY course_id
HAVING AVG(score) > (SELECT AVG(score) FROM score);
```

解析见《查平均分高于全体平均分的课程》。先分组再筛选，筛选用 `HAVING` 而不是 `WHERE`；括号里是查总体平均分的标量子查询，返回单值，可以直接参与比较。跑出来只有 01 学科，它的平均分 89 高于整体的 86。

**题目四：查询每名学生选课的平均成绩，并且按照平均成绩的降序排序。**

答案：

```sql
SELECT STU.name,
       AVG(SC.score) AS avg_score
FROM   score  SC
JOIN   student STU ON SC.student_id = STU.student_id
GROUP BY STU.name
ORDER BY avg_score DESC;
```

解析见《查每名学生选课的平均成绩》。单表版本是 `GROUP BY student_id ORDER BY AVG(score) DESC`；但分数表里只有学生 id 没有姓名，所以要先把学生表和分数表做一次水平连接，再拿姓名分组、再排序。两种写法道理完全一样。
