## 173-锁的概述_读写的并发问题
> 对应分集：P173 | 原始标题：《173-锁的概述_读写的并发问题》

### 锁机制的作用与事务隔离性的实现

前面我们讲了 Redo 日志和 Undo 日志。靠这两种事务日志，我们把事务的原子性、一致性、持久性体现出来了。那事务的隔离性该由谁来体现呢？答案就是这一章要讲的锁机制。所以锁不是一个孤立的知识点，它是事务这块拼图里最后缺的那一块。

先把一个前提说清楚：锁本身不是数据库独有的概念。只要是在编程语言里，涉及到多个进程或者多个线程并发地去访问某一个共享资源，我们就需要用锁机制来解决并发问题。尤其是针对一些敏感的数据，比如订单、金额，这类数据一定要保证它的完整性、一致性，也就是安全性。

那这种场景怎么办？我们要保证这份数据在任何时刻、或者某一段时间之内，最多只能有一个线程在访问它。当这个线程的访问结束以后，其他线程才可以继续进来访问这个共享数据。就这么一个场景。

到了数据库这一层，同样会遇到共享资源的问题。要把这里的"资源"说全：除了计算资源，像 CPU、内存（RAM）、I/O 资源，这些需要争抢之外，还有一类同样需要共享、需要争抢的东西，就是我们数据库里存的数据。为了保证这些数据的一致性，为了多个会话、多个请求、或者叫多个事务并发访问数据库数据时的安全性，我们就需要用到锁机制。

> **结论**：数据库里的锁，和 Java 里的 `synchronized`、Lock 锁，以及后面要讲的 JUC，是同一类解决方案。

锁机制为 MySQL 提供的各个隔离级别提供了保障。至于隔离级别具体是怎么被保障的，就是我们下面要讲的那些丰富的锁。

用了锁就会出问题，锁冲突是不可避免的：一个事务正在操作这条记录，其他事务想过来，可它已经被锁住了，这时候怎么处理？后面还有死锁的问题，这些都是会出现的。而锁冲突一定会影响并发的性能。这里就有一个平衡——我们既想提高并发性，同时又一定要保证数据的完整性、一致性、安全性。

这个平衡就落在锁的粒度上：希望并发性高一点，就让锁的粒度小一点；希望并发性低一点，就让锁的粒度大一点。表锁（Table Lock）、行锁（Record Lock）、页锁（Page Lock），这三种粒度是不一样的，具体讲到的时候再说。

### 并发事务访问相同记录的分类

具体讲各种锁之前，我们先从宏观上对"并发事务访问相同的记录"建立一个直观的印象。所谓大处着眼、小处着手，我们先大处着眼一下：并发事务访问相同的记录，会有几种不同的情况。

#### "相同记录"的界定

这里说的相同记录，既可以往小看，就是同一行数据；也可以往大看，就是同一个表，这两种粒度在一定程度上都能理解成"相同的"。

但前提是你得真的相同。如果事务 A 访问的是 A 表，事务 B 访问的是 B 表，两者访问的数据根本不一样，那就不可能影响数据的一致性，各自访问各自的就行了，该怎么着还怎么着。这种情况下加锁有什么意义呢？完全没有必要。

所以下面讨论的一切，都建立在"访问的是相同记录"这个前提上。

#### 读操作、写操作与三种组合

针对相同记录能做的事，无外乎增删改查。我们把查询看作读操作，把增删改看作写操作。

以两个并发事务为例，一个读一个读、一个写一个写、一个读一个写，组合起来只有三种情况：

| 组合 | 两个事务的动作 | 需要关注的问题 |
| --- | --- | --- |
| 读读 | 两个事务都在读 | 无并发问题 |
| 写写 | 两个事务都在写 | 脏写 |
| 读写 | 一个事务读、一个事务写 | 脏读、不可重复读、幻读 |

下面一个一个来看。

#### 读读

两个事务都在读，有问题吗？不会有任何问题。因为读操作都没有对这条记录产生任何影响，那大家读就完了。

这种情况非常安全，不需要考虑锁的问题。退一步说，即使考虑锁，两个读操作之间也是互相兼容的：不会因为我们的事务针对这条记录加了一个读锁，另一个事务来读也要排队加锁——没必要，同时执行就行。

#### 写写与脏写

两个事务都在写，这时候就可能发生脏写。脏写在讲事务并发问题的时候提到过，我们再来过一遍它到底是怎么发生的。

这有一条记录，事务 A 对它进行写入，事务 B 也对它进行写入。记录本身的值是 1，A 和 B 读到的都是 1；接着 A 把它改成 2，B 把它改成 3。然后 A 做了一个 `commit` 提交，它就认为这个 2 已经固定下来了；而 B 做了一个 `rollback` 回滚，回滚之后相当于把 3 又变回了 1。这时候 A 再一查，结果是 1。

> **易错点**：脏写是两个事务都改了同一条未提交的记录，后一个事务的回滚把前一个事务已提交的结果覆盖掉了。

问题出在哪？你会发现，其中一个事务对它进行修改还没改完的时候，另外一个事务就过来参与，这时候就乱套了。要解决这个问题，必须让它们两个排队执行，一个一个来：事务 A 改完了，提交了或者回滚了，事务结束了，另外一个事务再进来。用排队来解决它的安全问题。

#### 锁结构的字段与状态转移

这种"排队"用锁机制怎么体现呢？这里就引入一个概念，叫锁结构。

一条记录摆在那里，哪个事务都没来操作它，那它就是它自己。当有一个事务——比如事务 `T1`——要来操作这条记录的时候，发现没有提前的任何事务在操作它，那么这个 `T1` 就会生成一个锁结构。锁结构里的字段，我们先主要说两个：

- `trx_id`：标识当前这个事务是谁；
- `is_waiting`：代表当前事务是否需要等待。

只要操作这条记录，就会生成锁结构，而且这个锁结构是跟事务相关的。

> **易错点**：不会说有一条记录就只有一个锁结构。锁结构是跟事务打交道的——有几个事务来操作这条记录，就会有几个锁结构。

如果 `T1` 是最先来想操作它的（写操作），前提也没有别的事务在阻塞，那这时候它的 `is_waiting` 就是 `false`，意味着当前事务可以执行，相当于获取锁成功，或者叫加锁成功。

如果 `T1` 还没有结束，另外一个事务 `T2` 又来了，那 `T2` 是不是也会生成一个锁结构？会的。由于 `T1` 还没有操作完，针对写事务又必须排队，所以 `T2` 这个锁结构的 `is_waiting` 就是 `true`，相当于获取锁失败，你得等待。

当 `T1` 提交了或者回滚了——总之事务结束了——系统就会去看还有没有别的事务想操作这条记录。有，那就找到了 `T2`；找到它以后，就把它的 `is_waiting` 从 `true` 改成 `false`，它就不再是等待状态，可以进行操作了。

```text
T1 请求写               T2 请求写                T1 提交/回滚结束
    |                       |                          |
    v                       v                          v
锁结构1                 锁结构2                    扫描等待中的锁结构
trx_id     = T1         trx_id     = T2            找到 锁结构2
is_waiting = false      is_waiting = true          is_waiting: true -> false
加锁成功，开始执行       获取锁失败，排队等待         T2 加锁成功，开始执行
```

读图说明：一条记录上可以同时存在多个锁结构，分别对应来操作它的事务；先到的事务 `is_waiting` 为 `false` 直接执行，后到的事务 `is_waiting` 为 `true` 排队，前者事务结束后再把后者的等待标记改成 `false`。

整体看下来，这里其实有几种行为：

| 行为 | 锁结构 | `is_waiting` | 含义 |
| --- | --- | --- | --- |
| 不加锁 | 未生成 | —— | 记录上没有任何事务操作它 |
| 获取锁成功 | 已生成 | `false` | 当前事务可以执行 |
| 获取锁失败 | 已生成 | `true` | 必须等待其他事务执行完 |

获取锁成功这个状态，就类似于 Java 里讲 `synchronized` 的时候，相当于拿到了 `synchronized` 后边那个同步监视器。而如果别的事务没有拿到锁——因为别的事务正在操作——那它的 `is_waiting` 就是 `true`，表示得等待，等待别的事务执行完以后再去操作。

> **结论**：写写这种情形要记住的就一条——排队执行，剩下的都是排队在锁结构上的落点。

### 读写并发引发的三类问题

下面重点谈读和写：一个事务来读，另外一个事务来写。

这种情况下有可能发生脏读、不可重复读和幻读。这就是前面讲并发时提到的几个主要问题，也正因为有这几个问题，我们才把隔离级别分成了不同的档次。

> **提示**：脏写和这三个问题不是一回事。脏写在任何一个隔离级别下都不会发生，因为锁机制已经用排队执行把它直接挡掉了。真正要靠隔离级别去回答的，是有读有写的时候怎么解决这几个问题。

#### 脏读

A 事务负责读，B 事务负责写。表中的记录本身是 1，B 把这个记录从 1 改成 2，但 B 没有提交；就在没提交的时候，A 去读，把这个 B 还没提交的 2 读出来了。

读到了别人未提交的数据，这就是脏读。A 负责读、B 负责写，脏读正是在读写的时候出现的。

#### 不可重复读

怎么叫不可重复读？A 还是负责读，它去表里读数据的时候读到这条记录的值是 1；这时候 A 还没有结束，B 这个事务把 1 改成了 2，而且它提交了，相当于这个事务结束了。可是 A 的事务还没结束，它再去读这条记录的时候，发现值变成 2 了。

在同一个事务当中两次读，结果不一样，这就叫不可重复读。同样是 A 读、B 写，同样出现在读写当中。

#### 幻读

幻读也是类似的。A 去读 `id` 小于 10 的记录，读到了 5 条，A 还没有结束事务；B 往里边塞了两条记录，做了两次 `insert`，都是 `id` 在 10 以前的，添加完之后 B 自己提交了。A 再去读，发现变成了 7 条，多了两条记录。

在同一个事务当中再去读的时候，记录数变多了，这就是幻读。

三个问题放到一起对比：

| 问题 | 事务组合 | 触发动作 | 同一事务内的异常表现 |
| --- | --- | --- | --- |
| 脏读 | A 读、B 写 | B 修改后未提交 | 读到了 B 未提交的新值 |
| 不可重复读 | A 读、B 写 | B 修改并提交 | 两次读到的同一条记录值不同 |
| 幻读 | A 读、B 写 | B 插入并提交 | 两次读到的记录条数不同 |

> **结论**：脏读、不可重复读、幻读这三个问题，都是在"一个读、一个写"的事务组合中出现的。

另外要注意，不同的数据库厂商对 SQL 标准的支持不太一样。按 SQL 标准来说，可重复读（Repeatable Read）这个隔离级别只能解决脏读和不可重复读；但 MySQL 的可重复读还把幻读给解决了。这一点是靠下一章要讲的 MVCC 实现的，到时候再具体展开。

### 解法一：读使用 MVCC，写加锁

针对上面这些场景，并发问题该怎么解决？这里主要指的就是脏读、不可重复读和幻读——脏写的问题任何一种隔离级别都已经解决掉了，我们真正要解的是一个读、一个写的问题。

这个大家记住，一共两种方案。一种方案是读使用 MVCC（Multi-Version Concurrency Control，多版本并发控制），写去加锁；另一种方案是读和写都加锁。先看第一种。

#### Read View 与已提交事务

为什么写操作一定要加锁？因为增删改的操作一定是针对最新的记录版本进行的，所以写的这个行为一定要加锁，就像写写里面需要加锁是一样的，我们需要把它保护住。

那读呢？读可以不去碰最新的记录版本，而是生成一个读视图（Read View）。Read View 里记录的是符合条件的记录，而历史版本由 Undo 日志来构建——也就是说，我们对 MVCC 的支持还得依赖 Undo 日志。

Read View 里记录的是什么？是所有已提交事务所做的更改。注意，是**已提交**的事务：当这个 Read View 生成的时候，还没有提交的事务、或者之后才开启的事务，都不会记录到 Read View 当中。

> **结论**：读的时候就去 Read View 里读，读到的必然是提交后的数据。脏读不就是读到了别人未提交的数据吗？这里只有提交过的，所以不会有脏读。

#### 读已提交下的 Read View 生成时机

读的时候能读到什么，还要看你在什么样的隔离级别下。先看读已提交（Read Committed）。

在这个隔离级别下，一个事务每次执行 `SELECT` 都会生成一个 Read View，每次的 `SELECT` 都会记录进去。既然 Read View 里记录的只是已提交的数据，那从 Read View 里读出来的，就相当于读已提交的数据了——你没有提交的数据不会被记录进来。

所以从这个 Read View 里读出来的都是提交以后的数据，就不会出现脏读的问题。

#### 可重复读下的 Read View 生成时机

那在可重复读（Repeatable Read）这个隔离级别下怎么弄呢？规矩变了：事务在执行过程中，只有第一次 `SELECT` 这个操作才会记录到 Read View 里；你第一次执行的我们才放进去，后续的 `SELECT` 操作根本就不往 Read View 里面记录。

这样我们要去读的时候，每次读的都是第一次那个 `SELECT` 的结果：后续修改过的、或者后续往里边插过的记录，都读不出来。

不可重复读和幻读的问题不就这么避开了吗？每次读到的都是第一次的那一份，幻读看到的也是第一次的那些记录，不会看到多出来的记录，也不会看到其他事务修改过的值。

> **结论**：MVCC 配合 Read View，相当于把幻读的问题也一并解决了。这就是 MySQL 的可重复读比 SQL 标准多解决一个幻读的原因。

### 解法二：读写都加锁

第二种方案，就是读和写的操作都使用加锁。这个成本显然会更高一些：第一种方案里读跟写是没有冲突的，而这里就有冲突了。

#### 读操作也需要加锁的场景

在一些具体的业务场景当中，我们确实有可能还得针对读操作也进行加锁，也就是说读操作也得针对最新版本；只要针对最新版本，你就得考虑加锁。

比如银行存款：你先去把这个账户的钱读出来，然后往里边存钱，最后把它写回数据库。在你读出来以后、往里边存钱的时候，别的事务这时候必须等待。说白了，就是你这时候的读操作也要加锁，就是这样的场景。

读也加锁之后，实际上就跟前面写跟写都加锁一样了，也就相当于同样得排队执行。一旦排队，脏读、不可重复读和幻读的问题就都能解决。

#### 加锁对脏读与不可重复读的处理

先看脏读。A 事务负责读，B 事务负责写。B 负责写的这条记录原来是一，它把它改成二；只要它没提交，A 是不是就不能去读？因为这时候加了锁，A 读不了。等 B 提交了，A 才能够读。这样 A 就不会读到 B 未提交的数据，脏读不会出现。

再看不可重复读。A 事务去读这个数据的时候是一，B 想对它进行修改、想改成二；但注意，A 现在正在读，而且加了锁，那这时候 B 想修改就必须等待。等 A 提交了或者回滚了，B 这时候再去改。而 B 再看到的时候，已经是在另外的一个事务里了，不在原来那个事务内——不可重复读也就解决了。

#### 幻读的处理与间隙锁

幻读看似也能解决，其实稍微麻烦一些。为什么这么讲？我们换个数字，把刚才那个过程重走一遍。

A 去读 `id` 小于 10 的记录，读到了三条，A 正读着，那我们就针对这条数据加锁——或者说几条数据都加锁，加一条还是几条，这要看你的 SQL 怎么写；总之，要把要访问的记录都给它加上锁。

这样 B 想去修改这几条记录的时候，因为 A 加锁了，它就得等待，不可重复读的情况就不会出现。脏读也一样：B 正在修改这条记录，A 想去读，因为人家针对这条记录加锁了，A 读不了。

可是到幻读这里就有事了。一开始读的是 `id` 小于 10 的记录，读到了三条，那针对这三条记录加锁——可以。但 B 做的是 `insert` 操作，幻读说的就是 `insert`。它往里边插入数据的时候，会用你这三条记录上的锁吗？

显然不会，因为插入的是新增的记录。新增出来的这条记录，我们叫幻影记录；这条幻影记录，当初 A 根本没有办法给它加锁——那时候它还不存在。

所以 B 理论上是可能 `insert` 成功的。它一插入成功，A 再去访问 `id` 小于 10，就变成五条了。这就说明：针对已有记录加锁，根本加不到幻影记录上。

那怎么办呢？这就靠后面 InnoDB 行锁里边要提到的间隙锁（Gap Lock）和临键锁（Next-Key Lock）来解决：比如 `id` 假定是 10，那我们就让小于 10 的这一整块范围都锁上；你要添加的记录处在这个范围之内、也就是处在间隙内，我就不让你添加成功。用这样一种方式，避免 A 正在读的时候 B 去 `insert`。

> **提示**：这里初听起来会稍微有点吃力，等讲到下面具体的锁的时候再回来看这一段。

### 两种方案的对比

到这里，针对一个读、一个写的两个事务，两种大的解决方案就都说完了，我们把它们放在一起对比。

| 方案 | 读操作 | 写操作 | 读写之间 | 并发性能 |
| --- | --- | --- | --- | --- |
| 方案一 | 使用 MVCC | 加锁 | 彼此不冲突 | 比较高 |
| 方案二 | 加锁 | 加锁 | 需要排队 | 会受影响 |

采用 MVCC 这种方式，读用 MVCC、写加锁，读跟写首先彼此不冲突，性能比较高；而都加锁这种方式，读跟写都加锁，那它俩就得排队，会影响性能。

下一章重点是给大家讲 MVCC，所以这一章我们主要谈的还是加锁的方式：读、写各自的加锁方式怎么去理解。在正式引入锁之前的这些并发问题，我们先有一个宏观上的认识。

## 174-数据操作类型的角度理解S锁与X锁
> 对应分集：P174 | 原始标题：《174-数据操作类型的角度理解S锁与X锁》

锁这一章，如果你之前完全没接触过锁的概念，会觉得东西真是太多了——这是本章里稍微有点难度的点。反过来，如果你以前对锁有过直观的理解，学起来就会轻松不少。每一章都难啃一些，而本章的重点只有一个：怎么把锁理清楚。

我打算用几个不同的维度来切这把锁，而不是把所有锁揉成一堆名词硬背。第一个维度是按**对数据的操作类型**划分，严格来讲分成**共享锁（shared lock，S lock）**和**排他锁（exclusive lock，X lock）**——习惯上也把共享锁叫读锁，因为读的行为是读读共享的，这个区别的细节一会儿再展开。第二个维度是按**锁的粒度**划分：表级锁、页级锁、行级锁，表级锁的粒度比较粗，往下越来越细，重点掌握表级锁和行级锁，所以把这两个放在前面。第三个维度是按**对待锁的态度**划分，就是悲观锁和乐观锁。然后还有**加锁的方式**——显式加锁和隐式加锁；再往外还涉及全局锁和死锁的问题。这一讲的顺序就按这个来。

### 一、从读与写推出两种锁

先从最基础的一处推出这两种锁到底为什么存在。

按数据操作的类型，操作只分读和写。泛泛地划分：读就是共享，写就是排他。

看读写的组合场景。读读这种场景不会引起任何问题；后面这几种——写写、读写、写读——就会出现并发问题。其中读写与写读这两种，有两种方案可选：一个是 MVCC，一个是加锁。MVCC 放到下一章讲，所以这一讲讨论的范围全是加锁。写写本身也是加锁。

既然几种场景全都是加锁，而里面又涉及读、又涉及写，那自然就得**针对读提供一种锁、针对写提供一种锁，再让这两种锁相互阻塞**，问题就解决了。

于是分成两种锁：一种叫 `shared lock`，简称 S lock，就是 **S 锁（共享锁）**；另一种叫 `exclusive lock`，字母是 X，就是 **X 锁（排他锁）**。S 跟 X 长得比较接近，就用这两个字母来表示。

习惯上，共享锁对应地叫**读锁**，排他锁对应地叫**写锁**。这个对应关系不是随便配的：凡是出现写的场景，就像上面后面那三种情况，它一定都是排他的，也就是需要相互阻塞、需要排队；而读跟读之间就是共享的，不会出现任何并发问题。所以把读锁跟共享锁放一起、写锁跟排他锁放一起，先用这个泛泛的对应关系建立起感觉。

### 二、S 锁与 X 锁的兼容性

先把两个锁各自的行为说准，再说它们两两撞上是什么结果。

**共享锁**：同一份数据，多个事务如果都是进行读的操作，是可以的，相互之间不受任何影响、也不会阻塞。就是读跟读共享，两个共享锁之间互相不阻塞。

**排他锁**：一个写操作还没有完成之前、也就是这个事务还没完成之前，它会阻塞其他加写锁的事务，也会阻塞其他加读锁的事务。排他嘛——我现在正在操作，其他都得等，这才构成阻塞、才构成排队的前提。

> **结论**：只要出现了 X 锁，不管它是先来的还是后到的，组合一律不兼容；只有 S 与 S 之间兼容。

| 已持有锁 \ 新请求 | 请求 S 锁 | 请求 X 锁 |
| --- | --- | --- |
| 持有 S 锁 | 兼容，不阻塞 | 不兼容，阻塞 |
| 持有 X 锁 | 不兼容，阻塞 | 不兼容，阻塞 |

> **易错点**：不兼容不是"谁先来谁占理"，而是 X 锁一旦参与进来，无论它是先持有的那一方，还是后请求的那一方，结果都是阻塞。

把这张表读成一张排队规则表：两把 S 锁可以同时进门，S 与 X 之间必须排队，两把 X 锁之间也必须排队。前面说的读读共享、写写与读写互斥，全都能从这张表上读出来。

```text
事务 T1:  ──[ X 锁 持有中 ]──────────────────────────┐
                    │                                │
事务 T2:            └─ 请求 S 锁 ──▶ 阻塞 ──▶ 等待 T1 释放 ──▶ 取得 S 锁
事务 T3:            └─ 请求 X 锁 ──▶ 阻塞 ──▶ 等待 T1 释放 ──▶ 取得 X 锁
```

读图：T1 持有 X 锁期间，T2 请求 S 锁、T3 请求 X 锁都会被挡住，谁都不能插队，必须等 T1 把锁释放掉才能继续。

另有一处范围上的区别要交代：在 InnoDB 里，读锁和写锁既可以加在表上，也可以加在行上——因为它支持的粒度小到行级别，行级别都能体现，表级别当然也能。而 MyISAM 只支持表级别的锁，这一点讲表锁时再重点提。

### 三、读操作既可以是 S 锁也可以是 X 锁

前面说"读锁就是 S 锁"，这个说法其实还不够严谨。重点应该突出**共享锁**和**排他锁**这两个词：写锁明确就是排他的，而读锁既可以让它是共享的，也可以让它排他。

读操作就是 `select`，不管你是查一条数据还是多条记录，它也是一条语句。这条语句后面跟什么后缀，决定了它加的是哪种锁。

传统写法（5.7 和 8.0 都这样写）：

```sql
-- 加 S 锁：共享锁
SELECT * FROM account LOCK IN SHARE MODE;

-- 加 X 锁：排他锁
SELECT * FROM account FOR UPDATE;
```

`LOCK IN SHARE MODE` 加的是 S 锁，也就是共享锁，这是传统上一直这么写的方式。`FOR UPDATE` 加的是 X 锁，也就是排他锁——它本质上相当于你是一个增删改的角色，只不过这里执行的动作其实是读。

8.0 里给这两种写法各配了一个更贴近语义的新写法：

```sql
-- 8.0 新写法：加 S 锁（对应上面的 LOCK IN SHARE MODE）
SELECT * FROM account FOR SHARE;
```

`FOR SHARE` 对应 `LOCK IN SHARE MODE`，一看名字就知道是共享；而 `FOR UPDATE` 对应 X 锁。这两个单词本身长得挺接近，写的时候别混。

回到兼容性上再看一遍这两条语句的效果：T1 用 `LOCK IN SHARE MODE` 拿到 S 锁之后，其他事务对同样的数据也加 S 锁，互相不阻塞；但如果 T2 去加 X 锁，无论写的是 `FOR SHARE` 那种共享写法还是 `FOR UPDATE`，只要 T1 那个 S 锁还没结束，都得阻塞。反过来，T1 用 `FOR UPDATE` 拿到 X 锁之后，T2 无论是加 S 锁还是加 X 锁，也都要阻塞。

### 四、并发场景的实操演示

上面都是推出来的结论，下面在命令行里把这几种组合逐个撞一遍。

先登录并选库：

```bash
mysql -uroot -p
use atguigudb3;
show tables;
select * from account;
```

`account` 表里有三条记录。这里注意一个前提：没有执行 `begin`（或 `start transaction`）开启事务的时候，默认就是 `autocommit`，也就是自动提交，操作完事务就结束了。所以要让锁"留得住"，必须先开事务。一个会话代表一个事务，后面所有的加锁演示都在会话里用 `begin` 开启事务后再做。

（1）S 锁与 S 锁：兼容。会话 1 里 `begin` 之后执行 `SELECT * FROM account LOCK IN SHARE MODE;`，拿到 S 锁；会话 2 里同样 `begin` 再执行同样的语句，也能立刻查询出来，不会被挡住——因为 S 锁和 S 锁是兼容的。

（2）S 锁上再要 X 锁：阻塞。此时前两个会话的事务都还没结束，两个 S 锁都还在。第三个会话 `begin` 之后执行 `SELECT * FROM account FOR UPDATE;`，回车之后直接卡住，这就是阻塞行为。它要想不阻塞，得等前面两个事务都结束：先把一个 `commit` 掉，这块仍然出不来；再把第二个也 `commit` 掉，这回才查得出来，阻塞解除。

（3）X 锁上再要 S 锁：阻塞。反过来先把 `FOR UPDATE` 用上：会话里 `begin` 后执行 `SELECT * FROM account FOR UPDATE;`，这就是一个 X 锁、排他锁。此时另一个会话再去加 S 锁（`LOCK IN SHARE MODE`），同样阻塞——因为已经有一个 X 锁在那里。把持有 X 锁的事务 `commit` 掉，S 锁那边才查得到。

（4）X 锁上再要 X 锁：阻塞。在已经有 `FOR UPDATE` 的情况下，另一个会话再加 `FOR UPDATE`，一样阻塞，因为 X 对 X 也不兼容。

几种组合就这样都演示到了：先有 S 的情况看 S 兼容、S 上要 X 阻塞、S 上要 S 兼容、X 上要 S 阻塞、X 上要 X 阻塞。演示结束后把所有事务都 `commit` 掉。

### 五、不等待锁的超时策略与 NOWAIT、SKIP LOCKED

在已经持有排他锁的情况下，再想加别的锁——不管是排他的还是共享的——都得等待。那这个等待什么时候结束？会有个变量来控制超时，一旦超时它就结束了，这就是超时策略。

如果不想依赖这个变量，8.0 引入了一个新特性：在现有语句后面加后缀，`NOWAIT` 或者 `SKIP LOCKED`。

`NOWAIT` 就是不等待：只要发现等不到锁，就立刻返回。拿约会打个比方，你到了地方看约会对象在不在——在呢挺好；没在，没在立马走人，这就叫 `NOWAIT`。

`SKIP LOCKED` 也会立刻返回，但它的行为不一样：它只返回结果中**不包含被锁定行**的数据。如果有数据没有被锁定，它就把这些数据返回给你。两者之间就是这么一个小的区别。

演示一下。先在一个会话里 `begin`、用 `FOR UPDATE` 拿住 X 锁，然后在另一个会话里 `begin` 再做 `select * from account for update`——正常执行的话会阻塞。换写成：

```sql
-- 等不到锁就直接报错返回，不阻塞
SELECT * FROM account FOR UPDATE NOWAIT;

-- 跳过被锁定的行，返回剩余未被锁定的行
SELECT * FROM account FOR UPDATE SKIP LOCKED;
```

加上 `NOWAIT` 走一遍，它会提示有锁的情况，没有去阻塞。这就是它的场景。再加上 `SKIP LOCKED` 走一遍，它就不会像 `NOWAIT` 那样报错，没有报错，而是把没有被锁定的数据查出来——因为这次是把表中所有记录都给锁定了，剩下的数据就没有了，所以就是一个 empty 的结果集。

> **提示**：两者的差别只在"拿不到锁时怎么办"——`NOWAIT` 直接报错返回，`SKIP LOCKED` 不报错，而是绕过被锁的行、返回能读到的行；如果没有一行能读，就是空结果。

用完把两个会话都 `commit` 结束。这两个参数的意义就是：不会去等待，能查就查，不能查就马上执行相应的行为。

### 六、写操作的加锁行为

写操作就是增删改。这里没有读操作那种选择余地：读既可以加共享锁也可以加排他锁，写没什么可谈的，一定得加排他锁，也就是 X 锁。

#### delete 的加锁行为

`delete` 做的事是：去 B+ 树里找到这条记录，然后在这条行记录上把 `deleted_mark` 字段由 0 改成 1，表示把它删掉了。这个过程当中加的是 X 锁，也可以理解成它在读的方面要的是一个 X 锁——因为这种场景本身就是排他的，只要看到 X 就是排他。

```text
delete 一条记录
      │
      ├─ 1. 在 B+ 树中定位目标记录
      ├─ 2. 将该行 deleted_mark 由 0 置为 1
      └─ 3. 全程持有 X 锁（排他锁）
```

读图：`delete` 不是把行从页里抹掉，而是先定位、再改标记位，整段过程由 X 锁保护，别的事务在此期间加 S 锁或 X 锁都要等。

#### update 的三种情况

对一条记录做 `update`，要分成三种情况看。

第一种，没有修改这条记录的键值。所谓键值，举个主键的例子：对主键做 `update` 操作，你也得先做一次查找——在主键的聚簇索引里找，看你要不要改当前这个主键值。如果不改主键值，改的是这条记录当中的其他字段，那么再往下还要看这些字段占用的存储空间跟改之前相比有没有变化：没有变化是一种，有变化是另一种。第三种情况，就是改了记录的键值。

**情况一：不改键值，且字段占用的存储空间修改前后没有变化。** 这就相当于在原有记录的位置上直接把字段改掉，直接改这个字段就可以了。这个修改过程中加的是 X 锁，也可以看成是针对读的一个排他锁。

**情况二：不改键值，但修改数据导致前后的存储空间变了。** 这就麻烦一点：需要彻底删掉原有的那条记录——其实就是把它放到垃圾链表里——彻底删除之后，再插入一条新的记录，所以它其实是两个过程。彻底删除旧记录这个过程加排他锁；而插入新记录这一步是一个 `insert` 行为，这个 `insert` 行为由**隐式锁**来保护，确保你在 `insert` 的时候、在没提交之前，不会被其他事务看到。

```text
情况二：存储空间发生变化
      │
      ├─ 第一步：彻底删除旧记录（移入垃圾链表）──▶ 加 X 锁
      └─ 第二步：插入一条新记录 ─────────────▶ insert 行为，加隐式锁
                                                 （提交前其他事务看不到）
```

读图：一条看似简单的 `update` 在这里被拆成"删旧 + 插新"两步，加锁方式也随之分成显式的 X 锁与 insert 自带的隐式锁两段。

**情况三：修改记录的键值。** 想想聚簇索引，你最后要把 `ID` 从 1 改成 2，这就是要修改键值了。这时候同样得先把原来那条记录删掉，然后再做一次 `insert` 操作。删掉的过程加排他锁，`insert` 的时候自动也会加一个隐式锁，没有提交之前其他事务看不到。

#### insert 为什么一般不显式加锁

`insert` 这种情况，一般情况下是不需要加锁的。原因很直接：`delete` 是已经有一条数据、我们要把它删掉，所以能给它加锁；`update` 是已经有一条或多条数据，我们给它加 X 锁；但 `insert` 之前，它根本没有这个抓手——没有实体的东西，你就没法针对它去做加锁行为。所以一般就不加锁了。

但 `insert` 的过程当中还得有一个隐式锁去保证：我这条数据还没添加进去、这个事务还没提交呢，别的事务不能来访问我。要是一访问，不就出现隔离性的问题了吗？所以是没办法用抓手去加锁，但会有隐式锁来保证它在提交之前不会被别的事务访问。

| 写操作 | 是否真正加 X 锁 | 关键说明 |
| --- | --- | --- |
| `delete` | 是 | 定位记录后改 `deleted_mark`，全程 X 锁 |
| `update`（不改键值、空间不变） | 是 | 在原记录位置直接改字段 |
| `update`（不改键值、空间变化） | 是，另加隐式锁 | 删旧记录加 X 锁，插新记录走 insert 的隐式锁 |
| `update`（改键值） | 是，另加隐式锁 | 删旧记录加 X 锁，再 insert 并自动加隐式锁 |
| `insert` | 否 | 插入前没有实体抓手，无法显式加锁，由隐式锁保证提交前不可见 |

> **结论**：泛泛地讲，"写操作加 X 锁"这句话没毛病；细节上讲，`update` 和 `delete` 是真正加了 X 锁，而 `insert` 因为添加之前没有那条记录、找不到抓手，加不了 X 锁，靠隐式锁来兜底。

## 175-表锁之S锁、X锁、意向锁
> 对应分集：P175 | 原始标题：《175-表锁之S锁、X锁、意向锁》

按读写行为划分锁的第一个维度，我们已经讲完了——`S` 锁（共享锁，Shared Lock）和 `X` 锁（排他锁，Exclusive Lock，也叫独占锁）的区别，大家一定要去体会。接下来换第二个维度：从数据操作的粒度上划分。这条线上一共三级，表级锁、页级锁、行锁，粒度是越来越细的。

### 锁粒度的三个层次与并发度的权衡

表级锁锁的是整张表；页级锁锁的是若干数据页；行锁锁的就是一行行的数据。行已经是我们可以操作数据的最基本单位了，所以行锁的粒度非常小。

为什么要关心粒度？因为它直接决定数据库的并发度。假设事务 1 操作的是 `id = 5` 这条记录，我们给它加了一把行锁；事务 2 操作的是 `id = 7` 这条记录——大家都加行锁的话，两个事务互不影响，并发性自然更好。可如果两个事务操作的是同一张表，而我们加的是表锁：事务 1 把整张表锁住之后，事务 2 想再操作这张表就有问题了。

> **提示**：这里说的"有问题"，前提是至少有一方要写。两边都只是读，读跟读之间是兼容的，不存在冲突，所以没关系。我们现在讨论的，都是既有读又有写的场景。

所以想提高并发度，锁定的数据范围越小越好。但这里马上带出一个相反的问题：锁定范围越小，对资源的消耗反而越大——获取锁、检查锁、释放锁这些动作都是开销。两头都要，于是只能取平衡：高并发的响应能力和整个系统的性能之间的平衡。锁粒度这个概念就是为这个平衡而生的。

| 粒度层次 | 锁定范围 | 并发度 | 加锁／检查／释放的开销 |
| --- | --- | --- | --- |
| 表级锁（表锁） | 整张表 | 低 | 小 |
| 页级锁 | 若干数据页 | 中 | 中 |
| 行锁 | 若干数据行 | 高 | 大 |

> **结论**：粒度最大的表级锁开销小、并发度低；粒度最小的行锁开销大、并发度高；页级锁介于两者之间。

讲解顺序上，我们先讲表锁，再讲行锁，页级锁放到最后。

### 表锁的整体特征

表锁锁定的是整张表，这也是 MySQL 最基本的一种锁策略，而且它不依赖存储引擎——不管你用的是哪种存储引擎，表锁的策略都一样，就是针对整张表加一把锁。

它的好处很直接：开销小。粒度这么大，开销显然小。另一个好处是能够避免死锁——整张表都被你锁住了，哪还会有什么死锁问题？

> **提示**：后面讲行锁的时候就会遇到死锁问题了，这是粒度变细必然要付的代价。

问题同样直接：开销虽然小，但并发性差。

表锁这一块我一共罗列了四个。这一讲先把其中的表级 `S` 锁、表级 `X` 锁和意向锁讲透，元数据锁留到后面单独展开。

### InnoDB 中为什么仍存在表级锁

我们一般用的都是 InnoDB，这里就又要提到 InnoDB 和 MyISAM 的区别：InnoDB 支持行级锁，MyISAM 只支持表级锁。所以用 InnoDB 的话，通常不会去选表级的 `S` 锁或 `X` 锁——明明有粒度更小的行级锁可以用。

但有些场景下，即使你用的是 InnoDB，也确实需要表级别的锁，只不过加的不是 `S` 锁和 `X` 锁。这话说起来有点绕，跟说绕口令似的，看一个例子就清楚了。

假设我们针对某一张表做增删改查，这时候会加锁吗？其实不会。InnoDB 不会把这张表锁住，不管共享的也好、独占的也好，都不加。可如果我们对这张表做 DDL，比如修改表结构、或者删除这张表，这些行为对整个表都产生了影响，这时候相关的锁就出现了。

> **定义**：这种针对 DDL 操作、在 server 层加上的表级锁，叫元数据锁（metadata locks，MDL）。

阻塞是双向的。一个事务正在做 DDL，另一个事务想增删改查，那它一定要等一等；反过来，你现在正在增删改查，这时候要执行 DDL，是不是也得等一等？必须等。你想，如果 DDL 执行成功了，你在同一个事务里，第一次查完的表结构和后面查完的表结构都不一样了，这就出问题了。这种"等一等"，就是我们要说的阻塞行为。

所以虽然我们很少在 InnoDB 里做表级别的加锁——因为要体现高并发——但 InnoDB 中确实存在表级锁，`MDL` 就是其中之一。

拉回来：InnoDB 很少使用表级的 `S` 锁和 `X` 锁，只有在一些特殊场景下，比如崩溃恢复，才可能用到，而且是手动去加。

### 表级 S 锁与 X 锁的手动加解锁

通常用表级 `S` 锁或 `X` 锁的，都是 MyISAM。手动加的写法很简单：

```sql
-- 加表级共享锁（S 锁）
lock tables my_lock read;

-- 加表级排他锁（X 锁）
lock tables my_lock write;

-- 释放表锁
unlock tables;
```

`read` 对应共享锁，`write` 对应排他锁，`unlock tables` 负责释放。这里再说一遍：尽量不要在 InnoDB 里这么用，它厉害的地方是有更细粒度的行锁。不过在 MyISAM 上举的例子，把 `engine` 改成 InnoDB 同样能跑，只是没有必要。

要验证加锁效果，先得能看见锁。查看表上锁的指令是：

```sql
-- 查看所有打开的表
show open tables;

-- 只看正在被使用的表
show open tables where In_use > 0;
```

这条指令里我重点看 `In_use` 字段：它表示这张表正在被使用，也就相当于这张表上有锁。演示之前先查一次，`In_use > 0` 一条都查不出来，说明当时没有任何表被锁住。

演示过程是这样：先建一张 `my_lock` 表，往里插入一条 `id = 1`、`name` 为 `A` 的数据，两个会话都能正常查到。然后加表级 `S` 锁：

```sql
lock tables my_lock read;
```

再查 `In_use > 0`，这张表的 `In_use` 就变成 1 了，说明表级 `S` 锁加上去了。接着释放：

```sql
unlock tables;
```

再查 `In_use > 0` 就没有了。把 `read` 换成 `write`，同样先看到 `In_use` 变成 1，再 `unlock tables` 又回到 0。这是最基本的加锁、查看、释放三步。

### 表级 S 锁与 X 锁的行为验证

这两种锁加下去，自己会怎样、别人会怎样？验证大纲先钉在这里：自己可读吗？自己可写吗？自己能操作其他表吗？他人可读吗？他人可写吗？我们一条条来看。

#### 加表级 S 锁（读锁）的行为

先加读锁，`begin` 与否都没关系，因为我们锁的是整张表。加完之后逐条验证：

```sql
-- 自己可读吗
select * from my_lock;

-- 自己可写吗
update my_lock set name = 'a1' where id = 1;

-- 自己能操作其他表吗
select * from account;
```

自己可以读，这一条是"是"。自己想写就不行了——这条 `update` 不会执行，换成 `insert` 同样是"否"。自己能操作其他表吗？也不行，连 `select * from account;` 都会被拒绝，因为我们没有锁定它。所以表锁不只挡别人，也把自己挡在别的表外面。

再看他人，也就是另一个会话代表的另一个事务。他人可读吗？

```sql
select * from my_lock;
```

可以读。他人可写吗？否：

```sql
update my_lock set name = 'a2' where id = 1;
```

这条语句会一直等待，也就是阻塞住了，必须等到我们把表锁释放掉才能写。我 `unlock tables;` 之后，这条 `update` 才执行成功，再查一次，`name` 已经变成 `a2` 了。

```text
会话150：lock tables my_lock read;
        ├─ 自己 select * from my_lock        → 可以
        ├─ 自己 update my_lock set name='a1'  → 不可以
        └─ 自己 select * from account        → 不可以（其他表也挡住了）
另一个会话：
        ├─ select * from my_lock             → 可以
        └─ update my_lock set name='a2'      → 阻塞等待
              ▲
              └─ 直到会话150执行 unlock tables; 才成功，查到的 name 变成 a2
```

读图说明：加读锁之后，自己可读、自己不可写、也不能访问别的表；别人可以读，但写会一直阻塞到锁被释放。

读跟读这种行为不会对数据产生并发问题，所以放行；但写不行，因为表已经被锁住了。

#### 加表级 X 锁（写锁）的行为

换成写锁：

```sql
lock tables my_lock write;
```

查一下 `In_use`，表上已经有锁了，这时候加的是一把排他锁。继续逐条验证：

```sql
-- 自己可读吗
select * from my_lock;

-- 自己可写吗
update my_lock set name = 'a3' where id = 1;

-- 自己能操作其他表吗
select * from account;
```

自己可读，是。自己可写吗？这也是"是"，上面那条 `update` 直接就能执行成功。自己能操作其他表吗？否，`select * from account;` 照样不让。

他人的情况就全都要等了：

```sql
-- 他人可读吗
select * from my_lock;

-- 他人可写吗
update my_lock set name = 'a5' where id = 1;
```

他人可读吗？得等。你想，这已经是一把排他锁了，别人还想读，那不就有并发问题了吗，所以都得等。他人可写吗？可写也得等，另外那个会话里的 `update` 同样阻塞在那里。

```text
会话150：lock tables my_lock write;
        ├─ 自己 select * from my_lock        → 可以
        ├─ 自己 update my_lock set name='a3'  → 可以
        └─ 自己 select * from account        → 不可以
另一个会话：
        ├─ select * from my_lock             → 阻塞等待
        └─ update my_lock set name='a5'      → 阻塞等待
              ▲
              └─ 都要等会话150执行 unlock tables; 之后才继续
```

读图说明：换成写锁之后，自己读写都放开，但依然不能操作其他表；别人读和写全部阻塞。

那么别人能读别的表吗？毫无疑问可以，跟你这张表没关系，愿意读就读，关键是看别的表上有没有读锁和写锁。

验证完把锁释放掉：

```sql
unlock tables;
```

再 `show open tables where In_use > 0;`，已经回零了。

两种锁的行为汇总成一张表：

| 当前表的锁 | 自己可读 | 自己可写 | 自己能操作其他表 | 他人可读 | 他人可写 |
| --- | --- | --- | --- | --- | --- |
| 表级 `S` 锁（`lock tables ... read`） | 是 | 否 | 否 | 是 | 否（阻塞等待释放） |
| 表级 `X` 锁（`lock tables ... write`） | 是 | 是 | 否 | 否（阻塞等待释放） | 否（阻塞等待释放） |

> **易错点**：`lock tables` 之后，同一个会话里访问没有被锁定的表也会被拒绝。这一点跟"只影响别人"的直觉正好相反。

### MyISAM 的表级加锁策略

演示完再回到引擎层面看一遍。MyISAM 存储引擎在我们查询的时候，加的就是读锁，表级别的读锁；在进行增删改操作的时候，给表级别加的叫写锁。而 InnoDB 通常不会在表级别做这两个设置，因为它有粒度更低的行锁去处理。

MySQL 中表级锁的模式，我们是以 MyISAM 这张表来演示的：有表级的共享锁，也有表级的独占锁，一个是 `S`，一个是 `X`，它们的行为刚才已经验证清楚了。

> **提示**：上面这套演示，把 `engine` 换成 InnoDB 去测也没问题，只不过实际开发中我们很少这样做。

### 意向锁要解决的问题

第二种表级锁叫意向锁，注意它也是表级别的。

前面讲表级的 `S` 锁和 `X` 锁时说过，不建议在 InnoDB 中加表级的共享锁或排他锁，因为性能低一些；MyISAM 不支持行级锁，所以在 MyISAM 里只能这么做。但 InnoDB 中还是有表锁的：一个是刚才提到的 `MDL`，它因为针对 DDL 行为、对整个表结构产生了影响，粒度大一点可以理解；另一个就是意向锁。

这时候大家会想：InnoDB 明明支持行锁，你又整出一个意向锁，也是表级锁，那这个意向锁到底干什么用？会不会导致我们的并发性变低？

> **结论**：不会。InnoDB 允许行级锁和表级锁共存。有了这一句，你就能体会到它并不会使性能变低——不会因为表上加了一个意向锁，行级锁就加不上了，两者可以共存，也可以说能共生。

反过来讲，正因为表级别的意向锁存在，接下来那些判断锁的行为，性能反而会更高。

#### 表级加锁判断的逐行扫描开销

看一个需求。这里有两个事务，T1 和 T2，T2 想在表级别加一把共享锁，或者加一把排他锁。能不能加？得看这张表上之前有没有其他事务加过锁——表级别的也好，某一行上的也好。

举个例子：T1 针对表中的某一行数据加了一把 `X` 锁。T2 现在想给整张表加一把表级 `X` 锁，肯定加不了，会阻塞，因为这条记录上已经加锁了。

问题是，对于机器来讲，它怎么知道到底加没加？如果这张表有 10 万条数据，而我们只在其中一条上加了 `X` 锁，那么 T2 要判断能不能加表级 `X` 锁的时候，难道要一行一行地把表里的数据遍历一遍，去看有没有 `X` 锁的出现？这个性能是不是特别差？显然特别差，一个一个判断能把人累死。

#### 行锁对应的表级意向锁

办法就是意向锁。当我们针对某一行数据加了 `X` 锁之后，数据库会自动在这一行记录的上一层——你可以理解成页级锁，也可以理解成表级锁，我们这里就以表级为例——加一把锁：因为你在行上加的是 `X` 锁，所以自动加一把**意向的 `X` 锁**。

也就是说，针对这一行记录加一把 `X` 锁，实际上出现了两把锁：一把是行本身的 `X` 锁，另一把是自动补上的表级意向锁。

接下来 T2 想加全表排他锁的时候，就不用一条条记录去找有没有 `X` 锁了，直接看表级：已经有意向排他锁存在。既然存在，这次添加就直接阻塞，根本用不着一行行比较。这就是它让性能更好的地方。

> **结论**：如果我们给某一行的数据加上了排他锁，数据库会自动给更大一级别的空间（比如数据页或者数据表）加上意向锁，告诉其他人这个数据页或这张表中已经有人上过排他锁了。其他人想要针对这个表加排他锁，就需要阻塞。

```text
T1：select ... for update（命中 id = 6 这一行）
        ├─ 行级：排他锁 X  on  id = 6      ← 自己主动加
        └─ 表级：意向排他锁 IX              ← 自动补上

T2：lock tables teacher read / write;
        │
        ▼
   只需要看表级有没有意向锁，不必逐行扫描
        │
        ├─ 表级已有 IX ──► IX 与表级 X、表级 S 都冲突 ──► 阻塞等待
        └─ T1 commit 之后，行级 X 与表级 IX 一起释放 ──► T2 加锁成功
```

读图说明：行级的 `X` 锁会自动带出一把表级 `IX`，别人想加表级锁时只查表级这一层就能判定冲突，省掉了对整个表的逐行检查。

### 意向共享锁与意向排他锁的生成方式

意向锁具体分成两种表级锁：意向共享锁（Intention Shared Lock，`IS`）和意向排他锁（Intention Exclusive Lock，`IX`）。

如果我们要获取数据表中某些记录的共享锁，就会在这个数据表上添加意向共享锁；如果要获取某些记录的排他锁，就会添加意向排他锁。共享的对应共享的，排他的对应排他的。

> **提示**：这里的添加是自动的，不需要我们手动维护。你自己针对某一行或某几行想加什么锁就加，加完之后，表级别会自动生成相应的意向锁。

落到语句上就是我们熟悉的两个后缀：

```sql
-- 查询语句后加 lock in share mode：涉及的行加 S 锁，表级自动加 IS
select * from teacher where id = 6 lock in share mode;

-- 查询语句后加 for update：涉及的行加 X 锁，表级自动加 IX
select * from teacher where id = 6 for update;
```

`lock in share mode` 会获取一个 `IS` 锁：它首先针对语句涉及到的数据加 `S` 锁——比如涉及到三行，那这三行都加上 `S` 锁——同时自动帮我们补一个意向共享锁。`for update` 加的是 `X` 锁：如果不是全表，就针对这几条记录加排他锁，然后 InnoDB 自动帮我们加上表级别的意向排他锁。

### 意向锁的兼容性验证

先准备一张 `teacher` 表，字段是 `id` 和 `name`，往里插入 6 条记录。两个会话都能查到数据。隔离级别不用改，就是默认的 `repeatable read`（可重复读），我们在这个级别下演示。

这里的操作跟前面表级锁的演示不一样了：前面是不 `begin`、直接锁整张表；现在针对的是某一行或某几行加 `S` 锁或 `X` 锁，所以要在事务里体现，得先 `begin`。

#### 表级 S 锁被 IX 阻塞的场景

第一个会话里开启事务，然后执行：

```sql
begin;

select * from teacher where id = 6 for update;
```

这条语句下去会有两把锁出现：`id = 6` 这一行上的 `X` 锁是我主动加的，表级上的意向排他锁是自动补的。当前事务还没有结束。

换到另一个会话，也开启事务，然后想给整张 `teacher` 表加表级锁：

```sql
begin;

lock tables teacher read;
```

你觉得会阻塞吗？会的，直接卡住了。

原因在于：想给这张表加表级 `S` 锁，就要求执行之前，其他事务没有针对这张表加过表级 `X` 锁，记录上也没有加过 `X` 锁。这两个场景要分开看——表级的好判断，看一眼表上有没有锁就知道了；难办的是记录上的那一种，记录一多，一个个去判断性能极低。

而这时候的现场是：第一条语句在给这行数据加 `X` 锁之后，已经自动在表级补了一把 `IX`。那么表级 `S` 锁和 `IX` 冲突不冲突？

> **结论**：冲突。表级 `S` 锁与 `IX` 互斥，所以这里阻塞。加表级 `X` 锁也是一样的结果，`IX` 跟表级 `X`、表级 `S` 都互斥。反过来说，如果其他事务加的只是表级 `S` 锁，那就不冲突——`S` 跟 `S` 是兼容的。

锁要释放掉，阻塞的那条语句才能继续。让第一个会话提交：

```sql
commit;
```

事务一提交，作用在这行数据上的 `X` 锁就释放了，相应的表级 `IX` 也就跟着释放，另一边的 `lock tables` 立刻就加锁成功。演示完记得解锁：

```sql
unlock tables;
```

#### 不同数据行上行锁与意向锁的共存

还有一个点要提：意向共享锁、意向排他锁与其他意向锁之间的兼容性。你会看到表级的这几把锁之间居然是兼容的，这能理解吗？为什么兼容？

关键在这里：**意向锁虽然是表级别的，但它刻画的其实是某一行或某几行的实际情况。**

举例。第一个会话 `begin` 之后，`select * from teacher where id = 6 for update;`——`id = 6` 这一行有 `X` 锁，表级别有一个 `IX`。

第二个会话也 `begin`，然后针对同一条记录 `id = 6` 也用 `for update`：

```sql
select * from teacher where id = 6 for update;
```

你觉得这个事靠谱吗？走起，不靠谱，阻塞了。但这次的阻塞**不是** `IX` 跟 `IX` 造成的——这两个 `IX` 是无辜的，它俩并不冲突——真正的原因是前面那把行级别的 `X` 锁和你这把行级别的 `X` 锁不兼容：同一行上不能同时存在两把排他锁。

把 `6` 改成 `5`，再去走一次：

```sql
select * from teacher where id = 5 for update;
```

这时候就没事了。为什么？`id = 5` 这一行加的是 `X` 锁，`id = 6` 那一行加的也是 `X` 锁，两把 `X` 锁落在不同的数据行上，彼此没有冲突；它们各自带出来的表级 `IX` 之间同样没有冲突。两个条件都满足，所以能共存。

> **易错点**：如果 `IX` 之间互斥，那就麻烦了。那意味着只要表里有一把行级 `X` 锁，别的会话就再也加不上任何行锁——行级锁被硬生生拉成了表级锁，InnoDB 的优良特性一下子就被干没了。所以意向锁之间必须是兼容的。

### 意向锁的兼容关系与作用定位

把上面的结论汇总成一张表，行是请求加的锁，列是表上已经存在的锁：

| 请求加锁 ＼ 已有锁 | `X` | `IX` | `S` | `IS` |
| --- | --- | --- | --- | --- |
| `X` | 冲突 | 冲突 | 冲突 | 冲突 |
| `IX` | 冲突 | 兼容 | 冲突 | 兼容 |
| `S` | 冲突 | 冲突 | 兼容 | 兼容 |
| `IS` | 冲突 | 兼容 | 兼容 | 兼容 |

读表说明：意向锁之间（`IS` 与 `IS`、`IS` 与 `IX`、`IX` 与 `IX`）全部兼容；`IS` 除了与表级 `X` 锁冲突之外，跟表级 `S`、`IX` 都兼容；`IX` 与表级 `S`、表级 `X` 都冲突；表级 `X` 跟谁都冲突，表级 `S` 与表级 `S` 之间兼容。

> **结论**：InnoDB 支持多粒度锁，在特定场景下行级锁和表级锁可以共存。这里的表级锁就是意向锁——意向锁之间不排斥；`IS` 与表级 `S` 锁兼容；`IX` 与表级共享锁互斥；意向锁与表级 `X` 锁互斥；而意向锁不会与行级锁发生冲突，只会与表级锁发生冲突。有了它，才在保证并发性的前提下实现了行级锁和表级锁的共存，并且满足事务隔离性的要求。

回到最根本的一句话：意向锁的出现，不管是意向共享锁还是意向排他锁，都是为了协调行锁和表锁的关系。行锁跟表锁之间存在 `S`、`X` 之间的阻塞情况，而为了避免表锁要一行行去判断行锁，我们在表级别生成了与行锁对应的意向锁，让"能不能同时访问"这个判断变得非常方便。这就是它的全部作用。

## 176-表锁之自增锁、元数据锁
> 对应分集：P176 | 原始标题：《176-表锁之自增锁、元数据锁》

表级锁讲到这里，前面我们已经过了表级的 S 锁与 X 锁、意向锁，接着还剩两把：一个是自增锁，一个是元数据锁。先说自增锁（AUTO-INC Lock）。

为什么从完整性上讲还得把它讲一遍？因为我们设计一张表的时候，针对主键，在实际业务当中那些非核心的表，确实可以用 `AUTO_INCREMENT` 这种方式给主键设置值，让它自增长——我们实际创建表的时候就会这么干。基于这一点，这把锁值得说清楚。不过先给你们一个整体定位：这个锁大家整体上作为一个了解就可以了，知道确实有这么一个表级别的锁就行。

---

### 自增锁要解决的问题

#### 自增主键的赋值行为

先看演示用的这张表，表里 `id` 这个字段是 `AUTO_INCREMENT` 的，没问题。我们往表里添加数据的时候，就可以把主键"过滤掉"——只考虑 `name` 这个字段的赋值，`id` 字段它会自动帮我们做赋值的行为。

```sql
-- 演示表以 t_autoinc 代称：主键 id 自增，另有 name 字段
INSERT INTO t_autoinc (name) VALUES ('Tom');
```

这个大家都理解：不给主键值，MySQL 自己补上。真正的看点在于，这个"自动赋值"的行为放到并发场景下会变成什么样子。

#### 并发插入对自增取值的要求

如果多个不同的事务都去做 `INSERT`，我们要保证 `id` 这个字段赋的值首先必须是唯一的；此外，最好还是单调递增的，因为顺序递增的取值对我们生成 B+ 树的结构是有好处的。

这个时候就涉及这个字段上面的一把锁了，也就是我们要讲的自增锁。它并不是针对某一特定行数据起作用，而是针对整张表起作用，所以它是一把**表级**的自增锁。

> **定义**：自增锁（AUTO-INC Lock）是向包含 `AUTO_INCREMENT` 列的表插入数据时需要获取的一种特殊表级锁。一个事务持有自增锁期间，其他事务的插入语句都要被阻塞。

阻塞别人不是目的，目的是防止出现非 unique 的场景——谁拿到锁谁就来操作。代价也很直接：当我们向一个带 `AUTO_INCREMENT` 主键的表插入值时，**每一条插入语句都要对这把表锁进行竞争**，所以并发性是比较低的。既然并发性低，我们就可以设置不同的锁定机制，在一定程度上把并发性提上来。而在讲这三种机制之前，先要明确插入数据的三种模式。

### 插入数据的三种模式

有同学说："这个原来没想过。"其实插入数据可以归结为三种模式：简单的插入、批量的插入，以及混合的模式。它们之所以要拆成三种，关键差别只有一个——**这条语句在开始执行之前，到底知不知道要插入多少行**。

#### 简单插入

简单插入（simple inserts）就是我们最常用的 `INSERT ... VALUES`。不管你是这样一条一条记录地写 `VALUES`，还是在一个 `VALUES` 后面写上多条记录，都算这种简单的插入。

```sql
INSERT INTO t_autoinc (name) VALUES ('Tom');
INSERT INTO t_autoinc (name) VALUES ('Tom'), ('Jerry');
```

为什么它要单独成一类？因为在这种 SQL 语句当中，你是能够明确看到要插入的行数的：上面第二条语句一看就知道插入两条数据。如果之前也没有插入过数据，那么 `AUTO_INCREMENT` 就默认从头部开始，相当于这里赋的 ID 就是一个 1、一个 2；退一步说，至少你知道它需要占用两个 ID 的值。**要占多少个自增值，事先是知道的**，这个信息后面非常关键。

#### 批量插入

批量的插入（bulk inserts）对应的是 `INSERT ... SELECT ...`，也就是上一篇讲过的"基于现有的表我们去添加数据"的那种行为。

```sql
INSERT INTO t_autoinc (name)
SELECT name FROM other_table WHERE ...;
```

这种写法事先就不知道你要插入的行数了。`INSERT` 到某张表，`SELECT * FROM` 另外一张表，过滤条件你可能还加了，那一开始咱都不知道到底能查出来几条数据，进而也就不知道要往目标表里插几条。所以这一类场景的共同点是：**要插入的行数事先未知**。

#### 混合模式

混合模式（mixed-mode inserts）说的是这种写法：`INSERT INTO` 这张表的时候，我们明确地把 `id` 这个主键写出来，然后 `VALUES` 里面有的情况写了 ID 值，那你就不需要再过来赋了；有的又没有写，没写的就自动给我们赋 ID 值。

```sql
-- 列清单里写明了 id：显式给值的行不再自增，未给值的行仍由自增赋值
INSERT INTO t_autoinc (id, name) VALUES (100, 'Tom'), (NULL, 'Jerry');
```

同一张表、同一条插入语句里两种赋值方式混着用，这都属于混合模式。

### 自增锁的三种锁定模式

针对上面这三种插入模式，自增锁专门负责在给主键赋值时确保取值的全局唯一性。它的行为不是一成不变的，而是由同一个系统变量的取值来切换，一共三种。

> **提示**：这个控制自增锁模式的变量就是 `innodb_autoinc_lock_mode`，取值 `0`、`1`、`2` 分别对应下面三种模式。

#### 传统锁定模式

第一种叫做传统的锁定模式（traditional），对应的是这个变量取值 `0` 的时候。

所谓传统模式，就是我们说的这个 `AUTO-INC` 锁它是表级别的，然后大家都去争抢这把锁。谁拿到了谁就来操作，所以它这个并发能力是比较差的。这是三种模式里最朴素的一种：不管你是简单插入、批量插入还是混合模式，都得排在同一把表级锁后面。

#### 连续锁定模式

当我们把这个变量的值设置为 `1` 的时候，它表示的是连续的锁定模式（consecutive）。这是我们 8.0 之前默认的锁定模式。

它的处理方式要分两种情况看。

批量的插入模式：因为你批量插入的时候，我们也不知道你事先到底要插入多少行，所以它还是需要去抢这把表级锁的，跟传统模式一样。

简单的插入模式就不一样了。因为我已经事先知道你要插入多少条数据了，所以如果这个简单插入对应的那个事务抢到了表级锁，它就会**一次性地申请**这批值——比如我知道这里要插入 10 条记录，我就申请这 10 个值就行了；然后紧接着，它其实就会把这个锁释放掉。

```text
T1 简单插入（已知要插 10 行）
  [ 抢到 AUTO-INC 表锁 ] -> [ 一次性申请 10 个自增值 ] -> [ 立即释放锁 ] -> [ 自己慢慢插入 10 行 ]
                                                                  |
                                                                  v
T2 批量插入（行数未知）                                   [ 这时才能抢到锁 ]
  [ 抢到 AUTO-INC 表锁 ] -> [ 逐个申请自增值并插入 ] -> [ 全部插完才释放 ]
```

读图说明：简单插入只需要把表级锁"握一下"——申请到足够数量的自增值就立刻放手；批量插入要"握一段时间"——它得一个一个地申请、一条一条地插，插完才释放，所以后者会长时间占着这把锁。

锁释放以后，简单插入的那个事务该添加就添加，而其他事务——比如说批量插入——这个时候再拿到这把锁，你去一个一个地加就可以了。它只需要握一下就行，握一下完了以后，你添加呢慢慢加就可以，然后这个锁别人还可以再拿到。

但有一个前提：**你得先握到这把锁**。如果别的、比如批量插入的那个事务正握着 `AUTO-INC` 这把表级锁，你现在虽然只是一个简单的插入，你也得等它把这个锁释放、你拿到锁之后，才能一次性地申请多少个值。这一点大家注意一下。

所以连续锁定模式在一定程度上比传统模式的并发性能好一点，但整体上还差意思。

#### 交叉锁定模式

在 8.0 当中又引入了一个叫交叉的锁定模式（interleaved），也就是这个变量取值为 `2` 的场景。

这个模式下，所有的 `INSERT` 语句都不会再使用表级的 `AUTO-INC` 锁了，这时候并发性就大大提升了。

那它靠什么保证正确性？我们整个需要保证的其实就两点：主键这个值首先得是唯一的，然后最好呢是单调递增的。至于说中间会不会是连续的，其实我们并不关注。

- 在简单插入模式下，它其实是可以保证取值连续的，没有间隙。
- 而混合模式、批量插入这两种模式，都有可能存在间隙。

> **易错点**：间隙不是"少赋了值"，而是同一批插入里自增值可能被其他事务的取值穿插开。它在单机上看不出问题，但在主从复制时会出事——`binlog` 文件当中涉及的主键值可能出现不安全的问题。

任何事物有利有弊：交叉锁定模式的优点就是提高了我们插入数据的并发性，并发度高了，代价就是刚才说的取值连续性松动带来的复制安全问题。

把这三种模式放在一起对比，差异都集中在"还抢不抢那把表级锁"上：

| 取值 | 模式 | 领值与持锁方式 | 并发性 |
| --- | --- | --- | --- |
| `0` | 传统锁定模式 | 所有插入都竞争表级 `AUTO-INC` 锁，谁拿到谁操作 | 比较差 |
| `1` | 连续锁定模式 | 批量插入仍抢表级锁并握一段时间；简单插入拿到锁后一次性申请 N 个值并立即释放 | 比 `0` 好一点，整体仍不够 |
| `2` | 交叉锁定模式 | 所有 `INSERT` 都不再使用表级 `AUTO-INC` 锁 | 大大提升 |

到这里，表级别的 `AUTO-INC` 锁就讲完了。它作为一个了解即可，你只要记住：它确实是一把表级别的锁。

### 元数据锁与 InnoDB 的表级锁

#### InnoDB 中依然存在的表级锁

接着来看表级锁的最后一个，叫做元数据锁，这个我们在最开始讲表锁的时候其实已经提到过。

泛泛来讲，虽然我们说 InnoDB 支持行级锁了，那是不是说 InnoDB 里面表锁就没有了呢？事实情况你会发现：除了我们提到的第一个表级别的 S 锁和 X 锁之外，InnoDB 当中的意向锁、自增锁、元数据锁其实都是存在的。

我们平时说 MyISAM 跟 InnoDB 一个支持表级锁、一个支持行级锁，主要区别其实在于第一个——也就是表级的 S 锁和 X 锁。这一点大家注意一下。

#### MDL 的读写锁与兼容性

元数据锁存在的场景，我们在最开始也提到过：当我们对一个表进行增删改查操作的时候，如果另外一个事务、或者说另外一个线程，对这个表的表结构进行了变更——比如增加了一列，或者少了一列——那么这时候我们查询这个操作就会对不上，查出来的数据跟表结构对不上，这时候可能就会出错了。

说白了，另外一个线程对表结构的修改，相当于是一整个表级别的修改，那自然会影响到其他增删改查操作。怎么办呢？

- 你要做增删改查操作的时候，我们会给你加上一个 `MDL` 的**读锁**；
- 你要对表结构进行变更的时候，`ALTER` 也好、`DROP` 也好，都会加一个 `MDL` 的**写锁**。

> **定义**：元数据锁（Metadata Lock，MDL）是 MySQL 用来保护表结构不被并发修改破坏的表级锁：普通增删改查持 MDL 读锁，表结构变更持 MDL 写锁。

这两种锁的兼容关系是：读锁跟读锁之间不互斥，可以两个同时去读，这是没问题的；但是只要有写锁存在，那就不能去读，别的这个事务也不能再去写。

| 已持有 \ 新请求 | MDL 读锁 | MDL 写锁 |
| --- | --- | --- |
| MDL 读锁 | 兼容，可并发 | 冲突，阻塞 |
| MDL 写锁 | 冲突，阻塞 | 冲突，阻塞 |

> **易错点**：这里我仅针对 `MDL` 来谈。有同学要问：你刚才提到对表进行增删改查操作加的是读锁，那我另外又有一个增删改查、也是个读锁，这两个能共存，不是说增删改不能同时执行吗？注意，我们是从 `MDL` 这个锁的级别来谈的，读锁跟读锁之间是可以不互斥的。至于说真正增删改的时候，你跟另外一个增删改不能同时执行、处于阻塞状态，那不是因为我们这个锁导致的，而是因为你相应的行级别的 `X` 锁和 `S` 锁导致的。

另外一点：这个锁也不需要我们显式地去添加，只要你做操作，它会自动帮我们加上。

### MDL 阻塞的两个现场

#### 持读锁执行 ALTER 的阻塞与验证

回过来我们做演示，还是针对 `teacher` 这样一张表。首先开启一个事务，然后查一下这张表里的记录：

```sql
BEGIN;
SELECT * FROM teacher;   -- 自动加上 MDL 读锁，事务不提交则读锁一直被持有
```

这就相当于我们查询表中的记录数，这个没有问题。但注意，这条查询已经自动拿到了 `MDL` 的读锁，而事务还没提交，这把读锁就一直被它握着。

接着另开一个会话，做这样的操作：

```sql
ALTER TABLE teacher ADD age INT;
```

比如我们给 `teacher` 表加一个 `age` 字段，`int` 类型。回车之后你会发现，它此时就阻塞在这儿了。为什么？因为此时你要加上一个 `MDL` 的写锁，而我们前面已经有一个 `MDL` 的读锁了，这个读锁是自动给我们加的，读写之间这时候就冲突了，过不去——就是我们说的这样一个场景。

那有同学会想："是由于刚才说的这个 `MDL` 锁造成的吗？"好，在另外的一个会话当中，我们可以使用一个指令来验证：

```sql
SHOW PROCESSLIST;
```

在这个指令的结果当中，我们就能看到当前那条 `ALTER TABLE` 语句的状态是 `Waiting for table metadata lock`——这不就是 `MDL` 吗？看得非常清楚。这样一个场景就说清楚了。

#### 写锁排队对后续读锁的阻塞

再说一个事。我们刚才提到，如果不存在"写"这种行为，我们要是再开一个"读"，是不是没有问题啊？我们来演示一下。

先把前面那条 `ALTER TABLE` 停掉，再把它的事务提交、复原，然后在这边重新开启一个事务，也去查这张表：

```sql
BEGIN;
SELECT * FROM teacher;   -- 又一个 MDL 读锁
```

大家看到，这时候相当于又加了一个 `MDL` 读锁，这两条都是 `MDL` 读锁，它俩是没问题的，读跟读之间是可以并发执行的。

注意看接下来的关键操作。在我们当前这个 `MDL` 读锁**没有释放**的情况下，我再把 `ALTER TABLE` 加上：

```sql
ALTER TABLE teacher ADD age INT;   -- 需要 MDL 写锁，依然阻塞
```

是不是仍然是一个阻塞状态？这个清楚。那么在这个阻塞的场景下，你再看，我在另外的一个事务里再去 `BEGIN`，然后执行刚才的 `SELECT * FROM teacher;`——结果这条读也阻塞了。

```text
[会话 A] BEGIN; SELECT * FROM teacher;
         └─ 自动加 MDL 读锁，事务不提交 -> 读锁一直被持有
[会话 B] ALTER TABLE teacher ADD age INT;
         └─ 需要 MDL 写锁 -> 与 A 的读锁冲突 -> 阻塞（Waiting for table metadata lock）
[会话 C] BEGIN; SELECT * FROM teacher;
         └─ 需要 MDL 读锁 -> 本与 A 的读锁兼容，但要排在 B 的写锁之后 -> 也阻塞
```

读图说明：A 的读锁照旧持有，B 的写锁卡在 A 后面等待，C 的新读锁虽然与 A 的读锁兼容，却必须排在 B 的写锁之后，于是本来可以并发的两个读，现在都过不去了。

本来如果只有两个 `MDL` 读锁的话，我们是可以并发执行的；但是因为这里已经有了一个 `MDL` 读锁，你又加了个写锁，由于这个写锁的出现，我们就阻塞了；现在你又加了个读锁，这个读锁跟已有读锁本来可以并发执行，可它跟那个 `MDL` 写锁冲突——因为写锁的出现，导致我们现在这个读也阻塞了。这就是 `MDL` 在并发上的问题：此时两个"读"的行为已经不能够并发执行，降低了我们并发的性能。

> **结论**：MDL 写锁一旦进入等待队列，后续的读锁都要排在它后面，哪怕这些读锁彼此之间本来是兼容的。所以在有长事务（持读锁迟迟不提交）的情况下，一次表结构变更就能把整张表上的后续访问一起堵住。这个场景大家要注意一下。

演示到这里，把该停的都停掉、该提交的做一次 `COMMIT` 复原，方便后边做测试。这就是 `MDL`——表级别锁里的最后一个。

## 177-行锁之记录锁、间隙锁
> 对应分集：P177 | 原始标题：《177-行锁之记录锁、间隙锁》

行锁是我们讲到的所有粒度当中最小的那种锁——已经细到行级别了，再往下没有了。之所以要先把范围说清楚：MyISAM 不支持行锁，所以接下来讲的行锁，全部是针对 InnoDB 的。行锁还有个名字叫**记录锁**（Record Lock），因为一行数据本来就是一个记录，锁住表里的一行数据，就是锁住一条记录。

我们前面把表级别的 S 锁、X 锁摸清楚之后，行级别的这套规则其实并不难——难的是间隙锁，它是为幻读专门造出来的东西，理解它为什么要存在，比记住它的行为更重要。最后还有一件必须提前知道的事：行级锁层面是会出现死锁的。

### 行锁的定位、优点与代价

行锁是在存储引擎层实现的。它的加锁对象是表里的一行记录，粒度比表锁小了整整一个数量级，这一点直接决定了它的优缺点。

先看好的一面：粒度更细、更小，所以能实现的并发度更高，锁冲突的概率更低。举个例子最直观：我的事务访问的是这条记录，你的另一个事务访问的是另外一条记录，咱们各自在自己的记录上加锁，互相不影响，也不会冲突。表锁做不到这一点——一张表上只要有人加了写锁，别人连另一行都碰不了。

代价也来自同一个原因。粒度小，意味着同样一笔业务要维护的锁可能更多，而维护任何一把锁都是有开销的：锁的数量上去了，加锁就更慢，开销就更大。还有一条是我们必须重点关注的——**行锁还会出现死锁问题**。

> **结论**：InnoDB 与 MyISAM 的主要区别有两个，一个是事务，一个是行级锁。

把行锁和表锁放在一起对比：

| 对比项 | 表锁 | 行锁（记录锁） |
| --- | --- | --- |
| 加锁对象 | 整张表 | 表里的一行记录 |
| 支持引擎 | MyISAM、InnoDB 都支持 | 只有 InnoDB |
| 锁粒度 | 大 | 最小 |
| 并发度 | 低，锁冲突概率高 | 高，锁冲突概率低 |
| 锁开销 | 相对小 | 相对大，加锁更慢 |
| 死锁 | 不会出现 | 可能出现 |

### 演示环境与记录间隙分布

要讲清记录锁和间隙锁，得先有一张记录分布合适的表。这次的演示表还是 `student`，建在当前这个 `atguigudb3` 库下面——没记错的话，这个库里本来就有这张表，而且数据量还挺大，有 100 万条，光是 `select count(*) from student` 一下都要等上一会儿。旧数据用不上，直接删掉：

```sql
drop table student;
```

删干净之后按演示的需求把表重新建起来（建表语句是现成的，直接粘过来执行）。这张表有三个字段：`id`、`name`、`class`。接着往表里插入五条记录，这里有个刻意的安排——**让这五条记录的 ID 不连续，中间留出间隙**：

```text
id = 1, 3, 8, 15, 20
```

两个会话各自 `select * from student` 看一下，数据没问题。以后演示加锁，我们就拿这几条记录和它们之间的空档做文章。

```text
数据页上的记录（按 id 升序排列）
   id=1        id=3        id=8        id=15       id=20
    |           |           |           |           |
    +-- gap ----+-- gap ----+-- gap ----+-- gap ----+
       (1,3)       (3,8)      (8,15)     (15,20)
```

读图说明：聚簇索引的叶子节点（数据页）上就这么几条记录，记录与记录之间的空档就是后面间隙锁要管的区间；这个简图已经足够简了，但它把后面所有演示的舞台都画出来了。

### 记录锁（Record Lock）

#### 加锁对象与共享、排他的兼容规则

记录锁顾名思义，是把锁加到具体的一条记录上。比如针对 `id = 8` 这一条记录加一把锁，锁信息里写的是 `not gap`——意思就是我们加的不是下面要讲的间隙锁，就是针对这一条数据本身加的锁。

加锁同样要说清楚是哪种类型：跟我们前面讲表锁时一样，分 S 型（共享型）和 X 型（排他型、独占型）。规则也完全一样：

- 你拿到的是 S 型记录锁，那么其他事务再来拿 S 型记录锁没有任何影响；但不可以再去获取 X 型的记录锁。
- 你拿到的是 X 型记录锁，它是排他性的，其他事务既不能再拿共享型的，也不能再拿排他型的记录锁。

| 已经持有 | 别人再请求 S 记录锁 | 别人再请求 X 记录锁 |
| --- | --- | --- |
| S 记录锁 | 相容，可以拿到 | 冲突，拿不到 |
| X 记录锁 | 冲突，拿不到 | 冲突，拿不到 |

> **结论**：记录锁的互斥只发生在**同一条记录**上。针对不同的记录，各加各的锁，互相不冲突——这就是行级锁并发度高的来源。

#### 记录锁加锁过程的演示

回到会话层面，先开一个事务，然后做一次修改：

```sql
begin;
update student set name = '张三1' where id = 1;
```

把 `id = 1` 这条记录（原来叫张三）改成了张三1。因为增删改都属于写操作，这时候 InnoDB 就给这条记录加了一把 X 型的记录锁，也就是行锁。

现在换到另一个会话，也开一个事务，看看能不能碰到这些记录。关键全在 `where` 条件上：

```sql
begin;
select * from student where id = 2 lock in share mode;
```

`lock in share mode` 加的是 S 型锁，相比 `for update` 要更轻一些。`id = 2` 这条记录表里并不存在，所以这条语句只是能执行——查不出数据而已（把条件换成 `id = 3` 就能查出李四那条记录）。

接着把条件换成 `id = 1`：

```sql
select * from student where id = 1 lock in share mode;
```

这一次走不动了，直接阻塞。原因很清楚：这个位置上加的是 S 型锁，而 `id = 1` 上已经有会话 A 加好的 X 型记录锁，S 与 X 冲突，所以不让执行。按 `Ctrl+C` 把它停掉，事务还没有结束，接着往下试。

```sql
update student set name = '李四1' where id = 3;
```

这条**直接成功了**。它加的仍然是 X 型锁，但这把锁是针对 `id = 3` 加的，跟会话 A 手里的 `id = 1` 不是同一条记录，所以不冲突——这就是前面说的行级别并发性。反过来，把条件改回 `id = 1`（同样只是改 `name`），再执行就不行了：同一条记录上已经有一把 X 型锁，你再加一把 X 型锁，必然被挡住。

最后在会话 A 里 `commit;`，事务结束，`id = 1` 这条记录上的 X 型记录锁就被释放了。这时会话 B 那条被挡住的操作立刻执行成功，再 `select * from student` 查看，`id = 1` 这条记录的 `name` 已经是改过之后的值。

> **提示**：记录锁这一节整体难度不大。它无非是把前面表级 S 锁、X 锁的规则原样搬到了记录这一层：不同记录之间互不冲突，同一条记录上就按 S/X 的规则来。

### 间隙锁（Gap Lock）

#### 幻读问题与加锁方案的困境

在可重复读（Repeatable Read，RR）隔离级别下，MySQL 能解决幻读问题，这件事我们已经翻来覆去说了好多次了。解决方案有两种：一种是多版本并发控制（Multi-Version Concurrency Control，MVCC），下一章讲；另一种是加锁的方案，也就是这里要讲的。

MVCC 是非常漂亮的解决方案。加锁方案对付脏读、不可重复读也不成问题，因为这两种情况里都有实实在在的记录：脏读针对的是你要修改的那条记录，在它上面加个锁，不让别人访问就行；不可重复读针对的是我正在读的这条数据，加个锁不让别人改就行。它们都能落到一条真实的记录上。

幻读就不一样了，我们当初讲它的时候就说过它有点尴尬：一开始没有记录，别人插进来以后才有记录。你要加锁，加谁呢？它是幻影，没有东西可加，加了个寂寞——没有记录，你就加不了锁。加不了锁，那怎么锁？

思路就是绕开这条不存在的记录，去锁它所在的空档：这就是**间隙锁**（Gap Lock）。它和记录锁的区别也正好在这里——记录锁锁的是那一条数据，间隙锁锁的是那条数据旁边的间隙。

#### 间隙锁的加锁区间与共享排他等价性

拿我们表里的记录来举例：表中有 1、3、8、15、20 这几条记录。现在事务 A 查到了数据，事务 B 想往这表里插记录，比如插 `id` 为 4、5、6、7 的数据，也就是落在 3 和 8 之间的那些值。我们要做的，就是通过加锁的方式让 A 加把锁，不让 B 把这些数据插进来。

怎么加？可以理解成**针对 8 加了一把 gap 锁**。表达的意思就是：3 和 8 之间，注意这是个**开区间**，在这个区间之内不允许插入数据。

```text
   id=1      id=3                       id=8      id=15     id=20
              |                          |
              +===== 开区间 (3, 8) ======+
                 不允许 insert 4、5、6、7
```

读图说明：间隙锁锁的不是 3 也不是 8 这两条记录，而是它们之间那个开区间，区间内的一切插入都被挡住，3 和 8 这两条记录本身不在被锁范围内。

这里还要特别强调：锁住的只是**插入**。gap 锁仅仅是为防止插入幻影记录而生的——不让它插，就不会出现幻影记录，也就避免了幻读这个场景。它的全部价值就在这一条上。

也正因为如此，共享的 gap 锁和独占的 gap 锁其实没有区别。它针对的既不是这条数据的读，也不是这条数据的写，而是区间中间的 insert 行为，行为非常明确，就是 insert。既然目标只可能是插入，那么 S 型的间隙锁和 X 型的间隙锁作用完全相同。

#### 记录锁冲突与间隙锁共存的演示

先把 S 和 X 的冲突复习一遍。会话 A 里：

```sql
begin;
select * from student where id = 8 lock in share mode;
```

`id = 8` 这条记录真实存在，所以查得出来，事务不结束，S 型锁挂在这条记录上。复制到另一个会话，开一个事务，同一句话只把结尾换成 `for update`：

```sql
begin;
select * from student where id = 8 for update;
```

这一次查不出来——一个是 S 型锁，一个是 X 型锁，两者冲突。把这个操作停掉，但事务别结束。回到会话 A，`commit;` 提交，然后重新 `begin;`。

接下来是这次演示的重头戏。语句几乎没变，只做了一个微小的修改：把 `id = 8` 改成 `id = 5`。

```sql
begin;
select * from student where id = 5 lock in share mode;
```

`5` 在这张表里是不存在的——相当于加了一个寂寞。可这一回，执行没问题。再复制到另一个会话，同样把结尾换成 `for update`：

```sql
select * from student where id = 5 for update;
```

你会以为它又要阻塞，结果它**不冲突、不阻塞**。为什么同样的 S 与 X，这次就可以共存了？因为我们加到的锁变了：这一把是间隙锁。前面说了，间隙锁的 S 型和 X 型作用完全相同，所以两把锁都加得上——间隙锁是可以多次加的，也是可以共存的。

那这把间隙锁到底锁了哪一段？看 `5` 落在现有的哪两条记录之间：表里是 1、3、8、15、20，5 明显落在 3 和 8 之间，所以锁住的就是开区间 $(3, 8)$。

现在再开一个会话，往里塞数据：

```sql
begin;
insert into student(id, name, class) values(6, 'Tom', '三班');
```

这条记录插不进去，直接卡在那里——gap 锁起作用了：既然我们还占着这个间隙，就不允许往里面做 `insert`。按 `Ctrl+C` 让它停下来。

再回头看看写值的规律：写 5、写 6、写 7 其实没有任何区别，就看这个字段的值落在哪两个数值之间；落在哪两条记录之间，就把那两条记录之间的空档锁住。所以写 `id = 12` 就落到 8 和 15 之间，开区间 $(8, 15)$ 里的 9、10、11、12、13、14 都不允许插入。

| `where` 里的条件值 | 落在哪两条记录之间 | 被锁住的区间 | 区间内不允许 `insert` 的值 |
| --- | --- | --- | --- |
| `id = 5` | 3 与 8 | $(3, 8)$ | 4、5、6、7 |
| `id = 12` | 8 与 15 | $(8, 15)$ | 9 ~ 14 |
| `id = 25` | 20 之后 | $(20, +\infty)$ | 21 及更大的值 |

> **易错点**：间隙锁锁住的是记录之间的**开区间**，区间两端那两条记录本身不在锁的范围里；判断锁住哪一段，只看条件值落在哪两条现有记录之间，跟这个值本身在不在表中、写的是 5 还是 6、7 都无关。

#### 最大记录之后的区间与 supremum 伪记录

讲到这里自然有人要问：那 20 后边那一段怎么办？下面这段演示就算是自己脑洞出来的场景。先把两个事务都 `commit;` 结束掉，重新开始：

```sql
begin;
select * from student where id = 25 lock in share mode;
```

`25` 在表中同样不存在。它落在哪个范围里？表里最大的值是 20。锁上之后逐个试：插入 21 不允许，插入 22、23 是同样的道理，肯定都不行；再试比最大值还大的 26，照样不行；而试一个 20 之前的 17 就没问题——17 落在 15 和 20 之间，根本不在被锁的区间里。

也就是说，写一个比最大值还大的值，坐落的区间就是从 20 起一直到正无穷，20 成了这个区间的下界。换成 `where id > 20` 这样的写法也一样，体现的就是从 20 到正无穷这个大范围被加上了间隙锁。

把锁信息查出来看一眼，就能看到这件事的落脚点。讲数据页的时候我们说过：一个页里除了这几条记录，前面还有一个 `infimum`，它指向最小的那条记录；而 20 之后指向的是 `supremum`，相当于页里最大值的那条记录。我们写的是 25，它坐落的区间就是大于 20 的那一段，所以这把间隙锁就加在了 `supremum` 这个伪记录上。

```text
infimum -> id=1 -> id=3 -> id=8 -> id=15 -> id=20 -> supremum
                                                          |
                                    间隙锁挂在这里，范围 (20, +∞)
```

读图说明：页内的记录是单向串起来的，`id = 20` 的下一条就是 `supremum` 伪记录；条件值落在最大记录之后时，间隙锁就落在 `supremum` 上，锁住的是 20 之后一直到正无穷的整段空间。演示完把这些事务都提交掉。

### 间隙锁引发的死锁

#### 死锁的形成过程

间隙锁可能引发死锁，这一点必须知道。我们还用 id 为 5 这个例子，两个事务各自开始：

```sql
begin;
select * from student where id = 5 for update;
```

两个事务都执行这句，等于各自在 $(3, 8)$ 上挂了一把间隙锁。因为间隙锁可以共存，两把锁都加上了，谁也影响不到谁。

接下来在第二个事务里做插入：

```sql
insert into student(id, name, class) values(7, 'Jerry', '一班');
```

不能写 3 到 8 这个范围之外的值，就写范围内的 7，结果这条 `insert` 阻塞了——另一个事务手里有 $(3, 8)$ 的间隙锁，不让插。

在这个场景下，回到第一个会话，把同样的插入也执行一遍（写 7 或者写 6 都无所谓，只要在这个范围里）：

```text
ERROR: Deadlock found when trying to get lock; try restarting transaction
```

死锁被发现了，报错信息让我们重启这个事务。这个死锁怎么理解？学过多线程的话应该很熟悉：事务 A 手里有 $(3, 8)$ 的间隙锁，事务 B 手里也有 $(3, 8)$ 的间隙锁；事务 B 的 `insert` 恰好落在 $(3, 8)$ 里，它要等 A 的间隙锁释放；事务 A 的 `insert` 也落在 $(3, 8)$ 里，它要等 B 的间隙锁释放。

```text
事务 A                                    事务 B
  |                                         |
  |--- gap 锁 (3, 8) ---------------------->|  间隙锁可共存，两把都加上
  |                                         |--- gap 锁 (3, 8)
  |                                         |
  |                                         |--- insert id=7
  |                                         |      阻塞：等 A 的 (3,8) 释放
  |--- insert id=6                          |
  |      冲突：等 B 的 (3,8) 释放 <---------|
  |                                         |
  +------------ 互相等待，扣成死结 ---------+
```

读图说明：两个事务各持一把 $(3, 8)$ 间隙锁并各自发起区间内插入，插入又都需要对方的锁先释放，形成环形的等待关系。

要解开这个结，必须让其中一个事务的间隙锁释放，也就是它得先 `commit` 或者 `rollback`；可它正卡在 `insert` 上，根本没法往下执行。它解了它才能解，它解了它才能解——这是一个死扣，两边谁也别想靠自己结束阻塞状态。这就是死锁。

**只要行级锁都有可能死锁**，不是只有间隙锁才会，其它位置的行级锁同样可能出现；表锁是不会出现死锁的。这一点要记牢。

#### MySQL 的死锁检测与处理策略

有意思的现象是：报出死锁的那个事务没有僵在那里，而另一个事务的 `insert` **竟然执行成功了**。这背后是 MySQL 对死锁的处理机制。

默认情况下，死锁之后双方是互相僵持的，但显然不能让它们真正一直僵下去。处理策略有两种：

1. 进入等待状态，直到超时为止，超时之后它们就各自结束了；
2. 做死锁检测，发现死锁以后，主动回滚死锁链条中的某一个事务——主要是挑持有行级排他锁最少的那个事务来回滚，也就是挑成本最低的那个。

对照我们刚才看到的结果就通了：执行成功的那个事务，说明了另一个事务被做了回滚操作；一旦它回滚，$(3, 8)$ 上的间隙锁就释放了，另一个事务的插入自然就能执行成功。

> **结论**：这一讲要抓住两件事——间隙锁的作用是为防止插入幻影记录、避免幻读而生的；行级锁层面会出现死锁，凡是行级锁都可能出现，表锁不会。死锁这块后面还会专门再讲一遍。

## 178-行锁之临键锁与插入意向锁
> 对应分集：P178 | 原始标题：《178-行锁之临键锁与插入意向锁》

### 临键锁的命名与官方定义

接着讲下一种行级锁，叫**临键锁**。光看中文名字，好像完全摸不着头脑；看它的英文 `Next-Key Locks`，好像也好不到哪去，还是看不懂。为什么叫"临键"，从这个名字里完全看不出它具备什么样的特征，总感觉这个命名有点诡异。

不过它本身非常简单，一句话就能说清楚：

> **定义**：临键锁相当于**记录锁**与**间隙锁**的合体，既体现记录锁的作用，又体现间隙锁的作用。

官方给的名称是 `Lock Ordinary`，简称 `Next-Key Lock`，翻译成中文就叫临键锁。

顺着前面讲间隙锁的思路来理解它。给 `3` 和 `8` 之间的范围加一个间隙锁，锁住的其实是 $(3, 8)$ 这个**开区间**，不让别的事务在这里面 `insert` 新的记录——间隙锁影响的就是插入行为。那能不能把这个区间改成一个**闭区间**？

> **易错点**：所谓闭区间，**不是说"允许你插入一条值为 8 的记录"**，也不是"值等于 8 的记录不能被插入"。它指的是：间隙锁影响的仍然是那个开区间，而边界上的这条记录——也就是 `8`——**本身也要被锁住**。

也就是说，`8` 这条记录上已经有了 `X` 锁，你就不要再想着在它上面加 `S` 锁或者 `X` 锁了。

> **结论**：既锁中间这个区间、这个间隙，**又锁住它的边界**，这就相当于临键锁。

官方定义写得更清楚一些：有的时候我们**既想锁住某条记录，又想阻止其他事务在该记录前面的间隙插入新记录**，这个时候用的锁就叫 `Next-Key Locks`。

### 默认隔离级别下的临键锁

临键锁是 InnoDB 在**可重复读（Repeatable Read，RR）** 隔离级别下使用的锁。InnoDB 默认使用的就是 `Next-Key Locks`。

这正好解释了一件事：前面演示记录锁、演示间隙锁的时候，两种效果都能演示出来，就是因为实际用的是临键锁——它兼具了那两种锁的特征。

### 临键锁的构造与效果验证

#### 用一条范围查询构造临键锁

先把前面所有事务都提交掉，不管前面的事务进行到了哪一层，先做一次提交，然后重新开启新的事务。

第一个想法是：把 `8` 这条记录锁住，同时把 `3` 到 `8` 之间的间隙也锁住。写成这样一条语句：

```sql
begin;
select * from student where id <= 8 and id > 3 for update;
```

这里有个关键点：`id` 的条件**不能写成小于 8**，必须写成 `小于等于 8`。因为只有带上等于号，`8` 这个边界值才会被落在 `where` 条件里，从而在它上面加上记录锁；如果写成 `id < 8`，锁的区间就变了。

- 对 `8` 来说，条件里带了等号，相当于在 `8` 这条记录上加了一把记录锁；
- 对 $(3, 8)$ 这个开区间来说，里面没有任何一行满足条件，加上的就是间隙锁。

两者合起来，整体上就构成了一把临键锁。**一条范围查询语句就同时产生了两种锁**：等值命中的那一行上是一把记录锁，两个边界之间的空档上是一把间隙锁——这正是临键锁"合体"的直接体现。换句话说，"锁住某条记录"和"阻止别人在它前面的间隙里插入"这两件事，由一条语句一次完成，不用分别处理。

不过这个例子要换掉：前面已经往表里插入过一条 `id = 7` 的数据，`7` 插进来之后间隙的结构就变了，再用 `3` 到 `8` 这个范围，情况就不太对。改成 `8` 到 `15` 这个范围，效果完全一样。

#### 重新演示：8 到 15 的临键锁

先把表里的数据 `select` 出来看一眼，然后开始：

```sql
begin;
select * from student where id <= 15 and id > 8 for update;
```

这条语句的语义和上面那条完全一致：`id <= 15` 让 `15` 这条记录拿到记录锁，`(8, 15)` 这个开区间拿到间隙锁。锁住之后，到另一个会话里验证。

**验证记录锁**——先确认 `15` 这条数据上已经被加了锁，然后试着去读它：

```sql
begin;
select * from student where id = 15 lock in share mode;
```

这条 `lock in share mode` 请求的是 `S` 锁，回车之后直接阻塞。

> **结论**：对方已经持有 `X` 锁，这边无论请求 `S` 锁还是 `X` 锁都不行——共享的、排他的都白扯。改成 `for update` 更不行，因为对方本来就已经是排他锁了。

这就体现了临键锁里记录锁的那部分作用。

**验证间隙锁**——继续往表里插入一条落在这个范围内的记录：

```sql
insert into student (id, name, class) values (12, 'team', '一班');
```

`12` 在 $(8, 15)$ 这个开区间之内，回车之后同样卡住不动，这就是间隙锁的效果。停止这边的等待，把第一个事务提交掉。

| 验证动作 | 请求的锁 | 结果 | 体现的是临键锁的哪一部分 |
| --- | --- | --- | --- |
| `select ... where id = 15 lock in share mode` | `S` 锁（对边界记录 `15`） | 阻塞 | 记录锁 |
| `select ... where id = 15 for update` | `X` 锁（对边界记录 `15`） | 阻塞 | 记录锁 |
| `insert ... values (12, ...)` | 插入意向锁（针对间隙 `(8, 15)`） | 阻塞 | 间隙锁 |

### 插入意向锁

#### 等待中的插入也需要锁结构

下面看**插入意向锁**，英文叫 `Insert Intention Locks`，`Intention` 就是"意向"的意思。这又是一个什么锁？

回到前面已经出现过的那个场景：当某个间隙上已经有了一把间隙锁时——刚才已经提交了事务，所以现在重新开一个新的事务。先确认一下环境，`12` 那条记录刚才并没有插进去，保险起见先 `select` 一下确认表里的数据。

接着构造一把间隙锁。直接写 `select ... where id = 12` 是不行的，因为**没加锁类型**，所以要先 `begin`，再补上 `for update`：

```sql
begin;
select * from student where id = 12 for update;
```

这条语句锁住的是 `8` 到 `15` 这个范围，也就是在 $(8, 15)$ 上得到了一把间隙锁。

然后在另一个会话里发起插入：

```sql
begin;
insert into student (id, name, class) values (11, 'team', '一班');
```

只要落在这个 `8` 到 `15` 之间，写 `11` 也行、写 `12` 也行，回车之后立刻卡住。这就是前面说的间隙锁的效果。

现在重点来了：这个事务在等待。InnoDB 规定，**事务在等待的时候，也需要在内存中生成一个锁的结构**，用来表明有事务想在某个间隙里插入一条新记录，只不过现在处于等待状态。

> **定义**：等待插入的事务在内存中生成的那个锁结构，表达的就是"我有插入的意图"，所以叫**插入意向锁**。

#### 插入意向锁与意向锁的区别

> **易错点**：插入意向锁**不是一个意向锁**。名字里带着"意向"两个字，但它跟意向锁是两回事。意向锁是**表级锁**；而插入意向锁是针对具体的这几行数据做的行为，它是一把 **`gap` 锁**，属于**行级锁**。这一点一定要小心区分。

#### 引入插入意向锁的目的

为什么等待的时候还要专门引入这么一个锁结构？道理在于：**一旦左边那把间隙锁释放掉，这个插入意向锁就有机会进入执行状态**，等待中的 `insert` 操作就能真正执行下去。这就是它存在的意义。

#### 两个插入意向锁之间的关系

再换一个场景：两个事务同时在同一个间隙上等待插入，这两个插入意向锁之间是什么关系——互相影响吗？互相阻塞吗？兼容还是不兼容？

先把等待中的插入留在那里，回到另一个会话，同样 `begin`，把 `insert` 语句复制过来执行，结果同样是阻塞，同样产生一个插入意向锁。再到第三个会话里，`commit` 之后 `begin`，把 `insert` 也粘过来，只改一下具体的值：

```sql
begin;
insert into student (id, name, class) values (12, 'team', '一班');
```

`12` 同样落在 $(8, 15)$ 这个间隙锁的范围之内，回车之后还是阻塞，还是插入意向锁——两者都受到同一把间隙锁的影响。

> **结论**：这两个插入意向锁是**兼容**的，因为**它们要插入的具体值不一样**——一个是 `11`，一个是 `12`。一旦持锁的那个事务提交、间隙锁释放，它们就都可以正常执行下去。

提交之后可以看到，等待的插入确实都成功执行了。也就是说，**阻塞它们的自始至终是那把间隙锁，而不是彼此**：间隙锁在，两个都等着；间隙锁一释放，两个都放行。这里因为提交得比较晚，其中一个连接已经超时，但只要能落在允许的时间范围内，结果就是两个都执行成功。

整个过程的锁结构可以用下面这张图表示：

```text
记录         5        8        11  12          15
                   |         ^    ^           |
                   |         |    |           |
              [ 事务1：间隙锁 (8,15) ]         |
                   |         |    |           |
                   |    事务2:插入意向(11)  事务3:插入意向(12)
                   |         |    |           |
                   |      等待 |    | 等待      |
                   |         |    |           |
           事务1 COMMIT → 间隙锁释放           |
                   |         |    |           |
                   +---------+----+-----------+
                             |    |
                         授权执行 授权执行
```

读图说明：事务 1 先对 `8` 到 `15` 的间隙加了间隙锁，事务 2 想插入 `11`、事务 3 想插入 `12`，两者都在内存里生成了插入意向锁并处于等待；它们要插入的具体值不同，所以彼此不冲突，事务 1 一提交、间隙锁一释放，两个插入意向锁就都能获得授权。

#### 兼容性规则

关于兼容性，官方也提到：**插入意向锁并不会阻止别的事务继续获取该记录上的任何类型的锁。** 这句话其实不用去死记硬背，只要能判断出"它们应该是矛盾的"还是"应该是不矛盾的"就够了。

为什么可以这么判断？因为这些锁结构都是**人设计出来的**。`id` 是 `11`、`id` 是 `12`，你会觉得这两个插入会冲突吗？显然不会。既然设计这套结构的也是工程师、也是个正常人，那它事实上就是不会冲突。设计者比我们强的地方在于实操性——他确实把这套设计实现出来了；而我们可能只有想法，没有实现。

### 行级锁体系的学习要点

| 锁 | 级别 | 锁住的对象 | 主要影响的操作 |
| --- | --- | --- | --- |
| 记录锁（Record Lock） | 行级 | 索引上的一条记录 | 别的事务在该记录上加 `S` 锁／`X` 锁 |
| 间隙锁（Gap Lock） | 行级 | 两条记录之间的开区间 | 别的事务往该间隙里 `insert` |
| 临键锁（Next-Key Lock） | 行级 | 记录锁 + 它前面的间隙锁 | 上面两种同时被影响 |
| 插入意向锁（Insert Intention Lock） | 行级（`gap` 锁） | 等待插入的那个间隙 | 表达插入意图，本身不阻止别人加锁 |
| 意向锁（Intention Lock） | 表级 | 表 | 与表级锁配合，不是行级锁 |

这张表把本讲和前面几讲串起来：临键锁是记录锁与间隙锁的合体，插入意向锁是行级 `gap` 锁而非表级意向锁——名字里带"意向"的那把是表级锁，不带"意向"这两个字的这个组合体反而管着两种行级锁，这几处最容易混。

## 179-页锁的理解、乐观锁与悲观锁的使用
> 对应分集：P179 | 原始标题：《179-页锁的理解、乐观锁与悲观锁的使用》

前面我们已经把表锁和行锁说清楚了，那页锁又是怎么回事？页锁这一块讲完，还有另外一条线索：按"对待锁的态度"来划分，事务去操作表中的数据还会分成乐观派和悲观派。这一讲就把页锁的定位、锁空间与锁升级，以及乐观锁、悲观锁这两种并发控制思路一次讲清楚。

### 页锁的定位、死锁与锁升级

#### 页锁为什么介于表锁和行锁之间

通常一张数据表里的数据不会堆在一起，而是放在多个数据页（data page）当中；而一个页里面，又放多行数据。所以从粒度上讲，页锁（page lock）正好卡在表锁和行锁中间：表锁锁的是整张表，行锁锁的是一行记录，页锁锁的是一个数据页。

粒度的位置决定了它表现出来的特性也在两者之间。加锁的开销介于表锁和行锁之间——表锁的开销是最小的，行锁的开销是最大的；页锁的并发性同样介于这两者之间。

| 对比项 | 表锁 | 页锁 | 行锁 |
| --- | --- | --- | --- |
| 锁定粒度 | 整张表 | 一个数据页（页内含多行） | 一行记录 |
| 加锁开销 | 最小 | 介于两者之间 | 最大 |
| 并发性 | 最低 | 介于两者之间 | 最高 |

粒度越细，能同时做的事越多，但加锁本身要花的代价也越大——页锁正好是这套权衡里的中间档。

#### 页锁层面的死锁

行锁会出现死锁，页锁一样会出现死锁，原因还是加锁顺序相反。

假设事务 A 先锁定一个数据页（锁住页里的一行，或者整个数据页），接着它还要去操作另一个数据页，于是再去锁第二个页。而另一个事务恰好跟它反着来：先锁 A 想要的第二个页，再去锁 A 已经持有的那个页。这时候 A 卡在第二个页上等 B 解锁，B 卡在第一个页上等 A 解锁，两边都在等对方先放手，谁也走不下去。

```text
时间线    事务 A                          事务 B
  t1      锁定数据页 1                     —
  t2      —                                锁定数据页 2
  t3      请求锁定数据页 2 → 等 B 释放      —
  t4      —                                请求锁定数据页 1 → 等 A 释放
  t5      双方互相等待，事务都无法继续 → 死锁成立
```

读图：两个事务申请两个页的顺序刚好相反，各持有一把对方想要的锁，就会停在原地互相等待。

#### 实际开发中的锁粒度选择

页锁了解即可，实际做开发时按存储引擎来定：InnoDB 这一侧，我们一般选它的行锁；MyISAM 由于不支持行锁，那就只能做表级别的锁定。选择的依据就是我们上面看的那笔账——表锁开销小、并发差，行锁开销大、并发好，看业务更在意哪一头。

#### 锁空间有限与自动锁升级

这里有一件可能不太清楚的事：每一个层级——表锁、行锁、页锁——能加的锁的数量都是有限的。因为锁本身要占据内存空间，锁空间的大小是有上限的。

那如果某个层级上的锁数量超过了这个层级的阈值限制呢？数据库会自动进行锁升级，这是自动的行为，不需要我们手动去改。拿行锁来说，行锁层面有它自己的锁空间大小，数量一旦越过阈值，InnoDB 里的行锁就可能被升级成表锁；而一旦升级了，这个锁表现出来的就是表锁的特征：首先占用的锁空间降下来了，但其次并发性也跟着降下来了。

> **易错点**：锁升级本质上是拿并发性换空间。一般情况下我们不会把锁空间用超，但在极端情况下确实有这个风险，需要留意。

这样，从操作数据的粒度上讲的三类锁就讲完了。这块算是我们讲得比较重的内容，值得自己下来动手实操一遍再体会。

### 悲观锁：把安全交给数据库自身的锁机制

粒度的分法讲的是真正去实操时的加锁行为，接下来换个维度：从事务**对待锁的态度**上来划分。态度上分成两种，乐观锁和悲观锁。注意，这一块讲的是锁的设计思想，是一种思维方式。

在讲锁的分类概述时我打过这样一个比方：桌上有一瓶水，就剩半瓶了。乐观的人一看——不错，还剩半瓶水；悲观的人一看——唉，就剩半瓶水了。同一瓶水，两种看法的差别不在水，在态度。用事务去操作表里的数据也一样，有人是乐观派，有人是悲观派。

#### 悲观锁的思路与 Java 中的对应实现

悲观锁（pessimistic lock）对"数据被其他事务修改"这件事持保守态度——用我们常说的那句话，它总想着"总有刁民想害朕"。

它总是假设最坏的情况，每次去拿数据的时候都认为别人会修改，所以每次拿数据都先上锁。上了锁，别人对这条数据的修改就被阻塞住了，这很正常。共享资源每次只给一个线程使用，其它线程阻塞，用完以后再把资源转给其它的线程——这就是典型的独占锁思路。

写过 Java 的同学对这套东西不会陌生：`synchronized` 和 `ReentrantLock` 就是这种独占锁思想在语言层面的体现。一旦用了 `synchronized`，哪个线程拿到了里面的同步监视器，就由它来操作，其它线程这个时候都得阻塞。代价很明确——并发性会比较差；但换回来的是数据安全性有很好的保障。

这里要强调一句：悲观锁是一种设计思想，而这种思想在 MySQL 里的具体体现，就是使用数据库自身的锁机制，也就是我们上面提到的表锁、行锁，以及 X 锁、S 锁这些锁。

#### 秒杀超卖：不加锁会发生什么

举商品秒杀的例子。秒杀场景有个特点：商品数量本身不多，但同时操作它的事务、会话会多一些，这时候必须避免出现超卖——100 件商品你卖了 101 件，就属于超卖。

商品表里用一个 `quantity` 字段来表示商品的库存量。以华为 Mate 40 为例，商品 ID 是 1001，这次秒杀放出来的量比较少，就 100 台。（顺便说一句，我当时一直在用 Mate 30，做得确实还是挺好；那年上半年据说要发 Mate 50，在美国这么阻击的情况下还能有这么多突破，特别不容易，给华为点个赞。）

如果不用锁，流程是这样的：先查询库存，发现还有 100 台；接着根据 ID 生成对应的订单；订单生成之后，再按用户到底买多少台去冲减库存。在并发量比较小的场景下，这套流程没有问题。

放到秒杀里就不行了。同时想购买的用户远远大于剩下的数量时，就会出现这种情况：事务 A 一查，有 100 台；事务 B 一查，也是 100 台。接着两个事务都生成了订单，然后一起进入冲减库存的环节。假设两边都要买 60 台，冲减完就是 $100 - 60 - 60 = -20$，这就出现超卖现象了，显然不可以。

要避免它，就得保证事务 A（或者线程 B）把查询、生成订单、减库存这一整套动作都执行完，然后才让其它线程进来执行。

#### select ... for update 与"扫描行全部加锁"

用 SQL 来实现，就相当于在查询的时候就加锁：

```sql
-- 查询库存的同时就加上锁；这里的表名按你自己的库替换
SELECT quantity
FROM 商品表
WHERE id = 1001
FOR UPDATE;
```

`FOR UPDATE` 加的是排他锁（Exclusive Lock，X 锁）。这条语句执行之后，其它事务如果还想用 S 锁、X 锁的方式去查这条记录，就都得进入阻塞状态，只能等着；等当前这个事务把订单生成、把库存冲减完，别的事务再过来查还剩多少、还能不能买。

> **定义**：`SELECT ... FOR UPDATE` 就是 MySQL 中悲观锁最典型的用法。

这里有一个前面没有明确提过的点，必须注意：`SELECT ... FOR UPDATE` 在执行过程中，会把**所有扫描到的行**都加上锁，而不只是条件匹配上的那一行。所以使用的时候，一定要确保查询条件上是有索引的。

- **ID 上有索引**（比如它本身就是主键）：InnoDB 顺着 B+ 树一直往下找，直接定位到 `id = 1001` 这条数据并把它锁住，相对来说锁的力度还是比较小的。`id = 1002` 那条记录不受影响，别的事务照样能正常操作它。
- **ID 上没有索引**：假设这个字段在表里还比较靠后，那就只能从表里一条一条去检索，检索到 1001 的时候，前面扫过的数据也已经被加锁了——它并不确定你要操作哪些数据，所以会把扫描到的数据全部加锁。这时候就会影响到别的事务去操作那些本来不相干的数据。

> **结论**：写这类语句时，要根据过滤条件适当地设计索引，而且要让查询优化器真的用上索引。这个 SQL 语句在写的时候一定要注意这一点。

#### 悲观锁的适用场景与长事务的代价

悲观锁的适用场景其实不是特别多，因为它用的是数据库的锁机制去实现，并发性就会比较差。尤其是长事务：数据被锁住了，事务本身还特别长，其它并发的事务就都得等着，这是业务上无法承受的。

所以我们要想一种更好的方式，这就是乐观锁。

### 乐观锁：在程序层面实现的并发控制

乐观锁（optimistic lock）虽然名字里带"锁"，但它和悲观锁的实现位置完全不同：悲观锁是用数据库中的锁机制实现的，乐观锁则是在程序层面实现的，它没有采用数据库自身的锁机制。

另外，乐观锁对"一条数据被多个事务操作"这件事比较乐观，认为并发问题会少一些。所以它适用于读比较多的场景。

道理也简单：读和读，两个事务都去读同一个数据，本来就不会有并发问题。但既然讲了乐观，事情也不能做得太过分——真正操作这些数据的事务，改的情况也得少一点。要是改得特别多，为了保证安全性，那就真得悲观一点了。所以乐观锁的使用场景是：读操作比较多、改操作相对比较少。

还要说清楚一点：任何事物都有利有弊，很难说乐观锁就全面碾压悲观锁、把它彻底干掉，不至于，两者有不同的适用场景。

程序层面具体怎么体现？常见的是版本号机制，或者 CAS（Compare And Swap，比较并交换）机制——学过 JUC，也就是 `java.util.concurrent` 这个包的同学对 CAS 应该很清楚，JUC 的相关 API 这里就不展开说了。落到我们的更新操作上，乐观锁有两种实现机制：版本号机制和时间戳机制。

#### 版本号机制

版本号机制的做法是给表设计一个版本字段，比如说叫 `version`。读的时候把它读出来，写的时候拿它当条件。

事务 A 先读一下这条数据，`version` 是 1。接下来它要针对这条记录做一个 `UPDATE` 操作，还是同一个事务。修改的时候注意：一定要找 `version` 等于 1 的那条数据。

如果读的时候版本是 1，改的时候找的还是 1，并且找到了，那就说明在这个期间没有别的事务修改过它——因为只要有事务修改，我们就会把 `version` 加 1。修改完以后，其它字段都改了，同时记得把 `version` 从 1 改成 2。

```text
事务 A    读数据 → version = 1
            │
            └─→ UPDATE ... WHERE id = 1001 AND version = 1
                    │
                    ├─ 命中 version = 1：期间没人改过 → 更新成功，version 变成 2
                    └─ 未命中：version 已经变成 2 → 本次更新失败
```

读图：一次"查 + 改"被绑在同一个版本号上；这中间只要有人插进来改过这条数据，`version` 就对不上了。

接着事务 B 过来：它一读，`version` 是 2，读完以后接着去修改，修改时也是找 `version = 2` 的记录。这时候发现还是 2，就说明它读完之后、写之前，同样没有别的事务修改过这条数据。

> **结论**：版本号让查询和修改这两个行为在效果上具备了一个原子性——在你的查询和修改这个期间，没有别人操作过这条具体的数据。

#### 版本不匹配：更新失败是怎么发生的

```sql
UPDATE 商品表
SET quantity = quantity - 60,
    version  = version + 1
WHERE id = 1001
  AND version = 1;
```

这条语句限制住的正是要防的场景：事务 A 查的时候 `version` 是 1，事务 B 也查了一下，也是 1；A 接下来想要修改，但 A 的修改动作没有 B 快，B 先把这个数据改了，改完 `version` 就变成了 2。等 A 再去做修改，它要找的是 `WHERE version = 1` 的数据——结果找 1 的时候已经没有这条数据了。

那就意味着，A 要修改的记录已经不是它当初查出来的那条数据了，很有可能这个商品数量已经被冲减过。这时候修改就没改成功。没改成怎么办？那就要自己再去查看一下：一看，呦，变成 2 了，于是基于这个 2 再重新考虑怎么改。

这套思路和版本控制工具 SVN、CVS 的设计是一样的：我们自己当前修改完代码以后，检查一下当前代码的版本号和服务器上的版本号是否一致；一致就把代码提交上去；不一致就得先把服务器上的代码更新下来，然后你再改、再提交。

#### 时间戳机制

乐观锁的另一种实现是时间戳机制。它的原理和版本号机制其实是一样的，只不过上面用的是版本号，这里用的是时间戳：如果当前数据的时间戳，跟更新之前取到的那个时间戳一样，我们就能更新成功，否则就出现版本冲突。

这里的时间戳，作用就相当于上面那个 `version`，理解起来没有额外的东西。

#### 乐观锁下的秒杀流程

还是拿秒杀场景来体现乐观锁。我们先做查询：ID 1001 这个商品的库存，查到库存是大于 0 的，说明还能买，那么我们就会生成一个订单；接下来去修改商品的数量，这个时候就需要 `version` 等于查询时读到的那个 `version`。

跟之前一样，查询的时候这个 `version` 必须跟修改条件里的 `version` 保持一致，这就保证了"查"和"改"这两个操作相当于在同一个事务里，具备原子性——这个过程中别人没有改过；因为别人一旦改过，这个 `version` 就找不到了。

#### 读写分离下的版本号一致性

这里有一个点需要特别注意：在多台数据库服务器的情况下，我们会做读写分离。读写分离的原理是：查的时候用的是从机，而修改行为用的是主机。

那么从机查出来的 `version`，跟主机上的 `version`，就有可能因为主从同步的问题而对不上。一旦对不上，上面的 `version` 和下面的 `version` 匹配不上，就会导致这次更新失败。

```text
   应用
    │
    ├── 读：SELECT quantity, version ──→ 从机（复制有延迟，version 可能还是 1）
    │
    └── 写：UPDATE ... WHERE version = 1 ──→ 主机（真实 version 已经是 2）
                                              → 匹配不上，更新失败
```

读图：查走从机、写走主机时，从机返回的 `version` 可能落后于主机，更新条件就会失配。

怎么办？必须保证查询行为也走主机。因为下面的修改肯定是走主机的，所以我们希望上面的查也用主机，也就是强制从 master 读——这里的"主"指的是主从里的主机，不是说一台一台机器的意思。从 master 这里读数据，`version` 和 `version` 的比较才能不受主从复制的干扰。

#### 热点数据频繁修改时的兜底条件

如果多个事务要频繁地针对同一条数据修改，乐观锁的问题就出来了。你想：大家读到的都是 1，其中一个事务把它改成 2 了，其它这一堆事务都是基于 1 去改的，是不是全都改失败了？这时候在业务层面感觉上就会出现大量的失败情况。

怎么办？还可以通过另一种方式来做，就是确保 `quantity - number` 是大于 0 的，不要出现超卖的场景：

```sql
UPDATE 商品表
SET quantity = quantity - 60
WHERE id = 1001
  AND quantity - 60 > 0;
```

这里的 `number` 就是本次购买的数量，示例里买 60 台。这样后面买不到的人，就是真实地发现库存已经没有了；而只要库存还有，就可以正常做一个冲减。

### 悲观锁与乐观锁的对比

把两种态度放在一起看，差别集中在假设、实现位置和代价上。

| 对比项 | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 对并发的假设 | 总假设最坏情况，认为别人一定会改 | 认为并发冲突比较少 |
| 实现位置 | 数据库自身的锁机制：表锁、行锁、X 锁、S 锁 | 程序层面：版本号、时间戳、CAS |
| 适用场景 | 写操作比较多 | 读比较多、改比较少 |
| 并发性 | 比较差 | 比较好 |
| 死锁 | 可能在行锁、页锁层面出现 | 不存在死锁 |
| 冲突时的表现 | 其它事务阻塞等待 | 更新失败、版本冲突，由业务重读后重试 |

- **乐观锁**适合读比较多的场景：它对表中的数据被修改这件事比较乐观，认为修改的情况比较少；又因为读是允许并发执行的，所以它在读多的场景下效率更好。它是用程序实现的，因此不存在死锁的问题。
- **悲观锁**适合写操作比较多的场景：它总认为"刁民要害朕"，所以每次都得是排他的。排他多，并发性自然就差一些，但它能很好地防止读—写和写—写之间的冲突。

> **结论**：悲观锁是拿"让别人等"换安全，适合写多的场景；乐观锁是拿"失败后重试"换并发，适合读多改少的场景。两者不是谁取代谁的关系。

到这里，乐观锁和悲观锁这两种设计思想就说清楚了。回头把两条线索对齐一下：按操作数据的粒度分，我们有表锁、行锁、页锁，那是实操时真正加锁的行为；按对待锁的态度分，我们有乐观锁和悲观锁，那是锁的设计思想。这两条线索不要混在一起。

## 180-加锁方式划分：隐式锁与显式锁
> 对应分集：P180 | 原始标题：《180-加锁方式划分：隐式锁与显式锁》

前面我们已经按好几个角度给锁分过类了，这一讲再换一个角度——**按加锁方式**来划分。这么一分，锁就分成两类：显式锁和隐式锁。

这块稍微有点难度，而且隐式锁这个东西，在官方文档里的介绍文字反而比其他锁少得多。我确实去查过官网：别的锁官网上都有介绍，到了隐式锁这儿，能给出的就那么几句，还挺含糊。所以这一讲我把大部分笔墨花在它身上，先把概念说顺，再一层层往下看它在底层到底是怎么体现出来的。

### 按加锁方式划分的两类锁

先给一个泛泛的理解。凡是前面我们通过相关指令能够查看得到的那些锁信息，都叫显式锁。隐式锁言外之意就是你查不到了——查不到，就叫隐式锁。

> **定义**：按加锁方式划分，凡是在锁信息里能直接查看到的锁，叫显式锁（explicit lock）；不直接暴露在锁信息中、由 InnoDB 隐式维护的锁，叫隐式锁（implicit lock）。

那隐式锁主要针对什么行为？**它主要针对的是事务当中的 `insert`。** 但这句话马上要收一收：并不是事务里的 `insert` 都叫隐式锁，说成那样就不对了。

为什么不对？因为在讲到这里之前，`insert` 这个行为我们已经在两个位置提到过了。要弄清隐式锁的边界，得先把这两处位置翻出来对一遍。

### 此前提到 insert 的两个位置

#### 读锁、写锁处提到的写操作

第一个位置，是讲读锁、写锁时提到的写操作。写操作指的是增删改，其中的"增"就是 `insert`。那个位置讲的其实就是隐式锁这件事，当时给的结论是：**一般情况下，我们新插入一条记录是不需要加锁的。**

当时的场景是这样的：一个表里有这样一条记录，是我们通过事务 1 添加进来的。添加完以后事务一结束，这事也就结束了，这条数据正常来讲不需要加锁。但另一方面，我们又会通过一个叫隐式锁的结构对这条数据做保护——因为可能别的事务会去访问它。

单看这两句话，你们会觉得有矛盾：前面说不加锁，后面又说加了一个隐式锁。这个矛盾先记在这儿，等第 3 节把访问过程铺开，自然就化解了。

#### 插入意向锁处提到的 insert

第二个位置，是讲插入意向锁时提到的 `insert`。那个场景跟隐式锁不是一回事，必须把它先剥离出去。

设想有间隙锁（gap lock）或者临键锁（next-key lock）的情况：比如针对 `3` 到 `8` 这个范围加了 gap 锁；如果是临键锁，就把 `8` 这条记录也包含进来。在这个区间范围内我们去 `insert` 一条记录，此时针对这条新插入的记录，相应就会加一个插入意向锁（insert intention lock）。

关键差别在"被动"两个字：**是人家先有了间隙锁，你这会儿想插进去**，才出现这个插入意向锁。而隐式锁讲的是主动插入——我们自己在一个干净的事务里插一条记录，对应位置上并没有间隙锁或者临键锁存在。前提不同，两件事不要混。

| 对比项 | 隐式锁 | 插入意向锁 |
| --- | --- | --- |
| 对应行为 | 事务中主动 `insert` 一条新记录 | 在已被间隙锁/临键锁覆盖的区间内 `insert` |
| 成立前提 | 插入位置上不存在间隙锁或临键锁 | 该区间上先有了间隙锁或临键锁 |
| 出现方式 | 别的事务来访问时，替插入方构建出来 | 插入动作发生时即申请 |

一句话区分这两者：插入意向锁是"别人锁住了区间，我要往里插"，隐式锁是"我插进去了还没提交，别人要来动我"。

### 隐式锁的两种访问场景

#### 场景一：事务 2 从聚簇索引找到这条记录

先把前提摆干净：事务 1 想插入一条记录，没有别的事务干扰；这时另一个事务（事务 2）想访问它。访问行为无非读和写两种。

读的行为，前面讲过可以给查询加 S 锁，也就是 `lock in share mode`；也可以给读的行为加 X 锁，也就是排他锁 `for update`。写的行为就是要改这条记录。问题就出在这儿：事务 1 还没结束，事务 2 就把它读了——这不就是脏读吗？事务 2 去改事务 1 插入的这条记录，相当于对它加了 X 锁——这不就是脏写吗？

要限制这两种并发访问，就得看隐式锁在底层是怎么体现出来的。

事务 1 把这条记录（就叫它记录 1）添加到表里，它一定会落在聚簇索引叶子节点的某个页中，成为一条行记录。行记录我们讲行格式的时候讲过，它有三个隐藏列：`row_id`、`transaction_id`，以及回滚指针——回滚指针这一列，我们在讲 undo 页、讲 undo log 的时候提到过。这里主要看 `transaction_id`：这条记录是事务 1 添加的，事务 1 还没结束，那么这个 `transaction_id` 上记录的就是事务 1。

官方对隐式锁的解释就落在这一点上，而且说得比较含糊：它更倾向于讲这条记录上有一个隐式的列，只要这个列（`transaction_id`）记录的是事务 1，就把这儿当成一个隐式锁。说实话我觉得这个说法有点牵强，但你们就这么理解——它就叫隐式锁，加个引号。这个"锁"用查看锁信息的指令是看不到的，隐式的嘛。

接着事务 2 进来了，它想访问。

不管事务 2 要做的是读还是写，第一步都要先发现一件事：插入这条记录的事务（事务 1）是不是还活跃。如果事务 1 还活跃，那你就不能操作。

不能操作怎么办？注意听，这里有个反直觉的地方：**事务 2 会反过来帮事务 1 构建一个锁结构。**

再说一遍，我刚才说的是事务 2 帮事务 1 构建一个锁结构。这个锁结构里有一个属性叫 `is_waiting`：

- 事务 1 这一侧，`is_waiting` 是 `false` —— 人家目前是活跃的，这条记录还占着；
- 事务 2 再给自己提供一个锁结构，把自己那个 `is_waiting` 改成 `true` —— 言外之意就是你自己阻塞一下，先等着。

那如果事务 2 来操作的时候事务 1 已经提交了呢？那你就不用等，直接改就行。或者事务 1 后期结束了，事务 2 就把自己的 `is_waiting` 改成 `false`，也就可以去操作这条记录了。并发问题就是这么避开的。

```text
事务 1（insert 记录 1，尚未提交）        事务 2（要读或要写记录 1）
      │                                        │
      │  transaction_id = 事务 1               │  发现事务 1 仍然活跃
      │  （记录上并不挂任何锁结构）             │
      │                                        ├─ 替事务 1 建锁结构：is_waiting = false
      │                                        └─ 给自己建锁结构：is_waiting = true（阻塞等待）
      │
   commit / rollback
      │
      └──────────► 事务 2 把自己的 is_waiting 改成 false，随即操作记录 1
```

读图说明：事务 1 一侧从头到尾没有主动加锁，锁结构是事务 2 到来时替它补上的；`is_waiting` 的两个取值分别标出"谁占着记录"和"谁在等待"。

#### 场景二：事务 2 从二级索引找到这条记录

事务 2 也未必走主键这条路——它完全可能通过非主键的索引找到这条记录。

理由很直接：我们正常添加一条记录，字段通常是完整的。那么这条记录除了在聚簇索引里体现之外，也有可能在其他二级索引里体现。比如其中某个字段你建了二级索引，那你在二级索引当中同样能找到这条记录的存在。如果事务 2 是通过二级索引找到它的，那要看的就不是场景一，而是场景二了。

场景二立刻带来一个问题：`transaction_id` 是在行记录里提供的，而完整的行记录**只存在于聚簇索引的叶子节点中**。二级索引里并没有这条记录的完整记录信息，也就意味着二级索引上没有 `transaction_id` 可用。

那怎么办？看页结构。二级索引的页和聚簇索引的页都有页结构，但在二级索引的页里，`PAGE_HEADER` 中有这样一个属性：

> **定义**：`PAGE_MAX_TRX_ID`，仅在二级索引的页中定义，记录的是**修改当前页的最大的事务 ID**。

这个属性是我们在讲数据存储结构的时候出现过的，翻回那一段就能看到它。有了它，比较就成立了：事务 1 在这个页里插入一条数据，那么不管事务 1 结束没结束，事务 1 都会被记录在这个页的这个属性里。

事务 2 进来的时候，就拿自己的事务 ID 跟页里这个属性的值作个比较：

- 页里这个值更小：说明之前修改这个页的事务都已经提交过了，那你就可以去操作；
- 不满足这个条件：说明事务 1 还没有结束。那就得通过二级索引找到对应的主键索引，回到聚簇索引里，按 `transaction_id` 那一套去处理——给人家提供一个锁结构，这就又回到场景一了。

为什么值更小就意味着"都提交过了"？事务 ID 是递增分配的，页里记的最大事务 ID 比事务 2 自己的 ID 还小，说明改动过这个页的事务都排在事务 2 之前，也就都已经提交完了。

```text
事务 2 通过二级索引找到这条记录
        │
        ▼
读二级索引页 PAGE_HEADER.PAGE_MAX_TRX_ID
        │
        ├─ 该值比事务 2 的 ID 小 ──► 之前的事务都已提交 ──► 直接操作
        │
        └─ 否则 ──► 事务 1 尚未结束
                     │
                     ▼
             用二级索引记录里的主键回表
                     │
                     ▼
        到聚簇索引按 transaction_id 处理（场景一）
```

读图说明：场景二的判断入口是页头属性而不是记录本身；比较不通过时，处理权就交回场景一那条聚簇索引路径。

> **易错点**：二级索引页上没有 `transaction_id`，所以不能像场景一那样去看"记录上挂着哪个事务"，场景二必须先读 `PAGE_MAX_TRX_ID` 做一次判断。

把两条路径摆在一起，差别就很清楚了：

| 对比项 | 场景一：事务 2 走聚簇索引 | 场景二：事务 2 走二级索引 |
| --- | --- | --- |
| 判断依据 | 行记录上的 `transaction_id` | 页头 `PAGE_HEADER` 里的 `PAGE_MAX_TRX_ID` |
| 怎么判断插入方是否活跃 | 看 `transaction_id` 上记的那个事务还活不活跃 | 拿自己的事务 ID 与页里的最大事务 ID 比大小 |
| 判定活跃之后 | 替对方建锁结构，自己 `is_waiting = true` 等着 | 先回表到聚簇索引，再按场景一处理 |

### 隐式锁的两个性质

第一，隐式锁在内存中实际上**并不含有锁信息**。因为它是隐式的，你用查看锁信息的指令去看，是看不到的，这一点要注意。

第二，隐式锁是一种**延迟加载**的机制。本来记录上什么都不带，是因为有另外一个事务（事务 2）去访问，这个锁才出现——所以你可以把它理解成延迟加载、延迟加锁的方式。

把这两点合起来看还有个有意思的地方：事务 2 的访问导致隐式锁出现，而它一出现，其实也就变成一个显式锁了，这时候我们通过指令就能查看到它。这一点稍绕，下面用例子演示一遍。

### 演示：insert 事务与 S 锁查询的阻塞过程

先在一个会话里操作 `atguigudb3` 库：

```sql
use atguigudb3;

begin;                                          -- 开启一个事务
select * from student;                          -- 先看一眼这张表

insert into student(id, name, class)
values (2, 'Tom', '一班');                      -- 事务 1 插入记录，先不提交
```

这条 `insert` 是干净的插入：当前表里没有任何锁，不存在间隙锁的场景，所以这里走的不是插入意向锁那条线，而是隐式锁这条线。执行下去，插入成功。

整个演示的时序是这样的：

```text
会话 A  use atguigudb3 → begin → insert into student(id, name, class)
        values (2, 'Tom', '一班')   （事务一直不提交，记录 1 就停在这个状态）
会话 B  另开会话登录 mysql → use atguigudb3 → 查看锁信息 → 没有任何锁出现
        → begin → select * from student lock in share mode → 阻塞等待
        → 再查看锁信息 → 隐式锁现身，此刻已可看作显式锁
```

读图说明：同一个未提交的插入，在会话 B 的两次查看之间从"查不到锁"变成"能查到锁"，变化点正是会话 B 自己那条加 S 锁的查询。

然后另开一个会话登录 `mysql`，`use atguigudb3`，用前面那条查看锁信息的指令看一眼这张表上有哪些锁——**没有任何锁出现**。这正好印证了刚才说的：隐式锁在内存里没有锁信息，你查不到。

接着回到另一个会话（与执行插入的那个事务不同的会话），做两件事：

```sql
use atguigudb3;

begin;
select * from student lock in share mode;       -- 加 S 锁查询，执行后阻塞
```

这条查询执行下去，直接阻塞在那儿不动了。这个阻塞就是因为那条隐式记录引起的：刚才查看锁信息的时候明明什么都没有，现在这个操作却被挡住了，那就说明此刻确实是有锁的。

这时候再执行一次查看锁信息的指令，你就能看到它了——这就是那条隐式锁。既然你能看到它了，也就可以把它理解成：隐式锁现身了，变成了一个显式锁。

隐式锁这块我花了很多笔墨去描述，你们在开发当中接触它的机会其实是比较小的。既然讲到这内容了，咱就把它说透，理解这个过程就可以了。除此之外，剩下那些能够通过指令查看到的锁，都叫显式锁——比如前面加 `lock in share mode` 的 S 锁，或者 `for update` 的排他锁 X 锁，都算。

## 181-全局锁与死锁的理解
> 对应分集：P181 | 原始标题：《181-全局锁与死锁的理解》

锁从不同的角度划分下来，再到下边具体有哪些锁，我们基本上讲得差不多了。最后还剩两个内容要补进来：一个叫全局锁（global lock），一个叫死锁（deadlock）。这两个概念本身都不复杂，但都跟实际项目里的行为直接相关——全局锁决定了你做全库备份的时候数据还能不能动，死锁决定了一个正在跑的事务会不会被存储引擎强行按下去回滚。我们一个一个说。

### 全局锁

全局锁，顾名思义，作用范围是整个数据库实例。

> **定义**：全局锁是加在整个数据库实例上的锁。加锁之后，这个实例下所有的数据库、所有的表，全部只能处于只读状态。

只读是什么意思？别的事务过来可以读，但一定不能更新。落到具体的语句类型上：

- DML（Data Manipulation Language，数据操纵语言）里的增删改，也就是 `INSERT`、`UPDATE`、`DELETE`，不能做；
- DDL（Data Definition Language，数据定义语言）也不能做，建表、`ALTER TABLE`、`DROP TABLE` 全在禁止之列；
- 乃至其他任何更新行为，同样不能做。

一句话概括：这段时间里，只能读，不能改。

```text
正常实例（可读、可写）
        |
        | 加全局锁
        v
只读状态：实例下所有数据库、所有表
        |  允许：读取操作
        |  禁止：INSERT / UPDATE / DELETE（DML 增删改）
        |  禁止：建表 / ALTER TABLE / DROP TABLE（DDL）
        |
        | 释放全局锁
        v
正常实例（可读、可写）
```

读图说明：全局锁把整个实例从"可读可写"推到"只读"，释放之后才回到原状态；它覆盖的是实例下所有的库、所有的表，粒度不是某一张表、更不是某一行。

> **提示**：全局锁拦下来的不只是 DML 的增删改，`ALTER TABLE`、`DROP TABLE` 这类 DDL 同样进不来。加锁期间能通过的只有读操作。

典型的使用场景是做全库的逻辑备份。备份的过程当中数据不能再被修改，只能读——备份要的是那一刻的数据，中途让人改掉了，备出来的就对不上了。

也正因为如此，全局锁的粒度肯定是最粗的，比表级别的锁还要粗。粒度越粗，能并发的操作就越少，所以这种场景出现的次数必然比较少。

### 死锁的定义与构成条件

死锁这个词，我们在前边讲间隙锁的时候已经碰到过一次。间隙锁属于行锁，而行锁、页锁里边都可能出现死锁问题。当时其实已经看到了 InnoDB 针对死锁给出的解决方案，也感受到了它是怎么处理的。这里我们把死锁再完整地刻画一遍。

#### 线程死锁与事务死锁的对应关系

提到死锁，很多 Java 程序员并不陌生：多线程访问共享数据的时候讲过——一个线程先获取第一个共享数据，再去获取第二个共享数据；另一个线程的顺序正好反着，先拿第二个，再拿第一个。两个线程各攥着一把、又都想要对方手里那把，这个过程当中就可能构成死锁。

数据库事务里的死锁，原理跟线程里的死锁完全一样，只是习惯上把"线程"这个词换成了"事务"。事务本身也是在线程里执行起来的，所以两边是一致的。

> **定义**：两个事务都持有对方需要的锁，并且在等待对方释放，同时自己又不释放自己手里的锁，互相僵持下去，就构成了死锁。

这句话里有两个条件不能少：一是至少两个事务，一个事务自己跟自己锁不出死锁；二是双方都不撒手，谁都在等对方先让。

#### 两个事务交叉加锁的循环等待

先看第一个例子，用的是 `account` 这张表。事务一针对 `account` 表里 ID 为 1 的那条数据，获取了一个排他锁（exclusive lock，X 锁）。在事务一执行下一条语句之前，事务二针对同一个 `account` 表里 ID 为 2 的那条数据，也获取了一个排他锁。

接着，事务一又试图针对 ID 为 2 的数据获取排他锁。这时候 ID 为 2 的锁已经在事务二手上，事务一只能等待——这种等待很正常，别人已经把锁拿走了，你就得等。

问题出在事务二接下来的动作上：如果它下面这条 `UPDATE` 操作的是 ID 为 3，那还没有构成死锁；但它操作的恰恰是 ID 为 1。而 ID 为 1 的数据已经被事务一占了锁，事务二这时也只能进入等待状态。

于是这哥俩就僵持住了：我拿着 1 的锁等 2，你拿着 2 的锁等 1，彼此需要的锁谁也不释放，那就等着吧——这么等下去是没有头的，这就构成了死锁。

> **易错点**：死锁至少要有两个事务。单个事务自己加锁、自己等待，锁不出死锁来。

死锁问题是一定要解决的。讲事务的时候我们强调过：事务的最终状态只能二选一——要么执行完提交（commit），要么中止回滚（rollback），不能卡在中间这么半死不活的，那不行。

再看第二个例子：用户 A 给用户 B 转 100 块钱，与此同时用户 B 也给用户 A 转 100 块钱。这个过程**有可能**出现死锁——注意是"有可能"，不是"一定会"。

事务一先对 A 账户占了一个排他锁，接着事务二对 B 账户占了一个排他锁。接下来事务一想针对 B 获取排他锁，不行了，B 已经被事务二拿住，事务一等待。然后事务二去操作 A，A 也被事务一拿住了，事务二也等待。两个事务的关系跟上面那个例子大同小异，一个死锁场景就出现了。

```text
+----------+                    +----------+
|事务一 T1 |  ------ 等待 -----> |事务二 T2 |
|持有 A 锁 |  <----- 等待 ------ |持有 B 锁 |
+----------+                    +----------+
```

读图说明：事务一持有 A 账户的排他锁、等待 B 账户的锁，事务二持有 B 账户的排他锁、等待 A 账户的锁，两条等待关系首尾相接收成一个环，环一闭合就是死锁。

用生活里的例子来刻画这件事，网上有这么一张图，我觉得比较形象：一辆黄车要开走，得依赖那辆绿车先开走；绿车要往下移，绕到最后翻过来，它自己又得等黄车移走。谁也别想动，这就构成一个死锁。

再换个更简单的：两根筷子，A 这个人拿一根，B 这个人拿一根，而吃饭得用两根筷子。现在谁都拿着一根，都等着对方先把手里的让出来，自己还不撒手，那就僵在这儿了，同样是一个死锁。

#### 死锁的必要条件与加锁顺序

把上面这些例子总结一下，构成死锁的必要条件有这么几条：

- 至少要有两个事务（或 session 会话）参与；
- 每个事务自己已经持有锁，同时还在申请新的锁；
- 它申请的这个新锁，恰好被对面的另一个事务持有；
- 锁资源只能被一个事务持有和操作，不可能两个人同时攥着同一把锁；
- 事务之间因为持有锁和申请锁，彼此构成循环等待。

> **结论**：死锁的关键，是两个以上事务（或 session 会话）加锁的顺序不一致。

反过来看双向转账那个例子就很清楚：如果事务二不是"先减 B、再给 A 加钱"，而是把这两条语句颠倒一下、上来先给 A 加钱，你会发现这两个事务就不会构成死锁了——因为它们访问 A 和 B 这两个共享资源的**顺序是一样的**：谁先把 A 的锁拿到手，谁就能一路把 A、B 都走完，另一个老老实实在 A 这里等着就行，等待关系接不成环，死锁就无从谈起。

这本身就是一个解决死锁的措施：把相关的 SQL 改成获取锁的顺序一致，就可以了。

### account 表双向转账的死锁复现

理论上说清楚了，我们实际做一遍。用 `atguigudb3` 这个库里的 `account` 表，先看一眼数据：

```sql
USE atguigudb3;
SELECT * FROM account;
```

表里有三个人。我们让 ID 为 1 和 ID 为 3 这两位互相转账 10 块钱：一个事务里让 1 给 3 转 10 块，另一个事务里反过来让 3 给 1 转 10 块，中间就有可能转出死锁来。

第一个事务：

```sql
BEGIN;
UPDATE account SET balance = balance - 10 WHERE id = 1;
```

`BEGIN` 和 `START TRANSACTION` 在这里是一回事，用哪个都行。这条语句先把 ID 为 1 的余额减掉 10。

先把下一条 `UPDATE` 按住别写，转到第二个事务里：

```sql
USE atguigudb3;
BEGIN;
SELECT * FROM account;
UPDATE account SET balance = balance - 10 WHERE id = 3;
```

到这里两个事务都已经开启，并且各自拿到了一条 ID 数据上的排他锁。

再回到第一个事务。它已经减了 10 块钱，接下来该给 ID 为 3 加 10 块钱了：

```sql
UPDATE account SET balance = balance + 10 WHERE id = 3;
```

这条一执行，它就在等待了。

> **提示**：这里的等待是完全正常的。ID 为 3 那条数据的排他锁在第二个事务手上，第一个事务除了等没有别的办法。

演示的时候得抓紧操作：等待是有时限的，默认时间一过，这个事务就会被自动回滚结束，演示就做不下去了。

紧接着在第二个事务里，给 ID 为 1 加 10 块钱：

```sql
UPDATE account SET balance = balance + 10 WHERE id = 1;
```

这条一走，死锁就出现了，报错信息里带着 `restarting transaction` 这样的字样。

回头再看第一个事务，它已经不再等待，而是执行成功了。为什么它突然能执行了？因为 ID 为 3 上的那把锁被释放了——而锁之所以会释放，是因为持有它的那个事务回滚了。这正是 InnoDB 解决死锁的方式：不等到超时，它当场就把这个环拆掉了。

整条链路按时间顺序摆出来是这样的：

```text
T1: BEGIN
T1: UPDATE id=1 (-10)   -> 成功，持有 id=1 的排他锁
T2: BEGIN
T2: UPDATE id=3 (-10)   -> 成功，持有 id=3 的排他锁
T1: UPDATE id=3 (+10)   -> 等待（id=3 的锁在 T2 手上）
T2: UPDATE id=1 (+10)   -> 死锁被检测到，等待关系接成环
引擎回滚代价较小的一方 -> 它持有的锁被释放 -> 另一方等待结束，语句执行成功
```

读图说明：前两步各自占住一条记录，第三步开始交叉申请锁，第四步把等待关系接成一个环，引擎随即检测到死锁并回滚其中一方，环被拆开，另一方继续往下走。

### 死锁的处理方案之一：锁等待超时

下面说出现死锁该怎么解决。刚才的演示其实已经把 InnoDB 的做法露出来了，我们再把这事从理论上说明白。

事务的最终状态只能二选一：已提交（commit）或者已回滚（rollback），在中间僵着肯定不是事。所以一种方案就是超时。

我们有一个默认参数 `innodb_lock_wait_timeout`，默认值是 50 秒。想确认这个值，用 `SHOW` 看一下：

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
```

拿到的值是 `50`，单位是秒。含义是：锁等待超过 50 秒，事务会自动回滚。

这个机制并不只对死锁生效。如果你压根不是死锁，只是单纯地在等锁，超过 50 秒等待，一样会被自动回滚。

> **易错点**：`innodb_lock_wait_timeout` 管的是"等锁最多等多久"，不是"死锁最多等多久"。到点被回滚的，可能是死锁里的一方，也可能只是一个正常等待的事务。

这个方案的毛病很明显：50 秒挺长的。实际项目里有可能同时出现多个死锁、互相交织在一起，要是都等 50 秒，那是很崩溃的。

有同学会想到：这不就是个参数吗，我把值改小一点不就行了？改成 1 秒，甚至改成 0.1 秒，超过就立刻回滚。理论上死锁问题肯定能解决，但会**误伤**。

误伤在哪儿？回头看刚才的演示：第一步操作、第二步操作、第三步操作——第三步那个等待其实不是死锁，是正常等待。如果超时时间设成 1 秒，那这个正常等待等满 1 秒，事务立马就被回滚了，这显然不合适。等待本来是正常的，参数一改小，不光把死锁问题解决了，连正常的等待也一起伤到了。所以这条路不太合适。

### wait-for graph 死锁检测

第二种方案就是死锁检测机制。这也解释了刚才演示里为什么一构成死锁、立刻就报出了信息：引擎根本不用等 50 秒，它当场就检测到了。

这套检测用的是 `wait-for graph`（等待图）算法，是一种主动检测行为。

#### 检测所依赖的两张表

等待图的构造依赖两张表：

- **事务等待链表**：记录当前有哪些事务处于等待状态。这里的例子里，T1、T2、T3、T4 四个事务都在等待。
- **锁的信息列表**：记录每条数据上锁的持有与申请情况。这里的例子里，`row1` 这条数据上，T2 获得了一个排他锁，而 T1 正在申请一个共享锁（shared lock，S 锁）；`row2` 这条数据上还有另一组锁的持有与申请情况。

把这两张表合起来看，就能判断出"谁在等谁"。

#### 等待图的构造与环判定

构图规则很直接：

- 节点就是事务等待链表里那几个处于等待状态的事务，也就是 T1、T2、T3、T4；
- 边是一条等待关系，`Ti -> Tj` 表示 Ti 正在等待 Tj 释放锁。

按例子中两张表的信息画出来是这样：

```text
节点：T1、T2、T3、T4（均处于等待状态）

等待边：
  T1 ----> T2     T1 等待 T2
  T2 ----> T1     T2 等待 T1       <- 与上一条首尾相接，环在这里闭合
  T2 ----> T4     T2 等待 T4
  T3 ----> T1     T3 等待 T1
  T3 ----> T4     T3 等待 T4
  T3 ----> T2     T3 等待 T2
  T4 --x-> T1     T4 与 T1 之间是共享关系，互相兼容，不构成等待
```

读图说明：T1 与 T2 之间的两条反向边首尾相接，构成一个长度为 2 的环——图里出现环，就说明有死锁；事务再多一些的时候，也会出现三个事务依次等待、首尾相连的那种环。最后那条边本来看着像等待关系，但两者之间是共享锁，共享锁互相兼容、谁也挡不住谁，自然就不需要等待了。

> **结论**：等待图里只要有环，就是死锁；没有环，等待关系迟早能排出一个先后次序，等待就只是等待。

一旦检测到死锁，InnoDB 会选择回滚 **undo 量最小**的那个事务。为什么要挑 undo 量最小的？因为回滚是有成本的：事务改动得越少，undo 记录越少，回滚代价就越低。刚才演示里的两个事务，回滚粒度差不太多，实际情况下有的事务改得少、回滚成本低，引擎就会挑成本最低的那个来回滚。一个事务一回滚，它持有的锁就释放了，环随之断开，其他事务立刻就能正常往下执行。

> **提示**：这套检测由一个参数控制，它默认是 `on`。只有它是打开的，这种主动检测的方式才生效，这一点要注意。

#### 检测开销与并发控制

这种方式有没有缺点？有。

并发线程一多，代价就上来了。假设现在有 100 个并发线程要更新同一行数据，那这 100 个线程都得等待，引擎就得为它们画等待图——每个线程都要和其他线程逐一判断有没有等待关系，100 个线程就是 $100 \times 100 = 10000$ 次判断；要是有 1 万个线程，检测的次数就更多了，这个成本是相当高的。

那不用行不行？不行。退回超时方案太不靠谱，真出了死锁在那儿僵着也不合适，会对业务产生影响，所以这个机制得用。

既然要用，就得想办法在并发量大的场景下把并发访问的数量控制住。一个做法是在实际的数据库中间件层面，对"更新相同行"的请求排队：同一行的更新排好队依次进来，同时争抢同一行的线程数降下来，死锁检测的工作量也就跟着降下来了。

再进一步，是减少锁的冲突。举个例子：一个连锁超市，底下涉及五六十家门店，如果每卖一样东西、每有一笔收支，都跑到总部去更新同一张表，那显然不太靠谱，锁冲突的概率会明显增大。怎么办？平时让每家店先在自己店里做账目的增加、减少，然后在固定的时间——比如凌晨几点、或者每个月一次——再把数据汇总更新到总部的那张表里。这样锁的冲突就小多了。

### 死锁的避免措施

最后说说平时该怎么避免死锁，有这么几条思路。

1. **合理设计索引**：让 SQL 在检索过程中尽可能少地去锁定相关的行数据。索引设计不合理的时候，本来锁三行数据就够，它一遍历锁了三十行；锁住的数据越多，越有可能造成死锁的风险。
2. **调整业务 SQL 的执行顺序**：避免 `UPDATE`、`DELETE` 这种长时间持有锁的操作，在相关事务前面先占着资源不动。
3. **避免大事务**：把大事务分解成多个小事务。事务越小，单位事务获取的锁就越少，出现死锁的概率也就越小；反过来，占得越多风险越大。
4. **高并发系统里不要显式加锁**：本来就并发得厉害，还自己显式去加锁，有点自己作的感觉。
5. **降低事务的隔离级别**：这一条要具体问题具体看，看业务到底适不适合降低隔离级别。

> **结论**：死锁本身其实比较简单——两个以上事务加锁顺序不一致，各自拿着对方需要的锁不放，等待关系接成一个环，就成了死锁。处理上靠引擎的主动检测加"回滚代价最小的一方"；真正要下功夫的地方在平时：合理设计索引把锁的范围压小、别让长事务占着锁、把大事务拆小、控制并发争抢同一行的数量，把构成死锁的条件一条一条拆掉。

## 182-锁的内存结构与监控策略
> 对应分集：P182 | 原始标题：《182-锁的内存结构与监控策略》

各种丰富类型的锁讲到这儿就告一段落了，下面该往内存里看一眼：这些锁在 InnoDB 内部到底长什么样，这个结构简称叫**锁结构**。其实前面讲读读、写写的冲突情况时已经把它拎出来过一次，当时只说了内部的两个人事安排——一条是**这个锁是谁的**，也就是事务的信息；另一条是**当前事务能不能操作这条记录**，是要等，还是现在就能执行，对应 `is_waiting` 这个属性。现在把这两个先放一边，看看锁结构里还有什么。

还有一个悬着的问题正好在这里落地：讲行锁的时候，我们给 `ID` 为 8 的那条记录加过一个类型叫 `LOCK_REC_NOT_GAP`，非间隙的记录锁；后面讲间隙锁、临键锁，同样都有一个类似的类型声明。这些声明写在哪儿？就写在锁的内部结构里。

### 锁结构的生成与共用

第一个要回答的问题是：事务针对表里的记录加锁，是**一条记录生成一个锁结构**，还是另有安排？

先看一个很常见的写法：

```sql
SELECT * FROM user LOCK IN SHARE MODE;
```

这是给查出来的记录加 S 锁（共享锁）。假如此刻这张表里有 1 万条记录，要是老老实实生成 1 万个锁结构，内存直接就崩了。所以真实情况没这么干，但也不是简单地"永远只生成一个"，中间有一条判断线。

> **结论**：满足下面四个条件的加锁，会被收进**同一个锁结构**——
> 加锁的是同一个事务；被加锁的记录在同一个页面中；加锁的类型相同；等待状态（`is_waiting`）也相同。

四条里少一条，就分别落到不同的锁结构里去。

### 锁结构的内存布局

整体数下来，锁结构一共分成六个部分。其中第三个位置要分情况：加的是表锁还是行锁，这一格记录的信息不一样。

```text
+--------------------------------------------------------------+
|  1  锁所在事务的信息        —— 指针，指向内存中该事务的信息   |
+--------------------------------------------------------------+
|  2  索引信息                —— 指针，指向涉及到的索引记录     |
+--------------------------------------------------------------+
|  3  表锁 / 行锁的信息                                         |
|      表锁：表信息 + 其他信息                                  |
|      行锁：Space ID + Page Number + n_bits                    |
+--------------------------------------------------------------+
|  4  type_mode                                                 |
+--------------------------------------------------------------+
|  5  其他信息                —— 相关哈希表、链表的信息         |
+--------------------------------------------------------------+
|  6  一堆比特位              —— 逐位标记页内哪个记录被锁       |
+--------------------------------------------------------------+
```

读图说明：第 1、2、5 项存的是指针或索引类信息，第 3 项按表锁／行锁分成两支，第 4 项是一个按位分段的编码字段，第 6 项才是真正逐条记录标记加锁状态的比特位数组。

#### 事务信息与索引信息

第 1 项是锁所在事务的信息。既然锁结构是某个事务要操作记录时生成的，那首先得记清楚"这个锁结构归谁"。

> **易错点**：这里记录的**只是一个指针**，指向内存中该事务真正的信息所在的位置，不是把这个事务的全部信息都抄一份进来——那太浪费空间了。

第 2 项是索引信息，记录当前事务操作到的、与索引相关的那些记录，同样是以指针的形式存。

#### 行锁信息：Space ID、Page Number 与 n_bits

表锁这一格相对简单，需要记录的是"对哪一张表加的锁"，外加一些辅助信息，了解即可。

行锁要记三个重要信息：`Space ID`，即这条记录所在的表空间是哪个；`Page Number`，即这些记录所在的页号是多少；以及 `n_bits`。这前两个一看就明白，`n_bits` 得留到最后和"一堆比特位"一起说——它俩看着像一回事，其实分工完全不同。

#### type_mode 的三段划分

`type_mode` 是"类型模式"，一个字段里塞了三段信息，从低位到高位依次排开：

| 位段 | 字段 | 作用 |
| --- | --- | --- |
| 低位段 | `lock_mode` | 记录锁的模式：`IS`（共享型意向锁）、`IX`（独占型意向锁）、`S` 锁、`X` 锁、自增锁等 |
| 第 5 ~ 8 位 | `lock_type` | 第 5 位为 `1` 表示表级锁，第 6 位为 `1` 表示行级锁；第 7、8 位未使用 |
| 再往高位 | `rec_lock_type` | 记录行锁的具体类型，如 `LOCK_REC_NOT_GAP` 等 |

第一段 `lock_mode` 记录的就是我们前面讲过的那些行为。注意它不一定只对应表级的锁——`S` 锁既可能是表级的共享锁，也可能是行级的共享锁，所以模式和表级／行级是两件分开的事。

第二段 `lock_type` 占了 5 到 8 位，也就是 4 个 `bit`，但实际只用了两个：第 5 位为 `1` 表示这是一个表级锁，为 `0` 就不是；第 6 位为 `1` 表示这是一个行级锁。靠着第 5、6 位这一对，就能把表级锁和行锁区分开。第 7、8 位空着没用。

第三段 `rec_lock_type` 就是我们惦记了很久的那批声明：临键锁、间隙锁（`gap` 锁）、记录锁，都落在这个位置。前面给 `ID` 为 8 的记录加的那个 `LOCK_REC_NOT_GAP` 就能在这儿找到，它表示一个正经的记录锁，是针对这一条记录的锁。这一段里体现的，基本都是行级锁的各种形态。

那 `is_waiting` 又在哪儿？出于节省空间的考虑，它占的是**第 9 位**：这一位是 `1`，表示 `is_waiting` 为 `true`，你现在处于等待状态；是 `0`，表示你当前就可以操作这条记录，也就是获取锁成功了。

#### 其他信息与一堆比特位

第 5 项是其他信息，放的是用来识别当前这个锁结构的一些哈希表、链表相关的信息。

第 6 项"一堆比特位"，是真正逐条记录做标记的地方。这里要把 `n_bits` 的分工说清楚：

> **提示**：`n_bits` 只记录比特位的**个数**，比如 `110`，它就写个 `110` 这个数；比特位本身并不在 `n_bits` 里，而在最后这一格。

为什么行锁要维护一整排比特位？因为锁结构是针对**具体的一个页**生成的，而一个页里可能有好几条记录被锁，另外一些没被锁。假设一个页里放了 100 条记录，其中有的记录被锁住了、有的没有，那就必须一条一条地记下来：哪条锁了、哪条没锁。这一排比特位就是干这个的——一个 `bit` 只有 `0` 和 `1` 两种取值，加锁的用 `1` 表示，没加锁的用 `0` 表示，一一对应到记录上。

那 100 条记录是不是只需要 100 个 `bit`？不是。讲页结构的时候提过，一个页里除了真实数据，还必然有 `Infimum` 和 `Supremum`，也就是页中的最小记录和最大记录。刚才说的 100 指的是真实存了 100 条数据，加上这两个就是 102 条，这两个别丢了。

而且每条记录都有一个 `heap_no`：`Infimum` 的 `heap_no` 是 `0`，`Supremum` 的 `heap_no` 是 `1`，之后每多加一条记录这个值就加 1。于是比特位和记录是一一匹配的，通过它就能看出到底是哪一条记录被当前事务的锁结构给锁住了。

实际用起来也不是刚好 102 个比特位。因为后面还可能往这个页里插入新记录，到时候再去改这个比特位数组就没必要了——一个 `bit` 占的空间本来就很小，不妨多放一些，把后面新添加记录对应的位置预留出来。

### 锁监控：从状态变量到系统表

锁这一章最后还剩一件收尾的事：锁的监控。事务执行过程中会碰到各种各样的锁，我们能通过哪些语句去看清这里边的锁的情况？

其实前面讲隐式锁的时候已经用过其中一件工具了——从 `performance_schema` 这个系统提供的库里查当前等待锁的事务场景。除此之外还有别的，这里做一次系统的说明。

#### innodb_row_lock 系列状态变量

比较常用的一组是 `innodb_row_lock` 开头的一系列参数，通过它能看到一些主要信息：

```sql
SHOW STATUS LIKE 'innodb_row_lock%';
```

执行之后，会看到以这个字段开头的若干属性字段，逐个说清含义。

| 字段 | 含义 |
| --- | --- |
| `current_waits` | 当前正在等待锁定的数量 |
| `lock_time` | 从系统启动到现在为止，锁定的总时长 |
| `avg_lock_time` | 锁等待平均花费的时长 |
| `max_lock_time` | 锁等待最多花费的时长 |
| `waits` | 锁等待的总次数 |

`current_waits` 表示此刻正在等待锁的数量，演示时它显示没有等待，也就是 `0`。`lock_time` 是从系统启动到当下这一秒，锁等待累计的总时长。既然有了总时长，下一个自然是平均花费时长，也就是锁等待的平均开销；再下一个是锁等待花得最多的一次，演示里它已经超过 50 秒——这 50 秒就是锁等待的 `timeout`，一个时间上限。最后 `waits` 是锁等待的总次数，演示中是 31 次。

数据摆在面前，重点要盯的是三个：**总时长、平均时长、等待次数**。这三个里更重要的又是后两个。

> **结论**：平均时长和等待次数乘起来，正好就是总时长。所以如果这两个都比较大，就说明锁等待既频繁又费时间，这时候就该去查看相关的那些事务、相关的那些操作里边的结构，分析是什么原因造成锁这么多、单次又耗这么久。

这就是第一件监控工具。

#### 三张系统表与 5.7／8.0 的差别

如果想看眼下到底有哪些锁还在等待，就得换系统库里的表。以前用的是 `information_schema`，这个库下面对应着三张表：一张管事务，一张管锁，一张专门管"锁在等谁"。5.7 的时候就是拿这三张表去查的。

到了 8.0，策略有变化：三张表未必原样保留，其中一部分改用 `performance_schema` 里对应的表来替代——原来在 `information_schema` 里查锁的那张表，换成了 `performance_schema` 里对应的表，管锁等待的那张同样有对应替代。隐式锁那一节我们用的，正是其中负责锁等待的那一张。

> **易错点**：5.7 和 8.0 在这里有个关键区别。在 5.7 里用这套表去查，**只能看到被阻塞的事务、阻塞的锁**；如果某个锁并没有造成阻塞，你根本看不到它。比如演示时那条已经加了 `X` 锁（排他锁）但没有阻塞别人的记录，在 5.7 里边就是查不出来的。8.0 不一样，没有阻塞的锁也能看到。

#### 阻塞场景的实测

光看字段名没感觉，还是造一个具体场景来演示。

先在当前会话的事务里执行：

```sql
BEGIN;
SELECT * FROM student FOR UPDATE;
```

然后回到另一个会话的事务里，同样 `BEGIN` 之后再跑一句：

```sql
SELECT * FROM student FOR UPDATE;
```

第二个会话就阻塞住了——它要的锁被别人占着，只能等。这时候登录进去看：

```bash
mysql -u root -p abc123
```

因为锁等待有时间限制，得抓紧查。先查事务和锁的那张表：

```sql
SELECT * FROM information_schema.<表名> \G
```

结果里能看到两条信息，其中一条是 `select * from student for update`。它想表达的就是被阻塞的那个事务——正在等待锁的事务、以及它执行的 SQL 语句。顺着这一行往下读：前面是该事务的 ID，接着是它当前的状态，标明它处于等待中；再往下是这条操作开始的时间；还有这个事务锁定／影响的行数；以及当前事务的隔离级别。

就在我们翻看这些字段的时候，那边的 `timeout` 到了，等待超过 50 秒，第二个事务被干停（等待锁超时并放弃）。而被我们查出来的那一条本身没有阻塞，所以它一直待在那里，不会消失。

接着换查等待锁的场景，看当前处于等待状态的锁——没有超时的时候能看到它，超时之后再执行就查不到了。演示里第三个视图一共查到 11 行数据，一行一行细抠就不展开了。

> **提示**：上面这条语句里的 `<表名>` 用哪一张，取决于当前版本：5.7 走 `information_schema` 里那三张表，8.0 走 `performance_schema` 里替代它的表。

三个视图各管一段，串起来就是一条排查链路：

```text
先看状态变量 innodb_row_lock 系列
        |
        |  等待次数多、平均耗时长（两者相乘即总时长）
        v
查事务与锁的系统表
        |
        |  当前仍有事务在等锁
        v
查“锁在等谁”的那张表，定位等待中的锁
```

读图说明：先用状态变量判断"问题严不严重"，再用系统表判断"现在还有谁在等"，最后落到具体的等待锁上，属于由粗到细的递进。

排查思路就是这样：如果从统计上发现等待次数比较多、时间比较长，就进一步去分析；如果眼下还有处于等待的事务和锁，就用对应的表去看清楚。

## 183-MVCC解决读写问题
> 对应分集：P183 | 原始标题：《183-MVCC解决读写问题》

上一章我们把锁讲完了。讲锁的时候就提过一句：并发的事务访问同一条记录，读写之间那点冲突，其实还有另一条路可走。现在这条路正式摆到台面上来了。

### 本讲在课程中的位置

这一节要解决的是什么问题，得先把位置摆清楚。

把这一讲放回整门课的骨架里。MySQL 高级部分的内容被分成四个篇章：

| 篇章 | 章节范围 | 主题 |
| --- | --- | --- |
| 第一篇章 | 第 1 章 ~ 第 5 章 | Linux 环境下的安装，以及整个 MySQL 的架构 |
| 第二篇章 | 第 6 章 ~ 第 12 章 | 索引结构，以及数据库调优，内容量比较大 |
| 第三篇章 | 第 13 章 ~ 第 16 章 | 事务 |
| 第四篇章 | 第 17 章及以后 | 剩下的内容 |

事务这一篇里，我们已经讲完了三个篇章，接下来是第 16 章，多版本并发控制。这一节要解决的问题，就是我刚才说的那个读写冲突。

先说一下这一讲的"分量"落在哪里。从面试的角度讲，问到数据库比较高级的场景，通常就会问到 MVCC——它显然还是偏底层的内容，注意一下这一点。但从实际开发的角度讲，你基本上是碰不到 MVCC 的。为什么？

因为我们平时用数据库，关注的是隔离级别：隔离级别可以去设置，你只要清楚在不同的隔离级别下能解决什么样的并发问题，就可以了。而 MVCC 是隔离级别的再下一层——它管的是在这个隔离级别下，我们**如何**去实现并发、如何更好地实现并发。就是这个场景用到的一项技术。

> **提示**：这并不意味着它不值得学。一方面多学一些应用场景上的技术；另一方面，技术本身也要往深了挖，MVCC 到底解决了什么问题，还是有必要看一看的。

### 并发事务的几种访问行为与两种解决方案

按顺序把话头接上。注意这一节的推导是怎么引下来的，这一点要清楚：MVCC 的用处，在讲锁的时候其实已经提到过了，所以现在先做一次复习，看看当时是在哪儿讲的。

并发的事务访问相同记录，行为其实只有三类。

- **读读**：一个事务读，另一个事务也读。这种场景不会产生任何并发问题，所以允许它们同时读，并发性最好。
- **写写**：两个都要改动记录，所以必须加锁，让它们排队执行。这一类没什么可讲的。
- **读写或写读**：一个读、一个写。这是我们关注的重点，实际开发里也最常见。

读写这一类要守住的东西很明确：在相应的隔离级别下不能有脏读，不能有不可重复读，也不能有幻读。要解决这些问题，有两条路。

#### 读写都加锁的方案

其中一条思路——也就是上一章讲锁时讲的那个——是读和写都采用加锁。

比如针对读操作加一个 `S` 锁（共享锁）；另一个事务要增删改，就过不去了，只能阻塞等待。加锁的最终目的就是排队，所以这种方案会让并发性差一些。加锁本身是上一章的重点内容，这里只要认出它就是这条路的"原版"就够了。

#### 写加锁、读走 MVCC 的方案

那有没有更好的办法？有，这就是 MVCC（Multi-Version Concurrency Control，多版本并发控制）。

它的分工是这样的：**写操作仍然加锁**，也就是让写去使用数据最新的那个版本，这实质上是一种悲观锁的形象；**读操作交给 MVCC 来处理**，而 MVCC 更倾向于乐观锁的场景。

```text
方案一：读写都加锁
   读事务 ──加 S 锁──┐
                     ├── 互斥排队 ── 并发性差
   写事务 ──加 X 锁──┘

方案二：写加锁 + 读走 MVCC
   写事务 ──加锁──→ 最新版本（悲观）
   读事务 ──MVCC──→ 历史版本（乐观）
                     └── 读写不冲突，并发性更好
```

读图说明：两种方案的差别集中在读那一侧——要么读也被锁挡住排队，要么读走 MVCC 拿一个历史版本，从而和正在进行的写互不阻塞。

> **结论**：MVCC 要的就是读跟写不冲突。读不再是阻塞式的，而是非阻塞式的并发读；做到了这一点，并发性就比读写都加锁的方案更好。

把这条线捋一遍就很清楚了：并发访问相同记录有读读、写写、读写三类，前两类一个不用管、一个必须排队，真正要解决的是读写这一类；读写这一类有两条路，一条是读写都加锁，一条是写加锁、读交给 MVCC。MVCC 就是顺着这条线引出来的。

### MVCC 的概述与核心组成

宏观上先有个印象，接下来展开这一章。

#### 定义

> **定义**：顾名思义，MVCC 就是通过数据行的多个版本管理，来实现数据库的并发控制。

它比读写都加锁的效果要好一些。所谓"数据行的多个版本"，说的就是我们那些行记录有多个版本，也就是 `Multi-Version` 这个词的落点。

那么问题来了：多个版本到底怎么体现？先直接抛出来——**通过 undo log 来体现**。事务这一篇讲日志的时候提过它：你对记录做增删改，undo log 把每一个版本都记了下来，版本自然就有了。

再说"管理"这一半：不同事务过来的时候，到底让它看见哪一个版本、看哪一条 undo log 的记录？这个管理是通过 `ReadView` 来体现的。

#### 三要素与一句话回答

MVCC 的实现依赖三样东西：

- **隐藏字段**：里面有一个事务 ID，因为 `ReadView` 的判断要用到它；
- **undo log**：体现"多版本"；
- **ReadView**：体现"并发控制"。

面试里问"你是怎么理解 MVCC 的"，比较高质量的一句话回答就是把这件事抛出来：MVCC 的实现原理依赖于隐藏字段、undo log 和 ReadView。你说这三样行，只说后两样也行——多版本靠 undo log 体现，并发控制你也可以理解成一种管理，谁来管？`ReadView` 来管。所以准确讲，**undo log 加上 `ReadView`，就构成了 MVCC 的核心**。

这一句话抛出去，对方听下来就会觉得你这个回答是靠谱的。

> **提示**：MVCC 并没有正式的标准，在不同数据库管理系统里的实现方式各不相同，它也不是普遍使用的技术。即便在 MySQL 内部，不同存储引擎对它的支持力度也不一样——只有 InnoDB 支持了 MVCC 这套机制。

#### 它给了什么样的保证

用了这套技术，InnoDB 在事务隔离级别下执行一致性读的时候就有了保证。

一致性读这个词听着陌生，它说的其实就是快照读。也就是说，为了查询那些正在被另一个事务更新的行，并且看到它们**被更新之前**的值。

这一点非如此不可：如果看到的是它正在更新中的值，那就成脏读了。而反过来说，如果等人家更新完、把锁释放了你再去读，那就变成了串行，又退回到加锁方案的思路上去了。

换句话讲，MVCC 在这里取的是一个巧劲：我不去碰你手里那份正在改的数据，我去读它**改之前**已经留下的那个版本。改之前的值从哪儿来？就是 undo log 里记着的那些历史版本。所以"读旧版本"这件事本身不用加锁，也就不会和写抢资源。

### 快照读与当前读

上面提了这么多回"读"和"写"，现在把这两个词的正式名字单独说清楚——这也是这一讲最容易被问、也最容易说混的一处。

#### 划分依据

MVCC 主要解决的是上一章讲的那种读写场景冲突，它比读写都加锁的方案更好：不加锁，非阻塞式的并发读。这里的"读"，就是**快照读**；而这里的"写"，对应的概念是**当前读**。

先把两个名字对上：

- **一致性读**，也叫**快照读**，两者是一个意思；
- 与它相对的是**当前读**。

MVCC 给 InnoDB 带来的那份"一致性读的保证"，落在操作上就是快照读这一侧；而写那一侧认的是最新版本，也就是当前读。两边各认各的版本，读写才不打架。

```text
一次读写并发的分工

   写事务 ──→ 加锁 ──→ 读到/改到：最新版本（当前读）
                              │
                              │ 每改一次，旧值进 undo log
                              ↓
                        多版本（undo log 版本链）
                              ↑
                              │ ReadView 决定放哪个版本出来
                              │
   读事务 ──→ 不加锁 ──→ 读到：其中一个历史版本（快照读）
```

读图说明：写这一路走加锁、只认最新版本，同时每次改动都在 undo log 里留下旧版本；读这一路不加锁，由 `ReadView` 从这些版本里挑一个给它看。两条路各走各的，冲突就消掉了。

> **易错点**：不要以为快照读等于"读的一定是旧值"。它读的是 `ReadView` 允许它看见的那个版本，可能是历史版本，也可能就是最新版本。

#### 快照读

在一个具体的事务里，如果你写了一条 `SELECT` 语句，又没有对它做任何加锁行为，那么它就相当于一个快照读，读的是一个快照。

具体是哪一个快照？这就跟 `ReadView` 有关系，得由它来管理。

> **易错点**：快照读有可能读到的并不是最新的数据，有可能是之前的历史版本。注意措辞——是"不一定"读最新的，不是"一定"读旧的，它也可能是新的。

还有一个前提条件：快照读所对应的隔离级别不是串行化。一旦是串行化，那就退化成当前读了——因为事务一个个来，别人都提交了你才能访问，你读到的必然是最新数据。所以：

> **结论**：当前读意味着读记录的最新版本，而不是历史记录的版本。反过来说，凡是要读最新版本的场景，都要付出加锁的成本。

#### 当前读与加锁的关系

回到前面加锁的部分：我们对读操作加锁，或者对增删改操作加锁，这些场景要获取的其实都是当前读。

道理很直白。既然想获取最新版本，那就得付出点成本，这个成本就是加锁。反过来讲，如果我加了锁，读到的还是历史版本，那这个锁就白加了——直接用 `ReadView` 就完事了。所以加锁的主要目的，就是我要读它的最新版本，代价是会带来一定的阻塞。

#### 两种读的对比

| 对比项 | 快照读（一致性读） | 当前读 |
| --- | --- | --- |
| 读到的版本 | 可能不是最新，可能是历史版本，也可能是新的 | 一定是记录的最新版本 |
| 是否加锁 | 不加锁 | 要加锁（读加 `S` 锁，增删改加 `X` 锁） |
| 并发表现 | 非阻塞式并发读 | 会带来一定的阻塞 |
| 由谁实现 | 由 MVCC（`ReadView` 管快照）实现 | 由加锁实现 |
| 典型语句 | 不加锁的普通 `SELECT` | 加锁的读，以及增删改操作 |
| 隔离级别 | 不是串行化 | 串行化下一切读都是当前读 |

> **结论**：MVCC 解决的就是上一章提到的读写冲突问题。这个"读"说的是快照读，而这个"写"一定针对最新版本的数据，也就是当前读，通过加锁的方式去实现。

核心的一句话，理解到这里就够了。

## 184-MVCC三剑客：隐藏字段、UndoLog版本链、ReadView规则
> 对应分集：P184 | 原始标题：《184-MVCC三剑客：隐藏字段、UndoLog版本链、ReadView规则》

要把 MVCC 说清楚，我得先带你们复习两个内容：一个是隔离级别，一个是隐藏字段加 Undo Log 的版本链。这两样储备好了，我们再去看 ReadView，才有落脚的地方——MVCC 的实现原理，就是把这几样东西串起来的结果。

而且这两个复习项里各藏着一句面试里很值钱的说法，我们一边复习一边说。

### 四种隔离级别与 MySQL 的实际表现

事务有四种隔离级别，解决的是三种并发问题，这个应该闭着眼睛都能说出来。四种隔离级别从上往下，并发性越来越差，能解决的问题越来越多：读已提交解决第一个，可重复读解决上面的两个，串行化三个都解决，读未提交一个也不解决。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性 |
| --- | --- | --- | --- | --- |
| 读未提交（Read Uncommitted，RU） | 未解决 | 未解决 | 未解决 | 最高 |
| 读已提交（Read Committed，RC） | 解决 | 未解决 | 未解决 | 较高 |
| 可重复读（Repeatable Read，RR） | 解决 | 解决 | 未解决 | 较低 |
| 串行化（Serializable） | 解决 | 解决 | 解决 | 最低 |

这是 SQL 标准里给出的对应关系。但对 MySQL 来说，这张表其实并不准确。MySQL 默认的隔离级别就是可重复读，而这个默认级别不光解决了脏读和不可重复读，它把幻读问题也一起解决了——主要原因就是我们使用了 MVCC。在 MVCC 下，读的是一个快照，也可以看成乐观锁的一种实现方式，所以幻读不会出现；幻读既然不出现，那就相当于这个问题被解决了。

> **提示**：面试中只要谈到事务隔离级别、提到 MVCC，这个点你一定要主动抛出来，它是一个很高大上的说法——它证明你看的是 MySQL 的真实行为，而不是背 SQL 标准那张表。

不过话说到这里得收住：我们说 MySQL 的可重复读解决了幻读，并不是说 MySQL 就变成串行化了。串行化是靠加锁的方式实现的，事务一个个来，读也好写也好都得排队；而 MVCC 里面针对读是可以不用排队的。所以它不仅解决了幻读，性能相较于串行化还更高。这个区别要能够表达清楚。

### 隐藏字段与 Undo Log 版本链

#### 行格式中的三个隐藏字段

针对具体的每一条记录，它都有自己的行格式，行格式里有三个隐藏字段：

- `row_id`：如果这条记录没有主键，也没有非空的唯一索引，系统就会默认提供这样一个隐藏字段。本讲里它用不着。
- `transaction_id`：记录最近一次更新这条记录的事务 ID。
- 回滚指针（`roll_pointer`）：主要是跟 Undo Log 版本链打交道的。因为事务有可能回滚，我们就需要把"这个事务操作这条记录之前的样子"记下来，最后把这条记录和它的各个历史版本用链表连接起来。这个指针就指向最近的那一批 Undo Log 记录。

> **易错点**：三个隐藏字段里，MVCC 真正用上的是 `transaction_id` 和回滚指针这两个，`row_id` 与版本可见性判断没有关系。

#### 版本链的形成过程

先插一句关于 insert 的 Undo：insert 产生的 Undo 只在事务回滚的时候才会起作用；如果这个事务已经提交，这条 Undo Log 就完全没有作用了，接下来可能被回收，也可能被重用。

看一个具体场景。假设表里只有 `id = 1` 这一条记录，它是由事务 ID 为 `8` 的事务 insert 进去的。insert 完成以后，这条记录的 `transaction_id` 就是 `8`，而它的回滚指针要指向 insert 之前的 Undo——可 insert 之前根本不存在这条记录，没有什么可指的。所以要注意：insert 的 Undo 是没有回滚指针的。

接下来在这条已经存在、并且已经提交的记录上，用另外两个事务做 update：

- 事务 `10` 执行两次 update，把值改成李四，再改成王五，然后 `commit`；
- 事务 `20` 执行两次 update，把值改成钱七，再改成宋八，然后 `commit`。

这两组操作做完，整条 Undo Log 版本链就是这个样子：

```text
链头（最新版本）
   宋八      由事务 20 的 update 产生
    │ roll_pointer
   钱七      由事务 20 的 update 产生
    │ roll_pointer
   王五      由事务 10 的 update 产生
    │ roll_pointer
   李四      由事务 10 的 update 产生
    │ roll_pointer
   张三      由事务 8 的 insert 产生
    │
   NULL     insert 的 Undo 没有回滚指针，版本链到此为止
链尾（最旧版本）
```

读图说明：回滚指针把各个版本从新到旧串成一条链，链头的宋八就是最新数据；每一条 Undo 记录里都记着操作这条数据时的事务 ID，所以顺着链走一遍，就等于把这条记录的修改历史从后往前读了一遍。

有同学会发现一个特点：链上两个 `10` 是挨着的，两个 `20` 也是挨着的。有没有可能交叉操作呢——我把张三改成李四，紧接着用田七覆盖李四，再用王五覆盖田七，最后用宋八覆盖王五？

不可能。update 的时候会开启事务并加 X 锁，另一个事务再来访问这条记录就阻塞了，只能等前一个事务的两条 update 都执行完、排他锁释放之后，它才能进来操作。所以同一个事务产生的版本在版本链上必然是相邻的。

### MVCC 的三个核心结构

回过头看整体。MVCC 的实现原理依赖三个结构：

1. 隐藏字段，实际用到的是 `transaction_id` 和回滚指针这两个；
2. Undo Log 版本链，就是上面串起来的那条链；
3. ReadView，三个里面最核心的一个。

MVCC 叫多版本并发控制。这里所谓的"多版本"，指的就是 Undo Log 里的这些历史版本，也就是我们说的历史快照。对这些历史数据做读操作，对应的就是快照读。

而版本链上躺着这么多历史版本，不同的事务过来，到底该读哪一个？这个管理行为就由 ReadView 来体现——它解决的是 Undo Log 里的哪些版本对当前这个读事务可见、哪些不可见。

> **定义**：ReadView 是某一个事务在使用 MVCC 机制进行快照读操作的时候产生的一个读视图。它和事务是一对一的关系：是我们这个具体的事务要读，才会生成这个读视图。

这句话想明确的就是那个一对一。事务 A 想读，我们就为它生成一个读视图的快照，这个快照就是它的 ReadView。

生成快照的时候，InnoDB 会为这个事务构造一个数组。也就是说，ReadView 里存的是好多数据，用的是数组这种数据结构，记录的内容是系统当前活跃的事务 ID。

> **定义**：活跃的事务，指已经启动、但是还没有提交的事务。反过来说，已经提交的事务不会被记进当前这个 ReadView 里。

到这一步，ReadView 被烘托得已经很到位了——要干什么、里面放什么，都已经想好了，有点像孩子的名字都想好了、人还没追上，接下来就得看它到底怎么落地。落地的第一件事，是先明确它服务于哪几种隔离级别。

### MVCC 适用的隔离级别

ReadView 也好、MVCC 也好，都只针对**读已提交**和**可重复读**这两种隔离级别来谈。另外两种隔离级别里根本不会用到 MVCC，原因一看就清楚。

- **读未提交**（RU）下，我们本来就能读到未提交的数据，这就是脏读——这个隔离级别没有解决脏读问题。既然你读到的就是最新的记录，那你跟历史快照有什么关系？ReadView 要解决的是历史快照的读取问题，读最新数据根本用不着它，那 MVCC 也就用不上了。
- **串行化**（Serializable）下，靠的是加锁，事务全都得排队，读也好写也好，一个一个来。既然能轮到你去读，就说明别的事务现在都没有在改，所以你读到的也一定是最新的数据。既然读的是最新数据而不是快照，ReadView 和 MVCC 在这里同样没有意义。

而读已提交和可重复读这两种级别，读的时候都用到了快照这个行为，都要保证读到的是"已经提交的事务修改过的记录"——要是把没提交的读出来，那不就成脏读了吗？所以这两种级别下脏读是被解决的，你读到的一定是已提交事务改过的值。已经提交的事务改过什么，在相应的日志里是有记录的，剩下的判断就交给 MVCC 来做。

> **结论**：MVCC 主要针对读已提交和可重复读这两种隔离级别。核心问题只有一个——Undo Log 版本链上有好几个版本，现在来了一个事务要读，哪一个版本对它可见、哪一个不可见？

还是拿上面那条记录举例。现在有一个事务要查询：它是让我读宋八，还是读钱七、王五、张三？这个才是要解决的核心问题。

### ReadView 的四个判定字段

ReadView 的结构不需要我们自己设计——没必要像当初讲索引那样自己搭一棵 B+ 树，这里直接看它有什么就行。它里面固定有四个内容。

| 字段 | 含义 |
| --- | --- |
| `creator_trx_id` | 创建这个 ReadView 的事务 ID，也就是"谁生成了我" |
| `trx_ids` | 生成 ReadView 的那一刻，系统里活跃的读写事务 ID 列表 |
| `up_limit_id` | `trx_ids` 中的最小值 |
| `low_limit_id` | 生成 ReadView 时，系统应该分配给下一个事务的 ID 值 |

#### 四个字段各自的含义

在讲 `creator_trx_id` 之前，先明确事务 ID 怎么来：只有对表中的记录做增删改，系统才会分配一个事务 ID，分配方式是依次递增——现有的 ID 用掉了，再分配一个就接着往上加。如果只是一个读事务，它的 ID 是 `0`。前面例子里出现的 `10`、`20`，都是因为对表里的记录做过修改才拿到这些号；光读的事务一直是 `0`，这个要注意。

`creator_trx_id` 就是创建这个 ReadView 的事务自己的 ID。前面说了，ReadView 和事务是一对一的，所以这个字段回答的就是"你是谁"，或者说"是谁的操作导致这个 ReadView 被创建"。

`trx_ids` 是事务 ID 的列表，但它有一个定语一定要小心：它是**活跃的**读写事务 ID 列表。活跃就是已经启动了、但还没有提交。一个事务一操作、生成了 ReadView 的那一刻，我们就看当前系统里还有哪些事务没有提交、还活着，把它们记进这个列表里；已经提交过的事务，一个都不会放进来。

`up_limit_id` 是活跃列表里最小的那个事务 ID。这里有个反直觉的地方——它名字里带 `up`，但取的是小的那个值。

`low_limit_id` 是生成 ReadView 时系统应该分配给下一个事务的 ID 值。这句话读起来不顺，它的真实含义是：系统里已经出现过的最大事务 ID，再加一。

> **易错点**：`low_limit_id` 不是"活跃列表里的最大值加一"，而是"系统最大事务 ID 加一"。已经提交的事务也要考虑在内，因为已提交的事务里完全可能存在比活跃列表更大的 ID。

#### low_limit_id 取值的两个例子

第一个例子：假设目前有三个事务 `1`、`2`、`3` 在操作某个结构，现在我们又生成了一个读事务（不是这三个中的一个），生成它的 ReadView 时，事务 `3` 已经提交了。

```text
系统已出现过的事务 ID：1、2、3，以及更大的 5
生成 ReadView 的那一刻        →   trx_ids = {1, 2}      （3 已提交，不在列表里）

up_limit_id  = 1                    活跃列表中的最小值
low_limit_id = 5 + 1 = 6             系统最大事务 ID 加一，与活跃列表无关
```

读图说明：有人会顺着活跃列表算，认为最大值 `2` 加一等于 `3`，那就错了。活跃列表里最大的是 `2`，但 `low_limit_id` 取的是整个系统里出现过的最大事务 ID（这里是 `5`）再加一——已提交的事务也要算进来。

第二个例子更直观：生成这个读事务的 ReadView 时，当前一共有四个活跃事务，对应的 ID 是 `2`、`3`、`5`、`8`。

```text
trx_ids      = {2, 3, 5, 8}
up_limit_id  = 2                    列表中的最小值

假设没有比 8 更大的事务（别的事务都已提交，提交的里也没有超过 8 的）
low_limit_id = 8 + 1 = 9            系统最大事务 ID 加一
```

读图说明：列表里最小的是 `2`，所以 `up_limit_id` 取 `2`；而 `low_limit_id` 与列表里的最大值没有直接关系，它看的是整个系统出现过的事务 ID 的最大值——这里活跃的 `8` 恰好就是最大值，已提交的事务里也没有超过它的，加一就得到 `9`。

### 版本可见性的判定规则

ReadView 的结构清楚之后，就来看它具体实施时的规则。访问某条记录的时候，按照下面这几步判断一个版本是否可见。

被访问的那个版本，它的 `transaction_id` 记为 `T`。举个例子，我们执行这样一次查询：

```sql
SELECT * FROM student WHERE id = 1;
```

对 `id = 1` 这条记录来说，版本链上从链头到链尾有宋八、钱七、王五、李四、张三这么几个版本。被访问的版本不一定是链头那一个，但我们的查找是从链头开始的，下面就以链头这类版本作为"被访问的版本"来讲。

**规则一：`T` 等于 `creator_trx_id`，可以访问。**

拿链头的宋八来说，它的事务 ID 是 `20`；如果生成这个 ReadView 的事务，自己的 ID 也是 `20`，那就相当于你自己往这条记录里改了数据、又自己想查——自己改的自己查肯定没问题，所以这个版本可以访问，宋八就能被查出来。

**规则二：`T` 小于 `up_limit_id`，可以访问。**

`up_limit_id` 是活跃列表里的最小值，而系统的事务 ID 是依次递增往上分配的。一个版本的事务 ID 比"活着的最小事务 ID"还小，说明列表里的每个值都比它大，它不可能是活跃的——产生这个版本的事务肯定早就结束了，相当于已经提交过。既然已经提交，那这个版本就可以访问：读已提交下都能读到，可重复读更不用说。

**规则三：`T` 大于或等于 `low_limit_id`，不能访问。**

`low_limit_id` 是系统最大事务 ID 加一。一个版本的 `transaction_id` 一旦不小于这个值，就说明产生这次修改的事务是在我们生成 ReadView 之后才出现的——它是后来的事务。人家后来的，我们这个读视图就不应该承认它，所以这个版本不能被访问。不能访问就顺着版本链往后找更旧的历史版本。

**规则四：`T` 落在 `up_limit_id` 与 `low_limit_id` 之间，要再查一次 `trx_ids` 列表。**

落在这一范围内可能有好几个版本，但它们的 `transaction_id` 不一定真的出现在列表里，所以要再判断一次：这个值跟列表里的几个值有没有相等关系。

- 如果列表里正好有它，说明产生这个版本的事务现在还是活跃的，也就是还没有提交——既然没提交，就不能访问；
- 如果列表里没有它，说明这个事务已经不活跃了、已经提交了，那就可以访问。

四条规则连起来是这样一棵判断树：

```text
被访问版本的 transaction_id = T

步骤 1   T 等于 creator_trx_id ？
            是 → 可见（自己改的，自己读）

步骤 2   T 小于 up_limit_id ？
            是 → 可见（比最小活跃事务还小，早已提交）

步骤 3   T 大于等于 low_limit_id ？
            是 → 不可见（这是 ReadView 生成之后才出现的事务）

步骤 4   T 在 [up_limit_id, low_limit_id) 范围内：
            T 在 trx_ids 列表中   → 该事务仍活跃，尚未提交 → 不可见
            T 不在 trx_ids 列表中 → 该事务已提交           → 可见

判为不可见的 → 顺着回滚指针取下一个更旧的版本，从步骤 1 重新开始
```

读图说明：四条规则按从上到下的顺序判，前一条不成立才看下一条；只要落到步骤 4，判定依据就是"这个版本的事务 ID 还在不在活跃列表里"。所谓不能访问，并不是这次查询就结束了，而是换版本链上的下一个更旧的版本重新判一遍。

### 一次快照读的完整流程

把这几步接起来，一次查询的完整流程就是下面这样：

1. 在事务中执行查询语句，先获取这个查询事务自己的 ID 号；
2. 紧跟着为这个事务生成一个 ReadView，跟事务是一对一的关系；
3. 查询拿到数据后，从版本链的链头（最新版本）开始，把这个版本的 `transaction_id` 与 ReadView 里的内容做比较；
4. 如果不符合规则、判为不可见，就顺着回滚指针往下找版本链里的下一个版本，依次往下——越往后历史数据越旧，越靠前数据相对越新；
5. 一直找到符合规则的那个版本，它就是这次查询读到的数据。

如果依次找下去，一直找到版本链末尾都不可见，那就说明这条记录对你没有可见的版本，这次查询的结果里就不包含这条记录。这里讲的是 MVCC 针对读操作的部分，读都对你不可见了，结果里自然就没有它。

```text
事务中执行 SELECT
    │
    ├─ 1. 获取这个读事务自己的 ID
    ├─ 2. 为它生成一个 ReadView（creator_trx_id / trx_ids / up_limit_id / low_limit_id）
    ├─ 3. 从版本链链头（最新版本）开始，用版本的 transaction_id 与 ReadView 比较
    ├─ 4. 不可见 → 顺着回滚指针取下一个更旧的版本，回到第 3 步
    └─ 5. 第一个符合规则的版本 → 它就是本次查询读到的数据
          整条链都不可见       → 本次查询结果不包含这条记录
```

读图说明：判断永远从最新版本起步，一次不行就往旧版本退一步，第一个可见的版本就是结果；整条链走完都没有可见版本，这条记录就不会出现在查询结果里。

### ReadView 的生成时机

还剩一个问题要说清楚：ReadView 和事务是一对一，可一个事务里我可以读很多次，那到底是每次读都生成一个新的 ReadView，还是怎么回事？这就跟隔离级别有关系了。这个结论你记住就行，它也是设计出来的——只有这样设计，对应隔离级别要解决的问题才是准确的。

- **读已提交**：每做一次查询，都要重新获取一次 ReadView；每读一次获取一次。
- **可重复读**：只在第一次 `SELECT` 的时候生成 ReadView，后面再读不再生成。

为什么读已提交要每次读都重新获取？因为 ReadView 保证的是你能读到已提交的数据，而不同次数的读之间如果换一张新快照，就有可能读到别人刚提交的新版本，也就是出现不可重复读的数据——这恰恰是读已提交这种行为要允许的，不然它就跟可重复读没区别了。

可重复读正好相反：后面再读就不让你生成 ReadView 了，一直用最初的那一个。这样一来，你每次读出来的数据都是重复的，不可能出现不可重复读。

> **结论**：读已提交下每读一次获取一次 ReadView；可重复读下只在第一次 `select` 时生成 ReadView，后续查询一直沿用最初那一个。

ReadView 的四个字段和判定规则，到这里就说清楚了——它是 MVCC 实现原理里最核心的那一环，也是后面在两种隔离级别下走完整流程的底子。

## 185-MVCC在读已提交和可重复读隔离级别下的操作流程
> 对应分集：P185 | 原始标题：《185-MVCC在读已提交和可重复读隔离级别下的操作流程》

上面我们已经把 ReadView 的设计规则和 MVCC 的整体操作流程说清楚了。如果你听完之后觉得很清楚、一目了然，那特别好；如果你听完那两个结构之后还有点迷糊，也没有必要翻回去重看一遍，我们直接上例子：例子讲完你就清楚了，或者至少比盯着规则更容易清楚。这是第一件事。

还有第二件事：面试里如果问到 MVCC 的具体操作流程，你既可以照着我们上面讲的 ReadView 规则和整体流程去说，也可以举一个例子来讲，这同样是可以的。因为例子只是上面那套结构的一次具体展示而已。下面就把这个例子走一遍。

### 例子的场景设定

我们有一个大背景：`student` 表里有一条记录，`id` 为 1，这条记录是由事务 id 为 `8` 的事务插入的。整个例子都在这条记录上做文章。

讲的时候分成两个大方向。原因在于 MVCC 只在读已提交和可重复读这两个隔离级别下起作用，所以我们就分别在 `Read Committed`（读已提交，RC）和 `Repeatable Read`（可重复读，RR）这两个隔离级别下各走一遍整体流程。另外，可重复读还能解决幻读问题，顺便也要把幻读是怎么被解决的讲清楚。

下面先讲 `Read Committed`。

#### 事务 id 的分配

例子里会用到几个事务 id，这里先把它们是怎么来的说清楚。

一个事务 id 是由系统分配的。如果你执行的是增删改这类行为，系统会给你分配一个具体的 id 值，按依次递增的方式分配；但如果你执行的是一个查询行为，这个 id 值就是 `0`。

> **易错点**：例子里的 `20` 之所以特意写成"更新了一些别的表的记录"，就是为了让系统给它分配一个非 0 的数。如果它什么都没做，它就只能是 `0`，后面拿它跟活跃列表比较就没有意义了。这个 `20` 的作用仅此而已，它跟 `student` 表里那条 `id = 1` 的记录没有任何关系，也不会在那条记录上留下版本。

#### 初始版本链的形成

场景是这样的：有两个写事务，一个 id 是 `10`，一个 id 是 `20`，都准备去改 `id = 1` 这条记录。

最开始，事务 `10` 对 `id = 1` 这条记录做了更新，把张三改成李四，又改成王五。事务 `20` 目前什么都没做（它只是去更新了一些别的表的记录，好拿到一个非 0 的 id）。这时事务 `10` 和事务 `20` 都还没有提交。

两次更新执行完之后，`id = 1` 这条记录上就形成了下面这样的 undo 版本链：

```text
王五   trx_id = 10   roll_pointer ──┐
                                   ↓
李四   trx_id = 10   roll_pointer ──┐
                                   ↓
张三   trx_id = 8    roll_pointer ──→ NULL
```

读图说明：链头是最新版本王五，顺着 `roll_pointer` 往回走依次是李四和最初由事务 `8` 插入的张三；张三身后没有更早的版本，指针为空。链上每个版本记的都是产生它的那个事务 id，而事务 `20` 没有在这条记录上留下任何版本。

### 在读已提交隔离级别下的操作流程

先明确这个隔离级别的规则：在读已提交下，事务**每 `SELECT` 一次就会生成一个 `ReadView`**。这条规则很重要，所以我又重复了一遍。下面就基于这个规则往下走。

#### 首次查询的 ReadView 与张三版本可见性

现在有一个事务 `begin` 了，它执行：

```sql
SELECT * FROM student WHERE id = 1;
```

注意，此时事务 `10` 和事务 `20` 都还没有提交。在读已提交这个隔离级别下，你猜查出来是谁？应该是张三。下面就来解释为什么查出来是张三。

第一步，生成 `ReadView`。你这条 `SELECT` 一执行，就会生成一个 `ReadView`。这个快照里记录了三样东西：

- 谁生成了我：是当前这个读事务自己，所以你的 id 是 `0`；
- 生成快照的时候哪些事务还活着：`10` 和 `20` 这两个是活跃的，所以列表里有 id 为 `10` 和 id 为 `20` 的这两个事务；
- 其中比较小的那个是 `10`，往上我给成一个 `21`。

这个 `21` 可以理解为：除了这两个之外，系统可能还用过别的事务，但它们都不会超过 `20`，`20` 是目前为止最大的一个活跃事务，所以取它加一得到 `21`。后面的场景里也是同样的算法，我就不每次都解释一遍了。

第二步，从版本链里挑可见的记录。首先挑到的是链头的王五，它的事务 id 是 `10`：

- 这个 `10` 跟我们自己的 creator 不一样；如果一样，那王五就直接读出来了；
- 这个 `10` 落在"小于 21"这个范围里；
- 并且它恰好就在活跃列表 `{10, 20}` 里边。

在列表里就意味着这个事务现在还活跃，也就是还没有提交。既然没提交，王五能查出来吗？肯定不行。那就只能找下一个版本。

下一个版本是李四，一看又是 `10`，还是活跃的，还是不行。再往下找到了 `8`：`8` 不在活跃列表里，而且比 `10` 还小，说明它一定是一个之前已经提交过的事务。既然已经提交，这条记录就应该读出来，最终结果就是张三。

> **结论**：读已提交下"已提交"是靠活跃列表判出来的。比最小活跃事务还小，表示这个版本的产生者早就结束了（提交或回滚），所以可以读；落在列表里或者不小于 `21`，都表示它不该被你看见。

#### 事务 10 提交后第二次查询读到王五

接着往下操作：我们把事务 id 为 `10` 的这个事务提交了，执行了一次 `commit`。提交之后，事务 `20` 去更新表记录，把 `id = 1` 的记录改成钱七，又改成宋八。这些操作执行完，这条记录上的版本链就变成了：

```text
宋八   trx_id = 20   roll_pointer ──┐
                                   ↓
钱七   trx_id = 20   roll_pointer ──┐
                                   ↓
王五   trx_id = 10   roll_pointer ──┐
                                   ↓
李四   trx_id = 10   roll_pointer ──┐
                                   ↓
张三   trx_id = 8    roll_pointer ──→ NULL
```

读图说明：事务 `20` 的两次更新把两个新版本压到了链头，事务 `10` 的那两个版本被压在下面，但它们并没有消失——这正是读已提交下"提交后还能读到旧值"的基础。

现在还是刚才那个读事务，我又读了一次。注意我们处在读已提交，**每读一次就生成一个 `ReadView`**，所以这一次读又生成了一个新的 `ReadView`。

这个新 `ReadView` 里，事务 `10` 已经提交了，活跃列表只剩 `20`；读事务的 id 还是 `0`；上界 `low_limit_id` 还是 `21`。在这个场景下判断：

- 先看链头的宋八，事务 id 是 `20`，在列表里还是活跃的，说明人家还没提交——你读已提交，就不能用它这个宋八；
- 再往下，钱七还是 `20`，还是不行；
- 再往下是王五，事务 id 是 `10`：它不在列表里，而且比列表里的数还小，说明这个事务已经提交过了。

这里"比列表里的数还小"为什么能推出已提交？因为反过来想：如果它比列表里的值大，就说明它是在你生成这个 `ReadView` 之后才做的修改，那是一个后来的事务 id，你更不能去用它的版本。所以必须满足"不在活跃列表里，并且比列表里的值小"，才表示它是在我生成 `ReadView` 之前就已经提交的事务，我应该把王五读出来。

所以这一次读到的是王五。

> **易错点**：`ReadView` 两个边界的命名是反着的——`up_limit_id` 取的是活跃列表里的**最小值**（下界），`low_limit_id` 取的才是**上界**（系统已经出现过的最大事务 ID 加一）。照着名字望文生义，十有八九会把这两个值用反。

#### 事务 20 也提交后：宋八可以读了

以此类推，把事务 id 为 `20` 的这个事务也提交了。它一提交，活跃列表里就没有它了。这时候链头的宋八事务 id 是 `20`，它已经不活跃，而且比列表里的值还小，相当于它是已经提交的事务，于是宋八就能读出来了。

这就是 `Read Committed` 下的完整场景。

```text
RC：三条 SELECT 的可见性判断

① 事务10、20 均未提交
   活跃列表 {10, 20}，up_limit_id=10，low_limit_id=21
   王五(10) 在列表内 → 不可见
   李四(10) 在列表内 → 不可见
   张三( 8) 不在列表且 < 10 → 可见      结果：张三

② 事务10 已提交，事务20 未提交
   活跃列表 {20}，up_limit_id=20，low_limit_id=21
   宋八(20) 在列表内 → 不可见
   钱七(20) 在列表内 → 不可见
   王五(10) 不在列表且 < 20 → 可见      结果：王五

③ 事务10、20 均已提交
   活跃列表 {}，low_limit_id=21
   宋八(20) 不在列表且 < 21 → 可见      结果：宋八
```

读图说明：三次查询各自生成一个 `ReadView`，活跃列表从 `{10, 20}` 收缩到 `{20}` 再到空集，所以同一条记录先后读出了张三、王五、宋八三个不同的值，这就是不可重复读。

### 在可重复读隔离级别下的操作流程

顺着往下说，我们现在处在 `Repeatable Read` 这个隔离级别下。

这个隔离级别的规则，我再强调一下：**只有第一次执行查询语句的时候才生成 `ReadView`，之后你再查询就不再给你生成了**。

#### 首次查询的 ReadView 与读已提交一致

我们还是回到最开始的场景：`id = 1` 这条记录最初只有张三这一个版本。然后接入可重复读的设定，还是事务 id 为 `10` 的这个事务去 `update` 两次，事务 `20` 那边什么都没做。目前看到的就是和上面一样的初始版本链。

在这个场景下，事务开启以后我们做了一次 `SELECT`。首次 `SELECT` 会生成一个 `ReadView`，内容和上一节第一次读时完全一致：creator 是 `0`，活跃列表是 `{10, 20}`，上界 `low_limit_id` 是 `21`。

判断过程也和读已提交的第一个环节一模一样，没有什么可多说的：先看链头是 `10`，一看是活跃的，不行；下一个还是 `10`，还是不行；再往下是 `8`，`8` 不在列表里，而且比列表里的值还小，说明已经提交过，于是把张三读出来。

#### 事务 10 提交后再读：ReadView 不再生成

紧接着，我们把事务 `10` 提交了；事务 id 为 `20` 的这个事务做了两次更新。大体场景和上面一样。

注意，现在的关键差别在这里：刚才那个读事务又读了一次。因为我们在可重复读隔离级别下，**这一次读不再生成 `ReadView`**。所以这时候我们手里用的 `ReadView` 还是你刚才那一个，完全不动，直接拿过来用。

拿这个旧 `ReadView` 去判断，结果就变了：

- 宋八，事务 id 是 `20`，在你这个旧 `ReadView` 里，`20` 还在活跃列表里，不能用；
- 钱七，还是 `20`，也不能用（实质上事务 `20` 现在确实还是活跃的，但即便不是，这个旧 `ReadView` 也不会承认）；
- 王五，事务 id 是 `10`。事务 `10` 虽然在真实世界里已经提交了，可我现在用的 `ReadView` 是你首次 `SELECT` 时的那个，它里面还记着 `10`。所以按这个 `ReadView` 看，事务 `10` 仍然活跃，只要它在这个列表里，我们就不能用它。

这两个都不能用，那就继续往下找，找到了 `8`：`8` 不在列表里，而且比列表里的值还小，相当于它已经提交过了，于是还是把张三读出来。

整体上看，在可重复读隔离级别下，第一次读是张三，事务 `20` 没提交时第二次读还是张三。这就达到了可重复读的效果，也就规避了不可重复读的并发问题。

#### 事务 20 提交后再读：结果仍不变

接着再说：如果我把事务 `20` 也提交了呢？把它也提交以后，我们再去 `SELECT`，无所谓。你再 `SELECT`，用的还是第一次那个 `ReadView`。那个 `ReadView` 里边有 `20`，只要有 `20`，你就不能用它，所以读出来还是张三。

也就是说，**只要这个读事务自己没结束，用的就一直是第一次生成的 `ReadView`**，你不会把事务 `10` 和事务 `20` 的新版本查出来，读出来永远是张三，这就叫可重复读。

```text
RR：三次查询共用同一个 ReadView

首次 SELECT 生成 ReadView
   creator = 0 ，活跃列表 {10, 20} ，up_limit_id = 10 ，low_limit_id = 21
        │
        ├─ 事务10 提交、事务20 连续更新两次
        │     第二次 SELECT → 不生成新 ReadView，沿用上面那个
        │        宋八(20) 在列表内 → 不可见
        │        钱七(20) 在列表内 → 不可见
        │        王五(10) 仍在列表内 → 不可见
        │        张三( 8) 不在列表且 < 10 → 可见   结果：张三
        │
        └─ 事务20 提交
              第三次 SELECT → 仍沿用同一个 ReadView
                 宋八(20) 仍在列表内 → 不可见
                 最终仍为 张三
```

读图说明：可重复读下活跃列表被冻结在首次查询那一刻，后面发生多少次提交都改不动它，所以三次查询始终落在张三这个版本上。

### 两个隔离级别的差异与结论

把两种隔离级别摆在一起，差异只有一处，但结果完全不同。

| 对比项 | 读已提交（RC） | 可重复读（RR） |
| --- | --- | --- |
| `ReadView` 生成时机 | 每执行一次 `SELECT` 生成一个 | 只在第一次执行查询语句时生成一个 |
| 后续查询使用的快照 | 每次都换新的 `ReadView` | 一直沿用首次生成的那个 `ReadView` |
| 已提交事务的新版本 | 下一次查询就能读到 | 只要它还在首次的活跃列表里就读不到 |
| 同一读事务内的读结果 | 可能不同（张三 → 王五 → 宋八） | 始终相同（张三 → 张三 → 张三） |
| 对应的并发问题 | 存在不可重复读 | 规避了不可重复读，还能解决幻读 |

> **结论**：MVCC 在 RC 与 RR 下的版本链、可见性判断规则、以及首次查询的结果都完全一样，唯一的变量就是 `ReadView` 的生成时机。RC 每次读都刷新快照，所以能读到别人刚提交的数据；RR 只认第一次的快照，所以别人提交多少次都影响不了我这一次事务的读结果。

> **提示**：可重复读的"可重复"只对这个读事务自己成立。一旦这个事务结束、重新开启一个事务再查，生成的就是全新的 `ReadView`，那时宋八自然就读得到了。不要把"可重复读"理解成这条数据永远不变。

## 186-MVCC在可重复读下解决幻读的流程
> 对应分集：P186 | 原始标题：《186-MVCC在可重复读下解决幻读的流程》

前面我们把 MVCC 在两套隔离级别下的操作流程都走了一遍，但还剩一个问题没有正面回答：它到底是怎么把幻读也给解决的？下面专门来看这件事。

不过在动手之前，有一句话必须先说清楚——既然要谈的是幻读这个并发问题，那它就一定得放在 `Repeatable Read`（可重复读，RR）这个隔离级别下来讲。大家把这个大前提记住：后面所有的演示，都建立在可重复读之上。这一点含糊不得。

### 场景设定

我们表里目前只有一条数据，我先把这条数据的简要情况罗列出来：它是 `id = 1` 的一条记录，而最近一次修改它的事务 id 是 `10`。

问题的描述这样展开：现在有两个事务，一个叫事务 A，事务 id 是 `20`；另一个叫事务 B，事务 id 是 `30`。

事务 A 先做一次查询，语句是：

```sql
SELECT * FROM student WHERE id >= 1;
```

假设表里眼下就只有那一行记录。这次查询的时候，前面那个事务 id 是 `10` 的修改早已提交过了，所以这一条记录会被查出来，这没有问题。

关键在下一步。此时事务 A 并没有结束——它一直没结束——而在它没结束的情况下，事务 B 往表里新插入了两条数据，两条新数据的 `id` 都比 `1` 要大。插完之后，事务 A 再查一次，发现表里多了两条记录，这就叫幻读问题。

> **定义**：同一个事务，前后两次执行同样的查询，后一次看到了别的事务新插入的行——这多出来的行就是幻影，这个现象就叫幻读。

那为什么说能解决幻读？意思就是：在事务 B 插完这两条记录之后，事务 A 再去查，看到的仍然只有那一条记录。这就等于把幻读解决了。下面看它是怎么保证的。

```text
时间轴（RR 隔离级别）

事务 A (trx_id = 20)                事务 B (trx_id = 30)
─────────────────────              ─────────────────────
BEGIN
SELECT id >= 1
  → 生成 ReadView（就这一次）
  → 读到 1 条                      INSERT 两条（id > 1）
                                   （此时 B 仍活跃）
SELECT id >= 1   ← 沿用上面那个 ReadView
  → 仍然是 1 条
```

读图说明：事务 A 的两次查询夹着事务 B 的两次插入，但第二次查询用的是第一次查询留下的那个 `ReadView`，所以插入的记录进不了它的视野。

### 第一次查询：ReadView 的生成与判断

在事务 A 里做第一次查询。注意这是**首次**执行查询，于是就会生成一个 `ReadView`。

> **提示**：可重复读这个隔离级别只用第一次查询时生成的那个 `ReadView`，后面再查都复用它。这正是后面幻读能被挡住的全部原因。

那么这一次生成的 `ReadView` 里是什么内容？此刻活跃的事务有两个，一个是 `20`，一个是 `30`。这个 `ReadView` 是由事务 `20` 在查询时生成的，所以它记下来的信息是：

- 生成者：事务 `20` 自己；
- 活跃列表：`{20, 30}`；
- 上限值：`30 + 1 = 31`。

接下来执行那条语句，按理说从表里应该只能查到一条。但这一条到底能不能查出来，不是想当然的事，得老老实实做一次判断。

我们看这条记录的事务 id 是 `10`。拿它跟 `ReadView` 里的活跃列表比：`10` 比列表里最小的那个（也就是 `20`）还要小。比最小的活跃事务还小，说明这个事务在生成快照之前就已经执行完了，而且它不在活跃列表里——没活跃，就意味着它已经提交了。

既然已经提交，这条记录就应该被查出来。而当时表里也只有这一条记录，所以第一次查询顺利把它读到了，一切正常。

### 第二次查询中新插入记录的可见性判断

紧接着，在事务 A 没有结束的前提下，事务 B 往表里 `INSERT` 了两条记录。现在表里就是三条记录了。我们仍然执行同一条查询语句，理论上好像能看到这三条，但关键还是老问题：这三条记录是不是都能查出来？得一条一条做判断。

第一条记录刚才已经判过了，肯定可见。关键在新插入的这两条，它们的事务 id 是 `30`。

这时就要用到刚才那条规则了：我们处在可重复读隔离级别下，**这一次 `SELECT` 不会再生成 `ReadView`，用的还是第一次查询留下的那个**。所以判断依据仍然是最初那份信息，其中活跃列表还是 `{20, 30}`。

拿着这份快照去看事务 id 为 `30` 的两条记录，会看到什么？`30` 还在这份活跃列表里，还被认为处在活跃状态。既然它落在列表内，那这个数据能不能用？显然不能用，我们就不应该把它读出来。

那既然这两条不能用，是不是就只能读出那一条？是的。也就是说，再执行一条同样的 `SELECT`，后插入的这两条记录根本不会被读出来——幻读自然就不会发生了。

> **易错点**：判断的是 `ReadView` 里记的状态，不是此刻的真实状态。事务 B 可能已经提交了，但只要 `30` 还留在首次生成的活跃列表里，这条快照就永远不承认它的版本。

```text
RR：首次 SELECT 生成 ReadView 后，第二次判断

ReadView：creator = 20 ，活跃列表 {20, 30} ，上限 31

  id = 1   trx_id = 10
           10 < 20（比最小活跃事务还小）
           且 10 不在 {20, 30} 内 → 早已提交 → 可见

  id > 1   trx_id = 30
           30 落在 {20, 30} 内 → 仍视为活跃 → 不可见
  id > 1   trx_id = 30
           30 落在 {20, 30} 内 → 仍视为活跃 → 不可见

  结果：只读出 1 条，插入的两条被挡住
```

读图说明：三条记录走的是同一套规则，差别只在事务 id 落在活跃列表的哪一侧；`10` 落在左侧所以可见，`30` 落在列表内所以被挡下。

### 读已提交隔离级别下的对照

如果把隔离级别换到 `Read Committed`（读已提交，RC），同一个操作序列会不会产生幻读？

症结在于快照的生成时机变了。读已提交下，**每执行一次 `SELECT` 就重新生成一个 `ReadView`**。所以事务 A 第二次查询时拿到的是全新的一份快照，而不是原来那份。

不过这里有个细节要分清：重新生成快照不等于立刻就能看见。如果此刻事务 B 还没提交，那么新快照的活跃列表里仍然有 `30`，那两条记录还是不可见。可一旦事务 B 提交了，情况就反过来了——列表里不再有 `30`，新快照里 `30` 既不活跃、又比列表中的值小，相当于它已经提交，于是那两条数据就能被看到了。

同一条语句、同一个事务，头一次读出一条、后一次读出三条，这就叫幻读。

| 对比项 | 读已提交（RC） | 可重复读（RR） |
| --- | --- | --- |
| `ReadView` 生成时机 | 每次 `SELECT` 都重新生成 | 只在首次查询时生成 |
| 事务 B 提交后，插入的记录 | 新快照能读到 | 旧快照仍判定为活跃，读不到 |
| 同一事务内两次查询的行数 | 1 条 → 3 条，出现幻读 | 1 条 → 1 条，幻读被挡住 |
| 所依赖的快照 | 每次读的最新快照 | 冻结在首次查询那一刻的快照 |

读图说明（表）：两种级别的差别只有快照生成时机这一处，但正是它决定了新插入的记录能否进入视野。

> **结论**：可重复读解决幻读，靠的不是把新记录删掉，也不是给它加锁，而是靠"快照只生成一次、之后一直复用"——新插入的行产生于快照生成之后，其事务 id 被永久记在活跃列表里，因此在该事务结束之前始终不可见。

### MVCC 的适用范围与组成

到这里 MVCC 就讲得比较透彻了。最后收个尾，把需要真正掌握下来的几条列清楚。

第一，先明确适用范围：MVCC 只在读已提交和可重复读这两个隔离级别下才有效。因为只有这两个级别在读的时候才会考虑"是不是要用快照"。剩下的读未提交和串行化，其实都可以理解成读的是最新数据，所以用不到 MVCC。

第二，MVCC 针对的是什么问题？就是上一章提到的那种读写、写读互相影响的情况。处理这类问题有两种方案：一种是把读和写都加上锁；另一种就是我们现在选的 MVCC，读的是快照数据。选后者的好处是能提高并发性——这一点要清楚。

第三，两套级别的差别落在快照生成时机上：读已提交每一次 `SELECT` 都生成 `ReadView`；可重复读只在第一次 `SELECT` 生成，后面一律复用。正因为有这个特点，不可重复读和幻读这两个问题才被解决。

#### delete mark 标记与真实删除的区别

这里顺带补一个前面讲过的小知识点。我们说 `DELETE` 的时候，其实并没有真正意义上把数据删掉，而只是把行格式里的 `delete mark` 记录从 `0` 改成了 `1`，用这种方式表示"已删除"。

为什么不直接删？主要原因是还要考虑回滚这类需求，说到底是为 MVCC 服务的。所以这里不能真正把它删了，这一点要注意。

#### MVCC 能解决的具体问题

MVCC 能解决的具体问题有这么几个：

- 读写之间的阻塞问题——并发性更高了，同时降低了死锁的概率，我们用的是一种乐观的方式来解决读的问题；
- 快照读的问题——本质上和上一条其实是一件事。

这就是总体上的结论。而落到细节上，或者说得功利一点，为了应付面试，需要把两件事弄清楚：快照的生成时机，以及下面这个公式。讲的时候你举一个例子把这件事说清楚，就可以了。

#### MVCC 的组成公式

核心一点：MVCC 如果用个公式来表达，那就是两个隐藏列，加上 `undo log` 的版本链，再加上一个 `ReadView`。

$$ \text{MVCC} = \text{隐藏列} + \text{undo log 版本链} + \text{ReadView} $$

这三部分各自负责什么，也要说得出来：

- 多版本，指的就是 `undo log` 的版本链；
- 并发控制与管理，指的是 `ReadView`；
- 而 `ReadView` 在管理的过程中，又需要用到那两个隐藏列。

这个公式建议大家记一下。

```text
MVCC 的组成与职责

  隐藏列（trx_id / roll_pointer）
        │  被 ReadView 用于可见性判断
        ↓
  undo log 版本链  ──→  提供"多版本"
        │
        ↓
  ReadView  ──→  负责"并发控制与管理"
        │
        ↓
  快照读结果：只放出对当前快照可见的那个版本
```

读图说明：版本链负责把历史版本串起来，`ReadView` 负责在同一条链上挑出该给当前事务看的那个版本，而挑选过程要读隐藏列里记录的事务 id 和回滚指针。
