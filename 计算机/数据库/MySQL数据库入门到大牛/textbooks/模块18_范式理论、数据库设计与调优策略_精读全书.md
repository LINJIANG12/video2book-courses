## 151-范式概述与第一范式
> 对应分集：P151 | 原始标题：《151-范式概述与第一范式》

上一章我们花了不少篇幅折腾 SQL 优化——怎么让一条语句跑得更快。这一章换个方向，回到最前端去：**表本身该怎么设计**。

这个顺序其实有点倒过来了。真到了项目里，是先有表结构，才有基于它写的那些 SQL；表设计得不好，后面写出来的 SQL 是不是也会带着一堆低效问题？所以这一章要谈的是数据库的设计规范，落点就一个对象：**表**。表在设计的时候需要遵循哪些要求，这就是**范式**；设计过程中会涉及的**实体、属性**以及它们相互之间的关系，对应的是 **E-R 模型**；还有配套的一个建模工具 **PowerDesigner** 的用法。

先说难度：这一章整体不算特别高，不难。我们一个一个来。

### 数据库设计的出发点

#### 表设计要回答的四个问题

"我们为什么需要数据库设计？"这个问题问得其实比较幼稚——因为毫无疑问，我们要关注的就是表的设计。但幼稚归幼稚，真动手的时候摆在面前的问题一点都不少：

1. **用户到底需要存储哪些数据？** 哪些数据要持久化保存到表里去，这是第一个要考虑的问题。
2. **存进去了，怎么保证数据的正确性？** 这就落到约束的检查上。有些约束需要在业务逻辑层面做，有些需要在表层面做——约束我们以前都讲过了。
3. **怎么降低表的冗余度？** 冗余度是我们设计表的时候非常敏感、非常在乎的一个点。
4. **怎么让负责数据库维护的人更方便地使用？** 说白了，你的表设计成什么样，我们就得基于你这个表结构去写 SQL；表设计得不好，写出来的 SQL 也会存在低效的问题。

第 3 条值得多说一句，因为它不是"理论上应该"的事，而是量级问题。表数据量不大的时候，冗余度高一点也无所谓，浪费的空间是有限的。可一旦用户量涨起来、表的数据量迅速扩张，那些冗余的数据也会**成几何级数地增长**，这个就接受不了了。所以冗余度尽量低，是硬要求。

#### 没有黄金准则

把这四条摆完，一个更根本的判断要先立住：

> **结论**：数据库的应用场景各不相同，针对不同的情况设计出来的表千差万别，很难说存在一条"黄金准则"——看到它就醍醐灌顶，放之四海皆准，一下子成为表设计的大牛。

这不现实。学习也是一样的道理：有没有什么秘诀型的学习方法，一看就恍然大悟、突飞猛进、直接考上清华北大？不会有这种偷奸取巧的捷径。也正因为具体问题需要具体分析，你随着时间积累、经验积累，你的价值才可能更大。

反过来看更清楚：如果一样东西简单到所有人都能拿过来学，它一开始是个蓝海，价值很大；随后进来的人越来越多，价值很快也就降下来了。2011、2012、2013 一直到 2015 年那几年的移动互联网就是这样——Android 开发、iOS 开发，确实不太难，很多人都去学，薪资也很高，然后市场很快就饱和了，就出现了那样的场景。

这事在公司里应该也有共鸣。不管你是写具体功能模块、业务逻辑的，还是做数据库设计开发的，你会发现：不同的人写出来的功能可能都能实现，但代码真的是千差万别。多数情况下我们拿到别人的代码，通常会觉得"这写得啥呀，真烂"；很少能拿到大牛写的，让人拍案叫绝，说人家写得真漂亮。这种情况有吗？有，但多数时候大家都觉得对方写得不满意——因为每个人思考的角度不一样，代码质量也千差万别。

#### 设计时机与改表的代价

现实当中更常见的场景是：表设计完了，程序也跑起来了、上线了，运行一段时间之后发现表的设计存在问题。那怎么办？

> **易错点**：表结构一旦上线再改，就不是改几行 DDL 的事。你必须在**项目运行期间**把表结构换掉，而旧数据必须迁移出来——这个迁移过程还会影响到整个程序的业务逻辑，以及网站的正常访问，造成的影响面非常大。

对比一下就更明白：如果只是更新一个项目、纯代码层面的东西，那重新开发一套再上线就完了。但数据的调整、迁移、备份是非常关键的，因为一个公司当中最重要的东西就是**数据**。

举个例子：中国银行要迁移整个数据库，会找一个刚毕业的小孩去做吗？那他是疯了。数据的迁移必须交给有经验的人。

> **结论**：既然会出现这种情况，那我们在刚开始设计的时候就要尽量问清用户的需求，看他后期的发展是什么样——不同的阶段，表结构有时候也会有所不同。

#### 良好表设计的三个优点与总方向

糟糕的数据库设计会造成哪些问题，这里就不啰嗦了，一看都比较清楚。反过来，良好的数据库设计应该具备哪些优点？三个：

- **尽量节省存储空间**——还是对应上面说的冗余度问题；
- **能够保证数据的完整性**——我们要的数据你都得能存起来。不能说因为要删一条确实不用了的记录，连带把其他有用的数据也删掉了，而那些有用数据在其他表里还没有体现，这就很恶心了，不行；
- **方便数据库应用系统的开发**。

整体的大方向就是：**冗余度小一点，结构尽可能合理一些，方便我们后续写 SQL**。这个方向和上一章 SQL 优化是同一种思路——SQL 优化的大方向是什么？响应度尽可能高，也就是低延迟；另一个是吞吐量尽可能大。定好了方向，再往下才是具体规则的制定。

### 范式概述

#### 范式的定义与六种级别

> **定义**：在关系型数据库当中，关于数据表设计的基本原则或规则，称为**范式（Normal Form，NF）**。因为它是两个单词的缩写，所以简称 NF。

它是由一位英国人在上世纪 70 年代，在**关系数据库模型**的基础之上提出来的。

由于表的设计可以设置不同的层级，按层级划分就得到了第一范式、第二范式、第三范式等等这样一些规则。常见的共六种，按级别从低到高依次是：

| 级别 | 范式名称 | 英文与缩写 | 说明 |
| --- | --- | --- | --- |
| 1 | 第一范式 | First Normal Form，1NF | 最基础的要求 |
| 2 | 第二范式 | Second Normal Form，2NF | |
| 3 | 第三范式 | Third Normal Form，3NF | 实际开发中通常到这里就够 |
| 4 | 巴斯-科德范式 | Boyce-Codd Normal Form，BCNF | 别名巴斯范式，可看作改进后的第三范式 |
| 5 | 第四范式 | Fourth Normal Form，4NF | |
| 6 | 第五范式 | Fifth Normal Form，5NF | 又称**完美范式** |

关于级别，先明确两个性质：

> **定义**：级别依次递增——阶数越高，表设计中的冗余度就越低。所以到了第五范式，它被称为完美范式，你看这名字就感觉很不错。

> **提示**：如果满足了高阶范式，就一定满足相应的低阶范式。比如一个表满足第二范式，那它一定也满足第一范式。

这个道理可以用学历来类比：你已经是本科生了，面试官还会问你有没有高中毕业证、初中毕业证、小学毕业证吗？不会问了，因为你是本科的前提就是一定读过高中、读过初中。满足第三范式，前提就是第一范式、第二范式也已经默认满足了。

#### 巴斯-科德范式的定位

六种范式里有一个比较特别：**巴斯-科德范式**，它没有按 1、2、3、4、5 的顺序走到"第四范式"的位置上。原因在于——

> **结论**：巴斯-科德范式只是在第三范式的基础之上做了一个微调，所以没有把它称为第四范式。你可以把它看作**改进的、优化以后的第三范式**。

它的名字念起来很绕（巴斯-科德），一般就直接念"巴斯范式"，省掉"科德"两个字。

#### 实际开发中的范式选取与反范式

标准摆出来之后，真正要记住的是实践中的取舍：

- 实际开发中关于表的设计，多的也就遵循到巴斯范式（BCNF），**顶多到这个位置**；
- 大部分、或者说绝大部分情况下，**到三范式就可以**；
- 第四、第五范式，很多人——甚至做数据开发的人——可能都整不太清楚。这里也会做个介绍，但大家主要停留在"知道有这么回事"的层面就可以了，实际设计表的时候一般不会去遵循。

那问题就来了：既然越往下冗余度越低，都叫完美范式了，为什么不去追求它？

> **结论**：任何事物都是有利有弊的。越往下冗余度越低，但它相对应地也会带来一些弊端，所以我们在设计的时候要取得一个**平衡**——适可而止就行，中庸的思想。这就是大部分情况遵循三范式就够的原因。

甚至在某些场景下，我们还会**刻意地破坏范式的规则**，这叫**反范式**（反范式化），这个概念后面会专门讲。

> **提示**：这一节是本章的"总纲"，接下来几个范式要用的术语都在下一节统一交代清楚，不然后面讲不下去。

#### 规范化标准的来源与西方管理思路

这里插一段闲话，但它解释了"为什么会有范式这种东西"。

我们现在学的计算机知识，包括数学、物理这些自然科学，基本上都是学的西方那一套。包括现代的公司管理——管理学看着好像很玄妙，但西方人来讲，还是会把它定义成一条条规则，然后还有相应的考证、认证，一级一级往上提升。就说麦当劳，一说到麦当劳不就是做汉堡的吗？咱们中餐馆比西式汉堡复杂多了，菜式也多得多；但麦当劳管理起来有一套非常细节的规则和标准。西方人做事就是这样一个特征。整体来讲，从这一点上得承认确实要好一些。

再举孔子的例子。孔子厉害不厉害？确实厉害。我们学的那些孔子的话，说的都是很经典的。但是孔子从来没有告诉我们：怎么才能一步一步达到他那个境界。中间那条路径我们不知道，也没人给过——只告诉我们大家都是凡人，要么就是像孔子那样特别牛的境界，中间怎么走不知道。这是稍微欠缺的一点。

> **结论**：孔子是用来让我们崇拜的，我们很难去走完他那样一步一步的过程。而西方人做任何学科，都想着做一个**规范化的标准**。日本在这方面学西方学得比较多——你学相关专业就会发现，凡是涉及西方、涉及日本管理的，特征都是这样。

所以拉回到表设计上：不能"你就看着整吧"，这不行，一定要定义相关的标准。这就是范式的来由。

### 键与主属性

要讲清楚后面几个范式，先得把几个词搞懂，不然读不懂那些规则的表述。这里的词有：超键、候选键、主键、外键，以及主属性和非主属性。

我们统一用一张**球员表**来举例，它有这么几个字段：球员编号、姓名、身份证号、年龄、球队编号。

| 球员编号 | 姓名 | 身份证号 | 年龄 | 球队编号 |
| --- | --- | --- | --- | --- |
| 1001 | 张三 | 110101199001011234 | 24 | T01 |
| 1002 | 李四 | 110101199202022345 | 22 | T02 |

#### 超键

> **定义**：能**唯一标识元组**的属性集，叫做**超键（Super Key）**。

这里的"元组"（tuple）你可以理解成就是表中的一行数据。所以超键就是能唯一标识这一行的属性集。

先看主键，大家都比较熟悉了：这张表里哪个字段能做主键？球员编号能唯一定位，身份证号也可以——这两个都可以考虑作为主键。而**超键**的范围比这宽得多：只要能够唯一标识一行的属性集就算。也就是说，**只要包含主键，再加别的字段，都能构成超键**。

于是下面这些都成立：

- 球员编号 + 姓名 —— 可以；
- 身份证号 + 年龄 —— 可以；
- 身份证号 + 球队编号 —— 可以；
- 球员编号 + 球队编号 —— 也可以。

判据始终只有一条：它能不能唯一标识表中的一条一条数据。能，就是超键。

#### 候选键

> **定义**：如果超键**不包含多余的属性**，这个超键就称为**候选键（Candidate Key）**。

回头看刚才的"球员编号 + 姓名"：要唯一识别表中的一条记录，姓名其实是用不着的。把姓名砍掉，光看球员编号，是不是就能唯一识别这一条记录了？能。所以球员编号就是一个候选键。身份证号同理，也是候选键。

> **提示**：候选键也可以理解成**最小的超键**。像"球员编号 + 姓名 + 年龄"这三个字段合在一起确实是一个超键，但它不是候选键——因为姓名和年龄这两个在里面没用，砍掉。

所以这张球员表当中有**两个候选键**：球员编号，以及身份证号。

#### 主键

主键就是从候选键当中**随便选一个**，都可以作为主键。选球员编号做主键可以，选身份证号做主键也可以。

> **易错点**：主键在一个表中**只能有一个**，而候选键**可以有多个**。这一点容易记反。

#### 外键

外键和前面讲过的**外键约束**是一样的道理。针对球员表和球队表来看：球员表里有一个"球队编号"，而在球队表里，"球队编号"是可以作为主键出现的。我们拿球员表的这个字段去跟球队表做关联，那么在球员表里，"球队编号"就是**外键**。

#### 主属性与非主属性

> **定义**：包含在**任意候选键**中的属性，称为**主属性**（Prime Attribute）。

注意这里的措辞是"任意候选键"，不是"主键"。原因在于候选键也好、主键也好，都可能不是一个字段——联合主键大家肯定见过。键可能是由多个属性组成的，所以要用"候选键中的属性"来定义。

落到球员表上：球员编号是主属性，身份证号也是主属性（两者分别是两个候选键的组成属性）。而**抛开主属性，剩下的都是非主属性**——也就是姓名、年龄、球队编号。

结构理清之后，这张表里各种键的关系可以这么看：

```text
球员表（球员编号, 姓名, 身份证号, 年龄, 球队编号）

  超键（Super Key）—— 能唯一标识元组的属性集，范围最大
  +-----------------------------------------------------------+
  |  球员编号+姓名        含有冗余属性，只能算超键              |
  |  球员编号+姓名+年龄   含有冗余属性，只能算超键              |
  |  身份证号+年龄        含有冗余属性，只能算超键              |
  |                                                           |
  |  候选键（Candidate Key）—— 不含多余属性的超键（最小超键）    |
  |  +---------------------------+                            |
  |  |  球员编号                 |  主键 = 从候选键中任选一个   |
  |  |  身份证号                 |  （一个表只能有一个主键）     |
  |  +---------------------------+                            |
  +-----------------------------------------------------------+

  主属性   = 包含在任意候选键中的属性 → 球员编号、身份证号
  非主属性 = 其余属性               → 姓名、年龄、球队编号
  外键     = 球员表.球队编号 → 球队表.球队编号（球队表中的主键）
```

读图：从外到内是超键、候选键的包含关系——超键范围最大，候选键是其中不含多余属性的那些；主键再从候选键里任选一个。而主属性、非主属性的划分依据是"是否出现在任意候选键中"，跟主键选谁无关。

> **提示**：候选键还可以称为**码**，主键称为**主码**，这两个叫法了解就行。

这几个词一定要熟悉，因为接下来讲范式，用的就是这几个词。

### 第一范式

#### 原子性规则

首当其冲的是第一范式，也叫一范式，说的都是它。

> **定义**：第一范式（1NF）要求确保数据表中**每一个字段的值都必须具有原子性**。

"原子性"这个词后面讲事务的时候还会提到，就是 ACID 里面那个 A，Atomic。原子性意味着**不能再拆分**——物理世界当中的原子，我们理解成构成一个事物的最小单位，你就别再给它拆了。放到字段上，言外之意就是字段不能再拆分。

形式化一点说：对某个字段 $X$，不能把 $X$ 再拆成 $X_1$ 和 $X_2$。能拆，就不满足第一范式；不能拆，就满足。

> **结论**：这是设计表时**最最基本**的一个要求，所以实际设计当中，第一范式是一定都会遵守的。

#### 违反 1NF 的情形一：字段内存放多个手机号

看第一个例子。员工表里有员工 ID、员工姓名、员工地址（address）、员工手机号（mobile）：

| 员工 ID | 姓名 | address | mobile |
| --- | --- | --- | --- |
| 101 | 张三 | 北京市海淀区 | 13800000001 |
| 102 | 李四 | 上海市浦东新区 | 13900000002, 13900000003 |
| 103 | 王五 | 广州市天河区 | 13700000004 |
| 104 | 赵六 | 深圳市南山区 | 13600000005, 13600000006 |

有的员工就是有两个手机号。李四有两个，赵六也有两个，我们把它们都写在一起了。

> **易错点**：`mobile` 这个字段的值是"13900000002, 13900000003"，它还能再拆成两个手机号——所以这张表**不满足第一范式**。

要让它满足，就得这样处理：李四拆成两条记录，一条放他的第一个手机号，另一条放第二个手机号；赵六也是同样的道理。

| 员工 ID | 姓名 | address | mobile |
| --- | --- | --- | --- |
| 101 | 张三 | 北京市海淀区 | 13800000001 |
| 102 | 李四 | 上海市浦东新区 | 13900000002 |
| 102 | 李四 | 上海市浦东新区 | 13900000003 |
| 103 | 王五 | 广州市天河区 | 13700000004 |
| 104 | 赵六 | 深圳市南山区 | 13600000005 |
| 104 | 赵六 | 深圳市南山区 | 13600000006 |

拆完之后再去拆就拆不动了，这才满足原子性。

#### 违反 1NF 的情形二：字段内存放整块用户信息

第二个例子：设计了一张表叫 `user`，也就是用户表，里面有 `id`、`username`、`password`，还有一个 `user_info`，也就是用户信息。

这个"用户信息"里的内容还挺丰富：真实的姓名、电话、住址，全都合在一起放在"用户信息"里了。这种设计方式就不太好。为什么？因为我们实际写 SQL 的时候，可能要单独调用用户的真实姓名，也可能要单独调用他的电话，还可能要用他的地址——这些是分开的。你都合在一起就不合适。

所以要把字段拆开：`real_name` 一个字段、`phone` 一个字段、`address` 一个字段。

字段的演化关系是：

```text
user（不满足 1NF）
+--------+----------+----------+----------------------------+
|   id   | username | password | user_info                  |
+--------+----------+----------+----------------------------+
|   1    |  zhangsan|  ***     | 张三 / 13800000001 / 北京市 |
+--------+----------+----------+----------------------------+
                                     |  一次拆成三个字段
                                     v
user（满足 1NF）
+--------+----------+----------+-----------+-------------+----------+
|   id   | username | password | real_name |    phone    | address  |
+--------+----------+----------+-----------+-------------+----------+
|   1    |  zhangsan|  ***     |   张三    | 13800000001 |  北京市  |
+--------+----------+----------+-----------+-------------+----------+
```

读图：`user_info` 这一个字段被整体拆成了 `real_name`、`phone`、`address` 三个并列字段，每个字段只存一件不可再分的事实。

这两个例子应该很清楚地表达了第一范式的要求。

#### 字段可拆分性的主观判断

讲完规则和例子，还有一个必须说清楚的点：所谓"能拆还是不能拆"，实际上是**有主观性**的。

拿家庭住址来说。一张表的地址是这么设计的：

| 员工 ID | 姓名 | 家庭住址 |
| --- | --- | --- |
| 201 | 张三 | 北京市海淀区中关村大街 1 号 |
| 202 | 李四 | 上海市浦东新区世纪大道 100 号 |

那这个地址还能不能再拆？比如拆成省、拆成市，再拆出具体的街道地址。到底拆还是不拆？

> **结论**：这时候就有主观性了，得根据实际项目需求来判断——你是不是需要细分到这样的级别上，是不是需要查某个员工具体所在的市。有这种需求，就可以拆；没有这种需求，那就合在一起，你就认为它不可再拆分。

姓名也是同样的道理。我们中国人有姓有名，那有必要把姓拆出来、名再拆出来吗？老外更麻烦，有 first name、middle name、last name。比如 George W. Bush——乔治·W·布什，就是美国之前那位小布什总统，他的名字里 first name、middle name、last name 都有。

> **结论**：是拆成三个字段、拆成两个字段，还是全都放在一起，主要取决于实际的项目需求——查询是不是要用到这么细的粒度。有需求就拆开，没有需求就不要拆。

> **提示**：主观性只覆盖这类"语义上还可再分、但拆分有无必要取决于查询需求"的字段。上面 4.2、4.3 那两个例子不在此列——一个字段里塞了多个手机号、或者塞了姓名电话住址一整块，看完就知道是**肯定要拆**的。

第一范式到这里就讲完了，应该说比较简单。

## 152-第二范式与第三范式
> 对应分集：P152 | 原始标题：《152-第二范式与第三范式》

第一范式（First Normal Form，1NF）管的是列的原子性，这个说完了。接下来看第二范式（Second Normal Form，2NF）。

这里先把一条前置关系钉住：**一个表如果遵循第二范式，它的前提是已经遵循了第一范式**；同样，一个表如果符合第三范式（Third Normal Form，3NF），那它一定已经满足了第一范式和第二范式。范式是一档一档往上爬的，不存在跳过第几档直接满足第几档。

那在第一范式的基础上，第二范式额外加了什么约束？归纳起来就一句话：**表里的每一条数据记录都必须是可唯一标识的**，而且**所有非主键字段都必须完全依赖于主键，不能只依赖于主键的一部分**。这一讲的关键词因此只有两个——**完全依赖**和**部分依赖**。第三范式在第一、第二范式的基础上再往上加一条：**每个非主键字段都必须和主键直接关联，不能间接关联**。翻译过来就是，**非主键字段之间不能互相依赖**。

这就是这一讲的全部骨架。下面逐条讲透。

### 第二范式：非主属性必须完全依赖于主键

#### 从超键、候选键到主键，以及完全依赖与部分依赖

先解决"可唯一标识"这件事由谁来决定。前面提过**超键（super key）**的概念，超键能够唯一标识每一行的记录；超键里面最短的那个，把没有用的字段扣除掉，就叫**候选键（candidate key）**；候选键随便挑一个，就是**主键（primary key）**。

所以"表里的每一条记录都可唯一标识"这句话，言外之意就是：既然能唯一标识，就一定存在超键，一定存在候选键，也就一定有主键。第二范式的第一条要求就是——**表里得有主键**。

第二条才是它真正新增的约束，用一个抽象的模型来看最清楚。假设一张表的主键是一个**联合主键**，也就是两个字段合在一起才能唯一标识一行记录；除这两个字段之外还剩下三个字段，这三个都属于**非主键字段**。

满足第二范式是什么意思？就是这三个字段里的每一个都得如此：想知道它的值是多少，你必须同时告诉我主键里的这两个字段。只告诉我前面那个字段，确定不了；只告诉我后面那个字段，也确定不了；两个都告诉我，我才能把这个值唯一确定下来。三个字段都满足这一点，就叫满足第二范式。

不满足是什么样？比如其中有这么一个字段，你只需要告诉我主键里的某**一个**字段的值，我就知道它的值是多少，跟主键里的另外一个字段毫无关系。这种情况叫**部分依赖**，这样就不满足第二范式。

| 依赖形态 | 判断标准 | 是否符合第二范式 |
| --- | --- | --- |
| 完全依赖 | 必须同时给出联合主键的全部字段，才能确定该非主键字段的值 | 符合 |
| 部分依赖 | 只给联合主键中的某一个字段，就能确定该非主键字段的值 | 不符合 |

那怎么处理？把存在部分依赖的那个字段和它真正依赖的那个主键字段抽出来，让它们独立建一张新表；新表和原来的表构成**一对多**的关系。抽象地说可能还有点懵，看细节。

#### 满足第二范式的例子：成绩表

现在有一张成绩表，字段是**学号**、**课程号**、**成绩**。

先问一个问题：这张表的主键是谁？单独用学号不行，单独用课程号也不行——学号 `1001` 这个学生可能要考好几门课，每门课的成绩不一样；课程号 `001` 这门课也有好多同学去考，不同学号的成绩也不一样。所以**这两个字段合在一起构成主键**。

再看依赖关系。你告诉我学号且告诉我课程号，我才能决定成绩；反过来，你光问我"1001 考了多少分"——不行，你得告诉我哪门课；你光问"001 这门课多少分"——也不行，你得告诉我哪个学生。

> **结论**：成绩完全依赖于主键（学号且课程号），没有任何一个非主键字段能靠主键的一部分确定下来。这张成绩表是满足第二范式的。

#### 不满足第二范式的例子：球员比赛表

再看一张表，叫 `player_game`，也就是球员比赛表。捋一下它的主键应该是谁。

如果只拿**球员编号**当主键：球员编号一定，姓名、年龄就都定了；但比赛编号能定吗？一个球员会参加多场比赛，光说球员编号，比赛这一块定不下来，比赛的时间、场地也定不下来。所以单用球员编号当主键不行。

反过来，如果只告诉我**比赛编号**：这场比赛的时间和场地确定下来了，但一场比赛有好多球员参加，你能唯一定下来是哪一个球员吗？也不行。

要能唯一定义表中的一条记录，就必须把这**两个字段合在一起**构成主键。主键里有两个字段，这两个字段叫**主属性（prime attribute）**，剩下的字段就是**非主属性**了。

把主键放到左边，其他字段放到右边，为了把问题说清楚，这里再多加一个字段**得分**。结构长这样：

```text
+----------------+----------------+--------+--------+----------+--------+
|    球员编号     |    比赛编号     |  姓名  |  年龄  | 比赛时间  | 比赛场地 |  得分  |
+----------------+----------------+--------+--------+----------+--------+
|<--------- 主键（联合主键）-------->|<---------- 非主属性 ---------------->|
```

> **易错点**：这张表**不满足第二范式**。判定的关键不是"有没有主键"，而是主键是联合主键时，每个非主属性是不是都得靠**整个**主键才能定下来。

逐个字段看：

- **姓名、年龄**：只依赖于球员编号。你告诉我球员编号，我就知道他的姓名和年龄，跟比赛编号有关系吗？没有。
- **比赛时间、比赛场地**：只依赖于比赛编号。跟球员编号有关系吗？没有。
- **得分**：这个才是完全依赖。想看得分，你说"C 罗得分多少"，不行，你得告诉我是 C 罗参加哪一场比赛的编号；你光说"这场比赛得分多少"也不行，你得告诉我是哪个球员。所以得分同时依赖这两个字段。

姓名、年龄、比赛时间、比赛场地这**四个字段都属于部分依赖**，不是完全依赖——这就是它不满足第二范式的原因。

怎么办？把部分依赖的字段抽出来：

- 球员编号，连同姓名、年龄，单独造一张**球员表**；
- 比赛编号，连同比赛时间、比赛场地，单独造一张**比赛表**；
- 剩下得分，它完全依赖于这两个编号，那就让这三个字段（球员编号、比赛编号、得分）构成一张**球员比赛关系表**。

相当于原来一张表要拆成**三张表**来刻画，改造完就满足第二范式了：

```text
球员表 (球员编号 PK, 姓名, 年龄)
                          \
                           \  1
                            \
球员比赛关系表 (球员编号 PK/FK, 比赛编号 PK/FK, 得分)
                            /
                           /  1
                          /
比赛表 (比赛编号 PK, 比赛时间, 比赛场地)
```

球员比赛关系表的得分同时依赖球员编号和比赛编号；球员表与关系表在"球员编号"上是一对多，比赛表与关系表在"比赛编号"上也是一对多。

#### 部分依赖带来的四类异常

有的同学这时候会犯嘀咕：原来一张表刻画得还行，现在给整成三张表，表多了就觉得麻烦，反而觉得不好；要是三个变一个，潜意识里觉得挺好，现在一个变三个，怎么去理解这个改动？

那就看看不满足第二范式的场景下，用原来那张表会出现什么问题。

**第一是数据冗余**。假设球员编号为 C 罗的这个球员要参加 $M$ 场比赛，那么这个球员在这张表里就有 $M$ 条记录，$M$ 条记录里每一条都要记一遍 C 罗的姓名和年龄。本来只需要一份的信息，现在重复了 $M-1$ 份。反过来也一样：假设有 $N$ 个球员参加同一场比赛，这场比赛的时间、场地就写了 $N$ 条记录，重复了 $N-1$ 行。数据量小的时候还能忍一下，冗余就冗余了；数据量一上来，冗余度就很高，占用的磁盘空间会过大。这个问题是最不能接受的。

**第二是插入异常**。现在要添加一场新比赛，比赛编号填进去了，比赛时间和场地也就都知道了。接着要填**球员编号**——可这个球员还没定下来是谁呢，就不太合适。因为主键里一般不能有空值，而这里是联合主键，任何一个主键字段都不能有空值。于是想把比赛信息填下来，就**必须**把球员信息也填下来。有时候你恰恰确定不下来，这就很恶心。

**第三是删除异常**。要删除某个球员编号的时候，你会把比赛编号也一起删了。假设这场比赛目前只定下来这一个球员——确定 C 罗要参加某一场欧冠比赛，其他球员还没定——现在把 C 罗删掉，这场比赛的信息是不是也跟着没了？这就是删除的信息过多了，不合适。

**第四是更新异常**。某场比赛有 $N$ 个球员参加，比赛时间就在这 $N$ 条记录里各记了一遍。现在要改这场比赛的时间，你可不能只改一处就完了，这 $N$ 个球员的记录里比赛时间**全都得改**；比赛场地要改也一样。万一漏改一条，就会出现同一个球员、同一场比赛的时间或场地跟别的记录对不上，那就是错误数据。更新也很恶心。

#### 第一范式的原子性与第二范式的独立对象

到这里就能看清两个范式各自在管什么：

- 第一范式告诉我们，**字段的属性需要有原子性**；
- 第二范式告诉我们，**一张表就是一个独立的对象，一张表只表达一个意思**。

回到球员比赛表——里面既有球员信息又有比赛信息，那泛泛地说就是"球员归球员，比赛归比赛"，把两者拆开。这就是拆表的依据，也是判断该不该拆的标准。

### 第三范式：非主属性之间必须相互独立

#### 直接关联与间接关联的判定

一旦提到某个表符合第三范式，前提必然是它已经满足了第一范式和第二范式。在这个基础上，第三范式还要求：**数据表中的每一个非主键字段，都得和主键字段直接关联**。这里有两个主体——非主键字段和主键字段——而重点强调的是**直接相关，不能间接相关**。

这句话看不太明白的话，翻译一下就是：**要求数据表当中所有的非主键字段不能依赖于其他非主键字段**。既然要求它跟主键字段直接相关，言外之意就是它不能跟其他的非主键字段存在直接相关的关系。

再换一种说法。**非主属性**就是非候选键当中的那些属性——这里可以暂时先把它理解成非主键字段，因为在第三范式里，凡是上面提"主键"的位置其实都可以改成"候选键"，非主属性和非主键字段在这个语境下是一致的。

于是判定条件可以写成一个依赖链条：**非主属性 A 依赖于非主属性 B，而非主属性 B 依赖于主键 C**。只要存在这样的依赖关系，这个表就不满足第三范式。因为 A 和 B 都是非主键字段，它们必须直接关联于主键字段，不能它们俩之间还存在依赖。

> **结论**：第三范式强调的点可以这样理解——**非主键属性之间必须是相互独立的，不能有依赖关系**。

#### 部门与员工：部门名称该放在哪张表

第一组例子是部门信息表和员工信息表。

- 部门信息表：部门编号、部门名称、部门简介；
- 员工信息表：员工编号、员工姓名、部门编号。

这个设计是没问题的，目前是遵守第三范式的。怎么就不遵循了？假如给员工信息表**再加一个部门名称**，看它遵不遵循第二范式：员工编号显然是主键，员工姓名完全依赖于它，部门编号也完全确定了；同时一个员工编号唯一地决定了他所在部门的名称，所以部门名称也是一个完全依赖关系——**这符合第二范式**。

但第三范式不满足了。因为部门名称如果放在这张表里，它实际上是**依赖于部门编号**的，而部门编号依赖于员工编号，链条成了"部门名称 ← 部门编号 ← 员工编号"。它们之间就不是独立关系了，这就不行。

> **结论**：部门名称没有必要往员工表里放，它属于部门信息表——那个表里本来就有部门编号、部门名称、部门简介。

#### 商品与类别：类别名称该放在哪张表

第二组例子是商品表，字段有**商品类别 ID**、**商品类别名称**、**商品名称**、**商品价格**。

满足第二范式吗？满足。商品 ID 是主键，剩下的字段都完全依赖于主键，没问题。

但不满足第三范式：其中的**商品类别名称**依赖于**商品类别 ID**，而商品类别 ID 依赖于主键。这种情况不允许存在。怎么办？把这两个字段单独拿出来，先构建一张**商品类别表**，里面的 ID 就是商品类别的主键，再加上商品类别名称，构成一张表；然后在商品表里**只需要罗列商品类别 ID**，不用再罗列商品类别名称。这就满足第三范式了。

#### 球员与球队：教练依赖球队名称

第三组例子是球员表，字段有**球员编号**、**球员姓名**、**球队名称**、**球队教练**。

满足第二范式吗？显然满足，球员姓名、球队名称、球队教练都完全依赖于球员编号。

但球队教练其实**依赖于球队名称**，而球队名称依赖于球员编号，于是它就不满足第三范式。改造办法：把球队名称和主教练单独拿出来构成一张**球队表**；球员表里保留球员编号、球员姓名和球队名称就可以了。

#### 订单表：订单信息与顾客信息

现在把第二范式里那个订单的例子做一次修正，把它也改成符合第三范式的——也就是说，改造之前的订单表是**不满足第三范式**的。

先明确一个业务前提：一个订单里可能有多个商品。所以订单号要和产品编号合在一起构成联合主键（一个订单买三件商品，就有三条明细记录）。这张表里除了主键，还有 `order_date`（订单时间）、`customer_id`（提交订单的顾客）、`quantity`（某商品在订单里的购买量）。

先看第二范式。`order_date` 是直接由订单编号决定的；`customer_id` 同样看订单编号就能确定；`quantity` 依赖于订单编号加产品编号这一整个主键。每个非主键字段都与主键完全依赖，所以它满足第二范式。

再看第三范式，问题出在 `company_name` 上：它是顾客所属的公司。而公司名实际上**依赖于 `customer_id`**，`customer_id` 又依赖于主键——非主键字段之间出现了依赖关系，它们不独立，所以不满足第三范式。

怎么改造？把 `customer_id` 和 `company_name` 拿出来，专门建一张 `customers` 表；在 `orders` 表里只放一个 `customer_id` 就足够了。

回到第二范式里那个订单改造的例子上（举例三），改造后的形态是这样的：

- 把部分依赖订单编号的那三个字段（`order_date`、`customer_id`、`company_name`）连同订单编号抽出来，构成**订单表**；
- 原表剩下的订单编号、产品编号，加上 `quantity`，构成**订单明细表**（`order_details`）——它还是原来那张表；
- 再做第三范式改造：把 `customer_id` 和 `company_name` 拆成 `customers` 表，订单表里只留 `customer_id`。

第二范式的原文表述是：**要求实体的属性完全依赖于主关键字，如果存在不完全依赖，就把这个属性和主键抽取出来构成一个新的实体**。举例二、举例三都是这么处理的，而且**新实体跟原来这个实体之间是一对多的关系**。

以订单为例：一个订单是一条记录，一个订单里可能有多个具体商品，买了三件就是三条明细——一对多。球员也一样：球员表里一个球员，在球员比赛关系表里可能对应多场比赛——同样是一对多。

#### 第三范式的合并表述

既然第三范式一定满足第二范式，那就可以把二、三合起来通俗地记：

> **结论**：每个非主键属性**都依赖于主键**，并且**都依赖于整个主键**——这两句合起来表达的就是第二范式，你不能部分依赖；并且**除了主键之外别无他物**——非主键属性之间彼此独立，不能有依赖关系。这就是第三范式的内容。

### 范式的优点、代价与工程取舍

#### 三个范式各自管什么

- **第一范式**：主要保证每一列具有原子性，不可再分。
- **第二范式**：每一个非主键列跟主键之间都得是完全依赖的关系。
- **第三范式**：非主键属性之间是相互独立的关系，它们跟主键之间是直接相关，彼此之间不能再有依赖关系。

#### 消除冗余与"最好的平衡"

范式的主要优点，就是**消除了数据当中的一些冗余**。刚才那几个例子里冗余的消除是非常直观的——球员的姓名年龄不再按场次重复 $M$ 遍，比赛的时间场地不再按球员重复 $N$ 遍。

而第三范式通常被认为在**性能、扩展性和数据完整性**方面达到了一个**最好的平衡**。这里说到"平衡"就要留个心：一般提到平衡，往往是"对这些方面有利，对那些方面不利"，好的坏的都有，我们只是达到了一个平衡状态。

#### 拆表的代价：查询效率与索引失效

有好处就一定有代价，范式有哪些缺点？

你会发现**越往下拆，表就越多、越细**：原来只有一个订单表，现在拆成了三个表。越拆冗余越低——但什么会越来越麻烦？**查询**。

原来只有一个 `orders` 表，查相关信息直接从这一张表里查就行，过滤条件上还能用索引。现在有三个表了，三个表就意味着**要 JOIN**。而 JOIN 的时候：

- 多表查询本身的效率就比单表低；
- JOIN 写得不是特别合适的话，**索引还会失效**。

> **结论**：整体来讲，范式会降低查询的效率——要关联多张表，首先代价本身就很高，其次还可能导致索引失效。

#### 设计标准、反范式化与"没有完美的设计"

范式只是提出来的一个**设计标准**。实际设计表的时候，没有说非得要遵循这些标准，你可以根据实际情况看遵循到哪一档上。但一般情况下，我们在开发中通常都会去遵循**第三范式**——当然前提是第一、第二范式都已经满足了。既然说到第三范式，一、二肯定是在已经满足的情况之下。

所以我们不会再去追求巴斯范式、第四范式、第五范式、域键范式（讲到这里我写的是域键范式）那么高的档位。因为越往下追求，相应的弊端也会更突出。

实际开发当中，有时候为了提升执行效率，还要做一些**反范式化**的设计，也就是**增加少量冗余来提高读的性能**。增加冗余相当于浪费了空间——这是**用空间换时间**。具体怎么做，要具体问题具体分析。

> **结论**：没有完美的设计，只有合适的设计。

## 153-反范式化的应用
> 对应分集：P153 | 原始标题：《153-反范式化的应用》

第一范式、第二范式、第三范式讲完了，紧接着就该讲反范式化。为什么？因为范式这一路学下来，它有一个越来越明显的副作用：表设计得越多、越细致，冗余度确实越来越低，可一到查询的时候，效率反而低了——数据被拆进好几张表，想看一条完整的信息就得一路关联过去。所以有些情况下，我们不得不动用反范式化。

---

### 从三范式的查询代价到业务优先原则

有些时候，我们不能简单地按照范式的规范去设计表。很多数据看起来是冗余的，但对业务来讲却非常重要。这个时候我们优先考虑的是业务，遵循的原则叫**业务优先原则**；在满足这个原则的前提之下，再去考虑尽量地减少冗余。

什么叫业务优先？举个例子。数据库里的数据量比较大，系统的 UV（独立访客数）、PV（页面访问量）访问频次也非常高。如果完全按照三范式去设计，就会产生大量的关联查询，而这些关联查询会拖累数据库整体的性能。此时你就不能拘泥于"非要按范式设计"这一条——性能被拖下来之后，用户的体验就很差了。

> **结论**：性能撑不住的时候，可以适当地增加一些冗余字段。这些冗余字段，就是反范式化设计的具体体现。

反范式化也不是什么边角技巧：要想提高查询效率、对数据库做优化，反范式化本身就是其中一个思路。

### 规范化与性能的矛盾

规范化和性能之间，是一种相互较量的关系：想达到一定的规范化程度，性能就有可能受到影响。为了满足某种商业目的，数据库的性能比"一个高度规范化的数据库"更为重要；所以在做数据规范化的同时，要综合地考虑数据库的性能。

这个矛盾不只局限在数据库这一层。你们想一想，实际生活当中，规范化和性能是不是也是一对矛盾？

公司里就有现成的例子。公司越大，规范的东西就越多——公司大了，人与人之间不能太随意，于是就会出各种各样的规章制度和流程；尤其在大公司里，规章制度和流程复杂得吓人。可一旦规范化以后，人跟人协作去完成一件事情，效率（也就是这里的"性能"）反而变低了：

- 原来的做法：你喊一嗓子——"老板，这个事要做，行不行？"行，抬腿就去了；
- 现在的做法：你得先写邮件，邮件要层层审批，等审批下来，半个月都出去了。

老话讲得好：**水至清则无鱼**。这句话放在表设计上同样有道理。

> **提示**：规范化回答的是"数据怎么摆才不重复、不容易出错"，性能回答的是"取数据要花多久"。两者不是谁对谁错，而是同一张表上两个互相拉扯的目标。

### 反范式化的两种实现手段

那具体该怎么做？手段其实就两类。

第一，**在给定的表中添加额外的字段**，大量减少"从中搜索信息"所需要的时间。说白了，就是增加冗余字段。

第二，**在给定的表中插入计算列**，方便查询。

计算列这条举个例子：表里有两个字段，一个表示数量，一个表示花在这上面的时间，总时间要靠这两个相乘得到。你每次都得先算总时间；如果每次都是现算，而这个量还挺大，花的时间就会多一些。那不妨单独定义一个字段，把这两个的乘积直接记在里面，以后每次查的时候直接查这个字段就行了，不用现去计算——这也能节省时间。

> **结论**：后面加的这个乘积字段，按正常来讲就是一个冗余字段，不满足范式化的要求。但在这个时候，加它也是必要的。

### 冗余字段的三个典型案例

先看大家最熟的两个表：员工表 `employees` 和部门表 `departments`。

需求是查员工的信息：员工的 ID，以及这个员工所在部门的名称。部门名称并不在员工表里，所以必然要做多表联合查询，也就是关联查询，关联条件是 `department_id`——这样一次就用到了两张表。

如果这个操作经常做，而且员工表里的员工数量还挺多，怎么办？可以考虑在 `employees` 表里增加一个冗余字段 `department_name`。之后再经常做这个查询，就用不上关联查询了，直接查员工表就行。

> **易错点**：加了 `department_name` 之后，这个字段就是冗余的，不满足第三范式——`department_id` 和部门名称都落在员工表里，两者不是相互独立的（部门名称只依赖 `department_id`）。但为了提升效率，我们就是这么反范式化了。

第二个是商品的例子。当初讲商品信息的时候我们就说过它不满足三范式，因为那两列不是相互独立的，所以把它拆成了两张表。可要是经常查询某个商品的类别名称，还是得做关联查询，不方便。于是我们在 `goods` 表里增加了一个冗余字段，用来存类别名称。

第三个例子更贴近真实业务：两张表，一张是商品流水表，一张是商品信息表。流水表的信息量很大——400 万条记录；商品信息表里只存具体的商品，2000 条记录。我们经常要访问流水的记录信息，两张表靠"商品编号"这个字段关联：在流水表里它是外键，在商品信息表里它是主键。

问题在于，查商品流水的时候，我们经常要看一下这个商品的名称到底叫什么。光看商品编号——很抽象的一串号——你并不知道这条流水涉及的是什么商品。所以经常要额外把名称这个字段带上。按范式的要求，这个字段应该独立地只存在于商品信息表里；可你经常关联查询，性能不就变低了吗？于是我们考虑把 `goods_name` 加到流水表里。这样再做这个查询，就不用去关联另外一张表了，性能会好一些。

三个例子其实是同一个模式：

| 业务场景 | 关联键 | 新增的冗余字段 | 冗余字段落到哪张表 |
| --- | --- | --- | --- |
| 员工与部门 | `department_id` | 部门名称 | `employees` |
| 商品与商品类别 | 类别编号 | 类别名称 | `goods` |
| 商品流水与商品信息 | 商品编号 | `goods_name` | 商品流水表 |

### 反范式化的完整实验

光说有好处不算数。能不能真的举个例子，证明我们确实增加了冗余、而查询时间确实缩短了？下面用一个完整的实验来做。

#### 范式化基线的表结构与数据准备

实验只用两张表：课程评论表 `class_comment`，学生表 `student`。脚本我提前准备好了，编号顺延到 07（06 已经被占用），内容归在"数据表的设计规范"这一节底下，本次做的是"反范式化的举例"。

建库、建表这一步很直接：

- 创建数据库 `atguigudb3`，然后切换到它；
- 学生表：学生 ID、学生姓名，以及创建时间；
- 课程评论表：评论 ID、课程 ID（针对哪个课程评论）、评论的具体内容、评论时间、学生 ID（谁评的）。`student_id` 和学生表建立关联。

> **提示**：这里我没有写外键约束，知道这层关联关系就可以。

```text
   student（学生表）                      class_comment（课程评论表）
   +----------------------+               +---------------------------+
   | student_id  （主键） |<------+       | comment_id       （主键） |
   | student_name         |       |       | class_id                  |
   | create_time          |       |       | content                   |
   +----------------------+       |       | comment_time              |
                                  +-------| student_id    （关联列）  |
                                          +---------------------------+
```

读图说明：两张表靠 `student_id` 关联，评论表里存的是学生 ID，学生的名字只存在于学生表——这正是范式化设计的结果，也是后面必须做关联查询的原因。

接下来灌数据，两张表各 100 万条：

1. 写一个存储过程，向学生表添加数据。调用它之后，学生 ID 从 10001 开始——存储过程里有一个 `start` 变量，`i` 的初值是 0，上来先加了一个 1，所以第一条就是 10001——一共添加 100 万条数据。
2. 再写一个存储过程，向课程评论表添加数据，同样灌 100 万条。

用 `SELECT COUNT(*)` 验证一下，两张表都是 100 万条，没有问题。

#### 关联查询基线与它的耗时

需求是这样的：查询 `class_id = 10001` 这门课的评论信息——评论内容是什么、什么时间评的、以及是哪个学生评的（学生名字）。评论表里不包含学生名字，所以这必然是多表查询，关联条件是 `student_id`；结果还要按评论时间倒序排（`DESC`），一般看评论都是先看最近的；最后只取这门课的前 1000 条记录。

```sql
SELECT c.comment_id,
       c.content,
       c.comment_time,
       s.student_name
FROM class_comment c
JOIN student s
  ON c.student_id = s.student_id
WHERE c.class_id = 10001
ORDER BY c.comment_time DESC
LIMIT 1000;
```

执行一下，前 1000 条记录查出来了，耗时 **0.016 秒**。

你可能会说：这个时间还可以，能接受啊。但数据量越多的时候，就越麻烦；而且这个时间我们自己觉得挺快，对于整个程序在数据表里做查询来讲，其实已经算是比较慢的了。

> **结论**：当前这个结构是满足范式要求的——学生名字只存在学生表里，评论表里只有一个 `student_id`，没有任何冗余，代价就是每次都要关联两张表。

#### 表复制与冗余字段的添加

下面把它改造成反范式化的版本。严格说，正常的改造直接在原表上改就行；我为了把整个改造过程保留下来，重新造了一张表。

做法是把原来 `class_comment` 表里的字段和数据全部拿过来，相当于一次表的复制。复制过来的表跟原表有一个区别：里面的一些约束没有了，所以我给 `class_comment1` 补了一个主键，保证它和原来的 `class_comment` 表结构尽可能一致。

表有了，接下来是反范式化的核心一步：让这个需求只从课程评论表里操作，不再去查学生表。言外之意——把学生的姓名直接加到课程评论表里：

```sql
ALTER TABLE class_comment1 ADD student_name VARCHAR(20);
```

字段加好了，但这一列的数据全是空的，还得 `UPDATE` 一遍，让它的值等于学生表里对应 `student_id` 的那个名字：从当前表里取出一条数据、拿到它的 `student_id`，再去学生表里找到相同 ID 的那一行，把对应的名字设置过来。

```sql
UPDATE class_comment1 c
JOIN student s
  ON c.student_id = s.student_id
SET c.student_name = s.student_name;
```

到这里，`class_comment1` 里各个字段就都齐了——它比原来的评论表多了一个来自学生表的冗余列：

```text
   class_comment1（反范式化之后的评论表）
   +---------------------------+
   | comment_id       （主键） |
   | class_id                  |
   | content                   |
   | comment_time              |
   | student_id    （关联列）  |
   | student_name  <-- 新增的冗余字段
   +---------------------------+
```

读图说明：`student_name` 是从 `student` 表复制过来的，它不满足第三范式，但从此以后这个需求的查询不必再离开这张表。

#### 查询耗时的实测对比

还是同样的需求：评论内容、评论时间、学生名字，还是 `class_id = 10001` 这门课，还是前 1000 条记录——只不过这次只从新的评论表里查。

```sql
SELECT comment_id,
       content,
       comment_time,
       student_name
FROM class_comment1
WHERE class_id = 10001
ORDER BY comment_time DESC
LIMIT 1000;
```

选中执行，反应时间没省下多少；再走一遍，还是没少——没有想象中那么多。

那就把量加上去：把 `LIMIT` 改成 10000 条记录再测。

| 查询版本 | 访问路径 | 10000 条记录的耗时 |
| --- | --- | --- |
| 范式化 | `class_comment` 关联 `student` | 0.100 s |
| 反范式化 | 只查 `class_comment1` | 0.036 s |

整体来看，时间上肯定还是上面那个多、下面这个少，这一点应该没有问题。

> **结论**：数据量抬上来以后，反范式化的优势才真正显出来。你们自己实际去测，具体数字可能跟我这里有些区别，但整体上反范式化这一版要更好一些。

### 反范式化的代价

好处很直接：查询性能显著提升。代价也很直接，而且不止一条。

**第一，空间开销。** 我们本质上是拿空间换时间，存储空间肯定是要变大的。

**第二，冗余字段的同步修改——这一条要特别关注。** 一个表里的字段做了修改以后，另一个表里那个冗余字段也要做相应的同步修改。比如 `student_name` 是从 `student` 表复制过来的，学生表里学生的名字改了，评论表里的这个名字也得跟着改，这是一个很容易理解的道理。部门也一样：员工表记录员工，部门表记录部门，你现在把部门名称放到了员工表里；部门表里的部门名称一改，员工表里那个名称也得改，要不就不一致了。

**第三，存储过程带来的额外资源消耗。** 如果你要用存储过程来支持数据的更新和删除这类额外操作，更新比较频繁的话，还是挺消耗系统资源的。原来满足范式的时候没有冗余，也就没有"同步"这回事；现在有冗余了，频繁去改就得频繁执行存储过程，挺花时间。

**第四，数据量小的时候没有优势。** 在数据量比较小的情况下，反范式化其实体现不出太大的性能优势。就像刚才的实验，拿 1000 条、10000 条去体会，你会发现总耗时的绝对值差别没有多少时间；反倒是让我们这个数据结构设计得更复杂了，因为你要面对上面这些问题。

> **结论**：任何事物都是有利有弊的。真正要做的，是找到它实际的适用场景。

### 使用建议与两个适用场景

关键不在于反范式化好不好，而在于它什么时候好。

拿手机来说。现在大家都用智能手机，相较之下，十多年前的诺基亚、飞利浦，尤其是飞利浦，一部普通手机待机能待一个月。你说这些老手机跟我们现在的手机，是不是也叫有利有弊？那什么场景下我们还会去用那些手机？

爬山、远足、走沙漠——充电不方便的时候，你还真得有一部特别传统的手机。我记得以前看过一个新闻：一个小女孩去野外远足，一不小心跌到林子里一个坑里，隔了好几天才醒过来。醒过来之后就要去求救，她用的那部飞利浦手机把电话拨通了，最后被救了出来。你要是拿一部 iPhone，或者现在的小米、华为这种智能手机，一两天、一天就没电了，想打电话那就扯了。

所以要找到它在哪些情况下是有利的，那时候就用它。反范式化也是一样的道理。

#### 两条判断原则

要把反范式化用好，先记住两条使用建议。

1. **增加的冗余字段尽量不经常修改。** 只要它不需要经常改，前面那个"同步修改"的问题就被规避掉了；你虽然还是需要建一个存储过程，但消耗的资源就少了。
2. **这个字段在查询时一定不可或缺。** 要是不是不可或缺，你就没有必要加这个冗余字段，这不是给自己找麻烦嘛。

> **结论**：必须用、而且不经常改——这才是反范式化更好的应用场景。

#### 历史快照数据

第一个大场景是**历史快照数据**。这一类数据里，冗余信息是有价值的。

比如我们平时寄快递，订单里通常有收货人的信息：姓名、电话、地址。那么在订单表里，就可以考虑把收货人的这些信息作为冗余字段加进去——这就属于快照信息。

好处在哪里？用户随时可能修改自己的信息。过后他说："我那个快件怎么还没收到？"然后去查订单。如果按原来的做法，订单里记录的是地址 1，而用户在这之后（快件还没到的时候）把地址 1 改成了 2，那么重新查看订单时查到的就是地址 2；可他嘴上说的是"你看，我这快递就是没到我这儿"。其实他下单的时候，记录的明明是地址 1。

用了冗余字段、也就是做了反范式化之后，这个字段属于历史快照，我们不去修改它。这时候你就可以拿出证据来："看，你当初下单的时候记录的就是地址 1，不是你后来修改的地址 2。"

> **提示**：历史快照数据通常不需要经常修改，而我们又经常要查看它——两条判断原则它全都满足。

#### 数据仓库

第二个场景是**数据仓库**（Data Warehouse）。数据仓库跟我们平时说的数据库，在使用上还是有些区别的。

| 对比维度 | 数据库 | 数据仓库 |
| --- | --- | --- |
| 主要目的 | 捕获数据 | 分析数据 |
| 存储内容 | 实时性要求强的业务数据 | 历史数据、日志类型数据 |
| 冗余设计 | 尽量避免冗余 | 可考虑一定程度的冗余 |
| 原因 | 增删改频繁，实时性要求比较强 | 修改比较少，做分析时更方便 |

在大数据领域里，我们更多提到的就是这个"数仓"的概念。数据库的设计我们尽量要避免冗余，而数据仓库这边通常可以考虑有一定程度的冗余——主要原因就是修改也比较少，但要做分析的时候就更方便。

> **结论**：在数据仓库的设计当中，因为存的本来就已经是历史数据了，我们可以考虑一定程度的反范式化。

### 反范式化的使用前提

如果出于面试的考虑，反范式化确实可以去谈一谈、说一说。

但在开发当中，你得**先遵循三范式**：先要知道遵循三范式是什么样的场景，在遵循三范式的情况之下，再去考虑反范式。注意，是这样的一个逻辑。

而不是有同学一上来就说："你说了这么多，说还可以不遵循范式，那干脆我也不学了，我就直接看心情，我想怎么设计就怎么设计。一旦我设计的不遵循三范式被别人说了，我就说我这是反范式化的设计，是因为我们要提升效率。"这个就有点扯了。

这叫什么？叫**否定之否定**。你得先认可这个知识，然后在这个基础之上，再看我们为什么要去违反范式化的要求。你不能一上来就随意——那跟最终反范式化的境界，绝对是不同的。

## 154-巴斯范式、第四范式、第五范式和域键范式
> 对应分集：P154 | 原始标题：《154-巴斯范式、第四范式、第五范式和域键范式》

我们前面刚讲完反范式化——一范式、二范式、三范式的规矩，我们偏不遵守。当然反范式化通常不遵守的是第三范式和第二范式，第一范式还是一般都要守住的。往下接着看，范式这条线其实还没有走到头：三范式之上还有巴斯范式，再往上还有第四范式、第五范式，最后还有一个域键范式。这一讲我们把它们一次讲完，但先把话放在前头——**实际工作中你守到三范式，或者稍微优化一点的巴斯范式，就已经足够了**；后面这几个高级范式，了解一下就行。

越往下走，你会发现表的设计就越细，冗余度越低，但查询效率也越差。范式不是越高越好，我们要的是一个平衡点，而这个平衡点就在三范式到巴斯范式之间。

### 巴斯范式

#### 巴斯范式的定义与命名

巴斯范式是在第三范式的基础上做的一个改进，所以它通常也被叫做修正的第三范式，或者扩充的第三范式——注意，人们并没有因此把它改叫第四范式。

> **定义**：若一个关系已经达到第三范式，并且它**只有一个候选键**，或者它的**每一个候选键都是单属性的**（不是联合主键这种联合形式），那么该关系就自然地达到了巴斯范式。

从这个定义能看出，巴斯范式并没有推翻三范式，它只是把三范式的口子收得更紧了一点，让冗余度更小。

名字上要说一句：巴斯范式是**巴斯科德范式**的简称，巴斯、科德对应的是两个人；习惯上我们都叫它巴斯范式，缩写就是 BCNF（Boyce-Codd Normal Form）。

> **结论**：想要遵循范式的话，通常遵循到三范式，或者稍微优化一点的巴斯范式就可以了。四范式、五范式、域键范式，一般我们都不用了。

#### 案例表与候选键的判定

下面用一个网上比较经典的案例来展开。案例里的记录是这样的：

- 北京仓始终是张三在管理；
- 上海仓始终是李四在管理。

也就是说，**仓库名和管理员是互相决定的关系**：你说张三，我就自然知道是北京仓；你说李四，我就自然知道是上海仓。

仓库下面当然要放很多物品，所以还有物品名和物品数量。那么数量由谁决定？你得先告诉我“哪个仓库里的哪个物品”，我才知道数量是多少。

| 仓库名 | 管理员 | 物品名 | 数量 |
| :--- | :--- | :--- | :--- |
| 北京仓 | 张三 | 物品 A | 100 |
| 北京仓 | 张三 | 物品 B | 200 |
| 上海仓 | 李四 | 物品 A | 150 |
| 上海仓 | 李四 | 物品 C | 80 |

顺着这个“谁决定谁”的关系，可以找出两组候选键：

1. **仓库名 + 物品名**——知道了仓库和物品，数量就定了；
2. **管理员 + 物品名**——知道了管理员和物品，数量也定了（因为管理员反过来就确定了仓库）。

我们从中选一组当主键，比如就选 **仓库名 + 物品名**。于是：

- **主属性**：候选键里涉及到的属性都是主属性，所以仓库名、管理员、物品名这三个都是主属性；
- **非主属性**：只有数量一个。

> **提示**：主属性的判定看的不是“它在不在你选的那个主键里”，而是“它有没有出现在任何一个候选键里”。管理员虽然不在我们选的主键里，但它在另一组候选键里，所以它同样是主属性。

#### 三个范式的逐条校验

先判断这张表是不是满足三范式。

**第一范式**要求原子性，每个字段不可再分——这没问题。

**第二范式**要求每一个非主属性都完全依赖于候选键（或主键），不能只依赖一部分。这里非主属性只有数量一个，而数量完全决定于“仓库名 + 物品名”，也等于完全决定于“管理员 + 物品名”。所以第二范式满足。

**第三范式**要求非主属性之间不能存在依赖关系，彼此必须独立。这里非主属性就只有数量一个，一个属性当然是独立的。所以第三范式也满足。

> **结论**：这张表一二三范式全部通过，是符合三范式的。

#### 符合三范式后的插入、修改与删除异常

符合三范式，就说明这张表没有问题了吗？其实还是有问题。我们让仓库名和物品名勾在一起构成主键，然后来看几个场景。

**插入异常**：现在增加了一个新仓库，但仓库里还没有放任何物品。这时候往表里加数据靠谱吗？不靠谱——因为联合主键是不允许填空值的。你新增一个仓库，物品名这一列就必须填上一个值，而眼下又没有具体物品，那就填不进去，硬填就报异常。

**修改异常**：如果仓库更换了管理员，就要修改表中的多条记录。北京仓原来都写的是张三，改成别人时，这一个仓库下可能存着上百条商品记录，每一条都得跟着改。

**删除异常**：如果仓库里的商品全部卖空了，那这些行就没有存在的意义了。但主键不允许有 `NULL` 值，你不能把物品名留空，于是只能把对应的仓库记录也一并删掉——仓库本身的信息就这样被连坐删除了。

> **易错点**：这三类异常的根源不在“数量”这个非主属性上，而在**主属性**上。前面查三范式时我们只盯着非主属性看，所以完全查不出来。

#### 异常根源与主属性对候选键的部分依赖

分析一下造成异常的原因。

主属性**仓库名**，针对候选键“管理员 + 物品名”来说，是一个**部分依赖**的关系。为什么这么说？仓库名和管理员是互相决定的（一一匹配），而仓库名又是我们选定主键中的一个属性；这个主键中的属性，依赖于另一个候选键当中的**部分**属性（只依赖管理员这一半，不依赖物品名），这就构成了部分依赖。

```text
候选键①  仓库名 + 物品名 ──→ 数量
候选键②  管理员 + 物品名 ──→ 数量
             ↑
   仓库名 ←──→ 管理员       （互相决定）
             │
             └── 主属性“仓库名”只依赖候选键②的“管理员”这一部分
                           ⇒ 主属性对候选键存在部分依赖
```

读图说明：两组候选键都能决定数量，但主属性“仓库名”与“管理员”互相决定，导致“仓库名”实际上只依赖候选键②的一部分，而非整个候选键——这正是巴斯范式要消除的东西。

> **结论**：只要存在这种“主属性部分依赖于某个候选键”的关系，就不满足巴斯范式。反过来说，消除了这种部分依赖，关系就满足巴斯范式。

#### 拆分为仓库表与库存表

既然问题出在“仓库名”和“管理员”这对互相决定、又只依赖候选键一部分的属性上，改造办法就是把它们取出来单独成表。

**仓库表**：只要仓库名和管理员两列。

| 仓库名 | 管理员 |
| :--- | :--- |
| 北京仓 | 张三 |
| 上海仓 | 李四 |

**库存表**：放剩下的主键组合和数量。

| 仓库名 | 物品名 | 数量 |
| :--- | :--- | :--- |
| 北京仓 | 物品 A | 100 |
| 北京仓 | 物品 B | 200 |
| 上海仓 | 物品 A | 150 |

拆完之后，两张表仍然满足三范式，并且在此基础上还满足了巴斯范式。前面那三类问题——新仓库没有物品时插不进去、换管理员要改上百条记录、商品卖空要连坐删仓库——一个都不再出现了。

#### 学生导师表的部分依赖判定与拆分

为了把这个判断过程练熟，再看一张**学生和导师**的表，字段有：学生 ID、专业（major）、导师（advisor）、GPA。

先看学生 ID：它在整张表里**不是唯一的**。比如人工智能专业的学号是从 1 开始编的，大数据专业也是从 1 开始编的，两个专业的 1 号学生撞在一起了。

所以主键不能只用学生 ID。把学生 ID 和 major 合起来构成联合主键，就能定位到“某个专业的某个学生，他的导师是谁、GPA 是多少”。这和上面“仓库名 + 物品名”联合作主键是同一回事。

再看导师这一列。一个导师是哪个专业方向的，是确定的。于是“学生 ID + 导师”这俩合在一起**也能构成一个候选键**：我知道了这个学生和他的导师，导师的专业方向是确定的，这个学生的专业也就跟着确定了。

现在对照着看：

```text
候选键①  学生ID + 专业  ──→ 导师、GPA     （选为主键）
候选键②  学生ID + 导师  ──→ 专业、GPA
             ↑
   专业 ←──→ 导师        （导师一确定，专业就确定）
             │
             └── 主属性“专业”只依赖候选键②的“导师”这一部分
                           ⇒ 同样的主属性部分依赖
```

读图说明：结构与仓库案例完全一致——主键当中的一个属性（专业），被另一个候选键当中的一个属性（导师）所决定，所以它不满足巴斯范式。

改造方式也一样：把受影响的那一对属性拿出来，单独建一张**导师表**，一列是导师名，一列是导师的专业方向；剩下的学生信息表和导师组合使用，用“学生 ID + 导师”或者干脆用 major 都可以。

> **提示**：判断巴斯范式其实有一句更利落的说法——**每一个决定因素（determinant）都必须是候选键**。仓库案例里“管理员决定仓库名”、导师案例里“导师决定专业”，决定因素都不是候选键，所以不满足 BCNF。这和“主属性对候选键存在部分依赖”是同一件事的两种说法。

### 第四范式

#### 函数依赖、多值依赖与单值依赖

要把第四范式说清楚，得先理解**多值依赖**这个概念。

> **定义**：多值依赖就是属性之间的**一对多**关系——一个 K 值可以决定多个 A 的值。

与之对应的是**单值依赖**，那是一种**一对一**的关系。我们的函数依赖其实就属于单值依赖：一个自变量进去，经过一个函数出来一个因变量，一个对一个。所以函数依赖不属于这种一对多的关系。

#### 平凡多值依赖与非平凡多值依赖

多值依赖又分成**平凡多值依赖**和**非平凡多值依赖**两种。

> **定义（平凡多值依赖）**：整个表的字段集合 $U = K + A$，一个 K 对应多个 A，并且整张表里**只有这一组**一对多的关系。

> **定义（非平凡多值依赖）**：$U = K + A + B$，一个 K 对应多个 A，同一个 K 又对应多个 B。也就是说表里存在**多组**一对多的关系，而且这里有三个硬条件：多组关系里 A 和 B 必须**相互独立**；每组一对多的那个“一”必须是**同一个** K（不能是 K1 对应多个 A、K2 对应多个 B）；并且 A 与 B 之间互不决定。

> **提示**：这三个条件缺一不可，这里最容易混。判断的时候先找“一”，如果两组一对多的左边不是同一个属性，那它就不是我们说的非平凡多值依赖。

#### 第四范式的定义

第四范式是在满足巴斯范式的基础上，把**非平凡的多值依赖消除掉**、把函数依赖也去掉，**只保留平凡的多值依赖**，此时关系就满足第四范式。

#### 职工表的多值依赖与拆分

看第一个例子，一张**职工表**，字段是职工编号、职工孩子的姓名、职工选修的课程。

这张表里就是典型的多组一对多：一个职工编号可能对应多个孩子，同一个职工编号又可能选修多门课程。用上面的说法，就是非平凡的多值依赖——它是存在问题的，不满足第四范式。

| 职工编号 | 孩子姓名 | 选修课程 |
| :--- | :--- | :--- |
| 001 | 小明 | 音乐 |
| 001 | 小明 | 美术 |
| 001 | 小刚 | 音乐 |
| 001 | 小刚 | 美术 |

四个字段里主键就是职工编号。改造办法很直接：**把 K 决定 A 和 K 决定 B 这两组关系拆成两张表**。

**职工表 1**：职工编号、孩子姓名。

**职工表 2**：职工编号、选修课程。

#### 课程教师教材表的三范式校验与拆分

再看一个例子。一张表涉及三个字段：课程 ID、教师 ID、教材 ID。**一门课程可能对应多个老师来讲，一门课程也可能用多种不同的教材**——又是两组一对多。

为了表达方便，我们把 ID 换成具体的名字：英语、高数（course），具体的老师（teacher），具体的教材（book）。于是表里的行是这样的：英语这门课，某位老师讲，用的是某本教材；还是英语这门课，还是这位老师讲，但换了一本教材……

| 课程 course | 教师 teacher | 教材 book |
| :--- | :--- | :--- |
| 英语 | 张老师 | 教材 A |
| 英语 | 张老师 | 教材 B |
| 英语 | 李老师 | 教材 A |
| 高数 | 王老师 | 教材 C |

**先定主键**。单靠课程不行，它有重复值；课程加教师也不行，同一门课同一位老师可能配不同的教材。所以这张表的主键是**这三个字段合在一起**构成的一个联合主键。

因为主键把三个字段全占了，这张表里**只有主键，没有其他非主键属性**。那它满足三范式吗？毫无疑问：

- 第一范式的原子性满足；
- 第二范式要求非主属性完全依赖——现在根本没有非主属性，无从谈起，自然满足；
- 第三范式要求非主属性之间不能互相依赖——同样没有非主属性，也轻松满足。

> **易错点**：全主键的表非常容易让人误以为“高枕无忧”。它一二三范式确实都满足，但一个字段也没有的非主属性恰恰说明，这张表的信息全靠主键撑着，多值依赖一点没解决——所以它仍然不满足第四范式。

改造方式还是老规矩：**一个对应多个，就拆**。拆成两个一对多的关系，一个是课程对应教师，一个是课程对应教材。

```text
改造前（非平凡多值依赖）
+--------+---------+---------+
| course | teacher |  book   |     主键 = course + teacher + book
+--------+---------+---------+
| 英语   | 张老师  | 教材A   |
| 英语   | 张老师  | 教材B   |
| 英语   | 李老师  | 教材A   |
+--------+---------+---------+
        │  一个 course 对应多个 teacher
        │  一个 course 对应多个 book
        ▼
改造后（拆成两张表，各只保留一组一对多）
+--------+---------+          +--------+---------+
| course | teacher |          | course |  book   |
+--------+---------+          +--------+---------+
| 英语   | 张老师  |          | 英语   | 教材A   |
| 英语   | 李老师  |          | 英语   | 教材B   |
| 高数   | 王老师  |          | 高数   | 教材C   |
+--------+---------+          +--------+---------+
```

读图说明：原表把“课程—教师”和“课程—教材”两组互相独立的一对多塞进同一张表，形成非平凡多值依赖；拆成两张表后每组一对多各自成表，冗余度降下来，也就满足了第四范式。

#### 第四范式的实际取舍

虽然我们做了这一整套拆分，但**第四范式在实际当中已经用得很少了**。原因还是那个老问题：表拆得越细，相关查询的效率就越低。性价比不高，所以平时不太会主动往上走。

### 第五范式与域键范式

#### 连接依赖与第五范式的定义

除了第四范式，还有更高级的叫**第五范式**，它还有一个名字叫**完美范式**——都“完美”了。

第五范式是在第四范式的基础上，**消除不是由候选键所蕴含的连接依赖**。

> **定义**：如果关系模式 $R$ 中的每一个连接依赖均是由 $R$ 的候选键所隐含的，此时我们就称它满足第五范式。

这里冒出来一个新名词——**连接依赖**。这三种依赖是有层级关系的：

```text
函数依赖  ⊂  多值依赖  ⊂  连接依赖
（一对一）    （一对多）     （需经关系连接运算才显现）
```

读图说明：函数依赖是多值依赖的一种特殊情况，多值依赖又是连接依赖的一种特殊情况——越往右范围越大、条件越弱。

为什么要把连接依赖单拎出来？因为函数依赖和多值依赖的语义是**直接导出**的，看一眼属性关系就知道；而连接依赖属于**必须通过关系连接运算才能反映出来**的那种约束。存在连接依赖的关系模式，同样可能遇到相应的异常问题，这一点了解一下就行。

第五范式处理的是**无损连接**问题，它同样没有实际意义，做个了解就可以了。

#### 域键范式的理论定位

域键范式（Domain-Key Normal Form，DKNF）要解决的是一个“**终极范式**”的问题，属于理论上的研究，这个大家就不要去关注了。

为什么这类东西会一直有人在研究？一方面，理论研究在实践当中通常是更具前瞻性的——总得有人往前面探路；另一方面，研究也得有经费支撑，总得给研究者留点空间去研究些别的东西，不然经费不就没得花了吗。

#### 范式的实用取舍

学到这里，越往后的内容听一听就行。**整多了反而把自己整懵了。**

- **三范式 + 巴斯范式**：我们守到这儿，已经足够了；
- **第四范式、第五范式**：了解即可，实际用得很少；
- **域键范式**：理论研究的范畴，不用关注；
- **反范式化**：反倒是在很多情况下需要大家真正掌握的。

| 范式 | 解决的核心问题 | 实际使用建议 |
| :--- | :--- | :--- |
| 第一范式 | 属性的原子性 | 必须遵循 |
| 第二范式 | 非主属性对候选键的完全依赖 | 通常遵循 |
| 第三范式 | 非主属性之间的传递依赖 | 通常遵循 |
| 巴斯范式（BCNF） | 主属性对候选键的部分依赖 | 推荐遵循，性价比高 |
| 第四范式（4NF） | 非平凡的多值依赖 | 了解即可，用得很少 |
| 第五范式（5NF） | 非候选键蕴含的连接依赖、无损连接 | 了解即可，无实际意义 |
| 域键范式（DKNF） | 终极范式，域与键的约束 | 理论研究，不关注 |

这张表就是这一讲的取舍结论：范式这条线你可以一直往上走，但工程上真正要带走的是前面四行，以及在合适的时候主动往回走一步用反范式化换查询效率。

## 155-范式的实战案例
> 对应分集：P155 | 原始标题：《155-范式的实战案例》

范式讲完了，接下来我们把它用到一张真实的表上。我挑的例子是商超进货系统里的**进货单表**，也就是记录"哪一张进货单、从哪个供应商、进了哪个仓库、进了什么货、进了多少、多少钱"的那张表。

这张表已经摆在你们面前了，它的数据量非常庞大，很多行数据。一打开查询，花的时间很多，效率是比较低的。那么打眼一看这张表，你们其实就会发现里面有一些冗余的数据和字段，这种情况下就有必要对它进行改造。改造的标准是什么？就是我们前面讲过的范式。

先把这张表的结构摆出来，后面所有讨论都围绕它展开：

```text
                进货单表（改造前的单表）
+-------------------------------------------------------------------+
| 单号 供应商编号 供应商名称 仓库 条码 商品规格 单位 数量 单价 金额 |
+-------------------------------------------------------------------+
| 001       1      A 供应商   W1   0001  1袋6包   袋   200  ...  ...|
| 001       1      A 供应商   W1   0002   1盒10支  盒   400  ...  ...|
| 002       1      A 供应商   W1   0003    ...     支   ...  ...  ...|
| 003       1      A 供应商   W2   0001  1袋6包   袋   ...  ...  ...|
+-------------------------------------------------------------------+
     |         |                                       |      |
     |         |                                       |      |
     |         +--> 同一供应商的名称在每行重复一遍       |      |
     |                                                 |      |
     +--> 同一单号的多行里，单头信息被反复重复           +--> 单价 x 数量
                                                             即金额
```

读图要点：这张表的冗余不是"某几个字段写错了"，而是**同一份事实被存放在多个位置**——供应商信息跟着每一行商品重复，单头信息跟着每一行明细重复，而金额又完全由单价和数量算得出来。改造要做的，就是把这些重复存放的事实各归其位。

### 不规范的表结构带来的真实后果

在动手之前，先把"为什么非改不可"说清楚。这句话值得逐字读一遍：

> 在实际的工作场景当中，由于这种表的结构的设计的不合理，导致我们数据重复的现象，其实并不少见。往往是系统虽然能够运行，承载能力却很差，稍微有点流量，就会出现内存不足、CPU 飙升的情况，甚至导致我们整个项目失败。

这句话背后有一件事你们一定要意识到：**不像上学时考试那样，每一道题都有一个标准答案，还有人来给你打分。** 考试的时候这道题 20 分，你完全做出来了，过程一点问题没有，20 分；中间过程没问题、结果没算出来，15 分；一点不会，零分。可工作当中，谁给你针对一个需求、一张表的设计去打分？

- 首先，实际工作里**没有完美之说**。考试时一道题有个完美的解决方案、有个精准的做法，20 分全给你；工作当中没有这样的东西。
- 其次，**也没有人去衡量你是不是完美**。你说项目经理或组长给你审一遍？这不靠谱。他要是都给你审一遍，改是你改还行，改也不是你、他自己去改，那要你干啥呢？

从整个项目经理的角度来讲，他更多地看的是每个人分别负责的功能模块，然后该测试去测试，看看是不是通过测试；发现有 bug，就去改 bug。至于这张表你设计得可能并不好——**只要没有影响使用，测试的时候根本没测出来**。等数据量不断增长，后续才暴露问题，这时候反回去看，才发现当初的设计并不完美。

> **结论**：在实际生产环境当中，绝大部分场景下我们设计的表都不完美。那就得兵来将挡、水来土掩——后期发现了问题，我们再来改造。

下面这个流程就是"设计不完美"如何逃过测试、最终在线上爆发的路径：

```text
  表结构设计不合理（存在冗余）
            |
            v
  功能测试全部通过 ---------> 没有 bug，代码可以上线
            |
            v
  流量很小、数据量很小 -----> 慢一点，但察觉不到
            |
            v
  数据量持续增长、稍有流量 --> 内存不足 / CPU 飙升 / 承载能力差
            |
            v
  回头审视表结构 -----------> 承认设计不完美，此时改造
```

读图要点：这条链的关键在于**第一环和第三环**。冗余设计的代价不随功能上线而显现，只随数据量增长而显现，所以它在测试阶段是"隐形"的。这也是为什么表结构改造常常发生在系统跑了一段时间之后。

改造遵循的还是那三个范式，我们从低到高依次走一遍。

### 一范式改造：把可拆分的属性拆成原子字段

一范式的要求最直白：保证表里**每一个字段都是原子性的、不可再拆分的**。

那么从前往后逐个字段走一遍，看哪一个有可能会拆分。走到 `property` 这个属性上，问题就出来了——这个属性里写的是"一袋有 6 包""一盒有 10 支"这种信息。既然一袋、一盒是单位，6 包、10 支是具体规格，那我们完全可以把**单位和数量拆开**。

这就是从一范式角度做的处理：把 `property` 拆成两个字段。

| 拆出的字段 | 含义 | 例子 |
| --- | --- | --- |
| `specification` | 具体的规格 | 6 包、10 支 |
| `unit` | 计量单位 | 袋、盒、支 |

一范式也是最容易理解的一步，别的字段没有什么问题，就这样。

> **提示**：判断字段是否"原子"，要看它是否还承载了两个可以各自独立使用的事实。"一袋 6 包"这个字符串里，`unit`（袋）要参与后续的业务判断，`specification`（6 包）也要单独显示，它们就该是两个字段。

### 二范式改造：先定主键，再消除部分依赖

#### 二范式规则与主键的确定

在做二范式之前，你得先清楚它的规则：**在满足一范式的基础之上，数据表里边每条数据记录都必须可唯一标识。**

既然要能唯一标识，那实际上就是给这张表定义主键。定了主键之后，我们再看"完全依赖"的问题。

那么主键应该定义哪一个？这时候就要关注表里的这些字段了。一般来说，我们看到像"单号""编号"这类字段都会敏感一些——天然地就想把它们当成主键。

先看**单号**。单号是 001、002、003 这样递增的，而单号后面跟着供应商编号。你仔细想，这两个字段之间是不是有一种相互的依赖关系？

- 一旦确定了进货单号，**这个单号对应的供应商编号是谁，通常也就确定下来了**。001 对应供应商 1，002 也对应供应商 1，003 还是 1——供应商编号这块就依赖于单号。
- 供应商编号确定了，**供应商名称是不是也确定了**？所以供应商名称也依赖于单号。
- 仓库用的是哪一个，同样由单号确定。这几个字段都依赖于单号。

> **结论**：既然供应商编号、供应商名称、仓库这些都已经由单号决定，那单号和它们就没有必要合在一起构成主键。

继续往后看，单号下面就是这一单里具体进了哪些东西。这里注意到关键一点：**多行数据的单号都是 001**。那么条形码能完全由单号决定吗？显然不能——这些都是 001 的情况下，条码既有 0001 又有 0002，相当于这一单里进了两个不同的产品。如果拿单号单独当主键，就意味着出现了重复的主键值。

那我们把条码也考虑进来，两者合成主键，一看确实可以：在某个单号之下，具体进的是哪个产品就唯一确定了。这就像订单和订单里具体商品的 ID 一样，构成了一个**联合主键**。

再看后面的字段。条码其实就是我们平时买东西时商品后边那个条形码。**条形码确定了，你买的是什么东西就确定了；这东西以什么为单位也就确定了**——也就是说，后面那三个描述商品的字段都能由条码决定。所以主键里保留单号加条码这两个字段。

最后一批是进货数量、进货价格、进货金额。数量能完全由条码决定吗？不能，得看你买的是什么东西——这一行是 200 个，那一行是 400 个，数量必须结合单号才能定位到具体是哪一行。所以 `quantity` 是由**单号和条码共同决定**的，价格、金额同理，这几个合在一起考虑就行。

#### 部分依赖的识别与拆分

主键确定之后，接着看二范式真正要检验的东西：表里的主键是两个字段合起来的，后面那些非主键字段，**必须完全依赖主键**。如果某个字段只依赖主键的一部分，那就是部分依赖，不满足二范式，必须改造。

这张表里需要改造吗？显然需要，前面分析的时候你们已经发现了：

- 供应商编号、供应商名称、仓库这几个字段，**完全由单号就可以决定**，而单号只是联合主键的一部分。
- 条码后面的那几个字段，**完全由条码就可以决定**，条码同样只是联合主键的一部分。

这两个部分各自被"半把主键"决定，所以要把它们**单独拿出去各造成一张表**。这样一来，原来的一大张表就拆成了三张：

```text
  进货单表（原表）
        |
        |  单号部分依赖 -->  进货单头表      主键：单号
        |  条码部分依赖 -->  商品信息表      主键：条码
        |  剩下完全依赖 -->  进货商品明细表  主键：单号 + 条码
        v
  +-------------------+     +-------------------+     +---------------------+
  |  进货单头表       |     |  商品信息表       |     |  进货商品明细表     |
  +-------------------+     +-------------------+     +---------------------+
  | 单号      (PK)    |     | 条码      (PK)    |     | 单号      (PK)      |
  | 供应商编号        |     | 商品规格          |     | 条码      (PK)      |
  | 供应商名称        |     | 单位              |     | 数量                |
  | 仓库              |     | ...               |     | 单价                |
  +-------------------+     +-------------------+     | 金额                |
                                                      +---------------------+
```

读图要点：拆分的分界线不是"字段的个数"，而是**函数依赖的方向**。凡是只依赖单号的，进单头表；凡是只依赖条码的，进商品信息表；必须同时依赖两者才能确定的（数量、单价、金额），留在明细表里，用原来的联合主键。这三张表出来以后，二范式至少目前是满足了。

#### 条码作为主键的边界情况

在讲三范式之前，要说一个上面这张表里没有体现、但实际情况中一定会出现的小细节。

条码是商品上的条码。以棒棒糖为例，一盒当中有 10 支，其实**每一支上也都有一个条码**——只是这个条码是按盒卖的时候用的。可你在超市里会发现，有些商品不仅论盒卖，还可以散装卖：一支多少钱，或者论斤卖。

问题就出在这里：**散着卖和按盒卖用的是同一个条码。** 如果拿条码当主键，就会出现重复的情况，只是在这个例子里恰好没出现而已。就好比下面又出现了一行 `0002` 的棒棒糖，它却是散装的——这时候用条码当主键就不合适了。

> **易错点**：把业务上"看起来唯一"的编号直接当主键，是最常见的隐患来源。条码在"同一商品的不同销售形态"下会重复；单号在"一单多行明细"下会重复。真正能唯一标识一行的键，必须把这两种情况都覆盖掉。

所以我的建议是：**在这张表的基础之上，专门提供一个列来充当主键。** 比如同样是 0002 这个条码，我们额外给一个值：2 表示论盒卖，3 表示散装卖，这样就区分开了。

这个主键提出来之后，明细表里就不要再直接记条码了——因为你进货的时候也要指明到底进的是散装还是论盒装，光写 0002 说不清楚。所以要把它替换成商品信息表里的那个主键。

### 三范式改造：消除非主键字段之间的依赖

第三范式要先回顾它的要求：在一个表里，主键之外的那些非主键属性**彼此之间必须是独立的，不能相互依赖**。

现在回过头把拆出来的表一张张分析。

#### 进货单头表：`supplier_id` 与 `supplier_name` 的依赖

先看第一张表。它的主键是单号。那么后面这几个字段之间有没有相互依赖关系？一看还真有——因为**这里有重复数据出现**，重复数据一出现，八成就是这里有点问题。

具体是哪两个？`supplier_id` 和 `supplier_name`。供应商名称很显然是由供应商编号决定的：编号一定，名字就定了。这就是依赖关系，所以它**不满足第三范式**，需要改造。

至于仓库（`stock`）那一块，倒是没有问题。

#### 商品信息表：规格与单位是否构成依赖

再看第二张表。主键是条码，后面跟着商品规格、单位这些字段。这几个之间有没有依赖关系？

有同学会说"这两个互相依赖"，但**这不算**。它不一定是"有了这个之后，单位就一定是袋"这种一一对应的关系——规格是 6 包，单位也可以是盒；规格是 10 支，单位也可以是盒。它们之间没有函数依赖，所以这张表是满足第三范式的，不需要动。

#### 进货商品明细表：单价、数量、金额三者的相关性

第三张表的主键是单号和条码这两个字段，要重点看的是后面这三个字段之间有没有依赖关系。

> **易错点**：有同学一看说"没事，走吧"。有事，这个注意有事。

这三个字段分别是：具体商品的单价、进货的数量，以及两者相乘之后的结果（金额）。也就是说，**这三个字段之间是有依赖关系、有相关性的**。它不像是某个字段完全依赖于另一个字段那么直接，但你这两个的乘积**恰好就是后面这个金额**。

既然存在这种依赖，就不满足三范式。改造思路是：这三个里面留任意两个就行——留下单价和数量，金额由两者相乘得到；或者留金额和数量，除一下也能得到单价。

#### 供应商信息的抽取与改造结果

既然不满足三范式的原因是 `supplier_id` 和 `supplier_name` 这两个字段之间存在依赖，那把这俩单独抽出来就可以了。

于是那张表我们就不要了，把它拆出来造成单独一张**供应商表**。相应地，**进货单头表**改造成只记录 `supplier_id`，不再记录 `supplier_name`——原来一张表变成这两张表，这样就可以了。

```text
  改造前：进货单头表                     改造后：进货单头表      供应商表
  +--------------------------+          +------------------+  +------------------+
  | 单号 (PK)                |          | 单号 (PK)        |  | supplier_id (PK) |
  | supplier_id              |  ---->   | supplier_id (FK) |  | supplier_name    |
  | supplier_name            |          | 仓库             |  +------------------+
  | 仓库                     |          +------------------+
  +--------------------------+                  |
                                                  +--> 名称只存一份，靠 id 关联
```

读图要点：`supplier_name` 从单头表移到供应商表之后，单头表里只留 `supplier_id` 作为指向供应商表的外键。同一个供应商的名字不再随每一行进货记录重复存放，`id → name` 的依赖关系被收纳到供应商表内部——而这正是主键决定非主键的正常形态。

### 最终的四表结构与性能收益

改造到这里，连同前面拆出来的表，一共得到了四张表。把最初那张大表再拿出来对比一下：

| 表名 | 主键 | 保留的关键字段 | 这一步为什么这么拆 |
| --- | --- | --- | --- |
| 进货单头表 | 单号 | `supplier_id`、仓库 | 单号决定单头信息，供应商名称再抽到供应商表 |
| 商品信息表 | 商品主键列 | 商品规格、`unit` | 条码（或新增主键列）决定商品属性 |
| 进货商品明细表 | 单号 + 商品主键 | `quantity`、单价、金额 | 数量必须由单号与商品共同决定 |
| 供应商表 | `supplier_id` | `supplier_name` | 消除 `id` 与 `name` 之间的依赖 |

原有的表里存在很多冗余信息，现在拆成了四个。改完之后，收益体现在两个地方。

**第一是存储空间。** 冗余数据变少了，实际占用的存储空间就节省了。

**第二是查询性能。** 这一点更隐蔽，值得说细一点。查询的时候，我们不一定非得把整张表都用上。假设一开始走的是二级索引，而且没能用上覆盖索引，那就需要**回表操作**。回表意味着要把这张表里完整的一整行数据都加载进来。原来那张表的字段很多，一旦查询的数据量还比较大，需要加载的数据页就会很多；而每个页里能存下的数据行数又很有限——因为字段太多了。这样性能肯定会比较差。

拆成几张表之后就不同了：回头查询的时候，很可能根本不需要每次都把每个表都用一遍，性能反而还能好一些。当然，这样拆分之后我们是在一定程度上达到了一个平衡——空间、I/O 与查询便利性之间的平衡。

### 为什么不继续改造第三张表：反范式化

四张表出来了，但最后我们会发现，**第三张表（进货商品明细表）我们就不改造了**。为什么这里不再去解决它的冗余问题？这就回到我们想强调的一个概念：**反范式化**。

#### 业务优先原则

反范式化背后有一条原则叫**业务优先**。什么叫业务优先？就是在实际开发当中，**一定要以业务需求为主**——我们的技术是要服务于业务的，你不能反了。

你不要觉得"技术是老大，业务服务于技术"，那就反事了。除非你是专门开发框架的公司，否则你是要做具体业务的。所以**完全按照理论的设计不一定是最优的**，还需要结合实际情况去做决定。

那么，为什么这里就不处理这个冗余了？因为处理掉它，可能会带来下面两个真实的问题。

#### 计算精度问题

很多时候我们拿到这个字段的时候（比如有促销活动出现），对方可能**只给我们保留总金额这一个字段**，说金额是多少一定要看到。

那按照"三范式留两个字段"的思路，我们就不要单价这个字段了，只保留总金额和 `quantity`。可这时候如果业务上需要单价呢？**就要除一下**。而问题在于，这是搞活动之后的价格，你用它除以数量，得到的结果有时候是**除不尽**的。

除不尽就要四舍五入，一旦四舍五入，得到的值跟真实价格就不一致了。

举个例子：假设总金额是 25.5，数量是 34，相除得到 0.74——这已经做过四舍五入了。那么反过来用 0.74 乘以 34，结果是 25.16，跟原来的 25.5 就对不上了。

$$\frac{25.5}{34}\approx 0.7500 \quad\Longrightarrow\quad \text{四舍五入为 } 0.74,\qquad 0.74 \times 34 = 25.16 
eq 25.5$$

你可能会说，这不就小数点后差一点点吗？可你想想，如果整个进货系统数据量比较大，这些微小的差别**在核算汇总的时候，就有可能差几百块钱、上千块钱**。到那个时候，别人会怀疑"是不是有人做假账"。其实根本原因是**字段被省略之后，四舍五入的误差累积**造成的。这就会有问题。

```text
  只保留 金额 + quantity（去掉单价）
        |
        |  业务要单价  -->  金额 / quantity
        v
  除不尽  -->  四舍五入  -->  单价失真（0.7500 -> 0.74）
                                   |
                                   v
                    单价 x 数量 = 25.16  !=  25.5（原始金额）
                                   |
                                   v
                 单据级误差 0.34 元 --> 汇总核算放大为数百上千元
```

读图要点：误差不是在单行里"看起来很小"就安全。误差方向一致（都是四舍五入产生的方向性偏差）时，**行数越多，累计越大**，最终表现为账目对不上，而账目对不上在业务上是非常严重的问题。

#### 频繁查询的计算成本

另一个情况是查询。如果我们不要金额这个字段，只管单价和 `quantity` 这两个字段，那就意味着**每次查询的时候都要现算一次两者的乘积**。

如果查询的数据量还比较大，而且这种查询还很频繁，那么数据量一大、运算又常做，**花费的成本就会比较高**。这时候倒不如**浪费一点空间**，保留这样一个冗余字段，每次查询直接拿来用就可以了。

基于这两个原因，最终的决定就是：**保留这个冗余字段**——单价、数量、金额三者都留在进货商品明细表里。

> **结论**：三范式告诉我们"该拆"，反范式化告诉我们"哪里可以不拆"。判断依据不是理论纯粹性，而是**该冗余字段带来的是收益还是风险**：金额这类可直接引用的汇总值，保留它省下的是高频运算成本和舍入失真风险；而供应商名称那类可以被主键完全推导、且不参与高频精确运算的字段，拆出去才是净收益。

最终，我们用这四个表完成了对原有那一张表的改造，这就是这一讲的实战。

## 156-ER建模与转换数据表的过程
> 对应分集：P156 | 原始标题：《156-ER建模与转换数据表的过程》

### 为什么要在立项之初做 ER 建模

数据库的设计是牵一发而动全身的。这句话大家现在应该已经有概念了：一旦数据表设计好、数据也陆陆续续往里加了，后续才发现表设计本身有问题，这时候改动的成本是极高的。

那有没有什么办法，能让我们在项目立项之前就看到——或者说就能设计出——数据库里这些表之间的关系？当然，不管关系怎么定，首先得回答三个问题：到底有哪些表、每张表里该有哪些字段、表跟表之间靠什么字段连接。这就是立项之初必须想清楚的事。

> **定义**：ER 模型（Entity-Relationship Model，实体-关系模型）就是用来做这件事的工具，它帮助我们在创建数据库中的表之前，先把实体、属性和关系刻画出来。

需要建模的不只是新项目。一个项目已经建好了，现在要做二次开发，或者项目在运行过程中出了问题，我们想去看看现有项目里的表到底长什么样、是什么情况——这时候同样要用到 ER 模型。所以它不是为了创建而创建的东西，它是为我们服务的，这一点要先明确下来。

> **结论**：ER 模型是工具，不是负担。我们的目的是建表，ER 模型只是让建表之前先看得清楚。

用不用它，取决于项目规模：

- 项目很小，几张表就搞定了——比如写一个移动端的 Android 应用或 iOS 应用。客户端应用涉及的表其实非常少，几张表够用，顶多十几张。这时候你要觉得整一个 ER 模型有点麻烦，那不写就不写了，也 hold 得住。
- 项目一旦大起来，可能上百张表、几百张表，乃至更多，那就一定有必要先做一次建模分析：用 ER 模型把项目涉及的表、表里的字段、表之间的关系统统刻画出来，再照着这个结构去建表。

顺带说一句：我们开发项目的实质就是一个建模的过程。为什么我们叫开发工程师？工程师——学编程的时候我一想到工程师，脑子里就是盖房子那样，戴个安全帽。其实软件建模和真正盖房子那个建模是类似的，两件事都叫工程师，非常合理。

### ER 模型的三要素

ER 模型的三要素是实体、属性和关系。上篇讲数据库概述、引出关系型数据库设计规则的时候其实已经提过：E 就是 Entity，R 就是 Relationship。除实体、关系之外，还有第三个要素——属性。表跟表之间的关系，也提过一对一、一对多、多对多，以及自我引用的关系。这里在三要素上做一次复习并展开说明。

#### 实体与强弱实体

> **定义**：实体（Entity）可以看作数据对象。员工表、学生表、订单表、商品表，这些具体的表在 ER 模型里就是一个数据对象，用**矩形**表示。

实体分两种：

- **强实体**：不依赖于其他实体就能存在。
- **弱实体**：依赖于别的实体才能存在。

不依赖别人的叫强实体，那显然依赖别人的就叫弱实体。文化圈里不也有强势文化、弱势文化之说吗——强实体、弱实体，一个道理。

#### 属性

属性其实我们已经接触过很多张表了，可以直接说：属性就是实体里的一个字段。

> **定义**：属性（Attribute）是实体内部的字段，比如超市的地址、联系电话、员工数，员工表里的员工名字、员工 ID、员工薪资，在 ER 模型里用**椭圆形**表示。

#### 关系

> **定义**：关系（Relationship）刻画的是实体与实体之间的联系，在 ER 模型里用**菱形**表示。

#### 实体与属性的区分

这里有一个要注意的地方：实体跟属性容易分不清。有时候我们明明面对的是一个属性，却给它建成了实体。要知道，**实体是要以表的方式确定下来的**；一个本来只是属性的东西被造成实体，就不太合适了。

怎么判断？两句话：

> **结论**：可以独立存在的是实体；不可再分的是属性。

拿联系电话检验一下：联系电话能独立存在吗？说联系电话，你得说清楚是谁的电话、哪儿的电话，所以它不能独立存在——独立存在的是实体。再看不可再分：地址还能接着往下分吗？员工数还能往下拆吗？都不能，所以它们是属性。

刚开始区分不开很正常，随着经验越来越多，看一眼什么是实体、什么是属性，基本上就一目了然了。

> **易错点**：把属性误判成实体，就会多造出一张表。判断口诀就是「实体能独立存在，属性不可再分」。

---

### 关系的三种类型

#### 一对一

一个实体跟一个实体一一对应：一个人对应一份身份证信息，一份身份证信息也属于一个人。

#### 一对多

一对多在实际开发中的场景相当多：

- 一个班级对应很多学生，反过来一个学生只能对应一个班级——注意，学生这一侧要是「只能对应一个」，才是一对多，不能是多对多。
- 一个部门有很多员工，一个员工只属于一个部门。

#### 多对多

多对多的例子也很多：

- 供货商和超市：一个供货商可以给多个超市供货，一个超市也可以从多个供货商进货。
- 选课表：一个科目可以有很多学生选，一个学生也可以选很多科目。
- 订单和商品：一个订单里可以包括多个商品，一个商品也可以分布在多个订单当中。

### 电商场景的实体关系刻画

建模得有场景。这里以电商业务为例，因为电商业务比较复杂，所以我们做了一定的简化，以尚硅谷的电商项目「尚品汇」为例来说明。

简化在哪里？比如商品表里的 SKU、SPU，真正创建数据库的时候，商品表里是要体现这两个概念的，这里只提 SKU，SPU 就不提了。

这个电商业务一共简化为**八个实体**，八个实体对应的就是下面罗列出来的八个。其中要先强调一点：

> **结论**：用户实体和商品分类实体是两个强实体，不依赖其他实体存在；其余实体多少都依赖于用户实体存在，属于弱实体。

#### 实体与关系的结构

实体用矩形表示，关系用菱形表示，先把这两个要素刻画出来。八个矩形就是八个实体，其中有且只有两个强实体：

| 实体 | 强／弱 | 依赖谁 | 说明 |
| --- | --- | --- | --- |
| 用户 | 强实体 | 不依赖 | 其余实体的依赖源头 |
| 商品分类 | 强实体 | 不依赖 | 只被商品依赖 |
| 商品 | 弱实体 | 商品分类 | 归属于一个分类 |
| 订单 | 弱实体 | 用户 | 归属于一个用户 |
| 购物车 | 弱实体 | 用户 | 与用户一对一 |
| 地址 | 弱实体 | 用户 | 一个用户可有多个 |
| 评论 | 弱实体 | 用户、商品 | 同时关联这两个实体 |
| 订单详情 | 弱实体 | 订单、商品 | 订单与商品之间的中间实体 |

依赖方向画出来就是一棵以强实体为根的结构，读它是为了确认「先造谁、后造谁」。缩进表示依赖层级，每个实体后面括号里注明它依赖谁：

```text
用户（强实体，不依赖别的实体）
  +-- 订单（依赖 用户）
  |     +-- 订单详情（依赖 订单 + 商品）
  +-- 评论（依赖 用户 + 商品）
  +-- 购物车（依赖 用户）
  +-- 地址（依赖 用户）

商品（依赖 商品分类）
商品分类（强实体，不依赖别的实体）
```

读图要点：越靠左越先造。用户和商品分类不依赖任何实体，位于结构根部，必须先转成表；订单详情和评论各自挂在两个父实体下面，这也是它们身上要加两个外键的来源。

#### 关系的逐条剖析

实体之间一共连了九条关系线，一条一条看：

| 涉及的实体 | 关系类型 | 判断依据 |
| --- | --- | --- |
| 用户 — 地址 | 一对多 | 一个用户可以有家里、公司、老家多个地址；一个地址只属于一个用户 |
| 用户 — 购物车 | 一对一 | 一个用户就一个购物车，一个购物车也只归属一个用户 |
| 用户 — 订单 | 一对多 | 一个用户可以多次下单，光双十一就可能下好几单；一个订单只归属一个用户 |
| 用户 — 评论 | 一对多 | 一个用户可以在多个商品下评论，也可以在同一商品下多次评论；一条评论只归属一个用户 |
| 订单 — 订单详情 | 一对多 | 一个订单里有多个不同种类的商品，对应多条订单详情 |
| 订单 — 商品 | 多对多 | 一个订单中多个商品，一个商品也可能分属在不同订单当中 |
| 商品 — 商品分类 | 一对多 | 一个分类下多个商品，一个商品只归属一个分类 |
| 商品 — 评论 | 一对多 | 一个商品有多个评论，一条评论只归属一个具体的商品 |

> **易错点**：一对多里「一」在哪一侧要盯死。比如班级和学生：一个班级对应很多学生，但一个学生只能对应一个班级，这才是它成立为一对多的前提；学生那侧要是也能对应多个班级，就变成多对多了。

这里关系讲得有点像绕口令，但实体之间的关系捋清楚了。至此我们只涉及了两个要素——实体和关系，接下来要做的就是在结构之上把属性加上去，用椭圆表示。

> **提示**：属性这一层这里就直接罗列出来了。我们讲的是整个建模的过程，不是实际去写电商项目、讨论每张表该有什么字段，所以只做罗列，必要时也做了简化处理。

### 从 ER 模型到数据表的转换准则

把属性统一呈现在 ER 模型当中，图一下就变得密密麻麻了——这才是一个完整的场景。下一步就该考虑：怎么把这个 ER 模型转换成具体的数据表？

> **提示**：想查看一个数据库的 ER 模型是什么样，就可以看这样一张图景，看它的实体、属性、关系各是什么样子。当然这张图针对的是简化后的电商项目，实际的电商项目不可能只有这几张表。

转换有准则。不记住这个准则，你就不知道该怎么转：

1. **一个实体转换成一个表**。图上画的每个矩形，都对应一张独立的表。
2. **一个多对多的关系转换成一个表**。上篇讲多对多关系时就说过：要表达多对多的关系，必须创建第三张表，通常叫连接表，叫中间表也行。比如这样一张表和那样一张表是多对多关系，怎么表达？必须有个中间表。学生和课程之间要刻画，就得有一张选课信息表；订单和产品之间要刻画，就得有一张订单详情表。
3. **一对一和一对多的关系，通过外键来刻画**。
4. **属性就是表里面的字段**，这一条最简单。

#### 八个实体为什么不是八张表

按第一条准则，八个实体应该对应八个表。这里确实数出来是八个表，但其中有一个表的性质不一样，先说清楚：

- 其余**七个实体对应七张表**，走的是准则里的第一条——一个实体一个表。
- **订单详情**这张表不是实体直接转出来的，它走的是准则里的第二条：订单和商品是多对多关系，需要拿一张表去刻画，这张表就是订单详情表。

所以「八个实体」是从实体跟表的对应关系上数出来的，其中订单详情是由订单与商品这两个关系决定出来的一个实体，这一点要注意。

#### 转换顺序：必须先转强实体

先考虑一个实体转换成表。那先从谁下手？**先考虑强实体**。

为什么不按图的顺序、想整哪个整哪个？因为强实体的定义就是不依赖别人。先把强实体全部造完，再去造弱实体：弱实体依赖别人，那么在造它的表的时候，该加的外键这些东西是不是直接就能加上了？你依赖于别人嘛。

> **结论**：转换时一定要先转换强实体，再转换弱实体。顺序反了，弱实体该加的外键就没有着落。

---

### 强实体的转换

强实体有两个：用户实体和商品分类实体。

#### 用户实体

用户实体里有相关的一些字段，这些字段大家自行提供就行。这里有一个之前可能没提过的点：给字段加上 `comment`。

> **提示**：`comment` 相当于一个备注，指明这个字段具体是什么含义，起的就是这么个作用。

#### 商品分类实体

商品分类这个实体要多说两句：设计的时候我们把它**分成两个表**来存储，一个叫一级分类表，一个叫二级分类表。这也跟实际情况吻合。

比如打开京东，你看到的这一大块就相当于一级分类表——家用电器、手机、运营商、数码等等。你点一下「手机」，下面呈现出来的那一块就可以理解成二级分类。这么分的主要原因就是栏目太多了，相当于给它划分了层级。就像我们写书一样，有一级目录、二级目录、三级目录。

分成两个表的话，结构是这样：

- **一级分类表**：一个 `id`，一个 `name`，就完了。比如 `id` 是 1，`name` 叫家居；或者 `name` 叫手机。
- **二级分类表**：有自己的二级 `id`、二级名称，还要有「这个二级归属于哪一个一级」。比如归属于前面那个 id 为 2 的「手机」，那么这个二级分类里就有自己的 id 和名称，比如叫「手机配件」。

两种方案对照如下：

| 对比维度 | 单表 + 父分类编号 | 一级分类表 + 二级分类表 |
| --- | --- | --- |
| 表结构 | `id`、名称、父分类编号（自引用） | 一级表：`id`、`name`；二级表：二级 `id`、二级名称、所属一级分类 |
| 非空约束 | 该字段必须允许为空 | 两个表各自字段含义明确，不需要靠空值区分层级 |
| 业务风险 | 二级分类漏填父编号时会被误认为一级分类 | 层级由表本身区分，不存在误判 |
| 查询与索引 | 按「父分类编号非空」筛二级分类，`is not null` 用不上索引 | 需要哪一级就查哪张表 |
| 范式 | 不符合第二范式（该字段未严格依赖主键） | 符合规范要求 |

有同学会问：为什么要这样划分？我就用一张表刻画行不行？

用一张表刻画「商品分类」，字段是：一个 `id`、一个当前分类的名称，再加一个**父分类的编号**。

- 如果这一行是一级分类栏目，那就是有 `id`、有名称，父分类编号**全是 `null`**。
- 如果这一行是二级分类栏目，那就是有 `id`、有名称，父分类编号关联到它所属的那一级分类的编号——这其实相当于一个自引用。

看着挺好，没什么问题？不是。**从业务层面讲不好，从范式要求的结构层面讲也不好。**

业务层面的第一个问题是父子判断会混乱。一级分类的父分类编号肯定都是空的，这没问题。但为了让一级分类能存进来，这个字段就必须允许为空，也就没有非空约束了。那么用户添加一个二级分类时，如果父分类编号这一栏他没写具体值，这个二级分类的父分类编号也是空的——这时候你就有可能把一个二级分类误认为是一级分类，业务数据就乱套了。

业务层面的第二个问题是查询条件会用不上索引。二级分类的特点是这个字段一定是非空的：字段非空就一定是二级分类。所以我们会用「父分类编号非空」来筛二级分类。但前面讲过 `is not null` 这种写法是没办法使用索引的，等于这时候索引还用不上，从优化角度讲也差点意思。

再从范式规范上讲，用一张表也不符合第二范式。第二范式的要求是：以这个字段为主键，其他非主键属性（叫非候选键属性、非主属性都可以）要**完全依赖**于主键。而单表方案里，父分类编号这个字段很多值都是 `null`，它其实就不是依赖于这一行的编号了，不是严格依赖于主键。

> **结论**：无论从业务上讲还是从范式上讲，单表方案都要改造——把它拆成一级分类表、二级分类表两个表，这样表达是最好的。

### 弱实体的转换与中间表

强实体转完，剩下的是弱实体。原来数的是八个实体，先把订单详情抠掉，就是七个实体；七个减去用户、商品分类这两个强实体，还剩**五个**：商品、订单、购物车、地址、评论。这五个的具体细节这里不展开，加上前面两个强实体，正好七个。

#### 多对多关系转成的订单详情表

再来看多对多的关系：商品和订单这两张表要体现多对多，就得用一个中间表，这个中间表就是订单详情表。

订单详情表里要体现两边的主键：

- 订单详情表**自己的主键**；
- 一个字段相当于**订单表的主键**（`order_id`），关联到订单；
- `sku_id` 相当于**商品表的主键**，关联到商品。

除此之外，你再去加该提供的其他字段，比如商品的名称、商品购买的个数、操作的时间，需要就加。

> **结论**：中间表 = 自己的主键 + 两侧实体的主键 + 这张中间关系自身需要的业务字段。这就构成了描述多对多关系的中间表。

---

### 一对一与一对多关系的外键刻画

表定下来之后，关系里还剩一对一和一对多，这两种用外键去刻画就可以了，不需要单独建表。

以商品评论表为例：商品评论表跟商品表、用户表都是一对多的关系，那就用外键来衡量：

- 在商品评论表里加一个 `user_id`，跟用户表的 `id` 做关联；
- 商品评论表里再有一个 `sku_id`，跟商品表的 `sku_id` 做关联。

这样就体现了外键的关联。用户跟购物车是一对一的关系，同样建立这种外键关系就行。

#### 外键约束的两个面

关于外键，要再啰嗦两句。讲商品约束的时候提到过外键，不光是知道怎么创建，还说了一个结论：**在实际开发当中，我们不建议在表的设计当中应用外键约束**。这里是一样的道理。

- **好处**：保证数据的一致性，这不用多说。
- **坏处**：会导致性能下降。因为添加数据的时候，先要考虑从主表里做一个判断，然后再考虑从表；在处理数据的时候也很麻烦。像电商平台访问量突然很大的时候，设置了外键一定会对性能产生影响。

> **结论**：外键约束不建在表上，而是在应用层面去做数据的检查。

而且要说清楚：在应用层做数据检查是一个非常正常的需求。

#### 应用层检查的实例：学生选课

比如学生选课系统，学生需要选课。正常来讲这里应该有外键关联，因为你不能让学生去乱写课程 ID，写一个不存在的课程就麻烦了，这其实就是个外键关联。

但我们在客户端呈现的时候是怎么做的？一般情况下，学生选课的时候，课程 ID 这一栏都是一个**下拉框**，下拉框里能列出来到底有哪些课可以选；或者让他去写一个具体的文本内容，写完去搜索，没搜到就重写。

总之在客户端这块就可以加上这样的限制：只能从这里面去找。那其实自然而然就达到了外键约束同样的效果。

> **提示**：在应用层安排外键的功能，既避开了数据库层的性能开销，又保住了数据一致性，是一件非常合情合理的事。

### 属性与整体流程收束

实体和关系都刻画完了，剩下就是属性的问题。属性比较简单，它就体现为表中的字段，在表里设置具体字段就可以了；具体的设置方式在讲创建表的时候基本都提到过。

至此，整个流程就走完了：先在电商业务里创建一个 ER 模型，再把这个 ER 模型转化成具体电商项目当中的表。

```text
  梳理业务的实体、属性、关系
            |
            v
      画出 ER 模型图
   （矩形 = 实体 / 椭圆 = 属性 / 菱形 = 关系）
            |
            v
     按准则做转换
        +-- 1 个实体 ............ 1 张表
        +-- 1 个多对多关系 ...... 1 张中间表
        +-- 一对一 / 一对多关系 .. 用外键刻画
        +-- 属性 ................ 表中的字段
            |
            v
     转换顺序：先强实体，后弱实体
            |
            v
      落地成电商项目的表结构
```

读图要点：转换准则四句话是这张流程图的骨架，其中「先强实体、后弱实体」是动手建表时的执行顺序，多对多那一条会额外产出一张中间表。

通过这个过程也能感受到：ER 模型就是一个工具，方便大家在创建项目之初，对整个项目的表结构设计有一个更清晰的认识，然后按这个结构接着去创建表。它是个很好的工具，不要把它当成一个冗余的、限制你工作的东西——它是为你所用的，这点一定要注意。

> **结论**：本讲要记住的就是两件事——ER 模型的三要素（实体、属性、关系），以及把 ER 模型转成表时遵循的那套准则。ER 模型难度不大，但非常实用，课后可以再体会体会。

## 157-数据库的设计原则和日常SQL编写规范
> 对应分集：P157 | 原始标题：《157-数据库的设计原则和日常SQL编写规范》

范式、反范式、ER 模型都讲完之后，剩下的问题就很朴素了：落到键盘上，库名怎么写、表怎么建、索引怎么加、SQL 怎么敲。这一讲先收一个总纲——数据表的"三少一多"，再把编写层面那些一条一条的规则捋一遍。这些规则不难，也不需要背，但每一条背后都压着一个真实踩过的坑。

### "三少一多"：数据表的设计总纲

设计原则这一块，归根到底就一句话：**三少一多**。三少是数据表的个数越少越好、字段的个数越少越好、联合主键的字段越少越好；一多是使用主键和外键越多越好。下面逐个说。

#### 表的个数越少越好

表少，第一层好处是**关系简洁**。我们刻画表跟表之间的关系（relationship）时，实体越少，这个关系网就越简单，整个数据库的设计就更容易被理解。

第二层好处是**关联查询的性能**。表少意味着 JOIN 的表少，性能自然就更高。

> **结论**：减少表的数量，同时买到的是可理解性和查询性能两样东西。

#### 字段的个数越少越好

字段越多，发生**冗余**的可能性就越大。回想实战案例里那张表——就一张表，字段一大堆，冗余度非常高，所以我们才要把它拆着改造成满足第一范式、第二范式、第三范式。

但这里有个前提必须说清楚：**字段少是一个相对概念**。前面讲过反范式化，为了查询性能更高，我们是主动、适当地增加了冗余的。所以这不是要把字段压到最少，而是要在**数据冗余和检索效率之间达到平衡**。

再往深一层看，"表的个数少"和"字段的个数少"这两条自己就打架。案例里那张表只有一个表，按说挺好，可它字段极多；真要拆成好几个表，表就多了，字段却少了。所以这两条本质上是有矛盾的，也只能取平衡。

> **提示**：三少一多是一个**指导性的方向**，不是可以机械套用的硬指标。规则之间会冲突，冲突的地方就得靠判断去平衡。

#### 联合主键的字段越少越好

如果主键里只有一个字段，那当然最好。但在没法用单个字段唯一确定一条记录的时候，就只能上**联合主键**（composite primary key）。这种时候，联合的字段越少越好。

原因要落到索引的底层结构上看。主键对应的是主键约束，对应到底层就是一棵 B+ 树；而且不管是聚簇索引，还是非聚簇索引（也就是二级索引），**非叶子节点和叶子节点上都会存主键的值**。

```text
           B+ 树（含二级索引）中的主键值存储

  聚簇索引                          二级索引
  ┌──────────────┐              ┌──────────────────────┐
  │  非叶子节点   │              │  非叶子节点           │
  │  ├ 主键值     │              │  ├ 索引列值 + 主键值  │
  │  └ 页号       │              │  └ 页号               │
  └──────┬───────┘              └──────────┬───────────┘
         │                                  │
  ┌──────▼───────┐              ┌──────────▼───────────┐
  │  叶子节点     │              │  叶子节点             │
  │  └ 整行数据   │              │  └ 索引列值 + 主键值  │
  └──────────────┘              └──────────────────────┘
```

读图说明：两类索引的每一个节点上都要存放主键值，二级索引更要在每个目录项里额外带上主键值。

于是结论就顺着出来了：联合主键的字段越多，单个数据项（目录项）占用的空间就越大，一个**数据页**里能存放的数据项就越少，加载的时候也更浪费时间。

#### 主键和外键越多越好

主键不用多说，一张表一定会有，而且只会有一个。这一条真正想强调的是**外键**。

听到这里会有疑问：前面不是刚说过不要使用外键吗？**这里的"外键"要往外扩一点理解**——它指的不是外键约束本身，而是"描述外键关系的这样一种关系"。一对一的关系、一对多的关系，我们完全可以在业务逻辑层去实现；只要能实现这种外键关系，就算数。

> **定义**：本讲所说的"多外键"，指的是**实体之间被明确刻画出来的关联关系**（在业务层或模型层实现），而不是数据库里必须存在的 `FOREIGN KEY` 约束。

这种关系越多，实体之间的冗余度就越低，它们之间的利用度就越高。

到这里，四条的矛盾点也就清楚了：表的数量、字段的数量、联合主键的字段数、关联关系的数量，彼此之间互相牵制，最终都要落到平衡上。**整个规则体系都不是绝对的。**

### 库的编写规范

接下来是务实的部分——真正写 SQL 的时候要注意什么。先看**库**这一层。

#### 命名：小写加下划线，禁止关键字

库名**一定要小写**，不同单词之间用下划线分割。不规范地写大小写混排，数据库其实不报错，但规范上建议大家一律小写。

> **提示**：我见过很多编写不规范的写法，都是从小写这一条上开始跑偏的。它不会带来报错，所以最容易长期没人纠——正因为如此才要专门提一句。

命名方式上，前面的部分是**项目／系统名**，后面跟**子系统名**，中间用下划线连接。

```text
  库名构成：<项目系统名>_<子系统名>

  示例结构：  project_systemname_subsystemname
              └──── 项目/系统名 ────┘ └─ 子系统名 ─┘
```

库名里**禁止使用关键字**，这条不用多解释。

#### 字符集与服务器默认值

创建库的时候尽量显式指定字符集：

```sql
CREATE DATABASE db_name
  DEFAULT CHARACTER SET utf8;
```

不指定的话，就相当于按数据库服务器上的默认字符集来设置。所以**数据库服务器这边的字符集也建议统一是 utf8**。

#### 最小权限与临时库、备份库命名

程序连接数据库所用的账号要遵循**权限最小原则**：能给小就小。权限给大了，它就可能做出超出自己范围的事。

> **易错点**：原则上**不允许账号拥有 `DROP` 权限**——别给它留下从删库到跑路的机会。

临时库和备份库的命名也有约定，临时库用 `tmp` 开头，备份库用 `bak` 开头，后面再以日期作为后缀——一个前缀定性、一个后缀定时，临时和备份对象就不会和正式库混在一起：

| 对象 | 前缀约定 | 后缀 | 对齐说明 |
| :--- | :--- | :--- | :--- |
| 临时库 | `tmp` | — | 见名知意，一眼看出是临时对象 |
| 备份库 | `bak` | 日期 | 用日期做后缀，便于按时间回溯 |
| 中间表／备份表 | 与库同理 | 日期 | 表这一层沿用同一套约定 |

### 表和列的编写规范

库里装的是表，表里装的是列，这一层规则最多。

#### 命名规范与前缀统一

表名和列名一律**小写**，用下划线区分单词，做到**见名知意**。与某个模块相关的表，统一使用同一个前缀，便于按模块归拢。表名和列名上**禁止使用关键字**——倒也不是说完全不能用，而是用上以后很麻烦，有时候会被识别错。

#### 建表显式指定字符集

创建表的时候建议显式指定字符集。数据库层面指明了，表这层不指明就跟着数据库走。但值得留意一个现象：**用可视化工具创建、再导出的建表语句，会把每一张表的字符集都带上**。既然工具这么干，我们手写建表时也建议加上。

```sql
CREATE TABLE tbl_name (
  -- 字段定义
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8
  COMMENT = '表的说明信息';
```

#### 存储引擎显式写 InnoDB

存储引擎这一项，MySQL 5.5 以后默认就是 InnoDB 了。默认存储引擎当然也能改，但自己造表的时候建议还是把 `InnoDB` 明确写出来。

#### COMMENT：建表必须写

建表必须带 `COMMENT`。它就是给字段做备注，说明这个字段到底表达什么意思。前面造表的例子里都没加，后续建表可以考虑都加上。

#### 字段命名的缩写与布尔前缀

字段命名有时候需要**必要的缩写**。比如公司的 ID，写成 `corporation_id` 太长，缩成 `corp_id` 就够了。

布尔类型的字段建议以 `is_` 开头，一眼就能认出它是布尔类型。

#### 禁止在表内存放大文件

不要在数据表里存储图片、文件这类**大二进制数据**。淘宝上有大量图片甚至视频，那是靠 FastDFS 这类**分布式文件系统**来承载的；我们这里同样尽量不放进现有表结构中。

> **结论**：图片、文件这种大二进制内容放在表里，加载的时候速度会非常慢。

#### 主键：类型、生成方式与业务字段的区别

主键**一定要有**。类型上一般是 `INT` 和 `BIGINT` 两种。上一章讲过淘宝的主键是怎么设计的，结论落到选型上就是：

- **核心表**：自己去手动创建主键，不依赖自增；
- **非核心表**：用 `AUTO_INCREMENT` 是可以的。因为它们都是正数，再加一个 `UNSIGNED` 无符号标识。

关于"每行的主体字段不要设为主键"这条，意思是这样的：员工表里的 `employee_id`、用户表里的 `user_id`、订单表里的 `order_id`，建议**别拿它们当主键 ID**。这些其实已经相当于业务字段了，我们另外给它一个 `id`。比如下面这张 `user_info` 表，`user_id` 是用户 ID，另外专门提供一个主键。

```sql
CREATE TABLE user_info (
  id       BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  user_id  VARCHAR(64)     NOT NULL                COMMENT '用户ID（业务字段）',
  PRIMARY KEY (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8;
```

> **提示**：这样分开的好处是，主键是**自增**的，新增数据时顺序追加在末尾，就不会出现**页分裂**。

#### 时间字段与 NOT NULL 约束

核心表建议增加两个字段：**创建时间**和**最后更新时间**。

表中的字段尽量都用 `NOT NULL`，必要的时候配合 `DEFAULT` 给一个默认值。原因有两条，都能回溯到前面讲过的内容：

1. 讲**行格式**的时候提到过，允许为 `NULL` 就会有一个 `NULL` 值的列表，需要**额外的空间**去存储这些 NULL 值；
2. 使用**聚合函数**计算的时候，`NULL` 值**不计算在内**，结果会有偏差。

> **易错点**：`AVG()`、`COUNT(列)` 这类聚合会把 NULL 行跳过，语义上可能并不是你要的结果——这也是尽量全字段 `NOT NULL` 的现实理由。

#### 关联列的类型与列名

不同表之间如果有外键关联，关联的**列类型一定要一致**；列名没有强制要求，但建议也写成一样的。

> **易错点**：类型不一致会让**索引失效**，这是前面讲索引时已经确认过的。

中间表、备份表的处理与库那一层同理。

### 可视化建表工具

造表推荐使用可视化工具。授课过程中用的就是 **SQLyog**，它本身就能建表——在界面里创建表、在里面写字段定义。另外 **Navicat** 也是一样的路子，就不逐个演示了。现在用 **DBeaver** 的人也很多，展示效果各方面都挺不错。

用可视化工具的好处有三点：

1. **不用自己手写**建表语句；
2. 约束之类的结构设置，**点界面上相应的按钮**就能加上，很方便；
3. 建好的表**可以导出成规范的 SQL 语句**。

> **提示**：这里不逐个工具演示。工具的选择不影响规范本身——规范是约束你怎么组织库、表、列和索引的，用哪把 GUI 只是让你少敲几条语句。

### 索引的编写规范

#### 主键与存储引擎的相关约定

- 索引这块首先提到的还是主键，**禁止主键被更新**。这一条对应着理解：让它自增就行了，非核心表尤其如此。
- 关于 InnoDB 和 MyISAM 使用的索引结构，有一种常见疑问：文档里写的是 B 树，怎么不是 B+ 树？

> **提示**：MySQL 官方文档里凡是写 `BTREE` 这种写法的地方，指的其实就是 **B+ 树**。真正的 B 树（B-tree）是另一种结构，官方那个写法就是 B+ 树。

- 索引命名上，主键以固定前缀开头，普通索引、唯一索引各有自己的前缀；多单词构成时按既定方式拼接，中间可以再加上表名。取缩写时要**兼顾可读性与见名知意**，比如 `member_id` 直接缩成 `mid` 就行，别整太长。

```text
  索引名的构成顺序（多单词场景）

  <前缀区分索引类型> _ <表名，可选> _ <列名缩写>

  前缀  →  一眼分清这是主键、普通索引还是唯一索引
  表名  →  多表混杂时快速定位属于哪张表
  缩写  →  保证可读性优先，别为了短而失去见名知意
```

#### 单表索引不超过 6 个，多用联合索引

**单张表上的索引个数不要超过 6 个。**

建索引的时候多考虑**联合索引**。以联合索引 `(a, b, c)` 为例，虽然只有这一个索引，但：

```text
  联合索引 (a, b, c) 的三种可用路径

  查询条件          能否用上该索引        命中的列
  ─────────────    ─────────────────    ──────────
  WHERE a = ?        能                  a
  WHERE a = ? AND b = ?   能             a, b
  WHERE a = ? AND b = ? AND c = ?  能    a, b, c
```

读图说明：一个联合索引覆盖了三种不同情况的过滤需求，用最左的列、用最左两列、三列全用，都能走上它。

这比给每种情况各建一个单列索引划算得多。而且从维护角度看：**索引维护得少，增删改时的性能就会高一点**。

至于列的顺序，把**区分度比较高的字段放在前面**，这一点前面已经讲过。

#### 被驱动表要有索引，避免冗余索引

多表 JOIN 的 SQL 语句中，**被驱动表上要有索引**。前面讲索引优化时提到过：被驱动表上有索引，执行计划里的 `type` 会更好，不会退化成 `ALL`。

建表时还要保证表之间**不存在冗余索引**。

### SQL 语句的编写规范

#### SELECT 与 INSERT

- `SELECT` 不要写 `*`。
- `INSERT` 时建议**在 key 后面明确指明要添加的字段**，不要省略字段列表。

> **易错点**：省略字段列表时，一旦对不上就会报错；更麻烦的是类型恰好对得上、个数也恰好对得上，但写入的值不是你真正想写的那个字段——查起来非常费劲，可读性也差。

#### WHERE 条件、批量写入与 UNION

除了清表或者小表以外，**DML 语句一定要有 `WHERE`**，而且尽量用上索引。

批量写入（`INSERT INTO ... VALUES`）建议**一次不要超过 5000 条**：条数多的时候写入速度确实很快，但会引起后面要讲的**主从复制（主从同步）延迟**问题。

`UNION` 和 `UNION ALL` 之间**推荐使用 `UNION ALL`**，因为它不需要去重。用 `UNION` 的话还会额外产生临时表，这在讲 `EXPLAIN` 的时候提到过。另外 `UNION` 的个数尽量控制在 5 个以内。

| 写法 | 去重行为 | 额外开销 | 使用建议 |
| :--- | :--- | :--- | :--- |
| `UNION` | 会去重 | 可能产生临时表 | 确需去重时才用 |
| `UNION ALL` | 不去重 | 无 | 推荐，个数控制在 5 个以内 |

#### JOIN、排序与结果集规模

线上环境中**多表 JOIN 不要超过 5 个**，超过 5 个性能还是会降低。

**减少使用 `ORDER BY`**——和业务沟通一下，能不排序就不排序，或者把排序放到程序端去做。主要原因是 `ORDER BY`、`GROUP BY`、`DISTINCT` 这三个关键字在操作过程中都比较耗费 **CPU** 资源。

当然，如果能用上几个索引会好一些，因为相同的值在索引里都是挨着的，排序的代价可以顺势降下来。

> **结论**：包含 `ORDER BY` / `GROUP BY` / `DISTINCT` 的语句，`WHERE` 过滤出来的结果**请保持在 1000 行以内**，否则 SQL 会比较慢。

#### ALTER 的合并、审核与执行时机

对单张表的多次 `ALTER` 操作**必须合并为一次**。对于**超过 100 万行的大表**做 `ALTER`，要经过 **DBA 审核**，同时必须在**业务低峰期**执行。

原因是 `ALTER` 表会产生**表锁**，会阻塞其他的写入操作。

### 事务的编写规范

事务是下一个篇章的内容，这里只先给出几条编写层面的约束。

- 事务之间处理时，中间可以加一个 `sleep`；
- **事务里的 SQL 最好不超过 5 个**。较长的事务会导致锁数据的时间比较久，还会带来内部缓存、连接消耗等问题；
- 事务里的更新语句**尽量基于主键或者唯一键**（unique key）。

> **易错点**：更新不基于主键或唯一键，就可能产生**间隙锁**（gap lock），锁的范围会扩大，性能随之下降，还会引发**死锁**。这是事务类问题里最常见的一类成因。

到这里，编写 SQL 过程中的规范就捋完了。这些规范都是**经验之谈**，不用死记硬背，听完一遍大致就能记得差不多，剩下的是写的时候照着去遵循。

## 158-PowerDesigner创建概念、物理数据模型
> 对应分集：P158 | 原始标题：《158-PowerDesigner创建概念、物理数据模型》

前面我们把 ER 模型讲完了，接下来一个很实际的问题就摆在面前：在实际开发当中，到底我们用什么软件去帮我们生成这个 ER 模型呢？我们要讲的 PowerDesigner 就属于其中的一个工具。相较来讲，开发人员用它的还是比较多的，也是比较熟悉的一个工具，所以这里就拿它来讲解。实际当中你们也可以用其他工具——我这儿就还装了一个比较轻巧、比较小巧的工具，也能干这件事。而 PowerDesigner 相对来说工具大一些，工具大，具备的功能就多一些：比如制作数据流程图、概念数据模型、物理数据模型，包括数据库建模设计的全过程，这个软件都能搞定。它是 Sybase 公司开发的这样一套完整的解决方案。

这一讲我们主要讲两件事：如何创建概念数据模型（Conceptual Data Model，CDM）和物理数据模型（Physical Data Model，PDM），以及它们二者之间该如何进行转换。

### 工具准备与新建入口

这里用的是 PowerDesigner 16.5 这个版本。下载安装的过程我就省略了，大家直接在网上搜一下就能找到。

把软件启动起来，它有一个欢迎界面。欢迎界面当中其实已经给我们呈现出来可以去创建一些相关的结构了，你把这个提示的勾打上，然后 close 掉就 OK。

接下来选左上角的 File，它下面既可以创建 New 一个 Model，也可以创建 New 一个 Project，还可以 Open：

- New → Model：相当于直接创建一个新的文件；
- New → Project：相当于创建了一个文件夹，然后在这个文件夹里面你再创建具体的文件，区别就在这；
- Open：打开一个你已经创建好的 Model。

> **提示**：先想清楚这份模型是要单独交付，还是要成组管理，再决定从 Model 还是 Project 进去——文件与文件夹的区别就落在这里。

我们这里就直接 New 一个 Model。点完以后，界面上就出现了我们到底能够创建哪些类型的模型：常见的有业务模型、概念数据模型、面向对象模型，以及物理数据模型。

这一讲只讲其中两个。开发当中我们用得比较多的都是物理数据模型，而概念数据模型又属于比较基本的一个，所以顺序是先把概念数据模型讲清楚，再讲物理数据模型，最后讲它们二者之间如何相互转换。

### 概念数据模型的创建

选到概念数据模型，接着要起个名字——中文名字是可以的，我们就写一个「概念数据模型-1」，点 OK。生成以后，下面会有一个 Diagram-1，我们就在它上面开始画。

画之前先对一下 ER 模型的几个要素：E 就是 Entity，实体；实体跟实体之间有 relationship，也就是关系；实体里边再放具体的属性（attribute）。概念数据模型要落下来的，就是这三样东西：

```text
   Entity (实体)                          Entity (实体)
   ┌────────────────┐   Relationship     ┌────────────────┐
   │ class          │◄──────────────────►│ student        │
   └───────┬────────┘                    └───────┬────────┘
           │ Attribute                           │ Attribute
   ┌───────┴────────┐                    ┌───────┴────────┐
   │ class_id       │                    │ student_id     │
   │ class_name     │                    │ student_name   │
   └────────────────┘                    └────────────────┘
```

读这张图：左右两个方框是实体，中间那条线上写的是关系，每个实体下面挂出来的就是它自己的属性。

#### 实体的绘制与删除

右边工具栏里我们主要用的就是 Entity 这个框。点一下它，再在左边空白的地方点一下，它就帮我们生成了一个实体；再点一下，是不是又生一个？再点，就又生一个。

> **易错点**：画完一个实体之后，光标还停在 Entity 工具上，继续在空白处点就会不停地冒出新实体。这时候在空白处点一下鼠标右键，就恢复成箭头状态，不再继续生成了。

多余的实体，右键 → Edit → Delete 删掉就可以。

#### General 页：Name、Code 与 Comment

双击实体进入编辑，第一个选项卡叫 General，做的是这个实体在常规层面上的整体设计。

Name 这里我们写 student。前面讲表名规范的时候说过，创建表名用小写，这里就照着这个约定来。你会发现，Name 里一写，下面这一行的 Code 也同步把 student 写上了。这两个到底有什么区别？

> **结论**：Code 才是真正代码层面上的支撑，Name 只是方便我们查看。

所以对我们来说，最顺手的写法是：Name 写中文「学生表」，Code 写英文 student；你本身要是英语体系的，两个写成一样的也 OK。

再往下的 Comment 是对这张表的一个说明，可以写成「学生信息表」这样的内容。

#### Attributes 页：属性、数据类型与列属性

点一下 Attributes，就在这个位置去创建属性的信息。这里的 Name 和 Code 跟上面是同一个道理：Name 可以写中文，Code 必须写英文。

> **易错点**：字段的 Code 一定要用英文。概念数据模型里你用中文 Name 看着舒服，但 Code 是将来生成 SQL 的依据，Code 写成中文是要出问题的。

字段一行一行往下填：你是横着先把这一条都设计完再写下一条，还是像这样做完一列再做下一列，都可以，看个人习惯。

Data Type 是设置类型的地方：可以拉开下拉框去找，也可以点旁边那个带小点点的按钮，换一种方式查看可选类型。学号就选 Integer。

后面的几列要分清楚：

| 列 | 名称 | 含义 |
| --- | --- | --- |
| Data Type | 数据类型 | 该属性映射到数据库里的具体类型 |
| Precision | 精度 | 浮点类型这类需要指定精度的类型才会用到 |
| M | Mandatory | 是否强制，也就是这个字段是否非空 |
| P | Primary | 是否作为主键 |
| D | Displayed | 该字段在图上是否显示，默认全都是显示状态 |

学号这一项可以设成主键，把 P 勾上。勾完你会发现它自动也变成非空了。

> **结论**：主键天然非空，勾上 P 之后 M 会跟着成立，不用再单独去点一次。

学生姓名用字符串来表示，也就是 VARCHAR。注意 VARCHAR 必须指明长度，不指长度就点 OK，它会报错——这跟我们前面讲数据类型那一节的要求是一致的。长度填上，再 OK 就过去了。姓名这一项也是非空的，把 M 加上。

学生的年龄还是用 Integer；性别就是男和女，用 CHAR，长度选 1；学校用字符串，长度给 20。学校这一项就不打非空的勾了。

#### 学生表与班级表的完整字段

Attributes 后面还有一个 Identifiers，一看名字就知道是设置标识符的地方：如果我们不希望系统自动帮我们生成标识符，也可以在这个位置手动设置。这一讲我们不去动它，直接点 OK，再点一下应用，最后确定，表就创建好了。

> **提示**：图上的表如果看着小，可以按住 Ctrl 键滚动鼠标滚轮，它就变大了。

这时候你会注意到一件事：表里面帮我们显示出来的这些字段，全是中文的——也就是说，图上呈现的是我们设置时填的 Name，Code 并没有显示出来。但它的底层支撑就是这个英文 Code，将来需要转化成 SQL 输出的时候，用的全都是 Code 那个字段。

> **结论**：图上展示的是给人看的 Name，落到数据库里的是给机器用的 Code，两套名字各司其职。

同样的道理，再把班级表创建出来。点一下 Entity 工具，在空白处点一下，再点一下鼠标右键把工具恢复成箭头，然后双击进去：Name 写「班级表」，Code 直接写英文 class；Comment 需要就加上。

班级表的属性这样设计：

| 实体 (Code) | 属性 (Name) | 属性 (Code) | 数据类型 | 其他 |
| --- | --- | --- | --- | --- |
| student | 学号 | student_id | Integer | 主键，勾上 P 后自动非空 |
| student | 学生姓名 | student_name | VARCHAR（必须指明长度） | 非空 |
| student | 学生年龄 | student_age | Integer | — |
| student | 学生性别 | student_gender | CHAR(1) | — |
| student | 学校 | student_school | VARCHAR(20) | — |
| class | 班级编号 | class_id | Integer | 主键 |
| class | 班级名称 | class_name | VARCHAR(10) | — |
| class | 班级人数 | class_count | Integer | — |
| class | 班级介绍 | class_intro | VARCHAR(30) | — |

班级表这些字段的 Code 同样必须用英文，写完点应用、点确定，两个实体就有了。

#### 一对多关系与方向校正

实体建好了，下面要考虑的就是这两个实体之间的 relationship，也就是关系。

工具栏里有一个 Relationship 选项，点一下它，然后把这两个实体连起来。学生表和班级表应该是一对多的关系：一个班级有多个学生，而一个学生应该在一个班级里边。

连上以后你会发现，两个实体之间出现了一个像三股分叉一样的标志，这就体现了一对多的关系；中间还有一个 Relationship-1，双击它可以对这段关系再做刻画。

- Name 写「班级和学生的关系」；
- Code 为了可读性，用英文写成 class 和 student 的 relationship；
- 下面还可以写具体描述：一个班级对应多个学生，一个学生对应一个班级。

真正决定这段关系类型的，是它第二个选项卡里的选项：它们二者之间是一对一、一对多、多对一，还是多对多，都在这里选。

> **易错点**：刚才用 Relationship 工具连线的时候如果只是随便勾了一下，很容易选成「学生对于班级是一对多」，方向就反了。反了不要紧，不用删掉重画，在这个选项卡里改成正确的关系，点一下应用，方向就掉过来了。

这个选项卡里还能看出当前这两张表分别是哪张——这里显示的是班级表和学生表；如果你想换，也可以在这里交换它们俩的位置。设置好点确定，图上就是一个班级对应多个学生的关系。

#### 教师表与字段 Code 的命名区分

接下来我们再体现一下多对多的关系。还是点 Entity 工具，在空白处单击、点右键，然后双击进来：Name 写「教师表」，Code 写 teacher，Comment 写成教师信息表。

教师表的属性和学生表类似：教师编号、教师姓名、教师年龄、教师性别（所在学院这类字段就不一一加了）。类型上，编号用整型并设为主键，姓名用 VARCHAR、长度 15，年龄用 Integer，性别用 CHAR 并指定一个长度；年龄要非空就把 M 勾上。写完应用、确定，教师表就出来了。

这里有一个小细节要提前说清楚：教师表里有姓名、年龄、性别，刚才学生表里也有姓名、年龄、性别。在写这两个实体的 Code 时，建议把它们的值区分开：教师这边叫 teacher_name、teacher_age、teacher_gender，学生那边叫 student_name、student_age、student_gender。

要是图省事，两边都写成 name、age、gender，把前面的前缀去掉，会怎么样？在概念数据模型里面是没问题的；但当你把这个概念数据模型转化成物理数据模型、而这两个实体之间又已经建立了联系时，它就会认为这几个字段是相关联的，名字一样的话，转换的时候直接报错。

> **易错点**：每个实体里的字段名建议做区分。虽然都是姓名，但一个叫 teacher_name，一个叫 student_name，这样就拆开了。这条规律在建模阶段不显山不露水，一直要到转换那一刻才会以报错的形式提醒你。

#### 多对多关系与模型保存

现在给教师表和学生表之间设一个多对多的关系。在概念数据模型里，这个关系是直接在图上搭起来的：不像真实数据库里那样，多对多必须用一个独立的中间表去体现——这里我们直接把两个实体连起来就行。

连完点右键、双击，给这段关系起个名字，比如「学生与教师的多对多关系」，Code 写成 student 和 teacher 的 relationship，描述写「一个学生对应多个老师，一个老师对应多个学生」。然后在第二个选项卡里选 Many-to-Many，指明它是多对多的关系，点确定。

这时候图上学生和教师之间的连线是分叉的，这就是多对多的意思。至此，概念数据模型里这一个一对多关系和一个多对多关系就都搭好了。

接下来保存：保存到你想保存的位置上就行，文件名可以起成「学生管理系统」这样的名字。

### 物理数据模型的创建

概念数据模型讲完了，接下来看物理数据模型怎么创建。点一下新建，在模型类型里选物理数据模型，先给模型起个名字，比如「物理数据模型-1」。

接下来你会发现，在物理数据模型里一定要指明一下数据库管理系统（Database Management System，DBMS）。道理很直白：物理数据模型嘛，你得告诉我你到底对接的是哪一个数据库。

> **提示**：这里用的 PD 版本稍微靠前一些，版本下拉框里只给我们呈现到 MySQL 5.0，那就选 MySQL 5.0，点 OK。

物理数据模型里我们主要用的就是三个选项：

- Table：创建表；
- View：创建视图；
- Relationship：设置表与表之间的关系。

#### 学生表的列定义与 P、F、M 约束

点一下 Table，再到左边点一下，就生成一张表；点鼠标右键能把它清掉，双击就进去编辑。这里的操作和概念数据模型是类似的。

Name 写「学生表」，Code 仍然用英文 student，Comment 需要就加。往下的 Columns 就是具体的列了——在真实的表里，一个字段就是一列。

学生的字段我们少写几个：学号、学生姓名、学生的年龄。Code 分别写成 student_id、student_name（简写成 stu 开头也行）、student_age，然后逐个设置类型：student_id 选 Integer。

列后面那一排约束，含义要分清楚：

| 列 | 名称 | 含义 |
| --- | --- | --- |
| P | Primary Key | 主键 |
| F | Foreign Key | 外键，现在还没有别的表可关联，所以它是不可选的状态 |
| M | Mandatory | 非空 |

学号的 P 勾上，勾完之后后面那个非空也就自动跟着成立了。姓名设置成 VARCHAR，长度 15；年龄用 Integer。

> **易错点**：姓名要设非空时，一定要勾在 M 那一列上。要是勾到了 P 那一列，等于把这个字段也拉进了主键，这张表就变成联合主键了——P、F、M 三列挨在一起，最容易看串行。

表格后面还可以去设置具体的索引，这里就不举例子了。点确定，这张表就建好了；按住 Ctrl 滚动滚轮，把它稍微放大一些看。

#### 班级表与一对多关系的外键

再建一张表：点一下 Table 工具，在空白处点一下，点右键恢复箭头，双击进去。Name 写「班级表」，Code 写 class，描述可以加一下。

Columns 里填班级编号、班级名称、班级人数、班级介绍，Code 分别是 class_id、class_name、class_count、class_intro。类型上：编号用 Integer 并设为主键，名称用 VARCHAR、长度 15，人数用 Integer，介绍用 VARCHAR、长度 30（想长一点也行）。有非空要求的就顺手勾上 M。应用、确定，第二张表也设计好了。

接下来考虑这两张表之间的关系，它是一个一对多：一个班级对应着多个学生。点一下 Relationship 按钮，把两张表连起来。这里要注意连线的方式——在物理数据模型里，一对多要这样去指：

> **提示**：连线时箭头指向的那一端，就是一对多里的「一」。班级表在「一」这一端，学生表在「多」这一端，所以是班级指向学生。

生成以后你会看到，学生表里边多出来一个班级编号字段，类型是 int。这就是把班级表的主键作为学生表的外键字段，自动补进来的。

双击这段关系也可以编辑：Name 写「学生与班级的关系」，Code 改成和学生表、班级表配套的写法，比如 student_class_R；描述里写明一个学生对应一个班级、一个班级对应多个学生。其他没什么可设的，应用、确定就行。

#### 主键自增的设置

物理数据模型相较概念数据模型有一个小区别值得单独说一下：我们在列里明明设了主键，却好像没看到哪里能设自增。

其实是可以的。做法是：选中这张表，双击进去，找到 student_id 这一行，把它对应的自增选项打上勾，确定就行。班级表里的班级编号也一样，双击进去把这个勾打上。这样两张表的主键就都是自增的了。

> **提示**：改完一处先点一下应用，让表结构的修改落实下来，再双击列进属性去勾自增，顺序上会稳妥一些。

> **结论**：这里勾上的自增，到了生成 SQL 脚本的时候，就体现为建表语句里的 `auto_increment`。

另外你会发现，物理数据模型里关系设置完之后，图上并没有像概念数据模型那样显示出关系的描述信息，这一点稍微注意一下。

#### 教师表与多对多的中间表

再建一张教师表：双击进来，Name 写「教师表」，Code 写 teacher，描述这次就不写了。字段写教师编号、教师姓名、教师年龄这三个：teacher_id 用 Integer 并设为主键，teacher_name 用 VARCHAR、长度 15，teacher_age 用 Integer，需要非空就把 M 加上。教师编号也要自增，照前面的做法勾上。确定之后教师表就出来了。

教师表和学生表之间的关系是多对多的：一个学生对应多个老师，一个老师对应多个学生。真实的数据表里我们已经讲过，ER 模型里也提到过，这种多对多的关系一定要借助一张中间表来体现，所以这里需要再建一张中间表，让教师表和学生表分别跟它建立联系。

再点一下 Table 工具造一张表，Name 写「学生与教师的关系表」，Code 用 student、teacher、relationship 拼起来，比如 student_teacher_relationship。

这张表里先写一个字段：学生和教师的关系编号，Code 写成 student_teacher_id，类型用 Integer，主键，并勾上自增。

> **提示**：有同学会问，既然是描述多对多关系的表，里面不应该把学生和教师各自的主键也加上吗？不用手动加——一会儿把外键的关联建起来，它们会自动补进这张表。

接下来刻画这三者之间的关系。点一下 Relationship 按钮：一个学生在这张关系表里可能会有多条记录，所以学生这一端是 1、关系表那一端是多；教师这边同理，教师是 1、关系表是多。两头都连上之后，关系表里自然而然就有了学生的学号、教师的编号。这些关系也可以双击进去再细调。

物理数据模型里这一组表的结构长这样：

```text
   ┌────────────────┐  1        n     ┌────────────────┐
   │ class          │────────────────►│ student        │
   │ PK class_id    │                 │ PK student_id  │
   └────────────────┘                 │ FK class_id    │
                                      └───────┬────────┘
                                              │ 1
                                              ▼ n
                         ┌────────────────────────────────────┐
                         │ student_teacher_relationship       │
                         │ PK student_teacher_id IDENTITY     │
                         │ FK student_id                      │
                         │ FK teacher_id                      │
                         └───────────────▲────────────────────┘
                                         │ n
                                         │
                                         │ 1
   ┌────────────────┐                    │
   │ teacher        │────────────────────┘
   │ PK teacher_id  │
   └────────────────┘
```

读这张图：班级表和学生表之间是一对多，外键 `class_id` 落在学生表上；学生表和教师表之间的多对多，靠中间的 `student_teacher_relationship` 拆成两个一对多——学生、教师各自在「一」这一端，中间表在「多」这一端。

到这里，几张表和它们之间的关系就都建好了，同样可以做一次保存，比如还是存成「学生管理系统」。

> **结论**：看文件后缀就能分辨模型类型——c 开头的是概念数据模型，p 开头的是物理数据模型。

### 概念数据模型与物理数据模型的相互转换

两个模型都建起来之后，下面把转换讲清楚。转换之前，先看一眼它们在建模层面的差别：

| 对比项 | 概念数据模型（CDM） | 物理数据模型（PDM） |
| --- | --- | --- |
| 面向的对象 | 业务概念，不绑定具体数据库 | 具体数据库，创建时必须指定 DBMS |
| 主要工具 | Entity、Relationship | Table、View、Relationship |
| 字段所在页 | Attributes（属性） | Columns（列） |
| 多对多关系 | 两个实体直接连线，选 Many-to-Many | 必须借助一张独立的中间表 |
| 主键自增 | 不涉及 | 列属性里勾选自增，生成 SQL 时为 `auto_increment` |
| 关系描述文字 | 会显示在图上 | 不显示在图上 |

#### 概念数据模型转换为物理数据模型

选中我们的概念数据模型，打开 Tools 菜单，下面有一个转换的选项，转换的目标就是物理数据模型，点一下它。

弹出来的对话框里可以起个名字，比如「概念转物理模型-1」；因为你要转成的是物理数据模型，所以要先指明转成哪一个数据库。别的没什么选项了，直接点确定，转换就做完了。

这里再着重说一下字段 Code 命名的事：一开始创建概念数据模型时我就提过——学生表和教师表里都有姓名、年龄、性别，那时候给字段 Code 命名就不要再把老师那边的 Code 跟学生那边起成一样的，比如都叫 name、age、gender，把前面那个前缀都去掉。如果当时是那样命名的，这一步转换就会报错。

要核查也很方便，在概念数据模型里的 Data Item 位置就能看：学生姓名和教师姓名这两个的命名是不一样的。名字要是起成一样的，转换的时候就等着看错误信息吧。

转换还有一个结果值得注意：中间自动帮我们多生成了一张表。因为物理数据模型里刻画多对多关系，本来就得多要一张表；而且这张表是拿学生的学号和教师的编号共同构成了一个联合主键。

> **提示**：如果你更希望这张中间表有自己的主键，可以在这个基础上改造一下：给它真正意义上加一个主键，把学号和教师编号降成两个普通字段，再分别跟那两张表的主键做关联。

#### 物理数据模型转换为概念数据模型

反过来转也行。打开物理数据模型的 Tools 菜单，里面有一个生成概念数据模型的选项，点一下它。弹窗里可以起个名字，比如「物理转概念模型」，然后点应用，转换就成功了。

转出来的结果可以看一下：概念模型里会自动用相应的符号把表表达出来；因为我们物理模型里有四个表，所以概念模型里表达出来还是这四个表。在这个基础上，你可以继续做具体的编辑。

### SQL 脚本的生成与导入

物理数据模型还有一个很实用的用途：因为它本身就是针对 MySQL 的，我们可以把这个 ER 模型转换成具体的 SQL 语句，然后拿到相应的工具里导入执行，直接生成真正数据库当中的表。

```text
   ┌──────────────────────┐
   │  Conceptual Model    │  CDM，概念数据模型，不绑定具体数据库
   └──────────┬───────────┘
              │ Tools ▸ Generate Physical Data Model（需指定 DBMS）
              ▼
   ┌──────────────────────┐
   │  Physical Model      │  PDM，物理数据模型；多对多会自动补一张中间表
   └──────────┬───────────┘
              │ Database ▸ Generate Database
              ▼
   ┌──────────────────────┐
   │  SQL Script (.sql)   │  在 SQLyog 里导入执行，生成真实的表
   └──────────────────────┘
```

这张图是整条链路：概念模型往下走一步是物理模型，物理模型再往下走一步就是可以直接执行的 SQL 脚本。反向那条路（物理模型生成概念数据模型）走的是同一个 Tools 菜单。

#### Generate Database 生成 SQL 脚本

在物理数据模型里找到 Database 菜单，里面有一个 Generate Database，点击它。

第一步是选择文件保存的位置，这里也可以自己挑，比如改到桌面上——桌面上这会儿没给我呈现我们的课件，那就直接放桌面上得了，确定一下。

接着是转换出去的内容：这几个表对应的是一个 SQL 文件，文件可以自己命名，比如就叫 students。下面还有一个 Selection，也就是选择的意思：转换出去的时候是要把所有表都转出去吗？我们把四个表都打上勾，点确定，文件就生成好了。把窗口 close 掉、收起来，桌面上就出现了具体的 SQL 文件。

把它打开简单看一看，其实也能看得懂，它基本上是这么几段：

- 先把这几个表删掉——你要是库里已经存在同名表，先删掉，确保下面这个创建能够成功；
- 然后建表，表中字段、字段类型，包括 `auto_increment` 这些，里面都有；
- 最后是添加相关的外键约束。

> **提示**：项目里涉及的结构一旦复杂起来，就让这套流程自动帮我们去生成，虽然生成出来的脚本结构也会复杂一些，但比手写稳妥得多。

#### 在 SQLyog 中导入并刷新

回到 SQLyog 这个层面，就可以导入执行了。

这里有一个前提：刚生成的 SQL 文件里并没有指明数据库。所以导入之前，你需要先选中一个具体的数据库，而且这个数据库最好一开始是空的。

> **易错点**：为什么强调用空库？因为脚本开头会先删表，如果你库里本来就有同名的表，导入时会被删掉。我这次是看过库里没有重名的表，才没有专门去用一个空库。

导入的步骤是：选中数据库，点一下导入，找到桌面上的那个文件，点打开，再点执行，然后点完成，最后按 F5 刷新一下。稍等一下，这几张表就来了，包括 class 也在。

## 159-数据库调优整体步骤、优化MySQL服务器硬件和参数
> 对应分集：P159 | 原始标题：《159-数据库调优整体步骤、优化MySQL服务器硬件和参数》

索引和数据库调优这一大块，走到这里就进最后一个小章节了：数据库调优的其他策略。表设计上的东西我们讲过——范式、ER 模型；SQL 的优化、查询的优化、索引的优化，也都讲过了。那除此之外，还有哪些位置是可以动手调的？这一章整体补一补。它同时也算是一章统领性的内容：把调优这件事从宏观上重新梳理一遍、总结一遍，前面欠的，在这里加上。

那就先把一件事说清楚：调优的目标到底是什么？

### 调优目标：吞吐量与响应速度

简单讲就两个方向。

第一个方向是**吞吐量更大**。做法是节省系统的资源——资源省下来了，系统就能容纳更多的服务，单位时间处理掉的请求量自然就上去了。

第二个方向是**响应速度更快**。做法是合理的结构设计，加上合理的参数调整，把单个请求的返回时间压下来。

这两个方向之外，还有一条常被一起提到的：**减少系统的瓶颈，提高 MySQL 数据库整体的性能**。这就要靠调参数，靠增加服务器的硬件配置，把整个 MySQL 服务器的性能抬起来。

> **结论**：调优不是"让 SQL 跑得快一点"这一件事。它有两个明确的方向——单位时间能扛下多少请求（吞吐量），以及单个请求多久返回（响应速度）；而"减少瓶颈"是通往这两个方向的手段，不是一个并列的第三个目标。

### 调优问题的定位途径

现在很难用"更快"这样一个词去定义数据库调优的目标。为什么？因为实际场景太复杂了：在双十一、618 这种活动里，我们更多要关注的是大规模并发访问带来的访问延迟问题；而在另一些业务里，用户面对的是事务处理、SQL 查询这些东西，业务不同，遇到的问题也不一样。

所以要精准地定位问题，先得明确：从哪些方向上去找问题。你要调优，第一步就是发现你的问题在哪。

**用户的反馈**——这是最直接的一条路。用户是我们要服务的对象，他们直接反馈遇到的问题，通常不会造假，而且这个问题本身就最直接。用户提不出技术层面的建议，但他对问题场景的描述是比较真切的。这是我们最看重的一个方向之一。

**日志分析**——去查看数据库日志、操作系统的日志等等，从日志里找到异常问题出现在哪儿，然后再有针对性地去调优。

**监控工具**——服务器层面的监控，比如 CPU、内存、I/O 使用情况的工具；数据库内部状况的监控，针对活动会话的监控；还有事务、锁等待这一类行为的监控。

> **提示**：上面这几类监控属于辅助手段。真正发现问题，主要还是靠用户反馈和日志分析这两条路。

### 调优的六个步骤

具体的调优措施我们前面已经讲了不少，索引上的调优、SQL 语句上的调优，都属于这一类。现在要把高度拉起来：从宏观上讲，整个调优遵循什么样的步骤？

先把这条路线摆出来，后面再逐条说。

```text
第一步  选择合适的数据库管理系统 ── 选了开源 MySQL 还要指明存储引擎
   │
第二步  优化表结构设计 ── 范式 / 反范式化 / 字段数据类型选择
   │
第三步  逻辑查询优化 ── 对 SQL 做重写
   │
第四步  物理查询优化 ── 正确使用索引
   │
第五步  业务层缓存 ── Redis / Memcached 作为缓存出现
   │
第六步  库级优化 ── 主从复制、读写分离、分库分表
```

这张图是从上到下逐层往下压的关系：越靠前的步骤越靠近"定方案"，越靠后的步骤越靠近"扛并发"。

#### 数据库管理系统的选择

第一步是选择一个合适的数据库管理系统（Database Management System，DBMS）。为什么要先定这个？因为你说调优、说要针对表做优化，得先看这个表到底放在哪一个数据库管理系统当中——不同的数据库管理系统，调优这件事本身还是有区别的。

如果对事务性的处理和安全性的要求比较高，推荐你去选商用的数据库，也就是需要花钱的那一类，比如 SQL Server、Oracle 等等。像单表存储上亿条数据，对它们是没有任何问题的。当然，这并不是说 MySQL 存不了上亿条数据，只不过存了上亿条数据以后，它在优化等方面可能不如 Oracle。

如果选的是开源的 MySQL 来存储，那么在存表的时候你还要指明具体用的是什么样的存储引擎。因为像 InnoDB，它是支持事务的、支持行锁的、支持外键的，这跟我们用 MyISAM 是有区别的。

再往后，还可以去选择 NoSQL 型的数据库。上篇第一章里提到过：键值型的、文档型的、搜索引擎型的、列式存储、图形数据库等等，具体有哪些、各自怎么用，那里已经展开讲过了，这里不再重复。总之是根据适合的场景，去选最适合的那个数据库管理系统。

> **结论**：这一步是整个设计的第一步。没有这一步，后面的优化其实都谈不上。

#### 表结构设计与数据类型优化

第二个环节是优化表的设计。这实际上是上一章的重点。

一般情况下，要求表结构在设计的时候遵循第三范式（Third Normal Form，3NF），或者说再好一点，遵循巴斯范式（Boyce-Codd Normal Form，BCNF）。第四范式、第五范式一般就不考虑了。

> **易错点**：面试的时候一般没有人会问你第四范式和第五范式。真被问到了，直接回答"我不是很清楚"就完事了——这本身是个比较无聊的问题。

接下来是反范式化。反范式化相当于在表当中加入一些冗余字段，拿空间去换时间，提高查询效率，主要是为了避开多表查询。

再往下，是表字段的数据类型选择。这个在上篇数据类型精讲的时候，讲完具体的数据类型之后已经做过一次总结，从优化的角度提了提我们到底该选哪些常见类型。这里相当于再从优化的角度讲一讲这个问题。

表结构的设计是在数据库管理系统选好之后进行的，它算是比较重要的一项，尤其是当表里数据量比较大的时候——你想，数据类型要是选得不合适，占用的存储空间可能就会大不少。

#### 逻辑查询优化与 SQL 重写

再往下是优化整个逻辑查询。前面提过，查询可以分成逻辑查询的优化和物理查询的优化两种。

逻辑查询优化，主要指的是对 SQL 进行重写。比如原来是子查询的写法，优化以后改写成多表查询的方式；再比如等价谓词重写、视图的重写、条件的简化、连接的消除、嵌套连接的消除等等。这些措施的目的都是一个：把这条 SQL 重写掉。

这件事有点像写算法题——好的算法和不好的算法，作用是一样的，但性能差别很大。逻辑查询优化就类似于算法层面的优化。

前面讲 `exists` 和 `in` 的时候，我们提到过小表驱动大表这个问题，属于同一类考虑。

还有一个例子是语法层面的：同样一个 `where` 条件，一种写法里面出现了函数，就很显然用不上索引；换成另一种写法，把函数从字段上挪开，索引就能用上。这就是语法上的优化。

#### 物理查询优化与索引的正确使用

再下一步是物理查询的优化，这个优化主要就是正确地使用索引。

这一部分是我们需要掌握的一个重点。前面花了挺多篇幅，其实一直都在讲索引的正确使用，所以细节这里就不啰嗦了。

#### 缓存层：Redis 与 Memcached

第五个步骤是从业务层面考虑：我们可以引入 Redis 或者 Memcached 作为缓存来使用。如果实际开发中做过相关业务，这两个东西多少都应该用过。

比如在电商项目里，购物车就可以考虑用 Redis 加分布式集合的方式来实现；商品详情页也可以用 Redis 做缓存。

Redis 和 Memcached 的区别在哪？

| 对比项 | Redis | Memcached |
| --- | --- | --- |
| 持久化 | 支持，数据既可以放在硬盘上，也可以放在内存层面 | 不支持，只能放在内存层面 |
| 数据类型 | 除 key-value 之外，还支持 list、set、hash 等数据结构 | 只支持 key-value 类型 |

对这些区别，一句话概括选型：对响应速度要求比较高的场景，就要考虑内存级别的数据库了。

#### 库级优化：主从复制、读写分离与数据分片

最后是库级的优化。单机上的 SQL 优化、表的设计已经做到极限了，高并发的场景过来以后怎么办？这时候就从库级入手。

一个库搞不定了，可以考虑用多个服务器，也就是主从架构。这里面首先是读写分离：先做主从复制，主机负责写请求，从机负责读请求，主机上通过相应的 binlog 日志同步给 slave 从机。实现了主从复制之后，读写也就实现了分离，相当于把主机的压力分散出去了。

```text
   写请求 ──▶ 主库 master ──（binlog 日志同步）──▶ 从库 slave ◀── 读请求
                 负责写                              负责读
```

再进一步，还可以开启双主双从的模式——万一主机挂掉了怎么办？这时候还有一个备机顶上。数据库架构这块后面会专门展开来讲，这里先做个泛泛的讲解。

除了主从，还有一种方式是数据分片。如果数据库里的表特别多，我们还可以做分库分表：有些库、有些表放在这台主机上，另外一些放在另一台主机上。划分的时候最好按照功能模块来分——这样访问不同的功能模块就用不同的主机，主机的压力就被分散开了。

针对单张表，如果数据量达到千万级别，还可以对表做拆分，这里面有垂直分表和水平分表之分。

- **垂直分表**：可以把数据分成热数据和冷数据。常用的叫热数据分到一块，不常用的叫冷数据放到另外一个表当中。这也能提升查询和加载数据的速度，同时节省内存空间。
- **水平分表**：可以按取模的方式、按范围约定的方式、按日期的形式来做水平分表。

> **易错点**：分完之后不能都放在同一台主机上。你放在一台主机上就没有意义了——这台主机的压力还是很大。一定要分散到不同的主机上，才叫真正分散了主机的压力。

整体上讲，优化的步骤和策略就是刚才说的这 1 到 6 步，大家应该有一个宏观上的认识。其中 2、3、4 这三步前面都提到了；接下来要讲的，是这几个步骤之外、还没有讲到的那部分优化。

### MySQL 服务器硬件优化

MySQL 服务器的优化，实际上对应着调优步骤里的第一步。关于服务器优化，我们从两个方面来讲：第一是对硬件进行优化，第二是对 MySQL 服务的参数进行优化。

先说一件前几天的例子。雷军刚发布小米 12，在发布之前他就说了：小米 12 是全球最先使用高通最先进 CPU 的，也就是"首发"。结果这话刚说完，moto 就抢先了，moto 先发、先用了这颗 CPU。这时候"首发"就没办法讲了——相当于你没办法再凸显第一个优势了。那怎么办？就凸显第二个优势：说小米 12 是对高通这颗最先进的 CPU 最先进行调教的，调教得最好。主要就是想突出第二个特征。

这个例子对应到我们这里：硬件的优化也好，服务参数的调整也好，都需要专业的数据管理员才能做得对。如果你只是看到这里列的几个参数、知道它们的功能，却没有相应的经验在里边，那就不要随意地去调优。

> **提示**：知道参数的功能和会调参数，是两件事。没有经验的情况下乱调服务器参数，性能反而会更差。

#### 内存容量与磁盘系统

服务器的硬件性能直接决定了 MySQL 数据库服务器的性能，这一点毫无疑问。我们讲"巧妇难为无米之炊"——你再会做饭，食材不足、食材不够，那也很难做出一道丰盛美味的菜来。

再换句话说：一个是富二代家的家庭，一个是特别普通的工薪家庭，家底就不一样，对应的就是我们硬件水平不一样。那我们追求的是什么？是生活质量。家里有钱，生活质量就一定高吗？其实也不一定；但至少有钱的话，生活质量是有可能更高的。普通工薪家庭就得精打细算——该买的买、不该买的不买——才能让生活质量更高一些。

硬件对服务器就是这个关系。当然，硬件之上，服务器的参数你要是给它一顿乱配，性能也会差一些。所以硬件相当于那个"底"。

硬件层面的优化，从几个维度来做。

**配置较大的内存**。这一说大家都应该明白：内存大，我们能设置的系统缓冲区容量就会更大；缓冲区容量大了，数据在内存中停留的时间就更长，于是磁盘 I/O 就减少了。这就明显地提升了数据查询的性能。

**配置高速的磁盘系统**。这里说的是磁盘使用的格式。对服务器来讲，常见的一种格式是 SCSI，这种格式支持 7200 转每分钟。一旦网站的 PV（Page View，页面浏览量）上到 150 万，一般的配置就很难满足要求了。这时候怎么办？考虑使用 SSD（Solid State Drive，固态硬盘）这种固态的方式——它实现随机访问和顺序访问的性能几乎是差不多的，相当于大大减少了随机 I/O。

这个道理在普通用户的电脑上也是一样的。以前我不太懂，我想很多同学最初也是个小白：买第一台电脑的时候特别爱惜，用了好几年，最后发现性能实在太差了，这时候就会有个直观判断——觉得是自己电脑差，主要是 CPU 不行了。从这个角度上讲，英特尔的广告做得确实很到位。结果呢？我换了一台笔记本之后，开机速度并没有明显地提升：原来需要 3 分钟，以为买了新电脑会变成 1 分钟，结果发现还是两分多钟，总觉得自己这个钱花得冤枉。后来懂了以后才发现：电脑慢的时候，优先配一块固态硬盘，对开机和运行相关软件速度的提升，要远远高于只换一块 CPU。

#### 磁盘 IO 分布与多处理器

**合理地分布磁盘的 I/O**。能把磁盘 I/O 分配到多个设备上，就能减少资源的竞争，提高并发的能力。

**配备多处理器**。这时候我们可以用多线程的方式去工作；多处理器就能更好地执行多个线程。

硬件层面的分析就是这些，比较简单。重点在下面：优化 MySQL 的参数。

### MySQL 服务器参数优化

参数下面罗列了很多，我们一个一个来看。这些参数主要配置在 `my.cnf` 和 `my.ini` 这两个文件里，配置好以后重启 MySQL 服务，让它重新加载；参数主要是放在 mysqld 这个服务的段落当中。

#### 缓冲池与缓存类参数

**`innodb_buffer_pool_size`** ——首当其冲，这个必须最先讲。它就是我们所谓的缓冲区的大小。表数据、索引数据，都是可以放在这个缓冲区当中的。这个值越大，显然就越能降低 I/O 的频率，数据就可以在缓冲区中待的时间更长一些。

> **提示**：下面讲的这些参数都是有一定限度的，绝不是越大越好。值越大，就越挤占其他资源占用的空间。

**`key_buffer_size`** ——索引缓冲区的大小。索引缓冲区是被所有线程共享的。这个值大一点，相当于这一块能更好地处理索引，索引可以在这里边多放一些。对 4 GB 大小的内存来讲，设置成 256 或者 384 就比较好一些。

**`table_cache`** ——表示同时可以打开的表的个数。这个值越大，我们同时打开的表就越多。物理内存越大，这个值就设置得越大一些，默认的情况是另一个样子，这里就不多说了。

**`query_cache_size`** ——查询缓存的大小。这个参数前面讲过，它要配合 `query_cache_type` 一起使用。它对应的就是我们在讲逻辑架构时提到的那个查询缓存：执行过程当中有一个查询缓存，说的就是它。

在这个查询缓存当中，首先你要设置 `query_cache_type`，保证你能使用它；在能使用的前提下，再去设置 `query_cache_size` 的大小。这里面还有几个相关的观察点，还记得当时怎么讲的吗？

- 看到某个参数的值比较大，说明相应占用的缓存就比较多了；这个值大，你就需要适当地去调整 `query_cache_size` 的大小。
- 如果 `hits` 这个值比较大，说明每次查询命中查询缓存比较频繁——这是个好事。
- 如果 `blocks` 这个值比较大，说明缓存里的碎片比较多。

> **易错点**：`query_cache_size` 这块要特别注意，先确定 `query_cache_type` 是不是开启了，开启了才能从这里边去查。另外，如果这个值设置的是 0，注意它仍然会占用查询缓冲区的空间——比如在 5.7 当中，你这个值是 0，但只要你设置了一个大小，它仍然会占用那块空间，虽然你并不使用它。

至于在 SQL 语句里显式指定查询缓存的那几个写法，前面也都讲过了，不再重复。

> **提示**：查询缓存这个机制在 MySQL 8.0 的时候已经失效了，我们在 5.7 及之前的版本才会去使用它。

#### 排序、连接与顺序扫描缓冲区

**`sort_buffer_size`** ——对需要进行排序的线程分配的缓冲区大小。它是针对 `ORDER BY` 和 `GROUP BY` 起作用的。如果这类操作比较多，就可以去调整这个参数的大小。

**`join_buffer_size`** ——一看名字就是针对 `JOIN` 来设置的，为连接操作起作用的。

**`read_buffer_size`** ——每一个线程连续扫描时，为扫描的每个表分配的缓冲区大小。如果我们要从表中连续地读取行，就会用到这个大小，可以去设置它。

#### 日志缓冲区与刷盘时机参数

**`innodb_flush_log_at_trx_commit`** ——这是个很重要的参数。后面讲到事务的日志的时候，还会再去讲它。这个值可以设置成 0、1 和 2，它影响的是我们把缓冲区的数据写入日志文件的时机。

- 值为 **0** 的时候，每秒把数据写到日志文件一次，比如 redo log；然后同样地把日志文件写入到磁盘中。这是刷盘的操作。
- 值为 **1** 的时候，每次提交事务的时候再去写到文件里边，同时把这个文件同步到磁盘当中。
- 值为 **2** 的时候，每次提交事务的时候写到日志文件，然后每秒钟去刷盘。

我们把它整理成一张表，差别就清楚了：

| 取值 | 写日志文件的时机 | 刷盘（同步到磁盘）的时机 | 刷盘频率 |
| --- | --- | --- | --- |
| `0` | 每秒一次 | 每秒一次 | 低 |
| `1` | 每次提交事务 | 每次提交事务 | 高 |
| `2` | 每次提交事务 | 每秒一次 | 中 |

**`innodb_log_buffer_size`** ——日志的 `buffer_size`。顾名思义，就是日志文件所用的那个缓冲区的大小，这个参数设置的就是这块缓冲区的大小。

#### 连接数与线程池参数

**`max_connections`** ——连接到 MySQL 数据库的最大数量。如果我们看到另外的一个变量 `connection_errors_max_connections` 不为 0，而且一直在增长，那就意味着最大连接数已经被超了，你有必要增加这个变量的值。在 Linux 平台下，性能比较好的服务器支持 500 到 1000 个连接是正常的，没有问题。

> **易错点**：连接数也不是越大越好。很自然——连接越多，就越有可能导致 MySQL 服务器僵死，因为资源是有限的。

**`backlog`** ——用来控制 MySQL 监听 TCP 端口时积压的请求栈的大小。举个例子：`max_connections` 我们设成了 1000，而且现在确实同时有 1000 个连接。这时候多来了一个，那它就得等待。等待的这些请求放在哪？就放在 `backlog` 这样一个堆栈当中。你要来十个，就都放在这里，然后等哪些连接不用了、释放出来了，你再从这里边取出来一个，去分配连接的资源。所以如果我们是短期大量连接来访问，就要适当地调整这个值的大小。

**`thread_cache_size`** ——缓冲池当中缓冲线程数量的大小，也就是线程池。这个讲过线程池的一看就明白它主要的作用是什么，不用在这里多啰嗦。

如果通过这个参数不断地去查看，发现 `Threads_cached` 这个量越来越少、可用的越来越少，正在使用的那些迟迟下不来，而创建线程的个数又持续升高，那就意味着现在线程池中的线程不够了。怎么办？适当地提高 `thread_cache_size` 就可以了。

**`wait_timeout`** ——一个请求的最大的连接时间，我们可以对它进行设置。

**`interactive_timeout`** ——服务器在关闭前需要等待的秒数。

这些都还算是一些小参数。讲完这些，课件下面还给了一个建议的参数列表——但这里要注意，那也只是一个建议，因为更多的情况还是要具体问题具体分析。

### 电商平台高并发案例：三个参数的调整

讲了这么多参数，下面举一个具体的案例。还是以电商平台为例：这个平台涉及商家和客户，商家把商品放到平台上，客户通过手机或者 App 下单购买。系统刚上线的时候，整个系统运行是比较良好的。随着入驻的商家不断增多、用户量不断增多，订单很快达到了每天 5 万条以上。这个时候系统就出现问题了：CPU 使用率不断飙升，终于在这个双 11 或者 618 这样的活动期间，CPU 达到了峰值。

那就要调优。从数据库层面，这时候用到了三个参数。

第一个是 `innodb_flush_log_at_trx_commit`。它的取值有 0、1、2，默认值是 1。默认的 1 是什么场景？每次事务提交的时候写到日志，紧接着就把这个日志写到磁盘当中——相当于提交刷盘的频率是很高的。那我们把它改成 2：每次提交事务的时候把它写入日志文件，这个没问题；然后每隔一秒，再把它写入到磁盘中。相当于降低了刷盘的次数，此时就降低了 CPU 执行的压力。通过这个方式，我们把 CPU 的使用率降下来。

第二个是 `innodb_buffer_pool_size`。把这个缓冲池、缓冲区的空间加大。值加大以后，我们就更容易使用到缓冲区里的索引和数据，降低了磁盘 I/O，也就是降低了服务器的 CPU 压力。又鉴于这台 MySQL 服务器是数据库专属服务器——就是专门给我们数据库用的——那这时候就可以分配较大的值作为缓冲区的大小。

第三个是 `innodb_buffer_pool_instances`。上面没有讲这个参数：它相当于可以把 `buffer_pool` 分成多个部分，比如我们改成 64。改成 64 个分区以后，就可以有多个进程同时来访问这个 `buffer_pool` 了，相当于提升了系统的并发处理能力，CPU 的利用率就会更高，同时能处理的业务也就更多一些。

```text
   疏通瓶颈（参数 1、2）                       增加并行（参数 3）
   innodb_flush_log_at_trx_commit              innodb_buffer_pool_instances
   innodb_buffer_pool_size
             │                                          │
             ▼                                          ▼
     降低刷盘频率 / 减少磁盘 IO                多个进程并发访问 buffer pool
             └───────────────────┬──────────────────────┘
                                 ▼
                    降低 CPU 压力、提升并发处理能力
```

前两个参数解决的是"疏通"这一类问题，第三个参数解决的是"增加并行能力"那一类问题。

打个生活里的比方。我原来去尚硅谷北京校区上班的时候，经常过那条叫文华路的路，那块确实经常堵，因为路太窄了。那怎么办？一个思路是疏通这个路段、消除这个瓶颈，我等待的时间就更短了；另一个思路是，在间隔它一两公里的位置再修一条路，拓宽新的通道，增加并行的能力。这就是我们解决问题的两种思路——前两个参数相当于第一种，第三个参数相当于第二种。

服务器的硬件和参数这两个层面，就介绍到这里。这里的参数比较多，大家在真实开发中多用一用，才能够体会到它真实的用处。在这里，我们只能是进行一个泛泛的介绍。

## 160-数据库结构优化、大表优化、其它3个策略
> 对应分集：P160 | 原始标题：《160-数据库结构优化、大表优化、其它3个策略》

MySQL 服务器的优化措施讲完了，接下来轮到一个更容易被忽视、但收益往往更大的地方：数据库结构本身的设计。一句很实在的话——**一个好的数据库设计方案，对数据库性能的提升往往起到事半功倍的效果**。

那到底有哪些措施能让我们达到这个"事半功倍"？下面一个一个说。

---

### 数据库结构优化

#### 拆分表与冷热数据分离

先泛泛地说这个思路。假设现在有这么一张表，字段有好多。用着用着就会发现：有些字段在 SQL 语句里经常被使用、经常被查询，而另外一些字段很少用到。**经常用的那批就叫热数据，很少用的那批就叫冷数据。**

既然是这样，我们就可以考虑把这张表拆开：一张表变两张表，热数据构成一张表，冷数据构成一张表。

> **易错点**：主键不能只留在一边。原来表里的主键在两张表里都要写一份，否则两半数据就关联不起来了。

拆开之后日常怎么用？经常用热数据，直接查热数据那张表就行；冷数据很少用，真要用的时候随时从冷数据表里调一下，再做一次连接。

这样做的好处有两点：

- 减少磁盘 I/O，保证热数据的内存缓存命中率。原来聚簇索引 B+ 树的叶子节点里，所有字段都得存；现在叶子节点上只需要存热数据。单个页里装的数据量不再是原来那一大坨，**一个页能存下更多行，往内存里加载时读的页就更少**。
- 缓存利用率更高。冷数据本来就不怎么用，没必要把它缓存进内存，缓存里腾出来的位置全留给热数据。

看一个真例子。针对会员表 `members`，把数据拆成热数据和冷数据：

| 分类 | 字段 |
| --- | --- |
| 热数据 | `id`、`username`、`password`、最近一次登录时间、最近一次登录的 IP |
| 冷数据 | `id`（主键必须保留）、`address`、`telephone`、`description`（描述信息） |

现在如果要查询某个用户的 `username` 和他的 `telephone`，做一次多表连接就可以了。连接条件就是**主键 `id` 在两张表里都出现，让 `id` 相等**。

#### 增加中间表

第二个措施针对的是联合查询。比如有两张表，我们经常从这张表里用两个字段、从那张表里用两个字段，老是这么 JOIN。那不妨造一张中间表，把这四个字段取出来构成一张新表。

新表一开始没数据，就用 `INSERT ... SELECT` 把上面两表联合查询的结果复制进来，数据就有了。原来要做的联合查询，现在改成对中间表做单表查询，查询效率自然上去了。

拿班级表和 `student` 表举例：假设我们要查学生的 `id`、`name`，以及他所在班级的 `class_name` 和班长。这几个字段就可以构建成这样一张中间表，构建完再用 `INSERT ... SELECT` 从上面两表的多表连接里把数据灌进去。

后面跟着的问题是什么？**数据一致性**。学生表或班级表一旦改了数据，中间表也必须同步改。常用的一种做法是：上面数据一修改，就把中间表的数据全部清空，然后重新做一次 `INSERT`，数据就又对上了。

> **注意**：不能频繁这么干。每次修改都要清空再重新灌，成本挺高。所以**中间表只对不是特别频繁更新的表才比较有效**，这一点务必记牢。

#### 冗余字段与视图

第三个方式是增加冗余字段。这就是前面讲过的反范式化的意思——加一个冗余字段，原来要多表查询的地方现在一张表就够了。

顺便说一句视图：**视图大家就别用了**。视图本身还是对我们现有表的 SQL 语句做了一层封装，查询效率上不会有特别实质性的变化，多这一层封装不划算。

#### 数据类型优化

优化数据类型这件事，基础篇里讲数据类型精讲的时候已经说过该怎么选，这里针对性地再说一遍。

总体原则是：**优先选择符合存储需要的最小的数据类型**。能小就不要大，为的是节省空间。

> **结论**：字段越大，建立索引所需要的空间就越大，一个页里能放的索引数量就越少，遍历时 I/O 的次数就越多，性能就越差。这是一条连锁反应。不过要清楚，字段大只是性能差的原因之一，不是唯一原因。

**整型**这块，有好几种整型类型，不知道选哪种的话，**默认就选 `int`**，它的范围足够大、足够我们用。比 `int` 大的就只有 `bigint` 了：像双 11 这种交易量、大型门户网站的点击量，可以用 `bigint`；一般情况下 `int` 都足以承载，用它放心。

> **提示**：对于非负的整型数据，一定要加上 `unsigned`。把负数那一半砍掉之后，剩下的范围全归到正数里，等于提升了这个类型能存的数据量。比如存人的年龄用 `tinyint`，你会担心正负 127 不够——加上 `unsigned` 就肯定够了。

如果一份数据既能用文本类型存、也能用整数类型存，**那就用整数类型**，因为同样的数据整数占用的空间更小，能提升查询效率；道理还是那个：数据页里能放的记录更多了。比如把 IP 地址转换成整数来存，就是这类选择。

**尽量避免使用 `text` 或 `blob`**。这两种类型最大可以支持 4GB，一想着要把这种数据塞进表里，加载起来是件很崩溃的事。而且内存级的临时表不支持它们，想用临时表只能用磁盘临时表，还要做二次查询，性能很差。

所以这类字段**一定要分离到单独的表当中去存**。比如一张存用户信息的表，用户经常需要保存一张照片：照片就别在这张表里存了，这里只存一个 URL，另外建一张表专门存图片。真要查的时候，也**不要用 `SELECT *`** 把大字段一起查出来加载到内存，成本很高。能避开 `text` 就避开它。

**枚举类型**（`enum`）：它的值修改需要用 `ALTER`，`ORDER BY` 的时候效率也比较低，所以**建议用 `tinyint` 去替代 `enum`**。

**日期时间类型**：前面讲日期时间类型时提到过 `TIMESTAMP` 和 `DATETIME` 这两个——`TIMESTAMP` 占 4 个字节，`DATETIME` 占 8 个字节。所以像注册时间、商品发布时间这类场景，用 `TIMESTAMP` 存，占用空间更小。

**浮点类型**这块没有什么可商量的：**不要用 `FLOAT` 和 `DOUBLE`，就用 `DECIMAL`**，因为 `DECIMAL` 不会丢失精度。尤其是财务相关的金融数据，不允许有精度的损失。

> **结论**：遇到数据量大的项目，一定要在充分了解业务需求的前提下，合理配置字段的数据类型。

#### 插入记录速度优化（MyISAM）

如果只是插入一两条，那无所谓；插入数据量一大，就得考虑优化插入速度了。这里要按存储引擎分开看，因为 MyISAM 和 InnoDB 这两个引擎的一些特性不一样。

MyISAM 这边有四个点：

- **禁用索引**。大量 INSERT 的时候，凡是涉及到的索引字段都要跟着修改，插入速度就下来了。所以先把索引禁掉，等插入完成以后再启用。
- **禁用唯一性检查**。每加一条数据都要保证唯一性，等于每条数据都要和现有表里的字段做一次校验，成本很高。先禁用唯一性检查，添加完成以后再单独去校验。
- **批量插入**。如果每条数据写一条 INSERT 语句，那每个 SQL 都要做解析、优化、执行，成本很高。合成一个 SQL 语句来做，只需要解析一次就够了，这种方式优于逐条插入。
- **`LOAD DATA INFILE`**。MyISAM 引擎还可以用 `LOAD DATA INFILE` 这种批量导入数据的方式，它比批量插入还要更好。

#### 插入记录速度优化（InnoDB）

InnoDB 这边有几个点，第一个和上面一样：

- **禁用唯一性检查**。
- **禁用外键检查**。InnoDB 支持外键，添加数据的时候它会到子表（副表）里校验有没有对应的字段值，这个成本也很高，所以先关掉；插入完成之后再统一检查子表里有没有这些字段值，这样要好一些。
- **关闭自动提交**。InnoDB 支持事务，而 DML 的增删改默认每执行一次都会自动提交，一提交就要写入磁盘，成本比较高。所以在添加数据之前先让它不要提交，等全部插入完成以后再提交一次。

#### 非空约束

设计字段的时候，**能加上 `NOT NULL` 约束就给它加上**。原因有三层：

- **存储空间**。NULL 值在行格式里专门有一个 NULL 值列表来存，得占额外的空间；用 `NOT NULL` 就不需要考虑这个存储问题。
- **索引用不上**。`IS NOT NULL` 这样的判断、过滤语句是用不了索引的。如果默认大家都非空，就不用写它了，索引就能起到作用。
- **聚合函数偏差**。字段里有空值时，`COUNT` 之类的聚合函数不会计算空值，结果可能会有偏差。

#### 分析表、检查表与优化表

MySQL 提供了三个表维护操作，分别对应分析、检查、优化：

| 操作 | 关键字 | 作用 |
| --- | --- | --- |
| 分析表 | `ANALYZE` | 分析关键字的分布 |
| 检查表 | `CHECK` | 检查表是否存在错误 |
| 优化表 | `OPTIMIZE` | 消除删除或更新造成的空间浪费，相当于碎片整理 |

**分析表（`ANALYZE TABLE`）**

分析表可以一次写多个表，相当于这几个表都分析了。

前面这个参数可加可不加，叫 `LOCAL` 或者 `NO_WRITE_TO_BINLOG`，**这两个意思一样，选一个写就行，当然也可以不写**。用上它是什么意思？这涉及后面要讲的 binlog 日志——做主从复制的时候，从机要靠 binlog 日志同步主机上的任何修改。这两个参数决定的是**这条 `ANALYZE` 语句要不要写进 binlog 日志**。不希望它写就加上。实际上它也不会对表产生任何影响，所以可以考虑用上这两个参数。

> **注意**：`ANALYZE TABLE` 在分析表的过程中会给表加一个**只读锁**，言外之意就是这时候你不能更新或插入数据了。它针对 InnoDB、MyISAM 类型的表都有效，但**不能用在视图上**。

下面用例子把这件事走一遍。先选一个数据库，创建一张表，表里 `id` 是主键，`name` 上有一个普通索引：

```sql
CREATE TABLE user1(
  id   INT PRIMARY KEY,
  name VARCHAR(15),
  INDEX(name)
);
```

表建好以后往里面添加 1000 条记录（记录是随机添加的，用到了存储函数和存储过程，都提前创建好了），直接调用存储过程把 1000 条记录灌进 `user1`。数据量小，所以很快。

接着查看这个表的索引：

```sql
SHOW INDEX FROM user1;
```

结果里能看到两个：一个是 `PRIMARY`，一个是普通索引。重点看 `Cardinality` 这一列——它翻译成中文叫**基数**，这个基数正是给 `ANALYZE` 做分析用的。这里一个显示 1000，一个显示 1，什么意思？

```sql
SELECT * FROM user1;
```

结果里主键 `id` 是 1、2、3 一直到 1000，有 1000 个不同的值；而 `name` 这一列全部都是 `@硅谷`，一个重复度极高的值——所有值都一样，所以只能算 1 个不同的值。`SHOW INDEX` 里的 1000 就表示它有 1000 个不同的值，这里的 1 就表示只有 1 个不同的值。

再做一个操作，把某一行改成另一个名字：

```sql
UPDATE user1 SET name = '@硅谷01' WHERE id = 2;
```

执行完再 `SHOW INDEX`：表里现在应该有两个不同的 `name` 值了——`@硅谷` 和 `@硅谷01`。但 `Cardinality` 那一位**还是 1**，它没有及时帮我们做更新。这时候就该用分析表了：

```sql
ANALYZE TABLE user1;
```

执行返回 `status OK`。再 `SHOW INDEX`，这一位就变成 2 了，因为表里现在确实有两种不同的值。

再来一次，把某行改成 `@硅谷03`，这时表里已经有三个不同的值。执行完 `SHOW INDEX`，看到的还是 2；再 `ANALYZE TABLE user1`，然后再 `SHOW INDEX`，就变成 3 了。

> **提示**：`Cardinality` 体现的是不同值的个数，你也可以把它理解成**区分度**。我们在讲索引的时候提过区分度的概念：查询优化器选择索引时，会计算不同索引哪一个花的成本高、哪一个成本低，最后把成本最低的那个作为这张表真正执行时用到的索引。区分度就是它要考虑的一个因素。`ANALYZE` 的作用，就是让它去更新一下不同字段的区分度。

这个值还有一个特点：**它越大、越接近于表中的条目数，说明区分度越高**；如果你在这个字段上有索引，优化器就越优先去考虑这个字段。

另外要注意：`id` 这一位在我这里执行出来直接就是 1000，但在你们那里初次看到的**不一定**是 1000，有可能显示成 2——就是说一开始它认为这个 `id` 的区分度只有两个不同的值，等你 `ANALYZE` 一下，它一看"呦，是 1000"，相当于帮你做了一次刷新。

**检查表（`CHECK TABLE`）**

检查表用的命令是 `CHECK TABLE`，它在执行过程中同样会给表加一个**只读锁**，同样对 InnoDB 和 MyISAM 都有效。写法是 `CHECK TABLE` 后面跟表名，也可以写多个表，后面还有一个 `option`：

```sql
CHECK TABLE user1;
```

`option` 可以取这样一些值：不扫描行、不检查错误的连接、只检查没有被正确关闭的表等等。**这些 option 只有 MyISAM 能用，InnoDB 不能用这个 option**，这一点做个了解就行。

实际执行一下 `CHECK TABLE user1`，返回 `status OK`。这张表本身没什么问题，所以也看不出它报什么错误信息。有时候在表的操作过程当中，一些错误的行为可能导致表出现损坏，这时候做 `CHECK` 操作，它就会给我们展示一些信息出来。

**优化表（`OPTIMIZE TABLE`）**

优化的意思是优化表。它干什么用？比如这个表里删除了一大部分数据，或者对一大部分数据做了更新，这时使用这条指令，可以对整个表占据的空间做一次**碎片整理**。

> **注意**：`OPTIMIZE` 只对 `VARCHAR`、`BLOB`、`TEXT` 这类字段类型起作用。这也很自然——这类字段占用空间本来就大；你要整一个 `int`，也没有必要非得去做空间优化。而且优化本身是要付出成本的，所以最好是数据类型比较大、同时确实大幅删除或更新过数据的场景才去用。针对 MyISAM 和 InnoDB 都是有效的。

这里有一个小的区别，我还真为此去查过相关资料。先建两张表，分别用 MyISAM 和 InnoDB 引擎：

```sql
CREATE TABLE t1(
  id   INT,
  name VARCHAR(15)
) ENGINE = MyISAM;

CREATE TABLE t2(
  id   INT,
  name VARCHAR(15)
) ENGINE = InnoDB;
```

对 `t1` 做优化：

```sql
OPTIMIZE TABLE t1;
```

返回的信息是 `Table is already up to date`。这也正常，表刚创建，没什么需要优化的，等于说已经优化到最新了。

再对 `t2` 做同一个操作：

```sql
OPTIMIZE TABLE t2;
```

这次返回的信息就不一样了：`Table does not support optimize`，说你这张表不支持 OPTIMIZE，建议你改用 `recreate + analyze`。

一开始执行看到这条信息，我的理解就是：哦，`OPTIMIZE` 对 InnoDB 是不支持的。但是又看到一些资料说它是支持的。那该怎么办？**是不是就得找官方文档了**，看到底支持还是不支持——要确定这个知识点到底是对的还是错的。

先说这条提示本身表达的意思。对 InnoDB 来讲，它说"你这样做"，其实也暴露了它真要优化的时候是怎么处理的：

```text
OPTIMIZE TABLE t2（InnoDB 的实际做法）
        │
        ├─ 1. 先创建一个临时表 t3
        │
        ├─ 2. 把 t2 中剩下的数据全部 copy 到 t3
        │       → t3 里没有碎片
        │
        ├─ 3. 删除有碎片的原表 t2
        │
        └─ 4. 把 t3 重命名为 t2
                → 碎片整理完成，再做一次 ANALYZE
```

图里就是 InnoDB 优化碎片的完整替换流程：新建临时表 → 拷贝存活数据 → 删原表 → 改名接管，这就是提示里 `recreate` 的含义，随后再做一次 `ANALYZE` 分析。

那这个操作到底有没有帮我们做优化？返回信息里又跟着一个 `OK`，这就得找官网了。在 8.0 的官方文档里，针对 `OPTIMIZE` 有专门说明，这是最权威的。

> **提示**：一般情况下大家不会去官网学 MySQL，毕竟是英文的，读起来还是挺痛苦。但在有一些问题解决不了的时候，就去官方文档里找答案，因为**它是标准**。

文档里往下走，提到 `OPTIMIZE` 针对的数据类型是一个方面，然后说 `OPTIMIZE` works for——它对哪些存储引擎是有效的。这里就提到了常见的三种存储引擎，其中**包括了 InnoDB 和 MyISAM**。看到这儿，心首先就放下来了：InnoDB 确实是支持的。

那它既然支持，为什么又给我们呈现那样的提示信息？靠不靠谱？明明告诉我支持，返回信息却说不支持。继续往下走，走到 InnoDB details 的细节部分，点进去一看，跟它有共鸣了——文档里也是这样说的，它去优化一个表的时候也会出现这条信息。再上面一读就发现了：它原来确实也优化了，**这条信息就是这个样子**，所以可以放心，确实帮我们做了优化。

要是还不放心，我还特意准备了一个例子（提前演示好了，没必要真的再跑一遍）。过程是这样的：

- 创建一张 `order1` 表，表里放了 `VARCHAR` 数据类型，添加 100 万条数据。添完以后底层对应的 `.ibd` 文件大小是 **412MB**。
- 把这张表中**一半**的数据删掉。删完以后再去看数据目录下的 `.ibd` 文件，**还是 412MB**——空间并没有还回来。
- 然后执行：

```sql
OPTIMIZE TABLE order1;
```

再查看 `.ibd` 文件，变成了 **336MB**。相当于确实做了一次碎片整理。

官网也看了，实际举例也说清楚了，说明它确实有优化的效果。如果你针对的表满足上面这个场景，就用优化指令去整理一下空间。

除了 `OPTIMIZE`，还有一个命令叫 `mysqlcheck`，它的效果和 `OPTIMIZE` **完全一样**。要演示它就得换到命令行里：

```bash
mysqlcheck -o atguigudb13 user1 -u root -p abc123
```

其中 `-o` 就是 OPTIMIZE 的意思，后面跟数据库名和要优化的表名，`-u` 是用户名、`-p` 是密码。回车之后，返回的信息跟我们刚才看到的其实是类似的，相当于它也帮我们做了一次优化，这也是一种方式。

#### 各项措施的权衡

这些措施**不是说在开发中一定要选的**，要量力而行、做个权衡，根据业务需求来定。原因很简单：很多操作方式都是**有利有弊**的。

- 修改数据类型，看起来越小越好，但万一小到数据都存不下了，这就成了一个错误——值得衡量一下。
- 增加冗余字段，一定要确保数据的一致性，这一点别忽略。
- 增加中间表（反范式化），同样不要忘了数据一致性的问题。
- 把冷热数据拆分开，原先只查一张表就能拿到的数据，现在需要从多个表中做 JOIN，连接成本反而增加了。

> **结论**：整体上都是有利有弊，要做一个整体的权衡之后，再决定到底怎么做。

### 大表优化策略

当 MySQL 单表的记录数过大时，整个数据库的 CRUD 性能会明显下降。这时候怎么办？相关的优化策略有下面这些。

#### 限定查询的范围

记录数已经很多了，这时候如果还不加任何限制、不加过滤条件去做查询，查询性能必然很低——需要把太多数据都检测出来。所以这里**要用上过滤条件，同时尽量还要使用上索引**。

#### 读写分离

读写分离这一块，后面讲到主从复制的时候还会再讲，这里先从优化的角度谈一谈。

单台主机上，我们已经针对表、SQL 语句做了最大限度的优化，包括相关的参数配置。但现在面对的是**高并发**场景，那该怎么办？这就需要提到一些其他的策略——集群、读写分离等等，用它们去分摊单台服务器的压力。

读写分离的做法是：通过**主从复制**的方式保证主机和从机的数据同步，然后针对数据库的**写请求访问 master 主机，读请求访问 slave 从机**。这里演示时用的是数据库中间件 **MyCat**，以它为例说明的是**一主一从**模式：

```text
一主一从
        ┌──────────────┐
        │   master     │  写请求
        └──────┬───────┘
               │ 主从复制
               ▼
        ┌──────────────┐
        │   slave      │  读请求
        └──────────────┘
```

一主一从的结构就这样简单：写全走 master，读全走 slave，中间靠主从复制保持同步。但这台主机也可能有宕机风险，那怎么办？可以有**双主双从**模式：

```text
双主双从
   ┌───────────┐   互相复制   ┌───────────┐
   │ master A  │◀───────────▶│ master B  │
   └─────┬─────┘              └─────┬─────┘
         │                          │
    ┌────▼────┐                ┌────▼────┐
    │ slave 1 │                │ slave 2 │
    └─────────┘                └─────────┘
   常态：master A 承担写，其余三台充当读机
   故障：master A 挂掉 → master B 启用写，其余三台继续充当读机
```

两台 master 之间互相复制，这本身也是一种备份。比如一开始使用的写主机是 master A，那么包括 master B 在内的三台都相当于充当读的机器；当 master A 挂掉时，另一台 master B 就启用，其他三台继续充当读机。这就是主从复制加读写分离的模式。

#### 分库分表

当数据量达到**千万级以上**时，可以考虑分库分表。

> **提示**：首先说清楚，并不是说 MySQL 不支持千万级以上的数据，它是支持的。只不过数据量特别大、到了几千万的时候，对整个查询、对整个服务器的性能来讲是一个挺大的考验。

原来所有的表都放在一台主机上，大家都来访问这一台，压力肯定很大。怎么办？先考虑**垂直分库**：把有些表分到这台主机上，有些表放在那台主机上。

分的时候**不要随机分**。假设一个项目涉及 100 张表，一定要按功能模块来分：**功能模块相同的表分在同一台主机上**，另一个模块的分在另外一台主机上，借此**避免跨库去做 join 操作**。

如果表中列比较多，还可以做**垂直分表**——把列多的表拆开，一张表变成两张表——这跟我们前面讲的冷热数据分离是同一种方式。

| 拆分方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 垂直分库 | 按功能模块把表部署到不同主机 | 相关联的表在同一库内，避免跨库 join | 表分布在多台主机，运维与访问复杂度上升 |
| 垂直分表 | 按列拆分，把列多的表拆成多张 | 单表数据变小，减少 I/O | 原来不需要 join 的查询，现在需要 join 了 |

再往下是**水平拆分**，针对的是**单表中数据量横向来看很大**的情况——几千万条数据怎么办？可以对数据做拆分。拆分并不非得只拆两份，也可以拆成更多份，主要看你有几台主机：有三台就分成三份来拆。

拆的时候要考虑**按照什么样的方式来拆，这个规则就叫分片**。有时候不太适合按日期来分：比如按时间分成三段平均分，一段放一台主机，看起来很整齐。但实际会发现，用户看历史订单往往看他最近的，前几年的他可能根本不看。这样分完以后，放近期数据的那台压力还是很大，其他两台压力仍然很小——**那就说明你的分片规则不是特别合适**。

分片规则有取模、按枚举的方式、按范围的约定、按日期等等，都是不同的分片策略，后面还会再提。现在先知道有这么一回事就行：按某个属性的维度进行拆分，就是分片策略的意思。

整体上讲，处理大表就是这么三个概念：**垂直分库、垂直分表、水平分表**。

关于水平拆分还有一段评价值得记住：水平拆分能够支持非常大的数据量存储，应用端改动也少；但是**分片事务难以解决，跨节点 join 的性能比较差，逻辑还挺复杂**。《Java 工程师修炼之道》的作者就推荐尽量**不要**做数据分片，因为它会带来相关的复杂度。

> **提示**：每个人有不同的见解，这要尊重；而且面对不同业务场景时情况比较复杂，不同场景下确实应该有不同的策略去处理。如果实在要分片，尽量选择在**客户端**进行分片的架构，**减少使用中间件的方式**。前面图里的 MyCat 就是比较常见的一种数据库中间件方式，用来做分库分表和读写分离；另一种是客户端代理的方式，在应用端把它封装在 jar 包里，通过修改或封装 JDBC 这一层来实现。两种不同的策略了解一下就可以了。

### 其它优化策略

除了针对大表做优化，还有其他几个策略，做个了解就可以了。这里提到的其实都算是 8.0 的新特性。

#### 服务器语句超时限制

8.0 当中可以设置**服务器语句超时**的限制，超时时间可以达到**毫秒级**。通过对应的参数做好设置之后，一旦超出这个限制，服务器就会终止查询、终止影响不大的事务或连接，并把错误报给客户端。这是一个比较好的参数。

#### 全局通用表空间

8.0 还可以通过 `CREATE TABLESPACE` 创建一个**全局通用表空间**，然后把表放进这个全局通用表空间当中保存，好处是**可以节省元数据方面的内存**。

举个例子，创建一个叫 `atguigu1` 的表空间，底层对应的 `.ibd` 文件也叫 `atguigu1`，默认大小 16KB：

```sql
CREATE TABLESPACE atguigu1 ADD DATAFILE 'atguigu1.ibd' FILE_BLOCK_SIZE = 16K;
```

创建好之后就可以去建表，建表时指定使用这个表空间：

```sql
CREATE TABLE test(
  id INT
) TABLESPACE atguigu1;
```

这样非常灵活——建表的时候就可以指定表空间。这个表占据的空间就放进这个文件里了，而不再是原来的独立表空间。

修改表的时候也可以把它改到共享表空间当中：

```sql
ALTER TABLE test TABLESPACE atguigu1;
```

不用这个共享表空间了，就去删它：

```sql
DROP TABLESPACE atguigu1;
```

这时它会提示一个错误信息，说 `atguigu1` is not empty——它不是空的，因为里面还有 `test` 这张表。所以如果你确实要释放这个表空间，需要**先把这张表删掉**：

```sql
DROP TABLE test;
```

删掉表以后，再去删除这个共享表空间就可以了。

#### 隐藏索引

隐藏索引在讲索引的时候说过，它和降序索引一样，是 8.0 的新特性。对优化来讲它也算一个策略，**但只有 8.0 才能用**。

当一个索引被设置成 `invisible` 的时候，查询优化器就不再使用它了。通过这个功能就可以做验证：把一个索引隐藏起来，看性能是不是有所下降。如果性能下降了，说明这个索引是有用的；如果隐藏以后性能没受影响，说明这个索引没什么用，你就可以把它删掉了。

> **提示**：这个道理跟看一个人的价值有点像。你想知道自己对公司有多大价值，就想象一下公司如果没有你，运转是不是一点影响都没有，甚至没有你公司运行得还更好——那你就尽量早点撤出这家公司。

使用隐藏索引要注意两点：

- **隐藏的索引仍然实时更新**。虽然查询优化器默认情况下不能用它了，但插入、删除、更新的时候它还是会被实时维护。所以如果一个索引长期被隐藏，那就最难受了：一方面查询优化器默认用不了它，另一方面它还实时更新、还在影响插入删除更新的性能，那还不如干脆删掉。
- **主键不要设置成 invisible**。主键要是设成 invisible 就失效了，这时候它就会又去选择一个**非空的唯一约束的索引**来当主键，不合适。

到这里，"下篇"的第二个篇章——从索引的数据结构一直到这一章——就讲完了。接下来开始讲事务的内容。
