# 锁机制与 MVCC 多版本并发控制
## 并发问题与两条解法

* **并发事务访问相同记录（Concurrent Transaction）**
    * 讨论前提是"访问的是相同记录"：往小看是同一行数据，往大看是同一张表；两个事务各自访问不同的表，根本不可能影响一致性，加锁没有意义。
    * 针对相同记录的操作只有增删改查，查询算读操作，增删改算写操作；以两个并发事务为例，组合只有读读、写写、读写三种。
    * 三种组合与对应问题：

    | 组合 | 两个事务的动作 | 需要关注的问题 |
    | :--- | :--- | :--- |
    | 读读 | 两个事务都在读 | 无并发问题 |
    | 写写 | 两个事务都在写 | 脏写 |
    | 读写 | 一个事务读、一个事务写 | 脏读、不可重复读、幻读 |

    * 读读不产生任何并发问题，两个读操作之间互相兼容，不需要考虑锁。

* **脏写（Dirty Write）**
    * > **定义**：两个事务都改了同一条未提交的记录，后一个事务的回滚把前一个事务已提交的结果覆盖掉了。
    * 过程：记录值为 1，A 与 B 都读到 1；A 改成 2、B 改成 3；A `commit` 认定 2 已固定，B `rollback` 把 3 变回 1，A 再查结果是 1。
    * 解法：必须让两个写事务排队执行，一个改完并提交或回滚、事务结束后，另一个再进来。
    * 脏写在任何一个隔离级别下都不会发生，锁机制已经用排队执行把它挡掉了。
    * 获取锁成功相当于 Java 里拿到 `synchronized` 后边的同步监视器。

* **锁结构（Lock Structure）的基本字段与状态**
    * 一条记录上没有事务操作它时不生成锁结构；有事务来操作就生成一个，锁结构跟事务相关。
    * 字段 `trx_id` 标识当前这个事务是谁；字段 `is_waiting` 代表当前事务是否需要等待。
    * 三种行为状态：

    | 行为 | 锁结构 | `is_waiting` | 含义 |
    | :--- | :--- | :--- | :--- |
    | 不加锁 | 未生成 | —— | 记录上没有任何事务操作它 |
    | 获取锁成功 | 已生成 | `false` | 当前事务可以执行 |
    | 获取锁失败 | 已生成 | `true` | 必须等待其他事务执行完 |

    * 先到的事务 `is_waiting` 为 `false` 直接执行；后到的事务 `is_waiting` 为 `true` 排队；前者提交或回滚结束后，系统扫描等待中的锁结构，把后者的 `is_waiting` 由 `true` 改成 `false`。
    * 一条记录上可以同时存在多个锁结构，分别对应该记录上有几个事务来操作。

    ```text
    T1 请求写               T2 请求写                T1 提交/回滚结束
        |                       |                          |
        v                       v                          v
    锁结构1                 锁结构2                    扫描等待中的锁结构
    trx_id     = T1         trx_id     = T2            找到 锁结构2
    is_waiting = false      is_waiting = true          is_waiting: true -> false
    加锁成功，开始执行       获取锁失败，排队等待         T2 加锁成功，开始执行
    ```

    * > **易错点**：不是一条记录只有一个锁结构；锁结构是跟事务打交道的，有几个事务来操作这条记录就有几个锁结构。

* **三个读写并发问题（脏读、不可重复读、幻读）**
    * 脏读：B 把记录由 1 改成 2 但未提交，A 在这时读，读到了 B 未提交的 2。
    * 不可重复读：A 读到 1，A 还没结束，B 把 1 改成 2 并提交，A 在同一个事务里再读发现值是 2。
    * 幻读：A 读 `id` 小于 10 的记录读到 5 条，A 还没结束，B `insert` 两条 `id` 在 10 以前的记录并提交，A 再读变成 7 条。
    * 三个问题放到一起对比：

    | 问题 | 事务组合 | 触发动作 | 同一事务内的异常表现 |
    | :--- | :--- | :--- | :--- |
    | 脏读 | A 读、B 写 | B 修改后未提交 | 读到了 B 未提交的新值 |
    | 不可重复读 | A 读、B 写 | B 修改并提交 | 两次读到的同一条记录值不同 |
    | 幻读 | A 读、B 写 | B 插入并提交 | 两次读到的记录条数不同 |

    * 按 SQL 标准，可重复读只解决脏读和不可重复读；MySQL 的可重复读把幻读也解决了，这是靠 MVCC 实现的。
    * 脏写和这三个问题不是一回事：脏写被排队执行直接挡掉，靠隔离级别去回答的是有读有写时怎么解决这三个问题。

* **解法划分：读走 MVCC + 写加锁 / 读写都加锁**
    * 方案一：读使用 MVCC，写加锁；读写之间彼此不冲突，并发性能比较高。
    * 方案二：读和写都加锁；读写之间需要排队，并发性能会受影响。
    * 写操作一定要加锁，因为增删改一定是针对最新的记录版本进行的。
    * 读可以不去碰最新版本，而是生成一个读视图（Read View）；Read View 里记录的是所有**已提交**事务所做的更改，生成时还没提交的事务、以及之后才开启的事务都不记录进去。
    * 读操作需要加锁的场景：读操作也必须针对最新版本时（如先读账户余额再存钱再写回），读也要加锁；加锁之后读写同样排队，脏读、不可重复读、幻读都能解决。

    | 方案 | 读操作 | 写操作 | 读写之间 | 并发性能 |
    | :--- | :--- | :--- | :--- | :--- |
    | 方案一 | 使用 MVCC | 加锁 | 彼此不冲突 | 比较高 |
    | 方案二 | 加锁 | 加锁 | 需要排队 | 会受影响 |

* **加锁方案对幻读的短板与间隙锁的引子**
    * 针对已有记录加锁能解决脏读与不可重复读，因为这两种情况都能落到一条真实存在的记录上。
    * 幻读是 `insert` 造成的，插入的是新增的幻影记录，这条记录当初根本不存在，加锁加不到它身上。
    * 解法是让小于某值的整块范围都锁上：目标记录落在这个范围内也就是处在间隙内时不让它添加成功，这就是后面行锁里的间隙锁与临键锁。

* **锁粒度与并发度的权衡**
    * 锁不是数据库独有的概念；只要多个进程或线程并发访问共享资源就需要锁，数据库里需要争抢的资源除 CPU、内存、I/O 之外还有数据本身。
    * 锁机制为 MySQL 提供的各个隔离级别提供保障；用了锁就会出锁冲突，锁冲突一定会影响并发性能。
    * 平衡落在锁的粒度上：希望并发性高一点就把粒度放小，希望并发性低一点就把粒度放大。
    * 三个粒度层次：表级锁（Table Lock）锁整张表，页级锁（Page Lock）锁若干数据页，行锁（Record Lock）锁一行行数据，行是能操作数据的最基本单位。

    | 粒度层次 | 锁定范围 | 并发度 | 加锁／检查／释放的开销 |
    | :--- | :--- | :--- | :--- |
    | 表级锁（表锁） | 整张表 | 低 | 小 |
    | 页级锁 | 若干数据页 | 中 | 中 |
    | 行锁 | 若干数据行 | 高 | 大 |

    * 粒度层次是按数据操作粒度划分这条线上的三级，另外两个维度是按对数据的操作类型划分（S 锁与 X 锁）和按对待锁的态度划分（悲观锁与乐观锁）；再加加锁方式划分（显式锁与隐式锁），以及全局锁与死锁。
    * 讨论粒度冲突的前提是至少有一方要写：两边都只是读，读跟读兼容，不存在冲突。

## 两把基础锁：S 锁与 X 锁

* **共享锁（Shared Lock，S 锁）与排他锁（Exclusive Lock，X 锁，也叫独占锁）**
    * > **定义**：按数据操作类型划分，读提供一种锁、写提供一种锁，再让这两种锁相互阻塞来解决问题，于是得到 S 锁与 X 锁。
    * 习惯上共享锁对应叫读锁，排他锁对应叫写锁；凡是写的场景一定是排他的、需要相互阻塞，读跟读之间是共享的。
    * 读读共享：同一份数据多个事务都是读操作，相互之间不受影响、也不阻塞。
    * 排他：一个写操作未完成、即事务未完成之前，它会阻塞其他加写锁的事务，也会阻塞其他加读锁的事务。
    * InnoDB 里读锁和写锁既可以加在表上，也可以加在行上；MyISAM 只支持表级别的锁。

* **S 锁与 X 锁的兼容矩阵**
    * 只要出现了 X 锁，不管它是先来的还是后到的，组合一律不兼容；只有 S 与 S 之间兼容。
    * 把矩阵读成一张排队规则表：两把 S 锁可以同时进门，S 与 X 之间必须排队，两把 X 锁之间也必须排队。

    | 已持有锁 \ 新请求 | 请求 S 锁 | 请求 X 锁 |
    | :--- | :--- | :--- |
    | 持有 S 锁 | 兼容，不阻塞 | 不兼容，阻塞 |
    | 持有 X 锁 | 不兼容，阻塞 | 不兼容，阻塞 |

    ```text
    事务 T1:  ──[ X 锁 持有中 ]──────────────────────────┐
                        │                                │
    事务 T2:            └─ 请求 S 锁 ──▶ 阻塞 ──▶ 等待 T1 释放 ──▶ 取得 S 锁
    事务 T3:            └─ 请求 X 锁 ──▶ 阻塞 ──▶ 等待 T1 释放 ──▶ 取得 X 锁
    ```

    * > **易错点**：不兼容不是"谁先来谁占理"，X 锁一旦参与进来，无论它是先持有的一方还是后请求的一方，结果都是阻塞。

* **读操作既能加 S 锁也能加 X 锁**
    * 写锁明确是排他的；读锁既可以让它是共享的，也可以让它排他，决定权在这条 `select` 语句后面跟什么后缀。
    * 传统写法（5.7 与 8.0 都支持）：

    ```sql
    -- 加 S 锁：共享锁
    SELECT * FROM account LOCK IN SHARE MODE;

    -- 加 X 锁：排他锁
    SELECT * FROM account FOR UPDATE;
    ```

    * 8.0 给 S 锁配了更贴近语义的新写法 `SELECT * FROM account FOR SHARE;`，它对应 `LOCK IN SHARE MODE`；`FOR UPDATE` 对应 X 锁。
    * `FOR UPDATE` 本质上相当于你是一个增删改的角色，只不过执行的动作其实是读。
    * T1 拿 S 锁后，其他事务对同样数据也加 S 锁互不阻塞；T2 去加 X 锁则必须等 T1 结束。T1 拿 X 锁后，T2 无论加 S 锁还是 X 锁都要阻塞。
    * 加锁演示必须在会话里先 `begin`（或 `start transaction`）：不开启事务时默认 `autocommit`，操作完事务就结束了，锁留不住；一个会话代表一个事务。

* **不等待锁的策略：`NOWAIT` 与 `SKIP LOCKED`**
    * 等待什么时候结束由一个控制超时的变量决定，一旦超时等待就结束；不想依赖这个变量时，8.0 引入了在现有语句后面加后缀 `NOWAIT` 或 `SKIP LOCKED` 的新特性。
    * `NOWAIT` 就是不等待：只要发现等不到锁就立刻返回，并提示有锁的情况。
    * `SKIP LOCKED` 也会立刻返回，但它不报错，只返回结果中**不包含被锁定行**的数据；如果一行能读的都没有，就是一个空结果集。
    * 两者的差别只在"拿不到锁时怎么办"：`NOWAIT` 直接报错返回，`SKIP LOCKED` 绕过被锁的行、返回能读到的行。

    ```sql
    -- 等不到锁就直接报错返回，不阻塞
    SELECT * FROM account FOR UPDATE NOWAIT;

    -- 跳过被锁定的行，返回剩余未被锁定的行
    SELECT * FROM account FOR UPDATE SKIP LOCKED;
    ```


* **写操作的加锁行为：`delete`、`update`、`insert`**
    * 写操作没有读操作那种选择余地，一定得加 X 锁。
    * `delete`：去 B+ 树里找到这条记录，把该行 `deleted_mark` 字段由 0 改成 1，全程加 X 锁，不是把行从页里抹掉。
    * `update` 分三种情况：
        * 情况一，不改键值且字段占用的存储空间修改前后没有变化：在原记录位置上直接改字段，过程中加 X 锁。
        * 情况二，不改键值但修改导致前后存储空间变了：先彻底删掉原有记录（移入垃圾链表）并加 X 锁，再插入一条新记录，这一步由隐式锁保护，确保没提交之前不会被其他事务看到。
        * 情况三，修改记录的键值：同样先删掉原记录并加排他锁，再做一次 `insert`，`insert` 时自动加隐式锁，没提交之前其他事务看不到。
    * `insert` 一般情况下不需要加锁，因为插入之前没有实体抓手，无法针对它做加锁行为；它靠隐式锁保证提交之前不被别的事务访问。
    * 泛泛地讲"写操作加 X 锁"没毛病；细节上 `update` 和 `delete` 是真正加了 X 锁，`insert` 加不了 X 锁，靠隐式锁兜底。

    | 写操作 | 是否真正加 X 锁 | 关键说明 |
    | :--- | :--- | :--- |
    | `delete` | 是 | 定位记录后改 `deleted_mark`，全程 X 锁 |
    | `update`（不改键值、空间不变） | 是 | 在原记录位置直接改字段 |
    | `update`（不改键值、空间变化） | 是，另加隐式锁 | 删旧记录加 X 锁，插新记录走 insert 的隐式锁 |
    | `update`（改键值） | 是，另加隐式锁 | 删旧记录加 X 锁，再 insert 并自动加隐式锁 |
    | `insert` | 否 | 插入前没有实体抓手，无法显式加锁，由隐式锁保证提交前不可见 |

    ```text
    delete 一条记录
          │
          ├─ 1. 在 B+ 树中定位目标记录
          ├─ 2. 将该行 deleted_mark 由 0 置为 1
          └─ 3. 全程持有 X 锁（排他锁）
    ```

## 表级锁

* **表级锁（Table Lock）的整体特征**
    * 表级锁锁定整张表，是 MySQL 最基本的锁策略，不依赖存储引擎，任何引擎的策略都一样。
    * 好处是开销小，并且能够避免死锁——整张表都锁住了不会再有死锁问题；代价是并发性差。
    * 表锁这一族一共四把：表级 S 锁、表级 X 锁、意向锁、元数据锁；另有自增锁也属于表级。
    * InnoDB 支持行级锁、MyISAM 只支持表级锁，这是两个引擎在锁上的主要区别；平时之所以说引擎一个支持表级锁一个支持行级锁，指的主要是表级的 S 锁与 X 锁这一把。
    * InnoDB 很少用表级 S 锁与 X 锁，只有在一些特殊场景下（比如崩溃恢复）才可能用到，而且是手动去加。
    * 平时说 InnoDB 里增删改查不加表锁是对的，但 InnoDB 中的意向锁、自增锁、元数据锁其实都存在。

* **表级 S 锁与 X 锁的手动加解锁**
    * 通常用表级 S 锁或 X 锁的都是 MyISAM，因为 MyISAM 不支持行级锁，只能这么做。
    * `read` 对应共享锁，`write` 对应排他锁，`unlock tables` 负责释放；在 MyISAM 上举的例子把 `engine` 改成 InnoDB 同样能跑，只是没有必要。

    ```sql
    -- 加表级共享锁（S 锁）
    lock tables my_lock read;

    -- 加表级排他锁（X 锁）
    lock tables my_lock write;

    -- 释放表锁
    unlock tables;
    ```

    * 查看表上锁的指令：`show open tables;` 查看所有打开的表，`show open tables where In_use > 0;` 只看正在被使用的表；重点是 `In_use` 字段，它表示这张表正在被使用，也就相当于这张表上有锁。
    * 加锁、查看、释放三步：加锁后 `In_use` 变成 1，`unlock tables` 后回零。
    * MyISAM 在查询时加的是表级别的读锁，进行增删改操作时给表级别加的是写锁。

* **表级 S 锁与 X 锁的行为验证**
    * 验证大纲：自己可读吗、自己可写吗、自己能操作其他表吗、他人可读吗、他人可写吗。
    * 加表级读锁后：自己可读；自己想写不行（`update` 与 `insert` 都不行）；自己访问没有被锁定的其他表也直接被拒绝；他人可读；他人可写会一直等待，直到表锁释放才执行成功。
    * 加表级写锁后：自己可读、自己可写都放开；自己仍然不能操作其他表；他人读和写全部阻塞等待。
    * 别人要读别的表毫无疑问可以，跟你这张表没关系，关键看别的表上有没有读锁和写锁。
    * 加读锁时 `begin` 与否都没关系，因为锁的是整张表。
    * 读跟读不会对数据产生并发问题所以放行；写不行，因为表已经被锁住了。

    | 当前表的锁 | 自己可读 | 自己可写 | 自己能操作其他表 | 他人可读 | 他人可写 |
    | :--- | :--- | :--- | :--- | :--- | :--- |
    | 表级 `S` 锁（`lock tables ... read`） | 是 | 否 | 否 | 是 | 否（阻塞等待释放） |
    | 表级 `X` 锁（`lock tables ... write`） | 是 | 是 | 否 | 否（阻塞等待释放） | 否（阻塞等待释放） |

    ```text
    会话150：lock tables my_lock read;
            ├─ 自己 select * from my_lock        → 可以
            ├─ 自己 update my_lock set name='a1'  → 不可以
            └─ 自己 select * from account        → 不可以（其他表也挡住了）
    另一个会话：
            ├─ select * from my_lock             → 可以
            └─ update my_lock set name='a2'      → 阻塞等待
                  ▲
                  └─ 直到会话150执行 unlock tables; 才成功，查到的 name 变成 a2
    ```

    * > **易错点**：`lock tables` 之后，同一个会话里访问没有被锁定的表也会被拒绝；这一点跟"只影响别人"的直觉正好相反。

* **意向锁（Intention Lock）要解决的问题**
    * 表级 X 锁与表级 S 锁的判定本要求"其他事务没有针对这张表加过表级 X 锁、记录上也没有加过 X 锁"；表级的好判断，记录上的一多就得一行行遍历，性能极差。
    * 办法是当针对某一行加了 X 锁之后，数据库自动在这一行记录的上一层（比如数据页或数据表）加一把意向的 X 锁，于是这一行上实际出现了两把锁：行本身的 X 锁和自动补上的表级意向锁。
    * 别人想加全表排他锁时直接看表级有没有意向锁即可，不必逐行比较，这就是它让性能更好的地方。
    * InnoDB 允许行级锁和表级锁共存，所以意向锁不会使性能变低；正因为它存在，后续判断锁的行为性能反而更高。
    * > **定义**：意向锁是表级锁，它本身不锁任何记录，只用来说明这张表上已经有人对某些行加了 S 锁或 X 锁。

    ```text
    T1：select ... for update（命中 id = 6 这一行）
            ├─ 行级：排他锁 X  on  id = 6      ← 自己主动加
            └─ 表级：意向排他锁 IX              ← 自动补上

    T2：lock tables teacher read / write;
            │
            ▼
       只需要看表级有没有意向锁，不必逐行扫描
            │
            ├─ 表级已有 IX ──► IX 与表级 X、表级 S 都冲突 ──► 阻塞等待
            └─ T1 commit 之后，行级 X 与表级 IX 一起释放 ──► T2 加锁成功
    ```

* **意向共享锁（IS）与意向排他锁（IX）的生成方式**
    * 意向锁分两种：意向共享锁（Intention Shared Lock，简称意向共享锁 `IS`）和意向排他锁（Intention Exclusive Lock，`IX`）。
    * 要获取某些记录的共享锁，就在这个数据表上添加意向共享锁；要获取某些记录的排他锁，就添加意向排他锁；共享对应共享，排他对应排他。
    * 添加是自动的，不需要手动维护：自己针对某一行或某几行加什么锁，加完之后表级别会自动生成相应的意向锁。
    * `lock in share mode` 先对语句涉及到的数据加 S 锁（涉及三行就加三行），同时自动补一个意向共享锁；`for update` 针对这几条记录加排他锁，然后 InnoDB 自动加上表级别的意向排他锁。
    * 针对某一行或某几行加 S 锁或 X 锁要在事务里体现，必须先 `begin`；演示用的隔离级别是默认的可重复读。

* **意向锁的兼容关系与共存现象**
    * 意向锁虽然是表级的，但它刻画的其实是某一行或某几行的实际情况。
    * 表级 `S` 锁与 `IX` 冲突所以阻塞；加表级 `X` 锁也是一样的结果；如果其他事务加的只是表级 `S` 锁那就不冲突，`S` 跟 `S` 是兼容的。
    * 两个事务针对同一行 `id = 6` 都执行 `for update` 会阻塞，但这次的阻塞不是 `IX` 与 `IX` 造成的（这两个 `IX` 并不冲突），真正原因是两把行级 X 锁不兼容：同一行上不能同时存在两把排他锁。
    * 把条件改成 `id = 5` 就没事：两把 X 锁落在不同数据行上彼此没有冲突，各自带出来的表级 `IX` 之间同样没有冲突。
    * 行级 X 锁与表级 IX 一起释放：事务一提交，作用在这行数据上的 X 锁释放，相应的表级 IX 也跟着释放。
    * 汇总矩阵（行是请求加的锁，列是表上已经存在的锁）：

    | 请求加锁 ＼ 已有锁 | `X` | `IX` | `S` | `IS` |
    | :--- | :--- | :--- | :--- | :--- |
    | `X` | 冲突 | 冲突 | 冲突 | 冲突 |
    | `IX` | 冲突 | 兼容 | 冲突 | 兼容 |
    | `S` | 冲突 | 冲突 | 兼容 | 兼容 |
    | `IS` | 冲突 | 兼容 | 兼容 | 兼容 |

    * 意向锁之间（`IS` 与 `IS`、`IS` 与 `IX`、`IX` 与 `IX`）全部兼容；`IS` 除了与表级 `X` 锁冲突之外，跟表级 `S`、`IX` 都兼容；`IX` 与表级 `S`、表级 `X` 都冲突；表级 `X` 跟谁都冲突；表级 `S` 与表级 `S` 之间兼容。
    * 意向锁不会与行级锁发生冲突，只会与表级锁发生冲突；它存在的全部作用就是协调行锁和表锁的关系。
    * > **易错点**：如果 `IX` 之间互斥就麻烦了——只要表里有一把行级 X 锁，别的会话就再也加不上任何行锁，行级锁被硬生生拉成了表级锁。

* **自增锁（AUTO-INC Lock）**
    * > **定义**：自增锁是向包含 `AUTO_INCREMENT` 列的表插入数据时需要获取的一种特殊表级锁；一个事务持有自增锁期间，其他事务的插入语句都要被阻塞。
    * 它并不是针对某一特定行数据起作用，而是针对整张表起作用。
    * 要保证 `id` 字段赋的值必须是唯一的，最好还是单调递增的，因为顺序递增的取值对生成 B+ 树的结构有好处。
    * 代价很直接：向带 `AUTO_INCREMENT` 主键的表插入值时，每一条插入语句都要对这把表锁进行竞争，所以并发性比较低；并发低就可以设置不同的锁定机制，在一定程度上把并发性提上来。
    * 整体上了解即可，知道确实有这么一把表级别的锁就行。

* **插入数据的三种模式**
    * 三种模式的关键差别只有一个：这条语句在开始执行之前，到底知不知道要插入多少行。
    * 简单插入（simple inserts）：`INSERT ... VALUES`，一条记录也好、一个 `VALUES` 后面写多条记录也好，都算；能明确看到要插入的行数，也就是事先知道要占多少个自增值。
    * 批量插入（bulk inserts）：`INSERT ... SELECT ...`，一开始不知道能查出来几条数据，要插入的行数事先未知。
    * 混合模式（mixed-mode inserts）：列清单里写明了 `id`，`VALUES` 里有的行给了 ID 值、有的没给；同一条插入语句里两种赋值方式混着用。

    ```sql
    INSERT INTO t_autoinc (name) VALUES ('Tom');
    INSERT INTO t_autoinc (name) VALUES ('Tom'), ('Jerry');

    INSERT INTO t_autoinc (name)
    SELECT name FROM other_table WHERE ...;

    -- 列清单里写明了 id：显式给值的行不再自增，未给值的行仍由自增赋值
    INSERT INTO t_autoinc (id, name) VALUES (100, 'Tom'), (NULL, 'Jerry');
    ```


* **自增锁的三种锁定模式**
    * 自增锁的行为由系统变量 `innodb_autoinc_lock_mode` 切换，取值 `0`、`1`、`2` 分别对应三种模式。
    * 传统锁定模式（traditional，取值 `0`）：锁是表级别的，大家都去争抢，谁拿到谁操作；简单插入、批量插入、混合模式都得排在同一把表级锁后面。
    * 连续锁定模式（consecutive，取值 `1`）：8.0 之前默认的锁定模式。批量插入仍需要抢这把表级锁并长时间持有；简单插入因为事先知道要插多少条，抢到锁后一次性申请这批值（要插 10 条就申请 10 个值）并紧接着释放锁，然后自己慢慢插入。
    * 连续模式的前提是得先握到这把锁：如果批量插入的事务正握着 `AUTO-INC` 表级锁，简单插入也得等它释放、拿到锁之后才能一次性申请。
    * 交叉锁定模式（interleaved，取值 `2`）：8.0 引入，所有 `INSERT` 语句都不再使用表级的 `AUTO-INC` 锁，并发性大大提升。
    * 交叉模式下取值连续性松动：简单插入可以保证取值连续、没有间隙；混合模式、批量插入这两种都有可能存在间隙。
    * 三种模式的差异都集中在"还抢不抢那把表级锁"上：

    | 取值 | 模式 | 领值与持锁方式 | 并发性 |
    | :--- | :--- | :--- | :--- |
    | `0` | 传统锁定模式 | 所有插入都竞争表级 `AUTO-INC` 锁，谁拿到谁操作 | 比较差 |
    | `1` | 连续锁定模式 | 批量插入仍抢表级锁并握一段时间；简单插入拿到锁后一次性申请 N 个值并立即释放 | 比 `0` 好一点，整体仍不够 |
    | `2` | 交叉锁定模式 | 所有 `INSERT` 都不再使用表级 `AUTO-INC` 锁 | 大大提升 |

    ```text
    T1 简单插入（已知要插 10 行）
      [ 抢到 AUTO-INC 表锁 ] -> [ 一次性申请 10 个自增值 ] -> [ 立即释放锁 ] -> [ 自己慢慢插入 10 行 ]
                                                                       |
                                                                       v
    T2 批量插入（行数未知）                                   [ 这时才能抢到锁 ]
      [ 抢到 AUTO-INC 表锁 ] -> [ 逐个申请自增值并插入 ] -> [ 全部插完才释放 ]
    ```

    * > **易错点**：间隙不是"少赋了值"，而是同一批插入里自增值可能被其他事务的取值穿插开；它在单机上看不出问题，但在主从复制时会出事——`binlog` 文件当中涉及的主键值可能出现不安全的问题。

* **元数据锁（Metadata Lock，MDL）**
    * > **定义**：元数据锁是 MySQL 用来保护表结构不被并发修改破坏的表级锁——普通增删改查持 MDL 读锁，表结构变更持 MDL 写锁。
    * 它是针对 DDL 操作、在 server 层加上的表级锁；做增删改查加 MDL 读锁，`ALTER`、`DROP` 之类的表结构变更加 MDL 写锁。
    * 阻塞是双向的：一个事务正在做 DDL，另一个事务想增删改查就得等；反过来正在增删改查时执行 DDL 也得等——DDL 一旦成功，同一个事务里第一次查完的表结构和后面查完的表结构就不一样了。
    * 这个锁不需要显式添加，只要做操作就会自动加上。
    * 两种 MDL 的兼容关系：读锁与读锁之间不互斥、可以两个同时读；只要有写锁存在，那就不能去读，别的这个事务也不能再去写。

    | 已持有 \ 新请求 | MDL 读锁 | MDL 写锁 |
    | :--- | :--- | :--- |
    | MDL 读锁 | 兼容，可并发 | 冲突，阻塞 |
    | MDL 写锁 | 冲突，阻塞 | 冲突，阻塞 |

    * 触发场景：`BEGIN; SELECT * FROM teacher;` 自动加上 MDL 读锁，事务不提交则读锁一直被持有；此时另一会话执行 `ALTER TABLE teacher ADD age INT;` 需要 MDL 写锁，读写冲突就阻塞住。
    * 用 `SHOW PROCESSLIST;` 能看到那条 `ALTER TABLE` 语句的状态是 `Waiting for table metadata lock`。
    * 写锁排队会阻塞后续读锁：A 持读锁未释放，B 的写锁卡在 A 后面等待；C 的新读锁虽然与 A 的读锁兼容，却必须排在 B 的写锁之后，于是本来可以并发的两个读现在都过不去了。
    * > **易错点**：从 MDL 这个锁的级别来谈，读锁与读锁之间可以不互斥；真正增删改时另一个增删改不能同时执行、处于阻塞状态，那不是 MDL 导致的，而是相应的行级别 X 锁和 S 锁导致的。

    ```text
    [会话 A] BEGIN; SELECT * FROM teacher;
             └─ 自动加 MDL 读锁，事务不提交 -> 读锁一直被持有
    [会话 B] ALTER TABLE teacher ADD age INT;
             └─ 需要 MDL 写锁 -> 与 A 的读锁冲突 -> 阻塞（Waiting for table metadata lock）
    [会话 C] BEGIN; SELECT * FROM teacher;
             └─ 需要 MDL 读锁 -> 本与 A 的读锁兼容，但要排在 B 的写锁之后 -> 也阻塞
    ```

## 行级锁

* **记录锁（Record Lock）**
    * 行锁是在存储引擎层实现的，加锁对象是表里的一行记录，也叫记录锁，因为一行数据本来就是一条记录；MyISAM 不支持行锁，所以行锁全部是针对 InnoDB 的。
    * 优点：粒度更细更小，能实现的并发度更高、锁冲突概率更低。缺点：粒度小意味着同样一笔业务要维护的锁可能更多，加锁更慢、开销更大；并且行锁还会出现死锁问题。
    * 加锁到具体一条记录上时，锁信息里写的是 `not gap`，意思就是针对这一条数据本身加的锁而不是间隙锁。
    * 记录锁同样分 S 型与 X 型，规则与表级 S 锁、X 锁完全一样：拿到 S 型记录锁后其他事务再来拿 S 型没有影响、不可以再获取 X 型；拿到 X 型记录锁后其他事务既不能再拿共享型也不能再拿排他型。
    * 记录锁的互斥只发生在同一条记录上，针对不同的记录各加各的锁互不冲突，这就是行级锁并发度高的来源。
    * > **易错点**：不同记录之间互不冲突，同一条记录上就按 S/X 的规则来；把条件从 `id = 1` 换成 `id = 3` 就能直接成功执行。

    | 已经持有 | 别人再请求 S 记录锁 | 别人再请求 X 记录锁 |
    | :--- | :--- | :--- |
    | S 记录锁 | 相容，可以拿到 | 冲突，拿不到 |
    | X 记录锁 | 冲突，拿不到 | 冲突，拿不到 |

    | 对比项 | 表锁 | 行锁（记录锁） |
    | :--- | :--- | :--- |
    | 加锁对象 | 整张表 | 表里的一行记录 |
    | 支持引擎 | MyISAM、InnoDB 都支持 | 只有 InnoDB |
    | 锁粒度 | 大 | 最小 |
    | 并发度 | 低，锁冲突概率高 | 高，锁冲突概率低 |
    | 锁开销 | 相对小 | 相对大，加锁更慢 |
    | 死锁 | 不会出现 | 可能出现 |

* **间隙锁（Gap Lock）的加锁区间**
    * 幻读一开始没有记录、别人插进来以后才有记录，加锁没有东西可加；思路是绕开这条不存在的记录、去锁它所在的空档，这就是间隙锁。
    * 记录锁锁的是那一条数据，间隙锁锁的是那条数据旁边的间隙。
    * 间隙锁锁住的是记录之间的**开区间**：表中有 1、3、8、15、20 时，条件值落在 3 与 8 之间就锁住 $(3,8)$，区间之内不允许插入数据，3 和 8 这两条记录本身不在被锁范围内。
    * gap 锁仅仅是为防止插入幻影记录而生的，它锁住的只是插入，全部价值就在这一条上。
    * 共享的 gap 锁和独占的 gap 锁没有区别：它针对的既不是这条数据的读也不是写，而是区间中间的 insert 行为，所以 S 型与 X 型作用完全相同。
    * 间隙锁可以多次加，也可以共存：两个事务各自在同一个间隙上加 S 型与 X 型间隙锁都不冲突不阻塞。
    * 判断锁住哪一段只看条件值落在哪两条现有记录之间，与这个值本身在不在表中无关（`id = 5`、`6`、`7` 效果一样）。

    | `where` 里的条件值 | 落在哪两条记录之间 | 被锁住的区间 | 区间内不允许 `insert` 的值 |
    | :--- | :--- | :--- | :--- |
    | `id = 5` | 3 与 8 | $(3, 8)$ | 4、5、6、7 |
    | `id = 12` | 8 与 15 | $(8, 15)$ | 9 ~ 14 |
    | `id = 25` | 20 之后 | $(20, +\infty)$ | 21 及更大的值 |

    ```text
       id=1      id=3                       id=8      id=15     id=20
                   |                          |
                   +===== 开区间 (3, 8) ======+
                      不允许 insert 4、5、6、7
    ```

    * > **易错点**：间隙锁锁住的是记录之间的开区间，区间两端那两条记录本身不在锁的范围里；写成 `where id > 20` 与写一个比最大值还大的值效果一致。

* **最大记录之后的区间与 `supremum` 伪记录**
    * 条件值比表中最大值还大时，坐落的区间就是从最大值起一直到正无穷，最大值成了这个区间的下界。
    * 一个页里除真实记录外，前面有 `infimum` 指向最小的那条记录，最大值之后指向的是 `supremum`，相当于页里最大值的那条记录。
    * 条件值落在最大记录之后时，间隙锁就加在 `supremum` 这个伪记录上。
    * 落在最大值之前的值不受影响：`id = 17` 落在 15 和 20 之间，根本不在被锁的区间里，可以插入。

    ```text
    infimum -> id=1 -> id=3 -> id=8 -> id=15 -> id=20 -> supremum
                                                              |
                                        间隙锁挂在这里，范围 (20, +∞)
    ```


* **临键锁（Next-Key Lock）**
    * > **定义**：临键锁相当于记录锁与间隙锁的合体，既体现记录锁的作用，又体现间隙锁的作用。
    * 官方名称是 `Lock Ordinary`，简称 `Next-Key Lock`；官方定义是：有的时候既想锁住某条记录，又想阻止其他事务在该记录前面的间隙插入新记录，这个时候用的锁就叫 `Next-Key Locks`。
    * 构造方式：`select * from student where id <= 15 and id > 8 for update;`——对 `15` 来说条件里带了等号，相当于在 `15` 这条记录上加了一把记录锁；对 $(8,15)$ 这个开区间来说里面没有任何一行满足条件，加上的就是间隙锁；一条范围查询语句就同时产生了两种锁。
    * 关键点：`id` 的条件不能写成小于边界值，必须写成小于等于，只有带上等于号边界值才会落在 `where` 条件里从而在它上面加上记录锁。
    * 临键锁是 InnoDB 在可重复读隔离级别下使用的锁，InnoDB 默认使用的就是 `Next-Key Locks`；这也解释了为什么记录锁、间隙锁两种效果都能演示出来。
    * > **易错点**：所谓闭区间不是"允许你插入一条值为 8 的记录"，也不是"值等于 8 的记录不能被插入"；它指的是间隙锁影响的仍然是那个开区间，而边界上的这条记录本身也要被锁住。

    | 验证动作 | 请求的锁 | 结果 | 体现的是临键锁的哪一部分 |
    | :--- | :--- | :--- | :--- |
    | `select ... where id = 15 lock in share mode` | `S` 锁（对边界记录 `15`） | 阻塞 | 记录锁 |
    | `select ... where id = 15 for update` | `X` 锁（对边界记录 `15`） | 阻塞 | 记录锁 |
    | `insert ... values (12, ...)` | 插入意向锁（针对间隙 `(8, 15)`） | 阻塞 | 间隙锁 |

* **插入意向锁（Insert Intention Lock）**
    * > **定义**：等待插入的事务在内存中生成的那个锁结构表达的就是"我有插入的意图"，所以叫插入意向锁。
    * InnoDB 规定事务在等待的时候也需要在内存中生成一个锁结构，用来表明有事务想在某个间隙里插入一条新记录，只不过现在处于等待状态。
    * 引入它的目的：一旦左边那把间隙锁释放掉，这个插入意向锁就有机会进入执行状态，等待中的 `insert` 操作就能真正执行下去。
    * 两个插入意向锁之间兼容，因为它们要插入的具体值不一样（一个是 `11`、一个是 `12`）；阻塞它们的自始至终是那把间隙锁而不是彼此，间隙锁一释放两个都放行。
    * 官方也提到：插入意向锁并不会阻止别的事务继续获取该记录上的任何类型的锁。
    * > **易错点**：插入意向锁不是一个意向锁。它名字里带着"意向"两个字，但意向锁是表级锁，而插入意向锁是针对具体的这几行数据做的行为，它是一把 `gap` 锁、属于行级锁。

    ```text
    记录         5        8        11  12          15
                       |         ^    ^           |
                       |         |    |           |
                  [ 事务1：间隙锁 (8,15) ]         |
                       |         |    |           |
                       |    事务2:插入意向(11)  事务3:插入意向(12)
                       |         |    |           |
                       |      等待 |    | 等待      |
                       |         |    |           |
               事务1 COMMIT → 间隙锁释放           |
                       |         |    |           |
                       +---------+----+-----------+
                                 |    |
                             授权执行 授权执行
    ```

    | 锁 | 级别 | 锁住的对象 | 主要影响的操作 |
    | :--- | :--- | :--- | :--- |
    | 记录锁（Record Lock） | 行级 | 索引上的一条记录 | 别的事务在该记录上加 `S` 锁／`X` 锁 |
    | 间隙锁（Gap Lock） | 行级 | 两条记录之间的开区间 | 别的事务往该间隙里 `insert` |
    | 临键锁（Next-Key Lock） | 行级 | 记录锁 + 它前面的间隙锁 | 上面两种同时被影响 |
    | 插入意向锁（Insert Intention Lock） | 行级（`gap` 锁） | 等待插入的那个间隙 | 表达插入意图，本身不阻止别人加锁 |
    | 意向锁（Intention Lock） | 表级 | 表 | 与表级锁配合，不是行级锁 |

* **间隙锁引发的死锁**
    * 两个事务都执行 `select * from student where id = 5 for update;`，等于各自在 $(3,8)$ 上挂了一把间隙锁，两把锁都加上了谁也影响不到谁。
    * 接着两个事务各自插入落在 $(3,8)$ 里的记录（写 7 或写 6 都行），第一条 `insert` 阻塞在等对方释放间隙锁；第二条 `insert` 一并，就报出 `ERROR: Deadlock found when trying to get lock; try restarting transaction`。
    * 要解开这个结必须让其中一个事务的间隙锁释放，也就是它得先 `commit` 或者 `rollback`；可它正卡在 `insert` 上根本没法往下执行。
    * MySQL 对死锁的处理有两种策略：进入等待状态直到超时为止；或做死锁检测，发现死锁后主动回滚锁链条中持有行级排他锁最少、也就是成本最低的那个事务。
    * 演示中报出死锁的那个事务没有僵住，另一个事务的 `insert` 竟然执行成功了，就是因为持有间隙锁的那个事务被做了回滚，锁一释放另一边自然就能插进去。
    * 只要行级锁都有可能死锁，不是只有间隙锁才会；表锁是不会出现死锁的。

    ```text
    事务 A                                    事务 B
      |                                         |
      |--- gap 锁 (3, 8) ---------------------->|  间隙锁可共存，两把都加上
      |                                         |--- gap 锁 (3, 8)
      |                                         |
      |                                         |--- insert id=7
      |                                         |      阻塞：等 A 的 (3,8) 释放
      |--- insert id=6                          |
      |      冲突：等 B 的 (3,8) 释放 <---------|
      |                                         |
      +------------ 互相等待，扣成死结 ---------+
    ```

## 页级锁与锁升级

* **页锁（Page Lock）**
    * 一张数据表里的数据通常不会堆在一起，而是放在多个数据页（data page）当中，一个页里又放多行数据；页锁锁的就是一个数据页。
    * 粒度位置决定它表现出来的特性也在两者之间：加锁开销介于表锁和行锁之间，并发性同样介于这两者之间。

    | 对比项 | 表锁 | 页锁 | 行锁 |
    | :--- | :--- | :--- | :--- |
    | 锁定粒度 | 整张表 | 一个数据页（页内含多行） | 一行记录 |
    | 加锁开销 | 最小 | 介于两者之间 | 最大 |
    | 并发性 | 最低 | 介于两者之间 | 最高 |

    * 实际开发按存储引擎来定：InnoDB 这一侧一般选它的行锁，MyISAM 不支持行锁就只能做表级别的锁定；依据就是表锁开销小并发差、行锁开销大并发好。

* **页锁层面的死锁**
    * 行锁会出现死锁，页锁一样会出现死锁，原因还是加锁顺序相反。
    * 事务 A 先锁定一个数据页（锁住页里的一行，或者整个数据页），接着再去锁第二个页；事务 B 跟它反着来，先锁 A 想要的第二个页，再去锁 A 已经持有的那个页。
    * 结果 A 卡在第二个页上等 B 解锁，B 卡在第一个页上等 A 解锁，两边都在等对方先放手，谁也走不下去。

    ```text
    时间线    事务 A                          事务 B
      t1      锁定数据页 1                     —
      t2      —                                锁定数据页 2
      t3      请求锁定数据页 2 → 等 B 释放      —
      t4      —                                请求锁定数据页 1 → 等 A 释放
      t5      双方互相等待，事务都无法继续 → 死锁成立
    ```


* **锁空间与自动锁升级**
    * 每一个层级——表锁、行锁、页锁——能加的锁的数量都是有限的，因为锁本身要占据内存空间，锁空间的大小有上限。
    * 某个层级上的锁数量超过这个层级的阈值限制时，数据库会自动进行锁升级，不需要手动去改。
    * 行锁层级的数量一旦越过阈值，InnoDB 里的行锁就可能被升级成表锁；升级后首先占用的锁空间降下来了，其次并发性也跟着降下来了。
    * > **易错点**：锁升级本质上是拿并发性换空间；一般情况下不会把锁空间用超，但在极端情况下确实有这个风险。

## 悲观锁与乐观锁

* **悲观锁（Pessimistic Lock）**
    * > **定义**：悲观锁对"数据被其他事务修改"这件事持保守态度，总是假设最坏的情况，每次去拿数据都认为别人会修改，所以每次拿数据都先上锁。
    * 共享资源每次只给一个线程使用，其它线程阻塞，用完以后再把资源转给其它的线程，这是典型的独占锁思路。
    * 悲观锁是一种设计思想，这种思想在 MySQL 里的具体体现就是使用数据库自身的锁机制，也就是表锁、行锁以及 X 锁、S 锁这些锁；在 Java 里对应 `synchronized` 和 `ReentrantLock`。
    * 代价是并发性会比较差，换回来的是数据安全性有很好的保障。
    * `SELECT ... FOR UPDATE` 就是 MySQL 中悲观锁最典型的用法。
    * 适用场景其实不是特别多，因为它用数据库的锁机制实现，并发性比较差；尤其是长事务，数据被锁住、事务本身还特别长，其它并发事务都得等着，业务上无法承受。它适合写操作比较多的场景。

* **悲观锁下的秒杀超卖演示**
    * 商品表用 `quantity` 字段表示库存量，以商品 ID 1001 为例，这次秒杀放出来的量是 100 台。
    * 不加锁的流程：先查询库存发现还有 100 台，接着根据 ID 生成订单，订单生成之后再按购买数量冲减库存；并发量小的时候没有问题。
    * 秒杀场景下事务 A 和事务 B 都查到 100 台，都生成订单，各自要买 60 台，冲减完就是 $100 - 60 - 60 = -20$，出现超卖。
    * 解法是保证一个事务把查询、生成订单、减库存这一整套动作都执行完，然后才让其它线程进来执行。

    ```sql
    -- 查询库存的同时就加上锁；这里的表名按你自己的库替换
    SELECT quantity
    FROM 商品表
    WHERE id = 1001
    FOR UPDATE;
    ```


* **`FOR UPDATE` 的加锁范围与索引的关系**
    * `SELECT ... FOR UPDATE` 在执行过程中会把所有扫描到的行都加上锁，而不只是条件匹配上的那一行。
    * ID 上有索引（比如它本身就是主键）：InnoDB 顺着 B+ 树一直往下找，直接定位到 `id = 1001` 这条数据并把它锁住，锁的力度比较小，`id = 1002` 那条记录不受影响。
    * ID 上没有索引：只能从表里一条一条去检索，检索到 1001 的时候前面扫过的数据也已经被加锁了，因为它并不确定你要操作哪些数据，所以会把扫描到的数据全部加锁，影响别的事务操作那些本来不相干的数据。
    * 写这类语句要根据过滤条件适当地设计索引，而且要让查询优化器真的用上索引。

* **乐观锁（Optimistic Lock）**
    * > **定义**：乐观锁是在程序层面实现的并发控制，它没有采用数据库自身的锁机制，对"一条数据被多个事务操作"这件事比较乐观，认为并发问题会少一些。
    * 适用场景是读操作比较多、改操作相对比较少：读和读本来就不会有并发问题，但真正操作这些数据的事务改的情况也得少一点，改得特别多就得悲观一点了。
    * 两种态度没有谁取代谁的关系，两者有不同的适用场景。
    * 程序层面的常见做法是版本号机制，或者 CAS（Compare And Swap，比较并交换）机制；落到更新操作上有两种实现机制：版本号机制和时间戳机制。
    * 乐观锁适合读多的场景，因为它是用程序实现的，因此不存在死锁的问题。

* **版本号机制**
    * 给表设计一个版本字段（比如叫 `version`），读的时候把它读出来，写的时候拿它当条件。
    * 事务 A 先读这条数据、`version` 是 1，做 `UPDATE` 时一定要找 `version` 等于 1 的那条数据；找到了就说明这个期间没有别的事务修改过它，修改完把 `version` 从 1 改成 2。
    * 版本号让查询和修改这两个行为在效果上具备了原子性——在这个期间没有别人操作过这条具体的数据。
    * 版本不匹配就是更新失败：事务 A 与 B 都读到 `version = 1`，B 改完 `version` 变成 2，A 再去找 `WHERE version = 1` 的数据已经找不到了，说明 A 要修改的记录已经不是它当初查出来的那条数据；没改成就要自己再查一次，基于新的版本号重新考虑怎么改。
    * 这套思路和版本控制工具 SVN、CVS 的设计一样：检查当前代码的版本号和服务器上的是否一致，一致就提交，不一致就先更新再改、再提交。

    ```sql
    UPDATE 商品表
    SET quantity = quantity - 60,
        version  = version + 1
    WHERE id = 1001
      AND version = 1;
    ```

    ```text
    事务 A    读数据 → version = 1
                │
                └─→ UPDATE ... WHERE id = 1001 AND version = 1
                        │
                        ├─ 命中 version = 1：期间没人改过 → 更新成功，version 变成 2
                        └─ 未命中：version 已经变成 2 → 本次更新失败
    ```


* **时间戳机制**
    * 原理和版本号机制一样，只不过用的不是版本号而是时间戳：如果当前数据的时间戳跟更新之前取到的那个时间戳一样，就能更新成功，否则就出现版本冲突。
    * 这里的时间戳作用就相当于版本号里的 `version`。

* **读写分离下的版本号一致性问题**
    * 读写分离的原理是查的时候用从机，而修改行为用主机；从机查出来的 `version` 与主机上的 `version` 可能因为主从同步的问题而对不上，匹配不上就会导致这次更新失败。
    * 解法是必须保证查询行为也走主机，也就是强制从 master 读；因为修改肯定走主机，查也用主机，`version` 与 `version` 的比较才能不受主从复制的干扰。

    ```text
       应用
        │
        ├── 读：SELECT quantity, version ──→ 从机（复制有延迟，version 可能还是 1）
        │
        └── 写：UPDATE ... WHERE version = 1 ──→ 主机（真实 version 已经是 2）
                                                  → 匹配不上，更新失败
    ```


* **热点数据频繁修改时的兜底条件**
    * 多个事务频繁针对同一条数据修改时，大家读到的都是 1，其中一个改成 2 之后，其它基于 1 去改的事务全都改失败，业务层面会出现大量失败。
    * 兜底做法是确保 `quantity - number` 大于 0、不要出现超卖场景：这样后面买不到的人就是真实地发现库存已经没有了，而只要库存还有就可以正常冲减。

    ```sql
    UPDATE 商品表
    SET quantity = quantity - 60
    WHERE id = 1001
      AND quantity - 60 > 0;
    ```


* **两种态度的对比**

    | 对比项 | 悲观锁 | 乐观锁 |
    | :--- | :--- | :--- |
    | 对并发的假设 | 总假设最坏情况，认为别人一定会改 | 认为并发冲突比较少 |
    | 实现位置 | 数据库自身的锁机制：表锁、行锁、X 锁、S 锁 | 程序层面：版本号、时间戳、CAS |
    | 适用场景 | 写操作比较多 | 读比较多、改比较少 |
    | 并发性 | 比较差 | 比较好 |
    | 死锁 | 可能在行锁、页锁层面出现 | 不存在死锁 |
    | 冲突时的表现 | 其它事务阻塞等待 | 更新失败、版本冲突，由业务重读后重试 |

    * 悲观锁是拿"让别人等"换安全，适合写多的场景；乐观锁是拿"失败后重试"换并发，适合读多改少的场景。
    * 两条线索不要混在一起：按操作数据的粒度分得到表锁、行锁、页锁，那是实操时真正加锁的行为；按对待锁的态度分得到乐观锁和悲观锁，那是锁的设计思想。

## 加锁方式：隐式锁与显式锁

* **显式锁（Explicit Lock）与隐式锁（Implicit Lock）**
    * > **定义**：按加锁方式划分，凡是在锁信息里能直接查看到的锁叫显式锁；不直接暴露在锁信息中、由 InnoDB 隐式维护的锁叫隐式锁。
    * 隐式锁主要针对的是事务当中的 `insert`；但并不是事务里的 `insert` 都叫隐式锁。
    * 凡是能通过指令查看到的锁都算显式锁，比如 `lock in share mode` 的 S 锁，或者 `for update` 的排他锁 X 锁。

* **隐式锁与插入意向锁的边界**
    * 讲读锁、写锁时提到的写操作里，"增"就是 `insert`，当时给的结论是一般情况下新插入一条记录不需要加锁，但又会通过一个叫隐式锁的结构对这条数据做保护。
    * 讲插入意向锁时提到的 `insert` 是另一个场景：针对 `3` 到 `8` 的范围加了 gap 锁（临键锁则把 `8` 这条记录也包含进来），在这个区间范围内 `insert` 一条记录，此时针对这条新插入的记录会加一个插入意向锁。
    * 关键差别在"被动"两个字：是人家先有了间隙锁、你这会儿想插进去，才出现插入意向锁；而隐式锁讲的是主动插入，对应位置上并没有间隙锁或者临键锁存在。
    * 一句话区分：插入意向锁是"别人锁住了区间，我要往里插"，隐式锁是"我插进去了还没提交，别人要来动我"。

    | 对比项 | 隐式锁 | 插入意向锁 |
    | :--- | :--- | :--- |
    | 对应行为 | 事务中主动 `insert` 一条新记录 | 在已被间隙锁/临键锁覆盖的区间内 `insert` |
    | 成立前提 | 插入位置上不存在间隙锁或临键锁 | 该区间上先有了间隙锁或临键锁 |
    | 出现方式 | 别的事务来访问时，替插入方构建出来 | 插入动作发生时即申请 |


* **隐式锁的场景一：事务 2 从聚簇索引找到这条记录**
    * 事务 1 插入的记录会落在聚簇索引叶子节点的某个页中；行格式里有三个隐藏列 `row_id`、`transaction_id` 以及回滚指针，其中 `transaction_id` 上记录的就是插入它的事务 1。
    * 官方对隐式锁的解释落在这一点上：这条记录上有一个隐式的列，只要这个列（`transaction_id`）记录的是事务 1，就把这儿当成一个隐式锁；这个"锁"用查看锁信息的指令是看不到的。
    * 事务 2 进来后，不管要做的是读还是写，第一步都要先发现插入这条记录的事务是不是还活跃；还活跃就不能操作。
    * 反直觉的地方是：事务 2 会反过来帮事务 1 构建一个锁结构，替事务 1 那侧把 `is_waiting` 置为 `false`（人家还活跃、这条记录还占着），再给自己提供一个锁结构并把 `is_waiting` 改成 `true`（自己先阻塞等着）。
    * 事务 2 来操作时事务 1 已经提交，那就不用等直接改；事务 1 后期结束了，事务 2 就把自己的 `is_waiting` 改成 `false`，也就可以去操作这条记录了。
    * 事务 2 要读事务 1 未提交的记录就是脏读，要改它相当于加 X 锁就是脏写，隐式锁把这两种并发访问限制住了。

    ```text
    事务 1（insert 记录 1，尚未提交）        事务 2（要读或要写记录 1）
          │                                        │
          │  transaction_id = 事务 1               │  发现事务 1 仍然活跃
          │  （记录上并不挂任何锁结构）             │
          │                                        ├─ 替事务 1 建锁结构：is_waiting = false
          │                                        └─ 给自己建锁结构：is_waiting = true（阻塞等待）
          │
       commit / rollback
          │
          └──────────► 事务 2 把自己的 is_waiting 改成 false，随即操作记录 1
    ```


* **隐式锁的场景二：事务 2 从二级索引找到这条记录**
    * 完整的行记录只存在于聚簇索引的叶子节点中，二级索引里并没有这条记录的完整记录信息，也就意味着二级索引上没有 `transaction_id` 可用。
    * > **定义**：`PAGE_MAX_TRX_ID` 仅在二级索引的页中定义，位于 `PAGE_HEADER` 中，记录的是修改当前页的最大的事务 ID。
    * 事务 1 在这个页里插入一条数据，不管事务 1 结束没结束，事务 1 都会被记录在这个页的这个属性里。
    * 事务 2 进来时拿自己的事务 ID 跟页里这个属性的值作比较：页里这个值更小，说明之前修改这个页的事务都已经提交过了，可以直接去操作；不满足这个条件，说明事务 1 还没有结束。
    * 判断"值更小就意味着都提交过了"的依据是事务 ID 递增分配：页里记的最大事务 ID 比事务 2 自己的 ID 还小，说明改动过这个页的事务都排在事务 2 之前，也就都已经提交完了。
    * 不满足条件时，通过二级索引找到对应的主键索引、回到聚簇索引里，按 `transaction_id` 那一套去处理，也就是回到场景一。
    * > **易错点**：二级索引页上没有 `transaction_id`，不能像场景一那样去看"记录上挂着哪个事务"，场景二必须先读 `PAGE_MAX_TRX_ID` 做一次判断。

    | 对比项 | 场景一：事务 2 走聚簇索引 | 场景二：事务 2 走二级索引 |
    | :--- | :--- | :--- |
    | 判断依据 | 行记录上的 `transaction_id` | 页头 `PAGE_HEADER` 里的 `PAGE_MAX_TRX_ID` |
    | 怎么判断插入方是否活跃 | 看 `transaction_id` 上记的那个事务还活不活跃 | 拿自己的事务 ID 与页里的最大事务 ID 比大小 |
    | 判定活跃之后 | 替对方建锁结构，自己 `is_waiting = true` 等着 | 先回表到聚簇索引，再按场景一处理 |

    ```text
    事务 2 通过二级索引找到这条记录
            │
            ▼
    读二级索引页 PAGE_HEADER.PAGE_MAX_TRX_ID
            │
            ├─ 该值比事务 2 的 ID 小 ──► 之前的事务都已提交 ──► 直接操作
            │
            └─ 否则 ──► 事务 1 尚未结束
                         │
                         ▼
                 用二级索引记录里的主键回表
                         │
                         ▼
             到聚簇索引按 transaction_id 处理（场景一）
    ```

* **隐式锁的两个性质**
    * 第一，隐式锁在内存中实际上并不含有锁信息——因为它是隐式的，用查看锁信息的指令去看是看不到的。
    * 第二，隐式锁是一种延迟加载的机制：本来记录上什么都不带，是因为有另外一个事务去访问，这个锁才出现，所以可以理解成延迟加载、延迟加锁的方式。
    * 事务 2 的访问导致隐式锁出现，而它一出现其实也就变成一个显式锁了，这时候通过指令就能查看到它。
    * 演示验证：事务 1 `insert` 一条记录后不提交，另一个会话查看锁信息时没有任何锁出现；该会话再执行 `select * from student lock in share mode;` 会直接阻塞，此时再查看锁信息就能看到它。
    * 开发当中接触隐式锁的机会比较小。

## 全局锁与死锁

* **全局锁（Global Lock）**
    * > **定义**：全局锁是加在整个数据库实例上的锁；加锁之后，这个实例下所有的数据库、所有的表全部只能处于只读状态。
    * 只读意味着别的事务过来可以读，但一定不能更新：DML（Data Manipulation Language，数据操纵语言）里的增删改（`INSERT`、`UPDATE`、`DELETE`）不能做；DDL（Data Definition Language，数据定义语言）也不能做，建表、`ALTER TABLE`、`DROP TABLE` 全在禁止之列；乃至其他任何更新行为同样不能做。
    * 典型使用场景是做全库的逻辑备份：备份过程当中数据不能再被修改，只能读，中途让人改掉了备出来的就对不上了。
    * 它的粒度肯定是最粗的，比表级别的锁还要粗；粒度越粗能并发的操作就越少，所以这种场景出现的次数必然比较少。

    ```text
    正常实例（可读、可写）
            |
            | 加全局锁
            v
    只读状态：实例下所有数据库、所有表
            |  允许：读取操作
            |  禁止：INSERT / UPDATE / DELETE（DML 增删改）
            |  禁止：建表 / ALTER TABLE / DROP TABLE（DDL）
            |
            | 释放全局锁
            v
    正常实例（可读、可写）
    ```

* **死锁（Deadlock）的定义与必要条件**
    * > **定义**：两个事务都持有对方需要的锁，并且在等待对方释放，同时自己又不释放自己手里的锁，互相僵持下去，就构成了死锁。
    * 数据库事务里的死锁原理跟线程里的死锁完全一样，只是习惯上把"线程"这个词换成了"事务"；事务本身也是在线程里执行起来的。
    * 构成死锁的必要条件：至少要有两个事务（或 session 会话）参与；每个事务自己已经持有锁，同时还在申请新的锁；它申请的这个新锁恰好被对面的另一个事务持有；锁资源只能被一个事务持有和操作；事务之间因为持有锁和申请锁彼此构成循环等待。
    * 死锁的关键是两个以上事务（或 session 会话）加锁的顺序不一致。
    * 第一个例子：事务一针对 `account` 表里 ID 为 1 的数据获取 X 锁，事务二针对 ID 为 2 的数据也获取 X 锁；事务一又试图针对 ID 为 2 获取排他锁只能等待；事务二接下来操作的恰恰是 ID 为 1，于是它也进入等待，死锁构成。
    * 第二个例子：用户 A 给用户 B 转 100 块钱，与此同时 B 也给 A 转 100 块，这个过程**有可能**出现死锁（不是一定会）。
    * > **易错点**：死锁至少要有两个事务；单个事务自己加锁、自己等待，锁不出死锁来。

    ```text
    +----------+                    +----------+
    |事务一 T1 |  ------ 等待 -----> |事务二 T2 |
    |持有 A 锁 |  <----- 等待 ------ |持有 B 锁 |
    +----------+                    +----------+
    ```

* **加锁顺序一致即可避免死锁**
    * 如果事务二不是"先减 B、再给 A 加钱"，而是把这两条语句颠倒一下、上来先给 A 加钱，两个事务就不会构成死锁。
    * 因为它们访问 A 和 B 这两个共享资源的顺序是一样的：谁先把 A 的锁拿到手，谁就能一路把 A、B 都走完，另一个老老实实在 A 这里等着，等待关系接不成环。
    * 这本身就是一个解决死锁的措施：把相关的 SQL 改成获取锁的顺序一致。
    * 双向转账复现用的表是 `account`，让 ID 为 1 和 ID 为 3 两位互相转账 10 块钱；第二个事务给 ID 为 1 加 10 块钱的那条 `UPDATE` 一走，死锁就出现了，报错信息里带着 `restarting transaction` 这样的字样。
    * 演示时要抓紧操作：等待是有时限的，默认时间一过事务就会被自动回滚结束。

    ```text
    T1: BEGIN
    T1: UPDATE id=1 (-10)   -> 成功，持有 id=1 的排他锁
    T2: BEGIN
    T2: UPDATE id=3 (-10)   -> 成功，持有 id=3 的排他锁
    T1: UPDATE id=3 (+10)   -> 等待（id=3 的锁在 T2 手上）
    T2: UPDATE id=1 (+10)   -> 死锁被检测到，等待关系接成环
    引擎回滚代价较小的一方 -> 它持有的锁被释放 -> 另一方等待结束，语句执行成功
    ```

* **处理方案之一：锁等待超时**
    * 参数 `innodb_lock_wait_timeout` 默认值是 50 秒，含义是锁等待超过 50 秒事务会自动回滚；用 `SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';` 可以确认。
    * 这个机制并不只对死锁生效：如果压根不是死锁、只是单纯地在等锁，超过 50 秒等待也一样会被自动回滚。
    * 毛病很明显：50 秒挺长，实际项目里可能同时出现多个死锁、互相交织在一起。
    * 把值改小（改成 1 秒甚至 0.1 秒）理论上能解决死锁，但会误伤正常等待：那个不是死锁、只是正常排队的等待，等满 1 秒事务立马就被回滚了。
    * > **易错点**：`innodb_lock_wait_timeout` 管的是"等锁最多等多久"，不是"死锁最多等多久"；到点被回滚的可能是死锁里的一方，也可能只是一个正常等待的事务。

* **处理方案之二：`wait-for graph` 死锁检测**
    * 这套检测用的是 `wait-for graph`（等待图）算法，是一种主动检测行为，也是演示里一构成死锁就立刻报出信息的原因——根本不用等 50 秒。
    * 等待图的构造依赖两张表：事务等待链表记录当前有哪些事务处于等待状态；锁的信息列表记录每条数据上锁的持有与申请情况。
    * 构图规则：节点就是事务等待链表里那几个处于等待状态的事务；边是一条等待关系，`Ti -> Tj` 表示 Ti 正在等待 Tj 释放锁。
    * 等待图里只要有环就是死锁；没有环，等待关系迟早能排出一个先后次序，等待就只是等待。
    * 一旦检测到死锁，InnoDB 会选择回滚 **undo 量最小**的那个事务：事务改动得越少，undo 记录越少，回滚代价就越低。
    * 一个事务一回滚，它持有的锁就释放了，环随之断开，其他事务立刻就能正常往下执行。
    * 这套检测由一个参数控制，它默认是 `on`；只有它是打开的，这种主动检测的方式才生效。

    ```text
    节点：T1、T2、T3、T4（均处于等待状态）

    等待边：
      T1 ----> T2     T1 等待 T2
      T2 ----> T1     T2 等待 T1       <- 与上一条首尾相接，环在这里闭合
      T2 ----> T4     T2 等待 T4
      T3 ----> T1     T3 等待 T1
      T3 ----> T4     T3 等待 T4
      T3 ----> T2     T3 等待 T2
      T4 --x-> T1     T4 与 T1 之间是共享关系，互相兼容，不构成等待
    ```

* **死锁检测的开销与并发控制**
    * 并发线程一多代价就上来了：100 个并发线程要更新同一行数据、都得等待，引擎就得为它们画等待图，每个线程都要和其他线程逐一判断有没有等待关系，100 个线程就是 $100 \times 100 = 10000$ 次判断。
    * 退回超时方案太不靠谱，真出了死锁在那儿僵着会对业务产生影响，所以这个机制得用。
    * 既然要用，就得在并发量大的场景下把并发访问的数量控制住：一个做法是在实际的数据库中间件层面，对"更新相同行"的请求排队，同时争抢同一行的线程数降下来，死锁检测的工作量也就跟着降下来。
    * 再进一步是减少锁的冲突：比如连锁超市涉及五六十家门店，如果每笔收支都跑到总部更新同一张表，锁冲突概率会明显增大；改成平时让每家店先在自己店里做账目增减，然后在固定时间（比如凌晨几点、或者每个月一次）再把数据汇总更新到总部那张表里。

* **死锁的避免措施**
    * 合理设计索引：让 SQL 在检索过程中尽可能少地去锁定相关的行数据；索引设计不合理时本来锁三行就够、它一遍历锁了三十行，锁住的数据越多越有可能造成死锁的风险。
    * 调整业务 SQL 的执行顺序：避免 `UPDATE`、`DELETE` 这种长时间持有锁的操作在相关事务前面先占着资源不动。
    * 避免大事务：把大事务分解成多个小事务；事务越小单位事务获取的锁就越少，出现死锁的概率也就越小。
    * 高并发系统里不要显式加锁：本来就并发得厉害，还自己显式去加锁。
    * 降低事务的隔离级别：这一条要具体问题具体看，看业务到底适不适合降低隔离级别。

## 锁结构、锁监控与加锁时机小结

* **锁结构的生成与共用条件**
    * 事务针对表里的记录加锁并不是一条记录生成一个锁结构，否则给 1 万条记录加 S 锁就要生成 1 万个锁结构、内存直接就崩了。
    * > 结论：满足下面四个条件的加锁会被收进同一个锁结构——加锁的是同一个事务；被加锁的记录在同一个页面中；加锁的类型相同；等待状态（`is_waiting`）也相同。
    * 四条里少一条，就分别落到不同的锁结构里去。
    * 锁结构里最早提到的两项人事安排是：这个锁是谁的（事务信息）与当前事务能不能操作这条记录（`is_waiting`）。

* **锁结构的内存布局**
    * 整体数下来锁结构一共分成六个部分，其中第三个位置要分情况：加的是表锁还是行锁，这一格记录的信息不一样。

    ```text
    +--------------------------------------------------------------+
    |  1  锁所在事务的信息        —— 指针，指向内存中该事务的信息   |
    +--------------------------------------------------------------+
    |  2  索引信息                —— 指针，指向涉及到的索引记录     |
    +--------------------------------------------------------------+
    |  3  表锁 / 行锁的信息                                         |
    |      表锁：表信息 + 其他信息                                  |
    |      行锁：Space ID + Page Number + n_bits                    |
    +--------------------------------------------------------------+
    |  4  type_mode                                                 |
    +--------------------------------------------------------------+
    |  5  其他信息                —— 相关哈希表、链表的信息         |
    +--------------------------------------------------------------+
    |  6  一堆比特位              —— 逐位标记页内哪个记录被锁       |
    +--------------------------------------------------------------+
    ```

    * 第 1 项锁所在事务的信息记清楚这个锁结构归谁；第 2 项索引信息记录当前事务操作到的、与索引相关的那些记录，同样以指针形式存。
    * 表锁那一格相对简单，记录"对哪一张表加的锁"外加一些辅助信息。
    * 行锁要记三个信息：`Space ID`（这条记录所在的表空间是哪个）、`Page Number`（这些记录所在的页号是多少）、`n_bits`。
    * > **易错点**：第 1 项记录只是一个指针，指向内存中该事务真正的信息所在的位置，不是把这个事务的全部信息都抄一份进来。

* **`type_mode` 的三段划分与 `is_waiting` 的位置**
    * `type_mode` 是"类型模式"，一个字段里塞了三段信息，从低位到高位依次排开。

    | 位段 | 字段 | 作用 |
    | :--- | :--- | :--- |
    | 低位段 | `lock_mode` | 记录锁的模式：`IS`（共享型意向锁）、`IX`（独占型意向锁）、`S` 锁、`X` 锁、自增锁等 |
    | 第 5 ~ 8 位 | `lock_type` | 第 5 位为 `1` 表示表级锁，第 6 位为 `1` 表示行级锁；第 7、8 位未使用 |
    | 再往高位 | `rec_lock_type` | 记录行锁的具体类型，如 `LOCK_REC_NOT_GAP` 等 |

    * `lock_mode` 记录的就是前面讲过的那些行为；它不一定只对应表级的锁——`S` 锁既可能是表级的共享锁，也可能是行级的共享锁，所以模式和表级／行级是两件分开的事。
    * `lock_type` 占了 5 到 8 位共 4 个 `bit`，实际只用了第 5、6 两位，靠这一对把表级锁和行锁区分开。
    * `rec_lock_type` 落在的是临键锁、间隙锁（`gap` 锁）、记录锁这些声明；给 `ID` 为 8 的记录加过的 `LOCK_REC_NOT_GAP` 就在这里，它表示一个正经的记录锁，是针对这一条记录的锁。
    * `is_waiting` 出于节省空间的考虑占的是第 9 位：这一位是 `1` 表示 `is_waiting` 为 `true`、处于等待状态；是 `0` 表示当前就可以操作这条记录，也就是获取锁成功了。

* **`n_bits` 与一堆比特位的关系**
    * 行锁要维护一整排比特位，因为锁结构是针对具体的一个页生成的，而一个页里可能有好几条记录被锁、另外一些没被锁，必须一条一条记下来。
    * 一个 `bit` 只有 `0` 和 `1` 两种取值，加锁的用 `1` 表示，没加锁的用 `0` 表示，一一对应到记录上。
    * 一个页里除了真实数据还必然有 `Infimum` 和 `Supremum`，这两个别丢了：真实 100 条数据加上这两个就是 102 条。
    * 每条记录都有一个 `heap_no`：`Infimum` 的 `heap_no` 是 `0`，`Supremum` 的 `heap_no` 是 `1`，之后每多加一条记录这个值就加 1；比特位和记录一一匹配，通过它就能看出到底是哪一条记录被当前事务的锁结构锁住了。
    * 实际用起来也不是刚好 102 个比特位：后面还可能往这个页里插入新记录，一个 `bit` 占的空间本来就很小，不妨多放一些，把后面新添加记录对应的位置预留出来。
    * > **提示**：`n_bits` 只记录比特位的个数，比如 `110` 它就写个 `110` 这个数；比特位本身并不在 `n_bits` 里，而在最后那一格。

* **锁监控之一：`innodb_row_lock` 系列状态变量**
    * 用 `SHOW STATUS LIKE 'innodb_row_lock%';` 能看到以这个字段开头的若干属性字段。

    ```sql
    SHOW STATUS LIKE 'innodb_row_lock%';
    ```

    | 字段 | 含义 |
    | :--- | :--- |
    | `current_waits` | 当前正在等待锁定的数量 |
    | `lock_time` | 从系统启动到现在为止，锁定的总时长 |
    | `avg_lock_time` | 锁等待平均花费的时长 |
    | `max_lock_time` | 锁等待最多花费的时长 |
    | `waits` | 锁等待的总次数 |

    * 重点盯三个：总时长、平均时长、等待次数；这三个里更重要的又是后两个。
    * 平均时长和等待次数乘起来正好就是总时长；如果这两个都比较大，就说明锁等待既频繁又费时间，这时候就该去查看相关事务、相关操作里的结构，分析是什么原因造成锁这么多、单次又耗这么久。
    * `max_lock_time` 演示里已经超过 50 秒，这 50 秒就是锁等待的 `timeout`，一个时间上限。

* **锁监控之二：系统表与 5.7／8.0 的差别**
    * 以前用的是 `information_schema` 库下面对应的三张表：一张管事务，一张管锁，一张专门管"锁在等谁"；5.7 就是用这三张表去查的。
    * 8.0 的策略有变化：三张表未必原样保留，其中一部分改用 `performance_schema` 里对应的表来替代——原来在 `information_schema` 里查锁的那张表，换成了 `performance_schema` 里对应的表，管锁等待的那张同样有对应替代。
    * > **易错点**：在 5.7 里用这套表去查只能看到被阻塞的事务、阻塞的锁，某个锁并没有造成阻塞就根本看不到它；8.0 不一样，没有阻塞的锁也能看到。
    * 阻塞场景实测：先在当前会话的事务里 `BEGIN; SELECT * FROM student FOR UPDATE;`，另一个会话 `BEGIN` 后再跑一句同样的语句就阻塞住；这时用 `SELECT * FROM information_schema.<表名> \G` 去查，能看到被阻塞的事务 ID、当前状态（处于等待中）、操作开始的时间、锁定／影响的行数以及当前事务的隔离级别。
    * 翻看字段的时候等待超过 50 秒，第二个事务被等待锁超时并放弃；而被查出来的那一条本身没有阻塞，所以它一直待在那里不会消失。
    * 上面语句里的 `<表名>` 用哪一张取决于当前版本：5.7 走 `information_schema` 里那三张表，8.0 走 `performance_schema` 里替代它的表。

    ```text
    先看状态变量 innodb_row_lock 系列
            |
            |  等待次数多、平均耗时长（两者相乘即总时长）
            v
    查事务与锁的系统表
            |
            |  当前仍有事务在等锁
            v
    查“锁在等谁”的那张表，定位等待中的锁
    ```

* **加锁时机与释放时机小结**
    * 表级 S 锁、X 锁由 `lock tables ... read/write` 手动加、`unlock tables` 释放，锁的是整张表，与 `begin` 无关。
    * 意向锁（IS／IX）在行上加 S 锁或 X 锁时由 InnoDB 自动补在表级，随行锁一起释放。
    * 自增锁在向带 `AUTO_INCREMENT` 列的表插入数据时获取，连续锁定模式下简单插入申请到自增值后立即释放，批量插入插完才释放。
    * MDL 由增删改查或表结构变更自动加上，查询事务不提交则读锁一直被持有，写锁一旦进入等待队列后续读锁都要排在它后面。
    * 记录锁、间隙锁、临键锁在 `update`／`delete` 或加锁的 `select` 时加上，事务提交或回滚后释放；隐式锁在别的事务访问时才由该访问者替插入方构建出来。
    * 全局锁加在整个实例上，加锁期间实例下所有库、所有表只能读不能改；锁等待超过 `innodb_lock_wait_timeout`（默认 50 秒）时事务自动回滚。

## MVCC 的定位与快照读、当前读

* **MVCC（Multi-Version Concurrency Control，多版本并发控制）**
    * > **定义**：MVCC 就是通过数据行的多个版本管理，来实现数据库的并发控制。
    * 事务日志里的 Redo 日志和 Undo 日志体现的是事务的原子性、一致性、持久性，事务的隔离性由锁机制体现；MVCC 是隔离级别的再下一层，它管的是在这个隔离级别下如何更好地实现并发。
    * 写操作仍然加锁，也就是让写去使用数据最新的那个版本，实质上是一种悲观锁的形象；读操作交给 MVCC 来处理，而 MVCC 更倾向于乐观锁的场景。
    * 要的就是读跟写不冲突：读不再是阻塞式的，而是非阻塞式的并发读。
    * MVCC 并没有正式的标准，在不同数据库管理系统里的实现方式各不相同，它也不是普遍使用的技术；即便在 MySQL 内部不同存储引擎对它的支持力度也不一样，只有 InnoDB 支持了 MVCC 这套机制。
    * 实际开发中基本上碰不到 MVCC，平时关注的是可以设置的隔离级别；但从面试角度讲，问到数据库比较高级的场景通常会问到 MVCC。

    ```text
    方案一：读写都加锁
        读事务 ──加 S 锁──┐
                          ├── 互斥排队 ── 并发性差
        写事务 ──加 X 锁──┘

    方案二：写加锁 + 读走 MVCC
        写事务 ──加锁──→ 最新版本（悲观）
        读事务 ──MVCC──→ 历史版本（乐观）
                          └── 读写不冲突，并发性更好
    ```

* **MVCC 的三要素与组成公式**
    * MVCC 的实现依赖三样东西：隐藏字段（里面有一个事务 ID，因为 ReadView 的判断要用到它）、undo log（体现"多版本"）、ReadView（体现"并发控制"）。
    * undo log 加上 ReadView 就构成了 MVCC 的核心：多版本靠 undo log 体现，并发控制由 ReadView 来管。
    * 核心公式是两个隐藏列，加上 undo log 的版本链，再加上一个 ReadView；ReadView 在管理的过程中又需要用到那两个隐藏列。
    * 多版本指的就是 undo log 的版本链，并发控制与管理指的是 ReadView。

    $$ \text{MVCC} = \text{隐藏列} + \text{undo log 版本链} + \text{ReadView} $$

    ```text
      MVCC 的组成与职责

        隐藏列（trx_id / roll_pointer）
              │  被 ReadView 用于可见性判断
              ↓
        undo log 版本链  ──→  提供"多版本"
              │
              ↓
        ReadView  ──→  负责"并发控制与管理"
              │
              ↓
        快照读结果：只放出对当前快照可见的那个版本
    ```


* **一致性读与 MVCC 给出的保证**
    * 一致性读说的其实就是快照读，也就是为了查询那些正在被另一个事务更新的行，并且看到它们**被更新之前**的值。
    * 如果看到的是它正在更新中的值那就成脏读了；如果等人家更新完、把锁释放了你再去读，那就变成了串行，又退回到加锁方案的思路上去了。
    * 取的是一个巧劲：不去碰对方手里那份正在改的数据，而去读它改之前已经留下的那个版本，改之前的值就来自 undo log 里记着的历史版本；读旧版本本身不用加锁，也就不会和写抢资源。
    * MVCC 能解决的具体问题：读写之间的阻塞问题（并发性更高了，同时降低了死锁的概率，用的是乐观的方式来解决读的问题）；快照读的问题——本质上和上一条其实是一件事。

* **快照读（一致性读）与当前读的划分**
    * 两者是一组相对的概念：一致性读也叫快照读，与它相对的是当前读。
    * 快照读：在事务里写了一条 `SELECT` 语句、又没有对它做任何加锁行为，它就相当于一个快照读；具体读哪一个快照由 ReadView 来管理。
    * 快照读有个前提条件：它所对应的隔离级别不是串行化；一旦是串行化就退化成当前读了，因为事务一个个来、别人都提交了你才能访问，读到的必然是最新数据。
    * 当前读意味着读记录的最新版本而不是历史记录的版本；反过来说，凡是要读最新版本的场景，都要付出加锁的成本。
    * 对读操作加锁、或者对增删改操作加锁，这些场景要获取的其实都是当前读：想获取最新版本就得付出加锁这个成本，如果加了锁读到的还是历史版本那这个锁就白加了。
    * > **易错点**：不要以为快照读等于"读的一定是旧值"，也不要以为快照读"一定读旧的"——它读的是 ReadView 允许它看见的那个版本，可能是历史版本，也可能就是最新版本。

    | 对比项 | 快照读（一致性读） | 当前读 |
    | :--- | :--- | :--- |
    | 读到的版本 | 可能不是最新，可能是历史版本，也可能是新的 | 一定是记录的最新版本 |
    | 是否加锁 | 不加锁 | 要加锁（读加 `S` 锁，增删改加 `X` 锁） |
    | 并发表现 | 非阻塞式并发读 | 会带来一定的阻塞 |
    | 由谁实现 | 由 MVCC（`ReadView` 管快照）实现 | 由加锁实现 |
    | 典型语句 | 不加锁的普通 `SELECT` | 加锁的读，以及增删改操作 |
    | 隔离级别 | 不是串行化 | 串行化下一切读都是当前读 |

    ```text
    一次读写并发的分工

        写事务 ──→ 加锁 ──→ 读到/改到：最新版本（当前读）
                                   │
                                   │ 每改一次，旧值进 undo log
                                   ↓
                             多版本（undo log 版本链）
                                   ↑
                                   │ ReadView 决定放哪个版本出来
                                   │
        读事务 ──→ 不加锁 ──→ 读到：其中一个历史版本（快照读）
    ```

## ReadView 与可见性判定

* **四种隔离级别与 MySQL 的实际表现**
    * 事务有四种隔离级别，解决的是三种并发问题；四种隔离级别从上往下并发性越来越差、能解决的问题越来越多：读已提交解决第一个，可重复读解决上面的两个，串行化三个都解决，读未提交一个也不解决。

    | 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性 |
    | :--- | :--- | :--- | :--- | :--- |
    | 读未提交（Read Uncommitted，RU） | 未解决 | 未解决 | 未解决 | 最高 |
    | 读已提交（Read Committed，RC） | 解决 | 未解决 | 未解决 | 较高 |
    | 可重复读（Repeatable Read，RR） | 解决 | 解决 | 未解决 | 较低 |
    | 串行化（Serializable） | 解决 | 解决 | 解决 | 最低 |

    * 这是 SQL 标准给出的对应关系，但对 MySQL 来说这张表并不准确：MySQL 默认隔离级别是可重复读，这个默认级别不光解决了脏读和不可重复读，它把幻读问题也一起解决了，主要原因就是使用了 MVCC。
    * 说 MySQL 的可重复读解决了幻读并不是说 MySQL 变成串行化了：串行化靠加锁实现、事务一个个来；而 MVCC 里面针对读是可以不用排队的，所以它不仅解决了幻读，性能相较于串行化还更高。
    * MVCC 只在读已提交和可重复读这两个隔离级别下才有效：读未提交下本来就能读到未提交的数据，读的就是最新的记录，跟历史快照没有关系；串行化下能轮到你读就说明别的事务都没在改，读到的也一定是最新数据。

* **行格式中的三个隐藏字段**
    * `row_id`：如果这条记录没有主键、也没有非空的唯一索引，系统就会默认提供这样一个隐藏字段。
    * `transaction_id`：记录最近一次更新这条记录的事务 ID。
    * 回滚指针（`roll_pointer`）：因为事务有可能回滚，需要把"这个事务操作这条记录之前的样子"记下来，最后把这条记录和它的各个历史版本用链表连接起来；这个指针指向最近的那一批 Undo Log 记录。
    * > **易错点**：三个隐藏字段里 MVCC 真正用上的是 `transaction_id` 和回滚指针这两个，`row_id` 与版本可见性判断没有关系。

* **Undo Log 版本链的形成**
    * insert 产生的 Undo 只在事务回滚的时候才会起作用；如果这个事务已经提交，这条 Undo Log 就完全没有作用了，接下来可能被回收、也可能被重用。
    * insert 完成以后，这条记录的 `transaction_id` 就是插入它的事务 ID，而它的回滚指针要指向 insert 之前的 Undo——可 insert 之前根本不存在这条记录，没有什么可指的，所以 insert 的 Undo 是没有回滚指针的。
    * 版本链从新到旧串起来：链头是最新数据，每一条 Undo 记录里都记着操作这条数据时的事务 ID，顺着链走一遍就等于把这条记录的修改历史从后往前读了一遍。
    * 同一个事务产生的版本在版本链上必然是相邻的：update 的时候会开启事务并加 X 锁，另一个事务再来访问这条记录就阻塞了，只能等前一个事务的 update 都执行完、排他锁释放之后才能进来操作。

    ```text
    链头（最新版本）
       宋八      由事务 20 的 update 产生
        │ roll_pointer
       钱七      由事务 20 的 update 产生
        │ roll_pointer
       王五      由事务 10 的 update 产生
        │ roll_pointer
       李四      由事务 10 的 update 产生
        │ roll_pointer
       张三      由事务 8 的 insert 产生
        │
       NULL     insert 的 Undo 没有回滚指针，版本链到此为止
    链尾（最旧版本）
    ```


* **ReadView（读视图）的定位**
    * > **定义**：ReadView 是某一个事务在使用 MVCC 机制进行快照读操作的时候产生的一个读视图，它和事务是一对一的关系——是我们这个具体的事务要读，才会生成这个读视图。
    * 版本链上躺着这么多历史版本，不同的事务过来到底该读哪一个，这个管理行为由 ReadView 来体现：它解决的是 Undo Log 里的哪些版本对当前这个读事务可见、哪些不可见。
    * 生成快照的时候 InnoDB 会为这个事务构造一个数组，ReadView 里存的是好多数据、用的是数组这种数据结构。
    * > **定义**：活跃的事务指已经启动、但是还没有提交的事务；反过来，已经提交的事务不会被记进当前这个 ReadView 里。

* **ReadView 的四个判定字段**
    * 事务 ID 的分配规则：只有对表中的记录做增删改，系统才会分配一个事务 ID，分配方式是依次递增；如果只是一个读事务，它的 ID 是 `0`。
    * `creator_trx_id` 是创建这个 ReadView 的事务自己的 ID，回答的是"谁生成了我"。
    * `trx_ids` 是事务 ID 的列表，定语一定要小心：它是**活跃的**读写事务 ID 列表；一个事务操作、生成 ReadView 的那一刻，看当前系统里还有哪些事务没有提交、还活着，把它们记进这个列表里，已经提交过的事务一个都不会放进来。
    * `up_limit_id` 是活跃列表里最小的那个事务 ID——名字里带 `up`，但取的是小的那个值，它是下界。
    * `low_limit_id` 是生成 ReadView 时系统应该分配给下一个事务的 ID 值，它的真实含义是：系统里已经出现过的最大事务 ID 再加一，它是上界。
    * > **易错点**：`low_limit_id` 不是"活跃列表里的最大值加一"，而是"系统最大事务 ID 加一"；已经提交的事务也要考虑在内，因为已提交的事务里完全可能存在比活跃列表更大的 ID。

    | 字段 | 含义 |
    | :--- | :--- |
    | `creator_trx_id` | 创建这个 ReadView 的事务 ID，也就是"谁生成了我" |
    | `trx_ids` | 生成 ReadView 的那一刻，系统里活跃的读写事务 ID 列表 |
    | `up_limit_id` | `trx_ids` 中的最小值 |
    | `low_limit_id` | 生成 ReadView 时，系统应该分配给下一个事务的 ID 值 |

    ```text
    系统已出现过的事务 ID：1、2、3，以及更大的 5
    生成 ReadView 的那一刻        →   trx_ids = {1, 2}      （3 已提交，不在列表里）

    up_limit_id  = 1                    活跃列表中的最小值
    low_limit_id = 5 + 1 = 6             系统最大事务 ID 加一，与活跃列表无关
    ```

    ```text
    trx_ids      = {2, 3, 5, 8}
    up_limit_id  = 2                    列表中的最小值

    假设没有比 8 更大的事务（别的事务都已提交，提交的里也没有超过 8 的）
    low_limit_id = 8 + 1 = 9            系统最大事务 ID 加一
    ```

    * > **易错点**：两个 limit 的命名是反着的——`up_limit_id` 取活跃列表里的**最小值**（下界），`low_limit_id` 取的是**上界**（系统已经出现过的最大事务 ID 加一）；照着名字望文生义，十有八九会把这两个值用反。

* **版本可见性的四条判定规则**
    * 把被访问版本的事务 ID 记为 `T`，访问某条记录时按下面几步判断一个版本是否可见；查找是从链头（最新版本）开始的。
    * 规则一：`T` 等于 `creator_trx_id`，可以访问——自己往这条记录里改了数据又自己想查，自己改的自己查没问题。
    * 规则二：`T` 小于 `up_limit_id`，可以访问——一个版本的事务 ID 比"活着的最小事务 ID"还小，说明列表里的每个值都比它大，它不可能是活跃的，产生这个版本的事务肯定早就结束了，相当于已经提交过。
    * 规则三：`T` 大于或等于 `low_limit_id`，不能访问——说明产生这次修改的事务是在我们生成 ReadView 之后才出现的，是后来的事务，这个读视图就不应该承认它；不能访问就顺着版本链往后找更旧的历史版本。
    * 规则四：`T` 落在 `up_limit_id` 与 `low_limit_id` 之间，要再查一次 `trx_ids` 列表：列表里正好有它，说明产生这个版本的事务现在还是活跃的、还没有提交，不能访问；列表里没有它，说明这个事务已经不活跃了、已经提交了，那就可以访问。
    * 不能访问并不是这次查询就结束了，而是换版本链上的下一个更旧的版本重新判一遍。

    ```text
    被访问版本的 transaction_id = T

    步骤 1   T 等于 creator_trx_id ？
                是 → 可见（自己改的，自己读）

    步骤 2   T 小于 up_limit_id ？
                是 → 可见（比最小活跃事务还小，早已提交）

    步骤 3   T 大于等于 low_limit_id ？
                是 → 不可见（这是 ReadView 生成之后才出现的事务）

    步骤 4   T 在 [up_limit_id, low_limit_id) 范围内：
                T 在 trx_ids 列表中   → 该事务仍活跃，尚未提交 → 不可见
                T 不在 trx_ids 列表中 → 该事务已提交           → 可见

    判为不可见的 → 顺着回滚指针取下一个更旧的版本，从步骤 1 重新开始
    ```


* **一次快照读的完整流程**
    * 在事务中执行查询语句，先获取这个查询事务自己的 ID 号。
    * 紧跟着为这个事务生成一个 ReadView，跟事务是一对一的关系。
    * 查询拿到数据后，从版本链的链头（最新版本）开始，把这个版本的 `transaction_id` 与 ReadView 里的内容做比较。
    * 不符合规则、判为不可见，就顺着回滚指针往下找版本链里的下一个版本，依次往下——越往后历史数据越旧，越靠前数据相对越新。
    * 一直找到符合规则的那个版本，它就是这次查询读到的数据；如果一直找到版本链末尾都不可见，那就说明这条记录对你没有可见的版本，这次查询的结果里就不包含这条记录。

    ```text
    事务中执行 SELECT
        │
        ├─ 1. 获取这个读事务自己的 ID
        ├─ 2. 为它生成一个 ReadView（creator_trx_id / trx_ids / up_limit_id / low_limit_id）
        ├─ 3. 从版本链链头（最新版本）开始，用版本的 transaction_id 与 ReadView 比较
        ├─ 4. 不可见 → 顺着回滚指针取下一个更旧的版本，回到第 3 步
        └─ 5. 第一个符合规则的版本 → 它就是本次查询读到的数据
              整条链都不可见       → 本次查询结果不包含这条记录
    ```


* **ReadView 的生成时机**
    * 读已提交：每做一次查询都要重新获取一次 ReadView，每读一次获取一次。
    * 可重复读：只在第一次 `SELECT` 的时候生成 ReadView，后面再读不再生成。
    * 读已提交之所以每次读都重新获取，是因为 ReadView 保证的是你能读到已提交的数据；不同次数的读之间如果换一张新快照，就有可能读到别人刚提交的新版本，也就是出现不可重复读的数据——这恰恰是读已提交这种行为要允许的，不然它就跟可重复读没区别了。
    * 可重复读正好相反：后面再读就不让生成 ReadView 了，一直用最初的那一个，这样每次读出来的数据都是重复的。

## RC 与 RR 的流程与幻读

* **示例场景与事务 ID 的分配**
    * 大背景是 `student` 表里有一条 `id = 1` 的记录，它由事务 id 为 `8` 的事务插入；整个例子都在这条记录上做文章。
    * 有两个写事务，一个 id 是 `10`、一个 id 是 `20`，都准备去改 `id = 1` 这条记录；事务 `20` 特意写成"更新了一些别的表的记录"，就是为了让系统给它分配一个非 0 的数。
    * 事例里出现的事务 ID 都是因为对表里的记录做过修改才拿到这些号，光读的事务一直是 `0`。
    * > **易错点**：`20` 的作用仅此而已，它跟 `student` 表里那条 `id = 1` 的记录没有任何关系，也不会在那条记录上留下版本；如果它什么都没做它就只能是 `0`，后面拿它跟活跃列表比较就没有意义了。

    ```text
    王五   trx_id = 10   roll_pointer ──┐
                                       ↓
    李四   trx_id = 10   roll_pointer ──┐
                                       ↓
    张三   trx_id = 8    roll_pointer ──→ NULL
    ```

* **读已提交（RC）下的操作流程**
    * 规则：事务每 `SELECT` 一次就会生成一个 `ReadView`。
    * 首次查询时事务 `10` 和事务 `20` 都还没有提交：ReadView 的生成者是当前读事务自己（id 为 `0`），活跃列表是 `{10, 20}`，`up_limit_id` 是 `10`，`low_limit_id` 是 `21`（`20` 是目前为止最大的一个活跃事务，取它加一）。
    * 判断过程：链头王五的事务 id 是 `10`，不等于 creator、也不小于 `10`、且恰好就在活跃列表 `{10, 20}` 里边，落在这个列表里就意味着这个事务现在还活跃、还没有提交，所以王五查不出来；下一个版本李四又是 `10`，还是不行；再往下找到 `8`，`8` 不在活跃列表里而且比 `10` 还小，说明它是一个之前已经提交过的事务，最终结果就是张三。
    * 事务 `10` 提交、事务 `20` 做两次更新之后，读事务再读一次又会生成一个新的 ReadView：活跃列表只剩 `20`，读事务的 id 还是 `0`，`low_limit_id` 还是 `21`。宋八（`20`）与钱七（`20`）都还在列表里不能用，再往下是王五（`10`）：不在列表里、而且比列表里的数还小，说明已经提交过了，所以这一次读到的是王五。
    * "比列表里的数还小"为什么能推出已提交：如果它比列表里的值大，就说明它是在生成这个 ReadView 之后才做的修改，是一个后来的事务 id，更不能去用它的版本；所以必须满足"不在活跃列表里，并且比列表里的值小"。
    * 事务 `20` 也提交后活跃列表里就没有它了，链头的宋八事务 id 是 `20`，它已经不活跃、而且比列表里的值还小，于是宋八就能读出来了。

    ```text
    RC：三条 SELECT 的可见性判断

    ① 事务10、20 均未提交
       活跃列表 {10, 20}，up_limit_id=10，low_limit_id=21
       王五(10) 在列表内 → 不可见
       李四(10) 在列表内 → 不可见
       张三( 8) 不在列表且 < 10 → 可见      结果：张三

    ② 事务10 已提交，事务20 未提交
       活跃列表 {20}，up_limit_id=20，low_limit_id=21
       宋八(20) 在列表内 → 不可见
       钱七(20) 在列表内 → 不可见
       王五(10) 不在列表且 < 20 → 可见      结果：王五

    ③ 事务10、20 均已提交
       活跃列表 {}，low_limit_id=21
       宋八(20) 不在列表且 < 21 → 可见      结果：宋八
    ```


* **可重复读（RR）下的操作流程**
    * 规则：只有第一次执行查询语句的时候才生成 `ReadView`，之后再查询就不再生成。
    * 首次查询生成的 ReadView 与读已提交第一次读时完全一致：creator 是 `0`，活跃列表是 `{10, 20}`，上界 `low_limit_id` 是 `21`；判断过程也一模一样，结果是张三。
    * 事务 `10` 提交、事务 `20` 做两次更新之后读事务又读了一次，这一次不再生成 ReadView，手里用的还是刚才那一个、完全不动：宋八（`20`）在旧 ReadView 里还在活跃列表里不能用；钱七（`20`）也不能用；王五（`10`）虽然在真实世界里已经提交了，可这个 ReadView 里还记着 `10`，按这个 ReadView 看事务 `10` 仍然活跃、只要它在这个列表里我们就不能用它；继续往下找到 `8`，还是把张三读出来。
    * 把事务 `20` 也提交之后再去 `SELECT`，用的还是第一次那个 ReadView，那个 ReadView 里边有 `20`、只要有 `20` 就不能用它，所以读出来还是张三。
    * 只要这个读事务自己没结束，用的就一直是第一次生成的 ReadView，不会把事务 `10` 和事务 `20` 的新版本查出来，读出来永远是张三，这就叫可重复读。
    * > **提示**：可重复读的"可重复"只对这个读事务自己成立；一旦这个事务结束、重新开启一个事务再查，生成的就是全新的 ReadView，那时宋八自然就读得到了。不要把"可重复读"理解成这条数据永远不变。

    ```text
    RR：三次查询共用同一个 ReadView

    首次 SELECT 生成 ReadView
       creator = 0 ，活跃列表 {10, 20} ，up_limit_id = 10 ，low_limit_id = 21
            │
            ├─ 事务10 提交、事务20 连续更新两次
            │     第二次 SELECT → 不生成新 ReadView，沿用上面那个
            │        宋八(20) 在列表内 → 不可见
            │        钱七(20) 在列表内 → 不可见
            │        王五(10) 仍在列表内 → 不可见
            │        张三( 8) 不在列表且 < 10 → 可见   结果：张三
            │
            └─ 事务20 提交
                  第三次 SELECT → 仍沿用同一个 ReadView
                     宋八(20) 仍在列表内 → 不可见
                     最终仍为 张三
    ```

* **两个隔离级别的差异**
    * MVCC 在 RC 与 RR 下的版本链、可见性判断规则、以及首次查询的结果都完全一样，唯一的变量就是 ReadView 的生成时机。
    * RC 每次读都刷新快照，所以能读到别人刚提交的数据；RR 只认第一次的快照，所以别人提交多少次都影响不了我这一次事务的读结果。

    | 对比项 | 读已提交（RC） | 可重复读（RR） |
    | :--- | :--- | :--- |
    | `ReadView` 生成时机 | 每执行一次 `SELECT` 生成一个 | 只在第一次执行查询语句时生成一个 |
    | 后续查询使用的快照 | 每次都换新的 `ReadView` | 一直沿用首次生成的那个 `ReadView` |
    | 已提交事务的新版本 | 下一次查询就能读到 | 只要它还在首次的活跃列表里就读不到 |
    | 同一读事务内的读结果 | 可能不同（张三 → 王五 → 宋八） | 始终相同（张三 → 张三 → 张三） |
    | 对应的并发问题 | 存在不可重复读 | 规避了不可重复读，还能解决幻读 |


* **可重复读下解决幻读的流程**
    * > **定义**：同一个事务，前后两次执行同样的查询，后一次看到了别的事务新插入的行——这多出来的行就是幻影，这个现象就叫幻读。
    * 场景：表里只有一条 `id = 1` 的记录，最近一次修改它的事务 id 是 `10`（早已提交）；事务 A 的 id 是 `20`，事务 B 的 id 是 `30`。
    * 事务 A 先执行 `SELECT * FROM student WHERE id >= 1;`，此时表里只有那一行记录，这条记录会被查出来。
    * 事务 A 没有结束的情况下，事务 B 往表里新插入两条 `id` 都比 `1` 大的记录；事务 A 再查一次，如果看到了这两条就是幻读。
    * 事务 A 第一次查询是首次执行查询，生成 ReadView：生成者是事务 `20` 自己，活跃列表是 `{20, 30}`，上限值是 `30 + 1 = 31`。
    * 第一条记录的事务 id 是 `10`：`10` 比列表里最小的那个（也就是 `20`）还要小，且不在活跃列表里，说明它已经提交了，所以这条记录应该被查出来。
    * 第二次查询时事务 A 没有结束、事务 B 插入的两条记录事务 id 是 `30`，这一次 `SELECT` 不会再生成 ReadView、用的还是第一次留下的那个，活跃列表还是 `{20, 30}`：`30` 还在这份活跃列表里、还被认为处在活跃状态，落在列表内就不能用，所以这两条记录根本不会被读出来。
    * 结论：可重复读解决幻读靠的不是把新记录删掉、也不是给它加锁，而是靠"快照只生成一次、之后一直复用"——新插入的行产生于快照生成之后，其事务 id 被永久记在活跃列表里，因此在该事务结束之前始终不可见。
    * > **易错点**：判断的是 ReadView 里记的状态，不是此刻的真实状态；事务 B 可能已经提交了，但只要 `30` 还留在首次生成的活跃列表里，这条快照就永远不承认它的版本。

    ```text
    时间轴（RR 隔离级别）

    事务 A (trx_id = 20)                事务 B (trx_id = 30)
    ─────────────────────              ─────────────────────
    BEGIN
    SELECT id >= 1
      → 生成 ReadView（就这一次）
      → 读到 1 条                      INSERT 两条（id > 1）
                                       （此时 B 仍活跃）
    SELECT id >= 1   ← 沿用上面那个 ReadView
      → 仍然是 1 条
    ```

    ```text
    RR：首次 SELECT 生成 ReadView 后，第二次判断

    ReadView：creator = 20 ，活跃列表 {20, 30} ，上限 31

      id = 1   trx_id = 10
               10 < 20（比最小活跃事务还小）
               且 10 不在 {20, 30} 内 → 早已提交 → 可见

      id > 1   trx_id = 30
               30 落在 {20, 30} 内 → 仍视为活跃 → 不可见
      id > 1   trx_id = 30
               30 落在 {20, 30} 内 → 仍视为活跃 → 不可见

      结果：只读出 1 条，插入的两条被挡住
    ```

* **读已提交下的幻读对照**
    * 读已提交下每执行一次 `SELECT` 就重新生成一个 `ReadView`，所以事务 A 第二次查询时拿到的是全新的一份快照而不是原来那份。
    * 重新生成快照不等于立刻就能看见：如果此刻事务 B 还没提交，那么新快照的活跃列表里仍然有 `30`，那两条记录还是不可见。
    * 可一旦事务 B 提交，列表里不再有 `30`，新快照里 `30` 既不活跃又比列表中的值小、相当于它已经提交，于是那两条数据就能被看到了。
    * 同一条语句、同一个事务，头一次读出一条、后一次读出三条，这就叫幻读。

    | 对比项 | 读已提交（RC） | 可重复读（RR） |
    | :--- | :--- | :--- |
    | `ReadView` 生成时机 | 每次 `SELECT` 都重新生成 | 只在首次查询时生成 |
    | 事务 B 提交后，插入的记录 | 新快照能读到 | 旧快照仍判定为活跃，读不到 |
    | 同一事务内两次查询的行数 | 1 条 → 3 条，出现幻读 | 1 条 → 1 条，幻读被挡住 |
    | 所依赖的快照 | 每次读的最新快照 | 冻结在首次查询那一刻的快照 |


* **`delete mark` 标记与真实删除的区别**
    * `DELETE` 的时候其实并没有真正意义上把数据删掉，而只是把行格式里的 `delete mark` 记录从 `0` 改成了 `1`，用这种方式表示"已删除"。
    * 不直接删的主要原因是还要考虑回滚这类需求，说到底是为 MVCC 服务的，所以这里不能真正把它删了。
