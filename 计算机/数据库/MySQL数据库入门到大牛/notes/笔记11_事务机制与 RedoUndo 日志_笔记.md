# 事务机制与 Redo/Undo 日志
## 事务的定义与 ACID 特性

* **事务（Transaction）**
    * > **定义**：事务是一组逻辑操作单元，使数据从一种状态变换到另一种状态。
    * 事务是数据库区别于文件系统的重要特征之一，拉开这个差距靠的就是它的 ACID 四个特性。
    * 一个事务往往包含多个 DML 操作，结局只有两种：全部提交（`COMMIT`）使修改永久保存，或者数据库管理系统放弃所做的全部修改。
    * 事务必须作为一个工作单元来执行，即使出现故障也不改变这种执行方式；一个事务里 5 个 DML 做了 3 个、剩 2 个没做，已经做掉的 3 个也必须回滚回去。
    * 示例：`UPDATE account SET money = money - 100 WHERE name = 'AA';` 与 `UPDATE account SET money = money + 100 WHERE name = 'BB';` 这两条整体构成一个事务，要么都执行、要么都不执行。
    * AA 给 BB 转账与 CC 给 DD 转账这两组互不相干的操作是两个事务，两组之间没有「必须都做或者必须都不做」的要求。

* **存储引擎层面的事务支持**
    * `SHOW ENGINES` 列出的 `Transactions` 列表示该引擎支不支持事务，标成 `YES` 的只有 InnoDB 一个，MyISAM 标成 `NO`。
    * MySQL 5.5 之后默认使用的就是 InnoDB，事务相关的所有内容都落在 InnoDB 里。

* **原子性（Atomicity）**
    * > **定义**：事务是一个不可分割的工作单位，要么全部提交，要么全部失败回滚，没有第三种结果。
    * 名字借用了物理世界里「原子不能再分」的含义，用它表达整体性。

* **一致性（Consistency）**
    * > **定义**：事务在执行前后，数据从一个合法性状态变换到另外一个合法性状态。
    * 这里的「合法」指语义上的合法，不由 SQL 语法把关，只能由现实业务里的约束把关。
    * 例一：账户余额是 200 却要转出 300，转完的 -100 不满足余额大于等于 0 这条约束，不能让成功。
    * 例二：A 账户与 B 账户的金额总数应该一定，转出 50 之后总额变了，同样不满足一致性。
    * 例三：姓名被设置成唯一性约束，事务提交或回滚时发现姓名不唯一，就不合法。
    * 不合法、不满足合法状态时就回滚到最初的状态，这里体现的正是原子性。

* **隔离性（Isolation）**
    * > **定义**：一个事务的执行不能被其他事务干扰，即一个事务内部的操作及使用的数据对并发的其他事务是隔离的。
    * 并发场景的本质是「读—改—写」区间交错重叠：A 账户 200 元分两次各转 50 给 B，正确结果是 A 剩 100、B 有 100、合计 200，交错执行后实际是 A 剩 100、B 只有 50、合计 150。
    * 交错的原因：B 的两次自增都读到磁盘上的同一个旧值 0，第二次自增把第一次覆盖掉了。
    * 线程安全问题用 `synchronized` 包一层就能解决，搬到表上只是把「线程」换成「事务」。
    * 隔离性的落地方式是事务隔离级别（transaction isolation）。

* **持久性（Durability）**
    * > **定义**：一旦数据要提交，对数据库中的改变就是永久性的，不会随着数据库的故障等产生任何影响。
    * 提交之后就不能再反悔：想让钱退回来等于又开启了一个事务，那是另外一个事务的事。
    * 持久性靠事务日志保障，内存中的数据修改先记到重做日志里，崩溃重启后从日志里把操作读出来再执行一遍。

* **ACID 四个特性的角色分工**

    | 特性 | 在事务中承担的角色 |
    | :--- | :--- |
    | 原子性（Atomicity） | 基础：事务是一个不可分割的整体，要么都成、要么都退 |
    | 一致性（Consistency） | 约束条件：事务前后都必须落在语义合法的状态上 |
    | 隔离性（Isolation） | 手段：保证事务在操作过程中对其他事务是隔离的 |
    | 持久性（Durability） | 目标：最终让磁盘上的数据发生真实的、永久的修改 |

    * 四个特性被「事务」这一个词概括起来，所以一提到事务必然会提到这四个特性。

## 事务状态与状态转移

* **活动状态（active）**
    * 事务对应的数据库操作正在执行的过程当中，就说该事务处于活动状态；第一条语句操作完、正要执行第二条语句，这个「正在执行」的过程也算。

* **部分提交状态（partially committed）**
    * 事务中最后一个操作执行完成了，但操作都在内存中执行、还没把数据刷新到磁盘，此时称它处于部分提交状态。
    * 事务里的 DML 可能有四条：四条执行过程中都是活动状态，一旦第四条执行完、只是把内存里的数据改了（表数据以数据页方式加载到内存里），还没刷盘。

* **提交状态（committed）**
    * 把处于部分提交状态的事务中的数据修改同步到磁盘上，即做了一次持久化，这时就称为提交状态。
    * 它是部分提交的下一个阶段，也是事务的最终状态之一：磁盘上的数据最终被改掉了。

* **失败状态（failed）**
    * 事务处在活动或部分提交状态时遇到数据库自身的错误、操作系统的错误、直接断电，或者人为地让当前事务不能继续执行，就处在失败状态。
    * 它可以由活动状态直接奔到失败，也可以由部分提交状态、还没刷盘就奔到失败。
    * 语句执行失败只是让事务停在失败状态，这个状态是临时的，事务本身并没有结束。

* **中止状态（aborted）**
    * 把已经在这个事务中做过的修改还原到事务执行前的状态，这个整体还原的过程叫回滚；回滚之后的状态就是中止状态，也叫终止状态。
    * > **定义**：中止状态是遇到失败情况之后采取的一种处理方案，即终止并把数据回滚回去。
    * 事务的最终状态只有两种：要么提交状态，要么中止状态，二选一，没有第三种可能。

* **五种状态与两条归宿的转移关系**

    ```text
       ┌──────────────┐   最后一条 DML 执行完   ┌──────────────────┐   刷盘成功   ┌──────────────┐
       │ 活动的        │ ─────────────────────▶ │ 部分提交的        │ ──────────▶ │ 提交的        │
       │ active       │   （只改了内存数据）     │ partially comm.  │             │ committed    │
       └──────┬───────┘                        └────────┬─────────┘             └──────┬───────┘
              │                                         │                              │
              │  出错 / 断电 / 人为终止                   │                              ▼
              └────────────────┬────────────────────────┘                      最终归宿 ①
                               ▼
                       ┌──────────────┐   回滚（撤销已做的修改）  ┌──────────────┐
                       │ 失败的        │ ─────────────────────▶ │ 中止的        │
                       │ failed       │                        │ aborted      │
                       └──────────────┘                        └──────┬───────┘
                                                                      ▼
                                                                最终归宿 ②
    ```

    * 活动状态和部分提交状态都可能直接走向失败；失败之后必须回滚，回滚完成才落到中止状态。
    * 出错之后事务停在失败状态，需要显式执行 `ROLLBACK` 把它终止，才能回到最近一次提交之后的位置。

## 事务日志的分工与 WAL 原则

* **ACID 特性的保证手段**
    * 隔离性由锁机制实现，原子性、一致性、持久性三个特性靠日志来保证。
    * 跟事务相关的日志就两种：重做日志（`redo log`）与回滚日志（`undo log`）。

    | 日志 | 中文名 | 作用 | 保证的特性 |
    | :--- | :--- | :--- | :--- |
    | `redo log` | 重做日志 | 提供再写入操作，恢复提交事务修改的页的操作 | 持久性 |
    | `undo log` | 回滚日志 | 把行记录回滚到某个特定的版本 | 原子性、一致性 |

    * 两个最终状态与两种日志对得上：提交状态由 `redo` 保证，执行到一半失败、要回到中止状态由 `undo log` 保证。

* **两类日志的联系**
    * 联系一：二者都被视作一种恢复操作，`undo` 是把做过的操作回滚回去，`redo` 是从日志里把内存中已改、磁盘未改的数据恢复出来。
    * 联系二：二者都是存储引擎层生成的日志，后面要讲的 `binlog` 不是存储引擎层生成的。

* **两类日志的区别**

    | 对比项 | `redo log` | `undo log` |
    | :--- | :--- | :--- |
    | 记录内容 | 物理级别：哪个页号、什么偏移量、写入了什么数据 | 逻辑操作：与已执行操作相反的操作，如 insert 对应 delete |
    | 生成层次 | 存储引擎层 | 存储引擎层 |
    | 主要作用 | 恢复提交事务修改的页，保证持久性 | 事务回滚，保证原子性与一致性；另有一致性非锁定读 |

    * `undo` 除了事务回滚，还有一个作用是并发多版本控制（MVCC，Multi-Version Concurrency Control）用到的非锁定读，在讲 MVCC 时结合着说。
    * > **易错点**：不要简单地把 `undo` 理解成 `redo` 的逆过程——一个往前冲、一个往后退只是表面印象，`undo` 做的是逻辑恢复，物理上已经发生的页分配与空间占用收不回去。

## 显式事务与隐式事务

* **事务的三步与两种结束状态**
    * 第一步开启事务，第二步一系列 DML 操作，第三步结束事务：`commit` 进入提交状态，`rollback` 进入中止状态。
    * 单独的、一条 DML 语句独立构成一个事务是可以的，「一系列」是上限描述而不是下限要求。

* **开启事务的两条语句**
    * `START TRANSACTION` 后面可以跟修饰内容，`BEGIN` 不能跟，这是两者真正的区别；日常写事务用 `begin` 完全够。
    * 两种写法开启的事务在结束方式上没有区别。

* **三种事务模式**

    | 修饰项 | 作用 | 能否与另一模式共存 |
    | :--- | :--- | :--- |
    | `READ ONLY` | 开启只读事务，只能查询 | 与 `READ WRITE` 互斥 |
    | `READ WRITE` | 开启可读可写事务，默认值 | 与 `READ ONLY` 互斥 |
    | `WITH CONSISTENT SNAPSHOT` | 开启一致性读（快照） | 与前两者均可搭配 |

    * `START TRANSACTION` 后面什么都不写时默认就是 `READ WRITE`，等价于 `START TRANSACTION READ WRITE`。

* **`READ ONLY` 对临时表的例外**
    * 禁止在只读事务里改表的原因是这张表可能被别的事务同时操作，会带来并发上的麻烦。
    * 临时表（temporary table）只在当前会话当中起作用、别的会话看不到它，所以处在 `READ ONLY` 事务下也依然可以增删改。

* **`autocommit` 变量的查看与修改**
    * 查看：`SHOW VARIABLES LIKE 'autocommit';`，默认值是 `ON`。
    * 关闭自动提交：`SET autocommit = false;` 或 `SET autocommit = 0;`。
    * `false` 与 `0`、`true` 与 `1` 是等价写法，`SHOW VARIABLES` 显示出来的是 `ON` / `OFF`。

* **两种让多条 DML 归入同一事务的写法**
    * 方式一：`SET autocommit = false;` 之后执行多条 DML，它们合在一起构成一个独立的事务，直到显式 `commit` 或 `rollback` 才算收尾。
    * 方式二：`autocommit` 保持 `true`，用 `START TRANSACTION` 或 `BEGIN` 开启事务，后面的 DML 就不再自动提交。
    * 更规范、更主动的写法是：自己主动开启事务，同时把 `autocommit` 改成 `false`，结束时按需要提交或回滚。
    * 要看清 `BEGIN` 之后 DML 不自动提交的原因——不是因为 `autocommit` 的事，而是因为前面加了一个 `BEGIN`。

* **会触发隐式提交的五类操作**
    * 隐式提交不受 `autocommit` 变量控制，把它关成 `false` 也没用。
    * 第一类数据定义语言（DDL）：`truncate table` 就属于 DDL，它会自动提交数据。
    * 第二类针对用户、权限、账户的语句：`ALTER USER`、`CREATE USER`、`DROP USER`、`GRANT`、`RENAME USER`、`REVOKE`、`SET PASSWORD`。
    * 第三类：事务没结束（既没 `commit` 也没 `rollback`）就再写一个 `begin`，上一个事务会自动提交，第二次 `BEGIN` 不会嵌套进第一个事务、也不会报错等你先结束前一个。
    * 第四类：当前 `autocommit` 为 `false`，手动把它调成 `on` 时，隐式提交前面所属的那个事务。
    * 第五类：`LOCK TABLES` / `UNLOCK TABLES`、`LOAD DATA`、复制相关语句（`START SLAVE`、`STOP SLAVE`、`RESET SLAVE`、`CHANGE MASTER TO`）、表维护语句（分析表、检查表、优化表）。
    * `autocommit` 主要约束的是 DML 操作，不在这张控制网里的语句该提交的时候一定会提交。

* **DML 与非 DML 的提交路径**

    ```text
            会不会被隐式提交？
                    |
          +---------+---------------------------+
          |                                     |
       DML 操作                           非 DML 操作
      （update / insert / delete）        （DDL、用户权限、锁表、
          |                                LOAD DATA、复制语句、表维护）
          |                                     |
      受 autocommit 控制                 不受 autocommit 控制
      ON  -> 每条独立自动提交            一律隐式提交
      OFF -> 合并为一个事务
    ```

## 提交回滚与保存点

* **`ROLLBACK` 的落点**
    * > **定义**：`ROLLBACK` 的含义是回滚到最后一次 `COMMIT` 之后。
    * 自动提交也算一次提交，所以最近的那次提交可能就是某条自动提交的 `INSERT`。
    * 落点前移的对照：有 `BEGIN` 时那条 `INSERT` 留在事务里未提交，回滚后只剩张三；没有 `BEGIN` 时它执行完即自动提交，回滚落点挪到它之后，结果是张三、李四都在。

* **保存点（`SAVEPOINT`）**
    * > **定义**：保存点是给事务中「到这里为止都做对了」的位置临时做一个记号，回滚到点上即可丢弃后面的错误操作。
    * 设置与回滚：`SAVEPOINT s1;`、`ROLLBACK TO SAVEPOINT s1;`，后者里的 `SAVEPOINT` 关键字可以不再写，直接写保存点名 `ROLLBACK TO s1;`。
    * 保存点用完、不再需要时可以直接释放：`RELEASE SAVEPOINT s1;`。
    * 演示轨迹：余额 1000 减两次到 800 后设 `s1`，误写成 `+1` 到 801，`ROLLBACK TO s1` 回到 800，此时再整体 `ROLLBACK` 回到 1000。
    * > **易错点**：`ROLLBACK TO SAVEPOINT` 不会让事务进入中止状态，事务还在进行中，仍然必须再走一次 `COMMIT` 或 `ROLLBACK` 才结束。

* **`completion_type` 的三种取值**

    | 取值 | 提交时的行为 | 说明 |
    | :--- | :--- | :--- |
    | `0` | 正常提交事务，下一个事务需要重新用 `START TRANSACTION` 或 `BEGIN` 开启 | 默认值，显示为 `NO_CHAIN` |
    | `1` | 相当于 `COMMIT AND CHAIN`：提交后自动开启一个相同隔离级别的新事务 | 链式事务 |
    | `2` | 相当于 `COMMIT AND RELEASE`：提交后自动与服务器断开连接 | `RELEASE` 是释放、断开连接的意思 |

    * 演示差别：设成 `1` 之后，重新插入的李四落在 `COMMIT` 自动开启的新事务里、没有被自动提交，随后被 `ROLLBACK` 一并撤销，结果只剩张三。
    * 查看与设置：`SELECT @@completion_type;` 与 `SET @@completion_type = 1;`。

* **事务的五种常见分类**
    * 扁平事务：用 `BEGIN` 开启，用 `COMMIT` 或 `ROLLBACK` 结束。
    * 带保存点的扁平事务：扁平事务里用上了 `SAVEPOINT`。
    * 链式事务：一个事务由多个子事务构成，执行完一个事务并 `COMMIT` 之后，通过一个触发器触发下一个事务的执行。
    * 嵌套事务：一个大事务里涉及几个子事务，子事务还可以再往下嵌套。
    * 分布式事务：数据分布在网络中不同的节点上，需要对不同节点的资源做调用和读写操作。

* **两类存储引擎在回滚上的差异**
    * 对比结构：`CREATE TABLE test1 (i INT) ENGINE = InnoDB;` 与 `CREATE TABLE test2 (i INT) ENGINE = MyISAM;`。
    * InnoDB 表在 `ROLLBACK` 之后数据被撤销，MyISAM 表在 `ROLLBACK` 之后数据依然在。
    * > **易错点**：在 MyISAM 表上执行 `BEGIN`、`ROLLBACK` 都不会报错，但也都不会生效；语句照跑、数据却已经落盘。

## 并发问题与四种隔离级别

* **并发访问的前提与四类问题**
    * 讨论前提是不保证串行执行：串行执行不会导致一致性问题，但性能太低。
    * 四种并发问题都长在事务交叉访问里：脏写、脏读、不可重复读、幻读。

    | 问题 | 事务 B 的动作（相对事务 A 的读） | 事务 A 的观察结果 |
    | :--- | :--- | :--- |
    | 脏写（Dirty Write） | A 改写之前，B 已经改过但未提交 | A 提交成功之后，值被 B 的回滚带回了改动前 |
    | 脏读（Dirty Read） | A 读之前，B 已经改过但未提交 | A 读到了 B 那份未提交、随后被回滚掉的值 |
    | 不可重复读（Non-Repeatable Read） | A 第一次读之后，B 改并提交 | A 第二次读同一个字段，值不一样了 |
    | 幻读（Phantom Read） | A 第一次读之后，B 插入新行并提交 | A 第二次读同一个范围，行数变多了 |


* **脏写（Dirty Write）**
    * > **定义**：事务 A 修改了另一个未提交事务 B 修改过的数据，就发生了脏写。
    * 时间线：T2 时 B 把姓名由小谷改成李四但未提交，T3 时 A 把它由李四改成张三并 `commit`，T4 时 B `rollback` 使值回到小谷，T5 时 A 查出来的是小谷。
    * 改动链条是小谷 → 李四 → 张三，最后又回到小谷；脏写是四个问题里最严重的。
    * 脏写在四种隔离级别里都已经解决，想再现一次脏写是再现不出来的，写与写之间天然互斥。

* **脏读（Dirty Read）**
    * > **定义**：事务 A 读取了已经被事务 B 更新、但是还未提交的字段；B 之后若回滚，A 读取的内容就是临时且无效的。
    * 时间线：T2 时 B 把姓名由小谷改成张三且没有提交，T3 时 A 读出来的是张三，T5 时 B `rollback` 使值回到小谷。
    * 判定三条件：读发生在两个不同的事务之间、被读的那个事务还没有结束、读到的值来自对方的未提交修改，三条都满足才是脏读。
    * 根治方向只有一个：把隔离级别提上去，读已提交及以上就不会再出现脏读。

* **不可重复读（Non-Repeatable Read）**
    * > **定义**：事务 A 读取了一个字段，随后事务 B 更新了这个字段并提交；事务 A 再去读这个字段，发现值不一样了。
    * 时间线：T2 时 A 读到的王五，T3 时 B 把王五改成张三并 `commit`，T4 时 A 再读出来的是张三，T6 时又成了李四。
    * 不可重复读的肇事者从来不是读的那个人，而是别的事务的提交。

* **幻读（Phantom Read）**
    * > **定义**：事务 A 从一张表中读取了一个字段（一个范围），随后事务 B 在该表中插入了一些新的行；事务 A 再去读同一张表时，发现多了几行。
    * 时间线：T2 时 A 读 `number > 0` 只找到张三，T3 时 B 插入赵六并自动 `commit`，T4 时 A 再读张三和赵六都出来了。
    * 多出来的那条记录称为幻影记录，幻读的关键词是插入。
    * 边界一：B 做的是删除记录、A 再查发现记录变少，不算幻读。
    * 边界二：先前能查到、之后又读不到了，非要追究可以理解成不可重复读的场景。

* **四种隔离级别与解决范围**
    * 级别定名：`READ UNCOMMITTED` 读未提交、`READ COMMITTED` 读已提交、`REPEATABLE READ` 可重复读、`SERIALIZABLE` 可串行化。
    * 四个问题的严重程度从高到低是脏写、脏读、不可重复读、幻读，级别越往下、解决的问题越多。

    | 隔离级别 | 脏读 | 不可重复读 | 幻读 |
    | :--- | :--- | :--- | :--- |
    | `READ UNCOMMITTED`（读未提交） | 可能发生 | 可能发生 | 可能发生 |
    | `READ COMMITTED`（读已提交） | 已解决 | 可能发生 | 可能发生 |
    | `REPEATABLE READ`（可重复读） | 已解决 | 已解决 | 可能发生 |
    | `SERIALIZABLE`（可串行化） | 已解决 | 已解决 | 已解决 |

    * 表里没有脏写这一列，因为这四种隔离级别都解决了脏写的问题，不用逐个比较。
    * 按 SQL 标准，可重复读只解决脏读和不可重复读；MySQL 的可重复读在一定程度上连幻读也能解决。

* **各数据库的支持情况与默认级别**

    | 数据库 | 支持的隔离级别 | 默认隔离级别 |
    | :--- | :--- | :--- |
    | Oracle | `read committed`、`serializable` | `read committed`（读已提交） |
    | MySQL | `read uncommitted`、`read committed`、`repeatable read`、`serializable` | `repeatable read`（可重复读） |

    * Oracle 只实现了标准四种里的两种，默认落在较松的那一档。

* **隔离级别与并发性能的权衡**

    ```text
    隔离级别                          解决的问题                        并发性能
    -------------------------------------------------------------------------
    SERIALIZABLE     脏写 + 脏读 + 不可重复读 + 幻读                    最差
    REPEATABLE READ  脏写 + 脏读 + 不可重复读                           较差
    READ COMMITTED   脏写 + 脏读                                        较好
    READ UNCOMMITTED 脏写                                               最好
    -------------------------------------------------------------------------
            隔离级别越高  -->  解决的问题越多  -->  并发性能越差
    ```

    * 可串行化的行为：事务 A 占用着这张表或这一行记录时其他事务都得等待，已经不是并发问题而是串行化场景，性能十分低下。

## 隔离级别的查看与设置

* **变量名的版本分界**
    * 在 5.7.20 之前的版本里系统变量名叫 `tx_isolation`；从 5.7.20 开始改用全称 `transaction_isolation`。
    * > **易错点**：变量名写旧了、拼错了 MySQL 不会报错，只是查不到这个变量、返回结果为空。

* **两种查看写法**
    * 写法一：`SHOW VARIABLES LIKE 'transaction_isolation';`，写成全名时属于精确匹配，只会返回这一条记录。
    * 写法二：`SELECT @@transaction_isolation;`，两个 `@` 表示取系统变量，读的是同一个变量、结果一致。
    * 默认查到的级别就是 `repeatable read`。

* **两种设置写法**
    * 写法一：`SET [GLOBAL | SESSION] TRANSACTION ISOLATION LEVEL <隔离级别>;`，级别名用空格分隔，不加引号。
    * 写法二：`SET [GLOBAL | SESSION] transaction_isolation = '<隔离级别>';`，级别要当成一个整体、用中划线连接且必须加引号。

    | 隔离级别 | 写法一里的写法 | 写法二里的取值 |
    | :--- | :--- | :--- |
    | 读未提交 | `READ UNCOMMITTED` | `'read-uncommitted'` |
    | 读已提交 | `READ COMMITTED` | `'read-committed'` |
    | 可重复读 | `REPEATABLE READ` | `'repeatable-read'` |
    | 串行化 | `SERIALIZABLE` | `'serializable'` |

    * `SET GLOBAL transaction_isolation = 'read-committed';` 分成三段：赋值动作 `SET`、作用范围 `GLOBAL`、变量名加值。
    * 查看时写成 `@@transaction_isolation`，赋值时不加 `@`，直接写变量名。
    * > **易错点**：两种写法里的分隔符千万别串——写法一用空格，写法二用中划线，且中划线是值的组成部分、引号不能省。
    * > **易错点**：级别名 `uncommitted` 是 u-n-c-o-m-m-i-t-t-e-d，两个 `m`、两个 `t`。

* **`GLOBAL` 的作用范围**
    * 设置的都是内存级别的值，服务重启（`systemctl restart mysqld`）后全部回归最初的默认值。
    * `GLOBAL` 设置对当前已经存在的会话无效：在会话 A 里设置完、回到会话 A 再查，原来是什么还是什么。
    * 它对后起的会话有效；把会话 A `quit` 退出再重新登录，等同于开了一个新会话，新设置就生效。
    * 验证后的四种观察：会话 A 设置后立刻查仍是可重复读、新开会话查到读已提交、会话 A 退出重连后是读已提交、重启服务后任意会话回到可重复读。

* **`SESSION` 的作用范围**
    * `SESSION` 是会话级的：在当前会话里改了级别，之后这个会话里的后续事务就都用这个值。
    * 落在两个事务之间时，后续事务全部用新的隔离级别。
    * 落在一个已经 `BEGIN` 的事务中间时，语句能执行成功但不会影响当前正在执行的事务，当前事务继续用之前的级别，再起一个新事务才用新值。
    * 观察结果：会话 A 执行 `SET SESSION` 后查到读未提交，另一个会话查到的仍是可重复读。
    * > **易错点**：`SESSION` 这个词千万不要省，省掉之后会出现一些莫名其妙的问题。

* **验证一条隔离级别设置的固定路线**

    ```text
      ① 查默认值 ──▶ ② 执行设置 ──▶ ③ 在当前会话再查 ──▶ ④ 换一个会话查
                                                                  │
                                            （只有 GLOBAL 才需要） │
                                                                  ▼
                                                  ⑤ 重启服务，再查一遍

      每一步都在回答同一个问题：这一次，是"谁"的级别变了？
    ```

## 隔离级别的现象演示

* **演示环境与账户表**
    * 转账场景用 `account` 表：`id` 是主键、`name` 是账户名、`balance` 是余额。
    * 基础数据：`INSERT INTO account (id, name, balance) VALUES (1, '张三', 100), (2, '李四', 0);`。
    * 两条 `INSERT` 前面没有 `BEGIN`、也没有 `START TRANSACTION`，靠默认的 `autocommit` 为 `true`，一条 DML 自成一个事务、执行完就提交。
    * 两个会话都用 root 登录没有任何问题，会话是不是同一个跟用什么用户名登录无关。

* **单条更新下的脏读**
    * 事务 1 执行 `BEGIN;` 与 `UPDATE account SET balance = balance + 100 WHERE id = 1;`，修改既没提交也没落盘。
    * 事务 2 执行 `SELECT * FROM account;` 读出来的张三已经是 200，读到的是临时且最终无效的值，它从来没有真实存在过。
    * 事务 1 执行 `ROLLBACK;` 后张三又回到 100。

* **转账场景下的脏读、锁等待与余额错位**
    * 事务 1 在 `BEGIN` 里执行张三减 100、李四加 100 两条 `UPDATE`，自己查到 0 和 100，但事务没有结束。
    * 事务 2 `BEGIN` 后也读到 0 和 100，接着执行 `UPDATE account SET balance = balance - 100 WHERE id = 2;` 时卡住。
    * 卡住的原因是事务 1 还占着这一行的排他锁（Exclusive Lock，X 锁），事务 2 要改同一行只能排队等待；锁要等事务 1 结束才释放，不管它是提交还是回滚。
    * 事务 1 `ROLLBACK` 后事务 2 被卡的 `UPDATE` 立刻执行，李四那行此刻是 0，减完是 -100；随后再加回张三那行，100 加 100 成 200。
    * 最终两个会话都查到张三 200、李四 -100，两个数加起来仍是 100。
    * > **易错点**：卡住不是连接断了、也不是服务忙不过来，而是写操作要持有被修改行的 X 锁；脏读是「读」这一侧没有任何阻拦，锁等待是「写」这一侧必须排队。

* **脏读演示的时点与合计对照**

    | 时点 | 张三 balance | 李四 balance | 合计 |
    | :--- | ---: | ---: | ---: |
    | 演示开始（磁盘上的值） | 100 | 0 | 100 |
    | 事务 1 未提交（只在事务 1 内可见） | 0 | 100 | 100 |
    | 事务 2 脏读读到的值 | 0 | 100 | 100 |
    | 事务 1 回滚之后 | 100 | 0 | 100 |
    | 事务 2 提交之后 | 200 | -100 | 100 |

    * 合计数正确不代表结果正确，脏读破坏的是判断依据：事务 2 是拿着一个最终不成立的状态做出的决定。

* **读已提交（READ COMMITTED）下的脏读防护**
    * 两个会话各执行一次 `SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;`。
    * 事务二 `BEGIN` 后执行 `UPDATE account SET balance = balance - 50 WHERE ID = 1;`，自己查到张三 50、李四 0，事务内部自己改的看得见。
    * 事务一此时查到张三还是 100，读到的是磁盘上还存着的值，脏读被避免（若级别仍是读未提交，这里会直接看到 50）。
    * 事务二 `COMMIT` 后的事务一还未结束，它再查一次，结果变成了张三 50——同一条 `SELECT` 在同一个还没结束的事务里执行两次、拿到的值不一样，这就是不可重复读。
    * > 结论：`read committed` 只保证你读到的是已提交的数据，不保证你在一个事务里读到的值一直不变。

* **可重复读（REPEATABLE READ）下的事务内一致**
    * 两个会话各执行一次 `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;`。
    * 事务二 `BEGIN` 后查到张三 50、李四 0；事务一 `BEGIN` 后把张三减 10 变成 40，事务二再查还是 50，脏读被避免。
    * 事务一 `COMMIT` 之后事务二再查仍是 50——它在事务内第一次读到的是 50，此后读就一直沿着这个起点走，别的事务提交了 40 它也不改口，不可重复读被解决。
    * 快照建立在事务内第一次读的那一刻；事务二自己 `COMMIT`、事务终结之后再查才跟上磁盘变成 40。
    * > **易错点**：可重复读的「不变」是有边界的，它保证的是同一个事务内重复读一致，事务一结束、快照失效，新事务照样读到最新值。

* **两个级别的现象对照**

    | 隔离级别 | 事务二改完未提交，事务一读 | 事务一提交后，事务二在自身事务内再读 | 事务二提交后（事务结束）再读 |
    | :--- | :--- | :--- | :--- |
    | `read committed` | 张三 `100`（脏读被避免） | 张三 `50`（值变了，不可重复读） | 张三 `50` |
    | `repeatable read` | 张三 `50`（脏读被避免） | 张三 `50`（值不变，可重复读） | 张三 `40`（快照结束，读到最新） |


* **幻读的复现与隐式证明**
    * 事务 2 先 `begin` 再执行 `select count(*) from account where id = 3;`，结果是 0；顺序上是先开启事务再做查询，不是查完了才 `begin`。
    * 事务 1 `begin` 后执行 `insert into account(id, name, balance) values (3, '王五', 100);` 并 `commit`，事务 1 完全结束、数据写到磁盘。
    * 事务 2 再查同一个语句还是 0，但把那条 `insert` 复制过来执行会报 `duplicate` 唯一性约束错误。
    * 「查出来是 0、插入却报重名」这个组合就隐式地证明记录确实多了，事务 2 随后执行 `rollback`。

* **幻读的两类解法与取舍**

    | 方案 | 幻读是否避免 | 并发性能 | 关键手段 |
    | :--- | :--- | :--- | :--- |
    | `serializable` | 避免 | 差，读操作也被串行化 | 隐式加行的独占锁或间隙锁 |
    | `repeatable read` | 可以避免 | 较好 | 行的 X 锁（独占锁），按索引加锁 |
    | `read committed` | 不能避免 | 好 | 无相应加锁 |

    * 串行化的过程：事务 2 的 `select ... where id = 3` 虽为 0 条仍对 `id = 3` 加锁，事务 1 的 `insert` 被阻塞；事务 2 自己插得进去并 `commit` 放锁，事务 1 此时才轮到执行、报 `duplicate`。
    * 可重复读的过程：事务 2 没查到 `id` 为 3 的记录也会去锁定，锁的不是那条不存在的记录，而是索引上 `id` 为 3 的这个位置。
    * 隔离级别还可以改成持久生效：在配置文件里加参数 `transaction_isolation`（值可写 `serializable` 或 `read-committed`）并重启服务器；不想重启当前服务器就再用 `set global` 让它立刻生效，两件事可以分开做。

## redo 日志的必要性与 WAL

* **内存与磁盘的落差**
    * 数据的存储和访问都以页为最基本单位，访问页面时把磁盘中的数据以页为单位加载到缓冲池（buffer pool），增删改都先改内存层面、再以一定的频率更新到磁盘。
    * > **定义**：在刷盘之前，内存中改了、磁盘中还没改、两边还没同步的那个页叫脏页。
    * 刷盘必须做的两个理由：不更新则内存与磁盘不一致；内存不稳定、一旦断电就没有了。
    * 以一定频率刷新磁盘对应的机制叫 `Checkpoint`（检查点）机制。
    * > **定义**：只有真正把数据更新到磁盘里才算达到持久性，只更新了内存不能叫持久性。

* **未提交时宕机：不涉及刷盘**
    * 事务里做了几次内存修改之后服务器宕机，因为事务没提交，相当于这个事务没做。
    * 重启以后磁盘中的数据还是事务执行之前的状态，内存中的数据随内存一起没了，从逻辑上讲满足 ACID。

* **提交之后、刷盘之前宕机：持久性失守**
    * 时间轴：t1 最后一条 DML 执行完、内存里的操作全改好，t2 `commit` 逻辑上事务已经结束并提交，t3 本应在这里刷盘（刷盘频率一秒一次）。
    * 在 t2 到 t3 这不到一秒的窗口里宕机：内存中的修改全部丢失、磁盘中仍是最初的数据，而事务已经提交，持久性保证不了。

* **实时刷盘方案的两笔代价**
    * 代价一：修改量与刷新磁盘的工作量严重不成比例——只改页当中的一个字节，也要把这个页的数据完整刷新到磁盘，默认一页是 16 KB。
    * 代价二：随机 I/O——把工资是 5,000 的记录都改成 6,000，这些记录有可能存储在不同的页里，往磁盘刷新的时候这些页可能并不连续，得一个页一个页地去找。
    * 这两笔代价叠加，导致实际上没有选择实时刷盘这种做法。

* **redo 日志的引入与 WAL**
    * 做法是把内存中的修改先保存到一个文件里，这个物理磁盘上真实存在的文件就叫 `redo` 日志，后续刷盘仍按一秒一次的频率进行。
    * 服务器重启以后，因为事务已经提交、内存中改了、日志文件里也记录了，就把 `redo` 日志中的这些数据重新做一次恢复、对磁盘做出修改。
    * 这套技术叫 `WAL`（Write-Ahead Logging，日志优先写）：对内存中的数据做了更改之后，先保存到日志里，再考虑刷盘或恢复。

* **redo 日志的好处与特点**
    * 好处一：降低了刷盘的频率，相较实时刷盘仍然可以维持一秒刷一次。
    * 好处二：占用的空间比较小。
    * 特点一：`redo` 日志是顺序写入磁盘的，顺序 I/O 比随机 I/O 要快一些。
    * 特点二：事务的执行过程中 `redo log` 是不断记录的。

* **`redo log` 与 `binlog` 的区别**

    | 对比项 | `redo log` | `binlog` |
    | :--- | :--- | :--- |
    | 是否同一套日志 | 独立的一套 | 与 redo log 不是同一套 |
    | 产生层次 | 存储引擎层 | 数据库层（Server 层） |
    | 记录时机 | 事务执行过程中不断记录 | 事务提交时一次性写入 |
    | 主要用途 | 崩溃恢复、保证持久性 | 主从复制的数据同步 |

    * `binlog` 的场景：主机负责写、从机负责读，主机写入一条记录就在 `binlog` 里做一条记录，从机从 `binlog` 里把这个数据恢复过来。

## redo 日志的刷盘策略

* **内存层：重做日志缓冲（redo log buffer）**
    * 服务器启动时向操作系统申请一片空间专门用来存重做日志，默认大小是 16 兆，通过 `show variables like 'innodb_log_buffer_size';` 查看和修改，最小值可以是 1 兆。
    * 这片空间内部被分割成一个个 `redo log block`（日志块），一个块占 512 个字节。

* **持久化层：重做日志文件（redo log file）**
    * 默认在当前的数据目录（`/var/lib/mysql`）下有两个文件：`ib_logfile0` 与 `ib_logfile1`，两个文件的大小一模一样。
    * 两个文件一样大不是因为日志已经写满，而是先把空间开辟出来，之后文件不会再变大——空间预留式占用。
    * 恢复不是内存层面的恢复，内存一崩就没了，所谓恢复指的是从磁盘中的这两个文件里恢复。

* **redo 日志的两层结构与数据落点**

    ```text
                    内存（易失）                          磁盘（持久）
            ┌──────────────────────────┐        ┌──────────────────────────┐
            │      redo log buffer     │        │      redo log file       │
            │   默认 16M，可 1M 起调    │        │  ib_logfile0             │
            │  ┌────────┬────────┬───┐ │        │  ib_logfile1             │
            │  │ block  │ block  │...│ │        │  （大小固定、预先占好）    │
            │  │ 512B   │ 512B   │   │ │        │                          │
            │  └────────┴────────┴───┘ │        │                          │
            └──────────────────────────┘        └──────────────────────────┘
                        │                                   ▲
                        │            ┌──────────────┐       │
                        └───────────►│  page cache  │───────┘
                                     │（操作系统管） │
                                     └──────────────┘
    ```

    * 两者之间并不是直连的，中间隔着由操作系统管理的文件系统缓存 `page cache`。

* **一个更新事务的四步流转**
    * 第一步：把要改的数据页从磁盘加载进内存，放到缓冲池里。
    * 第二步：事务语句在内存里改数据，并按 write-ahead logging 的要求，在内存层面这个 `redo log buffer` 当中做一条记录。
    * 第三步：把 `redo log buffer` 的内容刷到磁盘中的 `redo log file`。
    * 第四步：以一定频率把内存中数据页的修改刷盘到磁盘。
    * > **易错点**：第二步不等事务 `commit` 之后才做，事务执行过程当中就已经开始记录了，实时记录与事务提交无关、也与刷盘参数无关。
    * 所谓 write-ahead logging 说的就是日志先落、数据页后落。

* **四步流转的链路示意**

    ```text
      磁盘                          内存                        磁盘
    ┌────────────┐  ①加载数据页  ┌────────────────────┐
    │  数据表     │─────────────►│    buffer pool     │
    │ （数据页）  │              │  ②语句在内存中修改  │
    └────────────┘              └─────────┬──────────┘
          ▲                               │
          │                               │ ③write ahead：先记日志
          │                     ┌─────────▼──────────┐
          │                     │   redo log buffer  │
          │                     └─────────┬──────────┘
          │                               │
          │  ④按频率刷脏页                │ ③刷盘
          │                               ▼
    ┌─────┴──────┐              ┌────────────────────┐
    │  数据文件   │              │   redo log file    │
    └────────────┘              │ ib_logfile0 / 1    │
                                └────────────────────┘
    ```

    * 刷盘策略管的是第三步，不是第四步；把修改记录到 `redo log file` 之后，MySQL 服务挂了或整个操作系统挂了都不用担心。

* **`page cache` 这一层中间结构**
    * `redo log buffer` 刷新到文件里其实不是直接刷新到磁盘，中间要经过文件系统缓存 `page cache`。
    * 所以刷盘操作其实是两个过程：`buffer → page cache` 与 `page cache → redo log file`。

* **`innodb_flush_log_at_trx_commit` 的三种取值**
    * 这个参数管的是事务提交的时候该如何刷新 redo log 日志。
    * 查看：`show variables like 'innodb_flush_log_at_trx_commit';`；设置：`set global innodb_flush_log_at_trx_commit = 1;`，必须按 `global` 级别设置，不带作用域的写法会报错。

    | 取值 | 事务提交时做什么 | 谁来决定落盘 | 持久性风险 |
    | :--- | :--- | :--- | :--- |
    | `1` | 同步刷盘：buffer → page cache → file 一次做完 | 提交动作本身 | 提交成功即安全；效率稍差 |
    | `2` | 只做 buffer → page cache，后边不管 | 操作系统，约每秒一次 | MySQL 挂了没事，操作系统挂了丢 |
    | `0` | 提交时什么都不做 | InnoDB 后台线程，每秒一次 | MySQL 挂、操作系统挂都丢；事务没提交也会被刷 |

    * 取值为 `1`（默认值）时，只要事务提交成功数据就已经落到文件里，持久性保证最好、代价是性能稍微差一点。
    * 取值为 `1` 时的刷盘频率还跟事务持续时间有关：事务持续 2 秒，这 2 秒里后台线程每隔一秒就已经刷了一次；事务只执行 0.5 秒，还没等到那一秒的点、提交时的刷盘动作就已经做完了。
    * 取值为 `0` 时执行的是 InnoDB 后台线程每秒一次的动作：把 `redo log buffer` 中的内容写入文件系统缓存，然后调用刷盘操作，它不看你提交没提交。
    * 取值为 `2` 时只要一提交事务就马上把 `redo log buffer` 更新到 `page cache`，之后 `page cache → redo file` 交给操作系统、大约每隔一秒钟做一次。
    * > **注意**：取值为 `0` 时会出现一个特别的情况——一个没有提交事务的 redo log 也会出现刷盘。

* **三种取值的持久化边界**
    * 值为 `0`：提交那一刻什么都不做、全靠后台线程每秒一次，不能保证数据安全性、有丢失数据的风险，是三种取值里最「放飞」的一种。
    * 值为 `2`：MySQL 服务器挂了不受影响，因为提交事务时数据已经更新到文件系统缓存、这块已归操作系统管；操作系统挂了就受影响，`page cache` 一挂当前事务就相当于没有保存到 `redo log file` 当中。
    * 值为 `2` 相对值为 `0` 的关键差别：MySQL 服务挂了以后 `redo log buffer` 这块不靠谱，但 `page cache` 里的内容还在。

* **三种取值在时序上的分岔**

    ```text
    时间轴 ──────────────────────────────────────────────────────────────►
            执行事务（redo log buffer 实时记录，与参数无关）
                                         │
                                      提交事务
                                         │
            ┌────────────────────────────┼────────────────────────────┐
            │                            │                            │
         值为 1                       值为 2                       值为 0
            │                            │                            │
       buffer→page cache          buffer→page cache            提交时无任何动作
            │                            │                            │
       page cache→file             （等待操作系统）                （等待后台线程）
       （同步，立即）                    │                            │
            │                      约每秒一次刷 file              每秒一次 buffer→
            │                            │                       page cache→file
            ▼                            ▼                            ▼
      提交即持久化              0.5s 窗口内 OS 挂则丢       未提交的事务也会被刷盘
    ```


* **三种取值的实测耗时对比**
    * 测试设计：在 `atguigudb3` 库建 `test_log` 表，用一个存储过程循环 30000 次插入，插入时主键位置写 `null` 交给自增列、字符列写入 `repeat('c', 80)` 构成的 80 字符定长值；过程里每插入一条就 `commit` 一次，所以 3 万条插入相当于 3 万个事务。

    | 测试 | `innodb_flush_log_at_trx_commit` | 执行 3 万条插入的耗时 | 说明 |
    | :--- | :--- | :--- | :--- |
    | 测试 1 | `1`（默认） | 1 分 28 秒 | 耗时最长，持久性最有保障 |
    | 测试 2 | `0` | 37.945 秒 | 耗时最短，安全性最差 |
    | 测试 3 | `2` | 45 秒多 | 介于两者之间，与 0 比较接近 |

    * 耗时关系大约在一比三这样的量级；取值 `0` 和 `2` 时两者耗时比较接近，都比取值为 `1` 时更少。
    * 建议仍相对 `0` 和 `2` 选择 `1`；唯一的例外是讲数据库调优案例时那种服务器宕机的场景，当时是把 1 改成了 2。
    * 插入 3 万条数据本身应该整体看成一个事务来操作，不要每插一条就 `commit` 一次。
    * 判断标准两条：要不要接受「提交后仍可能丢」的窗口；能不能接受「每次提交都同步刷盘」的开销。

## redo 日志的文件结构与循环写入

* **迷你事务（mini-transaction，MTR）**
    * > **定义**：MySQL 把对底层页面的一次原子访问的过程称为一个迷你事务，一个 MTR 可以包含一组 redo 日志记录。
    * 往索引对应的 B+ 树里插一条记录就是一次原子操作，也就是一个 MTR。
    * 一个 MTR 里一定有多条 redo 记录：插入位置之后原来在后头的记录得往后移，这一页本来就满时还得往下一页移，每一下都要记日志。
    * 包含关系：一个事务可能包含多个语句，每一个语句由若干个 MTR 构成，每个 MTR 又对应一组 redo 日志记录。
    * 示例：`update 表名 set salary = 6000 where salary = 5000;` 这一条语句底下要改的位置可能不止一处，每改一个位置相当于一次原子化的访问。

* **事务、语句、MTR 与 redo 日志的包含关系**

    ```text
    事务（transaction）
     |
     +-- 语句 1
     |    |
     |    +-- MTR-1 --+   redo #1
     |    |           +   redo #2
     |    |           +   ...（一组，必须连着）
     |    |
     |    +-- MTR-2 --+   redo #1
     |                 +   ...
     |
     +-- 语句 2
     |    +-- MTR-1 ...
     |
     +-- 语句 3 ...
    ```


* **日志块的组成与 `buf_free` 指针**
    * 一个 `redo log block` 由日志头（log block header）、日志体（log body）、日志尾（log block trailer）三部分构成，头和尾不存数据，真正放数据的是日志体。
    * 日志体里放的是一条一条的 redo 记录，填满一个块就依次往后走，前一个块满了就挤到下一个块。
    * 变量 `buf_free` 记录当前使用到哪个位置，之后新来的 redo 日志就从它指的位置继续往后放。

* **MTR 内部连续与 MTR 之间交错**
    * > 结论：一个 MTR 内部的 redo 日志必须完全挨着，不同 MTR 之间可以不挨着。
    * 事务本身是并发执行的，两个事务的 MTR 就可能交替地落在 `redo log buffer` 里；一个 MTR 在当前块里放不下时会跨到下一个块继续写。

* **日志缓冲中的实际排布**

    ```text
    redo log buffer 中的实际排布（两个事务共 4 个 MTR 交替落入）

    |<- block ->|<- block ->|<- block ->|<- block ->|<- block ->|
    +-----------+-----------+-----------+-----------+-----------+
    | T1-MTR1   | T1-MTR1   | T2-MTR1   | T1-MTR2   | T1-MTR2   | ...
    | redo #1   | redo #2   | redo #1   | redo #1   | redo #2   |
    +-----------+-----------+-----------+-----------+-----------+
                                                            ^
                                                         buf_free

      T2-MTR2 随后接在这里
    ```


* **日志块的字节划分与 512 字节的来源**
    * 块内三部分的字节数：日志头占 12 个字节、日志尾占 8 个字节，中间能存 redo 记录的是 492 字节。

    $$512 - 12 - 8 = 492$$

    * 块设计成 512 字节与磁盘扇区有关：机械磁盘默认一个扇区是 512 个字节，两者正好完全匹配。
    * 匹配的意义：写入数据大于 512 字节就要占两个扇区、得转动磁盘去找下一个扇区；A 扇区写成功而 B 扇区写失败还会出现非原子性的操作。

* **日志文件的位置与容量参数**

    | 参数 / 变量 | 作用 | 取值 |
    | :--- | :--- | :--- |
    | `innodb_log_group_home_dir` | redo log 文件的存放目录 | `.\`（即当前数据目录） |
    | 控制日志文件个数的系统变量 | 一个日志文件组里有几个文件 | `2` |
    | 控制单个文件大小的系统变量 | 每个日志文件多大 | 换算后为 48 MB |
    | 刷盘策略参数 | redo log buffer 何时刷到 redo log file | `innodb_flush_log_at_trx_commit` |

    * 用 `SHOW variables LIKE '%innodb_log%';` 可以看到这些变量；`innodb_log_group_home_dir` 只负责位置，文件个数与单个文件大小分别由另外两个变量控制。
    * 日志文件（组）的大小最大可以是 512 GB，这是整个组的上限而不是每个文件的上限；默认两个文件、每个 48 MB，当前占用 96 MB。
    * 文件显示为 48 MB 并不意味着当前已经把这个文件完全占满，48 MB 是文件的容量而不是当前的使用量。
    * 数据库实例更新得比较频繁时，可以把 group 增大，同时把每个文件的大小也设大一些，单个文件的大小可以通过修改配置文件设置。

* **容量不足时的复用前提**
    * 内存中的数据只要被更新了都要记录到 `redo log file` 里；反过来，内存中的数据已经更新到磁盘上了，它在 `redo log file` 里按说就没有必要再存。
    * 算式示例：当前待刷盘的数据是 90 MB，文件里另有 10 MB 是已经刷盘到磁盘的数据，按 90 + 10 = 100 MB 算存不下；把这 10 MB 覆盖掉后剩下 96 MB，90 MB 就放得下。
    * > 结论：`redo log file` 之所以能被循环覆盖，前提是被覆盖的那段数据已经刷盘到磁盘，它的日志使命已经完成。
    * 这么多日志文件合在一起构成一个日志文件组（log file group），组里每个文件的大小都一样；写入从头部开始，写到最后一个文件写完就翻回来再从头部接着写。

* **`write pos` 与 `checkpoint` 的推进**
    * `write pos` 记录当前写到哪儿，一边写一边往后移；`checkpoint` 是当前要擦除的位置，同样往后推移。
    * 最初两个变量都停在同一个位置上，只要往日志文件里写数据 `write pos` 就一直往后移。
    * 随着把内存中的数据刷新到磁盘，`redo log file` 里对应的那部分记录就没有必要了，于是 `checkpoint` 从它这个位置开始往后移。
    * > 结论：环上从 `write pos` 绕行到 `checkpoint` 的整段，都是可以再次写入的空间。

* **两个指针的相对位置与覆盖边界**

    ```text
    write pos 与 checkpoint 的三种相对位置

     情形一：正常推进（中间是未刷盘数据，后方是空闲）
    +--------+--------+--------+--------+
    | 空闲   | 空闲   | 已记录未刷盘      |
    +--------+--------+--------+--------+
          ^                   ^
      checkpoint           write pos

     情形二：write pos 绕行一圈，与 checkpoint 重合
    +--------+--------+--------+--------+
    | 已记录、未刷盘（占满整圈）        |
    +--------+--------+--------+--------+
                         ^
              write pos = checkpoint
              （下一刻 checkpoint 后移即可继续写）

     情形三：write pos 将要超过 checkpoint —— 文件真的满了
    +--------+--------+--------+--------+
    | 未刷盘（不可覆盖）| 未刷盘（不可覆盖）|
    +--------+--------+--------+--------+
                    ^              ^
              write pos        checkpoint
              （再往后写就无路可走，需要扩容）
    ```

    * `write pos` 与 `checkpoint` 重合时如果下一刻 `checkpoint` 接着往后移动就没问题，两个指针之间又腾出可以再次写入的空间。
    * `checkpoint` 后边的那部分数据还没有进行刷盘操作、不能覆盖；`write pos` 要去超过 `checkpoint` 就意味着这个日志文件真的是已经满了。

* **WAL 策略的整体把控**
    * > **定义**：预写式日志（Write-Ahead Log，WAL）说的是先把数据写入日志文件，然后才考虑把内存中的数据进行刷盘。
    * 环上从 `checkpoint` 到 `write pos` 的那一段是「已经写了日志、但还没刷盘」的数据，必须被保护起来、不能被覆盖。
    * 只有数据真正刷到磁盘之后 `checkpoint` 才能往前推，那一段空间才被释放出来供回卷覆盖。

## undo 日志的组织与版本链

* **undo 日志的基本概念与写入位置**
    * > **定义**：为了支持回滚而记录下来的内容，就叫撤销日志，也叫回滚日志（undo log）。
    * 更新数据的前置操作是先写入一条 undo log；它记录的是更改之前的数据，因为回滚要回到更新之前的状态。
    * 这里的「更新」是泛指：`insert`、`delete`、`update` 都算，唯独 `select` 不算，查询操作不会写入 undo 日志。
    * 正因为记录的是旧值、写的是逻辑信息，undo 日志整体上比 redo 日志要简单。
    * 还有一点要单独留意：undo log 本身也会产生 redo log，它同样需要持久化保护。

* **undo 日志在事务原子性中的作用**
    * 意外情况有两个来源：服务器本身（MySQL 数据库服务器、操作系统、甚至物理层面的断电）与我们主动执行 `rollback`。
    * 事务里的多个操作只执行了一半时，要用「退回去」的记录把执行到一半的事务抹平，效果上这个事务之前做的事等于什么也没做。

* **回滚数据这个作用的边界**
    * > **易错点**：undo 日志不可能把我们这个数据物理性地恢复到之前。
    * 示例：事务里插入一条数据时页满了，于是开辟了一个新的数据页，随后 `rollback` 只是相当于又做了一次 `delete`、把刚添加的那条数据删掉，而物理层面上的这个数据页不会跟着消失。
    * 页不能收回的原因：一个数据库里可能同时执行几百个甚至上千个并发事务，别的插入可能用的就是同一个新数据页。
    * 我们只是从逻辑上把数据恢复成原来的样子，物理层面上已经发生的变化改不了；所以 undo 与 redo 绝不是互为逆过程。

* **多版本并发控制（MVCC）这个作用**
    * InnoDB 存储引擎的 MVCC 实现是通过 undo 来完成的。
    * 当用户读取一行记录时，如果该记录已经被其他事务占用，当前事务可以通过 undo 读取这行记录之前的行版本信息，从而实现非锁定读取。

* **undo 日志的存储结构**
    * undo 日志采用段的方式来组织，这个段称为回滚段（rollback segment）。
    * 每个 rollback segment 里记录了 1024 个 undo log segment，在每一个 undo log segment 当中进行 undo 页的申请，undo 页里才是真正写的回滚记录。
    * 回滚段个数：InnoDB 1.1 版本之前（不包括 1.1）只有一个回滚段，意味着同时可以有 1024 个事务并发执行；1.1 之后 InnoDB 最大支持 128 个回滚段，128 × 1024 就能同时支持这么多在线并发事务。
    * 这些回滚段的数据都存在 `ibdata` 里，它是一个共享表空间。

    | 参数 | 含义 | 说明 |
    | :--- | :--- | :--- |
    | `innodb_undo_directory` | undo log 的存储位置 | 默认值是一个点即 `./`，实际存在当前数据目录下 |
    | `innodb_undo_logs` | 回滚段的个数 | 默认回滚段数量 |
    | `innodb_undo_tablespaces` | 构成回滚段的文件数量 | 可以设置多个，至少得有两个 |

    * undo 表空间至少要有两个的理由：这一个文件正在使用，另一个文件就可以拿去做一些清理操作，这样才有腾挪的余地。

* **undo 页重用**
    * 如果每个事务都去申请一个独立的页、而一个页的大小是 16 KB，这样分配非常浪费。
    * 算账：TPS 如果是 1000，1 秒钟一个事务对应一个页就是 1000 个页、大概 16 MB；一分钟下来相当于 1 GB。
    * 一个 undo 页当中可能混杂着好几个事务的记录；事务提交以后这个 undo 页会被放到一个链表当中，如果它的使用空间小于 3/4 就可以被重用。

* **回滚段与事务的六条关系**
    * 每个事务都会使用一个回滚段，而一个回滚段在同一个时刻可能会服务于多个事务。
    * 一个事务开始的时候会指定一个回滚段；事务进行的过程中数据被修改时，原始数据会被复制到这个回滚段里边。
    * 在回滚段中，事务会不断地填充盘区，直到事务结束、或者所有空间被用完。
    * 盘区不够用时，事务会在段当中请求下一个盘区；如果所有的盘区都用完了，事务会覆盖最初的盘区，或者在回滚段允许的情况下扩展新的盘区。
    * 事务提交的时候 InnoDB 判断两件事：是不是要提交了（提交后就可以把 undo log 放到列表当中供清除线程清理）、undo log 所在的页是不是可以被重用。

* **回滚段中数据的三种状态**
    * 第一种，未提交的回滚数据：事务里每做一次增删改之前都把原始数据记一笔，事务还没提交时随时可能回滚。
    * 第二种，已经提交但未过期的回滚数据：事务提交后不能马上删除 undo log 和它所在的页，因为可能还有其他的事务要通过 undo log 取得行记录之前的版本。
    * 第三种，已经提交并且已经过期的回滚数据：到这一步 purge 线程才会最终判断这个 log 和它所在的页是不是要删掉、是不是可以重用。

* **undo 的两种类型**

    | undo 类型 | 来源操作 | 对其他事务可见性 | 事务结束后的处理 |
    | :--- | :--- | :--- | :--- |
    | `insert` 类型 | `insert` | 不可见（隔离性要求） | 事务结束即可直接删除 |
    | `update` 类型 | `update`、`delete` | 可能被其他事务读取旧版本 | 放入 undo log 链表，交由 purge 线程判断 |

    * 没有 `delete` 类型，因为 `delete` 跟 `update` 合在一起了。
    * purge 线程的作用有两个：负责清理 undo 页，以及清除数据页里带有 `deleted bit` 标识的数据行（真正删除一条数据时只是把标记由 0 改成 1，并没有真正删掉）。

* **日志优先的写入顺序**

    ```text
            ┌──────────────┐
            │  Buffer Pool │（内存中的数据页，含更新后的最新值）
            └──────┬───────┘
       更新前记录旧值│            │更新后写入新值
            ▼                    ▼
       undo log（回滚段文件）   redo log buffer（内存）
            │                    │ 按参数控制的策略刷盘
            │                    ▼
            │              redo log file（磁盘日志文件）
            │                    │
            └────────► 后续再把内存中的数据页刷盘到磁盘数据页
    ```

    * 执行器完成更新操作后，要把更新后的数据记录到内存层面的 `redo log buffer` 里面，再由参数控制的策略把它更新到磁盘中的 redo 文件里。
    * 这么安排的道理就是日志文件优先（write-ahead logging）：先写日志，然后才把内存中的数据刷盘到真正磁盘中的数据页。
    * 这个过程中还要处理 `binlog` 日志文件，它是为主从复制准备的：主机把数据记录到 binlog 之后，从机拿到这个文件就能知道主机做了哪些操作。

* **行格式的三个隐藏列**
    * `row_id`：表里没有显式定义主键时，系统自动选择一个非空的唯一索引；这个也没有时 InnoDB 会自动添加一个叫 `row_id` 的隐藏列作为主键。
    * `transaction_id`：事务 ID，记录这条记录目前是哪一个事务正在操作它。
    * `roll_pointer`：回滚指针，记录的是关联到 undo log 的位置。

* **undo 版本链的构建过程**

    ```text
    行记录（最新状态永远在行里）
    ┌──────────────────────────────────────────────┐
    │ delete mark = 0                              │
    │ 事务 ID                     = 当前事务        │
    │ roll_pointer ────────────────────────┐       │
    │ id = 1                               │       │
    │ name = Tom                            │       │
    └──────────────────────────────────────┼───────┘
                                           ▼
                                undo log 编号 0（插入之前的行为）
    ```

    * 在 `begin` 里启动事务添加一条 Tom 记录：`delete mark` 是 0，事务 ID 记的是当前事务，回滚指针指向这条记录添加之前的那个行为。
    * 再 `update` 把 `id=1` 的名字从 Tom 改成 Rose：新生成的 undo log 编号 1 被记录的回滚指针所指，而这个新的 undo log 又去指向旧的 undo log 编号 0。
    * 再 `update` 把 `id=1` 改成 `id=2`：底层不是简单把 1 改成 2，而是把原来的记录标记为已删除状态、重新生成一条 `id` 是 2、名字还是 Rose 的记录，同时产生编号 2 的 undo log，记录 `delete mark` 由 0 变成 1 的过程与新记录的相关信息。
    * > **定义**：行记录本身永远记录最新的数据，历史值一律留在 undo 日志里，靠回滚指针一层层串起来。

* **回滚的执行顺序**

    ```text
    rollback
       │ ① 执行 undo log 编号 3：删除 id = 2 那条记录
       │ ② 执行 undo log 编号 2：delete mark 由 1 改回 0，让 id = 1 的记录回来
       │ ③ 执行 undo log 编号 1：把 Rose 改回 Tom
       │ ④ 再往前：insert 对应的两个行为也一并没了
       ▼
    回到事务开始之前的状态
    ```

    * 回滚是从最近的一条开始，沿着版本链由新到旧逐条反向执行。

* **undo log 的删除时机**
    * `insert` 行为：对其他事务不可见，只要事务结束（`commit` 已提交状态或相当于 `rollback` 的终止状态）这些 `insert` undo log 就没有用了，可以直接删除。
    * `update` 行为：涉及多版本并发的访问，需要先放到 undo log 链表当中，等事后的 purge 清除线程来决定要不要删。

## 事务控制举例的完整梳理

* **演示前的准备工作**
    * 先查 `SHOW VARIABLES LIKE 'autocommit';`，若是 `OFF` 就执行 `SET autocommit = true;` 改回默认行为，后面这组演示都建立在默认情况之上。
    * 建表：`CREATE TABLE user3 (name VARCHAR(15) PRIMARY KEY);`，`name` 既是唯一取值也意味着 InnoDB 会按主键构建聚簇索引。

    ```text
        情况1 的时间线（全程被 BEGIN 框住，没有自动提交）

          BEGIN ── INSERT 张三 ── COMMIT ── BEGIN ── INSERT 李四 ── INSERT 李四(冲突) ── ROLLBACK
                                   ▲                                                    │
                                   └─────────── 回滚落点：只剩张三，李四被撤销 ─────────┘
    ```


* **三种情况的参数与结果对照**

    | 环节 | 情况1：有 `BEGIN` | 情况2：没有 `BEGIN` |
    | :--- | :--- | :--- |
    | 提交时机 | 只有显式 `COMMIT` 才提交 | `autocommit = true`，DML 执行完即自动提交 |
    | `INSERT 李四` 之后 | 数据留在事务里，未提交 | 数据已经落盘 |
    | 冲突语句的效果 | 事务进入失败状态（临时状态） | 同样进入失败状态，但该语句本身没写入 |
    | `ROLLBACK` 的落点 | 显式 `COMMIT` 之后 | 自动提交的那条 `INSERT` 之后 |
    | 回滚后的结果 | 只剩张三 | 张三、李四都在 |

    * 情况3 与情况2 的差别只有一行 `SET @@completion_type = 1;`，结果却从「张三李四都有」变成「只有张三」，因为 `COMMIT` 相当于 `COMMIT AND CHAIN`、自动开启了一个相同隔离级别的新事务。
    * > **易错点**：`TRUNCATE TABLE` 属于 DDL，DDL 操作会自动提交数据、不受 `autocommit` 变量影响，不管前面它是 `true` 还是 `false`。

* **保存点的收尾双分支**

    ```text
    保存点之后的两种收尾方式

      事务开始 ── 若干正确操作 ── SAVEPOINT s1 ──┬── 出错 ──> ROLLBACK TO s1 ──> 继续做完 ──> COMMIT
                                                 │
                                                 └── 整个不做了 ──> ROLLBACK ──> 回到上次 COMMIT 之后
    ```

    * 保存点解决的是「事务做到一半写错了」的问题：一个事务要做五件事、现在做成了三件且都没写错，就在这儿设一个保存点；后面真写错了就回滚到保存点，这一条操作失效，接着再写一条正确的。
    * 若整个事务都不想做了，就整体 `ROLLBACK` 回到上次 `COMMIT` 之后，保存点也跟着一起被撤销。

* **redo 日志的全链路一览**

    ```text
      ① 修改内存中的数据页
            |
            |   必须先把对应的 redo 日志写下来（Write-Ahead）
            v
      ② redo log buffer（内存）── 按刷盘策略 ──> ③ redo log file（磁盘）
                                                         |
                         ④ 之后才考虑把内存中的数据刷盘   |
                                                         v
                                               ⑤ 表空间数据文件（磁盘）

      回卷覆盖的许可条件：redo log file 中"已经刷盘"的那一段
                          （checkpoint 之后才允许被 write pos 覆盖）
    ```
