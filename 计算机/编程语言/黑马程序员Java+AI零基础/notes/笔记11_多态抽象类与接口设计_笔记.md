# 多态、抽象类与接口设计

## 继承结构的分类与抽取

* **分类的两条硬标准**
    * > **定义**：一是事物之间是不是同一类；二是同一类事物当中有没有共性的内容。
    * 第一条好理解，不能把学生和手机分为一类。
    * 第二条才是关键：两个类当中如果没有共性的内容，就没法往上抽取成父类。
    * 结构规模超过三五个类时，不要靠脑子想，先在纸上把继承结构画出来。

* **抽取的推进顺序**
    * 先在同类的子类之间抽一层，再检查这一层之间的共性继续往上抽一层。
    * 以本科学生、硕士研究生、专业课老师、通识课老师为例：学生一侧抽出 `Student`，老师一侧抽出 `Teacher`。
    * `Student` 与 `Teacher` 都含姓名、年龄与吃饭、睡觉，于是再抽出 `Person`，只留姓名、年龄和吃饭、睡觉。
    * 抽完之后 `Student` 独有的属性只剩年级、独有的行为只剩学习；`Teacher` 独有的属性是学科、独有的行为是教书。
    * 叶子类没有独有属性，私有化成员变量和 get/set 一律不写。

* **抽取的判断依据**

    * > **结论**：该抽取的还是要往上抽取。抽取的理由不是"子类现在用得上"，而是"以后所有的子类都用得上"。
    * `study()` 在两个子类里一定要重写，照样要留在 `Student` 里——将来出现第三个、第四个没有特有内容的学生时，可以直接用父类的 `study()`。

* **标准 JavaBean 四件套**
    * > **定义**：私有化成员变量、get/set 方法、构造方法、其他成员方法——这四部分缺一不可。
    * 构造方法一般写两个：空参构造和带全部参数的构造。
    * 写代码顺序是从上往下，先写父类，再写子类。
    * get/set 只针对本类独有的私有化成员变量；父类里已经写好的那几对，子类不必再写一遍。
    * 子类的带全部参数构造是"父类的加上自己的"：先 `super(父类参数)`，再 `this.独有参数 = 参数`。

* **三层继承结构示例**

    ```text
    Person                     姓名 name、年龄 age
     ├─ eat()  吃饭
     ├─ sleep()  睡觉
     │
     ├─ Student                 年级 grade
     │   ├─ study()  学习（被子类重写）
     │   ├─ BachelorStudent      无独有属性，重写 study()
     │   └─ MasterStudent        无独有属性，重写 study()、sleep()
     │
     └─ Teacher                 学科 subject
         ├─ teach()  教书（被子类重写）
         ├─ MajorTeacher         无独有属性，重写 teach()
         └─ GeneralTeacher       无独有属性，重写 teach()
    ```

    | 类 | 继承自 | 独有属性 | 独有方法 |
    | :--- | :--- | :--- | :--- |
    | `Person` | 无 | `name`、`age` | `eat()`、`sleep()` |
    | `Student` | `Person` | `grade` | `study()` |
    | `Teacher` | `Person` | `subject` | `teach()` |
    | `BachelorStudent` | `Student` | 无 | 重写 `study()` |
    | `MasterStudent` | `Student` | 无 | 重写 `study()`、`sleep()` |
    | `MajorTeacher` | `Teacher` | 无 | 重写 `teach()` |
    | `GeneralTeacher` | `Teacher` | 无 | 重写 `teach()` |

* **叶子类的构造方法**
    * > **易错点**：叶子类的"带全部参数的构造方法"要把间接父类 `Person` 的属性也带上——间接父类 + 直接父类 + 自己，全部包含进来，这才叫带全部参数。
    * 直接父类提供带全部参数的构造时，子类要用 `super(...)` 把间接父类的参数一层层往上带。
    * 用 IDE 生成构造时，弹框会依次问"是否仿照父类构造生成"和"是否把子类独有属性加进去"，两问都要选是。

* **追加需求的落地方式**
    * 需求是硕士研究生的住宿条件升级，要改在豪华版学生公寓睡觉。
    * 父类的 `sleep()` 只表示"在普通宿舍睡觉"，已满足不了子类需求，处理办法就是重写 `sleep()`。

* **继承写法的易错点**
    * > **易错点**：同名的 `Person`、`Student` 在别的包里也有一大堆，新写子类时千万别继承错了，选的一定是当前包里的那个。

## 权限修饰符

* **权限修饰符的作用**
    * > **定义**：Java 中的权限修饰符就是 Java 的关键字，作用是控制一个成员被访问的范围，可以修饰成员变量、成员方法、构造方法。
    * 四种修饰符按作用范围从小到大排列。
    * "空着不写"这种写法也叫缺省（默认），普通成员变量前面什么都不写用的就是它。

    | 修饰符 | 名字 | 作用范围 |
    | :--- | :--- | :--- |
    | `private` | 私有 | 只能在本类当中访问，其他地方一律无法使用 |
    | 不写 | 缺省（默认） | 本类当中可以，本包中其他类里面也可以，其他包里面不行 |
    | `protected` | 受保护的 | 除了本类和本包当中，在其他包里面的子类也可以使用 |
    | `public` | 公共的 | 所有的地方都可以使用 |

    * > **结论**：`private` < 不写 < `protected` < `public`，范围一级一级放开。

* **用四个类实测范围**
    * 把被观察的 `Person` 放在 `aaa` 包，`Student` 与 `Test01` 也放在 `aaa` 包，`Teacher` 与 `Test` 放在 `bbb` 包。
    * `Student` 是"本包中的其他类"，无论它是不是子类，本包其他类的访问权限逻辑完全一样。
    * 全改成 `private`：本类可用，本包其他类即使继承了 `Person` 也报错，不同包同样报错。
    * 改成缺省：本包的 `Student` 不再报错，`bbb` 包的两个类仍然报错——这也解释了测试类为什么总是和被测试的类放在同一个包里。
    * 改成 `protected`：不同包的子类 `Teacher` 不再报错，但不同包的无关类 `Test` 依然报错。
    * 改成 `public`：所有地方全都能用。

* **实际开发中的取舍**
    * > **结论**：真正需要背下来的只有两句——`private` 修饰的成员变量和方法只能在本类中使用；`public` 修饰的成员变量和成员方法，在所有的地方都能使用。
    * > **提示**：实际开发一般只用最小的 `private` 和最大的 `public` 就够了，中间两个简单了解一下就行。
    * 真遇到"子类要用、父类又不想完全公开"的中间地带，再回头调 `protected` 也不迟。

## 多态

* **多态的定义与形式**
    * > **定义**：多态是面向对象的三大特征之一，含义是事物的多种形态；代码表现形式就是把子类对象赋值给它的父类类型。
    * `Student stu = new Student();` 是学生形态；`Person p = new Student();` 同样是那个对象，表现为人的形态。
    * 好处之一：方法形参写父类类型，就能接收它所有的子类对象，当前方法能接收的类型会更多。
    * 好处之二：方法体内用对象调方法，子类重写后，多态会根据传进来的实际对象调用到不同类里的方法，方法体一个字都不用改。
    * 形参写死某个子类型，就只能注册那一种角色；每新增一种角色都要补一个同名方法，这种设计不可取。

* **多态成立的条件**
    * 第一，必须有继承关系或者实现关系；没有真的写 `子类 extends 父类`，代码直接报错。
    * 第二，必须有父类引用指向子类对象，即左边父类类型变量、右边 `new` 出来的子类对象。
    * 第三，子类中对父类方法进行重写——这一条是可选的。
    * > **提示**：子类不重写父类方法，代码一样不报错，只是调用时拿到的是父类的方法版本。真正卡住你的只有前两条；第三条重写决定的是能不能享受多态第二个好处。
    * > **易错点**：如果左边变量不是父类，而是 `Student s = new Student()`，那就不是多态，是最普通的创建对象。

* **多态调用成员的两条规则**

    * > **结论**：调用**成员变量**编译看左边、运行也看左边；调用**成员方法**编译看左边、运行看右边。

    | 调用什么 | 编译期看 | 运行期看 | 实际结果 |
    | :--- | :--- | :--- | :--- |
    | 成员变量 | 左边（父类） | 左边（父类） | 拿到父类的值，子类同名变量被无视 |
    | 成员方法 | 左边（父类） | 右边（子类） | 调到子类重写的版本，没重写就调父类的 |

    * "编译看左边"指 `.java` 编译成 `.class` 的阶段，编译时看父类里有没有这个成员，有则通过，没有则在编译阶段就报错。
    * "运行看右边"的完整查找过程是：先到子类里找，子类有重写就调子类的；没有，再到父类里找，找到就调父类的。
    * 所以用父类引用调父类独有的方法不报错，运行结果仍是父类的方法；用父类引用调子类独有的方法则编译期直接拦下。

    ```text
      f.show()
          │
          ├─ ① 子类里有没有重写的 show？
          │        有 ──→ 调子类的 show
          │        没有 ↓
          │
          └─ ② 回父类里找 ──→ 找到，调父类的 show
    ```

* **"儿子穿上爸爸的衣服"的理解方式**
    * 把子类对象赋值给父类类型，好比儿子穿上了爸爸的衣服，外人眼中这个人就是爸爸。
    * 读成员变量相当于问"你是谁"，答案永远是父类的值，露不出馅。
    * 调成员方法相当于让这个人开始干活，一干活就露馅，走的是子类的实现。

    ```text
      Zi 对象 —— 穿上 Fu 的衣服 —— 对外就表现为 Fu

      f.name    （问「你是谁」）  →  父的值      露不出馅
      f.show()  （让「你」干活）  →  子的实现    一干活就露馅
    ```

* **多态的弊端**
    * > **结论**：多态的弊端就是它不能去调用子类的特有方法。
    * 原因仍是"编译看左边"：编译时先去父类里找该方法，父类里没有就直接报错，根本不需要运行。
    * 解决办法只有一个：把对象再转回子类类型。

* **类型转换**
    * 从小到大是自动类型转换，也叫向上转型，把子类类型转成父类类型，这正是多态本身，程序自动进行。
    * 从大到小是强制类型转换，也叫向下转型，把父类类型的变量转成子类类型，程序不会自动进行，需要手写。
    * 写法与基本数据类型一致：想转成什么类型，就在前面的小括号里写什么类型。
    * 强转能把对象转成它真正的子类类型，从而调用子类里的独有功能。
    * > **易错点**：强转这件事编译期是抓不住的，代码写完不报错，跑起来才炸，所以千万不要上来就转。
    * 转错时抛 `java.lang.ClassCastException`，含义是类型转换异常，后面会说明哪个类型不能转成哪个类型。

* **instanceof 判断**
    * 转换前先判断变量是不是自己要的类型，写法是前面变量名、后面类名，是则返回 `true`，否则返回 `false`。
    * 条件满足才执行强转，转成子类类型后既能调父类方法，也能调子类重写的方法和子类方法。
    * 转换的类型跟真实对象的类型不一致时程序会报错，用 `instanceof` 判断能避免出错。

## 抽象类与抽象方法

* **继承留下的两个问题**
    * 把共性内容抽到父类之后，父类里那个方法体是没有任何意义的，只能随便写一个让程序不报错，再让子类按真实需求去重写。
    * 如果子类是别人写的、对方压根没重写，你拿它没有任何办法，因为此时语法不会报错。

* **抽象方法**
    * > **定义**：在一个继承结构中，共性的行为被抽取到父类之后，由于每个子类的方法体都不一样，父类里不能确定具体方法体，此时这个方法就可以定义为抽象方法。
    * > **结论**：如果说有一个方法我不能确定它的方法体了，那么此时这个方法就要定义成抽象的。
    * 语法上有三处变化：方法前加 `abstract` 关键字、去掉大括号、用分号作为结尾。
    * `abstract` 关键字是连带的：一旦定义成抽象的，就强制让子类去重写，子类不重写代码直接报错。
    * 两个问题因此同时解决：父类不用再纠结方法体写什么，别人偷懒不重写也过不了编译这一关。
    * > **提示**：学抽象类之前要先学抽象方法，抽象方法是里子，抽象类是面子，顺序别反了。

* **抽象类**
    * > **结论**：如果说一个类当中存在抽象方法，那么这个类就必须声明为抽象类，否则代码直接报错。
    * 写法是在类的声明前面加 `abstract` 关键字。
    * > **提示**：不是所有的父类都要定义成抽象的。先观察父类里有没有哪些方法体确定不了，有就定义抽象方法、定义抽象类；如果所有方法的方法体都能确定，那就没必要定义抽象方法和抽象类。
    * 有抽象方法的类一定是抽象类，反过来不成立。

* **共性内容该往哪抽的判断**
    * > **结论**：方法体确定不了的抽上去定义成抽象方法；方法体一致的抽上去写成普通方法；只有一方才有的行为留在子类里不上提。

    | 行为 | 猫 | 狗 | 归属 | 原因 |
    | :--- | :--- | :--- | :--- | :--- |
    | `eat` | 猫吃鱼 | 狗吃骨头 | 抽到父类，定义成抽象方法 | 都叫"吃"，但方法体不一样，父类确定不了 |
    | 抓老鼠 / 看家 | 猫抓老鼠 | 无 | 各自留在子类里 | 猫独有的行为，没必要往上抽 |
    | `drink` | 猫喝水 | 狗喝水 | 抽到父类，普通方法 | 两个方法体一样，父类里能确定 |

    ```text
                     ┌──────────────────────────────┐
                     │   abstract class Animal      │
                     │  ------------------------------│
                     │  name     （共性属性）        │
                     │  color    （共性属性）        │
                     │  drink()  （普通方法，能确定）│
                     │  eat()    （抽象方法，确定不了）
                     └──────────────────────────────┘
                           ▲                ▲
              ┌────────────┘                └────────────┐
              │                                          │
     ┌────────────────────────┐              ┌────────────────────────┐
     │       class Cat         │              │       class Dog         │
     │  重写 eat() → 猫吃鱼    │              │  重写 eat() → 狗吃骨头  │
     │  catchMouse() 猫抓老鼠 │              │  lookHome()  狗看家     │
     │  drink() 继承自父类     │              │  drink() 继承自父类     │
     └────────────────────────┘              └────────────────────────┘
    ```

* **抽象类不能被实例化**
    * 对抽象类强行创建对象，程序直接报错，提示这个类是抽象的、不能对它创建对象。
    * 原因是如果能创建抽象类的对象，就能用这个对象去调一个没有方法体的抽象方法，这种调用没有任何意义。

* **抽象类里面不一定有抽象方法**
    * 一个抽象类里定义三个有方法体的方法，程序根本不报错。
    * > **结论**：抽象类里不一定有抽象方法，它的作用其实就是为了不让外界创建本类的对象。
    * 反例：抽象父类有十个抽象方法，子类必须把十个从头到尾重写一遍，哪怕只想用第三个，另外九个也得被迫重写。
    * 解决办法是在子与父之间加一个中间层，中间层命名用父类的名字加后缀 `Adapter`，`Adapter` 的含义是转换器。
    * 中间层对所有抽象方法做空实现，即方法体空着什么都不写；真正使用的子类直接继承 `Adapter`，想要用哪个方法就重写哪个方法。
    * 中间层本身没有实际用途，所以在它前面直接加 `abstract`，不让外界创建它的对象。

    ```text
       method1() method2() method3() ... method10()      ← 抽象父类（10 个抽象方法）
                             │
                             ▼
        ┌──────────────────────────────────────┐
        │  abstract class 父类Adapter extends 父类  │   ← 中间层：10 个方法全部"空实现"
        │  方法体空着什么都不写                     │
        └──────────────────────────────────────┘
                             │
                             ▼
                ┌────────────────────────┐
                │      class 子类          │   ← 真正使用的类
                │  只需要重写 method3()    │
                └────────────────────────┘
    ```

* **抽象类里可以有构造方法**
    * > **结论**：构造方法的作用不是创建对象，而是给成员变量进行初始化（赋值）；在抽象类里，它的意义就是给子类抽取上来的那些共性内容赋值。
    * 真正创建对象的是 `new` 关键字，构造方法只是整个过程里的一小步。

    ```text
                栈内存                          堆内存
             ┌───────────┐
     stu →   │  变量 stu  │ ──── 地址 ────▶  ┌──────────────────┐
             └───────────┘                   │  Student 对象     │
                                             │  name = null(默认) │
                                             │  age  = 0  (默认)  │
                                             └──────────────────┘
                                              ④ 默认初始化 → ⑤ 显式初始化
                                                  → ⑥ 构造方法初始化
                                                  → ⑦ 变量拿到地址
    ```

* **抽象类的子类只有两种写法**
    * 第一种是重写抽象类里所有的抽象方法，这是正常写法。
    * 第二种是子类本身也是抽象类，此时没必要重写父类的抽象方法。
    * > **易错点**：继承了一个抽象类却没重写它的抽象方法，代码是会报错的。
    * 第二种写法意义不大：子类仍然不能创建对象，要创建对象还得再写一个孙子类去继承这个子类，并把里面所有抽象方法重写一遍。
    * 一般来讲，子类就是重写父类里所有的抽象方法。

* **抽象方法存在的意义**
    * 把方法留在子类里当特有功能，语法上没有问题，但方法名、参数、返回值都不统一，调用方只能挨个去查看每一个类。
    * 类的数量一多就形成史山代码，根本原因就是子类写同一个方法时没有统一。
    * > **结论**：抽象方法还有一个隐藏含义——强制子类必须按当前格式重写，否则代码直接报错。统一之后调用时直接看父类就行，不必再逐个翻子类。

## 接口

* **接口的定位**
    * 场景是给动物继承体系加第三个行为"游泳"：写进父类对不会游泳的兔子不合理，写在各子类里当特有行为则无法确定书写格式。
    * > **定义**：接口其实是一种规则，而且是独立于继承体系以外的规则。
    * 规则体现在抽象方法上：子类必须按接口规定的格式重写，否则代码直接出错。
    * 好记的比喻是把接口理解成"干爹"，父类是"亲爹"——想拥有某项能力就让这个子类认接口为干爹。
    * 兔子不实现游泳接口，就调不到 `swim()`，因为方法压根不在它身上，编译期就拦下来了。

* **接口的定义与实现**
    * 定义接口用 `interface` 关键字而不是 `class`；写完之后编辑器左边的小圆圈变成绿色的，那就是接口的标识。
    * 接口与类之间不是继承关系而是实现关系，用 `implements`；继承父类相当于认亲爹用 `extends`，实现接口相当于认干爹用 `implements`。
    * 不小心新建成了类也有补救办法，把 `class` 改成 `interface` 即可。
    * 同时继承抽象类和实现接口时，必须把这两个里面所有的抽象方法全部重写。

* **实现接口的三个注意点**
    * 接口不能实例化，接口不能创建它的对象。
    * 接口的子类叫实现类，实现类必须要么重写接口里所有的抽象方法，要么本身是一个抽象类；实际开发中更多用前一种。
    * 一个类可以实现多个接口，也可以在继承一个类的同时实现多个接口——亲爹只能有一个，干爹可以有无数个。

* **接口中的成员变量**
    * > **定义**：接口中的成员变量只能是常量，默认会使用 `public static final` 修饰。
    * 只写 `int A;` 会直接报错，因为它默认被 `final` 修饰，常量需要手动赋值，所以必须写成 `int A = 10;`。
    * 常量名字要大写。
    * 用 `Inter.A` 就能直接访问并点出变量名，说明前面一定有一个 `static`；换到其他包也能访问，说明前面一定有一个 `public`。
    * 验证 `final` 的方式是在 `out` 文件夹对应包的路径里输入 CMD，用 `javap 接口名` 反编译，字节码里会显示完整的 `public static final`。

    ```text
    Compiled from "Inter.java"
    public interface com.itheima.test2.Inter {
      public static final int A = 10;
    }
    ```

    * 写熟之后直接写 `int A = 10` 没问题，初学阶段建议把三个修饰符手动补上。
    * > **提示**：在编辑器里，如果某些关键字写完之后变灰了，表示当前可以省略不写，编译时虚拟机会自动加上。

* **接口中的构造方法**
    * 接口当中没有构造方法，手动按构造方法格式写会直接报错。
    * 原因是接口不能创建对象，且里面所有成员变量都是常量、已经有真实数据，创建对象时无需再赋值，所以构造方法没有存在的必要。

* **接口中的成员方法**
    * 在 JDK7 及以前，接口中只能定义抽象方法，默认使用 `public abstract` 修饰，不能写有方法体的方法。
    * 不写修饰符直接写 `void method();` 不报错，反编译后能看到虚拟机自动补上了 `public abstract`。

    ```text
    Compiled from "Inter.java"
    public interface com.itheima.test2.Inter {
      public static final int A;

      public abstract void method();
    }
    ```

* **类与类、类与接口、接口与接口的关系**

    | 关系 | 关键字 | 能不能多 |
    | :--- | :--- | :--- |
    | 类 与 类 | `extends` | 单继承，不能多继承，但可以多层继承 |
    | 类 与 接口 | `implements` | 单实现、多实现都行，还能边继承类边实现多个接口 |
    | 接口 与 接口 | `extends` | 单继承、多继承都行 |

    * 实现类不知道名字怎么起时，命名习惯是前面放接口名、后面加 `Impl`，表示当前类是前面这个接口的实现类。
    * 实现多个接口时接口之间用逗号隔开，实现类就要重写多个接口中所有的抽象方法，少写一个代码就报错。
    * `extends` 必须写在 `implements` 前面，写反了会报错——亲爹的地位比干爹大。
    * 如果父类也是抽象类，子类要重写抽象父类和所有接口里全部的抽象方法，或者子类本身也是抽象类。
    * 多个接口中出现重复的抽象方法时只要重写一次；父类与接口方法重复时同样只要重写一次——亲爹和两个干爹都提同一个要求，做一次就够了。
    * 接口继承接口后相当于把多个接口的抽象方法全部继承下来，实现类要把它继承来的所有抽象方法全部重写。

## 运动员与教练综合设计

* **需求的分水岭**
    * 四类人是乒乓球运动员、篮球运动员、乒乓球教练、篮球教练，属性都是姓名和年龄。
    * 凡是跟乒乓球相关的人都要学英语；跟篮球相关的两类人不用。这一句是整道题的分水岭。

* **常见错误设计**
    * 常见做法是四个子类共同继承 `Person`，再在上面定义说英语、学、教三个接口，谁有什么行为就实现哪个。
    * > **易错点**：属性相同不等于可以抽成父类。用继承的前提是 **is-a** 关系成立——子类得是父类中的一种事物。共有的字段可以抽、共有的方法可以抽，但共有的属性不构成父子关系。
    * 一个父类中它所有的子类需要是同一种事物。乒乓球运动员跟篮球教练关系不大，篮球运动员跟乒乓球教练关系也不大，既然关系不大就不该认同同一个"当爹"。

* **两条能走通的路**
    * 按项目分：乒乓球从业者、篮球从业者各抽一层，再往上抽 `Person`，`Person` 里只留姓名和年龄；说英语留在乒乓球从业者里；"学"和"教"横跨左右两个体系，抽不出父类，做成两个接口横切在体系之外。
    * 按角色分：运动员这一支的父类叫 `Sporter`，教练那一支的父类叫 `Coach`；运动员的共性行为是学习，学习内容不一样就定义成抽象方法 `study`；教练的共性行为是教，定义成抽象方法 `teach`；两个"说英语"横跨运动员和教练两个体系，单独做成接口。
    * 两条路都是三层结构，最上层都是人，往下都是四个子类，光看继承结构几乎一模一样。

    | | 按项目分 | 按角色分 |
    | :--- | :--- | :--- |
    | 中间层 | 乒乓球从业者、篮球从业者 | `Sporter`（运动员）、`Coach`（教练） |
    | 中间层里的抽象行为 | 无（抽象方法都跑到接口里了） | `study()`、`teach()` 两个抽象方法 |
    | 体系外还要额外加的接口 | 学接口、教接口（两个） | 说英语接口（一个） |
    | 说英语放在哪 | 乒乓球从业者的方法 | 说英语接口 |

    * 把抽象行为放进中间层、只留一个接口的那条路更简洁，写代码时按这种方式开始。

* **按角色分的结构与代码**

    ```text
                              ┌─────────────────┐
                              │      Person     │    姓名、年龄
                              └────────┬────────┘
                     ┌─────────────────┴─────────────────┐
              ┌───────┴────────┐              ┌───────────┴──────┐
              │     Sporter    │              │      Coach       │
              │    运动员       │              │      教练         │
              │ 抽象方法 study() │              │ 抽象方法 teach()  │
              └───┬─────────┬───┘              └───┬──────────┬───┘
                  │         │                        │          │
           ┌──────┴──┐  ┌───┴─────┐            ┌──────┴──┐  ┌────┴─────┐
           │乒乓球运动员│  │乒乓球教练│            │篮球运动员│  │ 篮球教练  │
           └─────────┘  └─────────┘            └──────────┘  └──────────┘
               │              │                       │
               └──── 实现 English 接口 ──────────────┘
                    （只有乒乓球一方要说英语）
    ```

    * 落地后共九个类：`Person`（抽象）、`Sporter`（抽象）、`Coach`（抽象）、`English`（接口）、`PingPongSporter`、`BasketballSporter`、`PingPongCoach`、`BasketballCoach` 以及测试类。
    * 四个子类里只有乒乓球运动员和乒乓球教练需要 `implements English`，篮球的两类不需要。
    * 中间两层的空参构造和带全部参数的构造都要写上。
    * 类声明写完后先用编辑器的自动修复生成所有抽象方法的重写，再用快捷键生成构造方法。

* **顶层父类的抽象化**
    * 顶层 `Person` 本身没有抽象方法，但也可以把它定义成抽象类。
    * > **结论**：这么做的目的是不让外界直接创建顶层父类 `Person` 的对象——创建这样的对象是没有意义的。
    * 测试类里创建的都是运动员或者教练的对象，这才是有意义的。

## 接口升级与 JDK 新特性

* **接口新特性总览**

    | 版本 | 接口里能定义什么 | 格式 |
    | :--- | :--- | :--- |
    | JDK7 及以前 | 只能写抽象方法 | `public abstract void speak();` |
    | JDK8 新增 | 默认方法、静态方法（有了方法体） | `public default void show();` / `public static void show();` |
    | JDK9 新增 | 私有方法（普通私有方法、静态私有方法） | `private void check();` / `private static void check();` |

    * JDK8 允许接口定义有方法体的方法，是为了接口升级时向下兼容。
    * JDK9 允许接口定义私有方法，是为了抽取重复的代码。

* **接口升级的动机**
    * 软件不是一次开发到位的，靠版本迭代逐渐完善。
    * 接口中的抽象方法一发生变化，受语法限制实现类就不得不改变，否则代码直接报错、运行都运行不了。
    * 如果实现类不方便修改，就只能靠定义有方法体的方法来两全——这就是新特性出现的原因。
    * 项目 1.0 里接口有两个实现类，上线没问题；2.0 要加十个新方法时，用有方法体的方法就能让实现类不必立刻修改，用到哪个规则再重写哪个。

* **默认方法**
    * 用 `default` 关键字修饰，作用是在接口升级时让代码不报错。
    * 它不是抽象方法、有方法体，所以不会强制实现类去重写，实现类直接调用即可。
    * 被重写时需要去掉 `default` 关键字，强行加上反而会报错，运行走的是重写后的方法。
    * > **提示**：`public` 可以省略，`default` 不能省；省略后报错提示是抽象方法不能够拥有方法体。
    * 判别方式是看关键字的颜色——能省略的都显示为灰色，`default` 是高亮的。
    * 实现类实现多个接口且多个接口中有同名默认方法时，实现类必须显式重写这个方法，不重写代码就会报错。

    ```java
    public interface InterA {

        public abstract void method1();

        public abstract void method2();

        public default void function() {
            System.out.println("接口A当中新增的默认方法");
        }
    }
    ```

    ```java
    public class InterImpl implements InterA, InterB {
        @Override
        public void method1() {
        }

        @Override
        public void method2() {
        }

        @Override
        public void function() {
            System.out.println("重写接口里面的function方法");
        }
    }
    ```

* **静态方法**
    * 用 `static` 修饰，JDK7 以前接口中不能写，JDK8 开始可以；它同样不要求实现类强制重写，因为已经有方法体。
    * 静态方法只能通过接口的名字进行调用，不能通过实现类的类名或者对象的名字来调用，写反了在编译阶段就报错。
    * `public` 可以省略，`static` 不能省略。
    * 在实现类里写一个同名方法并加 `@Override` 注解会报错，提示静态方法不能用 `@Override` 标注。
    * > **结论**：只有虚方法表里的方法才能被重写，而能进虚方法表的是非静态、非 `final`、非私有的方法；静态方法不在虚方法表里，没法替换方法地址，所以不能被重写。
    * 去掉 `@Override` 之后同名方法确实能编译通过，但那是两个方法碰巧一样，不构成重写关系。

    ```java
    public class Test {
        public static void main(String[] args) {
            Inter.method();          // 正确
            InterImpl.method();     // 错误，程序都不用运行，直接报错
            InterImpl ii = new InterImpl();
            ii.method();            // 同样直接报错
        }
    }
    ```

* **亲爹与干爹在静态调用上的区别**
    * 父类里的静态方法，用子类对象去调是可以的，运行出来就是父类的静态方法。
    * 原因是虚拟机不推荐但语法允许这种写法，它先看本类有没有该方法，没有就沿整个继承链往上找。
    * 继承链上只看父类，**不会**看到父类后面实现的接口，所以接口中的静态方法用对象调不通。

    ```java
    public class Fu {
        public static void aaa() {
            System.out.println("父类中的静态方法");
        }
    }
    ```

* **私有方法**
    * JDK8 的尴尬：两个默认方法 `login` 和 `register` 有大量重复的校验代码，只能额外定义一个 `default` 方法把重复代码抽出来。
    * 但这个抽取出来的方法是为本接口服务的，其他类访问它没有意义，而它被 `public` 修饰，在任何地方都能被调到。
    * JDK9 新增私有方法修复了这个漏洞，外界再调 `check` 就直接报错。
    * > **结论**：接口中普通私有方法存在的意义，就是抽取默认方法中重复的代码。
    * 静态私有方法逻辑一样，是为了抽取静态方法中重复的代码；在静态方法里调用不能写普通的私有方法，得写成静态的私有方法。

    ```java
    public interface Inter {

        public default void login() {
            check();
            System.out.println("登录的业务逻辑");
        }

        public default void register() {
            check();
            System.out.println("注册的业务逻辑");
        }

        private void check() {
            System.out.println("检查网络是否畅通");
            System.out.println("检查用户名和密码格式");
            System.out.println("检查用户名是否存在");
        }
    }
    ```

* **新特性四句话总结**
    * JDK7 及以前接口里只能定义 `abstract` 修饰的抽象方法。
    * JDK8 接口里可以定义有方法体的方法，分为 `default` 默认方法和 `static` 静态方法两种。
    * 方法一旦有了方法体就不可避免出现重复代码，所以 JDK9 额外有了私有方法。
    * 私有方法分为普通私有方法（抽取默认方法中的重复代码）和静态私有方法（抽取静态方法中的重复代码）。
