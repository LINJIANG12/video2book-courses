只不过若依生成的这些基础代码只返回了区域的信息，并没有包含点位数量。而我们这个需求就会涉及到区域表的信息，将点位表统计后的数据整合到一起返回给前端。那么这个功能该如何实现呢？我们回到 PPT 来分析一下实现方案。

在这里，帅哥再明确一下需求：返回区域列表时，同时返回点位数。这里包含两张表，一个是区域表，一个是点位表。怎么做？兄弟们先来思考一下。

好，帅哥已经看到弹幕有同学说了，我们可以在区域表当中新增一个字段，就叫 `node_count`。这个字段专门来存储该区域下点位的数量的。将来我们只需要查询区域列表，就可以同时返回 `node_count` 点位的数量。好想法，这就是我们要学的第一种方案：同步存储。我们在区域表当中添加一个点位数字段，当点位发生改变时，比如说我们新增了一个点位，我们就可以更新区域表点位数的字段了。

那么这种方案是可行的，但是我们需要思考一下它的优点和缺点。首先，它的优点是单表查询，所以查询区域列表时的效率是非常高的。那缺点也很明显，每次点位数据发生变动时，我们都需要更新区域表，这增加了额外的工作量；并且如果更新操作出现了遗漏，可能导致数据的不一致。明明是四个点位，我们统计出来的结果可能是三个，也可能是五个，这就是我们所说的数据不一致。

基于这种优缺点，其实我们可以引出第二种方案，叫关联查询。我们可以在 Mapper 层当中编写 SQL 语句，通过关联查询获取每个区域的点位数。我们基于区域 ID 来统计点位的数量，将统计的结果跟区域表的列表合并输出返回给前端就可以了。

那么这种方案的优缺点，我们来思考一下。首先，它的优点，我们可以保证数据的实时性和准确性，因为点位是实时计算的，不需要单独维护。那缺点，SQL 语句涉及到多表关联了，所以比较复杂。如果点位的数据量很大，还有可能会影响查询的性能。考虑到区域和点位的数据量通常不会特别大，我们选择第二种方案：关联查询。这样我们就能保证数据的准确性，同时避免了维护额外字段的麻烦。

同学们，这两种方案都有利弊，选择哪一种取决于实际的数据量和业务需求。在这个案例当中，我们追求的是数据的实时性和准确性，因此我们选择了关联查询。

下面带各位老铁来写一下区域和点位关联查询的 SQL 语句。我们参考这两张表的关系模型图来编写。截张图，缩小放这里。回到数据库的客户端工具，右击我们打开 SQL 的命令行窗口。

那么 SQL 语句的编写，帅哥会讲两种模式。第一种是传统模式，我们从 SQL 的思路分析到 SQL 的编写全部都要自己来完成，那么这种效率是比较低的。那么在全面拥抱 AI 的时代，我们只需要把需求的 prompt 提示词写好，它就可以自动帮我们生成 SQL 语句，然后我们进行调整就可以拿到最终的结果了。所以一会我们来讲 AI 辅助编程的模式。

好，我们先来看传统模式。传统模式的话，SQL 语句的编写思路又分为很多种。帅哥讲其中一种跟 AI 来对比，突出 AI 的强大之处。好，那思路是这样的：我们先查询点位表，根据 `region_id` 进行分组统计，我们就可以拿到每个分组下面的点位数量了。拿到这个结果以后，我们再把它作为虚拟表去关联查询区域表。这样我们就可以拿到区域的所有数据以及当前区域的点位数量了。那么 SQL 语句的编写一共分为两步，我们来看一下。

首先，第一步，先聚合统计每个区域下的点位数。那么这个需求我们刚才说了，要确定查询的表，谁啊？`tb_node`。接下来我们还要确定分组字段，`region_id`。这两个确定以后，SQL 语句就出来了：

```sql
SELECT * FROM tb_node
```

然后来进行分组：

```sql
GROUP BY
```

针对于 `region_id` 分组。通常情况下，我们对谁分组就查谁，然后再来统计每个区域的点位数量，来个 `COUNT(*)`。SQL 语句就写完了，选中执行。大家来看一下执行结果，这是区域 ID，这是我们统计的数量。区域 ID 为 1 的，有一个点位数；区域 ID 为 2 的，同样也有一个点位数。这是我们之前生成的一些测试数据。

但这个 `COUNT(*)` 无法做到见名知意，普通用户怎么知道它是点位数呢？所以我们通常会给它加一个别名，来个 `AS node_count`。来，再选中执行。现在我们可以看到，`node_count` 已经做到了见名知意。

这个执行结果拿到手以后，我们把它作为虚拟表跟区域表进行关联查询。所以第二步，然后与区域表进行关联查询。我们希望是拿到区域表的所有数据，所以我们的查询主体是 `SELECT * FROM tb_region`，是这个区域表，给它加一个别名 `r`。然后跟我们刚刚执行的结果进行关联查询。而且关联查询分为内连接和外连接，小伙伴们思考一下，我们应该选择哪一种？

如果是内连接的话，它查询的是两张表的交集。那么交集就会造成什么问题呢？如果该区域下面没有点位的话，是不是这个区域就不会展示了？那肯定是不行的。所以我们选择外连接。那么选择外连接的话，我们的 `tb_region` 在左侧主体，所以我们使用的是左外连接，用 `LEFT JOIN` 去关联查询我们上一条 SQL 语句的执行结果，然后给这张表加一个别名，比如说叫 `n`。

好，那后面还要去写它的连接条件，内容比较长，我们换个行。来个连接条件 `ON`：

```sql
r.id = n.region_id;
```

好，SQL 语句我们写完了。来，兄弟们，选中执行一下。现在我们可以看到，查询了所有区域的数据。往右拉，再来看，每个区域下面的点位数量是不是也统计出来了？

但这个关联查询的执行结果返回的数据太多了，我们来看一下接口文档。最终前端只需要返回四个字段就可以了，所以我们在这里面要确定显示的字段。这里包含了 `remark`，它属于区域表的；`id` 也属于区域表的；`region_name` 也属于区域表的。我们在这里面通过区域表的别名 `r.id`，我们先返回区域 ID，然后呢再返回 `r.`

region_name 区域名称，再返回 `r.remark` 区域的备注信息，最后返回是虚拟表当中的 node_count。指定了返回字段以后，我们再次选中执行。

现在我们看一下返回的结果跟接口文档要求是一致，看起来就很清爽了。下面我们再来注意一下，这个执行结果还有一个小的 Bug。什么 Bug 呢？同学们思考一下，北京东城区、北京北五环奥体中心这两个区域下面还没有点位的数据，那么返回 NULL 兄弟们觉得合适吗？那肯定不合适啊。如果你没有点位数据的话，应该返回什么呢？是不是应该返回 0 啊？那么这个问题该如何解决呢？其实很简单，我们可以使用 MySQL 的一个内置函数 `IFNULL`。

来，我们操作一下。选中这个字段，我们给它加一个函数：`IFNULL`。这个函数的作用是，当返回结果为 NULL 值的时候，我们可以给它加一个默认值为 0。现在我们再选中执行。兄弟们再来看，东城区、奥体中心这两个区域下面的点位数量就是 0 了。但这个字段的名称又不能做到见名知意了，所以函数处理完之后，我们还要给它加一个别名：`as node_count`。再选中执行，node_count 已经做到了见名知意。
