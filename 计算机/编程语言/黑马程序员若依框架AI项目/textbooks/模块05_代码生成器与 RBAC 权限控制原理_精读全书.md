## 点一下「生成」背后：代码生成器源码精读与 Velocity 模板入门
> 对应块：BLK28 | 覆盖分集：P94-P97 | 块标题（分集名）：《原理篇-05.代码生成器-源码-生成代码》

各位同学，接下来我们深入了解生成并下载前后端代码的源码分析。

先把场景摆出来，这事儿一点都不复杂：管理员在生成页面勾上订单表、统计表、出货流水表，点下「生成」按钮，浏览器弹出另存为对话框，一个 zip 包落到本地。解压一看，前端页面、后端 Controller/Service/Mapper、SQL 脚本、接口 api 全部齐活。

就是这么一个动作，背后却藏着一整条链路：前端一个视图组件、一段抽取好的下载工具、一个 Controller 方法、两层 Service 方法，外加一个模板引擎。我们今天就把这条链路从头到尾捋一遍——捋完你就会发现，代码生成器说到底就是**「把数据库里的表结构，套进一份 Java 代码模板里」**。

捋完源码，我们再动手给生成器做两件事：把默认值改成符合我们项目命名习惯的，顺手解决 Lombok 和 Swagger 的问题。而解决这两个问题的钥匙，就是最后要讲的 Velocity 模板引擎。

### 一次生成请求的完整旅程

先看全局。这张图是今天这节的骨架，后面每一段代码都是在这条线上展开的：

```text
【浏览器】勾选业务表 → 点「生成」
   handleGenTable(row, type)
        │  GET /tool/gen/batchGenCode?tableName=tb_a,tb_b,tb_c  + 令牌
        ▼
【Controller】batchGenCode(response, tableName)
        │  tableName 逗号串 → String[]
        ▼
【Service 第 1 层】generatorCode(tableName)
        │  new ByteArrayOutputStream()  ← 存 zip 的字节
        │  new ZipOutputStream(bos)    ← 把生成的代码压成 zip
        │  for (表名 : 数组) → 逐张表生成
        ▼
【Service 第 2 层】generatorCode(单张表名, zip)
        │  1. 查表基本信息 + 字段信息
        │  2. 是子表 → 再挂上子表信息
        │  3. 标记主键列
        │  4. 建 VelocityContext，把所有模板变量塞进去
        │  5. getTemplate(模板类型, 前端类型) → 没加载到就结束
        │  6. 遍历模板：merge(context, writer) → 写进 zip
        ▼
【Controller 收尾】response.reset() → 一堆响应头 → writeBytes(...)
        │  字节流
        ▼
【浏览器】download.js 的 download() → 另存为 ruoyi.zip → 解压得到前后端代码
```

> **结论**：整条链路里真正干活的只有 Service 第 2 层的那句「把模板变量合并进模板文件」。Controller 和前端都只是在搬字节。

#### 前端只有两个入口，走的却是同一套接口

负责这一功能的前端代码在生成页的 `index` 视图组件里，后端处理逻辑则在代码生成模块的 Controller 中：前者负责「业务表的用户界面和交互逻辑」，后者负责「处理前端请求、执行代码生成逻辑，并把 zip 压缩包响应回客户端」。

找按钮很简单，打开 `index` 视图全局搜一下就能定位到——生成按钮在第 46 行附近，点一下触发点击事件，调用 `handleGenTable` 这个方法。

这里有个细节值得停一下：页面上其实有**两个**生成按钮，一个在左上角，负责批量生成；另一个在每一行业务表的右侧，属于单表生成。但这两个按钮走的是**同一套后端接口**。

> **提示**：所以你在代码里搜到第二个按钮也是调 `handleGenTable`，不用怀疑自己找错了。

#### handleGenTable：拿表名、拼串、判空，再交给下载器

这个方法按顺序做了四件事：

```js
// 生成代码（需选中业务表）——下面是它的骨架逻辑
function handleGenTable(row, type) {
  // 1. 单表：取当前行的对象，拿当前表的名称
  //    批量：从 tableNames 数组里取选中多张表的表名
  const tableNames = type === 0 ? [row.tableName] : tableNames.value;
  const tableName = tableNames.join(",");
  // 把这些表名转化为一个字符串

  // 2. 没勾表 → 提示 + 中断本方法
  if (!tableName) {
    proxy.$modal.msgError("请选择要生成的数据");
    return;
  }

  // 3. 判断是「下载」还是「自定义路径」
  //    自定义路径：代码直接落到指定路径下方
  //    默认：交给 download.js 的 download
  download("/tool/gen/batchGenCode?tableName=" + tableName, "ruoyi.zip");
}
```

这个空值校验跟我们前面讲的导入功能非常类似，都是先判有没有数据，没有就提示、中断，不往下走。

> **易错点**：注意这里发出去的是 **GET 请求，表名拼在 URL 后面**。到浏览器按 F12 一验证就看得清清楚楚：路径是 `batchGenCode`，后面带着三个表名，中间逗号分隔，同时还能看到压缩包的下载过程。

#### download.js：把 url 拼成完整路径，把令牌带上

刚才提到的 `download` 是一个抽取好的下载文件方法。往上前端目录结构里拉一拉，在 `plugins` 插件目录下有一个 `download.js`，双击打开全屏看：

```js
// download.js 的核心逻辑
export function download(url, name) {
  // 1. 接收两个参数：url（后端地址）、name（下载后的文件以及扩展名）
  // 2. 拼接 baseURL，组成一个完整的后端请求路径
  const requestUrl = baseURL + url;

  // 3. 下载时弹一个提示框
  ElMessage.loading("正在下载数据，请稍候");

  // 4. 通过 axios 发送请求，方式为 get，路径就是 url，并携带令牌信息
  axios.get(requestUrl, {
    headers: { Authorization: "Bearer " + getToken() },
    responseType: "blob"
  }).then(res => { /* 存盘 */ });
}
```

两个参数：一个 url，另一个是下载后的文件及扩展名。拼上 baseURL 之后就是一个完整的后端请求路径了。这一点小伙伴们能接受吧，没什么玄学。

前端这块到此为止，下面进后端。

### 后端：一张表是怎么变成 zip 的

我们在编辑器里双击 shift 全局搜 `batchGenCode`，打开就能看到批量生成代码的入口方法。它接收两个参数：

- `response`：作为响应流，返回下载文件；
- `tableName`：接收前端传来的表名字符串，需要把逗号分隔的字符串转换为字符串数组。

转换的这行代码大家并不陌生，真正重要的是第二步——**根据表的名称来生成代码的字节数组**，最后把字节数组交给 `response` 响应给客户端。

#### Controller 只做两件事

```java
@GetMapping("/batchGenCode")
public void batchGenCode(HttpServletResponse response, String tableName) throws IOException {
    // 前端表名字符串 → 字符串数组
    String[] tableNames = Convert.toStrArray(tableName);

    // 最重要的一步：按表名生成代码的字节数组
    byte[] bytes = genTableService.generatorCode(tableNames);

    // 把字节数组原样写回 response
    writeZipResponse(response, bytes);
}
```

`writeZipResponse` 是收尾的那段，我们放到后面单独讲。先按住 ctrl 跳进 service，看第一层。

#### Service 第 1 层：把字节数组灌进 zip 流

service 里同名方法一共有两层，我提前用通义灵码把注释写好了。先看外面这一层：

```java
/**
 * 生成代码（zip 压缩包字节数组）
 */
public byte[] generatorCode(String tableNames) throws IOException {
    // 第一步：创建字节数组输出流，一会用来存 zip 的压缩数据
    ByteArrayOutputStream bos = new ByteArrayOutputStream();

    // 第二步：创建 zip 输出流，把生成的代码压缩成 zip 格式，便于网络传输
    ZipOutputStream zos = new ZipOutputStream(bos);

    // 第三步（最重要）：遍历表名的数组，把每张表生成成代码并添加到 zip 输出流
    for (String tableName : tableNames) {
        generatorCode(tableName, zos);
    }

    // 第四步：所有文件都塞进去了，对流释放资源，返回 zip 格式的字节数组
    zos.finish();
    return bos.toByteArray();
}
```

中间那一步是重点。前端选中了三张表，这里就遍历三次，每一张表生成完的代码都交给同一个 zip 输出流。全部塞完之后关闭流，把整个 zip 的字节数组返回给上一层。

> **结论**：这一层只干三件事——开字节流、开 zip 流、循环。它不知道任何一张表长什么样。

#### Service 第 2 层：表信息 → 上下文 → 模板 → 渲染

真正的工作量在 `generatorCode(单张表名, zip)` 这个方法里，我们按顺序走一遍。

**第一步，查表的基本信息。** 按住 ctrl 找到方法签名，再打开实现。注意这个基本信息对象内部**也包含了该表的字段信息**——往下拉就能看到一个 `List` 集合存储了该表的列信息，也就是我们说的字段信息。拿到它以后，当前业务表的所有数据都可以获取到。

再往下进到实现里，这是一个 SQL 查询：先查业务的基本信息表，再关联查询业务的字段信息表，查询条件是根据我们指定的表名，然后把返回的所有数据封装到实体类中。

> 这个 SQL 语句比较简单，注释我就不写了，大家能接受吧。没问题，OK。

**第二步，判断是不是主子表。** 拿到表信息以后还要判断一下它是否为子表信息。如果是主子表的信息，还需要给主表去关联子表的信息；如果只是普通的单表操作，这一步不会执行这部分。先了解一下，后面模板加载那里还会再用到这个判断。

**第三步，设置主键列信息。** 这是紧跟着的一步，作用是告诉这个业务表：它这么多字段当中，哪个是主键。逻辑是遍历主表的列，寻找主键列，里面会做一个 `isPk` 的判断，符合主键列的就 `set` 一下。

> **易错点**：如果当前主表**并没有**主键列，它会默认把第一个列当作主键列。这也是数据库 InnoDB 引擎默认的设计原则，不用我们操心。
>
> 当前主表还有子表的话，设计规则跟刚刚一样：从子表当中找到主键列进行设置；不存在的话，就给子表的第一列设置为主键列。

**第四步，把数据库信息变成 Java 代码。** 接下来是整个方法里 388 行附近、最重要的一步：

> 我们需要将数据库的信息生成 Java 代码，这里会用一个技术叫 **Velocity 模板引擎**。

模板的作用很简单——把数据库的数据写入到代码文件当中。那它到底怎么写进去的？先看第一步：

> **结论**：需要将数据库查询的表信息，设置到模板变量当中。也有人称为上下文对象。它可以负责变量的填充。

先通过业务表的对象获取模块名、业务名、包名以及模板的类别，还有功能名。

- **模板的类别一共有三种**：一种是单表的 CRUD，一种是树表，另外一种呢是主子表；
- **前端类型有两种**：一种是 vue2 的，一种是 vue3 的。

取到这些信息以后，就创建了一个 Velocity 的上下文对象，把模板类别、表名、功能名称往里放。注意，如果数据库当中没有功能名，它这边会填充一个字符串——叫「请填写功能名」。

再往下是类名以及类名的首字母小写、模块名称、业务名首字母大写、业务名称、基础的包名、包名、作者、生成时间、组件列、导入列的类型、权限列的信息、表的信息等等，**所有的数据全部设置到上下文对象当中**。

这里还有一个判断：如果我们是树形模板类型，还需要加载树形数据相关的信息；如果是子表，也会在这里加载子表的相关信息。总之，它会根据我们在前端配置的所有生成相关信息，全部塞进模板的上下文对象。

#### 模板加载：模板类型 × 前端类型

设置完毕之后，下面就是加载模板列表了，加载的时候会传两个参数——模板类型和前端类型。

先看前端类型这边：默认用的是 vue2 的版本，如果是 element-plus 的话，它会改为 vue3 的版本。这就是前端类型的设置。

接着它创建一个模板列表来存储模板信息，这些模板数据我们看一下。首先添加的是**后端模板的文件路径**，这个路径对应的是代码生成模块的 `resources` 目录，在 `vm` 目录下方。第一个是 Java 的相关代码，这些文件全部交给模板引擎对象来加载；还有数据库的 SQL 文件，以及对应的 XML 也进行了添加；另外还有前端 api 模板的文件路径。

注意看小伙伴们，这里需要**根据模板的类型来区分**：

| 模板类型 | 页面上的说法 | 加载的模板 |
| --- | --- | --- |
| 单表 | CRUD | 只加载普通的 CRUD 模板 |
| 树表 | tree | 加载 `index_tree.java.vm` 这类带树结构的模板 |
| 子表 | sub | 加载主子表相关的模板 |

一旦模板全部加载完毕，就会封装到集合，返回到刚刚的方法。

**最后一步，渲染模板。** 对模板进行遍历时，有这么一步特别重要——它把我们刚才准备好的**模板变量合并到模板文件当中**，这个过程简称为**渲染模板**，就在这一步完成。通过加载好的模板变量，结合字符输出流写入到模板文件当中，就可以生成代码文件了。然后将生成好的代码文件添加到 zip 的字节输出流当中。

这是第一个模板的合并渲染，以及添加到 zip 文件当中。需要循环遍历，直到所有模板都填充完毕，这个代码才执行结束。

> **结论**：整个代码生成过程，翻译成一句话就是——**初始化模板引擎 → 设变量 → 加载模板 → 渲染模板 → 写进 zip**。

#### 回到 Controller：response 的那些设定

回到上一层，Controller 拿到 zip 的字节数组之后，就通过 HTTP 响应给客户端。这里要做的是：先通过 `response` 做一次 `reset()`，防止头部信息冲突，然后设置一堆响应头信息：

| 顺序 | 设置项 | 作用 |
| --- | --- | --- |
| 1 | `Access-Control-Allow-Origin` | 允许跨域访问 |
| 2 | `Access-Control-Expose-Headers` | 允许 JS 读取指定的响应头 |
| 3 | `Content-disposition` | 指定文件的下载名称 |
| 4 | `Content-Length` | 指定文件的大小长度 |
| 5 | `Content-Type` | 指定文件的 MIME 类型 |
| 6 | `Character-Encoding` | 指定字符集编码格式 |

全部设置完毕之后，就可以通过 IO 工具类把我们的字节数组写入到 `response` 的字节输出流当中，返回到客户端实现下载操作。

最终前端就拿到了这个 zip 压缩包，点保存、解压，就可以获取前后端代码了。

关于源码分析就讲到这里。我们回到 PPT 做个小结：

管理员选中需要下载的业务表，点生成按钮，前端传递需要生成代码的业务表名；后端根据表名查询业务表和它的字段信息；核心点就在于 Velocity 模板引擎，它可以把数据库的数据写入到代码文件，进行合并渲染，最终生成我们想要业务表的完整前后端代码。

剩下的预览、编辑、删除和同步这几个按钮，功能都是针对于业务表基本信息和字段信息的操作，这部分源码跟之前讲的类似，感兴趣的同学可以课下结合通义灵码自行阅读。

### 先给代码生成器换个默认值

源码看明白了，接下来动手改造一下，以适应我们的个性化需求。

问题是这样的：每编辑一张业务表，你都要在基本信息界面里手动去掉实体类的前缀 `tb`、手动指定作者；在生成信息界面里手动指定包路径、模块名等等。这些重复性的工作完全可以通过**调整默认值**来简化——结合当前项目的命名规范，直接在代码生成器当中设置默认值，减少每次编辑时的手动操作。

#### generator.properties 的四个开关

要改哪里？答案就在**代码生成模块的 generator 配置文件**当中。

| 配置项 | 改成的值 | 作用 |
| --- | --- | --- |
| `author` | `it黑马` | 生成代码头部的作者署名 |
| `packageName` | `com.dk.manager` | 新表默认的生成包路径 |
| `autoRemovePre` | `true` | 开启自动去除表前缀的功能 |
| `removeTablePrefix` | `tb_` | 要去除的表前缀 |

改完是这个样子：

```properties
# 代码生成默认值，导入新表时自动套用

# 作者
author=it黑马

# 默认的生成包路径
packageName=com.dk.manager

# 是否自动去除表前缀
autoRemovePre=true

# 要去除的表前缀，多个以逗号分隔
removeTablePrefix=tb_
```

> **易错点**：要去除多个前缀的话，它们之间以逗号分隔，别写成空格。

配置文件改完，按下 `Ctrl + F9` 热部署更新一下，就可以回浏览器测试了。

#### 改完必须重新导入才生效

这里有个非常容易踩的坑：

> **提示**：已经导入的表，它的默认值是在**导入那一刻**从配置文件里读出来存库的。你现在改了配置，数据库里存的还是老值。所以必须先把旧表**删除掉，重新完成表结构的导入**，它才会读取最新的配置文件默认值。

所以操作是：点返回，把出货流水和工单统计表选中删除，重新点击导入按钮，把最新两张表导入进来，点确定。

这次导入完毕以后，我们点第二页，再次点击编辑，注意看基本信息当中——实体类的前缀 `tb_` 已经没有了，作者也已经改成了 `it黑马`；生成信息当中生成包路径也已经改为了 `manager`，模块名同样也叫 `manager`。

到这里，我们已经成功改造了代码生成器的基本信息的默认值。

#### 生成的代码为什么还是不够优雅

默认值搞定之后，我们再来关注一下如何提升代码质量和可读性。

比如我们点预览按钮，目前生成的实体类当中，它的 get、set 以及 toString 方法显得不太优雅——是不是看起来密密麻麻的、不够直观？还有，为了方便查看在线接口文档，我们需要手动为生成的 controller 代码添加 Swagger 的相关注解，而这个过程是比较繁琐的。

所以为了解决这些问题，我们可以在项目当中去集成 **Lombok** 和 **Swagger**，这将大大简化我们的代码并提高可读性。

集成 Lombok 之后，生成实体类会自动包含所需要的 get、set、toString 等方法的注解——这几个注解都是 Lombok 提供的，我们无需再编写繁琐的 get/set/toString 以及有参无参构造，看起来是不是优雅很多了？同时还可以自动为 controller 类添加 Swagger 的相关注解，类上的、方法上的都有，使得在线接口文档生成变得更加方便。

> **结论**：要实现这些增强功能，我们就得掌握 **Velocity 模板引擎的使用**——Velocity 允许我们定制和优化代码的生成模板。所以下面我们开始学习它。

### Velocity 到底在干什么

Velocity 是一个基于 Java 语言的模板引擎，它允许我们使用特定的语法在模板当中嵌入 Java 的对象数据。换句话说，使用 Velocity 我们可以将**界面设计与业务逻辑相分离**，使得界面设计更加灵活，同时保持代码的可维护性。

#### 模板与数据模型的合并

这句话什么意思？我们来看这张图。刚才提到的「界面设计」就是**模板**，它是一种固定的文本结构；而「业务逻辑」呢指的是我们的**数据模型**，它是动态变化的数据。

Velocity 的作用，就是将这些动态数据**合并**到模板当中，然后输出到指定类型格式的文件当中。

```text
    模板：固定的文本结构                    数据模型：动态变化的数据
    index.html.vm                          VelocityContext
    "…成功即在前方，$message"                message = "加油同学"
              \                              /
               \        Velocity 合并         /
                \            ↓             /
                 └──────────────────────────┘
                            ↓
          输出：index.html（一份完整页面）
                "…成功即在前方，加油同学"
```

为了方便大家理解，我们举个例子。假如现在要生成一张电子发票：

- 发票的**格式是固定的**——它是模板，还是数据模型？（是模板）
- 但**每次开票人的信息是不同的**——这就是数据模型。

此时我们创建一个包含开票人信息占位符的模板，然后用 Velocity 把实际开票人的信息填充到模板当中。这是一个合并的过程，然后生成指定人的电子发票。

#### 三个用得上的场景

在项目开发当中，它的应用场景还是非常广泛的：

- **生成动态变化的 web 界面**：根据传入的数据模型，渲染出不同的页面效果。这些在前后端未分离的项目当中用得比较多，现在比较少了；
- **根据模板生成 Java 源码**：这也是若依框架代码生成器的核心能力之一，我们上面刚拆过一遍；
- **把动态页面转换为静态页**，从而提高网页的加载速度和性能。比如一些热点新闻页面、商品详情页，都会用静态化来处理。

其实在 Java 中有多种模板引擎可以选择，除了 Velocity 之外，还有 FreeMarker、Thymeleaf 等等。而若依框架选择了 **Velocity** 作为其模板引擎。

#### 入门案例：把「加油同学」做成变量

先来看需求。这是一个静态的 HTML 页面，内容写着：

> 只要大家心怀梦想，坚持不懈，成功即在前方，加油

这句话就是送给屏幕前的小伙伴们的。只要你坚持学习，未来可期。现在我想把最后结尾的这几个字——**加油同学**——使用 Velocity 模板引擎改为**加油少年**。

具体操作步骤我们来分析一下，一共三步：

- **第一步，准备模板。** 也就是一个 HTML 格式的页面。在这个页面当中注意看这里，我们把「加油同学」这几个字替换为一个**变量占位符**了，语法为 `$` 加花括号写上 `message`，稍后可以嵌入 Java 的数据。
- **第二步，完成数据的填充。** 主要代码一共分为四步，其中第 1、3、4 步是固定的，我们只需要关注**第二步**：定义模板所需要的 Java 变量数据模型即可。
- **第三步，运行代码。** 执行完毕以后，打开输出的 HTML 页面，就可以看到占位符被改成了「加油同学」这几个文字输出了。

非常简单，现在动手操作。

模板文件放在 `dk-generator` 这个代码生成器模块下（在 `src/main` 目录下存放 Java 代码和配置文件，最终会进行编译、打包、上线部署）。但我们写的这些测试代码，你期望它跟这些业务代码一起打包上线吗？肯定是不期望的。

那怎么办呢？很简单，咱们项目是 Maven 结构，可以创建一个 `test` 目录来存放测试的相关代码，最终它不会上线打包。

所以目录这样建：在 `src` 下新建 `test/java`，再新建 `test/resources` 用来存代码模板。模板该怎么命名呢？注意看，在若依原有的代码模板当中，它的后缀都是以 `.vm` 结尾的，所以我们也需要创建一个 `.vm` 结尾的模板文件——而它的格式内容是 HTML 页面，所以建一个 `index.html.vm`。

模板内容从一个标准的 HTML 页面复制过来，把「加油同学」这四个字改为变量占位符：

```html
<!DOCTYPE html>
<html lang="zh">
<head>
    <meta charset="UTF-8">
    <title>加油页面</title>
</head>
<body>
<h1>心怀梦想</h1>
<p>只要大家心怀梦想，坚持不懈，成功即在前方，${message}</p>
</body>
</html>
```

第一步模板定义完毕了。

#### 测试代码该放哪

在 `test/java` 目录下新建一个包叫 `com.dk.test`，然后写一个测试类，就叫 `VelocityDemoTest`。里面写一个 `main` 方法，一共四步，我们来写一下。

**第一步：初始化模板引擎。** 这个初始化操作若依已经提供了一个工具类，在 util 包下有一个 `VelocityInitializer`。我们简单看一下它做了什么：

```java
public class VelocityInitializer {
    public static void initVelocity() {
        Properties p = new Properties();
        // 加载类路径下方的所有以 .vm 结尾的文件
        p.setProperty("file.resource.loader.path", "classpath:");
        p.setProperty("file.resource.loader.class",
                "org.apache.velocity.runtime.resource.loader.ClasspathResourceLoader");
        // 指定模板文件的字符集为 UTF-8
        p.setProperty("input.encoding", "UTF-8");
        p.setProperty("output.encoding", "UTF-8");
        // 完成模板引擎的初始化操作
        Velocity.init(p);
    }
}
```

这些步骤全部抽取到了这个工具类当中，并且提供了一个静态方法 `initVelocity`，我们直接调用这个类的方法就能完成 `.vm` 的初始化了。

**第二步：准备模板的数据模型。** 也就是我们之前在做源码分析时介绍的上下文对象。

**第三步：读取模板。** 通过 Velocity 来读取 `vm/index.html.vm` 这个模板文件。

**第四步：渲染模板，也就是合并输出。**

把四步拼起来就是完整代码：

```java
package com.dk.test;

import org.apache.velocity.Template;
import org.apache.velocity.Velocity;
import org.apache.velocity.app.VelocityContext;
import com.dk.generator.util.VelocityInitializer;

import java.io.FileWriter;
import java.nio.charset.StandardCharsets;

public class VelocityDemoTest {

    public static void main(String[] args) throws Exception {
        // 第一步：初始化模板引擎
        VelocityInitializer.initVelocity();

        // 第二步：准备模板的数据模型（也就是上下文对象）
        VelocityContext context = new VelocityContext();
        context.put("message", "加油同学");

        // 第三步：读取模板
        // 初始化时已经默认能定位到 classpath 类路径了，直接写 vm 下方的文件即可
        Template template = Velocity.getTemplate("vm/index.html.vm", StandardCharsets.UTF_8);

        // 第四步：渲染模板，也就是合并输出
        // 第一个参数是数据模型的上下文对象，第二个参数是输出的位置
        FileWriter writer = new FileWriter("D:/workspace/index.html");
        template.merge(context, writer);

        // 注意最后别忘了关闭流
        writer.close();
    }
}
```

这里有两个细节是编辑器帮倒忙，我们得自己收拾：

- `Velocity.getTemplate` 有多个重载，写代码时 IDEA 会提示。选**带模板名称 + 字符集编码**的那个重载，初始化模板时已经默认能定位到 classpath 类路径了，所以直接写 `vm/index.html.vm` 这个模板文件，再补上 `UTF-8`；
- `merge` 的第二个参数 IDEA 默认给的是 `System.out` 系统输出流，那显然不是我们想要的——我们要的是一个静态的 HTML 页面，所以得自己 `new` 一个 `FileWriter`，把输出的位置指定到 `D:/workspace` 目录下，文件名叫 `index.html`。写 `FileWriter` 会抛异常，我们直接给 `main` 方法加 `throws Exception` 抛出去。拿到文件输出流以后，把 `System.out` 替换掉，就可以把变量渲染到模板完成合并，输出到指定路径下了。

> **易错点**：`FileWriter` 一定要做关流操作，不然生成的页面是空白的。
>
> 顺便记一笔：在未来的开发当中，第一步、第三步、第四步基本是固定的，我们只需要根据不同的模板给它填充数据模型，**第二步才是我们重点要关注的**。

#### 四步写完，再跑一次

点击执行，代码执行成功了。我们来看一下生成的文件 `index.html`，双击打开——这边显示的名称就叫做「加油同学」，是不是做到了动态填充？

那这部分的值我们其实可以做修改的。把 `context.put` 里的「加油同学」改为「加油少年」，重新生成合并文件，点击执行，回浏览器刷新页面，注意看，「加油同学」是不是改为了「加油少年」？从而做到了将界面设计的模板与我们的数据模型相分离。

> **结论**：大白话来说就是，模板界面没有动态数据，前端人员可以随时调整和修改；调整完毕以后，由后端人员重新把动态数据加载到模板当中，产生新的页面提供给用户访问。

回到笔记做个小结，一共三步：第一步准备模板，把「加油少年」改成一个 `${message}` 占位符，方便动态填充数据，注意模板的扩展名是 `.vm`；第二步完成数据填充，代码一共四个小步骤，我们只关注第二步——根据设计的模板准备数据模型；顺带提醒一下，做文件渲染合并输出时 `FileWriter` 一定要关流，不然页面是空白的；第三步执行代码，在 D 盘的 workspace 目录下查看生成好的 HTML 页面，双击打开就能看到动态填充的数据了。

### Velocity 基础语法：声明与取值

Velocity 的入门案例走完了，接下来学习它的基础语法，这将为后续代码模板的升级改造打下坚实的基础。我们从**变量定义和获取**开始。

#### 在模板里声明变量

除了在 Java 代码中定义数据模型的变量之外，我们也可以在**模板界面直接使用 `#set` 这个关键字来声明变量**。

语法长这样：`#set` 后面跟上一对圆括号，圆括号里左边是变量名 `$name`，右边就是该变量的值：

```velocity
## 定义变量
#set($name = "velocity")
```

另外注意，`##` 开头的这一行是 Velocity 的模板注释，页面上不会输出。在编辑器里可以直接用快捷键 `Alt + /` 生成。

定义好变量之后，我们在页面当中获取变量值呢有两种语法，它们都非常简洁和易于使用：

- **第一种**：直接通过 `$` 后面跟上变量名即可，跟定义时的语法是类似的，简洁明了；
- **第二种**：用 `$` 加花括号所包裹，内部写上变量的名称，也就是 `${name}`。

#### 两种取值写法，差别在拼接

这两种语法有什么区别呢？我们来演示一下。在模板文件第 12 行，我们先定义一个变量，然后分别输出：

```velocity
## 定义变量
#set($name = "velocity")

$name<br>
${name}<br>
```

执行一遍，回浏览器刷新，注意看，两种写法是不是都取到了 `velocity`？

这个时候有小伙伴问了：这两种情况有什么区别呢？开发时用哪一种比较好？

> **结论**：简单的方案可以快速地引入变量的值，但**涉及到字符串拼接的话，它就不太适用了**。

举个例子。假如我们现在要拼接一个 service 的名字，第三种情况：

```velocity
## 定义变量
#set($column = "order")

$columnService<br>
${column}Service<br>
```

注意看，`order` 是一个变量名，而后面跟的 `service` 是一个固定的字符串——因为将来我们可以生成订单的 service、设备的 service、商品的 service 等等，右侧 `service` 是固定值，左侧是变量。

那么简单语法行不行呢？我们执行一下，回浏览器刷新。注意看，**它把这个变量当成了一个普通文本，直接跟 `service` 拼接在了一起**，而不是我们想要的变量的值：

```text
页面输出：  $columnService
           orderService
```

所以这个时候就要使用标准的语法，给它加上花括号，这样再做拼接就没有毛病了。

> **易错点**：IDEA 给我们踩了一个坑——当我们在写左花括号的时候，它会在右侧帮我们补上一个右花括号。记得把多余的那部分删掉，不然渲染出来会多出一个 `}`。

到这里，小伙伴们能否区分两者获取变量的方式了？

> **结论**：**单独使用时推荐简单语法**，因为它语法简单；**涉及到字符串拼接时推荐使用标准语法** `${}`。记住这一个细节就够用了。

#### 对象变量：$region、$region.id、$region.regionName

上面都是简单类型的变量。那如果我想定义一个**对象**的变量呢？前端又该如何获取？

我们拿区域表的实体类 `Region` 举例。找到 `dk-manager` 模块，打开 `src/main/java` 下的 domain 包，这个实体类就在这里。双击打开后，把当前这个实体类复制一份，粘贴到代码生成器的模块，放到 test 包下即可。

粘贴过来的代码看起来不太优雅，我们把 get/set 方法删掉，然后手动给它添加 Lombok 的注解：get/set 方法加上 `@Data`，无参构造 `@NoArgsConstructor`，全参构造 `@AllArgsConstructor`：

```java
@Data
@NoArgsConstructor
@AllArgsConstructor
public class Region {
    private Long id;
    private String regionName;
}
```

对象定义完毕。通常情况下我们还是在 Java 代码当中来定义变量，所以回到我们的测试类当中，在第二步下方，我们先创建区域对象：

```java
// 创建区域对象（提供了全参构造，可以直接赋值）
Region region = new Region(1L, "北京北五环");

// 把它交给 Velocity 的上下文对象，准备好数据模型
VelocityContext context = new VelocityContext();
context.put("region", region);
```

到这里，区域对象的数据模型就准备好了。接下来看如何在模板文件中获取数据。找到 `index.html.vm`，为了看得清晰我们加一条 `<hr>`，然后获取区域对象中的数据。

我们知道区域对象一共有两个属性，一个是 id，一个是区域的名称。接下来通过模板把这两个属性取出来：

```velocity
<hr>
$region<br>
$region.id<br>
$region.regionName<br>
```

这里我们先使用简单语法，因为不涉及到字符串拼接。获取对象 id 很简单，直接写上 `$region` 后面跟上 `.id` 即可；再写上区域的名称 `$region.regionName`。

执行刷新之后，注意看结果：

- **第一行**我们直接写 `$region` 的话，它底层走的是 `toString` 方法，直接打印出了对象的 id 和区域名称；
- **后面两行**通过点的方式，获取到了区域的 id 和区域名称。

> **提示**：注意模板里的**变量名**是 `put` 时左侧的名称，跟右侧传进去的对象**没有**任何关系。你这里写 `a`，那下方就要写 `$a`，然后再去点实体当中的属性，比如 `id`、比如 `regionName`，来获取具体的属性值。
>
> 另外这里提示符是通义灵码帮我们生成的代码，建议小伙伴们还是**手写**一遍，毕竟是第一次学基础语法，手写一遍能巩固一下。

到这里，我们把变量声明和获取的两种方式、简单类型和对象类型全部过了一遍。接下来的活儿就交给你了：动手完成 Velocity 基础语法的变量练习，把代码生成器里那些密密麻麻的模板改成你自己想要的样子。

## 代码生成器模板与 Spring Security 安全控制
> 对应块：BLK29 | 覆盖分集：P98-P103 | 块标题（分集名）：《原理篇-09.代码生成器-velocity-循环》

### 循环与判断：模板里的 #foreach 与 #if

模板开发当中，我们经常需要遍历集合或数组，把其中的每一个元素输出到页面上。Velocity 为这种场景提供了一个很简洁的语法，基本格式就是井号 `forEach`，中间写上要遍历的集合和循环体，最后以 `#end` 结束。

> **定义**：`#foreach($item in $list) ... #end` —— Velocity 的循环指令。`$item` 是当前这一次循环拿到的元素值，`$list` 是被遍历的集合。

我们直接练一遍。先在模板上加一条水平线，然后定义一个集合，语法是井号 `set`：

```velocity
<hr/>

#* 定义集合 *#
#set($forList = ["春", "夏", "秋", "冬"])
```

方括号里把元素用逗号隔开就行。在 IDEA 里这类骨架都能靠实时模板和通义灵码的补全直接铺出来，敲几个字符按 Tab 键就完事。

集合定义完了，接下来做遍历循环。关键字是井号 `forEach`，遍历的集合写成 `$forList`，注意这里的写法和 Java 是一样的：先写 `in` 的关键字，左侧就是我们遍历到的每一个元素值，写成 `$item`。然后就可以在循环体里输出当前的元素了：

```velocity
#* 遍历集合 *#
#foreach($item in $forList)
    ${item}<br/>
#end
```

执行一下，回浏览器刷新——春夏秋冬全出来了，没毛病吧。

#### 给每个元素配个序号

现在我想给每一个遍历出来的元素再加一个序号，怎么办？在 `$item` 前面补个中括号，中括号里的序号值不能写死 123 吧，那得动态获取。这里就要用到 Velocity 的另一个语法 `$foreach.count`。

```velocity
#foreach($item in $forList)
    [${foreach.count}]${item}<br/>
#end
```

> **易错点**：`${foreach.count}` 是**从 1 开始**的，刷新页面你会看到 `[1]春[2]夏[3]秋[4]冬`。如果你想显示索引，就把 `count` 改为 `index`，而 `${foreach.index}` 是**从 0 开始**的。

这两个的差别很小，但选哪个要看场景——给人看的列表编号用 `count`，要跟数组下标、跟后端传过来的位置对齐就用 `index`。所以我一般会在模板里给它留一行中文注释，写明"count 是从一开始的，index 是从零开始的"，下次自己回来改的时候不至于搞混。

#### 遍历对象集合

上面玩的是简单类型，接下来演示对象类型该怎么遍历。还是以区域来举例，回到测试类当中，我们在里面再加一个区域对象，把第一个对象复制一份，上面叫 `region1`，下面叫 `region2`；原来那个还叫 `region1`。然后我们需要定义一个集合来存这两个对象。

这里直接调用 List 集合的静态方法 `of`，把两个元素加进去，补上分号，返回的就是一个 List 集合；再把它添加到上下文对象当中，模板变量名叫 `regionList`：

```java
Region region1 = new Region();
Region region2 = new Region();

region2.setId(2L);
region2.setName("北京四环");

// JDK 9 才提供的静态工厂方法
List<Region> regionList = List.of(region1, region2);

// 放进上下文对象，模板里就能用 $regionList 拿到
context.setVariable("regionList", regionList);
```

数据模型准备好了，回模板页面遍历输出：

```velocity
#* 遍历区域集合 *#
#foreach($region in $regionList)
    ${region.id} ${region.name}<br/>
#end
```

这里先遍历的是 `$regionList` 集合，拿到的元素是区域对象，我们分别取出区域的 id 和区域名称，通过点属性名获取对应的属性值，在页面展示即可。

一开始写的时候，id 和名称后面我都跟了 `<br/>`，两个元素各占一行，看起来不太方便，所以把第一个 `<br/>` 去掉了，让 id 和名称在一行内显示。执行一下刷新，两个区域的信息都展示出来了，只不过它们的 id 和名称是刚刚复制的那份，再把第二个区域改一下就完美了。

一执行就报错了，在代码第 23 行报"找不到该符号"。这个坑跟循环语法本身无关，但特别容易撞上，咱们顺手把它讲清楚。

`List.of()` 这个方法是在 **JDK 1.9 之后**才添加的，而若依的父工程版本是锁死的——打开 `pom.xml` 往上拉，这里指定的是 `jdk 1.8`。虽然我们在开发环境指定的是 JDK 11（点开工程结构一看，确实是 11），**但那是编译环境，运行时环境已经锁定为 1.8 了**，所以这里是不兼容这个方法的。编译期不报错，跑到运行期就炸。

解决方案也很简单，把 pom 里的 `<java.version>` 从 `1.8` 改为 `11` 就可以了。改完之后第一次执行需要重新编译，大家耐心等一下。编译成功，回浏览器刷新，对象类型就正常输出了。

> **提示**：如果你不想动 JDK 版本，坚持用默认的 1.8，那么换成 `new ArrayList<>()` 之后再 `add` 这两个区域对象也是完全可以的，大家可以根据自身的情况来调整。

到这里，Velocity 的循环语法我们就把简单类型和对象类型都练完了。

#### #if 条件判断

接下来学另外一个基础语法，条件判断。模板开发当中我们经常需要根据不同的条件规则，来决定是否输出特定的内容，而 Velocity 提供了一个简单直观的语法结构来实现条件判断，就类似于 Java 中的 `if...else if...else` 语句，只不过在每个关键字的前方增加了一个井号，并且还有一个 `#end` 结束语句。

我们拿成绩来举例。定义一个成绩变量，然后通过业务判断来看他的成绩：大于等于 80 分显示优秀，大于等于 60 分显示及格，小于 60 分默认就是不及格。

```velocity
#* 定义成绩变量 *#
#set($score = 80)

#if($score >= 80)
    优秀
#elseif($score >= 60)
    及格
#else
    不及格
#end
```

写的时候注意，井号 `if` 后面判断 `$score`，如果这哥们儿大于等于 80 分就显示优秀；第二个判断条件是井号 `elseif`，后面判断 `$score` 大于等于 60，显示及格；再往下走井号 `else` 就是不及格；最后以 `#end` 结束。格式化一下让 if 语句左侧对齐。

> **提示**：虽然 IDEA 都会帮我们把 `elseif` 补全出来，但这毕竟是咱们第一次练这个语法，**还是建议各位手敲一遍**——手敲一遍你才知道 `#elseif` 是一个整体，中间没有空格也没有多余的井号。

执行、刷新，录入的是 80 分，这里就显示优秀。把成绩变量改成 55 分重新执行，刷新，就显示不及格了。

那如果直接判断的是**对象**呢？这里跟前端的语法是一样的：我们不需要写"不等于空"，直接判断对象的话，就代表该对象不为空的时候，我们才会去执行 if 判断里面的语句；如果你想判断对象为空，只需要在前方加一个感叹号做逻辑取反，也就表示当对象为空的时候才执行里面的逻辑。

```velocity
#if($user)
    欢迎回来，${user.userName}
#end

#if(!$user)
    暂未登录
#end
```

看起来是不是简洁一些？另外补充一点，在条件判断当中 Velocity 也支持一些逻辑运算符，比如说与或非的符号 `&&`、`||`、`!`，这部分跟 Java 代码也是一样的。

先说清楚一件事：模板里的变量不是凭空来的。生成代码的时候，Velocity 的工具类已经把业务表的基本信息和字段信息全部放到了变量模型的上下文对象当中。

```text
业务表 sys_biz_order（表名、表注释、作者，以及每一列的
字段名、Java 类型、是否列表展示、是否父类属性、注释、Excel 日期格式）
        │
        │  代码生成器读取表信息 + 字段信息
        ▼

  moduleName         模块名

  className          大写类名

        │
        │  Velocity 渲染 ${变量} 与 # 指令
        ▼
  domain.java.vm  ─────────►  Order.java（实体类）
  controller.java.vm ─────►  OrderController.java（控制器）
```

后面读模板的时候你会发现，几乎每一行都能在这张图里找到来源。

#### 实体类模板

双击打开 `domain.java.vm`，往上拉，这就是实体类的代码模板。它映射数据库的表结构，使用 Velocity 模板以后，我们就可以自动化地生成这些数据模型，从而节省大量手动编码的时间。

**第一行**是定义包路径的，取的是上下文对象里的 `$packageName`，也就是当前项目的基础包名，形如 `com.dk.manager`，后面拼上固定的 `.domain`，这是当前实体类所存放的包路径。你可以对照着真实的 `Order` 实体类看，效果是一样的。

**中间的导包**是根据列的类型来做的。这里有个细节值得注意：像 `Long`、`String` 这些类型都在 `java.lang` 包下，而 `java.lang` 包是默认不需要导入的，所以实体类就简化了这部分操作；有其他特殊类型的，我们才会进行导入。

再往下看，这里导入了 Apache commons-lang 的包，主要用于生成对象的 toString 方法；还有我们项目自定义的 Excel 注解的包，这边也都做了导入。

**接着是一个 `#if` 判断语句**：如果它是一个单表的 CRUD 操作或者主子表，我们需要让类的默认去继承 `BaseEntity`；如果它是一个树表，这里需要继承 `TreeEntity`。所以导包这里也有一个判断。目前我们的订单实体导入的是 `BaseEntity`，它是一个单表的 CRUD 操作。

**再往下是生成实体类的注释**。对比一下实体类你会看到对应关系：`${className}` 对应类名，`${businessName}` 之类的变量对应业务名（比如订单管理），`${tableName}` 对应表名，`${author}` 是我们在配置文件里指定的作者（比如黑马），还有我们的代码生成时间，都通过变量获取到了。

这里还有一个判断：如果是单表或主子表，就设置 `baseEntity` 相关的变量；如果是树表，就设置 `TreeEntity` 这个变量，而它正是下方需要做继承的。很显然我们的订单表继承的是 `BaseEntity`。再往下还指定了类的名称，叫大写的 `Order`，然后是定义类的序列化版本号，固定值是 1，跟我们生成的代码结构完全一样。

**再往下这一步就比较重要了**：我们要获取当前业务表所有列的信息，也就是我们的字段信息，做一个 `#foreach` 的遍历，将订单表所有的字段属性在这里面遍历生成。

遍历的时候首先做了一个判断：**如果这不是父类的属性，才生成**。什么意思？大家别忘了，我们每一个实体类都会去继承 `BaseEntity`，而在 `BaseEntity` 当中已经有创建人、创建时间、更新人、更新时间以及备注说明这几个信息了，父类已经写好了，请问我们的子类还有必要重新去生成这些属性吗？显然是不需要的。所以这里有个判断的过程，如果是刚才命名的这五个字段，我们就跳过了。

如果不是的话，首先来生成属性的注释，比如说"主键"、"订单编号"；下面呢还有一个判断，**如果该字段是在列表展示的**——比如说订单编号是在列表展示的，那我们要生成订单编号的注解；而机器编码是不需要在页面列表当中展示的，那这个注解就不需要生成。所以这里面做了一系列的判断过程。

而在判断的时候还需要做一个处理：如果你是日期类型，我需要把日期类型转换为指定格式的字符串（年月日）；还有在解析 Excel 的时候，也要转换为年月日的格式。

```velocity
#if($column.isList())
@Excel(name = "${column.columnComment}", dateFormat = "yyyy-MM-dd", parseFormat = ["yyyy-MM-dd"])
#end
```

下面就是生成属性的定义了：跟上 `private` 关键字，获取该属性的 Java 类型（`Long`、`String`），还有获取该属性的字段名称（`javaField`，比如 `id`、`orderNumber` 等等）。通过整个遍历，订单表的所有属性就都生成出来了。

再往下还有一个判断过程：如果当前是表有子表的话，我们需要在里面定义一个子表的集合来表示主子表的关系、存储子表的相关数据。目前订单表是一个单表操作，所以这部分并没有包含。

**再往下是生成 get 和 set 方法**，当然它也是个 `#foreach` 的循环过程。对比一下订单实体类往下拉，生成 id、生成订单编号、生成设备编号，这就是我们生成的 get/set 方法，完全对得上。同理，如果有子表数据的话，还会生成 List 集合的 get/set 方法。

**最后是生成 toString 方法**。对比实体类往下拉能看到 toString 的拼接写法：

```velocity
@Override
public String toString() {
    return new ToStringBuilder(this)
        .append("id", getId())
        .append("orderNumber", getOrderNumber())
        .append("machineCode", getMachineCode())
        .toString();
}
```

回到模板当中：先定义 toString 方法，然后 `return` 返回了一个 `ToStringBuilder` 字符串拼接对象，通过 `#foreach` 来获取所有的字段属性名，再通过它们的 get 方法来获取具体的值。

以上就是我们读实体类模板的简单介绍。有了这个模板以后，我们就可以自动化地生成该表的所有数据模型，非常方便。

#### 控制器模板

接下来再看 controller 模板，双击打开往上拉。

**第一行**大家应该不陌生了，获取当前模板的包路径。下面是导入该项目的 Java 类库：List 集合、`AjaxResult`、`TableDataInfo`、权限控制、`@Log` 自动注入，还有我们 Rest 风格的请求方式、`@PathVariable` 获取请求路径参数、`@RequestBody` 获取请求体参数、`@RequestMapping`、`@RestController` 等等。

下方呢是做了一个判断。单表操作或主子表操作，这里需要返回一个分页对象 `TableDataInfo`；如果是一个树表，这边**不需要做导包**——因为树表我们查询的是所有数据，然后由前端来生成树形结构的，这里并不包含后端的分页功能。

**再往下是生成 controller 类的注释**，作者、时间，这跟刚才实体类的模板是完全一样的。下面是类的定义信息，我们找到订单的 controller 类来对比：

```java
@RestController
@RequestMapping("${moduleName}/${businessName}")
public class ${className}Controller extends BaseController
```

`@RestController` 是固定的，`@RequestMapping` 这里有一个 `${moduleName}`，它对应的就是我们的模块名，后面跟的是我们的业务名，中间做个拼接。`${className}` 这边注意是 C 大写的，所以对应的是大写的 `Order`；然后继承 `BaseController`，接着做订单的 Service 依赖注入——这里是大写的 `Order` 类型加一个小写的对象名，所以声明变量的时候我们用的是小写的 `className`。

**下面是方法的注释了**。`${businessName}` 对应的是订单管理，还有权限 `@PreAuthorize("@ss.hasPermi('${moduleName}:${businessName}:list')")`，其中 `list` 是固定的。下方呢就会做出一个判断：如果是单表或主子表，注意看我们的返回值是 `TableDataInfo`，也就是分页对象了；如果是树表，我们返回值就是一个标准的 `AjaxResult`，是查询 List 集合直接返回到前端，由前端来生成树表的结构。

单表/主子表与树表的差别，到这里就很清楚了：

| | 单表 / 主子表 | 树表 |
|---|---|---|
| 实体类继承 | `BaseEntity` | `TreeEntity` |
| 是否导入 `TableDataInfo` | 是 | 否 |
| 列表接口返回 | `TableDataInfo`（带分页） | `AjaxResult`（List 全量数据） |
| 树形结构谁生成 | — | 前端 |

查询列表方法之后的模板跟查询列表是类似的，就是来做增删改查的，这比实体类的模板要简单很多。往下拉：这是导出方法的，这是根据 id 做查询的，这是新增，这是修改，这是删除，跟我们订单 controller 当中这几个方法都一一对应上了。

有了这个固定的模板，我们将来除了导入订单，还可以导入商品、设备，变量名做了替换而已。所以通过 Velocity 模板，我们可以快速生成控制器框架的代码，为后续的功能开发打下坚实的基础。通过这两个模板，我们可以看到 Velocity 是如何帮助我们快速生成标准的代码结构的，这不仅提高了开发效率，还有助于保持代码的一致性和可维护性。

下小节我们对这两个模板进行升级改造，以支持 Lombok 和 Swagger 的相关注解。

### Lombok 集成：把冗余代码删干净

上一节把模板读懂了，现在动手改造，第一个目标是集成 Lombok 注解——这将使我们的代码更加简洁和优雅。

需求很明确：改造 domain 模板，也就是实体类的模板，通过集成 Lombok 添加相关注解；这四个注解会自动生成标准的 Java 属性方法，然后**删除冗余的 get/set 以及 toString 方法**，让生成的实体类代码看起来更加简洁和优雅。

> **提示**：若依默认并没有提供 Lombok 依赖，我们需要确保项目当中已经添加了 Lombok 的依赖坐标。其实这一步我们之前已经完成了——在 JDK 的 common 模块里。大家可以打开它的 `pom.xml` 往上拉确认一下；而且项目当中自定义的 DTO 和 VO 类已经在使用相关注解了。

#### 给类加上四个注解

找到实体类模板，`public class` 的上方就是我们的阵地：

```java
@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class ${className} extends ${entity}
{
```

四个注解的分工是这样的：

| 注解 | 作用 |
|---|---|
| `@Data` | 自动生成 getter、setter 以及 toString 方法 |
| `@NoArgsConstructor` | 生成无参构造方法，方便实体类操作 |
| `@AllArgsConstructor` | 生成全参构造方法 |
| `@Builder` | 简化对象的创建，快速完成对象属性的复制操作 |

这四个注解还是比较常用的。

#### 一定要手动检查导包

写完注解之后呢，**我们要检查一下当前的模板当中是否已经对 Lombok 进行了导包的操作**。逐个对一下：`builder` 没问题，`data` 没问题，无参构造没问题——缺了个谁？是不是缺了一个**全参构造**。

> **易错点**：由于我们当前的代码模板是 `.vm` 而不是 `.java`，IDEA 在导包的时候很有可能会出现遗漏问题。大家课下自己练的时候一定要注意不要去踩这个坑。

把缺少的这条补上。为了让这一部分导包的代码看起来结构更清晰，我们把 lombok 的导包先剪切走，把多余空格删掉，然后在最下方增加一行注释「导入 lombok 的相关注解」，放回原来那个位置就可以了。四个注解，对应四条导包操作。

#### 删掉被注解接管的代码

接下来找到当前模板的 get/set 方法这一段给它删除。看第 75 行附近，注释写着"为每个属性生成 get and set 方法"，这是 `#foreach` 的开始，往下拉是 `#foreach` 的结束，这部分整体删掉。

同理，如果是子表的话，这个集合的 get/set 方法我们也可以用注解来生成，所以这部分也删掉。还有最下方的重写 toString 方法，这部分也可以删除。

> **易错点**：删除时注意，**最后一个花括号是当前类的结束符，这个不能误删**。我们只删从 toString 方法开始一直到类结束花括号之前的部分，保留最后一个花括号。

还有一个小的细节，往上拉到当前模板的最上方：这里有一个 Apache commons 的导包代码，这两个对象是用于 toString 方法做字符串拼接的。请问 toString 方法都已经被我们删除了，那这两个导包咱们还需要吗？显然不需要了，所以这部分也一起删掉。

到这里，实体类模板就升级改造完毕了。按下 `Ctrl+F9` 热更新一下，更新成功以后回浏览器，就拿订单表来演示：点击一下预览按钮，注意看当前生成的预览代码当中，已经完成了 Lombok 的导包操作，并且在类上面增加了 Lombok 的相关注解；继续往下拉，冗余的代码、get/set 方法以及 toString 是不是都已经删除了？那这样的代码看起来是不是就简洁很多了。

#### 替换实体类并验证

接下来把生成的实体类代码拷贝到项目当中。往上拉点击复制按钮，找到对应的 `manager` 业务模块，打开 domain 包，找到 order 订单，打开——这是原来的，全选删除，做一个 `Ctrl+V` 的替换。

### Swagger 集成：让接口文档自动长出来

代码生成器集成完 Lombok，接下来进一步升级，这次集成 Swagger 注解。

Swagger 是一个强大的 API 文档生成工具，它可以帮助我们自动生成在线接口文档，极大地提高了 API 文档的维护效率和易用性。我们的目标是改造 controller 模板，也就是控制器模板，通过集成 Swagger 为当前的类和类中的方法添加相关注解，并生成相应的 API 文档。

若依的项目已经集成了 Swagger 的相关坐标，所以这一步直接跳过，我们只需要找到 control 的模板来改造。

#### 类上加 @Api

先找到当前类的位置，往上拉到第 33 号的位置，我们添加一个 `@Api` 的注解。这个注解当中有一个属性叫 `tags`，这个属性的作用将用于 Swagger 文档中的**分类显示**。

为了保持代码的清晰和直观，这里我们使用注释当中的方式，把名称复制下来拼接上 `Controller` 作为此属性值。最终我们生成的代码就叫"订单管理Controller"，是不是做到见名知意了？

```java
/**
 * ${moduleName}Controller
 *
 * @author ${author}
 * @date ${date}
 */
@Api(tags = "订单管理Controller")
@RestController
@RequestMapping("${moduleName}/${businessName}")
public class ${className}Controller extends BaseController
```

模板里这个值不是写死的"订单管理"，而是拿注释里的类名变量拼一个 `Controller` 后缀——换一张表，它就自动变成"商品管理Controller"。

#### 每个方法上加 @ApiOperation

```java
@ApiOperation(value = "查询订单管理列表")
@GetMapping("/list")
public TableDataInfo list(Order order)
```

做完第一个方法把它复制下来：找到第二个方法——导出列表的方法，粘过来，注意这个注释需要更替一下，改为"导出订单管理列表"。重新复制，找到第三个方法——获取详细信息，改为"获取订单详细信息"。再次复制，往下拉，新增方法，改为"新增订单详细信息"；再复制，修改方法，把"新增"改为"修改"，多余的后半截删掉；最后找到删除方法，把"修改"改为"删除"。

到这里，所有的方法我们都增加了 `@ApiOperation`，用于描述该方法的功能。

> **提示**：如果你希望 Swagger 能展示返回结果的详细信息，还有一个坑要先知道——还记得 `AjaxResult` 吗？它默认继承了 `HashMap`，所以 Swagger 是不兼容的。那怎么办呢？直接把它改为 `R` 类型，这是一种通用的返回类型，可以包含各种不同的数据结构。把需要返回结果的这部分全部改为 `R` 就可以了，这个改造我留作课下作业，具体做法放在文末的题目里。

它的两大核心，就是接下来要展开的**认证**和**授权**。

### 认证和授权：一张借书证

我用一个简单的例子来帮大家领会它们的意义。

想象一下，现在小智同学要去图书馆借书。门口的图书馆管理员会要求小智出示借书证，这个借书证上有小智的照片和姓名，管理员通过它来确认小智的身份——而这个过程就是一个认证的实例。在 Spring Security 的世界里，认证就像用户登录时提交用户名和密码，系统通过这些信息来验证你是谁。

再来看看授权。假设小智同学已经踏入了图书馆的大门，但小智想进入只有持有特定权限才能进入的参考书籍区时，管理员呢会再次检查小智的借书证，看他是否有相应的权限标记。如果有，小智就能进入这个区域；如果没有，小智只能遗憾地止步于此。这就是授权的精髓。

| | 认证 | 授权 |
|---|---|---|
| 回答的问题 | 你是谁 | 你可以做什么 |
| 图书馆比喻 | 管理员查借书证，确认身份 | 管理员查借书证上的权限标记，决定能否进参考书区 |
| 发生的时机 | 登录时提交用户名密码 | 认证通过**之后** |
| 保证了什么的合法性 | 用户**身份**的合法性 | 用户访问**资源**的合法性 |

通过这个图书馆的例子，希望大家能够对 Spring Security 的认证和授权有一个清晰的认识：认证确保了用户身份的合法性，而授权确保了用户访问资源的合法性。

### Security 配置类：把安全策略装配起来

知道了认证和授权是什么，接下来要解决一个更实际的问题：**怎么让它们真的生效**。答案就是配置类——它是实现安全控制的核心部分，可以开启 Spring Security 的各种功能，以确保外部应用程序的安全性：包括认证、授权、会话管理、过滤器的添加等等。

我们的配置类位于 JDK 的 framework 模块中的 config 包下，叫做 `SecurityConfig`。它是安全控制的指挥中心，从认证到授权，从会话管理到过滤器的设置，配置类无所不包，无所不管。

```text
   HTTP 请求
       │
       ▼
  CORS 过滤器
    ├─ 插在 JwtAuthenticationTokenFilter 之前 → 请求先做跨域检查
    └─ 插在 LogoutFilter 之前 → 退出逻辑跨域请求也能正确处理
       │
       ▼
  LogoutFilter                 退出：清掉 Redis 中的 login_tokens
       │
       ▼
  JwtAuthenticationTokenFilter  校验 token，并填充认证上下文
       │
       ▼
  permitAll 放行
    /login  /register  /captchaImage
    静态资源：*.html  *.css  *.js  /profile/**
    swagger-ui.html  swagger-resources/**  webjars/**
    Druid 连接池监控界面
       │
       ▼
  anyRequest().authenticated()
    其余所有资源，认证通过后才能访问
```

#### 方法级权限控制与认证管理器

当前配置类上面有一个注解叫 `@EnableGlobalMethodSecurity`，它的作用是**开启方法级别的权限控制**。比如 Controller 控制器当中每个方法上面我们都有一个叫 `@PreAuthorize` 的权限注解——打开 `OrderController` 看一下就知道，这些权限注解之所以能够生效，原因就是在配置类当中已经对它做了开启。

这个类继承了 `WebSecurityConfigurerAdapter`，实现外部应用的核心配置。下面注入了此配置类所依赖的对象：有用户认证逻辑的、认证失败逻辑的等等，这些我们稍后再介绍。

往下拉，第一个方法是把安全认证管理器交给了 IOC 容器。你看这边是不是有个 `@Bean` 的注解？所以项目在启动以后，就可以直接通过 IOC 来获取 `AuthenticationManager`，实现用户登录认证的操作。

#### 放行哪些 URL：@Anonymous 注解

最重要的方法在 `configure`，它实现配置 Web 应用程序的规则。

方法的前两行是用于配置 URL 访问权限规则的：通过依赖注入来获取 `PermitAllUrlProperties` 这个属性对象，而这个属性对象当中有一个叫 `getUrls()` 的方法，返回一个地址列表，然后进行遍历，将每一个 URL 添加到授权规则当中。而这个规则是**无需认证就可以进行访问的**，也就是支持匿名访问。

那这个地址有哪些呢？打开 `getUrls()` 这个方法，此方法直接返回了地址列表集合，而这个集合就是存储允许匿名访问 URL 模式的列表的。

这个列表是怎么获得的？顺着往下看，这个方法的主要作用呢是**检查我们 Controller 方法上面是否有 `Anonymous` 这个注解**：如果该方法上面有这个注解，我们就获取方法上的路径地址，存入到 URL 集合当中；同时呢我们再检查控制器类上面有没有 `Anonymous` 注解，如果有的话，同样的把类上的地址也存入到集合当中。

> **定义**：`@Anonymous` —— 支持匿名访问的标记。可以通过英文直译来获取它的含义。

举个例子，我们在 `OrderController` 类当中，比如说"修改订单管理"这个方法，如果用户没有登录也能进行修改的话，我们就把 `@PreAuthorize` 注解给注释掉，然后给它增加一个 `@Anonymous`，那么就表示该方法在未登录情况下，匿名用户也能进行访问了。

而这个注解呢可以放在方法上面，也可以放在类上面，从而影响当前订单管理的所有方法。

#### 认证失败与放行规则

再往下就是配置 Web 应用程序的具体规则了。

**第一部分是禁用 CSRF 的**，也就是我们所说的跨站请求伪造——因为项目当中我们不使用 session 会话这个功能，咱们把它关掉。还有禁用 HTTP 响应头的，这里我们关闭了 frameOptions 那几个响应头。

**第三个是认证失败的处理类**。那什么是认证失败呢？就是用户在登录时，用户名或密码输入错了，或者 token 被篡改了，那么它就会进入这个失败的处理类。

这个类具体做什么事呢，我们简单了解一下。找到它的注入位置，我们来看一下具体的方法实现。第一个方法就是来处理未通过身份验证的请求的。那么这个方法具体做什么呢？我们来看一下第一行的位置：

```java
response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
AjaxResult ajaxResult = AjaxResult.error(HttpStatus.UNAUTHORIZED,
        "认证失败，无法访问系统资源" + request.getRequestURI());
response.setContentType("application/json;charset=utf-8");
response.getWriter().print(JSON.toJSONString(ajaxResult));
```

我们设置了 HTTP 的状态码 401，也就表示未授权；然后来构建一个错误信息请求访问，通过 `request.getRequestUri()` 来获取这个资源地址，告诉它认证失败、无法访问系统资源。把状态码和消息准备好以后呢，我们以 JSON 的格式向客户端返回错误信息。此时呢客户端就根据状态码的判断，来给用户弹出错误消息，并跳转到登录页面。

**再往下第二个**，我们项目当中呢认证是支持 token 的，也就是我们的 JWT，告诉 Spring Security 底层使用 token 令牌，不再使用 session 的会话技术了。

**然后是一批放行的地址**。对于登录、注册还有验证码这三个后端的请求地址，我们是允许匿名访问的，所以这里呢配置了 `permitAll`。各位思考一下：在没有登录的情况下，我是允许注册的，允许访问登录请求，还要允许查看验证码的——这一点没毛病吧，这是后端控制器放行的三个接口。

还有前端的一些静态资源，这里也支持匿名访问：比如以 HTML 结尾的、CSS 结尾的、JS 结尾的，还有 `profile` 文件开头了——那么这些静态资源呢是都可以匿名访问的。还有 Swagger UI、Swagger resources 在线接口文档，在没有登录情况下我们也支持访问；还有 webjars 的 API docs，还有 Druid 连接池管理界面，这些呢在没有登录情况下我们也允许匿名访问。

**除了以上的过滤请求放行之外，剩下的所有资源全部需要经过认证以后，才能进行访问。**

#### 过滤器：LogoutFilter、Jwt 与 CORS

添加了 `LogoutFilter`，也就是我们退出功能的过滤器。那过滤器做什么事呢？找到这个对象，我们来看一下它的具体实现，往下拉，退出处理方法：首先呢它通过 `TokenService` 来获取当前的登录用户，然后判断这哥们儿是否已登录。如果这哥们儿处于登录状态的话，我们来获取用户名，然后删除用户的缓存记录，实现退出功能。

注意咱们在登录成功以后呢，会往 Redis 当中来存储 `login_tokens`，这是当前用户的登录信息。如果这个 Redis 信息被删除了，那么用户下次在访问时呢就处于未登录状态，所以就完成了退出的操作了。

退出以后呢，我们通过异步任务管理器来记录日志，而异步任务管理器呢我们在下一章节当中给同学们做详细的介绍。退出成功以后呢，我们会向客户端返回退出成功的消息，以 JSON 格式返回提示信息。

> **注意**：而这个提示信息我们并没有在后端代码去写死，而是把它设置到了 i18n 的配置文件当中。打开 admin 模块 resources 下面的 i18n 配置文件能看到，第 13 行的 `user.logout.success` 就是提示退出成功，前端会显示这四个字。抽取到 i18n 配置文件的好处是，我们可以根据不同国家和地区的语言，对这里面的提示信息进行文字的替换。

返回 JSON 提示信息以后呢，我们退出方法的逻辑就执行完毕了。核心点就在于**清空 Redis 当中的 token 数据**，Redis token 数据不存在的话，那么用户就处于未登录的状态。

还有一个 `JwtAuthenticationTokenFilter` 过滤器。它是在用户登录成功之后，再次访问时由客户端携带 token 令牌，来校验它的有效性与合法性。具体细节我们来看一下：先通过令牌服务来获取用户的登录信息，也就是说前端访问时，我们会通过 request 对象来获取携带的 token，通过解析 token 来获取登录用户对象 `LoginUser`。

然后判断一下这哥们儿是否已经登录——如果登录的话，此对象肯定不为空；还有第二个条件，Spring Security 的上下文对象当中是没有存入我们之前认证过的对象。那么它就会进入 `if` 判断体内：首先校验令牌的有效性，如果有效的话，我们创建认证对象，然后设置对象的详细信息，把它存入到 Spring Security 的上下文对象当中，就表示此用户认证通过了。那么我们的过滤器呢就会进行放行操作，当下次用户再访问时，Spring Security 的上下文当中已经存了认证对象了，所以就可以直接放行了。这就相当于我们之前的登录过滤器或者登录拦截器进行权限校验。

**最后是 CORS 过滤器**，两行代码。第一行代码，它是在 JWT 的过滤器之前进行处理的，他会首先进行跨域请求的检查，确保请求的合法性和安全性。第二行代码，我们将相同的 CORS 过滤器添加到 LogoutFilter 类之前，他表示在配置用户退出登录逻辑时呢，跨域请求也能得到正确的处理。因为目前我们的若依项目是基于前后端分离架构的，即使是跨域请求，我们也能保证 JWT 的校验和用户的退出这两个过滤器的功能实现。

### 密码编码器与登录认证入口

配置类里还有一个方法是用来创建 `BCryptPasswordEncoder` 对象的，它是 Spring Security 的密码加密工具类。我们在存储若依用户密码时呢，就会用到此工具类来实现加密操作；在做登录操作时，就会使用此工具类来实现密码的比较。

回数据库客户端验证一下，打开若依的 `sys_user` 用户表，往右拉，兄弟们来看用户的密码，就用到了我们刚刚所看到的这个工具类来进行加密的操作。

> **提示**：所以数据库里看到的密码一定是一串乱码，这是正常的。千万别觉得"数据库里居然不是明文，那是不是配错了"——明文存储密码才是事故。

最后一个方法，是来做用户认证接口的，大白话来说，此方法是用来实现用户登录的核心逻辑的。这里用到了 `UserDetailsService`，这是编写核心逻辑的代码，而右侧使用了我们刚刚介绍的密码处理工具类 `BCryptPasswordEncoder`。

那具体的 Service 实现呢？找到 `UserDetailsServiceImpl`，用户验证的处理逻辑我们先简单看一下：首先呢通过用户名来查询用户信息，然后呢校验用户名是否存在，如果不存在咱们记录日志抛出异常；如果存在的话，再判断此用户是否被逻辑删除，如果被逻辑删除的话我们再抛出异常；还要检查用户是否被停用、密码是否正确。如果这些校验都通过了，我们就创建并返回登录用户对象。

这个方法具体的实现逻辑，我们会在下一小节分析用户登录流程源码时，给大家做详细介绍。

以上就是 Spring Security 配置类的源码介绍。它是我们安全控制的指挥中心，从认证到授权，从会话管理到过滤器的设置，配置类无所不包、无所不管。这里呢是结合若依仅做了 Spring Security 核心配置的简单介绍，如果大家想系统性地掌握 Spring Security 的知识，我推荐大家观看黑马程序员提供的 Spring Security 专题课程。

### 本讲提到的题目

**题目**：把 Controller 模板中所有返回 `AjaxResult` 的地方改为 `R` 类型，让 Swagger 能展示返回结果的详细信息。

**为什么**：Swagger 解析返回类型时需要拿到具体的泛型结构才能展开字段，而 `AjaxResult` 默认继承了 `HashMap`，Swagger 对它是不兼容的，展开不了里面的数据。改成 `R` 之后，接口文档上就能看到完整的返回字段了。

**怎么做**：改造范围就是模板里需要返回结果的那几处——查询列表（树表分支）、按 id 查询、新增、修改、删除等方法的返回类型，逐个从 `AjaxResult` 换成 `R`，并把原来 `AjaxResult.success(...)` 的构造方式改成 `R.ok(...)` 这一类写法。改造完成后 `Ctrl+F9` 热部署，点预览就能在生成代码里看到效果。

## RBAC 权限控制：登录校验与角色权限下发
> 对应块：BLK30 | 覆盖分集：P104-P105 | 块标题（分集名）：《原理篇-15.RBAC权限控制-用户登录流程》

在之前的课程里，我们把 Spring Security 的配置类过了一遍。那份配置类写得挺漂亮，可它到底是在什么时刻被调用的？答案只有一个——用户点下"登录"按钮的那一刻。

这一讲我们就点到底。

### 一次登录，背后到底发生了什么

先把流程摆出来：管理员在登录界面输入用户名、密码以及验证码，点击登录按钮，就会向后台发送请求；后端则通过 Spring Security 的认证管理器进行登录校验。

功能分两层：

| 层次 | 位置 | 职责 |
| --- | --- | --- |
| 前端 | `views/login.vue` | 用户登录界面与交互逻辑 |
| 后端 | admin 模块的 `SysLoginController` | 接收前端请求、处理登录逻辑、返回 token 令牌 |

Controller 那层代码短得让人怀疑人生，真正的活儿全在 Service 里。我们从前端开始。

### 前端：点下登录按钮之后

打开 `login.vue`，按 `Ctrl + F` 搜"登录 按钮"（中间有个空格），第 52 行就是那个 `el-button`。点击它触发 `handleLogin` 方法。

#### 先做两件小事

`handleLogin` 第一步是**表单校验**：用户名、密码、验证码是否为空，各自的长度限制等等。校验一旦通过，就把 `loading` 这个响应式变量置为 `true`。

`loading` 一变 `true`，按钮就不可用了，界面上会显示"登录中"。默认状态显示"登录"，点击事件之后变"登录中"并且按钮置灰——就这么点。

接着往下拉，方法里还有第二个判断：有没有勾选"记住密码"。勾选了，就把用户名、密码以及记住密码这三个选项存进 cookie；没勾选，就把这三个从 cookie 里移除。记住密码这个功能在后台系统里用得比较多，大家了解一下就行。

真正干活的是下面这行。

#### 真正干活的是 userStore 里的 login

`useUserStore().login` 用到的是 Vue3 里的 Pinia 集中式状态管理对象，专门存放用户登录以后的信息。我们打开 `store/modules/user.js` 看一下这个方法。

登录之前，它先从登录表单对象里把四个值解出来：用户名、密码、验证码，以及验证码的标识 `uuid`。

> **提示**：`uuid` 是 Redis 存储正确验证码的 key。前端渲染验证码图片时，后端生成一个 uuid 存进 Redis、把 uuid 塞进图片的返回结果；用户提交时把 uuid 原样带回来，后端才能定位到"这张图对应的正确答案"。

拿到这四个参数之后，它创建了一个异步操作对象 `Promise`——成功执行第一个参数方法 `resolve`，失败执行第二个参数方法 `reject`。具体细节是：

1. 调用登录 API 请求方法 `login`，把这四个参数传过去，等待服务器返回结果；
2. 返回成功：把后端返回的 token（也就是令牌信息）存入 cookie，同时再把这个 token 存进 userStore 集中式状态管理对象；
3. 最后调用 `resolve` 结束这个 promise 异步操作。

第二步为什么要存两份？存 cookie 是因为前端可以据此判断登录态；存进 Pinia 是为了在其他界面灵活地拿到 token 信息。失败分支就简单了——传递错误信息给前端展示。

#### 请求层的两个开关

再看 `api/login.js` 里的 `login` 方法，它接收同样四个参数，新建一个 JSON 对象接收它们，通过 `request` 工具类向后端发请求，路径为 `/login`。

这里有两个细节值得单独拎出来：

- 请求头里把 `isToken` 设置为 `false`。因为我们做的是登录操作，前端的请求拦截器不需要帮我们拼接 token 令牌请求头；
- 同时标记了本次请求**不做重复提交拦截**，也就是用户在做登录时连续点击多次登录按钮，只有一次生效。这是前端拦截器帮我们做的事情。

最后指定请求方式为 `post`，参数就是刚才设置的 `data`。

打开 `utils/request.js` 的请求拦截器验证一下：我们刚刚把 `isToken` 设置为 `false`，所以前端在发送请求时并不会携带 token 令牌。这两点知道一下即可。

回到浏览器按 F12 验证：点登录按钮，第一个请求地址就是 `login`，请求方式为 post，请求体里携带了四个请求参数——验证码、密码、用户名以及 uuid。前端部分到此为止。

### 后端入口：SysLoginController 只做三件事

回到 IDEA 的 admin 模块，搜索定位到 `SysLoginController` 的登录方法。

这个方法通过 `loginBody` 对象获取请求体的参数，跟前端那四个一一对应：用户名、密码、验证码、uuid。没问题吧？

方法体就三步：

1. 初始化一个成功的 `AjaxResult` 对象，直接调用 `success` 表示成功；
2. 调用 Service 的登录认证；
3. 认证成功后会返回一个 token 令牌，把令牌放入 `AjaxResult`，最后返回这个对象。

Controller 代码比较简单，核心登录逻辑在 Service 里，我们往下钻。

### 第一关：验证码校验

因为校验细节比较多，这一步被单独抽成了一个方法。

**第一步，检查当前系统是否开启了验证码功能**，查的是若依的参数设置。系统管理里有一个"参数设置"，里面就有一个验证码开关，目前是打开的；这份信息在 Redis 里也有一份缓存数据，`true` 表示开启验证码校验功能。

它的兜底逻辑是这样的：如果获取的值为空或未设置，默认就使用验证码校验；如果不为空，就正常返回 `true` 或 `false`。很显然我们现在是开启的，返回值为 `true`。

**一旦为 `true`**，我们就通过 uuid 构建 Redis 缓存的键，然后从 Redis 中获取验证码。注意验证码**仅一次生效**，所以取到之后立即删除 Redis 中的验证码。

**然后是校验规则**：

- 如果 Redis 中的验证码没有取出来，表示验证码已经过期。这里使用异步工厂记录验证码失效的日志信息，同时抛出一个"验证码已经失效"的异常，由全局异常处理器统一捕获，给前端做出友情提示；
- 如果验证码没失效，就跟用户输入的验证码进行比对，**比对时不区分大小写**；
- 比对不一致，同样用异步工厂记录验证码不匹配的日志信息，并抛出异常给前端做友情提示。

### 第二关：登录前置校验

验证码过了之后，第二步会做一次登录前置校验，对前端传来的参数做格式校验。

> **提示**：这时肯定有人要问了——前端不是已经有正则表达式校验过了吗，为什么后端还要再校验一次？
>
> 还记得我们在实战篇提过的那句话吗：前端校验只防君子，不防小人。所以通常情况下，对一些敏感的数据，后端一定要进行二次校验。前端的正则写在浏览器里，改一下就能绕过去；只有后端的校验才是真正生效的那一道。

具体的校验有三组：

- **非空校验**：用户名和密码，如果这哥俩其中有一个为空，通过异步工厂记录错误日志，并抛出异常；
- **长度范围校验**：密码必须在 5~20 位之间，小于 5 位或大于 20 位同样记录日志并抛异常；用户名不能小于两位，也不能超过 20 位。代码里这两个范围是用常量定义的；
- **IP 黑名单校验**：用户名密码都没问题之后，还有一道 IP 黑名单校验。它通过参数配置获取我们之前设置过的 IP 黑名单列表——就在系统参数设置的最后一个，点修改可以看到，目前我们并没有参数的值，所以这个黑名单并不存在。如果你要设置的话注意，多个之间以分号分隔。

如果用户登录的 IP 落在黑名单之内，同样记录错误日志并抛出黑名单异常给前端做友情提示。

### 第三关：交给 Spring Security 做认证

前两步都过了，第三步才是重头戏：对用户进行验证。

具体做法是：把校验过的用户名、密码交给 Spring Security 管理，并放到认证的上下文对象中，然后交给认证管理器 `AuthenticationManager` 执行认证的登录校验。

校验的细节在 `UserDetailsService` 实现类的 `loadUserByUsername` 方法里。配置类中我们简单带兄弟们了解过，现在详细拆开看。

#### 用户查不出来的时候

方法一上来就根据用户名查数据库，调用 mapper 根据用户名查询 `sys_user` 系统用户表，最终把结果封装到实体类中。这种比较简单，我们快速过一下。

拿到 `user` 对象以后，第一件事是判断这哥们是否存在。不存在就记录不存在的日志信息，同时抛异常，友情提示前端"此用户不存在"。

> **提示**：这里的提示文案是"根据 code 的键来获取对应的值"给前端做出中文提示的——消息来自 i18n 配置文件。知道是哪个文件吗？把答案写到弹幕里。没错，就是 i18n 的配置文件，具体文件我们就不带兄弟们看了，对应的"用户不存在"这句话我已经提前把注释写好了。

如果用户存在，还要判断此用户**是否已经被逻辑删除**。逻辑删除字段长什么样？回到数据库客户端打开 `sys_user` 看字段列，有一个叫 `del_flag` 的删除标志：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `del_flag` | `0` | 存在 |
| `del_flag` | `2` | 已经删除 |
| `status` | `0` | 正常 |
| `status` | `1` | 停用 |

删状态值为 2，就表示此用户已被逻辑删除，记录日志并抛出"用户已经被删除"。

再往下，还要判断此用户是否**已经被停用**。打个比方：比如说波妞已经怀孕了，进入了待产期，那么他就会请 4~6 个月的长假；而在这个长假当中，我们就会把此用户的账号给它停用掉。停用的值就是 `status == 1`，代码里记录停用日志并抛出已停用的异常信息。

#### 密码比对与错误次数锁定

用户状态检查准确无误之后，就到了最重要的一步：验证用户名密码是否正确。

先通过认证的上下文对象获取用户的认证信息，里面就包含了用户输入的用户名以及密码。然后往下走，尝试从缓存当中获取**当前用户密码重置次数**。

这是个什么机制？还记得我们在基础篇介绍配置文件时讲过的吗？打开 `application.yml` 往上拉，用户配置当中有一个密码最大错误次数的限制，这里是 **5** 次。如果用户连续输入错误密码 5 次以后，就会给它进行锁定，默认的锁定时间为 **10 分钟**。

这段逻辑的细节就在我们正在看的代码里：

- 登录时会在 Redis 中记录当前用户的密码重试次数；
- 如果是第一次登录，说明缓存里没有重试次数，这里初始化为零——第一次登录嘛，你的重复次数肯定是零次；
- 判断重试次数有没有超过最大错误次数（从配置文件读取），以及锁定时间（默认 10 分钟，可以在配置文件中调整）；
- 如果 Redis 中的重复次数超过了最大的 5 次，抛异常，提示前端"你输入的次数已经超过五次了，那我接下来就要给你锁定 10 分钟了"。

如果没有超过最大错误次数，继续往下走：把用户输入的密码和数据库当中的密码进行比对。这个比对细节单独抽取了一个 `matches` 方法。

`matches` 使用 Spring Security 的 `BCryptPasswordEncoder` 工具类来实现密码校验——这哥们我们在上一小节的课程里介绍过。它的作用就是将用户输入的真实密码与数据库存出的密文进行比较，这里用到了哈希散列算法的处理。真实密码跟加密后的密文一致就返回 `true`，否则返回 `false`。

回到主业务线，根据密码校验的结果做判断：

- **密码错误**：把重置次数加一（原来是 0 次就变 1 次，原来是 3 次就变 4 次），再把重置次数更新到 Redis 中，并抛出密码不匹配的异常信息。此时用户需要在登录界面再输一轮用户名和密码，重新完成登录操作；
- **密码正确**：清理掉登录次数的缓存。

我们实际演示一下。先做一个退出功能，注意看验证码我输入正确，但密码故意输入错误的，点击登录按钮，提示"用户不存在或密码错误"。回到 Redis 客户端刷新，`pwd_err_cnt` 下面 admin 用户的重置次数是 1。更换验证码，输入正确的，同样的密码是错误的，再次点击登录提示错误信息，刷新 Redis 次数呢是 2。

一直到我们输错五次之后，就会达到最大的错误次数，就会锁定当前用户 10 分钟的时间，无法做二次登录。具体要锁定多久、最大次数是多少，可以根据你们自己的场景来设置。

再把密码最后一位改成正确的，重新获取验证码，点击登录——一旦登录成功，原来两次的登录记录就会被清理掉，刷新 Redis 就已经没有了。这里做了一个重置操作，兄弟们知道一下。

#### 装配 LoginUser：把角色和权限一起带出来

密码校验的主业务逻辑执行完毕，回到业务主线。`createLoginUser` 的调用者这里会**创建一个登录用户对象并返回给 Spring Security**。

这个 `LoginUser`（登录用户对象）里面包含什么呢？它 `new` 出来的时候带上了用户 id、此用户的 deptId、还有用户信息（也就是 `sys_user`），以及**此用户角色的权限信息**——而这个权限信息就是根据 RBAC 五表联查出来的。

具体实现我们看一下：

首先是初始化一个权限集合，注意这里用的是 **Set 集合**来存储此用户所有的权限数据。

> **提示**：为什么用 Set 而不用 List？
>
> 因为一个用户可以关联多个角色，而每个角色可能会有重复的权限数据，这部分重复的数据我们只要一个就可以了。

下面来看查询权限的具体细节。

首先判断登录用户是否为管理员。如果登录用户是管理员，就表示他拥有所有权限，设置一个权限字符为 `*:*:*`（星冒号星冒号星），它表示具有访问所有功能、所有的菜单权限。

如果不是管理员，就根据 RBAC 模型来查询该用户的角色信息。来复习一下，RBAC 是不是经典五表？有用户表、角色表、还有权限菜单表。用户和角色是多对多的关系，所以这里有一张中间表。我们可以根据用户的 id 查到他的角色列表——一个用户可能会查到多个角色，所以这里是一个角色的集合。

而角色跟权限是什么关系？**也是多对多**。我们可以根据每个角色的 id 查询中间表，来获取此角色所对应的权限菜单，这里也会包含多个，所以下方呢就有一个遍历角色的过程。

```text
      sys_user ──(sys_user_role)──▶ sys_role ──(sys_role_menu)──▶ sys_menu
        用户            用户角色中间表          角色        角色菜单中间表        菜单权限
         id                   user_id          role_id            role_id           menu_id
                                                 │
                          role_key = admin / common / account
                                                 │
                                                 ▼
                            LoginUser.permissions : Set<String>
                       admin 直接塞 "*:*:*"，其余遍历角色去重合并
```

图里这条路就是"根据已知的用户 id 来查询角色，再根据角色查询菜单集合"，然后把当前角色所对应的权限添加到这个集合当中。

注意这里可能两个角色会有相同的权限，所以这里我们就会有去重的业务场景——现在理解它为什么使用 Set 集合了吧。

`for` 循环内的实现细节是：调用菜单 service 根据角色 id 来做查询，将此角色的权限放入到角色对象当中，并添加到集合当中。

还有一个细节：如果该用户的对象当中，你没有查到角色，我们也可以根据用户的 id 来查询权限表。而这个逻辑其实跟上方是一样的——因为用户跟权限没有直接的关联，我们需要根据用户先查角色，再根据角色查询权限，实现多表联查。

这条联查的 SQL 长什么样？我们看 mapper 里的语句：查询菜单权限表，根据角色菜单的中间表，根据用户角色的中间表，再根据角色表，最终条件是用户的 id。先根据用户 id 来查询用户角色的中间表，获得角色的详细信息；再根据角色表来查询角色菜单的中间表，获取菜单的 id；最终查询此用户角色所对应的菜单列表。

这里对应的也是刚介绍的 RBAC 五表模型。

> **提示**：有小伙伴可能觉得，这一步的操作是不是有点多余？我们根据用户对象获取角色的集合进行遍历，不一样能查到吗？
>
> 但有可能用户在做登录时，查询用户对象并没有包含角色集合。此时我们就可以根据用户 id 先查角色，然后再来查菜单权限的数据即可。

最终返回此用户所有的权限集合，封装到登录用户对象当中，然后再把这个登录用户对象存入到 Spring Security 安全框架。

此方法就是 Spring Security 做认证处理的核心逻辑代码：当前用户登录成功，我们就会把登录用户对象存入到 Spring Security 的上下文当中；如果登录失败，它就会抛出异常。

### 登录成功之后：清理、留痕、发 Token

回到 Service 的登录主逻辑。

一旦登录失败就会抛出异常，而这个异常我们有细分的处理：如果你抛出的是认证失败的异常，此时会给客户端抛出"用户名或密码不匹配"的异常信息，从异常类当中获取异常的信息返回给前端。

注意再往下看，这里还有个 `finally` 的代码：**此用户无论是登录成功还是登录失败，都需要清理上下文当中的用户名和密码**。我们在登录之前是不是把用户名密码存进了上下文？那登录完之后，上下文对象就应该把它清理掉。

接下来的代码都是登录成功之后的逻辑，一共三步。

#### 记录日志 + 拿到登录用户

第一步通过异步工厂记录登录成功的日志信息。第二步通过 Spring Security 获取登录用户的信息 `LoginUser`，这里面包含了用户信息、角色信息以及该用户的权限信息。

#### 更新登录信息

第三步更新用户的登录信息。点开看具体实现：创建一个 `SysUser` 对象（也就是系统用户表所对应的实体类），设置用户 id、登录 IP、还有登录时间，以 id 为条件更新这张表的两个字段。

回到数据库客户端，在 `sys_user` 当中有一列 `login_ip` 和一列 `login_date`。用户每次登录时，我们都会记住他的最后登录 IP 以及最后登录时间，做一个留痕记录，防止恶意操作。

#### 生成 Token

最后一步就是生成 token，细节值得展开。

首先他用了一个 id 工具类生成了一个 UUID 作为用户的 token 令牌，然后把这个令牌存入到登录用户对象当中。

再设置此用户的**代理信息**。代理信息是什么呢？咱们来看一下：

- 获取请求头当中的 User-Agent；
- 获取用户的客户端 IP，把 IP 设置到登录对象当中；
- 再通过 IP 来获取真实的登录地点——通常情况下每一个 IP 都会对应一个真实的物理地址，我们使用 `AddressUtils` 工具类来解析 IP，设置此 IP 所对应的区域地址；
- 设置客户端的浏览器信息，以及操作系统信息。

这些都是用户在发送请求时浏览器告诉服务器的客户端信息，我们都会存入到登录的用户对象当中。

**这一步很重要：刷新 Redis 中的用户令牌。** 也就是说，Redis 会模拟 session 来记录用户的登录状态。如果 Redis 存在这个用户状态，就表示用户已经登录成功了；但如果 Redis 没有这个登录状态，抱歉，此用户就是未登录的，我们需要重新走一遍认证登录流程。

```text
   IdUtil.fastUUID() ──▶ 登录用户的 token（同时存进 LoginUser）
                              │
     代理信息：UserAgent / 客户端IP ──▶ AddressUtils 解析区域
               浏览器 / 操作系统
                              │
                 更新时间 + 重算有效期（配置文件，默认 30 分钟）
                              │
                              ▼
        Redis：login_tokens : {token}  ──▶ LoginUser 的 JSON
                 ├ browser       谷歌 12
                 ├ deptId        103
                 ├ expireTime    毫秒时间戳
                 ├ ipaddr        内网 127.x
                 ├ loginLocation IP 归属区域
                 ├ loginTime     登录时间
                 ├ os            Windows 版本
                 └ roles / permissions
                              │
                              ▼
        JwtUtils.createToken(map, secret)  ──▶ 加密 JWT
                              │
                     AjaxResult{token} ──▶ 前端 Cookie
```

这里会更新一下登录的时间，然后重新计算令牌的有效时间。而这个令牌的有效时间也是读取配置文件的，默认时间是 **30 分钟**，我们可以结合业务场景来修改。

再往下，会生成 Redis 的缓存键，这个键是通过 token 来指定的，保证每个用户之间不会冲突，然后重新把它写入到 Redis。也就表示用户在登录成功以后，Redis 就会存储 `login_tokens`，里面保存用户的登录信息——左边是固定值，右边就是我们 UUID 生成的 token。我们点击进去以后就可以查看此用户的 `LoginUser` 对象转换后的 JSON 格式：比如浏览器是谷歌 12、deptId 是 103、过期时间是一个毫秒值、IP 地址、IP 所对应的区域地址（`127` 很明显是内网的 IP）、登录时间、Windows 系统版本，以及该用户的权限信息等等，记录得非常详细。

存进 Redis 之后，回到方法调用者：它会创建一个 map 集合，把令牌信息存入到这个 map 集合当中，使用 `createToken` 方法来创建出令牌。而这个 `createToken` 底层用到了 **JWT 的工具类**，结合我们的 `secret` 密钥生成了加密后的 token 信息。

> **注意**：这个密钥在配置文件 `application.yml` 当中已经指定了。这个密钥信息千万不要泄露。往下拉能看到令牌的有效时间，为了方便调试，我已经把它改为了 300 分钟。

把加密后的 JWT token 返回给 Service，Service 再返回给 Controller，Controller 把令牌存入 `AjaxResult` 返回给客户端。一旦客户端拿到 token 对象，就会把它存入 cookie 当中。

### 回到前端：Token 入 Cookie 与路由重定向

回到 VS Code 打开 `user.js`，第 30 行的代码就是将登录返回的 token 设置到 cookie 当中。所以在客户端浏览器登录成功以后，我们按 F12，点击 Application，在 cookie 当中就可以查看令牌数据了。

还有一个细节：前端在登录成功以后，会从登录页面重定向到首页，所以这里还有一个**路由重定向操作**。

回到 `login.vue` 的登录方法，看 `router.push` 这一行——这是编程式路由的跳转，跳转到我们系统指定的首页。注意如果有参数的话，跳转时也需要携带路由参数。

什么意思呢？回浏览器看一下：我们先退出登录，注意看地址栏上方问号的后方是不是有一个 `redirect=/index`，这就是我们地址传递的参数。

那么我们就会通过 `route.query` 来获取当前路由的参数。只不过这个路由参数如果包含 `redirect`，我们认为它就是一个重定向地址，而不是普通参数，所以这部分需要过滤。如果是普通参数的话，在 `router.push` 跳转首页时，我们同时携带 query 参数信息。

很明显，当前路由当中是没有包含参数的，所以他默认只跳转到主页面了，对应就是系统的首页信息。

### 登录流程全景回顾

我们回到 PPT 来做个小结，把整个流程串起来看：

```text
浏览器                                      后端 admin 模块
─────────────────────────────────────────────────────────────────────────────
输入 username / password / code / uuid
  ↓  POST /login
  ① validateCaptcha()   验证码开关 → uuid 查 Redis
                        取到即删 → 比对（忽略大小写）
                        取不到 / 不一致 → 记日志 + 抛异常
  ② validate()          非空 / 密码 5~20 / 用户名 2~20
                        IP 黑名单（参数设置，分号分隔）
  ③ AuthenticationManager
       → loadUserByUsername()  查 sys_user
            不存在 / del_flag=2 / status=1 → 抛异常
            Redis pwd_err_cnt 计数 > 5 → 锁定 10 分钟
            matches() BCrypt 比对
              错 → 次数 +1 写回 Redis，抛异常
              对 → 清掉计数缓存
       → createLoginUser()
            admin → permissions = { *:*:* }
            否则 → 五表联查 用户→角色→菜单，Set 去重
  ④ finally 清理上下文中的用户名与密码
  ⑤ 记录成功日志 → 更新 login_ip / login_date
  ⑥ IdUtil 生成 UUID 作 token
        Redis：login_tokens:{uuid}（有效期默认 30 分钟）
        JwtUtils + secret → 加密 JWT
  ← AjaxResult { token }
  存入 cookie + 存入 Pinia
  router.push('/') 携带 redirect 之外的 query 参数
```

说人话：**先验验证码，再验参数格式，最后才让 Spring Security 去比对密码**。三关全过，记录日志、更新登录 IP 和时间、生成 JWT，同时把登录用户信息写进 Redis；token 返回给前端，存进 cookie，再跳首页。

下一小节我们探讨获取用户角色权限的源码分析。

### 前端：路由守卫在跳转前先问一遍身份

实现此功能的前端代码位于 `src/permission.js` 里面。它在登录成功以后，**跳转到新的路由之前**，会查询当前用户的角色和权限信息。

这个过程就像在告诉系统：稍等，我们先确认你是谁、你有哪些权限。这样的话，我们的前端就可以实现动态按钮的权限控制了。

后端的处理逻辑同样在 admin 模块的 `SysLoginController` 当中，他负责接收前端发来的请求、处理查询逻辑，并返回用户角色和权限信息。这就类似于：你好，这是你的角色和权限，请根据这些信息进行操作。

打开 VS Code，在 `src` 目录下注意看有一个全局的 `permission.js` 文件。当前文件的代码当中有一个**路由守卫**，它在路由跳转之前呢，会进行一些权限验证和状态的设置。

我们关注的代码往下拉：第 38 行的位置，这个对象熟悉吗？各位是不是 Pinia 的用户状态管理对象？这里呢会调用一个方法叫 `getInfo`，我们会向后台发送请求，查询用户的信息。

`getInfo` 实现在 store 目录下 `modules/user.js` 中——就是我们之前分析过登录方法的那个文件。`getInfo` 就是来获取用户信息：它创建一个 promise，然后调用 `getInfo` 的 API 方法向后台发送请求。

这个 API 定义在 api 目录下方同样叫 `login.js` 的文件里，第 35 行定义了一个 `getInfo` 方法，通过 request 工具类发送了一个 get 请求，而且路径为 `/getInfo`。

回浏览器验证一下：打开 F12 刷新浏览器，注意看第一个请求路径就叫 `getInfo`，点开来看请求方式呢为 GET。

### 后端：getInfo 返回用户、角色、权限三件套

回到 IDEA，Shift + Shift 搜索一下 `getInfo`——同学们看这么多同名方法，我们应该看哪个呢？注意我们前端发送的是一个 GET 请求，请求地址呢叫 `getInfo`，所以最后一个是符合我们条件的。

这个方法做三件事：

#### 先把当前用户捞出来

第一行，通过 Security 工具类来获取当前登录对象的用户信息，拿到 `SysUser`。为什么现在能拿到？因为用户在登录成功时，已经把此对象存入到了 Spring Security 的认证管理器当中，所以这里可以随时获取。

#### 查角色权限集合

接下来我们看第二行代码，调用了 permission 的 service 来查询当前用户的角色集合，也就是以用户为条件查询该用户的角色集合。

具体实现的第一步：初始化一个**字符串集合**（同样是 Set 集合），用于存储角色的字符串。

> **提示**：这里为什么用 Set 而不用 List 集合？这个在做登录流程时已经给小伙伴分析过了——因为一个用户可以关联多个角色，那么难免这些角色的权限字符串可能是相同的，而 Set 集合可以做到去重的处理。

第二行呢主要逻辑是判断一下当前登录的用户是否为超级管理员这个角色。如果是的话，添加角色字符串为 `admin`，表示他拥有所有的权限。如果不是超级管理员的话，注意看这里，我们会根据用户的 id 查询当前用户的角色权限，然后把它添加到集合当中。

这个方法的实现我们按住 Ctrl 找到接口的 Service 实现方法：首先会根据用户 id 查询当前用户所有角色权限集合对象，这里调用的是 roleMapper。咱们来看一下 SQL 语句——找到 mapper 的方法签名，找到对应的 XML。

当前的 XML 条件是 `user_id`，通过 `<include>` 引入了我们公共的 SQL 语句。在这条语句当中，注意看它查询了当前角色的字段信息，通过 `distinct` 这个关键字实现了去重操作。

查询的有角色表、用户角色的中间表、用户表以及部门表。其中部门表呢是涉及到数据权限控制的，这部分知识我们稍后给兄弟们介绍。

我们主要关注的是：根据用户表来查询用户角色的中间表，通过用户角色的中间表拿到角色表的详细信息。也就是说已知条件是用户 id，通过中间表查到当前用户的主要角色 id，再根据角色 id 查询这些角色的详细信息。一个用户可以拥有多个角色，所以我们的返回值呢是一个角色的集合。

OK，SQL 语句并不难，咱们就分析完了。

#### 角色权限字符串到底是什么

回到 service 方法，mapper 执行完毕以后，我们就拿到了当前用户的角色对象了。但是我们只是想获取该角色所对应的权限字符串。

那什么是权限字符串呢？我们回到数据库客户端工具，打开角色表：注意看，左侧的 `role_name` 是角色的名称，而右侧的 `role_key` 就是我们的角色权限字符串。

| `role_name`（角色名称） | `role_key`（权限字符串） |
| --- | --- |
| 超级管理员 | `admin` |
| 普通角色 | `common` |
| 财务人员 | `account` |

我们最终需要返回的是每个角色的权限字符串，所以我们需要遍历角色，一个个给它获取并添加到新的集合当中：定义一个新的 Set 集合，然后遍历角色对象，对当前角色的权限字符串进行非空判断，如果不为空的话，就把它添加到集合当中。

这里有个细节要说明一下：他拿到这个角色字符串以后呢，会进行一个 `split` 切割。

这是什么意思呢？来说明一下——一个角色呢可能会涉及多个权限字符串，多个之间怎么定义呢？比如说 `role1,role2`。那现在呢我们通过 `split` 按中间逗号的分隔呢，就可以拿到此角色有两个权限字符串，把它转换成数组，然后再通过 Arrays 的工具类把它再转换成集合，把它添加到我们刚刚定义的角色权限的集合当中。

但一般情况下，一个角色只有一个权限字符串，所以这个转换过程呢你们知道一下即可。经过多个集合的编译之后呢，最终能返回几个 Set 集合，那么我们的 permission service 当中就拿到了非管理员用户的角色集合了，最终把它返回给 control 层。

#### 查权限集合

接下来是第三步，根据当前用户来查询权限集合。其实这一步呢，我们在之前做登录流程时已经分析过了，咱们简单地来看一下这段代码。

同样的，初始化权限集合，判断一下当前用户是否为管理员，如果是的话设置 `*:*:*` 的权限标识，拥有所有的权限。如果不是管理员的话，获取当前用户的角色，然后遍历角色集合，根据角色 id 来查询权限列表，再把它设置到角色对象当中，以及把这些权限合并到总的权限集合当中。

如果当前用户没有角色集合也没关系，我们也可以根据用户的 id 进行查询，将结果添加到总的集合当中。最终呢返回所有的权限数据。这些代码我们都比较熟悉了。

OK，最终呢 Controller 就拿到了当前用户的信息、当前用户的角色集合以及当前用户的权限集合。然后创建一个成功的 `AjaxResult`，把这三个信息给它添加到对象当中，最终返回此对象。那么前端就可以拿到用户信息、角色信息以及权限列表了。

#### 前端存下来

回到 VS Code 打开 `user.js`，这个返回结果就是我们刚刚一起分析的用户信息、角色信息和权限信息。

首先我们先取出用户信息，然后拼接出用户的头像——因为在用户表当中我们是存储了头像的地址。然后再判断下返回的结果当中有没有角色集合，我们来保存当前用户的角色集合以及权限集合，把这些呢我们都封装到用户的状态对象了，所以其他的视图组件都可以获取这些权限信息。

如果没有返回角色的话，这里呢我们设置了一个默认角色，同时呢给装载对象保存了用户的 id、用户名称以及用户头像。这个异步请求就处理结束了。

### 按钮级权限：两条指令搞定

到这里又有人会提出新问题了：**后端已经返回了权限数据了，那么前端怎么做到按钮的动态权限控制呢？**

若依封装了指令的权限，能够快速实现按钮级别的权限判断。

```text
      <el-button v-hasPermi="['system:user:add']">添加</el-button>
                             │
                    按钮挂载 → mounted 触发
                             ▼
        1. 取指令属性 → ['system:user:add'] → permissionFlag
        2. all_permission = "*:*:*"
        3. 从 Pinia 取 permissions（后端刚返回的那份）
                             │
                             ▼
        permissions.some(p => all_permission === "*:*:*"
                             || p === 遍历中的 permission)
                  ┌──────────┴──────────┐
                true                 false
                  │                    │
           保留，渲染按钮        parentNode.removeChild(el)
                                  按钮从 DOM 移除 → 页面看不到
```

图里这个指令叫 `v-hasPermi`，每个按钮都有这个指定属性。看这个示例：当前按钮呢我们设置了一个权限叫 `system:user:add`，那么也就表示当前登录用户呢拥有此权限，此按钮呢才能进行显示。

当然了，我们也可以给一个按钮设置多个权限。看第二个示例，一个添加、一个编辑的权限，他表示当前登录用户只要包含任意一个权限，我们页面呢就可以显示此按钮。

那这个指令的底层是如何进行判断的呢？在 `directive/permission` 的目录下有个 `hasPermi.js` 文件，它就是来处理这段逻辑的，咱们来分析一下。

先往上拉看这一行，它是来获取当前用户的状态对象的，而这个对象是不是已经包含了用户的基本信息、角色集合、还有权限列表？此按钮呢在进行页面挂载时呢，就会触发此方法。

这个方法做什么事呢？咱们来看：

- **第一步**，将指令当中的属性给它取出来，拿到这个权限的数组。也就是说我们取出这个属性的值有可能是一个，也可能是多个，整体来说它就是一个数组，是不是已经被中括号所包裹了；
- 同时我们还定义了一个所有权限字符串，三个星号表示超级管理员；
- 然后从用户的状态管理器当中来获取当前用户的权限集合——这是不是我们后端刚刚返回的这个权限集合；
- 接下来做判断：如果页面指令当中的数组不为空，就把它取出来叫做 `permissionFlag`；
- 然后判断当前用户是否拥有此指令的权限，有的话返回 `true`，否则返回 `false`。

在这一步当中，`permissions` 就是后端我们查询的结果，通过 `some` 来进行筛选：

- 左侧这一段代码兄弟们不难理解，`all_permission` 是不是三个星？如果你登录的是超级管理员的话，那么就跟这三个星咱们对应上了，此时呢就会返回 `true`；
- 如果你登录的是普通用户的话，看这一段，我们这个权限数组如果包含遍历当中的这个 `permission`，就证明当前用户呢是拥有此权限的，此时呢也能返回 `true`；否则的话就会返回 `false`。

拿到这个布尔值的返回结果以后呢，下面这一步就比较容易理解了：如果当前用户没有相应的权限，我们就在 DOM 当中呢移除该元素。那么在页面渲染时呢，此按钮就会被移除，所以页面呢我们就看不到了，从而实现了前端的权限控制。

### v-hasRole：判断角色的那一条

除了权限控制之外，小伙伴们可能又引出一个新疑问：我们还返回了角色集合，那它有什么用呢？

其实在若依当中呢，还支持一个角色的权限指令，叫 `v-hasRole`，它也能控制按钮的显示隐藏。

看示例：这里我们写了一个 `v-hasRole="admin"`，而这个角色的权限字符串呢为 `admin`，那么也就表示此按钮呢只有超级管理员登录以后呢，他才能看到——这是单个角色的设置。同时呢我们也支持多个角色权限的设置：如果当前登录用户，他的角色权限呢包含以下任意一个，我们的按钮呢就可以在页面进行显示了。

那么此代码的实现细节呢，我们来带兄弟们分析一下。位置同样在 `directive/permission` 目录下的 `hasRole.js` 文件当中。这段逻辑呢，跟刚才的权限是非常类似的，咱们快速过一下：

- 首先获取当前用户的状态对象，按钮在页面进行挂载时呢，执行此方法；
- 获取当前指令的角色数组，单个的也有可能是多个的；
- 定义超级管理员角色标识为 `admin`；
- 通过用户状态管理器取出当前用户的角色数组；
- 判断当前按钮的指定数组是否为空，如果不为空，给它抽取出来叫做 `roleFlag`；
- 接下来判断当前用户是否拥有此角色的标识，拥有返回 `true`，否则返回 `false`；
- 如果返回是 `false`，那么在页面当中呢，我们就给它移除该元素，所以当前页面呢就看不到此按钮了。

这个逻辑处理呢跟权限都是完全一样的。

在页面的最终效果，大家可以看到：黑马彭于晏用户登录以后只能做区域的查询功能，新增、修改、删除按钮是不是统统的都隐藏掉了。

### 获取角色权限的全景回顾

最后再回到 PPT 来做个小结。

```text
登录成功 ─▶ 路由守卫（跳转新路由之前）
                  │  GET /getInfo
                  ▼
        ┌─────────────────────────────────────────┐
        │ ① SecurityUtils 取当前登录用户 → SysUser │
        ├─────────────────────────────────────────┤
        │ ② 查角色权限列表                          │
        │     是管理员？ ─是─▶ {"admin"}            │
        │        否                               │
        │     user_id → 用户角色中间表 → 角色表     │
        │     role_key: admin / common / account   │
        │     split(",") → Arrays → Set（去重）     │
        ├─────────────────────────────────────────┤
        │ ③ 查权限列表                              │
        │     是管理员？ ─是─▶ {"*:*:*"}            │
        │        否                               │
        │     取角色 id → 遍历查菜单权限 → 合并      │
        │     无角色？ ─▶ 直接按 user_id 联查        │
        └─────────────────────────────────────────┘
                  ▼
        AjaxResult { user, roles, permissions }
                  ▼
            前端存入 Pinia 用户状态对象
                  ▼
        每个按钮的 v-hasPermi / v-hasRole 读它
        命中 → 渲染；没命中 → DOM 删除 → 隐藏
```

三步走：**先用 Security 工具类拿到当前登录用户信息**；**第二步查角色权限列表**，执行时先判断当前用户是否为管理员，是的话直接返回关键字 `admin`，不是的话根据用户 id 查询角色的权限列表；**第三步根据用户 id 查询权限列表**，先判断是否为超级管理员，是的话返回 `*:*:*` 表示拥有所有的菜单权限，不是的话取出当前的用户角色 id，来查询每个角色的权限列表。

三步执行完，就能拿到用户信息、角色列表和权限列表了，把这三个封装到 `AjaxResult` 当中返回到前端，此时前端就会把它存入到用户的状态管理对象当中。

那么我们的前端在加载各个页面时呢，每个按钮当中都有对应的 `v-hasPermi` 或者说 `v-hasRole` 这两个指令。我们通过前端的这些代码来判断当前登录用户是否拥有此按钮的角色或权限：有的话按钮就在页面进行渲染展示，没有的话就给它进行 DOM 的删除，页面就会隐藏此按钮，从而做到了前端的 RBAC 的权限控制。

## RBAC 权限控制的三层落地:动态菜单、接口鉴权与异步任务
> 对应块：BLK31 | 覆盖分集：P106-P108 | 块标题（分集名）：《原理篇-17.RBAC权限控制-获取动态菜单路由》

### 同一个系统,菜单为什么不一样

上一小节我们建了个用户,叫黑马彭于晏,还顺手给他分配了角色和权限。这哥们儿一登录若依,看到的侧边菜单就跟别人不一样——他目前只分到了点位管理这一块。而超级管理员登录,能看见所有菜单。

菜单为什么会长成这样?这不是前端写死的,是后端根据他的角色现查出来、现拼树、再翻译成前端路由格式发过去的。今天咱们就把这条链路从前端一路挖到 SQL。

先把整条流程摆出来,后面每一步都对得上这张图:

```text
登录成功
   │
   ▼
src/permission.js ─────► PermissionStore.generateRoutes()
   (跳首页前生成可访问路由)          │
                                    ▼
                         api/menu.js 里的 getRouters()
                         GET /getRouters
                                    │
                                    ▼
                    SysLoginController.getRouters()
                                    │
                    ① SecurityUtils.getUserId()
                    ② selectMenuTreeByUserId(userId)
                                    │
                                    ▼
                          SysMenuServiceImpl
                    isAdmin ? 查全部菜单 : 五表联查
                                    │
                                    ▼
                   buildMenus(平铺列表) ──► 菜单树
                                    │
                                    ▼
                   buildMenus(菜单树) ───► 路由列表
                                    │
                                    ▼
                        JSON ──► 前端 permission store
                                    │
                                    ▼
                    Layout 布局 ─► Sidebar 渲染侧边栏
                                    │
                        点击菜单 ─► 主体区域渲染视图组件
```

#### 前端只做一件事:把动态路由塞进状态

前端的入口在 `src/permission.js`。第 42 行这块注释写着"需要生成可访问的路由表",它调用的是权限路由的状态管理对象 `PermissionStore` 里的 `generateRoutes()`——名字很直白,就是"生成路由列表"。

这个状态对象在 `store/models/permission.js`,往下拉到第 44 行就是 `generateRoutes` 的实现。第一步它先 `new Promise` 一个对象,因为整个过程是异步的;然后调用一个 API 方法 `getRouters`。

注意这个 `getRouters` 已经不在 `login.js` 里了,我们在 `api/menu.js` 找。这个文件当前只有一个方法,专门用来拿动态路由:

```js
// api/menu.js
export function getRouters() {
  return request({
    url: '/getRouters',
    method: 'get'
  })
}
```

不信就打开浏览器 F12 验证一下:刷新页面,Network 里除了我们上小节分析过的 `getInfo`,紧跟着就是 `getRouters`,点开 Headers,请求方式 GET,请求地址 `/getRters`——路径一模一样。这条链路就接上了:前端在跳新路由之前,主动去后端查询"当前用户有权访问的动态菜单路由列表"。

#### 后端 Controller 的两步走

后端处理逻辑在 admin 模块的 `SysLoginController` 里,职责就两句话:接收前端请求,然后构建出完整的菜单树结构,把符合条件的路由返回给前端。

方法体本身极简:

```java
@GetMapping("/getRouters")
public AjaxResult getRouters()
{
    // ① 拿到当前登录用户的 id
    Long userId = SecurityUtils.getUserId();
    // ② 按用户 id 查他所有能访问的菜单,以树状结构返回
    List<SysMenu> menus = menuService.selectMenuTreeByUserId(userId);
    return AjaxResult.success(menus);
}
```

它把 `userId` 交给 `selectMenuTreeByUserId`,拿回来的是一个 `List`,而且**这个 List 是有树状结构的**。真正的活儿全在这个方法里,咱们 Ctrl+Shift+N 搜过去看实现。

### 菜单是怎么查出来的:admin 与普通用户两条路

方法第一步先 `new ArrayList` 作为菜单容器。第二步是一个岔路口:**判断当前登录用户是不是 admin**。

> **定义**:菜单表里的 `menu_type` 字段有三个取值——`M` 是目录菜单,`C` 是组件菜单,`F` 是按钮。
>
> 我自己习惯把目录菜单叫**一级菜单**,把组件菜单叫**二级菜单**。

为什么只要 M 和 C?回到浏览器看一眼:工单管理、点位管理、设备管理这些是左侧栏里的一级目录,每个目录下挂着若干二级组件;再往下的三级按钮,在左侧栏根本不显示。所以这一档直接过滤掉。

#### 超级管理员:菜单表单表查询

admin 走的是 `selectMenuTreeAll`,对应 XML 里的一条单表查询:

```sql
SELECT m.*
FROM sys_menu m
WHERE m.menu_type IN ('M', 'C')
  AND m.status = '0'
ORDER BY m.parent_id, m.order_num
```

就查一张 `sys_menu` 表,条件只有菜单类型和菜单状态。粘到数据库客户端跑一下,结果就是我们的目录菜单和组件菜单,最右边那列 M/C 一目了然。而且它还做了排序:`parent_id` 为 0 的一级目录排在前面,二级组件排在其后——用户管理、角色管理、菜单管理、管理部门都挂在系统管理底下,这不就是标准的树表结构吗。

> **易错点**:`status` 是 `0` 启用、`1` 禁用。别把这两个值记反了。

#### 普通用户:RBAC 五表联查

不是 admin 就换一条路:按用户 id 查他能访问的菜单,这就得动用 RBAC 的多表联查了。

```text
        sys_menu  (菜单表)
             │
        sys_role_menu  (菜单↔角色 中间表)
             │
          sys_role  (角色表)
             │
        sys_user_role  (角色↔用户 中间表)
             │
         sys_user  (用户表)
```

菜单表、角色表、用户表,外加两张中间表,五张表串起来——这不就是标准的 RBAC 吗。查询条件也齐:

- 当前登录用户的 id;
- `menu_type` 为目录菜单和组件菜单;
- 菜单状态、角色状态均为启用;
- 最后按 `parent_id` 和 `order_num` 升序。

还是粘到数据库客户端验证。这次把用户 id 换成了黑马彭于晏的 **100**(在用户表里翻到的)。执行结果只有两条:一个是目录菜单**点位管理**,一个是组件菜单**区域管理**——正好是我们当时分配的权限。再看区域管理的 `parent_id`,是 2000,而 2000 正是点位管理;点位管理自己挂在主类目下,`parent_id` 为 0。

所以这一条父子关联,就是后面构树和路由翻译的全部依据。大家记住,咱们截张图,稍后有用。

### 从一张平铺列表到一棵菜单树

现在是重点。咱们查出来的 List,是**所有数据的平铺集合,彼此之间没有父子关系**。可前端页面明明是层层嵌套的,左边展开工单管理下面还挂着东西。这中间差的那一步,就是构树。

先看这个树长什么样:

```text
主类目 (parent_id = 0)
├── 工单管理   (parent_id = 0)
│   └── ...
├── 点位管理   (menu_id = 2000, parent_id = 0)
│   ├── 区域     (parent_id = 2000)
│   ├── 点位     (parent_id = 2000)
│   └── 合作商   (parent_id = 2000)
└── 设备管理   (parent_id = 0)
```

注意 `parent_id` 为 0 的含义:0 就是创建菜单时指定的**主类目**,是整棵树的根。工单管理、点位管理、设备管理都是主类目下的一级节点;点位管理往下有三个二级节点,它们那三条记录的 `parent_id` 都等于点位管理的 id(2000),所以就能挂到点位管理身上。

**说白了,一条记录靠两个字段就能归位:自己的 `menu_id`,和自己的 `parent_id`。** 剩下的就是纯代码活了。

`buildMenus` 这个方法干的事,拆开看就是"先建一级,再建二级,以此类推":

1. 初始化一个"子菜单列表",也叫权限列表,拿它当返回容器;
2. 传进来的 `parentId` 是 0,也就是主类目,所以这个容器最终装的是一级目录菜单;
3. 遍历刚才查出来的整个菜单集合,逐条判断:当前这条 T 的 `parent_id` 是不是等于传进来的那个"父 id"?相等就收进来;
4. **在收进来之前还有一步**,调 `buildMenuChildList(menus, t)`,去整个集合里找当前节点的所有子节点挂上去。

第 4 步传的两个参数很重要:整个数据库返回的菜单集合(当全量数据池子用),以及当前这个节点 T(点位管理)。它是个**递归查找**机制。

```java
private List<SysMenu> buildMenuChildList(List<SysMenu> menus, SysMenu t)
{
    List<SysMenu> childList = new ArrayList<>();
    for (SysMenu menu : menus)
    {
        // 这条记录的 parent_id 等于当前节点 id,就证明它归当前节点管
        if (StringUtils.equals(t.getMenuId(), menu.getParentId()))
        {
            childList.add(menu);
        }
    }
    return childList;
}
```

逻辑朴素到有点不像样:把整个集合再遍历一遍,`parent_id` 等于当前节点 id 的就全收走。区域、点位、合作商三条记录就这么被捞了出来。

拿到这三个子节点后回到上一层,第二步把集合塞进点位管理对象里的 `children` 属性;然后对这三个子节点**再来一遍遍历**,看它们各自有没有孩子,有的话继续递归往下找。目前若依菜单只分两级,所以这个递归走到区域、点位、合作商这里就自然结束了。

> **结论**:菜单树要这么写,是为了留扩展性。万一将来加到三级、四级,递归可以原封不动地往下钻;写死两层的话,改了就得重写。处理树形结构,递归是常规解法。

回到主方法:for 循环跑完,菜单树就构建完毕了,`return` 出去的是**工单、点位、设备等等这些一级子菜单**。这个 menus 回到 Controller 手上时,已经是完整的树形结构了。

### 菜单树怎么翻译成前端路由

菜单树还只是"菜单",前端要的是"路由"。这是两套不同的数据格式,还得再翻译一次。

先看看前端到底要什么。F12 里把 `/getRouters` 的 Response 复制出来,丢进 JSON 美化工具,data 返回的结果就是前端要的路结构:

```json
{
  "path": "/order",
  "component": "Layout",
  "children": [
    { "path": "order", "component": "manager/order/index", "name": "Order" }
  ]
}
```

字段包括:路由的名称、路由的路径、是否隐藏、是否重定向、组件名称,以及有没有子路由——有的话就挂一个 `children`。

翻译的活儿在 `buildMenus(List<SysMenu> menus)`:

```java
List<RouterVo> routers = new ArrayList<>();
for (SysMenu menu : menus)
{
    RouterVo router = new RouterVo();
    RouterVo.MetaVo meta = new RouterVo.MetaVo();
    // 把菜单数据搬到路由对象上:名称、图标、缓存标志、路径……
    router.setName(getRouteName(menu));
    router.setPath(getPath(menu));
    router.setHidden("1".equals(menu.getVisible()));
    router.setComponent(getComponent(menu));
    router.setMeta(meta);

    // 关键:有子菜单就继续递归,把子菜单扔回当前方法构建子路由
    List<SysMenu> cMenus = menu.getChildren();
    if (CollUtil.isNotEmpty(cMenus) && isRouter(menu))
    {
        router.setChildren(buildMenus(cMenus));
    }
    routers.add(router);
}
return routers;
```

每一条菜单都得配一个路由对象——第一个是工单,就得给工单造一个路由,把它的菜单名称、图标、路径这些搬进去。搬完之后**关键判断来了**:当前菜单有没有子菜单?工单管理下面有没有?点位管理下面有没有(区域、点位、合作商那三个)?有的话就把这三个子菜单扔回当前方法,继续造它们的路由。

这个递归的思想跟构菜单树一模一样:**按树形结构逐层往下走**。所以系统管理底下的用户管理、角色管理、菜单管理这些二级菜单路由,跑完这遍就全有了。

到这里核心代码就讲完了。核心讲完,还有两个特殊判断要扩展一下。

#### 特殊情况一:挂在主类目下的组件菜单

第一个特殊判断是:**判断当前菜单是不是主类目下的组件菜单**,也就是 `parent_id = 0` 且 `menu_type = 'C'`。如果是,不能直接把它当成一级路由挂上去,而是要给它**造一个子路由**。

咱们演示一下。进菜单管理新增一个菜单:

- 上级菜单:主类目(它的 id 就是 0)
- 菜单类型:二级组件菜单
- 菜单名称:测试管理,显示排序:5
- 路由地址:`test`,组件路径:我写个 `manager/order/index`

保存、刷新,菜单列表里就多出这条了,它挂在主类目下。

它跟我们之前的订单管理有什么区别?订单管理是**目录菜单**,下面挂一个组件菜单,跳转时路由路径由两层组成:第一层 `order` 对应订单管理的目录菜单,第二层对应它的组件菜单。**若依默认情况下,通过路由找视图组件,地址都是两层:一级目录 + 二级组件。**

但我们新建的测试管理,肉眼看只有一层。**这是肉眼欺骗你了**——它的路由跳转同样是两层:第一层是一个正斜杠的根,第二层才是 `test`,而这个 `test` 是由子路由组成的。

刷新 F12 看返回结果验证一下:第一个正斜杠 `/` 对应 path 地址,下面有一个子路由叫 `test`,和浏览器里访问的路径严丝合缝。两个一拼,就得到完整的路由路径,跳到对应视图组件了。

```text
错误直觉:  /test              ← 以为只有一层
实际结果:   /  +  test         ← 根 + 子路由,拼出来才是 /test
               └── test
```

有小伙伴会纠结:为啥这么设计?因为**前端代码是固定的**,后端返回的格式必须统一,才能保证前端代码的通用性。

> **结论**:就算你创建的是主类目下的组件菜单,返回的格式也必须跟普通二级组件菜单一模一样,做到统一性。

#### 特殊情况二:被误配成外链的内部链接

第二个特殊判断:**判断是不是主类目下的菜单,并且路径以 http 开头的内部链接**。如果是,同样创建子路由,子路由的作用是把 http 开头的那一段**删掉**,只保留基础域名,再改造成一个内部链接的路径。

为什么要有这个兜底?看个真实的翻车现场。

菜单管理里把测试管理的上级菜单恢复成主类目,其中有个选项叫"是否外链"。点"是",路由地址就填外链地址,比如 `https://www.itcost.cn` 这样的官网地址。正常配置下刷新页面,测试管理就是个外链,点击跳转会打开新窗口访问官网——**这是正常配置**。

但我**不小心配置错了**:在测试管理里我没有把它设置为外链,却点了"否"。那这个路由地址还能当外链跳吗?肯定不能啊。

点确定、刷新、再点测试管理——它不再是外链跳转了,路径被处理了一下,而处理规则就是代码注释里写的那一套:**它会创建一个子路由,删掉 `https://` 开头的这一部分,只保留基础域名,并改成一个内部链接的路径。**

```java
else if (menu.getParentId() == 0 && isInnerLink(menu))
{
    router.setPath("/");
    router.setComponent(null);
    StringRouterVo path = new StringRouterVo();
    // 去掉 https:// 前缀,把外链降级成站内路由
    path.setPath(removeStartWith(menu.getPath(), Constants.HTTP_PREFIX));
    path.setComponent(getInnerPath(menu));
    router.setChildren(CollectionUtils.arrayToList(path));
}
```

一句话概括:**这个方法是用来防止我们不小心把内部链接改成了外部地址的。** 了解一下即可,记住结论就行。

两个特殊情况处理完,最终把构建好的路由加进路由列表,全部遍历完就返回完整路由列表给 Controller,Controller 再把它返回给前端。后端部分到此就分析完了。

### 路由怎么变成左边那列菜单

回到前端。拿到结果以后,状态管理对象里会先做一个**深拷贝**,把后端返回的 JSON 格式数据转换为各自对应的前端路由格式,然后调 `setRouters`——这个 set 就是我们的**侧边栏**——把后端返回的动态路由存入到当前的状态管理对象当中。

> **提示**:这一刻请务必记住:状态管理对象里已经有动态路由了。为什么非要记住它?因为前端页面加载完毕之后会触发路由的核心代码。

路由的核心代码在 `src/layout/index.vue`。它加载的就是登录之后的基础布局:侧边栏、头部导航栏、主体区域三块,对应到浏览器上就是这三片地方。主体区域负责显示各个视图组件,而**侧边栏这一块,就涉及动态路由了**。

侧边栏组件在 `layout/components/Sidebar/index.vue`,看第 15 行,有个菜单项,它做了一个 `for` 循环遍历。遍历的集合是谁?**就是刚才路由状态管理对象里存着的那些路由**。把后端返回的数据遍历一遍,视图就渲染出菜单了。

用户点击每一个组件菜单,布局页面的主体区域就会根据 path 地址找到对应的视图组件,在主体区域渲染,从而展示对应页面。这就解释了为什么点工单管理出工单管理界面、点运维工单出运维工单界面:**通过你指定的 path 找到对应的视图组件,在主体区域渲染。**

到这,"获取动态菜单路由"的前后端源码就全部分析完了。小结一下,前端这条线是:

```text
登录成功 ─► 加载 permission.js
         ─► 跳首页,加载 layout 布局组件
             ├─► 加载 Sidebar 侧边栏 ─► 遍历动态菜单路由渲染出菜单
             └─► 用户点击菜单
                     └─► 路由里的 path 跳到对应视图组件
                             └─► 在主体区域显示
```

后端这条线是:拿到当前登录用户 id → 判断是否超级管理员(是就查全部菜单,不是就五表联查) → 从 `parent_id = 0` 的根节点开始构菜单树、一级一级递归往下 → 构建前端需要的路由格式(同样是先一级再递归二级) → 返回给前端存进状态管理对象 → 侧边栏遍历渲染 → 点击菜单跳到指定路径的视图组件。

### 前端挡不住 Postman:权限注解怎么补上最后一层

前面这一整套有个前提:用户是规规矩矩从菜单点进去的。但只要有人**绕开前端控制,直接拿接口测试工具去调他没权限的接口**,菜单藏得再深也没用。

在若依里,我们用**权限注解**来强化安全措施。Spring Security 提供了一个注解叫 `@PreAuthorize`,它能实现**方法级别的访问控制**,确保只有符合条件的用户才能访问特定方法。

在若依框架生成的代码里,你会发现每个 Controller 方法上都装饰了这么个注解,它的作用就是**在方法执行之前进行权限校验**:满足条件就顺利访问,不满足就给出相应的提示。

#### 先把现象演一遍

用超级管理员账号,给黑马彭于晏开放"系统工具 → 系统接口"的测试权限。因为这个模块是我们改造代码生成器之后提供的 Swagger 注解,正好拿它做功能测试。

为了方便测试,我准备了第二个浏览器,登录黑马彭于晏的账号。现在他多了"系统工具",点进系统接口,找到"查询订单列表",点调试。

发送请求之前得先携带 token 令牌,而令牌在浏览器的调试工具里:按 F12,找到 Storage/Application,Cookie 里存的就是登录用户的 token,选中复制。

发请求,返回结果:**"没有此权限,请联系管理员授权"**。因为黑马彭于晏本身没有订单访问的权限,后端就进行了拦截,并友好地提醒他权限不足。

#### 为什么授权后还要重新登录

接着回到超级管理员,给订单管理开放全部权限。确定之后,回到黑马彭于晏这里,**注意:此时需要退出用户重新登录**。

为什么必须重新登录?因为**后端校验此用户的权限,是基于上次登录的缓存数据进行的**。我们之前登录时,已经把用户的权限存入 Redis 缓存了。看看当前登录用户黑马彭于晏的权限字符串——只有区域列表的查询和 Swagger 的接口测试,**并没有订单的**。

所以配置完毕后也需要重新登录才生效:退出、重新登录、输验证码、重新进系统工具、重新打开系统接口。注意重新登录后 **token 也已经重新生成了一份**,原来那份令牌就失效了,所以还得再开一次 F12、把新 token 复制替换进去。

再次发送请求——响应 200,数据成功返回到前端。

> **结论**:权限数据是登录时一次性加载进 Redis 缓存的。管理员改了权限,**被改的用户必须重新登录,新权限才会生效**。这是新手最容易踩的坑:明明授权了,接口还是报权限不足。

#### @PreAuthorize 的底层:PermissionService

回到 PPT。注解的属性值就是它的底层实现:

```java
@PreAuthorize("@ss.hasPermi('manage:order:list')")
@GetMapping("/list")
public TableDataInfo list()
{
    // ...
}
```

这个表达式由三部分组成:`@ss` 表示 `PermissionService` 这个服务类;点 `hasPermi` 是一个方法,作用是判断该用户是否拥有当前的权限;`'manage:order:list'` 就是当前方法的权限参数。**就这三部分完成权限校验。**

`@ss` 取名于 Spring Security 的首字母缩写。按住 Ctrl 定位过去,它是若依自定义的权限实现类,里面有个 `hasPermi` 方法专门验证用户是否具备某种权限,我们在 Controller 里把参数传给了它。

方法实现拆开其实非常简单:

```java
public boolean hasPermi(String permission)
{
    // 第一步:传进来的权限参数为空,直接 false
    if (StringUtils.isEmpty(permission))
    {
        return false;
    }
    // 第二步:拿到当前登录用户信息
    LoginUser loginUser = getLoginUser();
    Collection<String> permissions = loginUser.getPermissions();
    // 登录状态失效 -> false
    if (CollUtil.isEmpty(permissions))
    {
        return false;
    }
    // 把权限集合存进上下文,底层是 ThreadLocal,方便后续操作
    ...
    // 最关键的一步:权限集合里有没有我当前方法的权限参数
    return permissions.contains("*:*:*") || permissions.contains(permission);
}
```

逐条说:

- **权限参数为空**,直接返回 `false`,false 表示不具有当前权限,直接拦截;
- **拿到 `LoginUser` 对象**,它包含用户基本信息、角色集合、权限集合;
- **判断当前登录用户是否存在**,不存在说明登录状态已经失效了——你都没登录,当然不具有当前权限,返回 `false`;
- **再判断权限集合是否为空**,为空说明用户虽然登录了但没有任何权限,还有必要校验吗?没必要,返回 `false`;
- 最后也是最关键的一步:把权限集合存进上下文(底层是 **ThreadLocal**),然后检查这个集合**是否包含当前方法的权限参数**。

而最终那行判断其实只有一次或运算。左边判断 `permissions`(当前登录用户的权限集合)是否包含常量里的 `*:*:*`——**这个常量就是超级管理员的三个星,一旦出现就表示你拥有所有权限**,那当然放行;如果是普通用户,就看权限集合是否包含当前方法的权限字符串,包含返回 `true`,否则 `false`。

回到 Controller:`@PreAuthorize` 注解拿到这个表达式返回的布尔值,Spring Security 框架就根据这个布尔值操作——合法就执行方法逻辑,非法就拦截并抛出异常,给前端做出友情提示。

#### 六个方法:权限与角色各三把

`PermissionService` 里除了 `hasPermi`,还有几个同样是做权限/角色校验的:

| 表达式 | 作用 | 通过条件 |
| --- | --- | --- |
| `@ss.hasPermi('manage:order:list')` | 验证用户是否具备某个权限 | 权限集合含该权限,或含 `*:*:*` |
| `@ss.lacksPermi(...)` | 验证用户是否**不**具备某个权限 | 与 `hasPermi` 逻辑相反:满足权限就拦截 |
| `@ss.hasAnyPermi('a:b:c', 'd:e:f')` | 验证是否具备任意一个权限 | 多个权限用逗号分隔,命中其一即放行 |
| `@ss.hasRole('accountant')` | 判断用户是否拥有某个角色 | 拥有则放行,否则拦截 |
| `@ss.lacksRole(...)` | 判断用户是否**不**拥有某种角色 | 与 `hasRole` 完全相反 |
| `@ss.hasAnyRoles('a', 'b')` | 判断是否拥有任意一个角色 | 多个角色用逗号分隔,命中其一即放行 |

`lacksPermi` 咱们实测过:把 `hasPermi` 改成 `lacksPermi`,Ctrl+F9 热部署更新后重新发请求,业务异常就来了——因为黑马彭于晏**有**订单权限,`lacksPermi` 要求他没有才放行,所以被拦。刷新一下浏览器重新打开接口再发,就能看到明确的权限不足提示了。(第一次看不到提示是 Swagger 页面的显示 bug,不是代码问题。)

`hasAnyPermi` 我们就不演示了,它跟我们之前讲过的前端权限数组有点像,感兴趣的同学可以课下玩一下。

角色那边也是同理:`hasRole('accountant')`,我们把表达式改成这个,黑马彭于晏当前登录拥有"财务人员"这个角色,所以请求成功返回数据。大家可以发现,**判断角色的逻辑跟判断权限逻辑是一样的**,根据自己的业务场景调整即可。而若依默认使用的 `hasPermi`,已经能满足绝大多数场景。

#### @Anonymous:给不想登录的人留个门

有小伙伴提了个新问题:**如果我们编写的某个方法是不需要登录、用户也能访问的,该怎么办?**

这时候就用到一个注解——`@Anonymous`。它可以放在方法上,也可以放到类上:

- 放在**方法**上:此方法不登录也可以匿名访问;
- 放在**类**上:该类所有方法都不需要登录,可以匿名访问。

> **易错点**:有一个细节你必须知道——**需要把之前的 `@PreAuthorize` 注解给它注释掉**。不注释的话这两个注解就会产生冲突:一个是需要权限校验,一个是不需要权限校验的。

应用场景也很明确:比如**系统公告**,在没有登录、或者说没有权限的情况下,应该所有人都能看到系统公告的更新、版本信息等等。

### 登录成功了凭什么还要等 100ms:异步任务管理器

前面我们说过,登录流程里会用异步任务管理器来记录登录日志。那这个东西到底解决什么问题?为什么非它不可?

`AsyncManager` 主要用于处理那些**不需要及时返回结果的后台任务**,它的核心优势在于能够提高程序的响应速度和整体的性能。语法很简单:`AsyncManager.getInstance()` 拿到单例对象,`execute` 方法底层通过多线程执行任务,而这个任务由异步线程工厂创建出来。

应用场景上,基础篇我们已经介绍过——若依提供了查询登录日志的功能来监控和维护系统运行状态,而这段代码就是用异步任务管理器实现的。

#### 一笔算得清的账

咱们通过用户登录的例子把账算清楚。

用户在浏览器输入用户名密码和验证码,发送登录请求,业务层的登录认证是核心业务:验证码校验、用户名查询、密码校验。校验失败就记录日志并返回提示信息,校验成功同样要记录日志并返回 token。

**假设登录认证核心业务耗时 50ms,记录日志也耗时 50ms——那整个登录请求耗时多久?100ms。**

现在产品经理根据客户要求加了个功能:后台登录成功后给用户发一条提示短信。这意味着业务层要加发送短信的代码,同样耗时 50ms。**整个登录请求耗时变成 150ms**,用户等待时间增加,系统性能随之下降。

更麻烦的在后面。我们的登录业务还涉及事务控制以保证一致性——**如果登录认证成功了,但记录日志时出现异常,就会导致事务回滚**。那这样的设计合理吗?显然不合理,这就是**"连锁失败"**。

可对当下业务来说,用户只关心登录是否成功;记录日志、发短信这些非核心业务,他并不关心是否立即完成。所以我们可以把它们交给异步任务管理器的多线程去处理。

```text
同步写法  总耗时 150ms
主线程 ──┬── 登录认证 50ms ──┬── 记日志 50ms ──┬── 发短信 50ms ──┬──► 返回
         │                   │                 │                 │
                        抛异常 ╰─► 事务回滚,前面白干

异步写法  总耗时 50ms
主线程 ──┬── 登录认证 50ms ──┬──► 返回 token
         │
         └─(交给线程池,延迟 10ms 起线程)─► 记日志 ─► 发短信
                                              │
                                       失败也回不到主线程
                                       登录事务不受影响(故障隔离)
```

改完之后:业务层只关注认证的核心业务代码,记录日志和发送短信交给异步任务管理器。用户登录耗时只剩 50ms,**无需等待异步任务完成**,性能显著提升。

更重要的是,**登录认证作为一个独立的事务在主线程中执行,记录日志在另一个线程中进行**。即使记录日志失败了、登录认证成功了,也不会影响登录认证的事务——实现了**故障隔离**,彼此互不影响。

#### 从业务代码到线程池

源码我们直接看。业务代码里是在登录成功的位置(第 102 行)通过异步任务管理器记录登录成功的日志信息:

```java
AsyncManager.getInstance().execute(new AsyncFactory() { ... });
```

这里 `AsyncManager` 并没有 `new` 出来,我们调用的是它的静态方法。这个方法返回的是当前的实例对象:

```java
public class AsyncManager
{
    /** 异步操作任务调度的线程池:从 IOC 容器中拿到 */
    private final ThreadPoolExecutor executor =
            (ThreadPoolExecutor) SpringUtils.getBean("scheduleThreadPool");

    /** 单例 */
    private static final AsyncManager INSTANCE = new AsyncManager();

    public static AsyncManager getInstance()
    {
        return INSTANCE;
    }

    public void execute(Runnable task)
    {
        // 延迟 10ms 执行
        executor.schedule(task, 10, TimeUnit.MILLISECONDS);
    }
}
```

> **提示**:这里用的是**饿汉式单例**。静态字段直接 `= new AsyncManager()`,类加载时就把实例造好了,而不是等到第一次调用 `getInstance()` 才创建。

线程池是通过 Spring 的工具类 `getBean` 从 IOC 容器里拿到的。搜一下 `scheduleThreadPool` 这个 bean:

```java
@Bean(name = "scheduleThreadPool", destroyMethod = "shutdown")
public ScheduledExecutorService scheduleThreadPool()
{
    ScheduledExecutorService scheduledThreadPool = new ScheduledThreadPoolExecutor(
        CORE_POOL_SIZE,                 // ① 核心线程数
        new ThreadFactory() {
            @Override
            public Thread newThread(Runnable r) {
                Thread thread = new Thread(r, "schedule_pool_" + count.getAndIncrement());
                thread.setDaemon(true); // ② 守护线程
                return thread;
            }
        },
        new ThreadPoolExecutor.CallerRunsPolicy() // ③ 拒绝策略
    );
    return scheduledThreadPool;
}
```

三个参数很清楚:第一个是**核心线程数**,这里定义的是 50,大家可以结合自己的业务场景调整;第二个用**线程工厂**创建线程,同时指定了线程名称,并把守护线程设置为 `true`;第三个设置**线程的拒绝策略**。

拿到线程池对象之后,用它的 `schedule` 方法做任务调度,这里要三个参数:**任务对象、延迟时间、延迟单位**。后面两个我已经写好注释了——延迟 10ms 执行,单位是 `TimeUnit.MILLISECONDS`。

#### 任务本身:异步线程工厂怎么记一条登录日志

回到登录 Service,那边调用异步线程工厂创建了一个任务,传递三个参数:**当前登录的用户名、登录状态为成功、以及 I18N 对应的提示信息**。

任务方法内部拿到这三个参数之后:

1. **解析客户端的代理信息**,拿到客户端的操作系统和浏览器信息;
2. **获取客户端的 IP 地址**,再通过 IP 去获取用户所在的地理信息;
3. **用 StringBuilder 构建日志字符串**,拼上 IP、用户名、状态、message;
4. **通过 slf4j 把日志信息输出到控制台**。

但光输出到控制台可不够,我们还需要把登录信息保存到数据库的系统访问记录表 `sys_logininfor` 里。

这张表的字段我们直接对着看:`id` 是自增不用管;然后是用户账号、用户登录 IP、登录地点、浏览器类型、操作系统、登录的状态(成功还是失败)、提示信息,以及访问时间。

所以代码里还要通过 User-Agent 拿到操作系统和浏览器信息,然后封装一个 `SysLogininfor` 实体类,把这些参数 set 进去,**跟这张表做到一一对应**。其中登录状态要转换一下:根据传过来的状态判断成功还是失败,**成功是 `0`,失败是 `1`**。

最后一行,同样用 Spring 工具类的 `getBean` 方法从 IOC 容器里获取记录登录日志的 Service 层对象,调用它的 `insert` 插入方法。方法实现最终落到 Mapper 的 `insertLogininfor`,通过 SQL 语句把这条记录插进数据库。

所以在若依提供的登录日志界面里,我们就能查到之前的登录数据,成功的、失败的都有。

最后再把这条流程串一遍:记录日志本身就是一个具体的任务,所以我们先通过异步线程工厂生成一个任务,这个任务负责从 IOC 容器里获取登录日志业务层的对象,把日志信息保存到数据库;任务创建完毕之后交给异步任务管理器,底层通过线程池延迟执行;而线程池对象也是通过 Spring 工具类从 IOC 容器里获取的。延迟 10ms 执行,从而实现**多线程执行非核心业务代码,优化系统性能,提高用户体验**。

这也是若依框架设计的一个亮点。希望大家能掌握这种设计思想,以后开发遇到类似场景,也可以用这种模式优化代码。异步任务管理器还能提高代码复用性——我们只需要把任务创建出来,它就能执行各种类型的任务,比如记录日志、发送短信等等,通用性非常好。
