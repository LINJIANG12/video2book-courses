## 操作日志的切面机制与定时任务的调度原理
> 对应块：BLK32 | 覆盖分集：P109-P112 | 块标题（分集名）：《原理篇-20.操作日志》

上一章我们一起学习了异步任务管理器的特点和源码实现。接下来这一程，我们先把操作日志的源码剖析掉，然后正式进入第五章——定时任务。

先说清楚操作日志为什么重要。在日常编程中，记录日志是我们的得力助手，尤其在处理关键业务的时候，它能帮助我们追踪和审查操作的过程。若依提供的那个「查询操作日志」的列表大家都见过：重要的业务模块，增删改查，我们都需要记录下来。这个功能在基础篇已经给大家演示过了。

可是到了业务代码当中，如果你要手动去记录日志，那往往是繁琐且容易出错的。因为我们不得不去收集系统模块、操作类型、操作人员等等，这不仅增加了工作量，还有可能导致代码重复，影响业务逻辑的清晰度。

那有没有什么办法，可以让我们更优雅地来处理这个问题呢？

答案是肯定的——那就是**使用注解**。

在若依框架生成的代码当中，你会发现 Controller 方法上面装饰了一个 `@Log` 注解，它的作用是在方法执行时记录当前业务的操作日志，把它保存到数据库当中。

用注解的好处很直接：我们不需要在每个方法里面重复地编写日志记录的代码，减少了重复代码；同时我们的业务代码可以保持纯净，不被日志记录的逻辑所干扰做到了业务代码无入侵；还方便后期的扩展和维护。比如说我们需要调整日志记录的细节或策略，在使用 `@Log` 注解之后，只需要在一处进行修改，而其他引入此注解的方法都会同步生效。

那为什么一个注解就能这么强大？其实底层用到了 **AOP** 的思想——它可以做到在程序运行期间，不修改源代码的基础之上，对已有的方法进行增强，而增强的内容就是来记录操作日志的。

好，那下面我们就钻到源码里去看一看它到底是怎么做到的。

### `@Log` 注解：挂在方法上的那一行字

先回到 IDEA 当中，我已经提前打开了订单管理的 Controller，在新增方法上，注意看这边有一个 `@Log` 注解。按住 Ctrl 键点进去，往上拉，这就是若依自定义的操作日志记录注解。

```java
@Target({ ElementType.METHOD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface Log
{
    // 模块名称
    String title();

    // 操作类型
    BusinessType businessType() default BusinessType.OTHER;

    // 操作人类别
    OperatorType operatorType() default OperatorType.MANAGE;

    // 是否保存请求参数
    boolean isSaveRequestData() default true;

    // 是否保存响应参数
    boolean isSaveResponseData() default true;

    // 排除的参数
    String[] excludeParamNames() default {};
}
```

> **定义**：元注解 `@Target` 指定当前注解的使用位置，可以放在参数上，也可以放在方法上，但通常情况下我们使用在方法上；`@Retention` 指定当前注解的作用范围，它表示在**运行时有效**（`RUNTIME`）；`@Documented` 则表示在生成代码的文档时，也会包含此注解。

下面看这个注解的属性，我这里已经把注解属性的说明整理到 PPT 上了，咱们一起来看一下。

| 属性名 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `title` | `String` | 空 | 描述操作模块，比如订单管理、设备管理、工单管理等等，你操作哪个模块在这里面做一个记录 |
| `businessType` | `BusinessType` 枚举 | `OTHER`（其他类型） | 描述当前方法的操作功能 |
| `operatorType` | `OperatorType` 枚举 | `MANAGE`（后台用户） | 操作人的类别 |
| `isSaveRequestData` | `boolean` | `true` | 是否保存当前方法传过来的请求参数 |
| `isSaveResponseData` | `boolean` | `true` | 是否保存方法的响应参数 |
| `excludeParamNames` | `String[]` | 空 | 指定需要排除的请求参数 |

`BusinessType` 这个枚举，除了默认的 `OTHER`（其他），它的枚举值还有新增、修改、删除、授权、导出、导入、强退、生成代码，还有清空数据等等，用来描述当前方法的操作功能。我们可以根据业务来做调整，当然了这个枚举值也是可以进行扩展的，感兴趣的同学课下可以去玩一下。

`OperatorType` 也是枚举类，有三个枚举值：其他、后台用户和手机端用户。我们知道若依既有 PC 端的也有手机端的，如果是 PC 端用户，我们就采用 `MANAGE`；手机端用户的话可以改成 `MOBILE`；如果是其他平台访问，就改为 `OTHER`。

再说最后两个布尔属性。`isSaveRequestData` 问的是我们是否保存请求参数，也就是说是否保存当前方法传过来的参数。我们在做订单新增时会传递一个 `order` 参数，而这个参数默认是要保存到操作日志当中的；`isSaveResponseData` 问的是是否保存响应的参数，我们可以看到该方法有一个 `AjaxResult` 的返回结果，这个返回结果默认也会保存到操作日志当中。如果你想排除某个请求参数的话，就用 `excludeParamNames`。

> **结论**：通常情况下，后面这四个注解属性咱们使用默认值即可。所以我们在操作日志的查询页面当中，点击「详细」按钮，就可以查看该方法的请求参数、返回参数这些比较详细的信息。

### 切面：注解是靠什么被拦下来的

注解本身只是个标记，真正干活的是切面。上面我们提到了底层用的是 AOP，所以我们需要找到拦截此注解的切面类了。

来，我们找到 `ruoyi-framework` 框架模块，打开 `src` 下面的 `aspectj` 包，下面有一个 `LogAspect`，它就是记录日志的切面类。

```java
@Aspect
public class LogAspect
{
    // 方法开始前记录的时间
    private Long operTime;

    // 切点表达式：专门拦截 Controller 类上增加了 @Log 注解的方法
    @Pointcut("@annotation(com.ruoyi.common.annotation.Log)")
    public void logPointCut()
    {
    }

    // 前置通知：在每个方法执行前记录当前时间
    @Before("logPointCut()")
    public void doBefore(JoinPoint joinPoint)
    {
        operTime = System.currentTimeMillis();
    }

    // 后置通知：方法正常返回时记录日志
    @AfterReturning(pointcut = "logPointCut()")
    public void doAfterReturning(JoinPoint joinPoint)
    {
        handleLog(joinPoint, null, null);
    }

    // 异常通知：方法抛异常时同样记录日志
    @AfterThrowing(pointcut = "logPointCut()")
    public void doAfterThrowing(JoinPoint joinPoint, Exception e)
    {
        handleLog(joinPoint, e, null);
    }
}
```

`@Aspect` 表示当前类是一个切面类，而切面类可以定义四大通知加环绕通知。那么若依使用了哪些通知呢？我们来看一下。

第一个是 `@Before` 前置通知，后面跟的是切点表达式，这个表达式专门来拦截在 Controller 类上面增加了 `@Log` 注解的方法。而这个前置通知的作用，就是在每个方法执行前记录下当前的时间。记录时间是为了方便我们计算每个业务代码的耗时——方法开始之前记录一个时间，方法执行之后再记录一个时间，两个时间相减就是该方法的耗时，这点小伙伴们能接受吧。

再往下是 `@AfterReturning`，表示后置通知；它下方还有一个 `@AfterThrowing`，表示异常通知。这两个通知的作用是：无论业务方法是执行成功还是执行失败，它们的内部都会去调用 `handleLog`。

所以当前业务方法甭管是执行成功了还是执行失败了，都需要记录操作日志——**成功要记，失败了更要记**，因为失败的那次恰恰是最需要被追查的。

### `handleLog`：一条操作日志是怎么拼出来的

按住 Ctrl 键我们进到 `handleLog` 的实现细节。这个方法一共要吃四份信息：

- 第一个是我们的**切点**，也就是我们访问的目标方法；
- 第二个是**切点上面的自定义注解**，也就是我们的 `@Log` 注解；
- 第三个是**是否有异常信息**；
- 第四个是**方法的返回结果**。

> **易错点**：第三和第四份信息是**互斥**的。如果方法成功返回，它是没有异常信息的；如果方法发生异常了，它是没有返回结果的。所以这两份不会同时存在。

拿到这几份信息之后，方法的执行步骤是这样的。首先它通过 `SecurityUtils` 来获取当前的登录用户，然后创建了一个操作日志的实体类，而这个实体类对应的就是数据库的**操作日志记录表**，也就是说我们最终需要封装好几个属性字段，把它保存到数据库当中来。

我们回到代码来看每一步具体设置了什么：

| 步骤 | 设置的字段 | 取值来源与说明 |
| --- | --- | --- |
| ① | 执行状态 | 默认是正常的，也就是设置为 `0` |
| ② | 请求地址 | 包含两个参数：请求 IP 和请求 URL |
| ③ | 操作人、部门名称 | 登录用户不为空时才设置，部门名称正好和我们在用户信息里看到的对上 |
| ④ | 执行状态 + 错误信息 | `e != null` 表示当前 Controller 方法已经发生了异常，此时把状态改为 `1`，并把错误信息也存入进去 |
| ⑤ | 方法名称 | 通过切点表达式获取类名，再获取方法名，然后类名加方法名组合成一个完整的方法名称，包括包名、类名和方法名 |
| ⑥ | 请求方式 | 是 `GET` 还是 `POST`、`PUT`、`DELETE` 等等 |
| ⑦ | 模块名称等 | 这一行代码专门用来处理 `@Log` 注解上面的参数：系统模块名称、操作人类别、是否保存请求参数、是否保存返回值等等，一把 `set` 到我们的日志属性当中 |
| ⑧ | 耗时时间 | 方法即将结束时的当前时间，减去前置通知中记录的 `operTime`，就是整个业务方法的总耗时 |

最后一行使用了**异步任务管理器**，底层就是线程池来执行一个任务，而这个任务就是保存操作日志到数据库当中。所以这里使用了异步线程工厂来创建一个任务。

### 落库交给异步，最后跑在线程池里

这个任务的细节我们按住 Ctrl 键跳转过去看：首先它用到了 `AddressUtils` 工具类来获取我们的 IP 地址，从而解析此 IP 所对应的操作地点，是哪个区域下的。

当我们记录完毕以后，熟悉吗兄弟们——使用了 Spring 提供的工具类 `SpringUtils`，从 IOC 容器当中获取记录操作日志的业务层 Service 代码，然后调用它的 `insert` 方法实现操作日志的保存。我们再按住 Ctrl 键指到方法签名，方法实现调用了 Mapper 层，来看一下 SQL 语句，实现了操作日志的新增功能。

整个链路串起来就是这个走向：

```text
客户端发送请求
      |
      v
Controller 方法（标注了 @Log）
      |   AOP 代理在这里拦一道
      v
LogAspect（切点：@annotation(...Log)）
      |-- @Before          --> 记下开始时间 operTime
      |-- @AfterReturning  --+
      +-- @AfterThrowing   --+--> handleLog()
                                    |  收集：操作人 / 部门 / IP / URL
                                    |        模块 / 操作类型 / 请求方式
                                    |        执行状态 / 异常信息 / 耗时
                                    v
                    AsyncManager + 异步线程工厂 + 线程池
                                    |
                                    v
                    ScheduledRunnable
                       |-- AddressUtils：IP -> 操作地点
                       +-- SpringUtils.getBean(SysOperLogService)
                              +-- insert() --> sys_oper_log 表
```

这里有两点要特别注意。其一，我们获取操作日志的业务层对象用到了 Spring 的工具类，从 IOC 容器当中来获取，然后再把日志保存到数据库当中；其二，异步管理器底层那个线程池对象，我们同样是用 Spring 的工具类从 IOC 容器当中来获取对象实例，然后调用它的方法完成任务的执行。

所以，操作日志这一部分我们也是通过**异步多线程**来执行的，从而提升整体的性能。

> **结论**：同学们到这里我们发现，记录操作日志跟我们之前讲的记录登录日志是一样的——都使用了异步任务管理器，底层通过多线程来执行任务，从而优化了系统的整体访问性能。回头看这一块，若依的操作日志首先使用了自定义注解，加上 AOP 的切面，还有异步任务管理器。这三个基础也是绝大多数框架底层的实现原理。

### 定时任务的骨架：先看两张表

接下来我们正式开始第五章定时任务的学习。这一章共分为两个小节：源码分析我们从基础开始，一步步构建起对定时任务模块的理解——先介绍代码的基本结构，包括它所依赖的表结构和字段，然后深入到 Quartz 的核心，探索它的体系结构和核心 API，最后一起分析定时任务执行的核心代码，理解它是如何工作的。第二小节探讨集群的概念，以及它是如何帮助我们在生产环境中应对各种挑战，此外还会学习如何将现有的项目升级为 Quartz 集群模式。

先从表结构入手，因为要想深入理解定时任务，我们需要从若依框架的表结构开始。

定时任务在实际开发中应用非常广泛，它可以每天给用户增加积分，可以定时地发送邮件或生成报表，还可以用来定时清理数据，保持数据库的整洁。这些场景大家是比较熟悉了。为了方便开发者能够更灵活地来管理这些任务，若依提供了一个友好的外部界面，实现动态管理任务，以达到动态控制——比如我们可以开启或暂停定时任务，重启或删除现有的任务，添加新任务或修改现有任务的配置，极大地方便了开发的过程。

这里有两张关键的表。第一个是 `sys_job`，这是定时任务的**核心表**，存储了任务所有的配置信息，包括任务名称、任务分组等等；第二个是 `sys_job_log`，它记录了**任务调度的详细日志**，包括执行时间和执行结果等等。

#### 核心表 `sys_job`

我们配合页面来讲解，新增定时任务的时候需要保存这张表的配置信息。

第一个要说的是前面三个字段——界面上是有小钥匙的，它表示一个**联合主键**：由任务 ID、任务名称和任务组名组成，是该表的唯一标识。

那为什么要这么设计呢？因为在不同的分组下，任务名称是允许重复的。而任务 ID 呢是主键自增的，我们可以在前端页面指定任务的名称，在输入框输入你想要的名称就可以了；还有任务的分组，对应的是数据字典，默认和系统，后期我们可以结合业务的场景对任务分组的数据字典进行扩展。

接下来是调用方法对应的字段 `invoke_target`，这个调用方法的语法有两个，小伙伴们还记得我们在基础篇介绍过的吗？第一个是通过 **Bean 的方式**来调用，左侧是 Spring IOC 容器中 Bean 的 ID，而右侧是方法名，还可以传递参数；第二种是通过**全限定类名**，由包名和类名组成，底层是通过反射来执行此方法，同样的可以支持参数的传递。而参数支持 String 类型、布尔类型、长整型、浮点型以及普通的整型等等。

再往下是 **cron 表达式** `cron_expression`，用来定义此任务的时间规则。在表达式的下方呢有**执行策略** `misfire_policy`，这个执行策略我们之前也介绍过：是任务失败之后、服务器重启了，它该如何恢复我们之前没有执行的任务，有三种方案——立即执行、执行一次、放弃执行。

还有同一个任务是否支持**并发**执行，对应的是 `concurrent`，`0` 是允许，`1` 是禁止。

还有一个**状态**字段 `status`，我们创建好的任务默认是**暂停**的状态，界面上这里有个开关，我们可以在这里面点击把状态设置为 `0` 正常，而灰色的是 `1` 暂停的状态；正常的状态就会按照 cron 表达式的时间规则定期来执行此任务。

剩下的五个字段小伙伴们应该不陌生了，这是我们实体类继承 `BaseEntity` 之后提供的五个公共字段：创建人、创建时间、更新人、更新时间，最后一个是备注说明。

#### 日志表 `sys_job_log`

每一个定时任务在执行时都会有它的调度日志存入到这张表当中。那怎么来查看呢？注意看列表最右侧的位置有一个**调度日志**的按钮，我们点击以后会打开一个新的界面，那么在当前界面就会展示该任务的执行日志列表：有任务名称、所属分组、调用目标字符串、日志信息等等。当然我们也可以点击右侧的「详细信息」按钮，查看它所有的字段。

我们一个一个字段对比着看：

| 页面字段 | 数据库字段 | 说明 |
| --- | --- | --- |
| 日志序号 | `job_log_id` | 该条调度日志的主键 |
| 任务名称 | `job_name` | 当前这条日志记录所对应的任务名称 |
| 所属分组 | `job_group` | 任务所属的分组 |
| 调用目标字符串 | `invoke_target` | 这里用的是 Spring Bean ID 来执行此方法，**没有看到括号，表示是无参传递** |
| 日志信息 | `job_message` | 这里打印了任务名称以及耗时的毫秒值 |
| 执行状态 | `status` | `0` 正常，`1` 失败 |
| 异常信息 | `exception_info` | 用于记录异常信息；由于我们当前的任务是执行成功的，所以异常信息并没有输出 |
| 执行时间 | `create_time` | 也就是我们的创建时间 |

#### 两张表是一对多

我们在执行任务时需要记录每个任务的日志信息，那这两张表是什么关系呢？小伙伴们你来回答一下。

没错，**是一对多的关系**：一个核心任务可以有多个执行日志的记录。所以在日志表当中有两个外键字段——`job_name` 和 `job_group`，指向任务核心表的联合主键。通过任务名称和任务组名，就可以确保当前这条日志属于哪一条核心任务。

通过以上这两张表，我们就能保存和管理新增的定时任务，以及它们的调度日志了。

### 代码放在哪儿：模块与目录结构

接下来我们来看一下定时任务代码的目录结构。先看后端：若依框架为定时任务提供了一个独立的模块，叫 `ruoyi-quartz`，这使得代码管理和维护变得更加容易。此模块主要分为四部分——

1. **配置类**：通过它可以开启 Quartz 集群的模式，这是我们第二小节主要要讲的；
2. **定时任务的三层代码**，以及对应的实体类和 Mapper 的映射文件，都在这几个包下面；
3. **`task` 包：开发任务的类**，用于编写具体业务处理代码的地方，默认要求任务代码都要放在此包下；
4. **`util` 包：定时任务相关的工具类**，这里包含了创建执行定时任务的工具，以及处理时间规则等实用的功能。

再看前端。在 `api/monitor` 目录下有两个 JS 文件，分别负责定时任务和调度日志的 API 请求；它们对应的视图组件在 `views/monitor` 目录下，`index.vue` 是我们定时任务管理的界面，而 `log.vue` 呢是用于查询和展示定时任务的调度日志。

通过之前的学习，我们已经对若依前端代码的交互模式有所了解，因此在稍后的源码分析当中，我们将重点关注后端的代码实现。

### 项目一启动，谁先把任务跑起来

项目启动以后，根据任务的配置、勾选状态来创建和执行任务。那若依是如何知道这三个任务谁要执行、谁处于暂停状态呢？为了解答这个问题，我们对这一部分的源码来进行分析。

在定时任务的 Service 实现类当中，有一个 `init` 方法，上面添加了 `@PostConstruct` 注解，这个注解的作用是来告诉 Spring：当前方法会在对象构造完成之后立即执行。

我们来看一下他做了什么：

1. 首先这个方法会**清空已有的调度器中的任务**，以确保从数据库加载最新的；
2. 第二步，从数据库当中**查询了所有的任务配置对象**（目前呢是三个）；
3. 最后**遍历任务的配置列表**，使用 `ScheduleUtils` 这个工具类来创建出定时任务。

由于这一部分的源码细节是比较多的，直接阅读呢可能有些困难。为了帮助大家更好地理解，我们先通过一张流程图来梳理整个过程。

```text
项目启动
   |
   v
定时任务 Service 对象被初始化
   |  同时执行 init 方法（@PostConstruct：对象构造完立刻执行）
   |     |-- ① 清空调度器中的历史任务，确保加载最新的
   |     |-- ② 通过 jobMapper 查出数据库中的全部任务配置
   v
遍历任务配置列表 --> ScheduleUtils.createScheduleJob(job)
   |  ① 按 concurrent 取 Job 任务类：
   |        0      --> QuartzJobExecution            （支持并发）
   |        其它   --> DisallowConcurrentExecution  （禁止并发，默认）
   |  ② JobBuilder  -> JobDetail（jobClass / jobId / jobGroup）
   |  ③ 取 cron 表达式，CronExpression 解析，
   |     按 misfirePolicy 决定错过后的补执行策略
   |        -> TriggerBuilder 生成 Trigger 并与 JobDetail 绑定
   |  ④ 数据库查出的 job 配置塞进 JobDataMap（键值对）
   |  ⑤ 任务已存在 --> 先删除，避免与旧任务冲突
   |  ⑥ cron 未过期 --> 放入 Scheduler 容器，可以被调度
   |  ⑦ status == 1 --> 暂停；status == 0 --> 执行
   v

   |

   +-- doInExecute()  : 调用 JobInvokeUtil 反射执行目标方法
   +-- after()       : 取出开始时间并清空 ThreadLocal，
   |                   封装 SysJobLog -> SpringUtils 取 Service
   |                   -> add() -> sys_job_log 表
```

#### 先定任务类，再定触发器

我们在创建定时任务时，会根据配置得到一个 Job 的任务类。注意这哥们是一个**抽象类**，同时实现了 `Job` 的接口，所以我们需要根据用户勾选是否并发来加载具体的实现类。界面上那个「是否并发」的字段，`0` 就表示允许，`1` 就表示禁止。

- `concurrent == 0` 的话，就会执行 `QuartzJobExecution` 这个实现类，表示支持并发；
- 其余的情况表示不允许并发执行，对应 `DisallowConcurrentExecution`——**DISALLOW 就是不允许的意思**，而且它不支持并发执行，咱们在类的上方添加了 Quartz 的 `@DisallowConcurrentExecution` 注解来表示禁止并发执行。

而这两个类默认都继承了我们的抽象类 `AbstractQuartzJob`。

确定了任务类以后呢，我们使用 `JobBuilder` 来构建 `JobDetail`，这里就会包含任务的名称、分组，还有我们刚刚得到的 Job 任务类——构建时需要包含 `jobClass`（任务类），还传递了 `jobId`、`jobGroup`，也就是任务的唯一标识和所属分组，创建出任务的详情对象。

然后我们再使用 `TriggerBuilder` 来构建一个 cron 时间规则的触发器。若依推荐我们使用的就是 **cron 表达式**。当这两个对象创建好之后呢，我们会把它存入到 Scheduler 容器当中，这样它们就可以被调度了。

把从数据库查询的 job 配置信息存入到 JobDetail 当中，这里使用的是 `JobDataMap`，以键值对的方式来存储。

接下来还有两个判断。第一个是**判断此任务是否存在**，如果存在的话，我们实现了任务的删除，确保新任务能够成功创建，避免与旧的任务产生冲突。第二个是**判断当前任务的时间规则是否过期**，如果没有过期的话，咱们就把 `JobDetail` 和 `Trigger` 存入到 Scheduler 的容器当中，这样他们就可以被调度了。

#### 宕机了怎么办：三种执行策略

触发器建好之后还要确定一个策略：解析 cron 表达式，解析成功以后根据 cron 时间规则来设置定时任务的策略。这个策略对应的就是 `misfire_policy` 字段，代码里用了 `switch` 语句来进行判断，**默认策略我们对应的就是放弃执行**。

我们回到那个场景去理解：数据库的客户端里对应字段就是 `misfire_policy`。在服务器正常运行时突然宕机了，那档期周期呢有一个小时——在这一小时当中，任务肯定是不会执行的。当服务器重新恢复以后，请问这些没有执行的任务，它有哪些策略可以重复执行呢？

| 执行策略 | 宕机恢复后的行为 |
| --- | --- |
| 立即执行 | 把之前没有执行的任务**全部**执行了 |
| 执行一次 | 仅执行**最后一个**任务 |
| 放弃执行 | 全部不补，**默认策略**，一般情况下用这个就可以了 |

这个执行策略我们在基础篇已经介绍过了，如果忘了的同学建议你去复习一下。

#### 暂停还是执行，就看状态字段

最后还有一个分支判断。因为默认是执行任务的状态，所以这里呢有一个判断的过程：**如果任务状态为 `1`**（界面上那个单词 `pause` 对应的就是暂停），那么我们就会使用 Scheduler 来暂停当前的任务；**如果为零的话**，咱们就会执行当前的任务。

而执行这个任务的话，底层呢会调用任务类，而这个任务类就是我们刚提到的允许并发执行和不允许并发执行的那两个，**默认的是不允许并发执行的**。它俩的底层呢又会去执行 `JobInvokeUtil` 这个工具类。

### 任务真正执行的那一刻

回到 `ruoyi-quartz` 的 `util` 包，这里有个方法叫 `execute`，就是 Scheduler 来执行的任务。我们先看它的第一行：首先初始化了任务的配置对象 `SysJob`，然后从**上下文**当中将属性复制到这个配置对象当中。而这个上下文就是我们刚刚存储的——我们把 job 的对象存进去了，所以这里可以把它取出来。

取出来之后呢，注意看这有个叫 `doInExecute` 的方法，他就是来执行具体任务的，这个我们稍后介绍。

在执行任务前，注意看这里有一个 `before`，它是一个前置处理，有点像我们 AOP 当中的前置通知；还有一个 `after`，这是执行之后的处理，有点像我们 AOP 当中的后置通知。那这两个方法做了什么事呢？

`before` 这行代码其实非常简单，跟我们之前讲过的记录操作日志是不是很像？——通过 **`ThreadLocal`（线程局部变量）来存入当前的系统时间**。存入完毕之后呢，就会通过 `doInExecute` 来执行具体的任务。任务执行完毕之后呢，就会触发后置处理，而这个后置处理就是来记录任务日志的。

我们来看一下 `after`。它把刚刚在 `before` 当中存入的 `ThreadLocal` 时间取出来，然后呢**清空一下这个局部变量**。

> **易错点**：这里咱们使用了线程池，如果你不清空的话，下个线程就会获取脏数据。这是线程池 + 线程局部变量组合使用时最容易踩的坑。

接下来它记录了任务日志的对象：有任务名称、任务分组、任务的目标字符串、开始时间、停止时间，然后计算一下此方法的耗时时间；还有如果该任务有异常的话，记录下任务的失败标志并设置异常信息；如果任务成功的话，就设置一下成功的标志。到这里，日志表的数据我们就封装完毕了。

封装完毕以后呢，注意看最后一行，熟悉吗兄弟们？——`SpringUtils`，这是 Spring 提供的工具类，然后从 IOC 容器当中获取一下 `SysJobLogService` 的实现类，调用它的 `add` 方法实现日志的添加。我们按住 Ctrl 键指到方法签名，方法实现调用了 `SysJobLogMapper`，实现了 SQL 语句的日志添加。这就是最后一步。

### 为什么记录日志的代码要写在抽象类里

这时候呢就有小伙伴们比较好奇了：那**为什么记录日志的代码要交给抽象类呢**？

是这样的：将来无论我们是并发执行还是不允许并发执行，这两个类在任务执行完毕以后，是不是都要记录日志？而记录日志是属于公共代码，请问各位，有必要在每个类当中都写一份记录日志的代码吗？那肯定是不需要的。所以我们就把这个公共代码抽取到了父类当中，这么做的好处——实现了代码的复用性。

### 反射：目标字符串怎么变成一次方法调用

我们回到任务抽象类当中，重点来看 `doInExecute`，它就是来执行具体任务的，而这个方法是一个**抽象方法**。看具体的执行——我们说了有两个子类，一个是允许并发的，一个是不允许并发的，而默认情况下是不允许并发的。

底层呢调用了 `JobInvokeUtil` 这个工具类来执行此任务。我们看一下方法的细节，首先呢我们来获取一下**调目标的字符串**——这个字符串有两种类型：

- **第一种是 Bean 的调用类型**，格式是「Spring 的 Bean 名称 + 点 + 方法名 + 方法参数」，例如 `ryTask.ryParams('ry')`；
- **第二种格式**是「包名 + 类名 + 方法名」，通过反射来调用。

这个字符串大家还有印象吗？就是我们前面讲 `invoke_target` 时说的那两种格式。但无论是哪种方式呢，我们都需要把这三个部分取出来：**`beanName`、方法名称以及方法参数**。

接下来就是对 `beanName` 的判断了，其实判断方式非常简单：如果你传递的 `beanName` **一个是没有包含点的**，那就是 Spring 容器的名称；另外一个是**包名类名**，中间以点分隔的。

那么如果不是类名的话，我们就从 Spring 容器当中来获取 Bean 的实例——这里用到了 Spring 的工具类 `SpringUtils` 获取实例，获取实例以后呢，底层通过反射来执行此方法。

那么如果是 Bean 的实例呢，来看这 `Class.forName`，熟悉吗兄弟们——这不就是来获取当前类的字节码对象；再通过 `getDeclaredConstructor` 获取它的构造器，`newInstance` 来实例化对象，拿到这个 Bean 再通过 `invokeMethod` 调用此方法。

> **提示**：`Class.forName` → `getDeclaredConstructor` → `newInstance` 这一套是标准的反射三连，作用是**运行时才决定要创建哪个类**，所以填在数据库里的那个类名甚至不需要在编译期被引用。这正是定时任务能「动态添加」的底层原因。

那调用细节呢，我们来看一下：这里呢我们也对方法的参数做了一个判断。**如果传过来参数数组不为空，且数组长度大于零**，那么就表示此任务方法是有参数的，所以我们在通过反射执行方法时呢，会传递对应的参数；如果数组为空，或者数组的长度小于等于零，那么我们就会获取它的**无参方法对象**，调用它的无参方法来执行。对于我们目前的案例来说，执行的就是这个无参方法。

一旦方法执行完毕之后呢，那么最后一步呢就会通过抽象类的 `after` 方法来记录当前任务的日志，并把它保存到数据库当中。

### 回头再看这两条链路

好，到这里定时任务的创建和执行流程我们就过完了。这一段功能涉及的类比较多，我们来盘一下：**定时任务的业务层实现类**、**`ScheduleUtils` 工具类**、**任务的抽象类和它的两个实现类**（上面那个是不支持并发的，下面那个是支持并发的），最后一个是 **`JobInvokeUtil`** 来完成任务的执行操作，底层呢是反射实现的。其中还有一个 **`CronUtils`** 这个类呢，我们在下个小节给兄弟们来进行介绍。

前面这两条链路——操作日志的「注解 + AOP 切面 + 异步任务管理器」，定时任务的「启动钩子 + Quartz 调度 + 反射执行 + 抽象类复用」——串起来看，你会发现它们其实是同一套思路：**把横切的东西从业务代码里抽出来，交给容器和框架去统一处理**，业务代码只管写自己那一摊。

## 定时任务源码走查、Quartz 集群改造与数据权限入门
> 对应块：BLK33 | 覆盖分集：P113-P118 | 块标题（分集名）：《原理篇-24.定时任务-源码-新增任务》

刚才我们分析了在项目启动时，从数据库中查询任务的配置列表，创建出定时任务，并根据任务的状态来判断是否执行该任务的调度。那如果是我们新添加了一个任务呢？这个任务该如何处理呢？项目已经跑起来了，启动时那套扫库建调度的逻辑不会再跑一遍，所以新任务只能走另外一条路——从接口进来，一路走到被调度器接管。为了解答这个问题，我们来对这部分的源码进行分析。

前端代码的交互模式我们已经比较熟悉了，所以本次只关注后端逻辑，入口就在定时任务模块的 `SysJobController` 中。

### 新增一个任务，请求是怎么走完的

来看第一个方法，`add`，就是来做新增定时任务的。我们将前端输入的参数封装到请求体——任务的配置对象，简称为 `job`。

#### 控制器里的三道校验

该方法的第一步，我们使用了 Cron 工具类对用户输入的 Cron 表达式进行校验。如果咱们输入的语法格式不正确，它就会返回错误信息；如果格式没问题，接下来就是对目标字符串的一系列校验。

那什么是目标字符串呢？注意看这边有 `invokeTarget` 调用方法，写的就是调用目标字符串的内容。它的语法有几种小伙伴们是不是有两种？

- **对象名.方法名**：这个对象呢已经在 IOC 容器了，直接从容器里拿；
- **包名.类名.方法名**：底层通过反射来实例化对象，然后完成方法的调用。

> **结论**：调用目标字符串只支持本地任务的执行。也就是说 RMI 这种远程调用的协议它是不支持的，LDAP（轻量级目录访问协议）呢也是不支持的，HTTP、HTTPS 这种超文本传输协议呢也是不支持的。所以若依支持的任务调用方法仅仅是本地方法，不支持远程调用。

咱们再往下看这一行，他是要判断一下目标字符串是否存在违规的问题，而这个违规呢有一个常量，它提供了违规的字符。我们来看一下，按住 Ctrl 键点开，先来看提供了一个字符串数组——如果我们调用方法包含以下这些内容，抱歉，我们认为这是违规的。

> **易错点**：所以将来我们编写的任务代码呢，千万不要放到这些包下。大家能接受吧？

如果语法没问题的话，咱们继续往下走，来看最后一个白名单的校验。这里呢使用了 Schedule 工具类来判断下目标方法是否属于白名单，而这个白名单是什么呢？咱们打开 `isWhiteList` 这个方法的实现细节来分析一下。

首先方法的第一步，我们来获取调用目标的包名或类名，也就是说去除方法调用部分，相当于我们拿到了任务类。那么接下来呢，这一步是来判断当前的任务类是否是包名加类名组成的，如果是的话，下面就是来判断包名的白名单。这里提供了一个字符串常量，默认要求我们的任务类必须放到 `com.ruoyi.quartz.task` 包下。

还记得我们在介绍目录结构时曾经提到了，咱们的任务类必须放到这几个包下，正是因为白名单在这里面写死了。如果将来小伙伴们想把这些任务类放到其他的业务模块，比如说某个 manager 模块的包下面，那么你就可以在白名单的数组当中增加一个逗号，把该模块的包名写进去就可以了，实现任务类的扩展存放。这一点小伙伴们能接受吧？

好，我们再回到 Schedule 工具类。注意这部分咱们判断的是反射相关的是包名加类名组成，那如果我们写的是一个 bean 的名称，我怎么知道这个 bean 是否在白名单内呢？哎，其实很简单：首先呢，我们通过 Spring 的工具类来获取他的实例对象，底层呢也是通过反射——

```java
Object bean = SpringUtils.getBean(beanName);
String packageName = bean.getClass().getPackage().getName();
```

兄弟们看这个 `getClass`，是不是拿到当前类的字节码对象？再点 `getPackage` 获取它的包对象，再点 `getName` 获取包名，那么返回的结果呢，就是当前对象所在的包路径。然后我们再使用工具类做判断，你是否在白名单内、是否有违规字符串。如果合法的话，咱们会返回一个布尔值 `true`；如果不合法的话，返回一个 `false`。那么控制器就可以根据返回结果做判断，错误信息呢就会返回到前端。

#### 服务层：先落库，再建调度对象

如果是正确的，兄弟们来看这里：通过 `job.setCreateBy(...)` 来设置一下当前登录用户的名称，也就是说该任务是谁创建的；然后呢调用 service 实现新增。

service 的实现细节我们来看一下，按住 Ctrl 键找方法签名。在当前方法内，第一行，我们给初始化的这个任务配置对象把状态设置为暂停——也就是说，默认新增加的任务他是不会执行的。设置完毕以后呢，就调用了 Mapper 把它新增到数据库当中，返回的影响行数如果大于零，就表示新增成功了。

那很简单，我们使用 Schedule 的工具类——兄弟们看这行代码熟悉吧——来创建出定时任务对象，而工具类的实现细节呢，我们在上一个小节当中已经给兄弟们分析过了，所以这段代码看起来就比较简单了。最后呢，返回数据库的影响行数告诉前端新增成功即可。

整个流程串起来，其实就是这个样子：

```text
[前端] 新增任务表单
   |  POST，请求体 = SysJob（invokeTarget / cron 表达式 / 任务分组 / 状态…）
   v
[SysJobController.add(job)]
   |-- 1) Cron 表达式语法校验 --- 不合法 ---> 返回错误信息，结束
   |-- 2) 目标字符串校验
   |        RMI / LDAP / HTTP(S)  ---> 判违规（只允许本地方法）
   |        违规字符数组命中       ---> 判违规
   |        白名单校验 com.ruoyi.quartz.task ---> 不在白名单则判违规
   |-- job.setCreateBy(当前登录用户)      <- 记录是谁创建的
   +-- sysJobService.insertJob(job)
            |
            v
   [SysJobServiceImpl.insertJob(job)]
            |-- job.setStatus("1")          <- 新任务默认暂停，不执行
            |-- Mapper.insert(job) ---> rows
            +-- rows > 0 ---> ScheduleUtils.createScheduleJob(job)   <- 建调度对象
            |
            v
        返回 rows ---> 前端提示新增成功
```

一句话读图：整条链路是"校验 → 打标 → 落库 → 建调度对象"。任何一道校验不通过，任务根本进不了数据库；即便进了库，状态也是暂停，绝不会立刻跑起来。

所以小伙伴们掌握了 Quartz 的执行流程以后，再去看这个代码是不是就简单很多了？

### 拨一下开关，任务就启停

刚才我们在分析新增任务的源码时，发现了任务在初始化时是处于暂停的状态。如果我们想启动任务的话，可以在页面进行任务的开关控制，所以接下来我们对此功能源码进行分析。入口呢同样在定时任务模块的 `SysJobController` 中。

首先用户在前端进行开关操作时呢，我们就会向后台发送一个 PUT 的请求，而这个请求呢会携带两个参数：一是当前任务的 ID，二就是当前任务的状态——高亮呢是正常，置灰呢就是暂停。而我们的控制器呢通过 `SysJob` 来接收这个参数。

拿参数以后呢，方法第一步取出任务的 ID 进行查询，获取当前任务的配置信息；第二步，将前端的状态设置到任务的配置对象当中——注意 `0` 是正常，`1` 就是暂停；最重要的是第三步，我们调用服务层的方法，根据状态来决定该任务是启动还是暂停，最终呢返回结果到前端。

#### 业务层：按状态分流

找到 service 的签名，打开方法实现。第一行我们初始化了一个返回结果 `rows`，默认是零，然后根据业务操作进行处理。具体业务我们来看一下：首先呢获取了前端的任务状态进行判断——

```java
// 前端任务状态：'0' 正常（恢复执行），'1' 暂停
if ("0".equals(job.getStatus())) {
    rows = resumeJob(job);   // 恢复任务
} else {
    rows = pauseJob(job);    // 暂停任务
}
return rows;
```

如果前端传递任务状态为启动的也就是 `0`，那么我们就来调用方法执行恢复任务操作，并返回受影响的行数；如果前端传过来状态唯一表示暂停，那么我们就会去执行暂停任务的方法操作，并返回受影响的行数。无论是走哪一种分支，最终呢将结果返回到控制器当中。

#### 恢复与暂停的两条支路

咱们先来看一下恢复任务操作的。我们拿到了从数据库查询的任务配置信息，里面包含了前端设置的任务状态，然后呢我们取出任务 ID、任务所在的分组，并重新将状态设置为正常——这是一个重置操作。接下来我们执行了一个更新操作，就是把用户最新的状态给他更新到数据库。如果数据库更新成功了，注意看这一步当中，通过 Schedule 来恢复任务调度，这里呢我们传递了任务 ID 和 group 来获取任务的信息，那么他就处于正常的执行状态了，最终我们返回数据库的影响行数。这是从暂停到恢复执行的一个业务流程。

那么接下来呢我们再来看一下从正常到暂停的过程。找到方法实现，同样的，我们先获取当前任务的 ID 和任务的所属分组，再重新设置一下当前任务状态为暂停，把它更新到数据库当中。一旦更新成功了，兄弟们，返回的行数呢就会大于零，就会通过 Schedule 的调度器来暂停当前任务的执行，最终呢返回影响行数。

```text
                  前端开关（PUT：任务ID + 状态）
                              |
                 +------------+------------+
              高亮(正常)                置灰(暂停)
                 |                          |
            状态 = '0'                 状态 = '1'
                 |                          |
             resumeJob                   pauseJob
                 |                          |
      状态重置为正常并落库           状态置为暂停并落库
                 |                          |
            rows > 0 ?                  rows > 0 ?
                 | 是                        | 是
     ScheduleUtils.resumeJob        ScheduleUtils.pauseJob
          (传 jobId + group)            (传 jobId + group)
                 +------------+------------+
                              v
                   返回影响行数 -> 前端刷新开关状态
```

读图要点：不管走哪个分支，最终都会把最新任务状态更新到数据库；那么下次项目再重新启动时呢，就会根据最新的状态来判断是否执行此任务了。所以这个开关不是"临时开关"，它是**写进库里的任务定义**。

定时任务模块还有一些其他功能，比如说修改任务的配置信息、删除、仅执行一次，还有查看详情，这些代码的逻辑呢相对来说是比较简单的。我们已经掌握了初始化、新增和修改状态了，那么这一部分就留作课下作业：把这些源码的注释通过 AI 工具给它补全，并画出流程图。在做完这些以后，对你后期阅读其他框架的源码帮助是非常大的——你需要能够独立掌握阅读源码的这种能力，正所谓授人以鱼不如授人以渔。

### 单机模式的软肋，催生了集群

在之前的学习中我们了解了若一定时任务的源码，掌握了任务执行的基本流程，接下来我们一起来看一下 Quartz 的集群模式。首先我们来聊一下为什么需要 Quartz 集群。

在单机模式下，默认所有的 `jobDetail` 和 `trigger` 都存储在内存当中。这样做的好处呢是读取速度快，但缺点也很明显：一旦服务器故障，所有任务的数据呢就会丢失，这就是所谓的**单点故障**问题。还有，如果在一个高峰时段，比如说上午九点，我们需要触发 500 个任务，这将给服务器带来巨大的负载压力，这不仅影响性能，还可能引发服务中断。

为了解决这个问题，我们可以部署多个服务器节点，将任务信息存储到数据库当中，这样多个节点通过共享数据库来协调任务的执行，形成 Quartz 集群模式。这种方式呢不仅解决了单点故障，还能通过负载均衡来提升效率。

```text
        单机模式                              集群模式
  +------------------+              +---------------------------+
  | 节点 A（唯一）    |              | 节点A(8080)    节点B(8081) |
  | Quartz 调度器     |              | 调度器 A      调度器 B    |
  | jobDetail 存内存  |              +---+--------------+--------+
  | trigger   存内存  |                  |              |
  +--------+---------+                  v              v
           |                      +--------------------+-----+
           |                      |      共享数据库       |
           v                      | QRTZ_JOB_DETAIL      |
     服务器一挂，任务全丢          | QRTZ_TRIGGERS        |
     = 单点故障                    | QRTZ_CRON_TRIGGERS   |
                                  | QRTZ_SCHEDULER_STATE  |
                                  +--------------------+-----+
                                   心跳互相探测，谁空闲谁干活
```

读图要点：单机模式的任务信息在各自进程内存里，节点一挂任务就全丢；集群模式把任务信息整体搬进共享数据库，节点只是执行者。

集群模式的优势呢，一高可用：即使某个节点出现问题了，那么其他节点呢仍然可以正常运行。二呢负载均衡：我们可以将一个任务分散到不同的节点去执行，避免单个节点的过载。刚才我们提到了上午九点需要触发 500 个任务，而现在呢可以把这 500 个任务分给多个节点来工作，避免了单节点的负载压力问题。通常在生产环境中我们会部署多台服务器，所以采用集群模式呢也不会产生额外的成本。

### 集群里最核心的是数据库

那么在 Quartz 的集群当中，数据库扮演着核心角色。我们需要在数据库当中创建特定的表结构来存储任务信息，跟 Quartz 集群相关的一共有 **11 张表**。在基础篇我们已经简单了解过了，这里呢我们先来关注四张表：

| 表名 | 存什么 | 关键内容 |
| --- | --- | --- |
| `QRTZ_TRIGGERS` | 触发器的基本信息 | 触发器名称、所在分组、类型（cron）等 |
| `QRTZ_CRON_TRIGGERS` | cron 触发器的额外信息 | cron 表达式描述的时间规则 |
| `QRTZ_JOB_DETAIL` | 任务的详细信息 | 任务名称、分组、描述、任务类名、任务数据 |
| `QRTZ_SCHEDULER_STATE` | 调度器的状态信息 | 集群中每个节点的实例信息 |

第一张 `QRTZ_TRIGGERS`，它是用于存储触发器的基本信息，比如说触发器的名称、所在分组、类型等等，而若依默认推荐我们使用的是 cron 的类型，所以第二张表 `QRTZ_CRON_TRIGGERS`，它是用于存储 cron 触发器的额外信息，比如说 cron 表达式的时间规则。这是跟触发器相关的两张表。

咱们再往下看 `QRTZ_JOB_DETAIL`，它是存储任务的详细信息，比如说任务的名称、所在分组、描述以及任务的类名等等。当我们存储了 `jobDetail` 和 `trigger` 信息以后呢，还有最重要的 `QRTZ_SCHEDULER_STATE`，它是来存储调度器的状态信息的。在集群模式下，每一台服务器呢都是一个节点信息，在同一个集群当中，每一个节点的 ID 呢是具有唯一性的。

看完这四张表我们就清楚了：将单机模式当中的任务信息，从内存当中给它存到了数据库。除了这四张表，其他表的用途兄弟们课后呢仔细阅读了解一下。

### 三步把项目改造成集群

我们将在若依的项目中一起实现 Quartz 的集群模式，步骤非常简单，一共三步。

#### 导入 SQL 脚本

首先我们在 `sql` 目录下方找到 `qrtz.sql` 文件，这个文件呢包含了 Quartz 所需要的数据库表结构，我们需要将它导入到我们的数据库当中。这一步是为了让我们的定时任务能够在数据库当中存储，实现任务信息的共享。

若依默认提供了 Quartz 的集群脚本，右击选择打开，磁盘路径下的 SQL 目录复制一下，回到数据库客户端执行 SQL 脚本，把路径粘过来，执行成功。咱们来看一下，执行成功后当前数据库当中已经包含了 50 张表了，其中呢 `QRTZ_` 开头的有 11 张表。OK，到这里咱们第一步就搞定了。

#### 打开集群配置类的注释

接下来进入到 Quartz 模块的 `config` 包下，找到一个名为 `ScheduleConfig` 的配置类。在这个类当中你会看到一些被注释的配置项，我们需要将这些注释取消，启用 Quartz 集群的模式配置。

注意看该配置类呢我们现在属于注释的状态，这是一个定时任务的配置类。在单机部署情况下，我们建议删除此类和 Quartz 的数据库表，默认呢它是将任务信息存储到内存当中，所以效率是非常高的——这也是我们在上一小节给兄弟们介绍的。但是在生产环境下，我们要保证它的可用性和负载均衡，所以我们就需要将该配置类的注释给它打开，Ctrl+A 全选，把注释取消。到这里，咱们的第二步也就搞定了。

#### 复制启动节点，端口改成 8081

最后呢我们要将我们项目作为一个集群来启动，这可以通过 IDEA 来复制现有的启动类实现。将原有的复制一份，然后呢修改复制出来的启动类端口号，咱们默认原来是 `8080`，这里呢改为 `8081`，以确保每个节点能够在不同的端口上运行。因为我们现在呢只有一台电脑，所以在完成这三步以后，我们需要分别启动这两个节点，一旦启动成功，我们 Quartz 集群模式就成功运行了。

具体怎么做呢？注意看在菜单栏当中会显示启动类的名称，我们点击一下，这边呢有一个编辑配置，打开上方呢有一个按钮，这个按钮呢就是来做复制了。咱们在复制之前呢先给他改一个名称，原来叫若依 Application，那现在我们把它标记为节点一，加个杠一；接下来呢我们选中它点击复制，OK 我们复制了第二个节点，把第二个节点名称呢改为杠二。这是两个节点，但这两个节点启动时，他们这两个共用端口号呢都是 `8080`，在配置文件已经指定好了，所以就会造成两个节点同时启动端口号冲突的问题。

所以我们需要在 2 号节点的位置重置一下项目启动端口，而重置的选项呢就是环境配置当中，咱们增加一个启动参数来写一下：

```text
-Dserver.PORT=8081
```

那么该节点启动时呢就会重新加载端口号为 `8081` 了，而一号节点呢是 `8080`，这样就可以在一台电脑来模拟两个节点了。

> **易错点**：我第一次写这个参数的时候把 `port` 的单词写错了，结果 2 号节点启动失败，日志直接报 `8080 端口已经被占用`。把这个单词改成全大写的 `PORT` 之后，再重新启动，两个节点就都正常了。

启动的时候 IDEA 右下角会弹出一个框，因为我们是 Spring Boot 工程，为了方便启动，它问我们是否打开 Spring Boot 启动配置的新窗口，那肯定是需要的，我们点新窗口。这样在新窗口当中我们看到了两个启动类，分别启动一下，先启动一号节点，选中第二个再启动 2 号节点，两个节点同时启动，大家耐心地等待一下。

#### 看效果：任务在节点间漂移

已经启动成功了，咱们先清空下日志。兄弟们，一号节点可以看到咱们的定时任务其实已经执行了，默认执行的是无参方法，因为之前我们开启了这个状态的开关，所以此任务呢先分配给一号节点执行；而 2 号节点启动好以后呢，咱们就把它重新分配给了 2 号节点来执行，这样的话一号节点就处于暂停的等待状态了。哪个节点在启动以后比较空闲，我们就把任务交给哪个节点来执行，我们就感受到了负载均衡的效果。

这时有小伙伴说，有没有可能两个节点同时执行啊？肯定是不会发生的，注意看一号节点的控制台输出呢，是没有再次打印执行无参方法的，而 2 号节点呢是每间隔十秒打印一次，所以是不会出现任务重复执行的问题，大家呢无需担心。

接下来呢我们来看一下数据库存储的任务信息。回到数据库客户端，还记得我上一小节给小伙伴们介绍的四张表吗？咱们先来看一下调度器的表，注意看现在调度器呢有两个节点信息，分别是一号机和 2 号机，来将 `jobDetail` 和 `trigger` 整合到一起完成任务的调度功能。

那接下来呢我们再来看一下 `QRTZ_JOB_DETAIL`，这里呢就会有三条记录，因为在我们的界面呢一共有三个任务的配置。而任务执行时呢，注意看兄弟们这边有一个 Job 的实现类——`@DisallowConcurrentExecution`，是不允许并发任务执行的实现类，底层呢会完成具体任务的实现逻辑。咱们再往下拉最后一个字段就是 `JOB_DATA`，这是一个二进制文件存储的，就是我们的任务信息。

咱们再来看一下触发器，找到 `QRTZ_TRIGGERS`，三个任务咱们对应的也是三个触发器，而这个触发器的规则我们来看一下，在这里 `TRIGGER_TYPE` 就是 cron 表达式的类型。所以我们再来看一下 `QRTZ_CRON_TRIGGERS`，这里呢就存储了我们三个任务的时间规则：每间隔十秒、每间隔 15 秒、每间隔 20 秒分别去执行。我们就将单机模式下内存存储的信息呢全部放到了共享数据库当中。

#### 模拟一次单点故障

接下来呢我们就来模拟一下单点故障的问题。首先我们的任务呢目前是交给 2 号节点来执行的，大家来观察一下，是不是间隔了十秒之后执行了一次控制台打印？OK，现在呢我来模拟机器故障，把 2 号节点呢给它关掉。已经关闭了，那么关闭之后呢，注意我们再来看下一号节点，咱们先清空日志。

其实集群当中呢，服务器节点之间会有一个心跳监听的过程，当一号机监听到 2 号机挂掉了，那么一号机就会担任执行此任务的节点，保证任务呢可以正常地执行，从而避免了单点故障的问题，提高了系统的可用性。这一点小伙伴们能接受吗？

至此三步全部完成：SQL 脚本让任务信息有地方共享，配置类注释把单机切换成集群，复制启动类造出第二个节点。启动完成后，到 `QRTZ_SCHEDULER_STATE` 表里就能查看到这两个节点的实例信息。

### ScheduleConfig：集群是怎么被配置出来的

接下来我们对 Quartz 配置类的源码进行介绍。首先若一定义了一个名为 `ScheduleConfig` 的配置类，使用了 `@Configuration` 注解，这个注解告诉 Spring 容器：这个类里面呢有些 Bean 需要被特别加载。

类当中呢有一个方法就是用于创建 `SchedulerFactoryBean` Bean 的，创建好的对象通过方法进行返回，交给了 IOC 容器，然后呢给他设置了一些配置信息。首先方法从 IOC 容器当中呢获取了 DataSource，也就是我们的数据源，然后把它设置给了 `SchedulerFactoryBean`，这样 Quartz 就可以使用数据库来存储任务和触发器的信息了。接下来呢就是配置了 Quartz 的一系列属性参数，我们创建了一个 `Properties` 对象，然后进行了 put 的赋值。

```java
// 集群身份：实例名称必须一致，机器中所有节点才知道它们是一伙的
props.put("org.quartz.scheduler.instanceName", "RuoYiScheduler");
// 集群身份：实例 ID 在同一个集群中必须唯一，AUTO = 计算机名 + 时间戳，由 Quartz 自己生成
props.put("org.quartz.scheduler.instanceId", "AUTO");

// 线程池：用线程来执行每个节点的任务，从而提高效率
props.put("org.quartz.threadPool.class", SimpleThreadPool.class.getName());
props.put("org.quartz.threadPool.threadCount", "20");
props.put("org.quartz.threadPool.threadPriority", "5");

// JobStore：单机模式存内存，这里改用数据库存储 job 与 trigger
props.put("org.quartz.jobStore.class", JobStoreTX.class.getName());
// 开启集群
props.put("org.quartz.jobStore.isClustered", "true");
// 心跳检测间隔，单位毫秒
props.put("org.quartz.jobStore.clusterCheckinInterval", "15000");
// 错过触发时间的判定阈值与一次最多补处理的数量
props.put("org.quartz.jobStore.misfireThreshold", "12000");
props.put("org.quartz.jobStore.maxMisfiresToProcessAtATime", "10");

// 事务隔离级别，MySQL 最高级别，防止任务之间出现脏读、不可重复读或幻读
props.put("org.quartz.jobStore.txIsolationLevelSerializable", "true");
// 我们的数据库如果使用的是 SQL Server，请把这一行注释打开
// props.put("org.quartz.jobStore.driverDelegateClass", "org.quartz.impl.jdbcjobstore.SQLServerDelegate");
// 定时任务相关的表前缀
props.put("org.quartz.jobStore.tablePrefix", "QRTZ_");
```

#### 集群身份：名字要一样，ID 不能一样

第一个参数是集群实例的名称，我们设置的是统一名称，要求是在同一个集群当中，多个节点该实例名称必须是一致的，这样机器中的所有节点就知道它们是一伙的了，从而做到实现负载均衡的效果。

第二个是集群实例 ID，我们设置参数值为 `AUTO`，而这个实例 ID 呢在同一个集群当中多个节点必须是唯一的，这样每个节点呢就可以被区分出来，谁执行任务、谁不执行任务。而这个 `AUTO` 呢就是让 Quartz 自己来生成一个独一无二的 ID，生成格式呢就是计算机名加时间戳。

回到数据库看这里就很直观了：`QRTZ_SCHEDULER_STATE` 表里，左侧是集群名称（若依 Scheduler），`INSTANCE_NAME` 列则是计算机名 + 毫秒值。在上一个小节当中呢我们运行了两个实例，所以这边呢显示两个独一无二的 ID，而左侧呢就是集群的名称。

#### 线程池与 JobStore

这三个参数是线程池的配置，在集群当中呢，我们使用线程来执行每个节点的任务，从而提高效率。而线程池我们采用的是 `SimpleThreadPool`，默认的线程数呢是 20，而每个线程的优先级呢我们设置为五，它也是默认值。那么这个设置的范围呢在 1~10 之间，我们设置五就够了，不要跟那些主业务线程呢来竞争优先级。

好，咱们再来看 JobStore 的配置。原来我们单机模式呢是将 job 和 trigger 信息存储到内存当中了，而在这里呢我们采用数据库来存储——请你们来看一下这个本地数据源 JobStore，用来存储我们的 job 和 trigger 信息，所以我们在上个小节就可以看到多个节点之间通过数据库来共享任务的信息。

#### 集群的三个关键参数

首先是第一个参数呢是开启集群。第二个参数呢是心跳的间隔时间，单位呢是毫秒，这边写的是 `15000`，也就是 15 秒，它就是集群各个节点来检测对方是否还活着的间隔时间。所以当第一个节点挂掉以后呢，15 秒之后我们发现这哥们没有给我们返回信息，我们认为你挂机了，你的任务就可以交给我来执行，从而解决单点故障的问题。

还有 misfire 的处理，它指的是任务错过了触发时间该怎么处理呀。我们在页面当中呢都设置了执行策略：有立即执行、仅执行一次，还要放弃执行。如果你配置了立即执行或仅执行一次，那么在恢复以后呢我们最多呢可以同时处理十个 misfire 的数量。

再往下看，还有事务的隔离级别，而这个级别呢叫 `SERIALIZABLE`，也是 MySQL 数据库最高的隔离级别，来防止各个任务之间出现脏读、不可重复读或幻读的问题，保证了执行任务的一致性。如果我们项目数据库呢使用的是 SQL Server，请把这一行注释打开。此外还指定了 misfire 的时间间隔，这边呢是 12 秒，还有 Quartz 相关的表前缀呢都是 `QRTZ_`。

最后呢，把这些配置参数设置到该 `SchedulerFactoryBean` 对象当中。我们继续往下看，这里呢我们还为 Quartz 调度器设置了一个名称，并设置了延迟启动，还要设置上下文的信息，同时呢也允许它更新已有的 job，而不需要删除再重新创建了——那这种效率呢会提高一些——然后开启自动启动。最后，若一把配置好的 `SchedulerFactoryBean` 实例返回，这样 Spring 就可以用它来启动和管理 Quartz 的调度器了。

通过这些步骤，若依不仅让 Quartz 在集群模式下运行起来，还确保了我们定时任务能够在多个节点之间高效稳定地执行，提高了系统的可用性和容错性。

那我们先来看第一小节功能介绍。在我们深入学习数据权限控制之前，让我们先来思考一个实际开发中经常遇到的关键问题：**如何确保用户只能访问他们被授权查看的数据呢？** 这个问题的答案就是数据权限控制。

### 为什么数据权限非有不可

小伙伴们想象一下，我们有一个大型的集团公司，旗下呢有多个子公司和部门。大家来看一下若依科技，下面有深圳总公司和长沙分公司等等。那么每个部门，比如说市场部和财务部都有自己的敏感数据，我们肯定不希望一个部门的员工能够访问另一个部门的敏感数据，对吧？

这时呢可能会有同学问，为什么我们如此重视数据权限控制呢？原因很简单：要保护敏感信息。数据权限控制呢就像一把锁，防止敏感数据呢泄露给未授权的人员，确保信息的安全。

为了方便理解，我们再来看一下数据权限的应用场景。第一个呢是**部门级别的权限**，比如说市场部的员工呢应该只能访问到市场部门的销售数据，确保他们只能触及自己部门的信息。还有**公司级别的权限**，子公司的经理呢可能需要有更广阔的视野，需要查看整个子公司的数据，以做出战略和决策。还有**跨部门的权限**，他们可能需要有更全面的数据访问权限，以便跨部门或跨子公司进行管理和决策——比如说可以查看深圳总公司的某几个部门，也可以查看长沙分公司的多个部门。

通过数据权限控制，我们不仅保护了公司数据的安全，还确保了数据的合理利用和流程的顺畅。

### 五种数据权限范围

在系统当中，权限分配主要依赖于角色，每个角色可以被赋予不同的菜单权限和数据权限。其中菜单权限就是我们之前所说的 RBAC，而数据权限就是我们接下来要讲的，用户通过他们的角色来继承这些权限，进而决定他们能够访问哪些系统资源。

目前若依系统支持以下五种类型的权限类型：

| 权限类型 | 含义 | 典型场景 |
| --- | --- | --- |
| 全部数据权限 | 无限制地访问所有的数据 | 超级管理员、公司高管 |
| 自定义数据权限 | 用户可以根据自己的需求设定访问特定的数据规则 | 跨公司或跨部门的数据访问 |
| 本部门数据权限 | 用户只能访问自己所在部门的数据 | 部门内部协作 |
| 本部门及以下数据权限 | 用户可以访问自己所在部门及其下属部门的数据 | 管理层级员工 |
| 仅本人数据权限 | 用户只能访问和操作自己的数据 | 保护个人隐私，实现数据隔离 |

还有一点需要注意一下，小伙伴们在默认情况下，超级管理员用户指的是 `admin`，他拥有所有的数据权限，而判断条件呢就是 `userId` 等于 `1`，就可以查看所有数据了——这是为了便于系统的管理和维护。

### 数据权限的骨架，是三张表之间的关系

若依的数据权限设计，说到底就是靠**用户表、角色表、部门表**三张表之间建立的关系来实现数据访问控制的。

先说第一条线：**用户表和部门表是一对多**。一个部门可以有多个员工，所以我们添加新用户的时候一定会指定它属于哪个部门；在用户表里有一个 `dept_id` 作为外键，指向部门表的主键。

第二条线：**用户表和角色表是多对多**。一个用户在创建时可以分配多个角色，一个角色也可以被多个用户使用。多对多没法靠一张表的外键表达，所以必须有一张中间表，这张表有两个外键字段，分别是 `user_id` 和 `role_id`，分别指向用户表和角色表的主键。

第三条线就是关键了：**角色表和部门表之间也是多对多**。

```text
   sys_dept（部门表，自关联：dept_id / parent_id）
      ▲     ▲
      │     │
      │     └────────────────────┐
      │ dept_id（一对多）         │ dept_id（多对多）
      │                          │
   sys_user（用户表）         sys_role_dept（角色-部门中间表）
   user_id(PK)  dept_id(FK)      role_id  │  dept_id
      │                              │ role_id
      │ user_id                       ▼
      │ 多对多                   sys_role（角色表）
      │                        role_id(PK)
      │                        data_scope   ← 数据权限范围 1~5
      │                              ▲
      └───► sys_user_role ──────────┘
           （用户-角色中间表，user_id | role_id）
```

> **为什么非要加角色-部门这张中间表？**
> 因为目前我们能做到的，只有本部门、本部门及以下、仅个人这三种范围。要做**自定义数据权限**，光靠用户表上那个 `dept_id` 是不够的——一个角色可能对应好几个部门，这时候就必须靠角色和部门的中间表来确定用户能访问的部门范围。用户根据自己的角色 id 去查这张中间表，拿到对应的部门列表，数据范围自然就筛出来了。

这些关系建立起来之后，用户登录系统时就能拿到登录用户的信息，包括**用户 id 和部门 id**，然后根据这个用户所分配的角色来控制数据访问的权限：

| 范围值 | 数据权限类型 | 范围从哪里来 |
|---|---|---|
| 1 | 全部数据权限 | 不受任何限制 |
| 2 | 自定义数据权限 | 角色 ↔ 部门中间表（可跨部门、跨子公司） |
| 3 | 本部门数据权限 | 用户表里的 `dept_id` |
| 4 | 本部门及以下数据权限 | 用户表里的 `dept_id` + 部门表父子关系 |
| 5 | 仅本人数据权限 | 用户表里的 `user_id` |

这里有一个特别容易被忽略的点：**「仅本人」这一种，注释里根本没体现出来**。它的范围值是 5，看到这里先记下来，后面切面里会专门回来对账。

最后补一句：只要一个用户拥有**全部数据权限**，那他就不会受到上面这三张表的数据范围限制，可以查询所有的数据。

### 两个别名，就是两个开关

表关系搞清楚了，接下来看实现数据权限的**代码入口**：在需要做数据权限控制的方法上面，加一个 `@DataScope` 注解。系统就会自动根据当前用户的登录信息，拼接出数据范围的 SQL 条件，实现数据筛选和过滤。

这个注解里有两个关键属性：

- **`deptAlias`**：部门的别名，对应的属性值是 `d`（dept 的缩写）。如果我们只想筛选特定部门的数据，就用它。
- **`userAlias`**：用户的别名，对应的属性值是 `u`（user 的缩写）。如果我们只想筛选特定用户的数据，就用它。

> **规则**：如果两个属性都写上，系统就知道我们需要完整的五种类型数据权限控制；只写部门别名，就只对部门维度做筛选。

这两个开关的差别，我们直接到真实代码里对比着看。

**角色的实现类** `SysRoleServiceImpl`，第 53 行的查询角色列表方法：

```java
@DataScope(deptAlias = "d")
public List<SysRole> selectRoleList(SysRole role) { ... }
```

注意，它**只指定了部门的别名**。

**用户的实现类** `SysUserServiceImpl`，第 72 行的查询用户列表方法：

```java
@DataScope(deptAlias = "d", userAlias = "u")
public List<SysUser> selectUserList(SysUser user) { ... }
```

这个方法**两个属性都写上了**，所以它支持我们前面提到的全部五种类型。

现在回头解释那个扎眼的画面。若依用户的角色当时被我们设置成了**仅本人**的数据权限。也就是说，这个角色只希望看到当前用户自己的数据。而部门列表的查询方法上，`@DataScope` 只指定了 `deptAlias`，**没有设置 `userAlias`**。方法层面压根不支持按用户维度过滤，那用户维度这条要求就落不下去——最终部门列表什么都查不到。

所以那一屏的空白，不是 bug，是注解属性和方法需求对不上。

### Mapper 层的那把钥匙

不过光在 Service 方法上挂个注解还不够。数据权限要在 **Mapper 层**进一步过滤数据。怎么把切面算出来的条件送到 SQL 里去？

回到 MyBatis 的映射文件里，答案就是一个占位符：

```xml
<!-- 最后一行的位置 -->
AND ${params.dataScope}
```

`${}` 花括号在实战篇我们都用来**接收前端参数**，这里却用来**获取 `params` 里的 `dataScope` 这个动态 SQL 语句**——它的作用就相当于在一个 `select` 语句后面，拼接一个 `and` 条件的语句来实现查询的限制。

那这里 `params` 是哪来的？往下看实体类，我们能看到它继承了一个 `BaseEntity` 基类：

```java
public class SysUser extends BaseEntity {
    ...
}
```

而 `BaseEntity` 里有一个 `params` 的 `Map` 集合属性——**它就是继承自 `BaseEntity` 的那个参数 `map` 集合**。

对应关系很清楚：

- 这个 `params` 对应的是 `map` 集合；
- `dataScope` 就是用来存储 SQL 条件的 key；
- 它的值，就是我们稍后拼接好的 SQL 语句。

到这儿可能就有小伙伴要问了：**实战篇我们用 `${}` 接前端参数，那这里用 `${}` 拼 SQL，会不会存在 SQL 注入的风险？**

> **这个问题的答案是：不会。**
> 因为我们数据权限的 SQL 拼接是在**后端**进行的，不是前端传进来的，所以不需要担心前端的 SQL 攻击。而且切面里在拼之前还会**先把 `dataScope` 强制置为空串**，等于又上了一道保险。具体实现细节，等我们拆切面的时候就能看到。

#### 拼接前与拼接后的对比

光看代码不过瘾，我们到数据库客户端里跑一遍。我提前准备了两段 SQL：上面那段是用户管理的查询，是**未过滤数据权限**的情况，直接执行，查询出所有用户的信息。

下面那段同样是用户管理查询，但我们**增加了新的条件**，实现已过滤数据权限：

```sql
-- 未过滤：所有人的登录信息都能查出来
SELECT ... FROM sys_user;

-- 已过滤（拼接后的实际形态）
SELECT ...
FROM sys_user
WHERE ...
  AND dept_id IN (
      SELECT dept_id FROM sys_role_dept WHERE role_id = 2
  );
```

执行结果只返回了两个员工信息——若依和黑马彭于晏。数据权限确实生效了。

那它到底是怎么过滤的？注意我们增加的那个 `and` 用于拼接后面的 SQL 语句，通过它实现了一个**嵌套条件查询**。查的这张表就是**角色-部门的中间表**，查询条件是角色的 id，表示根据当前登录用户来获取他的角色，查这个角色所对应的部门 id。这个部门 id 可能是多个，所以外面以 `in` 的方式进行条件筛选，做到了数据权限的过滤。

结合刚才表关系的分析，同学们思考一下，它应该属于**哪一种类型**的条件过滤？

```text
 角色-部门中间表 + 角色 id  →  自定义数据权限（范围值 2）
```

> **结论**：想在 SQL 里用 `IN (SELECT ...)` 关联中间表来筛部门，那就必须是自定义数据权限，因为只有这一种依赖角色-部门中间表。

#### 实现数据权限的两个前置条件

在真正动手改代码之前，有两个硬性要求必须先记住：

1. **只有继承了 `BaseEntity` 的实体类，才能使用数据权限控制。** 因为 SQL 语句会存储在这个实体类的 `params` `Map` 集合属性当中，你没有继承，自然就取不到。
2. **如果业务表要实现数据权限，这张表就必须包含 `dept_id` 和 `user_id` 两个字段。** 只有这样，才能根据部门或用户来筛选数据。

这两个前置条件，在后面的业务改造里会直接决定我们改不改得动。

### 注解本身：三个元注解、三个属性

注解用得这么爽，我们总得看看它长什么样。`@DataScope` 放在 ruoyi 的 `common` 模块下的 `annotation` 包里，打开它的定义，上面有三个**元注解**：

| 元注解 | 作用 |
|---|---|
| `@Target(ElementType.METHOD)` | 指定使用位置，**仅在方法上**，其他位置不能用 |
| `@Retention(RetentionPolicy.RUNTIME)` | 保留策略为运行时，程序运行时可被反射读取 |
| `@Documented` | 会被 Java 的 doc 工具记录，生成文档时包含该注解信息 |

> **易错点**：`@Retention` 必须是 `RUNTIME`。否则注解在编译期就没了，AOP 那套反射扫描全白干——这是自定义注解+AOP 最经典的一个坑。

下面看它的属性。前两个我们已经很熟了：**部门别名**对应 `d`，**用户别名**对应 `u`；两个都用上，表示五种数据权限类型我们都要控制。

第三个属性是**权限字符串 `permission`**，它可以用于匹配多个角色、符合要求的权限。

这什么意思呢？简单来说：如果登录用户有三个角色，其中两个角色没有访问此方法的权限，这个方法还有没有必要做数据范围筛选？肯定没必要。

还记得我们介绍 RBAC 权限控制时，Controller 方法上是不是有一个权限字符串？打开查询用户列表的 Controller：

```java
@PreAuthorize("@ss.hasPermi('system:user:list')")
```

这个 `permission` 指的就是它——**访问当前方法的全字符 `system:user:list`**。

那新的问题来了：`@DataScope` 里我们发现**并没有指定 `permission` 属性啊**，那怎么做到限定呢？

看 `@ss.hasPermi` 这个默认情况下走的就是 `PermissionService`。点进 `hasPermi` 方法，有一行关键代码：**把权限信息设置到上下文当中，供后续的操作使用**。用的就是 `PermissionContextHolder` 这个对象——**它是一个线程局部变量（ThreadLocal）**。我们把 `system:user:list` 这个权限字符串存进当前线程的局部变量里，稍后在数据权限的切面类中，通过上下文来获取权限字符串，就可以进行角色权限的一系列校验了。

> **结论**：所以 `@DataScope` 里不设置 `permission` 是完全没关系的，因为默认情况下 `hasPermi` 已经把权限串存进上下文对象了。这个先记住，切面里还要用。

### 切面 DataScopeAspect 的一次完整处理

拦截这个注解的切面类叫 `DataScopeAspect`，在 ruoyi 的 `framework` 模块下。

先看这个类的骨架：类上加了 `@Aspect`，表示这是一个切面类，交给 IOC 容器；下面定义了一些属性常量，比如**全部数据权限**对应的值是 1，还有**自定义数据权限**、**部门数据权限**等等，这些常量代表了不同的数据权限范围，从 1 到 5。还有最后一个常量指的是**数据权限过滤关键字**——说白了就是我们 `BaseEntity` 的 `params` `Map` 集合里指定的那个 key，叫 `dataScope`，而它的值就是我们稍后需要拼接的 SQL 过滤条件。

真正干活的方法叫 `before`，方法上加了 `@Before`，表示它是一个**前置通知**，会在被 `@DataScope` 注解的方法执行之前触发，切点表达式就写在注解里。

整个方法分成两大步。

#### 进门先扫地

第一步是**清理数据范围，也就是清理数据权限的过滤条件**。

具体做法是：拿到切点方法的第一个参数——切点方法就是我们要执行的用户列表查询那个目标方法，比如 `SysUser` 对象——判断它不为空，并且属于 `BaseEntity` 类型；如果是，就对子类做一个**强转**，转成父类，然后拿到 `getParams()` 这个 `map` 集合，最后一步：

```text
params.put("dataScope", "")     ← 强制置为空串
```

这么做的目的，就是为了**防止 SQL 注入**。

所以前面我们提到「即使使用 `${}` 做拼接，也不用担心 SQL 注入」，具体细节就在这里：**即使有人在前端恶意地拼接了 SQL 语句，我们也会在这一步把它置为空串**，防止 SQL 注入，保证系统的健壮性。

> **这一行代码同时回答了两个问题**：为什么实体类必须继承 `BaseEntity`（因为要强转），以及为什么 `${}` 是安全的（因为有人帮我们清了场）。

#### 超管直接放行

清理完之后，回到业务主线，第二步是**设置数据范围的过滤条件**。

第一步先获取当前的登录用户，比如说我登录的是若依用户。拿到用户的基本信息之后，注意看下一行：**判断他是否是超级管理员**。

小伙伴思考一下，如果他是超级管理员，他应该拥有访问所有数据的权限，那还需要进行数据范围过滤吗？不需要了。所以切面方法就**提前结束执行**了，直接进入 mapper 层执行 SQL 语句。

而 mapper 的那段 SQL 里面，最后这个位置**并没有拼接任何参数**，也就不会进行数据范围的过滤，相当于查询所有数据。

#### 两道关卡：跳过重复的，跳过没权限的

如果不是超级管理员，我们就要拿到当前用户所分配的角色集合去遍历。

先准备两样东西：一个是 `SQL` 字符串拼接对象（现在是空串），用于稍后拼接数据范围条件；另一个是**数据范围类型的集合**，用来存储已经添加过的数据范围类型，值就是 1 到 5。

然后开始遍历角色。遍历这一圈，**两道关卡必须先过**。

**第一道关卡：类型是「自定义」并且集合里已经有了。**

我们判断一下：当前数据范围的类型是不是自定义类型，**且**已经被添加过了？

如果是，说明我们前面已经有一个角色，它的数据范围已经是自定义类型了，已经添加过了。现在遍历到第二个角色，它的类型也是自定义的，还有没有必要再重复添加一遍？答案是不需要的。我们遵循**第一添加者优先原则**——哪个角色先设置了，我们就以哪个角色为准，后设置的就不需要了。所以这里会做一个 `continue` 的跳过，直接遍历下一个角色。

**第二道关卡：当前角色的权限列表里不包含目标方法的权限字符串。**

一个角色是有多个权限列表的（这个我们之前在 RBAC 时分析过）。如果它压根就不包含 `system:user:list`，也就表示该角色压根就没有权限访问此方法，那我还有没有必要进行数据权限过滤？肯定不需要。所以也跳过本次循环，不再拼接 SQL 语句。

#### 五种数据范围，五段 SQL

两道关卡都过了，才轮到真正拼条件。

**类型 1｜全部数据。** 这个类型的权限等同于超级管理员，所以我们会**清空之前拼接的 SQL 语句**，并把当前角色的权限类型存入集合，然后 `break` 跳出**整个**循环——注意是整个循环，即使你后面还有新的角色，我们也不再去拼接条件过滤了，就是来查询所有。清空 SQL 拼接的目的，是为了防止之前角色已经拼进去的条件过滤；清空之后默认就相当于查询所有了。

**类型 2｜自定义。** 自定义在上个小节介绍过了，它可以做到跨子公司、跨部门——通过角色直接关联多个部门 id。拼接用的是 Spring 的工具类来完成，两个花括号占位符：第一个设置部门别名，第二个设置当前角色的 id：

```sql
 AND #{deptAlias}.dept_id IN (
       SELECT dept_id FROM sys_role_dept WHERE role_id = #{roleId}
 )
```

实现了嵌套查询：以角色 id 查这个角色关联了哪些部门，可能是多个，所以外层的部门 id 通过 `in` 来筛选。假如关联了五个部门，OK，那我们就查这五个部门的数据，实现了数据范围的过滤。

> 这段 SQL 眼熟吗？正是我们在数据库客户端里跑的那一段嵌套查询，一模一样。

**类型 3｜本部门。** 这个拼接更简单了，同样两个占位符，第一个是部门别名，第二个就是当前用户的部门 id：

```sql
 AND #{deptAlias}.dept_id = #{deptId}
```

以当前用户的部门 id 作为条件，拿到的结果都是本部门的数据。

**类型 4｜本部门及以下。** 这里会包含**两个**条件——一本部门的，二子部门的。这一段有三个占位符：第一个还是部门别名，第二个是嵌套 SQL 语句里部门的 id（你得先查是不是本部门）；跟上面类似，但后面多了一个函数叫 **`find_in_set`**：

```sql
 AND #{deptAlias}.dept_id IN (
       SELECT dept_id FROM sys_dept
       WHERE dept_id = #{deptId}
          OR find_in_set(#{deptId}, ancestors)
 )
```

**类型 5｜仅本人。** 它的值就是 5。判断的是**当前注解当中有没有用户别名**：

- 如果**有**用户别名，就表示你要以当前用户 id 作为条件查询，只能查询仅本人的数据，做到了个人数据的隔离。尤其是像市场部的销售数据，是不是每个人只能看自己的。
- 如果**当前注解当中并没有用户的别名**，就表示该数据不需要与用户隔离，但你传的类型还是「仅本人」，那怎么办？这样我们就把 id **设置为零**。设置为零，就表示**不查询任何数据**。

现在回到最开始那个空白的部门列表：方法上面只有部门别名，没有用户别名，但当前用户的角色是「仅本人」，那部门列表这边拼接的条件就是 `dept_id = 0`，表示什么都不让查。**谜底揭开了。**

每一轮遍历的最后，把当前角色的数据范围类型存入集合，还有角色就进行下一轮遍历。

遍历结束之后还有两个收尾判断：

**如果数据范围类型的集合是空的**，表示当前用户所有角色都不包含传递过来的目标方法的权限字符串。简单来说就是，你当前登录用户的所有角色权限集合都没有包含 `system:user:list`，也就表示你所有角色都没有访问此方法的权限。那还需要进行数据权限过滤吗？不需要。但我们这里**还是把部门 id 设置为零**，啥也查不到。

**如果集合不为空**，下面就要判断一下 SQL 拼接字符串是不是空。如果不是空的话，这段代码熟悉吗？**获取方法的第一个参数，判断它是不是 `BaseEntity` 类型，如果是强转为父类，就可以拿到 map 集合的方法进行 put 赋值**——左侧就是 `dataScope` 这个 map 的 key，右侧就是我们要拼接的 SQL 条件。

但请注意下面这一行 `add`，拼接时**通过 `substring` 过滤掉了前四位，只拿后面内容**。

那这前四位是什么呢？把我们每一段 SQL 都看一遍，会发现它们**都有 ` and ` 左右两侧的空格**——这些是不包含在 SQL 语句内的，我们要把这四个字符过滤掉，只要后面 `dept_id = 0` 这部分。拼接完以后，执行 mapper 语句时就相当于拿到了 `and` 括号，后面跟部门 id 等于某一个值，最终完成了 SQL 的数据范围过滤。

### ancestors 与 find_in_set：为什么不用递归

刚才类型 4 里的 `find_in_set` 到底解决了什么问题，咱们必须掰开揉碎讲清楚。

先看部门表。部门表我们在基础篇就介绍过了，它是一个**自关联表**：左侧是当前部门 `dept_id`，右侧是部门的 `parent_id`，就建立了它们之间的父子关系。

来画张图解释一下。若依科技是公司的顶级部门，它的 id 是 100。为了防止若依科技的 `parent_id` 为空，我们指定了一个**虚拟部门**，部门 id 为 0，然后让若依科技去继承这个 `parent_id = 0`，就建立了一个根节点。往下，若依科技下面有深圳总公司和长沙分公司，这两个公司的 `parent_id` 都是 100，所以若依科技下方有两个子节点 101 和 102。101 是深圳总公司，它下方还有研发部、市场部、测试部、财务部、运维部等等，太多了，我们随便画三个：103 是研发部，104 是市场部，105 是测试部，它们的 `parent_id` 都指向 101。

```text
        dept_id = 0
        （虚拟根节点）
              ▲  parent_id
              │
        若依科技  100
              ▲
        ┌─────┴─────┐
    深圳总公司 101   长沙分公司 102
        ▲
    ┌───┼─────┬─────┐
  103   104   105   106
  研发部 市场部 测试部 ……
```

> 是不是有点似曾相识？没错，和我们之前讲过的菜单权限表是同一个套路。

形成这种树形节点以后它可以做到什么呢？比如当前登录用户属于深圳总公司，他的 `dept_id` 就是 101，我就可以以 101 为条件去查询它的子节点，拿到 103、104、105，而这些是属于我的子部门，子部门是不是也应该在我的数据范围内？那我就以 101、103、104、105 作为条件来筛选数据了。

**但这种筛选方式是有缺点的。** 比如 103 下方还有子部门，104 下方也有子部门，那一层层去找就要用到**递归**，而递归的效率是比较低的。那怎么办呢？

注意看，部门表里有一个字段叫 **`ancestors`，祖先的意思**。这个字段记录的是当前部门的**家谱**。

以 id 103 为例：103 的父节点是 101，101 的父节点是 100，100 的上面是 0——这就是当前节点的一个**家谱数**。而 `ancestors` 这个字段，就是记录它的家谱信息的。103 的 `ancestors` 存下来就是把根节点到它的父辈节点全部存了下来。通过这个字段，我就可以**一口气**把整条链路上的部门 id 全拿到。

```text
 dept_id  dept_name      parent_id   ancestors
------------------------------------------------------
 0        （虚拟根节点）      0        0
 100      若依科技          0        0,100
 101      深圳总公司        100       0,100,101
 102      长沙分公司        100       0,100,102
 103      研发部           101       0,100,101,103
 104      市场部           101       0,100,101,104
 105      测试部           101       0,100,101,105
```

好处就来了：`ancestors` 把此部门的上级部门 id 存成了一个**字符串列表**，然后我传递一个 101 进去——请问 101 有没有在这个字符串当中？答案是**在的**。那你就属于我的子部门，我的查询条件就会包含这个 103。以此类推，104 当中有没有包含 101？包含了，你也属于我的子部门；105、106、107 都包含了，那它们都属于我的子节点，查询条件就从 103 到 107 了。而 108 和 109 并没有包含这个 101，那么这些就会被过滤掉。

> **定义**：`find_in_set(str, strlist)` 的作用就是**在一个字符串列表当中查找一个特定的字符串**。比如右边的 `ancestors` 就是一个以逗号分隔的字符串列表，左边传入需要查找的特定字符，与右侧的字符列表进行比对，**存在返回真，不存在返回 `false`**。就这么简单。

这就是查找子部门的一个实现思路：**指定一个字符串列表去查找有没有特定字符串，有的话你属于我的子部门，没有的话就不属于，我们就进行过滤。**

> **一句话总结这一段**：数据库自带的字符串查找函数 + 一个「家谱」冗余字段，把递归查询压成了一次字符串匹配。这是典型的**用空间换时间**。

### 走一遍完整流程

到这儿，源码就算分析完了。我们回到笔记做个小结，把整个链路串一遍：

```text
 用户发起请求，访问一个加了 @DataScope 的方法
        │
        ▼
 ┌─────────────────────────────────────────────┐
 │ DataScopeAspect  @Before 前置通知            │
 ├─────────────────────────────────────────────┤
 │ ① 清理：BaseEntity.params.put(              │
 │      "dataScope", "" )        ← 防 SQL 注入  │
 │ ② 取当前登录用户                              │
 └──────────────┬──────────────────────────────┘
                │
        ┌───────┴────────┐
        │ 是超级管理员？   ├── 是 ──► 什么都不拼，直接放行
        └───────┬────────┘           ▼
                │ 否           Mapper 执行原始 SQL
                ▼                查询全部数据
   遍历当前用户的角色集合
                │
    ┌───────────┴────────────┐
    │ 关卡1：自定义型已添加？  ├─是─► continue（第一添加者优先）
    │ 关卡2：角色无此方法权限？ ├─是─► continue（没权限就不筛）
    └───────────┬────────────┘
                │ 都通过，按 1~5 拼 SQL
                │
    1 全部 → 清空已拼条件，break 整个循环
    2 自定义 → 部门id IN (角色id 查中间表)
    3 本部门 → 部门id = 当前用户部门id
    4 本部门及以下 → 本部门 + find_in_set(部门id, ancestors)
    5 仅本人 → 有用户别名拼 user_id；没别名就拼 0
                │
                ▼
   集合为空（所有角色都没权限）→ 部门 id 拼成 0
                │
                ▼
   SQL 非空 → params.put("dataScope", sql.substring(4))
              （substring 掉前置的 " and " 四个字符）
                │
                ▼
   Mapper 执行 SQL，${params.dataScope} 自动拼进来
                │
                ▼
        返回筛选后的结果集
```

所以整个机制就是：**通过 AOP 的切面技术，动态地根据用户的角色和权限来过滤数据**，确保了数据的安全性和合规性。

### 给登录日志做一次改造

有了整套理论，我们拿一个真业务练手。

#### 需求背景

我们系统里有一个**登录日志**的功能，记录了所有用户的登录信息。但并不是每个用户都有权限查看所有的日志——比如**普通用户只能查看自己的登录记录**。因此我们需要对现有的业务代码进行改造，根据用户的角色来控制数据的访问范围。

#### 第一步：给查询方法挂上注解

在登录日志 service 层的查询方法上面添加 `@DataScope` 注解，同时指定**部门和用户的别名**。到 ruoyi 的 `system` 模块下，`service` 包里的实现类中找到 `SysLogininforServiceImpl`，第 43 行到 46 行的位置就是查询登录日志集合的方法，在它上方添加注解：

```java
@DataScope(deptAlias = "d", userAlias = "u")
public List<SysLogininfor> selectLogininforList(SysLogininfor logininfor) { ... }
```

两个别名都指定上，这就开启了数据权限的控制。

#### 第二步：给表补上两个字段

在 `sys_logininfor` 登录日志表当中，新增 `dept_id` 和 `user_id` 两个字段，用于存储登录用户与用户和部门的关联信息。

添加方式有两种。一种是**图形化工具**：右击这张表 → Modify Table，里面会显示这张表原有的字段信息，点加号就可以指定字段名、字段类型、默认值和注释说明。

另一种是**直接写 SQL 命令行**：

```sql
ALTER TABLE sys_logininfor
    ADD COLUMN dept_id BIGINT COMMENT '部门id',
    ADD COLUMN user_id BIGINT COMMENT '用户id';
```

> `ALTER TABLE` 是修改表，`ADD COLUMN` 是添加字段，后面的 `COMMENT` 是注释。

那有小伙伴说：这条 SQL 我很久没写了，忘了怎么办？没关系，我们不是还有一个好助手吗——**通义灵码**。我们只需要把需求写成 prompt 提示词，它就可以自动帮我们生成 SQL 语句。最近没有使用通义灵码了，带兄弟们玩一下：

```text
你是一名软件工程师，请为登录日志表 sys_logininfor 添加 dept_id 和 user_id 两个字段，
这两个字段还要生成注释，类型应该是一个长整型（big int），最后帮我生成 SQL 语句。
```

按回车执行，它就开始分析提示词、帮我们生成代码了。下面出来的 SQL 语句我们已经分析过一遍了。**只要你把提示词写好了，SQL 语句记不住也没有关系。**

> **提示**：写 DDL 的提示词要交代清楚四件事——操作哪个表、加哪些字段、字段类型和注释、以及要什么形态（建表语句还是修改语句）。这已经成了新一代工程师必须掌握的技能之一，一定要勤加练习。

执行的时候还有个小插曲：直接粘贴到命令行执行会报错，提示**没有选中数据库**。因为命令要在目标数据库下执行，所以得先在命令行里选中对应的库，再重新执行，这就 OK 了。

#### 第三步：实体类补上两个属性

找到了表，就得找到对应的实体类。找到 `SysLogininfor`，往下拉，加上两个属性，一个用户 id、一个部门 id。因为 id 用 `long` 的话如果为空就没法判断，所以我们用包装类 `Long` 来写：

```java
/** 用户id */
private Long userId;

/** 部门id */
private Long deptId;
```

写完注释后，按回车通义灵码还会结合上下文帮我们补全。然后我们生成它的 get 和 set 方法：换行之后按 `Alt + Insert`，选择 getter 和 setter，把 userId 和 deptId 两个都选上，OK，get 和 set 方法就添加完毕了。

#### 第四步：映射文件从单表改三表

这是最重要的一步。在登录日志的 MyBatis 映射文件当中，我们通过动态 SQL 拼接实现数据范围的过滤。

这条 SQL 语句至少涉及到**三张表**的查询：登录日志表、部门表、用户表。所以 SQL 语句本身也得改造——现在是**单表查询**，我们要先查日志表，然后左外连接部门表，再左外连接用户表。

先把 `from` 关键字这部分换一行，给当前登录日志表设置一个别名，比如叫 `l`，然后 `left join` 左外连接部门表，别名 `d`，连接条件 `on` 是登录日志表的外键部门 id 等于部门表的主键；再换一行，同样 `left join` 用户表 `sys_user`，设置别名 `u`，连接条件是登录日志表的 `user_id` 外键等于 `user` 表的主键：

```sql
SELECT   l.user_name,
         l.ipaddr,
         l.login_location,
         l.browser,
         l.os,
         l.status,
         l.msg,
         l.login_time,
         u.user_id,
         d.dept_id
FROM     sys_logininfor l
LEFT JOIN sys_dept d ON l.dept_id = d.dept_id
LEFT JOIN sys_user u ON l.user_id = u.user_id
WHERE    1 = 1
```

> **注意**：三表查询以后，查询的字段当中是有可能**出现重名冲突**的，所以这些字段千万别忘了加表的别名。上半部分写的这些默认都属于日志表，所以要补上 `l.`；`u.` 是用户表的别名，`d.` 就是部门的别名——这三个别名和 `@DataScope` 里配的 `deptAlias`、`userAlias` 必须一一对应，否则切面拼出来的条件就找不到表。

除了查询原有字段，我们还期望能显示出用户的 id 和部门的 id，所以额外补上 `u.user_id` 和 `d.dept_id`。其他字段咱们先不需要。

然后在查询条件的下方，拼接数据范围过滤的动态 SQL，位置就在 `where` 条件的最后一行：

```xml
        <!-- 数据范围过滤 -->
        AND ${params.dataScope}
    </select>
```

> **易错点**：注意这个单词千万别写错，`dataScope` 的 `S` 是大写。

查询改完了，但还有个细节：**我们在查询时登录日志表当中必须有 `dept_id` 和 `user_id` 这两个字段值**，否则将无法连接部门表和用户表。所以新增的时候，是不是要同时给它记录上 `user_id` 和 `dept_id`，不然这两个字段为空，就无法实现关联查询。那 `insert` 语句也得做改造：上半部分是指定的字段名，补上 `user_id`、部门 id 的列；下面是两个占位符，也补上对应的值：

```xml
<insert id="insertLogininfor" parameterType="com.ruoyi.system.domain.SysLogininfor">
    insert into sys_logininfor (
        <trim prefix="(" suffix=")" suffixOverrides=",">
            <if test="infoIp != null and infoIp != ''">info_ip,</if>
            <if test="userName != null and userName != ''">user_name,</if>
            ...
            <if test="userId != null and userId != 0">user_id,</if>
            <if test="deptId != null and deptId != 0">dept_id,</if>
            ...
        </trim>
        <trim prefix="VALUES (" suffix=")" suffixOverrides=",">
            ...
            #{userId},
            #{deptId},
            ...
        </trim>
</insert>
```

大家编写的时候一定要认真仔细一点，尤其是中英文的标点符号，千万别写错了。

#### 第五步：异步工厂补上用户与部门信息

第四步搞定以后，兄弟们还记得咱们的登录日志是怎么保存到数据库的吗？

就是我们的**异步任务管理器**。这里我们通过异步任务工厂（`AsyncFactory`）来创建一个任务，而这个任务就是来保存登录日志的。我们在创建任务的同时，是不是要设置登录用户的 id 和所属部门 id，以便把这些数据保存到数据库当中。

所以我们把**记录用户登录信息的那个定时任务的逻辑**做一下调整，确保能够设置登录用户的 id 和部门 id。

那异步工厂代码在哪呢？找到 ruoyi 的框架模块，打开 src，注意看 `manager` 就是异步任务管理器的包，点开其中有一个子包叫 `factory`，双击打开，这个方法就是来记录用户登录信息的定时任务，是不是创建的 `TimerTask`。它的实现细节我们之前已经分析过了，最后就是通过 `SpringUtils` 这个工具类来获取登录日志的 service 层，实现登录日志的插入操作，最终把它保存到数据库当中。

我们要做的是**在保存数据之前，设置当前用户的 id 和部门 id**。但同学们思考一个问题：目前这个方法当中，有没有传过用户 id 和部门 id 的参数啊？是不是没有传过来啊，那我怎么取出用户 id 和部门 id 呢？

其实很简单。我们虽然没有传用户 id 和部门 id，**但是我传了登录用户名了**。如果传了登录用户名的话，我们就可以以它为条件查询用户表。而用户表当中能不能拿到 `user_id` 和 `dept_id`？答案是可以的，在登录的源码当中，若依就提供了以 `username` 作为条件查询用户表的方法。

我们要找到这个 service，找到之后咱们能不能**照猫画虎**？参考旁边这行代码 `SpringUtils.getBean`，就可以从 IOC 容器当中拿到指定类型的实例对象，然后就可以调用它的查询方法了：

```java
// 设置登录用户的id和所属部门id
SysUserService userService = SpringUtils.getBean(SysUserService.class);
SysUser user = userService.selectUserByUserName(username);
if (user != null) {
    // 设置用户id和部门id
}
```

设置完毕以后，就可以把它保存到数据库的日志表当中了。

诶？怎么查询所有了呢？不对呀，我们明明已经设置了数据权限控制啊。

> 在开发时难免会出现查询结果跟预期不一样的情况。那接下来就带大家来检查一下是哪一步代码出现了问题。咱们**倒着推**。

- **第五步异步工厂调整**——回到代码里看，这一步应该没问题，因为数据库当中已经存储了 `dept_id` 和 `user_id` 了。所以第五步没毛病。
- **第四步映射文件**——`insert` 语句没问题；再往下走，SQL 的多表查询应该也没有问题，因为查询时并没有报错，而是把所有数据都返回了。
- 那么大概出现的位置呢？**来看这里，数据范围过滤并没有指定。**

坑在这儿！注意看 `${params.dataScope}` 这边，我们**多打了一个字母**，导致条件呢并没有被拼接进来。把多余的字母干掉，再 `Ctrl + F9` 热部署更新一下，问题就找到了。

#### 改造五步回顾

| 步骤 | 做什么 | 关键点 |
|---|---|---|
| 第一步 | 加权限注解 | `@DataScope` 要同时指定部门、用户两个别名 |

### 本讲提到的题目

这一讲里留了不少「思考一下，把答案写到弹幕当中」的题，我把题干和答案统一还原在这里。

**角色表和部门表之间应该是什么关系？**
解析：参考用户表和角色表之间多对多的处理方式。答案：**多对多**，需要一张中间表，表里两个外键字段分别是 `role_id` 和 `dept_id`，分别指向角色表和部门表的主键。

**那段嵌套查询 SQL 属于哪一种数据权限类型？**
解析：看它查的是哪张表、条件是什么。答案：**自定义数据权限（范围值 2）**，因为它查的是角色-部门中间表、条件是角色 id，只有这一种范围依赖该中间表。

**添加完表字段之后，还要添加什么？**
解析：字段要能在业务逻辑中拿到，就得映射到对象上。答案：**实体类的属性**，同时补上 get/set 方法。

**咱们的登录日志是怎么保存到数据库的？**
解析：注意它不是 Controller 直接调的。答案：**通过异步任务管理器 / 异步工厂（`AsyncFactory`）创建的定时任务**，最后借助 `SpringUtils` 拿到登录日志的 service 完成插入。

**日志表里的历史记录没有 `dept_id` 和 `user_id`，能实现数据权限控制吗？**
解析：关联查询和过滤条件都依赖这两个字段的值。答案：**不能**，必须先把旧数据清掉，重新造一批带完整字段的模拟数据。

**用通义灵码生成 DDL，提示词该怎么写？**
参考答案：

```text
你是一名软件工程师，请为登录日志表 sys_logininfor 添加 dept_id 和 user_id 两个字段，
这两个字段还要生成注释，类型应该是一个长整型（big int），最后帮我生成 SQL 语句。
```

### 结课

拔高原理篇到这里就结束了，这一整套课程也画上了句号。

回头看这一段路：RBAC 解决**能不能访问**、数据权限解决**能看到多少**，两者通过「注解 + 切面 + 动态 SQL」这套组合拳合到了一起。今天我们把这套组合拳从表结构一路拆到了业务改造，最后落到登录日志这个真刀真枪的需求上，验证了「超级管理员看全部、若依只看自己」的预期效果。

这一讲的核心其实就几句话，记住它们就够用了：

1. 想开数据权限，方法上挂 `@DataScope`，**要部门就写 `deptAlias`，要用户就写 `userAlias`**；
2. 想让它生效，**实体类必须继承 `BaseEntity`，业务表必须有 `dept_id` 和 `user_id`**；
3. 条件怎么进来？**Mapper 里写 `${params.dataScope}`**，切面负责往这个 key 里塞拼好的 SQL；
4. 安全性？**切面在拼接前先把 `dataScope` 置空**，前端恶意拼接的值在这一步就被抹掉了。
