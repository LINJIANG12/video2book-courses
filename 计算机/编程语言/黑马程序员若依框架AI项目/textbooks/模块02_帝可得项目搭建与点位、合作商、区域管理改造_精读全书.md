#### 改 Druid 的连接配置

那么接下来呢，我们回到 IDEA 当中，找到项目的配置文件，打开 `dk-admin`，找到 Spring Boot Druid 的配置文件。

我呢在这里面已经帮兄弟们配置好了：连接本机地址，数据库名就叫 `dk`，账号 `dk`，密码都是 `root`。

```yaml
spring:
  datasource:
    druid:
      master:
        url: jdbc:mysql://localhost:3306/dk
        username: dk
        password: root
```

> **注意**：如果你连接的环境跟我的是不一样的，这部分呢大家一定要进行修改。URL、用户名、密码三样都不能落。

OK，到这里第二步 MySQL 导入与配置我们就搞定了。

#### 启动 Redis 并把密码补上

那么接下来呢，我们来完成第三步：启动 Redis 与配置。

来，回到 Redis 的解压路径。注意兄弟们，现在呢我们是项目实战篇了，尽量地去模拟真实的企业开发环境。那同学们来思考一下，如果我们的 Redis 没有设置密码，启动以后直接去进行连接，大家来思考一下，这样的项目开发环境是安全的吗？

那肯定是不安全的，对吧。

我们可以找到 Redis 配置文件，右键打开。在这个配置文件 503 行的位置呢，有一个属性叫 `requirepass`，它默认是由 `#` 号进行注释的。我们需要把井号去掉，然后呢就可以在后方指定连接密码了。那我呢在这里面设置是跟数据库一样的，密码为 `root`。

```conf
requirepass root
```

那我们项目在启动时，也需要去配置 Redis 的连接密码了。

OK，配置文件我们就修改完毕了。回到解压路径，右击我们打开终端，输入 Redis 启动命令，让 `redis-server` 加载 Redis 配置文件，按回车执行。

```bash
redis-server redis.windows.conf
```

现在我们成功启动了 Redis。

回到 IDEA 当中，找到 Redis 的配置文件 `application`，双击打开，往下拉，找到 spring 相关的。在 77 行的位置呢，我已经指定好了，连接密码同样为 `root`。

```yaml
spring:
  redis:
    password: root
```

小伙伴们，如果你的密码不是 `root` 的话，也可以在这里面进行修改。

OK，到这里第三步启动 Redis 与配置我们就完成了。

### 点位管理的业务场景与需求

刚才我们已经顺利完成了项目的搭建工作，接下来呢我们开始点位管理相关功能的开发。

#### 一个从选址到投放的故事

首先呢，让我们来梳理一下业务场景和需求说明。

假设我们公司呢现在有一个宏伟的计划，在北京发展业务。首先我们需要确定几个有潜力的区域——这些区域呢可能是人流量大、消费能力高的商业区或居民区。

然后呢，我们要与这些区域的潜在合作商进行洽谈，比如说商场、写字楼、学校等地方的管理者或所有者。

一旦我们洽谈成功以后，确定了合作细节和点位，我们可以安排工作人员去投放智能售货机了。这些点位将成为我们智能售货机的家，为消费者提供便捷的购买服务。

以上呢就是我们的业务场景。而点位管理在此业务场景当中，主要涉及三个功能模块：

```text
   点位管理
     |
     +-- 区域管理   —— 我们在哪儿
     +-- 合作商管理 —— 跟谁合作
     +-- 点位管理   —— 货机放在哪儿
```

#### 完整业务流程

回到页面原型，我们能看到有区域管理的功能模块、点位管理的功能相关内容，以及合作商管理的相关内容。他们之间具体的业务流程呢，我们回到 PPT 来看一下。

```text
  ① 管理员登录帝可得后台管理系统
              |
              v
  ② 新增区域信息，录入系统
     （如北京北五环奥体中心等区域）
              |
              v
  ③ 录入已达成合作协议的合作商信息
              |
              v
  ④ 在特定区域下新增点位
```

首先呢，后台管理员需要登录帝可得的后台管理系统。系统登录成功以后，管理员呢就可以新增区域信息，把它录入到系统当中。

在确定好区域以后，管理人员就可以将达成合作协议的合作商信息呢也录入到系统当中。

> **定义**：合作商就是提供点位的合作伙伴，我们也可以理解为「点位主」。

在区域以及合作商确定以后，后台管理人员就可以在特定的区域下新增点位。

> **定义**：点位，就是放置智能售货机的具体位置。

到这里呢帅哥需要再强调一下：

> **易错点**：**合作商和区域之间是没有关系的。** 因为合作商拥有的点位可以分布在不同的区域下，它们之间是没有直接的关联关系的。这一点在后面设计表结构的时候，我们会再强调一次。

以上呢就是点位管理的主要业务流程。

#### 本章的学习路线

到这里，同学们现在我们对点位管理的业务流程有了清晰的认识。接下来让我们一起梳理一下本章的学习路线。

首先呢，我们将参考页面原型和具体的需求，利用 AI 辅助设计数据库的表结构。这不仅能够帮助我们更高效地完成设计，还能生成符合需求的测试数据。

设计完以后，我们将把这些 AI 生成的 SQL 语句导入到我们的开发数据库当中。

接下来我们将利用若依的代码生成器来生成基础代码。这个工具呢可以帮助我们快速生成前后端代码，并把它导入到开发环境当中。

不过需要注意的是：

> **注意**：这些基础代码，目前**仅涵盖了单表的增删改查操作**。为了满足需求，我们还要参考页面原型和具体的业务场景，对区域管理、合作商管理以及点位管理这三个关键模块进行代码改造。在这个过程当中，我们会结合 AI 逐步调整和优化代码，直到它们完全符合我们的业务需求，实现完整的业务功能。

所以学习路线可以概括成：

```text

          |
          v

          |
          v
  ② 把 AI 生成的 SQL 导入开发数据库
          |
          v
  ③ 用若依代码生成器生成前后端基础代码
```

以上就是我们本章的学习路线。那么本节内容呢我们就讲到这里。

### 从页面原型反推表结构

我们已经清楚了点位管理的需求说明，现在我们开始完成点位管理相关功能的数据库表结构的设计。

设计表结构这件事没有什么巧办法，就是老老实实回到页面原型上，一个字段一个字段地看：**哪些东西该落库，哪些东西根本不该落库**。这一节我们就按区域、合作伙伴、点位三张表的顺序来。

#### 区域表：三个字段就够了

#### BaseEntity 带来的五个公共字段

这里呢我们还需要补充一下。在我们构建业务表的时候，通常会引入一些**公共字段**，来帮助我们记录和管理数据的状态以及它们的历史变更。比如有创建时间、创建人、修改时间、修改人、备注信息等等。

那么这些字段该如何命名，以保证它的清晰和一致性呢？

> **定义**：若依提供了一个 `BaseEntity` 这个基类，它是每张表对应实体类**默认继承**的一个父类。

我们回忆一下啊，通过代码生成器生成的业务实体类，都会自动地去继承这个 `BaseEntity`，并拥有它所提供的所有属性。这里面我们需要关注五个：

| 属性名 | 含义 |
| --- | --- |
| `createBy` | 创建者，就是我们的创建人 |
| `createTime` | 创建时间 |
| `updateBy` | 更新人 |
| `updateTime` | 更新时间 |
| `remark` | 备注 |

通过使用 `BaseEntity` 类，我们就可以确保所有的业务实体类都包含了这些公共字段，从而简化了代码的编写和维护工作。这也使得我们数据库的设计和业务逻辑呢，更加的规范和标准化。

看到这里，有细心的同学已经发现了：

> **易错点**：在区域表当中有一个「备注说明」，它和 `BaseEntity` 当中的 `remark` 字段是**同一个含义**。那区域表的备注说明呢，就不需要再单独设计了，我们直接使用 `BaseEntity` 的 `remark` 就可以了。

OK，到这里我们完成了点位管理三大模块的页面原型和表字段的分析，并说明了若依提供的五个公共字段的命名格式。

#### 提示词怎么写

我们来操作一下，首先把这三张业务表的主要字段截图，放到右上角。回到浏览器打开通义千问。

那下面呢我们就可以写提示词的内容了。首先，他的角色是一位软件工程师：

```text

```

> **提示**：表名我们要尽量给他规范化，不然他自己去起名的话，有的时候看起来是比较乱的。所以我们统一给它 `tb_` 前缀加下划线的写法：`tb_region`、`tb_partner`、`tb_node`。

```text
你是一位软件工程师，帮我生成 MySQL 的表结构。

  主要字段有：主键 id、合作商名称、联系人、联系电话、

  存 70% 这里就写 70，是不包含小数的）、账号、密码

    这部分先跳过）

其他要求：
  1. 每张表都需要有一些公共字段：创建时间、修改时间、创建人、

     这些字段保持一致。
  2. 每张表的主键呢，都是自增的。
  3. 区域表跟点位表是一对多的关系，合作商与点位也是一对多的关系，
```

> **结论**：第 3 条是整个提示词里最重要的一句。有了它，AI 就会在点位表当中帮我们添加区域和合作商的外键，并添加外键约束——关系设计这件事，我们就彻底交给它了。

### 三张表的关系模型

OK 到这里，我们利用 AI 辅助工具通义千问，快速完成了三张业务表结构的创建，并添加了测试数据，是不是非常的高效啊同学们。

接下来我们回到 PPT，看下这几张表的关系模型。这里展示的这张图，就是我们刚刚基于 AI 工具生成的三张表：有区域表、点位表以及合作商表。

```text
+--------------------------------+
|  tb_region  区域表             |
|  PK   id                       |
|       region_name              |
|       remark                   |
+----------------+---------------+
                |
                |   1  :  N
                |
+----------------+---------------+
|  tb_node  点位表               |
|  PK   id                       |
|       node_name                |
|       address                  |
|       business_type            +----> 数据字典：商圈类型
|  FK   region_id                |
|  FK   partner_id               |
+----------------+---------------+
                |
                |   N  :  1
                |
+----------------+---------------+
|  tb_partner  合作商表          |
|  PK   id                       |
|       partner_name             |
|       contact_person           |
|       contact_phone            |
|       profit_share             |
|       account                  |
|       password                 |
+--------------------------------+
```

> **结论**：这张图里只有两条连线——区域到点位，合作商到点位。**区域表和合作商表之间一根线都没有**，这正是前面强调过的那句话：合作商和区域之间是没有关系的。

#### 区域与点位：一对多

首先是区域和点位。小伙伴们来回答一下吧，很好没有错，就是一对多的关系。一个区域下面是拥有多个点位的，所以在点位表当中有一个外键叫 `region_id`，去指向区域表的主键。

将来呢，我们就可以通过这个区域的 `region_id` 来统计点位的数量了。

#### 合作商与点位：一对多

再来看合作商和点位表什么关系呢？哎，没有错，也是一对多的关系。咱们在点位表当中有一个 `partner_id` 作为合作商的外键，去指向合作商的主键。

将来呢，我们就可以基于这个 `partner_id` 来统计合作商的点位数量了。

#### 商圈类型：只存字典值

那接下来呢我们还需要关注一个 `business_type`，它是点位的商圈类型。那么刚才我们提到了这些呢——旅游区、商城、写字楼、学校、交通枢纽——这些属于静态数据，我们把它设计为数据字典以及对应的字典值。而我们这个字段呢，只需要存储字典值就可以，方便我们的查询操作了。

所以在整个业务当中，我们重点关注的其实就是这张点位表：通过 `region_id` 去关联区域，通过 `partner_id` 呢去关联合作商，通过这个 `business_type` 呢去指定数据字典。

OK，以上就是点位管理相关的数据模型介绍了。同学们，本小节我们利用 AI 辅助工具完成了业务表结构的设计与创建，并分析了这三张表的数据模型关系。下一小节呢，我们将利用若依的代码生成器来生成基础代码。

## 对照原型改造区域管理与合作商管理

### 区域管理：先拿原型和生成代码逐块比

打开页面原型，回到帝客的管理界面找到区域管理，把原型和生成代码摆在一起，一块一块比下去。

第一部分条件搜索，用的就是区域名称，和原型完全一致，功能也测过了没问题——**不改造**。

第二部分按钮区域，原型里只有一个"新增"，而若依生成的代码除了新增，还有修改、删除、导出这三个额外的按钮。

#### 列表区只改两处

比到列表展示就发现问题了。

- 复选框留着，它是做批量删除用的；
- 主键 ID 要改成**序号**。为什么要改？因为将来做排序的时候，主键那一列（若依默认是雪花 ID，十几位数字）看起来特别凌乱，而序号永远是 1、2、3、4，更直观、更有条理；
- 区域名称、备注说明，跟原型一致；
- **点位数**，涉及后端代码改造，稍后再做；
- **查看详情**，同样涉及后端，稍后再说；
- 修改、删除按钮——原型里这两个按钮是没有图标的，若依生成的有，怎么办？

这里要停一下想一想：将来我们要在列表左侧增加一个"查看详情"按钮，那个按钮**有没有图标**？没有。既然同一排按钮有一个没图标，就把另外两个的图标也去掉，整体才是一套。

> **结论**：区域列表部分需要改造的就两处——第一，主键改为序号；第二，移除修改和删除按钮的图标。

思路明确了，回 VS Code 找视图管理的 `region` 组件。第一个改造点，主键 ID，把 `label` 改成"序号"。

改完回浏览器刷新——序号出来了，1、2、3。可是这一列宽度太窄，自动换行了，所以再加个 `width="50"` 把宽度撑开。宽度也调好了，序号功能完成。

### 点位数从哪儿来：冗余字段还是实时统计

回到 PPT，还剩两个涉及后端的功能：区域查看详情、区域列表显示点位数。

**查看详情**要做的是：点进某个区域，展示这个区域下的所有点位列表——上半部分是区域名称，下半部分是点位列表。方案是**复用现有的查询点位列表接口**，这样既能减少开发工作量，又能保证代码的整洁和一致。具体改造细节会在后面的点位管理模块里展开讲，这里先跳过。

**区域列表显示点位数**就不一样了：查区域列表的同时，把每个区域的点位数一起带回来。要做这件事，先得知道后端返回的数据该长什么样——接口文档已经给出来了（后续要改造的功能我都准备了离线文档放在资料里，课下可以自己翻）。

| 项目 | 内容 |
|---|---|
| 请求路径 | `/manage/region/list` |
| 请求方式 | GET |
| 请求参数 | `pageNum` 当前页、`pageSize` 每页个数、`regionName` 搜索条件 |
| 返回字段 | `total` 总记录数、`rows` 当前页结果集、`code` 状态码、`msg` 返回信息 |
| rows 中单条数据 | `remark` 备注说明、`id` 区域 ID、`region_name` 区域名称、`node_count` 点位数量 |

`total`、`rows`、`code`、`msg`——这就是若依标准的分页返回对象，没什么好说的。关键在 `rows` 里那条区域数据上，除了 ID、名称、备注，还多了一个 `node_count`。只要我们能把这个点位数量返回给前端，Element Plus 的表格就能直接把它显示出来。

先复习一下现有代码。回到 IDEA，找到 `RegionController`，第一个方法就是列表查询：请求路径能对上，请求方式能对上，参数用 `region` 接收。这个方法基础篇分析过，流程是——拿到参数先开启分页，然后调 service 按条件查，拿到一个 list 集合，再交给 `getDataTable` 封装成分页对象返回前端。里面的数据就是区域信息：区域 ID、区域名称，还有继承 `BaseEntity` 的备注说明。

只不过它只返回了区域自己的信息，没有点位数。而我们的需求要把区域表的信息和点位表统计后的数据整合到一起返回。怎么做？先思考一下。

#### 方案一：同步存储（冗余字段）

在区域表当中新增一个字段，就叫 `node_count`，专门存这个区域下的点位数量。将来只查区域列表，就能顺带把点位数带出来。

这就是第一种方案——**同步存储**：在区域表里加点位数字段，点位发生变动时（比如新增了一个点位），顺手更新一下区域表的这个字段。

- **优点**：单表查询，查区域列表的效率非常高；
- **缺点**：每次点位数据变动，都要额外更新一次区域表，工作量翻倍；更要命的是，**一旦更新操作有遗漏，就会数据不一致**——明明是四个点位，统计出来可能是三个，也可能是五个。

#### 方案二：关联查询

在 Mapper 层里写 SQL，通过关联查询，实时算出每个区域的点位数。基于区域 ID 统计点位数量，把统计结果跟区域表的列表合并，输出返回给前端。

- **优点**：数据的实时性和准确性有保证，因为是实时算的，不需要单独维护；
- **缺点**：SQL 涉及多表关联，语句比较复杂；如果点位数据量非常大，还有可能影响查询性能。

考虑到区域和点位的数据量通常不会特别大，我们选第二种：**关联查询**。

| 维度 | 方案一：同步存储 | 方案二：关联查询 |
|---|---|---|
| 做法 | 区域表加 `node_count` 冗余字段，点位变动时同步更新 | Mapper 里写 SQL，按区域 ID 实时统计，与区域数据合并返回 |
| 优点 | 单表查询，查列表效率高 | 实时准确，不需要单独维护 |
| 缺点 | 每次点位变动都要多更新一次；更新一旦遗漏就数据不一致（明明 4 个点位，统计出 3 个或 5 个） | 多表关联语句复杂；点位数据量很大时可能影响查询性能 |
| 本案例 | 不选 | 选它 |

> **结论**：这两种方案都有利弊，选哪种取决于实际的数据量和业务需求。这个案例里我们追求的是实时性和准确性，所以选关联查询。这不是"关联查询更高级"，是"这个场景下它更合适"。

### 手写 SQL：先聚合，再左外连接

下面我们来手写这条 SQL。SQL 的编写有两种模式：一种是**传统模式**，从思路分析到语句编写全部自己完成；另一种是**AI 辅助编程模式**——在全面拥抱 AI 的时代，我们只需要把需求的 prompt 提示词写好，它就能自动生成 SQL，然后我们调整一下就拿到最终结果。

先走传统模式，把思路吃透，再用 AI 模式做个对照。

整体思路是两步：

```text
第 1 步：点位表按 region_id 分组统计
        tb_node ──GROUP BY region_id──> (region_id, node_count)
                                                    │
                                                    │ 把它当作"虚拟表" n
                                                    ▼
第 2 步：区域表主体 r  ──LEFT JOIN──> n  ON r.id = n.region_id
        没有点位的区域也照样出来，只是 node_count 是 NULL
```

#### 第一步：按 region_id 分组统计

这个需求拆开来其实就三件事：要查哪张表？`tb_node`。按什么分组？`region_id`。分完组统计什么？`COUNT(*)`。

通常我们对谁分组就查谁，再统计数量，所以 SQL 出来了：

```sql
SELECT *
FROM tb_node
GROUP BY region_id
```

选中有 `COUNT(*)` 的那条执行：区域 ID 为 1 的有一个点位，区域 ID 为 2 的同样有一个点位——这是我们之前生成的测试数据。

但这个 `COUNT(*)` 见名不知意，普通用户哪知道它表示的是点位数？所以加个别名：

```sql
SELECT region_id, COUNT(*) AS node_count
FROM tb_node
GROUP BY region_id
```

`node_count` 就见名知意了。

#### 第二步：虚拟表左外连接区域表

现在把这个聚合结果当虚拟表，去关联查询区域表。我们希望拿到区域表的所有数据，所以查询主体是 `SELECT * FROM tb_region`，给它加个别名 `r`。

关联查询分内连接和外连接，该选哪种？想想后果：内连接查的是两张表的**交集**，那没有点位的区域——是不是就不展示了？那肯定不行。所以选外连接。`tb_region` 是左侧主体，用**左外连接** `LEFT JOIN`，把上一条 SQL 的执行结果接进来，给它加个别名 `n`。

```sql
SELECT *
FROM tb_region r
LEFT JOIN (
    SELECT region_id, COUNT(*) AS node_count
    FROM tb_node
    GROUP BY region_id
) n ON r.id = n.region_id;
```

选中执行：所有区域的数据都查出来了，往右拉一拉，每个区域下面的点位数量也统计出来了。

#### 用 IFNULL 补零

但这个执行结果返回的字段太多了，接口文档里前端只要四个字段。这里要收敛一下：`remark`、`region_name` 属于区域表，`id` 也属于区域表，最后点位数量来自虚拟表。

```sql
SELECT
    r.id,
    r.region_name,
    r.remark,
    n.node_count
FROM tb_region r
LEFT JOIN (
    SELECT region_id, COUNT(*) AS node_count
    FROM tb_node
    GROUP BY region_id
) n ON r.id = n.region_id;
```

清爽多了，但还有个**小 Bug**：北京东城区、北京北五环奥体中心这两个区域下面还没有点位数据，返回的是 `NULL`。返回 NULL 合适吗？肯定不合适——没有点位数据，就该返回 0。

MySQL 内置函数 `IFNULL` 就是干这个的：当结果为 NULL 时，给一个默认值 0。

```sql
SELECT
    r.id,
    r.region_name,
    r.remark,
    IFNULL(n.node_count, 0) AS node_count
FROM tb_region r
LEFT JOIN (
    SELECT region_id, COUNT(*) AS node_count
    FROM tb_node
    GROUP BY region_id
) n ON r.id = n.region_id;
```

东城区、奥体中心的点位数变成 0 了。不过加了函数之后字段名就不见名知意了，所以还得补个别名 `AS node_count`。选中执行，返回结果跟接口文档要求完全一致。

### AI 辅助编程：换个顺序，SQL 反而更短

传统模式我们一步一步推导，最终把 SQL 写出来了，但这个效率实在太低。现在来体验一下 AI 辅助编程。

DataGrip 这个数据库客户端是可以装通义灵码插件的（安装操作基础篇讲过，这里不复述）。把功能打开，把本地模型和云端模型都打开，就可以用 prompt 提示词自动生成 SQL 了。

这里有个细节要注意：在当前窗口它会学习我们刚刚写过的 SQL 代码，生成的结果和我们自己写的**完全一样**——它等于在抄我们自己。所以要右键新建一个窗口，在新窗口里写 prompt。

提示词写上：查询区域表所有的信息。按 Tab 接受它的补全，回车换行。注意看，这条 SQL 它也帮我们生成了。

执行一下，跟我们预期的完全一样：查询了所有区域表的信息，并显示了每个区域下面的点位数。

那这条 SQL 的思路是什么？**先查区域表，左外连接查询点位表；拿到结果以后，再根据区域 ID 进行分组**，对分组后的数量做 `COUNT` 统计。

```text
AI 版本：一条语句走完
tb_region ──LEFT JOIN──> tb_node
                │
                └──> 按 region_id 分组 → COUNT(*) → 每个区域的点位数

关键差别：分组发生在"连接之后"
左外连接补出的那些没有点位的行，在按 region_id 分组时
同样会进入 COUNT，于是天然拿到 0，不需要 IFNULL
```

对比一下就明白了：

| 维度 | 我们手写的两步 | 通义灵码生成的一步 |
|---|---|---|
| 结构 | 先聚合成虚拟表，再用虚拟表外连接区域表 | 直接区域表左外连接点位表，再按区域 ID 分组 |
| 空值处理 | 没有点位的区域是 NULL，得用 `IFNULL` 兜底 | `COUNT` 在分组统计，不会出现空值 |
| 阅读成本 | 子查询嵌套，多处别名限定，读起来费劲 | 一条平铺语句，一眼看懂 |

> **结论**：两种 SQL 都能用，别把它们当成"标准答案"和"错误答案"。真实项目里以能跑通、能读懂为准。

有没有感受到 AI 辅助编程的魅力？只要我们明确需求，把 prompt 提示词写好，AI 就能自动帮我们生成 SQL，开发效率大大提升。

### 从数据库到前端：VO、Mapper、Service、Controller

SQL 有了，接下来就是把它接进代码里。整条链路是这样的：

```text
浏览器表格列 prop="nodeCount"
   │  GET /manage/region/list?regionName=xx
   ▼
RegionController.list(Region)
   ▼
IRegionService.selectRegionVoList(Region)
   ▼
RegionMapper.selectRegionVoList(Region)
   ▼
RegionMapper.xml   LEFT JOIN + GROUP BY + IFNULL
   ▼
List<RegionVo>  →  getDataTable(list)
   ▼
{ total, code, msg, rows: [{ id, regionName, remark, nodeCount }] }
   ▼
Element Plus 表格渲染
```

#### RegionVo：只多一个 nodeCount

先创建一个用来映射数据库查询结果、并返回给前端的 VO 类。放哪儿合适？其实可以在 `domain` 包下面再建一个子包，叫 `vo`——将来所有定义返回给前端的类，都放在这里，命名统一叫 `XXXVo`。本次需求做的是区域管理，所以叫 `RegionVo`。

它要返回的结果包含四样东西：区域 ID、区域名称、备注说明、点位数量。前三个属性，区域实体类 `Region` 已经有了——为了简化操作，我们让这个 VO **直接继承 `Region`**，当前类只需要定义点位数量这一个属性。

```java
package com.itheima.manager.domain.vo;

import com.itheima.manager.domain.Region;
import lombok.Data;

/**
 * 区域列表VO
 */
@Data
public class RegionVo extends Region {

    /**
     * 点位数
     */
    private Integer nodeCount;
}
```

这里有两个细节值得停一下：

**第一，属性命名**。通义灵码结合注释帮我们生成了一个属性，但它默认叫 `pointCount`，而我们 SQL 里的别名是 `node_count`，所以要手动改成 `nodeCount`（VO 用驼峰，SQL 用下划线，靠 MyBatis 的映射开关对接，后面还会讲）。

**第二，getter/setter**。`Alt + Insert` 选 Getter and Setter 是能生成的，但代码看起来实在不够优雅。通常我们会用 Lombok 来生成 getter、setter、`toString`，以及有参无参构造方法。项目初始环境搭建时，common 模块下就已经引入了 Lombok 坐标，所以这个 VO 类直接加一个 `@Data` 注解就行，自动生成那套方法——是不是优雅多了？

> **提示**：`RegionVo extends Region` 是一种务实取舍——省掉三个一模一样属性的重复声明，代价是 VO 会带上 Region 的全部字段。当前场景两者字段高度重合，很划算；如果将来两个模型分家了，再拆开也不迟。

#### Mapper 接口与方法

打开 `RegionMapper`，这里已经是若依生成的五个增删改查常用方法。我们在此基础上**增加一个新方法**，返回 `List<RegionVo>`：

```java
/**
 * 查询区域列表
 *
 * @param region Region
 * @return RegionVo集合
 */
public List<RegionVo> selectRegionVoList(Region region);
```

方法名可以参考若依原有的命名：`selectRegionList`，我们这个叫 `selectRegionVoList`，多一个 `Vo`，一眼就知道返回的是 VO。唯一要注意的是，**查询条件用的还是原来的 `Region`**，不是 VO——VO 是用来承载返回值的，不该拿来当查询入参。

方法下面飘起一条红色波浪线，是什么？当前开发环境的 IDEA 装了 **MyBatisX** 插件，它会自动校验这个方法有没有对应的 SQL 语句。校验之外，选中方法名按 `Alt + 回车`，它还能直接帮我们生成 XML 的查询标签，是不是非常方便？

#### XML 里必须记住的三件事

回到数据库客户端，把 AI 生成的 SQL 复制下来，直接粘进 Mapper 的 XML。有三件事必须注意：

**第一，最后一条 SQL 不能有分号。** 这里面包含分页查询，我们用了 PageHelper 的分页插件，它会动态拼接 `LIMIT` 关键字，如果加了分号，代码就会直接报错。

**第二，动态 SQL 要加表别名前缀。** 我们这条 SQL 查的是所有区域列表，但实际业务场景还要按区域名称过滤。若依原有的条件查询代码就在手边——一个 `where` 加 `if` 标签，判断前端传的 `regionName` 不为空且不为空串时，做模糊匹配。直接 `Ctrl + C` 复制过来粘上。

但粘过来不能直接用：原有的是单表查询，我们这里的多表查询设置了别名，所以 `region_name` 必须加别名前缀，写成 `r.region_name`。

**第三，下划线转驼峰的开关必须打开。** 这是个特别容易踩的坑：我们在 SQL 里定义的别名是 `node_count`（下划线），而 VO 里的属性是驼峰式 `nodeCount`。若依默认把这个转换功能给**关掉了**，需要找到模块下的 MyBatis 配置文件，把那行注释放开，它就会自动把下划线转成驼峰。这里不需要做任何额外配置。

> **注意**：如果你用的后端工程不是跟着课初始化的，这个开关**千万别忘了打开**，否则字段全是 null，你都不知道问题出在哪。

完整版长这样：

```xml
<select id="selectRegionVoList" resultType="com.itheima.manager.domain.vo.RegionVo">
    SELECT r.id, r.region_name, r.remark, IFNULL(n.node_count, 0) AS node_count
    FROM tb_region r
    LEFT JOIN (
        SELECT region_id, COUNT(*) AS node_count
        FROM tb_node
        GROUP BY region_id
    ) n ON r.id = n.region_id
    <where>
        <if test="regionName != null and regionName != ''">
            AND r.region_name LIKE concat('%', #{regionName}, '%')
        </if>
    </where>
</select>
```

#### Service 与 Controller

业务层很简单。找到 `IRegionService` 接口，方法定义可以直接参考 Mapper 层——这样就节约时间，把 Mapper 层的方法签名直接复制过来即可。创建实现类，实现类的注释也用 CV 大法从接口那边粘过来。方法体里调用 `regionMapper.selectRegionVoList(region)`，把条件扔过去。

Controller 那边只改一处：原来查的是单表的区域信息，现在改成调 `selectRegionVo`，把条件传进去，返回的是一个 `voList` 集合；再把这个 VO 集合交给 `getDataTable` 转成分页对象，返回前端。

### 搜索一点就报错：GROUP BY 站错了位置

接下来测试条件搜索功能。这一测就出事了——点搜索以后，控制台报错，说是个 SQL 语法错误。

可我们的 SQL 明明没写错啊？

> **易错点**：这是我在课程设计里特意加的一个环节。假如这个错误你连看都看不出来，怎么办？

有小伙伴说，可以问通义灵码啊，那就听你的。把 SQL 复制过来，打开通义灵码粘进去，问它"有什么错"，回车。

通义灵码给了参考答案，答案里可以看到：`GROUP BY` 分组放到**最后**，在它上面的是一个 `WHERE` 查询条件。也就是说，正确的 SQL 语法是**先做条件过滤，再做分组统计**；而我们自己写的那条是**先分组、后条件**——有 `GROUP BY` 的时候还去写 `WHERE`，位置就不对了，直接语法报错。

现在动手改造，把 `GROUP BY` 放到最后。

### 一个对话框，两种形态：v-if 判 id

修改的合作商原型跟新增不一样：在原型当中，我们通常不会去修改账号和密码这两个字段，而且还需要额外展示合作商的创建时间。

这就带来了一个问题——若依的新增和修改**用的是同一个对话框**，这意味着两者显示的内容是完全相同的。怎么调整对话框，才能符合这种需求？

有同学想到了：**专门为修改合作商定义一个新的对话框**。这个方案完全可行，但实现起来相对比较麻烦。这里有一个更简单的方法：使用 Vue 的 `v-if` 指令做条件判断。

怎么判断当前是新增还是修改？看表单对象里的 **id**：

```text
点击"新增" → 表单里没有 id（没有回显数据）
点击"修改" → 数据回显，表单里有 id

              form.id 存在？
              ┌────┴────┐
             是           否
        修改状态         新增状态
              │            │
    ┌─────────┴──────┐     │
    │                │     │
隐藏账号、密码    显示账号、密码   显示创建时间
```

规则就三条：**id 不为空就是修改态**，此时隐藏账号和密码，同时显示创建时间；id 为空就是新增态，账号密码显示、创建时间隐藏。一个对话框，就能根据不同条件展示不同内容，简单又高效。

回到代码。找到账号和密码这两个字段，给它们加上 `v-if` 条件——表单对象的 id 等于空的时候显示，密码复制同一份条件：

```vue
<el-form-item label="账号" prop="username" v-if="form.id === undefined">
<el-form-item label="密码" prop="password" v-if="form.id === undefined">
```

测试一下：点修改，表单包含了 id，所以账号密码隐藏了；点新增，表单不含 id，账号密码就显示了。没问题。

**创建时间**是第二个要加的。这个字段表单里默认是不存在的，它在原型里放在联系电话的下方。做法是以"联系电话"表单项为模板复制一份，改名为"创建时间"，`prop` 属性改为 `createTime`（若依的通用字段），下面不用 `el-form-item` 了——因为时间我们不打算一道修改，直接用插值表达式输出 `form.createTime` 就行。

```vue
<el-form-item label="创建时间" prop="createTime" v-if="form.id !== undefined">
    {{ form.createTime }}
</el-form-item>
```

设置完以后，**千万别忘了加条件判断**。这个条件该怎么写？来，弹幕走一波——已经看到弹幕了，回答得非常好：表单 id 不为空的时候就显示。写上 `v-if="form.id !== undefined"` 就行。

回浏览器测试：点修改，创建时间显示出来了，可以修改分成比例、联系电话、联系人，跟原型完全一致；点新增，新增对话框里没有创建时间，但可以让用户输入账号和密码。`v-if` 指令一加，就区分出了新增和修改两种对话框的显示效果——是不是非常简单？

那就把新增和修改功能完整测一遍：添加一个"传智合作商"，联系人小智，联系电话 13500135001，分成比例 15%，账号跟手机号相同，密码设为 123456，点确定，新增完成。再点修改，看看回显的数据——合作商名称、联系电话、创建时间、分成比例都没问题；把分成比例从 15 改成 20，点确定，数据也完成更新了。

### 明文密码入库：交给 Spring Security

但从功能角度来说，还有一个 Bug：当我们新增合作商时，管理员输入的密码是**以明文的形式保存在数据库当中**。

打开数据库客户端工具，找到 `partner` 表，看最后一条记录"传智合作商"——我们添加的密码是不是就是 `123456`？明文存储。

> **结论**：显然这不是一个安全的保存方式。如果数据库遭受未授权访问，密码很容易被盗用，存在安全隐患。

怎么解决？答案很简单：**加密**。用若依内置的安全框架 Spring Security 来对密码进行加密处理。

有了思路回到 IDEA，找到合作商的业务层代码 `PartnerService`，定位到新增的方法。在这个方法里，我们可以拿到前端输入的密码，然后通过安全框架进行加密：

```java
// 使用spring security的工具类对前端传入的密码进行加密
partner.setPassword(SecurityUtils.encryptPassword(partner.getPassword()));
```

通义灵码非常智能，结合我们写的上下文注释，直接帮我们把 `partner.getPassword()` 补全了。加密后的结果，还需要重新复制给 `partner` 的 password 属性，一行内搞定。

整个流程是：**前端传过来的是明文 → 我们进行加密 → 再把加密后的结果复制回当前密码**。这样再次保存到数据库时，密码字段就是密文了。

按 `Ctrl + F9` 热部署，回浏览器测试：再新增一个"黑马合作商"，联系人波妞，联系电话 13500135001，分成比例 20%，账号与联系电话相同，密码同样输入 123456。点保存，回数据库刷新——最后一条记录黑马合作商的密码，已经是加密后的密文了。

> **结论**：通过这个简单改造，我们不仅提高了系统的安全性，也避免了潜在的数据泄漏风险。

**第三步，调用 `getPartner` API 请求方法**，向后台发送一个根据 id 查询合作商的请求。后台处理完之后，会把结果放进 `response` 当中。

这就是修改按钮的完整工作流程。

### 让合作商列表顺带报出点位数

需求很朴素：查询合作商列表的时候，把每个合作商名下有几个点位一起显示出来。

这个功能我们在**区域列表**里其实已经做过了，所以方案不用重新想——**关联查询**。一条 SQL 把合作商表和点位表左连接起来，按合作商分组，统计点位数量，在 Mapper 层执行 SQL，把结果封装进 VO 对象，前端就能直接展示了。

```text
浏览器（合作商列表页）
        │  GET /manager/partner/list?pageNum=1&pageSize=10&name=xx
        ▼
PartnerController.list          ← 由「查单表」换成 selectPartnerVOList
        ▼
PartnerServiceImpl              ← 命名与 Mapper 保持一致
        ▼
PartnerMapper.selectPartnerVOList
        ▼
PartnerMapper.xml               ← 合作商表 LEFT JOIN 点位表 + GROUP BY 合作商 id
        ▼
List<PartnerVO>                  ← 父类字段（合作商全部信息） + nodeCount（点位数）
        ▼
AjaxResult.rows → 前端表格多出「点位数」这一列
```

#### 先让 AI 出 SQL，再把上下文喂给它

写 SQL 语句有两种模式：一种是**传统模式**，一种是**AI 辅助编程模式**。我们这次用后者。在数据库客户端里右击打开命令行窗口，切换到 AI 辅助编程模式，然后写下提示词：

```text
查询合作商表的所有信息，同时显示每个合作商的点位数
```

回车，通义灵码就开始生成了。生成的时候按 Tab 缩进、再按 Tab 换行，顺带分组，SQL 就出来了。

我们一起看看它给的思路：**先查合作商表，再通过左连接查询点位表**，这里是连接条件——按合作商 id 关联，然后**根据合作商 id 分组**，查询合作商的信息，再统计每个合作商的点位数。

执行一下，结果左侧是所有合作商信息，右侧就是点位的数量。没毛病吧，兄弟们。

> **易错点**：但小伙伴们，你们课下练习的时候，照抄我这条提示词，**这条 SQL 可能生成不出来**。

为什么？因为我课下的时候手写传统模式的 SQL 写得多了，它**记录并学习过**：知道合作商表的表名和字段信息，也知道点位表的表名和字段信息。所以它能根据我之前的历史记录，生成出这条完整的关联查询。而你们课下没有写过合作商和点位的关联查询，那它生成出来的 SQL 就很可能是**不及预期**的。

小伙伴肯定要问：那怎么办？难道 AI 是摆设吗？

别着急，还记得我们之前学的**提示词工程**吗？我们定义好**角色**、定义好**指令**，还可以结合**上下文**让它去学习。所以有一个通用方案：打开通义灵码的**智能问答**界面，把提示词信息和上下文信息一起告诉它不就行了。

我提前把提示词写好了，大家一起看：

```text
你是一个软件工程师。
现在要根据数据库的 SQL 脚本，查询并显示合作商所有的字段信息，
同时显示每个合作商上的点位数。
SQL 脚本如下：
<这里把合作商表、点位表的建表语句粘进来>
```

上下文怎么准备？在项目里把两张表的建表语句复制过来，点位表的粘一段，换行；合作商表的再粘一段。上下文准备好了，它就能根据我们的提示词生成 SQL 语句了。

回车，耐心等一下。生成出来的思路和本地那份**几乎一样**，只不过它这里指定了返回字段——合作商 id、合作商的名称、点位的数量，其他信息它没展示。而我们前端要展示的合作商信息是比较多的，不可能只展示 id 和名称，所以这一步我们把它改成 `bd.*`；分组字段呢，我们这边只需要根据 id 做分组就可以了。

改完之后你再对比一下，两个答案其实是完全一样的。

> **结论**：如果你本地没让大模型学习到你之前写过的 SQL 语句，那就得**先把上下文的信息喂给它去学习**，然后它才能按你的需求生成我们需要的答案。这一点小伙伴们学明白了吗。

#### 从 VO 到 Controller 的四层改造

拿到 SQL 之后，剩下的活就很常规了。回到 IDEA——VO 对象还记得在哪个包下创建吗？没错，`domain` 包。

我们新建一个合作商的 VO，叫 `PartnerVO`，老规矩让它继承父类 `Partner`。继承完以后在里面定义一个属性叫**点位数量**：

```java
package com.itheima.pojo.vo;

import com.itheima.pojo.Partner;
import lombok.Data;

/**
 * 合作商VO对象
 */
@Data
public class PartnerVO extends Partner {

    /** 点位数量 */
    private Long nodeCount;

}
```

属性名让通义灵码生成之后我们改成 `nodeCount`，get/set 和 toString 都通过 Lombok 注解生成，VO 类就定义好了。

接下来找到合作商的 **Mapper**，在最后一行加一个方法：

```java
/**
 * 查询合作商列表
 * @return 合作商VO集合
 */
List<PartnerVO> selectPartnerVOList(Partner partner);
```

返回值是 `List` 集合，泛型是 `PartnerVO`，方法名叫 `selectPartnerVOList`。通义灵码这里也把参数顺手写成了 VO，我们把 VO 去掉——用**普通实体类**接收就可以了，VO 是给人看的返回结果，查询条件用实体就够。

下面是 XML 的 SQL 语句。把刚才生成的 SQL 复制过来，粘到 Mapper XML 里，注意两件事：

```xml
<select id="selectPartnerVOList" resultType="com.itheima.pojo.vo.PartnerVO">
    select bd.*, count(td.id) as node_count
    from bd_partner bd
    left join td_node td on bd.id = td.partner_id
    <!-- 若依原生的动态查询条件，原样搬过来 -->
    group by bd.id
</select>
```

> **易错点**：**最后一个位置不能有分号**。因为这里要接动态 SQL 条件，还要参与分页查询。
>
> 另外，动态 SQL 那一块该粘在哪儿？我们找到若依**原有**的动态查询 SQL，复制一份——**应该在 `group by` 之前**。换行，粘到这个位置，Mapper 层就定义好了。

接着定义 Service 接口。方法命名的规范呢，**可以和 Mapper 保持一致**——找到 Mapper 接口，把注释补齐（查询合作商列表，返回结果是 `PartnerVO` 集合），然后把这个方法复制下来，粘贴到 Service 接口的位置；再创建实现类，同样加上注释，`Alt + 回车` 创建出方法的实现，复制一份 `PartnerMapper` 的写法，`selectPartnerVOList` 调用一下，把参数传过去。Service 的接口和实现类就定义完了。

最后改造 **Controller**。找到合作商查询列表的位置，原来是查合作商单表数据的，现在我们把它替换成 `partnerService.selectPartnerVOList`，把条件扔过去，返回的结果就是 VO List，**将返回的集合封装成分页对象**返回给前端就可以了。

按 `Ctrl + F9` 让它热更新一下，回到浏览器打开 F12 刷新，观察返回的结果里是不是已经有 `nodeCount` 了。后端这边就算改造完毕。

#### 前端加一列点位数

回到 VS Code，找到合作商表格部分，在**合作商名称的下方复制一份**，列名叫「点位数」，`prop` 属性改为 `nodeCount`。

回浏览器看效果：合作商 A、合作商 B 有点位数；刚新增的船只合作商和黑马合作商没有点位，所以这里显示 **0**。再测一下条件搜索，搜索「船只」，也没毛病。

到这里，**查询合作商列表时同时显示每个合作商的点位数**，前后端代码就改造完毕了。

> **结论**：这一节的完整链路是——关联查询定方案 → AI 辅助编程生成 SQL（注意补上下文）→ 创建合作商 VO 对象 → 编写 Mapper 方法以及 XML 动态 SQL → Service 接口与实现类（直接复制 Mapper 的方法就行，这部分比较简单）→ 改造 Controller，把单表查询换成多表查询并把结果封装给 VO 返回前端 → 最后改造前端展示点位数。

### 给合作商做重置密码

合作商管理最后一个需求：**作为管理员，能够为每一个合作商重置密码，并且将初始密码统一设置为 123456**。

目前若依框架**并没有**为我们提供这一功能的现成代码，所以需要我们自己动手设计并实现。

那从哪儿着手呢？这就要回顾一下前后端分离项目的开发流程：

```text
        ① 查看原型 → 确定需求
                         │
                         ▼
        ② 设计接口文档（前后端沟通的桥梁）
             请求方式 · 请求路径 · 参数 · 预期的返回结果
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
      后端：Controller          前端：视图组件
             Service                API 请求 JS
             Mapper
             │                       │
             └───────────┬───────────┘
                         ▼
                   ③ 前后端联调测试
```

接口文档是前后端沟通的桥梁，它包括了请求方式、请求地址参数以及预期的返回结果；后端工程师根据接口文档开发，前端工程师也依据接口文档和需求开发界面。我们这门课程目的是培养大家的全栈开发能力，所以在这个环节，我们将**亲自动手同时完成前后端代码的编写**。

#### 需求、接口与三步实现

回到浏览器里的管理员页面，点击「重置密码」，会弹出一个对话框问你确定要重置该合作商密码吗。当管理员点击确定，就会向后台发送请求完成密码的重置；操作成功以后前端会提示操作完成的提示信息。但如果点击取消，我们不做任何操作。这就是页面原型和需求说明。

再看接口文档。请求方式为 **PUT**，请求路径为 `/manager/partner/resetPwd`，这是 password 的缩写 **PWD**；通过路径传递了合作商的 id。请求发送成功以后，后端就会拿到合作商的 id，以它为条件就可以重置密码了。操作成功以后，后端返回结果里有 message（返回内容）以及 code（状态码），前端就可以据此提示操作成功还是失败。

实现思路：后端部分，在合作商的 Controller 当中新增一个方法负责重置密码的请求，具体的操作细节有**三步**。前端部分要修改**两个文件**：一个是 partner.js，在里面抽取一个用于重置密码的 API 请求方法，通过 Ajax 向服务器发送请求并处理返回结果；另一个是合作商的视图组件页面，实现界面上的重置密码功能，确保它能调用我们定义的 API 请求并处理用户的交互逻辑。分析完以后，先写后端再写前端。

回到 IDEA，找到合作商的 Controller，在当前类的尾部增加一个新的方法，先写上注释「重置合作商密码」：

```java
@PreAuthorize("@ss.hasPermi('bd:partner:edit')")
@Log(title = "重置合作商密码", businessType = BusinessType.UPDATE)
@PutMapping("/resetPwd/{id}")
public AjaxResult resetPwd(@PathVariable Long id) {
    // 1. 接收请求参数
    //    即合作商id，路径变量已自动绑定

    // 2. 创建合作商对象，设置 id 和加密后的初始密码
    Partner partner = new Partner();
    partner.setId(id);
    partner.setPassword(SecurityUtils.encryptPassword("123456"));

    // 3. 调用 service 更新密码
    return toAjax(partnerService.update(partner));
}
```

这里有几个细节要掰开说：

- 请求路径前两层类上已经定义好了，我们只写 `resetPwd/{id}`；
- 方法返回值参考之前写的 `AjaxResult`，方法名也叫 `resetPwd`；
- **上面那两个注解别忘了**：第一个做权限控制，第二个做日志记录，这一部分我们在前面已经学过了。思考一下——重置合作商密码需不需要权限控制，需不需要日志记录？答案肯定是需要的。重置密码也是修改数据库的一种操作，所以完全可以**参考之前的修改代码**，把这两行拿过来直接用，只把日志记录的描述信息改成「重置合作商密码」即可，其余保持一样。

第二步里，通义灵码结合上下文注释已经把密码设置好了，只不过这个密码是明文的 `123456`。**明文安全吗？不安全。** 那怎么办？是不是要进行加密啊？还记得加密的工具类吗——`SecurityUtils`，方法叫 `encryptPassword`，把密码设置进去。

第三步，通义灵码连 `partnerService.update` 都帮我们做了补全，按 Tab 就能用：以 id 为条件，把加密后的密码更新到数据库当中。把返回的结果交给 `toAjax` 方法，转换成 JSON 格式返回给前端。

至于通义灵码是怎么知道要调 `toAjax` 的？其实它学习了我们的其他方法——看到没有，我们的删除操作、修改操作也是这么干的。

> **易错点**：初始密码 `123456` **必须先加密再入库**，绝不能把明文密码直接写进数据库。前面新增合作商的时候，我们就已经用 Spring Security 的这套工具对密码做过加密了。

#### 前端：从删除按钮抄一份

前端这段，大家思考一下该怎么写？如果还没有思路没有关系——我们可以**借鉴已有的实现：若依的删除按钮**。

删除按钮点下去，同样会弹出一个对话框，点击确定完成删除，点击取消不做任何操作。这个效果和我们原型里「重置密码」的效果非常相似。回 VS Code 定位到删除按钮，看看 `handleDelete` 这个方法：

```text
 点击「删除」
        │
        ▼
 const id = row.id                     ← 1. 先取出当前行 id
        │
 ElMessageBox.confirm(...)            ← 2. 弹出确认框（点击取消则到此为止，不做任何操作）
        │
        ▼
 .then(() => { 删除请求 })            ← 3. 点确定：向后端发送请求完成删除
        │
        ▼
 .then(() => {                        ← 4. 后端返回成功
     getList()                        ←    重新查询最新数据并刷新页面
     ElMessage.success('删除成功')      ←    再提示操作成功
 })
```

整个执行流程不就跟原型对上了吗？点击确定向后端发送请求，点击取消则不做任何操作，确定成功以后提示操作成功的消息。所以删除按钮的功能与原型中重置密码的效果是一致的，**这一部分的逻辑可以直接借鉴过来**。

那就开始动手。回到 VS Code，分三步走：

**第一步，把抽取好的方法引入进来。** 定位到视图组件 JS 代码的头部，把刚才从 partner.js 复制的方法名完成导入。

**第二步，添加重置密码按钮。** 重置密码按钮的权限和修改按钮是一样的，所以以修改按钮为模板复制一份，把名称改为「重置密码」，指定方法名为 `handleResetPwd`。

**第三步，实现方法细节。** 参考删除按钮，先加注释「重置合作商密码」，加 `function` 关键字。第一行取出合作商 id，直接复制删除的那行，只不过我们这里取出的是**单个 id**，所以那个 `s` 给去掉；第二行把确认框那一部分整体粘过来。

> **易错点**：确认框的提示信息这里我们**偷个懒**，直接参考页面原型里的原文，不另写了——CV 大法。

`.then` 里面调刚刚抽取好的 API 方法 `resetPartnerPwd(id)`，这里的 id 是没有 `s` 的，替换掉。还有一个**关键区别**：重置密码成功以后**不涉及数据的新增操作**，所以没必要再向后端发送一次查询请求，这个 `getList()` 删掉；提示信息也不再是「删除成功」，而是「重置密码成功」。

回到 partner.js，我们再把 API 方法补上。同译灵码结合我们的注释生成了一段代码，我们检查一遍：

```js
/**
 * 重置合作商密码
 * @param {*} id
 */
export function resetPartnerPwd(id) {
  return request({
    url: '/manager/partner/resetPwd/' + id,
    method: 'put'
  })
}
```

- `export` 导出方式没问题，方法名 `resetPartnerPwd` 也可以用；
- **方法参数注意**：接口方法传递的是 id，所以这里不是 data，改为 `id`；
- 请求地址 `/manager/partner/resetPwd` 跟我们接口文档保持一致，后面补上 id，用 `+` 拼接，通过**路径传参**；
- 请求方式为 `put`，没问题；我们没有请求体参数，所以把 `data` 删除；
- 还有一个小的细节：**拼接 id 的时候少了一个路径的正斜杠**，别忘了给它补上。

测试一下：回浏览器找到管理界面，多了「重置密码」按钮，现在比较丑没关系，先测功能。点击弹出对话框提示确定要重置合作商密码吗，点取消不做任何操作，点确定向后端发送请求重置成功。再观察数据库，打开合作商表，第三行船只合作商的密码**已经进行了加密的操作**了，证明功能生效。

最后收个尾：调整「操作」这一列的宽度，让它看起来更加美观，给列加一个宽度属性，设置为 `300` 像素。现在操作列四个按钮——重置密码、查看详情、修改、删除——就跟原型保持一致了。

> **结论**：整个功能是**根据接口文档**完成前后端代码编写的。后端在 Controller 中定义一个方法处理重置请求，接收 id 作为路径参数，创建合作商对象并设置**加密后的**密码，调用 service 完成更新并返回结果；前端先在 API 请求 JS 中抽取 `resetPartnerPwd` 方法，然后在视图组件中加按钮，交互流程参考删除逻辑——点击弹确认框，点确定调用 API 请求，点取消不做操作，成功后提示重置成功。

#### 复用分页接口，把「全部」数据查出来

要把区域文本框改成下拉框，前端得先有数据。怎么拿？思路很简单：在点位管理页面里，通过**区域的 API** 向后端发送查询请求，后台返回区域列表，前端遍历展示即可。

但先别急着写，回到 IDEA 看一下区域的 Controller，看它有没有现成的列表查询方法。打开 `RegionController`，**第一个方法就是查询区域列表**，看起来好像能直接用——但这个方法内部第一行通过 starter 配置开启了分页查询，它接收前端的当前页和每页个数，通过分页插件实现分页查询，调用 service 返回一个 List，然后再通过 `getDataTable` 返回一个**分页对象**。

能不能直接用它？看起来是不行的，因为它返回的是**分页后的结果集**。那有没有其他方法可以用呢？其他方法就是若依生成的传统增删改查，**并没有提供一个单独查询列表的方法**。

这时有小伙伴会说：那我们可以为这个需求再写一套后端的查询方法。但这么做会**耗时耗力**。为了避免这种麻烦，我们能不能**复用现有的分页查询方法**？怎么复用？其实我们可以**调整一下前端的请求参数**：

```text
区域列表接口 /manager/region/list
  默认：pageNum=1, pageSize=10   → 只拿到前 10 条

  改：pageNum=1, pageSize=10000 → 一次性把区域全查回来
                                  后期区域数据不太可能超过 1 万条
                                  从第一页开始查就相当于查询所有数据
```

后端把处理后的结果封装给分页对象，我们**单独取出里面的 `rows`**，然后在前端遍历这个结果展示给用户。

```java
@GetMapping("/list")
public TableDataInfo list(@RequestParam(defaultValue = "1") Long pageNum,
                          @RequestParam(defaultValue = "10") Long pageSize) {
    startPage();
    List<BdRegion> list = regionService.selectBdRegionList(new BdRegion());
    return getDataTable(list);
}
```

这么做的好处呢：**提高了后端接口的复用性，减少了代码的编写量，也提升了开发效率**。大家能接受这种方法，那接下来的改造就只需要修改前端代码，以适应这种「查所有数据」的方式。

#### 数据源怎么在前端落地

回到 VS Code，找到点位管理的视图组件 `index.vue`。当前页面要调用区域的 API，同样需要通过 `import` 完成导入：

```js
import { listRegion } from '@/api/manager/region'
```

这个 `@` 就相当于我们的 `src`——从 src 下面找到 api，找到 manager，定位到 region 就可以了。

接下来定义一个查询区域列表的方法：

```js
/**
 * 查询区域列表
 */
function getRegionList() {
  listRegion(loadAllParams).then((response) => {
    regionList.value = response.rows
  })
}
```

这里有两个响应式定义的区别要分清楚：**响应式对象定义有两种方式，一种叫 `ref` 它定义简单类型，一种叫 `reactive`**。我们这个对象里面需要存两个参数（`pageNum`、`pageSize`），所以不能用 `ref`，而要改成 `reactive`。

```js
// 查询所有的条件对象
const loadAllParams = reactive({
  pageNum: 1,
  pageSize: 10000
})

// 区域列表，简单类型集合，用 ref 定义即可
const regionList = ref([])
```

`listRegion` 需要接收前端查询的条件，对应的就是这个 `loadAllParams` 对象——包含 `pageNum`（当前页）、`pageSize`（每页个数）。这里我们从第一页开始查，一页查询一万条，下面的 `regionName` 等其他参数我们不需要，只保留 `pageNum` 和 `pageSize`。

返回的结果是一个**分页对象**，里面定义了 `rows`，就相当于我们的整个分页对象了，它包含 `total`、`rows`。所以通义灵码专门把分页结果集取出来，封装给 `regionList` 这个响应式集合。这里它多了个小括号，删掉就可以了。

那这个方法该在哪儿调用呢？参考点位管理的分页查询——最后一行有个 `getList()` 方法，当页面加载到那儿时就会调用它向后台发送查询请求并接收分页数据。我们**在这个方法的上一行**去调用 `getRegionList()`，这样页面一加载完，区域列表就查回来了。

回浏览器打开 F12 刷新验证：倒数第二条记录，当前页是 1，每页个数传的是 1 万，请求地址就是 `/manager/region/list`，返回结果就是所有的区域列表，我们把 `rows` 单独封装给 `regionList`，这个集合里就存储了所有区域信息了。

> **提示**：`loadAllParams` 这个「查全量」的响应式对象，我们在区域与合作商两个查询方法里都在用，而在当前页面中这是很常见的业务场景——**其他视图组件也会需要它**。所以在每个视图页面都编写一次就过于繁琐了，这个代码可以单独抽取到 JS 文件当中，哪一个视图页面想使用直接引入即可。
>
> 我已经提前把它放到 `api` 目录下面了，有一个叫 `config.js` 的文件：

```js
// src/api/config.js
import { reactive } from 'vue'

// 查询所有的条件对象
export const loadAllParams = reactive({
  pageNum: 1,
  pageSize: 10000
})
```

在点位管理的视图页面里，只要通过 `import` 导入就行了：

```js
import { loadAllParams } from '@/api/config'
```

#### 区域与合作商的文本框换下拉框

数据有了，现在把条件搜索区的区域文本框改掉——原来那个文本框注释掉，换成下拉框：

```html
<el-form-item label="区域搜索" prop="regionId">
  <el-select v-model="queryParams.regionId" placeholder="请选择区域" clearable>
    <el-option
      v-for="item in regionList"
      :key="item.id"
      :label="item.regionName"
      :value="item.id"
    />
  </el-select>
</el-form-item>
```

`el-select` 里面需要运用三个属性：第一个 `v-model` 是做**双向绑定**的，没问题；第二个 `placeholder` 是做**占位符提示**的，只不过我们占位符提示的不再是「请输入区域 id」了，而是「请选择区域」——把 id 删除，把输入改为选择；第三个属性 `clearable`，用来清理搜索条件。

定义好之后再定义子标签 `el-option`。在 `option` 当中我们需要做一个 `v-for` 的遍历，遍历的集合就是 `regionList`，遍历的元素咱们就叫 `item`。每一个元素需要设置一个唯一标识 `:key`，这个唯一标识就使用 `item.id` 就可以了。接下来还需要定义一个 `label` 属性用于展示下拉框显示的名称——`:label="item.regionName"` 展示名称，而我们提交的值是区域 id 作为条件搜索的，所以 `value` 我们这里使用的就是 `item.id`。

回浏览器测试：文本框已经改为了下拉框，里面展示的是所有区域信息。搜索「朝阳区」点击搜索，真正传入的条件 id 还是 1，展示的是三里屯；再改成「北京海淀区」，展示的是五道口的信息；其他区域没有数据所以查不到。

还有一个**小的细节**：区域搜索这一块的 label 名称不应该是「区域 id」，应该是「**区域搜索**」，我们把这个 label 改一下。


> **结论**：写这段代码时，**前提条件是你需要把注释写好**。注释写到位了，通义灵码完全学习了我们刚刚查询区域列表的那一部分——调用 `listPartner`、把查询所有的条件定义过去、向后台发送请求、返回 `response` 分页对象、把 `rows` 单独定义给 `partnerList` 集合——**效率就会翻倍**。这样也顺便解决我们在传统开发时不喜欢写代码的坏习惯了。

页面的 `getPartnerList()` 调用同样放在底部位置，和 `getRegionList()` 放一起。F12 一刷新就能看到两个查询一万条数据的请求，一个查合作商，一个查区域。

然后把**新增/修改对话框**里的文本框也换掉：定位到合作商 id 原来的文本框，先注释掉换行——注意看，结合上下文以及我们刚刚写的条件搜索代码，通义灵码直接帮我们生成了 `el-select` 和 `el-option` 两个标签，实现了下拉框的改造。其中 `el-select` 通过 `v-model` 实现双向绑定，跟上面保持一致；`placeholder` 也是「请选择区域」，只不过 `clearable` **这个属性我们是不需要的**，因为它不是条件搜索部分，不需要做清除。`el-option` 里 `v-for` 实现了遍历循环，`:key` 实现了唯一标识的指定，`:label` 实现了区域名称的展示，`:value` 实现了数据提交。

## 把四张表揉进一个接口：点位列表改造与区域详情
> 对应块：BLK11 | 覆盖分集：P34-P35 | 块标题（分集名）：《实战篇-13.帝可得-点位管理改造-列表查询》

点位管理视图组件的基础布局展示，我们已经改造完了。接下来是三个改造需求，而第一个——点位的查看详情——要先搁一搁。

### 剩下的改造需求

点击某个点位查看详情时，我们希望展示该点位下所有的售货机，也就是设备列表这个功能。可以打开设备管理模块的原型来对照，`设备管理` 页面上展示的那些信息，就是我们要的效果。

为了实现这一功能，我们计划复用若依已经生成的查询设备列表接口。这样做不仅可以减少开发工作量，还能确保代码的整洁和一致性。具体的改造需求会在设备管理模块的后续开发中一并完成，所以这个功能先给它搁置。

第二个需求：在区域管理界面的"查看详情"对话框中，需要展示点位列表，以及每个点位下的设备数量。这里会涉及到点位和设备的多表查询。我们之前提到过，此功能可以复用点位列表的同一个接口来实现，所以这个需求与第三个需求一起完成。

第三个需求就是这次的主线：在查询点位列表中，我们不仅要展示点位的信息，同时还要关联显示区域、合作商等信息。要实现这个功能，就需要后端把设备数量、区域、合作商等信息一并查出来返回，这样前端界面就可以展示这些关联的数据了。

### 四张表的关系

这一共涉及到四张表，我们先来看一下它们之间的表关系。

区域和点位之间是**一对多**，我们可以通过点位的外键 `region_id` 来查询区域的信息，这一段大家并不陌生了。合作商和点位也是一对多，通过合作商的外键 `partner_id` 来查询合作商的信息。最后是点位和设备的关系：一个点位下可以包含多台设备，而每一台设备从属于一个点位，所以它们也是一对多，我们可以根据点位的 id 来统计设备的数量。

```text
      tb_region            tb_partner
          │ 1                  │ 1
          │                    │
          │ N                  │ N
          └────┬───────────────┘
               │ 1
          ┌────┴────┐
          │ tb_node │
          └────┬────┘
               │ 1
               │ N
          ┌────┴─────┐
          │ tb_device│
          └──────────┘

  region_id   ：tb_node.region_id  →  tb_region.id
  partner_id  ：tb_node.partner_id →  tb_partner.id
  node_id     ：tb_device.node_id  →  tb_node.id
```

图里三条连线全是"一对多"，而查询的起点始终是中间的 `tb_node`：区域、合作商是从点位这头往上找，设备是从点位这头往下找。记住这三把外键钥匙，后面的 SQL 和 XML 全都围着它们转。

### 四张表一起查，凭什么不炸

在之前的课程当中，我们学习了区域和合作商统计点位数量，是通过关联查询来实现的。但这种方案存在一些挑战：当涉及的表较多、数据量较大时，SQL 的编写难度就会增加，如果产生笛卡尔积，数据量就会急剧增加，有可能导致内存溢出的问题。

咱们当下的功能是不是符合这个场景？一共有四张表，是不是表比较多？而且设备数据量是比较大的，产生的笛卡尔积极有可能导致内存溢出。

面对这种情况，我们采用了两种策略来解决：

1. **设备数量的统计**：仍然执行关联查询。这种方案可以确保数据的实时性和准确性，因为设备数量是实时计算的，不需要单独维护。
2. **区域以及合作商的数据**：采用 MyBatis 提供的嵌套查询功能，结合关联实体完成 ORM 映射。这种方法是将原本的多表联合查询拆分成单个表的查询，然后再利用 MyBatis 语法将它们嵌套在一起，通过定义的 `resultMap` 标签完成手动映射，里面包含 `association` 以及 `collection` 元素完成嵌套的关联。

使用 MyBatis 嵌套查询的好处在于：我们将复杂的多表查询分解为更简单、更容易管理的单个表的查询，这么做不仅简化了 SQL 语句的编写，而且提高了查询的效率和性能；有效地解决了多表关联查询当中的难题，避免了内存溢出的风险，同时保持了代码的整洁和可维护性。

> **结论**：设备数量走关联查询（保实时、保准确），区域与合作商走嵌套查询（保简洁、避笛卡尔积）。

#### association：一个点位只有一个区域

`association` 标签是用来解决一对一或多对一的映射结果封装，即结果中只有一个对象时完成的 O2M 的映射封装。

什么意思呢？比如说我们现在是以点位为中心去查询区域表或合作商表的详细信息，它的返回结果集是不是只有一个对象？一个点位是不是只对应一个区域？一个点位是不是也只对应一个合作商？所以这个时候我们就可以选择 `association` 标签来完成一对一或多对一的映射，点位和区域、点位和合作商就是多对一。

#### collection：一个区域下面有一堆点位

`collection` 标签是用来解决一对多的场景下来映射多个结果的集合。

比如说我现在想查询单个区域表的信息，同时查询该区域下面所有的点位列表，那么根据区域 id 查询的点位列表是不是包含多个结果集？那么你要映射的应该是一个集合，这个时候我们就可以选择 `collection`。同理，你如果想统计某个合作商下所有的点位信息，也包含多个结果集，也需要采用 `collection`。

通过这两个标签，我们就解决了多表关联的映射查询的结果封装，并把它映射到对应的实体上，就能实现高效的嵌套查询了。

### 定义 NodeVO：多出来的三个属性

回到 IDEA，打开 domain 包，右击新建 `NodeVO`。

首先呢我们先让 `NodeVO` 去继承原有的父类 `Node`，直接可以使用点位原有信息。在此基础之上，我们还要增加三个属性：第一个是设备数量 `private Integer vmCount`；第二个呢是区域信息，我们关联的是实体，所以这边定义的类型是 `Region`，属性名呢我们也叫做 `region`；再往下走就是合作商的信息，同样的也是关联实体，定义一个 `Partner`。最后给这三个属性增加 getter、setter 方法以及 toString，增加一个 `@Data` 注解。

```java
package ...domain.vo;

import ...domain.Node;
import lombok.Data;

/**
 * 点位管理列表查询结果
 */
@Data
public class NodeVO extends Node {

    /** 设备数量 */
    private Integer vmCount;

    /** 区域信息 */
    private Region region;

    /** 合作商信息 */
    private Partner partner;
}
```

### NodeMapper：从自动映射切到手动映射

找到 `NodeMapper`，在最后一行当中我们增加一个新的方法，`public` 返回值是一个 List 集合，泛型就是 `NodeVO`。通义千问已经帮我们准备好了方法名和参数，咱们先使用一下，按一下 Tab 键接收，这个参数我们使用 `Node` 就可以了，把 VO 去掉。给此方法补上中文注释，然后选中方法名，按下 Alt + Enter，通过 MyBatis 插件帮我们生成 XML 标签。

首先呢我们把关联查询的 SQL 语句拿过来，直接粘贴。复制过来之后呢，我们还要增加动态 SQL 的标签：找到若依原有生成的代码，一共有三个条件，咱们把它复制一下，粘贴到 `GROUP BY` 关键字之前。第一个是根据点位名称做模糊查询，第二个是根据区域 id 查询，第三个是根据合作商 id 进行查询。

至此，查询点位列表同时统计设备数量的 mapper 层代码就完成了。接下来呢我们就要使用 MyBatis 的嵌套查询功能，来实现点位关联区域以及合作商结果的映射。

> **易错点**：我们的 SQL 之前是通过 MyBatis 的 `resultType` 属性完成了自动映射封装，直接把结果映射给 `NodeVO` 的实体类。而嵌套查询**不能**使用 `resultType` 属性做自动映射了，而要改为 `resultMap` 属性完成映射。

所以这个属性我们先修改一下，改为 `resultMap`，值呢我们叫做 `NodeVOResult`。这个 `resultMap` 标签还不存在，所以咱们往上拉增加一个 `resultMap` 标签：这个 id 就是我们刚才编写的 `NodeVOResult`，而 `type` 属性对应的是我们最终映射的实体类，这里我们选的是 `NodeVO`。

```xml
<resultMap id="NodeVOResult" type="NodeVO 的全限定名">

    <!-- 点位基础信息：若依生成的 result 标签，直接复制过来 -->
    ...

    <!-- 设备数量：需要我们手动映射 -->
    <result property="vmCount" column="vm_count"/>

    <!-- 区域信息：多对一，用 association -->
    <association property="region" javaType="Region" column="region_id"
                 select="RegionMapper 的全限定名 + selectRegionById"/>

    <!-- 合作商信息：多对一，用 association -->
    <association property="partner" javaType="Partner" column="partner_id"
                 select="PartnerMapper 的全限定名 + selectPartnerById"/>
</resultMap>
```

#### result：把设备数量对上号

先回到接口文档这一部分，截张图缩小放到右上角的位置，回到 IDEA。

首先上半部分我们还需要返回点位的基础信息，而这个基础信息呢，若依生成代码当中已经包含了这些标签了，我们直接把这部分复制拿过来即可使用。

除了有点位的基本信息之外，我们还要包含设备的数量，那这个呢需要我们手动映射。`result` 标签当中有两个属性：第一个呢叫 `property`，对应的是我们 `NodeVO` 实体类的属性名，咱们就叫 `vmCount`；而第二个属性 `column`，它对应的是我们数据库查询返回的字段，而这个返回字段呢我们用的是 `vm_count`（把标签起的内容改为单标签）。

那现在呢我们通过 `result` 标签，已经将包含的设备、也叫售货机的数量映射给 VO 了。

#### association：把区域挂进来

那下面呢就到了我们的重点了：我们需要将区域的信息以及合作商的信息通过嵌套关联映射给 `NodeVO`。那么这个嵌套查询我们使用的是 `association` 标签还是 `collection` 标签？来兄弟们把答案在弹幕当中走一走——咱们是多对一的查询，所以选择 `association` 标签。

我们先来关联映射区域信息。这个标签的第一个属性 `property` 对应的也是我们 `NodeVO` 区域信息的属性名，这里叫做 `region`；在里面还要用到第二个属性叫 `javaType`，它对应的是 Java 的类型，而区域的类型呢就是 `Region`；第三个属性是 `column`，它是来指定区域的外键字段 `region_id`，以它为条件去执行查询。而查询的 SQL 语句呢，就是我们刚刚在这里面定义的 `SELECT * FROM tb_region WHERE id = #{region_id}`——条件 id 后面等于的就是这个 `region_id`，我们区域的外键。如果你查询的点位外键是 1，那么他就会获取 1 的区域信息；如果你查询点位为 2，那么他就获取 2 的区域信息。

好，那在这里面呢我们再来写一个属性叫 `select`。那 `select` 后面跟什么呢？咱总不能去跟这个 SQL 语句吧，因为这个 SQL 语句的条件咱们不能写死啊。那怎么办呢？

我们可以这样：`select` 属性呢，我们需要指向区域 mapper 层根据 id 查询区域信息的一个方法，而这个方法呢若依也帮我们提供好了。找到 `RegionMapper`，往上拉，就在这里 `selectRegionById`。那么这个 id 呢就是我们点位表区域的外键字段。接下来呢我们就需要拿到方法的全限定名——定名是接口的全名加上方法名，右击 `Copy Reference`。接下来呢我们把这个全限定名粘过来，包名加接口名加方法名，这就是此方法的全限定名。MyBatis 底层呢会通过反射来执行当前方法，根据区域的外键 id 来查询区域的信息。给它增加一个自闭合的标签。

> **提示**：`select` 后面跟的是方法的全限定名，不是 SQL 语句。直接用 IDE 的 `Copy Reference` 复制最省事，也最不容易写错包名。

#### 嵌套查询的执行流程

这个标签的整体执行流程，我再给兄弟们来解释一下。

首先我们执行了点位的关联查询，那么它的返回结果当中呢就会包含这个 `region_id`——回到数据库执行一下那段 SQL，就可以拿到每个点位的区域外键以及合作商的外键信息了。拿到这个信息以后呢，回到我们的代码当中，就可以把这个 `region_id` 作为条件放入到 `column` 当中，然后呢去执行区域当中的 `selectRegionById` 方法。

那这个方法呢他在执行的时候，就需要我们传递区域的 id，以他为条件呢，就把区域的信息拿到手并封装给这个 `Region` 对象。而这个返回的 `Region` 对象呢，我们最终需要映射给 `NodeVO` 的 `region`。那他怎么做到映射呢？我们需要在 XML 当中去指定映射的属性名以及 Java 的类型，这样的话我们就完成了 MyBatis 的嵌套查询。

```text
      点位关联查询   SELECT * FROM tb_node ...  LEFT JOIN 统计设备数
              │
              │  每一行都携带 region_id / partner_id / vm_count
              ▼
    ┌───────────────────────────────────────────┐
    │  resultMap = NodeVOResult   type = NodeVO  │
    └───────────────────────────────────────────┘
              │            │               │
     column=region_id   <result>    column=partner_id
              │        vm_count             │
              ▼            ▼                 ▼
   selectRegionById   → NodeVO.vmCount   selectPartnerById
        (Region)                            (Partner)
              │                               │
              ▼                               ▼
      NodeVO.region                     NodeVO.partner
```

图里那条主线是"外键值从点位行里被取出来，再被当作入参交给另一个单表查询"，`column` 就是这条线上的接力棒，`select` 是接力棒交到的那只手。

在编写 SQL 时，`selectRegionById` 就是一个单表查询，然后呢通过 MyBatis 的这个标签呢，我们将两个查询嵌套到一起，最终呢封装给 `NodeVO`。这就是嵌套查询的一个基本流程。

#### association：把合作商挂进来

接下来呢我们实现点位合作商的嵌套映射。回到 `NodeMapper`，咱们再来增加一个 `association` 标签。通过刚才的讲解，大家看一下这个 `property` 你应该写什么？是不是应该写 `NodeVO` 当中 `partner` 这个属性的名称，来粘过来。

它对应的类型呢也是 `Partner`；作为外键的字段应该用的是 `partner_id`；而我们通过 `select` 属性呢，需要指定合作商根据主键查询的方法。而这个方法呢我们需要找到合作商的 Mapper，往上拉，找到 `selectPartnerById`，右击复制此方法的全限定名，在这里我们直接粘过来，把标签改为自闭合。合作商的关联嵌套映射呢我们也就完成了。

通过刚才的练习，我们对于这四个属性现在有一个初步的掌握：`property` 对应的是 `NodeVO` 的属性名；`javaType` 对应的是该属性的 Java 实体类型；而 `partner_id` 就作为点位数据的外键 id，以它为条件去执行 `PartnerMapper` 的方法，完成合作商信息的查询，再把查询信息的结果封装给 `NodeVO` 里那个属性实体类当中，完成嵌套关联的组合映射。

到这儿嵌套查询的代码就编写完毕了。

> **结论**：mapper 层的思路是这样的——先做点位列表与设备数量的关联查询；这个查询结果需要做**手动映射封装**，而手动映射封装的目的正是为了实现多表的嵌套组合查询：一个根据 `region_id` 查区域表信息封装到 `NodeVO` 当中，一个根据 `partner_id` 查合作商信息也封装到 `NodeVO` 当中。做完之后，`NodeVO` 就可以返回四张表的数据——点位基本信息、设备数量、区域以及合作商的信息。

### Service 与 Controller

mapper 层思路给兄弟们整理完了，接下来呢我们来编写点位的 service 层。找到 service 接口，在最后一行我们也来定义一个查询点位管理列表的方法，而这个方法命名呢，我们完全可以参考 mapper 层——找到 `NodeVO` 这个方法和它的注释，把这个方法和注释复制一下，粘到 service 接口当中。

按 Alt + Enter 创建出 service 的方法实现。在实现当中呢，我们直接调用 `NodeMapper` 的 `selectNodeVOList`，把条件呢给他传过去，把方法注释从接口部分复制拿过来粘贴好。这样接口和方法实现我们就定义完毕了。

接下来我们来修改一下 `NodeController` 层的代码。原来呢是查询点位单表的基本信息，这样代码呢我们把它删除，改为调用 `nodeService` 的 `selectNodeVOList` 方法，把条件传过去，返回值呢就是 `voList`，再把 `voList` 交给分页对象返回到前端即可。

```java
@GetMapping("/list")
public TableDataInfo list(Node node) {
    startPage();
    List<NodeVO> voList = nodeService.selectNodeVOList(node);

}
```

### 二义性报错：给条件加表别名

此功能还有一个小 bug，我们需要解决一下。目前呢我们根据点位名称搜索是没有问题的，来测试一下，没毛病吧。但是呢我们根据区域条件搜索时呢，点击执行程序就会报错——这是一个 SQL 的完整性错误。

那现在有小伙伴说这个错误我看不懂，那怎么办呢？不用担心，我们是不是还有 AI 辅助工具通义千问？让这个哥们儿来帮助我们分析这个错误。首先呢我们回到 IDEA，找到控制台，将错误信息先复制出来，交给通义千问，让他帮我们来分析错误信息，找出可能导致错误的原因，点击执行。

现在我们可以看到，通义千问已经帮助我们分析出错误的原因了，并提供了一些解决方案。只不过这些解决方案呢是英文的信息，对于我们初学者来说并不是特别友好，所以我们可以让它翻译成中文，让它重新生成一次。

这里告诉我们的错误类型以及错误的原因：他说我们的 SQL 查询的 `where` 子句当中使用了 `region_id` 作为条件，但是他没有指定是哪张表的，是 `tb_node` 还是设备表的，所以就出现了二义性的问题；并告诉了我们此错误出现的位置——`NodeMapper` 的 XML 映射文件当中，还给我们提供了解决方案。那这个解决方案呢，就是原来是没有指定表的名称，而现在呢我们需要加一个表的别名。

之前的课程也提到过多表查询对于条件字段我们一定要加别名，而我们刚刚复制的这一部分代码呢，是不是没有加别名？坑都踩到这里了没有关系，兄弟们。在真正的企业开发当中，我们每天不是在写 bug，就是在解决 bug 的路上，而现在呢我们学会了通过通义千问来提高我们解决问题的这种能力，是不是非常的棒啊？

那下面呢我们就根据通义千问提供的解决方案来优化一下：将这些条件呢我们加一个表的别名——第一条件 `n.node_name`，第二条件 `n.region_id`，第三条件 `n.partner_id`，代码就改造完了。

> **提示**：为什么我根据 `node_name` 查询没有加表的别名，他不会报错呢？因为在设备表当中它是没有 `node_name` 这个字段的，不会产生二义性。但是这个 `region_id` 和 `partner_id`，在设备表当中以及点位表当中都存在这两个字段，如果你不加别名的话，他不知道你用的是点位表还是设备表。为了防止出现类似的问题——我们不能确定这两张表当中哪些是公共字段、哪些是独有的——所以我们建议这些条件呢咱们都增加下表的别名，这样的话我们就避免了错误的发生了。

好那代码咱们已经解决完了，按一下 `Ctrl + F9` 热部署更新一下环境，我们来测试一下。兄弟们看一下，我们再点击搜索，是不是就没毛病了？北京朝阳区查到了，再来测试一下，北京海淀区也查到了。通过这个过程，我们掌握了利用 AI 工具来提高解决问题的能力。

> **结论**：这次改造的完整脉络是这样的——需求上，区域详情和点位分页查询共用一个接口，一共涉及到区域表、合作商表、点位表以及设备表四张表；方案上，点位 + 设备数量用关联查询保实时，区域与合作商用 MyBatis 的嵌套查询（`resultMap` 手动映射 + `association` 关联进 `NodeVO`），换来更低的 SQL 复杂度和避开笛卡尔积内存溢出的风险；工具上，用 AI 辅助结合 prompt 生成关联查询的 SQL，再根据区域的外键字段查区域信息、合作商的外键字段查合作商信息，最后通过 MyBatis 将这些单表查询牵到一起封装给 `NodeVO`；代码上，定义了包含 `vmCount`、`region`、`partner` 的 `NodeVO`，编写了 `NodeMapper` 的查询方法与 XML 中的手动映射标签和动态 SQL，再由 Service 调用 Mapper，最后改造 Controller 返回四张表的数据；前端拿到分页数据以后，就可以显示所在区域的名称以及合作商的名称了。

> **结论**：区域查看详情的实现步骤是这样的——添加一个"查看详情"按钮并绑定事件，调用 `getRegionInfo` 方法来查询区域和点位的信息，还指定了按钮的权限 `manager:node:list`；在方法内部呢，我们先查询区域信息，这里参考的是修改按钮的部分，而查询点位列表我们需要引入点位的 API JS 文件，同时呢还需要引入查询所有的条件对象 `loadAllParams`，只不过这个条件对象呢我们还需要添加一个 `regionId` 来查询当前区域下面的所有点位列表，把查询结果呢封装给 `nodeList`；然后呢我们定义了查看详情的对话框，通过复制表单项显示区域的名称，再复制点位管理的表格来显示序号、点位名称以及设备的数量，最终呢就可以实现区域详情的展示了。

### 本讲提到的题目

**题目**：`association` 和 `collection` 这两个标签分别用来解决什么关系？在"点位关联区域与合作商"这个场景里，应该选哪一个？

**分析**：判断依据只有一条——要映射的对象是一个，还是一堆。`association` 用来解决一对一或多对一的映射封装，结果中只有一个对象时用它；`collection` 用来解决一对多的场景，映射多个结果的集合。而点位和区域、点位和合作商，都是"一个点位只对应一个区域/合作商"，所以是多对一。

**答案**：选 `association`，而且是两个独立的 `association` 标签——一个 `property="region"`、`column="region_id"`，一个 `property="partner"`、`column="partner_id"`。

## 帝可得实战：数据完整性与人员管理起步
> 对应块：BLK12 | 覆盖分集：P36-P38 | 块标题（分集名）：《实战篇-15.帝可得-数据完整性》

### 级联删除在技术上没错，在业务上要命

区域管理、合作商管理、点位管理这三个模块的前后端改造我们已经拿下了，功能是照着页面原型做的，但更有价值的收获是——借着手写这三张表的关联，我们终于把它们的关联关系理顺了。

现在问题来了：**当我们删除一条区域或者一条合作商时，跟着它走的点位数据该怎么办？**

弹幕里一下子冒出来好多方案，答得都挺漂亮。我先说说这次课程是怎么处理的。

点位表当初是通过通义灵码辅助建出来的，它默认帮我们加了外键约束，而且把引用动作配成了**级联删除（CASCADE）**。听起来多顺手的——父表一删，子表跟着一起清干净，多省事。

我们到浏览器里验一验。区域管理里找到「北京市北五环奥体中心」，它下面挂着一个点位「北京奥运博物馆」。没问题吧？点删除。区域没了，回到点位表刷新一下，北京奥运博物馆也跟着没了。

```text
        区域表                      点位表                    设备信息
   （被删除的那一条）              （子表，级联删除）        （更下游的数据）
          │
          │  删除这一条
          ▼
  外键规则：CASCADE（级联删除）
          │
          ├──▶ 点位表：该区域下的 N 条点位，全部被删除
          │          │
          │          └──▶ 设备信息：这些点位下挂的设备，跟着一起消失
          ▼
  结果：一次误操作 = 一整片区域的数据蒸发
```

从技术角度说，这完全符合数据库外键约束的规则：区域没了，关联它的点位当然也不该留着。

但从业务角度看，这就相当不合适了兄弟们。你想，一个区域下面挂着多个点位，手滑点一下「删除」，所有点位数据、连带着这些点位关联的设备信息，全都一起没了。这显然是我们不愿意看到的。

### MySQL 外键的四个引用动作

解决办法其实很朴素：**把外键约束的引用动作改掉，改成限制删除**。这样一来，当我们试图删除一个区域或合作商时，如果它下面还挂着点位，数据库就直接不让我们操作，并把错误信息甩出来。

改之前先搞清楚一共有哪些规则可选。打开数据库客户端，找到点位表，右击 → 修改表，第四个选项就是 `foreign keys`，专门设置外键约束的。双击打开，里面可以选择外键约束的规则。

规则一共有四个。有小伙伴不太理解含义，怎么办？让通义灵码来解释一下——打开它的智能问答窗口，提示词就一句：**「MySQL 外键约束的操作规则有哪些」**。回车，等它生成。

```text
  规则名          父表记录被修改 / 删除，且子表存在关联记录时
  ─────────────────────────────────────────────────────────────────────
  RESTRICT        不允许该操作，防止违反外键约束
  CASCADE         自动在子表更新或删除所有关联记录，保证数据一致性
  SET NULL        把子表的外键字段置为 NULL（前提：该外键允许为空）
  NO ACTION       行为依赖数据库系统；在 MySQL 中等同于 RESTRICT
```

逐条说清楚一点：

- **RESTRICT**：如果在父表当中要修改或删除记录，而子表中有关联记录，则不允许该操作，以防止违反外键约束。
- **CASCADE**：当父表记录被更新或删除时，自动在子表更新或删除所有关联的记录，以保证数据的一致性。这就是我们之前被坑的那一个。
- **SET NULL**：如果父表记录被更新或删除，子表中的外键字段就会被置为 `NULL`。有个前提条件——**该外键必须允许为空才行**。
- **NO ACTION**：这个选项的具体行为是依赖于数据库系统的。在 MySQL 当中，它就等同于 `RESTRICT`：如果操作会导致违反外键约束，则操作不会被执行。

> **提示**：删除和更新这两组动作都可以各自设置这四个规则，它们不是二选一，而是分开的开关。

> **定义**：外键约束上的这套「引用动作」（referential action）规则，决定了父表记录被更新或删除时，数据库自动对子表做什么。其中 `RESTRICT` 和 `NO ACTION` 在 MySQL 里效果一致，都是**拒绝**操作；`CASCADE` 和 `SET NULL` 则是**级联处理**。

那我们要把「级联删除」改成「限制删除」，该选哪个规则呢？答案写弹幕里，我看到两个：有人答 `RESTRICT`，有人答 `NO ACTION`——**这两个都是对的**。

我实际改的时候，两个都设成了 `NO ACTION`，也就是更新规则和删除规则都选第一个 `NO ACTION`。设置完点执行，再打开来看一眼，界面上已经从「级联删除操作」变成了「限制删除或更新」。

### 改完规则，亲手验证一遍

验证之前手头没数据了，先重新造一份。区域名称还是「北京市北五环奥体中心」，备注说明复制一份。接着新增点位：点位名称「北京奥运博物馆」，区域选北京北五环，类型旅游区，归属合作商选黑马合作商，详细地址从百度地图里把完整地址复制一份粘过来。点确定——

**报错了。** 错误信息是数据的完整性约束。

为什么？我们按 F12 打开 network 看抓包。请求里提交的区域 id 是 **4**，而这是我们之前的旧数据。刚才我们已经删过一次数据，本次新加的区域 id 已经变成 **5** 了。而点位管理的页面在点「添加」时并没有重新刷新，所以下拉框里还是上一次加载的旧数据，提交的自然是那个已经不存在的 4。

所以这一报错反而是个好消息——**我们的完整性约束已经生效了**。

刷新页面，重新添加一遍，这次提交的区域 id 是对的，点位新增成功。

> **易错点**：课下练习时如果重新添加被删过的原有数据，千万别忘了刷新页面。不刷新，前端提交的还是上一次访问时的旧 id，数据库一样会给你报完整性错误，而这个报错跟外键没关系，很容易白排查半天。

现在回到正题，再试一次删除区域。刷新，点删除——数据库的完整性约束生效，删除被拦住，并且给出了错误提示。

### 用全局异常处理器把数据库报错翻译成人话

可是这个错误提示，对系统的操作用户来说不友好。他看得懂吗？看不懂。看不懂就会困惑，觉得是你系统现在出了 bug，于是更不敢用，删除功能也就这么被"劝退"了。

所以要提升用户体验：**用 Spring Boot 框架的全局异常处理器把这些错误信息捕获下来，返回友好的提示信息给用户**。用户遇到这种情况，就能收到一个清晰易懂的提示，告诉他操作为什么无法完成。

这时候有小伙伴说了：全局异常处理器我之前学过，工作当中也用过，但平时都是用别人写好的，现在自己不会写了，怎么办？没关系，我们把错误信息复制一份，粘到通义灵码的智能问答界面里，配上一句提示词：**「使用 Spring Boot 框架如何捕获此异常」**，让它帮我们生成一个全局异常处理器的代码。我们参考示例代码做改造，再放进项目里就能直接用。

它生成的结果分三块，我们逐块过一遍：

1. **自定义异常类**——异常类名叫 `DataIntegrityViolationException`。这名字念出来确实有点塑料英语，不过这个类 Spring 框架已经帮我们提供了，不需要再单独定义，可以直接使用。
2. **全局异常处理器**——在处理器中捕获完整性约束异常，捕获后定义一个返回结果的 `AjaxResult` 对象来指定错误提示信息，并设置业务状态码。
3. **事务管理**——对应的是业务代码。如果是单表操作，事务默认就是自动提交的，这个事务注解不添加也可以。

所以我们只需要关注前两步。

若依其实已经把全局异常处理器这个类给我们准备好了。我们找到 dk-framework，在 web 包下面的 exception 包里，类名就叫 `GlobalExceptionHandler`。它已经捕获了若依自带的很多业务异常类信息，我们要在最后一行再追加一个。

先写上注释「数据完整性异常」，回车换写——通义灵码非常聪明，光看注释就帮我们生成了处理异常的方法。我们一起来分析一下：

- `@ExceptionHandler` 这个注解的作用，是声明下面的方法专门处理并捕获 Spring 框架的数据完整性异常信息；
- 方法的返回值是 `AjaxResult`，若依提供的统一结果对象，我们可以在这里指定错误信息和状态码。这个返回结构对象是通义灵码结合上下文学习了其他异常方法之后处理出来的，挺聪明；
- 方法体内通过日志记录了异常信息，并通过 `AjaxResult.error` 返回了提示的错误信息，内容为「数据完整性异常，请联系管理员」。

按它生成的这样写，够用吗？不够。

这个提示不够精准。用户做的是删除操作，你甩给他一句「数据完整性异常，请联系管理员」——对我们程序员来说是看得懂的，但对普通用户来说，他可能就理解成业务出问题了。所以我们应该把这个提示设置得更加精准。

那怎么设置得更精准？我们回到 PPT 捋一捋。刚报出来的是 `DataIntegrityViolationException` 这个异常类，它通常表示 SQL 数据库操作当中完整性约束违反的异常，比如**外键约束、唯一约束**，当数据库操作违反这些约束时就会抛出这个异常。

既然一个异常类管着好几类约束，那在处理器里直接写死「外键约束原因，无法删除，有其他数据引用」也就同样不精准了——唯一约束等其他原因造成的异常也会走到这里。

所以正确的做法是：**从错误信息里面去找关键词**。如果引起的是 `foreign` 关键字、跟外键因素相关的，我们就可以提示它「无法删除，有其他数据引用」；如果是唯一约束等其他原因造成的异常信息，我们再去提示它「数据库的完整性约束」。这样就能区分开，到底是外键约束引起的删除错误信息，还是唯一约束等其他操作提示的完整性信息，用户体验也就上来了。

回到编辑器，在方法里加一个小小的判断：

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public AjaxResult handleDataIntegrityViolation(DataIntegrityViolationException e)
{
    log.error("数据完整性异常", e);

    // 错误信息里带 foreign，说明是区域/合作商删除时关联点位引起的
    if (e.getMessage().contains("foreign"))
    {
        return AjaxResult.error("无法删除，有其他数据引用");
    }
    return AjaxResult.error("数据完整性异常，请联系管理员");
}
```

回到浏览器做测试。继续删除「北京市北五环奥体中心」，点删除——注意看，现在提示的是**「无法删除，有其他数据引用」**。再测合作商，「黑马合作商」刚才也关联了点位，点删除，同样的提示。

到这里，区域/合作商删除操作的处理流程就全部定义完毕了，一共两大步：

```text
  用户点击「删除」
        │
        ▼
  第 ① 步：点位表的外键规则已由级联删除改为 NO ACTION / RESTRICT
        │
        ▼
  数据库：区域/合作商下面还挂着点位 → 拒绝执行删除，保护数据完整性
        │
        ▼
  抛出 DataIntegrityViolationException
        │
        ▼
  第 ② 步：GlobalExceptionHandler 捕获并分流
        │
        ├── 错误信息含 foreign ──▶ "无法删除，有其他数据引用"
        └── 其他完整性约束       ──▶ "数据完整性异常，请联系管理员"
        │
        ▼
  浏览器弹出用户看得懂的提示
```

第 ① 步让数据库本身守住数据完整性，第 ② 步把守不住时的那声「哎这个数据不让删」翻译成人话。这样的设计不仅提升了用户体验，还避免了可能的数据误删。

到这里，我们在删除操作中处理关联数据这件事，算是有了更清晰的认识。

### 人员管理：常驻大兴的员工管不了海淀的点位

接下来我们转向一个新的业务模块——人员管理。在动手写代码之前，先把业务场景和需求说明梳理清楚，确保开发方向和业务目标是一致的。

先想一个很朴素的业务问题：区域、合作商、点位都定下来之后，下一步是什么？当然是安排工作人员去投放智能售货机。

但问题紧接着就来了：**我们如何合理地分配和调度这些工作人员？**

举个例子。假设我们在北京海淀区有一个点位——北京大学。如果你安排一个常驻北京大兴区的工作人员，去负责这个点位的设备投放和安装，这样做合适吗？显然不合适。因为两地距离较远，这将增加工作人员的通勤时间，降低工作效率。

人员管理模块要解决的，就是这个问题。

回到浏览器看页面原型。管理后台里，点位管理的下方有一个「人员管理」，点开主要是人员列表功能，里面有人员名称、归属区域、角色、联系电话等等。

那么人员名称、归属区域、角色，它们之间到底是什么关系？具体业务流程我们回到 PPT 看：

```text
  后台管理人员登录 dk 后台管理系统
        │
        ▼
  新增工作人员：姓名、联系方式等信息
        │
        ▼
  关联角色 ──▶ 确认此员工是运维人员还是运营人员
        │          （这将影响他们的职责和权限）
        ▼
  关联区域 ──▶ 确认此员工负责的区域范围
        │
        ▼
  在该区域内高效完成：设备安装 / 维修 / 商品补货
```

这样就实现了**每个区域关联一个或多个工作人员**，让他们负责该区域内的工作任务。既保证了工作人员能够高效地完成职责，也保证了服务质量。

### 三张表：角色表、员工表、区域表

人员管理主要涉及三张核心表：角色表、员工表，以及我们已经非常熟悉的区域表。

这里要先说明一件事：**角色表和员工表并不是若依框架自带的标准组件**，而是我们为了运营管理 app 的员工端特别定制的功能。

看页面原型就明白了。管理后台下方有个「运营管理 app」，里面有登录功能，登录时我们可以选择运营或运维人员的角色，输入账号密码，登录成功后进入工作台。运营人员处理的工单是进行捕获相关的，而运维人员的工单是设备的投放和设备的维修等相关的业务。

这就意味着我们刚刚的员工表和角色表，是为了满足这个特定需求而设计的，它并不适用于所有类型的后台管理系统。而若依框架当中原有的员工表和角色表，是为通用的后台管理系统而设计的，只提供基本的用户管理和角色授权功能。在我们当前的业务场景中，运营管理端的 app 需要更专业、更细致的解决方案，所以我们要做一些定制化的开发。这样专门定制的角色和员工表，才更加贴合运营管理端 app 的业务流程，确保系统能够高效地处理员工信息决策分配以及权限控制等关键任务。

#### 角色表：三个字段，三条固定数据

角色表只有三个字段：角色的主键 `id`、角色的编码、角色的名称。

这张表的数据相对来说是比较固定的，我们并没有提供页面来实现管理——回到页面原型，管理后台里并没有专门的角色管理界面，而是提供了固定的数据。打开数据库客户端双击角色表，里面有三条记录：

| 角色名称 | 角色编码 | 含义 |
| --- | --- | --- |
| 工单管理员 | `1001` | 相当于运营部门的负责人 |
| 运营人员 | `1002` | 负责智能售货机的商品补货 |
| 维修员 | `1003` | 负责投放并维修智能售货机 |

角色表就介绍到这里。不过这时有小伙伴可能会问：这些也属于静态数据呀，我们能不能把它设置为数据字典？答案在后面的小节里。

#### 员工表：对着原型看字段

员工表的字段我们结合页面原型来看。打开人员列表：

- 第一个是员工的主键 `id`——这个不用介绍了；
- 第二个「员工名称」对应页面上的「人员名称」；
- 第三个 `regionId` 和第四个 `regionName` 对应「归属区域」；
- 再往下是 `roleId`、`roleCode`、`roleName`，这里对应前端的角色名称字段；
- 再往下是联系电话，对应 `mobile`；还有员工头像和是否启用，这两个在页面原型里要往右拉到新增对话框才能看到；
- 最后是创建时间以及修改时间。

其中新增员工时的「是否启用」，业务含义也很直白：员工正式入职并处于工作日时，我们把它设置为启用；员工在休假期间，可以把它设置为停用。

角色表我们没什么好聊的，下面是区域表。这张表大家应该比较熟悉，我就不再介绍了。

### 一组一对多关系，和三个冗余字段

了解了每张表的主要字段之后，我们来看它们之间的关联关系。

首先是角色和员工，这是一对多的关系。我们在员工表当中有一个 `roleId` 作为外键字段，去指向角色表的主键。一个角色下可以拥有多个员工，而每一个员工属于某一个角色、将来我们就可以根据角色编码或外键字段来查询对应的员工列表信息了。

区域和员工表之间呢？也是一对多的关系。员工表当中有一个 `regionId` 作为外键字段，去指向区域表的主键。一个区域下面可以关联多名员工，而员工只负责某一个区域。

```text
     角色表 role              员工表 employee              区域表 region
    ┌────────────┐          ┌──────────────┐           ┌────────────┐
    │ id (PK)    │──── 1:n ──▶│ roleId   (FK)│           │ id (PK)    │
    │ roleCode   │          │ regionId (FK)│───── n:1 ▶│            │
    │ roleName   │          │ 员工名称      │           └────────────┘
    └────────────┘          │ 联系电话      │
                            │ 头像 / 状态    │
                            │ 冗余字段 ×3    │
                            └──────────────┘
```

员工表里还有个字段叫 `status`，指的是员工的状态，`1` 表示启用，`0` 表示停用。这些属于静态数据，所以我们把它设置为数据字典，以简化查询操作。

> **结论**：这三个角色（工单管理员、运营人员、维修员）**不能**做成数据字典。因为数据字典只能设置字典标签、字典值两个字段，而角色表当中有三个字段（主键、编码、名称）。所以我们必须先设计好数据库的表结构，再添加角色数据。

那么角色表这条也讲完了。接下来是重点：小伙伴们有没有发现，为了提升查询效率，我们在员工表当中特意添加了三个冗余字段，分别是 `regionName`（区域名称）、`roleCode`（角色编码）、`roleName`（角色名称）。

这样的设计意味着我们采用了**反范式**的方法。我们并没有使用常规的关联查询，而是通过这种方式来减少数据库的关联查询次数，从而加快查询速度。

这个设计的优点有三：

1. **减少关联查询，直接提升查询速度**。原本需要多表联合的操作，现在只需要单表完成即可。来同学们，我们回忆一下——原来我们做点位管理时，点位管理的列表要展示点位的基本信息、所在区域、还有合作商，虽然我们使用了嵌套查询，是不是还要把它们组合到一起啊？而现在有了冗余字段之后，只需要单表就可以搞定了。
2. **简化了查询逻辑**。因为这种冗余字段让我们的查询逻辑变得更加简单。以前复杂的 SQL 查询，不管是嵌套还是多表关联，现在都是变成单表了，更加直观易懂。
3. **优化了读写操作**。在中大型项目当中，我们通常会采用读写分离的架构，而冗余字段可以降低对主表的依赖，增加了操作的灵活性。

> **易错点**：这种设计当然也有缺点——它会增加数据维护的复杂性，而且冗余字段会占用更多的存储空间。

不过在这个场景中，我们的主要目标是为了提高员工列表的查询效率，并且我们之前也练习过多表查询、MySQL 嵌套查询等等。综合考虑，本次我们选择的就是这个方案。

### 本讲提到的题目

**一、从「级联删除」改为「限制删除」，应该选择哪个引用动作规则？**

答案：`RESTRICT` 和 `NO ACTION` 都可以。两个的共同点是：当区域/合作商下面还挂着点位时，数据库会拒绝执行该操作。课程中实际改成了 `NO ACTION`，把更新规则和删除规则两个都设成了 `NO ACTION`。`SET NULL` 也不行，因为它把子表外键字段置空，属于放行而不是拦截。

**二、角色表里那三条固定角色，能不能设置成数据字典？**

答案：不能。数据字典只能设置字典标签、字典值两个字段，而角色表当中有三个字段（主键、角色编码、角色名称）。所以必须先设计好数据库的表结构，再手动添加角色数据。

**三、在新增对话框里，前端会提交「归属区域」的区域名称和「角色」的角色编码、角色名称吗？**

答案：不会。下拉框选中之后提交的只是区域 id 和角色 id。区域名称、角色编码和角色名称都需要我们根据这些 id 去查询数据库拿到值之后，再进行封装。因此这几个字段在前端是不需要设置文本框的——这也正是员工表里那三个冗余字段存在的理由。

## 人员管理改造与文件存储升级
> 对应块：BLK13 | 覆盖分集：P39-P43 | 块标题（分集名）：《实战篇-18.帝可得-人员列表改造-基础布局》

我们已经成功利用若依平台生成了人员管理的相关基础代码。它为我们提供了一个良好的起点，单表的增删改查功能全都能跑。但代码生成器给出的从来是"标准答案"，真正的业务页面不是那个样子。

所以这一讲，我们要把这份生成代码往页面原型上搬：搜索区、列表区、对话框，一块一块对齐。顺带把一个数据一致性的坑填上，再把文件存储从服务器本地挪到阿里云 OSS 上。

### 搜索区与列表区：先把骨架摆成原型的样子

先把页面原型和若依生成的界面并排摆出来，一项一项对。

**搜索条件区**：原型上只有一个"人员名称"，若依这边一模一样。输入一个"刘"点搜索，数据出来了，这条不用动。剩下的人员 ID、角色 ID、角色编号、是否启用这几个条件，原型上压根没有——那是代码生成器替我们多送的，直接删掉。

**按钮区**：人员新增保留，跟原型一致；修改、删除、导出先留着，后面同步存储那一节还要靠它们做验证。

**列表区**改动有四：

- 复选框留着，将来批量操作用得上；
- 主键列改成序号。用户不关心数据库的自增 ID，他们关心的是"这是第几条"；
- 人员名称、归属区域、角色名称、联系电话这四列与原型完全一致，一个字都不用动。特别是归属区域和角色名称——我们在建表时给员工表留了冗余字段（从区域表、角色表各冗一份到员工表上），显示格式自然和主表对得上，这也是当初这么设计的原因；
- 操作列把修改、删除按钮前面的图标删掉，原型上是纯文字，保持简洁。

改的时候就是纯体力活，但有两个地方要说清楚。

序号列不需要自己算，el-table-column 的 `type="index"` 会自动生成，宽度给 50 刚好：

```html
<el-table-column type="index" label="序号" width="50"></el-table-column>
```

> **提示**：`type="index"` 生成的是**当前分页内**的序号，翻到第二页会重新从 1 开始编号。这正是原型要的效果——编号是给人看的页内流水，不是全局 ID。

图标就写在 el-table-column 的 `icon` 属性上，把属性值清空即可。

改完刷新浏览器，拿原型一比，没毛病。

### 新增对话框：两个文本框换成下拉框

点开"新增"对话框，我们逐项过一遍页面原型：

- 人员名称、联系电话——文本框，没问题；
- 角色——原型上是**下拉框**，生成出来的是文本框，要改；
- 负责区域——原型上也是下拉框，同样要改；
- 员工头像——文件上传，生成的代码本来就是上传，保留；
- 是否启用——单选按钮。选"启用"就是这个员工正常出勤，选"停用"就是休假状态，语义也对得上。

所以要动的是两个下拉框。还有表单项顺序也要按原型摆：角色 ID 表单项剪切到人员名称下方，联系电话表单项剪切到所属区域上方，中间那一段顺一顺就顺过来了。

改之前先想清楚一个问题：下拉框里的选项，从哪儿来？

> **结论**：下拉框的数据不能写死在页面里，必须在打开对话框前查出来——查后台。回到后端代码看一眼，角色列表的查询接口生成器早就给我们留好了，前端也生成了对应的 API 请求 JS 文件。**这就是为什么角色没有页面原型，我们也要生成它的后端代码和 API 请求 JS 文件**——因为下一个页面一定会用到。

#### 角色下拉框

改造思路就两大步，跟之前做点位管理时一模一样。

**第一步：引入 API，定义查询方法，把结果封装成响应式集合。**

找到 API 目录下的 `manager/role.js`，第一个方法就是查询角色列表的。它需要传一个查询条件进去，而这个条件涉及分页——所以还要再引一个分页条件对象 `pageAll`（`pageNum` 传 1、`pageSize` 传 10000，一页查一万条就等于查全部了）。

在人员列表视图组件的 `<script setup>` 里引进来：

```js
import { listRole } from '@/api/manager/role'
```

然后回到页面底部定义方法：

```js
// 查询角色列表
function getRoleList() {
  // listRole 需要一个查询条件，用 pageAll 一次把角色全拉回来
  listRole(pageAll).then(response => {
    // response 就是后端返回的分页对象，取其中的 rows 集合
    roleList.value = response.rows
  })
}
```

集合本身用响应式对象声明：

```js
const roleList = ref([])
```

最后在页面加载完成后调用它，数据就有了：

```js
onMounted(() => {
  getRoleList()
})
```

回浏览器 F12 一验证：请求条件是"从第一页开始查 10000 条"，返回结果里有管理员、运营员、维修员三个角色。没毛病。

**第二步：把文本框换成下拉框。**

先把原来的 el-input 注释掉（注释掉而不是删掉，方便对照），换行写 el-select，自闭合标签：

```html
<el-form-item label="角色" prop="roleId">
  <!-- <el-input v-model="form.roleId" placeholder="请输入角色id" /> -->
  <el-select v-model="form.roleId" placeholder="请选择角色">
    <el-option
      v-for="item in roleList"
      :key="item.id"
      :label="item.name"
      :value="item.id"
    />
  </el-select>
</el-form-item>
```

几个属性挨个说清楚：

- `v-model` 双向绑定，直接从原输入框上拿过来，绑的还是表单里的角色 ID；
- `placeholder` 从"请输入角色"改成"请选择角色"，原来的 `id` 字样去掉；
- `v-for="item in roleList"` 遍历刚查回来的集合，遍历出来的元素官方示例里叫 `dict`，我们换成更顺手的 `item`；
- `:key="item.id"` 设置当前选项的唯一标识，用角色 ID；
- `:label="item.name"` 设置界面上显示的名称；
- `:value="item.id"` 设置选中后真正提交的值——**提交的是角色 ID，不是角色名称**。

这一步是整套改造里最需要记住的地方：下拉框展示给人看的是名称，落到数据库里的是外键 ID。用户选了哪个角色，我们只知道他是谁，不知道他叫什么。

刷新页面点开新增，管理员、运营员、维修员三个选项都在。

### 修改对话框：只在修改态出现的创建时间

修改对话框和新增对话框长得并不完全一样。原型上，联系电话下面多了一个**创建时间**表单项——而这个表单项只用于回显，不参与提交。

这个问题我们之前遇到过：做合作商管理改造时，新增和修改用的是同一个对话框，字段不一样。我们没有另建一个对话框，而是用 `v-if` 判断。

判断依据是什么？是**人员 ID**：

> **结论**：新增时表单里没有人员 ID，修改时表单会回显数据、带上人员 ID。所以只要 `form.id` 不为空，就说明当前处于修改态，此时显示创建时间；新增时没有 ID，这个字段自然就不出现。

动手：在联系电话下方新增一个表单项。最省事的做法是以联系电话那个表单项为模板复制一份过来，然后改三处。

第一，把表单项名称改成"创建时间"。第二，因为只做回显不参与提交，**这里不能用文本框**，直接用差值表达式把值打出来：

```html
<el-form-item label="创建时间" v-if="form.id !== undefined">
  {{ form.createTime }}
</el-form-item>
```

第三，这里有个坑值得单独说。通义灵码会结合上下文帮我们补出一段日期格式转换的代码——后台返回的创建时间本来就是"年-月-日 时:分:秒"，前端根本不需要再转一次，这段补出来的代码是我们不需要的，删掉就完事。

浏览器验证：点修改，创建时间正常显示；再点新增，创建时间不见了。对了。

### 测出来的空洞：冗余字段没人填

新增和修改都试一遍。填个叫"小智"的员工，角色选运营员，电话 13800138001，负责区域选北京市北五环奥体中心，头像上传，状态启用，确定。提交成功。

但翻到第二页一看：序号有了，人员名称有了，联系电话有了，**归属区域和角色名称是空的**。

回到数据库客户端，打开员工表看最后一条记录：`region_id` 有值、`role_id` 也有值，可对应的区域名称、角色编码、角色名称全是空的。

原因很清楚：前端在点击新增时，只提交了角色 ID 和负责区域 ID，并没有提交关联的名称。所以这部分数据必须由后端来补。

> **易错点**：冗余字段的"冗"字，代价就是它没人自动长出来。存进去的那一刻，就有人在负责把它填对——否则冗余字段会安静地烂掉。

思路用 PPT 上那张表关系图捋一遍：

1. 我们提交的数据里**是包含区域 ID 和角色 ID 的**；
2. 以这两个外键为条件，先根据 `regionId` 查区域信息，取出区域名称，设置到员工对象的 `regionName` 上；
3. 再根据 `roleId` 查角色表信息，取出角色编码和角色名称，设置到员工对象的 `roleCode` 和 `roleName` 上。

### 同步存储策略：让冗余字段跟上主数据

等等，这还没完。这节课开头我给你们演示过一个问题，现在正好接着说。

冗余字段的好处是查询人员列表时可以单表查询，查询效率高、开发代码也简单。但代价来了：我去改**区域管理**里的数据，把"北京市北五环奥体中心"改名为"北京市奥体中心"，然后回到人员列表一刷新——员工列表里的区域名称还是老的，没跟着变。

```text
   改区域表          员工表（冗余字段）        用户看到的列表
   ────────          ─────────────────        ─────────────
  名称改成                没动                 旧名称
  "北京市奥体中心"
       │                    ▲                    │
       └──── 没有任何联系 ───┘              数据不一致
```

这会给用户带来困扰，也会影响我们系统的准确性和可靠性。根源在于：既然用了冗余字段，就必须同时保证这些冗余字段能够及时更新。

弹幕里大家都写"同步更新"，没毛病。我们采用的方案叫**同步存储策略**：在员工表里保留区域名称这个冗余字段，要求我们在更新区域表的同时，必须更新员工表中的区域名称字段。

若依已经提供了修改区域表的后端代码，但**没有**提供"根据区域 id 更新区域名称"的代码，这部分得我们自己写。

#### 第一步：手写按区域 id 更新的 SQL

回到数据库客户端，打开命令行窗口，先把数据同步过来验证一下 SQL 对不对。这条语句很简单，就不折腾 AI 工具了，直接手写：

```sql
-- 根据区域id修改区域名称
update tb_emp
set region_name = '北京市奥体中心'
where region_id = 5;
```

选中执行，提示执行成功。刷新员工表——小智和波妞的区域名称都同步过来了。SQL 没问题。

#### 第二步：Mapper 层用注解建立映射

回到 IDEA，找到员工表的 `EmpMapper`。因为这条 SQL 不含动态 SQL（没有 `<if>`、`<where>` 那些标签），为了提高可读性，就不写 XML 了，直接用注解方式，在接口末尾加一个方法。

先从数据库把刚才的 SQL 复制过来，注意**不要粘分号**：

```java
/**
 * 根据区域id修改区域名称
 *
 * @param regionName 区域名称
 * @param regionId   区域id
 * @return 影响行数
 */
@Update("update tb_emp set region_name = #{regionName} where region_id = #{regionId}")
public int updateRegionNameByRegionId(@Param("regionName") String regionName,
                                      @Param("regionId") Long regionId);
```

这里有两个必须抠一下的细节。

**细节一：写死的值要变成占位符。** SQL 里的 `'北京市奥体中心'` 和 `5` 是我们测试时写死的两个值，肯定不能留在代码里，要换成 `#{}` 占位符——第一个叫 `regionName`，第二个叫 `regionId`。

**细节二：类型要跟实体对得上。** 通义灵码帮我们补全参数时，两个都给成了 `String`。`regionName` 是字符串没问题，但 `regionId` 显然是字符串吗？那显然不是。打开员工实体类确认一下——`regionId` 对应的是 `Long` 类型，那就同步改过来。类型不匹配，运行时才会炸，现在改成本最低。

> **易错点**：现在这个方法传的是**两个**参数，MyBatis 怎么知道第一个给 `regionName`、第二个给 `regionId`？靠的是 `@Param` 注解给每个参数起一个别名，并且**别名必须和占位符名字一模一样**。嫌麻烦也可以不写这两个注解，但那样占位符就得改成 `#{arg0}` 和 `#{arg1}` 才能映射上——新写代码还是老老实实用 `@Param`。

返回类型是 `int`，返回的就是影响行数——增删改都会返回影响行数，这个概念记住就行。

#### 第三步：Service 层串起来，并加上事务

最后一步，在区域 Service 实现类的更新方法里动手。

先看原来的代码，它更新完区域表就直接 `return` 了：

```java
return regionMapper.updateRegion(region);
```

这显然不合适，我们还需要更新员工表里的区域名称。所以先把返回值抽出来，不要直接 return——里面会返回一个影响行数变量，名字就叫 `result`。

然后在类里注入员工表的 Mapper：

```java
@Autowired
private EmpMapper empMapper;
```

最后把三段逻辑串在一起：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public int updateRegion(Region region) {
    // 1. 先更新区域信息
    int result = regionMapper.updateRegion(region);

    // 2. 区域表更新成功后，同步更新员工表中的区域名称
    empMapper.updateRegionNameByRegionId(region.getName(), region.getId());

    return result;
}
```

传两个参数：第一个是区域名称 `region.getName()`，第二个是区域 ID。

按 `Ctrl+F9` 热部署，回浏览器验收。到区域管理里把"北京市奥体中心"再改回"北京市北五环奥体中心"，顺便把备注也补上，确定。再回人员列表一刷新——小智和波妞的归属区域名称也一起变回来了。

> **易错点**：这里有个坑，是弹幕里兄弟们先发现的——**这个方法现在涉及了两张表的 SQL 更新**。两张表的更新必须当成一个整体，要么都成功，要么都失败。所以要加 Spring 的声明式事务，在方法上加 `@Transactional`，并且一定要补上 `rollbackFor = Exception.class`，这样才能把 `Exception` 类型的异常也捕获到并回滚。少了这个属性，受检异常抛出时事务是不会回滚的。

> **结论**：同步存储策略落下来就三步——**按区域 id 写一条更新员工表区域名称的 SQL；在 Mapper 层加一个方法把 SQL 映射起来（两个参数要 `@Param` 别名）；在区域 Service 的更新方法里先更新区域表、再同步更新员工表，最后补上事务。**

到这里，人员列表的基础布局展示和冗余字段的同步更新都搞定了，数据一致性有了保证。

### 文件存本地，迟早要出事

接下来换个方向，聊点跟列表改造无关但同样会疼的事。

新增对话框里的员工头像上传，我们生成的代码本来就能用。点新增、选一个头像，头像就保存到了服务器本地，浏览器刷新后照样显示。找到配置文件，第十行就写着存储路径，在 `D:\ruoyi\uploadPath` 目录下。翻到这个目录看看，里面确实躺着我们刚才传的那几张图片。

简单吧？但这种简单是有代价的。回到 PPT 来分析一下这三个问题。

**第一，性能瓶颈。** 文件直接落到我们自己的服务器上，一旦服务器处理能力不足或者网络带宽有限，上传、下载、甚至访问速度都会受影响。

**第二，磁盘会满。** 想象一下微信服务器——它要存数十亿用户的头像和视频。这是什么量级？已经远远超过 GB、TB 的计算范围，到了 PB 的级别。再大的磁盘也装不下这么多数据。

**第三，单点故障风险。** 服务器一挂，存上面的所有文件全都访问不了。虽然可以通过备份或其他冗余措施来降低风险，但风险本身是永远存在的。

> **结论**：所以在项目开发中，我们通常不会把文件直接存在服务器本地。

那存到哪儿去？两条路。

一条是自己搭服务。可以基于分布式文件系统 FastDFS 搭自己的文件存储系统，也可以基于 MinIO 来搭。但这条路要自己准备服务器，还得考虑搭集群来做扩容，技术要求高、还要额外采购服务器——对中小型公司来说就不太友好了。

另一条是不用自己搭，直接用现成的云服务，比如阿里云、腾讯云、华为云。既省成本，又降低技术难度。

所以我们本次课程采用的方案是：**把文件存到云端**，利用云服务的优势来解决存储问题。

### 阿里云 OSS：把文件交给云

先认识一下这个哥们儿。阿里云对象存储 OSS，全称 Object Storage Service，对象存储服务。

这里的"对象"就是我们要存的文件——文本、图片、音频、视频，统统都叫对象。阿里云的 OSS 是一款海量、安全、低成本、高可靠的云存储服务，你可以通过网络随时存取各种文件。

它的强大之处在于极高的数据持久性和可用性。官方给的数字是：

| 指标 | 数值 |
| --- | --- |
| 数据持久性 | 99.99999% |
| 数据可用性 | 99.995% |

简单来说，用 OSS 存图片或其他文件，你几乎不用担心文件丢失或者无法访问。当然官方也很诚实地说明：虽然非常接近 100%，但并不保证绝对的 100%，毕竟任何服务都可能遇到不可预见的情况。

那具体怎么用？假设我们选择用 OSS 存上传的文件（比如视频、音频），操作流程是这样的：

```text
        ① 用户在浏览器发起上传请求
                        │
                        ▼
        ② 请求发送到我们的服务器
                        │
                        ▼
        ③ 服务器不再把文件写进本地磁盘
           而是带着 AccessKey 凭证直连阿里云 OSS
                        │
                        ▼
        ④ 文件进入 OSS 桶中存储
                        │
                        ▼
        ⑤ 服务器不必占用本地空间
           图片改由 OSS 通过 URL 对外提供访问
```

对比一下改造前后，思路就非常清楚了：

```text
改造前： 浏览器 ──▶ 服务器 ──▶ 磁盘目录 ──▶ URL 返回
         文件全堆在单机磁盘上，磁盘满了、机器挂了，文件就全没了

改造后： 浏览器 ──▶ 服务器 ──▶ 阿里云 OSS ──▶ URL 返回
         服务器只做中转不落文件，文件交给云端持久保存
```

前面说的三个问题，一次性全解决，还顺带白拿了 OSS 的高可靠和高可用。

### 开通前的五步准备

实际上无论用哪种云服务，流程都大同小异，就三步：

```text
第 1 步  准备工作   注册云账号 → 实名认证 → 登录平台 → 开通所需服务
第 2 步  入门程序   参考官方 SDK 的示例，写一个能跑起来的程序
第 3 步  项目集成   把云服务真正接进我们的项目，解决业务问题
```

第二步里冒出来一个新词——SDK。SDK 的英文全称是 Software Development Kit，中文直译是"软件开发工具包"，里面包含了辅助软件开发的各种依赖 jar 包。

> **定义**：SDK 是云服务官方提供的工具包，里面把程序所需要的依赖 jar 包和示例代码全都给你准备好了。你要用的就是这个技术，它连示例代码都贴在你脸上了——我们不需要写任何一行代码，把示例粘过来做点微调就能直接用。

第二步的核心就是**参考官方 SDK 的示例代码，写一个能跑起来的入门程序**，确保它能正常运行。第三步才是把云服务集成到我们自己的项目里，真正解决问题。

具体到阿里云 OSS，准备工作有五步。

#### 账号、充值与服务开通

**第一步，访问阿里云官网注册一个属于自己的账号，并完成实名认证。** 注册成功、实名认证通过之后，就能访问阿里云的产品界面了。里面有很多产品，我们这次要用 OSS，所以在搜索框里搜 "OSS"，回车，点进"对象存储 OSS"。

（注册这一步之前已经做过的同学可以跳过，这里就不演示了，笔记里给了注册地址。）

**第二步，充值。** 其实对于新用户来说，充值并不是必须的——很多服务都有免费的试用额度。但额度用完之后还想用，就得充值了。点击右上角头像，进"费用与成本"那一栏，下面有个充值按钮。

**第三步，在控制台里开通 OSS 服务。** 这一步特别容易被忽略：我们刚刚注册好的账号，OSS 服务默认是**未开通**状态。充值不等于开通，必须单独在控制台点一下开通。

#### 建桶：唯一性与公共读

**第四步，创建一个 Bucket。**

Bucket 是什么？是存储空间里的一个容器。将来我们上传的图片、视频、音频都要放到这个容器当中。我们可以创建一个或多个 Bucket 作为容器来存文件。

创建的时候有两个地方必须盯紧：

**桶的名称必须保证全网唯一。** 这里我们起一个 `dkgd-itheima`。名称一旦创建就**不能更改**，重名了就得换一个。

**必须把阻止公共访问的开关关掉，并设置为公共读。** 为什么？因为将来我们上传的头像，是需要通过客户端直接访问的。如果保持默认的私有权限，你能上传，但别人访问不了。

除了这两项，桶的地域位置也很关键——它决定阿里云最终把你的文件放到哪个地域的服务器机房。我们这里选华北 2（北京），大家按自己的实际情况调。存储类型、冗余类型这些保持默认就行。

创建完成进入桶内部，可以用控制台界面上传一个文件试一下：点"上传文件"，选择本地文件，上传成功，文件列表里就多出来一个文件对象。

> **易错点**：注意，这只是阿里云控制台界面的上传。真实场景下我们绝不会在这个界面上传——我们是在帝可得的管理系统里上传，涉及的是我们项目的 Java 代码和阿里云 OSS 对接。

#### 密钥与环境变量

要对接，就得有身份验证的凭证，这个凭证就是 AccessKey，也就是我们说的密钥。

**第五步，创建 AccessKey。** 点右上角头像，里面有 AccessKey 的管理，点进去，新用户需要自己创建一个。创建需要手机号验证。

创建成功后会拿到两个信息：

- **AccessKey ID**——相当于你的身份证号；
- **AccessKey Secret**——相当于你的密码。

> **注意**：这两个信息千万不要泄露给其他人。一旦泄露，别人就可以拿到你的 ID 和 Secret，用你的账号完成文件上传或其他服务操作。但你自己一定要保存好，因为稍后通过 Java 代码上传时就要用到它。

拿到密钥之后还要做一个简单配置：以**管理员身份**打开 CMD 命令行，把这两个值分别写进对应的环境变量，一条对应 ID，一条对应 Secret——注意一定复制自己的，别抄错。执行完之后再运行刷新命令，让配置生效。

然后可以验证一下：把查询命令复制到 CMD 里执行，能回显出你的 AK，说明环境变量已经配好了。

配环境变量是为了稍后使用 SDK 入门案例时用的。

> **易错点**：这里有个细节必须强调——**配完环境变量之后必须重启 IDEA**，它才能加载到环境变量里的数据。没重启就往下写代码，凭证那一步必然出问题。

准备工作到此为止：注册账号并实名认证、充值（新用户可跳过）、开通 OSS 服务、创建公共读的 Bucket、获取并配置 AccessKey 密钥。

### 参照官方 SDK 写上传入门程序

准备工作做完了，接下来参照官方 SDK 写一个文件上传的入门程序。

这一节其实不用查讲义也不用百度——需要的信息官方文档里全都有。到 OSS 控制台左侧菜单往下拉，最后一行有个"SDK 下载"，点进去，这里展示了所有语言的 SDK 文档：Java、Node、PHP、Python 等等。我们点 Java 的"查看文档"，右侧会弹出一个帮助文档，但那个对话框信息太小了，不方便看，点左下角的"文档中心"，新窗口打开，这就舒服多了。

左侧菜单拉到最下面就是 Java 相关的内容：前言介绍、安装配置、访问凭证、初始化、快速入门，非常详细。

> **提示**：在企业开发时，这类官方文档我们需要从头到尾完整读一遍。但现在是教学环境，咱们节约时间，挑几个跟程序直接相关的重点看。

#### 环境要求与依赖坐标

第一件事看"安装"。准备工作的要求里写明：Java 必须是 JDK 1.7 及以上版本。我们本次课程用的是 JDK 11，所以没问题。

接下来是 SDK 的下载。其实这个下载操作可以跳过，因为我们项目是通过 Maven 的方式引入依赖的，这也是阿里官方推荐的方式。页面上有坐标信息，点右上角的复制按钮复制下来。

回到 IDEA，问题来了：**这个阿里云 OSS 依赖应该放到哪个模块里？**

> **结论**：文件上传属于**公共组件**部分，所以放到 `dk-common` 这个子模块下。打开这个子模块的 `pom.xml`，在最后一行写上注释"阿里云 OSS"，把坐标粘过来。

第一次粘贴的同学这里会有一个下载坐标的过程，大家耐心等待一下。导入完**一定要检查**：找到当前子模块的 pom 文件，看依赖的最后位置，阿里云 SDK OSS 一定要引入成功。

再回到官方文档往下走，还有一条要求：如果你用的是 Java 9 及以上版本，需要额外添加 JAXP 的相关依赖。这几个坐标在我们若依工程里已经包含了，所以不用导入；但如果你搭的是一个新的 Spring Boot 工程、想单独测阿里云 OSS，这三个坐标不能省略。

#### 官方示例只改几处

继续往下是"访问凭证"。文档里列的第一个是**临时访问凭证**，它有时间限制，超时了就访问不了，这个先不介绍。往下有**长期访问凭证**，支持 Mac、Linux 和 Windows 系统；其中 Windows 既支持图形化界面配置环境变量，也支持 CMD 命令行方式——这几个命令行是不是眼熟？上一个小节我们已经配置过了，所以访问凭证这块也就搞定了。

接着是"快速入门"，包含三步：创建存储空间（也就是 Bucket）、实现文件上传、上传成功后下载文件。写得非常详细，代码还有注释，拿过来就能用。不过本次入门程序只涉及文件上传，快速入门先放着，直接去找对象存储里的"上传文件"。

上传支持多种方式：简单上传、表单上传、追加上传、断点续传上传等等，非常全面。我们看简单上传，它又分几种形式：

- 上传一个字符串；
- 上传一个字节数组；
- 上传一个网络流；
- 上传一个文件流。

**第四种就是我们想要的**——把一个本地文件以流的形式上传到 OSS 的桶空间里。左上角有个复制按钮，这个代码我们不需要编写，直接复制即可。

回到 IDEA，测试代码推荐放在 `dk-common` 里做。建一个 `test` 目录，包路径必须和项目保持一致，命名为 `com.dk.common.test`。直接 Ctrl+V 粘贴，整个类连导包都给我们搞定了，是不是非常方便？

代码我们逐行过一遍，官方示例里需要按自己情况填的就是下面这几处：

| 要改的地方 | 是什么 | 怎么取 |
| --- | --- | --- |
| `endpoint` | 端点，即地域对应的访问节点 | 桶详情页"概览"里复制，注意保留 `https://` 协议 |
| `accessKeyId` / `accessKeySecret` | 身份凭证信息 | 从环境变量读取，不硬编码 |
| `bucketName` | 存储空间的桶名称 | 之前建好的那个桶 |
| `filePath` | 本地上传路径 | 准备好的本地文件，属性面板里复制完整路径 |
| `objectName` | 上传到 OSS 之后叫什么名、扩展名是什么 | 自己定，和本地一致最省事 |

```java
// 端点：桶所属地域对应的节点（这里以北京地域为例）
String endpoint = "https://oss-cn-beijing.aliyuncs.com";

// 身份凭证：从环境变量读取（变量名取决于你上一步配的叫什么）
String accessKeyId     = System.getenv("你的 AccessKeyId 环境变量名");
String accessKeySecret = System.getenv("你的 AccessKeySecret 环境变量名");

// 桶名称：之前创建好的那个
String bucketName = "dkgd-itheima";

// 本地待上传文件的完整路径
String filePath = "D:\\...\\gaoyuanyuan.png";

// 上传到 OSS 之后的名字和扩展名
String objectName = "gaoyuanyuan.png";
```

几个要展开说的点。

**什么是端点？** 回到创建桶的环节：地域有北京、杭州、上海、南京、青岛等等，**每一个地域都有自己对应的端点**。进桶的"概览"里就能看到北京地域的 Endpoint 节点信息，复制出来粘贴到代码里。

> **易错点**：粘贴的时候，**请求协议 `https://` 一定要保留**，我们只替换后面的部分。别把协议也一起删了。

**为什么凭证要用环境变量读？** 因为上一个小节我们已经配好了，直接这么写就能拿到。但如果你刚才没有重启 IDEA，这里一定要先重启，否则它加载不到环境变量。

**本地文件选哪个？** 选一个"心仪的女神"的图片就行，我们这里用"高圆圆.png"。在资源管理器里选中文件，右键属性，安全面板里可以直接复制图片的完整路径。

**`objectName` 是什么？** 它指的是这个文件上传到阿里云之后叫什么名字、扩展名是什么。我们本地文件叫"高圆圆.png"，那这里跟它保持一致，阿里云 OSS 里就显示"高圆圆.png"。

再往下是官方代码的主体：创建一个 OSS 的客户端对象，它就可以向指定的端点发送请求、携带我们的身份凭证信息，然后把文件转成流的形式，实现上传。异常处理部分官方示例里都写好了，我们不再赘述。

#### 跑通并回控制台验收

代码配好了，点击执行前注意一件事：**一定要保证电脑是联网状态**，否则文件根本传不上去。

选 Debug 执行，控制台提示正在上传，很快就上传成功了。回到阿里云 OSS 界面，找到当前存储空间的文件列表——"高圆圆.png"已经躺在那里了，点一下图片直接能预览。

再往下看，有一个 URL。这个 URL 就是当前图片对外访问的链接，其他用户访问这个链接就能查看这张图片——**因为我们前面把桶的权限设置成了公共读**。

> **结论**：整个文件上传入门程序，我们一行代码都没写，官方示例粘过来只改了四处——端点（结合自己的地域）、环境变量凭证（一定要配）、桶名称（改成自己的）、本地路径和上传后的名称。改完就能跑通，是不是非常简单？

到这里，参照官方 SDK 编写的文件上传入门程序就测试成功了。下一个小节，我们就把 OSS 真正集成到项目当中。
