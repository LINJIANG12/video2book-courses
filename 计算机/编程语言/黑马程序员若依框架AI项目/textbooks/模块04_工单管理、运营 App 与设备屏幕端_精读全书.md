## 工单管理：需求说明与基础代码生成
> 对应块：BLK22 | 覆盖分集：P71-P72 | 块标题（分集名）：《实战篇-50.帝可得-工单管理需求说明》

商品管理的业务代码写完之后，我们正式迈进新的阶段——工单管理。

不过在下代码之前，得先把业务场景和需求说明捋一遍，确保我们的开发方向跟业务目标是对得上的。这一讲就把这件事办完：先看业务场景，再看工单的状态流转，接着把四张核心表的字段和关系一条条过掉，最后用若依的代码生成器把工单模块的骨架搭起来。

### 售货机投出去之后的事

到这一步，我们已经在系统里录入了售货机的详细信息，并且给售货机的每个货道都关联上了相应的商品。接下来要解决的就是**设备的投放运营以及商品补货**。

这条业务链路是这样的：管理人员登录后台系统创建工单，工作人员在运营管理的 App 端就能看到分配给自己的工单，根据实际情况选择接受并完成，也可以进行拒绝或取消。

工单管理在这个业务场景当中主要涉及两个功能模块，我们分别看一下。

#### 运营工单与运维工单

**运营工单**：管理员根据售货机的库存情况来创建，用来指派运营人员去维护售货机内的商品，实现补货，确保售货机中的商品充足，满足消费者的需求。

**运维工单**：管理员用来指派运维人员进行售货机的设备维护工作。这里包括多种工单——投放工单、维修工单、撤机工单，确保售货机设备运行稳定，及时更新或修复。

> **定义**：投放工单就是投放新设备，也叫装机工单；撤机工单就是撤出旧设备。后面讲工单类型表的时候还会再碰到这两个名字。

#### App 端：两个角色看到的是两套界面

运营人员登录 App 之后，会看到一个专门为他们设计的界面，这个界面展示他们需要处理的工单，可以选择接受、查看工单详情，完成商品的补货相关任务。

运维人员登录 App，界面则根据角色定制，展示与设备维护相关的工单界面：投放新设备的工单（装机工单）、撤出旧设备的工单，以及进行必要维修工作的相关工单。点进去可以查看详情，里面有工单的具体地址；然后点击接受，完成工单。当然了，也可以选择拒绝、取消工单。

同样的一套交互动作，界面内容却完全由角色决定——这也是为什么后台要把工单管理拆成运营工单和运维工单两个入口。

### 管理员建一张工单要走三步

具体的业务流程我们回到 PPT 来看。

后台管理人员先登录帝可得的管理系统，进入工单管理模块，开始创建新的工单。

创建工单之前，管理员需要确定工单的相关设备信息——是哪个区域下面的设备需要进行投放、维修或者补货。这里我们需要确定所在区域和具体的地址。

接下来管理员需要选择工单的类型，包括投放新的设备、维修设备、撤机旧的设备，以及商品补货。每种类型对应不同的任务。

最后，管理员需要根据设备所在的区域，选择相应的工作人员来处理这个工单。比如你的设备在海淀区，那么人员选择也应该从这个区域下面的工作人员里挑。这个区域与工作人员划分的功能我们之前已经完成过了，这里直接进行查询即可。

> **结论**：建单的三要素是「哪个设备（区域 + 地址）」、「什么类型」、「派谁去」。区域这一层不是可有可无的，它是把设备和人力对上号的那道桥。

### 四种状态与它们的流转

工单在系统当中一共有四种状态：

| 状态 | 含义 |
| --- | --- |
| 待处理 | 管理员刚创建出来，还没派人接 |
| 已接收 | 也称为进行中，工作人员已经接单 |
| 已取消 | 工作人员拒绝，或接单后遇到无法完成的突发情况而取消 |
| 已完成 | 任务执行完毕，工作人员点击已完成 |

它们之间的流转是这样的：

```text
  待处理(1)
      │
      ├── 拒绝 ──────────────────────────────┐
      │                                        ▼
      └── 接受 ──▶ 进行中(2) ──┬── 任务完成 ──▶ 已完成(4)
                              │
                              └── 遇到突发事件无法完成 ──▶ 已取消(3)
                                                                │
                                                                ▼
                                          管理员重新创建工单，指派新工作人员
```

具体展开说：管理人员创建工单之后，工单处于待处理状态，等待相关人员登录 App 以后做出响应。一旦工作人员登录了 App，就可以查看待处理工单——运营人员查看的是补货的工单，运维人员查看的是投放、维修和撤机的相关工单。在这个界面上他们可以选择接受或拒绝，一旦选择接收，工单状态就改为进行中，工作人员根据工单的分类执行相应的任务。任务执行完毕以后，工作人员点击已完成来更新工单的状态。

当然，即使工作人员已经接收了工单，也可能会遇到无法完成任务的突发情况。在这种情况下，工作人员可以取消工单，状态改为已取消，之后再由管理人员重新创建工单、指派新的工作人员，确保任务最终完成即可。

> **易错点**：已取消不是一个死胡同。它不是「任务失败」的终态，而是一个可以回炉重来、重新派单的中间状态——因为流程的终点只有「已完成」。

### 四张表撑起工单管理

业务流程和开发任务有了清晰的认识之后，我们来看一下工单管理的数据模型。

工单管理主要涉及四张核心表：工单表、工单补货详情表、工单类型表，以及自动补货任务表。接下来我们来看一下这四张表的主要字段信息。

#### 工单表

先看工单表。这部分我们结合页面原型来看几张图。

第一个是 `task_id`，作为工单 id，是主键自增的。第二个是 `task_code`，作为工单编号，页面中我们展示了工单编号。这时候小伙伴可能会有一个疑问：`task_code` 和 `task_id` 有什么区别呢？

> **定义**：`task_id` 是工单表的唯一标识，将来做修改或删除时以它为条件来完成业务操作；而 `task_code` 是具有业务规则的，它的格式为年月日以及当前工单的序号信息——先是年，然后是月，然后是日，最后的四位是当前日期的工单序号。也就是说，我们每一天的工单都是从 `0001` 开始的，创建第二个工单就是 `0002`。工单编号由日期加自增序号组成，就做到了见名之意，将来便于我们查询某些日期下都有哪些工单，便于后期的一个业务管理操作。

再往下走，还有工单状态字段，在页面列表中我们展示了工单状态：已完成、进行中、已取消这几个状态，我们刚刚已经分析过了。

还有创建类型，`0` 表示自动创建，`1` 表示手动创建。在页面列表当中，大家来看一下工单的创建方式，有自动的也有手动的，我们来解释一下什么是自动工单：

当售货机的设备满足某些条件后，由系统自动触发创建的工单。举个例子，北京奥体中心的售货机设备，商品即将卖完了，而这个货道原来存放的是十件，现在只剩下四件了，到达了货道设置的库存警戒线，那么系统就会自动触发并创建一个补货工单，分配工作人员前去补货，确保售货机的商品充足，满足消费者的需求。

而手动创建工单就比较容易理解了：管理人员在帝可得的管理界面手动去检查设备的库存，然后创建工单，指定工作人员前去补货。

再往下看，还有售货机的编码，在这一点进行了展示。每一个工单都是在执行某个设备的具体任务，比如说投放设备、货道补货等等，所以我们需要根据设备编号，获取设备的所在区域、点位等信息，便于工作人员进行定位。

再往下走，执行人员 id 以及执行人的名称，这两个字段就是负责我们当前工单处理的人，有运营人员，或者说运维人员，对应的是我们员工表的 id 和员工的名称，在这一列我们展示了员工的名称信息。

再往下看，还有所属区域 id，这个字段非常重要。我们之前实现了区域与工作人员的划分功能，这意味着每个区域都可以关联特定的运维或运营的工作人员。而有了这个 region id，我们就可以查找该设备所属区域的特定的工作服务人员，为工单的分配提供精准的定位依据，找到合适的人来处理当前的工单。

再往下走，还有备注信息。这个备注信息是我们在新增工单时在这里面进行指定的，比如说它是一个加急工单，请在 12 点之前完成等等相关的备注说明。

再往下看，`product_type_id`，它对应的是工单的类型，而这个类型我们刚才提到了，有运营人员的补货工单，还有运维人员的——来看一下投放工单、维修工单、还有撤机工单，对应的四种类型。

再往下看，还有一个指派人 id。那什么是指派人 id？它跟 `user_id` 有什么区别呢？咱们来介绍一下：指派人 id 指的是创建工单的人，也就是我们帝可得系统的管理人员，他在新建工单时指的是指派人 `assigner_id`；而 `user_id` 是负责干活的人，是执行工单的人，指的是运维或运营人员。

> **易错点**：这两个 id 小伙伴们一定要分清楚。一个是派活的人，我们可以把它理解为包工头；另外一个是干活的人，就是包工头的小弟。这一点小伙伴们能理解吧。

好，再往下看 `addr`，指的是这台设备的地址，执行人员就可以查看地址，找到这台设备，完成相应的任务。

还有创建时间以及更新时间这两个字段。以上就是工单表的主要字段介绍，大家先了解一下。

#### 工单补货详情表

接下来我们来看一下工单补货详情表。注意它指的是补货工单，所以我们要找到运营工单的管理界面。往右拉，这里有一个「补货详情」，当我们新建补货工单时，有一个补货详情按钮，点击此按钮就会弹出详情页面，这里展示的就是每一个补货详情的数据。

第一个 `detail_id` 作为主键自增。第二个是工单 id，也就是说补货详情属于哪个工单，这里有一个外键字段建立关联关系。

还有货道编号，是哪个货道需要补货呢，有 1-1、1-2、1-3、1-4 等等。

还有补货期望的容量。那这是什么意思呢？注意看我们当时在介绍货道表时，提到了每一个货道它都有一个当前容量和一个最大容量。当前容量就是货道目前商品剩余的容量，最大容量是当前货道最多可以放多少件商品。我们可以通过这两个字段进行计算，就可以得到还可以添加多少容量。

举个例子，比如说当前容量我们这边是五，而最大容量是十，那么当前货道最大可以添加几件可口可乐呢？是不是也是五啊？所以我们右侧的补满数量，它的范围应该是 1 到 5 之间。兄弟们，最少你可以补一件，最多的你可以补五件，总体来说你是不能超过当前货道的最大容量。

> **提示**：所以我们需要在前端当中进行计算，根据设备或货道返回的最大容量和当前容量，来计算出还可以添加多少；然后我们可以在右侧当中输入你要补货的商品数量，那么就会保存到补货期望的容量当中。到时候由运营人员根据这个数量，实现商品的补货工作。

可补数量上限的计算方式就是：

$$
补货数量上限 = 最大容量 - 当前容量
$$

再往下看，还有当前货道关联的商品 id、商品名称、商品图片。有了这些补货详情字段以后，工作人员就可以在 App 当中查看补货清单，准备相应的商品，找到设备完成补货任务，并同步更新数据库的信息。

#### 工单类型表

咱们再来看一下工单类型，这个功能类型我们刚才已经介绍过了，咱们再来确认一下。

在运营人员当中，我们可以选择的工单类型只有一个，对应的是补货工单，那么字段名呢叫 `type_name`，而且提交的是 `type_id`。

在运维工单的界面当中，点击新增对话框时，可以选择有投放工单、维修工单以及撤机工单。同样的，前端提交的是工单的 `type_id`。

那在这里面呢还有个字段叫 `type`，这个字段当中，`1` 表示的是运维相关的工单，`2` 表示的是运营相关的工单。这个 type 字段可以区分工单的类型——比如说将来我想统计运营工单的数量，咱们的条件就是 `type = 2`；想统计运维工单数量，条件就是 `type = 1`，是不是就可以了。

#### 自动补货任务表

咱们截张图，它对应的页面原型是在运营工单当中，其中有个按钮叫「工单配置」，点击此按钮以后会弹出一个对话框。往下拉，在这个界面当中显示了补货的警戒线，而这个警戒线呢是一个百分比的值，比如说我们在这里面写一个 50%。

那它有什么用呢？每天凌晨，我们的系统会自动扫描所有的售货机，而售货机货道的容量警戒线到达 50% 以后，系统就会自动创建一个补货工单，交给工作人员完成补货操作，确保售货机中的商品充足，满足消费者的需求。

我们在这个前端页面呢可以灵活地调整这个警戒线，可以把它设置为 60%，也可以把它设置为 40%，动态地调整它的补货频率。这点大家先了解一下。

### 表与表之间怎么挂

在了解了每张表的主要字段以后，我们来看一下它们之间的表关系。

```text
                      工单类型表 task_type
                              │ 一对多
                              ▼
   设备表 ◄── inner_code ──  工单表 task
                                │  一对多
                                ▼
                      工单补货详情表 task_detail

   工单表 task ── user_id ────▶ 员工表（执行人：运营/运维人员）
   工单表 task ── region_id ──▶ 区域与员工的关联（查该区域的工作人员）
   工单表 task ── assigner_id ▶ 管理端用户（指派人：创建工单的人）

   自动补货任务表：与上面三张表均无直接关联
```

首先是工单表以及工单补货详情表，它们的关系是一对多。这里需要小伙伴们注意一下：**只有补货工单才会有详情**。将来我们可以通过 `task_id` 来查询此工单货道的补货信息、商品的 id，还有需要补货的数量。

接下来我们再来看一下工单类型和工单表的关系，同样的也是一对多。我们在创建工单时需要选择指定的工单类型，来区分任务的安排是投放的、补货的，还是维修、撤机的等等。

再往下看自动补货任务表，那么这张表呢并没有与我们刚刚介绍的这三张表产生直接的关联关系，大家先知道一下。

除此之外，工单表的关键字段还有 `inner_code` 设备编码。每一个工单都是来服务某一台具体设备的，所以工单表跟设备表也是存在关联关系的。第二个 `user_id`，每一个工单都要交给具体的工作人员来完成执行，这个时候我们需要知道是哪个工作人员，在这里面通过 user id 来建立关联。

还有所属区域 id。我们在新增工单时，就需要通过 region id 来查询该区域下面的工作人员列表，从这里面去选取一个实现本区域内的工单派发。还有指派人 id，咱们刚才提到了，就是我们帝可得的管理人员。

好的表的关键字段我们就聊到这里。那么工单表呢还有两个特殊字段：第一个 `task_status` 叫工单状态，工单状态呢刚刚我们介绍过了，`1` 表示待办，`2` 表示进行中，`3` 表示取消，`4` 表示完成；还有 `create_type`，指的是工单的创建类型，`0` 表示自动，`1` 表示手动。

> **结论**：这些呢是属于静态数据，其实我们可以把它设置为数据字典，来简化查询操作。所以工单表当中有两个数据字典字段。这一点兄弟们先了解一下——下一步配代码生成器的时候，就靠它俩把界面上的中文和数据库里的数字对上号。

### 本章学习路线：代码生成只是起点

到这里，同学们，我们对工单管理的业务流程和数据模型已经有了清晰的认识了。接下来我们来看一下本章的学习路线。

首先，我们将使用若依的代码生成器来生成基础代码，并将其导入到我们的项目当中。然而这些现有的基础代码仅涵盖了单表的增删改查操作，这还不够。为了满足更复杂的业务需求，我们需要深入分析页面原型和具体的需求，然后对工单管理代码进行一系列改造。

### 踩坑：desc 是 MySQL 保留关键字

下面来看一下报错的信息。首先第一个关键字：SQL 语法错误。那为什么会报 SQL 语法错误呢？那么出现错误的位置呢，在 `desc`。

> **易错点**：有小伙伴纠结了，我们整个后端代码都是由若依代码生成器生成的，那为什么会报一个 SQL 语法的错误呢？这个时候呢我们就需要来分析一下生成的工单管理的 mapper 层。

来找到 IDEA，我们定位到 mapper 的代码，找到 `TaskMapper.xml`，双击打开。咱们刚刚执行的是查询语句，所以在查询语句当中，首先我们来执行的是 select 关键字，后面跟上我们显示的字段。再往右拉，出现错误的位置在 `desc` 这里。

这个 `desc` 呢是数据库的一个保留关键字，它用于排序的，我们可以设置当前字段为降序。所以呢你会发现这个字段跟其他显示字段呢颜色不一样，是不是进行了一个高亮呢？

而在工单表当中，这个 `desc` 有什么用呢？来咱们回到数据库再来确认一下，找到工单表，打开字段，这边显示了一个备注说明。也就是说我们在创建工单时，可以在这里面写上备注说明，比如说这是一个加急工单，请在 12 点之前务必完成。所以我们在执行查询语句时这边呢显示备注字段，说明了我们在执行 MySQL 的查询语句时，咱们发现 `desc` 跟在了 select 后方，而它是一个保留关键字，所以放到这个位置呢它就报了一个语法的错误。

那这个问题该怎么解决呢？其实很简单。既然我们现在项目当中想要使用这个保留关键字，作为一个普通字段来描述备注说明的话，那么这里呢我们可以把它改为一个普通字段。那么改为一个普通字段的话，我们需要给它增加一个反引号的标记。

```sql
-- 报错的写法
SELECT task_id, task_code, desc FROM task

-- 加反引号之后
SELECT task_id, task_code, `desc` FROM task
```

> **提示**：反引号就是数字 1 旁边的那个反引号，注意是英文半角状态。我们写上反引号把 `desc` 包起来，那么它就改为了一个普通字段。所以你观察颜色是不是就一致了？

那么咱们改了一个位置还不够。再往下走，咱们在执行动态 SQL 查询时呢，其中判断条件也有一个 `desc`，这里呢我们也需要增加反引号；再往下走，我们还需要在其他的 SQL 片段当中也需要增加一个反引号。内容太多了，咱们自己在课下练习时改造起来呢可能有遗漏的地方，所以我在资料当中为小伙伴们准备了修改后的 mapper 文件。来我们看一下，找到资料目录 day08 当中工单后端，这里来看有一个 `TaskMapper.xml`，咱们来复制一下，替换一下若依生成的部分。

## 工单管理改造：区分工单类型，按设备定位人员
> 对应块：BLK23 | 覆盖分集：P73-P75 | 块标题（分集名）：《实战篇-52.帝可得-工单管理改造-查询工单列表》

工单管理的基础代码我们已经用 AI 平台生成出来了，接下来这段改造要解决三件事：查询工单列表要在同一个接口里区分运营工单和运维工单；新增工单对话框里要根据售货机编号把补货清单和负责人一起带出来；人员清单要分成运营人员和运维人员两条。

这三件事看起来是三个需求，其实是一条主线：**用尽量少的表、用尽量少的对象，把"当前页面到底要看哪一类工单、当前这台设备到底归谁负责"这两件事算清楚。**

### 两个页面为什么显示一模一样的工单

先看现象。在若一管理界面里，运维工单页面点开是这些数据，切到运营工单页面，展示出来的数据跟它一模一样。

为什么？因为这两个页面背后共用的是同一套工单管理的后端接口。接口不区分类型，页面当然只能拿到同一份东西。

所以接下来我们要通过特定的查询条件来区分工单类型，做到：

- 运营工单页面只展示补货工单的列表数据；
- 运维工单页面展示投放工单、维修工单以及撤机工单的列表信息；
- 每一条工单回显的时候，还要带上工单类型（页面上要显示类型名称）。

> **结论**：这一轮改造的核心不是新写一个接口，而是把已有的 `/manager/task/list` 改造成"一个接口、按参数返回不同结果"。

### 读接口文档：五个参数加一个隐藏开关

回到浏览器打开接口文档，看"查询工单列表"这一页：

- 请求路径：`/manager/task/list`
- 请求方式：GET
- 返回结果：标准的分页对象，`total` 是总记录数，`rows` 是结果集

请求参数分两类。

第一类是分页参数 `pageNum`、`pageSize`，这两个是前端必须要传的。中间三个 `taskCode`（工单编码）、`taskStatus`（工单状态）、`productTypeId`（工单类型）是非必需的，对应的正是前端页面上的搜索条件框。

对照页面看就很清楚了：

| 页面 | 搜索条件 |
| --- | --- |
| 运营工单 | 工单编号（`taskCode`）、工单状态（`taskStatus`） |
| 运维工单 | 工单编号（`taskCode`）、工单状态（`taskStatus`）、工单类型（`productTypeId`） |

前端可以把条件传过来做搜索，也可以什么都不传，默认查全部。

第二个参数才是重点，它不在普通的参数列表里，而是藏在 `params` 后面：`params.isRepair`。

它的含义很简单：

- 传 `true`：查运维工单的数据；
- 传 `false`：查运营工单的数据。

怎么确认它真的是这样？抓包最直接。打开 F12 的 Network，刷新运维工单页面，看搜索条件那一串，末尾确实跟着 `isRepair`，值是 `true`；再切到运营工单页面，同样是 `isRepair`，值变成了 `false`。

对上了。所以我们后端就通过 `params.isRepair` 携带的这个值来区分工单类型和返回的工单列表信息。

> **注意**：返回的 `rows` 里，除了工单本身的信息，还必须包含每条工单所关联的工单类型信息，因为前端页面要展示工单对应的类型名称。

### 参数怎么接：复用 Task 和 BaseEntity 的 params

现在问题来了：这些参数我们该怎么接收？

有小伙伴提了个方案——我们之前讲"货道关联商品"的时候设计过 DTO，这里也可以设计一个 DTO 来接收。这没问题，那确实是一种思路。

这里我们用一个更省事的思路：直接复用若一已经生成好的 `Task` 实体类来接收。

回到 `TaskController` 里看那个列表查询方法，还记得我之前分析过的那几个方法吗？`startPage()` 的作用就是从 request 里把 `pageNum` 和 `pageSize` 取出来，实现自动分页。所以这两个参数我们根本不需要手动接收。

那么剩下的四个参数呢？打开 `Task` 实体类看看：

- 有没有 `taskCode`？有，正好对应工单编码；
- 有没有 `taskStatus`？有，正好对应工单状态；
- 再往下拉，有没有 `productTypeId`？有，正好对应工单类型。

那 `params.isRepair` 呢？`Task` 本身没有这个字段，但它有——所有实体类都继承自那个基类 `BaseEntity`，基类里有一个 `params` 属性。

这个 `params` 是干什么用的？它就是专门负责接收前端请求参数的。因为前端传来的参数，命名格式有可能跟实体类的属性名并不相同，`params` 是一个 Map，可以接收各种命名格式、各种类型的参数值。

我们这里通过 `params` 传的是 `isRepair`，它就会把 `isRepair` 封装成 Map 的 key，把前端传的 `true` / `false` 当作 value 塞进去。

```text
前端请求：/manager/task/list
          ?pageNum=1&pageSize=10
          &taskCode=&taskStatus=&productTypeId=
          &params[isRepair]=true

  pageNum / pageSize  --->  startPage() 读走做自动分页，后端不接收
  taskCode            --->  Task.taskCode
  taskStatus          --->  Task.taskStatus
  productTypeId       --->  Task.productTypeId
  params[isRepair]    --->  BaseEntity.params 里的 key "isRepair"
```

所以参数的接收我们直接用 `Task` 实体类就可以，不必额外造 DTO。这也是若一设计的一大特点。

> **提示**：`params` 能这么用，是因为它是一个 Map，前端用 `params[xxx]=yyy` 这种格式传，后端就以 `params.get("xxx")` 这种方式拿，中间不经过任何属性名映射的约束。

### 四层改造：从 TaskVo 一路写到 Controller

确定接口文档之后，我们做一遍思路分析。

#### 先造一个 TaskVo

接口文档返回的结果里，除了工单信息还有工单类型信息，所以我们要设计一个 `TaskVo`。它继承 `Task`，直接拿到父类的工单属性字段，然后自己再增加一个工单类型的对象属性。

```java
@Data
public class TaskVo extends Task {
    /**
     * 工单类型
     */
    private TaskType taskType;
}
```

属性名叫 `taskType`，用 `@Data` 注解拿 getter、setter 和 toString。到这儿 VO 就定义完毕了。

#### Mapper：补上 isRepair 这个开关

找到 `TaskMapper`，在最下方新增一个方法，接收条件就是那个 `Task` 对象，返回 `List<TaskVo>`，方法名就叫 `selectTaskVoList`：

```java
/**
 * 查询工单列表
 *
 * @param task Task
 * @return List<TaskVo>
 */
List<TaskVo> selectTaskVoList(Task task);
```

写完方法名，鼠标悬停，`Alt` + 回车选 `Generate Statement`，IDEA 直接帮我们在同名 XML 里生成一个标签。

里面的 SQL 我们可以参考若一已有的"查询工单列表"那一段——往上拉就在那儿：`include` 是公共的 SQL 语句，`<where>` 里是搜索条件。直接全选复制，粘贴到刚生成的标签里。

注意，这段复制来的搜索条件已经包含了刚才分析接口时的 `taskCode`、`taskStatus`、`productTypeId`，还剩下 `params.isRepair` 这一个条件，这个需要我们手动加。

先看数据库里工单类型表的编号。`1 3 4` 是投放、维修、撤机，这三个对应运维工单；`2` 是补货，对应运营工单。

所以第一个条件：运维工单要匹配三个类型，等号用不了，得换成 `in` 关键字——大家把答案写到弹幕里，`in` 后面可以跟多个条件。

```xml
<where>
    <!-- 从若一已生成的查询工单列表复制来的条件，已包含 taskCode / taskStatus / productTypeId -->
    <if test="params.isRepair != null and params.isRepair == 'true'">
        and product_type_id in (1, 3, 4)
    </if>
    <if test="params.isRepair != null and params.isRepair == 'false'">
        and product_type_id = 2
    </if>
</where>
```

这里有三个细节必须抠一下：

1. `params` 是个 Map 集合，它的 key 叫 `isRepair`，所以后面要跟一个点写 `params.isRepair`，不能写成 `params.isRepairMap` 之类。
2. 先判断 `params.isRepair != null`，不为空再进第二个条件。
3. **判断值要带单引号**。我在 XML 里写的是一个布尔类型的 `true`，但前端通过 GET 传过来的 `true` 和 `false` 其实是字符串——我们现在走的是 HTTP 1.1，GET 请求传递的都是字符串。所以这里必须用单引号包起来，判断的是一个字符串类型的 `"true"`。

运营工单那边只有一个类型，就不能偷懒用 `in` 了，把 `in` 换成等号、`2` 写上就够了。

#### 手动映射：把工单类型一起查出来

条件写完了，但我们返回的是 `TaskVo`，需要手工做映射封装。

往上拉找若一生成的 `resultMap`，以它为模板复制一份，`id` 改名为 `taskVoResult`，返回的结果类型也改成 `TaskVo`。

原本这些自带的标签只映射工单自己，现在要嵌套关联查询工单类型，用的标签是 `<association>`：

```xml
<resultMap id="taskVoResult" type="TaskVo">
    <!-- 若一原本生成的工单字段映射，保持不动 -->
    <id property="id" column="id"/>
    <result property="taskCode" column="task_code"/>
    <result property="taskStatus" column="task_status"/>
    ...

    <!-- 新增：按 product_type_id 嵌套关联查询工单类型 -->
    <association property="taskType" column="product_type_id"
                 select="com.dkd.mapper.TaskTypeMapper.selectTaskTypeById"/>
</resultMap>
```

三个属性这么来的：

- `property` 写 `taskType`，对应 VO 里的对象属性，往下拉若一生成的工单类型映射，它也是 `taskType`；
- `column` 写查询条件，也就是我们的 `product_type_id`，直接复制过来；
- `select` 这里，先自闭合，然后去找工单类型 Mapper 里根据主键查询的那个方法——往下拉第一个就是，根据主键查询返回工单类型实例对象。鼠标右键复制它的方法全限定名，粘到这个位置。粘完记得回头检查包名、类名、方法名三处有没有对错。

这样一来，我们就以工单所对应的类型 id 去查询类型对象，把结果封装给 VO 里的 `taskType` 属性，VO 就同时包含了工单信息和工单类型信息。

最后回到刚才那个 select 标签，把 `resultType` 属性删掉，换成 `resultMap`，值粘上 `taskVoResult`，Mapper 层就编写完毕了。

#### Service 与 Controller：把链路串起来

Service 层最简单。把 `TaskMapper` 里的方法名 `selectTaskVoList` 复制过去，找到对应的 service 接口放到底部，补上签名和注释，`Alt` + 回车选 `Implement Method` 生成实现，里面直接调 Mapper 的同名方法就行。

Controller 层去改造若一已经生成的查询工单列表方法。它的权限注解和请求地址都有，我们跟接口文档核对一下：

- 类上面的 `manager/task` 加上方法上的 `/list`，请求方式是 GET——对应前端 `/manager/task/list`，没问题；
- 条件直接用 `Task` 实体类接收；
- `startPage()` 已经开着了，把原来那一行查询删掉，换成调用 service 取 `TaskVo` 集合，再用 `getDataTable` 转换成分页对象返回给前端。

```java
@GetMapping("/list")
@PreAuthorize("@ss.hasPermi('manager:task:list')")
public TableDataInfo selectTaskList(Task task)
{
    startPage();
    List<TaskVo> voList = taskService.selectTaskVoList(task);
    return getDataTable(voList);
}
```

整条链路是这样串起来的：

```text
Controller  selectTaskList(Task task)
    │  startPage()  ->  pageNum / pageSize 自动分页
    ▼
Service     selectTaskVoList(task)
    ▼
Mapper      selectTaskVoList(task)
    │  动态条件：params.isRepair
    │     'true'  ->  product_type_id in (1, 3, 4)
    │     'false' ->  product_type_id = 2
    ▼
resultMap   taskVoResult  --association-->  taskType（按 product_type_id 查类型）
```

> **易错点**：这是我们第一次在 XML 里写这种动态条件。`true` 查运维、`false` 查运营，千万别写反了。

`Ctrl` + `F9` 热部署更新一下，开始测。

### 翻车现场：漏掉的那个 and

第一个测试就露馅了。

运营工单：只返回两条，数据都是运营工单，类型名称也对。运维工单：返回的也都是运维工单，投放的、维修的都有。基础的类型区分没问题。

紧接着测条件查询，输入一个工单编号点搜索——报错了，SQL 语法错误。

报错位置就是刚刚自己添加的那段 SQL，`product_type_id` 后面那几个数字。回到代码一看，原因很清楚：**新增的这几行忘了加 `and` 关键字**。

多个条件之间必须用 `and` 或 `or` 拼接。上一行的条件末尾没有 `and`，SQL 直接就串成了一坨，数据库自然解析不了。

```xml
<!-- 错误：上一行条件后面少了 and -->
product_type_id in (1, 3, 4)

<!-- 正确：补上 and -->
<if test="params.isRepair != null and params.isRepair == 'true'">
    and product_type_id in (1, 3, 4)
</if>
<if test="params.isRepair != null and params.isRepair == 'false'">
    and product_type_id = 2
</if>
```

> **易错点**：复制若一的 `where` 片段时，它内部的每个条件都自带 `and`；而我们手写的新增条件，`and` 是要自己负责的。这两批条件混在同一个 `where` 里时，特别容易漏。

### 测试：类型、编号、状态与排序

补上 `and` 之后重新热部署，再回来逐项测。

工单编号：填进去搜索，返回的就是匹配的那一条。

工单状态：选"代办"，返回的两条都是代办工单；选"记账中"（这段没有数据）；选"已取消"，出来的是取消数据；"完成中"的数据比较多，都能对上。

工单类型：这是运维工单页面才有的第三个条件。选投放工单，返回的都是投放工单相关的；换维修工单，同样对得上。运维侧的条件查询全部测完。

运营工单的接口跟运维走的是同一个，所以运营侧就不重复测了。

还剩一个排序。查询条件和排序关键字要一起补上：

```xml
order by create_time desc
```

意思是工单按创建时间降序展示。把这一行加到 `where` 下面，热部署刷新页面——最新创建的工单排到了第一条。切到运维工单页面也一样，第一条投放工单就是创建时间最新的那个。

到这里，查询工单列表的后端接口改造完成并测试通过。回头理一下：先设计 `TaskVo` 承接返回结果（工单信息 + 工单类型信息），再写 `TaskMapper`，按 `Task` 条件查询返回 `TaskVo` 集合，手动补两个条件区分运营 / 运维，同时加上创建时间降序，然后做手动映射封装和关联嵌套查询；Service 只是复制方法名重写实现，Controller 改造若一已有的方法、把 service 换成查 VO 集合、再返回分页对象。屏幕前的小伙伴们可以照着笔记动手实操，加油，下一讲等你。

### 按售货机编号获取运营人员

需求是这样的：管理员在运营工单页面点"新增工单"，会弹出一个对话框。我们输入售货机编号、失掉焦点之后，系统要动态做两件事——查出这台设备的补货清单，以及查出负责当前区域的运营人员列表。

补货清单这块我们在设备管理模块已经做完了：之前实现的"根据售货机编号查询货道列表"接口，在这个场景里直接复用就能拿到货道编号、名称、当前数量、剩余可添加数量和补满数量，实现数据回显。

但点击补货详情对话框时控制台报了个 404。为什么？因为"获取运营人员列表"的后端接口我们还没写。

那就来看这个接口的文档：`GET /manager/emp/business/{innerCode}`，路径参数就是我们的设备编号，返回是标准的 `AjaxResult`——`code`、`message`、`data`，其中 `data` 是一个数组，表示返回的运营人员列表集合。

看接口文档会引出一个问题：**怎么根据售货机的编号查到运营人员列表？**

#### 四张表，还是两张表

先回到业务关系图。我们的设备是投放在某个点位的，点位属于某个区域，区域再关联工作人员。

```text
按业务关系看：

    设备（售货机）
        │
        │ 投放在
        ▼
      点位
        │
        │ 属于
        ▼
      区域 ──────────► 关联工作人员

    这条链路走下去 = 设备表、点位表、区域表、员工表，四张表
```

看起来要关联四张表才能查到人，对不对？把答案写到弹幕里——其实两张表就够了。

关键在于设备表里有一个冗余字段 `regionId`，也就是这台设备所属的区域 id。

```text
实际查询只要：

    innerCode  --->  设备表  --->  region_id
                                        │
                                        ▼
                     员工表 where region_id = ? and role_code = ? and status = ?
```

第一步，根据前端传来的 `innerCode` 查设备表数据，拿到里面的 `regionId`；第二步，用这个 `regionId` 去查负责该区域的员工列表。

但光有区域还不够。因为负责这个区域的员工，角色有运营的、有维修的——你在运营工单界面把维修人员也列出来，这显然不合适吧？所以还得再加一个角色编号 `roleCode` 作为条件，运营这边取 `1002`，表示运营员。另外员工的状态必须为启用（`1`），也就是正常上班的员工。

三个条件一组合，负责当前区域的运营人员列表就出来了。

> **结论**：得益于我们之前在设备表里做了反三范式的设计（冗余存了 `region_id`），本来要串四张表的查询被压缩成了两张表，查询操作得以简化。

#### 设备层：一条注解 SQL

代码分三块来写。

第一块在设备 Mapper：新增一个"根据售货机编号查询设备信息"的方法，返回售货机对象，里面自然就带着这台设备所属的区域 id。

方法名叫 `selectByInnerCode`，参数是 `String innerCode`。这个 SQL 非常简单，所以我们不用 XML，直接用注解的方式：

```java
/**
 * 根据设备编号查询设备信息
 *
 * @param innerCode 售货机编号
 * @return 售货机对象
 */
@Select("select * from t_vending_machine where inner_code = #{innerCode}")
VendingMachine selectByInnerCode(String innerCode);
```

表名 `t_vending_machine` 比较长，千万别手写——回到数据库客户端工具找到设备表，复制表名粘过来就行。

第二块在设备 Service：把 Mapper 里的方法签名复制过去，**把 `@Select` 注解去掉**（这一层不碰数据库），`Alt` + 回车重写方法，实现里直接调 mapper 的 `selectByInnerCode`，把 `innerCode` 传过去。

到这儿设备这边就搞定了，这是准备工作。

#### 员工 Controller：三个条件把人筛出来

重点在员工的 Controller。按接口文档写方法：

- 请求方式是 GET，写一个 `@GetMapping`，路径 `/manager/emp` 在类上面已经声明好了，方法上只需要写 `/business/{innerCode}`；路径参数用占位符，内容叫 `innerCode`；
- 返回值是标准的 `AjaxResult`，方法名就叫 `businessList`；
- 权限注解直接复制若一生成的"查询人员列表"那个注解——它是查询员工列表的权限，正好对得上。不需要 `@Log` 日志记录；
- 中文注释按若一的格式写，把 `@param` 和 `@return` 干掉的风格保持一致。

方法架子搭好之后，实现就三步。

**第一步：根据 `innerCode` 查询售货机信息。** 这里要调设备的 Service，而在员工的 Controller 里调设备 Service，得先把设备 Service 注入进来——`@Autowired` 注解，`private VendingMachineService vendingMachineService`，写完变量名 IDEA 会帮你补全。

```java
// 1. 根据 innerCode 查询售货机信息，获取设备所属区域id
VendingMachine vendingMachine = vendingMachineService.selectByInnerCode(innerCode);
```

**第二步：加非空判断。** 这一步一开始写漏了，回来补的。

前端如果传了一个不存在的设备编号，我们拿不到设备对象，接着调 `vm.getRegionId()` 就会抛空指针异常——用户体验非常不友好。所以在中间插一个判断：设备为空就直接返回一个 error。

`error` 是 `BaseController` 提供的，底层走的是 `AjaxResult.error()`；如果你想做精准提示，直接在括号里传一句提示文案给前端就行。

```java
if (vendingMachine == null) {
    return error("售货机不存在");
}
```

**第三步：封装条件查人。** 新建一个 `Emp` 对象，把三个条件 set 进去：

```java
// 2. 根据区域id、角色编码以及员工状态查询运营人员列表
Emp emp = new Emp();
// 设备所属区域id
emp.setRegionId(vendingMachine.getRegionId());
// 角色编码：运营员
emp.setRoleCode(DkConstant.ROLE_CODE_BUSINESS);
// 员工状态：启用
emp.setStatus(DkConstant.EMP_STATUS_NORMAL);

return success(empService.selectEmpList(emp));
```

`empService.selectEmpList` 这个查询方法是若一已经生成的，按员工条件查员工集合，我们直接调用，把结果 `success` 返回给前端就完事了。

#### 把 1002、1003 交给常量

这里插一段我们不写死数字的理由。

角色编码我们取的是 `1002`，去数据库的工单角色表里确认一下，确实是运营员。但代码里直接写 `1002` 可读性太差——半年后谁看得懂这个 1002 是谁。

所以提前准备一个常量类：`dk.common.constant` 下的 `DkConstant`，里面定义了两个常量：

```java
public interface DkConstant {
    /** 运营员 */
    Long ROLE_CODE_BUSINESS = 1002L;

    /** 维修员 */
    Long ROLE_CODE_OPERATOR = 1003L;

    /** 员工启用 */
    Long EMP_STATUS_NORMAL = 1L;

    /** 员工停用 */
    Long EMP_STATUS_STOP = 0L;
}
```

通过常量做到"见名知意"，代码可读性立刻上来了。Controller 里就改成 `DkConstant.ROLE_CODE_BUSINESS`，不用再写字符串或数字。

员工状态这个常量还有一个额外情况：我之前其实已经准备好了员工启用和禁用的常量，只不过类型写成了布尔类型，现在要调整。打开代码的历史记录能找到：把启用那个常量的类型改成 `Long`、值改为 `1`；停用那个也改成 `Long`、值改为 `0`（状态 `1` 对应启用，`0` 对应停用）。用数字表达状态的时候，同样不建议各位小伙伴直接在代码里写数字。

现在测试。`Ctrl` + `F9` 热部署，回到页面：运营工单 → 新增 → 复制第三台设备的编号进去，运营人员一栏展示出曹操和夏侯惇。再换第一台设备的编号，展示的是孙权。这就做到了根据设备所属区域的 id 查找对应角色的员工列表，区域划分精准。

最后再测那个非空判断：随便输入一个不存在的设备编号，失焦，页面直接提示"售货机不存在"。

顺带把这三个条件再强调一次，它们就是"人"的筛选公式：

| 条件 | 含义 | 运营人员取值 |
| --- | --- | --- |
| `regionId` | 设备所属区域 | `vendingMachine.getRegionId()` |
| `roleCode` | 角色编码 | `1002`（运营员） |
| `status` | 员工状态 | `1`（启用） |

设备存在就封装这三个条件、调 Service 查询、把符合条件的人员列表返回前端展示。写完了，大家可以照笔记动手实操。

### 换个角色再来一次：运维人员列表

需求换一个方向：同样是在运营工单界面点击新增工单，这次要根据售货机编号动态获取负责当前区域的**运维**人员列表。前端代码已经写好了。

接口文档看得很轻：`GET /manager/emp/operation/{innerCode}`，路径参数 `innerCode`，返回标准 `AjaxResult`，把符合条件的运维人员列表返回前端。

关系图还是那张，答案也还是两张表：设备表 + 员工表。先根据设备编号查设备表拿到 `region_id`，再根据 `region_id` 查负责该区域的员工列表。角色编号这里换成 `1003`，也就是维修员；状态同样是 `1` 表示启用。

至于代码，Mapper 层和 Service 层完全复用——上一讲我们已经写好了"根据售货机编号查询售货机信息"这一步，这两步可以省略不写。只需要在员工 Controller 里再写一个方法：

- `@GetMapping`，路径类上已经有两层了，直接写 `/operation/{innerCode}`。这个单词比较长，回到浏览器把路径复制过来，把冒号改成花括号；
- 返回 `AjaxResult`，方法名 `operationList`；
- 权限注解直接复制"查询运营人员列表"的注解，中文注释按若一风格写；
- 接收 `innerCode` → 查售货机信息 → **判空**（售货机不存在就返回报错提示）→ 设备存在就封装三个条件调 `empService.selectEmpList`，把结果响应给前端。

```java
/**
 * 根据售货机编号获取运维人员列表
 *
 * @param innerCode 售货机编号
 * @return 结果
 */
@GetMapping("/operation/{innerCode}")
@PreAuthorize("@ss.hasPermi('manager:emp:list')")
public AjaxResult operationList(@PathVariable("innerCode") String innerCode)
{
    // 1. 根据 innerCode 查询售货机信息
    VendingMachine vendingMachine = vendingMachineService.selectByInnerCode(innerCode);

    if (vendingMachine == null) {
        return error("售货机不存在");
    }

    // 2. 根据区域id、角色编码以及员工状态查询运维人员列表
    Emp emp = new Emp();
    // 设备所属区域id
    emp.setRegionId(vendingMachine.getRegionId());
    // 角色编码：维修员
    emp.setRoleCode(DkConstant.ROLE_CODE_OPERATOR);
    // 员工状态：启用
    emp.setStatus(DkConstant.EMP_STATUS_NORMAL);

    return success(empService.selectEmpList(emp));
}
```

写这段的时候有个小体会：整个编码几乎都是靠 IDEA 的通用代码模板补全的，只要注释写清楚，方法和参数它就能连注释一起帮你生成出来——它甚至判断出了这里要查的是运维人员，直接把常量写成了 `ROLE_CODE_OPERATOR`。注释对后期可读性的帮助也确实非常大。

测试：复制一台 `A10` 开头的设备编号，新增工单输入后失焦，显示陆逊，就是该设备所属区域的负责人；换成第二台 `5CY` 开头的设备，列出了许褚、张辽等三名负责该区域的工作人员。我们选择一名员工，再选工单类型、写上备注、点"加急单"确定，前端就向后端发送请求了——下一讲我们来实现工单的新增功能。

到这里，按售货机编号获取当前区域运维人员列表也改造并测试完成。整个思路和获取运营人员列表一模一样：Mapper 和 Service 复用，Controller 按接口文档写，接收参数、查售货机、判空返回提示、再封装"区域 id + 员工启用 + 角色编码"三个条件查询返回前端。小伙伴们动手实操吧，加油，下一讲等你。

## 新增工单：一张接口扛起运维与运营两套业务
> 对应块：BLK24 | 覆盖分集：P76-P77 | 块标题（分集名）：《实战篇-55.帝可得-工单管理改造-新增工单上》

刚刚把"根据设备所在区域获取人员列表"这个功能收尾，接下来就轮到新增工单了。

前端咱们早就写完了——有新增运维工单的界面，也有新增运营工单的界面。现在要干的事，就是把这个界面对应的后端接口实现出来。

这里先说清楚一个设计上的决定：**这个接口将被运维工单和运营工单共享**，目的是提高代码的复用性。

### 需求：一个接口，两种工单

运营和运维两类工单，操作的对象根本不是一回事：

- **运维工单**，动的是售货机本身。投包工单用于新设备的投放，撤机工单用于设备的撤回，维修工单用于设备的维修。
- **运营工单**，动的是售货机里的货。目前我们关注的是**补货工单**，用于售货机货物的补充。

补货工单还多一层东西：提交的时候还得带**补货详情**——哪个货道对应什么商品、需要补几件货。因为一台售货机有好几个货道，一条补货工单可能对应好几条货道。

```text
                      新增工单（一个接口）
                              │
            ┌─────────────────┴─────────────────┐
            │                                   │
        运维工单                            运营工单
     操作的是售货机本身                  操作的是售货机里的货
            │                                   │
      ┌─────┼─────┐                    ┌────────┴────────┐
     投放   维修   撤机                 补货（本讲关注）
                                          │
                                    还要带补货详情
                                 （货道 → 商品 → 数量）
```

所以这个接口天然是一个"主单 + 明细"的形态，而我们的代码里也是按这个形态来设计的。

### 照着接口文档认参数

在动手写之前，先把接口文档翻出来对一遍——请求路径 `manager/task`，请求方式 `post`，调参数是 JSON 格式。重点看请求参数这一块。

| 参数 | 含义 | 谁来给 |
| --- | --- | --- |
| `createType` | 工单创建类型 | 前端写死传 `1`，后台点"新增"是手动创建 |
| `innerCode` | 工单所服务的设备编号 | 前端，靠它能反查设备信息 |
| `userId` | 执行人 id | 前端选中的干活的人 |
| `assignerId` | 指派人 id | **前端标的是非必需**，前端不一定给 |
| `productTypeId` | 工单类型 | 投放/维修/撤机是运维，补货是运营 |
| `desc` | 工单的描述信息 | 前端，就是界面上的备注说明 |
| `details` | 补货详情集合 | 只有补货工单才有 |

几个点要特别拎出来。

**`createType` 为什么固定是 1？** 因为在后台管理系统里，我们点"新增"创建出来的就是手动创建的单子，创建方式永远是手动的，前端直接写死传 1。

**`assignerId` 前端不给怎么办？** 前端把 `assignerId` 标记成了非必需，那我们就在后端取**当前登录人的 id** 来设置——登录人就是工单的创建人，也是派活的人。这一点没毛病吧？

**参数和原型是对得上的。** 设备编号对应 `innerCode`，选中的人对应 `userId`，还有备注说明。而创建类型在前端写死、指派人前端没选所以要后端补。

补货工单还要多传一个 `details` 的集合，里面每一条包含：货道的编号、补货的数量、所对应的商品 id、商品名称、商品图片。

```text
右侧的「补货详情」区域
┌──────────────────────────────────────────────┐
│  货道编号   │  补货数量   │  商品名称         │
│  （原型显示）│ （原型显示） │ （原型显示）      │
└──────────────────────────────────────────────┘
   ↓ 前端提交
details : [
  { skuCode, expectCapacity, skuId, skuName, skuImage },
  { skuCode, expectCapacity, skuId, skuName, skuImage },
  ...
]
     ↑ skuId 和 skuImage 前端界面上并没有显示，
       但后端这边是需要的，所以一并传过来
```

这里有多个货道信息，所以我们需要通过 `details` 的集合来接收。

返回结果就是一个标准的 AjaxResult：业务状态码 `200`，`msg` 提示"操作成功"。

### 造两个 DTO 把参数接住

看完请求参数就要问了：我们后端接收前端这些参数，有没有对应的实体类？

小伙伴们思考下——**是不是没有啊？**

因为这里面涉及到**两张表**数据的新增：有工单表的，有工单详情表的。一个实体类装不下，那就得设计一个专门用来接收前端参数的实体类。

这个实体类的简称是什么呢？小伙伴们把答案写到弹幕当中。

……没错，就是 **DTO，数据传输对象**。

我们需要设计**两个** DTO。

第一个 `TaskDetailsDto`，用于接收前端每个货道的补货清单数据。字段参考页面原型来写：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `skuCode` | `String` | 货道编号 |
| `expectCapacity` | `Long` | 补货数量 |
| `skuId` | `Long` | 商品 id |
| `skuName` | `String` | 商品名称 |
| `skuImage` | `String` | 商品图片 |

```java
@Data
public class TaskDetailsDto {
    /** 货道编号 */
    private String skuCode;
    /** 补货数量 */
    private Long expectCapacity;
    /** 商品 id */
    private Long skuId;
    /** 商品名称 */
    private String skuName;
    /** 商品图片 */
    private String skuImage;
}
```

写字段的时候有几个小细节挺有意思。敲完 `skuName` 这个名字，回车换行，光标在上一行——通义灵码立刻就明白了，"生成了关键字、类型以及变量名"，直接按 Tab 键就能用；到 `skuImage` 这一行它就没这么智能了，变量名给的不是我们要的，但关键字和类型还是能用的，我们把变量名改成 `skuImage` 就行。

属性定义完，生成 get/set 方法，类上加上 `@Data`。第一个 DTO 就齐了。

第二个 `TaskDto`，用于接收前端的整体数据——点击新增工单时所有的数据先封装到这个 DTO 里面。

```java
@Data
public class TaskDto {
    /** 创建类型 */
    private Long createType;
    /** 设备编号 */
    private String innerCode;
    /** 执行人 id */
    private Long userId;
    /** 指派人 id */
    private Long assignerId;
    /** 工单类型 */
    private Long productTypeId;
    /** 描述信息 */
    private String desc;
    /** 工单详情（只有补货工单才有这个集合） */
    private List<TaskDetailsDto> details;
}
```

注意 `assignerId` 这个字段前端没有提供，我们在稍后的后端流程里来设置。另外 `details` 这个集合，只有补货工单才有。

我再强调一下这个结构：前端提交工单时，先把所有数据封装给 `TaskDto`；如果是补货工单，那么 `TaskDto` 里面会包含一个 `details` 集合，集合里的元素就是 `TaskDetailsDto`，一个元素里装着一个货道的补货清单数据。

```text
TaskDto  （整体提交数据）
  ├─ createType / innerCode / userId / assignerId
  ├─ productTypeId / desc
  └─ details : List<TaskDetailsDto>
        ├─ [0] skuCode / expectCapacity / skuId / skuName / skuImage
        ├─ [1] skuCode / expectCapacity / skuId / skuName / skuImage
        └─ [n] ……（有几条货道就几条）
```

DTO 创建完毕，接下来编写后端的三层代码。

### 批量新增工单详情

#### 让通义灵码把单个新增改成批量

一个补货工单会带好几条工单详情，所以我们要在工单详情的 Mapper 里添加一个**批量新增**的方法。

先让通义灵码学习它的单个新增——找到单个新增的方法，打开它对应的 XML 标签，复制一份，然后跟通义灵码说：

> 你是一名软件工程师，请把下面的 XML 改成批量新增。

它生成的结果里还带着动态 `<if>` 判断，我们就告诉它不需要动态 `<if>` 标签，再生成一次。这回得到的 XML 就是我们想要的结果了：`insert into` 后面**直接指定字段名**，然后通过 `<foreach>` 遍历多个值。

```xml
<insert id="batchInsertTaskDetails" parameterType="java.util.List">
    insert into t_task_details (sku_code, sku_id, sku_name, sku_image, expect_capacity)
    values
    <foreach collection="list" item="item" separator=",">
        (#{item.skuCode}, #{item.skuId}, #{item.skuName}, #{item.skuImage}, #{item.expectCapacity})
    </foreach>
</insert>
```

> **提示**：字段名要和实际的表结构对齐，这里按 DTO 的属性名写，落地时以数据库建表语句为准。

XML 生成完毕，接着创建 Mapper 的方法，放在接口的最下方，返回值是 `int`，参数是一个泛型为 `TaskDetailsDto` 的 `List` 集合：

```java
/**
 * 批量新增工单详情
 * @param taskDetailsList 工单详情集合
 * @return 影响行数
 */
int batchInsertTaskDetails(List<TaskDetailsDto> taskDetailsList);
```

#### Mapper 之上为什么还要罩一层 Service

这里可能小伙伴有一个疑问：我们已经编写好了工单详情的 Mapper 层代码，在工单的业务层当中**直接调用 Mapper 层**也可以完成批量新增，为什么还要编写工单详情的 Service 层代码呢？

这么做的目的，是为了**业务层和持久层实现责任分离**，同时呢也提高代码的可维护性。在业务层当中我们还可以控制事务的传播行为等等优点。

所以我们建议：不同模块之间的业务调用，走的是 **Service 层之间的调用**。当然了，业务简单的时候直接调 Mapper 层也是可以的，这一点小伙伴们知道一下就可以了。

Service 层代码的命名我们完全可以参考 Mapper 层的，所以这个方法直接复制过来重写一下就行，实现里直接调用 Mapper 的批量新增，把 `List` 集合传过去：

```java
/**
 * 批量新增工单详情
 */
@Override
public int batchInsertTaskDetails(List<TaskDetailsDto> taskDetailsList) {
    return taskDetailsMapper.batchInsertTaskDetails(taskDetailsList);
}
```

到这里，新增工单的准备工作——**两个 DTO 创建**以及**工单详情的批量新增**——就完成了。

### 核心业务八步

整个新增工单的核心业务是在 Service 层当中。先看它的方法签名：

```java
/**
 * 新增运营和运维工单
 * @param taskDto 工单数据
 * @return 影响行数
 */
@Transactional
public int insertTask(TaskDto taskDto) { ... }
```

拿到前端传过来的 `TaskDto` 之后，业务流程一共八步。整体长这样：

```text
TaskDto
  │
  ├─1 设备存在？ ──── 不存在 ──▶ ✗ 抛异常
  ├─2 设备状态配得上工单类型？ ─ 不配 ──▶ ✗ 抛异常
  ├─3 该设备有"未完成的同类型工单"？ ─ 有 ──▶ ✗ 抛异常
  ├─4 执行人存在？ ──── 不存在 ──▶ ✗ 抛异常
  ├─5 执行人区域 == 设备区域？ ──── 不等 ──▶ ✗ 抛异常
  │
  ├─6 DTO→PO，补齐属性 → insert 工单表
  │
  ├─7 是补货工单？ ──── 否 ──▶ 方法结束
  │
  └─8 DTO→PO，补 taskId → 批量 insert 工单详情表
                （整个方法 @Transactional，涉及两张表）
```

#### 先校验设备存在

第一步是工单的业务校验：根据前端传来的 `innerCode` 查询售货机，不存在就抛出异常。

在工单类当中要查询售货机，我们就需要注入设备的 Service：

```java
@Autowired
private DkDeviceService deviceService;

// 1.查询售货机是否存在
DkDevice vm = deviceService.selectDeviceByInnerCode(taskDto.getInnerCode());
if (vm == null) {
    throw new ServiceException("设备不存在");
}
```

> **易错点**：售货机都不存在了，后续的工单业务还有必要创建吗？肯定不需要。所以这里必须先拦下来，抛出异常做一个友情提示。

#### 设备状态必须和工单类型对得上

第二步校验售货机的**状态**与**工单类型**是否相符。这是什么意思呢？来同学们思考一下。

- 如果管理员创建的是一个**投放**工单，但这个设备状态为"运行中"，表示这个设备曾经已经被别人投放成功了，**还能再投放吗？** 不能，设备已经在运营中，无法进行二次投放 → 抛异常。
- 如果管理员创建的是一个**维修**工单，但设备状态不在运行中，说明设备要么没投放、要么处于撤机状态，**还能维修吗？** 肯定不行 → 抛异常。
- 如果创建的是一个**补货**工单，设备状态同样得在运行中，不然你没法往一台没运营的机器里补货 → 抛异常。
- 最后是**撤机**工单：只有运行中的设备才能撤。你没投放，或者已经撤机成功了，还能再次撤机吗？肯定不行 → 抛异常。

所以创建工单之前，都要根据工单的类型和当前设备状态来校验：投放工单要求设备**不能**处于运行中，而其他三种类型——维修、补货、撤机——要求设备**必须**处于运行中。

| 工单类型 | 常量 | 值 | 对设备状态的要求 |
| --- | --- | --- | --- |
| 投放 | `DkTaskType.DEPLOY` | 1 | 设备不能在运行中 |
| 补货 | `DkTaskType.RESTOCK` | 2 | 设备必须在运行中 |
| 维修 | `DkTaskType.REPAIR` | 3 | 设备必须在运行中 |
| 撤机 | `DkTaskType.REMOVE` | 4 | 设备必须在运行中 |

这四段判断内容实在太多了，全写在一个方法里看起来不太优雅，后期的扩展与维护也不太方便，所以我们专门抽取一个新的方法来干这件事。这个方法不需要返回值，接收设备状态和工单类型两个参数：

```java
/**
 * 校验售货机的状态与工单类型是否相符
 * @param vmStatus 设备的状态
 * @param productTypeId 工单的类型
 */
private void checkCreateTask(Long vmStatus, Long productTypeId) {
    // 如果是投放工单，设备在运行中，无法投放
    if (productTypeId.equals(DkTaskType.DEPLOY) && vmStatus.equals(DkConstant.VM_RUNNING)) {
        throw new ServiceException("该设备状态为运行中，无法进行投放");
    }
    // 如果是维修工单，设备不在运行中，无法维修
    if (productTypeId.equals(DkTaskType.REPAIR) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
        throw new ServiceException("该设备状态不为运行中，无法进行维修");
    }
    // 如果是补货工单，设备不在运行中，无法补货
    if (productTypeId.equals(DkTaskType.RESTOCK) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
        throw new ServiceException("该设备状态不为运行中，无法进行补货");
    }
    // 如果是撤机工单，设备不在运行中，无法撤机
    if (productTypeId.equals(DkTaskType.REMOVE) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
        throw new ServiceException("该设备状态不为运行中，无法进行撤机");
    }
}
```

写完注释之后，这段业务判断基本就是照着注释敲——**只要你把注释写好，这些繁琐的代码通义灵码就能自动生成**，实在太方便了。

抽取完之后，回到新增方法里，在第二步调用它，把设备的状态和工单类型传进去：

```java
// 2.校验售货机状态与工单类型是否相符
checkCreateTask(vm.getStatus(), taskDto.getProductTypeId());
```

#### 别让同一种工单重复创建

第三步，检查这台设备是否有**未完成的同类型工单**。

这是什么意思呢？同学们思考一下：如果我已经创建了个工单分配给张三了，但张三还没有完成，请问这个工单我还能再次创建分给其他人吗？如果我硬是再创建分配给其他人，那这个工单不就重复了嘛。比如它是一个维修工单，张三刚维修完，李四再去维修，是不是就不合适了。

所以说，**正在进行中的工单，或者说未完成的工单，同一种类型只能有一个**。创建第二个的话，我们就应该抛出异常提示用户不能重复创建。

校验要**根据设备编号 + 工单类型 id + 工单状态属于进行中**这三个条件去查询数据库，看看是否有记录：

```java
// 3.检查设备是否有未完成的同类型工单
if (hasTask(taskDto)) {
    throw new ServiceException("该设备已有未完成的工单，不能重复创建");
}

/**
 * 是否存在进行中的同类型工单
 */
private boolean hasTask(TaskDto taskDto) {
    // 创建task条件对象，并设置设备编号和工单类型以及工单的状态为进行中
    Task taskPara = new Task();
    taskPara.setInnerCode(taskDto.getInnerCode());
    taskPara.setProductTypeId(taskDto.getProductTypeId());
    taskPara.setStatus(DkTaskStatus.IN_PROGRESS);
    // 调用taskMapper来查询数据库，查看是否有符合条件的工单列表
    List<Task> list = taskMapper.selectTaskList(taskPara);
    return list != null && list.size() > 0;
}
```

三个条件封装好之后，调 Mapper 查询，返回的是一个 `Task` 的 `List` 集合。如果这个集合有数据，就表示有未完成的同类型工单，直接抛异常。

> **提示**：这里有个细节——工单状态的常量**不叫** `TASK_STATUS_DOING`，我们项目里叫 `IN_PROGRESS`，对应的数值是 `2`。写错了编译能过，行为就不对了。

顺带说一句，这段代码我们也可以像第二步那样抽取成一个独立的方法。第二步那个抽取是我们手动敲出来的，其实**也可以交给 IDEA 来抽取**，快捷键是 `Ctrl + Alt + M`，选中代码按下去就自动抽好了，我们只需要改个方法名。

#### 员工存在，并且区域要对得上

第四步，查询并校验员工是否存在：

```java
// 4.查询并校验员工是否存在
DkEmployee emp = empService.getById(taskDto.getUserId());
if (emp == null) {
    throw new ServiceException("员工不存在");
}
```

这里有个坑要特别注意。通义灵码给我们补全的代码，提供的是 `getAssignerId()`——而 `assignerId` 是谁呢？是**指派人** id，也就是创建工单的人。我们要查询的是**干活的人**，所以一定要把它改成 `getUserId()`。

> **易错点**：`getById(谁)` 决定了我们查的是"派活的人"还是"干活的人"。这两个 id 在工单表里可是两个独立的字段，填反了业务就全乱了。

而这一步为什么非做不可呢？小伙伴们可能会好奇：`userId` 我之前查过数据库，它肯定是存在的呀，为什么还要再做二次校验？

是这样的——**因为前端传递的参数是可以篡改的，我们认为这种传参是不安全的**。举个例子：负责当前设备区域的员工是张三，但我故意在前端传的 id 并不是张三而是 10，而这个 10 号员工又不存在，那么请问这个工单创建完以后它是有效工单吗？那肯定不是啊。

所以对于一些比较敏感的数据，我们在后端一定要进行**二次校验**。

第五步，员工存在了，还得判断当前设备所属的区域是否跟员工负责的区域一致。如果不是同一个区域，我们还需要抛出异常，给前端做出一个提示：**非同区域下的工作人员是不能接受工单的**。

```java
// 5.校验员工区域是否匹配
if (!emp.getRegionId().equals(vm.getRegionId())) {
    throw new ServiceException("员工区域与设备区域不一致，无法处理此工单");
}
```

> **提示**：这里为什么用 `equals` 而不是不等号 `!=`？因为我们的 `regionId` 用的是**包装类**，包装类是有**缓存**的。如果超过这个缓冲区——比如我们区域的 id 是 200——用不等号判断的话，它比的是**内存地址**。虽然这两个包装类的值都是 200，但内存地址是有所不同的，返回值也为 false，那这种设计就有坑了。所以我们建议所有的包装类型都用 `equals`，不要用 `==` 或 `!=` 来判断。

#### DTO 转 PO，把缺的属性补上

前面五关都过了，第六步就可以保存工单信息了。这里需要把前端传递的 DTO 转为 `Task` 的 PO 实体类，并补充部分属性，然后调用 Mapper 保存。

先看一下两边字段的对比。前端提交的参数一共六个：创建类型、设备编号、干活的人、派活的人、工单类型、描述信息。而数据库工单表所需要的字段就比较多了：

| 工单表字段 | 谁来给 |
| --- | --- |
| `id` | 主键自增，不用管 |
| `task_code` 工单编号 | **我们稍后需要生成** |
| `status` 工单状态 | 稍后手动指定为"已创建" |
| `create_type` 创建类型 | 前端提供 |
| `inner_code` 设备编号 | 前端提供 |
| `user_id` 执行人 | 前端提供 |
| `user_name` 执行人名称 | 通过员工表获取 |
| `region_id` 所属区域 id | 通过设备表获取 |
| `remark` 备注信息 | 前端提供 |
| `product_type_id` 工单类型 | 前端提供 |
| `assigner_id` 指派人 id | Controller 层通过 BaseController 获取登录人设置到 DTO 里 |
| `addr` 地址信息 | 通过设备获取 |
| `create_time` 创建时间 | 我们设置 |
| `update_time` 更新时间 | 我们设置 |

看到这里小伙伴们就知道了：**主键是自增的，前端一共提供了六个参数，其余部分我们需要补充**。

先把 DTO 的这六个参数拷贝到 PO 里，可以用 `BeanUtils.copyProperties`：

```java
// 6.将DTO转为PO，并补充属性，然后保存工单
Task task = BeanUtils.copyProperties(taskDto, Task.class);

// 工单状态：创建工单，也是待处理的工单
task.setStatus(DkTaskStatus.CREATED);

// 执行人名称，可以通过员工对象来获取
task.setUserName(emp.getUsername());

// 所属区域id，可以通过设备对象来获取
task.setRegionId(vm.getRegionId());

// 地址，可以通过设备来获取
task.setAddr(vm.getAddr());

// 创建时间
task.setCreateTime(LocalDateTime.now());

// 工单编号（稍后详细介绍）
task.setTaskCode(generateTaskCode());
```

更新时间我们在这里就不再指定了。普通字段的补充就搞定了，还剩下一个**工单编号**。

保存之前先把工单编号设置上，然后调用 Mapper 完成保存：

```java
// 调用mapper实现保存
int rows = taskMapper.insertTask(task);
```

返回的结果就是影响的行数，我们叫它 `taskResult`，方法本身返回的也是影响行数，直接把它返回即可。第六步搞定。

#### 只有补货工单才落工单详情

第七步，判断这个工单类型是否为**补货工单**：

```java
// 7.判断是否为补货工单
if (!taskDto.getProductTypeId().equals(DkTaskType.RESTOCK)) {
    return rows;
}
```

不是补货工单的话，方法到这里就结束执行了。

那如果是补货工单，我们就需要保存工单详情——这就是第八步。把前端传递的 `TaskDetailsDto` 转成 PO 的实体类 `TaskDetails`，补充相关属性，调用我们刚刚编写的工单详情的批量保存方法，加到数据库当中。

在取出这个集合之前先做个判断：

> **易错点**：如果这个集合为空的话，后续代码还有必要去执行吗？是不是就没有必要了？所以这里需要判断一下工单详情不能为空。对集合做空值判断，可以使用 hutool 的工具类 `CollUtil.isEmpty`，为空就抛出业务异常"补货工单详情不能为空"。

真正的第八步是 **DTO 转 PO**。这个转换操作我们之前学过，可以使用 Stream 流的 `map` 方法实现类型的转换。

先看两边的字段：工单详情表第一个字段 `id` 自增不用管，第二个 `task_id` 在新增完工单以后可以通过它的主键回填获取，剩下的五个参数就跟前端提交的是一样的。那我们是不是可以用工具类直接做属性拷贝，免去一个一个 set 的操作了？

```java
// 8.将DTO转为PO，补充属性，然后保存工单详情
List<TaskDetails> detailsList = taskDto.getDetails().stream()
    .map(detailDto -> {
        TaskDetails detail = BeanUtils.copyProperties(detailDto, TaskDetails.class);
        // 单独设置工单id，通过task对象的主键获取
        detail.setTaskId(task.getId());
        return detail;
    })
    .collect(Collectors.toList());

// 调用工单详情的Service完成批量新增
taskDetailService.batchInsertTaskDetails(detailsList);
```

> **提示**：通义灵码给的那段转换不是我们想要的，我们自己用 `BeanUtils.copyProperties` 写，反而更直白，也比我们写 for 循环效率高很多。

到这里八步就全部走完了。

### 工单编号：日期 + Redis 自增序列

页面原型里，工单编号是有一定业务规则的：**开头位置由年月日组成，后面四位是一个自增序列**。今天的第一个工单写 `0001`，第二个写 `0002`。

年月日比较好处理，通过日期对象转换一下就能拿到前面八位。但后面四位要做到自增——**每一天的工单编号自增序列都要求从 1 开始**。比如今天是 8 月 27 号，序列是 `0001`、`0002`、`0003`；到了第二天 28 号，它又要从 `0001` 开始。

所以数据库的自增肯定就不合适了，这时候我们可以使用 **Redis 自增器**。

#### 演练一遍 Redis 自增器

还记得这个指令吗？我们来复习一下。打开 Redis 客户端连接工具，连接本地开发环境的 Redis：内存数据库地址我这里用默认的 `127.0.0.1`，端口 `6379`，密码为 `root`——如果这三个参数你跟我的不一样，结合自身情况调整一下，点 OK 就建立连接上了。

连接成功之后，找到它的命令行，对应的关键字是 `INCR`。我们指定一下 key，比如 `task_code`，执行一下，它已经自动为 1 了。刷新一下左侧的 key 列表，目前值为一。再执行一次，变成 2；再执行一次，3、4、5——是不是就做到了一个自增的效果？

思路就出来了：**以日期为单位，每一天创建一个 key，它的自增序列就从一开始了**。第二天以后这个序列如果不需要了，就给它设置一个过期时间，让它 24 小时以后销毁即可。这样既实现了功能，也不会对内存造成过大的开销。

#### 动手实现

因为生成工单编号的代码内容比较多，我们抽取一个独立的方法，不需要参数，返回一个字符串：

```java
/**
 * 生成并获取当天的工单编号（唯一标识）
 */
private String generateTaskCode() {
    // 1.获取当前日期，格式化为年月日（注意中间不能加横杠哦）
    String dateStr = LocalDate.now().toString().replace("-", "");

    // 2.根据日期来生成Redis的key
    String key = DkConstant.TASK_CODE + dateStr;

    // 3.如果key不存在，设置初始值为1，并指定过期时间为一天
    //    （第二天序列还要从一开始，没必要在内存里占这个空间，自动销毁即可）
    if (!redisTemplate.hasKey(key)) {
        redisTemplate.opsForValue().set(key, "1", Duration.ofDays(1));
        return dateStr + "0001";
    }

    // 4.如果key存在，计数器加一，补齐四位后返回
    Long count = redisTemplate.opsForValue().increment(key);
    return dateStr + StringUtil.padLeft(count.toString(), 4, '0');
}
```

这里有三个细节值得单拎出来。

**第一，日期格式。** 我在写注释的时候写的是"格式化为年月日，注意中间不能加横杠"，通意灵码生成出来之后我们点进去看一下它的格式——格式是年月日，**没问题，但中间多了我们刚刚所说的不需要的横杠**。那怎么办呢？其实很简单，它返回值是一个字符串，我们可以通过字符串的 `replace`，把两个横杠替换为空串不就行了吗？所以后面加上 `.replace("-", "")`，这样就可以拿到纯年月日的普通字符串了。

**第二，`hasKey` 的判断。** 我们需要判断 Redis 当中有没有这个 key——如果有的话直接自增就可以了；如果没有的话，我们就该设置一个初始值并指定过期时间为一天。这里用到的模板操作对象是 `redisTemplate`，需要注入进来。`redisTemplate.hasKey(key)` 这个方法就是来判断此件是否存在，存在返回 `true`，不存在返回 `false`。注意这里我们要增加一个**逻辑非**的判断。

**第三，补零怎么补。** 这里小伙伴就纠结了：前面这个 `0001` 是我手动写的，那后面自增完了怎么去写这个 `0002` 呢？难道需要我们手动拼三个零吗？

**手动拼三个零肯定不合适啊。** 万一我原来值是 11，这里生成的是 12，你帮我补三个零，是不是就多了一位啊？所以我们要动态地去补齐。动态补齐可以使用 hutool 工具包提供的字符串工具类 `StringUtil` 里面的 `padLeft` 方法，这个方法需要我们传递三个参数：

- 第一个参数是自增序列的值，比如说是数值 2；
- 第二个参数是自增序列总体的长度，比如我们设置为四位，现在这个数值 2 肯定是不满足四位的；
- 第三个参数就是来定义它前面补齐的值，比如我们前面补齐一个零。

有了这三个参数，我们就可以拼接出 `0002`，正好满足四位。

> **提示**：`padLeft` 的第一个参数也要求是 `String` 类型，所以 `increment` 后面要加一个 `toString()`，把它转换成字符串类型的数值。

完整的就是这样：

```java
// 使用Redis的自增器 opsForValue().increment 把key扔过去，这是它自增后的结果
// 我们一共需要四位，如果不满足四位的话，帮我们补零
Long count = redisTemplate.opsForValue().increment(key);
return dateStr + StringUtil.padLeft(count.toString(), 4, '0');
```

这两步其实可以合并为一步——下次再自增就是 `0003`，再自增就是 `0004` 了。

### 事务，以及被学员揪出来的那个 bug

生成工单编号这个方法完成后，回到新增工单的方法里，把编号设置进去：

```java
// 工单编号
task.setTaskCode(generateTaskCode());
```

设置完之后就可以调用 Mapper 实现保存了。

第八步做完，这里要提醒一件很重要的事：这个方法涉及**两张表**的新增操作——工单表和工单详情表，所以这个方法我们需要**添加事务**。找到方法上方，补上事务注解 `@Transactional`。加完之后，整个新增工单的核心业务代码就搞定了。

到这里整个思路一共八步，咱们再梳理一遍：

前两步是**售货机的校验**——设备存在吗？状态和工单类型配得上吗？不通过就抛异常。

第三步校验**是否有同类型的工单**——比如说我已经创建一个投放工单分给张三去干了，你再创一个新的，是不是就重复了。

然后校验**员工是否存在**、**员工与设备是否在同一个区域**。

这些校验都通过了没问题，咱们就可以保存工单。保存工单的时候，需要通过 **Redis 自增序列**来实现工单编号的生成，生成完工单编号以后调用 Mapper 实现保存。

再来判断该工单的类型是否为补货工单——不是的话方法结束，是的话还需要保存工单详情。这里涉及到两张表新增，所以我们需要增加事务注解。

思路梳理完了，这时候有小伙伴向我提问：**在生成并获取当天工单编号时，第一个 `if` 判断当中返回的结果是没有问题的**，日期加自增序列数值 1；但**第二个返回的结果，我们只返回了自增序列 `0002`，前面是不是忘了拼一个日期字符串呢？**

说得对。这个小 bug 我们就修复了，补上 `dateStr`。好，Service 层咱们就搞定了。

### Controller 层：最后把登录人补上

前面所有的准备工作和核心业务都做完了，最后一步是参考接口文档改造工单的 Controller 方法。

回到接口文档，提交的请求路径是 `manager/task`，而这个路径对应的方法我们已经有了——工单的 Controller，往下拉就能找到新增工单的方法。它现在接收的参数是 `Task`，我们把它**改造成接收 `TaskDto`**。

```java
@PostMapping("/manager/task")
```

至此，一个接口就同时服务了运维工单（投放、维修、撤机）和运营工单（补货），而且工单编号的规则、参数防篡改的二次校验、区域的匹配性检查、工单详情与工单表的事务一致性，全部都在这一个方法里收拢了。

### 回头把新增工单的整条脉络捋一遍

测试做完，回到笔记做小结。这一段把整个新增工单的骨架完整交代一遍，其中 DTO 设计、Mapper 批量新增、补货清单的 Service 这几块是前面几集完成的，这里一并归拢。

#### 两个 DTO 与分层落点

参考接口文档，我们设计了**两个** DTO：

- `TaskDetailsDto`：接收补货清单数据；
- `TaskDto`：接收工单整体数据。如果是补货工单，它还会包含工单详情。

```text
TaskDto（工单整体）
   └── List<TaskDetailsDto>（补货清单，仅补货工单非空）
              │
              ▼
TaskServiceImpl（核心业务，八步）
              │
              ├─► TaskDetailsService ──► TaskDetailsMapper（批量新增工单详情）
              ▼
          TaskMapper ──────────────► 存工单
```

分工是这样的：`TaskDetailsMapper` 负责批量新增工单详情（SQL 交给通义灵码生成）；补货清单的 Service 层代码单独写，后面由工单 Service 调用它完成批量新增；真正的核心业务全部落在 `TaskServiceImpl` 里。

#### TaskServiceImpl 里的八步

整个业务流程一共八步：

1. **查询售货机是否存在**，不存在就抛出异常；
2. **校验售货机状态与工单类型是否相符**；
3. **判断当前设备是否有未完成的同类型工单**，避免工单重复创建；
4. **校验员工是否存在**；
5. **校验设备和员工是否在同一个区域内**；
6. **保存工单信息**；
7. **如果是补货工单，保存工单详情**；
8. **调用 service 完成新增并返回响应结果**。

第 2 步单独拎出来说，因为它是唯一一条"按工单类型分支"的规则。工单类型一共有四种：

| 工单类型 | 对设备状态的要求 |
| --- | --- |
| 投放工单 | 设备**不能**处于运行状态 |
| 维修工单 | 设备必须处于运行状态 |
| 撤机工单 | 设备必须处于运行状态 |
| 补货工单 | 设备必须处于运行状态 |

第 6 步有两个细节：一是把 DTO 转为 PO 并补充相关属性，其中工单编号是用**日期字符串 + Redis 自增序列**生成的（刚才那个 `202407270001` 就是这么来的）；二是补齐后调用 mapper 把工单保存进数据库。

第 7 步要先对补货工单集合做非空判断，不为空才往下走：把 DTO 转成 PO，补上 `taskId` 属性，转换为工单详情，然后调用工单详情的批量新增 service。

至此，新增工单的实现细节就齐了。

### 取消工单接口

#### 接口文档与抓包里的两个参数

我已经提前打开了取消工单的接口文档页面：

- 请求路径为 `/manager/task/cancel`；
- 请求方式为 `PUT`；
- 请求参数的类型为 JSON。

重点是请求体 body 当中将包含两个参数：

- `taskId`，也就是我们工单的 id；
- 取消理由，也就是我们拒绝的理由。

这两个参数在管理员点击取消时就会携带上。

这里有个小伙伴提了个好问题：我们点击确定按钮时，并没有编辑任何参数啊，那 `taskId` 和拒绝理由是从哪里来的呢？

打开 F12 抓包看一下就明白了——**前端已经帮我们写好了**，看 payload 当中这两个参数都携带了。`taskId` 是 544，即当前工单的主键；取消理由是前端写死的内容，内容是"后台工作人员取消"。

所以有时候这两个参数前端已经帮我们设置好了，我们只需要通过后端的实体类 `Task` 对象来接收即可。返回结果就是一个标准的 `AjaxResult`，有 `message` 以及 `code`。

#### Controller：注解可以整套复用

代码实现分三块。先看 `TaskController`，我们根据接口文档创建一个取消工单的方法。

```java
@PutMapping("/cancel")
public AjaxResult cancelTask(@RequestBody Task task)
{
    return toAjax(taskService.cancelTask(task));
}
```

几个可以照抄的地方：

- **请求方式**是 `PUT`，写一个 `@PutMapping`；**请求路径**的前两层类上已经有了，这边直接写 `cancel`；
- **权限注解和日志注解**直接参考"修改工单"的复制过来，属性值不需要做任何调整，可以完全复用——因为取消工单本质上也是修改工单的状态；
- 前端传的是 JSON 格式，IDEA 的提示非常智能，直接帮我们做完了补全，`@RequestBody` 敲完按 Tab 键即可；
- 方法注释写"取消工单"，把 `@params` 和 `@return` 删掉，跟若依生成的注释保持一致；
- 返回结果交给 `toAjax` 响应即可——Service 返回的是影响行数，`toAjax` 会把它包装成标准响应。

Controller 层的架子就搭完了，接下来创建 Service 方法。

#### Service：三步走，千万别传错对象

Service 里要做的事情明确是三步。

**第一步：判断工单状态是否可以取消。**

这是什么意思呢？举个例子：如果这个工单的状态已经是**已完成**了，你现在再点取消，这是不是就乱套了？已完成的工单，请问还能取消吗？或者说这个工单状态**已经取消**了，我们再次点取消，还能二次取消吗？那肯定不合适啊。

所以这一步需要对前端传递的工单 id 进行状态校验。这里有个细节：前端传递的 `Task` 对象**只有工单的 id 和取消的原因，对象当中并没有当前工单状态**，所以我们必须根据 id 先查数据库。

```java
@Override
public int cancelTask(Task task)
{
    // 1. 判断工单状态是否可以取消
    // 先根据工单id查询数据库
    Task taskDB = taskMapper.selectTaskById(task.getTaskId());

    // 判断工单状态是否为已取消
    if (Constants.TASK_CANCEL.equals(taskDB.getTaskStatus()))
    {
        throw new ServiceException("该工单已取消了，不能再次取消");
    }

    // 判断工单状态是否为已完成
    if (Constants.TASK_FINISH.equals(taskDB.getTaskStatus()))
    {
        throw new ServiceException("该工单已完成，不能取消");
    }

    // 2. 设置更新字段
    task.setTaskStatus(Constants.TASK_CANCEL);
    task.setUpdateTime(DateUtils.getNowDate());

    // 3. 调用Mapper层接口，直接完成更新工单
    return taskMapper.updateTask(task);
}
```

`equals` 比较时把常量写在前面，避免空指针；异常提示信息 IDEA 自动生成得太简单，我们手动改成"该工单已取消了，不能再次取消""该工单已完成，不能取消"这样人话。

**第二步：设置更新字段。这里是本节最容易踩的坑。**

注意这个更新字段设置的是 `task` 还是 `taskDB` 呢？**那肯定是 `task`。**

为什么呢？因为这个 `task` 对象当中，它里面存储了**取消的原因**，还有**工单的 id**。我们以工单 id 为条件，更新前端传递的实体类就可以了。因为数据库当中有动态 SQL，把 null 值排除在外了。

> **易错点**：这里千万要注意，我们更新的不是数据库的那个对象（`taskDB`），而是前端传递的那个对象（`task`）。传错了，你就不会拿到前端更新的备注说明以及"工单状态为已取消"。

要补的字段就两个：工单状态和更新时间。状态用常量 `Constants.TASK_CANCEL` 来指定；更新时间直接给 `setUpdateTime` 传入当前系统时间。

**第三步：调用 mapper 层接口更新工单。**

Mapper 层我们不需要编写，直接复用若依生成的更新工单方法即可。`updateTask` 返回影响行数，所以我们把代码直接写在 `return` 当中即可——顺便再强调一次，**别传错了，这里要传前端的 `task` 参数**。

按 `Ctrl + F9` 热部署更新一下，弹出黄色警告不用管它。回浏览器测试：运维工单点取消、点确定，工单状态已经改为了已取消。运营工单用的是同一套接口，点查看详情、点取消、点确定，状态同样改为了已取消。

至此取消工单完成。

### 查看工单补货清单接口

这个接口非常简单，简单到可以一口气写完，但有一个设计上的取舍值得说清楚。

接口文档：请求路径为 `/manager/task/details/byTaskId`，通过路径传参，请求方式为 `GET`，路径参数就是 `taskId`。以当前工单的 id 为条件查询工单详情，把符合条件的补货列表返回到前端。返回结果是标准的 `AjaxResult`，有提示信息 `message`、业务状态码 `code` 和数据的集合 `data`。

现在有个疑问：拿参数以后直接查不就行了吗？**为什么还要封装一个条件对象？**

是这样的——为了提高代码的复用性，Service 层和 Mapper 层我们不需要编写，直接复用若依生成的查询工单详情的集合方法。而这个方法它需要的条件就是 `TaskDetails`，所以我们需要把 id 封装到这个条件上，就可以简化代码的开发。

也就是说，**只编写 Controller 层**，拿到 Service 返回的结果响应到前端，后端代码就完成了。

在 `TaskDetailsController` 当前类的最下方新增一个方法：

```java
@GetMapping("/byTaskId/{taskId}")
public AjaxResult byTaskId(@PathVariable("taskId") Long taskId)
{
    // 将taskId封装到条件对象
    TaskDetails taskDetails = new TaskDetails();
    taskDetails.setTaskId(taskId);

    return success(taskDetailsService.selectTaskDetailsList(taskDetails));
}
```

几个细节：

- 类上的前两层路径已经有了，这里直接写 `byTaskId`；注意它是**通过路径传参**，所以要写占位符，路径里的值就命名为 `taskId`；
- 写完按 `Ctrl + Alt + L` 格式化一下；
- **针对于查询的请求，我们不需要记录日志，但需要增加权限注解**。权限注解写什么呢？思考一下——我们返回的结果是工单详情的列表，所以可以参考若依提供的列表查询的权限注解，复制过来即可；
- 方法注释补"查看工单补货详情"，`@params` 和 `@return` 删掉，跟若依代码保持一致；
- 第二步返回的 list 集合和第三步响应结果写到一起，通过返回的 `success` 方法把集合响应到前端。粘完代码删掉几个分号，这样代码看起来就非常简洁了。

`Ctrl + F9` 热部署，回浏览器测试：第一个补货工单点"补货清单"，货道商品补货数量清单列表就展示到前端页面了；第二个补货工单点查看详情，历史记录这些也都可以查询。

### 让 Knife4j 接管接口文档

在工单管理的开发过程当中，接口文档是不可或缺的一部分。它不仅帮助我们理解后端 API 的功能和使用方式，还便于前端开发者和测试人员进行接口测试。

这时有小伙伴问到：如果我在开发工单管理功能时，并没有现成的接口文档，或者说我还想测试后端接口是否可用，该怎么办呢？

哎，这时 Swagger 就派上用场了。这哥们呢咱们基础篇讲过，咱们来复习一下：**Swagger 是一个强大的工具，它能够根据我们编写的 Controller 代码，自动生成 API 的在线文档**。更重要的是，Swagger 提供了一个 Web 界面，允许我们在浏览器中调用和测试这些接口，无需再使用像 Postman 这样传统的工具了。

但是这个 Swagger 界面，对于我们国内开发者来说可能不太友好。为了提升用户体验，我们将引入 **Knife4j**。

Knife4j 是一个前端 UI 的增强解决方案，它对 Swagger 进行了增强，提供了更加美观和易阅读的接口文档。大家来看一下这个界面，是不是看起来清爽很多了？非常像 YApi 等相关的在线接口工具。

#### 复习 TestController：注解是怎么生效的

接下来我们就要思考一下：如何像 `TestController` 一样，给我们自己写的这些业务代码也来增加接口文档的阅读与测试？

先复习 `TestController` 的代码编写。找到 dk-admin 的 admin 的 Controller 包下的 tools，双击打开。之所以能够在 Knife4j 显示的话，得益于两个东西：

- 当前类上面增加了一个 `@Api` 的注解，在这里面提示了"用户信息管理"；
- 每个方法上面都有一个 `@ApiOperation`。

那么项目就可以在启动时通过 Swagger 解析当前类上面的注解，把每个方法渲染成一个接口文档，识别方法的参数以及方法的返回值，在接口文档中进行展示。

以"获取用户详细信息"为例，回到浏览器点开看一下：有请求地址、请求参数、响应的状态码，还有响应的结果——用户手机、用户密码、用户 id、用户名称，是不是返回结果也写得非常详细？

那是因为我们在返回的用户实体类上面，也增加了 `@ApiModel` 以及 `@ApiModelProperty`，让它识别当前实体内每一个属性，然后给它增加中文注释的说明，前端界面呢就可以进行展示了，还有它对应的类型。比我们自己根据代码来设计接口文档，是不是就方便很多了。

这里呢还提供了**调试功能**：在当前界面我们可以模拟浏览器，直接向后台发送请求来拿到返回结果，来代替传统的 Postman 等调试工具。

#### 响应结果识别不出来：把 AjaxResult 换成 R

改完刷新，点开"查看工单补货详情"，参数说明、路径参数、是否必须都没毛病。但往下拉会发现，**响应结果没有识别**，是空的。

我们当前 Controller 的方法当中明明是有返回值的，而这个返回值就是工单详情的列表集合。那为什么 Knife4j 界面没有显示呢？

```text
AjaxResult  extends  HashMap
        │
        ├─ code     ─┐
        ├─ msg      ─┼─► HashMap 的 key（静态）
        └─ data     ─┘
                          value 是 Object 类型（动态，按业务场景拼接）
                                      │
                     Swagger / Knife4j 不兼容 HashMap
                                      │
                                      ▼
                        无法识别 AjaxResult，页面显示空内容
```

因为当前方法返回结果是 `AjaxResult`，而这个 `AjaxResult` **继承了 HashMap**。它返回的值 code、msg、data 就是 HashMap 的 key，根据对应的业务场景去给它拼接对应的值，而这个值呢是 Object 类型的。但是 Swagger 和 Knife4j 它是不兼容 HashMap 的，所以就导致它无法识别 `AjaxResult`，返回结果在页面显示了空内容。

这个时候怎么办呢？**其实我们可以抄作业**，来看看若依是怎么解决的。

`TestController` 当中是不是有获取用户列表的方法？点击一下，看看它有没有响应参数——有的！这个响应参数也有 code、data、msg，还有我们返回的数据。

那这一点呢 Knife4j 就解决了。它怎么解决的呢？回到 IDEA 找到 `TestController`，按 `Ctrl + E` 打开历史记录，往上拉：它方法的返回结果**不再是一个 `AjaxResult` 了，而是一个 `R` 后面指定一个返回结果的泛型**。

```java
public class R<T>
{
    private int code;
    private String msg;
    private T data;

    public static <T> R<T> ok(T data)   // 表示返回成功
    public static <T> R<T> fail(String msg)  // 表示返回失败
}
```

这个 `R` 呢是什么呢？咱们点开看一下，它就是一个**普通的实体类**，里面定义了 code、msg 和 data，**它是没有继承 HashMap 的**，所以 Swagger 和 Knife4j 是可以识别它返回的参数的。定义的三个属性名称与 `AjaxResult` 是一致的，所以我们这里可以采用它。

想让自己编写的业务代码也能够被 Swagger 和 Knife4j 识别，这里就**不能再返回 `AjaxResult` 了，而要改为 `R`**，同时要指定泛型——返回结果是一个 List 集合，而 List 集合里面封装的是 `TaskDetails`：

```java
@GetMapping("/byTaskId/{taskId}")
public R<List<TaskDetails>> byTaskId(@PathVariable("taskId") Long taskId)
{
    TaskDetails taskDetails = new TaskDetails();
    taskDetails.setTaskId(taskId);
    return R.ok(taskDetailsService.selectTaskDetailsList(taskDetails));
}
```

> **易错点**：改造完毕之后，**这里就不能使用 `BaseController` 当中的 `success` 方法了**，因为这个 `success` 它的返回结果是 `AjaxResult`，就不通用了。我们需要使用 `R` 提供的一个静态方法 `ok`，把结果返回过去就可以了。别忘了 `Alt + Enter` 导包。

热部署，浏览器刷新，再次点开"查看工单补货详情"，往下拉：响应参数识别了——`code`、`data`，而 `data` 当中就是我们返回的工单详情列表，显示的是当前工单详情的实体类以及对应的类型。

#### 实体类注释与 BaseEntity 的盲区

但缺少了属性说明的中文注释。所以我们也需要给工单详情的实体类增加 Swagger 的相关注解。

这里咱们也可以交给通义灵码来完成：复制一下，不用复制全类，**只需要把实体的属性复制完**，`Ctrl + C` 回到通义灵码的对话界面，咱把实体类粘过去，点击生成。好的，实体类相关的 18 个注解我们就生成完毕了。

复制的时候有个讲究：直接从实体属性往上拉到当前类的相关注解，**咱们只复制这一部分就可以了，get/set 方法我们不需要**。回到 IDEA 替换一下，导包成功。

看一下它做了什么：

- 给当前实体类增加了一个注解叫 `@ApiModel`，来描述当前实体类的信息——"工单详情对象"；
- 给当前实体类的每个属性上面增加了 `@ApiModelProperty`，用来描述当前字段的意义，比如说 `taskDetailId` 表示工单详情 id，`taskId` 表示工单 id。

比我们自己写起来要高效很多。

热部署再刷新，回到"查看工单补货详情"，现在来看返回的结果当中，是不是都有中文的解释说了？

**但有个别的 `createBy`、`createTime`、`params`、`remark` 这几个没有说明**，是什么原因呢？（这里又是一个弹幕题，答案非常好）

是因为我们实体类呢都继承了一个父类，叫 `BaseEntity`，而这个 BaseEntity 当中这些属性返回的结果，咱们没有增加 Swagger 的说明。

> **结论**：你想要在前端也要显示这些中文说明的话，请为每个实体属性上面增加 `@ApiModelProperty` 注解，写上相应的注释说明即可。

```text
│  请求头     Authorization = <前端 cookie 里复制>   │
└──────────────────────────────────────────────────┘
```

注意向后台发送请求的话，**必须要携带令牌**，令牌就是我们身份的登录信息。如果没有携带令牌的话，它会返回 401 的权限不足的状态码。

登录成功的信息呢，我们可以在前端的 application 当中通过 cookie 来获取。我们来看 `Admin-Token`，这是我们的身份令牌，`Ctrl + A` 全选，`Ctrl + C` 复制，将原有的替换一下。好的，令牌和参数我们就搞定了。

向后台发送请求（调试工具挡住了，给它关闭）——下面来看一下，请求已经成功，状态码 200，下面是他返回的结果：`code` 200、`msg` 操作成功，而这个 `data` 就是数组，返回了当前工单的补货清单。这是第一个清单，这是第二个清单，功能我们测试成功了。

#### 测试地址别写成 localhost

打开 App 之后，右下角有个"设置 URL"，里面默认填着一个测试地址，我们需要把它改为**本地环境地址**。而本地环境就是我们稍后要搭建的帝可得 App 后端，它的端口是 **9007**。

> **易错点**：本地环境发送请求并不是 HTTPS，所以要把 S 删掉，写成 `http://`。

那这里能直接写 `localhost` 吗？那肯定不行。为什么呢？因为 `localhost` 就相当于**当前安卓模拟器的本地环境**，而安卓模拟器的本地环境会不会运行这个 Java 的后端代码？那肯定不会对吧。

所以呢，我们需要通过安卓模拟器去访问我们的 **Windows 系统环境**。而 MuMu 模拟器访问 Windows 有一个固定的 IP，这个固定 IP 为 **10.0.2.2**，那么他就可以找到 Windows 的环境了，后面我们加上端口号冒号 9007。

```text
  帝可得 App（运行在安卓模拟器里）
        |
        |   HTTP 请求
        v
  10.0.2.2  ==  你这台 Windows 电脑
        |
        v
  运营管理 App 后端（Spring Boot，端口 9007）
        |
        +------> MySQL（dico）
        |
        +------> Redis（验证码、缓存）
```

读图：模拟器里的 App 用 `localhost` 是找不到后端的，必须借 `10.0.2.2` 这个宿主机别名跨到 Windows 上，再打到 9007 端口；协议只能是 `http`，没有 S。

所以兄弟们一定要改成这个测试地址：`http://10.0.2.2:9007`。HTTP，注意没有 S；10.0.2.2 是我们 Windows 的环境；9007 是我们 Java 后端运行的端口。这边修改完毕以后点击保存，客户端这边就搞定了。

### 运营管理 App 后端源码结构

前面把流程和测试都走了一遍，下面回过头来给运营管理的 Java 后端源码做一个简单介绍，方便各位老铁课下自学和阅读源码。

#### 技术栈与三大模块

技术栈上，我们项目采用了主流的技术组合：**Spring Boot** 作为后端框架，**MyBatis-Plus** 作为数据访问层的工具，以及**阿里云短信服务**用于发送短信通知。

> **提示**：应大家要求，我已经把数据访问层的基础栈从若依的 MyBatis 改为了 MyBatis-Plus。只要你把 MyBatis 玩转了，再去看 MyBatis-Plus，就可以提高开发效率了。

模块划分上，本项目呢主要分为三个核心模块：**员工管理、工单管理、工单详情**。

| 模块 | 承载的功能 |
| --- | --- |
| 员工管理 | 发送短信验证码、App 登录员工、查询员工信息 |
| 工单管理 | 查询工单、接收工单、拒绝或取消工单、完成工单 |

其中查询员工信息，说白了就是我们登录 App 端以后，可以显示员工的基本信息资料。下面分别看看这三个模块在源码里长什么样。

#### 员工管理：发短信、登录、查资料

员工管理实现了三个关键功能。

**发送短信**，用于短信验证码的通知。员工输完手机号以后，点击获取验证码的按钮，它就会向后台发送请求来执行此方法——Controller 通过路径参数拿到手机号，然后调用 Service 实现发送短信的功能。

Service 的实现里有个细节我得强调一下：生成五位随机验证码的那行代码（`RandomUtil`）我给注释掉了，由于是开发环境，所以我把验证码暂时显示为 `12345` 了。

> **注意**：在产品上线之前，请务必把上面的随机验证码代码打开，把下面写死 `12345` 的代码注释掉。

生成完毕以后呢，在这里面我们会调用阿里云短信的工具类，实现发送短信的功能。而这个短信工具类的模板呢，我已经给小伙伴们抽取好了：就在这里我们拿到配置文件读取的这些参数，调用工具类实现短信的发送功能。

那么在配置文件当中，大家要使用的话来我们找到 `application-dev.yml`，在这里面呢我们指定了短信的配置信息，有 Key 和 Secret 密钥对，还有短信签名以及短信的模板编码。大家呢可以自行注册阿里云短信，输入自己的密钥对，就可以使用阿里云短信测试呢，给自己手机号做一个功能测试。

短信发送成功以后呢，我们需要往 **Redis** 当中来存储刚刚生成的验证码，而且设置有效时间呢为 **5 分钟**，也就是 300 秒。将来我们在 5 分钟内做登录的话，就可以从 Redis 当中来获取正确的验证码，跟 App 端输入的这个做对比。

**App 登录员工**，通过登录验证来访问我们的系统资源。我们这边呢会设计出一个 **DTO** 来接收参数，然后调用我们的 Service。在 Service 当中第一步我们先来比对验证码：首先会从 Redis 当中获取我们刚刚存入的有效验证码，跟前端录入的做一个对比，如果不一致的话，我们会抛出一个业务异常，给前端提示"验证码错误"，这是第一大步。

如果验证码正确的话，我们再比对手机号是否正确，如果手机号有问题的话，这边我们提示手机号非法，就表示登录成功了。所以第三步呢，我们就返回一个登录的 `LoginVO` 结果，设置登录的一些员工参数，比如说角色编码、员工姓名、员工 id、员工所负责的区域，还有提示的登录成功信息。下面就是制作 **JWT token** 的令牌，还要判断员工是维修员还是运营员，那么在前端呢就可以进行区分了。

**查询员工的信息**。我们登录 App 端以后，前端呢会根据当前登录好的员工 id 去查询员工的基本信息，这里调用的是员工 Service，其中的方法叫 `getById`，用的是 MyBatis-Plus 通用 Service 的功能，所以 Service 层这一步呢我们就省略了。然后拿到员工对象以后呢，我们需要封装一个返回结果，基本信息都在这里面进行封装了，需要把实体类转换成前端所需要的 **VO** 对象即可。

#### 工单管理：四个动作各自的校验链

工单管理主要包含四个功能，Controller 里从上往下正好就是这四个方法。

**查询工单**，我们支持各种条件的检索查询。注意这个搜索工单对应的是 App 端的**三个界面**——首页当中有待办工单状态，还有进行中的工单，以及全部工单，这里有一个时间范围，也支持条件搜索，都会执行这个方法。所以该方法接收参数非常多：支持分页查询，根据设备编号、用户 id、工单编号、工单状态、是否为运维工单，还有日期范围，接受这些参数然后调用 Service。

在 Service 当中，首先我们封装了 MyBatis-Plus 的分页查询对象，再通过 `LambdaQueryWrapper` 来构建出动态 SQL，支持我们刚刚介绍的各种条件查询：设备编号、用户 id、工单编码、工单状态、是否为补货工单；工单查询还要根据时间范围进行查询，根据时间呢实现**倒序**查询，最终执行分页，再获取该工单的类型和工单状态的文字说明，返回最终的分页结果即可。也就是说这一个方法就支持了各种条件查询。

**接收工单**，这个不难理解，允许员工接收指派给他们的工单信息。前端呢会传递一个工单的 id,但是我们需要获取当前登录人的 id，然后以这两个条件去调用 Service 完成接收。Service 的实现分四步：

1. 首先我们先根据工单 id 判断工单是否存在，如果不存在的话，咱们抛出异常；
2. 接下来我们再判断一下工单的状态是否为**刚创建**，也就是待处理的——如果工单状态已经为进行中了、或已完成、已取消，请问它还能再接受吗？肯定是不行的，所以这是工单状态的校验；
3. 再判断下当前登录人**有权接收此工单**，也就是说登录人必须跟工单的分配人保持一致，如果不一致的话，咱们也需要抛出异常信息；
4. 以上三个条件都满足的话，咱们第四步呢就是修改工单的状态，把它改为**进行中**，然后调用 MyBatis-Plus 的通用 Service 实现数据库的更新操作，mapper 层就可以省略不写了。

**拒绝或取消工单**。当员工现在比较忙，他可以选择拒绝或取消工单。那在这里面呢，我们可以拿到前端的工单 id，以及拒绝或取消的理由，再获取当前登录人的 id，以这三个参数呢调用 Service 完成取消业务。

Service 里首先第一步我们还是需要进行工单的判断，如果不存在，那么肯定不能拒绝或取消啊。那接下来我们还需要判断一下工单的状态，如果不是待处理或进行中的话，它是无法取消的，这是工单状态的校验。再来看一下当前工单的分配人是否跟登录人是一致的，如果不是一致的话，那么他就没有权限去取消或拒绝此工单。如果前三个校验通过的话，咱们就可以把工单状态改为**已取消**，并且把拒绝或取消的理由更新到数据库当中，返回数据库的操作结果即可。

**完成工单**。我们拿到前端所提供的完成工单的 id 以及当前登录人的 id，然后调用 Service 实现完成。老规矩，先对工单进行判断是否存在，还对工单的状态进行判断：只有工单属于**进行中**，咱们才能完成工单；如果是刚创建的、已取消或已完成，它就不能再次完成了。最后判断登录人是否有权完成工单——三个基本的校验。

如果这三步校验通过以后呢，咱们就可以更新工单的状态了。工单状态更新成功以后呢，**我们还需要更新设备的状态**：

- 如果工单类型是**投放工单**，那么我们就把设备状态呢改为**运营状态**；
- 那么如果工单类型呢为**撤机工单**，这个时候我们就把设备状态呢改为**撤机**的；
- 还有如果是**补货工单**的话，那么我们就需要查询工单的明细，也就是我们的补货清单，把明细中的数据呢更新到数据库的库存当中。

> **结论**：所以我们刚刚在测试补货工单时，一旦点击完成，数据库的库存是不是也得到更新了——就是上面这个第三个分支干的活。

四个动作的校验链放在一起看，其实是高度同构的，区别只在"允许的当前状态"和"落到什么终态"：

| 动作 | 工单必须存在 | 允许的当前状态 | 权限校验 | 最终结果 |
| --- | --- | --- | --- | --- |
| 接收 | 是 | 待处理（刚创建） | 登录人 = 工单分配人 | 改为进行中 |
| 拒绝 / 取消 | 是 | 待处理 或 进行中 | 登录人 = 工单分配人 | 改为已取消，并记录理由 |
| 完成 | 是 | 进行中 | 登录人有权完成 | 改为已完成 + 更新设备状态 / 货道库存 |

#### 工单详情：一个工单 id 查出一张补货清单

最后是工单详情模块，在里面我们实现了一个核心功能，也就是**根据工单 id 查询补货详情列表**，这里我们将允许工作人员查看自己负责工单的具体补货信息。

Controller 里我们可以拿到工单 id，然后调用 Service，我们通过 MyBatis-Plus 实现条件封装、执行查询，直接将结果返回了——只需要编写 Service 层，是不是非常的简单。

当前项目呢就实现了这三个核心模块的业务功能，用于服务运营管理的 App 端。这部分呢并不难，而技术栈从若依的 MyBatis 改造为大家所要求的 MyBatis-Plus，这样的话通过本项目，你不仅可以学习 MyBatis 基础应用的知识，也可以学习到 MyBatis-Plus 来简化 SQL 的编写。

#### 支付二维码背后的长途跋涉

接下来就是用户呢选择自己心仪的商品，比如说选择冰红茶。我们点击以后呢，系统就会弹出支付方式，提供用户选择，有微信支付，还有支付宝支付。这里呢我们选择微信支付，选择之后呢，将生成二维码供用户呢扫码支付。

由于第三方支付平台没有针对于个人用户开放，所以我并没有实现具体的支付代码。不过没关系，接下来我将为大家串联一下支付功能的实现思路。

我们能够在屏幕上看到支付二维码，其实是经历了**长途跋涉**，具体流程如下：

```text
  用户点击商品
      |
      v
  H5 屏幕端向后端发起购买请求
      |
      v
  订单服务：根据前端传入的商品 id 和购买数量创建订单
      |
      v
  调用第三方支付平台，生成一个预交易的链接
      |
      v
  把预交易链接返回到前端的 H5 界面
      |
      v
  前端用 qrcode 技术生成二维码，屏幕上显示出来
      |
      v
  用户拿出手机扫码，在第三方支付平台完成支付
      |   （用户与第三方平台直接交互，我们的系统不参与）
      v
  第三方平台向订单服务发送支付回调
      |
      v
  订单状态：待支付  --->  已支付
      |
      v
  系统通过 MQTT 向智能售货机设备下发出货指令
      |
      v
  设备从相应的货道当中调出商品，完成发货
      |
      v
  系统自动更新库存，对应商品库存数量减一
```

读图：二维码只是这条链路的第一站，真正的闭环在最后一环——设备出货之后库存要减一，否则屏幕上那个"已售罄"就永远不会出现。

#### 统一支付框架与支付回调

一般在项目开发当中，涉及到第三方支付平台的代码编写是非常繁琐的，而且我们项目呢还同时支持微信支付和支付宝支付，这就更加痛苦了。为了简化开发，我给兄弟们推荐一款开源框架叫 **Jeepay**，他可以做到优雅地完成支付。

Jeepay 是一个支付框架，底层封装了支付宝和微信支付的功能，使用起来非常简单，我们可以用最小的学习成本在项目当中完成集成——也就是说我们可以做到在几分钟之内，在项目当中集成这个框架，完成支付功能。

它有几个特点，第一个是为支付宝和微信提供了**统一的调用接口**，两个第三方平台的调用呢他帮我们统一好了；第二个是支持本地支付、小程序、H5、App 多种支付方式，提供了统一入口。

> **结论**：它一直在强调的就是"统一"——我们只需要学会一套代码，就可以完成微信、支付宝以及对应各种类型的支付方式了。

具体的使用步骤带兄弟们看一下：

**导入相关的依赖坐标**，第一个是微信支付的，第二个是支付宝支付的。

**在配置文件当中增加配置**。微信支付的相关配置里面有我们的商户号、AppId、密钥、签名等等，还有支付宝的 AppId 以及我们的回调地址。注意这个**回调地址必须是外网能够访问的**——也就是说我们支付成功以后呢，由第三方平台访问这个回调地址，通知我们系统："这哥们儿已经付款了，你可以更新订单状态、进行发货了。"

**在订单模块里面注入一个对象** `JeepayPayment`，而这个对象提供的 API 非常简单。第一个参数是 `setTotalFee`，也就是我们支付的金额，注意它的**单位是分**——传递这个分呢，我们就不用担心精度丢失的问题了；第二个参数呢是我们的订单号；第三参数是商品的名称。这三个参数设置完毕以后呢，就可以调用它的方法发送下单的请求，而返回的结果是一个 response。那这个 response 有什么呢？兄弟们来看一下重点：我们来拿它的 `codeUrl`，也就是二维码的支付链接。咱们拿到这个支付链接以后呢，就可以响应到 H5 的屏幕端，通过 qrcode 来生成二维码，用户呢就可以进行扫码支付了。

回调这边也很简单。当用户付款成功之后，在这里面我们只需要定义一个对象叫 `CallbackService`，去实现一个接口，然后就会让我们重写这几个方法：有支付成功的回调、支付失败的回调，还有退款成功、退款失败的回调信息。是不是第三方平台的底层很多细节，该框架就帮我们简化完毕了。

如果你这边能够拿到第三方支付平台的密钥对，可以在配置文件当中去配置这些信息的话，就可以尝试编写一下我们刚刚提到的订单支付的代码，生成预交易的链接，然后呢在屏幕端就可以让用户呢扫码完成支付了。

#### MQTT：订单服务怎么喊动设备出货

还有一点我需要强调一下：我们的订单服务要跟真实的设备去通信的话，刚才我提到了，会用到一个物联网的通信技术，叫做 **MQTT**，通过此技术的相关技术栈，就可以向智能售货机的设备发送一条指令。那设备呢在收到指令以后，就会从相应的货道当中调出商品，并完成发货的操作。发货完成以后呢，系统将会自动更新库存信息，相应的商品库存呢数量就会减一。

而实现这个技术的话，有一个国内的开源产品叫 **EMQX**，感兴趣的同学呢可以对它进行学习。我们安装这个环境之后，就可以做到设备之间通过互联网连接起来，实现信息的交换和通信，我们可以简称为**万物互联**。

支付出货流程我们先简单介绍到这里。通过这次业务功能的测试，我们不仅加深了对于支付流程的理解，还了解到了可以使用 MQTT 等物联网技术，来实现设备之间的通信和控制。接下来，动手实操，完成设备屏幕端的功能测试吧。

### 设备屏幕端后端：一次查询背后的分层

前面我们已经带着大家把设备屏幕端的功能跑通了：模拟器里点开售货机，商品列表出来了，支付出货的流程也走了一遍。但"能跑"和"知道它为什么这么跑"是两件事。这一节我们把目光转向设备屏幕的 Java 后端源码——不是为了炫技，而是因为你以后要改这套东西。

先看技术栈，没什么意外的：后端框架是 Spring Boot，负责快速开发；数据访问层用的是 MyBatis-Plus，把数据库操作简化掉。真正值得看的是它目前只实现了一个模块——设备管理模块。

这个模块的核心功能，用一句话说清楚：**根据设备编号，获取这台售货机的商品列表**。

> **定义**：设备编号在代码里叫 `innerCode`，是每台售货机唯一的身份标识。屏幕端 H5 上你看到的那些商品、每一个商品的售价，都是围绕这一个编号查出来的。

回到 IDEA，找到设备的 Controller 打开：

- 方法接收设备编号；
- 查询出 `SkuVO`——也就是包装之后的商品列表。

具体的实现细节，顺着 Controller 往下点：

```text
设备屏幕端 H5
     │  传 innerCode
     ▼
DeviceController          ← 接收请求
     │
     ▼
IDeviceService            ← 接口
     │
     ▼
DeviceServiceImpl         ← 实现
     ├── ① baseMapper.findSkuByInnerCode(innerCode)   查商品
     ├── ② 按 innerCode 查售货机，取 policy 策略折扣
     └── ③ 遍历商品，套用折扣算真实价，打"打折标记"
     │
     ▼
返回 List<SkuVO> → Controller 响应 → H5 渲染
```

Service 里的第一步是调 `baseMapper`。

这里插一句，很多人第一次看到这个名字会懵：`baseMapper` 其实就是 `SkuMapper`。MyBatis-Plus 在 Service 层注入 Mapper 时，习惯用一个统一叫 `baseMapper` 的变量来指代当前实体的 Mapper，所以它不是某个特殊对象，就是这张表自己的 Mapper。

### 用库存量给商品排序：一张虚拟表在中间

`findSkuByInnerCode` 是我们自己定义的方法——不是 MyBatis-Plus 自动生成的，必须自己写 SQL。按住 Ctrl 点进去看。

这个方法做的事是：**根据设备编号，查询货道的商品信息，以及商品的库存总量**。涉及多表查询。

第一张表查的是商品表，紧接着关联查询了货道表。但这里有个关键——**货道表是作为一张"虚拟表"参与查询的**。

这张虚拟表干了什么？往右拉一下 SQL：

1. 根据设备编号，查询当前设备的所有货道信息；
2. 判断 `sku_id > 0`。

> **易错点**：`sku_id > 0` 这个条件是什么意思？它表示**货道已经关联了商品**。如果没有关联商品，`sku_id` 的默认值就是 0。所以"设备编号 + sku_id > 0"这两个条件合起来，就能拿到"指定设备关联了商品的货道信息"。

3. 然后根据 `sku_id` 进行分组——也就是**按商品分组**，拿到商品的 ID 和这个商品的库存容量；
4. 把这个分组结果**当作一张虚拟表**，跟商品表做内连接查询。

内连接之后，返回的字段就齐了：商品的 ID、名称、图片、价格、商品类型 ID、单位（比如净含量），还有商品的库存容量。

最后，按照商品的库存量排序——**库存量大的商品，排名靠前**。

讲师在这里画了张图帮我们理解。我把它整理成这样：

```text
某台设备的货道现状
┌──────────┬────────────┬────────┐
│  货道号  │  关联商品  │ 剩余量 │
├──────────┼────────────┼────────┤
│   1-1    │  冰红茶    │    5   │
│   2-1    │  冰红茶    │    7   │
└──────────┴────────────┴────────┘
              │  按 sku_id 分组，库存累加
              ▼
      ┌───────────┬────────────┐
      │  商品     │  库存总量  │
      ├───────────┼────────────┤
      │  冰红茶   │  5 + 7 =12 │
      └───────────┴────────────┘
              │  作为虚拟表，与商品表内连接
              ▼
      ┌───────────┬────────┬─────────────┐
      │  商品     │  价格  │  库存总量   │
      ├───────────┼────────┼─────────────┤
      │  冰红茶   │  ...   │     12      │
      └───────────┴────────┴─────────────┘
              │  按库存量降序
              ▼
   屏幕端：同一件商品只显示一张图，库存多的排前面
```

所以整个逻辑就是：我们先按设备编号统计出所有关联了商品的货道，把**同一个商品在多个货道里的库存累加起来**，再拿这个结果去和商品表做内连接，补全商品名称、图片、价格这些信息。

这样做的业务道理很直白：**屏幕端同一件商品只显示一张图片，然后把库存量最高的商品排在最前面，优先让消费者去买库存最多的那个。**

### 折扣是怎么算进价格里的

回到 Service。拿到商品列表之后，下一步是根据设备编号去查这台智能售货机。

查售货机是为了看一件事：**这台机器有没有关联策略**。代码里就叫 `policy`。

流程是这样的：

1. 先给折扣率一个初始值——**100%，表示无折扣，就是不打折**；
2. 然后判断策略是否存在。如果存在，就把折扣覆盖过来。比如上一小节我们设置的九折，那么 `discount` 就变成 90；
3. 拿到 90 之后，**遍历所有商品**，目的是算出每件商品的**真实价格**。

真实价格的算法很直白：

```text
真实价格 = 商品原价 × discount ÷ 100
```

乘以 90，再除以 100，就得到真实价格。

> **提示**：`÷ 100` 这一步别省。折扣率在系统里是用整数百分数存的（90 表示九折），要还原成乘数必须除回 100。少这一步，价格会放大 100 倍。

算出真实价格之后还要做一个判断：

- 如果**真实价格 < 原价**，就给这个 `SkuVO` **设置打折标记**；
- 否则，设置**不打折**。

设置完这个标记有什么用？售货机的屏幕端就能据此**做 CSS 样式**——打折的商品加上特殊标记（比如划线价、折扣标签），没打折的原样输出。

最后返回 `SkuVO` 的 list 集合，Controller 响应到前端，H5 就把商品列表展示出来了。

### 原理篇开篇：为什么要回头读源码

实战篇收尾之后，课程转向"拔高原理篇"。

讲师给了一个很好的理由：技术会用只是"知其然"，**理解背后的原理同样重要**——它"不仅能够帮助我们更好地来运用技术，还能在遇到问题时提供更多的解决思路"。这就是那句"知其然，更要知其所以然"。

原理篇要学的内容，可以当成一张路线图来看：

| 模块 | 讲解的功能 | 背后要碰的技术 | 要解决的问题 |
| :--- | :--- | :--- | :--- |
| 代码生成器 | 代码生成器的配置与增强 | Velocity 模板引擎、Lombok、Swagger | 消除配置繁琐、让生成的代码更优雅 |
| RBAC 权限控制 | 登录到获取权限的完整流程 | Spring Security | 前后端如何协同做权限控制 |
| 操作日志 | `@Log` 注解记录增删改 | 自定义注解 + AOP 切面 + 异步任务管理器 | 三者结合的日志方案可以复用到类似场景 |
| 定时任务 | 动态管理定时任务 | Quartz | 单机/集群部署、修改代码白名单 |
| 数据权限 | 按公司/部门/个人展示数据 | 自定义注解 + AOP + SQL 拼接 | 细粒度数据权限控制 |

每一条都不是空话，都有具体的痛点驱动：

- **代码生成器**：我们已经用它把单表 CRUD 的便利拉满了，但配置上很烦——每张表生成前都要去掉 `tb` 前缀、设置作者为 IT 黑马、指定包路径、模块名设为 manager。这些问题虽小，但影响开发流畅度。另外生成的实体类里那些 getter/setter/toString 密密麻麻的，生成的 Controller 里还得手动加 Swagger 注解才能看在线接口文档——这个实践过程"咱们也感受到了是非常繁琐的"。**学 Velocity 模板引擎，就能集成 Lombok 和 Swagger 技术，实现代码生成的增强。**
- **RBAC**：不同用户根据角色和权限看到的是不同的系统菜单。功能在基础篇演示过了，但底层会涉及 **Spring Security**，要分析从用户登录到获取权限的整个流程，还要探讨**如何根据用户角色生成动态路由**。
- **异步任务管理器**：分析登录流程时会牵扯到它。"这哥们儿呢可以做到在应用程序不阻塞主线程的情况下来执行任务"，意味着用户操作能得到更快响应——它底层是**线程池 + 异步工厂**。
- **操作日志**：`@Log` 注解会自动捕获用户执行的增删改操作。它底层结合了**自定义注解、AOP 切面技术，以及刚才提到的异步任务管理器**，三个技术结合为日志记录提供了强大支持——"将来遇到类似的场景，你也可以用这种方案来解决"。
- **定时任务**：涉及 **Quartz**，可以指定单机或集群方式部署，还能掌握修改代码的白名单，做到定时任务部署在自己的业务模块下。
- **数据权限**：先演示功能——用户登录后，系统根据其所属公司、部门或个人展示相应数据；再深入源码。实现起来其实比较简单：**通过自定义注解标识哪些方法或类需要权限控制，底层用 AOP + SQL 拼接**，来展示本公司、本部门或个人的相应数据。

### 代码生成器的两张核心表

代码生成器要提高开发效率，主要分两部分：

1. **设计**——把业务表的结构导入到系统；导入成功后，开发者可以预览、编辑、删除和同步业务表结构；
2. **生成**——选中特定表后点击生成按钮，单个生成或批量生成，系统根据表结构生成相应的前后端代码并提供下载。

要想彻底搞清楚这两部分，首先得弄清楚一件事：**若依框架是如何存储导入后的业务表结构的？**

若依提供了**两张核心表**：

| 表名 | 存什么 | 对应哪个配置页面 |
| :--- | :--- | :--- |
| `gen_table` | 业务表的**基本信息** | 「基本信息」和「生成信息」两个页面 |
| `gen_table_column` | 业务表的**字段信息** | 「字段信息」页面 |

> **定义**：这两张表的关系是**一对多**——一张业务表可以有多个字段的信息，所以在字段表当中有一个外键叫 `table_id`，去指向业务表的主键。

#### 基本信息表里都存了什么

`gen_table` 之所以字段不少，是因为它对应着两个视图页面。为了帮我们区分，讲师把「基本信息」页面用高亮标了出来——一共五个字段：

| 页面上的东西 | 对应字段 |
| :--- | :--- |
| 表名称 | `table_name` |
| 表的描述 | `table_comment` |
| 实体类名称 | `class_name` |
| 作者名 | `function_author` |
| 备注说明 | `remark` |

比如针对订单表的名称、描述、实体名称、作者以及备注说明，我们更新以后都会存储到 `gen_table` 的这五个字段中。**剩余字段都在「生成信息」页面里。**

「生成信息」这边值得留意的字段有：

| 配置项 | 字段 | 说明 |
| :--- | :--- | :--- |

#### 后端：那条查询语句其实在读 MySQL 自带的表

前端找到之后轮到后端。复制请求路径，打开 IDEA，代码在 generator 模块的 `GenController` 里。

> **提示**：这里有个很好用的小技巧，**如果小伙伴们对于后端的代码结构并不是特别熟悉，其实我们可以用一个简单的技巧来快速定位**——双击 Shift，把路径粘过来，直接就能定位到 `GenController` 的这个方法。

这个方法接收前端请求，**而且这个请求是有参数的**：支持表名称，也可以根据表的描述作为条件来传递。然后开启分页，调用 Service 查询，把结果封装成分页对象响应到前端。

Service 也比较简单，**直接调用 Mapper 层来执行查询**。打开 XML 映射文件，这里通过 SQL 完成了查询。

但需要注意的是——

> **易错点**：他查询的表叫 `information_schema.tables`，后面还跟了一些条件。"这跟我们项目当中的业务表完全不一样呢"。

**`information_schema.tables` 是 MySQL 数据库自带的表**，它默认会查询当前数据库软件**所有的表信息**的。也就是说，你的 MySQL 软件有十个数据库、每个库里有五张表，它就会一口气查询出 50 张表来展示。

但这么多表并不是我们想要的，所以后面加了一些过滤条件，一个比一个收紧：

1. **`table_schema = select database()`**——限定在当前的数据库当中，只查询帝可得当前项目的业务数据库；
2. **排除 `QRTZ` 开头的表**——"看起来有点熟悉啊，它是不是定时任务相关的表？请问它属于我们业务相关的部分吗？不属于，所以咱们不需要导入，这个要排除"；
3. **排除代码生成器自带的 `gen_` 开头的两张表**——`gen_table` 和 `gen_table_column`，这张表我们也需要排除；
4. **排除已经在 `gen_table` 当中存在的表名**——打开 `gen_table` 看一下，目前项目里已经导入了 16 张业务表并生成了前后端代码，从点位表到订单表都完成了。"当我们在查询数据库时，这些业务表还需要重复导入吗？那肯定不需要"。

通过这些条件过滤，剩下的就都是待导入的业务表了。

怎么用？选中这一行代码，右击 → 通义灵码 → 第一个是「解释代码」。

### 导入表结构：从前端点击到数据库落库

接下来是第二段：管理员在对话框中**选中需要导入的业务表**（比如选择了策略表），点击确定，前端向后端发送请求，保存业务表的基本信息和它的字段信息。

前端代码在 `importTable` 组件里，后端处理仍在 `GenController`。

打开 `importTable` 组件，找到确定按钮——第 44 行，点击后触发 `@click`，调用 `handleImportTable` 方法。

这个方法做了三件事：

**第一步，把表格里选中的表名数组转成一个字符串。**

原文是这样的：

```text
点选两个表 → tables 数组 = [表A, 表B]
           → join(',')  →  "表A,表B"
```

因为前端接收的是数组，但向后台传递参数时传的是**一个字符串**，所以需要把两个表名以逗号分隔拼接成字符串。

> **提示**：紧跟着有个判断——**如果你没有选中表就直接点这个按钮，转换后的字符串就是个空串**，所以前端会提示"请选择需要导入的表"并终止方法执行，下面的代码不再执行。如果确实选了表，才会调用 API JS 当中的 `importTable` 方法向后端发送请求。

**第二步，请求发出去了。** 在 `api/tool/gen.js` 里找到 `importTable`：路径 `/tool/gen/importTable`，方式 POST，请求参数就是 `data`。

浏览器里验证一下：选中两张表，清空历史记录，点确定——**请求地址携带了参数，而这个参数就是一个字符串，多个值之间以逗号分隔**；当后端返回状态码 200 时，对话框隐藏，同时重新查询业务列表，把最新数据展示到页面。

后端保存成功后要给前端返回一个操作提示信息：操作成功就隐藏对话框并提示，然后前端重新查询最新的数据列表。

**第三步，看后端。** 还是那个 `Shift` 定位的技巧，把路径粘过来就找到方法了。这个方法的主要逻辑就是**导入表结构、实现最终的数据库保存**。

拿到请求参数后注意一个细节：

```text
前端传进来的是：  "表A,表B"     ← 字符串
后端第一行做的事： 转成数组      ← ["表A", "表B"]
```

之后根据表名查询业务表的基本信息。找到 Service、Service 实现、Mapper 以及它的 XML——"各位，查询 `information_schema.tables`，那么它的条件呢是当前数据库、排除定时任务和 `gen_` 开头的表，就可以根据指定的表名来查询当前项目数据库下面的业务表信息了"。

查询到信息后封装到 `GenTable` 实体类里，然后进入最重要的一行代码：

> **提示**：我们把集合传过去，**同时还传递了当前登录人的用户名**——因为后面生成的代码里，`create_by` 这些审计字段要有值。

调用 `importGenTable` 方法实现表结构的保存。因为传进来的是一个集合，所以要对集合做遍历，每张表的导入业务逻辑是：

#### 初始化表信息

先获取当前表的名称，然后初始化表信息。这个工具类里讲师已经提前用通义灵码把注释写好了——"这是为了节约时间"，课下阅读自己代码时也可以交给通义灵码来学习。

初始化的字段：

- 根据表名生成类名；
- 通过配置类读取的包路径设置包名；
- 读取配置文件来设置生成代码的作者；
- 当前操作人就是系统的登录用户（通过 Ctrl 传过来的）；
- 还可以获取模块名，根据表名设置业务名，根据表注释设置功能名。

那个配置文件专门读取了 generator 模块的配置，里面定义了**默认生成的作者、生成的包路径（如 `com.dkd.system`）、是否去除表的前缀**。默认值是 `false`——"如果你把它改为 true 的话，可以在最后一行指定去除前缀的名称，比如说 `tb` 下划线，**注意多个前缀之间以逗号分隔**"。

> **结论**："这部分代码改造呢我们稍后来进行调整。"

初始化完毕回到 Service，调用 `gen_table` 的 Mapper 实现新增，返回**影响行数**。一旦插入成功，返回的影响行数大于 0，就表示业务表的基本信息插入成功了。

#### 查询列信息并初始化字段

接下来保存该表的**列信息（字段信息）**。先根据表名查询数据库表的所有列信息——打开 Mapper 的 XML，里面有判断、列注释、是否自增、列的类型等。

这张表同样是 MySQL 自带的 `information_schema.columns`，它默认查询**所有库当中所有表的列**的信息，所以要加条件过滤：**查询当前库指定表名的列信息，并根据排序序号做升序**。

> **易错点**：这个 SQL 拿到数据库客户端执行前需要改造一个小细节。**由于在 XML 当中双引号是一个特殊字符，所以要通过 CDATA 区域给它转义**；但在数据库当中双引号是不需要转义的，所以要把 CDATA 的标记去掉——左侧去掉，右侧也去掉。另外这边要传入一个表名，比如大家比较熟悉的实战订单表，就写 `tb_order`。

粘贴执行一下，订单表的所有列名、是否必填项、是否主键排序、列的说明、是否自增、列的类型，全都查询到了，一共 **25 个字段**。

结果封装到 `GenTableColumn` 实体类里，然后对集合做遍历——25 个字段就遍历 25 次，分别插入到业务字段信息表。

插入之前会执行**最重要的一步**：初始化列字段的信息，同时让它去关联表。

这个工具类里做的事：

- 获取该字段的数据库类型、列名（也就是字段名）；
- 关联当前表的 id，以及创建者（系统登录人）；
- 根据数据库列名设置 Java 字段名——**注意这里面有一个驼峰式转换的操作**，数据库两个单词之间是以下划线分隔的，通过工具类处理以后就转换成驼峰式命名；
- 设置该列的**默认类型**：Java 类型先默认设置为字符串类型 `String`，查询类型默认是 `EQ`（等值查询）——回到前端找到订单表点编辑按钮，会发现查询方式都为等号。

然后判断数据库类型，设置 Java 类型和对应的前端 HTML 控件类型：

| 数据库类型 | Java 类型 | 前端控件 |
| :--- | :--- | :--- |
| 字符串（`char`、`varchar`、`tinytext`、`text`、`mediumtext`、`longtext`） | `String` | 默认文本框；**长度超过 500 则改为文本域** |
| 时间类型 | `Date` | 日期控件 |
| 浮点型 | `BigDecimal` | |
| 整型 | `Integer` | |
| 长整型 | `Long` | |

> **易错点**：字符串这一行有个细节——**如果字符串的长度超过 500，我们在 HTML 的控件类型当中就给它显示为文本域**。它对应的是前端页面当中的显示类型：默认的字符串这边显示是文本框，长度超过 500 就会改为文本域。

接着是几个勾选项的处理：

- **插入字段**：默认所有字段都需要插入，所以前端页面「插入」这一列默认都是勾选上的；
- **编辑字段**：如果字段名是 `id`、`create_by`、`create_time` 以及删除标记，就不需要编辑，其余所有字段都要勾选上。回到前端确认一下——`id` 是不是没勾选，剩下的是不是都勾上了；
- **列表展示字段**：通常情况下 `id`、创建人、创建时间、删除标记、更新人和更新时间在列表当中是不需要展示的，这是默认值；
- **查询条件字段**：也有一些过滤条件，这些是不需要在前端页面作为查询条件勾选的。

最后设置查询类型和前端控件类型，规则全靠**字段命名**：

| 字段名包含 | 处理结果 |
| :--- | :--- |
| `name` | 查询类型改为模糊查询 `LIKE`（其他字段默认等值） |
| `status` | 前端控件改为单选框 `radio` |
| `type` 或性别 | 改为 `select` 下拉框 |
| `image` | 改为图片上传空间 |
| `file` | 改为文件上传空间 |
| `content` | 改为富文本控件 |

这样设置好以后，新增或修改时就会有图片上传空间、文件上传空间、富文本编辑空间、下拉框等等——**主要得益于我们命名的规范性**。

#### 两个必须注意的点

初始化完毕之后调用 `gen_table_column` 的 Mapper 新增字段列信息，插入完进入下一层循环插入第二个列、第三个列，以此类推。订单表所有列名全部插入完毕后才结束执行。

所以整个插入操作涉及**两张表**：第一张是业务表的基本信息，第二张是业务表的字段信息。

**只不过字段信息是在 for 循环内做插入的，所以性能不太友好。** 那么在项目当中怎么解决？——"咱把这个代码呢改为一个批量新增，是不是更为合适啊？"

**还有一点：当前方法需要增加一个事务，保证我们的插入操作要么都成功，要么都失败。**

回到数据库验证一下：`gen_table` 里已经有订单表的信息，还有刚刚演示的策略表、出货流水表；`gen_table_column` 里能看到出货流水对应的字段、统计表对应的字段，数据最多的 16 号对应订单表。

插入成功以后，前端页面就能展示当前表的基本信息、字段信息还有生成信息了。

### 把这一段的收获串起来

回顾一下这一块跨越实战篇与原理篇的内容：

- **设备屏幕端**只实现了一个模块，但它把 Controller → Service → Mapper 的分层、以及"虚拟表分组统计 + 折扣计算"这两手典型手法都演示了一遍。真正的业务价值在于：同一商品合并库存、库存多的排前面、折扣落到真实价格并打标记，让消费者优先买到库存充足的商品。
- **订单管理**被留作实战练习，但"生成基础代码 → 判断是否引入数据字典 → 分析每个字段 → 改造页面，日期范围查询可参考代码生成页"的路径是通用的。
- **代码生成器**的底座就是 `gen_table` 和 `gen_table_column` 这两张一对多的表。理解它们之后，导入表结构这条链路就通了：前端 `proxy.$refs.importRef.show()` 弹框 → `listDbTable` 拉列表 → 后端查 `information_schema.tables` 并逐层过滤 → 选中后 `handleImportTable` 把数组 join 成字符串提交 → 后端转回数组、初始化表信息与列信息、插两张表、靠事务兜底。
- 最后那个性能问题很值得记：**循环里逐条 insert 是不可取的，要改批量插入**。这是读框架源码时最常见的一类收获——不是看它多巧妙，而是看它哪里还能更好，然后在自己的项目里改掉。
- 顺带记住那两个通用习惯：**不认识的 SQL 交给通义灵码「解释代码」和「生成代码注释」**；**后端工程结构不熟就用 Shift 双击粘贴路径快速定位**。两个都是能长期复用的效率技巧。
