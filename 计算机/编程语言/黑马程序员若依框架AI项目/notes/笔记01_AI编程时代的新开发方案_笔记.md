# AI 编程时代的新开发方案

## AI 提效的边界

### AI 在开发四阶段的作用

* **AI 编程辅助工具**

    * > **定义**：借助大模型辅助编程的开发工具，通义灵码是其中一类。
    * 覆盖环节不止代码自动生成，调试、测试等多个开发环节都能发挥关键作用。
    * 带来的变化是编码速度和质量的提升，开发者因此更能专注创新和解决复杂问题。

* **一个系统从零到上线的四步**

    * > **定义**：以 CRM 客户关系管理系统的开发流程为例，划分出的四个阶段。
    * 环境搭建阶段 AI 不太能：技术选型、框架整合没有对应功能，得自己干。
    * 设计阶段 AI 可以大显身手：根据产品原型设计库表、设计接口。
    * 编码阶段是 AI 的强项：编写前后端代码，把设计变成实际功能。
    * 测试与部署阶段同样能发挥作用：生成测试用例、编写部署脚本。
    * 结论：除了第一步环境搭建得自己干，其他阶段 AI 都能提效。
    * 由此留下的缺口：第一步的技术选型和环境搭建需要更简单的实现方式。

### 环境搭建缺口的补位

* **若依（RuoYi）**

    * > **定义**：一款基于 Java EE 技术的企业级快速开发平台，让 Java 开发者通过少量代码就能快速搭建和开发出各种系统的工具。
    * 定位：正好补上 AI 覆盖不到的环境搭建与技术选型环节。
    * 通用性：无论公司处于哪个行业、开发哪种类型的后台管理系统，都能用它快速开发，缩短项目交付周期。
    * 分工结论：通用功能和基础代码交给若依；基础代码满足不了的业务需求，通过 AI 辅助编程来解决编码环节。

## 若依的三大核心能力

### 快速构建与内置通用模块

* **快速构建：站在巨人的肩膀上**

    * 传统开发中技术选型和环境搭建既繁琐又耗时。
    * 若依整合了当前的主流技术栈，提供一套完整的脚手架工具。
    * 官方 Git 仓库里的项目本身已基于若依脚手架搭建，包含框架整合的各个模块。
    * 把仓库克隆到本地，项目初始化就完成，环境搭建无需从零开始。

* **内置通用模块**

    * 覆盖后台管理系统的常见需求：系统登录、权限控制、日志记录等。
    * 代码克隆下来直接运行就能访问，不需要自己写登录功能。
    * 登录后看到的列表和按钮来自自带的权限控制功能，再加上日志记录等。
    * 集成在一起简化了开发流程，让开发者专注业务逻辑的实现。

### 代码生成器

* **代码生成器（Code Generator）**

    * > **定义**：只要定义好数据表的结构，就能自动生成前后端代码的工具。
    * 解决的问题：实际开发中经常要写大量重复代码，比如增删改查。
    * 操作形态：把业务表结构交给代码生成工具管理，页面左边是后端代码、右边是前端代码，复制下来导入开发环境即可。
    * 边界：是前后端代码一起生成，不是只生成一半。
    * 收益：编码工作量大幅减少，同时代码的一致性和可维护性提高。

## AI 加若依的完整流水线

### 五步流水线

```text
① 确定系统原型
        │
        │ 用若依搭环境：克隆后端 → 导入自带 SQL → 启动后端
        │                克隆前端 → 启动前端 → 浏览器访问管理界面
        ▼
② 查看页面原型，明确业务需求
        │
        │ AI 辅助设计数据库表结构 + 生成测试数据
        │ 把 AI 生成的 SQL 导入开发数据库
        ▼
③ 若依根据表结构生成前后端代码
        │
        │ 下载到本地，分别导入前后端开发环境
        ▼
④ 管理界面上出现单表增删改查页面
        │
        │ 生成代码往往还得改：用 AI 补业务细节
        ▼
⑤ 功能落地，反复测试
```

* **阶段一：用若依把项目环境搭起来**

    * 克隆若依后端代码并初始化项目，把自带的 SQL 文件导入数据库，启动后端工程。
    * 接着克隆若依前端代码，启动前端工程，通过浏览器访问若依管理界面。

* **阶段二与阶段三：AI 参与设计，再交给若依生成代码**

    * 查看页面原型，明确业务需求后，用 AI 辅助设计数据库表结构并生成测试数据。
    * 把 AI 生成的 SQL 语句导入开发数据库中。
    * 简单配置一下，若依基于表结构生成前后端代码，大幅减少手动编码工作量。

### AI 收拾生成代码的尾巴

* **页面美观性改造**

    * 典型问题：课程介绍展示内容过长，影响页面的美观性。
    * 处理方式：把这个需求告诉 AI 工具，它提供解决方案，选取合适的方案、复制代码，回浏览器测试美化后的内容展示。

* **业务规则改造**

    * 典型问题：新增课程时根据业务需求，需要在后端生成一个八位的唯一课程编码。
    * 处理方式：把课程编码需求告诉 AI 工具，它给出工具类方案。
    * 落地三步：把工具类复制到项目中，打开业务代码，在新增课程的方法中使用这个工具类设置课程编码，回浏览器录入课程信息测试新增功能。
    * 结论：通用功能、基础代码交给若依；业务细节交给 AI，这就是 AI 加若依的创新项目开发新方案。

## 若依的版本选择

### 五个版本对照

| 版本 | 后端 | 前端 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 若依 | Spring Boot | Bootstrap | 前后端混合开发，前后端代码在同一个项目里，是早期 Web 开发的常见模式，目前已经被市场淘汰，了解即可 |
| RuoYi-Vue | Spring Boot | Vue | 前后端分离，前后端可以并行开发和独立部署，目前广泛采用的主流模式；对单体项目非常合适，能满足大多数开发需求 |
| RuoYi-Cloud | Spring Cloud + 阿里巴巴微服务架构 | Vue | 前后端分离的微服务版本，确保系统的伸缩性和稳定性；中大型项目单体架构可能遇到性能瓶颈或扩展性问题时就选它 |
| RuoYi-App | 不提供后端代码 | uni-app + Vue | 一次编写多端运行，同一套代码适配 iOS、安卓以及各种小程序和 H5 页面，降低跨平台维护的复杂性 |
| RuoYi-Other | 第三方贡献 | 第三方选择 | 由第三方开发者贡献的生态系统版本，为用户提供更多样的选择 |

* **版本选择结论**

    * 想做单体项目选 RuoYi-Vue；想做分布式微服务项目选 RuoYi-Cloud。
    * 熟练掌握单体架构后再学微服务架构会发现很多通用模块和核心概念一致，学习会顺畅很多。
    * RuoYi-App 并不提供后端代码，可以结合真实业务需求适配单体 RuoYi-Vue 后端，也可以适配微服务 RuoYi-Cloud 后端。

* **RuoYi-Vue3 的由来**

    * 若依官方提供的前后端版本原先使用的是 Vue 2。
    * 官方已经在 2023 年停止了对 Vue 2 的维护和更新，新项目建议直接从 Vue 3 开始。
    * 基于这个需求，第三方版本 RuoYi-Vue3 把前端升级为 Vue 3，并适配了兼容的 Element Plus 框架和 Vite 构建工具。
    * 前端用哪套由 RuoYi-Other 这一类第三方版本直接决定。

## 后端项目搭建

### 克隆脚手架并初始化

* **操作路径**

    * 打开 IDEA，点击右上角的 `Get from VCS`。
    * 把仓库地址复制到 URL 当中，并指定开发路径，点击克隆完成项目初始化。

* **过程现象**

    * 第一次克隆速度可能慢，周期会很长，因为涉及源代码下载和第三方 jar 包依赖下载。
    * 初始化的判断标准：父工程的名称和子模块的名称高亮且加粗。
    * 如果迟迟没有高亮变黑，打开 Maven 菜单先执行一次 clean 清理，再执行 package 打包。
    * 打包过程会重新下载第三方依赖 jar 包，最后点一次刷新，左侧就会完成初始化，基本可以构建成功。

### 导入表结构并改连接配置

* **导入 30 张表**

    * 若依通用功能模块涉及的表结构和数据脚本放在项目的 `SQL` 目录里，包含两个 SQL 脚本。
    * 先在数据库客户端工具里创建若依的数据库，前后端分离的 Vue 版本库名是 `ry-vue`。
    * 分别执行这两个 SQL 脚本完成表的导入，两个脚本的执行先后顺序无所谓。
    * 执行完毕一定要检查是不是 30 张表，表的具体内容在功能详解篇再讲。

* **改 Druid 连接配置**

    * 项目连接数据库的配置文件在 `ruoyi-admin` 子模块的 `src/main/resources` 里，是 Druid 连接池配置文件。
    * 双击打开，在里面指定连接地址、用户名和密码。
    * 本地数据库的话，地址和库名 `ry-vue` 不用改，把用户名和密码换成自己的环境即可。
    * > **易错点**：MySQL 导入完毕之后千万别忘了修改 Druid 配置文件，否则项目启动时连不上数据库。

### 启动 Redis 与后端工程

* **启动 Redis**

    * 找到 Redis 的安装目录，通过终端把它启动起来。
    * 看到欢迎窗口以及端口 6379，就说明 Redis 已经启动好。
    * 如果开发环境的 Redis 有密码，项目启动连接时也需要找到一个配置文件，双击打开定位到 Redis 相关配置，往下拉大概在第 69 行的位置指定密码。
    * Redis 不在本地时，同样可以改成其他的 IP 地址或端口。
    * > **易错点**：Redis 设置了密码就还要改 Spring 相关的 Redis 配置，指定密码信息。

* **启动 RuoYiApplication**

    * 启动类在 `ruoyi-admin` 子模块中，名称叫 `RuoYiApplication`。
    * 找到启动方法，选择 debug 模式点击运行，后端项目就跑起来了。
    * 方法内部用 `System.out.println` 打印欢迎提示信息，控制台里会同步看到该界面。
    * 控制台确实打印出"若依启动成功"，后台端口默认是 8080。

## 前端项目搭建

### 三步搭建

* **克隆并初始化**

    * 若依官方提供的那个前端版本是 Vue 2，后期不再使用，改为使用第三方的 RuoYi-Vue3 脚手架。
    * 执行 Git 克隆命令完成项目下载，然后通过 VS Code 打开项目进行初始化。
    * 若依的前端环境默认放在 GitHub 中，国内下载可能很慢甚至失败，可以改用 Gitee 地址克隆。
    * 项目打开后左侧已经有工程结构，但还不能执行，因为缺少第三方依赖。

* **安装第三方依赖**

    ```bash
    npm install
    ```

    * 没有配置过全局的国内镜像源时下载速度会非常慢，需要手动加上资料里提供的国内镜像源地址，直接复制粘贴。
    * 安装完毕后左侧会多出一个 `node_modules` 目录，专门存放第三方依赖包。

* **运行前端项目**

    ```bash
    npm run dev
    ```

    * 运行成功后浏览器会自动打开并访问若依后台管理系统的登录页面，第一次启动速度可能慢。
    * 页面里已经自动填充了用户名和密码，输入验证码即可完成登录，这是若依自带的登录功能，不需要自己写。
    * 除此之外若依还提供系统管理、系统监控、系统工具等通用功能。

## 代码生成器入门案例

### 案例需求与表结构

* **需求**

    * 利用若依的代码生成器，生成课程管理的前后端代码。
    * 根据页面原型确定表结构设计和相关的公共接口有几个。

* **五个功能接口**

    * 课程的条件搜索查询。
    * 添加课程时录入课程基本信息，把它保存到数据库当中。
    * 每个课程当中都有一个编辑按钮，点击编辑根据 id 回显课程的基本信息。
    * 录入完毕以后，再把它更新到数据库。
    * 完成课程 id 的删除。

* **课程管理表字段**

    * 课程 id、课程编码、课程学科、课程名称、课程价格、适用人群、课程介绍，以及创建时间和更新时间。
    * 表结构设计是基于页面原型来做的，一旦设计好交给代码生成器，它就可以自动生成五个功能接口完成增删改查。

### 操作步骤与基本信息

* **三步操作**

    * 第一步：把表结构语句导入数据库，SQL 文件在数据库客户端里右击执行 SQL 脚本，执行完检查课程表已经出现。
    * 第二步：登录若依后台系统，代码生成配置在系统工具菜单下，打开代码生成页面，点导入把课程表交给代码生成器管理。
    * 第三步：点下载拿到压缩包，解压后包含 Java 后端代码、Vue 前端代码和动态菜单三部分，分别导入项目即可使用。

* **基本信息四项**

    * 表名称、表描述：由数据库自动获得。
    * 实体类名称：基于 MyBatis 的 ORM 思想，默认跟表名一致；一般把 `tb_` 前缀干掉，只保留"课程"的实体名。
    * 作者：可以根据实际情况改成我们自己的名称或公司的名称。
    * 备注：并不是必填项，可以省略。
    * 这一步只关注两点：实体类名称确定一下，作者是谁。

### 字段信息：决定页面效果的那一页

* **列的构成**

    | 列 | 是什么 | 怎么对待 |
    | :--- | :--- | :--- |
    | 序号 | 排序用 | 不用管 |
    | 字段列名 | 读取数据库每一个字段名，以及字段的描述信息 | 描述信息将决定最终页面展示效果 |
    | 物理类型 | 与数据库一一对应 | 一般走默认 |
    | 实体类型（java 类型） | 生成实体类对应的 java 类型 | 一般走默认 |
    | java 属性 | 生成实体类的属性名 | 一般跟字段名一一对应 |
    | 一堆复选框 | 新增、编辑、列表、查询、必填、显示类型、字典类型 | 最重要的一列，决定页面最终效果 |

* **字段描述与类型的对应关系**

    * 字段列名显示"课程 id"，页面生成完以后这边显示的也是"课程 id"；不想包含"课程"可以把前缀去掉只保留 id。
    * 物理类型跟数据库一一对应，生成实体类用的是 java 类型：`bigint` 和 `int` 对应的都是 `Long`，时间戳对应 `Date`。
    * 不想用 `Long` 也可以修改，一般情况下走默认即可。
    * java 属性是实体类的属性名，一般跟字段名一一对应；数据库是下划线分隔的，java 中是驼峰式命名，剩下的保持一致。

* **复选框逐项规则**

    * 新增：主键 id 是自增的，不需要勾选；课程编码在入门案例里需要手动输入，还有课程学科、课程名称、课程价格、适用人群、课程介绍这些都是前端需要录入的，全部勾上；创建时间和更新时间让系统自动填充，不用勾。
    * 编辑：指修改内容，一般跟新增保持一致，但也要通过页面原型确认一下。
    * 列表：决定页面展示时哪些字段显示、哪些隐藏；id 需要展示就勾上；在代码生成器中 id 勾不勾都会默认自动生成。
    * 查询：决定哪些字段作为条件进行页面搜索；页面最终效果是四个搜索条件——课程编码、课程学科、课程名称和适用人群，价格和课程介绍不需要。
    * 查询方式：课程编码和课程学科用等值查询，课程名称一般改成模糊匹配；点下拉框还可以改成大于等于、小于、between 等，结合业务需求调整。
    * 必填：区分新增或修改时哪些字段是选填、哪些是必填，根据页面原型勾选，课程管理里这些都是必填项所以全部勾上。
    * 显示类型：默认是文本框，后期可以改成下拉框、日期组件、复选框、单选框等；入门案例统一使用文本框。
    * 字典类型：在功能详解篇重点讲解，这一步先跳过。

* **易错点**

    * 字段列名和 java 属性要一一对应。
    * 物理类型和 java 类型要一一对应。
    * 字段描述要和页面原型的展示效果对应。
    * 那一堆复选框一定要根据页面原型确认之后再勾选，因为它将决定页面当中新增、修改、查询具体展示的字段。

## 立可得项目

### 项目定位与物联网

* **立可得**

    * > **定义**：基于若依框架打造的一个企业级后台管理系统，聚焦新零售行业特别是智能售货机领域。
    * 目标是把编码技能与行业知识相结合，在实战篇深化对若依编码的理解和应用。
    * 它是基于物联网概念下的智能售货机运营管理系统。

* **物联网（IOT）**

    * > **定义**：将各种物品通过互联网连接起来，实现信息的交换和通信。
    * 类比：像一个超大的社交网络，只不过网络里的成员不是人类，而是冰箱、洗衣机、汽车等各种物品。
    * 关键能力：让物品能够感知周围的环境，并且能够根据情况做出反应。
    * 举例：装上智能家居系统后，下班回家路上家里的空调就能提前开启、自动调整到喜欢的温度。
    * 应用场景：智能家居、共享充电桩、智能售货机等。

### 智能售货机的四个特点

* **状态可感知**

    * 物联网技术就像给售货机装上了顺风耳和千里眼。
    * 无论售货机放在哪个角落，管理人员都能通过电脑或手机实时了解它的一举一动。
    * 哪商品快要卖光、哪商品需要及时补货，管理人员都能第一时间知道。

* **智能分析与推荐**

    * 与 AI 技术相结合，售货机能分析出顾客的喜好，推荐出让顾客心动的商品。
    * 起的是贴心小助手的作用，总能帮顾客找到想要的东西，从而提高销量。

* **人员设备绑定管理**

    * 每个售货机都有自己的专属"保镖"，指的就是工作人员。
    * 售货机一旦有问题，这些"保镖"就能立刻出现迅速解决，让售货机始终保持最佳运行状态。

* **线上线下相融合**

    * 顾客可以在线上通过小程序浏览商品，然后直接在售货机购买。
    * 也可以在售货机上看到喜欢的商品之后直接在线上下单。
    * 这种模式让购物变得更加灵活和便捷。

### 四个专业名词

* **区域**

    * 公司为了管理起来更加得心应手，把运营范围切分成一块一块的逻辑区域。
    * 划分是基于业务需求而定的，可能与地理上的行政区域有所区别；像北京东城区、西城区、朝阳区这样的行政范围太大，反而不太好管理。
    * 可以根据人流量进行逻辑区域划分，保证资源分配更加合理、管理更高效，比如把北五环的奥体中心划为一个逻辑区域，里面可以包含多个点位。

* **点位**

    * 指的是智能售货机具体存放的位置。
    * 选择点位时会考虑人流量、目标顾客群体、可见度以及便利性等因素。
    * 确定标准是最大化售货机的使用效率和顾客的购买体验。

* **售货机与货道**

    * 售货机像自动小卖铺，顾客看中什么直接在屏幕上一点，机器就把东西送到面前。
    * 货道像超市一格一格的货架，每一层能放好几种商品，层层叠放就能放更多商品，顾客的选择也更多。

```text
一个区域（逻辑区域，如"北京北五环奥体中心"）
  └─ 包含 ─▶ 多个点位（售货机具体存放位置，如"国家奥体中心C区南门"）
               └─ 存放 ─▶ 多个售货机设备（如：饮料机）
                            └─ 包含 ─▶ 多个货道（超市货架上的一格）
                                         └─ 存放 ─▶ 一类商品
```

### 五端五角色

| :--- | :--- | :--- |

    * 北五环属于逻辑区域，据此创建"北京北五环奥体中心"，可以额外增加一个备注。

* **合作商**

    * 合作商也有一个管理界面，可以提前准备多个合作商。
    * 若某个合作商在奥体中心有店铺和营业点，就据此确定合作商。

* **点位管理**

    * 新增点位时填点位名称（如"国家奥体中心C区南门"）、所在区域、商圈类型、合作商。
    * 具体的点位地址也可以通过地图获取，比如"北京市朝阳区奥体内环路附近"。
    * > **提示**：也可以在这个界面增加百度地图搜索功能；本次重点是练习若依所以没有添加，感兴趣的同学可以补上百度地图的接口调用功能。

* **人员关联**

    * 在人员列表里添加工作人员，可录入员工头像（找到员工图像、点击打开、完成文件上传），并设置员工状态为启用。
    * 每个工作人员要指定角色和负责的区域，区域就是刚创建的逻辑区域。

### 设备投放与工单状态流转

* **设备管理**

    * 新增售货机属于设备管理，可以选择设备的型号。
    * 型号由设备类型管理决定，里面包含饮料机、综合机、零食机和果蔬机。
    * 每一种设备类型不同，它的货道种类也是有所区别的。
    * 设备刚创建好时状态是"未投放"。

* **运维工单（投放）**

    * 在工单管理的运维工单里新建，需要录入一个设备号，设备号从刚新增完的设备那里复制过来。
    * 工单类型第一个就是投放工单，运维人员选择设备所属区域的工作人员，备注可写"辛苦了"。
    * 工单创建完成后是一个待办的状态。
    * 运维人员登录 APP 查看工单，点击接收，然后去厂商拉取设备，找到指定点位进行投放安装。
    * 投放安装成功后，在"进行中"的工单里点"完成工单"。
    * 状态结果：后台工单状态变为已完成，设备管理里设备由"未投放"变为"运营中"。

* **教学环境说明**

    * 可以用手机模拟器安装工作人员 APP，输入手机号完成登录获取验证码。
    * 由于是教学环境，验证码已经提前写死为 `12345`。

### 货道商品与打折策略

* **商品管理**

    * 商品类型有饮料、零食、食品、玩具、化妆品等等，可以提前准备对应的测试数据。
    * 设备进入运营状态后就可以给货道关联商品，新设备的货道默认没有关联商品。
    * 逐个货道点添加即可指定商品，**多个货道可以添加同一款商品**。

* **策略（Strategy）**

    * 市场竞争压力大时，可以通过打折吸引更多人通过售货机购买商品。
    * 策略管理里准备了九折、八折等相关的优惠信息。
    * 给新建的售货机增加一条九折优惠策略并确定，将来用户通过这个设备购买的商品就是打了九折。

### 运营工单与消费者下单

* **运营工单（补货）**

    * 在工单管理的运营工单里新增，录入设备号，工单类型选择补货。
    * 补货的数量就是刚才指定货道的商品数量；默认的货道当前数量都是零，每个货道的最大容量是十，所以补满数量也是十件，这边默认自动补全。
    * 选择运营人员并填写备注后工单创建完成。
    * 运营人员登录 APP 看到工单的补货详情和备注信息，点击接收后完成补货，在"进行中"里完成工单。
    * 完成工单以后数据库也会同步更新该货道的商品数量。

* **屏幕端模拟与下单闭环**

    * 由于是教学环境没有真实的售货机设备，可以有一套前端页面来模拟售货机的屏幕端。
    * 输入设备号就可以查询数据库，展示该设备的货道商品信息。
    * 用户点击想要的饮料，可以选择各种支付方式，手机扫码完成支付。
    * 设备出货，数据库的库存减一，完成整个业务的闭环。

```text
后台新增设备 ──▶ 设备状态：未投放
                     │
                     ├─ 运维工单（投放）──▶ APP 接单 ──▶ 到点位安装 ──▶ 完成工单
                     │                                                      │
                     │                                            工单：已完成
                     │                                            设备：运营中
                     ▼
             货道关联商品 + 打折策略（如九折）
                     │
                     └─ 运营工单（补货）──▶ APP 接单 ──▶ 到点位补货 ──▶ 完成工单
                                                                        │
                                                            货道库存：补满至 10
                                                                        ▼
                                            消费者下单 ──▶ 扫码支付 ──▶ 出货 ──▶ 库存 -1
```

### 功能模块与九张表

* **后台管理端的功能范围**

    * 所有业务功能和数据库表设计都参考页面原型来完成，页面原型提供的是一个在线地址。
    * 登录功能若依框架已经提供了，直接使用就可以。
    * 需要自行完成的有工单管理、点位管理、设备管理、人员管理、商品管理、订单管理、策略管理。
    * 实现路径一致：先基于若依框架生成每一个功能的基础代码，再结合页面原型和实际需求完成具体业务的升级改造。

* **九张表的关系**

    ```text
    区域表   1 ── N  点位表      一个区域下可以有多个点位
    点位表   1 ── N  售货机表     一个点位下可以设置多个售货机
    售货机表 1 ── N  货道表      一个售货机可以设置多个货道来存放商品
    货道表   N ── 1  商品表      多个货道可以放置同一款商品（商品表 1 ── N 货道表）
    商品类型表 1 ── N 商品表     一个类型下可以拥有多款商品
    设备类型表 1 ── N 售货机表    一个类型下可以拥有多款售货机
    合作商表 1 ── N  点位表      一个合作商可以拥有多个点位
    区域表   1 ── N  人员表      一个区域内可以有多个运维或运营工作人员
    ```

* **关系的理解要点**

    * 区域、点位、售货机、货道之间层层一对多。
    * 多个货道可以放置同一款商品，所以商品和货道也是一对多。
    * 商品类型下可以有多款商品，比如"饮料"下面有可口可乐、芬达、雪碧、绿茶。
    * 设备类型下可以有多款售货机，比如饮料类型售货机、食品盲盒类型售货机。
    * > **易错点**：合作商和区域并没有直接关系，因为合作商拥有的多个点位可以分布在不同区域；区域和合作商是通过点位来建立关联的。
    * 一个区域内可以有多个运维或运营工作人员，负责整个区域的设备维修和商品补货。

## AI 与 AIGC

### 概念链

* **人工智能（AI）**

    * > **定义**：通过计算机系统模拟人类思维和行为的一种技术。
    * 实现手段：通过机器学习、深度学习等算法，使计算机具备对数据分析理解、推理和决策的能力。
    * 结果：计算机能够执行许多通常需要人类智能才能完成的任务。
    * 大白话理解：把 AI 当做一个人来看待。
    * 举例：华为智能驾驶通过 AI 模拟人类的行为实现自动驾驶，解放双手。

* **AIGC**

    * > **定义**：AI 领域的一个应用分支，专注于利用 AI 技术自动生成内容。
    * 能力：根据给定的指令或数据生成文本、代码、图片、音视频等等。
    * 水平：已经发展到可以创造出几乎与人类创作无异的艺术作品。

* **AI 大模型**

    * > **定义**：经过大量数据训练、具备复杂计算能力的人工智能模型，其中就包括 AIGC 生成内容。
    * 现状：各领域的大模型专注各自方向，推出了各种产品。

### AI 大模型与产品

| 方向 | 产品 | 背景与特点 |
| :--- | :--- | :--- |
| 文本 | ChatGPT | 由 OpenAI 公司开发，基于 GPT-4 大模型，擅长对话和撰写文章，目前版本是第四代，让人们以自然语言的方式与机器交流 |
| 代码 | 通义灵码 | 阿里巴巴公司基于 Qwen-Max 大模型推出的产品，帮助编写代码，显著提高编程效率 |
| 图片 | Midjourney | 根据文本描述生成精美图片，利用扩散模型和 CLIP 技术（预训练图文表征技术），目前版本已更新到第六版 |
| 音频、视频 | 各类专用模型 | 专门生成音频和视频的 AI 模型，在各自领域发挥着重要作用 |

* **国内通用大模型产品**

    * 文心一言：百度推出，基于文心 4.0 大模型，文本理解方面表现出色，能精准捕获和解析语言的细微差别。
    * 讯飞星火：科大讯飞公司开发，基于星火 3.5 大模型，在语音识别和语言处理方面具有显著优势。
    * 通义千问：阿里巴巴公司推出，基于 Qwen-Max 大模型，能够智能处理各种查询和问题，提供及时准确的反馈。
    * KIMI：月之暗面公司推出的 Moonshot 大模型产品，在处理长文本方面能力尤为突出。

* **AGI**

    * > **定义**：人工智能通用智能，也就是常说的人工通用智能。
    * 形象：像一个多才多艺的助手，从简单日常事务处理到复杂专业问题都能游刃有余。
    * 区别于专用 AI：专用 AI 只擅长做某一件事，AGI 的特点是通用性，能跨越不同的领域和任务提供帮助。
    * 编程价值：生成代码、检查错误、优化程序，还能提供编程的建议和解决方案。
    * 本项目的选型：使用阿里巴巴推出的通义千问加通义灵码来实现 AI 辅助编程。

## 提示词工程

### 从"你是谁"说起

* **提示词（prompt）**

    * > **定义**：我们向 AI 提出的问题，很多人习惯直接叫它的英文名 prompt。
    * 例：第一次使用 AI 时问 AI"你是谁"，这个问题便是 prompt。
    * 关键点：prompt 的质量与模型推理的结果息息相关，光把问题表述清楚并不够。

* **同一问题不同问法的差异**

    * 直接问"你知道圆的面积吗"，AI 回答一个"知道"，显然不是想要的结果。
    * 换成"圆的面积如何计算"，AI 就会返回圆面积计算的公式，这才是想要的结果。
    * 由此引出：同一个问题使用不同的 prompt 可能会得到不同的答案，需要调教出聪明的 AI 助手。

* **提示工程**

    * > **定义**：也被称为上下文提示，涉及到设计和优化输入文本（prompt），通过精心的设计引导 AI 模型让它的输出更加准确、相关和有用。
    * 一句话理解：给 AI 出一个好的问题，让它给出一个满意的回答。

### prompt 的六个组成部分

| 组成部分 | 作用 | 举个例子 |
| :--- | :--- | :--- |
| 角色 | 定义与任务最匹配的角色，相当于告诉 AI 它在回答时应该扮演的身份 | 你是一位专业的博客作者 |
| 指令 | 对任务进行具体的描述，明确告诉 AI 我们需要它做什么 | 撰写一篇关于最新 AI 技术发展的文章 |
| 上下文 | 提供与任务相关的背景信息，帮助 AI 更好地理解任务的情景和需求 | 文章应涵盖 AI 技术的当前状态和未来的发展趋势 |
| 例子 | 给出一些具体的例子，实践证明可以帮助 AI 更准确理解我们的需求 | 引用最近的 AI 技术突破和行业专家见解 |
| 输入 | 明确标注出任务的输入信息，有助于 AI 知道它处理的数据是什么 | 当前 AI 技术的相关信息和数据 |
| 输出 | 描述期望输出的格式，AI 就可以按照指定格式来提供结果 | JSON 或 Java 对象 |

* **为什么要凑齐这些部分**

    * 这么做的目的是为了减少歧义。
    * 清晰明确的 prompt 可以让问题更加聚焦，引导 AI 更准确地理解需求并提供满意的答案。
    * 在所有组成部分当中，角色和指令是最重要的，必须被清晰地写出。
    * 上下文、例子、输入、输出则根据实际情况灵活调整。
    * 编程场景里这些部分可以精简：角色和指令可以在一行内写不加关键字，上下文、例子、输入、输出也可以省略。

### 完整走一遍的组装样例

```text
你是一位专业的博客作者

撰写一篇关于最新AI技术的发展文章

文章应该涵盖AI技术的当前状态和未来的发展趋势

可以引用最近的AI技术突破和行业的专家见解

当前AI技术的相关信息和数据

一篇结构清晰、观点鲜明的文章草稿
```

* **组装顺序**

    * 先设定角色，再给出明确的任务指示。
    * 觉得不够就补充与任务相关的背景信息，也就是上下文。
    * 必要时给出具体例子，帮助 AI 更准确地把握方向。
    * 告诉 AI 哪些信息是已知的输入。
    * 最后明确输出的结果。

* **产出效果**

    * 把完整 prompt 应用到通义千问执行，生成标题《探索未来边界：最新的 AI 技术进展与未来展望》。
    * 正文开篇强调 AI 在 21 世纪科技浪潮中的重要地位，引出深度学习、自然语言处理和计算机视觉三个关键领域的进展。
    * 未来趋势部分做了前瞻性探索，包括伦理责任的强化、量子计算机与 AI 的融合、AI 服务的普及。
    * 结尾以对 AI 技术未来发展的乐观态度收束，同时提醒需要审慎考虑技术发展带来的挑战。

### 编程场景里的 prompt 实操

* **案例一：生成 MySQL 建表语句和测试数据**

    ```text
    你是一个软件工程师，帮我生成 MySQL 的表结构

    我需要生成一张课程管理表：
    - 表名：tb_course
    - 字段：主键 id、课程编码、课程学科、课程名称、课程价格、适用人群、课程介绍

    其他要求：
    1. 每张表当中都需要有创建时间、修改时间、创建人、修改人以及备注信息
    2. 每张表的主键都是自增的
    3. 课程价格是整型，课程编码是字符串
    4. 每个字段都要添加 comment 注释
    5. 帮我给生成的表插入一些 IT 课程示例数据，比如课程学科有 java、人工智能，适用人群有小白学员、中级程序员
    ```

    * 需求信息的来源是阅读页面原型获取到的。
    * 产出包含课程表 `tb_course` 的建表语句以及那几个通用字段，下面还附带了测试数据。
    * 落地路径：确定字段名称和类型跟原型保持一致，把建表 SQL 语句和测试数据插入数据库，再通过若依生成前后端代码。

* **案例二：生成数据库说明文档**

    ```text
    你是一个软件工程师
    请根据数据库的 SQL 脚本来编写数据库的说明文档，SQL 脚本如下：
    <把刚刚生成的建表语句粘贴到这里>

    输出要求：
    1. 每个表以及每个表字段都需要详细说明，包括字段名称、类型以及作用
    2. 要求以 Markdown 的格式来输出，字段描述用表格来展示
    3. 如果表之间有关系，需要描述清楚表之间的关系
    ```

    * "SQL 脚本如下"后面跟的建表语句扮演的是上下文的角色，后面三条是要求 AI 输出的结果。
    * 产出的字段详情表格有五列：字段名称、字段的类型、该字段是否可空、有没有默认值、描述该字段作用。
    * 典型字段说明：主键 `id` 为 `int` 类型、不能为空、主键自增，作为每条课程表的唯一记录标识；`course_code` 为 `varchar` 类型、不能为空、没有默认值，作用是课程编码，用于唯一标识课程、方便查询与管理；`course_subject` 同为 `varchar` 类型、不能为空、无默认值，作用是课程学科，比如 java、Python、大数据，描述该课程所属领域。
    * 还会补充表的数据库引擎 InnoDB，提供事务处理、行级锁以及外键约束等功能。
    * 还会说明字符集编码 `utf8mb4`，支持更广泛的 Unicode 字符集，包括表情符号等四个字节的字符。
    * 表关系方面：只提供了一张表，并没有与其他表建立关系，所以没有输出表的关系。
    * 但它会根据实际场景分析出可能与课程分类、讲师表关联，还有课程选课等扩展需求；如果有这类业务场景，还需要添加外键约束以维护数据之间的一致性完整性。

* **案例三：生成代码与代码流程图**

    * 代码生成的几种常见情况：给出表来生成代码，这在项目当中比较常见，但这一部分若依已经实现了；后面的立可得项目着重使用通义灵码补全代码的功能；还可以根据接口文档来提取 DTO 或 VO 的实体类字段信息等等。
    * 复杂业务流程难理解时需要画流程图梳理思路，过去这个过程效率太低，现在可以用 AI 协助绘制。

    ```text
    你是一个软件公司
    为了方便理解代码的执行流程，需要给出代码的执行流程图

    具体代码如下：
    <把代码粘贴到这里>

    请使用 Mermaid 的语法来描述这个方法的流程
    ```

    * 这里角色是一家公司，指令是给出代码的执行流程图，中间那段代码是上下文信息，最后告诉 AI 的输出格式是 Mermaid 语法。
    * 生成的 Mermaid 语法直接肉眼看比较复杂，需要复制一份交给支持 Mermaid 语法的 Markdown 工具去渲染。
    * 典型场景：立可得在添加工单之前需要查询售货机判断售货机是否存在，不存在就抛出异常；存在的话再校验售货机的状态与工单类型等一系列校验。
    * 结论：一个好的 prompt 可以减少歧义，确保 AI 的回答更符合需求，从而高效完成这类繁琐的设计工作。
