# RBAC 权限控制与 Spring Security

## 登录请求在前端做了什么

### 表单提交与加载态

* **登录入口 `handleLogin`**

    * > **定义**：登录页点击「登录」按钮后触发的前端方法，是整条登录链路的第一站。

    * 第一步做表单校验，检查用户名、密码、验证码是否为空以及各自的长度限制。

    * 校验通过后把响应式变量 `loading` 置为 `true`，按钮随即不可用，文案由「登录」变为「登录中」并置灰。

* **记住密码**

    * 判断是否勾选「记住密码」：勾选则把用户名、密码和记住密码这个选项一起写入 cookie；未勾选则把这三项从 cookie 中移除。

    * 该能力主要用于后台管理系统，登录态本身仍由 token 决定。

### userStore.login 与 token 的两份存储

* **集中式状态管理对象（Pinia，userStore）**

    * > **定义**：Vue3 里集中存放登录后用户信息的全局状态对象，存放位置是 store 的 user 模块。

    * 登录前先从登录表单对象中解出四个值：用户名、密码、验证码、验证码标识 `uuid`。

    * 用 `Promise` 包裹异步流程，成功执行 `resolve`、失败执行 `reject`。

    * 第一步调用登录 API 方法把这四个参数传过去等待服务器返回；第二步把返回的 token 存入 cookie，同时再存入 userStore；第三步调 `resolve` 结束异步操作。

    * > **提示**：存 cookie 是因为前端可以据此判断登录态；存进 Pinia 是为了在其他界面灵活拿到 token 信息。

* **验证码标识 `uuid`**

    * > **定义**：Redis 中存放正确验证码的 key，由后端在渲染验证码图片时生成。

    * 渲染图片时后端生成一个 uuid，把验证码值存进 Redis、把 uuid 塞进图片的返回结果。

    * 用户提交时把 uuid 原样带回来，后端才能定位到「这张图对应的正确答案」。

### 请求层的两个开关

* **登录 API 方法**

    * 接收同样四个参数，新建一个 JSON 对象接收，通过请求工具类向后端发请求，路径为 `/login`，方式为 `post`。

    * 请求头里把 `isToken` 设为 `false`，登录操作不需要由前端请求拦截器拼接 token 令牌请求头。

    * 同时标记本次请求不做重复提交拦截，用户连续点击多次登录按钮只有一次生效，这由前端拦截器完成。

    * 浏览器验证：点登录后第一个请求地址是 `login`，方式 post，请求体携带验证码、密码、用户名、uuid 四项。

## 后端入口与三道校验关卡

### 登录控制器只做三件事

* **`SysLoginController`**

    * > **定义**：admin 模块中接收登录请求的 Controller，代码极短，真正的活在 Service 里。

    * 通过 `loginBody` 对象获取请求体参数，与前端四项一一对应：用户名、密码、验证码、uuid。

    * 初始化一个成功的 `AjaxResult`；调用 Service 的登录认证；认证成功后把返回的 token 令牌放入 `AjaxResult` 并返回。

### 第一关：验证码校验

* **验证码开关**

    * 校验第一步先查若依「系统管理 → 参数设置」里的验证码开关，目前是打开的，这份信息在 Redis 中也有一份缓存数据，`true` 表示开启验证码校验。

    * 兜底逻辑：取到的值为空或未设置时默认使用验证码校验；不为空则原样返回 `true` 或 `false`。

    * 一旦为 `true`，就用 uuid 构建 Redis 缓存键取出验证码；验证码仅一次生效，取到之后立即从 Redis 中删除。

* **验证码比对规则**

    * Redis 中没取到验证码表示已过期，用异步工厂记录验证码失效日志并抛出「验证码已经失效」异常，由全局异常处理器统一捕获做提示。

    * 未失效则与用户输入的验证码比对，**比对时不区分大小写**。

    * 比对不一致同样用异步工厂记录不匹配日志并抛出异常给前端做提示。

### 第二关：登录前置校验

* **后端二次校验的必要性**

    * > **提示**：前端校验只防君子不防小人，前端正则写在浏览器里改一下就能绕过去，只有后端校验才真正生效。

    * 前端已用正则校验过一遍，后端仍必须对敏感数据做二次校验。

* **三组校验规则**

    * 非空校验：用户名和密码其中有一个为空，即通过异步工厂记录错误日志并抛出异常。

    * 长度范围校验：密码必须在 5~20 位之间，用户名不能小于两位且不能超过 20 位，这两个范围在代码里用常量定义。

    * IP 黑名单校验：从参数配置获取事先设置过的 IP 黑名单列表，就在系统参数设置的最后一个；多个 IP 以分号分隔；登录 IP 命中黑名单即记录日志并抛出黑名单异常。

## Spring Security 认证核心

### 用户状态校验

* **用户详情服务 `UserDetailsService`**

    * > **定义**：Spring Security 中按用户名装载认证信息的扩展点，本例的认证细节全部落在实现类的 `loadUserByUsername` 方法里。

    * 方法一上来就根据用户名查数据库，调用 mapper 查询 `sys_user` 系统用户表，结果封装成实体类。

* **三种拦截分支**

    * 用户不存在：记录不存在的日志并抛出异常，提示「此用户不存在」，提示文案来自 i18n 配置文件。

    * `del_flag` 等于 `2` 表示已被逻辑删除，记录日志并抛出「用户已经被删除」。

    * `status` 等于 `1` 表示账号已被停用（例如用户请长假期间把账号停用），记录停用日志并抛出已停用异常。

| 字段 | 值 | 含义 |
| :--- | :--- | :--- |
| `del_flag` | `0` | 存在 |
| `del_flag` | `2` | 已经删除 |
| `status` | `0` | 正常 |
| `status` | `1` | 停用 |

### 密码错误次数锁定

* **密码重置次数缓存**

    * 登录时会在 Redis 中记录当前用户的密码重试次数，缓存在 `pwd_err_cnt` 下按用户区分。

    * 第一次登录缓存里没有次数，初始化为零。

    * 配置文件 `application.yml` 的用户配置中有密码最大错误次数限制，为 **5** 次；连续输错达到后进行锁定，默认锁定时间 **10 分钟**，两者都可按场景调整。

    * Redis 中重复次数超过最大值时直接抛异常，提示前端接下来要锁定 10 分钟。

* **密码比对结果分支**

    * 密码错误：重置次数加一（原来 0 次变 1 次、3 次变 4 次）并写回 Redis，再抛出密码不匹配异常，用户需在登录界面重新输一轮。

    * 密码正确：清理掉登录次数的缓存。

    * > **易错点**：两次输错后把密码改对再登录成功，原来的登录记录会被清零而不是累加保留。

### matches 与 BCrypt

* **密码校验方法 `matches`**

    * > **定义**：把密码比对细节单独抽出的方法，由 Spring Security 的 `BCryptPasswordEncoder` 实现。

    * 底层走哈希散列算法，把用户输入的真实密码与数据库存出的密文比较，一致返回 `true`，否则返回 `false`。

    * 认证失败抛出异常时，主逻辑从异常类中取出异常信息向客户端返回「用户名或密码不匹配」。

## 登录用户对象装配

### createLoginUser 做了什么

* **登录用户对象 `LoginUser`**

    * > **定义**：认证成功后创建并返回给 Spring Security 的登录用户对象，承载用户信息、角色信息与权限信息。

    * 创建时带上用户 id、此用户的 `deptId`、`sys_user` 用户信息，以及按 RBAC 五表联查得到的角色权限信息。

    * 权限集合用 **Set** 存储，因为一个用户可关联多个角色、每个角色之间权限数据可能重复，重复部分只要一份。

    * 最终返回所有权限集合封装进登录用户对象，再把该对象存入 Spring Security 安全框架，之后可随时从上下文取用。

### RBAC 五表模型与查询路径

* **五表关系**

    * 三张主表是用户表、角色表、菜单权限表；用户与角色是多对多、角色与权限也是多对多，各有一张中间表。

    * 查询路径：已知用户 id → 查用户角色中间表得角色详细信息 → 按角色 id 查角色菜单中间表得菜单 id → 得到该用户角色所对应的菜单列表。

    * > **提示**：这一步看似多余，是因为登录时查询到的用户对象未必包含角色集合，此时可退化为按用户 id 先查角色再查菜单。

```text
      sys_user ──(sys_user_role)──▶ sys_role ──(sys_role_menu)──▶ sys_menu
        用户            用户角色中间表          角色        角色菜单中间表        菜单权限
         id                   user_id          role_id            role_id           menu_id
                                                 │
                          role_key = admin / common / account
                                                 │
                                                 ▼
                            LoginUser.permissions : Set<String>
                       admin 直接塞 "*:*:*"，其余遍历角色去重合并
```

* **权限集合的两种取法**

    * 登录用户是管理员时直接置权限字符 `*:*:*`，表示拥有访问所有功能、所有菜单的权限。

    * 非管理员则按 RBAC 模型查询角色集合，遍历每个角色按角色 id 查菜单权限，把当前角色对应权限合并进集合。

    * 循环内调用菜单 service 根据角色 id 查询，将角色权限放入角色对象后加入集合，两个角色权限相同时由 Set 完成去重。

    * 用户没有角色时也可直接按用户 id 查权限表，因为用户与权限没有直接关联，必须先查角色再查菜单做多表联查。

## 登录成功后的收尾

### 上下文清理与登录留痕

* **上下文清理**

    * 登录前会把用户名密码放进认证上下文对象。

    * 主逻辑用 `finally` 收尾：无论登录成功还是失败，都要清理上下文中的用户名和密码。

* **登录成功三步**

    * 第一步通过异步工厂记录登录成功日志。

    * 第二步通过 Spring Security 获取登录用户信息 `LoginUser`，其中包含用户信息、角色信息与该用户的权限信息。

    * 第三步创建 `SysUser` 对象，设置用户 id、登录 IP、登录时间，以 id 为条件更新用户表的 `login_ip` 与 `login_date` 两列，留痕防止恶意操作。

### Token 生成与 Redis 登录态

* **令牌与代理信息**

    * 用 id 工具类生成一个 UUID 作为用户 token 令牌，并把令牌存入登录用户对象。

    * 代理信息包括请求头中的 User-Agent、用户的客户端 IP、通过 `AddressUtils` 由 IP 解析出的区域地址、浏览器信息与操作系统信息。

* **Redis 模拟 session**

    * 刷新 Redis 中的用户令牌，更新登录时间并重新计算有效期；令牌有效期读取配置文件，默认 **30 分钟**，可结合业务场景修改。

    * 缓存键由 token 指定，保证用户之间不冲突，键左侧是固定值 `login_tokens`，右侧是 UUID 生成的 token。

    * Redis 中存在该用户状态即表示登录成功，不存在则视为未登录，必须重新走一遍认证登录流程。

```text
   IdUtil.fastUUID() ──▶ 登录用户的 token（同时存进 LoginUser）
                              │
     代理信息：User-Agent / 客户端IP ──▶ AddressUtils 解析区域
               浏览器 / 操作系统
                              │
                 更新时间 + 重算有效期（配置文件，默认 30 分钟）
                              │
                              ▼
        Redis：login_tokens : {token}  ──▶ LoginUser 的 JSON
                 ├ browser       谷歌 12
                 ├ deptId        103
                 ├ expireTime    毫秒时间戳
                 ├ ipaddr        内网 127.x
                 ├ loginLocation IP 归属区域
                 ├ loginTime     登录时间
                 ├ os            Windows 版本
                 └ roles / permissions
                              │
                              ▼
        JwtUtils.createToken(map, secret)  ──▶ 加密 JWT
                              │
                     AjaxResult{token} ──▶ 前端 Cookie
```

* **JWT 与密钥**

    * 方法调用者创建 map 集合装入令牌信息，用 `createToken` 创建令牌，底层走 JWT 工具类结合 `secret` 密钥生成加密 token。

    * > **注意**：`secret` 在配置文件中已经指定，绝不能泄露；令牌有效时间也在同一文件中，为方便调试被改成了 300 分钟。

    * 加密后的 JWT 依次返回给 Service、Controller，Controller 装入 `AjaxResult` 返回客户端，客户端拿到后存入 cookie。

### 前端 token 入 cookie 与路由重定向

* **token 入 cookie**

    * 用户状态管理对象的登录方法里有一行把登录返回的 token 写入 cookie。

    * 浏览器登录成功后按 F12，在 Application 的 cookie 中即可查看令牌数据。

* **编程式路由跳转**

    * 登录成功后前端会从登录页面重定向到首页，用的是编程式路由跳转，跳转到系统指定首页；有参数时跳转需携带路由参数。

    * 通过 `route.query` 获取当前路由参数，其中包含 `redirect` 的部分被识别为重定向地址而非普通参数，会被过滤掉；普通 query 参数在跳转首页时一并携带。

    * 地址栏问号后方的 `redirect=/index` 就是这个重定向参数；当前路由没有参数时默认只跳到首页。

## 角色与权限下发

### 路由守卫的触发时机

* **全局路由守卫**

    * > **定义**：前端在跳转到新路由之前执行的校验钩子，用于确认用户身份并做状态设置。

    * 守卫内调用用户状态管理对象的 `getInfo`，向后端发送请求查询用户信息。

    * `getInfo` 实现在用户状态管理对象中，创建 promise 后调用同名 API 方法发请求；API 定义在登录 API 文件里，走请求工具类发 GET 请求，路径为 `/getInfo`。

    * 后端同名方法众多，应按请求方式 GET、请求地址 `getInfo` 定位到符合条件的那一个。

* **后端入口职责**

    * 后端登录控制器接收前端请求、处理查询逻辑并返回用户角色和权限信息。

### getInfo 的三个查询动作

* **第一步取当前登录用户**

    * 通过 Security 工具类获取当前登录对象的用户信息 `SysUser`。

    * 能取到的前提是登录成功时已把该对象存入 Spring Security 的认证管理器。

* **第二步查角色权限集合**

    * 初始化一个字符串 **Set** 集合存储角色字符串，用 Set 是因为一个用户可关联多个角色，角色权限字符串可能重复。

    * 先判断当前登录用户是否为超级管理员：是则直接加入角色字符串 `admin` 表示拥有全部权限；否则按用户 id 查询角色权限后加入集合。

    * mapper 的 XML 以 `user_id` 为条件，通过 `<include>` 引入公共 SQL，联查角色表、用户角色中间表、用户表以及部门表，部门表涉及数据权限控制。

    * SQL 用 `distinct` 关键字实现去重；已知用户 id，先由中间表拿到角色 id，再按角色 id 查角色详细信息，一个用户可拥有多个角色所以返回角色集合。

* **角色权限字符串 `role_key`**

    * 角色表左侧 `role_name` 是角色名称，右侧 `role_key` 才是权限字符串，最终要返回的是后者。

    * 遍历角色对象，对当前角色的权限字符串做非空判断，不为空才添加到新的 Set 集合。

    * 一个角色可能涉及多个权限字符串（如 `role1,role2`），代码用 `split` 按中间逗号切割成数组，再通过 Arrays 工具类转成集合合并进总集合。

    * > **提示**：一般情况下一个角色只有一个权限字符串，这个切割转换过程了解即可。

| `role_name`（角色名称） | `role_key`（权限字符串） |
| :--- | :--- |
| 超级管理员 | `admin` |
| 普通角色 | `common` |
| 财务人员 | `account` |

* **第三步查权限集合**

    * 同样先判断当前用户是否为管理员：是则返回 `*:*:*`；否则获取当前用户角色集合，遍历角色按角色 id 查权限列表，设置到角色对象并合并进总权限集合。

    * 用户没有角色集合也没关系，可直接按用户 id 查询并把结果并入总集合。

* **三件套封装与前端接收**

    * Controller 拿到用户信息、角色集合、权限集合后，创建成功的 `AjaxResult` 把三者装入并返回。

    * 前端先取出用户信息并拼接用户头像（头像地址存在用户表中），再判断有无角色集合，把角色集合与权限集合一并封装进用户状态对象供其他视图组件取用。

    * 没有返回角色时设置默认角色，并给状态对象保存用户 id、用户名称与用户头像。

## 按钮级权限指令

### 权限指令

* **`v-hasPermi`**

    * > **定义**：若依封装的自定义指令，用于按钮级权限判断，按钮挂载时触发。

    * 第一步取出指令属性值，得到中括号包裹的权限数组，可能一个也可能多个。

    * 同时定义超级管理员权限标识 `all_permission` 为 `*:*:*`，并从用户状态管理器取出当前用户的权限集合，也就是后端刚返回的那一份。

    * 指令数组不为空时记为 `permissionFlag`，用 `some` 遍历判断：命中 `*:*:*` 或权限集合包含遍历中的权限即返回 `true`。

    * 返回 `true` 保留渲染按钮；返回 `false` 则通过 `parentNode.removeChild(el)` 把元素从 DOM 移除，页面渲染时看不到该按钮。

    * 一个按钮可以设置多个权限，包含任意一个即显示，例如同时声明添加与编辑权限。

```text
      <el-button v-hasPermi="['system:user:add']">添加</el-button>
                             │
                    按钮挂载 → mounted 触发
                             ▼
        1. 取指令属性 → ['system:user:add'] → permissionFlag
        2. all_permission = "*:*:*"
        3. 从 Pinia 取 permissions（后端刚返回的那份）
                             │
                             ▼
        permissions.some(p => all_permission === "*:*:*"
                             || p === 遍历中的 permission)
                  ┌──────────┴──────────┐
                true                 false
                  │                    │
           保留，渲染按钮        parentNode.removeChild(el)
                                  按钮从 DOM 移除 → 页面看不到
```

* **实际效果**

    * 演示时新建「财务人员」角色，权限字符为 `account`，菜单权限仅勾选点位管理下区域管理的查询功能。

    * 再新建用户并绑定该角色登录，侧边栏只有点位管理一级菜单，打开后仅含区域管理二级菜单，新增、修改、删除按钮全部隐藏；超级管理员则可见全部按钮并能增删改查。

### 角色指令

* **`v-hasRole`**

    * > **定义**：与权限指令并行的角色判断指令，同样能控制按钮的显示隐藏。

    * 单个设置如 `v-hasRole="admin"`，该角色权限字符串为 `admin`，表示只有超级管理员登录后此按钮才可见。

    * 也支持多个角色，只要当前用户的角色权限包含其中任意一个，按钮即在页面显示。

    * 实现与权限指令完全一致：取用户状态对象、取指令角色数组、定义超级管理员角色标识 `admin`、从状态管理器取角色数组、数组非空记为 `roleFlag`、判断命中后返回布尔值。

    * 返回 `false` 时同样把该元素从页面 DOM 移除。

## 动态菜单路由链路

### 前端发起与后端接收

* **前端只做一件事**

    * 入口在全局路由守卫中，跳首页之前调用权限路由状态管理对象的 `generateRoutes` 生成可访问的路由表。

    * 该方法第一步 `new Promise`（整体是异步过程），然后调用 API 方法 `getRouters`。

    * `getRouters` 定义在菜单 API 文件中，该文件当前只有一个方法，请求路径 `/getRouters`，方式为 `get`。

    * 浏览器验证：刷新页面时 `getInfo` 之后紧跟着 `getRouters`，请求方式 GET，路径完全对应。

* **后端 Controller 的两步走**

    * 职责只有两句：接收前端请求，构建出完整的菜单树结构，把符合条件的路由返回前端。

    * 先用 `SecurityUtils.getUserId()` 拿到当前登录用户的 id，再交给 `selectMenuTreeByUserId`，拿回来的是带树状结构的菜单列表，最后成功返回。

```java
@GetMapping("/getRouters")
public AjaxResult getRouters()
{
    // ① 拿到当前登录用户的 id
    Long userId = SecurityUtils.getUserId();
    // ② 按用户 id 查他所有能访问的菜单,以树状结构返回
    List<SysMenu> menus = menuService.selectMenuTreeByUserId(userId);
    return AjaxResult.success(menus);
}
```

### 菜单查询的两条分支

* **菜单类型 `menu_type`**

    * > **定义**：菜单表中的类型字段，共三个取值。

    * `M` 是目录菜单（习惯叫一级菜单），`C` 是组件菜单（习惯叫二级菜单），`F` 是按钮。

    * 查询只取 `M` 与 `C`：工单管理、点位管理、设备管理是左侧栏里的一级目录，其下挂若干二级组件，再往下的三级按钮在左侧栏根本不显示，直接过滤。

* **超级管理员：单表查询**

    * 走 `selectMenuTreeAll`，只查 `sys_menu` 一张表，条件只有菜单类型 `IN ('M','C')` 和菜单状态 `status = '0'`。

    * 排序按 `parent_id, order_num` 升序，`parent_id` 为 0 的一级目录排在前面、二级组件排在其后，用户管理、角色管理、菜单管理、管理部门都挂在系统管理底下，正是标准树表结构。

    * > **易错点**：`status` 是 `0` 启用、`1` 禁用，这两个值不要记反。

* **普通用户：RBAC 五表联查**

    * 不是 admin 就换一条路，按用户 id 查他能访问的菜单，需要菜单表、角色表、用户表外加两张中间表共五张表串起来。

    * 查询条件：当前登录用户 id、`menu_type` 为目录与组件菜单、菜单状态与角色状态均为启用、按 `parent_id` 和 `order_num` 升序。

    * 验证时用户 id 取 `100`，结果只有目录菜单「点位管理」与组件菜单「区域管理」两条；区域管理的 `parent_id` 是 2000 而 2000 正是点位管理，点位管理自己挂在 `parent_id` 为 0 的主类目下。

```text
        sys_menu  (菜单表)
             │
        sys_role_menu  (菜单↔角色 中间表)
             │
          sys_role  (角色表)
             │
        sys_user_role  (角色↔用户 中间表)
             │
         sys_user  (用户表)
```

### 从平铺列表构出菜单树

* **父子归位依据**

    * 查询出来的列表是所有数据的平铺集合，彼此之间没有父子关系，前端却需要层层嵌套，差的这一步就是构树。

    * 一条记录靠自己的 `menu_id` 和 `parent_id` 两个字段归位；`parent_id` 为 0 就是创建菜单时指定的主类目，是整棵树的根。

```text
主类目 (parent_id = 0)
├── 工单管理   (parent_id = 0)
│   └── ...
├── 点位管理   (menu_id = 2000, parent_id = 0)
│   ├── 区域     (parent_id = 2000)
│   ├── 点位     (parent_id = 2000)
│   └── 合作商   (parent_id = 2000)
└── 设备管理   (parent_id = 0)
```

* **构树方法 `buildMenus`**

    * 第一步初始化一个子菜单列表（也叫权限列表）作为返回容器。

    * 传入的 `parentId` 是 0 即主类目，所以这个容器最终装的是一级目录菜单。

    * 遍历整个菜单集合逐条判断，当前这条记录的 `parent_id` 等于传入的父 id 就收进来。

    * 收进来之前还有一步：调 `buildMenuChildList(menus, t)`，用整个集合当全量数据池子，找出当前节点的所有子节点挂上去。

* **子节点查找 `buildMenuChildList`**

    * > **定义**：把整个菜单集合再遍历一遍、`parent_id` 等于当前节点 id 的记录全部收走的递归查找方法。

    * 两个参数分别是全量菜单集合与当前节点对象；区域、点位、合作商三条记录就是这样被捞出来的。

    * 拿到子节点后塞进当前节点的 `children` 属性，再对这三个子节点重复一遍，看它们各自有没有孩子，有就继续递归往下找。

    * > **结论**：菜单树这样写是为留扩展性，万一将来加到三级、四级，递归可以原封不动往下钻，写死两层改了就得重写；处理树形结构递归是常规解法。

### 菜单树翻译成前端路由

* **路由对象格式**

    * 菜单树还只是「菜单」，前端要的是「路由」，两套格式必须再翻译一次。

    * 路由字段包括名称、路径、是否隐藏、是否重定向、组件名称，以及有没有子路由，有就挂一个 `children`。

    * 翻译由重载的 `buildMenus` 完成：每个菜单配一个路由对象，把名称、图标、缓存标志、路径搬进去，隐藏标志由 `visible` 决定，并新建一个 `meta` 对象。

    * 关键判断是当前菜单有没有子菜单，有且是路由类型时把子菜单扔回同一方法继续造路由，递归思想与构菜单树完全一致。

```java
List<RouterVo> routers = new ArrayList<>();
for (SysMenu menu : menus)
{
    RouterVo router = new RouterVo();
    RouterVo.MetaVo meta = new RouterVo.MetaVo();
    // 把菜单数据搬到路由对象上:名称、图标、缓存标志、路径……
    router.setName(getRouteName(menu));
    router.setPath(getPath(menu));
    router.setHidden("1".equals(menu.getVisible()));
    router.setComponent(getComponent(menu));
    router.setMeta(meta);

    // 关键:有子菜单就继续递归,把子菜单扔回当前方法构建子路由
    List<SysMenu> cMenus = menu.getChildren();
    if (CollUtil.isNotEmpty(cMenus) && isRouter(menu))
    {
        router.setChildren(buildMenus(cMenus));
    }
    routers.add(router);
}
return routers;
```

* **特殊情况一：主类目下的组件菜单**

    * 判定条件是 `parent_id = 0` 且 `menu_type = 'C'`，此时不能直接当成一级路由挂上去，而要给它造一个子路由。

    * 若依默认情况下通过路由找视图组件，地址都是两层：一级目录加二级组件。

    * 新建一个挂在主类目下的组件菜单，肉眼看只有一层是错觉，实际是根 `/` 加子路由 `test` 拼出来才是完整路径。

    * > **结论**：因为前端代码是固定的，后端返回格式必须统一；就算创建的是主类目下的组件菜单，返回格式也要跟普通二级组件菜单一模一样。

```text
错误直觉:  /test              ← 以为只有一层
实际结果:   /  +  test         ← 根 + 子路由,拼出来才是 /test
               └── test
```

* **特殊情况二：被误配成外链的内部链接**

    * 判定条件是主类目下的菜单且路径以 http 开头，同样创建子路由，子路由的作用是把 http 开头的那一段删掉、只保留基础域名，再改造成一个内部链接的路径。

    * 兜底动机是防止误操作：给一个内部链接误点「是否外链」填了官网地址后，它既不能外链跳转也不能当站内路由用。

    * 代码里路由 path 置 `/`、component 置 null，用 `removeStartWith` 去掉 `https://` 前缀，组件取 `getInnerPath`，把外链降级成站内路由。

```java
else if (menu.getParentId() == 0 && isInnerLink(menu))
{
    router.setPath("/");
    router.setComponent(null);
    StringRouterVo path = new StringRouterVo();
    // 去掉 https:// 前缀,把外链降级成站内路由
    path.setPath(removeStartWith(menu.getPath(), Constants.HTTP_PREFIX));
    path.setComponent(getInnerPath(menu));
    router.setChildren(CollectionUtils.arrayToList(path));
}
```

* **前端渲染侧边栏**

    * 后端结果回来后，状态管理对象先做一次深拷贝，把后端返回的 JSON 数据转成各自对应的前端路由格式，再用 `setRouters`（侧边栏）存入当前状态管理对象。

    * 路由的核心代码在布局页，加载侧边栏、头部导航栏、主体区域三块；主体区域负责显示各个视图组件，侧边栏这一块涉及动态路由。

    * 侧边栏组件对状态管理对象里存着的路由做 for 循环遍历，视图就渲染出菜单。

    * 用户点击每个组件菜单，布局页主体区域按 path 地址找到对应的视图组件并渲染，这就是点不同菜单显示不同界面的原因。

```text
登录成功 ─► 加载 permission.js
         ─► 跳首页,加载 layout 布局组件
             ├─► 加载 Sidebar 侧边栏 ─► 遍历动态菜单路由渲染出菜单
             └─► 用户点击菜单
                     └─► 路由里的 path 跳到对应视图组件
                             └─► 在主体区域显示
```

## 接口级鉴权

### 前端挡不住接口测试工具

* **权限注解 `@PreAuthorize`**

    * > **定义**：Spring Security 提供的注解，实现方法级别的访问控制，在方法执行之前做权限校验，满足条件才放行。

    * 若依生成的 Controller 每个方法上都装饰了它，不满足条件时给出相应提示。

    * 现象演示：用超级管理员给受限用户开放「系统工具 → 系统接口」的 Swagger 测试权限，该用户登录后从调试工具复制 cookie 里的 token 发起请求，返回「没有此权限，请联系管理员授权」。

* **授权后必须重新登录**

    * 管理员开放权限后，受限用户需要退出并重新登录，新权限才会生效。

    * 原因：后端校验权限是基于上次登录的缓存数据，那时权限已存入 Redis，当前缓存里仍只有区域列表查询和 Swagger 接口测试权限，没有订单权限。

    * 重新登录后 token 也重新生成了一份，原令牌失效，还要再开一次调试工具复制新 token 替换进去。

    * > **易错点**：权限数据是登录时一次性加载进 Redis 缓存的，管理员改了权限而用户没有重新登录，接口依旧报权限不足。

* **表达式三段式**

    * 表达式由三部分组成：`@ss` 表示权限服务类（取名自 Spring Security 的首字母缩写），`hasPermi` 是判断方法，`'manage:order:list'` 是当前方法的权限参数。

    * 注解拿到布尔值后，Spring Security 据此决定执行方法逻辑还是拦截并抛出异常给前端提示。

```java
@PreAuthorize("@ss.hasPermi('manage:order:list')")
@GetMapping("/list")
public TableDataInfo list()
{
    // ...
}
```

### 权限服务类的判定逻辑

* **`PermissionService`**

    * > **定义**：若依自定义的权限实现类，注解属性值就是它的底层实现，专门验证用户是否具备某种权限。

    * 权限参数为空直接返回 `false`，直接拦截。

    * 取 `LoginUser` 对象拿到用户基本信息、角色集合与权限集合；登录用户不存在说明登录状态已失效，返回 `false`。

    * 权限集合为空说明用户已登录但没有任何权限，没必要继续校验，返回 `false`。

    * 把权限集合存进上下文，底层是 **ThreadLocal**，方便后续操作。

    * 最关键一步是集合是否包含当前方法的权限参数，判断式只有一次或运算：包含 `*:*:*` 或包含当前权限字符串；三个星一旦出现就表示拥有所有权限直接放行。

```java
public boolean hasPermi(String permission)
{
    // 第一步:传进来的权限参数为空,直接 false
    if (StringUtils.isEmpty(permission))
    {
        return false;
    }
    // 第二步:拿到当前登录用户信息
    LoginUser loginUser = getLoginUser();
    Collection<String> permissions = loginUser.getPermissions();
    // 登录状态失效 -> false
    if (CollUtil.isEmpty(permissions))
    {
        return false;
    }
    // 把权限集合存进上下文,底层是 ThreadLocal,方便后续操作
    ...
    // 最关键的一步:权限集合里有没有我当前方法的权限参数
    return permissions.contains("*:*:*") || permissions.contains(permission);
}
```

* **权限与角色各三把方法**

    * `hasPermi` / `lacksPermi` / `hasAnyPermi` 判定权限，`hasRole` / `lacksRole` / `hasAnyRoles` 判定角色，语义与前端权限数组类似。

    * 实测把 `hasPermi` 改成 `lacksPermi` 后，因该用户确实有订单权限而被拦下，属于预期行为；第一次看不到提示是 Swagger 页面的显示问题，不是代码问题。

    * 角色表达式改成 `hasRole('accountant')` 时，拥有「财务人员」角色的用户请求成功返回数据，判断角色的逻辑与判断权限一致；若依默认使用的 `hasPermi` 已能满足绝大多数场景。

| 表达式 | 作用 | 通过条件 |
| :--- | :--- | :--- |
| `@ss.hasPermi('manage:order:list')` | 验证用户是否具备某个权限 | 权限集合含该权限，或含 `*:*:*` |
| `@ss.lacksPermi(...)` | 验证用户是否**不**具备某个权限 | 与 `hasPermi` 逻辑相反：满足权限就拦截 |
| `@ss.hasAnyPermi('a:b:c', 'd:e:f')` | 验证是否具备任意一个权限 | 多个权限用逗号分隔，命中其一即放行 |
| `@ss.hasRole('accountant')` | 判断用户是否拥有某个角色 | 拥有则放行，否则拦截 |
| `@ss.lacksRole(...)` | 判断用户是否**不**拥有某种角色 | 与 `hasRole` 完全相反 |
| `@ss.hasAnyRoles('a', 'b')` | 判断是否拥有任意一个角色 | 多个角色用逗号分隔，命中其一即放行 |

* **匿名访问注解 `@Anonymous`**

    * > **定义**：标记不需要登录也能访问的方法或类。

    * 放在方法上：该方法不登录也可以匿名访问；放在类上：该类所有方法都不需要登录。

    * > **易错点**：必须把原有的 `@PreAuthorize` 注释掉，否则两个注解冲突，一个要校验一个不要校验。

    * 典型场景是系统公告，未登录或没有权限的人也应能看到公告更新与版本信息。

## 异步任务管理器

### 同步串行带来的两个问题

* **耗时账**

    * 假设登录认证核心业务耗时 50ms、记录日志耗时 50ms，同步串行下整个登录请求耗时 100ms。

    * 产品经理追加「登录成功后给用户发提示短信」需求，发送同样耗时 50ms，整个登录请求耗时变成 150ms，用户等待时间增加、系统性能下降。

* **连锁失败**

    * 登录业务还涉及事务控制以保证一致性，若登录认证成功但记录日志时出现异常就会导致事务回滚，这样的设计显然不合理。

    * 用户只关心登录是否成功，记录日志、发短信这些非核心业务并不要求立即完成，所以可以交给异步任务管理器的多线程处理。

```text
同步写法  总耗时 150ms
主线程 ──┬── 登录认证 50ms ──┬── 记日志 50ms ──┬── 发短信 50ms ──┬──► 返回
         │                   │                 │                 │
                        抛异常 ╰─► 事务回滚,前面白干

异步写法  总耗时 50ms
主线程 ──┬── 登录认证 50ms ──┬──► 返回 token
         │
         └─(交给线程池,延迟 10ms 起线程)─► 记日志 ─► 发短信
                                              │
                                       失败也回不到主线程
                                       登录事务不受影响(故障隔离)
```

* **改造收益**

    * 登录耗时只剩 50ms，无需等待异步任务完成，性能显著提升。

    * 登录认证作为独立事务在主线程执行、记录日志在另一个线程执行，即使日志失败也不影响登录事务，实现故障隔离。

    * 通用性非常好：只需把任务创建出来，就能执行记录日志、发短信等各种类型任务。

### 单例与线程池

* **`AsyncManager`**

    * > **定义**：处理那些不需要及时返回结果的后台任务的单例组件，核心优势是提高程序响应速度和整体性能。

    * 用 `getInstance()` 拿到单例对象，`execute` 方法底层通过多线程执行任务，任务由异步线程工厂创建。

    * 用的是饿汉式单例：静态字段直接 `= new AsyncManager()`，类加载时就把实例造好，而不是等第一次调用才创建。

    * 线程池字段从 IOC 容器中通过 Spring 工具类 `getBean` 拿到，bean 名是 `scheduleThreadPool`。

* **线程池三个参数**

    * 核心线程数，这里定义为 **50**，可结合自己的业务场景调整。

    * 线程工厂创建线程时指定线程名称（`schedule_pool_` 加自增序号），并把守护线程设置为 `true`。

    * 拒绝策略设置为 `CallerRunsPolicy`。

```java
@Bean(name = "scheduleThreadPool", destroyMethod = "shutdown")
public ScheduledExecutorService scheduleThreadPool()
{
    ScheduledExecutorService scheduledThreadPool = new ScheduledThreadPoolExecutor(
        CORE_POOL_SIZE,                 // ① 核心线程数
        new ThreadFactory() {
            @Override
            public Thread newThread(Runnable r) {
                Thread thread = new Thread(r, "schedule_pool_" + count.getAndIncrement());
                thread.setDaemon(true); // ② 守护线程
                return thread;
            }
        },
        new ThreadPoolExecutor.CallerRunsPolicy() // ③ 拒绝策略
    );
    return scheduledThreadPool;
}
```

* **任务调度**

    * 拿到线程池对象后用它的 `schedule` 方法做任务调度，需要三个参数：任务对象、延迟时间、延迟单位。

    * `execute` 中固定延迟 10ms 执行，单位是 `TimeUnit.MILLISECONDS`。

### 异步线程工厂记一条登录日志

* **任务构造**

    * 登录 Service 在登录成功的位置调用异步线程工厂创建任务，传入三个参数：当前登录的用户名、登录状态为成功、I18N 对应的提示信息。

* **任务内部四步**

    * 解析客户端的代理信息，拿到操作系统和浏览器信息。

    * 获取客户端 IP 地址，再通过 IP 取得用户所在的地理信息。

    * 用 `StringBuilder` 构建日志字符串，拼上 IP、用户名、状态与 message。

    * 通过 slf4j 把日志信息输出到控制台。

* **落库系统访问记录表**

    * 只输出到控制台不够，还要把登录信息保存到 `sys_logininfor` 表；字段有自增 id、用户账号、用户登录 IP、登录地点、浏览器类型、操作系统、登录的状态、提示信息、访问时间。

    * 代码里通过 User-Agent 拿到操作系统和浏览器信息，封装成 `SysLogininfor` 实体类逐个 set，与表字段一一对应。

    * 登录状态需要转换：成功是 `0`，失败是 `1`。

    * 最后同样通过 Spring 工具类 `getBean` 从 IOC 容器获取记录登录日志的 Service 对象，调用 `insert`，最终落到 Mapper 的 `insertLogininfor` 用 SQL 插库。

    * 完整链路：异步线程工厂生成任务 → 交给异步任务管理器 → 线程池延迟 10ms 多线程执行 → 任务内从容器取日志 Service → 写库，若依提供的登录日志界面即可查到成功与失败记录。
