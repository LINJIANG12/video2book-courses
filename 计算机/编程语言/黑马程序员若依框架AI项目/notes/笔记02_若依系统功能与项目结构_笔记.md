# 若依系统功能与项目结构

## 权限控制模型

### RBAC 授权模型

* **权限控制（Permission Control）**

    * > **定义**：让不同角色、不同岗位的账号登录同一系统后看到的菜单互不相同的功能级授权手段。

    * 判定效果：超级管理员、市场专员、销售专员三类账号登录后，各自只看到本岗位相关的菜单。
    * 若依已经把权限控制的代码写好，使用时只做配置即可，不必编写复杂授权逻辑。
    * 对应的三块功能：用户管理、角色管理、菜单管理。

* **RBAC（Role-Based Access Control，基于角色的访问控制）**

    * > **定义**：把「角色」插在用户与菜单之间的一层授权模型——用户关联角色，角色关联菜单。

    * 直连授权的问题：入职配一次、离职撤一次，新增一个公共菜单要逐个改 N 个账号。
    * 引入角色后：新人入职只需分配一个角色；角色上提、职责变大时，再叠加第二个角色即可获得更大的权限范围。
    * 角色一旦与菜单绑定，其管理的菜单就是固定的，员工只需跟角色打交道。

### 粗粒度与细粒度

* **粗粒度权限**

    * > **定义**：以角色（RBAC）为依据的权限控制，决定不同用户登录后能查看哪些菜单。

* **细粒度权限**

    * > **定义**：以「部门 + 岗位」为依据的权限控制，决定员工登录后能查看哪些数据。

    * 例：销售部门的主管登录后可查看本部门全部数据，普通员工只能查看自己的。
    * 细粒度涉及的源码较多，先作为了解。

* **两类粒度对照**

    | 粒度 | 依据什么 | 效果 |
    | :--- | :--- | :--- |
    | 粗粒度 | 角色，即 RBAC | 不同用户看到的菜单有所区别 |
    | 细粒度 | 部门 + 岗位 | 员工看到的**数据**有所区别 |

### 五张表与登录链路

* **三张主体表**

    * 用户表（员工表）、角色表、菜单表。

* **两张中间表**

    * 用户角色中间表、角色菜单中间表。
    * 一个员工可关联多个角色，一个角色也可被多个员工关联；一个角色可关联多个菜单，一个菜单也可被多个角色关联——两组关系都是多对多，必须建中间表维护。

* **登录链路**

    * 用户登录 → 查用户角色中间表得到他拥有的角色 → 按角色查角色菜单中间表得到他拥有的菜单 → 由此确定登录后可见的菜单。

* **附加的表**

    * 若除上述五张外还提供部门表、岗位表、角色部门中间表、用户岗位中间表。

## 权限配置三步流程

### 菜单的创建

* **菜单类型（Menu Type）**

    * 目录菜单：点击后展开二级菜单，本身不做页面跳转。
    * 页面菜单：点击后展示页面。
    * 按钮菜单：点击后是一个按钮操作。

* **上级菜单（Parent Menu）**

    * 首页、系统管理、系统监控这类顶级分类称为主类目，与它们同属最外层几个菜单栏。
    * 页面菜单不能挂在主类目下，要挂到某个目录菜单之下，形成父子路由地址。

* **关键表单项**

    * 显示排序：值越小，排名越靠前。
    * 是否外链：选「否」表示当前目录是内部的。
    * 路由地址：页面组件之间的跳转方式；目录菜单用它管理所有二级嵌套子菜单，可建立父子路由。
    * 显示状态：可选显示正常。
    * 组件路径：页面菜单最终还需要它来完成页面展示。

### 角色的创建与菜单授权

* **角色表单字段**

    * 角色名称、权限字符串（与后台权限控制相关）、角色顺序、状态、菜单权限。

* **菜单权限的父子联动**

    * 勾上目录，它下面的二级页面跟着勾上；勾上二级页面，三级按钮跟着勾上。
    * 目录、页面、按钮三种类型都可以在角色里勾选授权。

* **多角色授权**

    * 一个用户可关联多个角色，权限范围因此可以更细。

### 用户的创建与角色关联

* **三个必填项**

    * 用户昵称、归属部门、用户名（即登录账号）。

* **可选项**

    * 手机号、邮箱可留空；性别、状态、岗位走默认值。
    * 密码可与超级管理员保持一致，方便测试登录。

* **角色关联**

    * 创建时勾选目标角色，用户登录后就只能看到该角色所辖菜单，其余菜单全部隐藏。

* **验证**

    * 退出管理员账号，用新用户重新登录并输入验证码验证菜单裁剪效果。

## 数据字典

### 静态数据与字典价值

* **静态数据（Static Data）**

    * > **定义**：不经常变动的数据，例如性别男、女、未知，状态正常、关闭；可简单理解为 Java 中的静态变量。

    * > **易错点**：把这类值直接写死在页面上会失去复用性——添加用户要选状态，添加菜单也要选同一批状态，写死就得改两处；想把「正常、停用」改成「开启、关闭」更要去逐处修改。

* **数据字典（Data Dictionary）**

    * > **定义**：把静态数据存进数据库统一维护的功能模块。

    * 一处编写、多处使用，实现数据复用性。
    * 要改显示文案时只改字典一处，不动所有使用方的代码，系统更灵活、维护更容易。

### 字典类型与字典数据

* **字典类型**

    * > **定义**：字典值所属的分类，例如「男、女、未知」这批值的分类叫「性别」。

    * 操作路径：先建字典类型，再点进该类型添加它下面的字典数据。

* **字典数据**

    * > **定义**：某个字典类型下的具体字典值，例如「性别」下的男、女、未知。

* **两张表的关联**

    * 字典类型表与字典数据表通过主外键建立一对多关系：按「用户性别」这个字典类型可查出对应的男、女、未知三条字典数据。

* **新增后的落位**

    * 新建的字典类型默认排在第二页，因为第一页已被自带数据占满。

### 字典标签与字典值

* **字典标签（Dict Label）**

    * > **定义**：最终展示给用户做选择用的文案，例如性别栏里的男、女或未知。

* **字典值（Dict Value）**

    * > **定义**：用户选择后真正提交、并写入数据库的值，性别对应 0、1、2。

    * 用户表不存汉字，只存 0、1、2，可降低存储空间、提升磁盘利用率。
    * 拿到字典值可以反查字典标签，这是系统优化的设计思想。

* **存量数据改造**

    * > **易错点**：字段改成数据字典后，数据库里的存量文本必须同步改成字典值。页面上按 JavaEE 搜索时提交的条件是字典值 0，而库里存的还是「JavaEE」文本，查询会返回空。

    * 改完数据库记得提交事务，再回页面验证。
    * 改完后页面展示字典标签、数据库存字典值，两边各得其所。

### 学科字段改造案例

* **适用条件**

    * 静态数据、不经常修改、内容是长文本——符合这三条才值得交给数据字典。

* **四个步骤**

    * 第一步：结合页面原型设计字典类型与字典数据，先定好字典标签与字典值的对应关系。
    * 第二步：在代码生成器里把该字段的显示类型由文本框改为下拉框，并选中刚建好的字典类型。
    * 第三步：下载最新代码。因为后端与动态菜单和入门案例一致，只需要覆盖前端的视图组件。
    * 第四步：把数据库里的存量文本改成对应字典值，并提交事务。

* **示例取值**

    * 字典类型名称「学科」，字典类型 `cos_subject`。
    * JavaEE → 0、Python+大数据 → 1、鸿蒙应用开发 → 2，排序依次 1、2、3，备注与标签保持一致。

* **推广**

    * 「适用人群」字段性质与学科相同，同样符合静态数据条件，可以照搬这套四步改造。

## 参数设置、通知公告与日志管理

### 参数设置

* **参数设置（Parameter Setting）**

    * > **定义**：对系统参数做动态维护——不修改源码、不重启服务器，改完立即生效。

    * 单条参数包含参数名称（描述作用）、参数键（用于按键查询与修改）、参数值、备注。
    * 验证码开关：`true` 表示开启，`false` 表示关闭，默认值是 `true`，所以后台登录界面默认带验证码校验。
    * 是否开启用户注册功能：默认关闭，用户一般由管理员新增；要开启就置为 `true`。

* **注册入口**

    * 注册界面路由是 `/register`，但让用户手输地址不方便。
    * 登录界面自带一个「立即注册」跳转链接，默认是隐藏的。
    * 打开方式：在前端登录页的视图组件里把注册开关改成 `true`，保存后登录页即出现该链接。

* **缓存影响**

    * 若依提供了缓存以提升访问性能，改完字典或参数需要刷新浏览器才能看到新值。

### 通知公告

* **功能范围**

    * 管理员可以编辑、修改、删除通知与公告，再以邮件形式传达给用户。
    * 公告类型（通知、公告）同样由数据字典维护，可以再增加一栏新闻。
    * 正文使用富文本编辑器，支持超链接、图片与视频链接。

* **半成品定位**

    * > **定义**：若依只实现了管理员录入这一半，通知的发布查看界面与发送邮件的代码需要二次开发。

    * 原因是各公司需求不同：A 公司要邮件形式，B 公司要登录后弹框提示公告，还有的要对接微信、QQ 等平台。

### 登录日志与操作日志

* **登录日志**

    * 记录当前登录用户、登录地点、登录时间、操作系统、浏览器，以及本次登录是成功还是失败，可监控每一个用户的登录行为。

* **操作日志**

    * 记录用户访问了哪个系统模块、在该模块下做了什么操作（新增、删除还是修改）、执行该方法所耗时的时间。
    * 还保留非常详细的操作参数：传递了什么参数、返回了什么结果，出现风险时可据此快速定位。

* **日志膨胀与清理**

    * > **易错点**：日志保存在数据库表里，系统长期运行记录会越来越多，对数据库的负载压力越来越大；点「清空」按钮会全部删掉，事后想追溯就没有数据了。

    * 对策：用定时任务按每周、每月、每季度导出日志做文本备份。
    * 并建议在前端把「清空」按钮关闭。

## 系统监控

### 在线用户与缓存列表

* **在线用户**

    * > **定义**：展示当前登录用户的名称、所属部门、登录 IP、登录地点、操作系统、浏览器以及登录时间。

    * > **结论**：在线用户页面本身不查数据库，只是把登录那一刻写进 Redis 的用户信息原样查出来。

* **缓存列表**

    * 罗列当前 Redis 里缓存的全部 key 与缓存值，可查看也可操作。
    * 除在线用户信息外，参数配置（如验证码开关）、数据字典（如学科）也都在缓存里。

* **数据流向**

    * 用户登录成功 → 写入 Redis；在线用户页面与缓存列表页面都是从 Redis 里读。
    * 页面上每一条在线用户，都严格对应 Redis 里的一条缓存记录，而不是数据库里的一条用户记录。

### 缓存监控与服务监控

* **缓存监控**

    * > **定义**：帮助了解 Redis 使用情况的监控页，分基本信息、命令统计、内存信息三块。

    * 基本信息含 Redis 版本、运行模式（单机还是集群）、单机端口 6379、当前客户端连接数、运行时间、使用内存。
    * 使用内存还提供图表呈现内存消耗，另有命令使用占比。

* **服务监控**

    * > **定义**：实时查看服务器各项指标的页面。

    * 指标包含 CPU 利用率、内存使用情况、服务器基本信息、Java 虚拟机运行环境、磁盘运行状况。

* **两者分工**

    * > **结论**：缓存监控回答「Redis 自己用得怎么样」，服务监控回答「这台机器跑得怎么样」。

### 数据监控

* **数据监控（Druid）**

    * > **定义**：若依集成的 Druid 提供的 Web 监控工具，不是若依自己开发的，进入需要二次登录。

    * 账号密码配在 Druid 的配置文件里，不在若依的业务数据中；长文给出的示例是账号 `ruoyi`、密码 `123456`。
    * 数据源：查看连接池配置，如最大连接数、初始化连接数、最小空闲连接数。
    * SQL 监控：记录 SQL 执行信息，帮助快速发现慢 SQL 日志并做优化。
    * SQL 防火墙：通过 SQL 拦截机制防止错误 SQL 执行。例如更新条件漏写 `where id` 会导致整张表被更新，通过拦截可避免这类事故。
    * Web 应用监控：最大并发数、请求连接次数、请求地址。

* **四层视角**

    * > **定义**：在线用户与缓存列表看「Redis 里存了什么」，缓存监控看「Redis 自己跑得怎么样」，服务监控看「服务器跑得怎么样」，数据监控看「数据库这一层用得怎么样」。

## 系统工具

### 表单构建的三栏与栅格

* **三栏布局**

    * 左侧：基于 Element UI 的表单组件，分输入型、选择型、布局型。
    * 中间：拖拽后的页面效果，与最终看到的结果几乎一致。
    * 右侧：当前表单项的名称与属性设置，含标题、字段名、必填、只读、禁用、正则表达式校验、错误提示。

* **行容器与栅格**

    * 默认每个表单项独占一行。
    * 布局型组件里的「行容器」可以让一行内放多个表单项，它基于 Element UI 栅格系统，最大占用 24 分。
    * 一行放两个表单项时各占 10 分；单个表单项占满整行时用 24 分。

* **表单属性**

    * 表单对象名称默认是 `formRef`，可以修改；还能调整大小与对齐方式。
    * 默认自带提交按钮和重置按钮。

* **字段命名**

    * > **易错点**：字段名不能随便起，要参考页面原型对应的表结构与数据库一一对应，或与前端 DTO 对应。界面上显示的是标题，真正提交上去的是字段名，两者不是一回事。

### 表单页面的三步落地

* **第一步：制作并导出**

    * 支持两种导出形态：生成独立页面访问，或以弹框形式点击按钮弹出对话框。

* **第二步：复制进前端工程**

    * 下载后改名（例如 `add`），粘贴到前端工程 `views` 下的对应业务目录。
    * 把粘贴后的目录路径记下来，第三步配置动态菜单要用。

* **第三步：创建动态菜单**

    * 添加课程是页面跳转的菜单，所以菜单类型选「菜单」，不是目录也不是按钮。
    * 路由地址用于页面之间的视图组件跳转；组件路径指定由路由地址跳到哪个位置的视图组件。

* **组件路径的约束**

    * > **易错点**：组件路径不能随便写，必须参考前端 `views` 下面的目录层级来写，否则菜单点开就是空白。

### 代码生成的三种模板

* **单表模板**

    * 数据关系是一张表，解决分页 + 条件查询 + 增删改查的基础需求。
    * 入门案例的课程表用的就是它，是最简单的一种。

* **树表模板**

    * > **定义**：一种展示层级数据的表格，能展开也能折叠，清晰呈现父子关系；若依内置的菜单管理和部门管理就是树表式设计。

    * 适用于数据之间存在层级关系的场景，如若依科技 → 深圳总公司 / 长沙分公司 → 市场部 / 财务部。
    * 手写麻烦：要查询并计算数据之间的父子关系返回前端，还要做层级遍历展示。

* **主子表模板**

    * 数据关系是一对多，解决一次提交两张表的需求，典型是菜品表 + 口味表。
    * 单表生成器做不到；改用表单工具只能省掉前端部分，JS 与后端代码仍要自己写。

* **模板与需求的匹配**

    | 模板 | 数据关系 | 典型例子 | 解决什么麻烦 |
    | :--- | :--- | :--- | :--- |
    | 单表 | 一张表 | 课程表 | 分页 + 条件 + 增删改查 |
    | 树表 | 层级父子 | 部门表 | 算父子关系、层级遍历展示 |
    | 主子表 | 一对多 | 菜品表 + 口味表 | 一次提交两张表 |

### 树表模板的三个字段

* **parent_id 的含义**

    * > **定义**：`parent_id` 是层级关系里的那条「指针」——谁的 `parent_id` 等于我的 `id`，谁就是我的下级；`parent_id = 0` 表示上面没人，自己就是根。

    * 示例：若依科技 id=100、parent_id=0；深圳总公司与长沙分公司 parent_id=100；长沙分公司 id=102；市场部与财务部 parent_id=102。

* **三个字段的固定规则**

    * 树的编码字段 = 树表的主键（示例中选部门 ID）。
    * 树的副编码字段 = 该表的 `parent_id`。
    * 树的名称字段 = 最终展示给页面的字段（示例中选部门名称）。

* **配置与验证**

    * 导入表后点「编辑」，在生成信息里把生成模板由单表改为树表，多出的三栏按上面规则选好，提交后即可下载生成。
    * 界面上有「预览」按钮，可直接看前端视图是否为树形可折叠结构。

### Swagger 在线接口文档

* **系统接口（Swagger）**

    * > **定义**：根据编写的 Controller 代码自动生成 API 在线文档，并提供外部界面直接调用与测试接口的工具。

    * 前端可据此查看每个接口的请求方式、请求路径、请求参数，并查看响应结果。
    * 后端可据此做功能测试，不一定再单独用 Postman 等工具。
    * 界面上默认只出现若依预置的 `test controller`。

* **注解缺失的原因**

    * > **结论**：`@Api` 标在类上、`@ApiOperation` 标在方法上，Swagger 才知道这个 Controller 叫什么、每个接口干什么用；没加注解的 Controller 在文档里自然一片空白。

* **401 与 404**

    * > **易错点**：直接执行返回 401 认证失败——Swagger 在线测试是独立请求，不走前端，没有做用户认证，也就没有 token。

    * token 存在浏览器 cookie 里，cookie 名称为 `Admin-Token`；F12 打开 application 取到值，填进「增加授权」后再执行。
    * 加了 token 后出现 404 请求资源未找到——Swagger 生成的测试文档带了 `/dev-api` 前缀，而 Controller 代码上没有这个前缀。
    * 解决办法：在配置文件的 Swagger 配置里（约第 120 行处）去掉该前缀，重启后端，刷新浏览器页面，并重新复制一次 token。
    * 改完最终返回状态码 200、操作成功，并返回测试用户数据。

* **后续替代**

    * 这个界面后期用得不多，因为界面太丑且多个 Controller 不好操作；后续会用 Knife4j 与 Swagger 集成，提供更友好的文档阅读与接口测试界面。

## 后端工程模块划分

### ruoyi-admin 启动入口

* **ruoyi-admin**

    * > **定义**：整个后端的启动入口，把它运行起来整个项目就跑起来了。

    * 代码分两块：通用功能的 controller 包，放后台登录、权限控制、数据字典相关的 controller 类，只负责接收前端请求并作出响应；以及两个启动类。

* **RuoYiApplication**

    * 运行方式：基于 Spring Boot 内置的 Tomcat 直接运行。
    * 用途：常规开发和部署都用它。

* **RuoYiServletInitializer**

    * 运行方式：把 Spring Boot 功能打成 war 包。
    * 用途：丢进外置 Tomcat 里跑。
    * 触发条件：部署环境给的是外部 Tomcat、且不能把 fat jar 塞进去。

* **两个启动类的取舍**

    * > **结论**：不是「两个都要用」，而是「看部署方式选一个」，开发阶段基本只碰第一个。

### ruoyi-common 通用工具

* **模块定位**

    * 装全项目公用的东西，跟业务无关，所以别的模块都能放心依赖它。

* **包职责**

    | 包 | 放什么 |
    | :--- | :--- |
    | `annotation` | 项目中自定义的注解 |
    | `config` | 全局配置类，负责读取项目配置文件信息 |
    | `constant` | 通用的常量类信息 |
    | `core` | 核心控制代码 |
    | `enums` | 通用枚举 |
    | `exception` | 自定义异常类型，如用户相关异常、任务相关异常 |
    | `utils` 等工具包 | 日期、日志、分页、过滤器相关工具类 |
    | `xss` | 防止跨站脚本攻击的工具 |

* **core 包**

    * > **定义**：通用工具模块里最核心的包，将来写的所有基础代码都跟它有关系。

    * `BaseController`：所有业务 controller 都要继承的基类。
    * `AjaxResult`、`BaseEntity`：实体类定义的统一返回结果。
    * `TableDataInfo`：分页返回的统一结果对象。

* **扩展方式**

    * 自己项目里的自定义常量、自定义枚举可以往 `constant`、`enums` 里放。
    * 工具类或异常类型不够用时直接往对应包里加，不必另起炉灶。

### ruoyi-framework 框架核心

* **模块定位**

    * 这里全是框架核心代码，重要程度上比通用工具再上一个台阶；登录、权限认证的业务代码也落在这一块。

* **aspect**

    * 自定义的 AOP 代码，全是切面类，想对方法做增强就放这里。

* **config**

    * Spring Boot 集成第三方组件后的配置文件：Redis 相关、MyBatis 相关都在这里。
    * 想连多个数据库（多数据源）、配置拦截器、异步处理（多线程）同样在这里配。

* **security**

    * Spring Security 权限控制，结合 RBAC 模型做粗粒度与细粒度权限控制。

* **web**

    * 前端相关的控制，以及自定义的全局异常处理器。

### 其他业务模块

* **ruoyi-generator**

    * 代码生成器相关内容，是单独拎出来的模块；不想用代码生成器可以直接移除，不影响若依整体运行。

* **ruoyi-quartz**

    * 定时任务相关内容，同样可单独移除而不影响整体运行。

* **ruoyi-system**

    * 系统模块的业务代码：业务层、持久层、实体类，再跟后台服务的 controller 组合，实现权限控制与后台登录。

* **ruoyi-ui**

    * 前端工程，不是后端模块。

### 模块依赖链

* **只启动 admin 的原因**

    * 只启动 `ruoyi-admin` 一个服务，代码生成、定时任务、权限控制却全部生效，答案在 `pom.xml` 的依赖关系里。

```text
                      ruoyi-admin
                     （程序入口）
                          │
        直接依赖 ┌─────────┼─────────────┐
                │         │             │
        ruoyi-framework  ruoyi-quartz   ruoyi-generator
        （框架核心）       （定时任务）      （代码生成）
                │
                │ 直接依赖
                ↓
          ruoyi-system
          （系统模块）
                │
                │ 直接依赖
                ↓
          ruoyi-common
          （通用工具）
```

* **三步验证依赖链**

    * 在 `ruoyi-admin` 的 `pom.xml` 依赖里能看到 framework、定时任务、代码生成这三个直接依赖。
    * `Ctrl` 点 framework 模块名跳进它的 `pom.xml`，能看到 system。
    * 再 `Ctrl` 点 system，里面就是 `ruoyi-common`。

## 前端工程结构

### 外围三样

* **vite.config.js**

    * Vue 项目配置信息，如设置前端端口、向后做代理转发。
    * 一般项目打包之后不会再修改，知道就行。

* **package.json**

    * 前端项目配置文件，含项目名、版本号、依赖包，类似 Maven 项目的 `pom.xml`。
    * 想用第三方依赖、想指定版本信息都在这个文件里设置。

* **node_modules**

    * 下载下来的第三方依赖包都放在这里，别误删。

### src 目录

* **动手范围**

    * > **结论**：后端工程师在 `src` 下面真正操作的只有 `api` 和 `views` 两个目录，再了解一下 `router` 就可以了。

* **api**

    * 存放所有请求的 js 文件，主要是向后端发送请求的代码——必须动手。

* **views**

    * 视图组件，课程管理、添加课程的表单独立页面都在这儿——必须动手。

* **router / assets / components**

    * `router` 是视图组件之间的路由代码，了解一下即可。
    * `assets` 是静态资源，如图片、字体，知道就行。
    * `components` 是前端通用组件，先跳过。

* **App.vue 与 main.js**

    * `App.vue` 是 Vue 的根组件，项目中所有页面和视图都基于它构建，知道是入口就行。
    * `main.js` 是 Vue 的应用入口文件，负责创建应用实例并设置生命周期，知道是入口就行。
    * 两者组合成完整的 Vue 应用：一个负责定义结构与外观，一个负责设置应用的运行规则与行为。

## 课程管理前端源码

### 视图模板的五个区域

* **代码生成的前端产物**

    * 基于代码生成器生成的前端代码只有两个文件：`course.js`（向后端发 Ajax 请求的 API 接口代码）与 `index.vue`（浏览器里展示课程管理的视图组件）。

* **两个标签页**

    * `template` 存放前端展示的各个组件标签，`script` 编写业务逻辑代码。

* **五个区域**

    * ① 搜索栏区域（查询条件 + 搜索/重置）
    * ② 按钮区域（新增/修改/删除/导出/刷新/展开）
    * ③ 数据表格展示区域（含操作列）
    * ④ 分页栏区域（总条数 + 页码 + 每页条数）
    * ⑤ 新增和修改对话框（表单）

### 搜索栏与按钮区

* **el-form 的关键属性**

    * `:model`：双向绑定，把前端录入的查询条件封装给响应式对象 `queryParams`。
    * `v-show`：控制搜索栏显示还是隐藏，由 `showSearch` 决定，`true` 显示、`false` 隐藏。

* **el-input 的四个属性**

    | 属性 | 作用 |
    | :--- | :--- |
    | `v-model="queryParams.code"` | 课程编码双向绑定，输入值绑到 `code` 上 |
    | `placeholder` | 灰色文本占位提示信息，如「请输入课程编码」 |
    | `clearable` | 清理已输入内容，恢复到占位符提示 |
    | `@keyup.enter` | 回车事件，调用 `handleQuery` 完成搜索，等同于点搜索按钮 |

* **el-option 的绑定**

    * `v-for` 遍历课程学科的字典数据列表，展示 Java、Python、大数据、鸿蒙应用开发等选项。
    * `label` 是字典标签，展示给用户；`value` 是字典值，用户选完提交给后端。
    * 搜索按钮调 `handleQuery` 完成条件查询；重置按钮把整个表单项内容全部清空。

* **按钮区的属性与指令**

    | 属性 / 指令 | 作用 |
    | :--- | :--- |
    | `type`、`plain`、`icon` | 控制按钮颜色样式与图标 |
    | `@click` | 点击事件，触发后调用对应方法 |
    | `v-hasPermi` | 自定义属性，结合 RBAC 权限模型完成菜单按钮的显示或隐藏 |
    | `:disabled` | 控制该按钮是否可用，结合 JS 代码做动态控制 |

* **修改按钮的差异**

    * 修改按钮比新增按钮多一个 `:disabled`：只有勾选了表格复选框它才可用，没勾选就是不可用。

* **RightToolbar 组件**

    * 第一个按钮触发 `showSearch` 修改，控制搜索栏显示还是隐藏。
    * 第二个按钮触发 `queryTable` 事件、调用 `getList`，重新加载表格数据。

### 数据表格区与字典插槽

* **el-table 的三个属性**

    | 属性 | 类型 | 作用 |
    | :--- | :--- | :--- |
    | `v-loading` | 指令 | 控制表格加载状态，网络慢时给出友好提示 |
    | `:data` | 绑定属性 | 指定数据源，如后端返回的 `courseList` |
    | `@selection-change` | 事件监听器 | 监听选中行的变化 |

* **列标签**

    * 第一列不是数据本身，是复选框，通过 `type="selection"` 指定，列宽 55 像素、居中对齐；勾选后触发事件调用 `handleSelectionChange`。
    * 从第二列开始用 `label` 指定列标题、`prop` 指定该列展示的具体内容，如课程 ID、课程编码。
    * 注释掉某一列代码即可让该列在页面上隐藏。

* **模板插槽（Slot）**

    * > **定义**：数据库存的是字典的值，页面展示的是字典的标签，二者的转换由模板插槽完成。

    * 通过 `scope` 拿到整个表格的数据并取出当前行的 `row.subject`（字典值），交给 `<dict-tag>` 组件。
    * `dict-tag` 拿字典值去匹配字典数据列表，找到对应的字典标签再显示到前端页面。
    * 操作列也用了模板插槽，其中修改按钮的 `@click` 绑定 `handleUpdate`，把当前行数据传给该方法。

### 分页栏与新增修改对话框

* **el-pagination 的属性**

    | 属性 | 作用 |
    | :--- | :--- |
    | `v-show` | 接口返回数据大于 0 条时才显示分页栏，否则隐藏 |
    | `:total` | 展示总条数，由后端查询返回 |
    | `v-model:page` | 展示页码 1、2、3、4、5，并对当前页高亮 |
    | `:page-size` | 限制每页条数，默认 10 条 |
    | `@pagination` | 分页事件，改每页条数或跳页时调用 `getList` 重新查询 |

* **el-dialog 的属性**

    * 默认在页面隐藏，点新增按钮通过双向绑定把 `open` 改成 `true` 才弹出。
    * 宽度 500 像素，`append-to-body` 把对话框元素添加到 `body` 上。

* **对话框标题**

    * > **定义**：标题不是写死的，而是属性动态绑定，目的是让新增与修改共用同一个对话框。

    * 点新增显示「添加课程管理」，点修改显示「修改课程管理」。

* **对话框内的表单**

    * `:model="form"` 做双向绑定，用户输入的课程编码、课程学科等封装给 `form` 对象。
    * `:rules="rules"` 是校验规则，如必填校验，用户没填就点提交会进行校验；还指定了 `label-width`。
    * 点确定提交，点取消关闭对话框。

### script 中的响应式对象

* **第一行的 import**

    * 引入课程管理的 API 接口文件，里面包含若干个方法。

* **getCurrentInstance**

    * 返回当前实例的代理对象 `proxy`，可以访问整个视图组件的数据内容并调用它的方法。

* **数据字典加载**

    * 紧接着调用查询课程学科的数据字典，把列表封装给 `courseSubject`，供下拉框展示。

* **ref 定义的响应式对象**

    | 变量 | 默认值 | 作用 |
    | :--- | :--- | :--- |
    | `courseList` | 空 | 列表数据，接收后端返回的课程列表供表格遍历 |
    | `open` | `false` | 是否显示新增和修改对话框 |
    | `loading` | `true` | 表格加载状态，网速不好时改善体验 |
    | `showSearch` | `true` | 是否显示搜索栏 |
    | `ids` | 空数组 | 存放选中的多个复选框 id，用于批量删除 |
    | 两个禁用标记 | `true` | `true` 表示按钮不可用，`false` 表示可用 |
    | `total` | 0 | 接收后端返回的总条数 |
    | `title` | — | 区分新增或修改对话框的标题 |

* **reactive 定义的 data**

    * 包含三个属性：`form` 接收新增或修改的表单双向绑定数据，`queryParams` 接收搜索条件参数，`rules` 是表单校验规则。
    * 为了方便分别操作，又把这个 `reactive` 对象转换成 `ref`，从而能单独操作表单部分、参数部分和校验规则。

### 视图组件中的方法串联

* **getList（查询列表的核心方法）**

    * 四步：`loading` 置为 `true` 打开表格加载状态；调 API 的 `listCos` 把前端录入参数作为条件传过去；后端返回结果封装给 `response` 对象，包含课程列表和总条数两部分；最后把 `loading` 置为 `false` 隐藏加载状态。

* **取消按钮与表单重置**

    * 两者组合使用：先把对话框设为隐藏 `false`；再调 `resetForm`，先清空双向绑定的 `form` 对象内容，再把表单显示内容也重置掉，方便下次点修改时回显最新数据。

* **handleQuery（搜索按钮）**

    * 先把当前页置为第一页，再调 `getList`——上一次与本次的查询条件可能不同，最新条件应从第一页开始查。

* **handleReset（重置按钮）**

    * 将搜索框的表单数据全部清空，再调 `handleQuery`，完成一次无条件的搜索查询。

* **handleSelectionChange（多选）**

    * 用户勾选复选框触发事件，把选中的行对象传过来，调它的 `map` 方法遍历取得每一个课程 id，封装给 `ids` 响应式数组对象。

* **禁用标记的判定规则**

    * 选中长度为 1 时置为 `false`，修改和删除按钮才可用。
    * 选中两条或三条时仍为 `true`、默认不可用。
    * 为修这个 bug 另有一段判断：只要长度大于零就置为 `false`，因为修改按钮是支持批量操作的。

* **handleAdd（新增按钮）**

    * 将原有表单数据全部清空，打开对话框，标题设为「添加课程管理」。

* **handleUpdate（修改按钮）**

    * 接收当前行对象或选中行的 id；先重置表单，再调 API 按 id 到后台查询，把课程详情封装给 `response` 对象，在表单中回显，然后打开对话框，标题设为「修改课程管理」。

* **提交按钮（新增与修改共用）**

```text
点击确定
   │
   ▼
第一步：表单规则校验（正则规则、是否必填项）
   │      校验不通过 ─→ 直接中断，什么都不做
   │ 通过（valid = true）
   ▼
第二步：判断表单对象里有没有 id
   ├── 有 id ──→ 一定是修改操作（因为回显时详情里带了 id）
   │              调 API 的修改方法 → 成功 → 关闭对话框 → 再执行一次查询，展示最新内容
   └── 无 id ──→ 走新增的 API 方法      → 成功 → 关闭对话框 → 再执行一次查询，展示最新数据
```

* **删除按钮**

    * 支持单个和批量删除，拿到的 `row` 可能是一行取出的一个 id，也可能是数组。
    * 为防误操作先弹确认框做二次确认；确认后调 `deleteCos` 完成删除，删除成功再执行一次查询，并给页面提示「删除成功」。

* **导出按钮与初始化方法**

    * 导出按钮把表格内容导出成 Excel 文件，便于汇总和统计。
    * 最后一个方法在页面加载时执行，查询课程管理列表。

### API 文件的五个方法

* **request 请求工具类**

    * > **定义**：封装了 Ajax 基础代码（含请求拦截器和响应拦截器）的工具类，将来每一个请求都要用它。

    * 封装的意义在于不必在每个方法里重写一遍 Ajax 基础代码，简化书写、提高效率。

* **查询课程列表（listCos）**

    * 接收用户输入的参数封装给 `query` 对象，调用工具类把参数传过去，向后台发送请求完成查询，并返回给前端展示。

* **查询课程详情**

    * 用户点修改按钮时按 id 查询，把课程详情返回给前端，让对话框能展示原有数据、方便修改。

* **新增课程管理**

    * 用户点新增按钮、在弹框里输入课程信息后点确定，把数据封装给 `data` 对象发往后台，返回添加成功或失败的操作结果。

* **修改课程管理**

    * 与新增非常类似，区别是 `data` 里比新增多一个 id，然后以 id 为条件更新数据库，再把更新结果返回给前端。

* **删除课程管理（deleteCos）**

    * 支持批量删除和单个删除：点某一行右侧的删除按钮会传递课程 id，也能接收多个选中的课程 id 数组，一样能向后端发送请求并返回删除结果。

## 课程管理后端源码

### 四个文件四种职责

* **Controller**

    * 主要用来接收前端请求，调用 service 处理业务逻辑并返回结果，共提供六个方法。

    | 方法 | 请求方式 | 干什么 |
    | :--- | :--- | :--- |
    | 查询课程管理列表 | GET | 拿请求参数，调 service 实现分页查询并返回分页结果 |
    | 导出课程管理列表 | POST | 拿请求参数，调 service 生成 Excel 文件完成下载 |
    | 获取课程管理详细信息 | GET | 根据 id 查询，调 service 后返回查询结果 |
    | 新增课程管理 | POST | 拿表单请求参数，调 service 完成新增并返回结果 |
    | 修改课程管理 | PUT | 拿表单实体，调 service 实现更新并返回结果 |
    | 删除课程管理 | DELETE | 拿 id 数组，调 service 完成批量或单个删除 |

    * > **结论**：这六个方法遵循 RESTful 风格——GET 是查询，POST 是新增，PUT 是修改，DELETE 是删除。

* **Service 接口**

    * Controller 调用的都是 service 接口里的方法，它们只是方法签名声明，规定方法定义（接收 id 查详情、接收条件查集合、新增、修改、删除），具体业务由实现类完成。
    * > **注意**：新增、修改和删除这些方法返回 `int` 类型——对数据库的增删改会返回影响的行数，行数大于 0 表示成功，否则是失败，程序据此给用户提醒。

* **Service 实现类**

    * 实现接口并重写所有抽象方法，然后调用 mapper 完成数据库操作。
    * 按 id 查询直接调 mapper 返回结果；按条件查询返回集合；新增和修改涉及自动填充创建时间与修改时间；删除支持批量数组也支持单个。
    * 具体 SQL 操作都在 mapper 中实现。

* **Mapper 接口与 XML 映射文件**

    * 方法签名跟 service 的接口和实现类命名一致，每个方法对应的 SQL 都生成到 XML 映射文件里。
    * 最上面是统一的 `resultMap`，下面是抽取的 SQL 公共片段，再下面是 `select` 查询和 `insert`，通过 XML 动态 SQL 做到通用性与灵活性。

* **实体类 Course**

    * 继承了一个基类，属性跟数据库表字段一一对应，完成 XML 的自动映射封装。

### 两个额外注解

* **@Log**

    * > **定义**：用于记录用户操作日志的注解，用户在这里删除一个课程这类操作会被记录下来。

    * 实现细节涉及 Spring 的 AOP 和异步管理器。

* **@PreAuthorize**

    * > **定义**：Spring Security 安全框架提供的注解，用于做权限校验控制。

* **共性**

    * 这两个注解叠加在 Spring MVC 基本注解之上，是每个方法里除接收请求之外多出来的部分。

### 分页的实现原理

* **Controller 的三行代码**

    * 开启分页；调 service 查询课程列表、把条件传过去并返回 `list` 集合；返回表格的分页数据对象。

* **BaseController 的来源**

    * 「开启分页」和「返回分页数据对象」都来自 web 层通用的数据处理类 `BaseController`，所有业务 Controller 默认都继承它，继承后其公开的属性方法都可以使用。

* **BaseController 的三类能力**

    | 类别 | 提供的能力 |
    | :--- | :--- |
    | 分页相关 | 开启分页、开启分页排序、清理线程内的分页数据 |
    | 返回结果相关 | 返回分页对象、返回操作成功信息（`success` 的多个重载）、返回操作失败信息 |
    | 获取登录用户相关 | 获取登录用户信息、获取用户 id、获取用户所属部门 id、获取用户名 |

* **开启分页的内部四步**

    * 第一步：创建 `PageDomain` 对象接收前端分页参数（当前页、每页大小、排序条件等）。
    * 第二步：获取当前的页码和每页大小。
    * 第三步：取出分页条件并做转义处理，防止 SQL 注入攻击。
    * 第四步：把页码、每页大小、排序信息告诉 PageHelper——它是 MyBatis 的搭档，会自动对执行的 SQL 进行拦截实现分页逻辑。

* **PageHelper 的拦截机制**

```text
我们执行的查询（假设是课程列表）：
    select ... from course where ...

                  │
                  ▼
      PageHelper 拦截器自动拦截
                  │
        ┌─────────┴─────────┐
        │                   │
        ▼                   ▼
   截取中间内容，把 * 改成   在 SQL 末尾拼上 limit 关键字
   count 数量的统计操作            │
        │                        ▼
        ▼                 当前页的数据列表
    总记录数 total         List<Course>
        │                        │
        └─────────┬──────────────┘
                  ▼
        组合成一个分页的数据对象
```

* **结论**

    * > **结论**：service 只是按条件查询并返回一个 `list`，分页是由 PageHelper 插件在 SQL 层面自动做掉的。

### 两种统一返回对象

* **TableDataInfo（分页返回对象）**

    * > **定义**：分页查询专用的统一返回对象，四个属性是总记录数、列表数据、消息状态码、消息内容。

    | 字段 | 含义 |
    | :--- | :--- |
    | `total` | 总记录数 |
    | `rows` | 当前页的列表数据集合 |
    | `code` | 业务消息状态码 |
    | `message` | 业务操作信息 |

    * 这四个字段是与前端团队共同协商确定的分页对象标准数据格式，转成 JSON 后前端即可分页展示。
    * 前端拿到后先按 `code` 判断业务成功还是失败，成功则取出总条数和当前页集合渲染页面。
    * 返回过程：设置状态码 200 表示成功，提示查询信息，把 `list` 放进 `rows`，把分页插件拿到的总记录数设置给 `total`。

* **AjaxResult（非分页统一操作结果）**

    * > **定义**：非分页操作专用的统一返回对象，也叫操作消息提醒对象，三个属性是业务状态码、返回内容、数据对象。

    | 字段 | 含义 |
    | :--- | :--- |
    | `code` | 业务状态码，200 表示成功 |
    | `message` | 提示信息 |
    | `data` | 返回的数据对象 |

    * 课程修改时需要回写数据，就是从 `data` 里取出来在页面显示。

* **toAjax 与三元判定**

    * 增删改方法返回的仍是 `AjaxResult`，但调的不是 `success` 而是 `toAjax`，它接收 service 返回的影响行数。
    * `rows > 0` 调无参的 `success()`，只告诉前端「成功了」，不需要返回 `data`；否则调 `error()`，返回失败状态码 500 和提示信息。
    * > **结论**：200 表示成功，500 表示失败；`success` 和 `error` 都提供了方法重载，用于应对不同业务场景。

* **选用规则**

    * > **结论**：将来做分页查询，返回对象就叫 `TableDataInfo`；做非分页的操作，返回结果就是统一的 `AjaxResult`。

### BaseEntity 公共字段

* **来源**

    * 返回的课程数据里包含 `createBy`、`createTime`、`updateBy`、`updateTime`、`remark`，但这些实体属性没有在课程实体类里定义，而是由它继承的 `BaseEntity` 提供。

* **设计意图**

    * > **定义**：若依设计者认为每一张表都应该有创建人、创建时间、修改人、修改时间以及备注信息，把这些共有属性放到父类里由子类继承，不必在每个实体类中重复定义。

    * 表存在 `create_by` 就返回对应值，表没有设计则返回 `null`。

* **自动填充**

    * `createBy`、`createTime` 这类字段在新增和修改时会自动填充。

* **searchValue**

    * 用于全文检索时接收前端传递的一个参数。

* **params**

    * > **定义**：一个 Map 集合形式的请求参数，用来做灵活定义。

    * 产品已上线后客户想在前端加一个新请求参数、又不想修改实体类代码时，把参数放进这个 map 接收，减少代码改造，提高灵活性。
