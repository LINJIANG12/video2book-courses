# 文件上传与批量数据落库

## 上传成功的判定

* **Element Plus 上传组件的默认成功判定**
    * > **定义**：组件在请求发出、并且拿到了 HTTP 响应之后，就认定上传成功并打钩。
    * 它判断的是网络层有没有响应，不是业务层有没有办成事。
    * 后端返回 500 时，前端看到的是"我发出去的东西回来了"，组件照样显示绿色对勾。
    * > **结论**：前端不能只依赖组件的默认行为，必须在自己的回调里再判一次业务状态码。
    * > **易错点**：这种"骗人的成功"比直接报错更危险——报错至少诚实，成功是骗人。用户信了，运营也以为这批商品进库了，数据库里却什么都没有。

* **on-success 与 on-error 回调**
    * `on-success`：文件上传成功之后执行的回调函数。
    * `on-error`：前端上传失败之后主动触发的函数，用来给出友好提示信息。
    * 成功回调接一个参数 `res`，是 response 的缩写，代表后端返回的响应对象。
    * 属性只管"什么时候调"，方法体才是要动手改的地方。

* **成功回调 handleUploadSuccess 的四件事**
    * 判状态码：`res.code` 为 200，说明文件上传成功。
    * 弹成功提示：直接参考删除按钮的写法，把文本改成"上传excel成功"。
    * 关对话框：`excelOpen.value` 置为 `false`，上传成功了还杵着这个框就没意思。
    * 重新查数据：再执行一次 `getList()`，重新向后台查询最新的商品数据展示到页面。
    * 业务状态码不为 200 走失败分支：`proxy.$modal.msgError(res.msg)`，由后端返回的 `msg` 告诉用户报错原因。
    * 方法里其余没用的代码全部删掉。

* **两个回调共用的收尾动作**
    * `uploadRef.value.clearFiles()`：上传对象暴露的外部方法，作用是清空已上传的文件列表。
    * 不清的后果：对话框虽然关了，"已上传文件列表"里还堆着上一次的记录，下次打开对话框历史记录还在。
    * `proxy.$modal.closeLoading()`：关掉 loading。
    * 不关的后果：界面卡死在"正在上传excel，请稍后"这一句上，怎么都动不了。
    * > **易错点**：只在成功或失败时处理提示、却没人负责关 loading，是这个环节最典型的坑。
    * 失败回调 `handleUploadError` 更简单：提示"上传excel失败"，然后同样清一次文件清单、关一次 loading。

## 上传地址与请求头

* **响应式对象 uploadProps**
    * `action` 不能写死：先取当前环境的路径前缀 `/dev-api`，再拼上后端 `/manager/sku/import`。
    * 写法是 `import.meta.env.VITE_APP_BASE_API + '/manager/sku/import'`。
    * `headers` 用引入的 `getToken()` 方法把令牌放进请求头，写成 `Authorization: 'Bearer ' + getToken()`。
    * 上传请求发得出去，全靠这两行。

* **导入入口**
    * 商品管理视图页面加一个导入按钮，管理员点击后调用 `handleExcelImport`，把开关 `excelOpen` 置为 `true`，数据导入对话框弹出。
    * 对话框内放一个 `el-upload` 标签，挂上 `action`、`headers`、`before-upload`、`limit`、`on-success`、`on-error`。

## before-upload 前置校验

* **before-upload 钩子**
    * > **定义**：在文件上传**之前**执行的方法，能在这儿做校验就不要等请求发出去。
    * 对话框里那句"仅支持excel的文件格式，且文件大小不能超过一兆"是防好人的，不是防恶意提交的。
    * 实测传一张图片进去，提示文案写着只支持 excel，请求照样发到了后台。
    * > **结论**：前端该拦的必须自己拦在浏览器里，别把非法文件丢给后端。

* **扩展名校验**
    * 取扩展名：`rawFile.name.substring(rawFile.name.lastIndexOf('.') + 1)`。
    * 白名单 `fileType` 从官方图片组件的 `['png','jpeg','jpg']` 换成 `['xls','xlsx']`。
    * 用 `includes` 判断扩展名在不在白名单里的那一行不用删，它继续负责这件事，只是白名单换了内容。
    * 不通过就 `proxy.$modal.msgError('文件格式不正确，请上传excel文件格式的')` 并 `return false`。
    * 官方组件里判断"是不是图片"的变量 `isImage` 默认为 `true`，换成 Excel 场景后涉及的四处变量名全都要改成 `isExcel`。
    * 验收表现：选一个视频文件，前端直接弹格式错误提示，**根本没发请求**。

* **体积校验**
    * `fileSize` 从官方组件的 5M 改成 1M，跟对话框里那句提示对得上。
    * 判定式是 `rawFile.size / 1024 / 1024 > fileSize`，超了就提示 `上传excel大小不能超过 ${fileSize}M` 并 `return false`。
    * 本地准备一个超过 1M 的 Excel 即可验证，会被前端拦下。

* **通过校验后的动作与删减项**
    * 校验通过先 `proxy.$modal.loading('正在上传excel，请稍后')`，再 `return true`。
    * 官方组件里那行 loading 的文案"正在上传图片，请稍后"把"图片"换成"excel"即可。
    * 官方组件支持多图上传，所以里面有个 `number++` 统计数量；这里是单文件上传，这行直接删掉。
    * "是否显示提示信息"那一段删掉；图片数量的限制固定成 1 就行，多余的全删。
    * 前提条件：方法里要取 `uploadProps` 里的 `fileType` 和 `fileSize`，所以这个响应式对象也得整段复制过来，用不上的字段再按清单删减。

* **limit 数量限制**
    * 连着选两个文件（先图片、再视频），两个文件清单都会加载进来，点上传时会把这两个文件**都**提交给后台。
    * 功能只支持单文件上传，解决办法是 `:limit="1"`，表示允许上传文件的最大数量。
    * 加上之后，第一张选了图片，第二张视频就选不进去了。

## 整条上传链路

```text
   点击"导入"
        │
        ▼
   excelOpen = true ──► 数据导入对话框弹出
        │
   用户选择本地文件（limit=1，多一个选不进去）
        │
        ▼
 ┌──────────────────────────────────────────┐
 │  :before-upload  前置校验（不发请求）     │
 │   1. 扩展名 ∈ { xls , xlsx } ?           │
 │   2. 体积 ≤ 1M ?                         │
 │      任一不满足 → msgError → return false│
 │      满足     → loading("正在上传excel") │
 └────────────────────┬─────────────────────┘
                      ▼
        POST /dev-api/manager/sku/import
        （headers 里带 getToken()）
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
   业务码 = 200                业务码 ≠ 200
   msgSuccess("上传excel成功")  msgError(res.msg)
   excelOpen = false           （如"不支持请求方式为post"）
   getList() 刷新列表               │
        └─────────────┬─────────────┘
                      ▼
   收尾：clearFiles() 清空上传清单
          closeLoading() 关闭"正在上传excel"
```

* **链路上的三个要点**
    * 绿色对勾只会出现在"业务码 = 200"这一条支路上。
    * 文件在离开浏览器之前就被 `before-upload` 拦掉的，请求根本不会发出。
    * 无论走哪条支路，最后都会回到同一个收尾动作上。

> **提示**：不要试图一次性写完所有前端代码再测试，那样一旦出错很难定位。正确做法是每写完一段就立刻测一下，边写边测、调通一段再往下走一段。

## EasyExcel 的定位

* **原链路的局限**
    * 现在的 Excel 链路用的是若依的 Excel 工具类，它底层封装的是 Apache POI。
    * Apache POI 在某些情况下存在局限性问题：处理超大型 Excel 文件时内存消耗比较高，可能导致性能下降甚至内存溢出；对初学者来说 API 较为复杂，会增加学习难度。
    * 当前没感受到这些缺点有两个原因：前端把上传的 Excel 限制在 1M 以内，减少了内存压力；以及若依的 Excel 工具类简化了文件读取，API 用起来非常简单。
    * 将来业务里要上传视频这类大型文件、要处理复杂的 Excel 解析时，这个工具类就满足不了。

* **EasyExcel（阿里巴巴开源的 Excel 处理框架）**
    * > **定义**：一个基于 Java 的快速、简洁，解决大文件内存溢出的 Excel 处理工具——让你在不用考虑性能、内存等因素的情况下，快速完成 Excel 的读和写操作。
    * 以使用简单、功能强大、节省内存而著称，特别适合需要进行大量数据的导入和导出场景。

| 特点 | 说明 |
| :--- | :--- |
| 快速 | 在读写 Excel 文件时表现出色，特别是对于大型文件，通过优化数据流的处理减少了 IO 操作的延迟，使得操作更加迅速 |
| 简洁 | API 设计简洁直观、易于上手，通过注解和回调机制简化了 Excel 的读写过程 |
| 大文件 | 处理大文件时不会一次性将所有数据加载到内存中，而是采用**逐行读取和解析**的方式，极大减少内存消耗 |
| 兼容性 | 可以与 Apache POI 兼容，老项目中使用 POI 的同时可以无缝切换到 EasyExcel |

* **性能数据与天花板**
    * 官方性能数据：通过 16M 的内存、23 秒，读完了 75M 的数据，这份数据包含 46 万行、25 列。
    * > **易错点**：EasyExcel 只能专注于 Excel 文件的处理，不像 Apache POI 那样能处理 Word、PPT 等各种 Office 文件格式；其他类型的文件还是得用 Apache POI。
    * 官方文档入口有三个：官方网站、GitHub 地址、Gitee 地址。GitHub 服务器在国外访问不便，一般看 Gitee，里面存放源码以及官方示例的 Demo。

## EasyExcel 的读、写、填

* **读 Excel**
    * 流程是：先有一个 Excel 示例文件，包含标题部分以及数据的行信息。
    * 针对这个 Excel 设计一个实体类，比如叫 `DemoData`，类里的属性跟这几列一一对应上。
    * 接着用 EasyExcel 的监听器来读取数据，监听器的作用是把 Excel 数据读到 Java 的集合当中，再调用 Mapper 层保存到数据库。
    * 监听器不需要自己写，直接点击复制就能用。

* **写 Excel**
    * 先准备一个集合的测试数据，然后将这个数据写出到 Excel 文件。
    * 关键在实体类上的 `@ExcelProperty`，它把实体类的属性字段跟 Excel 的标题建立对应关系：字符串标题对应 `String`，日期标题对应 `Date`，数字标题对应 `Double`。
    * 设计好实体类后用 Java 代码实现写出，官方给了几种写法方案，照着挑一种即可。

* **填充 Excel**
    * 这种"模板填充"是常见的业务需求：提前设计好一个复杂的 Excel 模板，再通过占位符动态填充数据。
    * 典型场景：生成财务报表、销售报表、工资单、订单详情处理。
    * 占位符就是**一对花括号里面写变量的名称**。
    * 先根据模板的占位符变量设计出对应的实体类，再按官方提供的代码方案选一种完成填充。

## EasyExcel 的注解

* **属性级注解**

| 注解 | 作用 |
| :--- | :--- |
| `@ExcelProperty` | 匹配 Excel 和实体类，将实体类的属性与 Excel 的标题建立对应关系 |
| `@ExcelIgnore` | 忽略当前实体类的属性字段；默认情况下 EasyExcel 会把所有属性字段建立 Excel 的读写映射关系，想排除某个字段就用它 |
| `@ExcelIgnoreUnannotated` | `@ExcelIgnore` 的增强版；判断当前类的属性有没有加 `@ExcelProperty` 注解，加了才参与读写，没加就不参与；**需要和 `@ExcelProperty` 组合使用** |

* **`@ExcelIgnoreUnannotated` 存在的理由**
    * 如果实体类只有两三个属性参与 Excel 读写，其他字段都加 `@ExcelIgnore` 就太麻烦了。
    * 设计者因此提供了增强版，让"只映射显式标注的字段"变成一次类级声明。

* **类级样式注解（写出时用）**

| 注解 | 作用 | 不加会怎样 |
| :--- | :--- | :--- |
| `@ExcelIgnoreUnannotated` | 类中没有 `@ExcelProperty` 标注的属性，不与 Excel 建立映射 | 见下方说明 |
| `@ExcelColumnWidth(16)` | 设置列的宽度为 16 | 只是不好看 |
| `@ExcelHeadRowHeight(14)` | 设置表头行（列标题）的高度为 14 | 只是不好看 |
| `@ExcelHeadFontStyle(fontHeight = 11)` | 设置表头的字体样式，字体高度为 11 | 只是不好看 |

* **类级第一个注解为什么必须加**
    * 若依的实体类默认都继承了 `BaseEntity`，而 `BaseEntity` 里有一些公共字段：创建时间、更新时间、创建人、更新人等等。
    * 这些数据不需要跟 Excel 建立映射关系，所以在实体类上增加 `@ExcelIgnoreUnannotated`，公共字段属性就不会参与 Excel 的读写操作。
    * 后面三个样式注解不添加也没有关系。
    * `@ExcelProperty` 的属性是 `value`，这个 `value` 可以省略不写，直接写这一列对应的中文标题即可。

## 若依集成 EasyExcel 的改造

* **第一步：坐标要用新版本**
    * 坐标导入到 `ruoyi-common` 通用模块下。
    * 若依官网给的版本是 **2.2.6**，太老了；目前 EasyExcel 已更新到 **4.0.1**。
    * 在 `ruoyi-common` 的 `pom.xml` 最后一行把新坐标粘过来，再补一行注释：Excel 处理工具。
    * > **注意**：第一次粘贴需要下载依赖，要耐心等待。
    * 导入后必须检查 Maven 是否加载成功：打开 Maven 面板，把 `ruoyi-common` 的依赖列表往下拉，看最后一行是不是多出了阿里巴巴 EasyExcel 4.0.1。

* **第二步：给 ExcelUtil 添两个方法**
    * Excel 工具类的位置是 `src/main` 下的 `utils` 包里、`poi` 包下的 `ExcelUtil`，两个方法放在当前类最下方，粘贴完实现自动导包。
    * `importEasyExcel`：实现导入。给它一个字节输入流，它就完成读取，把数据封装到指定泛型的 class 实体类中，返回一个 list 集合。
    * `exportEasyExcel`：实现导出。三个参数依次是 `response` 响应对象（用于文件下载）、`list` 集合、工作表名称；把 list 数据写入 Excel 并指定工作表名称，再通过 response 完成下载，底层用的就是 EasyExcel。
    * 就这两个方法，已经满足商品管理的导入和导出两个功能。

* **第三步：实体类加注解，Controller 换调用**
    * 把工具类的方法调用从 Apache POI 改成 `exportEasyExcel`，但光换方法不够——实体类还要增加 `@ExcelProperty` 来建立属性和 Excel 标题的映射。
    * `SkuInfo` 实体类补齐导出字段：商品名称、商品图片、品牌、规格、商品的价格、商品类型 id。
    * Controller 里导入操作的方法改为调用 `importEasyExcel`，导出操作的方法改为调用 `exportEasyExcel`（同样三个参数），其余不需要调整。
    * > **易错点**：Apache POI 的 `@Excel` 注解先保留下来，不要删。这样实体类既支持 Apache POI 的导入导出，也支持 EasyExcel 的导入导出。

* **改造后的验收**
    * 改造涉及坐标导入，后端项目需要重新启动。
    * 先测导出：在商品管理里搜索"可口可乐"，这样只会导出这一条记录；点导出、选下载路径、保存，双击打开 Excel 看标题名称和这一行数据是否都完成了导出。
    * 再测导入：把刚才导出的那份 Excel 里的商品名称后面补上 `plus`，Ctrl+S 保存，回浏览器点导入并上传，文件上传成功。

## 货道关联商品的需求结构

* **业务目标**
    * 管理人员已经把商品信息录完了，接下来要在设备管理界面里对售货机内部的货道做商品摆放管理。
    * 这个动作有两个受益方：运营人员可以照着货道信息快速去补货补品，顾客也可以按货道选购。

* **对话框的两块结构**
    * 上方是当前售货机的设备类型信息：行数、列数，以及每个货道的最大容量。
    * 下方按货道编号排序列出这条机器上的所有货道；已关联商品的货道格子里还显示商品的图片和商品名称，没关联的只显示一个货道编号。

* **「确定」两个字的分量**
    * 选中某个货道点「添加」，右侧弹出商品对话框，挑完点「确定」，这一道货道的商品就选好了。
    * 点「删除」，当前货道的商品信息就被清空。
    * > **易错点**：**只有点了货道设置对话框上的「确定」按钮，才会向后端发送请求，把数据更新到数据库。**
    * 「添加」「删除」这两个动作都是纯前端的状态修改，页面看着像那么回事了，数据库里其实纹丝不动。
    * 联调时特别容易误判：看到界面变了就以为功能做完了，其实只是做了一半。

```text
设备管理页（每行右侧一个「货道」按钮）
    │  点击「货道」
    ▼
货道设置弹框
    │  顶部：设备类型信息（行 × 列 / 每道最大容量）
    │  主体：按编号排序的货道格子，已关联的显示 图片 + 商品名
    │
    │  点「添加」 ──────────────► 商品选择弹框（查商品列表）
    │                                  │ 选中商品 → 点「确定」
    │  ◄───────────────────────────────┘
    │  此时货道格子里已经变了样，但一切都没进数据库
    │
    │  点「删除」→ 格子清空成占位符，同样不发请求
    │
    │  点「确定」← 只有走到这一步，浏览器才和后端说话
    ▼
PUT /manager/channel/configure  ──►  更新 tb_channel.sku_id
```

* **四个接口，其中两个已经白送**

| 接口 | 路径 | 什么时候用 | 状态 |
| :--- | :--- | :--- | :--- |
| 查询设备类型 | —— | 弹框顶部显示行数、列数、每道最大容量 | 若依代码生成器已生成 |
| 查询货道列表 | `GET /manager/channel/list/{innerCode}` | 渲染弹框里的货道格子，已关联的要带商品名和图片 | 本块开发 |
| 查询商品列表 | —— | 点「添加」后弹出商品列表供挑选 | 若依代码生成器已生成 |
| 货道关联商品 | `PUT /manager/channel/configure` | 点「确定」后真正写库 | 本块开发 |

    * 真正要动手写的只有查询货道列表和货道关联商品两个。
    * 这是代码生成器用起来最舒服的地方：CRUD 那一半它替你干了，只补业务那一半。

* **商品表与货道表：一对多 + 逻辑外键**

```text
tb_sku（商品表）
   │  主键：sku_id
   │
   │  一对多
   │  货道表里的 sku_id 作为「逻辑外键」指过来
   ▼
tb_channel（货道表）
   ├─ inner_code    售货机编号
   ├─ channel_code  货道编号
   ├─ sku_id        ──► 指向 tb_sku.sku_id（逻辑外键）
   └─ update_time   最后修改时间
```

    * > **定义**：**逻辑外键**——数据库表里并不真的建 `FOREIGN KEY` 约束，只是靠一个字段的值指向另一张表的主键，由应用层代码保证数据的一致性和完整性。
    * 用逻辑外键而不是物理外键，是因为表更轻、插入更新更自由，写代码的人也完全可控；代价就是一致性的责任落到自己肩上。
    * 这个关系直接决定了两个接口的写法：查询货道列表不能只 `select * from tb_channel`，还得关联查出商品表的信息，返回一个 VO 对象；货道关联商品则是拿到前端传来的货道信息和商品信息，更新货道表的 `sku_id`，顺带把更新时间也刷上。

## 查询货道列表的三层实现

* **接口约定**
    * 请求路径 `/manager/channel/list`，请求方式 GET，请求参数走**路径传参**，参数名 `innerCode`，也就是设备编号。
    * 返回结构是标准三件套：`msg` 是提示信息，`code` 是业务状态码，`data` 是数据集合。
    * > **易错点**：`data` 里除了每条货道自己的信息，还额外带着它关联的商品信息；这是这个接口和若依生成的普通列表查询最大的区别，也是 VO 要存在的原因。

* **ChannelVO**
    * 在 `com/dkd/manager/domain/vo` 包下新建 `ChannelVO`：继承货道实体类拿到货道本身的全部属性，再额外加一个商品对象的属性 `private SkuSku sku`。
    * 加 `@Data` 注解，getter、setter、toString 全都有了。
    * > **结论**：实体类解决「和数据库表一一对应」，VO 解决「前端要什么我给什么」；前端要的组合实体类给不了，就开个子类补上。

* **Mapper 方法签名**
    * 返回 `List`，泛型是 `ChannelVO`，方法名 `selectChannelVOListByInnerCode`，查询条件是 `by innerCode`，参数也叫 `innerCode`。
    * > **易错点**：自动生成的方法签名命名和泛型都不对，返回值会手滑多敲一个字母，要改回来，改完不报红才算完。
    * `innerCode` 是 `String` 类型，拿不准就翻到设备实体类里搜一眼确认，别拍脑袋。

* **XML 查列表**
    * SQL 语句不用全部手写：若依生成的货道列表查询里已有一段现成语句，用 `<include>` 标签引出的 SQL 片段（`select` 出货道表各字段加 `from` 表名），复制过来补上 `where` 条件就行。

```xml
<select id="selectChannelVOListByInnerCode" resultMap="ChannelVOResult">
    <include refid="selectChannelVoSql"/>
    where inner_code = #{innerCode}
</select>
```

    * > **易错点**：代码补全工具会在粘贴位置自动生成一段 `<foreach>` 标签，那是它以为要做动态条件查询；多余的删掉，`where inner_code = #{innerCode}` 就是全部。
    * 最后把 select 标签上的 `resultType` 自动映射改成 `resultMap` 手动映射，`id` 填 `ChannelVOResult`。

* **resultMap 与 association**
    * 若依默认生成的 `ChannelResult` 映射里已经把货道表所有字段映射好了，直接复制过来改两处：`id` 改成 `ChannelVOResult`，`type` 改成 `ChannelVO`。
    * 一个货道对应一个商品是标准的一对一，所以用 `association` 标签把这层嵌进去。

| 属性 | 填什么 |
| :--- | :--- |
| `property` | VO 上商品对象的属性名，这里是 `sku` |
| `javaType` | 商品对象的类型，这里是 `SkuSku` |
| `column` | 用哪个字段去关联，这里是货道表里的 `sku_id` |
| `select` | 到哪个 Mapper 的哪个方法上继续查，这里是 `SkuMapper.selectSkuBySkuId` |

    * `select` 属性里要写全限定名：**包名 + 类名 + 方法名**。`SkuMapper` 里确实有 `selectSkuBySkuId` 这个按主键查商品的方法，复制方法签名过来核对一下就能对上。

* **Service 与 Controller**
    * Service 层直接抄 Mapper 的方法签名，让 IDE 生成实现体，里面就一句 `return baseMapper.selectChannelVOListByInnerCode(innerCode);`。
    * Controller 返回结果**不是分页对象**（没有 `startPage()`、没有 `TableDataInfo`），所以用标准的 `AjaxResult`。
    * 前端是 GET，注解是 `@GetMapping`；类上已经拼好了前两层路径，这里只写 `/list/{innerCode}`。
    * 路径参数用 `@PathVariable` 取，并且写成 `String innerCode`。
    * > **易错点**：**权限注解要加，日志注解不加。** 查询类接口只挂 `@PreAuthorize`，因为查询不改变数据，记操作日志没有意义。
    * 权限串不要用若依生成的单条查询的 `...:query`，这个返回的是列表，要跟它生成的货道列表查询保持一致，用 `...:list`。
    * 实测：点第一台设备的「货道」，货道信息出来了，已关联过的那台机器上商品图片和名称也都显示着；两行两列的机器则是四个货道，没关联的显示占位符。

## 批量配置的接口约定

* **请求形态**
    * 请求路径 `/manager/channel/configure`，请求方式 **PUT**，请求参数是 **JSON 格式**提交。
    * 最外层的 `innerCode` 是当前售货机的设备编号，`channelList` 是前端提交上来的货道配置集合。

```json
{
  "innerCode": "5C……",
  "channelList": [
    { "innerCode": "5C……", "channelCode": "2-1", "skuId": 1001 },
    { "innerCode": "5C……", "channelCode": "2-2", "skuId": 1002 }
  ]
}
```

    * 每一条货道带三个字段：`innerCode`（当前货道的设备编号）、`channelCode`（当前货道编号）、`skuId`（当前货道关联的商品 id）。
    * > **注意**：这个集合是**当前设备所有货道的完整集合**，不是「只有我改过的那几条」；前端一次性把所有格子都提交上来，后端统一处理。
    * 想看真实报文：按 `F12` 打开开发者工具切到 `Network` 选项卡，点一下「确定」就能看到一个 PUT 请求；Payload 挤成一团时点 `view source` 把源码复制出来，用 JSON 美化插件处理一下，结构就清楚了。
    * 返回结果就是标准的 `AjaxResult`：`msg` 是「操作成功」，`code` 是 200。

* **为什么必须同时传 innerCode 和 channelCode**
    * 货道编号长得像「二杠五」，而别的设备上也有二杠五；只提交「二杠五」根本没法判断要更新哪台设备的哪一个货道。
    * 同样是二杠二，一台是设备编号 `5C` 开头的，一台是 `TC` 开头的：货道编号在设备内部唯一，`innerCode + channelCode` 合起来才是货道在全局范围内的唯一标识。
    * > **结论**：`innerCode + channelCode` 组合定位货道，`skuId` 提供要写入的新值；后端拿到这两组信息，就能确定「更新哪条货道」和「更新成什么」。

## DTO 与 PO

* **DTO（Data Transfer Object，数据传输对象）**
    * > **定义**：专门用来在接口两端搬运数据的对象，字段按「前端传什么」来定，而**不按数据库表结构来定**。
    * 数据库对应的实体类 `Channel` 根本没有 `channelList` 这个属性，货道实体里也没有「一堆 DTO 组成的集合」这种结构，所以要专门设计 DTO 来接收前端参数。
    * 在 `manager` 包下新建一个 `dto` 包，两个类都加 `@Data` 自动生成 getter/setter/toString。

| DTO | 对应前端的哪一部分 | 属性 |
| :--- | :--- | :--- |
| `ChannelSkuDTO` | 单个货道的配置 | `innerCode`、`channelCode`、`skuId` |
| `ChannelConfigDTO` | 最外层整体 | `innerCode`、`List<ChannelSkuDTO> channelList` |

    * `skuId` 用的是 `Long` 而不是 `String`，它对应数据库主键，类型要跟实体对得上。

* **PO（Persistent Object，持久化对象）**
    * > **定义**：实体的属性名跟数据库的字段名一一对应，是 MyBatis 增删改查真正操作的载体。
    * 它和 DTO 的最大区别是：DTO 面向传输，PO 面向存储。

* **数据的层级关系**

```text
前端提交的 JSON
┌─ innerCode: "5C……"
└─ channelList: [ {innerCode, channelCode, skuId}, ... ]   ← 整个设备的全部货道
        │
        │ @RequestBody
        ▼
ChannelConfigDTO  ── 外层：一个设备
   └─ channelList : List<ChannelSkuDTO>
                    └─ ChannelSkuDTO ── 内层：一个货道
                                            │
                                            │ service 里遍历 + 查询 + 赋值
                                            ▼
                                     Channel（PO）
                                    货道表 tb_channel 对应的一行
                                            │
                                            │ baseMapper.batchUpdateChannels(...)
                                            ▼
                                 批量 update，一次请求发出
```

    * 前端提交的所有数据先给 `ChannelConfigDTO`，然后每一条货道的数据存进 `channelList` 集合里。
    * 接下来 service 遍历这个集合，取出 `innerCode` 和 `channelCode` 去查货道表，然后更新当前货道的 `sku_id`。

## Mapper 层的批量更新

* **查单条用注解就够了**
    * 这条 SQL 没有动态条件，不需要 XML：

```java
/**
 * 根据售货机编号和货道编号查询货道信息
 *
 * @param innerCode 售货机编号
 * @param channelCode 货道编号
 * @return 货道 Channel
 */
@Select("select * from tb_channel where inner_code = #{innerCode} and channel_code = #{channelCode}")
Channel getChannelInfo(@Param("innerCode") String innerCode, @Param("channelCode") String channelCode);
```

    * 表名和字段名要用下划线，写成 `inner_code`、`channel_code`，跟数据库字段保持一致，不要写成驼峰。
    * > **定义**：`@Param` 的作用是给形参起一个「别名」，让 MyBatis 能把 SQL 里 `#{...}` 占位符的名字和形参一一对应上。
    * > **易错点**：不加 `@Param` 时，多参数方法在 MyBatis 眼中只剩 `param1`、`param2`（或 `arg0`、`arg1`）这种位置化的名字，`#{innerCode}` 找不到对应值，运行时直接抛异常。
    * `Channel getChannelInfo` 这条 SQL 里用了两个具名占位符，而方法有两个形参，所以每个参数前面都要加 `@Param`。

* **批量修改的 XML**

```xml
<update id="batchUpdateChannels">
    <foreach collection="list" item="channel" separator=";">
        update tb_channel
        set sku_id = #{channel.skuId},
            update_time = #{channel.updateTime}
        where id = #{channel.id};
    </foreach>
</update>
```

    * 做法是找到若依生成的 `updateChannel` 单条修改的 XML，复制出来交给代码补全工具，提示词就一句："你是一名软件工程师，请把下面 XML 改成批量修改。"
    * `foreach` 标签负责遍历传进来的货道集合，**每一个货道对象都生成一条 update 语句**，按 id 更新；每条语句后面都补上分号作为结束；遍历完所有货道，这些语句被一次性发给后端统一执行。
    * > **易错点**：`collection` 必须和 Mapper 方法里参数的绑定名对上——加了 `@Param("channelList")` 就写 `channelList`，单个 List 参数没加 `@Param` 时写 `list` 或 `collection` 都行。
    * 对应的 Mapper 方法返回影响行数：`int batchUpdateChannels(List<Channel> channelList);`

* **多个分号的坑**
    * 这种批量更新的写法会产生**大量的 SQL 语句**，对数据库是有性能要求的；而且在某些场景下，数据库压根不支持在一个请求里执行多条 SQL。
    * 具体到 MyBatis 连 MySQL：默认情况下一个请求只能执行一条 SQL 语句，出现多个分号会直接报错。

```text
批量新增（INSERT）：一条语句、一个分号 —— 天然支持
  INSERT INTO tb_xxx (a, b) VALUES (1,2), (3,4), (5,6);
                        ↑ 多个 value 组，但整条只有这一个分号

批量修改（UPDATE）：N 条语句、N 个分号 —— 默认报错
  UPDATE tb_channel SET sku_id=1 WHERE id=10;
  UPDATE tb_channel SET sku_id=2 WHERE id=11;
  UPDATE tb_channel SET sku_id=3 WHERE id=12;
                        ↑ 从第二个分号开始，MySQL 直接拒绝
```

    * 解决办法是在连接数据库的配置文件里加参数：找到 `ruoyi-admin` 模块下的 Druid 配置文件，往最后一行加上 `allowMultiQueries: true`，作用是允许一次连接里执行多条 SQL。
    * > **提示**：如果用的是初始化工程，这个参数已经配好了；自己搭的项目就得手动加上。真出问题时它就是第一嫌疑人。

## Service 的 DTO 转 PO

* **方法签名与两步骨架**
    * `int setChannel(ChannelConfigDTO channelConfigDTO);` 返回影响行数。
    * 实现方法里一共两步，先把这两行注释补在方法开头，写代码时就不会乱：将 DTO 转为 PO 对象；批量修改货道。
    * 三层里 Controller 是固定套路，**Service 才是这个功能的重点**，因为前端提交的是 DTO，而 DTO 不能直接拿去更新数据库的货道表，必须先转成和数据库对应的 PO。

```java
/**
 * 货道关联商品
 */
@Override
public int setChannel(ChannelConfigDTO channelConfigDTO)
{
    // 1. 将DTO转为PO对象
    List<Channel> channels = channelConfigDTO.getChannelList()
            .stream()
            .map(channelSkuDTO -> {
                // 根据售货机编号和货道编号查询货道信息
                Channel channel = baseMapper.getChannelInfo(
                        channelSkuDTO.getInnerCode(), channelSkuDTO.getChannelCode());
                // 一定要先做非空判断，非空才说明找到了这条货道
                if (channel != null)
                {
                    // 关联本次提交的商品id
                    channel.setSkuId(channelSkuDTO.getSkuId());
                    // 设置本次修改的时间
                    channel.setUpdateTime(DateUtils.getDate());
                }
                return channel;
            })
            .collect(Collectors.toList());

    // 2. 批量修改货道
    return baseMapper.batchUpdateChannels(channels);
}
```

* **lambda 里四件事，一件都不能少**
    * 拿编号查货道：`getChannelInfo(innerCode, channelCode)`，这就是前面那个 Mapper 方法的用处。
    * 判空：拿到的对象**一定要先做非空判断**，非空才表示这条货道确实存在，查不到就原样返回 `null`，交给后续流程处理。
    * 赋值：把 DTO 里带来的 `skuId` 设置到实体上，这才是「关联商品」的实质。
    * 刷时间：`setUpdateTime(DateUtils.getDate())` 顺带把货道修改时间更新掉。
    * > **易错点**：`DateUtils` 的字母大小写要写对，手敲容易写成 `dateYoutus.getNOdate`，正确写法是 `DateUtils.getDate()`。
    * 用 stream 流的 `map` 做类型转换、再用 `Collectors` 收集结果，比手写 for 循环遍历拼接简洁清晰；这就是 stream 最舒服的地方。
    * 第二步就一行，把转换好的 `channels` 集合丢给 `baseMapper.batchUpdateChannels(...)`，返回影响行数。

## Controller 的批量配置与开发顺序

* **注解要挑对**
    * 请求方式是 PUT，注解写 `@PutMapping("configure")`；`/manager/channel` 前两层类上已经声明过了，这里只写 `configure`。
    * 参数是 JSON，要转成实体对象，用 `@RequestBody`。
    * 权限注解和日志注解**都要加**——货道关联商品是更新数据的操作，参考若依生成的「修改」功能把两行复制过来即可。
    * 返回用 `toAjax(...)` 包一层：去若依生成的**删除**方法里抄，它的写法是 `return toAjax(channelService.deleteChannel(ids));`，service 返回影响行数，交给 `toAjax` 判断成功还是失败。抄完记得把多余的分号删掉、结尾补上。

```java
/**
 * 货道关联商品
 */
@PreAuthorize("@ss.hasPermi('manager:channel:edit')")
@Log(title = "货道管理", businessType = BusinessType.UPDATE)
@PutMapping("configure")
public AjaxResult setChannel(@RequestBody ChannelConfigDTO channelConfigDTO)
{
    return toAjax(channelService.setChannel(channelConfigDTO));
}
```

* **Controller 的固定三步**
    * 接收货道配置参数 → 调用 service 实现货道关联商品 → 返回响应结果；第二步和第三步可以合并成一行。

* **验收与取消关联**
    * 给当前设备的货道分别关联上商品，点「确定」提示关联成功；再点开货道看，数据回来了，页面重新加载后也还在，说明是真写进了数据库。
    * 取消关联：点某货道上的商品「删除」再点「确定」，货道就变成占位符；想改回来，重新添加、选商品、确定即可。

* **开发顺序**
    * 做**思路分析**时从 Controller 开始：先看接口文档、前端传什么、Controller 接什么、交给 Service 干什么、Service 又需要 Mapper 撑腰，顺着请求的调用方向从前到后捋一遍，就知道每层该写什么。
    * 但真正**动手写代码**顺序要倒过来从后往前：Service 的代码得等 Mapper 写完才能写，Controller 的代码得等 Service 写完才能写。
    * > **结论**：思路分析从前到后，代码开发从后到前。分析时自顶向下拆解，落地时自底向上实现——下层是上层的地基，这个顺序不能反。
