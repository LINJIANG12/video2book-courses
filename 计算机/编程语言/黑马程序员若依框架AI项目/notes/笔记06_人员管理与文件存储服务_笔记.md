# 人员管理与文件存储服务

## 外键引用动作与级联删除

### 引用动作的四个取值

* **外键引用动作（referential action）**

    * > **定义**：外键约束上的这套规则，决定父表记录被更新或删除时数据库自动对子表做什么

    * `RESTRICT`：父表要修改或删除记录而子表中存在关联记录时，不允许该操作，防止违反外键约束

    * `CASCADE`：父表记录被更新或删除时，自动在子表更新或删除所有关联记录，以保证数据一致性

    * `SET NULL`：把子表中的外键字段置为 `NULL`，前提是该外键必须允许为空

    * `NO ACTION`：具体行为依赖数据库系统；在 MySQL 中等同于 `RESTRICT`，操作会导致违反外键约束时不执行

    * 归类：`RESTRICT` 与 `NO ACTION` 属于**拒绝**操作，`CASCADE` 与 `SET NULL` 属于**级联处理**

    * 更新规则与删除规则是分开的两个开关，各自都能设这四个取值，不是二选一

* **数据库客户端的修改入口**

    * 右击点位表 → 修改表 → 第四个选项 `foreign keys` → 双击打开设置引用动作规则的那一项

    * 查询规则含义的快速办法：在智能问答窗口提示「MySQL 外键约束的操作规则有哪些」

### 从级联删除改为限制删除

* **级联删除带来的连锁损失**

    * 点位表由智能辅助建表时默认加了外键约束，引用动作被配成 `CASCADE`

    * 删除一条区域 → 该区域下 N 条点位全部被删除 → 这些点位挂的设备信息跟着消失

    * 技术上符合外键约束规则，业务上一次误操作就是一整片区域的数据蒸发

    ```text
      区域表              点位表                设备信息
     （被删的那条）      （子表，级联删除）     （更下游的数据）
          │ 删除这一条
          ▼
      外键规则 CASCADE
          ├──▶ 该区域下的 N 条点位全部被删除
          │          └──▶ 这些点位挂的设备跟着消失
          ▼
      结果：一次误操作 = 一整片区域的数据蒸发
    ```

* **改造目标与取值**

    * 目标：删除区域或合作商时若其下还挂着点位，数据库直接拒绝操作并抛出错误

    * 应选 `RESTRICT` 或 `NO ACTION`，两者都对，课程中更新规则与删除规则都设为 `NO ACTION`

    * 设完再打开查看，界面文案已从「级联删除操作」变为「限制删除或更新」

    * `SET NULL` 不适用：它把子表外键字段置空，属于放行而不是拦截

### 拦截生效后的验证动作

* **重新造数与旧 id 陷阱**

    * 区域名称「北京市北五环奥体中心」+ 备注复制一份；新增点位「北京奥运博物馆」，类型旅游区，归属黑马合作商，地址从地图复制

    * 点确定即报数据完整性约束错误：请求提交的区域 id 是旧值 `4`，而新加区域 id 已变成 `5`

    * 原因：点位管理页面点「添加」时没有重新加载，下拉框里仍是上一次加载的旧数据

    * 这个报错反而证明完整性约束已经生效，刷新页面重加一次即成功

    * > **易错点**：课下重新添加被删过的原有数据时一定要刷新页面，不刷新提交的还是旧 id，数据库同样报完整性错误，而这个报错与外键无关，很容易白排查半天

## 数据完整性异常的友好提示

### 异常类型与分流依据

* **DataIntegrityViolationException**

    * > **定义**：Spring 框架提供的异常类，通常表示数据库操作中完整性约束被违反，外键约束、唯一约束等违规时抛出

    * 一个异常类管着多类约束，所以不能在处理器里把提示语直接写死成「外键约束原因，无法删除，有其他数据引用」

    * 写死会导致唯一约束等其他原因造成的异常也走到同一句提示上，同样不精准

    * 正确做法是从错误信息里找关键词分流

    * 分流规则一：消息中含 `foreign`，说明是区域/合作商删除时关联点位引起的，返回「无法删除，有其他数据引用」

    * 分流规则二：其他完整性约束原因，返回「数据完整性异常，请联系管理员」

    ```java
    @ExceptionHandler(DataIntegrityViolationException.class)
    public AjaxResult handleDataIntegrityViolation(DataIntegrityViolationException e)
    {
        log.error("数据完整性异常", e);

        // 错误信息里带 foreign，说明是区域/合作商删除时关联点位引起的
        if (e.getMessage().contains("foreign"))
        {
            return AjaxResult.error("无法删除，有其他数据引用");
        }
        return AjaxResult.error("数据完整性异常，请联系管理员");
    }
    ```

### GlobalExceptionHandler 的改法

* **框架已备好的处理类**

    * 若依已提供 `GlobalExceptionHandler`，位于 web 包的 exception 包下，已捕获若依自带的多个业务异常类

    * 新增的处理方法追加在该类的最后一行

    * 只写注释「数据完整性异常」让智能工具补全，它能结合上下文里其他异常方法给出相同风格的返回值

    * `@ExceptionHandler` 声明下面这个方法专门捕获数据完整性异常

    * 返回值用若依统一结果对象 `AjaxResult`，在其中指定错误信息与业务状态码

    * 方法体内先用日志记录异常信息，再通过 `AjaxResult.error` 返回提示文案

    * 对应的业务代码属于第三步事务管理：单表操作事务默认自动提交，所以事务注解不添加也能正常工作

    * 智能工具生成的三块里只需要关注自定义异常类与全局异常处理器两块

    * 这个异常类 Spring 框架已经提供，不需要自己再定义

* **删除操作的完整处理链路**

    ```text
      用户点击「删除」
            │
            ▼
      第 ① 步 点位表外键规则由 CASCADE 改为 NO ACTION / RESTRICT
            │
            ▼
      数据库：区域/合作商下还挂着点位 → 拒绝执行删除
            │
            ▼
      抛出 DataIntegrityViolationException
            │
            ▼
      第 ② 步 GlobalExceptionHandler 捕获并分流
            │
            ├── 含 foreign ──▶ "无法删除，有其他数据引用"
            └── 其他约束     ──▶ "数据完整性异常，请联系管理员"
            │
            ▼
      浏览器弹出用户看得懂的提示
    ```

    * 第 ① 步让数据库本身守住数据完整性，第 ② 步把守不住时的那声「数据不让删」翻译成人话

## 人员管理的数据模型

### 业务动机与定制来源

* **要解决的实际问题**

    * 区域、合作商、点位定下来之后，下一步是安排工作人员去投放智能售货机

    * 典型反例：常驻北京大兴区的工作人员去负责海淀区的北京大学点位，距离远、通勤久、效率低

    * 目标是实现每个区域关联一个或多个工作人员，让他们在负责区域内完成设备安装、维修、商品补货

    * 业务流程链条：新增工作人员姓名与联系方式 → 关联角色确定是运维还是运营 → 关联区域确定负责范围 → 在该区域内作业

* **为什么不用若依自带表**

    * 人员管理主要涉及角色表、员工表，以及已经熟悉的区域表

    * 角色表和员工表**不是若依框架自带的标准组件**，而是运营管理 app 员工端专门定制的功能模块

    * 运营管理 app 登录时可选运营或运维角色，运营人员处理捕获相关工单，运维人员处理设备投放与维修工单

    * 若依原有的员工表与角色表面向通用后台，只提供基本用户管理与角色授权，粒度不够

    * 管理后台页面原型里没有角色管理界面，角色数据以固定三条记录的形式给出

### 角色表与三条固定角色

* **表结构**

    * 只有三个字段：角色主键 `id`、角色编码 `roleName` 之外的 `roleCode`、角色名称 `roleName`

    * 数据固定，没有配套的页面来管理

    | 角色名称 | 角色编码 | 含义 |
    | :--- | :--- | :--- |
    | 工单管理员 | `1001` | 相当于运营部门的负责人 |
    | 运营人员 | `1002` | 负责智能售货机的商品补货 |
    | 维修员 | `1003` | 负责投放并维修智能售货机 |

* **能否做成数据字典**

    * 不能。数据字典只能设置字典标签、字典值两个字段，而角色表有三个字段（主键、编码、名称）

    * 所以必须先设计好数据库的表结构，再手动添加角色数据

### 员工表字段

* **对应页面原型的字段序列**

    * `id`：员工主键

    * 员工名称：对应页面上的「人员名称」

    * `regionId` 与 `regionName`：对应「归属区域」，其中 `regionName` 是冗余字段

    * `roleId`、`roleCode`、`roleName`：对应前端的角色名称字段，后两者是冗余字段

    * `mobile`：联系电话

    * 员工头像与是否启用：在页面原型里要往右拉到新增对话框才能看到

    * 创建时间与修改时间

* **`status` 字段**

    * 取值 `1` 表示启用，`0` 表示停用

    * 业务含义：员工正式入职并处于工作日设为启用，休假期间设为停用

    * 属于静态数据，因此设置为数据字典以简化查询

### 两组一对多关系

* **角色与员工**

    * 一对多：员工表用 `roleId` 作外键指向角色表主键

    * 一个角色下可以拥有多个员工，每一个员工属于某一个角色

    * 将来可以根据角色编码或外键字段查询对应的员工列表

* **区域与员工**

    * 同样是一对多：员工表用 `regionId` 作外键指向区域表主键

    * 一个区域下面可以关联多名员工，而员工只负责某一个区域

    ```text
      角色表 role          员工表 employee           区域表 region
     ┌────────────┐      ┌──────────────┐         ┌────────────┐
     │ id (PK)    │──1:n─▶│ roleId   (FK)│         │ id (PK)    │
     │ roleCode   │      │ regionId (FK)│───n:1──▶│            │
     │ roleName   │      │ 员工名称     │         └────────────┘
     └────────────┘      │ 联系电话     │
                        │ 头像 / 状态   │
                        │ 冗余字段 ×3   │
                        └──────────────┘
    ```

### 反范式冗余字段

* **三个冗余字段**

    * `regionName`（区域名称）、`roleCode`（角色编码）、`roleName`（角色名称）都冗余在员工表上

    * 采用**反范式**思路：不做常规关联查询，而是减少关联查询次数来加快查询速度

    * 好处一：原本多表联合的操作现在单表完成；点位管理列表还要把嵌套查询结果组合，这里单表即可搞定

    * 好处二：查询逻辑从嵌套或多表关联变成单表，更简单直观易懂

    * 好处三：读写分离架构下可降低对主表的依赖，增加操作灵活性

    * > **易错点**：代价是增加数据维护的复杂性，冗余字段会占用更多存储空间

    * 本场景的主要目标是提高员工列表查询效率，且已练习过多表查询与嵌套查询，故选定该方案

### 冗余字段与数据字典的取舍

* **冗余字段不能由前端提交**

    * 前端下拉框选中后提交的只有区域 id 与角色 id，不会提交区域名称、角色编码、角色名称

    * 这几个值需要根据 id 去查询数据库拿到后再做封装，因此新增对话框里不需要给它们设置文本框

    * 这正是员工表里那三个冗余字段存在的理由

* **整体路线**

    * 先生成基础代码导入项目，但生成器给出的代码仅涵盖单表 CRUD

### 员工表的条件查询取舍

* **保留的五个条件**

    * 页面原型上只有人员名称一项搜索，按员工名称模糊匹配

    ```text
      条件查询：保留 5 个              去掉 4 个
      ───────────────────────        ────────────────────────
      · 员工名称（模糊匹配）           · 区域名称
      · 所属区域 id                   · 角色名称
      · 角色 id                       · 联系电话
      · 角色编号                      · 员工头像
      · 员工状态
    ```

* **判断依据**

    * 页面原型没有的不急着配，保留是为了让后续查询有现成的动态 SQL 可用

### 员工表的列表与新增对话框

    * 创建时间与修改时间取消掉

    * 若依生成的修改对话框与新增保持一致，这里同步更新

    * 最后给表单项增加必填校验并勾选

* **Java 类型映射**

    * 默认对应数据库类型做自动映射，Java 属性名与列名之间完成驼峰转换

## 人员列表页面对齐原型

### 搜索区与列表区

* **搜索条件区**

    * 原型只有「人员名称」一项，与生成结果一致，输入「刘」点搜索数据正常，这条不动

    * 人员 ID、角色 ID、角色编号、是否启用这几个条件原型上根本没有，是生成器多送的，直接删掉

* **按钮区**

    * 人员新增保留，与原型一致

## 同步存储策略

### 不一致的根源

* **改主表带不动冗余字段**

    * 冗余字段的好处是人员列表能单表查询、效率高、开发简单；代价是主表改了它不跟着变

    * 把「北京市北五环奥体中心」改名为「北京市奥体中心」，回到人员列表刷新，员工列表里的区域名称依然是旧值

    ```text
       改区域表            员工表（冗余字段）        用户看到的列表
      ────────           ─────────────────         ─────────────
     名称改成                  没动                  旧名称
     "北京市奥体中心"
          │                     ▲                      │
          └──── 没有任何联系 ─────┘                  数据不一致
    ```

    * 根源：既然用了冗余字段，就必须同时保证这些冗余字段能够及时更新

* **同步存储策略的定义**

    * 在员工表里保留区域名称这个冗余字段，要求更新区域表的同时必须更新员工表中的区域名称字段

    * 若依已提供修改区域表的后端代码，但**没有**提供「根据区域 id 更新区域名称」的代码，这部分要自己写

### 手写更新 SQL 与 Mapper 映射

* **第一步：先在数据库客户端验证 SQL**

    * 这条语句简单，直接手写不折腾智能工具

    ```sql
    -- 根据区域id修改区域名称
    update tb_emp
    set region_name = '北京市奥体中心'
    where region_id = 5;
    ```

    * 执行提示成功后刷新员工表，小智和波妞的区域名称都同步过来了，说明 SQL 没问题

* **第二步：Mapper 层用注解建立映射**

    * 这条 SQL 不含动态 SQL（没有 `<if>`、`<where>` 标签），为提高可读性不写 XML，直接在接口末尾用注解加方法

    ```java
    /**
     * 根据区域id修改区域名称
     *
     * @param regionName 区域名称
     * @param regionId   区域id
     * @return 影响行数
     */
    @Update("update tb_emp set region_name = #{regionName} where region_id = #{regionId}")
    public int updateRegionNameByRegionId(@Param("regionName") String regionName,
                                          @Param("regionId") Long regionId);
    ```

    * 细节一：写死的值要变成占位符，`'北京市奥体中心'` 和 `5` 是测试值，换成 `#{}` 占位符 `regionName` 与 `regionId`

    * 细节二：类型要跟实体对得上，智能工具补全时两个参数都给成了 `String`，`regionId` 对应实体里是 `Long`，要同步改过来

    * > **易错点**：类型不匹配运行时才会炸，现在改成本最低

    * > **易错点**：方法传两个参数，MyBatis 靠 `@Param` 给每个参数起别名来区分，别名必须和占位符名字一模一样；嫌麻烦可以省略注解，但占位符就得改成 `#{arg0}` 和 `#{arg1}`

    * 返回类型是 `int`，返回的就是影响行数——增删改都会返回影响行数

### Service 层串接与事务

* **改写原有的更新方法**

    * 原来的代码更新完区域表就直接 `return regionMapper.updateRegion(region)`，这显然不合适

    * 先把返回值抽出来不直接 return，里面会返回一个影响行数变量，名字就叫 `result`

    * 在类里注入员工表的 Mapper：`@Autowired private EmpMapper empMapper;`

    * 三段逻辑串起来，并加上事务注解

    ```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public int updateRegion(Region region) {
        // 1. 先更新区域信息
        int result = regionMapper.updateRegion(region);

        // 2. 区域表更新成功后，同步更新员工表中的区域名称
        empMapper.updateRegionNameByRegionId(region.getName(), region.getId());

        return result;
    }
    ```

    * 传两个参数：第一个是区域名称 `region.getName()`，第二个是区域 ID

* **事务边界的硬要求**

    * 这个方法涉及两张表的 SQL 更新，两张表的更新必须当成一个整体，要么都成功要么都失败

    * > **易错点**：要加 Spring 声明式事务，并且**一定补上 `rollbackFor = Exception.class`**，否则受检异常抛出时事务不会回滚

* **验收**

    * 热部署后把区域名改回去并补上备注，人员列表一刷新，小智和波妞的归属区域名称也一起变回来

* **落地三步小结**

    * 按区域 id 写一条更新员工表区域名称的 SQL

    * 在 Mapper 层加方法把 SQL 映射起来，两个参数要 `@Param` 别名

    * 在区域 Service 的更新方法里先更新区域表、再同步更新员工表，最后补上事务

## 文件存本地的代价与上云路线

### 本地存储的三个问题

* **默认的落盘方式**

    * 生成的代码本来就能用，点新增、选一个头像，头像就保存到了服务器本地，浏览器刷新后照样显示

    * 配置文件第十行写着存储路径，目录为 `D:\ruoyi\uploadPath`，里面确实躺着刚上传的图片

* **三个绕不开的问题**

    * 性能瓶颈：文件直接落到自己服务器上，处理能力不足或网络带宽有限时，上传、下载、访问速度都受影响

    * 磁盘会满：以微信服务器为例，数十亿用户的头像和视频到了 PB 级别，远超 GB、TB 的计算范围，再大的磁盘也装不下

    * 单点故障风险：服务器一挂，存上面的所有文件全都访问不了；备份或冗余只能降低风险，风险本身却无法根除

    * 所以项目开发中通常不会把文件直接存在服务器本地

### 自建与云服务的两条路

* **自己搭服务**

    * 可以基于分布式文件系统 FastDFS 搭自己的文件存储系统，也可以基于 MinIO 来搭

    * 要自己准备服务器，还得考虑搭集群扩容，技术要求高，还要额外采购服务器，对中小型公司不友好

* **用现成的云服务**

    * 直接用阿里云、腾讯云、华为云等现成服务，既省成本又降低技术难度

    * 本次采用的方案是**把文件存到云端**，利用云服务优势解决存储问题

### 阿里云 OSS 的服务指标

* **服务定位**

    * 全称 Object Storage Service，对象存储服务

    * 这里的「对象」就是要存的文件——文本、图片、音频、视频统统都叫对象

    * 官方定位为海量、安全、低成本、高可靠的云存储服务，可通过网络随时存取各种文件

    | 指标 | 数值 |
    | :--- | :--- |
    | 数据持久性 | 99.99999% |
    | 数据可用性 | 99.995% |

    * 官方也诚实说明：虽然非常接近 100%，但并不保证绝对的 100%，任何服务都可能遇到不可预见的情况

* **存到云端的链路变化**

    ```text
      ① 用户在浏览器发起上传请求
                        │
                        ▼
      ② 请求发送到我们的服务器
                        │
                        ▼
      ③ 服务器不再把文件写进本地磁盘
         而是带着 AccessKey 凭证直连阿里云 OSS
                        │
                        ▼
      ④ 文件进入 OSS 桶中存储
                        │
                        ▼
      ⑤ 服务器不必占用本地空间
         文件改由 OSS 通过 URL 对外提供访问
    ```

    * 改造前：浏览器 → 服务器 → 磁盘目录 → URL 返回，文件全堆在单机磁盘上，磁盘满了、机器挂了文件就全部丢失

    * 改造后：浏览器 → 服务器 → 阿里云 OSS → URL 返回，服务器只做中转不落文件

    * 前述三个问题一次性全解决，还顺带拿到 OSS 的高可靠和高可用

### 接入云存储的三段流程与 SDK

* **通用三步**

    ```text
    第 1 步  准备工作   注册云账号 → 实名认证 → 登录平台 → 开通所需服务
    第 2 步  入门程序   参考官方 SDK 的示例，写一个能跑起来的程序
    第 3 步  项目集成   把云服务真正接进项目，解决业务问题
    ```

* **SDK**

    * 英文全称 Software Development Kit，中文直译「软件开发工具包」，包含辅助软件开发的各种依赖 jar 包

    * > **定义**：云服务官方提供的工具包，把程序所需的依赖 jar 包和示例代码全都准备好了，不用写任何一行代码，把示例粘过来做点微调就能用

    * 第二步的核心是参考官方 SDK 的示例代码写一个能跑起来的入门程序，确保它正常运行；第三步才是把云服务集成到项目里

## 阿里云 OSS 开通五步

### 账号充值与服务开通

* **三步动作**

    * 第一步：访问阿里云官网注册账号并完成实名认证，之后才能访问产品界面；搜索框搜 `OSS` 进入「对象存储 OSS」

    * 第二步：充值。对新用户来说充值并非必须，很多服务有免费试用额度，额度用完还想用才需要充值；入口在右上角头像 → 费用与成本 → 充值

    * 第三步：在控制台里开通 OSS 服务

* **容易被忽略的一步**

    * > **易错点**：刚注册好的账号 OSS 服务默认是**未开通**状态，**充值不等于开通**，必须单独在控制台点一下开通

### 建桶的名称与权限

* **Bucket 的含义**

    * Bucket 是存储空间里的一个容器，上传的图片、视频、音频都要放到这个容器里

    * 可以创建一个或多个 Bucket 作为容器来存文件

* **两个必须盯紧的地方**

    * 桶的名称必须保证**全网唯一**，本例起名 `dkgd-itheima`；名称一旦创建就**不能更改**，重名了就得换一个

    * 必须把阻止公共访问的开关关掉，并设置为**公共读**

    * 为什么：将来上传的头像需要被客户端直接访问，保持默认私有权限的话你能上传但别人访问不到

* **其他选项**

    * 桶的地域位置决定阿里云最终把文件放到哪个地域的机房，本例选华北 2（北京）

    * 存储类型、冗余类型保持默认即可

    * 创建完成可在控制台界面上传一个文件试一下，上传成功后文件列表里就多出一个文件对象

    * > **易错点**：这只是阿里云控制台界面的上传，真实场景是在项目里上传，涉及 Java 代码与 OSS 的对接

### AccessKey 与环境变量

* **凭证的含义**

    * 对接要有身份验证凭证，这个凭证就是 AccessKey，也就是密钥

    * 入口：右上角头像 → AccessKey 管理，新用户需要自己创建，创建需手机号验证

    * **AccessKey ID** 相当于身份证号，**AccessKey Secret** 相当于密码

    * > **注意**：这两个信息千万不要泄露，泄露后别人就能用你的账号完成文件上传或其他服务操作；自己一定要保存好，Java 代码上传时就要用到

* **写进环境变量**

    * 以**管理员身份**打开 CMD 命令行，把两个值分别写进对应的环境变量，一条对应 ID 一条对应 Secret，注意复制自己的别抄错

    * 执行刷新命令让配置生效，再用查询命令执行验证，能回显出 AK 就说明配置已经生效

    * 配环境变量是为了稍后使用 SDK 入门案例

    * > **易错点**：配完环境变量之后**必须重启 IDEA**，它才能加载到环境变量里的数据，没重启就往下写代码，凭证那一步必然出问题

## x-file-storage 抽象多厂商存储

### 换厂商的代价

* **入门程序写得很「死」**

    * 端点写死、容器写死、文件名也写死

    * 入门程序的逻辑只有四步：拿到文件对象 → 传给工具方法 → 上传到指定端点下方的容器 → 上传成功后返回该文件的 URL 访问地址

    * 拿到地址后存进数据库，将来访问该文件资源时直接拿 URL 访问

    ```text
          用户在前端选择文件并提交
                     │
                     ▼
          工具类方法：接收一个文件对象
          （端点、容器、文件名都不能写死）
                     │
                     ▼
            上传到「指定端点」下的容器中
                     │
                     ▼
           上传成功后，返回该文件的 URL
                     │
                     ▼
                  URL 存进数据库
                     │
                     ▼
        将来访问该资源：直接拿 URL 访问即可
    ```

    * 抽取工具类的思路就是把「写死的东西」变成「传进来的东西」

* **抽完之后的新问题**

    * 入门程序和项目集成这两段代码虽然都是官方提供的、且有内在关联性，但要理解一套 SDK 本身有学习成本

    * 更要命的是两段都绑死在同一家厂商上

    * > **易错点**：公司用的如果不是阿里云 OSS，比如忽然改成华为云 OBS，第二步和第三步就得从头再搞一遍——重新翻那家的文档、跑一遍入门案例、再改一遍工具类

    ```text
    【每家一套】                       【x-file-storage】

    阿里云 SDK ──┐                     ┌── 本地存储
    华为云 SDK ──┤                     │
    腾讯云 SDK ──┼──► 每换一家都要：    ├──►  一套代码 + 一份配置
    七牛云 SDK ──┤    翻文档            │
    S3 协议 SDK ─┘    跑入门案例        ├── 阿里云 OSS
                    抽成工具类         │
                                          ├── 华为云 OBS
      换一家 = 从头再来一遍             │
                                          ├── 七牛云 / 腾讯云
                                          └── 兼容 S3 协议的平台

                                          换一家 = 只改配置文件
    ```

### 工具定位与四个优点

* **定位**

    * 国产开源的文件存储工具，允许开发者通过**一行代码**实现多平台的文件存储

    * 支持本地存储、FTP/SFTP，还有阿里云、华为云、七牛云、腾讯云等等，以及兼容 S3 协议的存储平台

    * 有了它不必再学习每一个云平台的 SDK、文档和入门案例再改造为工具类

    * 官网名 X-File-Storage，原名 `x-spring-file-storage`，目前已捐赠给 dromara 开源组织（hutool 工具包也在这个组织下）

    | 优点 | 说的是什么意思 |
    | :--- | :--- |
    | 简化配置 | 通过统一配置轻松切换存储平台。原来用阿里云 OSS 改华为云 OBS 只需修改配置文件，源代码不动 |
    | 易于集成 | 提供 Spring Boot 集成支持，在启动类上加一个注解就能开启文件存储功能 |
    | 功能丰富 | 支持上传、下载、删除等基本操作，还有上传进度监听、缩略图生成等高级功能 |
    | 开箱即用 | 提供丰富的示例代码和文档，方便快速上手 |

### 依赖坐标与导入位置

* **两个坐标**

    * 官网上「快速入门」首先提供 Spring Boot 起步依赖，项目里只需要导入这一个起步依赖坐标

    * 除此之外它提到：如果项目不是 Spring Boot，还有一个单独使用的方案

    * 起步依赖导入之后，文档还列出各大云平台的坐标，按需复制——用阿里云复制阿里云的，用华为云复制华为云的坐标

    ```xml
    <!-- 文件上传坐标 -->
    <dependency>
        <groupId>org.dromara</groupId>
        <artifactId>x-file-storage-spring-boot-starter</artifactId>
        <version>${x-file-storage.version}</version>
    </dependency>
    ```

    * 也就是说先导入核心 starter 坐标，再导入对应云平台的坐标，**不需要再访问对应官网查看 SDK**

    * 在通用模块的 `pom.xml` 粘贴好坐标、写上「文件上传」中文注释后，坐标会有下载过程要耐心等待

    * 下载成功后**一定要检查 Maven 面板中是否已经把它引入进来**

### 基础配置与平台配置

* **配置分两段且一起生效**

    * 官方文档要求在 `application.yml` 中先添加基础配置，再去找对应平台的配置

    * 位置在 `dk-admin` 模块下的 `application.yml`，在底行位置加上这一段

    ```yaml
    # 文件上传
    dromara:
      x-file-storage:
        # 默认的存储平台
        default-platform: aliyun-oss-1
        # 缩略图生成的图片类型
        thumbnail:
          image-type: jpg
    ```

    * 基础配置就这几样：dromara 是开源组织名称，下面是 x-file-storage 的文件存储配置

    * 官方文档里 `default-platform` 默认写的是华为 OBS（注释还贴心地写了「国货之光」），稍后要做调整

    * 官方示例中华为 OBS 有 OBS1、OBS2 两条，这个位置指定 1 或 2 都没问题

    * 缩略图的扩展名默认给的是 `jpg`，也可以改成 `png` 等，本例用默认值

* **平台配置段**

    ```yaml
        # 阿里云 OSS
        - platform: aliyun-oss-1
          # 是否启用
          enable: true
          # 访问密钥
          access-key: 你的AccessKey
          # 访问密钥
          secret-key: 你的SecretKey
          # 上传端点
          endpoint: oss-cn-beijing
          # 存储空间名称
          bucket-name: dk-ad-heima
          # 访问域名
          domain: https://dk-ad-heima.oss-cn-beijing.aliyuncs.com/
          # 基础路径
          base-path: dk/images/
    ```

* **三个必须注意的地方**

    * 第一，粘贴时**一定要左侧对齐，注意缩进**，多一个空格或少一个空格这一段就会加载失败

    * 第二，`default-platform` 里写的名称**必须和下面 `platform` 里的名称保持一致**，把华为云那份覆盖掉、项目重启后就会加载阿里云配置

    * 第三，`domain` 最后**需要有正斜杠结尾**，因为它将来要去拼接我们的文件名

* **多平台的动态切换**

    * x-file-storage 支持多个平台的参数配置：上面配阿里云、下方配腾讯云或华为云，然后在 `default-platform` 中灵活修改使用，做到动态切换

### 平台配置项逐条对照

| 配置项 | 含义 | 填写方式 |
| :--- | :--- | :--- |
| `platform` | 存储平台的标识，要和 `default-platform` 对应 | `aliyun-oss-1` |
| `enable` | 是否启用存储 | 要存文件，所以启用 |
| `access-key` | 身份认证凭证之一 | 之前申请好的 AK |
| `secret-key` | 身份认证凭证之二 | 之前申请好的 SK |
| `endpoint` | 上传端点信息 | 从入门案例里拿，**复制时不用再加 https**，只复制后面的 `oss-cn-beijing` |
| `bucket-name` | 存储容器的名称 | 本例容器名 `dk-ad-heima` |
| `domain` | 访问域名 | **文件名之前的全部请求部分**就是访问域名 |
| `base-path` | 基础路径 | `dk/images/` |

### base-path 的年月日切割

* **为什么要指定基础路径**

    * 所有文件都放到容器内根路径下会杂乱无章，后期维护不方便

    * 若依的设计是指定一个叫 `upload` 的基础路径，同时提供一个子文件夹 `upload`，里面再按**年、月、日**做文件夹切割

    * 所以本项目也建议指定基础路径 `dk/images/`，用来存帝可得项目的文件

    * > **注意**：后面的年月日信息**不能写死在配置里**，通过 Java 代码跟文件名做拼接就能实现

## 集成 x-file-storage 进通用上传接口

### 启动类注解与服务注入

* **启动类加注解**

    ```java
    @SpringBootApplication
    @EnableFileStorage
    public class DkApplication {
        public static void main(String[] args) {
            SpringApplication.run(DkApplication.class, args);
            System.out.println("(♥◠‿◠)ﾉﾞ  若依启动成功   ლ(´ڡ`ლ)ﾞ");
        }
    }
    ```

* **需要做文件上传的 Controller 上注入服务对象**

    ```java
    @Autowired
    private FileStorageService fileStorageService;
    ```

* **上传接口提供的参数**

    * 第一个是文件对象；拿到文件对象后还可以指定一个**相对路径**

    * 这个相对路径指在 OSS 做文件存储时可以设置 `2024-06-18` 这种以日期分隔的路径，用 Java 代码动态生成便于后期管理

    * 后面还有关联对象 Id、关联对象类型、保存一些属性信息，**不需要的话可以省略不写**

    * 执行 `upload()` 上传成功后返回 `FileInfo` 文件信息对象，里面有 `getUrl()` 方法拿到图片访问地址，还支持直接返回 URL 地址的方法

    * 整个上传代码都由 x-file-storage 封装好，看不到底层实现，无需关心到底用的阿里云还是华为云，只改配置文件就能动态切换

### 通用上传接口的改造

* **定位到要改的 Controller**

    * 选择头像上传时可以看到上传路径叫 `common/upload`，据此在 IDEA 里 `Shift Shift` 全局搜索找到 `CommonController`

    ```java
    /**
     * 通用请求
     */
    @RestController
    @RequestMapping("/common")
    public class CommonController
    {
        @Autowired
        private FileStorageService fileStorageService;

        /**
         * 文件上传
         * 支持单个文件上传
         */
        @PostMapping("/upload")
        public AjaxResult uploadFile(@RequestParam("file") MultipartFile file) throws Exception
        {
            // 原来上传到若依自带的本地存储（若依 upload 目录），先注释掉
            // String fileName = FileUploadUtils.upload(DkConstants.RESOURCE_PATH + "/upload", file);

            // 1）按当天日期生成相对路径，形如 2024-06-18，next day 是 2024-06-19
            String datePath = LocalDate.now()
                    .format(DateTimeFormatter.ofPattern("yyyy-MM-dd"));

            // 2）与配置文件里的 base-path 拼接；后面还要接文件名，所以日期后方必须有正斜杠
            String objectName = "dk/images/" + datePath + "/";

            // 3）上传文件并返回文件信息对象
            FileInfo fileInfo = fileStorageService.getFileStorage()
                    .of(file)
                    .setPath(objectName)
                    .upload();

            // 4）从文件信息对象里拿到访问地址
            String url = fileInfo.getUrl();

            // 5）统一返回 URL
            return AjaxResult.success().put("url", url)
                    .put("fileName", url)
                    .put("newFileName", url);
        }
    }
    ```

* **几个要抠的细节**

    * 日期用 JDK 的 `LocalDate`：`now()` 拿当前时间，`format` 方法做格式转换，`DateTimeFormatter` 里指定的格式把年月日补全

    * 为什么日期后面还要再拼一个正斜杠：`2024-06-18` 这个相对路径指定完毕只是目录不是完整文件名，后面紧接着要添加文件名，所以日期后方也需要斜杠

    * 前面的正斜杠不用写死，由 Java 代码跟文件名做拼接

* **返回值的改动**

    * 原来若依返回的是地址、文件名、新文件名以及原始文件名

    * 现在把 `fileName` 和 `newFileName` 的值都改为 URL，因为**前端的访问地址会做一个判断，如果以 HTTP 开头就直接显示此图片**

    * 新文件名其实不返回也不产生影响，这里统一都返回 URL 地址；原始文件名不做任何调整

### 前端的 HTTP 判断

* **为什么要改返回值的类型**

    * 把浏览器里的头像图片地址复制出来在新窗口访问，会发现它是通过 `localhost/dev-api` 做了拼接

    * 因为这是若依自带的本地存储路径，而项目里头像已经存到 OSS 里了，再拼几个前缀就不合适

    * 基础篇时已经改过这个 bug：如果返回的图片并不在若依的本地存储、返回的是一个以 HTTP 开头的地址，前端就不会再拼这个前缀

* **改动位置与写法**

    * 在 `imageUpload` 组件的第 96 行位置增加一个判断：如果返回的文件名包含了 HTTP，就不再做拼接直接返回 URL

    ```javascript
    // 如果后端返回的文件名里包含 http，说明它给的是完整的 OSS 地址
    // 此时不再拼接 localhost + 请求前缀，直接返回 URL
    if (fileName.indexOf('http') > -1) {
      return fileName;
    }
    ```

* **重启与验收**

    * 因为涉及坐标导入，热更新不好使，需要重新启动后端项目

    * 清除原有头像请求记录后重新上传，返回的文件名、新文件名以及 URL 已经改为阿里云 OSS 的请求地址

    * 结果**按年、月、日为单位做目录分级**，还顺带实现了随机文件名的生成

    * 阿里云控制台刷新后 `dk/images/` 下面出现当天日期的文件夹，里面就是刚上传的员工头像

    * 将来保存员工时把这个地址存进数据库，后期访问员工头像就不再用本地存储而改用 OSS

* **集成流程五步小结**

    * 从官方文档导入 x-file-storage 的坐标 + 对应云平台的坐标

    * 在 `application.yml` 里加基础配置和对应云平台配置，注意缩进对齐、名称对应、域名末尾的正斜杠

    * 在启动类上加 `@EnableFileStorage`

    * 注入 `FileStorageService` 一行代码完成上传

    * 返回结果统一改成 URL

    * 设备管理下面有三个页面：设备类型管理、设备管理、设备状态

* **设备类型管理**

    * 商场上的设备有卖饮料的、卖零食的、卖盲盒的，通过类型分类管理

    * 不同类型的设备，其货道行列以及设备容量都有区别

* **设备管理**

    * 设备就是商场里看到的智能售货机，每台都带编号、型号、点位、合作商、设备状态这些信息

    * 设备内部有多个货道，货道负责摆放商品、提供销售

* **设备状态**

    | 页面 | 定位 |
    | :--- | :--- |
    | 设备状态 | 与设备管理共用**同一套后端代码**，但主要用于查询 |
    | 设备管理 | 主要负责业务功能实现：添加设备、货道管理、策略管理、修改管理等等 |

* **角色分工**

    * 管理员在系统中录入设备信息，员工负责设备的投放和商品补货

    * 也就是先有设备信息，再完成补货或投放的任务

### 业务流程

* **从定义型号到自动生成货道**

    ```text
            后台管理人员登录帝可得后台管理系统
                            │
                            ▼
          定义新的售货机型号（即设备类型）
            └─ 设置规格：货道的行数、列数，以及货道容量
                            │
                            ▼
            在设备管理中允许添加新的售货机实例
                            │
                            ▼
                  把设备分配到特定的点位
                            │
                            ▼
       系统为每一个添加的设备，自动创建对应类型的货道
                            │
                            ▼
                货道用于后续关联相应的商品（SKU）
                            │
                            ▼
              为商品管理和销售做好准备工作
    ```

* **要点**

    * 左侧零食机、右侧饮料机就是设备类型；每个设备都要先选类型再选投放的点位

    * 每一个设备一定属于某一个类型，类型不同设备的货道也有区别

    * 新增设备时只勾选三个表单项：设备编号、设备的型号、选择的点位

### 设备类型表

* **列表主字段**

    | 字段 | 含义 |
    | :--- | :--- |
    | 主键 | 自增 |
    | 型号名称 | 列表中有展示 |
    | 型号编码 | 列表中有展示，每个型号都对应一个编码 |
    | 设备图片 | 该设备类型的图片 |
    | 货道行数 / 货道列数 | 该设备类型货道的行列大小 |
    | 货道容量 | 每个货道可以容纳多少个商品 |

* **新增对话框字段**

    * 型号名称、型号编码、货道的行和列、货道的容量，以及该设备的图片

* **与员工表的同构点**

    * 主键自增对应勾选项、编号与名称分离、图片字段——与人员管理里的表设计套路一致

### 设备表

* **设备编号为什么不用主键**

    * 设备编号也是该设备的唯一标识，但主键自增拿来做编号会暴露信息——外面的人甚至竞争对手就知道公司一共有多少台设备

    * 设备编号可以设置成无规律的，内部有一定编码方便管理，外部无法判断有多少台设备

    * 页面原型的「设备编号」搜索条件对应数据库里的 `inner_code` 字段

* **其他字段**

    * 设备容量：即设备类型的货道容量；**容量字段是由后台填充的**

    * 设备所属的点位 id 以及点位的详细地址，详细地址可根据点位 id 查点位表补充

    * 上次的补货时间：由运营工作人员补完货以后更新的记录时间

    * 所属商圈类型、所属区域 id、所属合作商 id 以及设备型号，其中合作商 id 和设备型号在列表中有展示

    * 设备的运行状态：由物联网通过 EMQ 的 MQTT 协议上传

    * 设备 GPS 上传的经纬度坐标、连接 EMQ 的 client id

    * 策略 id：例如定义 9.8 折、9.7 折，每一个折扣对应一种策略，这个功能后续再实现

    * 创建时间和更新时间

* **修改对话框的边界**

    * 设备编号、供货时间、类型、设备容量、所属点位、合作商、所属区域以及设备地址——修改时**只支持设备点位的修改**，其他数据只做回显

    * 若依生成的新增与修改对话框是同一个，这部分后续还要改造

### 设备状态的三个取值

* **`vm_status` 字段**

    | 取值 | 含义 |
    | :--- | :--- |
    | `0` | 未投放 |
    | `1` | 运营 |
    | `3` | 撤机 |

* **状态流转**

    * 刚添加的设备应该是未投放状态

    * 工作人员投放完毕以后改为运营状态

    * 点位运营一段时间后销售数据太差甚至亏钱，就撤机，修改状态后再重新投放

    * 属于静态数据，所以可以设置为数据字典来简化查询操作

### 售货机货道表

* **表的定位**

    * 没有独立的页面，是集成在设备管理视图页面当中的一个组件

    * 在设备创建时确定了设备类型、知道了几行几列之后产生的货道信息

* **主要字段**

    * 主键自增、货道编号

    * 每个货道所关联的商品（比如可口可乐的 SKU id）

    * 该货道所属的设备 id（也叫售货机 id），以及设备编号

    * 货道的最大容量：对设备的容量，指每个货道允许存放多少件商品

    * 货道的当前容量：最大容量 10、已卖 4 件时当前容量是 6；当前容量置零说明该货道商品已售完

    * 上次的补货时间：每次补货都记录，下次补货前可查询

    * 创建时间以及修改时间

* **货道编号的规律**

    * 每一台设备有多个货道：第一行第一列叫 `1-1`，第一行第二列叫 `1-2`、`1-3`、`1-4`、`1-5`，第二行就是 `2-1`、`2-2`、`2-3`

    * 每个货道都要有唯一编号，方便对商品进行管理；编号由货道的行跟列组成

### 三组一对多与四个冗余字段

* **三组关系**

    * 一个点位下可以投放多台设备 ⇒ 设备表中有「点位 id」外键；既可按点位 id 查该点位下的设备列表，也可按点位 id 查该设备的点位信息

    * 一个类型下有多个设备 ⇒ 设备表中有 `vm_type_id` 外键指向设备类型表；将来可通过型号编码查出该型号下的设备列表

    * 一台设备有多个货道 ⇒ 货道表中有 `vm_id` 外键指向设备表；设备确定型号后通过行跟列添加货道表数据

    ```text
       点位表 ──1:N──► 设备表 ◄──1:N── 设备类型表
                          │
                          │ 1:N
                          ▼
                   售货机货道表
    ```

* **设备表上的四个冗余字段**

    * 详细地址、商圈类型、区域 id、合作商 id，其实都属于点位表

    * 有了它们可以直接查询「该区域下」「合作商下」「商圈类型下」的设备信息

    * 每个设备都要有具体详细地址，有冗余字段就无需再查点位表，简化 SQL 操作、提升查询效率

    * 与人员管理里冗余 `regionName`、`roleCode`、`roleName` 是同一种手法

## 设备管理的基础代码生成

### 目录菜单与设备状态字典

* **目录菜单的字段取值**

    * 入口：系统管理 → 菜单管理 → 新增，上级菜单选「主目录」，菜单类型为目录

    * 图标在图标下拉的最后位置已有设备管理图标；名称叫「设备管理」

    * 显示排序看原型：工单第一、点位第二、设备管理第三，所以录入 **3**

    * 路由地址使用设备缩写 `vm`，其余默认值

* **设备状态的数据字典**

    * 入口：字典管理，先添加字典类型，名称叫「设备的状态」，字典类型值为 `vm_st`

    | 字典标签 | 字典值 | 显示排序 |
    | :--- | :--- | :--- |
    | 未投放 | 0 | 1 |
    | 运营 | 1 | 2 |
    | 撤机 | 3 | 3 |

### 设备类型表的生成配置

* **条件查询**

    * 前端原型上只有一个「型号名称」的搜索，将来可能按编码搜索，所以这两个条件先保留，保证生成的动态 SQL

    * 其他条件——图片、行列、容量——先去掉

* **列表展示**

    * 第一列型号名称对应型号名称，第二列型号编码没问题，第三列设备图片也没问题

    * 第四、第五列对应货道的行和列以及设备的容量

    * 还有一个创建日期字段，提供的开发数据库里并没有这个字段，所以先不做展示

* **新增对话框**

    * 主键自增的对勾先去掉

    * 新增型号名称、编码、设备图片、货道的行和列以及设备的容量，与原型保持一致

    * 修改和新增用的是同一个对话框，勾选保持一致即可，再给这几个表单项设置必填

* **生成信息**

    * 生成模板为单表，前端类型为 VUE3；包路径与模块名都改为 `manager`

    * 业务名若依默认给的是 `type`，目前看合理因为它表示设备类型；但将来还会添加商品类型，也叫 `type` 就会混淆

    * 所以增加前缀改成 `vmType`，把 `t` 改为大写，这就是生成的业务名

    * 生成的功能名补上「管理」两字叫「设备类型管理」，上级菜单改为「设备管理」

### 设备表的生成配置

* **条件搜索的取舍**

    * 页面原型只有一个「设备编号」，对应数据库的 `inner_code` 字段

    * 取消：设备容量、上次补货时间、经纬坐标、客户端连接 id、策略 id

    * 保留：点位 id（将来要统计某点位下的设备列表）、详细地址、商圈类型、区域 id、合作商 id（可能作为条件查询）、设备型号与设备状态与运行状态（将来也可能作为条件搜索）

    * > **提示**：页面原型只需要一个条件，但后续业务中这些动态 SQL 要保留好查询——宁可多留几个条件，后面删比现在猜要容易

* **列表展示的取舍**

    * 设备编号没问题，第二列展示设备的型号；设备容量与点位 id 取消，详细地址保留；上次补货时间保留

    * 商圈类型与区域 id 取消；**合作商 id 保留**，将来需要展示合作商名称，先拿它占个位置

    * 设备状态保留并改为数据字典、做成下拉框，字典类型选「设备状态」；运行状态保留

    * 经纬度、客户端连接 id、策略 id 取消

* **新增对话框的取舍**

    * 主键取消，保留设备编号的文本框

    * 选择型号（设备类型）提供下拉框；通过设备型号可以给该设备设置容量，所以**容量字段由后台填充，这里取消**

    * 选择点位对应点位 id，勾选剩下的详细地址字段——将来可根据点位 id 查点位表补充，所以由后台生成

    * 上次补货时间是工作人员补完货之后填充的，新增时不需要，取消；商圈类型、区域 id、合作商 id 同样可通过点位表查询获取、由后端提供，取消

    * 设备状态前端新增时不提交——刚创建的设备应该是**未投放**，投放成功后系统改为运营，下线后改为撤机，设一个默认状态就行

    * 运行状态由智能售货机通过物联网 MQTT 协议实时上传，新增时不提交；经纬度坐标需要上传；客户端连接 id 取消；策略 id 在刚创建的设备里不需要，取消

    * 创建时间和修改时间都由后端生成

    * 勾完发现新增对话框**只剩下三个**：设备编号、设备的型号、选择的点位

* **修改对话框**

    * 若依生成的新增和修改对话框是同一个，这里先保持一致

    * 「编辑」对勾先取消掉，跟新增保持一致

    * 必填项只保留**点位 id 和设备的型号**——设备编号由系统自动生成不是前端录入，必填先取消

* **生成信息**

    * 模板单表、前端类型 VUE3、包路径 `manager`、模块名 `manager`

    * 业务名用「设备」两个单词的缩写简称为 `vm`

    * 生成的功能名跟原型保持一致叫「设备管理」，上级菜单叫「设备管理」

### 货道表的生成配置与导入

* **只生成后端代码**

    * 货道并没有单独的页面原型，是紧密集成到设备管理视图页面当中的一个组件

    * 只需要后端代码即可，它能支持货道的创建和商品配置的管理

    * 插入、编辑、列表使用默认配置

    * > **提示**：查询条件多多益善，将来使用的是动态 SQL，支持多场景查询

    * 生成信息：包路径 `manager`，模块名 `manager`，业务名就叫「货道」不需要调整；功能名没有二级菜单所以无所谓，上级菜单先选为「设备管理」

* **导入的顺序与排除项**

    * 选中三张表点击「生成下载」，保存后右击解压；解压目录第一个是 SQL 目录，第二个是 vue 目录，另有三个动态菜单 SQL 脚本

    * 先导 SQL 菜单：三个动态菜单脚本要**排除货道的**，只导入设备和设备类型的两个

    * 再导前端代码：API 部分货道不需要复制，只复制设备和设备类型的到 `api` 目录下的 `manager`

    * 视图组件在 vue 目录的 views 下找到 `manager`，同样只复制设备和设备类型的两个文件夹

    * 最后导后端：复制 java 目录下的 `java` 和 `resources` 两个目录，粘贴到业务模块的资源路径下

    * > **提示**：后端代码复制这部分建议重启工程，保证 target 目录下是最新的代码

* **验收**

    * 重启后点「设备管理」正常展示设备数据，按设备编号搜索没问题；「设备类型管理」展示设备类型信息，按设备名称搜索也没问题

    * 增删改查功能若依已经实现，剩下的差异留给后续的页面改造

### 二级菜单的显示排序

* **默认值冲突**

    * 若依生成的二级菜单排序默认都是 1

    * 页面原型里「设备管理」目录下第一位是设备管理（保持 1 不动），第二位留给后面要加的设备状态，第三位是设备类型管理

    * 所以要到系统管理的菜单管理里，把「设备类型管理」的显示排序改为 3

    * 改完之后刷新，一、三的顺序就没问题了；将来设备状态的菜单在这里面添加并把排序设置为 2 就行
