# 权限注解与业务模块二次开发

## 权限注解与权限校验

### 方法级权限注解 @PreAuthorize

   * **@PreAuthorize（方法级权限注解）**

       * > **定义**：Spring Security 框架提供的方法级权限注解，值是一段 SpEL 表达式，在方法执行之前完成权限校验；权限够了就放行执行后续代码，权限不够就直接拦截。

       * 注解的值相当于调用了 `ss` 对象的 `hasPermi` 方法，该方法接收一个参数，这个参数就是权限字符串。

       * 写法为 `@PreAuthorize("@ss.hasPermi('course:course:list')")`，用户必须拥有这个权限字符串才能执行该方法。

       * 方法执行前的判断动作发生在方法体内部，用户登录成功后带着自己的权限去匹配这个方法所需要的权限，存在则执行，不存在则拦截并提示权限不足。

       * 代码生成器为每个方法都添加了相应的权限注解，保证只有具备相应权限的用户才能访问对应功能，避免权限滥用和未授权访问。

   * **课程管理的权限标识**

       * 课程管理菜单下的每个按钮后面都跟一个权限标识字符串。

       * 列表按钮的权限标识是 `course:course:list`，查询按钮是 `course:course:query`，新增、修改、删除同理各自一个权限标识。

       * 用户登录成功以后就能查询到自己的权限标识，执行方法时拿方法所需的权限与用户的权限列表逐一比对。

### 权限标识与 RBAC 权限模型

   * **RBAC 权限模型**

       * 登录成功以后，基于 RBAC 权限模型就可以查到该用户是否具有指定的权限。

       * 案例中的「小智」用户关联了「科研人员」这一个角色，同时分配了「课程管理」和「统计分析」两个菜单权限。

       * 一个用户可以关联多个角色，所以登录时装载的是角色集合而不是单个角色。

       * 角色身上也带权限字符串，角色管理里的修改操作能看到角色的权限字符串，这个权限既能控制菜单也能控制角色。

       * 用户登录成功后就知道自己的基本信息、角色信息和权限列表：基本信息包含昵称、登录地点、登录 IP、登录时间。

### 菜单可见不等于按钮可用

   * **权限校验真正生效的表现**

       * 把课程管理的权限字符串删掉之后，小智用户仍然能看到课程管理菜单，但点击执行查询时后端提示权限不足。

       * 演示路径是：先用小智登录确认课程列表原本能查到 → 退出后用超级管理员 admin 登录 → 菜单管理中修改课程管理，把权限字符串干掉 → 再退出并重新登录小智。

       * 前端菜单渲染只依赖菜单本身，权限校验发生在后端方法执行前，两者是分离的。

       * > **注意**：菜单看得见、按钮点不动，才是权限校验真正起作用的地方；绕过前端直接调后端接口同样会被拦截。

## 权限控制流程

### 登录成功时装载权限

   * **登录后的信息装载**

       * 用户访问后台系统完成登录，登录成功后紧接着获取用户信息。

       * 先取基本信息：昵称、登录地点、登录 IP、登录时间。

       * 再取角色集合，因为一个用户可关联多个角色，每个角色身上也有权限字符串。

       * 最后根据角色查询它的菜单权限，把每个菜单权限放进同一个集合，合并成一份权限列表。

### 访问功能时逐一比对

   * **@PreAuthorize 的执行**

       * 用户访问课程列表时，方法被 `@PreAuthorize` 注解拦截，通过 `ss.hasPermi` 方法进行权限校验。

       * 校验过程是先获取当前登录用户信息，判断当前权限是否在登录用户的权限列表当中，逐一匹配比对。

       * 命中 `course:course:list` 就放行，执行后续代码并返回课程列表；匹配不到就拦截，给前端提示权限不足。

```text
  登录成功
     │
     ├─ 基本信息：昵称 / 登录地点 / 登录 IP / 登录时间
     ├─ 角色集合：一个用户可关联多个角色，角色身上也有权限字符串
     │            （既能控菜单，也能控角色）
     └─ 菜单权限列表：按角色查出来，合并成一份权限列表
     │
     ▼
  带着这份权限去访问业务功能
     │
     ▼
  请求课程列表 → 命中 @PreAuthorize → ss.hasPermi('course:course:list')
     │
     ▼
  从登录上下文取出当前用户的权限列表，逐一比对
     │
     ├─ 命中 → 放行，执行后续代码，返回课程列表
     └─ 没命中 → 拦截，提示权限不足
```

   * > **提示**：先应用而后原理——先掌握权限注解的作用与配置方式，保证能在此基础上做功能扩展和定制开发，熟悉之后再看源码剖析就容易理解了。

## 前端请求链路

### 视图组件的 getList

   * **getList（列表查询方法）**

       * 课程管理接口文档为 GET 请求，路径 `/course/course/list`，请求参数分两部分：分页参数和课程条件。

       * 后端执行业务操作和数据库查询后，把结果封装成分页对象返回，返回体固定四个字段：`code` 状态码、`msg` 消息内容、`total` 总记录数、`rows` 课程列表集合。

       * 打开课程管理的视图组件页面，页面最后一行就是视图组件，加载完毕以后调用查询接口完成数据回显，执行的正是 `getList` 方法。

       * 方法第一行开启表格的加载状态 `loading.value = true`，第二行调用 api 里的 `listCourse` 方法，传入查询对象，成功后返回的 `response` 里包含课程列表和总条数。

       * 增加查询条件后点击搜索按钮或刷新按钮，都会再次触发该接口的调用。

   * **listCourse（API 接口函数）**

       * 定义在前端的 course.js 文件里，为简化 axios 请求的发送，直接调用 `request` 工具类。

       * 传给工具类的是请求路径、请求方式、请求参数三项，严格按 API 接口文档指定。

       * 具体写法为 `url: '/course/course/list'`、`method: 'get'`、`params: query`。

### request.js 的 axios 实例

   * **axios 实例创建**

       * 工具类位于前端工程 `src/utils/request.js`，文件开头用 `@` 别名导入，`@` 相当于 src 根路径。

       * 通过 `axios.create` 创建请求实例，创建时传两个参数。

       * `baseURL` 作用是 axios 发送请求前为地址拼接一个前缀，这个前缀不写死，而是读取当下的环境文件。

       * `timeout` 指定请求超时时间，单位是毫秒，设置为 `10000`，即请求超时时间是十秒钟。

   * **三套环境文件与 VITE_APP_BASE_API**

       * 项目共有开发环境、生产环境、测试环境三个环境文件，`npm run dev` 这个 dev 指的就是开发环境配置。

       * 开发环境文件里的 `VITE_APP_BASE_API` 变量就是拼接的前缀，它会拼接 `/dev-api`。

       * 不写死前缀是因为测试环境、生产环境的地址不同，准备三套文件后按需选择读取，前缀可以动态切换。

### 两个拦截器

   * **请求拦截器**

       * 第一部分是问是否要设置 token，token 就是用户的登录信息，登录成功后访问后端代码必须携带 token，后端拦截器才会放行，没有携带则认为权限不足，需要重新登录。

       * 代码中先获取前端登录后的 token 并判断是否携带，条件成立就在请求头写入授权信息 `Authorization`，新增、修改、删除功能默认携带这个 token。

       * 第二部分是防止表单重复提交，后面几段是 GET 请求拼接 URL 地址参数的逻辑，与防重复提交参数对应，另外还有请求大小的限制。

   * **响应拦截器**

       * 拿到 response 结果后，在返回之前做增强。

       * 后端没有返回状态码时，这里设置一个 200 的成功状态。

       * 单独取出错误消息；如果是二进制文件就直接返回。

       * 后端返回状态码为 401 表示权限不足，跳转到登录页面重新登录，并给出提示信息。

       * 再往下按各种状态码给用户提示信息展示，只有 200 才返回成功。

### vite 代理转发

   * **地址不匹配的问题**

       * 前端发送请求时指定 localhost，端口默认 80，请求地址带 `/dev-api` 前缀；后端基于 Tomcat 运行，端口 8080，路径没有前缀，直接是课程列表地址。

       * 前端没有直接向后端发请求，后端却能收到并返回结果，靠的是前端的代理转发实现跨域访问。

   * **server.proxy 配置**

       * 代理转发配置在前端工程的 `vite.config.js` 中，`server` 配置项设置当前服务器端口为 80，往下的 `proxy` 就是代理转发选项。

       * `proxy` 专门拦截请求路径包含 `/dev-api` 前缀的请求，转发给目标服务器 `localhost:8080`。

       * `target` 指定后端转发的服务器地址 `http://localhost:8080`。

       * `rewrite` 重写操作使用正则表达式，把以 `/dev-api` 开头的请求路径替换为空串，这样才能向 8080 端口发送请求。

       * > **结论**：前端拼 `/dev-api` 不是为了把它发给后端，而是故意拼一个前缀好让 vite 的 proxy 认出来；认出来之后转发到 8080，再把前缀用正则抹掉，后端收到的才是它认识的地址。

```js
export default defineConfig({
  plugins: [vue()],
  server: {
    port: 80,
    proxy: {
      '/dev-api': {
        target: 'http://localhost:8080',
        rewrite: (path) => path.replace(/^\/dev-api/, '')
      }
      // ... 其它模块的代理项
    }
  }
});
```

```text
  course.js（视图组件最后一行的 getList）
        │  url: /course/course/list，method: get，params: 分页 + 课程条件
        ▼
  request.js —— 创建 axios 实例
        │      baseURL = VITE_APP_BASE_API  →  /dev-api
        │      timeout  = 10000 毫秒（十秒）
        │      请求拦截器：带 Authorization、加防重复提交标记
        │      响应拦截器：认状态码，401 跳登录页，只有 200 才算成功
        ▼
  实际发出的地址：/dev-api/course/course/list?...
        │
        ▼
  vite.config.js 里的 server.proxy
        │      匹配 '/dev-api'  →  target http://localhost:8080
        │      rewrite：正则把 ^/dev-api 替换成空串
        ▼
  localhost:8080/course/course/list
        │
        ▼
  tomcat → CourseController#list
        │      ① 开启分页  ② 执行 SQL（count + limit 两条）  ③ 封装分页对象
        ▼
  响应回到前端 → 响应拦截器加工 → 视图渲染表格
```

### 后端接收与分页增强

   * **CourseController#list 的三步**

       * 在课程 Controller 的 `list` 方法上打断点，浏览器重新发送请求就能进来。

       * 第一步开启分页，分页底层用的拦截器会对第二步的 SQL 做增强，一分为二：先查询总记录数，再查询当前页的 SQL。

       * 清空日志放行第二步，可以观察到执行了两条 SQL，第一条是 count 统计，第二条带 limit 分页。

       * 第二步执行完，第三步把数据封装成分页对象返回给前端，前端拿数据展示。

       * 断点停留太久时数据来不及回显，前端会一直处于表格加载状态，再次刷新就正常。

   * **框架修改器**

### sky-merchant 子模块三步

   * **创建商家管理子模块**

       * 第一步：在 IDEA 右击父工程新建子模块，选择 Maven 结构，模块名填 `sky-merchant`，点击分析和创建。

## 菜品管理的主子表需求

### 五个公共接口

   * **接口清单**

       * 菜品加条件的分页搜索查询。

       * 新增菜品，包含菜品名称、售卖状态、菜品价格、菜品图片、菜品描述这些基本信息，还要包含菜品的口味列表。

       * 一个菜品可以设置多个口味，先选择口味名称，在名称后方添加口味列表，例如甜度可以选择半糖、全糖、无糖，还能再增加第二个口味。

       * 修改和新增用同一套页面，包含两个接口：一个是数据回显，一个是更新数据库。

       * 删除操作，支持单个删除也支持批量删除。

       * 新增、修改、删除三个动作都涉及菜品表和口味表两张表的操作。

### 主表与子表的一对多

   * **菜品表（主表）**

       * 字段包含菜品 id、菜品名称、菜品价格、菜品图片、菜品描述、售卖状态、创建时间、更新时间。

       * 售卖状态取值为 `0` 停售和 `1` 起售，起售状态下的菜品用户才能通过商家下单，这部分要设计为数据字典。

   * **口味表（子表）**

       * 字段包含口味主键、菜品 id 的外键字段、口味名称、口味选项，口味选项可以提供选择多个的列表。

       * 通过这个外键字段与菜品表的主键建立一对多关联关系，一个菜品对应 N 条口味。

       * 菜品口味表不会单独生成前后端页面，而是与菜品管理融合到一起实现业务操作。

   * **主子表模板带来的便捷**

       * 主子表模板的界面分成两部分，前半部分是菜品的基本信息，与单表操作类似。

       * 后半部分增加了口味的关联操作，点添加按钮可以增加多个口味选项，让用户一次完成菜品和口味的新增。

```text
   菜品表 dish（主表）              口味表 dish_flavor（子表）
   ------------------------        ---------------------------------
   id           主键                id           主键
   name         菜品名称             dish_id      外键 -> 菜品表.id
   price        菜品价格             name         口味名称
   image        菜品图片             options      口味选项（可提供多个）
   description  菜品描述
   status       售卖状态 0停售/1起售
   create_time  创建时间
   update_time  更新时间

   一对多：一个菜品 -> N 条口味；新增/修改/删除都要同时动这两张表
```

## 代码生成器三步曲

### 导入两张表

   * **导表操作**

       * 资料里已经准备好菜品管理的两张建表语句以及部分测试 SQL。

       * 打开数据库客户端工具，右击运行 SQL 脚本，定位到菜品管理，点击 OK 执行。

       * 执行完成后往下拉检查，能看到菜品表和口味表即导入成功。

### 配置代码生成信息

   * **基本信息与字段信息**

       * 在系统工具里打开代码生成界面，先导入菜品管理和菜品口味两张表。

       * 编辑菜品管理的基本信息时改两处：实体类名称去掉 `tb` 前缀，作者改成 `it黑马`。

       * 字段信息决定最终页面展示效果，必须对照页面原型勾选，不能乱选。

       * 字段信息以列为单位：第一列是读取数据库的字段列名；第二列是字段描述，决定页面展示效果；主键页面不展示不用改，菜品名称与原型对应没问题。

       * 菜品价格在原型里叫「售价」，字段描述要跟着改成售价；`status` 字段要改描述为售卖状态。

       * 描述信息前端没有展示，不做修改；物理类型、Java 类型不需要修改，Java 属性与字段名一一对应保持同风格。

       * 菜品名称、售价、图片、售卖状态、创建时间、更新时间这些 Java 属性同样不需要修改。

       * 菜品名称、售价、图片、菜品分类、描述信息、售卖状态、创建时间、更新时间这几列的勾选规则如下。

| 字段 | 列表（页面展示） | 查询（查询条件） | 处理动作 |
| :--- | :--- | :--- | :--- |
| 菜品名称 | 勾选 | 勾选 | 模糊查询 |
| 售价 | 勾选 | 勾选 | 字段描述由「菜品价格」改为「售价」 |
| 图片 | 勾选 | 不勾 | 原型不按图片查 |
| 菜品分类 | 不勾 | 不勾 | 本次关注主子表生成，分类暂时不处理 |
| 描述信息 | 不勾 | 去掉勾选 | 前端不展示也不作为查询条件 |
| 售卖状态 | 勾选 | 勾选 | 原型上是下拉框，需要数据字典 |
| 创建时间 | 不勾 | 不勾 | 原型不展示 |

| `d` | 日 |
| `h` | 小时 |
| `i` | 分钟 |


### 图片回显：前缀被拼了两遍

   * **问题现象与定位**

       * 「新增毛血旺」这一行点修改图片能回显，其余测试数据随便点开再换一张图片就无法回显，但列表里所有图片都能展示，说明图片路径本身是对的。

       * 查数据库发现：预置的测试数据图片保存在阿里云 OSS，而「新增毛血旺」的图片是若依默认保存到本地服务器的。

       * 本地保存的位置在配置文件第 10 行指定，形如 `/profile/upload/2024/...`，到 D 盘对应路径下能看到这次上传的图片。

   * **两种路径的本质区别**

       * 阿里云存储的图片都以 `http` 开头，组成完整的资源访问路径，可以直接访问并回显。

       * 若依本地存储的仅仅是服务器内部的资源地址，不包含 `http`，只有 `/profile/upload/...` 不能单独直接访问。

       * 按 `F12` 打开 Network 抓包可以看到，图片上传组件回显时会拼一个前缀 `http://localhost/dev/api`，再跟上数据库里存的值。

```text
数据库里存的 image 值                  ImageUpload 拼前缀后的最终 URL
──────────────────────────────────────────────────────────────────────────
/profile/upload/2024/毛血旺.jpg  →  http://localhost/dev/api/profile/upload/...
https://oss.aliyuncs.com/a.jpg  →  http://localhost/dev/api/https://oss.aliyuncs.com/a.jpg
                                       ↑ 前缀重复，这串地址根本不存在
```

   * **改上传组件源码**

       * 修复思路是给图片上传组件加一个判断：图片路径如果以 `http` 开头就不拼接前缀，直接显示。

       * 按住 `Ctrl` 键可以跳转到 `el-image-upload` 标签的源代码，关注两个位置。

       * 第 81 行附近 `const baseUrl = ref(import.meta.env.VITE_APP_BASE_API)` 读取当前环境的 URL 前缀，这个变量就是用于拼接的。

       * 第 97 行附近因为支持多图片上传，完成了一个 `forEach` 遍历，`item` 就是图片路径，拼接 `baseUrl` 组成了完整路径。

       * 原有代码就有一个判断：用 `indexOf` 检查 `item` 中之前有没有包含 `baseUrl` 地址，包含就不拼接直接返回 `item`。

       * 在这个判断里再加第二个条件 `item.indexOf('http') !== -1`，图片路径包含 `http` 同样不再拼接，直接返回图片路径。

```js
props.fileUrls.forEach((item, i) => {
  if (item.indexOf(baseUrl.value) !== -1 || item.indexOf('http') !== -1) {
    fileUrls.value.push(item)
  } else {
    fileUrls.value.push(baseUrl.value + item)
  }
})
```

## 口味列表改造

### 为什么不用数据字典

   * **联动需求否掉字典方案**

       * 口味名称和口味列表需要做到数据联动，即根据选中的口味名称展示不同的选项列表。

       * 数据字典不支持这种联动，所以这个方案 pass 掉，改为手动在前端定义静态数据供下拉框加载。

       * 随之而来的新问题是静态数据的格式该怎么定义，同时还要实现数据联动。

### 静态数据结构

   * **照着提交格式抄**

       * 参考前端表单提交的口味 JSON 格式，下半部分的口味列表 `dishFlavorList` 存储了多个口味对象。

       * 每个对象存储两个字段：口味的名称 `name`，以及口味列表的选项标签数组 `value`。

       * 前端遍历时左侧位置遍历所有 `name` 展示辣度、忌口等等，右侧位置根据 `name` 去查找对应的 `value` 展示选项数据。

       * 变量命名不能跟前端提交的 `dishFlavorList` 一致，否则会冲突，另起新变量名 `dishFlavorListSelect`。

       * 定义一个响应式数组，里面存放完整的口味名称和口味列表，内容参考数据库口味表已有的辣度、忌口、甜味三组数据替换粘贴。

       * 数组元素之间要记得加逗号分隔，屏幕上置灰的就是漏写的那个，后期追加数据往后加即可。

```js
// ===== 二次开发：口味下拉框静态数据 =====
const dishFlavorListSelect = ref([
  {
    name: '辣度',
    value: ['不辣', '微辣', '中辣']
  },
  {
    name: '忌口',
    value: ['不要葱', '不要蒜']
  },
  {
    name: '甜味',
    value: ['少糖', '无糖']
  }
])
```

### 口味名称改成下拉框

   * **改造位置与写法**

       * 原本口味名称是文本框，在对话框代码第 150 行附近，先注释掉再改造成下拉框。

       * 使用 `el-select` 标签，同样需要双向绑定和占位符提示，`v-model` 和 `placeholder` 可以直接从原输入框拿过来。

       * `v-model` 绑定要提交的 `name` 数据，`placeholder` 由输入提示改成「请选择」。

       * 用 `el-option` 遍历静态数据，`v-for` 遍历的集合改成 `dishFlavorListSelect`，元素变量名取 `dishFlavor`。

       * `key`、`label`、`value` 三者展示的都是 `name`，都要跟着改；`label` 是用户最终看到的下拉框内容，`value` 是最后提交的内容。

```html
<el-form-item label="口味名称" prop="name">
  <el-select v-model="form.dishFlavors[scope.$index].name" placeholder="请选择">
    <el-option
      v-for="dishFlavor in dishFlavorListSelect"
      :key="dishFlavor.name"
      :label="dishFlavor.name"
      :value="dishFlavor.name"
    />
  </el-select>
</el-form-item>
```

### 联动、多选与清空

   * **changeFlavorName 方法**

       * 先定义一个存储当前选中口味列表的数组 `dishValueList`。

       * 再定义方法 `changeFlavorName`，作用是根据名称去查找静态数据的 `value` 并赋给当前选中的口味列表数组。

       * 方法体第一行 `row.value = []` 清空当前行的 value，第二行用 `find` 按 `item.name === row.name` 匹配后取出 `value`。

       * `dishFlavorListSelect.value` 是响应式的数组对象，`find` 方法遍历静态数据，当属性与传进来的选中口味名称一致时就把对应的 value 取出来。

   * **绑定事件与改造口味列表**

       * 给口味名称下拉框绑定改变事件 `@change="changeFlavorName(scope.row)"`，要把当前口味行的对象传过来。

       * 口味列表下拉框可以直接复制口味名称下拉框来改：双向绑定从 `name` 改成 `value`，`placeholder` 改成「请选择口味列表」，删掉改变事件。

       * `el-option` 遍历的不再是静态数据而是选中数组，改成 `dishValueList`，数组中每个元素就是具体的口味标签，变量名取 `value`，`key`、`label`、`value` 都要替换为 `value`。

       * 一个口味可以设置多个标签，默认是单选，要给口味列表下拉框增加 `multiple` 属性支持多选。

       * > **提示**：从辣度改为忌口时，原来选中的辣度口味标签必须被清理掉，这正是方法体里第一行 `row.value = []` 的作用。

```js
// 定义：改变口味名称时，更新当前选中的口味列表
const changeFlavorName = (row) => {
  // 清空当前行的 value
  row.value = []
  // 根据选中的 name 去查找静态数据的 value
  row.value = dishFlavorListSelect.value.find(item => item.name === row.name).value
}
```

```html
<el-form-item label="口味列表" prop="value">
  <el-select
    v-model="form.dishFlavors[scope.$index].value"
    placeholder="请选择口味列表"
    multiple
  >
    <el-option
      v-for="value in dishValueList"
      :key="value"
      :label="value"
      :value="value"
    />
  </el-select>
</el-form-item>
```

### 类型不一致导致的 JSON 解析失败

   * **报错现象与原因**

       * 新增鱼香肉丝选择口味后点确定会报错，后端控制台显示 JSON 解析错误：不能将一个数组的值反序列化为 `String` 类型的字符串。

       * 通义灵码给出的分析是：Jackson 在反序列化时遇到不匹配的输入，它期望字符串，但前端给的是 JSON 数组。

       * 定位方式：浏览器 `F12` 的 Network 里看提交请求体，口味列表中的 `value` 确实是 JSON 数组（不要葱、不要蒜）；IDEA 里看 `DishFlavor` 对象，`value` 字段声明的是 `String` 类型。

   * **为什么不改后端**

       * 数据库存储的 `value` 确实需要字符串类型，把它改成数组的话保存数据库就会报错。

       * 除非在 Service 层里再把这个 List 集合转成字符串进行保存，操作起来比较繁琐。

       * 更好的思路是在前端提交这个 value 之前把它转换成字符串类型的 JSON 数组，这样实体就能接收，后台也正常保存，改造代码更简单。

   * **发送 AJAX 之前转成字符串**

       * 找到新增和修改提交表单的方法，第 323 行附近已经取出了口味列表 `dishFlavorList`。

       * 通义灵码生成的代码是把整个 `dishFlavorList` 转成字符串，这不是我们想要的，期望的是把里面元素的 `value` 属性转成字符串。

       * 所以在它的 `forEach` 基础上改造：遍历元素变量名取 `item`，箭头函数可以直接用，`item.value` 是那个数组集合，用 JSON 工具类的 `stringify` 转成 JSON 字符串再赋回给它。

       * 改完提交时 `value` 会被双引号包裹，后端接收到的就是一个字符串。

       * > **易错点**：这里千万别漏掉非空判断。`forEach` 一旦作用在 `null` 上就是当场空指针，页面直接白屏，写完顺手看一眼比回头排查省事。

```js
// 在发送 ajax 之前将口味列表中的 value 属性转换为 JSON 字符串的格式
if (form.dishFlavorList != null) {
  form.dishFlavorList.forEach(item => {
    item.value = JSON.stringify(item.value)
  })
}
```

   * **回显时再转回数组**

       * 采用提交前转字符串的方案后，点修改按钮回显时口味名称能展示，但口味列表无法回显。

       * 原因是后端返回的这个 `value` 是字符串，前端无法解析，在最后一个返回数据里能看到 value 就是字符串。

       * 解决方式是在拿到后端返回的字符串时把它再转回 JSON 数组：点击修改会向后台发送查询请求，第 313 行附近拿到后端返回的口味列表集合。

       * 通义灵码生成的 `forEach` 功能没问题，但它没考虑后端返回空集合的情况，遍历前必须加非空判断，否则可能空指针。

```js
// 将后端返回的口味列表的 value 字符串转为 JSON 数组
if (res.data.dishFlavorList != null) {
  res.data.dishFlavorList.forEach(item => {
    item.value = JSON.parse(item.value)
  })
}
```

### 回显后标签改不了：focus 事件

   * **问题原因**

       * 口味列表现在能回显数据了，但想在此基础上修改标签时发现无法实现，旧的数据没了。

       * 原因是 `changeFlavorName` 只在点击口味名称时触发，打开修改弹窗时并没有点名称，数组是空的，所以改不了标签。

       * 解决办法是给口味下拉框绑定获取焦点事件，在事件内同样调用方法，根据当前行的口味名称查静态数据，再把静态数据复制给当前列表数组。

   * **changeFlavorNameFocus 方法**

       * 这个新方法**不能**复用 `changeFlavorName`，因为后者多了一行「清空当前行的 value」，共用的话获取焦点会把原有的回显数据清理掉，只展示下拉框的数组数据，回显功能就失效了。

       * 正确做法是复制一份方法，把第一行清空 value 干掉，只保留 `find` 那一行，方法名改成获取焦点 focus。

       * 然后给口味列表下拉框绑定 `@focus="changeFlavorNameFocus(scope.row)"`，同样需要把当前的行对象传过来。

       * 改完后口味列表获取焦点时会根据口味名称查询对应的静态数据，列表展示正常，同时会对回显的数据进行高亮，标签可以动态取消勾选和重新勾选并更新到数据库。

       * > **结论**：两个方法只差一行，语义却完全不同。`@change` 意味着「用户换了一个口味类别」，旧的标签必须清掉；`@focus` 意味着「用户只是要动当前已有选项」，清掉就等于把回显数据自己毁了。复用之前先问一句：这个事件代表的是「切换」还是「查看」？

```js
// 定义：口味列表获取焦点时，更新当前选中的口味列表
const changeFlavorNameFocus = (row) => {
  // 根据选中的 name 去查找静态数据的 value（注意：不清空 row.value）
  row.value = dishFlavorListSelect.value.find(item => item.name === row.name).value
}
```

```html
<el-select
  v-model="form.dishFlavors[scope.$index].value"
  placeholder="请选择口味列表"
  multiple
  @focus="changeFlavorNameFocus(scope.row)"
>
```

### 对话框与列表宽度调整

   * **样式美化**

       * 口味标签每个都独自占一行太丑，先调整对话框宽度，`width` 属性由 500 改为 600。

       * 再把口味列表这一列的宽度设置为 350，浏览器测试后表格宽度增加，但下拉框宽度仍然不够。

       * 在下拉框里增加 CSS 样式，`style` 宽度设置成 90%，之后口味列表就能在一行内展示多个标签。

```html
<el-select
  v-model="form.dishFlavors[scope.$index].value"
  placeholder="请选择口味列表"
  multiple
  @focus="changeFlavorNameFocus(scope.row)"
  style="width: 90%"
>
```

### 改造总览

   * **三条改造主线**

       * 工具线：在 VS Code 和 IDEA 分别安装通义灵码辅助开发，从「解释现有代码」到「按关键词生成新代码片段」，再到「把报错信息丢给它分析」，前端记不住的模板插槽写法、`parseTime` 格式、多选清空这类琐碎逻辑都由它兜住。

       * 列表展示线：售价增加人民币标识符，更新时间增加时分秒，主键列注释掉，并解决回显图片的 bug。

       * 口味列表线：文本框改成下拉框并支持多选，按 `name` 反查 `value` 完成联动，提交前把数组 `stringify` 成字符串对上后端的 `String`，回显时再 `JSON.parse` 转回来。

       * 图片回显 bug 的本质是给 OSS 的完整 URL 加了个「已带前缀就不拼」的判断。

       * 串起来要记住的三个坑：切换口味类别要清空旧标签、回显后要靠 `focus` 事件把静态数据重新灌进下拉框、所有遍历之前都必须先做非空判断。
