# 项目搭建与点位管理建模

## 后端工程搭建

### 初始仓库的预置改造

* **帝可得后端初始仓库**

    ```text
        初始仓库（已改造好）
                |
         fork 到自己账号
                |
        +-------+-------+
        |               |
      后端工程        前端工程
     IDEA 克隆      VS Code 克隆
        |               |
     导库 / 配 Redis   npm install
      启 Application   npm run dev
    ```

    * > **定义**：面向帝可得项目的后端起点工程，已经使用若依框架的代码生成器处理过，可直接使用。
    * 模块的命名以及包的命名，都按照帝可得项目的命名格式设置好了。
    * 已创建存放业务代码的子模块 `dk-manager`。
    * 全项目只需记住两样与帝可得绑定的东西：子模块 `dk-manager`，前缀 `dk`。

* **`dk` 前缀的落点**

    * 数据库名、Redis 里的 key、启动类名都使用 `dk` 这个前缀。

### 四步流程与 Fork 克隆

* **后端搭建四步**

    * 第一步：通过 IDEA 完成 Git 克隆并初始化项目。
    * 第二步：将若依的 SQL 文件导入到数据库中，并修改 Spring Boot Druid 的配置文件，指定数据库的连接地址、用户名、密码等。
    * 第三步：启动 Redis；如果 Redis 设置了密码，配置文件当中也要进行修改。
    * 第四步：启动后端项目。

* **Fork 的目的与克隆入口**

    * 先把初始工程 Fork 到自己的 GitEE 账号，好处是能在自己的账户下面管理这段代码，方便后续的代码编写和 Git 版本控制。
    * Fork 成功后点"克隆"复制仓库地址，在 IDEA 点 `Get from VCS` 粘贴地址、选择开发路径即可完成克隆。
    * 第二次克隆速度会非常快，因为基础篇已经搭建过若依初始仓库并下载好了相关 jar 包。
    * 父工程、子模块都已高亮且加粗，`dk-manager` 就是存放业务代码的地方。
    * > **易错点**：如果父工程和子模块没有高亮加粗，点 Maven 找到父工程，先执行一次清理（clean）再执行一次打包（package），项目会重新初始化加载，直到父工程和子模块都高亮加粗为止。

* **命令行等价写法**

    ```bash
    mvn clean package
    ```

### 导入若依的 SQL 脚本

* **先建库再执行脚本**

    * 数据库客户端里创建帝可得项目的数据库 `dk`，再右击执行 SQL 脚本，把脚本路径粘过来。

* **SQL 目录下的两个脚本**

| SQL 文件 | 用途 | 是否必须导入 |
| :--- | :--- | :--- |
| `quartz.sql` | 定时任务相关 | 项目里的定时任务只是简单配置、不含集群等复杂操作时，不导入也可以 |
| `ry.sql` | 若依自带功能的 SQL 脚本 | 必须导入 |

* **导入结果核对**

    * `ry.sql` 导入成功后一共 19 张表。

### 数据源与 Redis 配置

* **Druid 数据源配置**

    ```yaml
    spring:
      datasource:
        druid:
          master:
            url: jdbc:mysql://localhost:3306/dk
            username: dk
            password: root
    ```

    * 配置位置是 `dk-admin` 下的 Spring Boot Druid 配置文件，url 连本机地址、数据库名 `dk`、账号 `dk`、密码 `root`。
    * > **注意**：连接的数据库环境不一样的话，URL、用户名、密码三样都不能照抄。

* **Redis 密码两端要对齐**

    ```conf
    requirepass root
    ```

    * 项目实战篇要模拟真实的企业开发环境，Redis 不设密码直接连接是不安全的。
    * 在 Redis 配置文件第 503 行找到 `requirepass`，它默认由 `#` 号注释，去掉井号后就在后方指定连接密码。
    * 在 Redis 解压路径右击打开终端，用启动命令让 `redis-server` 加载配置文件。

    ```bash
    redis-server redis.windows.conf
    ```

    * 项目侧的 Redis 配置文件 `application` 里，在第 77 行位置配置 `spring.redis.password`，密码同样为 `root`。

    ```yaml
    spring:
      redis:
        password: root
    ```

    * 密码不是 `root` 的，就在这两处同步修改。

* **Debug 方式启动后端**

    * 启动类是 java 下帝可得的 `Application`，选中 Debug 方式运行。
    * > **提示**：第一次启动项目需要编译，速度会慢一点，不要以为程序卡死了。

## 点位管理的业务场景与流程

### 三个功能模块

* **业务场景链条**

    * 先确定几个有潜力的区域，这些区域可能是人流量大、消费能力高的商业区或居民区。
    * 再与这些区域的潜在合作商洽谈，比如商场、写字楼、学校等地方的管理者或所有者。
    * 洽谈成功、确定合作细节和点位后，安排工作人员投放智能售货机，这些点位就是智能售货机的家。

* **点位管理拆成三个模块**

    ```text
       点位管理
         |
         +-- 区域管理   —— 我们在哪儿
         +-- 合作商管理 —— 跟谁合作
         +-- 点位管理   —— 货机放在哪儿
    ```

    * > **定义**：合作商，就是提供点位的合作伙伴，也可以理解为「点位主」。
    * > **定义**：点位，就是放置智能售货机的具体位置。
    * > **易错点**：**合作商和区域之间是没有关系的。** 合作商拥有的点位可以分布在不同的区域下，它们之间没有直接的关联关系，这一点在设计表结构时会再强调一次。

### 完整业务流程

* **四步业务流**

    ```text
      ① 管理员登录帝可得后台管理系统
                |
                v
      ② 新增区域信息，录入系统
         （如北京北五环奥体中心等区域）
                |
                v
      ③ 录入已达成合作协议的合作商信息
                |
                v
      ④ 在特定区域下新增点位
    ```

    * 后台管理员先登录系统，登录成功后才把区域信息录入系统。
    * 区域确定以后，再把达成合作协议的合作商信息录入系统。
    * 区域与合作商都确定以后，后台管理人员才可以在特定的区域下新增点位。

### 改造前的推进顺序

* **四步走完一轮**

    ```text
      页面原型 + 需求说明
              |
              v
      ① 用 AI 辅助设计表结构（顺带生成测试数据）
              |
              v
      ② 把 AI 生成的 SQL 导入开发数据库
              |
              v
      ③ 用若依代码生成器生成前后端基础代码
              |
              v
      ④ 针对区域 / 合作商 / 点位三个模块做代码改造
    ```

    * AI 辅助设计表结构既能提高设计效率，还能生成符合需求的测试数据。
    * 若依代码生成器能快速生成前后端代码，并直接导入开发环境。
    * > **注意**：生成器产出的基础代码**仅涵盖单表的增删改查操作**，区域管理、合作商管理、点位管理这三个关键模块都必须再按页面原型和业务场景做代码改造。

## 表结构设计

* **设计的下手方式**

    * 设计表结构没有巧办法，就是回到页面原型上一个字段一个字段地看：哪些东西该落库，哪些东西根本不该落库。
    * 按区域表、合作商表、点位表的顺序来做。

### 区域表

* **逐个字段判定**

    * 序号：展示的是 1、2、3 递增的信息，它**并不是数据库的主键**，而是由前端自动生成的；有了它数据列表展示更美观优雅，所以不设序号字段。
    * 区域名称：用来存储每一个区域的信息，需要添加。
    * 点位数：指每个区域下面点位的数量，应该查点位表提供的信息，而不是在数据库中写死，暂时不设。
    * 备注说明：说明每个区域下面的详细信息，需要添加。
    * 新增时需要给这条记录增加唯一标识主键 id，主键设置为**自增**。
    * 修改和新增用的是同一个对话框，里面也需要区域名称和备注说明，两个字段是统一的。
    * 查看详情对话框上半部分展示区域名称、下半部分展示当前区域下面点位的详细列表，这些数据通过点位表查出，区域表不需要这些字段。
    * 删除功能是根据区域的 id 作为主键完成删除的。

* **最终只有三个字段**

| 字段 | 说明 |
| :--- | :--- |
| 区域 id | 主键，自增 |
| 区域名称 | 区域列表展示的实体字段 |
| 备注说明 | 区域详情说明，复用公共字段 `remark` |

### 合作商表

* **列表字段判定**

    * 序号：跟区域管理一样，不需要添加该字段。
    * 合作商名称、账号：需要添加。
    * 点位数：跟区域管理类似，要统计每个合作商下面的点位数量，涉及多表查询，暂时不添加。
    * 分成比例信息那一侧：需要添加联系人以及联系电话。

* **新增与修改的差别**

    * 新增对话框包含合作商名称、联系人、联系电话、分成比例、账号以及密码这些基本字段。
    * 修改对话框跟新增是有区别的：修改时不支持账号和密码的修改，所以这部分被隐藏了。
    * 修改之外单独提供了一个**重置密码**的功能，点击以后把该合作商上的密码设置为初始密码。
    * 删除是根据主键来完成的，查看详情是展示该合作商的详细信息。
    * 确定的主要字段：主键 id、合作商名称、联系人、联系电话、分成比例、账号密码，还有创建时间等等。

### 点位表

* **两个一对多外键**

    * 序号：不需要设置。
    * 点位名称：需要添加。
    * 所在区域：展示的是每个点位所属于区域的名称，数据从区域表查询；一个区域下面有多个点位、一个点位归属于一个区域，是一对多，添加区域外键 `region_id`。
    * 合作商：展示的是该点位所属合作商的信息，名称由合作商表提供；一个合作商下面可以包含多个点位、一个点位仅可归属于一个合作商，也是一对多，添加合作商外键 `partner_id`。

* **商圈类型走数据字典**

    * 商圈类型展示的是学校、写字楼、旅游区等静态数据。
    * 静态数据没有必要浪费数据库空间来存储这些文本信息，用若依的数据字典添加字典类型、字典标签和字典值，商圈类型就设置为数据字典的值，让它跟字典标签对应起来。

* **地址与新增对话框**

    * 详细地址：需要添加该字段。
    * 新增对话框包含点位名称、所在区域（下拉框，提交的是区域的外键）、商圈（通过数据字典展示，提交的是字典值）、归属合作商（展示合作商名称，提交的是合作商外键）、详细地址文本。
    * 修改和新增用的是同一个对话框，字段展示内容一样。

* **详情里的设备不在本表设计**

    * 点位详情展示的是该点位下**设备列表**的信息，而这个设备就是智能售货机。
    * 一个点位可以摆放多台智能售货机，智能售货机的表设计留到设备管理模块再讲，点位表中不设计这一部分。

### BaseEntity 与公共字段

* **业务表要引入公共字段**

    * 构建业务表时通常引入一些公共字段，记录和管理数据的状态以及历史变更，比如创建时间、创建人、修改时间、修改人、备注信息。
    * > **定义**：`BaseEntity` 是若依提供的基类，是每张表对应实体类**默认继承**的一个父类。
    * 通过代码生成器生成的业务实体类都会自动继承它，并拥有它提供的所有属性。
    * 统一使用基类能确保所有业务实体类都包含这些公共字段，简化代码编写与维护，让数据库设计和业务逻辑更规范、更标准化。

* **需要关注的五个属性**

| 属性名 | 含义 |
| :--- | :--- |
| `createBy` | 创建者，就是创建人 |
| `createTime` | 创建时间 |
| `updateBy` | 更新人 |
| `updateTime` | 更新时间 |
| `remark` | 备注 |

    * > **易错点**：区域表里的「备注说明」和 `BaseEntity` 的 `remark` 字段是**同一个含义**，所以区域表的备注说明不需要再单独设计，直接使用 `remark` 就可以。

## 用通义千问生成建表语句

### 提示词的写法

* **先定角色再给需求**

    ```text
    你是一位软件工程师，帮我生成 MySQL 的表结构。
    ```

    * 把 AI 当作一个软件工程师，职责是基于这三张表的主要字段生成 MySQL 的表结构。
    * 表名要尽量给它规范化，不然它自己去起名时看起来比较乱，统一用 `tb_` 前缀加下划线：`tb_region`、`tb_partner`、`tb_node`。

* **三张表的需求描述**

    * 区域表 `tb_region`，主要字段有主键 id、区域名称；备注说明属于所有表的公共字段，一会单独再告诉 AI 生成。
    * 合作商表 `tb_partner`，主要字段有主键 id、合作商名称、联系人、联系电话、分成比例、账号、密码。
    * 分成比例按 int 类型存，存 60% 就写个 60、存 70% 就写 70，不包含小数。
    * 点位表 `tb_node`，主要字段有主键 id、点位名称、详细地址、商圈类型、区域和合作商的外键字段。
    * 商圈类型存的是数据字典的值，所以它也是一个 int 类型；由于涉及多表关系以及外键约束的创建，稍后交给 AI 单独设计，这部分先跳过。

* **其他要求的五条**

    * 每张表都需要公共字段：创建时间、修改时间、创建人、修改人以及备注，且每个字段的命名语法格式严格要求与若保持一致。
    * 每张表的主键都是自增的。
    * 区域表跟点位表是一对多关系，合作商与点位也是一对多关系，请用字段表示出来。
    * 为每个字段添加 comment 注释。
    * 生成北京城市相关的区域、点位、合作商测试数据。
    * > **结论**：一对多关系那条是整个提示词里最重要的一句。有了它，AI 就会在点位表当中添加区域和合作商的外键并添加外键约束，关系设计这件事就彻底交给它了。

### 产出与核对

* **AI 分三段给出**

    * 第一段区域表：id、区域名称、创建时间、更新时间、创建人、更新人、备注信息，并插入测试数据。
    * 第二段合作商表：合作商主键、合作商名称、联系人、联系电话、分成比例、账号密码，下面是公共字段，并插入测试数据。
    * 第三段点位表：点位 id、点位名称、详细地址、商圈类型、区域 id、合作商 id，下面是公共字段，并插入测试数据。

* **粘贴后先核对再执行**

    * 把每一部分复制到数据库客户端的执行命令行窗口粘贴。
    * > **提示**：粘贴之后先别急着执行，**先核对字段**。这一步花不了十秒钟，能省掉后面一晚上的排查时间。
    * 区域表核对出主键 id、区域名称 `region_name`、备注说明 `remark`，没有问题。

| 合作商表字段 | 对应含义 |
| :--- | :--- |
| `id` | 主键 |
| `partner_name` | 合作商名称 |
| `contact_person` | 联系人 |
| `contact_phone` | 联系电话 |
| `profit_share` | 分成比例 |
| `account` | 账号 |
| `password` | 密码 |

    * 点位表核对出六个字段，跟原型分析的一致。

| 点位表字段 | 对应含义 |
| :--- | :--- |
| `id` | 主键 |
| `node_name` | 点位名称 |
| `address` | 详细地址 |
| `business_type` | 商圈类型 |
| `region_id` | 区域外键 |
| `partner_id` | 合作商外键 |

    * 三段全选执行后，数据库建好 `tb_node`、`tb_partner`、`tb_region` 三张表，并分别带着 AI 生成的测试数据。

| 表名 | AI 生成的测试数据条数 |
| :--- | :--- |
| `tb_region` | 3 |
| `tb_partner` | 2 |
| `tb_node` | 2 |

### AI 的缺漏与一致性保障

* **AI 漏掉的东西要自己补**

## 多表查询的两种策略

### 关联查询的风险

* **老方案的隐患**

    * 此前区域和合作商统计点位数量是通过关联查询实现的。
    * 当涉及的表较多、数据量较大时，SQL 的编写难度就会增加。

* **当前场景正好踩中**

    * 如果产生笛卡尔积，数据量就会急剧增加，有可能导致内存溢出的问题。
    * 这个功能一共有四张表，表比较多，而且设备数据量比较大，产生的笛卡尔积有可能导致内存溢出。

### 两种策略的分工

* **设备数量仍执行关联查询**

    * 这种方案可以确保数据的实时性和准确性。
    * 设备数量是实时计算的，不需要单独维护。

* **区域与合作商采用嵌套查询**

    * 采用 MyBatis 提供的嵌套查询功能，结合关联实体完成 ORM 映射。
    * 将原本的多表联合查询拆分成单个表的查询，再利用 MyBatis 语法把它们嵌套在一起。
    * 通过定义的 `resultMap` 标签完成手动映射，里面包含 `association` 以及 `collection` 元素完成嵌套的关联。
    * 好处是把复杂的多表查询分解为更简单、更容易管理的单表查询，简化 SQL 编写、提高查询效率与性能，避免内存溢出风险，同时保持代码整洁和可维护性。
    * > **结论**：设备数量走关联查询（保实时、保准确），区域与合作商走嵌套查询（保简洁、避笛卡尔积）。

## 嵌套查询的映射标签

### association

* **一对一与多对一的封装**

    * > **定义**：`association` 标签用来解决一对一或多对一的映射结果封装，即结果中只有一个对象时完成 O2M 的映射封装。
    * 以点位为中心去查询区域表或合作商表的详细信息时，返回结果集只有一个对象。
    * 一个点位只对应一个区域、也只对应一个合作商，所以点位与区域、点位与合作商是多对一，用 `association`。

### collection

* **一对多的集合封装**

    * > **定义**：`collection` 标签用来解决一对多的场景下映射多个结果的集合。
    * 查询单个区域表信息的同时查询该区域下所有点位列表时，按区域 id 查出的点位列表包含多个结果集，要映射的应该是一个集合。
    * 想统计某个合作商下所有点位信息时同样包含多个结果集，也需要采用 `collection`。

### 标签选择的判定依据

* **只看要映射的对象是一个还是一堆**

    * 结果中只有一个对象时用 `association`，要映射多个结果的集合时用 `collection`。
    * 落在"点位关联区域与合作商"这个场景里应该选 `association`，而且是两个独立的 `association` 标签。

* **两个标签的属性分配**

    * 一个 `property="region"`、`column="region_id"`，另一个 `property="partner"`、`column="partner_id"`。

## NodeVO 与 Mapper 层改造

### NodeVO 的三个新增属性

* **VO 定义**

    ```java
    package ...domain.vo;

    import ...domain.Node;
    import lombok.Data;

    /**
     * 点位管理列表查询结果
     */
    @Data
    public class NodeVO extends Node {

        /** 设备数量 */
        private Integer vmCount;

        /** 区域信息 */
        private Region region;

        /** 合作商信息 */
        private Partner partner;
    }
    ```

    * 在 domain 包右击新建 `NodeVO`，让它继承原有的父类 `Node`，直接可以使用点位原有信息。
    * 第一个新增属性是设备数量 `private Integer vmCount`。
    * 第二个是区域信息，关联的是实体，类型定义为 `Region`，属性名也叫 `region`。
    * 第三个是合作商信息，同样关联实体，定义一个 `Partner`。
    * 给这三个属性增加 getter、setter 方法以及 toString，并加上 `@Data` 注解。

### NodeMapper 方法与动态 SQL

* **新增查询方法**

    * 在 `NodeMapper` 最后一行增加一个新方法，`public` 返回值是 List 集合，泛型就是 `NodeVO`。
    * 方法名和参数通义千问已经准备好，按 Tab 键接收；参数使用 `Node`，把 VO 去掉。
    * 给方法补上中文注释，选中方法名按 Alt + Enter 通过 MyBatis 插件生成 XML 标签。

* **粘贴 SQL 并补动态条件**

    * 把关联查询的 SQL 语句直接粘贴进来。
    * 还要增加动态 SQL 的标签：若依原有生成的代码里一共有三个条件，复制到 `GROUP BY` 关键字之前。
    * 三个条件依次是：根据点位名称做模糊查询、根据区域 id 查询、根据合作商 id 进行查询。

### 从 resultType 切到 resultMap

* > **易错点**：SQL 之前是通过 MyBatis 的 `resultType` 属性完成自动映射封装，直接把结果映射给 `NodeVO` 的实体类。嵌套查询**不能**再使用 `resultType` 做自动映射，必须改为 `resultMap` 属性完成映射。

* **resultMap 的骨架**

    ```xml
    <resultMap id="NodeVOResult" type="NodeVO 的全限定名">

        <!-- 点位基础信息：若依生成的 result 标签，直接复制过来 -->
        ...

        <!-- 设备数量：需要我们手动映射 -->
        <result property="vmCount" column="vm_count"/>

        <!-- 区域信息：多对一，用 association -->
        <association property="region" javaType="Region" column="region_id"
                     select="RegionMapper 的全限定名 + selectRegionById"/>

        <!-- 合作商信息：多对一，用 association -->
        <association property="partner" javaType="Partner" column="partner_id"
                     select="PartnerMapper 的全限定名 + selectPartnerById"/>
    </resultMap>
    ```

    * 把属性先修改为 `resultMap`，值取名 `NodeVOResult`。
    * 这个 `resultMap` 标签还不存在，所以往上拉补一个：id 就是 `NodeVOResult`，type 属性对应最终映射的实体类 `NodeVO`。

### result 与 association 标签

* **result 把设备数量对上号**

    * 上半部分还要返回点位的基础信息，若依生成代码里已经包含了这些标签，直接复制过来即可。
    * 设备数量需要手动映射：`result` 标签的第一个属性 `property` 对应 `NodeVO` 的属性名 `vmCount`，第二个属性 `column` 对应数据库查询返回的字段 `vm_count`，并把标签内容改为单标签。

* **association 的四个属性**

    * `property` 对应 `NodeVO` 的属性名，区域是 `region`，合作商是 `partner`。
    * `javaType` 对应 Java 类型，区域是 `Region`，合作商是 `Partner`。
    * `column` 指定外键字段并以它为条件执行查询：区域用 `region_id`，合作商用 `partner_id`。
    * `select` 指向按主键查询的方法，区域用 `RegionMapper` 里的 `selectRegionById`，合作商用 `PartnerMapper` 里的 `selectPartnerById`。
    * 全限定名 = 接口的全名加方法名，右击 `Copy Reference` 最省事，也最不容易写错包名；MyBatis 底层通过反射来执行当前方法。
    * 标签写成自闭合。
    * > **提示**：`select` 后面跟的是方法的全限定名，不是 SQL 语句——SQL 的条件不能写死。直接用 IDE 的 `Copy Reference` 复制最不容易出错。

### 嵌套查询的执行流程

* **外键值当入参接力**

    ```text
          点位关联查询   SELECT * FROM tb_node ...  LEFT JOIN 统计设备数
                  │
                  │  每一行都携带 region_id / partner_id / vm_count
                  ▼
        ┌───────────────────────────────────────────┐
        │  resultMap = NodeVOResult   type = NodeVO  │
        └───────────────────────────────────────────┘
                  │            │               │
         column=region_id   <result>    column=partner_id
                  │        vm_count             │
                  ▼            ▼                 ▼
       selectRegionById   → NodeVO.vmCount   selectPartnerById
            (Region)                            (Partner)
                  │                               │
                  ▼                               ▼
          NodeVO.region                     NodeVO.partner
    ```

    * 主线是外键值从点位行里被取出来，再被当作入参交给另一个单表查询；`column` 是这条线上的接力棒，`select` 是接力棒交到的那只手。
    * 点位关联查询的返回结果里包含 `region_id`，把它作为条件放入 `column`，去执行区域中的 `selectRegionById` 方法。
    * 该方法以传入的区域 id 为条件拿到区域信息并封装给 `Region` 对象，再由 XML 中指定的属性名与 Java 类型映射给 `NodeVO` 的 `region`。
    * 编写 SQL 时 `selectRegionById` 就是一个单表查询，通过 MyBatis 标签把两个查询嵌套到一起，最终封装给 `NodeVO`。

* **mapper 层的整体脉络**

    * 先做点位列表与设备数量的关联查询。
    * 这个查询结果需要做手动映射封装，而手动映射封装的目的正是实现多表的嵌套组合查询：一个根据 `region_id` 查区域表信息封装进 `NodeVO`，一个根据 `partner_id` 查合作商信息也封装进 `NodeVO`。
    * 做完之后 `NodeVO` 就可以返回四张表的数据——点位基本信息、设备数量、区域以及合作商的信息。

    ```java
    public TableDataInfo list(Node node) {
        startPage();
        List<NodeVO> voList = nodeService.selectNodeVOList(node);
        return getDataTable(voList);
    }
    ```

    * 把原来查询点位单表基本信息的代码删除，改为调用 `nodeService` 的 `selectNodeVOList` 方法，把条件传过去。
    * 返回值就是 `voList`，再交给分页对象返回到前端即可。

* **验证**

    * 按 `Ctrl + F9` 实现一次热部署更新，刷新点位管理界面。
    * 返回结果中包含了点位的基本信息、设备的数量、区域实体类的属性信息以及合作商实体类的属性信息，前端就能拿到区域名称与合作商名称进行展示。

## 二义性报错与表别名

* **报错现象**

    * 根据点位名称搜索没有问题；根据区域条件搜索时，点击执行程序就报错，是一个 SQL 的完整性错误。

* **让 AI 定位错误**

    * 回到 IDEA 找到控制台，把错误信息复制出来交给通义千问，让它分析错误信息、找出可能导致错误的原因。
    * 它给出的解决方案是英文信息，对初学者不友好，可以让它翻译成中文重新生成一次。
    * 它指出的原因是：`where` 子句当中使用了 `region_id` 作为条件，但没有指定是哪张表的，是 `tb_node` 还是设备表，所以出现了二义性问题。
    * 它指出的位置是 `NodeMapper` 的 XML 映射文件，给出的解决方案是原来没有指定表的名称，现在需要加一个表的别名。

* **三个条件都加别名**

    * 第一条件改为 `n.node_name`，第二条件改为 `n.region_id`，第三条件改为 `n.partner_id`。

* > **提示**：按 `node_name` 查询没加表别名却不报错，是因为设备表当中没有这个字段，不会产生二义性；而 `region_id` 和 `partner_id` 在设备表和点位表当中都存在，不加别名它不知道用的是哪张表。因为无法确定哪些是公共字段、哪些是独有字段，建议这些条件都增加表的别名。

* **验证结果**

    * `Ctrl + F9` 热部署更新后再搜索不再报错，北京朝阳区和北京海淀区都能查到。

## 区域详情实现

### 实现思路

* **页面原型要求**

    * 管理员点击"查看详情"按钮时，页面弹出对话框，展示该区域的名称、区域下的所有点位列表和设备数量。
    * 后端接口已经开发完成，这一部分只需要对前端页面做一些改造。

* **三步走**

    * 在区域列表的操作一栏中添加一个"查看详情"按钮，为按钮绑定点击事件，点击时触发相应方法。
    * 在触发的方法中根据区域的 id 向后端发送请求，查询该区域的信息以及该区域下的点位列表。
    * 查询到数据后把这些数据封装到响应式对象，展示区域详情的对话框，展示区域名称、点位列表和设备数量。

### 查看详情按钮与权限

* **按钮复制自修改按钮**

    * 以修改按钮为模板复制一份，改名为"查看详情"。
    * 点击事件调用的方法名不应再叫 `handleUpdate`，改为 `getRegionInfo`（查看详情）。
    * 方法调用时要把当前区域行的数据传过去，方便获取区域的 id。

* **权限换成点位列表查询**

    * 按钮的权限不应该是修改区域的信息，而是查询权限。
    * 页面中重点展示的是点位列表，所以权限应该与点位列表相关。
    * 点位 Controller 里查询点位管理列表的方法，权限名称是 `manager:node:list`，复制到前端粘贴即可。

### getRegionInfo 的两部分查询

* **查区域信息，参考修改按钮**

    * 修改按钮点击时会根据 id 查询区域的信息并回显到前端，而区域详情对话框的第一部分正好就是展示区域信息。
    * 保留的部分是：重置表单、获取当前行的对象、根据 id 向后台发送请求并把请求结果封装给表单对象。
    * 删除的部分是：弹出新增修改对话框、修改对话框的标题，以及 id、数组这一部分。

* **查点位列表，复用点位接口**

    ```js
    import { listNode } from "@/api/manager/node";
    import { loadAllParams } from "@/api/manager/config";
    ```

    * 点位列表的请求路径是 `/manager/node/list`，因此要在区域管理页面引入点位 API 的 JS 文件，方法名叫 `listNode`。
    * 这个方法的查询需要参数，查询条件有当前页和每页个数；要查当前区域下的所有点位列表，每页个数肯定不能是十条。
    * 之前抽取过一个配置对象：当前页为 1，每一页查询 1 万条，相当于查询所有，需要把它也引入过来。
    * > **提示**：`loadAllParams` 的 `pageSize` 必须调大。默认值是 10 条，而区域详情要展示的是这个区域下的全部点位，不改大就只能看到第一页。
    * `loadAllParams` 只有 `pageNum` 和 `pageSize`，还要补上当前区域的 id 作为 `regionId` 条件。

    ```js
    queryParams.value.regionId = row.id;
    ```

    * 调用 `listNode` 并把查询参数传过去，返回结果 `res` 就是分页对象，重点取出 `res.rows` 就能拿到点位列表以及设备数量。

    ```js
    const res = await listNode(queryParams.value);
    // res.rows 里就有该区域下的点位列表（含 vmCount）
    ```

    * 通义千问生成的代码要改两处：`response.rows` 取出集合后封装的 `regionList` 命名不对，应改为 `nodeList`；取出总记录数和 `total.value = 0` 这两行不需要，移除掉。
    * 还缺少 `nodeList` 集合的定义，在上方补 `const nodeList = ref([])`。

### 对话框与只读表单项

* **对话框开关**

    * 把原有的对话框先关掉，参考添加或修改信息的对话框复制一份模板，新增一个查看详情对话框。
    * 标题不是动态的，可以写死为"区域详情"。
