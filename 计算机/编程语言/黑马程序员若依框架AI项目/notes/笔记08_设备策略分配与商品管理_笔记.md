# 设备策略分配与商品管理

## 点位详情对话框

### 按钮与方法

* **点位详情**

    * > **定义**：在点位列表操作列点击「查看详情」弹出的对话框，列出该点位下挂载的全部设备。

    * 按钮以「修改」按钮为模板复制改写，不手写；`@click="getNodeInfo(scope.row)"`。
    * 事件必须传入 `scope.row`，点位 id 就在这个行对象里。
    * 引入设备管理 API：`import { listVm } from '@/api/manager/vm'`，该方法接收一个 query 参数，返回分页对象。
    * 方法体四步：`loadAllParams.nodeId = row.nodeId` → `listVm(loadAllParams)` → `vmList.value = response.rows` → `nodeOpen.value = true`。

    * > **易错点**：先在模板写下 `v-model="nodeOpen"` 再回 JS 补 `const nodeOpen = ref(false)`，顺序反了编辑器会持续报未定义。默认给 `false`，点击成功后改 `true`。

* **按钮权限串（v-hasPermi）**

    * > **定义**：挂在按钮上的权限控制指令，决定该按钮在当前账号下是否渲染。

    * 点位「查看详情」干的是「查设备列表」，权限串应挂设备列表的 `manager:vm:list`。
    * 权限串去设备 Controller 的列表查询方法上复制，做全字符串替换。
    * 设备「策略」按钮改的仍是设备表，权限串与「修改」保持一致，不必另建。

### 表格复制与时间格式化

* **设备表格改造清单**

    * > **定义**：从设备状态页面整段复制 `el-table` 后，逐列增删以匹配点位详情原型。

    | 位置 | 处理 |
    | --- | --- |
    | `v-loading` | 指令写法，不加冒号 |
    | `data` | 由点位集合换成 `vmList` |
    | 复选框列 `type="selection"` | 删掉，批量删除用不上 |
    | 序号、设备编号 | 保留 |
    | 设备型号、详细地址 | 删掉 |
    | 原「运营状态」列 | 列标题改成「设备状态」，原「设备状态」列删掉 |
    | 操作列 | 删掉 |

* **时间格式化（parseTime）**

    * > **定义**：把后端返回的原始时间串渲染为指定格式的内置函数。

    * 最后一次供货时间列用插槽表达式，通过 `scope` 作用域拿到当前设备行对象再取字段。
    * 格式串传两个参数：`parseTime(scope.row.lastSupplyTime, '{y}-{m}-{d} {h}:{i}:{s}')`。
    * 不包 `parseTime` 时页面出得来值，但格式不是原型要的样子。
    * 点位详情对话框宽度默认 500，最后一列时间挤不进一行，调成 600。

### 字典预加载

* **数据字典（data dictionary）**

    * > **定义**：由后端维护的编码到中文标签的映射表，页面加载时随请求预取，列绑定它才能显示中文。

    * 表格列走字典翻译时，页面必须预加载对应字典，否则该列为空。
    * 症状：序号、设备编号都有，唯独设备状态是空的。
    * 原因是当前页面预加载过商圈类型字典，但没生成设备状态字典。
    * 解法：到设备状态页面的 JS 部分，把引入设备状态字典的那一行复制到当前页面对应位置，刷新让字典预取后再点。

    * > **结论**：从别的页面复制代码过来，字典不会自己跟着跑过来，凡是字典列都要在当前页面单独补预加载。

## 策略管理

### 折扣率的业务定位

* **策略（policy）**

    * > **定义**：为每一台设备设置的一个固定折扣率，用于营销，提高用户粘合度与销量。

    * 策略管理页面两块内容：策略管理本身（列表含策略名称与策略方案），以及设备管理里的策略分配。
    * 业务链路：管理人员定义新策略 → 把策略分配给一个或多个售货机 → 消费者在该设备购买商品时按优惠价支付。

### 策略表与一对多关系

* **策略方案（discount）**

    * > **定义**：策略表中的百分比值字段，写 80 表示八折，写 90 表示九折。

    * 它是一个百分比，不写小数。
    * 策略名称举例：八折优惠、九折优惠、夏日优惠，既用于列表展示也用于条件查询。

* **策略表字段**

    | 字段 | 含义 | 说明 |
    | --- | --- | --- |
    | 策略 id | 主键，自增 | 系统生成 |
    | 策略名称 | 如「八折优惠」 | 列表展示、条件查询都用它 |
    | 策略方案 | 折扣率 | 百分比值，不要写小数 |
    | 创建时间 | — | 列表展示 |
    | 修改时间 | — | 列表不展示 |

* **策略与设备的一对多**

    * > **定义**：策略表与设备表是 N : 1，落地方式是在设备表里放 `strategy_id` 外键指向策略表主键。

    ```text
       设备表 (tb_device)                    策略表 (tb_policy)
      ┌──────────────────────┐              ┌──────────────────────┐
      │ id                   │              │ id  （主键）          │
      │ code / status / ...  │              │ name  （策略名称）    │
      │ strategy_id (外键)   ├─────────────►│ discount（策略方案）  │
      │                      │      N : 1    │ create_time          │
      └──────────────────────┘              └──────────────────────┘
    ```

    * 双向可查：按策略 id 可查该策略下有哪些设备；按设备的策略 id 可查策略名称与折扣。
    * 新增与修改共用同一个对话框。
    * 策略详情里要包含策略名称，以及使用该策略的当前设备都有哪些。

### 代码生成器三步

* **目录菜单**

    * > **定义**：给待生成的二级菜单做容器的菜单项，类型选「目录」。

    * 显示排序对照原型定：工单 1、点位 2、设备 3、人员 4、商品 5、订单 6、策略管理 7。
    * 策略管理路由地址填关键字 `policy`，外链选否，其余用默认。
    * 策略管理模块**不需要数据字典**，配生成信息时要记住。

* **生成信息配置**

    * > **定义**：代码生成器里逐字段勾选查询、列表、表单项与生成路径的那一步，是整个生成最关键的一步。

    * 数据类前缀 `tb` 去掉，作者改成 itheima。
    * 条件查询只留策略名称；列表展示勾策略名称、策略方案、创建时间，修改时间不勾。
    * 新增对话框去掉主键 id，创建时间与修改时间交给后台补充；只保留策略名称与策略方案两个表单项。
    * 生成模板选单表，前端类型选 Vue3，生成的包路径与模块名都改为 `manager`，业务名 `policy`。
    * 生成的功能名即二级菜单名称，对照原型叫「策略管理」，上级菜单选刚建的策略管理。

* **下载与落地**

    ```text
    解压目录                        去向
    ──────────────────────────────────────────────────────────
    vue/api/manager/*.js        →   VS Code：src/api/manager/       （请求 JS）
    vue/views/manager/policy/  →   VS Code：src/views/manager/     （视图组件）
    java/（controller、service、
          mapper、实体、XML）  →   IDEA：若依 manager 子模块目录下
    policy_menu.sql            →   MySQL：执行 SQL 脚本
    ```

    * 先导动态菜单 SQL，它决定菜单出不出现，执行成功后刷新浏览器即出现二级菜单。
    * `java` 目录是整包拷贝，必须连 Controller、service、mapper 一起复制，不能只粘一半。
    * 全部就位后重启后端项目，页面展示基本信息、条件搜索即可用。
    * 生成器产物只涵盖单表 CRUD，与原型仍有差异化，后续需逐列改造。

### 列表布局改造

* **策略管理六处调整**

    | 位置 | 生成器给的样子 | 原型要求 | 改造动作 |
    | --- | --- | --- | --- |
    | 条件查询区 | 策略名称 | 策略名称且支持模糊查询 | 不用调整 |
    | 按钮区 | 新增、修改、删除、导出 | 新增一致，其余先保留 | 不用调整 |
    | 列表第 1 列 | 主键列 | 序号列 | 加 `type="index"`，宽度设 50 |
    | 策略方案列 | 标题带逗号后缀说明 | 只要「策略方案」 | 删掉逗号及后面的文字 |
    | 创建时间列 | 只有年月日 | 年月日 + 时分秒 | 格式补上时分秒 |
    | 操作列 | 修改、删除带图标 | 只要文字按钮 | 删掉 `icon` 属性 |

* **时间与序号**

    * `parseTime` 格式串在原「年月日」后加空格，再补 `{h}` 冒号 `{i}` 再冒号 `{s}`。
    * 改序号列只改一行不够：生成的主键列上没有序号所需属性，必须补 `type="index"`，再把宽度设成 50。

### 策略方案的数字输入

* **数字输入框（el-input-number）**

    * > **定义**：Element Plus 提供的只能输入数值的输入组件，由最小值、最大值、精度、步进四个属性约束取值。

    ```html
    <el-form-item label="策略方案">
      <el-input-number v-model="form.discount" :min="1" :max="100" :precision="0" />
    </el-form-item>
    ```

    * 策略方案范围 1 到 100，即 1% 到 100%；字母与汉字都敲不进去。
    * `:min="1"` 与 `:max="100"` 挡住越界值：输入 1000 回车会自动恢复成 100。
    * `:min` / `:max` **挡不住小数**：输入 `10.5` 仍会被接受。
    * 禁小数必须显式设 `:precision="0"`；精度属性官网示例写 2 表示支持两位小数。
    * 精度设为 0 后输入 `11.5`，回车会通过四舍五入补齐成 12，所以策略方案只支持正整数。
    * 策略方案文字较长，把逗号后的说明清掉，`placeholder` 也去掉。

    * > **结论**：`el-input-number` 的 `:min` / `:max` 只能挡住越界的值，挡不住小数；不显式设 `:precision="0"`，小数会被静默接受。

### 策略详情

* **把行对象当接口返回值**

    * > **定义**：查看详情时不再按 id 回查后端，直接把当前行对象 `row` 封装给表单。

    * 行对象本身就是完整策略信息，字段齐全，与按 id 查一次后端拿到的结果一样。
    * 面向内部员工的后台系统，不必担心数据被恶意篡改，省掉一次后端交互。
    * 做法是把修改按钮那行复制过来，把右侧改成 `row`。

    ```js
    // 查看策略详情
    function getPolicyInfo(row) {
      // 第一步：获取策略信息 —— 直接把当前行封装给表单
      form.value = row
      // 第二步：根据策略 id 查询设备列表
      loadAllParams.policyId = row.policyId
      listVm(loadAllParams).then((response) => {
        vmList.value = response.rows
      })
      policyOpen.value = true
    }
    ```

* **两个 import 的必要性**

    * > **定义**：策略详情需要同时引入设备 API 与查询条件对象，两者缺一不可。

    ```js
    import { listVm } from '@/api/manager/vm'
    import { loadAllParams } from '@/utils/ruoyi'
    ```

    * `loadAllParams` 是响应式对象，得单独 import；只导入设备 API 的 JS 行不通。

* **策略详情对话框**

    * 开关用 `const policyOpen = ref(false)`，设备列表拿到后再置为 `true`；标题固定「策略详情」。
    * 策略名称表单项从被隐藏的新增修改对话框复制过来，回显后加 `disabled`，因为详情里文本不可修改。
    * 设备表格从点位详情对话框整段 `el-table` 复制：保留序号、设备编号，删掉设备状态与最后一次供货时间。
    * 在序号与设备编号中间插入「点位地址」列：复制设备编号列，label 改为点位地址，`prop` 写 `addr`（该地址就是设备地址）。
    * 地址内容过长一行放不下时，给这列加 `show-overflow-tooltip`，鼠标移过去显示全。

## 设备策略分配

### 只提交两个参数

* **最小提交原则**

    * > **定义**：策略分配只提交设备 id 作为更新条件、策略 id 作为更新字段，不回写也不更新设备其余信息。

    * 原「修改」按钮的做法是按设备 id 查回整个设备信息回写表单、整份提交，策略分配不照抄。
    * 策略分配只需回显当前设备的策略信息，并提交设备 id 与选中的策略 id。
    * 直接从当前行对象 `row` 拿 id，不查数据库，顺带减少一次后端查询请求。
    * 表单赋值两行搞定：`form.id = row.id`、`form.policyId = row.policyId`。

* **按钮与方法**

    * > **定义**：设备管理操作列新增的「策略」按钮及其绑定方法 `handleUpdatePolicy`。

    * 按钮复制「修改」按钮改名「策略」，方法名加 `policy` 后缀区分，参数仍传当前行对象。
    * 权限串与「修改」按钮保持一致即可，因为改的仍是设备表。
    * 策略列表查询：引入 `import { listPolicy } from '@/api/manager/policy'`，调用后从 `res.rows` 取集合赋给 `policyList`。

    ```js
    // 设备管理页面的顶部，引入策略管理的 API
    import { listPolicy } from '@/api/manager/policy'

    const policyList = ref([])      // 策略列表

    // 设备策略分配
    function handleUpdatePolicy(row) {
      // 只以设备 id 为条件更新策略信息，其他数据不提交
      form.value.id = row.id
      form.value.policyId = row.policyId

      // 查询有效的策略列表
      const res = await listPolicy(loadPolicyList)
      policyList.value = res.rows

      // 列表查询成功后，弹出策略管理对话框
      policyOpen.value = true
    }
    ```

    * > **易错点**：代码补全插件不知道集合叫策略列表，会顺手封装到设备类型集合里去；必须自己定义 `const policyList = ref([])`，再把自动生成的 `vmTypeList` 整个替换掉。

### 策略管理对话框

* **对话框表单属性**

    | 属性 | 处理 | 理由 |
    | --- | --- | --- |
    | `ref` | 不能用 policy 的 | 最终提交的是设备相关信息，标识应参考设备管理对话框 |
    | `v-model` | 绑 `form` | 与设备管理保持一致 |
    | `rules` | 直接删掉 | 策略管理只有一个下拉框，不做表单校验 |
    | 宽度 | 默认值不调整 | — |

    * 开关用 `const policyOpen = ref(false)`，查询成功后置为 `true`。
    * 新增修改对话框标签过多，先加注释把它隐藏掉，另起一段「策略管理对话框」。
    * 表单项只有一个：`label` 叫「选择策略」，`prop` 值是 `policyId`，不是 `id`。

* **下拉框选项绑定**

    * > **易错点**：`el-option` 的 `:key` 是唯一标识，策略的主键不叫 `id`，用的是全称 `policyId`；展示 label 用 `policyName`，提交值同样是 `policyId`。

    ```vue
    <!-- 策略管理对话框 -->
    <el-dialog v-model="policyOpen" title="策略管理">
      <el-form ref="…" v-model="form" :width="800px">
        <el-form-item label="选择策略" prop="policyId">
          <el-select v-model="form.policyId" placeholder="请选择策略">
            <el-option
              v-for="policy in policyList"
              :key="policy.policyId"
              :label="policy.policyName"
              :value="policy.policyId"
            />
          </el-select>
        </el-form-item>
        <!-- 确定 / 取消按钮：从新增修改对话框复制过来 -->
      </el-form>
    </el-dialog>
    ```

    * 回显验证：已关联策略的设备会回显出「九折优惠」「八折优惠」，从未关联过的新设备为空。

* **复用按钮后的两处补漏**

    * > **结论**：复制按钮容易，改开关容易漏；凡是共用一份按钮模板的地方，都要回头检查绑定的是不是自己那个对话框的开关。

    * 确定与取消按钮直接复制自新增修改对话框最底部的 template 标签内。
    * 取消按钮点了没反应：它调用的是 `cancel` 方法，只把 `open` 置为 `false`，而策略对话框的开关是 `policyOpen`，要在 `cancel` 里补一行 `policyOpen.value = false`。
    * 确定按钮提交成功但对话框不关：关闭代码要加在「修改成功」之后而不是「新增成功」之后，补一行 `policyOpen.value = false` 并写中文注释「关闭策略对话框」。

### 确定按钮 500 排查

* **空指针链路**

    * > **定义**：只提交 id 与 policyId 导致后端拿不到点位对象、设置设备地址时对 null 取值而抛出的空指针异常。

    * 前端请求参数确认无误：只有设备 id 与策略 id，其他一个都没提交。
    * IDEA 控制台异常位置在设备管理业务层第 131 行，该行用于设置设备地址，而地址是从点位对象中获取的。
    * 空指针只可能出在两处：设备对象或点位对象；前端提交的是设备对象，可排除，故为点位对象。
    * debug 模式打断点验证：点位对象是 null，说明按设备提供的点位 id 查不到点位。
    * 用 SpEL 表达式求设备获取点位 id 的代码，值为空，证明提交数据中确实不含点位 id。

    ```text
    前端只提交 id 和 policyId
            |
            v
    后端拿不到 pointId
            |
            v
    查不到点位对象
            |
            v
    设置设备地址时对 null 取值
            |
            v
    NullPointerException -> 500
    ```

* **冗余字段回填的非空判断**

    * > **定义**：只有请求里带了点位 id 才去查点位并回填冗余字段的守卫逻辑。

    * 判定依据：只有更新设备基本信息时前端才会带上 pointId，策略分配不包含 pointId。
    * 把原本无条件回填点位列的代码整体包进 `if (device.getPointId() != null)`，其余两行点位冗余字段回填同样放进去。

    ```java
    // 只有更新设备基本信息时，前端才会带上 pointId
    if (device.getPointId() != null) {
        Point point = pointService.getById(device.getPointId());
        device.setAddress(point.getAddress());
        // 其余两行点位冗余字段的回填，同样放在这个 if 里面
    }
    ```

    * Ctrl + F9 热部署后重测，返回 `code 200`、`msg` 为「操作成功」，策略已写入数据库。
    * 复验：再次点开策略按钮回显刚选的策略，更换策略后确定，操作成功且对话框自动关闭。

## 商品管理的业务与数据模型

### 三个功能模块

* **商品管理业务范围**

    * > **定义**：以「商品类型 → 商品 → 货道」的链条为核心，保证智能售货机每个货道承载特定商品、每种商品归属特定类型。

    * 商品类型：定义商品分类，如饮料、零食。
    * 商品管理：包含商品编号、商品名称、图片、品牌规格等信息。
    * 货道关联商品：在设备管理里对应「货道」，把系统录入好的商品关联到指定货道下。
    * 闭环作用：运营人员按货道剩余容量补货，消费者按货道选购商品。

    ```text
    后台管理人员登录「帝可得」后台管理系统
            |
            v
    定义商品的不同分类（有助于后续的商品管理和用户的选购）
            |
            v
    添加新的商品信息：名称、规格、价格、所属类型等等
            |
            v
    将商品与售货机的货道进行关联
            |
            +--> 运营人员：按货道当前剩余容量补货
            +--> 消费者  ：按货道选购商品
    ```

### 四张核心表

* **商品类型表（tb_sku_class）**

    * > **定义**：存放商品分类的表，包含主键、分类名称与上级 id。

    | 字段 | 含义 | 说明 |
    | --- | --- | --- |
    | `class_id` | 主键 | 自增 |
    | `class_name` | 商品类型名称 | 列表展示、条件查询 |
    | `parent_id` | 上级 id | 数据库设计预留字段，运行中并未关联 |

    * 新增时只需输入类别名称，主键自增。
    * 上级 id 类似树表关联，用于设计大分类与小分类：食品下含零食、方便食品、生鲜食品；饮料下含碳酸饮料、果汁、功能性饮料。
    * 加它的目的是方便后期业务扩展；当前业务只需一级分类。

* **商品表（tb_sku）**

    | 原型展示 | 数据库字段 | 说明 |
    | --- | --- | --- |
    | 商品名称 | `sku_name` | — |
    | 商品图片 | `sku_image` | — |
    | 品牌 | `brand_name` | — |
    | 规格 | `unit` | 饮料的话表示净含量 |
    | 商品价格 | `price` | 数据库以分为单位存储 |
    | 商品类型 | `class_id` | 外键，指向商品类型表主键 |

    * 新增时主键自增，创建时间和修改时间由后台系统自动补上。
    * 表中还有一个「是否打折促销」字段，它不在商品管理页面上。
    * 它由设备管理中的策略控制：设备设置了策略且其货道关联了该商品时，消费者购买时系统判断有无打折促销方案，按折扣付款。
    * > **结论**：「是否打折促销」这个字段涉及商品管理、设备管理、策略管理三个功能模块的联合操作。

* **货道表与设备表**

    * 货道表在设备管理中已介绍，这里只关注 `sku_id` 字段。
    * 货道编号形如 1-1、1-2、2-1、2-2，设备新增时按设备类型自动生成并入库。
    * 下一步是给每个货道添加对应商品，货道关联商品 `sku_id` 后运营人员才能补货、消费者才能选购。

* **表关联关系**

    ```text
      商品类型   1  ────────  N  商品     （商品表 class_id → 商品类型表主键）
      商品       1  ────────  N  货道     （货道表 sku_id   → 商品表主键）
      设备       1  ────────  N  货道     （一台设备可以拥有多个货道）
      商品       N  ────────  N  设备     （把货道表当作一张中间表）
    ```

    * 商品类型 : 商品 = 一对多，用商品表的 `class_id` 作外键指向商品类型表主键。
    * 商品 : 货道 = 一对多，用货道表的 `sku_id` 作外键指向商品表主键。
    * 设备 : 货道 = 一对多，一台设备可以拥有多个货道。
    * 商品 : 设备 = 多对多，把货道表当作一张中间表建立关联。

* **精准提示**

    * > **定义**：在全局异常处理器中按异常关键字分流，给出更具体的用户提示。

    * 位置：dkd 的 framework 模块 → `web` 包 → `exception` 包 → 全局异常处理器类中已有的「数据完整性异常」方法。
    * 该方法已有外键约束分支：包含 `foreign` 就提示无法删除、有其他数据引用。

    ```java
    // 已在方法中：
    if (e.getMessage().contains("foreign")) {
        return AjaxResult.error("无法删除，有其他数据引用");
    }

    // 我们新加的一段：Duplicate = 重复键值
    if (e.getMessage().contains("Duplicate")) {
        // 返回信息还是复制原来那段 AjaxResult.error，把提示语改掉
        return AjaxResult.error("无法保存，名称已存在");
    }
    ```

    * Ctrl + F9 热更新后重测，再次添加「饮料」提示「无法保存，名称已存在」。

### 价格的分与元

* **金额存分（integer cents）**

    * > **定义**：金额在数据库用整数「分」存储、页面用「元」展示的编码方式，避开浮点精度问题。

    * 数据库存 `100` 表示一元，存 `200` 表示两元。
    * 设计动因：Java 里用 `float` 或 `double` 处理小数，浮点用二进制近似表示十进制数，计算时产生精度损失；用整数分存储则全程整数运算。
    * 换算写在模板插槽里，列从单标签改成双标签加 `template`，并去掉列头多余的标题。

    ```html
    <el-table-column label="商品价格" prop="price" align="center" width="120">
      <template #default="scope">
        <el-tag>{{ scope.row.price / 100 }}</el-tag> 元
      </template>
    </el-table-column>
    ```

    * 单纯除以 100 数字干巴巴，再用 `el-tag` 高亮并在后面补单位「元」。
    * 商品编号在数据库里没有对应字段，先跳过，后续由主键保证唯一性。

### 商品类型列的前端预加载

* **两种解法**

    | 方案 | 做法 | 优点 | 代价 |
    | --- | --- | --- | --- |
    | 后端多表查询 | 后端直接把类型名称查出来 | 前端工作量小 | 数据库查询复杂度上升 |
    | 前端预加载 | 页面先拿到全部类型数据，遍历匹配 id | 减少数据库查询次数，页面加载更快 | 前端要多写遍历逻辑 |

    * 选择前端预加载：把活儿交给前端渲染能力，减轻服务器负担。

* **三步实现**

    ```js
    import { listSkuClass } from '@/api/manager/skuClass'
    import { props } from '@/api/manager/props'

    // 查询商品类型列表
    function getSkuClassList() {
      return listSkuClass(props).then(response => {
        skuClass.value = response.rows
      })
    }

    const skuClass = ref([])
    ```

    * 第一步引入商品类型 API 请求文件与查询条件对象 `props`。
    * 第二步在 JS 底部写注释「查询商品类型列表」并用 `function` 定义 `getSkuClassList`，内部取 `response.rows` 封装给自建的 `skuClass` 响应式数组。
    * 第三步页面加载成功后调用该方法完成预加载，再把类型列改成双标签加插槽。

    ```html
    <el-table-column label="商品类型" align="center" width="120">
      <template #default="scope">
        <div v-for="item in skuClass" :key="item.classId">
          <span v-if="item.classId == scope.row.classId">{{ item.className }}</span>
        </div>
      </template>
    </el-table-column>
    ```

    * > **易错点**：写完 `v-for` 会直接报错，因为缺 `:key`；且唯一标识不能用 `id`，商品类型 ID 在数据库里全称是 `classId`，必须写 `:key="item.classId"`。

    * 外层 `div` 用 `v-for` 遍历 `skuClass`，元素名 `item`；内层 `span` 用 `v-if` 判断 `item.classId` 是否等于 `scope.row.classId`，相等则插值显示 `item.className`。

* **AI 生成代码的调整**

    * 代码补全直接调用 `listSkuClass` 没带参数，要手动把 `props` 传进去。
    * 它把返回结果整个塞给响应式对象，要手动改为通过 `rows` 取出集合再赋值。
    * 写组件时把注释掉的旧标签一并留在结果里，粘贴后无法使用，得手动删掉。
    * > **提示**：AI 工具目前只能作为辅助开发的助手，前后编程基础扎实才能游刃有余地用好它。

## 商品新增与修改对话框

### 顺序与文案

* **表单项顺序**

    * > **定义**：对照原型重排后的表单项自上而下次序。

    * 最终顺序是：**商品名称 → 品牌 → 规格 → 商品价格 → 商品类型 → 商品图片**。
    * 做法是在编辑器里剪切粘贴：品牌剪切到商品名称下方，商品图片剪切到最下方，价格挪到品牌下方，类型挪到价格下方。
    * 文案：商品价格的 label 去掉逗号后的「单位：分」；商品类型的 label 去掉 `id`，placeholder 也去掉 `id`；规格去掉括号里的净含量。
    * 新增与修改在原型中共用同一套对话框，改完两边都能用。

### 价格数字输入框

* **价格输入的四属性**

    * > **定义**：价格类数字输入框的标准配置组合，四个一起上，输入合理性就被锁住。

    ```html
    <el-form-item label="商品价格" prop="price">
      <el-input-number v-model="form.price" :min="0.01" :max="999.99" :precision="2" :step="0.5" />
    </el-form-item>
    ```

    * `:min="0.01"` 最小金额一分钱，`:max="999.99"` 是最高金额。
    * 有最小与最大两个边界，可保留的小数位就是两位，所以 `:precision="2"`。
    * 默认步进是 1，每点一次加号涨一块钱，不符合 2.5、3、3.5、4、4.5、5 元的常见定价。
    * `:step` 步进属性控制步长，官网文档写 `:step="2"` 时点 5 变 7、7 变 9，复制回来把 `2` 改成 `0.5`。
    * > **结论**：`min` / `max` / `precision` / `step` 这四个属性是价格类数字输入框的标配。

### 商品类型下拉框

* **下拉框写法**

    ```html
    <el-form-item label="商品类型" prop="classId">
      <el-select v-model="form.classId" placeholder="请选择">
        <el-option
          v-for="item in skuClass"
          :key="item.classId"
          :label="item.className"
          :value="item.classId"
        />
      </el-select>
    </el-form-item>
    ```

    * 原来的文本框先注释掉再写 `el-select`；`v-model="form.classId"` 从原文本框直接复制，不用改。
    * placeholder 由「请输入」改成「请选择」。
    * `v-for` 遍历 `skuClass` 得到每个商品类型元素，`:key` 是唯一标识，`:label` 显示名称，`:value` 提交选中的类型 ID。
    * 生成结果逻辑没问题，但会把注释掉的旧文本框和 `el-select` 一起留下，必须手动删除。

### 双向单位换算

* **回显与提交的闭环**

    * > **定义**：价格在数据库（分）与页面表单（元）之间的双向换算配对，缺任一处都会写坏数据。

    ```text
            数据库（单位：分）                 页面表单（单位：元）
                  |                                 ^
                  |  点修改：响应数据填表单          |  提交：表单数据发给后端
                  |  price = price / 100           |  price = price * 100
                  +---------------------------------+
    ```

    * 症状：新增「营养快线」价格 3.5 元，页面显示 0.03 元。
    * 根因：前端已把分换算成元，提交时也按元入库；回显时再除以 100，3.5 变 0.035，落库截断后回显 0.03。
    * 用数据库客户端工具验证：其他记录存的是一百、二百的分值，这条新记录存的是 `3`。
    * 提交侧在提交按钮处补一行把元转回分：取当前价格 `*= 100`。
    * 回显侧在 `handleUpdate` 里，响应数据封装到表单后补一行 `form.value.price = form.value.price / 100`。

    ```js
    function handleUpdate(row) {
      // ...
      proxy.getSku(row.id).then(response => {
        form.value = proxy.assignFormData(response)
        // 将价格单位从分转换为元
        form.value.price = form.value.price / 100
        dialog.visible = true
        // ...
      })
    }
    ```

    * 复测：0.03 元改成 3 元，页面回显 3 元，点修改显示 3.00 两位精度，数据库那条记录显示 300 分。
    * > **易错点**：新增或修改商品时，提交数据之前要把元再转换回分。

## 商品删除的逻辑外键校验

### 从物理外键转向逻辑外键

* **逻辑外键（logical foreign key）**

    * > **定义**：放弃数据库层面的外键约束，改由应用程序代码检查与维护的数据一致性规则。

    * 需求背景：商品靠货道关联销售，删除商品前必须先确认没有售货机货道关联它，否则不能删，以保证销售连续性与数据一致性。
    * 表关系支撑：商品表与货道表一对多，货道表 `sku_id` 外键指向商品表主键。
    * 原计划用物理外键约束让数据库自动维护完整性，但当前场景不适用。
    * 实证：货道表 `sku_id` 新增记录用默认值 `0`，而商品表不存在 ID 为 0 的数据，物理外键会阻止插入。
    * 转向逻辑外键的好处是灵活性更大，允许在应用层处理复杂业务逻辑，同时避开数据库层面外键约束带来的限制。

### 校验链路

* **删除前先数货道**

    * > **定义**：删除商品前统计关联货道数量，非零则抛业务异常终止方法的规则。

    * 该功能只涉及商品管理的后端改造。
    * Controller 的删除方法通过路径传参拿商品 ID 集合；之所以是集合，是因为前端既支持单个删除也支持批量选择删除。
    * 改造点是 service 实现方法：原逻辑拿到 `skuId` 集合直接调 mapper 批量删除，现在要在批量删除前先判断是否关联货道。
    * 要查货道表，需在商品业务层依赖注入货道 service：`@Autowired private IChannelService channelService;`

    ```java
    @Override
    public void deleteByIds(Long[] ids) {
        // 统计货道，根据 skuIds
        int count = channelService.countChannelBySkuIds(ids);
        if (count > 0) {
            throw new ServiceException("此商品被货道关联，无法删除");
        }
        skuMapper.deleteByIds(ids);
    }
    ```

    * `count` 大于 0 说明这批商品里至少有一个被货道引用，拒绝删除并抛 `ServiceException`。
    * `ServiceException` 是若依提供的业务异常提示类，类中定义的提示信息会返回给前端展示。
    * 没有关联货道时直接调 mapper 执行删除。

    ```text
       DELETE /manager/sku/{ids}
                  |
                  v
            SkuController  --路径传参--> 拿到 skuId 集合（支持批量删除）
                  |
                  v
          SkuServiceImpl.deleteByIds(ids)
                  |
                  +-- 步骤一：channelService.countChannelBySkuIds(ids)
                  |            |
                  |            v
                  |     ChannelServiceImpl --> ChannelMapper --> channel 表 count(1)
                  |
                  |        count > 0  ==>  throw new ServiceException
                  |        count = 0  ==>  放行
                  |
                  +-- 步骤二：skuMapper.deleteByIds(ids)
    ```

* **三层方法补齐**

    * 选中 `countChannelBySkuIds` 按 `Alt + 回车` 选第一个 **Create method** 创建方法，注释写「根据商品 id 集合统计货道数量」。
    * 把注释复制到接口，按 `Alt + 回车` 选第四个 **Implement method** 创建实现并重写方法体。
    * 实现内补上 `channelMapper`，方法命名与参数传递见名知意，命名格式和业务层一致。
    * mapper 里同样不存在，`Alt + 回车` 选 Create method 补齐。
    * IDEA 自动创建的方法在接口里没加 `public` 关键字，而它在接口中本就是默认值，写不写一样，写了会显示为灰色。

### SQL 与验证

* **统计 SQL**

    * > **定义**：按商品 ID 集合统计货道数量的 MyBatis 映射语句。

    ```xml
    <select id="countChannelBySkuIds" resultType="int">
        select count(1) from channel where sku_id in
        <foreach collection="array" item="id" separator="," open="(" close=")">
            #{id}
        </foreach>
    </select>
    ```

    * `count(1)` 与 `count(*)` 作用相同，都做数量统计。
    * 通过 MyBatis-Plus 插件生成 `select` 标签（`Alt + 回车` 选生成查询标签 select）。
    * `collection="array"` 是方法参数名的固定值，`item="id"` 是遍历变量名，`#{id}` 是每个元素的占位符。
    * `separator=","` 用逗号分隔元素，`open="("` 与 `close=")"` 补上左右括号，完成 `in` 列表拼接。
    * 拼接规则是前端传什么值后面就拼什么值。

* **验证结果**

    * 未关联货道的自建测试数据可正常删除。
    * 关联了货道的商品：星巴克 ID 为 9，A10 开头设备的 2 号货道关联了该数据，点击删除时提示「此商品被货道关联，无法删除」。
    * 异常被系统捕获后终止代码执行并返回清晰提示，由前端展示给管理员删除失败的原因。
    * > **结论**：逻辑外键校验不仅确保了数据的一致性和完整性，还提升了系统的健壮性。

## 商品 Excel 批量导入

### 导入接口定义

* **批量导入接口**

    | 项目 | 内容 |
    | --- | --- |
    | 请求路径 | `/manager/sku/import` |
    | 请求方式 | `POST` |
    | 请求头一 | `Content-Type`，告诉后端我是一个表单文件提交 |
    | 请求头二 | `Authorization`，携带前端用户的 token 身份令牌信息 |
    | 请求体 | 上传的 Excel 文件对象，参数名为 `file` |

    * 返回结果是标准的 AjaxResult，`result` 里带提示信息 `msg` 与业务状态码 `code`。
    * `Authorization` 请求头必须强调：只有登录成功后前端持有的令牌才能完成上传，否则被拦截器拦截。
    * 需求的目的是提升商品数据录入效率，通过 Excel 文件实现批量导入。

* **若依的 Excel 工具类**

    * > **定义**：若依封装、底层基于 Apache POI 的 Excel 工具类，提供文件导入解析与导出操作两大能力。

    * 代码生成器默认已集成导出能力：搜索条件筛出的数据点导出即可下载 xlsx。
    * 导出文件的商品类型那一列是 ID 而不是名称，记住这点，导入环节还会再遇到一次。
    * Controller 中 `export` 方法的流程：接收前端请求条件 → 调 service 查商品列表 → 把 `list` 交给 Excel 工具类生成并下载。
    * 创建工具类对象时要指定实体字节码对象，因为底层靠反射解析实体属性取数，再调 `exportExcel` 完成生成下载。
    * 原生 Apache POI 代码繁琐，若依把上传与下载的基础部分做了封装抽取。

### 导入按钮与对话框

* **导入按钮**

    * > **定义**：按钮区里复制导出按钮改造而来、点击后弹出数据导入对话框的按钮。

    ```html
    <el-button
      type="primary"
      plain
      icon="Upload"
      @click="handleImport"
      v-hasPermi="manager:sku:add"
    >导入</el-button>
    ```

    * 以导出按钮为模板复制一份换行粘贴，按钮名称改为「导入」，类型与样式不变。
    * 图标由 `download` 改为 `upload`，`@click` 绑定 `handleImport` 做见名知意。
    * 权限串不能叫 `export`；导入本质是新增，故与新增一致用 `manager:sku:add`。

* **对话框与开关**

    * > **定义**：承载 Excel 文件上传表单项的小对话框，默认隐藏。

    ```js
    // 打开数据导入的对话框
    function handleImport() {
      excelOpen.value = true;
    }

    const excelOpen = ref(false)
    ```

    * 先把新增修改对话框隐藏掉，另写注释「数据导入对话框」再写标签。
    * `title` 改为与原型一致的「数据导入」；生成器给出的开关名 `openImport` 要改成 `excelOpen`。
    * 宽度先设 300 偏窄，放上上传组件后改成 400 合适。

### 上传组件改造

* **三种上传模板**

    * > **定义**：Element Plus 的 `el-upload` 提供的上传交互模板，选哪种决定了用户先选文件还是一点就传。

    * 基础用法：仅提供上传按钮，点击之后立马上传，与原型有区别，不使用。
    * 照片墙 / 图片列表：显示缩略图并支持多图同时提交，新增修改对话框上传员工头像、商品图片用的就是它。
    * 手动上传：先选择文件并对格式、大小做限制，确认后点上传按钮才发请求——本功能使用的就是这种。

* **标签部分**

    * > **定义**：`el-upload` 主标签及其内部触发按钮、真实上传按钮与提示区。

    ```html
    <!-- 数据导入对话框 -->
    <el-dialog v-model="excelOpen" title="数据导入" width="400">
      <el-upload
        ref="uploadRef"
        class="excel-uploader"
        :action="uploadExcelUrl"
        :auto-upload="false"
        :headers="headers"
      >
        <template #trigger>
          <el-button size="large" type="primary">上传文件</el-button>
        </template>
        <el-button type="large" type="primary" @click="submitUpload">上传</el-button>
        <template #tip>
          <div class="el-upload__tip">仅支持 xls、xlsx 格式，文件大小不超过 1M</div>
        </template>
      </el-upload>
    </el-dialog>
    ```

    * `el-upload` 是文件上传主标签；`ref` 关联一个文件上传对象，最终发请求由该对象控制。
    * `class` 定义上传区域样式，用默认的即可；`:auto-upload="false"` 关闭自动上传；`:action` 设置发往后台的请求地址。
    * `#trigger` 内的按钮对应选择上传文件，按钮名称改为「上传文件」；模板外的 `el-button` 对应真正执行上传，名称改为「上传」，绑定 `submitUpload`。
    * `#tip` 里的 `div` 提示上传格式与大小限制，按原型抄写：仅支持 xls、xlsx 格式，文件大小不超过 1M。

* **TS 语法不能直接用**

    * 官网示例的 `script` 部分基于 TS 语法，而若依项目是原生 JS 写的，无法直接使用，需参考它改造成 JS。
    * TS 的实例对象写法，在 JS 里等价于 `ref` 小括号内嵌套一个空花括号对象。

    ```js
    // 上传excel文件
    const uploadRef = ref({})

    // 上传文件
    function submitUpload() {
      uploadRef.value.submit()
    }
    ```

    * 方法内拿到上传的 Excel 文件对象，调用其内置 `submit` 完成提交，从而按 `action` 向后台发送请求。
    * 未写这段 JS 时，选完文件点上传没有任何反应。

### 代理前缀与令牌请求头

* **跨域与代理转发（proxy forwarding）**

    * > **定义**：前后端分离下由前端构建配置把带约定前缀的请求转发到后端端口的机制。

    * Element Plus 官网示例的 `action` 是官网地址，必须改成帝可得的 `/manager/sku/import`。
    * 但只写 `/manager/sku/import` 仍走不通：若依项目是前后端分离架构，数据交互存在跨域问题，靠 `vite.config.js` 里的代理转发解决。
    * 代理转发要求前端请求路径包含 `/dev-api`，才会向后台 8080 端口转发。
    * 不建议直接硬编码 `/dev-api`：现在开发环境可用，生产环境前缀一调整这段代码就得跟着改，后期维护繁琐，因此要做动态拼接。

* **令牌请求头**

    * > **定义**：携带登录身份令牌的 `Authorization` 请求头，缺失会被后端拦截器拦下返回 401。

    * 平时写的 API 请求 JS 里看不到请求头，是 `src/utils` 下的 `request` 工具类在请求拦截器中自动拼接了 token。
    * 后端校验 token：合法放行业务逻辑，不合法拦截并返回 401，前端跳回登录页。
    * 文件上传直接触发 `action` 提交，底层不走 `request` 工具类，因而不会触发请求拦截器，请求头必须手动拼。

* **抄作业两处**

    ```js
    // 上传地址
    const uploadExcelUrl = ref(
      import.meta.env.VITE_APP_BASE_API + '/manager/sku/import'
    )

    // 上传请求头
    const headers = ref({ Authorization: 'Bearer ' + getToken() })
    ```

    * 新增修改对话框里本来就有 `el-upload` 组件，可以直接借鉴两行。
    * `import.meta.env.VITE_APP_BASE_API` 是动态获取当前前端环境信息的响应式对象，开发环境下取到的路径就是 `/dev-api`，再拼上接口定义的路径。
    * 原代码里方法拼的是 `common/upload`（图片上传服务器地址），必须按接口文档改成 `/manager/sku/import`，不能把图片上传地址直接搬过来。
    * 请求头名称 `Authorization` 与接口文档对应，值是 `Bearer ` 加空格再拼动态获取的登录令牌。

    ```text
       el-upload  :action="uploadExcelUrl"
                       |
                       v
       uploadExcelUrl = import.meta.env.VITE_APP_BASE_API + '/manager/sku/import'
                       |                (开发环境下就是 /dev-api)
                       v
       vite.config.js 中的代理转发  -------->  后端 8080 的 /manager/sku/import
                       |
                       + 同时携带 :headers="headers"
                         Authorization: 'Bearer ' + getToken()
    ```

* **getToken is not defined**

    * > **易错点**：引入动态请求头代码后页面空白、控制台报 `getToken is not defined`，因为当前页面没有导入这个方法。

    * `getToken` 是框架提供的方法而非自己写的，复制请求头代码时必须一并把它的 import 一起复制。
    * 在商品上传组件里搜索 `getToken` 可找到那行导入：`import { getToken } from '@/utils/auth'`。
    * 想用哪个方法就要提前做一个 `import` 导入。
    * 补上导入后刷新页面不再报错，点上传在 Network 抓包可见 `/dev-api` 前缀与 `Authorization` 令牌信息都已带上，请求路径与接口文档一致。

## 交付纪律

* **测试后再交付**

    * > **结论**：写完看着对不等于对，必须功能测试跑通才能进入下一个模块。

    * 商品价格那个坑纯靠功能测试测出来：页面跑起来才发现新增完是 0.03 元，打开数据库客户端看最后一条记录存的是 `3` 而非 `300`，才顺着「回显除以一百、提交乘以一百」把根因找到，改完复测才敢说交付。
    * 无论日常练习还是项目开发，都要等写好的代码测试完毕再提交交付，然后开发下一个功能模块。

* **见名知意加注释**

    * 后端 `countChannelBySkuIds` 写完名字和注释，SQL 就自己生成了且完全可用。
    * 通义灵码生成的内容普遍需要辨别与调整：方法漏参数、返回结果没拆开、注释掉的旧标签被一并留下。
    * AI 工具目前只能作为辅助开发的助手，前后端编程基础扎实才能提高开发效率。
