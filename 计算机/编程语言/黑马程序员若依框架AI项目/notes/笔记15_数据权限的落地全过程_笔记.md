# 数据权限的落地全过程

---

## 数据权限的骨架

数据权限的整套机制由三样东西接力完成：一个自定义注解、一段 AOP 切面、一段靠 `${}` 注入的动态 SQL。

### 三张表之间的关系

* **用户表 `sys_user` 与部门表 `sys_dept`（一对多）**

    * 用户表上的 `dept_id` 是外键，指向部门表主键；添加新用户时必定要指定其所属部门。

* **用户表与角色表 `sys_role`（多对多）**

    * 通过中间表 `sys_user_role` 表达，该表含 `user_id` 与 `role_id` 两个外键，分别指向用户表和角色表主键。

* **角色表与部门表（多对多）**

    * 通过中间表 `sys_role_dept` 表达，该表含 `role_id` 与 `dept_id` 两个外键。
    * > **结论**：要做自定义数据权限必须依赖这张中间表，光靠用户表上的 `dept_id` 不够，因为一个角色可能对应多个部门。

```text
   sys_dept（部门表，自关联：dept_id / parent_id）
      ▲     ▲
      │     │
      │     └────────────────────┐
      │ dept_id（一对多）         │ dept_id（多对多）
      │                          │
   sys_user（用户表）         sys_role_dept（角色-部门中间表）
   user_id(PK)  dept_id(FK)      role_id  │  dept_id
      │                              │ role_id
      │ user_id                       ▼
      │ 多对多                   sys_role（角色表）
      │                        role_id(PK)
      │                        data_scope   ← 数据权限范围 1~5
      │                              ▲
      └───► sys_user_role ──────────┘
           （用户-角色中间表，user_id | role_id）
```

* > **注意**：部门表是自关联表，靠 `dept_id`（当前部门）与 `parent_id`（父部门）两个字段建立父子关系，与菜单权限表是同一套路。

### 五种数据权限范围

范围值存放在角色表的 `data_scope` 字段上，取值 1~5；用户登录后拿到用户 id 与部门 id，再按其角色决定可访问的数据范围。

| 范围值 | 数据权限类型 | 范围从哪里来 |
| :--- | :--- | :--- |
| 1 | 全部数据权限 | 不受任何限制 |
| 2 | 自定义数据权限 | 角色 ↔ 部门中间表（可跨部门、跨子公司） |
| 3 | 本部门数据权限 | 用户表里的 `dept_id` |
| 4 | 本部门及以下数据权限 | 用户表里的 `dept_id` + 部门表父子关系 |
| 5 | 仅本人数据权限 | 用户表里的 `user_id` |

* 拥有「全部数据权限」的用户不受这三张表的数据范围限制，可以查询所有数据。
* > **注意**：「仅本人」这一种在字段注释里根本没有体现出来，对应的是范围值 5。

## `@DataScope` 注解的两个别名开关

`@DataScope` 放在 ruoyi 的 `common` 模块下的 `annotation` 包里，用在需要做数据权限控制的方法上，系统会据此拼接数据范围的 SQL 条件。

### 别名与生效范围

* **`deptAlias`**：部门的别名，属性值为 `d`，用于只筛选特定部门的数据。
* **`userAlias`**：用户的别名，属性值为 `u`，用于只筛选特定用户的数据。
* 两个属性都写上，系统才知道需要完整的五种类型控制；只写部门别名，就只对部门维度筛选。

```java
// 角色实现类 SysRoleServiceImpl 的查询角色列表方法，只指定部门别名
@DataScope(deptAlias = "d")
public List<SysRole> selectRoleList(SysRole role) { ... }

// 用户实现类 SysUserServiceImpl 的查询用户列表方法，两个别名都写
@DataScope(deptAlias = "d", userAlias = "u")
public List<SysUser> selectUserList(SysUser user) { ... }
```

* > **结论**：部门列表查询方法上只指定了 `deptAlias` 而没有 `userAlias`，方法层面压根不支持按用户维度过滤，当角色被设为「仅本人」时这一维度要求就落不下去，最终列表一片空白——这不是 bug，而是注解属性与方法需求对不上。

### 元注解与权限字符串属性

| 元注解 | 作用 |
| :--- | :--- |
| `@Target(ElementType.METHOD)` | 指定使用位置，仅在方法上，其他位置不能用 |
| `@Retention(RetentionPolicy.RUNTIME)` | 保留策略为运行时，程序运行时可被反射读取 |
| `@Documented` | 会被 Java 的 doc 工具记录，生成文档时包含该注解信息 |

* 第三个属性是权限字符串 `permission`，用于匹配多个角色、符合要求的权限。
* 它指的就是 Controller 上 RBAC 权限串的全字符形态，例如 `@PreAuthorize("@ss.hasPermi('system:user:list')")` 中的 `system:user:list`。
* 默认情况下 `@ss.hasPermi` 走 `PermissionService`，其中有一行关键代码把权限信息写入 `PermissionContextHolder`——它是一个线程局部变量（ThreadLocal）。
* > **结论**：`@DataScope` 里不设置 `permission` 完全没关系，因为 `hasPermi` 已经把权限串存进了上下文对象，切面中还要靠它做角色校验。

* > **易错点**：`@Retention` 必须是 `RUNTIME`。否则注解在编译期就没了，AOP 那套反射扫描全白干——这是自定义注解加 AOP 最经典的一个坑。

## Mapper 层的 `${params.dataScope}`

光在 Service 方法上挂注解还不够，数据权限要在 Mapper 层进一步过滤，关键是一个占位符。

### 占位符与 params 的来源

* 映射文件在 `where` 条件的最后一行写 `AND ${params.dataScope}`，作用相当于在 `select` 语句后拼接一个 `and` 条件语句来实现查询限制。
* 这里的 `${}` 与实战篇接收前端参数的用法不同，它取的是 `params` 里的 `dataScope` 这个动态 SQL 语句。
* `params` 来自实体类继承的基类 `BaseEntity` 中的 `Map` 集合属性：`dataScope` 是 key，值就是稍后拼接好的 SQL 语句。

```xml
<!-- 最后一行的位置 -->
AND ${params.dataScope}
```

* > **结论**：此处用 `${}` 拼 SQL 不存在注入风险，因为拼接在后端进行，且切面在拼接前会先把 `dataScope` 强制置为空串，等于又上了一道保险。

### 拼接前后的 SQL 对比

未过滤时执行的是原始单表查询，能查出所有用户；已过滤时实际执行的形态是嵌套条件查询。

```sql
-- 未过滤：所有人的登录信息都能查出来
SELECT ... FROM sys_user;

-- 已过滤（拼接后的实际形态）
SELECT ...
FROM sys_user
WHERE ...
  AND dept_id IN (
      SELECT dept_id FROM sys_role_dept WHERE role_id = 2
  );
```

* 查的表是角色-部门中间表，条件是角色 id，表示根据当前登录用户获取其角色，再查该角色对应的部门 id。
* 部门 id 可能有多个，所以外面以 `in` 的方式做条件筛选。
* > **结论**：在 SQL 里用 `IN (SELECT ...)` 关联中间表筛部门，那就必须是自定义数据权限（范围值 2），因为只有这一种依赖角色-部门中间表。

### 实现数据权限的两个前置条件

* **只有继承了 `BaseEntity` 的实体类，才能使用数据权限控制**，因为 SQL 语句要存在该实体的 `params` `Map` 集合属性中，没继承就取不到。
* **业务表要实现数据权限，就必须包含 `dept_id` 和 `user_id` 两个字段**，只有这样才能按部门或用户筛选数据。

## 切面 `DataScopeAspect` 的处理流程

拦截该注解的切面类叫 `DataScopeAspect`，位于 ruoyi 的 `framework` 模块，类上带 `@Aspect` 交给 IOC 容器，真正干活的方法叫 `before`，带 `@Before` 前置通知，会在目标方法执行之前触发。

### 类骨架与常量

* 类中定义了各数据权限类型对应的常量值，从 1 到 5，含义与角色表 `data_scope` 范围值一一对应。
* 最后一个常量是数据权限过滤关键字，也就是 `BaseEntity` 的 `params` Map 里指定的那个 key：`dataScope`，其值为待拼接的 SQL 过滤条件。

### 进门先扫地

* 拿到切点方法的第一个参数，判断它不为空且属于 `BaseEntity` 类型，是则对子类强转成父类，取 `getParams()` 得到的 map 集合，执行 `params.put("dataScope", "")` 强制置为空串。
* 置空的目的就是防止 SQL 注入：即使有人在前端恶意拼接了 SQL，也会在这一步被抹掉。
* > **结论**：这一行同时回答了为什么实体类必须继承 `BaseEntity`（因为要强转），以及为什么 `${}` 是安全的（因为有人先清了场）。

### 超管直接放行

* 清理完成后先获取当前登录用户，再判断他是否为超级管理员。
* 若是超级管理员，切面方法提前结束执行，直接进入 Mapper 层；Mapper 的 SQL 末尾并没有拼接任何参数，等于查询所有数据。

### 两道关卡

不是超级管理员时，遍历当前用户所分配的角色集合，准备一个空串 SQL 拼接对象和一个存储已添加数据范围类型（值 1~5）的集合，每一轮必须先过两道关卡。

* **第一道关卡：类型是「自定义」并且集合里已经有了。**

    * 遵循第一添加者优先原则，哪个角色先设置就以哪个为准，后面重复的自定义类型直接 `continue` 跳过。

* **第二道关卡：当前角色的权限列表里不包含目标方法的权限字符串。**

    * 该角色压根没有权限访问此方法，就没有必要做数据权限过滤，同样 `continue` 跳过，不再拼接 SQL。

### 五种范围对应的 SQL 片段

* **类型 1 全部数据**：权限等同于超级管理员，会清空之前拼接的 SQL 语句，把当前类型存入集合，然后 `break` 跳出整个循环，后续角色不再拼接条件；清空之后默认就相当于查询所有。
* **类型 2 自定义**：用 Spring 工具类拼接，两个花括号占位符分别设置部门别名和当前角色 id，可跨子公司、跨部门。

```sql
 AND #{deptAlias}.dept_id IN (
       SELECT dept_id FROM sys_role_dept WHERE role_id = #{roleId}
 )
```

* **类型 3 本部门**：两个占位符，第一个是部门别名，第二个是当前用户的部门 id。

```sql
 AND #{deptAlias}.dept_id = #{deptId}
```

* **类型 4 本部门及以下**：包含两个条件（本部门、子部门），三个占位符，比类型 3 多一个函数 `find_in_set`。

```sql
 AND #{deptAlias}.dept_id IN (
       SELECT dept_id FROM sys_dept
       WHERE dept_id = #{deptId}
          OR find_in_set(#{deptId}, ancestors)
 )
```

* **类型 5 仅本人**：判断当前注解当中有没有用户别名；有则以当前用户 id 作为条件查询，做到个人数据隔离（如市场部销售数据每人只看自己的）；没有则把 id 设置为零，即不查询任何数据。
* 每一轮遍历的最后，把当前角色的数据范围类型存入集合，还有角色就进入下一轮遍历。

### 两个收尾判断

* **数据范围类型集合为空**：说明当前用户所有角色都不包含目标方法的权限字符串，不需要做数据权限过滤，但仍把部门 id 设置为零，结果依然啥也查不到。
* **集合不为空**：判断 SQL 拼接字符串是否非空，非空则强转第一个参数为 `BaseEntity` 后拿到 map 集合做 put 赋值，左边是 `dataScope` 这个 key，右边是拼好的 SQL 条件。
* 赋值时通过 `substring` 过滤掉前四位，只取后面内容——因为每段 SQL 都带有左右两侧带空格的 ` and `，这四个字符不属于要拼进 `select` 的内容。
* > **注意**：这是那个空白的部门列表的谜底——方法上只有部门别名没有用户别名，角色又是「仅本人」，拼出来的条件就是 `dept_id = 0`，什么都不让查。

* 完整链路如下：

```text
 用户请求进入挂了 @DataScope 的方法
        │
        ▼
 ┌────────────────────────────────────┐
 │ DataScopeAspect @Before 前置通知   │
 ├────────────────────────────────────┤
 │ 1. 清理 params.dataScope 为空串    │
 │    ← 防 SQL 注入                   │
 │ 2. 取当前登录用户                  │
 └────────────────┬───────────────────┘
                  │
          ┌───────┴────────┐
          │ 超级管理员？    ├── 是 ─► 什么都不拼，直接放行
          └───────┬────────┘          ▼
                  │ 否         Mapper 执行原始 SQL
                  ▼             查询全部数据
    遍历当前用户的角色集合
                  │
     ┌────────────┴─────────────┐
     │ 关卡1 自定义型已添加？   ├─ 是 ─► continue（第一添加者优先）
     │ 关卡2 角色无方法权限？   ├─ 是 ─► continue（没权限就不筛）
     └────────────┬─────────────┘
                  │ 都通过，按 1~5 拼 SQL
                  │
     1 全部          → 清空已拼条件，break 整个循环
     2 自定义        → 部门id IN（按角色id 查中间表）
     3 本部门        → 部门id = 当前用户部门id
     4 本部门及以下  → 本部门 + find_in_set(部门id, ancestors)
     5 仅本人        → 有用户别名拼 user_id，没别名则拼 0
                  │
                  ▼
     集合为空（所有角色都没权限）→ 部门 id 拼成 0
                  │
                  ▼
     SQL 非空 → params.put("dataScope", sql.substring(4))
                去掉前置的 " and " 四个字符
                  │
                  ▼
     Mapper 执行 SQL，${params.dataScope} 自动拼进来
                  │
                  ▼
           返回筛选后的结果集
```

* 整个机制就是通过 AOP 的切面技术，动态地根据用户的角色和权限过滤数据，确保数据的安全性和合规性。

## ancestors 与 find_in_set

### 用家谱字段替代递归

* 部门表的自关联结构以虚拟部门 id 为 0 作根节点，`parent_id = 0` 的顶级部门再往下挂子部门，形成树形结构。
* 一层层往下找子部门需要递归，而递归效率较低；部门表里的 `ancestors` 字段记录了当前部门的「家谱」，即从根节点到它父辈节点的全部部门 id 组成的逗号分隔字符串列表。
* 传一个部门 id 进去匹配这个列表，命中说明它属于该部门的子部门，未命中则被过滤掉，查询条件一次性覆盖整条链路。

```text
 dept_id  dept_name        parent_id  ancestors
------------------------------------------------------
 0        （虚拟根节点）      0         0
 100      若依科技          0         0,100
 101      深圳总公司        100        0,100,101
 102      长沙分公司        100        0,100,102
 103      研发部           101        0,100,101,103
 104      市场部           101        0,100,101,104
 105      测试部           101        0,100,101,105
```

* > **定义**：`find_in_set(str, strlist)` 的作用是在一个字符串列表当中查找一个特定的字符串，左边传入需要查找的特定字符，与右侧的字符列表比对，存在返回真，不存在返回 `false`。
* 数据库自带的字符串查找函数加一个「家谱」冗余字段，把递归查询压成一次字符串匹配，这是典型的用空间换时间。

### 部门树的层级示例

* 顶级部门若依科技 id 为 100，其 `parent_id` 指向虚拟部门 0；深圳总公司 101 与长沙分公司 102 的 `parent_id` 都是 100；101 下面挂研发部 103、市场部 104、测试部 105 等子部门，`parent_id` 都指向 101。

```text
        dept_id = 0
        （虚拟根节点）
              ▲  parent_id
              │
        若依科技  100
              ▲
        ┌─────┴─────┐
    深圳总公司 101   长沙分公司 102
        ▲
    ┌───┼─────┬─────┐
  103   104   105   106
  研发部 市场部 测试部 ……
```

* 当前登录用户属于深圳总公司（`dept_id = 101`），就以 101 为条件查出其子节点 103、104、105，这些子部门也在其数据范围内。

## 登录日志的数据权限改造

### 改造五步

| 步骤 | 做什么 | 关键点 |
| :--- | :--- | :--- |
| 第一步 | 加权限注解 | `@DataScope` 要同时指定部门、用户两个别名 |
| 第二步 | 加表字段 | `dept_id`、`user_id`；提示词写好，DDL 不用背 |
| 第三步 | 加实体属性 | 用 `Long` 包装类，顺手生成 get/set |
| 第四步 | 改映射文件 | 单表改三表 `LEFT JOIN`，别名前后对应；查询和 insert 都要改 |
| 第五步 | 改异步工厂 | 按 `userName` 反查用户对象，设置两个 id 后再入库 |

* **第一步**：在登录日志 service 实现的查询集合方法上添加 `@DataScope(deptAlias = "d", userAlias = "u")`，两个别名都指定即开启数据权限控制。
* **第二步**：给 `sys_logininfor` 表新增 `dept_id` 和 `user_id` 两个 `BIGINT` 字段，用图形化工具的 Modify Table 加号或 `ALTER TABLE ... ADD COLUMN ... COMMENT` 命令行都可以。

```sql
ALTER TABLE sys_logininfor
    ADD COLUMN dept_id BIGINT COMMENT '部门id',
    ADD COLUMN user_id BIGINT COMMENT '用户id';
```

* 执行报错提示没有选中数据库，是因为命令要在目标库下执行，得先在命令行里选中对应的库再重新执行。
* **第三步**：在 `SysLogininfor` 实体类上补 `userId` 与 `deptId` 两个属性，id 用 `long` 为空时没法判断，所以用包装类 `Long`，再用 `Alt + Insert` 生成 getter 和 setter。

```java
/** 用户id */
private Long userId;

/** 部门id */
private Long deptId;
```

* **第四步**：映射文件里的 SQL 至少涉及登录日志表、部门表、用户表三张，要把单表查询改为左外连接三表，并额外查出 `u.user_id` 与 `d.dept_id`。

```sql
SELECT   l.user_name,
         l.ipaddr,
         l.login_location,
         l.browser,
         l.os,
         l.status,
         l.msg,
         l.login_time,
         u.user_id,
         d.dept_id
FROM     sys_logininfor l
LEFT JOIN sys_dept d ON l.dept_id = d.dept_id
LEFT JOIN sys_user u ON l.user_id = u.user_id
WHERE    1 = 1
```

* `where` 条件最后一行补上数据范围过滤的动态 SQL，位置就在条件末尾。

```xml
    <!-- 数据范围过滤 -->
    AND ${params.dataScope}
</select>
```

* > **易错点**：三表查询后字段可能出现重名冲突，一定要加表别名；`l.` 是日志表、`u.` 是用户表、`d.` 是部门表，这三个别名必须与 `@DataScope` 里配的 `deptAlias`、`userAlias` 一一对应，否则切面拼出来的条件找不到表。
* > **易错点**：占位符里的 `dataScope` 的 `S` 必须大写，抄错大小写条件就不会被拼接进来。
* 查询时日志表里必须有 `dept_id` 和 `user_id` 的值，否则关联不上部门表和用户表，所以 `insert` 语句也要同步补上这两列的字段名、判空条件和占位符。

* **第五步**：登录日志由异步任务管理器保存，具体是异步工厂创建的定时任务，最终通过 `SpringUtils` 拿到日志 service 完成插入，需要在入库前设置用户 id 和部门 id。

```java
// 设置登录用户的id和所属部门id
SysUserService userService = SpringUtils.getBean(SysUserService.class);
SysUser user = userService.selectUserByUserName(username);
if (user != null) {
    // 设置用户id和部门id
}
```

* 该方法原本只传了登录用户名而没有传两个 id，但可以以用户名作条件反查用户表拿到 `user_id` 和 `dept_id`，登录源码中已提供按 `username` 查询用户表的方法。

### 造数据与排错

* 历史记录里没有 `dept_id` 和 `user_id`，无法做细粒度数据权限控制，必须先清掉旧数据再重新造一批带完整字段的模拟数据。
* 造数方式是退出登录后分别为超级管理员、黑马彭于晏、若依制造验证码失败、密码失败等登录失败记录，密码故意多写一位，然后再正确登录一次。
* 超级管理员在系统管理的登录日志页面可以查看所有用户的登录信息。
* 出现查询结果与预期不符时倒着推：先看异步工厂（库里已有两个 id，没问题），再看映射文件的 insert 与多表查询（没报错且能返回全部数据），问题就落在数据范围过滤没有被指定上——`${params.dataScope}` 多打了一个字母，删掉后 `Ctrl + F9` 热部署即可修复，普通用户随即只能查看自己的登录记录。

## 核心结论与自测题

### 一句话链路

* RBAC 解决能不能访问，数据权限解决能看到多少，两者通过「注解 + 切面 + 动态 SQL」这套组合拳合到一起。
* 想开数据权限：方法上挂 `@DataScope`，要部门就写 `deptAlias`，要用户就写 `userAlias`。
* 想让它生效：实体类必须继承 `BaseEntity`，业务表必须有 `dept_id` 和 `user_id`。
* 条件怎么进来：Mapper 里写 `${params.dataScope}`，切面负责往这个 key 里塞拼好的 SQL。
* 安全性：切面在拼接前先把 `dataScope` 置空，前端恶意拼接的值在这一步就被抹掉。

### 自测题与答案

* **角色表和部门表之间应该是什么关系？**

    * 多对多，需要一张中间表，表里两个外键字段分别是 `role_id` 和 `dept_id`，分别指向角色表和部门表的主键。

* **那段嵌套查询 SQL 属于哪一种数据权限类型？**

    * 自定义数据权限（范围值 2），因为它查的是角色-部门中间表、条件是角色 id，只有这一种范围依赖该中间表。

* **添加完表字段之后，还要添加什么？**

    * 实体类的属性，同时补上 get/set 方法，字段才能在业务逻辑中拿到。

* **登录日志是怎么保存到数据库的？**

    * 通过异步任务管理器 / 异步工厂创建的定时任务，最后借助 `SpringUtils` 拿到登录日志的 service 完成插入，不是 Controller 直接调的。

* **日志表里的历史记录没有 `dept_id` 和 `user_id`，能实现数据权限控制吗？**

    * 不能，关联查询和过滤条件都依赖这两个字段的值，必须先清掉旧数据重新造一批带完整字段的模拟数据。
