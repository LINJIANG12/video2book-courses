# 运营管理 App 与设备屏幕端

## 运营管理 App 业务闭环

### 工单的创建与自动派单

* **工单类型**

    * 后台管理员可创建的工单分为投放运营设备、维修设备、撤机、商品补货等类型。

    * 工单一旦被创建，系统会自动把工单分配给相应的工作人员，分配动作不由管理员手动指定。

* **工单详情字段**

    * 员工在待办列表点开工单可看到详情，其中包含工单编号、设备编号、创建时间与地址、功能类型、备注说明。

    * 补货工单的详情比投放工单多三项：要补的货道、对应的商品和数量，这是员工到现场照着干的动作清单。

### 员工在 App 端的操作集合

    * 运营管理 App 的完整链路是后台造单 → 自动派单 → 员工接单 → 干活 → 完单，功能测试与源码讲解都围绕这四步展开。

    * 员工登录后可执行三类状态跃迁：接受工单（工单进入进行中）、标记工单已完成、拒绝或取消工单（工单进入已取消）。

    * App 端共三个工单界面：待办工单、进行工单、全部工单，三者由同一个工单查询方法支撑，靠工单状态条件区分。

## 客户端与后端联调环境

### 模拟器与 APK 安装

    * 在电脑上运行 APK 必须先有安卓模拟器，常见产品有 MuMu 模拟器、雷电模拟器、夜神，本课程使用 MuMu 模拟器。

    * 模拟器安装包随课程资料提供，双击在线安装；安装路径推荐选非中文路径。

    * APK 的装法不是拖拽，而是在模拟器右下角的「更多」按钮里找到 `APK 安装`，选中安装包后确认安装成功。

### 后端测试地址的写法

    * App 右下角的「设置 URL」默认填着测试地址，要改成运营管理 App 后端的本地地址，该后端端口是 9007。

    * 地址不能写 `localhost`：`localhost` 指向安卓模拟器自身，而模拟器里并没有运行这个 Java 后端。

    * 模拟器访问 Windows 宿主机使用固定别名 `10.0.2.2`，因此正确写法是 `http://10.0.2.2:9007`。

    * > **易错点**：本地环境发送请求并不是 HTTPS，`http` 后面多写一个 S 会导致请求失败。

    ```text
      帝可得 App（运行在安卓模拟器里）
            |
            |   HTTP 请求
            v
      10.0.2.2  ==  你这台 Windows 电脑
            |
            v
      运营管理 App 后端（Spring Boot，端口 9007）
            |
            +------> MySQL（dico）
            |
            +------> Redis（验证码、缓存）
    ```

### 后端工程导入与启动

    * 导入方式是把源码目录复制到开发路径下，再在 IDEA 里 `File` → `Open` 指向该目录，弹窗时选择在新窗口打开。

    * 首次打开会下载工程依赖，必须保证电脑联网；初始化完成的标志是项目名高亮且加粗。

    * 配置检查项有两类：数据库连的是帝可得 `dico`，用户名密码都是 `root`；Redis 的连接地址、端口、密码按本地环境调整。

    * 启动类 `Application` 用 debug 方式运行，控制台出现端口 9007 即启动成功。

    * 登录联调所需的手机号取自管理端员工列表，验证码在开发环境被写死为 `12345`。

    * 登录成功后界面应显示当前员工的姓名、角色、负责区域，以及待办工单列表；列表为空说明该员工暂无待办工单。

## 投放工单的状态流转

### 建单前的设备准备

    * 在设备管理中新增设备，选择型号为饮料机、点位为已建好的点位，确定后系统生成了设备编号。

    * 新增设备列表同时显示设备型号、详细地址、合作商，其中最关键的信息是当前设备状态为「未投放」。

### 接收工单

    * 在工单管理里新增投放工单，粘贴设备编号、选择工单类型为投放工单、指定运营人员并填写备注，创建后工单状态为「待办」。

    * 员工用自己的手机号在 App 登录后，待办列表出现该工单，详情页可选择拒绝或接收。

    * 点击接受后，待办列表立刻不再显示该工单，同时管理端工单状态变为「进行中」，App 的「进行工单」页签开始显示它。

### 完成工单与两处连锁变化

    * 工单状态更新成功之后，系统还要同步更新设备状态。

    * 投放工单完成时，管理端工单状态刷新为「已完成」，设备管理中该设备的状态由「未投放」改为「运营中」，表示正式对外提供服务。

    * 设备刚投放时货道里还没有商品，因此投放完成之后紧接着要走补货工单流程。

## 补货工单与库存更新

### 货道关联商品

    * 补货之前要先在设备的货道页面为货道关联商品，未关联时货道列表是空的。

    * 验证时只关联第一行的 1 到 6 号货道，练习中可以把六行全部关联完。

### 创建与派发补货工单

    * 补货工单在运营工单里新增，同样需要设备编号，运营人员选为负责该设备区域的工作人员。

    * 补货数量受货道容量约束：每个货道最大的限额是十件，补满数量默认为十件。

    * 工单创建完成后状态为「待办」，负责人为被指派的工作人员，其 App 的待办列表随即出现这条工单。

    * 员工接受后待办列表不再显示该工单，管理端工单状态变为「进行中」。

    * 在「进行工单」界面可以再次查看详情，补货成功后点完成工单，忙不过来时也可以点取消工单交给别人做。

### 完成后的库存验证

    * 补货工单点完成后，管理端工单状态刷新为「已完成」，该设备货道的库存同步更新。

    * 货道表 `tb_channel` 中能看到各货道剩余容量变为满额，最右侧还有最后一次补货时间字段。

    * 再次为该设备新建补货工单时，默认数量仍显示为十件，反向证明上一次补货成功且当前处于满库存状态。

## 运营管理 App 后端源码

### 技术栈与模块划分

    * 后端框架用 Spring Boot，数据访问层工具用 MyBatis-Plus，短信通知用阿里云短信服务。

    * 数据访问层的基础栈由若依原生的 MyBatis 改为 MyBatis-Plus，目的是在掌握 MyBatis 之后再用 MyBatis-Plus 提高 SQL 编写效率。

    * 项目只分为三个核心模块：

| 模块 | 承载的功能 |
| :--- | :--- |
| 员工管理 | 发送短信验证码、App 登录员工、查询员工信息 |
| 工单管理 | 查询工单、接收工单、拒绝或取消工单、完成工单 |
| 工单详情 | 根据工单 id 查询补货详情列表 |

### 员工管理：短信验证码

    * 发送短信的流程是 Controller 通过路径参数拿到手机号，再调用 Service 触发发送。

    * 开发环境把 `RandomUtil` 生成五位随机验证码的那行代码注释掉，改为在日志中直接显示固定验证码 `12345`。

    * > **注意**：产品上线之前必须把随机验证码代码打开、把写死 `12345` 的代码注释掉。

    * 短信通过阿里云短信工具类发送，模板已抽取好：从配置文件读取参数后调用工具类完成发送。

    * `application-dev.yml` 中配置短信的 Key 与 Secret 密钥对、短信签名、短信模板编码，自行注册阿里云短信后可自行测试。

    * 短信发送成功后把验证码写入 Redis，有效时间设为 5 分钟，也就是 300 秒；登录时在有效期内取出做比对。

### 员工管理：登录与资料查询

    * 登录接口用 DTO 接收参数，Service 第一步从 Redis 取出有效验证码与前端录入值比对，不一致则抛业务异常并提示「验证码错误」。

    * 验证码正确后再比对手机号，手机号有问题则提示手机号非法，两个校验都通过才算登录成功。

    * 登录成功返回 `LoginVO`，其中设置角色编码、员工姓名、员工 id、员工负责区域和登录成功提示信息。

    * 随后制作 JWT token 令牌，并判断员工是维修员还是运营员，供前端区分身份。

    * 查询员工信息时前端传当前登录员工 id，调用员工 Service 的 `getById`，走 MyBatis-Plus 通用 Service 功能，Service 层因此可以省略。

    * 拿到员工实体后封装返回结果，把实体类转换成前端需要的 VO 对象即可。

### 工单管理：查询

    * 查询方法同时支撑 App 端三个界面：首页待办工单、进行中工单、全部工单。

    * 接收参数非常多：分页参数、设备编号、用户 id、工单编号、工单状态、是否为运维工单、日期范围。

    * Service 先封装 MyBatis-Plus 分页对象，再用 `LambdaQueryWrapper` 构建动态 SQL 支持上述各种条件。

    * 查询按时间范围实现倒序，执行分页后再补上工单类型与工单状态的文字说明，返回最终分页结果。

### 工单管理：四个动作的校验链

    * 四个动作的校验链高度同构，区别只在「允许的当前状态」和「落到什么终态」：

| 动作 | 工单必须存在 | 允许的当前状态 | 权限校验 | 最终结果 |
| :--- | :--- | :--- | :--- | :--- |
| 接收 | 是 | 待处理（刚创建） | 登录人 = 工单分配人 | 改为进行中 |
| 拒绝 / 取消 | 是 | 待处理 或 进行中 | 登录人 = 工单分配人 | 改为已取消，并记录理由 |
| 完成 | 是 | 进行中 | 登录人有权完成 | 改为已完成 + 更新设备状态 / 货道库存 |

    * 接收工单的前端只传工单 id，当前登录人 id 由服务端自己获取，两者一起传给 Service。

    * 接收时的第三道校验是有权接收，即登录人必须与工单的分配人一致，不一致抛异常。

    * 三个校验全过后把工单状态改为进行中，用 MyBatis-Plus 通用 Service 完成更新，mapper 层可以省略不写。

    * 拒绝或取消会额外拿到拒绝或取消的理由，校验通过后把状态改为已取消并把理由写回数据库。

    * 完成工单只允许状态为进行中的工单，刚创建、已取消、已完成的都不能再次完成。

    * 完成工单后按工单类型分三条支路更新设备侧数据：

    | 工单类型 | 完成后的联动 |
    | :--- | :--- |
    | 投放工单 | 设备状态改为运营状态 |
    | 撤机工单 | 设备状态改为撤机 |
    | 补货工单 | 查工单明细的补货清单，把明细数据更新到库存 |

    * 补货工单完成时库存跟着变，正是第三条支路干的活。

### 工单详情模块

    * 工单详情模块的核心功能是根据工单 id 查询补货详情列表，供工作人员查看自己负责工单的具体补货信息。

    * Controller 拿工单 id 调 Service，Service 用 MyBatis-Plus 做条件封装后执行查询直接返回，只需要编写 Service 层。

## 设备屏幕端环境搭建

### H5 页面与设备编号参数

    * 屏幕端前端代码随资料提供，双击打开 `index.html` 就能模拟设备屏幕端的展示效果；资料里对应的文件夹名叫 `secret`。

    * 刚打开时没有商品展示，因为还没有连后端服务。

    * 让页面连上后端的方法是在地址栏用问号拼接参数，参数名是 `innerCode`，值填设备编号，回车即刷新出该设备的货道商品列表。

    * 界面上某款商品显示「已售罄」，表示该货道的商品已经卖完。

### 屏幕端后端工程

    * 屏幕端后端的导入步骤与运营管理 App 后端一致：`File` → `Open`、选新窗口、等右下角下载依赖完成、项目名高亮加粗即初始化完毕。

    * 数据库同样连帝可得 `dico`，用户名密码都是 `root`；Redis 的连接地址、端口、密码也要逐一核对。

    * 数据库与 Redis 信息都写在 `application-dev.yml` 里，确认无误后用 debug 启动 `Application`。

    * 控制台看到端口 9008 即屏幕端后端启动成功。

### 两端工程对照

| 工程 | 端口 | 入口怎么打开 | 关键参数从哪儿来 |
| :--- | :--- | :--- | :--- |
| 运营管理 App 后端 | 9007 | MuMu 模拟器里的 APK | App 内「设置 URL」里配 `http://10.0.2.2:9007` |
| 设备屏幕端后端 | 9008 | 双击 `index.html` 打开的 H5 | 地址栏 `?innerCode=<设备编号>` |

## 折扣策略与支付出货链路

### 折扣落到价签

    * 屏幕端刚打开时显示的都是商品原价，需要在管理端验证固定折扣策略是否生效。

    * 验证方式是在设备列表中给该设备点击「策略」，选择九折优惠并确定，策略就关联到该设备上了。

    * 回到屏幕端刷新页面，价格变成策略优惠后的价格，九折策略下冰糖雪梨显示 2.25 元。

### 支付二维码链路

    * 用户点击商品后系统弹出支付方式，提供微信支付与支付宝支付，选定后生成二维码供用户扫码支付。

    * 由于第三方支付平台没有针对个人用户开放，课程并未实现具体支付代码，只串联了实现思路。

```text
  用户点击商品
      |
      v
  H5 屏幕端向后端发起购买请求
      |
      v
  订单服务：根据前端传入的商品 id 和购买数量创建订单
      |
      v
  调用第三方支付平台，生成一个预交易的链接
      |
      v
  把预交易链接返回到前端的 H5 界面
      |
      v
  前端用 qrcode 技术生成二维码，屏幕上显示出来
      |
      v
  用户拿出手机扫码，在第三方支付平台完成支付
      |   （用户与第三方平台直接交互，我们的系统不参与）
      v
  第三方平台向订单服务发送支付回调
      |
      v
  订单状态：待支付  --->  已支付
      |
      v
  系统通过 MQTT 向智能售货机设备下发出货指令
      |
      v
  设备从相应的货道当中调出商品，完成发货
      |
      v
  系统自动更新库存，对应商品库存数量减一
```

    * 二维码只是这条链路的第一站，真正的闭环在最后一环——设备出货之后库存要减一，否则屏幕上那个「已售罄」永远不会出现。

### Jeepay 统一支付框架

    * 同时支持微信支付和支付宝支付时，直接对接两套原生 SDK 代码繁琐，开源框架 Jeepay 底层封装了这两个平台的功能。

    * 特点一是为支付宝和微信提供统一的调用接口；特点二是支持本地支付、小程序、H5、App 多种支付方式并提供统一入口。

    * 核心价值就是「统一」：学一套代码就能完成微信、支付宝以及对应各种类型的支付方式。

    * 集成步骤第一步是导入依赖坐标，分别为微信支付和支付宝支付两个依赖。

    * 第二步在配置文件中加配置：微信支付填商户号、AppId、密钥、签名等，支付宝填 AppId，另外还要配回调地址。

    * > **注意**：回调地址必须是外网能够访问的，因为支付成功后由第三方平台访问它来通知系统更新订单状态并发货。

    * 第三步在订单模块里注入 `JeepayPayment` 对象，它的 API 只需设置三个参数即可发起下单。

    | 参数 | 含义 | 注意事项 |
    | :--- | :--- | :--- |
    | `setTotalFee` | 支付金额 | 单位是分，用整数传就不用担心精度丢失 |
    | 订单号 | 本次交易的业务单号 | |
    | 商品名称 | 展示给用户的商品名 | |

    * 下单返回的 response 中要取的是 `codeUrl`，它就是二维码对应的支付链接；拿到后响应到 H5 屏幕端，用 qrcode 生成二维码供扫码支付。

    * 回调侧只需定义 `CallbackService` 对象并实现对应接口，重写支付成功、支付失败、退款成功、退款失败四个回调方法即可。

### MQTT 设备出货

    * 订单服务要指挥真实设备出货，用的是物联网通信技术 MQTT，向售货机设备发送指令。

    * 设备收到指令后从相应货道调出商品完成发货，系统随即自动更新库存，对应商品库存数量减一。

    * 实现这套技术可用的国内开源产品是 EMQX，安装后能让设备之间通过互联网互联交换信息，简称万物互联。

## 设备屏幕端源码分层

### 从 innerCode 到 SkuVO

    * 屏幕端后端目前只实现了一个模块，即设备管理模块，其核心功能是根据设备编号获取这台售货机的商品列表。

    * > **定义**：设备编号在代码里叫 `innerCode`，是每台售货机唯一的身份标识；屏幕上看到的商品与每个商品的售价都围绕这一个编号查出来。

    * Controller 方法接收设备编号，查询出 `SkuVO`，也就是包装之后的商品列表。

    ```text
    设备屏幕端 H5
         │  传 innerCode
         ▼
    DeviceController          ← 接收请求
         │
         ▼
    IDeviceService            ← 接口
         │
         ▼
    DeviceServiceImpl         ← 实现
         ├── ① baseMapper.findSkuByInnerCode(innerCode)   查商品
         ├── ② 按 innerCode 查售货机，取 policy 策略折扣
         └── ③ 遍历商品，套用折扣算真实价，打"打折标记"
         │
         ▼
    返回 List<SkuVO> → Controller 响应 → H5 渲染
    ```

    * `baseMapper` 并非特殊对象，MyBatis-Plus 在 Service 层注入 Mapper 时习惯用这个统一变量名指代当前实体的 Mapper，此处它就是 `SkuMapper`。

### 库存分组统计与虚拟表

    * `findSkuByInnerCode` 是自己定义的方法，不是 MyBatis-Plus 自动生成的，必须手写 SQL。

    * 该方法做的事是根据设备编号查询货道的商品信息以及商品的库存总量，涉及多表查询。

    * 第一张表是商品表，紧接着关联查询货道表，关键在于货道表是作为一张「虚拟表」参与查询。

    * 虚拟表第一步按设备编号查出当前设备的所有货道信息，第二步加上 `sku_id > 0` 的条件。

    * > **易错点**：`sku_id > 0` 表示货道已经关联了商品；未关联时 `sku_id` 的默认值是 0，所以「设备编号 + sku_id > 0」两个条件合起来才能拿到「指定设备关联了商品的货道信息」。

    * 第三步按 `sku_id` 分组，也就是按商品分组，拿到商品 ID 与该商品的库存容量。

    * 第四步把分组结果当作一张虚拟表，与商品表做内连接查询；内连接后返回商品的 ID、名称、图片、价格、商品类型 ID、单位（如净含量）和库存容量。

    * 最后按库存量排序，库存量大的商品排名靠前。

    ```text
    某台设备的货道现状
    ┌──────────┬────────────┬────────┐
    │  货道号  │  关联商品  │ 剩余量 │
    ├──────────┼────────────┼────────┤
    │   1-1    │  冰红茶    │    5   │
    │   2-1    │  冰红茶    │    7   │
    └──────────┴────────────┴────────┘
                  │  按 sku_id 分组，库存累加
                  ▼
          ┌───────────┬────────────┐
          │   商品    │  库存总量  │
          ├───────────┼────────────┤
          │  冰红茶   │ 5 + 7 = 12 │
          └───────────┴────────────┘
                  │  作为虚拟表，与商品表内连接
                  ▼
          ┌───────────┬────────┬───────────┐
          │   商品    │  价格  │ 库存总量  │
          ├───────────┼────────┼───────────┤
          │  冰红茶   │  ...   │    12     │
          └───────────┴────────┴───────────┘
                  │  按库存量降序
                  ▼
       屏幕端：同一件商品只显示一张图，库存多的排前面
    ```

    * 业务道理是屏幕端同一件商品只显示一张图片，再把库存量最高的商品排在最前面，优先让消费者买库存最多的那个。

### 折扣计算与打折标记

    * 拿到商品列表后按设备编号查这台智能售货机，目的只有一个：看它有没有关联策略，代码里叫 `policy`。

    * 折扣率的初始值是 100%，表示无折扣；策略存在就把折扣覆盖过来，九折对应 `discount` 变成 90。

    * 真实价格的算法是商品原价 × discount ÷ 100。

    * > **提示**：÷ 100 这一步不能省，折扣率在系统里用整数百分数存（90 表示九折），要还原成乘数必须除回 100，少这一步价格会放大 100 倍。

    * 算出真实价格后还要判断：真实价格小于原价就为该 `SkuVO` 设置打折标记，否则设置为不打折。

    * 标记的用途是让屏幕端据此做 CSS 样式——打折商品加划线价、折扣标签等特殊标记，没打折的原样输出。

    * 最后返回 `SkuVO` 的 list 集合，Controller 响应到前端，H5 把商品列表展示出来。

### 排序结果的现场验证

    * 验证方法是给 2-1 货道关联康师傅冰红茶并补上库存，使其库存最高，从而在屏幕端排到第一位。

    * 补货清单中 2-1 需要补 10 件，其余货道处于满容量，显示为 0。

    * 补货工单完成并回到屏幕端刷新后，康师傅冰红茶排到第一位，库存为 20 件。

    * 按 F12 打开调试工具在 Network 抓包可再次确认：康师傅库存容量 20 件，可口可乐、统一奶茶等仍是默认的 10 件。

## 原理篇技术路线

    * 实战篇之后的原理篇围绕六块内容展开，每一块都由具体痛点驱动：

| 模块 | 讲解的功能 | 背后要碰的技术 | 要解决的问题 |
| :--- | :--- | :--- | :--- |
| 代码生成器 | 代码生成器的配置与增强 | Velocity 模板引擎、Lombok、Swagger | 消除配置繁琐、让生成的代码更优雅 |
| RBAC 权限控制 | 登录到获取权限的完整流程 | Spring Security | 前后端如何协同做权限控制 |
| 操作日志 | `@Log` 注解记录增删改 | 自定义注解 + AOP 切面 + 异步任务管理器 | 三者结合的日志方案可以复用到类似场景 |
| 定时任务 | 动态管理定时任务 | Quartz | 单机/集群部署、修改代码白名单 |
| 数据权限 | 按公司/部门/个人展示数据 | 自定义注解 + AOP + SQL 拼接 | 细粒度数据权限控制 |

    * 代码生成器的痛点是配置繁琐：每张表生成前都要去掉 `tb` 前缀、设置作者为 IT 黑马、指定包路径、模块名设为 manager；生成的实体类里 getter/setter/toString 密密麻麻，Controller 还得手动加 Swagger 注解才能看在线文档。学 Velocity 模板引擎就能集成 Lombok 和 Swagger，实现代码生成增强。

    * RBAC 的痛点是不同用户按角色和权限看到的菜单不同，底层涉及 Spring Security，要分析从用户登录到获取权限的整个流程，并探讨如何根据用户角色生成动态路由。

    * 异步任务管理器能在不阻塞主线程的情况下执行任务，用户操作响应更快，其底层是线程池 + 异步工厂。

    * 操作日志靠 `@Log` 注解自动捕获用户的增删改操作，底层结合自定义注解、AOP 切面技术和异步任务管理器，三个技术组合可复用到类似场景。

    * 数据权限的演示效果是用户登录后按其所属公司、部门或个人展示相应数据，实现方式是自定义注解标识需要权限控制的方法或类，底层用 AOP + SQL 拼接。

## 代码生成器的两张核心表

### 表结构与关系

    * 代码生成器分设计和生成两部分：设计是把业务表结构导入系统，导入成功后可预览、编辑、删除和同步表结构；生成是选中表后单个或批量生成前后端代码并提供下载。

    * 导入后的业务表结构由两张核心表存储：

| 表名 | 存什么 | 对应哪个配置页面 |
| :--- | :--- | :--- |
| `gen_table` | 业务表的基本信息 | 「基本信息」和「生成信息」两个页面 |
| `gen_table_column` | 业务表的字段信息 | 「字段信息」页面 |

    * > **定义**：两张表是一对多关系，一张业务表可以有多个字段的信息，所以字段表里有一个外键 `table_id` 指向业务表的主键。

### 基本信息字段

    * 「基本信息」页面一共五个字段：

| 页面上的东西 | 对应字段 |
| :--- | :--- |
| 表名称 | `table_name` |
| 表的描述 | `table_comment` |
| 实体类名称 | `class_name` |
| 作者名 | `function_author` |
| 备注说明 | `remark` |

    * 表名称、描述、实体名称、作者、备注这五项更新之后都会存入 `gen_table`，`gen_table` 的其余字段都在「生成信息」页面里。

### 生成信息字段

| 配置项 | 字段 | 说明 |
| :--- | :--- | :--- |
| 生成模板 | `tpl_category` | 默认是单表 CRUD，还有树表操作与主子表共三种类型 |
| 前端类型 | `web_type` | 可选 Vue2 和 Vue3 |
| 生成的包路径 | `package_name` | |
| 生成的模块名 | `module_name` | |
| 生成的业务名 | `business_name` | |
| 生成的功能名 | `function_name` | |
| 生成代码的方式 | `gen_type` | 默认值 `0` 是 zip 压缩包下载；选自定义路径时下方多出路径输入框，对应 `gen_path` |
| 上级菜单 | `options` | 指定上级菜单的选项 |
| 关联子表 / 外键名 | `sub_table_name`、`sub_table_fk` | 模板选为主子表后才指定 |

    * 创建者、创建时间、更新者、更新时间这四个字段对应的是 `BaseEntity` 提供的审计信息。

## 导入业务表的前后端链路

### 前端如何弹出对话框

    * 导入业务的界面代码在 `views/tool/gen/index.vue`，后端接收请求的入口是生成模块的 `GenController`。

    * 导入按钮触发 `@click` 调用 `openImportTable` 方法，方法内通过 `proxy.$refs.importRef.show()` 把弹框叫出来。

    * > **提示**：`proxy.$refs` 的作用是获取子组件的实例对象，`importRef` 是组件的 ref 属性名，相当于 id 的作用。

    * `importTable` 视图组件的 `show` 方法做两件事：调用 `getList` 向后端发送请求、把 `visible.value` 置为 true 显示对话框。

    * `getList` 内部调用 `listDbTable` 传入查询条件，把结果封装到 `dbTableList` 供页面遍历展示。

    * `listDbTable` 定义在 `api/tool/gen.js` 中，用于查询 DB 数据库列表，请求路径是 `/tool/gen/db/list`，请求方式为 GET，会传递请求参数。

    * 用 F12 抓包可验证请求路径正是 `/tool/gen/db/list`，这里涉及分页查询，当前页面查询十条记录。

### 后端读的是 MySQL 自带表

    * 该方法支持按表名称、表描述作为条件传递，开启分页后调 Service 查询，把结果封装成分页对象响应前端；Service 直接调 Mapper 执行查询。

    * > **易错点**：这条 SQL 查询的表叫 `information_schema.tables`，跟项目中的业务表完全不一样。

    * `information_schema.tables` 是 MySQL 自带的表，默认查询当前数据库软件所有库中所有的表信息——十个库每个五张表就会一口气查出五十张表。

### 四层过滤条件

    * `table_schema = select database()` 限定在当前数据库，只查帝可得当前项目的业务库。

    * 排除 `QRTZ` 开头的表，因为它属于定时任务相关，不属于业务部分。

    * 排除代码生成器自带的 `gen_` 开头的两张表，即 `gen_table` 和 `gen_table_column`。

    * 排除已存在于 `gen_table` 中的表名，已导入并生成过代码的业务表不需要重复导入。

    * 剩下的动态 SQL 条件支持按表名称、表注释或描述信息、开始时间、结束时间查询，最后按创建时间降序。

### 用通义灵码读不熟的代码

    * 遇到不认识的 SQL 或后端结构不熟时的处理办法是借手通义灵码：选中代码右击，第一个功能是「解释代码」，第三个功能是「生成代码注释」。

    * 生成注释后可复制到原有代码中做替换并删掉末尾空行，后期读源码时通过注释就能理解这条 SQL 的含义。

    * 后端工程结构不熟时还有个定位技巧：双击 Shift 把接口路径粘过来，可直接定位到 `GenController` 的对应方法。

## 表结构落库

### 表名数组与字符串互转

    * 确定按钮触发 `@click` 调用 `handleImportTable`，第一步把表格中选中的表名数组用 `join(',')` 转成一个逗号分隔的字符串。

    * > **提示**：不选表直接点确定时转换结果是空串，前端会提示「请选择需要导入的表」并终止方法执行，下面的代码不再执行。

    * 转换完成后调用 `api/tool/gen.js` 中的 `importTable`，路径 `/tool/gen/importTable`，方式 POST，请求参数就是 `data`。

    * 后端返回状态码 200 时对话框隐藏并重新查询业务列表，把最新数据展示到页面。

    * 后端第一行做的事是把传进来的字符串再转回数组，然后按表名查询业务表的基本信息。

    * 查询到的信息封装到 `GenTable` 实体类，调 `importGenTable` 保存表结构；因为传进来的是集合，要对集合遍历，每张表走一遍导入逻辑。

    * > **提示**：调用时除了集合还要传当前登录人的用户名，因为后面生成的代码里 `create_by` 这些审计字段要有值。

### 表信息初始化

    * 先取当前表名再初始化表信息，初始化的字段包括：根据表名生成类名、按配置类读取的包路径设置包名、读配置文件设置作者、当前操作人取系统登录用户、获取模块名、按表名设置业务名、按表注释设置功能名。

    * 读取的配置文件专门读取 generator 模块的配置，其中定义了默认生成的作者、生成的包路径（如 `com.dkd.system`）、是否去除表的前缀。

    * 是否去除前缀的默认值是 `false`；改成 true 后要在最后一行指定去除的前缀名称（如 `tb`），多个前缀之间以逗号分隔。

    * 初始化完回到 Service，调用 `gen_table` 的 Mapper 新增并返回影响行数，影响行数大于 0 即基本信息插入成功。

### 字段信息的查询与插入

    * 接着保存该表的列信息，先按表名查数据库表的所有列信息，XML 中有判断、列注释、是否自增、列的类型等字段。

    * 这张表同样是 MySQL 自带的 `information_schema.columns`，默认查询所有库中所有表的列，因此要加条件过滤：查当前库指定表名的列信息，并按排序序号升序。

    * > **易错点**：把这段 SQL 拿到数据库客户端执行前要去掉 CDATA 标记——XML 中双引号需 CDATA 转义，而数据库里双引号不需要转义，所以左右两侧的标记都要去掉；还要传入表名，如 `tb_order`。

    * 以订单表为例执行后，列名、是否必填项、是否主键排序、列说明、是否自增、列类型全部查出，一共 25 个字段。

    * 结果封装到 `GenTableColumn` 后对集合遍历，25 个字段就遍历 25 次，分别插入业务字段信息表。

    * 插入前要先初始化列字段信息并让它关联表：取数据库类型与列名、关联当前表的 id 与创建者、按数据库列名通过驼峰式转换设置 Java 字段名。

    * 默认类型是 Java 类型先设为 `String`、查询类型默认 `EQ` 等值查询，所以前端订单表的查询方式默认都是等号。

### 类型到控件的映射

    * 初始化时根据数据库类型设置 Java 类型和对应的前端 HTML 控件类型：

| 数据库类型 | Java 类型 | 前端控件 |
| :--- | :--- | :--- |
| 字符串（`char`、`varchar`、`tinytext`、`text`、`mediumtext`、`longtext`） | `String` | 默认文本框；长度超过 500 则改为文本域 |
| 时间类型 | `Date` | 日期控件 |
| 浮点型 | `BigDecimal` | |
| 整型 | `Integer` | |
| 长整型 | `Long` | |

    * > **易错点**：字符串那一行的细节是长度超过 500 时 HTML 控件类型会被改成文本域，默认长度显示为文本框。

### 字段勾选项与命名规则

    * 插入字段默认全部勾选，所以前端「插入」这一列默认都是勾上的。

    * 编辑字段在字段名为 `id`、`create_by`、`create_time` 以及删除标记时不需要勾选，其余字段都要勾上。

    * 列表展示字段默认把 `id`、创建人、创建时间、删除标记、更新人、更新时间排除在列表之外。

    * 查询条件字段中一些过滤条件不需要在前端页面作为查询条件勾选。

    * 查询类型和前端控件类型最后按字段命名推断：

| 字段名包含 | 处理结果 |
| :--- | :--- |
| `name` | 查询类型改为模糊查询 `LIKE`（其他字段默认等值） |
| `status` | 前端控件改为单选框 `radio` |
| `type` 或性别 | 改为 `select` 下拉框 |
| `image` | 改为图片上传空间 |
| `file` | 改为文件上传空间 |
| `content` | 改为富文本控件 |

    * 这套推断让新增或修改页面自动出现图片上传空间、文件上传空间、富文本编辑空间、下拉框，得益于字段命名的规范性。

### 批量插入与事务

    * 整个导入插入操作涉及两张表：先写业务表基本信息表，再写业务表字段信息表。

    * 字段信息是在 for 循环内逐条插入的，性能不友好，项目中应改为批量新增。

    * 该方法还需要增加事务，保证插入操作要么都成功、要么都失败。

    * 插入成功后前端页面就能展示该表的基本信息、字段信息和生成信息。
