# 区域管理与合作商管理改造

## 对照原型改造的执行原则

### 先划「不改」清单

* **对照原型改造**
    * > **定义**：把代码生成器产出的、能跑通单表增删改查的代码，改成与页面原型对得上的代码。
    * 改造不是把生成器的东西全删了重写；先划出「不改」的清单，能不动的地方原封不动留着，把力气花在真正不一致的地方。
    * 代码生成器只认识表结构，不认识业务，页面原型上那些密密麻麻的细节它一个都不知道。

### 条件搜索与按钮区

* **条件搜索区**
    * 区域管理按区域名称、合作商管理按合作商名称，与原型完全一致且功能实测通过，不改造。
* **扩展按钮**
    * 原型按钮区只有一个「新增」，若依生成的代码另有修改、删除、导出三个扩展按钮，这三个先保留。
    * > **结论**：客户或产品经理明确说不要时再删也来得及；现在删了人家又要，还得加回去。
* **label 宽度**
    * 若依搜索区 label 宽 68px、对话框内 label 宽 80px，文字偏长时会自动换行、视觉不美观；调宽即可，搜索区改 90px、对话框内改 100px。

## 列表展示区改造

### 主键改序号

* **序号列（index）**
    * > **定义**：把列表首列的主键 ID 列替换为从 1 开始连续编号的列。
    * 动机：若依默认主键是雪花 ID、十几位数字，做排序时那一列显得凌乱；序号永远是 1、2、3、4，更直观更有条理。
    * 复选框列保留，它服务于批量删除。

    ```vue
    <el-table-column label="序号" type="index" width="50" />
    ```

    * > **易错点**：只把 `label` 改成「序号」并不会自动往下排，必须同时给 `type` 属性并取值 `index`；列宽过窄会换行，再补 `width="50"` 撑开。

### 按钮图标统一清理

* **按钮图标（icon）**
    * > **定义**：`el-button` 标签上的 `icon` 属性，用来定义按钮图标。
    * 原型里的修改、删除按钮不带图标，若依生成的带；改造时各移除一个 `icon` 属性即可。
    * 判定依据是整体一致性：将来要在同一排增加「查看详情」按钮，那个按钮没有图标；同一排有一个没图标，其余两个也要去掉。
* **改造范围**
    * > **结论**：区域列表部分需要改造的只有两处——第一，主键改为序号；第二，移除修改和删除按钮的图标。

### 列顺序调整

* **合作商列表的列序改动**
    * 复选框保留（批量删除用），主键 ID 改为序号，合作商名称不用调整。
    * 账号列要提到合作商名称的后面。
    * 联系人和联系电话要挪到最后，也就是分成比例的下方，注意是**剪切**过去不是复制。
    * 分成比例需要加百分号后缀。

* **百分号后缀靠插槽**

    ```vue
    <el-table-column label="分成比例" prop="percentRshell" width="120">
        <template #default="scope">
            {{ scope.row.percentRshell }}%
        </template>
    </el-table-column>
    ```

    * 做法：把该列由单标签改成双标签，添加模板插槽，用 `template` 增加 `default` 属性并设置 `scope` 作用域，通过插值表达式用 `scope` 取当前合作商行对象上的分成比例，尾部补百分号。
    * 实测效果：合作商 A 的分成比例显示 30%，合作商 B 显示 25%。

* **超长文本截断与对齐**

    ```html
    <el-table-column label="详细地址" prop="address" show-overflow-tooltip />
    ```

    * `show-overflow-tooltip` 把过长文本以省略号形式显示，鼠标移入表格可展示完整文本。
    * 页面默认每列数据居中展示，文本长短不一时观感差，给该列补 `align="left"` 改为左对齐。
    * > **易错点**：对前端不熟悉时压根想不到这个属性，可能改用 CSS 隐藏文本，整个操作过程太繁琐。

## 点位数统计：冗余字段还是实时统计

### 两种方案的对比

* **同步存储（冗余字段）**
    * > **定义**：在区域表新增 `node_count` 字段专门存点位数量，点位发生变动时顺手更新该字段。
    * 优点：单表查询，查区域列表的效率非常高。
    * 缺点：每次点位数据变动都要额外更新一次区域表，工作量翻倍；一旦更新操作有遗漏就会数据不一致——明明 4 个点位，统计出来可能是 3 个也可能是 5 个。

* **关联查询（association query）**
    * > **定义**：在 Mapper 层写 SQL，基于区域 ID 实时算出每个区域的点位数，把统计结果与区域表列表合并后输出返回前端。
    * 优点：数据的实时性和准确性有保证，实时算出来，不需要单独维护。
    * 缺点：SQL 涉及多表关联、语句比较复杂；如果点位数据量非常大，还有可能影响查询性能。

* **选型判定**
    * 考虑到区域和点位的数据量通常不会特别大，本案例选关联查询。
    * > **结论**：不是「关联查询更高级」，是「这个场景下它更合适」；选哪种取决于实际的数据量和业务需求。

    | 维度 | 方案一：同步存储 | 方案二：关联查询 |
    | :--- | :--- | :--- |
    | 做法 | 区域表加 `node_count` 冗余字段，点位变动时同步更新 | Mapper 里写 SQL，按区域 ID 实时统计，与区域数据合并返回 |
    | 优点 | 单表查询，查列表效率高 | 实时准确，不需要单独维护 |
    | 缺点 | 每次点位变动多更新一次；遗漏就数据不一致 | 多表关联语句复杂；点位数据量很大时可能影响查询性能 |
    | 本案例 | 不选 | 选它 |

### 传统模式手写 SQL：先聚合再左外连接

* **两步整体思路**

    ```text
    第 1 步：点位表按 region_id 分组统计
            tb_node ──GROUP BY region_id──> (region_id, node_count)
                                                        │
                                                        │ 把它当作"虚拟表" n
                                                        ▼
    第 2 步：区域表主体 r  ──LEFT JOIN──> n  ON r.id = n.region_id
            没有点位的区域也照样出来，只是 node_count 是 NULL
    ```

    * > **易错点**：内连接查的是两张表的**交集**，没有点位的区域会直接不展示；`tb_region` 是左侧主体，必须用**左外连接** `LEFT JOIN`。

* **第一步：按 region_id 分组统计**

    ```sql
    SELECT region_id, COUNT(*) AS node_count
    FROM tb_node
    GROUP BY region_id
    ```

    * 需求拆成三件事：要查哪张表 `tb_node`、按什么分组 `region_id`、分完组统计什么 `COUNT(*)`。
    * > **易错点**：`COUNT(*)` 见名不知意，普通用户哪知道它表示点位数，必须加别名 `AS node_count`。

* **第二步：虚拟表左外连接区域表**

    ```sql
    SELECT
        r.id,
        r.region_name,
        r.remark,
        IFNULL(n.node_count, 0) AS node_count
    FROM tb_region r
    LEFT JOIN (
        SELECT region_id, COUNT(*) AS node_count
        FROM tb_node
        GROUP BY region_id
    ) n ON r.id = n.region_id;
    ```

    * 查询主体是 `tb_region` 并取别名 `r`，聚合结果当虚拟表取别名 `n`，连接条件是 `r.id = n.region_id`。
    * 字段收敛时 `id`、`region_name`、`remark` 都属于区域表，只有点位数量来自虚拟表。
    * 没有点位的区域返回 `NULL` 不合适，该返回 0；MySQL 内置函数 `IFNULL` 就是干这个的，结果为 NULL 时给一个默认值 0。
    * > **易错点**：加了函数之后字段名就不见名知意了，所以还得补个别名 `AS node_count`。

### AI 辅助模式：一条语句走完

* **思路倒置**
    * AI 生成版本的思路是：先查区域表、左外连接查询点位表，拿到结果以后再根据区域 ID 进行分组，对分组后的数量做 `COUNT` 统计。

    ```text
    AI 版本：一条语句走完
    tb_region ──LEFT JOIN──> tb_node
                    │
                    └──> 按 region_id 分组 → COUNT(*) → 每个区域的点位数

    关键差别：分组发生在"连接之后"
    左外连接补出的那些没有点位的行，在按 region_id 分组时
    同样会进入 COUNT，于是天然拿到 0，不需要 IFNULL
    ```

* **两种写法的取舍**
    * 传统模式一步步推导效率低；AI 辅助编程只需把需求的 prompt 提示词写好，就能自动生成 SQL，调整一下就拿到最终结果。
    * 数据库客户端里要**右键新建一个窗口**再写提示词——当前窗口会学习刚写过的 SQL，生成结果和自己写的完全一样，等于在抄自己。

    | 维度 | 我们手写的两步 | 通义灵码生成的一步 |
    | :--- | :--- | :--- |
    | 结构 | 先聚合成虚拟表，再用虚拟表外连接区域表 | 直接区域表左外连接点位表，再按区域 ID 分组 |
    | 空值处理 | 没有点位的区域是 NULL，得用 `IFNULL` 兜底 | `COUNT` 在分组统计，不会出现空值 |
    | 阅读成本 | 子查询嵌套，多处别名限定，读起来费劲 | 一条平铺语句，一眼看懂 |

    * > **结论**：两种 SQL 都能用，别把它们当成「标准答案」和「错误答案」；真实项目里以能跑通、能读懂为准。

### GROUP BY 必须放在条件之后

* **语法位置**
    * 正确语法是**先做条件过滤，再做分组统计**——`WHERE` 查询条件在上，`GROUP BY` 分组放在最后。
    * 自己写的那条是先分组、后条件，有 `GROUP BY` 的时候还去写 `WHERE`，位置不对，直接语法报错。
    * 报错信息很难自己看出来，把 SQL 粘给 AI 助手问「有什么错」就能得到参考答案。

* **条件搜索与热部署**
    * 点搜索报 SQL 语法错误时，先对照 AI 给出的参考结构确认 `WHERE` 与 `GROUP BY` 的相对位置，再动手改造。
    * 若依项目提供热部署插件，**在没有新文件创建**的情况下直接按 `Ctrl + F9` 就能完成代码热更新，不需要重启项目。
    * > **结论**：企业开发中遇到未知问题，都可以交给 AI 辅助工具帮我们分析解决，从而提高开发效率。

## 后端四层：VO、Mapper、Service、Controller

### 完整调用链路

* **从数据库到前端**
    * 链路固定为七跳，改造区域和合作商时每一跳的位置都不变。

    ```text
    浏览器表格列 prop="nodeCount"
       │  GET /manage/region/list?regionName=xx
       ▼
    RegionController.list(Region)
       ▼
    IRegionService.selectRegionVoList(Region)
       ▼
    RegionMapper.selectRegionVoList(Region)
       ▼
    RegionMapper.xml   LEFT JOIN + GROUP BY + IFNULL
       ▼
    List<RegionVo>  →  getDataTable(list)
       ▼
    { total, code, msg, rows: [{ id, regionName, remark, nodeCount }] }
       ▼
    Element Plus 表格渲染
    ```

* **接口契约**
    * 分页返回对象是若依标准四件套：`total` 总记录数、`rows` 当前页结果集、`code` 状态码、`msg` 返回信息。
    * 区域列表请求路径 `/manage/region/list`，请求方式 GET，请求参数是 `pageNum` 当前页、`pageSize` 每页个数、`regionName` 搜索条件。
    * `rows` 中单条区域数据在 ID、名称、备注之外多一个 `node_count` 点位数量；只要把它返回给前端，Element Plus 表格就能直接显示。

### VO 继承实体类

* **区域列表 VO（RegionVo）**
    * > **定义**：映射数据库查询结果并返回给前端的值对象，统一放在 `domain` 包下的 `vo` 子包，命名统一叫 `XXXVo`。
    * 区域 ID、区域名称、备注说明三项 `Region` 实体已有，为简化操作 VO **直接继承 `Region`**，当前类只定义点位数量一个属性。

    ```java
    package com.itheima.manager.domain.vo;

    import com.itheima.manager.domain.Region;
    import lombok.Data;

    /**
     * 区域列表VO
     */
    @Data
    public class RegionVo extends Region {

        /**
         * 点位数
         */
        private Integer nodeCount;
    }
    ```

    * 属性名要用驼峰 `nodeCount`，不能沿用 AI 默认生成的 `pointCount`，因为 SQL 里是下划线别名 `node_count`；VO 用驼峰、SQL 用下划线，靠 MyBatis 的映射开关对接。
    * getter、setter、`toString`、有参无参构造方法由 `@Data` 注解自动生成，不必用 `Alt + Insert`；项目初始环境搭建时 common 模块下已引入 Lombok 坐标。
    * > **注意**：`Vo extends 实体类` 是一种务实取舍——省掉三个一模一样属性的重复声明，代价是 VO 会带上实体的全部字段；当前场景两者字段高度重合很划算，将来两个模型分家了再拆开也不迟。

* **合作商 VO（PartnerVO）**
    * 同样建在 `domain` 包下并继承 `Partner` 父类，只新增一个点位数量属性。

    ```java
    @Data
    public class PartnerVO extends Partner {

        /** 点位数量 */
        private Long nodeCount;

    }
    ```

    * > **易错点**：区域 VO 的点位数是 `Integer`，合作商 VO 的是 `Long`，两者类型不同，抄写时容易带错。

### Mapper 方法与命名

* **方法签名**
    * 在若依生成的五个增删改查常用方法基础上**增加一个新方法**，返回 `List<XXXVo>`。

    ```java
    /**
     * 查询区域列表
     *
     * @param region Region
     * @return RegionVo集合
     */
    public List<RegionVo> selectRegionVoList(Region region);
    ```

    * 命名规范：原有方法叫 `selectRegionList`，新增的叫 `selectRegionVoList`、合作商叫 `selectPartnerVOList`，多一个 Vo，一眼就知道返回的是 VO。
    * > **易错点**：查询条件用的还是原来的实体类，不是 VO；VO 是用来承载返回值的，不该拿来当查询入参。

* **开发工具辅助**
    * IDEA 的 **MyBatisX** 插件会自动校验方法有没有对应的 SQL 语句；校验之外，选中方法名按 `Alt + 回车` 还能直接生成 XML 的查询标签。

### XML 里的三件必记事项

* **一、最后一条 SQL 不能有分号**
    * 这里面包含分页查询，用的是 PageHelper 的分页插件，它会动态拼接 `LIMIT` 关键字；加了分号代码就会直接报错。
* **二、动态 SQL 要加表别名前缀**
    * 原有单表查询的 `where` 加 `if` 标签，判断 `regionName` 不为空且不为空串时做模糊匹配，直接 `Ctrl + C` 复制过来粘上。
    * 粘过来不能直接用：多表查询设置了别名，`region_name` 必须写成 `r.region_name`。
    * 合作商这条 SQL 里，若依原生的动态查询条件要原样搬到 **`group by` 之前**。
* **三、下划线转驼峰的开关必须打开**
    * SQL 里定义的别名是下划线 `node_count`，VO 里属性是驼峰式 `nodeCount`；若依默认把这个转换功能给**关掉了**，需要找到模块下的 MyBatis 配置文件把那行注释放开，不需要任何额外配置。
    * > **注意**：后端工程若不是跟着初始工程建起来的，这个开关千万别忘了打开，否则字段全是 null，还很难定位问题出在哪。

    ```xml
    <select id="selectRegionVoList" resultType="com.itheima.manager.domain.vo.RegionVo">
        SELECT r.id, r.region_name, r.remark, IFNULL(n.node_count, 0) AS node_count
        FROM tb_region r
        LEFT JOIN (
            SELECT region_id, COUNT(*) AS node_count
            FROM tb_node
            GROUP BY region_id
        ) n ON r.id = n.region_id
        <where>
            <if test="regionName != null and regionName != ''">
                AND r.region_name LIKE concat('%', #{regionName}, '%')
            </if>
        </where>
    </select>
    ```

### Service 与 Controller

* **Service 层**
    * 接口方法定义可以直接参考 Mapper 层——这样就节约时间，把 Mapper 层的方法签名直接复制过来即可。
    * 实现类的注释用 CV 大法从接口那边粘过来；方法体里调用 `regionMapper.selectRegionVoList(region)`，把条件原样扔过去。
    * Service 方法命名规范可以和 Mapper 保持一致；实现类里 `Alt + 回车` 创建出方法实现，复制一份 `PartnerMapper` 的写法即可。
* **Controller 层只改一处**
    * 原来查的是单表区域信息，现在改成调 VO 查询方法，把条件传进去，返回的是一个 `voList` 集合；再把这个 VO 集合交给 `getDataTable` 转成分页对象，返回前端。
* **后端原方法流程**
    * 原来的列表查询流程是：拿到参数先开启分页，然后调 service 按条件查，拿到一个 list 集合，再交给 `getDataTable` 封装成分页对象返回前端；里面的数据只有区域 ID、区域名称和继承 `BaseEntity` 的备注说明。

### 联调验证

* **F12 里多出来的 nodeCount**
    * 重启后端工程，打开 Network 点搜索查询，返回的结果当中已经包含了 `nodeCount` 属性。
    * 前端在区域名称下方再加一个表格列，列名「点位数」，`prop` 属性改为 `nodeCount`；没有点位的区域显示 0，符合预期。

## 一个对话框，两种形态

### v-if 判 id

* **共用一个对话框带来的问题**
    * 若依的新增和修改**用的是同一个对话框**，两者显示的内容完全相同。
    * 原型要求：修改合作商时通常不会去改账号和密码这两个字段，还需要额外展示合作商的创建时间。
    * 专门为修改合作商另定义一个新对话框完全可行，但实现起来相对麻烦；更简单的办法是用 Vue 的 `v-if` 指令做条件判断。

* **判定依据是 id**

    ```text
    点击"新增" → 表单里没有 id（没有回显数据）
    点击"修改" → 数据回显，表单里有 id

                  form.id 存在？
                  ┌────┴────┐
                 是           否
            修改状态         新增状态
                  │            │
        ┌─────────┴──────┐     │
        │                │     │
    隐藏账号、密码    显示账号、密码   显示创建时间
    ```

    * 规则就三条：id 不为空就是修改态，隐藏账号和密码、同时显示创建时间；id 为空就是新增态，账号密码显示、创建时间隐藏。

    ```vue
    <el-form-item label="账号" prop="username" v-if="form.id === undefined">
    <el-form-item label="密码" prop="password" v-if="form.id === undefined">
    <el-form-item label="创建时间" prop="createTime" v-if="form.id !== undefined">
        {{ form.createTime }}
    </el-form-item>
    ```

    * 创建时间以「联系电话」表单项为模板复制一份改名为「创建时间」，`prop` 属性改为 `createTime`（若依的通用字段）；下面不再包一层 `el-form-item`，因为时间不打算一起修改，直接用插值表达式输出。

## 密码安全与重置密码

### 明文入库必须加密

* **明文密码入库**
    * > **定义**：新增合作商时管理员输入的密码以明文形式保存在数据库当中。
    * 后果：数据库一旦遭受未授权访问，密码很容易被盗用，存在安全隐患，显然不是安全的保存方式。
    * 解法：加密，用若依内置的安全框架 Spring Security 处理，改造点在合作商业务层 `PartnerService` 的新增方法里。

    ```java
    // 使用spring security的工具类对前端传入的密码进行加密
    partner.setPassword(SecurityUtils.encryptPassword(partner.getPassword()));
    ```

    * 完整流程是：前端传过来的是明文 → 进行加密 → 再把加密后的结果复制回当前密码；这样再次保存到数据库时，密码字段就是密文了。

* **改造后的实测**
    * 新增合作商、密码同样输入 123456，点保存后回数据库刷新，最后一条记录的密码已经是加密后的密文。
    * > **结论**：通过这个简单改造，提高了系统的安全性，也避免了潜在的数据泄漏风险。

### 重置密码接口

* **需求与接口文档**
    * 需求是**作为管理员能够为每一个合作商重置密码，并且将初始密码统一设置为 123456**；若依框架并没有提供这一功能的现成代码，需要自己设计并实现。
    * 请求方式 **PUT**，请求路径 `/manager/partner/resetPwd/{id}`——`resetPwd` 是 password 的缩写 PWD；通过路径传递合作商的 id。
    * 请求成功后后端返回 `message`（返回内容）和 `code`（状态码），前端据此提示操作成功还是失败。
    * 前后端分离开发流程固定三步：查看原型确定需求 → 设计接口文档（前后端沟通的桥梁）→ 前后端分别开发并联调测试。

* **Controller 三步实现**

    ```java
    @PreAuthorize("@ss.hasPermi('bd:partner:edit')")
    @Log(title = "重置合作商密码", businessType = BusinessType.UPDATE)
    @PutMapping("/resetPwd/{id}")
    public AjaxResult resetPwd(@PathVariable Long id) {
        // 1. 接收请求参数
        //    即合作商id，路径变量已自动绑定

        // 2. 创建合作商对象，设置 id 和加密后的初始密码
        Partner partner = new Partner();
        partner.setId(id);
        partner.setPassword(SecurityUtils.encryptPassword("123456"));

        // 3. 调用 service 更新密码
        return toAjax(partnerService.update(partner));
    }
    ```

    * 实现细节只有三步：接收路径变量 id（路径变量已自动绑定）→ 新建合作商对象设置 id 和加密后的初始密码 → 调 service 以 id 为条件更新密码，返回结果交给 `toAjax` 转成 JSON 返回前端。
    * 请求路径前两层类上已经定义好，只写 `resetPwd/{id}`；方法名 `resetPwd`、返回类型 `AjaxResult` 参考之前已写的方法。
    * 上面两个注解别忘了：第一个做权限控制，第二个做日志记录；重置密码也是修改数据库的一种操作，完全可以参考之前的修改代码把这两行拿过来，只把日志描述改成「重置合作商密码」，其余保持一样。
    * > **易错点**：初始密码 `123456` **必须先加密再入库**，绝不能把明文密码直接写进数据库。
    * 之所以自动补出 `toAjax`，是因为它学习了其他方法——删除操作、修改操作也都是这么写的。

* **原型交互要求**
    * 点击「重置密码」弹出对话框询问是否确定要重置该合作商密码；点确定向后台发送请求完成重置，成功后前端提示操作完成的提示信息；点取消不做任何操作。

### 前端从删除按钮抄一份

* **删除按钮的四步流程**
    * 若依的删除按钮点下去同样会弹出对话框，点确定完成删除、点取消不做任何操作，这个效果和原型里「重置密码」非常相似，逻辑可以直接借鉴。

    ```text

            │
            ▼

            │
            ▼
     ElMessageBox.confirm(...)            ← 2. 弹出确认框（点击取消则到此为止，不做任何操作）
            │
            ▼
     .then(() => { 删除请求 })            ← 3. 点确定：向后端发送请求完成删除
            │
            ▼
     .then(() => {                        ← 4. 后端返回成功
         getList()                        ←    重新查询最新数据并刷新页面
         ElMessage.success('删除成功')      ←    再提示操作成功
     })
    ```

* **前端三步落地**
    * 第一步，把抽取好的方法名从 partner.js 引入到视图组件 JS 代码头部。
    * 第二步，以修改按钮为模板复制一份改名「重置密码」，指定方法名 `handleResetPwd`；重置密码按钮的权限和修改按钮是一样的。
    * 第三步，方法第一行取出合作商 id，直接复制删除那一行，只不过这里取出的是**单个 id**，所以 `row.id` 里的 `s` 要去掉；第二行把确认框那一部分整体粘过来。
    * `.then` 里面调抽取好的 API 方法 `resetPartnerPwd(id)`，这里的 id 同样没有 `s`。
    * > **易错点**：重置密码成功以后不涉及数据的新增操作，没必要再向后端发送一次查询请求，这个 `getList()` 必须删掉；提示信息也不再是「删除成功」，而是「重置密码成功」。
    * 确认框的提示信息直接抄页面原型里的原文，不另写。

* **API 方法**

    ```js
    /**
     * 重置合作商密码
     * @param {*} id
     */

      return request({
        url: '/manager/partner/resetPwd/' + id,
        method: 'put'
      })
    }
    ```

    * 接口方法传递的是 id 而不是请求体，所以参数不是 `data` 而是 `id`，同时把 `data` 删除。
    * 请求地址与接口文档保持一致，后面补上 id 用 `+` 拼接，通过**路径传参**；请求方式为 `put`。
    * > **易错点**：拼接 id 的时候少了一个路径的正斜杠，别忘了给它补上。
    * 收尾：调整「操作」这一列的宽度属性设为 300 像素，让重置密码、查看详情、修改、删除四个按钮与原型保持一致。

## 合作商列表点位数

* **复用现成方案**
    * 查询合作商列表时把每个合作商名下有几个点位一起显示；这个功能在**区域列表**里已经做过，方案不用重新想——关联查询。
    * 一条 SQL 把合作商表和点位表左连接起来，按合作商分组统计点位数量，在 Mapper 层执行 SQL，把结果封装进 VO 对象，前端就能直接展示。

    ```text
    浏览器（合作商列表页）
            │  GET /manager/partner/list?pageNum=1&pageSize=10&name=xx
            ▼
    PartnerController.list          ← 由「查单表」换成 selectPartnerVOList
            ▼
    PartnerServiceImpl              ← 命名与 Mapper 保持一致
            ▼
    PartnerMapper.selectPartnerVOList
            ▼
    PartnerMapper.xml               ← 合作商表 LEFT JOIN 点位表 + GROUP BY 合作商 id
            ▼
    List<PartnerVO>                  ← 父类字段（合作商全部信息） + nodeCount（点位数）
            ▼
    AjaxResult.rows → 前端表格多出「点位数」这一列
    ```

* **XML 与四层改造**

    ```sql
    select bd.*, count(td.id) as node_count
    from bd_partner bd
    left join td_node td on bd.id = td.partner_id
    <!-- 若依原生的动态查询条件，原样搬过来 -->
    group by bd.id
    ```

    * Controller 由查合作商单表数据换成 `partnerService.selectPartnerVOList`，把条件传过去，返回结果就是 VO List，将集合封装成分页对象返回给前端。
    * Service 接口把 Mapper 的方法连同注释一起复制过来，实现类 `Alt + 回车` 创建实现并调用 Mapper；VO 建在 `domain` 包下并继承 `Partner`，新增 `nodeCount` 属性。
    * > **易错点**：动态 SQL 条件必须粘在 **`group by` 之前**，位置放错会直接报错。

* **AI 生成不出来时的通用解法**
    * > **易错点**：课下练习时照抄这条提示词，这条 SQL **可能生成不出来**；因为写它的人此前手写传统模式 SQL 写得多了，AI 记录并学习过合作商表和点位表的表名字段信息，才给得出完整关联查询。
    * 通用方案是用**提示词工程**：在智能问答界面把**角色**、**指令**和**上下文**一起告诉它。

    ```text
    你是一个软件工程师。
    现在要根据数据库的 SQL 脚本，查询并显示合作商所有的字段信息，
    同时显示每个合作商上的点位数。
    SQL 脚本如下：
    <这里把合作商表、点位表的建表语句粘进来>
    ```

    * 上下文准备：把两张表的建表语句复制过来，点位表的粘一段换行，合作商表的再粘一段，它就能根据提示词生成 SQL。
    * > **结论**：本地没让大模型学习到你之前写过的 SQL 语句，就得先把上下文的信息喂给它去学习，然后它才能按需求生成需要的答案。
    * 它给出的返回字段只有合作商 id、合作商名称、点位数；前端要展示的合作商信息比较多，需要改成 `bd.*`，分组字段只需要按 id 分组。
    * 前端在合作商名称下方复制一份表格列，列名「点位数」，`prop` 改为 `nodeCount`；没有点位的合作商显示 0，条件搜索同样正常。

## 下拉框与全量数据源

### 复用分页接口查全量

* **把 id 文本框换成下拉框**
    * 若依生成的条件里区域是一个输入区域 id 的文本框，功能上完全能用——输入 id 点搜索返回的确实就是该区域的点位，但体验不够友好。
    * 管理员知道「1」是哪个区域吗？肯定是不知道的；管理员知道的是**区域的名称**——北京朝阳区、北京海淀区、北京北五环奥体中心等等。
    * 正确做法是提供下拉框展示所有区域信息，选中的是区域名称，**提交的是区域 id**；合作商 id 这个搜索条件原型没要求，直接删掉整个 `el-form-item`。
    * 区域搜索这一块的 label 不应是「区域 id」，应改为「**区域搜索**」。

* **复用区域分页接口**
    * `RegionController` 第一个方法就是查询区域列表，但它内部第一行通过 starter 配置开启了分页查询，接收当前页和每页个数，通过分页插件实现分页，返回的是**分页后的结果集**；其他方法就是若依生成的传统增删改查，并没有单独查询列表的方法。
    * 为这个需求再写一套后端查询方法会耗时耗力，办法是**调整前端的请求参数**来复用现有分页查询方法。

    ```text
    区域列表接口 /manager/region/list
      默认：pageNum=1, pageSize=10   → 只拿到前 10 条

      改：pageNum=1, pageSize=10000 → 一次性把区域全查回来
                                      后期区域数据不太可能超过 1 万条
                                      从第一页开始查就相当于查询所有数据
    ```

    * 后端把处理后的结果封装给分页对象，前端**单独取出里面的 `rows`** 遍历展示给用户。
    * 好处是提高了后端接口的复用性、减少了代码的编写量、提升了开发效率；后续改造就只需修改前端代码。

### ref 与 reactive 的选型

* **两种响应式定义**
    * > **定义**：`ref` 定义简单类型，`reactive` 定义对象类型。
    * 存两个参数（`pageNum`、`pageSize`）的条件对象不能用 `ref`，要改成 `reactive`；区域列表这种简单类型集合用 `ref` 即可。

    ```js
    // 查询所有的条件对象
    const loadAllParams = reactive({
      pageNum: 1,
      pageSize: 10000
    })

    // 区域列表，简单类型集合，用 ref 定义即可
    const regionList = ref([])
    ```

    * 返回的结果是一个**分页对象**，里面定义了 `rows`，所以要把分页结果集单独取出来封装给 `regionList`；AI 生成的多余小括号删掉就可以了。

* **定义查询方法**

    ```js
    import { listRegion } from '@/api/manager/region'

    /**
     * 查询区域列表
     */
    function getRegionList() {
      listRegion(loadAllParams).then((response) => {
        regionList.value = response.rows
      })
    }
    ```

    * `@` 就相当于项目的 `src`——从 src 下面找到 api，找到 manager，定位到 region 就可以了。
    * 调用位置：参考点位管理的分页查询，最后一行有个 `getList()` 方法，页面加载到那儿就会调用它向后台发送请求；**在这个方法的上一行**调用 `getRegionList()`，页面一加载完区域列表就查回来了。

### 抽取 loadAllParams

* **查全量参数复用**
    * > **提示**：`loadAllParams` 这个「查全量」的响应式对象在区域与合作商两个查询方法里都在用，其他视图组件也会需要；在每个视图页面都编写一次过于繁琐，这段代码可以单独抽取到 JS 文件中，哪一个视图页面想使用直接引入即可。

    ```js
    // src/api/config.js
    import { reactive } from 'vue'

    // 查询所有的条件对象
    export const loadAllParams = reactive({
      pageNum: 1,
      pageSize: 10000
    })
    ```

    * 在视图页面里只要通过 `import { loadAllParams } from '@/api/config'` 导入即可。

### 下拉框的属性组合

* **el-select 的三个属性**
    * `v-model` 做双向绑定；`placeholder` 做占位符提示，由「请输入区域 id」改为「请选择区域」——把 id 删除、把输入改为选择；`clearable` 用来清理搜索条件。

    ```html
    <el-form-item label="区域搜索" prop="regionId">
      <el-select v-model="queryParams.regionId" placeholder="请选择区域" clearable>
        <el-option
          v-for="item in regionList"
          :key="item.id"
          :label="item.regionName"
          :value="item.id"
        />
      </el-select>
    </el-form-item>
    ```

* **el-option 的四个属性**
    * `v-for` 遍历集合，遍历集合就是 `regionList`，元素记为 `item`；`:key` 用 `item.id` 作唯一标识。
    * `:label="item.regionName"` 用于展示下拉框显示的名称，`:value="item.id"` 是作为条件搜索提交的值。
    * > **易错点**：新增/修改对话框里的下拉框 **不需要 `clearable`**，因为它不是条件搜索部分，不需要做清除。
    * 合作商下拉框的改造思路和区域一模一样：先定义 JS 代码把结果封装给 `partnerList` 集合，再把文本框改为下拉框，遍历展示每个合作商的名称、提交时关联合作商的 id。

    ```js
    import { listPartner } from '@/api/manager/partner'

    /**
     * 查询合作商列表
     */
    function getPartnerList() {
      listPartner(loadAllParams).then((response) => {
        partnerList.value = response.rows
      })
    }

    const partnerList = ref([])
    ```

    * > **结论**：写这段代码的前提条件是**注释要写好**；注释写到位后，通义灵码完全学得会刚刚查区域列表的那一部分——调 `listPartner`、把查所有的条件定义过去、向后台发送请求、返回 `response` 分页对象、把 `rows` 单独定义给 `partnerList` 集合——效率就会翻倍。
    * `getPartnerList()` 的调用同样放在底部，和 `getRegionList()` 放一起；刷新后能看到两个查询一万条数据的请求。

## 改造清单

### 区域列表显示点位数六步

* **六步顺序**
    * 1. 确定关联查询方案并编写 SQL；先用传统模式一步步分析构建，再用 AI 辅助工具结合提示词动态生成 SQL，再优化调整拿到最终结果。
    * 2. 创建 `RegionVo` 映射数据库返回的结果，最终才能在前端显示点位数。
    * 3. 在 `RegionMapper` 和 XML 中添加查询 VO 的方法和 SQL；记住最后不能加分号——底层用了 PageHelper 分页插件会动态拼接 `LIMIT`，加分号代码就报错；动态 SQL 和 `GROUP BY` 的语法错误交给 AI 辅助工具分析解决。
    * 4. 在 `RegionService` 接口定义方法签名，在实现类中调用 Mapper 查询即可。
    * 5. 修改 `RegionController` 查询方法，由单表查询改为区域加点位的 VO 查询，并把结果封装成分页对象返回前端。
    * 6. 修改前端视图组件，展示点位数。

### 合作商查看详情四步

* **四步顺序**
    * 1. 添加查看详情按钮，在按钮中定义方法 `getPartnerInfo`，它的作用是向后台发送请求。
    * 2. 定义这个方法：根据 id 向后台发送请求，拿到合作商详情，封装给表单对象。
    * 3. 定义一个对话框来展示合作商详情内容，基础布局展示用 `el-row` 栅格布局系统做简单排布。
    * 4. 用通义灵码对内容布局样式完成美化。

### 合作商改造四部分

* **整体划分**
    * 基础布局展示的改造（以及新增时用 Spring Security 对密码加密）、查看详情、查询合作商列表（与区域列表类似，通过 AI 工具生成关联查询的 SQL，定义 VO 编写代码并返回结果）、重置密码。
