# 工单管理全流程改造

## 业务场景与工单分类

### 运营工单与运维工单

* **运营工单**

    * > **定义**：管理员依据售货机库存创建，指派运营人员去维护货道内商品以实现补货的工单。

    * 触发条件是库存到达补货警戒线，运营人员在 App 端接受后可完成补货任务。

* **运维工单**

    * > **定义**：管理员指派运维人员进行售货机设备维护的工单，包含投放、维修、撤机三类子任务。

    * 投放工单即投放新设备，也叫装机工单；撤机工单即撤出旧设备。

* **工单类型编号 `product_type_id`**

    * 投放 `1`、补货 `2`、维修 `3`、撤机 `4`，常量分别落在 `DkTaskType.DEPLOY`、`RESTOCK`、`REPAIR`、`REMOVE`。

    * 运营工单界面新增时只有补货一种类型可选，运维工单界面新增时可选投放、维修、撤机三种。

* **App 端按角色渲染两套界面**

    * 同一套接受、拒绝、取消、查看详情的交互动作，界面内容完全由登录角色决定。

    * 后台因此要把工单管理拆成运营工单与运维工单两个入口菜单，而不是一个列表页。

### 建单三要素

* **建单三要素**

    * > **结论**：哪个设备（区域 + 地址）、什么类型、派谁去，三者缺一不可。

    * 区域这一层不是可有可无的，它是把设备与人力对上号的那道桥。

    * 人员选择从设备所在区域下面的工作人员里挑，区域与工作人员的划分功能此前已完成，此处直接查询复用。

## 工单状态与流转

### 四种状态取值

| 状态 | 字典值 | 含义 |
| :--- | :--- | :--- |
| 待处理 | 1 | 管理员刚创建出来，还没有派人接 |
| 已接收 | 2 | 也称进行中，工作人员已经接单 |
| 已取消 | 3 | 工作人员拒绝，或接单后遇到无法完成的突发情况而取消 |
| 已完成 | 4 | 任务执行完毕，工作人员点击已完成 |

* **状态回退路径**

    * 已取消之后由管理人员重新创建工单、指派新的工作人员，确保任务最终完成。

    * > **易错点**：已取消不是一个死胡同。它不是「任务失败」的终态，而是一个可以回炉重来、重新派单的中间状态——因为流程的终点只有「已完成」。

* **状态流转示意**

    ```text
      待处理(1)
          │
          ├── 拒绝 ──────────────────────────────┐
          │                                        ▼
          └── 接受 ──▶ 进行中(2) ──┬── 任务完成 ──▶ 已完成(4)
                                  │
                                  └── 遇到突发事件无法完成 ──▶ 已取消(3)
                                                                    │
                                                                    ▼
                                              管理员重新创建工单，指派新工作人员
    ```

* **角色与可见工单的对应**

    * 运营人员登录 App 看到的是补货工单，运维人员看到的是投放、维修、撤机工单。

## 数据模型

### 工单表 `task`

* **主键与编号**

    * `task_id` 主键自增，是工单的唯一标识，修改与删除都以它为条件。

    * `task_code` 是带业务规则的工单编号，格式为「年 + 月 + 日 + 当日四位序号」，每天从 `0001` 重新开始，见名知意，便于按日期检索某天的全部工单。

* **状态与创建类型**

    * `task_status` 取值 `1` 待办、`2` 进行中、`3` 取消、`4` 完成。

    * `create_type` 取值 `0` 自动、`1` 手动。

    * 两个字段属于静态数据，都可做成数据字典，用它把界面中文与数据库数字对上号。

* **设备相关字段**

    * `inner_code` 售货机编码，通过它获取设备所在区域、点位等信息，便于工作人员定位。

    * `addr` 这台设备的地址，执行人员据此找到设备完成任务。

    * `region_id` 所属区域 id，冗余存下来后可直接查出该区域的服务人员，为工单分配提供精准定位依据。

* **人员相关字段**

    * `user_id` 与 `user_name` 是执行人员，对应员工表的 id 与名称，人员可能是运营人员也可能是运维人员。

    * `assigner_id` 是指派人 id，即创建这张工单的后台管理人员。

    * > **易错点**：`assigner_id` 与 `user_id` 必须分清楚。一个是派活的人（可比作包工头），一个是干活的人（包工头的小弟），两者在工单表里是独立字段，填反了业务全乱。

* **其余字段**

    * `remark` 备注，新增工单时指定，例如「这是一个加急工单，请在 12 点之前务必完成」。

    * `create_time` 创建时间与 `update_time` 更新时间。

* **自动工单示例**

    * 北京奥体中心的售货机某货道原存 10 件商品，剩 4 件时到达货道设置的库存警戒线，系统自动触发创建补货工单并分配工作人员。

### 工单补货详情表 `t_task_details`

* **归属与定位**

    * `detail_id` 主键自增，`task_id` 是外键，指明这条补货详情属于哪张工单。

    * 货道编号形如 `1-1`、`1-2`、`1-3`、`1-4`，标明是哪一个货道需要补货。

* **补货期望的容量**

    * 货道表本身有当前容量与最大容量两个字段，两者相减就是还能再添加多少容量。

    * $$\text{补货数量上限} = \text{最大容量} - \text{当前容量}$$

    * 当前容量 `5`、最大容量 `10` 时，补满数量的可填范围是 `1` 到 `5`，最少补一件，最多为补满，不能超过最大容量。

    * > **提示**：可补数量由前端根据设备或货道返回的最大容量与当前容量算出，右侧输入的数量保存到补货期望的容量里，由运营人员按数补货。

* **商品快照字段**

    * 当前货道关联的商品 id、商品名称、商品图片。有了这些字段，工作人员可以在 App 中查看补货清单、备齐商品、找到设备完成补货并同步更新数据库。

### 工单类型表 `task_type`

* **字段含义**

    * `type_name` 是类型名称，界面选择后前端提交的是 `type_id`。

    * `type` 字段区分业务归属：`1` 表示运维相关工单，`2` 表示运营相关工单。

* **统计口径**

    * 统计运营工单数量的条件是 `type = 2`，统计运维工单数量的条件是 `type = 1`。

### 自动补货任务表

* **警戒线配置**

    * 入口在运营工单页面的「工单配置」按钮弹出的对话框中，配置项是补货的警戒线，取值是百分比，例如填 `50%`。

* **执行机制**

    * 每天凌晨系统自动扫描所有售货机，货道容量到达警戒线后自动创建补货工单并交给工作人员。

* **可动态调节**

    * 警戒线可以在前端调整为 `60%` 或 `40%`，从而动态调整补货频率。

* **关联关系**

    * 这张表与工单表、工单补货详情表、工单类型表均无直接关联。

### 表间关系

* **一对多关系**

    * 工单类型表与工单表是一对多，创建工单时选择指定类型，以区分任务到底是投放、补货还是维修、撤机。

    * 工单表与工单补货详情表是一对多，通过 `task_id` 可查该工单各货道的补货信息、商品 id 与需要补的数量。

    * 只有补货工单才会有详情，投放、维修、撤机工单不存在补货详情数据。

* **工单表的外键指向**

    * `inner_code` 指向设备表：每个工单都服务于某一台具体设备。

    * `user_id` 指向员工表：知道是哪个工作人员在执行。

    * `region_id` 指向区域与员工的关联：新增工单时据此查出该区域的工作人员列表供指派。

    * `assigner_id` 指向管理端用户：即帝可得的后台管理人员。

    ```text
                          工单类型表 task_type
                                  │ 一对多
                                  ▼
       设备表 ◄── inner_code ──  工单表 task
                                    │ 一对多
                                    ▼
                          工单补货详情表 task_detail

       工单表 task ── user_id ────▶ 员工表（执行人：运营/运维人员）
       工单表 task ── region_id ──▶ 区域与员工的关联（查该区域的工作人员）
       工单表 task ── assigner_id ▶ 管理端用户（指派人：创建工单的人）

       自动补货任务表：与上面三张表均无直接关联
    ```

### desc 保留关键字冲突

* **故障现象**

    * 生成代码后点开运营工单页面即报 SQL 语法错误，错误位置落在 `desc`。

* **成因**

    * `desc` 是 MySQL 的保留关键字，用于排序表示降序。

    * 工单表里的 `desc` 是备注说明字段，被放在 `select` 字段列表后方，MySQL 不认它是普通列。

* **修复方式**

    * 给这个保留关键字加英文半角反引号，使它变回普通字段名，字段颜色随即与其他列一致。

    ```sql
    -- 报错的写法
    SELECT task_id, task_code, desc FROM task

    -- 加反引号之后
    SELECT task_id, task_code, `desc` FROM task
    ```

* **改造范围**

    * 动态 SQL 的判断条件里还有 `desc`，其他 SQL 片段中也有，都需要加反引号。

    * > **注意**：替换完源码中的 `TaskMapper.xml` 后，`target`（编译后的运行环境）目录下也有一份 mapper，需要手动再复制一份，否则刷新浏览器会报查询语句 XML `not found`。

## 查询工单列表改造

### 现象与改造目标

* **原始现象**

    * 运维工单页面与运营工单页面展示的数据完全一样，因为两个页面共用同一套工单管理后端接口，接口不区分类型。

* **改造目标**

    * 运营工单页面只展示补货工单列表，运维工单页面展示投放、维修、撤机工单列表。

    * 每条工单回显时还要带上工单类型名称。

    * > **结论**：本轮改造的核心不是新写接口，而是把已有的 `/manager/task/list` 改造成「一个接口、按参数返回不同结果」。

### 接口约定与 isRepair 开关

* **接口信息**

    * 请求路径 `/manager/task/list`，请求方式 GET，返回标准分页对象，`total` 是总记录数，`rows` 是结果集。

* **参数分成两类**

    * 分页参数 `pageNum`、`pageSize` 前端必传，由框架的 `startPage()` 处理。

    * 搜索条件 `taskCode`（工单编码）、`taskStatus`（工单状态）、`productTypeId`（工单类型）非必需，不传则默认查全部。

* **两类页面的搜索条件差异**

    | 页面 | 搜索条件 |
    | :--- | :--- |
    | 运营工单 | `taskCode`、`taskStatus` |
    | 运维工单 | `taskCode`、`taskStatus`、`productTypeId` |

* **隐藏开关 `params.isRepair`**

    * 它不出现在普通参数列表里，而是藏在 `params` 后面；传 `true` 查运维工单数据，传 `false` 查运营工单数据。

    * 抓包验证方式：F12 的 Network 刷新运维工单页面，搜索条件串末尾跟着 `isRepair` 且值为 `true`；切到运营工单页面，值变成 `false`。

    * > **易错点**：`true` 查运维、`false` 查运营，千万别写反了。

### 参数接收方式

* **复用 `Task` 实体类接收**

    * 不必另造 DTO：`Task` 中已经有 `taskCode`、`taskStatus`、`productTypeId` 三个属性，与搜索条件一一对应。

    * `params.isRepair` 靠继承链拿到——所有实体类都继承自基类 `BaseEntity`，基类里有一个 `params` 属性。

* **`params` 的作用**

    * 它是一个 Map，专门用来接收前端请求参数，因为前端传来的参数命名格式可能与实体属性名不一致。

    * 前端用 `params[xxx]=yyy` 传，后端就以 `params.get("xxx")` 拿，中间不经过任何属性名映射约束。

    ```text
    前端请求：/manager/task/list
              ?pageNum=1&pageSize=10
              &taskCode=&taskStatus=&productTypeId=
              &params[isRepair]=true

      pageNum / pageSize  --->  startPage() 读走做自动分页，后端不接收
      taskCode            --->  Task.taskCode
      taskStatus          --->  Task.taskStatus
      productTypeId       --->  Task.productTypeId
      params[isRepair]    --->  BaseEntity.params 里的 key "isRepair"
    ```

### TaskVo 与结果映射

* **`TaskVo` 的定义**

    * 继承 `Task` 直接拿到父类工单属性，再自己增加一个工单类型对象属性 `taskType`，类上加 `@Data`。

    ```java
    @Data
    public class TaskVo extends Task {
        /**
         * 工单类型
         */
        private TaskType taskType;
    }
    ```

* **Mapper 方法**

    * 在 `TaskMapper` 最下方新增 `List<TaskVo> selectTaskVoList(Task task)`，鼠标悬停后 `Alt` + 回车选 `Generate Statement`，IDEA 会在同名 XML 中生成标签。

    * 标签内的 SQL 可直接复制若依已生成的「查询工单列表」那段，`include` 是公共 SQL，`<where>` 内是搜索条件，已包含 `taskCode`、`taskStatus`、`productTypeId`，只剩 `params.isRepair` 需要手写。

* **动态条件写法**

    ```xml
    <where>
        <!-- 从若一已生成的查询工单列表复制来的条件，已包含 taskCode / taskStatus / productTypeId -->
        <if test="params.isRepair != null and params.isRepair == 'true'">
            and product_type_id in (1, 3, 4)
        </if>
        <if test="params.isRepair != null and params.isRepair == 'false'">
            and product_type_id = 2
        </if>
    </where>
    ```

    * 运维侧要匹配投放、维修、撤机三个类型，等号不够用，换成 `in`；运营侧只有补货一个类型，把 `in` 换成等号即可。

    * 三个必须抠的细节：`params` 是 Map，key 就是 `isRepair`，所以后面跟点号写 `params.isRepair`；先判 `params.isRepair != null` 再进第二层条件。
      > **易错点**：判断值必须带单引号，因为走的是 HTTP 1.1，GET 请求传的都是字符串，判的是字符串 `"true"` 而不是布尔 `true`。

* **`resultMap` 手工映射**

    * 以若依生成的 `resultMap` 为模板复制一份，`id` 改为 `taskVoResult`，返回类型改为 `TaskVo`。

    * 用 `<association>` 嵌套关联查询工单类型：属性 `property` 写 `taskType`，关联列 `column` 写 `product_type_id`，`select` 填工单类型 Mapper 中按主键查询的方法全限定名 `com.dkd.mapper.TaskTypeMapper.selectTaskTypeById`，粘完要回头核对包名、类名、方法名三处。

    ```xml
    <resultMap id="taskVoResult" type="TaskVo">
        <!-- 若一原本生成的工单字段映射，保持不动 -->
        <id property="id" column="id"/>
        <result property="taskCode" column="task_code"/>
        <result property="taskStatus" column="task_status"/>
        ...

        <!-- 新增：按 product_type_id 嵌套关联查询工单类型 -->
        <association property="taskType" column="product_type_id"
                     select="com.dkd.mapper.TaskTypeById.selectTaskTypeById"/>
    </resultMap>
    ```

    * 最后把 select 标签上的 `resultType` 属性删掉，换成 `resultMap="taskVoResult"`。

* **排序**

    * 在 `where` 下面加 `order by create_time desc`，工单按创建时间降序展示，最新创建的排在第一条。

### 调用链与易错

* **Service 与 Controller**

    * Service 接口底部补上方法签名与注释，`Alt` + 回车选 `Implement Method` 生成实现，内部直接调 Mapper 同名方法。

    * Controller 保留若依原有的权限注解与 `startPage()`，把原来那行查询换成调用 service 取 `TaskVo` 集合，再用 `getDataTable` 转换成分页对象返回。

    ```java
    @GetMapping("/list")
    @PreAuthorize("@ss.hasPermi('manager:task:list')")
    public TableDataInfo selectTaskList(Task task)
    {
        startPage();
        List<TaskVo> voList = taskService.selectTaskVoList(task);
        return getDataTable(voList);
    }
    ```

* **整条链路**

    ```text
    Controller  selectTaskList(Task task)
        │  startPage()  ->  pageNum / pageSize 自动分页
        ▼
    Service     selectTaskVoList(task)
        ▼
    Mapper      selectTaskVoList(task)
        │  动态条件：params.isRepair
        │     'true'  ->  product_type_id in (1, 3, 4)
        │     'false' ->  product_type_id = 2
        ▼
    resultMap   taskVoResult  --association-->  taskType（按 product_type_id 查类型）
    ```

* > **易错点**：复制若依的 `where` 片段时，它内部的每个条件都自带 `and`；而手写的新增条件，`and` 要自己负责。两批条件混在同一个 `where` 里时极易漏，漏掉后输入工单编号做条件查询就会报 SQL 语法错误。

## 按售货机编号获取人员列表

### 两个接口的约定

* **触发场景**

    * 管理员在运营工单页面点「新增工单」，输入售货机编号并失焦后，系统动态做两件事：查出这台设备的补货清单，查出负责当前区域的运营人员列表。

    * 补货清单直接复用设备管理模块已实现的「根据售货机编号查询货道列表」接口，能拿到货道编号、名称、当前数量、剩余可添加数量和补满数量。

* **接口形态**

    * 运营人员：`GET /manager/emp/business/{innerCode}`，路径参数是设备编号，返回标准 `AjaxResult`，`data` 是运营人员列表数组。

    * 运维人员：`GET /manager/emp/operation/{innerCode}`，路径参数同样是设备编号，返回符合条件的运维人员列表。

### 两表查询与筛选公式

* **业务链路要串四张表**

    ```text
    按业务关系看：

        设备（售货机）
            │
            │ 投放在
            ▼
          点位
            │
            │ 属于
            ▼
          区域 ──────────► 关联工作人员

        这条链路走下去 = 设备表、点位表、区域表、员工表，四张表
    ```

* **实际只需两张表**

    * 关键在设备表里冗余存了 `regionId`（这台设备所属的区域 id），这是反三范式设计带来的收益。

    ```text
    实际查询只要：

        innerCode  --->  设备表  --->  region_id
                                            │
                                            ▼
                         员工表 where region_id = ? and role_code = ? and status = ?
    ```

    * 第一步按 `innerCode` 查设备表拿到 `regionId`，第二步用 `regionId` 去查负责该区域的员工列表。

* **人员筛选三条件**

    | 条件 | 含义 | 运营人员取值 | 运维人员取值 |
    | :--- | :--- | :--- | :--- |
    | `regionId` | 设备所属区域 | `vendingMachine.getRegionId()` | 同左 |
    | `roleCode` | 角色编码 | `1002` 运营员 | `1003` 维修员 |
    | `status` | 员工状态 | `1` 启用 | `1` 启用 |

    * 光有区域不够，负责该区域的员工有运营的有维修的，在运营工单界面把维修人员也列出来不合适，所以必须加角色编号；员工还必须处于启用（正常上班）状态。

### 设备层查询

* **Mapper 层的注解 SQL**

    * 方法名 `selectByInnerCode`，参数 `String innerCode`，返回售货机对象，对象里自然带着该设备所属的区域 id。

    ```java
    /**
     * 根据设备编号查询设备信息
     *
     * @param innerCode 售货机编号
     * @return 售货机对象
     */
    @Select("select * from t_vending_machine where inner_code = #{innerCode}")
    VendingMachine selectByInnerCode(String innerCode);
    ```

    * 表名较长不要手写，回数据库客户端复制表名粘过来。

* **Service 层**

    * 把 Mapper 的方法签名复制过去，**去掉 `@Select` 注解**（这一层不碰数据库），实现里直接调 Mapper 并把 `innerCode` 传过去。

### 员工 Controller 的三步实现

* **架子**

    * 路径 `/manager/emp` 类上已声明，方法上只写 `/business/{innerCode}` 或 `/operation/{innerCode}`，占位符内容为 `innerCode`。

    * 返回值是标准 `AjaxResult`，方法名分别为 `businessList`、`operationList`。

    * 权限注解直接复制若依生成的「查询人员列表」注解 `manager:emp:list`，不需要 `@Log` 日志记录，中文注释按若依风格把 `@param`、`@return` 删掉。

    * 因为要调设备 Service，需先在 Controller 中 `@Autowired` 注入设备 Service。

* **第一步：查设备信息**

    ```java
    // 1. 根据 innerCode 查询售货机信息，获取设备所属区域id
    VendingMachine vendingMachine = vendingMachineService.selectByInnerCode(innerCode);
    ```

* **第二步：判空返回提示**

    ```java
    if (vendingMachine == null) {
        return error("售货机不存在");
    }
    ```

    * 前端可能传一个不存在的设备编号，拿不到设备对象再调 `vm.getRegionId()` 会抛空指针，体验很差，所以中间必须插判断。

    * `error` 由 `BaseController` 提供，底层走 `AjaxResult.error()`，括号里可以传一句精准的提示文案。

* **第三步：封装条件查人**

    ```java
    // 2. 根据区域id、角色编码以及员工状态查询运营人员列表
    Emp emp = new Emp();
    // 设备所属区域id
    emp.setRegionId(vendingMachine.getRegionId());
    // 角色编码：运营员
    emp.setRoleCode(DkConstant.ROLE_CODE_BUSINESS);
    // 员工状态：启用
    emp.setStatus(DkConstant.EMP_STATUS_NORMAL);

    return success(empService.selectEmpList(emp));
    ```

    * `empService.selectEmpList` 是若依已生成的按条件查员工集合的方法，直接调用并 `success` 返回。

    * 运维人员方法步骤完全一致，只有角色编码换成 `DkConstant.ROLE_CODE_OPERATOR`，Mapper 层与 Service 层复用「按设备编号查售货机信息」即可。

### 常量类 DkConstant

* **常量清单**

    ```java
    public interface DkConstant {
        /** 运营员 */
        Long ROLE_CODE_BUSINESS = 1002L;

        /** 维修员 */
        Long ROLE_CODE_OPERATOR = 1003L;

        /** 员工启用 */
        Long EMP_STATUS_NORMAL = 1L;

        /** 员工停用 */
        Long EMP_STATUS_STOP = 0L;
    }
    ```

    * 代码里直接写 `1002` 可读性太差，半年后没人看得懂这个数字是谁，因此提前放进常量类做到见名知意。

    * 员工启用与停用的常量原先写成了布尔类型，现统一改为 `Long`，启用值 `1`、停用值 `0`。

* **实测效果**

    * 复制第三台设备的编号进新增工单框，运营人员一栏展示曹操和夏侯惇；换成第一台设备的编号，展示孙权；输入不存在的设备编号，页面直接提示「售货机不存在」。

## 新增工单接口

### 一个接口承载两类业务

* **共享设计**

    * 新增工单接口被运维工单与运营工单共享，目的是提高代码复用性。

* **两类工单操作对象不同**

    * 运维工单动的是售货机本身：投放用于新设备投放，撤机用于设备撤回，维修用于设备维修。

    * 运营工单动的是售货机里的货，目前关注补货工单，且提交时还要额外带补货详情——一台售货机有好几个货道，一条补货工单可能对应好几条货道。

    ```text
                          新增工单（一个接口）
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                运维工单                      运营工单
             操作的是售货机本身            操作的是售货机里的货
                    │                           │
              ┌─────┼─────┐              ┌─────────┴─────────┐
             投放   维修   撤机           补货（本阶段关注）
                                            │
                                      还要带补货详情
                                   （货道 → 商品 → 数量）
    ```

* **接口形态天然是「主单 + 明细」**

    * 请求路径 `manager/task`，请求方式 POST，参数为 JSON，返回标准 `AjaxResult`，业务状态码 `200`，提示「操作成功」。

### 请求参数与两个 DTO

* **参数一览**

    | 参数 | 含义 | 谁来给 |
    | :--- | :--- | :--- |
    | `createType` | 工单创建类型 | 前端写死传 `1` |
    | `innerCode` | 工单所服务的设备编号 | 前端，靠它反查设备信息 |
    | `userId` | 执行人 id | 前端选中的干活的人 |
    | `assignerId` | 指派人 id | 前端标记为非必需，后端取当前登录人 |
    | `productTypeId` | 工单类型 | 投放/维修/撤机是运维，补货是运营 |
    | `desc` | 工单描述信息 | 前端界面上的备注说明 |
    | `details` | 补货详情集合 | 只有补货工单才有 |

* **两个必须拎出来的点**

    * `createType` 固定为 `1`，因为在后台管理系统里点「新增」创建出来的永远是手动创建的单子。

    * `assignerId` 前端不给，就在后端取当前登录人的 id 补上——登录人就是工单的创建人、派活的人。

* **补货详情集合的元素**

    | 字段 | 类型 | 含义 |
    | :--- | :--- | :--- |
    | `skuCode` | `String` | 货道编号 |
    | `expectCapacity` | `Long` | 补货数量 |
    | `skuId` | `Long` | 商品 id |
    | `skuName` | `String` | 商品名称 |
    | `skuImage` | `String` | 商品图片 |

    * `skuId` 与 `skuImage` 在前端界面上并不显示，但后端需要，所以一并提交。

* **为什么需要 DTO**

    * 一次新增涉及工单表与工单详情表两张表的数据，一个实体类装不下，必须设计专门接收前端参数的 DTO。

* **`TaskDetailsDto` 与 `TaskDto`**

    ```java
    @Data
    public class TaskDetailsDto {
        /** 货道编号 */
        private String skuCode;
        /** 补货数量 */
        private Long expectCapacity;
        /** 商品 id */
        private Long skuId;
        /** 商品名称 */
        private String skuName;
        /** 商品图片 */
        private String skuImage;
    }
    ```

    ```java
    @Data
    public class TaskDto {
        /** 创建类型 */
        private Long createType;
        /** 设备编号 */
        private String innerCode;
        /** 执行人 id */
        private Long userId;
        /** 指派人 id */
        private Long assignerId;
        /** 工单类型 */
        private Long productTypeId;
        /** 描述信息 */
        private String desc;
        /** 工单详情（只有补货工单才有这个集合） */
        private List<TaskDetailsDto> details;
    }
    ```

    ```text
    TaskDto  （整体提交数据）
      ├─ createType / innerCode / userId / assignerId
      ├─ productTypeId / desc
      └─ details : List<TaskDetailsDto>
            ├─ [0] skuCode / expectCapacity / skuId / skuName / skuImage
            ├─ [1] skuCode / expectCapacity / skuId / skuName / skuImage
            └─ [n] ……（有几条货道就几条）
    ```

* > **提示**：写完字段注释后，AI 补全工具能顺着注释生成关键字、类型与变量名——`skuName` 这一行一次到位，`skuImage` 只给对了关键字和类型，变量名要自己改成 `skuImage`。

### 批量新增工单详情

* **批量插入 SQL**

    * 把单个新增的 XML 标签复制一份交给 AI 改成批量插入，第一次生成的结果还带动态 `<if>` 判断，说明不需要后再生成一次，得到的是 `insert into` 直接指定字段名加 `<foreach>` 遍历多个值。

    ```xml
    <insert id="batchInsertTaskDetails" parameterType="java.util.List">
        insert into t_task_details (sku_code, sku_id, sku_name, sku_image, expect_capacity)
        values
        <foreach collection="list" item="item" separator=",">
            (#{item.skuCode}, #{item.skuId}, #{item.skuName}, #{item.skuImage}, #{item.expectCapacity})
        </foreach>
    </insert>
    ```

* **Mapper 方法**

    * 放在接口最下方，返回值 `int`，参数是泛型为 `TaskDetailsDto` 的 `List` 集合。

    ```java
    /**
     * 批量新增工单详情
     * @param taskDetailsList 工单详情集合
     * @return 影响行数
     */
    int batchInsertTaskDetails(List<TaskDetailsDto> taskDetailsList);
    ```

* **为什么 Mapper 之上还要罩一层 Service**

    * 目的是业务层与持久层实现责任分离，同时便于在业务层控制事务传播行为，提高可维护性。

    * 建议不同模块之间的业务调用走 Service 层之间的调用；业务简单时直接调 Mapper 也可以。

    ```java
    /**
     * 批量新增工单详情
     */
    @Override
    public int batchInsertTaskDetails(List<TaskDetailsDto> taskDetailsList) {
        return taskDetailsMapper.batchInsertTaskDetails(taskDetailsList);
    }
    ```

### 八步核心业务

* **方法签名**

    ```java
    /**
     * 新增运营和运维工单
     * @param taskDto 工单数据
     * @return 影响行数
     */
    @Transactional
    public int insertTask(TaskDto taskDto) { ... }
    ```

* **整体流程**

    ```text
    TaskDto
      │
      ├─1 设备存在？ ──── 不存在 ──▶ ✗ 抛异常
      ├─2 设备状态配得上工单类型？ ─ 不配 ──▶ ✗ 抛异常
      ├─3 该设备有"未完成的同类型工单"？ ─ 有 ──▶ ✗ 抛异常
      ├─4 执行人存在？ ──── 不存在 ──▶ ✗ 抛异常
      ├─5 执行人区域 == 设备区域？ ──── 不等 ──▶ ✗ 抛异常
      │
      ├─6 DTO→PO，补齐属性 → insert 工单表
      │
      ├─7 是补货工单？ ──── 否 ──▶ 方法结束
      │
      └─8 DTO→PO，补 taskId → 批量 insert 工单详情表
                    （整个方法 @Transactional，涉及两张表）
    ```

* **第一步：校验设备存在**

    ```java
    @Autowired
    private DkDeviceService deviceService;

    // 1.查询售货机是否存在
    DkDevice vm = deviceService.selectDeviceByInnerCode(taskDto.getInnerCode());
    if (vm == null) {
        throw new ServiceException("设备不存在");
    }
    ```

    * 售货机都不存在了，后续工单业务没有创建的必要，必须先拦下来抛异常做友情提示。

* **第二步：设备状态必须与工单类型对得上**

    | 工单类型 | 常量 | 值 | 对设备状态的要求 |
    | :--- | :--- | :--- | :--- |
    | 投放 | `DkTaskType.DEPLOY` | 1 | 设备不能在运行中 |
    | 补货 | `DkTaskType.RESTOCK` | 2 | 设备必须在运行中 |
    | 维修 | `DkTaskType.REPAIR` | 3 | 设备必须在运行中 |
    | 撤机 | `DkTaskType.REMOVE` | 4 | 设备必须在运行中 |

    * 投放工单遇「运行中」说明设备已被投放过，不能二次投放；维修、补货、撤机三类的逻辑前提都是设备已在运营中，设备没投放或已撤机时都不成立。

    * 四段判断内容太多，全写在一个方法里不优雅也不利于扩展维护，因此单独抽出一个无返回值、接收设备状态与工单类型两个参数的方法。

    ```java
    /**
     * 校验售货机的状态与工单类型是否相符
     * @param vmStatus 设备的状态
     * @param productTypeId 工单的类型
     */
    private void checkCreateTask(Long vmStatus, Long productTypeId) {
        // 如果是投放工单，设备在运行中，无法投放
        if (productTypeId.equals(DkTaskType.DEPLOY) && vmStatus.equals(DkConstant.VM_RUNNING)) {
            throw new ServiceException("该设备状态为运行中，无法进行投放");
        }
        // 如果是维修工单，设备不在运行中，无法维修
        if (productTypeId.equals(DkTaskType.REPAIR) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
            throw new ServiceException("该设备状态不为运行中，无法进行维修");
        }
        // 如果是补货工单，设备不在运行中，无法补货
        if (productTypeId.equals(DkTaskType.RESTOCK) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
            throw new ServiceException("该设备状态不为运行中，无法进行补货");
        }
        // 如果是撤机工单，设备不在运行中，无法撤机
        if (productTypeId.equals(DkTaskType.REMOVE) && !vmStatus.equals(DkConstant.VM_RUNNING)) {
            throw new ServiceException("该设备状态不为运行中，无法进行撤机");
        }
    }
    ```

    * 调用方式是 `checkCreateTask(vm.getStatus(), taskDto.getProductTypeId())`；注释写清楚后，这段繁琐判断交给 AI 按注释生成即可。

* **第三步：禁止同一种工单重复创建**

    * 已经派给张三的工单还没完成，再派给李四就是重复；维修工单张三刚修完李四又去修同样不合适。

    * 规则：正在进行中的工单，未完成的工单，同一种类型只能有一个。

    * 校验按「设备编号 + 工单类型 id + 工单状态属于进行中」三个条件查库。

    ```java
    // 3.检查设备是否有未完成的同类型工单
    if (hasTask(taskDto)) {
        throw new ServiceException("该设备已有未完成的工单，不能重复创建");
    }

    /**
     * 是否存在进行中的同类型工单
     */
    private boolean hasTask(TaskDto taskDto) {
        // 创建task条件对象，并设置设备编号和工单类型以及工单的状态为进行中
        Task taskPara = new Task();
        taskPara.setInnerCode(taskDto.getInnerCode());
        taskPara.setProductTypeId(taskDto.getProductTypeId());
        taskPara.setStatus(DkTaskStatus.IN_PROGRESS);
        // 调用taskMapper来查询数据库，查看是否有符合条件的工单列表
        List<Task> list = taskMapper.selectTaskList(taskPara);
        return list != null && list.size() > 0;
    }
    ```

    * > **提示**：工单状态的常量不叫 `TASK_STATUS_DOING`，项目里叫 `IN_PROGRESS`，对应数值 `2`。写错了编译能过但行为不对。

    * 这段也能像第二步一样交给 IDEA 抽取方法，快捷键 `Ctrl + Alt + M`，选中代码自动抽好，只需改个方法名。

* **第四步：执行人存在且区域匹配**

    ```java
    if (emp == null) {
        throw new ServiceException("员工不存在");
    }

    // 5.校验员工区域是否匹配
    ```

### 工单编号：日期加 Redis 自增序列

* **编号规则**

    * 前八位是年月日，后四位是当日自增序列，今天第一张工单写 `0001`，第二张写 `0002`。

    * 每一天的序列都必须从 1 开始（8 月 27 日是 `0001`「0002」「0003」，到 28 号又从 `0001` 开始），数据库自增做不到这个语义，所以用 Redis 自增器。

* **INCR 演练**

    * 连接本地开发环境的 Redis（内存数据库地址 `127.0.0.1`、端口 `6379`、密码 `root`），命令行关键字 `INCR`，指定 key 如 `task_code` 执行一次自动为 `1`，再执行依次变为 `2`、`3`、`4`、`5`，即自增。

    * 思路：以日期为单位每一天创建一个 key，自增序列自然从一开始；第二天这个序列若不再需要，设过期时间让它 24 小时后销毁，既实现功能也不占内存。

* **实现方法**

    ```java
    /**
     * 生成并获取当天的工单编号（唯一标识）
     */
    private String generateTaskCode() {
        // 1.获取当前日期，格式化为年月日（注意中间不能加横杠哦）
        String dateStr = LocalDate.now().toString().replace("-", "");

        // 2.根据日期来生成Redis的key
        String key = DkConstant.TASK_CODE + dateStr;

        // 3.如果key不存在，设置初始值为1，并指定过期时间为一天
        //    （第二天序列还要从一开始，没必要在内存里占这个空间，自动销毁即可）
        if (!redisTemplate.hasKey(key)) {
            redisTemplate.opsForValue().set(key, "1", Duration.ofDays(1));
            return dateStr + "0001";
        }

        // 4.如果key存在，计数器加一，补齐四位后返回
        Long count = redisTemplate.opsForValue().increment(key);
        return dateStr + StringUtil.padLeft(count.toString(), 4, '0');
    }
    ```

* **三个细节**

    * 日期格式：`LocalDate.now().toString()` 中间带横杠，用字符串 `replace("-", "")` 换成纯年月日串。

    * `hasKey` 判断要带逻辑非：key 存在就直接自增，不存在则设初始值 `1` 并指定一天过期时间；`redisTemplate` 需要注入。

    * 补零用 hutool 的 `StringUtil.padLeft`，三个参数分别是自增序列的值、总体长度（四位）、前面补齐的字符。
      > **易错点**：`padLeft` 的第一个参数要求 `String`，所以 `increment` 后面要加 `toString()`。手动拼固定个数的零不靠谱——原值 `11` 补三个零会变成四位而不是两位。

    ```java
    // 使用Redis的自增器 opsForValue().increment 把key扔过去，这是它自增后的结果
    // 我们一共需要四位，如果不满足四位的话，帮我们补零
    Long count = redisTemplate.opsForValue().increment(key);
    return dateStr + StringUtil.padLeft(count.toString(), 4, '0');
    ```

* > **易错点**：上面方法里第一个 `return` 返回的是「日期 + `0001`」没问题，第二个 `return` 最初只返回了自增序列 `0002`，忘了把 `dateStr` 拼上，必须补齐。

### 弹窗按钮由工单状态决定

* **三种状态的弹窗内容**

    ```text
    工单状态
       │
       ├─ 待办 / 进行中 ──► 弹窗显示【取消按钮】
    ```

* **运维与运营详情共用一套接口**

    * 共两个：取消工单的后端接口、查看补货清单的后端接口。

### 取消工单接口

* **接口文档与参数**

    * 请求路径 `/manager/task/cancel`，请求方式 `PUT`，请求参数类型为 JSON。

    * 请求体中包含两个参数：`taskId`（工单 id）与取消理由（也就是拒绝的理由）。

    * 抓包 payload 证实：界面点确定时并没有编辑任何参数，`taskId` 是当前工单主键，取消理由是前端写死的「后台工作人员取消」——这类参数前端已帮我们设置好，用后端实体类 `Task` 接收即可。

    * 返回结果是标准 `AjaxResult`，含 `message` 与 `code`。

* **Controller**

    ```java
    @PutMapping("/cancel")
    public AjaxResult cancelTask(@RequestBody Task task)
    {
        return toAjax(taskService.cancelTask(task));
    }
    ```

    * 请求方式 `PUT` 写 `@PutMapping`；请求路径的前两层类上已经有了，这里只写 `cancel`。

    * 权限注解与日志注解直接复制「修改工单」的，属性值不用调整可完全复用——取消工单本质也是修改工单状态。

    * 前端传 JSON，`@RequestBody` 敲完按 Tab 由 IDEA 补全；方法注释写「取消工单」，把 `@params` 与 `@return` 删掉保持若依风格。

* **Service 三步**

    ```java
    @Override
    public int cancelTask(Task task)
    {
        // 1. 判断工单状态是否可以取消
        // 先根据工单id查询数据库
        Task taskDB = taskMapper.selectTaskById(task.getTaskId());

        // 判断工单状态是否为已取消
        if (Constants.TASK_CANCEL.equals(taskDB.getTaskStatus()))
        {
            throw new ServiceException("该工单已取消了，不能再次取消");
        }

        // 判断工单状态是否为已完成
        if (Constants.TASK_FINISH.equals(taskDB.getTaskStatus()))
        {
            throw new ServiceException("该工单已完成，不能取消");
        }

        // 2. 设置更新字段
        task.setTaskStatus(Constants.TASK_CANCEL);
        task.setUpdateTime(DateUtils.getNowDate());

        // 3. 调用Mapper层接口，直接完成更新工单
        return taskMapper.updateTask(task);
    }
    ```

    * 前端传来的 `Task` 对象只有工单 id 和取消原因，对象里并没有当前工单状态，所以必须先根据 id 查库拿到 `taskDB` 才能校验。

    * `equals` 比较时把常量写在前面避免空指针；异常提示 IDEA 自动生成的太简单，改成人话。

    * > **易错点**：更新字段要设置在 `task`（前端对象）上而不是 `taskDB` 上。因为 `task` 里存着取消原因和工单 id，以 id 为条件更新即可；数据库有动态 SQL 把 null 值排除在外。传错了就拿不到前端更新的备注说明，也拿不到「工单状态为已取消」。

    * Mapper 层无需编写，直接复用若依生成的 `updateTask`，返回影响行数直接写在 `return` 中。

* **实测**

    * 运维工单点取消点确定，状态改为已取消；运营工单用的是同一套接口，效果相同。

### Swagger 注解体系

* **接口能在文档中显示的依据**

    * 当前类上面加了 `@Api` 注解提示这个类是做什么的（`TestController` 里提示「用户信息管理」）。

    * 每个方法上面加了 `@ApiOperation` 描述方法功能与参数，`@ApiParam` 用于描述请求参数。

    * 项目启动时通过 Swagger 解析这些注解，把每个方法渲染成接口文档，识别方法参数与返回值。

* **实体类上的注解**

    * 实体类上加 `@ApiModel` 描述实体信息，属性上加 `@ApiModelProperty` 描述字段意义，文档里才会显示中文说明与对应类型。

    * 把 Controller 类代码复制给 AI，提示词是「你是一名软件工程师，请为以下 java 代码添加 swagger 注解」，生成的代码粘回替换即可；个别报错的注解用 `Alt + Enter` 手动识别导入。

    * > **提示**：Knife4j 只是对 Swagger 的一种增强，对 Swagger 注解做兼容，所以用 Swagger 注解即可，不需要换成 Knife4j 自己的注解。

* **BaseEntity 的盲区**

    * > **易错点**：即使实体属性都加了 `@ApiModelProperty`，`createBy`、`createTime`、`params`、`remark` 这几个仍没有说明——因为它们继承自父类 `BaseEntity`，而父类上的这些属性没有加 Swagger 说明。

    * 结论：想让这些字段在前端显示中文说明，就要为每个实体属性加上 `@ApiModelProperty` 并写上注释。

### AjaxResult 与 R 的取舍

* **现象**

    * 参数说明、路径参数、是否必须都正常，但「响应结果」是空的，尽管 Controller 方法明明有返回值。

* **成因**

    ```text
    AjaxResult  extends  HashMap
            │
            ├─ code     ─┐
            ├─ msg      ─┼─► HashMap 的 key（静态）
            └─ data     ─┘
                              value 是 Object 类型（动态，按业务场景拼接）
                                          │
                         Swagger / Knife4j 不兼容 HashMap
                                          │
                                          ▼
                            无法识别 AjaxResult，页面显示空内容
    ```

* **解法：抄若依的作业**

    * `TestController` 的方法返回结果不再是一个 `AjaxResult`，而是一个带泛型的 `R`。

    ```java
    public class R<T>
    {
        private int code;
        private String msg;
        private T data;

        public static <T> R<T> ok(T data)      // 表示返回成功
        public static <T> R<T> fail(String msg) // 表示返回失败
    }
    ```

    * `R` 是普通实体类，没有继承 HashMap，所以 Swagger 与 Knife4j 能识别；三个属性名与 `AjaxResult` 一致，因此可以直接采用。

* **改造写法**

    ```java
    @GetMapping("/byTaskId/{taskId}")
    public R<List<TaskDetails>> byTaskId(@PathVariable("taskId") Long taskId)
    {
        TaskDetails taskDetails = new TaskDetails();
        taskDetails.setTaskId(taskId);
        return R.ok(taskDetailsService.selectTaskDetailsList(taskDetails));
    }
    ```

    * > **易错点**：改成 `R` 之后就不能再用 `BaseController` 中的 `success` 方法了——它的返回结果是 `AjaxResult`，两者不通用。改用 `R` 提供的静态方法 `ok` 返回结果，别忘了 `Alt + Enter` 导包。

### 在线调试与令牌

* **调试流程**

    * 在文档页面上点「调试」按钮可设置请求参数的值，把路径参数 `taskId` 改成实际存在的工单 id。

    * 工单 id 可以从浏览器 F12 的 Network 里拿：点运营工单的查看详情，会发出两个请求，第一个是查看工单详情，第二个是查看补货清单，它的 id 就是当前工单 id。

    ```text
    ┌── 调试面板 ───────────────────────────────────────┐
    │  路径参数   taskId = 549                          │
    │  请求头     Authorization = <前端 cookie 里复制>   │
    └──────────────────────────────────────────────────┘
    ```

* **令牌是硬要求**

    * 向后台发送请求必须携带令牌，它就是身份登录信息；不携带会返回 `401` 权限不足的状态码。

    * 登录信息在前端 application 的 cookie 中，`Admin-Token` 就是身份令牌，全选复制后替换掉原有的。

* **返回结果**

    * 请求成功后状态码 `200`，`code` 为 `200`、`msg` 为「操作成功」，`data` 是数组，返回了当前工单的补货清单。

* **适用范围**

    * 工单管理、点位管理、设备管理、人员管理等模块的接口文档生成与调试，都可以照着同样的操作完成。

### 文档显示信息配置

* **标题与描述**

    * Swagger 配置类在 `dk-admin` 模块下 `java` → `web` 包 → `config` → `core` 的 `SwaggerConfig`，其中可以控制 Swagger 开关（在配置文件里指定）与统一请求前缀。

    * 最后一个方法是描述接口文档摘要信息的，把标题从「RuoYi 管理系统」改为「帝可得管理系统」，描述信息也可一并调整。

* **作者与版本**

    * 配置类里看不到作者在哪里改，因为它在配置文件中，作者与版本信息都在配置文件里指定。
