# 操作日志与定时任务

## 操作日志的自定义注解

* **操作日志注解（`@Log`）**

    * > **定义**：若依自定义的注解，装饰在 Controller 方法上，作用是在方法执行时把当前业务的操作日志保存到数据库。

    * `@Target({METHOD, PARAMETER})` 指定使用位置，可以放在参数上也可以放在方法上，通常用在方法上。
    * `@Retention(RUNTIME)` 指定作用范围，表示注解在运行时有效，切面才能反射读到它。
    * `@Documented` 表示生成代码文档时也会包含此注解。
    * 手写记录日志要收集系统模块、操作类型、操作人员等信息，工作量大、代码重复，还会干扰业务逻辑的清晰度。
    * 注解带来的收益：业务代码保持纯净做到无入侵；调整记录细节或策略只改一处，引入该注解的方法全部同步生效。

* **注解属性**

    | 属性名 | 类型 | 默认值 | 作用 |
    | :--- | :--- | :--- | :--- |
    | `title` | `String` | 空 | 描述操作模块，比如订单管理、设备管理、工单管理 |
    | `businessType` | `BusinessType` 枚举 | `OTHER`（其他类型） | 描述当前方法的操作功能 |
    | `operatorType` | `OperatorType` 枚举 | `MANAGE`（后台用户） | 操作人的类别 |
    | `isSaveRequestData` | `boolean` | `true` | 是否保存当前方法传过来的请求参数 |
    | `isSaveResponseData` | `boolean` | `true` | 是否保存方法的响应参数 |
    | `excludeParamNames` | `String[]` | 空 | 指定需要排除的请求参数 |

    * 后面四个属性一般直接用默认值即可，操作日志查询页点击「详细」按钮就能看到请求参数与返回参数等详细信息。
    * `isSaveRequestData` 控制的请求参数，在订单新增时就是那个默认要入库的 `order` 参数。
    * `isSaveResponseData` 控制的响应参数，指方法的 `AjaxResult` 返回结果，默认同样入库。
    * 要排除某个请求参数就用 `excludeParamNames`。

* **业务类型枚举（`BusinessType`）**

    * 除默认的 `OTHER` 外，还有新增、修改、删除、授权、导出、导入、强退、生成代码、清空数据等值。
    * 该枚举值可以按业务扩展。

* **操作人类别枚举（`OperatorType`）**

    * 三个枚举值：其他、后台用户、手机端用户。
    * PC 端用户用 `MANAGE`，手机端用户用 `MOBILE`，其他平台访问用 `OTHER`。

## 操作日志的切面机制

* **日志切面（`LogAspect`）**

    * > **定义**：位于框架模块的 `aspectj` 包下、带 `@Aspect` 注解的切面类，专门拦截标了 `@Log` 的方法并落日志。

    * 注解本身只是标记，真正干活的是切面。
    * 切面类可以定义四大通知加环绕通知，若依只用到前置、后置、异常三种通知。
    * 类中有一个 `Long` 类型字段 `operTime`，记录方法开始前的时间。

* **切点表达式**

    * > **定义**：`@Pointcut("@annotation(com.ruoyi.common.annotation.Log)")`，专门拦截 Controller 类上标了 `@Log` 注解的方法。

* **前置通知（`@Before`）**

    * 在每个方法执行前用 `System.currentTimeMillis()` 记下当前时间到 `operTime`。

* **后置通知（`@AfterReturning`）与异常通知（`@AfterThrowing`）**

    * 正常返回时调用 `handleLog(joinPoint, null, null)`。
    * 抛出异常时调用 `handleLog(joinPoint, e, null)`。
    * 业务方法成功要记、失败了更要记，失败的那次恰恰是最需要被追查的。

* **方法耗时**

    * 方法开始前记一个时间、方法执行后再记一个时间，两者相减就是该业务方法的耗时。

## 操作日志的组装与落库

* **`handleLog` 的四份输入**

    * 切点，也就是访问的目标方法。
    * 切点上面的自定义注解，也就是 `@Log`。
    * 是否有异常信息。
    * 方法的返回结果。

    * > **易错点**：第三份和第四份信息互斥——成功返回时没有异常信息，发生异常时没有返回结果，两者不会同时存在。

* **字段装配步骤**

    * ① 执行状态默认正常，设为 `0`。
    * ② 请求地址由请求 IP 和请求 URL 两部分组成。
    * ③ 操作人、部门名称在登录用户不为空时才设置，部门名称与用户信息里的部门对上。
    * ④ `e != null` 说明 Controller 方法已经发生异常，此时把状态改为 `1` 并把错误信息存进去。
    * ⑤ 方法名称通过切点表达式取类名再取方法名组合而成，包括包名、类名和方法名。
    * ⑥ 请求方式是 `GET` 还是 `POST`、`PUT`、`DELETE` 等等。
    * ⑦ 模块名称等字段专门处理 `@Log` 注解上的参数：系统模块名称、操作人类别、是否保存请求参数、是否保存返回值，一把设置进日志属性。
    * ⑧ 耗时 = 方法即将结束时的当前时间 − 前置通知记录的 `operTime`。

* **落库前先取当前用户**

    * 通过 `SecurityUtils` 获取当前登录用户。
    * 随后创建操作日志实体类，该实体对应的就是数据库里的操作日志记录表，最终封装好几个属性字段写库。

* **异步保存（`AsyncManager`）**

    * 最后一行使用异步任务管理器执行保存动作，底层是线程池，任务由异步线程工厂创建。
    * 任务内先用 `AddressUtils` 工具类获取 IP 地址，解析出该 IP 对应的操作地点。
    * 再用 `SpringUtils` 从 IOC 容器拿到记录操作日志的业务层 Service，调用其 `insert` 方法。
    * `insert` 再调 Mapper 层的 SQL 语句，实现操作日志的新增。

* **链路上两次从容器取对象**

    * 业务层 Service 是用 Spring 工具类从 IOC 容器获取的。
    * 异步管理器底层那个线程池对象，同样是用 Spring 工具类从 IOC 容器获取实例，再调用其方法完成任务的执行。
    * 操作日志因此走的是异步多线程执行，从而提升整体性能。

## 操作日志的完整链路

```text
客户端发送请求
      |
      v
Controller 方法（标注了 @Log）
      |   AOP 代理在这里拦一道
      v
LogAspect（切点：@annotation(...Log)）
      |-- @Before          --> 记下开始时间 operTime
      |-- @AfterReturning  --+
      +-- @AfterThrowing   --+--> handleLog()
                                    |  收集：操作人 / 部门 / IP / URL
                                    |        模块 / 操作类型 / 请求方式
                                    |        执行状态 / 异常信息 / 耗时
                                    v
                    AsyncManager + 异步线程工厂 + 线程池
                                    |
                                    v
                    ScheduledRunnable
                       |-- AddressUtils：IP -> 操作地点
                       +-- SpringUtils.getBean(SysOperLogService)
                              +-- insert() --> sys_oper_log 表
```

* **三件套的共性**

    * 记录操作日志与记录登录日志的做法一致，都使用异步任务管理器，底层靠多线程执行任务优化系统访问性能。
    * 操作日志这一块由自定义注解、AOP 切面、异步任务管理器三者构成，这三个基础也是绝大多数框架底层的实现原理。

## 定时任务的数据结构

* **核心表 `sys_job`**

    * 定时任务的核心表，存储任务所有配置信息，包括任务名称、任务分组等。
    * 前面三个字段组成联合主键：任务 ID、任务名称、任务组名，界面上有把小钥匙标识，是该表的唯一标识。
    * 之所以这样设计：不同分组下任务名称允许重复，而任务 ID 是主键自增的，前端可自行指定任务名称。
    * 任务分组对应数据字典，默认是「系统」，后期可结合业务场景扩展该数据字典。
    * `cron_expression` 定义此任务的时间规则。
    * 执行策略 `misfire_policy` 决定任务失败、服务器重启后如何恢复此前没执行的任务。
    * 是否并发 `concurrent`：`0` 允许，`1` 禁止。
    * 状态 `status`：创建好的任务默认是暂停；界面上点击开关可设为 `0` 正常（按 cron 规则定期执行），灰色为 `1` 暂停。
    * 另有继承 `BaseEntity` 后的五个公共字段：创建人、创建时间、更新人、更新时间、备注说明。

* **调用目标字符串 `invoke_target`**

    * 第一种是通过 Bean 的方式调用：左侧是 Spring IOC 容器中 Bean 的 ID，右侧是方法名，还可以传递参数。
    * 第二种是通过全限定类名调用：由包名和类名组成，底层通过反射执行此方法，同样支持参数传递。
    * 参数支持 String 类型、布尔类型、长整型、浮点型以及普通的整型等等。

* **日志表 `sys_job_log`**

    * 每一个定时任务执行时都会把调度日志存入这张表，列表最右侧的「调度日志」按钮可打开该任务的执行日志列表。

    | 页面字段 | 数据库字段 | 说明 |
    | :--- | :--- | :--- |
    | 日志序号 | `job_log_id` | 该条调度日志的主键 |
    | 任务名称 | `job_name` | 当前这条日志记录所对应的任务名称 |
    | 所属分组 | `job_group` | 任务所属的分组 |
    | 调用目标字符串 | `invoke_target` | 用 Spring Bean ID 执行此方法；没有括号表示无参传递 |
    | 日志信息 | `job_message` | 打印了任务名称以及耗时的毫秒值 |
    | 执行状态 | `status` | `0` 正常，`1` 失败 |
    | 异常信息 | `exception_info` | 用于记录异常信息；任务执行成功时没有输出 |
    | 执行时间 | `create_time` | 也就是任务的创建时间 |

* **两张表是一对多**

    * 一个核心任务可以有多条执行日志记录。
    * 日志表中有两个外键字段 `job_name` 和 `job_group`，指向任务核心表的联合主键。
    * 靠任务名称加任务组名，就能确定当前这条日志属于哪一条核心任务。

## 定时任务的代码位置

* **后端独立模块 `ruoyi-quartz`**

    * 定时任务被放在独立模块里，代码管理和维护更容易，主要分四部分。
    * 配置类：通过它可以开启 Quartz 集群模式。
    * 定时任务的三层代码，以及对应的实体类和 Mapper 映射文件，都在这几个包下面。
    * `task` 包：编写具体业务处理代码的地方，默认要求任务代码都放在此包下。
    * `util` 包：定时任务相关的工具类，包含创建执行定时任务的工具以及处理时间规则等功能。

* **前端目录**

    * 接口层在 `api/monitor` 目录下，两个 JS 文件分别负责定时任务和调度日志的 API 请求。
    * 视图层在 `views/monitor` 目录下，一个组件是定时任务管理界面，另一个用于查询和展示定时任务的调度日志。

## 启动时的任务初始化

* **初始化钩子（`@PostConstruct`）**

    * > **定义**：定时任务 Service 实现类上的 `init` 方法，该注解告诉 Spring 当前方法在对象构造完成之后立即执行。

    * 第一步清空调度器中已有的任务，确保从数据库加载最新的。
    * 第二步从数据库查询所有任务配置对象。
    * 第三步遍历任务配置列表，使用 `ScheduleUtils` 工具类创建出定时任务。

* **创建调度对象的七个步骤**

    * ① 按 `concurrent` 取 Job 任务类。
    * ② 用 `JobBuilder` 构建 `JobDetail`。
    * ③ 取 cron 表达式由 `CronExpression` 解析，按 `misfirePolicy` 决定错过后的补执行策略，`TriggerBuilder` 生成 Trigger 并与 JobDetail 绑定。
    * ④ 数据库查出的 job 配置塞进 `JobDataMap`，以键值对方式存储。
    * ⑤ 任务已存在则先删除，确保新任务能创建成功，避免与旧任务冲突。
    * ⑥ 判断当前任务的时间规则是否过期，未过期才把 JobDetail 和 Trigger 存入 Scheduler 容器。
    * ⑦ `status == 1` 暂停，`status == 0` 执行。

* **先定任务类，再定触发器**

    * Job 任务类是抽象类，同时实现了 `Job` 接口，所以要根据用户勾选是否并发来加载具体实现类。
    * `concurrent == 0` 加载 `QuartzJobExecution`，表示支持并发。
    * 其余情况加载 `DisallowConcurrentExecution`，DISALLOW 就是不允许的意思，该类上方加了 Quartz 的 `@DisallowConcurrentExecution` 注解表示禁止并发执行。
    * 两个实现类默认都继承抽象类 `AbstractQuartzJob`。
    * `JobDetail` 中包含任务类 `jobClass`，以及任务的唯一标识 `jobId` 和所属分组 `jobGroup`。
    * 若依推荐使用 cron 表达式，`TriggerBuilder` 据此构建 cron 时间规则的触发器。
    * 两个对象建好后存入 Scheduler 容器，它们才能被调度。

* **宕机后的三种执行策略**

    * 解析 cron 表达式成功后按 cron 时间规则设置定时任务策略，代码用 `switch` 语句判断，默认策略对应放弃执行。
    * 场景：服务器正常运行时突然宕机，档期周期有一个小时，这期间任务不会执行，服务器恢复后这些未执行的任务怎么办。

    | 执行策略 | 宕机恢复后的行为 |
    | :--- | :--- |
    | 立即执行 | 把之前没有执行的任务全部执行了 |
    | 执行一次 | 仅执行最后一个任务 |
    | 放弃执行 | 全部不补，默认策略，一般情况下用这个就可以了 |

* **按状态字段分流**

    * 状态为 `1`（界面上 `pause` 这个单词对应暂停）时，使用 Scheduler 暂停当前任务。
    * 状态为 `0` 时执行当前任务。
    * 执行时底层调用的就是允许并发与不允许并发那两个任务类，默认是不允许并发执行。
    * 两个任务类底层又会去执行 `JobInvokeUtil` 工具类。

## 任务真正执行的那一刻

* **执行入口（`AbstractQuartzJob.execute`）**

    * > **定义**：Scheduler 实际执行的方法，先初始化任务配置对象 `SysJob`，再从上下文中把属性复制到这个配置对象当中。

    * 上下文正是创建调度对象时存进去的 job 对象，所以这里能原样取回。
    * 执行任务前走 `before` 前置处理，执行具体任务走 `doInExecute`，执行完触发 `after` 后置处理。
    * `before`/`after` 的角色类似 AOP 当中的前置通知与后置通知。

* **前后置处理（`before` 与 `after`）**

    * `before` 用 `ThreadLocal`（线程局部变量）存入当前的系统时间。
    * `after` 把 `before` 存入的开始时间取出来，然后清空这个局部变量。

    * > **易错点**：这里用了线程池，不清空的话下一个线程就会获取脏数据，这是线程池加线程局部变量组合使用时最容易踩的坑。

* **任务日志的封装**

    * 字段含任务名称、任务分组、任务的目标字符串、开始时间、停止时间，以及由起止时间相减算出的耗时。
    * 有异常时记录任务的失败标志并设置异常信息；成功时设置成功的标志。
    * 最后一行用 `SpringUtils` 从 IOC 容器取出 `SysJobLogService` 实现类，调其 `add` 方法，日志添加最终落到 Mapper 的 SQL。

* **日志代码为什么放在抽象类里**

    * 并发执行与不允许并发执行这两个类执行完都要记录日志，而记录日志属于公共代码。
    * 把公共代码抽取到父类，避免在每个类中重复一份，换来代码的复用性。

* **反射执行（`JobInvokeUtil`）**

    * `doInExecute` 是抽象方法，具体执行交给 `JobInvokeUtil` 工具类，默认情况下走禁止并发的实现类。
    * 目标字符串第一种格式是 Bean 调用类型：Spring Bean 名称 + 点 + 方法名 + 方法参数，例如 `ryTask.ryParams('ry')`。
    * 第二种格式是包名 + 类名 + 方法名，通过反射来调用。
    * 两种格式都要把 `beanName`、方法名称、方法参数这三部分取出来。
    * 判断方式很简单：`beanName` 不含点的就是 Spring 容器的名称，含点的就是「包名.类名」。
    * 走 Bean 名时用 `SpringUtils` 从容器取实例，再通过反射执行此方法。
    * 走类名时 `Class.forName` 取字节码对象，`getDeclaredConstructor` 取构造器，`newInstance` 实例化对象，再通过 `invokeMethod` 调用此方法。
    * 传过来的参数数组不为空且长度大于零时，按对应参数反射调用；数组为空或长度小于等于零时，取无参方法对象调用无参方法。
    * 方法执行完毕后由抽象类的 `after` 记录当前任务日志并保存到数据库。

    * > **提示**：`Class.forName` → `getDeclaredConstructor` → `newInstance` 这套标准反射三连，作用是运行时才决定要创建哪个类，所以填在数据库里的类名甚至不需要在编译期被引用，这正是定时任务能动态添加的底层原因。

* **调度全流程图**

    ```text
    项目启动
       |
       v
    定时任务 Service 对象被初始化
       |  同时执行 init 方法（@PostConstruct：对象构造完立刻执行）
       |     |-- ① 清空调度器中的历史任务，确保加载最新的
       |     |-- ② 通过 jobMapper 查出数据库中的全部任务配置
       v
    遍历任务配置列表 --> ScheduleUtils.createScheduleJob(job)
       |  ① 按 concurrent 取 Job 任务类：
       |        0      --> QuartzJobExecution            （支持并发）
       |        其它   --> DisallowConcurrentExecution  （禁止并发，默认）
       |  ② JobBuilder  -> JobDetail（jobClass / jobId / jobGroup）
       |  ③ 取 cron 表达式，CronExpression 解析，
       |     按 misfirePolicy 决定错过后的补执行策略
       |        -> TriggerBuilder 生成 Trigger 并与 JobDetail 绑定
       |  ④ 数据库查出的 job 配置塞进 JobDataMap（键值对）
       |  ⑤ 任务已存在 --> 先删除，避免与旧任务冲突
       |  ⑥ cron 未过期 --> 放入 Scheduler 容器，可以被调度
       |  ⑦ status == 1 --> 暂停；status == 0 --> 执行
       v
    AbstractQuartzJob.execute(context)
       |
       +-- before()      : ThreadLocal 存入当前系统时间
       +-- doInExecute()  : 调用 JobInvokeUtil 反射执行目标方法
       +-- after()       : 取出开始时间并清空 ThreadLocal，
       |                   封装 SysJobLog -> SpringUtils 取 Service
       |                   -> add() -> sys_job_log 表
    ```

* **两条链路共同的思路**

    * 操作日志是「注解 + AOP 切面 + 异步任务管理器」。
    * 定时任务是「启动钩子 + Quartz 调度 + 反射执行 + 抽象类复用」。
    * 两者的共同点是把横切的东西从业务代码里抽出来，交给容器和框架统一处理，业务代码只管写自己那一摊。

## 新增任务的请求链路

* **新增入口**

    * 项目已跑起来后不会再执行一遍启动时扫库建调度的逻辑，新任务只能从接口进来，一路走到被调度器接管。
    * 入口是定时任务模块的 `SysJobController` 中的 `add` 方法，前端输入的参数封装成请求体，即任务配置对象 `job`。

* **控制器里的三道校验**

    * 第一道用 Cron 工具类校验用户输入的 cron 表达式语法，格式不正确直接返回错误信息。
    * 第二道判断调用目标字符串是否存在违规问题，命中违规字符数组即判违规。
    * 第三道用 `Schedule` 工具类的 `isWhiteList` 判断目标方法是否属于白名单。

* **只支持本地调用**

    * 调用目标字符串只支持本地任务的执行。
    * RMI 远程调用、LDAP（轻量级目录访问协议）、HTTP、HTTPS 都不支持，命中即判违规。

    * > **易错点**：将来编写的任务代码千万不要放到这些违规包下。

* **白名单机制（`isWhiteList`）**

    * 第一步取出调用目标的包名或类名，也就是去除方法调用部分，等于拿到了任务类。
    * 若目标是「包名 + 类名」组成，就判断包名是否在白名单内。
    * 白名单是一个字符串常量，默认要求任务类必须放到 `com.ruoyi.quartz.task` 包下。
    * 想把任务类放到其他业务模块（比如某个 manager 模块的包下），在白名单数组中增加一个逗号再写上该模块的包名即可，实现任务类的扩展存放。

* **Bean 名怎么查白名单**

    * 先通过 Spring 工具类拿到实例对象：`SpringUtils.getBean(beanName)`。
    * 再用 `bean.getClass().getPackage().getName()` 依次取到字节码对象、包对象、包名，返回当前对象所在的包路径。
    * 然后用工具类判断是否在白名单内、有无违规字符串；合法返回布尔值 `true`，不合法返回 `false`。
    * 控制器据此做判断，把错误信息返回到前端。

* **服务层先落库再建调度对象**

    * 校验通过后控制器用 `job.setCreateBy(...)` 设置当前登录用户的名称，记录该任务是谁创建的。
    * 服务层第一行把任务状态设置为暂停，默认新增加的任务不会执行。
    * 调 Mapper 新增到数据库，返回的影响行数大于零表示新增成功。
    * 成功后调 `ScheduleUtils` 工具类创建出定时任务对象。
    * 最后把数据库的影响行数返回给前端，提示新增成功。
    * 任何一道校验不通过，任务根本进不了数据库；即便进了库，状态也是暂停，绝不会立刻跑起来。

```text
[前端] 新增任务表单
   |  POST，请求体 = SysJob（invokeTarget / cron 表达式 / 任务分组 / 状态…）
   v
[SysJobController.add(job)]
   |-- 1) Cron 表达式语法校验 ---> 不合法则返回错误信息，结束
   |-- 2) 目标字符串校验
   |        RMI / LDAP / HTTP(S) 命中   ---> 判违规（只允许本地方法）
   |        违规字符数组命中            ---> 判违规
   |        白名单校验 com.ruoyi.quartz.task ---> 不在白名单则判违规
   |-- job.setCreateBy(当前登录用户)     <- 记录是谁创建的
   +-- sysJobService.insertJob(job)
            |
            v
   [SysJobServiceImpl.insertJob(job)]
            |-- job.setStatus("1")          <- 新任务默认暂停，不执行
            |-- Mapper.insert(job) ---> rows
            +-- rows > 0 ---> ScheduleUtils.createScheduleJob(job)  建调度对象
            |
            v
        返回 rows ---> 前端提示新增成功
```

## 任务启停

* **开关请求**

    * 前端做开关操作时发送 PUT 请求，携带当前任务 ID 和任务状态两个参数，由 `SysJob` 接收。
    * 界面上高亮是正常，置灰是暂停。
    * 控制器第一步按任务 ID 查出当前任务配置信息，第二步把前端状态设置进任务配置对象，第三步调服务层按状态决定启动还是暂停，最后把结果返回前端。

* **服务层按状态分流**

    * 返回结果 `rows` 初始化为默认零，然后根据前端传来的任务状态判断走哪条分支。

    ```java
    // 前端任务状态：'0' 正常（恢复执行），'1' 暂停
    if ("0".equals(job.getStatus())) {
        rows = resumeJob(job);   // 恢复任务
    } else {
        rows = pauseJob(job);    // 暂停任务
    }
    return rows;
    ```

* **恢复支路（`resumeJob`）**

    * 从数据库查询的任务配置里取出任务 ID 和任务所在分组，并把状态重新设置为正常，这是个重置操作。
    * 执行更新操作把用户最新的状态更新到数据库。
    * 数据库更新成功后，通过 `Schedule` 传任务 ID 和分组恢复任务调度，使其处于正常执行状态，返回影响行数。

* **暂停支路（`pauseJob`）**

    * 同样先取出当前任务 ID 和所属分组，把状态重新设置为暂停并更新到数据库。
    * 返回的行数大于零后，通过调度器暂停当前任务的执行，最后返回影响行数。

* **开关不是临时开关**

    * 无论走哪个分支，最新任务状态最终都会写进数据库。
    * 下次项目重新启动时，会根据最新的状态判断是否执行此任务。

```text
        前端开关（PUT：任务 ID + 状态）
                       |
          +------------+-----------+
          |                        |
      高亮（正常）            置灰（暂停）
          |                        |
      状态 = '0'               状态 = '1'
          |                        |
       resumeJob                 pauseJob
          |                        |
状态重置为正常并落库      状态置为暂停并落库
          |                        |
      rows > 0 ?               rows > 0 ?
          | 是                    | 是
ScheduleUtils.resumeJob ScheduleUtils.pauseJob
     (jobId + group)           (jobId + group)
          |                        |
          +------------+-----------+
                       |
        返回影响行数 -> 前端刷新开关状态
```

* **定时任务模块的其余功能**

    * 包括修改任务配置信息、删除、仅执行一次、查看详情，逻辑相对简单。
    * 模块参与的类有定时任务的业务层实现类、`ScheduleUtils` 工具类、任务抽象类及其两个实现类（一个不允许并发、一个支持并发），以及靠反射完成执行的 `JobInvokeUtil`，另有处理时间规则的 `CronUtils`。

## 单机模式与集群模式

* **单机模式**

    * > **定义**：默认所有 `jobDetail` 和 `trigger` 都存储在内存当中。

    * 好处是读取速度快。
    * 缺点是一旦服务器故障，所有任务数据就会丢失，即单点故障。
    * 高峰时段压力明显，例如上午九点触发 500 个任务，会给服务器带来巨大的负载压力，不仅影响性能，还可能引发服务中断。

* **集群模式**

    * > **定义**：部署多个服务器节点，把任务信息存储到数据库，多个节点通过共享数据库协调任务的执行。

    * 解决单点故障：某个节点出问题，其余节点仍可正常运行。
    * 负载均衡：一个任务可分散到不同节点执行，避免单个节点过载，上午九点的 500 个任务可以分给多个节点分担。
    * 生产环境本来就部署多台服务器，采用集群模式不会产生额外成本。

```text
[单机模式]
   Quartz 调度器（唯一节点）
       |-- jobDetail -> 进程内存
       |-- trigger  -> 进程内存
   服务器一挂 -> 任务全丢 = 单点故障

[集群模式]
   节点A(8080) 调度器 A --+
                          +--> 共享数据库
   节点B(8081) 调度器 B --+       |-- QRTZ_JOB_DETAIL
                                  |-- QRTZ_TRIGGERS
                                  |-- QRTZ_CRON_TRIGGERS
                                  +-- QRTZ_SCHEDULER_STATE
   节点之间心跳互相探测，谁空闲谁干活
```

## 集群里的数据库表

* **表的数量与四张核心表**

    * 在 Quartz 的集群中数据库扮演核心角色，需要创建特定表结构，与集群相关的一共 11 张表。

    | 表名 | 存什么 | 关键内容 |
    | :--- | :--- | :--- |
    | `QRTZ_TRIGGERS` | 触发器的基本信息 | 触发器名称、所在分组、类型（cron）等 |
    | `QRTZ_CRON_TRIGGERS` | cron 触发器的额外信息 | cron 表达式描述的时间规则 |
    | `QRTZ_JOB_DETAIL` | 任务的详细信息 | 任务名称、分组、描述、任务类名、任务数据 |
    | `QRTZ_SCHEDULER_STATE` | 调度器的状态信息 | 集群中每个节点的实例信息 |

    * 若依默认推荐使用 cron 类型，所以触发器信息拆成 `QRTZ_TRIGGERS` 和 `QRTZ_CRON_TRIGGERS` 两张表。
    * 存了 jobDetail 和 trigger 信息之后，最重要的就是 `QRTZ_SCHEDULER_STATE`，它存调度器状态。
    * 集群模式下每台服务器都是一个节点，同一集群中每个节点的 ID 唯一。
    * 效果就是把单机模式中存内存的任务信息整体搬进数据库。

## 三步改造成集群

* **导入数据库表结构脚本**

    * 在 `sql` 目录下找到 Quartz 集群的 SQL 脚本，它包含 Quartz 所需的数据库表结构，把它导入到数据库中。
    * 执行成功后当前数据库共 50 张表，其中 `QRTZ_` 开头的有 11 张。

* **打开集群配置类的注释**

    * 进入 Quartz 模块的 `config` 包，找到 `ScheduleConfig` 配置类，里面有一些被注释的配置项，取消注释即可启用集群模式配置。
    * 单机部署情况下建议删除该类和 Quartz 的数据库表，内存存储效率非常高。

* **复制启动节点改端口**

    * 通过 IDEA 复制现有启动类，把复制出来的启动类端口号由默认的 `8080` 改为 `8081`，确保每个节点在不同端口运行。
    * 复制前先改名称标记为节点一，复制出第二个后改名为节点二。
    * 两个节点默认共用配置文件里指定的 `8080`，同时启动会端口冲突，所以在二号节点的位置重置启动端口。

```text
-Dserver.PORT=8081
```

    * 在二号节点的环境配置中增加上面这个启动参数，该节点启动时就会重新加载 `8081`，一号节点仍是 `8080`，一台电脑即可模拟两个节点。

    * > **易错点**：启动参数里 `port` 的单词一旦写错，二号节点启动失败，日志直接报「8080 端口已经被占用」；改成全大写的 `PORT` 后重新启动，两个节点都正常。

## 集群的运行效果

* **任务在节点间漂移**

    * 一号节点先启动，定时任务已经执行，默认执行的是无参方法，因为之前开启了状态开关。
    * 二号节点启动后，任务被重新分配给二号节点执行，一号节点处于暂停的等待状态。
    * 哪个节点启动后比较空闲，任务就交给哪个节点执行，体现出负载均衡的效果。
    * 两个节点不会同时执行：一号节点控制台没有再次打印执行无参方法，二号节点是每间隔十秒打印一次。

* **数据库里看到的任务信息**

    * `QRTZ_SCHEDULER_STATE` 表里有两个节点信息，分别是一号机和二号机，由它们把 jobDetail 和 trigger 整合完成调度。
    * `QRTZ_JOB_DETAIL` 表里有三条记录，对应界面上三个任务的配置。
    * 任务执行用的是带 `@DisallowConcurrentExecution` 的 Job 实现类，即不允许并发任务执行的实现类。
    * `JOB_DATA` 是以二进制文件形式存储的任务信息。
    * `QRTZ_TRIGGERS` 表里三个任务对应三个触发器，`TRIGGER_TYPE` 就是 cron 表达式的类型。
    * `QRTZ_CRON_TRIGGERS` 表里存三个任务的时间规则：每间隔十秒、每间隔 15 秒、每间隔 20 秒分别执行。

* **模拟一次单点故障**

    * 集群中服务器节点之间有心跳监听的过程。
    * 关闭正在执行任务的二号节点后，一号机监听到二号机挂掉，就由一号机担任执行此任务的节点。
    * 任务因此继续正常执行，避免了单点故障问题，提高了系统可用性。

## 集群配置源码

* **配置类（`ScheduleConfig`）**

    * > **定义**：带 `@Configuration` 注解的配置类，方法内创建 `SchedulerFactoryBean` Bean 并返回给 IOC 容器。

    * `@Configuration` 告诉 Spring 容器这个类里有些 Bean 需要被特别加载。
    * 先从 IOC 容器获取 DataSource（数据源），设置给 `SchedulerFactoryBean`，这样 Quartz 就能用数据库存储任务和触发器信息。
    * 接着创建 `Properties` 对象，逐项 put 配置。
    * 最后把配置好的 `SchedulerFactoryBean` 实例返回，Spring 用它来启动和管理 Quartz 调度器。

```java
// 集群身份：实例名称必须一致，机器中所有节点才知道它们是一伙的
props.put("org.quartz.scheduler.instanceName", "RuoYiScheduler");
// 集群身份：实例 ID 在同一个集群中必须唯一，AUTO = 计算机名 + 时间戳，由 Quartz 自己生成
props.put("org.quartz.scheduler.instanceId", "AUTO");

// 线程池：用线程来执行每个节点的任务，从而提高效率
props.put("org.quartz.threadPool.class", SimpleThreadPool.class.getName());
props.put("org.quartz.threadPool.threadCount", "20");
props.put("org.quartz.threadPool.threadPriority", "5");

// JobStore：单机模式存内存，这里改用数据库存储 job 与 trigger
props.put("org.quartz.jobStore.class", JobStoreTX.class.getName());
// 开启集群
props.put("org.quartz.jobStore.isClustered", "true");
// 心跳检测间隔，单位毫秒
props.put("org.quartz.jobStore.clusterCheckinInterval", "15000");
// 错过触发时间的判定阈值与一次最多补处理的数量
props.put("org.quartz.jobStore.misfireThreshold", "12000");
props.put("org.quartz.jobStore.maxMisfiresToProcessAtATime", "10");

// 事务隔离级别，MySQL 最高级别，防止任务之间出现脏读、不可重复读或幻读
props.put("org.quartz.jobStore.txIsolationLevelSerializable", "true");
// 我们的数据库如果使用的是 SQL Server，请把这一行注释打开
// props.put("org.quartz.jobStore.driverDelegateClass", "org.quartz.impl.jdbcjobstore.SQLServerDelegate");
// 定时任务相关的表前缀
props.put("org.quartz.jobStore.tablePrefix", "QRTZ_");
```

* **调度器附加设置**

    * 为 Quartz 调度器设置了一个名称，并设置了延迟启动。
    * 设置上下文信息，允许更新已有的 job，而不需要删除再重新创建，这样效率更高。
    * 开启自动启动。

* **集群身份：名字要一样，ID 不能一样**

    * `org.quartz.scheduler.instanceName` 统一设为 `RuoYiScheduler`，同一集群中多个节点的实例名称必须一致，机器中所有节点才知道它们是一伙的，从而实现负载均衡。
    * `org.quartz.scheduler.instanceId` 设为 `AUTO`，实例 ID 在同一集群中多个节点必须唯一；`AUTO` 让 Quartz 自己生成独一无二的 ID，格式是计算机名加时间戳。
    * 数据库中 `QRTZ_SCHEDULER_STATE` 表左侧是集群名称，`INSTANCE_NAME` 列是计算机名加毫秒值，运行两个实例就显示两个独一无二的 ID。

* **线程池与 JobStore**

    * 集群中用线程执行每个节点的任务以提高效率，线程池采用 `SimpleThreadPool`。
    * `org.quartz.threadPool.threadCount` 默认线程数为 `20`。
    * `org.quartz.threadPool.threadPriority` 设为 `5`，取值范围 1~10，这也是默认值，不要跟主业务线程竞争优先级。
    * `org.quartz.jobStore.class` 用 `JobStoreTX`，这是本地数据源 JobStore，用来存储 job 和 trigger 信息，多个节点由此共享任务信息。
    * `org.quartz.jobStore.tablePrefix` 指定 Quartz 相关表的表前缀为 `QRTZ_`。

* **集群的三个关键参数**

    * `org.quartz.jobStore.isClustered` 设为 `true` 开启集群。
    * `org.quartz.jobStore.clusterCheckinInterval` 设为 `15000`，单位毫秒即 15 秒，是集群各节点检测对方是否还活着的间隔；某节点挂掉 15 秒后，任务就交给其他节点执行，从而解决单点故障。
    * `org.quartz.jobStore.misfireThreshold` 设为 `12000`，即 12 秒是错过触发时间的判定阈值。
    * `org.quartz.jobStore.maxMisfiresToProcessAtATime` 设为 `10`：页面配置了立即执行或仅执行一次时，恢复以后最多同时处理十个 misfire。
    * `org.quartz.jobStore.txIsolationLevelSerializable` 设为 `true`，隔离级别为 `SERIALIZABLE`，是 MySQL 数据库最高的隔离级别，防止各个任务之间出现脏读、不可重复读或幻读，保证执行任务的一致性。
    * 数据库若使用 SQL Server，要把 `org.quartz.jobStore.driverDelegateClass` 指向 `SQLServerDelegate` 的那一行注释打开。
