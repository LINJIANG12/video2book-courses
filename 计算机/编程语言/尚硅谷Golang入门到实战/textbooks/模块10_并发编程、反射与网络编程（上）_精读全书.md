## 协程、Go 主线程，和那条决定生死的规则
> 对应块：BLK100 | 覆盖分集：P266-P268 | 块标题（分集名）：《264_尚硅谷_go协程和go主线程》

下面我们来看一下另外一个概念，叫 Go 里面的协程和 Go 的主线程。

这个地方要有对应关系了。虽然确实不是特别好讲，因为这边概念叫得有点混乱，目前来说叫得还比较混乱。你们如果说有兴趣看书，会发现在 Go 语言里面，它的概念没有像传统语言写得那么明确。比如说 C 语言，它叫进程、线程，对吧？它这边多了一个东西叫协程。

### 协程是从哪儿来的

为什么有协程呢？它是这样子的。我先说一下历史的原因。

首先大家都知道，原先程序最早最早的时候没有并发和并行的概念，根本就没有，什么多核听都没听过。最早的时候就是一个进程打天下，就干一件事。后面发现进程效率太低了，程序专家、设计专家搞出一个线程。这样我们可以极大地发挥 CPU 的能力。

因为硬件发展总是比软件发展快。大家都知道，这点是一个定律，叫摩尔定律什么玩意儿，我忘了。有这么一个定律说法吗？就是硬件发展的比软件发展快。事实也是如此。

后面发现进程效率有点低，怎么办呢？就搞出一个线程。线程这个东西虽然很好，的确解决了很多问题，就是它至少能够做到并发了。但是又来一个新的问题：**线程还是比较吃资源**。也就是说，它虽然是一个轻量级的进程，但是它仍然也是比较吃资源的。所谓吃资源指的是占用 CPU 和内存还是比较多，因为有些地方还是物理态的，比较笨拙。

于是乎，Go 语言的设计者，就是 Ken Thompson 这帮哥们，他们就想：现在最大的问题就是要解决两个问题。

> **第一个要解决**：能不能让我们的 CPU 全部都参与工作？他要解决的第一个问题是：我的 CPU 假如说有八核，我能不能把我的任务全部分配下去，八个同时干？这样就很爽嘛。
>
> **第二件事情**：你这个线程虽然好，但是还是有点重。于是在底层做了一些优化。他把这个完全做成一种叫做逻辑态的。他在算法上做了一些优化，编译器做了一些优化，做成逻辑态。做成逻辑态过后，这个线程就变得更轻巧了、变得更轻了，从它的效率上、占的 CPU、吃的内存都更小了。因为可以在协程之间能够做到一些资源的共享，其实底层就做优化。做优化可能就是最核心的东西了。

那么他就搞了一个什么呢？干脆这样子，我提一个新的东西，叫协程。

> **结论**：**协程可以理解为是轻量级的线程。**

### 一个主线程里跑很多协程

那么这个时候就有概念了，又提出一个叫 Go 的主线程。Go 的主线程是什么呢？

有程序员直接把主线程就叫线程。所以我在讲课的时候，我可能会这样说：这个线程里面跑了多少个协程。提到这个线程，就是主线程。那么这个主线程从我们前面讲的概念上来看，这个主线程有点类似于传统语言的进程，只是叫法不一样而已。所以你看我这写两个：主线程，有的程序员直接叫线程，也可以理解成就是进程。

> **提示**：那有时候面试官问你：Go 里面有没有进程？这废话，没有进程能跑起来吗？但是有些程序员他会这样说：我们跑了一个主线程，主线程里面有多少个协程。不要认为没有进程，没有哪个语言说没有进程，没进程那是不可的事。只是它的叫法发生了一点变化，明白？

在一个线程上——如果我在说一个线程的话，你就可以理解成是主线程或者进程——我们可以起很多的协程。

```text
        ┌──────────────────────────────────────────────┐
        │  Go 主线程（有人直接叫"线程"，也可看成进程）  │
        │  物理线程，直接落在一颗 CPU 上，重量级         │
        └──────────────────────────────────────────────┘
            │      │      │      │      │      │
            ▼      ▼      ▼      ▼      ▼      ▼
          协程1  协程2  协程3  协程4  协程5  ...  协程N
            └─ 可以轻轻松松地起上万个协程，还非常稳定 ─┘
```

你可以这样理解：说我这里有一个线程，当然是主线程。这个主线程，这是我们 Go 的一个主线程。在这个 Go 的主线程里边，我们可以跑很多协程。所以叫法上稍微有点变化，但是本质上没有太大的变化，叫协程。协程说白了，就是我们所说的 goroutine。

在 Go 里面可以轻轻松松地起上万个协程。轻轻松松地起上万个协程，而且还非常的稳定。这个不得不服，在这个点上我们必须要服气。

> **易错点**：当然你不要跟那个携程搞到一起了。有个搞笑的笑话，说：你知道协程是什么吗？我知道，携程是专门做旅游的。那你就答错了。

为什么能起这么多？因为这个协程它做了优化了，它原先是在编译器在原先线程里面有很多可以共享的东西，整个直接拿过来给协程共享了，所以协程变得更轻了，跑得更稳健。

### 协程的四个特点

Go 的协程的特点必须记住，一定会有面试官问你，这个绝对跑不了。如果你将来面试 Go 程序员，或者你做区块链，肯定有人会问你协程的特点。

不用答得太多，就答四点就行了：

1. **有独立的栈空间**。也就是说，一旦开启一个协程，它们的数据空间是独立的，不打架，跟我们以前讲的栈一样，它数据是独立的。当然，它也有共享的东西。
2. **共享程序的堆空间**。它也可以去共享一个堆的空间。
3. **调度由程序员控制（用户控制）**。
4. **协程可以理解成是轻量级的线程**。

> **为什么第三条要单独拎出来说？** 因为协程的开启，还有协程的终止，完全可以由程序员去控制的。但是进程是没法做到的，这个你没法控制。说老师这个我能不能控制？这个不行。进程这个级别你是控制不了的。就是它什么时候调度起来，你控制不了。说老师我双击一下它调起来不是我控制的吗？不是这样子的。实际上是你双击过后，它把它分配到哪里、什么时候跑起来，是靠操作系统来玩的。所以重点来说还是：协程可以理解为是用户调度的，可以自己在程序里面直接去控制。你双击的时候只是一个动作，你能去程序里面去调？对吧。

把这四点给它答上来，我觉得就可以了，也不用说得太多。有时候说得太多吧，反而露怯。

有时候跟别人聊天是吧，你怎么说有钱呢？比如你去交一个女朋友，女朋友问你，她很想……其实你有两个方法去表示你比较有钱。你直接告诉她"我有一千万"，显得很没档次。你这样说嘛："我早上起来的时候，二姐在我们楼上四楼叫我，中午吃饭的时候，我妈在一楼叫我们去吃饭"，对吧？这就表示你们至少有四层楼，你们楼房有四层。人家觉得低调有内涵。你要表示你的房子，人家问你的房子是不是坐落在偏远的地方？你说"哎呀吵死了，旁边地铁声音太响了"，你的房子在地铁附近，一下就觉得又有钱，还很低调。所以有时候说话也有技巧。有时候真的是这样子，你们不相信去问小夏，问本杰。有时候面试不用说得特别多，简洁干脆就行了。你说太多吧，觉得你啰嗦。你就告诉他这四点，完了。如果再问到，再去详细解释就行了。

### 快速入门：两个互相打招呼的人

我们讲了协程还有主线程，但是没有看一个案例，心里总是很不舒服。我们来一个快速入门，讲完快速入门再往里面追。这里的内容很多的，你看这个幻灯片三十七张，现在讲到第七张，所以说咱们不着急。心急吃不了热豆腐。

有这么一个案例：请编写一个程序，完成如下功能。

- 在主线程中——也可以理解成那个进程——开启一个协程（goroutine），该协程每隔一秒钟输出"hello, world"；
- 在主线程中，也每隔一秒钟输出"hello, golang"；
- 输出十次后退出程序；
- 要求主线程和协程同时执行，同时画出主线程和协程的执行流程图。

不废话，我们直接代码实现。打开 VS Code，新建一个章节 `chapter16`，新建第一个小案例，新建文件 `main.go`：

```go
package main

import (
	"fmt"
	"strconv"
	"time"
)

// 编写一个函数，每隔一秒钟输出 hello, world
func test() {
	for i := 1; i <= 10; i++ {
		fmt.Println("test() hello, world " + strconv.Itoa(i))
		time.Sleep(time.Second)
	}
}

func main() {
	for i := 1; i <= 10; i++ {
		fmt.Println("main() hello, golang " + strconv.Itoa(i))
		time.Sleep(time.Second)
	}
}
```

首先他说开启一个协程。一般来讲，协程是以函数为单位来开启的，所以我先编写一个函数。该函数干什么呢？每隔一秒钟输出"hello, world"。这太 easy 了。

把一个整数转成字符串，用 `strconv.Itoa`，把 `i` 写进去。休眠一下，因为他说的是每隔一秒，`time.Sleep(time.Second)`。写完了过后，人家说了，在主线程中每隔一秒也干这件事情。那这个代码也很简单。

#### 顺序调用：看着很笨

如果我这样玩，大家看，我先按照传统写法：

```go
func main() {
	test()
	for i := 1; i <= 10; i++ {
		fmt.Println("main() hello, golang " + strconv.Itoa(i))
		time.Sleep(time.Second)
	}
}
```

如果我这样写，同学们知道，其实在调用 `test` 的时候，是不是先要把 `test` 整个执行完，才会执行主函数里面的 `for` 循环？这是个基本知识，大家要懂。这时候是主线程，它先要把 `test` 全部十次打完了过后再去打这个 `for` 循环。

```bash
cd chapter16
cd goroutine
go run main.go
```

这样子它是很笨的，就是按照顺序来走。但是大家想，这样子其实很不划算，因为我们想让它同时执行。即使这两个任务本身是独立的，你也会按顺序去执行。

但实际上我们在工作中往往是你这块执行和这块执行是需要并行的。比如说我们要算一个结果，你可以去执行一个任务，我也可以执行一个任务。但是你看，在默认的情况下是先干完第一件事，再干第二件事情，CPU 其实在一颗上，不行。

#### 加一个 go，输出就穿插了

那怎么做呢？如果我这样做，看，我就改一点点：

```go
go test()
```

就一句话搞定了。非常简洁，这就相当于开启了一个协程。

当我做了一个很简单的语法叫 `go test()` 的时候，你们再来体验一下用法发生变化：可以看到，它输出是穿插的。

什么意思？就是说它其实两个任务同时在做。打完做完了过后退出来。因为刚好大家都是一秒。如果时间我让休息得更长一点，可能另外一个干得更快。你看这个结果，其实相当于说，主函数和我们的 `test` 都在同时执行。

相当于说我在进行一个 `go` 的时候，你可以这样理解这个图：主干线往下走，走到这个地方的时候，伸出一个支线，在这里面玩。大家都一起做自己的事情，这样子的话，效率就大大地提升。这就叫开启一个协程。

它执行输出的效果是穿插的。从这个地方我们可以看出它是同时在执行，说明我们的主线程和我们的 `test` 协程是同时执行。

### 主线程与协程的执行流程

主线程和协程执行的示意图很重要。程序开始玩了，程序一旦开始，我们就认为一个进程或者一个主线程开始执行了，往下走。

走的时候突然发现有一个 `go test()`。当它发现一个 `go test()` 的时候，这个时候它马上会开启一个新的分支，让它在这里执行。**但是主线程并没有阻塞在这里**，它会继续往下走。它执行到这里的时候发现我有 `for` 循环，那就在这开始执行它的 `for` 循环。等到什么时候执行呢？等到我这个主线程执行完毕，就退出去。

```text
   主线程（进程）          协程 test()
        │                      │
  开始执行                    │
        │                      │
        ├── go test() ───────►│  立刻分叉，不阻塞
        │                      │
   for 循环 第1次             ├─ 循环第1次
        │                      ├─ time.Sleep(1s)
   for 循环 第2次             ├─ 循环第2次
        │                      ├─ ...
        ▼                      │
   主线程执行完毕 ──────────────┤
        │                      │
   （主线程已退出）              ▼
                            协程被连带干掉
```

大家可能有很多疑惑了。这里有很多细节了，你们脑海里面应该有很多问号。第一个：你这执行完了，但是它还在执行，退不退出？第二种情况下：你这还没有执行完，我这执行完了怎么办？

这就是我们后面要具体讲的细节。但是大体的流程大家要知道，重点就是要体现出这点：你们是开始分支了，你做你的事，我做我的事。至于他们之间怎么样去通信，是一个问题；至于谁退出为主，这也是个问题。因为他们之间可能有个通信机制。

> **结论一**：**如果主线程退出了，则协程即使还没有执行完毕，也会退出。** 比如说我主线程输出了十个，但是你协程要出一百个，我主线程先执行完毕，主线程一旦执行完毕，你这个协程也被干掉了。"老师，我还没有执行完呢？"不管，主线程都死了你还能活着？就好像一个主体都消失了，比如一个学校都没有了，学生肯定没地方去了，就这么简单。

> **结论二**：当然，协程也可以在主线程还没有退出前就结束自己，比如完成自己的任务。主线程是输出一百次，而你是输出十次，那谁先完成呢？它先完成。它先完成就完成，我主线程不会说你这完成了我就退出了，不行。

> **总结**：一定是以主线程的退出为主。大家可以看到，结论是以主线程的退出为主。

从上一个快速入门案例里边，我们可以得出这样一些结论：

- **主线程是一个物理线程**，直接作用在一个 CPU 上面的，是重量级的，非常耗费 CPU 资源。主线程是一个物理级的，由操作系统来控制的。
- **协程是从主线程开启的**，是轻量级的线程，是逻辑态，相对来说资源消耗相对较小。
- **Golang 的协程机制可以轻松地开启上万个协程**。其他编程语言的并发机制一般是基于线程，开启过多线程资源耗费大，这里就凸显出 Golang 在并发上的优势。这一块我们个人感觉，Golang 在协程、在并发性上面确实是它的一个特色。

### MPG：一个主线程凭什么能调度成千上万的协程

下面我们来看一下 goroutine 的调度模型是一个什么样的机制。MPG 是它的一个调度模型。这个模型我们也不需要说把它了解得多么透彻，但是基本原理大家还是要知晓的。一般面试的时候，如果问到 Go 的核心开发，多少会提一下 MPG 是什么东西。

#### M、P、G 分别是啥

**M 代表的是操作系统的一个主线程。** M 相当于是我们的主线程，你可以这么去理解，就像我们线程是从这里开始执行的。它是一个物理级的线程，所以它比较耗费资源。

**P 是什么东西呢？** P 你可以认为它是在整个执行过程中的一个上下文环境。什么叫上下文环境呢？这个上下文环境在很多编程语言里面都会有提到。

> **定义**：所谓上下文环境你可以简单理解成运行的时候所需要的一些资源，或者当时操作系统的一个状态。

你可以这样理解，就好像说我们这有一个 M 主线程，在运行的过程中，比如说在这个位置我们需要开启一个协程，在协程起来的时候需要有一个上下文环境。就好像一个人一样，一个人要生活，得有空气，得有水。人的上下文环境就是你生活的环境，你不能把一个人扔在火星上去，扔在月球上就 game over 了。就好像我们 Golang 起来的时候，它要依赖于当前操作系统的环境，还有没有内存可分配，还有没有 CPU 可分配，这些都可以称之为上下文环境。它是一个相对来说比较抽象的概念，就是它需要的资源和运行当时的一个状态，就这么理解。像人一样，得有空气有水才能生活。

**G 就是个协程。** 在创建运行过程中突然在这个地方需要去开启一个协程，那么这个协程可以往这走。这边可以有协程，甚至这个协程还可以形成一个队列。比如运行到这个位置，又需要创建或者开发一个协程，那么这边又算是一个节点或者上下文的一个环境，从这又可以继续开启另外的协程，同样也可以形成一个队列。简单地这么理解。

#### 静态模式：并发还是并行

MPG 模式运行的状态一，第一种情况我们来分析一下。

```text
        ┌──────┐       ┌──────┐       ┌──────┐
        │  M1  │       │  M2  │       │  M3  │
        │ CPU1 │       │ CPU1 │       │ CPU1 │   ← 全挤一颗 = 并发
        └──┬───┘       └──┬───┘       └──┬───┘
        ┌──┴──┐       ┌──┴──┐       ┌──┴──┐
        │  G1  │       │  G1  │       │  G1  │   ← 各执行一个 G
        ├─────┤       ├─────┤       ├─────┤
        │G3→G2│       │  G2  │       │     │   ← 排队的 G
        └─────┘       └─────┘       └─────┘


        ┌──────┐       ┌──────┐       ┌──────┐
        │  M1  │       │  M2  │       │  M3  │
        │ CPU1 │       │ CPU2 │       │ CPU3 │   ← 一人一颗 = 并行
        └──┬───┘       └──┬───┘       └──┬───┘
        ┌──┴──┐       ┌──┴──┐       ┌──┴──┐
        │  G1  │       │  G1  │       │  G1  │
        ├─────┤       ├─────┤       ├─────┤
        │G3→G2│       │  G2  │       │     │
        └─────┘       └─────┘       └─────┘
```

当前程序有三个 M，如果三个 M 都运行在一个 CPU，我们就称之为并发，并发就是这样来的。如果说它运行在不同的 CPU，我们认为就是并行。

第二点，M1、M2、M3 正在执行一个 G。从这里可以看出来，对于 M1（我们把它叫 M1，把这个叫 M2，把这个叫 M3），在 M1 它现在正在执行的是这个 G，这是个协程，它正在执行。同样这边也在执行一个 G，这边也在执行一个 G，当然主线程也在执行一个 G。

从这里看出来，这里还有一个队列。M1 协程还形成了一个队列，说明它这边还有好多协程等着它去执行；这边也有；这边只有一个协程在等待。

这就是它运行的一种模式。像这种 G（就是协程），可以轻松地起上万个，每个协程可以去完成它的一个任务。其他程序像 C 和 C++ 是多线程，起的是线程。线程往往是内核态的，比较重量级，几千个线程就可能耗光你的 CPU。

#### 动态模式：G0 被阻塞了怎么办

除了这种模式，我这还有一个动态的状态，这个比较有意思。

原来的情况是 M0 这个主线程正在执行 `go0` 这个协程，另外有三个协程在这里等待。

等待的时候如果遇到了 `go0` 协程被阻塞，比如什么情况下会阻塞一个协程呢？比如读文件或者数据库。因为你读文件的时候不知道要花多少时间，协程底层就会想：你这个地方读一个文件到底要读多久我不知道。有些同学说读文件不是挺快的吗？读一秒钟读两秒钟不是挺快吗？读一秒钟两秒对计算机来说已经很长了，它认为你在读文件的时候 CPU 有点浪费。

所以这个时候它有可能会做这样一件事情，因为你继续去做别的事，CPU 在这处于一个空闲状态。它会怎么办呢？这个时候就会创建一个叫 M1 的主线程。那也有可能已经从已有的线程池取出 M1，这要根据当时的情况。比如 M0 在运行了，它有可能在它的底层维护了一个线程池。线程池里面也有可能预留了一个 M1，但也可能没有，不知道。这个就跟操作系统底层相关了，如果有，我就把 M1 拿过来唤醒它，让它工作；如果没有，我就创建。这个情况就跟操作系统底层有关系了，跟你的上下文环境有关系。

不管怎么样它有个 M1。它有 M1 干什么事呢？M1 的作用就是说，你原先不是这挂了三个 G 在等待吗？现在我就可以来为你工作了。怎么做呢？并且将等待的三个协程挂到 M1 下面去执行。

```text
   【阻塞前】
      M0 (CPU1) ──执行──► G0
            │
            └─► 队列:  G1 ◄── G2 ◄── G3      (干等着)


   【G0 被阻塞的瞬间】
      ┌───────────────┐                ┌───────────────┐
      │    M0 (CPU1)  │                │    M1 (CPU2)  │
      │  卡在 G0 上    │                │  从线程池唤醒  │
      │  （在读文件）  │                │  或者新建      │
      └───────────────┘                └───────┬───────┘
                                                 │ 把等待队列整个挂上来
                                          G1 ◄── G2 ◄── G3
                                                 │
                                          开始轮流执行

   【G0 不阻塞之后】
      M0 读文件完毕 → 又被放回空闲态，继续执行 G0
```

有些同学可能对这个词不好理解，"挂到"。这是一个比较通俗易懂的讲法，其实说到我们程序底层，说白了可能就是一个链表，也可能是一个队列，数据结构完全可以做。挂到你可以简单的认为让这个 M1 指向一个队列。指向这个队列很简单，因为队列这些东西一般我们……我们可以创建，然后把这个队列指向给它就行了，就相当于挂到这上面去了。

那么 M0 这个主线程呢，它的 G0 仍然执行原先 G0 的读写。注意，它读写的时候就相当于阻塞了。

> **结论**：这样的 MPG 模式有什么好处？**既可以让 G0 去读它的文件，同时也不会让队列中的其它协程一直阻塞，没有机会执行。**

#### 用餐馆打个比方

打个比方说，现在有一个餐馆，我们去吃饭。前面有一堆家伙是这样子的，我们排队，有一个厨子正在这儿炒菜。厨子就相当于这个主线程在这炒菜。

炒着炒着呢，他本身是给一个客户在炒菜。假设这是客户 A，这是客户 B、客户 C、客户 D。客户 A 要的菜特别的多，他们这个客户一共点了有 100 个菜。B 和 C 是我们同学，中午要吃饭，我们只点一个盖饭。这就麻烦很大了，如果我们只为客户 A 服务的话，那么 B 和 C 可能要等到一两点半了，那就吃不了饭了。

那它有什么机制呢？因为客户 A 要 100 个菜，其中有一道菜是叫红烧熊猫肉，这个时候他得去搞一些——当然吃熊猫肉是违法的——比如说他搞一个海鲜。海鲜在做的时候呢，它有道工序，要先把海鲜比如临时的去洗一下、去泡、发，需要点时间。

在这个去做海鲜的时候，他有点空闲时间了。因为海鲜需要洗的时候、去让他的另外一个助手去洗一洗，或者说要泡一泡，比如说这个海鲜要泡五分钟才能够去煮。这个时候呢，他把这个海鲜一泡，相当于阻塞在这儿了。但是他有时间了，这个时候他就找正在排队的 B 客户说："你要什么？""我要一个鱼香肉丝盖饭。""我临时就给你炒一份。"炒完了过后，你这个 B 就服务完了，然后这边的海鲜也泡好了，我再回头回来再执行 G0。

等到 G0 不阻塞了，也就是说假设它的文件读取完毕了，M0 又会被放到空闲的主线程继续执行等等，也是这样子的一种感觉。

> **易错点**：有些同学说："老师，那你给 B 去做一个鱼香肉丝不就五分钟吗？那有可能这五分钟没有把鱼香肉丝炒好怎么办呢？难道炒半截就跑了吗？"
>
> 我们说的五分钟也好，这边泡海鲜五分钟、这边炒五分钟，这是我们人的一种时间的单位。在计算机里面，它其实片段很多。它来回一切，可能 0.01 毫秒一下就切过去了。因为这样一切，可能是瞬间就完成了。这边马上又有了一个事情，他马上切过去又去干，然后又来回切。这个东西它就有效地把 CPU 利用起来了。你不能理解成光泡海鲜，它还干很多其它事。这样来回一切换呢，就可以既保证我们主线程的执行，又能够保证协程的执行。这样子并发和并行都能执行。

### 关于 MPG 要记住的三点

第一点，别人问到这个 MPG，你能够大概知道 M、P、G 是什么东西，这个你得给他答上来。

第二点，你要明白在工作的时候它的模式是：M 代表一个主线程往下执行的时候，这个 P 可以根据实际情况开启一个协程去工作。M 可能有很多，这些 M 既可能是执行在一个 CPU 上，可能是这几个都挂在同一个 CPU 的，也有可能是每一个 M 挂一个 CPU，那个就叫并行。

第三点，同学们要清楚地知道，当有一个协程被阻塞的时候，它有一种来回切换的机制。这种机制既能够保证我们 M 主线程的执行，同时呢也能够让排队的 G 协程得到一种执行的机会。因为这个时间来回切换比较快，所以说你感觉效率很高，有效地利用了我们的 CPU 资源。

把这个理解了就可以了，也不需要同学们研究得特别透彻，因为我们更要理解的、待会儿最重要的是什么呢？要理解 Go 协程和 Channel 的一种通信，这个是我们的重点。因为这个东西你理解不理解都是操作系统加编译器来完成的。

## 把 CPU 用几个说清楚，再让 200 个协程一起写 map
> 对应块：BLK101 | 覆盖分集：P269-P270 | 块标题（分集名）：《267_尚硅谷_go设置运行cpu数目》

同学们，我们来看下一个案例。

下一个案例就是刚才我们讲的一个很经典的案例。Golang 能够充分发挥多 CPU 模式的优势，那么在 Golang 程序中，如何去设置运行的 CPU 数目呢？

### runtime 包里的两个函数

这里我们要看一个包。在 Golang 里面提供了一个叫 `runtime` 的运行时包。这个运行时包里面有两个比较重要的函数。

我们把 `runtime` 包打开看一下手册。`runtime` 包提供了 Go 运行时环境的互操作，比如控制 Go 协程的函数，也包括反射包和底层的一些类型信息，后面还会用到。

> **`NumCPU`**：返回本地机器的**逻辑 CPU** 个数。注意，是逻辑 CPU 的个数，不一定是真实的物理 CPU 颗数。比如有些物理上真正只有两个 CPU，但是逻辑上变成了四个 CPU，也有可能。
>
> **`GOMAXPROCS`**：用来设置**可同时执行的最大 CPU 数**。意思是说，你可以把所有的 CPU 全部设置进去，也可以保留一个 CPU。

为什么要保留一个呢？比如韩老师的机器有四个逻辑 CPU，但是在这个程序里面我只想用三个，另外一个要保留下来给别的程序用。因为如果全部占光了，可能别的程序瞬间就跑不起来了。所以这个根据实际情况来定。

### 写代码试一把

我们建一个新的文件夹叫做 `cpuDemo`，做一个 CPU 的测试。新建一个文件 `main.go`：

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	cpuNum := runtime.NumCPU()
	fmt.Println("cpuNum=", cpuNum)

	// 可以自己设置使用多少个CPU
	runtime.GOMAXPROCS(cpuNum - 1)
}
```

> **易错点**：注意 `NumCPU` 后面的 CPU 全部是大写的。`GOMAXPROCS` 也全是大写的，看清楚了。

有些时候，默认会把所有的 CPU 都用上。但有些时候可能想预留一个 CPU，就可以自己设置使用多少个 CPU。写法很直接：`runtime.GOMAXPROCS(cpuNum - 1)`，预留一个留给系统自己用，这样就设置成功了。

```bash
cd cpuDemo
go run main.go
```

看一下结果，显示目前确实是有四个逻辑 CPU。

> **版本提醒**：在 Go 1.8 以后，默认让程序运行在多核上，通常不用专门去设置 `GOMAXPROCS`，因为 1.8 以后会自动使用多核。Go 语言本身就默认支持多核并发，所以不需要额外设置。但是在 Go 1.8 以前，是需要手动设置一下的，这样可以更高效地利用 CPU。我们当前使用的版本是 1.9，所以通常可以不用去设置。

关于怎么去使用和设置 CPU 就先介绍到这里。

### 新的需求：把一到 200 的阶乘塞进 map

下面我们来给大家看一个东西叫做管道。这个就要画图了，这个挺有意思的，但是理解起来有一点点小难度。

大家看，问题来了，我们先看一个需求，还是先抛一个问题引起大家思考。

我们现在有一个需求：要计算 1 到 200 的各个数的阶乘，这个很简单，说白了就是 1 一直乘到 $n$，这个大家都会。**并且把这些数的阶乘放入到 map 中，最后显示出来。要求使用 goroutine 来完成。**

那么这个题对我们来说有难度吗？没有难度。我个人认为大家应该可以做出来。因为说白了，他就说让你用协程去做，让你用协程去做。那思路很简单，我们使用这个 goroutine 来完成，效率高，但是会出现一个并发和并行安全的问题，提出一个概念。说："老师，没什么问题啊。"

当这个问题产生了过后，我们就提出了一个思考。什么思考呢？就是**不同的 goroutine 之间如何通讯的问题**。

### 思路：写一个函数，起一堆协程，共同写一个 map

好，同学们，现在我们来一起完成这个代码。

我们还是新建一个文件夹，就叫 `goroutinedemo02`。新建一个文件 `main.go`，把我的需求先拿过来，主包，`import`。

它一共是 1 到 200 的各个数的阶乘。那么我们怎么来完成这个事情呢？它的要求是使用 goroutine 来完成，那我首先写段代码，主函数。

思路是这样的。第一步，我编写一个函数，来计算各个数的一个阶乘，并放入到一个 map 中。

第二点，我们应该分析出来：既然你将来会出现一个情况是你可能起很多这个协程，比如说我们启动四个或者五个，我们多起几个协程来完成，那么这个时候效率才会高嘛。然后我们这个 map 呢，我们启动的这个协程是多个，然后它们统一地去干什么呢？统一地去访问这个 map，统一地将阶乘的这个结果放入到 map 中。

那你为了让这个结果放到这个 map 中，那这个 map 是多个协程都要访问的，那你只能把这个 map 在初始情况下做成一个全局的，因为大家都要去访问。所以在这种时候，这个 map 应该是个全局的。这就是我们分析出来的三点。

先定义一个全局的 map：

```go
var (
	myMap = make(map[int]uint64, 10)
)
```

事先我们给它分配一个空间。我看我的输出是什么，将来输出的结果是一个 map，把各个数的阶乘放入到 map 中，最后我们显示出来。那就是说整个这个 map 呢，最后把结果都放到这里面去，最后我再遍历这个 map 就完事了。好，那 map 事先给它分配一个适合空间的大小。

那怎么 for 循环呢？先写一个 `test`，参数传一个 `n int`，是不是它可以是传一个数，我就把它这个阶乘求出来，是吧，这个没问题：

```go
func test(n int) {
	res := 1
	for i := 1; i <= n; i++ {
		res *= i
	}
	myMap[n] = res
}
```

就是我不停地去乘，最后这个 `res` 呢就是我们最后这个数的一个结果。循环完了过后，我就把这个 `res` 放入到这个 map 里面去。第一个值就是你当前这个 `n`，它对应的阶乘这个值呢，我们认为就是 `res`。这就写完了。

放进去过后，我们用起协程，我们多起几个协程来完成它。人家是要求用协程来完成嘛。你不是要求 1 到 200 的吗？那我就起 200 个，200 个最多：

```go
for i := 1; i <= 200; i++ {
	go test(i)
}
```

大家可以看到相当于我起了多少个呢？我起了 200 个。那也就是说你们可以想象到，当我们运行的时候，我们就一起启动了 200 个协程去帮我们做这个事情。每一个协程就完成一件事情，就是说你给我传进的 `i`，我算出阶乘并且把它放进去。

那起了 200 个过后呢，我们来这里输出结果。就是 map 里面这个结果有哪些，我们可以把它遍历出来看一下：

```go
for i, v := range myMap {
	fmt.Printf("map[%d]=%d\n", i, v)
}
```

理论上是这样写的嘛。第一个是它的 `i`，第二个是它的值。我们把它打印出来看一下，`fmt.Printf`，我们可以这样写，`map[%d]=%d
`，然后第一个 `%d` 呢是 `i`，第二个 `%d` 是 `v`。

```bash
cd goroutinedemo02
go run main.go
```

### 第一个坑：主线程早退了，一个结果都没有

同学们看到，什么都没有。有问题。说："老师，你这儿不是起了这么多的协程，为什么它一个都没有呢？"

是不是上午我曾经讲过一个特别重要的一个知识点？我说它的一个主线程和协程执行的一个流程。在这里用 for 循环开启了很多很多协程，200 多个协程。但是这个协程在还没有执行完毕的时候，主线程是不是已经结束了？**主线程一旦结束，下面的协程有没有执行完毕根本不管，所以说一个结果都没有。**

> **结论**：这正是上午那条规则在现实里咬人——**如果主线程退出了，则协程即使还没有执行完毕，也会退出。**

现在已经很尴尬了。说老师那我怎么办呢？我们现在先不想那么多，一步一步解决。现在假定我让你在这跑 10 秒钟，看有没有结果。一个最笨的办法就是，在主线程这一方等着，我等你 10 秒钟。

在这个主线程先不要着急走，先等 10 秒钟，这是最笨的办法。但是大家可能会说："老师，为什么等 10 秒钟，不等 20 秒呢？"等 20 秒你又会说为什么不等 30 秒是吧？

> **结论**：这个等长等短其实已经很麻烦了，这里已经提出一个问题了。**主线程什么时候退出，和协程什么时候完成，现在缺乏一种机制。** 它们之间必须要有机制，现在还没有好的机制，只能先来玩一个简单的。

最简单的办法就是等，休眠 10 秒。但这个地方其实很尴尬，时长了短了都不好，先暂时等 10 秒钟：

```go
time.Sleep(time.Second * 10)
```

10 秒乘一个 10，引入 `time` 包。我们再跑一下。

### 第二个坑：fatal error: concurrent map writes

同学们看到，这个时候报的错误很恐怖，报了一个 `fatal error: concurrent map writes`，什么意思？并发向 map 进行写入操作。

```text
      ┌──────────────────────────────────────────────┐
      │   全局 myMap （没有任何保护机制）              │
      └──────────────────────────────────────────────┘
          ▲          ▲          ▲          ▲
          │          │          │          │
      go test(1)  go test(2)  go test(3)  go test(4)   ... 共 200 个
      算完就写     算完就写     算完就写     算完就写

   CPU1 ─┐
   CPU2 ─┼─► 同一瞬间，多个 CPU 往同一块空间写
   CPU3 ─┤
   CPU4 ─┘
```

现在主线程起了 200 个协程，假设点到 200 了。这 200 个协程其实是不是都在同时操作同一块空间，这个 map 空间？没有任何保护机制。目前出现问题的原因是，主线程整了 200 个协程，都在做同一件事情：拿到一个 $n$，计算完了之后往 map 里面写。

现在这个家伙在疯狂地往里面写，另一个也同时往里写，因为现在至少有 4 个 CPU 在用。4 个 CPU 可能在同一个瞬间都往里面写。往同一个数据空间同时写的时候就会出现并发问题。

> **写不能有并发，必须要保护。读可以。** 两个人同时看一本书没问题，就像看电影，放映出来下面多少人都可以同时看。但是写不行，一张纸韩老师在写的时候，班长、副班长都要写，肯定要出问题。

### 加锁的思路：先来的人先上，后来的排队

用全局变量加锁什么意思呢？咱们可以这么玩一把。听我的这种思想。

现在的问题不就是因为协程一、协程二、协程三、协程四都有可能同时来操作 map 吗？其实问题就在这导致的。

如果我这样说呢，假设我在这有一把锁。当任何一个协程去操作我们这个空间时，先看这个锁有没有被关闭。如果是被关闭的，你就在这里进行一个等待。也就是说在这个地方我们对它做了一个处理，做了个什么处理呢？**让它排队。**

协程一想来操作它，因为先来这，持有这把锁。当协程一正在操作这个锁的时候，如果拿到这个锁，他就继续执行，往下执行。他执行完了之后，这边就解锁，就 `unlock`。这边我们叫做 `lock`，加锁；这边操作完完毕过后就 `unlock`。

当正在操作的时候，比如说协程一正在操作这个数据空间的时候，假设他正在操作，而协程二又来的时候，他也先到这边去看目前这个锁是不是加上的。如果他发现加锁了，他怎么办呢？他应该把它扔到一个叫做队列里面去，队列缓冲。比如说这边会产生一个队列。

这个时间协程一先到这来排队。协程一说我不着急，等你做完了我再说。他先把自己排到这。协程二也在这等待。

如果说协程三，因为协程三也傻乎乎的他也要操作，但是他发现协程一还正在操作，于是他也跑到这边说我也老老实实的在这排队，我不跟你抢，对吧？他也在这排队。于是乎他就排到了协程二的屁股后边，大家都按秩序来。协程四说我也去操作，发现协程一有可能还正在操作，协程四也可能排队。以此类推。

这样子他们就有一个很好的机制了。大家不着急，大家都按照顺序来玩。大家看到，大自然其实就是这样子的。

```text
        全局 myMap
   ┌───────────────────────┐
   │                       │◄──── 只有拿到锁的人能进来
   └───────────────────────┘
        ▲        ▲        ▲
        │        │        │
      go(1)    go(2)    go(3)      ← 全都往同一块空间写

   ═══════════  等候队列（谁先来谁先走）═══════════
      go(2)  ──►  go(3)  ──►  go(4)
                    ↑
            队伍里的一个都没资格动手
```

> **结论**：当协程一来操作，他先给这个 map 空间加一把锁。协程二他发现有锁，他就不操作。等到协程一执行完毕过后，他会把这个锁解开。解开完了之后，底层有一种机制会从这个队列里面取出排在最前面的这个协程，让你去工作。

这就跟一个排队上厕所一样，很形象。说我们班有个同学张三去上厕所了，厕所只有一个坑，张三很惨，只有一个坑。他去了过后我先把门关上。这个时候小明来了，他发现那个地方门是关上的，那肯定不能冲进去，人家正在这解决问题，你冲进去太没礼貌了。所以他就在这排队。

这个时候李四又来了，李四说你们在这干什么？我在排队呢。李四肯定要讲道理，说那我就排在张三的屁股后面。

这个时候王五又来了，王五说那我也排在李四后边，我排好。排好了过后，第一个人去的班长他解决问题了，解决完了他门一开说你进去吧，走了。那这个人就开始进到这边。他进去的时候他是不是也得把门锁上？要是别人冲进来怎么办？所以他要把锁锁上。这样子就不会出现什么问题呢？一个坑同时有几个人在上，那这个就非常恐怖了。

### sync.Mutex：Lock 与 Unlock

代码怎么实现呢？怎么加锁呢？它的观点就是全局变量加锁。

因为没有全局变量对加锁，因此会出现这个资源争夺问题。代码会出现错误提示这个。解决方案，我们加入互斥锁就可以了。

既然是全局变量，那不啰唆了，上来过后先搞一个东西。在这定义或者声明一个，声明一个全局的互斥锁：

```go
var (
	myMap = make(map[int]uint64, 10)
	lock  sync.Mutex
)
```

变量随意，它的类型是 `sync.Mutex`。

> **两个词要记牢**：`sync` 是一个包，它是 synchronize 的缩写，同步的意思，全称是 synchronized；`Mutex` 这个单词是互斥的意思。互斥锁就说我用了你就不能用，这就叫互斥锁。其实还有一种锁叫读锁，有读锁和写锁，读和写两种锁。这个是互斥锁，属于写锁。

我们把 `sync` 这个包找到。这个单词翻译过来叫 synchronize，就叫同步的意思。他说这个包提供了基本同步的单元，如互斥锁。

> **手册里的原话很有意思**：他说这个是适用于低水平的程序员的线程。高水平的同步应该是用 channel。

那老师我们先来一个高水平的？我们先低再高，有时候你简单一点都用全局的也还可以，对吧？通讯我们肯定会讲的，通讯我们会讲，但是我们不着急。我们先来搞一个这个东西。

打开手册，我们看到里面确实有一个 `Mutex` 的结构体。结构体里面有两个非常重要的函数，一个叫 `Lock`，一个叫 `Unlock`。`Lock` 方法锁住 `m`。如果 `m` 已经加锁，则阻塞直到 `m` 解锁。`Unlock` 就是解锁。

那现在就拿到这个东西，在执行之前先来加锁。好比你上厕所之前，你来先把门、小门给它扣上：

### 全局锁为什么还不够完美

刚才我们给大家讲解了管道的引出问题。而且我们也用了全局变量加锁来解决，但是它不够完美。人家在这个地方写得非常的经典，这句话说得也很经典的，他说这是一个低水平的。

我总结了这么几句话，大家来看看有没有道理。前面使用的全局变量加锁同步来解决 goroutine 的通讯，可以，但不够完美。不够完美主要体现在哪里？

> **第一点**：主线程在等待所有 goroutine 全部完成的时间很难确定。这里我们设置了 10 秒，仅仅是估算而已。如果你不设置，大家都知道，其实一个结果都没有。大家再体验一下，如果我们这没有设这个休眠时间，其实你在遍历的时候什么都拿不到，因为瞬间就飘过去了。
>
> 这个是因为 time 没有用。如果我没有休眠时间，加锁没有任何意义，加了和不加没什么用。直接一执行，它一跑。你看，它执行了一点，但是执行到第 10 个的时候就没了，因为你没有等待。所以这肯定程序就错了，因为你才 10 个，人家 20 个呢。假设我 30 个呢？所以说这个肯定是不行的。
>
> **第二点**：时间设置了 10 秒，太长了、太短了也不好设置。如果主线程休眠时间长了，会加长等待时间；如果设置得短了，可能还会使 goroutine 处于工作状态，这样也会随主线程退出而销毁，你还没工作完毕就跑了。
>
> **第三点**：通过全局变量加锁同步来实现通讯，也并不利于多线程对全局变量的读写操作。有时候你不知道在哪处理。刚才同学们也看到了，虽然我们用加锁解决了，我们在这加了，你还得分析出来要在这加。如果不细心地方少加一个都会出问题，还不好分析。

所以第四点，种种原因我们就需要一种新的机制叫 channel。

> **总结**：不够完美；主线程等待的时间不好估算；全局变量实现同步并不利于多线程对全局变量读写；我们要新的一个机制。

### channel 的本质：有类型的先进先出队列

首先我们开宗明义。channel 即管道的本质就是一种数据结构，即队列。

我们很多同学学过数据结构，有些同学没有学过数据结构。那我这里不管你学过没学过，我简单说一下队列是什么玩意儿，它有什么特点。因为你要彻底明白 channel，必须对队列有一定的了解。

队列是个什么玩意儿呢？这是我的协程，我这可能有很多协程，至于有多少个我们不去管。这里有一个数据结构，我姑且把它称之为一个管道。管道你要这么去理解，长得跟管子一样。它像一个队列一样，就跟排队。

```text
              写 入 符  ←                    →  读 取 符

             ┌────────────────────────────────────┐
   10   ──► │  10   │   211  │   50   │          │ ──► 读走队头
   211  ──► │       │        │        │          │ ──► 再读下一个
   50   ──► │       │        │        │          │
             └────────────────────────────────────┘
                 ▲                        ▲
               队头                     队尾（新数据追加在这）
             最先放进来               后放进来
             最先被读走               最先被读走 = 先进先出
```

当你向这个管道里面放东西的时候，它就把这个新的数据扔在后面按顺序排队存放。所以它好像排队一样，排队买票。

从这个管道读的时候怎么读呢？它把第一个读出来。你第一个读出来过后，这个长度就变小了。待会儿你会发现一些非常奇怪的现象：**一旦读出来，它的长度变成 3 了，但是容量没有变化，容量还是那么大。** 于是这个就顶到前面去了，相当于说它会排到第一去。

紧接着假设要再取的话，就取的是第二个。如果再取一个，它会往前移动，它会有一个移动的过程。它一旦移动，这个长度也就变成了 2。

同样再取的话，就把这个取出来了，3 号往前面移动。再取，就到这儿来了。**如果再取，就报错了。如果你没有任何机制，直接取就直接给你报错，告诉你是一个 `deadlock`**，除非你有别的机制。

它的本质就是一种队列。队列我们后面会教大家写，队列的实现方式很多，可以用链表来实现队列，也可以用简单的数组、切片实现队列。

> **结论一**：数据是**先进先出**，它有个专业的术语叫 First In First Out，即 FIFO。如果你看到这个词，代表 First In First Out，先进先出。跟栈刚好反过来的，栈是先进后出。作为一个程序员必须了解。

> **结论二**：**线程安全**，这是它最牛的地方。之所以用管道，就是管道它本身是线程安全的。意思就是说，你在对管道读取的时候，我不管你有多少个协程在对同一个管道操作，不管是读和写，你放心大胆直接用，绝对不出毛病。这一点是由它的编译器在底层给你维护的。因此当多个 goroutine 访问时无需加锁，这说明 channel 本身就是线程安全的。

也就是说，假如后面我们这有 100 个，哪怕你有 1000 个、10000 个，你去操作我这个玩意儿，你也来操作，大家都来操作，欢迎操作。无论你怎么操作，它始终是能够维护管道的线程安全，因为它本身是有机制的。

至于它的机制是什么样子的，大家可以去看一下代码。其实它内部也是要有锁的机制在里面维护的。底层高手写的代码肯定是比较漂亮的，咱们有兴趣、有机会可以去看一下源代码，现在先把它基本常识弄懂了再说。

> **结论三**：管道还有一个特别明显的特点，它本身是**有类型的**。也就是说这个管道里面能放什么数据，你可以指定这个类型。比如说管道类型是 `string`，那你只能放 `string`；如果你这个管道是 `int`，那你只能放 `int`。

当然有同学说，假设管道又想放 `int` 还想放 `float` 怎么办呢？那你把这个管道声明成 `interface{}` 空接口也可以，它也可以接受这个事情。但一般来讲，咱们最好不要去混用，没有特殊情况下不要混用，因为你取的时候还要用类型断言才能取，也很麻烦。

### 管道的声明与 make

首先我们来看一下管道怎么去声明。它的基本语法是这样子的：`var`，变量的名称，就是管道名，然后 `chan`。这个 `chan` 是一个关键字，就不能改，后边是我们的数据类型，表示这个管道放的是什么样的类型。

```go
var intChan chan int
```

那么这个地方就表明这个 `intChan` 是用于存放 int 数据的。

第三点我们再看，除了这个东西我们能不能放 person 呢，放个结构体呢？也可以，你也可以放结构体。那么除此之外，我们还可以放结构体的指针，也都可以，以队列的形式来放的。

> **结论**：channel 是**引用类型**。channel **必须初始化才能写入数据**，即 `make` 后才能使用。就是你不能说我没有 `make` 我就直接往里面放，那是要出问题的。

如果说我们使用这个 channel 的时候，一定要用一个 `make`。你如果不 `make`，这时候会报错。

新建一个文件夹叫 `channeldemo`，新建一个文件 `main.go`：

```go
package main

import (
	"fmt"
)

func main() {
	// 声明一个存放 int 的管道
	var intChan chan int
	// 初始化：3 是容量，int 是类型
	intChan = make(chan int, 3)

	fmt.Printf("intChan 的值=%v\n", intChan)
	fmt.Printf("intChan 本身的地址=%p\n", &intChan)
}
```

> **小案例**：创建一个可以存放三个 int 类型的管道。看要求，3 是代表大小，int 是代表类型。

写完过后，我们来看看它到底本质是什么东西。看看这个 `intChan` 是个什么玩意。我们把这个值打印出来，看它到底是一个什么玩意。执行一把：

```bash
cd channeldemo
go run main.go
```

哦，我们一看，有点意思，我们发现这个家伙是一个地址。那你怎么理解这个管道呢？你完全可以这样理解：哦，这有个地址。那这个地址怎么理解它呢？就好像是在我们的内存里面，我们有一个这样的东西，有一个地址，这个地址有一个名称叫 `intChan`。

```text
   &intChan                intChan
  (变量本身的地址)        (变量里存的值)
      0xc000...             0xc000...        ← 两个地址不一样
                            │
                            ▼
                   ┌─────────────┐
                   │ 真正的队列   │  cap = 3
                   └─────────────┘
```

> **结论**：**因为它是引用类型，所以我们把一个 channel 传给另外一个函数，在那个函数里面操作的其实是同一个管道。**

### 写入：len 会变，cap 不会

向管道写入数据的时候非常简单。你刚开始可能有点不习惯，看到没有，这个箭头叫写入符，一个叫读取符，一个叫写入符。这个反正大家看一下也很形象，就是什么呢？数据向这个管道流入，屁股后面追加嘛。

```go
intChan <- 10
```

说老师，这是一个具体的常量，我们能不能写个变量呢？当然也可以。比如说你有个 `num`：

```go
num := 211
intChan <- num
```

这样也可以放。就相当于说放了两个数据。

再放一个，我们看一下它的长度。这个时刻我们来看看，输出看看管道的长度和它的 `cap`。`cap` 是它的容量。

> **结论**：容量一般来讲就是你在 `make` 的时候是多大就是多大，它**一般不会动态增长**。注意听，管道跟我们原先讲的 map 类型不一样，map 它可以自动增长，你这个管道可不能自动增长。说老师，我往里面加，加多了怎么办？加多了直接就爆了，爆仓了，直接报错。

```go
fmt.Printf("channel len=%v cap=%v\n", len(intChan), cap(intChan))
```

那么这个时候应该输出什么呢？应该是两个值，一个是 2，一个是 3。跑一个，因为我向里面追加了两个数据。

我们可以清楚地看到，它的长度是 2，它的容量是 3。为什么长度是 2？因为你加了两个数据。为什么容量是 3？因为你 `make` 就 3。注意，这个容量不会变化。如果你多了，它直接给你报了。

```go
intChan <- 50
```

这个时候你再运行，两个都是 3 了，长度和 `cap` 都是 3，已经到极限了。

> **重要注意点**：当我们给这个管道写入数据时，不能超过其容量。

```go
intChan <- 98
```

好，各位同学请看第 24 行会出现一个什么信息。走，我们看效果。可以看到报了一个非常恐怖的错误叫死锁：

```text
fatal error: all goroutines are asleep - deadlock!
```

放不进去了。所以说我们这地方要注意一下，这个管道是不能够不停地往里面装的，超过这个就报错了。

那有同学说老师，那这管道不就是最大只能放 3 个，那多了怎么办呢？

> **结论**：管道的价值是这样子的：**一边放一边取**。你只要取出来过后呢，你取一个又能往里面加了。

```text
   写满（len=3, cap=3）              取走一个（len=2, cap=3）
   ┌────────┬────────┬────────┐      ┌────────┬────────┐
   │  10    │  211   │   50   │  ──► │  211   │   50   │  ──► 又能塞新数据
   └────────┴────────┴────────┘      └────────┴────────┘
      再写一个 → deadlock                cap 始终是 3
```

### 读取：先进先出，取空了也 deadlock

那怎么办呢？取一个。

再说读，看看从管道中读取数据。读取数据什么意思呢？就是说你从这个地方取一个数据出来。当然你从管道里面取一个数据过后，里面的数据长度就会发生变化，就减了一个。但是容量不会减少，容量不会变。

第一种取法，就是说我把这个取出来的值交给另外一个变量。比如说我有个 `num2`：

```go
var num2 int
num2 = <-intChan
```

这个符号很形象，就是说我从这个 `intChan` 这个管道里面取出一个数据，推出来一个数据，交给 `num2`。

那你交出来过后呢，同学们想，我们推出来的这个数据应该是几？大家猜一猜。是 10，还是 211，还是 50？

> **结论**：显然是 **10**，因为我们就是先进先出嘛，先进先出。

```go
fmt.Println("num2=", num2)
```

取完了过后，我们再看一下它的大小，我们可以推一推。同学们看啊，你取出来一个过后，是不是这个时候又变成 2 和 3 了？因为你原先加完了过后是 3 和 3。你现在有三个数据，你取完一个过后，长度就变 2 了，但是容量不会变化。

那我们在取的时候也有一些限制条件，就是说你不能死劲地取。你如果取完了，还继续取，也会报错。

> **重要注意点**：在没有使用协程的情况下，如果我们的管道数据已经全部取出，再取，就会报 `fatal error: all goroutines are asleep - deadlock!`。

因为它已经没有了，你还要取，它就认为老在这儿不停地取，它死在那个地方了，对不对？死锁了嘛。取不出来没东西，它又不知道，你又不告诉它，它死锁了。

好，那怎么办呢？我来取几个。我再取一个 `number3` 吧，把它也取出来。再取一个 `number4`，取出来。大家看，3 也取了出来。

其实这个时候还不会报错。但是因为你没有用这个数据，肯定它是会报错的，他说你这两个没有使用过。

那这个 `number3` 就应该是 211，`number4` 应该是 50。可以看出，效果跟我们想的是一样的，211 和 50。但是你再取一次，完蛋了。

```go
num5 := <-intChan
```

在取 5 的时候，因为它已经没有了。因为你看这里它写得很清楚，长度已经变成 0 了，你再执行，报错了。而且写的是 `chan receive`，取的时候报错了。因为没有了嘛，你不停地取，没有东西了，它自己又没有保护机制。

说老师那怎么办呢？这个我们再说后面怎么解决。关于这一个管道的最最基本的读、写、创建我们就说完了。

## 管道的细节、六种读写案例，以及关闭与遍历
> 对应块：BLK103 | 覆盖分集：P274-P275 | 块标题（分集名）：《272_尚硅谷_管道的细节和课堂练习》

### 三条使用注意事项

我们接着刚才讲的内容继续。前面已经聊完了 channel 的初始化、读、写入、取出，现在在前面再做一个小小总结。

**第一，channel 中只能存放指定的数据类型。** 假如这里指定的是一个 `int`，你就不能往里面放 `10.9`。你一放就报错，它告诉你得很清楚：`constant 10.9 truncated`——不能截取成一个 integer，不能转成整数。这地方大家要注意这个细节。

**第二，数据放满以后就不能再放了，放满了再继续放，它会报一个死锁。** 但是——**如果从 channel 中取出数据，可以继续放。**

这一条很关键，因为 channel 最重要的价值就在这儿：**一边往里面放，一边从里面取。** 它就像一个管道一样——你们想，现实生活中一根水管，它是有水流在不停地流动的，**没有哪一个东西在里面静态不动。如果水在管子里一动不动，那就不叫水管子了，那叫水池了**，是不是一个道理？

我们要把什么样的数据放在这个管道里面呢？**就是这种流动的数据——一边往里面放，同时还要有另外一个人从里面去读。而这种需求其实特别多。** 如果这个机制一旦形成，它们之间的通讯机制也就自动形成了。

怎么从 channel 里取数据？

```go
<-intChan
```

这样就可以了。**注意，取的时候也可以不给它任何值**，这样写也可以。这句话就代表：我把管道里面的数据取出来扔了，我不要。可以的，不是说非要来一个变量去接收。有时候你就要利用这种特性——有个数据我不想用，先把数据扔出去就完了。**这也叫取，只是你没有接收而已。**

**第三，在没有使用协程的情况下，如果 channel 数据取完了，再去取就会报错。**

具体演示一下：一共放了一个、两个、三个，在放第四个之前，我先取了一把——这样就不会报错了，成功了。这就是我们说的这个细节。

### 六种读写案例：从 int 一路走到 interface{}

接下来看读写 channel 的各种案例。前面的案例已经有了，有些我就不重复写了，大家直接看幻灯片就应该能接受。

**第一个案例：基本数据类型的管道。** 创建一个最多可以存放三个 `int` 的 channel，演示存入 10、20、30 然后取出来。取出来依次是 `num1 = 10`、`num2 = 20`、`num3 = 30`，正确。

**第二个案例：存放 map 的管道。** 我们想创建一个存放 10 个 map 的管道：

```go
var mapChan chan map[string]string
```

大家想得到，如果这样存放，我们管道里面放的是 10 个数据，但每一个数据都是一个 map。**要很清晰地知道，这边有很多很多个 map——这是一个 map，这边又来一个 map，等等，一共 10 个。** 我初始化的是 10 个、20 个 key-value；创建 m1，把 m1 推送到队列里，再创建一个 m2，里面放的是"宋江"和"武松"，然后把 m2 也推送到 `mapChan` 里面去。

使用的方式跟前面一模一样，**只是大家要注意一点：如果你向管道里面放 map，在使用 map 之前先要 `make` 一把。**

**第三个案例：存放结构体。** 创建一个可以存放 10 个 `Cat` 结构体的管道，写入和读取都演示一下。创建第一个猫猫、第二个猫猫，把它们推进管道，取的时候"顺便取就完了"。**这个案例说白了就是给大家演示，我们这个管道是可以存放结构体实例的。**

**第四个案例：存放结构体指针。** 我们的管道也可以放指针，这个大家应该很好理解。

**第五个案例：存放任意数据类型。** 有些时候我们可能有这种需求——我们既想放结构体，又想放字符串。**可以，没有问题。** 这个时候要注意一个细节：**定义管道的时候应该是 `interface{}`，空接口。**

> **为什么空接口就可以了呢？因为任何数据类型我们都认为它实现了空接口——空接口什么方法都没有，你敢传，它就可以接收。**

**第六个案例是一道题**，我等下单独拿出来讲。

### 那道会报错的题：空接口取出来，为什么不能直接取字段

既然向管道里可以推送任何数据类型，只要把它的类型声明成空接口类型，那就没有问题。现在请大家看这段代码会输出什么——**认真的考虑，看一分钟，我找同学来回答。**

先看代码。这个我们姑且叫做"channel 练习"：

```go
package main

import (
	"fmt"
)

type Cat struct {
	Name string
	Age  int
}

func main() {
	// 定义一个可以存放任意数据类型的管道
	var allChan chan interface{}
	allChan = make(chan interface{}, 3)

	allChan <- 10
	allChan <- "tom jack"

	cat := Cat{Name: "小花猫", Age: 10}
	allChan <- cat
```

这个代码也可以用类型推导写成 `allChan := make(chan interface{}, 3)`。**在开发中这种写法应该更简洁**，我那样写更明确，就看你的习惯。下面这种在开发中用得比较多一点，简单嘛。

放三个数据：先推一个整数 `10`，再推一个字符串 `"tom jack"`，接着建一个猫猫推进去。因为有三个空间，够用。

**现在我想拿到这个猫猫。** 注意听，我**只关心第三个数据**，前两个我觉得很麻烦。有人会问：老师，我能不能有一种能力，我跳过前两个数据，直接拿这个猫猫？

**没有。你要这么玩的话它就不是队列了。** 你说我想取哪个就取哪个——那不行，那这样的话就不要用管道了。**如果你想取第三个数据，那你得先把前两个先推走。**

怎么推走呢？很简单，还是那个接收语句：

```go
<-allChan   // 扔掉第一个
<-allChan   // 扔掉第二个
```

因为你不想用，那你就干脆扔掉就完了。当然你也可以用一个 for 循环，待会儿我们再讲遍历。

现在你想要这个猫猫了。因为已经把它推进去了，所以用一个变量来接收：

```go
var newCat Cat
newCat = <-allChan
```

**大家注意，此刻这个猫猫的类型应该是什么？** 是 `Cat`，因为你先推进去再取的。

好，现在我们打印出从管道里取出来的这个猫是什么——先看它的类型，再看它的值：

```go
fmt.Printf("newCat=%T\n", newCat)
fmt.Printf("newCat=%v\n", newCat)
```

跑一下：

```text
newCat=main.Cat
newCat={小花猫 10}
```

**这里可就有意思了。** 从管道里取出来的这个猫，它确确实实告诉你是一个 `main` 包下面的 `Cat` 类型，值是"小花猫"。那你这样取出来，不就已经是个结构体了吗？

**但是我们发现一个非常有意思的现象。** 我们再取出这个猫猫的名字看看：

```go
fmt.Printf("cat.Name = %v\n", newCat.Name)
```

一执行，它就报错了：

```text
newCat.Name undefined (type interface {} is interface with no methods)
```

编译器说得很清楚：**它在编译这一层，仍然认为 `newCat` 是一个 interface。** 你这个类型虽然在运行的时候确实打印出来是那个结构体，但**从编译这个层面，它仍然认为这是一个接口**。它直接说 `type interface {} is interface with no methods`——interface 里面是没有字段的，所以它报错。

> **难理解吗？你明明看到它打印出来就是那个结构体啊？注意，这个打印是在运行的层面，它在运行的那一瞬间发现你是这个类型；但你在这儿取字段，是在编译层面，因此找不到东西。** 一个在运行时，一个在编译时，两回事。

**那怎么办？很简单——用类型断言。** 咱们已经学过类型断言了，转一下就完事：

```go
a := newCat.(Cat)
fmt.Printf("cat.Name = %v\n", a.Name)
```

**这个时候 `a` 才是真正的猫猫，真正的猫猫。** 这样写就没问题了。跑一下，小花猫取出来了。

> **结论**：从 `interface{}` 里取出来的值，**编译层面它仍然是 `interface{}`，要访问字段必须先做类型断言。**

### 关闭：管道的门一旦关上，就只能出不能进

刚才其实还有一个待解决的问题一直没有解决——**为什么没上来就解决？因为首先你得对 channel 有个基本认识，不认识这个东西你也解决不了。** 现在我们就来看 channel 的关闭。

使用内置函数 `close` 可以关闭这个管道。**当 channel 关闭以后，就不能再向 channel 写入数据了，但是仍然可以从该 channel 读取数据——这是它重要的一个特性。**

一旦关闭了，**只能读，不能写**。言外之意就是这个意思。你打开我们的示意图理解一下：**就好像在管道的屁股后面加了一个标志，加了一个类似 EOF 这样的标识，就代表说——别往里面加了，我不接收了。**

这个其实用一个生活的道理就很好理解：你们去一个地方买火车票，大家都排队。后面管理员发现买火车票怎么这么多人，**把大门一关**——是不是就没人能再进到队伍里面了，不让你买了。**但是前面排队的人是不是还是可以买完票走人呢？** 你不能说我把门关了，你们这还有十个人在排队，你们也别出去了，就跟着过吧——他还是可以买完票就走的嘛。

所以这么理解就不难了。**它相当于在这个地方关起来、加了一把锁的感觉，叫写锁，想写写不进去了。** 这个锁的机制有点类似于我们前面那个全局加了锁：我 `lock` 了，但没有 `unlock` 了，只有 `lock`，类似于这么一种动作。

我们来看一个关于 channel 关闭的小案例。新建一个文件夹 `channelclose`，里面新建 `main.go`：

```go
package main

import (
	"fmt"
)

func main() {
	intChan := make(chan int, 3)

	intChan <- 100
	intChan <- 200

	// 本身还可以放，因为容量是三个，但我直接关闭了
	close(intChan)

	intChan <- 300   // ← 这里会 panic
	fmt.Println("ok ok")
}
```

`close` 是一个**内置函数**，所以你在 `builtin` 包里能看到它。它写得很清楚：**内建函数 `close` 关闭信道。** 这就叫信道了，其实我们平常都叫管道，这个"信道"也不知道怎么翻译的，一会儿信道一会儿通道又变成什么玩意儿了。

它后面的说明是：**该通道必须为双向的或只发送的。它应当只由发送者执行，而不应当由接收者执行。其效果是在最后发送的值被接收后停止该通道。在最后发送的值从已关闭的信道中接收后，任何对其接收操作都不阻塞成功。** 也就是说——**这时候只能读，而不能写了。**

执行一下：

```bash
cd channelclose
go run main.go
```

```text
panic: send on closed channel
```

报了一个恐慌 `panic`，具体是第 13 行，正是我们往关闭的 channel 里写数据的那一行。

**但是读是没问题的。** 我们用一个 `n1` 来接收：

```go
n1 := <-intChan
fmt.Println("n1=", n1)
```

跑一下没问题，`100` 确确实实读出来了。**所以这个特性大家要有基本认识：channel 关闭以后，写会 panic，读照常。**

顺便说一句，取的时候它其实有两个值——一个是 `x`，这个 `x` 就是从里面取出来的值；另一个是 `ok`，代表**是否取出来了**。这种写法我们后面还会用到。

### 遍历：千万不要用普通 for 循环

关闭说完，接着说遍历。

**因为我们在做管道的时候是一个一个取的。假设它有 100 个数据，你一个一个取，那不累死了吗？你不能一个一个取，取死你。** 假设管道里放了 1 万个数据，你写 1 万行？不现实。**所以 channel 是支持遍历的，遍历主要用 `for range`。**

为什么不用普通的 for 循环？**最大的问题是它的长度会变化。** 你取一次，长度就变化一次，这个不好确定。

打个比方：你往管道里放 100 个数据，用普通 for 循环，你会**只取出来 50 个数据**。为什么？因为你取一次长度减一次，再取一次再减一次，刚好取 50 个就没有了。**那 50 个数据怎么没有了？——因为长度会变化。** 有些同学就搞不懂：长度不是 100 吗？结果发现只取了 50 个。

所以有两种错误写法要避开：

- **不能写 `for i := 0; i < len(intChan2); i++`**——`len` 会变，一共生效一半；
- **也不能写 `for i := 0; i < cap(intChan2); i++`**——**容量也不一定代表它真实有多少个数据**，所以容量也不能用。

> **结论**：**遍历管道时不能使用普通的 `for` 循环。** 要用 `for range`：

```go
for v := range intChan2 {
	fmt.Println("v=", v)
}
```

这个方法相当于从管道里依次取出这个值——**取的时候也是先进先出。**

这里还有一个要点要讲清楚：**管道本身是队列，它没有所谓的下标。** 这就是为什么它取的时候不能说我跳过什么取，它必须按顺序取；**它返回的时候也不会返回所谓的下标**，所以 `for range` 出来的就只有 `v` 这一个值，没有别的，所以你这样写是没问题的。

我们做个完整的演示。因为数据太少了，我写稍微多一点：

```go
intChan2 := make(chan int, 100)

// 存放 100 个数据
for i := 0; i < 100; i++ {
	intChan2 <- i * 2
}

// ✘ 错误示范：只能取到 50 个
// for i := 0; i < len(intChan2); i++ { }

// 用 for range 遍历
for v := range intChan2 {
	fmt.Println("v=", v)
}
```

放进去的数据是 0、2、4……最后是多少，大家可以自己猜。

**现在关键的地方来了。如果我这样写——前提是我要先把这个管道 `close` 掉。**

如果你不关闭会怎样？**你会发现它取到最后，100 个全部取完了，它还傻乎乎地再去取，就报错了。** 为什么？因为你没有关闭这个管道，最后没有那个标志，**它以为还可以取，就傻乎乎在那等；等久了，发现这是一个死锁。**

跑一下你就看到：取到 198 的时候其实已经全部取完了。你想，我们放了 100 个，最后一个是 $99 \times 2 = 198$。但是取的时候它很郁闷，它发现到最后一极取不出来了。

```text
fatal error: all goroutines are asleep - deadlock!
```

**数据确确实实是全部取出来了，但如果遍历时 channel 没有关闭，就会出现死锁错误。**

那这种遍历怎么办？**同学们一定要记住：一定要关闭这个管道。**

```go
close(intChan2)
```

搞定。关闭管道就没问题了，它会把所有数据取出来，然后正常退出。

> **结论**：遍历时——**如果 channel 没有关闭，则会出现死锁；如果 channel 已经关闭，则会正常地遍历数据，遍历完后退出遍历。**

**这一点是特别特别有用的东西。** 因为这样子就可以达到一个用管道来解决通讯问题的目的：**我怎么知道你这一个协程做完事情了呢？** 我可以在这个协程干完事过后 `close` 一下这个管道；然后我这边遍历出来，一旦遍历退出了，我就不阻塞了——**我就知道等到什么时候这个问题可以解决了。**

**原先我等三秒、五秒我不确定，现在我可以确定了。** 当你的协程把事情做完了过后，你顺带把那个管道一关闭，我在这个主程序里面一看，你退出了，我也就退出。

关于 channel 的遍历和关闭就讲到这里。下面我们来解决一个综合性的问题。

## 协程配合管道：一条能自己宣布结束的流水线
> 对应块：BLK104 | 覆盖分集：P276-P277 | 块标题（分集名）：《274_尚硅谷_协程配合管道的综合案例》

我们前面讲了那么多关于管道的知识点，其实就是为了解决问题。我们讲的它的定义、它的特点、它的关闭、它的遍历，其实都是为了一样、一个问题在服务，就是最开始提出来的那个问题。

现在我们已经有一点功力了，就是我们在少林寺学了一个基本功，挑了一年水，然后砍了两年柴。现在我们可以干什么呢？打人去了。

### 需求：写一个、读一个，还得知道什么时候收工

请完成一个 goroutine 和 channel 协同工作的案例。也就是现在我们要把协程和 channel 合并在一起，让他们一起去作事情。具体要求是什么呢？

- 第一个要求，开启一个 `writeData` 协程，向管道 `intChan` 写入 50 个数据。
- 第二个，开启一个 `readData` 协程，从管道 `intChan` 中读取 `writeData` 写入的数据。
- 第三个，主线程需要等待 `writeData` 和 `readData` 协程都完成工作才会退出。

这里面就有几个关键点，我们要解决前面提出的一个痛点：**我等多久？** 显然，这种绝对不能再用 `sleep`。而且你也不能一点都不处理，因为你一点都不处理，主线程噌地一下就跑了。你 50 个数据它还没写呢，直接就跑了。

所以这个地方呢，我们就会引出一个什么呢？管道。

### 思路分析：三个管道，或者两个

我先给同学们说一下我要解决它的问题的思路。注意听讲，这个思路很很重要。思路分析完了过后，同学们，那我可以说，你只要把这个思路分析完了，后面只要涉及到管道和 channel 的一个通信，大家心里面就不会那么紧张了。

第一个协程我们叫做 `writeData`，第二个协程我们叫 `readData`，一读一写嘛。另外这两个协程没有了，因为我们现在不起那么多，就起这两个协同工作的。

你要这样理解：你的主线程是一个很长的线。它在一个上下文环境的时候，比如说这有一个 P，有了一个上下文环境，然后由这里面跑出去，创建了两个协程。

```text
              ┌──────────────────────────────────┐
              │           主线程（进程）            │
              │  创建两个管道 → 创建两个协程 →      │
              │  然后一直守着 exitChan 不撒手       │
              └───────┬──────────────────┬────────┘
       go writeData  │                  │ go readData
                      ▼                  ▼
              ┌────────────┐      ┌────────────┐
              │ writeData  │      │  readData  │
              └─────┬──────┘      └──────┬─────┘
                    │  写                 │  读
                    │                     │
       ┌────────────┴─────────────────────┴─────────┐
       │                 intChan                     │
       │        （容量 50，先进先出，一边写一边读）    │
       └────────────────────────────────────────────┘
                                                     │
   readData 读完 50 个之后，顺带报个信：                │
                                                     ▼
                                          ┌─────────────────┐
                                          │    exitChan     │
                                          │  写入 true 然后  │
                                          │     close()     │
                                          └────────┬────────┘
                                                   │ 主线程循环读
                                                   ▼
                                          读不到东西了 → break → 退出
```

那这里至少要创建两个管道。有一个管道呢，这个写的管道都往这一个地方写，这根管道我们给取个名字叫 `intChan`。注意听啊，`intChan`。那么这个写的管道是往里面写，而读的管道呢是读，所以它呢应该换一个方向。

就是说这个协程这个管道，协程一这个管道呢，它是拼命的往里面写，而我这个 read 管道是读，**它们是同时工作的**。没有谁先谁后，可能是这边一边在写，而另外一个同时在读。**不是说你写完了我才读，不是这样子的。**

那有一个问题，我怎么知道你们把这个事干完了呢？说你读完了、写完了，我怎么知道呢？

好，同学们，我问大家一个问题。读这个数据，这个读他是不是他自己是很清楚的？他说我要读 50 个，那我只要保证我能读 50 个，就代表结束。

那么这个时候呢，我们有一个办法这样解决这个问题。就是说我呢在这个地方再设计一个新的管道。对，刚才有同学已经有思路了。就是说我再新设计一个新的管道。这个管道叫什么名字无所谓，比如说我们叫退出管道。

这个管道里面呢是放布尔类型的，或者放个什么数都行，就 int 也无所谓。我只需要这个 `readData` 在它读取完 50 个数据以后——**注意啊，这有一个前提**——让它向这个管道里面写入一个值，并关闭这个管道。

比如说他在里面写一个布尔值吧，写入一个 `true`，然后呢并关闭。它只要写完了它就关闭。

> **机制**：这个管道事先就有。然后呢我的代码它不是当它把这个 P 执行完了过后它继续往下面执行，它是不是还有代码吗？然后呢我在这里有一个 `for` 循环，注意听，我在这里 `for` 循环去读取这个管道。因为这个管道都是在主线程创建起来的，就是说我在这里一直读。只要我这没有退出来，我就一直读取，直到你关闭过后，我把这个读完了，我才退出来。

这边呢它一直在这儿读，它只要读到一个 `true` 就代表我也该退出来了。因为你不往里面写，我读不到，读不到我就阻塞在这个位置。

### 代码落地

首先是两个管道必须在主线程里面创建。因为协程读的这两个管道，主线程读的也是这个退出的管道，这个就没问题，因为它是共享的。

我们刚才讲过，管道它是引用类型，所以说你在不同的栈里面，其实用的是同一个管道，这个很重要。

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	// 创建两个管道
	var intChan chan int
	intChan = make(chan int, 50)

	exitChan := make(chan bool, 1)

	// 开启两个协程
	go writeData(intChan)
	go readData(intChan, exitChan)

	// 主线程在这里一直盯着退出管道
	for {
		v, ok := <-exitChan
		if !ok {
			break
		}
		fmt.Println("主线程收到退出信号，v=", v)
	}
}

func writeData(intChan chan int) {
	for i := 1; i <= 50; i++ {
		fmt.Println("writeData 写入数据", i)
		intChan <- i
		time.Sleep(time.Second)
	}
}

func readData(intChan chan int, exitChan chan bool) {
	for {
		v, ok := <-intChan
		if !ok {
			break
		}
		fmt.Println("readData 读取到数据", v)
		time.Sleep(time.Second)
	}

	// 任务完成，通知主线程可以退出了
	exitChan <- true
	close(exitChan)
	fmt.Println("readData 任务完成，通知主线程退出")
}
```

`writeData` 需要知道一个 int channel，我才能往里面写嘛，里面这个数据无所谓了，因为这个管道有多大它事先就应该写好了。也可以，就你直接在这个地方去 `go` 一个匿名函数也可以，所以我现在还是写稍微简单一点，编写函数相对清晰一点嘛。

`readData` 为什么要这个退出管道呢？因为你没有这个管道我不知道从哪读啊。我还得有个退出的一个管道，因为我写完了我相当于向这个管道发个消息说：对不起，我做完了。那么它的类型呢是一个布尔类型。

### readData 里那个 close 到底有多重要

我直接把它关闭这个管道，是不是？大家知道我什么意思吧？就是说我这样 `close` 这个，就是说当我把 50 个写完，我就关闭这个 channel。就是说我写完了，我关闭了，**我并不影响你读**。这个能理解我意思吧？就是我写了 50 个，我的任务就完成了，我关掉。关闭的好处是我在这个地方可以用 `for` 循环去读啊。

怎么读呢？我用这种换一种方式，和前面本质是一样的。我就直接读这个东西，一个是 `v`，一个是它的那个 `ok`。大家还记得这种写法也会返回两个值。

`v` 呢就是取出的一个值，`ok` 代表到底取没取成功。一旦关闭读到关闭的时候，它就不成功了。所以说我这做一个判断，如果 `ok` 它取不出来了，我就 `break`。

那这样它不停地读不停地读，等到它一 `close`。**它一 `close`，它并不会退出**，它是不断地取，取到最后它才会退出。刚才我在讲那个基本原理的时候，大家想一想，说你这关闭并不影响我读。我什么时候退出呢？我把你这 50 个数据全部读完了，我才 `break`。

所以这里 `close` 显得很重要，如果你不 `close` 啊同学们，这个地方就会发生一个死锁。所以一定要 `close` 掉。

### 为什么必须要有 exitChan

好，同学们，现在这两个都在工作。如果现在我们不做处理啊同学们，你会发现读的这个任务瞬间秒闪，直接就出去了。

假设我在这主函数没有做任何工作，请问这段代码你们预计它会出现一个什么情况？是不是基本上就是秒闪，一下就退出了？

因为它现在确实起了两个协程准备做这个事，一个往里面写一个，但是因为你这没去管它，直接就这个主线程就退出了。**主线程一退出，你两个协程也没命了。** 就相当于说什么呢？说有一个主体都消失了，那你这个附在它身上的也就没有了。就好像鬼附身，那鬼它得附在人的身上嘛，人都没有了，它得重新找家呀。

```bash
cd channelapply
go run main.go
```

直接是秒闪，就啥都没看到。

"老师，那我用 `sleep` 呢？" sleep 也可以搞定，但是肯定不是我们想要。你看 sleep 呢，比如说我来乘一个 10 秒，你们可以看到数据它也能完成，10 秒过后退出，这也可以。但是这个 10 秒很明显就不是我们希望的。因为我们现在就是要解决问题。

好，我们现在已经搭好了，我们看这个传统方法还是可用。跑，你看这个数据。你看，是不是这个数据已经处理完了？已经读完了。老师，写的数据在哪儿呢？写的数据我们没打这个信息啊，我该打印出来啊。写的时候我也可以把它打一下。

> **小提示**：如果你不加 `Sleep`，输出会全挤在一起，因为太快了。让它休眠一秒再写、读的时候也一样，这个时候一定是个**交叉**的，一边写一边读，一边读一边写。

好，现在问题已经解决了。最后一个问题：老师，写 10 秒显然不行。我们搞了这么久就是要解决这个问题。

```go
	// 主线程在这里一直盯着退出管道
	for {
		v, ok := <-exitChan
		if !ok {
			break
		}
		fmt.Println("主线程收到退出信号，v=", v)
	}
```

怎么阻呢？我就这样写，我就去从这个地方取，那就是 `v`，还有一个 `ok`。如果你要那样的话，你得用 `for range` 才行，这个不然的话推不出来。也可以用 `for range` 遍历 `exitChan`。

> **小提示**：`v` 如果没有用，那就不要它了，忽略掉就好，没有用就不要用。

好，同学们看，现在我们实际上啊，这个就很完整。你会看到它完成这个事情就直接按照实际情况退出，而不是在那傻傻地等。

好，写、读、写、读。好，这个时间太太长了啊，我把这个 `sleep` 关掉吧。因为 `sleep` 这个等的时间太长，把它关掉。

关掉，我们来看一下这个时候。数据首先我要保证数据全都有了。`time` 包因为我不用了是吧？好，你们这个时候看到速度很快就完成，同时呢，我们在这个地方也没傻等。

> **结论**：完全是一边读一边写，读读写写，然后呢最后读完了过后退出来，没有等，而且呢数据也是正确的。

### 只有写没有读：死锁从哪里冒出来

第二个应用实例叫阻塞。阻塞是个什么样的情况呢？

在这里，如果说我们把前面写的这个 `readData` 注销——如果我们把这个注销，程序会怎么样呢？这个只是让大家先思考一下。

它应该会出现这么一个情况：其实你这个 `writeData` 只有往里面写的过程，但是**没有人取**。

没有人取会出现一个什么情况呢？就意味着你在这个地方傻傻地往里面扔，但是没有人取。你想一想，当我们存入的这一个数据超过了你的这一个——我们这儿刚好是 10，我把这个调成 10——你不停地往里面写，但是你只有 10 个，等到你又不取，那么最终这个管道会因为你的数据多了、往里面放的数据多了、你又没有取而阻塞。

> **结论**：阻塞在哪个位置？阻塞在往管道里放数据的这一行。

所以这就是为什么如果我给的这个容量就是 50，那可能是刚好就放进去，它没问题。但是我们给的管道跟你放进去的数据量不匹配，就是说你的管道的容量小于你要放进去的数据，但是你又不取的话，它就会阻塞。阻塞它就会报一个 deadlock。

也就是说：**如果只向管道里面写数据而没有读取，就会出现阻塞而发生一个 deadlock。** 原因是 `intChan` 的容量只有 10，而代码会写 50 个。

那有些同学就说，老师，如果它写得快、读得慢呢？没问题，这个它本身是会有种机制的。比如说你写得很快，但是它读得慢，它写的时候它就会在这儿阻塞。**它只要阻塞，编译器会发现：虽然我会阻塞，但是有一个人在不停地取，这个就不会发生死锁。**

死锁是什么问题？是说编译器底层会进行一个分析，它发现我这个地方在不停地写，但是**没有任何一个协程去读**，完蛋。但是如果它发现有一个协程在慢慢地读，无所谓。

### 写得快读得慢，为什么不死锁

那我刚才就把这个 `readData` 进行了一个注销。来，我们来运行一下。

```bash
go run main.go
```

果然发生了一个非常经典的错误，叫 deadlock。**原因是在第 47 行**——第 47 行是主线程那一块。你这边有一个接收的地方死锁，因为你没有关闭嘛，你不关闭它也会发生一个死锁。因为你没有机会关闭，它发现永远没有机会，它永远没有机会，所以说 47 行会发生死锁。

同时在 `writeData` 里面第 12 行也会发生一个死锁，因为编译器会分析，它说完蛋，没有机会，永远出不去。

> **注意**：如果编译器在运行时发现一个管道只有写而没有读，则该管道会阻塞。

那有些同学说，老师，假设我这就开了 50 个，我也写 50 个，但是有一个地方没有读怎么办呢？它会不会阻塞在那？写都写完了还阻塞个屁啊，对不对？写完它管你写，阻塞啥？只是你没有读嘛，没有读的话最后它就至少阻塞不会发生在这里，可能是其他原因、其他的问题了。

现在我们把 `readData` 打开，我读的时候是每隔一秒读一次，我不休眠。写的时候是蹭的一下就写进去了。来跑一下：

**完全没有问题。** 你看，写的时候是蹭的一下写进去了，而读的时候是每隔一秒我读一次，显然这个时间它本身是不同步的。

你们可以看到，因为它前面先写了 10 个我才开始读的，那这个时候它就迫于这种不同步机制，**你写也只能变慢了**。因为我只能读一个，你才能写进去。

> **结论**：你本质写得很快，但是你没有机会写——**因为我没有读**。所以你仍然不会报错。后面还留了 10 个，等到你全部写进去，里面还有 10 个，读、读、读，最后读完了过后关闭退出，正确。

很多同学在学 Go 协程的时候容易蒙圈：同学们说我取的时候是不是一定要怎么怎么样。大家理解了这个机制了过后，大家再回头想一想小夏写的代码——小夏写的代码是，他蹭的一下先把那个地方……这也是另外一个问题，他说也可以调。其实你共用的一个数据通道是可以不用开那么大的。

> **结论**：这个阻塞是**有效阻塞**。它会阻塞在那等你，干一个我进一个。这个阻塞它是有意义的阻塞，因为它觉得我等一段时间，等一秒或者等两秒，我就可以让它这个管道动起来。**如果它发现我在这等是没有希望的，它就会报 deadlock。**

### 编译器怎么知道有人在读

至于说它是怎么知道的呢？写编译器的人不是吃饱了没事干的，人家是要做底层分析的。它运行的时候，编译器的底层还是在不停地维护上下文。而且你会发现，只要你没有略写，它不是要等几秒，马上就能分析出来。

就好像咱们去上厕所，你进去了过后，你知道上厕所的人肯定要出来的，只是时间长短的问题。如果你知道这个人上厕所等他肯定要出来，你肯定不着急，因为肯定要等，对不对？所以说把这个地方一定要搞清楚。

> **一定要记住这句话**：**写管道和读管道的先后位置无所谓，但是一定要让它对应起来。**

### 本讲提到的题目

**课后第一题：一写八读，再汇总**

- 启动一个协程，将 1 到 2000 的数据放到一个 `numChan` 里面去；
- 启动 8 个协程，从 `numChan` 取出数据。取出来是一个 $n$，计算这个 $1 + n$ 的值，并且把它存放到一个叫 `resChan` 的 channel 里面去；
- 也就是说最后这个结果呢，全部都是在一个管道里面；

**解析依据**：这一题的骨架就是上面正文里那套 `writeData` / `readData` / `exitChan` 的三段式思路——只不过写入方换成了"1 到 2000"，消费方从一个 `readData` 换成了 8 个而已。真正要新增的思考点是：8 个协程都干完了，主线程靠什么信号收工？答案仍然是 `close`——某一个协程写完退出管道并不合适，正文里已经点明"多个协程不能同时 close 一个 channel"，所以退出信号的发送方式必须重新设计。这一点正文没有给实现，作业要求各位自己想清楚。

**课后第二题：协程加 channel 配合排序写并写入文件**

**扩展题**：把一个全部给我扩展成 10 个，就用 10 个协程在写，每一个 1000 个数据写到 10 个文件里面去；还有，让 10 个 `sort` 协程从 10 个文件里面读取 1000 个数据，然后排完序，最后写到 10 个结果文件。

## 协程求素数：把一个老问题用管道串起来
> 对应块：BLK105 | 覆盖分集：P278-P279 | 块标题（分集名）：《276_尚硅谷_协程求素数的思路分析》

### 开篇就埋下的伏笔

我在这一章的第一页幻灯片上写过一句话：**为什么需要协程**。那句话底下跟着一个问题——**哪些是素数**。

这个问题从开篇挂到现在，一直没解。今天我们终于把它解开。而且这个例子相对前面讲的那些要综合一些，但也更有意思，因为它能把前面零散讲过的管道、协程、阻塞、关闭这些点全部串起来。

> **需求**：统计 1 到 20 万的数字中哪些是素数。

不过实际演示的时候我把它调整成 8 万了。20 万在我机器上跑，咱们估计都得该吃中午饭了，所以我不跑 20 万，我改成 8 万。后面代码里再缩到 80 做验证、再放到 8000 跑一遍，都是同一套代码。

### 第一种思路：老老实实循环

第一种思路就是传统方法，用一个循环逐个判断每个数是不是素数，这当然没问题，功能上是完全正确的。

但同学们可以想一想，它**不能充分发挥多核的优势**。因为它就是一颗 CPU 在那儿傻乎乎地算，很慢。

### 第二种思路：并发加并行

第二种思路就是用并发，或者并行，也可能并发加并行。

先把这两个词分清楚，因为后面要反复用：

> **定义**：多个 CPU 同时运行，叫**并行**；一个 CPU 交替地对多个协程做片段化操作，叫**并发**。

实际工作中，我们常常是**并行加并发**的混合模式——用多个 CPU 跑，每个 CPU 上又有多个协程在轮流切换。

这一版我把统计素数的任务分给**四个协程**去做。为什么是四个？因为我逻辑上的 CPU 刚好四颗，我就分配到四颗去，这样构成一个完整的全并行模式。如果我写八个，那就是并行加并发——八个协程挤在四颗 CPU 上，每颗 CPU 上得切两次。

### 思路分析：三个管道撑起整个流程

思路分析这一步很重要，比代码本身重要得多。下面是我画出来的整张图。

```text
          +-------------------------------------------+
          |              main goroutine               |
          +-----------------------------------------+
                            |
              +-------------+-------------+-------------+
              v             v                           v
   +----------+      +----------+      +----------+
   | intChan  |      | primeChan|      | exitChan |
   |   int    |      |   int    |      |   bool   |
   |  cap1000 |      |  cap1000 |      |  cap 4   |
   +----------+      +----------+      +----------+
        |                 ^                  ^
        v                 |                  v
   +----------+      +----------+      +----------+
   |putNumber |      | prime x4 |      | main read|
   +----------+      +----------+      +----------+
```

#### 存放数字的 intChan

先看这张图的这根线，这是主线程。它要做的事是"把这些素数统计出来"，所以第一步得先设计一个管道。

这个管道我取名叫 `intChan`（叫 `numberChan` 也行，我习惯 `intChan`）。它干什么呢？**专门往里面扔 1 到 8000 的数**。

怎么扔？我会启动一个协程，名字姑且叫 `putNumber`，这是很经典的一个名字。它干的事就一件：**把数据往 `intChan` 里写**。

> **提示**：为什么开 20 万我就说太费劲？因为念数字费劲，也因为要演示、要跑很多遍。这里同样的道理——这个管道估计开这么大就可以了，我不把它开大，就开 **1000** 个。我故意这么写：我不开 8000，也不开 20 万，我就开小一点，**因为我想让它流动起来**。容量小一点、有阻塞，读写才真的交互起来，才看得出管道在干什么。

#### 存放结果的 primeChan

有了往里放的，任务才刚开始。人家要的是统计素数，所以你还得**起四个协程去完成统计素数的任务**。

素数的单词是 `prime`，p-r-i-m-e，所以这四个协程就叫 `primeNumber`——大家可以去查一下英文，`prime` 就是素数的意思。

这四个协程不停地从 `intChan` 里取数，取出来一个就判断一次是不是素数。它的任务其实是两件：**取出这个数**，然后**计算它是否为素数**。

问题来了，**如果判定是素数怎么办**？那就再把它放到另外一个管道里去。

> **易错点**：为什么不放回 `intChan`？放回去不就混在一起了吗？你本身这个地方是产生数据、去读数据的，你又把它放进去，那不就死掉了。

所以图上必须还有第三个管道。这个管道我叫 `resChan` 或者 `primeChan`——这里面的数据，就真的是素数了。

它开多大？这要看经验。**它的容量必须真实体现出 1 到 8000 里到底有多少个素数**，开小了放不下。那么开多大呢？1 到 8000 的素数应该不会超过 1000 个，我们姑且放 1000 个，先保险一点。

有同学问：能不能开小一点，一边写一边读？

> **提示**：这个优化后面再说，现在不好估算。我们先把容量整大一点，让它先跑通、跑对。

#### 判断素数的逻辑

素数是什么？除了 1 和它本身，别的数都不能整除它。

那代码里就很好写：拿到一个 `num`，我先乐观地假设它是素数，把 `flag` 置为 `true`；然后 `for i := 2; i < num; i++`，只要 `num % i == 0`，说明找到了一个能整除它的数，它就不是素数，把 `flag` 置为 `false`，然后立刻跳出内层循环。

扫完一遍，`flag` 还是 `true`，就说明整个扫描过程中一次都没进去——它确实是个素数，把它扔进 `primeChan`。

### 最关键的一环：exitChan 退出机制

这是整个思路里最要紧的地方，也是我和很多同学思路不一样的地方。

先回到那个问题：**我怎么知道什么时候才算干完了？**

`primeNumber` 这个协程一直在不停地从管道里取东西，它总有取完的时候。取完之后呢？它怎么知道可以退出了？

`putNumber` 那边倒是好办，它是个 for 循环，放完 8000 个数据后循环自然退出，**退出的时候把 `intChan` 关掉**。这样取的那边也是个 for 循环，管道一关闭，`ok` 就变成 `false`，它自然也就退出来了。

那么问题来了：**四个 `primeNumber`，哪一个退出来才算整个事做完了？**

有的同学是"判断这个结果是不是搞定了再退出来"——只要整体结果没出来，我就不许退出。

> **结论**：这样效率不能充分发挥。因为有可能某一个协程已经把事情做完了，但因为另外几个还没做完，你硬拽着它不让退出，它还在那儿空转。

所以我换了机制。我再写一个管道，名字每个人叫法不一样，我姑且叫 **`exitChan`**，退出协程用的。

这个管道开四个，容量就是 4。

机制是这样的：`primeNumber` 协程不停地干活，它总有一个时间点会**取不到东西**了。取不到怎么办？它就往 `exitChan` 里写一个数据，比如一个 `true`，意思是"我完成了，我已经完成了"。写完它就可以退出了。

**我完成了，我不管你有没有完成，我的任务完成了，我就往退出通道里写个东西，我就走了。**

主线程这边也一样，反过来从 `exitChan` 里读。最后如果四个 `primeNumber` 都完成了，那这个管道里就正好有四个 `true`。

```text
   primeNumber 协程             exitChan              main 主线程
   （做完了就走）                                    （只数个数）
        |
        +-- 取不到 intChan 了 -----------------------+
        |                                             |
        +--> exitChan <- true  ------------------+    |
                                                  |    |
        primeNumber 协程（第二个）                  |    |
        +-- 取不到 intChan 了 -------------------+  |    |
        +--> exitChan <- true  -----------------+    |    |
                                                    |    |
        primeNumber 协程（第三、四个）…              |    |
        +--> exitChan <- true  x2 -------------+      |    |
                                                    v    v
                                                  exitChan
                                                  取出 4 个 true
                                                        |
                                                 全部工作完成
                                                    |
                                                 close(primeChan)
```

**这样设计的好处是什么？**

协程之间的退出**互不依赖**。我不能依赖你，你也不要依赖我。我们做完了，我管你醒不醒，我管你完没完，我就走了。我做完了就往一个管道里说"我做完了，拜拜"。

> **易错点**：如果你没做完，我也退不了，我还得在那儿傻乎乎地判断你是不是等于一个值——这不合理。

而且最关键的是：**主线程的退出依赖于 `exitChan` 有没有被取完，而 `exitChan` 有没有被取完，依赖于四个协程是不是都往里面写了标志。** 这是一个互相依赖的关系，闭环就成立了。

也就是说，上面所有工作都做完了，主线程才能退出。主线程这边一定有个 for 循环，就干一件事：不停地 `read` 这个管道。只要我取出了四个 `true`，就说明整个任务全部都做完了——甚至说明 `primeChan` 里的数据也全部正确，因为只有四个协程都写了 `true` 才会有四个。

### 代码实现

思路有了，代码就快了，最多五分钟。我们打开 `chapter16`，新建一个 `goroutineapply` 文件夹，这就是我们的 03 案例，新建 `main.go`。

#### 三个管道

```go
var intChan chan int
intChan = make(chan int, 1000)

var primeChan chan int
primeChan = make(chan int, 1000)

var exitChan chan bool
exitChan = make(chan bool, 4)
```

类型是放整数的，大小随意。`intChan` 放 100 个也行，只要有读，它就不会阻塞在这儿。

`primeChan` 要稍微大一点，先来个 1000。做完之后我们其实也可以把它弄小点，做完了直接马上取出来放到一个 map 里面，但先做大一点保证放得进去。

`exitChan` 是 `bool` 类型的，也可以是别的类型，只要是 4 个就行。

> **提示**：这里一定要确定是 4，因为我们目前就开 4 个协程。那有同学问：假设我将来要开 4 万个，难道这里也这么写吗？

那当然要用别的思路来解决了。**不能说一招走遍天下**，我讲一个方法你就全都拿这个思路去套。你开 4 个，那这容量就写 4；你也可以动动脑筋，开 4 个但里面不是 `bool`，换个 `map`，用 `len()` 取它的大小，不也是一样的吗？

#### 生产者：putNum

```go
func putNum(intChan chan int) {
	for i := 1; i <= 8000; i++ {
		intChan <- i
	}
	close(intChan)
}
```

管道是引用类型，我讲课的时候开宗明义说过这一点，所以这里传进去的管道和外面那个是同一个。

就是个简单的 for 循环，往里扔 1 到 8000。扔完了，循环退出，我关闭它。

```go
go putNum(intChan)
```

完事。大家可以想象到，这个协程这时候已经开始工作了。

> **易错点**：**关闭不是别人才能读的前提**。在还没有关闭之前，这几个协程就已经可以开始工作了。千万不要理解成"我在 `primeChan` 去读 `intChan` 的时候，人家必须关闭了才能读"。不是。没关闭我一样可以读。关闭的作用只是——读到那个标识位的时候，我好退出。所以你会看到，你在往里面放的时候，其实我这边已经开始工作了。

#### 消费者：primeNum

```go
func primeNum(intChan chan int, primeChan chan int, exitChan chan bool) {
	var num int
	var flag bool
	for {
		num, ok := <-intChan
		if !ok {
			break
		}
		flag = true
		for i := 2; i < num; i++ {
			if num%i == 0 {
				flag = false
				break
			}
		}
		if flag {
			primeChan <- num
		}
	}
	// 做完了，写一个标志到退出管道
	exitChan <- true
}
```

这个函数必须传三个管道进来：

- 第一个，你得告诉我**从哪儿取**；
- 第二个，你得告诉我**结果放哪儿**，所以 `primeChan` 得传进来；
- 第三件别忘了，你做完之后往退出管道里还要写个 `true`，所以 `exitChan` 也得传进来。

注意管道本身是线程安全的，所以往里扔一个 `number` 就完事了。

#### 退出时的那个"关键"

跳出整个外层 for 循环，就意味着当前这个协程工作完毕了——它已经取不到东西了，它完成作业了。我们一共开了四个 `primeNum`，这就说明有一个 `primeNum` 协程完成工作了，退出掉了，取不到东西了。

但是这个时候退出，**我能不能够把这个管道关闭？这是关键。**

> **易错点**：你退出来的原因是因为你取不到了，但**并不意味着别人取不到**。别人可能正在处理。所以这个时候你不能马上关闭它。你要做的是另一件事：告诉这个管道"我已经完成了"就行了，你不要管别的事。**安全起见，这里不能关闭管道。**

于是就向退出的管道写入一个 `true`，告诉它我完成了。

#### 启动四个协程

```go
for i := 0; i < 4; i++ {
	go primeNum(intChan, primeChan, exitChan)
}
```

取四个协程，让它们作用在四个不同的 CPU 上。这里我起的是四个 `primeNum`，它们已经开始同时工作了。

#### 主线程：必须阻塞等待

但别忘了，**如果不做阻塞处理，所有的协程就像白干了**。因为不做处理的话，主线程"蹭"的一下就跑了，你这还没干完呢，什么事没干就跑路了。

而且大家发现没有，`primeChan` 到现在还没有关闭，它实际上还处于打开状态。如果你打开着就要退出，只能依赖它的长度，这样也不划算。

所以我们还要做一件事：**怎么在这里等待它把所有事情做完，同时还要解决关闭的问题？** 因为你不关闭，待会儿还要遍历这个管道。

关键判断标准是：**从这个 `exitChan` 里取出四个结果，就证明大家都完成了。**

```go
go func() {
	for i := 0; i < 4; i++ {
		<-exitChan
	}
	close(primeChan)
}()
```

取出四个之后，我们就可以放心地关闭 `primeChan` 了，因为我们真正要的东西在这里面。

这几个结果对我们来说没有重要性，我直接扔出去就可以了——我只希望从管道里取出四个东西出来，至于那个值是什么其实无所谓，直接把它扔走就完了。**但是如果取不到四个，我就卡在这儿等。**

至于为什么把这段包在一个 `go func()` 匿名函数里——因为这样它跟主线程的关系特别好，不会阻塞在主流程上。相当于我这儿也做了一个很简单的协程，让它帮我去盯着有没有做完成。

#### 遍历结果

```text
for {
    res, ok := <-primeChan
    if !ok {
        break
    }
    // 将结果输出
    fmt.Println("素数=", res)
}
```

因为最终是有一个协程帮你关的，所以你放心，它总有一个时间点 `ok` 取不到东西了。这时候我们就 `break`，否则就把结果输出：`fmt.Println("素数=", res)`。

这个 `res` 就是你的素数。最后再提示一句话：一直卡着，所以最后提示一句"主线程退出"。

完整的主函数大致是这样：

```go
func main() {
	var intChan chan int
	intChan = make(chan int, 1000)

	var primeChan chan int
	primeChan = make(chan int, 1000)

	var exitChan chan bool
	exitChan = make(chan bool, 4)

	go putNum(intChan)

	for i := 0; i < 4; i++ {
		go primeNum(intChan, primeChan, exitChan)
	}

	go func() {
		for i := 0; i < 4; i++ {
			<-exitChan
		}
		close(primeChan)
	}()

	for {
		res, ok := <-primeChan
		if !ok {
			break
		}
		fmt.Println("素数=", res)
	}
	fmt.Println("主线程退出")
}
```

写完先别急着上大数据，80 就能验证一下结果对不对：

```bash
cd ..
cd channel_goroutine03
go run main.go
```

我们能看到，结果是正确的。

不过第一次跑的时候，有个同学问：为什么一下就退出来了？

> **易错点**：其实这个地方的顺序，不是"存的速度太快、还没存就去读"这个原因。

那到底是什么原因？你看，我们把素数**其实都做完了**。有可能是因为我这里是 `fmt.Println`——**打印的时机和它处理数据的时机不是一回事**。可能你那边还没打印，这边它已经打印出来了。如果真是"取不到值就退出了"的话，结果数据不可能还出得来，对不对？

那就是**时机**的问题。这个地方没毛病，我们做一个很简单的处理，让它去取的时候稍微慢一下：

```go
time.Sleep(10 * time.Millisecond)
```

放在遍历之前。不用休眠一秒，一秒太慢了。`time` 包里有常量，挨着秒的下面是毫秒，再上面那个是微秒。我们毫秒就够了，来 10 毫秒。

这样大家应该就能看出效果了，出来的顺序就正常了。因为数太少了才会出现这种情况，数多就不会。

顺带查一下手册复习一下：`time` 包里的时间常量怎么写的。

最后把数据量调大，比如 8000，大家看这个结果——素数，全是素数。有同学问"这是不是素数"，给的 2000 可能就不够了，素数还挺多的。

### 一个值得想一想的现象

停一下，这里有一个特别重要的现象，你们应该感觉到很奇怪。

我打印这个素数，这个 `fmt.Println` 是在哪儿打的？我是在遍历 `primeChan` 那个循环里打的。

大家有没有感觉到很奇怪？**打印的代码是写在屁股后边的**，在函数的最末尾。但实际运行起来，最先出现的输出却是它。

我代码的顺序明明是它在后面，为什么输出反而跑到前面去了？谁来解释这个问题？

```text
代码里书写的顺序                          运行时实际发生的事

  go putNum(intChan)          ┐
  go primeNum ×4              ├─▶  四个协程同时开跑
                              │    素数一个一个进 primeChan
  go func(){ 等 4 个 true      │
                close(primeChan) }
                              │
  ┌───────────────────────────┴────────────────────────────────┐
  │ 下面这段打印，代码位置排在最后，但输出却最先冒出来        │
  │                                                            │
  │   fmt.Println("素数=", res)   ← 素数早就躺在管道里了      │
  │   ...                                                        │
  │   fmt.Println("主线程退出")   ← 这句反而最后才打印        │
  └────────────────────────────────────────────────────────────┘
```

原因就是：**它是同步的。**

大家不能想象成程序是按行顺序、一步一步慢慢执行的——程序一跑起来，大家都在工作，不是我在等你。

所以你会看到这个结果：统计出一个结果就扔进去，那边 `primeChan` 就在等着取；我这边一边取、一边放，同时它那边也在取。当然，它取的时候是要等 `close` 之后才能退出循环的。

这样大家体会一下它的用法。

## 效率实测与管道细节：只读只写和 select
> 对应块：BLK106 | 覆盖分集：P280-P282 | 块标题（分集名）：《278_尚硅谷_协程求素数的代码效率测试》

### 先算一笔效率账

刚才那个协程求素数写完了，但我心里一直有个地方想证明一下。尽管意义不是很大，我还是说一下。

**用了 goroutine 加 channel 做并发之后，效率到底真的提高了吗？** 我们现在实际上是并行，因为是在四个 CPU 上的。到底能不能有效执行，大家心里肯定有所怀疑。

理论上来说应该提高四倍，因为有四个 CPU。我们来简单证明一下。

#### 计时从哪里开始，到哪里结束

计时点很关键。`putNum` 一开始工作，我们就把起始时间拿过来：

```go
start := time.Now().Unix()
```

`time.Now().Unix()` 拿的是当前的 Unix 时间戳。

那么什么时候算结束？

> **易错点**：**不能算在打印那里。打印跟任务没有关系。**

真正的结束点是：**一旦拿到了四个退出的标志，就说明任务完成了。** 在那个地方再记一个时间：

```go
end := time.Now().Unix()
```

然后打印出耗费的时间：`end - start`。

> **提示**：跑的时候把数据调成 8000，为了能看到效果，**先把打印注释掉**——打印太费时间了。而且要记住，我们真正等待完成任务的关键是在**取标志的地方**，跟打印一点关系都没有。

#### 两个把人坑了一下的地方

第一次跑，时间根本没打印出来。为什么这个地方直接没进到这里面来？

因为**没有等待读取就直接结束了**。也就是说，那个等四个标志的动作得保留，结果可以先不用，我们只等协程完成。

第二次跑，8000 为什么这么慢？

一看，里面还留着上一节的 `time.Sleep`——**把它去掉**。

去掉之后，差不多两秒。

#### 跟传统写法对个账

现在把数据量改一改，看看如果用传统写法一共是多少时间。新建一个简单的 `test.go`，把代码粘过来做测试：

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	start := time.Now().Unix()

	for num := 1; num <= 80000; num++ {
		flag := true
		for i := 2; i < num; i++ {
			if num%i == 0 {
				flag = false
				break
			}
		}
		if flag {
			// 是素数
		}
	}

	end := time.Now().Unix()
	fmt.Println("普通的方法耗时=", end-start)
}
```

前面把时间拿过来作为起始时间，整个 `for` 循环结束以后记录 `end`，耗时就是 `end - start`。

保存后检查一遍代码：把缺少引用的 `fmt` 包导进去，把 `flag` 变量定义好。执行 `go run test.go`。

现在估算一下：根据理论来说，**单线程应该至少不低于 8 秒**，因为原先协程是 2 秒嘛，跑一下看对不对。

结果：

| 写法 | 数据量 | 耗时 |
| :--- | :---: | ---: |
| goroutine + channel（4 个协程） | 80000 | 约 2 秒 |
| 传统单线程 for 循环 | 80000 | 10 秒 |

**10 秒，在预期范围之内**。原先协程一共花了 2 秒钟，普通方法花了 10 秒钟，提升大于等于 4 倍。

> **结论**：使用 Go 协程后，执行速度比普通方法**提高了至少 4 倍**。而且这个倍数跟 CPU 的核心数密切相关——目前是 4 核；如果换到比较彪悍的服务器上，比如 16 核、32 核，性能提升会更强。

### 那要是改成 8 个协程呢

有同学马上举手：**老师，你刚才做实验起的是 4 个，那咱要起 8 个呢？起 8 个协程会不会比 2 秒还快？**

实话说，我还没试过。不过你们猜——**我认为速度不会有明显提升。** 因为刚才这个任务已经作用在 4 个 CPU 上了，CPU 它已经是并行了，再加也没用。有可能会提高一点点，但绝对不像"原来是 2 秒，改成 8 个就变成 1 秒"这样。

不过到底是不是这样，试一下不就知道了，我刚才也有点兴趣。我以前就是按 4 个来写，因为我是 4 个 CPU。

要改的话改哪几个地方？

- `primeNum` 的循环 `i < 4` 要改成 `i < 8`；
- 主线程那个等标志的 `for i := 0; i < 4; i++ { <-exitChan }` 也要改成 8；
- `exitChan` 的容量 `make(chan bool, 4)` 要改成 8；
- **别的还要改吗？不需要改了。**

看清楚，别跑错了。

跑一下：

```bash
go run main.go
```

**3 秒。变慢了，没用。**

为什么这么讲呢？因为你开 8 个，它也是作用在 4 颗 CPU 上，没用。

> **结论**：**你不能说我开多少个协程速度就上去了。** 如果真是这样子，那硬件都不用升级了——你直接把协程多开几个速度不就上去了？刚才 4 颗 CPU 已经全跑满了。

所以千万不要祈求协程开多了就一定按这个倍数增加。**多开不一定更快，这一条一定要记住。**

### 打开任务管理器看一眼

如果对这个结论还有疑虑，最直接的办法就是打开任务管理器。

你执行协程那一版的时候，可以看到 CPU 使用率**蹭的一下就上去了**。如果它能把 CPU 全部利用起来，就说明我们这个程序已经很好了。

你看我现在的 CPU 还处于有空闲的状态，因为平时负载在 30%、19% 左右。我一跑起来——**你看，是不是上去了？100% 了。** 这就很牛逼了已经，等于把你的 CPU 拉到了一个极限。

那你再去跑刚才那个传统写法的代码，`cd` 到 `test` 里面去，那边也写了一个 `test.go`。你看这个时候 CPU 的利用率应该不会飙到 100%。**它飙不上去。** 它本身就占了 20%，它下来了，你看到没有？

```text
  协程版 main.go                传统版 test.go
  ┌─────────────────────┐      ┌─────────────────────┐
  │ ████████████████████│ 100% │ ████                │  ~20%
  └─────────────────────┘      └─────────────────────┘
  4 个协程 × 4 颗 CPU          单线程只占住一颗
  已经把并行度吃满              还有 3 颗在空转
```

所以这个东西大家要去理解，它已经很厉害了，**至少四倍**。

> **结论**：以后想提高速度，可以考虑使用协程。但**提高的是"利用率"，不是"协程数量"**——协程的数量要跟 CPU 核心数配套。

### 管道的方向：只读、只写

下面进入 channel 的使用注意事项和细节。我一共整理了四点，都比较重要，这一节先讲前两点。

> **定义**：channel 可以声明为**只读**或者**只写**的性质。如果有一个管道你只允许读，就把它声明成只读的；如果你希望它只写，就把它声明成只写的。

在默认情况下，我们的管道是**双向管道**——什么是双向呢？即既可读也可写。比如你这样声明一个管道：

```go
var chann1 chan int
```

这个就是双向的，它是可读可写的，这个我就不举例子了。

我们新建一个文件夹，叫做 channel 的细节，`channeldetails`，新建第一个案例 `demo01`，在里面直接写 `main.go`。

#### 声明为只写

只写的话，非常简单，直接这样写就可以了。比如说我有一个 `chann2`：

```go
var chann2 chan<- int
```

这个时候你这个管道只能往里面写，不能读了。我举一个例子，比如你给它 `make` 了一个空间：

```go
chann2 = make(chan<- int, 3)
```

> **易错点**：**类型不能乱写。** 有的同学会问："老师，那我定义类型的时候是不是要把这个带上？"这不行。**`chan<- int` 是一种性质**，表示它有只写的性质；但实际上它装的还是 `int` 类型的东西，你不要在这儿把"只写"都写进元素类型里去。

这时候我们往里面写是没有问题的：

```go
chann2 <- 20
fmt.Println("chann2=", chann2)
```

保存之后代码不会报错，它最多报告你这个变量没有用过。打印出来是个地址，这样是没有错的。

但如果你这样写就会出问题。假设我有一个 `number`，注意听，如果你这样写就会报错：

```go
var num int = <-chann2
```

一保存就提示错误信息。它说的是 `invalid operation`，就是**无效的一个操作符**。它说这个地方它是一个 **send-only**——send 就是发送的意思，**只能往里面给我发送，不能接收**。

#### 声明为只读

反过来，还有一种声明为只读的。有时候我们确实需要只读。比如说我这里有一个 `chann3`，箭头写到前面去就可以了：

```go
var chann3 <-chan int
```

这样一写，就说我这个 `chann3` 只能读而不能写。只能读不能写，所以语法上这样写是可以的：

```go
var num2 int
num2 = <-chann3
fmt.Println("num2=", num2)
```

当然现在因为你没 `make`，运行肯定出错，但**从语法上是可以的**，代码能通过。

但是你不能这样用：

```go
chann3 <- 30
```

这个代码会在这儿报错，说无效的一个操作符，因为它是一个 **receive-only**——receive 就是我只能接收，不能写。接收嘛，就是别人往我这边扔。这个也是错的。

#### 在形参上收敛方向

那么这个只读只写，在什么地方可能用得到呢？我举一个最佳案例。这个案例我就不去写了，因为比较简单，大家看一下幻灯片就可以过了。

比如说我有这么一个情况，我这里 `make` 了一个**双向**通道，这是个双向的管道，大家应该可以看出来。这个双向通道里面，我这边定义了一个退出的管道。然后我编写了一个协程叫 `send`，还编写了一个协程叫 `receive`，一个发，一个接。

假设我这个 `ch` 协程只希望它只写、只能往里面写：

```go
func send(ch chan<- int, exitChan chan struct{})
```

我这样声明。一旦这么写了过后，你这个 `ch` 就变成了一个只写的。那你在这个函数里面做只读操作就会报错——**这样子可以有效地防止我们的误操作**。而且这个东西在底层它也做了一个优化，所以说这个更好一点，效率更高一点。

这是最标准的一个写法，但前提你一定要清楚：**你这个管道在这里只当做只写的。**

同样，假设你还有一个协程叫 `recv`，你希望这个 `ch` 只读而不能写，那就在这儿声明：

```go
func recv(ch <-chan int, exitChan chan struct{})
```

> **结论**：记住这个位置的差别——**主要看这个 `chan`，箭头在 `chan` 的后边就是只写，在前面就是只读。别写错位置了。**

#### 只读只写不是类型，是属性

有同学问了：**"老师，在这里面，你声明的那个管道它是双向的，然后传到了一个形参里面，那个形参一个是只写的、一个是只读的，那这样子不会类型不匹配吗？"**

不会。这个准确地讲，它们的**类型仍然是 `chan int`**，注意听，仍然是 `chan int`。

它这个只读只写**并不代表它的一种类型，是代表一种属性**。明白吧？代表它的一种属性而已。

> **提示**：好比说咱们这个人——**人都是人**，人还是人嘛，分个男、分个女，但人还是能匹配上的，人还是能匹配上的，就这样子的。

所以你可以这样理解：当我们把一个双向管道传给了一个这样东西之后，那么这个 `ch` 在这里相当于**把那个只读的操作给你封起来了，不让你用了**。就这么一点，但类型仍然还是 `chan int`。

### select：不关闭也能退出

接着再介绍两点 channel 的使用细节和注意事项，也比较重要。第一个就是 `select`。

> **定义**：使用 `select` 可以解决从管道取数据的阻塞问题。

什么意思呢？我们前面记得，从一个管道里面读取东西，我们需要 `close` 这个管道。**如果不 `close`，你在遍历这个管道的时候它会阻塞，而且会发生一个死锁。**

但有些情况下你会说："老师，我不想关闭它，我也希望它能够不阻塞、能够正常地退出，行不行呢？"

也可以。这时我们就会用到一个关键字叫 `select`。

#### select 的基本形态

我们新建一个 `demo02`，新建 `main.go`。为了讲解，我们先做第一步：

```go
// 1. 定义一个管道 10 个数据 int
intChan := make(chan int, 10)
for i := 0; i < 10; i++ {
	intChan <- i
}

// 2. 定义一个管道 5 个数据 string
stringChan := make(chan string, 5)
for i := 0; i < 5; i++ {
	stringChan <- "hello" + fmt.Sprintf("%d", i)
}
```

传统的方法在遍历管道时，如果不关闭会阻塞而导致 `deadlock`。有些同学就说了："老师，既然这个管道你遍历的时候不关闭就阻塞，你关闭不就完了吗？"

这就是一个问题。是的，**关闭确实可以解决问题**，但是在我们有时候写代码的时候，**你要确定在什么时候关闭这个管道，其实是一件挺难的事**。

大家明白我的意思吧？有时候你不好确定到底怎么关。如果说将来你写一个很复杂的代码——当然现在这种情况比较少，将来你们做开发，遇到一个非常变态的需求，有可能会遇到你自己不确定什么时候关、它可能是一个不好确定的时机。这种情况下你用关闭的方式它搞不定，因为你不知道怎么关。我们前面举的案例说白了还是比较容易确定的，因为我可以做标识，但有时候你不知道怎么关怎么办呢？

咱们有新的方案。传统方法我就不写了，我就直接上代码：

```go
for {
	select {
	case v := <-intChan:
		fmt.Printf("从 intChan 读取了数据%d\n", v)
		time.Sleep(time.Second)
	case v := <-stringChan:
		fmt.Printf("从 stringChan 读取了数据%s\n", v)
		time.Sleep(time.Second)
	default:
		fmt.Printf("都取不到了，不玩了\n")
		time.Sleep(time.Second)
		return
	}
}
```

语法就是这么包起来：上来先来一个死循环，然后写上 `select` 包起来，`select` 包起来过后有 `case`，然后把管道里面的值放到一个 `v` 里面去。

这个关键点很重要：**这种思路去取一个管道的时候，即使你这个管道关闭、取不到数据了，它也不阻塞，它会往下走。**

注意，按这种方式，这里如果管道最终都没关闭、一直也没有关闭，**也不会一直阻塞在这里而导致死锁**。那它会怎么样呢？

在这取不到会怎么办呢？你又没有关闭，我又取不到东西——**在这种情况下，它会自动地到下一个 `case` 去匹配。**

那这样就好了。如果我这取不到，你又不关闭，无所谓，我接着往下走，我就直接又来一个 `case v`。如果在这取不到，我到哪里去取呢？我到 `stringChan` 管道里面去取。这还是有用的——我又说我从哪里取到呢？我从 `stringChan` 这个管道里面取到值了。

那有些同学说："老师，如果这个再取不到呢？"

再取不到我就 `default` 一下，我就 `default` 说都取不到了。如果在这还取不到，我就说都取不到了，不玩了。

> **结论**：它有一种机制——**在这取不到，我到这取；这取不到，`default`，取不到，不玩了。** 不玩了过后你可以加入自己的逻辑，程序员可以加入自己的业务逻辑。比如说你打个比方，都取不到我就退出，或者是我去做一些别的事情。**我不依赖你关闭，因为我关闭也不知道什么时候关闭。**

> **易错点**：这里有个小坑。我们跑一下的时候，编译器会报格式错误：`stringChan` 那边取出来的是个**字符串**，所以格式串应该用 `%s` 而不是 `%d`。你写成 `%d` 就会报错。

`cd` 到 `channeldetails`，进到 `demo02`，`go run main.go`，跑！

你会发现：老不玩了也不行，先从 `string` 取，再从 `int` 取，这就看顺序了，看它是怎么取的。它先从这取，那也是看它从哪能取到东西，因为你放的时候这个时机不确定。如果从这取到了他就取。

至于这个顺序咱就不好控制了，**因为跟它当前的上下文环境是有关系的。**

当它都取完了——你看 `hello0`、`hello1`、`hello2`、`hello3`、`hello4`，这边 0 到 9 都取完了，这时它走到 `default` 那儿。

#### 怎么跳出 select

那这个时候怎么办呢？你可以 `break`。**没用，这个 `break` 没用。** 因为你 `break` 还是 break 在 `select` 这个地方，你还跳不出去。

跳不出去怎么办呢？好办，来个 `label` 就行了。假设你这就 label，我就直接 `break label`：

```go
label:
for {
	select {
	case v := <-intChan:
		...
	default:
		return
		// break label
	}
}
```

> **注意**：label 这个东西我们**尽量不要使用**，但是没有办法的话也可以用一用。你也可能是 `end`，比如说有些地方是 `return`。

我们先来测试，看 `break` 到底管不管用。为了好看，每个地方都让它去休眠大概一秒钟，`time.Sleep(time.Second)`。别忘了引 `time` 包。

跑一下你会发现：它先从 `string` 取，再从 `int` 取，这次是从 `string` 取的。这都能取到东西，它很正常，都取，很开心。后面把 `string` 取完了就只能取 `int` 了，取完了过后——看到没，取不到了，不玩了，**但是它不退出。**

那这个时候你有两个解决办法。

**第一种：你这段代码是封装到一个协程里面的，那直接 `return` 就完了，最简单。** 你连标签都不用。

这个 `return` 的含义跟函数里的 `return` 根本不一样——**这里的 `return` 代表整个协程结束**，这个函数都不执行了，就相当于退出这个系统了。跑一下，取到、取到、取到，再取，最后一个取不到了，直接退出去，完全正常。

**第二种：如果你确实想用这个 `label` 也可以。** 说用 label 然后加 `break`，它也能达到效果——你以前学过 label，这次用上了一点。看到 break label 到标签那个地方去，它也能跳出去，效果也是可以的。

> **结论**：那么我推荐大家**使用 `return` 比较好**。这两个有什么区别大家想一下：**如果写了 `return`，你下面的代码是没有机会执行的，它也不能执行；而 `break` 完了过后，下面代码还可以执行。** 区别还是有的。

label 标签在我们开发中用的很少，尽量不要用 label。

> **结论**：这一条细节还是很有用的，同学们以后在开发中应该是能够用得到。

## 用 recover 兜住 panic，然后正式走进反射
> 对应块：BLK107 | 覆盖分集：P283-P286 | 块标题（分集名）：《281_尚硅谷_管道的注意事项和细节(3)》

### 协程里的 panic 为什么会炸掉整个程序

goroutine 和 channel 我们就讲到这里了，最后一个需要注意点的地方是：**goroutine 中 panic 的捕获。**

如果我们在一个协程中不使用 `recover`，会出现一个什么情况呢？如果你在一个协程里面出现一个 `panic`，**会导致整个程序崩溃**。

那有时候我们有两个协程，如果有一个协程它崩溃了，**我们并不希望它影响到别的协程**，这很正常，对吧？我举个例子，怎么去控制这个问题、解决这个问题。

#### 先制造一个 panic

我们在 `channeldetails` 下面新建 `demo03`，写一个 `main.go`。

第一个函数是每隔一秒钟输出一个 "hello,world"，输出十次。我们叫它 `sayHello`：

```go
func sayHello() {
	for i := 0; i < 10; i++ {
		time.Sleep(time.Second)
		fmt.Println("hello,world")
	}
}
```

另外还有一个函数，我们叫 `test`。它去定义了一个 map：

```go
func test() {
	var myMap map[int]string
	myMap[0] = "golang" // error
}
```

它的值是 `string`。上来以后，这个人使用错了——他上来以后写了一个 0，然后给它了一个值，叫作 "golang"。同学们知道，这种写法应该是错误的，对吧？**因为我们的 map 是不是应该先 `make` 一下。** 但是他上来就这样用，这种用法显然是错的。

如果说我们没有去控制，我这里起了一个 `sayHello` 协程，同时又起了一个 `test` 协程：

```go
go sayHello()
go test()
```

会怎么样呢？**本身 `sayHello` 这块协程是没毛病的，但是因为 `test` 报错了，导致整个程序崩溃。**

我们让主函数也说说话，不然它跑得太快我们看不到东西：

```go
for i := 0; i < 10; i++ {
	time.Sleep(time.Second)
	fmt.Println("main() ok=", i)
}
```

`cd ..`，`cd demo03`，`go run main.go` 跑起来。大家看：**主函数输出了一次 ok 以后，立马就崩了。**

为什么崩了呢？它告诉你有一个 `panic` 发生了。为什么发生呢？是因为你分配了一个 entry——entry 不就是键值对的意思吗？然后你给它了一个 `nil`，把这个键值对给了一个 `nil`，那当然就报错了。

> **易错点**：看起来是我这个函数没问题，那个函数也没问题，但**一个协程里的错误会把整个程序带走**。

#### defer 加 recover 把它拦下来

实际在开发中，我们是希望有这样一种机制：**如果你有一个协程出了问题，你不要去影响我，不要去影响我的这个协程和主线程的执行。**

那这个时候怎么办呢？非常简单，把我们原先讲的错误处理机制引进来就可以了——`defer` 加 `recover`：

```go
func test() {
	defer func() {
		// 捕获 test 抛出的 panic
		if err := recover(); err != nil {
			fmt.Println("test() 发生错误", err)
		}
	}()

	var myMap map[int]string
	myMap[0] = "golang" // error
}
```

写一个匿名的函数，写到这里面来。在这里面我可以去捕获抛出的 `panic`——**怎么捕获这个问题呢？非常的简单，我们前面讲过 `if` 语句，直接用 `recover` 来捕获。**

大家还记得 `recover` 会返回什么东西吗？它返回一个 `error` 值。那我用这个 `recover` 来解决它：**如果这个 `err` 它不等于 `nil`，就说明的确确发生了一个错误**，这个时候我们就处理一下，说 test 发生错误了。

一旦发生错误的话，也很简单，我们就把这个错误打出来就完了。

> **易错点**：少了一句调用——**这是匿名函数的调用，要打一对小括号。** 如果这里有参数，你还得传参数进去。

大家再来看一下效果，这就不一样了。它说 test 发生错误了，但是你看，**我的两个输出仍然是正常的**，退出了，完事。

这样子的话，你这个发生错误了，大不了就是说你在这发一封电子邮件，或者发一个预警给管理员。**管理员知道有一个协程有问题了，赶紧去处理就行了。** 所以这个机制在我们开发中也是用得比较多的。

> **结论**：如果我们起了一个协程，但这个协程出现了 `panic`，又没有捕获这个 `panic`，就会造成整个程序的崩溃。这时我们可以在 goroutine 中使用 `recover` 来捕获并处理。这样即使这个协程出了问题，**主线程仍然不受影响，其它协程也不会受影响**，还是可以正常执行，可以继续执行。

### 反射为什么值得学

好，16 章关掉，我们打开新的章节——**反射**。

我们讲课一定要说这个东西**有什么用、它能干什么**，不然的话你就觉得不好玩。先看问题：既然是反射，那什么时候可能用到反射呢？

#### 结构体 tag 决定了序列化后的字段名

前面我们曾经学过结构体的序列化和反序列化，大家应该是有印象的。当时我们有这么一个情况——结构体里面可以加一个东西：

```go
type Student struct {
	Name string `json:"name"`
	Age  int    `json:"age"`
}
```

大家还知道这个叫什么吗？这叫 **tag**，对不对，叫标签。

这个东西用来干什么呢？**这是为了解决序列化的时候我们可以指定一个 key 的名字**，当时是这么来的。当时我用结构体的标签解决的问题就是：我们去进行一个序列化的时候，它的字段的名称可以根据我指定的这个名字来序列化。

当时我还讲过它的底层机制到底怎么回事——我说道会用到反射，但是**我们没有具体地去讲，只是提了一嘴**。

现在引起大家思考：**为什么序列化过后，它的这个名称就跟它保持一致了？**

告诉大家，这里就是我们的反射。当时我还说了一句话：**学习 reflect 回头解决。** 现在我们就要解决它了。但是因为这里只是提出一个概念，所以说怎么解决，我们把基本知识讲完再解决。这是第一个需求，第一个可能用到反射的地方。

#### 函数的适配器

反射除了在这个地方用得到，别的地方有没有呢？用的地方还很多。

第二个应用的场景：比如说将来我们有这样一个需求，说这里有一个匿名的函数，我把这个函数赋给了一个变量，相当于函数变量了。

这个时候我们假设有这么一个需求——**听我讲啊，这听起来有点吃力啊同学们**：假设你有这样一个需求，你想干什么呢？**你想编一个适配器函数。**

你想编一个适配器函数干什么呢？**作为统一的处理函数。** 比如说你给我传进来一个函数的名称 `call`，`call` 我写的是空接口 `interface{}`，然后这边是它的参数，是个可变参数。

我希望通过这个桥——**通过这个东西，你将来去使用它，就把我的函数 `test1` 传进去，再给它传 1 和 2**，因为他原先定的是 1 和 2，我就能把这个程序跑起来了。同样，我也可以把 `test2` 这个函数传进去，再给它传三个参数，因为它是需要三个参数，又把我们 `test2` 运行起来了。

> **定义**：同学们，这种就叫**适配器函数**。在一些高级的使用里面，将来大家去写一些底层的代码——比如将来你们有机会去写 Go 的框架，自己去研发框架——**这个反射最大的价值就是自己写框架。自己写框架的时候，反射就必用无疑。**

#### 反射最大的用武之地：写框架

我现在给有些同学讲，可能大家很清楚。我们班有很多同学以前写过 JavaEE。你们有没有发现一个非常奇怪的现象？

**你在 Web 界面输了一个用户名和密码，你提交，结果你的那个 Action 被调用起来了。**

```text
   浏览器里输用户名 + 密码
              |
              |  submit
              v
    +---------------------+
    |   Action 是个类      |   ← 它没有被你 new 出来过
    +---------------------+
              |
              |  是谁把类变成对象的？
              v
        【 反射 】：靠类型找到实例
              |
              v
        Action 真的被调用起来了
```

你在 Web 界面输一个用户名、一个密码提交给 Web 过后，结果发现 Action 运行起来了。**这个 Action 难道没人去实例化它吗？** 全是底层的一个反射给你搞出来的。

Struts2、Hibernate、Spring、Spring MVC——这些经典的框架，底下全是这个在玩。

如果你学过 PHP——**比如像小彭学过**，肯定会学过一个叫 TP 的框架吧？它就是反射过来的。

将来以后同学们要自己去学这个框架，或者自己要去开发框架。比如将来我们班有些同学做 Go 程序做了两年、三年，突然你们项目经理说：**咱自己来写一个框架吧。** 中国也有很多人写框架呀。这个时候你的反射就是特别重要。

当然如果你到了让自己去开发框架这个层面，那你技术已经很牛了。你写的框架让别人去用了，那这个就很厉害了。在写这里面，类似于这种东西都会用到，像写适配器函数。

这两个应用场景是很经典的。我再给大家举一个例子：**比如说我们想用反射机制去调函数。** 比如说你有结构体，我把一个结构体的实例给你，**我要求用反射去拿到这个结构体所有的字段信息、所有的方法信息，然后用反射把它给我调起来**，这就很有意思了。

**甚至你还可以用反射去创建一个结构体的实例**，这就很厉害了。我们都会讲到，应用场景还是非常多的。

### 反射的基本能力

上午我们给同学们介绍了一下它的一个简单的应用场景。下面我们来看反射的基本介绍。

首先，在学任何一样东西，先把它一个简单的原理搞清楚。因为**反射里面有大量的函数，它的难度是在这些函数的应用上面。**

首先我们看：**反射可以在运行的时候动态地获取变量的各种信息。** 什么信息呢？比如变量的类型、变量的类别。

#### Type 和 Kind 不是一回事

> **定义**：类型和类别是有区别的。一般来讲，从英文字母来说，**类型叫 Type，类别叫 Kind**，是有稍微一点点小区别的。

如果说你的变量是基本数据类型，其实这两者是相同的；如果你这个变量是结构体，**类型和类别是不一样的**，待会儿我们还要举例。

如果你是结构体的一个实例——当然我们也可以叫变量——还可以获取到结构体本身的信息，**比如说它的字段、它的方法等等**，这是它的第二个用处。

还有，**通过反射我们可以修改变量的值**——当然我们用的是变量加引用的传递——**还可以调用关联的方法。** 比如说我通过反射，可以以反射的方式去调用结构体的方法。

在使用反射的时候，我们用到一个非常重要的包，叫 **`reflect`**。

#### 骨架图：变量、Type 和 Value

最后我要画一个示意图。这个示意图对我们来说特别重要，**如果我不画一个示意图，到时候想讲的时候都容易讲蒙圈。** 这个示意图其实挺简单，但是很有指导意义。

你可以这样理解反射的原理，或者说反射要做的事。

这个地方是我们的一个变量。这个变量可能是基本数据类型，比如一个非常简单的 `number`；当然也有可能是一个结构体：

```go
type Student struct {
	Name string
	Age  int
}

func (this Student) Print(i int) {
	// 你的代码
}
```

对于一个基本数据类型来说，它还是比较单纯一点的。因为基本数据类型一般我们不会把一个方法绑定到基本数据类型上。当然也是可以的——**如果你给 `int` 取一个别名，其实也是可以给它绑定相关方法的**，但一般情况下我们不会。

如果是结构体的话，就相对复杂一点。假如 `Student` 结构体里面有一些字段，比如说 `Name` 字段、`Age` 字段；**除了字段之外，我们往往还会有一些方法跟它绑定。**

那反射要做的事就来了：

```text
                        +---------------------------+
                        |      变量  variable        |
                        |                           |
                        |   number      (基本类型)  |
                        |   stu         (Student)   |
                        +-------------+-------------+
                                      |
                     +----------------+----------------+
                     |                                 |
          reflect.TypeOf(v)                  reflect.ValueOf(v)
          参数: 空接口 interface{}          参数: 空接口 interface{}
                     |                                 |
                     v                                 v
        +------------------------+           +------------------------+
        |     reflect.Type       |           |     reflect.Value     |
        |   这是【一个接口】      |           |   这是【一个结构体】    |
        +-----------+------------+           +-----------+------------+
                    |                                    |
   Kind / Name / PkgPath / Size              IsValid / IsNil / Kind
   Bits / Elem / Key / Field / Method        Type() / Float / NumField
                    |                          FieldByIndex / Call ...
                    |                                    |
                    |          两者之间有桥梁关系          |
                    +<------ Value.Type() 绕回来 ------>+
                    |                                    |
                    +------------>  反向操作  <----------+
                                    你的变量
```

> **结论**：我们学反射就是学的这一堆东西——**我们的变量怎么转换到 `Type`，然后又通过 `Type` 怎么去操作它；或者说通过变量怎么去拿到 `reflect.Value` 这种类型，通过它提供的这样一些方法，然后我又反向去操作它。** 就这个意思。

#### 为什么官方要提供这些东西

那有些同学可能会觉得很奇怪，说老师为什么它要提供这个东西呢？

它提供这个东西有一个特别好的地方：**就是它底层可以帮你去创建对象，它在底层可以帮你去做很多事情，不需要完全由程序员去做。**

打个比方，举个最简单的例子：**你给我提供一个 Student 的名字和 age，我在底层帮你去创建，然后再给你使用**，甚至我还可以帮你去通过反射调用方法。

有些工作我可以在底层框架帮你做很多事情，但这个事情对用户来说可能就是透明的了，类似于这样一种感觉。

### 变量、空接口和 Value 怎么转圈

> **定义**：在反射中有一个重要的函数和一个概念：**反射中变量、空接口还有 `reflect.Value` 是可以相互转换的。** 这一点在实际开发中会经常用到。

一般来讲，如果你通过一个方法把一个变量传递给一个函数让它去做反射，**函数参数应该是接口，不会直接传一个固定的东西。**

比如这里有一个变量，假设是个结构体：

```go
var stu Student
```

然后这个结构体一般怎么去玩反射呢？一般会把这个结构体传给一个函数：

```go
func test(b interface{})
```

这个 `test` 一般不但可以去反射 `Student`，也可以反射其它的一些类型。比如既可以反射 `Student` 这种实例，也可能去反射一个非常简单的 number 类型。

在实际工作中，玩反射的时候，通常这个函数是专门用于做反射的，**一般会把 Student 这个值传给它，所以这个地方一般来讲是一个空接口类型。**

#### 从变量到 reflect.Value

拿到接口 `b`，我们真正把它转成 `reflect.Value`，通常情况下是通过一个函数来转的。

这里一个重要概念就是：**如何将一个空接口 `interface{}` 转成我们需要的 `reflect.Value`？**

它用的是一个函数：

```go
rVal := reflect.ValueOf(b)
```

一般来讲就是这样做的，调用 `reflect.ValueOf`，然后把 `b` 传进去。

#### 从 reflect.Value 转回原来的类型

那又有一个问题了：**如果将来需要把这个类型重新再转回原来的类型，这种情况还比较多，这个时候又怎么做呢？**

先解决一个这样的问题：**如何将 `reflect.Value` 这种类型转成空接口类型？** 这个很有用，因为有时候往往先把它转成空接口，然后再做下一步工作。

这时用的是它的一个方法，叫 `Interface()`，**注意这个 `I` 是大写的**：

```go
iv := rVal.Interface()
```

这个地方它又变成一个接口了。打开文档看 `Value`，真的会有一个 `Interface()` 方法：**本方法将返回 v 持有的值，返回是一个接口类型。** 因为有时候这个接口很有用，可以做类型断言，或者做更广泛的应用。

下一步，第三步。在开发中有时候还会做一个特别重要的功能：**如何将 `interface{}` 这种空接口类型，转成原来的变量类型？**

这个非常简单，使用**类型断言**即可。比如叫 `v`，表示真正的变量类型：

```go
v := iv.(Student)
```

直接断言。想把它转成原先的 Student，这里就放一个 `Student` 就可以了。此时此刻这个 `v` 又变成了它，相当于**转了一圈回去了**。这个我们在做反射的时候会经常用到。

```text
   stu (Student)
        |
        |  传参
        v
   test(b interface{})            <-- 第 1 步：变量交给空接口
        |
        |  reflect.ValueOf(b)
        v
   rVal  (reflect.Value)          <-- 第 2 步：转成 Value
        |
        |  rVal.Interface()
        v
   iv    (interface{})             <-- 第 3 步：转回空接口
        |
        |  类型断言  iv.(Student)
        v
   v     (Student)                 <-- 第 4 步：断言转回原类型
        |
        +----> 又回到最开始的变量类型
```

> **结论**：它们之间的关系是可以随意进行切换的，想转到哪儿都可以。**变量通过传递参数交给空接口，空接口通过反射的函数 `ValueOf` 拿到了反射的 Value 类型；通过反射的 Value 类型，可以再返回去变成接口，使用 `v.Interface()`（`I` 是大写的），又转回去；再回到原来的变量类型，使用类型断言。**

所以这个关系图大家要有一个基本认识。有了这个基本知识结构过后，心里面就有底了，下面玩起来就比较轻松了。

> **结论**：前面我们已经把基本的东西说完了——包括它的原理，包括它涉及到的**变量、空接口**，还有重要的两个反射类型：**一个是 `reflect.Type`，一个是 `reflect.Value`**。总结起来就是四点：**一个是传递过去，第二个是转成 Value，第三个是转成空接口，再断言转回去，又回到最开始的变量类型。**

## 反射入门：Type、Value，和那个绕不过去的类型断言
> 对应块：BLK108 | 覆盖分集：P287-P288 | 块标题（分集名）：《285_尚硅谷_反射的快速入门(1)》

### 第一个案例：把一个 int 交给反射，再要回来

第一个快速入门案例：**请编写一个程序，演示把基本数据类型转成 `interface{}` 空接口，再把它转回 `reflect.Value` 进行反射的基本操作。** 先不上复杂的，先来简单的。

新建 `chapter17`，里面建 `reflectdemo/reflectdemo01/main.go`。

**做反射一般会专门写一个函数**，专门用来演示反射：

```go
func reflectTest(b interface{}) {
```

**为什么参数要用这个接口呢？因为我可以对任何数据类型进行反射**，当然就用它了。

现在先创建一个 `int` 类型的变量，给它一个值 100。我们的目标是：**通过反射拿到这个 num 的 kind、type 以及它的值。**

再说一遍，我们假设现在演示的是通过这个 num 拿到它的一系列信息。**注意：type 是类型，kind 是类别。**

#### 第一步：拿到 reflect.Type

先把 num 传进去，因为形参是接口，所以你能拿到。

```go
rTyp := reflect.TypeOf(b)
```

> **为什么变量名要用 `r` 打头？** 为了以示区别。你看这个地方写的是 `type`，它是指反射的那种类型；而不以 `r` 开头的 `type`，是指我们原先讲的那种传统的类型。**这个很容易听懵圈，所以说我在定义的时候前面写个 `r`。你看到是 `r` 打头的，就代表是反射的这个 type。**

打印出来你会看到它显示的就是 `int` 类型，因为这个时候它反射过来的类型跟它是一样的。

**但是——这个本质上的东西还可以调函数的，如果是普通的 `int` 那是不行的。** 你现在看到它看上去是个 `int`，但**它真正的类型是 `reflect` 这个类型**（`Type` 本质是一个接口）。只是你输出来它打印是个 `int`，说它本质是个 `int`，是可以的；**但你原先那个 `int` 是不能调东西的，而它可以调。** 只是你现在是个基本数据类型，调这个没有什么意义。

至于它的 `Name()`：返回的是该类型在自身包内的类型名，如果未命名就返回空串。这个基本数据类型我们就不管它了。

#### 第二步：拿到 reflect.Value

第二步我们演示一下获取 `reflect.Value` 这个类型。同样 `r` 打头：

```go
rVal := reflect.ValueOf(b)
fmt.Println("rVal=", rVal)
```

打印出来值是 100。

**但这个地方特别容易懵圈，大家一定要认真听讲：它看起来是一个 100，其实它不是真正意义上我们原先那个 100。**

我们对比一下。如果它真的是普通的 100，你可以这样操作：

```go
n1 := 10
n2 := 2 + n1
fmt.Println("n2=", n2)
```

这段代码没有毛病，因为它们都是 `int` 类型，输出 `n2= 12`，完全正确。

但如果我把那个 `2` 换成反射的值——`n2 := 2 + rVal`——**它马上报错**：`invalid operation: 2 + rVal (mismatched types int and reflect.Value)`。**因为你这个 `int` 和这个不匹配，因为它是 `reflect.Value` 类型。**

> **难理解吗？你直接输出的时候，它其实会返回 100——因为底层应该是有这样一个机制，直接输出这个结构体，把它代表的值输出来了。**
> **但如果你真的想看它的类型，想看它真正的类型，应该用 `%T` 来看。**

```go
fmt.Printf("rVal=%v, type=%T\n", rVal, rVal)
```

这样再打一次，你就会看到这个类型是 **`reflect.Value`**。代码本身一行都没变，`rVal` 还是那个 100——**只是你想看类型，得换个打印方式。**

现在明白这个东西有什么好处了吗？**明白它你就知道将来你想用它干什么事都可以——因为你相当于已经拿到了它，那它里面的方法全部都可以用，你想通过它对原先的变量进行各种操作都可以玩了。**

#### 第三步：把真正的值取出来

我们还没有完成我们的事情——怎么真正拿到这个 int 值？

有人说："老师，假设我就想给它加怎么办？"没问题。你要这么干，你作为一个程序员就得想：**这个 `reflect.Value` 到底有没有提供一个方法，把真正的值取出来呢？**

显然它必须提供。**否则你将来做反射就有这个需求了——它明明就是 100，我在这儿想对它做加减乘除，你还让我做不了事，那还了得。** 打开手册一看，它提供了大量的方法：

- 它可以提供**改变这个值的方法**，也就是我可以在底层通过反射去改变你原来的值；
- 它有没有返回一个 `int` 呢？有——`Int()`；
- 还有什么？`Bool()`、`Uint()`、`String()`、`Bytes()`、`Pointer()`，连它的指针都能拿到。

`Int()` 那一行的说明写得很清楚：**返回 v（也就是 `reflect.Value` 类型）持有的符号整数。这个才是真正的值。** 所以你要做加法，其实应该这么玩：`.Int()`，搞定。

```go
n := rVal.Int() + 1
fmt.Println("n=", n+1)
```

跑一下返回 **102**。

**当然有同学问：老师，那假设我传进来的不是一个 `int`，而是一个 `float` 怎么办？用断言就可以了。** 这样一做，绝对不会再报错了。

#### 第四步：转回 interface{}，再转回 int

我还有一个需求——我还想把这个家伙重新转回成 num 这个类型。

先把 `reflect.Value` 转成 `interface{}`，这个很简单，一句话的事。我来个 `iv`，代表它是一个接口的值：

```go
iv := rVal.Interface()
```

**后面这个 `Interface()` 方法你以后会大量地看到。** 它又把它重新转成这个接口了。

然后再通过断言，把它重新转回需要的类型。当然是对应的关系，我再转回一个 `num2`：

```go
num2 := iv.(int)
fmt.Println("num2=", num2)
```

这个 `num2` 绝对是个整数，我不需要再打它的类型，直接输出给你看一下——**这个应该就是真正的、真正的 100。**

跑一下，整个流程做完了，**基本数据类型的一个反射流程全部做完。**

> **别急**：有些同学说"老师我还是没明白反射到底在干什么"，不要着急，先把这些基本的整完。后面大概有 4 到 5 个真正的反射应用，你一听就明白了。你现在没有基础，肯定是听不懂的，在工程里也是懵圈——**先把基础搞懂。**

### 第二个案例：结构体，和那个必须先断言的坑

有了前面的基础，我们来看对结构体的操作，这个就简单了。老规矩再写一个案例，我重新取个名字 `reflectTest02`。

先声明一个结构体：

```go
type Student struct {
	Name string
	Age  int
}
```

里面第一个字段是 `Name`，`string`；然后有一个年龄，`int` 就可以了。第二步定义一个 `Student` 的实例：

```go
var stu = Student{
	Name: "tom",
	Age:  20,
}
```

前面的部分不用改——该拿反射的 `Type` 还是拿，拿到值也是一样的。我们看怎么把它转成接口：

```go
fmt.Printf("iv=%v, type=%T\n", iv, iv)
```

把学生传进去运行一下：

```text
iv={tom 20}, type=main.Student
```

**其实这个特别正确**——因为它是接口，你把它转过来，这个接口仍然指向这个类型；而且打印出来它确实也是个结构体，跟我们想的一样。

**但是有一个很奇怪的事情我要告诉大家**：你现在这个类型打印出来是这个，**但你根本就不能把 `Name` 取出来。**

你看我要取出这个名字，这个学生不是有 tom 吗？如果直接 `iv.Name`，一保存就报错了。**刚才我们明明已经看到，它反射过去还是指向这个 `Student` 的，内容也是这样子的，为什么取不出来？**

**因为编译器在编译的时候没有办法确认它是什么。** 你一保存就错了。**这又是一个运行期的问题。**

> **大家一定要非常清楚地认识反射的本质：反射的本质是运行时的。**
> 虽然在运行的那一瞬间，编译器是能够确认 `iv` 它的的确确就是这个类型、它的值是这个；**但是在编译阶段，它没有办法确认这个东西是什么，因此编译器在这儿过不去。**
>
> 这就是为什么我们想反过来回头拿这个值的时候，**必须通过断言先把它转成对应的类型，然后再取值**的根本原因。

所以开篇明义：反射这边有一句话说得非常到位——**它实现了运行时的反射。** 不然的话你会觉得怎么回事取不出来呢？

#### 带 ok 的断言，和更灵活的 switch

怎么做呢？非常简单：**你要么直接断言，要么用带检测的断言。**

有些同学会问："老师，你怎么敢肯定它就是 `Student`？那假设我们将来还有一个 `Monster` 类型，它也是 `Name`、`Age` 两个字段，我把 `Monster` 传进去，你怎么敢这样写 `iv.(Student)`？"

**是的，我确实不敢这样写。** 那怎么办？**大家知道断言本身是可以带检测的**：

```go
stu, ok := iv.(Student)
```

有个 `ok`。这个我们以前学过——**我可以判断你有没有成功，你成功我再干，不成功就算了。** 这是第一个方法。

**第二个方法，你完全可以给我搞一个 `switch`。** 如果你将来真的要变得很灵活，那就是 `switch`。我们讲 `switch` 的时候讲过一个 `.(type)`，还记得吗？**就是在讲类型断言的时候讲过这个。**

当时我们是怎么做的？大家打开手册找找——当时给了一个比较灵活的处理方法。虽然那个例子用的是 `for` 循环，但这里用不上，因为它只有一个变量。你只需要把那段代码拿过来——**那个 `x` 不就是接口吗，我这传的也是接口类型，你把这个接口 `.(type)`，看它适合哪个类型进去，不就完了吗？**

所以你可以把它做得更灵活，把以前那个笔记拿过来用就行了。**这个笔记是非常有用的，大家不要去扔了，扔了不好。**

现在回到这边，你就会觉得——**原来把以前学过的东西也整合上去了。**

我这里先不用 `switch`，我就简单用一下带检测的类型断言：

```go
if ok {
	fmt.Printf("student.Name=%v\n", stu.Name)
}
```

有了这个东西老师就比较放心了。如果这个 `ok` 真的成功了，断言成功了，那这个 `student` 就真的拿到了，**现在我们就可以放心大胆地把名字、把它的信息全部遍历出来了**，把整个字段都给取出来。

这个你放心，绝对取出来了——**因为从编译的层面，它知道你这个时候就是 `Student` 的。** 但是如果你断言失败了，那就算了，我也不影响我。

执行一下，跟我们想的完全一样。

> **想做得更灵活的同学**：晚上可以把它写成 `switch` 的断言形式，把你能想到的类型都写进去，封装成一个函数就完事了。

基本知识我们又进了一步，接下来就可以做更加高级的东西了。

### Kind 是常量，不是类型

接下来讲反射的注意事项和细节，一共六点。第一个：**反射取得的 `Kind` 是获取变量的一个类别，返回的是一个常量。**

有些同学一直在问 `Kind` 到底是什么东西。打开手册，`Kind` 有两种方式可以拿到：

- **第一种，通过反射的 `Value` 类型本身提供的方法 `Kind()`**——它返回 v（也就是 `reflect.Value` 类型）持有的分类；
- **第二种，通过 `Type` 来拿**——因为 `TypeOf` 返回的是一个实现了 `Type` 接口的变量类型，打开手册你会发现 `Type` 里也有一个 `Kind()`。

**那这两个 `Kind` 调用的到底是不是同一个值呢？** 点进去看，发现它定位到同一个地方。**说明它们说白了就是一个意思**——对于刚学反射的同学会觉得怎么这样子，但确实都可以。

```go
kind1 := rVal.Kind()
kind2 := rType.Kind()
fmt.Println("kind1=", kind1, "kind2=", kind2)
```

跑一下你会看到这两个是一样的，都是 `struct`——**这是类别。**

那么类型和类别谁大谁小？**你们感觉 `Type` 是一个大的范畴，还是 `Kind` 是一个大的范畴？显然 `Kind` 范畴要大一点。** 打个比方：**这是"电器"，一个类别里面有冰箱；"冰箱"就是一个类型。** 或者是"冰箱"是一个大类，那比如我这个是 500 毫升的冰箱，那个是一万的，它是有类型的。

所以这个结构体，它既可以是 `Student`，也可以是 `Monster`，也可以是 `Person`——它是这样一个关系。

> **面试里什么时候会问这个？** 反射在要求比较高的公司问得多。为什么呢？**因为他觉得这个东西难，他就问你，用不用他无所谓，他先问你比较困难的。** 等会儿他不问你 `for` 循环会不会，问你反射会不会，问你几个问题就懵圈了，这样他可以打压你的气势——比如你满怀信心准备要两万是吧？第一个题没答上来，一万八也行；第二个题又没答上来，一万六也行了；连续几个没答上来，最后一句：给多少算多少。
>
> **所以面试官他是有技巧的。你们以后去面试，也不要去准备说全部都答上来。** 全部都答上来说实话不好管理你——面试官出了十个题你全部答上来了，我以后怎么压你？他一定会找些他自己都不会的问题，都让你答上来了你想一想那还了得，工资怎么算？出了十个题考了一百分，七八个题全部做对，那不是显得自己很没档次？他一定会出一些比较困难的题。**所以面试有些题做不出来很正常，但是你不要一个题都做不出来。**
>
> 它一般会这样分布：可能百分之五六十是基本的，中档的可能有百分之二三十，比较困难的一定会有二三十，是一定让你答不出来。反正各公司都这样子，一般的公司也会这么设计，不然不好弄。

理解了过后，我回头花几分钟补讲一下 `const`——**`Kind` 本质其实就是一个常量**，而我以前好像没有专门给大家讲过常量。刚好借这个机会把常量补一下。

### 顺便把常量补上

常量是个什么玩意儿呢？几句话的事。

**第一句：常量要用 `const` 来修饰。** 它的关键字就是 `const`，你只要看到 `const` 就知道这是个常量，没什么好说的。

完整格式是：

```go
const identifier [type] = value
```

`identifier` 就是变量名称，后面这个类型你可以写也可以不写。

**第二点：常量在定义的时候就必须初始化。** 这点一定要注意。

```go
var num int      // 变量可以不赋值，它有默认值 0
const tax int    // ✘ 报错
```

一保存就有错误提示：`const declaration cannot have type without expression`——**你后面没有一个表达式。** 言外之意就是：**在声明的时候必须给值。常量就必须给值，如果不给值就违反了它的语法，哪怕给它一个 0 也可以。** 给 0 和不赋值，含义是不一样的。

**第三点：常量不能修改。** 常量一旦定义好了就不能改。`num` 做完后我可以改它，原先默认是 0，我给它一个 90 没问题，它是变量。但常量原先是 0，我要给它改成 10——对不起，报错 `cannot assign to tax`。**常量就是不能改的，不许你改。**

**第四点：常量只能修饰布尔、数值和 `string`。** 也就是说常量不能去搞其他类型——**你不能去搞一个切片。切片的目的本身就是可以变的，结果你搞个常量，那肯定错了。** 所以说白了，常量只能修饰基本数据类型。

#### 为什么 `const b = num / 3` 不行

常量还有一点特点，我们来做几个题，看看这几个对不对。

```go
const b = 9 / 3     // ✓ 可以
```

这个是 OK 的，因为 $9 / 3$ 是个固定的值——**因为 9 和 3 是常量值。**

那如果说老师我把这个 9 改成一个变量呢？

```go
var num = 9
const b = num / 3   // ✘ 报错
```

这就错了。**注意：你之所以说这个 `num` 等于 9，是因为你是人，你一眼就看出来了，编译器不知道。** 编译器认为：你这个 `num` 将来是可变的，这个值将来是不确定的。

**为什么编译器不能接受这种写法呢？因为编译器的常量是需要在编译的时候就确定这个 `b` 到底是多少。** 而你这种写法是不确定的——假如你这个 `num` 是通过控制台输入的，怎么办？那编译器怎么知道？**那就变成运行时了，所以这个写法是错的。**

同理，下面这个显然也是不对的：

```go
const b = getValue()   // ✘ 报错
```

**因为刚才大家都知道，只要是常量，那这里头就必须是确定的值。** 而这个 `getValue` 如果能接受，那就意味着你这个函数将来返回值可能是随便变的，所以这个也是错的。

#### 两种写法，以及 iota

常量有两种比较简单的写法。第一种比较简洁：

```go
const (
	a = 1
	b = 2
)
```

这样子相当于你有多个常量，用这种小括号的形式把它写进去就完事了。

还有一种形式是比较"专业"的，很多 Go 程序员写久了喜欢这么干，显得很专业：

```go
const (
	a = iota
	b
	c
	d
)
```

**`iota` 是什么意思呢？** 就是表示给 `a` 赋一个 0——其实这个 `a` 就是 0。下面不给值，就代表在这个 0 的基础上依次加 1。换言之 `b` 等于 1，`c` 等于 2，`d` 等于 3。**就这么一个简单的东西，不就是赋一个 0 给它吗？它自己定的一些常量在这里面，表示一个预定义的值。**

```bash
go run main.go
```

```text
0 1 2 3
```

完全正确，没有任何毛病。

**顺便说一下作用域**：`const` 如果定义在 `main` 函数里边，它就是局部常量；如果写在外边，就是全局的常量。

**最后是访问范围的问题。** 很多编程语言一般推荐常量使用大写，比如 PHP、Java、C 语言里一般都有这种规定。**但在 Go 里面没有这个规定——Go 没有说常量必须大写。** 我们上午还用到过时间单位，它就不是全大写的，这个要注意。

**但是常量仍然是有访问范围的问题的，它的访问范围机制和原先讲的变量一模一样**——也就是说，它要是一个全局的，也是通过首字母大小写来控制访问范围的。这个大家清楚一下。

#### iota 的两个常见疑问

最后有两个同学提出的好问题，我觉得挺好，说一下。

**疑问一：在常量里面，在一行里赋多个 `iota`，它是不是都是同样的一个值？**

**是的，写多少遍都是一个值。**

那如果用逗号隔开赋两个 `iota` 呢？

```go
const (
	a = iota          // 0
	b                 // 1
	c, d = iota, iota // c = 2, d = 2  ← 同一行不递增
	e                 // 3  ← 换一行才继续递增
)
```

`a` 肯定是 0，`b` 在上面递增 1，所以是 1。**到了 `c`、`d` 那一行给了它一下，`c` 是 2，而 `d` 还是 2——就相当于说这个地方就没有再递增了。** 换一行是不是它又变 3 了？**对，换一行。** 我们认为它是一行来进行递增一次，这样就又变成 0、1、2、3 了。

**疑问二：只要在后面再遇到新的 `const`，`iota` 又变成 0。**

再写一个新的 `const`，那肯定是重新算的。**这个显然应该这么干——你写了一个新的东西，那个 `iota` 它只是在这个范围起效。** 说白了就这个意思。

**很好，咱们有同学提出这样的观点是一件好事，大家不能嫌烦。** 我还是恢复到最初那个最常规的写法，因为**最多常规的用法还是这个写法用得多一点**。

总结一下 `const` 的使用注意事项，一共四点：

1. **写法上**有两种：一种是简洁的放在一起；另一种是用 `iota`，它可以达到一个自增的效果，看起来比较专业；
2. **Go 语言没有说常量必须大写这个要求**，很多其他语言是有的，我们这儿没有，所以你写小写也是很规范的一种写法；
3. **常量的访问范围仍然是通过首字母的大小来实现的**，范围的控制跟以前是一样的；
4. **常量在声明时必须给值、不能修改、只能修饰布尔和数值和 `string`。**

明白这个道理过后，常量这块就 OK 了。
