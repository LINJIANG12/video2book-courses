## 稀疏数组:别让一屏的 0 占满你的磁盘
> 对应块：BLK137 | 覆盖分集：P345-P346 | 块标题（分集名）：《343_尚硅谷_数据结构和算法-稀疏数组介绍》

### 下到一半,想去上个厕所

上次我们把数据结构的基本概念讲了一遍,也说清了它和算法的关系——数据结构是算法的基石,一个算法往往就建立在某种数据结构之上。今天开始,我们一个一个来看:在实际开发里到底会用到哪些常见的数据结构。

这里先说两条学习上的前提,因为它会直接影响你接下来几节课的手感。

第一,**一个数据结构总是跟一个具体的需求绑定**。所以学数据结构的方式不是背定义,而是"看需求 → 导出数据结构"。今天这个稀疏数组,就是从一个再普通不过的需求里长出来的。

第二,今天这一章会比你前面学的文件编程、JSON 序列化和反序列化抽象一点。文件读写和 JSON 那套东西,照着模板写就能跑;而这一章需要你动脑筋去想"它为什么要存在"。所以你写着写着突然觉得思路不畅通、甚至怀疑自己是不是不会编程了,这种错觉很正常,我当年也一样。

来看第一个数据结构:稀疏数组(SparseArray)。

先说需求。我们要写一个五子棋程序,这个程序有一个功能,叫**存盘退出和续上盘**。

什么叫存盘退出?就是你棋下着下着,突然想去趟厕所,但又不想直接退出认输。对方说,那咱们先存盘再退出吧,你一点"存盘退出",程序就得把你当前这个二维数组的棋盘给记录下来。

我们约定好:没有下棋子的地方用 `0` 表示,黑子用 `1`,蓝棋用 `2`。

第一种做法:什么都不优化,把二维数组原封不动地存下来。棋盘是 $11 \times 11$ 的,11 行 11 列,黑子标 1,蓝子标 2,其他地方全是 0。

功能上当然一点问题没有。但你想想这样到底好不好?

假设这个棋盘上只有两个棋子,你却为了存一个 1 和一个 2,存了 $11 \times 11 = 121$ 个数,其余 119 个全是 0——这些 0 是没有意义的。你想,这肯定不划算。

有人会说:一个棋盘不就那么点东西吗,无所谓。**单看一个人玩,确实无所谓。**但你想想,将来你做的是 C/S 结构,类似的问题多得很。我只是抛砖引玉:将来你做一个游戏,网游也好,普通 C/S 结构的游戏也好,保存地图这类需求满地都是。数据量一大,不加处理,第一是占磁盘空间,第二是效率不高——因为你恢复的时候得一个一个把它恢复回去,很不划算。

> **易错点**:这一类问题里,"功能能不能跑通"和"做得好不好"完全是两码事。第一种写法一定能跑,可它把 90% 的资源花在存 0 上。

### 稀疏数组到底存了什么

既然这样,我们就得想:有没有一种方法能把它解决?

解决思路其实很朴素——**那些没有意义的数据、默认的数据,干脆不记录,只记录有意义的数据**。这就叫稀疏数组。

官方的说法是这样的:当一个数组中大部分元素为 `0`(当然也可能是其他某个固定的值),或者大部分元素都是同一个值的时候,可以用稀疏数组来保存这个数据。

它的处理方法分两步:

- **先记录数组一共有几行几列**。为什么要记这个?因为有些编程语言在定义数组时,行和列可以是一个变量、可以临时输进去;只是我们 Go 语言这边必须写死。但数据结构不是只服务于 Go 语言的,所有语言都适用,所以标准做法是先把行列记下来。
- **再把那些具有不同值的元素,连同它的行号、列号和具体的值,记录在一个小规模数组里**,从而缩小程序的规模。

一个标准的稀疏数组长什么样?打个比方:先做一个 $n \times 3$ 的数组,列数写 3 是固定的,行数写 $n$ ——因为将来到底有多少个有效数据还不知道。先在第一行记下原始规模:6 行、7 列,第一列叫 `row`(行),第二列叫 `col`(列),第三列叫 `val`(值),默认值全为 `0`。之后再逐行往下追加每个有效数据:第 0 行第 3 列的值是 22,第 0 行第 6 列的值是 15,依此类推,最后一条是第 6 行第 2 列,值是 28。

这个 $n \times 3$ 的形式,就是稀疏数组的标准长相:**表头记规模,下面每一行记一个有效数据的位置和值。**

### 从 42 个数到 24 个数

来看一个经典案例。原始二维数组里,真正不为 0 的只有 8 个数据。如果要把它保存起来,该怎么办?

第一步,记下它一共有几行几列:6 行、7 列,也就是 $6 \times 7$。

第二步,记下有多少个有效数据。

第三步,把具体的数一条条记下来。

这么一算就很有意思了:原始数组 $6 \times 7 = 42$ 个数据,现在算上表头一共 8 行 × 3 列 = 24 个数据,规模一下子就缩小了。

而且这还只是一个很小的地图。实际开发中地图可能会非常庞大,而且这种大数组往往不止一张。这样处理,相当于把数组**压缩**了。

> **结论**:稀疏数组本质上就是一种压缩数组,它的原理和压缩算法完全一样——把有用的数据记录下来,把没用的、默认的数据直接丢掉。

打个你一定见过的比方。一段字符串:"汤姆汤姆汤姆汤姆汤姆abc","汤姆"一共出现了 5 次。最基本的压缩思路就是:把相同的字符串只记录它出现的次数,再把不同的部分记录下来,拼成一个新串发过去;对方收到后解压,又恢复成原样。只是有些压缩算法会比这个复杂得多。

原理就是这么个原理。那有人面试会问你:"同学,假设我们聊天时有人发了一篇很长的文章,请你设计一种方式,能不能把这个字符串做一个简单的压缩再传递?"

你可以非常干脆地回答:"可以。"——先把我这一段内容检索一遍,发现里面有很多重复的字符串,然后给对方先发一个大致说明:我这个串里有哪些内容、各出现多少次。比如 Tom 有几次、Jerry 有几次。原始内容我就不发了,直接告诉对方这些;对方解压,又还原出原始字符串。基本原理就是这样。

### 动手:把 $11 \times 11$ 的棋盘转成稀疏数组

原理讲完了,来实现一把。

新建章节 `chapter20`,在里面建一个文件夹,叫 `sparsearray`,再新建 `main.go`。

#### 原始数组先跑起来

```go
package main

import "fmt"

func main() {
    // 第一步:创建原始数组,假设是 11*11 的棋盘
    // 1 表示黑子,2 表示蓝子
    var chessMap [11][11]int

    chessMap[1][2] = 1
    chessMap[2][3] = 2
```

先把原始数组打印出来看看长什么样,用 `for range` 遍历两层:

```go
    for i, v := range chessMap {
        for j, v2 := range v {
            fmt.Printf("%d\t", v2)
        }
        fmt.Println()
    }
```

外层的 `i` 和内层的 `j` 这里都没用上,没用到的先把它们忽略掉。

在终端里 `go run main.go` 跑一下,你就会看到当前这个二维数组的样子——跟脑子里想的一样,有一个 1,有一个 2,其余全是 0。

这个时候问题就来了:这样存盘的话,它一共有 $11 \times 11$ 个数据,规模太大了,不合理,得转成稀疏数组。

#### 为什么必须是切片和结构体

问题来了:老师,我要把它转成稀疏数组,怎么转?

**显然,你事先并不知道它有多少个有效数据。**在 Go 语言里面,你只能使用切片,因为程序不知道你这儿有一个 1 和一个 2,你事先也没办法知道。

用切片的话,怎么保存比较好?我觉得最好的一种设计方式,就是直接用一个结构体就可以了。结构体也可以做成数组——我在一个切片里放多个结构体,它就是结构体的一种切片,而**切片的本质还是一个数组**,所以这完全没有问题。

说老师这个算法好像很神秘。算法可以说是无处不在:冒泡排序我们说算算法;将来你做 Go Web 编程,别人让你把最近浏览量前十的商品排在最上面,你写的那段代码也叫算法。只不过有些是大家都认同的常规算法,比如语音识别、图像识别、文字识别那些有名的算法;还有些是你在实际开发中为解决一个小问题设计出来的方案,这也叫算法。我们今天这个,就是算法。

所以问题就落到了一个很具体的地方:**这个结构体该怎么设计?**

你想想它将来长成什么样子?不就是有行、有列、有值嘛。所以这个结构体至少应该有三个字段:一个是行,一个是列,一个是值。分析到这一步,东西就出来了。别把"解决问题"搞得神秘,这就是让你解决一个压缩的问题。

```go
type ValNode struct {
    row int
    col int
    val int
}
```

叫它"值节点"——后面我们还有好多节点,各种节点都有,所以这里用 `ValNode` 这个名字是对的。

> **提示**:`row` 和 `col` 肯定是 `int`,因为行和列不可能是小数下标,没有"2.5 行"这种说法。但 `val` 不一定——如果将来这个值是小数或者字符串,那你把 `val` 写成 `interface{}` 接口就可以了,没问题,根据你的需要来走。

结构体定好,切片就可以定下来:

```go
var sparseArr []Node
```

我将来这个就叫 `sparseArr`,我就认为这是一个稀疏数组了。它是以这种节点切片的形式实现的,一共有多少个?不知道。

#### 遍历收集有效值

思路是这样的:第一步,遍历 `chessMap`;如果我们发现有一个元素的值不等于 0,我们就创建一个结构体,把它放到对应的切片里。

这段遍历代码和刚才打印的那个很像,有些地方不一样——这里不用打印了,而是要开始判断,假设这个值不等于 0,你必须全部扫描一遍:

```go
    // 第二步:遍历原始数组,把非 0 的值转换成值节点,放入稀疏数组
    // 注意:声明 ValNode 之前已经定义好结构体
    var sparseArr []ValNode

    for i, v := range chessMap {
        for col, v2 := range v {
            // 如果不等于 0,说明这是一个有效的值
            if v2 != 0 {
                // 创建一个值节点
                valNode := ValNode{
                    row: i,
                    col: col,
                    val: v2,
                }
                // 把值节点,追加到稀疏数组
                sparseArr = append(sparseArr, valNode)
            }
        }
    }
```

你会发现,刚才在打印时"没用上"的 `i` 和 `col`,现在全都有用了:你现在是第几行 `row: i`,第几列 `col: col`,值是多少 `val: v2`。按顺序扔进去就行了,`append` 一下就可以。

经过一番遍历,有效数据就被我们收进去了。但这里有一个**巨大的问题**:我们做的还不是一个标准的稀疏数组。

#### 补上表头,做个标准的

标准稀疏数组的前面,还应该有一行记录原始数据的规模和默认值——原始是几行几列,默认值是多少。这个必须补上,才算"标准的"。

不过在 Go 里,这个行和列的意义确实不是特别大:**Go 语言定义数组的时候必须把长度写死**,你要是想恢复成一个任意规模的二维数组,就得想办法做成切片性质的东西,那意义就不大了。但既然是标准做法,你也可以把它记录下来,所以我们就记。

要补这个头也很简单,因为行和列我们先前就知道了,初始化一个节点加进去即可:

```go
    // 把数据放入到稀疏数组中,第一个节点记录原始数组的规模和默认值
    valNode := ValNode{
        row: 11,
        col: 11,
        val: 0,
    }
    sparseArr = append(sparseArr, valNode)
```

这个节点是原始的一个节点,行和列都写死:第一个是 11,第二个是 11,默认值是 0。

然后把整个稀疏数组遍历打印出来看看:

```go
    // 遍历稀疏数组
    for i, valNode := range sparseArr {
        fmt.Printf("%d: %d %d %d\n", i, valNode.row, valNode.col, valNode.val)
    }
```

这里的 `i` 代表它是第几个值节点,冒号后面依次是它的行、列和值。跑起来之后你会看到:

```text
0: 11 11 0
1: 1 2 1
2: 2 3 2
```

原来那么大的一个数组,变成这么几行了。

### 这个"标准表头",在别的语言里价值更大

这里值得多说一句,因为它正好照出了语言之间的差别。

原始数组 $11 \times 11$ = 121 个数,现在一下子变成 3 条数据。这个好处是实打实的。而且对于某些编程语言来说,它的行和列可以直接从这儿读出来,直接初始化一个新的二维数组——你看 Java 里面、PHP 里面,直接把这个读出来就知道你原始规模是什么,这多舒服,而且还可以动态变化:你原始规模是 10 × 10 也照样成立。

只是 Go 语言里这个必须写死,所以稀疏数组在 Go 里面用得不是特别顺手,但也有别的办法,用切片。

> **结论**:如果你的脑子里从来没有"压缩"这种思想,从来没想过这事,那其实挺失败的。你看为什么有些程序员代码一跑起来又省内存、速度又快,还"感觉到很有灵魂"?因为人家脑子里是有想法的。

当然,从代码功能上说,"直接存原数组"也完全能实现,多占点空间、多占点内存、速度稍微慢一点,对不对?无所谓。但你既然知道有更好的,就应该想着怎么让它变得更小一点。

### 从存盘退出,到续上盘

现在有了这个东西,你得反过来用它——把它存到磁盘里。因为你的目标不就是希望将来能"存盘退出"吗?那你得把它写到磁盘上,等别人要恢复的时候,再把它读出来,还原成原来的数组。

这里又得动脑筋了。前面我们讲过怎么把东西存到文件里面,大家回忆一下是在哪一章讲的?不记得没关系,翻回去找——有 `reader`,那是读;还讲过一个存。它里面有一个是一次性写入的写法,**那个肯定不合理**,咱们不能用。我们肯定是一行一行地存:**一条有效数据存一行**,第一行存一行,第二行存一行,每写一行后面跟一个换行。

所以你可以这么写:新建一个文件,名字取 `chessmap.data`——注意后缀无所谓,一般我们自己定一个格式,`.data` 就叫数据。以写的方式打开它,把稀疏数组遍历出来的每一行做成一个串,用空格隔开,一行一行写进去,最后关闭。

我们遍历稀疏数组的那段 `for` 循环,正好就是写入的位置。前面打印时带的 `0:`、`1:` 这种序号只是为了让你们看得方便,真正存进文件里是不带它们的。所以最后文件里应该是这样:

```text
11 11 0
1 2 1
2 3 2
```

就这么三行。压缩过后的文件里,真正存着的就是这么一点数据。这个文件就叫**存盘退出**的产物。

接下来是**续上盘**:把这个文件重新读出来,恢复成原来的数组。

这一步其实非常简单,因为你在遍历地图的时候,**完全可以直接恢复成原始的数组,没必要先恢复成稀疏数组再恢复一次**——你这个中间步骤完全没有必要这么走。你每遍历一行、每遍历一个数,就知道现在第一个数是 `0`,那就把它初始化出来就行了。

至此,一次完整的"存盘退出 → 续上盘"闭环,在稀疏数组这个数据结构上就打通了。

## 把棋盘读回来,顺便看清队列的脸
> 对应块：BLK138 | 覆盖分集：P347-P348 | 块标题（分集名）：《345_尚硅谷_数据结构和算法-稀疏数组转原始数》

### 恢复:一行读进去,一行还原回去

上一节我们把棋盘转成了稀疏数组,也打印出来了。但那只是演示——真实场景里,这个稀疏数组是得**存盘**的,而恢复的时候,是得**从文件里读**回来的。

恢复的思路特别朴素:**遍历这个文件,遍历一行就往数组里扔一行。**

我演示的时候图省事,直接从我手里这个 `sparseArr` 切片来恢复,没有真的走文件。但因为我现在又多了这一步:我直接遍历这个稀疏数组,把节点一个个取出来,取出来往原始数组里填。**你们真正做的时候是遍历文件**,把那个 `reader` 拿出来读一行、处理一行、把行分割一下——道理完全一样,循环地读不就这么回事吗,原先讲文件读的时候那段代码你再回忆一下。

先创建一个准备恢复出来的原始数组:

```go
var chessMap2 [11][11]int
```

> **提示**:标准的写法应该是"先读出 `11` 和 `11` 这两个数,再根据它们决定你要开多大的数组"。但前面讲过了,Go 语言创建数组时必须直接指定具体数值,所以你可以先做切片、用切片来维护。我这里就直接写死了。这个"必须写死"的特点,是 Go 语言和 Java、PHP 这些语言差别最大的地方之一。

数组建好之后里面全是 `0`,现在肯定是全 `0`,跟原始数组还有差距,得开始往里面放东西。放什么呢?**遍历稀疏数组 `sparseArr`**,把每一个值节点取出来。取的时候下标对我没用,我忽略;每一个值节点是有用的。

```go
for i, valNode := range sparseArr {
    chessMap2[valNode.row][valNode.col] = valNode.val
}
```

非常直接:找到这个节点里的行 `row`、列 `col`,把它的值 `valNode.val` 放进去。

这里你可以放心的是,你稀疏数组里存的肯定都是有效的、非 0 的数据,而 `chessMap2` 其它位置默认就是 `0`,所以**不用动的就别动了**。

最后把 `chessMap2` 遍历打印出来,加一句说明:

```go
fmt.Println("恢复后的原始数据")
```

### 那个"数组越界",以及表头真正的价值

一运行,报错了——第 79 行数组越界。

来,我们看看问题出在哪。报错的这一行就是上面那句赋值。为什么?

非常明显:**因为我们稀疏数组的第一条记录是 `11 11 0`**,而这个值被你当成一个普通的数据节点给扔进去了呀!你想想看,`chessMap2[11][11]` 越界了吧?数组下标最大才到 10。

那么第一行这个 `11 11 0` 是什么?它记录的是**你原始二维数组的规模**。在恢复时它暂时没用,但它的真正价值在别的地方——如果将来要开一个对应规模的二维数组,就得靠它来确定开多大。**在 Go 语言里因为长度写死,这两个数据我们跳过就行**;在 Java、PHP 里,读出来就直接能 new 出对应尺寸的数组,那才是它发挥价值的地方。

那怎么跳过?非常简单——**第一次进来的时候先跳过第一行**:

```go
for i, valNode := range sparseArr {

    }

```

因为第一次取出来的下标肯定是 `0`,不等于 `0` 我才去恢复。

你注意,这个 `i` 在这儿终于发挥重要作用了——它就是干这个用的。

再跑一遍,没问题了。你会看到中间这个过渡非常清晰:这是原始数组,这是稀疏数组,最后恢复完又变回了这个数组。

### 换个新的数据结构:队列

好,稀疏数组就介绍到这里。接下来我们看另外一种非常常见的数据结构,也是你们前面经常用到的一种:**队列**。

前面讲 Redis 的时候,其实就遇到过队列这么一种用法。在现实生活中和编程过程中,都大量存在这种"以队列的方式来对数据进行处理"的应用。

最典型的就是**排队**。比如来一个人排队,你做一个叫号系统,先来的人应该先被服务,后来的人后被服务。**你别整反了**——整反了就是先来的一直在那儿等着没人管,后来的人全被先送走,那这个系统就出问题了。

编程里还有哪些地方会用队列?比如留言板,谁先留言谁总是排在前面——当然这已经掺了排序,但队列这个形式本身到处都是。

### 队列是什么:有序列表加先入先出

首先,队列是一个**有序列表**。

注意,我说的"有序"不是那个排序的有序——不是从大到小、从小到大那个叫排序。我说的有序是指:**它的数据是按照一定顺序排的,你先进去的排在前面,后进去的排在后面**。这就叫有序列表。它可以由数组来实现,同样也可以由链表来实现。

哪一种实现更难一点?准确地讲,**链表实现相对简单一些**;数组实现其实相对麻烦,尤其是用环形数组来实现队列,那还是比较麻烦的,待会儿理解起来有一定难度。

队列还有一个最重要的特点,那就是**先入先出**(FIFO):先存入队列的数据要先取出来,后存入的数据后取出来。

> **结论**:以后别人问你队列的特点是什么,你必须答上来两条——**第一,遵循先入先出的原则;第二,在编程里我们一般用数组或者链表来实现队列**。这两个答上来,别人至少知道你是有一点计算机底蕴的。

顺便记一下这个词:队列有一个专业的技术术语叫 `queue`,Q-U-E-U-E。以后你在代码里看到 `queue`,就知道人家说的是队列。Redis 那个我们前面碰到过。

### 数组模拟队列的老毛病:前面的空间白白浪费

我们用数组的形式来把这个队列画一遍,你就明白后面为什么要搞环形的了。

假设有一个数组,一共五个格子,编号 1、2、3、4、5。我们横着放,看得清楚一点。当我们存数据的时候:首先存在第一个位置,这是**队首**;再放数据就存在它后面,再放还是存在后面,不停地往后存。

```text
下标:   0     1     2     3     4
      +-----+-----+-----+-----+-----+
      |  ●  |  ●  |  ●  |     |     |   <-- 入队: 从队首往后一个个放
      +-----+-----+-----+-----+-----+
       rear  rear  rear
       (跟着入队往后挪)
```

取的时候呢?从最前面取走,再取一个取走,再取一个取走,再取——没有了。

你可能会问:老师,这个数组后面不是还有吗?不行。你要那么去取,那它就不是队列了,它就是个纯纯的数组。

这里就出问题了。原先数组里三个元素,当你取走一个的时候——**注意听,大家思考这个问题**——这个队列的队首就往后跑了,它变成了队列的第一个。

```text
下标:   0     1     2     3     4
      +-----+-----+-----+-----+-----+
      |  ●  |  ●  |  ●  |     |     |   <-- 取出第一个之后
      +-----+-----+-----+-----+-----+
            front(不包含)      rear(含)
```

这种形式最大的问题是什么?假设再取走一个,队首又往前挪一格;这时候我又要往里面加数据,应该往哪儿加?**只能加在这个屁股后面。**所以它有队首和队尾:队尾永远指向最后那个元素。

于是就来了那个经典的问题:存完之后我要是再放一个数据,**放哪儿呢?后面没有了,说队列已经满了**——可你前面还空着两个格呢。怎么处理?

这就是要上算法的地方了。

有同学提过这样一个想法:老师,你推到后面没地方放了,但前面还有两个空间,你把它放到前面不就完了吗?

**你这个想法我们要在这儿打住——这种方式是不行的。**为什么不行?因为前面空着的两格里,东西是乱的,你怎么知道哪个空哪个不空?你到最后面要找前面,这就涉及算法了:你怎么在遍历的时候还找得到最前面那个?

还有同学知道怎么简单做:元素你先都放这儿,有人取走一个,你赶紧把前面整体挪一下,后面不就有空间了吗?**这个效率极为低下。**你队列要是很大,你移走一个把整体往前挪一下试试看?假设队列里有 1000 个数据,你移动一个,就得把剩下 999 个整体往前挪;再移动一个,速度有多慢?这样做下去,那就彻底完蛋了,那还用什么数据结构,你不用数据结构没准还快一点。

所以结论是:**用数组来模拟队列,最大的问题就是怎么有效地利用前面的空间。**这就引出了今天要重点讲的**环形数组**。

用数组实现队列一共有两种形式:第一种比较简单,但它不能有效地利用数组空间;第二种是环形的,用环形思想来实现队列。第二种比较烧脑,不是很容易理解,相对麻烦一点,但也还好。

> **提示**:数据结构这一块确实有点尴尬——你学完一个框架,就知道它能干什么;但数据结构学完,你有时候会觉得"不知道它在哪儿用"。所以要认真地听,这一课认真听还是很有收获的;你要觉得这个没用,那确实就没什么用。

### front 和 rear 的分工,以及那个容易懵圈的 -1

好,现在进入思路分析。用数组来实现队列,思想基本上都是这样的,但具体实现略有差别——我们大学里学数据结构时是一种写法,参加工作后你会发现有人是另一种写法,但整体思想是差不多的。

**第一个要点:必须有 `maxSize`。**不管你用不用环形思想,队列都有一个容量。你假设最多能存放五个数据,你不能存第六个。就好像我们排队,排到一定程度地铁关门了,不让你进去了,容量已经满了。

**第二个要点:队列的输入和输出是分别从前后端来处理的**,所以我们至少需要两个变量来表示它的队首和队尾。我这里用的是 `front` 和 `rear`——`front` 是前端,`rear` 是尾部、尾巴。

这两个指针的分工一定要记死:

- **`rear` 随着数据的输入而改变**,入队一个它就往后挪一格;而且在我这个设计思想里,`rear` 是**真真正正指向队列最后一个元素的,包含它**。
- **`front` 随着数据的输出而改变**,取走一个它就往后挪一格;但它**只指向队列的最前面,而且不包含那个元素**。

它们都初始化为 `-1`。看清楚,是 `-1`。

```text
                    rear(含最后一个)          front(不包含,指向待取位置)
空队列:   front = rear = -1

入队后:   front = -1        rear = 0
          [ ● ][   ][   ][   ][   ]   <-- front 停在 -1,不包含第一个元素

再取一个: front = 1         rear = 0
          [ ● ][ ● ][   ][   ][   ]   <-- front 指向下标 1,但下标 1 其实还没取走
```

`front` 这块没弄清楚,你待会儿看代码就会懵圈。等一下我说清楚:当 `front` 指到 `2` 的时候,其实这个数据已经取出过了——`2` 已经取走了,它相对指向队列的最前面,但不包含那个元素。

### 入队 addQueue 的两步判定

最后落到方法上。一个队列要完成它的基本操作,无非这么几个:

- `addQueue`:添加一个数据进队列;
- `getQueue`:从队列里取出数据;
- `showQueue`:显示一下这个队列。

其中**入队 `addQueue` 的处理需要两个步骤**:

- **第一步,尾指针后移**。当 `front == rear` 的时候,我们认为队列是空的;队列满了就用 `rear` 卡在一个上界上;
- **第二步,判断能不能存**。当 `rear` 到了队列的最大下标,也就是 `maxSize - 1` 的时候,再放就接受不了了,队列满。

也就是说,**当 `rear` 等于 `maxSize - 1` 的时候,我们就认为队列满了**。

顺便说一句为什么数组声明的长度要减一:下标肯定不能到最大值,这是基本常识。

你看,目前这个数组模拟队列其实是一个**非环形状**的,用完就没有了——最多放五个,放完就没了。所以这个方法比较简单、相对好理解,但它肯定不灵活。

代码怎么组织呢?我们先创建一个数组 `array`,为了好管理把它放进一个结构体里,作为队列的一个字段;因为这个数组要跟两个指针绑定,所以先创建这样一个结构体。里面三个字段:一个是 `front`,初始化为 `-1`;一个是 `rear`,表示队列尾部,也初始化为 `-1`;再加上 `maxSize` 和那个数组本身。

到这里思路就说完了,接下来就是正式实现代码——我们下节课就从这三个方法开始动手。

## 手写一个"用一次就完"的队列,然后逼自己绕回原地
> 对应块：BLK139 | 覆盖分集：P349-P350 | 块标题（分集名）：《347_尚硅谷_数据结构和算法-数组模拟队列实现》

### 先把 Queue 这个壳子立起来

打开 VS Code,新建一个文件夹,叫 `queue01`。这是我实现的**第一种**,不是环形的,可以认为叫 single——单单一的队列,它**用完就没有了**,所以叫 single queue。

新建 `main.go`,打上 `package main`,`import "fmt"`。

我们刚才讲过,队列里有这么几样东西:一个是数组本身,第二个是前后两个指针,或者说前后两个标识。所以我们直接用结构体,用一个结构体来管理我们的队列:

```go
type Queue struct {
    maxSize int
    array   [5]int // 数组
    front   int    // 表示指向队列首部
    rear    int    // 表示指向队列的尾部
}
```

里面包含这么几个数据:第一个是它的最大值,比如我们现在认为数组最大值为 4 个;第二个是真正存放数据的地方 `array`,我们认为它存 5 个数据;然后是 `front`,表示指向队列首部;还有 `rear`,表示指向队列的尾部。

注意这里有个思想:**光有这个数组没有用**——光有这个数组、里面没有操作,它真的就只是个数组。只有当这个数组被注入了管理的方法,它才变成了一个队列。大家要理解,**数组是一种数据类型,等到我们给它了一些操作,它就变成了一种结构,就带算法了。**

### AddQueue:两步,以及一个必须记住的约定

先给它提供第一个方法:添加数据到队列。

```go
func (this *Queue) AddQueue(val int) (err error) {
    // 先判断队列是否已满
    // 提示:rear 是包含最后那个元素的
    if this.rear == this.maxSize-1 {
        return errors.New("queue full")
    }

    this.rear++
    this.array[this.rear] = val
    return
}
```

注意听讲,这个队列看着写很简单,但你仔细想,还是很容易绕进去。

先看签名。你要 `AddQueue`,肯定得给我一个值——添加数据的时候显然要传一个值进来,假设叫 `val int`。那你添加的时候可不可能出错呢?**完全有可能。**打个比方,你往里面不停添加,要是队列满了怎么办?你加不进去了。所以它有可能出错,因此我们写一个 `error` 返回值。

那怎么加进去呢?队列的特点是**总是从它的屁股后边往里面加**。

**第一步,先判断队列是否已满。**有同学问:队列满不满我怎么知道呢?作为搞算法的人,你就必须得研究清楚什么叫"队列已满"。那肯定就是 `rear`——我现在不是环形的,你这个 `rear` 已经到了最后,你不停走走到这儿,再走就掉下去了,所以肯定是通过 `rear` 来判断。

**第二步,没满就加。**既然没满怎么办?你现在是在做数据结构,你要想清楚队列满了怎么办。那你就先让 `rear` 往后挪一挪:`this.rear++`。你之所以可以 `++`,是因为你现在还没到那个边界——到那儿了不可能再 `++`,再 `++` 不是跳出去了吗?后移一下,然后把数据放进去:`this.array[this.rear] = val`。放完了,恭喜你加成功了。最后这个 `return` 还是要打出去的,成功没成功可以通过这个 `error` 来判断。

> **提示**:这里有个**特别重要的约定**,你到时不听清楚一定会出问题。我这样一写,就意味着 `rear` **指向队列的最后,而且包含最后那个元素**。你要是没把这个分析出来,到时候会出问题——因为后面那个环形队列的设计**刚好是相反的**。到时你听到后边就完全要蒙圈。含最后那个元素,记住。

### ShowQueue:不能直接把数组打出来

加进去了,总得证明一下到底有没有成功,所以我们先写显示队列。

```go
// 显示队列,找到队首,然后遍历到队尾
func (this *Queue) ShowQueue() {
    // this.front 是不包含队首元素的
    for i := this.front + 1; i <= this.rear; i++ {
        fmt.Printf("array[%d]=%d\t", i, this.array[i])
    }
    fmt.Println()
}
```

有人会问:老师,简单啊,把这个数组直接输出来不就行了吗?不行。因为你将来要取,有可能取走了它就不能显示。

所以显示的时候应该怎么办?**要找到它的队首,然后直接遍历到队尾。**

那循环从哪儿开始?这里问题就来了——**到底这个 `front` 含不含队首的元素?**根据我的思路,我这个是**不含**的。我不含的原因是有讲究:看你的设计,如果你让它包含队首的元素,后面环形那套代码实现起来其实是比较困难的。前面那个元素刚来的时候是空的,它本身却"含有",从道理上很难讲通。当然你非要包含也可以实现,大不了前面加个判断,也行。

所以我这个设计思路是:`this.front` 是队首,**不包含队首的元素**,因此循环要从 `this.front + 1` 开始,一直到 `i <= this.rear`,到我们的屁股后边,`i++`,写完了。

打印的时候用格式化形式打出来,看得清楚一点:`array[%d]=%d\t`,打完一个加个 `\t`,下标就是 `i`,值就是这个数组里的 `i`。遍历完了就成功了。最后还可以打一句话,就是队列当前的情况是这样子的。

### main:一个 add / get / show / exit 的小菜单

写个主函数测试一下,非常简单。

```go
func main() {
    // 先创建一个队列
    queue := &Queue{
        maxSize: 5,
        front:   -1,
        rear:    -1,
    }
```

这里有几个坑,正好我们一起踩一遍。

**第一个坑:结构体字段的顺序。**`type Queue struct` 里面第一个字段是什么,我初始化时就必须对上。结构体没初始化对,编译器直接给你报错。

**第二个坑:`array` 不用管。**因为数组是值类型,创建的时候它就自然全给你初始化成零值了。所以这里 `maxSize` 填 5,正好对应"最多能存放五个元素"。

**第三个坑:`front` 和 `rear` 都初始化为 `-1`,**因为刚开始一个元素都没有。

然后我们写一个简单的菜单来测试。菜单我写一次,后面就直接粘贴复制了:

- 输入 `add`,表示添加数据到队列;
- 输入 `get`,表示从队列中获取数据,就是出队列;
- 输入 `show`,显示这个队列;

### GetQueue:front 是靠追上 rear 才算出空的

趁热打铁,把取队列写了。一个是入队,一个是出队。

```go
// 从队列中取出数据
func (this *Queue) GetQueue() (val int, err error) {
    // 先判断队列是否为空
    if this.rear == this.front {
        return -1, errors.New("queue empty")
    }

    // front 不包含队首元素,取之前先后移
    this.front++
    val = this.array[this.front]
    return val, err
}
```

出错的可能性当然也有:**取的时候不小心队列已经空了,你还在取,那就不行。**

那我怎么知道它为空了?这里有个特别容易搞错的地方——**不能说 `front == 0` 就等于空,这个说法不对。**最好的情况应该是 `front` 追到了屁股后边,`front` 跟 `rear` 相等了。你想想是不是这个道理:你每取一次它就往前走一次,一直走,走到跟 `rear` 一模一样、两边相等,就说明**它已经追上来了,队空了**。所以判断条件是 `this.rear == this.front`,这种情况就认为队列已经空了,直接 `return -1, errors.New("queue empty")`。

没有空那就取出来。但**注意,取的时候要先让 `front` 往后面移一下再取**,因为前面讲过,`front` 指向队首的前一个,它不含队首。所以先 `this.front++`,`++` 完了过后再把这个值取出来:`val = this.array[this.front]`。

> **易错点**:返回的时候要么两个都不写,要么两个都写上。上面那个满的判断也是一样的道理——你一直返回一个 `error`,`val` 没改,那就写个 `-1` 占位。因为到时候我们先判断这个 `err` 为不为空,再去取这个值;如果 `err` 不为空,说明肯定没拿到值,就不必去取了。

调用方就一句话:

```go
val, err := queue.GetQueue()
if err != nil {
    fmt.Println(err.Error())
} else {
    fmt.Printf("从队列中取出了一个数,这个数等于%d\n", val)
}
```

### 环形队列的思路:取模,和必须空出来的一个位置

刚才那个队列的缺陷,就是**没有有效地利用数组的空间,用它一次就完了**——好比一次性餐具,到餐馆里吃一次就没了,这肯定不合理。那怎么办?我们现在就用数组实现一个**环形队列**。

先做思考和分析。前面那个数组模拟队列的优化,就是在这上面优化,充分利用数组,**把数组看成一个环状的**。

#### 环是怎么转起来的:取模

这个环状的关键点在于**取模**。你到最后再往下走,虽然不能往后走了,但是我加一,它不就回去了吗?

举个例子:我们两个都跑这儿来了,我怎么让这个队尾 `rear` 到前面去?假设 `rear` 目前等于 4,我怎么让它的下标又重新回到前面去?一个最简单的方式就是:**让 `rear` 加 1,再模上它的最大值 `maxSize`**——当然要括起来,也就是:

$$(rear + 1) \pmod{maxSize}$$

这样一算,不又变回前面去了吗?它就有效地绕回去了。这是第一个思路。

> **提示**:这里我把它叫做 `tail` 和 `head`,你们就理解成队尾和队头;真正落到字段上,还是代码里那两个 `rear` 和 `front`。

#### 什么时候满:必须空出一个位置

那新的问题来了:**怎么判断这个环状数组它满了呢?**

条件是:**`(tail + 1) % maxSize == head` 的时候就表示满。**也就是说,尾部再加 1 模上 `maxSize` 之后等于头部,就是满了。

这里有一个**特别重要的约定**,用数组模拟环形队列时,**队列的容量要空出一个来作为约定**。这点不是特别容易分析出来——它一定要空一个,一个都不空的话很难实现。

这个约定是什么意思呢?假如我们这个地方快满了,尾部在这一边,`front` 在这边,加了一个,又加了一个,又加了一个。如果这个时候我们继续往前面再走一下,那么我们就得先去探测一下还能不能往后走——因为**我们要留一个位置出来**。所以在我们要去到 `(tail + 1) % maxSize` 的时候,得去看它到底还能不能往里面加,所以我们留出一个容量做一个约定。

什么时候为空呢?**尾部和头部相等的时候,我们认为它是空的。**跟原先一样的道理,不停地追,追到最后它们相同了,就认为是空。

#### 三个必须记住的结论

思路分析到这儿,有这么几个比较重要的地方:

- **满**:`$(tail + 1) \pmod{maxSize} == head$` 时表示满;
- **空**:`tail == head` 时表示空;
- **初始化**:刚开始的时候,`tail` 和 `head` 都等于 `0`。这跟刚才那个有点区别——等于 0 就相当于直接指向了数组的最前面,刚开始都指到最前面。

#### 元素个数怎么统计

还有一点要分析出来:**这个队列里到底有多少个数据,怎么计算出来?**

公式是这样:

$$(tail + maxSize - head) \pmod{maxSize}$$

为什么这么算呢?**因为理论上来说,尾部总是应该比头部要大的**,队列尾肯定比 `head` 要大。但是因为我们的队列到最后的时候会反过来跑到前面去,所以统计的时候,我把 `maxSize` 加上,再减掉它,再模上 `maxSize`,就对了。

举个例子:数据不停地走,`front` 初始化为 0,然后我加了一个元素 1,加了之后尾部往后面移一下,尾部变成 1。那我一共有多少个元素呢?头部这个地方相当于还没取,按公式来算:尾部 1 + maxSize 5 - 头部 0 = 6,而 $6 \pmod 5 = 1$,正是我们期望的结果。

当然这个大家可能还需要想一想,待会儿我把 maxSize 调小一点,调成 4,不然不好做测试。

有了元素个数,基本上就可以来实现它了。思路分析我们先说到这儿。

### 先把 CircleQueue 这个壳子立起来

打开 VS Code,新建一个文件夹,叫 `circleQueue`,别跟前面那个写在一起了。新建 `main.go`,`package main`。这个还是很多面试官喜欢去考的。

还是用一个结构体来管理我们的环形队列,当然还是用数组来模拟:

```go
type CircleQueue struct {
    maxSize int
    array   [4]int
    head    int
    tail    int
}
```

里面有个数组,它有一个最大值,假设我现在变成 4 个——到时候我们给它一个 4,5 个有时候不好测试,太宽了。里面的真正的数组还是 `array`,这个没有变化,还是 `[4]int`。

接着是它的尾部和头部。**前面那个队列我们用的是 `front` 和 `rear`,但也有些程序员喜欢用 `head` 和 `tail` 来写,也是可以的**——头和尾更形象一点。`head` 指向队首,`tail` 指向队尾。

有了这两个结构体,我们就来做主函数。主函数里面有些代码可以拿来用,前面那个提示性信息我直接粘贴拷贝过来了,这一系列的信息我可以拿来用一下。只是里面调用的方法会发生一点变化,取的时候也会有点变化,名字到时候可以改。

方法的名字这里顺便说一下:入队列我们还是用 `addQueue`,出队列仍然用 `getQueue`。不过有些程序员把 `add` 直接叫 `push` 也可以,推进去;栈我们可以叫 `push`,队列也可以叫 `push`。`getQueue` 也有人直接叫 `pop`,从队列里弹一个出来。大家看到我们前面学 list 的时候,也是这种用法。两个都行,我们换着用一下:

```go
func (this *CircleQueue) Push(val int) (err error) {
}

func (this *CircleQueue) Pop() (val int, err error) {
}
```

### 三个基础判断:IsFull、IsEmpty、Size

现在我们还迫切需要几个特别重要的方法。第一个是判断它什么时候为空、什么时候满了,这两个方法特别有用。

先看它是不是满了,`isFull`:

```go
func (this *CircleQueue) IsFull() bool {
    return (this.tail+1)%this.maxSize == this.head
}
```

直接返回哪一个条件呢?就是它的下一个——`tail + 1` 模上 `maxSize`,是不是等于 `head`。加起来过后再模上 `this.maxSize`,如果这两个相等,等于了 `this.head`,说明它已经追上来了。**但它中间留了一个位置**,所以是先判断加 1 之后再判断到底对不对。

然后判断是否为空,`isEmpty`:

```go
func (this *CircleQueue) IsEmpty() bool {
    return this.tail == this.head
}
```

为什么这么写?就是我不断地取,我终于把你追上了。`this.tail` 如果等于了 `this.head`,它们相等了,就说明我已经追上你了,最后跟你相同了。这个地方返回一个布尔值。

最后还有一个特别重要的函数:**能取出这个环形队列有多少个元素**。

```go
func (this *CircleQueue) Size() int {
    return (this.tail + this.maxSize - this.head) % this.maxSize
}
```

返回是一个 `int`。怎么返回它的大小呢?就是 `this.tail` 加上 `this.maxSize`——因为每次都在不断取模,把这个加起来,再减掉一个 `this.head`,看它们之间的差值有多大;差值还要再取一下模,模上它的最大值。

> **提示**:这个公式大家可能看起来有点吃力。为什么这样算?因为你想,这是个环形队列,大家都在不停地在后面动:它的 `head` 不停地加,加到快要出去的时候加了一个 `maxSize`,然后它又回去了。所以会造成 `tail` 在某个情况下它的自然值是**小于** `head` 的——`head` 在后面去了,但 `tail` 绕过来一圈了,所以要把它加上再减掉再模上。大家待会儿去推断一下这个算法对不对。**这个地方是很关键的**,这个地方如果没突破,这个环形队列就很难做出来。

### 为什么要预留一个空位

这个 `Push` 的第一步就是判断满:

```go
func (this *CircleQueue) Push(val int) (err error) {
    if this.IsFull() {
        return errors.New("queue full")
    }
    this.array[this.tail] = val
    this.tail++
    return
}
```

满了我就不能再加了,所以直接返回一个错误。没满的话,那太好了,就在它的尾部把这个数加进去。

现在这里有一个**必须理解清楚的地方**:它的尾部是**先放进去,然后再往后面退一步**。也就是说 `this.tail` 刚开始的时候确确实实指向队列的尾部,它包含队列的尾部。

> **结论**:但在环形队列里,`this.tail` 在队列尾部**却不包含最后一个元素**,它相当于最后那个元素后面再移了一位。

有同学会问:老师,你原先前面做的好像尾部刚好包含最后一个,现在为什么又不包含了呢?

告诉大家,如果包含的话这个就不好做。你想:我走、再加、再加,加到某的时候——因为其实真正的数据还在这,它真正的数据在前面这一个。等到我再加一个,我到这个地方来了。其实这个时候 `tail` 指向这个位置的时候,**这个地方还没有真正往里面放东西**。看到第四个空间是没有放东西的——因为我要把这个地方留下来当一个**标志位**。

那为什么要留这个标志位?在写的过程中你会发现,写了好久没有这个东西,你没办法弄。**用数组模拟环形队列,它实际的容量是这个数组的大小减 1。**如果你们试一下,最后不留一个约定、或者叫做标志,这个环形链表很难实现,很难实现。

为什么要这样做?就是因为做的过程中实在没办法,想来想去没办法,只能做一个约定。当然,如果你有一个办法,连最后这个都能用上,那你牛——反正是实现不了,那说明你真的很牛,你这样去试一下,实现了再说。

有两种方式:一种就是可以不留,但它需要再判断一下,那逻辑上看起来可能更复杂一点,我估计会多一点判断,因为在这个地方不留这个东西,不知道会出什么毛病。我这儿采用了一个**相对容易理解的**,就是留一个。这个代价影响也不大:比如你数组有 50 个元素,有一个没用,应该还是能够接受的,并不是说预留了很多。我采用这种方式,预留一个,最后做一个约定。

### Pop:跟 Push 恰好相反的那一面

出队列快速写一下:

```go
func (this *CircleQueue) Pop() (val int, err error) {
    if this.IsEmpty() {
        return 0, errors.New("queue empty")
    }
    val := this.array[this.head]
    this.head++
    return val, err
}
```

如果它已经空了,你就不能再出了,返回一个错误,叫 `queue empty`。因为他要求两个返回值,你这就没办法了,所以随便给他一个值吧,默认值 `0`。当然最后判断到底有没有弹出来,你可以先判断这个 `error` 是不是为 `nil`。

不为空就取东西。因为上面已经判断过是不是为空了,所以直接从 `head` 里面弹一个出来,然后把 `head` 再往后面移一下:`val := this.array[this.head]`。

注意这个和 `tail` 正好相反——**`head` 是指向队首的,并且包含这个元素**。所以当 `head` 在这个地方时,它是包含队首元素的。把它取出来过后,`this.head` 就要往后面移动一下,因为你已经弹出来了嘛,队首发生变化,往后面弹了一下,`head++`,然后 return。

### 怎么"显示"一个绕圈的队列

现在有 push 有 pop 了,但还差一个非常重要的方法,就是显示它。

显示队列多简单呀?你不是有一个队首吗、一个队尾吗,从队首开始遍历遍历到这儿不就完了吗?**不对。**因为你现在已经变成环形的了,就会出现这种情况:比如我这个队尾走走走,你这儿取了一个到这儿来了,取了一个到这儿来,突然因为某种原因我往前面加了一个——**那也就是说,队尾的下标有可能是小于队首的。**

所以说你现在不能说我就给一个 `front` 然后遍历,那遍历根本就不对,跑不起来,没准直接一歇就跑了。这个地方不能再用那种方式了,要显示队列我们得写一个新的方法。

那怎么显示呢?这个思路大家想想怎么做。先说我的思路,`showList` 一下,`ListQueue`。

首先你要看它先为不为空——为空的话就不要显示了,空队列懒得走。但**不能直接看队尾到队首**,所以说我们先取出当前队列有多少个元素,能理解吧?那就是 `size`,`this.Size()`。现在就有两种可能性:

- 一种 `size` 直接等于 0,它等于 0 那就是空的,就提示它:当前队列是个空队列,无法显示;
- 如果不为空,就 `for` 循环。

那 `for` 循环怎么循环呢?**从队首开始**,而且每加一次要加一个 1,再取一下 `maxSize`,这样才能找到它的位置。

所以我这样写,思路更清晰一点——我设计一个**辅助变量**,让它指向 `head`。头我不去动它,我做一个临时的头 `tempHead`,让它等于 `head`,然后让它跑 `size` 次:

```go
func (this *CircleQueue) ListQueue() {
    size := this.Size()
    if size == 0 {
        fmt.Println("队列为空,无法显示")
        return
    }
    tempHead := this.head
    for i := 0; i < size; i++ {
        fmt.Printf("array[%d]=%d\t", tempHead, this.array[tempHead])
        tempHead = (tempHead + 1) % this.maxSize
    }
    fmt.Println()
    fmt.Println("环形队列情况如下")
}
```

`i` 就是用来控制打多少次的;打完之后取这个值就是 `this.array`,把它的下标和值打出来,这个 `%d` 肯定就是它下标,没什么可说的。

然后把这个 `tempHead` 做一个处理:按理说它应该加加,**但如果仅仅是加加这要出问题,因为你现在是环形的**,所以说应该等于:

$$(tempHead + 1) \pmod{this.maxSize}$$

这样子它到最后才又跑回来嘛。你不这样处理的话比较麻烦。

> **易错点**:写这个循环时我漏了两处,编译器都给我指出来了——一是 `this.maxSize` 前面少了一个 `this`;二是 `tempHead = tempHead + 1` 这里**少了一个取模**。少一个 `% this.maxSize`,一跑越界就暴露了。

### 换个更硬的骨头:链表

上午我们讲了一下用数组来模拟环形队列,你们肯定会看到一些其他不同的方式。但不管怎么样,**它的核心思想都是一样的:标识元素的下标在到达队尾的时候,可以通过取模的方式又重新回到数组的前面。**

下面我们来看另外一种数据结构,这个数据结构确实非常有用。我为什么说它更有用、更有意思呢?**因为链表可以实现前面的队列,它还可以实现栈。**

还记得我们在前面讲 Redis 的时候,曾经有一个数据结构叫 List 吗?那个 List 底层可以用数组实现,也可以用链表实现。链表就很灵活了,这个数据结构可以做很多好玩的东西出来。

#### 链表在内存里长什么样

链表是一个有序的列表,但它在内存中的存储是这样的:比如说这有个头指针,这个头指针指向后面的各个节点,节点之间可以互相指向——下一个域我指向它,它又指向下一个,再下一个又指向下一个。

```text
head ──► [ 节点 ] ──► [ 节点 ] ──► [ 节点 ] ──► nil
```

> **提示**:在我们看来,你感觉好像它并不是完全连续的,这很正常。因为地址的分布其实还是由系统来决定的,这并不影响我们。**在我们来看,它就是有序的就行了。**将来有可能这个地址不是连续的,这个节点肯定指向 Tom,但地址不是说 11 之后是 15,它可能是另外一个地方引用过去的;可是从形式上来说,肯定是个有序的。

#### 为什么我更看重链表

先看一个单链表带头节点的结构。

最经典的案例是这样:我们这有一个 `head` 节点,它指向一个头节点。头节点里面有一个字段,这个字段又指向另外一个节点;另外一个节点里面又有一个字段,它又指向另外节点。

这个节点里装的内容我们可以随意,比如说是一个人 `Person`。这个 `Person` 假设有一个字段是名字叫 Tom,另外还有一个域叫 `Next`。那这个 `Next` 是什么类型呢?我们姑且认为它是一个 `*Person` 这样的类型:

```go
type Person struct {
    Name string
    Next *Person
}
```

里面有它自己的信息,比如 `Name string`;另外一个最重要的地方就是 `Next` 指针,它又指向什么呢?类型是 `*Person`。

假设我们有这么几个节点:一个叫 Tom,一个叫 Jacky,还有一个叫 Scott。用链表来管理它们可以这样管理:我先来一个头节点,**这个头节点没有具体的数据,就它专门用来做头节点而已**,里面的内容可以不给任何东西。然后头节点指向下一个,下一个节点再指向 Tom,Tom 指向 Jacky,Jacky 指向 Scott,这样就形成了一个链表的结构。

有同学会问:"老师,那这个链表它形成的意义有什么用呢?"

大家可以想象,现实生活中就存在类似这种结构。比如一群小朋友围成一圈丢手帕,我就可以形成一个环状的——这个地方让它再重新回来指向头节点,就是一个环状。如果不想做环状的,**它本身看起来也像是一个队列**,也就是说它又可以当成队列来使用。

更有意思的是:**它可以在我们的内存里面形成一些非常实用的结构,比如哈希。**比如说这个地方有一组人,将来假设有多组人,我可以这样干:这是一组,没问题;我还有一组,来,我还有一组;这又是一组人。假设你还有一组,我还有一组人。那么我可以让这么多组人形成什么呢?**形成一个哈希。**到时我在里面找某一组人的时候,我通过这个节点能很轻松地找到我哪一组人——我可以让外面的数组里的一个位置指向这组的头节点,还可以让数组里面的又一个地方指向另外一个头节点,让它跟另一组发生关系,等等等等。

所以它是非常有用的。

> **易错点**:我这张示意图画得有一点点不准确。这个图在 Java 或 C++ 里面是一个很精准的图,但是放在 Go 里面有一点不准确。
>
> 不准确在哪?因为在 Go 语言里,**结构体本身是一个值类型**。所以 `Next` 这个指针准确地说,它**并没有直接指向这个结构体**——它指向的是一个地址,再由这个地址去指向我们这个 Tom 真正的结构体。因为我们前面讲过,指针是先指向一个地址,再由这个地址指向真正的结构体。后面每一段都是这样:Jacky 的下一个节点本身是先指向一个地址,再由这个地址指向我们真正的结构体所在的内存空间;每个地址可能都不一样。
>
> 但这样画有时我画得很麻烦,看着也不舒服,所以我讲课的时候可能就把中间这个地址不画了,大家理解一下。

#### 链表 + 哈希:你自己的内存数据库

这就是我们链表最基本的结构。接下来我们就来完成对这个链表的增、删、改、查,通过这个练习我们就能知道链表是怎么用的。

有一句话我觉得还是比较到位的:**你可以这样理解,我们可以利用链表来做一个自己的、属于自己的内存数据库。**

什么意思呢?有些时候我们往往把数据放在数据库里面,没问题,但是那是人家的东西,是人家的东西。但是有些时候,你想自己去存放一个数据量比较大的数据,而且你还要让它具有很好的扩展性,比如你在内存里面存放的数据有增删改查的功能——这个时候,**链表加上哈希,就是链表配合哈希的算法,就是非常不错的一种结构。**

这就是为什么后边我给大家讲散列的时候,散列加上散列本身就是一个哈希,然后配合链表,这相当于说你自己可以做一个小小的、内存的数据管理机制——这可就上档次了,明白吧?有人说:"那是不是意味着我们将来自己想去搞一点数据,自己在内存里面把它维护起来,有增删改查的功能,是不是就可以了?"就是这个意思。

所以链表这个必须学会。看起来它虽然不是很难,但是它很有用。反正以前我在工作中,说实话队列我还用得比较少,但真正用到的链表还是不错的,是个好东西。后面我们还要把它进行一个扩展。

### 单链表的头节点:只认位置,不存数据

把链表的基本介绍整理一下:**链表是一个有序的列表**,它在内存中的存储可能不是连续的,但是在形式上体现出来,肯定必须是一个有序的。

接下来我们来看一个单链表。单链表一般来讲会带一个表头,这样会容易一点。

一般单链表都会带一个表头。一般来说,**为了比较容易控制这个链表、为了比较好地对单链表做增删改查的操作,我们都会给它设置一个头节点。**

那这个头节点是什么玩意儿呢?我强调一句:**头节点主要是用来表示它是链表的头,它本身并不存放数据。**

它的作用、它的价值,主要是用来标识链表的头。**这个是不能动的**——一旦头没有了,那你整个链表就完全找不到了,你头都没有了,肯定没法下手了。头节点本身一般不存放数据,空着就空着。

好,这就是我们单链表的一个基本介绍。下边我们就来做一个应用实例。

打开 VS Code,新建一个文件夹,单链表就叫 `single link`,然后写一个 `main.go`。

**这个我要求同学们背下来的,这是必须的。**你听完这课过后,必须在脑海里面形成链表的感觉,知道它可以完成很多事情。

首先定义英雄节点。因为你操作的时候就是对这些节点进行操作,所以肯定先得把这个节点定义出来:

```go
type HeroNode struct {
```

### 第一种插入:在链表最后加入

#### 第一步,创建头节点

我们先做初始化。**第一步,先创建一个头节点**——这个头节点刚开始就得有,不管怎么样,先把这个头节点整出来:

```go
head := &HeroNode{}
```

这里面的东西都可以不要,它就是一个空的,啥都没有,所以里面根本不用给它赋值,都是默认值。头节点不需要给值,先采用默认值。

#### 第二步,创建一个新的英雄节点

```go
hero1 := &HeroNode{
    no:       1,
    name:     "宋江",
    nickname: "及时雨",
}
```

那么它的下一个节点是多少呢?**这个没办法定。**它的下一个节点到底指向谁,要在链表里面去确定,所以这个地方我们先空着。

#### 第三步,写插入方法

现在开始写给链表增加、或者说插入一个节点的方法。怎么把它插进去呢?非常简单:**你必须先要告诉我头节点是谁**,然后找到合适的位置把它插进去。

```go
func InsertHeroNode(head *HeroNode, newHeroNode *HeroNode) {
```

这里要强调一下:**头节点是个至关重要的点,没有头节点一切玩完。**甚至头节点一旦丢失,你整条链表都没有用了。所以头节点不能乱动,这个头节点只要乱动了就麻烦。

#### 跑龙套的 temp

在这个函数里面,现在已经拥有了头节点和新节点。那怎么加呢?我们的思路是:**先定位该链表的最后一个节点。**

有人说:"老师,这个最后节点不就是头节点吗?"**不一定。**因为你现在第一次,刚好看到就是头节点,但是加了宋江、再加卢俊义,那最后这个节点就是宋江了,所以你还得想办法找。

怎么找?**头节点不能动,所以我需要一个跑龙套的。**我先给一个辅助节点,它为什么叫跑龙套的呢?因为它帮我们做了很多工作,它是帮忙的。

```go
temp := head
```

`temp` 现在就指向 `head` 了。那它有什么用呢?**我让这个 `temp` 找找找,把它定位到最后。**

```go
for {
    if temp.next == nil {
        break
    }
    temp = temp.next
}
```

各位同学想想,为什么这个条件成立就意味着 `temp` 已经到这条链表的最后了?**因为只有最后一个节点的 `next` 才是空,才是我们链表的最后。**

现在你在脑海里这么去想:目前我们的内存里已经拥有了 head,指向了头节点;现在又创建了 hero1,宋江,准备把它加进去。宋江这个节点现在已经创建好了,它现在有了名字,叫宋江。宋江现在要想办法跟它关联起来——就是我要把这个节点连到头节点去。

它们之间还没有关联起来,他是他,他是他。那怎么关联?进到循环里,一判断 `temp` 下一个等于什么?你现在这个地方肯定是个空,因为你刚开始建的头节点啥都没有,所以它是 `nil`。我一看,你这个 `temp` 就是最后。那我就让这个 `temp` 把它关联起来——**让 `head` 的这个地方指向宋江。**

条件成立就表示找到最后了,找到最后我就不要再找了,`break`。

`break` 出来过后,有一个动作非常重要。你这个地方走运了,`temp` 刚好第一个就等于 `next`;**但是你不敢保证下一次是**,所以这里有个非常重要的工作——**你得让 `temp` 不停地往下走。**

因为你现在是第一次,第一个刚好找到了;但是将来假设是这个情况:`temp` 指向这儿了,第一个不是空,第二个不是空,你要去看它下一个是不是空,你的 `temp` 不得往下走吗?假设你的链表已经有三个元素了,你让 `temp` 指向它,肯定第一个不是空;然后你往下走一下,判断它会不会空;再往下走一下,再判断;再往下走一下——这个才是最后。

所以当你退出这个 `for` 循环的时候,你可以肯定的是:**`temp` 一定指向了该链表的最后一个节点**,这个不用怀疑了。

#### 第三步,连上最后一根线

现在工作做完了,把 `newHeroNode` 加入到链表的最后。怎么加进去呢?非常简单,**一句话:你让 `temp` 的下一个节点指向它就可以了。**

```go
temp.Next = newHeroNode
```

完事。这个动作非常重要——**如果你今天自己去写,会出现很多这样的错误,什么空指针的错误。**

那这句话等价于什么呢?我让 `temp` 的 `Next` 指向 `HeroNode`,相当于说这个地方就不再是 `nil` 了,它指向了宋江。

这个时候你可以看到,我们这个头节点还是头节点,但是它已经指向宋江了。

#### 再来一个:卢俊义

假设我们又加了一个叫卢俊义的人,我们看这个逻辑是不是也能走通。

宋江刚加进去的时候,他这个节点是不是也是 `nil`?因为你没有动过他,他默认就是 `nil`,没问题。

卢俊义刚出来的时候,他的下一个节点这个值其实也是 `nil`。现在进来,head 给了,卢俊义也给了,让 `temp` 指向 `head`。`temp` 指向 `head` 过后,我开始定位 `temp` 的下一个是不是空的——不是空的,于是 `temp` 往这边移动一下,直到这儿。因为它的 `Next` 就是宋江,它一看,宋江下一个是不是空?已经是空了。宋江就是最后一个,宋江是最后一个我就退出来,然后让 `temp` 的 `Next` 指向卢俊义。

这个地方又让宋江的这地方指向卢俊义了,卢俊义也加入到我们这个大家庭了,大家欢迎。而卢俊义的 `Next` 还是空,所以说下一个再加的时候就在卢俊义屁股后面加,依此类推。

> **结论**:这个逻辑大家要非常清晰,不然到时候出问题。

### 显示链表:先判空,再像 do-while 那样先打后走

### 单链表删除:为什么 temp 必须盯着下一个

我给大家演示一个删除的功能,**修改大家可以自己去玩一把**。

删除就是说你给我一个 ID 吧,你给我一个 ID,然后我就到这里去找。但找的时候要遵循一个原则:**你在找的时候依然要让 `temp` 的下一个跟这个 ID 比较。**

为什么?**你如果不让 `temp` 的下一个比较,你即使找到了你也干不掉它。**假设你找到了宋江,你的 `temp` 就在宋江——你怎么把它干掉?你干不掉。

> **结论**:这就是头节点的价值所在。**你一定要找到 `temp` 的下一个,让下一个直接跟它比较。**

### 找,标记,然后一刀切下去

好,直接写代码。案例叫删除:

```go

```

你要删除一个东西,必须给我一个头节点——你不给我头节点,我什么都干不了;第二个,你还要给我一个你要删除的 ID。

老规矩,还是要一个跑堂的,你没有跑堂的干不了事。找的时候怎么找呢?跟我找插入节点类似,只是不一样的地方是它要找相同的,所以我把整个复制过来,大体的含义是相同的。

```go
temp := head

    if temp.next == nil {
        // 找到链表最后了
        break
    }
    if temp.next.no == id {
        flag = true
        break
    }
    temp = temp.next

    fmt.Println("对不起,你要删除的 ID 不存在:", id)

```

先写个 `false`,假设找不到。`temp.next` 还没比较过一次,始终是 `temp` 跟它后一个比,所以走的是 `next` 比较。如果这个条件一旦成立,就说明找到了——**`temp` 的下一个节点就是我们要删除的那个**,把它改成 `true`,退出。

```go

```

这么指有什么好处呢?**当我头节点在遍历的时候,这个节点就会被抛弃。**那这个节点会变成什么?它会变成一个**垃圾节点**。

好,单链表这块就先说到这里,接下来我们看下一种链表:**使用 head 头的双向链表**。

单向链表其实有一点缺陷,我给它数了两个。

**第一,它查找只能是一个方向。**只能从头往后面一条线走,中间不能乱跑,不能反向从尾往头找。所以它只能是一个方向,而双向链表可以从前或者向后查询,效率有时候会比较高一点。

**第二,它不能自我删除。**打个比方:现在有这么几个节点,这个节点是二号节点。我们有一个 `temp` 在不停地找,突然 `temp` 找到一个节点是二号,说要把这个节点删掉——**它其实没有机会删掉的,它干不掉这个人。**假设我们的 `temp` 引用指向了二号节点,你想把二号节点从链表里拿掉,拿不掉——**因为你没办法去访问到它前一个节点的 `next` 字段。**

### 双向链表:每个节点多一个 pre

如果是双向链表,情况就不一样了。双向链表是在原先基础上做成这样,改进只有一点:

```text
head <──> [宋江] <──> [卢俊义] <──> [林冲]
             ↑              ↓
             └──────────────┘
        每个节点既有 next,也有 pre
```

头节点还是头节点,前一个可以指向它,那么我这个节点也可以指向它;同样的道理,二号这个节点既可以指向后面的节点,也可以指向前面的节点;卢俊义也可以指向前一个节点。**我们就把它叫做双向链表。**

当然这还是个非环形的双向链表。还有一种链表更恐怖,它这个地方还指回来,形成一个环形——**双向的环形我们就不讲**,我们待会儿讲一个单向环形,那个还是有点用的。这种双向链表其实一点都不难,还是比较简单的,必须也掌握一下,因为有些面试官也喜欢问双向链表会不会用。

#### 自我删除:双向链表最实在的用处

一旦这种形式存在了,就有一个好处:**我们就可以实现自我删除。**

比如现在的 `temp` 指向了二号节点,想把自己干掉,非常的轻松。你只需要通过这个节点访问到它前一个节点的下一个节点,让它指向它的下一个节点——因为这个地方还可以访问到我的下个节点,我可以让它指向它。然后我再通过我的下个节点找到卢俊义的前一个节点,让这个家伙又指向它。**这样一条线形成过后,会是个什么情况呢?宋江直接指向了卢俊义,卢俊义直接指向了宋江。**

中间这个家伙上哪儿去了呢?**它只有两条线,下个节点指向卢俊义,前一个指向宋江,但是没有人指向它了**,所以它也会成为一个垃圾被销毁。它是这么一种逻辑。

### 双向链表的创建与输出

直接上代码。打开 VS Code,新建一个文件夹叫 `doublelink`,双向嘛,double link,里面新建 `main.go`。

前面单向链表虽然没有双向功能,但是很像,写过的东西就不反复重写了,工作量太大——**直接把代码先复制过来,在上面做一个改进就可以了。**

#### 结构体多一个 pre

先看添加这一块。给链表添加一个节点也分两种情况,双向链表也一样:往屁股后面加和在中间加,只是看怎么连接。

第一种方法,先找到屁股后边。一旦找到屁股后边——原先 head 节点找到了,相当于在屁股后边找到了——**找到过后要做两件事**:

```go
temp.next = newHeroNode       // 先让 temp 找到的节点的下一个指向它
newHeroNode.pre = temp        // 再让新节点的前一个节点指向 temp
```

一旦找到了这个位置,就要做这两件事:先让 `temp.next` 指向新节点,同时让新节点 `HeroNode` 的前一个节点 `pre` 指向 `temp`。

> **结论**:只要这么做了,就会发现**双向链表一定是形成的**。

先把这个测试一下,在屁股后面增加就这么一点改动,看能不能用起来。

#### 显示,以及怎么证明它真的双向了

怎么证明现在已经形成双向了呢?**有一个办法,可以逆序打。**

按理说这是想让大家玩的,既然有兴趣,就写一下。显示链表所有节点仍然是跟单向一样的,还是从 `head` 这开始一个个找、遍历出来;**除非你有需求想逆序打出来。**要逆序打的话,先把跑龙套的指到屁股后边,然后反向地走。

怎么知道卢俊义是最后一个呢?**因为它的 `next` 仍然是空。**卢俊义下一个节点没有,只有指向前一个节点的。跑龙套再往前面跑,跑到有一个节点的前一个节点等于 `head` 的时候,循环就结束了。

```go
temp := head
if temp.next == nil {
    fmt.Println("空链表,空空如也")
    return
}
// 正序:从头往后打
for {
    fmt.Printf("no=%d, name=%s\n", temp.next.no, temp.next.name)
    temp = temp.next
    if temp.next == nil {
        break
    }
}
```

逆序打出来,就是让 `temp` 定位到双向链表的**最后**这个节点:

```go
// 先定位到最后一个节点
for {
    if temp.next != nil {
        temp = temp.next
    } else {
        break
    }
}
```

一旦出了 `for` 循环,`temp` 就相当于走到最后了。这个地方就要反向打。先把这个节点打出来——**现在已经是最后一个节点了,不能写前面**,直接打出 `temp` 这个节点。然后判断是不是到了表头,怎么样才能知道它是头呢?先把自己打出来,打出来过后挪动,再往这边走的话,**`pre` 为 `nil` 就代表是到 `head` 节点了**。

```go
for {
    fmt.Printf("no=%d, name=%s\n", temp.no, temp.name)
    if temp.pre == nil {
        break
    }
    temp = temp.pre
}
```

> **提示**:`break` 后面要跟一个表达式,所以要加一个 `if`。

顺着打一次,再逆序打一次:顺着打印是 1、2、3,逆序打印是 3、2、1,正确,完全没问题。**一下就很轻松地实现了一个逆序打印。如果没有双向链表,根本就做不到,几乎做不到——双向链表是有价值的。**

大家现在应该有一种感觉,感觉有点接近计算机了,但是还没有接近。如果再往下面接近一点,就是编译原理和操作系统。大家把这块找到,后面讲区块链算法的时候,理解的层次会稍微深一点点——**原来它们下面还有这些东西在帮忙,不是无缘无故整出来的,是有东西在里面的。**

### 按编号添加:顺序比逻辑更难

刚才我们已经讲了双向链表的正向输出和逆序输出,也讲了添加。**如果说我们要实现双向链表按照顺序添加,其实非常简单,改一个地方就行了。**前面这些地方都用不着变化,只是在进行关联的时候,要想办法让它形成一个双向的——你必须要考虑这个问题。**如果你按照之前那种方式添加,它仍然是个单向链表。**

我们打开 Excel 表,还是以这张图为例来推导。假设头节点还是从这里开始的,我们寻寻觅觅找到了一个点,找到 2 号的位置。现在我们有一个 3 号节点要插进去——**这个地方顺序是非常重要的,一旦你加得不对,把整个链表就会搞乱。**

是不是数据结构听久了过后,突然感觉头有点晕了?**头有点晕很正常,这是正常反应。你要是不觉得晕反而是不正常的。**

#### 一条原则:先动新节点

一般来讲原则是这样子的:**先让这个新节点指向这些节点,然后再让链表节点去指向它。**

也就是先把新节点能够关联的节点先做完,不要去断掉它们之间的两根线——**这两根线一旦断掉的话,你就找不到它们之间的关联了。**

为什么不要先动 `temp` 呢?**因为你通过 `temp` 能够找到它的后一个节点,先动这根线大家理解我的意思吧,先让它走过去。**

那顺序就来了:

**第一步**,先动新节点,新节点的 `next` 节点等于 `temp` 的 `next` 节点——这个不动,是 OK 的,没有任何问题,新节点往下走的线不就有了吗?

**第二步**,还要让它的前一个节点指向 `temp` 节点:

```go
newHeroNode.pre = temp
```

**第三步**,让 `temp` 节点的下一个节点的 `pre` 指向新节点:

```go
temp.next.pre = newHeroNode
```

**第四步**,让自己的下一个节点也指向这个新节点:

```go
temp.next = newHeroNode
```

到这一步,双向链表就形成了。

#### 一个巨大的漏洞:当 temp 是最后一个节点

**这个地方有一个漏洞,同学们仔细看的话,这边是有一个非常巨大的漏洞的。**

什么漏洞呢?**如果你的 `temp` 就是最后这个节点的话,那么你最大的问题是——你的 `next` 已经没有了,你居然还敢去访问它的前一个节点。**

什么时候会爆发呢?就是你刚好在添加的时候,那个节点刚好是最后一个节点。你要添加到最后,数值太大了排到链表最后,你去访问 `temp.next` 时它已经是个 `null` 了。**它既然是空,你再去取 `pre` 肯定就报错。**

因此在这里加一个条件就可以了:`temp.next != null` 的时候,我們才去做第三步这个工作。

```go
if temp.next != nil {
    temp.next.pre = newHeroNode
}
```

也就是说,**相对来说最后那个节点它少一个连接,这是很正常的**;如果它不等于 `null`,我们再把它加进去,这 就完事了。

双向链表在有效的时候它就加进去了,这段代码肯定是没问题的,大家放心好了。

### 删除:同样两行,同样一个条件

还有一个问题没讲:**删除。**删除的话,怎么让它删完了过后仍然是一个双向链表?

刚刚添加是按照编号添加时保证是个双向链表,那么删除我讲一个就行了,抛砖引玉讲一个。

这个删除怎么删呢?其实跟前面这个也很相似。比如说 3 号它光荣地加入到我们的团队,现在因为种种原因我们又要干掉它了。怎么把它干掉过后它还是个双向的?

假设我们现在要删除的就是 3 号。你首先要明白你现在找到这个被删除的节点是哪一个——**其实这个 `temp` 也可以直接指向它,也可以删,就看你的实际情况了。**我就以 `temp` 找到前一个节点为例吧。

**第一步,让它脱离。**第一个动作是让 `temp` 的 `next` 指向它的 `next` 的 `next`,让它先指向后面这个:

```go
temp.next = temp.next.next
```

**第二步,让它的 `next` 节点的前一个节点不再指向 `temp`:**让它指向它,那这个线也很好做:

```go
if temp.next != nil {
    temp.next.pre = temp
}
```

> **易错点**:此刻这个 `temp.next` 已经指向了后面的节点了——因为这个 `next` 已经改变了,所以你就不能再写 `next.next` 了。**这个时候的 `next` 已经跟前面不一样了,它等价于原先的 `next.next`。**

#### 风险到底在哪:最后那个节点

我们来看看这里有没有危险。最大的危险可能性来自于**最后这个节点**。

假如我们找到的就是最后一个节点,如果这样做的话,风险比较高。因为它的 `next` 再 `next` 就是空。如果 `temp.next` 是它,再 `next` 是空——**把空给它反而是正确的,因为本身就是要置空,把自己置空这是对的。**

但是置空了以后,`pre` 这个地方应该有一个前提。所以这边要加个条件,分析出来了风险度很高:**你一定要保证 `temp.next` 不等于空才去做这个连接。**假设它最后就是一个 `null`,你就不需要再去动它了,因为你已经把它干掉了。

我们把这根线画好:原先是这样一种情况,现在要删除的是卢俊义(删中间没问题)。`temp.next` 等于 `temp.next.next`——你看,`temp.next` 已经是它了,再 `next` 不就空吗?这就等价于 `temp.next = null`,这个是可以的,因为你本身就是要删除的这个节点,**它相当于把这个线断掉了**。

它断掉了,其实这个事情已经结束了——因为你最后这个节点,它后面没有节点。**但是你没有结束,你为什么没有结束呢?你没加条件判断。**你干了一件什么事呢?你说了 `temp.next.pre`,`temp.next` 已经指向了空了,如果你再去取空的一个 `pre`,**必然报错**。

所以说这个地方要有一个条件,一定要保证 `temp.next` 不等于空。把这个条件加进去,这个代码就完美了——**这个条件其实就是说,我删的不是最后一个节点。**

> **结论**:这个地方是有点绕,，因为你赋完这个 `next`,`temp.next` 已经发生变化了。我把这个条件加进去就完事了,这个就是我们的删除动作,肯定是对的。

#### 一个常见疑问:要删的是 4 号怎么办

有同学问:假设要删的是 4 号呢?

我反复强调了,**因为它始终是跟它后面那个比对**。如果它到 4 的话,就说明根本一个都没有要删除的——因为我们始终是在以 `temp` 的下一个节点跟节点进行比对的。如果真的 `temp` 到这儿来的话就不用删了,直接走到这句提示代码了。

而且我最终是从 `head` 开始走的:到 3 的时候我把 4 就已经做了比较了。假设我这个 `temp` 定位到这儿了,发现要删的就是 4,那说明**这个 `temp` 其实就在 3 这个位置**——这点大家必须认同。

## 环形链表:一只猫,也是可以成环的
> 对应块：BLK143 | 覆盖分集：P359 | 块标题（分集名）：《357_尚硅谷_数据结构和算法-环形链表创建和显》

### 先做环形链表,因为约瑟夫在等着

下面我们来实现一个环形链表,就是一个**单向环形链表**的应用。刚才我们讲了,单向环形链表最经典的一个用法就是**约瑟夫问题**。

它的结构大概是这样子的。我们的案例就围绕环形链表的添加、删除和显示展开——把这个讲完了以后,也就是说我们先走完一个单向环形链表的案例,然后我们**回头再去解决约瑟夫问题,就是丢手帕问题**。

打开 VS Code,我们新建一个文件夹,叫 `circle`,环形。

### 一堆猫猫,和一个非空的头节点

新写一个文件叫 `main.go`。假设我们放了一堆小猫。我还要画一个示意图,因为待会儿我要用这个图来帮助大家理解。

我们新建一个结构体,叫做猫猫结构体——比如说我们放了一个环形的猫,一堆猫。这个节点我们就叫 `CatNode`:

```go
package main

import (
    "fmt"
)

// 定义猫的结构体节点
type CatNode struct {
    no   int // 猫猫的编号
    name string
    next *CatNode
}
```

这个节点里面有什么信息呢?**猫猫有个编号,猫猫有个名字;同时它是单向的链表,所以它应该有一个 `next` 节点,指向下一个猫猫的节点。**这点大家应该可以很清楚地知道。

#### 环形链表也有头节点,而且它得放数据

现在我们先来做添加的操作:

```go
func InsertCatNode(head *CatNode, newCatNode *CatNode) {
}
```

问题来了:你往里面添加的时候需要什么?仍然需要一个头节点。

有人说:"老师,这个环形不是没有头节点吗?"**对,环形确实没有头节点,但是你自己要初始化一个头节点。**你刚开始的时候要想象这里面什么都没有——这里面确实什么都没有,所以你要先做一个头节点才能玩。没有头节点,你到时什么都干不了,**只是这个头节点的维护比较麻烦一点。**

所以我们仍然要有一个头节点,这个是我们的猫。它仍然是有 `no` 的,当然它也有 `next`,`next` 我们待会儿再说。

> **提示**:这里和前面学的单链表有一个**很大的不同**——以前前面我们学的头节点只是一个空的头节点,**但环形链表的头节点一定要放数据**。所以这个地方要特别小心。

头节点初始化在哪里做呢?显然在主函数里面是比较合理的:

```go
head := &CatNode{}
```

里面不知道是什么,所以先放这儿。因为第一只猫我也想通过这个添加进去。

然后我们创建一只新猫:

```go
cat1 := &CatNode{
    no:   1,
    name: "tom",
}
```

当然这些你也可以通过键盘输进去,问猫的名字是什么。我这里就直接写了,第一只猫的名字叫 tomcat,汤姆猫。然后它的 `next` 默认肯定是 `nil`,所以你也不用给它赋值。

第一只猫有了过后,我们调用 `InsertCatNode`,把这个头节点传进去,然后把这只猫也传进去。**因为你这是通过引用传进去的,你里面的改变会直接影响到这个 `head` 的指向。**

### 第一只猫:head.next = head

现在我们做个判断——**判断是不是第一只猫来了**。为什么你要判断是不是第一只猫呢?**因为你现在的 `head` 本身要放数据了。**所以先判断是不是第一只,如果不是第一只,你就必须把这个 `newCatNode` 赋给它;如果不是第一只,就是真的添加。所以这边是有两种逻辑在里面的。

怎么判断是不是第一只呢?非常简单:

```go
if head.next == nil {
    head.no = newCatNode.no
    head.name = newCatNode.name
    head.next = head // 构成一个环形
    fmt.Println(newCatNode, "加入到了环形的链表")
    return
}
```

如果这个条件成立,说明它是第一只猫,也就是说头猫还没有——那第一只来的猫就是头猫。因为我现在没有头猫,所以我就给它赋一下值:`head.no = newCatNode.no`,等于你新来的这只猫它的 `no`;同样,`name` 也相当于你新猫给我带过来的名字。

紧接着它有个问题:**这个头猫的下一个节点怎么办呢?**头猫的下一个节点让它形成一个环状——**一只猫也可以形成环状。**

这个大家可能有点不好理解:自己指向自己,其实这也是个环状,因为你是环形的。

有人说:"老师,一只猫怎么也形成环状呢?"**它自己有 `next`,它指向自己不就是一个环形吗?只是这个环状里面只有一只猫而已,这很正常。**就好像一个圈圈里面就一个人——一个人也是一个圈。两个人可以是一个圈,那一个人为什么不能是个圈呢?因为它的下一个 `next` 就是指向自己,自己形成一个闭合的环形,这是可以的。

那怎么样让它形成呢?非常简单,加句话就行了:`head.next = head`,因为你要保证它是环形,形成一个环状。

`no` 给了,`name` 也有了,**它的 `next` 指向它才行**,这样子 `head` 就形成一个环状了。

好,环形第一只猫就做完了,下面的直接 `return` 就完了,走路了。也可以说第一只猫已经来了,输出一句话:直接把它输出来就行了,说这只猫已经加入到环形链表中。

### 第二只猫:终点是 head,不是 nil

好,第一只猫有了。但是你这是第一只猫,你第二只猫来怎么办呢?第二只猫来的话,这就有一个问题了——**你要找到这个环中的最后。**因为我们目前只考虑它加的时候加到最后,先不考虑排队这个问题了。

如果已经有一只猫了,我们就先让一个 `temp` 指向它,找到最后把它加进去就行了。

```go
temp := head
for {
    if temp.next == head {
        break
    }
    temp = temp.next
}
```

怎么找到最后这个呢?我先让 `temp` 指向 `head`,然后用 `for` 循环去做。

**注意这里和单链表最大的不同:终止条件不再是 `nil`,而是 `head`。**如果 `temp.next == head`,等于头节点——因为它最后走走走形成头节点,走到这个头节点过后,我们就认为它找到了。然后 `temp = temp.next`,我就不停地找。等到出来过后,`temp` 到了环中最后。

那最后这个怎么加进去呢?大家想一想,这个环状的链表怎么加进去?其实挺简单。现在已经有一个 `temp` 指针找到了环中最后这一个,那你要做的事情是:**让这个 `temp.next` 先指向它,然后让猫猫这个节点的 `next` 指向头节点,形成环状。**

```go
temp.next = newCatNode
newCatNode.next = head
```

你看,这样子就形成一个环状了。它做的是两个工作。

## 单向环形链表的删除：一个跟着屁股跑的 helper，和一个必须搬家的 head
> 对应块：BLK144 | 覆盖分集：P360-P362 | 块标题（分集名）：《358_尚硅谷_数据结构和算法-环形链表的删除》

### 先把三只猫连成环

下面我们来整一个删除。现在你可以不停地往里面加了——刚才只加了一只猫，可以加很多只猫。第二只猫比如它的编号为 2，是汤姆 2；第三只猫是汤姆 3。我就示意一下，这个没有关系。

我们看看三只猫是不是都已经放到环形链表里面去了。**第一只猫 ID 为 1，它指向了下一只猫；第二只猫，没问题。**

那么怎么删除这只猫呢？大家想象一下，我们现在要把一只猫从环形里面删掉——**就跟刚才我们说有个人数数，数到那个地方要把它干掉一样。**

假设已经有三只猫了。这是第一只猫，这是第二只猫汤姆 2，还有第三只猫汤姆 3。它们现在的关系是这样子的：第二只猫指向了第三只猫，第三只猫指向了第一只猫，形成一个环状。

现在我们想删除第二只猫，怎么删呢？

```text
   删除前

        ┌────────┐        ┌────────┐        ┌────────┐
        │ Cat 1  │───────▶│ Cat 2  │───────▶│ Cat 3  │
        │ (head) │◀───────│        │◀───────│        │
        └────────┘        └────────┘        └────────┘

   想删 Cat 2：得有人从后面伸手把它摘下来
```

**首先要删的时候大家都知道，它是一个单向的。虽然是环形，但是是单向的。你想删掉第二只猫，必须有一个辅助节点在这个节点上。**

而且还要考虑有可能把 head 节点给干掉了。**如果你把 head 节点干掉的话，原先的 head 节点还要重新返回值。** 像 Java 等有些语言不存在这个问题，但 Go 语言有这样一个问题：你把它删掉过后，head 节点有可能被删掉。所以这个地方我们要考虑的东西很多，我们一点一点来写。

### 删除的思路：temp 去比较，helper 去摘人

我们写一个函数叫 `delete`。原先是 insert 一只猫，现在就是删除一只猫：

```go
func deleteCatNode(head *CatNode, id int) *CatNode
```

首先你得先给我 head 头节点 `*CatNode`，然后给我一个 ID 值 `id int`。

那删除的时候思路应该怎么走比较合理呢？

```text
   指针分工

        ┌────────┐
        │  temp  │─────▶ 负责"找"：一个一个往前比 id
        └────────┘          它不能直接删人，因为它是单向的
        ┌────────┐
        │ helper │─────▶ 负责"摘"：一旦命中，用它来干掉 temp
        └────────┘          它必须跟在 temp 的屁股后面
```

删除一个环形单向链表的思路如下：

- **第一点，先让 `temp` 指向 head**；
- **第二点，新建一个 `helper` 指针，上来先让它指向环形链表的最后**——因为现在头节点还是有的。思路是让 `temp` 跟要删除的 ID 比较，如果相同，就让 `helper` 想办法干掉它。

**为什么要这么做呢？** 这样有个好处，就是让 `temp` 参与比较。有人会问："老师，你以前不是让 `temp` 往前面比较一下就可以了么？"是的，**但是现在的问题是 head 节点本身就有值，你不能说不去比较它。** 原先之所以可以做到让比较的 ID 跟 `temp` 的下一个节点比较，是因为原先 head 节点本身是没有值的，它可以不参与比较；而现在这个 head 节点是有值的，所以上来就得比。

**最极端的例子，如果删掉的就是 1 号节点，怎么办？你根本就把它干不掉。**

比如要删除猫 1，现在 head 指向它，`temp` 也指向它，你怎么删掉它？**它是个单向的，那你必须有一个节点刚好是在它的屁股后边**，也就是说这个节点有点类似于我们单向链表的 `temp` 了。当目标节点往前面走，辅助节点跟着往屁股后面追，**发现匹配之后，通过辅助节点把前面的干掉。** 它的逻辑是这样子的。虽然听起来有点绕，但是没有办法，数据结构就是这样。

那 `head` 自己到底能不能动呢？

> **提示**：**让 `temp` 这个节点移动，因为 head 节点是不能乱动的。** head 节点一旦动了，外面就找不到了。
>
> 其实这里的 head 动了的话，理论上还影响不到外面，改变它的值才会影响。**因为这里的 head 和主栈的 head 不是同一个变量，只是它们指向的空间是同一个。只要你不改变它指向的空间内容，其实这边的 head 怎么变化都影响不到外面主栈的 head**——主栈有一个 head 指向它，删除函数所在的栈里面也有一个 head 指向它，它们仅仅是指向同一个空间而已。所以这个 head 即使移走了，外面还是指向原来的节点，并没有动。**但是千万不要用 head 去改变里面的值**，如果通过里面的 head 把空间置空了，外面的 head 也找不到值了，记住这个原则。

### 三种情况：空链表、只有一个节点、两个及以上

#### 空链表

如果链表本身就是一个空节点，就不去处理了：

```go
if temp.next == nil {
	fmt.Println("这是一个空的环形链表，无法删除")
	return nil
}
```

因为空链表往后执行会出问题。

#### 只有一个节点

**环形链表在遍历和删除时要考虑的东西很多。** 如果只有一个节点，也可以单独处理。

怎么判断呢？如果 `temp.next == head`，说明目前环形链表只有一个节点。**只有一个节点怎么把它删除呢？回到刚才的逻辑，如果真的只有一个节点，从理论上说只要把头节点的 `next` 置空就完了**：

```go
if temp.next == head {
	temp.next = nil
	return nil
}
```

因为只有一个节点时它自己指向自己，把 `next` 置空就完成了删除，然后直接返回，不继续往下走。

#### 两个及以上的节点：开始真正的环形遍历

**下面的情况就是我们真正的环形了**，因为空链表或者只有一个节点比较麻烦、不好处理。现在我们把这两个情况处理完了过后，我们看：

**不着急，同学们，这个本身稍微有点麻烦。如果同学们有更好的解法，也可以拿出来分享一下。** 我们就按刚才的这个思路来搞定它。

首先，**如果 `temp.next == head`，这说明我们已经找到了最后，但是还没有比较。** 也就是说现在 `temp.next` 等于 head 了，说明我整个转了一圈，`temp` 到这儿来了。那如果在这种情况下还没有找到，说明我哪怕比较到最后一个还没有比较——**最后一个还来不及比较，都还没有找到，还没比较。**

那这个就我准备退出了，因为这个地方再不退出没机会退了。**如果你再不退的话，你只能再往前面走，而你前面的 head 曾经比较过一次——因为你上来先比较的头，如果你再去比较一次你就不划算了，你退出的时候就不好控制这个，所以说先退出。** 当然注意，退出之后这地方最后一个还没有比较，我退出之后再比较。

**还有一个情况就是，在这一步过程中我比较的时候找到了。** 也就是 `temp.no == id`，说明你的 id 和我现在要找的刚好就找到了。恭喜，找到了。

那找到之后，我要删除的就是 `temp`。**有老师说：你这个 helper 到底是干嘛的呢？告诉大家，没有 helper 你干不掉它。** 这个 `temp` 的移动是在于它去进行比较，它是用来比较到底是不是要删除的节点；而 `helper` 的移动，**它一旦找到过后，就用它来干掉这个 temp**。

> **结论**：**helper 的价值在于——一旦我们找到了要删除的这个节点，这个 temp 就能发挥巨大作用。如果没有这个 helper，你就干不掉它，因为我们是单向的。** 意味着你要找到的这个被删除节点，前面那个标识的节点必须要有用。一旦有这个东西，那么这个就跑起来了。

跑起来过后，在这儿假设找到了我们就删除它。**怎么删除？非常简单，一句话就搞定了**：

```go
helper.next = temp.next
```

你想想这个道理是不是这样的？`helper.next` 就是它的 next，指向 `temp.next`，不是它就指向它了吗？**就这根线就指向到了这儿**，那你看这个环形链表就变成第一个指向它、它指向它、循环。**这个节点就被扔出去了，把这个节点就扔出去了。**

#### 为什么要一个 flag：最后一个节点还没被比较到

好的，但是这里面还有一个逻辑很麻烦，你这样写还有一个问题：不停地找、不停地找，假设我们一直没找到，回到刚才这个逻辑来——**假设我们这个 temp 找找找，找到最后这个地方了**，我发现我下一个已经到头节点了，说明这个条件已经满足，我已经跑出去了，就是现在 temp 找到最后这个节点，我发现我还没有找到，还没找到我就退出来了。**那说明你最后这个哪怕没有比较，你还得来一把才行。**

**当然有同学说："老师，我把这个逻辑写到这里面，可不可以？"这个我也在想，我想了一阵我没想出一个特别好的方法，同学们也可以想一下。** 我的逻辑就比较直接一点：因为你在这个地方比较的时候，虽然到 head 了，但是你这个 temp 本身还没有比较你就跑了，**所以这里面还要进行最后一次比较。**

那比较一次有一个问题：**假设里面已经删掉过了**——最后这个 temp 肯定不是，所以说我们加一个 flag。**flag 假设我给它一个 true，什么意思呢？就是说我们认为它在这个过程中就能删除。** 那么一旦在这个过程中是 false 吧，我们认为它删除过，我将来还要比较一次——**因为在这里面真正删除了一次，所以说把它置成一个 false，就说明你外面不要再去玩了，我已经在里面删掉过了。**

```go
flag := true   // 认为它能在 for 循环里被删掉

for {
	if temp.next == head {
		break              // 转到最后一个了，但最后一个还没比
	}
	if temp.no == id {
		// ...删除...
		flag = false       // 已经删过一次了，外面就别再删
		break
	}
	temp = temp.next
	helper = helper.next
}

// flag 保持为真 = for 循环里一次都没删过 = 最后一个节点还没比较
if flag {
	// 再比一次，这次比的就是最后一个
	if temp.no == id {
		// ...同样地删除...
	} else {
		fmt.Printf("对不起，没有 number=%d 的猫猫\n", id)
	}
}
```

**我们保证 id 不重复。如果你的 id 还是重复的，那就更麻烦了，那你也想得很多。** 所以说你看，做数据库的那些人，他底层写的很多东西——**我们现在可以看到，这里面好多复杂的情况。**

#### 删的是头节点：head 要搬家

好，这个删除完了过后呢，还要考虑一个特别恐怖的问题。

**如果你删除的是头节点。** 你删除头节点只有在这个地方才有可能删除头节点，这个地方因为是尾节点，所以这还好办一点。

**假设我上来过后真的就把头节点删除了**：假设上来过后 temp 就等于它，helper 呢指向的是它。结果你上来一比较，temp 就是要被干掉的人。然后你做了件什么事情呢？你说："好办，根据你刚才业务逻辑，`helper.next = temp.next`。"那也就说明你现在一做，就把这样一件事情——让这个 helper 的 next 指向它的下一个。

```text
   head 还是指向已删节点

        ┌────────┐        ┌────────┐
        │ Cat 1  │───────▶│ Cat 2  │──▶ ...      环断了，不再是环
        │ (head) │  ←删   │        │
        └────────┘        └────────┘
           ▲
           └── head 还指着已经被摘出去的节点
```

**头节点还是它，那这个链表它已经不是环形的了。** 那就意味着**如果你删除的是头节点，你要让原先这个头节点往这边移动一下——因为真正的头节点要指向它的下一个节点**。所以说这里面还有一个非常重要的判断，不然的话这个跑不起来。

有同学说"怎么这么麻烦"？**可能我这思考得有点麻烦，可能有些同学有更简单的方法。我们先这样子做着，大家不用特别害怕这个事情，可能会有更简洁的方式，有简洁方式我们到时候再来给大家分享一下就行了。虽然算法很多，我这加一个判断就行了。**

加个什么判断呢？**如果你删除的这个 temp 刚好就等于 head，说明我们删除的是头节点。** 那么如果删除头节点的话，下面这个代码还是一样一样的，这个该怎么做还是怎么做，**只是你这个头节点要发生一个修改，就是你这个 head 要变化，走，你要让它指向自己的下一个节点。** 你这边再指向，这仍然是一个有效的链表。

**但是这样做又出大问题了**：你原先这个、你主栈那个 head，还傻傻地指到这儿呢。**因为你在最后你在遍历的时候，你还是用主栈这个 head 呀。** 所以这个主栈一跑，他一跑："哎？我跑这儿来，跑这儿来，跑这儿来。"实际上他这个地方就变成一个很怪的一个逻辑了，**因为他相当于说在这走了一圈，走了一圈，他找不到他自己了。**

你在进行遍历的时候，怎么停下来的？是不是因为你在找最后这个的时候等于头节点——**结果它永远找不到头节点，这一定是个死循环，一定是个死循环。**

**那就意味着我们还要做一件事情，就最后一步了，大家不要害怕，最后一点点。说老师您老说最后一点点，最后把这个结点返回去就可以了。没问题，你这样做它就简单了。**

**最后不管怎么样，`return` 把这个改过的结点再返回去。** 你那边接收过后把它改一下就完事了，这个代码就写完了。当然这个地方是没有改过的，但是也要 return，因为从语法上是需要的。

### 定位 helper 到链表末尾

写完这个逻辑我发现——**这个 helper 我上来过后没有动过呀**。刚才我们发现的那个小问题就是：**helper 指向环形链表最后，是不是这个工作没做？**

那现在我们就做一下最后这个事情：**让这个 helper 到链表末尾去**。因为空链表和只有一个节点都不需要跟 helper 有关系，所以在这个地方做一个定位：

```go
for {
	if helper.next == head {
		break
	}
	helper = helper.next
}
```

**helper 移动，一旦找到了删除节点，我看看这个地方有什么问题吗？break 退出。** 这上面有个 break——**因为做完这个事情我就 break 了嘛**。像这个还要 break 吗？**这个不需要 break，这个不能 break。这个就是让它不停地走的 break。**

### 约瑟夫问题：环形链表最经典的应用

上次课我们讲了一个单向环形链表，讲了添加、遍历以及删除，但**还没有讲它的应用，也就是它到底用到哪个地方**。

**环形单向链表一个很经典的应用实例是什么呢？就是解决约瑟夫问题，也就是丢手帕的问题。**

它是这样子的：**设编号为 $1$ 到 $n$ 的 $n$ 个人围成一圈，约定编号为 $k$ 的人开始报数。** 这个 $k$ 有个要求，就是它必须在 $1$ 到 $n$ 之间，不能大于 $n$。然后从这个地方开始报数，**数到 $m$ 的那一个人就出列**，这个人就出去了。

**出去过后，他的下一位——注意听这话——他的下一位又从 1 开始报数，数到 $m$ 的那个人又出列，以此类推，直到所有的人出列**，由此产生一个出队列的序号，**问最后剩下的人是谁。**

#### 提示：用一个不带头节点的环形链表来做

对于这样的问题或者类似的问题，怎么解决呢？**比较经典的一种方式就是模拟它的实际场景。它围成一圈，这一圈跟我们的环形链表其实是非常相似的。** 这样子的话，我们就可以用一个**不带头节点的环形链表**来处理约瑟夫问题：

- **第一步，构建一个有 $n$ 个节点的单循环链表**；
- **第二步，由第 $k$ 个节点开始报数，数到 $m$，对应的节点就从这个链表中删除**。

当然要想一想怎么删掉。**我们讲过，环形链表尤其是单向链表，它的删除必须在前面有一个辅助节点；如果你没有这个辅助节点，你是干不掉它的，除非你是双向的。**

**那你听到这句话，你的脑海里面就应该闪现出这么一个场景：有一个节点在这儿不停地数，另外一个节点在它屁股后面跟着跑。当前面那个节点数到 $m$ 的时候，就用后面那个辅助节点想办法删掉数到 $m$ 的那个节点**，依次类推，最后就形成一个出队列的顺序。

#### 走一遍五个人

假设我们有五个人。**这是一个人，我复制五个点：1、2、3、4、5。** 编号可能不一定完全是顺序编号，它也可以跳着编，但现在我们假设有这么一个场景，先把这个意思说清楚。

现在有五个人围成一圈，那相当于这个 $n$ 就是 5。然后我们假设**从第二个人开始报数**——数两下的话 $m$ 相当于 2，但从第二个人开始数的话 $k$ 相当于 2；**干脆我们数三下吧，不要两个都一样**，那从第二个人开始数的话，这个 $k$ 就相当于 2。

```text
   k = 2 表示从 2 号开始，m = 3 表示数到 3 出列

              ┌───┐
          ┌──▶│ 1 │◀──────┐
          │   └───┘       │
        ┌─┴─┐           ┌─┴─┐
        │ 5 │           │ 2 │  ← 从 2 开始报数
        └─┬─┘           └─┬─┘
          │               │
        ┌─┴─┐           ┌─┴─┐
        │ 4 │◀──────┐   │ 3 │
        └───┘       │   └───┘
                     │
```

- **先从第 2 个人开始数：一下、两下、三下——他本身是要数一下的**，那么第四个人出列；
- **第四个人出完列过后，是第五个人接着数**——下一个人接着数，不是前面这个人。第五个人报数：一下、两下、三下，第二个人出列；
- 然后他的下一个第三个人接着数：一下、两下、三下，相当于数到 1 了，1 又出列；
- 紧接着只剩两个人了，第三个人开始数三下——**因为它是环形的，所以他数 1、2，又数 1**，即 1、2、3，他出列；
- 最后第五个人出列。**因为他虽然只有一个节点，他仍然是一个环形的，所以他会相当于自己数 1、2、3，都是他一个人数，最后他也出列。**

**那么这个顺序就应该是 4、2、1、3、5。** 这样的问题，我们要用一个编程的方式来解决。大家其实应该感觉到这还是很有意思的，因为这种类似的应用还是很多的。

### 本讲提到的题目

#### 题目

**数据结构的作业一共三道题。**

**第一题**：创建一个数组模拟一个队列，每隔一定时间随机给该数组添加一个数；启动两个协程，每隔一定时间到这个队列里面去取数据，看怎么取；在控制台输出"某某协程服务某某客户"。在进行数组读取的时候可以使用锁机制。

**第二题**：用链表实现一个队列，模拟一个队列，实现数据入队列、数据出队列，还有显示队列。

**第三题**：约瑟夫问题。也就是上面那个题目——编号为 $1$ 到 $n$ 的 $n$ 个人围成一圈，约定编号为 $k$ 的人开始报数（$1 \le k \le n$），数到 $m$ 的那个人出列，他的下一位又从 1 开始报数，依次类推，直到所有人都出列，问最后剩下的人是谁。

#### 解析

第一题考的是**数组模拟队列 + 协程 + 锁**：两个协程同时往同一个数组队列里取数据，如果没有锁就会出现数据竞争和下标错乱，所以取的时候要加锁。

第二题是把同样的队列用链表来实现，链表正好在头部 O(1) 插入、在头部 O(1) 删除，出队入队都方便。

第三题考的是上面刚讲的**单向环形链表**。

> **结论**：**约瑟夫问题其实核心已经基本上出来了，就是数到第几个，然后把它删除。因为删除的方法不是我们都有了吗？** 其实它删除比我们这个简单，**约瑟夫的删除要比这个简单**——因为它是数几个人、确定几个人，它没有让你考虑过多的情况，比如说原先是几个人、比如说他们考虑的是十个人，数两个再弹出去一个，它没有考虑过多的东西。**所以约瑟夫问题也可以照着这个思路来分析。**

#### 答案

第三题的走法就是正文的解题思路：**先用 `insert` 类的方法构建 $n$ 个节点的单循环链表，再把指针停到第 $k$ 个节点；用一个 `helper` 跟在报数指针的屁股后面，指针每往前走一步 `helper` 也往前走一步；指针数到 $m$ 时执行 `helper.next = temp.next` 把人摘出去，然后从被摘掉那个人的下一个节点重新从 1 开始数。** 循环到只剩一个人为止。

按正文那个 $n=5$、$k=2$、$m=3$ 的例子，跑出来的出列顺序是 **4、2、1、3、5**，最后剩下的是 **5**。

### 先有一群小孩：Boy 结构体

有了这个空壳，怎么把东西填进去呢？我个人的思路是分两步：先写一个函数把这个环形的单向链表形成起来，第二步把环形链表里的小孩显示出来。

怎么来做呢？先写这个函数 `AddBoy`，加小孩进去。

因为我们示意图里面的每一个小圆圈代表的是一个小孩，既然代表一个小孩，我们应该用一个结构体来描述这个小孩。所以我们先来创建一个小孩的结构体：

```go
// 小孩的结构体
type Boy struct {
	No   int  // 编号
	Next *Boy // 指向下一个小孩的指针
}
```

它有什么属性呢？至少应该有它的一个编号。我这里就不写名字了，直接写个编号 `No int`——因为我们主要是看编号出圈的一个顺序。第二个，它应该有一个指向下一个小孩的指针 `Next *Boy`。

构建多少个小孩呢？最好做一个变量。比如想构建 20 个小孩、构建 10 个小孩，给它一个变量传进去，写个 `num int`。最后整个 `AddBoy` 过后，给我返回一个环形链表的头指针，也就是第一个小孩的指针 `*Boy`。

这个参数 `num` 表示小孩的个数，返回的 `*Boy` 返回该环形链表的第一个小孩的指针。为什么非要这个第一个小孩的指针？因为如果最终没有它，后面的代码都不好走——待会儿要从第几个人开始数几下，都需要从第一个小孩开始来定位。没有第一个小孩的指针，后面代码就没法写。

#### 为什么 first 一旦定下就不能再动

```go
// 编写一个函数，构成单向的环形链表
// num ：表示小孩的个数
// *Boy ：返回该环形的链表的第一个小孩的指针
func AddBoy(num int) *Boy {
	first := &Boy{}   // 空的节点
	curBoy := &Boy{}  // 空的节点

	if num < 1 {
		fmt.Println("num的值不对")
		return first
	}
```

先做一个判断：如果这个 `num` 小于 1，说明没法给你构建，你给的值太少了，比如 `num` 的值不正确。如果不对的话就直接返回 `first`。

这里先创建了两个空节点 `first` 和 `curBoy`。为什么不小于 1 至少就等于 1 呢？那我们就可以开始循环地构建环形链表：

```go
	// 循环地构建这个环形链表
	for i := 1; i <= num; i++ {
```

这里面有一个问题：**因为第一个小孩比较特殊，所以我这里分成两个逻辑来处理**。每个同学的处理方案可能不一样，我是这样处理的——如果 `i == 1`，说明是构建第一个小孩，我专门特殊一下。

```go
		// 因为第一个小孩比较特殊
		if i == 1 {
			boy := &Boy{
				No: i,
			}
			first = boy
			curBoy = boy
			curBoy.Next = first
		}
```

它的 `No` 我们就暂时以 `i` 作为它的编号，直接用循环的方式给它赋一个 `i` 就可以了。它的 `Next` 默认值就是 `nil`，可以保留 `nil` 这个值。

有了这个小孩过后，它又是第一个，怎么办呢？先让 `first` 指针指向它：

```go
			first = boy
```

把第一个小孩指完了过后，这个头指针**就不能动了**。因为一旦动了，后面就找不到第一个小孩的位置了。因此这个时候大家应该分析出来，应该有一个辅助指针来帮助它形成循环链表。

这个指针你可以理解成是一个帮忙的、跑龙套的，都无所谓。它为什么要在呢？因为 `first` 指针一旦给定了就不能动，如果 `first` 动了，环形链表就没法构建成功。所以我们需要一个辅助指针 `curBoy`，当前这个小孩。它目前也是一个空节点。

当 `i == 1` 的时候，`first` 指向了 `boy`，`curBoy` 也指向这个 `boy`：

```go
			curBoy = boy
			curBoy.Next = first
```

`curBoy.Next = first`，这句话的作用是让它形成一个环形。因为有可能就构成一个小孩，这样它就构成了一个环形。`first` 指针指向该 `boy`，`curBoy` 也指向这个 `boy`，`curBoy.Next` 指向 `first`，相当于自己指向自己，形成一个环形。

> **结论**：`first` 是这个环的"门牌号"，从头到尾只赋值一次；所有"往前挪"的动作都交给 `curBoy` 代劳。

#### i == 1 之后的 else 支线

第一个小孩就这样去处理了。后面的小孩怎么办呢？后面的小孩就是 `else`。如果是第一个小孩以后的小孩，我们就应该这样做了：`first` 指针别动它了，这个不能动，动了过后头指针就找不到了。下面全靠辅助指针帮忙了。

```go
		} else {
			boy := &Boy{
				No: i,
			}
			curBoy.Next = boy
			curBoy = boy
			curBoy.Next = first
		}
	}
	return first
}
```

来了一个二号小孩，先让 `curBoy.Next` 指向这个小孩，原先的线就没有了，指向了它。显然这个时候还不是环形链表了，紧接着应该让 `curBoy` 往后面挪一下，也就是 `curBoy = boy`。然后让它重新指向 `first`：`curBoy.Next = first`。这就又形成了一个环形链表。

你看这个 `first` 就非常重要，不要去动它。如果 `first` 跑了的话，环形链表就形成不了了。

通过这样处理过后，我们就可以构建一个环形的单向链表了。最后把这个返回去——经过你的一番处理过后，**不要忘了一件事情：return**。return 什么呢？return 这个 `first`。好，这个头指针就有了。

没有返回值，因为是遍历。遍历的时候大家也注意，**我们也不要去动这个 `first` 指针**。我们来做一个动作，先定义或者创建一个指针帮助遍历：

```go
	curBoy := first
```

帮助遍历的话，我们就这样子来处理就行了。来一个跑龙套的，我们也叫 `curBoy` 吧，等于 `first`，先给它。

先给它过后，我们用 `curBoy` 帮助我们遍历。其实大家应该可以想象，假设我们就用这个 `first` 指针去遍历行不行呢？其实也可以——因为这边的改变也不会影响到主指针的改变，对不对？好，我们用这个帮助遍历的指针写完了，赋值为 `first`，然后开始做循环。

首先还是老规矩，对这种空的环形链表咱们单独处理一下：

```go
	if first.Next == nil {
		fmt.Println("链表为空，没有小孩")
		return
	}
```

什么时候为空呢？显然是如果 `first.Next == nil`，说明这是个空链表，啥都没有，一个小孩都没有。这个时候就不要遍历了，直接给它打一句话，说链表为空，没有小孩，就退出了，直接 `return` 就完事了。

如果说不为空，那下面就接着走。怎么走呢？说明它这至少有一个。只要这个地方没有进去，说明至少有一个小孩，对不对？那么我们就用 `do ... while` 的形式来处理它。因为说明至少有一个小孩，既然有一个小孩，那么我们就直接先输出小孩的信息。

注意听，看我的逻辑：`fmt.Printf`，我说"小孩编号为：%d"，它的编号怎么取呢？非常简单，直接用 `curBoy.No` 就可以了。我们也不去换行，就让它打成一排。

但是什么时候退出呢？退出的条件是什么呢？要思考。**如果没有退出条件，它就死在里面了，一定要退出**。它退出的条件是什么呢？退出的条件就是把整个遍历完了。也就是说 `curBoy.Next == first` 的时候，它就遍历完了。你想，现在 `curBoy` 指向这儿，你先把 1 输出出来了。输出出来之后再判断。注意我是先输出再判断的，它把 1 输出出来过后，我再下去把 2 输出去再判断。所以说这地方是很有讲究的。

```go
	for {
		fmt.Printf("小孩编号为：%d \t", curBoy.No)
		if curBoy.Next == first {
			break
		}
		curBoy = curBoy.Next
	}
	fmt.Println()
```

如果 `curBoy.Next == first`，这就说明我们显示到最后这个小孩了，就这个环形链表里面那个最后小孩。这个地方就是退出条件，我们这边就可以 `break` 出去，完事了。

### 核心算法：playGame 到底要做什么

现在我们已然构建出一个小孩了，下面就要解决它的一个核心问题，就是**算法**。你用一个什么样的算法把这个东西给搞出来，这个就叫算法了。

算法其实我们以前讲过，有固定的算法，比如说识别算法、语音识别算法，或者是一个编码算法；但是也有一些针对实际问题解决的，这个也叫算法——就相当于你自己设计的一个解决方案，都可以叫算法。

```go
func playGame(first *Boy, startNumber, countNumber int) {

}
```

`k` 这个含义不太容易理解，我就直接叫做 `startNumber`，代表从第几个小孩开始数；`m` 我取个名叫 `countNumber`，就是你数几个。这样相对来说比较好理解你想干什么。如果你直接写个 `k` 和 `m`，说实话你自己读起来比较累，别人也不太理解你是什么含义。

#### 两个前置判断

现在开始做第一件事情。刚才我们讲过，只要是单向环形链表，在删除人的时候有一个特别重要的要求，就是**它一定有一个辅助节点**，这个跑不了。所以我们先定义一个辅助的指针来帮助我们删除小孩。

还有一个情况，如果上来是个空的环形链表，咱们就别去删了，要防止这个问题，空的链表我们单独立处理一下：

```go
	// 空的链表，没有小孩，不玩了
	if first.Next == nil {
		fmt.Println("空的链表，没有小孩")
		return
	}
```

这就谈不上你出列的顺序了，那就直接 `return`。

第二个，你还应该要做一个判断：你的 `startNumber` 不能够大于小孩的总数。比如统共有五个小孩，但是你说我要从第一百个小孩数，这显然是不合理的。当然 `countNumber` 数几下可以是大于 `n` 的——虽然你只有一个小孩，我可以数一万下都行，自己数 1、2、3、4、5，这个无所谓。

> **注意**：这里还缺一个判断——`startNumber` 至少要小于等于小孩的总数。

#### tail 为什么要先站到队尾

接着我们往下说删除的事。先搞一个辅助节点，我们干脆就叫 `tail` 节点，叫最后。先让它指向 `first`——这显然是不对的，因为我们要知道这个 `tail` 一定要指向队尾、指向环形链表最后一个。先给它，然后下一步让 `tail` 指向环形链表的最后一个小孩。**为什么要这么做呢？因为在删除小孩的时候，`tail` 非常要用到它。**

我说一下这个思路，可能有些同学不理解什么意思了。打个比方，我现在有五个小孩，大家看我的思路。五个小孩已经形成环形链表了，我先把我思路给大家理一下，然后再写代码。假设是这样子的：

```text
   1 → 2 → 3 → 4 → 5
   ↑              │
   └──────────────┘

   上来过后，有一个 first 指针已经指向了一号
```

现在我需要一个什么东西呢？我的思路是这样子的：**我现在需要有一个指针要指向第五号节点**，我叫它 `tail`，它是一个辅助指针。

有些同学问为什么要这样做？因为待会儿我们要去比如说删除一号节点，如果后面没有这个节点，你删除不了。所以我们现在首先需要有一个 `tail` 指针指向最后。但现在还没有指向最后——你看目前我是让 `tail` 指向 `first`，也就是目前是这样一种情况。`tail` 先暂时指向它，这个没有用，你先得让 `tail` 定位到最后一个。

定位到最后一个，然后待会儿我们怎么做呢？比如说我们要从第二个开始数，那你先让它指向第二个。它在指向第二个的时候，`tail` 跟着同步往前移动——你移动几下我也移动几下。紧接着它又数两下，比如数两下，1、2，指到这儿来了。它指到这儿来的时候，`first` 指针也要指到这里。

比如说第三号应该被删除，第三号删除的时候我怎么做呢？我要这么做：我先让 `first` 指向这个，然后让这个 `tail` 指针的 `next` 指向它。

```text
   3 → 4 → 5 → 1 → 2
   ↑              │
   └──────────────┘
   first          tail

   做完 first 走一步 + tail.next 指向 first 这个动作之后：

   4 → 5 → 1 → 2 → 4
   ↑              │
   └──────────────┘
   first          tail
```

同学们看到，一旦我做了这么一个动作的话，其实整个环形链表这个就出列了。因为这个一旦指向它的话，**这根线就断掉了**。因此这个就变成一个出列的小孩。

弄完了过后，你这个 `first` 又开始数两下。它说 1、2，好，五号是 2。那么我后面这个 `tail` 指针也是跟着它同步往后面移动的。也就是说我这个 `tail` 永远在你的 `first` 的后边。

#### 两次同步移动

先定位，先让 `tail` 指向环形链表最后一个小孩：

```go
	// 先让 tail 指向环形链表的最后一个小孩
	tail := first
	for ; tail.Next != first; tail = tail.Next {

	}
```

只要这个 `tail`，它的 `tail.Next` 等于了 `first`，就说明它已经到最后了。加一个 `if` 语句：如果 `tail.Next == first`，那说明这个 `tail` 就已经到了最后一个小孩。大家看能不能理解。这个时候我们就毫不犹豫地 `break`。

**注意下面有个动作要跟着联动：`tail = tail.Next`。** 整个这个 `for` 循环结束以后，我们的环形链表的情况应该是这样子的——相当于你的 `first` 节点在这儿，你的尾节点到这儿来了。

紧接着我们来做一件事情。人家说了要从 `startNumber` 开始走，那也就是说此时此刻我们这两个指针要同步地往下移动。移动到什么位置呢？移动到你指定的 `startNumber` 这个地方去。那我们应该移动几次呢？显然我应该移动 `startNumber - 1` 次。

**为什么要减一次呢？因为你本身已经在第一个位置了嘛。** 比如说我要从第二号开始走，其实我只要移动一次就行了，因为你本身已经在一号了。

```go
	// first 和 tail 同步移动到 startNumber
	for i := 1; i <= startNumber-1; i++ {
		first = first.Next
		tail = tail.Next
	}
```

如果有同学这样写的话——如果这写的是 `0`，那你把等号去掉也是一样的，无所谓，看你是怎么理解的。我觉得写成从 1 开始、小于等于它减 1，可能大家看起来轻松一点，也可以。

移动的时候是 `first` 和 `tail` 都要移动，它们一起移动。当这句话走完了以后，你们可以想象，比如说数两下，它自己数一次，所以它就相当于移动到 2 了；移动到 2 之后，`tail` 就移动到 1 了。

> **易错点**：有人会问，为什么这个时候不去再设一个辅助节点让 `first` 不动？其实完全不用。因为反正我要把它全部干掉，`first` 最后也会被干掉的，你让它不动也没有意义——可能第一个干掉的就是它。所以 `first` 这个时候再设置一个辅助节点没有用了，`tail` 已经是辅助节点了。**我们删除小孩就以 `first` 为准：走完了过后 `first` 指向谁就删掉谁。**

#### 出列、终止条件与最后那个小孩

移动到这个位置了，紧接着开始数 `countNumber` 下。数 `countNumber` 下其实也是移动的意思，紧接着再移动。第五步，继续移动，开始数 `countNumber` 下，然后就删除 `first` 指向的那个小孩。

这一定是个循环。因为无论数多少下，最后只留一个人，所以它一定是个循环，`while` 循环来了。怎么是个循环呢？因为你不是删一个小孩就走，你要删到剩最后一个小孩，所以肯定是用循环干掉的。

```go
	// 循环地数 countNumber 下，然后干掉 first 指向的小孩
	for {
		for i := 1; i <= countNumber-1; i++ {
			first = first.Next
			tail = tail.Next
		}
	}
```

开始数 `countNumber` 下，其实也是移动 `countNumber - 1` 次，因为它自己要数一下，所以不能移动 `countNumber` 下，而是移动 `countNumber - 1` 下。这段代码和刚才很像。

> **提示**：这个地方是一个考大家的重点，稍微好一点的公司可能会问这些东西。

循环移动完之后，现在可以干掉它了。也就是说这个时候代码已经走到这儿了，它数两下，1、2，这两个指针分别移动到位。现在相当于 3 号要被干掉，怎么删掉它？非常简单，删除 `first` 指向的小孩节点：

```go
		// 干掉 first 指向的小孩，先把它的信息报出来
		fmt.Printf("小孩%d出圈\n", first.No)

		// first 往前走一步
		first = first.Next
		// tail.next 指向 first
		tail.Next = first
	}
}
```

这两句话怎么理解呢？被干掉的就是 `first` 原来指着的那个人。先把 `first` 往前移动一步，紧接着让 `tail` 的 `next` 指针指向它移过去之后的那个位置——原来那条线就断了，被夹在中间的节点就脱离出了这个环。

> **易错点**：打印出圈编号必须放在 `first = first.Next` **之前**。一旦先移动，`first` 已经指着下一个人了，再打印报出来的名字就整体错位一位——而现场测试出来的出圈顺序是对的，这一步的先后关系一眼就能验出来。

那问题来了，这个地方如果没有退出条件，它会死循环，不会停止。什么时候代表整个处理完了？大家想一想，根据刚才这个逻辑一直走，只有一个条件：**最后只剩下一个小孩了**。只有一个条件，最后只剩下一个小孩会形成什么情况呢？就是你的 `first` 和 `tail` 相等了。大家要有想象能力，剩两个的时候再删一个，`first` 再一移动不就又指向 `tail` 了吗？所以什么时候退出呢？就是只留一个小孩的时候，我们可以加一个判断：

```go
		// 说明圈子中只有一个小孩了
		if first == tail {
			break
		}
	}

	fmt.Printf("最后留在圈里的小孩编号为：%d \n", first.No)
```

如果把这个小孩也删掉就相当于整条链表置空了，所以我们这里加一个判断：如果 `first == tail`，那么这个时候就 `break`。

`break` 之后，留下的最后一个小孩把它也输出出来。把最后这个 `first` 的编号打印出来就可以了。

整段代码梳理一遍检查一下：空链表做了一个判断，做了一个辅助指针 `tail` 移到最后，再移动到 `startNumber`，开始数 `countNumber` 次，不停地循环数并出圈，最后留下一个。

### 跑一遍：从第 2 个开始数 3 下

我们来进行一个简单的测试，`playGame`。走一个简单一点的顺序，就根据刚才老师说的方式来玩——从第 2 个开始数，数 3 下：

```go
	first := AddBoy(5)
	showBoy(first)
	playGame(first, 2, 3)
```

输出的时候换一行，我们看看出圈的顺序。第一个是 4 号，接着是 2、1、3、5，最后一个是 5 号。我们手动分析验证一下：

从第 2 个小孩开始，指针先移动到这儿，没问题。然后开始数 3 下，1、2、3，指针移动到相应位置，4 号出列。4 号出列后指针调整，第一个是 4 号出列，没问题。紧接着接着数，1、2、3，2 号出列，让指针往前移动，指向下一个节点。再紧接着继续数 3 下，1、2、3，1 号出列，指针对应移动——4、2、1，正确。

最后只剩两个人，数 1、2、3，3 号出列，最后只剩 5 号。出圈顺序是 **4、2、1、3、5**，代码是完全正确的。

## 四个排序的名字，和选择、插入两种排序的思路推导
> 对应块：BLK146 | 覆盖分集：P365-P366 | 块标题（分集名）：《363_尚硅谷_数据结构和算法-选择排序》

### 你们现在还能不能把冒泡默写出来

排序是一个比较重要的知识点，因为它可以锻炼一些编程的思想在里面。

排序最常见的有这么四种：第一种叫**冒泡排序法**，第二种叫**选择排序法**，第三种叫**插入排序法**，第四种叫**快速排序**。这四种是比较经典的，作为编程人员必须掌握的经典排序算法。

关于冒泡排序法，在前面已经讲过了，这里就不再多说。但是冒泡排序大家想一想，以前在讲的时候，你们现在还能不能把它默写出来？

选择排序法、插入排序法和快速排序法，今天我们来讲一讲。我是要求同学们**选择、插入、快速必须把它默写出来**。快速排序可以不做默写，因为快速排序确实稍微难一点；但是选择和插入，也需要同学们能够不参考任何代码也能把它写出来。

排序是一种将一组数据按照指定的顺序排列的一个过程。从速度上来看，**选择排序要快于冒泡，插入排序又比选择要快一些，快速排序是最快的**，在这四个方法里面它是最快的。

> **结论**：四种排序的定位先摆在这里——冒泡是入门，选择是稍快，插入又快一倍，快速最快。四个名字必须张嘴就来，因为后面要拿它们互相比较。

### 选择排序：把"选"和"交换"拆成两步

选择排序也叫选择式排序，它也属于**内部排序法**。什么叫内部排序呢？就是把这些数据都调入到内存里面，然后进行排序。它从排序的数据中按指定的规则选出某一个元素，经过和其他元素的重整，再依原则交换位置后达到排序的目的。

但这句话说完了过后，大家可能不太清楚它说的什么意思，我们就来看它的一个思想，这样子大家可能看起来比较简单一点。

**基本思想是**：第一次从 $R[0]$ 到 $R[n-1]$ 选取一个最小的数值——先从整个数组里面选一个最小的，与 $R[0]$ 进行交换。第二次从 $R[1]$ 到 $R[n-1]$ 中选取最小值，再跟 $R[1]$ 交换。其他以此类推。经过 $n-1$ 次，我们就得到一个顺序了。这个顺序可能是从大到小，也可能是从小到大。

> **定义**：注意"选"和"交换"是分开的两件事。选，是在剩下的乱堆里把最小的挑出来；交换，只挑中之后才动一次手。

#### 在 8, 3, 2, 1, 7, 4, 6, 5 上走一遍

我们来看它的一个图解，大家一看就清楚了。同学们看这里，这地方有一个数组：

```text
   初始：  8   3   2   1   7   4   6   5
   第1轮：  1   3   2   8   7   4   6   5     ← 找最小 1，与 8 换
   第2轮：  1   2   3   8   7   4   6   5     ← 找最小 2，与 3 换
   第3轮：  1   2   3   8   7   4   6   5     ← 最小就是 3，自己跟自己换
   第4轮：  1   2   3   4   7   8   6   5     ← 找最小 4，与 8 换
   第5轮：  1   2   3   4   5   8   6   7     ← 找最小 5，与 7 换
   ……
   最终：  1   2   3   4   5   6   7   8
```

假设我们要从小到大排。它第一次的初始状态就是这样子的，然后它找到这个数里面最小的这个数——是谁呢？是 `1`。让这个 `1` 和第一个元素进行交换，相当于 `1` 和 `8` 交换。

完了过后，再找第二个元素，从后面的元素里面找一个最小的，跟谁交换呢？跟第二个元素交换。大家想一想，`3, 2, 8, 7, 4, 6, 5` 里面最小的显然是 `2`，那就是 `2` 和 `3` 交换。

紧接着再从这个数组里面找一个最小的，显然是 `3`。`3` 因为它本身已经最小了，相当于自己跟自己交换，不交换。

紧接着又在这个数组里面找出最小的，这里面最小的是 `4`，`4` 和谁交换呢？`4` 和 `8` 交换。

紧接着再从这里面找出最小的，是 `5`，`5` 和谁交换？`7` 交换，以此类推。最后形成一个顺序，叫 `1, 2, 3, 4, 5, 6, 7, 8`。

当然这是从小到大。如果从大到小，你判断的时候只需要把最小的改成最大的就可以了。

#### 第一步：先把最大值钉到 arr[0]

我们来分阶段走。

**为什么要分步骤呢？因为希望你们理解。** 等哪一天突然你有将近半年没有写选择排序了，突然有个面试官说来写一个，你想用这种方法——因为我们人的思维最好一般有个过渡的。所以我先给你们完成一个最简单的，一看规律马上就套出来了。所以仍然使用我们的**先易后难**法，先易后难，然后层层分解。一定要学会这种编程的方法：**先易后难，先死后活**，以前我讲过。

第一步，先完成将第一个最大值和它交换。这个对我们来说应该没有难度。你可以这样做：你先假设你的第一个元素就是最大值，我们以前就这么干的。

```go
	max := arr[0]
	maxIndex := 0
```

这个没有毛病。然后我把它的最大值的下标也记录下来，因为待会儿要发生交换——就是 0，没问题。

但是你这假设的最大值是不是最大值呢？不一定。因此你要开始遍历。

第二步，遍历后面的元素，1 到哪里呢？到 `len(arr) - 1`，注意听，是 `len(arr) - 1` 这么多的元素。因为下标是要减 1 的。遍历后面的数进行比较。

这对于我们来说特别的简单。那 $i$ 等于几呢？1。但是这个 1 是怎么来的？各位同学，这个 1 其实准确地讲是 $0 + 1$。**为什么我这么去写？** 就代表我遍历的时候是第一个——你假设这个值不需要再参与比较了，你自己跟自己比较不是很无聊吗？我已经假设它是最大了，它只跟后面的进行比较。所以这个 0 其实就是代表的这个值，因为待会儿就能把这个规律找出来。

$i$ 小于多少呢？它小于 `len(arr)` 就可以了。因为我是小于，没有取等于，所以相当于它本身这个是取不到的，然后 `i++`。

现在开始比较。如果你认为的最大值，它还小于了你的这个值——如果这个条件成立，就说明什么呢？说明你认为的最大值它不是最大值。你就交换。

> **注意**：现在**不要交换**。注意选择排序法它最经典的地方是**先不交换，先找到最大，最后再交换一次，这是它的一个效率提升的关键**。如果你这马上交换就毫无意义了。

所以这个地方是"假设最大值不是最大值"，这就**开始更新记录**：

```go
		if max < arr[i] {
			max = arr[i]
			maxIndex = i
		}
```

经过你的这层 for 循环，那么你就应该找到了下标为 1 到下标 `len(arr) - 1` 之间的最大值，是不是？如果是这样子的话，我们就**交换一次**。

但是交换有没有一个判断呢？什么情况下交换？`maxIndex` 不等于 0 的时候才交换。如果结果你假定的最大值就是最大值，那就不要交换了。所以这边应该有一个判断条件：如果我们最后得到这个 `maxIndex` 不等于我假设的这个 0，如果它等于 0 说明我们假设的就对了；它如果不等于，我们才交换。

这样可以节省一次交换。因为**交换本质它是很费时间的，交换是尽量少发生。比较可以，比较相对来说比交换的效率要高**，所以你看它有效地利用了这个特点。

那么怎么交换呢？非常简单：

```go
	if maxIndex != 0 {
		arr[0], arr[maxIndex] = arr[maxIndex], arr[0]
	}
```

大家看这个能不能理解？我们以前是写过这种写法的，这种写法就相当于把这个值给到了 0，把这个 0 给到了它。我们以前写的是用了中间变量，这个我就不用了——其实它底层也会用一个中间变量来处理，或者是用地址来处理的。我们就用它的方式就可以了，这效率相对高一点。以后发生交换咱们就用这种写法，这是 Go 语言的一种比较有意思的语法现象，大家记住就可以了。

### 插入排序：一边找位置，一边让有序表后移

好的同学们，刚才给大家介绍了选择排序。现在我们来看另外一种排序方法，叫插入排序。插入排序的速度会比选择排序更快，待会儿我们会做一个比较——待会儿我们会去构建一个 8 万甚至是 800 万的一个数组，我们看看哪一个排序方法更快。你会突然发现，它们真的是有差别的，它的差别在哪个地方，到时候可以做一个分析。

插入排序它也属于内部排序，它是**对欲排序的元素以插入的方式来寻找该元素适当的位置**，以达到排序的目的。

插入排序理解起来，从代码的理解难度上比选择排序要稍微麻烦一点，但是**它的思想很先进，所以它的速度一般来讲会比选择排序至少快一倍**。那为什么呢？大家看它的思想。

**插入排序基本思想是**：把 $n$ 个待排序的元素看成是一个**有序表**和一个**无序表**。什么意思？就是说我先把第一个元素就当做一个有序的，因为你只有一个元素，无论从小到大还是从大到小，它都是有序的。

开始的时候只有一个元素，无序表中有几个呢？有 $n-1$ 个。就是说我把第一个看成一个有序的，$n-1$ 看成一个无序的，然后干什么呢？排序过程是每次从无序表中取出第一个元素，把它的排序码依次与有序表的元素码进行比较，将它插入到有序表中的适当的位置，使之成为一个新的有序表。

但这句话说完过后你也不知道它在说什么，因为你很难理解它的含义。那么这样子，我给大家画一个简单的示意图，我把我的思想给它说出来，然后我们走代码。还是以小牛的成绩排序来进行，现在我们还是以从大到小。假设这个数组最原始的时候是这样子的：

```text
   原始：  [ 23 ][  0 ][ 12 ][ 56 ][ 34 ]
           有序表            无序表
```

#### 第一步：把 23 当成一个有序表

好，这是第一步。此时 `insertIndex` 停在有序表最后一位，也就是 `23` 所在的下标。

#### 第二步：把 0 插进去

第二步，从它后面的数给它找一个适当位置——给 `0` 找一个位置插入。注意还不涉及到后面，`12、56、34` 没有参与。

那么它在找的时候是从哪儿开始找呢？注意，它的思想是这样子的，**这个地方很重要，思路特别重要**：

- **先**将 `0` 保存到一个变量中，比如说我姑且把它叫做 `insertVal`——就是这个值是准备我要插入的，往 `23` 这个有序数组里面插；
- 然后插入的时候，插入的位置用一个变量保存，姑且叫 `insertIndex`——它是 `0` 的下标的前一个下标；
- 然**后**从这个有序数组的**后面**开始比较，给 `insertVal` 找到一个位置，找到位置然后插入。

那就开始比较了。它先让 `0` 跟 `23` 比较，如果它发现 `0` 比 `23` 小，那么说明这个位置就找到了。

> **易错点**：在找位置的过程中，有序数组的元素会后移。这个大家可能有点不好理解。

第一次找到插入位置。因为 `0` 它的确比 `23` 小，所以说它一下就找到位置了。找到位置过后，就变成这个样子了，有序列表就变成 `23、0`，后面还有三个数是无序的：`12、56、34`。

#### 第三步：把 12 插进去

第二次就给 `12` 找位置。那么现在 `insertVal` 这个值就变到了 `12`，它的 `insertIndex` 变到了 `1`。

第二次开始找位置，注意看，`12` 它是比 `0` 大的，它如果比 `0` 大的话，这个 `0` 就往后移。后移就变成 `23、0、0、56、34`。

当然有同学会说了："老师，那你这个 `0` 往后面移动了一下，那 `12` 不就没有了吗？"不要忘了，`12` 已经被保存到一个变量里面了，它已经被保存起来了。所以说这个时候继续让 `insertIndex` 往前移动一下。当然这个时候这个 `insertVal` 还是 `12`，它没有动过。然后让 `23` 跟 `12` 进行比较——`23` 是大于 `12` 的，位置找到了。

位置一旦找到，好，在这个地方只需要在 `insertIndex + 1` 的位置把它加进去就可以了。`23` 不动了，因为它已经比 `12` 大了，不能再往后面移动了。那这个时候就把这个位置的 `0` 用 `12` 替换——`12` 因为已经保存到 `insertVal` 了嘛，所以说这个 `12` 就被覆盖了。

覆盖过后，这个 `0` 还是这个位置，`56、34`。第二次做完了以后，这个结果应该是有序的：

```text
   [ 23 ][ 12 ] | [ 0 ][ 56 ][ 34 ]
```

#### 第四步：56 和 34 的下场

其他依次类推。比如第三次，`insertVal` 就变成了 `56`。这时候下标在这儿，`56` 比 `0` 大，所以 `0` 会往后面移动一下，就变成 `23、12、0、0`——没问题。后面这个 `34` 不参与比较，但是放在这儿的。

那么这个时候你的比较下标往前移动一下，继续指到前面那个位置。你的 `insertVal` 还是 `56`。那么 `56` 比 `12` 大吗？还是比它大，说明没有找到位置，所以说继续往后面移动。也就是把 `12` 往后面移一下，移一下过后，我紧接着再让 `insertIndex` 往前移动，再比较——`23` 比 `56` 大吗？`23` 比 `56` 不大。不大的话，好，那这个时候继续往后面移动一下。

> **提示**：难就难在这个地方，它在不停地移动。

`23` 往后移动一下就相当于拷贝了一下。好的，这个时候注意听，它再往前移动，发现已经不能再移动了——它移动不了就说明的的确确这个 `insertVal` 是最大的。它移动不了的话，它当然仍然会移动一下才会退出这个循环。也就是说这个时候 `insertIndex` 还是指向 -1 了。这个是它不参与比较了。这个时候怎么办呢？它让 `insertVal` 直接在 `insertIndex + 1` 的位置把它覆盖了。

**这点很重要，就是加一的位置加进去。** 也就是说这边变成了 `56、23、12、0、34`。它其实在不停地找位置，然后找到一个适当位置加进去，就是这个道理。

第四次也是一样的道理了。第四次的话，插入的值就相当于是 `34` 了。他每次都从最后找。`34` 和 `0` 比较——`0` 不对。于是乎这个地方就移动了：`56` 不动、`23` 不动、`12` 不动、`0` 往后面移动一位。移动一位，下标就指向了它。

`12` 比 `34` 仍然是小的，所以说还没找到位置，紧接着把 `12` 往后面移动——`56、23、12` 不动，`12` 往后面移动一位，原先那个位置现在是 `12`、`0`。注意，移的时候这个地方还是 `12`。说老师这两个 `12` 怎么办？没关系，它是复制过去的。

`12` 移动完了过后，继续往前面移动一位，变成 `23`。`23` 跟 `34` 比较，仍然没有找到位置，因为 `23` 比 `34` 小。小的话，`23` 继续往后面移动。那这个变成了 `56、23、23、12、0`。

它移动完了过后，往前面移动一下，走到 `56` 这边了。他发现 `56` 比 `34` 大，说明找到位置了。紧接着就在 `insertIndex` 这个指标的**后面**这个地方插入。

> **结论**：这点很重要，它是在 `insertIndex` **后面**这个位置插入。这样子一插进去，`34` 就插入到 `23` 的位置，`56` 仍然还在最前面——变成 `56、34、23、12、0`。完毕。

#### 为什么它比选择排序快：比较次数除以 2

那有同学说，老师，这个有什么好处吗？这个的好处其实大家可以看到，它非常优越的地方是：**因为它总是从一个有序数组在找位置，所以它的比较次数其实是在减少的。**

因为我在从后面找，我是容易找到有序数组的位置加进去，我不需要遍历整个数组。而你以前的冒泡也好，包括你以前的选择排序也好，它总是从一个无序里面找的，所以说它比较的次数总是要遍历完。所以插入排序它的速度绝对是要比选择和冒泡快，至少一倍。

待会儿我们可以做一个试验：比如我 8 万的数据，我用插入排序可能 4 秒，那么你的选择应该是至少 8 秒，冒泡就更长了，冒泡一般在 9 秒、10 分钟左右。

至于大家可以看到，现在有一个问题，就是说他在每一次比较的次数到底是多少次，能确定吗？**不确定。** 它可能很快就退出来了，也可能把这个遍历完才退出。打个比方，你运气很好，这个地方刚好不是 `34`，是一个 `-1`，它就比较一次就完事；如果你很不幸，这个地方它就是最大的，它就遍历完。

所以说他每次进行比较，比较次数是多少次，不清楚。**按概率来说应该除以 2 的。** 因此就相当于说原先我们冒泡也好、选择也好，都是要进行整个数组的遍历，但是它变成了除以 2，所以它的速度就会变成原先的两倍。从概率上来讲就是这样子的，所以它的速度相对来说是前面三种里面最快的一种。

> **结论**：选择排序每一轮都要在**无序区**里把整个区间扫一遍，扫完才知道该换谁；插入排序每一轮只在**有序区**里从后往前找，找到就停——平均扫一半。快一倍不是玄学，就是这个 `1/2` 的来源。
