## 把 Redis 跑起来：最先要熟的十几条指令，和它们背后的那块内存

### 启动：双击 server，双击 client

首先把它启动起来，这个非常简单。在这里我们直接双击一下 server。双击过后，同学们，**这个服务就不要关闭了**。

大家现在看这个应该看得很亲切了，因为 `accept` 什么意思、端口什么意思、连接什么意思，大家不会说一点概念都没有了。**所以说前面基础知识还是非常重要的**，尤其是第一次接触这种编程的同学。这就相当于你可以理解成我们上午写的一个 server，其实本质是一样的。

启动起来之后——有同学问，跑得了不？跑得了，放心好了，肯定跑得了。你是担心什么呢？担心本地服务？这个应该没有这个问题，有问题我们再说。你可能以前遇到过这个问题，但这个应该没有什么毛病，本地服务如果遇到了我们再调，应该不会出什么问题。

有了过后，刚才画的示意图我也讲过了，这个就不再多说。启动起来以后，我们把客户端也启动起来。

大家看，我们目前**先用 redis-cli 去玩，先不用 Go 语言**。因为先用它把基本的指令学完了，咱们再去用 Go 语言去连，其实就是顺理成章的事情，就特别简单。

注意，这个 client 端它已经把它要操作的端口配置好了，所以你双击就有点类似于我们启动今天早上写的那个 `client.go`，机制上它里面也有去连。双击，大家看已经连上了。因为你是本地，所以一下就连上了。它的意思就是说，我已经连到了本地的 IP 的 6379 端口。

### 指令去哪查：redisdoc.com，以及为什么不用背

启动起来过后，我们来看一下它的基本指令。Redis 的基本指令在哪里呢？网上有一个站点叫 **redisdoc.com**，这里面就把我们 Redis 的一些指令或者叫命令全部都写出来了，很多。

今天我们不可能把所有的全部讲完。如果把 Redis 放在 Java 里面去讲的话，一般我会至少讲两到三天。那么我们这块因为是 Go 语言，我们主要是解决怎么往里面存和取的问题，我们讲一些最核心的就可以了。

这个站点里是按结构分好类的，可以用 Ctrl+F 来快速查找：

| 你想做什么 | 去哪一栏找指令 | 常见的几条 |
| --- | --- | --- |
| 操作 Key 本身 | Key 的操作 | — |

今天我们不可能把这全部说完，我们说的是核心。只要今天学完了过后，我可以负责任地讲，你往里面存数据，**任何一种数据你基本可以玩了，怎么取咱们也能玩了**。至于其它的，在项目的使用过程中咱们再加深一下就可以了。

> **结论**：相关的指令在哪个网站去找呢？在这去找就行了，**不用背**。这玩意你没有必要去背它，把原理搞清楚了。

### 快速入门：十六个库，先摸五个指令

Redis 一启动以后，它**默认有 16 个数据库**，这 16 个数据库是用编号来标识的，一个是 0 到 15，一共 16 个。

我们先快速过一遍：添加一个 Key、查看数据库里面所有的 Key、获取 Key 中对应的值、切换、查看当前数据库的 key-value 数量，还有清空当前数据库的 key-value 和清空所有数据库的 key-value。也就是说它操作的数据都是对这里面的操作。

#### 添加一个

添加 key-value 的指令是 `SET`，那我就直接来玩了。打开客户端，往里面操作，输入 `SET` 指令。当你输入的时候，它会有提示信息——你看这个 `SET` 后面可以带什么呢？带 key、value；后面中括号的部分代表其他信息，比如说超时多少时间，对不对？这些如果你不需要，可以先不用管它。

```bash
set k1 "hello"
```

一回车，OK 了。这个指令就是往里面添加一个 key-value。这个是你的 Key，名字就叫 `k1`；你的值就叫 `"hello"`。

#### 一次 set 背后到底发生了什么

大家想一想，刚才这个指令一执行过后，在你的脑海里面，你应该想象到这个指令是怎么执行的呢？我就画一次示意图。

```text
   客户端 (redis-cli 或 Go 代码)
            │
            │  set k1 "hello"
            │  ① 指令通过网络发给 Redis
            ▼
   ┌──────────────────────────────────┐
   │        Redis 核心组件            │
   │  ② 解析：哦，是 SET，字符串类型   │
   └────────────────┬─────────────────┘
                    ▼
   ┌──────────────────────────────────┐
   │     内存中的 0 号数据库          │
   │        k1  ──►  "hello"          │
   └──────────────────────────────────┘

   取的时候反过来：
   get k1 ──► 核心组件解析出要 k1
          ──► 在内存里找到 k1
          ──► 把 "hello" 返回给你
```

读图：`SET` 一回车就通过网络发给了核心组件，核心组件解析出这是字符串类型，就往内存里放；此时默认是在 0 号数据库里放了一个 Key 为 `k1`、值为 `"hello"` 的数据。反过来取的时候，`get k1` 同样走网络、同样被解析，核心组件在内存里找到 `k1`，把值返回来。就是这么一个简单的过程。

#### 取出它

获取怎么写呢？

```bash
get k1
```

这样就把 `"hello"` 得到了。

#### 切换数据库

如果说你不想在 0 号数据库，说：「老师，你不是有 16 个吗？我想用第二个数据库行不行？」可以，这样操作，非常简单——`SELECT`。

```bash
select 1
```

这个时候同学们，我就切换到 1 号数据库了。你可以这样想象：在它这里面，它的内存有 16 份，有一份是我们的 0 号，还有一份是 1 号，还有一份是 15 号。这个时候这里面是空的，这个数据库里面的内容是空的，啥都没有。那大家想，如果这没有的话，我要去获取肯定是拿不到东西的：

```bash
get k1
```

是个空的，没有东西。好，我再切回去 0 号：

```bash
select 0
```

我再 `get k1`，拿到了。这个很好理解，来回可以切换。

#### 数一数和清空

紧接着我们看一下查看数据库当前一共有多少 key-value 数量，指令很简单：`DBSIZE`。

```bash
dbsize
```

你要查哪个数据库？默认是当前数据库。回车，我现在只有一对 key-value。假设我再加一个：

```bash
set k2 "atguigu"
```

回车。这个时候我再看 `dbsize`，果然是返回 2，有两对，非常简单。

然后是清空数据库。清空指令是 `flushdb`。

> **结论**：如果我写的是 `flushdb`，代表我清空**当前**数据库；如果我执行的是 `flushall`，代表把 16 个数据库的数据**全部**清空。区别就在这里。

所以你看，当你把一些复杂的东西都搞明白的时候，这个就跟玩儿似的了。**学习的先学的东西如果你越困难，你再去看简单的东西，你觉得很轻松。**

### 字符串：它就是最普通的一对 key-value

虽然我们学完 Redis 时间不是很长，但是别人一问你「Redis 支持哪些数据类型」，你必须得答上来。这个是必须答上来的。

字符串是 Redis 的**最基本的数据类型**。它是一个 key 对应一个 value，一个 key 就对应一个 value，key-value、key-value、key-value。

有点像怎么理解呢？比如说我们学 Go 的时候，我们是这样定义一个字符串的：

```go
str1 := "hello"
str2 := "张三"
```

这个就是一个字符串。你看这个 key 就有点类似于 `str1` 和 `str2` 这个名字，这个值就有点类似于你赋给它的这个值。这样一下就理解了——说白了就是用一个 key 来标示一个字符串。那我们在 Go 里面，我们不是用一个名字去标示一个字符串吗？意思一下就到位了，没难度。

#### 二进制安全，和 512M 的天花板

它在 Redis 里面是**二进制安全**的。它可以存放普通的文本，也可以存放图片。

你可以这样想：我们前面不是学过对文件的读写吗？你可以用读文件的那个把 file 一读进来，不是 byte 切片吗？你把这个东西整合一下，装在这个 Redis 里面都能装进去，理论上都能装进去。也就是说，你把图片保存到数据库里面去了，别人看不到；你要读的时候你把它一读出来，然后再重写回去，它又变成一个图片了，还是很有意思。

但是**一般也没有哪个人吃饱了没事干把图片存在数据库里面**。比如图片很大，10 兆，你把 10 兆存在内存里面去，很浪费的——刚才大家看到这个图，这个**内存本身是很珍贵的**，没有哪一个人吃饱了没事干说我这有一个电影，我存到内存里面去。电影 10 个 G，内存本身很珍贵，10 个 G 一下撑满了，你看电影也不方便了。所以一般不会这么干，但是它理论上是可以支持的。

还有：**Redis 的字符串最大是 512M**。所以说你也存不太大，它默认支持 512M，这是它在设计层面上面就这样干的。其言外之意就是说，你别给我整得太大了——但是指的是一个，它是指**一个**字符串只能存这么大，那两个字符串就二倍了。

#### 增删改

我们来存放一个信息吧。存放一个地址信息，地址：北京天安门。说明：这个 key 就是 `address`，北京天安门就是值。

```bash
set address beijing
```

这个我输中文，大家看，进不去。我一输中文变成一个空格了。我一回车，进去了。但是当我获取的时候——

```bash
get address
```

其实我是获取到的，一看，同学们看，这个就是北京天安门。但是有的时候怎么变成这个样子了呢？它在存放的时候它是转了一下码的。所以你也不用担心说「老师，那我将来在程序里面读出来难道它也是这个码」？

> **提示**：不会。如果当你读出来以字符串的形式打出来，它又变成正确的编码了。所以这个地方只是在我这个控制台是这样子的，因为我的控制台编码是 GBK，所以它有可能显示不正确，**但是用程序读出来它会正确显示**。所以大家不用特别担心这个事情。

> **结论**：`set` 指令如果存在就相当于**修改**，如果不存在就相当于**添加**。还有 `get` 和 `delete`——`get` 就是把那个键的名字写进去就可以了；`delete` 就代表删除，比如说因为某种情况你不想想要这个字符串了，你可以把它 `delete` 掉：

```bash
del address
```

回车，删掉了。我再获取：

```bash
get address
```

一回车，`nil`，空了。这个就是删除指令。先删掉，然后我再去获取的时候，它就变成了一个 `nil`。

### setex：让数据自己过期

关于字符串的操作，还有几个需要注意的地方。

有一个地方需要同学们注意，说老师，假设我有这么一个功能，你能不能帮我实现：我需要这个人在线，最多他登录上去过后，给我在线 30 秒，我就让他消失在人间？

**可以。** 你比如说有的时候我们放一个留言，我们是保留 30 秒，如果 30 秒之内你取就有，30 秒之后没有了。比如有些代码里面有这个需求，我发一个消息，你在 30 秒之内不取我就给你删掉，可不可以？可以。还有我们有这样一个功能是，比如说我们一个用户在线时间最多你操作的时候最多操作一分钟，一分钟如果你没有操作完的话直接给你退出，也可以。

那这个时候可以怎么做呢？它有一个指令叫 **`setex`**。

这个 ex 翻译成英文就是 expire，就是超时、废除的意思。

```bash
setex message01 10 hello,world
```

这个指令非常简单：就是 set，把这个 key、秒和值写进去就完了。比如说我有一个业务消息 `message01`，然后我给它设置 10 秒钟，这个值是什么呢？比如说叫做 `"hello,world"`。

写完了，回车。再 `get message01`，可以看到。我们稍微等一会儿，再回车，没了，`(nil)`。

10 秒已经到了。它自动在内存里面有一个机制，它发现你设置了这个超时以后，发现 10 秒钟过后，数据就自动给你销毁了。谁来销毁的？大家想一想——肯定是我们在核心组件在不停扫描，它发现 10 秒过后，再去就没有了，它就自动给销毁。

> **结论**：这个指令可以帮助我们去做一些比较特殊的需求，就是需要有定时的、定时器、定时任务，咱们可以这样做。

### mset 和 mget：一次搞定多个键值

关于字符串的增删改，还有两个比较有用：一个是 `mset`，一个是 `mget`。

听这个意思就知道了，`mset` 是一次性可以设置多个 key-value，就有点类似于我们在 Golang 里面一次性声明多个字符串：

```go
var (
	name1 = "tom"
	name2 = "..."
)
```

一次性定义多个这样的字符串。在 Redis 里面它也可以这么干，怎么干呢？`mset key value key value`。

比如第一个我们要存放什么呢？第一个人的名字，比如是 `worker01`，他的名字是汤姆；再来一个 `worker02`，第二个工人的名字是什么呢？是 `scott`。写完了，回车。

这个时候相当于我定义了两个字符串，一个字符串的 key 为 `worker01`，一个字符串为 `worker02`，这个关系是给你匹配的。

那我怎么获取它呢？获取的时候完全可以一个一个获取。「老师，我一个一个获取可不可以？」当然可以了，比如我就直接获取到 `worker02`，那就是 `scott`。

有些同学说：「我想一次性把它都获取回来，可不可以？」也可以，就是 `mget`：

```bash
mget worker01 worker02
```

回车，两个就都出来了。

> **结论**：如果说翻译到我们的 Golang 语言，它会给你返回一个切片，也可能是个数组，反正你遍历就把这个东西拿到了，所以它这个还是很灵活的，完全可以类比来学习。

我们学这个技术，只要你思路清晰了，还是很容易学好。包括你们做项目以后，只要思路清晰了，没有什么特别难的。

### 哈希：把一个人的信息收进一个 key

待会儿会有小练习。

哈希，来看看哈希。其实哈希是一个人的名字——**哈希这个人为什么这么有名？他搞了一个哈希算法。** 他是一个人，他真的是一个人。哈希这个人搞了一个算法，搞出来的算法特别好，大家觉得这个人很好，于是就以他的名字来命名这个算法，叫哈希算法。以后你搞一个名字，比如说肖健算法，也行。

这个哈希类似于 Go 语言里面的一个 `map` 这种结构。也就是说，刚才大家看这个字符串是很简单的，就是 key-value、key-value，很笨。有时候你想描述一个人的信息，比如说我让你们在 Redis 里面去保留一个人的信息，你把它分散存起来你肯定不舒服吧。当时我们在讲 Go 语言的时候，我们也是这样想的：**单个基本数据类型不行，于是人家搞了一个 map。**

Redis 的设计者也不是吃素的，他想一定会有人想去描述一个相对综合一点的数据，那这个时候他就搞了一个哈希。

> **定义**：哈希是一个**键值对的集合**。原来是这个意思，那就有意思了。map 说到底本质上不也是键值对的集合吗？它本质也是这样子。

它的结构有点类似于：`user1` 就有点类似于我们 map 里面的名字，如果这个 `user1` 是 map 的名字，那么到时候哈希的 key、哈希的名字就是这个 `user1`；里面 map 里面的 key-value、key-value，那我这个哈希的名字也对应这个东西，待会儿大家注意看。

> **定义**：Redis 哈希是一个 **string 类型的 field 和 value 的映射表**。听这个名字，string 类型的——它也就是说它只能放字符串了。

哈希**特别适合用于存储对象**。那反过来就是特别适合存放我们的结构体，是不是这个意思？你看，咱们在 Go 语言里面，我们说对象其实就是用结构体实例来体现出来的。其实以后你们要去存结构体，你们就可以这么玩了。

#### 存一个 user

我举个例子。比如现在我给大家一个要求：要求同学们在 Redis 里面存放一个 user 信息，这个 user 的名字叫 `user1`。这个 user 有什么信息呢？名字叫史密斯（Smith），年龄是 30 岁，工作 job 假设是一个 Golang 开发工程师，Golang coder。

那如果我让你在 Go 语言里面去定义，你肯定会选 map，或者说放一个结构体。那这个时候，在 Redis 里面我们就可以用哈希来保存。

首先，往里面放这个哈希怎么存呢？它的指令要发生变化。我们前面放字符串的时候我们用 `set`，如果我们放哈希这种结构要用 **`hset`**，前面这个 `h` 代表 hash 的意思。

```bash
hset user1 name Smith
hset user1 age 30
hset user1 job "Golang coder"
```

这两端引号你可以给，也可以不给，写完了过后你回车就可以了。当然有同学说了，好麻烦，怎么要一个一个写呢？当然，它也可以一次性地写，我们待会儿再说。现在我们先看看信息有没有。

那么怎么获取呢？显然，它有一个叫 **`hget`**：

```bash
hget user1 name    → Smith
hget user1 age     → 30
hget user1 job     → Golang coder
```

速度非常的快。现在 Redis 速度很快的，它相对在内存操作，所以现在 Redis 为什么这么流行。

> **易错点**：大家看到，你其实给了一个整数也没用，**等到它存到 Redis 里面，它都变成字符串了**。所有的本质都字符串。大家想一想 JSON，其实 JSON 也是这样子的，把它序列化过后，说白了全是字符串。获取年龄回来也是变成了一个小小的字符串——这说明，当我们把一个数据存到 Redis 的时候，其实它都变成了字符串。

这是一个基本的案例，我们就说完了。基本案例说完了以后，我们就来看细节。

## Redis 的 Hash、List 与 Set：字段可以批量取，列表两头都能塞，集合天生去重
> 对应块：BLK116 | 覆盖分集：P306-P310 | 块标题（分集名）：《304_尚硅谷_Redis中Hash的使用细节》

来看下一个。既然有了这些，那么哈希在使用的时候要注意哪些问题呢？来看一个。

### Hash：一个一个设太低端，索性一次设完

刚才我们讲了一个 `hset`，还有一个 `hget`。那有一个问题：老师，我有这么一个需求，你在获取的时候能不能不要一个一个获取，把它全部给我获取回来？**可以**，那么这个时候这个指令叫 `hgetall`。

还有一个指令我们演示一下。`hgetall` 就刚好用刚才这个演示——现在我要把 `hgetall` 写进去：`user1`。这一回车，把它的三个字段值取出来了：名字是史密斯，年龄是 30，工作是 Golang。

> **结论**：**它是按照你存放的顺序给你取出来的**，每次取都应该是稳定的，没有乱，都很稳定。

然后还有一个 `hdel`，这个猜一猜都是干什么？删除它。就是如果你不想要这一个哈希对应的这个值，你可以 `hdel` 把那个名字写进去，就 OK 了。

#### 一次性设置和获取：`hmset` 与 `hmget`

这是它的一个使用细节。**在给 user 设置名字和年龄的时候，前面我们是一步一步设置的，你也可以一次性地设置**——刚才那样设置太低端了是吧？`user1` 名字、`user1` 年龄、`user1` job，太低端了。你也可以一次性搞定，用我们的这个指令叫 `hmset` 和 `hmget`。

比如我要创建一个新的用户了：

```bash
hmset user2 name Jerry age 110 job "Java coder"
```

这个是代表一个哈希的一个变量，然后这个哈希里面有多少个 field value 呢？第一个是人的名字 Jerry；第二个是年龄，假设这个人是 110 岁；还有一个是工作岗位，假设是 Java coder。

> **易错点**：**注意这个地方，如果你中间有空格，那就必须得用引号引起来。因为你有空格的话，你不写肯定语法要报错的。** 如果你没有空格，你可以不要双引号。

回车，成功。这个时候就相当于把前面三句话搞成了一句话。获取的时候，你可以一次性获取，叫 `hmget user2`。你要获取 user2 的哪些字段要写清楚：

```bash
hmget user2 name age job
```

回车，全部取来了。看这里很清楚，它告诉你名字是 Jerry，年龄是 110，然后工作岗位是 Java coder。

这里还有一个很真实的**翻车现场**：我第一次敲的时候不小心多打了一个空格，结果取出来就带上了那个空格。这个细节就说到这里了——重新设置一下，清掉多余空格，就没问题了。

#### 统计字段个数与判断字段存在

我们也可以统计一个哈希它对应有多少个这样的 field 字段，用什么指令呢？用 `hlen`。比如说我看 user2 里面有多少个，一回车，有三个字段和值。

最后一个，还可以判断哈希里面有没有这样的一个字段。比如我想判断 user2 里面有没有一个字段叫 name 呢？`hexists user2 name` 一回车，它说有；如果我写个 `hexists user2 2`，它说没有，为 0。

把上面这些用法整理一下就是：

| 场景 | 指令 |
| :--- | :--- |
| 一次性设置多个 field | `hmset key field1 v1 field2 v2 ...` |

> **提示**：最后注意听，**它返回来的应该是一个这样的集合。反映到我们 Golang 里面，待会儿我们用这个指令、通过 Golang 程序去数据库取的话，它返回的应该是一个切片或者是一个数组。**

### List：翻译过来就是"列表"，它是一根两头都没封口的管道

那么上次课我们讲到了 Redis 它操作几种数据类型，其中我们哈希还有字符串我们说了。那现在我们来再看一下这个 list，list 是什么东西？

它翻译成中文就叫**列表**的意思。那列表它是简单的字符串的列表，**它有个特点，是按照插入的顺序排序**。你可以怎么想呢？**你可以添加一个元素到这个列表的头部，也可以添加到它的尾部。它好像是一个管道一样**，你可以在它的前面加数据，也可以在它的后面加数据。

**所以说这里有一个什么说法呢？就是 list 的本质它是一个链表。** 那这个链表我们还没学，但是后边很快就要学这个链表了。

那么 list 的元素有几个特点：**第一个，它是有序的**，就是它是有顺序的，它是跟你这个顺序是有关系的；**第二个，元素的值是可以重复的**。注意，前面我们讲的那个哈希，它有个特点，**它的元素是不可以重复的，它的 key 不能重复**。

#### 快速入门：为什么取出来是反的

比如说我们存放多个城市，`key` 就是 city，它的值就是后面的这些城市的名称。我们启动 Redis，把 server 起起来，然后启动 client。

```bash
lpush city beijing shanghai tianjin
```

这个是一个 key，后面是它的值。一个 list 对应的值可以有多个元素。那怎么取呢？

```bash
lrange city 0 -1
```

我待会儿解释一下：`start` 代表你从哪一个位置开始取元素，它的元素对应的下标从 0 开始，所以说我从 0 开始取；取到第几个呢？假设你想全部取完，各位同学你就写个 `-1`。**`-1` 代表我要把它全部取完，相当于取到倒数第一个的意思**；如果你要取到倒数第二个就是 `-2`，以此类推。

一回车，你会看到三个元素都取来了。**那取回来的时候你们就注意一个顺序**——顺序是什么呢？

**你可以把我们的这个 list 想象成一根管道，你把它想成一个管道，两头都没有封尾。** 那封起来变成数组了。那么这个没有封的话，你看这个 `lpush` 代表从这个管道的左边往里面扔。那左边往里面扔，它第一个扔的是 beijing，相当于北京，我写个 B。扔了第一个过后，它又扔了一个 shanghai——上海仍然往里面扔，往里面扔的时候，相当于把这个 B 往后面挪了一下。那我形象地说，它里面这个链表实际上不是说往后挪了，而是在这个 B 的前面插入了一个东西，不是往后面挪，因为链表它没有往后面挪，它是往前面插了一个，相当于插在这个 B 的前面，那这个时候就变成这个上海在前面了。

上海在前面过后，再上一个天津，天津又在它的左边往里面添加，所以说天津在最左边，上海在中间，B 在最后边。那这样子我取的时候，`lrange` 相当于是从左边开始取，因此它的顺序是天津、上海、北京，**跟我们存放的顺序刚好反过来**。

回车，我们可以看到果然如此。这些都有用处的，同学们，因为你将来在做这个开发的时候，肯定会有这种特性。

#### list 的数据结构分析

list 的一个基本语法是 `key start stop`，返回列表 key 中指定区间内的元素，区间以偏移量 start 和 stop 指定。**下标 index 参数都以 0 为底**，也就是说以 0 表示列表的第一个元素，以 1 代表第二个元素，以此类推。那你要取到哪个元素，你就写到哪里去。比如你想截取我们这个 list 里面的第一个到第二个，那就是 `0 1`，完事。

**那么你也可以使用负数下标**，`-1` 代表列表的最后一个，`-2` 代表列表的倒数第二个，以此类推。那比如说刚才老师用的 `0 -1`，就代表从第一个元素取到最后一个元素。

那这个 list 到底怎么理解呢？**它的本质是一个链表**，那如果说链表的话应该是这样子的：list 最先它只有一个，比如说你加了一个 A，在这。如果你往这个列表的左边开始加入，它会形成了一个指向，它们的指向永远是前面的指向它；如果再加一个 C，它又找到这个 list 最前面这个元素，在这前面再插入一个数据，插完了过后，他们之间又形成一个指向。

**如果你的数据是从这个右面、也就是从它的尾部添加的时候呢？** 它就找到这个 list 最后面，然后从这开始加入，比如说 D，然后他们之间由它又指向它。注意，它仍然是这样指向，不会反过来指向，那这个 D 就变成屁股后面了。如果你再加一个元素 E，它是找到队尾，插进去过后让他们这个链表继续形成一个指向。**所以说它永远是这样子的。**

```text
   从左边加入： lp          从右边加入： rp

        ┌───┐                    ┌───┐
        │ C │                    │ A │
        └─┬─┘                    └─┬─┘
          │                        │
        ┌─┴─┐                    ┌─┴─┐
        │ B │                    │ B │
        └─┬─┘                    └─┬─┘
          │                        │
        ┌─┴─┐                    ┌─┴─┐
        │ A │                    │ C │
        └───┘                    └─┬─┘
                                   │
                                 ┌─┴─┐
                                 │ D │
                                 └─┬─┘
                                   │
                                 ┌─┴─┐
                                 │ E │
                                 └───┘

   取的时候默认从左边开始取
```

那后面我们在学数据结构的时候，还会形成我们自己写这样一个 list 的结构，这样就更好——比如说有些地方你发现一个 list 不能满足你的需求，你想自个自定义一个 list，也是可以的。

#### `rpush`、`lpop`、`rpop` 与 `delete`

我们举一个例子，比如说我放很多英雄人物的名称，借这个案例来讲一下它的 `lpush`、`rpush`、`lrange`、`lpop` 和 `rpop`，还有 delete。**在讲这几个指令的时候，大家脑海里面要有这样一个图**，只要有这个图的话，心里面就应该特别清楚了这样子你就可以把实际的应用给它结合起来。

```bash
lpush herolist aaa bbb ccc
```

同学们可以看到，现在你们在脑海里面想，在我们管道里面应该放了 aaa、bbb 和 ccc。**好，同学们，现在假设我这么取，我找一个同学说一下，我们会取出什么东西。** 比如说我现在用的是 `lrange herolist 0 -1`——**这个时候我取的时候，顺序应该是 aaa、bbb、ccc 还是 ccc、bbb、aaa？我们顺序应该是 ccc 先取出来，然后是 bbb，然后是 aaa。果然如此。**

现在接着我再来做一个案例，叫做 `rpush`。rpush 我仍然往这个 herolist 里面放东西，这个时候我放的是 `ddd`、`eee`。**同学们，现在 ddd 和 eee 其实它们所在的位置应该是从右面往里面添加的**，因此如果我现在再 `lrange herolist 0 -1` 的话，取出来顺序应该是 ccc、bbb、aaa，然后是 ddd 和 eee。因为你现在是从右面往里面插入的，因此它的顺序和前面老师讲的这个是一个道理。

接下来我们看下一个指令，叫 `lpop`，还有 `rpop`。**什么叫 lpop 呢？lpop 代表是从我们这个链表的左边弹出去一个数据，相当于说取出一个数据。取的时候跟 lrange 不一样的地方是：lrange 在取的时候，它并不会把你的数据从这个链表里面剔掉，不会剔掉，也就是说它只是取，并不拿走。但是这个指令不一样，lpop 是从我们链表的最左边取出并移走，它把它取出来然后拿走了，就给你弹走了。**

`lpop herolist`，我一弹，弹出来一个 **ccc**，果然弹出 ccc。弹出来过后我们再遍历一下：

```bash
lrange herolist 0 -1
```

我们的队列里边其实只留下了四个数据，它的顺序仍然是按照这个顺序来的，应该是 bbb、aaa、ddd、eee。回车，果然如此。

那么我再来做一个案例叫 `rpop`。**rpop 我就不多说了**，同学们应该是非常清晰地明白了，它应该是从右面弹出一个数据。走，弹出 **eee**。弹出 eee 过后，我们现在数据只留下了三个，就是 bbb、aaa、ddd。看一下 `lrange`，果然是如此。

再来看一个指令叫 `delete`。如果你不想要这个链表了——"老师，我这个东西我不想了，这个链表我想彻底地把它干掉"——那你直接把它的 key 干掉就行了。**因为实际上你这个链表它的指向是由一个 key 值指向的**，比如说刚才我们写的是 herolist，你直接把它拿掉，delete 掉就可以了。

```bash
delete herolist
```

当我这样一删掉过后，再去遍历这个 herolist 的时候就已然没有东西了。它直接告诉你 `empty list or set`——就是说**你这个可能是一个 list，可能也是一个 set，set 也是这样遍历的**。从这个指令可以看出来，它俩指令很像。

> **提示**：**这个很有用，不要小看这种东西。** 比如说将来让你们去在网站里面做一个浏览顺序，我始终把你一个用户他最近浏览的商品、最近浏览的前十个商品给我显示出来——你想如果我们有这种结构的话，非常轻松。**如果你没这个结构很麻烦的**，你还得按时间排序，还得动数据库。好，这个就可以了。

### List 的使用细节和注意事项

在 List 的使用的时候，有几个地方需要同学们知道。

**第一个，关于 index 这个说法。** 大家看这里有个 `LINDEX`，按照索引下标获取，就是按照索引下标获取元素，可以通过这个方式来做这个工作。而且大家知道，**它是从左边开始编号，从左到右，编号是从 0 开始**，这个很好理解。

**然后还有一个 `LLEN`。** 前面这个 L 代表就是 List 的意思，那么 `LLEN` 就代表返回当前这一个 List 的长度，到时你有可能需要。**如果这个 key 不存在，则 key 被解释为一个空列表，返回一个 0。**

我们做一个小小演示：`LLEN hero_list`，它应该返回一个 0。当然如果你里面曾经加过东西的话，是多少就是多少。比如我们 `lpush hero_list aa bb cc dd`，就这么四个数据，我再用 `LLEN` 去看，返回 **4**，很赞吧。

**List 的其他说明**：List 的数据可以从左或从右插入，跟我们刚才讲的一样，可以从左边插，也可以从右边插，看你的需求。

**然后有一点，如果我们把所有的值全部移除，把这个全部删掉的话，对应的这个键也就相对没有了。** 比如说你不停地 pop，当你把所有的数据全部都 pop 出去了，那你这个 List 也就自动消失了，这个我就不演示了。

### Set：无序，而且不能重复

下面我们来看另外一个数据类型，叫集合。**集合翻译成英文它是 Set。那么 Redis 的 Set 也是字符串类型的集合，而且默认是无序的，底层它的结构是 hash table 的一种数据结构。**

Set 也可以存放很多的字符串元素，但是有几个特点：**第一个，元素首先是没有顺序的**，跟前面刚好不一样；**第二个，元素的值是不可以重复的**。

> **易错点**：**就比如你放了一个 aaa，你再放一个 bbb 的话就报错了。** 所以说它有两个特点，第一个是无序，第二个是不能重复。

什么情况下可能用到这个东西，大家想一想？比如我们要存放一些人名，**但是我们要求人的名字不能重复，你就可以用 Set**。再举个例子，比方说我要存放多个电子邮件，**但是我们认为电子邮件是不可以重复的**——显然理论上说在我们现实的生活中电子邮件都不应该有重复的，哪两个相同的电子邮件，那肯定邮件就发不过去了。**所以说用 Set 来存放特别的合适。** 比如说这个时候 key 就是 emails，值就是里面的电子邮件的地址。

#### `sadd` 与 `smembers`

```bash
sadd emails tom@sohu.com jacky@qq.com
sadd emails kkk@uu.com yyy@sohu.com
smembers emails
```

**那同学看到现在我们添加的顺序是 tom 在前、jacky 在后，但是我们在取的时候会不会也是这样子的呢？** 我们来看看。取的时候可以用 `smembers` 就全部取出来了，第一次取出来 tom、jacky 都有，好像是有顺序是吧？**我们再重新多加几个吧**，在这基础上多加几个，看有没有效果。

**你看这个顺序，明显就感觉没有顺序了。** 你看 kkk 明明是在后面加入的，它跑到前面去了；而 yyy 呢，它就是在最后加的，它还在后面。**所以这个是没有顺序的，它是无序的。**

再看它的一个特点，它是不可重复的。比如 `sadd emails tom@sohu.com`，原先已经有一个 `tom@sohu.com` 了，你再一回车就发现 **0**。**0 代表什么呢？就是我没有加进去，0 代表没有加进去。**

#### `sismember` 与 `srem`

**`sismember`，** 听这个名字就知道了，它是判断里面有一个值是不是存在，这个很有用。你比如说将来我们想去看，你存放的电子邮件里面有没有这个电子邮件呢？可以用 `sismember`。

```bash
sismember emails tom@sohu.com    → 1
sismember emails tom~sohu.com    → 0
```

**如果有的话会返回一个 1；如果没有，返回 0，非常简单。这是一个查是不是成员元素。**

**还有一个，删除指定的值。** 比如里面有一个元素你不想掉了——比如有个电子邮件，你发现这个电子邮件这个人已经走了，你也可以把它删除掉。怎么删除呢？非常简单，`srem`。**remove 嘛，rem 就是单词 remove 的意思，简写的。**

```bash
srem emails tom@sohu.com    → 删除成功返回 1，删除不成功返回 0
smembers emails             → tom 已经被干掉了
```

**那么这个其实就是增加、删除，修改就是继续用这个 add。** 把这些指令归拢一下：

| 场景 | 指令 |
| :--- | :--- |
| 往集合里添加元素 | `sadd key element [element ...]` |
| 取出集合中所有元素 | `smembers key` |
| 判断某元素是不是成员 | `sismember key element` |
| 删除指定的值 | `srem key element` |

### Set 和 Get：Do 就是你敲过的那些指令

写入数据的时候，我们先写一个字符串的，叫 key-value 的一种结构。

conn 本身是个连接，它提供了一个方法，刚才老师已经带大家看过了，是 `Do`。这个 `Do` 里面是什么参数？第一个是命令行，第一个参数是命令，就你要干啥；第二个是后面一堆可变参数，想写多少写多少；最后返回的是一个任意类型。

所以说我们现在就比较清楚了，写入刚才我们用的指令是 `Set`。这个地方大小写无所谓，一般人喜欢写首字母大写 `Set`。

```go
_, err = conn.Do("Set", "name", "tomjerry")
if err != nil {
	fmt.Println("Do Set err=", err)
	return
}
fmt.Println("操作成功")
```

这个时候它会返回什么信息呢？它会返回两个信息：一个是结果，第二个是 err。注意，添加进去，往里面添加一般这个结果我们忽略，我们要的是返回错误，所以一般这样写。

我做一个判断：如果 `err != nil`，不等于 nil 表示什么意思？就是说你错了，就说 `Do Set` 出错，错误原因打印出来，退出。

我们来玩一把，看看有没有成功。它说操作成功。如果操作成功，同学们应该想象得到，在我们 Redis 里面应该有个 `name`。我查一下，`get name`，是不是 `tomjerry`？好，我们看到有 tomjerry，说明我们加进去了。这个很简单。

紧接着第三步，怎么获取？既然能往里面加，那一定要从里面取。这个不就是一个反向操作吗？直接拷贝一份就完了，太 easy 了，只是把这个指令改成 `Get`：

```go
r, err := conn.Do("Get", "name")
if err != nil {
	fmt.Println("Do Get err=", err)
	return
}
fmt.Printf("name = %v\n", r)
```

### 返回的是 interface{}，所以要转类型

这个 `r` 同学们注意，这个 `r` 你要把它转成字符串，因为它是接口类型。所以说你这样直接输出是有问题的。

因为返回的 `r` 是什么类型呢？是 `interface{}`，它其实是一个**空接口**。所以说你为了看到这个信息，应该根据你的实际情况把它转成对应的类型。名字是字符串，所以我就这样转。

那怎么转呢？可能同学这样说的，我这样给你转：

```go
name := r.(string)
```

这个用**类型断言**是吧？它是接口，我们转是不是要类型断言？是小写的 `string`。

> **易错点**：我故意把这个值改成中文「汤姆猫猫」，看情况，中文能不能放进去？这个很关键。走——我们发现**报错了**，它说有一个接口转换出错。

这个时候同学们注意，我们不要这么去转。怎么转比较好呢？其实完全没有必要这么写，它给我们提供了一个方法——redis 提供了大量自带的方法。大家看这里，redis 库里面它有很多自身的一些方法，比如在前面应该有 **`redis.String`**，它直接有 String 方法，大写的 S：

```go
r, err := redis.String(conn.Do("Get", "name"))
```

它这个里面它帮你转了，这样是最好的方式。也就是说，这样子我一步到位，你返回的结果我直接给你转成 String。这是它提供的一个内置方法，这个方法就最好用了，然后这个结果自然就是一个 `string`。写完了，再看代码，这个就不会报错了。

同学们可以看到，完全没问题，汤姆猫猫这个时候你在终端去获取这个名字，它仍然是乱码。这个你不用担心，因为我们说白了，你在控制台看什么码无所谓，我们主要是看程序里面，对不对？

> **结论**：从这个地方我们可以看出来，操作非常简单，就是把刚才咱们的指令放进这个 `Do` 里面去，然后把这个结果拿回来过后，转成对应的类型——**如果是字符串就转字符串，如果是 int 你就写 Int，如果是 float 就是 Float**。有同学说，假设我返回的是多个类型怎么办呢？加个 s，`Strings`，这个返回多个字符串。

最后不要忘了一件事情：`defer conn.Close()`。

### 操作哈希：一个 field 一个 field 地读写

我们接着看刚才写的代码，我们来看一下怎么去操作多个，操作哈希。

通过 Go 对 Redis 操作哈希数据类型，其实只要做一点点变化，哪一点变化呢？**你只需要把这个 `Do` 指令把刚才的 `Set` 改成 `HSet`**，然后按照哈希的数据组织形式往里面扔。

```go
_, err = conn.Do("HSet", "user01", "name", "john")
_, err = conn.Do("HSet", "user01", "age", 18)
```

写完了过后注意听，这个时候你在获取的时候，还不行，因为这个 `HSet` 是单个单个给的，所以说这边只能一个一个给。比如先把 `user01` 名字给了，再给年龄，这是可以的。大家应该还记得，`HSet` 前面讲的是给 `user01` 一个字段一个字段地赋值。如果有多字段给的话，要用 `HMSet`，待会儿我们再举例。

取出来也是一样的道理：

```go
r1, err := conn.Do("HGet", "user01", "name")
r2, err := conn.Do("HGet", "user01", "age")
```

> **提示**：这里必须有同学会提醒——**你必须告诉我取哪个哈希里面的 name，取哪个哈希里面的 age**。刚才同学们提醒得很好。

这个时候取完了以后，我把这两个打印出来，稍微地改一下。两个都叫 `r1` 可能很麻烦，就叫 `r1` 和 `r2`，区分一下。因为 `r2` 我们明明知道它是 `int`，我就转成 `int`：

```go
name := r1.(string)
age := r2.(int)
fmt.Printf("name = %v, age = %v\n", name, age)
```

跑一下，我们提取到 john 和 18。当然如果说同学们在这一边看，用客户端 `hgetall user01`，应该也能看到。

有些同学说：「老师，假设我也想一次性取出来可不可以？」你仍然可以用这个指令 **`HGetAll`**，然后把这个 `user01` 写出来，它会返回一个你可以把它转成一个集合，把这个东西取出来。但是麻烦就在这个地方，**你得一个个再转一次**。

### 批量操作：MSet/MGet 与 HMSet/HMGet

这是一个一个放，太慢了。我们还有一个案例，什么呢？我们来批量的 `Set` 和 `Get`——比如我们通过 Go 对 Redis 操作，一次操作可以 `Set`、`Get` 多个 key-value。

我这儿举个例子，比如说 **`MSet`**，注意，我这个地方用的不是操作哈希了，我相当于给里面放的是多个 key-value，这个也可以。那有些同学说我想用哈希的呢？一样的，道理一样。

如果在操作哈希的时候我一次性加进去，就是这么改进：

```go
_, err = conn.Do("HMSet", "user02", "name", "john", "age", 19)
```

取数据我也想一次性把它取出来，叫 **`HMGet`**。这个时候我取的是 `user02`，这时你要写上你要取它的哪些信息——名字你还要取，还要取它的年龄。

这个时候它取回是多个值，所以这里面转的话，应该转成一个切片或者数组：

```go
r, err := redis.Strings(conn.Do("HMGet", "user02", "name", "age"))
if err != nil {
	fmt.Println("HMGet err=", err)
	return
}
fmt.Printf("r = %v\n", r)
```

### 为什么要连接池：每次 Dial 再 Close，其实挺浪费

介绍完过后，我们还有一个知识点要给大家讲一下，就是关于 **Redis 连接池**的问题。

**听其名而知其意，连接池。** 首先我还是要先跟大伙聊一聊为什么需要连接池的问题——为什么他们要用连接池，不用连接池难道就不行吗？

目前我们去操作 Redis 是这么干的，同学们写代码也都是这么玩的：`redis.Dial`，然后拨一个号，拿到这个连接；用完了过后，我们再把它关闭了。**其实在这种情况下，它的效率有时候是比较低的。**

为什么这么讲？我给同学们画一个示意图。

```text
   传统方式：每次都重新来一遍

   Go 程序 ──Dial──▶ Redis   （Redis 临时创建一条连接，耗费资源）
        │
        └──Close──▶            （用完就扔，下一次再重新建）

   客户端一多，每次都要重新建，重复劳动


   连接池：事先把连接建好放着

        ┌─────────────────────────────┐
        │         连接池 pool         │
        │  ┌───┐  ┌───┐  ┌───┐  ┌───┐│
        │  │ 1 │  │ 2 │  │ 3 │  │ 4 ││   连接提前建好，不关闭
        │  └─┬─┘  └─┬─┘  └─┬─┘  └─┬─┘│
        └──┼────────┼────────┼────────┼──┘
           │        │        │        │
   Go 程序─Get─┘  ─Get─┘   ─Get─┘   ─Get─┘      取一个用一下
      归还 ◀────归还 ◀────归还 ◀────归还       用完放回池中
```

**你想，你客户端来连我，我是临时给你创建连接再返回给你，这个是比较耗费资源的。** 这个连接之间，我跟你的连接之间要去作这个事情还是很累。

那么现在有一个方法叫连接池的这么一个概念。**我上来过后先给你分配一些你可以用的连接**——打个比方，我先不这么干了，我有一个连接池，相当于这个连接池子里面已经有很多连接了，我不关闭。至于到底创建多少个连接，由你来决定，由程序员来决定，**根据你项目的大小、根据你规模的大小来决定创建多少个连接。**

连接池创建好了以后，当我们要去操作这个连接的时候非常简单，**我直接从这个池子里面取一个连接出来，取一根**。

我先 Get 一个连接，因为这个连接它已经跟你的数据库已经连好了。**相当于什么感觉呢？就像我们打电话，我们打电话过了后我们不挂掉，我们一直保持这个连接，不占线，别人想用也用不了，连号都不用拨了。** 这个时候我要用的时候，我直接从这个连接池取一个连接出来；如果说另外又来一个程序说我也想用，那我又从这个连接池给他取一个。

**用完了过后你也别关了**，你用完了过后把这个连接不用了，它又回到这个连接池，它仍然跟我们数据库保持这个连接。所以这种效率就会大大提升。

> **结论**：**事先初始化一定数量的连接放入到连接池；当 Go 需要操作 Redis 时，直接从连接池中取出连接即可。这样可以节省临时获取 Redis 连接的时间，从而提高我们的效率。** 就相当于我程序跟你数据库之间这个连接我事先已经搭好了，我要用直接从池里面取一个，用完了过后再回放到这个连接池就行了。
>
> **但是这个连接池谁来维护呢？由 Golang 它的连接池技术来维护。**

### 连接池的关键参数

核心代码其实就这么一点东西。它如果要用连接池的话，必须满足两点：

- **第一，你在程序运行之前，一定先要初始化我们这个 pool**，也就是连接池。**我们可以把初始化的工作放在 `init` 里面去做。**
- **第二，初始化过后我们再去使用。使用的关键是怎么从连接池得到一个连接**——它里面有一个非常重要的方法叫做 `pool.Get()`。拿完这个连接，你用完了过后它自己可以去回收。当然你用完了过后最好可以把它关闭一下，**关闭过后它就回收到 pool 里面去了。**

我们简单看这几个参数。

#### 最大空闲数、最大连接数与最大空闲时间

| 参数 | 含义 |
| :--- | :--- |
| `MaxIdle` | 最大空闲连接数 |
| `MaxActive` | 和数据库的最大连接数，0 表示没有限制 |
| `IdleTimeout` | 最大空闲时间 |
| `Dial` | 初始化连接的代码，指定连接哪个 IP 的哪个 Redis |
| `Get()` | 从连接池中取出一个连接 |
| `Close()` | 关闭连接池 |

`MaxIdle` 代表最大空闲连接数。简单解释一下：假设你这个 Go 程序一直没有人去用这个连接池，这个连接池里面我最多放 8 个。当然你也可以调，我说我最大空闲 8 个。

`MaxActive` 代表和数据库的最大连接数。**最大连接数和最大空闲数不一样**，就是说你通过连接池我最多可以跟数据库发多少个连接，因为还有并发的问题。0 表示不限制，没有限制，理论上我不限制你。

> **提示**：**但是写的是 0 不限制，实际上系统还是有限制的。** 说"老师我设个 0 是不是我的连接数就是无穷大了？"——它只是说我连接池的技术核心我不去限制你，但是你自己能不能达到这个并发，跟操作系统还有很大的关系。**你自己才设了 8，那你这个 0 有什么用呢？相当于说我这设了 8，那最大连接数也就 8 个了。就是我不限制你而已。**

`IdleTimeout` 是最大空闲时间。什么意思呢？假设有一个连接，在连接池里面有一个连接在 100 秒之内没有人用了——比如上次用了一下这个连接，用完了过后你放回去，在 100 秒以内再也没有用过这个连接，它就达到最大空闲了。

**它会自动增长，有时候它有自动生长这个机制，达到一个峰值的时候它会自动增长。在最大空闲 100 秒过后，它就自动又放到空闲连接数里面去了。**

至于 `Dial`，就是代表初始化连接池的代码。大家看这里面它指定什么呢？**它指定我要去连接哪一个 IP 的哪一个 Redis**，这里要写清楚。这个 `localhost` 代表本地，如果你的 Redis 放在某一个 IP 的，你就写清楚；这边是它的端口号，是哪个端口，这样子它就给你初始化了。

**最后这个 `Close` 函数代表关闭连接池。大家注意：一旦关闭连接池过后，就不能再从连接池里面取连接了。**

#### 不放心？直接看源码

说老师这个地方你说的含义我还是觉得不太清楚，有没有相关的文档能够把它解释得更清楚更明白呢？可以的，我给大家看一个源码。

我们打开 Redis 的插件，找到 `src/github.com/garyburd/redigo/redis`，打开 `pool.go`——因为它是连接池嘛。打开它过后，你们可以看到一个熟悉的东西：**这里有个 `Pool`，原来 Pool 是个结构体。** 它是一个结构体，也就是说我们待会儿返回的这个 `redis.Pool` 它本质是个结构体，所以我这样用的，我返回的是它的一个**指针**。

在这个结构体里面有什么东西呢？首先它有这样一个方法叫 `Dial`，然后往下看里面的这些参数：

- `MaxIdle`：在这个连接池最大的空闲连接数；
- `MaxActive`：最大的连接数，分配给这个连接池的在给定时间里面最大连接数。**如果等于 0 是什么意思呢？`There is no limit on the number of connections in the pool`——在这个连接池里面我就不限制它的数量了。** 默认是这样子的，但是它有一个最大连接数的问题；
- `IdleTimeout`：超时，你看它用的时间是 `time` 包里面的 `Duration`；
- 还有 `Wait`，还有 `MaxConnLifetime` 等等很多。这些大家自己看一下就行了。

其实一个标准的配置大体是这样子的，我这儿有一个标准配置大家可以参考，大家用得比较多的。**8**，这个可以调大一点，如果说你的项目比较大，你可以把它调大一点；然后空闲时间，比如你觉得你想空闲时间大一点，你可以调大一点。**如果你发现你的性能不够了，你把这个数据量适当调大一点就可以了。**

### 用代码把连接池跑起来

还是我们的 chapter18，然后我们写一个文件夹叫做 `redispool`，写一个 `main.go`：

```go
package main

import (
	"fmt"

	"github.com/garyburd/redigo/redis"
)

// 第一步：定义一个全局的 pool，任何一个地方都可以使用到
var pool *redis.Pool

// 当启动程序时，就初始化连接池（init 在 main 之前执行）
func init() {
	pool = &redis.Pool{
		MaxIdle:     8,   // 最大空闲连接数
		MaxActive:   0,   // 表示和数据库的最大连接数，0 表示没有限制
		IdleTimeout: 100, // 最大空闲时间
		Dial: func() (redis.Conn, error) { // 初始化连接，连接哪个 ip 的 redis
			return redis.Dial("tcp", "localhost:6379")
		},
	}
}

func main() {
	// 第二步：从 pool 里取出一个连接
	conn := pool.Get()
	defer conn.Close()

	// 往 Redis 里放一个东西
	_, err := conn.Do("Set", "name", "汤姆猫")
	if err != nil {
		fmt.Println("conn.Do err=", err)
		return
	}

	// 再取出来
	r, err := redis.String(conn.Do("Get", "name"))
	if err != nil {
		fmt.Println("conn.Do err=", err)
		return
	}
	fmt.Println("r=", r)
}
```

几个地方要拆开看：

**为什么 `pool` 要定义成 `*redis.Pool` 指针？** 因为它的 `Get` 方法是跟指针类型关联的。**你不是指针类型你也搞不定，因为它的 Get 方法是跟这个指针绑定的。** `Get` 了过后它返回的是一个 `Conn`，这一点大家可以看一下手册。

**`defer conn.Close()` 这个动作还是要有的。** 这个延时关闭的动作还是要有的，不然的话到时候你用完了过后这个连接池不关闭的话，它回不回去——**回不去那你越用越少**，因为持有它不放，它认为你还在用，它不会把它重新放到空闲的地方去，那别人就用不了了。**比如说你又没有用，你还持有这个连接，那这个连接池就没有意义了。大家注意这个细节，一定要用完要把它关闭，让它回放回去。**

`conn.Do` 放东西进去，它会返回一个结果我们不要，还有一个就是返回有没有 error，这个要接收一下。做一个判断：如果 error 不等于 nil，那么我们就说这个地方出错了，取出来就可以了；当然你取出可以 return，不走了，放不进去说明有问题。

取出和以前是一样的，仍然是 `Do`，`Get` 的时候我就取这个 `name`。因为我们知道是字符串，我直接就不啰嗦了，用 `redis.String` 把它转一下就可以了。

我们执行一下这个代码：`go run main.go`，**可以成功，汤姆猫取出来了。**

### 一个必须注意的坑：连接池关掉之后，`Get` 不一定立刻报错

那么这里我要强调一个细节：**如果说你要从这个连接池取东西，一定要保证连接池是没有关闭的。** 如果执行下面这个代码就要出错——**如果我们要从 pool 里面取出连接，一定要保证连接池是没有关闭的。**

比如有些同学不小心写了这么一个动作：`pool.Close()`。**一旦你做了这个动作，那么连接池就关闭了，你再去获取东西就获取不到了。**

那有意思的地方来了——**我们去跑一下，它居然没有立刻报错**。我关闭了以后又获取到一个 `conn2`，我打印出来给你们看一下。它这边可能分配了一个地址，**但是那个地址实际上是指向了一个无效的地方——因为它是引用嘛，它可能指向一个无效的地方。**

于是我接着用这个 `conn2` 去 `Set` 一个 `name2`、汤姆猫2，然后再用这个 `conn2` 去 Get 刚才的数据，最后打印出这个结果。

跑一跑。**大家看果然出错了，是有问题的：**

```text
redigo: "get on closed pool"
```

Redigo 他说 "get on closed pool"，拿不出来了已经，因为你关闭了。

**那到底是哪个地方报错呢？应该是在这个位置，是 `conn.Do` 的时候。** 因为你在用的时候，他发现其实你取的东西根本就没取到。**我怀疑这个地方它只是指向了一个引用而已，指向连接池的一个引用；相当于说这个连接先指到连接池去，然后 Do 的时候才正式去取**，应该是这样一种操作。所以说他这块肯定给你报错，就是这儿错的。

> **易错点**：**也就是说，`pool.Close()` 之后调 `pool.Get()` 并不会立刻炸，`conn` 甚至可能看起来是正常的——真正的错误要等到你拿它去 `Do` 的时候才爆出来。** 大家调试的时候很容易被这个"半死不活"的连接给绕进去。**所以在这里面，我们这个连接池一定不要关闭，关闭肯定就没法玩了。**

### 第一个功能：客户端的登录菜单

我们已经讲了项目的开发流程，也讲了它的需求分析，而且我们也做了一个小小的界面，那是个登录界面。现在 Redis 咱们也说完了。下面我们接着来做它的功能，一步一步完成。

第一个功能：**显示客户端的一个登录菜单**。因为这里面它有两级菜单——首先它登录成功过后，我们会让它再看到第二层菜单。

界面长这个样子，第一级界面：可以登录聊天系统，可以注册用户，可以退出系统。当这个用户登录聊天系统成功以后，我们让它看到的是另一个界面。

> **注意**：这边挺复杂的，因为我要作一个**消息的协议**。这个消息协议怎么定，这是个关键点，而且涉及到**读包和写包**的一个流程。

思路很简单，这个谈不上什么分析，直接写就行了。打开 VS Code，新建一个文件夹叫 `chatroom`，聊天室。里面先建一个子文件夹，代表我们的客户端 `client`；当然了，我们后面应该还有一个服务端 `server`。客户端这块先来一个 `main.go`，然后再写一个 `login.go`。

> **提示**：今天班上**至少有一半同学要听懵圈**。因为我们写的聊天系统不是站在实现这个功能的角度，而是站在**代码怎么设计更合理**的角度。所以代码稍微不注意，肯定就听懵了。现在先来点简单的，有一个简单的过渡。

#### main.go

```go
package main

import "fmt"

var (
	userId  int
	userPwd string
)

func main() {
	var key int
	loop := true
	for loop {
		fmt.Println("--------- 欢迎登录多人聊天系统 ---------")
		fmt.Println("1.登录聊天室")
		fmt.Println("2.注册用户")
		fmt.Println("3.退出系统")
		fmt.Println("请选择 1 到 3")
		fmt.Scanf("%d\n", &key)
		switch key {
		case 1:
			fmt.Println("登录聊天室")
			fmt.Println("请输入用户的 ID 号")
			fmt.Scanf("%d\n", &userId)
			fmt.Println("请输入用户的密码")
			fmt.Scanf("%s\n", &userPwd)
			err := login(userId, userPwd)
			if err != nil {
				fmt.Println("登录失败")
			} else {
				fmt.Println("登录成功")
			}
			loop = false
		case 2:
			fmt.Println("注册用户")
		case 3:
			fmt.Println("退出系统")
			loop = false
		default:
			fmt.Println("你的输入有误，请重新输入")
		}
	}
}
```

老规矩，我们定义两个变量：一个变量是接收他的输入，就是他选择哪一个——`var key int`；第二个就是判断是否还继续显示菜单——`loop`，默认我们就让它一直显示，`true`。

> **易错点**：这地方用 `fmt.Println` 打印菜单没问题，但接收输入这里 `fmt.Scanf("%d
", &key)`——**注意 `

我为什么用整数没用字符串，本身就是有道理的。如果我用字符串，它本身一回车全部一下就打下去了，这也是个坑——但是你们就看不到这个坑了。

我们这个 ID 就只能用数字。刚才说 QQ 号，你登录的时候 QQ 其实我们只有数字，QQ 号里面一般不含字符串——比如你的 QQ 号是 12345，没有 abc12345。包括银行卡一般也就是纯的数字，那么我们也用数字就行了。

而且既然这个 ID 将来肯定要用到别的函数里面去，所以说我先暂时在这定义两个全局变量，后面再说怎么去处理：



他说你这个地方 `login` 调用错了，也就是说他告诉我这个地方 `login` 没有定义。这个坑的解决方案我们以前讲过。原因是两个文件都在主包，主包要完成编译的话，应该退到它的 `src` 去，到这个 `src` 去调用：

跑起来。欢迎登录多人聊天系统，没问题。比如说我输一个乱七八糟的 5，它说你输入有误，你给我输对；你不输对，那我就不让你走。输一个 3 看一下有没有退出——退出系统了。

有人说：「老师，那我换成 `Scanln` 呢？」一样的下场。下面如果不是 `Scanln` 也一样倒霉。

### 拆出 login.go，以及一个必须记住的命名习惯

既然要登录，肯定不能把所有的代码都统统写在这一个 `main` 文件里面，这是不现实的。所以你现在一个最直观、最原始、最朴素的想法，就是可能会把登录写在另外一个文件里面去。

但是其实这样也不够，因为这样还是没有程序的结构。这个程序结构我们会一步一步把它推导出来。现在出于一个最朴素的想法，你会把登录写在另外一个文件——作为一个初学者肯定这样写的，我也这样去想。

```go
package main

import (
	"fmt"
)

func login(userId int, userPwd string) (err error) {
	// 下一步就要开始定协议
	fmt.Printf("userId=%d userPwd=%s\n", userId, userPwd)
	return nil
}
```

既然是登录，那我肯定要知道你的用户名和你的密码，于是乎我这个函数肯定至少要接收两个参数：第一个是用户 ID，int 类型的；第二个是用户密码，string 类型的。

> **结论**：注意咱们命名这个参数的名称，我的建议是——**你在借用名字的时候最好跟你这边保持一致**，这样你免去命名的一个痛苦。

给我们的变量命名、给函数命名、给参数命名其实是件特别头疼的事情。你后面就知道了，甚至有时候你都不知道怎么命名。我们今天可能就会面临这个困难，因为我们的**消息种类很多**了：我们会有登录消息，还有一个返回响应的消息，还有一个发送消息，那边还有一个上线消息，还有一个群发消息，还有一个点对点——你名字都不知道怎么取，很麻烦。所以我给大家一个小小的建议：**那边叫什么，这边就叫什么，就完了。**

最后你有没有登录成功呢？这边应该给它返回一个结果——比如一个信息，我们就以 **error** 的形式返回。

> **结论**：尽量以这种 error 的形式返回，**不要用真假**。因为真假描述的能力太弱了。比如登录，我有可能要知道你登录失败的原因是因为这个用户名不存在的，还是因为你的密码不对，还是因为服务器那边遇到了故障的错误。如果你只是一个真和假，这个描述能力很弱，它就是两个：1、2。
>
> 但是 error 就不一样了，error 它可以返回各种错误。比如你自定义，你甚至就像前面我们讲的定义一个常量，我一判断错误信息是这个，还有描述信息。

因为你成功了大不了是个 `nil` 嘛。你看我们为什么动不动就是 `if err != nil` 怎么样，等于 `nil` 怎么样——它就这个道理。

因为我现在没有去判断有没有对，所以直接返回一个 `nil`，就表示暂时没有错。

**最好的方法就是写一步测一步。** 我今天写代码压力也很大，因为稍一不注意一旦调错调不出来，我自己也想不出来——就算做了好多年开发，他到这来压力也很大。因为它这个东西比较复杂了，你后面就知道了。出错了调起来很麻烦，因为是有网络在里面，还有协议很多。

第一个功能我们就做完了。client 下边我们写了两个文件，一个是 `main.go`，一个是 `login.go`。

### 登录没你想的那么简单

我们把刚才的第一个界面做出来了。当然这个对我们来说还是比较 easy 的。第二个功能一下难度就上去了，有些同学可能一下就会听懵圈，因为这里面有好多东西以前大家没有怎么接触过。还是老规矩，我先说一下我要做什么，然后我再给大家分析我的思路，然后再代码实现。

这次我们完成的是：**实现用户登录**。

> **提示**：如果你只是要做得比较简单，其实很容易：你把用户名、密码在后台一拿，判断对不对，返回一个 OK 就可以了。**但是如果你这样处理思路，那你就是做的小玩具。**

我们来看多人聊天室的结构分析。如果仅仅是为了完成登录，非常简单：假设这边是我们的客户端，这边是我们的服务器端。我把这个信息发过来，服务器端接收——接收你的用户 ID，肯定能够拿到用户 ID。但是你想想怎么拿？**你肯定要起协程**，你不能说来一个人我就死死地盯在这个地方，那肯定不行。然后你接收用户名和密码，再去比较，比较完了过后给它返回一个结果，把这个结果给它打回来。

那客户端这边的代码，最简单的逻辑就是三步：

```text
   客户端                              服务器端
     │                                     │
     │  ① 拿到输入的 ID 和密码              │
     │  ──────── 创建连接 · 发送 ───────►  │
     │                                     │  listen / accept
     │                                     │  起 goroutine 接收
     │                                     │  比较用户名密码
     │                                     │
     │  ◄──────── 返回结果 ───────────────  │
     │  ③ 判断成功还是失败                   │
     │     显示对应的界面                    │
```

如果只是一个简单的东西，就已经这么复杂了，好几步：拿到、发送——**发送你是不是要创建连接了**？你创建连接过后人家这边要 `listen`、`accept`，然后比较。比较的时候接收到过后肯定是一个 goroutine，不可能说还就一个单机版那样去玩。两头光这个就很麻烦。

> **结论**：但是这里面最麻烦的问题是什么地方？**是数据的通道问题，这是最麻烦的。** 如果你曾经做过这个服务器数据通道你就知道，这两根线很麻烦。它的麻烦不在于说你能不能把数据发过去，而是在于**数据以什么形式发过去**的问题。

因为你将来发送的信息不仅是登录，还有很多信息。比如说用户上线了、用户离线了，然后用户上线过后服务器还得把所有用户在线信息群发给其他在线的用户，挺麻烦的。所以你只是这种很单薄的一个结构——说我给它来一个字符串——**根本撑不住**。

现在的问题是我们要定协议。

### 消息协议：一个 Message，两层套娃

怎么设计呢？同学们看，老师一画图你大致就明白了。通常情况下，在我们开发中一般会采用通用的原则。

这个地方是我的一个 message，是我的一个结构体 `Message`。**肯定在开发中一定是用结构体**，不可能用一个字符串，那是小儿科。

```go
type Message struct {
	Type string
	Data []byte
}
```

这个结构体怎么做呢？一般来讲把它分成两个部分。

**第一个部分，我们叫做消息的类型。** 因为将来消息可能有很多类型，可能 10 种、20 种——想想 QQ 消息类型，少说不下 100 种类型。你发的是语音，还是在线，还是离线，还是文本，还是图片等等。所以它首先有一个 `Type`，string 类型的，**肯定用 string 来描述它**。

**第二个，除了有类型之外，是不是还有数据本身？** 你光说我要登录了，登录是一种消息类型，那你登录的时候肯定要带你的 ID 和密码，而且还要**具有扩展性**——没准下次发的不是 ID、密码，还要带这个小朋友的好友是哪些，里面又涉及到一堆东西。所以这里面的数据，也是一个类型。

这是一个总的 `Message`。但是我们将来 message 会很多，它的区别在哪里？这是一个大类、总类，但是我们每个消息从哪里体现出来呢？将来这个地方会有很多不同种类的消息。

假如这地方我有一种消息叫登录消息，我就拿一个举例：

```go
type LoginMessage struct {
	UserId  int
	UserPwd string
}
```

这个结构体里面可能就会根据你的实际情况来定它有哪些字段。咱们可以根据你的实际情况来定义。比如说我们认为它应该有 `UserId`，int 类型的；再比如说我们认为它有用户密码，string 类型的。当然还有很多其他，我就不一一说了。

### 发送的五步

现在我们怎么样把这个消息和它整在一起？因为我们还要定义消息的各种类型——将来我们的消息到底是什么消息，把它塞给这个 `Type`。每一个消息结构体序列化后，把序列化后的内容塞给消息的 `Data`。

```text
  发送流程（五步）

  ① 创建一个空的 Message 结构体
              │
              ▼
  ② 设置消息类型：message.Type = 登录消息类型
              │
              ▼
  ③ 把 LoginMessage 序列化后的字节放进 message.Data
              │
              ▼
  ④ 对 Message 整体再做一次序列化
              │
              ▼
  ⑤ 先发长度（几个字节），再发消息本身  ───►
```

所以最后，相当于说你在发消息之前，要确定发送消息的类型是什么，以及发送消息的数据是什么。你把序列化的这部分塞给它的 `Data`，把类型塞给它的 `Type`。

序列化过后，你是不是马上就发了？**也不行。**

### 为什么要先发长度

在我们网络里面最害怕的一个东西就是**丢包**。因为这个丢包，一旦丢了过后，少了一个字节——比如少了一个字节，有可能导致整个程序你调不出来错误。

> **易错点**：比如说因为网络这个东西，你发一个文件过去，结果少了一两个字节，整个视频都打不开，整个视频都打不开。你不相信你试试看，你用像我们一般可以打开二进制的那种 EditPlus，或者有一个叫 UltraEdit 还是什么东西，打开过后你把一个视频打开，你把里面的文件删掉一个字母，整个文件就废了。

那丢包怎么解决呢？一般程序员在程序里面是怎么解决丢包的呢？我举一个例子。同学们都上过网，你们发现 HTTP 协议里面第一个有一个字段就是这个包有多长，就叫 **`Content-Length`**。它一定会告诉服务器我这个包有多长。

> **结论**：那个长度是非常重要的。因为它在发送之前，它告诉你我这个 Message 或者我这个数据有多长，比如说 20 个字节还是 30 个字节。那对方在里面一定要**读到这么多字节**，如果少读一个，它判断有错误，读不到，他就认为这个包错了，他会弃包，再重新让他重发。不然的话这个网络你将来写的这个程序一定是会有很多 bug。

所以我们处理方法就按照这个严格的一种方式：**在发包、在网络传输之前，第一步先不要发这个 Message 本身**，先给服务器发送——注意听啊——**先发送这个 Message 的长度，它有多少个字节。**

这是它第一步要发的。它先把这个发过去，发过去过后，它再发送消息本身。这个发完了以后，这个发送的任务才算是完成。

### 热土豆：为什么包必须丢

有人会问：老师，为什么不能够把这个长度封装到 `Message` 里面一起给？

其实这个也可以，这样的话也是可以的。比如像 HTTP 协议，它在发的时候直接把这个长度给了。**那是因为 HTTP 协议它一次连接马上就断掉了。我们这个 TCP 本身是长连接**，所以说我们也可以先发长度再接收，也没问题。

当然也可以扩一下，给它增加一个 `len`，`len` 是个 uint，比如一般是 `uint32` 来表述它。我先把整个长度都计算出来放到这里面去，然后把包给你，你再去读，看看这个 data 是不是等于长度，也可以。**那么我采用的是这种方式，稍微麻烦，但这种方式更稳定一点。**

再说说丢包怎么处理。假设我丢包了，那么只有两种情况：要么你代码写错了，就是代码本身有问题；第二个就是网络错误。

> **提示**：网络错误的话，一般互相有一种底层的这种协议，叫做**纠错协议**。TCP 有一个最经典的原理叫**热土豆原理**——你们有时候去看下它这个底层，叫热土豆。热土豆就是说他是经过了多少个路由，比如我有一个包要发给张三，如果我经过了多少个路由——大概 20 个还是 30 个我忘了，有个数——如果经过这么多路由，这个数据还不能到达对方，那么 TCP 整个这个网络、大的网络就会把这个包扔掉。

如果不丢的话，整个网络就会游荡很多什么数据呢？**孤魂野鬼。** 就好像有一个人一样，没人管了，他认为不可达。如果你不扔掉的话，会出现什么情况？整个很多已经没有主人的这个数据，它整个就阻塞在公网上面去，**这很可怕**。

> **结论**：你现在知道为什么咱们公路上的这些阿姨他们扫地吧？因为这些垃圾你不清的话，你自己都出不去。以前我们小时候还学过一篇文章，说美国还是哪个国家，说因为不满意，说我们是清洁工人为什么工资这么低，我们全部都不扫地了，结果过了几天，大街上全是垃圾，知道吗？大致就这个意思——**数据一定要丢掉。**

### 接收的十步

接收的流程它是这样子的：它一旦要去接收你发送的这个 `Message`，因为这个 `Message` 还是个字符串嘛，它首先先去判断我应该接收多少个字节，也就是说**它先接收的是个长度**。

```text
  接收流程（十步）

  ① 先接收对方发来的长度 n
     （以字节形式发送：byte 切片 → 还要转成 int）
              │
              ▼
  ② 根据这个长度再次接收，接收消息本身
              │
              ▼
  ③ 判断：实际收到的长度 len 是否等于对方说的长度
     ├─ 不等 → 说明有丢包，走纠错协议
     └─ 相等 → 继续
              │
              ▼
  ④ 把消息反序列化成 Message
              │
              ▼
  ⑤ 取出 Message 里的 Data（此时是字符串/字节）
              │
              ▼
  ⑥ 把 Data 再反序列化成具体消息类型（如 LoginMessage）
              │
              ▼
  ⑦ 终于拿到真家伙了：可以取出 UserId 和 UserPwd
              │
              ▼
  ⑧ 去数据库或文件里比对
              │
              ▼
  ⑨ 按比较结果组装新的 Message 返回
              │
              ▼
  ⑩ 客户端收到后重复 ①②④⑤⑥
```

关于第①步，这里还有一个麻烦事：**发送的时候还不能以 int 发送，还得按字节的形式发送长度**，接收到的是一个 byte 切片，你还得把 byte 切片转成这个 int。

> **结论**：因为**网络传输的时候不能以 int 这种类型发送，它全是以字节发送的**。这就是为什么网络可以传输文件、传输图片。你这个明白了过后，我可以这么说——你就是传一个图片给服务器，通过 TCP 传都能成功，为什么？因为他底层是字节的形式，你图片、视频我都可以搞定，只是大小的问题了。

然后第二步，它拿到这个长度过后，根据这个长度来接收你的内容，因为他们两个这个链接是没有断掉的。第三步，如果它发现这个长度——它接收到的长度和你发过来的长度和我实际接收的长度不一致，**就说明有丢包现象**。如果要做得更严谨一点，它就会发一个消息说：「对不起，请你重发。」

这个就更复杂了。像一些稳定的像迅雷、像百度它这个其实挺不好做的——就是有个叫**断点续传**，你今天没有下完，你把这个一关闭，你第二天再点接着做，它还能把这个文件给你下载下来，其实挺不容易，因为它要记录你现在传到哪一个地方去了。那这个我们先呆会儿再说。

拿到这个消息过后，**第五步**该做什么呢？第五步就是你要把这个消息先反序列化成这个 `Message`，然后再取出这个 `Data` 再反序列化。所以他们这两个 `Message` 定义的一定要相同——**客户端和服务端的这个 `Message` 的结构要相同**。

第六步，你再取出这个 `Message` 里面的 `Data`。这个 `Data` 取出来，这个时候其实是字符串，因为你现在是相当于这个 `Message` 包裹了里面这个 `Message`，它是一个包裹关系、包含关系。然后你拿到这个过后，你还要再反序列化。

在反序列化过后，同学们，这个时候你就终于拿到了这个玩意儿——**第七步你就可以干事儿了**。因为这里面就真正能够取出它的 ID 和密码了。这样就取出这个 `LoginMessage` 的 `UserId` 和它的 `UserPwd`。

拿到这个东西过后，非常好了，因为你有这个东西你就可以到数据库或者到这个文件里面去比对，这时就可以比较。

#### 返回的 Message 长什么样

比较过后，根据比较结果返回这个 `Message`。我返回的肯定就是——**我返回这个消息类型和你发过来的消息类型可能就不一样了**，因为我们两个是不同类型的东西。比如说我可能返回的是 `LoginResultMes`，就是你登录的时候我给你返回。

但这个消息呢可能我就定得比较简单，可能定的是这样一个东西：**有个 `code`，`code` 是个 int，这个代表你的错误码。**

> **提示**：你看为什么有些同学学过 HTTP 协议，你看它有 200，它有 500，它有 404，它有 403——其实大致也是这样协议定的。那这个时候你可以根据它实际的情况，比如说 200 我们就代表成功了；比如说 500 我们就代表你的用户我检查了，**用户不存在**。
>
> 当然这边可能还有说明，比如说你这边有一个 error 的信息，是个字符串。如果没有错误的话，你就不用去读；如果有错误，把这个错误信息也给它打回去。

所以说在这儿，我又组装了一个这样的东西，把消息类型给到它，再把我这边组织的一个塞到它的 `Data`。当然这个地方你又要经过一系列的操作了，就是说你先把结构体做出来，然后传给它，先把她序列化给到 `Data`，再把这个 `Message` 再序列化，得到一个字符串，最后把它发回去，发送给客户端。

那么客户端拿到这个东西呢，他又开始对它进行刚才这一个操作。你看多复杂——「老师，这个……」别写了，我都开始蒙圈了。

其实我说的这个过程很复杂，但是代码我一写，也发现其实还真的有点复杂。你写代码也是一样的。但是有一个好处就是你学完了之后，**你对网络的一个过程确实是理解得比较透了**。就会感觉，哦，原来这么回事——先发一个长度，再接收内容等等。为什么要发长度呢？就是因为怕丢包。

发送有大概五个步骤，接收有十个步骤。当然，到时候我们发送和接收肯定要封装成函数。思路说完了，先放到这儿。

## 把消息长度发出去：第一个真正跑通的字节
> 对应块：BLK120 | 覆盖分集：P318 | 块标题（分集名）：《316_尚硅谷_海量用户通讯系统-服务器接收长度》

上午我们给同学们说了一下关于我们 TCP 通讯的这么一个基本的步骤。这个步骤相对来说看起来是比较复杂一点，但是代码也还是要体现，要体现，所以说我们一步一步来看。

上午我们说完了 message 的组成，还有发送一个 message 的流程。现在我们用代码来实现它。

### 今天要打通哪一条线

今天实现的要求是：**当用户 ID 等于 100，密码为 123456 就可以登录，其他用户暂不能登录**，指定用户。

在这个基础上，我们做第一步：**完成客户端可以发送消息的长度，服务器可以正常收到该长度值。**

> **提示**：这一个功能咱们就得讲一会儿，因为前面是最费劲的，前面是最费劲的。就这一个，我们先完成这一条线——把这条线发过去的长度先接收到，服务器这边先能接收到，把这一步先完成。

### 思路：定结构、起监听、开协程

第一步，首先我们在代码上先把这些消息的格式定好，先确定 message 的这个格式和它的结构。

第二步，我们让服务器这边来进行监听。它在这里监听，**这个端口我们把它定成 8889**，但你也可以随意。

第三步，客户端连上了之后怎么交互？我们今天这个思路稍微有点绕，跟上思路：

```text
              服务器主线程（上下文空间 P）
                        │
   客户端 A 连接 ──────►│ Accept 成功，拿到 conn
                        │
                        ├──► go process(conn)   协程 1  ← 只服务 A
                        │
   客户端 B 连接 ──────►│ Accept 成功，拿到 conn
                        │
                        └──► go process(conn)   协程 2  ← 只服务 B
```

读图：你可以认为主线程是它的一个主线程，主线程这边会有一个上下文空间。当有一个请求过来以后，我给它开一个协程，这个协程是专门让它跟客户端进行这个交互的，它跟客户端的端口通过这个 `conn` 相互通讯。

> **结论**：因为服务器这边它要去读消息，而客户端要发消息；反过来也一样，服务器也可能发消息，客户端要接收消息——**所以我们要新建一个共用的包**。

新建一个 package，比如 `pkg/common`——这个包里面放我们的消息结构体。文件布局大致是：新建两个文件夹，一个是 `common`，`common` 下面再建一层专门放消息，以后还有新的共用部分也写到这里；`server` 这边至少目前应该有一个 `main.go`，这是必须有的。

客户端这边目前有个 `main.go`，`login.go` 已经有了，我们再增加一个 **`utils.go`**。这个文件是我们的一个工具，就是关于**发送消息包和接收消息包**，我们到时候都在这个地方写东西。

### 先把 common/message 定下来

```go
package message

type Message struct {
	Type string `json:"type"` // 消息类型
	Data string `json:"data"` // 消息的内容
}
```

它是一个结构体。结构体里面根据我们上午的分析，它目前需要有两个字段，一个是 `Type`，一个是 `Data`。

> **注意**：这里面的 `Data` **不要把它定义成字节切片**，因为你到最终在程序里面操作的时候，它仍然是字符串。

Type 现在我先都不进行封装，我都把它做成一个公开可以访问的，string，它是消息的类型。

然后我们先定义两个具体的消息。目前我们至少需要两种：一个是登录的这个消息，第二个是这边回送的登录结果消息。

```go
type LoginMes struct {
	UserId   int    `json:"userId"`   // 用户ID
	UserPwd  string `json:"userPwd"`  // 用户密码
	UserName string `json:"userName"` // 用户名
}
```

这个是我登录的一个消息。当然都是结构体——你既然是面向对象，你这个 TCP 也用到面向对象嘛，你肯定是定成这个结构体的。

第一个，UserId 肯定是跑不了的。因为你在传递的时候没有 UserId 肯定跑不起来嘛，你登录肯定要给它，所以说是 int 类型。第二个，用户的密码跑不了，给它一个吧，string。那后面有可能还需要传递一些其他信息，比如说 UserName，好，我也先写到这儿，用不上也无所谓，后面扩展的时候还能用到。

紧接着，我们还需要一个它登录过后我这边给它回送的一个消息。这两个消息长得不一样：

```go
type LoginResMes struct {
	Code  int    `json:"code"`  // 返回状态码 500 表示该用户未注册 200 表示登录成功
	Error string `json:"error"` // 返回错误信息
}
```

> **结论**：状态码我们先确定两样：**500 表示该用户还没有注册**（你给我来个 ID，我发现没有这个人，没有这个 ID，那说明还没注册），**200 表示登录成功**。当然你可能还有别的，比如你用 300 表示什么权限不够啊、或者网络不通啊，后面可以再说。

另外有个 `Error`，用 `string` 表示，就是你这个错误信息是什么。如果没有错误的话，返回的错误信息就是空的。

再来一个——大家看到这个 `Type`，**你这个 Type 你最好给它一个常量来确定**。

> **提示**：`LoginMes` 还有 `LoginResMes` 将来都是填充到 `Data` 这个地方，那这个地方你给它什么呢？你得给它描述你这个消息是什么类型。这个是结构体本身的名字，消息呢，你还得给它一个字符串。所以这个消息呢我们应该定义一些常量，确定一些消息类型。

```go
const (
	LoginMesType    = "LoginMes"
	LoginResMesType = "LoginResMes"
)
```

这样肯定好管理，你不能说每次就在这去一个个给，太累了。**消息类型我们都定义成常量，它不能改。**

在后面我们还要加很多消息。比如说将来还有用户上线的消息，还有聊天的消息，结构肯定是不一样的。现在确定了两个，确定这两个过后，我们再继续往下走。

### 服务器端：监听、Accept、起协程

写代码的时候先把哪一个写出来呢？**大家共用的一个部分**——因为客户端和服务器端都会要共用到一个消息结构。上面我们把 `message.go` 定义好了。

> **易错点**：我把刚才 `Message` 的定义放在 `message.go` 这个文件里面才对，不能放在 `main.go`。`main.go` 那是我们的 server 嘛。

回忆一下怎么写：

```go
package main

import (
	"fmt"
	"net"
)

func main() {
	// 提示信息
	fmt.Println("服务器在 8889 端口监听...")
	listen, err := net.Listen("tcp", "0.0.0.0:8889")
	if err != nil {
		fmt.Println("net.Listen err=", err)
		return
	}

	// 一旦监听成功，就等待客户端来连接服务器
	for {
		conn, err := listen.Accept()
		if err != nil {
			fmt.Println("listen.Accept err=", err)
		}

		// 一旦连接成功，则启动一个协程和客户端保持通讯
		go process(conn)
	}
}
```

先给提示信息，写上我们是 TCP 这种协议，然后我要在本地监听，端口是 8889。这边就会返回两个东西，一个 `listen`，还有一个 `err`。如果有错的话呢，我们就不监听了——因为你监听都监听不了，那下面代码就别玩了，`return`。

一旦监听成功，就应该循环地等待客户端来连接。

这边一旦连接成功，就相当于说我可以提示一句话，说等待客户端来连接服务器。然后 `Accept` 成功了，它应该返回一个连接——**这个东西很重要，将来这个东西就是服务器和客户端之间相互交互的一个重要的线。**

> **结论**：准确地说它们是**一根互通的管道，或者叫一个套接字**。所以这个线咱们还得画得严谨一点。要不然的话导致大家认为好像去是一个连接，回来是一个连接，那就错了。这个线你就理解成就是我们这个可爱的 `conn`。

这个时候我们做一个判断，如果 `err != nil`，说明我们这 `Accept` 可能出错了。提示它一个信息。**这个地方可以暂时不退出**，因为可能有一个连接出错了，其他还是可以工作的。

紧接着拿到这边该干什么了呢？我拿到这个连接过后，我就应该起一个协程，让它为我服务。这个是老套路。

> **提示**：你会看到写这个网络特别有意思，喜欢网络的同学特别喜欢写网络，他会觉得很好玩，感觉好像有两个人在这玩一样。

```go
// 处理和客户端的通讯
func process(conn net.Conn) {
	defer conn.Close()

	for {
		// 循环地读取客户端发过来的数据长度
		buf := make([]byte, 1024*4)
		n, err := conn.Read(buf[:4])
		if err != nil || n != 4 {
			fmt.Println("conn.Read err=", err)
			return
		}
		pkgLen := binary.BigEndian.Uint32(buf[:4])
		fmt.Println("读到客户端发送的数据长度 pkgLen =", pkgLen)
		fmt.Println("等待读取客户端发送的数据...")
	}
}
```

你在处理这个通讯的时候，一个最重要的东西你必须给我传过来，就这玩意儿——**你连接不给我，我没办法跟人家玩，就这根线**。所以这个地方我们一定要把套接字传给它。这里有个 `conn`，**这个套接字是引用类型，所以你不用加星号了**，`conn net.Conn`。

> **易错点**：这个 buf 有点大，我们尽量给它大一点，按 $1024 \times 4$ 来开。但是——**读的时候我只读前面的这个四个**，因为你给我发的是四个，我也读四个字节，这样子才是对的啊。如果你读得很多，把后面的那个没有用的东西也给你带过来了，就麻烦了。

然后判断：如果 `n` 不等于 4，因为我读要读四个字节，你给我发了四个字节，我也读四个字节；或者 `err` 不等于 `nil`，说明我这个读就读错了。写句话：`conn.Read` 读错了，把这个错误打出来。一旦读错的话，要么你就 `return`，要么你就干别的事，假设我就 `return` 了，我就不玩了。

> **提示**：注意，**这地方会阻塞啊**。如果你这个读不到东西，它会堵在这个地方——前面我们讲过这个原理。

### 客户端：七步把一个长度发出去

现在回到客户端来写一点。因为人家（服务器）已经到雷区了，已经等待你来发东西了，而你还没连。

```go
// 1. 连接到服务器
conn, err := net.Dial("tcp", "localhost:8889")
if err != nil {
	fmt.Println("net.Dial err=", err)
	return
}
defer conn.Close()
```

连接服务器这个很简单，我们学过 `net.Dial()`。因为我这是本地，所以我写的是 `localhost`。

> **结论**：理论上说将来这个地方到底连哪儿，**应该去读一个配置文件**，这样子你就不用去改源代码了。所以以前我们学过的读配置文件那个知识点又可以用上了。端口是 8889。

一旦拨号，会得到一个连接和一个 `err`。做个判断，如果 `err != nil`，代表我们这地方连接失败了，那肯定这个就没法玩了，打印出来然后 `return`。如果没有报错，那说明我们连上了，连上了你就可以发一个东西过去了。

**第二步，准备通过这个 conn 发送消息给服务器。**

```go
// 2. 准备通过 conn 发送消息给服务器
var mes message.Message
mes.Type = message.LoginMesType
```

因为你发的是结构体，所以你二话不说先搞一个结构体整出来再说。这个 `mes` 这个包，我干脆叫 `message` 吧——`message` 包下面有这些 message 嘛，也很好理解。

这个时候它是空的，没用。我们先把类型给它，先确定下来是登录的这种消息。但这还不够，因为里面还有一个特别重要的，就是这个 `Data`。

**第三步，创建一个 `LoginMes` 结构体。**

```go
// 3. 创建一个 LoginMes 结构体
var loginMes message.LoginMes
loginMes.UserId = userId
loginMes.UserPwd = userPwd
```

它现在是空的，往里面给我填东西吧。第一个把 ID 给它，第二步这个重要信息是密码——就是这边传过来的 `userPwd`。

> **提示**：这个赋值还是大写的，因为你还没序列化，所以说它的字段名仍然是 `UserId`。为什么我定义的时候用大写呢？因为你将来肯定是结构体要序列化才能发送的，序列化之后得到的都是小写的，所以我给每个字段都加了 `json:"..."` 这个**结构体的标签**。

**第四步，先序列化。** 现在你准备要发送，你得把这个 message 给到 `mes` 的 `Data` 这个字段。**但现在能不能这样写？**

```go
mes.Data = loginMes   // ❌ 行不行？不行
```

> **结论**：行不行这样干？**不行。** 为什么不行呢？因为 `Data` 它的类型是 string，`loginMes` 它是一个结构体。**所以你必须先把它们进行一个序列化，然后放进去。** 序列化在前面咱们学过：

```go
// 4. 将 LoginMes 序列化
data, err := json.Marshal(loginMes)
if err != nil {
	fmt.Println("json.Marshal err =", err)
	return
}
```

序列化的时候，你得把它给我扔进去。扔进去过后，它返回了一个 `data`，还有一个 `err`。

OK，那这个时候这个 `data` 它的类型是一个 byte 切片。是个 byte 切片，所以你先做一个判断：如果 `err != nil`，就不玩了，走了，不玩。

如果这序列化成功，那么这个时候这个 `data` 就可以填到——**但是呢你要这样转**，因为这个 `data` 它是一个 byte 切片，而人家这个 `Data` 的类型是 string，因此你要先把它转成 string 再给它。

**第五步**，把这个 `data` 填充到 `message` 的 `Data` 字段。到这一步，我们的 message 就既有了 `Data`，又有了 `Type`。

**第六步，将 message 进行序列化。** 因为到这个时候，你的这个 `message` 结构体才是一个正确的、可以发送的结构体。

```go
// 6. 将 message 进行序列化
data, err = json.Marshal(mes)
if err != nil {
	fmt.Println("json.Marshal err =", err)
	return
}
```

好，同学们，最后这个 `data` 就是我们要发送的数据了。

### 一个 int 为什么不能直接 Write

**第七步**，到这个时候，`data` 就是我们要发送的消息。但是发送的时候，根据我们原先的一个规则——**我们是先发送一个长度，再发送消息本身**。

所以现在又有麻烦事了：我们先把这个 `data` 的一个长度发送给服务器。因为我们为了防止丢包，我们先让它知道说：告诉你，你应该先给我接收多少个字节的内容。

怎么发呢？有同学说老师，太简单了：

```go
conn.Write(data)   // ❌ 不行，这是发内容本身
conn.Write(len(data)) // ❌ 也不行
```

> **易错点**：`len` 返回的是个 `int` 类型，`Write` 发送的是 **byte 切片**。你这样一保存马上就报错了。这地方很多同学不理解——这地方就是工作过一段时间的，他只要愣了一下类做，他不一定想明白怎么弄。

所以你得先获取到这个 `data` 的长度，然后将这个长度转成一个可以表示这个长度的切片。这个有点麻烦，那我告诉大家怎么处理。

这里边有一个特别重要的方法要给大家聊一聊。Go 官方文档，打开 `net` 包——`net` 里面有一个 `Write` 方法，就是 `Conn`，这个 `Conn` 是我们现在最重要的一个结构体，它应该是一个接口。

那怎么把一个长度转成一个切片呢？`encoding/binary` 包。

> **定义**：`encoding/binary` 包实现了**简单的数字与字节序列转换**的一个方式。它可以把你的一个具体的数字转成字节序列，说白了就转成我们的这个字节码。

里面有一个特别重要的方法：`ByteOrder`，它里面定义了好些方法，其中有一个方法叫做 **`PutUint32`**，我们用这个。它这个地方是：你把一个 uint32 的一个具体的数字填到这儿，然后再给它一个切片，这样子就会把这个数转成一个 byte 的切片的序列。

这个可能同学们第一次接触有点不太理解。那我先写一下，来，看我的思路：

```go
// 先算长度
var pkgLen uint32
pkgLen = uint32(len(data))
```

> **提示**：为什么我把它定成 `uint32` 呢？第一个原因是因为它是作为一个无符号的 32，这个数能表示的数据量比较大；第二个原因就是因为待会儿我想使用的是这个方法 `PutUint32`。
>
> 有些同学说，老师，那我如果想使用 `PutUint64` 呢？那可以——你可能就是想发送的数据量更大嘛。
>
> 但我觉得 32 应该很大了。它是 $2^{32}-1$，除以 1024 就是多少 K，再除 1024 就是兆，再除一个 1024 就是 G。**也就是说你已经可以发将近 4 个 G 了**——我估计一般网络都快冲死了，足足的够了，所以暂时没有必要整那么大。

`len` 算下来它返回的类型大家都知道，它是一个 `int` 类型。把一个 `int` 给一个 `uint32` 肯定是不能行的，因此要进行一个强转：

```go
var pkgLen uint32
pkgLen = uint32(len(data))
```

现在这个 `pkgLen` 长度已经有了。但是你还要把它放在一个切片里面去。先定义一个数组，四个字节，因为一个 uint32 就是 4 个字节：

```go
// 转成 byte 切片
buf := make([]byte, 4)
binary.BigEndian.PutUint32(buf, pkgLen)
```

`binary` 包里面有一个这样的东西，它有一个变量，叫 **`BigEndian`**。好，也不要怎么去念它，管它是什么，先用它。它的这个类型就是 `ByteOrder`，就是字节序列的一个类型，里面就有这个方法。

好，把它放进去，我要做一个切片，切片我就认为从 0 到 4——**其实就是把四个都全部拿到了**。这样子就相当于说我把这个长度转成了这个 `buf`。

现在就可以正式发送了：

```go
// 7.1 先发送长度
n, err := conn.Write(buf)
if err != nil || n != 4 {
	fmt.Println("conn.Write fail, err=", err)
	return
}
fmt.Println("客户端发送消息长度成功")
```

那么我们现在怎么知道它发送成功了呢？**首先它应该一共这个 n 必须等于 4**，如果它不等于 4，就说明它失败了；或者这个 `err` 不等于 `nil`，说明它也失败了。在这两个条件只要有一个条件成立，就说明我们这个发送没有成功。

> **注意**：现在我们已经把这个消息的长度发送出去了，**但是消息的本身我还没有发**，因为消息本身实际上是 `data`，我按照我的逻辑是，我先给它发个长度，我再接着发消息本身。

## 让服务器读懂客户端：长度头解析与 readPkg 封装
> 对应块：BLK121 | 覆盖分集：P319 | 块标题（分集名）：《317_尚硅谷_海量用户通讯系统-服务器接收消息》

接着上面的代码继续往下讲。先把服务器这一块的两处小毛病改掉——虽然是小毛病，但都是"看起来能跑、其实埋了坑"的那一类。

### 先把两处能收拾的地方收拾了

**第一处：`make` 提到上面去。**

原来这个 `make` 写在循环里面，每次进来都重新开一块 buffer。其实这个地方有一个 buffer 就够了，进入这个函数先把 buffer 开出来，后面循环复用它就行。

**第二处：`n` 的判断去掉，只留 `err`。**

有同学说那个 `n` 判断根本没什么意义——你都指定读四个字节了，它就读四个字节。这里我们不妨回到 `net.Conn` 的定义上再确认一遍。

`net` 包里有个接口叫 `Conn`，它上面挂着 `Read` 方法。这个方法有一个返回值 `n`，含义是它**实际上**读了多少个字节。

所以这么看，`n` 并不是完全没意义：它和 `err` 表达的是两件不同的事。`err` 是"读出错了"，`n` 是"没报错，但可能没读够"。

不过在当前这个场景里，因为对端指定的就是四个字节的长度头，判断不判断问题都不大，判一个 `err` 就够了。**但这是"当前场景够用"，不是"这个判断没意义"**——下面封装 `readPkg` 的时候你会看到，在读消息体的地方，这个 `n` 的判断是必须加回来的。

### 下一个功能：让服务器真正"读懂"客户端

我们要完成的功能是这么一小段，但工作量和它的篇幅完全不成正比：

- 客户端可以发送**消息本身**（不只是发个长度头就完事）；
- 服务器可以接收到正常的消息；
- 服务器根据这条消息判断用户合不合法——这条消息前面我们已经讲清楚了，它就是一条 `LoginMes`；
- 判断完返回相应的 `LoginResMes`；
- 客户端再解析这个 `LoginResMes`，显示出对应的界面。

看起来挺简单，但因为这是第一次真正动手写这套结构，工作量一点也不小。所以先做思路分析。

#### 发送、处理、返回、再处理

拆成四步：

**第一步，客户端发送消息本身。**就是发送那条登录消息。

**第二步，服务器把消息收下来，反序列化成对应的 message。**注意，此时此刻服务器接到的东西说白了就是一个字节切片——我们拿到的只是一堆字节，还不是结构体。得把它反序列化成对应的消息结构体才能用。

**第三步，服务器根据反序列化出来的消息判断登录用户是否合法**，判断完之后返回 `LoginResMes`。返回的时候当然也要做序列化工作——发出去的东西必须是字节。

**第四步，客户端解析返回的 `LoginResMes`，然后显示对应的界面。**

就这么四步：**发送、处理、返回、再处理**。

### 客户端：把 `data` 发出去

打开 VS Code，找到登录那一段。你的这个地方已经把长度头发过去了，对面也顺利接收到了。现在不着急退出，接着把消息本身也发出去。

发消息本身其实非常简单——你手上不是已经有 `conn.Write` 这个连接了吗？跟发长度头那个思路是一样的，复制一份贴过来就行。

要发的内容大家都非常清楚，就是 `data`。因为你前面已经把这个 message 序列化成了一个 `data`，所以这儿发出去的就是 `data`。

放进去之后，看它有没有发送成功。`n` 的意义也不是特别大，我们主要是判断它有没有产生一个 `err`：

```go
if err != nil {
    // 说明这边发送失败了，data 没发出去，或者是什么原因
}
```

这个就发送出去了，消息本身这一步就完成了。

### 封装 readPkg：把"读"这件事整个藏起来

消息本身发出去了，接下来就是接收。但这里我们不在主流程里直接写读取的代码。

大家想一想：如果在这一块写，显然有点不划算。因为读完之后你还要读它的内容，最终我们希望读完这个数据**直接就得到一个消息体**。

读的事情很多，它不是简简单单把这个字符串读到——它还要把这个字节切片重新恢复成一个结构体。干脆我们就封装成一个函数，封装成一个函数更合理一点。

所以我们在这里做一个 `readPkg`。它大体的意思是这样的：

> 你给我一个连接，然后最终我给你返回一个什么？你给我一个连接，我读长度，读完之后我直接反序列化，把这个 message 反序列化以后给你返回去。如果有错误，我还给你返回一个错误。

就这么个逻辑。因为读这个数据，你最终不就是想要读完过后拿到一个 message 的结构体吗？这样子就简单了。整个 message 直接给你封装好了。

它是不是可以循环地读？是的。所以我们把读取消息、读取数据包整个封装成一个函数，函数的名字就叫 `readPkg`。

开始封装。下面这些代码都有可能要把它拿走——从读长度头开始，整体剪走。

```go
func readPkg(conn net.Conn) (mes message.Message, err error) {
```

里面你给我一个连接，连接是 `net.Conn`；最后我给你返回的是一个 `message.Message`，同时也有可能有个 `err`，把 error 也给你返回。好，就这么个玩意儿。

#### 把 buffer 的长度读成 uint32

前面那段代码大致是相同的——先读出长度，读完之后根据读到的长度来处理。

注意听，关键动作来了：**把 buffer 的长度转换成一个 `uint32` 类型**。为什么要转？因为我想知道到底我应该读多少个字节，所以在这个地方要做一次转换。

怎么转换？先给它声明一个 `uint32` 类型的变量：

```go
var pkgLen uint32
```

那怎么把一个 buffer 的长度转换成 `uint32` 呢？还得用刚才那个包——`binary` 包。把刚才写过的那个函数拿来用一用，刚才在 login 的时候用过这么一个函数。

打开手册，`binary` 在 `encoding/binary`，点进去里面有个 `order`，它里面有个函数叫 `Uint32`。你把 byte 切片放进去，然后给你返回一个 `uint32`。也就是说，这是一个**反方向**的转换：把 byte 字符序列表示的值转成一个 `uint32`。这样我们就拿到了。

#### 按长度去 conn 里读消息体

现在根据 `pkgLen` 来读取消息内容。怎么读呢？很简单：

```go
conn.Read
```

读多少呢？buf 切片走，我要读这么长。

**这句话怎么理解，这地方特别容易理解错**：这句话不是从 buffer 读，而是从 **conn 套接字里面**读这么多字节，扔到 buffer 里面去。

有同学把这句话理解错了。再说一遍这个函数的意思：**从 conn 套接字里面读这么多字节，扔到 buffer 缓冲里面去。**

那这里 `n` 的判断就有意义了。刚才有同学说那个判断没有意义，不是这样的，其实那个判断还是有一些意义的。因为你想读这么多，你就一定能读这么多吗？**不一定**。你说你要读 4 个，结果 conn 连接只给你发了 2 个字节呢？它是期望读这么多，但实际从 conn 读了多少个字节，是不敢确定的。

所以这里写个 `n` 和 `err`，这个时候我们要做一个判断。如果这个 `n` 它不等于实际期望读的长度，那就说明有可能丢包了——这个道理和刚才 4 字节的比对其实是一个意思。

或者 `err != nil`。有两种可能性：

- 第一种可能性，我的的确确从 conn 里面读到东西了，但我想读 20 个字节，实际上只读了 10 个字节，那就说明错了；
- 还有一种可能性，就是因为对方管道关闭了，也有可能错。

所以不管是什么原因，都是错误。打印出来一个错误信息，然后 return，不做了：

## 那个刷个不停的 read pkg header error，到底是谁在作祟
> 对应块：BLK122 | 覆盖分集：P320 | 块标题（分集名）：《318_尚硅谷_海量用户通讯系统-服务器接收消息》

### 罪魁祸首：Read 的阻塞前提被打破了

服务器这边是一直在 `for` 循环里读取、读这个包的。它其实是反复地读，读的时候它会**阻塞**在这里——阻塞的前提是：对面这个 `conn` 一直是个有效的、大家都是持有的一个连接。**只有在 `conn` 没有被关闭的情况下，它才会阻塞在这里等你输入。**

> **关键**：阻塞是有前提的。连接一旦被关闭，`conn.Read` 就不再阻塞。

那么只要任意一方——不管是客户端还是服务器端——有一方关闭了这个连接，就"马上这个就不玩了"。

如果客户端关闭了 `conn`，那么就不阻塞了。**那么不阻塞就会出现刚才这样一个情况，就是反复地打这个东西。**

为什么呢？因为他不阻塞，他就去读，显然读不到东西；读不到东西，它报一个错，又 `return`，`return` 到这个地方。`return` 这个错过后，你又说 read package err，然后你也没做任何处理，你又去读；再去读，它又到这个地方，它又发现又读不到东西，又把这个错误抛出来，然后又回来——**所以是反复地打。**

```text
客户端 close(conn)
        │
        ▼
服务端 conn.Read 不再阻塞 ──► 读不到东西 ──► 报错 ──► return
        ▲                                                    │
        └───────────────── 主流程没做任何处理，接着循环 ◄────┘
```

解决方案很简单。读的时候已经读错了，你可以有两个方案。第一个是——**你退出，我也退出**，大家相当于说你不玩了嘛。

打个比方：比如说我跟那个客户端正在聊天，我说"你好啊。"对方一句话不说直接挂了。挂了过后我这边"嘟嘟嘟"，你都不跟我说了，那算了，我也不玩了，我也退。对吧？你不玩了我就退嘛。


#### 为什么非分层不可

因为我们做编程，尤其是程序的结构，它有一个核心的观点：

> **优化效率一般用缓存来解决，优化程序结构一般用分层模式来解决。**

这是一个非常重要的两个核心观点，你不管怎么样都跑不了这两个观点。你要优化速度，一定是缓存来解决加算法；你要优化你程序的结构，一定是分层。MVC 也好，还是什么模式、多层模式，它根本的核心思想就是**各司其职**——这一层做什么事，这一层做什么事，把它分散下去。

就好像我们这个国家一样：班子要管理好，总书记能力很强吧，十三亿人口让他一个人直接管，他管得了吗？你看人家很聪明，管几个部长就行了。我管二十多个省长，省长管市长，市长管县长，县长管镇长，镇长管村长，村长管组长，组长管家长，最后管到你身上了。这不是一个分层的模式吗？所以总书记把二十几个省长管起来，把部长管起来，这个国家就治理得很好。

包括以后做服务器集群，它也是分级模式。我一个总的服务器，下面挂几个服务器，服务器下面又再分级，都是这种思想。这种思想在任何一个地方都会适用的。以后你学到这个关键点，你就发现其实程序也不是很难，它都是这种思想。

### 为什么这一段"看着最烦"：字节与结构体的鸿沟

好，这段代码保存一下看看能不能跑起来，这段代码有点难，有点绕。

刚开始大家这样写会觉得有点麻烦，但是你用久了过后你会发现，其实这种封装能够适应很多需求。说白了就是一个逻辑：发出去之前，因为网络发的时候它只允许传字节。

**关键是在什么地方呢？为什么会觉得很麻烦呢？根本原因是在两点：**

- 第一个，网络传输它只允许是字节；
- 而我们在程序里面操作，却要求是结构体。

因为你网络传输的东西和你程序里面操作的类型不一样，导致你在程序里面要做大量的转换工作。你在真正这个逻辑里面一定要用结构体的类型你才能玩，但是你要发送的时候，你首先还得把它序列化，序列化过后还要搞成字节发过去；发过去那边还得取，取完过后还得把里面的内容取出来。它的难度肯定就增加了。

而这些底层的工作，如果你是用 Web 开发，这些转换工作全部由底层的框架帮我们做完了。而你现在用的是什么？TCP。

**你如果是 TCP 编程，最恐怖的动作是因为没有 Web 服务器了，没有 Web 解析器了。**平时你用 PHP、你用 Java，为什么你会觉得简单？原因是你有 Tomcat 帮你接收，你不需要写传输的连接，第二个，你有一个 Tomcat，Tomcat 会帮你解析这些东西，你直接结果全部拿到了。而你 TCP 是个什么东西呢？**服务器完全是你在写，解析也是你在写**，所以代码一定会比那个复杂。

所以说我们经常说，CS 从底层来说它一定难度要大于直接写 BS 的。因为没有服务器，服务器是你自己在写，协议还是你自己在定，所以难度肯定都要大。大家通过这个也挺好，一下认识它的本质了。以后你在学 Web，可以这么讲，应该很轻松，至少你比别人认识的底层东西要多很多很多。所以这个付出还是有回报。

### 把登录这条链路的改动清单捋一遍

我把这个代码整理到笔记里面去。看是完成了哪些功能，在原先基础上加了哪些东西。把源代码直接给你们反而不好，直接看都不知道怎么看。我们看看在原先基础上加了哪些东西。

**首先是服务器端的 `main.go`，在里面做了修改。**

- 在服务器的 `process` 里，我们增加了一段逻辑：根据你的消息不同让它去处理，这相当于是像其他框架的一个总控制器。我把它放在这里，这是第一个地方改的。
- 我们还增加了两个特别重要的方法：一个是 `serverProcessMsg`，它是决定哪个函数来调用；另一个是具体去处理登录的这么一个函数。这个函数相对代码量大一点，其他你就可以照这个套路走了。

**紧接着，客户端这边我们做了哪些工作呢？**

- 我们增加了一个函数叫 `utils`，里面那个方法我用到了，这是新增的。把它的 `read` 和它的 `write` 封装到函数里面来了。

### 结构改进：为什么一个 `main.go` 写不下去了

那我们接着上一节课讲的内容继续。上一节课我们已经完成了登录这一块——用户可以跟服务器进行一个交互，服务器这一块它会根据你发的消息不同类型，用不同的方法来进行处理。

现在我们来思考一个新的问题。

前面完成的那个固定登录，就说叫指定用户名和密码的这种登录，**但是它没有结构**。什么叫没有结构呢？就说你现在代码一打开看一看你的服务器端，说白了你是采取一个**流水线的形式**。你把所有的代码——像 `readPkg`、`writePkg`、还有我们的这个登录的处理、还有 `process`、包括这个 `serverProcessMsg`——都固定写在了一个文件里面。

大家想一想，如果我们在这种模式不停地往下写，**那后面的功能你基本上就写不动了**。因为你把所有的事情都放在一个文件里面去，这个叫做程序没有结构。程序没有结构指的就是这个意思，它的结构是没有的。

那如果说对一个没有结构的项目来说，你写到后边再加一点功能，基本上加不进去，甚至可读性很差，你也不可能让所有代码让一个人去写。因此系统的可读性、可扩展性，还有维护性都比较差，所以**我们需要对程序的结构进行一个改进**。

#### CS 的改进要动两头

那改进涉及到两个问题。

如果说我们以前写的是 BS 开发，BS 开发的话，因为浏览器这一块同学们是不需要自己写的。如果我们前面写的像这个客户关系管理系统，它是单机版，它其实不涉及到服务器。

所以说：

- 如果你是 **BS**，你的客户端不用写；
- 如果你是**单机版**，没有服务器，所以你只写客户端，你只写一头就可以了。

但是现在我们的结构是 CS 的结构，我们既有客户端又有服务器端。因此我们的改进涉及到两方面——**你只要写我们这种 CS 结构，你完成一个功能，你要写两头**。你既要写服务器端又要写客户端，所以你想你的这个代码的工作量无形中就比 BS 要增加一倍。当然增加一倍你看起来是增加了一倍，但实际上它的复杂度肯定要更多，因为它是网络传递，你测试起来有时还比较麻烦。

因此，我们这样子说：我们首先画出框架图，然后根据我们的这个框架图进行改进。我们先改哪一块？**我们先改进服务器端，然后再修改客户端。**咱们有个步骤——你最好不要两头同时写，两头同时写有时候也比较懵圈。

好，既然有思路分析，我们先把这个程序结构图画出来，然后开始动手。**这是一个很好的一种思想，就是把一个大的东西画成一个小的东西。**这是我们去做一件比较复杂的功能时的一个核心思想。

### 服务器端改进框架图

好的，我们来开始画这个示意图。整个这个框框代表我们的服务器端。

```text
┌────────────────────────────── 服务器端 ──────────────────────────────┐
│                                                                       │
│  main.go（主函数）                                                    │
│    ① 监听我们的程序                                                   │
│    ② 等待客户端的连接                                                 │
│    ③ 完成一些初始化的任务（比如 Redis 连接池）                        │
│                    │                                                  │
│                    │ 一旦接收到客户端连接，这件事情交给另一个文件去做   │
│                    ▼                                                  │
│  processor（总处理器 · 类 MVC 思想）                                  │
│    根据客户端的请求，调用不同的具体处理器完成任务                     │
│         │                │                │                           │
│         ▼                ▼                ▼                           │
│  userProcess.go    smsProcess.go      （以后会有更多）                 │

│                                                                       │

│    大家共用，你用我也用，你要用我就给你用                             │
│                                                                       │

│    message.go：共用的消息定义                                          │

│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

#### 每一层的职责，说清楚

**`main.go` 它的功能呢？**你写的是这个样子的。它在里面完成了哪些功能呢？它完成了一个监听和接收客户端连接的功能，然后呢它起了一个协程。

那一般来讲的话，这个协程起来过后，按理说就跟这个 `main.go` 没有什么关系了——你看这个 `process` 做完了过后，你就去让它去处理这个消息了。所以我想这么去设计，**它只做一件事**。

**第一件事：监听我们的程序。**第二点呢，仔细听讲，获取——获取什么呢？**等待、监听和等待**，等待什么呢？等待客户端的连接，这是第二件事情。

那么还有什么事情它可以做呢？它还可以去完成一些初始化的任务。因为你后边我们今天呢还会写这个用 Redis 的连接池做些工作，那这个时候它有些初始化的工作呢，可以让这个主函数帮我们来完成。

**`processor`：它是一个总管家。**这个地方我采取的一种思想呢，就类似于 MVC 的思想。MVC 这个思想最核心就是说：把一个请求、把一个事情先交给一个控制器，或者叫一个处理器。这个处理器根据这个业务的不同，把它分散到不同的控制器去去做。那么小的控制器呢，又去调它的 service 层或者是 DAO 层完成。

好，这是它要做的一件事情。它的核心点就是它去根据客户端的请求来做处理。到时候呢，它的连接是这样一种方式，就它把这个请求就发给了它——其实它是一个调用的关系，它调用它。

**那么这一套控制器呢，是不行的，太单薄了。**你看我们以前有同学学过 Struts2 就知道，Struts2 有一个总的这个控制器，叫 ActionServlet 类似这么一个东西。那么由它呢，就好像是个大管家一样，它管了很多小的这种控制器。

**`userProcess.go`**——这是一种思想，同学们，这种思想呢，它已经很成熟了。它是处理跟用户相关的这种请求。比如像登录、注册、注销，再比如说这个用户的取它的用户列表等等，你都跟用户相关的嘛。再比如说我们是用户列表的管理。

**`smsProcess.go`**——因为我们作为这种聊天室，你肯定会聊天嘛，聊天呢我们把它称之为短消息。它处理跟短消息相关的请求，比如群聊，或者是点对点的聊天，也就是我们私聊。

那当然说，还有什么呢？比如说将来你想发这个跟文件、语音相关的，我们叫做 IM，即时通讯的 IM。比如你要发个文件，你要发个图片，你要发一个什么共享的东西，你再写一个处理器，专门处理那个逻辑。

**它这样就分而治之了。**相当于说我根据你的请求，我来调用或者是让不同的处理器帮我干活。

#### 这套图现实里长什么样

这就跟我们现实生活很像了。就好像有一个客户来了，先有一个前台。前台说："来，客户，你来了。好，我就找到咱们的总调度室。"一般公司都有一个专管总调度的，总调度说："你要找谁啊？你要找张经理，你要找跟咱们业务相关的经理，我就去找业务的。你要找销售相关的，我找销售的一个负责人。"这种思想是很通用的，也很形象，而且扩展性也非常的棒。

写完这个地方，对我们目前后面还有一堆东西，我先暂时不画。因为现在我们暂时还没跟数据库发生交互。等到数据库发生交互的时候，我们这地方还有一层，叫 Service 层或者叫 DAO 层。但现在我们还没涉及到数据库，所以说我先打到这个地方。

**那这地方还有一个东西，同学们，我们应该还有一个特别重要的东西，就是那个工具类。**我们一般还会单独地抽一个东西出来，叫 utils。比如说我把 `utils.go` 单独地写出来——就是把一些常用的工具类或者工具的函数、结构体抽取出来，等到别人要用的时候统一提供。

因为你想，同学们想，你在这个过程中不可避免的，就是在 `processor` 里面都会用一些通用的方法。比如说读文件或者读包、写包，肯定是通用的。通用的地方何必要写到这呢？甚至将来像这种消息的定义，大家都用的、共用的东西，我们就单独地抽出来。这样子如果你想用，你就从这里来用它就可以了。

**当然服务器端和客户端还有一个共用的，就是我们刚才写的 common 包。**因为它有时还有共用的一些协议，我们可以单独地再抽出来。比如说我这里面还有 common，如果将来要增加这个东西，我们在这儿加 message。这个包里面有服务器端和客户端共用的一些文件。比如说现在我们共用的就有这个 `message.go`。当然这后面还有很多共用的，比如说后边我们肯定在操作的时候要把这个信息抽取成一个 `User` 结构体，这 `User` 结构体肯定客户端和服务器端都是一样的，那肯定要这么做。

思路分析完毕。下一个工作就是把它给抽取出来。我先把这个思路给大家画到这里来，然后我们再写代码。这是我们的一个思路分析，就先给大家介绍到这里。

## 把一个大文件拆成一堆小文件：服务端分层改造实录
> 对应块：BLK124 | 覆盖分集：P323 | 块标题（分集名）：《321_尚硅谷_海量用户通讯系统-服务端结构改进》

思路前面已经说清楚了，下面我们来改。

但改的时候怎么改呢？这也涉及到一些方式和方法。注意听老师的思路是怎么样做的——这个也很重要。不相信你拿到这个东西，你通常不知道怎么改。就把这个东西给你了，你不知道怎么抽出来。**把一个大文件的东西抽取到各个小文件，这很有讲究，绝对不是说大家想的那么简单。**

### 步骤：先把空文件夹摆好，再往里剥

改的步骤应该是如此这般的。当然这个思路是韩老师的一个总结，可能不同的老师、不同的开发人员会有自己的一套套路，但我认为我这个思路可能更接近咱们刚刚入门的、或者工作了一两年有工作经验的人。

**第一步，先把分析出来的文件创建好。**你不是要抽取出来这些文件吗？先把这些文件写出来——虽然这文件是空的，先把文件放到不同的文件夹、放到相应的文件目录中。实际上就是包，因为**在 Go 里面文件夹其实就是体现出一种包**，一般一个文件夹就对应一个包。这样先有个大体的思路。

```text
server/
├── main/                  ← 主包，相当于界面层
│   ├── main.go            （已有，待剥离）
│   └── processor.go       ← 总控
├── process/               ← 处理器这一层包
│   ├── userProcess.go     ← 处理用户相关的
│   └── smsProcess.go      ← 处理短消息相关的
├── model/                 ← 目前还没写东西
└── utils/                 ← 放相应的工具文件
```

我们新建第一个包 `main`，这个一般会有一个主包，这个主包其实相当于是我们的界面层。

第二个包，根据我们刚才的分析，应该还有一层包叫 `process`，这个是作为我们处理器的这一层包。那么还有什么包呢？应该还有一个 `model` 包，但这个 `model` 包目前还没写东西。还有一个包就是我们的 `utils` 包，这个 `utils` 包就放我们相对应的这些个文件。

#### 别拽，用复制粘贴

然后不用犹豫，把你现在这个 `main` 扔到主文件夹下面去。因为所有的文件我们都应该放在一个文件夹下面便于管理。

**简单的思路：先复制一下。**我看有些同学喜欢直接往这儿拖一下，拖的时候当然看起来很简单——我曾经就有一个学生，他说就是因为不小心一拖，拖完了过后不知道拖哪儿去了，最后拖到垃圾桶里面去了。

所以我的做法是比较稳健的：**我先复制一下，然后再粘贴。我粘贴完了发现没问题，我再删**，尤其是对这些重要的文件。熟练了就没事，对这种重要文件大家尽量用我这个方法。拖过去一看真的没问题，OK，好，这个文件就可以干掉了，这样它比较稳当一点。当然你也可以用你比较快捷的方法。

`model` 现在还没东西，先暂时不写，一会儿就会用到了。

在 `process` 里面，根据刚才的分析应该有两个文件，对不对？一个是 `userProcess.go`，处理用户相关的；再一个 `smsProcess.go`，处理短消息相关的。它们都是 `package process`。

> **提前留坑**：因为将来我有个函数，先给大家把这个坑留在这儿——**这边会有包和函数同名的时候在同一个文件会出问题**，我先留在这儿吧，这个坑到时候再带大家挖起来。

第三个就是一个总控。这个总控放哪里呢？这个总控一般来讲它可以放在 `process`，**有些程序员也可以直接放在主包**——因为他认为这个总控和 `main` 关系很密切，它是 `main` 拿到了过后马上交给它，让它去指挥。所以有些程序员直接把这个总控放在 `main` 这个包下面也是可以的。那我就选用这种思想，把这个总控放到这儿，`processor.go`。

再来一个 `utils`。这个 `utils` 包下面我们就写一个自己的工具文件，专门放我们工具类、工具函数、方法的。第一步搞定。

### 为什么必须"先摆架子再搬东西"

### 分层 + 面向对象：先造 Transfer

主文件其实只留了一点东西，它拿到这个地方过后做了一个处理。它做一个处理干什么呢？它让它去得到一个连接，然后处理这个 server。现在这个结构就变化了——因为你现在的 `main.go` 的任务已经发生变化了。**你的任务就一件：监听、等待客户的连接、初始化的工作。**当然它在这里面肯定还有的事情就是它会调用 processor 的一个方法，让它去完成调度任务。

我们在调试的过程中要这样来处理：**先从最底层的走**，也就是说哪个被调用的多，就从这一层开始反着推过去，把代码写完。因为你首先，你这边都会调我，那我显然应该把它全部搞定，然后再搞定它。

> **结论**：分析是从上往下分析，写代码是从下往上写——**写代码跟分析的思路刚好是逆向的**。

#### Transfer：Conn 与 buf

那你作为一个传输者，应该需要哪些字段呢？**看起来这个简单，你看起来简单，去备课我不敢这么去讲**，因为你要分析这个东西怎么出来。

我认为你作为一个传输者，最重要的第一个：**连接必须要有**，没有连接你这么传呢？第二个，**你得给我一个缓冲 `buffer`**。这两个是必须的。

```go
type Transfer struct {

    buf  [1024]byte
}
```

这里我先暂时不考虑封装，各位同学，暂时不考虑封装——因为现在这个代码已经有点结构了，封装我们后面再说，先把它整过去先调一下。

只是说有两种管理形式：

| 形式 | 做法 | 特点 |
| --- | --- | --- |
| 集中公用 | 抽到 `common` 包里，大家都指向这一个包 | 干净，但**必须保证同步**，你那边更新了这边没更新也是麻烦事 |
| 各自一份 | 各写各的，上线前再整合 | 少了同步的麻烦，整合成本很低 |

有些项目经理喜欢第一种：你是公用的吗？你是公用的，对，好，没问题，我就把这个公用东西拿过来，`common` 拿过来，然后呢大家都指向这一个包。这是一种形式。

还有一种思路就是说，你有一份你公用的，最后到了这个要上线的时候大家再整合一下也可以。**所以说这个不是大事。**

### 新增 server.go：为了那根"不能断的连接"

我这里面还要设计一个东西，同学们，还有一个特别重要的文件要出现了。这个文件呢以前是没有的，但是我要把它分析出来。

大家看，在这里呢我会新增一个文件，这个文件呢我把它起名叫 `server.go`。

那这个 `server.go` 呢可以理解成这样一种含义：**因为你将来这个客户端登录以后，你不会马上退出。你登录成功过后你退出干啥？你有病啊，对不对？**你刚好看上去了，甚至没聊天你要跑了。

所以这个 `server` 呢我们可以理解成它要完成这样几个任务：

#### 任务一：显示登录成功的界面

第一个任务，它要显示登录成功的一个界面，必须显示出来。

#### 任务二：起一个协程，保持和服务器端的通讯

第二个，它有一个特别重要的能力。大家想，你上线以后，是不是别人可能跟你通讯呢？跟你聊天？还有可能是你的好友上线了，你的好友离线了，甚至有一个好友群发一个消息，你是不是这个客户端这边应该拿到这个消息啊？你必须得做这个事情。

**那么你之所以能够拿到这些消息——你连接已经成功了，难道你会反复地去取吗？显然不可能。**

所以说你这还有一个任务就是保持和服务器端的一个通讯。也就是说它这边会起一个协程。**它为什么要起协程？它这边必须要启动一个协程。**这个协程干什么呢？就是不停地在跟服务器之间进行一个交互。比如我不停在读——你有没有给我发东西啊？你如果有发的话，我就会体现在这个界面上。

你看你为什么你上了 QQ，你上线过后，等到你的好友上线，你"嘟嘟嘟、嘟嘟嘟"就响了？它怎么来的呀？那肯定是——你有没有再次登录啊？那肯定是你的客户端登录成功以后，它一定会在底、在偷偷地跟你再进行这个服务器的交互。

所以你看你上一个客户端，你会发现你流量本身没有用，但下面不停地在传输。它干什么事啊？**一直在跟服务器保持交流呢。如果服务器有东西推过来，它就会展现在你的页面上。**

#### 任务三：把推送的消息显示到界面上

第三点，就是当读取到服务器端发送的消息后，就会显示在客户端界面上。

你比如说你的好友上线了，打个比方，你的好友上线了，你这边读到了，读到过后呢你就把这个好友提示一下，"嘟嘟、嘟嘟"——当然我这个"嘟嘟"肯定发不出来了，就是说你可以给它一个文字打出来说"你的好友上线了"。

**因为你后台这个没死掉嘛，所以说这个地方很重要。**

那也就是说将来还有一个逻辑就是：它一旦登录成功以后呢，我让它转到它。它是这么一个关系。

### 顺手留一条：客户端的"数据保存"

因为这个客户端它比较简单，客户端一般不是用于数据库。但是也有很多东西呀。

**比如说你客户端一旦退出，会不会保留一些东西？**你们有没有发现你跟腾讯聊完天过后，你会发现你的聊天记录下次打开还有啊。

#### 一个 for 循环读到地老天荒

```go
func serverProcessMes(conn net.Conn) {
    for {
        tf := &utils.Transfer{
            Conn: conn,
        }
        mes, err := tf.ReadPkg()
        if err != nil {
            fmt.Println("服务器端出错了，读出错 err =", err)
            return
        }
        fmt.Println("message =", mes)
        // 如果读取到了这个消息，那么就是下一步处理逻辑了
    }
```
