## 接口：定一个规范，谁来做都行
> 对应块：BLK79 | 覆盖分集：P214-P217 | 块标题（分集名）：《213_尚硅谷_接口介绍和快速入门》

面向对象的三大特性我们讲了封装、继承，这两块说完了，按理说现在应该讲多态。

**但我先讲接口。**因为在 Go 中，多态这个特性主要是通过接口来实现的——如果离开了接口，多态这个特性其实讲不明白。所以我们先讲接口，再讲多态。

### 为什么需要接口：USB 插槽

为什么需要接口呢？我拿一张图来说明，它比较形象地说明了现实生活中的接口。

现实生活中我们有电脑，电脑里面都有一个叫 **USB 接口**。假设你有手机、有相机，当你把手机和相机插接到这个接口的时候，计算机就会来识别你是什么设备，然后就开工了。

**对于这个手机和相机来说，它并不关心自己是什么**，它只要把自己通过 USB 线插入到接口里面，计算机就能识别它，就能为它工作。

USB 插槽就是现实中的接口——你可以把手机、相机、U 盘都插在这个 USB 插槽上，而不用担心哪个插槽是专门插哪个的。对于这个接口来说，**我并不关心你插的是手机还是相机，我不管**，只要你把这个给我插上了，我就能识别你。

**它这个接口是有自动识别的功能。**为什么？因为 USB 插槽的厂家和各种设备厂商，他们都遵循了统一的规则、统一的尺寸和排线。

我们体会一下这种感觉：**一个接口就可以搞定所有的设备。**这种现实生活中的接口其实是非常有意思的一种东西。

那这种设计需求，在 Go 编程中是不是也大量存在呢？——**告诉大家，是大量存在的。**

我曾经说过一个程序就是一个世界，现实中存在的情况在程序中也会出现。那我们就用程序来模拟一下前面的应用场景。

### 快速入门：写一个 USB 接口，让手机和相机都插上去

新建一个文件夹 `interface_demo`，写一个 `main.go`。

#### 接口长什么样

首先声明一个接口。有些人喜欢把"声明"叫"定义"，也是一个意思。

```go
type Usb interface {
	Start()
	Stop()
}
```

这个接口叫 `Usb`，根据刚才那张图——USB 接口。里面我们简单地模拟一下：一个外设插入的时候它就开工，拔出来的时候它就停止工作，所以声明两个方法 `Start()` 和 `Stop()`。

**注意，这里面就是接口的两个方法，而且都是没有实现过的。**

顺便说，Go 标准库里的接口非常多。你在文档里随便找一个，看它就是一个接口：`type xxx interface { ... }`，这是接口的名称，这是接口的类型，然后里面有一堆方法。有返回值的方法就要把返回值写出来，我这没有返回值，所以我就没有写。

#### Phone 和 Camera 各自去实现

这是一个接口，那么现在我们需要写两个结构体：一个是手机 `Phone`，一个是相机 `Camera`。

手机这个结构体里面暂时没有什么字段，我直接实现方法。让它实现 `Usb` 这个接口的方法——接口的方法不是有两个吗，那我就实现它。怎么实现？跟前面一样：

```go
type Phone struct {
}

func (p Phone) Start() {
	fmt.Println("手机开始工作")
}

func (p Phone) Stop() {
	fmt.Println("手机停止工作")
}
```

**这个地方我们就不用星号了**，直接 `Phone` 就行，接收者简写一个 `p`。方法名要有，保持一致，没有返回值。

那么现在这个 `Phone` 就实现了 `Usb` 接口的两个方法。**实现了这两个方法，那么这个 `Phone` 的结构体对象实例，其实就可以当做这个接口来使用了。**

相机一样道理，为了省事粘贴一份，改成 `Camera`、接收者改成 `c`：

```go
type Camera struct {
}

func (c Camera) Start() {
	fmt.Println("相机开始工作")
}

func (c Camera) Stop() {
	fmt.Println("相机停止工作")
}
```

现在大家可能还没体会到接口的好处——你看我们写了两份：`Phone` 实现了两个方法，`Camera` 也实现了这两个方法。

那接下来再写一个计算机 `Computer`：

```go
type Computer struct {
}

// Working 这个方法接收一个 Usb 接口类型的变量
func (c Computer) Working(usb Usb) {
	usb.Start()
	usb.Stop()
}
```

**大家看到这是什么意思没有？**我这个 `Working` 方法可以接收一个接口类型的参数，就是 `Usb` 这种接口类型。只要是实现了这个接口的，你都可以给我传给我。

这里我要把一个特别重要的概念说清楚：

> **定义**：所谓"实现了 Usb 接口"，其实就是指**实现了 Usb 接口声明的所有方法**。如果别人说某个类型实现了某个接口，言外之意就是它把这个接口里面声明的所有方法都实现了。

我这个 `Camera`、这个 `Phone`，是不是已经把接口里面的 `Start` 和 `Stop` 都实现了？是的，所以它们就实现了这个接口。大家看，`usb.Start`、`usb.Stop`——**我是通过接口来调用 `Start` 和 `Stop` 的，是通过 `Usb` 这个接口变量来调用的。**

#### 跑起来：它真的"自动识别"了

测试的时候要创建相关的结构体变量：先创建一个 `Computer`，再创建 `Phone` 和 `Camera`。

然后关键点来了：

```go
func main() {
	computer := Computer{}
	phone := Phone{}
	camera := Camera{}

	computer.Working(phone)
	computer.Working(camera)
}
```

大家有没有感觉到，好像是**把这个手机插入到了这个接口**？我把 `Phone` 传进去了，接口就会去调用 `Start` 和 `Stop`。至于你这个 `Start` 和 `Stop` 怎么实现的，那就根据你的 `Phone` 怎么写的。

跑起来：

```text
手机开始工作
手机停止工作
相机开始工作
相机停止工作
```

**我传的是 `Phone`，它就调的是 `Phone` 的方法。**我把这 `Camera` 也传进去，它会自动识别——**看到没有？自动识别到这是相机来了，它就会去调相机的这个方法。**

是不是有点像我们刚才说的那个应用场景？当我们把手机插进去，它识别是手机；当我们把相机插进去，电脑能识别是相机。

通过这个案例，大家有什么感觉？**当我们去定义一个接口，把这些方法定好，然后让别的结构体或者变量来实现它，我们就可以工作了——是不是特别方便？**

这种应用场景就叫做**高聚合、松耦合**，或者说松耦合、高内聚的一种编程思想。大家可能一时半会儿还理解不到，我先整理一下，后面我们会逐步一层一层往里面深入展开。现在还只是一个入门，因此细节我还没有谈。

> **提示**：这段代码虽然很简短，但**其实已经体现出多态的影子了**。当我给它传一个 `Phone`，它就知道你是 `Phone`；当我传一个 `Camera`，它就知道是一个 `Camera`。`Usb` 随着你传入的参数类型不一样，能体现出不同的状态——**这不就是多态吗？**只是我们现在还没有把这个概念深入剖析进去，但接口编程的雏形、大体结构已经出来了。

### 接口的概念和基本语法

#### 接口里只能有方法，不能有变量

先把这个概念再说明一下。

**`interface` 这个类型就是接口类型，接口里面可以定义一组方法，这些都是不需要实现的。**而且——**`interface` 不能包含任何变量**，这点大家记住。

我们在别的编程语言里面，接口是可以有变量的，或者叫常量。**但在 Go 里面的接口，它是不允许有任何变量的，不管什么变量都不能有。**

然后到某个自定义类型——比如结构体 `Phone`——需要使用的时候，再根据具体情况把这些方法写出来。写出来，这就叫实现这个方法，叫实现。

> **易错点**：这里特别强调一下——**接口里面没有任何变量**。写一个成员变量进去是语法错误。

#### 基本语法长这样

```go
type 接口名 interface {
	Method1(参数列表) 返回值列表
	Method2(参数列表) 返回值列表
	...
}
```

`type` 和 `interface` 是关键字。里面你可以声明很多的方法：方法名、参数列表、返回值列表。**这个部分叫函数的签名**，函数的签名要跟接口里的完全保持一致，不能不一样，一定要一样。

前面 `Usb` 是不是就声明了两个方法？`Start` 和 `Stop`。但我们的方法特别简单，没有形参也没有返回值。

那什么叫实现了接口呢？有两层含义：

```go
func (自定义类型) MethodName(参数列表) 返回值列表 {
	// 方法的具体实现
}
```

**第一层：把这个方法具体的内容写出来。第二层：必须把所有方法都实现了。**

你不能说我只把接口里面的一个方法写出来了，就认为我实现了这个接口，这是不对的。它是要把这个接口里面**所有的方法**都实现了，我们才叫实现了这个接口。

自定义类型可以是任意的，比如前面的 `Phone`，也可以是 `Camera`，完全是你自己定义的。A 自定义类型可以实现这个接口，那 B 自定义类型也可以。

#### 小结说明：两条硬规则

**第一条：接口里所有的方法都不能有方法体。**

你不能在里面多写一句话说我来写一点东西在里边，这个不行。你像这样写的话，它立马给你报错，语法出错。**接口方法是不会有方法体的。**

**第二条：在 Go 中不需要显式地实现这个接口。**

大家有没有发现一个特点？我们写一个 `Phone`，又写了一个 `Camera`，去实现这个方法，**其实你都没有感觉到你实现这个接口了。**

为什么？这就好像你给这个结构体写了一个方法而已，你都不知道这个方法是属于 `Usb` 的。它并没有体现出这个方法是属于 `Usb` 接口的。

你不像以前我们写的代码。比如在 Java 里面，你写一个类：

```java
class A implements Usb
```

在 Java 里面它要明确指定这个类实现了这个接口。**但是在 Go 里面，它都不知道要去指定哪个接口**，它只是说我把这个方法实现了。那你只要把这个方法实现了，这个接口就实现了。

> **结论**：只要一个变量含有接口类型中的所有方法，那么这个变量就实现了该接口。**因此在 Go 里面没有 `implements` 这样的关键字。**

我再问大家一个问题，注意听：**假设我有一个接口叫 `Usb2`，它这里面也有这两个方法。请问 `Phone` 和 `Camera` 有没有实现 `Usb2` 这个接口呢？**

**实际上它也实现了。**因为 Go 里面实现接口是**基于这个方法的，而不是基于接口本身的**。你这个接口叫什么名字它并不关心，它只要把里面的方法给你实现了，自然就实现这个接口了。

也就是说，我们这样一改，就意味着这个 `Phone` **既实现了 `Usb` 接口，又实现了 `Usb2` 这个接口。**

**这在 Java 里面是做不到的。**因为 Java 是显式实现，它必须指定一个 `implements` 哪个接口；你不可能同时实现两个接口。

我再问一个问题：**如果 `Usb2` 里面有三个方法，而我只实现了两个方法，代码能不能跑？**

跑一下，它果然报错了：`cannot use phone (type Phone) as type Usb2 in value`。为什么？因为你有一个方法没有实现。

**但你把这个 `2` 去掉，它又能跑起来了。**你看多灵活！体会一下 Go 接口编程的这种灵活性，它的耦合度真的是很低，甚至比 Java 面向接口编程还要松散。**所以它就是基于方法的。**

### 高内聚、低耦合：我在用友遇到的一件事

接口方法都没有方法体，接口体现的其实是一种程序设计思想——**高内聚、低耦合。**

什么叫高内聚？**就是它能够把自己的代码全部写到函数里边去。**什么叫低耦合？就是程序之间的耦合性降低了。

我给大家举个例子。以前参加工作的时候，我是在用友，刚入职的时候做过三个月的测试，前期要求你做一段时间测试，然后再去做开发。当时就遇到过这么一个情况。

**你发现一个 bug，把 A 程序员找过来说："小 A，你看你这个程序有问题。"**

小 A 回去检查了一下，告诉你说："对不起，这个错真的不是我的错，因为我是调用了 B 写的代码、写的一个函数，结果是他的错，所以这个程序错误你要去找 B 程序员。"

于是测试人员就去找 B。B 说："真的，我回去检查了一下，真的也不是我的错。为什么呢？因为我调了 C 程序员写的一段代码、写的一个函数，结果是他的问题。"

你找到 C，C 又说什么呢？"真的不是我的错，因为我调用了 A 程序员写的一个函数。"

**你看，这样就形成了一个循环。这种代码是特别不希望在实际开发中出现的，你找不到这种东西。**

因为在实际开发中我们尽量需要的是：**你的代码错误就出现在你本身写的这段代码里面去，不要去波及到无辜。**

还有一例子更形象。以前我们最早参加工作的时候，有些程序员在一个函数里边开辟了一段内存，他把这个指针传到另外一个函数里边去——**他在一个函数里面开了内存，把指向这块内存的地址传给下一个函数，然后他在那个函数里面把内存给 `free` 掉。**

**你想这多可怕！这个就叫耦合性很强。**因为你在这开的内存，原则上说你用完了就自己把它 `free` 掉。结果有些程序员在这函数里面开了内存，把指针传给下一个函数，让别人的函数去 `free`。那别人可能不太知道你这有块内存没有释放。

**这种代码就很垃圾。**所以说接口的出现，它可以解决一个高内聚、低耦合的问题，这样的代码就很好。

后面几乎我们在用 Go 开发的时候，**这个接口是无处不在的。**

### 什么时候用接口：几个应用场景

对于刚学接口的同学来说，理解接口本身并不难——从语法层面上说，不就是那么点东西吗：定义一个接口，声明一些方法，别的自定义类型去实现它，我们就可以用了。

**但是初学者最麻烦的是：不知道在什么地方去用它。**大家是不是有这种感受？**什么时候去用它，这一点其实对我们来说是比较困难的。**

我举几个场景。

#### 造飞机：专家定规范，别人来实现

现在美国要去制造轰炸机，还有武装直升机。**专家只需要把飞机需要的功能还有规格定下来就可以了，让别人去实现。**

这就好比我们要去写一个结构体，这个结构体里面有些方法，方法很多。**如果都让一个程序员去写，肯定是不太好的。**我们希望让每个人都动起来，于是项目经理定义一个接口，然后大家去实现这个接口就完事了。

这样可以很方便地去管理和控制项目的进度，而且能够做到规范化开发。**接口就体现出它的强大了——我只需要定规范，而别的人去把这个规范实现。**

#### sort 包：接口早就用在你身上了

我们自己的代码里有一个 `sort` 包，这个包里面有一个方法叫 `Sort`。大家看这个 `Sort` 里面有一个 `data`，这个 `data` 是一个 `Interface`。

什么意思呢？**你只要想去对它进行一个排序，只要实现了这个接口就可以了。**点进去看这个接口是什么，你就明白了：

也就是说，你只要给它传一个**实现了 `Interface` 接口的类型**——把里面的 `Len`、`Less`、`Swap` 这三个方法实现了——你就可以去调用 `sort` 包里面的 `Sort` 方法。

**只要你传进去的变量实现了 `Len`、`Less` 和 `Swap` 这三个方法，传进去过后，它自然就给你排序了。至于它怎么排序你就不用去管它了**，只要你实现这个接口，`Sort` 方法本身就会帮你把排序完成。

大家先体会一下：我定义一个接口，里面有这么三个方法；你只要找一个结构体或者某种自定义类型把这三个方法实现了，然后传到 `Sort` 方法里面去，顺序就给你排好了。

**包括你的结构体变量数组，它也可以实现，这就很厉害了。**

#### 项目经理：定三个接口，三个人同时开工

现在有一个项目经理，管理了三个程序员。我们需要共同开发一个软件，**为了控制和管理软件，项目经理可以定一些接口，然后让程序员具体去实现。**

比如我现在有这么三个接口。定义好之后，我让 A 程序员去实现接口一，让 B 程序员去实现接口二，让 C 程序员去实现接口三。那是不是就意味着**项目经理只需要花一部分时间把接口定好，余下的事情就让程序员 A、B、C 三个程序员去共同完成？**

这样有什么好处呢？

- **我可以控制和管理软件的开发进度。**三个人一起来开发，肯定比项目经理一个人来做速度要快一些；
- **而且因为接口定好了，每一个程序员写的函数做什么事情都已经规定好了，再怎么出偏差也不会差到哪里去。**

所以接口还有利于我们去控制和管理软件的开发，同时也把规范管理起来了。

### 注意事项和细节

接口的注意事项我一共总结了十个，分成两个部分来讲。这一块是前五个。

#### 接口本身不能实例化

**接口本身是不能创建实例的。**也就是说，接口它本身不能定义一个变量，你不能直接用接口来创建一个变量。

我们举个例子。干脆新建一个文件 `details`，新建 `main.go`：

```go
type AInterface interface {
	Say()
}

func main() {
	var a AInterface
	a.Say()
}
```

这样直接写了过后，其实它是没有什么东西的。运行一下看它提示什么——直接报错了，提示**无效的地址，也是个空指针**。也就是说你直接用这个接口去调它是肯定调不起来的，因为这个方法都没实现过。

那它怎么用才可以呢？**它自己不能实例化，但是它可以指向一个实现了该接口的自定义类型的变量。**

比方说我这里有一个结构体叫 `Stu`，我让它来实现这个接口：

```go
type Stu struct {
	Name string
}

func (stu Stu) Say() {
	fmt.Println("Stu Say()")
}
```

然后：

```go
func main() {
	var stu Stu
	var a AInterface = stu
	a.Say()
}
```

这个时候就可以调用起来了。这个结构体变量既然实现了 `Say` 方法，它就实现了这个接口，于是我把这个变量交给它是可以成功的。然后再通过 `a` 去调，它就把 `Stu` 里面的 `Say` 方法调起来了。运行看效果，没问题。

**但有一点：如果你没有实现这个方法，那是不可以给的。**比如我把 `Say` 方法注释了，这样给它就会报错：

```text
cannot use stu (type Stu) as type AInterface in assignment:
stu does not implement AInterface (missing method Say)
```

> **结论**：接口本身不能实例化，但**可以指向一个实现了该接口的自定义类型的变量**——前提是这个变量对应的类型实现了对应的方法。

另外还有三条一起说了：接口中所有的方法都没有方法体，前面已经讲过；在 Go 中一个自定义类型需要把某个接口的**所有**方法实现，我们才说它实现了这个接口，**缺一不可**；一个自定义类型只有实现了某个接口，才能把它的实例赋给这个接口类型。

#### 不只是结构体：任何自定义类型都能实现接口

第五条比较重要，而且经常作为一个面试题：**只要是自定义数据类型，都可以实现接口，而不仅仅是结构体类型。**

我们前面都是用结构体这种类型来实现接口的，但实际上它不一定是结构体。

比如我这里定义了一个类型叫 `integer`，它是 `int` 类型的：

```go
type integer int

func (i integer) Say() {
	fmt.Println("integer Say i =", i)
}
```

我也可以让它来实现这个接口。此时此刻 `integer` 这个类型的变量也就实现了这个接口。怎么体现呢？

```go
func main() {
	var i integer = 10
	var b AInterface = i
	b.Say()
}
```

为什么可以？因为 `i` 对应的类型叫 `integer`，`integer` 又实现了 `Say` 方法，那就间接地实现了 `AInterface` 这个接口。通过 `b` 来调用 `Say` 方法也是成功的，输出：

```text
integer Say i = 10
```

**也就是说，普通的非结构体的自定义类型，其实也可以实现接口。**只要把它的方法实现了，就实现了这个接口。

后面有些程序员会针对某一个自定义的非结构体类型去给它实现接口。

**关于接口注意事项的第一部分就说到这里，剩下的几个点我们放到下一部分讲。**

> **承前启后**：上一节讲完「接口：定一个规范，谁来做都行」，下一节接着讲「接口的后五条细节：一个类型实现多个接口，空接口能接一切」。

## 接口的后五条细节：一个类型实现多个接口，空接口能接一切
> 对应块：BLK80 | 覆盖分集：P218-P219 | 块标题（分集名）：《217_尚硅谷_Go接口注意事项和细节(2)》

接口的注意事项一共十个，上一部分讲了前五个。这一部分讲后五个，最后再把三道判断题过一遍。

### 一个自定义类型可以实现多个接口

第六个：**一个自定义类型可以实现多个接口。**也就是说我这一个自定义类型，我可以既实现 `A`，又同时实现 `B`。

举个例子。还是在这里写：

```go
type BInterface interface {
	Hello()
}

type Monster struct {
}

func (m Monster) Hello() {
	fmt.Println("Monster Hello()~~")
}

func (m Monster) Say() {
	fmt.Println("Monster Say()~~")
}
```

前面已经有一个 `AInterface` 了，里面有一个 `Say`。我再写个 `BInterface`，它有一个方法叫 `Hello`。

`A` 接口和 `B` 接口，一个是 `Say`，一个是 `Hello`。现在我有一个类型 `Monster`，我想让它**既实现 `B` 接口又实现 `A` 接口**，那我就把两个方法都写出来——`Hello` 写完，接着再实现 `Say`。

**此时此刻，这个 `Monster` 结构体就同时实现了 `A` 接口和 `B` 接口。**

怎么证明它实现了两个接口？可以这样写：

```go
var monster Monster
var a2 AInterface = monster
var b2 BInterface = monster

a2.Say()
b2.Hello()
```

我把这个 `Monster` 实例赋给 `AInterface`，没问题；再把它赋给 `BInterface`，也没报错。而且我还可以把它调起来：用 `a2` 调 `Say`，用 `b2` 调 `Hello`。

跑一下，`Monster` 把 `Say` 调起来了，也把 `Hello` 调起来了。也就是说，我们在同一个 `Monster` 上实现了两个接口。

从这几个细节分析里你会发现，**Go 里面这个接口的实现非常灵活，耦合性很小**。

它为什么灵活？**因为它最大的差别在于：它是基于这个方法来实现这个接口的。**而像 Java、.NET 或者 PHP，它们是显式实现——必须指定我去实现哪一个接口。**但对 Go 来说，它根本不关心你是实现哪个接口，它只关心你写了哪个方法。**

> **易错点**：这里有个细节大家注意——**你交给 `A` 接口之后，`a2.Say()` 可以，但你不能用 `a2` 去点 `Hello`**，因为你手上这个接口里面是没有 `Hello` 方法的。接口变量能调哪些方法，取决于它的静态类型是哪个接口。

### 接口里不能有任何变量

第七个：**Golang 的接口中不能有任何变量。**这一点大家一定要清楚。

因为有很多 OOP 语言里面，接口里面是可以有常量的，**但是在 Go 里面，它不准有任何变量。**

我不在这里举例了，你可以自己试一下：在 `AInterface` 里面随便写一个成员，比如 `Name`，或者随便写个什么类型，你这一保存就报错了。它会报一个语法错误——**不管是什么类型，它都不让你放进去，不能放变量。**

### 接口之间也能"继承"，而且必须全部实现

第八个：**一个接口可以继承多个别的接口。**比如 `AInterface` 可以继承 `BInterface` 和 `CInterface`。

这时如果要实现 `AInterface`，就必须把 `B` 和 `C` 的接口方法也全部实现。也就是说，**接口之间也可以有这个继承的关系**。

代码越来越多了，我们另建一个文件夹 `details2`，写一个 `main.go`：

```go
type BInterface interface {
	test01()
}

type CInterface interface {
	test02()
}

type AInterface interface {
	BInterface
	CInterface
	test03()
}
```

看这个 `AInterface`：它里面继承了 `B` 接口和 `C` 接口，同时它自己有一个方法叫 `test03`。

**这个时候如果你要去实现这个 `AInterface`，就意味着你要把 `test03`，还有 `B` 和 `C` 里面所有的方法，也都要实现。**

我们用 `Student` 来实现它：

```go
type Student struct {
}

func (stu Student) test01() {}
func (stu Student) test02() {}
func (stu Student) test03() {}

func main() {
	var stu Student
	var a AInterface = stu
	a.test01()
}
```

注意听——**你不用去管这个 `test01` 是谁的**。你不用显式地告诉别人说这个 `test01` 是 `A` 接口的、这个 `test02` 是 `C` 接口的，你不用这样子，**你只要把它的方法找到就可以了**。

跑一下，代码没有报任何错误，说明成功了。

**但是你试试看：如果你把某一个方法注释了，这个地方一定会报错。**比如把 `test03` 去掉，或者把 `test01` 去掉，都会报错。

提示的信息是这样的：不能够使用 `Student` 这个类型赋值给 `AInterface`。为什么不可以？因为 `Student does not implement`——它没有实现 `A` 接口里的某一个方法。

> **结论**：一定要把它所有的方法都实现，**这是没有办法的，就是强制要求，缺一不可**。

我再问大家一个问题：**当我们这样做过了过后，请问这个 `Student` 它是不是也同时实现了 `B` 和 `C`？**

肯定也实现了——我不仅实现了，我还多了几个函数，肯定嘛。你把 `Student` 赋给 `BInterface` 也是没问题的。

但**你在调的时候，你只能调 `BInterface` 里面的 `test01` 方法，你不能调 `test02`**，明白吧？

也就是说，`Student` 这个结构体类型，实际上把 `A`、`B`、`C` 三个接口**全部实现了**。这一点大家一定要认真理解。

### interface 是引用类型

第九个细节也很重要：**`interface` 类型默认是一个指针，也就是说它是引用类型。**

这一点大家一定要知道。

**如果没有 `interface` 初始化就使用，那么它会是一个 `nil`**——就是刚才我们所说的，如果你没初始化就直接用 `interface`，直接就是报一个错误。

还有一点：`interface` 是引用类型，**跟我们前面的结构体不一样**。你看我们前面那个 demo，我们不是把 `Phone` 还有 `Camera` 传给了 `Usb` 这个接口吗？**你传的时候其实是按引用方式传过去的**，因为接口是引用类型。

如果面试官问到你——说接口是什么类型的？是值类型还是引用类型？**那你要非常准确地回答他：接口就是引用类型。**那它当然接收的其实是个地址了。

**接口，我再说一遍，是特别重要的知识点。在面向对象里面，它几乎就是核心中的核心了。**

### 空接口：什么都能往里装

还有一点，也是非常重要的一个知识点：**空接口。**

空接口就是 `interface{}` 这种，**它直接就是一种数据类型**。因为这个空接口**没有任何方法**，因此**所有的类型都实现了空接口**。

换言之就是：**我们可以把任何一个数据类型的变量赋给空接口。**

如果你有一个参数，这个参数是个空接口的形参，**它就意味着它可以接收任何一种数据类型**。这个特性我们后面要反复地提到，用得非常非常多。

举个例子。我定义一个空接口：

```go
type T interface {
}
```

**我没有给它任何的方法。**那大家想一想，因为我没有给它任何方法，我这样写可不可以？

```go
func main() {
	var stu Student
	var t T = stu
	fmt.Println(t)

	var t2 interface{} = stu
	fmt.Println(t2)
}
```

**显然这是可以的。**为什么？因为你这个 `t` 是个空接口，那就说明我可以接收任何数据类型。**你也可以认为 `Student` 就默认实现了空接口。**

第一种写法输出的就是一个空的 `{}`（因为 `Student` 本身是个空结构体）。第二种写法用 `interface{}` 直接当类型用，输出也完全一样。

那它能不能装别的东西呢？可以。比如：

```go
var num1 float64 = 8.8
num1 = num1

t = num1   // T 是个空接口，可以
t2 = num1  // t2 的类型也是空接口，也可以
```

跑一下，就输出了 8.8。**这两个都是空接口类型，所以随便给。**

> **结论**：因为空接口没有任何方法，所以**任何一个类型都实现了空接口**，即我们**可以把任何一个变量赋给空接口**。这个特性我们在后面用得非常多非常多，因为它可以接收任何一种数据类型。这一点大家一定要重视。

### 本讲提到的题目

三道判断题，我们一道一道过。

#### 题目一

接口 `AInterface` 里有 `test01`、`test02`；接口 `BInterface` 里有 `test01`、`test03`。结构体 `Student` 把这三个方法都实现了。现在创建 `stu` 变量，然后 `stu` 赋给 `A` 接口、`stu` 赋给 `B` 接口。这两句话 OK 还是不 OK？

#### 解析

完全 OK。

因为 `stu` 对应的类型是 `Student`，而 `Student` 确实把 `A` 和 `B` 的方法都实现了。**尽管两个接口里都有 `test01`，也无所谓**——`test01` 是 `A` 的还是 `B` 的，根本无所谓，它关心的就是方法有没有实现、方法是不是一致。

注意，**这个方法一定要完全一样才行，包括参数类型这些都要一样**。所以我们可以理解成：它既实现了 `BInterface` 里的 `test01`，又实现了 `AInterface` 里的 `test01`。

#### 答案

正确。这段代码编译通过。

> **结论**：在实现接口的时候，**它的标准只看方法，而不看它属于哪一个接口。接口是基于方法来实现的。**

#### 题目二

接上一题，现在再定义一个接口 `CInterface`，把 `AInterface` 和 `BInterface` 两个接口都继承进来。这一段代码有没有错误，为什么？

#### 解析

**这个问题就比较严重了。**

因为 `AInterface` 和 `BInterface` 里面都有 `test01`，那就麻烦了。**这相当于在 `CInterface` 里面有了两个 `test01` 方法**，继承下来有两个完全相同的 `test01` 方法。

编译器不期望一个接口里有重复的方法，所以它不会通过。

用 `go run main.go` 跑一下，它会报一个 `duplicate method test01`——重复定义的方法。

#### 答案

**编译错误。**因为 `CInterface` 里面有两个相同的 `test01` 方法，编译器不能通过，报重复定义错误。

> **结论**：接口之间不管是什么关系、继承多少次，**绝对不允许有相同的方法名**。

#### 题目三

接口 `Usb` 有一个方法 `Say`。结构体 `Student` 用 `func (this *Student) Say()` 实现了这个方法——注意接收者是**指针类型**。然后创建 `stu` 变量，再写成 `var u Usb = stu`。这段代码行不行？

#### 解析

**加一个星号和不加星号是有区别的。**如果你加了星号，就代表这是这个类型的指针类型；如果不加星号，才是结构体类型。

此刻这个 `stu` 是什么类型？它就是 `Student` 类型。而 **`Student` 这个类型并没有实现 `Say` 方法**——因为 `Say` 是用 `*Student` 的指针实现的。所以这个地方一定会报错。

编译器会直接告诉你 `Student` 没有实现 `Usb` 接口，并且会补一句 `Say method has pointer receiver`——**它自己告诉你应该给它传什么类型、告诉你要怎么改了。**

#### 答案

**应该改成加一个地址：**

```go
var stu Student
var u Usb = &stu
u.Say()
```

因为这个 `Usb` 接口是**用指针实现的**，所以传个指针进去就行了。其它调用没有变化，还是一样的——因为本身就是指针去实现这个 `Say` 方法，直接调它没毛病，运行结果也是正确的。

> **结论**：接口方法用什么接收者定义，就只能用相应的类型去赋值。**值接收者的方法，`T` 和 `*T` 都能满足；指针接收者的方法，只有 `*T` 满足。**第三道题错就错在把 `stu`（一个 `Student` 值）传给了只由 `*Student` 满足的接口。

## 把排序交给系统，把标准留给自己
> 对应块：BLK81 | 覆盖分集：P220-P221 | 块标题（分集名）：《219_尚硅谷_接口编程的经典案例》

前面我们把接口的基本语法、使用的注意事项都一一介绍过了，也带着大家做了课堂练习。但那些全是语法层面的东西——接口到底有什么用、为什么值得这么强调，说实话，到现在为止大家的认识还不够深刻，对不对？

语法讲完了，滋味还没尝到。这一讲我们不谈语法，谈应用。看完这个案例，你应该能真切体会到接口编程的妙处。

我们要做的事很具体：**实现对 `Hero` 结构体切片的排序**。也就是写一个 `Hero` 结构体，定义它的切片类型，然后对这个切片排序。就这么一件事，把接口的价值一次说透。

### 先从 int 切片说起

我们先做个引导。大家回忆一下，前面讲数组排序的时候用的是冒泡排序，还有印象吗？当时是先定义一个数组，当然也可以是切片。我以切片为例，把当时的场景再搭一遍。

```go
var intSlice = []int{0, -1, 10, 7, 90}
```

这个切片现在有序吗？显然没有。现在要求对它排序，你有两个办法：一种是自己写冒泡排序，一步一步怎么走，笔记里写得清清楚楚，这块我不再重复；另一种是用系统提供的方法。

我们看第二种。打开 Go 官方手册，进去有个 `package`，里面有个包叫 `sort`。点进去，里面有一个函数叫 `Ints`，文档写的是 `Ints sorts a slice of ints`——对一个 int 切片排序，默认升序，还带案例。

要用它，先引入 `sort` 包，然后：

```go
sort.Ints(intSlice)
```

把这个切片丢进去就完事了。

> **提示**：这里**不需要加地址**。前面讲变量的时候说过，切片是引用类型（引用类型包括指针、切片）。既然是引用类型，传进去的就相当于把 `intSlice` 本身交给了 `sort` 的方法，它在内部排完序，外面的 `intSlice` 立刻跟着变。

想深究的同学可以去点一下 `Ints` 的源码，它内部也是调 `sort` 包里的另一个方式完成的。

跑一下：

```bash
cd ../chapter11
cd exercise02
go run main.go
```

输出是 `-1 0 7 10 90`，有序了。

### 冒烟问题：结构体切片怎么排

到此为止一切都很平淡。现在我突然给大家出这么个问题：**请大家编写代码，对一个结构体切片进行排序。**

第一种思路，你当然还是可以用冒泡排序，大不了一个一个比较，也能实现。但我们出于通用性的考虑，希望还能用系统提供的方法。

系统真的提供了。就在 `sort` 包里，有一个方法叫 `Sort`，它接收一个 `Interface`。还记得 `Interface` 是什么吗？就是接口，前面讲过的。它接收的可以是**任何实现了这个接口的类型的变量**。

这个接口里有三个方法必须实现：`Len`、`Less`、`Swap`。

为什么是这三个？道理很简单——接口是我们（或标准库）定义好的，`Sort` 内部自然会去调用它们。你去看看源码就知道：`Sort` 里用到了 `data.Len()`，默认用的是 `quickSort`，也就是快速排序；`quickSort` 里会继续往下传 data，在里面就能找到 `Less` 和 `Swap`。

追进去你会发现，`quickSort` 的实现里有这么一层意思：如果 `Less` 返回真，就调用 `Swap` 去交换两个位置的元素。

> **结论**：只要你自定义的类型实现了这三个方法，就能直接交给 `sort.Sort` 完成排序。我不管你是什么类型——这就是接口的妙用。

道理讲清楚了，我们直接上手实现，不说废话了。这也是我们面向对象编程里的核心内容。

### 亲手实现一遍 Interface

**第一步，声明 `Hero` 结构体：**

```go
type Hero struct {
	Name string
	Age  int
}
```

字段是我自己定的，你随意。一个名字，一个年龄。

**第二步，声明这个结构体的切片类型。**注意听，是**切片类型**。为什么非要切片？因为只有切片里才能放多个 `Hero`。

```go
type HeroSlice []Hero
```

**第三步，把 `sort.Interface` 这三个方法实现出来。**接口的名字还真的就叫 `Interface`，没办法，它就叫这个名字，我们就实现它。

第一个，`Len`——返回集合的长度：

```go
func (hs HeroSlice) Len() int {
	return len(hs)
}
```

第二个，`Less`——文档写的是 `Less reports whether the element with index i should sort before the element with index j`，返回一个布尔值，意思是"下标 i 的元素是否应该排在下标 j 的元素前面"。

第三个，`Swap`——交换 i 和 j 这两个位置的元素：

```go
func (hs HeroSlice) Swap(i, j int) {
	temp := hs[i]
	hs[i] = hs[j]
	hs[j] = temp
}
```

为什么要自己写交换？因为快速排序过程中它会通过接口来调用你的 `Swap`，它只管喊，具体怎么换是你的事。

> **易错点**：接收者必须写成 `func (hs HeroSlice)`，不能写成 `func hs HeroSlice`——后者编译器会直接报 `return len, is not ...` 的语法错。

三个方法都写完了，就意味着 `HeroSlice` 实现了 `sort.Interface`，现在就可以交给 `sort.Sort` 了。

### 造点数据，看看效果

既然要排序，先得有数据。一个一个往切片里塞太麻烦，我们循环造 10 个：

```go
var heroes HeroSlice
for i := 0; i < 10; i++ {
	hero := Hero{
		Name: fmt.Sprintf("英雄%d", rand.Intn(100)),
		Age:  rand.Intn(100),
	}
	heroes = append(heroes, hero)
}
```

名字用 `fmt.Sprintf` 拼一个格式化的字符串，`%d` 后面接 `rand.Intn(100)`，这样名字就会变化。

> **提示**：`rand.Intn` 在 `math/rand` 包下，别导错包——是 `math/rand`，不是别的什么 rand。它返回一个 0 到 n 之间的随机值。

这里有个细节别忘：`append` 不会就地改掉原来的切片，它是**有返回值的**，你必须接住再赋回去：

```go
heroes = append(heroes, hero)
```

不接回去，就等于白做。

然后用 `for range` 把排序前的顺序打印出来看：

```go
fmt.Println("排序前", heroes)
```

跑起来你会看到年龄是乱的：87、59、18、40……一看就知道没序。

现在，神奇的事情发生了：

```go
sort.Sort(heroes)
fmt.Println("排序后", heroes)
```

它不报错。原因就是 `heroes` 的类型 `HeroSlice` 实现了那三个方法。

顺带给大家看一个反证：你要是把其中一个方法注释掉再来编译，它立刻报错——`HeroSlice does not implement sort.Interface`，缺哪个方法编译器会明确告诉你。缺的就是 `Swap` 那次。这个"少一个方法就编译不过"的机制，前面我们已经讲过好多次了。

跑出来是升序。

### 顺序由 Less 说了算

这里我要特别强调，因为这是整个案例的关键：**`Less` 就是决定你按什么标准排序的那个开关。**

`Less(i, j)` 的语义是：`i` 该排在 `j` 前面就返回 `true`。所以：

- 想按年龄升序（小的在前），就返回 `hs[i].Age < hs[j].Age`；
- 想按年龄降序（大的在前），就把比较号反过来，返回 `hs[i].Age > hs[j].Age`。

想清楚这一点，后面所有玩法都通了。而且你也不用死记这个语义——顺着 `quickSort` 的源码追进去就明白了：它判断 `Less` 为真，就调 `Swap` 把 i 换到 j 的位置上去，也就是把 i 挪到前面；为假就不动。也就是说，返回 `true` 的那一对，i 会被排到前面。

### 换个标准，只要改一行

现在我换一个要求：**我不想按年龄排了，我想按姓名排。**

改一行就够：

```go
return hs[i].Name < hs[j].Name
```

名字是 `Name`，比较照旧，小的在前，所以按名字升序。跑一下，排序后的名字果然是升序的。想要降序，把 `<` 改成 `>` 即可。

到这里好处还没完全显出来，我再往前推一步。

假设我还有一个结构体叫 `Student`，有名字、有年龄，再加一个成绩 `Score`。现在要求：定义很多学生放进切片，把这些学生**按成绩从低到高排序**。

你们想一想，是不是只要把上面这段代码复制一份，给 `Student` 的切片类型把三个方法实现一遍，就可以马上排序了？接口的妙用就在这：你只要实现了那三个方法，别的就交给 `sort` 去做。它内部怎么调用你的方法你不用管，而且人家写的代码效率肯定很高。

你可以这样理解：这种方式相当于给你开放了一个接口，你实现了，别人就自动按你指定的顺序、指定的字段帮你完成排序。特别漂亮的一件事。

而且条件还可以更复杂——比如名字结合年龄，想个办法返回一个布尔值，照样能排。

> **结论**：这就是接口编程的最佳实践——**把可以放开的部分做成接口留给别人，把最核心的代码握在自己手里**。`quickSort` 才是这段代码的核心，因为核心的排序算法应该交给写得好、效率高的人去写；能放开的是"长度是多少""按什么标准比""两个位置怎么换"，这三件事交给实现者，灵活度就极高。

为什么这三个方法适合放开？

- 放开 `Less`，别人才能告诉你按什么标准排；
- 放开 `Swap`，才能适配各种类型——因为它只给下标 i、j，不指定具体类型。你将来这个类型是 `Student` 还是别的，它不管；
- 而 `quickSort` 这种算法实现，不适合放开，放开就乱套了。

能放开的就放开，不能放开的就写进自己内部。这就是接口的体现，也是最经典的接口应用场景。

### 顺手带走一个面试题

刚才交换那三行其实有点繁琐：

```go
temp := hs[i]
hs[i] = hs[j]
hs[j] = temp
```

Go 语言开发里你会看到有人这么写，非常简洁的一句：

```go
hs[i], hs[j] = hs[j], hs[i]
```

完全等价：把 j 交给 i，把 i 交给 j，完事了。

那面试官要是出这么一道题，你能不能答上来？

```go
i := 10
j := 20
i, j = j, i
fmt.Println("i=", i, "j=", j)
```

请问此时 `i` 等于多少？发生交换了吗？等价的含义就是：把 j 给 i，把 i 给 j。所以此刻 `i` 等于 20，`j` 等于 10。跑一下验证，结果确实如此。

# 接口和继承：一只会爬树的小猴子

前面我们把接口的概念和应用都介绍过了，也写了不少案例。有些同学可能对"接口"和"继承"这两个概念容易混淆，我们来专门看一看它们之间到底是什么关系。

### 一只不安分的小猴子

我画一张图大家看：有一只老猴子，有一只小猴子，小猴子继承了老猴子。这是继承关系——假设小猴子继承了老猴子，那么老猴子所拥有的能力，包括它的字段、包括它的方法，就会**自动地**被小猴子继承。小猴子什么都不用做，就能拿到老猴子的字段和方法。这就是继承。

但有这么一种情况：小猴子不甘心于现状，它说"我除了会爬树，还想像小鸟一样飞翔，像鱼一样游泳"。那它就得去实现——通过**实现接口**的方式来增强自己的能力。

这样去理解：一个结构体继承了另一个结构体，就拥有了对方的字段和方法；但如果它还想扩展一些方法，**又不破坏已有的继承关系**，那就用实现的方式来做。小猴子通过努力去实现"飞翔"这个功能，通过学习去实现"游泳"这个功能。

> **定义**：接口是对继承的一种**补充**。

```text
                  ┌───────────────────────────┐
                  │   Monkey（老猴子）         │
                  │   字段：Name              │
                  │   方法：climbing()        │
                  └─────────────┬─────────────┘
                                │  匿名结构体嵌入
                                │  → 字段与方法自动获得
                  ┌─────────────▼─────────────┐
                  │  LittleMonkey（小猴子）   │
                  └─────────────┬─────────────┘
                                │  实现接口（不破坏继承）
                ┌───────────────┴───────────────┐
     implements │                               │ implements
   ┌────────────▼───────────┐     ┌─────────────▼──────────┐
   │  BirdAble             │     │  FishAble              │
   │  Flying()             │     │  Swimming()            │
   └───────────────────────┘     └────────────────────────┘
```

读图：横向那条线是**继承**，小猴子不写一行代码就拿到了 `Name` 和 `climbing()`；纵向那两条线是**实现接口**，飞翔和游泳是小猴子额外扩展出来的，`Monkey` 一行都没被改。

光这么一说可能还是不太明白，我们走代码。

### 走一遍代码

在 `chapter11` 里新建一个文件夹 `interface_vs_继承`，里面建 `main.go`。老规矩，包和 import 从上面复用。

先来个猴子结构体：

```go

	Name string
}

	fmt.Println(this.Name, "生来会爬树...")
}
```

猴子生来会爬树，所以给它绑定一个 `climbing` 方法。

再来一个 `LittleMonkey`，这里我复制一份偷个懒，改个名字，里面用**匿名结构体**继承 `Monkey`：

```go
type LittleMonkey struct {
	Monkey // 继承
}
```

我问大家：此刻创建一个 `LittleMonkey` 的变量，能不能用 `climbing` 方法？显然可以，因为它继承了。创建实例：

```go

	Monkey{
		Name: "悟空",
	},

```

`LittleMonkey` 里有一个匿名的 `Monkey`，我们直接把名字给它，"悟空"——大家都知道悟空很厉害，是个猴子。

调用 `monkey.climbing()`，跑一下，输出是"悟空 生来会爬树..."。

### 不能写在 Monkey 上的 flying

现在我要做扩展了。假如这只小猴子很想去学飞翔、学游泳，作为**设计者**，你会怎么设计这个需求？

有些同学说："老师，简单嘛，我直接在 `Monkey` 这一层给它加一个 `flying` 方法不就行了？"

可是你想一想，猴子本身是不会飞翔的。写一个 `flying` 方法显然不合理——只是说**小猴子这个结构体**比较特别，它希望有这样一个功能扩展；但你又不能把方法绑定到 `Monkey` 结构体上。为什么？因为猴子本身不会飞。

我既不想破坏继承的合理性，同时又希望 `LittleMonkey` 拥有 `flying` 功能，怎么办？**接口搞定。**

声明一个接口，只有一个方法 `Flying`：

```go
type BirdAble interface {
	Flying()
}
```

然后让 `LittleMonkey` 去实现它。注意这个结构体方法要提到前面去，因为 main 里要用：

```go
func (this *LittleMonkey) Flying() {
	fmt.Println(this.Name, "通过学习，会飞翔...")
}
```

跑一下，输出"悟空 通过学习，会飞翔..."。

**而原先的 `Monkey` 没有受到任何影响——这一点是关键。**

同样的做法再来一遍。这次想让小猴子像鱼一样游泳：

```go
type FishAble interface {
	Swimming()
}

func (this *LittleMonkey) Swimming() {
	fmt.Println(this.Name, "通过学习，会游泳...")
}
```

大家感受到它的灵活性了吧？再让 `monkey` 调用 `Swimming()`，输出"悟空 通过学习，会游泳了"。

### 两句结论

通过上面这段代码，我们得出两个结论。

**第一，继承是什么？**所谓继承，就是当 A 结构体继承了 B 结构体之后，A 结构体就**自动地**继承了 B 结构体的字段和方法，并且可以直接使用。

**第二，扩展怎么办？**当 A 结构体需要扩展某个功能、同时又不希望破坏这个继承关系时，去**实现某个接口**即可。

所以我们可以下一个总的结论：

> **结论**：实现接口这个机制，其实是对继承机制的一种**补充**。

它在设计层面是一种**解耦**的方式——在不破坏继承关系的前提下扩展结构体的功能。

面试官要是问你"实现接口和继承有什么区别"，你就按这个方式简单分析一下，他应该能理解。

```text
        （会念书）   │
                      └──────► 中学生
```

现在我提这么一个需求，请大家思考怎么实现：**足球运动员和大学生掌握英语。**

只有这两类人要学英语，别的都不要。

**第一种做法：直接写在 `运动员` 结构体里。**这显然有问题——写在 `运动员` 上，就意味着篮球运动员本身不想学英语、他不需要掌握这个技能，也被**被动地**接受了。同样，如果你把学英语写在 `学生` 结构体上，那中学生也破被动地要去学英语了。

所以你看，**用继承这种关系不太好搞定这种需求**。

**第二种做法：直接写在子类上。**在足球运动员上加一个学英语的方法，再在大学生上加一个学英语的方法，理论上需求是满足了。但大家有没有注意到这样有什么不好？至少有一点肯定不好——**规范性不好**。

足球运动员写这个方法，和大学生写这个方法，有可能规范就出现了偏差。因为你希望这个项目是有规范性的，你并不希望足球运动员的方法和大学生的方法名字不一样、参数不一样。对一个项目来讲，肯定希望有统一的规范性。

### 用接口，两个好处都有了

所以这个时候用接口来实现其实是特别好的。我定义一个"学习英语的技能"这样的接口，里面定义相关的方法，然后让足球运动员和大学生来实现这个接口就可以了。

这有什么好处？两个。

**第一，解耦。**我让足球运动员去实现这个接口，不影响篮球运动员，也不影响 `运动员`；我让大学生去实现这个接口，不影响中学生，也不影响 `学生`。所以它解耦了。

**第二，规范性得到了保证。**因为这个接口是**事先定义好的**。足球运动员实现的是这个接口，大学生也实现这个接口——同一个方法签名、同一个规范，规范性自然就得到了保证。

> **结论**：接口可以解决很多问题——第一，不破坏继承；第二，规范性能够得到保障。

大家可能目前还没有大量去使用接口，所以可能还没感觉到它的妙用。但的的确确，接口确实可以解决很多问题。

### 接口和继承，解决的问题不一样

接下来我们把这两者的关系再往深里挖一层。**接口和继承着重解决的问题是不一样的**，这句话你必须能回答上来——面试官很可能会问。

#### 继承的价值：复用性和可维护性

继承真正的价值，主要是解决**代码的复用性和可维护性**。

复用性怎么理解？我们让一个结构体去继承另外一个结构体，那么这个结构体里有些重复的代码就不需要重复再写一遍了，复用性就解决了。

可维护性怎么理解？比如说我让被继承的那一个增加一个方法，那么其他所有继承它的结构体也就相应地拥有了这个方法——**改一处，全都有**，可维护性当然就提高了。

#### 接口的价值：设计

接口的价值主要在于**设计**，这一点特别重要。

因为它设计好各种规范，说白了这些规范就是一堆方法。接口里面声明好这些方法，然后让其他自定义类型去实现这些方法就可以了。

特别是在 Golang 语言里面大家可以看到，讲接口最佳实践那个案例的时候，你应该已经感觉到了接口的威力——它可以设计好很多规范，你只要去实现这个接口了，"好，我就可以用了"。

#### 接口比继承更加灵活

第三点，接口比继承更加灵活。特别是在 Golang 里面，这个接口还是一种**很松散的实现机制**，所以它比继承更加灵活、更加方便。

打个比方：继承它满足的是 **is-a** 的关系。你有一个 `Person` 结构体，然后有个学生——`Person` 和 `Student` 是不是满足一个 is-a 的关系？学生是不是一个人？当然是。所以这两者容易构成继承关系。

但是接口只要满足 **like-a**，"像一个什么样子"就可以了。前面我们写了一个接口 `BirdAble`，然后有一个结构体叫 `LittleMonkey`——它们就可以。你不能说一个猴子是一只鸟，对吧？但你可以说一个猴子**可以像小鸟一样飞翔**。通过一种功能的扩展，让这个结构体的功能得到扩展，这是 like-a。

所以你们看，它们之间的关系要**弱于** is-a，是比较松散的一种关系。

#### 接口在一定程度上实现了代码解耦

这个就不多说了。特别是在 Golang 里面，它这个接口还是一种松散的实现，因为它**并不需要你去指定实现的是哪一个接口**，你只需要把这个方法实现出来就可以了。

大家回到前面的代码再看一眼：我们在 `LittleMonkey` 上定义了 `Flying` 方法，但我并没有在代码里写任何"我正在实现 `BirdAble`"的声明。它是基于这个方法、遵循接口里约定的签名，就算实现了这个接口。

所以接口在一定程度上实现了代码的解耦，非常的灵活。

### 三句话总结

关于接口和继承的关系，我们总结这么几点：

| 关系维度 | 继承 | 接口 |
| --- | --- | --- |
| 着重解决 | 复用性、可维护性 | 设计（事先定好规范） |
| 关系强弱 | is-a，强绑定 | like-a，松散耦合 |
| 波及范围 | 父结构体加方法，所有子类被迫获得 | 谁实现谁生效，不影响别人 |

具体三句话：

- **它们解决的问题不一样**。一个是解决复用性和可维护性，接口的价值更多的是在于设计——设定好很多规范，让其他的自定义类型去实现。
- **接口比继承更加灵活**，因为它的关系相对来说比继承要弱。
- **接口在一定程度上实现了代码的解耦**。

关于继承和接口之间的这个关系，我们就讲到这里，大家认真地去体验一下。

## 多态与类型断言：一个变量，多种形态
> 对应块：BLK83 | 覆盖分集：P224-P226 | 块标题（分集名）：《222_尚硅谷_多态及体现》

面向对象编程里还有一个重要的概念叫**多态**。

什么是多态？多态指的是变量——或者说我们叫它实例——具有多种形态。多态是面向对象里的第三大特征。在 Golang 里面，多态是通过接口来实现的：也就是说，**在 Golang 里面，是接口体现出多态这个特征的**。

它的意思是什么呢？就是我们可以按照统一的接口来调用不同的实现，这时接口变量就呈现出不同的形态。

### 一个变量指向两种东西

我们来看前面讲过的一个案例——USB 接口。大家还有印象吗？当时我们定义了一个接口变量叫 `USB`，它既可以接收手机变量，又可以接收相机变量。

来，我们回忆一下当时怎么写的。我们定义了一个 `Usb` 接口，里面有两个方法；然后 `Phone` 实现了这两个方法，就相当于实现了这个接口；同时也定义了一个 `Camera`，`Camera` 也实现了这两个方法，也相当于实现了这个接口。然后我们还定义了一个方法叫 `Working`，里面可以接收一个 `Usb` 这样的变量。

关键的地方在这里：我在这里可以传一个 `Phone` 进去，也可以传一个 `Camera` 进去。

为什么可以？因为这两个变量对应的结构体都实现了这个接口，对不对？

而且有一点特别有意思的事情就发生了：当你传了一个 `Phone` 进去，当你调用的时候，它**自动地**就能判断这个 `USB` 指向的是一个 `Phone`；而当你传的是 `Camera` 这个变量的时候，它就自动地知道这个 `USB` 指向的是一个 `Camera`。也就是说，这个 `USB` 就已经呈现出了一种多种状态——它会自动根据运行的上下文环境，判断自己到底是一个 `Camera` 还是一个 `Phone`。

所以，这个 `USB` 其实就体现出多态了。我们把这种形式叫做**多态参数**。

```text
                Working(usb Usb)
                       │
        ┌──────────────┴──────────────┐
        │                             │
   usb = Phone{"vivo"}          usb = Camera{"尼康"}
        │                             │
   usb 呈现 Phone 形态         usb 呈现 Camera 形态

   同一个接口变量 usb，不同的实参 → 不同的形态
```

读图：这就是多态参数——`usb` 变量的形态由运行时传入的实参决定，调用方却完全不需要区分。

这里我不再重新敲一遍这段代码了，因为前面已经讲过，这次只是把它点名、把道理说清楚。

### 多态数组：一个数组放两种结构体

在 Golang 里面，接口体现多态主要就两种形式。第一种是刚才说的**多态参数**，第二种叫**多态数组**。

多态数组是什么意思呢？就是我给你一个 `Usb` 数组，里面既可以存放 `Phone` 结构体，又可以存放 `Camera` 结构体。

你们都知道，Golang 里面数组是什么类型就只能存什么类型——你是 `int` 类型的数组，就不能塞一个 `string` 进去，对不对？但是**当我们用接口过后，你可以存放实现了该接口的任何结构体的变量**，这就是多态数组。

来，跟上思路，我们新建一个文件夹，多态我们一般叫 `poly`——`poly` 就是多态的意思，一个简写。里面建 `main.go`。因为时间的关系我不想从头再写一遍，直接拿前面讲过的这个 `USB` 来做案例演示。

```go
func main() {
	var usbArr [3]Usb

	fmt.Printf("%T %T %T\n", usbArr[0], usbArr[1], usbArr[2])
}
```

先打印一下不放任何东西的时候里面存的是什么。跑一下你会发现都是空的、`nil`，正常，因为你根本没往里赋东西。

现在往里面放点东西：

```go
usbArr[0] = Phone{"vivo"}
usbArr[1] = Phone{"小米"}
usbArr[2] = Camera{"尼康"}
```

第一个元素是手机，第二个元素也是手机，第三个元素这次不放 `Phone` 了，放一个 `Camera`。

再跑一跑，三个元素都在。你看，这个数组里其实放了两种结构体，一种是 `Phone`，一种是 `Camera`。

> **结论**：**如果你不用接口，绝对是放不进去的。**一个数组只能放一种数据类型，这是我们前面讲数组时反复强调的。但现在我们既能放 `Phone` 又能放 `Camera`——就是因为利用了接口的多态特点。

以后要实现这类需求，就可以用多态数组。

### 但马上来了一个新麻烦

讲到多态数组的时候我曾经埋了一个伏笔，这里把它捡回来。

现在要求：给 `Phone` 结构体增加一个**特有的**方法 `Call`——注意这个方法不在接口里，是 `Phone` 自己独有的。然后我们希望能遍历这个 `Usb` 数组，如果发现传进来的是 `Phone` 变量，除了调用接口声明的两个方法之外，**还要调用 `Phone` 特有的 `Call` 方法**。

你不能直接写 `usb.Call()`。为什么？因为传进来的 `usb` 有可能是 `Camera`，而 `Camera` 根本没有 `Call` 这个方法。你这么直接调，肯定要出问题。

所以我们需要一个判断，能知道传进来的这个 `usb` 到底是一个 `Phone` 还是一个 `Camera`。这就是我们接下来的新知识点——**类型断言**。

### 类型断言：把空接口变回具体类型

先看一个需求。这里有一个结构体叫 `Point`，有两个字段 `x` 和 `y`，表示一个点。这里有一个 `main` 函数，里面定义了一个空接口，然后我把一个 `Point` 结构体变量交给 `a`。

这一步能否成功？显然没问题。因为 `a` 是一个空接口，我们讲过，空接口可以接收任何一个变量，所以把 `Point` 赋给这个 `a` 是没问题的。

现在我们反过来提一个需求：**希望把这个 `a` 重新赋给一个 `Point` 变量。**这种需求客观存在——写代码的时候，我们确实可能希望把一个空接口再还原成 `Point`。

那么能不能直接赋值？我们新建一个文件夹，就叫 `assert`，这个就是断言的意思。

```go
var a interface{}
p := Point{1, 2}
a = p

var b Point
b = a // 编译报错
```

我们试一下，报错了：

```text
cannot use a as Point value in assignment: cannot use a (variable of type interface{})
as Point value in assignment: missing type assertion
```

注意最后那句话——`missing type assertion`，需要使用一个类型断言。

那怎么办？非常简单：

```go
b = a.(Point)
```

**这个就叫类型断言。**它的意思是：把这个 `a` 看看能不能转换成一个 `Point`，然后再赋给 `b`。转换成功就成功，转换不成功就报错。

跑一下，输出是 `1 2`，成功了。也就是说，如果我们希望把一个空接口类型重新转换成对应的具体类型，就会使用到类型断言。

> **定义**：`b = a.(Point)` 表示**判断 `a` 是否指向一个 `Point` 类型的变量，如果是，就转成 `Point` 类型并赋给 `b`；否则报错。**

所以这个地方也不能瞎转。这句话能成功，前提是你这个 `a` 的的确确指向一个 `Point`。如果你没有指向，类型断言就会报错。

### 类型断言的其他案例

所谓类型断言是指：由于接口是一个一般类型，不知道具体类型，如果要转成一个具体类型，就需要使用到类型断言。

我们再举一个。前面那个 `x` 是个空接口：

```go
var x interface{}
var b2 float32 = 1.1
x = b2
```

反过来，把这个 `x` 转回 `float32`：

```go
y := x.(float32)
fmt.Printf("%T %v\n", y, y)
```

跑一下，你重新用类型断言转换过后，`y` 又变成 `float32`，它的值是 `1.1`，完全 OK。

那大家想一想，这段代码转能成功吗？

```go
z := x.(float64)
```

这里是 `float32`，你却要转成 `float64`。我们跑一下——报错了，**panic**。原因非常简单：你的空接口原先是一个 `float32`，**not** 不是一个 `float64`。

> **易错点**：**转换不是说你想怎么转就怎么转，你必须清楚知道原先这个 `x` 指向的是什么类型，才能转回来。转错了就会 panic。**

### 带检测的类型断言

问题又来了：写代码的时候我怎么知道能不能转换成功？有没有一种判断机制？

有，而且用得非常的多，我们接着看。

设想你要转成 `float64`。直接这么写肯定报 panic，程序直接退出，下面的代码根本执行不了。比如我在下面还写了一句打印 `ok ok ok`——大家想，你在这个地方断言就已经失败了，那个 `ok ok ok` 还能输出来吗？程序可能在这一行就已经崩溃了。

但有时候我们确有这样一种需求：**断言成功就成功，失败了就算了，但代码不要给我直接崩溃。**

因为老报 panic 肯定不是一件好事，panic 一出程序就没法继续运行了，很麻烦。我们用一个变量来接收，看看到底成功了没有：

```go
var y float64
y, ok = x.(float64)
if ok {
	fmt.Println("convert OK")
} else {
	fmt.Println("转换失败")
}
fmt.Println("继续执行")
```

运行一下，你会看到输出"转换失败"，然后——**代码可以继续执行**，它并不会因为一次类型断言失败就让整个程序崩溃。所以这个检测机制是比较好的。

这里 `ok` 你也可以写成 `flag`，随便什么名字都行。

> **提示**：既然 `ok` 本身就是布尔类型，其实前面那个 `if ok == true` 的比较是画蛇添足，直接 `if ok` 就行——成功就是 `true`，失败就是 `false`，就这么简单。

另外还有一种更简洁的写法，有些 Go 程序员比较喜欢：

```go
if y, ok = x.(float64); ok {
	fmt.Println("convert OK")
} else {
	fmt.Println("转换失败")
}
```

直接把断言写在 `if` 后面，用分号隔开。这种写法我们在前面讲 if 分支的时候用过，也是可以的。当然这纯粹是个人习惯，你习惯哪种就用哪种。

### 最佳实践：遍历多态数组，调用特有方法

现在回到那个伏笔——给 `Phone` 增加特有的 `Call` 方法，遍历 `Usb` 数组时，如果元素是 `Phone`，就额外调用 `Call`。

我们新建一个文件夹叫 `assertapply`，从前面讲多态的地方复制一份过来——其实写得差不多了，就差一点。

先给 `Phone` 增加一个特有的方法：

```go
func (p Phone) Call() {
	fmt.Println("手机 在打电话..")
}
```

注意这个 `Call` 在接口里是**没有定义的**，它是 `Phone` 独有的，`Camera` 里也没有。

再写一个 `Computer` 结构体，它有一个 `Working` 方法：

```go
func (c Computer) Working(usb Usb) {
	usb.Start()
	usb.Stop()
}
```

然后遍历数组。先看看不加任何东西能不能跑通：

```go
for _, v := range usbArr {
	computer.Working(v)
}
```

`index` 用不到，直接忽略。跑一下，输出是：手机开始工作、手机停止工作；手机开始工作、手机停止工作；相机开始工作、相机停止工作。这是正常的，因为前两个元素是手机，后一个是相机。

现在要加需求了：**如果 `usb` 指向的是一个 `Phone` 变量，则还需要调用 `Call` 方法。**

先看看错误做法。直接 `usb.Call()` 行不行？不行。编译器直接告诉你 `usb.Call undefined`，因为你这个接口里面本身就没有定义 `Call`；就算你去接口里加上 `Call`，要求所有实现者都实现它，那也违背了接口"只描述共性"的原则。

现在**类型断言**出场：

```go
func (c Computer) Working(usb Usb) {
	usb.Start()
	if phone, ok := usb.(Phone); ok {
		phone.Call()
	}
	usb.Stop()
}
```

这句话什么意思呢？如果 `usb` 在做类型断言成 `Phone` 的时候成功了，我就去执行 `phone.Call()`；如果没有成功，那就算了。

跑一下看效果：当它是手机的时候，输出"手机开始工作、手机打电话、手机停止工作"；当它是相机的时候，它**既没有报 panic**，同时相机仍然可以正常地运行。

因为当它发现是一个相机的时候，断言就失败了，`ok` 返回 `false`，那大不了就是不执行对应的 `Call` 方法，**它并不影响整个程序的运行**。

```text
遍历 usbArr
   │
   ├─ v 是 Phone  ──▶ usb.(Phone) 成功, ok = true  ──▶ 调用 Call
   │
   └─ v 是 Camera ──▶ usb.(Phone) 失败, ok = false ──▶ 跳过 Call，继续 Start/Stop

   两种情况都不 panic，循环照常走完
```

读图：这就是带检测的类型断言在真实场景里的价值——**判断成功就多干一件事，判断失败就跳过，程序永远不会因为一次断言而中断。**

这种用法我们后边学框架、还有一些高级用法的时候会经常使用到，所以大家一定要去体会它的好处。

最后回答一个初学者常问的问题：`if phone, ok := usb.(Phone); ok` 里面这个变量名，是不是**必须**叫 `phone`？不是的。它就是个变量名，你写成 `a` 也行，写成 `b` 也行，没有任何问题。老师取名 `phone`，只是为了让代码更好读、一看就知道是什么意思而已。千万不要以为这个名字有什么特殊含义。

## 通用一点的类型断言，和一个项目的六个阶段
> 对应块：BLK84 | 覆盖分集：P227-P229 | 块标题（分集名）：《225_尚硅谷_类型断言最佳实践(2)》

类型断言的第二个最佳实践，我直接给你一个需求：**请大家编写一个函数，循环地判断传入参数的类型。**

这个在项目里面是能用到的。什么意思呢？我给你传入一个参数，你就告诉我这个参数是什么类型。这个参数到底是什么类型，事先我有可能不知道，只能通过你这个函数来判断传入的实参到底是什么类型。

### items ...interface{} 与 switch x.(type)

这里可以写一个函数叫 `TypeJudge`。我用到了一种写法，还记不记得这是什么？讲函数的时候给大家讲过，这种参数叫**可变参数**——参数的个数我们通过三个点 `...` 来表示。所以 `TypeJudge` 可以接收任意多个实参。然后这个类型又是空接口类型，也就是说我这个函数可以接收任意多个、任意类型的实参。

我们新建一个文件夹 `assertapply02`，里面建 `main.go`。

```go
func TypeJudge(items ...interface{}) {
	for index, x := range items {
		switch x.(type) {
		case bool:
			fmt.Printf("第%v个参数是 bool类型，值是%v\n", index, x)
		case float32:
			fmt.Printf("第%v个参数是 float32类型，值是%v\n", index, x)
		case float64:
			fmt.Printf("第%v个参数是 float64类型，值是%v\n", index, x)
		case int, int32, int64:
			fmt.Printf("第%v个参数是 整数类型，值是%v\n", index, x)
		case string:
			fmt.Printf("第%v个参数是 string类型，值是%v\n", index, x)
		default:
			fmt.Printf("第%v个参数类型不确定，值是%v\n", index, x)
		}
	}
}
```

逐条说清楚。"第几个参数"刚好就是 `index`，值就是 `x`。`bool` 写一个 case；如果是 `float32`，我们这改成 `float32`；同样的道理，`float64` 写一个 `float64`；假设它是一个 `int` 类型，或者 `int32`、`int64`，我可以一次性把它们全部判断——`int, int32, int64`——那么我直接就说它是一个**整数类型**，值是多少也打印出来。最后判断它是不是一个 `string`，也把它输出出来。还有一种可能：一个都没匹配上，走 `default`，我们说类型不确定、不知道这个类型是什么，把第多少个参数、值是多少也输出出来。

> **易错点**：`switch x.(type)` 里的 `type` 是一个**关键字**，是固定写法，不是某个类型名。它做的是"把这个 `x` 做类型断言之后，它到底是什么类型"的判断——可能是 `bool`，可能是 `float64`，可能是 `int` 或 `int64`，也可能是其他类型。如果对上了，就进入对应的 `case` 语句。

### 一次判断六个参数

我们试一下。现在我有这么几个参数：

```go
func main() {
	var n1 float32 = 1.1
	var n2 float64 = 2.3
	var n3 int32 = 30
	var name string = "tom"
	address := "北京"
	n4 := 300

	TypeJudge(n1, n2, n3, name, address, n4)
}
```

跑一下：

```bash
cd ..
cd assertapply02
go run main.go
```

结果跟我们想象的一样：第一个参数是 `float32`，确实；第二个是 `float64`；整数类型出来了；字符串、字符串、整数。

> **提示**：注意每一条 `Printf` 的格式串末尾都有 `
`。不加 `
` 的话，全部会打到一行输出，格式化就乱了。

大家可以看到，通过这一个类型断言的函数，我们就可以非常灵活地判断你传进来的参数到底是什么类型。这就是我们在项目中可能会用到的一个比较常用的函数，也是类型断言的一个经典使用场景，希望同学们能够掌握它。

### 连你自己定义的类型也能判断

最佳实践案例三我要求同学们**自己**去完成：在前面的代码基础之上，增加判断 `Student` 类型和 `*Student` 类型，也就是 `Student` 类型和 `Student` 的指针类型，你能不能给我判断出来？

什么意思呢？假设我这里有一个学生结构体：

```go
type Student struct {
}
```

然后有这么两个变量：

```go
var stu1 = Student{}
var stu2 = &Student{}
```

当我把 `stu1` 和 `stu2` 也传进去的时候，能不能通过这个函数判断出来它到底是什么类型？它到底是 `Student` 类型，还是 `Student` 指针类型？

如果你正在跟着学，先把内容停掉，思考一分钟再回来看。几分钟的思考，应该大体就知道怎么完成。

其实非常简单，你只需要在 `switch` 里再加两段 `case`。加一个 `Student`，如果类型是 `Student`，就打印"第几个参数是 Student 类型，值是多少"；指针类型也写一个对应的 case。简单吧？

> **易错点**：这里有个疑问——`Student` 已经在下面用了，我把 `Student` 类型写在 `switch` 的 `case` 里面，保存的时候会不会报错？

我们把这两个传进去跑一下就知道。其实这个地方它也能搞定。**因为在调用的时候，这个 `Student` 类型已经被加载到内存了**，所以你把这个 `Student` 类型写在后面，它也知道 `Student` 是什么。

不过最好我建议同学们**把定义写在前面去**更好一点，因为这样更利于我们的理解——相当于我先定义一个 `Student` 类型，下面这个方法用到了这个类型，这样更好理解。虽然写在后面也可以跑起来，但写在前面更适合这种代码的理解。

跑完你会看到，判断出来了：第六个参数 `stu1` 它的确是 `Student` 类型；后面那个 `stu2` 也能判断出它是**指针类型**。

所以我们这个类型断言不但可以判断已有的数据类型，**也可以判断你自定义的数据类型**。`Student` 是我们自己定义的，在进行类型断言的时候，这个自定义的类型同样可以直接判断。

# 该动手写项目了

关于 Go 语言里面面向对象的这些知识点，就全部介绍完了。

下面我们把这些知识点串联起来写一个项目。我们写两个项目：第一个是**家庭收支记账软件项目**，第二个叫**客户关系管理项目**。通过这两个项目，我希望我们能把面向对象编程、包括 Go 语言的一些知识点串起来，加深对 Go 语言编程的理解，这样才能达到灵活地应用和驾驭 Golang 语言的效果。

### 家庭收支记账软件怎么讲

先看第十二章，家庭收支记账软件项目，这是我们的第十二章，也是第一个项目。

这个项目我分几步给大家讲：

**第一步**，先介绍一下一个项目开发的流程是怎么回事。尤其是对于初学者、以前没有做过项目的同学，要认真听一下项目开发流程包括哪些阶段，以及各个阶段要完成什么样的任务——这块是个重点。

**第二步**，项目需求分析，也就是我们这个记账软件要完成哪些功能。

**第三步**，界面。

**第四步**，实现代码。

实现代码的时候请注意：为了让大家有一个从面向过程编程到面向对象编程的过渡，我先用面向过程来把这个项目实现了，然后稍微一修改，就能改成面向对象的编程方式。大家注意体会一下它是怎么进行合理过渡的。

实现基本功能以后，我们还要做项目代码的改进——实现上面这些功能，对前面做的项目进行完善，然后将面向过程的代码修改成面向对象的方法。

### 项目开发的六个阶段

现在我们重点来介绍一下：一个项目开发的流程是什么，它主要包含哪些内容。

**第一步，需求分析。**

**第二步，设计阶段。**你们以前做项目的时候，第二步一般干什么事？其实就就到了设计阶段，我们叫设计阶段也行，叫项目设计也行。

**第三步，代码实现。**这个叫实现阶段，就是我们所说的编写代码。

**第四步，测试阶段。**

不过要澄清一点：测试阶段和实现阶段并不是"全部写完再测试"。准确地说，它应该是这样子的——

```text
需求分析 ──► 设计 ──► 实现 ──► 测试
              ▲                 │
              └──── 螺旋递增 ────┘

   一边写代码，一边测试
   先有单元测试，后面还有集成测试
```

读图：实现和测试是**螺旋递增**的关系，不是两个割裂的先后阶段。你先有一个单元测试，后面再补集成测试，一轮一轮往上走。

**第五步，实施阶段。**

**第六步，维护阶段。**对于一个好一点、大一点的项目，其实还有一个阶段叫维护阶段。因为你实施的时候，不敢保证你的项目绝对没问题吧？哪个敢说绝对没问题？就算微信这么牛的软件，它没 bug 吗？微软那么牛的公司，它也经常搞个什么漏洞补丁呢，对不对？

所以大体就是这六个阶段。

### 六个阶段的时间怎么分配

这六个阶段时间怎么分配呢？先说清楚：**没有一个很标准的比例。**为什么？因为一个项目的大小决定了你的分配。

比如说这个项目就五六万块钱，是个小项目，我估计需求分析都没有，直接上来就干代码了，对不对？但好一点的项目、稍微上一点档次的，比如上百万甚至上四五百万的这种项目，它的需求分析占的比重是比较大的。咱们别扯那个一万块钱的——有人说"我接了个小活儿，500 块"，500 块的活儿我们都没这些，直接干代码，可能直接粘贴拷贝就完活了。

我们就按大项目来说，按一个 200 万到 500 万的这个量级：

| 阶段 | 大项目的大致时间占比 |
| --- | --- |
| 需求分析 | 30% |
| 设计 | 20% |
| 实现 | 20% |
| 测试 | 30% |

大项目嘛，大项目才会有这个分析。我们就按 30%、20%、20%、30% 这个比例来——前两头占的比例比较大，实现阶段占的时间一般来讲不会超过设计阶段。

如果小项目的话，需求分析可能就很短了，没什么太多需求，对不对？

### 每个阶段是谁在干

这部分我简单聊一下，本身这个地方不想展开。

#### 需求分析：需求分析师

主要是一个叫**需求分析师**来做这件事。需求分析师至少要满足两点：**第一，必须懂技术，但技术不一定是最强的；关键是要懂业务。**

你们刚刚参加工作，先不要去搞需求分析师，因为一般来讲这个是需要有一定阅历的人。打个比方，有些大学刚刚毕业的同学，你去做一个电力软件，让你去搞这个需求分析，我估计你一头雾水——电力行业你根本不了解。

而且真正搞需求分析的人，一般是要到**对方的公司里面去常驻**的。以前在用友工作的时候，很多搞需求分析的人你都看不到他在这儿上班。"好久没见你，最近还好吗？""我还好。""你在哪儿去了？""我在石油勘探那个地方去呆了一个月。"呆了一个月干什么？搞需求分析。为什么要到那儿去？因为你要搞清楚别人的业务逻辑，你得跟人家那边管事的人沟通，得跟那边说了算的人沟通——**他拍板你才敢做**，不然做出来的东西人家不要。

而老大一般时间都比较紧张，所以他一般趁着他有时间的时候，"今天咱们约两个小时，说一下这个需求你是怎么想的"，赶紧跟他聊完。人家要到那边去上班，工资还是用友给他发。整完了过后，一个月，终于把需求分析搞定。

需求分析师要得到一个最终的结果——**需求分析报告**，要搞清楚人家到底要做成什么样的东西。这个事他做完了，其他事他基本就不管了。当然如果需求分析师本身是项目经理，他要跟着往下走下一个流程。

#### 设计：项目经理或架构师

一般是项目经理，或者架构师。我说"或者"是因为不同公司不一样。有些公司就是项目经理本身负责全局，整个设计全管起来；有些专业一点的公司就搞架构，把架构搞起来。

架构主要干什么？第一，用什么技术；第二，用什么操作系统；第三，用什么框架——用现有的 SSM，还是自己搞一个框架起来；第四，用什么数据库。还要考虑服务器集群是一层、两层还是三层，撑不撑得住。因为需求分析出来过后你肯定要说"我将来这个项目要按照支撑千万在线"，那设计肯定不一样。你要是分析下来就说"我们这就是个内部系统，200 多个人用"，那随便用什么技术都行。

然后项目经理还要干一件事，就是**选人**。为什么选人？因为他不可能自己一个人干。你们将来参加工作以后，其实你们是属于开发部的——但你属于哪个项目不一定。比如你跟小田坐在我旁边，有可能我在 U8 项目组，他是在 CRM 组。

我 U8 项目做得非常漂亮，可能每一季度都会有项目奖，每一季度给我发个两万；小田因为他那个项目 CRM 不行，可能过了三三个月过后就直接被开掉了。你别不信，微信当时做的时候不是说有两三个项目组在搞嘛，最后张小龙的整出来了，其他那些组不淘汰了吗？

选人的时候就很重要了。如果一个人技术很牛，既会 Java 又会 .NET，那有可能同时跟两个项目组，那他拿的工资就是两份，double。技术好是有好处的。以前有些学生去了过后说："韩老师，我们现在要转型了，要全部用 Java，我不会，我被淘汰了。"也有学生说："老师，我会 Java，他们要用 PHP，我不会，我也被淘汰了。"这都有可能的。

所以我告诉大家一个小技巧：**经常要跟管事的人交流交流。**发现有一个特别好的项目，你赶紧进去，有前途的项目赶紧进去；如果这个项目冷门、人家在做实验品，那你还是画个问号。平时多交流，人家就把你拉过去了。

最后设计阶段要出的结果是一个**设计文档**。设计文档最重要的是各种图：类图、实例图、流程图等等。还有一个最重要的就是**数据库设计**。

同学们都知道，数据库其实是一个项目的核心。对于一个大项目来说，数据库设计一定是要有经验的人——没经验的人是不让你去设计的。

我讲个自己被骂的经历。我们去了过后直接设计数据库，因为没有人嘛，老韩你赶紧设计一下，其实我也不会；搞了搞然后又被骂了一通，所以我又想起被骂的经历。搞了半天过后，我们那个 CTO 过来了："这谁干的？""是我。""你这个数据库设计有问题啊，三范式都没满足，有个字段有问题。"好，然后又告诉你怎么写——这个成长是非常快的。

数据库设计我们没有专门的课程，说实话我们将来就讲两个项目，你对数据库设计的理解还是不到位。你只有在真正做过一个大项目的时候，才知道数据库才是一个项目的核心。哪些表、哪些字段，没有一点能力的人根本驾驭不住，你整出来就是个跑不起来的东西。

现在比较流行的开发方式叫**原型开发**。原型开发就是说，除了上面这些东西之外，还有一个特别重要的：**界面原型必须出来。**

界面原型出来有什么好处呢？最大的好处就是可以直接跟大佬交流和沟通。你可以跟他说："大佬，我们将来做出来的样子大概是这样子的，你看满意不满意，颜色啊、功能啊。"因为原型有专门画图工具，啪啪啪就画出来了，连页面都不需要，画得非常漂亮、非常到位。

大佬一看："这个功能是不是还少了点？加点。"一般来说功能他不会再加了，他只会对界面提点意见，其实他也不懂。因为我们中国的很多客户不成熟，客户喜欢这么干："那个软件有这个功能，给我们加进去。"如果分析师不懂，加进去加进去，等到最后设计的时候，架构师就要骂人了——这东西根本实现不了，或者说一实现成本太高了。

#### 顺便说说项目怎么报价

昨天好多同学最喜欢问我这个问题："韩老师，我现在接了一个活儿，你能告诉我我应该问对方要多少钱吗？"

首先看功能——你这个功能有多大，这是一个功能；第二个，你将来的**硬件开支**。这是两大块。

人工其实是很高的。那人工我就要算：对方说两个月出活，我找的人和三个月出活找的人不一样。两个月要把东西做出来，那我就要找熟练的开发工程师。

熟练开发工程师一天多少钱？这个大致有个范围。比如一个比较成熟的、比较有经验的工程师，一般来说每一天的薪水我们假设按工作日算，假设他月薪两万块，你折到每一天大概是多少钱？大概算下来一千块钱，一千块钱的话可能还有点其他开销，就多算一点，算一千一。然后我整个工时量算出来是多少人、多少天。比如我这是二十个人，要二十天完成，那就是 $20 \times 20$ 再乘以这一千一，这就是**人工费**，这是我的成本。

还有**硬件开销**我也要加进去，比如你的服务器、你的带宽，我都要给你买起来，是你负责还是我负责？整个算下来过后，我要算我的**利润率**。比如成本假设整个算下来是三十万，我希望从三十万里赚到 30% 或者 40%，那我总价报七十万。

报完七十万过后看对方懂不懂行。如果不懂行的话，再加三十万，对不对？如果懂行的话就算了，懂行的话就别这么搞了。

这个阶段还有一个很重要的事：**原型**。原型就告诉他——是不是？要不要这个功能？我保证按照这个原型完成。对方一拍板说 OK，那你就签字画押，写一个大概的确认书，说什么时候完成、功能如何。确认了，这个家伙以后再不能找你麻烦。你不然的话，我跟你说，你的麻烦永远完不了：你刚做了一半，把东西做完了交给他，说"这不是我想要的"。

一般现在的软件公司先付 20%、30%，有付一半的，后面钱不给你，天天找你你也受不了。

#### 实现：软件工程师

实现阶段实际上就是我们所谓的软件工程师，也就是我们经常所说的**码农**。码农听过吗？你们千千万要干一段时间码农。码农就是堆代码的。

这里面也有档次之分，有些码农是很厉害的高级码农，你们先去可能是初级码农。去了过后软件公司说白了就是实现各个功能模块——因为你这地方已经把模块画出来了，你就是实现各个模块，把各个模块写好。

#### 测试：软件测试工程师

写完了过后是测试阶段，谁来干呢？**软件测试工程师**。软件测试工程师测你开发工程师的代码，他看好不好用。好用，过；如果不好用，你就赶紧给我重新写。然后不停地在这儿螺旋递增。

所以你看以前我们在用友软件的时候，为什么开发工程师和软件测试工程师不在一起吃饭？大家都怒目而视。因为有些时候 bug 给你发现了，你解决不了还很郁闷。有些 bug 不好解决，因为 A 工程师调了 B 工程师的代码，其实这个错误是 B 的，但人家软件测试工程师说是从你这儿发现的，你直接去找那个 B 工程师。**螺旋的嘛。这个是最可怕的——那叫软件耦合度太高了。**

我见过在中国最好的软件工程师就是用友的，用友的软件测试工程师是特别牛的。为什么呢？跟他们做的东西有关系，他们做的是**财务软件**，财务软件的要求是很高的。当时用友的软件测试工程师人数，几乎可以跟开发工程师达到一比一，这已经很高了。

其实国外有一个理论叫做**一比三**——一个开发人员按理说应该配三个软件测试工程师。但是现在中国反过来都没有：三个开发工程师一个测试都没有，甚至都是自娱自乐。自己写完了自己测，测完了 OK，上线，就这么干的。

现在不一样了，现在逐渐在重视这个事儿。因为现在各个公司 PK 很厉害，中国人用软件也有这个意识了：哪个软件好、哪个软件不出 bug 我就用谁。你这个产品老出 bug 就麻烦了，别人就不要。你看微信还是很少 bug 的，对吧？游戏也是——你拿一个游戏过来天天出 bug，你好不容易升级到十级，突然间一打开只有一级了，你还跟他玩什么呢？

测试工程师至少要有这么几个技术：**黑盒测试、白盒测试、还有一个灰盒测试**。灰盒子我就不写了。

**黑盒测试**是最基本的，但它也不是说你随便找一个菜市场买菜的大妈就能干，他也干不了。黑盒测试的意思是：我用这个软件，第一下、第二下、第三下出了什么问题，我要写一个 bug 报告提交过去。而且**一定是点什么、再点什么、再点什么，然后出现一个错误，这才是一个有效 bug**。不是说用了一下错了；下次如果不出现这个错误，说明你这个软件工程师没有发现 bug。

如果你们以后参加工作，哪个软件测试工程师跟你说"有 bug"，你就把他拉过来问："怎么操作会出现 bug？"第一步打开软件，第二步点击某个按钮，第三步输入什么数据，再一提交出现 bug——这才是有效 bug，而且**一定要稳定地出现**。如果测试工程师告诉你"它有时候出现，有时候没出现"，那这种错误说实话很难，找不到规律的那种错误是最难的。所以测试工程师也不是白白拿钱的。

**白盒测试**就不一样了，档次更高，它需要写代码，得懂代码。像我有一个朋友，在一家外企做了一个电信测试的项目经理，他们就用 Python——Python 在 Linux 下面做运维，写各种用例。所以现在软件测试工程师好多人也要开始学程序了，不懂代码是很难混下去的。

#### 实施：实施工程师

实施阶段是谁来干呢？还有一种工程师叫**实施工程师**，这也是一个职位。

实施工程师是干什么的？简单地说，你这个项目写完了，你得上架上线；上架的话你得搭服务器，得各种配置，这项工作就是实施工程师去做。

像好一点的公司，像惠普、IBM 的实施工程师待遇还是很不错的。一般来说别人派你们去出差，一般至少是三星级的宾馆，对吧？待遇还可以，一出差有补助。

如果是小公司就惨了。小公司的话把你发配到某个地方去，那你自己就在那个地方把这个东西弄完，弄完了过后如果有问题就找你。我以前有些学生干一段软件开发实在干不下去了，就转实施工程师了，经常打电话说："韩老师，我现在你知道我在哪儿吗？我在海南。""你知道我在哪儿吗？""我在新疆。"所以说实施工程师必须具备一个最基本的素质——**身体要好**，不然扛不住。

我有一个同学也挺有意思。以前我教 Java 是 06 年带的一个学生，他是北京人，一上课就天天睡觉，一睡觉就流哈喇子，有时候还打呼噜，让我受不了。我就跟他说："朋友，我们聊聊。"因为他们就是混的嘛，以混为主——我也不敢说他，因为他长到一米九，真的很高。他以前是干保安的。

我也不敢说他。他每次还说："韩老师，你讲课讲得可好了，我就是听不懂。"这不气人吗？

后来我跟他说："你到后面去睡。我有一个要求——你睡觉在后面不要让人发现，而且尽量不要发出声音好不好？"他还是比较配合我，很给老师面子。

后面找工作找不着，找了一个月还找不着。有一天他打电话给我："韩老师，我找到工作了。"我说："你还不错啊。"我很吃惊——怎么找到工作呢？他说："明天我就要出差了。而且公司给我配备了一个 IBM 笔记本，而且工资是八千。"那个时候八千不错。我说："你怎么要出差呢？"他说："我要到新疆有一个油田……我忘是哪个油田了，我去了过后呆一年。"

实在什么人去呢？你知道他终于找到一份工作，我说你去成长吧。虽然他基本功还是有的——去过后大概干了十个月提前回来了，回来还找我吃饭。"韩老师，我去了过后存了不少钱。""为什么？你不是挺爱花钱的吗？""实在花不出去那边。"吃饭别人管，住宿费也不用掏了，那个地方又不怎么通网。就这么存了一点钱。回来现在也成长起来了。

我真是发现一点：**坚持真的很重要。**我好多个学生都已经完全觉得不太可能了，人家扛下来了。

所以做实施工程师大家尽量先暂时不要去干，等到以后想旅游全中国的时候可以去考虑。

### 第一个功能：显示主菜单，并能退出

这个项目我按步骤走：第一步先用面向过程，把它改成面向对象。在写面向过程的时候，我们一共把它分成这么几步功能。现在先完成**基本功能**里的第一件：**可以显示主菜单，并且输入 4 可以退出这个软件。**

写一个功能的时候，我们的步骤就两步：**第一步先完成思路分析，完成思路分析过后再走代码。**

思路分析很简单。因为我们要显示这个主菜单，让它输一个数，然后我们就可以根据用户的输入来处理他不同的请求。这几乎没什么可说的，就是按照我们给出的界面来输出就可以了——根据给出的界面完成主菜单的显示，当用户输入 4 时，就退出该程序。

因为这块特别简单，直接按照套路出牌就完了。

新建一个文件夹 `chapter12`，新建 `testMyAccount.go`：

```go
package main

import (
	"fmt"
)

func main() {

	// 声明一个变量，保存接收用户输入的选项
	key := ""
	// 声明一个变量，控制是否退出 for 循环
	loop := true

	// 显示这个主菜单
	for {
		fmt.Println("-----------------家庭收支记账软件-----------------")
		fmt.Println("                 1 收支明细")
		fmt.Println("                 2 登记收入")
		fmt.Println("                 3 登记支出")
		fmt.Println("                 4 退出软件")
		fmt.Print("请选择(1-4)：")

		fmt.Scanln(&key)

		switch key {
		case "1":
			fmt.Println("-----------------当前收支明细记录-----------------")
			fmt.Println("收支\t账户金额\t收支金额\t说    明")
		case "2":
		case "3":
		case "4":
			loop = false
		default:
			fmt.Println("请输入正确的选项..")
		}

		if !loop {
			break
		}
	}

	fmt.Println("你退出了家庭记账软件的使用...")
}
```

有几个地方我拆开说。

**第一，主菜单必须是循环显示的。**你看它是这样子的：你输入一个 1 之后，它显示收支明细，**再次显示这个主菜单**。所以我们可以看出来，这个主菜单应该是循环显示的，因此用一个 `for` 循环。

**第二，得有个变量接收用户输入。**既然他要选择 1 到 4，那是不是应该有个变量来接收他的输入？这就是"感情的自然流露"——你肯定要有一个变量来接收这个用户输入的选项，因此我们声明一个变量保存用户的选择，就写一个 `key`，给它一个空串，然后用 `fmt.Scanln(&key)` 接收。

**第三，怎么退出这个 for 循环？**这里是本节最值得体会的地方。我这里是一个 `for` 循环，我怎么退出它呢？如果是 `for` 循环，要退出它直接 `break` 就可以了——**但是退出软件，你的 `break` 只能退出 `switch` 语句**，要退出这个 `for` 循环，我们还需要一个变量。

怎么做呢？非常简单：我用一个 `loop`，默认是 `true`，默认它就一直循环地输出这个菜单。那当我这一旦为 4 的话，我就把这个 `loop` 改成一个 `false`；如果他输的都不对，我们给它一个 `default`，提示一句"请输入正确的选项"。

`switch` 做完了以后，我就来判断这个 `loop`。如果这个 `loop` 还为真，我就让他继续显示菜单；如果它为假，那我就退出这个 `for` 循环了——`loop` 为假，我取反就为真，整个就 `break`。

> **易错点**：`switch` 语句里的 `break` 只跳出 `switch`，**跳不出 `for` 循环**。所以需要 `loop` 这个标志位。后面这种"用标志位控制 for 循环退出"的写法，我们在做编程的时候经常使用，可以说是一种编程思想。大家仔细体会体会，也自己敲一敲。

保存一下，看代码有毛病没有。现在没有报错，我们来用一下：

```bash
go run testMyAccount.go
```

界面已经有了：家庭收支记账软件有四个选项。输 1，显示当前收支明细；输 4，显示"你退出了家庭记账软件的使用"。第一个功能实现了，非常简单。

大家先跟着这段代码自己也敲一敲，主要是听一下这个思路的实现方式——**为什么用 `for` 循环反复来循环地显示，为什么要用一个 `loop` 变量来控制是否退出这个 `for` 循环**。

### 第二个功能：显示明细 + 登记收入

接下来完成下一个功能。因为显示明细这个功能特别简单，所以我们把显示明细和登记收入这两个功能放在一起实现。

还是先做思路分析。这一步特别重要，**同学们一定要根据老师的思路分析来做这个代码，不然的话你总感觉没有这个套路。**

我们要实现显示明细。你想，输个 1 就能把它显示出来，那也就是说**你必须得有一个字符串来记录收支的明细**——这个是肯定要的，没什么可说的。

第二个，界面上有一个**账户金额**——就是它统共现在有多少钱；还有一个**收支金额**——就是你这个变化是多少钱，肯定有个 `money`；还有一个**说明**。所以这里面肯定要有变量才能体现出这个特点，没有变量的话根本没有办法体现。

而且大家看到它的收支明细：如果是收入，这地方显示的就是收入；如果是支出，这地方显示的就是支出。所以我们在拼接这个字符串的时候，**肯定要根据用户选择来判断**这个地方第一个是写收入还是写支出。

分析出来的结论是：因为需要显示明细，所以我们需要定义一个变量——`details`，这是个字符串来记录它。这个字符串会不停地拼接，根据你是支出还是收入不停地拼接。这是第一个。

而且我们还需要定义几个变量：**余额**——我到底还有多少钱，这个跑不了；**每次收支的金额**——这个跑不了吧；**说明**——每次收支的一个说明。

那我用 `balance` 来记录余额，当然名字你可以自己确定；每次收支的金额用 `money`；每次收支的说明用一个字符串 `note`。

有了这几个概念过后，就可以走代码了。

```go
// 账户余额，初始预设 10000
var balance = 10000.0
// 每次收支的金额
var money = 0.0
// 每次收支的说明
var note = ""
// 收支明细详情，使用字符串来记录
var details = "收支\t账户金额\t收支金额\t说    明\t\n"
```

`balance` 的初始值我们参考需求：收入 1000 之后账户余额是 11000，说明原先本身有一个预留的值，就是 10000。所以初始化的时候，我们假设这个人就有 10000 块钱的初始资金。

`details` 字符串初始化应该是什么情况？它每次有个**表头**——收支明细有个表头，我就直接刚开始的时候赋给它。为了好看，我们这个地方直接用 `\t` 来进行格式化的控制，用个制表符。

有了这个东西过后，后面就不停地拼接：**当有一笔支出或者收入的时候，就对这个 `details` 进行一个拼接处理即可。**

当前收支情况只需要把这个输出出来就行了：

```go
fmt.Println(details)
```

> **提示**：写到这里先编译一下，编译器会提示 `balance` 定义了没有使用。这个是正常的——我们现在还没有录入任何收入。先把它暂时注释掉，等会儿做完登记收入再打开。

先输一个 1 看看：当前收支明细是空的，看起来没东西。是不是显示得太紧了？最好给它来一个换行，每次先来一个换行，看着才舒服。

因为目前我们没有一笔收支——既没有支出也没有收入——所以它这儿显示的是空的，这是对的。

### 登记收入

现在赶紧把登记收入这块完成。

当用户输入 2 的时候，就代表他会登记一笔收入。我们来看看它的要求：如果选择 2，就先提示"本次收入金额"，让他输一个金额；再提示"本次收入说明"，让他输一个说明。

好，根据刚才这一段代码提示，我们手写一下：

```go
fmt.Println("本次收入金额:")
fmt.Scanln(&money)

fmt.Println("本次收入说明:")
fmt.Scanln(&note)
```

两个输入，两个变量接收：一个是 `money`，一个是 `note`。

> **注意**：当你的 `money` 和 `note` 已经接收到了过后，同学们想一想——你这个地方是**收入**，所以你的余额就会发生变化，对不对？因为你是收入嘛，那你的余额就应该加上你输入的那个钱。

```go
balance += money
```

这就修改了我们的账户余额。

同样，你这地方有个收入说明，你的收入说明就得把它**记录到你的收入字符串里面去**。看怎么拼接——用 `fmt.Sprintf` 格式化一下：

- 首先，这里要拼接这么一个串串，这个串串是固定的，因为你这地方就是收入，所以把"收入"写进去；
- 然后余额用一个制表符 `\t`，再加一个 `%v`，这个 `v` 第一个变量就是我们的 `balance`；
- 再来一个 `\t` 加 `%v`，第二个变量的值就是我们的 `money`；
- 第三就是一个 `\t`，然后把这个说明输进去，也就是我们的 `note`。

```go
details += fmt.Sprintf("收入\t%v\t%v\t%v\n", balance, money, note)
```

经过这一番，我们就把这个 `details` 拼接到收入这个信息里面去了。

既然如此，这笔收入就会保留到 `details` 里面。当你输入 1 的时候，是不是就能看到这个效果？

## 登记支出、把退出做稳，以及改成面向对象
> 对应块：BLK86 | 覆盖分集：P233-P235 | 块标题（分集名）：《231_尚硅谷_收支软件-登记支出和完善退出》

### 第三个功能：登记支出

第三个功能是**完成登记支出**。比如我们有一笔钱要支出去，这个时候也要把它记录下来。

还是老规矩，先思路分析再走代码。因为前面已经完成了登记收入，所以登记支出基本上就是在登记收入的基础上稍微做一点变化，变化不大：**登记支出的功能和登记收入的功能类似，做些修改即可。**

我们来看看界面怎么说的：**本次支出金额、本次支出说明**——基本上就是在刚才的基础上做些变化。

但有一个地方不一样，很关键：**支出金额要做判断。**收入可以直接加，支出不行——你的余额不满足这个支出金额，就不能做这个处理。所以这里不能像收入一样直接加，你还得有一个判断：

```go
if money > balance {
	fmt.Println("余额不足")
	break
}
```

什么意思呢？如果你要支出的这个钱大于了 `balance`——就是你的钱不够，比如只有十块钱，你要支出二十块钱，肯定是不允许的。那这个时候就提示一句话："支出的金额不足"，或者说"余额不足，不能支出"。然后直接 `break` 就可以了。

> **易错点**：这个 `break` 只是退出了这个 `switch`，**并没有退出 `for` 循环**，看清楚了。

如果支出的金额是小于等于 `balance`，那我们的 `balance` 就可以进行一个减的操作：

```go
balance -= money
```

然后提示"本次支出说明"，让它输入一下；支出说明有了过后，是不是又要进行拼接了？这块简单，把登记收入那段复制下来，把"收入"改成"支出"就可以了；`balance` 还是 `balance`，`money`、`note` 就写完了。

```go
fmt.Println("本次支出金额:")
fmt.Scanln(&money)
fmt.Println("本次支出说明:")
fmt.Scanln(&note)
```

我们运行一下。先登记一笔收入 100 块钱，就当是工资，看一下支出——现在是一万零一百。然后登记 3 支出，本次支出金额 20 块钱，买糖吃。支出了 20 块钱，我们看收支情况：原先是一万零一百，现在余额只有 **10080**，说明是"买糖吃"。没问题，支出功能完成了，非常简单。

### 项目代码的改进

接下来我们对项目代码做几个改进。同学们，我们做项目往往是这样：**先完成一个大概，然后根据项目情况进行完善和处理。**

#### 改进一：退出前问一句"你确定要退出吗"

第一个改进是：当用户输入 4 时，给出提示。

你看我们目前直接就退出了，我输一个 4，它没有任何提示就退出了。那也有可能是用户输错了呢？比如说你退出微信、退出 QQ 的时候，往往会有一个对话框提示你"真的要退出吗"吗？我们的软件为了适当地考虑一下易用性，应该给它一个提示信息：**你是不是真的要确定退出？**如果他输入一个 `y`，我们就让他退出；而且**必须输入正确的 `y` 或者是 `n`**，否则就循环输入，直到他输入 `y` 或者 `n`。

这个处理代码应该写到哪里呢？输入 4 过后**不要马上**给它来一个 `loop = false`，先提示它一句话：

```go
case "4":
	fmt.Print("你确定要退出吗？y/n\n")
	choice := ""
	// 只有输入 y 或者 n 才退出
	for {
		fmt.Scanln(&choice)
		if choice == "y" || choice == "n" {
			break
		}
		fmt.Println("你的输入有误，请重新输入")
	}
	if choice == "y" {
		loop = false
	}
```

为什么这里要 `for` 循环呢？因为如果他输的不是 `y` 和 `n`，我就让他一直输入，直到他输入 `y` 或者 `n` 才退出这个 `for` 循环——因为你的要求就是这样子的。

如果输的是 `n` 呢？`n` 就是 no，代表不退出。那怎么做？什么都不做，这个 `loop` 仍然保持 `true`，下面判断的时候它仍然不会退出，它会继续打印这个主菜单。

我们运行一下专门测这个 4：输一个 `w`，它说"你的输入有误，请重新输入"；输一个 `p`，反正不让你出来；输一个 `y`，退出了。再试一次，输 4，输一个 `n`，主菜单马上又打印出来了，你还可以继续玩。

大家把这一段消化一下——其实就是一个 `for` 循环，里面用一个 `if`，同时有 `break` 语句，还是比较综合的。这里考察的就是你的编程思想。

#### 改进二：没有明细的时候，别只打印一个表头

第二个改进：**当没有任何收支明细时，提示"当前没有收支明细，来一笔吧"。**

目前我们的情况是什么样子的呢？我们输入 1 的时候，其实直接打出了一个表头。按理说这样打出来是没什么意义的——因为你现在一笔收支都没有，你把这个表头打出来，第一次用的人可能还会觉得你的项目是不是写错了。

既然如此：当没有任何收支的时候，我们这儿**不要打这个表头**了，直接输出一句话："当前没有收支，请来一笔吧"。

怎么完成？问题在这儿：输入 1 的时候，我们没有做任何的判断，直接就把这个 `details` 打出来了，相当于把这个表头也打出来了。但是现在我们需要**至少有一笔收入或者有一笔支出**，才做这个事情。

遇到这种类似的情况，我们可以做一个**标识符**。我们定义一个变量，记录是否有收支的行为：

```go
var flag = false
```

假定初始化的情况下是没有收支行为的。如果这个人产生了一次支出——当然是成功的支出——或者是成功的一次收入，我们就把这个 `flag` 置成 `true`。这样有什么好处呢？当我有一笔支出或收入的时候，这个 `flag` 就变成 `true` 了。

那我在这儿就可以加一个判断：

```go
case "1":
	fmt.Println("\n-----------------当前收支明细记录-----------------")
	if flag {
		fmt.Println(this.details)
	} else {
		fmt.Println("当前没有收支明细，来一笔吧")
	}
```

如果 `flag` 为真，说明确有收支，我就打印出这个 `details`；否则说明一次收支都没有，那就直接输出这句话。

我们运行一下。重新运行程序，第一次输 1："当前没有收支明细，来一笔吧"，因为刚刚运行这个软件，没有任何收支。现在登记一笔收入，100 块钱，工资。再查看收支明细——就直接打印出收支了，不会再提示"当前没有收支明细"。再登记一笔支出，10 块钱，看电影，再输出一下，没有任何问题。

这个功能本身很简单，但我们要重点讨论的是**怎么用程序去实现**——面对这样的问题咱们怎么去处理，这里涉及到一种编程的思想。

#### 改进三：余额不足的提示

第三个功能是在支出的时候判断余额是否够，并给出相应的提示。这个好像我们已经做过了？是的，我们已经做过了。这里做了一个判断：`money` 如果大于 `balance`，就说"余额不足"。

我们直接来一个支出，支出 2 万块——显然不够，因为我的余额只有 1 万块钱。你看，"余额的金额不足"，这就直接不给你做处理了。

这个很简单，**但是大家要知道在哪里加，这个很重要。**

### 改进四：把面向过程改成面向对象

现在我们来看下一个改进。此时此刻我们写的这个代码，大家可以看到**完全没有用到面向对象这个特性**——我们完全是流水账，是不是？就在这个 `main` 函数里面把所有的功能都做完了。

但是大家想一想，如果我们这个软件很大、功能很多，我们这样做肯定会不方便。所以同学们要慢慢适应**由面向过程向面向对象开发方式的转变**。

#### 思路：把所有功能封装到一个结构体里

先说思路。因为你现在是面向过程的，现在要改成面向对象，我们就这样思考这个问题：**把记账软件的所有功能封装到一个结构体中，然后调用该结构体的方法就可以了。**通过调用该结构体的方法，来实现记账、显示明细。

结构体的名字我们取 `FamilyAccount`。

第二个呢，我们在 `main` 方法中创建一个结构体——注意听，是 **`FamilyAccount` 结构体的实例**——创建这个结构体的一个实例，实现功能的使用，实现这个记账即可。

意思清楚了吧：先把记账功能和显示明细功能放到一个结构体里面去，然后在 `main` 方法里面去调用 `FamilyAccount` 的实例，就实现这个记账功能就可以了。

代码并不需要重写，**只需要重新组织一下**即可。我们新建一个文件夹，就叫家庭记账软件 `familyAccount`，里面建两个文件夹：一个是 `main`，第二个把完成各个功能的结构体封装到另一个文件里面去，叫 `utils`——这是个工具，对吧？我们在这里写 `familyAccount.go`。

```go
package utils

type FamilyAccount struct {
	key     string
	loop    bool
	balance float64
	money   float64
	note    string
	flag    bool
	details string
}
```

这个结构体里面有哪些字段呢？大家想一想——是不是就是 `testMyAccount` 里面的这些字段？因为你要用的就是这些呀。所以不用犹豫，也不用彷徨，把这一段代码整个拷贝下来，放到结构体里面就可以了。

但**因为这个地方已经变成字段了，所以你在这里就不能像这样写了**，得全部改一改：

- 这是个字符串，所以写成 `string`；
- `loop` 是个布尔类型，所以这块写成 `bool`；
- `balance` 是个 float 类型，把 `balance := 10000.0` 改成 `balance float64`；
- `money` 也是 `float64`；
- `note` 是个 `string`；
- `flag` 也是布尔类型；
- 收支情况 `details` 也用字符串记录，写成 `string`。

保存一下会发现报错——因为一会儿我们要用这个包里面的方法，对不对？没关系。

#### 把功能拆成方法

有了结构体过后，我们就给该结构体编写、绑定相应的方法。我们来看看它里面有哪些方法。首先要显示主菜单，是不是应该有显示主菜单？第一个方法就是显示主菜单：

```go
func (this *FamilyAccount) MainMenu() {
	// 循环显示菜单、接收 key、switch 分派到各个方法
}
```

它怎么显示呢？它是循环显示的，所以我把原先 `for` 循环那一段复制过来。这里面的 `switch` 代码你可以把它拷贝一下，应该是没有问题的。

> **提示**：但是这里面有很多要改变的东西。首先，**这个方法你就不能一下写到这儿了**——因为你这一个主菜单像这样用的话，显得很不专业。于是乎我们可以把显示收支明细封装到一个方法里面，把登记收入封装到一个方法里面，把支出封装到一个方法里面，把退出也封装到一个方法里面。**是不是这样子才是我们面向对象的一种编写方式？**

所以我们的代码应该再做一个扩展。第一个，显示明细写成一个方法：

```go
func (this *FamilyAccount) showDetails() {
	fmt.Println(this.details)
}
```

里面的代码其实就是它，我把它剪切放到这儿，写完了。那要去调用这个 `showDetails` 是不是非常简单？你只需要用这个 `this` 去调它就可以了：`this.showDetails()`。你看这个代码显得很简洁了，是不是？

同样的道理，登记收入的那段代码我们也把它剪掉，绑定到这个结构体中做一个方法，叫 `income`：

```go
func (this *FamilyAccount) income() {
	// 读 money 和 note，balance += money，拼接 details
}
```

绑定好以后，调用的时候是不是就用 `this.income()` 就可以了？又很简单的。

支出也一样，绑定到一个方法里面，就叫 `pay`——付款嘛：

```go
func (this *FamilyAccount) pay() {
	// 余额判断，balance -= money，拼接 details
}
```

用户输入 3 的时候，`this.pay()`，完事。

退出也一样，把退出系统也写成一个方法，就叫 `exit`：

```go
func (this *FamilyAccount) exit() {
	// y/n 二次确认，通过后 this.loop = false
}
```

这才是面向对象——你实际上是通过一个结构体的方法来实现的。这样看起来就比较简洁了，比原先简洁很多。

#### 补上 this.，break 改成什么都不用做

保存一下，我们看错误在哪里，一个个看。

首先提示了很多错误：`flag` 没有定义。这是为什么？因为你这个 `flag` 其实是定义到这个结构体里面的一个**字段**，因此你在这儿直接用肯定用不了。怎么用？我们原先学结构体的时候老师反复讲过，要调用这个结构体传进来的变量，是通过这个变量来调用的，因此这块应该写 `this.`。同样，下面的各个字段的使用也如法炮制，全部都要加 `this.`。

这里说一句绕的话——因为你要明白，调用这个 `income` 的实际上是 `myFamilyAccount` 这个结构体指针变量，那我调用它字段的时候，就必须要通过这个变量名来调用。这个名字我们叫 `this`，如果你叫别的名字，那这儿就该是别的名字。全部都要给我加上 `this`。

接下来这块有个 `break`。这个地方就不能用 `break` 语句了——**因为你原先是在一个 `switch` 里面，现在不在了**。那怎么办？

我们想一想这个地方怎么处理。金额不足，那就**不用管它**——因为它执行完了过后，自然就退出这个 `switch` 语句了，所以说这个 `break` 就不要了，注释掉就可以了。

> **易错点**：**方法里的 `break` 不再能退出调用方的 `switch`**——这是从函数体里抽出来的方法之后非常容易踩的一个坑。

`exit` 这边也有相应的处理：`this.loop`。

#### 工厂模式的构造方法

虽然没有错误了，可是这个结构体我们其实是**有可能是一个小写的**。那不管怎么样，我还是给它提供一个类似构造方法的东西，其实是一个**工厂模式**。

```go
func NewFamilyAccount() *FamilyAccount {
	return &FamilyAccount{
		key:     "",
		loop:    true,
		balance: 10000.0,
		money:   0.0,
		note:    "",
		flag:    false,
		details: "收支\t账户金额\t收支金额\t说    明\t\n",
	}
}
```

大家注意听好，我写了一个方法，我要返回一个这样的实例，这是工厂模式写的。怎么做还记得吗？`return` 一个 `&FamilyAccount`，初始化一下。

大家想一想，这个时候这些字段是不是没有初始值？但是以前我们在写面向过程的时候，这里面都有初始值。所以我们在返回实例的时候，**也应该给它相应的初始值**来完成这个事情：

- `key` 的初始值是空；
- `loop` 初始值应该是 `true`；
- `balance` 初始值还记得是多少？**10000**，不要少了一个逗号；
- `money` 初始值应该给多少比较合理？`0.0`，以前也是这么写的；
- `note` 是一个说明，初始值为空串；
- `flag` 初始值默认 `false`——因为它是用来记录是否有收支行为的，刚启动的时候还没有一笔收支，因此默认是 `false`；
- `details` 初始值就是那个表头字符串。

#### main 里只剩两行

现在第二步工作：在 `main` 方法中去创建一个 `FamilyAccount` 实例，实现记账功能就可以了。

```go
package main

import (
	"fmt"
	"go_code/12/familyaccount/utils"
)

func main() {
	myFamilyAccount := utils.NewFamilyAccount()
	fmt.Println("这是面向对象的方式完成")
	myFamilyAccount.MainMenu()
}
```

因为我在这个文件里面要使用这个方法——这个方法才会返回一个 `*FamilyAccount` 的指针类型——所以我首先要把这个包引进来。还记得怎么引吗？引入的时候是从 `src` 下面开始计算，写成 `go_code/`，然后项目名称叫 `familyaccount`，再来一个斜杠，引的是 `utils` 这个包，实际上就是引到这个文件夹。

然后创建实例，再直接调用它的 `MainMenu`。这个 `MainMenu` 其实就是主菜单，它就把这个打印出来了，然后在里面又调用了这一个结构体里面的各个方法。**这才叫面向对象。**

从这个地方来看，我们的代码更加地清晰了。说白了就是：**把所有的字段封装到一个结构体里面，然后把相应的方法也给这个结构体进行绑定**——因为你就是一个记账软件嘛，我把这些方法跟它绑定。最后提供一个 `NewFamilyAccount` 工厂模式的构造方法，返回它的一个实例；最后在 `main` 里面去创建了一个这样的实例，再调用它的菜单，完事了。

> **提示**：这里有个细节值得大家认真观察——**`MainMenu` 是大写的，其他方法 `exit`、`pay`、`income` 我都是小写的**。这样也体现出封装的特性。

我们运行一下。`cd familyaccount`，里面有两个文件夹：一个是 `main`，一个是 `utils` 包。我们进到 `main` 这边，里面有一个 `main.go`——就是刚才这段代码，你看很简洁了，我们把大量的代码都封装到 `FamilyAccount` 这个结构体里面了。如果你是学过 Java 的同学，就更好地理解这个封装特性了。

跑起来玩一把：输 1，完全没问题——"当前没有收支明细，来一笔吧"。登记一笔收入 100 块、工资，再查看明细，入账了。再登记一个支出 90 块钱，看电影，看电影花了 90 块钱，没问题。

最后演示一下退出：4，"是否要退出啊？"，我瞎输一个 `o`，它说"你的输入有误，请重新输入"；输一个 `n`，不退出，又打印出这个主菜单；这次真的退出，输 `y`，退出成功。

### 面向对象带来的两个好处

从这段代码你可以体验到面向对象的好处。

**第一点，代码更清晰。**原先的代码都写到一个 `main` 方法里面，`main` 方法很乱。有人说"这也不算很乱呀，思路还是很清晰"——对，如果乍看一眼的话确实不乱，这是因为我们目前这个功能很简单。如果这个功能越来越复杂，你想一想，你可能把所有的方法都封装到一个 `main`、把所有功能都放到一个 `main` 方法里面去吗？不现实。

反观我们的面向对象：`main` 里面其实就是创建了一个结构体实例，然后调用它的主菜单，完事了；所有功能都封装到了结构体里面。结构体里面有字段，结构体里面有相应的方法，非常清晰，要改起来也比较容易。最后留在主菜单里，思路很清晰——输入 1 就调用 `showDetails`，输入 2 就调用 `income`，输入 3 就调用 `pay`，依次类推。

**第二点，从项目开发分工来看，面向对象也很方便。**如果我有五个人来写这个代码，我可以把这个功能分成好几个结构体，让每一个人去写一个结构体，到时我在主函数里面根据实际情况来完成一个调用就完事了。它也利于我们的合作完成一个项目，开发项目的效率会大大提高。

## 客户信息管理系统：需求、界面，和动手之前的那张图
> 对应块：BLK87 | 覆盖分集：P236-P238 | 块标题（分集名）：《234_尚硅谷_客户管理系统-需求分析和界面》

### 为什么还要再写一个项目

先说说为什么。这个系统相对来说要比刚才那个程序难一点。

你看我们前面写的家庭收支软件，总体来说难度还算不算太大？**连数组都没有用到**，是不是这个道理？第二点，它连一个程序的结构都没有，是一种很简单的案例。这里重点就是给大家把编程思想、还有 `for` 循环、分支判断做了一个使用而已，**整体业务逻辑还是比较简单**。

现在写第二个项目，客户信息管理系统，这个要比刚才的稍微综合一点，难度更大一点。但你要认真听，它也不难。

只有通过这种写项目，我们才能够把 Golang 语言更加灵活地掌握到。所以我们来写第十三章，项目二：客户信息管理系统。

### 项目需求分析

还是老规矩：写一个项目，先要把项目的需求搞明白。

**需求是：模拟实现基于文本界面的客户信息管理软件。**这个软件能够实现对客户对象的插入、修改、删除；同时要求**要用切片实现**；另外，能够打印客户明细表。

大家看到这里有切片的概念了，为什么？因为我们这个客户的个数是**不确定**的——它可能有 10 个，也可能有 100 个，因此我们用切片来保存我们的客户信息。

课件里对这个项目还给了几个学习目标：进一步提高我们编程技巧、调试技巧，发现错误怎么去解决；熟悉面向对象编程。涉及到的知识点有：切片的插入、删除和替换，而且要**解决一个多对象协同工作的问题**。

用切片而不是数组，是因为**切片的灵活性更高**——切片可以动态地变化。

### 项目界面设计

有了需求分析，就来看项目的界面设计。大体它是一个什么样的界面，咱们要有一个认识。这部分我已经给大家设计好了。

主菜单可以输入添加客户、修改客户、删除客户、客户列表和退出，选择 1 到 5。根据它的选择不同，我们就应该有相应的处理方案：输入 1 就添加客户，输入 2 是修改客户，依此类推。


#### 添加客户界面

有了主菜单页面过后，下面有一个**添加客户**的页面。比如他输入了 1，就代表要添加一个客户。那添加客户的时候，我们让他输入姓名、性别、年龄、电话、邮箱，最后有一个"添加完成"。一回车，如果添加成功了，我们就提示添加完成。

#### 修改客户界面

肯定还有删除、修改。

还有一个界面非常重要，就是**客户列表**。当他输入 4 的时候，我们可以把当前所有的客户信息显示出来——你有多大客户，我就显示多少客户。

### 动手之前：程序框架图

有了这些界面，下一步按理说应该写代码了。**但是还不能写代码**——我们这里边要先做一个程序框架图。

有些同学问了："老师，项目设计这个程序框架图是什么意思呢？"我先简单说一下：**所谓程序框架图，就是要描述我们这个项目里边有哪些文件，以及文件和文件之间的调用关系。**这个我们就叫程序框架图。

#### 公司里到底是什么流程

在我们做软件开发的过程中，尤其是在软件公司，一般来讲，在做项目开发之前，我们应该先画出这个程序框架图。

我们以前在公司工作的时候，它是这样子的：首先，我们的项目经理或者架构师会给我们**设计文档**。这个设计文档里面内容很多，比如类图、用例图、流程图。好，这个有了。设计文档有了过后，他会把数据库表也给我们——**有些时候不给，让你自己设计；有些时候让程序员自己设计**，都有可能。

那么还有一个地方：就是他把它画成**功能模块**了。他可能会分一个叫**用户管理模块**；还有一个叫**订单管理模块**；比如还有像**购物车模块**、**支付模块**，还有像**安全模块**——专门负责安全的。

好，他把这些东西给你搞出来过后，他有时候只画了一个大概。他告诉你应该怎么做，这些东西都给你了，**但是每个模块之间的文件他不一定给你写得那么详细。**

于是我们程序员有一个重要的功能，就是程序员要把每个模块拆开做。比如说这个用户模块是韩老师来完成，老韩做；这个模块是老李做；像这个模块是小田来做。

分析完了过后，小田或者老韩拿到这个东西，是不是马上就动手了呢？理论上说马上动手，**但是你在动手之前你得知道你要干件什么事**。所以我们一般会干这么一件事情：先画一个所谓的**程序框架图**。

小田也会画他订单模块的程序框架图，因为整体架构太大了，你也画不了，也不是你的事。你有你的模块，我有我的模块，我也不可能帮你设计，你也不会帮我设计。

#### 什么是程序框架图

所谓程序框架图，简单解释一下，**注意这个就是以后你们工作中可能是这样去做的**，因为不同公司它也不一定完全按这个思路。

程序框架图就是要分析出——**这程序员你自己分析了，项目经理不一定帮你分析，但有些项目经理会给你分析**——分析出该模块**有多少个文件**。说白了就是多少个类，因为我们是面向对象嘛，**文件就是类，类就是文件**。

**以及和各个类或者叫文件之间的调用关系。**这个要画出来，协同关系要把它画出来、画好。画好过后，**你还要分层**——程序员需要按照架构师的要求进行分层设计。

你说："老师，我怎么知道他要让我干什么？"如果你连这个都不知道，那你跟架构师沟通起来就有障碍了。人家跟你说我们用 **MVC**，好吧？我们有一个界面层、一个业务逻辑层、一个数据层，还有一个持久层。你说"我听不懂"，那人家就让你走人了。

好，我们就把这个图画出来，画出来过后再去写代码。其实我们程序员也要简单地设计一下。比如老师现在要做这个东西了，那我做之前就要把我的程序框架图设计设计。设计设计过后，我明确有几个类了、调用关系也明确了，然后我再动手去写东西。

所以大家**不要上来过后就着急忙慌地往那儿写**。写了半天，不对呀，对不对？你要慢点，尤其是刚开始这块。

到这边我们才是真正地去写代码、代码实现。代码实现的过程一边写一边测。

最后把这个写完了过后，写完这个模块你交给谁呢？每到下午下班的时候一般都要出活的——你不能说"我干了一天"，人家问你"干了啥了？""我写代码呀。"你把代码写完，代码完了过后**你要提交给架构师**。

其实你不是把代码拷给他，**你是把代码提交给一个叫做 SVN 或者叫 Git 的服务器**，他们一定会到那里去看你的代码。负责任的看；不负责任的，估计一看"我明天要跳槽了，我才不管这事"。

有时候我们在工作的时候，你刚刚在这儿干一段时间，项目经理上哪儿去了？跑路了已经，跳到更高工资。所以有些缺乏安全感的人不太适合干程序员。但是好就好在你技术牛逼了过后，你发现哪儿跳都是一样，一看："咱们以前是同事哦。"

我们程序员你放心，失业的可能性很小。因为我们中国的整个信息化，跟发达国家像美国、日本、德国，还差一个很大的档次，所以还需要很多程序员去做。当然，目前随着发展，需要的程序员的层次是越来越高了——基础的程序员太容易培养了，他需要的是高级的。

我从事培训行业太早了，将近是 05 年下半年、06 年的样子，到现在有 12 年了，好多学生基本上都当项目经理了，有些当架构师。每次有同学说："韩老师，我要推荐一个人过来嘛。"工资真的是随便要，拿个三万、四万没问题。人家说："要求比较高，韩老师，你刚出来的暂时不要给。"我们都是熟人嘛，我也知道。但如果是你有别的做过高级的，帮我推荐过来——他需要这种人。**所以大家要赶紧成长。**

### 客户信息管理系统的这张框架图

好，代码实现完了过后，我们来画一下这个框架图。

因为我们的程序框架要分层，不能一股脑地把这些文件写到一个包里面去，每一个文件都有自己相应的功能，所以说我们做一个设计。

**第一个是 `customerView.go`。**这个文件干什么呢？它是用来做界面的，完成三个功能：第一，显示界面；第二，接收用户的输入；第三，根据用户的输入完成客户的管理——主要来说就是修改、删除、显示等等。

但是要注意一点：**它这虽然可以修改、删除和显示，但它本身并不是实实在在地做，它其实是调用下面的另外一个文件来完成的。**

**第二个是 `customerService`。**按照 MVC 的模式来说，还有一个文件是专门用来做业务处理的。它真正处理业务逻辑，完成对用户的各种操作——具体来说有增、删、改、显示等功能。关系就是：View 根据用户的输入调用 `customerService` 的方法完成对客户的管理，它调它，然后这边会返回一个结果给它。比如你要显示，我会把显示的数据提供给 View，然后你把它输出来就可以了；比如你要删除，我帮你删除过后就告诉你删除成功了还是删除失败了。在 MVC 这个角度它叫 V 界面，这个我们一般管它叫做**业务处理**。

**还有一层是 Model 层**，就是专门用来表示客户的，叫 `customer.go`。它是属于 Model，表示数据——它表示的是一个客户信息，里面有客户的各种字段。

```text
┌──────────────────────────────────────────────────────┐
│  customerView.go            界面层（View）           │
│  ① 显示界面  ② 接收用户输入  ③ 调用 Service 完成管理 │
│  自己并不真正做修改/删除/显示，只负责发起和呈现       │
└───────────────────────┬──────────────────────────────┘
                        │ 调用；View 持有一个 CustomerService 实例
                        ▼
┌──────────────────────────────────────────────────────┐
│  customerService.go        业务处理层（Service）     │
│  增 / 删 / 改 / 显示 —— 真正执行，并把结果返回给 View │
│  持有一个 Customer 切片                                │
└───────────────────────┬──────────────────────────────┘
                        │ 使用；Service 持有一个 Customer 切片
                        ▼
┌──────────────────────────────────────────────────────┐
│  customer.go               Model 层（表示数据）      │
│  type Customer struct { Id / Name / Gender / ... }   │
└──────────────────────────────────────────────────────┘
```

读图：三条线是自上而下的**单向调用**——View 调 Service，Service 用 Model；反过来 Service 把结果返回给 View。数据本身存在 Service 持有的那个 `Customer` 切片里。

这里要说清楚了：**`Service` 里面会有一个 `Customer` 的切片。**为什么这么说？因为你既然要用 `CustomerService` 来对客户进行增删改查，那么这里面会声明一个 `Customer` 的切片，在这个切片里面可以包含很多 `Customer`——因为我们知道切片其实就是动态数组，它里面可以包含多个 `Customer` 数据，或者说多个 `Customer` 结构体的实例。

同样的道理，因为 `CustomerView` 要去调用 `CustomerService` 里面的方法来完成各种操作，**那它这里面也需要含有一个 `CustomerService` 的实例**，所以我们也把它写清楚，含有一个 `CustomerService` 字段。

到此为止我们可以看到，其实它是一个结构体——到时它们也都会做成结构体。

#### 编写顺序和方向的顺序是相反的

我们在进行开发的时候，顺序是这样的，请听我说：**在分析的时候我们是从界面到业务逻辑再到 Model 层；但是在开发的时候顺序刚好相反**——我们应该先写 Model（`Customer`），然后写 Service 层，最后再写最上面的界面层。

有了这样一张图，我们就可以具体地写代码了。

### Customer 该有哪些字段

既然我们已经知道编写顺序是先写 Customer，再写 Service，再写 View，那我们就来看看 `Customer` 应该写成什么东西。

`Customer` 表示的是一个客户信息，因此它需要含有客户必须的各个字段。我们从界面来分析——待会儿我们要显示的界面有编号、姓名、性别、年龄、电话和邮箱，那也就是说我们这一个客户信息**至少应该包含六个字段**，分别是 `Id`、`Name`、`Gender`、`Age`、`Phone`、`Email`。

```go
type Customer struct {
	Id     int
	Name   string
	Gender string
	Age    int
	Phone  string
	Email  string
}
```

现在我们把这个示意图、框架图放到笔记里面去，大家有一个认识。

这个图对我们来说有非常重要的指导意义，因此同学们一定要把它看懂。你如果没把这个图看懂的话，待会儿咱们写代码的时候就会比较吃力。

有了这个程序框架图做指导过后，我们就变得比较轻松了。**待会儿我们先完成第一个功能，就是显示主菜单和完成退出软件的功能。**注意，在写代码的时候，我们一定要根据程序框架图的设计方案来完成。

大家先把老师画的这个程序框架图好好消化一下，看看这种方式是不是更好去开发一个大型的项目。我们前面写的家庭收支软件其实是没有结构的，这个程序没有结构；**但是现在不一样了，我们有结构了**——我们有界面、有业务处理、有 Model，这个 Model 是用来表示数据的。程序框架图的设计我们先分析到这里。

## 主菜单和退出：先把框架图上的三块文件搭起来

### model：Customer 和它的工厂方法

我们先写第一个 model，文件叫 `customer`。

```go
package model

// 声明一个 Customer 结构体，表示一个客户信息
type Customer struct {
	Id     int
	Name   string
	Gender string
	Age    int
	Phone  string
	Email  string
}
```

它有哪些字段呢？`Id` 就是 ID 号，大家一看就知道；这是客户的名字、客户的性别、客户的年龄、客户的手机和客户的电子邮件。

但这里有一个思考题：**因为你将来这个客户信息会在哪里使用？**是不是到时候我们会在 `customerService` 这个文件去用？

既然如此，我们在 `Customer` 这个结构体里面应该给它提供一个方法——**给它提供一个工厂模式的方法，给它返回一个 `Customer` 这样一个对象实例**。这个我们以前讲过的。

```go
func NewCustomer(id int, name string, gender string,
	age int, phone string, email string) Customer {
	return Customer{
		Id:     id,
		Name:   name,
		Gender: gender,
		Age:    age,
		Phone:  phone,
		Email:  email,
	}
}
```

那 `return` 什么呢？同学们，你这里肯定要给我传参数吧？你不给我传参数，我怎么知道是什么呀？所以 `id int`、`name string`、`gender string`，传进来一个性别；再来一个 `age int`。

这个代码会越来越多，怎么办？可以换行写。老师以前讲过：**换行的时候要把逗号保留到上一行**。

然后这个地方我们就可以 `return` 一个这样的实例了——把值给它，`Id` 等于你传进来的 `id`，`Name` 等于你到时传进来的 `name` 值，再来 `Gender` 返回一个 `gender`，`Age` 返回一个 `age`，`Phone` 返回一个 `phone`，`Email` 你给我一个 `email` 我就把它存进去。

保存一下，这里会有很多错误，是为什么？他说一个"无效的"——是不是当时我有一部分代码是从别的地方拷贝过来的，里面有一些字符可能出了点问题。

> **提示**：遇到这个问题大家不要怕，清一下就可以了。有时候你在粘贴代码的时候，有可能会把一些特殊的字符、或者说它不能识别的字符也粘过来了。**最好的方法就是先把它放在记事本里面，放进去再清一下再粘过来**，把格式给它去掉再粘贴。

#### 结构体和主菜单方法

既然我们讲过要把界面的显示功能封装到 `customerView` 里面去，于是乎我们要写一个结构体：

```go
type customerView struct {
	key  string // 接收用户的输入
	loop bool   // 表示是否循环的显示主菜单
}
```

> **提示**：因为目前这个结构体它就是在本文件用，所以说这个 `c` 可以不用大写，能明白吧？

现在我们先来写方法，就是显示主菜单：

```go
func (this *customerView) mainView() {
	// for 循环显示菜单，接收 key，switch 分派
}
```

`customerView`，我们来写一个 `cv` 吧，简单这样写。给它绑定一个方法，干什么呢？叫 `mainView`——主菜单。

这个主菜单怎么显示呢？还是老规矩，用 `for` 循环，我们以前是不是用过这个方式？

```go
for {
	fmt.Println("-----------------客户信息管理软件-----------------")
	fmt.Println("                 1 添 加 客 户")
	fmt.Println("                 2 修 改 客 户")
	fmt.Println("                 3 删 除 客 户")
	fmt.Println("                 4 客 户 列 表")
	fmt.Println("                 5 退       出")
	fmt.Print("请选择(1-5)：")
}
```

大家看是不是有点看不太习惯是吧？开始写了。第一个是 1，添加客户；紧接着 2，修改客户；再来一个 3，删除客户；第四个功能是显示客户列表；最后一个 5，退出。

最后我们还有一个叫它"请选择"，`fmt.Print`，**不要来一个换行了**。

#### key 和 loop 这两个字段是怎么来的

同学们又要思考了。因为你目前既然要让用户去输入一个 1 到 5，那是不是就意味着我们这个地方应该有个变量来接收他的输入？

所以我在定义一些字段。**第一个字段**就是这儿，我要用来接收他的输入，这个是必要的：

```go
key string // 接收用户的输入
```

**第二个**，如果他输入一个 5 的话，我是不是就退出了？因此我还有一个变量，还是老规矩，有个 `loop`：

```go
loop bool // 表示是否循环的显示主菜单
```

这个用来表示是否循环地显示主菜单。在前面我们其实用过这个方式，还记得吧？

有了这个过后，来做一个判断、接收它一下。现在我们就接收了：

```go
fmt.Scanln(&this.key)
```

`cv` 里面有一个——干脆这样子，为了偷个懒，全部叫 `this` 算了，`&this.key` 没问题吧？

然后用 `switch` 语句进行判断：

```go
switch this.key {
case "1":
	fmt.Println("添 加 客 户")
case "2":
	fmt.Println("修 改 客 户")
case "3":
	fmt.Println("删 除 客 户")
case "4":
	fmt.Println("客 户 列 表")
case "5":
	this.loop = false
default:
	fmt.Println("你的输入有误，请重新输入...")
}
```

如果输入的是 1，这个时候干什么事呢？这个地方**我们先输出一句话**，就说"添加客户"。其他依次类推：case 2 是修改客户，case 3 是删除客户，这个比较简单我就不啰唆了；输入 4 就提示"显示客户列表"。

**最后一个第五个比较关键。**如果是 case "5"，它就表示要退出了。如果要表示退出，我就把 `loop` 置成一个 `false`，表示他要退出了。

最后还有一种情况：他输的不是 1 到 5，怎么办？`default`，提示一句话"你的输入有误，请重新输入..."。

下面同学们，我就要判断你这个 `loop` 现在是不是已经为 `false` 了：

```go
if !this.loop {
	break
}
```

如果说 `this.loop` 为假，我取反就为真了；如果它为假了我就 `break`。**这个地方的 `break` 相当于就是跳出整个 `for` 循环了**，明白这意思吧？

跳出这个循环过后，我们这儿再打一句话：

```go
fmt.Println("你退出了客户关系管理系统...")
```

肯定就退出来了。

## 显示客户列表与添加客户：客户管理系统的三层结构第一次跑通
> 对应块：BLK89 | 覆盖分集：P240-P241 | 块标题（分集名）：《238_尚硅谷_客户管理系统-显示客户列表》

上一个功能刚收尾，我们接着往下做——客户信息管理系统的第二个功能：**显示客户列表**。

还是老规矩，一边做一边记笔记。每个功能都是同三步曲：**功能说明、思路分析、代码实现**。这三个词你一定要在心里立成条件反射，后面添加客户、修改、删除、查询，全是这个套路走一遍。套路走顺了，写代码才不会慌。

---

### 老规矩三步曲：功能说明、思路分析、代码实现

#### 功能说明

功能说明就是把"这个功能到底完成一件什么事"讲清楚，不用 fancy，一张界面图就够了。

我们输入"显示客户列表"之后，要把客户列表里所有客户的信息都展现出来——编号是多少、姓名叫什么、年龄多大，全都要摆出来。就这么一句，功能就说完了。

#### 思路分析

思路分析才是这一讲真正要练的东西。

大家想一想，要在 Service 里面写一个方法，能把这个客户所有的信息给显示出来。写什么方法？姑且就叫 `List` 方法，它要返回客户信息。

> **定义**：客户信息其实就是**切片**。我们把所有客户信息都放在切片里面，所以"返回客户信息"等价于"返回这个切片"。

同样的道理，在 `CustomerView` 里面也应该编写一个方法，就叫 `list`，去调用 `CustomerService` 的 `List` 方法，然后把客户列表显示出来。

到这里还不够。这里头有个坑：你在 `CustomerView` 里要调 `CustomerService` 的方法，那你的 `CustomerView` 得**先拥有一个 CustomerService 字段**。没有这个字段，你连调都调不到。

所以第三步：`CustomerService` 里还得再编写一个方法——`NewCustomerService`，返回一个 `CustomerService` 实例。有了这个实例，View 才能拿它去调 `List`。

于是这一步的思路就清晰了：

```text
┌─────────────────────────────┐
│  CustomerView (界面层)       │
│  ├─ customerService 字段      │
│  └─ list() ──────┐            │
└──────────────────┼────────────┘
                   │ 调用
                   ▼
┌─────────────────────────────┐
│  CustomerService (业务逻辑层) │
│  ├─ NewCustomerService()     │
│  │     └─ 返回 *CustomerService
│  └─ List() ──► 返回 []model.Customer
└─────────────────────────────┘
```

"其中一个 `List` 方法去调用 `CustomerService` 里面的方法"——记住这个套路，等一下写添加客户的时候你会发现，套路是**一模一样**的。

---

### 代码实现：先把 service 造出来

打开 `service` 包，我们先写那个能造出实例的方法。返回什么类型？我们返回一个指针类型：

```go
func NewCustomerService() *CustomerService {

}
```

New 一个 CustomerService，返回的是指针类型，这没问题。

然后怎么返回它？注意这个结构体里有两个属性。为了能看见效果，我们初始化一把，让切片里先躺着一个客户，不然你运行起来是个空列表，还以为代码写错了。

```go
func NewCustomerService() *CustomerService {
	customerService := &CustomerService{}
	customerService.customerNum = 1

	customer := model.NewCustomer(1, "张三", "男", 20, "112", "zhangsan@sohu.com")
	customerService.customers = append(customerService.customers, customer)
	return customerService
}
```

逐句拆开看：

- `customerService := &CustomerService{}`——先把这个对象创建出来；
- `customerService.customerNum = 1`——编号先默认给个 1，这个字段是留着后面分配新客户 ID 用的；
- `customer := model.NewCustomer(1, "张三", "男", 20, "112", "zhangsan@sohu.com")`——先造一个客户出来。注意这个 `NewCustomer` 是我们在 `Customer` 里早就写好的方法，id 直接写 1，名字叫张三，性别男，年龄 20，电话号码 112，邮件 `zhangsan@sohu.com`；
- `customerService.customers = append(customerService.customers, customer)`——用 `append` 把它塞进切片。

> **易错点**：`append(切片, 元素)` 的第一个参数就是**原来的切片**。写成 `append(customerService.customers, customer)`，含义是"在 `customerService.customers` 的基础上增加一个 customer"，返回值再赋回去。这一句看不懂的同学，把前面切片的基础部分再回去过一遍。

保存一下看看有没有代码错误。

#### 两次编译报错，各教你一件事

第一次报错：`undefined: NewCustomer`。

好懂——这个 `NewCustomer` 是在 `model` 包里定义的，不在当前包。所以前面得加包名：

```go
customer := model.NewCustomer(1, "张三", "男", 20, "112", "zhangsan@sohu.com")
```

改完再保存，第二个报错来了：`is not a type`。

这个错更有意思。你看清楚了，我定义的是一个**方法**，不是一个类型。我刚才把它当类型用了，所以报 `is not a type`。要调方法，得用小括号：

```go
customer := model.NewCustomer(1, "张三", "男", 20, "112", "zhangsan@sohu.com")
```

> **提示**：`model.NewCustomer` 是**函数/方法名**，后面跟参数列表；`model.Customer` 才是**类型名**。这两者只差一对小括号，编译器的报错就在这儿。

#### 再写 List：把切片原样交出去

造出实例还不够，别人 View 那边要调的可是 `List`。这个方法你事先必须写好：

```go
func (this *CustomerService) List() []model.Customer {
	return this.customers
}
```

`this` 走接收者，然后 List 返回切片，那就 `return this.customers`，完事了。返回类型是 `[]model.Customer` 这种切片。

这个 Service 侧的两个核心方法，到这儿就写完了。

### 代码实现：view 侧接住 service

回头来写 `CustomerView`。

#### 先加字段

`CustomerView` 里面应该首先含有一个 `CustomerService` 的字段。为什么要有？因为我要通过 Service 里面的方法来调用它们。没有这个字段，我没办法调用，那就不满足面向对象编程的基本要求了。

```go
type CustomerView struct {
	customerService *service.CustomerService
}
```

但你这样写肯定失败，因为 `CustomerService` 并不在 `main` 包里，它在 `service` 包里，所以得把包引进来。从 `src` 下面开始引：

```go
import "go_code/customerManage/service"
```

引完之后，`*service.CustomerService` 这个指针类型就成立了。

#### 再在创建 View 的时候顺手初始化

现在有了这个字段，那它在哪儿初始化比较合理？显然是在创建这个 View 的时候，顺带把 CustomerService 也创建起来。注意听：**是初始化结构体的 customerService 这一个字段**，不是整个结构体。

```go
customerView.customerService = service.NewCustomerService()
```

`NewCustomerService` 需要传参数吗？不需要。所以初始化到此完成。此刻 `customerView` 已经包含 `customerService` 字段，而且已经被初始化了。

#### 写 list：取数据、打表头、遍历

有了初始化，现在就可以在 `CustomerView` 里写 `list` 方法了。

```go
func (this *CustomerView) list() {
	customers := this.customerService.List()

	fmt.Println("---------------------------客户列表---------------------------")

	for i := 0; i < len(customers); i++ {
		fmt.Println(customers[i].GetInfo())
	}

	fmt.Println("-------------------------客户列表完成-------------------------")
}
```

先获取当前所有客户信息——所有信息都在切片里，很好处理；因为这里已经初始化了一个 `customerService`，所以就一行：

```go
customers := this.customerService.List()
```

此刻这个 `customers` 就是切片了，我把 Service 里的切片拿了过来。眼下它里面只有一个用户，因为我只初始化了一个；想加多个客户当然也可以，后面通过动态输入来添加。

显示的部分，先打表头，打完客户信息之后再打一个"客户列表完成"的表尾。为了好看，我们用制表符 `\t` 来控制格式。

然后就是遍历。我用一个最简单的方式：

```go
for i := 0; i < len(customers); i++ {
```

把切片大小统计出来，`i++`，每取出来一个就是一个客户。

#### 格式化输出：把 GetInfo 塞回 Customer 自己身上

我问大家一个问题：此刻这个 `customers` 是不是就是所有客户信息？因为 Service 里维护了一个切片，我把切片也拿到了，显然对它遍历一下就行了。

那怎么打印？按最笨的办法，你可以一句话一句话地打：

```go
fmt.Printf("%v\t", customers[i].Id)
fmt.Printf("%v\t", customers[i].Name)
// ……性别、年龄、电话，一个一个写
```

这样**可以完成**，但是"太 low 了"。这六个字段你要写六遍，客户字段一改，你得回来改六个地方。所以我们干脆**把这个方法直接封装到每一个客户里面去**：

```go
func (this Customer) GetInfo() string {
	info := fmt.Sprintf("%v\t%v\t%v\t%v\t%v\t%v",
		this.Id, this.Name, this.Gender,
		this.Age, this.Phone, this.Email)
	return info
}
```

写一个方法叫 `GetInfo`，返回一个字符串不就完了吗？先 `fmt.Sprintf` 把这六个字段格式化、拼成一个字符串，再 `return info` 就行。注意这里接收者是**值类型** `Customer` 而不是指针——我们只是想读它的字段，不需要改，没必要传地址。

六个 `%v\t` 依次对应：ID、名字、性别、年龄、电话号码、电子邮件。这样子就能体现出**封装**的特点了。

这里会报一次错：没有引包，把 `import "fmt"` 引进去就完事。

有了这个方法，显示的时候就没有必要一个一个地取出来了。而且将来这个 ID 假设人家是小写的，你照字段名那样写还取不出来呢。有了方法，直接一句话：

```go
fmt.Println(customers[i].GetInfo())
```

调用 `GetInfo()` 把它输出来就行了——它返回的就是当前客户的信息，而且已经格式化好了。

#### 挂到菜单上

保存一下。当用户输入 4 的时候就是显示客户列表，那这个时候我们就把原来那段代码换成：

```go
this.list()
```

`this` 就是 `CustomerView`，`CustomerView` 里面又写了一个 `list` 方法，这个 `list` 方法又去调了我们 Service 里面的 `List`。

大家可能会有点犯嘀咕：为什么这么麻烦？

> **结论**：这就叫**结构**。如果我们没有这种结构，直接用 View 去调用 Customer，我告诉大家，后面我们的代码就会越来越难写。而当我们用了这种结构——有界面层、有业务逻辑层、有 Model 层——这样的代码扩展性、可读性都会非常好。

大家现在如果还没有体会的话，后面我们写修改、删除和查询的时候，会更加体现出它的优势。

#### 三层结构长什么样

我们把这个流程再走一遍：创建了 `CustomerView`，而且初始化了它里面的 service；这个 service 里面是有方法的；然后我给 `CustomerView` 里面写了一个 `list` 方法；这个 `list` 方法上去以后，先调用 `CustomerService` 里面的 `List` 方法把客户信息拿到；拿到以后输出表头还有表尾；然后遍历从 `CustomerService` 里获取到的所有客户信息，调用 `Customer` 它本身的一个方法叫 `GetInfo`，把客户信息返回来，进行格式化的输出。

```text
┌────────────────────────────────┐
│  CustomerView  (界面层)         │  重点：跟人打交道
│   字段 customerService           │
└───────────────┬────────────────┘
                │ 调用 List()
┌───────────────▼────────────────┐
│  CustomerService (业务逻辑层)   │  真正干活的
│   customers 切片  ← 数据         │
└───────────────┬────────────────┘
                │
┌───────────────▼────────────────┐
│  model.Customer (数据层)        │  一个客户长什么样
│   GetInfo()                     │
└────────────────────────────────┘
```

大家一定要记住，写程序就是要由结构、由框架的概念。你不能说我上来过后，把所有的功能都写到一个文件里面去。

> **结论**：没有这个分层的概念，我可以负责任地告诉大家，这个程序只要稍微大一点点，你立即就看不懂了。界面层是跟用户打交道；业务逻辑层是真正干活的；Model 层是数据。这里面的切片维护了所有的客户信息，而上面那层重点是调用 Service 里面的方法来完成相应的处理。

#### 盖房子那个比喻

说完结构，我想说一个初学者特别常见的问题。

写代码的时候，每完成一个功能，其实是这儿 Go 文件改了一点，那个 Go 文件增加了一点。初学者可能不太适应，他会问："老师你为什么一会儿在这个文件写，一会儿在那个文件写，一会儿这儿增加一点，那个地方又修改点？"

写程序跟盖房子不一样。我们盖房子是第一层盖了盖第二层，第二层盖了盖第三层。但是写代码呢，它其实是一个**反复、螺旋递增**的过程。同一个文件，完成这个功能的时候你会加点东西，完成那个功能的时候你会修改一点东西。大家在这儿一定要想明白。

我在整理代码的时候，不可能每次都把代码重新给大家抄一遍，也没有必要。板书时我只把**变化的代码**标成蓝色——哪些方法是新增的、哪些地方是修改过的，一目了然。

这个功能我们一共改了三个文件：

- `model` 包下面的 `customer.go`：**增加**了一个方法 `GetInfo`，返回用户信息；
- `service` 层：**增加**了两个方法，一个是返回 `*CustomerService` 指针类型的 `NewCustomerService`（并做了初始化），一个是返回客户切片的 `List`；
- `view` 层：变化最多。**增加**了一个字段 `customerService`，**增加**了一个 `list` 方法，另外在创建 View 的时候**修改**了初始化，顺手把这个字段也初始化了。

好，关于显示客户列表这个功能，我们就介绍到这里。大家好好地消化和吸收一下。

### 添加客户：同一个套路再走一遍

前面完成了显示客户列表，现在我们来完成下一个功能——添加客户。

怎么样来完成一个添加客户的功能呢？还是老规矩，**功能分析、思路分析、代码实现**。

#### 功能说明

我们这个菜单里说得很清楚：如果用户输入 1，就表示他要添加一个客户。那么当他输入 1 的时候，我们就会出现一个界面，让他来输入这一个新客户的信息，然后把这个客户添加到我们的客户切片里面去。

#### 思路分析

要动的地方清楚了。因为 `CustomerService` 才是真正完成对客户增删改查的，所以代码从这里开始加。

要添加客户，编写一个方法，叫 **Add**。这个 Add 方法就是将新的客户加入到 `customers` 这个切片里面去——因为你所有的用户都在这个切片里面嘛。而且我们显示的时候也是找的这个切片，那这样子最新的客户就会被显示出来。

同样的道理，你这儿加了 Add，那 `CustomerView` 里面是不是也应该写一个 Add 方法？它去调用 `CustomerService` 里面的 Add 方法。这样子才体现一种封装的效果。

你看，这个套路是不是已经出来了。大家要有所体会——你在学习的时候，一定要体会编程的一种思想和编程的一个结构，这样子写代码才会做到游刃有余。

### service 侧的 Add：往切片里 append 一个 Customer

打开 `CustomerService`，我们做一个方法，把添加客户到 customers 切片中。这个难不难呢？不难，照着这个写就可以。

```go
func (this *CustomerService) Add(customer Customer) bool {
	this.customerNum++
	customer.Id = this.customerNum

	this.customers = append(this.customers, customer)
	return true
}
```

- 你在 Add 的时候应该给我传过来一个什么东西？是不是应该给我传过来一个 Customer？所以我就写个 `customer Customer`，你给我一个 Customer，我就把它放进去了——这个切片是 Customer 这种切片；
- 返回一个 bool 值，表示成功还是失败。

这里有个细节要特别注意。

我们在添加这一个 Customer 的时候，其实这个 Customer 已经在 View 这一层构建好了，实例已经在 View 那一层给你构建好了。所以你要做的一件事情非常简单：把这个 Customer 加到这个切片里面就可以了。

```go
this.customers = append(this.customers, customer)
```

就是在它的基础上将你这个最新的 customer 加进去。加进去以后下一步要做的事情也很简单——返回一个 true。当然如果说这块添加失败的话，你就返回一个 false。一般情况下不会产生一个 false，所以我就直接返回一个 true 就完事了。

### view 侧的 add：五个输入项和一个不给你输入的 ID

写完了 Service 侧的 Add，紧接着应该写哪个文件？同学们想一想——是不是应该写上面这个 Add 方法了？因为你这个 Add 方法要调用它的 Add 方法嘛。

打开 View，我们就在 `list` 的下面写，方法叫 `Add`：

```go
func (this *CustomerView) add() {
	fmt.Println("添加客户")

	var name string
	fmt.Scanln(&name)

	var gender string
	fmt.Scanln(&gender)

	var age int
	fmt.Scanln(&age)

	var phone string
	fmt.Scanln(&phone)

	var email string
	fmt.Scanln(&email)

	customer := model.NewCustomer2(name, gender, age, phone, email)

	if this.customerService.Add(customer) {
		fmt.Println("添加完成")
	} else {
		fmt.Println("添加失败")
	}
}
```

界面是这么设计的：先把"添加客户"这句话提示出来，然后一句句地提示用户输入。

- 第一个是**姓名**，那我们应该有一个变量来接收：`name`，初始化为空，然后让它输入——`fmt.Scanln(&name)`，其它以此类推；
- 下一个是**性别**，`gender`，初始化为空，让它输入；
- 再下一个是**年龄**，用 `age` 接收，初始化给它一个 0，然后让它输入；
- 再下一个是**电话号码**，`phone`，保持跟 Model 里的字段名一致，它也是个字符串；
- 再下一个是**电子邮件**，就叫 `email`。

到此为止，我们就接收到客户端输入的姓名、性别、年龄、电话号码、电子邮件了。

#### 那个没让你输入的 ID

有了这些信息过后，我们要构建一个新的 Customer 实例。但问题来了——**大家有没有发现这个 ID 我们并没有输进去？**

为什么我们不输 ID 呢？因为这个 ID 我们并不希望它去指定，我们希望系统给它分配一个 ID。

大家注意这里面有个细节：ID 号没有让用户直接输入。为什么呢？因为 ID 是唯一的，需要系统分配。你们有没有注意到，你们去注册一个 QQ 号，会发现 QQ 号也不是让你指定的，而是系统给你分配的，对不对？所以说这个 ID 我们要系统分配。

那问题就来了：我们 `NewCustomer` 其实是要输一个 ID 的，所以这就比较郁闷了。那怎么办？我们**再构建一个不带 ID 的**、不需要传入 ID 的第二种创建 Customer 实例的方法，这个方法是不带 ID：

```go
func NewCustomer2(name string, gender string, age int, phone string, email string) *Customer {
	customer := &Customer{
		Id:     2,
		Name:   name,
		Gender: gender,
		Age:    age,
		Phone:  phone,
		Email:  email,
	}
	return customer
}
```

把 ID 那一行去掉，这个 ID 到时我让系统给它分配。

回头到 View 里，我们就可以构建 Customer 了：

```go
customer := model.NewCustomer2(name, gender, age, phone, email)
```

刚才我们在 model 里面写了一个 `NewCustomer2`，它是公开方法，所以这里点一下包名就可以了。

有了 customer 以后，下一步就是调用 `this.customerService.Add(customer)`，把这个 customer 传进去就完事了。

### 分配 ID 的规则，和那个必须点亮的星号

现在的问题又麻烦了：你的 customer 是没有带 ID 的，所以在真正 Add 这一个 customer 的时候，这个方法应该要去给这个新的客户**分配一个 ID 号**。

这样一回头，我们发现前面写的这个方法有问题——它是直接把 customer 加到了切片里面，但此时此刻这个 customer 是没有 ID 的。那怎么办呢？我们定一个规则。

> **结论**：我们确定一个分配 ID 的规则，就是**添加的顺序**——添加的顺序就是它的 ID。

前面我们不是给这个 `customerService` 定了一个字段 `customerNum` 吗？既然如此，干脆就用这个字段加 1 作为新客户的 ID。

你看我原先在讲的时候其实就说明白了：

```go
this.customerNum++
customer.Id = this.customerNum
this.customers = append(this.customers, customer)
return true
```

加一个我就增加一个，加一个就增加一个。ID 是它的数量加 1——比如你是第五个加入的，那你的 ID 就是 5 号。然后我把这个分配给传进来的 `customer.Id`，再 append 一下。

> **易错点（重中之重）**：注意这里我用的是 `this *CustomerService`，是**指针类型**。
>
> 如果你这地方没有星号，我可以告诉大家，你永远只能得到一个客户。因为你每次来了过后它就是一个**值拷贝**——一值拷贝，那你原先切片里面的信息就丢掉了。你会发现加一个客户仍然看不到新的；或者说更糟的情况，你新加的客户能看见，但原先的客户全丢了。
>
> 大家一定要用 `customerService` 这个**指针**的方式来给这个方法绑定的。不然的话，你每次添加一个新客户过后它会分配一个新的 `customerService`，那你以前的客户就丢掉了。

这块有点绕，我们再理一遍。

大家看，我写的是 `this.customers`，这个 `this` 其实就是 `CustomerService`，而 `CustomerService` 又是引用传递。因此在我整个进行管理的过程中，**其实我只有一个实例**——就是这个 CustomerService，始终是第一次创建的那个 CustomerService 实例。

知道结构体实际是值拷贝、但指针是地址拷贝之后，很多疑惑就通了：我们用的是一个 customerService，就保证你的这一个切片一直是同一个切片；你的增删改查都是针对同一个切片来完成的。所以这点很重要，尤其是初学者很容易在这儿搞蒙圈。

把 ID 分配做完以后，下面的代码就比较 easy 了：做一个判断，如果添加成功（这里当然肯定是成功了，因为我并没有考虑失败的情况），就打印"添加完成"；当然如果真的失败了，我们也留一个接口、留一个判断，那就打印"添加失败"。

#### 挂到菜单上

代码写完了以后不要忘了一件事情：原先在这个地方输入 1 添加客户的时候，并没有调这个方法；现在怎么调？是不是 `this.` 点我们的这个 `add` 方法，完事了。

这个 `add` 方法不需要传东西，它在里面让你输入信息，然后构建一个新的客户传给 Service 的 `Add` 方法，完成这个操作。

## 删除客户与退出确认：一次切片手术，和一份被留到最后的作业
> 对应块：BLK90 | 覆盖分集：P242-P243 | 块标题（分集名）：《240_尚硅谷_客户管理系统-删除客户》

接着把删除客户这个功能完成掉。

老规矩，功能说明、思路分析、代码实现，我们还是分阶段来。好，先板书一下：先是功能说明——咱们要完成一个什么事；然后思路分析；最后代码实现。

删除客户看着简单，但它是这套 CRUD 里第一个真正碰到"**从切片里把东西挖掉**"的功能，所以坑也在这里。

---

### 功能说明：为什么必须先来一句"你确定吗"

我们要完成的功能很明确：当用户输入"删除客户"这个选项以后，程序会提示他——**请选择待删除客户的编号**。

- 如果他输入一个 `-1`，就代表他不想删除了，放弃操作；
- 如果输入的是其他数字，我们就去删除这个 ID。

但这里有一个问题：如果他输入的这个 ID 号不存在，我们应该给他提示"删除失败、ID 不存在"这样一个信息。所以这个分支你必须考虑到。

而且他输入了具体编号以后，我们在这个地方**应该再给他提示一下是否真的要删除**。如果输入一个 `y`，就代表真的要删除。然后根据他输入的 ID 去查找这个客户，再把它删除。要是找不到这个 ID 呢？那就提示没有这个 ID 号、删除失败。

看清楚了吗？删除这个功能，天然带着两层确认：**先确认"删谁"，再确认"真删吗"**。

---

### 思路分析：为什么你必须额外写一个 FindById

打开我们这一个程序框架图。既然你要去删除一个客户，那显然在 `CustomerService` 里面要添加一个方法了。编写什么方法呢？`Delete`。这个方法会接收一个 ID 号——你到时给我传个 ID 过来，我去删除一个客户。

但是有一个问题：我们在删除的时候，肯定要去查找这个 ID 到底存不存在，才能决定是否真的删除。

因此我们最好**还要单独地写一个函数**——`FindById`，根据 ID 去查找一个客户的方法。这样更好管理，更容易组织我们的程序。

这个地方也可以写成一个大写，因为别的地方也可能用到这个方法，对不对？同样，它也接受一个 ID，然后这个地方就会返回这个 ID 号对应的**切片的索引，切片的下标**。

> **结论**：为什么非要返回下标？因为你最终是要**从切片里把这个用户干掉的**。你不知道这个客户对应的切片下标，你是没有办法删除的。

#### 有些同学说："老师，你这个 ID 不就是对应的切片的下标吗？"

**不一定，不一定啊同学们。**

大家想，我们这个客户的 ID 号是在不停增长的。也有可能你原先有一个客户删除了，然后你又加一个新的——加一个新的话，它的编号是在不停地往上涨的。所以说这个客户的 ID 和它对应的切片下标**不一定相等**。

真正删除一个客户，其实你要找到的是这个客户对应的**切片下标**，也就是这个 customer 切片里它是在第几个位置。因此这两个方法我们都要完成。

#### 完整的关系图

同样的道理，写完以后，在我们的 `CustomerView` 里面还得编写一个方法叫 `Delete`，这个方法去调用 `CustomerService` 里面的 `Delete` 方法，完成客户删除。

```text
┌──────────────────────────────┐
│  CustomerView                 │
│  Delete()                     │  ← 界面：问编号、问确认
└───────────────┬──────────────┘
                │ this.customerService.Delete(id)
                ▼
┌──────────────────────────────┐
│  CustomerService              │
│  Delete(id) bool              │
│     └─ FindById(id) int  ──┐  │
└────────────────────────────┘ │
                               │
┌──────────────────────────────▼┐
│  customers 切片                │
│  [0]=1  [1]=2  [2]=4           │  ← Id 与下标可能对不上
└──────────────────────────────┘
```

看图就明白了：View 的 `Delete` 调 Service 的 `Delete`，Service 的 `Delete` 又先调自己的 `FindById` 问一句"这个人在哪儿"。所以我其实要在这儿编写两个方法，在 View 那儿编写一个方法，然后这个方法去调它。思路分析就到此为止。

### 代码实现：先写 FindById

打开 `service`，我们先写一个方法：根据 ID 查找客户在切片中对应的下标。如果没找到怎么办？返回 `-1`。如果没有该客户，返回一个 `-1` 就可以了——它如果返回一个 `-1`，我就知道你这个 ID 在这个切片里面是不存在的。

```go
func (this *CustomerService) FindById(id int) int {
	index := -1
	// 遍历 this.customers 切片
	for i := 0; i < len(this.customers); i++ {
		if this.customers[i].Id == id {
			// 找到
			index = i
			break
		}
	}
	return index
}
```

这时你给我传一个 ID 进来，有没有成功我返回一个 `int`。首先我们来进行一个查找——那怎么样我才知道有没有呢？那我肯定要遍历。

我先定一个 `index`，默认为 `-1`，默认我是找不到的。然后我遍历这个切片，看看有没有这个 ID。

这里我不用 `for range`，用一个普通的 `for` 就可以了：`i` 从 0 开始，`i` 小于 `len`，把这个切片的长度统计出来，`i++`。

判断是这样的：如果说你这个切片里面第 `i` 个客户它的 ID 就等于你现在要查找的这个 ID，那说明什么？**找到了**。找到的话，这个 `index` 就应该改成 `i`。然后 `break`，不用再往下找了。

最后 `return index`。那如果我找不到怎么办呢？找不到返回的就是 `-1` 了，`-1` 就代表没找到。

> **提示**：这里 `index` 初值为 `-1` 这个设计很关键。它让"找到"和"没找到"两种情况共用一个返回值，不用额外返回一个 bool，也不用定义错误变量。这种"用哨兵值表达失败"的写法在 Go 里非常常见。

### 代码实现：Delete 与那段切片手术

现在我们再来写一个方法，根据 ID 删除这个客户。当然是从切片中删除。老规矩，仍然跟结构体进行一个绑定：

```go
func (this *CustomerService) Delete(id int) bool {
	index := this.FindById(id)
	if index == -1 {
		return false
	}
	this.customers = append(this.customers[:index], this.customers[index+1:]...)
	return true
}
```

好的，那我也接收一个 ID，有没有删除成功我返回一个 bool 值。

首先我先看一下你准备删除的这个 ID 到底有没有。我用 `index` 来接收——`index := this.FindById(id)`。那这个时候这个 `index` 就有两种可能：一种就是找到了，它是一个非 `-1` 的；还有一种可能就是 `-1`。

那如果是 `-1` 就简单了。如果 `index` 等于 `-1`，说明没有这个客户——你输了一个 10，那么没有一个客户的 ID 等于 10。那我怎么办？那就不要走了，直接 `return false` 就完了。

否则的话怎么玩呢？那就找到了呗，找到就删除嘛。

#### 关键那一行

那怎么从一个切片里面把这个人干掉呢？其实非常简单：

```go
this.customers = append(this.customers[:index], this.customers[index+1:]...)
```

大家看这边很关键了。`append` 什么？它从 0 这个位置开始截取到 `index`——这里面是什么意思呢？就是我先用一个切片的方式，找到从 0 这边开始取，找到 `index`，但是**这个地方是不含 index 的**。

那后面这部分怎么写呢？后面就从 `index + 1` 到后面全部写完。但是后面这一部分，如果从后面全部写的话，这地方是不是可以空下来？但是因为你后面这部分**也是一个切片**，应该怎么写？`...`。应该是记得的啊同学们。

合起来是这样一幅图：

```text
原切片:  [ c0 | c1 | c2 | c3 | c4 ]
                      ↑
                    index=2

this.customers[:index]        → [ c0 | c1 ]        （不含 index）
this.customers[index+1:]      → [ c3 | c4 ]
append( 左, 右... )           → [ c0 | c1 | c3 | c4 ]
                                   ↑ c2 被干掉了
```

这样我们就把中间这个叫 `index` 的元素给干掉了。干掉完了以后，最后返回一个 `true`，完事了。

如果你忘了切片这个用法，去前面讲切片的章节看一看——入门介绍、包括使用、注意事项我全部都讲过。我不可能每次再去重讲一次，这也不现实，对不对？

### View 侧的 Delete：两层确认怎么落地

现在留了一个方法：`CustomerView` 要写一个 `Delete`，来调用 Service 的 `Delete` 方法完成这个删除。

打开 View，老规矩，现在我们写一个方法——得到用户的输入，然后删除对应 ID 的客户：

```go
func (this *CustomerView) Delete() {
	fmt.Println("删除客户")
	fmt.Print("请选择待删除的客户编号:")
	var id int
	id = -1
	fmt.Scanln(&id)
	if id == -1 {
		return
	}

	fmt.Print("确认删除，请输入(Y/N):")
	var choice string
	fmt.Scanln(&choice)
	if choice == "y" || choice == "Y" {
		if this.customerService.Delete(id) {
			fmt.Println("删除完成")
		} else {
			fmt.Println("删除失败，输入的 id 号不存在，请重新输入")
		}
	}
}
```

逐段看。

首先说"删除客户"，那删除客户的话他会提示这么一句话——请选择待删除的客户编号。我现在用 `id` 来接收一下，**默认我给它一个 `-1`**。

接收了输入以后，我就做一个判断：如果 `id` 等于 `-1`，说明什么？说明你想放弃，或者你就回车了——你回车就相当于什么都没输入，那这个 `id` 还保持 `-1`；如果你输入的是 `-1`，那它还是 `-1`。那说明这个时候你就不想删除了，直接 `return` 就完了，不做任何操作，相当于放弃删除操作。

如果它不等于 `-1`，那就说明他的的确确输了一个编号。这时候我们就可以调用 Service 的 `Delete` 方法来完成它。

那么这个怎么做呢？非常简单，我们来做一个判断，看有没有删除成功。

不过这里还没完——界面里还有没写完的地方，它还有一个确认是否删除，我在这儿还要提示他一句话：**确认删除，请输入(Y/N)**，否则就不删除了。

那我用 `choice` 来接收，默认给它一个空串，然后 `Scanln(&choice)`。

那我就会做一个判断。如果他输的不是 Y 和 N 怎么办？按理说他如果输的不是 Y 和 N，我们就让他反复地输才行，那这样子还得用一个 `for` 循环。

> **提示**：这里我先不做循环，就简单一点——如果他输的不是 Y 或 N，我们就不删除。这个循环判断你在前面学过，前面添加客户、删除客户都涉及到"用户输入的是不是我要的东西，不是我就让他重输"。这个不难，你可以自己把它加进去。

如果 `choice` 等于小写的 `y` 或者大写的 `Y`，我们都认为他要删除。在这这两种情况下，他就真的要删除了，于是我们就可以去调 Service 里面的 `Delete` 方法。`if` 为真就打印"删除完成"，`else` 就打印失败——"删除失败，输入的 id 号不存在，请重新输入"。

最后不要忘了一件事情：因为你要删除，所以说你这儿应该调用它一下——`this.Delete()`。

保存一下，看代码能不能跑起来。目前有一个错误，点进去一看，这地方是等号吧？应该是等于，而不是赋值。这样就没问题了，再保存一下。

### 跑一遍：编号会空着，这是故意的

来运行一下。我先退出，重新玩一把。

- 先列出，目前有一个张三；
- 添加一个客户汤姆：男，20，电话 112，电邮 `tom@sohu.com`，回车。列出来，目前有两个客户；
- 再加一个 Mary：女，年龄 25，电话 113，电邮 `mary@qq.com`。列出来，三个客户。

现在我们准备把 2 号汤姆删掉。输入 3 号，它说"请选择待删除的客户编号"，我输一个 2，回车。它问我"是否确认要删除"，好的，我就输一个 `y` 吧。它说"删除完成"。我们再来列出来一下，看看 2 号还有没有——删掉了。大家可以看到 2 号已经没有了。

#### "2 号没有了，这个编号不就空着了吗？"

空着就空着，无所谓。在我们的实际开发中，这个编号空了，就是**曾经被占用过**，我们就不去用它了。

如果你要用它的话也可以，那你就得把 3 号客户往前面挪一下，把它变成 2 号。但一般来讲业务逻辑不会这么处理。大家想一想，一个人的编号是唯一标识他的，你不能说你刚刚加进来的时候他的编号是 3，结果过了一段时间编号变了——编号变了这个人自己都不知道自己是什么号了。

> **提示**：打个大家都有的比方：你在学校里面，学生一般会有一个学号。有了这个学号过后，如果我们班有一个学生退学了，大家的编号都会变一下吗？不会变。没有就没有了，无所谓。这样子业务处理也是合理的，咱们不用把这个 3 号变成 2 号，没有必要。

所以接着上面的演示走：我们再加一个史密斯进去，男，56 岁，电话 115，邮箱这次是 sina.com，回车。大家想一想，当我加了一个新的客户过后，这个时候他的编号应该是几呢？它的编号应该是在 3 的基础上加了一个 1，就变成 4 了。来走一个 4，列出来——史密斯变成了 4 号，没问题。

```text
阶段                  Id          切片内容（Id）
---------------------------------------
刚初始化              1           [1]
添加汤姆              2           [1, 2]
再添加 Mary           3           [1, 2, 3]
删除 2 号汤姆          —           [1, 3]      ← 下标塌陷
添加史密斯             4           [1, 3, 4]
```

你看这张表就明白了：删除之后，3 号 Mary 的**下标**从 2 变成了 1，但她的 **Id** 仍然是 3；新来的史密斯 Id 是 4，下标却只有 2。所以 `FindById` 那一次遍历是**省不掉**的。

好，我们继续来删除。这次我故意删除一个不存在的编号，比如 89。它说"是否要删除"，回车。它说"删除失败，输入的 id 号不存在"，完全正确。最后我退出系统。

### 顺手补上：退出确认

我们继续来完成客户信息管理系统的其它功能，先把项目功能进行一个完善——**完善退出确认功能**。

这个本身就是**一个课后作业**，是让同学们自己去做过的，大家先看一看要求是什么。

功能说明：要求用户在退出的时候，在退出时提示确认是否退出，用户必须输入 `y` 或者 `n`，否则就循环提示。

目前我们项目是怎么回事？一跑起来，输一个 5 就直接退出了。其实不太人性化，没有考虑到用户的体验——也有可能人家输错了，也是有可能的。因此输入一个 5 过了之后，我们需要让他确认到底是不是真的要退出。

#### 思路分析：这一次连 Service 都不用碰

思路分析其实挺简单的。如果要完成这个功能，它**只涉及到界面这个层面**，也就是说只需要在 `CustomerView` 里面做一些变化和调整即可。而我们的 `CustomerService` 和 `Customer` 这个 model 是**不需要变化**的。所以这个还是比较简单，相对来说也是比较清晰的。

我们来完成这么一个功能：功能说明、思路分析、代码实现。

功能说明其实很简单，就是要求用户退出时必须输入 `y` 和 `n`，如果输入的不是 `y` 和 `n`，，那么就循环地提示。这里只需要去修改 `customerView.go` 这个文件。

#### exit 方法

找到 `customerView`，是不是主要是在这里进行一个控制？同样，我们是不是也可以把整个封装到一个方法里面去更合理一点？所以把这个删除了，我们写一个退出功能。

```go
func (this *CustomerView) exit() {
	for {
		fmt.Println("确认是否退出(Y/N):")
		fmt.Scanln(&this.key)
		if this.key == "Y" || this.key == "y" || this.key == "N" || this.key == "n" {
			break
		}
		fmt.Println("你的输入有误，请重新输入(Y/N):")
	}

	if this.key == "Y" || this.key == "y" {
		this.loop = false
	}
}
```

这里我们是这样说的：确认是否退出，输入 Y 和 N。输入 Y 和 N——这个时候我们就接收到他的输入。

输入的话，其实可以用这个 `key`。因为这个结构体里面是有一个 `key` 的，我们可以用这个 `key`，也没有关系，我们就不去定义新的变量了。所以我们就这样接收一下：`fmt.Scanln(&this.key)`。

拿到这个，我们就要做一个判断了。**为什么循环？因为这儿不循环的话，假设他输的不对，你不就直接退出了吗？** 所以我们要循环。

如果 `this.key` 等于大写的 `Y` 或者小写的 `y`，假设我们这两个都可以；或者 `this.key` 等于大写的 `N`；或者等于小写的 `n`。输入的必须是这几个字符，这个时候我们就 `break`，退出这个 `for` 循环。否则，我们就提示一句话：你的输入有误，请重新输入(Y/N)。让他再重新输入就行了。

最后，退出这个 `for` 循环只有一种可能，就是它**必须**是 Y 或者是 N。那这个时候我们就做一个判断：如果他输入的值就是大写的 `Y` 或者小写的 `y`，这时我们将这个 `loop` 改成 `false` 就可以了。如果他输入的是 `N`，那我就相当于不退出，那我仍然保存这个 `loop` 为 `true`。

#### 指针这一课，又上了一遍

因为在这个地方一旦改成了 `false`……大家注意听，`this` 大家都知道它是一个 `*CustomerView` **指针**，所以在这个地方的 `this.loop` 和 mainView 里面使用的 `this.loop` 是**同一个**。

> **结论**：也就是说，我在这里改变了 `loop`，其实在 mainView 里面的 `this.loop` 也被修改了。因为你们用的都是**同一个 CustomerView 实例**。

> **易错点**：同学们一定要非常清晰地知道，你这个地方引用是非常重要的，它是个指针类型，非常重要。如果**不是**指针类型，那就麻烦了——CustomerView 在这地方修改的 `this.loop` 和那个地方的 `this.loop` 就不**是**同一个 loop 了。

这个道理跟前面 Service 用 `*CustomerService` 是一模一样的，只不过这次改的是"要不要继续循环"这个开关。

现在我把这一个地方调整到这里来：`this.exit()`。

#### 跑一遍

- 输入一个 5，它说"确认是否退出(Y/N):"，我们输一个 `O`——"你的输入有误，请重新输入(Y/N):"；
- 假设输入一个 90，也是输入有误，不让你出去；
- 那我输入一个 `N` 呢？相当于说他不退出，是不是又显示这个主菜单了？
- 那我再来一次 5，我直接输入 `Y`，退出了。

没问题吧？这个功能我们就加进去了。

代码其实就是写了一个退出函数，里面我们加了一些判断。然后不要忘了，写完这个方法过后，你要在这儿调一下——**如果你不调用的话也不好使**。

#### 功能说明

这个功能是这样子的：如果输入了这么一个东西，叫做 `2`，他如果输入 2 的话，我们就去让他提示：把这个新的信息输进去。如果修改完毕过后，指定的 ID 号，比如说 1 号，1 号这个客户就会有新的信息。

就这么一个功能——**修改指定的 ID 号的用户的信息**。当然这个 **ID 号我们不能改**。

有人说为什么 ID 号不能改呢？如果 ID 号都改了，那你这个客户就不知道是谁了。你在做 QQ 修改的时候，你可以改昵称，你也可以改你的签名，但是你有没有看到直接改 QQ 号的？有没有？QQ 号是唯一标识这个 QQ 的，因此这个 QQ 号一旦分配了就不能改。

> **提示**：就好比你的银行卡一样，你的银行卡你可以改密码，但是你绝对不能把银行卡的卡号给改了——卡号改了，那就不是这张卡了。所以我们这个客户的 ID 号是不能改的，而其它信息——姓名、性别、年龄、电话、邮箱——可以改变。

#### 思路分析

打开这里，同样的道理，你肯定要在 `service` 里面编写一个方法——`Update`。

Update 的时候，你肯定要把新的客户信息拿到，然后**先去看有没有这个人**——你要修改的 ID 到底存不存在？所以你还是要用到 `FindById`。然后在 `customerView` 里面还要写一个 `Update` 方法，来调用 `CustomerService` 里面的 `Update` 方法。

也就是说，如果从思路深度来说：

- 你这儿应该编写一个 `Update` 方法。这个方法里面，你给他传进来一个新的 `Customer`，**但是这个新的 Customer 里面要包含 ID**；
- 然后你在 `Update` 里面先去看你要修改的客户 ID 是否存在。如果存在，你再去修改；如果 ID 都不存在，你肯定没法修改，那就失败了；
- 如果 ID 存在，你再把最新的信息给它**替换掉**就可以了。

同样，你这儿写完了过后，在 `customerView` 里面也要写一个 `Update` 方法，它要去调用 `CustomerService` 里面的 `Update` 方法，完成客户的修改。

- **要求**：用户输入 `2`，提示输入新的客户信息；修改完成后，指定 ID 号（比如 1 号）的客户就带上了新信息。

- **实现路线**（依据本讲正文）：
  - 在 `CustomerService` 中新增 `Update` 方法，接收一个**含 ID 的**新 `Customer`，先用本讲写好的 `FindById(id)` 判断该 ID 是否存在；不存在则直接返回 `false`，存在则用新信息替换切片中对应位置的客户，返回 `true`；

  - 别忘了最后在菜单分支里把 `this.Update()` 调用上。

> **提示**：这条路线里唯一的新东西，就是 `FindById` 返回的那个**下标**——它是把"新信息"塞回"老位置"的唯一桥梁。跟 `Delete` 用的是同一个原理，只不过 Delete 是把它删掉，Update 是把它覆盖。
