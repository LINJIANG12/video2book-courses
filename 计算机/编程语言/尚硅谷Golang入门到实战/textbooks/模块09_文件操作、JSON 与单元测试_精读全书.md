这个章节重点就是给大家讲一下在 Go 语言里面如何操作我们的文件——如何读文件、如何写文件，对不对？主要是这样一些操作，包括对文件的增删改查等等。

### 文件是什么：数据库也是文件

第十四章既然是文件的操作，首先我们要对文件做一个基本介绍，要对文件有一个初步的认识。

文件对我们并不陌生。**文件是数据源。**

> **定义**：文件是数据源——我们的数据其实都是保存在文件里面的。

当然有同学说了："老师，我记得有些数据它不是保存在数据库里面的吗？"告诉大家，**数据库本质也是文件**，只是它的文件的形式跟我们普通的文件不太一样，明白我的意思吧？所以文件其实就是数据源，它是保存数据的一个地方。

比如说大家经常使用的 Word 文档、文本文件、Excel 文件，都是文件。那文件最主要的作用就是保存数据。它既可以保存一张图片，也可以保存视频和音频——比如保存一个声音、保存一首歌，或者保存一部电影，这些都是我们文件要做的事情。

大家就记住一句话：**文件就是数据源**。文件就是保存数据的地方。你把这个概念要有认识。

---

### 流：数据从数据源到程序的那条路

在我们编程里面，在整个文件操作里面，**文件在程序中是以流的形式来操作的**。所以说我们经常说文件它是一种流——文件流嘛。

既然谈到流，那就有必要介绍一下什么叫流。

> **定义**：流指的是**数据在数据源（也就是文件）和程序之间经历的路程、路径**，我们就把它叫做流。

我们经常操作的有两种流：一种叫输入流，一种叫输出流。各位，听其名而知其意。

```text
        输入流：读
   ┌──────────────┐         ┌──────────────┐
   │   数据源     │ ──────► │  程序内存    │
   │   （文件）   │         │  （Go 变量） │
   └──────────────┘         └──────────────┘

        输出流：写
   ┌──────────────┐         ┌──────────────┐
   │   数据源     │ ◄────── │  程序内存    │
   │   （文件）   │         │  （Go 变量） │
   └──────────────┘         └──────────────┘
```

什么是输入流呢？大家看我这个图。如果这个数据是**从文件向我们 Go 程序里面的内存流动**，我们把它叫输入流。也就是说，当我们要去读取的时候，我们叫输入流——**读，输入流往往对应的是读的操作，读文件**。

当然还有一种流叫输出流。比如说我们把内存里面的数据重新写回到文件，那么这个数据的流向是**从内存向文件流动**，我们把这个叫做输出流。这往往对应的操作是什么呀？是**写文件**。

一个是读文件，一个是写文件。这个基本常识大家要有一定认识。数据从数据源到程序的路径，我们叫输入流，就是从文件向程序内部流动；反过来叫输出流，就是数据从程序的内存向数据源流动。比如内存里面有些数据，我们要把它保存到文件里面，我们叫输出流。

怎么判断是输入流还是输出流？**主要看它的流向**。这个基本认识大家要有。

### Go 里的 File：所有文件操作的入口

在 Golang 里面，对于文件的操作，它主要是由哪个结构体来提供的呢？是这个结构体。

在 Golang 里面有一个包叫 **`os` 包**，这个 `os` 包里面有一个结构体叫 **`File`**，这个 `File` 它**封装了所有文件相关的操作**。

它是个结构体，里面有很多方法。我带大家看一下：`Read` 读、`ReadAt`；写，写一个字符串，对不对？`Seek` 定位；同步；`Close`，等等等等。大家看到这里面其实都是这个 `File` 结构体跟它绑定的方法。

我们打开 Go 的官方文档来看看。`os` 包里面确实有一个 `File` 结构体。大家注意看这里——**前几个其实它不是跟这个结构体绑定的，它就是普通的方法**；后边从这一行开始，才是跟 `File` 结构体绑定的方法。

打开 `File` 点进去：它是结构体，代表什么？**`File` 代表一个打开的文件对象**，有些喜欢把它叫文件句柄，都可以。它里面有很多方法：`Create`、`Open`；下面都是跟它绑定的。比如 `Name`，就可以返回文件的名称；`Stat` 可以返回文件的一个 `FileInfo` 类型，从这个 `FileInfo` 可以拿到文件的大小、文件的修改时间等等。

> **结论**：后面我们操作文件时，会经常使用到 `os` 这个包里面的 `File` 结构体。你必须要知道我们大体将来会用到哪些函数，那这样子听起来就会比较轻松。

到哪去找呢？注意听，是 **`os` 这个包里面的一个 `File` 结构体，封装了所有文件的操作**。

### 打开与关闭：Open 和 Close 这一对

我们接着来看一下文件的基本操作。

在 Go 语言里面，我们要去操作一个文件，首先要**打开一个文件**。你既然要对这个文件进行读或者写的操作，或者修改的操作，那你首先应该打开一个文件。

#### Open 是一个函数，不是 File 的方法

`os` 包里面提供了一个 `Open` 函数。这个 `Open` **并没有跟 `File` 直接绑定**，它就是 `os` 包里面的一个 `Open` 函数。

```go
func Open(name string) (file *File, err error)
```

它干什么呢？`Open` 打开一个文件**用于读取**。如果操作成功，返回的文件对象可以读取数据。这里直接给它传一个字符串就可以了，`name` 就是写上你这个文件的路径，就是你打开的是哪个地方的文件。

它会返回两个参数：一个是返回一个文件的指针——其实它返回的就是 `File` 这个结构体的一个**指针**；同时返回一个 `error`，也就是说如果打开失败，它会返回一个 error。

> **结论**：所以我们可以看到，**文件其实是个指针类型**。你打开一个文件过后，返回的是 `File` 这个结构体的一个指针类型。换言之，我们文件准确地讲它是一个指针类型。

#### Close 必须靠指针变量去调

打开一个文件过后，还有一个特别重要的操作：当你对文件进行操作完毕以后，比如说读或者写做完了以后，**你必须要记住一件事情，要关闭文件**。

关闭文件是怎么做的呢？在 `File` 这个结构体里面有个 `Close` 方法：

```go
func (f *File) Close() error
```

它是关闭这个文件的。它干什么呢？使文件不能用于读写。这个时候如果关闭错误，它会返回一个 `error`；如果成功当然就没有错误了。

> **易错点**：注意，这个 `Close` 它是**跟 `File` 结构体指针类型绑定的**方法，也就是说你不能直接去用这个 `Close`，你必须是用 `File` 结构体指针这种变量才能调 `Close`。

#### 第一个案例

我们新建一个 `chapter14` 文件夹，在里面先建一个文件夹，这是文件的 demo，一个最基本的 demo，里面我们写一个 `main.go`。

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	// 打开文件
	// 概念说明
	file, err := os.Open("d:/test.txt")
	if err != nil {
		fmt.Println("open file err=", err)
	}

	// 输出下文件，看看文件到底是什么
	fmt.Printf("file=%v\n", file)

	// 关闭文件
	err = file.Close()
	if err != nil {
		fmt.Println("close file err=", err)
	}
}
```

因为你要打开文件，所以要 `os` 这个包——这个 `os` 包里面有我们需要操作文件相应的函数和方法，还有结构体什么的。

这里有个概念要说明一下，就是关于这个 `file` 的叫法，**它有三种叫法**：有些人喜欢把 `file` 叫 **file 对象**——刚才我们看文档的时候，它说打开的就是一个文件对象，其实本质就是这个指针；有些人喜欢把它叫 **file 指针**，因为它的确是个指针；还有一种是 **文件句柄**。**都是一个意思，不要搞蒙圈了。** 有些程序员把它叫文件对象，有些叫文件指针，有些叫文件句柄，其实都是一个意思，不要因为这个概念听得模模糊糊的。

关闭文件注意听：关闭文件是**要通过这个 `file` 来关闭的**，因为它是属于 `File` 结构体指针类型绑定的一个方法，所以说 `file.Close()`。当然这个也会返回一个 error。如果这个 error 不等于 nil，就输出关闭文件错误，把这个 error 输出出来就可以了。

这就是一个最简单的操作：打开了一个文件，输出了一下文件是什么，然后关闭文件。其实我什么都没干。

### 带缓冲读取：一行一行地读

我们来看关于读取文件的几个应用实例。第一个应用实例是：**读取文件的内容并显示在终端**。而且我们第一个用的是带缓冲的。

带缓冲的方式往往可以提高效率，而且特别适合去读取比较大的文件。在这里我们会用到 `os` 包里面的 `Open`、`File` 结构体里面的 `Close`，以及 `bufio` 包里面的 `NewReader`，以及 `Reader` 里面的 `ReadString` 函数和方法。

打开 VS Code，在 chapter14 里面新建一个文件夹叫 `filedemo02`，在里面建一个 main 包，新建一个 `main.go`。

因为前面有一部分代码是相同的，打开文件这块都是一样的，就把这块粘贴过来。打开文件之后，先在文件里面写一点内容进去：

```text
hello, world! 北京
abc
golang
go
hello, world!
```

把它保存一下，待会儿我们要把文件的这些内容读取出来。

#### defer：写在打开之后，函数退出之前

当函数退出时，要及时地关闭 `file`。怎么做呢？用 `defer`。前面学过，`defer` 就是说在函数结束之前，它会调用 `defer` 后面的这些代码。

```go
defer file.Close()
```

这样写是最合适的，在函数退出的时候再去调用 `file.Close()`。这样就会**避免文件句柄的泄漏**——要及时关闭 file 句柄，否则会有内存泄漏，这点大家要注意一下。

因为 `defer` 是函数退出时才去调用，所以下面还是可以正常使用文件句柄的。关于 `defer` 关键字的运行机制，前面已经讲过，这里就不再反复多说。

#### NewReader 里那个 4096

文件打开之后，下一步就是创建一个 `Reader`。这个 `Reader` 是带缓冲的，它是一个**指针类型**。

在 `bufio` 包里面有一个函数叫 `NewReader`，把 `file` 写进去，这就返回一个 `reader`。我们打开文档看看这个 `Reader` 是什么样子的。`NewReader` 会返回一个 `Reader` 指针类型，点开可以看它的源代码：

```go
// NewReaderSize returns a new Reader whose buffer has at least the specified
// size. If the argument io.Reader is already a Reader with large enough
// size, it returns the underlying Reader.
type Reader struct {
	buf          []byte
	rd           io.Reader // reader provided by the client
	r, w         int       // buf read and write positions
	err          error
	lastRuneSize int       // size of last rune read for UnreadRune; -1 means invalid
	lastByte     int       // last byte read for UnreadByte; -1 means invalid
}
```

它里面会有缓冲，这个缓冲默认大小是 **4096 个字节**。它是带缓冲的输入，也就是缓冲输入。

> **提示**：有缓冲有什么好处呢？如果有缓冲，在读取文件的时候**并不是一次性把整个文件读到内存，而是读一部分处理一部分**，这样可以处理一些比较大的文件。这就是带缓冲的意义。

#### ReadString('
') 与 io.EOF

有了 reader，下面就循环读取文件的内容。既然是循环读取，那就是一个 `for` 循环。在这个 `reader` 里面有一个方法叫 `ReadString`：

```go
str, err := reader.ReadString('\n')
```

传入一个结束符 `'
'`。这句话的意思是，用这个 `reader`——因为 reader 已经跟 file 文件绑定了，通过 reader 去读取文件的内容。读到多少就结束呢？读到一个 `'
'`。`'
'` 是换行符的意思，读到一个换行就结束一次。

也就是**一行一行地读**。文件里面第一句话先读到 `hello, world!`，一换行再读取第二行，循环地读。因为读到一个换行——这个换行符在编辑器里如果打开显示所有字符，可以看到确实有一个换行符，只是平时隐藏起来了。每读到一个换行符就结束。

读取的时候，`reader` 会返回两个结果：一个是 `str`（`string`），一个是 `err`（`error`）。读取的内容会放在 `str`，如果在读取过程中产生了错误，会把错误信息放在 `err` 变量。`str` 是它具体的内容，而 `err` 是在读取过程中产生的错误信息。

既然如此，我们就可以来做一个判断。有一个错误是 `io.EOF`。如果 `err` 等于了 `io.EOF`：

```go
if err == io.EOF {
	break
}
```

`io.EOF` 表示**文件的末尾**（End of File），就应该结束读取，`break` 就行了。

如果还没到文件末尾，就反复读取。读取一行就把这个内容输出，输出内容用：

```go
fmt.Print(str)
```

> **易错点**：不要打 `ln`（用 `Print` 即可），因为 `str` 本身就会把换行符也读进去。如果打一个 `Println` 的话，就会有两个换行。

等到不停地读、不停地读，最终读到文件末尾就退出来了。最后输出一句话："文件读取结束"。

#### 完整代码

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"os"
)

func main() {
	// 打开文件
	file, err := os.Open("d:/test.txt")
	if err != nil {
		fmt.Println("open file err=", err)
	}

	// 当函数退出时，要及时的关闭file
	defer file.Close() // 要及时关闭file句柄，否则会有内存泄漏

	// 创建一个 *Reader，是带缓冲的
	/*
		const (
			defaultBufSize = 4096 // 默认的缓冲区为4096
		)
	*/
	reader := bufio.NewReader(file)
	// 循环的读取文件的内容
	for {
		str, err := reader.ReadString('\n') // 读到一个换行就结束
		if err == io.EOF {                  // io.EOF表示文件的末尾
			break
		}
		// 输出内容
		fmt.Print(str)
	}

	fmt.Println("文件读取结束...")
}
```

这里用到了 `io` 包的 `io.EOF` 常量，所以需要把 `io` 这个包也引进去。代码就没有问题了。等到函数退出的时候，它会去调用 `defer`，把文件句柄进行关闭。这就相当于把一个文件读取完成了。

内容全部拿到了。这第一个案例演示了使用带缓冲区的 reader 来读取一个文件并显示在终端。

### 一次性读取：ioutil.ReadFile

下面我们再为大家介绍第二种读取文件的应用方式。

前一种方式是带缓冲的，是一次一次地读入。在 Golang 里面还有一种方式：在 `ioutil` 包里面有一个方法叫 **`ReadFile`**，它可以**一次性将整个文件读入到内存中**，也就是一次搞定。这种方式比较简单、比较直接。

> **注意**：这种方式有一个前提，它**比较适用于文件不太大的情况**。如果文件比较大，用这种方式就不太好了；如果文件比较大，还是用前面带缓冲的方式，效率会比较高一点。

而且文件也不用打开，因为它把文件的打开和关闭整个操作都封装到 `ReadFile` 函数里面去了，所以看起来比较简洁。

打开 VS Code，新建一个文件夹 `filedemo03`，新建一个文件 `main.go`：

```go
package main

import (
	"fmt"
	"io/ioutil"
)

func main() {
	// 使用 ioutil.ReadFile 一次性将文件读取到位
	file := "d:/test.txt"
	content, err := ioutil.ReadFile(file)
	if err != nil {
		fmt.Printf("read file err=%v", err)
	}
	// 把读取到的内容显示到终端
	fmt.Printf("%v", string(content))
}
```

我们用一个方法就可以搞定了。`ioutil` 包下面有一个函数叫 `ReadFile`，直接把 `file` 放进去就可以了。

这个函数会返回两个值。在 `io` 下面的 `ioutil` 这个包里面有一个方法叫 `ReadFile`：它传入的形参是**文件的名字**，实际上就是文件的全路径；它返回的是一个 **byte 切片**，也就是按字节的形式返回的，同时有个 `error`。如果有错误，error 就不会为 nil。

所以在此处把文件名字写清楚，然后有个 `content`，有个 `err`。这个 `content` 就是 byte 切片。如果 `err != nil` 说明出错了，把错误信息打出来。如果没出错，我们把读取到的内容显示到终端。

#### 为什么直接打出来是一堆数字

直接输出 `content` 的话，大家想一想，这样输出的是什么内容？它实际上输出的是一个切片，是一个 byte 切片，所以你会看到一堆数字，因为 byte 按输出的时候是**按数值打印的**。

我们要输出具体内容的话，要把 byte 切片**转成 string** 就可以了，所以要写成 `fmt.Printf("%v", string(content))`。

我们再跑一下看效果。此刻内容就出来了，包括汉字也没有写错："北京 hello, world"。

还有一个细节：如果大家认真观察，会发现**我没有打开这个文件就直接读取了**。因为你没有打开，所以你也不用关闭，没有 `Close` 的方式。因为文件的打开和关闭都被封装到 `ReadFile` 函数内部了，所以我们不需要去管理。

前面我们还写了不少代码，还 `defer` 了一下，然后循环地去读取；而这个地方直接一个函数就把内容读出来了，输出就完事，显得很简洁。

> **结论**：但是有一个前提——这种方式因为是一次性把整个文件内容读进来，**如果文件过大，效率就会很低**。因此这种方式只适合文件不太大的情况来使用。所以我们这里没有打开，也没有关闭，不需要显式地关闭。

这就是我们第二种读取文件的方式，用 `ReadFile` 一次性读取到位。

## 写文件：OpenFile 的三个参数，和四道由浅入深的题
> 对应块：BLK92 | 覆盖分集：P248-P249 | 块标题（分集名）：《246_尚硅谷_创建文件并写入内容》

前面我们讲了两个案例，都是介绍的如何从文件里面去**读取**内容。现在我们来看看怎么把内容**写入**到文件——在我们的实际开发中这也是用得非常多的。

### OpenFile：文件名、打开模式、权限

在写文件的时候，我们首先要用一个函数，叫做 **`OpenFile`**。这个 `OpenFile` 里面有三个参数，我们一个一个地为大家介绍。

首先要记住，`OpenFile` 这个函数是在 **`os` 包**里面，也就是说它是属于 `os` 包里面的一个函数。

**第一个参数**就是你要把这个内容写入到哪个文件里面去，这个就是**文件的路径**。

**第二个参数**是 flag，这个 flag 代表你打开这个文件的**模式**。文件的模式有几种打开方式呢？有这么多种打开方式，比如说只读、只写，或者读写的模式等等，还有追加的模式，待会儿我们会再介绍一下。

我们把这个 flag 到底有哪些给大家看一看。打开 `os` 包，`os` 包里面有一个叫 Constants，这是常量。大家看这里，这一块就是我们打开文件的几种模式。而且告诉大家，**这几种模式可以通过一个竖杠组合使用**。

**第三个参数**叫文件权限 `FileMode`。

#### flag：打开模式的几种取值

| 常量 | 含义 |
| :--- | :--- |
| `O_RDONLY` | 以**只读**的模式打开，文件只能读而不能写 |
| `O_WRONLY` | 以**只写**的方式打开，文件只能往里写而不能读取 |
| `O_RDWR` | **读写**模式打开，既可以读也可以写 |
| `O_APPEND` | **追加**。往里写的内容不会覆盖原先的内容，而是追加到文件尾部 |
| `O_CREATE` | **创建**。如果这个文件不存在，它会创建一个新文件 |
| `O_SYNC` | 同步 |
| `O_TRUNC` | 打开的时候**清空** |

大家注意到，在我们的文件操作里面**没有一个专门的函数是创建文件的**。也就是说，当你以 `O_CREATE` 这个模式打开文件的时候，如果该文件不存在，它就会自动给你创建一个新文件。往往我们会把这个 create 和这个写组合在一起使用——待会儿有一个案例，就是把这两个模式组合在一起使用，这也是允许的。

其它的另外几种我就不再介绍了，用得比较少。

#### O_TRUNC：一个手滑就全没了的选项

> **易错点**：所以这个模式打开很重要，如果你打开错了，我告诉大家，那这个问题就很严重。比如说你用 `O_TRUNC` 打开，那你原先这个文件就自动被清空了，你原先有多少内容全部清空，**这是一件灾难性的事情**。比如说你用一个 for 循环把你文件夹里面所有文件都遍历打开一次，那里面的文件就全部丢掉了。
>
> 所以大家在选择这个文件打开模式的时候，一定要特别地认真小心，要根据自己的需求来打开。

#### FileMode：Linux 和 Unix 才认它

这个 `FileMode` 是什么东西呢？我们打开 `OpenFile` 看到里面有个 `FileMode`。

> **注意**：这个 `FileMode` 主要是用在 **Linux 操作系统下面的，或者是在 Unix 操作系统下面的。如果在 Windows 操作系统下面，这个 `FileMode` 没有作用，就是无效的。**

那准确地来讲它有哪些模式呢？它一般是有三个占位符：第一个代表**文件所有者**所拥有的权限，第二个是代表**文件所在组的那些用户**对这个文件所拥有的权限，还有一个就是**其它组用户**的权限。

- `r` 是可读，用 **4** 来表示；
- `w` 代表可写，用 **2** 这个数字来表示；
- `x` 代表可执行，是用 **1** 来表示的。

如果你想对这块权限控制有一个更详细的了解，可以去看一看尚硅谷的 Linux 课程，里面有一个章节就说得很清楚。

整个这个 `OpenFile` 它会返回两个参数，一个是这个文件的指针，也就是我们前面所说的**文件句柄**，还有一个就是 `error`——如果你这个打开错误了，那么会返回一个 error 值。

#### 写文件为什么推荐带缓冲的 Writer

这里我先说清楚：在写文件的时候，我采用的是**带缓冲的 writer**。

前面我们在读这个文件的时候是不是用了一个 `reader`？那个 reader 是带缓冲的。同样，在 `bufio` 里面它也提供了一个**带缓存的 writer**，这个 writer 可以通过带缓存的方式往这个文件里面写内容。**为了提高效率，往往我们会选用带缓存的 writer 来完成写文件的任务。**

### 案例四：先读后写，O_RDWR 加上 O_APPEND

### 用 ioutil 把一个文件的内容导入另一个文件

同学们跟着老师思路。这个是写文件操作的第二个应用实例。

我们也算是个练习吧，直接在文件夹里面建一个 `exec05`，在里面写一个文件叫 `main.go`。

我们现在首先先写一个文件。假设有这么一个需求：**将 D 盘下面的 `abc.txt` 这个文件的内容，导入到 E 盘下面的 `kkk.txt` 里面去**。当然这个文件事先我们先把它创建好；当然你也可以做个动作，就是说如果没有的话，是不是我们也可以创建。目前这个文件是空的，大家看看是 0 个字节。

那现在我们要开始导。第一步该怎么办呢？第一步，**首先将这个文件的内容读取到内存**；第二步，**将读取到的内容写入 E 盘的 `kkk.txt` 文件**。是这个思路吧？

所以说我们写两个路径，一个是第一个文件的路径，写清楚是在 D 盘下面 `abc.txt`；第二个就是待会儿我们要写入的这个文件，在 E 盘下面的 `kkk`。

```go
package main

import (
	"fmt"
	"io/ioutil"
)

func main() {
	file1Path := "d:/abc.txt"
	file2Path := "e:/kkk.txt"

	// 第一步：把源文件读出来
	data, err := ioutil.ReadFile(file1Path)
	if err != nil {
		fmt.Printf("read file err=%v\n", err)
		return
	}

	// 第二步：写进目标文件
	err = ioutil.WriteFile(file2Path, data, 0666)
	if err != nil {
		fmt.Printf("write file error=%v\n", err)
	}
}
```

首先第一步，我们先把这个文件读出来。读出来非常简单，因为我们用的是 `ioutil` 包里面的东西，所以直接 `ReadFile`，把文件路径写一下就可以了，这样子一下就把东西读出来。先把内容读到 `data`，这边有可能有个错误，所以把这个错误也收一下。

如果 `err` 不等于 nil，说明读文件出错了。那怎么办呢？咱们把这个错误信息输出出来就退出了。那下面就不能走了，因为你文件读取都出错了，那显然就没有办法再往下面走了，对吧？

大家还回忆一下，这个读出来它是一个 **byte 切片**，对吧？读出来过后下一步我们可以把它写进去。那写进去的话，我们用 `ioutil` 这个包里面它有一个方法叫 `WriteFile`。

我们打开看一下这个函数：`ReadFile` 是返回一个 byte 切片和一个 error，刚才我们已经处理了。它还有一个 `WriteFile`——第一个参数是要把内容写到哪个文件里面去，第二个是一个 byte 切片，这个切片就是刚才那一个，所以你这也可以写成 `data`。

> **提示**：第三个参数大家注意观察，它还有一个参数——这个参数是**文件的模式**，前面我们已经用过了。这个我反复讲过，**在 Windows 下面这个 FileMode 是无效的**，所以你可以随便写一个值，比如 `0666` 就行了。

它这边有没有返回值呢？大家看到它这边也返回一个 error。那有没有 error 我们可以把它收一下。

> **结论**：这里面大家看到，`ReadFile` 和 `WriteFile` 是**隐式地打开和关闭文件**的，因此这个代码就写完了。

### 判断文件或目录是否存在：os.Stat 的三条规则

我们在进行文件操作的时候，有时候会有这样一个功能，就是**判断文件是否存在**。这个在我们做项目的时候经常会用到，看看这个文件或者是目录有没有存在。

Golang 判断文件或者文件夹是否存在，用到的方法是 **`os.Stat` 这个函数**。

打开文档，`os` 包里面有一个函数叫 `Stat`，进去看一下：Stat 返回一个描述 name 指定的文件对象的 `FileInfo`。如果说这个文件在读取的时候、如果你打开这个文件或者读取这个文件有错误，那么这个 error 里面会包含一些信息。

具体是哪些信息？大家看这里，官方把规则讲得清清楚楚，一共三种：

| `os.Stat` 返回的 error | 说明什么 |
| :--- | :--- |
| 为 `nil` | **文件夹和文件是存在的** |
| 通过 `os.IsNotExist` 判断为 `true` | **文件夹是不存在的** |
| 为其他类型 | **不确定是否存在** |

基于这三个规则，我们写了一个函数，这是我们自己写的一个函数：

```go
func PathExists(path string) (bool, error) {
	_, err := os.Stat(path)
	if err == nil {
		return true, nil
	}
	if os.IsNotExist(err) {
		return false, nil
	}
	return false, err
}
```

那这个函数可以干什么呢？可以根据你的输入——比如说你输入一个路径过来，或者输入一个文件过来——那么我就可以判断你这个目录或者是你这个文件是否存在。

我是怎么做的呢？大家看，首先我调用 `os.Stat` 把这个路径传进去，然后我根据这个 error 来判断：

- 如果这个 `err` 等于 nil，这说明文件或者目录存在，那我返回的布尔值为 `true`，error 为 nil；
- 如果说这个 `err` 不等于 nil，那我就判断它这个是不是一个 `IsNotExist` 的错误。如果我发现这个 error 就是 `IsNotExist` 这个错误，那么我就返回一个 `false`——返回这个 `false` 的同时，这个 error 仍然是 nil；
- 还有一种情况，就是有错误了，但是它并不是这个 `IsNotExist` 错误，那么这个时候我就把这个错误**原封不动地返回**。

后面同学们想去判断一个文件或者一个目录是否存在，可以使用这个函数来完成。怎么弄呢？你把路径给我传进去，根据返回的布尔值来判断：

- 如果为**真**，说明目录存在；
- 如果为**假**，说明这个目录或者这个文件不存在；
- 如果它为**假同时还有一个 error**，那就说明可能是其他错误信息。

> **结论**：只要不出什么意外，一般来讲，这个 Stat 打开也是因为这个文件存在或者不存在导致的错误，因此一般说来**都是用 true 和 false 来判断就足够了**。

那我把这一块就不去测试了，直接拿到笔记里面去。现在我们又写了一个案例，这个案例是判断文件或者目录是否存在——重点就是这个函数，大家用这个函数来玩一把就行了。

那么在 Golang 里面，它怎么去拷贝一个文件呢？它在 **`io` 包里面提供了一个叫 `Copy` 的方法**。

打开我们的手册，在 `io` 包里面我们可以看到有一个函数叫 `Copy`。它需要传入这么一个 Writer 和一个 Reader——Writer 肯定就是写的，也就是目标文件；这个 Reader 呢是读，就是我把这个源文件里面数据读出来，然后写入到这个 dst，这是我们的目标文件。

文档上说：它将 `src` 的数据拷贝到 `dst`。如果发生了错误就会截断。这个 `written`，就是**一共你操作了多少个字节**；`err` 呢就是在拷贝的时候如果发生了错误，那么就会返回一个错误。

#### 自己封装一个 CopyFile

我们来完成这个案例。现在呢我们拷贝文件，先做一个说明：**这个 Copy 函数是 `io` 包提供的**，这点大家要注意。

现在我们首先先要准备一个图片。我现在有一个图片已经准备好了，叫 `flower`，我先把它放在 D 盘。当然这个 E 盘现在还没有这个文件，那待会儿没有这个文件呢，就会创建一个文件，并把数据写进去。

新建一个 `exe06`，写一个 `main.go`。

因为真正完成这个拷贝是用 `Copy` 这个函数来完成的，而它在拷贝的时候需要你提供一个 Writer 和一个 Reader，所以我们干脆自己写一个函数。

> **结论**：它接收两个文件的路径——一个叫 `srcFileName`，就是**源文件**的名字；另一个叫 `dstFileName`，就是**目标文件**，就是说我们要把这个文件拷贝到这个目标文件去。

```go
func CopyFile(dstFileName string, srcFileName string) (written int64, err error) {
	// 打开源文件，得到一个 Reader
	srcFile, err := os.Open(srcFileName)
	if err != nil {
		fmt.Printf("open file err=%v\n", err)
		return
	}
	defer srcFile.Close()
	srcReader := bufio.NewReader(srcFile)

	// 打开目标文件，得到一个 Writer
	dstFile, err := os.OpenFile(dstFileName, os.O_WRONLY|os.O_CREATE, 0666)
	if err != nil {
		fmt.Printf("open file err=%v\n", err)
		return
	}
	defer dstFile.Close()
	dstWriter := bufio.NewWriter(dstFile)
	defer dstWriter.Flush()

	// 真正干活的一行
	return io.Copy(dstWriter, srcReader)
}
```

我们看这个 `src`：到时间提供的是一个 Reader，所以说我们先把它打开。`src` 是 Reader，它要读取它，所以这里我们直接用 `os.Open` 把它打开就可以了。打开，还记不记得这个 Open 会返回一个什么？返回一个文件的句柄，当然也可能有个 `err`。

这个就是我们的源文件的句柄。那我做一个判断，如果 `err != nil`，说明我们打开这个文件错误了，那我们把这个错误信息输出出来。

如果没有出错，说明我们把这个句柄就拿到了。那这个时候呢我们就可以构建一个 Writer 了——不对，先构建 Reader。就通过这个 `srcFile` 获取到这个 Reader，因为将来我们要从这个源文件里面读东西嘛。还记不记得这个 Reader 怎么拿到？是不是通过 `bufio` 这个包？这个 `bufio` 包里边呢，它有一个叫 `NewReader`，把这个 `srcFile` 放进去。

那我们还有一个 `dst`，这个呢要得到一个 Writer，也是带缓冲的一个 Writer。怎么办？打开文件。这个文件路径**有可能不存在**，所以说这个传过来的文件名可能不存在，因此我们**不能用 `os.Open` 打开**——因为这里面我们还要往里面写，要创建。这时候呢我们要用另外一种方式，大家还记不记得我们在讲前面这个案例的时候曾经讲过这个东西？是不是以写、只写的方式打开，同时呢如果这个文件不存在就创建一个。`OpenFile`。

最后通过这个文件句柄获取一个 Writer，老规矩 `bufio.NewWriter`，把这个句柄放进去，最后我们就拿到一个 Writer 了。

```text
 源文件 side                                        目标文件 side
────────────                                        ─────────────
 srcFileName                                         dstFileName
      │                                                 ▲
      │ os.Open                                         │ os.OpenFile
      ▼                                                 │ (O_WRONLY|O_CREATE)
  *os.File (srcFile)                                   │
      │ bufio.NewReader                                │ bufio.NewWriter
      ▼                                                 ▼
  *bufio.Reader  ──────── io.Copy(dst, src) ───────►  *bufio.Writer
                                                          │
                                                    Flush + Close
```

这张图就是整个函数的骨架——**一个 Reader 接源，一个 Writer 接目标，中间交给 `io.Copy`**，一眼就清楚。

#### io.Copy 里面到底做了什么

我们来看一看 `io` 这个包 `Copy` 的源代码是怎么写的，给大家欣赏一下。

大家可以看到，其实这个 Copy 的源代码它这边调用了 **`copyBuffer`**。它的源代码其实就在这里。如果有兴趣的同学可以去看一下。

其实你们有没有发现，它是这样写的：大体我们简单看一下，它有一个 writer 和一个 reader，然后呢收到一个 `buf`。`buf` 呢就是它自己在这传的时候传个 `nil` 进来，就没用，没有用，我们这个 Copy 没有用到。

那它怎么走的呢？大家看，其实并不难。它大概是这样走的——

```go
for {
	nr, er := src.Read(buf)
	if nr > 0 {
		nw, ew := dst.Write(buf[0:nr])
		// ... 出错与短写的处理
	}
	if er != nil { /* 到末尾或出错，返回 */ }
}
```

有一个 `for` 循环，不停地去读取这个 src，就是这个 reader 里面的东西。**读一个就通过 dst 往里面写**——读一个写一个，读一个写一个，不停地 for 循环，就是一边读一边写。

那这样子的话我们可以看到，因为它这个 Copy 函数用的是**带缓冲**的，因此我们用这种方式——就是刚才老师写的这个方式——来完成**拷贝一个大文件也是可以的**。因为它带缓冲，它是读一点写一点，读一点写一点，对不对？所以说这个我们大家可以看到，用这种方式是可以处理这种大文件的。

#### 别忘了关句柄

还有不要忘了，一定要及时的把这个打开的句柄关闭掉。一个是这个句柄，还有一个是这个句柄，别忘了。因为**有时候我们写代码的时候容易忽略掉关闭文件句柄**。

> **结论**：如果你忽略关闭文件句柄会有什么后果呢？就会造成**内存泄漏**，跑一段时间，我们这个代码可能就会**越来越慢**了，因此大家一定要注意这个细节。

我们再来看一个文件编程的应用实例。它有这样一个要求：**统计一个文件里面有多少个英文，有多少个数字、空格和其他字符**，把这些字符的数量做一个统计。

这个题做完，我们顺手把 Go 里的命令行参数也过一遍——从最原生态的 `os.Args`，一路讲到更好用的 `flag` 包。

### 统计文件里各类字符的个数

#### 用结构体把四种计数装起来

我们的思路先理一下：**首先打开一个文件，然后创建带缓冲的 reader，每读取一行就去统计该行有多少个英文、数字、空格和其他字符，然后将结果保存到一个结构体中。**

所以我们需要先定义一个结构体，这个结构体里面有这么些字段——统计英文的字段、数字的字段、空格的字段和其他字符的字段：

```go
type CharCount struct {
	ChCount    int // 用于记录英文的个数
	NumCount   int // 记录数字的个数
	SpaceCount int // 记录空格的个数
	OtherCount int // 记录其他字符的个数
}
```

有了这个结构体过后，我们接着往下看。

为了做这个测试，我在 E 盘写一个文件叫 `abc.txt`，在里面写一些字符：

```text
ab123 89 op go
yy 89 hello
```

先把它保存好。

#### 打开文件、建 reader、逐行读

现在打开这个文件。怎么打开？用 `os` 里面的函数 `Open`：

```go
fileName := "e:/abc.txt"
file, err := os.Open(fileName)
if err != nil {
	fmt.Printf("open file err=%v\n", err)
	return
}
defer file.Close()
```

如果打开文件出错，输出信息后下面就不用走了——因为文件都打不开就没办法统计了。及时用 `defer` 关键字让它延迟关闭。

然后我们再定义一个 `CharCount` 的实例：

```go
var count CharCount
```

目前创建完了过后，里面的默认值都是**零值**，int 类型就是 0。这一点很省心——不需要初始化。

接着我们来创建 reader，这个 reader 是带 buffer 的：

```go
reader := bufio.NewReader(file)
```

把句柄放进去，它会返回一个 reader。现在开始循环地读取文件内容：

```go
for {
	str, err := reader.ReadString('\n')
	if err == io.EOF {
		break
	}
	// 统计 str 里的字符
}
```

用 reader 的 `ReadString` 方法，给它一个终止符 `'
'`。拿到内容 `str`，同时会有一个 `err`。如果读到最后 `err == io.EOF`，代表读到了文件末尾，就不读了，直接 break 跳出。

#### 逐行遍历，用 switch 分流

这个时候拿到的 `str` 就是我们读到的字符串，我们现在就可以遍历它进行统计：

```go
for _, v := range str {
	switch {
	case v >= 'a' && v <= 'z':
		fallthrough
	case v >= 'A' && v <= 'Z':
		count.ChCount++
	case v == ' ' || v == '\t':
		count.SpaceCount++
	case v >= '0' && v <= '9':
		count.NumCount++
	default:
		count.OtherCount++
	}
}
```

**字符串的本质其实是一个 byte 数组**，所以是可以遍历的。在比较字符的时候，会比较它们对应的 ASCII 码：

- 如果大于等于 `'a'` 并且小于等于 `'z'`，或者在大写的 `'A'` 到 `'Z'` 之间，利用 **`fallthrough` 穿透**处理，让 `count.ChCount++`；
- 如果它是空格或者制表符 `'\t'`，就让 `count.SpaceCount++`；
- 如果大于等于 `'0'` 并且小于等于 `'9'`，说明是个数字，让 `count.NumCount++`；
- 如果不属于这些情况，`default` 里面我们就认为它是其他的字符——比如中文或者特殊字符等等，把 `count.OtherCount++` 即可。

经过这一番循环，**每读一行我们就去处理一次**，读到最后 for 循环就结束了。

for 循环完了，我们输出统计的结果：

```go
fmt.Printf("字符的个数为=%v\n", count.ChCount)
fmt.Printf("数字的个数为=%v\n", count.NumCount)
fmt.Printf("空格的个数为=%v\n", count.SpaceCount)
fmt.Printf("其它字符个数=%v\n", count.OtherCount)
```

#### 编译器不让你那么写 switch

我们来运行一下。保存一下看代码有没有错误——可以看到这里有两个错误，我们定位一下。

**错误一**：这里少了冒号，这里也少了冒号。

**错误二**才是有意思的：不匹配布尔类型和 rune。

为什么？因为 `switch v { case v >= 'a' && v <= 'z': ... }` 这种写法——带表达式的 `switch v`，要求每个 case 的值跟 `v` 是**同一个类型**。而 `v >= 'a' && v <= 'z'` 是个**布尔表达式**，你这边返回一个布尔类型，`v` 不是一个布尔类型，所以这里我们就不要这么处理，换一个思路。

其实也很简单：**把 `v` 直接拿掉就可以了**。我根本不用这个 `v` 去匹配，相当于把 `switch` 当做**一个 if 分支判断**就完了。

```go
switch {          // ← 没有表达式，就是一串条件分支
case v >= 'a' && v <= 'z':
```

大家还记得 switch 有这种用法吗？直接把 switch 当做一个分支结构来使用就可以了。

#### 多出来的四个字符，还有中文的坑

现在我们直接运行，可以看到结果：**字符有 13 个，数字有 7 个，空格有两个，其它字符有 4 个**。

我们打开文件来比较一下，看对不对：

- **字符 13 个**：前面这有 4 个（`ab` + `op` + `go` = 6 个），加上下面 `yy` + `hello` 这 7 个，完全正确；
- **数字 7 个**：`1 2 3`、`8 9`、`8 9`，一共 7 个，也是正确的；
- **空格两个**：这里有一个空格，这里还有一个空格；
- **其它字符为什么有 4 个呢**？大家知道，这个地方其实有**看不见的字符，就是 `\r` 和 `
`**。因为它是回车换行，这边有两个，那边也有两个，所以其它字符有 4 个，完全正确。换行在记事本里是回车换行 `\r
`，把这两个算进去刚好是 4 个。

大家可以在这个基础上做得更完善一点，比如把中文有多少个加进去，或者要统计大写字母有多少个、小写字母有多少个，也可以在这个基础上去完善。

思路很重要，其实很简单：**用一个结构体来记录统计的结果，打开文件，每读取一行就去遍历一次，最后拿到这个结果。**

#### 中文：把 string 转成 []rune

在这我再多说一句：**因为 string 这样统计的话，不能处理中文。**

有些时候你会看到有人为了处理中文、兼容中文字符，可以将 string 转成 **rune 切片**：

```go
str := []rune(str)
```

把它转一下就 OK 了。rune 可以兼容中文，怎么转呢？其实很简单，这样写就完了。

这样的话就可以兼容中文了——相当于把 string 转成 rune 切片，然后对它进行遍历。这个时候有中文的话，也可以把它统计和处理出来。

> **提示**：为什么 `for _, v := range str` 不需要转呢？因为**不带 `:=` 的下标形式 `for i, v := range`** 里，`v` 的类型是 `rune`（Go 会自动解码 UTF-8），所以中文其实已经按字符拆开了；真正会出问题的是**直接按索引访问** `str[i]`，那样拿到的是单个字节。了解这一层，你就不用记"要不要转"了。

### os.Args：拿到命令行的所有参数

我们来了解一下 Go 里面的命令行参数。

先看一个需求。比如说现在我们希望获取到命令行输入的各种参数，应该如何处理？大家看我这有一个图片：比如说我们去执行一个可执行文件，在这个地方我们可能会在执行这个程序的时候，**顺带就传入一些参数**——如果我在这个命令行后边直接带了一些参数进去，比如 `tom`，还有一个路径，还有一个 `88` 这个数字。那么我们怎么在程序里边、在这个 `test.exe` 里面去拿到这几个参数呢？

怎么拿到？告诉大家，在 `os` 这个包里面有一个切片叫 **`Args`**（arguments），它是一个 **string 的切片**。这个切片可以存储所有的命令行参数。

打开文档，大家看到在 `os` 这个包里面有一个 Variables（变量），里面有一个这个东西——这个变量是它这个包事先已经定义好的一个**全局变量**，大家可以看到是个大写的 A。

它是干什么呢？这是一个 string 切片，它保管了命令行的所有参数。**第一个是程序的名字**，也就是说这个切片里面的第一个元素就是程序的名称；**从第二个开始，就是你的参数的值**。

我们在做开发的时候，有可能需要从命令行得到一些参数。比如说我们得到一个配置文件的路径，或者说一个端口号，我们要监听哪个端口，我们希望把这个做得更加灵活一点。这时我们可能是在执行这个程序的时候，在这个命令行里面给它传入了一些动态的参数。那些动态参数我们可以通过 `os` 包里面的 `Args` 这个切片来获取。

新建一个文件夹，把它叫做 `argsdemo`，写一个文件 `main.go`：

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Printf("命令行参数有 %v\n", len(os.Args))
	// 遍历 os.Args 切片，就可以得到所有命令行输入的参数值
	for i, v := range os.Args {
		fmt.Printf("args[%v]=%v\n", i, v)
	}
}
```

命令行参数有多少个呢？其实就是这个 `os` 包里面的 `Args` 这个切片，我们用 `len` 取一下。然后我们遍历一下 `os.Args` 这个切片，就可以得到所有的命令行输入的参数值。

for 循环这个可以用 for range，也可以用普通的 for 循环，我这里用 for range 来处理：`i` 是下标，`v` 是值，range `os.Args`。因为它是一个切片，我们就把它输出出来。`i` 代表它是第几个参数——如果下标为 0，其实是代表第一个参数，因为**切片都是从 0 开始编号的**。

写完过后我们来测试一下。保存。刚才忘了引入 `os` 包，把这个包引进去就没事了。现在我们来玩一把：

```bash
cd ..
cd chapter14/argsdemo
go build -o test.exe main.go
```

编译成功了，在这里生成了一个 `test.exe` 文件。我们来运行一下：

```bash
test.exe tom aaa/bbb/init/init.log 909
```

回车。我们可以看到，他说你一共有四个参数：第一个参数就是它自己，第二个参数是 `tom`——**因为它是按空格来间隔的**；第三个参数也拿到了，第四个参数 `909`。如果你输得更多，它依然可以给你处理，因为你这地方所有的参数都会被系统自动放到那个切片里面去。

#### os.Args 的硬伤：位置就是一切

前面的这种方式，同学们已经看到，我们用的是 `os` 下面的 `Args` 切片来获取参数。这个是没有问题的，但是**这种方式有些缺点**。

大家发现有什么缺点没有？如果你将来去写这个参数的时候**顺序写错了**，比如说把 `tom` 写到后面来了，那原先这个 tom 的值就跑到第四个参数去了。这是第一个不太方便的地方。也就是说，你这种方式**要严格地按照参数的顺序来编写，有点麻烦**。

而且还有一个问题。在实际的开发中，如果同学们用过 MySQL 或者其他的数据库的话，你们都知道 MySQL 在登录的时候往往是这样写的：`-u root -p`，然后比如带一个密码 `123456`，然后 `-h` 我连接哪个主机，然后 `-P` 端口比如说 `3306`。

在很多程序里面，我们经常会看到这种用法：**前面是一个应用程序，后边用一个 `-u` 来指定参数**。前面有一个指定参数的标识，后面才是这个参数的值。

> **结论**：这样子有什么好处呢？好处在于，**如果我用指定参数的方式来给参数值的话，顺序就不受约束了**。也就是说，`-u root` 可以写在前面，也可以写到后面。因为程序在解析命令的时候，是根据指定的参数来确定到底是什么值。

### flag 包：让参数自己报名字

既然如此，在 Golang 里面也支持这种写法，用 **`flag` 包来解析命令行参数**。前面的方式是比较原生态的，对解析参数不是特别方便，特别是带有指定参数形式的命令行。

这个案例是这么设计的：要求同学们去写一个程序，可以在程序内部拿到 user，比如 `u` 是什么、密码是什么、`h` 是什么、端口是什么，**通过指定参数来获取参数的值**。

在讲代码实现之前，我先给大家介绍一下 flag 包。打开文档点一下 flag：**flag 包实现了命令行参数的解析**。这里面有几个比较重要的方法：一个是 `StringVar`，还有一个方法是 `IntVar`。这两个方法用得比较多。

我们点开一个看一下，`IntVar` 的**第一个参数是一个引用类型**——把一个值用引用的方式传进去，待会儿就把指定参数的值放进去；**第二个位置**填的就是指定你要获取哪一个指定参数的值，比如 `u` 或者密码或者 `h`；**后面的 `value` 是一个默认值**，如果他没有填、没有给值，可以给一个默认值；**后面则是 usage 说明**。

新建一个文件夹叫 `flagdemo`，在里面新建一个文件叫 `main.go`：

```go
package main

import (
	"flag"
	"fmt"
)

func main() {
	// 定义几个变量，用于接收命令行的参数值
	var user string
	var pwd string
	var host string
	var port int

	flag.StringVar(&user, "u", "", "用户名，默认为空")
	flag.StringVar(&pwd, "pwd", "", "密码，默认为空")
	flag.StringVar(&host, "h", "localhost", "主机名，默认为 localhost")
	flag.IntVar(&port, "port", 3306, "端口号，默认为 3306")

	// 转换
	flag.Parse()

	fmt.Printf("user=%v pwd=%v host=%v port=%v\n", user, pwd, host, port)
}
```

首先定义几个变量，用于接收命令行输入的参数值。根据这个案例而言，将来会有四个参数，前三个是字符串，第四个是一个 int 类型，是个端口。

定义好过后就来接收。flag 包里面有一个 `StringVar`，里面传四个参数：

```go
flag.StringVar(&user, "u", "", "用户名，默认为空")
```

`&user` 就是用来接收用户命令行中输入的 `-u` 后面的参数值。`"u"` 就是 `-u` 指定参数。空字符串代表默认值——假设我们在命令行里面没有传 `-u` 指定参数，那么 `user` 默认就是空值。后面就是对参数的一个说明。

其它以此类推，密码按指定的参数 `pwd` 来做——指定了 `pwd` 之后，在传参数的时候就必须写 `-pwd` 了：

```go
flag.StringVar(&pwd, "pwd", "", "密码，默认为空")
```

主机指定按 `h` 来获取。如果没指定这个参数，那么 host 默认就是 localhost：

```go
flag.StringVar(&host, "h", "localhost", "主机名，默认为 localhost")
```

最后还有一个端口，因为是 int 类型，所以用的是 `IntVar`：

```go
flag.IntVar(&port, "port", 3306, "端口号，默认为 3306")
```

#### StringVar、IntVar 和那个不能省的 Parse

> **易错点**：写完过后还有一个**非常重要的动作**——转换，必须调用该方法：
>
> ```go
> flag.Parse()
> ```
>
> 这个很重要。我们来看看这个函数是干什么的：它是从切片里面**解析注册的 flag**。**必须在所有 flag 都注册好后，而未访问其值前执行**。必须进行转换，才能真正把值转换成功。**所以 `Parse` 必须有，不然拿不到值。**

最后输出结果看一下：

```go
fmt.Printf("user=%v pwd=%v host=%v port=%v\n", user, pwd, host, port)
```

代码保存一下。我们来玩一把，看看能不能跑起来：

```bash
cd ..
cd flagdemo
go build -o test.exe main.go
```

编译过后会得到一个 `test.exe`。根据我们刚才指定的参数，`-u root`，密码 `-pwd`，比如密码我们写的是 123456；然后我们还有一个主机，主机我们看是用 `-h`，写个 IP 地址，比如说 `127.0.0.5`；最后还有一个端口 `-port`，那么我给端口来一个 8080，回车。

同学们可以看到，此时此刻我们拿到所有的值，而且都是正确的。

#### 顺序乱写也照样认

有些同学说了，你这个有什么好处呢？**好处是在于我这个顺序可以乱写**。比如说我把 `-u root` 就不写到这儿，我偏偏要写到最后，这个也没有任何影响。比如说我故意换一个名字，比如叫汤姆、Jackie，回车。你看，你把 `-u` 这个指定参数写到最后，你发现它也能解析出来，对吧？

同样，说老师你还有默认值给我们玩一下。假设这个端口我没有给它传这个值，那么这时因为你没有传指定 port 的参数值，那么它会启用默认值。大家还记不记得我的默认值写的多少？**3306**。也就是说如果你没有传 port，那么这个 port 就是 3306。看，果然如此。

所以这种用法非常的灵活。在我们实际开发中会经常使用到 flag 包来解析我们的命令行参数。**所以这个大家必须掌握**，好吧？必须掌握。也比较简单，但是必须给大家点出来。

关于使用 flag 包来解析命令行参数，我们就给大家介绍到这里。这个大家一定要掌握，以后我们在用命令行来指定参数的时候用得特别的多。

### 什么是 JSON，什么是序列化

首先我们来看看 JSON 是什么。**JSON 的全称是 JavaScript Object Notation，就是 JavaScript 对象标记法。**

也就是说，它可以把我们的数据按照 JSON 的格式进行传输。JSON 这个格式是一种**轻量级的数据交换格式**，它利于人的阅读和编写，而且利于机器的解析和生成。

我这样讲可能大家还不太清楚 JSON 是什么，除非你曾经学过。后面我会给大家举一些案例，让大家认识一下。**JSON 最经典的用法就是 key-value**——它总是以 key-value、key-value 这种形式来描述一个信息的。

这个 JSON 它在 **2001 年**的时候就推行和使用了，目前已经成为主流的数据格式。目前我们在编程里面，JSON 是一种主流的数据传输格式。

具体来说是这样子的：**JSON 有利于网络传输效率**。通常在程序网络传输时，先将数据——比如说结构体或者 map——先把它**序列化成 JSON 字符串**，然后到接收方得到这个 JSON 字符串时，再**反序列化**恢复成原来的数据，比如说结构体或者 map，然后再进行操作。

> **定义**：这里就出现了两个概念——**序列化**和**反序列化**。序列化是把数据变成 JSON 字符串，反序列化是把 JSON 字符串变回数据。这两个概念我们放在后面去讲。

### 应用场景之一：Web 编程的 B/S

现在我给大家说一下 JSON 这种格式的应用场景。说完了应用场景过后，大家可能对 JSON 这个格式会有一种比较形象的认识。

**第一个场景，就是 Web 编程中的应用。** 大家知道 Web 编程是一种 B/S 结构的，那就意味着这边有我们的一个 Web 服务器。假设这个服务器是用 Go 语言写的。这边有一个浏览器——浏览器是什么无所谓，具体是 IE 浏览器还是谷歌浏览器无所谓。

现在我们就要开始进行一个操作了。比方说我这个服务器要返回一些数据给浏览器，一般会怎么做呢？比如说我们要给浏览器返回一个数组，比如表示一个省有多少个城市的一个数组。

那该怎么做呢？这里边有一个 Go 数组，这个 Go 数组我们**不会直接返回**给它，往往会这样处理一下——**把它 JSON 化，进行 JSON 序列化**。序列化过后在这里我们就得到了一个 JSON 字符串。那么这个时候，我们把 JSON 字符串返回给我们的浏览器。

```text
【场景一 · Web 编程（B/S）】

  Go Web 服务器                              浏览器
 ┌─────────────────┐                       ┌─────────────────┐
 │  Go 数组         │ ① json.Marshal      │                 │
 │  [北京 上海]     │ ───────────────────► │  JSON 字符串    │
 │                  │                       │                 │
 │                  │                       │ ② 反序列化     │
 │                  │                       │   → 数组        │
 │                  │                       │ ③ 渲染到页面   │
 └─────────────────┘                       └─────────────────┘
      整个网络上传递的，只有中间那段 JSON 字符串
```

> **提示**：为什么有些同学可能就要问了——老师，为什么不把这个数组直接返回给浏览器呢？因为 **JSON 这种字符串特别利于网络传输**，因为这种格式很科学。

传输过去过后，浏览器接收到这个 JSON 字符串过后，它一般会怎么处理呢？它会进行一个**反序列化**。我们浏览器先接收到了这个 JSON 字符串，那 JSON 字符串我们往往还要把这个 JSON 字符串再重新反序列化成一个数组，或者是其它什么数据。拿到过后我们要把它**恢复成原来的数组**，然后让这个数组来进行一个显示操作——因为你这边返回的数组最终是要显示在浏览器上的，对不对？那我还原成数组过后，我再用来显示，再进行 DOM 编程进行显示，一般来说是这样一个流程。

所以大家看到，我们网络传输的时候，往往是用 JSON 这种格式来进行传输的。因为这种 JSON 格式它**更加利于网络传输**，因此目前很多程序都采用 JSON 这种标准的数据格式来进行传输。

### 应用场景之二：聊天程序的 C/S

反过来了，同学们，我们也有可能是这样子的。假设我们用 Go 编写了一个网络程序，比如说**聊天程序**，它也可以用 JSON 来进行传输。

打个比方，现在我用 Go 写了一个聊天系统。如果是聊天系统的话，因为你聊天肯定数据要从 A 客户端发到 B 客户端，对不对？那这个时候我们也可以用 JSON 格式来进行传输。

现在我在服务器这头，假设我这有两个客户端：客户端 A 和客户端 B。那么 A 和 B 他们之间要进行通讯，往往要经过我们的**中转服务器**，比如说这里是我们的一个后台服务器，是用 Go 语言写的。

这个时候我们假设要把客户端 A 的一个信息发给 B，那我们也会通常选用 JSON 的形式来进行处理。比如说我这有个数组，那我先把这个数组转成一个 JSON 字符串——当然这里面我们可能会用到**序列化**。

一旦我拿到这个字符串过后，我就把这个字符串传给 Go 后台的服务器。Go 后台服务器拿到这个 JSON 字符串过后，它再**原封不动地**把这个 JSON 字符串再传回给 B 客户端。因为你在传送的时候肯定这里面会指定我要把这句话发送给哪一个客户端，对不对？假设这个数组我要发送给 B 客户端，那这个它就相当于在这里做了一个**中转**。

```text
【场景二 · 聊天程序（C/S）】

 客户端 A         Go 中转服务器         客户端 B
┌─────────┐      ┌────────────┐      ┌─────────┐
│ 消息数组 │ ①    │            │  ④   │JSON字符串│
│         ├─────►│  原样中转  ├─────►│         │
└─────────┘      └────────────┘      └─────────┘
   ② 序列化成 JSON 字符串，两端都遵守这个格式；
      服务器不改内容，只负责转发，客户端 B 再反序列化、显示
```

这边它把数据拿到这边过后，B 客户端拿到的是什么呢？其实 B 客户端拿到的是一个 JSON 字符串。JSON 字符串它往往会把它进行一个反序列化，反序列化会得到一个什么呢？又会得到一个对应的数组，然后我们再显示。

那这样有个什么好处呢？**好处就是大家如果都遵守 JSON 这种数据格式的话，我们的程序就比较容易控制了。** 也就是说大家都遵守 JSON 数据格式，那么我们在转换的时候就比较方便。如果 A 客户端用的是一种数据格式，B 客户端用的是另外一种数据格式，那显然我们在进行通讯的时候就很困难了。

> **提示**：打个大家都懂的比方——比如我在聊天的时候我说的是**汉语**。如果对方也是一个中国人，我们聊天就比较顺畅，因为我说每句话他都能听得懂。比如我说"咱们今天晚上吃个红烧肉"，他就知道什么意思了。但反过来，如果对方是一个**法国人**，那我今天晚上说吃红烧肉，他可能就听不懂，对不对？因为他的大脑里面编码是法语，除非他学过中文。

所以目前 JSON 这种数据格式，因为非常轻便，而且比较容易控制、高效，因此现在不管是我们的 Web 编程——Web 编程是 B/S，还是我们的这种 TCP 编程——比如是 C/S，目前大家在传输的时候**基本上都遵守 JSON 这个格式**。

### JSON 长什么样：键值对、数组和逗号

讲了半天，我们还没有说 JSON 这个数据格式到底长什么样子。

先记住一个结论。在 JS 语言中**一切皆为对象**，因此任何支持的数据类型都可以通过 JSON 来表示——比如**字符串、数字、对象和数组**。也就是说我们在 Golang 语言里面也好，还是 JS 里面也好，还是其它的编程语言里面也好，你如果是字符串或者数字或者对象或者数组，我们都可以把它做成一个 JSON 格式。当然了，在我们的 Golang 里面还有 map 也可以，还有像结构体也是可以的。

> **结论**：也就是说我们一切这种数据类型都可以把它转成一个 JSON 格式——**任何一种数据类型都可以转成 JSON 格式**。这句话很重要。

那么 JSON 格式到底是怎么做的呢？同学们请注意，**JSON 它是靠键值对来保存数据的一种方式**。也就是说它在去描述一个信息的时候，它总是一个键值对的形式来描述——一个键、一个值。那么键我们把它叫做**属性**，值就是对应的具体的数据。

你比如说，我们来描述一个人吧。首先我们说他的 `firstName` 是什么，比如说叫 `Jason`。那么你看这个 `firstName` 就是一个 key，这个 `Jason` 就是一个值。那如果说你认为这一对键值对不能够描述这个信息又怎么办呢？没关系，**你可以不停地加**。

> **结论**：所以说它的**扩展性特别好**——一是扩展性好，第二个它是灵活。因为你这个键值对可以无限地增加。

再看一遍规则：键名写在前面，并且**用双引号包裹**，然后后面这个值**用冒号分开**；如果你有多个键值对，**用逗号间隔**；如果这个人的值有多个，可以用数组，**数组是用中括号**。

```json
{
	"name": "tom",
	"age": 20,
	"address": ["上海", "北京"]
}
```

如果说你想用 JSON 描述**多个人**又怎么办呢？也好办——你这地方中括号写在外面去，一个人，然后用逗号一间隔，又是第二个人。

#### 拿 json.cn 当一把尺子

有些同学说老师你给我们实实在在地写几个案例吧。好，没问题。

在我们的网络上有一个站点，叫 **`json.cn`**。这个网站可以验证一个 JSON 格式的数据是不是正确的，尤其是我们在编程、编写比较复杂的 JSON 格式的时候特别有用。

打开这个站点，我们来写一个 JSON 数据，我们看看格式对还是不对，我们可以用它来做一个验证。

**第一个案例**，我们描述一个人，这个人有名字和年龄：

```json
{
	"name": "tom",
	"age": 20
}
```

先是一对大括号，那你在里面要描述这个人有几个属性啊？你说这个人有名字，所以首先是名字，和名字是一个具体的值——`"tom"`。你看这就写完了，这就是合理了。但是你认为刚才讲了他还有年龄，所以用一个逗号间隔，写上 `age`。注意，因为 `age` 是一个整数，所以说你可以写 20。你看这个地方验证就是正确的，对不对？

**第二个案例**，我们来描述地址。假设这个人的地址有多个，如果他只有一个地址，比如说上海，我们就写一个；那如果这个人他有两个住址，一个是上海，一个是北京，那怎么办呢？**用中括号包起来**。你看，又可以成功了，是不是？

**第三个**，假设我要描述两个人。这是一具人嘛，这是一个人的 JSON 数据，假设我想描述还有一个 mary，那我怎么写呢？好，没问题，**你可以把它再包起来**。整个包起来过后呢，你可以再写一个人。我为了偷懒我就复制一下——比如这个人的名字叫 mary，她的年龄是 18，地址是天津和成都。

甚至里面还可以进一步扩展：说老师假设我这里面还有一个键值对怎么办呢？你还可以继续写。

当然我们还可以进一步扩展，比如说你觉得这里面信息还不够——这个人里面还有一个属性是什么呀？是他的**爱好 hobby**，你可以再写。里面他有几个爱好呢？比如说他喜欢**足球**，他还喜欢**乒乓球**，ping-pong。

> **结论**：用 JSON 格式来进行这个数据的保存和显示**特别的方便，而且很灵活**。而且同学们注意，将来我们在做这个开发的时候，我们会经常使用到这个 JSON 数据格式。大家一定要记住它的一个原则，就是 **key-value**——多对 key-value 可以组成一个非常复杂的、而且描述信息功能很强的 JSON 字符串。

这个站点还有几个顺手的功能：它可以**转成 XML 格式**，可以保存、复制、折叠，可以展开或者压缩显示，还可以折叠起来看到"这是一个数组，里面有两个 object"这样的层级结构。

最关键的一点：**如果你这写错了，打个比方说我假设少了一个逗号，那马上就给你检测到了**——它会告诉你在第二行发生了一个错误，说这个地方缺少了一个逗号，它连这个都给你检测出来了。所以说当我们在做编程的时候，你假设要去构建一个 JSON 字符串，但是你又不确定这个格式对不对，你就可以打开这个站点，然后把你的字符串往这一放，就可以进行一个验证了。一打开马上就进去了，非常的灵活，很好用。

> **结论**：把这个原则记住就可以了：**如果是数组的话用中括号；如果是键值对的话用冒号间隔；多个键值对用逗号间隔**。这是原则，不要忘了。

### json.Marshal：结构体、map 和切片

我们具体来看一下 JSON 的**序列化**的操作。那什么叫 JSON 序列化呢？就是说，如果我们把一个 Go 里面的数组把它进行一个序列化，那么就可以拿到一个对应的字符串。除了有数组，还有哪些东西呢？比如说结构体，再比如说 map——map 也是一个 key-value 的格式对吧，还有切片。

**序列化**是指将有 key-value 的这种结构的数据类型，比如说**结构体、map 和切片**，序列化成 JSON 数据、JSON 字符串的一种操作，这个就叫序列化。

那基本数据类型呢？比如说一个 int、一个字符串直接序列化，它都是可以的——只是说这样**没有意义**。所以我们经常序列化的呢，往往是具有这种 key-value 结构的、数据类型才比较有意义。

新建一个文件夹 `serial`，在里面写一个 `main.go`。我要引两个包：一个是 `fmt`，另一个是 `encoding`——`encoding` 下面有个 `json` 包。

先定义一个结构体 `Monster`，它有名字、年龄、生日、薪水、技能：

```go
type Monster struct {
	Name      string  // 名字
	Age       int     // 年龄
	Birthday  string  // 出生日期
	Salary    float64 // 薪水
	Skill     string  // 技能
}
```

然后写一个测试函数，我们用它来演示对结构体的一个序列化操作：

```go
func testStruct() {
	// 先声明并创建一个结构体
	monster := Monster{
		Name:     "牛魔王",
		Age:      500,
		Birthday: "2011-11-11",
		Salary:   8000.0,
		Skill:    "牛魔拳",
	}

	// 序列化
	data, err := json.Marshal(&monster)
	if err != nil {
		fmt.Printf("序列化错误 err=%v\n", err)
	}

	fmt.Printf("monster序列化后=%v\n", string(data))
}
```

牛魔王有 500 岁了，对不对；生日是 2011-11-11；每一个月能挣 8000 块；它最厉害的功夫是牛魔拳。

有了这个东西过后，这就是一个结构体的数据类型了。现在我们把它序列化。

#### json.Marshal 的脾气

打开我们的手册，在 `encoding` 的 `json` 里面呢，它有一个方法叫 **`Marshal`**。它是干什么的？`Marshal` 函数返回 `v` 的一个 **JSON 编码**。

注意啊，它在这里接受的是**一个空的接口类型** `interface{}`——那也就是说，任何一种数据类型是不是都可以让它进行序列化呀？没有说错吧？

然后它序列化完了过后呢，**它会返回一个 byte 切片**——这个注意啊，它返回的不是一个 byte 数组，**是一个 byte 切片**。如果序列化失败会返回一个 `error`。

> **结论**：所以我们用的最核心的序列化方法是 `Marshal`，而且它接受的参数是一个空接口，任何一种数据类型都可以传进去。最后返回的是一个 byte 切片，**你要显示成字符串，你还要对它进行一个转换才可以**。注意这个细节。

所以我这样写：

```go
data, err := json.Marshal(&monster)
if err != nil {
	fmt.Printf("序列化错误 err=%v\n", err)
}
fmt.Printf("monster序列化后=%v\n", string(data))
```

我给它直接传一个指针类型。为了好操作。序列化过后呢，这边就会返回一个 byte 切片，我把它放进去，然后接收一下 error。

我们来看一下序列化过后这个结果是什么样子的：

```text
{"Name":"牛魔王","Age":500,"Birthday":"2011-11-11","Salary":8000,"Skill":"牛魔拳"}
```

> **易错点**：注意啊，因为它是 byte 切片，因此你直接这样输出来是看不到内容的，你看到又是一堆什么呀？——你是不是又看到一堆数字啊？所以你要看这个效果，你要转成 `string` 类型。

那这个序列化我们就做完了。运行一下 `testStruct()`：

```bash
cd ..
cd serial
go run main.go
```

我们把这个序列化的东西复制一份，放到 `json.cn` 那个站点去进行一个验证——完全 OK。当我把这个结果往那个站点一放，它马上就把它翻译成了序列化的字符串。而且我们发现它的语法是没有问题的，都是正确的。**如果它真的序列化失败了，这个地方肯定会报错。**

#### 结构体：牛魔王

| 字段 | 类型 | 序列化结果里的键 |
| :--- | :--- | :--- |
| `Name` | `string` | `"Name"` |
| `Age` | `int` | `"Age"` |
| `Birthday` | `string` | `"Birthday"` |
| `Salary` | `float64` | `"Salary"` |
| `Skill` | `string` | `"Skill"` |

现在还没讲字段名怎么改，所以键就是字段名本身，一个不多一个不少。

#### map：顺序会变，结果不会错

第二个，我们来演示将 map 进行序列化：

```go
func testMap() {
	// map 的 key 是字符串，值是任意类型
	a := make(map[string]interface{})

	a["name"] = "红孩儿"
	a["age"] = 30
	a["address"] = "火云洞"

	data, err := json.Marshal(a)
	if err != nil {
		fmt.Printf("序列化错误 err=%v\n", err)
	}
	fmt.Printf("a map 序列化后=%v\n", string(data))
}
```

这个 map 呢，它的 key 是字符串，而它的值呢是任意类型——就是前面我们讲过的 `interface{}`，能看懂吧？

使用 map 之前需要 `make`——**如果你没有 make 就直接使用，会报错的**。

这个地方不需要再传地址了，因为大家都知道 **map 本身是按引用方式来传递的**，因此在这直接写个 `a` 就行了。它同样会把序列化的结果放在 `data` 里面去。

运行一下 `testMap()`：

```text
{"address":"火云洞","age":30,"name":"红孩儿"}
```

> **结论**：注意看——它**没有顺序**。大家都知道 map 的 key 是没有顺序的，所以序列化过后也不一定跟你写的顺序保持一致。你给的 key 是 `name`、`age`、`address`，但是序列化完了过后，它的顺序并不是跟你写的顺序保持一致的。**但不管怎么样，这个结果是对的**——我们把它进行一个验证，也是正确的，没毛病。

#### 切片：两个 map 就是一个数组

下面我们演示对切片进行序列化：

```go
func testSlice() {
	var slice []map[string]interface{}

	m1 = make(map[string]interface{})
	m1["name"] = "jacky"
	m1["age"] = 7
	m1["address"] = "北京"
	slice = append(slice, m1)

	m2 = make(map[string]interface{})
	m2["name"] = "tom"
	m2["age"] = 20
	m2["address"] = "墨西哥"
	slice = append(slice, m2)

	data, err := json.Marshal(slice)
	if err != nil {
		fmt.Printf("序列化错误 err=%v\n", err)
	}
	fmt.Printf("slice 序列化后=%v\n", string(data))
}
```

这里面的很多很多的 map，可以有多个 map——这个切片是**切片 map**，不是一个普通数据类型的 map。

这个住址甚至再给它放一个数组进去都是可以的。因为这里是 `interface{}`，那就意味着对应的值其实什么都可以。

运行 `testSlice()`：

```text
[{"address":"北京","age":7,"name":"jacky"},{"address":"墨西哥","age":20,"name":"tom"}]
```

可以看到，当对切片序列化过后，**它是一个数组了**。为什么是一个数组？因为这里面有两个 map——第一个 map 的值是它，用逗号隔开；也就是说这个 JSON 字符串其实包含了两个 map，它就相当于是一个数组了。

> **结论**：因为 JSON 是 key-value 结构，所以这个顺序其实并不是特别重要的。比如把 `address` 写在前面，还是把 `address` 写在后面无所谓，**只要它在大括号里面就行**。因为它是按 key-value 来进行区分的，所以对它的顺序就没有那么严格的要求，只要能够把 key-value 值对应上就可以。

#### 基本类型：能序列化，但没意义

我们再来讲一个案例。刚才讲过，对这种普通的数据类型，其实也可以序列化。比如一个 int 可不可以序列化？也可以序列化。

我们写一个函数 `testFloat64`，对 `float64` 这个类型序列化。首先有一个变量 `num1`，类型是 `float64`，直接给它赋一个值，比如是 2345.67，然后直接把它序列化。

运行一下看结果：首先它**没有报错**，也就是说它还是可以序列化的。但是我们发现它序列化过后其实**还是一串东西**，只是把它变成一个字符串而已。因为它没有 key-value，就不存在 key-value 对应信息的问题，只是相当于把 float64 直接转成了一个字符串。你要有兴趣把它打开，会发现它就是一个字符串。

所以刚才讲过，**对基本数据类型进行序列化其实意义不是很大**，在实际开发中我们几乎很少对基本数据类型进行序列化。

#### 顺带一提：interface{} 里放数组

另外，因为这里的类型是 `interface{}`，也可以放一个数组进去。比如定义一个 `[2]string` 数组也是可以的。大家可以观察一下如果是数组的话，序列化过后会变成什么样子。

### 一个"多此一举"的 tag

大家看我们的代码里面有一个问题。我们对结构体进行序列化的时候，可以看到：**它是把这个结构体的字段名字当做是 key，把字段的值当做是 value**。

但是大家有发现，因为我们这一个字段的名字有可能不满足你的需求。比如说你看，我这个 `Name` 是大写的 N。

那有一个什么问题呢？大家看我们这个图。**假如我们是一个 Web 程序**，我们这个 Go 服务器把这个结构体进行序列化过后，传给了浏览器。浏览器这一头肯定是用像 jQuery 或者是 JavaScript 进行解析。那这一边客户端，也就是我们说的浏览器端，它往往希望你返回来的这一个 key 值都保持一个小写；或者说我们这个浏览器这端，它可能给你指定一个名字，它要求你的每一个 key 是它指定的名字，它可能觉得更标准一点，对不对？因为你这个返回的是个大写的，它可能觉得不方便。

那怎么办呢？以前我在讲的时候提过这么一句，就是**结构体里面有个标签叫 `tag`**。如果说你希望你这个序列化过后的 JSON 串，它的这个 key 值按照你指定的标准来显示的话，你可以给这个结构体加一个 tag 标签。

```go
type Monster struct {
	Name string `json:"monster_name"`
	Age  int    `json:"monster_age"`
	Birthday string
	Sal float64
	Skill string
}
```

怎么写呢？先是**反引号**，然后写 `json`，**冒号**，然后这里面写上你的 JSON 过后的那一个字段的名称。比如说我这里写小写的 `name`；比如说这个年龄，我也可以改一下，我可以在这儿给它来一个指定，比如说 `json:"monster_age"`。

> **易错点**：这里有个地方特别容易搞错——**不能写在赋值的地方**。它必须写在**结构体的定义的位置**去指定 tag 标签，就在这儿写才是对的。

这样有什么好处呢？同学们，这样好处就是说，将来我们在序列化过后返回给客户端的时候，**浏览器可以用它喜欢的方式**，就是它觉得 key 都应该是小写的方式来进行操作。

保存一下，我们再来进行一个序列化的操作：

```text
{"monster_name":"牛魔王","monster_age":500,"Birthday":"2011-11-11","Sal":8000,"Skill":"芭蕉扇"}
```

大家看——它的 key 就变成 `monster_name` 了。如果你没有指定结构体的这个 tag 标签，那它还保持原先的标签的名字。这样的话，我们客户端或者说另外一方，它拿到这个串过后，就可以根据它喜欢的方式、习惯的方式去进行一个反序列化。

> **提示**：那它这怎么实现这个机制的呢？它是**用反射机制**。在进行序列化的时候，把这个 key 由 `Name` 改成了 `monster_name`。反射机制后面我们有一个专门的章节来进行讲解，这块我就先不讲了，后面在讲反射机制的时候我再详细说一下它是怎么实现这种转换的。

> **结论**：注意，注意事项——对于这个结构体的序列化，**如果我们希望序列化后的 key 的名字由我们自己重新指定，那么可以给这个 struct 指定一个 tag 标签**即可。

#### 为什么不能直接把字段名写成 monster_name

那有些同学可能会问了：老师，你这不就是**多此一举**吗？你既然想让它变成 `monster_name`，那你干脆直接把这个字段名叫做 `monster_name` 不就完了吗？何必还要多此一举呢？

同学们想一想，我这样做能行吗？显然，肯定是要失败的。为什么？

因为你在进行这个结构体序列化的时候，其实你用的是 `json.Marshal`——**json 是另外一个包**，它里面的一个函数来完成这个序列化的。那也就意味着，在我们 `Marshal` 这个函数里边，它会去**读取你的这个字段**来进行序列化。

但是因为你这个字段又是小写的 m，大家想一想，你在这个 `Marshal` 里面，一个**跨包的函数**去使用一个首字母小写的字段能行吗？因为你字母小写的话，它其实是一个**私有的**，也就是说它是**不可导出**的一个字段。那你这样用的话，它一定会在序列化的时候报错。

所以说，你没有办法直接在这写一个首字母小写的字段——**因为你要跨包去用它，那你这个字段必须首字母大写，你才能在别的包里面去用**。

好，我们来试一下，看是不是会报错。

果然已经报错了，27 行。改一下，把这边也改成 `monster_name`——它可能这儿不会报错了吧，因为你既然这儿写的是 `monster_name`，那这边肯定也是 `monster_name`。但是我告诉你，你这样改了过后这儿**还是要报错**，原因还是一样的，因为你跨包去使用一个不可导出的字段。

再来跑一下，看效果。序列化过后，**没有报错了**，但是你发现有个什么问题？`Age`、`Birthday`、`Sal`、`Skill` 都有了，但是**有一个字段丢掉了**——`Name` 就没有了。

它虽然没有报错，它肯定是在它的 `Marshal` 这个函数里面做了一个判断：**如果说可导出，我就去处理；如果不可导出，我就不处理了。**

> **结论**：那你不管怎么样，你丢掉了一个字段信息，那相当于就是错了嘛。你看原先这个 Monster 里面有五个字段，年龄、生日、薪水和它的 skill；但是等你序列化过后，你会发现你丢掉了一个字段，只是说它这儿**没有报异常而已**。大家可以去看源代码，它这个源代码里面，它肯定做了一个判断，就说这个字段能不能用，如果它不可用的话，它直接就不去处理这个字段——那显然这并不是我们程序员想要的效果。

**所以为什么我要把它写成 tag 这样的形式呢？** 因为我要兼顾两点：一是 `Marshal` 这个序列化函数**能够使用到、访问到**这个字段；同时我还希望它序列化过后，**这个字段的名字按照我指定的这个名字**来处理。

好，我把它再改回去。改回去过后——在 Go 程序里面，我们还是用 `Name`，对不对？再来看一把，这个又恢复正常了，是不是这个道理？你看，是不是又多了一个 `monster_name` 过来了，`monster_age` 也过来了。

### 反序列化：json.Unmarshal 与它的两个参数

我们来说一下反序列化。何为反序列化？把反序列化的概念给大家聊两句。

> **定义**：**反序列化是指将 json 字符串反序列化成对应的数据类型。** 比如说原先本身是一个结构体，结构体序列化过后成了一个 json 字符串，然后通过网络或者什么方式传送到另外一个程序，比如说是浏览器。浏览器拿到 json 串过后，可能会根据它的需要把它还原成数组或者是结构体。
>
> 反正就是说，拿到一个字符串传给了另外一个程序，程序希望能够把 json 串重新返回成原先的数据类型，这个我们就叫做反序列化。**其实反序列化就是序列化的一个逆向操作。**

```text
   Go 结构体                        JSON 字符串                       Go 结构体
 ┌──────────────┐   json.Marshal   ┌─────────────┐  json.Unmarshal  ┌──────────────┐
 │ Name: 牛魔王  ├─────────────────►│ {"Name":    ├─────────────────►│ Name: 牛魔王  │
 │ Age: 500     │                  │  "牛魔王",  │                  │ Age: 500     │
 │ Birthday: …  │                  │  "Age":500} │                  │ Birthday: …  │
 └──────────────┘                  └─────────────┘                  └──────────────┘
       ↑ 字段名必须是可导出的                │
        加 tag:json:"monster_name"          └── 键名默认取字段名，被 tag 覆盖
```

打开 VS Code，新建一个文件夹。反序列化的单词可以有两种写法：第一种叫 `unserialize`，还有一种干脆用 `unmarshal` 也可以，就看你的需求。我就叫 **`unmarshal`**，因为我们的函数刚好是 `Marshal`，它反序列化的函数名是 `Unmarshal`，这样子就保持一致。

#### 反序列化成结构体

写一个函数 `unmarshalStruct`。既然要把一个 json 串反序列化成结构体，我们首先应该先拿到这个字符串。因为这个字符串里面有双引号，所以先把它转义一下。

拿到一个字符串，你们怎么理解呢？可以这样理解：**相当于 A 客户端把一个结构体序列化过后成了一个字符串，通过后台服务器传给了 B 客户端**，B 客户端就拿到了一个 json 字符串。至于这个 json 字符串怎么拿到的，通过网络传输过来就行了。我这里因为演示，直接写了一个字符串，但这个字符串是满足序列化过后的规范的。**在真实的项目开发中，是通过网络传输获取到的，或者是读取文件获取到的**。

怎么样把它反序列化呢？非常简单。首先**结构体你还得把它拿过来**——因为你要把字符串反序列化成 Monster，肯定要有这个结构体的声明和定义，如果没有结构体的定义，肯定没有办法把它反序列化成 Monster，这个必须要有。（把反射机制、tag 标签拿掉，也可以保留，这个也没问题。）

```go
func unmarshalStruct() {
	str := "{\"Name\":\"牛魔王\",\"Age\":500,\"Birthday\":\"2011-11-11\",\"Sal\":8000,\"Skill\":\"芭蕉扇\"}"

	var monster Monster

	err := json.Unmarshal([]byte(str), &monster)
	if err != nil {
		fmt.Printf("unmarshal err=%v\n", err)
	}
	fmt.Printf("反序列化后 monster=%v\n", monster)
	fmt.Printf("反序列化后 monster.Name=%v\n", monster.Name)
}
```

先定义一个 Monster 的实例，然后调用 json 里面的一个函数叫 **`Unmarshal`**。

> **提示**：`Unmarshal` 里面会接收两个参数——**一个参数就是你的字符串所对应的 byte 切片**；**另外一个就是你要把字符反序列化过后交由哪一个结构体变量，改变哪一个结构体变量**。所以这里大家看到是**引用传递**。如果你不用引用传递，这个地方是改变不了它的值的，因为只有引用传递才能改变函数外面的参数，这个在以前是讲过的。

最后反序列化过后会返回一个信息。如果 `err` 不等于 nil，就说明反序列化失败了，把信息打出来。

运行：

```bash
cd ..
cd unmarshal
go run main.go
```

我们可以看到，当反序列化过后，结果跟我们想的是一样的——它已经有年龄、有生日。

**名字到哪去了？** 我们看看名字为什么没有看到？是不是因为在这粘贴的时候没有把名字粘过来？刚才少粘了个名字，粘的是刚才在演示的时候故意把名字拿掉的那一块，所以应该重新粘一份才能看到名字。

我们再运行一把，这时名字也就过来了。这个反序列化实际上就成功了。既然它已经变成了一个结构体的变量，你也可以取出里面的每一个字段——比如说我只想取出其中的一个，它的名字：

```go
fmt.Printf("反序列化后 monster.Name=%v\n", monster.Name)
```

跑一个。大家看，我也可以单独地取出其中的一个字段，完全正确。

这就是我们结构体的一个反序列化。其它的就比较轻松了——因为我们已经有了将字符串反序列化成结构体的讲解，那么下面把它反序列化成 map 和切片就**如法炮制**了。

#### 反序列化成 map：为什么不用 make

我们写一个函数 `unmarshalMap`：

```go
func unmarshalMap() {
	str := "{\"address\":\"火云洞\",\"age\":30,\"name\":\"红孩儿\"}"

	// 这个 map 要跟原先序列化的 map 结构保持一致
	var a map[string]interface{}

	err := json.Unmarshal([]byte(str), &a)
	if err != nil {
		fmt.Printf("unmarshal err=%v\n", err)
	}
	fmt.Printf("反序列化后 a=%v\n", a)
}
```

还是老规矩，首先把这个串串拿到——你首先要通过网络或者是读取文件拿到一个 map 的字符串。因为你是在这直接写字符串的，所以说这个转义符号得给，不然语法会出问题。

拿到这个字符串过后，我们反序列化老规矩，先定义一个 map。**这个 map 要跟你原先那个 map 的结构要一样，你不能瞎定义一个 map**——比如说你这地方这个 map 它的 key 是字符串的，你不能写成 int 了。你这个 map 要跟你原先以前定的这个 map 的结构保持一致。

那这个时候，map 按理说它是需要先 make 一下再使用的。但是——

> **结论**：**如果是反序列化，我们不需要 make 这个 a 了**，你看我这直接反序列化就行了。**因为反序列化底层它会自动地 make 这个 map 空间。**
>
> 为什么不需要 make 呢？因为这个 make 的操作被**直接封装到 `Unmarshal` 函数里面去了**。也就是说，你这个 `Unmarshal` 里面，它一检测 `a` 是个 map，怎么办呢？它**利用类型断言**，它知道这个 `a` 是一个 map，它在这个函数内部进行了一个 make 操作。所以说我们在外面就不需要再 make 了。

我们可以看到，当我们反序列化这个 map 过后，它的的确确成功了。那有些同学可能有点疑惑——老师，那我前面讲过，一个 map 在使用之前需要先 make 一个空间，那为什么我在反序列化时没有 make 呢？这个道理大家要搞清楚。

#### 反序列化成切片，和长字符串的拼接

接着我们演示第三个：演示将这个 JSON 串反序列化成 slice。函数名改叫 `unmarshalSlice`。

同样的道理，首先得有一个字符串。我还是老规矩从这边粘一份过来——这个是一个 slice 的结构，比较长。

> **易错点**：这个字符串越来越长，那怎么办呢？大家想一想，如果这样的话肯定不利于我们的阅读。**当一个字符串很长的时候，我们可以把它换行来写。** 怎么换行呢？把第一个人写完了就换一行。换一行这样子肯定是要报错的，怎么办？简单——**用这个引号给它截了，再用个加号**。加号就是字符串拼接嘛，当然你不要忘了，这边也有一个加号。这样就可以了，就是说把上面这个字符串加上下面这个字符串进行一个拼接就 OK 了。

```go
func unmarshalSlice() {
	str := "[{\"address\":[\"墨西哥\",\"夏威夷\"],\"age\":20,\"name\":\"tom\"}" +
		",{\"address\":[\"北京\"],\"age\":7,\"name\":\"jacky\"}]"

	var slice []map[string]interface{}

	err := json.Unmarshal([]byte(str), &slice)
	if err != nil {
		fmt.Printf("unmarshal err=%v\n", err)
	}
	fmt.Printf("反序列化后 slice=%v\n", slice)
}
```

因为你要把它反序列化成切片，你首先得有一个空切片。而且**这个切片的类型也不能乱写**——你原先在序列化的时候，你的切片的类型是这个类型，那你不能说，到时候我把它反序列化过后，我变成另外一种类型的切片，那就不行。

> **结论**：所以你要**严格地保证这个类型的一致**，两边都要沟通的。比如说我这个序列化过后，原先这个数组或者这个结构体或者切片是什么样子，那你这边 B 端也得按照这种方式进行反序列化。**你不能说我序列化了一个 JSON，你想把它转成什么类型就转成什么类型，那是不可以的。**

同样道理，这个 map 也不需要 make——因为这个 make 操作，它也被封装到 `Unmarshal` 里面去了。它不管是 slice 还是 map，它直接把所有的 make 操作全部封装到 `Unmarshal` 里面去了。所以说这个反序列化其实还是挺简单的。

我们把结果打印出来看一下。我们可以看到反序列化后完全 OK——`slice` 是一个切片，它里面有两个 map，而且第二个 map 里面的地址是一个数组，是墨西哥和夏威夷。

### 两条容易翻车的规矩

关于上面的这些代码，老师还有一些需要交代的地方，我再总结一下。这很重要，注意听讲，不然的话以后这个细节容易忽略。

**第一个：反序列化后的数据类型，必须和序列化前的数据类型一致。**

在反序列化一个 JSON 字符串时，要确保反序列化后的这个数据类型和原来序列化前的数据类型一致。怎么个意思呢？比如说，你这个地方反序列化一个 Monster，它是这么一个字符串。它原先这个字符串是怎么拿到的？它是序列化一个 Monster 结构体才拿到这个字符串的。那你反序列化的时候呢，你也要反序列化 Monster——**你不能反序列化另外一个结构体**。

比如说，我有一个别的结构体叫 `Dog`，它也有名字，是 string；它还有一个地址 address，也是 string。你不能说，老师我想把这个字符串反序列化成 `Dog`——**那这种就不可以**。这样反序列化过后其实是一个很奇怪的东西，因为你原先是 Monster，你反序列化成 Dog，它字段可能就匹配不上了。

> **提示**：除非你这样子——老师，我能不能这样，我这虽然是个 Dog，但是里面的字段，我这里面的字段跟原先 Monster **完全一样**？那可以，那是可以的。
>
> 为什么？因为**这个字符串里面并没有包含它到底是一个 Dog 还是 Monster，它主要是取决于你这个字段到底有哪些**。你只要保证你这个结构体里面有 `Name`、有 `Age`、有 `Birthday`、有 `Sal`，就行了。至于你这个是 Monster 还是 Dog，它不管。**但是作为我们这个结构体来说，它真正确定它是什么类型，主要还是取决于这个字段嘛。**

所以我就把它直接换成 `Dog`——你看它也能跑起来。这个 `Dog` 的字段和 `Monster` 的字段是完全匹配的，在这种情况下你可以。如果说你这个 `Dog` 里面有个别的类型，那就麻烦了。

**结论**：对结构体来说，"数据类型一致"主要是指**字段类型要完全一样，名字也要一样**。你名字不一样，那肯定就反序列化不成功了。

**第二个：反引号和转义符那个坑——字符串如果是程序获取到的，就不需要转义。**

老师在演示的时候加了很多反斜杠。有些同学说：老师，那以后这个反序列化好麻烦啊，难道我拿到一个字符串过后，我还要把里面的引号进行一个转义吗？

> **结论**：**不需要。** 如果你的 JSON 字符串是通过程序获取到的，是不需要加这些反斜杠的。因为字符串里面它本身通过程序得到的，引号它自己会做转义处理。

我给大家举个例子。我们前面不是有一个 `testMap` 吗？我把这个 `testMap` 拿过来，让它返回一个 string——那这我就不输出了，然后我直接 `return string(data)`：

```go
func testMap() string {
	a := make(map[string]interface{})
	a["name"] = "红孩儿"
	a["age"] = 30
	a["address"] = "火云洞"

	data, err := json.Marshal(a)
	if err != nil {
		fmt.Printf("序列化错误 err=%v\n", err)
	}
	return string(data)
}
```

然后我这个字符串，这样获取：

```go
str := testMap()
```

你看，如果我是通过一个程序或者是一个网络获取到这个字符串，**其实我没有必要再去加一堆反斜杠**。跑起来我们可以看到，反序列化也是 OK 的，完全没问题。

所以总结一句：**如果 JSON 字符串是通过程序本身获取到的，则不需要再对双引号进行转义处理。** 老师这儿进行转义处理，完全是因为我直接写了一个原生形态的字符串，所以我才要对它进行转义处理。**原生字符串是需要转义处理的；程序获取的不需要转义，因为字符串内部已经转义了。**

## 单元测试的来路：从 main 里的一次手工对答案说起
> 对应块：BLK97 | 覆盖分集：P260-P261 | 块标题（分集名）：《258_尚硅谷_单元测试的引出》

今天要讲的东西，可以说相对来说比较重要，而且听起来应该是有一定小小的难度。一个是单元测试，第二个就是 goroutine 和管道，叫 channel。这两个东西虽然听起来比较麻烦，但实际上特别好玩，它可以做一些很有意思的东西出来。

我经常讲，如果说 Go 语言的核心，或者它跟别的语言不一样的地方、它的特色，我感觉 goroutine 和管道是它很重大的一个特色，包括前面讲的接口编程也是它的一个特色。这个大家听起来会比较好玩，我也会尽量把它讲得透彻一点。

那么先来给大家讲一下单元测试。

### 一个很朴素的需求

单元测试是什么呢？听其名而知其意，肯定是一个关于测试的框架。我们学 Java 也好，学 PHP 也好，它都有自己的一个测试框架。这个单元测试往往是针对一个模块，或者是针对一个函数来进行测试的。

还是老规矩，先看一个小小的需求，由这个需求引出我们的单元测试。这里有一个可爱的函数 `addUpper`，非常简单：我传进去一个 $n$，然后进行一个累加，从 1 加到 $n$，得到一个结果，就这么简单一个题。这个函数本身是非常简单的。当然在实际开发中，将来这个函数可能很复杂，可能会很复杂。

那这个时候我们有一个需求是：我们怎么确认它运行的结果是正确的？

当然有同学会说：韩老师，这个东西有什么可讲的？那我这个地方输入一个 10，看它结果是不是等于 55 不就得了吗？可以，确实是如此。但是大家要想到，你们将来面对调用的这个函数可能很复杂，也有可能这个函数是你的一个队友写的。比如你的队友写了一个对数据库或者 Redis 的一个操作，然后你希望把这个数据取出来，然后再干什么事情。你可能很清楚地知道结果，但是它本身函数很复杂，这是第一种。

第二种，有可能你调用的是第三方的接口，然后你给它传一个参数，你希望它返回一个结果。好，这个时候我们就涉及到去测试它的结果是否正确。

所以这个需求咱们引出来了，就是在开发中我们经常有这样一个需求：去确认一个函数或者一个模块的结果是否正确。这个需求肯定是客观存在的，不管你是一个开发人员，还是一个测试人员，你都必须要面对这样的情况。

那么面对这样一个情况，咱们怎么解决呢？还是老规矩，第一个，我们先看看传统的方法能不能解决。

### 传统做法：在 main 里手测

传统的方法解决还是比较简单的，一个最简单、最直接的想法就是说：我在一个 `main` 函数里面去调用你给我的一个函数或者是一个模块，我看看实际输出的结果和我预期的结果是不是一样，就完了。这是一个非常直观、原始的想法。如果一致说明正确，如果不一致说明错误，然后修改就完了。

我们新建一个目录 `chapter15`，底下建一个 `testingdemo01`，再在里面新建一个 `main` 目录，写上 `main.go`：

```go
package main

import (
	"fmt"
)

// 一个被测试的函数
func addUpper(n int) int {
	res := 0
	for i := 1; i <= n; i++ {
		res += i
	}
	return res
}

func main() {
	// 传统的测试方法，就是在 main 函数中使用，看看结果是否正确
	res := addUpper(10)
	if res != 55 {
		fmt.Printf("addUpper 错误 返回值=%v 期望值=%v\n", res, 55)
	} else {
		fmt.Printf("addUpper 正确 返回值=%v 期望值=%v\n", res, 55)
	}
}
```

回到上一级进入到 `testingdemo01` 目录，跑起来：

```bash
go run main.go
```

运行过后，我们发现结果跟我们想的是一样的，输出 `addUpper 正确 返回值=55 期望值=55`。如果我返回的值不正确呢？假定我的代码不小心写成了 `n - 1`，那这个时候我一测试，它返回什么呢？`addUpper 错误 返回值=45 期望值=55`。

好，这是我们传统的一个测试方法。那么这种传统测试方法有什么缺点呢？我们先来做一个简单的分析，找到它的缺点，大家才知道为什么我们需要单元测试这一个技术。

### 传统做法的两个死结

我要善于总结。第一点，是**不方便**。

为什么说不方便？首先因为你要把这个 `addUpper` 直接放到 `main` 里面去写。你这个函数假如正在运行，假如你的项目已经运行了，你放这儿去测试，即使你没有在生产环境，你就是在别的地方，比如说你这儿写的一个程序假设正在运行，你还得把它停一下。停一下过后你还要改这个主函数，你还得去改人家的代码，很麻烦的。就是说你至少要涉及到去改现在有可能正在运行的代码，这个肯定是不方便的。

不方便的原因是：我们需要在主函数中去调用，这样就需要去修改我们的代码，修改这个主函数。如果现在项目正在运行，就更加的麻烦，就有可能去停止项目。

当然有同学可能这样说的：老师，那我自已做一个测试环境就可以了嘛。当然也可以。我说如果如果你现在就想简单地测试一个函数对不对，那你只能去搭建一个完整的、跟你真实正在运行的项目一模一样的，你才能去测试。假使不一样，你还不敢保证你在那儿测试正确了，在真实环境里面可能它又是错的，这个不好说，因为有时候是跟你这个环境有关系的。

有些时候测试是可以直接做一个真正的测试环境，但有时候的测试你必须在生产环境。大家明白我意思吧？因为生产环境有很多数据，你在测试环境是没有的，没有办法。这就是我们有些同学没有经验。

以前我们在新浪工作的时候就有这种情况，你就必须在这个生产环境测试，因为你没有这个数据。比如打个最简单的比方，你生产环境的数据量产生的假设是几千万，你在测试环境有这个环境吗？你没有。第二个，你在真实环境你要去调用对方第三方的一个文件，你在测试环境有吗？人家根本不给你开放，你没办法。所以有时候你必须在这个生产环境测，很麻烦的。

第二个，我觉得**不利于管理**。

为什么说不利于管理呢？各位同学看，你现在是测试一个函数，那我假设我这儿还有第二个函数，或者第二个功能模块叫 `addUpper2`，你来给我测一个 `addUpper2` 会不会正确。当然这个假设是另外一个功能，比如说求它的一个和。那你这个时候还得把这个注销，注销完了过后你再去判断，很麻烦。

因为它融在一起的，它是把你这个测试给它放在一个主函数。你想一想，相当于一坨。你为了去测试这个，没准还得这样子：把它注销了，然后说我要测试 `addUpper`，你麻烦不麻烦？显然这个很不方便，因为你把所有的测试只能写在一个主函数里面去。

自己测的时候都不知道我测的到底是哪一个函数，我测的是哪一个功能模块，对不对？

所以第二个是不利于管理。因为当我们测试多个函数或者多个模块时，都需要写在这个 `main` 函数中，不利于我们的管理和清晰我们的思路。

大家看到，第一个不好，第二个也不好。现在所有的不好就在发出一种呼唤，赶紧出现一个新的东西吧，对不对？引出我们要讲的单元测试。

### Go 自带的 testing 框架

Golang 跟别的编程语言一样，一般的编程语言都会有一个叫测试框架的东西。我们的 Golang 里面它有一个叫 `testing` 测试框架。这个框架待会儿我讲原理，你把这个原理一听就知道，这个家伙还是挺好的。`testing` 这个测试框架可以很好地解决这个问题，让我们测试变得比较简单。

Go 语言中自带一个轻量级的测试框架叫 `testing`，和自带的 `go test` 命令来实现单元测试和性能测试。

> **注意**：它既可以做单元测试，同时它还可以做性能测试。

怎么说体现出性能测试呢？性能测试其中一个最主要的参考指标就是时间。也就是说我执行你这个代码，我花多少时间，是不是？如果说它本身能够把这个函数测试的时间返回来，那不更方便吗？尤其是在我们生产环境，我们想去测一个函数，它运行的效率、速度怎么样，这样就非常方便。

`testing` 框架和其他语言的框架类似，可以基于这个框架写针对于相应函数的测试用例。测试用例我们经常叫这个词叫 test case，或者叫 testing case。将来测一个函数，或者说测一个模块，我们通常把它叫测试用例，这个概念。也可以基于该框架写相应的压力测试用例。

通过单元测试可以解决如下问题：

- 第一个，确保每个函数是可运行的，并且正确；
- 第二点，确保我们写出的代码性能是好的。你千万不要写了一个代码，是吧，张三写个代码，李四写个代码，你想知道谁的代码更好，直接用这个 `testing` 一下就测试出来了；
- 单元测试能及时的发现程序设计中实现的逻辑错误。也就是说我希望一个值，但是你返回的不是对的，好，逻辑错误，让这个问题及早暴露，便于定位解决。

而性能测试重点在于发现程序上设计的问题，让程序能够在高并发的情况下还能保持稳定。

> **提示**：第二点很重要。如果说你将来想去看你下面的手下，比如说你下面管了十个程序员，你想看看哪一个程序员到底是真的干活还是假干活呢？简单，你把这个测试用例一测，发现人家写代码要么是错的，要么性能很差，这个时候一下就把这些抓出来了。

### 快速入门：第一个测试用例

刚才老师已经讲了，我们再来说一下。现在我们直接用 Go 的单元测试来对 `addUpper` 和 `sub` 函数进行测试。这个 `sub` 函数我们没写，待会儿我加一个，就是求两个数的差。

> **温馨提示**：有些时候你们在测试的时候，就在你们机器上测试的时候，可能需要暂时退一下 360。因为 360 有可能会认为生成的测试用例是一个木马，但实际上我们不是木马。有可能如果你出现这个情况，你就退；但如果没有出现就算了。因为 360 有时候在不同系统下它也不一样，跟你运行的时间也是有关系的，反正这块跟它底层是有关系的。

首先我把这个 `main.go` 换一个别的名字。为什么呢？因为你这个函数将来，你测试的函数不会直接放在 `main.go`，对不对？大家想一想，我们是不是将来会把自己的函数写在一个专门的 `utils` 底下去啊？所以我干脆就不动它，给它留一个主函数接口也无所谓。

我们新建一个文件叫 `cal.go`，也就是说我将来计算的、关于计算的函数我就直接放在这个包里面去：

```go
package main

// 一个被测试的函数
func addUpper(n int) int {
	res := 0
	for i := 1; i <= n; i++ {
		res += i
	}
	return res
}
```

写到这个地方它报错，报错的原因是它发现你这儿没有主函数。注意，没有主函数不要管它。

紧接着写下一个文件，叫 `cal_test.go`：

```go
package main

import (
	"fmt"
	"testing"
)

func TestAddUpper(t *testing.T) {

}
```

这有规范了。我们先给大家入门，细节我先不说，我直接说：前面命名必须是 `Test`，必须是 `Test`，然后我们后面一般会写上你要测的这个函数的名字。那么这个地方这个 A 呢，我们要大写。

这边会有一个参数，这个参数比较重要：`t *testing.T`。待会儿我再解释。既然用了它，我们需要引一个包，`testing` 包，相当于引入我们 Go 的测试、`testing` 这个轻量级框架的包。

打开我们的手册，定位一下这个 `testing` 里面有哪些内容。Go 官方文档，我们搜到 `testing` 这个包。

它写着：`testing` 提供了对 Go 包的自动化测试的支持。通过 `go test` 指令，能够自动执行如下形式的任何函数。

> **定义**：`Test` 打头的函数，后面这个 xxx 随便写，但是有要求，其中这个 xxx 可以是任何字母、数字组成的字符串，但是第一个字母不能是小写的 a 到 z。为什么？因为它是用于识别测试用例的。

它的语法就这么简单。接着往下写，调用我们刚才写的那个函数：

```go
func TestAddUpper(t *testing.T) {
	res := addUpper(10)

	if res != 55 {
		t.Fatalf("AddUpper 执行错误，期望值=%v 实际值=%v\n", 55, res)
	}

	t.Logf("AddUpper 执行正确...")
}
```

`t` 长什么样子？打开手册找到 `testing`，里面有一个类型 `T`。这个 `T` 是一个结构体，这个结构体提供了很多的方法，其中有一个方法叫 `Fatalf`，就是格式化，可以调用它相当于在输出这个日志，输出这个日志的同时，它还把这个程序给停止了。这个用得比较多，所以说我用这个 `Fatalf`。

> **结论**：`t.Fatalf` = 打日志 + 终止这个测试用例；`t.Logf` = 只打日志，不终止。

那如果没有退出怎么办呢？好，下面我们就正常写日志。如果正确，到这儿就正确了，如果正确我们就记录日志、输出日志都可以。这个日志怎么输呢？`t` 有一个方法叫 `Logf`，我们就写一句话，就说 "AddUpper 执行正确"，执行正确。

保存这个代码。发现 `fmt` 因为没有用到，是不是就可以让它暂时地取消了？好的，看还有没有错误，我们发现没错。

大家可能会觉得，老师好像没什么感觉啊，你这写的不就是相当于写了个 `addUpper`，然后写了一个你把它叫做测试用例的这么一个东西吗？好像没有感觉。但是当我一运行的时候，你会觉得很奇怪。至少你应该有一个疑惑：老师为什么可以测试呢？你连主函数都没写。

### 主函数去哪了：运行原理

这个示意图也很重要，你把这个示意图搞懂了，各位朋友，那也就是说底层的原理也是清楚的。

`cd ..` 我回到上一级，`dir` 一下，看到现在我这边有两个文件，一个是 `cal.go`，一个是 `cal_test.go`。现在我要运行它，使用我们的 `go test -v`：

```bash
go test -v
```

大家可以看到，我们这里有一个问题：

```text
=== RUN   TestAddUpper
--- FAIL: TestAddUpper (0.00s)
    cal_test.go:14: AddUpper 执行错误，期望值=55 实际值=45
```

它说现在它帮你运行了一个叫 `TestAddUpper` 这么一个用例，或者叫例程。然后它说你这个错了，为什么错了？你这个是 14 行，说 `addUpper` 执行错误了，期望值是 55，但是实际上是一个 45。而且它告诉你，你的这一个文件一共用了 0.00 秒时间。

也就是说实际上它已经帮我们调用了这个函数。但是你们应该会觉得很奇怪，老师主函数在哪儿去了呢？

主函数其实是被隐藏起来的。因为我们这个地方其实是跑了一个 testing 框架，也就是说当你运行的时候，其实调用的是 testing 这个框架。

```text
              你的普通文件                      你的测试文件
        ┌───────────────────┐            ┌──────────────────────┐
        │      cal.go       │            │     cal_test.go      │
        │                   │  直接调用   │                      │
        │   addUpper(n)     │◄───────────┤  TestAddUpper(t)     │
        │   getSub(n1,n2)   │            │        │             │
        └───────────────────┘            └────────┼─────────────┘
                                                    │ 框架扫描并调用
                                                    ▼
                                       ┌────────────────────────┐
                                       │    testing 框架         │
                                       │  （隐藏的 "main"）     │
                                       │                        │
                                       │  ① 引入 *_test.go 文件  │
                                       │  ② 调用 TestXxx 函数   │
                                       └────────────────────────┘
```

它会做两件事情：

**第一件**，默认情况下将 `_test.go` 结尾的文件引入。那么相当于说，你可以理解成这有个主函数——你可以这样简单理解说，主函数被它隐藏起来了。它把你的这个文件引入，相当于一个 `import`，我不去写得那么详尽，因为它是按照规范来引的。

**第二步，这个很重要。** 它也有个规范，它将你以 `Test` 打头的函数全部给你调一下。只要你这按这个函数写的，我就给你调起来。

于是乎同学们看到，其实就这样子的。也就是说我们的系统一运行，它就跑过来去执行你的这段代码。系统一调用，它发现你这引的是一个 testing 框架，它就调这个。调这个的时候，这个 testing 框架会把你的这些个以 `_test.go` 结尾的这些文件引进去，然后它继续扫描你这个文件里面有哪些是以 `Test` 打头的函数再调。而你这里面又写的是把原先函数调进去，所以说这个就一层一层地进行了一个简单的引入并操作。

### 亲手推翻自己：两个实验

既然刚才韩老师说了，只要是以 `Test` 开头的都会被调用，那么我们再写一个文件，看看跟韩老师讲的是不是一样的。

**第一个实验**，我们证明一下。首先把这个函数名给我瞎改一个，你们看看能不能跑起来。请看，我把它改成一个 `Ok`。这个时候，此时此刻这个函数已经不再是以 `Test` 打头了。那么这个时候我们一运行：


啥都没有。但是它还是跑了一下，因为本身框架执行是需要时间的。它说 `PASS`，啥都没有，`[no tests to run]`，什么意思？没有一个测试用例去运行，完事。因为你的函数已经跟人家写的不是一个规范了，你写错了。

**第二个实验**，我们证明第二点，只要你有别的函数一样会被调用。打个比方说假设我写了一个 `TestHello`，然后我在里面写了一句话，说 `Hello` 被调用。同学们动动脑筋，你们觉得会不会被调用呢？必须的。所以你就写个 `TestHello 被调用`，或者说被测试，对不对？被调用。

### 多个文件、多个包

求两个数的差就可以了，$n_1$、$n_2$，返回一个值，非常的简单。

```go
func TestGetSub(t *testing.T) {
```

## 把 testing 框架的规矩抠干净，再拿一个 Monster 练手
> 对应块：BLK98 | 覆盖分集：P262-P263 | 块标题（分集名）：《260_尚硅谷_单元测试细节说明》

那么我们接着上节课的继续讲。刚才呢，我们已经把单元测试的基本原理、它的一个运行机制做了一个说明。做一个说明过后呢，我们来看一下它的细节。就是把刚才讲的东西再总结一下，大家心里面就比较有底了。

### 文件名必须以 _test.go 结尾

第一个，我们看一下测试用例的文件名必须以 `_test.go` 结尾，比如说 `cal_test.go`。

这个 `cal` 怎么写，没有规定。手册里面写得也是非常清楚的：它说要编写一个测试的套件（又翻成套件，你受得了吗？对吧，case 就一样的），需要创建一个名字以 `_test.go` 结尾的。说得很清楚，你一定是必须以这个结尾的。但是你前面怎么写都无所谓，因为它都会把它加载进去。

那么这个文件放在哪儿呢？将该文件放在与被测试包相同的包中就可以了，当然也可以是主包——刚才我们换了一个包名，它的错误信息一点都没有了。

> **提示**：该文件将被排除在正常的程序支持包之外，在运行 `go test` 命令时将被包含进去。这一点大家要清楚，这是第一个需要同学们知道的。

### 函数名以 Test 打头，但别把它写得太随意

测试用例的函数必须以 `Test` 打头，刚才已经说了。一般来讲，我们这个测试函数是 `Test` 加被测试函数的名字。

> **易错点**：这个字母只要不以 `a` 到 `z` 小写就可以了。如果我这样写肯定就是错的。比如说我把 `TestAddUpper` 这个 `A` 改成小写的 `a`，我们来运行一下，看看有什么问题。它已经告诉你一个警告了，它检测出来了。它怎么检测的呢？它检测到你前面是 `Test`，它认为你应该是一个测试用例；但是你又不是这样写的时候，它告诉你 `TestaddUpper` 是一个不规范的、不规则的名字，第一个字母 `must not be lowercase`，就是必须不能是小写。

但是你后面那个名字叫什么都可以。假设我用 `y` 行不行？也可以，它测试的仍然是 `addUpper`。也就是说它到底测试哪一个函数，其实不是你前面这个名字决定的，而是你里面内容决定的。这个大家要一定清楚。

看，我这一保存，它就不报错了，它仍然是会调用这个东西。但是我们也没有必要故意瞎写一个名字。因为这个名字一看，别的同事一看 `TestAddUpper`，也就很清楚测试的是 `addUpper`。你不要写个 `Test` 什么其他毫不相关的名字，也不对。

### 形参必须是 *testing.T

第三个细节，`TestAddUpper` 这个参数的形参必须是 `*testing.T`。

手册上写得很清楚，就是 `*testing.T`。那这个 `T` 是什么东西呢？我们来看一下它里面包含什么东西。往下拉，里面呢有一个 `type T`，包含了很多的方法。这个大家应该能看懂，因为前面我们讲过，这个是代表它和一个 `T` 绑定。

| 方法 | 作用 |
| --- | --- |
| `Error` / `Errorf` | 打一个错误，格式化的错误 |
| `Fail` / `FailNow` | 致命的错误，致命错误并把这个输出的日志格式化 |
| `Logf` | 记录日志 |
| `Run` | 运行 |
| `Skip` | 跳过 |

最常用的就是刚才老师所说的，一个是 `Fatalf`，另外一个呢就是我刚才说的这个 `Logf`，这是格式化输出一个日志，这两个用得比较多。其它的函数呢，同学们有兴趣自己点进去看一下就行了。因为我们现在呢还是要重点就是大家能用，达到能用就行了。

### 一个文件里可以塞多个测试用例

第四个细节，一个测试用例文件中可以含有多个测试用例函数。

什么意思呢？就这个图。就说我这一个测试用例文件，可以包含很多个函数。我既可以测试 `TestAddUpper`，也可以测试 `TestHello`，这个都是可以的。

### -v 加不加，输出完全不一样

第五个，这个有用。运行测试用例的指令呢，我们前面用的是 `-v`。这个方式呢，运行正确或是错误都会输出日志。

如果说你只想看错误的——比如如果正确，你就不要告诉我了，你只告诉我这个错误的，那你就不要带 `-v`。

大家看我运行一下。比如说我把这个 `-v` 去掉，你们可以看到此时此刻输出的信息其实非常的简洁，就告诉你 `PASS`，其他不要了。因为你都正确。有一个呢就是这是我的一个显示输出，因为不是以日志的形式打出的，所以它还是给你调出来了。但是其他的，像你刚才看到的 `t.Fatalf` 和 `Logf` 就不给你输出来了，他认为是正确的，你不想看。

如果错误呢，他仍然会提示。打个比方，我给你们改一下。假设我们这个函数 `addUpper` 又写错了，我们又把它改成 `n - 1`，`-1` 显然是错的，对不对？好，这个时候我们再来运行一下，你看错误信息还是会输出的。因为他就觉得正确就算了，错误还是给你显示。大家看这里，他还是告诉你错了，他说 `FAIL`。哪里错了呢？就是这里面有 14 行说执行错误。

> **结论**：`PASS` 表示测试用例运行成功，`FAIL` 表示测试用例运行失败。当出现错误时使用 `t.Fatalf` 来格式化输出错误信息并退出程序；正常日志用 `t.Logf`。

### 只测一个文件，或者只测一个函数

测试单个文件一定要带上被测试的源文件。什么意思呢？因为在默认情况下呢，我们测试框架它会整体扫描你这个所在文件夹所有的测试文件。但是有时候你可能不是这个需求，说我只想测试这一个文件里面的测试用例。那怎么办呢？你就指定文件名就可以了：

```bash
go test -v
```

默认是全部测试。刚才我们一共测试了三个。现在我只想测试那个 `cal_test.go` 那个文件里面的测试用例，我应该这么写：

```bash
go test -v cal_test.go cal.go
```

这个顺序应该无所谓，你可以把这个写前面。这样就可以了。这样代表就测试 upper 和 hello。我们运行一下，大家请看到，那个 `sub_test.go` 就不会再被测试了。

> **结论**：只测一个文件，等于以**文件**为单位筛选。哪一个不会被调用呢？就是你的这一个 `sub_test` 这个函数就不会再被测试了。

还有一点呢，有些同学说老师我有这样一个需求，我只想测试其中一个函数，也可以。因为有时候这个测试用例特别多，你每次全部测试你不是吃饱了没事干吗，对不对？因为将来你真实测试的时候这个测试用例很多，函数很多。你说有一百个我都去测试一下，自个儿看得都眼晕。

那怎么写呢？就带上 `-run` 参数，再加上你要测试的那一个测试用例的函数名：

```bash
go test -v -run TestAddUpper
```

好，同学们大家可以看到呢，现在就测试了一个，哪一个呢？就是 `TestAddUpper`。

> **易错点**：这里有一个很容易踩的坑——`-run` 后面的名字必须跟你测试用例里写的**一模一样**，包括大小写。我第一次敲的时候把大写的 `U` 写成了小写，结果它告诉你 `no tests to run`，一个都没测到。改回大写就正常了。

### 拿一个 Monster 练练手

好，细节我们就说完了。下面呢就要给大家出一个题了，我先截取一段视频。

那么我们讲了这么多，我想给大家一点时间，布置一个单元测试综合案例要求。

既然你做这样一个单元测试，我们最好是新建一个文件夹，就不要跟它打架了。但实际上你要把它放在一起也是可以的，不过我个人并不是习惯这种写法，所以我们最好是新建一个文件夹。

来，新建一个文件夹，比如我们叫 `testcase02`。然后在这里边，我们把该有的文件就放在这个文件夹就可以了。我们新建第一个文件 `monster.go`，因为我要测试的就是它。然后对它进行测试的这个文件，我们按照这个规范来写就可以了，我们叫做 `monster_test.go`。这样子就代表一个测试文件。

包的名字只要不起主包就可以，起别的包都行。那我们就叫 `monster` 吧，简单一点。

先来做一个结构体：

```go
type Monster struct {
	Name  string
	Age   int
	Skill string
}
```

有名字、有年龄，还有一个 `Skill`，它的一个技能，string。好，这就写完了。

#### Store：序列化并保存到文件中

给它绑定这个方法非常的简单。`Store` 呢？将它序列化并保存到文件中。那也就是说对方会传一个 Monster 这个实例过来，也就是说到这函数的时候，它已经有这个实例了，调用我们的方法就可以了。这时我们需要引包。

就是直接将序列化后保存到文件中，那得两步走。第一步先序列化，第二步再保存。先序列化，把它先写。那这个时候还得引文件包，那就还稍微麻烦一点。我们把序列化的包包引进来，叫 `encoding`——大家应该还有印象，`encoding` 下面有一个叫 `json` 包，对不对？

保存的时候就简单一点，就用 `io` 里面的 `ioutil`。这个包简单，一次性地把它写进去就完事了，我也不去啰嗦了。

序列化调用的是 `json` 里面有个函数叫 `Marshal`。把这个 Monster 传进去，你这个不是 `m` 吗？传进去。传进去过后，它这个 `Marshal` 完了过后，序列化过后，它是不是会返回两个数据？一个是它的 `data`，`data` 里面有另外一个就是 `err`，就是有没有失败，是不是？是这意思吧？

那这个时候我们就可以做这个工作了。它既然有错误，干脆我们把错误信息给它返回。所以说我这定一个 `error`。这样就比较简单。

```go
data, err := json.Marshal(m)
if err != nil {
	fmt.Println("marshal err =", err)
	return false
}
```

说简单一点也可以返回一个 bool 型，是吗？那也可以。返回 `error`，如果 `error` 的话用是不是空也可以判断嘛，也可以。就是 bool、error 都行。因为他如果说没有错误，它是一个 nil 嘛。那这个返回 bool 也行，那就简单了。

好，说明它是有错误的。我们可以把这个错误信息直接就给它返回回去，或者怎么样打印出来都可以，看你的一个需求。比如说，我们 `Print` 一下，就说这个序列化失败了，`Marshal err`，把这个信息我们可以把它打出来。打出来过后我们就不玩了，直接返回一个 `false`。

那如果说它不等于这个的话，我们就继续往下走了，因为还要保存到文件里面去。

那保存文件的话，我们得先要定义一个文件名。所以说我们现在给它写个序列化后的文件名，比如说 `filePath`。我就假设定到 D 盘去吧。D 盘，写个 `monster.ser`，一个日志，或者 `ser`，看你怎么取这个名字，看你的习惯。

写进去过后我们怎么写呢？我们直接用这个 `ioutil` 包里面的一个方法，它里面有什么方法就一次性地写进去了？好像叫 `WriteFile`。

这 `WriteFile` 回忆一下是怎么写的？我们来看一下：一个是数据，一个是把这个文件写到哪里去。找一下这个 `io` 下面一个 `ioutil` 包。

```go
filePath = `D:/goproject/src/gocode/15/testcase02/monster.ser`
err = ioutil.WriteFile(filePath, data, 0666)
if err != nil {
	fmt.Println("WriteFile err =", err)
	return false
}
return true
```

### 本讲提到的题目

**单元测试综合案例**

- 编写一个 `Monster` 结构体，里面有 `Name`（string）、`Age`（int）、`Skill`（string）三个字段；
- 给 `Monster` 绑定两个方法：`Store`，将 `Monster` 序列化保存在文件中；`Restore`，将序列化的 `Monster` 从文件读取，然后反序列化；
- 编写测试用例文件 `monster_test.go`，测试这两个函数能不能正确使用。

**验收标准**：一，在序列化的时候能不能正确地保存到文件里面去；二，能不能把它恢复回来，恢复后结构体的名字是否跟原先保存的那个一样。

**解析与答案**

先新建 `testcase02` 文件夹，放 `monster.go` 和 `monster_test.go`，包名统一为 `monster`。

`Store` 的思路是"先序列化、再落文件"：`json.Marshal` 拿到 `data` 和 `err`，`err != nil` 就返回 `false`；再 `ioutil.WriteFile(filePath, data, 0666)`，`err != nil` 同样返回 `false`；全部成功返回 `true`。

`Restore` 的思路是"先读回、再反序列化"：`ioutil.ReadFile(filePath)` 拿到 `data` 和 `err`；再 `json.Unmarshal(data, m)` 把结果直接写回 `m`；两处 `err` 都判空返回 `false`，全通过返回 `true`。

测试这边，`TestStore` 里先造一个实例 `Monster{Name: "红孩儿", Age: 10, Skill: "吐火"}`，调 `res := monster.Store()`，`res` 为假就 `t.Fatalf`，为真就 `t.Logf`；`TestRestore` 里先声明一个空的 `var monster Monster`，调 `res := monster.Restore()`，先判 `res`，再判 `monster.Name != "红孩儿"`——名字对不上，说明序列化文件被改过或者读错了文件，同样 `t.Fatalf`。

跑的时候两个用例的顺序是有意义的：先 `Store` 落盘，后 `Restore` 才能读到东西，所以它们写在同一个文件里从上到下执行是可以的；如果要拆开分文件测，就得注意这个先后。想只跑其中一个，就 `go test -v -run TestRestore`。

需求：要求统计 1 到 20000 的数字中，哪些是素数？素数是很经典的，好多讲课都喜欢用这个案例，当然也可以是排序、冒泡，后面我们也有很多案例。

各位，我问大家，如果你没有学 goroutine，或者说以你现有的知识结构、现有的知识储备，你怎么去完成？

**传统的分析思路**就是使用一个循环，我对 1 到 20000 的数字进行一个循环。循环的时候，我把这个数据取出来过后，让这个数从 2 到 $n-1$ 进行取模，对它进行一个取模。也就是说用它来除，就是用这个 $n$ 去模 2 到 $n-1$。如果在这个模的过程中，2 到 $n-1$ 一个都没有被整除的，那说明这个 $n$ 就是一个素数，否则就不是一个素数。

所以传统思路非常简单，就是用循环来判断。这种传统思路同学们应该都可以完成。待会儿我们也可以写个代码，但是现在先不着急写。

### 慢在哪：一个人干四个人的活

思路已经有了，同学们想一想，这只是 20000 个数字。那如果说我要求大家统计这么多的数字，如果我要求你们完成 1 到这么多个数字的判断哪些是素数，你想想这个时间会不会很长呢？肯定会很长。

你想这个素数是怎么来确定的？它是要让它自己去除以 2 到 $n-1$，这个范围其实量很大的。而且你还是这么大的数字，相当于一个双层循环，而且还是很大的一个循环。

> **结论**：传统的方法肯定是很慢的。很慢的原因，因为你把一个任务就让一个 CPU 去做。

我们一般电脑上就有 4 核、8 核、16 核的多了是，那你其实一个人去做的话，其实只让一个 CPU 在工作，挺不划算的。你看我们现在电脑上哪一个电脑不是多核的？看我这个机器这么差，我都有 4 个核。看出来了，一个 CPU，两个、三个、四个，一共 4 个。你们现在电脑稍微买得新一点一般是 8 核。

一个 CPU 去干一件事情和让 4 个 CPU 去干一件事情，那肯定不是一个档次。相当于说另外 3 个 CPU 你没有充分发挥它的威力，对吧？所以说这个肯定不划算。

### 换个思路：把大任务分给全中国人

第二个思路，就是说我们能不能用并发加并行的方式？待会儿我们再说明并发和并行有什么区别，你可以简单理解成并发。

我们能不能这样做呢？将统计的素数任务分配给多个协程去做。你可以理解成让多个程序去完成，我可以把它分解，比如说你做一部分，我做一部分。

就好像咱有一个任务，我现在要统计这么多到这么多的一个素数，我交给一个人去做，比如交给班长，班长肯定觉得很累，根本完成不了。如果我把这个任务交给全中国的人去做，13 亿人口，每个人把它除以 13 亿份，你统计一下，这个事情就相对简单了一点，对吧？最后把这个结果一汇总，完事了，因为我把这个任务分解下去了。

> **结论**：这个就是我们 goroutine 的一个非常经典的作用。它可以做一个并发和并行处理，让我们的大任务分解到多个 goroutine 去完成。如果把这个任务分配给 4 个 CPU 去做，速度至少明确告诉大家，速度至少提高 4 倍。

这个有点像现实生活中把一个大任务分配给多人去做。这个就是我们的需求，大家基本上也听懂了。

下面我们来看 goroutine 的一些基本介绍。

### 进程：程序在操作系统中的一次执行

在讲 goroutine 之前，我们先给大家介绍几个比较重要的概念。这些概念同学们听起来可能有点吃力，因为它涉及到一点点操作系统的东西，但是我尽量给大家讲解清楚一点。我们在学 goroutine 的时候，我会讲到一点操作系统的东西，但不会太多，因为我们毕竟不是讲操作系统。现在我们不是站在操作系统这个层面来讲的，更多的是在概念层面来讲的。

在学 goroutine 的时候，我们需要明确这么几个概念：第一个，进程；第二个，线程。

那么进程和线程指的是什么？

> **定义**：进程就是程序在操作系统中的一次执行过程。这句话说得还是比较经典的。

打个比方，我们前面写了很多的程序，比如说刚才你们的 `.exe` 文件，比如说前面我们讲的客户关系管理系统，那么你整完了过后，其实它是一个 `.exe` 的文件。这个并不能叫程序，你可以叫做一个文件，源代码你也叫文件，也可以把这个叫做我们的源码。

进程指的是什么呢？进程是我们去运行了这个东西，我们运行它，让它在内存里面，让操作系统开始执行了，我们把这个叫做一个进程。它是系统进行资源分配和调度的基本单位。

最直接的，你们可以看到，在任务管理器里边打开它，这里我们都可以叫做一个一个的进程。这里的进程很多，但有些进程是后台进程，有些进程是前台，就是说它有界面。

比如 Word 文档，我们打开了这个 Word 文档，其实一双击，它就会以一个进程的形式来执行。包括你们用得最多的迅雷，比如说我起个迅雷，你们就可以看到在这里就会抓住一个进程。迅雷我是不敢起的，因为迅雷太猛了，上来后吃的资源太狠了，它是重量级的。我们就举一个最简单的。

现在 `n` 打头的没有记事本，我双击一下打开一个，你们就会看到多了一个东西。我把这个定位到这儿，然后双击一个，你们会看到多了一个进程的名字，就是 `Notepad`。这个就是刚才我们双击 Notepad 的时候产生的。那如果我关闭它，一旦我结束这个进程，那么这个界面也会被关闭。很简单的，这就叫一个进程，就是一个程序执行就叫一个进程。这个进程系统就会分配资源，它是一个基本调度单位。

> **追问**：老师，我一个程序能不能起多个进程呢？
>
> 这就要看这个程序允不允许和操作系统允不允许。有些是可以的。我记得以前最早的时候暴风影音，现在暴风影音你打开一个再双击，它就会把原先打开的给你调过来。但是最早的时候，我记得好像暴风影音可以起好多个。以前我们有个学生在上大学，那小伙子看电视剧太猛了，同时起三个，我都不知道他怎么看电视剧的，三部电影同时看。我说你这有病吧。他说时间太紧了。时间太紧了就同时看三部电影，就是那种人，很怪。以前我们上大学的时候最流行的是到 FTP 国外资源网，那上面好多好多外国电影，高清的，都特别好看。

### 线程：进程的一个执行实例

那么有一个问题，什么是线程呢？线程也很重要。

> **定义**：线程是进程的一个执行实例，是程序执行的最小单位，是比进程更小的、能独立的基本单位。

这有点不好理解，说进程不都已经跑起来了，怎么还有一个线程呢？最经典、最好的理解方式还是举例子。同学们都用过迅雷，没有用过迅雷的应该比较少。当我们打开一个迅雷的时候，这个时候你双击迅雷，其实它就会起一个进程。但是在这个进程里面，一个迅雷可以同时下载多个文件，这个大家都是知道的。比如我下载封神英雄榜，一共下载这么多，你们可以看到，每下载的一个文件就可以相当于是个线程。

这个线程也是独立的，它相当于说一个进程下面可以有很多很多的线程。

> **结论**：一个进程可以创建和销毁多个线程。同一个进程中的多个线程可以并发执行。

注意我说的是并发，并没有写并行。待会儿我再讲并发和并行的区别。并发执行就是说，从效果上来说好像是我们这儿有五个文件同时下载，但实际上从一个微观的角度来看，其实它只是时间片很短，来回切换。在一个微观的角度来看，一个时间点只有一个文件在下载。如果你不是并行的情况下，它就是这样子的。

那么这个是我们所说的一个概念。还有一点，**一个程序至少有一个进程，一个进程至少有一个线程**。

### 程序、进程、线程的层次关系

如果我画一个图的话，说有一个程序打开了，比如说这有一个迅雷 `.exe`，我们把它叫做是一个程序，或者叫做一个文件、一个程序文件。这时我们运行它，当运行的时候它就起一个进程。一旦运行的话，它就会把它调入到我们内存里面去执行。这个时候，这个程序我们就管它叫做一个具体的进程了。

```text
            thunder.exe
          程序 / 程序文件
                │
                │  双击运行 → 调入内存开始执行
                ▼
   ┌────────────────────────────────────────┐
   │  进程：Thunder                          │
   │  系统进行资源分配和调度的基本单位         │
   │  任务管理器里的一条记录                  │
   └────────────────────────────────────────┘
                │ 一个进程至少有一个线程
      ┌─────────┼─────────┼─────────┬─────────┐
      ▼         ▼         ▼         ▼         ▼
   线程1     线程2     线程3     线程4     线程5
  下载封神   下载 A    下载 B    下载 C    下载 D
  英雄榜
                                            ┌────────┐
                                            │ 排队中 │
                                            └────────┘
```

这个进程叫什么呢？一般来讲会以它的文件名命名，比如像迅雷可能类似于 `Thunder` 等等这样类似一个名字。那么这一个进程里面它可以起很多线程，这是没问题的。先把这个关系搞清楚，一个进程里面可以起多个线程，进程里面可以对应很多线程。这样子大家可能就变得比较清楚了。这是线程 1，这个地方是线程 2，以此类推。

比如刚才你们看的这个图，就相当于说我这一个进程里面有五个正在执行的，另外在排队。到底起几个，这个要看程序本身。有些程序是可以让你起很多，有些程序可能就阻止你了，说最多下载几个。好像迅雷是可以设置的，迅雷同时下载几个有个设置，可以设置 5 还是 10。

> **结论**：程序或者代码，双击运行成一个进程，进程里面可以有多个线程。

> **提示**：这里为什么没给它对齐，就是因为有些程序是可以同时起多个进程的，就是我双击再双击一次它又起一个，也有这样子的程序，现在就看操作系统支不支持这种。

基本介绍咱们就说到这儿。下面接着看并发和并行。

### 并发：一颗 CPU 上的来回切换

可以这样理解：什么叫做并发？什么叫做并行？听其名而知其意，**并发是指多线程程序在单核上运行**，我们叫做并发。

你的 CPU 假设只有一颗，或者说你的程序运行作用在一颗 CPU，我们叫做并发。简单的来讲，这个 CPU 它切换的时间单位是以零点零几秒或者叫几毫秒来切换的。对我们人来说，我们的反应根本就反应不过来，所以对我们来说好像是同时在跑。实际上在一个时间点上，它只是在执行一个任务。

就好像你打开一个网页，假设你是单核的，打开了两个视频，你感觉两个视频在同时播放，其实它在一个时间点上实际上只是在执行一个任务上面而已。我说的是单核，如果你是多核那就是另外一回事。所以单核我们把它叫并发，在这个概念叫并发。

> **提示**：当然这个并发的概念跟我们外部的并发不是同一个含义。外部并发是指比如我这里有 CPU，一下子有一万个请求过来，这个时候可能是同时的。我们说的是 goroutine、Go 程序的并发。

那我画个图给大家描述一下。假设韩老师的电脑上假设有一颗 CPU，`CPU1`，这个 CPU 上面我跑了有三四个任务，这是任务 1，这是任务 2，这是任务 3。

```text
并发：任务都挤在一颗 CPU 上，靠切换伪装成同时
        ┌────────────── CPU1 ──────────────┐
  时刻1 │  task01      │                 │
  时刻2 │  task02      │                 │
  时刻3 │  task03      │                 │
  时刻4 │  task01      │                 │
  时刻5 │  task02      │                 │
        └──────────────────────────────────┘
        切换以毫秒为单位 → 人眼以为同时在跑
```

也就是说我这一个任务是同时跑在这一颗 CPU 的。大家想一想，如果是这种情况，显然在同一个时间点上来说，一个 CPU 不可能在微观世界上既执行 01 又执行 02，这是不可能的。所以这种我们叫做并发。

> **结论**：并发的特点是——第一是多个任务作用在一个 CPU 上；第二是从微观的角度看，在某一个时间点、那一瞬间，其实只有一个任务在执行。当然从宏观上看，从人的角度来看感觉是在同时执行。

### 并行：把任务分给多颗 CPU

那并行是什么意思呢？并行是这个意思：它能够把这三个任务分配到三颗 CPU 上去做。

这就是为什么 Go 语言要这么做，因为现在传统的编程语言，即使有多个任务也是分配在一个 CPU 的，所以有时候多核不能发挥威力。那么 Go 语言能够把所谓的并发转成并行，它这块可以做一个改进。

> **结论**：Go 语言支持并行，是 Go 语言重大的一个改进。

它怎么做呢？我还是这么一个任务，但是情况发生了变化。因为一个 CPU 的效率太低了，如果假设有三个 CPU，另外两个 CPU 在睡觉，很不划算。那么第一个 CPU 就做这一件事情。然后再来两个 CPU，这儿一个 CPU 2，直接让 CPU 2 去做 `task02`。假设还有一颗 CPU 3，当然 CPU 一般不会是奇数，一般来说是 4、8、16、32 这样子递增，很少说是三个、五个，这里只是示意一下。让三号 CPU 专门干这件事情，作用在 `task03` 上去执行。

```text
并行：任务分给多颗 CPU，真同时
        ┌────────┐    ┌────────┐    ┌────────┐
        │  CPU1  │    │  CPU2  │    │  CPU3  │
        │ task01 │    │ task02 │    │ task03 │
        └────────┘    └────────┘    └────────┘
                 同时刻，三件事真的在一起跑
```

并行的特点是：**多个任务作用在多个 CPU 上**。从微观的角度看，在同一个时间点有多个任务在同时执行。注意是同时，不是在切换，它就是真的在同时执行。这样看来，我们并行的速度肯定要比并发快。

### 把两者放在一起看

并发，因为是在一个 CPU，比如有 10 个线程，每个线程执行 10 毫秒，进行轮询操作。其实它是轮询操作，但是 10 毫秒太快了，给我们人的感觉好像都在同时执行。从人的角度来看好像 10 个线程都在运行，但是从微观上看，某一个时间点其实只有一个线程在执行，这个叫并发。

反过来，并行因为是在多个 CPU 上，比如有 10 个 CPU，有 10 个线程，每个线程执行 10 毫秒，在各自不同的 CPU 上运行。从人的角度看 10 个线程都在运行，从微观上看也是 10 个。这就是并发和并行。

| | 并发 | 并行 |
| --- | --- | --- |
| 任务落在几个 CPU 上 | 多个任务挤一个 CPU | 多个任务分多个 CPU |
| 微观（某一瞬间） | 只有一个任务在执行 | 多个任务真正同时执行 |
| 宏观（人的感觉） | 好像都在同时执行 | 确实都在同时执行 |
| 机制 | 时间片轮询、来回切换 | 各自独立的 CPU 同时跑 |
| 速度 | 受单核限制 | 明显更快 |
