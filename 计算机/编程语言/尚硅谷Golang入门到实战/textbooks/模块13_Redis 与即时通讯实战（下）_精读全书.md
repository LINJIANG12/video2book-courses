## 让登录不再写死：从 Redis 里认出这个用户
> 对应块：BLK127 | 覆盖分集：P326-P328 | 块标题（分集名）：《324_尚硅谷_海量用户通讯系统-Redis用户》

上午我们完成了这样一个功能：把服务器和客户端的结构做了一个合理的改进，让我们的程序可以支持更加复杂的业务逻辑。

下面来看下一个功能——**Go 语言和 Redis 的一个互通**。因为前面我们登录是直接把用户 ID 和密码写死的，这个实际上在开发中也是不太可能的。所以我们来做这样一个工作，就是在 Redis 里面来验证用户 ID 和密码是否正确。

针对这个步骤，代码量也会比较大。怎么来做呢？**我们把它分成这么几个步骤，一步一步地来做，思路会比较清晰一点。**

- **第一步**，先在 Redis 手动地添加测试用户。也就是说，我们先添加一个在数据库里边存在的用户，然后我们去登录成功；
- **第二步**，登录成功完了过后，我们再去完成一个真实的注册。

这里边把这个打通了的话，我们后台这一大块的内容又通了。

### 选一个数据结构：为什么是 hash

目前来说，我们这些程序，包括 `UserProcess`、还有 `smsProcess`，都没有跟数据库发生交互。现在我们要增加数据库这一块。这是一个数据库，当然可以是 MySQL，也可以是我们的 Redis——**我们现在用我们学过的 Redis 数据库来做这个事情**。

大家想一想，我们现在做一个简单的分析。现在我们先做第一步，先直接把一个用户添加到 Redis 里面去。那**我们的用户结构到时候做成什么结构比较合理呢？大家可以动一动脑筋。**

前面我们学 Redis 的时候，学了它的数据类型有这么几种：`string`、`hash`，还有 `set` 就集合，还有 `list`，主要就有这么几种。那么这个时候，**我们要挑一种相对来说比较高效，同时它的 key 不能重复的这样一种数据结构来存放。**

这个时候我想，**咱们队列肯定不太合适**——队列直接往里面扔东西，看不出来有什么效果。**什么比较合理呢？我们选择 hash 比较合理。**

hash 到时候的结构大概是这样子：我们写一个 `users`，这个是 hash 的一个名称。这里边由它延伸出去有一堆 key 和 value。在这个用户里面，我们认为有这么一些信息，它有 key 和 value 的这种键值对。

```text
users （hash）
 ├─ "100" ──▶ "{\"userId\":100,\"userPwd\":\"123456\",\"userName\":\"Scott\"}"
 └─ "200" ──▶ "{\"userId\":200,\"userPwd\":\"abc123\",\"userName\":\"Kai\"}"
```

到时候我们要去看 Redis 里面有没有这个用户呢，我们只需要通过 `users` 这个 hash 的名称，找到它的这一个 key——当然这也叫字段，可以理解成字段，就是 `100`——这个 100 里面有没有对应这个值。**如果有的话，说明这个用户是存在的；如果没有，就说明不存在。**我们在添加的时候也可以这么去处理，就是我们得到一个用户过后，把它序列化成一个用户信息，然后再去做。

所以到时候在这个地方我们要加一层东西——**加一层 model 层**。这也是一种设计的思路。在这个 model 层里面，model 这个地方相当于是我们的数据。

model 层里面最重要的就是我们的数据。到时候我们会做这么几个东西：

**第一个，我们要添加一个 User 结构体，就加一个文件 `user.go`。**

这个 `user.go` 里面会定义一个 User 结构体。大家到时候想想，这个结构体里面应该包含哪些字段？大家可以动脑筋。**至少用户的 ID、用户的密码、用户的名字要有**——当然还可以加很多用户的性别、电子邮箱、包括他对应的有哪些好友等等都可以。

但是现在最基本的、迫切需要的肯定 ID、密码和用户名，这是最基本的。后面可以加很多东西，可以扩展，这个扩展性就会很好。

里边我们会编写对 User 对象进行操作的各种方法：**比如说增删改查、登录、获取等等都可以**，包括把分页加到这里面的。我们现在没有分页，就不去考虑了。反正这里面有很多的操作，主要就是对其实施操作。包括我们的获取用户、注册，都可以写到这里面去。

**第三个，我们还要写一个文件，叫 `error.go`。**

因为我们将来登录也好，注册也好，会有各种各样的错误。这个错误我们现在没有自定义错误也不行，这个错误种类将来会比较多，所以我们还要去编写一些错误的各种信息。这个地方是一个错误信息，到时候在这里面自定义一些关于用户的错误。

#### Dao 与 utils 的分工

大家可以看到，到时候我们会这么去使用：如果我们的 `UserProcess` 要跟它进行数据的交互，他们之间的一个数据交互——听我讲，**客户端和服务器端的交互，我们使用 utils，因为这是读写的操作，我们用这个工具。**

当我们的 `UserProcess` 或者是 `smsProcess` 要去对 Redis 进行操作的时候，我们会去使用哪一个呢？**我们会去使用 Dao，用这个 Dao 去完成对数据库的一个操作。**

也就是说，后边跟数据库进行交互的动作主要是放它来完成。大家看这个逻辑：**跟后台操作我们用的是 `UserDao`，跟前台操作我们用的是 utils 里面的方法。**

### 连接池：谁在维护

那除此之外，我们还要做一些工作。还有哪个工作必须要作呢？同学们想，**我们既然要完成对 Redis 的操作，那么这个时候我们就要去连接 Redis。**

连接 Redis 我们有两个方法：第一个就是**当操作一次，我们就连接一次**，对不对？但显然，这个效率会比较低下。

那还有一种什么思路呢？**我们还有一种思路就是可以事先初始化一些 Redis 的连接池。当我们操作的时候，我们就让 UserDao 去连接池里面取一个连接，操作完了再放回回去，效率会大大提升。**

因此我们这边还要建一个东西，就是我们可爱的连接池。

```text
┌──────────────── 服务器端 ────────────────┐        ┌──────────┐
│                                          │        │          │
│  main ──► process ──► model.UserDao      │        │  Redis   │
│                        │                 │        │          │
│                        ▼ 取连接          │        │          │
│                  ┌───────────┐           │        │          │
│                  │ 连接池    │  ──放回──► │        │          │
│                  └───────────┘           │        │          │
│                                          │        │          │
└──────────────────────────────────────────┘        └──────────┘
```

**首先大家要知道连接池是谁在维护？**显然不可能是 Redis 数据库在维护，而是**我们服务器在维护**。所以这个连接池如果要在画的话，它也应该画在服务器这个内部。这个大家能理解吗？因为你这个 Redis 是由谁来创建的？当然就是由哪个程序来维护的，对不对？

**你别说 Redis 它在维护，这就不可理了。**

但这个维护的东西最好是画在这个 model 和 Redis 之间更合理，但是它还是属于服务器的一个范畴。它的逻辑会这样子：我往这边再挪一挪，因为这个空间不够我使用了。我们可以把服务器这块灰色的底线往后面挪动一下。

**我们原先最普通的方法就是，我如果要去操作 Redis，我就这样去操作。这种操作效率很低下。**我们实际上在写代码的时候会这么去操作：这个线不要了，效率太低。

我先怎么办呢？**我先让这个连接池跟我们的数据库 Redis 已然建立好连接的关系。**然后我这个 `UserDao` 要去操作 Redis 的时候，我就从它这里取出连接。我从它取出一个连接，然后从这个连接再去操作它。**操作完了过后，我把这个连接使用完了，我再把它放回连接池就可以了。**它是这么一个逻辑。

好了，代码我们大致就分析完了。既然是连接池，我肯定会写一个文件，我用一个文件来维护叫 `redis.go`。

### 目标：Redis 里有就登录成功，没有就退出

我们来开始写这个东西。下面我们完成第二步：**如果输入的用户名和密码正确，在 Redis 中，就是你输入的用户名和密码在 Redis 中存在就登录成功，否则就退出系统，并给出相应的提示信息。**

一种是用户不存在或者密码错误，还有一种就是再给它提示你可以重新注册再登录。

登录的时候有可能是因为你的用户不存在，也有可能是你的密码不对，这个你可以分成两种形式提示。第一种是用户不存在，你可以这样写"用户不存在，你可以重新注册再登录"；还有一种可能性就是你的密码不正确，比如说"你的密码不正确"。

#### 为什么现在还没有 service 层

我们把它的示意分析放到这儿。提示信息这儿就完了，然后我们代码来实现它一下。

现在的程序结构是这样子的：**新增三个文件，然后 Redis 在这里也是生成。**

先把 model 这一块的三个文件写完，然后再去写 Redis。**这个 Redis 它是属于一种初始化的信息，所以这个文件可以直接放在 main 这个文件夹下面。**这个位置可以根据自己的实际需要放在相应的位置。

第一个，我们新增加一个文件叫 `user.go`；第二个文件是用来自定义错误的，`error.go`；第三个文件是专门用来操作 user 这一个结构体的，`userDao.go`。

#### tag 不是装饰品

先写 `user.go`：

```go
package model

// 定义一个用户的结构体
type User struct {
    // 确定字段信息
    UserId   int    `json:"userId"`
    UserPwd  string `json:"userPwd"`
    UserName string `json:"userName"`
}
```

**如果我这样写一个 User 结构体，问题就很严重了。**为什么这么说呢？因为将来这个 User 一定会被反序列化或者序列化操作，而我们现在往这里面添加的序列化的 User，**它的名字是小写的，前面的 key 是小写的，因此你在反序列化的时候根本就不会成功。因此必须把这个 tag 写进去。**

为了能够序列化和反序列化成功，**我们必须保证用户信息的字符串，也就是 JSON 串的 key，和我们结构体的字段对应的 tag，也就是 struct 里面的 tag 的名字保持一致，否则就一定会失败。**

那这里是不是少了一层？有同学说以前学 MVC 的时候听说都有一个 service 层，也就是服务层。服务层一般都会有的，对一些比较复杂的项目都会有一个 service 层。

**但是因为目前这个项目比较简单，所以 service 层就没有用。理论上一个标准的 MVC 中间还有一层。但是我们这个项目太小了，还谈不上。**

标准的一个结构中，控制层一般会先调 service 层，service 层再去调 model 层。那现在为什么没有写 service？**我可以留一个接口在这儿，但是我先暂时不用，因为现在的业务功能很清晰简单。**

什么时候会有 service 层呢？**当业务很复杂，service 之间会相互调用，或者一个 service 的业务会调用到多个 DAO 来完成的时候，才会有 service 层。简单的情况下一个 DAO 就可以处理完了。**

以后业务复杂的时候可以加一层，现在暂时用不上就先不写。我们在 server 这边再加一个 package 叫 `service`，但里面现在暂时是空的。

#### 自定义错误先备好

我们接着写，把 `user.go` 搞定之后，再把 `error.go` 搞定。将来我们在登录或者注册的时候有各种错误。比如用户不存在是一种错误，用户已经存在也是一种错误——你在注册的时候指定的 ID 已经被占用了，也是一种错误，就把"用户 ID 已存在"返回回去。

```go
package model

import "errors"

// 根据业务逻辑的需要，自定义一些错误
var (
    ERROR_USER_NOT_EXISTS = errors.New("用户不存在")
    ERROR_USER_EXISTS     = errors.New("用户已经存在")
    ERROR_USER_PWD        = errors.New("密码不正确")
)
```

定义这么几个：第一个是用户不存在；第二个是用户已存在，注册的时候如果 ID 已经存在了就返回用户已存在；还有一种错误是输入的密码不正确。密码，`pwd`，简写。

我这样做，我怎么做呢？**我做一个东西：`pool`。它有一个字段叫 pool。这个 pool 的类型是什么呢？是 redis 这个包里面的 Pool。**

#### GetUserById：先按 ID 把人捞出来

### 接下来：登录时返回在线用户列表

前面我们已经完成了一个到服务器注册的功能。现在我们完成这么一个功能，叫**完成登录时能返回当前在线的用户**。

甚至我还可以做得更好一点，我可以返回当前在线用户的各种状态。因为一个用户的状态可能有很多种，他可能是发呆，也可能是吃饭，也可能是忙碌，也可能是在线等等。那么这些如果让大家都能实现，你现在都可以搞定。

我把这个功能分成两步，先谈思路。

#### 为什么这一节特别烧脑

这里面的问题是这样的：当一个用户登录以后，比如说这边有一个张三，张三通过这个客户端登录到我们这个服务器，登录到服务器以后他应该怎么办呢？

今天讲的内容看起来功能说起来很简单，但实际上特别烧脑。知道什么叫烧脑吗？**烧脑的意思就是说，你突然感觉到你的 CPU 内存不够用了。因为你写代码你会突然，你原先是单机版的，现在你变成多核了。**

当我一点，我说这样一写，你马上"诶，这样写还挺对的"，但是我不说你就很难想得到那儿去，明白我意思吧？所以这个地方是烧脑，但是很有意思的一节课。写完了过后，你会突然感觉到这个结果是未知的；你感觉突然一下整出来以后你会感觉到很爽，但是一旦整不出来，你会调好几天都调不出来。

#### 核心不是信息，是连接

首先我认为在服务器这边，我们应该有一个专门来维护当前在线用户的结构体，我姑且把它叫做 `userMgr.go`。它要完成这么几个功能：维护一个用户在线列表。

你要维护一个用户在线列表，具体来说你得有一个数据结构。用一个什么样的数据结构比较合理呢？显然用 map 或者是切片都可以，但是用 map 相对来说比较容易一点。所以待会儿我会建一个这样子的东西，叫 `onlineUsers`。

那这个 `onlineUsers` 里面我们认为它是长什么样子呢？这里面的问题就是说，肯定这个 map 它的 key 应该是个 int，这个 int 就表示这个用户的 ID 号。

那第二个最为关键的问题是什么？**你维护这个在线列表的目的是什么？**

你的目的可能是希望通过这个在线列表想一个办法，能够让这个服务器跟各个在线用户进行一个通讯，是这意思吧？**你要通讯，你怎么做？**

> **结论**：你维护在线列表的目的不是维护用户的 ID 和信息本身——数据库里有信息你还维护这个干啥？**最主要是说你要想办法维护你这个服务器要跟各个客户端的连接。关键就是跟连接要抓住。**

因为如果你把这个连接忘掉了，那我告诉你，你啥事都干不了。你光有他的信息有什么用呢？因为你只有这个连接了过后，你就可以做任何事情——你既可以群发，也可以点对点私聊，你甚至可以指定发一个图片、发一个视频、发一个声音都可以了。

所以这里面最关键就是说，它的 map 里面这个值用什么比较合理呢？显然，同学们要动脑筋了。

#### 绕一圈回到 UserProcess 的 Conn

寻寻觅觅，我们发现这里面一定要维护连接，而这个连接在哪里有呢？我们又一动脑筋，发现原来 `UserProcess` 是有的。

那这个时候你就打开你的 VS Code，你看一下当时我们这一个 `UserProcess` 是一个什么样的玩意儿。打开我们在 server 这一端的 process 这一层，里面有个 `userProcess.go`，而这个 `UserProcess` 里面大家可以清楚地发现，**它本身就维护了一个可爱的 `Conn`**。

那差一个了。你这个时候这个 `UserProcess` 有了这个字段过后，那我就想办法了。如果说我在这头再维护它的一个指针就好，它本身是一个结构体，那我这样子做，我就维护一个 `*UserProcess`。

那将来我这个 map 里面长的是什么样子呢？注意听，这个是关键点：**它有用户 ID，它对应一个 key，这个 key 值就是我们的一组 `UserProcess` 的一个指针**。说白了，就是你的这个 user 说白了就是一个 `UserProcess`。

比如说有一个客户是 100 号，100 号这个人对应一个 key，这个 key 值就是 `*UserProcess`。这个 `UserProcess` 是第几号呢？是 100 号的。那当然将来还有可能是有 200 号的，200 号的它也维护起来，当然还有 300 号的、400 号的，很多，这个我就不去一个一个的去做展示了。

```text
        onlineUsers  map[int]*UserProcess
        ┌────────┬──────────────────────────┐
        │  key   │  value（指针）            │
        ├────────┼──────────────────────────┤
        │  100   │ ──▶ UserProcess{ Conn, … }│
        │  200   │ ──▶ UserProcess{ Conn, … }│
        │  300   │ ──▶ UserProcess{ Conn, … }│
        │  400   │ ──▶ UserProcess{ Conn, … }│
        └────────┴──────────────────────────┘
            ▲
            │  key = 用户 ID（int）
            └──▶ value 抓的是 Conn，不是信息
```

读图说明：value 用指针而不是拷贝结构体，是因为要拿到 `UserProcess` 里那个 `Conn`；有了 `Conn` 服务器才既能给这一个客户端点对点私聊，也能群发消息。

#### 第一步：建一个 userMgr，做增删改查

在服务器端维护一个 `onlineUsers`，它里面维护的信息就是一个 map。维护这个 map 的价值在什么地方呢？因为我们在维护这个 map 的时候，`UserProcess` 里面有一个特别重要的字段就是那个连接。就是我们希望它维护自己的一个连接。但这个连接是独立的，各个客户端的连接它是不一样的，所以说这才是我们的一个核心点。

有这个了，维护它。那么这个时候我就会去创建一个新的文件，我会创建一个新文件吧，这个文件我就把它叫做 `userMgr.go`。这个文件里面维护了它的一个结构体，它要完成什么呢？就是对这个 user map 实际上就是对它的一个增删改查。因为有可能要离线，离线你还得把它干掉。

也就是说，你紧密维护这个在线列表，**增、删、改、查全部都要有**。一旦有了这个 `onlineUsers` 这个 map 过后，你要干的事情就很轻松了。

这个文件我就把它放在处理层，就是我们的控制层。

#### 第二步：在 LoginResMes 里加一个切片

第一步是维护这个 map。但是你光有这个增删改查没有用，**你得找准这个时机**，什么时候增加、什么时候删除、什么时候改。这是第一个。

第二个问题：目前当一个用户登录以后，我们返回的这个 message 它的字段是这样的：`LoginResMes`——只有个 code，只有个 error，没有用。

那么这个时候我们希望在登录的时候，返回的这个结构体里面**再增加一个东西**，就是当前在线用户的 ID 的一个切片。你有多少个，我给你遍历起来返回给你，你解析它就可以看到了。也就是说他一登录的时候，我把这个也返回。

所以在 `LoginResMes` 这个结构体中增加一个字段：


这个切片就会把在线用户的用户 ID 返回去。有了这两个思路以后，我们就可以来动手写一写了。

### 全局唯一的那个 UserMgr

好，`package`——这边这个包是 `process`，把我们都要用的统一的包，`process`。

然后引入必要的一些包。因为它是个结构体，所以说我们这直接先去定义或者声明一下这个结构体，就 `type UserMgr`，然后是 `struct`。

```go
type UserMgr struct {

}
```

然后我们把它直接声明成一个全局变量。注意，这里有两个原因：**因为这个 User Manager 在整个服务器里面有且只有一个；第二个就是因为在很多地方都会使用到。** 因此我们将其实例定义为一个全局变量。

那既然是个全局变量，这个很 easy，`var` 写一个全局的 `userMgr`，它的类型就是它——当然是个指针类型的：

```go
var userMgr *UserMgr
```

然后我们完成一个初始化的工作，对这个 User Manager 的一个初始化：

```go
func init() {

```

因为它是指针嘛，所以说咱们来个 `&` 符号。里面它重要的一个字段就是 `onlineUsers`，我们给它赋一个值、初始化一下 `make`，上来先给它 1024 个这样的一个大小。

### 增删改查四个动作

#### 增：AddOnlineUser

添加给完成对这个 `onlineUsers` 的添加：

```go
func (this *UserMgr) AddOnlineUser(up *UserProcess) {
	this.onlineUsers[up.UserId] = up
}
```

那么你这个 onlineUser 你给我一个什么东西？显然，同学们，我们要维护的实际上就是这个 `UserProcess` 的一个指针，所以说你在这就直接给我传一个 `UserProcess` 指针就可以了。

> **注意**：因为这个 `UserProcess` 里面它有这个连接，现在为了好管理，我们也应该再加一个字段。什么字段？**表明这一个连接到底是属于哪个用户的连接。你不加的话到时候很麻烦。**

所以这里面我们需要增加一个字段，增加一个什么字段呢？增加一个字段表示该连接是哪个用户的。那这个很 easy：

```go
type UserProcess struct {
	UserId int
	Conn   net.Conn
}
```

有了它过后，这地方就轻松了：来个指针叫 `up`，简写成 `up`。我给你这么一个东西，我怎么加进去呢？非常简单。其实这个添加同时也是修改——如果你要改变的话也是一样的。就是说我们找到这个 `this.onlineUsers`，然后里边是这个 `up` 带进来的那个 `UserId`，再把 `up` 给它。

#### 删：DelOnlineUser

假如有一个用户他离线了，他有可能注销了、退出了嘛，那也有可能是删除这个功能。删除这个功能也 very 的 easy，把它复制到这边来，把这个名字改成 `DelOnlineUser`，他走了，delete。

那这个时候你就给我传一个这个用户的 ID 就可以了，就是你要把哪个用户干掉啊，你得告诉我：

```go
func (this *UserMgr) DelOnlineUser(userId int) {

}
```

从一个 map 里边把一个 key-value 删掉，有一个专门的内置函数叫 `delete`。前面是它对应的 map，后面是它的值。

#### 查一：GetAllOnlineUser

查询里面最关键的一个任务是什么？因为待会儿我们要去返回，就是当一个用户登录以后，我们要去返回当前在线用户有哪些，所以说它必须有一个 `GetAllOnlineUsers` 这么一个方法。我要把所有这个在线的用户给返回去。

```go
func (this *UserMgr) GetAllOnlineUser() map[int]*UserProcess {
```

你要用什么你自己去用，你要什么你直接拿去玩就行了。

#### 查二：GetOnlineUserById

还有一个最重要的功能，我觉得还应该提供一个方法：给你传进的一个 ID，你给它返回一个对应的这个 map 的值。

因为有时候你可能是要针对点对点的聊天。比如说将来你张三 A 客户端想给 B 客户端说句话，那肯定 A 客户端说"我要跟 B 客户端说"，那么服务器这边它会从这个 map 里边拿出来 B 客户端它对应的这个 `UserProcess`，然后给它传东西过去，是不是？

所以我们应该再提供一个根据 ID 返回这一个对应的 `UserProcess` 的功能。

那这个也很有意思，咱们写这么一个东西：就是根据 ID 返回一个 `UserProcess`，返回这个对应的值。Very 简单：

```go
func (this *UserMgr) GetOnlineUserById(userId int) (up *UserProcess, err error) {
	up, ok := this.onlineUsers[userId]
	if !ok {
		err = fmt.Errorf("用户 id=%d 不存在", userId)
		return
	}
	return
}
```

既然是 by ID，你就给我传个 ID 过来嘛。那我给你返回个什么东西呢？这个时候显然我们主要返回的还是这个东西——因为这个东西是核心是关键，你想去服务器端找哪个人肯定是靠它嘛。

> **易错点**：这个地方有**两个**东西返回，一个是 `up`，还有一个是 `err`，因为可能有错误。如果有错误，就是找不到，也要给它提示一个信息。

怎么去找呢？我们在前面学过 map，如何从 map 中取出一个值。还是带检测的，因为有可能找不到这个嘛。应该是这样写的：`this.onlineUsers[userId]`，第一个会返回这个 `up`，第二个返回一个 `ok`。

如果这个 `ok` 如果为假，我们就返回一个错误信息，就说找不到这个人就行了。如果 `ok` 为假，取反就为真——那代表你要找的这个用户当前是不在线的。为什么说不在线呢？因为我都找不到嘛。给它定义一个，`fmt.Errorf`，这地方是可以把一个格式化的 error 给它返回去。那么这时候 `up` 是什么？肯定是个空。

否则的话那就是正确了。正确的话直接 return，就找到了嘛。找到你这地方是 `ok` 也是真的，`up` 也有了，就返回它。因为这是用命名的，`err` 这地方有，如果你这没有错误，`err` 就是一个空。

#### 改：本质就是 add

然后呢还差一个修改。修改其实本质就是 add——大家都知道，map 它是这样子的，它的 key 是唯一的。如果说你给它传进去一个相同的 key，它相当于去替换了原有的那一个值。

### 什么时候往里加：登录成功的那一刻

同学们可以看到，我们现在已经有了它了。既然有了它过后，而且初始化的工作也做完了，下面我们应该做什么事呢？

因为目前我们现在还要完成的功能是当他登录以后，我们就把这个东西放进去。所以说你在事先这个用户列表肯定是有东西的才行，对吧？**你事先是有东西的，那什么时候往里面添加呢？**

非常简单：**就是当一个用户登录以后，登录成功以后，我们就把这个用户的 ID 还有它的 process 给它放进去就完事了。**

找到我们登录成功的那个位置。说现在你要找位置了，这有一点小难度。那么我们是在哪里表示这个用户登录成功呢？寻寻觅觅，我们发现在登录的那个方法里面，在这。我们在这表示这个用户是登录成功了，那既然你登录成功了，我们就应该把这个用户的 map 放进去。

```text
时刻      发生什么                        谁看到的在线列表
────────────────────────────────────────────────────────
t1       100 号登录成功，服务端 Add       100 的客户端：打印 [100]
```

## 在线用户列表：为什么让每个客户端自己维护一份 map
> 对应块：BLK132 | 覆盖分集：P335-P337 | 块标题（分集名）：《333_尚硅谷_海量用户通讯系统-显示在线用户列》

### 不显示自己：一个 continue 就够了

刚才那块还差一点尾巴。

大家可以看到目前有一个问题：**这个人他登录过后，他看到当前在线用户，按理说他自己是不用显示出来的**——一般来讲自己不用显示。当然 QQ 是不是把自己也显示出来了？那就这样子吧，无所谓了。

**如果你们想不显示自己，这个逻辑怎么加？** 非常简单：**如果这个 `v` 刚刚等于你自己的 ID，咱们就 `continue`。**

你自己 ID 是多少？**你在登录的时候，自己是有这个 ID 的**——这是你登录的时候你自己输的 ID。所以你只要判断它等于它，就 `continue`，不走了。

> 我主要是想给大家说一下，这个 `continue` 在这儿用得特别有意思、很到位。如果它等于这个我就不做了，这样子比较 OK。**你用别的思路就没有这么漂亮，对不对？**

所以写网络程序的、像写网络游戏的，一般来讲**他的工资相对来说，尤其是写底层的、写数据通道那一层的，一般会高一点，一般会比写界面的工资高。** 现在普遍情况就是做后台的，尤其是做数据通道这一块的，薪水一般比较高。**你看我这里涉及的东西很多，而且我还没涉及到优化，我还没涉及到压缩**——因为你现在数据还没有经过压缩来处理，如果要涉及到压缩还会节省你的带宽。那这里面的东西就多了，**算法、优化、压缩、安全全部都在底层。**

### 思路：三条路，两条太贵

现在到了一个比较关键、也是相对来说比较麻烦的地方——看这个代码，明显感觉到比刚才要多一点。

我们要完成这样一个情况：**当一个新的用户上线后，其他已经登录的用户也能够获取到最新的在线用户列表。** 什么意思呢？**就是当一个新的用户上线以后，其他的登录用户也知道你上线了，要去通知对方他上线了。**

打个比方：**A 上线了，他就要告诉 B 说"我来了"；B 上线了之后，也要告诉 A。反过来也是一样。** 假设 A 上线了，下面有十个人，比如客户端 C、D、E、F，**那你就要通知其他人"我来了"，并且列表要有所显示。**

就这么一个小小的功能，但想一想怎么做？

每个人的方案可能都不一样，**但是哪个方案更优秀、更好一点，咱们就要动脑筋了。**

#### 思路一：整个 map 推给所有人

这是大家最容易想到的：**当有一个用户上线后，服务器就马上把维护的 `onlineUsers` 这个 map 整体推送。** 比如张三上线了，就遍历一下现在的 map，把这个包发下去。

**假设在线用户一千个人，就发一千份。**

#### 思路二：起个定时器定时群发

当有一个用户上线我也不管，我有我自己的节奏：**在服务器起一个 `timer` 定时器**，定时地去完成群发任务。

你们学 JavaScript 的时候肯定学过类似的东西。也就是说，**服务器有自己的一个策略，不管你上不上线，每隔一定的时间，把服务器维护的 `onlineUsers` 整体推送。** 因为用户上线也好、状态变化也好，都会通知到 online，所以也可以把这个推送出去。

**但是这样一想，代价可能比刚才那个更高。** 刚才那个是有人上线才推一下，这个是每隔一定时间推一下——**每隔多长时间呢？10 秒还是 30 秒？这个量是很大的。**

**一般的聊天室在线十万人是很轻松的事，像 QQ 在线有时候其实几千万人。** 几千万人的话发下去是很恐怖的。而且**每个人的好友列表还不一样，还要把张三的好友列表搂出来、把李四的搂出来，然后再发，其实是一个很复杂的过程。**

**所以这两个思路虽然可行，但是代价比较高。**

#### 思路三：只推这一个用户的状态

**我的思路是这样子的：当有一个用户上线过后，他只把自己的状态推送给在线的客户端。我不推送所有的。**

那么这里就有一个问题了：**因为是单个单个推送的，原先的用户状态到哪去了呢？**

这就意味着——**客户端应该也有一个 map，它要记录它现在掌握的那些用户的状态。** 客户端那边也应该有一个 map，来记录它所持有的、或者它关心的那些在线用户的信息。**因此客户端也需要维护一个 map**，这里记录了他的好友（**目前我们没有分好友，目前就是所有人**）。

定义这个 map 之后，你不停地维护这个 map 的信息：**当有一个变化了，就把状态更新到这里；你要看或者要更新，就调一下方法，从 map 里面取出来就完了。**

**这样就把一个重的服务器端的功能分散给各个客户端了，服务器压力不至于那么大。**

这个 map 应该长什么样子呢？它应该至少也有一个 `int`，后面维护的是一个用户的 User 信息，**包含它的 ID、名字、昵称等就可以了。**

#### 推送靠谁：serverProcessMes 协程

但这里还要解决一个问题：**当一个用户上线过后，要想办法通知他、推送给他，怎么推送呢？**

这就要用服务器端和客户端维护的一个协程。大家还记不记得，我们在客户端登录成功以后起了一个重要的协程，叫 **`serverProcessMes`**。**这个协程具有重大的作用，它会不停地保持跟服务器端的通讯。如果服务器有数据推送给客户端，我就接收并显示。**

这里的信息很多：**用户状态变化了、有人私聊了、有人群发信息了、有人发起视频会议了等等，都要通过它来处理。这个协程一起来之后，复杂度就上去了。**

**大体的思路已经有了。具体实现起来，我们得一步一步来搞。写好了就一步通过，写不好的话就接着调。**

我们现在编写通知所有在线用户的方法：

```go

	// 遍历 userMgr 里面的在线用户 map，一个一个地发送
	for id, up := range userMgr.onlineUsers {
		if id == userId {
			continue
		}
		up.NotifyMeOnline(userId)
	}
}
```

在 for 循环的时候就可以把 `onlineUsers` 里面的内容拿到——**它里面有一个 ID，同时还有一个 `up`（也就是其他人的 `UserProcess`）。**

**有一个地方不能发送，就是通知其他人的时候不需要通知自己。** 因为你自己给自己发没有意义——**你上线了难道你自己不知道吗？你肯定知道。**

做法也好办：**这个 map 里面肯定有你自己**，你上线服务器肯定要把你自己扔进去。所以这个 ID 如果等于了你要通知的那个人——这个人就是刚刚上线的——**如果它等于自己了，我就不去处理，`continue`。** 如果它不是自己，那就开始一个一个通知了。

#### 发出去：Transfer 绝对不能提到循环外

准备发送了，服务器端快 OK 了。怎么发送呢？

**你现在这边已经拿到了它**——注意这个地方这个 `this` 就代表这个 `up`，就是你从那个 map 里面取出来的那个带连接的那个 `up`。

**我们现在发送还不能靠它，还得创建我们一个 `Transfer` 实例。** `utils` 里面有个 `Transfer`，里面有个 `Conn`，**这个 `Conn` 刚好就是我们带过来的**——`this` 里面是带一个 `Conn` 的，然后我们通过 `tf` 去 `WritePkg` 一下，把这个 `data` 给它发出去。

当然这边可能会有错误，收一下：

```go
err = tf.WritePkg(data)
if err != nil {
	fmt.Println("notifyOnline err=", err)
	return
}
```

就说明我们在 `NotifyMeOnline` 的时候发错了。最后 `return`，因为没有返回值，所以最后这个可以不要 `return`。

**这里有一个问题，请同学们思考：刚才说的这段代码，它实际上永远都是同一个 `data`**——就相当于说你有一份 `data` 要发给 10 个、20 个、100 个，这个可以把它提出去，这没问题。

**那么 `Transfer` 能不能提出去呢？说统一用一个 `Transfer` 不就完了，每次整这么多 `Transfer` 干啥？**

**答案是：绝对不能提出去。**

因为每次传进去的 `up` 不一样，**`this` 就不一样，`Transfer` 就不一样**——因为最终目的是要把里面的 `Conn` 拿到，一个一个地发。**如果这个东西你敢提出去，你就发给一个人了，永远是发给一个人，其他人在那儿傻傻地等都不知道。** 你把这段代码提出去，你会发现只有一个人拿到这个推送消息，**其他人全部一个消息都拿不到。**

**但是上面那段组装加序列化的代码是可以提出去的。** 到时候我给大家这个任务：**你们怎么提、放到哪一个位置比较合理，动脑筋就行。**

#### 什么时候去调它

发送代码写完了。**在哪里去调这个方法比较合理呢？** 动动脑筋。

因为我现在已经编写了一个"一个用户上线过后我就通知他"——那显然**调用的地方应该放在这个用户登录的时候，登录成功，或者状态发生变化的时候**。

**现在因为只有一个在线，我还没写离线。离线都很简单**：比如注销的时候，这个人注销之前、要退出之前，他按下注销或者退出之前，或者检测到连接断了的时候，**再去把他的状态改成离线就完了。**

现在只有上线，所以这个函数的调用就应该放在**登录成功的位置**：

```go
this.NotifyOthersOnlineUser(userId)
```

**因为 `NotifyOthersOnlineUser` 是属于这个的，所以直接用 `this` 调用就行了。** 把当前登录的这个家伙的 `userId` 传进去——**登录这个家伙的 `userId` 不就是他吗？**

> **这句话看起来很简单，就一句话，但是我们写了好多代码。** 它就是当通知其他在线的用户：我上线了。

你上来过后大家可以想象这样一个场景：**有一个 A 客户端上线了。假设下面还有 C 客户端、D 客户端——A、B 已经上线了，C 一上来登录成功过后，先把 C 也加进 map 里面了，相当于这个 map 里面已经有 A 和 B 了。C 一上线，服务器就遍历了整个 map，然后把 map 里面的 `Conn` 拿到过后，通知 A 和 B 说：C 上线了。**

## 客户端接住推送：协程里的 switch、客户端的 UserMgr，和三个人跑通的验证
> 对应块：BLK133 | 覆盖分集：P338 | 块标题（分集名）：《336_尚硅谷_海量用户通讯系统-显示在线用户列》

客户端这块你得想这个事情：**人家已经把东西给你了，那你得想它送到哪一个位置去了。**

你比如说你在这个上线了过后，你上线了过后你不是通过服务器端搞了一个，你在这儿遍历了嘛，你肯定调用它了嘛。你上来过后，你调了一下这个 `NotifyOtherOnlineUser`，然后它里面就去遍历了所有在线的人，把它一个个发过去，最后它的关键点是不是 `write` 了一下？

**那你得想它 `write` 到哪儿去了。它把这个包——就是那个 `NotifyUserStatus` 这个 `Message`——会送到什么地方去了呢？得想。**

对了，这个地方你一定要分析出来到哪儿去了。因为大家都知道，在客户端这边其实人家早就一直在等待你的了——它就已经等得黄花菜都凉了，终于发现有人把东西发回来了，不在这儿吗？

我在这儿起了一个跟服务端保持通讯的协程，人家一直在这儿等呢。客户端正在等待读取服务器端发出的消息，终于等到了一个结果，终于等到一个类型。

这个类型，你现在干什么？你把这个 `message` 拿到过后你就直接跑路了，你说你写了一句话"读取到消息，暂不处理"——这不是以前我们留的一个逻辑孔在这儿吗？你看这个东西都是有思考的，不是说乱七八糟再去写的。

### 老套路：先 switch，再干两件事

好，那现在你就真的要去处理了。那处理最好的方式肯定就是先看你的返回的消息的类型，又是那一个套路了，`switch`——就是你服务器端返回什么消息类型，我就处理什么类型。

它的类型，我们首先把 `message` 的那个类型取出来。那这个时候我就要做一个判断，`case`。如果这个消息类型它是 `message.NotifyUserStatusMes`，那我就非常高兴——**它就是告诉我，有用户的状态发生了变化了，那我们要的就是它呀！**

我们再写个 `default`。如果是 `default` 呢，说没有匹配的，返回了一个消息，但是这个类型我不能识别，那我就写一句话嘛，提示一句：服务器端返回了一个我暂时不能处理的消息类型。

> **提示**：比如你服务器端写了东西了，但是客户端是另外一个张三在写，他说："这个类型我不能识别，我还不知道怎么干呢。"所以你可以提示一下：服务器端返回了一个未知的消息类型。

那这个处理完了过后，这里面要写代码了。同学们想，你这里面应该怎么做呢？**既然别人已经把消息给你了，你肯定要想办法先把消息取出来，然后进行一个改写。**

#### 第一件事：从 Data 里取出 NotifyUserStatusMes

第一件事情：取出这个 `NotifyUserStatusMes`，你肯定要把它取出来。因为这个 `NotifyUserStatusMes` 里面包含了一个用户的 ID 和他的状态——有 ID，有 `Status`，那就说明我知道有一个人来了。

#### 第二件事：把这个人加进客户端自己的 map

但是这个人来了过后你怎么处理啊？**你不能把它直接显示出来。** 这个地方就意味着第二个动作来了：你得把这个人加入到你本身客户端维护的那个 map 里面去。因为人家来了嘛，你肯定要把他加进去啊，比如他的状态是什么。

因为我刚才讲过我的一条重要的思路是：我的思路是让客户端也要维护一个 map。你不维护它，每次服务器只能硬生生地把所有的全部一返回，**你这个代价太高了**。

所以现在我们还得有一个事情：把这个用户的这个信息或者状态保存到我们客户端的 map 中。问题来了——**map 你有吗？你根本都没有，你现在的 map 还是空的呢。**

所以你一分析到这地方，你马上觉得 map 还没有写完。所以现在你要先不能着急，你还得先把 map 写出来。你看这个代码就感觉有点跳跃了，有点跳跃——突然一下怎么到这儿还要写这个东西？回头又回去写，然后那边服务器那边我还得管。

#### 为什么写网络通讯要先定协议

所以说写网络通讯的时候，一般如果是两个人写的话，**这个项目经理最主要的责任就是先定这个协议**。就定好我给你什么、你给我什么就完了，我也不问你要什么。他事先说我给你那个 message 是这样子的，你返回一个什么东西就可以了，其他我不管。

当时我们在做金开协同之星的时候，就是这样定的。我们那老大就说一句话：说我给了你这样一个包包，你返回我格式是什么就行了，**至于你怎么返回那是你的事**。

现在我们没有办法，我们现在还得搞一个 map。

### 客户端的 userMgr.go

这个 map 刚才我已经分析出来了，它是长这个样子的：**有个 int，还有一个 User**，它里面保存了很多 User。

那把这个放在哪里比较合适呢，各位同学？我们整个这个东西也需要写一个专门来管理它的文件会比较好，所以我新建一个文件也叫 `userMgr.go`。**这个跟服务器不一样，它是管理客户端的 user，管理、维护，这个是它一直在的。**

**第三步，客户端的 map。** 客户端代码其实并不多，但是思路很重要。我们首先里面做了一个客户端要维护的 map，这个 map 我们是专门维护这个客户端关心的那些用户。在客户端 `client/process` 下面写了一个 `userMgr.go`，它是专门用来管理在线这些用户的一些信息。

**第四步，调用点。** 它的调用其实是在客户端的一个协程里面玩的，也就是在 `server.go` 这个地方玩了一把。**这个地方很关键，因为你在这个地方才能够去处理它**——我上来过后在这偷偷地看你到底给我返回什么呢？如果是 notify，我就去更新我的在线列表，如果不是就算了，不是的话我就干别的事。

> **提示**：大家可以想象到，我们将来群发消息或者叫私聊，肯定也是在这加一个 `case`。因为你这到底是后台的、保持通讯这块肯定是在这，所以我们在这加了一段代码。

**第五点，在客户端的 `process/server.go` 里，为了能够支持当用户输入 1 的时候也能看到最新的在线列表，我们做了一个改动，调用了一下它。**

```text
       服务端                                   客户端（协程 server.go）
  ┌──────────────────┐                    ┌──────────────────────────────┐
  │ 登录成功           │                    │  阻塞等待读包                │
  │  ├ AddOnlineUser  │                    │        │                     │
  │  └ NotifyOthers…  │                    │   收到 message               │
  │      for id,up    │                    │        │                     │
  │        up.Notify… │──NotifyUserStatusMes──▶  switch mes.Type            │
  └──────────────────┘                    │        │                     │
                                          │  ├ NotifyUserStatusMes：    │
                                          │  │   Unmarshal(Data)        │
                                          │  │   updateUserStatus()     │
                                          │  │   outputOnlineUser()     │
                                          │  └ default：未知类型提示     │
                                          └──────────────────────────────┘
```

读图说明：客户端这套逻辑全部挂在那个"偷偷在跑"的通讯协程上——它唯一的动作就是等着，收到什么类型就走哪个分支；`updateUserStatus` 负责把增量合进客户端自己的 `onlineUsers`，`outputOnlineUser` 负责把维护结果落到界面上。

> **承前启后**：上一节讲完「客户端接住推送：协程里的 switch、客户端的 UserMgr，和三个人跑通的验证」，下一节接着讲「客户端发消息：先把连接存起来，才谈得上群发」。

## 客户端发消息：先把连接存起来，才谈得上群发
> 对应块：BLK134 | 覆盖分集：P339-P340 | 块标题（分集名）：《337_尚硅谷_客户端发消息思路分析》

现在我们完成一个群聊功能。群聊这个功能我们也分为两个步骤来完成。第一个步骤是这样子的：**当一个用户上线以后，可以将群聊的消息发给服务器，服务器可以正常地接收到。**

也就是说我们可以把客户端发送的消息发给服务器，服务器这边可以正常接收。

### 输入 2 之后应该发生什么

这块倒还变得比较简单了。因为你现在已经进入到 `server.go` 显示的这一个界面了，`server.go` 能够显示哪一块页面了？大家看，它已经可以显示这个页面了。

这个时候比如说我们输入一个 2，现在是没有反应。输这个 2 我们希望它能够干什么呢？**提示你要说什么内容。** 比如说我们提示你想给大家说点什么，然后它就提示一句话让你输入。

那问题又来了，你既然要发送这个内容给服务器，服务器肯定拿到这个内容来进行转发，这个时候每个人的想法可能就不一样。

### 消息体怎么设计：两块东西

我是这样来设计的：待会儿我们在这儿写一个新的结构体，这个结构体我们是新增的，比如我取个名字就叫 `SmsMessage`。

这里面我们要包含的内容是什么？大家可以想象：

- 肯定要有用户的 `UserId`，有谁发的；
- 肯定要有用户的名字；
- 肯定还有一个特别重要的东西是什么呢？就是你要发送的内容是什么，`Content`。

当我们这么一设计的时候，我们发现有一点不好了。**因为我们发现这种设计方法没有有效地利用前面我们定义好的结构体。**

大家有发现吗？你这消息主要分成两大块：第一大块就是你这个 SMS 要发送的内容是什么；第二大块就是发送人的信息——你是谁；第二个，你把这个信息发送给谁。如果是点对点聊的话还麻烦一点，点对点你还得告诉我你要把这个消息发送给谁。

既然如此，那么我们干脆就设计成两个部分：**一个部分就是 `User`，用我们原来学过的继承的这么一个东西，用一个匿名的结构体；然后这边是内容就可以了。**

这是第一个我们分析出来在客户端我们要增加的一个东西。

### 顺手补上 SmsMes 的类型常量

首先我们先把这两个新增的结构体把它搞定。

那大家要想一想，有没有再新增一个？有些同学会想说：老师，群发消息的话有没有一个 Response 呢？也有可能。就是说我这儿新增加的这个消息是发送的。

> **提示**：有些服务器拿到你发的这个消息过后，会进行一定的过滤或者增加一些东西。比如说你群发消息里面有一些比较敏感的关键字，他可能会把敏感词给你换成星号，这些都要在服务器做。
>
> 说："老师，我在客户端做可不可以？"客户端也可以做，但是服务器也要做一下。你如果不相信，可以去试一下。比如说你在 QQ 里面说一些特别敏感的词，当你发送过去的时候，你会发现你对方收到的那个消息，那个比较敏感的就直接变成星号了，或者根本就发不出去——它会直接从服务器给你打回来一个消息说：你这儿什么内容涉及一些敏感词，直接拒绝为你转发。

甚至有些时候你们看到，当你发一个消息过后顺带发给对方的时候它带一个广告过去，也有可能——它根据你发送的内容，比如说你说"我想看一本 Java 书"，它可能带一点 Java 的广告、书籍的广告一起发给你。

所以这个我先暂时不去设计了，因为设计的东西扩展起来很多。这个我就设计一个比较简单的，就叫做发送的消息。**回送的我们相当于直接转发了**：我在服务器做一个比较简单的处理，我拿到这个东西也不去过滤，我也不去检查，我就直接相当于服务器做了一个中转，拿到过转给其他的人就行了。

那我的设计思路是这样子的：

```go
type SmsMes struct {
	Content string `json:"content"`
	User
}
```

它里面的内容，第一个就是它肯定要有说话的内容，我们叫 `Content`，单数叫 `Content`。

> **易错点**：建议不要这么取名——因为这个 `con` 很容易跟连接 `connect` 很像，所以我就写个全称叫 `Content`。有些人喜欢叫 `Body` 也行，是个字符串。

第二个，你得表示短信消息是谁发出来的。因为服务器里面可能会做一个组装，代表是谁——对方拿到过后知道是谁发过来的，他的昵称是什么，他的 ID 是什么，甚至包括他的 IP 地址是什么，我都可以把它包裹在这个包里面去。

所以这块**咱们直接用 `User` 就完事了，不用再去写一遍**。它的类型就是这个 `User` 就行了。因为里面的信息很全，ID、密码、用户名——但是你在发的时候肯定不会把自己的密码也带过去，肯定你不会说我的密码是谁，肯定是不带的，你肯定带个 ID、名字，状态也有可能有。

因为他们在同一个包里面，所以你这一个匿名结构体就应该可以了。**这边其实用了一点我们所说的继承的一种关系。**

保存一下看有没有问题。应该没事的话，我们同样把这个类型也增加进去：`type`，这个叫做短消息。

### CurUser：一个被我们用了却从没存下来的连接

紧接着根据刚才的分析，我们应该还有一个 `CurrentUser`。那为什么要有 `CurrentUser` 呢？就是因为**你必须得维护你自身的信息——你自己的连接是谁，你是谁，你得有啊。**

那现在的问题来了。你既然要把这个消息发送出去，那就需要你客户端这边也应该维护一个很重要的连接。**你的连接现在你在维护吗？你好像没有维护，你只是在用，你没有维护。**

也就是说，当你要从这儿发一个消息给服务器的时候，你突然感觉到你没有连接了——你的连接在哪里？你的连接根本就没有。**你的连接虽然在这儿一直在用，确确实实你也没关闭；你看这儿，你在不停地用这个连接在读东西，可是你在这儿怎么去取呢？其实你一直没有保存。**

#### CurUser 该长什么样

在哪加呢？我们在 `model` 层里面加一个新的东西叫 `CurUser`，就是当前的用户。这个命名就看你的习惯了。

当前这个用户里面肯定也有它自己的信息，对不对？那这个是个结构体，它应该包含什么呢？我觉得它至少要包含这么两个比较重要的东西：

- 首先它有一个连接，必须由它给我维护住——**这个连接就是你在登录成功以后，你获取的跟服务器进行通讯的这个连接**；
- 第二个，它既然是当前用户，它应该也有相应的用户的信息，所以这边也可以把这个 `User` 放进去。

那么现在我们把这个定义在哪里呢？**这个不是共用的，所以不要写在这个 common 里面**，咱们单独地放在 `model` 包里面去，新建一个文件夹，我们就叫 `curUser`。`package model`，在里面我们就先写一个结构体，它就叫 `CurUser`。

它也用到一个匿名的，首先它自己会去维护自身的一个连接，那么这个连接是 connect 里面的一个连接，**这边我要引一个包 `import "net"`**。然后它还要嵌入一个 `User` 信息，它自己的信息，那就是 `message.User` 就可以了。因为用到 message 了，所以我们要引入 message 的这么一个东西。

```go
package model

import (
	"net"

	"go_code/chatroom/common/message"
)

type CurUser struct {
	net.Conn
	message.User
}
```

#### 它必须是全局的

那这个 `CurUser` 在什么时候给它初始化一下？

> **结论**：那肯定你作为一个 `CurUser`，它一定是个全局的。因为你将来在很多地方你都可能会用到这个连接，甚至会去提示、提醒他自己的 ID、用户名这些，所以我们把它做成一个全局的。

因为在客户端，我们很多地方会使用到这个 `CurUser`，所以我们将其作为一个全局的。那这个全局的变量在哪里呢？**你可以放在这个 model 包，也可以放在别的包。** 比如说你放在这个地方也行，放在这儿也行。因为统一管理嘛，我们这儿不是有一个 `main.go` 了吗？那同时在这儿建一个 `CurUser` 也可以。那我直接写在这儿了：

```go
var CurUser model.CurUser
```

#### 初始化放在登录成功之后

但是你这个值在这儿只是定义一个全局，你没有初始化它也不行，到时候它啥都没有。那问题来了，在什么地方去把这些值送给它比较合理呢？

**显然还是在它登录成功以后去完成对它初始化是最合理的。**

找到在 `userProcess` 里面，它其实是有这么一个动作的。大家看，跟上思路。在 login 登录成功 200 号，找到它。在这个地方登录成功以后呢，我就直接在这儿初始化我们的这个 `CurUser`。

初始化哪个呢？`CurUser`。很简单：

```go
CurUser.Conn = conn
```

连接，我要的就是它，因为待会儿我要用它这个连接发东西。**连接其实就是这儿创建好的这个连接。在客户端这头呢，只有一个 connect，跟服务器不一样，服务器有多个，它这儿只有一个。**

第二个，你得把这个用户的信息也给它初始化一下。那这个也很简单——`CurUser` 它这里面因为用的是继承的关系，`CurUser` 这个里面直接用了 `message.User`，而 `message.User` 里面包含的信息是这些。我们用它的特点，直接点就行了。**这就是我们以前学过，嵌入一个匿名的结构体，如果它本身没有含这个字段的话，它可以直接用。**

当前这个用户 ID 不就是你登录的 ID 吗？你登录的 ID 不就是你这儿输进去的吗？

```go
CurUser.UserId = userId
```

好，我们再看这有没有这个东西？有，有个用户状态，我给他一个用户状态吧。**用户状态我们假定就是一个在线的**——`message` 里面有一个 `UserOnline`。

> **提示**：名字、状态这些呢，你也可以写一下。将来我还想把我自己的地址带给对方，可以。性别、电子邮件、头像、座右铭、什么时候出生的等等——你想加就加，这就是你的自由。好，这个就是你们自己可以扩展。

那么这个信息有了，就相当于是说我们这个 `CurUser` 已经在登录成功以后就把这些东西拿到了。**拿到这个信息的目的干什么呢？你要它的目的不就是想放东西出去吗？**

### SendGroupMes：把内容裹好扔出去

现在我们已经完成了它，最后需要做这个动作了：群发。

那你群发的话，问题又来了。**你要群发的话，你首先得给我传一个什么进来，我帮你群发？** 你得看以前你这个登录是怎么做的，或者注册是怎么做的，你可以按照这个思路来玩一把。

找到 `smsProcess`，现在这个地方是啥事都没有，之前什么都没做过，是个空的。现在就要把它用起来了。

首先 `import fmt`。然后我们写 `type SmsProcess struct{}`。

它这里面有什么东西呢？好像暂时想不出来。**因为连接我们也不交给他，连接交给他也不合理——它只是个短信处理；ID 也有那个 `CurUser` 来维护了**，所以它相对来说只是声明了一下。

然后我们老规矩写 `func (this *SmsProcess) SendGroupMes(content string) (err error)`，发送群聊的消息。

我们看以前类似登录是怎么做的，我们可以模仿一下：注册是给它用户名密码，有个 error。这是登录，注册好像也是类似的一种写法吧。

那么我们可以这样来想，在这块我们也要返回一个 error，它肯定要发东西出去。

> **提示**：你现在其实说白了就是你把内容给我就可以了。因为目前对它来说只要一个比较简单的，就是你要说什么话，因此咱就简单一些，`content string` 就行了。

#### 组包：又是那个老套路

发送怎么发呢？又是一个套路了。首先把你的内容封装到一个 `Message` 这么一个结构体里面去，并序列化，发送出去、扔出去就行了。

```go
var mes message.Message
mes.Type = message.SmsMesType
```

第二个，把它的类型给我指定——就是刚才我们刚刚自定义的一个短消息类型。

紧接着它的 `Data` 部分，要给它一个新的东西。创建一个 `SmsMes` 这个实例：

```go
var smsMes message.SmsMes
smsMes.Content = content
smsMes.UserId = CurUser.UserId
smsMes.UserStatus = CurUser.UserStatus
```

首先第一个，你发送的内容现在人家已经告诉你了，就是这个 `content`，所以你二话不说，给它赋过去就行了。

第二个，**你还得告诉别人你是谁**。你不是 `CurUser` 已经有了吗？你把 `CurUser` 扔过去就行了。

> **易错点**：这里我要说一句：我刚才还想这么做——在这个消息里面我做一个 `User`，**直接把 `CurUser` 赋给它**。但是这样子一想呢，会多把连接也给它带过去，这样不划算了，所以还得一步步给它重新赋值。
>
> 其实这里用到了匿名的好处：直接访问 `smsMes.UserId`，从我们这个 `CurUser` 取 `CurUser.UserId`。没事，信息也不多。大家可以再把它分一下，`UserStatus` 也从这取出来。

那这一套有了过后呢，我们把这个 `smsMes` 进行一个序列化：

```go
data, err := json.Marshal(smsMes)
if err != nil {
	fmt.Println("json.Marshal err=", err)
	return
}
mes.Data = string(data)
```

如果序列化没有错误，OK；如果有错误，我们就打印出一句话——序列化失败，序列化失败就不玩了。

如果这个序列化成功了，我们就把这个 `data` 给它关联上，`mes.Data = string(data)` 就可以了。这个我们以前写过好多遍。

紧接着对我们的 `mes` 再次序列化。在序列化过后呢，我们再去把它发送——这个代码就比较简单，复制一份。

#### 用 CurUser 里的连接发出去

第五步，发送。将这个序列化后的 `mes` 发送给服务器。怎么发呢？显然你还得用我们这个 `Transfer` 来发：

```go
tf := &utils.Transfer{
	Conn: CurUser.Conn,
}
err = tf.WritePkg(data)
if err != nil {
	fmt.Println("sendGroupMes err =", err)
	return err
}
return nil
```

& 符号，就是我们 utils 包里面有一个非常可爱的 `Transfer`，然后把连接给它——**这个连接已经在我们的 `CurUser` 身上了**，所以你直接取出来就行了。

有了它过后，不要犹豫，不要彷徨，发送！仍然用 `tf` 的 `WritePkg` 这个方法，把 `data` 放进去，因为 `data` 现在已经是一个 byte 切片了，所以完全没问题。

### 菜单里的衔接：2 → 输入内容 → 调用

好的，现在我们已经把它写好了，写好过后你得想一下在哪里去调用了。因为你现在已经把这些都搞定，那你在发送的时候你得调它，而你输入的内容是在 `server` 主菜单里面提示的，所以现在我们完成一个衔接。

找到我们的 `server.go`，我们是在这个地方的——说"请输出……要发送消息吗？"好，你要发送消息，我就来提示一下：

```go
fmt.Println("请输入你想对大家说的话：")
```

你想对大家说点什么？这样说，"你想对大家说点什么"，OK，一个冒号。

这个时候你肯定要有一个字符串来接收了，这是必然的。怎么接收呢？**你可以把这个变量定在 `switch` 的外边**：

```go
var content string
fmt.Scanf("%s\n", &content)
```

它的类型是 `%s`，斜杠 n，然后我们把它接收到 `content` 里面去。

咱们把这个做完了以后呢，我们调用刚才写的那个方法。那你调它，我们以前的老规矩就是：**要使用哪一个 process，先去实例化这样一个对象，然后再去做。**

#### 实例为什么放在 switch 外面

其实像这个 process 呢，你也可以不用反复实例化，因为以后可能只会用到一个。所以这是个好处。

> **提示**：这是 CS 开发有一个特别好的地方：**只要你这个程序不退出，它的实例其实一直可以使用。这个跟 Web 开发有一个巨大区别**——Web 开发一般是一个请求过去，然后这些东西用完就全部清空了。PHP 就是这个经典的特例，所以那个时候就是一次请求用完就销毁了，效率上就不能反复使用这个实例。现在像这种都可以反复使用。

> 对应块：BLK135 | 覆盖分集：P341-P342 | 块标题（分集名）：《339_尚硅谷_服务端转发消息思路分析》

### 思路分析：三处都要动

打开我们这个图。假设你通过 `SmsProcess`，把这个群发的消息发送到哪里去了呢？发送到服务器端来了。那服务器这边肯定先是由 `Processer` 来接收到的。

大家看，在 Server 端我们有一个总控。**总控这个地方，它是能够拿到你发送的所有消息的，而且它已然给你反序列化过了。** 我们这可以处理登录的消息，我们也可以处理注册的消息。现在我们应该增加一个处理群发短消息的这么一个分支——**所以说代码一定要在这写**，这是第一个分析出来的。

那第二个呢，我们应该想一想，你在处理这个群发的时候，转发、或者说转发这个消息吧，**这个任务显然应该交给服务器这一端的 `SmsProcess` 来处理更为合理。因为它是属于短消息相关的，不是跟用户相关的**，对不对？所以在这里面我们要增加一个群发消息的方法吧。

那你发完了过后，你还得想怎么处理呢？**你把这个转发回去**——因为你这相当于说服务器拿到又转发给其他在线用户了嘛，那就意味着你的客户端还要去做一个响应。什么响应呢？就是如果别人转发了这个消息，你要怎么去处理？

所以说这个地方你还得回头在客户端的这个 `Server` 里面，就是偷偷运行的协程里面，还要增加一个处理：**如果这个消息是 `SmsMes`，你要怎么去处理？**

#### 一个关于命名的反省

所以大家可以看到，是这么一个逻辑了。你看**为什么我在刚开始的时候，我说这个消息最好写两种呢？** 你看，你发送的时候是 `SmsMes`，现在你把这个东西推回给客户端，你的类型还是它。所以有时候不是特别的好——你看这两个类型都在，相当于在客户端这个又是发送，又是接收，因为它会推送给你一个嘛，所以显得不是特别好。

所以很多地方它是把它做成一个 `SmsResMes`，只是这两个结构长得很像，但是名称不一样。这里我就没有去做这个区分了，同学们，你们后边反正知道这个事儿就可以了。**将来你在公司里面做开发的时候，你最好还是给它稍微地有一个名称上的变化。**

好，现在我们思路已经分析出来了。第四步：**在服务器端接收客户端发送的消息并处理**，在服务器端接收到 `SmsMes` 这种消息。第五步：**在服务器端 `process/smsProcess.go` 这个文件中增加一个群发消息的方法**。然后呢，**在客户端还要去处理一个响应——别人给你发过来的群发消息**。

OK，群发消息。大体来说又是三部曲。

### 服务端实现：总控加一个分支

打开我们的 VS Code，先找到 server 端的 `processor`，这个地方肯定要加东西了。照猫画虎，粘贴拷贝不就完了吗？套路已经有了：

```go

```

同样道理，因为现在要去处理的时候，这个地方是**必须创建新的**。

> **提示**：你说这个为什么不能共用呢？**你要是共用的话，`Conn` 都不一样。服务器端这个可不能共用，你的思路要分析清楚。** 不能说客户端写了一个 `UserProcess` 就可以了，服务器端是每一个连接，你不知道是谁——张三来了李四来了，他们能共用吗？因为它的 `Conn` 不是同一个，所以每次必须创建一个新的。

这里我们要去创建一个 `SmsProcess` 的一个实例，完成转发群聊消息的一个任务。

#### 一个空结构体也是合理的

打开它，这边一个东西都没写。先来定义一个结构体：

```go
type SmsProcess struct {
}
```

那这个结构体里面有什么东西呢？一时半会儿还想不到，应该没啥。**相当于就是用这个结构体把这些方法管理起来而已。** 当然你也可以直接写方法，但是因为我想还是用面向对象的一种思路来做，所以我还是定了一个结构体，只是现在没有用。

> **结论**：**为什么它不需要字段呢？因为说白了，你现在整个服务器端各个连接已经在手上了，在 `UserMgr` 里面已经在里面了，消息也能拿得到，那就不需要了**，所以可以不写。

#### SendGroupMes：收一个 Message 就够了

开始写方法，转发：

```go
func (this *SmsProcess) SendGroupMes(mes *message.Message) {
```

你得告诉我，发这个消息你得告诉我发什么东西，你得给我一个 `Message` 才可以。`Message` 在总控这边是可以拿得到的，因为 `Message` 已经有了。所以到这个地方、到 `SmsMes` 的时候，这个地方消息其实我们是可以拿得到的。

只是这个消息，你需要这种 `Message` 的还是说已经序列化过后的？这里我们看看我以前是怎么设计的——我应该是直接拿的一个，就是 `Message`，他就不需要他去处理，我直接自己来处理的。那也可以，就直接这样写，**也不让你去反序列化了，全部交给我们其实就行了**。

现在你要做的事情是什么？现在的任务就是要群发。**现在的任务是这样子的：遍历服务器端的这个 map**，哪个 map 呢？就是他这个 `UserManager` 里面维护的这个 map。对，是它。遍历这个 map，然后将这个消息转发出去。

那么这个消息转发出去，咱们得遍历了，用 `for` 循环：

```go
for id, up := range userMgr.onlineUsers {
```

遍历的是谁？遍历的是这一个全局变量的，因为都在 `process` 里面，那我可以直接用这个变量里面的 `onlineUsers`，没问题。

#### SendMesToEachOnlineUser：内容加连接两个入参

遍历的地方，当我们遍历一个过后，我们就把它发出去，send 这个 message，把它发出去。**所以我这里应该还写一个函数，还写一个函数比较好**，因为你都写到这一块不是特别方便：

```go
func (this *SmsProcess) SendMesToEachOnlineUser(data []byte, conn net.Conn) {
```

这个地方我就写个叫做 send 每个 online 的 User，`SendMesToEachOnlineUser`。**这个函数名稍微有点长，但是无所谓，只要信息比较明确也是可以的。**

你得想，我把这个消息发出去，怎么才能发呢？

- 首先这个**内容**你得给我，你得把这个内容给我，所以我首先需要你要发送的这个信息内容是什么，就这个群聊消息是什么；
- 第二个，**你还得给我一个连接**，这个连接你得给我一把。

那么连接咱们就可以直接从这儿拿一个，`conn net.Conn`。有了这两个东西，我们现在这个方法就有了。

#### 过滤掉自己：SmsMes 里已经带着发送者 ID

当遍历一个，我就这样写了：**内容还没从这里面取出来呢，内容都没取出来你没法发，所以你得先把内容取出来。**

先取出这个 message 里面的内容。`Message` 的内容它是藏在 `SmsMes` 里面的，所以你还得把它反序列化一下才行：

```go
var smsMes message.SmsMes
err := json.Unmarshal([]byte(mes.Data), &smsMes)
if err != nil {
	fmt.Println("json.Unmarshal err=", err)
	return
}
```

我们要反序列化的内容是哪里呢？是这个 message 里面的 `Data` 部分。它在 `Data` 部分其实现在是个字符串，是个字符串，**所以说我得先把它改成这个切片**，反序列化。然后这个地方我把这个引用传进去：`&smsMes`。

现在有办法了，我取一个我就这样写了：

```go
if id == smsMes.UserId {
	continue
}
this.SendMesToEachOnlineUser(data, up.Conn)
```

> **易错点**：这样写会存在一个比较麻烦的事，就是**你会把这个内容再重新发回给自己**。你发了一句消息，从服务器里面绕了一圈又回来，又给你自己打回来一个消息，你想想是不是这个道理？
>
> 因为你这个 `onlineUsers` 里面其实你自己也在里面。你相当于是说把这个消息，比如"Hello"，打出去过后，服务器把它所在的成员全部串了一圈，把你自己再发进去了。
>
> 所以这里我们还需要**过滤掉自己**。这里 `SmsMes` 里面其实已经包含了这个传进来的用户 ID——大家看这里是不是有一个 `UserId`？**这个 `UserId` 里面其实包含他自己的那个 ID，所以我们完全可以利用这个特点把它过滤掉。**

如果这两个 ID 相同的话，就说明刚好你遍历出来的 map 里面这个人就是自己，那这个时候我们不做处理，`continue`。其它的该怎么做就怎么做，就完了。

#### 参数为什么应该是 data 而不是字符串

接着往下写。因为你已经有内容了，也有这个连接了，那就很简单。你看这里是不是有点不太划算？**因为你要转发过去，这个内容还不行，不要内容。因为你是把整个这个 message 相当于转发，那就没有必要再把它打开。**

这里有点不划算——我们现在又做了一件比较不划算的事情。但也不是不划算，代码还是这么写也是对的。**我们这个地方传的不应该是一个字符串，而应该就是这个 message 序列化过后的那个 byte 切片就可以了。**

大家看是不是这个道理？因为我们这是完全不做任何处理的一种转发工作，**所以其实这个内容对我们来说没有什么实际的价值，只是这个 ID 对我们是有作用。**

```go
data, err := json.Marshal(mes)
if err != nil {
	fmt.Println("json 序列化 Marshal 出错 err=", err)
	return
}
```

就是说相当于说你这个你发过来的消息，我把它反序列化过后，我主要的目的就是**看看你到底是谁，把你自己过滤掉**。然后这个 message 我**还原封不动地再给你转发**给其他的人，是这意思吧？

大家把这个逻辑捋一捋，怎么走的：先拿到这个 message，把这个 `SmsMes` 取出来。取出来的目的主要是在这儿用了一下。**但是我们用完了过后，我们真正要发的仍然是这个 message 的序列化的那个 `data`。** 因为相当于做转发嘛，我没有落盘，我就直接在内存里面，直接读完了过后我就通过连接啪扔走了，我也没有在中间进行存数据。

> **提示**：你们将来想一想，假设有一个情况——将来你要给某某个人做一个离线留言。如果你要做一个离线留言，你就应该去扫描所有的 ID，你发现有一个人现在不在线，**你就应该把这个消息放到一个数据库里面去，然后记录该消息是谁没有拿到的。等到他上线的时候，你就去读那个数据**，说这条消息哪个人还没发过，然后读出来过后重新扔给他，那就实现一个离线留言了。就在这儿有办法。

#### 发送：注意连接方向是反过来的

那就直接创建一个 `Transfer` 实例：

```go
tf := &utils.Transfer{
	Conn: conn,
}
err = tf.WritePkg(data)
if err != nil {
	fmt.Println("转发消息失败 err=", err)
}
```

因为是你从这儿取出来的，从每个 map 里面的那个 `UserProcess` 里面取出来的。好，给它一个。有了它过后，不用二话，直接 `write` 发出去，把这个 `data` 发出去就可以了。发出去过后这边可能会有一个 `err`，但也可能没有，我们判断一下。

> **结论**：其实这段代码比原先要简单。但只有一点大家需要注意：**原先这个连接是直接拿来用的，但是现在变了，是我把这个连接通过参数传进去，在这个函数里面用这个连接去转发。因为这个逻辑跟原先刚好是反过来的。**
>
> 因为我这里面这个 `SmsProcess` 里面是没有连接的，所以说我把它遍历出来过后，通过这个参数塞进去，然后在这个函数里面我用这个连接再转发出去。这个很重要，大家好好想一想。

你比如说让你就开发一个项目，这个系统要解决一个什么问题？**哪个人来了，一个人来了在银行要去办业务，那办业务的话你得讲一个先后顺序，他会有一个号。** 比如说有一个业务员给一个客户 服务完毕过后，他按一下这个键，喊某某某某号到我这来服务，对不对？然后呢这个人走了过后，另外你有几个窗口，有五个、六个、十个都有可能，你下面排队的客户呢有很多，那哪一个人服务完了过后他就按一下那个红色按钮，说到我这来。

**其实呢，这个东西如果你学过队列的话，你就感觉有思路了。它倒不是很难，如果你学过这个队列，你会发现它其实就是个队列嘛。**

```bash
java MyBank
```

我运行一下。你们可以看到，我这里可以产生很多的分数。你看这个相当于是一个服务人员，他服务完了过后他就叫号，叫号过了这个就漂过去，最后服务完毕，他有一个服务时间，服务完毕过后大家都消失了。

> **结论**：**如果说这种系统的话，你要没有队列这个概念在里面，你会觉得怎么做到的？**

再比如说，**汉诺塔**。这是一个经典的**回溯**问题。我们以前呢同学们肯定都玩过这种小游戏——把 A 塔的盘子按照这个顺序搬到 C 塔，但是呢有一个前提：**这个小盘子才能放上面，大盘在下边，不能颠倒过来。**

像只有五个这样的盘子让你移动，一般来说我们人的大脑是可以反应过来的。**但是这个盘子要是 64 个的话，我估计一般人基本就 Game Over 了**，因为 64 个全部搬过去的话是一个非常复杂的过程，一般人肯定是不行的。

**但是如果你有这个递归回溯这种思想，你也能把它搞定。** 你看，他已经告诉你怎么做了，这个底层就是一个小算法——**其实它这里就用到一些递归的东西**。看到没有？它最后这个很标准的一步一步按照这个流程，**只要你告诉他怎么做，他就可以帮你把这个东西做完**。看到没有？大概是 20 多步，不到 30 步。**你看越到最后呢就越容易，越到最后就越容易了。**

当然这样的案例还有很多。以前 Google 专门搞了一个算法编程大赛，里面有很多经典的案例：**瓷盘问题、公交车问题、画图问题、矩阵、查询单词路径问题——也就是最短路径、荷兰旗问题、扔石头问题**，好多好多。

做游戏的一般都会考察你们的算法，除非是做界面的。**所以你看做游戏的一般他会要求是学 C、C++ 的比较多一点**，那这里边它也会用到我们的一些数据结构。

### 数据结构是干什么的

所以说我这总结了两点。

> **结论**：**第一，数据结构是一门研究算法的学科。** 只有自从有了编程语言，也就可以有了数据结构。

> **结论**：**第二，学好数据结构可以编写出更加漂亮、更加效率高的代码。**

比如说有时候你去看有些比较厉害的人写的代码，短短的 20 行，你看不懂他在做什么；有些 200 行你可能几分钟就看完了。**给你 20 行代码我告诉你，基本上你看不懂，就你不知道它在说什么——因为里面大量的都是调用递归或者是那个叠加的一些算法在里面，就很麻烦。但是呢这种代码往往比较有价值。**

学好这个数据结构呢，要多多地考虑**如何将生活中遇到的问题用程序去解决**。

#### "程序 = 数据结构 + 算法"？这话不完全对

曾经有一个老外——这个老外名字我都忘了叫什么——他说：**程序就等于数据结构加算法。**

当然他这个站在底层这个角度，其实这句话呢**也不能说完全正确，当然也不是错的**。核心可以这么说，你可以说程序的核心是这个；但是现在随着软件的发展，它融入了很多新的东西在里面——**你比如说界面它也很重要，业务逻辑也很重要啊**。他如果说程序只是等于数据结构加算法，那业务逻辑难道就不重要吗？有时候业务逻辑也是非常重要的。

**但是你的业务逻辑也要靠什么来支撑呢？也要靠数据结构加算法来支撑。** 你比如说有些同学学过像工作流这些东西，它里面也有大量的这些东西在里面。

### 算法是程序的灵魂

算法首先是程序的灵魂。什么叫算法呢？我举一个例子。

你比如说你将去做 Go Web 方面的开发，那么 Go Web 开发一定要解决几个大的问题：**高并发、海量吞吐。**

你 Web 服务器现在最牛逼的 Nginx 就是比较厉害，写得比较坚如磐石。大家可能会说：网站使用了这种服务器集群、数据库读写分离和缓存技术，比如说 Redis，那它就可以跑得很快了呀，就可以支撑这个大并发、大流量。**是的，你用了这些东西肯定是可以的。但是我们要深入地再问一句：这些优化技术又是怎么搞出来的呢？它的底层又是什么呢？**

**它还是最底层的那些算法。** 就是说它之所以去给你搞了一个集群，搞了一个读写分离，搞了一个缓存，**它也靠算法**。

最简单的一个例子：**读写分离的核心是什么？** 当你发的是 SELECT 语句的时候，我就认为你是读；当你是其他操作，我认为是写。**光这一个东西，它就有很多算法在里面。难道仅仅靠一个 SELECT 的一个关键词来判断吗？它肯定有些优化的东西。**

再比如说是集群：你集群完了过后，你同时跑了 16 个或者 32 个后台服务器，**那么我们用什么样的算法让各个服务器能够充分发挥它的最大效率，而且保证它的一个稳定性？**

再比如说有些同学说的像**测心跳**——有些服务器它为了防止宕机，它一般都会有一个备用服务器，发现有一个服务器宕机了，它立马就顶上去了。**那想想这些东西怎么做？肯定要用网络，咱们的网络肯定跑不了；它同时它还有一个算法，怎么样做？**

#### 我们刚写的"维护好友在线"，里面就有算法

旁的就不说了，就说我们现在刚刚写的**维护好友在线，它就有很多算法在里面。**

我们当时最经典的案例是这样子的：**比如说张三有一堆好友，那么这一堆好友，他的状态是不是我每隔五分钟要把所有的好友全部发上去问服务器要？** 这一堆好友是干什么的？——他是**分波要**的。

**他怎么分波呢？** 他先每次发 10 个过去；发 10 个过去过后，发现这 10 个要了几次都没有变化——他应该是这样子的：**刚开始他要的人很多，比如说你现在有 100 个好友，我可能第一次把 100 个全部发给你；服务器回过来的时候，它肯定用一个标识来标示它的状态。到了第二次我又要求的时候，发现其中有些状态是稳定的，我就要把这 100 个里面比较稳的筛出去，下次我就不要了。**

不要了过后，我再去要经常变化的人。**等到有一段时间我还要再算一下，以前没有要的东西，我用一个算法再把它提出来，我还要问他要一遍。**

他这里面就有很多东西在里面：**到底每隔多少时间要，而且要的时候是不是每次都向顶级服务器要，还是说中间做一个缓存？** 比如说我客户端做一个缓存，缓存的时候这个地方我每隔一定时间自动去——客户端偷偷地去定时地要一下服务器数据。

所以他里面有很多算法在里边。

### 为什么功能一样的代码，效率能差天壤之别

**我们再请大家思考一个问题，你们一定要去思考：为什么不同的人写出来的代码，从功能上看是一样的，但是从效率上却有天壤之别？**

这句话只有你去跟那些真正做过核心开发的人交流，你会有感受。

#### 我遇到过的那位真正的大牛

我的感受最深是在哪个地方呢？**我还是比较幸运的一个人。我之所以幸运是因为我参加工作的时候，确实遇到了真正的高手，不是假高手。**

现在动不动这个大牛那个大牛，很多，但是**真正的大牛其实挺少的。大牛是你写个 Hello World、或者说你不会的他会，那叫大牛？那不算大牛。**

**我参加工作的时候，直接带我的那个人，他就是新浪的第一任 CTO。** 以前老程序员是真的有本事，真是真才实学。但我不是说现在不行——**因为那帮老程序员他很多东西是没有地方查询，是靠自己去研发出来的。**

像现在，你在网上去找点资料，别人会告诉你这应该怎么做，也有书籍。**那帮老程序员他从 97 年、95 年开始搞这种程序的，他没东西查，全靠自己去研发——这个就很有能力了。**

#### 支撑千万在线的那个设计

当时我做服务器，环境是 Unix。当时它的功能是要**支撑上千万在线**，他是这样设计的。但实际上用户还没那么多，**不过它从效率上设计的规模是要上千万的**。

而且**他用的服务器都比较低端，为了节省成本，那几年没成本**。他从那边新浪出来过后，大概也就十几个人，资金也不是很充裕。

我说那现在我们要想这个程序怎么去跑。我写完了过后挺高兴，我就给他看一下。他说：

> **"你的代码不行。我一个很普通的 PC 机，我就要支撑 10 万在线，你这个设计肯定是不行的。"**

为什么呢？**第一个，你大量的数据都是走数据库，这一下就完了。**

我说走数据库有什么问题吗？**你走数据库本身是没问题的，但是当你量大的时候，你都走数据库的话，你想一想数据库根本就支撑不了。你的瓶颈就在哪呢？你的瓶颈就在你的程序和数据库之间，就是你数据的吞吐量在这挡住了。**

你可以扩带宽，其实外包这一层——就是前面这一层——可以用集群来解决。**现在其实最难的地方在哪里呢？现在最难的地方还是程序跟数据库的交互，很难去解决。同步怎么解决？** 光一个数据库，这么多并发都来了，全部都卡在数据库跑不了、跑不动，全部堵在那了。

所以现在你可以加带宽，带宽一加大流量没问题，**大流量我可以解决。大并发其实也不是问题，因为大并发我前面有很多负载均衡也可以解决。现在大型网站最难的地方还是在于程序和数据库。**

数据库的性能提不起来的话，一般都搞读写分离。**可是一搞读写分离又出现很多问题——什么问题呢？就是读写分离还有一个同步的问题。** 而且问题是，你数据表特别大的情况你还要分表。**你分完表了过后，你数据量再大你怎么办呢？你所有的优化，最终还是要落实到你的代码的算法上。**

> **结论**：就是能不能设计一种方案，**咱们减少对数据库的查询，同时还能够让程序正常运行**——这就是它的一个设计理念了。

#### 那句话和那辆车

为什么我当时给你们讲那个故事？**下面那个小伙子把我们这个方案一说，给朗讯的老板一说，直接当天就拍板让他去朗讯，当时年薪就是 20 万了。**

我每次就说这个故事。那小伙子，其实这些东西都是我们那个小组好多人一起想出来的，怎么去优化。**这些东西其实就是现在所谓的这些缓存产品。那个时候没有缓存产品，什么 Memcached、Redis 都没有，所以说那个都是程序员自己在想办法。**

所以我们就说了一句话：**当时我们认为程序是有灵魂的，是有算法的。如果你不想永远是个代码工人，那么就花时间要研究算法。** 这一天是你想往上走，最终一定要突破这个问题。

**如果说你是想在架构上、在效率优化上有所提升，你肯定要去多看一些这样的东西，否则你的代码肯定跑不起来。**

就好像两个人一样——**比如说我们说汽车吧，从外形上看大家都是奔驰，但是里面那个发动机完全不是一个档次，一跑起来，别人只要一开起来能把你扔到十万八千里去。从外形看他也奔驰，我也奔驰，你没看人家内核是什么？**

> **结论**：**程序对外行来说，看一个程序就看界面漂不漂亮；内行人家就干什么？测你的性能。**

### 大学里那些让人头大的作业

我现在来看几个实际编程中遇到的问题。

**比如说现在有个字符串，在进行 replace。那么现在我要求大家使用单链表来表示字符串类、字符串节点类的定义，并依次实现它的构造函数、计算长度，还有赋值、判断相不相等、求子串、两个数的连接等等七个成员函数。** 这些函数本身是由 API 给我们提供的，但是要你自己去实现。

你看当时我们在大学里面学的时候，我们也有很多作业，当时主要是集中在 C++ 里面的。我记得当时应该有一堆作业在里面。其中就有一个链表，其中一个链表它就出了一个这样类似的一个题，大概是在第六题，我还有点印象。当时这个用的是 C++ 来写的——**你看这东西看起来就吓人，C++ 这样子的。当时就给我们出了这么一个题，要用自己的数据结构来实现。**

最后实现的效果是这样子的。还让我们去搞一个叫做**多项式**，要求写一个算法，计算两个多项式的乘积，要用多项式来实现。一般人看完了过后……这个还算是简单的，它不算特别难的。**当然这个你要能写出来，肯定是需要好好地去想一想的。**

再比如说一个实际需求：**五子棋**。五子棋相对比较简单——五子棋就说它判断输和赢，你去写一个算法怎么判断输和赢，怎么效率更高一点。

#### 约瑟夫问题：用链表特别简单

再比如说**约瑟夫问题**，很经典的一个。**如果这个东西你要用链表来完成就特别简单；如果你没有学链表，你只能用数组来解决，数组解决起来就比较困难。** 你用数组解决这个约瑟夫问题，绝对它的难度不小。

它的经典案例是这样子的：它也叫**丢手帕问题**。**它设 1、2 到 n 围成一圈圈，约定编号为 k 的人从 k 这个人开始报数，数到 m 的人出列，然后下一个又从下一个人开始，又从 1 开始，又数到 m 又出列，最后问哪个人出列？最后留的是谁？**

你想想这就是个算法，你得去解决。**那么这个时候你可以用链表加上你的思想形成一个算法，算法就来了。那么每个人的算法可能就不一样，效率也会不一样。**

再比如说我们后面常见的算法问题：**瓷盘、公交车、画图、邮差、汉诺塔**，对吧？比如这个汉诺塔，那学完了过后汉诺塔你就能解决。

还有像这种实际的小游戏，像**华容道**，这些都可以用算法来解决。

### 三句话把它记住

大体我们把数据结构的一个需求简单说了下。你就记住这么一句话：

> **结论**：**第一句：你可以认为程序就是数据结构加算法。**
>
> **结论**：**第二句：数据结构和算法又是什么关系呢？数据结构是算法的一个基础。** 就是说你的算法建立在数据结构基础之上，这个算法就会相对来说实现得更容易。
>
> **结论**：**第三句：我们学完数据结构就可以解决这样的问题——当有一个实际需求摆在你面前的时候，你如果学了数据结构，你相对比较容易把这个算法写出来。**

明白我的意思吧？**相对而言你有工具了。**

就好像你有一天想去盗墓——**盗墓是不允许的，假如你去盗墓，赤手空拳去盗墓，进去 Game Over。** 有一天你发现当你盗墓的时候你有很多秘籍：第一个你有秘籍，第二个你有许多先进的工具，**比如洛阳铲之类的，一看我就没有干过；还有罗盘，一测这个地方有一个曾经死去过大官、皇帝的位置，位置能找到，然后洛阳铲一铲大概深度是多少，然后有一帮哥们儿帮你，你就很容易把这个墓给起起来，就是时间问题。**

如果你没有这些工具，你赤手空拳这个事你很难做。

**所以说算法和数据结构，数据结构是它的一个基础。但是你离开这个数据结构，你搞一个算法很吃力，就不搞这个东西。**

### 板书与推荐

大体就这样子的。我给同学们先把它板书一下——这个就叫我们的**数据结构**。我刚才介绍了什么东西呢？我先对大家说了一下数据结构的一个基本的概念，大家脑海里面稍微有一个概念的。

第二个我说了**数据结构是干什么的**，来做了一个基本的介绍。我总结了这么三句话——**第一句话它是研究算法的学科，但数据结构它不完全等于算法**：用数据结构来解决一个具体的问题，那个代码就可以叫一个算法。

大家以后就会慢慢有感受。**我相信我们班将来一定会有同学在编程这个道路上走得比较远，你们的成就将来肯定比我要大很多，我们班肯定有这样的同学。但是，你哪一天就一定要去研究这个东西。**

待会儿我再给你们推荐一些哪些东西要看。在笔记里面有其他几个东西，你们有时间去看：**一个是以后把编译原理看看；数据结构看好看编译原理，编译原理看完再去看看数值分析——但现在你们先不要去看数值分析。**

**数值分析它可以对你的程序比较精准地判断效率到底是什么样子的。编译原理可以让我们对编译器本身比较了解。** 当时我们学这个完了过后让我们自己写了一个 PL/0，就是写了一个编译器出来。**编译器还让我们一行一行说这是为什么**，就是 PL/0，当时我们写的。但这个我都忘了，我记得那段代码好像挺复杂的。

但是**编译原理你打开了过后你就觉得简直就像天书一样**。你可以看一下，上面文法和语法的形式定义、上下文无关这些。当时我们讲课基本上就是这样念一遍，念完了过后"你们听懂了吗？""我们听懂了。"——对，就是这样子的，**你们看了估计好多同学都懵圈了。**

当然你也不用把它吓得很害怕，其实我当时也没搞懂，到底什么意思我都看不懂。**之后我怎么搞懂的呢？最后还是靠老师说："你们现在懂不懂也无所谓，把编译器写出来就行了。"我们把编译器写出来，我们就懂了。** 最后就把它这个栈的关系各方面就理解得比较到位了。
