# 哈希表与二叉树遍历

## 哈希表

* **上机题与四个前提**

    * > **定义**：这道题考察的正是知识结构里有没有哈希思想——新员工来报到就把信息加入，输入 ID 要求查询到该员工的所有信息。

    * 员工信息包含 ID、性别、年龄、住址；演示时只添加 ID 和名字。

    * 四个前提缺一不可：不许用数据库（能查，但凭什么保证快）、要节省内存（不能拿大数组暴力铺）、速度越快越好（目标是 $O(1)$ 级定位）、原题要求自己设计（现成的映射不许用，考的是原理）。

    * > **结论**：如果允许直接声明一个以 ID 为键的映射，这题就不成立；它真正在问的是——能不能自己设计一个把数据摊开存放、还能按 ID 一步到位找到的东西。

* **三层结构**

    * > **定义**：散列表（Hash Table）是根据关键码值直接访问的数据结构，它通过散列函数把关键码映射到表中某个位置以加快查找。

    * 散列函数把数据分散到不同的存储位置，可能是链表也可能是数组，这里用链表。

    * 示意图上画的是 **16 根链表**，演示时只用 7 根。

    * 三层是一层套一层的：`HashTable` → `EmpLink` → `Emp`。

    * `HashTable` 本质是一个**链表数组**，结构体里只有一个字段 `LinkArr [7]EmpLink`；数组的每个元素本身是一条链表。

    * `EmpLink` 是雇员链表，结构体里只有一个字段 `Head *Emp`，实际就是一个头指针；它要挂很多方法，所以必须用结构体。

    * `Emp` 是具体雇员节点，字段有 `Id int`、`Name string`、`Next *Emp`。

    * > **易错点**：这套链表**不带表头**——第一个节点就直接存放雇员数据，不是先有一个空头节点再挂数据。带表头也行，这是设计上的选择。

    * > **结论**：手写结构体的顺序由依赖关系决定，谁用到谁谁就先写，本例是 `Emp` → `EmpLink` → `HashTable`。

* **散列函数**

    * > **定义**：散列函数回答「去哪儿」的问题，链表内部的有序性回答「怎么找」的问题，两个机制配合才让哈希表既快又可控。

    * 取模决定去向：`链表编号 = ID % 7`。

    * 举例：$7 \% 7 = 0$ 进第 0 根，14、28 同理；$8 \% 7 = 1$ 进第 1 根，22、29 也进第 1 根。

    * > **结论**：同一根链表里的 ID **不一定是连续的**（比如第 1 根里可能没有 29 而是直接放 36，因为 $36 \% 7 = 1$），但必须保证**从小到大**。

    * 这个散列函数很粗糙，水平高的程序员可以写出完全不同的算法——按 ID 散列、按名字散列、按 ID 加名字散列都可行；还可以做多级，模完之后再模。

* **快在哪一笔账**

    * 一根链表中串了 1000 个雇员时，不散列的单链表只能一个一个往后查，查 ID 等于 998 就要查 998 次。

    * 散列之后，存入 998 时就先算 $998 \% 7$ 把去向定死，查询时同样取一次模直接跳到指定那根链表。

    * > **结论**：从「一根链表里线性找」变成「七根链表里锁定一根」，理论上省了六七倍时间；原先花 7 秒，现在可能只花 1 秒。

    * > **结论**：哈希表就是把一条长链拆成若干条短链，再用一个便宜的取模运算把「在哪儿」一次性算出来——它的价值就是**用空间换时间**。

    * 长度 7 写完后想调整，把 7 一改成 70、700、7000 都能用，速度也会跟着上去，因为空间被有效利用了。

* **真正的用武之地**

    * 典型场景是维护用户在线状态：传统做法是状态一变就打数据库，同时在线一千万时冲击巨大。

    * > **定义**：用户状态不是特别重要的数据——要么离线、在线、繁忙，第一次没更新上、第二次来了再更新上就行，丢了也无所谓，不像存款余额那么重要。

    * 所以**经常操作、但又不特别重要、不是必须入库**的数据适合用哈希表来接。

    * 结构体只设计两个字段：用户 ID 用 `int`，状态用 `byte`，其中 0 表示离线、1 表示在线、2 表示繁忙。

    * 存进哈希表散列到 2000 根链表后：查询和修改状态理论上比以前快 2000 倍；读操作基本不用考虑并发问题，一万个人读、一千万人读都无所谓。

    * 内存账：按 `int` 占 8 字节、`byte` 占 1 字节算，一条状态 9 字节。

    * 一千万条状态占用的空间是 $1000\text{万} \times 9\ \text{字节} = 9000\text{万字节} \approx 85\ \text{MB}$。

    * 85 兆，再乘以 10 存一亿个在线用户也连 1 G 都不到。

    * > **提示**：散列的键不一定是 ID。想用名字查就先给名字算一个固定的值转成整数（很多算法能做到，比如生成一个唯一的 32 位整数）再取模。

    * > **提示**：全靠现成映射的话，上面两件事都做不了，这就是代码层面的优化。

## 哈希表的插入

* **先散列再委派**

    * 签名为 `func (this *HashTable) Insert(emp *Emp)`，参数一定要带指针，否则创建后会做值拷贝，更麻烦。

    * 第一步先用散列函数确定添加到哪一根链表：`linkNo := this.HashFun(emp.Id)`。

    * 第二步委派给对应的链表：`this.LinkArr[linkNo].Insert(emp)`。

    * > **结论**：真正干活的不是 `HashTable`；它在这里只做了一件事——散列，把它散开。不做散列的话它就是孤零零一个单链表，毫无意义。

    * 散列方法就是 `return id % 7`，返回一个 `int` 表示该扔到哪根链表。

* **有序插入：pre 与 cur**

    * > **结论**：有序插入是整个哈希表案例里最难的一个点，其他都不难。

    * 签名为 `func (this *EmpLink) Insert(emp *Emp)`，初始 `cur := this.Head`、`var pre *Emp = nil`。

    * > **结论**：之所以要 `pre`，是因为要保证插入后从小到大，而单链表没法自己知道前面是谁，所以必须有辅助指针始终保持在 `cur` 前面，两者同步往后走。

    * 空链表单独处理：`if cur == nil { this.Head = emp; return }`。

    * 非空时循环条件 `cur != nil`，命中 `cur.Id > emp.Id` 说明该插在 `cur` 前面，`break`；否则 `pre = cur`、`cur = cur.Next` 同步下移。

    * 循环退出只有两种可能：中途 `break` 插到中间，或一路走到 `cur == nil` 说明它最大、加到最后面。

    * > **结论**：这两种情况可以用同一段代码 `pre.Next = emp` 加 `emp.Next = cur` 处理——加到最后时 `emp.Next = cur` 等于赋成空，而它后面本来就是空的；不要为此写两份代码。

    * > **易错点**：退出条件用 `>` 还是 `>=` 取决于业务对重复 ID 的态度。默认假设 ID 唯一用 `>` 就够；一旦允许重复，必须明确「新来的覆盖旧的」还是「两个都留」，这会影响后面查找函数的返回值语义。

* **三种临界情况**

    * 拿一条 $3 \rightarrow 6 \rightarrow 9$ 的链表来验，三种临界点是中间、最前面、最后面。

    * 插到中间（加 4）：`cur` 指向 3 时 $3 > 4$ 不成立，`pre` 移到 3、`cur` 移到 6；$6 > 4$ 成立就 break，结果是 $3 \rightarrow 4 \rightarrow 6 \rightarrow 9$。

    * 加到最后（加 12）：三步比较都不成立，`cur` 走到空，循环结束，执行同一段插入代码，结果是 $3 \rightarrow 6 \rightarrow 9 \rightarrow 12$，代码与插中间那句一模一样。

    * 空链表：上来 `cur` 与 `pre` 都是空，直接 `this.Head = emp` 就把第一个节点放进来了。

* **那个特别不容易找的漏洞**

    * 链表里已经有 12，紧接着再加一个 ID **比 12 还小**的雇员，会把它踢掉。

    * 原因是循环判断的顺序只处理了空链表和插中间/最后，**没有处理「新来的比头节点还小」这一种插入位置**。

    * > **易错点**：此时 `pre` 初始仍是 `nil`，正确做法是 `this.Head = emp` 再 `emp.Next = cur`，而写成 `pre.Next = emp` 就是空指针 panic；原链也会因此断掉被破坏。

## 哈希表的显示

* **ShowAll：一次全打出来**

    * 签名为 `func (this *HashTable) ShowAll()`，就是一个 `for` 循环遍历整个链表数组。

    * 循环条件用 `len(this.LinkArr)` 做大小统计，不管有多少根全部显示，逐条委派 `this.LinkArr[i].ShowLink(i)`。

    * > **易错点**：下标 `i` 就是第几条链表，不要调错；把 `i` 作为参数传进去更方便，因为链表自己并不知道自己是第几条。

* **ShowLink：显示当前链表**

    * 签名为 `func (this *EmpLink) ShowLink(no int)`，空链表打印「链表 %d 为空，没有雇员」后返回。

    * 遍历时另起 `cur := this.Head` 当游标，只管往前走，**不动 `Head`**。

    * 打印格式形如 `链表 %d 雇员 id=%d 名字=%s -> `，结尾补一个换行，免得下一条链表全挤在一行。

    * > **结论**：上层的显示逻辑薄到可以忽略，真正有内容的是下层的空链表判断和游标遍历——这就是分层的舒服之处：上层只管「到哪儿去」，下层才管「怎么办」。

* **菜单与主流程**

    * 菜单四个选项：`input` 添加雇员、`show` 显示所有雇员、`find` 查找雇员、`exit` 退出系统。

    * `input` 分支先接收 id 和名字（id 初始化为 0、name 初始化为空串），构造雇员后交给 `hashtable.Insert(emp)`，底下散列、找链表、按序插入这一整套自动发生。

    * `show` 调 `hashtable.ShowAll()`，`exit` 调 `os.Exit(0)`，其余落到 `default` 打印「输入有误」。

    * > **提示**：`HashTable` 实例要定义在**外面**——它是整个程序唯一的那张哈希表，是一份被反复填充的数据而不是临时对象；它不需要显式初始化，里面都是值类型直接用就行。

* **落点验证**

    * 一上来先 `show`，输出的是七根链表全部为空的提示。

    * 输入 ID 为 1（汤姆），因为 $1 \% 7 = 1$ 落在链表 1；再输入 8（Jacky），$8 \% 7 = 1$ 也落链表 1，显示时在汤姆的后边。

    * 输入 89（Scott），$89 \% 7 = 5$ 落链表 5。

    * 测插到中间：链表 1 里已有 1 和 8 时加入 22（Mary）再加 15（史密斯），因为 $15 = 8 + 7$，所以 15 正好在 8 和 22 之间，链表 1 变成编号 1、8、15、22。

## 按 ID 查找

* **先定链表，再在里面找**

    * 菜单的 `find` 分支提示输入 ID 后，把这个 ID 传给哈希表的方法。

    * 签名为 `func (this *HashTable) FindById(id int) *Emp`，第一步 `linkNo := this.HashFun(id)` 定链表，第二步 `emp := this.LinkArr[linkNo].FindById(id)` 委派查找，最后返回。

    * > **结论**：先确定是哪一根链表——如果这根链表里找不到那就肯定没有了，别的链表肯定没有，哈希在这里就体现出应用优势。

    * 返回的是 `Emp` 指针，因为全过程都按引用方式处理。

* **链表里的遍历与两个出口**

    * 签名为 `func (this *EmpLink) FindById(id int) *Emp`，直接 `cur := this.Head` 开始循环。

    * > **提示**：查找不需要 `pre`——找到就找到了，找不到就找不到，所以没有前驱指针。

    * 循环体是命中 `cur != nil && cur.Id == id` 就 `return cur`，`else if cur == nil` 就 `break`，否则 `cur = cur.Next`；整个循环结束没返回值就 `return nil`。

    * > **易错点**：空指针判断不能省。空链表时 `cur` 本身就是空指针，如果只写 `if cur.Id == id` 就往下走，第一次上来就去取 `cur.Id`，直接空指针 panic。

    * > **结论**：关键不是 `else if` 能不能加，而是**让循环有两个明确的终止出口**——找到（return）、走到头（break）。

* **雇员自己报信息（ShowMe）**

    * 签名为 `func (this *Emp) ShowMe()`，绑定在雇员结构体上，打印格式与前面保持一致。

    * 它在哪一根链表里，直接用 `this.Id % 7` 就能算出来。

    * > **结论**：如果散列方法本身比较复杂，就没法简单取模，那时必须真的去调它——**散列函数一旦变复杂，这块跟着就要变**。

    * 调用方很简单：拿到指针为 `nil` 就打印「id 为 %d 的雇员不存在」，否则调 `employee.ShowMe()`。

* **查找验证**

    * 空链表是临界值最容易报错的场景：还没添加任何数据时 `find` 一个 10，输出「id 为 10 的雇员不存在」，没有异常。

    * 接着输入 ID 为 10（汤姆），它落在编号 3 的链表上，再 `find` 10 能在链表 3 找到。

    * 再输入编号较大的 8712（Scott），它落在编号 4 的链表上，`find` 8712 同样找到，位置也对。

* **删除的思路**

    * 删除作为练习留给大家，答案其实已经铺在正文里：和查找一样，先用散列函数确定是哪一根链表，再在那根链表里操作。

    * 只不过这次找到之后要做的是**重连指针**，而不是返回指针。

    * > **结论**：要注意的临界情况仍然是那三个——第一个节点（也就是插入留下的那个漏洞）、中间、以及最后一个节点。

## 二叉树

* **定义与术语**

    * > **定义**：二叉树的每个节点都有一个左指针和一个右指针，下一个节点同样有自己的左指针和右指针。

    * 与前面「横着长」的单链表不同，二叉树是「竖着长」的结构。

    * 最上面那个节点叫**根节点**，遍历要从根节点开始。

    * 没有子节点的节点称为**叶节点**。

    * 节点字段是 `No int`、`Name string`、`Left *Hero`、`Right *Hero`，一左一右两个指针。

    * 建节点时左右指针默认为空，此时还构不成二叉树，再把关系指过去才算成型。

* **三种遍历**

    * > **结论**：三种遍历的概念差别只有一个——**根节点被输出的位置在哪一位**；代码几乎一模一样，唯一的差别就是打印那一行放在哪、递归按什么顺序调用。

    | 遍历方式 | 顺序 | 专业词 |
    | :--- | :--- | :--- |
    | 前序 | 根 → 左子树 → 右子树 | PreOrder |
    | 中序 | 左子树 → 根 → 右子树 | Infix |
    | 后序 | 左子树 → 右子树 → 根 | PostOrder |

    * `Order` 就是遍历的意思；给一个根节点就能搞定。

    * 前序的函数体是先打印当前节点，再递归左子树，再递归右子树，整个过程是递归。

    * 中序唯一的变换就是把打印挪到中间；它的行为是**一直往下跑到最左边先打印**，然后回溯。

    * 后序把打印放到最后，也就是**先打左边、再打右边、最后打根**。

    * > **易错点**：递归调用时**必须传正在处理的那个子树指针**——写 `PreOrder(node.Left)` 和 `PreOrder(node.Right)`；写成 `PreOrder(node)` 就成了无限递归，栈会一直涨到爆。

* **四节点树的遍历结果**

    * 第一棵树的形状是：根宋江，左孩子吴用（无子节点），右孩子卢俊义，而林冲是卢俊义的右孩子。

    * 前序结果是**宋江、吴用、卢俊义、林冲**：吴用下面左子树为空就回溯到上面打卢俊义，卢俊义左边是空的再打林冲。

    * 中序是左子树 → 根 → 右子树，宋江先不打、先从最左边打起。

* **加两个节点后的完整验证**

    * 再在吴用下面挂两个节点编号 10（汤姆）和 12（杰克），左 10 右 12，林冲仍是卢俊义的右孩子。

    * | 遍历 | 顺序 | 编号序列 |
    | :--- | :--- | :--- |
    | 前序（根左右） | 宋江、吴用、汤姆(10)、杰克(12)、卢俊义、林冲 | 1、2、10、12、3、4 |
    | 中序（左根右） | 汤姆(10)、吴用、杰克(12)、宋江、林冲、卢俊义 | 10、2、12、1、4、3 |
    | 后序（左右根） | 汤姆(10)、杰克(12)、吴用、林冲、卢俊义、宋江 | 10、12、2、4、3、1 |

    * 前序：先宋江，再整棵左子树；打 10 之后它下面没有了就回溯到吴用的右边打 12；左子树打完再打右边，先卢俊义，林冲排在最后。

    * 中序：宋江先不打，跑到最左边先打 10，然后打吴用，再打 12，最后才打根 1；右子树是先打 4 再打 3。

    * 后序：先打 10 再打 12，然后打吴用；右边先打 4 再打 3；根节点最后打，所以是宋江。

    * > **结论**：面试里问到这三种遍历的含义要答得上来，可能是问答题也可能是选择题。

## 开发环境与插件

* **先调整设置**

    * 入口是「文件 - 首选项」里的设置，里面分成常用的编辑器、代码管理、工作台、窗口等分类。

    * 经常要改的几项：忽略缺失 Git 的警告、配置更新通道接受自动更新（用默认的 `default`）、启用 Windows 后台更新、扩展要不要自动更新、以及文件编辑里的「控制键入时是否应自动提示建议」。

    * > **提示**：「快速的建议」那一栏默认全是 `false`，是不对的，应该都打开；其中注释里不启用提示（`false`），字符串里启用为 `true`。

    * 改完保存并重新打开编辑器才会生效；其中「更新通道」一项会提示要重启，可以一并重启。

* **插件安装的硬前提**

    * 装 Go 相关的插件之前，**必须先装好 Git 并配置好环境变量**，否则装不上。

    * > **注意**：所有插件都是在 Git 之上安装的，Git 没配好它们不可能成功；看到类似版本号提示就说明 Git 装好了。

    * 右下角出现「分析缺失的工具」时，点它再点 `Install` 就能触发插件安装；安装需要联网，会比较慢。

* **装不成功怎么办**

    * 常见现象是**下载几乎都能成功，但就是没有安装成功**。

    * 第一步，切换到 Go 的源码目录下，可以看到里面确实有一个第三方插件目录，好多插件其实已经下载下来了。

    * 第二步，切到源码树里的 golang 目录执行一次克隆，把没有成功的包重新下载处理一遍，克隆之后会多出一个 `tools` 目录。

    * 第三步，把 `tools` 目录下的文件拷贝到工具链的 `x/tools` 目录下。

    * > **易错点**：执行克隆时报「不能切换克隆、无效的一个参数」，怀疑是路径末尾多敲了字符或空格，去掉后仍不行；克隆本身要等很久、进度条百分之一百分之二地爬。

    * 全部做完会得到一个完整的工作目录：源码树里的插件目录是完整的插件包，`tools` 里也是完整的工具包。

    * > **提示**：实在装不上（网络环境所限）可以直接用现成的整包，把项目重新定位过去；中间有个小坑——文件夹正被某个命令窗口访问时会被锁，要先退出窗口再改名。

* **装好之后能干什么**

    * 写一段对切片排序的代码，打出 `sort.` 时补全会列出全部可用方法，回车就自动把包引进来了；打 `fmt.` 同理。

    * 有时候反应会稍显迟钝，多敲一下就好了。

    * 第二个好处是**保存时自动格式化**，比如 `Ctrl+S`，以前要反复手动设置。

    * 第三个好处是**可以往里追源代码**：右键有「转到定义」，比如 `sort` 用的什么方法都能一步步追进去，包括快速排序是怎么实现的。

    * 第四个好处是**跨文件定位**：项目文件很多时，一个文件用到另一个文件里的函数也能定位到，哪怕相隔十万八千里或根本不在同一个文件。

* **常用快捷键**

    * 快捷键在「首选项 - 键盘快捷方式」里，数量很多而且都可以自定义。

    * 查法是直接输入命令名，比如输入 `delete` 就能看到「删除行」，默认是 `Ctrl + Shift + D`，改成别的组合回车即生效。

    * 常用的还有向上向下复制、补全代码自动补全、添加和取消注释（整体注释，再按一次取消）。

    * 格式化默认是 `Shift + Alt + F`，但因为保存会自动格式化，实际上用不着手动触发。

    * > **结论**：没有专门的快捷键文档也要心里有数——常用的就那么几个，需要时去查即可；而且导包是自动完成的，跟需要大量手写导入语句的语言不一样。
