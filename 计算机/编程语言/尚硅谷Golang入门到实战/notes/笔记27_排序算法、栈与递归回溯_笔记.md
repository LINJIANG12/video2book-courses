# 排序算法、栈与递归回溯

## 四种经典排序的定位

* **排序的四种常见方法**

    * > **定义**：排序是把一组数据按指定顺序排列的过程。

    * 最经典的是冒泡排序、选择排序、插入排序和快速排序四种，必须张嘴就来，因为后面要靠它们互相比较。

    * > **结论**：从速度上看，选择快于冒泡，插入又比选择快一些，快速最快。

    * 要求是选择与插入必须能默写出来，不参考任何代码也能写；快速排序不做默写要求，因为它确实稍微难一点。

    * 排序重要是因为它能锻炼编程思想，出排序题一般就是在这四种里选一个。

* **内部排序**

    * > **定义**：内部排序是把数据全部调入内存后再进行排序，冒泡、选择、插入、快速都属于内部排序。

    * 写一个函数来改变外面的数组时要注意：Go 的数组默认是值传递。

    * > **提示**：想让函数内部改动影响到外部，必须传指针；标准写法是 `(*arr)[0] = 600` 这种取地址形式，Go 编译器还做了优化支持 `arr[0] = 600` 的简写，两者等价。

## 选择排序

* **基本思想**

    * > **定义**：把「选」和「交换」拆成两步的排序方法——选是在剩下的乱堆里把最小或最大的挑出来，交换只在选中之后动一次手。

    * 第一次从 $R[0]$ 到 $R[n-1]$ 选出最小值与 $R[0]$ 交换，第二次从 $R[1]$ 到 $R[n-1]$ 选出最小值与 $R[1]$ 交换，依次类推，经过 $n-1$ 次就得到有序序列。

    * 要从小到大就把「最小」改成「最大」即可，代码其他部分不动。

* **落地代码**

    * 签名为 `func SelectSort(arr *[5]int)`，指针接收。

    * 第一步先假设当前下标上的元素就是最大值：`max := arr[0]`、`maxIndex := 0`。

    * 第二步遍历后面的元素，循环变量 `i` 从 `1` 开始（准确说是 $0 + 1$），条件是 `i < len(arr)`，这样最后一个下标取不到。

    * 命中 `if max < arr[i]` 时只更新记录 `max = arr[i]` 和 `maxIndex = i`。

    * > **注意**：循环里**绝对不要马上交换**——先不交换、先找到最大、最后只交换一次，这是选择排序的效率提升关键。

    * 循环结束后只有 `maxIndex != 0` 才执行一次交换 `arr[0], arr[maxIndex] = arr[maxIndex], arr[0]`。

    * > **结论**：交换很费时间，要尽量少发生；比较的效率比交换高得多，所以只在最后交换一次是刻意的设计。

    * 这种双变量交换写法等于把两个值对调，底层相当于用了中间变量或地址处理，以后发生交换都用这种写法。

* **从固定到循环**

    * 五个元素的例子要跑四次大循环，代码几乎完全相同，唯一变的就是那个下标值。

    * 把针对 0、针对 1、针对 2、针对 3 的四段统统注释掉，外面套上 `for j := 0; j < len(arr)-1; j++`。

    * > **结论**：循环上界是 `len(arr)-1` 而不是 `len(arr)`，因为最后一个元素不需要再排序，它没法跟谁比较。

    * 循环体内把所有写死的 `0` 换成 `j`，打印格式是 `第%d次`，其中 `%d` 取 `j+1`。

    * > **结论**：原先那一大段复杂代码就是一个 `for` 循环包出来的，整体过程就是先易后难、先死后活的层层分解。

    * 把数组扩成 6 个元素（比如补一个 `789`）并把类型长度改成 6，循环变成五次，结果 `789、100、80、34、19、10` 正确。

## 插入排序

* **基本思想**

    * > **定义**：把 $n$ 个待排序元素看成一个有序表加一个无序表，每次从无序表取出第一个元素，跟有序表的元素依次比较后插入到适当位置。

    * 开始时第一个元素自成一个有序表，无序表有 $n-1$ 个；它属于内部排序，要全部加载到内存。

    * 三个关键变量：先把待插入的值保存到 `insertVal`，把插入位置保存到 `insertIndex`（它是待插入元素的**前一个**下标），然后从有序区的**后面**开始往前比较。

    * 拿 23、0、12、56、34 从大到小举例：第一步把 23 当成有序表；第二步给 0 找位置，0 比 23 小，一比就定位，有序表变成 23、0；第三步给 12 找位置，先把 0 后移再跟 23 比，插在 23 后面变成 23、12、0。

    * 第四步 56 最难，要连续后移三四个元素，最后插到最前面变成 56、23、12、0。

    * 第五步 34 会依次让 0、12、23 后移，最后插在 56 后面变成 56、34、23、12、0。

* **落地代码**

    * 签名为 `func InsertSort(arr *[7]int)`，拿 7 元素数组做测试，补进 `-1` 和 `55`。

    * 外层 `for i := 1; i < len(arr); i++`，初值是 `insertVal := arr[i]`、`insertIndex := i - 1`。

    * > **提示**：外层从 1 开始是因为第一个元素自己就是有序的；内层初值是 `i - 1`，因为 `insertIndex` **始终指向待插入元素的前一个位置**。

    * 内层循环条件是 `insertIndex >= 0 && arr[insertIndex] < insertVal`，成立就执行后移 `arr[insertIndex+1] = arr[insertIndex]` 再 `insertIndex--`。

    * > **提示**：后移时先不要动 `insertIndex`；后移会覆盖掉原位置的值不用担心，因为 `insertVal` 已经单独保存好了。

    * 循环结束后插入，条件是 `if insertIndex+1 != i`，成立才执行 `arr[insertIndex+1] = insertVal`。

    * > **结论**：这个判断和前面的 `i - 1` 是同一个道理——待插入的值本来就该待在原位时，就不要再赋值一次。

    * > **易错点**：外层的 `1`、内层的 `i-1`、末尾的 `insertIndex+1 != i` 这三个数字分别代表「第一个元素已有序」「插入位置在待插元素之前」「原位不重写」，混淆就会写错。

    * 上界是 `len(arr)` 而**不是** `len(arr)-1`，因为最后一个元素也要参与比较。

    * 五元素数组跑完四次依次是：0 原地不动、12 插到 23 后面、56 一路后移到最前、34 插到 23 前面。

* **为什么它快一倍**

    * > **结论**：选择排序每一轮都要在无序区里把整个区间扫一遍，扫完才知道该换谁；插入排序每一轮只在有序区里从后往前找，找到就停，平均只扫一半。

    * 快的根源就是这个 $1/2$，不是玄学。

    * 每轮到底比较多少次不确定：运气好时比一次就退出，很倒霉时要把有序区遍历完。

    * 按概率折算下来比较次数除以 2，而冒泡和选择每轮都要遍历整个数组，所以插入排序的速度至少快一倍。

## 快速排序

* **基本思想**

    * > **定义**：对冒泡排序的一种改进——通过一趟排序把数据分割成两部分，使一部分的所有数据都比另一部分小，再对两部分分别递归快排。

    * > **结论**：它的思想要用到递归，理解难度比选择和插入大很多。

    * 一趟分解之后只是保证「比基准小的在左、比基准大的在右」，**左右两边本身仍然不是有序的**，还得继续分解。

    * 中轴（pivot，也叫支点）不一定非取最后一个数，案例中取的是中间位置的数。

* **三个变量与两头对撞**

    * 签名为 `func QuickSort(left int, right int, array *[6]int)`，左右下标加数组指针。

    * 局部变量是 `l := left`、`r := right`、`pivot := array[(left+right)/2]`、`temp := 0`。

    * 外层条件是 `for l < r`；`l >= r` 时说明两头已经扫描到中间，本次分解完成。

    * 内层第一段 `for array[l] < pivot { l++ }` 是从左边找到大于等于 pivot 的值。

    * 内层第二段 `for array[r] > pivot { r-- }` 是从右边找到小于等于 pivot 的值。

    * > **结论**：所谓「两头对撞」就是这个意思——一边找一个大的，一边找一个小的，找到就交换。

    * 用 `-9, 78, 0, 23, -567, 70` 演示时 $pivot = array[(0+5)/2] = array[2] = 0$，左边先找到 78，右边找到 -567，交换一次就得到 `-9, -567, 0, 23, 78, 70`。

* **交换、错位一步，然后递归**

    * 交换之后有一个优化判断：若交换完 `array[l] == array[r]` 就让 `l++`、`r--`，因为相等的元素下一次不必再比较。

    * > **易错点**：这个错位一步一定要加，否则相等的元素会互相卡住不动，一比较又相等，形成死递归。

    * 整个 `for l < r` 结束后，左右两边只是各自完成了「小的在左、大的在右」；这一步单独做完还不够，0 的左边不是有序的、0 的右边也不是有序的。

    * 递归写法是 `if left < r { QuickSort(left, r, array) }` 与 `if r < right { QuickSort(l, right, array) }`。

    * > **易错点**：递归条件不能写成 `left < r` 就完事，向左递归的下界必须是原始的 `left`，向右递归的右界必须是原始的 `right`；只开向左递归时右边完全没动过。

    * 只开向左递归的结果是 0 左边变成有序、右边保持原样；两边都开之后右边也从 `23, 78, 70` 变成 `23, 70, 78`。

    * 想改成从大到小，只要把比较符号反过来——从左边找小的、从右边找大的。

    * > **提示**：中轴基准不一定取中间，但用中间效率一般更高。

    * > **结论**：看不懂别人的代码时，把看不懂的先注释掉反而更快理解——快速排序剩下的部分无非是向左递归和向右递归，进去之后再分割，以此类推。

## 排序性能实测

* **计时台子**

    * 造 8 万个随机数：`var array [80000]int`，每项用 `rand.Intn(9000000)` 填充，范围越大越散、越容易体现速度差异。

    * 计时用 `start := time.Now().Unix()` 与 `end := time.Now().Unix()` 相减。

    * > **易错点**：8 万个数据绝对不要再打印，打印会拖慢到无法忍受，而且打印时间并不属于排序时间，输出会把测量污染。

* **实测数据**

    * 选择排序 8 万个数据第一次 12 秒、第二次 10 秒，数据散开之后耗时比较稳定。

    * 插入排序 8 万个数据 4 秒左右，再跑一次 5 秒左右，就在这个范围波动。

    * 快速排序 8 万个数据 0 秒——从秒的单位上看不到；扩到 80 万仍然是 0 秒；扩到 800 万是 3 秒。

    * 换成 800 万数据的冒泡的话，可以直接去吃饭了，吃完回来它还在排。

* **它快不是因为同时在排**

    * > **结论**：快速排序并没有多线程，它仍然是先把左边递归排完再去排右边，绝不是同时在排。

    * 快的原因有两层：一是找到中轴后左右两头同时扫描、扫描完同时交换，光这一下就比传统方法省很多时间。

    * 二是每扫描到一个中轴，比较次数就按**折半**的方式减少。

    * > **结论**：对比来看，选择或插入每排定一个数，下一次的比较次数只减少 1；快速排序是每轮直接减半——它的根本原因就是减少了比较和交换的次数。

    * 代价是资源消耗大，因为它开了很多栈：任务管理器里 CPU 一度蹿到 60，运行期间维持在 50 左右；选择排序只维持在 30 到 40，因为它不开栈。

    * > **提示**：想让多个协程同时排一个数组未必可行，因为要对数组加锁，一个协程在操作时另一个可能就动不了。

## 栈

* **定义与特征**

    * > **定义**：栈（Stack）是先入后出（Last In First Out）的一种限制性线性表。

    * > **易错点**：先入后出必须记牢——做表达式求值时忘了它，做减法结果会刚好反过来，$5 - 4$ 会算出 $4 - 5$。

    * 比喻是弹夹：往下压一颗再压一颗，打出来的是最后压进去的那颗。

    * 插入和删除只在同一端进行，这一端叫**栈顶**（top），另一端固定的叫**栈底**（base）。

    * > **结论**：栈底动不了，队列才有队头队尾，栈只有一个可动的一端。

    * 有些程序员把栈叫堆栈，严格来说栈和堆是有区别的，准确的叫法是栈，英文单词是 `Stack`。

* **用在哪**

    * 第一是子程序的调用：跳往子程序前先把下一条指令的地址压进栈，执行完再取出来回到原处，这就是 `return` 的底层动作。

    * 第二是处理递归调用：参数和局部变量都压进栈，每开一个新栈就把新变量压进去，所以数据相互独立。

    * 第三是表达式的求值和转换，第四是二叉树的前序、中序、后序遍历，第五是图的深度优先搜索。

    * > **注意**：写一个非常完整的表达式求值其实相当麻烦，因为还要考虑小括号、中括号、大括号，这里实现的那个版本只能做加减乘除。

* **数组模拟栈**

    * 结构体三个字段：`MaxTop int` 表示最多能存多少个、`Top int` 表示栈顶、`arr [5]int` 是数组本身。

    * > **结论**：结构体里不单独存栈底——因为栈底是固定不变的，只要知道栈顶在哪儿就知道栈底在哪儿。

    * 初始化是 `MaxTop: 5`、`Top: -1`，栈顶为 `-1` 表示栈为空。

    * 栈一般用数组模拟，也可以用链表或切片；链表最灵活，既能模拟队列也能模拟栈。

    * 空栈时 top 和 base 都是 `-1`；压入第一个元素时两者一起上移一位；之后再压只有 top 上移，base 钉死在 0；弹出一个时 top 下移一位、base 不变。

    * > **结论**：判断空栈看 `Top == -1`，判断满栈看 `Top` 有没有撞到数组的最大下标。

* **入栈与遍历**

    * 签名为 `func (this *Stack) Push(val int) (err error)`，返回 `error` 是因为可能栈满。

    * 判满条件是 `if this.Top == this.MaxTop-1`，因为下标到 4 时就等于 $5-1$，说明已经存满了。

    * 未满就先 `this.Top++` 再 `this.arr[this.Top] = val`，顺序不能反。

    * 签名为 `func (this *Stack) List()`，遍历**必须从栈顶开始**：`for i := this.Top; i >= 0; i--`。

    * > **易错点**：不能直接拿栈顶当循环变量去改，必须先把它赋给局部变量 `i`，否则栈顶被改动之后就不知道这个栈原先有多深了。

    * 先判 `if this.Top == -1` 打「stack empty」返回，否则逐个打印 `arr[%d]=%d`。

    * 实测按 1、2、3、4、5 顺序入栈，`List` 打出来正好是 5、4、3、2、1；再压第 6 个时报「stack full」。

* **出栈**

    * 签名为 `func (this *Stack) Pop() (val int, err error)`，至少要有两个返回值。

    * 先判 `if this.Top == -1`，打印「栈空, stack empty」并返回 `0` 和错误。

    * > **结论**：出栈必须**先取值再减栈顶**——`val = this.arr[this.Top]` 之后才 `this.Top--`。

    * > **易错点**：不移动栈顶就等于没弹出去，再次调用还会取到同一个栈顶。

    * 弹空的栈会返回 `stack empty` 错误；调用方必须用两个变量接收，不能只写一个。

    * > **结论**：栈最核心的三个操作就是 `Push`、`Pop`、`List`，后面做计算器全靠它们。

## 用两个栈求表达式

* **为什么要设计算法**

    * > **结论**：人眼一眼就能看出该先算哪一步，是因为眼睛能把整个算式一次扫完；计算机只拿到一个字符串，对它来说就像瞎子，不知道后面是什么。

    * 所以只给你看 `3 + 2` 你也不敢断定先算它，因为你不知道后面那个运算符的优先级是高是低还是相同。

    * 表达式用字符串传入时才需要栈，因为字符串本质上就是一个切片。

* **一条扫描线，两个栈**

    * 算法分两个栈：数栈 `numStack` 存数字，符号栈 `operStack` 存运算符；再加一个从 0 开始的 `index` 逐位扫描表达式。

    * > **提示**：先只考虑个位数字，多位数要另行处理拼接；做东西先做简单版本，想复杂了思路反而卡住。

    * 扫到数字直接入数栈，因为一个数后面跟着什么运算符还不知道，先存起来。

    * 扫到运算符且符号栈为空时，直接入栈。

    * 扫到运算符且符号栈不为空时，比较**栈顶运算符的优先级**与**当前运算符的优先级**：栈顶大于等于当前就赶紧算，否则直接入栈。

    * 用 $3 + 2 \times 6 - 2$ 演示：扫到 `3` 进数栈；扫到 `+` 时符号栈空，入栈；扫到 `2` 进数栈；扫到 `*` 时栈顶是 `+`，优先级低于乘，走「否则」分支直接入栈；扫到 `6` 进数栈。

    * 扫到 `-` 时栈顶是 `*`，优先级大于等于减，于是从数栈弹两个、再从符号栈弹一个做乘法。

    * > **易错点**：弹的顺序是先弹 2、再弹 6，而运算结果 12 要重新入数栈；算完之后当前这个 `-` 还没入栈，接着要把它压进符号栈。

    * 扫完最后一个数字后，扫描结束——符号栈里还剩东西，**第七个逻辑**是依次弹两个数、弹一个符号、算一次、把结果再入栈，直到符号栈为空。

    * 最后一次弹数弹出 2 和 12，做减法时是 **12 减 2**。

    * > **易错点**：一定是**后面弹出的数对前面弹出的数做操作**，这样 12 - 2 = 10 才是对的；再弹 10 和 3 做加法得 13，最终数栈里剩下的 13 就是结果。

    * > **结论**：三个分支是 if-else 关系——符号栈为空直接入栈；不为空时分成「栈顶优先级更高，先算」和「否则直接入栈」两条路。

* **三个辅助方法**

    * > **结论**：判断是不是运算符、执行运算、返回优先级这三个方法本身就是需要动脑筋才能想出来的。

    * `IsOper(val int) bool` 的判据是 ASCII 码：乘 42、加 43、减 45、除 47，只做加减乘除，取模那些先不做。

    * > **易错点**：这四个码很诡异——顺序是**乘、加、减、除**而不是中文说的加减乘除，而且**不连续**（42、43 之后跳过了 44 才是 45）。惯性思维写成 42、43、44、45 必然全错。

    * `Cal(num1 int, num2 int, oper int) int` 用 `switch` 分派：42 乘、43 加、45 减、47 除，`default` 打印「运算符错误」并返回 0。

    * > **结论**：`Cal` 里**永远把 `num2` 写在前面**，减法和除法必须是 `num2 - num1`、`num2 / num1`；乘加顺序无所谓但也按这个规矩写更安全，因为栈本身就是先入后出的。

    * `Priority(oper int) int` 自己定优先级：乘 42 与除 47 为 1，加 43 与减 45 为 0，其他默认 0。

    * > **结论**：这个优先级是程序员自己定的，非常有弹性，没有固定说法；将来要加括号，把括号的优先级定成 2 即可，底层就是这么干的。

* **从字符到 int**

    * 扫描取单字符用 `ch := exp[index : index+1]`，返回值是一个只含一个字符的字符串。

    * `IsOper` 要的是 `int`，所以必须先过一道坎：`temp := int([]byte(ch)[0])`，先转成字节切片，取第 0 个再转 `int`。

    * > **提示**：不转成 `int` 的话它是单个字节，传不进方法签名；这一步没突破，后面的表达式求值就写不下去。

    * 判断是不是运算符用符号栈来调更贴切，用数栈调也可以，因为方法本身与具体实例无关。

* **符号栈不空时的两条路**

    * 第一条路先判 `if operStack.Top == -1`，说明是空栈，直接 `operStack.Push(temp)`。

    * 第二条路取栈顶运算符的优先级 `operStack.Priority(operStack.oper[operStack.Top])`，注意这里**只是看没有弹**。

    * > **注意**：能走到这里数栈里一定有东西，如果没有只有一种可能——表达式写错了。

    * 弹栈的三句是 `num1, _ := numStack.Pop()`（先弹）、`num2, _ := numStack.Pop()`（后弹）、`oper, _ := operStack.Pop()`；`Pop` 的两个返回值要收掉，错误值直接忽略。

    * > **易错点**：变量必须按弹出的顺序赋值，因为运算方法里的顺序已经按后进先出颠倒过了，这里再错位整个结果刚好相反。

    * 算完 `res := operStack.Cal(num1, num2, oper)` 之后要把结果 `numStack.Push(res)` 重新压回数栈。

    * 压完结果**还没完**，当前这个符号自己还没入栈，必须再 `operStack.Push(temp)`，否则会少一个运算符。

    * 优先级不够高的分支是 `else`，直接入栈即可。

* **index 的自增**

    * > **易错点**：`index` 不能乱加，可能已经越界。

    * 先判断 `if index+1 == len(exp)` 说明已经是最后一位而且处理过了，直接 `break`；否则才 `index++`。

    * > **易错点**：只取一个就跳出的话 `for` 循环永远是死的，必须把取符号的逻辑整个放进循环体里。

* **扫描结束后清栈**

    * 退出条件是 `for operStack.Top != -1`，循环体与前面相同：弹两个数、弹一个符号、算、再压回数栈。

    * 这一轮与前面唯一的区别是**只有取没有压**，符号栈不再压入新符号。

    * 循环结束后数栈里必然只剩一个结果，`res, _ := numStack.Pop()` 打印出来。

* **两个真实的坑**

    * 第一次运行 $3 + 2 \times 6 - 2$ 算出来是 `2704`。原因是把数字字符也当 ASCII 码压进去了——`3` 压进去的是 51。

    * > **结论**：所以数字分支不能压 `temp`，要压字符的数值：`val, _ := strconv.ParseInt(ch, 10, 64)` 之后再转成 `int` 压栈，改完结果是 13；换成 `3+3*6-4` 得 17 也正确。

    * > **易错点**：多位数同样错——把 `3` 改成 `30`，`30+3*6-4` 算出来是 14，因为 `0` 根本没有被处理过。

    * 多位数的解法是加一个字符串变量 `keepNum` 做拼接，每次扫描先 `keepNum += ch`。

    * 判断数字何时结束要**往后探头一位**：如果 `index == len(exp)-1` 说明已到最后一位，不要再探，直接转整数入栈；否则看 `exp[index+1:index+2]` 是不是运算符，是就说明这个数结束了。

    * > **提示**：探头有风险，已经到最后一位再探会探到空指针，所以必须先判是否最后一位。

    * > **易错点**：入栈之后一定要 `keepNum = ""` 清空，否则会在上一次的基础上继续拼接。

    * 验证：$30 + 3 \times 6 - 4 = 44$、$30 + 30 \times 6 - 4 = 206$、再减去一个 6 得 200，都正确。

    * > **结论**：讲栈的目的有两个——体验运算的底层运行方式，以及体会栈的使用场景；要求写出来的是第一版，带各种括号的完整版属于扩展。

## 递归

* **定义**

    * > **定义**：递归就是函数或方法自己调用自己，每次调用传入的参数和变量都不一样。

    * 递归能让复杂问题变简单、代码变简洁，所以开发中用得很多，比如快速排序就用到了。

    * 现实问题里有大量自调用的逻辑：显示目录树、排序、二分查找都是。

* **栈里的机制**

    * 举例：函数接收 $n$，若 $n > 2$ 则先 `n--` 再调用自己，最后打印 $n$；传入 4 时的输出是 **2、2、3**。

    * > **结论**：这里其实就是栈在起作用——程序开始执行时有一个主栈，主栈里有 $n = 4$，调用时开辟新的栈空间并把新栈压在上面，因为栈是先入后出的。

    * 第一层栈里的 $n$ 也是 4（值传递），两个 $n$ 互不打架；判断大于 2 后执行 `n--`，减的是**这个栈里的 $n$**，变成 3。

    * 第二层栈里 $n = 3$，同样 `n--` 变成 2；此处代码还停留在调用那一行。

    * 第三层栈里 $n = 2$，不满足条件，直接往下走到打印，输出 2；该栈执行完毕后栈顶回退到第二层。

    * 第二层继续往下走到打印，输出它自己的 2，再回退到第一层；第一层输出它的 3，然后回退主栈退出。

    * > **易错点**：`n--` 减的是当前这一层栈里的 $n$，不是外面那个；不弄清这一点，后面的迷宫问题会非常难理解。

    * 同一个例子加上 `else` 把打印放进 `else` 分支之后，结果只剩一个 2。

    * > **结论**：一是各层数据相互独立，二是各层代码按各自的条件执行——进了 `if` 的那几层不会输出，所以最终只有栈顶那一层打印了一个 2。

* **四条必须记住的原则**

    * 第一，递归调用函数时会创建一个受保护的独立空间，底层靠保存现场、记录返回地址并压栈来实现返回。

    * 第二，函数的局部变量互相独立，即使变量名相同也不影响；但有时恰恰要利用「各栈共用同一份数据」这个特点。

    * > **结论**：快速排序里每个栈用的是**同一份数组**，所以要传引用；迷宫问题也**必须传同一份地图**，否则就出问题了。而像 $n$ 这种每层都不同的变量就该用值传递。

    * 第三，递归必须向退出条件逼近，否则就是死循环——这也是为什么示例里要减减而不是加加。

    * > **结论**：看到某一行被反复执行、程序停不下来，基本都是死循环；退出条件必须自己分析出来，迷宫问题里就是「什么时候找得到路、什么时候确实找不到」。

    * 第四，函数执行完毕或遇到 `return` 就返回，返回给谁就调用谁；同时这个函数本身也会被系统销毁、空间被回收。

* **递归能解什么**

    * 经典问题有八皇后、汉诺塔、阶乘、迷宫、球和篮子（在 2005 年 Google 编程大赛里出现过），栈的一些问题也能用递归简化。

    * > **结论**：一条是「凡是逻辑上重复的地方都能用递归」，另一条是「能用栈解决的问题可以再用递归简化」。

    * > **结论**：写代码的前提是程序员自己知道怎么做——如果连汉诺塔三个盘子都玩不过去，就不可能把它写成代码。

## 迷宫回溯

* **地图与四个数字**

    * > **定义**：用一个二维数组模拟迷宫，行列刚好对应；案例是 8 行 7 列，设计两堵红墙。

    * 用 `int` 的不同取值表达不同状态：**1 是墙**（必须设墙，否则到处是通路、不知道何时停）、**0 是没探过的路**、**2 是通路**（最终会连成一条由 2 组成的通路）、**3 是死路**（走过但走不通）。

    * > **结论**：`3` 这个标识是回溯的思想所在——进去发现走不通就退回来，得插个旗子标一下走过但不通，否则会反复再走一遍。

    * 建墙的规律是四边最上、最下、最左、最右全是墙；最上最下用列的循环置 1，最左最右用行的循环置 1。

    * > **提示**：因为地图是 8 行 7 列，两次循环的边界不同——置最上最下时列循环到 7，置最左最右时行循环到 8。

    * 四个角会被重复设置一次，但不去判断也无妨。

* **SetWay 的三层判断**

    * 签名为 `func SetWay(myMap *[8][7]int, i int, j int) bool`，函数名也可以叫 `FindWay`。

    * > **结论**：地图必须用引用传进来——每层递归都要指向同一张地图，否则每层都复制一份就彻底乱了。

    * 第一层判断 `if myMap[6][5] == 2` 就返回 `true`，表示找到出路了。

    * 为什么是 6 和 5：那是第七行第六列，下标从 0 开始算是 6 和 5；为什么判 2：是因为前面把 2 定义成了通路，如果规则里 5 表示通路那就该判 5。

    * > **结论**：递归必须先分析出「什么时候算找到」，这一条是最重要的。

    * 第二层判断 `if myMap[i][j] != 0 { return false }`——不是 0 在初始情况下只能等于 1，也就是一堵墙，根本没法探。

    * 第三层是「先假设它通」：直接 `myMap[i][j] = 2`，但这只是假设，实际通不通必须靠探测来证明。

* **四个方向与死路**

    * 探测策略由四个 `else if` 串联组成，依次是 `SetWay(myMap, i-1, j)`、`i+1, j`、`i, j-1`、`i, j+1`，即上、下、左、右。

    * > **结论**：这里返回的 `true` 是一路递归下来的——只有整条路真的通，才会一层层返回 `true`；不要理解成只有某一层返回。

    * 下一个方向是在上一条走不通时才尝试的，向下走进入下一层之后又按同样顺序重新探，不是直着往下走到底。

    * > **结论**：正因为四个方向是 `if else if` 串联，一个方向成功就不再往下试，代码一点都不能错，顺序错路径就全变。

    * 四个方向都不通说明这里是一条死路，把刚才「假设通」的 2 推翻，改为 `myMap[i][j] = 3` 并返回 `false`。

* **策略决定路径**

    * 起点固定是 `(1, 1)`，调用时传地址 `SetWay(&myMap, 1, 1)`。

    * 最初的策略是上右下左，跑出来的地图显示它反复向上探，路径很别扭——这说明策略选得不好，而不是代码错。

    * 把策略换成**下、右、上、左**之后，跑出来的 `2` 连成的线与人工推演的路径完全一致。

    * > **结论**：路径长什么样完全由程序员设定的探测策略决定，不同策略结果不同；这是因为小球每到一个点都按同一套优先级顺序试。

    * > **结论**：人走这张图时很容易看懂，程序走就容易懵，所以调这类程序前最好自己先人工推演一遍。

* **彻底堵死的地图**

    * 再加两堵墙（比如把 `(1, 2)` 和 `(2, 2)` 设成 1）就能把入口彻底封死。

    * 实测没有出现死循环，函数正常退出来了。

    * > **结论**：退出只能是从那条 `return false` 退的——`else` 分支进来之后只能一路返回 false，不停地回溯，直到所有可能都被排除。

* **最短路径的思考题**

    * 题目是在这套代码基础上求出最短路径。

    * > **结论**：这是个正经题目，因为策略对路径影响很大，迷宫大了挡板多了之后不可能靠人数路。

    * 现实意义是公交站最短路线规划——从 A 站到 K 站有大量节点，不能靠人一条条数。

    * > **结论**：老师给的最笨办法是穷举——把所有路径都走一遍存进一个 `map`，最后看哪个最短。

    * 方法虽然笨但已经解决了问题，优化要牵涉很多数学算法；先用最笨的办法做出思路，再往优化方向探。
