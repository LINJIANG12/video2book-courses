# 网络编程与 Socket 通信

## 网络编程的两大结构

* **C/S 结构（Client/Server）**

    * > **定义**：客户端把数据先发给公网上的服务器，由服务器做中转再送达对方，程序上要同时写客户端和服务器端两套代码。

    * 中转的两种常见方式：把数据放进数据库，让对方去数据库取；或者建立一个 Socket 在内存里直接传过去，实时性更强但难度更大。

    * 聊天程序是最经典的综合案例，QQ 本身就是一个 IM 程序；几乎讲 TCP 编程都会用这个案例，因为它能把所有知识点串起来。

    * > **易错点**：客户端 A 直接把数据发给客户端 B、B 再直接回给 A，那不叫网络编程，那叫对讲机。

* **B/S 结构（Browser/Server）**

    * 底层同样由 TCP/IP 协议支撑，只是在上面包装成 HTTP 协议，因此属于 Go Web 的范畴。

    * 与自定协议的唯一差别是发送的协议变了：从自己定义的协议换成大家都遵守的标准超文本传输协议。

    * 学透 TCP 编程之后再学 HTTP 和 Web 编程，认识会更深一层，TCP 始终是基础。

## 协议

* **协议（Protocol）**

    * > **定义**：协议是通信双方都认同、都认识、都能识别的约定。

    * 类比：人与人靠语言交流，语言就是一种协议；中文、英文、越南语这些具体的语言，就是一条条具体的协议。

    * 分公认与自定义两类：HTTP、FTP、HTTPS、SMTP 是大家都认可的通用协议；自己定义结构体当作协议也是完全可以的。

    * 做网络编程必须学会自定义协议。

* **用结构体自定义协议**

    * 一般一个结构体就足以描述一个完整协议，双方都认同即可。

    ```go
    type Message struct {
    	Id      int
    	Content string
    	Time    string
    	To      map[string]string
    }
    ```

    * `Id` 是 `int` 类型的消息编号，`Content` 用 `string` 记录消息内容，`Time` 用 `string` 记录发送时间。

    * `To` 表示接收者，用来区分发给张三、发给李四还是群发。

    * > **易错点**：接收者既可以用数组也可以用 `map`，用 `map` 才能同时表达"发给某个人"和"群发"这两种情况。

    * 对方拿到消息后读取里面的内容并显示，协议就闭环了。

## TCP/IP 分层与数据封装

* **TCP/IP 协议族（Transmission Control Protocol/Internet Protocol）**

    * 全称是传输控制协议和网际协议，这两个只是最有代表性的两个，TCP/IP 实质上是一族协议。

    * 在电脑上分成四层：应用层（Application）、传输层（也叫 TCP 层）、网络层（也叫 IP 层）、链路层。

    * 链路层之下直接对应网卡，网卡是硬件设备。

    * 每台电脑都装有 TCP/IP，在本地连接属性里能看到 IPv4 和 IPv6 两种形式的这套协议。

    * > **易错点**：TCP/IP 是必装协议，根本删不掉；真卸掉之后电脑就完全没法进行网络通信了。

* **OSI 模型与四层简化**

    * OSI 模型是最早由美国一个标准化组织提出的网络分层模型，一共七层：应用层、表示层、会话层、传输层、网络层、数据链路层、物理层。

    * 真实环境里做了简化，只保留应用层、传输层、网络层和链路层四层。

    * 做运维的人必须把这一套分层学得很透。

* **往下走：逐层加头**

    * 数据每往下一层就在前面加一个头，到链路层再补上帧头帧尾，加完之后变成一帧二进制数据，这才是最终发出去的东西。

    ```text
       走到哪一层                        此刻这个包长什么样
       ------------------------------------------------------------------
       起点                              [ "Hello" ]

       应用层  Application          +    [ APP头 | "Hello" ]
                                         APP头：表明是哪个程序发过来的

       传输层  TCP                 +    [ TCP头 | APP头 | "Hello" ]
                                         保证数据包准确地送到对端

       网络层  IP                  +    [ IP头 | TCP头 | APP头 | "Hello" ]
                                         IP头记录两样：我的 IP、对方的 IP

       链路层                       +    [ 帧头 | IP头 | TCP头 | APP头 | "Hello" | 帧尾 ]
                                         加了帧头帧尾就"变成一帧数据"
    ```

    * 各层职责：APP 头告诉对方是哪个程序发来的；TCP 头负责把包准确送到对端；IP 头记录双方的 IP；链路层加帧头帧尾把包变成一帧。

    * 能准确定位到对端，靠的是每个网络都有一个独一无二的 IP 地址。

    * > **易错点**：包在网络某处被截获后头部可以被改写，包就会被送到别的地方去，网络世界的风险很高。

* **往外走：网卡、网关与路由器**

    * 数据交给网卡后，局域网里由网卡对接网关；出了网关就是大量的路由器，每个路由器都有自己的 IP 地址。

    * 一个包要到达对端要经过很多路由，具体经过多少个事先是不知道的。

    * > **结论**：到站点的最终地址是明确的，途中显示超时的那些跳只是路由器不支持或不返回这条追踪指令。

* **tracert 追一个包**

    * `tracert` 里 `trace` 是追踪，`rt` 是 router（路由）的简称，Windows 和 Linux 都能用它追一个包的完整路由路径。

    ```text
       hop   看到的地址            说明
       -------------------------------------------------------
       1     192.168.4.3           第一个出口，进了内网
       ...   192.168.53.x          还在内网里面跑，不知道跑哪儿去了
       ...   (超时)                路由器不支持/不返回这个指令
       ...   ...
       末    111.13.101.x          快到目标站点
       -------------------------------------------------------
       一共大概十来个，12 个，有时候八九个就到了
    ```

    * 出现超时不代表包没过去，而是路由器不响应这个指令、不返回包。

    * 出现 192.168.53 这类地址说明包还在内网里跑，最终目标是那个公网地址。

    * 有些地址会被伪装或隐藏，本是公网地址却返回内网地址。

    * 追美国站点（比如亚马逊）经过的路由会更多，通常有十二个左右。

    * > **提示**：每一次的路径不一定完全相同，这次走这十二个，下次可能走另外十二个。

* **假网关广播事故**

    * 有人写了一段不停发广播的代码，一直宣称"我是服务器""我是网关"，整个公司的人都去问他，结果正常的包一个都出不去，连网都上不了。

    * 原因是他本身没有路由能力，却占据了网关的位置；类比是在电梯口拦住所有人说"门堵了走那边"，而那边是死路，结果全堵在里面。

* **往回走：逐层拆包**

    * 接收方做完全相反的处理：链路层去掉帧头帧尾，IP 层去掉 IP 头，传输层去掉 TCP 头，应用层去掉 APP 头。

    * 每层都要校验"这是不是给我的"，最后由应用层决定交给哪个程序。

## IP 地址

* **IP 地址（Internet Protocol Address）**

    * > **定义**：因特网上的每一台主机和路由器都有一个 IP，它由网络号和主机号组成。

* **IPv4**

    * 全称里的 4 指 4 个字节，也就是 32 位。

    * 地址总量上限是 $2^{32} = 4294967296$，折合 42 亿个，根本不够用；当时预计 2008 年前后整个地址空间就会用光。

* **IPv6**

    * 按 128 位计算，文档里的说法是"每平方米放一台电脑，整个地球都能放满"，所以足够用。

* **查本机 IP：ipconfig**

    * `ipconfig` 用来查看自己的 IP 地址，输出里会同时出现 IPv6 和 IPv4 两种地址，这是每个同学都要会的基本指令。

## 端口

* **端口（Port）**

    * > **定义**：这里说的端口是 TCP/IP 协议中的逻辑端口，不是电脑上物理意义上的插口；它是其他程序与该服务通信的通道，没有它就没法玩。

    * 一台电脑相当于一个房间，IP 地址就是房间号；一台电脑共有 65535 个端口，即 $256 \times 256$，当时把 0 也算了进去。

    * 端口通过端口号标记，端口号只有整数，没有小数。

    * 每个服务程序相当于房间里的一只耳朵，客户端发来的包就是靠端口号区分该交给 Tomcat 还是交给 MySQL。

    ```text
            你的电脑  =  一个房间，IP 地址就是它的房间号
       +--------------------------------------------------------------+
       |                                                              |
       |   +---------------+  +---------------+  +----------------+   |
       |   | Tomcat         |  | MySQL         |  | 聊天服务器      |   |
       |   | 监听 8080(耳)  |  | 监听 3306(耳) |  | 监听 8888(耳)  |   |
       |   +-------+-------+  +-------+-------+  +--------+-------+   |
       |           |                   |                   |           |
       +-----------|-------------------|-------------------|-----------+
                   |                   |                   |
            客户端(随机端口)      客户端(随机端口)      客户端(随机端口)
                1245                  7861                   ...
    ```

* **监听即占用**

    * > **定义**：只要是做服务的程序，一定会监听一个端口，这是重要原则。

    * "监听"可以简单理解成"占用"，一个端口一旦被某个程序监听，其他程序就不能再在这个端口上监听。

    * > **易错点**：聊天系统启动一次后再启动第二次就会报错，原因就是那个端口已经被占用了。

    * 做服务器要尽量少开端口；发现某个平时没开的端口莫名其妙打开，就是风险信号，可能是木马在搞事。

    * 装操作系统一律装纯净版、不装插件版本，多打开一个端口就多一分风险。

    * `netstat -an` 可以查看本机有哪些端口在监听，出现 `LISTENING` 的那一行后面就是端口号。

    * `netstat -anb` 能进一步看到是哪个程序占用了端口，比如能看到 135、443 在监听，也能看到 2425、6691 这类程序自带的监听。

    * 木马程序起来之后会偷偷扫描电脑，按密码、账号、隐私这类关键字搜到文件就送到远端公网服务器，而那个服务器正开着端口在监听。

* **客户端也有端口，而且是随机分配的**

    * 服务端在 3306 上监听之后，客户端连接上来时自己也有一个端口。

    * 这个客户端端口由 TCP/IP 协议在连接建立后随机分配，落在可分配的范围内，具体号码事先不确定，比如可能是 7861。

    * 服务端回数据时同样是靠这个客户端端口找到对方，再把数据推回去。

* **端口的三类划分**

    | 范围 | 名字 | 谁能用 |
    | :---: | :--- | :--- |
    | 0 | 保留端口 | 不能用 |
    | 1 - 1024 | 固定端口，又叫有名端口 | 某些程序固定使用，程序员一般不能用 |
    | 1025 - 65535 | 动态端口 | 程序员可以编程使用，可以指定监听哪个端口 |

    * 常见固定端口：22 一般不让用，23 是 Telnet，21 是 FTP，25 用于收发电子邮件，80 一般是 IIS，7 是 echo 端口。

    * > **提示**：自己指定监听端口时尽量往大了取，一般至少四万以上，一般人不会用到，这样不容易冲突、监听时也不容易报错。

## Socket

* **Socket（套接字）**

    * > **定义**：之所以叫 TCP Socket 编程，其根本原因是它底层用的是 TCP/IP 协议；这里把 TCP Socket 编程简称为 Socket 编程。

    * 结构上客户端可以有多个，都与同一个服务器端建立连接，每条连接对应一根线。

    * 连接理论上不会自己关闭，只要连上了原则上就不关，是长连接；关闭的时机只有两个：一方主动关闭，或者长时间没有数据触发超时。

    * HTTP 协议一般是连上过后把数据一发就关了，TCP 的长连接特性与之不同。

    * 连接建立后双方可以互发数据，数据在这根管道里流动。

    * 每条连接彼此是可区分的，能分辨数据是客户端 A 发的还是客户端 B 发的，靠的就是 TCP 本身。

* **一个连接一个协程**

    * 服务器主线程循环 `listen.Accept()` 等待连接，来了 A 客户端就为 A 起一个协程，来了 B 再为 B 起一个，形成分支结构。

    * > **易错点**：不能让服务器主线程一直为某一个客户端服务，那样会造成阻塞；服务器运行期间主线程不能死掉。

    * 真正通信仍然走同一个监听端口，端口始终在；区别在于通过端口拿到连接，而真正读写数据由协程在两端之间交互。

    * 类比前台接待：张三来办事就让他去 101 房间找某某某，再来一个客户就安排他去 102 房间，来多少个客户端都无所谓，这就实现了并发。

    ```text
                         server 主线程
                      listen.Accept()  循环等待
                              |
              +---------------+---------------+
              |                               |
         来了 A 客户端                  来了 B 客户端
              |                               |
       go func(){ 服务 A }           go func(){ 服务 B }()
              |                               |
       连的是 8888 端口               连的还是 8888 端口
       服务的是这条 goroutine        服务的是这条 goroutine

         前台接待：张三来办事 -> 让他去 101 房间找某某某
                  又来一个客户 -> 让他去 102 房间
    ```

## net 包

* **net 包**

    * 提供可移植的网络 I/O 接口，包括 TCP/IP、UDP、域名解析、Unix domain sockets 等；做网络开发时需要的所有方法和函数都在这个包里。

* **三个核心函数**

    | 函数 | 谁用 | 干什么 |
    | :--- | :--- | :--- |
    | `Dial` | 客户端 | 和服务器建连接 |
    | `Listen` | 服务端 | 返回一个本地网络地址监听的 `Listener` |
    | `Accept` | 服务端 | 等待并返回下一个连接到该接口的连接 |

* **Listener**

    * > **定义**：`Listen` 返回的就是 `Listener`，它是一个接口，相当于有人支棱着耳朵在等着。

    * 第一个参数填监听协议，可以是 `tcp`、`tcp4`、`tcp6` 等；第二个参数是地址，表示在哪个 IP 的哪个端口上监听。

    * 监听成功返回一个 `Listener`，失败返回一个 `error`。

    * 连接成功后可以通过 `Listener` 拿到网络地址，也可以通过它去 `Accept`。

    * `Close` 关闭该接口，会让任何阻塞中的 `Accept` 不再阻塞并返回错误。

* **服务端监听的写法**

    ```go
    listen, err := net.Listen("tcp", "127.0.0.1:8888")
    if err != nil {
    	fmt.Println("listen err", err)
    	return
    }
    fmt.Printf("%v\n", listen)
    defer listen.Close()

    for {
    	conn, err := listen.Accept()
    	if err != nil {
    		fmt.Println("Accept err:", err)
    	} else {
    		fmt.Printf("Accept 成功，conn = %v\n", conn)
    	}
    }
    ```

    * 第一个参数 `tcp` 表示用 TCP 协议交流，别的协议不认，发 HTTP 协议过来是不认的；`127.0.0.1:8888` 表示在本地监听 8888 端口。

    * `defer listen.Close()` 保证 main 不退出就不关闭，属于及时、延迟关闭。

    * `Accept` 在没人连接时会阻塞在那里一直等，所以必须放进 `for` 循环。

    * > **易错点**：`"tcp4", "127.0.0.1:8888"` 只支持 IPv4；`"tcp", ":8888"` 同时支持 IPv4 和 IPv6 更严谨，用 tcp4 的话对方走 IPv6 就可能连不上。

    * 监听失败必须 `return`，因为监听都不成功，后面的代码没必要再跑；比如同一个端口连续监听两次就会失败。

    * > **易错点**：监听成功后程序立刻退出是没有意义的，必须靠 `Accept` 循环把进程堵在那里持续等待。

    * > **易错点**：`Accept` 出错不需要 `return`。A 客户端连上了、B 没连上，不能因此把 A 也干掉；并发一万只有一个没连上，重连一下即可，打个警告就行。

* **Conn 接口**

    * `Accept` 返回的就是 `Conn`，它是实现了 `net.Conn` 接口的实例，里面有大量需要的东西。

    * 有了连接就能读能写，就像打电话一样，既能说也能听。

    * `Close` 关闭连接；`LocalAddr` 拿本地地址，`RemoteAddr` 拿对方地址，可以据此踢掉特定来源，比如凡是 `192.168` 开头的连接直接 `Close` 掉。

    * `Set` 用来设置周期，用得相对少一些；`Read`、`Write`、`Close`、`LocalAddr`、`RemoteAddr` 这几个用得特别多。

    * 学 TCP 编程比学 HTTP 编程痛快，因为这些底层的东西在 HTTP 里以前都看不到。

* **telnet 测一根线**

    * `telnet` 是远程连接指令，也可以专门用来测试某个端口是不是在监听，例如 `telnet baidu.com 80`，连上就说明对方 80 端口确实在监听。

    * 退出 telnet 要按 `Ctrl` 加中括号，`Ctrl+C` 在里面不管用。

    * `telnet 127.0.0.1 8888` 可以验证自己的服务器是否监听成功，连上之后服务端会立刻打印出一条新连接。

    * > **易错点**：别人的机器不能写 `127.0.0.1`，那是你自己的地址，要写对方的内网 IP 才能连上。

## 客户端发一行数据

* **net.Dial 拨号**

    ```go
    conn, err := net.Dial("tcp", "127.0.0.1:8888")
    if err != nil {
    	fmt.Println("client dial err=", err)
    	return
    }
    fmt.Println("conn 成功=", conn)
    ```

    * 第一个参数写协议，第二个参数写服务端的 IP 加端口；成功返回一个 `Conn`，就是那根连接起来的线。

    * > **注意**：一定要写服务端的 IP 加端口，一个 IP 上可以跑几万个程序，只给 IP 根本不知道要找哪一个。

    * 拨号失败必须 `return`，连都连不上就什么也干不了；`127.0.0.1` 是本地地址，这样写更准确、兼容性也更好。

    * 正式的 IP 地址不能写死在程序里，应该做成 `configure.ini` 从文件读，因为每个客户端不一定一样，它会变化。

* **看清对方是谁**

    * `conn.RemoteAddr()` 返回一个 `Addr`，`Addr` 是接口，调用它的 `String()` 就能拿到字符串形式的地址。

    * 服务端打印出来形如"客户端IP=192.168.20.253:51741"，能看到客户端也有端口，而且每退出重连一次端口就变一次。

    * > **结论**：一次连接 = 服务端的固定监听端口 + 客户端的随机端口，`RemoteAddr().String()` 一行就能拿到。

* **bufio 读终端输入**

    * `bufio.NewReader(os.Stdin)` 创建一个 reader，`os.Stdin` 指向标准输入，标准输入就是终端。

    * `NewReader` 要求传一个实现了 `io.Reader` 的接口对象，它既可以读键盘，也可以指定一个连接。

    * > **易错点**：`NewReader` 不返回 error，所以这里不用判断返回值，直接接收就行。

* **读一行并发出**

    ```go
    reader := bufio.NewReader(os.Stdin)

    line, err := reader.ReadString('\n')
    if err != nil {
    	fmt.Println("read string err=", err)
    }

    n, err := conn.Write([]byte(line))
    if err != nil {
    	fmt.Println("conn.Write err=", err)
    }
    fmt.Printf("客户端发送了 %d 个字节的数据，并退出了\n", n)
    ```

    * `ReadString` 要给一个终止符，`'\n'` 就是回车、回车代表一行；它返回的是字符串和 error，不是字节切片。

    * `Write` 的参数是字节切片，字符串要强转成 `[]byte(line)`；返回的 `n` 表示写了多少字节。

    * `Write` 可能在超过某个时限时返回错误，这个超时时间可以用 `Timeout` 查看。

    * > **易错点**：`Write` 失败不必 `return`，打个错误信息就行；大面积并发时丢包很正常，甚至可能是网络传递时在路由器里丢的。

* **丢包与拒绝服务**

    * 拒绝服务的技术相对原始却最难解决：用大量"肉鸡"往一个网站猛发请求，几百万个请求就能让服务器直接瘫掉。

    * 难在不好区分谁是坏人谁是坏人，他们发起的都是正常请求；就像有人在店门口雇一千个人排队问有没有熊猫肉，真买汉堡的进不来。

* **两边都要写**

    * 开发时先写服务端再写客户端，测完客户端又回去改服务端，来回折腾是网络编程最典型的开发模式，因为服务端代码必须依赖客户端才能测出写没写对。

    * 真实开发里 client 和 server 跑在不同电脑上；本机演示时可以同一台机器既当服务端又当客户端，分 `server`、`client` 两个目录。

    * 难点在于思维方式一下子多元化：要同时考虑客户端、服务器端、两者之间的通信，以及服务器端怎么把数据分发到别的客户端。

## 服务端接收

* **用协程承接每个连接**

    ```go
    func process(conn net.Conn) {
    	defer conn.Close()
    	for {
    		buf := make([]byte, 512)
    		n, err := conn.Read(buf)
    		if err != nil {
    			fmt.Printf("server read err=%v\n", err)
    			return
    		}
    		fmt.Printf("服务器正在等待客户端 %v 发送信息\n", conn.RemoteAddr())
    		fmt.Print(string(buf[:n]))
    	}
    }
    ```

    * 接收工作不能写在主线程里，否则一个客户端发数据时其他客户端全堵在那里，是很可怕的现象。

    * 经典解法是起协程：来一个客户端就用一个协程为它服务，下一个客户端再来时主服务并没有阻塞。

    * 协程必须拿到 `conn` 才能干活，所以要把连接传进去；参数类型是 `net` 包里的 `Conn`，这是个接口类型，任何实现了该接口的对象都能传。

    * 调用要写成 `go process(conn)`，而且必须放在 `for` 循环里面：一次 `Accept` 就代表一个客户端，`Accept` 一个就该开一个。

    * > **易错点**：每次 `Accept` 得到的 `conn` 都不一样，因为每次都是新建的。

    * `defer conn.Close()` 放在处理函数里最合理，处理完就关闭；连接是资源，用完必须释放，否则连接越来越多，最后别的客户端就再也连不上。

* **Read 的阻塞语义**

    * `Read` 需要事先准备好一个切片，所以先用 `make([]byte, 512)` 分配，写 1024 也可以，元素类型是 byte。

    * 每次创建新切片是为了防止后面还挂着一堆乱七八糟的内容。

    * `Read` 返回 `n` 和 error。

    * > **结论**：客户端没有 `write`（也就是发送）动作时，服务端就一直阻塞在那里等；对方长时间不发也可能触发超时关闭。

    * 读出错有两种常见情形：等了很久对方不发而超时；或者对方突然直接把连接关掉了。

    * 连接其实是由 TCP 协议在底层维护的：每隔一定时间发一个包问"你还在吗"，对端回一句"我还在"，这个会话是看不到的，会自动维护。

* **显示的两个细节**

    * 要用 `fmt.Print(string(buf[:n]))` 而不是 `fmt.Println`，因为客户端发过来的数据里本身已经把 `'\n'` 读进来了，再加 `ln` 显示时就会多出一行。

    * 显示的是服务器端终端，客户端的任务就是把收到的信息显示在服务器终端上。

    * > **易错点**：不按实际读到的 `n` 截取切片、直接转换整个缓冲区，会带入多余的空字符或脏数据，引发很多不确定的错误；缓冲区里前面有没有内容、后面有什么都是未知的，所以一定要写 `buf[:n]`，显示实际读到的内容。

* **对方退出怎么识别**

    * 客户端退出后服务端再读，会得到 `use of closed network connection` 或 `closed by remote host` 这种错误信息。

    * > **结论**：它的本质是 `io.EOF`，表示读到最后了，所以 `if err == io.EOF { return }`，远程客户端一退出协程也跟着退出，代码就干净了。

    * > **易错点**：读出错后不 `return`，就会又回到那里不停地等，在那里反复做一件很傻的事；对方已经关闭，`for` 循环再转下去没有意义，协程也没有存在的价值了。

    * 这个错误信息也可以不打印，自己定义一句"对方已退出"看起来更轻松；协程退出之后服务器仍然可以继续接受新的连接。

* **net.Error**

    * `net` 包里定义了一个 `Error` 类型，它是一个接口，里面有个 `Timeout`，返回的还是一个字符串。

    * 打印出来是一大串文字，但它对应的其实是一个常量。

## 客户端循环交互

* **for 循环包住 ReadString**

    ```go
    for {
    	line, err := reader.ReadString('\n')
    	if err != nil {
    		fmt.Println("readString err =", err)
    	}

    	// 如果用户输入 exit，就退出
    	line = strings.Trim(line, " \r\n")
    	if line == "exit" {
    		fmt.Println("客户端退出...")
    		break
    	}

    	// 发送给服务器端，补上换行符
    	_, err = conn.Write([]byte(line + "\n"))
    	if err != nil {
    		fmt.Println("conn.Write err =", err)
    	}
    }
    ```

    * 不发一次就跑，在客户端的 `ReadString` 处用 `for` 循环包起来即可；要用 `strings` 就得在文件上方引入 `strings` 包。

    * > **易错点**：直接写 `line == "exit"` 逻辑上行不通，因为从终端读到的字符串自带 `\n` 或 `\r\n`，必须先处理掉再比较。

    * `strings.Trim` 把 `line` 中的 `\r`、`\n` 以及空格截取去除，然后再判断是否等于 `exit`。

    * > **易错点**：为了判断 `exit` 把换行 Trim 掉了，就必须在上行时手动补 `\n`，否则服务端 `Print` 出来的内容会全部糊成一行。

* **把服务端的等待提示去掉**

    * 服务端循环打印"等待输入"很不友好，因为只要客户端不回车它就一直刷，所以第一件事是把服务端的等待提示信息去掉。

    * 服务端可以同时接两个客户端：第二个客户端连上后服务端提示又有新客户端连上来，两个客户端各发各的内容，服务端都能分别接收并打印出来。

    * 这说明服务端起了两个不同的协程分别为它们服务。

    * 一个客户端输入 `exit` 退出，服务端也能捕获到并打印退出，因为客户端断开后，服务端在读取时发现了 `io.EOF`，知道远端主机关闭了连接，于是退出协程。

* **练习：让 A 和 B 互相聊天**

    * 目标是让 A 客户端和 B 客户端之间能发生交互，直接对接受不通，因为那意味着 B 也必须是一个服务器。

    * 做法是在 A 说一句话后，发给服务 A 的协程；这个协程要拿到与 B 连接的那个协程的连接对象，再把这句话通过该连接转发给 B。

    * > **结论**：服务器端需要一个机制——连接建立时如何标识并保存不同客户端的连接，A 发消息后如何识别目标并转发过去。

    * 只要服务器端能拿到各个客户端的连接，并进行管理与区分，这件事就能做成。

## 用户即时通讯系统需求

* **目标功能清单**

    * 用户注册。

    * 用户登录，用户名不存在就不让登录；密码对就建立连接，密码不对就打回去。

    * 显示在线用户列表，否则 A 不知道 B、C 在不在线，没法给这两人对接。

    * 群聊，相当于把消息广播出去，一说话大家都能看到。

    * 点对点聊天，A 指定和 C 私聊、A 指定和 B 聊天，反过来对方也可以指定过来。

    * 离线留言，这一项必然要用到数据库：给张三发一句话而张三不在线，消息先存着，等张三上线后从服务器把发给他的消息拽下来，跟手机关机再开机收到一堆短信一个道理。

* **开发流程**

    * 需求分析 → 设计 → 编码实现 → 测试 → 实施。

    * 界面是基于文本的：上来先登录聊天系统、注册用户、退出，登录进去以后再看到一个新的菜单，菜单说明要干什么。

* **为什么选 Redis**

    * 注册和登录必然要在服务器端有存储数据的地方，不能全放在内存的 `map` 里，否则服务器一重启东西就没了。

    * 候选有 MySQL、Oracle 这类关系型数据库，也有 Redis、MemCache 这类 NoSQL。

    * > **结论**：选 Redis 是因为它相对容易上手、学习成本比 MySQL 低，不用先学 SQL 语句；会 Go 的 `map`、管道、`for` 循环和切片基本就能跑起来，但要用好同样很难。

    * Web 开发很多东西已经现成，而 TCP/IP 编程要从头到尾全靠自己确定，连协议都是自己决定，所以还是有不小难度。

## Redis 基础

* **Redis（Remote Dictionary Server）**

    * > **定义**：Redis 是一种 NoSQL 数据库，不是 MySQL、Oracle 那种靠主键外键做关联的关系型数据库。

    * 全称是远程字典服务器，直白说就是一个存数据的服务器。

    * 性能非常高，单机能够达到 15 万个 QPS，比一般的关系型数据库高出很多。

    * 既适合做缓存，也可以持久化：既能把数据加载到内存，也可以定期把数据直接持久化到文件里。

    * 特点是开源、高性能、分布式，基于内存并支持持久化，是目前最热的数据库之一。

    * 也叫**数据结构服务器**，因为它支持的数据类型都跟数据结构相关；学过数据结构的人听起来会更轻松。

* **内存里的五种数据形式**

    * `string`：最常见，以 key-value 形式保存，可以有很多。

    * `hash`：哈希表结构，存放大量哈希数据。

    * `list`：以 list 形式维护数据。

    * `set`：集合。

    * `zset`：有序集合，与 set 的唯一区别是有顺序。

    * 内存里放的任何数据（字符串、int 之类）最终都以字符串形式存在。

* **持久化**

    * 数据全在内存里，一关机就全没了，所以还涉及持久化的问题。

    * 落盘的目标本质是文件，一般叫 `dump.rdb` 之类的名字；落盘之后还能再读出来。

* **安装方式**

    * Linux 和 Windows 上都非常简单，基本上是解压即用，不存在安装这一步。

    * 解压后有 `redis-server.exe` 和 `redis-cli.exe` 两个程序，双击即可运行；前者是服务器，后者是专门用来测试的客户端。

* **运行结构**

    * `redis-server` 是真正的服务端，它既然是一个服务，就必然有监听层、有端口，这个端口是 6379。

    * 我们写的 Go 代码（`xx.go`）和专门用来测试的 `redis-cli` 都把指令发到这个监听层。

    * 监听层把指令交给核心组件去解析，解析就是解释指令的含义，然后做相应的处理。

    * 处理的对象就是那一大块内存里的 string、hash、list、set、zset，处理完还可以落盘到 `dump.rdb` 这样的文件里。

    ```text
       Go 代码 (xx.go)            redis-cli.exe
            |  发指令                 |  发指令
            +-----------+-------------+
                        v
           +----------------------------+
           |    Redis 服务端 (server)   |
           |  +----------------------+  |
           |  | 监听层   端口 6379   |  |
           |  +----------+-----------+  |
           |             v              |
           |  +----------------------+  |
           |  | 核心组件             |  |
           |  | 解析你的指令，       |  |
           |  | 做相应的处理         |  |
           |  +----------+-----------+  |
           |             v              |
           |  +----------------------+  |
           |  | 它维护了一块内存     |  |
           |  |  string / hash /     |  |
           |  |  list / set / zset   |  |
           |  +----------+-----------+  |
           +-------------+--------------+
                         | 持久化（入库）
                         v
                dump.rdb 等文件
    ```

    * 一个端口当然可以连接多个人，`redis-cli` 能连上服务端的指令区操作，Go 程序也能连上去操作。

    * 实际开发中用得最多的还是 Go 程序，不可能每次都手敲指令。

    * 两者的指令形式非常像，学完 Go 这边的用法后再看 `redis-cli`，基本不用额外学，只需要加载一个 Redis 第三方插件。
