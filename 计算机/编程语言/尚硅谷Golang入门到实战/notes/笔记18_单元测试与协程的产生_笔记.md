# 单元测试与协程的产生

## 手工测试的做法

### 在 main 里对答案

* **传统测试方式**
    * > **定义**：在 `main` 函数里调用待测函数，拿到实际值与期望值比对，一致即正确，不一致就修改。

    * 典型形态是 `res := addUpper(10)`，再判断 `res != 55` 时输出错误，否则输出正确。
    * 被测函数写错时（例如循环条件误写成 `n - 1`）会输出 `返回值=45 期望值=55`，说明这种手段能发现错误。

### 两个死结

* **不方便**
    * 为测试必须把调用写进 `main` 函数，即需要修改正在运行的代码，项目在跑时得先停下来。
    * 想绕开只能另搭一个与真实运行环境完全一致的测试环境；但两边的数据量和依赖可能不同（生产环境有几千万数据、第三方接口不对测试环境开放），测试通过不保证真实环境也正确。

* **不利于管理**
    * 所有测试只能堆在一个 `main` 函数里，测完一个要把上一个注销掉再测下一个。
    * 多个函数、多个模块都要在同一个 `main` 中表达，自己都说不清测的是哪一个。

## testing 测试框架

### 框架定位

* **testing**
    * > **定义**：Go 语言自带的轻量级测试框架，配合 `go test` 命令实现单元测试和性能测试。

    * 它能基于框架编写针对某个函数的测试用例（test case），也能编写压力测试用例。
    * 单元测试解决三件事：确保每个函数可运行且正确；确保写出的代码性能好（可以横向比较不同人写的代码）；及时发现程序设计中实现的逻辑错误，让问题及早暴露、便于定位。
    * 性能测试重点在于发现程序设计上存在的问题，让程序在高并发情况下仍能保持稳定。

* **运行机制**
    * > **定义**：主函数被框架隐藏起来了，测试时实际调用的是 `testing` 框架。

    * 第一步：默认引入所有以 `_test.go` 结尾的文件，相当于替调用方写了 `import`。
    * 第二步：扫描这些文件，把所有以 `Test` 打头的函数全部调用一遍。
    * 被测函数写在普通源文件里，测试函数通过直接调用它的方式验证结果。

    ```text
                  你的普通文件                      你的测试文件
            ┌───────────────────┐            ┌──────────────────────┐
            │      cal.go       │            │     cal_test.go      │
            │                   │  直接调用   │                      │
            │   addUpper(n)     │◄───────────┤  TestAddUpper(t)     │
            │   getSub(n1,n2)   │            │        │             │
            └───────────────────┘            └────────┼─────────────┘
                                                        │  框架扫描并调用
                                                        ▼
                                           ┌────────────────────────┐
                                           │    testing 框架         │
                                           │  （隐藏的 "main"）     │
                                           │                        │
                                           │  ① 引入 *_test.go 文件  │
                                           │  ② 调用 TestXxx 函数   │
                                           └────────────────────────┘
    ```

* **可自证的实验**
    * 把 `TestAddUpper` 改名成 `Ok` 后再运行，输出 `[no tests to run]` 与 `PASS`，因为它不再符合以 `Test` 打头的规范。
    * 额外写一个 `TestHello` 并在其内部输出，同样会被扫描并调用，说明凡 `Test` 开头一律执行。

## 测试用例规范

### 文件与函数命名

* **文件名 `_test.go`**
    * 测试套件文件必须以 `_test.go` 结尾，前面叫什么无所谓。
    * 文件放在与被测试包相同的包中即可，也可以放在主包里。
    * 该文件会被排除在正常的程序支持包之外，只有运行 `go test` 命令时才被包含进去。

* **函数名以 Test 打头**
    * 一般写成 `Test` 加被测试函数名，如 `TestAddUpper`、`TestGetSub`。

    * > **易错点**：`Test` 后面的第一个字母不能是小写 `a` 到 `z`。写成 `TestaddUpper` 会被检测为不规范，报 `first letter must not be lowercase`。

    * 后面具体叫什么不影响实际测到哪个函数，测试的到底是哪个函数由函数体内容决定，而不是名字决定。
    * 但仍应按“Test + 被测函数名”统一命名，同事看一眼就知道测的是谁。

### 形参与方法

* **形参 *testing.T**
    * > **定义**：测试函数的形参固定写成 `t *testing.T`，`T` 是 `testing` 包中的结构体类型，代表与这次测试绑定的测试对象。

    * 使用它就要引入 `testing` 包。

| 方法 | 作用 |
| :--- | :--- |
| `Error` / `Errorf` | 打一个错误，格式化的错误 |
| `Fail` / `FailNow` | 致命的错误，格式化输出日志 |
| `Logf` | 记录日志 |
| `Run` | 运行 |
| `Skip` | 跳过 |

    * 最常用的是 `Fatalf` 和 `Logf`。
    * `t.Fatalf` = 打日志 + 终止当前测试用例；`t.Logf` = 只打日志，不终止。
    * `PASS` 表示测试用例运行成功，`FAIL` 表示运行失败；出错时用 `Fatalf` 格式化输出错误信息并退出，正常日志用 `Logf`。

* **一个文件放多个用例**
    * 一个测试用例文件里可以包含多个测试函数，分别测不同的被测函数。

## 测试运行与筛选

### -v 开关

* **`go test -v`**
    * 带 `-v` 时，无论运行正确还是错误都会输出日志。
    * 不带 `-v` 时输出非常简洁，全部正确时只给 `PASS`，`t.Fatalf` 与 `t.Logf` 的内容都不再输出。
    * 即使不带 `-v`，一旦有用例失败仍然会显示 `FAIL` 和出错行号。

* **耗时统计**
    * 每个用例会打印自己花费的时间，整体还会打印一个总耗时。
    * 各用例耗时之和小于整体总耗时，差值来自加载框架的开销，这部分时间要排除在外。

### 按文件和函数筛选

* **只测指定文件**
    * 默认会扫描并执行所在文件夹下所有测试文件；只测一个文件要把被测的源文件也一起带上，例如 `go test -v cal_test.go cal.go`。
    * 筛选以**文件**为单位，命令里没列出的文件其用例不会被执行。

* **只测指定函数**
    * 用 `-run` 加上用例函数名，例如 `go test -v -run TestAddUpper`。
    * 用例多时不必每次全量跑，筛选后可快速定位单条用例。

    * > **易错点**：`-run` 后面的名字必须与用例函数名完全一致，包括大小写。把大写 `U` 写成小写会得到 `no tests to run`，一条都没跑到。

### 整体通过判定

* **全过才算过**
    * 框架会把所有注册的用例都跑一遍，只要有一个错，整体就判为错；全部正确才算正确。
    * 多个源文件分属不同包名时，被测函数会报未定义，需把包名统一。

## Monster 综合案例

### 案例结构

* **被测对象**
    * > **定义**：`Monster` 结构体带三个字段 `Name`（string）、`Age`（int）、`Skill`（string），并绑定 `Store` 与 `Restore` 两个方法。

    * 单独建一个文件夹存放 `monster.go` 与 `monster_test.go`，包名统一为 `monster`，不必和主包同名。
    * 验收标准两条：序列化时能否正确保存到文件；能否恢复回来，且恢复后的名字与保存时一致。

* **Store 方法**
    * > **定义**：先序列化再落文件，把 `Monster` 保存到文件中，成功返回 `true`，任一步出错返回 `false`。

    * 序列化用 `json.Marshal(m)` 得到 `data` 与 `err`，`err != nil` 时打印 `marshal err` 并返回 `false`。
    * 落文件用 `ioutil.WriteFile(filePath, data, 0666)`，`err != nil` 时打印 `WriteFile err` 并返回 `false`。
    * 文件不用显式关闭，`WriteFile` 内部已完成；`data` 是字节切片，与 `WriteFile` 要求的类型正好匹配。
    * 返回 `bool` 还是 `error` 都可以，返回 `error` 更利于把信息带到上一层再输出。

    * > **易错点**：结构体字段和函数签名末尾的冒号不能漏写。

* **Restore 方法**
    * > **定义**：先读回文件再反序列化，成功返回 `true`，任一步出错返回 `false`。

    * 读文件用 `ioutil.ReadFile(filePath)` 得到 `data` 与 `err`，`err != nil` 时打印 `ReadFile err` 并返回 `false`。
    * 反序列化用 `json.Unmarshal(data, m)`，结果直接写回 `m`，`err != nil` 时打印 `Unmarshal err` 并返回 `false`。
    * 读与写用的是同一个 `filePath` 常量。

* **测试用例写法**
    * `TestStore` 先造实例 `Monster{Name: "红孩儿", Age: 10, Skill: "吐火"}`，调 `res := monster.Store()`，`!res` 时 `t.Fatalf`，否则 `t.Logf`。
    * `TestRestore` 先声明空的 `var monster Monster`（不必赋初值），调 `res := monster.Restore()`，先判 `res`。
    * 判完 `res` 再判 `monster.Name != "红孩儿"`：名字对不上说明序列化文件被改过或读错了文件，同样 `t.Fatalf`。
    * `Store` 与 `Restore` 写进同一文件从上到下执行，顺序保证先落盘后读取；若拆到不同文件就要注意这个先后。
    * 只跑其中一个用 `go test -v -run TestRestore`。

* **方法与指针的关系**
    * 方法绑定在指针上时，用指针调用更稳健，两种写法都能跑通。
    * `monster.Restore()` 传的是地址，传的本质是引用；写成指针形式调用只是让写法上更安全。

### 环境干扰

* **杀软误报**
    * > **注意**：360 一类杀软可能把生成的测试用例识别成木马，这是它底层机制导致的现象，与代码本身无关；出现时暂时退出杀软再跑即可。

## 单元测试的价值与追问

### 测试的价值

* **复杂场景下的意义**
    * 简单函数肉眼看就能判断对错，测试价值不大；真正的价值在于被测函数功能复杂、内部还层层调用其它函数，甚至结果不稳定时。
    * 典型做法是把大量测试数据放在文件里循环读入、反复调用同一个函数，只有多次结果都符合期望才说明它稳定。
    * 以排序为例，只测一个无序数组通过不能说明正确，应该写上千个无序数组测上千次；更严格的做法是拿一个已验证的算法作参照，逐个比对被测函数的结果，这才是测试的本质。

* **框架能横向比性能**
    * 用同一个测试用例去测不同人写的同一功能，代码写错或性能差的一测就暴露出来。

### 常见追问

* **测试函数有返回值吗**
    * 没有。`testing` 的用例函数不返回任何值，结果通过 `Fatalf`、`Logf` 表达。

* **按模块分工怎么协作**
    * 各模块小组自己写单元测试并保证通过，另一模块调用时直接复用对方的测试流程；对方流程走不通就直接掐断，测试报告错误落在对方模块，走得通就说明对方模块没问题。

* **用例之间的顺序与关联**
    * 确实弱。被测函数层层调用张三、李四的函数时，一旦出错很难定位是本函数还是被调函数带来的。
    * 解法一：细化，把每个函数都单独做小测试，先确认每个函数没问题，再往上测。
    * 解法二：加格式化的日志，日志能记录时间、文件、模块甚至行号，出错时可直接定位到具体函数。

## 素数统计需求

### 传统做法

* **需求**
    * 统计 1 到 20000 中哪些是素数。

* **双层循环判定**
    * 对 1 到 20000 逐个取数，让每个 $n$ 从 2 到 $n-1$ 逐个取模，只要 2 到 $n-1$ 中没有任何一个能整除它，$n$ 就是素数。
    * 慢的原因有两层：一是除数区间本身量很大，二是外层还要再遍历 20000 个数字，形成很大的双层循环。
    * 本质问题是一个任务只交给一个 CPU 做，其余多核资源闲置；电脑上普遍是 4 核、8 核、16 核，只让一颗核工作非常不划算。

* **分解任务的思路**
    * 改用并发加并行，把统计任务分配给多个协程去做，各算一部分，最后汇总结果。
    * 类比：把任务交给一个人做班长肯定完成不了，交给全中国的人各除以 13 亿份就简单了。
    * 分给 4 个 CPU 做，速度至少提高 4 倍。

## 进程与线程

### 进程

* **进程（Process）**
    * > **定义**：进程是程序在操作系统中的一次执行过程，是系统进行资源分配和调度的基本单位。

    * 程序本身是磁盘上的 `.exe` 文件或源码文件，运行它、调入内存让操作系统开始执行，才产生了进程。
    * 任务管理器里的每一条记录就是一个进程，分前台进程（有界面）和后台进程。
    * 双击打开一个应用就产生一个进程，结束该进程对应界面也会关闭。
    * 一个程序能否起多个进程，取决于程序本身和操作系统是否允许。

* **线程（Thread）**
    * > **定义**：线程是进程的一个执行实例，是程序执行的最小单位，比进程更小、能独立运行的基本单位。

    * 一个进程可以创建和销毁多个线程，同一进程中的多个线程可以并发执行。
    * 一个程序至少有一个进程，一个进程至少有一个线程。
    * 类比下载工具：一个进程可以同时下载多个文件，每个下载任务相当于一个线程；同进程里的线程共享地址空间，同时下载的数量由程序设置决定（如可设 5 或 10）。

* **层次关系**

    ```text
                thunder.exe
              程序 / 程序文件
                    │
                    │  双击运行 → 调入内存开始执行
                    ▼
       ┌────────────────────────────────────────┐
       │  进程：Thunder                          │
       │  系统进行资源分配和调度的基本单位         │
       │  任务管理器里的一条记录                  │
       └────────────────────────────────────────┘
                    │ 一个进程至少有一个线程
          ┌─────────┼─────────┼─────────┬─────────┐
          ▼         ▼         ▼         ▼         ▼
       线程1     线程2     线程3     线程4     线程5
      下载封神   下载 A    下载 B    下载 C    下载 D
      英雄榜
                                                ┌────────┐
                                                │ 排队中 │
                                                └────────┘
    ```

    * 进程名一般以文件名命名，进程里可以起多个线程。

## 并发与并行

### 并发

* **并发（Concurrency）**
    * > **定义**：多个任务挤在一颗 CPU 上运行，靠时间片来回切换，从效果上看像是同时执行。

    * CPU 切换的时间单位是零点零几秒或几毫秒，人眼反应不过来，感觉像同时在跑。
    * 微观（某一瞬间）只有一个任务在执行，宏观上人感觉全都在同时执行。
    * 例：单核机器上打开两个视频，看着像同时播放，实际一个时间点只在执行一个任务。
    * 这里说的并发是 Go 程序的并发，与外部“一颗 CPU 短时间涌进一万个请求”那种并发不是同一个概念。

    ```text
    并发：任务都挤在一颗 CPU 上，靠切换伪装成同时
            ┌────────────── CPU1 ──────────────┐
      时刻1 │  task01      │                 │
      时刻2 │  task02      │                 │
      时刻3 │  task03      │                 │
      时刻4 │  task01      │                 │
      时刻5 │  task02      │                 │
            └──────────────────────────────────┘
            切换以毫秒为单位 → 人眼以为同时在跑
    ```

### 并行

* **并行（Parallelism）**
    * > **定义**：把多个任务分配到多颗 CPU 上，微观上同一时间点确实有多个任务在真正同时执行。

    * 例：一颗 CPU 干 task01，CPU2 干 task02，CPU3 干 task03，三件事真的一起跑。
    * 传统编程语言即使有多个任务也往往集中在一颗 CPU 上，多核威力发挥不出来；Go 语言能把并发转成并行，这是它重大的一个改进。
    * 并行速度明显快于并发。

    ```text
    并行：任务分给多颗 CPU，真同时
            ┌────────┐    ┌────────┐    ┌────────┐
            │  CPU1  │    │  CPU2  │    │  CPU3  │
            │ task01 │    │ task02 │    │ task03 │
            └────────┘    └────────┘    └────────┘
                     同时刻，三件事真的在一起跑
    ```

* **两者对照**

| | 并发 | 并行 |
| :--- | :--- | :--- |
| 任务落在几个 CPU 上 | 多个任务挤一个 CPU | 多个任务分多个 CPU |
| 微观（某一瞬间） | 只有一个任务在执行 | 多个任务真正同时执行 |
| 宏观（人的感觉） | 好像都在同时执行 | 确实都在同时执行 |
| 机制 | 时间片轮询、来回切换 | 各自独立的 CPU 同时跑 |
| 速度 | 受单核限制 | 明显更快 |
