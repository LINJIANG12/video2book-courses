# 聊天室实战：消息协议与登录流程

## 客户端起步与目录约定

* **两级菜单**

    * > **定义**：聊天室客户端的交互界面分两层，第一级是登录前菜单，第二级是登录成功后菜单。

    * 第一级菜单固定三项：登录聊天系统、注册用户、退出系统。

    * 第二级菜单在登录成功后才出现，包含显示在线用户列表、发送消息、信息列表、退出系统四项。

    * 第二级菜单必须用 `for` 循环反复显示，用户每选一次、执行完动作后菜单还要再出现一次，否则选完一次就看不到选项了。

* **工程目录拆分**

    * 客户端建 `client` 目录，里面放 `main.go` 和 `login.go`；服务端另建 `server` 目录。

    * 收发消息包一类的操作统一放到客户端的 `utils.go` 里。

    * 客户端和服务端共用一份消息定义，抽到独立的 `common` 包下，`common` 里再分一层专门放消息。

    * Go 里面**一个文件夹就是一个包**，拆目录本质上是在拆包。

* **可执行文件命名**

    * 用 `go build` 编译后默认生成的是 `main.exe`，客户端和服务端都会叫这个名字，互相覆盖。

    * 所以必须用 `-o` 显式指定名字，客户端为 `client.exe`，服务端为 `server.exe`。

    * 两个文件都在主包时，必须退到 `src` 目录下编译：`cd client` 后执行 `go build -o bin/client.exe go_code/chatroom/client`。

* **待填的全局变量**

    * 登录需要的用户 ID 和密码先定义为包级全局变量 `userId int` 和 `userPwd string`，后续再决定怎么在函数间传递。

    * ID 只用整数类型，不用字符串，因为 QQ 号、银行卡号这类标识天然是纯数字。

## 接收输入的坑

* **`fmt.Scanf` 必须带 `\n`**

    * > **定义**：`fmt.Scanf` 的格式串里要写上 `\n`，用来吞掉用户敲下的回车。

    * > **易错点**：⚠️ 不写 `\n`，程序会把回车当成用户输入的内容，后面所有输入会一次性跑光，一回车全被读走。

    * 换成 `Scanln` 同样躲不掉这个问题，下面不是 `Scanln` 的地方也一样倒霉。

    * 之所以选 `Scanf` 而不是字符串扫描，正是因为字符串扫描会把这个坑掩盖掉，看不出问题。

* **`key` 与 `loop`**

    * `key int` 接收用户的选择项，`loop bool` 默认 `true`，用来控制菜单是否继续显示。

    * 选 1 走登录分支，选 3 或输入非 1~3 的值时把 `loop` 置为 `false` 退出菜单循环。

    * 一开始写 `fmt.Scanf("%d\n", &key)` 后选择 1 的分支里直接 `loop = false`，登录后要看到第二级菜单，这段就要改掉。

## 登录函数与返回值选择

* **`login` 函数签名**

    * > **定义**：`func login(userId int, userPwd string) (err error)`，登录至少要接收用户 ID 和用户密码两个参数。

    * 参数命名建议跟对方那边保持一致，借用名字可以省掉命名的痛苦。

    * 长文给的经验是：**那边叫什么，这边就叫什么**。消息种类多起来以后命名会非常困难，登录消息、响应消息、发送消息、上线消息、群发消息、点对点消息，名字很容易撞车。

* **用 error 而不是 bool 表示结果**

    * > **结论**：结果尽量以 `error` 的形式返回，不要用真假值。

    * 真假只有 1 和 2 两种状态，描述能力太弱；`error` 可以区分用户名不存在、密码不对、服务器故障等不同失败原因。

    * 成功时返回 `nil`，调用方统一用 `if err != nil` 判断。

* **拆出 login.go 的意义**

    * 把登录逻辑单独放一个文件只是最朴素的做法，程序结构还要一步步推导；写一步测一步，出错时才好定位。

    * 通信代码调错的压力大是因为里面既有网络又有协议，出错时没有头绪。

## 消息协议的设计

* **Message（消息结构体）**

    * > **定义**：所有消息的总结构体，分成「消息类型」和「消息数据」两部分。

    ```go
    type Message struct {
        Type string `json:"type"` // 消息类型
        Data string `json:"data"` // 消息的内容
    }
    ```

    * `Type` 用 string 描述消息种类，因为实际场景里消息类型可能有多达上百种，语音、在线、离线、文本、图片各算一种。

    * `Data` 定义成 string 而不是字节切片，因为程序里最终拿到手操作的仍然是字符串。

    * `Message` 放在共用的 `message.go` 里，不能放在服务端或客户端的 `main.go` 中。

* **具体消息结构体**

    * 每一种消息单独定义一个结构体，字段按实际需要来定，后续需要时再扩展。

    ```go
    type LoginMes struct {
        UserId   int    `json:"userId"`
        UserPwd  string `json:"userPwd"`
        UserName string `json:"userName"`
    }
    ```

    * `UserName` 当前用不上也无妨，先写上，等扩展时直接可用。

    * 结构体字段之所以写成大写，是因为结构体要序列化之后才能发送，序列化得到的结果全是小写键名，所以每个字段都加了 `json:"..."` 结构体标签。

* **消息类型常量**

    * > **定义**：把消息类型名定义为常量，避免到处硬编码字符串。

    ```go
    const (
        LoginMesType    = "LoginMes"
        LoginResMesType = "LoginResMes"
        RegisterMesType = "RegisterMes"
    )
    ```

    * 结构体名不能直接当消息类型用，`LoginMes`、`LoginResMes` 这些最终都要被填进 `Message.Data`，所以需要单独的字符串常量来描述它们。

    * 消息类型常量不能改，将来还要往里加用户上线的消息、聊天的消息等。

## 登录结果消息与状态码

* **LoginResMsg（登录结果消息）**

    * > **定义**：服务端回送给客户端的登录结果结构体，与请求消息结构体不同。

    ```go
    type LoginResMsg struct {
        Code  int    `json:"code"`
        Error string `json:"error"`
    }
    ```

    * `Code` 是 int 型错误码，沿用 HTTP 协议那套数字状态码的思路：200 表示成功，404、403、500 各代表一类问题。

    * `Error` 是字符串型错误描述，没有错误时可以留空。

* **两个确定下来的状态码**

    | 状态码 | 含义 |
    | :--- | :--- |
    | 200 | 登录成功 |
    | 500 | 该用户还没有注册 / 用户不存在 |

    * 还可以继续扩展，比如用 300 表示权限不够或者网络不通。

    * 失败时可以在 `Error` 里带上中文描述，比如「该用户不存在，请注册再使用」，也可以写英文；一般开发都会在码之外再带一个说明。

## 为什么必须先发长度

* **丢包是网络最怕的事**

    * > **定义**：丢包指数据在网络传输中少了字节，一旦少了一个字节，整个程序可能调不出错误。

    * 打个比方：一个视频文件少了一两个字节，整个视频就打不开；用二进制编辑器打开视频删掉一个字母，文件就废了。

    * 传统协议的做法是提前告诉对端包有多长，HTTP 的 `Content-Length` 就是干这个的。

* **先发长度再发内容**

    * > **结论**：发送包在网络传输之前，第一步先不发消息本身，先把这条消息的字节长度发给对端，然后再发消息本身，这两步都完成才算一次发送结束。

    * 对端按声明的长度去读，少读一个就判定包错、弃包并要求重发；不校验长度，网络程序后面一定会有很多 bug。

* **为什么不把长度塞进 Message**

    * 也可以给 `Message` 增加一个 `len` 字段，用 `uint32` 存长度，一次性发出去；HTTP 就是这么干的。

    * HTTP 能这么干是因为它一次连接马上就断掉，而这里用的是 TCP 长连接，所以先发长度再收内容也没问题。

    * 长文选的是先发长度这种稍麻烦的方式，理由是更稳定。

* **热土豆原理**

    * > **定义**：TCP 底层有一个热土豆原理，一个包经过二十到三十个路由还到不了对方，整个网络就把这个包扔掉。

    * 数据一定要丢掉，不丢的话那些已经没主人的数据会一直阻塞在公网上，危害很大。

    * 丢包只有两种原因：代码本身写错，或者网络错误。

    * 严一点的做法是发现长度对不上就发一条消息说「对不起，请你重发」；像断点续传那种要记录传到哪了，比这复杂得多。

## 发送与接收的流程

* **发送五步**

    * > **定义**：把一条具体消息变成网络字节流要经过的固定步骤。

    ```text
      ① 创建一个空的 Message 结构体
                  │
                  ▼
      ② 设置消息类型：message.Type = 登录消息类型
                  │
                  ▼
      ③ 把 LoginMes 序列化后的字节放进 message.Data
                  │
                  ▼
      ④ 对 Message 整体再做一次序列化
                  │
                  ▼
      ⑤ 先发长度（几个字节），再发消息本身  ───►
    ```

    * 第④步不能省，序列化完成后 `data` 才是真正要发送的数据。

* **接收十步**

    * > **定义**：对端收到字节流后还原成业务消息的固定步骤。

    ```text
      ① 先接收对方发来的长度 n
         （以字节形式发送：byte 切片 → 还要转成 int）
                  │
                  ▼
      ② 根据这个长度再次接收，接收消息本身
                  │
                  ▼
      ③ 判断：实际收到的长度 len 是否等于对方说的长度
         ├─ 不等 → 说明有丢包，走纠错协议
         └─ 相等 → 继续
                  │
                  ▼
      ④ 把消息反序列化成 Message
                  │
                  ▼
      ⑤ 取出 Message 里的 Data（此时是字符串/字节）
                  │
                  ▼
      ⑥ 把 Data 再反序列化成具体消息类型（如 LoginMessage）
                  │
                  ▼
      ⑦ 终于拿到真家伙了：可以取出 UserId 和 UserPwd
                  │
                  ▼
      ⑧ 去数据库或文件里比对
                  │
                  ▼
      ⑨ 按比较结果组装新的 Message 返回
                  │
                  ▼
      ⑩ 客户端收到后重复 ①②④⑤⑥
    ```

    * 第③步长度不一致就说明有丢包，严谨的话要发消息请对方重发。

    * 客户端收到响应后重复的是①②④⑤⑥，即先读长度、再读消息体、反序列化两次，不走比对逻辑。

* **网络只传字节**

    * > **结论**：网络传输不能以 int 这种类型发送，全部以字节形式发送，所以长度本身也要按字节发。

    * 这也是网络能传文件、传图片的原因，底层就是字节，大小不同而已。

    * 收端拿到的是一个字节切片，还得把字节切片转成 int。

## 长度头的字节处理

* **`encoding/binary`（数字与字节序列转换）**

    * > **定义**：`encoding/binary` 包提供了数字与字节序列之间的转换方式。

    * `PutUint32` 把一个具体的 uint32 数字写进切片，把数字转成字节序列。

    * `Uint32` 是反方向，把字节序列表示的值还原成 uint32。

    * `binary` 里的 `BigEndian` 变量类型是 `ByteOrder`，要用它才能调用上面两个方法。

* **为什么定成 uint32**

    * 无符号 32 位能表示的数据量已经很大，而且 `PutUint32` 这个方法正好对应它。

    * $2^{32}-1$ 除以 1024 是 K，再除是兆，再除是 G，足够发将近 4 个 G，一般网络早就冲死了，暂时没必要整更大。

    * 也可以用 `PutUint64`，适合想发送更大数据量的场景。

* **读写长度头的代码**

    ```go
    var pkgLen uint32
    pkgLen = uint32(len(data))

    buf := make([]byte, 4)
    binary.BigEndian.PutUint32(buf, pkgLen)

    n, err := conn.Write(buf)
    if err != nil || n != 4 {
        fmt.Println("conn.Write fail, err=", err)
        return
    }
    ```

    * `len` 返回的是 int，要赋给 uint32 必须做一次强转。

    * 发送成功的判定条件是 `err == nil` 且 `n == 4`，两个条件只要有一个不成立就说明没发成功。

## 服务器端的监听与并发模型

* **监听、Accept、起协程**

    ```go
    listen, err := net.Listen("tcp", "0.0.0.0:8889")
    if err != nil {
        fmt.Println("net.Listen err=", err)
        return
    }

    for {
        conn, err := listen.Accept()
        if err != nil {
            fmt.Println("listen.Accept err=", err)
        }
        go process(conn)
    }
    ```

    * 监听端口定为 8889，这个值可以随意换。

    * `Accept` 出错时可以暂时不退出，因为一个连接出错不影响其他连接继续工作。

* **`conn` 的含义**

    * > **定义**：`Accept` 返回的 `conn` 是一根互通的管道，也就是套接字，是服务器与客户端之间唯一的一条双向通信线。

    * 不是「发过去一个连接、回来又一个连接」，收发都在同一根线上。

    * `net.Conn` 是接口类型，属于引用类型，所以写成 `conn net.Conn` 时不用加星号。

    * 主线程带一个上下文空间，每来一个连接就开一个协程专门服务它，多个客户端各占一个协程。

* **为什么必须新建共用的包**

    * 服务器要读消息客户端要发消息，反过来也一样，收发两端都要用到同一套结构，所以要新建共用的包。

## 读长度头与读消息体

* **`process` 里的第一版读取**

    ```go
    func process(conn net.Conn) {
        defer conn.Close()

        for {
            buf := make([]byte, 1024*4)
            n, err := conn.Read(buf[:4])
            if err != nil || n != 4 {
                fmt.Println("conn.Read err=", err)
                return
            }
            pkgLen := binary.BigEndian.Uint32(buf[:4])
            fmt.Println("读到客户端发送的数据长度 pkgLen =", pkgLen)
            fmt.Println("等待读取客户端发送的数据...")
        }
    }
    ```

    * buffer 按 $1024 \times 4$ 开，尽量开大一点。

    * > **易错点**：⚠️ 读的时候只读 `buf[:4]` 前四个字节，因为对方发的是四个字节；读多了会把后面没用的数据一起带过来。

    * `conn.Read` 是阻塞调用，读不到东西就堵在这一行。

* **`n` 的含义要搞清**

    * `net.Conn` 接口上的 `Read` 方法返回值 `n` 表示**实际**读了多少个字节。

    * `err` 表示「读出错了」，`n` 表示「没报错，但可能没读够」，两者表达的是两件事。

    * 读固定四字节的长度头时，对端指定的就是四字节，判断不判断问题都不大，判一个 `err` 就够——这是「当前场景够用」，不代表这个判断本身没意义。

    * 读消息体的地方 `n` 的判断必须加回来，因为想读多少不代表真能读够。

* **把 make 提到循环外**

    * 原来 `make` 写在循环里每次进来都重新开一块 buffer，其实一块就够，函数入口处开出来循环复用即可。

## 客户端发送一个长度

* **七步里的前三步**

    ```go
    conn, err := net.Dial("tcp", "localhost:8889")
    if err != nil {
        fmt.Println("net.Dial err=", err)
        return
    }
    defer conn.Close()

    var mes message.Message
    mes.Type = message.LoginMesType

    var loginMes message.LoginMes
    loginMes.UserId = userId
    loginMes.UserPwd = userPwd
    ```

    * 本地调试连 `localhost:8889`；正式环境该连哪个地址应该读配置文件，免得改源代码。

    * 赋值仍然写大写字段名，因为此时还没序列化，字段名仍是 `UserId`。

* **第四次序列化**

    * > **易错点**：⚠️ 不能写 `mes.Data = loginMes`，因为 `Data` 是 string 而 `loginMes` 是结构体，必须先序列化再放进去。

    ```go
    data, err := json.Marshal(loginMes)
    if err != nil {
        fmt.Println("json.Marshal err =", err)
        return
    }

    mes.Data = string(data)

    data, err = json.Marshal(mes)
    if err != nil {
        fmt.Println("json.Marshal err =", err)
        return
    }
    ```

    * `json.Marshal` 返回的是字节切片，赋给 string 字段时要转一下。

    * 第二次序列化之后 `data` 才是真正要发送的字节。

* **不能直接 Write**

    * > **易错点**：⚠️ `conn.Write(len(data))` 编译就报错，因为 `len` 返回 int，而 `Write` 要的是字节切片。

    * 正确做法是先用 `uint32(len(data))` 拿到长度，再通过 `binary.BigEndian.PutUint32` 写进长度为 4 的切片，最后把这个切片发出去。

* **两个 defer 不能省**

    * > **注意**：拿到 `conn` 之后要马上写 `defer conn.Close()`，客户端和服务端两边都要写。

    * 少写一个延时关闭，后面出现的错误会非常诡异且难调；不关连接也会出现一些奇怪现象。

    * `listen` 不一定非关不可，它本来就不出来，延时关闭无所谓。

* **验证长度对不对**

    * 把客户端算出的长度打印出来和服务器端收到的长度对照，两边必须一致。

    * 把 `data` 转成 `string` 打印就能看到真正发出去的内容，这是最直接的调试手段。

## readPkg 封装

* **封装的理由**

    * > **定义**：`readPkg(conn net.Conn) (mes message.Message, err error)` 把「读长度头 + 读消息体 + 两次反序列化」整个藏起来，读完直接得到消息体。

    * 收发消息的地方很多，每次都写一遍冗长代码复用性极低。

    * 该函数可以循环调用，所以读包和读消息体统一封装成一个函数。

* **反解长度**

    ```go
    var pkgLen uint32
    pkgLen = binary.BigEndian.Uint32(buf[:4])
    ```

    * 用的是 `binary` 包 `order` 里的 `Uint32`，方向与 `PutUint32` 相反。

* **按长度读消息体**

    * `conn.Read(buf[:pkgLen])` 不是从 buffer 里读，而是**从 conn 套接字里读这么多字节，扔到 buffer 里面去**。

    * 期望读多少不代表实际能读够，所以这里 `n` 和 `err` 都要判断：`n` 不等于期望长度说明可能丢包，和四字节长度头的比对是同一个道理；`err != nil` 还有可能是对端管道关闭了。

    * 出错就打印 `read pkg body error` 然后 return，不再往下做。

* **反序列化的顺序**

    * > **结论**：先反序列化成 `Message`，取出 `Data` 后再反序列化成具体的 `LoginMes`，顺序不能颠倒，因为发的时候就是按 `Message` 序列化的。

    * 字节切片反序列化后还不是能用的消息，必须转成真正要的类型。

* **必须加的地址符**

    * > **易错点**：⚠️ `json.Unmarshal(buf, &message)` 的 `&` 绝对不能漏，漏了以后从 `message` 里取到的就是空的，数据根本没写进去。

    * 返回值已经命名成 `message` 了，所以这里不需要再 `var` 声明一次，也不能再用 `:=`（会报 no new variables）。

    * 这类细节平时想不到，长文的说法是「技术就是一层窗户纸」：捅破了觉得啥都没有，不捅破永远觉得神秘。

* **命名返回值与自定义错误**

    * 不同类别的错误最好分开定义，用 `errors.New("read pkg header error")` 给读头错误起个名字，读消息体错误再来一个，让错误信息更清晰。

    * 调用处统一 `msg, err := readPkg(conn)`，`err != nil` 就打印 `readPkg err` 并 return。

## 阻塞与连接关闭

* **Read 阻塞的前提**

    * > **定义**：服务器在 `for` 循环里反复读包时会阻塞在这里，阻塞的前提是双方都还持有同一个有效的 `conn`。

    * 连接一旦被关闭，`conn.Read` 就不再阻塞。

    * > **易错点**：⚠️ 只要客户端和服务端任意一方关掉 `conn`，服务器就会陷入「读不到 → 报错 → return → 主流程没处理 → 接着循环读」的反复刷屏。

```text
客户端 close(conn)
        │
        ▼
服务端 conn.Read 不再阻塞 ──► 读不到东西 ──► 报错 ──► return
        ▲                                                    │
        └───────────────── 主流程没做任何处理，接着循环 ◄────┘
```

* **解决方案：改成 io.EOF**

    * 自定义的 `read pkg header error` 没法拿来判断，所以改成把 `err` 原样 return 上去，让调用方看到它本来的样子，它应该是 `io.EOF`。

    * 调用方在循环里判断：

    ```go
    if err == io.EOF {
        fmt.Println("对方关闭了连接，客户端退出了")
        return
    }
    ```

    * 语义是「你不玩了我也退」，服务器端跟着正常关闭退出；其他错误信息照常打印，分成「客户端退出」和「其它情况」两种。

    * 别忘了引入 `io` 包。

* **另一种选择**

    * 报错时也可以选择直接退出，双方相当于互相不玩了；但要区分清楚是自己要退出还是对方断了。

## 服务端按消息类型分派

* **为什么必须分层**

    * > **结论**：优化效率一般用缓存解决，优化程序结构一般用分层模式解决。

    * 分层模式的核心是**各司其职**，MVC、多层模式都是这个思想的延伸。

    * 服务器端将来要处理登录、注册、发消息、离线留言、群发消息等完全不同的业务，全塞进一个协程函数里不现实。

* **`serverProcessMsg`（消息调度函数）**

    * > **定义**：`func serverProcessMsg(conn net.Conn, mes *message.Message) (err error)`，根据客户端发来的消息种类决定调用哪个处理函数。

    * `Message` 用指针传，因为它已经被拿到了，不要吝啬地复制一份。

    * 用 `switch mes.Type` 分派，消息种类再多也就十几二十种。

    ```go
    switch mes.Type {
    case message.LoginMesType:
        // 处理登录的逻辑
    case message.RegisterMesType:
        // 处理注册的逻辑
    default:
        fmt.Println("消息类型不存在，无法处理")
    }
    ```

    * `Type` 字段在这里充分发挥威力，登录、注册各自走各自的业务函数。

    * `LoginResMesType` 是服务器发给客户端的，服务器端自己用不上这个 case。

    * 这套写法像在写一个小框架的总控或控制器。

* **`serverProcessLogin`（处理登录）**

    * > **定义**：`func serverProcessLogin(conn net.Conn, mes *message.Message) (err error)`，从 `Message.Data` 里挖出用户 ID 和密码。

    * 进了这个函数不用怀疑，`Data` 一定是 `LoginMes`，因为外面已经按类型判断过了。

    * 取出 `Data` 后转成字节切片再反序列化：

    ```go
    data := []byte(mes.Data)
    var loginMsg message.LoginMes
    err = json.Unmarshal(data, &loginMsg)
    if err != nil {
        fmt.Println("反序列化失败")
        return
    }
    ```

* **先到数据库之前的判断规则**

    * > **定义**：逻辑是先不入库，直接判断「用户 ID 等于 100 且密码等于 123456 就合法」，否则不合法。

    * > **易错点**：这里判断的是**合法性**，不是「这个用户存不存在」，写死的 100 / 123456 只是为了让整条链路先跑通。

    * 正式版本这里应该有一段到数据库验证的逻辑。

## 构造响应与 writePkg

* **三步构造响应**

    ```go
    var resMsg message.Message
    resMsg.Type = message.LoginResMesType

    var loginResMsg message.LoginResMsg
    loginResMsg.Code = 200
    loginResMsg.Error = ""

    data, err := json.Marshal(loginResMsg)
    if err != nil {
        fmt.Println("序列化失败 err fail")
        return
    }

    resMsg.Data = string(data)

    data, err = json.Marshal(resMsg)
    if err != nil {
        fmt.Println("序列化失败 err fail")
        return
    }
    ```

    * `Code` 给 200 表示登录成功，给 500 表示用户不存在、可以注册；`Error` 按情况填中文描述或留空。

    * 第五步要再对 `resMsg` 序列化一次，此时它才变成真正要发送的东西。

    * 这套结构虽然繁琐，但结构做得规范之后很多业务需求都能满足；结构单薄的话稍微复杂一点的逻辑就处理不了。

* **为什么底层这么麻烦**

    * > **定义**：麻烦的根源是网络传输只允许传字节，而程序内部操作要求用结构体。

    * 真正要玩的时候必须用结构体，发送前要序列化成字节，对端收到后要取出来再反序列化。

    * Web 开发里这些转换全由框架（如 Tomcat）帮你做掉了；TCP 编程没有 Web 服务器也没有解析器，服务器和解析全得自己写，所以代码必然复杂。

    * 也正因为如此，CS 从底层来说难度一定大于直接写 BS。

* **`writePkg`（写包函数）**

    * > **定义**：`func writePkg(conn net.Conn, data []byte) (err error)`，把「先发长度再发消息体」封装起来，和 `readPkg` 成对出现。

    * 参数直接收字节切片，因为发的时候正好就是它，不用再转成字符串。

    * 发送时不区分客户端和服务器端，一律理解为「发给对方」。

    * 发送长度后要判断 `n` 是否等于预期长度，不等就说明发送过程出错。

* **一对收发函数**

    * > **结论**：`readPkg` 和 `writePkg` 是一对，一个定义协议，一个遵守协议，双方都按这个协议来就能共用同一份实现。

    * 后续把这两个函数再封装进一个结构体里会更漂亮。

## 客户端解包

* **调用 readPkg 并二次解包**

    * `readPkg(conn)` 返回的已经是解好包的 `message.Message`，直接取它的 `Data` 部分。

    * `Data` 是字符串，要转成字节切片再 `json.Unmarshal` 成 `message.LoginResMsg`，反序列化时同样要加地址符。

    * `Code` 等于 200 说明登录成功，等于 500 说明用户不存在、需要注册，可以直接把错误信息打出来。

    * 错误描述通过结构体里的 `Error` 字段带回来。

* **容易重复提示的原因**

    * 客户端提示了两次「登录成功」，是因为主函数里原来那段判断成功的代码还在，`login` 内部已经判断过一遍，主函数那次的意义不大，注释掉即可。

    * 注释掉之后因为 `err` 没被使用而报错，把 `err` 一起删掉就行。

* **补上调度调用**

    * 服务器端 `process` 里如果没调 `serverProcessMsg`，连接建好了、消息也读到了，但就是没有任何业务处理，客户端看起来像卡住了。

    ```go
    err = serverProcessMsg(conn, &mes)
    if err != nil {
        return
    }
    ```

## 服务端分层改造的步骤

* **先摆架子再搬东西**

    * > **定义**：把一个大文件拆成小文件的正确顺序是：先按框架图建好空的文件夹和空文件，再把代码一块块剥过去。

    * 先建 `main`（主包，相当于界面层）、`process`（处理器层）、`model`（暂时空着，很快会用到）、`utils`（工具文件）四个包。

    * 先把 `main.go` 复制到主文件夹下，确认没问题了再删原文件；重要文件用「先复制、再粘贴、确认无误后删」的稳妥做法，不要一拖了事。

    * 长文给的比喻是：中国人搬家是先把家具全扔进房子再规划布局，日本人搬家是先画草图；做程序应该学后者，先规划再往里搬。

    * 先摆架子还有个好处：程序大体结构先立住了，剥的时候才有地方放。

* **剥洋葱式地一层层来**

    * > **结论**：剥离时不要一上来就剪，先复制一份再把原处注释掉，这是好习惯，否则剪完东西不知道上哪儿去了。

    * 保存后出现大量报错是正常的，此时不要急着改，先把该剥的都剥完再统一调代码。

* **每个文件的归属**

    | 代码 | 去处 |
    | :--- | :--- |
    | `readPkg`、`writePkg` | `utils` 包，每处都要用，属于工具性质 |
    | `serverProcessLogin` | `userProcess.go`，处理用户相关的逻辑 |
    | `serverProcessMsg` | `processor.go`，做分配管控，决定调哪个处理器 |
    | 监听、Accept、起协程 | `main.go` |

    * 总控放在 `process` 还是主包都可以，认为它和 `main` 关系密切的人会直接放主包。

    * `process` 包里的两个文件都是 `package process`。

* **调试的推进方向**

    * 调试时先从最底层走，哪个被调用得多就从这一层开始反着推过去。

    * > **结论**：分析是从上往下分析，写代码是从下往上写，写代码跟分析的思路刚好是逆向的。

## Transfer 传输者结构体

* **Transfer（传输者）**

    * > **定义**：分层加面向对象之后，读包写包需要一个承载者，命名为 Transfer，专门管传输。

    ```go
    type Transfer struct {
        Conn net.Conn
        buf  [1024]byte
    }
    ```

    * 连接必须有，没有连接没法传；buffer 也必须有，读的时候没必要每次新建，跟着 Transfer 实例走。

    * buffer 用数组字面量声明，用的时候当成切片用即可；数组和切片只差一处：指定起始位置时它就是切片。

    * 结构体里会用到 `net` 包。

* **把方法绑到结构体上**

    * `readPkg` 和 `writePkg` 都变成 Transfer 的方法，签名带 `(this *Transfer)`。

    * 跨包调用时方法名必须首字母大写，`writePkg` 要改成 `WritePkg`，`serverProcessLogin` 要改成 `ServerProcessLogin`；同一个包内部调用则不受大小写限制。

* **参数大撤退**

    * 连接一旦封装进 `Transfer`，`ReadPkg` 和 `WritePkg` 的 `conn` 参数就可以直接删掉，方法体里改成从 `this.Conn` 取。

    * `buf` 参数同样删掉，改成从 `this.buf` 取。

    * 所有依赖连接和缓冲的地方都要跟着改，`this.Conn.Write` 这种写法随之出现。

    * 原来函数入口处的 `buf` 声明因为不再使用要删掉或注释掉。

## UserProcess 与 Processor

* **UserProcess（用户处理器）**

    * > **定义**：服务端把连接绑到 UserProcess 实例上，处理登录、注册、注销、用户列表等用户相关的请求。

    ```go
    type UserProcess struct {
        Conn net.Conn
    }
    ```

    * > **结论**：结构体该有哪些字段，主要看将来绑定或关联的方法里需要什么。

    * 连接是必须的；buffer 不用放进来，它已经绑定在 Transfer 上了，用的时候通过 UserProcess 把连接传给 utils 就行。

    * 因为连接已经绑在实例上，方法签名里再传一遍 `Conn` 就是多余的，直接从字段取。

    * 这个实例还方便后续管理：群发、维护在线用户时可以往上加字段标明这个实例属于谁、ID 是多少。

* **Processor（总控）**

    * > **定义**：总控也是一个结构体，只有一个 `Conn` 字段，方法绑定 `(this *Processor)`。

    ```go
    type Processor struct {
        Conn net.Conn
    }
    ```

    * Processor 收到消息后按类型创建下级实例：

    ```go
    up := &UserProcess{
        Conn: this.Conn,
    }
    up.ServerProcessLogin()
    ```

    * 连接就是这样从最外层主函数一层层往下传的，到了具体处理器就不再往下传了，因为它已经隐藏在实例里。

    * 总控的方法名要避免和包名重复，临时用了 `process2` 这个名字表示第二层处理。

* **主函数只做三件事**

    * > **定义**：`main.go` 只负责监听程序、等待客户端连接、完成初始化任务（比如 Redis 连接池）。

    * 连接拿到后起协程把活交给总控，主函数不处理读包这些细节。

    ```go
    processor := &Processor{
        Conn: conn,
    }
    err := processor.process2()
    if err != nil {
        fmt.Println("客户端和服务器端的通讯协程错误 err=", err)
        return
    }
    ```

    * 协程返回值一定要接住并判断，出错就直接退出，这才是「哪一层出问题就往哪一层追」的排查依据。

* **改造后外部接口不变**

    * 这次改动相当于内部装修，对外接口没有任何变化，所以客户端一行都不用改就能照常跑通。

    * 编译服务端时必须指到新的入口，因为原来的 `server/main.go` 已经被搬走：`go build -o server.exe go_code/chatroom/server/main`。

    * 验证方式是先用不存在的用户看是否返回「该用户不存在，请注册」，再用 100 / 123456 看是否登录成功。

## 服务端改造踩到的两个坑

* **err 的 shadow**

    * 编译器提示 `err` 是 shadow 的，含义不明确，直接把 `err` 写明确即可。

* **包名和函数名撞车**

    * > **易错点**：⚠️ `process` 包和 Processor 上的 `process` 方法重名时，编译器会报重复声明。

    * 解决办法是把包名改掉，比如改成 `process2`，同时把调用处的包名一起改；`processor` 里引用这个包的地方只有一处。

    * 这个坑在写完主函数、开始连接主包和处理器时才会冒出来。

## 客户端分层的框架

* **现有结构的问题**

    * 客户端原来只有 `main`、`login`、`utils` 三个文件，比较单薄。

    * 一个登录一个文件，将来一个注册再写一个文件，一个功能对一个文件是不现实的；应该是**一个功能绑定一个文件**，即按业务分文件而不是按单个动作分文件。

* **改进后的框架**

    * `main.go`：显示第一级菜单，并根据用户选择调用对应的处理器。

    * `userProcess.go`：用户相关业务，登录、注册。

    * `smsProcess.go`：短消息相关业务，私聊、群聊、群发。

    * `fileProcess.go`：文件传输相关。

    * `voipProcess.go`：声音、视频、图片等流量大的数据，网络处理很麻烦，要单独一个处理器。

    * `server.go`：本次新增的重点。

    * `utils`：工具类，客户端与服务器端可以共用一份。

    * `model`：后面会用到。

* **客户端不写总控**

    * > **定义**：客户端的 `main.go` 直接按用户选择调用对应处理器，不设总控。

    * 原因是最复杂的逻辑在服务器端，客户端说白了就是几个菜单、发东西收东西；写一个总控按同样的思路也可以，只是做了简化。

* **utils 共用还是各写一份**

    | 形式 | 做法 | 特点 |
    | :--- | :--- | :--- |
    | 集中公用 | 抽到 `common` 包，大家都指向它 | 干净，但**必须保证同步**，那边更新这边没更新也是麻烦 |
    | 各自一份 | 各写各的，上线前再整合 | 少了同步的麻烦，整合成本很低 |

    * 两种都是常见做法，不是大事；客户端这里先单独放一份，之后再整合进公用包，工作量很小。

* **客户端的数据保存**

    * > **定义**：客户端一般不直接连数据库，因为数据库不一定装了，但会用文件形式保存聊天记录。

    * 聊天记录下次打开还在、甚至离线时也能看到别人发的图片和视频，就是因为这些东西被偷偷存进了本地文件，文件在这里充当了数据库。

    * 聊天软件提示空间已满要清理，也是因为这些文件在占着空间。

## 新增 server.go

* **三个任务**

    * > **定义**：`server.go` 负责登录成功之后的所有事情，登录成功的客户端不会马上退出，所以需要单独一个文件来承载。

    * 任务一：显示登录成功的界面。

    * 任务二：起一个协程，保持和服务器端的通讯，不停地问「有没有给我发东西」。

    * 任务三：把推送来的消息显示到界面上。

* **为什么必须有那个协程**

    * 上线之后别人可能跟你聊天、好友上线、好友离线、好友群发消息，这些客户端都要拿到。

    * 不可能反复地去取，所以登录成功后必须有一个后台协程一直在跟服务器交互；客户端流量没用却一直有传输，就是干这个的。

    * `showMenu` 之后要转到 `server` 这条逻辑上来，菜单和这个后台协程是并行存在的。

* **ShowMenu（显示登录成功菜单）**

    ```go
    func ShowMenu()
    ```

    * 先不做结构体封装，直接写一个函数把菜单显示出来。

    ```go
    fmt.Println("------------------ 恭喜，某某某 登录成功 ------------------")
    fmt.Println("1. 用户列表")
    fmt.Println("2. 发送消息")
    fmt.Println("3. 信息列表")
    fmt.Println("4. 退出系统")
    ```

    * 「恭喜某某某登录成功」里的名字要填进去，涉及信息封装，封装成 User 结构体更合适。

    * 输错选项就提示输入不对让他重输，菜单要循环显示。

    * 需要引入 `os` 包。

* **四个选项背后要什么**

    | 选项 | 功能 | 想清楚它背后要什么 |
    | :--- | :--- | :--- |
    | 1 用户列表 | 显示在线用户列表 | 多人聊天系统里怎么拿到在线用户列表 |
    | 2 发送消息 | 给在线的人发消息 | 知道谁在线后才能指定发给张三还是李四，文本界面先输对方 ID |
    | 3 信息列表 | 罗列别人跟你聊过的信息 | 类似历史记录，客户端不存数据库，用文件形式保存 |
    | 4 退出系统 | 这个人不想玩了 | 提示一句让他退了 |

* **退出前先给服务器说一声**

    * > **定义**：退出之前先给服务器发个消息说「我要走了」，比如「拜拜」，服务器收到后主动把连接关掉，这是最好的方式。

    * 之所以要这样，是因为客户端可能有很多消息还写在缓存里没入库，服务器知道用户要走时可以先把跟他相关的缓存刷盘或入库。

    * 思路可以照搬大厂 IM 的历史：微软的 MSN 靠和操作系统绑定一度抢走大量企业用户，腾讯随后出企业版 QQ 又抢了回来；雅虎通、UC 等也都砸过钱。

## 客户端 UserProcess 落地

* **迁移的三个决定**

    * 主文件复制一份到 `main` 包。

    * `login.go` 不再需要，因为不可能一个功能对应一个文件，登录逻辑要拆到 `userProcess` 里。

    * `utils.go` 直接从服务端复制一份过来，读写逻辑两边完全一样，先保留客户端原来那份以防出问题。

* **同名文件不用刻意区分**

    * 客户端的 `userProcess.go` 和服务端同名没关系，不用特意取成 `server_userProcess` 这种名字，两个在不同的大文件夹下本来就能区分。

* **UserProcess 暂时不要字段**

    * > **结论**：客户端的 UserProcess 暂时不需要任何字段，分析方法是回溯原来的 login 用了什么。

    ```go
    type UserProcess struct {
    }
    ```

    * 连接不需要，因为它自己就能拿到；传输时直接在这儿创建一个 Transfer 就行，buffer 也不用放。

    * 只是暂时不需要，将来要管理在线用户时可以往上加字段。

* **login 变成方法**

    ```go
      func (this *UserProcess) Login()
    ```

    * 为了访问方便把它改成大写，方法名和里面调用的 `WritePkg` 都要大写。

* **main.go 的调整**

    * 创建实例再调用方法：

    ```go
    up := &process.UserProcess{}
    up.Login(userId, userPwd)
    ```

    * 结构体是空的所以一行就写完，注意要引入 `process` 包。

    * 原来那段收用户 ID 和密码的代码可以提到上面去，`key` 和 `loop` 因为登录后已经进入第二级菜单而失去意义，可以直接删掉。

* **登录成功后进二级菜单**

    * 登录成功后不能什么都不干就跑路，必须调用 `ShowMenu` 并循环显示菜单。

    * 循环放在外面还是放在 `ShowMenu` 内部都行，放里面可能更好一点，两种写法没有区别。

    * `server.go` 和 `userProcess.go` 同属 `process` 包，所以互相调用不需要再引包。

## 客户端的后台协程

* **`serverProcessMes`（保持通讯的协程）**

    * > **定义**：`func serverProcessMes(conn net.Conn)`，登录成功后用 `go` 起来，专门保持与服务器端的通讯。

    ```go
    func serverProcessMes(conn net.Conn) {
        for {
            tf := &utils.Transfer{
                Conn: conn,
            }
            mes, err := tf.ReadPkg()
            if err != nil {
                fmt.Println("服务器端出错了，读出错 err =", err)
                return
            }
            fmt.Println("message =", mes)
        }
    }
    ```

    * 必须传连接进来才能保持通话，而且跟服务器的连接只有一个，userProcess 那一方是能拿到的。

    * 调起方式就是在登录成功后 `go serverProcessMes(conn)`，只起一次，之后它就一直等读。

    * `tf.ReadPkg()` 返回的 message 已经是解好包的，消息到底是什么类型在这里就能拿到。

    * 需要引入 `utils` 包。

* **推送与 get**

    * > **定义**：服务器主动发过来的叫推送，客户端自己去取才叫 get。

    * 比如张三给用户发了消息，服务器直接推给客户端，客户端接收并显示在终端上。

* **阻塞的前提**

    * > **注意**：这里会一直阻塞在读取上，前提是对方不关闭连接；连接畅通时它就一直问「有没有东西」，对程序效率没有影响。

    * 读出错说明对方可能关闭了连接或服务器出问题，这时提示一句并 return，不要死循环下去。

    * 目前先把这个 message 打出来，后面再接「下一步处理逻辑」。

* **空指针 bug**

    * > **易错点**：⚠️ 运行时报空指针异常，原因是创建 `Transfer` 实例时没有把 `Conn` 赋进去，读的时候从 `tf.Conn` 取出来的是零值。

    * 把 `Conn: conn` 补上即可，注意传进来的 `conn` 要小写、指向实例字段。

    * 修好后表现是：菜单正常显示，客户端停在等待读取服务器消息那里，输 1 能正常响应，而后台协程仍在后台读。
