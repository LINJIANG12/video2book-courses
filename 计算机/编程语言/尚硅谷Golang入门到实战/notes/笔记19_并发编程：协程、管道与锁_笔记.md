# 并发编程：协程、管道与锁

## 协程与主线程

### 协程的由来

* **协程（goroutine）**
    * > **结论**：协程可以理解为是轻量级的线程。

    * 演进路径是：最早只有一个进程干一件事 → 引入线程以发挥 CPU 能力 → 发现线程仍然吃资源（占用 CPU 和内存偏多，部分仍在物理态）→ Go 的设计者把线程改造成逻辑态，在算法和编译器上做优化，让它更轻巧、占用更小。
    * 底层优化的核心是协程之间能做到资源共享，线程与协程原本可共享的东西被直接共享。
    * 因为变轻了，Go 里可以轻轻松松起上万个协程而且非常稳定；C、C++ 那种内核态线程几千个就可能耗光 CPU。

### 主线程与协程的关系

* **Go 主线程**
    * 有程序员直接把它叫线程，也可以理解成进程，叫法不同、本质没有变化。
    * 一个主线程上可以起很多协程；主线程是物理线程，直接落在一颗 CPU 上，属于重量级，由操作系统控制。
    * 协程是从主线程开启的，是逻辑态，资源消耗相对小。

    ```text
            ┌──────────────────────────────────────────────┐
            │  Go 主线程（有人直接叫"线程"，也可看成进程）  │
            │  物理线程，直接落在一颗 CPU 上，重量级         │
            └──────────────────────────────────────────────┘
                │      │      │      │      │      │
                ▼      ▼      ▼      ▼      ▼      ▼
              协程1  协程2  协程3  协程4  协程5  ...  协程N
                └─ 可以轻轻松松地起上万个协程，还非常稳定 ─┘
    ```

    * > **易错点**：别和“携程”混为一谈。

* **退出规则**
    * > **结论一**：主线程一旦退出，协程即使还没执行完也会被连带干掉。

    * > **结论二**：协程也可以在主线程退出前先完成自己的任务，主线程不会因为某个协程结束就跟着退出。

    * 总体上一定是以主线程的退出为准。

* **执行流程**
    * 遇到 `go test()` 时主线程立刻分叉出协程，自己不阻塞，继续往下执行自己的循环。
    * 主线程执行完毕后退出，尚未完成的协程随之被终止。

    ```text
       主线程（进程）          协程 test()
            │                      │
      开始执行                    │
            │                      │
            ├── go test() ───────►│  立刻分叉，不阻塞
            │                      │
       for 循环 第1次             ├─ 循环第1次
            │                      ├─ time.Sleep(1s)
       for 循环 第2次             ├─ 循环第2次
            │                      ├─ ...
            ▼                      │
       主线程执行完毕 ──────────────┤
            │                      │
       （主线程已退出）              ▼
                                协程被连带干掉
    ```

### 四个特点

* **协程的特点**
    * 有独立的栈空间，开启后各协程的数据空间互不干扰。
    * 共享程序的堆空间。
    * 调度由程序员（用户）控制，协程的开启与终止完全可由程序员决定。
    * 可以理解成是轻量级的线程。

    * 第三点要单独拎出来说，是因为进程做不到这一点：进程什么时候被调度起来、分配到哪里由操作系统决定，程序员控制不了。

## MPG 调度模型

### M、P、G 的含义

* **M（machine）**
    * 对应操作系统的一个主线程，是物理级线程，比较耗费资源。

* **P**
    * > **定义**：执行过程中的上下文环境，可以理解为运行时所需资源和当时的系统状态。

    * 抽象但不难类比：人要生活得有空气有水，协程要运行也得依赖当前操作系统环境——还有没有内存可分配、还有没有 CPU 可分配。

* **G（goroutine）**
    * 就是协程本身；运行过程中开启的协程挂在这里，甚至可以形成队列，一个节点还能再继续开协程。

### 静态与动态模式

* **静态模式**
    * 三个 M 都运行在同一颗 CPU 上就是并发；三个 M 分别落在不同 CPU 上就是并行。
    * 每个 M 正在执行一个 G，同时各自还挂着一个待执行的 G 队列。

    ```text
            ┌──────┐       ┌──────┐       ┌──────┐
            │  M1  │       │  M2  │       │  M3  │
            │ CPU1 │       │ CPU1 │       │ CPU1 │   ← 全挤一颗 = 并发
            └──┬───┘       └──┬───┘       └──┬───┘
            ┌──┴──┐       ┌──┴──┐       ┌──┴──┐
            │  G1  │       │  G1  │       │  G1  │   ← 各执行一个 G
            ├─────┤       ├─────┤       ├─────┤
            │G3→G2│       │  G2  │       │     │   ← 排队的 G
            └─────┘       └─────┘       └─────┘


            ┌──────┐       ┌──────┐       ┌──────┐
            │  M1  │       │  M2  │       │  M3  │
            │ CPU1 │       │ CPU2 │       │ CPU3 │   ← 一人一颗 = 并行
            └──┬───┘       └──┬───┘       └──┬───┘
            ┌──┴──┐       ┌──┴──┐       ┌──┴──┐
            │  G1  │       │  G1  │       │  G1  │
            ├─────┤       ├─────┤       ├─────┤
            │G3→G2│       │  G2  │       │     │
            └─────┘       └─────┘       └─────┘
    ```

* **动态模式：G 被阻塞**
    * 读文件、读数据库这类操作耗时不确定，协程一旦被阻塞，底层会从线程池取出或新建一个 M，把等待的 G 队列整个挂上去执行。
    * M0 继续完成它原先 G0 的读写，解除阻塞后再放回空闲态。
    * 好处是既让 G0 去读文件，又不让队列里其它协程一直阻塞没有执行机会。

    ```text
       【阻塞前】
          M0 (CPU1) ──执行──► G0
                │
                └─► 队列:  G1 ◄── G2 ◄── G3      (干等着)


       【G0 被阻塞的瞬间】
          ┌───────────────┐                ┌───────────────┐
          │    M0 (CPU1)  │                │    M1 (CPU2)  │
          │  卡在 G0 上    │                │  从线程池唤醒  │
          │  （在读文件）  │                │  或者新建      │
          └───────────────┘                └───────┬───────┘
                                                   │ 把等待队列整个挂上来
                                            G1 ◄── G2 ◄── G3
                                                   │
                                            开始轮流执行

       【G0 不阻塞之后】
          M0 读文件完毕 → 又被放回空闲态，继续执行 G0
    ```

* **餐馆类比**
    * 厨子相当于主线程；客户 A 点的菜多且有一道需要先泡发海鲜，厨子在这段时间是闲着的，于是先给排队的客户 B 炒一份，海鲜泡好后再回头继续。
    * 时间尺度的误解要澄清：所谓五分钟是人的时间单位，计算机里片段极短，来回一切可能 0.01 毫秒就切一次，这样才把 CPU 利用起来。

## CPU 数目的设置

* **runtime.NumCPU**
    * 返回本地机器的**逻辑 CPU** 个数，不一定等于真实物理 CPU 颗数（物理两颗也可能逻辑上呈现为四颗）。

* **runtime.GOMAXPROCS**
    * 设置可同时执行的最大 CPU 数，可以全部用上，也可以留一颗给别的程序。
    * 全部占光可能让别的程序瞬间跑不起来，所以按实际情况定，例如 `runtime.GOMAXPROCS(cpuNum - 1)`。

    * > **易错点**：两个函数名里的 CPU、PROCS 全部是大写字母。

    * > **版本边界**：Go 1.8 以后程序默认跑在多核上，通常不必专门设置 `GOMAXPROCS`；1.8 以前需要手动设置才能更高效地利用 CPU。

## 阶乘案例与并发写 map

### 需求与思路

* **需求**
    * 计算 1 到 200 各个数的阶乘并放入 map，最后显示，要求使用 goroutine 完成。

* **三点分析**
    * 写一个函数算某个数的阶乘并写入 map。
    * 要多起协程才有效率，因此起 200 个协程各算一个数。
    * 因为多个协程都要访问同一个 map，所以这个 map 必须定义成全局变量，并事先 `make` 好空间。

* **主线程早退**
    * 直接跑起来一个结果都没有：起 200 个协程后主线程立刻结束，协程还没执行完就被连带终止。
    * 最笨的办法是让主线程 `time.Sleep(time.Second * 10)` 等 10 秒。
    * 等待时长本身就是问题——等 10 秒会有人问为什么不等 20 秒，说明主线程何时退出与协程何时完成之间缺乏机制。

### concurrent map writes

* **并发写报错**
    * 加了 10 秒休眠后仍然报 `fatal error: concurrent map writes`，含义是并发向 map 写入。
    * 成因是 200 个协程同时往同一块 map 空间写，至少 4 个 CPU 在同一瞬间写入同一个数据空间。
    * 规律是写不能有并发、必须保护，读可以；两个人同时看一本书没问题，同时在一张纸上写就会出问题。

    ```text
          ┌──────────────────────────────────────────────┐
          │   全局 myMap （没有任何保护机制）              │
          └──────────────────────────────────────────────┘
              ▲          ▲          ▲          ▲
              │          │          │          │
          go test(1)  go test(2)  go test(3)  go test(4)   ... 共 200 个
          算完就写     算完就写     算完就写     算完就写

       CPU1 ─┐
       CPU2 ─┼─► 同一瞬间，多个 CPU 往同一块空间写
       CPU3 ─┤
       CPU4 ─┘
    ```

* **-race 检测**
    * 用 `go build -race main.go` 编译后执行可把竞争关系抓出来。
    * 输出中会给出 `Found 4 data race`，表示有 4 处数据在写入瞬间产生过竞争；虽然跑出了结果，但存在竞争关系。

## 互斥锁解决资源竞争

### 加锁思路

* **排队模型**
    * 协程来操作共享空间前先看锁：拿到锁就执行，执行完解锁；没拿到就进队列排队。
    * 后来者依次排在前一个后面，队伍里没人有资格动手。
    * 前一个解锁后，底层机制从队列里取出排在最前面的协程让它工作。

    ```text
            全局 myMap
       ┌───────────────────────┐
       │                       │◄──── 只有拿到锁的人能进来
       └───────────────────────┘
            ▲        ▲        ▲
            │        │        │
          go(1)    go(2)    go(3)      ← 全都往同一块空间写

       ═══════════  等候队列（谁先来谁先走）═══════════
          go(2)  ──►  go(3)  ──►  go(4)
                        ↑
                队伍里的一个都没资格动手
    ```

    * 类比单个坑位：先进的人把门关上，后面的人只能排队，出来的人进去时还得再把门锁上。

### sync.Mutex

* **sync.Mutex**
    * `sync` 是 synchronize（同步）的缩写，提供基本同步单元如互斥锁；`Mutex` 是互斥的意思，我用了你就不能用，属于写锁（另有读锁）。
    * `Lock` 锁住 `m`，若已加锁则阻塞直到解锁；`Unlock` 解锁。
    * 用法是操作共享数据前 `lock.Lock()`，操作完立刻 `lock.Unlock()`；漏掉解锁别人会一直等下去。

    ```go
    var (
        myMap = make(map[int]uint64, 10)
        lock  sync.Mutex
    )
    ```

    * > **提示**：官方手册对这个包的定位有一句耐人寻味的话——它适用于低水平的程序员，高水平的同步应该用 channel。

    * 加锁后重新 `go build -race` 编译运行，写入处不再报竞争错误。

* **读的时候也要加锁**
    * 只在写处加锁后 `-race` 依然报竞争，说明遍历 map 的读操作处也存在竞争，读同样需要加锁。

    * > **结论**：主线程并不知道你休眠的是 10 秒还是 3 秒，它可能去试探性地测试资源、看看锁还在不在，于是读这边也构成资源竞争。

* **map[185] 为什么是 0**
    * map 的值类型是 `uint64`，有符号 64 位最大能存 $2^{63}-1$；阶乘增长极快，20 的阶乘就已经存不进去，越界后表现为 0。
    * 这不是代码写错，把数据量调小（例如算到 20 的阶乘）就正常了。

* **全局锁的不足**
    * 主线程等待所有协程完成的时间很难确定，不设休眠则一个结果都拿不到，设成 10 秒也只是估算。
    * 时间设长了拉长等待，设短了协程还没干完就被主线程退出连带销毁。
    * 靠全局变量加锁实现通讯不利于多线程读写全局变量，要逐处分析哪里该加锁，少加一处就出问题。
    * 结论是需要一种新机制，即 channel。

## channel 的本质与声明

### 队列本质

* **channel（管道、信道）**
    * > **定义**：channel 的本质是一种数据结构，即队列。

    * 写入时新数据追加到队尾，读取时从队头取走，规则是**先进先出**（First In First Out，FIFO），与栈的先进后出相反。
    * > **结论**：channel 本身是**线程安全**的，多个 goroutine 对同一个 channel 读写都可以直接用、无需加锁，安全性由编译器在底层维护；内部其实也有锁机制。

    * > **结论**：channel 本身是**有类型的**，声明成 `int` 就只能放 `int`，放别的类型报错；实在要混用可以声明成 `interface{}`，但取出时要做类型断言，一般不建议混用。

    ```text
                  写 入 符  ←                    →  读 取 符

                 ┌────────────────────────────────────┐
       10   ──► │  10   │   211  │   50   │          │ ──► 读走队头
       211  ──► │       │        │        │          │ ──► 再读下一个
       50   ──► │       │        │        │          │
                 └────────────────────────────────────┘
                     ▲                        ▲
                   队头                     队尾（新数据追加在这）
                 最先放进来               后放进来
                 最先被读走               最先被读走 = 先进先出
    ```

### 声明与 make

* **声明语法**
    * 基本形式是 `var 管道名 chan 元素类型`，例如 `var intChan chan int`。
    * 除基本类型外，channel 里也可以放结构体、结构体指针、map 等。
    * 元素类型也可以直接写成 `interface{}` 来接受任意数据类型。

* **必须 make**
    * > **结论**：channel 是**引用类型**，且**必须初始化才能写入数据**，即 `make` 之后才能使用。

    * `make(chan int, 3)` 中 `3` 是容量、`int` 是元素类型；打印出来是一个地址，且这个地址与变量本身的地址 `&intChan` 不相同，地址指向真正的队列。

    * > **结论**：因为是引用类型，把 channel 传给另一个函数时，函数里操作的就是同一个管道。

    ```text
       &intChan                intChan
      (变量本身的地址)        (变量里存的值)
          0xc000...             0xc000...        ← 两个地址不一样
                                │
                                ▼
                       ┌─────────────┐
                       │ 真正的队列   │  cap = 3
                       └─────────────┘
    ```

## channel 的读写

### 写入与容量

* **写入**
    * 用 `intChan <- 10` 写入，写入的可以是常量也可以是变量。
    * 容量在 `make` 时定多大就是多大，一般不会动态增长；写多了会直接爆仓并报 `fatal error: all goroutines are asleep - deadlock!`。
    * 写入后 `len` 增长而 `cap` 不变；管道装满时 `len` 与 `cap` 相等，再写就死锁。

    ```text
       写满（len=3, cap=3）              取走一个（len=2, cap=3）
       ┌────────┬────────┬────────┐      ┌────────┬────────┐
       │  10    │  211   │   50   │  ──► │  211   │   50   │  ──► 又能塞新数据
       └────────┴────────┴────────┘      └────────┴────────┘
          再写一个 → deadlock                cap 始终是 3
    ```

* **管道的价值**
    * 容量上限不是问题，核心在于**一边放一边取**；取走一个就又能往里面加。
    * 类比现实中的水管，水一直在流动；水静止不动的那就不叫水管，叫水池。
    * 适用的正是“流动的数据”这类需求：一边放、一边被另一个人读走，两者之间的通讯机制也就自动形成了。

### 读取

* **读取**
    * 用 `num2 = <-intChan` 把数据弹出交给变量，读到的必然是先放进去的那个。
    * 读一次 `len` 减 1，`cap` 始终不变；剩余数据会依次前移。
    * 在没有使用协程的情况下，数据全部取完后再取会报 `fatal error: all goroutines are asleep - deadlock!`，错误信息是 `chan receive`。

### 三条注意事项

* **注意事项**
    * channel 只能存放指定的数据类型，声明成 `int` 放入 `10.9` 会报 `constant 10.9 truncated`。
    * 数据放满以后不能再放；**但只要取走数据就可以继续放**，这是 channel 最重要的价值。
    * 在没有使用协程的情况下，数据取完后再取会报错；放三个先取一个再继续放就不会报错。

* **取出来也可以不接收**
    * 写成 `<-intChan` 而不赋给任何变量是合法的，代表把数据取出来直接扔掉。
    * 有时候确实只想丢弃某个数据，这时就用这种写法。

* **可存放的六类数据**
    * 基本数据类型；map（注意放入前要先 `make`）；结构体；结构体指针；`interface{}` 接受任意类型；以及作为练习题的第六类。
    * 用 `allChan := make(chan interface{}, 3)` 这种写法在开发中更简洁。

## 空接口取值与类型断言

* **从 interface{} 取值**
    * 定义成 `chan interface{}` 后依次放入整数、字符串、结构体，取出时因为接收变量类型是 `Cat`，打印出的类型确实是 `main.Cat`。

    ```text
    newCat=main.Cat
    newCat={小花猫 10}
    ```

* **为什么不能直接取字段**
    * 紧接着访问 `newCat.Name` 会报错 `newCat.Name undefined (type interface {} is interface with no methods)`。
    * > **结论**：从 `interface{}` 里取出来的值，**编译层面它仍然是 `interface{}`**，要访问字段必须先做类型断言；打印类型是运行层面的事，取字段是编译层面的事，两者不是一回事。

    * 正确写法是先断言成具体类型再访问字段，`a := newCat.(Cat)` 之后 `a` 才是真正的结构体实例。

* **只能按顺序取**
    * 空接口管道里混着多种类型时，取第三个必须先把前两个取走或丢弃；想“想取哪个取哪个”那就不是队列了，不要用管道。

## 关闭与遍历

### close

* **close（内置函数）**
    * 关闭 channel 后**不能再写入，但仍然可以读取**，这是它最重要的特性。
    * 写在 `builtin` 包里，文档说明该通道必须为双向或只发送的，只应由发送者执行；效果是在最后发送的值被接收后停止该通道，此后任何接收操作都不再阻塞。
    * 往已关闭的 channel 写会 `panic: send on closed channel`，读则照常。

    * 类比买票时管理员把大门关上：不让再进队了，但已在排队的人照样能买完票离开；相当于加了一把只有 lock 没有 unlock 的写锁。

* **接收的两个返回值**
    * 接收语句可以写成 `n, ok := <-ch`，`n` 是取到的值，`ok` 表示是否成功取到；读到关闭标志时 `ok` 变成 `false`。

### for range

* **为什么不能用普通 for 循环**
    * 最大问题是长度会变化：放 100 个数据用 `for i := 0; i < len(ch); i++` 只会取出一半，后一半的循环条件因为长度递减而提前失效。
    * 用 `cap` 当条件同样不行，容量不代表实际数据量。
    * 管道本身是队列，没有下标，所以也不能“跳过某些数据去取”，返回值也不含下标，`for range` 出来只有值这一个变量。

* **遍历前必须 close**
    * > **结论**：channel 没有关闭时，`for range` 取完所有数据后还会傻乎乎再去取，报死锁错误；关闭之后才会正常遍历完并退出遍历。

    * 关闭带来的价值是：协程干完活顺手 `close` 一下管道，主线程遍历退出就意味着这件事做完了，可以确定收工时机，不再靠猜几秒。

    ```go
    intChan2 := make(chan int, 100)
    for i := 0; i < 100; i++ {
        intChan2 <- i * 2
    }
    close(intChan2)

    for v := range intChan2 {
        fmt.Println("v=", v)
    }
    ```

## 协程配合管道的综合案例

### 三段式骨架

* **需求**
    * 开启 `writeData` 协程向 `intChan` 写入 50 个数据；开启 `readData` 协程从 `intChan` 读取；主线程要等到两者都完成工作才退出。
    * 这里不能再用 `sleep`，也不能完全不处理——完全不处理主线程会瞬间退出，数据还没写完就没了。

* **结构**
    * 两个数据管道在主线程里创建：`intChan` 容量 50 供一读一写同时进行，`exitChan` 容量 1 装退出信号。
    * `readData` 读完 50 个之后往 `exitChan` 写入一个 `true`，然后 `close(exitChan)`。
    * 主线程 `for` 循环读 `exitChan`，读到取不到时（`ok` 为 `false`）就 `break` 退出。

    ```text
                  ┌──────────────────────────────────┐
                  │           主线程（进程）            │
                  │  创建两个管道 → 创建两个协程 →      │
                  │  然后一直守着 exitChan 不撒手       │
                  └───────┬──────────────────┬────────┘
           go writeData  │                  │ go readData
                          ▼                  ▼
                  ┌────────────┐      ┌────────────┐
                  │ writeData  │      │  readData  │
                  └─────┬──────┘      └──────┬─────┘
                        │  写                 │  读
                        │                     │
           ┌────────────┴─────────────────────┴─────────┐
           │                 intChan                     │
           │        （容量 50，先进先出，一边写一边读）    │
           └────────────────────────────────────────────┘
                                                           │
       readData 读完 50 个之后，顺带报个信：                  │
                                                           ▼
                                            ┌─────────────────┐
                                            │    exitChan     │
                                            │  写入 true 然后  │
                                            │     close()     │
                                            └────────┬────────┘
                                                     │ 主线程循环读
                                                     ▼
                                            读不到东西了 → break → 退出
    ```

* **close 在读侧的作用**
    * `readData` 的 `close` 只是标记“发送方干完了”，并不影响读；它要一直读到 50 个全部取完、`ok` 为 `false` 时才 `break`。
    * 不 `close` 这里就会死锁，所以一定要 `close`。

* **主线程必须有事可做**
    * 什么都不做的话主线程秒退，两个协程一起没命；类比鬼附身，人没了鬼就得另找宿主。
    * 用 `sleep` 也能跑通，但那正是要解决的问题。去掉 `sleep` 后输出会全挤在一起，说明读写确实是交叉进行的。

### 死锁从哪里冒出来

* **只写不读会死锁**
    * 把 `readData` 注销后，`intChan` 只有写没有读；容量 10 却要写 50 个，阻塞发生在**往管道里放数据的那一行**。

    * > **注意**：运行时如果发现一个管道只有写而没有读，该管道就会阻塞。

* **写得快读得慢为什么不死锁**
    * 编译器会做底层分析，发现虽然写入方会阻塞，但确实有另一个协程在读，就没有死锁；这种阻塞是**有效阻塞**，我进一个才能推进一个。
    * 反之它分析出没有任何协程在读，就会判定 deadlock。
    * > **一定要记住**：写管道和读管道的先后位置无所谓，但一定要让它对应起来。

* **阻塞位置**
    * 注销 `readData` 后，错误分别出现在 `writeData` 里的写入行，以及主线程读取 `exitChan` 的那一行（因为没人关闭它，永远等不到标志）。

## 协程求素数

### 三管道结构

* **需求与思路选择**
    * 需求是统计 1 到 20 万中哪些是素数，实际演示缩小到 8 万，再缩到 80 做验证、放到 8000 跑一遍。
    * 传统循环功能正确但只有一颗 CPU 在算，发挥不出多核优势；改进思路用并发加并行，把任务分给四个协程，正好对应四颗逻辑 CPU，构成纯并行模式。
    * 若开八个协程则是并行加并发的混合：八个协程挤在四颗 CPU 上，每颗要切两次。

    ```text
              +-------------------------------------------+
              |              main goroutine               |
              +-----------------------------------------+
                            |
                  +-------------+-------------+-------------+
                  v             v                           v
       +----------+      +----------+      +----------+
       | intChan  |      | primeChan|      | exitChan |
       |   int    |      |   int    |      |   bool   |
       |  cap1000 |      |  cap1000 |      |  cap 4   |
       +----------+      +----------+      +----------+
            |                 ^                  ^
            v                 |                  v
       +----------+      +----------+      +----------+
       |putNumber |      | prime x4 |      | main read|
       +----------+      +----------+      +----------+
    ```

* **intChan：存放待判定的数字**
    * 由 `putNumber` 协程往里扔 1 到 8000，放完循环自然退出，退出时 `close(intChan)`。
    * 容量故意只开 1000，容量小才有阻塞，读写才真正交互起来，看得出管道在干什么。

* **primeChan：存放素数结果**
    * 四个 `primeNumber` 协程不断从 `intChan` 取数，判断后把素数放进 `primeChan`。
    * 容量必须真实容纳 1 到 8000 里的所有素数，先开 1000 保险；能否开小一点边写边读属于后续优化，现在不好估算，先跑通跑对。

    * > **易错点**：不能把素数放回 `intChan`，那是生产端的数据源，放回去就混在一起、等于死循环。

* **素数判定逻辑**
    * 乐观地先把 `flag` 置 `true`，然后 `for i := 2; i < num; i++`，一旦 `num % i == 0` 就把 `flag` 置 `false` 并立刻跳出内层循环。
    * 扫完一遍 `flag` 仍为 `true` 就说明是素数，投进 `primeChan`。

* **exitChan：退出机制**
    * `primeNumber` 取不到东西时，往 `exitChan` 写一个 `true` 表示自己完成了，写完就退出。
    * 主线程从 `exitChan` 里读，最终四个协程都完成则管道里正好有四个 `true`；主线程取出四个 `true` 就说明整个任务完成，也说明 `primeChan` 数据完整。

    ```text
       primeNumber 协程             exitChan              main 主线程
       （做完了就走）                                    （只数个数）
            |
            +-- 取不到 intChan 了 -----------------------+
            |                                             |
            +--> exitChan <- true  ------------------+    |
                                                      |    |
            primeNumber 协程（第二个）                  |    |
            +-- 取不到 intChan 了 -------------------+  |    |
            +--> exitChan <- true  -----------------+    |    |
                                                        |    |
            primeNumber 协程（第三、四个）…              |    |
            +--> exitChan <- true  x2 -------------+      |    |
                                                        v    v
                                                       exitChan
                                                       取出 4 个 true
                                                             |
                                                     全部工作完成
                                                            |
                                                         close(primeChan)
    ```

    * 设计要点是协程之间的退出互不依赖：我做完了就报个信然后走，不管别人做完没有。
    * 用“判断整体结果出来才许退出”的办法效率发挥不出来，因为某个协程干完了还被硬拽着不退出，只能空转。

    * > **易错点**：`primeNumber` 退出是因为自己取不到数据，不意味着别人也取不到，别人可能正在处理，所以此时**不能关闭 `intChan`**，安全起见只往 `exitChan` 写标志。

    * 主线程的等待逻辑放在匿名协程里，从 `exitChan` 取满四个才 `close(primeChan)`，这样遍历才能正常退出；这段不需要的值直接扔掉，只关心取满四个。

* **运行中的现象**
    * 小数据量时第一次跑好像秒退，并不是取不到值就退出了，而是**打印的时机和处理数据的时机不同步**——处理早已完成，打印还没来得及输出。
    * 在遍历前加 `time.Sleep(10 * time.Millisecond)` 让取慢一点，输出顺序就正常了；数据量大时不会出现这个问题。

    * 代码里写在末尾的打印最先输出，是因为它是同步的：程序一跑起来各方同时工作，不是按行顺序一步步等你。

    ```text
    代码里书写的顺序                          运行时实际发生的事

      go putNum(intChan)          ┐
      go primeNum ×4              ├─▶  四个协程同时开跑
                                  │    素数一个一个进 primeChan

      go func(){ 等 4 个 true      │
                    close(primeChan) }
                                  │
      ┌───────────────────────────┴────────────────────────────────┐
      │ 下面这段打印，代码位置排在最后，但输出却最先冒出来        │
      │                                                            │
      │   fmt.Println("素数=", res)   ← 素数早就躺在管道里了      │
      │   ...                                                        │
      │   fmt.Println("主线程退出")   ← 这句反而最后才打印        │
      └────────────────────────────────────────────────────────────┘
    ```

### 效率实测

* **计时口径**
    * 起始点是 `putNum` 开始工作时的 `time.Now().Unix()`，结束点是拿到四个退出标志的时刻，再打印 `end - start`。

    * > **易错点**：不能把结束点算在打印那里，打印跟任务完成与否没有关系。

    * > **提示**：为了看出效果要把数据调到 8000 并先把打印注释掉，打印太费时间。

* **实测对比**

| 写法 | 数据量 | 耗时 |
| :--- | :---: | ---: |
| goroutine + channel（4 个协程） | 80000 | 约 2 秒 |
| 传统单线程 for 循环 | 80000 | 10 秒 |

    * 提升大于等于 4 倍，且这个倍数与 CPU 核心数密切相关，换到 16 核、32 核的服务器提升会更强。
    * 任务管理器的观感印证了这一点：协程版运行时 CPU 使用率蹭地上到 100%，传统版只占约 20%，还有三颗在空转。

    ```text
      协程版 main.go                传统版 test.go
      ┌─────────────────────┐      ┌─────────────────────┐
      │ ████████████████████│ 100% │ ████                │  ~20%
      └─────────────────────┘      └─────────────────────┘
      4 个协程 × 4 颗 CPU          单线程只占住一颗
      已经把并行度吃满              还有 3 颗在空转
    ```

    * > **结论**：想提高速度可以考虑用协程，但提高的是“利用率”，不是“协程数量”——协程数量要与 CPU 核心数配套。

* **开八个协程反而更慢**
    * 从 4 个改成 8 个，结果从约 2 秒变成 3 秒，变慢了。
    * 要改的地方只有三处：`primeNum` 循环上限、等待标志的循环次数、`exitChan` 的容量，其余不用动。
    * > **结论**：不能认为开多少协程速度就上去了，多开不一定更快。

* **思路优先于实现**
    * 讲这套机制的目的是让人遇到同类场景时能想到扩展，而不是一招套天下；写编程始终在做“思路 → 实现”，思路理清后代码是分钟级的事。

## 管道方向：只读与只写

* **方向属性**
    * > **定义**：channel 可以声明为只读或只写的性质，默认声明是双向管道，既可读也可写。

    * 只写写成 `var chann2 chan<- int`，箭头在 `chan` 后面；只能往里写，取出来会报 `invalid operation`，提示是 send-only。
    * 只读写成 `var chann3 <-chan int`，箭头在 `chan` 前面；能读，写会报 `invalid operation`，提示是 receive-only。

    * > **易错点**：类型不能乱写。`chan<- int` 是一种性质，实际装的仍是 `int` 类型的东西，不要把“只写”写进元素类型里。

* **在形参上收敛方向**
    * 标准写法是把形参声明成 `func send(ch chan<- int, exitChan chan struct{})` 或 `func recv(ch <-chan int, exitChan chan struct{})`。
    * 这样在函数内部做反向操作会直接编译报错，能有效防止误操作；底层也据此做了优化，效率更高。

    * > **结论**：只读只写不是类型而是属性，双向管道传进这种形参后**类型仍然是 `chan int`**，只是把不允许的那一侧操作封起来了；类比人分男、女但都还是人。

## select

* **select**
    * > **定义**：使用 `select` 可以解决从管道取数据的阻塞问题，让你不关闭管道也能正常退出。

    * 传统办法必须 `close` 才不会在遍历时死锁，但有时确实判断不好什么时候关闭，复杂需求下容易卡住；`select` 提供了另一条路。

    ```go
    for {
        select {
        case v := <-intChan:
            fmt.Printf("从 intChan 读取了数据%d\n", v)
        case v := <-stringChan:
            fmt.Printf("从 stringChan 读取了数据%s\n", v)
        default:
            fmt.Printf("都取不到了，不玩了\n")
            return
        }
    }
    ```

    * 即使管道已关闭、取不到数据也不阻塞，会自动往下走到下一个 `case` 继续尝试，直到所有 case 都取不到才走 `default`，此时可以自己决定退出还是做别的事。
    * 它完全不依赖 `close`，因此解决了“不知道何时关闭”的麻烦。

    * > **易错点**：`stringChan` 取出来是字符串，格式串必须用 `%s` 而不是 `%d`，写错会编译报格式错误。

    * 取值的先后顺序不好控制，与当前的上下文环境有关；观察到的现象是先从能取到的那条管道取值。

* **跳出 select**
    * 直接 `break` 没用，它只跳出 `select` 而跳不出外层循环。
    * 两种解决办法：一是外面包一个协程，用 `return` 直接结束整个协程；二是给外层 `for` 加 label 再 `break label`。
    * > **结论**：推荐用 `return`。写了 `return` 下面的代码没有机会执行，而 `break` 之后下面的代码还能执行；label 在开发中用得很少，尽量不要用。

## 协程中的 panic 与 recover

* **panic 的传染性**
    * 协程里出现一个未被捕获的 `panic` 会导致整个程序崩溃，即使其他协程本身毫无问题。
    * 例如一个协程声明了 `var myMap map[int]string` 却直接赋值、忘了 `make`，另一个协程在正常输出，结果主线程刚输出一条就整体崩掉。

    ```go
    func test() {
        var myMap map[int]string
        myMap[0] = "golang" // error
    }
    ```

    * > **易错点**：看起来两个函数都没问题，但一个协程里的错误会把整个程序带走。

* **defer 加 recover 兜底**
    * > **结论**：在 goroutine 中用 `recover` 捕获并处理 `panic`，即使该协程出问题，**主线程不受影响，其它协程也不受影响**，仍可继续执行。

    * 写法是在函数开头 `defer` 一个匿名函数，在其中 `if err := recover(); err != nil` 判断并打印；`recover` 返回一个 `error` 值，不为 `nil` 就说明确实发生了错误。
    * 捕获后可以发邮件或预警通知管理员，由管理员处理有问题的协程。

    * > **易错点**：这是匿名函数，必须在末尾打一对小括号调用它；有参数时还要把参数传进去。

    ```go
    func test() {
        defer func() {
            if err := recover(); err != nil {
                fmt.Println("test() 发生错误", err)
            }
        }()

        var myMap map[int]string
        myMap[0] = "golang" // error
    }
    ```
