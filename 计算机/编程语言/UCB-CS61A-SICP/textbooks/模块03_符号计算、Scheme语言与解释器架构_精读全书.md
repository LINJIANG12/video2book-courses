## 探索上帝的编程语言：Scheme 语法、求值模型与符号列表
> 对应块：BLK19 | 覆盖分集：P26-P27 | 块标题（分集名）：《Lecture 28 Scheme-cn》

迄今为止，你已经学到了关于函数和数据的核心知识，这是编程的实质所在。实际上，你们已经掌握了 Python 语言的基础。

现在是时候转向一门全新的语言了——Scheme。通过学习 Scheme，我们会发现许多关于程序设计的理念可以非常自然地从一种语言迁移到另一种语言。Scheme 是一门诞生极早的语言，在 Python 的设计与创造过程中产生了极其深远的影响。我们要去了解它的历史、感受它的美丽，同时看看哪些核心思想能够跨越语言的边界自由流淌。

### 从 Python 走向 Lisp：简单性的艺术

Scheme 是 Lisp 语言的一种方言。而 Lisp 是今天仍在使用中最古老的两门编程语言之一（另一门是 Fortran）。可以说，它是当今增长最快、生命力最旺盛的古老语言，因为越来越多的人正在重新发现它，并为其构建令人兴奋的前沿应用。

人们对 Lisp 有过什么评价？面向对象编程的发明者 Alan Kay 曾说：这是有史以来设计的最伟大的单一编程语言。我最喜欢的科幻小说作者说，它是唯一一种美丽的计算机语言。Brian Harvey 曾经告诉我：这是上帝的编程语言。甚至连知名极客漫画 xkcd 都在赞美它：Lisp 已经诞生了半个多世纪，但它依然散发着完美的光辉。每一代新的程序员都在重新发现 Lisp 的艺术，正如那句名言所说：“这些是你父亲的括号。更文明时代的优雅武器。”

Lisp 的美在于它的纯粹与简单。它的核心语法与规则非常精简，你甚至可以在一天之内全部学会。然而，就是这样一门简单的语言，却足以用来构建我们在这门课中见过的最复杂的系统，甚至比那些系统还要强大得多。

### 表达式与求值模型

在 Scheme 中，程序完全由表达式组成。表达式主要分为两类：原始表达式与组合表达式。

原始表达式（Primitives）包括自我求值的数字和布尔值，比如 `2`、`3.3`、`true`、`false`，也包括内置过程的名字，比如加号 `+`，或者用于执行整数除法的 `quotient`。

组合表达式（Combinations）的结构非常统一：一个开括号 `(`，后面跟着一系列由空格分隔的子表达式，最后是一个闭括号 `)`。例如，求 10 除以 2 的商，我们写作：

```scheme
(quotient 10 2)
```

在 Python 中，内置的运算对象被称为函数（Function），而在 Scheme 中，我们通常称之为过程（Procedure），但它们本质上是完全相同的概念。

> **定义**：数字在 Scheme 中是自我求值的（Self-evaluating），而符号（Symbol）则绑定到具体的值。调用表达式以括号内的第一个子表达式作为运算符（Operator），其余子表达式作为操作数（Operands）。

与 Python 把运算符写在外面不同（例如 `quotient(10, 2)`），Scheme 把运算符放到了括号内部。这种前缀表示法（Prefix Notation）初看可能有些不习惯，但它带来了一致的语法结构。

调用表达式可以随意嵌套。比如我们要计算 $(8 + 7) / 5$：

```scheme
(quotient (+ 8 7) 5)
```

解释器会先计算内层的 `(+ 8 7)` 得到 15，然后计算外层的 `(quotient 15 5)`，最终返回 3。

在 Scheme 中，换行与空格不会影响语义，解释器完全不在乎缩进。多行排版完全是为了让人类读起来更轻松。例如下面这个复合运算：

```scheme
(+ (* 3
      (+ (* 2 4)
         (+ 3 5)))
   (+ (- 10 7)
      6))
```

我们可以拆开来看：
- `(* 2 4)` 是 8，`(+ 3 5)` 是 8，两部分相加 `(+ 8 8)` 得 16；
- 乘以 3，即 `(* 3 16)`，得到 48；
- 下半部分 `(- 10 7)` 得 3，再加上 6，`(+ 3 6)` 得 9；
- 最终将 48 与 9 相加，整个表达式求值为 57。

运算符支持任意数量的操作数。比如求和：

```scheme
(+ 1 2 3 4)
```

返回 10。乘法也是一样：

```scheme
(* 1 2 3 4)
```

返回 24。

那么如果我什么都不传呢？输入 `(+)` 会发生什么？加法的无参数单位元是 0，因此 `(+)` 返回 0。而对于乘法，`(*)` 的无参数单位元是 1，因此返回 1。

我们可以随时进行更深层的嵌套，比如计算完乘法后再减去 1：

```scheme
(- (* 2 2 2 2 3 3 3) 1)
```

Scheme 的求值规则与 Python 完全一致：**先对运算符和操作数子表达式从左到右递归求值，然后将得到的过程应用于所得的参数值**。

除了算术过程，Scheme 还包含许多内置谓词（返回真假值的过程）。按照 Scheme 的命名惯例，谓词名字末尾通常会带有一个问号 `?`：

```scheme
(number? 3)    ; 返回 true
(number? +)    ; 返回 false
(zero? 2)      ; 返回 false
(zero? 0)      ; 返回 true
(zero? (- 2 2)); 返回 true
(integer? 2.2) ; 返回 false
(integer? 2)   ; 返回 true
```

> **提示**：问号 `?` 只是标识符名称中的一个普通字符，并不是什么特殊的语法操作符。在 Scheme 中，连字符 `-` 和问号 `?` 都可以作为符号名称的一部分。

你可能会好奇，这些代码是在哪里执行的？你可以去网络上寻找各种 Scheme 解释器，也可以本地安装。但在本课程中，我们使用的是你们将在项目四（Project 4）中亲手编写的 Scheme 解释器。你们会用 Python 实现词法分析、语法解析，并编写核心的求值循环（Evaluator）。学习这门新语言的一个关键目的，正是为了彻底搞懂如何为一门语言构建解释器。

### 特殊形式：打破常规调用规则

如果所有的组合都要严格遵循“先计算所有子表达式、再应用过程”的规则，有些逻辑就无法实现。比如条件判断：如果无论真假，两个分支的代码都要提前求值，那么递归就会陷入死循环，报错也无法被抑制。

因此，Scheme 引入了特殊形式（Special Forms）。

> **定义**：特殊形式是指那些求值规则不同于标准调用表达式的组合。在语法上它们同样被括号包裹，但第一个子表达式是一个特殊的关键字。

#### 条件分支与短路求值

最基础的条件特殊形式是 `if` 表达式：

```scheme
(if <predicate> <consequent> <alternative>)
```

它的求值规则是：首先计算谓词 `<predicate>`。如果为真，则计算并返回结果表达式 `<consequent>` 的值；如果为假，才计算并返回备选表达式 `<alternative>` 的值。未被选中的分支绝对不会被求值。

逻辑运算符 `and` 和 `or` 也是特殊形式。因为它们具备短路求值（Short-circuiting）的特性：
- `(and e1 e2 ... en)` 会从左往右求值，一旦某个表达式返回假，后续表达式根本不会被计算，整个式子立即返回假；
- `(or e1 e2 ... en)` 一旦遇到真值，就会提前终止求值并返回该真值。

#### 环境与绑定：`define`

在 Scheme 中，将值绑定到符号是通过 `define` 特殊形式完成的：

```scheme
(define pi 3.14)
```

求值规则：先计算第二个子表达式（此处是 3.14），然后将符号 `pi` 绑定到该值，存入当前环境框架（通常是全局框架）。此后，任何引用 `pi` 的表达式都会解析为 3.14。Scheme 遵循我们在 Python 中学过的完全相同的环境模型。

`define` 还可以通过简洁的语法糖直接定义新过程：

```scheme
(define (<name> <formal parameters>) <body>)
```

注意，紧跟在 `define` 后的括号并不是调用表达式，而是声明了新过程的名称与形式参数列表。

例如，定义一个求绝对值的过程 `abs`：

```scheme
(define (abs x)
  (if (< x 0)
      (- x)
      x))
```

调用 `(abs -3)` 时，环境模型会创建一个局部框架，将形参 $x$ 绑定到 -3，并在该环境中求值主体表达式 `(if (< x 0) (- x) x)`，最终返回 3。

再看两个基础示例：

```scheme
(define (square x) (* x x))

(define (average x y)
  (/ (+ x y) 2))
```

在这些过程定义中，嵌套调用清晰明了。你可以随时调用 `(square 16)` 得到 256，或者调用 `(average 3 7)` 得到 5。

#### 词法作用域与递归实战：巴比伦法求平方根

由于 Scheme 没有类似 Python 的 `while` 或 `for` 循环语句，所有的迭代过程都通过递归调用来实现。

我们可以利用古老的巴比伦方法（牛顿迭代法的一种特例）来编写一个计算平方根的过程：

```scheme
(define (sqrt x)
  (define (update guess)
    (if (= (square guess) x)
        guess
        (update (average guess (/ x guess)))))
  (update 1))
```

这段代码展现了 Scheme 的几个核心机制：
1. **内部过程定义**：我们在 `sqrt` 内部定义了辅助过程 `update`；
2. **词法作用域（Lexical Scope）**：内部过程 `update` 可以直接访问外部过程的形参 `x`；
3. **递归作为控制流**：基准条件（Base Case）是 `(= (square guess) x)`。如果猜测值的平方正好等于 $x$，我们直接返回猜测值；否则，用当前猜测值和 $x / \text{guess}$ 的平均值作为新的猜测，递归调用 `update`。

运行 `(sqrt 256)`，它从 1 开始逐步逼近，最终准确返回 16。

#### 匿名过程：`lambda`

与 Python 一样，Scheme 拥有第一类函数（First-class Procedures），过程本身就是一种数据。我们可以使用 `lambda` 特殊形式动态创建匿名过程：

```scheme
(lambda (<formal parameters>) <body>)
```

定义一个名为 `plus4` 的过程，下面两种写法在语义上是完全等价的：

```scheme
(define (plus4 x) (+ x 4))
(define plus4 (lambda (x) (+ x 4)))
```

在第二种写法中，`lambda` 表达式求值后产生一个匿名过程对象，随后 `define` 将符号 `plus4` 绑定到这个对象上。

甚至在调用表达式中，运算符本身也可以是一个由 `lambda` 构成的复合表达式：

```scheme
((lambda (x y z) (+ x y (square z))) 1 2 3)
```

解释器首先计算运算符子表达式 `(lambda (x y z) ...)`，得到一个接受三个参数的过程；接着计算三个操作数 1、2、3；最后将该过程应用于参数，计算 $1 + 2 + 3^2 = 12$。

### 流程控制与局部环境

为了编写逻辑更清晰的代码，Scheme 提供了另外三种常用的特殊形式：`cond`、`begin` 和 `let`。

#### 多分支选择：`cond`

在 Python 中，当我们面对多个并列条件时，会写一连串的 `if ... elif ... elif ... else`。如果只用 Scheme 的基本 `if`，我们就必须一层套一层地进行嵌套：

```scheme
(if (> x 10)
    'big
    (if (> x 5)
        'medium
        'small))
```

为了避免这种深层嵌套的括号地狱，Scheme 提供了 `cond`（Condition 的缩写）：

```scheme
(cond
  ((> x 10) (print 'big))
  ((> x 5)  (print 'medium))
  (else     (print 'small)))
```

`cond` 由若干个子句（Clause）组成，每个子句包含一个条件和一个或多个结果表达式。它会自上而下逐一检查条件：一旦某个条件求值为真，就执行该分支并返回结果，后续所有子句全部跳过。最后的 `else` 子句是可选的，用来兜底。

更地道的 Scheme 风格是将 `cond` 视为有返回值的表达式，而不是单纯在分支内执行打印副作用：

```scheme
(print
  (cond
    ((> x 10) 'big)
    ((> x 5)  'medium)
    (else     'small)))
```

这样写不仅逻辑更干净，而且只保留了一处打印调用。

> **结论**：如果只有两个分支选项，优先使用 `if`；当选项超过两个时，应当使用 `cond`。

#### 顺序执行：`begin`

在 `if` 表达式的单个分支位置，语法只允许放置一个表达式。但如果你希望在满足条件时连续做两件事（比如先后打印两条调试日志），该怎么办？

这时就需要使用 `begin` 特殊形式：

```scheme
(if (> x 10)
    (begin
      (print 'big)
      (print 'guy))
    (begin
      (print 'small)
      (print 'fry)))
```

`begin` 会按顺序依次求值其包含的所有子表达式，并将**最后一个子表达式的值**作为整个 `begin` 表达式的最终返回值。

#### 局部变量绑定：`let`

在 Python 中，如果我们为了计算直角三角形的斜边 $c = \sqrt{a^2 + b^2}$ 而引入局部变量：

```python
a = 3
b = 2 + 2
c = sqrt(a*a + b*b)
```

计算完成后，变量 `a` 和 `b` 依然残留在当前的作用域中。如果不小心覆盖了外层的同名变量，或者在后续代码中误用了它们，就会引发 Bug。

Scheme 的 `let` 表达式专门用于创建临时局部绑定：

```scheme
(define c
  (let ((a 3)
        (b (+ 2 2)))
    (sqrt (+ (* a a) (* b b)))))
```

`let` 表达式的结构分为两部分：
1. **绑定列表**：由若干个 `(符号 表达式)` 对组成。这些符号只在 `let` 的主体作用域内可见；
2. **主体表达式**：使用这些临时绑定计算最终结果。

一旦整个 `let` 表达式执行完毕，临时符号 `a` 和 `b` 的绑定就会随之消失，只有全局的 `c` 被成功绑定到了 5。

> **提示**：在编写复杂的 Scheme 程序时，我们尽量克制使用全局 `define`。`define` 通常只留给全局常量或函数定义；所有临时的中间计算状态，都应当使用 `let` 进行局部封装。

### 案例演练：递归海龟绘制谢尔宾斯基三角形

为了将上面学到的语法融会贯通，我们来看一个用海龟绘图（Turtle Graphics）绘制分形图形的经典例子。

在配备绘图环境的 Scheme 中，内置了一些控制小海龟的命令：
- `(forward 100)`：让海龟向前走 100 个单位；
- `(right 90)`：让海龟顺时针右转 90 度；
- `(left 120)`：让海龟逆时针左转 120 度；
- `(penup)` 与 `(pendown)`：抬笔与落笔，抬笔移动时不会留下轨迹。

我们可以把画一条线封装为一个无参过程：

```scheme
(define (line) (forward 50))
```

为了让某个过程连续执行两次，可以编写一个高阶过程：

```scheme
(define (twice fn) (fn) (fn))
```

如果调用 `(twice line)`，海龟就会连续画出两条线段。

更进一步，我们需要一个通用的循环机制：将某个过程重复执行 $k$ 次。在没有循环语句的 Scheme 中，递归就是天然的循环：

```scheme
(define (repeat k fn)
  (fn)
  (if (> k 1)
      (repeat (- k 1) fn)))
```

利用 `repeat` 和 `lambda`，我们可以让海龟画出一个五角星。每次前进 50 步，右转 144 度，重复 5 次：

```scheme
(repeat 5 (lambda () (forward 50) (right 144)))
```

接下来，我们抽象出一个绘制等边三角形的通用框架 `tri`。为了能够支持复杂的边，我们让它接受一个过程参数 `fn` 来决定如何画一条边：

```scheme
(define (tri fn)
  (repeat 3 (lambda () (fn) (left 120))))
```

如果传入普通的画线过程 `line`，它画出来的就是一个普通的实心线段三角形。

现在，我们希望绘制**谢尔宾斯基三角形（Sierpinski's Triangle）**。它具有递归分形特征：深度为 $d$、边长为 $k$ 的谢尔宾斯基三角形，其每一条“边”不再是单调的线段，而是由更小规模的谢尔宾斯基结构复合而成。

这里采用互相递归（Mutual Recursion）的技巧：

```scheme
(define (sier d k)
  (tri (lambda ()
         (if (= d 1)
             (forward k)
             (leg d k)))))

(define (leg d k)
  (sier (- d 1) (/ k 2))
  (penup)
  (forward (/ k 2))
  (pendown))
```

我们来剖析这两段代码的协作逻辑：
- `sier` 负责整体的三边拓扑结构。如果达到基准条件 `(= d 1)`，它就用基础的 `(forward k)` 绘制普通线段；否则，它委托 `leg` 过程去绘制一条递归边。
- `leg` 负责这条边的构造逻辑：它首先递归调用 `(sier (- d 1) (/ k 2))`，在当前位置原地画出一个深度减一、尺寸减半的小谢尔宾斯基三角形；画完之后，海龟抬笔向前平移半个边长的距离 `(/ k 2)`，再落笔。这样就移动到了下一个绘图起点。

当我们在解释器中执行：

```scheme
(sier 5 200)
```

海龟就会层层向下递归展开，最终在画布上呈现出由无数微小三角形嵌套组合而成的宏伟分形图案。

### Scheme 列表：纯粹的链表世界

Python 为我们封装了极为丰富的内置数据结构：动态数组列表（List）、元组（Tuple）、字典（Dictionary）、集合（Set）等。

而在 Scheme 的世界中，最核心的数据结构只有一种——列表。并且**每一个 Scheme 列表，底层都是严格的单向链表（Linked List）**。

上世纪 50 年代末 Lisp 刚诞生时，计算机科学家们喜欢使用来自底层硬件架构的简称来命名操作。这些古老的名字一直沿用至今：
- `cons`：接收两个参数，创建一个新的链表节点（Pair）；
- `car`：获取链表节点的第一个元素（在单链表中即为当前节点的值）；
- `cdr`：获取链表节点的剩余部分（在单链表中即为指向下一个节点的指针）；
- `nil`：代表空列表，通常用符号 `nil` 或字面量 `'()` 表示。

创建一个只包含元素 2 的单元素列表，代码如下：

```scheme
(cons 2 nil)
```

如果要创建一个包含 1 和 2 的列表，就是把 1 连接到一个包含 2 的列表前面：

```scheme
(define s (cons 1 (cons 2 nil)))
```

它的内存逻辑就是经典的盒式指针（Box-and-Pointer）模型：

```text
s ---> [ . | . ] ---> [ . | / ]
         |              |
         v              v
         1              2
```
*图解说明：每个方框代表一个通过 `cons` 分配的内存单元，左半格存储 `car`，右半格存储指向下一个单元的 `cdr`，斜杠表示指向空列表 `nil`。*

> **易错点**：虽然底层的物理结构是分散链接的节点对，但 Scheme 解释器在终端中打印输出时，会自动隐藏这些指针细节，直接用扁平化的括号形式呈现：`(1 2)`。

我们可以通过提取操作验证这一结构：

```scheme
(car s) ; 返回 1
(cdr s) ; 返回 (2)
```

注意，`(cdr s)` 返回的依然是一个合法的列表 `(2)`，而不是数字 2 本身。

如果我们将 3 追加到已有的列表 $s$ 前面：

```scheme
(cons 3 s)
```

返回的结果将是新列表 `(3 1 2)`。由于我们传入的第二个参数 $s$ 本身就是一个合法链表，`cons` 只是创建了一个新的头节点，其 `cdr` 直接指向了原有的 $s$ 结构。

常见的列表谓词包括：
- `(list? s)`：判断是否为一个合法列表，`(list? s)` 返回 `#t`（Scheme 中的真值常量），而 `(list? 3)` 返回 `#f`；
- `(null? s)`：判断是否为空列表，只有当参数是 `nil` 时才返回 `#t`。

除了用嵌套的 `cons` 手工穿针引线，Scheme 还提供了高层构造过程 `list`：

```scheme
(list 1 2 3 4)
```

这与 `(cons 1 (cons 2 (cons 3 (cons 4 nil))))` 完全等价。

如果我们取出它的尾部：

```scheme
(cdr (list 1 2 3 4)) ; 得到 (2 3 4)
```

再在前面接上一个 0：

```scheme
(cons 0 (cdr (list 1 2 3 4))) ; 得到 (0 2 3 4)
```

### 符号式编程与引用

Lisp 在计算机历史上最著名的贡献之一是开创了**符号式编程（Symbolic Programming）**。在传统的数值计算中，程序处理的是具体的数字或布尔值；而在符号式编程中，程序可以直接操作代表数学公式、逻辑命题甚至代码本身的“符号”。

这也是为什么几十年来，Lisp 一直是人工智能、符号微积分系统以及定理自动证明器的首选语言。

要理解符号式编程，核心在于理清**符号（Symbol）**与**值（Value）**的区别：

```scheme
(define a 1)
(define b 2)
(list a b)
```

当执行 `(list a b)` 时，解释器会对符号 `a` 和 `b` 求值，最终得到的列表是 `(1 2)`。在这个结果中，变量的名字 `a` 和 `b` 彻底蒸发了，只留下了它们指向的具体数值。

但如果我们希望把符号 `a` 本身当作数据放进列表中呢？

为此，Scheme 提供了**引用（Quote）**机制。通过在符号前面加上一个单引号 `'`，我们指示解释器：**不要对它求值，直接将这个符号字面量作为数据返回**。

```scheme
(list 'a 'b) ; 返回 (a b)
(list 'a b)  ; 返回 (a 2)
```

> **易错点**：Scheme 中的单引号并不是成对出现的包裹符号。它是一个前缀修饰符，仅仅作用于紧随其后的**那一个**完整表达式。

事实上，单引号 `'<expr>` 只是特殊形式 `(quote <expr>)` 的语法简写：

```scheme
'a              ; 等价于 (quote a)
'(1 2 3)        ; 等价于 (quote (1 2 3))
```

当引用被应用于一个由括号构成的组合时，它不仅会阻止对这个组合本身的求值，还会递归地阻止对其中所有子表达式的求值：

```scheme
(define s '(+ 1 2))
```

此时的 $s$ 并不是数字 3，而是一个包含三个符号元素的列表：首元素是符号 `+`，后续是数字 1 和 2。我们可以像处理普通列表一样检查它的元素：

```scheme
(car s) ; 返回符号 +
(cdr s) ; 返回 (1 2)
```

这也揭示了 Lisp 语言最底层的哲学——**代码即数据（Homoiconicity）**。在 Scheme 中，程序代码本身就是用列表这种数据结构写出来的。

### 列表处理高阶过程

在日常编程中，频繁地手写递归遍历链表非常繁琐。Scheme 标准库提供了一组功能强大的高阶过程，用于批量操作列表。

#### `append`：列表拼接

`append` 接收任意数量的列表作为参数，将它们的所有元素依次按顺序摊平连接成一个新的单一列表：

```scheme
(append '(1 2) '(3 4) '(5 6)) ; 返回 (1 2 3 4 5 6)
```

注意它与 `cons` 的区别：
- `(cons '(1 2) '(3 4))` 会把整个第一个列表作为单个头元素，得到 `((1 2) 3 4)`；
- `(append '(1 2) '(3 4))` 则把两者的元素打平合并，得到 `(1 2 3 4)`。

#### `map`：元素变换

`map` 接收一个变换过程 $f$ 和一个列表 $s$，将 $f$ 分别作用于 $s$ 中的每一个元素，并将所有返回值收集为一个新的列表：

```scheme
(map even? '(1 2 3 4))
; 返回 (#f #t #f #t)

(map (lambda (x) (* x 2)) '(1 2 3 4))
; 返回 (2 4 6 8)
```

#### `filter`：元素过滤

`filter` 接收一个谓词过程 $f$ 和一个列表 $s$，依次检查每个元素；只有当 $f$ 返回真值时，该元素才会被保留：

```scheme
(filter even? '(5 6 7 8 9))
; 返回 (6 8)
```

#### `apply`：参数解包调用

`apply` 常常与 `map` 产生混淆，但它们的执行模型截然不同。

> **结论**：`map` 将过程分别应用到列表中的**每一个独立元素**上，产生一个包含多次调用结果的新列表；而 `apply` 则是将**整个列表当成参数包**，直接解构传递给目标过程，只执行**一次**调用。

例如：

```scheme
(apply + '(1 2 3 4))
```

在语义上等价于执行：

```scheme
(+ 1 2 3 4)
```

最终返回单一数值 10。

对比一下：如果你写 `(map + '(1 2 3 4))`，相当于分别计算 `(+ 1)`、`(+ 2)`、`(+ 3)`、`(+ 4)`，得到的是列表 `(1 2 3 4)`，完全起不到求和的效果。正是因为有了 `apply`，Scheme 根本不需要单独内置一个求和函数 `sum`，直接通过 `(apply + s)` 即可优雅完成。

### 综合实战：求解偶数和非空子集

现在我们来解决一个综合算法问题：编写一个过程 `even-subsets`，它接收一个由整数构成的列表 $s$，返回 $s$ 的所有**和为偶数的非空子集**组成的列表（每个子集保持原列表中的相对次序）。

例如：

```scheme
(even-subsets '(3 4 5 7))
```

3、4、5、7 的非空子集中，像 `(5 7)` 的和是 12（偶数），`(4 5 7)` 的和是 16（偶数），它们应当出现在结果中；而 `(3 4)` 的和是 7（奇数），就必须被排除。

#### 递归分治思路

我们采用分治法来思考任意一个列表 $s$ 的子集构成。对于首元素 `(car s)`，任何一个子集要么包含它，要么不包含它。

要让一个子集的元素和为偶数，存在三种互斥的情况：
1. **不包含首元素**：直接取剩余部分 `(cdr s)` 的所有偶数和子集；
2. **包含首元素，且首元素与剩余子集拼接**：
   - 如果首元素是**偶数**，为了保证相加后仍为偶数，它必须与 `(cdr s)` 的**偶数和子集**拼接（偶 + 偶 = 偶）；
   - 如果首元素是**奇数**，为了让总和变为偶数，它必须与 `(cdr s)` 的**奇数和子集**拼接（奇 + 奇 = 偶）；
3. **只包含首元素自身的单元素子集**：
   - 只有当首元素本身就是**偶数**时，单元素 `(list (car s))` 才是一个合法的偶数和子集。

#### 互相递归的初步实现

根据上述数学推导，我们需要同时定义两个相互依赖的过程：求偶数和子集的 `even-subsets` 与求奇数和子集的 `odd-subsets`。

```scheme
(define (even-subsets s)
  (if (null? s)
      nil
      (append
        ; 情况 1：不包含首元素
        (even-subsets (cdr s))
        ; 情况 2：包含首元素，与其余部分的子集拼接
        (map (lambda (t) (cons (car s) t))
             (if (even? (car s))
                 (even-subsets (cdr s))
                 (odd-subsets (cdr s))))
        ; 情况 3：单元素本身构成的子集
        (if (even? (car s))
            (list (list (car s)))
            nil))))

(define (odd-subsets s)
  (if (null? s)
      nil
      (append
        (odd-subsets (cdr s))
        (map (lambda (t) (cons (car s) t))
             (if (even? (car s))
                 (odd-subsets (cdr s))
                 (even-subsets (cdr s))))
        (if (odd? (car s))
            (list (list (car s)))
            nil))))
```

逻辑非常严密：在 `odd-subsets` 中，如果首元素是奇数，它需要去寻找其余部分的偶数和子集（奇 + 偶 = 奇）；如果首元素是偶数，它则去寻找其余部分的奇数和子集（偶 + 奇 = 奇）。

#### 高阶函数重构：消除冗余

审视上面的代码，你会发现 `even-subsets` 与 `odd-subsets` 的代码骨架完全一模一样，唯一的区别只在于谓词是 `even?` 还是 `odd?`。复制粘贴如此大量的代码是不符合优良工程原则的。

我们可以提取出一个高阶辅助过程 `subset-helper`，将目标属性对应的判定条件参数化：

```scheme
(define (subset-helper f s)
  (if (null? s)
      nil
      (let ((first (car s))
            (rest (cdr s)))
        (append
          (subset-helper f rest)
          (map (lambda (t) (cons first t))
               (if (even? first)
                   (subset-helper f rest)
                   (subset-helper (lambda (x) (not (f x))) rest)))
          (if (f first)
              (list (list first))
              nil)))))

(define (even-subsets s)
  (subset-helper even? s))
```

在这里，如果首元素是奇数，目标子集的奇偶性要求发生翻转，我们通过 `(lambda (x) (not (f x)))` 动态传递相反的测试谓词，极大幅度精简了代码结构。

#### 管道化过滤视角

其实，解决这个问题还有一条更加直观清晰的思路：**先生成列表的所有非空子集，然后用高阶过程过滤出和为偶数的那些**。

首先，一个列表 $s$ 的所有非空子集生成非常简单：
- 剩余部分 `(cdr s)` 的非空子集；
- 将 `(car s)` 拼接到每一个剩余子集前端；
- 仅包含 `(car s)` 的单元素列表。

```scheme
(define (nonempty-subsets s)
  (if (null? s)
      nil
      (let ((first (car s))
            (rest (nonempty-subsets (cdr s))))
        (append rest
                (map (lambda (t) (cons first t)) rest)
                (list (list first))))))
```

拿到所有非空子集后，我们只需要构造一个判断“某个列表元素之和是否为偶数”的谓词：

```scheme
(define (sum-is-even? s)
  (even? (apply + s)))
```

最后通过 `filter` 组装完成：

```scheme
(define (even-subsets s)
  (filter sum-is-even? (nonempty-subsets s)))
```

这种数据驱动的管道化写法将子集生成逻辑与条件校验逻辑彻底解耦，不仅代码大幅精简，阅读和维护也变得极其轻松。

```text
[ . | . ] ---------------------> [ . | . ] ---> [ . | / ]

  v                                v              v
[ . | . ] ---> [ . | / ]           1              2
  |              |
  v              v
  4              3
```
*图解说明：顶层链表包含三个主节点；首节点的 `car` 指针下行指向一个独立的子链表 `(4 3)`。*

#### 题目 2：共享引用的 `cons` 结构追踪

**题干**：
已知 $s$ 为 `(1 2)`，请推演以下表达式的求值结果，并说明其内部指针关系：
```scheme
(cons s (cons s nil))
```

**解析**：
我们由内向外拆解：
1. `(cons s nil)` 创建了一个长度为 1 的链表，其唯一的元素是指向 $s$ 的引用；
2. 外层的 `cons` 将 $s$ 作为首元素，连接到上述单元素链表前端；
3. 最终形成一个长度为 2 的列表，其中的两个元素都是 $s$ 列表本身。

在内存模型中，两个节点各自的 `car` 指针实际上指向了同一块由 $s$ 占据的物理内存单元。

```text
       +-----------------------+
       |                       |
       v                       |
     [ . | . ] ---> [ . | / ]  |
       |              |        |
       v              v        |
       1              2        |
       ^                       |
       |                       |
[ . | . ] --------> [ . | / ] -+
```
*图解说明：底层两个主节点的 `car` 指针分别向上汇聚指向同一个单链表 `(1 2)`。*

**答案**：
终端显示结果为 `((1 2) (1 2))`。

### 异常处理与控制流拦截

#### 异常的引发与内建类型

在 Python 中，你可以主动引发（raise）异常来指示异常情况的发生。异常通过包含 `raise` 关键字的语句触发，后面跟一个求值为异常对象或异常类的表达式：

```python
raise <expression>
```

这个表达式必须求值为内建基础异常类 `BaseException` 的子类，或者该子类的某个实例对象。

异常的构造方式与 Python 中普通的面向对象实例完全相同。标准库提供了大量内建异常类，例如类型错误（`TypeError`）、名称错误（`NameError`）、字典键缺失（`KeyError`）以及递归层级过深时的递归错误（`RecursionError`）。要构造一个携带具体上下文的异常对象，只需在实例化时传入描述发生情况的字符串即可：

```python
>>> raise TypeError('Very bad idea')
Traceback (most recent call last):
  ...
TypeError: Very bad idea
```

如果不提供描述字符串，直接 `raise TypeError`，程序同样会抛出该类型错误，只是缺少了具体的错误消息。

在日常编程中，很多异常是由系统底层根据运行时状态自动触发的。比如我们取一个整数的绝对值没有任何问题：

```python
>>> abs(3)
3
```

但如果我们试图取一个字符串的绝对值，Python 解释器会自动拦截并抛出类型错误：

```python
>>> abs('hello')
Traceback (most recent call last):
  ...
TypeError: bad operand type for abs(): 'str'
```

同样地，如果代码访问了一个未绑定的变量名，会触发 `NameError`；访问字典中不存在的键会触发 `KeyError`；如果函数陷入死循环调用自身：

```python
def f():
    return f()
```

连续的帧栈堆积最终会触碰 Python 设定的深度阈值，自动抛出 `RecursionError`。

除了等待系统自动报错，我们还可以主动使用异常来约束函数的输入域。假设我们要编写一个 `double(x)` 函数：

```python
def double(x):
    if isinstance(x, str):
        raise TypeError('double only takes numbers')
    return 2 * x
```

为什么我们要特意加上这段类型检查？在 Python 的原生语法中，字符串乘以 2 是合法的（`2 * 'hello'` 会得到 `'hellohello'`）。但如果我们的业务设计要求该函数严格只能对数值翻倍，我们就可以主动抛出 `TypeError`，并附带清晰的提示文本：

```python
>>> double(4)
8
>>> double('hello')
Traceback (most recent call last):
  ...
TypeError: double only takes numbers
```

> **定义**：异常的类型一方面用于向开发者精准描述故障性质；另一方面为运行环境提供了**分类捕获并恢复程序运行**的程序化入口。

#### 使用 try 语句拦截异常与维护程序连续性

在默认情况下，未被拦截的异常会导致程序立即终止执行，在终端打印调用栈回溯（Traceback）信息，将排错修复的责任甩给程序员。然而在实际生产环境中，比如 Web 服务器处理外部网络请求，或者交互式终端接收用户的即兴输入，输入数据格式不规范是家常便饭。我们绝不希望因为某一次非法输入就让整个后台服务崩溃。

为了让程序在发生错误后仍能维持运转，我们使用 `try` 语句：

```python
try:
    <try suite>
except <ExceptionType> as <name>:
    <except suite>
```

`try` 语句的执行逻辑如下：
1. 首先执行 `try suite` 代码块。如果内部没有发生任何异常，执行完毕后直接跳过后续的 `except` 分支，流程正常继续。
2. 如果在执行 `try suite` 过程中抛出了异常，当前代码块的后续指令会立刻中断。
3. 解释器会检查引发的异常对象是否属于 `except` 后面声明的 `ExceptionType`（或其子类）。如果匹配成功，且定义了 `as <name>`，该异常对象会被绑定到该局部变量名上，接着执行对应的 `except suite`。
4. 只要 `except suite` 中没有再次主动抛出异常，整个 `try` 结构执行完毕后，程序将平稳过渡到下一行指令，不会发生非正常崩溃，也不会向控制台输出长串调用栈回溯。

来看一个除以零的典型场景：

```python
>>> try:
...     x = 1 / 0
... except ZeroDivisionError as e:
...     print('handling a', type(e))
...     x = 0
handling a <class 'ZeroDivisionError'>
>>> x
0
```

在这段交互中，赋值操作 `x = 1 / 0` 触发了 `ZeroDivisionError`，导致右值未完成计算就发生了跳转。但由于我们捕获了该异常，程序不仅输出了错误类型，还将 `x` 安全地降级回退赋值为 `0`。控制台自始至终没有暴露任何红字 Traceback。

为了更透彻地观察执行流的中断与跳过，我们看下面两个求倒数函数的对比：

```python
def invert(x):
    result = 1 / x
    print('Never printed if x is 0')
    return result
```

调用 `invert(2)` 时，运算顺畅，打印信息正常显示并返回 `0.5`。但如果调用 `invert(0)`，在计算 `1 / x` 的瞬间异常抛出，后面的 `print` 与 `return` 彻底失去了执行机会。此时若有变量赋值 `b = invert(0)`，变量 `b` 将根本不会被成功绑定。

我们可以为它套上一层安全防护网：

```python
def invert_safe(x):
    try:
        return invert(x)
    except ZeroDivisionError as e:
        return str(e)
```

```python
>>> a = invert_safe(2)
Never printed if x is 0
>>> a
0.5
>>> b = invert_safe(0)
>>> b
'division by zero'
```

在 `invert_safe(0)` 的调用中，`invert` 内部的打印同样没有触发，但抛出的 `ZeroDivisionError` 被 `except` 捕获并转化为了字符串 `'division by zero'` 优雅返回，变量 `b` 被安全绑定。如果我们希望发生错误时回退到默认数值，只需将 `except` 代码块里的返回值改为 `0` 即可。

#### 关注点分离：以 reduce 与除法运算为例

掌握了异常拦截后，我们来看它如何在系统设计中促成**关注点分离（Separation of Concerns）**。我们以经典高阶函数 `reduce` 为载体展开探讨。

`reduce` 的职责是将一个序列中的所有元素通过一个二元函数不断两两结合，最终压缩规约为一个单一值。其概念模型可以形式化表示为：给定二元运算函数 $f(acc, x)$、序列 $s = [x_1, x_2, \dots, x_n]$ 以及初始累积值 $initial$，规约过程为：

$$acc_1 = f(initial, x_1)$$
$$acc_2 = f(acc_1, x_2)$$
$$\dots$$
$$result = f(acc_{n-1}, x_n)$$

例如，以初始值 `1` 对序列 `[2, 4, 8]` 进行连续乘法，等价于计算 $((1 \times 2) \times 4) \times 8 = 64$。如果我们以初始值 `2` 对序列 `[1, 2, 3, 4]` 进行幂运算（`pow`），计算链条将沿着 $2^1 = 2 \to 2^2 = 4 \to 4^3 = 64 \to 64^4 = 16777216$ 极速膨胀。

我们可以通过迭代和递归两种方式来实现 `reduce`：

```python
from operator import add, mul

def reduce(f, s, initial):
    """迭代实现版本"""
    for x in s:
        initial = f(initial, x)
    return initial
```

递归版本则体现了自顶向下的分治逻辑：若列表为空，直接返回累加器当前值；若非空，将首元素与累加器结合，随后递归处理剩余列表：

```python
def reduce(f, s, initial):
    """递归实现版本"""
    if not s:
        return initial
    else:
        first, rest = s[0], s[1:]
        return reduce(f, rest, f(initial, first))
```

测试验证两个基础案例：

```python
>>> reduce(mul, [2, 4, 8], 1)
64
>>> reduce(add, [1, 2, 3, 4], 0)
10
```

现在，假设我们需要实现一个业务函数 `divide_all(n, ds)`，它接收分子 `n` 和一组分母列表 `ds`，要求将分子依次除以所有分母。借助 `reduce` 与标准除法 `operator.truediv`，逻辑非常直接：

```python
from operator import truediv

def divide_all(n, ds):
    try:
        return reduce(truediv, ds, n)
    except ZeroDivisionError:
        return float('inf')
```

正常执行时，`divide_all(1024, [2, 4, 8])` 会按序计算 $((1024 / 2) / 4) / 8 = 16.0$。可一旦分母列表中夹杂了 `0`，底层 `truediv` 就会立刻抛出 `ZeroDivisionError`。

```python
>>> divide_all(1024, [2, 4, 8])
16.0
>>> divide_all(1024, [2, 0, 8])
inf
```

> **结论**：请仔细体味这种架构模式带来的优雅性：
> 1. `reduce` 函数只负责通用遍历与元素折叠逻辑，它完全不需要预判任何除法规则，代码里**没有一行**针对 `ZeroDivisionError` 的特殊逻辑。
> 2. `divide_all` 负责组合具体运算，它明晰被调函数可能产生的风险，因而独立负责捕获 `ZeroDivisionError` 并给出业务回退值 `float('inf')`。
> 
> 算法骨架与业务异常处理实现了彻底解耦。

### 编程语言的层次与核心抽象

#### 机器语言与高级抽象

掌握了异常处理机制后，我们把视线拓宽到宏观软件体系的核心：解释器（Interpreter）。

> **定义**：**解释器**是一个程序，它将以某种编程语言编写的代码文本作为输入，通过解析与求值，最终执行出该代码所描述的行为。

在底层物理世界中，计算机硬件（中央处理器 CPU）只能执行**机器语言（Machine Language）**。机器语言由特定的硬编码指令集构成，直接对应寄存器、高速缓存与内存地址的操作。机器指令极度晦涩，缺少对人类友好的抽象工具：你无法为复杂数据结构命名，没有高级函数概念，也没有对象和类。更重要的是，想要扩展机器语言，你甚至必须重新设计修改电路拓扑。

高级编程语言（如 Python、Scheme、C）的出现，正是为了将程序员从具体的硬件细节中解放出来。高级语言通过编译器（Compiler）或解释器（Interpreter）架设在低级硬件之上：
- **编译（Compilation）**：预先将源代码全量翻译为另一种更底层的目标语言（如机器码），保存为二进制文件供后续直接执行。
- **解释（Interpretation）**：直接读取源代码，实时分析其语义并逐步驱动硬件执行相应逻辑。

现代编程语言通常将两者融合。以 Python 为例，代码在被执行前，首先由解释器内部编译为一种更为规整的中间形态——**Python 3 字节码（Bytecode）**。你可以通过 Python 内置的 `dis`（反汇编）模块查看底层字节码指令。随后，Python 虚拟机（PVM）再逐条解释运行这些字节码。

```text
+-----------------------+
|  高级源代码 (Python)   |
+-----------------------+
            |
            v (编译为中间字节码)
+-----------------------+
| Python 3 字节码 (Bytecode) |
+-----------------------+
            |
            v (虚拟机/解释器驱动)
+-----------------------+
|  底层硬件与操作系统执行  |
+-----------------------+
```

高级语言构建了层层抽象封装：你可以在不同架构的 CPU 或操作系统上编写同一段 Python 脚本，而无需关心具体内存引脚的有效电平或寄存器分配。

---

#### 语法、语义与领域专用语言

任何一门编程语言都由两个核心维度定义：
- **语法（Syntax）**：合法的字符排列规则，决定了一个表达式或语句在**形式（Form）**上是否有效。
- **语义（Semantics）**：合法表达式和语句被执行时的评估规则，决定了代码的**意义（Meaning）**与行为。

设计一门新语言时，通常有两种落地路线：一种是先制定严格的形式化规范（Specification）文档，再编写实现（Scheme 便是由规范先行，后续发展出不同解释器）；另一种则是先产出参考实现（Reference Implementation），再逐步倒逼总结出语言规范（Python 便是由最初的 CPython 参考实现发展出标准语法描述）。

并非所有语言都必须追求如 Python 那样大而全的通用能力。在计算机科学中，针对特定问题域定制**领域专用语言（Domain-Specific Language, DSL）**是一种强大的工程抽象：
- **Erlang**：专为大规模并发通信与容错系统设计。银行 ATM 网络与高并发聊天系统需要确保全球各地的终端绝不会因时序错乱而产生同一账户重复出款等严重并发冲突。Erlang 的语法与运行时模型从底层消除了数据竞争，为这种并发调度提供了原生语言支持。
- **MediaWiki 标记语言**：维基百科词条编辑所使用的轻量级标记语言。它不具备通用图灵完备编程能力，但内置了超链接关联、模板拼接与文本排版等语法元素，极度适配非技术人员协作编撰大型模块化知识库的需求。

接下来，我们将使用 Python 构建一个专属于 Scheme 算术子集的解释器。这个案例不仅规则精炼，更集中体现了解释器的标准构造范式。

### 语法解析：将文本转化为表达式树

计算机无法直接理解由纯文本组成的字符串代码。要让解释器执行代码，首先必须通过**解析（Parsing）**将非结构化的字符流重塑为内存中的**表达式树（Expression Tree）**。

#### 表达式的内部表示：Pair 与 nil

Scheme 程序最迷人的特性在于它的“同像性”（Code as Data）：**代码的语法组织形式与语言内建的列表数据结构完全一致**。在 Scheme 中，嵌套括号 `(+ (* 2 4) 6)` 本质上就是一个以符号、子列表和数字构成的链表结构。

为了在 Python 中表示这种链表结构，我们需要一个极简的对（Pair）类以及一个表示空表的 `nil` 单例。其核心数据抽象包含 `first` 和 `rest` 两个属性：

```python
class Pair:
    """在 Python 中表示 Scheme 列表节点的数据结构。"""
    def __init__(self, first, rest):
        self.first = first
        self.rest = rest

    def __repr__(self):
        return f"Pair({repr(self.first)}, {repr(self.rest)})"

    def __str__(self):
        # 按照 Scheme 的括号风格格式化输出列表
        s = "(" + str(self.first)
        second = self.rest
        while isinstance(second, Pair):
            s += " " + str(second.first)
            second = second.rest
        if second is not nil:
            s += " . " + str(second)
        return s + ")"

class nil:
    """表示 Scheme 中的空列表。"""
    def __repr__(self):
        return "nil"
    def __str__(self):
        return "()"

nil = nil()  # 实例化全局单例
```

通过这套表示法，Scheme 表达式 `(1 2 3)` 在内存中被构建为嵌套的链表对象：

```python
Pair(1, Pair(2, Pair(3, nil)))
```

请注意它的双重呈现方式：
- `repr` 视角展示了底层的 Python 对象嵌套拓扑：`Pair(1, Pair(2, Pair(3, nil)))`。
- `str` 视角则精确还原了 Scheme 程序员眼中的原生括号文本：`(1 2 3)`。

---

#### 词法分析与语法分析的流水线

解析文本的过程由前后承接的两个阶段构成：

```text
+-----------------------+
|  原始输入文本 (String) |  "(+ 23 (* 4 5.6))"
+-----------------------+
            |
            v 【词法分析 (Lexical Analysis)】
+-----------------------+
|  词法标记序列 (Tokens) |  ['(', '+', 23, '(', '*', 4, 5.6, ')', ')']
+-----------------------+
            |
            v 【语法分析 (Syntactic Analysis)】
+-----------------------+
|  表达式树 (Pair 结构)  |  Pair('+', Pair(23, Pair(Pair('*', ...), nil)))
+-----------------------+
```

1. **词法分析（Lexical Analysis / Tokenization）**：
   词法分析器的任务是扫描原始字符串，剔除无意义的空白符，识别合法的原子单位（标记，Token）。
   词法分析器具备向前看字符的能力：例如输入中连续的 `2` 和 `3` 必须被合流解析为一个整数 `23`；遇到浮点数 `4.5`，它能识别出中间的点号代表小数位而非独立句点；遇到紧挨着的括号（如 `))`），词法分析器知道括号是语法定界符，即便中间没有空格，也必须拆分为两个独立的右括号标记。

2. **语法分析（Syntactic Analysis）**：
   语法分析器接收标记流，根据括号匹配规则构建嵌套的树形结构。这一过程由树递归函数 `scheme_read` 驱动。
   - 当遇到普通标记（数字或符号），属于递归基，直接返回该基本对象。
   - 当遇到左括号 `(` 时，意味着一段复合表达式的开启。解析器必须启动更深一层的递归，依次消费标记并将其包装成 `Pair` 链表节点，直到定位到与之闭合匹配的右括号 `)` 为止。
   - 如果遇到孤立的多余右括号，解析器会抛出 `SyntaxError` 提示标记异常；若文件扫描结束仍有未闭合的左括号，同样会触发解析错误。

经过语法分析器的洗礼，不管程序员在原始代码中使用了怎样随意的换行和多余空格，它们都将被抹平成一棵标准、规整的 `Pair` 表达式树。

### 计算器语言的核心：Eval 与 Apply 的双重奏

现在，我们正式实现**计算器语言（Calculator）**的求值引擎。计算器语言是 Scheme 的一个极简子集，它剥离了变量定义与自定义函数，专注于支持嵌套的算术调用表达式。

#### 计算器语言的语法与语义规则

计算器语言的表达式只有两类：
1. **基本表达式（Primitive Expressions）**：仅包含数字（整数或浮点数），其求值结果就是该数字本身。
2. **调用表达式（Call Expressions）**：表现为 Scheme 列表结构，首个元素是运算符（`+`、`-`、`*`、`/` 之一），后续元素是零个或多个操作数表达式（操作数本身既可以是基本数字，也可以是嵌套的调用表达式）。

该语言的求值语义与标准 Scheme 保持一致：
- `+`：对所有参数求和。若无参数，返回 `0`。
- `*`：计算所有参数的乘积。若无参数，返回 `1`。
- `-`：必须至少提供一个参数。若只给一个参数，语义是对其**取相反数**（例如 `(- 5)` 得到 `-5`）；若提供多个参数，语义是用**第一个参数依次减去后续所有参数**（例如 `(- 10 1 2 3)` 得到 $10 - 1 - 2 - 3 = 4$）。无参数时抛出类型错误。
- `/`：必须至少提供一个参数。若只给一个参数，语义是对其**取倒数**（例如 `(/ 4)` 得到 `0.25`）；若提供多个参数，语义是用**第一个参数依次除以后续所有参数**（例如 `(/ 1024 2 4 8)` 得到 $1024 / 2 / 4 / 8 = 16$）。遇到除数为 0 抛出 `ZeroDivisionError`。

对于嵌套表达式 `(+ (* 2 3) (* 2 5 5))`，其对应的表达式树拓扑展开如下：

```text
                  +
                 / \
                /   \
               *     *
              / \   / | \
             2   3 2  5  5
```

解释器的核心任务，就是自底向上递归解开这棵树：先算出左子树 $2 \times 3 = 6$，再算出右子树 $2 \times 5 \times 5 = 50$，最后将两个中间结果汇总相加得到 `56`。

---

#### 表达式求值器 calc_eval

解释器的中枢神经由两个相互交织调用的函数组成：负责**树形分发求值**的 `calc_eval`，与负责**实际执行运算**的 `calc_apply`。

`calc_eval` 是一个通用的类型分派器。它的输入是一个可能包含嵌套结构的表达式 `exp`：

```python
def calc_eval(exp):
    """求值 Calculator 表达式 exp。"""
    # 分支 1：如果是基本数字类型（int 或 float），求值结果为其自身
    if isinstance(exp, (int, float)):
        return simplify(exp)

    # 分支 2：如果是调用表达式（以 Pair 链表组织）
    elif isinstance(exp, Pair):
        # 运算符是链表的第一个元素
        operator = exp.first
        # 对 rest 链表中的每一个操作数子表达式，递归调用 calc_eval
        args = []
        rest = exp.rest
        while rest is not nil:
            if not isinstance(rest, Pair):
                raise TypeError("Malformed expression: bad argument list")
            args.append(calc_eval(rest.first))
            rest = rest.rest

        # 将运算符与已全部求值为数字的参数列表，交由 calc_apply 处理
        return simplify(calc_apply(operator, args))

    else:
        raise TypeError(f"Unknown expression type: {exp}")

def simplify(value):
    """将类似 8.0 的浮点数简化显示为整数 8，优化显示效果。"""
    if isinstance(value, float) and value.is_integer():
        return int(value)
    return value
```

> **提示**：这里展示了典型的**树递归（Tree Recursion）**：
> 一个调用表达式的操作数本身可能是另一个深层嵌套的 `Pair`。在运算符执行前，`calc_eval` 会沿着分支不断向下递归，直到抵达基本数字叶节点；叶节点返回自身后，计算结果再自底向上汇集。

---

#### 运算符分派器 calc_apply

当 `calc_eval` 将所有子表达式打平成一组纯数字参数后，便将运算符和实参列表打包转交给 `calc_apply`。`calc_apply` 扮演了具体算术逻辑的执行中枢：

```python
def calc_apply(operator, args):
    """将具体的算术运算符 operator 应用于已求值的数字参数列表 args。"""
    if not isinstance(operator, str):
        raise TypeError(f"{operator} is not a symbol")

    # 1. 加法运算
    if operator == '+':
        return sum(args)

    # 2. 减法运算
    elif operator == '-':
        if len(args) == 0:
            raise TypeError("- requires at least 1 argument")
        elif len(args) == 1:
            return -args[0]
        else:
            return reduce(lambda a, b: a - b, args[1:], args[0])

    # 3. 乘法运算
    elif operator == '*':
        return reduce(mul, args, 1)

    # 4. 除法运算
    elif operator == '/':
        if len(args) == 0:
            raise TypeError("/ requires at least 1 argument")
        elif len(args) == 1:
            return 1 / args[0]
        else:
            return reduce(truediv, args[1:], args[0])

    else:
        raise TypeError(f"Unknown operator: {operator}")
```

`calc_eval` 与 `calc_apply` 之间的相互协作关系被称为**求值/应用循环（Eval-Apply Cycle）**。这是整门计算机科学中最为核心的架构模型之一：

```text
                  calc_eval(exp)
                  /            \
        (基本数字)              (调用表达式)
           |                        |
         返回数值        1. 对子表达式递归调用 calc_eval
                         2. 提取运算符与数字参数
                                    |
                                    v
                         calc_apply(operator, args)
                                    |
                            执行具体算术规约
                                    |
                                产出结果
```

---

### 交互式解释器的基石：REPL 与集中式错误恢复

#### 读取-求值-打印循环的生命周期

解释器对外的交互界面通常被组织为一个**读取-求值-打印循环（Read-Eval-Print Loop，简称 REPL）**。它的运行流程周而复始：

```text
   +------------------------------------------------------+
   |                                                      |
   v                                                      |
[ 1. 打印提示符 (Prompt) ]                                |
   |                                                      |
   v                                                      |
[ 2. 读取文本行 (Read) ]                                  |
   |                                                      |
   v                                                      |
[ 3. 语法解析 (Parse -> scheme_read) ]                    |
   |                                                      |
   v                                                      |
[ 4. 表达式求值 (Eval -> calc_eval) ]                     |
   |                                                      |
   v                                                      |
[ 5. 输出求值结果 (Print) ]                               |
   |                                                      |
   +------------------------------------------------------+
```

1. **Prompt**：打印提示符（例如 `calc> `），告诉用户解释器已准备好接受新的输入。
2. **Read**：从标准输入流捕获用户敲入的代码字符串。
3. **Parse**：调用词法分析与语法分析器 `scheme_read`，把字符串提炼为内存中的 `Pair` 表达式树。
4. **Eval**：将表达式树送入 `calc_eval`，产出最终计算结果。
5. **Print**：如果计算中途未遭遇任何错误，打印求出的值；随后重启循环，打印新的提示符。

---

#### 集中式异常处理与容错体验

一个健壮的交互式解释器，必须处理解释执行链条中各个环节引发的异常。请注意整个流水线中潜在异常的分散性：
- **词法分析阶段**：用户输入了格式错误的标记（如连续多个小数点的非法数字 `2.3.4`），词法分析器抛出 `ValueError`。
- **语法分析阶段**：用户多敲了括号（如 `(+ 1 2))`）或缺少右括号，`scheme_read` 抛出 `SyntaxError`。
- **求值阶段（calc_eval）**：遇到空列表 `()` 这类既非基本类型也非有效操作符的输入，抛出 `TypeError`。
- **应用阶段（calc_apply）**：减法运算缺少参数、传入未定义的操作符（如 `(? 1 2)`）抛出 `TypeError`；而在进行除法运算时遇到除数为 0，底层的 Python 运算则会抛出 `ZeroDivisionError`。

如果在交互过程中发生上述任何一个错误，解释器直接崩溃退出并打印一长串内部 Python 栈帧，对于终端用户来说将是一场灾难。解释器应当做到：**终止当前非法表达式的求值，打印面向用户的错误诊断，并立刻恢复监听，等待用户的下一条输入修正**。

这种“错误四处引发，捕获集中一处”的设计哲学，通过最顶层的 `try...except` 循环得到了完美兑现：

```python
def read_eval_print_loop():
    """交互式运行计算器解释器。"""
    while True:
        try:
            # 1. 读取输入文本
            line = input('calc> ')
            
            # 2. 语法解析 (此处使用假设已实现的 scheme_read_line)
            tokens = tokenize(line)
            if not tokens:
                continue
            expression = scheme_read(tokens)

            # 3. 求值
            result = calc_eval(expression)

            # 4. 打印正常结果
            print(result)

        except (SyntaxError, ValueError, TypeError, ZeroDivisionError) as err:
            # 集中捕获语法、词法与运行时错误，向用户展示错误信息，程序绝不崩溃中断
            print(type(err).__name__ + ':', err)

        except (KeyboardInterrupt, EOFError):
            # 只有当用户按下 Ctrl-D (EOF) 或 Ctrl-C 时，才优雅终止退出
            print("\nCalculation completed.")
            break
```

```text
calc> (+ 1 2)
3
calc> (/ 10 0)
ZeroDivisionError: division by zero
calc> (- )
TypeError: - requires at least 1 argument
calc> (* 2 3 4)
24
calc> Calculation completed.
```

看看这个 REPL 的表现：当用户输入非法的 `(/ 10 0)` 或 `(- )` 时，顶层的 `except` 准确捕获了异常并打出简明提示，当前的非法状态被即刻清除，下方的 `calc>` 提示符如期而至。用户得以在不丢失进程状态的情况下修正代码。只有按下 `Control-D`（发送文件结束符 EOF）或者发生键盘中断时，解释器才打印 `Calculation completed.` 并优雅退出。

从最基础的 `raise` 和 `try...except` 语法，到 `reduce` 的关注点分离，再到解析树的构造与 `Eval-Apply` 循环的搭建，最终收束于具备集中异常容错的 REPL——我们不仅构建了一个完整的 Scheme 算术解释器，更领略了计算系统是如何通过层层解耦与抽象，将纷乱的字符流一步步推演为严整的执行秩序。

## 解释器的架构：求值、应用与环境模型
> 对应块：BLK21 | 覆盖分集：P29 | 块标题（分集名）：《Lecture 31 Interpreters-》

我们在之前实现计算器（Calculator）时，整个语言其实只允许两种东西：数字和调用表达式。只要遇到调用表达式，就把操作符和所有操作数老老实实算出来，然后传给底层的 Python 函数做运算。

但在真正的 Scheme 中，我们不仅想做加减乘除，我们还想定义变量、编写条件分支，甚至定义新的函数并在之后调用它们。计算器在那套极其死板的求值规则下根本做不到这些。

要让一个程序能够理解并运行其他程序，解释器的核心就是一套分发调度机制：拿到一个 Scheme 表达式，判断它究竟是什么类型，然后决定是直接返回值、查找名字，还是交给特定的规则去处理。

---

### 解释器的双核骨架：eval 与 apply 的相互递归

一个完整的解释器在顶层是由两个相互配合的核心函数驱动的：`scheme_eval` 和 `scheme_apply`。它们之间的关系不是单向的调用链，而是一个相互递归的循环系统。

```text
               +----------------------------------+
               |           scheme_eval            |
               |                                  |
               |  - 自求值表达式 (数字/nil等)    |
               |  - 符号 (在当前环境中 lookup)    |
               |  - 特殊形式 (if/define/lambda等) |
               |  - 调用表达式 (求值操作符与参数) |
               +----------------+-----------------+
                                |
             遇到过程调用       | 调用 eval 求值操作符
             (Call Expression)  | 与所有操作数
                                v
               +----------------+-----------------+
               |          scheme_apply            |
               |                                  |
               |  - 内置过程: 直接计算结果        |
               |  - 用户定义过程 (LambdaProcedure)|
               |    * 创建绑定实参的新帧          |
               |    * 在新环境中求值过程体        |
               +----------------+-----------------+
                                |
                                | 在新环境下递归调用 eval
                                v
                       (求值过程的主体表达式)
```

读懂这张图，你就抓住了整个解释器的灵魂：
1. `scheme_eval` 接收一个表达式和一个环境。如果是基本数据，它直接返回；如果是符号，它去环境中查找；如果是特殊形式，它按特殊语法规则递归求值部分子表达式；如果是调用表达式，它必须先递归调用 `scheme_eval` 把操作符和所有操作数求出具体的值，然后把这些值打包送给 `scheme_apply`。
2. `scheme_apply` 拿到一个过程对象和一组实参。如果是加减乘除这种内置的原始过程，直接执行；但如果是我们自己用 `lambda` 写出来的过程，它就必须基于该过程当初保存的环境创建一个新的框架（Frame），把形参和实参绑定好，然后**再次调用 `scheme_eval`** 去求值该过程的主体。

这一来一回，`eval` 调用 `apply` 来应用过程，而 `apply` 又调用 `eval` 来运行过程体，构成了通用解释器执行复杂嵌套逻辑的基石。

---

### 表达式调度与特殊形式

当一个表达式传入 `scheme_eval` 时，我们必须对它进行类型分发。在 Scheme 中，我们遇到的表达式大体上可以分为三类：

1. **自求值表达式（Self-evaluating expressions）**：比如数字、布尔值，以及空列表 `nil`。传入什么，求值结果就是什么。
2. **符号（Symbols）**：比如变量名 `x`、过程名 `demo`。它们代表一个名字，必须在当前环境（Environment）中查找其绑定的具体值。
3. **组合式（Combinations）**：在语法形式上表现为良好构建的 Scheme 列表（Well-formed Scheme lists），即括号括起来的一串元素。

> **定义**：组合式是 Scheme 源码中最普遍的结构。根据列表的第一个元素，组合式被分为**特殊形式（Special Forms）**和**普通调用表达式（Call Expressions）**。

在评估一个组合式时，解释器首先查看该列表的第一个元素：
- 如果第一个元素是特殊的关键字，比如 `if`、`lambda`、`define` 或 `quote`，这就说明它是一个**特殊形式**。特殊形式之所以“特殊”，是因为它绝不遵守“先求值操作符、再自左向右求值所有操作数”的标准调用规则。每一种特殊形式都有自己专属的求值规约。
- 如果第一个元素不是任何已知的特殊形式关键字，那么它就是一个**普通调用表达式**。此时，第一个元素被当作操作符求值，剩余元素作为操作数求值，最后将操作符产生的方法应用在操作数的值上。

---

### 数据化代码：引用（Quote）

在编程中，我们有时候写下括号并不想让它去执行，而是想把它当成一个字面上的列表数据。这就是引用特殊形式要做的事情。

引用的作用极其纯粹：**直接返回被引用的表达式本身，不对其做任何求值计算。**

例如，如果让解释器执行 `(+ 1 2)`，它会进行加法运算得到 3。但如果我们写：

```scheme
(quote (+ 1 2))
```

求值结果不是 3，而是一个 Scheme 列表，这个列表里依次存放着符号 `+`、数字 1、数字 2。通过这种方式，代码与数据之间的边界被完全打破了——你可以通过引用，将任何合法的程序代码瞬间降维成纯粹的数据列表。

在日常编写 Scheme 时，每一个引用都写一遍 `(quote ...)` 会带来大量的多层括号。因此语言提供了单引号简写语法糖：

```scheme
'(1 2)
```

它与 `(quote (1 2))` 在语义上是完全等价的，这种等价性是双向的。

> **提示**：在解释器的实现架构中，词法与语法分析器（如 `scheme_reader`）在把代码文本解析成内部列表结构时，就会在第一时间将 `'<expr>` 展开转换为 `(quote <expr>)`。也就是说，后端的 `scheme_eval` 根本不需要为单引号单独写逻辑，它看到的永远都是规范的 `quote` 组合式列表。

---

### 逻辑分支：条件与短路

像 `if` 和 `cond` 这样的逻辑特殊形式，核心特征在于：**它们绝对不能在进入分支前把所有的子表达式都算一遍**。如果把 `if` 做成了普通函数调用，根据调用规则，解释器会把每个分支都算出来，那条件判断就完全失去了分支隔离的意义。

以 `if` 表达式为例，它的语法结构是：

```scheme
(if <predicate> <consequent> <alternative>)
```

它的求值逻辑被非常清晰地分为两步：
1. 调用 `scheme_eval` 求值谓词表达式 `<predicate>`。
2. 根据谓词的真假值做出二选一抉择：如果为真，仅去求值 `<consequent>`（结果项）；如果为假，仅去求值 `<alternative>`（替代项）。被选中的那一项的求值结果，就是整个 `if` 表达式的值。没有被选中的分支，自始至终连碰都不会碰一下。

在解释器的 Python 代码内部，通常由一个专门的分发函数（例如 `do_if_form`）来处理它：

```python
# 解释器内部处理 if 形式的核心逻辑切片示意
def do_if_form(expressions, env):
    # expressions 是包含 predicate, consequent, alternative 的列表
    predicate = expressions.first
    consequent = expressions.rest.first
    alternative = expressions.rest.rest.first
    
    # 1. 求值谓词
    if scheme_eval(predicate, env):
        # 2. 仅求值结果项
        return scheme_eval(consequent, env)
    else:
        # 3. 仅求值替代项
        return scheme_eval(alternative, env)
```

看看这个例子：

```scheme
(if #t 1 (/ 1 0))
```

因为谓词是 `#t`，解释器选择执行结果项并返回 1。后面的替代项是一个严重的除以零错误 `(/ 1 0)`，但整个表达式执行毫无异常，因为根本没有去求值它。反之，如果谓词变成了 `#f`，解释器去求值替代项，就会立刻抛出除零错误。

这就是为什么必须把它作为特殊形式：**由解释器去控制求值的时机与路径，而不是交给统一的参数预计算逻辑**。

### 帧与环境：变量与作用域的底层实现

当我们在程序里写下 `(define x 3)`，这个 `x` 存到了哪里？后续又该怎么找出来？这就涉及到解释器中的**帧（Frame）**与**环境（Environment）**。

#### 帧链结构与查找机制

一个**环境**代表了程序执行某段代码时所有可见名称的集合。但在实现上，环境并不是一个扁平的大字典，而是一条由**帧（Frame）**构成的单向链表。

每个帧对象主要维护两件东西：
- 一个局部绑定字典（保存当前这一层作用域里定义的名字与值）。
- 一个指向父帧（Parent Frame）的指针。

```text
+----------------------------+
| 全局帧 (Global Frame / G)  |
| 绑定:                      |
|   y: 3                     |
|   z: 5                     |
+--------------^-------------+
               |  (parent)
+--------------+-------------+
| 本地帧 (Local Frame / F1)   |
| 绑定:                      |
|   x: 2                     |
|   z: 4                     |
+----------------------------+
```

在这个环境中，查找变量遵循**就近遮蔽原则**：
- 如果我们在环境 $F_1$ 中查找变量 `x`，在当前帧立刻命中，得到 2。
- 如果我们在环境 $F_1$ 中查找变量 `z`，当前帧直接命中，得到 4。虽然全局帧中也有一个 `z: 5`，但被本地帧的同名绑定遮蔽（Shadow）了。
- 如果我们在环境 $F_1$ 中查找变量 `y`，本地帧没有，解释器沿着父指针向上爬到全局帧 $G$，在全局帧中找到 `y: 3`。
- 如果一路爬到全局帧依然找不到该符号，解释器报错：未知的标识符。

在实现中，`Frame` 类的核心就是两个操作：
1. `define(name, value)`：始终在**当前帧**建立或更新绑定关系。
2. `lookup(name)`：先看当前帧有没有，没有就递归调用 `parent.lookup(name)`。

#### 定义表达式的工作流

当我们求值一个定义表达式时，机制如下：

```scheme
(define x (+ 1 2))
```

解释器首先在当前环境下调用 `scheme_eval` 计算表达式 `(+ 1 2)` 得到具体值 3，然后直接在**当前帧**将符号 `x` 绑定到 3。一旦绑定完成，解释器就不再关心 3 是通过什么加法算出来的，帧里只保留最终结果。

对于过程定义：

```scheme
(define (square x) (* x x))
```

在语义上，它不过是 `lambda` 过程定义的简写形式，完全等价于：

```scheme
(define square (lambda (x) (* x x)))
```

解释器在语法层面直接将前者重写为后者，然后统一交由 `lambda` 的逻辑来创建过程并将其绑定到名字 `square` 上。

### 过程抽象与调用：Lambda 与用户定义过程

在所有特殊形式中，最重要的莫过于 `lambda`。

`lambda` 表达式求值的结果是一个**用户定义过程**。在 Python 解释器实现中，它被实例化为一个 `LambdaProcedure` 对象。

> **定义**：一个 `LambdaProcedure` 实例由三部分组成：
> 1. **形式参数列表（Formals）**：由 Scheme 符号构成的列表，指明调用时接收哪些参数。
> 2. **主体表达式（Body）**：过程内部待执行的 Scheme 表达式。
> 3. **闭包环境（Environment）**：**该过程被创建时所处的环境（即该环境的起始帧）**。

#### 应用用户定义过程的三步法则

当解释器要对实参应用一个 `LambdaProcedure` 时，`scheme_apply` 必须严格执行以下三步：
1. **开辟新帧**：实例化一个新的 `Frame`。这个新帧的父帧指针，**必须指向该过程对象自身保存的定义环境（env）**。
2. **绑定形参**：将过程的各个形式参数按顺序绑定到传入的实际参数值上，存入这个新帧中。
3. **求值主体**：以这个刚刚建好的新帧为环境起点，调用 `scheme_eval` 求值过程的主体表达式。

#### 递归追踪：demo 过程的调用剖析

让我们通过一个具体的例子来透视这套机制的运作。假设我们在全局环境中定义了过程 `demo`：

```scheme
(define (demo s)
  (if (null? s)
      '(3)
      (cons (car s) (demo (cdr s)))))
```

这个过程接收一个列表 `s`。如果 `s` 为空，返回只包含 3 的列表 `'(3)`；否则，取出 `s` 的第一个元素，与在 `s` 剩余部分上递归调用 `demo` 的结果 `cons` 起来。本质上，它是在原始列表的末尾追加一个数字 3。

注意，当解释器求值这个 `define` 表达式时，**它完全不会去求值过程主体**。它只是把包含主体、形参 `(s)` 以及全局帧指针打包封装为一个 `LambdaProcedure`，然后把符号 `demo` 绑定到它上面。

接下来，我们在全局帧下执行调用：

```scheme
(demo '(1 2))
```

追踪解释器的底层运作链条：

```text
[初始调用] scheme_eval 遇到 ((demo '(1 2)))
   |-- 查找 demo -> 得到 LambdaProcedure(formals=(s), body=..., env=G)
   |-- 求值 '(1 2) -> 得到列表 (1 2)
   \-- 调用 scheme_apply(demo, [(1 2)])

[第一层 apply]
   |-- 创建帧 F1 (parent = G)
   |-- 在 F1 中绑定 s: (1 2)
   \-- 在 F1 环境下求值 demo 主体:
         (null? s) 为假 -> 执行 (cons (car s) (demo (cdr s)))
         (car s) -> 1
         (cdr s) -> (2)
         准备调用 (demo '(2)) ------+
                                     | 递归触发
[第二层 apply] <--------------------+
   |-- 创建帧 F2 (parent = G)
   |-- 在 F2 中绑定 s: (2)
   \-- 在 F2 环境下求值 demo 主体:
         (null? s) 为假 -> 执行 (cons (car s) (demo (cdr s)))
         (car s) -> 2
         (cdr s) -> nil
         准备调用 (demo '()) -------+
                                     | 递归触发
[第三层 apply (基本情况)] <---------+
   |-- 创建帧 F3 (parent = G)
   |-- 在 F3 中绑定 s: nil
   \-- 在 F3 环境下求值 demo 主体:
         (null? s) 为真 -> 命中分支返回 '(3)
         结果回传: (3)

[逐层构造返回]
   |-- F2 恢复现场: (cons 2 '(3))   -> 返回 '(2 3)
   \-- F1 恢复现场: (cons 1 '(2 3)) -> 返回 '(1 2 3)
```

在这个过程中，每一次递归调用都在重用同一段代码主体，但**每一次调用都在一个全新的局部帧中执行**。帧记录了每次调用时各自的绑定状态（第一层 `s` 是 `(1 2)`，第二层是 `(2)`，第三层是 `nil`），使得互不干扰的递归运算成为可能。

### 作用域规则：词法作用域与动态作用域

在构建解释器时，最核心的语义设计抉择之一就是：**当一个过程被调用而生成一个新帧时，这个新帧的父帧究竟应该指向哪里？**

针对这个问题，计算机语言历史上演化出了两种截然不同的策略：**词法作用域（Lexical Scope，又称静态作用域）**与**动态作用域（Dynamic Scope）**。

| 作用域机制 | 新帧的父帧由谁决定？ | 决定时机 | 代表语言 |
| :--- | :--- | :--- | :--- |
| **词法作用域** | 过程**被定义**时所在的环境 | 代码编写时（静态确定） | Python, Scheme, 现代绝大多数语言 |
| **动态作用域** | 过程**被调用**时所处的环境 | 代码运行时（动态决定） | 早期 Lisp, 部分 Shell 脚本 |

为了彻底搞清楚两者的差异，我们来看一段精简的测试代码：

```scheme
(define (f x) (+ x y))

(define (g x y) (f (+ x x)))

(g 3 7)
```

在这段代码中，函数 `f` 试图将参数 `x` 和一个未在自身形参中声明的变量 `y` 相加。在全局定义 `f` 时，全局帧中根本没有定义 `y`。然后，我们在函数 `g` 的内部调用了 `f`，而 `g` 恰好有一个形参叫 `y`。

让我们分别用两种作用域规则来追踪执行 `(g 3 7)` 时的环境结构：

#### 词法作用域下的求值过程

```text
+------------------------------------+
| 全局环境 (Global Frame / G)         |
| 绑定: f, g                         |
+-----------------^------------------+
                  |
        +---------+---------+
        | (parent)          | (parent)
+-------+--------+  +-------+--------+
| 帧 F1 (来自 g) |  | 帧 F2 (来自 f) |
| x: 3           |  | x: 6           |
| y: 7           |  |                |
+----------------+  +----------------+
```

1. 执行 `(g 3 7)`，开辟帧 $F_1$，其父帧为全局帧 $G$。$F_1$ 中 $x=3, y=7$。
2. 在 $F_1$ 中计算参数 `(+ x x)` 得到 6，然后调用 `f`。
3. 按照词法作用域规则，新帧 $F_2$ 的父帧必须是**定义 `f` 时的环境**，也就是全局帧 $G$。
4. 在 $F_2$ 中求值 `(+ x y)`：查找 `x` 命中 6；接着查找 `y`，在 $F_2$ 中没有，顺着父指针直奔全局帧 $G$，依然没有。
5. **求值结果**：解释器直接抛出错误：`Unknown identifier: y`。

#### 动态作用域下的求值过程

```text
+------------------------------------+
| 全局环境 (Global Frame / G)         |
| 绑定: f, g                         |
+-----------------^------------------+
                  | (parent)
+-----------------+------------------+
| 帧 F1 (来自 g)                     |
| x: 3, y: 7                         |
+-----------------^------------------+
                  | (parent)
+-----------------+------------------+
| 帧 F2 (来自 f)                     |
| x: 6                               |
+------------------------------------+
```

1. 执行 `(g 3 7)`，开辟帧 $F_1$。
2. 调用 `f` 时，动态作用域不再关心 `f` 是在哪里写出来的，只关心**是谁在调用它**。因为此时处于 $g$ 的求值上下文，所以 $F_2$ 的父帧直接挂载在 $F_1$ 下面。
3. 在 $F_2$ 中求值 `(+ x y)`：查找 `x` 命中 6；查找 `y`，在 $F_2$ 中没有，顺着父指针向上在 $F_1$ 中找到 $y=7$。
4. **求值结果**：计算 $6 + 7 = 13$，程序正常返回 13。

> **结论**：动态作用域让函数的含义变得极其不可预测——函数内部游离变量的值，完全取决于外层是哪个函数调用了它。而在词法作用域下，你阅读一个函数时，只要看它写在代码的什么位置，就能彻底锁定每个非局部变量的归属。这也是现代程序设计语言无一例外倒向词法作用域的原因。

### 函数式编程的困境与尾递归救赎

函数式编程的核心理念，是用纯函数来组织整个软件系统。这些函数具有极高的模块化程度，能以数学上严谨而优美的方式相互组合。

当我们谈论纯粹的函数式编程时，通常意味着以下几个极为严苛的属性：
- 所有函数都是纯函数（Pure Functions）；
- 不存在任何副作用（No Side Effects）；
- 没有任何重新赋值（No Reassignment）；
- 不存在任何可变数据类型（No Mutable Data Types）。

当你创建了一个对象，它就会永久保持原样；当你为某个名称绑定了一个值，这个绑定在当前作用域内就是永恒的。

这些限制初看像是一种自我阉割，但它为我们带来了巨大的优势。首先，表达式的值与子表达式的求值顺序彻底脱钩。在 Python 中，我们强制规定了从左到右等求值顺序；但在纯函数式世界里，由于不存在副作用，我们可以根据系统资源随心所欲地安排求值顺序。如果机器拥有多个计算核心，我们可以直接并行评估各个子表达式；甚至我们还可以采取惰性求值策略——在真正需要子表达式的值之前，根本不去计算它。

这种特性的基石是**引用透明性（Referential Transparency）**：任何表达式都可以直接用它所求得的值进行替换，而绝对不会改变整个程序的外部行为。正因为有了引用透明性，像记忆化（Memoization）、公共子表达式消除、自动并行化等优化手段，才能完全不带顾虑地施展。在这个多核处理器日益普及的时代，函数式编程因此焕发出强大的生命力。

然而，一个尖锐的工程问题随之而来：如果没有 `for` 语句，没有 `while` 语句，变量又绝对不允许被重新绑定，我们该如何高效实现最基础的“迭代”逻辑？

难道只能依靠递归吗？如果纯函数式语言只能靠递归，而递归在传统计算机体系结构中需要不断压栈、速度缓慢且耗尽内存，那么这类语言岂不是永远与“高性能”无缘？

答案是否定的。通过**尾递归（Tail Recursion）**与**尾调用消除（Tail Call Optimization）**，函数式语言在执行迭代过程时，能够做到与指令式语言中的 `while` 循环完全一致的效率与常数空间占用。

我们不妨在 Python 中直观对比递归与迭代两种写法。假设我们需要编写一个计算 $k \times n!$ 的函数 `factorial(n, k)`：

```python
# 递归版本
def factorial_recursive(n, k):
    if n == 0:
        return k
    return factorial_recursive(n - 1, k * n)
```

```python
# 迭代版本
def factorial_iterative(n, k):
    while n > 0:
        n, k = n - 1, k * n
    return k
```

在这两个实现中，数学计算逻辑是完全对称的：当 $n > 0$ 时，我们不断把 $n$ 递减，同时将当前值乘入累加器 $k$；一旦 $n = 0$，累加器 $k$ 内部就已经收集齐了阶乘的所有项，直接返回 $k$。

然而，它们在运行资源上的消耗有着本质差别：
- **时间复杂度**：两者都经历 $n$ 次递减计算，仅相差一个很小的常数因子，都是 $O(n)$ 线性时间。
- **空间复杂度**：迭代版本只需要常数空间 $O(1)$，因为在整个循环过程中，计算机只需要在内存中维护固定数量的几个变量名（`n` 和 `k`）；而 Python 中的递归版本却需要 $O(n)$ 的线性空间，每一次递归调用都会在调用栈上新建一个活动帧（Frame）。

如何抹平语法递归与常数空间迭代之间的这道鸿沟？

Scheme 语言规范给出了明确的裁定：**Scheme 的实现必须是“正确的尾递归”（Properly Tail-Recursive）。** 

这一硬性规范要求解释器：即使计算过程是用递归调用的语法形式写出的，只要它表达的是迭代计算逻辑，就必须在常数空间内执行。

### 淘汰中间人：尾调用与尾上下文

要让递归具备与循环相同的常数空间性能，底层的破局之道非常直观：**淘汰中间人（Eliminate the Middleman）**。在进行下一次调用时，直接淘汰掉那些已经完成使命、后续不再需要的调用帧。

让我们仔细审视 Python 在执行上述 `factorial_recursive(4, 1)` 时，调用栈中究竟发生了什么：

```text
Global Frame
  factorial_recursive: func ...
       │
       ▼
Frame 1: factorial_recursive(n=4, k=1)
       │  等待 Frame 2 返回并直接 return 其值
       ▼
Frame 2: factorial_recursive(n=3, k=4)
       │  等待 Frame 3 返回并直接 return 其值
       ▼
Frame 3: factorial_recursive(n=2, k=12)
       │  等待 Frame 4 返回并直接 return 其值
       ▼
Frame 4: factorial_recursive(n=1, k=24)
       │  等待 Frame 5 返回并直接 return 其值
       ▼
Frame 5: factorial_recursive(n=0, k=24) ───► 返回 24
```
*图说明：普通递归调用链中的所有中间帧都在做无意义的原样传递，形成了空间浪费。*

当递归推进到最深处的 `Frame 5` 时，$n = 0$，它计算出最终答案 24 并返回。请观察上面的所有中间帧：`Frame 4` 接到 24，什么也没算，直接把它向上丢给 `Frame 3`；`Frame 3` 拿到 24，原封不动丢给 `Frame 2`；`Frame 2` 再丢给 `Frame 1`。

在此期间，`Frame 1` 里的局部变量 `n = 4`、`Frame 2` 里的 `n = 3` 还有用吗？没有任何用处。当 `Frame 1` 算好了下一层调用的实参（`n - 1` 为 3，`k * n` 为 4）的那一瞬间，`Frame 1` 自身的使命就已经全部终结了。它存在于内存中的唯一目的，只是像个机械的邮递员一样，等下层返回结果后再往上交差。

在标准的 Python 解释器中，这些无用的中间帧被完整保留着；但一个正确实现了尾递归的解释器绝不会允许这种情况发生。

> **定义**：如果一个过程调用另一个过程，而在被调用过程执行完毕后，当前过程除了“直接返回该调用的返回值”之外，不需要再执行任何其他计算，那么这个调用就被称为**尾调用（Tail Call）**。

一个尚未返回的过程调用被称为“活动的”（Active）。Scheme 解释器能够支持无限深度的尾调用，且仅消耗常数级别的调用栈空间，依靠的正是这种识别机制：识别出尾调用后，直接丢弃或复用当前帧，跳过调用栈上无意义的帧累积。

要从代码结构上精准识别尾调用，我们必须定义什么是**尾上下文（Tail Context）**。

> **定义**：**尾调用是处于尾上下文中的过程调用表达式。**

一个表达式是否处于尾上下文，取决于它在语法树中所处的位置。主要有以下几条判断法则：
1. **函数体末尾**：在 `lambda` 表达式（或由 `define` 隐式创建的 `lambda`）中，主体表达式序列里的**最后一个子表达式**处于尾上下文。因为该表达式的求值结果直接决定了整个函数的返回值。
2. **条件分支末尾**：如果一个 `if` 表达式本身处于尾上下文，那么它的推论子表达式（Consequent，即分支 2）和替代子表达式（Alternative，即分支 3）也同样处于尾上下文。
3. **复合表达式延续**：
   - 如果一个 `cond` 表达式处于尾上下文，其中所有分支的最后一个子表达式都处于尾上下文；
   - 如果 `and` 或 `or` 处于尾上下文，其最后一个操作数处于尾上下文；
   - 如果 `begin` 块处于尾上下文，其最后一个子表达式处于尾上下文。

现在我们重新审视 Scheme 版本的阶乘定义：

```scheme
(define (factorial n k)
  (if (= n 0)
      k
      (factorial (- n 1) (* k n))))
```

在这个过程中：
1. 整个 `(if ...)` 表达式是函数定义体的最后一个子表达式，因此 `if` 整体处于尾上下文；
2. 依据规则，它的分支 2（即符号 `k`）和分支 3（即 `(factorial (- n 1) (* k n))`）均处于尾上下文；
3. 分支 3 本身是一个过程调用表达式，并且它处在尾上下文中，因此它是一个**尾调用**。

当执行这个尾调用时，一旦参数表达式 `(- n 1)` 和 `(* k n)` 计算完毕，当前帧的历史数据（旧的 `n` 和 `k`）就已经彻底失去了存在价值。解释器可以直接在当前帧的原地覆盖新参数，或者回收当前帧再创建新帧。环境的大小绝不会随着递归深度而线性膨胀。

#### 尾调用优化实测

为了验证这一点，我们在开发 Scheme 解释器（`scheme.py`）时，可以对比启用与未启用尾调用优化的实际表现。

在未实现尾调用优化的标准递归求值逻辑中，每次对函数的求值都会在 Python 环境中发起一次递归的 `scheme_eval` 调用。

如果我们在该环境下加载尾递归的阶乘函数：
- 计算 `(factorial 10 1)`：瞬间返回；
- 计算 `(factorial 100 1)`：正常返回；
- 计算 `(factorial 1000 1)`：解释器崩溃，抛出异常：`RecursionError: maximum recursion depth exceeded while calling a Python object`。

Python 自身的调用栈深度通常限制在 1000 左右。在计算到大概 673 的阶乘时，由于 Python 解释器为每一层未完成的 `scheme_eval` 维护了活动帧，宿主环境的栈空间耗尽，程序被迫终止。

但当我们开启解释器中的尾调用优化实现（通过蹦床机制或迭代求值循环，使处于尾上下文的过程调用不再派生新的 Python 栈帧）：
- 计算 `(factorial 1000 1)`：平滑运行并输出结果；
- 计算 `(factorial 10000 1)`：虽然需要花费一定的时间进行大数乘法运算，但它完全没有耗尽栈空间，平稳输出了这个长达数万位的庞大数字。

这表明，尾调用优化并不会改变大数计算本身固有的算法时间，但它从根本上消除了调用栈空间的线性增长。

### 递归重构与尾递归判定实战

一个递归函数要想被称为**尾递归函数**，其所有可能的递归调用路径都必须是尾调用。

判断一个过程调用是否为尾调用的铁律在于：**在调用完成之后，是否还有后续计算等待进行？** 如果返回之后还要拿这个值参与加法、拼接列表等任何额外操作，它就绝不是尾调用。

#### 列表长度求解的尾递归重构

我们先看最符合直觉的列表求长过程：

```scheme
(define (length s)
  (if (null? s)
      0
      (+ 1 (length (cdr s)))))
```

让我们严格根据规则分析其上下文：
1. 整个 `if` 是函数体的最后一个表达式，处于尾上下文；
2. `0` 和替代分支 `(+ 1 (length (cdr s)))` 处于尾上下文；
3. 替代分支是一个加法调用 `+`，因此**加法操作本身是一个尾调用**；
4. 但是，递归调用 `(length (cdr s))` 只是加法操作的一个操作数子表达式，它**不在尾上下文内**。

在我们获得 `(length (cdr s))` 的结果之后，解释器还必须挂起当前执行点，等待结果返回，然后再将该结果与 1 相加。为了完成加法，解释器必须保留包含当前列表局部变量 `s` 的环境帧。因此，这个版本的空间复杂度是 $O(n)$。

为了将其重构为尾递归，我们引入辅助过程与累加器参数 $n$：

```scheme
(define (length s)
  (define (length-iter s n)
    (if (null? s)
        n
        (length-iter (cdr s) (+ n 1))))
  (length-iter s 0))
```

在内部辅助函数 `length-iter` 中：
- `(length-iter (cdr s) (+ n 1))` 位于 `if` 的替代分支上，而这个 `if` 是 `length-iter` 函数体的末尾；
- 该调用表达式本身处于尾上下文，其返回值直接作为当前函数的返回值，后面没有加 1，也没有任何附加计算；
- 这是一个标准的尾调用。

虽然输入数据列表 `s` 本身在内存中占据线性空间，但在计算长度的过程中，解释器维护的活动帧始终只有 1 个，调用栈空间降为了 $O(1)$。

#### 复杂递归案例解析

我们进一步分析四个典型函数的空间行为与尾递归特性：

```scheme
;; 案例 A：判断元素是否在列表中
(define (contains s v)
  (if (null? s)
      false
      (if (= (car s) v)
          true
          (contains (cdr s) v))))
```

在 `contains` 中，外层 `if` 处于尾上下文，内层 `if` 处于外层 `if` 的替代分支，因此内层 `if` 也处于尾上下文。内层 `if` 的替代分支是对 `contains` 的递归调用。因为它是尾上下文中的调用表达式，所以这是一个尾调用。`contains` 是完全的尾递归，在常数空间内运行。

```scheme
;; 案例 B：判断列表中是否有重复元素
(define (has-repeat s)
  (if (null? s)
      false
      (if (contains (cdr s) (car s))
          true
          (has-repeat (cdr s)))))
```

`has-repeat` 的结构与 `contains` 完全相同，其递归调用 `(has-repeat (cdr s))` 处于内层 `if` 的尾上下文中，因此该递归调用是尾调用。

> **易错点**：注意到它在条件判断中调用了 `(contains (cdr s) (car s))`。这个谓词调用并不在尾上下文中，因为它的结果必须被求值以决定进入哪个分支。但这是否会破坏常数空间保证？不会。因为被调用的 `contains` 本身是一个尾递归过程，只占用常数额外空间，执行完立即销毁，不会造成调用栈随列表长度累积。因此 `has-repeat` 依然在常数辅助空间内运行。

```scheme
;; 案例 C：斐波那契数计算（互递归/辅助函数）
(define (fib-iter current k n)
  (if (= k n)
      current
      (fib-iter (+ current (fib (- k 1))) (+ k 1) n)))

(define (fib n)
  (if (<= n 1)
      n
      (fib-iter 1 2 n)))
```

我们来追踪 `fib-iter` 的调用：
- 函数末尾的 `(fib-iter ...)` 处于尾上下文；
- 但是看它的第一个实参表达式：`(+ current (fib (- k 1)))`。为了计算出传递给下一次迭代的参数，它必须先调用 `(fib (- k 1))`，然后执行加法；
- `(fib (- k 1))` 是处于操作数子表达式位置的非尾调用，而且它会反过来再次触发树状递归；
- 只要调用链中包含非尾递归调用，解释器就必须保存现场，因此它绝不是尾递归，无法在常数空间中运行。

#### 高阶函数的尾递归设计：以 reduce 与 map 为例

高阶函数对于尾调用的要求更为精细。

首先看序列规约过程 `reduce`。它接收一个二元合并过程 `procedure`、一个序列 `s` 和一个初始值 `initial-value`：

```scheme
(define (reduce procedure s initial-value)
  (if (null? s)
      initial-value
      (reduce procedure
              (cdr s)
              (procedure initial-value (car s)))))
```

在 `reduce` 中：
- 对 `reduce` 的递归调用处于 `if` 的替代分支上，处于尾上下文，因此递归调用本身是尾调用；
- 但是，第三个实参表达式调用了 `(procedure initial-value (car s))`，这是一个非尾调用。
- **空间结论**：`reduce` 自身的递归机制是尾递归的；但整个求值过程是否真正能在常数空间内运行，取决于传入的 `procedure` 本身是否仅消耗常数空间。

相比之下，列表映射函数 `map` 的尾递归改造要复杂得多。最自然的 `map` 定义如下：

```scheme
(define (map procedure s)
  (if (null? s)
      nil
      (cons (procedure (car s))
            (map procedure (cdr s)))))
```

在这个常规版本中，`cons` 处在尾上下文，但 `(map procedure (cdr s))` 处在 `cons` 的参数位置。必须先等 `map` 返回其余子列表，当前帧才能执行 `cons` 节点分配。这会导致 $O(n)$ 的线性调用栈开销。

在纯函数式列表的单向链表结构中，从前向后扫描输入列表时，如果想要顺向构造新列表，最直接的构造方式是从尾部向前结合。要将其改造为纯尾递归，必须分为两步处理：
1. **反向累积映射**：利用累加器，边向前扫描边通过 `cons` 把新元素挂在前面，得到一个反向的映射列表；
2. **尾递归反转**：再通过一个尾递归的列表反转过程，把反向列表恢复为正确的正向顺序。

```scheme
;; 尾递归版本的反转过程
(define (reverse-iter s r)
  (if (null? s)
      r
      (reverse-iter (cdr s) (cons (car s) r))))

(define (reverse s)
  (reverse-iter s nil))

;; 尾递归版本的 map 过程
(define (map-reverse procedure s m)
  (if (null? s)
      m
      (map-reverse procedure
                   (cdr s)
                   (cons (procedure (car s)) m))))

(define (map procedure s)
  (reverse (map-reverse procedure s nil)))
```

通过这一重构：
- `map-reverse` 每次扫描一个元素，执行 `(procedure (car s))` 并立即挂入累加器 `m`，其对自身的调用是绝对的尾调用；
- `reverse-iter` 每次把输入列表的表头移到累积列表 `r` 的前端，递归调用也是尾调用；
- 整个映射计算完全在常数调用栈空间下完成。为了获得空间上的严格保证，这种两阶段的处理模式是函数式编程中极具代表性的工程技巧。

### 解释器即通用计算机

在深入到程序与数据的边界之前，我们有必要停下来审视一下：当我们亲手用 Python 实现一个 Scheme 解释器时，我们到底在制造什么？

**我们在制造一台通用计算机（Universal Computer）。**

我们可以用物理机器来进行类比：
- 传统观念里的一个“程序”，就像是针对某个专门目标设计的一台特定硬件设备。例如，一个计算阶乘的硬件电路，它固定接收一个输入 $n$，内部按照分支与乘法规则运转，输出 $n!$。

```text
专用硬件视角（单一程序）：
输入 (5) ────► [ 阶乘专用计算设备 ] ────► 输出 (120)

通用硬件视角（解释器）：
输入数据 (5) ──┐
               ├─► [ 通用计算机器 (解释器) ] ────► 输出 (120)
源代码定义 ────┘
'(define (fact n) ...)'
```
*图说明：专用程序是固定逻辑的处理机，而解释器通过将源代码作为参数输入，模拟出任意机器的计算逻辑。*

解释器本身并不固化任何具体的业务计算。它接受两个输入：
1. 告诉它“模拟哪台机器”的**源代码**；
2. 交给这台被模拟机器去处理的**实际数据**。

在解释器内部，只存在一套由形式化评估规则构成的机械内核（求值-应用循环）。一旦将特定的 Scheme 代码注入其中，它就能瞬间被参数化为执行该任务的专用设备。

代码和数据在这一层面上彻底融合了：**在解释器眼里，你写的程序本质上就是它正在读入、拆解、解析并据此行动的数据结构。**

### 程序即数据：同像性与代码生成

在 Scheme 语言中，“程序由表达式构成”绝不仅仅是一个语法概念。Scheme 的核心设计哲学之一就是**同像性（Homoiconicity）**：程序的表现形式与它的核心数据结构完全一致。

Scheme 程序的代码不是平铺的文本字符串，它本身就是 Scheme 内置的链表（List）：
- 原始表达式对应基本类型：数字 `2`、`3.3`、布尔值 `#t`、符号 `+`、`quotient`；
- 所有复合表达式（组合式），无一例外全都是 Scheme 的标准列表。

例如，表达式 `(quotient 10 2)` 在内存中的物理结构，就是一个由三个元素组成的链表：符号 `quotient`、数字 `10`、数字 `2`。

如果我们利用基本的列表构造过程：

```scheme
(list 'quotient 10 2)
```

对该表达式求值，并不会触发除法计算，而是返回一个包含三个元素的列表：`(quotient 10 2)`。这就是一小段存放在列表中的 Scheme 源代码。

如果我们希望把这段原本作为“数据”存在的列表转化为“可执行的代码”，只需要调用内置的元循环核心过程——`eval`：

```scheme
(eval (list 'quotient 10 2))
;; 结果输出: 5
```

在 Python 中，虽然也有 `eval("10 // 2")` 这样的函数，但它处理的是冰冷、脆弱、缺乏结构的纯字符串，操作起来极易出错。而在 Scheme 中，由于程序本身就是用最基础的链表表达的，我们拥有针对链表的全部内建操作工具（`car`、`cdr`、`cons`、`list`、`map` 等）。在 Scheme 中“编写一个生成程序的程序”，就像处理普通数据列表一样自然。

#### 从返回数值到返回表达式

为了彻底体会这种区别，我们来对照两个阶乘实现的变体：

```scheme
;; 变体 1：常规函数，返回具体计算出的数值
(define (fact n)
  (if (= n 0)
      1
      (* n (fact (- n 1)))))

;; 变体 2：代码生成函数，返回“计算阶乘的表达式”
(define (fact-exp n)
  (if (= n 0)
      1
      (list '* n (fact-exp (- n 1)))))
```

这两个函数的结构近乎完全一致，但产物截然不同：
- 执行 `(fact 5)`，解释器返回数值 `120`；
- 执行 `(fact-exp 5)`，解释器返回一个深层嵌套的列表表达式：
  `(* 5 (* 4 (* 3 (* 2 (* 1 1)))))`

`fact-exp` 的任务不是计算出结果，而是通过操作列表，动态装配出一棵语法树。当我们对其生成的表达式调用 `eval` 时：

```scheme
(eval (fact-exp 5))
;; 结果输出: 120
```

同样的思想可以无缝迁移到斐波那契数列上：

```scheme
;; 返回数值
(define (fib n)
  (if (<= n 1)
      n
      (+ (fib (- n 2)) (fib (- n 1)))))

;; 返回生成计算树的表达式
(define (fib-exp n)
  (if (<= n 1)
      n
      (list '+ (fib-exp (- n 2)) (fib-exp (- n 1)))))
```

调用 `(fib-exp 4)`，返回的并不是数字 3，而是一个完整的嵌套加法结构：
`(+ (+ 0 1) (+ 1 (+ 0 1)))`

这正是 Lisp 系语言具备超凡表达力的根源：代码可以像黏土一样被其他代码任意揉捏、拼装与展开。

### 准引用与代码模板

虽然我们可以通过不断嵌套 `list` 和 `'`（Quote）来手工拼接代码，但当生成的程序结构稍微复杂一点时，满屏的 `(list 'define (list ...) ...)` 会迅速演变成不可读的灾难。

为此，Scheme 提供了更为强大的程序构造工具：**准引用（Quasiquote）**与**取消引用（Unquote）**。

- **引用（Quote）**：使用单引号 `'`，对其后的一切表达式禁止求值，将其整体作为字面量数据保留；
- **准引用（Quasiquote）**：使用反引号 `` ` ``，功能与引用类似，但它允许在模板内部“挖空”；
- **取消引用（Unquote）**：使用逗号 `,`，专门放置在准引用的内部。被逗号标记的子表达式**会跳出引用状态，强制恢复求值**，并将其求得的值填入模板的对应位置。

我们通过具体的求值对照来理解两者的语法行为。假设我们事先定义了变量：

```scheme
(define b 4)
```

| 表达式 | 求值结果 | 机制说明 |
| :--- | :--- | :--- |
| `'(a b)` | `(a b)` | 纯引用，`b` 仅被视为符号字面量 |
| `'(a (+ b 1))` | `(a (+ b 1))` | 纯引用，内部的 `(+ b 1)` 不会执行 |
| `` `(a ,(+ b 1)) `` | `(a 5)` | 准引用配合取消引用：`a` 作为符号保留，`(+ b 1)` 被求值为 5 填入 |

准引用实际上构筑了一种“代码模板填充机制”。例如，我们可以编写一个专门用于按需生成新过程表达式的函数：

```scheme
(define (make-procedure n)
  `(lambda (d) (+ d ,n)))
```

当我们调用 `(make-procedure 2)` 时，取消引用的 `,n` 被当前传入的实参 `2` 替换，生成的返回结果是一个列表：
`'(lambda (d) (+ d 2))`

如果我们对这个生成出来的列表执行 `(eval (make-procedure 2))`，就能在运行时动态得到一个专门用于“加 2”的一元函数。

### 元编程：在 Scheme 中“发明” while 循环

现在，我们把本讲的所有要素串联起来，完成一个极具代表性的综合挑战：**在根本没有循环控制结构的 Scheme 语言中，通过代码生成来“发明”一个通用的 while 结构。**

#### 问题的提出

考虑一个典型的迭代累加任务：计算小于 10 的所有正偶数的平方和，从 2 开始算起，即计算：
$$2^2 + 4^2 + 6^2 + 8^2 = 120$$

在 Python 中，这只需一个非常朴素的 `while` 循环：

```python
x = 2
total = 0
while x < 10:
    total = total + x * x
    x = x + 2
```

但在原生 Scheme 中，由于缺乏循环语句，我们必须手工编写一个辅助的尾递归过程来模拟这一状态转移：

```scheme
(begin
  (define (loop x total)
    (if (< x 10)
        (loop (+ x 2) (+ total (* x x)))
        total))
  (loop 2 0))
```

再看另一个类似的需求：从 1 开始求和，只要数值的平方小于 50 就持续累加，即计算：
$$1 + 2 + 3 + 4 + 5 + 6 + 7 = 28 \quad (7^2 = 49 < 50, \text{但 } 8^2 = 64 \ge 50)$$

在 Scheme 中，我们又必须重新手写一遍结构极其雷同的模板代码：

```scheme
(begin
  (define (loop x total)
    (if (< (* x x) 50)
        (loop (+ x 1) (+ total x))
        total))
  (loop 1 0))
```

这种代码充满了机械的样板结构（Boilerplate）。两段代码之间，唯一的变数仅仅是：
1. 循环变量的初始值；
2. 循环继续的判断条件（`condition`）；
3. 循环变量的更新步进表达式（`update-x`）；
4. 累加项的表达式（`add-to-total`）。

我们难道必须每次都手动编写这些重复的递归脚手架吗？我们能不能编写一个过程，让 Scheme 替我们把这套递归代码自动“写”出来？

#### 动态构建求和代码

答案就是利用准引用模板，编写一个名为 `sum-while` 的代码生成器：

```scheme
(define (sum-while initial-x condition add-to-total update-x)
  `(begin
     (define (f x total)
       (if ,condition
           (f ,update-x (+ total ,add-to-total))
           total))
     (f ,initial-x 0)))
```

让我们仔细拆解这个准引用内部的每一处“挖空”：
- 整个模板以符号 `begin` 开头；
- `(define (f x total) ...)` 定义了一个局部的辅助循环函数；
- `,condition`：取消引用，将外部传入的判断条件表达式（如 `'(< x 10)`）直接作为 `if` 的谓词子表达式植入；
- `,update-x` 与 `,add-to-total`：取消引用，将变量递增表达式与累加计算规则动态嵌入递归调用 `f` 的实参位置；
- `,initial-x`：取消引用，把初始值作为 `(f ... 0)` 启动调用的第一个参数。

现在，我们调用该过程来生成针对“偶数平方和”的代码：

```scheme
(define code-1 (sum-while 2 '(< x 10) '(* x x) '(+ x 2)))
```

检查 `code-1`，它所保存的求值结果是一个完整的、语法完全合法的 Scheme 表达式列表：

```scheme
(begin
  (define (f x total)
    (if (< x 10)
        (f (+ x 2) (+ total (* x x)))
        total))
  (f 2 0))
```

这正是我们之前手工费力编写的代码！现在我们只需将这个数据交给 `eval`：

```scheme
(eval code-1)
;; 结果输出: 120
```

同样，针对“平方小于 50 的数字之和”，我们生成并求值：

```scheme
(define code-2 (sum-while 1 '(< (* x x) 50) 'x '(+ x 1)))
(eval code-2)
;; 结果输出: 28
```

整个过程的运行流向如下所示：

```text
参数输入:
initial-x = 1
condition = '(< (* x x) 50)
add-to-total = 'x
update-x = '(+ x 1)
         │
         ▼
[ sum-while 过程 (准引用模板拼接) ]
         │
         ▼ 输出为纯 Scheme 链表数据 (代码结构)
'(begin (define (f x total) (if (< (* x x) 50) ...)) (f 1 0))
         │
         ▼
[ eval 求值器 ] ──► 动态定义尾递归函数并执行常数空间迭代
         │
         ▼
输出最终计算结果: 28
```
*图说明：从参数到代码生成，再通过 eval 完成求值的完整元编程生命周期。*

这展示了为什么 Lisp 与 Scheme 能够给予程序员如此震撼的思维解放。在这里，我们通过程序自动写出了另一个遵循严格尾递归的函数，并通过 `eval` 立即投入运行。语言中原本没有 `while` 语法，但借助“程序即数据”的力量，我们轻而易举地在用户层面为其扩展出了等价于 `while` 的高阶抽象工具。

### 本讲提到的题目

在分析尾递归与尾调用概念时，课上明确提出了以下核心练习任务：**请分析下列四个过程定义的语法结构，判定其中哪些是尾递归的（即所有递归调用均处于尾上下文，能够在常量调用栈空间中执行）。**

#### 题目代码定义

```scheme
;; 过程 1：求列表长度
(define (length s)
  (if (null? s)
      0
      (+ 1 (length (cdr s)))))

;; 过程 2：判断元素是否存在
(define (contains s v)
  (if (null? s)
      false
      (if (= (car s) v)
          true
          (contains (cdr s) v))))

;; 过程 3：判断列表中是否有重复元素
(define (has-repeat s)
  (if (null? s)
      false
      (if (contains (cdr s) (car s))
          true
          (has-repeat (cdr s)))))

;; 过程 4：计算斐波那契数
(define (fib-iter current k n)
  (if (= k n)
      current
      (fib-iter (+ current (fib (- k 1))) (+ k 1) n)))

(define (fib n)
  (if (<= n 1)
      n
      (fib-iter 1 2 n)))
```

#### 题目解析与答案

##### 过程 1：`length`
- **判定结果**：**非尾递归**（消耗 $O(n)$ 线性调用栈空间）。
- **解析依据**：外层的 `if` 整体处于尾上下文，但其替代分支是 `(+ 1 (length (cdr s)))`。在这里，最外层的加法操作 `+` 处于尾上下文，而递归调用 `(length (cdr s))` 仅仅是该加法调用的操作数子表达式。在递归调用返回后，解释器仍必须进行“加 1”的剩余计算，当前活动帧无法被丢弃。

##### 过程 2：`contains`
- **判定结果**：**是尾递归**（在 $O(1)$ 常数辅助空间中执行）。
- **解析依据**：外层 `if` 位于函数末尾，属于尾上下文；其替代分支是内层 `if`，因此内层 `if` 整体处于尾上下文；内层 `if` 的替代分支 `(contains (cdr s) v)` 同样处于尾上下文，且它直接构成了递归调用。在该调用返回时无需执行任何后续计算，解释器可直接复用当前帧。

##### 过程 3：`has-repeat`
- **判定结果**：**是尾递归**（在 $O(1)$ 常数辅助空间中执行）。
- **解析依据**：其函数体结构与 `contains` 完全同构，对自身的主体递归调用 `(has-repeat (cdr s))` 处在内层 `if` 的替代分支尾上下文中。虽然在内层谓词位置调用了 `contains`，该谓词子表达式本身不是尾调用，但由于 `contains` 自身也是一个常数辅助空间的尾递归函数，它在执行过程中绝不会引起调用栈累积，调用完即销毁。因此整个 `has-repeat` 过程严格保持在常数调用栈深度内。

##### 过程 4：`fib` 与 `fib-iter`
- **判定结果**：**非尾递归**（消耗非线性的栈空间）。
- **解析依据**：虽然 `fib-iter` 末尾对自身的调用处于替代分支的尾上下文中，但观察其第一个实参子表达式：`(+ current (fib (- k 1)))`。在发起对 `fib-iter` 的调用前，解释器必须先对该操作数求值，这导致了对 `(fib (- k 1))` 的递归调用。该调用处于操作数内部，绝非尾调用；且该非尾调用会进一步交替展开递归调用树，使得解释器必须保留大量未完成的活动帧，无法在常数空间内运行。

> **承前启后**：上一节讲完「尾调用优化与程序即数据」，下一节接着讲「宏与代码转换：在 Scheme 中自定义特殊形式」。

## 宏与代码转换：在 Scheme 中自定义特殊形式
> 对应块：BLK23 | 覆盖分集：P32 | 块标题（分集名）：《Lecture 34 Macros-cn》

今天我们来练习编写一类非常特殊的表达式：**返回代码的表达式**。在 Scheme 中，表达式本身就是列表。如果我们的程序可以随意构造、拼接和变换列表，那是不是意味着——我们的程序可以随心所欲地生成程序？

这就是让人彻底爱上 Lisp 编程的王牌特性：**宏（Macro）**。

在深入宏的黑魔法之前，我们必须先彻底理清它的基石工具：准引用（quasiquote）与取消引用（unquote）。

---

### 准引用热身：用代码生成代码的骨架

在 Scheme 中，如果你想构造一个包含运算符号和变量的表达式，普通引号 `'` 会把后面的一切都原封不动地变成静态符号或列表。但很多时候，我们既希望保留一部分代码骨架不求值，又希望把某些计算结果动态嵌入进去。

这时就需要准引用：

*   **准引用（quasiquote）**：符号是反引号 `` ` ``。它的作用是引用下一个表达式，但允许内部进行局部求值；
*   **取消引用（unquote）**：符号是逗号 `,`。它的作用是发出明确指令：即使外围整个表达式都被引用了，被逗号标记的这个子表达式也**必须立刻求值**。

比如下面这个小例子：

```scheme
`(+ ,(* 2 3) 1)
; 求值结果为：(+ 6 1)
```

在这个表达式中，外层被准引用罩住，因此 `+` 和 `1` 都保持原样；但由于 `(* 2 3)` 前面戴了一个逗号，解释器会强行计算 $2 \times 3 = 6$，然后把 `6` 填回列表。最终我们得到一个由符号 `+`、数字 `6` 和数字 `1` 组成的列表。

现在，我们来看一个综合填空题。

#### 填空实战：生成平方和表达式

我们的目标是构造出形如 $a^2 + b^2$ 的 Scheme 表达式列表。换句话说，求值结果必须是一个包含加号、子表达式 `(* a a)` 和子表达式 `(* b b)` 的列表：`(+ (* a a) (* b b))`。

我们计划分两步走：
1. 定义一个辅助过程 `square-exp`，它接收一个项（term），并生成代表该项自乘的表达式列表 `(* term term)`；
2. 在符号 `'a` 和 `'b` 上分别调用 `square-exp`，并将它们与加号符号 `+` 组装在一起。

下面是骨架代码，其中的每一处下划线 `___` 都可以留空，或者填入准引用 `` ` `` 或取消引用 `,`：

```scheme
___(define (square-exp term)
  ___(* ___term ___term))

___(+ ___(square-exp ___a) ___(square-exp ___b))
```

建议你先不要往下看，花一分钟在草稿纸上填一填。我们将在 3、2、1 后揭晓答案。

```text
答案揭晓：

(define (square-exp term)
  `(* ,term ,term))

`(+ ,(square-exp 'a) ,(square-exp 'b))
```

> **提示**：最后一行调用处的 `'a` 也可以写成准引用 `` `a ``。因为符号 `a` 内部没有任何取消引用的逗号，常规引用与准引用的效果完全等价。

#### 错误推演：填错一个符号会发生什么？

要把求值机制搞透，最好的办法就是亲手看一看各种典型错误会引发什么灾难。

##### 错误一：`square-exp` 内部漏掉了逗号
如果我们写成：

```scheme
(define (square-exp term)
  `(* term term))
```

执行后，外层的加法表达式会变成 `(+ (* term term) (* term term))`。
因为你没有取消引用，解释器会把 `term` 当作字面符号 `term` 塞进列表，而不是取出绑定到形参 `term` 上的实际参数（比如符号 `a` 或 `b`）。

##### 错误二：`square-exp` 内部完全不用引号
如果我们写成：

```scheme
(define (square-exp term)
  (* term term))
```

当我们调用 `(square-exp 'a)` 时，解释器会直接崩溃报错：
`operand 0 is not a number: a`。
因为乘法过程 `*` 要求操作数必须是数值，而你直接把符号 `'a` 当作数字传给 `*` 进行算术运算，这在动态类型检查时是通不过的。

##### 错误三：组装表达式时给 `+` 加上了引用
如果在总表达式中把加号也引用了：

```scheme
`(',+ ,(square-exp 'a) ,(square-exp 'b))
```

最终生成的列表第一项就不是纯净的加号符号 `+`，而是变成了带有引号包装的字面结构，破坏了标准 Scheme 语法树的形态。

##### 错误四：调用 `square-exp` 时漏掉了逗号
如果外层有准引用，但函数调用前没加逗号：

```scheme
`(+ (square-exp 'a) (square-exp 'b))
```

解释器根本不会去执行 `square-exp`。你最终得到的结果列表里，会直接硬生生地躺着四个子表达式列表：`square-exp`、`'a`……它把函数调用表达式本身当成了数据文本，而不是执行该函数并取回返回值。

##### 错误五：传入参数时漏掉了对 `a` 的引用
如果写成 `(square-exp a)`：
注意，此时 `(square-exp ...)` 前面已经加了逗号，意味着当前子表达式处于**正常求值上下文**中。如果 `a` 裸奔而不带引号，解释器会把 `a` 当作当前环境中的变量去查找绑定值。如果此时并未定义变量 `a`，就会当场抛出未知标识符错误（unknown identifier）。因此必须给它加上引号 `'a`。

### 什么是宏：打破求值规则的语言扩展器

在 Python 中，语言预先设计好了固定种类的表达式和语句；Scheme 也是如此，语言内置了诸如 `define`、`lambda`、`if`、`cond`、`and`、`or`、`begin` 等固定数量的**特殊形式（Special Forms）**。除了这些特殊形式，其他所有调用都遵循一套铁律：**普通过程调用规则**。

> **回顾**：普通过程调用的求值规则：
> 1. 先对运算符子表达式求值，得到一个过程；
> 2. 对所有操作数子表达式**从左到右依次求值**，拿到实际的参数值；
> 3. 将过程应用在这些参数值上。

但这套铁律有时候会成为一副枷锁。有些控制逻辑（例如短路逻辑、延迟执行、代码复刻）在普通过程调用下是根本无法实现的。

而宏（Macro）赋予我们的能力，就是**允许程序员在语言中发明属于自己的全新特殊形式**。

这意味着我们可以亲手改写语言的工作方式，创造全新的代码评估流程。

```text
                    ┌────────────────────────┐
                    │ 程序员编写的源代码文本 │
                    └───────────┬────────────┘
                                │ 解析为列表 (S-expression)
                                ▼
                    ┌────────────────────────┐
                    │  宏 (Macro) 转换阶段   │  <--- 不求值操作数！
                    │  代码作为数据进行重组  │       直接对源码树进行计算
                    └───────────┬────────────┘
                                │ 生成全新的代码列表
                                ▼
                    ┌────────────────────────┐
                    │  标准求值器二次求值   │  <--- 真正执行业务逻辑
                    └────────────────────────┘
```

宏在像 Lisp/Scheme 这样的语言中之所以极其自然且威力无穷，核心在于八个字：**代码即数据（Code as data）**。在 Scheme 中，程序的语法树就是由基础的 Cons 单元拼成的列表。因此，宏的本质无非就是**一个在代码被求值之前运行的转换程序**：它吃进一段代码列表，吐出一段新组装的常规 Scheme 代码列表，最后交给解释器二次求值。

在 Scheme 中，我们使用 `define-macro` 特殊形式来定义一个宏。

### 从 `twice` 看宏的本质：控制代码的求值时机

为了直观体会宏与普通过程的分水岭，我们来看一个需求：编写一个名为 `twice` 的结构，让某个表达式连续执行两遍。

比如，我们希望执行 `(twice (print 2))`，控制台能连续打印出两个 2。

#### 普通过程的无能为力

假设我们试图用普通过程来实现它：

```scheme
(define (twice expr)
  (list 'begin expr expr))
```

现在我们在终端中调用 `(twice (print 2))`，会发生什么？

根据过程求值规则，解释器在进入 `twice` 的函数体之前，**必须首先对操作数 `(print 2)` 求值**！
1. `(print 2)` 立即被执行，控制台上打印出了第一个 `2`；
2. `print` 的返回值通常是无意义的值（比如 `undefined` 或空值）；
3. 随后，这个空值被当作形参 `expr` 传进了 `twice` 函数体；
4. `twice` 拼出了列表 `(begin undefined undefined)` 并将其返回。

一旦一个表达式被提前求值了，伴随它的副作用（副作用打印）就已经烟消云散，你再也没有机会让它“重新执行一遍”。你无法用一个普通函数去“复制”一次原本该发生的计算过程。

如果想用过程达到目标，调用方必须极度别扭地手动加引号传递源代码：`(twice '(print 2))`，然后再手动调用解释器内部的 `eval` 去跑两次。这把巨大的心智负担转嫁给了调用者。

#### 用 `define-macro` 实现优雅拦截

现在我们把它改写为宏：

```scheme
(define-macro (twice expr)
  (list 'begin expr expr))
```

定义语法看起来和普通函数如出一辙，但它的底层执行机制彻底变了。

当我们写下 `(twice (print 2))` 时，求值流程如下：

```text
调用: (twice (print 2))
         │
         │ 1. 解释器发现 twice 是一个宏
         │    【绝不求值操作数！】
         │    形参 expr 直接绑定到原始表达式列表: '(print 2)
         ▼
执行宏体: (list 'begin expr expr)
         │
         │ 2. 宏完成代码拼接，返回全新表达式:
         ▼
展开结果: (begin (print 2) (print 2))
         │
         │ 3. 解释器对展开后的新表达式进行【二次求值】
         ▼
执行效果: 连续两次求值 (print 2)，屏幕上依次打印出两个 2
```

> **核心机制**：
> 普通过程接受**值**，返回**值**；
> 宏接受**表达式**，返回**表达式**。

这件事情既简单又深刻：
*   **简单之处在于**：宏做的事情本质上就是帮我们自动完成了“先引用阻断求值 $\to$ 传给函数重组代码 $\to$ 最终对展开代码求值”这整套繁琐手工流水线；
*   **深刻之处在于**：我们彻底接管了代码何时求值、求值多少次甚至要不要被求值的终极控制权。

### 实战一：构建带代码上下文的测试断言 `check`

让我们把宏运用到一个极具工程价值的场景：单元测试断言。

假设我们要写一个小工具：检查某个布尔条件是否为真。如果为真，输出测试通过；如果为假，输出测试失败。

#### 普通断言的盲区

如果用普通过程写，通常会这样实现：

```scheme
(define (check val)
  (if val 'passed 'failed))
```

假设我们设定变量 $x = -2$，然后运行测试：

```scheme
(define x -2)
(check (> x 0))
; 返回: failed
```

程序确实返回了 `failed`。但当你的工程里有上千个断言时，单独看到一个冷冰冰的 `failed` 会让人抓狂：**究竟是哪一个子表达式导致了失败？**

普通过程 `check` 根本无能为力。因为当执行权移交给 `check` 时，操作数 `(> x 0)` 早就被求值成了字面量 `#f`。形参 `val` 拿到的仅仅是一个布尔值 `#f`，原始表达式的文本信息早已在求值过程中灰飞烟灭。

#### 用宏保留失败现场

为了让报错不仅说出“失败了”，还能把导致失败的**具体源码表达式**原汁原味地吐出来，我们必须把 `check` 升级为宏。

此时形参 `expr` 接收到的不是布尔值，而是未求值的代码列表 `'(> x 0)`。

```scheme
(define-macro (check expr)
  (list 'if expr ''passed (list 'quote (list 'failed expr))))
```

我们来逐层拆解这个宏返回的代码树：
1. 列表最前头是符号 `'if`；
2. 随后放入我们想要执行的条件表达式 `expr`；
3. 如果条件成立，返回符号 `'passed`（所以在宏构造时写两个单引号 `''passed`，求值后变成引用形式 `'passed`）；
4. 如果条件失败，返回一个列表，该列表以符号 `'failed` 开头，紧跟被保留下来的原始表达式 `expr`。通过加上 `'quote` 包装，确保失败分支返回的是未被再次计算的代码结构。

让我们加载这个宏，看看实际运行表现：

```scheme
(define x -2)
(check (> x 0))
; 返回: (failed (> x 0))
```

看到差别了吗？
返回结果不再只是一个抽象的 `failed`，而是明白地写着：`(failed (> x 0))`！

```text
传入代码: (check (> x 0))
              │
              │ 宏展开阶段 (expr 绑定为字面列表 '(> x 0))
              ▼
组装为:   (if (> x 0) 'passed '(failed (> x 0)))
              │
              │ 解释器二次求值阶段
              │ 1. 评估条件 (> x 0) -> 计算结果为 #f
              │ 2. 命中 else 分支 -> 求值 '(failed (> x 0))
              ▼
最终输出: (failed (> x 0))
```

这正是宏的绝活：**它能把源代码本身捕获为数据，并自由注入到最终生成的执行流中**。

### 实战二：无中生有，给 Scheme 制造 `for` 循环

Scheme 语言的一大特色就是极简——它甚至连命令式语言里最普遍的 `for` 循环语句都没有。

在没有宏之前，如果我们想对列表 `'(2 3 4 5)` 中的每个元素求平方，我们必须老老实实写高阶函数 `map`，并显式构造一个 `lambda` 匿名函数：

```scheme
(map (lambda (x) (* x x)) '(2 3 4 5))
; 返回: (4 9 16 25)
```

这种写法语义非常清晰，但在语法结构上略显冗长。如果我们要为 Scheme 扩充一套原生的 `for` 语法，期望能够写出这种形式：

```scheme
(for x '(2 3 4 5) (* x x))
```

这可能吗？我们用宏来凭空创造这个语法！

#### 宏展开的结构映射

我们要做的，就是把用户编写的简洁语法，在编译/求值前重写成底层的 `map` 表达式。

对比两者的结构差异：

```text
程序员想写的代码:
(for       x          '(2 3 4 5)         (* x x)       )
 │         │              │                 │
 │         ▼              ▼                 ▼
 │     [循环变量 sym]  [数据列表 vals]  [执行体 expr]
 │         │              │                 │
 └─────────┼──────────────┼─────────────────┼─────────┐
           │              │                 │         │
           ▼              │                 ▼         ▼
转换后的目标代码:         │                 │         │
(map (lambda (x) ─────────┼─────────────> (* x x)) '(2 3 4 5))
```

从结构上一目了然：
宏需要接收三个参数：变量符号 `sym`、数据源 `vals` 以及循环体表达式 `expr`。
宏的任务就是生成一个以 `map` 开头的列表，其第二项是一个构造出来的 `(lambda (sym) expr)` 列表，第三项是 `vals`。

#### 实现 `for` 宏

我们来写出它的通用定义：

```scheme
(define-macro (for sym vals expr)
  (list 'map 
        (list 'lambda (list sym) expr) 
        vals))
```

如果你习惯使用准引用，这段代码写起来会更加舒展：

```scheme
(define-macro (for sym vals expr)
  `(map (lambda (,sym) ,expr) ,vals))
```

> **注意**：在构造 `lambda` 形参时，`sym` 必须被包装在一个列表中（即 `(list sym)` 或 `(,sym)`），因为在 Scheme 语法规范中，`lambda` 的形参列表必须是一个括号括起来的列表结构。

现在我们测试这套全新发明的语言语法：

```scheme
(for x '(3 4 5) (* x x))
; 返回: (9 16 25)
```

解释器在面对 `(for x '(3 4 5) (* x x))` 时：
1. 识别出 `for` 是宏；
2. 不对 `x`、`'(3 4 5)`、`(* x x)` 进行预先求值，而是作为语法列表传入；
3. 展开成 `(map (lambda (x) (* x x)) '(3 4 5))`；
4. 解释器评估该映射调用，最终吐出 `(9 16 25)`。

通过短短三行代码，我们把一种全新的控制流语句毫无违和感地织入了语言核心。

### 实战三：非侵入式函数跟踪器 `trace`

我们在分析递归程序时，经常需要观察函数的调用过程与调用栈深度。

#### Python 中的做法：装饰器与它的局限

在 Python 中，我们通常使用装饰器来实现这个功能：

```python
def trace(fn):
    def traced(n):
        print(f"{fn.__name__}({n})")
        return fn(n)
    return traced

@trace
def fact(n):
    if n == 0:
        return 1
    else:
        return n * fact(n - 1)
```

当我们在 Python 中执行 `fact(5)` 时，终端会一路层叠打印出 `fact(5)`、`fact(4)`、`fact(3)`……最后返回 120。

但 Python 装饰器有一个根本性的限制：**它是永久性、静态绑定的**。一旦你在 `def fact` 头部挂上了 `@trace`，`fact` 这个全局名字就被永久替换成了包装后的函数。在随后的程序中，无论你想不想看调用追踪，只要调用 `fact`，它都会无条件打印输出。除非你重新定义它，否则无法做到“这一次调用打印，下一次调用保持安静”。

#### Scheme 中无装饰器下的动态追踪

在 Scheme 中，我们有一个标准的阶乘函数：

```scheme
(define (fact n)
  (if (= n 0)
      1
      (* n (fact (- n 1)))))
```

调用 `(fact 5)` 返回 120，没有任何多余的输出。
如果我们希望在某一次计算时追踪它的每一步递归过程，但在追踪结束后**立即将函数还原，不留任何后遗症**，我们该怎么做？

最原始的思路是打一套“组合拳”：
1. 把原本纯净的 `fact` 函数指针备份到一个中间变量 `original`；
2. 把 `fact` 重新定义为一个包装函数：先打印当前的符号与参数，再调用 `original`；
3. 执行 `(fact 5)`；
4. 调用结束后，再把 `original` 重新赋值回 `fact`。

在终端中手动敲这四步显然太反人类了。我们能不能写一个宏，直接以这样的形式调用：

```scheme
(trace (fact 5))
```

让它在单次表达式执行期间启动追踪，一旦表达式计算完毕，自动恢复现场？

#### 构造恢复机制：`begin` 组合体

要在一个表达式内部完成“备份 $\to$ 劫持 $\to$ 计算 $\to$ 还原 $\to$ 输出结果”的全生命周期，我们需要利用 `begin` 特殊形式。

```text
┌────────────────────────────────────────────────────────┐
│ begin 复合表达式内部时序                                │
├────────────────────────────────────────────────────────┤
│ 1. (define original <operator>)    ; 备份原函数        │
│ 2. (define <operator>              ; 劫持并重构函数名   │
│       (lambda (n)                                      │
│          (print (list '<operator> n))                  │
│          (original n)))                                │
│ 3. (define result <expr>)          ; 执行原表达式拿结果 │
│ 4. (define <operator> original)    ; 恢复现场还原函数   │
│ 5. result                          ; 作为整个 begin 结果│
└────────────────────────────────────────────────────────┘
```

把这个逻辑固化为一个通用宏，我们需要解决两个细节：
1. 提取操作符：对于输入表达式 `expr`（如 `(fact 5)`），其函数名是列表的头部，即 `(car expr)`。在我们的宏中，把它命名为 `op`；
2. 打印的是**符号**而不是过程对象：如果在打印时写 `(print (list op n))`，由于 `op` 此时求值为过程对象，终端会打印出一长串晦涩的 `<procedure fact>`；我们必须对操作符加单引号 `',op`，确保终端优雅地输出清晰的符号文本 `(fact 5)`。

#### 编写通用的 `trace` 宏

将这些要素用准引用编织在一起，就得到了这个强大的通用跟踪宏：

```scheme
(define-macro (trace expr)
  (let ((op (car expr)))
    `(begin
       (define original ,op)
       (define ,op (lambda (n)
                     (print (list ',op n))
                     (original n)))
       (define result ,expr)
       (define ,op original)
       result)))
```

我们来逐段品味这段宏构造的精妙之处：

*   `(let ((op (car expr))) ...)`：在展开期先拿到被调用函数的符号（例如符号 `'fact`）；
*   `define original ,op`：把当前的 `fact` 绑定保存一份；
*   `define ,op (lambda (n) ...)`：由于使用了 `,op`，这里会被精准展开为 `(define fact (lambda (n) ...))`，从而在递归调用的作用域内完成了局部名称覆盖；
*   `print (list ',op n)`：这里展开为 `(print (list 'fact n))`，在每次递归进入时打出调用参数；
*   `define result ,expr`：执行实际的函数调用（展开为 `(define result (fact 5))`），并将最终返回值锁存在 `result` 中；
*   `define ,op original`：现场清理！把 `fact` 重新拨回纯净的未追踪状态；
*   `result`：作为 `begin` 块的最后一个子表达式，它的值将作为整个 `trace` 表达式的最终求值结果返还给调用者。

运行效果立竿见影：

```scheme
; 1. 常规调用，毫无杂音
(fact 5)
; 返回: 120

; 2. 动态临时追踪
(trace (fact 5))
; 终端输出调用栈：
; (fact 5)
; (fact 4)
; (fact 3)
; (fact 2)
; (fact 1)
; (fact 0)
; 返回: 120

; 3. 再次常规调用，函数已被完美还原，没有任何副作用遗留！
(fact 5)
; 返回: 120
```

> **结论**：
> Python 装饰器追踪的是**过程实体（Function definition）**，是永久性的侵入式修改；
> 而 Scheme 宏追踪的是**表达式调用（Expression evaluation）**。我们可以任意选择在何时追踪某一次调用，一旦执行完毕系统自动恢复如初。这种关注点分离的粒度比传统装饰器更加轻盈、也更加纯粹。

#### 题目一：准引用与取消引用拼装

##### 题干
请在下面 Scheme 代码的所有空白处（下划线 `___` 位置）填上合适的内容。每个空白处可以保持为空，也可以填入准引用符号（`` ` ``）或取消引用符号（`,`）。

要求代码运行后，第二个表达式必须求值为等价于 $a^2 + b^2$ 的 Scheme 语法列表，即 `(+ (* a a) (* b b))`：

```scheme
___(define (square-exp term)
  ___(* ___term ___term))

___(+ ___(square-exp ___a) ___(square-exp ___b))
```

##### 解析
1. **第一行顶层定义**：我们要定义一个全局过程 `square-exp`，此处必须正常执行 `define` 特殊形式，绝不能被引用，因此顶层空白处必须**保持为空**；
2. **`square-exp` 的函数体**：
   * 我们的目标是返回一个形如 `(* a a)` 的表达式列表，因此必须对外层使用准引用 `` ` ``；
   * 在准引用内部，如果我们直接写 `(* term term)`，得到的将是字面符号 `term` 而不是参数值；为了取出实参所绑定的符号（如 `'a` 或 `'b`），必须在两个 `term` 前面分别添加取消引用逗号 `,`；
   * 因此函数体应为：`` `(* ,term ,term) ``；
3. **主调用表达式**：
   * 最终目标是生成一个以加号开头的列表 `(+ ...)`，因此最外层必须使用准引用 `` ` ``；
   * 在准引用内部，符号 `+` 需要保持原样作为列表的表头，其前面**保持为空**；
   * 两个 `(square-exp ...)` 是需要被实际求值并生成子列表的函数调用表达式，必须在它们前面分别加上逗号 `,` 取消引用；
   * 传给 `square-exp` 的参数是变量名本身（即符号 `'a` 和 `'b`），由于此时处于被逗号取消引用的正常求值环境中，直接写 `a` 会被当作未定义变量求值报错，因此必须通过引号保护起来，写成 `'a` 或 `` `a ``。

##### 答案
```scheme
(define (square-exp term)
  `(* ,term ,term))

`(+ ,(square-exp 'a) ,(square-exp 'b))
```

#### 题目二：实现自定义 `for` 循环宏

##### 题干
Scheme 语言原生并没有提供针对列表进行迭代的 `for` 循环语句。请利用 `define-macro` 编写一个名为 `for` 的宏，使其允许程序员使用如下语法遍历列表并对每个元素执行表达式求值：

```scheme
(for <sym> <vals> <expr>)
```

例如，执行 `(for x '(2 3 4 5) (* x x))` 时，要求返回一个包含各元素计算结果的列表 `(4 9 16 25)`。

##### 解析
1. **确定展开目标**：
   在底层，对一个列表 `vals` 的每一项应用某种表达式运算，对应的原生机制是 `(map (lambda (<sym>) <expr>) <vals>)`。
2. **确定宏参数处理机制**：
   宏 `for` 接收三个操作数表达式：`sym`（符号）、`vals`（数据源列表表达式）、`expr`（循环体计算表达式）。
   因为宏的操作数不会被预先求值，所以传入的 `sym` 就是变量符号本身，`expr` 是未执行的计算代码。
3. **代码拼接**：
   * 我们需要把 `sym` 封装为 `(list sym)`，作为 `lambda` 的形式参数列表；
   * 将 `expr` 作为 `lambda` 的函数体，拼成 `(list 'lambda (list sym) expr)`；
   * 最后把符号 `'map`、构造好的 `lambda` 表达式以及数据源 `vals` 组装成一个三元素列表并返回。
   * 使用准引用语法可以更直观地写成：`` `(map (lambda (,sym) ,expr) ,vals) ``。

##### 答案
**方式一：纯列表构造法**
```scheme
(define-macro (for sym vals expr)
  (list 'map 
        (list 'lambda (list sym) expr) 
        vals))
```

**方式二：准引用拼装法**
```scheme
(define-macro (for sym vals expr)
  `(map (lambda (,sym) ,expr) ,vals))
```
