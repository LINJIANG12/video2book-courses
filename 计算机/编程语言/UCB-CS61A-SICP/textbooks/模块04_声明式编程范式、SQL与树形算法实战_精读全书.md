## 声明式编程与表处理：SQL 核心心智模型
> 对应块：BLK24 | 覆盖分集：P33-P34 | 块标题（分集名）：《Lecture 35 SQL-cn》

平时我们写 Python 或 Scheme，核心都在关注执行过程：第一步做什么，第二步调用什么函数，变量怎么随时间变化，递归到基线条件没有。我们的大脑一直在模拟计算机解释器的运行步调。

但在现实世界中，几乎所有大型系统和组织都在花费惊人的资金维护另一类完全不同的软件——数据库管理系统（DBMS）。无论是在商业级闭源系统还是出色的开源项目中，它们都围绕一种独特的编程语言展开：结构化查询语言（SQL，Structured Query Language）。

SQL 是最广泛使用的编程语言之一，但它会彻底改变你与程序执行之间的关系。这一次，我们暂时远离斐波那契数列与整数序列，换一个更有趣的主题——狗，来建立声明式数据处理的完整心智模型。

### 声明式编程的本质：告诉计算机“要什么”而不是“怎么做”

我们此前接触的大多数语言都属于**命令式编程语言**（Imperative Programming Language）。在命令式语言里，程序是对计算过程的详细描述，解释器负责按部就班地执行这套规则。

SQL 以及像 Prolog 这样的语言，属于**声明式编程语言**（Declarative Programming Language）。在声明式世界里，程序只是一份对**期望结果的描述**，至于到底怎么生成这个结果，全权交给解释器（数据库引擎）去找出方案。

```text
+--------------------------------------------------------------+
| 命令式编程 (Imperative)                                       |
| 程序员描述算法执行过程  --->  解释器一步一步照做             |
+--------------------------------------------------------------+
| 声明式编程 (Declarative)                                      |
| 程序员描述期望的结果    --->  DBMS 引擎自行寻找最优计算路径  |
+--------------------------------------------------------------+
```

这带来了一个根本性的转变：程序变得更加容易编写，因为你不用再把执行与求值的每个微小步骤事无巨细地罗列出来；但这也让程序的运行变得不那么直观可测。

对于同一个 SQL 查询，底层可能有多种完全不同的算法来生成结果。数据库管理系统会根据当前表中数据的规模、分布和索引情况，动态挑选它认为最快的一条路径。写同样的代码，面对不同的数据，底层执行过程可能截然不同。

#### 记录与属性构成的表结构

数据库组织数据的基础是**表**（Table）。表是记录的集合，每一条记录就是表中的一**行**（Row）。

每一行都为表中的各个**列**（Column）保存了一个具体的属性值。列有自己的名称（Column Name），列名并不是数据记录的一部分，而是用来告诉你该位置代表了记录的哪项属性。

```text
+-------------+--------------+-----------------+  <-- 列名 (Column Names)
|  latitude   |  longitude   |      name       |
+-------------+--------------+-----------------+
|     38      |     122      |    Berkeley     |  <-- 行 / 记录 (Row / Record)
|     42      |      71      |    Cambridge    |
|     45      |      93      |   Minneapolis   |
+-------------+--------------+-----------------+
```

上面这张表记录了城市的信息。这里的 Cambridge 指的是马萨诸塞州的剑桥，而不是英国的剑桥——看它的经纬度数值就能确定。每一行代表一个地点，每一列都是这些地点的固定属性。

#### 声明式与命令式的执行鸿沟

SQL 虽然有国际规范，但有趣的是，各个大型数据库供应商在激烈竞争中总会夹带自己的私货，扩展出不同的方言。不过别担心，核心的语言行为在各大系统中高度一致。

实际上，执行核心查询操作的代码非常紧凑，紧凑到足以写在一张纸上，用 Python 也能轻松搭建出一个简易解释器。

在 SQL 中，我们虽然会见到 `INSERT`、`UPDATE`、`DELETE`、`ANALYZE`、`EXPLAIN` 等语句，但对于理解数据处理的核心逻辑而言，**`SELECT` 语句**才是绝对的主角。SQL 的大部分魅力，就在于如何利用 `SELECT` 表达复杂的关联与投影。

### 从字面值到投影查询

我们平时使用的数据库表，大多数是由外部应用程序持续记录或人工录入逐渐建立起来的。但在学习与探索阶段，我们需要掌握如何从零开始，凭空用 SQL 声明出一张表。

#### 用 SELECT 和 UNION 凭空造表

在 SQL 中，最基础的造表积木是使用字面常量构成的 `SELECT` 语句。

列的描述由一个表达式构成，后接可选的 `AS` 关键字来指定列名，多列之间用逗号分隔，语句以分号结尾：

```sql
SELECT 38 AS latitude, 122 AS longitude, 'Berkeley' AS name;
```

这段语句会创建一张只有一行三列的临时表。注意 `'Berkeley'` 用单引号括起来表示字面字符串值，而 `latitude`、`longitude` 和 `name` 是没有引号的列名标识符。

单独一行表没有太大实用价值。要构建多行表，可以使用 `UNION` 关键字将多个单行查询联合起来：

```sql
SELECT 38 AS latitude, 122 AS longitude, 'Berkeley' AS name UNION
SELECT 42,            71,             'Cambridge'          UNION
SELECT 45,            93,             'Minneapolis';
```

> **提示**：联合（`UNION`）要求两边的查询具有相同的列数，并且对应列的数据类型相容。最终结果集的列名由第一个 `SELECT` 语句中定义的名称决定，后续的 `SELECT` 语句不需要重复写 `AS 列名`。

默认情况下，直接输入 `SELECT` 语句，终端只是把查询计算出来的表打印在屏幕上，并不会永久保留。如果想把结果存下来反复使用，需要用到 `CREATE TABLE` 语句：

```sql
CREATE TABLE cities AS
  SELECT 38 AS latitude, 122 AS longitude, 'Berkeley' AS name UNION
  SELECT 42,            71,             'Cambridge'          UNION
  SELECT 45,            93,             'Minneapolis';
```

接下来引入我们的核心实验对象——狗。我喜欢狗，虽然我现实中没养这么多狗，但我很喜欢按字母表 A 到 H 顺着给它们起名字，恰好我也很喜欢美国总统，于是有了 Abraham、Barack、Clinton、Delano、Eisenhower、Fillmore、Grover、Herbert。

我们把它们的亲子血缘关系构建成一张 `parents` 表：

```text
                    Eisenhower
                        |
                     Fillmore
                  /     |     \
          Abraham    Delano    Grover
          /     \       |
     Barack  Clinton Herbert
```

读图说明：树形结构表示谱系亲子关系，上方为父辈，下方为子代。Fillmore 是 Abraham、Delano、Grover 的父辈；Abraham 又是 Barack 和 Clinton 的父辈。

我们在 SQL 中用字面值联合声明这张表：

```sql
CREATE TABLE parents AS
  SELECT 'Eisenhower' AS parent, 'Fillmore' AS child UNION
  SELECT 'Fillmore',             'Abraham'           UNION
  SELECT 'Fillmore',             'Delano'            UNION
  SELECT 'Fillmore',             'Grover'            UNION
  SELECT 'Abraham',              'Barack'            UNION
  SELECT 'Abraham',              'Clinton'           UNION
  SELECT 'Delano',               'Herbert';
```

执行后，我们就拥有了一张由两列（`parent`、`child`）、七条记录构成的基准数据表。

#### 基础查询骨架：FROM、WHERE 与 ORDER BY

有了现成的表，我们就可以使用 `SELECT` 将一张已存在的表投影（Project）成一张新表。标准的查询骨架包含以下子句：

```sql
SELECT [列描述列表]
FROM [输入表]
WHERE [过滤条件]
ORDER BY [排序表达式];
```

各个子句各司其职：
- `FROM`：指定从哪张（或哪些）原始表中提取行。
- `WHERE`：对输入的每一行应用布尔判断，只有计算结果为真的行才会被保留。
- `ORDER BY`：决定最终输出行按照怎样的顺序排列。
- `SELECT` 之后的列表：决定保留下来的行如何映射、投影到最终的输出列中。

比如，我们要找出 Abraham 的所有孩子：

```sql
SELECT child FROM parents WHERE parent = 'Abraham';
```

系统会逐行扫描 `parents` 表，匹配 `parent` 列为 `'Abraham'` 的行，仅投影出 `child` 列，最终生成一张单列、包含两行（Barack 与 Clinton）的新表。

如果我们写出这样的查询：

```sql
SELECT parent FROM parents WHERE parent > child;
```

在 SQL 中，字符串之间的比较使用的是字典字母序。`parent > child` 意味着父亲的名字在字母表中的排序位于孩子之后。

对照家谱数据：
- Fillmore 与 Abraham 相比，F 在 A 之后（成立）。
- Fillmore 与 Delano 相比，F 在 D 之后（成立）。
- 其余行均不满足该条件。

因此查询结果将包含两行数据，且两行内容都是 Fillmore。

> **易错点**：表中出现完全相同的重复行是完全合法的。`SELECT` 的过滤与投影作用于输入的每一行，只要输入行中有两行独立的数据都满足条件，输出表中就会如实产生两个看似相同的记录。

#### 行内算术表达式与缆车载客量

在 `SELECT` 语句的列描述中，列名会被解析为该行对应的数值。我们可以引入常数与加、减、乘、除等算术运算符，直接从旧值计算出新值。

以滑雪场的缆车（chairlift）为例。假设我们有一张表记录了不同编号缆车上的乘客组合：单人乘坐者（single）的数量，以及双人情侣乘坐者（couple）的组数。

```text
+---------+----------+----------+
|  chair  |  single  |  couple  |
+---------+----------+----------+
|   101   |    2     |    2     |  --> 2 人独自坐，2 对情侣坐 (2 + 2*2 = 6人)
|   102   |    0     |    3     |  --> 0 人独自坐，3 对情侣坐 (0 + 2*3 = 6人)
|   103   |    6     |    0     |  --> 6 人独自坐，0 对情侣坐 (6 + 2*0 = 6人)
+---------+----------+----------+
```

如果我们要计算每把缆椅上的总人数，只需写出算术表达式：

```sql
SELECT chair, single + 2 * couple AS total FROM lift;
```

在执行过程中，算术运算纯粹是在**单行内部**独立完成的。系统处理 101 号椅子时，取出的就是这一行的 `single` (2) 和 `couple` (2)；绝对不会把 101 号椅子的数据与 102 号椅子的数据串在一起相加。

```text
输入行: [ chair: 101 | single: 2 | couple: 2 ]
                   │
                   ▼ (执行 single + 2 * couple)
输出行: [ chair: 101 | total: 6 ]
```

### 表的连接与多表组合

如果只能从单张表中筛选投影，SQL 的表现力依然有限。关系型数据库最强大的能力在于**连接**（Join）——将分散在不同表中的结构化事实拼装关联起来。

#### 逗号连接与笛卡尔积

在学术界和工程界，表与表之间的连接有多种名称和类型，但其核心逻辑可以归结为最纯粹的形式：在 `FROM` 之后用逗号列出两张表。

用逗号将表 A 和表 B 连接时，数据库引擎会计算两张表的**笛卡尔积**（Cartesian Product），即：**拿出 A 的每一行，与 B 的每一行进行穷举配对**。如果 A 有 7 行，B 有 8 行，连接出的新表就包含 $7 \times 8 = 56$ 行。

为了进行有意义的数据组合，我们引入第二张表：`dogs`，记录每只狗的毛发特征（长毛 long、短毛 short、卷毛 curly）。

```sql
CREATE TABLE dogs AS
  SELECT 'Abraham' AS name, 'long' AS fur UNION
  SELECT 'Barack',         'short'       UNION
  SELECT 'Clinton',        'long'        UNION
  SELECT 'Delano',         'long'        UNION
  SELECT 'Eisenhower',     'short'       UNION
  SELECT 'Fillmore',       'curly'       UNION
  SELECT 'Grover',         'short'       UNION
  SELECT 'Herbert',        'curly';
```

现在两张表各司其职：`parents` 存家谱亲子关系，`dogs` 存品种毛色关系。

假设我们要回答一个问题：**所有卷毛狗的父母分别是谁？**

这需要将两张表的信息粘合起来。我们在 `FROM` 后写出两张表，并在 `WHERE` 子句中声明两张表之间的关联线索：

```sql
SELECT parent
FROM parents, dogs
WHERE child = name AND fur = 'curly';
```

让我们拆解底层的运行过程：

```text
parents 表的一行: [ parent: 'Eisenhower', child: 'Fillmore' ]
                                  │
                                  ├─ 笛卡尔配对
                                  ▼
   dogs 表的一行: [ name: 'Fillmore', fur: 'curly' ]

检查 WHERE 条件:
1. child = name  --> 'Fillmore' = 'Fillmore' (真)
2. fur = 'curly' --> 'curly' = 'curly'       (真)

保留该行，投影 SELECT parent:
输出结果: 'Eisenhower'
```

笛卡尔积会产生大量风马牛不相及的配对（比如把 Abraham 和 Delano 的毛发信息配在一起），但 `WHERE child = name` 强行划定了语义边界——只有当 `dogs` 表里的名字恰好等于 `parents` 表里的孩子名字时，这种配对才被认可；再加上 `fur = 'curly'`，最终精准过滤出我们想要的两条记录：Eisenhower（Fillmore 的父母）和 Delano（Herbert 的父母）。

#### 别名与自连接：找出所有的兄弟姐妹

当两个表里包含同名的列，或者**将一张表与它自身连接**（Self-join）时，歧义就出现了。如果两边都叫 `child`，解释器怎么知道你比的是哪一边的列？

解决之道是**表别名**（Alias）和**点表达式**（Dot Expression）。

语法是在 `FROM` 后面的表名后跟一个 `AS 别名`（`AS` 经常可以省略，但写出来更清晰），随后用 `别名.列名` 来精准定位数据来源。

考虑一个典型任务：**在 `parents` 表中，找出所有亲兄弟姐妹对（拥有相同父母的两只狗）。**

同一个父母的多只小狗是作为独立的两行记录分别存储在 `parents` 表中的。要对比它们，我们必须同时审视两行数据——这意味着需要把 `parents` 表与它自身连接：

```sql
SELECT a.child AS first, b.child AS second
FROM parents AS a, parents AS b
WHERE a.parent = b.parent AND a.child < b.child;
```

这段代码包含了极其精妙的逻辑设计，值得逐条剖析：

- `FROM parents AS a, parents AS b`：在概念上克隆出两张一模一样的家谱表，分别叫 $A$ 和 $B$，并将它们所有的行两两组合。
- `a.parent = b.parent`：要求 $A$ 行中的父母必须等于 $B$ 行中的父母，这锁定了同一个双亲。
- `a.child < b.child`：这一行条件同时解决了两个严重的问题：
  1. 如果只写 `a.child != b.child`，我们会同时得到 `Barack, Clinton` 和 `Clinton, Barack`。它们本质上是同一对兄弟，只是顺序相反，造成了无意义的重复镜像。
  2. 如果写 `=`，小狗就会和自己结成兄弟对（比如 `Barack, Barack`）。
  3. 采用 `<` 严格比较字符串字母序，不仅天然排除了自身等于自身的情况，还强行规定**排在前面的孩子名字必须在字母序上小于排在后面的孩子**，每对兄弟姐妹在结果集中有且仅有一行。

查询执行后，我们得到干净优雅的结果：

```text
+-----------+-----------+
|   first   |  second   |
+-----------+-----------+
|  Barack   |  Clinton  |
|  Abraham  |  Delano   |
|  Abraham  |  Grover   |
|  Delano   |  Grover   |
+-----------+-----------+
```

#### 多表串联：毛色相同的祖孙犬

连接操作不仅限于两张表，三张、四张乃至更多表都可以通过逗号链式串接在一起。

我们先利用自连接定义一张包含隔代关系的**祖孙表**（`grandparents`）：

```sql
CREATE TABLE grandparents AS
  SELECT a.parent AS granddog, b.child AS grandpup
  FROM parents AS a, parents AS b
  WHERE a.child = b.parent;
```

这里的关联条件是：$A$ 表中的孩子是 $B$ 表中的父母（即“我孩子的孩子”）。结果表中生成了两列：`granddog`（祖父母犬）和 `grandpup`（孙辈犬）。比如 Fillmore 是 Abraham 的父母，Abraham 是 Barack 的父母，那么 Fillmore 就是 Barack 的 granddog。

现在提出一个更具挑战性的问题：**选出所有与自己的孙辈犬毛发类型完全相同的祖父母犬。**

要回答这个问题，我们需要核对四项信息：
1. 谁是谁的祖父母？（由 `grandparents` 表提供）
2. 祖父母的毛色是什么？（需要查一次 `dogs` 表）
3. 孙辈的毛色是什么？（需要再查一次 `dogs` 表）
4. 这两种毛色是否相等？

因此，我们需要将三张表联立：一张 `grandparents`，以及两张 `dogs` 的副本（分别起别名为 $C$ 和 $D$）：

```sql
SELECT granddog
FROM grandparents, dogs AS c, dogs AS d
WHERE granddog = c.name AND grandpup = d.name AND c.fur = d.fur;
```

```text
   grandparents 表: [ granddog: Eisenhower | grandpup: Grover ]
                                │                    │
              ┌─────────────────┘                    └─────────────────┐
              ▼                                                        ▼
dogs AS c 表: [ name: 'Eisenhower', fur: 'short' ]   dogs AS d 表: [ name: 'Grover', fur: 'short' ]

验证条件:
1. granddog = c.name  --> 'Eisenhower' = 'Eisenhower' (真)
2. grandpup = d.name  --> 'Grover' = 'Grover'         (真)
3. c.fur = d.fur      --> 'short' = 'short'           (真)

结果匹配成功！
```

经过三表连接比对，整个谱系中只有两组祖孙毛色吻合：
- Eisenhower（短毛）是 Grover（短毛）的祖父。
- Fillmore（卷毛）是 Herbert（卷毛）的祖父。

最终 `SELECT granddog` 输出的就是 Eisenhower 和 Fillmore。

### 表达式进阶与数据建模边界

SQL 的表达式系统与 Python 等通用语言有很多相通之处。你可以在列描述、`WHERE` 条件、`ORDER BY` 排序子句中使用内置函数与运算符。

#### 数值计算与纬度海里测距

在 SQL 中，相等比较用单等号 `=`，不等号可以用 `!=` 或 `<>`。为什么可以用单等号判断相等？因为在数据查询的语境下根本没有“赋值”这一概念，单个 `=` 没有任何歧义。

利用数值表达式，我们可以处理有趣的现实世界度量。例如，地球纬度每相差 1 度，表面南北距离大约相差 60 海里（Nautical Miles）。假设我们有一张城市经纬度表 `cities`：

```sql
CREATE TABLE cities AS
  SELECT 38 AS latitude, 122 AS longitude, 'Berkeley' AS name UNION
  SELECT 42,            71,              'Cambridge'         UNION
  SELECT 45,            93,              'Minneapolis'       UNION
  SELECT 33,            117,             'San Diego'         UNION
  SELECT 26,            80,              'Miami'             UNION
  SELECT 90,            0,               'North Pole';
```

纬度高于 43 度的地方已经相当靠北、十分寒冷了。现在假设我身处严寒的明尼阿波利斯（Minneapolis），想要寻找避寒去处。我们可以通过表自连接，计算出明尼阿波利斯到各个其他城市的相对南北距离：

```sql
SELECT b.name, 60 * (b.latitude - a.latitude) AS distance
FROM cities AS a, cities AS b
WHERE a.name = 'Minneapolis'
ORDER BY distance;
```

这里将 `cities` 表与自身连接，$A$ 固定为始发地明尼阿波利斯，$B$ 遍历所有可能的目标城市。表达式 `60 * (b.latitude - a.latitude)` 计算出南北向距离差，负值表示该城市在明尼阿波利斯以南。

配合 `ORDER BY distance` 升序排列，排在最前面的正是负得最多的迈阿密（Miami）和圣迭戈（San Diego），而北极（North Pole）则因为纬度极高排在最后。这生动地展示了算术表达式与排序子句在过滤分析中的威力。

#### 字符串拼接与“链表反模式”告诫

在 SQL 中，字符串拼接使用的是双竖线操作符 `||`，而不是加号 `+`：

```sql
SELECT 'hello, ' || 'world';  -- 输出 'hello, world'
```

SQL 提供了一些内置的子字符串切片函数（如 `substr`），但总体而言，关系型数据库对复杂字符串深层解析的支持并不优雅。

在实际开发中，有一种非常糟糕的**反模式**（Anti-pattern）：试图用分隔符将多个数据挤在一个字符串字段里，用来模拟类似 Lisp 的链表（`car` 和 `cdr`）。

```text
千万不要这么设计表结构：
+-------+--------------------+
|  car  |        cdr         |
+-------+--------------------+
|  '1'  |     '2, 3, 4'      |  <-- 试图用带逗号的字符串表达链表剩余元素！
+-------+--------------------+
```

有人会洋洋自得地写出复杂的字符串匹配逻辑：在 `cdr` 中搜索第一个逗号的位置，切出第一段作为下一个元素……

> **易错点**：绝不要在关系型数据库中用带有分隔符的字符串去存储列表或结构化集合。这是对关系模型的背叛。如果数据具有一对多的集合属性，规范的做法是创建一张从属表，让每一项作为独立的一行，通过外键建立连接。

字符串最合理的用法之一，是用于生成自然语言或组合语法分析。例如我们有一个名词表 `nouns`：

```sql
CREATE TABLE nouns AS
  SELECT 'dog' AS word UNION
  SELECT 'cat'         UNION
  SELECT 'bird';
```

我们可以将名词表进行自连接，快速排列组合出各种句式结构（要求主语和宾语不重合）：

```sql
SELECT a.word || ' chases ' || b.word AS sentence
FROM nouns AS a, nouns AS b
WHERE a.word != b.word;
```

这条简练的声明式语句会瞬间推导并输出所有合法配对：
- `dog chases cat`
- `dog chases bird`
- `cat chases dog`
- `cat chases bird`
- `bird chases dog`
- `bird chases cat`

通过将计算过程委托给关系引擎，我们不必编写任何循环或嵌套递归，仅仅描述结构特征与限制边界，结果集便自然涌现。

#### 题目 1：2 的幂次求和还原整数值

**题干**：
已知正整数在二进制思想下都可以唯一表示为 2 的幂之和。现有一张表 `ints`，描述了如何将 1、2、4、8 组合相加得到不同的整数：

```sql
CREATE TABLE ints AS
  SELECT 'zero'  AS word, 0 AS one, 0 AS two, 0 AS four, 0 AS eight UNION
  SELECT 'one'   ,        1,        0,        0,         0          UNION
  SELECT 'two'   ,        0,        2,        0,         0          UNION
  SELECT 'three' ,        1,        2,        0,         0          UNION
  SELECT 'four'  ,        0,        0,        4,         0          UNION
  SELECT 'five'  ,        1,        0,        4,         0          UNION
  SELECT 'six'   ,        0,        2,        4,         0          UNION
  SELECT 'seven' ,        1,        2,        4,         0          UNION
  SELECT 'eight' ,        0,        0,        0,         8          UNION
  SELECT 'nine'  ,        1,        0,        0,         8;
```

请编写一条 `SELECT` 语句，投影出两列：第一列为英文单词 `word`，第二列为该单词对应的实际数值大小（列名为 `value`）。

**答案与解析**：
在 SQL 表达式中，列名会被自动求值为当前行中该列对应的具体数值。每一行中，`one`、`two`、`four`、`eight` 列要么保存了对应的权重常数，要么保存为 0。因此，直接将四个列的值相加，即可通过投影完成求值计算：

```sql
SELECT word, one + two + four + eight AS value
FROM ints;
```

#### 题目 2：筛选出本身就是 2 的幂次的单词

**题干**：
在上述 `ints` 表的结构基础之上，编写一条 `SELECT` 语句，仅筛选出那些**数值本身即为 2 的幂**的单词（即 `one`, `two`, `four`, `eight` 这四个数字本身，排除 0 以及通过多项求和构成的 3, 5, 6, 7, 9 等组合数）。

**答案与解析**：
一个正整数如果恰好是 2 的基数幂（1、2、4、8 中的一个），意味着在它对应的行中，**有且仅有一列是非零的正数，其余三列必须全为 0**。

为了利用行内算术运算检测“恰好有一个分量”，我们可以对每一列除以自身的位权基数（`one/1`, `two/2`, `four/4`, `eight/8`），从而将所有存在的非零位统统**归一化**（Normalize）为 1：
- 对于 1：四列归一化后为 `1, 0, 0, 0`，和为 1。
- 对于 2：四列归一化后为 `0, 1, 0, 0`，和为 1。
- 对于 3：四列归一化后为 `1, 1, 0, 0`，和为 2（不满足）。
- 对于 0：四列归一化后全为 0，和为 0（不满足）。

利用这一算术特征，我们在 `WHERE` 子句中检查归一化总和是否严格等于 1：

```sql
SELECT word
FROM ints
WHERE (one / 1) + (two / 2) + (four / 4) + (eight / 8) = 1;
```

执行该语句，系统将准确滤掉组合数与零，仅返回 `one`、`two`、`four`、`eight` 四行记录。

## SQL 聚合查询、数据变更与 Python 数据库交互
> 对应块：BLK25 | 覆盖分集：P35-P36 | 块标题（分集名）：《Lecture 37 Aggregation-c》

到目前为止，我们在 SQL 中写过的所有表达式都有一个共同特点：**它们一次只处理一行数据**。

无论是在 `SELECT` 的列描述里做加减乘除，还是在 `WHERE` 子句里用表达式做条件过滤，或者在 `ORDER BY` 里指定排序规则，这些表达式虽然引用了列名，但它们实际引用的只是“当前行”对应列的具体数值。比如写 `WHERE latitude > 38`，数据库在评估时，是对表里的每一行挨个检查：这一行的纬度是不是大于 38？是就留下，不是就扔掉。这种逐行评估的模式构成了单表查询的基础。

但现实中的数据分析往往不是问“哪一行的值是多少”，而是要问“这一批数据的总和是多少”、“平均值是多少”、“最高纪录是多少”。这就需要引入一组全新的工具——**聚合函数（Aggregation Functions）**，以及能够把数据分门别类进行归纳的 `GROUP BY` 与 `HAVING` 机制。此外，我们还将打破“只读查询”的局限，学习如何通过原生 SQL 以及 Python 脚本来动态创建、修改、删除数据库表，并看看多个程序同时操作同一个数据库时会发生哪些奇妙的化学反应。

### 聚合函数：从“单行计算”跃迁到“多行归约”

聚合函数会出现在 `SELECT` 的列描述表达式中。它的特殊之处在于：普通的列运算输入一行输出一行，而聚合函数输入的是**一组行**在某一列或某几个表达式上的所有取值，最终汇总计算出一个单一的值。

为了看清聚合函数的运作机理，我们需要一张专门的数据表。这里有一张包含六种动物的表 `animals`：

| kind（种类） | legs（腿数） | weight（体重/磅） |
| :--- | :--- | :--- |
| dog | 4 | 20 |
| cat | 4 | 10 |
| ferret | 4 | 10 |
| parrot | 2 | 6 |
| penguin | 2 | 10 |
| t-rex | 2 | 12000 |

这里有 4 条腿重 20 磅的狗、4 条腿重 10 磅的猫，还有一只对于雪貂来说体型相当巨大（足足 10 磅）的雪貂；鸟类里有 2 条腿、6 磅重的鹦鹉，以及 2 条腿、10 磅重的大企鹅。当时我在想：还有什么动物是 2 条腿但非常重的？你可能会想到鸵鸟，但我选了一只重约 6 吨（12000 磅）的霸王龙（T-Rex）。

#### 基础聚合操作：最大值、最小值、求和与平均

现在对这张 `animals` 表执行一个最简单的聚合查询：

```sql
SELECT max(legs) FROM animals;
```

在普通的查询中，如果输入表有 6 行，并且没有 `WHERE` 过滤，我们通常会得到 6 行结果。但运行这条语句后，控制台只输出了单一的一行：

```text
4
```

`legs` 指的是表中的特定列，而 `max(legs)` 把这 6 行数据里出现的 `legs` 全部抓出来，计算出其中的最大值 4。

除了 `max` 之外，SQL 还提供了 `min`（最小值）、`sum`（求和）、`avg`（平均值）等聚合函数。聚合函数的参数也可以是一个复合算式：

```sql
-- 计算所有动物体重的总和
SELECT sum(weight) FROM animals;
-- 输出：12056

-- 计算 (legs - weight) 的最大值，然后再加 5
SELECT max(legs - weight) + 5 FROM animals;
-- 输出：1
```

这个 `1` 是怎么算出来的？数据库逐行计算每一行的 `legs - weight`：
- dog: $4 - 20 = -16$
- cat: $4 - 10 = -6$
- ferret: $4 - 10 = -6$
- parrot: $2 - 6 = -4$
- penguin: $2 - 10 = -8$
- t-rex: $2 - 12000 = -11998$

在所有结果中，最大值是鹦鹉产生的 `-4`。最后外层的标量运算加 5，$-4 + 5 = 1$。

我们还可以在一个 `SELECT` 中并列使用多个不同的聚合函数，甚至让它们互相做运算：

```sql
SELECT max(legs), min(weight) FROM animals;
-- 输出：4 | 6

SELECT max(legs) - min(weight) FROM animals;
-- 输出：-2
```

> **注意**：
> 表中并没有任何一种动物同时满足“4 条腿”且“体重为 6 磅”。`max(legs)` 和 `min(weight)` 是彼此独立聚合出来的，它们之间不存在绑定关系。

聚合函数也可以与 `WHERE` 子句协同工作。数据库的处理顺序是：**先用 `WHERE` 过滤掉不符合条件的原始行，再对保留下来的行应用聚合计算**。

比如，我们想要找出动物的最大体重，但把那个重达 12000 磅的大家伙霸王龙排除在外：

```sql
SELECT min(legs), max(weight) FROM animals WHERE kind != 't-rex';
-- 输出：2 | 20
```

霸王龙被过滤后，剩下的两足动物里最小腿数依然是 2，而最大体重变成了狗的 20 磅。

#### 行数统计与唯一性去重：count 与 DISTINCT

如果想知道表中一共有多少行，可以使用 `count`：

```sql
SELECT count(legs) FROM animals;
-- 输出：6
```

`count` 的作用就是数出行数。数 `legs`、数 `kind` 还是数 `weight`，得到的结果都是 6。正因如此，在纯粹统计行数时，更通用的惯用语法是使用特殊形式 `count(*)`：

```sql
SELECT count(*) FROM animals;
-- 输出：6
```

但有一种情况我们必须在 `count` 的括号中指定列名，那就是结合 `DISTINCT` 关键字使用。`DISTINCT` 放在列名前面，表示在统计或聚合之前**先剔除重复值**：

```sql
-- 统计去重后的腿数种类：只有 4 和 2 两种
SELECT count(DISTINCT legs) FROM animals;
-- 输出：2

-- 统计去重后的体重数量：有 20, 10, 6, 12000 四个独特值
SELECT count(DISTINCT weight) FROM animals;
-- 输出：4

-- 对去重后的体重求和：20 + 10 + 6 + 12000（重复的 10 只算一次）
SELECT sum(DISTINCT weight) FROM animals;
-- 输出：12036
```

#### 混合聚合列与非聚合列的深坑

如果在一个 `SELECT` 语句中，同时列出了聚合函数和普通的列名，会发生什么？

```sql
SELECT max(weight), kind FROM animals;
```

这条语句会返回一行结果：

```text
12000 | t-rex
```

看起来非常完美：最大体重是 12000，对应的动物正是霸王龙。这是因为当 SQLite 在寻找 `weight` 的最大值时，它锁定了包含最大值的那一整行数据，并在输出额外的非聚合列（`kind`）时，取出了那一行的值。类似地，查询字典序最小的种类：

```sql
SELECT min(kind), legs, weight FROM animals;
-- 输出：cat | 4 | 10
```

按字母排序，`'cat'` 最小，SQLite 挑出这整行，返回了猫对应的 4 条腿和 10 磅体重。

但**千万不要依赖这种机制**。一旦逻辑稍有歧义，你得到的数据就会完全失去意义：

```sql
-- 查询拥有最大腿数的动物种类
SELECT max(legs), kind FROM animals;
-- 输出：4 | cat （在某些执行环境下可能返回 dog 或 ferret）

-- 查询平均体重以及对应的种类
SELECT avg(weight), kind FROM animals;
-- 输出：2009.33333333333 | t-rex
```

在这两个例子中：
1. 拥有 4 条腿的动物有三种（狗、猫、雪貂），它们都是最大值，数据库挑出哪一个都是合法的，返回猫只是某种内部遍历顺序的产物；
2. 计算平均体重时，2009 磅是所有动物体重的均值，没有任何一种动物的体重是 2009 磅，此时它抓出来的 `kind` 居然是 `t-rex`——霸王龙在任何维度上都跟“平均”沾不上边。

> **易错点**：
> 在包含聚合函数的查询中，如果出现了非聚合的裸列，且该列没有出现在后续要讲的 `GROUP BY` 分组键中，除了少数能够明确锁定唯一行的极值查询外，大部分情况下返回的非聚合列数据都是没有业务意义的，甚至在其他主流数据库（如 MySQL 的严格模式或 PostgreSQL）中会直接报错拒绝执行。

### 分组查询：GROUP BY 与 HAVING

默认情况下，表里所有通过 `WHERE` 过滤的行都被划分在同一个“大组”里，因此聚合函数最终只压平输出一行。

但数据分析中最强大的能力在于**分组归约**：把数据按照某种特征切成几个小组，然后分别对每个小组独立执行聚合运算。这就是 `GROUP BY` 的核心作用。

```text
原始数据表 animals
+---------+------+--------+
| kind    | legs | weight |
+---------+------+--------+
| dog     | 4    | 20     |
| cat     | 4    | 10     |
| ferret  | 4    | 10     |
| parrot  | 2    | 6      |
| penguin | 2    | 10     |
| t-rex   | 2    | 12000  |
+---------+------+--------+
             │
             │ 按 legs 拆分 (GROUP BY legs)
             ▼
┌─────────────────────────┐      ┌─────────────────────────┐
│ legs = 4 组             │      │ legs = 2 组             │
│ dog     (weight: 20)    │      │ parrot  (weight: 6)     │
│ cat     (weight: 10)    │      │ penguin (weight: 10)    │
│ ferret  (weight: 10)    │      │ t-rex   (weight: 12000) │
└─────────────────────────┘      └─────────────────────────┘
             │                                │
             │ 独立聚合 (max(weight))           │ 独立聚合 (max(weight))
             ▼                                ▼
       legs=4, max=20                   legs=2, max=12000
```
*图解：GROUP BY 将多行数据按指定键分区，聚合函数在每个分区内独立执行计算。*

#### 按单列、多列与任意表达式分组

让我们用实际查询验证上述逻辑：

```sql
SELECT legs, max(weight) FROM animals GROUP BY legs;
```

输出结果为：

```text
2 | 12000
4 | 20
```

`GROUP BY legs` 根据 `legs` 列中的唯一值，把整张表切成了两部分：`legs=2` 组和 `legs=4` 组。最终输出的行数，恰好等于分组表达式唯一值的个数。这里的 `legs` 列直接取自分组键，而 `max(weight)` 则分别在各组内部求最大值。

我们还可以统计每种腿数对应的动物数量：

```sql
SELECT legs, count(*) FROM animals GROUP BY legs;
```

```text
2 | 3
4 | 3
```

分组不仅可以按单列划分，还可以按**多个列的组合**进行更细粒度的切分：

```sql
SELECT legs, weight FROM animals GROUP BY legs, weight;
```

```text
2 | 6
2 | 10
2 | 12000
4 | 10
4 | 20
```

输入数据一共有 6 行，但输出只有 5 行。因为猫（cat）和雪貂（ferret）的腿数都是 4、体重都是 10，当按 `legs, weight` 联合分组时，它们俩被归入了同一个组。

更进一步，`GROUP BY` 后面可以跟**任意算术表达式**。比如计算每只动物“体重与腿数之比”（注意：SQLite 在两个整数相除时默认执行整数除法）：

```sql
-- 20/4=5, 10/4=2, 6/2=3, 10/2=5, 12000/2=6000
-- 分组键的唯一取值为：2, 3, 5, 6000
SELECT weight / legs, max(kind), count(*) 
FROM animals 
GROUP BY weight / legs;
```

```text
2    | ferret  | 1
3    | parrot  | 1
5    | penguin | 2
6000 | t-rex   | 1
```

在比值为 5 的这个组里，包含狗（20/4=5）和企鹅（10/2=5）两个成员，`max(kind)` 取字母序靠后者，因此输出了 `penguin`，组内计数为 2。

#### 分组过滤：HAVING 与 WHERE 的根本区别

当我们对行进行了分组后，有时并不想保留所有的组，而是希望剔除那些不满足特定条件的组。这时就要用到 `HAVING` 子句。

很多初学者容易混淆 `WHERE` 与 `HAVING`，关键区别在于**过滤发生的时机与处理的对象不同**：

> **结论**：
> - `WHERE` 作用于**分组之前**，过滤的是**单行数据**。`WHERE` 子句内部**不能**包含聚合函数；
> - `HAVING` 作用于**分组之后**，过滤的是**整个分组**。`HAVING` 子句的判断条件中**可以且经常包含聚合函数**。

看一下这个筛选重复特征分组的例子：

```sql
SELECT weight / legs, count(*) 
FROM animals 
GROUP BY weight / legs 
HAVING count(*) > 1;
```

```text
2 | 1  -- (注：如果某组只有1行则被过滤)
```

仔细拆解执行过程：
1. 每一行计算 `weight / legs`；
2. 按照计算结果分组，得到四个组：值为 2 的组、值为 3 的组、值为 5 的组、值为 6000 的组；
3. 执行 `HAVING count(*) > 1`：检查每个组的成员数量。值为 3 和值为 6000 的组只有 1 个成员，直接丢弃；值为 5 的组（狗和企鹅）有两个成员，保留；值为 2 的组在整数除法下（10/4=2，即猫和雪貂）有两个成员，保留；
4. 最终只输出满足组内行数大于 1 的分组聚合结果。

### 数据库表管理与数据变更（DDL 与 DML）

如果数据库只能查询预先存在的静态数据，那它的用处就太有限了。实际工程中，数据是不断流入、变更和清理的。

在 SQLite 规范中，建表语句 `CREATE TABLE` 包含庞大的语法体系（涉及各种约束、数据类型、排序规则等），但我们先略去那些属于专门数据库课程的高深细节，专注于最核心的两种形式：
1. `CREATE TABLE 表名 AS SELECT ...`（之前见过的从查询直接生成新表）；
2. 通过指定列名与列约束创建一张空表。

#### 创建与删除表：约束与空表的价值

创建一个空表的基本语法如下：

```sql
CREATE TABLE IF NOT EXISTS 表名 (
    列名1 类型 约束,
    列名2 类型 约束,
    ...
);
```

其中：
- `IF NOT EXISTS`：可选子句。如果表已存在，不会抛出报错，静默跳过创建；
- 列约束：常用的约束包括 `UNIQUE`（该列的值必须全局唯一，若插入重复值会引发错误）和 `DEFAULT <默认值>`（插入行时如果未指定该列的值，自动填入默认值）。

比如创建一个记录素数状态的表 `primes`：

```sql
CREATE TABLE IF NOT EXISTS primes (
    n UNIQUE, 
    prime DEFAULT 1
);
```

> **提示**：
> SQLite 内部没有独立的布尔类型（Boolean），在惯例上，通常使用整数 `1` 代表 `True`，用 `0` 代表 `False`。上面的定义意味着：默认假设插入进来的每一个数都是素数（`prime=1`），直到后续我们证明它不是。

删除一张不再需要的表使用 `DROP TABLE`：

```sql
DROP TABLE IF EXISTS primes;
```

如果不带 `IF EXISTS`，删除一个不存在的表会导致数据库抛出运行时错误。

#### 数据变更三部曲：INSERT、UPDATE 与 DELETE

空表本身没有任何数据，必须通过数据操作指令向其中写入内容。

##### 插入行：INSERT INTO
插入数据可以指定部分列，也可以提供整行的所有列：

```sql
-- 插入完整的一行（同时指定 n 和 prime）
INSERT INTO primes VALUES (2, 1);

-- 也可以显式插入多行
INSERT INTO primes VALUES (3, 1);

-- 只插入 n 列，prime 列自动使用 DEFAULT 声明的值 1
INSERT INTO primes (n) VALUES (4), (5), (6), (7);
```

此时执行 `SELECT * FROM primes;`，会看到如下内容：

```text
2 | 1
3 | 1
4 | 1
5 | 1
6 | 1
7 | 1
```

表格声称 4 和 6 也是素数，这显然不符合事实，我们等会儿来修正它。

如果想快速扩充表中的数字，`INSERT` 还可以与 `SELECT` 子句配合，把查询结果批量灌入表中：

```sql
-- 把当前表中的每个数加上 6，然后作为新行插回表中
INSERT INTO primes (n) SELECT n + 6 FROM primes;
```

执行后，原本的 2 到 7 加上 6 变成了 8 到 13，这些新数据全部被插入了表中。

##### 修改已有行：UPDATE
为了修正合数的状态，我们需要修改表中已有行的内容：

```sql
UPDATE 表名 SET 列名 = 新值表达式 WHERE 过滤条件;
```

在我们的素数表里，所有大于 2 且能被 2 整除的数都不是素数。我们可以通过取模运算 `%` 找到它们，并将 `prime` 列更新为 0：

```sql
UPDATE primes SET prime = 0 WHERE n > 2 AND n % 2 = 0;
```

运行这条语句后，4、6、8、10、12 对应行的 `prime` 字段瞬间全部变成了 `0`。同理，我们还可以继续针对 3 的倍数（`n > 3 AND n % 3 = 0`）和 5 的倍数执行类似的 `UPDATE`。这种初始批量载入、后续逐步筛查清洗的模式，在数据处理中非常典型。

##### 删除行：DELETE
当我们完成标记后，如果只想保留纯粹的素数，可以把那些合数行彻底从表中删去：

```sql
DELETE FROM primes WHERE prime = 0;
```

再次查询 `SELECT * FROM primes;`，剩下的就全是合法的素数了。

> **易错点**：
> `DELETE FROM primes;`（不带 `WHERE`）与 `DROP TABLE primes;` 截然不同。
> - `DELETE FROM 表名` 只是删除了表里的**所有行**，表的结构、列定义、约束仍然存在，它变成了一张合法的空表；
> - `DROP TABLE 表名` 会将整张表连同它的定义从数据库中彻底抹去。

### Python 与 SQLite 交互编程

在真实的工程架构中，我们很少纯手工在数据库终端里一条条敲命令，而是由程序动态生成并执行 SQL。Python 标准库自带了 `sqlite3` 模块，无需额外安装任何第三方依赖就能直接操作 SQLite 数据库。

#### 连接、游标与事务提交

看一个最基础的交互式脚本：

```python
import sqlite3

# 连接到数据库文件（如果文件不存在，会自动在磁盘创建）
db = sqlite3.connect("n.db")

# 创建一张名为 nums 的表
db.execute("CREATE TABLE IF NOT EXISTS nums (val);")

# 使用 Python 动态构造数据并通过占位符安全插入
for x in range(2, 7):
    # '?' 是占位符，数据通过第二个元组参数传入
    db.execute("INSERT INTO nums VALUES (?);", (x,))

# 必须提交事务，否则数据只存在于内存缓冲区，不会持久化写入磁盘文件
db.commit()

# 执行查询，返回游标对象（Cursor）
cursor = db.execute("SELECT * FROM nums;")

# fetchall() 将查询的所有结果拉取为一个由元组构成的列表
rows = cursor.fetchall()
print(rows)
```

运行这段代码，Python 打印出的内容是：

```text
[(2,), (3,), (4,), (5,), (6,)]
```

每一行都是一个独立的元组，元组里的元素就是该行对应的各列取值。

> **提示**：
> 注意代码中的 `db.commit()`。当你对数据库执行了 `INSERT`、`UPDATE`、`DELETE` 或 `CREATE TABLE` 等修改操作时，必须显式调用 `commit()` 提交事务。如果漏掉了这一步，程序退出后磁盘上的数据库文件可能依然是空的。

#### 为什么在 SQL 中使用占位符？

在向数据库灌入 Python 变量时，务必养成使用 `?` 占位符的习惯（如 `db.execute("INSERT INTO nums VALUES (?);", (x,))`），而不是用 Python 的字符串格式化去拼 SQL（如 `f"INSERT INTO nums VALUES ({x});"`）。

占位符机制由底层驱动负责对变量进行类型转换与特殊字符转义，这不仅能正确处理字符串中的单引号、换行符等特殊内容，更是防止**SQL 注入攻击（SQL Injection）**最基础也是最重要的防线。

### 多连接并发实战：21点游戏模拟与控制台算牌

数据库管理系统（DBMS）最迷人的特性之一在于：**它允许多个客户端程序在同一时刻连接并操作同一个数据库文件**。一个程序往表里写入数据，另一个程序可以立刻感知到并读取这些数据。

为了直观体会这种并发与数据共享的魅力，我们来看一个基于 Python 和 SQLite 构建的“21点（Blackjack）”扑克牌游戏。

#### 游戏规则与数据建模

21 点的规则非常简单：
- 目标：手中牌的点数总和尽量接近 21 点，但绝对不能超过 21 点（超过即“爆牌”判负）；
- 牌面计分：2 到 10 按票面数字计分；人头牌（J、Q、K）均计为 10 分；花色无关紧要；
- A 的特殊性：A 既可以计为 1 分，也可以计为 11 分。如果算作 11 分不会导致爆牌，就优先按 11 分计算；
- 对局流程：玩家拿两张明牌；庄家拿一张明牌和一张暗牌（扣着的牌）。玩家可以选择“要牌（Hit）”继续摸牌，或者“停牌（Stand）”。玩家停牌后，庄家翻开暗牌，如果庄家总点数小于 17，则**必须**强制继续摸牌，直到点数达到 17 至 21 之间或爆牌。

在底层，游戏并不把所有状态藏在 Python 对象的私有变量里，而是全部写入 SQLite 数据库 `cards.db` 的 `cards` 表中：

```sql
CREATE TABLE cards (
    card TEXT,      -- 牌面：'2', '3', ..., '10', 'J', 'Q', 'K', 'A'
    who TEXT        -- 当前持有者：'player', 'dealer', 或 'discard'（弃牌堆）
);
```

发牌的本质，就是执行一条插入语句并立即提交：

```sql
INSERT INTO cards VALUES ('J', 'player');
```

计算某个参与者的分数，就是用 SQL 查出他手上的所有牌，再由规则函数计分：

```sql
SELECT card FROM cards WHERE who = 'player';
```

一局结束后，清理牌桌只需将这些牌的状态批量更新为已弃牌：

```sql
UPDATE cards SET who = 'discard' WHERE who != 'discard';
```

#### 并发操控与黑客式“出千”

游戏程序启动后，Python 模拟器进入事件循环，发了牌并停在终端等待用户输入：

```text
Dealer shows: 7
Your hand total: 7 (3 and 4)
Action? (hit/stand): 
```

此时 Python 进程正在挂起等待。在现实赌场中，你只能看发牌员的脸色行事，但现在因为底层是数据库，我们可以**打开第二个终端窗口**，直接启动 SQLite 命令行连接到同一个 `cards.db` 文件！

##### 场景 1：跨进程实时观察
我们在 SQLite 终端里直接敲入：

```sql
SELECT * FROM cards WHERE who != 'discard';
```

```text
3 | player
4 | player
7 | dealer
Q | dealer
```

看！庄家那张扣着的暗牌在 Python 程序里被隐藏了，但在数据库层面它清清楚楚地躺在那里——是一张 Q！庄家当前总点数其实已经是 $7 + 10 = 17$。

我们在 Python 终端输入 `hit` 要了一张牌，拿到 J，手牌变成了 17。既然我们提前通过数据库窥探到底牌，知道庄家必然是 17 点停牌，我们果断输入 `stand` 停牌，双方战成平局。

##### 场景 2：基于 GROUP BY 的高级“算牌法”
在又玩了几局之后，弃牌堆里积攒了大量的牌。现在轮到我们决策：手牌 17 点，庄家亮出一张 6 点。此时到底该不该要牌？

在真实赌场里，职业赌徒会通过记忆所有打出的牌来“算牌”，推断牌靴里剩余大牌和小牌的比例。在数据库面前，我们甚至不需要费脑子记，直接在 SQLite 窗口用一条聚合分组查询统计打出的牌：

```sql
SELECT card, count(*) FROM cards GROUP BY card;
```

```text
10 | 1
J  | 3
Q  | 1
...
```

结果一目了然：牌靴里原本有 4 张 10、4 张 J、4 张 Q、4 张 K（总共 16 张 10 点大牌）。而聚合统计显示，目前仅仅消耗了 1 张 10、3 张 J、1 张 Q，还有整整 11 张 10 点大牌留在牌堆里！

这意味着庄家亮出的 6 点极大概率会连续抽到 10 点大牌从而爆牌。于是我们在 Python 终端果断选择 `stand`，结果正如聚合统计预测的那样，庄家摸出大牌当场爆牌，我们轻松取胜。

##### 场景 3：直接通过 SQL 修改物理现实
最后一局，我们手气极差，拿到了 4 点和 Q（总计 14 点），而庄家亮出了 9 点，我们处于绝对劣势。

在赌场里，偷换手牌是极其严重的作弊；但在由数据库支撑的虚拟世界里，数据的控制权就在我们手中。我们切到 SQLite 控制台，敲入一条修改指令：

```sql
UPDATE cards SET card = 'A' WHERE who = 'player' AND card = '4';
```

回车执行后，我们手里的 4 瞬间在物理数据库层面变成了 A！

重新切回 Python 模拟器，程序根据数据库重新计算点数：$A + Q = 21$ 点。我们直接停牌，赢下了这一局。

这生动地展示了数据库的本质：**它是一个脱离于单个程序进程生命周期之外的、共享的、持久的状态存储中心**。无论外部有多少个程序在用什么语言（Python、C++ 还是直接的人工 SQL 控制台）与之交互，只要大家连接的是同一个数据库，所有对数据的读取、聚合、修改和约束就全部在这个统一的数据空间内实时生效。

## 树形结构与递归解题思维：从祖先比较到后代聚合
> 对应块：BLK26 | 覆盖分集：P37 | 块标题（分集名）：《Lecture 39 Final Example》

在这门课中，我们已经多次与树打交道了。

回顾一下我们最初处理树形结构的方式：可以用纯函数式的数据抽象，也就是通过列表以及配对的构造器和选择器来实现，再配合一个辅助函数 `is_leaf` 来判断某个节点是否是叶子；到了课程后半部分，我们引入了面向对象编程，用一个类（Class）来表示树。在类的体系下，我们用实例属性来记录树的核心部件——标签（`label`）与分支（`branches`）。这时我们不再需要选择器，直接访问属性名即可；而原先独立的辅助函数则蜕变成了类中的方法，只需检查 `self.branches` 是否为空就能判断它是不是叶子。毕竟，叶子节点的本质就是没有分支的树。

但 Python 本身并没有内置任何名为 `Tree` 的基础数据类型。为什么？因为计算机科学中的“树”是一个高度抽象的概念，它泛化了一切具有树形层级特征的事物。

### 为什么树在计算机科学中无处不在

树最本质的特征只有一条：**一棵树可以包含其他树，而且往往包含不止一棵树**。这种嵌套与分支的自相似性，构成了自然界与数字世界中层次结构的基础。

#### 嵌套与分层：自然界与软件中的树

只要数据中存在层次结构，树就会自然浮现：

*   **嵌套列表**：一个列表中可以包含其他列表，被包含的列表内部又嵌套着列表。这就是最朴素的树结构。
*   **程序语法与表达式**：在 Python 或 Scheme 中，一个调用表达式是由操作符与操作数表达式构成的，而这些操作数子表达式本身往往又是嵌套的调用表达式。它们在解释器内部就是以表达式树的形式存在的。
*   **自然语言分析**：在英语语法分析中，一个完整的句子（Sentence）可以拆解为一个名词短语（Noun Phrase）、一个动词短语（Verb Phrase）和一个标点符号；名词短语与动词短语又可以逐层细化拆解成更小的短语和词汇。
*   **网页布局（HTML）**：现代网页通过超文本标记语言构建，外层是一个描述无序列表的标签（`<ul>`），内部嵌套着描述列表项的标签（`<li>`），列表项内部又可能嵌套着指示加粗的文本标签（`<b>`）。

树在计算机科学中无处不在。而操纵这种层次结构最自然、最有力的武器，正是**递归**。从本质上说，我们深入学习递归机制的核心目的之一，就是为了能够优雅地处理树形结构数据。

```text
       树结构（自相似嵌套）
              [ 根节点 ]
             /    |    \
      [ 子树A ] [ 子树B ] [ 子树C ]
        /   \              /   \
     叶节点 叶节点       叶节点 叶节点
```

> **结论**：对树的处理，天然对应着对各子树的递归调用。理解树递归的关键，在于把控树遍历过程中信息“向下传递”与“向上聚合”的数据流向。

### 攻克未知问题：以标签与祖先比较为例

面对一个复杂的树形处理问题，如果你读完题后无法立即看出解法，这再正常不过了。无论是在考场上，还是在未来构建独立的软件项目时，多数非平庸的问题都不会一眼展现答案。关键在于，你必须建立一套行之有效的问题拆解流程，帮助自己在面对空白屏幕时摆脱困境，步步逼近正确答案。

我们来看这样一个具体的问题：

> **实现目标**：编写函数 `bigs(t)`，它接受一个包含整数标签的树实例 $t$。该函数需要返回 $t$ 中所有**标签大于其所有祖先节点标签**的节点数量。

遇到这种题目，哪怕题目附带了填空模板，我也强烈建议你：**先不要碰代码，甚至不要去看模板给出的代码提示**。我们要从问题的本质出发，先通过具体的推演建立对题意的精确感知。

#### 理解问题与用例追踪

题目第一句话说明了输入是一棵带有整数标签的树。核心难点在第二句：“返回所有标签大于其祖先节点标签的节点数量”。

什么是祖先（Ancestor）？在树中，某个位置就是一个节点，每个节点同时也是以它为根的子树。一个节点的祖先，就是它的父节点、父节点的父节点，乃至一直向上回溯到根节点的所有前驱。

口头说很抽象，我们必须借助具体的树结构进行推演。如果在草稿纸或试卷上没有图，**第一件事永远是亲手画一棵树**：

```text
            1
          /   \
         4     3
        / \   /
       4   5 0
            /
           2
```

我们知道最终统计出的答案是 4，但单看数字毫无意义，我们需要找出究竟是哪 4 个节点满足条件。让我们从根节点开始逐一检验：

1.  **节点 1（根节点）**：它有祖先节点吗？没有。因此“它的标签大于其所有祖先”这一命题在逻辑上空真（Vacuously True）成立。根节点算一个。
2.  **节点 4（左子节点）**：它的祖先只有根节点 1。$4 > 1$，满足条件，算一个。
3.  **节点 4（左子节点的左孩子）**：它的祖先是 4 和 1。它并不大于父节点 4，因此不符合条件，不算。
4.  **节点 5（左子节点的右孩子）**：它的祖先是 4 和 1。$5 > 4$ 且 $5 > 1$，满足条件，算一个。
5.  **节点 3（右子节点）**：它的祖先只有 1。$3 > 1$，满足条件，算一个。
6.  **节点 0（节点 3 的左孩子）**：它的祖先是 3 和 1。0 不大于 3，不算。
7.  **节点 2（节点 0 的左孩子）**：它的祖先是 0、3 和 1。虽然 $2 > 0$（大于其直接父节点），但它**不大于祖先节点 3**！因此它不是我们要找的节点。

> **易错点**：千万不能只将当前节点与它的“直接父节点”比较。定义要求的是大于“所有祖先”，这意味着只要祖先链条中存在任意一个大值，该节点就失去资格。

经过这一轮推导，我们确认了符合条件的 4 个节点分别是 `1`、`4`、`5`、`3`。这也揭示了一条关键性质：**根节点永远被计入，因为它是没有祖先的。**

#### 方案碰撞：从经典遍历受挫到状态传递

明确了规则后，我们开始思考实现结构。

通常我们处理树的经典模式是：判断当前节点是否是叶子；若是叶子则返回某个值；若不是叶子，则对所有分支进行递归调用，最后将分支的结果聚合起来返回。

```text
标准自底向上模式（在当前问题中会失效）：
叶子节点向上汇报警报 ──> 缺少祖先上下文，叶子无法自决是否符合条件！
```

如果我们直接套用这种结构，很快就会撞墙：当你递归深入到叶子节点（比如节点 2）时，该节点仅仅持有着自己的标签（2），它根本不知道自己头顶上的祖先曾经出现过 3 和 1。由于缺乏祖先历史信息，叶节点无法判断自己该不该被计入。

意识到经典结构行不通，就要果断放弃并记录下关键缺失：**我们需要一种机制，在向下遍历的过程中把祖先信息传递下去**。

具体而言，要判断一个节点是否大于它的所有祖先，我们并不需要把所有祖先的标签保存成一个长长的列表依次比较；**我们只需要知道当前节点之前出现过的“最大祖先标签”是多少**。只要当前节点的标签大于历史最大祖先，它就必然大于所有祖先。

#### 模式一：自底向上的递归聚合

引入一个接收额外状态的辅助函数，是打破这类信息不对称的经典范式。外层函数 `bigs` 接收单个参数树 `t`，而内部辅助函数 `f` 则需要接收两个参数：
*   `a`：当前正在考察的子树；
*   `x`：从整棵树的根到达当前节点之前，沿途所见过的**最大祖先标签**。

```python
def bigs(t):
    """返回 t 中标签大于其所有祖先标签的节点数量。"""
    def f(a, x):
        count = 1 if a.label > x else 0
        new_x = a.label if a.label > x else x
        return count + sum([f(b, new_x) for b in a.branches])

    return f(t, t.label - 1)
```

我们来逐行解析其中的逻辑链条与参数传递：

1.  **比较与计数**：当我们在子树 `a` 处时，只需比对 `a.label > x`。若大于，说明当前节点符合条件，为总计数贡献 `1`；否则贡献 `0`。
2.  **维护向下传递的最大值**：如果 `a.label > x` 成立，意味着深入到 `a` 的子分支时，见过的最大祖先已经更新为了 `a.label`；反之，若 `a.label <= x`，深入子分支时沿途的最大祖先依然是原先的 `x`。
3.  **分支递归与聚合**：对于 `a` 下面的每一个子分支 `b`，我们递归调用 `f(b, new_x)`。由于我们是在统计节点总数，所以将各分支返回的结果用 `sum(...)` 求和，再累加当前节点贡献的 `1` 或 `0`。如果到达了叶节点，其 `a.branches` 为空列表，列表推导式为空，`sum([])` 自然返回 `0`，基线条件无需额外手写 `if a.is_leaf()` 也能完美自洽。
4.  **根节点的初始参数设计**：我们在启动对根节点 `t` 的调用 `f(t, ...)` 时，传给它的初始最大祖先应该是什么？因为根节点必然要被计入（它没有祖先），所以我们传入的值只要严格小于 `t.label` 即可，最稳妥的做法就是直接传入 `t.label - 1`。

> **提示**：手动追踪（Trace）代码的执行流程是验证逻辑的核心手段。想象一下在节点 1 处调用 `f(t, 0)`，得到 $1 + \dots$；接着向下遍历到 4，最大祖先更新为 4；再向下到 5，得到 $1$；回溯到右子树 3，以 1 为最大祖先向下……在草稿纸上模拟环境图的这一推演过程，能让你对递归树的调用展开有绝对确信的掌控。

#### 模式二：可变状态的自顶向下累加

在树递归中，累积最终计数除了“每个子调用返回局部的和，再在父级用加法聚合”之外，还有第二种常见思路：**在外部维护一个可变容器（如单元素列表），递归过程纯粹用于自顶向下遍历树并就地更新该容器**。

很多考试或工程模板会强制采用这种架构。假设模板要求我们初始化一个包含数字 0 的列表 `n = [0]`，最后返回 `n[0]`：

```python
def bigs_alt(t):
    """通过可变状态追踪实现 bigs。"""
    n = [0]
    def f(a, x):
        if a.label > x:
            n[0] += 1
        for b in a.branches:
            f(b, max(x, a.label))

    f(t, t.label - 1)
    return n[0]
```

这两种解法背后的思维差异值得深思：

| 维度 | 模式一：递归返回值聚合 | 模式二：可变状态遍历更新 |
| :--- | :--- | :--- |
| **数据流转方向** | 自底向上：子节点返回值向父节点汇聚 | 自顶向下：递归函数只管向下推进，结果留在全局/闭包中 |
| **函数职责** | `f` 拥有纯函数特征，返回值代表子树内部统计值 | `f` 依靠副作用（Side Effect），通过修改外部列表累积计数 |
| **分支汇总机制** | 使用 `sum([...])` 将列表推导式的结果相加 | 使用 `for` 循环顺序遍历分支，不关心递归调用的返回值 |

在模式二中，`max(x, a.label)` 极其洗练地表达了向下传递的状态演化：无论当前节点是否被计入，深入到分支 `b` 时，新的最大祖先要么是沿袭旧的 `x`，要么被提升为当前的 `a.label`。

### 系统化函数设计的六个步骤

计算机科学的教学路径有很多种，有的着重于底层语言特性，有的侧重特定框架应用。然而，最核心的技术竞争力永远是**有条理地分析并解决未知问题的工程能力**。

优秀的设计方法学将一个函数的诞生系统化地拆解为六个阶段。当你面对一道毫无头绪的难题时，可以强迫自己依照这六个步骤推进：

```text
    六步系统设计法
[1. 数据定义] ──> [2. 文档与存根] ──> [3. 示例先行]
                                            │
[6. 全面测试] <── [5. 填补实现] <── [4. 骨架模板]
```

1.  **设置数据定义（Data Definition）**：搞清楚要处理的信息到底是什么，以及在程序中用什么数据结构来表达（例如用类、字典、嵌套列表还是元组）。
2.  **编写函数文档与存根（Signature, Purpose Statement, Stub）**：
    *   明确函数签名（Signature）：定义域（输入类型）与值域（输出类型）分别是什么；
    *   目的陈述：用一两句极其简明的话概括函数要达成的目标；
    *   函数存根（Stub）：先写出 `def` 头部，给参数起好有意义的名字。
3.  **编写函数示例（Examples）**：在动笔写任何内部实现之前，先构造出一两个包含边界情况的具体输入，并手动算出预期的输出。
4.  **构建函数模板（Template）**：根据数据结构的特征（例如树的遍历），写出控制结构的大致轮廓——是一个 `if-else` 分流？还是遍历 `a.branches` 的循环？记录下实现中必须调用的核心操作或辅助函数。
5.  **填补函数定义（Definition）**：利用第三步推演出的示例和第二步明确的目标，把模板中的空格填满。
6.  **针对性测试（Tests）**：把第三步手算的示例作为单元测试运行，验证实际执行结果与预期是否吻合。

这套方法的核心思想是**示例驱动（Example-driven）**：绝对不要试图凭空用意志力憋出一段通用的代码，而是永远通过具体的数据实例来指导状态传递与逻辑分支的构建。

### 实战演练：筛选小于所有后代的非叶节点

我们现在把这套六步设计法，原汁原味地应用到另一个更具挑战性的树问题中。

> **实现目标**：编写函数 `smalls(t)`，它接受一个包含整数标签的树实例 $t$。该函数需要返回一个包含 $t$ 中所有**标签小于其所有后代节点（Descendants）标签的非叶子节点**的集合/列表。

#### 规格剖析与示例逆推

我们先严格执行前三步：

*   **数据定义与签名**：输入是一个树实例 $t$；输出应该是什么？文档表明返回值是一个包含树实例的可迭代对象（列表），而且要求筛选出来的都是**非叶子节点**（即 `not b.is_leaf()` 的节点）。
*   **示例推演**：画出一棵具备代表性的树：

```text
            1
          /   \
         2     3
        / \   /
       4   5 0
            /
           6
```

我们来逐个审查每一个非叶子节点，看它的标签是否严格小于其“所有后代节点”：

*   **节点 1**：它的后代包括 2, 4, 5, 3, 0, 6。其中存在一个后代标签为 0。因为 $1 > 0$，所以节点 1 不符合要求。
*   **节点 2**：它不是叶节点。它的后代有 4 和 5。由于 $2 < 4$ 且 $2 < 5$，节点 2 符合要求！
*   **节点 4、5、6**：直接排除，因为题目显式要求只寻找**非叶子节点**。
*   **节点 3**：它的后代有 0 和 6。$3 > 0$，不符合要求。
*   **节点 0**：它不是叶节点（它有孩子 6）。它的后代只有 6。$0 < 6$，节点 0 符合要求！

因此，对于这棵树，`smalls` 应当返回的子树列表包含两个树对象：以 2 为根的子树，以及以 0 为根的子树。

> **提示**：观察节点 1 与节点 3 的失效原因可知：判断一个节点是否小于所有后代，我们不需要逐一遍历所有后代并一一比对；**只要当前节点的标签小于其所有后代节点中的最小值，它就必然小于所有后代**。

#### 双重职责的辅助函数设计

要获得某个节点所有后代的最小值，必须自底向上地汇总子树中的数据。这正好与 `smalls` 收集目标节点列表的需求交织在一起。

我们可以设计一个内部辅助函数 `process(t)`。为了完成整个任务，这个函数需要同时承担双重职责：
1.  **返回值**：计算并返回以当前节点 `t` 为根的**整棵子树中的最小标签**（包括根标签及其所有后代标签）；
2.  **副作用**：在自底向上返回最小值的过程中，如果发现当前节点是非叶节点且小于其所有后代的最小值，就顺手将当前子树 `t` 追加到一个累积列表 `result` 中。

```python
def smalls(t):
    """返回 t 中所有标签小于其所有后代标签的非叶子节点列表。"""
    result = []

    def process(t):
        if t.is_leaf():
            return t.label
        
        # 递归计算所有分支内部的最小标签，并取得后代中的全局最小值
        min_descendant = min([process(b) for b in t.branches])
        
        # 如果当前根标签小于其所有后代的最小值，则它必定小于所有后代
        if t.label < min_descendant:
            result.append(t)
            
        # 返回以当前节点为根的整棵树的最小值（包含根自身与所有后代）
        return min(t.label, min_descendant)

    process(t)
    return result
```

我们来剖析 `process` 函数的精密运作机理：

1.  **基线条件（叶节点）**：
    如果 `t.is_leaf()`，它没有任何后代，也不可能属于“非叶子节点”，因此绝对不加入 `result`。此时以它为根的子树的最小值就是它自己的标签，直接 `return t.label`。
2.  **递归深入与分支汇聚**：
    对于非叶节点，我们对它的每一个子分支 `b` 调用 `process(b)`。这个调用不仅会递归地去把下层符合条件的节点追加到 `result` 中，还会向上传递该分支内部的最小值。通过 `min([process(b) for b in t.branches])`，我们一举拿到了当前节点的所有后代中的最小标签 `min_descendant`。
3.  **当前节点的资格裁决**：
    比较 `t.label < min_descendant`。如果满足，说明它比所有子孙都小，且它是非叶节点，因此放心地将 `t` 加入 `result`。
4.  **向上层继续汇报**：
    最后一行非常关键——该子树向上级父节点汇报时，能保证代表整棵子树最小值的数字是 `min(t.label, min_descendant)`。

这样一来，通过一次后序遍历（Post-order Traversal），整棵树的每个节点被访问且仅被访问一次，后代极值汇总与目标节点筛选在单次递归回溯中全部顺畅完成。

#### 题目一：统计大于所有祖先标签的节点数（`bigs`）

**题干**：
实现函数 `bigs(t)`，输入为一个 `Tree` 类的实例 $t$（节点标签为整数）。如果一个节点的标签严格大于从根节点到该节点路径上的所有祖先节点的标签，则称该节点满足条件（根节点无祖先，默认满足条件）。函数应返回整棵树中满足条件的节点总数。

**解析依据**：
正文在“理解问题与用例追踪”中明确指出，若节点无祖先（根节点），属性空真成立；对于其余节点，等价于该节点的标签严格大于路径上见过的最大祖先标签。在递归过程中，我们需要一个额外的参数 $x$ 来记录当前分支上方的最大祖先值。

**参考答案**：
```python
def bigs(t):
    def f(a, x):
        count = 1 if a.label > x else 0
        new_x = a.label if a.label > x else x
        return count + sum([f(b, new_x) for b in a.branches])

    return f(t, t.label - 1)
```

#### 题目二：收集小于所有后代标签的非叶子节点（`smalls`）

**题干**：
实现函数 `smalls(t)`，输入为一个 `Tree` 类的实例 $t$（节点标签为整数）。函数需要返回一个列表，包含 $t$ 中所有满足“其标签严格小于其所有后代节点标签”的**非叶子节点**（作为树实例本身存入列表）。

**解析依据**：
正文在“双重职责的辅助函数设计”中指出，叶节点不符合非叶条件，但需要向上提供自身的标签作为极值比对基准；非叶节点满足条件的充要条件是：当前节点的标签严格小于其所有子分支返回的最小值中的最小值（即所有后代的极小值）。通过辅助函数在回溯时返回子树最小值，并在满足条件时将子树追加到列表中。

**参考答案**：
```python
def smalls(t):
    result = []
    def process(t):
        if t.is_leaf():
            return t.label
        min_descendant = min([process(b) for b in t.branches])
        if t.label < min_descendant:
            result.append(t)
        return min(t.label, min_descendant)
    process(t)
    return result
```
