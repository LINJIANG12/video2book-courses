尾递归

函数式编程就是这样一种理念，你可以根据纯函数组织整个程序。这些函数是模块化的，可以以有趣的方式组合，并且还具有其他优势。

函数式编程是一个非常广泛的术语，但通常指的是以下属性：所有函数都是纯函数，它们没有副作用，没有重新赋值，没有可变数据类型。当你创建了某样东西，它就在那里永远存在；你创建的名称，值绑定也是永久的。当你拥有这些东西时，你就会获得一些优势。

首先，表达式的值与子表达式评估的顺序无关。我们可以随意选择一个特定的顺序，在 Python 中我们就是这样做的。但如果根据情况，我们可以任意选择任何顺序，不是更好吗？特别是，如果我们有多个不同的处理单元，我们甚至可以并行评估子表达式，或者在真正需要子表达式的值之前等待并查看是否真的需要评估它。

这些东西是引用透明性的产物。这个观点是，当你用其子表达式的值替换表达式的一个子表达式时，表达式的值不会改变。这使得你可以进行记忆化等操作，而无需担心改变程序的行为。

所以，这些都是好事情。因此，函数式编程在这个时代特别受欢迎，尤其是在计算机拥有越来越多的处理单元的情况下。自动并行化工作岂不是很好？

但是，有人可能会想，如果没有 for 和 while 语句，因为我们不允许将名称重新绑定到新值，我们真的能够使基本的迭代过程高效吗？还是我们只能使用递归，而递归很慢，所以这些语言永远不可能快？

事实证明这个问题是有答案的。通过使用我们今天要讨论的尾递归的想法，你可以使一种函数式编程语言与非函数式的效率一样高。

让我们看一个例子。在 Python 中，递归与迭代相比。在 Python 中，递归调用总是创建新的活动帧。让我们看看这意味着什么。假设我们正在编写一个计算 $k$ 倍 $n$ 阶乘的函数 `factorial(n, k)`：

这是一个递归定义：如果 $n$ 为 0，我们直接返回 $k$，因为 0 的阶乘是 1；否则我们返回一个递归调用，其中 $n$ 被递减，并且也乘以常数，这样在达到 $n$ 为 0 时，我们已经累积了阶乘的所有不同项。

这是一个迭代定义：`factorial(n, k)`，当 $n$ 大于 0 时，重新绑定 $n$ 和 $k$ 到 $n - 1$ 和 $k \times n$，然后返回 $k$。在这两种情况下应用相同的逻辑，但存在一些差异。

时间上的差异仅限于一个常数因子。这是一个线性时间递归，但线性时间递归需要线性空间。迭代版本也需要线性时间，你必须通过这个 while 语句的主体多次，每次为一个 $n$，然后每次它都会递减。但我们只需要恒定的空间，因为我们只需要记住恒定数量的名称：`n`、`factorial`、`k`，不管 $n$ 有多大。

那么我们如何弥合递归意义上阶乘所需的空间与迭代的空间之间的差距呢？这就是我们今天讨论的整个思路。

如果你读一下 Scheme 语言的规范，它说：Scheme 的实现必须是正确的尾递归。这允许在常量空间中执行迭代计算，即使迭代计算由语法递归过程描述。

记住，我们在 Python 中有我们的迭代版本，它花费线性时间，但占用常量空间。思路是，如果你将相同的逻辑写成 Scheme 过程，这说的是计算 $k$ 次 $n$ 的阶乘的方法是检查并看 $n$ 是否为 0，然后返回 $k$，否则进行递归调用。而这应该使用资源如下。

但我们如何做到呢？答案是：我们淘汰中间人。在进行递归调用时，我们会淘汰不再需要的帧。让我向你展示这些帧是哪些。

我们回到了 Python，我们看一下阶乘的递归定义。当我们逐步进行时，我们看到每次调用阶乘都会创建一个新的帧：这里 $n$ 绑定到 4，这里 $n$ 绑定到 3，$n$ 绑定到 2。很快我们将把 $n$ 绑定到 1 和 $n$ 绑定到 0，这是最终状态。

现在，会返回什么呢？这将返回 240。我们看到了，但请注意，每一个这些其他调用也只会返回上一个的结果：240、240、240，我们就完成了。现在，没有必要保留这个 $n$ 和这个 $k$。为了弄清楚，我们只是要返回我们从下一次调用中得到的任何东西。因此，这些额外的时间帧在短暂地弄清楚如何进行递归调用后就再也不需要了。

我们仍然保留它们，因为这是 Python 的工作方式，但是一个正确的尾递归语言不会这样做。

这里的基本思想是，使这些递归过程高效的关键是有些调用是尾调用，而有些不是。这是一个区分，它判断当一个过程调用另一个过程时，当被调用的过程完成时，是否还有更多的工作要做。如果除了返回调用表达式的值之外没有其他事情要做，那么那就是一个尾调用。

尾调用有点长的定义。那么，让我们来详细了解一下。尚未返回的过程调用是活动的，这意味着我们迟早会从中返回一些东西。一些过程调用是尾调用。一个方案解释器应该支持无限数量的尾调用，这意味着我们可以有尽可能多的尾调用，而只使用恒定的空间。它将通过跳过在 Python 环境图中显示的所有额外帧来实现这一点。

那什么是尾调用？尾调用是尾上下文中的调用表达式。

什么是尾上下文？有几种情况：
一种是 `lambda` 表达式中的最后一个主体子表达式。原来，一个 `lambda` 表达式可以有多个不同的主体表达式，最后一个是确定返回值的那个。所以，该表达式处于尾部上下文中，也就是说，它是这个过程在返回之前要做的最后一件事的描述。

此外，你还可以在尾部上下文中将尾调用作为 `if` 表达式的子表达式 2 或 3。因此，请记住，`if` 表达式有三个子表达式，分别是谓词、结果和替代项。如果整个 `if` 表达式处于尾部上下文中，那么结果和替代项也是尾部上下文。

那么让我们看一下这个阶乘的定义。阶乘定义中的最后一个主体子表达式是整个表达式，它是一个 `if` 表达式。这个 `if` 表达式处于尾部上下文中，这意味着它的子表达式 2 和 3 也处于尾部上下文中。这里是 $k$，然后是对阶乘的调用。这就是一个尾部上下文，而这是一个尾部上下文中的调用表达式，因此它是一个尾调用。这是一种应该只需要恒定空间的情况，无论我们调用多少次。

这想法是，一旦你计算出 $n - 1$ 和 $k \times n$ 的阶乘，你已经完成了计算 $n$、$k$ 阶乘所需的所有工作，你只需要将其返回即可。一旦完成了所有这些工作，$n$ 和 $k$ 的具体值就不再重要了。

现在，还有其他尾部上下文。在尾部上下文 `cond` 中所有非谓词子表达式，你将在项目中了解到；在尾部上下文 `and` 或 `or` 中的最后一个子表达式；以及在尾部上下文 `begin` 中的最后一个子表达式。这些并不是特别重要，除非你真的坐下来编写一个 Scheme 程序。你需要知道尾部上下文是什么，这样你才能知道程序的时间效率或空间使用情况。

因此，人们花费了很多时间确保他们在可能的情况下将所有递归调用和尾部上下文放在一起，以确保整个程序不占用太多空间。但是今天我们只关注这前两种情况：在 `lambda` 表达式中的最后一个子表达式，或者在尾部上下文中的子表达式 2 和 3。我们已经看到了这两个例子。

## P31 Lecture 33 Programs as Data-cn

程序就是数据。

Scheme 程序由表达式组成。这些表达式可以是原始表达式，比如数字 2、3.3、`true`、符号 `+`、符号 `quotient`。但其他所有的都是组合，每个组合都是一个 Scheme 列表。

这里我们有一个包含符号 `quotient`、数字 10 和数字 2 的列表。这里我们有符号 `not` 和原始值 `true`。

我们之前讨论过的内置 Scheme 列表数据结构，它以 `car` 和 `cdr` 的形式表示为链表，但它可以用来表示 Scheme 程序中的组合。

如果我评估以下表达式：构建一个商数列表，然后是 10，然后是 2。我得到的是一个小片段的 Scheme 程序，一个组合，它说取 10 和 2 的商数。

现在请注意，评估这个实际上并没有将 10 除以 2；相反，它只是构建一个列表。但有一个内置的过程叫做 `eval`。`eval` 接受任何表示为 Scheme 列表或原始的表达式，并返回其值。

`eval` 商数 10 和 2 会给你数字 5。

这里的教训是，如果我想写一个生成 Scheme 代码的程序，我只需构建列表。如果在任何时候我已经构建了代码，并且想知道在评估它时会发生什么，那么我只需调用 `eval`。

Python 还内置了一个 `eval` 函数，它接受一个字符串并告诉你其值。Scheme 的特殊之处在于，它具有用于处理 Scheme 列表的所有内置功能，而所有代码都只是列表。通过编写诸如 `(list 'quotient 10 2)` 之类的东西，构建程序更容易。

关于 Scheme 语言的一项美妙之处，这也适用于 Lisp 总体而言，编写一个编写程序的过程非常简单。

但这不是 Scheme 代码。Scheme 代码看起来像这样：我在加号这里加引号的原因是说我并不想求值这个加法，我想把它留作一个符号。只要我要求 Scheme 评估整个组合，那个符号就会被评估。因为这在操作元位置，所以它被评估为加法过程，然后我们将其应用于 1 和 2。
