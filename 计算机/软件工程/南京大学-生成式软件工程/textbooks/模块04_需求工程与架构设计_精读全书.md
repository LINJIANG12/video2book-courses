## 软件为什么一点都不软：需求工程与架构设计入门
> 对应块：BLK11 | 覆盖分集：P07上 | 块标题（分集名）：《需求工程与架构设计入门》

上一节课我们讲软件工程的来龙去脉：软件危机出现以后，大家发现原来的开发方式已经撑不住了，需要一套工程化的方法来解决问题。我们也看了 Royce 那篇老 paper。他描述了一条看起来很顺的路径：先有一个 intent，再走向 specification，最后走向 implementation，最后产出软件。

但软件的生命周期没有在 implementation 结束。代码交付以后，还要继续维护。你今天做出的一个决定，可能在半年后、两年后仍然会影响系统；它可能决定了以后改需求要付出多少代价。需求、设计、模块、函数、代码、测试，表面上看起来是从上到下排列的，实际上它们之间还有直接和间接的 data dependency，形成了一张错综复杂的网络。

```text
intent
  │
  ▼
specification ─────► design ─────► implementation
       │                 │                │
       └─────────────────┴────────────────┘
             直接与间接的依赖网络
```

这就是软件工程的起点。如果后面发现某个东西错了，这个错误会沿着依赖关系反推回前面。需求错了，设计可能不合理；设计不合理，实现就达不到预期；实现达不到预期，后面的测试和交付物又会大面积失效。于是你可能要重做，而且会带来大量成本。

所以软件工程研究的不只是“代码怎么写”。它研究的是在需求分析、系统设计、系统实现等各个阶段，应该采用什么方法。人和人之间如何对齐，产品经理怎么管理团队，写代码时怎么写测试，能不能做自动化测试和自动化分析，这些都在软件工程的范围内。

为什么要有 traceability（可追踪性）？因为人和人很难对齐。如果只留下代码，甚至出了问题都不知道该追溯到过去的哪一个决定。理想情况下，每一个测试用例、每一段代码，都应该能追溯到过去做过的设计。这样才能知道系统里到底发生过什么，改动会影响谁，改设计会影响哪些测试用例。

如果只有自然语言，往往还是不够。结构化、有语义的语言能够更好地表达这种关系。UML 试图对齐全世界软件工程实践，就是这个方向的一种尝试。结构化不是为了让文档看起来更漂亮，而是为了让需求、设计、实现和测试之间能够保持可追踪的关系。

### 软件为什么一点都不软

说到“软”，我们很容易想到椅背：你按下去，它瘪下去；你松手，它又弹回来；下次坐，它还是好的。软件却不是这样。它是一个纯粹的逻辑制品，里面容不下任何细微的差错。

你可以想象一个程序：输入一个整数 `N`，输入 `N=1` 后，程序循环从数组中读取元素。接着，假设这个软件运行在卫星上，有一颗宇宙射线击中了内存，把一个 unsigned integer 的最高位翻转了。原本的 `1` 突然变成一个巨大无比的值，程序就会彻底 collapse，继续无限制地从输入中读取数据；也可能继续等，最后在读了一千个数字以后才出现 memory error。

当然，这是一个极端例子。现实中的数据中心也会观察到类似问题。处理器制程越来越先进，热噪声会影响某些指令；有些指令密度特别大，在一台机器上执行和另一台机器上执行，结果可能不一样，甚至要运行一段时间后才会出现 silent error。这样的缺陷有时候在制造时就埋下了，只是一直没有被触发。

> **易错点**：软件不是“软”的材料。它看起来由代码组成，但代码有形式语义；一个 bit 的变化，可能就足以让整个逻辑制品失效。

软件同时又承载着人的智慧和客户的需求。我们今天写一个 Java 系统，既要把逻辑设计出来，也要防止它最后堆积成屎山。于是，软件工程是一门关乎整个软件生命周期的学科。

但我们一开始往往只能从最底层开始学：先学 C 语言，再在这个基础上不断产生新的知识。因为如果你不理解代码是什么，没有写过代码，也没有体会过开发软件时的痛苦，就不可能真正做好一个产品经理。你不能只是在脑子里想“这个事情应该可以办到”“花多少成本可能可以办到”，却没有一手的经验。知道世界是怎么失败的，新的语言为什么被创造出来，为什么要有它，才能一点点往上走。

### AI 把实现变便宜以后，什么反而更重要了

在 AI 时代，一个目标明确的代码已经变得非常便宜。现在让 AI 生成代码，只要把边界划定清楚，我甚至可以不看它的实现细节。昨天生成的代码，时间和规模已经超出我能够逐行理解的范畴，但从结果上看它是对的。只要边界划得清楚，并且我知道怎样做好 validation，我就可以把 agent 展开，让它帮助实现软件，而且仍然有一定的质量保证。

这件事反过来把软件系统的压力推到了别的地方：方向、边界、验证和架构。

我们前面讲版本管理，是因为软件总是从一个空项目开始。先把“从空项目怎么往后走”讲清楚，下一步才是把控软件执行的方向。软件到底往东南西北哪个方向开，一开始的方向选择，影响是非常大的。

但是，现有的需求和产品设计很难做出两个真正好的研究。现实里，很多需求只能告诉你“今年只能这样”，或者把一堆模糊的功能名称塞给你。于是很多人会本能地想：我先做一个 minimum viable product，也就是 MVP，先把最重要的功能做出来。

MVP 没有问题。它可以让我们快速找到一个从 intent 到 specification、再到 implementation 的切片，然后在这个切片上走完一条完整的软件流程。但这个版本肯定不完备。做 MVP 时，一定要先选最重要的功能，不要一开始就纠结按钮长什么样、界面样式应该怎么设计。因为如果上面的设计发生变化，按钮样式很可能很快就会不可用。

> **结论**：做 MVP 的时候，不要研究一个你过一会儿就会扔掉的东西。选对最重要的功能，先得到一个可以运行的版本。

今天的 AI 不会自动从需求、产品设计和架构的角度替你思考，除非你明确用 prompt 告诉它。甚至只是多写几个字，也会得到完全不同的 MVP。

比如，同一个“做一个 coding agent”的需求，你要求它使用 client-server 架构，它可能会先设计数据存储，选择一个数据库；你要求它做成命令行的程序，它可能采用另一种组织方式。功能看起来可能差不多，都是实现了你想要的那个 agent，但生成出来的代码、文件和上下文会完全不同。

一旦某个文件写下来了，它就会进入 agent 的上下文。后面继续做下一个需求时，之前的全部历史都会跟着带过来。你在软件工程里已经给这件事起了名字：technical debt，技术债。

你在做任何决定的时候，都背上了这个债务。决定来自需求：你要的是功能代理，还是要一个帮助你学习的工具，或者是一个帮助读研究论文的工具？不同需求下，软件走向当然不同。决定也来自产品设计：这个软件只有你自己用，还是交给另一个人用？自己用得很顺手的命令和偏好，换成普通人可能就无法接受。还有一个经常被忽略的东西，就是架构：它决定软件最终会变成什么样。

这三段会成为撬动软件生产力的真正杠杆。它们会直接影响 AI 生成代码的走向，也会让技术债不断累积。需求、产品设计和架构看起来像是三件事，实际上一个都不能少。

还有一个很实际的例子。我的系统 UI 还正常工作，OBS 还在正常推流，但我不知道发生了什么，因为我所有设备都不能用了：鼠标键盘都没用，插上一个新的鼠标也没有用。以前碰到软件问题，第一反应就是看日志。这就意味着，写软件时要输出足够多的日志。

如果你不明确告诉 AI，它通常不会主动做这件事，可能直接给你生成一个没有任何日志的软件系统。没有日志，真出了问题，你连排查的入口都没有。这个技术债是马上就会产生成本的。

### 需求是把客户想要什么想清楚

需求工程以前很难讲，因为学生通常不会去见真正的客户，也没有机会真正承担一个系统的交付责任。AI 之前，能独立做产品的开发者也不多，很多人要经过几年开源社区的洗礼，才觉得自己终于可以独立做东西，也才有了一些付费用户。现在，独立开发者一下子多了起来，付费用户面对这些变化甚至有点瑟瑟发抖。

我想用自己熟悉的教务系统说明这个问题。它简直就是一个“史诗级的需求爆炸”。

我最近登录教务系统，发现它这几年一直在进步。先扫码登录，然后我搜索“仙灵教学楼的灯一直没有解决，我应该打电话给谁”，系统开始显示“正在理解您的问题”。最后要找的是基建处；但我在系统平台上提了工单，基建处又把它打回来，说这件事不归他们管，只好再打电话。这个例子已经说明，界面上的一个搜索入口，背后也有一堆业务边界和协作问题。

我还可以问“我现在在上什么课”。只要已经登录，系统似乎就能载入我的上下文，给出我的教师课表和本科课表。这个功能以前肯定没有，至少我自己从来不会用快捷搜索栏去专门找它。以前我总是在快捷搜索栏里输入，等下一个界面弹出时直接点开，突然发现系统已经支持这样做了。

这还只是入口。教学任务页面里有我的教学任务、班级学生信息，甚至可以看到电话号码。能在学生名单里直接看到电话号码，显然是一个糟糕的 feature。页面里还有编辑联系方式、当前教学学期、最新排课学期、历史授课信息；历史授课信息还要选择学年学期。期末考试期间，可以点击打印期末考试签到表；在没有到期末考试发布的时候，系统会弹窗告诉你无法打印。

“查看大纲”也有自己的要求，大纲页面刷新得很慢，而且只展示最新一个教学班。这个功能可能不满足“状态正常”的功能性要求。继续往下，还有我的助教、班级助教、慕课助教。疫情以前没有慕课功能，疫情期间领导说需要给老师添加慕课；加完慕课以后，又要添加慕课助教，而且不能把慕课助教当成普通教学班的助教来管理。这个需求是在不断叠加的。

你还可以尝试删除和新增教学班，但系统会提示：请在可维护时段内操作。于是原本非常自然的点击，在不同状态下变成了不同的结果；有时成功，有时弹窗，有时又进入另一个页面，甚至曾经还能编辑的教材功能，后来也可能变成需要重试。

这就是需求爆炸。每一个看起来很小的新功能，都可能和过去的角色、权限、学期、教学班、慕课、助教以及维护时段发生关系。它不是一个按钮，而是一整张功能网络。

更荒唐的是，教学周次这类内容也可以直接用 AI 的 slop 去填满。没有人来审计，也没有人认真检查里面填了什么。相比之下，教室的灯到底什么时候修好，反而更应该有人认真处理。

这个系统花了很多钱。某种意义上，我甚至觉得，如果把这些钱变成 token 补贴给大家，让大家用 AI 去做一些事情，可能还会更便宜；什么功能都不实现，搞不好反而更省。这是需求和成本之间一个很尖锐的反讽：我们花了大量资源实现功能，最后却可能没有实现真正重要的事情。

但是，需求工程不是为了嘲笑一个系统，也不是为了把所有功能都删掉。它要把客户想要什么想清楚，小到界面上要不要放当前学期、学年，修改按钮放在哪里，都要和用户对齐。因为你的用户不是你自己。

我自己的工具有时用得特别顺手，换成另一个人就可能不舒服。我有自己的知识和偏好，喜欢的命令、熟悉的操作，对别人来说可能完全无法接受。你不能因为自己是一个 geek，就假设所有人都会写程序、都会适应你的工作方式。

假设我们要设计一个教务系统，不能只想年轻人怎么用，也要想一位本科毕业、已经工作多年、距离退休只剩两年、可能连电脑都没有操作过的教务员怎么用。这完全不是同一个问题。计算机专业的同学可能缺乏的正是这种软技能：要有同理心，要能把不同用户的经验差异考虑进去。

行业经验也会影响需求。真正摸爬滚打多年的公司，可能比一个刚起步的本科生更清楚学位授予流程，也知道这些流程应该怎样变成需求文档。学生没见过真正的客户，设计出来的东西就可能有偏差；有行业经验的人，可能更接近用户的真实需求。

这还不是这门课的重点。重点是：当系统已经长成刚才那样的需求列表时，你其实已经进入了泥潭。交互系统的行业壁垒和经验，常常迫使你从零开始理解业务。但一旦你写出第一版需求列表，AI 或人类就会马上把它实现出来；从那一刻起，你就背上了技术债。

### 需求一改，技术债就长出来

> **结论**：在真实系统里，需求永远不可能一次说清楚，需求也不会一成不变。

我们举一个我自己很熟悉的例子。我们把离散数学课拆开了，因为觉得原来的第一门课没有教会大家数学的语言。拆开以后，准出结果变了，保研要求也变了，而且新旧课程衔接不上。

以前，系统里的规则很简单：计算机学院的学生如果要毕业，就必须选修离散数学。现在离散数学从一个学期的一门课，变成了上下学期两门课。那怎么办？总不能只修改课程名称，而要让系统承认，离散数学一或离散数学二满足毕业要求吧？这中间就是一个“或”的关系。

最早在沟通需求的时候，肯定没有人想到这件事。第一版 checklist 可能只是：在界面上放一个“毕业要求”；给教务员一个下拉框；再放一个“增加一条”按钮；用户可以选择一门课程。站在当时的时间点上，这个需求非常合理。

但等离散数学真的拆成两门课，就只能把需求文档重新调出来，在下拉框里加一个“或”。以后每叠加一个类似的规则，史山就开始累积。改需求为什么这么难受？因为你之前做的整体设计可能是一致的；新需求一旦在中间撕开一道裂缝，就会传递到系统的各个部分。一个看似很小的修改，牵动全系统以后，就会变成一团乱麻。

后面还可能有重修、课程抵扣、从别的院系转过来的情况。别的院系有一门离散数学，来到计算机学院后，能不能抵扣计算机学院的离散数学一和二？还是只能抵扣离散数学一，然后还要再上一门离散数学二？

一旦面对开放的物理世界，你没有办法把需求穷举完。最后，系统里总会存在一个 override（人工覆盖）。比如某个同学已经学习了六年，因为离散数学课程拆分，马上就要毕业，不可能再去修一个已经没有开课的学期。最后教学主任判断，这两门课之间存在替代关系；工程师打电话确认后，直接在数据库里把这个同学的毕业条件改成满足。

这个操作在数据库里是“绕过”的，但在人类世界里有一个合理的解释，而且档案仍然可查：最终是教学院长认为，这个同学学过的旧离散数学可以抵扣新的离散数学。也就是说，系统不能把所有现实世界的情况都建模完，最后仍然要留出人工判断和审批的空间。

需求变更不是某个人特别笨，也不是某个程序员不小心写错了。开放世界本来就会不断出现新的组合。你一开始做出的设计越具体，将来遇到没有覆盖的情况时，就越容易发现它不够用。

还有一个我亲自踩过的例子。2018 年我开始上课时，教务系统还是老版本，和我上学时用过的系统差不多。第一天我第一次用教师端，发现很好玩，竟然可以给同学设置缺课次数。

我很怀疑这个需求为什么要做。如果是我来做，我可能不会把“缺课次数”放进教务系统：同学缺课就缺课，老师有一张签到表或点名表，扫描留证就够了；学生手册里已经写了无故缺课达到多少次可以开除，也没有必要一定要在系统里留下一个数字。

我试着绕过前端的校验，想输入一个非常大的缺课次数。我以为前端和后端都做校验，结果后端直接拒绝了。这个质量还不错。真正出问题的是，我把一位同学的缺课次数从零改成了一以后，只要页面能够选出这位同学，相关的选课记录页面就全部 crash，直接返回 500。最后只好打电话给教务，教务也不知道怎么处理。第二天，工程师登录数据库，把那个“1”的条目修复了。

这就是你们以后会真实面对的软件系统和需求。不是每一行代码都写得很漂亮，界面也不是简单地改个按钮。需求要真的被人使用，校验、日志、数据库状态和业务流程要一起经得住现实折腾。

### 没有银弹，架构是长期生存能力

在 AI 时代做 MVP 没有问题，而且前所未有地容易：先实现最重要的功能，快速迭代三个版本，AI 都可以在你后面修。

但是，这也容易给人一个错觉：好像 AI 能把任何设计都救回来。

真实系统运行足够长的时间以后，原来能工作的设计可能突然不起作用。比如计算机系改成了计算机学院，需求已经变了，原来的组织方式还适不适合？AI 可以先帮你修三个版本，但第四个、第五个版本呢？系统越往后走，旧的决定越难撤回。

这就是所有软件工程都面对的问题：**there is no silver bullet，没有银弹**。

所谓银弹，好像有一种特殊的子弹，可以把吸血鬼和狼人普通杀死。但软件工程里没有这样的东西。软件会增长，需求会变化，软件要活下去，要挣钱，要和物理世界打交道。课程作业可以随时清零，从头再做一遍；一旦软件上线，就要持续维护背着 technical debt 往前走。前面没有做够前瞻的地方，后面就会不断变得更糟。

那怎么应对？答案是架构。

架构听起来很玄，好像很高大上。其实它并不神秘。你第一次开始设计任何代码、任何系统的时候，无论它多小，里面都已经有一种控制复杂性的思维。架构的本质，就是怎样控制一个东西的复杂性。

你一开始可以只有一个 MVP，只实现最重要的功能，但你不能只想着“今天先跑起来”。你应该想一想，怎样做一个最小的软件，使它能够随着需求膨胀和改变，仍然保持一定的韧性。

这实际上就是要把耦合解开。

```text
需求 A ─┐
需求 B ─┼──► 同一个数据库 ──► 界面与业务功能
需求 C ─┘
             初期能工作
             后续需求不断穿透整条路径
```

如果一开始就把所有需求都放进一个数据库，你当然可以很快得到一个能工作的原型，AI 也能很快把它写出来。但如果你没有仔细思考系统里哪些概念可以分开，这个决定就很容易把系统带进软件维护的泥潭。

架构不是等到产品已经堆积成屎山以后，再找一个神秘的框架来拯救它。架构要在第一步就开始影响系统：你的第一步究竟迈向哪里，怎样才不会让后面的每一次需求变化都牵动全局。

### 架构从第一行代码就开始

写一个很小的命令行程序，也会有架构问题。

你可能会这样组织一个 OJ 程序：

```text
main
  ├─ read input
  ├─ process input
  └─ write output
```

这不是什么高深架构，但已经把复杂性拆开了：输入、处理和输出各自有边界。程序规模一大，里面再出现参数解析、数据结构选择、错误处理和业务流程，就必须继续把它们分开，否则复杂性就会堆在一个巨大的 `main` 里。

比如，一个命令行程序的 `main` 会按照操作系统和进程之间的约定收到参数。文本可能以 `argc` 和 `argv` 的形式传过来。参数处理如果只是简单地反复做 string compare，很快就变得难以维护；你就会想起 `getopt` 这个东西，因为命令行工具还要处理短参数和 Unix 风格的长参数。`npm run help` 这类命令的参数，也不是靠程序员手写一长串字符串比较就能自然解决的事情。

这就是架构的思维：把一个复杂问题拆成几个可以理解、可以分别处理的部分。它不是什么神秘的名词，而是从第一行代码就开始的复杂性控制。

所以现在回头看，需求工程和架构设计并不是软件生命周期里两个互不相干的阶段。需求决定我们要往哪个方向走，架构决定这个方向上的系统以后能不能承受变化。AI 让我们可以更快地得到 implementation，却不会替我们决定 intent，也不会替我们承担需求变化的长期后果。

先把方向和边界想清楚，再让 AI 往 specification 和 implementation 上铺开；一开始就为变化留下一点韧性。这个系统才有机会活过需求膨胀，才有机会在真正上线以后继续往前，而不是每修一个功能就再制造一个新的技术债。

## 从 getopt 到事件溯源：架构是怎么从需求里长出来的
> 对应块：BLK12 | 覆盖分集：P07下 | 块标题（分集名）：《需求与架构（续）：从设计到落地》

写一个 parser 是复杂的。真的复杂。你得面对一长串参数，处理顺序、取值方式、可选项、前后依赖、各种奇奇怪怪的组合；每加一个新选项就多一处判断，代码很快就会变成一团缠绕的分支。

所以架构的第一步，往往不是什么庞大的框图，而是一个很小的动作：先把复杂性隔开。这段开头正好是今天要讲的那件事——**任何软件工程行为里都同时有 intent、specification 和 implementation**，你在任何一个模块里都可以谈需求、谈架构、谈优雅。

### 好代码背后都有架构，架构背后都映射到需求

看一份符合 best practice 的代码：不管是你在 GitHub 上翻到的一个好项目，还是某段你反复读过的 `getopt`，再往后多想一层——这确实是一种模式。把一个复杂的字符串，最后变成一个简单的 parsing state，这就是一种抵抗需求变化的方式：argv 会变，各种参数形态会变，但 parsing state 把这个问题隔开了。最后你只要写一个 `switch case` 加一个 `while` 循环，就能解析完这些参数。学会这一种 parser 的架构模式，后面就有了立身之本。

我们说过要讲 C++，可能要到 C++11/14/17 里的一些特性，在 PRIMERA 时代这些东西以及它们应该怎么用。有的老教师说"我讲了"，可怎么没讲呢——他讲的是"lambda 这个，`a + b` 等于 return `a + b`，没有了"。这讲了和没讲有什么区别？回到那个 parser 的例子：你在 GitHub 上看到一个 `getopt`，往后想一想，它确实是一种 parsing 模式。人在学习时看到的每一样东西，只要你再往后想一想，都能看出它背后的模式。

> **易错点**：把"讲了某个语法"当成"讲了架构"。`lambda` 怎么写只是 implementation；它为什么能把复杂结构隔开、怎么映射需求，才是 specification 层面的东西。

任何好的、符合 best practice 的代码，背后都有架构的设计，而背后都映射到需求。我很讨厌那种老古董的授课方式：讲 C++ 就只给你一个 `a + b` 的 lambda，然后说"这个我讲了"。我们不需要一个教务系统那种 monolithic 的东西、随时随地的架构——在一个模块里就可以谈需求、谈架构、谈优雅。

### 大模型为什么对架构掌控得还不够好

那为什么现在大模型对架构掌控得还不是很好？或者说，架构是一种品位？答案是：**架构和需求是连在一起的**。你没有需求，就不用谈架构；你谈架构时，面对的其实是为未来的需求做的一个开放的架构。那么你什么时候能设计出好的架构？取决于你对需求的掌握到什么程度。

我喜欢拿汉诺塔当例子。我以前开始上课的时候，先问我的研究生——保研的研究生："你让你写个非递归的 Tower of Hanoi，你能写出来吗？"研究生摇头。所以最后这十行代码就变成了我上课的一个例子。

你们肯定想问：为什么写一个非递归的汉诺塔就那么困难？

现在的人和模型对这个架构的理解差异，一下就拉开了。同样一个 prompt，GPT 写出来的代码是这样：定义盘号、步号，二进制末尾零的个数，每个盘子的移动方向；你看不明白，但 `highly optimized`、极度最优。反过来我给它一个明确的题目，它说"我数学不如你好"，它找到了 Tower of Hanoi 的数学性质。我作为架构师看到的是：这只不过是一堆数学——GT 是在数学道路上狂奔，希望数学上的能力拯救人类世界的一切。而 DeepSeek V4 flash 更有人感，它写了一个非常优雅的代码，基本是标准答案：如果你要写一个非递归的汉诺塔不跑动的话，这是一个非常干净的解法。因为它知道我们的 recursion——当我说要把一些盘子移过去的时候，剩下的任务一定要留在栈里（还要继续执行的任务留在站里），这样我总是执行栈顶的任务往前推，所以非常优雅。

豆包也试了一下，写了一个错的、有瑕疵的代码，我就不展示了。

我作为架构师，架构关乎的是我对需求的掌握到什么程度。所以我要写一个非递归的汉诺塔，我想的是：为什么大家写不出来？大家写不出来，是因为你对递归这件事情理解得不够深。所以我故意地说——上过我课的同学都见过这个代码：我们的程序实际上是一个状态机，可以回头看；你们可以去看我操作系统讲的这个课。C 语言是一个状态，一个 `single step` 是它的 operational semantics，叫操作语义；小步语义——比如汉诺塔减一，它在程序语言世界上是 a well-defined 的一步操作。所以我们只需要模拟这个，我可以写一个 C 语言的解释器。当你理解了 C 语言的解释器，你就能很容易地写出任何代码：我当时讲的其实是两个函数互相调用的，GG 调 F，没有任何难度，因为你就是把 C 语言的小步语义翻译成一个状态机的表示。

所以这个代码其实是从任意程序的翻译，如果你觉得这个代码不够优雅——对于汉诺塔来说 `overkill` 了，因为我可以把任意程序翻译过去，他们俩是等价的；做个 simplification、做个优化就可以从它变成它。所以我来看，作为架构师，这是理解 C 语言形式语义的好机会。看到不同的人，我还可以守住我的品位：GPT 可能它其实懂，但它不会往这个方向去想；DeepSeek 可能他不会往这个方向去想。我觉得比较有信心认为，强化学习可以把 GPT 往这个方向去引导，他一旦学会，也能做出在适当的时候会做出这样的实现。

一个搞笑的事情是：我在百度上搜索"非递归汉诺塔"，找到的第一个条目——百度很搞笑——第一个条目还是递归汉诺塔；往下找到 CSDN 的第一个非递归汉诺塔，看到的代码，啧，我甚至比 AI slop 都还要问题严重。这里有一个 `move`，但是 `STD` 是有 `move` 的。不知道是不是 AI 的评论，AI 给你营造一种 CSDN 的博客质量很高的感觉。但你们如果在上学的时候被这种 slop 污染了，还不如跟 AI 学，跟 DeepSeek 学都很好。GPT 已经不当人了。

> **易错点**：判断代码质量不能只看它跑没跑对。数学上对的东西，和理解了整个系统运行机理之后写出的优雅实现，是两个层次的东西。

### 同一个汉诺塔，四种表达

我们说我们要控制的是复杂性——它是一个架构，也关乎抽象。然后我们站在不同的层面上考虑这个问题，叫**跳出问题看问题**。那 GPT 也跳出问题看问题了：一切都是数学规律，我只要把程序世界里面的数学规律理解清楚，没有任何问题是我解决不了的。DeepSeek 做了正确的事情——人类反复说"递归是栈"，他在语料里面学到了这一点，做了正确的事情。然后我往外走了一步：你们对编程语言世界的理解投射成了递归和非递归的区别，然后投射成这样的一份代码。那 CSDN 那个就属于训练还没有收敛。我觉得训练还没有收敛，这个很有意思。

这就是：你在任何一个小的地方，都能看出架构水平的高低。这是实行的架构。

如果你要再大一点，比如 2000 行的架构：跳出问题看问题，代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的的规律。架构的能力从哪来？从你学过的每一个东西上来。如果它是好的，它是优雅的，它促使了你对这个问题的思考。**压缩就是智能**——你把它压缩了，你的那个 first principle，你总是从 first principle 去推导应该怎么样。所以这些能力就是你在学校里面学习社会上面的积累，共同赋予了你这个能力。

比如说你必须要和除了教科书、除了做题之外的人打交道，你才能知道一个马上就要退休的、优雅的教务老师，是怎么看待教务系统的。他的想法可能和你的不一样。你的想法总是最好的：数据库最高的性能啊，whatsoever。但对他来说他只是想要那个字大一点，他能够点鼠标的时候，不要手滑到那个按钮边上。**共情别人的能力**——这就是架构能力的一部分。

### QR Code Generator：需求明确，架构难做

讲一个 2000 行的例子：QR code generator，也就是二维码生成。我上课的时候讲了一个 Excel 生成二维码的例子。生成这样一个可以扫描的二维码，它可以把任何一个长的字符串编码成一个你能够直接扫描的二维码。然后你回头再用软件工程的概念去理解这个问题。

我们的需求非常明确：需求就是 Excel 的一个单元格。我希望在这个 Excel 里面有一个生成零一序列的单元格，然后它有一个输入的单元格，有一些输出的单元格。这是非常非常 deterministic 的任务。但是这里面是有架构的考虑的。

> **注意**：agent 对自己的能力到底到什么程度是有估计的。所以当这个任务足够困难的时候，他就会不做了。

你的 Excel 的公式——agent 其实还挺好玩的。比如说你有两个 sheet：第二个工作表里面是输入的单元格，里面是我的学生的实验成绩；第一个工作表里面是我存好了的学生期末考试成绩，然后我说："给我写一个公式，把那个学号对应的实验成绩给我拉过来。"那这个是在他能力范围内，他就会一把梭。这个事情显然超出他的能力范围，他还是会尝试去分解这个问题。它也会做架构，但至少今天的模型在做架构这件事上稍稍是有一些落后的。

如果你直接把它写成一个公式，你就会得到一个笑话——我们偷了一个 Lisp 程序，然后看到最后一页。因为这个公式实在是太长了，因为 Excel 的计算比较有限，它只能用——就好比是让你们用那种什么 brain 去实现一个 nontrivial 的程序，什么毁灭战士的游戏，那你写出来的程序就会是这样的。那这个时候你就需要一个抽象。

而且我觉得 AI 之前我看到那两个版本，他没有考虑到的是：这个需求看起来明确，但其实有很多坑。比如说 Excel 是有版本的。我们知道 Excel 从 2019 到 2023 它不断地都在增加新的功能。

比如说我刚才讲的那个需求叫"去查找学号对应的成绩"，以前是一个叫 VLOOKUP 的函数（有没有同学知道吗？没有同学知道，说明你们都不是 Excel 的 power user，太好了，你们是 agent 时代的第一类人——你要干什么，只要跟 agent 说就行了，你永远永远不需要再学一个像吃屎一样的语言了）。然后微软大概终于在某一年的时候受不了了，说我们推出了一个新的叫 XLOOKUP（extended or 卡牌），可以更方便地查找。Excel 是在演化的。

那么马上这个需求就会变得模糊不清。我到底是应该兼容一个旧版本的标准，使得我在各种人身上都能打开——我发给那个教务老师，教务老师也能打开这个二维码；还是我要做一个就是我自己用、用完即抛的，那我就可以用最新的语法实现最简单的公式。那到底是哪个呢？

> **易错点**：需求"明确"和需求"不会变"完全是两码事。把版本兼容的边界讲清楚，本身就是需求的一部分。

然后你看到的是：如果需求变了，你的代码维护是极度痛苦的。你想，如果 AI 给你 web code 了一个用 2023 Excel 公式的这个代码，然后你突然说"哎呀不行，2023 不行，要改成 2019，要改成 2003"，好，全完蛋——你的设计和实现就会从头回到原点，然后重新再做一遍。那对于一个 2000 行的项目来说，这个是 OK 的，你可以重做。但是如果这个 2000 万的项目已经嵌入到了一个巨大无比的需求，嵌入到教务系统的时候，它和其他的部分产生关联，加钱，对不对？那你作为项目经理说话：我要加人，我要加钱。对我没办法，我只能用这个方法来满足你的需求。但这显然就是一个架构没有设计好的。

这个还有很多。比如说我最后出来以后对它放的位置不满意，我要把它整体往右移一格——如果你所有的单元格都是这个硬编码的，就直接立即崩溃。你看到它对需求的变更抵抗是很糟糕的。

### 这其实是一个编译的问题

所以如果我们跳出问题看问题，其实这是一个编译的问题。我要开个 A，正常是这样的——先把这个关掉。我可以给你一个从字符串到二维码的伪代码。这这这这这个问题本身是清楚的，他显然这个 or react react，就是我给他了一个 very clear 的问题，他还要去读文件，对吧？二维码是完全有规范的。他给了一个非常短的代码，对吧？非常难。而且这个就是一个代码：有什么版本纠错等级、掩码，然后有一个大小，然后有数据编码；现在有 0100，然后有一个八进制字节，怎么然后有一个纠错码——一个纠错码啊，它是一个什么 data 乘以 X 的 26 次方模，最后加上 134 个码字，最后加上一个 ECC，最后直接放到这个空间里。

那为什么这么简单的东西在 Excel 里面实现这么困难呢？这个 gap 到底在哪里呢？如果你跳出到问题外面，你就很明显能看到二维码容易用算法来描述，对吧？这个过程，这个过程我用一个 Python 就再容易不过了。

> **思考题**：明年保研机试我就出一个这个题，让你去实现，最后打一个 0/1 矩阵，好像是一个 OK 的。如果要拖网的话，还必须要拖网的话，是一个不错的测试大家的题目。但是我们的要求是 Excel。我们不存在任何一个翻译器、一个编译器，可以把一个 Python 编译成 Excel，对吧？这显然也是做不到的。

Excel 它本质上是为了财务啊、报表啊、这些而设计的，对吧？管理学生成绩是一个小的数据库，它本身就不是为了做 Turing complete 计算来做的。所以没有一个 py to excel 的编译器，叫 PYXLC，这个东西不存在。

然后如果我们直接把它变成伪代码，或者是自然语言，然后我们用 LLM 去编译，那我们也看到了这个 LLM 的问题：他直接上手就做，做了就——需求漂移的时候就会遇到很大的问题。

### 中间语言加两种执行：从 LLM 到 Excel 交付

所以你马上就知道：如果我有个好的架构，我是不是可以在 Python 和 Excel 之间构造另外一个语言？这个语言它既可以很容易地翻译成 Excel，又可以继承一定的 Python 的功能。就是刚才那个伪代码——我希望我要的东西其实是一个中间的编程语言，然后这个编程语言能够支持描述这些东西，描述这些运算中需要的东西。然后这个语言又可以翻译成 Excel。

我做了这样的一个设计：我这样的语言是可以翻译成 Python 的。就比如说你们都写过那种表达式求值的程序，对吧？我就是做一个表达式树。比如说我就说比如说异或加什么 `a` `b`，对吧？或者 `x[0][1]`——这可以取出一个字符串里面的某一个。这就是一个小的编程语言。然后这个编程语言显然很容易翻译成 Python，对吧？你直接把它打包就行了。它递归地翻译——你把任何一个表达式树 dump 出来，你就是递归地左子树、右子树，然后把它根据这个节点拼起来啊。所以这个语言可以翻译成 Python。

这个语言也可以翻译成 Excel。我只要要求每一个节点都有一个翻译成 Excel 的规则，对吧？我可以把这个东西放到一个格子里——任意的格子都可以——然后把这个结果放到一个格子里，然后我就可以在这里做出这两个格子拼起来的结果。好，那我就好办了。我让大语言模型生成这个语言的二维码计算逻辑，然后我用把这个语言翻译成 Python 去验证，看我的这个公式写的对不对；然后这个公式写的对不对，等我公式写对了，我再去写 Excel。

然后你看到这样的架构：不就是我们刚才在第一个最小的例子里讲的那个 `getopt` 吗？你说我们要写一个程序，写一个命令行的工具，我们第一件事情先 `getopt` 得到一个 parsing state，再从那个 parsing state 出发去做下一步，一样的设计，对吧？

> **定义**：一份中介语言，两种执行方式。构造一次，中间语言可翻译成 Python 去验证，可翻译成 Excel 去交付。

所以你们作为一个 unsupervised learner，你们作为神经网络对吧，大家神经网络你就是看好的东西，你看得多了，你自然就能泛化了。当然你看得多的时候，你要有意识去看好这个东西——为什么要这样。你回头突然有一天你会想通：对啊，看到某一个 blog 的时候，或者有一天听我上课的时候，突然就想通了一件事——原来这个世界上大家做的事情都是差不多的，就是在做的事情：一份中介语言，两种执行方式。所以我就可以构造一次。

这个架构就是：我做了这样的一个架构，这个架构是从 LLM 翻译成中间语言，这个用来验证，这个用来交付。

> **易错点**：别一上来就让 LLM 直接写 Excel 公式。需求漂移的时候你会发现你根本没法维护。

而且这个架构在这个架构上我还可以发展出：比如说优化。什么是优化呢？我不是一种语言吗？一个语言我如果觉得性能不好，哪个地方生成了太长的代码，我就有一些改写的规则，我就可以把一个程序从一个形态改写成另一个形态。比如��你们都知道，如果我有一个变量在循环里面每次都计算，但它们的值都一样，我就可以把这个变量的计算提到循环的外面——编译器可以自动做这件事，语言模型，你自己也可以手动把这个计算给移出去，你可以做手工的优化。

而如果我有个中间语言，我就可以让大圆模型去优化它，对吧？然后你在这个计算机系统里面学到的，比如说 profiling guided optimization——你可以先要去知道性能瓶颈在哪里，然后再用这个 profile、性能的 profile 再去指导你代码应该写成啥样更好。你的概念又用上了。

所以一个好的架构可以承载这个需求的变化。未来 Excel 如果版本要改，没没问题啊，我无非就是把一些算子用另外一个方式去实现。然后我讲算子的时候，你发现今天这个 AI 也在干这个事——人类就是这样。

### 数据库建模的三个好消息与一个坏消息

这样的一个架构来自一个什么样的基本原理？我们的软件是物理世界过程在信息世界里面的投影，对吧？然后我们的物理世界是有状态的，`Everything is a state machine`，我自己也是一个 state machine。所以软件系统它很容易会建模成一个 state transition system：它有一个状态，然后这个状态一般来说是用数据库，就是 persistent 的状态是用数据库。

比如说一张表来表示学生，学生有学号、姓名、院系等等。然后我还有一张表表示学院、表示选课——反正各种各样的东西都可以用二维的表来表示，这是你们在数据库课上面学过的。

然后数据库要求你消除这个表里面所有的冗余，要把这个数据库 factor 成 normal form。什么意思呢？你最好不要学生里面有一个课程。比如说学生有一个学号，学号是唯一的，比如说 1234，好。那学生还有个姓名。那你在另外一张表里面如果要引用一个学生，尽量不要用姓名来引用，因为姓名学生可能会重名，然后就算不重名，这个也会带来一些麻烦。你更好的是不要用姓名，就把这一列从这个表里面去掉，而是这里面放一个学生的 id，比如说 1234。这个 id 就相当于一个链接，这个链接指向了学生的这个信息，然后这个学生还可以再指向别的表里面的某一些信息。这样把信息给最小，原则就不会——其实是铲除冗余的 dependency，对吧？我一个地方改了以后，我不需要改另外一个地方。因为如果这个学生真的改名字了，不要笑，这件事情在中国是合法的，对吧。你现在在这个表上，如果你用这个方式、用这个分解的方式，那学生改了名字，这个名字改掉就行了，你就记一个曾用名。但如果你是这样的两份就存了两份名字，那对不起，你知道这两个地方都要都要修改，对吧？这就是一个很大的很大的代价。

然后我们一般来说会把这样的世界建模成这个状态，然后在任何时候这个状态就代表了——比如说在现在这个时间点上，南京大学有哪些学生，然后有哪些学生选了哪些课，有哪些老师等等。

然后每当我们这个信息系统（前后端分离嘛，这也是一个非常经典的、刚才说的前后端分离的架构），如果比如说今天我选择退学——我没有买到 token，然后我选择退学——那就是一个 update 这个数据库的过程，然后它就从一个状态迁移到了下一个状态。就比如说我现在 A 现在还在，那在下一个状态里面，A 就没有了，A 这个记录就不存在了。那这就是一个始终是 consistent 的视图。你永远是在交互系统里面打开那个网页，就看到这个东西的一个投影，它的投影。这是非常经典的架构，没有任何的错误。

但是但是但是——如果我们想想，教务系统为什么不适合这样一个 CRUD 的架构？因为当前的状态里面，当我看这个当前状态的时候，我看到的是一片祥和的景象，但是这个当前状态所有的历史它丢掉了。

### 状态丢弃历史：无法解释的黑洞

比如说如果我真的在某一个地方里面，学生的姓名存了两次，这是非常正常的，对吧？在某一个表里面，姓名存了两次。因为这可能是一个字符串，对吧？这可能是一个字符串，然后这个字符串就是什么——加当时加学号，对吧？授予谁谁谁什么什么的一个——这个东西对它没有用关联的方式，而用一个字符串加它写到数据库里了。那这个时候数据库内部就发生了不一致了。

所以比如说 GP 给了我一个例子：学生在学生字段里面，学号在这个学生表里面；比如说有一个 column 就叫"是否允许毕业"，对吧？比如说你们现在上我的课应该学分还不够，所以应该都不允许毕业，对吧？然后有的同学这个学分修够了，他就允许毕业。而这个允许毕业的这个，一是有很多其他的状态算出来的，是有之前之前有触发（trigger），对吧？比如说每当你修了一个学分，或者你的毕业设计状态改变等等的时候，它都要重新计算一个你是否毕业的逻辑。

这样因为这个东西对信息系统来说很重要，这个教务员老师需要能够——辅导员老师能够在教务系统里面导出到现在还毕不了业的学生，要找你一个一个谈话，对吧？他必须要在教务系统里面才行，这是个很典型的需求点才能做到。

但是这样的东西是历史上面的计算的 dependency，然后他们随着当前的状态都没有了。你知道这个学生可以毕业，但是你不知道他为什么可以毕业；你知道他这个不能毕业，你不知道他为什么不能毕业。这个计算的过程丢掉了。

而计算的过程丢掉，这个软件又是现实世界物理过程的一个有损的投影。那么最后导致的是：物理世界里面我建模不了的，全部都需要通过其他的途径来解决，对吧？今天政策更新了，领导批准了，但是这个培养计划新的方案、新的数据还没有导入到教务系统——你们经常遇到这个问题，对吧？不一致。就物理事件已经发生了：这个培养计划已经通过了，学期已经开始了，我已经上课了，这个没有灯（没有录），对吧？就物理世界已经发生的事实在系统里面没有建模。

然后在系统里没有建模的时候，哎呀比如说这个教室还不能用——就第一周很典型，第一周整个这个仙一这一片都还在修，教室不能用。然后不能用的时候，这个显然教务系统没有建模。这一点没有建模，这一点最后就靠他们手改重新安排教室，然后再把那个教室安排到另一个——对吧，我第一周就去另外一个教室上课了。

然后这样慢慢慢慢随着时间的积累，你的系统里面会有大量不一致的数据，随着时间变成无法解释的黑洞。哎，明明这个同学不该不能毕业的，他为什么毕业了呢？突然回想起来的时候，明明这个同学没有交学费，应该毕不了业的，为什么他能毕业呢？系统里面就无数无数这样你想都不能想的不一致。

所以你们在面对这种需求的时候，CRUD 就会死。比如说南大没戏了，哎，当前环境异常——啊我知道他对 Linux 很害怕，Linux 的这个，嗯，对吧，南大没戏了。我们是最后一批系，现在成为了计算机学院。

### 一次查询，两种答案：院系调整的困境

在南大院系发生调整的时候，这个教务系统就瑟瑟发抖了。因为还是这样的 CRUD，它是一个 point of truth，就是所有的事实都在这。那好，我们的这个 department 变了，那我应该是把旧的这个 department——我这个世界里面实际上是一个对象，虽然是表嘛，它还是对象，这个表就叫计算机——那我要把他的 name 从计算机系改成计算机学院吗？

要吗？要也不对，不要也不对。你想首先如果要这个，就你把这个 object 改了，计算机系现在确实是变成计算机学院了，但是这意味着我的毕业记录——如果我 select 我到系统里面查询，我就变成了这个：`2011 年毕业于南京大学计算机学院`。这个就属于我事实不符了，因为我在 2011 年的时候，这个前面计算机学院，它生成了一个系统里面给我生成打印什么证明的时候，给我生成了这个东西。好糟糕。

然后如果不变呢，也很麻烦，对吧？因为你现在的所有的这个 department id 都指向这个学生的这个 department id，都指向计算机系，还是得把它改过来。你需要对它做一个数据库的迁移：你要创建一个新的对象，然后新的对象和旧的对象之间的这个关联关系，你还要把它考虑清楚。

所以你看到，如果你假设这个世界就是这样的、这个投影不变了，CRUD 当然是一个完美的架构。但是只要你假设这个需求会发生摧毁性的变化，那么这个数据库你每次你就要这样想——你每次都会涉及一个数据库的迁移，对吧？业务逻辑的重写。代码是可以重写，但是你的历史因为历史消失了吗？我们说这个因为这是一个 database 的 transaction，对它 update 完了以后，就从这个状态彻底地挪到了新的状态。你做一次数据库的迁移，你就要考虑历史上所有可能发生的情况，而且何况这个数据库里面已经有很多的不一致了，你很难写出一个规则来迁移啊。你还要冒着数据库迁移完了以后这个数据库就坏掉了的风险。你就像我那个把选课给改成一模一样——因为你在你的测试环境里面做一次迁移，和你把一个真的、学校里面所有的数据都做一次迁移，这个难度是完全不一样的。

### 好架构：先记下所有操作

但是如果我要重做一个教务系统的架构，我会怎么做呢？我就会看到，这个 single point of truth 太危险了，对吧？它一旦你有任何的不一致，你都不知道应该怎么样把它拿出来啊。然后你就想到数据结构。课上讲过一种非常神奇的东西，叫 persistent data structure，它可以得到这个数据结构所有的历史。

也就是你存一个数据结构，对吧？你存一个一棵树，好，那这就是 CRUD，对吧？你看数据库也是一个数据结构，对吧？然后你当前就是存一个库，然后你你对它做一个操作，它就到下一个状态，这就是经典的 CRUD。

但我还有另外一种：我可以一开始只有一个节点，然后有一个节点以后，我可以创建——就下一次它树不变了，那我可以这个节点还在，我把这个节点放过来。然后如果我到有一天，比如说这个数变了、它变大——比如说我我的这个要在这个节点上新建一个，那我就把它从到根的路径上面这个长出来一个，然后它的左子树可以指向它。这个数无论多大，我其实都是可以存下来的。

然后当然我可以这个——就是我我可以存状态，也可以存操作，也可以存操作对状态的 delta。这三种视图是等价的，对吧？你看我存它的日志，就是一个 local head 的 write-ahead 的 journal——你们在数据库操作系统课上都学过。然后你存它们的这个 delta，就是 git 这样的版本管理里面的思想，然后你存这个状态，当前的状态就是 CRUD。但是他们都可以帮你回放历史，得到当前的状态。

> **易错点**：把"状态"和"事实"画等号。状态只是事实的投影；一旦丢掉历史，事实就无法重建。

所以如果你想要设计一个更好的架构，最好是先把干的所有的事情都先记下来。今天张三退学了，今天张三又复学了，对吧？——你可以假想，就比如说啊这个世界是之前没有复学这个操作的，没有复学这个操作，就是把张三从这个数据库里面抹掉——好，抹掉了它就抹掉了，对吧？他可能有一些记录就删掉了。你要把这些这些和他和其他部分的关联重新给建起来，那你就付很大的代价。你要加上复学这个操作，对吧？他又买到 token 了。

然而如果你是用比如说记录所有的操作的方式，你就可以知道，通过 replay 可以知道张三复学前的状态是什么，然后你再把这个状态拿过来，他没有丢。就你的逻辑是不能减少的，就是你即即便使用记录日志、记录历史的方式，你比如说复学这个事情之前没有考虑过，我依然是要为他写一个逻辑。但是因为事实是不可篡改的，你世界里面所有东西都是对事实的投影，事实投影出来的哦，那你就好像就有底气了一些。你就不怕错了，你就不会像刚才那样说：我要做一个数据库迁移的时候，我手在抖。因为你总知道你任何一个这个做错了，你都可以很快地回到过去的一个快照，然后把逻辑修复，然后再来。

然后你也可以看到，计算机系、计算机学院的问题相对来说也好解了一些，对吧？我可以在某一个时刻发生了一个事件，叫这个院系调整。你查询一个过去的人的时候，你会查询到他过去的版本，然后并且你知道他经历了这个——就是说如果你要查询他过去、比如说毕业时候发生的事情，你直接查他毕业时候就可以；然后如果你想要得到一个它比较新的信息，你可以看到比如说投影出和这个人相关的：这个同学在比如说 2007 年入学，2011 年毕业，然后到这个都是计算机系，然后计算机系在 2024 年改为了计算机学院。你看到我可以裁出一个对吧，就是总是你总是可以想要得到一个事实——当前的事实，你可以裁出一个和事实相关的历史，然后把这个相关历史 replay 得到我现在要的状态。我可以查询过去，也可以查询现在，这就是一个好的架构设计。

然后你祝贺你，你就发明了一个叫 event sourcing 的一个非常经典的设计模式。它可以从这想法很简单：从历史事件生成状态，而不是直接维护这个 CRUD 的状态。你们可以回去可以在这个 agent 的带领下，去了解一下，比如说如果用……对吧，然后一般 switch 他有……就你马上会反应过来哦，是不是会有性能问题，对吧？因为要比大量的 replay。但这都不是很大的问题，我们总可以比如说用快照缓存，各种各样的优化技巧。
