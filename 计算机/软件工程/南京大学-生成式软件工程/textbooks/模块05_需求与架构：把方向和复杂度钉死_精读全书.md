### 软件工程是从一张依赖网里长出来的

上一节课我们把软件工程的来龙去脉捋了一遍：软件危机是怎么冒出来的，大家发现那会儿软件开发已经做不下去了，于是需要一套工程化的方法来解决软件里的问题。我们也看了 Royce 那篇老 paper——他画出来的那条路是这样的。

先有 intent，然后走向 spec，最后走向 implementation，最终产出一个软件。

> **提示**：但这张图纸只画了一半。implementation 做完之后你还得维护它，软件的生命周期并没有结束。

所以这一路向下走，自然就长成了一条瀑布一样的过程。而走的过程里，每一段都会往下一段沉淀东西。intent 和需求的阶段，你对软件形成的一些认识，会逐渐进入 specification 这个 space，并且形成依赖关系；等到系统实现的时候，又会出现各种模块、函数、代码、测试，各种各样软件里的 artifacts，它们之间既有直接依赖、也有间接依赖，于是就织成了一张错综复杂、交错的网络。

```text
      intent ──▶ spec ──▶ implementation ──▶ 运行与维护
                    │
         模块 ─┬─ 函数 ─┬─ 代码 ─┬─ 测试       ← artifacts 交织成网
                └────────┴────────┘
                          │
                 data dependency（直接 + 间接）
                          │
                          ▼
        后端发现一个错 → 沿依赖反推回上游某个决策
                                  │
                                  ▼
              那条决策被证明是错的（设计不合理 / 实现达不到预期）
                                  │
                                  ▼
                 下游一大片被污染、全部失效 → 重做 → 大量成本
```

回过头来再想一下这个过程——软件工程困难的本质原因，一半就藏在这张网里。

对这种模式的批判，逻辑就来自 data dependency。如果你按照这样的模式开发，很可能你在后面对吧。他的分析其实就来自于 data dependency：链条是这样的——如果你在后面某个地方发现有一个东西错了，这个错会沿着依赖关系一直反推、回溯到前面的某一个决策上。而如果那个决策在事后被证明是错的——设计不合理、实现达不到预期、需求或者设计做错了——那它会导致后面很大的一个部分，被污染到的部分都会失效。你可能需要重做，会带来大量的成本。

就在这样的一个背景下，软件工程诞生了。它研究的是：在做需求分析、做系统设计、做系统实现的时候，我们有什么样的方法。

这里面既有带人文关怀的方法——你需要用 checklist，你得说清楚这个产品经理应该怎么管人，这其实也是软件工程的一部分；也有关于你写代码的时候应该怎么写测试，我们有没有可能做自动化的测试、自动化的分析。就这样一个整个软件工程的故事展开了。

而在那个年代，软件工程里还有一个我觉得挺有意思的尝试。人和人很难对齐，而且我如果不写文档的话，很有可能最后只剩一份代码；甚至你出错了，都不知道应该去追溯到过去的什么时候。所以在那个时候，软件工程提出了很多重要的概念，比如说 traceability（可追踪性）——理想情况下，每一个测试用例、每一段代码，它都能够关联到、可以 trace 到过去发生的事情、做过的设计上。这样整个系统里面到底发生了什么、我改它会影响谁、我改这个设计会影响哪些测试用例，都能维护起来。

而且这还不够。如果我们有一个结构化的、有语义的语言来表示它呢？显然是更好的。所以就有了 UML——他试图去对齐整个世界上面的软件工程的实践。这当然都是有智慧的。

### 软件其实一点都不软

我们回过头来再想一想这个过程，软件工程困难的另一个本质原因，其实要更朴素一些。

我们觉得什么东西是"软"的呢？你们现在坐在教室里面的这个椅背，它就是软的——它有弹性。你把它摁下去，它就瘪下去了；做完以后它又弹回来了，你下次做的时候它还是好的。

软件和物理世界里的这些东西很不一样。它是一个纯粹的逻辑制品，而这个逻辑制品容不下任何细微的差错。作为一个程序，它是有形式语义的。

> **易错点**：你可以想象，你们在写代码的时候，从来没有考虑过"如果你的程序里面的内存可能会发生一个 bit 的翻转，你的程序还对吗？"——肯定不对了。

举个稍微极端一点的例子。你写了一个程序，从 STDIN 输入一个 N。现在一切很好，输入 N 等于 1，然后循环接下来会从数组里面读一个元素到寄存器里。这个时候，如果你的软件是运行在卫星上的，然后有一个宇宙射线击中了你的内存——那个 1，它的 unsigned integer 的最高位翻转了——它突然就变成了一个巨大无比的数，然后你整个程序就彻底 collapse 了。它会无限制地去从输入里面读数据；如果没有那么巧，那可能会挂在那儿。你的程序表现出来就是：他好像在读，也可能读了一千个、一万个数字以后，才产生一个 memory error。

所以软件其实一点都不软。

刚才我说的是一个比较极端的例子，它运行的环境可能是你不可预见的。但其实大家在 data center 里是会观察到的：比如说你的处理器随着制程越来越先进，它在这个热噪声下，有些指令——特别是那些密度特别大的那个指令——它可能会产生 silent error。就是这条指令，你在这台机器上执行和在那台机器上执行，它结果就不一样；而且甚至可能要这台服务器运行一段时间以后才会出现这样的缺陷，是制造时候的缺陷。

所以软件本身就是一个——大家都认为是集成了人类智慧的——一个东西，然后同时它又要承载客户提上来的这些需求。今天我会花时间来讲这个系统应该怎么样设计，应该怎么样防止它堆积成屎山。那就是软件工程。

在这样的背景下，我想说一句你们可能不爱听的：也许你们之中有学软件工程的同学，学计算机专业的同学肯定要上软件工程的课程——软件工程是一个关乎整个软件生命周期的学科，但是你们被迫只能从底下这个地方开始学。

为什么？因为如果你不理解代码是什么，如果你写不出代码，没有体会过码农开发软件的痛苦，那你是不可能做好一个产品经理的，对吧？你设想的"这个事情应该可以办到""这个事情花多少成本可能可以办到"——如果你没有一手的经验，你确实是做不到的。

所以你们上来以后就先学 C 语言，先学一个最基础的、老的、已经过时了、没有人用的、也还算有一些人用的编程语言。然后在这个基础上不断地产生新的知识——知道世界是怎么失败的，新的语言是怎么创造出来的，为什么要有它——然后一点一点往上走。

> **结论**：所以今天你看到的是像需求、产品、架构，这是我这门课要讲的主题。intent 到 spec 的这个阶段，其实决定了一个软件系统从零开始走向的最关键的部分。

前面上课的时候我们先讲了版本管理。为什么先讲版本管理？因为你总是要从一个空的软件项目出发——我们总说"从零开始"嘛——那我们先讲一下如何从空的出发，这个软件怎么样往后走。接下来下一步，我们就要把控软件执行的方向：软件的走向，你的船到底是往东南西北哪个方向开。

### AI 时代：代码便宜了，方向没有

方向这件事一开始就极其重要。但是像现在的需求、产品、架构，很难做出两个来——你只能要么就是硬着头皮安利："今年没办法，我只能这样安利"；要么就是先把"这个产品到底是什么"当成一个还没定义清楚的概念，硬给它规定一串必须满足的性质：要做 ABC，要满足 AB、BC 什么什么什么。

我们学校号称南京大学软件工程世界第一，在那些排名里面，如果你出的文章大部分都集中在和编码相关、implementation 相关的东西上的。当然也有些做 NLP 的会说：好，traceability 在软件世界里面是非常重要的，那我们能不能训练一个神经网络模型，直接从数据当中把这个推导出？也许用模型就可以做到。

但我今天还是要讲一讲这个里面最重要的东西，或者说，对 AI 时代来说最重要的东西。

> **结论**：在 AI 时代，你生产一个目标明确的代码，已经变得非常便宜了。

而且现在对我来说，我让 AI 生成代码，我只要把它的边界划定清楚，我其实真的已经不看它的实现了。后面我会给大家看到那个模型昨天写的那个代码，那个量已经超越人类能够理解的范畴了——但是它是对的，我还能比较好地信任它。只要我把边界划定清楚，并且我能够知道它怎么样做一个好的 validation，那么我可以把这些 agent 铺开去帮我实现这个，还是有一定质量保证的。

那剩下的东西呢？剩下的其实就是我做软件系统的压力，或者说，能够决定这个软件系统最后能走多远的东西。

我们总说做一个 minimum viable product（MVP），这没有问题。因为做 MVP 可以让你快速地找到一个从 intent 到 specification 再到 implementation 的切片，然后在这个切片上，你可以走完整个软件完整的流程。

> **易错点**：但是它不完备。

你在做这个 MVP 的时候，一定想的是先做最重要的功能。你并不会想着你在做 MVP 的时候，就去想那个按钮、那个样式应该长什么样。因为这是 dependent 的——你的按钮是你的按钮的样式，你整个界面的设计 depend 到整个你的所有功能的实现。如果它还不确定，你现在就去调那个按钮的样式，当上面的设计发生改变以后，你觉得这个按钮的样式很有可能就作废了。

所以你会有一个倾向：不要做无用功，不要去研究一个你即将会扔掉的东西，对吧。每一个人都有这个本能。

那如果你确实有这个本能，那么你就应该知道，在做 MVP 的时候选哪些最重要的功能，你会得到一个可以运行的版本。好，没问题，AI 会给你一个。

但是今天的 AI——至少今天的 AI——它没有去从需求、产品设计、架构的角度去看这件事。除非你去显式地用 prompt 去告诉它。甚至哪怕可能只是几个字告诉它，都会不一样。因为你从一个零开始的项目的零开始，如果你要让它用比如说这个 client–server 的架构，或者你让它做一个 CLI 的架构，同样的一个 MVP 的需求——需求定下来，它加上几个字的 prompt，你会得到完全不同的 MVP。

```text
                    同一个 MVP 需求
                          │
      ┌───────────────────┼───────────────────┐
      │                   │                   │
 "用 client–server"   "做成命令行程序"     "做成网页应用"
      │                   │                   │
 先设计数据的存储      选一个命令行库      选一个前端框架
      │                   │                   │
      ▼                   ▼                   ▼
      这个文件一写出来，就进入了 agent 的上下文
                          │
                          ▼
     每当你继续做下一个需求，都会带上之前的所有的历史
                          │
                          ▼
                  技术债开始累积
```

它们功能上都差不多，看起来都是实现了你的需求——比如我要做一个 coding agent，或者做一个你 lab 里那个学生的 agent——但是这几个字的 prompt 都会膨胀。因为一个架构选择会一路落成具体的技术栈决定：如果你有 CRUD 操作，你这里面可能就涉及到一个数据库的选型；或者是依赖一个 JavaScript 里面的命令行库。那你如果先要求它做 client–server，它可能就会先设计数据的存储，然后给你选一个数据库。它一旦这个文件写了，它就会进入 agent 的上下文，然后每当你继续想要做下一个需求的时候，都会带上之前的所有的历史。

而这在软件工程里面也有一个专门的术语，叫做技术债（technical debt）。你做任何决定的时候，你就已经背上了这个债务。因为这个决定，你在做 MVP 的时候是不知道后面会怎样的。

```text
                 撬动软件生产力的三段杠杆
   ┌──────────────────┬──────────────────┬──────────────────┐
   │       需求       │     产品设计     │       架构       │
   ├──────────────────┼──────────────────┼──────────────────┤
   │ 我到底要一个     │ 这个产品是只有   │ 这个软件会变成   │
   │ 什么功能的代理   │ 我自己用，还是给  │ 什么样           │
   │                  │ 另外一个人用     │                  │
   ├──────────────────┼──────────────────┼──────────────────┤
   │ 你自己版本的需求 │ 你有些知识和偏   │ 几个字的 prompt  │
   │ 不同 → 软件走向  │ 好，别人可能不   │ 就会膨胀成一整   │
   │ 肯定不同         │ 习惯             │ 套技术栈         │
   ├──────────────────┼──────────────────┼──────────────────┤
   │ 后面全是白做     │ 自己顺手，别人   │ 需求一膨胀就进   │
   │                  │ 不舒服           │ 维护的泥潭       │
   └──────────────────┴──────────────────┴──────────────────┘
```

你的决定性来自于需求：我到底要一个什么功能的代理？显然是写了需求的。但这个需求要有一个自己的版本——比如说，你就想做一个不帮助你学习的（agent）；或者说你已经进入了课题组，你对"读研究论文"这件事情有很强的需求。那你看到，在不同的这个需求下，你的软件的走向肯定是不同的。

再加上你的产品设计。我直面一下你最终的产品：这家比你想象的——这个产品是只有你自己用的，还是说我想给另外一个人用？我自己有很多自己用的、非常顺手的东西，但是我想给另外一个人用，他就用得那么舒服了。因为我有些我自己的知识，还有自己的偏好，对别人来说可能是受不了、不习惯的。比如说我喜欢的命令，内行的工作，普通人肯定不要。

除此之外，还有一个隐藏的东西：架构——就是这个软件会变成什么样。

这三段会成为撬动软件生产力真正的杠杆。你在需求上可能是极端的，但是它会对你的 AI 生成的东西的走向、技术债的累积，带来一个非常大的影响。所以我会花两节课的时间来讲这个需求和架构。

我插一段我刚才翻车的事情。我的系统 UI 还在正常工作，然后我的 OBS 还在正常地推流，但是我不知道发生什么，因为我所有的设备都不能用了——我鼠标键盘都没用了，我插上一个新的鼠标也没有用。

以前当然这也是一个软件工程实践，对吧：出了问题你要去看日志。这意味着你在写软件的时候，需要输出足够多的日志。这个好像 AI 就不行：如果你不告诉 AI 的话，AI 也不会主动做，它会生成一个没有任何日志的软件系统。它都会留下这样的技术债。我不确定我能不能找到这个问题。

### 需求工程：一份真的需求说明书

好，我们回到今天要讲的内容：需求工程。

我们说需求工程曾经很难讲。因为学生不会去见这个真正的客户，也做不了需求级的软件系统。你们从刚才说从最刚开始的时候学编程语言，到你毕业的时候，你的能力增长不足以让你去面对一个真正的软件的客户。

当然现在这个事情有点变了。你看在 AI 之前，我们有很少量的精英独立开发者——你们经历了几年的开源社区的洗礼以后，终于觉得自己可以独立了，做开发者，然后会有一些付费用户。

然后现在变了。现在这个独立开发者就爆炸了，然后付费用户瑟瑟发抖。

#### 史诗级的需求爆炸

我们今天要讲的这个软件系统的例子，是我比较喜欢的这个教务系统。教务系统啊，我可以称它是史诗级的需求爆炸。

我昨天就趁机会看了一下，然后我发现——我登录还在吗？好，我的登录不在了。让我扫码登录一下。扫码登录。好，我发现这个教务系统这几年一直都在进步。虽然这是我的界面，我稍微放大一点点。

好，我最近发现史诗级的更新：教学楼的灯一直没有解决，我应该打电话给谁？我可以直接搜索。"我正在理解您的问题"——我不知道。基建处嘛，基建处。但是我在那个平台上面提了，然后基建处就把我打回来了，说这个事情不归我们管。回头再给他打电话。

那我现在在上什么课？——我不知道，这个行不行啊。我不确定他有没有载入我的上下文，我猜是可以的，因为我登录了。诶，他还是"教师课表/本科"，这是我的课表，对吧？这是一个史诗级的更新。你们竟然不知道有这个东西，突然间有这个功能了。我不知道是什么时候加上的，曾经肯定是没有的。因为我总是不会去搜索，我总是在那个快捷搜索栏里直接等着它下一个界面弹出的时候，我就点它。

所以这是一个非常典型的需求爆炸的系统。

> **提示**：这个系统肯定是花了很多钱的。然后这个钱我觉得某种程度上还不如变成 token 的补贴给大家，对吧？因为他要购买算力，他要购买开发。我刚才如果用一个 agent 去找一下的话，可能就一毛钱两毛钱。所以把 token 送给大家，然后不要实现任何的功能，可能是更便宜的。

好，讲需求，我是讲需求的。那这样的一个系统，就是一个非常典型的业务系统。

比如说，我除了找到我的课表以外，我应该还可以找我的教学任务。这里你可以看到大家的信息，我就不点了——因为点开以后好像会显示电话号码还是什么的。这显然是一个比较糟糕的 feature，在学生名单里面可以看到电话号码。

然后在这里，上一次给大家演示过，直接用 AI 来用 slop 填满教学周底。你看没有人管我对吧，我没有任何人来审计，我填的任何内容，至少目前还没有。我觉得他们更应该把这个教室的灯给修好。

然后你就看到在这个界面里面有无穷多的功能。你看比如说有"编辑联系方式"，然后我在这里有"当前教学学期""最新排课学期""历史授课信息"，然后在这个"历史授课信息"里面，我要选择学年学期——选择学年学期不太好用，对吧？你的感觉是不太好用，又还蛮好用的。他还是做了需求分析的，对吧。

比如说"期末考试签到表"——这也是一个需求功能点。它在期末考试期间允许你点击这个按钮；在没有到期末考试发布的时候，你要弹出一个窗口，告诉你无法打印。再比如说"编辑教材"——编辑教材进入了另外一个页面，有一个弹出窗口。"再试一次"啊。编辑教材——曾经好像是是可以的。好，我们已经成功发现了一个 bug。

"查看大纲"啊。大纲是大纲说的教学安排，仅展示最新一个教学班。它等了很久才把这个页面刷新出来——这个可能不满足它的功能性需求的"要求状态正常"。

看有没有还有没有别的可以点的——我就不用 A 键的点，我还是用古法方式来点。

这是我的教学任务。然后和本科生相关的还有很多功能，助教。比如"我的助教"——我这门课好像没有助教。我能搜我的名字吗？不对，这是学号。这个是我班上的助教。找不到？课表内教学班没有助教。

这是什么？让我瞧一瞧。咳咳，在这里我看到了一些……JX。太厉害了，教学班名称堪比 agent，对吧。

"搜索"——就看到这个需求是不断叠加的。因为曾经是没有慕课这样的功能的。毫无疑问，在疫情之前是没有慕课功能的。然后在疫情的时候，领导说我们需要为老师添加慕课；添加完慕课以后需要慕课的助教；而在慕课的助教里面，不要把它当成普通教学班的助教，要把它当成慕课的助教。然后就有了这个——这是个史诗级的 bug。我不知道为什么，但是这是一个史诗级的。

然后我点删除，可以吗？好，点新增，可以吗？"请在可维护时段内操作课内教学班。"——新增，请在可维护时段内，现在不能，已经不能申请助教了。

Anyway，这就是你看到的教务系统。所以你们就理解上一页我说曾经很难讲：你们不会去见真正的客户，你们可能也不敢拍胸脯说——"这个给我 20 万，我找几个同学，我们把这个南大的教务系统给包了。"你承担不了这个责任，对吧？他到时候跟你签一个合同，然后你说你如果逾期交付的时候、达不到功能要求、达不到非功能要求的时候，怎么办？——你就傻眼了。

当然，你们作为一个成年人，你们是可以去成立自己公司，然后去和学校签订这样的协议的。但是你们不敢不要紧，agent 他敢就行。

#### 让 agent 爬出一份需求说明书

所以我干了这样一件事。我让 GPT 帮我就用 agent 爬一下、去探索一下这个教务系统里面和教师相关的功能——注意，只是教师相关的功能——然后得到一个需求说明书。

好，我们来看一看，这份需求说明书还是很不错的：《南京大学本科教学服务平台需求说明书》。这就是一个真实的需求报告的案例。你们可以在软件工程的课上看到这样的案例，软件工程课上可能也会给你们看一些来自真实企业的需求说明书的一部分。但这个就是真的。

所以 AI 真的是很好用。你要学东西的时候，如果要教需求工程，我当然可以找一个经典的案例，那我也可以把身边的案例直接变成需求说明书。

```text
《南京大学本科教学服务平台需求说明书》
│
├── 调研方法
├── 证据边界
├── 业务目标
├── 成功标准
├── 详细用例规约
├── 功能需求目录            ← 每条带编号 ID，traceability 就挂在这里
│   ├── 门户与身份
│   │   ├── 检索和应用入口
│   │   └── 身份选择：服务支持多种已分配身份时，
│   │                  提供身份选择并显示当前身份
│   └── ……
├── 验收场景
├── 需求清单（结构化 checklist）
└── 术语文档与配套文件
```

好，你马上就发现这个目录里面有这么多项：从调研方法、证据边界到业务目标、成功标准，到各种各样的详细用例规约、功能需求目录，最后还有术语文档与配套文件。

所以你看，GPT 是懂软件工程的——他为什么要写这么多？在我们看来，这已经是一个做好的系统了，这完全是 slop，就突然间写了好多好多的东西。

> **结论**：但他懂得：如果你要做一个真正的工程，当你面对的是客户的时候，一个术语就很重要——在他看不懂的时候，他可以去查一下术语，他就对齐了。虽然你不是 UML，不是一个还在早期的意图沟通的阶段，但是这些东西显然是有一定用处的。

需求功能的目录，他是有 traceability 的——里面的每一个需求遵循了一个比较好的软件工程的规范。比如说前面是不是有叫"角色"，或者说参与者、或者业务目标。他都有一个形式语义，而这个形式语义可以帮你建立 traceability。

而不是说"我这个教学班是和学生管理有关的"——你用自然语言肯定是说了这样一句话的，但是他用有编号、有形式意义的 ID，就一定程度上帮你做了 traceability。

我们来看一看功能需求。"门户与身份"——提供分类服务检索和应用入口；当一个服务支持多种已分配身份时，提供身份选择并显示当前身份。你看，当你真正做软件的时候，这个复杂的就来了。你可以不说这些，这些你都不说，但是到底有还是没有呢？

他应该是观察到了身份选择。诶，我就不登录了——刚才在那个本科生、我在选择教师课表还是哪一个界面的时候，确实看到了，他让我选。反正我选了底下那个，本科生/教师。但在多种身份的时候，服务页面明确当前学年学期，允许在授权范围内切换。

这其实也是一个设计，就在意图阶段：你的领导想要——不光是领导，还是一线的教师——说我打开这个页面以后，什么样的界面对我来说是比较舒适的？所以你看，刚才那个交互系统还是有一定的设计感的。它认为你做这件事情的时候会想要做什么，然后它会留一个 dropdown 在那边，你可以选那个 dropdown，然后选一个学期，或者选一个什么东西——教学周次、课程与大纲、教材选用。

好，我就随便看一看。这些东西你根本不想干，因为你做这些事情，对你获得学分、获得绩点、获得长进，看起来没有什么本质的好处。你还不如去做一道你之前没有想过的算法题，使你解决算法问题的能力高一点，使得你在最后保研机试的时候可以比别人多拿一点分数。而你在这里面一个一个条目往后写，是非常 nonsense 的，你自己不会想去写。

> **结论**：但是量变引起质变。

你的课程作业也会给你一个需求文档。你看 OJ 一直都是一个非常短的需求文档，明确给你输入接口是什么、输出接口是什么，而且那个输入输出的接口都很简单——一般都是输入一个整数，或者空格分隔的整数，你只要用 `cin` 就可以输入了。

你们在计算机系统基础课上，第一次见到一个比较长的 specification guide。它的需求要求是：你要实现一个 NEMU。你的第一个 lab 可能是实现一个调试器——这个调试器你不需要事先解释指令；第二个实验你需要实现指令的解释，这也是一句话。但是到底什么是指令呢？指令的行为写在文档里——于是你就得到了另外的一个更大的需求文档。

所以其实，当系统走到大到一定程度的时候，你们做的训练都是相通的。你在计算机系统基础这门课里面，其实一定程度上学了软件工程。

#### 只给它需求，它把系统造出来

好，然后是需求工程里面 AI 的魅力时刻了。

你看，这是验收场景，还有需求清单——一个非常好的结构化的需求清单。这个 checklist 最终你就可以把它分掉：前 20 个需求分给这个团队，后 20 个需求分给这个团队，然后就可以 track 每一个人的进度，你就知道哪一个团队落后于实现需求、落后于进度了。这个 traceability 有了以后，你作为一个管理者就可以把团队管起来了。这个当然，这是我们本科上课的时候不怎么学的。

AI 的魅力时刻就在于——我又干了这样一件事。我让 GPT 起一个 sub agent，然后这个 sub agent 不要看任何的其他的教务系统，只根据这份需求说明书，来实现一个假的教务系统。

然后就得到了一个……突然你又有信心了，对吧？觉得好像我也可以 20 万跟学校谈一个合同了。

真的还就是还跟我刚才看的那个挺像的：返回到全部教学任务、我的教学任务、本科教材管理、软件工程实践者的研究项方法、编辑记录。我看这能不能编辑。演示数目，一保存记录——哦，记录已保存。这个成功的保存了。学生名单。

诶，这是 GPT 起名字的偏好，对吧？它认为在这个我的教务系统里面，这些名字其实挺文雅的。然后你又觉得它有自己的偏执。

而且它没有阻止我：我记录一个缺课，这个其实也不合理，对吧？因为这个数字已经超过了这学期上课次数的总和了。

> **结论**：这就是软件工程的魅力时刻——当你的需求是清楚的时候，当你的需求文档已经写到那个程度的时候，那么编码的事情、traceability 的事情、测试的事情，其实 AI 都能帮你搞定。你只需要一份需求就行了。

> **提示**：有意思的是，这份需求说明书里居然真的包含了"缺课次数"这个功能点——刚才那个假系统里，你已经能看出 AI 为什么会原样把它实现出来。但这个功能点在真实系统里发生了什么，我们回一会就会回到这里。

### 需求永远说不清楚

好，我们先给大家看一下一个从入学到毕业的教务系统——它包括了权限规则、版本、数据同步、操作留痕，各种各样这样的一个功能。你就知道了：需求无非就是通过无尽的和客户的沟通，把客户想要什么给想清楚。小到包括你要不要在界面上面放一个当前学期和学年、要不要在哪一个地方有一个修改的按钮，这些都要跟用户对齐。

因为你的用户不是你自己。

在你做设计、尤其是做需求的时候，这是 computer science 同学普遍缺乏的那种软技能：**你要有同理心**。你不是说我是一个 geek，我就假设所有人都会写程序。你要考虑的是那个教务员——那个教务员可能是本科学历，然后今年已经 53 岁了，还有两年就要退休了，对吧？一个优雅的女士。她在她上大学的时候，可能甚至都没有操作过电脑。我们要设计一个教务系统，要为她设计，也要同样为我设计、为年轻人设计。这个时候怎么得到那一张表（需求表），完全是另外的一个问题。

当然，这不是这门课的重点。这门课重点是说：当你第一步的时候——或者这么说吧，如果你真的要做一个交互系统，你就是被迫要从零开始。当然这就是行业的壁垒和经验：如果我是一个有行业资质，或者说在这个行业已经摸爬滚打 20 年的公司，我有很多这个领域的领域知识，我知道教务员想要什么；而你作为一个毛头小伙子、一个本科生，你不知道这个教务员到底想要什么，所以你设计出来的那个软件、你做的那份需求很有可能就是有偏差的。但我有这个行业的经验，我设计出来的东西可能就对学位授予的流程比你清楚，我就知道这个流程应该怎么样变成这个需求的文档列表。

但某种程度上，做软件都是被迫的。在刚开始的时候，一个空项目的时候，没有任何东西是漂移的。但当你一旦写出了一个需求列表的时候，马上——不管是 AI 还是人类——就给你实现了一版，就像刚才我们看到的那个教务系统一样。那实现完那版以后，你就背上了技术债。

> **结论**：我们的定律是：需求永远不可能说清楚。第一就是，你永远不可能真的把用户的需求说清楚；其次，需求不是一成不变的。

这是一个我这边 AI 帮我虚构的一个案例，但这个案例在实际中很可能会发生——这真的是可能在学校里发生的。

比如说我们干了这样一件事：我们把离散数学课拆开了。我们觉得大家第一门课的那个离散数学没有教会大家那个数学的语言，所以我把它拆开了。然后拆开以后就带来一个非常糟糕的后果：我们的准出结果变了，我们的保研要求也变了，然后新旧是衔接不上的。

因为以前的系统里面，我们要求计算机学院的学生如果要毕业，那就必须要选修离散数学。而现在，这个离散数学从上学期一门课，变成了上下学期两门课。那怎么办呢？我是不是要在系统里面增加一个规则，说我允许毕业，要么选修了离散数学，要么选修了离散数学一？——这就一个"或"的关系。

最早的时候，第一版本在沟通这个需求的时候，肯定没有想过这件事。当他写这个需求的 checklist 的时候，他会说什么呢？好，我们要在界面上面有一个叫"毕业要求"；在毕业要求上面，要给教务员一个下拉框、一个"增加一条"的按钮；然后这个"增加一条"的按钮可以选一个课程。这在刚开始做需求的那个时间点，当然是非常合理的需求。

但是一旦这个需求固定下来，当我们的离散数学课拆成两份了——好，完蛋了，这个东西不能适应我们新的需求。对不起，重构吧。我们再把这个需求的文档调出来：这个地方不能这样了，我要在这里加一个"或"，下拉框里加一个"或"。

```text
第一版需求：「毕业要求」= 必须选修《离散数学》
        │
        │  离散数学 1 门  →  2 门（拆成上下学期）
        ▼
需求裂缝 ①：得加一个「或」
        │  毕业 = 选过离散数学  ∨  选过离散数学一
        ▼
需求裂缝 ②：转专业的课能不能抵扣？
        │  抵扣「离散数学一」，还得再上「二」？
        │  还是一门抵扣「一 + 二」？
        ▼
需求裂缝 ③：重修的算不算？交换的算不算？
        ▼
裂缝一直叠，叠到无穷多
        ▼
系统里没有的东西，最后还是有个 override
        ▼
打电话给工程师，直接改数据库里这个同学的毕业条件
        —— 而且这个是档案可查的
```

然后每当你叠加一个这样的东西的时候，这个屎山就开始累积了。你们写过软件的都有，都懂这个。你不要紧，你让我做个东西、改需求真的受不了。因为改需求它会破坏——你做了一个整体上一致的设计，但是一旦这个需求中间产生了一个裂缝以后，它会传递到系统里的各个部分。然后当你一个看似很小的需求要改的时候，牵动了整个系统的各个部分，你就会一团乱麻。

这里面举的更多的例子：什么重修，然后还可以交换、可以抵扣——也就有些课程可以抵扣。如果有一个同学从别的院系转过来，然后别的院系又有一个离散数学课，这时候这门课能不能抵扣计算机学院的离散数学呢？它应该抵扣计算机学院的离散数学一和二，还是我要求他抵扣离散数学一、他还要再上一个离散数学二？

这就无穷多。你一旦面对这个开放的物理世界的时候，你就没有办法了。1 万个、1 万个。

最后到最后，你的系统里没有的东西，还是可以暗箱操作的，最终还是有个 override 的。因为比如说你今年 6 年了，拿不到本科学位，就是因为离散数学这门课；然后刚好你在这个时候碰到了——我把离散数学课拆成两门。那怎么办呢？现在已经是秋季学期了——或者说，现在已经是春季学期了，马上要毕业了——你已经不可能再去修那个学期的课了，它不开，它在春季学期开。

那怎么办呢？最后领导说、教学主任说：我认为这两门课之间是可以存在替代关系的。那这个系统里面最终怎么办呢？最终——打电话给工程师，改一下数据库里面这个同学的毕业条件，把它改成满足。然后这个就过去了，这个还是档案可查的。最终是教学院长认为，这个同学学了旧的离散数学，还是可以抵扣新的离散数学的——也合理嘛，就是在人类世界意义上有一个合理的解释。

所以这就是软件系统的复杂。

再说一个我自己的例子。我记得我开始上课的第一天，那应该是 2018 年的时候，好多年以前了。那个时候还是一个老版的教务系统，跟我上学的时候教务系统差不多。然后上课第一天我就发现，这个系统我没有用过，因为我以前都是学生端，我第一次用老师端，然后发现很好玩：可以给同学设置缺课次数。

我不知道为什么要做这个需求。就是如果是我来做这个需求的话，我就不会把缺课次数这个 feature 放在我的教务系统里面——同学缺课就缺课吧。你不需要在系统里留证据，只要老师比如说有一个签到表、点名表留证据，然后扫描一下，我就可以把你开除了，对吧？你们学生手册里面有写的：你们无故缺课达到多少次，就可以开除。

然后我就试着绕过了那个前端的校验。刚才你们看那个 AI 实现的质量还是不错的，我相信他前端后端也都会做校验：我要输入一个非常大的缺课次数，他直接拒绝我了。后来我把一位同学的缺课次数从零改成了一——这好像也不是什么有害的操作。

但立马我就发现了：所有只要能够选出这位同学的、这个选课记录的页面，就全部 crash 了，直接 500 就 crash 了。

然后我就只好打电话给教务，说这个交互系统崩溃了，我不知道他怎么解决。反正第二天，工程师登录到了那个数据库里面，把那个"一"的条目给修复了。然后我就知道：这就是软件系统，这就是你们真实面临的软件系统的需求。

### 没有银弹，所以第一步要做的是架构

这意味着什么呢？这意味着就只是需求只是一个 lesson——因为我其实没有办法在这门课上面讲需求和产品设计，产品设计这个可能应该是另外一门产品课，我这门课讲软件工程课，可能就这样带过比较合适。

在 AI 时代，你做 MVP 没问题，正确，对吧？而且是前所未有的容易：先优先实现那个最重要的功能；你看到一个产品，你马上就知道哪个地方设计错了，这个时候返工的成本是比较低的。

> **易错点**：但是这也给你产生了一个"驾驭 AI"的错觉。因为 AI 确实可以往后修——你迭代三个版本，AI 都是可以往后修的。但一旦你在一个真实的系统里面运行足够长的时间，比如说计算机系改成了计算机学院——当你一开始面对这些事、你原来的设计不起作用的时候，好，你就面临麻烦了。

这也是所有的软件工程都面临的问题，叫 There is no silver bullet。没有银弹。

所谓的银弹是什么？银弹就是——吸血鬼和狼人是没有办法普通杀死的，但是要有一个 silver bullet。但是，没有银弹。

随着软件的增长，你在最早的时候、第一个时刻制定下来的那些决策，会不断失效。因为你的软件要生存、要挣钱。假设这个软件不是你的课程作业——我随时可以把它清零，从零从头再做一遍。但你的软件一旦上线，它就开始和物理世界产生交火，那你就必须持续地背着这个 technical debt 维护下去。那它的成本就会因为你前面做的不够前瞻，不断地变得更糟糕。

对，这是需求。那解决这个问题的方式是什么呢？是架构。

### 架构就是控制复杂性

其实刚才我已经有一点点透露了我们怎么应对这个问题：当你刚开始的时候，你可能有一个需求；或者在 MVP 的阶段，你还没有试图把所有要做的事情都放进来。你可以想一想：我们的软件第一步迈向哪里，是对软件的长期生存有最好的效果的？而第一步你要做的，实际上是软件的架构。

> **提示**：这里说的"架构"不只是一个 MVP。刚才我们看的那个 AI 生成的 MVP，那已经不能算 MVP 了，这已经算是一个小小的产品原型了，维护它会变得非常困难。

你想要驾驭这个软件系统的复杂性，在一开始的时候就要想：我怎么样做一个最小的软件，使得这个软件能够随着需求的膨胀和改变，它依然能够一定程度上有一点韧性。实际上，哪怕是最小的代码，它都是有软件的架构的。

而这里面说白了就一个：把耦合解开。

```text
✗ 一步到位：所有东西塞进一个数据库
   ┌────────────────────────────────────────────┐
   │  需求 · 课表 · 教材 · 助教 · 成绩 …        │
   └────────────────────────────────────────────┘
   快，能 work，AI 也能很快给你做出来；
   但只要需求一膨胀，你就进维护的泥潭。

✓ 留出余地：先把耦合解开
   需求 ──▶ [需求表]        课表 ──▶ [课表表]
   教材 ──▶ [教材表]        助教 ──▶ [助教表]
   每块独立演化，改动不会互相传导。
```

比如说，一开始我就用一个数据库来存放所有的需求。如果你在一开始的时候就立即做这个决定，你可以快速得到一个能 work 的原型，AI 也能很快给你做出来。但是如果你不去仔细思考这个系统里面到底哪些概念是可以分开的，就很容易进入软件维护的泥潭。

好，讲到架构，大家都觉得有玄学，好像很高大上，但其实不是的。架构从你第一次开始设计任何的代码、任何的系统的时候，无论它多小，它里面都有一种这种架构的思维。因为架构本质上就是怎么样去控制一个东西的复杂性。而当你的代码开始稍微哪怕有一点点的规模，你都可以去考虑这个复杂性应该怎么样去分解。

```text
   argc / argv
        │
        ├──▶  逐个 string compare？ 规则越堆越乱  ✗
        │
        └──▶  getopt：长选项 / 短选项 /
             UNIX 风格参数                          ✓
             ── 复杂性被分解、被封装起来
```

你看，`main` 是有 `argc` 和 `argv` 的——这是操作系统和进程之间的约定，它会传一个 arguments 的向量，把参数以字符串的形式传过来。那你们怎么处理参数呢？一个 string compare 吗，对吧？

你就想想，如果今天在保研机试的现场，那个题目要求你处理这个 `argv`，你会 string compare 吗？然后你们就会回想起，这个世界上有一个东西叫 `getopt`。然后你们在课上看过这样的代码，在做实验的时候写过这样的代码，在别人实际的项目里面——比如你们感兴趣的那些命令行工具是怎么实现的——你会看到这样的一个代码。

它也是一个架构，它也是一个分解复杂性的方法，对吧？因为有复杂性——`argv` 本身就是一个非常复杂的东西。比如你敲一条 `npm run dev`，它本身就有很多参数，而且有些还支持 UNIX 风格的长参数、短短参数。然后在 C 的时代，你要写一个这样的 parser 是很复杂的。

## 架构长在需求上：从 getopt 到 event sourcing
> 对应块：BLK12 | 覆盖分集：P07下 | 块标题（分集名）：《需求和架构 (1) [06-Raw_26生成式软》

### 写一个 parser 有多复杂

要把一个 parser 从零写出来，是很复杂的一件事。可是在真实的代码里，你几乎见不到有人去写它——因为已经有人替我们把这团复杂性隔开了。

那个"有人"叫 `getopt`，它背后是 POSIX 标准里的**一整套约定**。它把"参数长什么样才算合法"这件事整个接了过去，穿过这一层交给你的，是一个干净的 parsing state。剩下你要写的只有两样东西：一个 `while` 循环，一个 `switch case`。这就是一种 parser 的架构模式。

```text
        argv：原始字符串
        （长短选项混排、顺序不定、平台差异全在这一层）
                          │
                          ▼
        ┌──────────────────────────────────────┐
        │        getopt / POSIX 约定             │
        │  把「字符串」消化成「参数序列」          │
        └──────────────────────────────────────┘
                          │
                          ▼
              parsing state（几个干净的变量）
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
    while + switch case              你的业务逻辑
    （参数怎么组合都已经处理完了）      （只面对简单状态）
```

> **结论**：这就是"符合 best practice 的代码"的样子。你看到任何一个好代码，它背后都有架构设计，架构背后都映射到需求。

需求这件事我得说清楚一点——我刚才举教务系统，其实有点过度了。不是要一个教务系统那种 monolithic 的东西、随时随地能做的那种。在任何一个模块里，你都可以谈需求、都可以谈架构、都可以谈优雅。

说到这儿我想吐槽一种授课方式。我很讨厌那种老登的授课方式。以前我和学院的老教师有过比较大的分歧：我们说，讲 C++ 就得讲至少 C++11、14、17 里的一些特性，以及这些特性应该怎么用——那可能要到 P1700 的时代了。老登的回应是："我讲了，我怎么没讲呢？"

他讲什么呢？他讲：好，lambda，`a`、`b`，`return a + b`，没有了。

> **易错点**：这个讲了和没讲有什么区别呢？把一个语法点念出来，不等于让学生知道这个语法点为什么存在、什么时候该用。

我在学 C++ 的时候，你们在学习的时候看到的每一个东西——不管是你在 GitHub 上找到一个好的项目、读它的 Readme，还是你就看到一个 `getopt`——你再往后想一想："这确实是一种模式。"这个模式就是把一个复杂的字符串，最后变成一个简单的 parsing state。

它是一种**抵抗需求变化**的方式。因为你的 argv 是可以变化的，argv 各种各样的变化；但是他用这个 parsing state 把这个问题给解决了。

> **定义**：parsing state——把外部世界不可控的复杂输入，先归约成你自己可控的简单状态，再在简单状态上做业务逻辑。

所以我们可以看到几个比较典型的架构。我从最小的十行代码的架构开始讲。

> **结论**：架构和需求其实是连在一起的。你没有需求，就不用谈架构。而你谈架构的时候，你面对的是一个开放的需求——为未来的需求做的架构。所以你问"我什么时候能设计出好的架构"？答案就是：**你对需求掌握到什么程度**。

### 十行代码的汉诺塔

我最喜欢的例子是 Tower of Hanoi。我以前开始上课的时候，先问我的保研研究生："哎，你让你写个非递归的汉诺塔，你能写出来吗？"研究生摇头。

所以最后它就变成了我上课的时候的一个例子。其实就这十行的代码，它背后联系到的架构，就回答了大家"为什么写不出来"这个问题。

#### 同一个 prompt，四个答案

我把这个题丢给不同的模型和不同的人，让他们写非递归的汉诺塔。

GPT 的回答是这样：盘号等于一加上步号二进制末尾零的个数，$$peg = 1 + \text{末尾零的个数}$$，然后每个盘子的移动方向也给出来。这个移动方向是固定的吗？We don't know。反正它应该是对的，你看不明白——但是 highly optimized，极度最优。

我看到它这个说法就笑了。它说得很狂："即便我不做人类了，你也写不出来，是因为你的数学不如我好。"在他看来，他找到了 Hanoi 的数学性质，数学上是对的，那我就是对的，这毫无破绽。

DeepSeek V4 flash 的回答更有人味。它写了一个非常优雅的代码，基本就是标准答案：

```text
递归的真相是什么？——递归就是栈。
把「还没搬完的那一堆任务」留在杆上，当成栈底；
每一轮只执行栈顶的那一个任务。

    ┌─────────────────────────────┐
    │  杆 A：  待办任务栈（永远在这里）│
    │  ┌───┐                     │
    │  │ n-1│ ← 栈顶，下一步就搬它 │
    │  ├───┤                     │
    │  │ n-2│                    │
    │  └───┘                     │
    └─────────────────────────────┘
       ↓ 每轮弹一个
    搬运一个盘子 → 压回剩余任务
```

豆包也选了同一个方案，但写出来有瑕疵，我就不展示了。

而我在百度上搜"非递归汉诺塔"，第一个条目居然还是递归汉诺塔；往下找到 CSDN 的第一个非递归汉诺塔，我看到了这样一份代码：这里有一个 `move`，可是 `std` 里本来就有 `move` 了。

> **易错点**：这份东西甚至比 AI slop 还要严重。而评论区还有 AI 在帮你营造一种"这个 CSDN 博客质量很高"的感觉。

如果你们在上大学的时候被这种 slop 污染了呢？说实话，你还不如跟 AI 学——跟 DeepSeek 学都很好啊。不要，GPT 已经不当人了。

| 答案 | 落在哪儿 | 我的评价 |
| --- | --- | --- |
| GPT | 步号二进制末尾零的个数 → 盘号 | 数学上是对的，highly optimized |
| DeepSeek V4 flash | 递归即栈，任务留在杆上 | 非常优雅，基本是标准答案 |
| 豆包 | 同上 | 思路对，代码有瑕疵 |
| CSDN 那篇 | 自己定义了一个 `move` | 比 AI slop 还严重 |

#### 我的架构：它本来就是一个状态机

我作为一个架构师，我想的是：为什么大家写不出来？是因为你们对递归这件事情理解得不够深。

所以我故意说，我们的程序实际上是一个状态机——回头可以去看我操作系统讲的这个课。C 语言是一个状态机，一个 single step 就是它的 operational semantics，叫**操作语义**；小步语义里，比如"汉诺塔减一"，它是一个 well-defined 的、程序语言世界里的一步操作。既然它是 well-defined 的，那我们就只需要模拟这个操作。

我完全可以写一个 C 语言的解释器。当你理解了 C 语言的解释器，你就很容易写出把任何 C 代码变成状态机的实现——我当时讲的其实是两个函数互相调用，非常容易，没有任何难度。因为你就是把这个 C 语言的小步语义翻译成一个状态机的表示。

```text
     C 语言程序（递归写法）
              │
              │  翻译
              ▼
     小步语义（operational semantics）
     每一步都是 well-defined 的状态转移
              │
              │  模拟
              ▼
     状态机表示（显式的、可回退的）
              │
              │  simplification
              ▼
     非递归的十行实现
```

这两个是等价的——如果你觉得这个代码不够优雅，对于 Hanoi 来说这是 overkill 了，因为我可以把任意的程序翻译成它，也可以做一次 simplification、从它变回它。

> **结论**：所以从我来看，这是我作为架构师理解 C 语言形式语义的好机会。

看到不同的人，就现在我还可以守住我的品位：GPT 其实可能懂，但是他可能不会往这个方向去想。所以我觉得有比较强的信心认为，强化学习可以把这个 GPT 往这个方向去引导——他一旦学会，在适当的时候也能做出这样的实现。

有意思的是，这四种表达其实是同一件事：

- GPT 跳到了数学规律那一层——一切都是数学规律，我只要把程序世界里的数学规律理解清楚，那没有问题是我解决不了的；
- DeepSeek 跳到了编程语言世界的那一层——递归是栈，这句话他在语料里学到过，他只是把人类反复说的话投射成了代码；
- 我往外多走了一步——你们对编程语言世界的理解，投射成了递归和非递归的区别，再投射成了这样的一份代码。

这就是**跳出问题看问题**。代码之外有数学的规律，数学之外有社会的规律，社会之外有宇宙的规律。你在任何一个小的地方，都能看出架构水平的高低。

### 架构的品位是从哪来的

那你们肯定想问：架构的能力从哪来？

从你学过的每一个东西上来。如果它是好的、它是优雅的，它促使了你对这个问题的思考。**压缩就是智能**——你把它压缩了，你的第一性原理（first principle）就出来了，你总是从 first principle 去推导"应该怎么样"。

所以这些能力就是你在学校里面、在社会上面的积累，共同赋予了你的能力。

举一个很具体的例子。你必须要和除了教科书、除了做题之外的人打交道，你才知道一个马上就要退休的、很优雅的教务老师，他是怎么看待教务系统的。他的想法可能和你的想法不一样。你的想法总是最好的——数据库最高的性能啊，whatsoever；但他来说，他只是想要那个字大一点，他点鼠标的时候不要手滑到旁边那个按钮上。

> **结论**：架构能力里有一块，叫**共情别人的能力**。这一块是任何编译器都教不了你的。

好，那么十行的讲完了，两千行的架构是什么样？

### 两千行：Excel 里的二维码生成器

我上课的时候讲过一个 Excel 生成二维码的例子。它可以把任何一个长的字符串，编码成一个你能够直接扫描的二维码。

这个需求非常明确：需求就是 Excel 的一个单元格——我希望在这个 Excel 里面生成一个 0/1 序列的单元格，它有一个输入的单元格，有一些输出的单元格。就非常非常 deterministic 的任务。

但这里面是有架构的考虑的。

> **注意**：顺便讲一个挺好玩的事——agent 对自己的能力到底到什么程度是有估计的。所以当这个任务足够困难的时候，它会"不做了"。比如你说：你有两个 sheet，第二个 sheet 里是我的学生的实验成绩，第一个 sheet 里是我填好的期末考试成绩，你给我写个公式，把学号对应的实验成绩拉过来——这在它能力范围内，它会一把梭。但是明显超出它能力范围的，它还是会试图去分解这个问题，它也会做架构。不过至少今天的模型，在做架构这件事上，稍稍是有一些落后的。

如果 AI 直接给你写成一条 Excel 公式会怎样？你会得到一个笑话——我们"偷"了一个 Lisp 程序。因为这个公式实在是太长了，Excel 的计算能力又有限。就好比让你们用 brain 去实现一个 nontrivial 的程序，什么毁灭战士级别的游戏，那你写出来的程序就会是这样。

这个时候你就需要一个抽象。而且——AI 之前给我看的两个版本都没有考虑到：**这个需求看起来明确，但其实有很多坑。**

#### 坑一：Excel 本身在演化

Excel 是有版本的，我们知道 Excel 从 2019 到 2023，不断地增加新功能。

我刚才讲的那个需求，叫"去查找学号对应的成绩"，以前是一个叫 VLOOKUP 的函数。有没有同学知道？——没有同学知道。说明你们都不是 Excel 的 power user。太好了，你们是 agent 时代的第一类人：你要干什么，只要跟 agent 说就行了，你永远永远不需要再学一个像吃屎一样的语言了。

然后微软大概终于在某一年受不了了，推出一个新的叫 XLOOKUP，可以更方便地查找。

你看，Excel 是在演化的。那么马上这个需求就会变得模糊不清：**我到底是应该兼容一个旧版本的标准，使得我在各种人身上都能打开——我发给那个教务老师，教务老师也能打开这个二维码？还是我要做一个我自己用一用即抛的，那我就可以用最新的语法实现最简单的公式？**

那到底是哪个呢？

```text
   如果需求变了，你的代码维护是极度痛苦的
   ─────────────────────────────────────────────
   AI 给你 vibe code 了一个「Excel 2023 公式」的实现
                        │
                        ▼
   突然有人说：「2023 不行，要改成 2019」
                        │
                        ▼
   再改：「再改成 2003 这样的老版本」
                        │
                        ▼
   全完蛋。设计和实现从头回到原点，重新再做一遍
```

#### 坑二：单元格位置是需求

再比如，我的需求可能是我最后出来以后，我对它的位置不满意，我要把它整体往右移一格。如果你所有单元格都是硬编码的——就直接立即崩溃。

> **结论**：你看到它对需求变更的抵抗，是很糟糕的。

那对于一个 2000 行的项目来说，这个是 OK 的，你可以重做。但是如果这个 2000 万行的项目，已经嵌入到了一个巨大无比的需求、嵌入到教务系统里面，和其他部分产生关联的时候——加钱，对不对？那你作为项目经理说话：我要加人，我要加钱。对，我没办法，我只能用这个方式来满足你的需求。

但这显然就是一个架构没有设计好的。

#### 跳出问题看问题：这是一个编译的问题

正常是这样的。（我先把这个关掉。）

这个问题本身是清楚的，二维码是完全有规范的。AI 给了一个伪代码，非常短。我给你们念一下它里面有什么：

- 版本、纠错等级、掩码、大小；
- 数据编码，把字符串变成码字；
- 一个纠错码：把 data 乘以 $x^{26}$，在生成多项式上取模，$$c(x) = f(x) \cdot x^{26} \bmod g(x)$$；
- 134 个码字，最后加上一个 ECC；
- 最后直接把这些码字放到空间里。

```text
   字符串
     │  ① 数据编码（版本 / 纠错等级 / 掩码 / 大小）
     ▼
   n 个码字
     │  ② 生成纠错码  c(x) = f(x)·x^26 mod g(x)
     ▼
   数据码字 + ECC
     │  ③ 铺进矩阵
     ▼
   0 / 1 矩阵  →  扫码枪一扫，字符串回来了
```

那为什么这么简单的东西，在 Excel 里面实现就这么困难呢？这个 gap 到底在哪里？

如果你跳到问题外面，你就很明显地看到：**二维码容易用算法来描述**。这个过程我用一个 Python 就再容易不过了——明年保研机试我就出一个这个题，让你去实现，最后打出一个 0/1 矩阵。如果要考综合能力的话这是一个不错的题目。

但是我们的要求是 Excel。

我们不存在任何一个翻译器、一个编译器，可以把一个 Python 编译成 Excel。这显然也是做不到的——Excel 它本质上是为了财务、报表这些而设计的；管理学生成绩是一个小的数据库，它本身就不是为了做 Turing complete 计算来做的。所以没有一个 py-to-excel 的编译器，叫 PYXL，这个东西不存在。

那么如果我们直接把它变成伪代码，或者是自然语言，然后用 LM 去编译呢？那我们也看到了这个 LM 的问题了：它直接上手就做，做了；然后需求漂移的时候，就会遇到很大的问题。

### 一份中介语言，两种执行方式

所以你马上就知道：如果我有个好的架构，我是不是可以在 Python 和 Excel 之间构造另外一个语言？这个语言它既可以很容易地翻译成 Excel，又可以继承一定的 Python 的功能。

就是刚才那个伪代码——我希望我要的东西，其实是一个**中间的编程语言**。这个语言能够支持描述这些运算中需要的东西，然后它这个语言又可以翻译成 Excel。

我就做了这样的一个设计：这样的语言可以翻译成 Python。你们都写过那种表达式求值的程序对吧？我就是做一个表达式树。比如说我说"异或"、加什么 AB；或者是取出一个字符串里面的某一个字符——这就是一个小的编程语言。

这个语言显然很容易翻译成 Python：你直接把它 dump 出来，递归地左子树、右子树，然后根据这个节点拼起来就好了。

这个语言也可以翻译成 Excel：我只要要求**每一个节点都有一条翻译成 Excel 的规则**，我就可以把这个东西放到一个格子里——任意的格子都可以——然后把这个结果放到一个格子里，那我就可以在这里做出两个格子拼起来的结果。

```text
        需求：Excel 里生成一个可扫描的二维码
                        │
                        ▼
          LLM 生成「中间语言」程序（表达式树）
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
    翻译成 Python                 翻译成 Excel 公式
  （逐节点递归，验证语义）     （每个算子一条「落格」规则）
          │                           │
          ▼                           ▼
   公式写对了吗？                 交付给用户
          │                           │
          └──────► 对了才往下走 ◄──────┘
```

> **结论**：你看到这样的架构，不就是我们刚才在那个最小的例子里讲的 `getopt` 吗？写一个命令行工具，第一件事情先 `getopt` 得到一个 parsing state，再从那个 parsing state 出发去做下一步，一样的设计。

所以你们作为一个 unsupervised learner，作为神经网络——大家神经网络你就是看好的东西，你看得多了，你自然就能泛化了。当然你看得多的时候，你要有意识去意识去看好这个东西：**为什么要这样**。你回头突然有一天会想通——看到某一个 blog，或者有一天听我上课的时候，突然就想通了一件事：哦，原来这个世界上大家做的事情都是差不多的，就是在做一个中介语言、两种执行方式。

这个架构上我还可以发展出优化。我是一个语言，如果我觉得性能不好，哪个地方生成了太长的代码，我就有一些改写的规则，我可以把一个程序从一个形态改写成另一个形态。

比如你们都知道，如果我有一个变量在循环里面每次都计算，但它们的值都一样，我就可以把这个变量的计算提到循环的外面。编译器可以自动做这件事，语言模型你也可以手动把这个计算给移出去——你可以做手工的优化。而如果我有一个中间语言，我就可以让大语言模型去优化它。

然后是 profiling guided optimization——你在计算机系统里学到的这个概念：你要先知道性能瓶颈在哪里，然后再用性能的 profile 去指导你的代码应该写成什么样。你的概念又用上了。

所以一个好的架构，可以承载需求的变化。未来 Excel 如果版本改了，没问题啊，我无非就是把一些算子用另外一个方式去实现。

哦对，然后你讲到算子的时候，你发现今天的 AI 推理也在干这个事，对吧？人类就是这样。他们因为有很多领域的知识，所以他们领域里面有非常多好的设计，这些都是非常值得大家学习的。

### CRUD 为什么会让人这么放心

那这样的一个架构，来自什么样的基本原理呢？

我们的软件是**物理世界过程在信息世界里面的投影**。而我们的物理世界是有状态的——everything is a state machine，我自己也是一个 state machine。所以软件系统它很容易会建模成一个 state transition system。

它有一个状态，而这个状态一般来说是用数据库——persistent 的状态是用数据库。比如说我可以用一张表来表示学生：学生有学号、姓名、院系等等。然后我还有一张表表示学院，一张表表示选课……反正各种各样的东西都可以用二维的表来表示。这是你们在数据库课上面学过的。

```text
   物理世界（有时间、有历史、会变）
              │
              │  投影
              ▼
   信息系统：持久化的「当前状态」= 一组二维表
              │
              ▼
   任何时刻打开网页 → 当前状态的一个 consistent 视图
```

然后数据库要求你消除这个表里面所有的冗余，要把这个数据库 factor 成 normal form。什么意思呢？

你最好不要在学生表里放一个课程。举个例子：学生有一个学号，学号是唯一的，比如 1234；那学生还有个姓名。如果在另外一张表里要引用一个学生，尽量不要用姓名来引用——因为姓名学生可能会重名；然后就算不重名，这个也会带来一些麻烦。

更好的做法是：把姓名的这一列从这张表里面去掉，而是这里放一个学生的 id，比如 1234。这个 id 就相当于一个链接，这个链接指向了学生的信息；然后这个学生还可以再指向别的表里面的某一些信息。

这样就是**把冗余给铲除**，把冗余的 dependency 铲除掉。我一个地方改了以后，我不会需要改另外一个地方。因为如果这个学生真的改了名字——这件事情在中国是合法的——你现在用这个分解的方式，学生改了名字，你把这个名字改掉就行了，你记一个曾用名；但如果你是这样的两份、存了两份名字，那对不起，你这两个地方都要修改。这就是一个很大的、很大的代价。

然后我们一般来说会把这样的世界建模成状态。任何时候这个状态就代表了在现在这个时间点上，南京大学有哪些学生、有哪些学生选了哪些课、有哪些老师。

然后每当我们这个信息系统——前后端分离嘛，这也是一个非常经典的架构——比如说今天我选择退学，因为我没有买到 token，我选择退学。那就是一个 update 数据库的过程，然后它就从一个状态迁移到了下一个状态。在这个状态里 A 还在，在下一个状态里面 A 就没有了，A 这个记录就不存在了。

那这就是一个始终是 consistent 的视图：你永远在交互系统里打开那个网页，就看到这个东西的一个投影。这是非常经典的架构，没有任何的错误。

### 但是当前状态把历史全丢了

但是，如果我们想想：教务系统为什么不适合这样一个 CRUD 的架构？

因为当我看这个当前状态的时候，我看到的是一片祥和的景象；但是——**这个当前状态把所有的历史都丢掉了。**

```text
   退学（没买到 token）
        │
        │  CRUD：一次 UPDATE
        ▼
   ┌──────────┐   ┌──────────┐
   │  状态 S0 │ ─►│  状态 S1 │   一切正常，视图一致
   │  A 在    │   │  A 不在了 │
   └──────────┘   └──────────┘
   ✗ S0 和 S1 之间到底发生了什么？没有留下任何痕迹
```

比如说如果我真的在某一个地方，学生的姓名存了两次，这是非常正常的。在某一个表里面，姓名、学号存了两次——因为这可能是一个字符串嘛，然后这个字符串就是"学号 + 姓名"，加当时授予谁谁什么东西，他用这个跟授予人没有用关联的方式，而用一个字符串写到数据库里了。那这个时候，数据库内部就发生了一个不一致。

所以比如说 GPT 给了我一个例子：学生表里面有一个 column，它就叫"是否允许毕业"。

比如说你们现在再上我的课，学分应该还不够，所以应该都不允许毕业；有的同学学分修够了，就允许毕业。而这个"是否允许毕业"是有很多其他的状态算出来的，因为之前有触发：每当你修了一个学分，或者你的毕业设计状态改变的时候，它都要重新计算一遍你能不能毕业的逻辑。

这个对信息系统来说很重要：教务员老师、辅导员老师，需要能够在教务系统里面导出到现在还毕不了业的学生，才能找你一个一个谈话。他必须要在教务系统里才行——这是个很典型的需求点。

但是这样的东西，是历史上的计算的 dependency，然后它们随着当前的状态都没有了。你知道这个学生可以毕业，但是你不知道他为什么可以毕业；你知道他不能毕业，你不知道他为什么不能毕业。

> **结论**：这个计算的过程丢掉了。而计算过程丢掉，这个软件又是现实世界物理过程的一个**有损的投影**。

那么最后导致的是：物理世界里面我建模不了的东西，全部都需要通过其他的途径来解决。

今天政策更新了，领导批准了，但是新的培养方案还没有导入到教务系统——你们经常遇到这个问题，不一致。物理事件已经发生了：培养方案已经通过了，学期已经开始了，我已经上课了，这个没有灯。物理世界已经发生的事实在系统里面没有建模。

然后在系统里没有建模的时候，"比如说这个教室还不能用"——就第一周很典型，第一周整个仙林这一片都还在修，教室不能用。这个显然教务系统没有建模。这一点最后就靠他们手改：重新安排教室。第一周我就去另外一个教室上课了。

然后这样慢慢、慢慢，随着时间的积累，你的系统里面会有大量不一致的数据。随着时间变成无法解释的黑洞：明明这个同学没交学费，应该毕不了业的，他为什么毕业了呢？明明这个同学不该毕业的，他为什么毕业了呢？突然回想起来的时候——系统里面就无数无数这样你想都不能想的不一致。

> **结论**：所以你们在面对这种需求的时候，CRUD 就会死。

### 系要改名，数据库就得迁移

因为南大院系发生调整的时候，这个教务系统就瑟瑟发抖了。因为它还是这样的 CRUD，它是一个 point of truth——所有的事实都在这儿。

那好，我们的 department 变了。我应该把旧的这个 department——我这个世界里实际上是一个对象，虽然是表，它还是对象——这个表就叫"计算机"。那我要把它的 name 从计算机系改成计算机学院吗？

**要，也不对。不要，也不对。**

```text
   ┌─────────────────────┬──────────────────────────────┐
   │  改：把对象改名      │  不改：保留历史对象           │
   ├─────────────────────┼──────────────────────────────┤
   │ 计算机系 → 计算机学院│ 计算机系 保持原名              │
   │ 当前状态确实对了     │ 历史状态确实对了              │
   │                     │                              │
   │ 但 2011 年的毕业记录 │ 但所有 department id 仍指向    │
   │ 变成「2011 年毕业于 │ 旧对象，仍得做一次数据库      │
   │ 南京大学计算机学院」 │ 迁移，并想清楚新旧对象的      │
   │ → 事实不符          │ 关联关系                     │
   └─────────────────────┴──────────────────────────────┘
```

你把这个 object 改了，计算机系现在确实是变成计算机学院了。但是这意味着我的毕业记录——如果我 select 到系统里面查询，我就变成了"2011 年毕业于南京大学计算机学院"。这就属于事实不符了，因为我在 2011 年的时候，这个"计算机学院"它生成了一个系统里面给我生成打印什么证明的时候，给我生成了这个。好糟糕。

然后如果不变呢？也很麻烦。因为你现在所有的 department id 都指向这个学生的 department id，都指向计算机系，还是得把它改过来。你需要对它做一个数据库的迁移：你要创建一个新的对象，然后新对象和旧对象之间的关联关系，你还要把它考虑清楚。

所以你看到，如果你假设这个世界就是这样的、这个投影不变了，CRUD 当然是一个完美的架构。但是只要你假设这个需求会发生**摧毁性的变化**，那么这个数据库你每次都要这样想：每次都会涉及一个数据库的迁移、业务逻辑的重写。

代码是可以重写，但是你的历史——因为历史消失了吗？我们说这个，因为这是一个 database 的 transaction，对它 update 完了以后，就从这个状态彻底地挪到了新的状态。

你做一次数据库的迁移，你就要考虑历史上所有可能发生的情况。而且何况这个数据库里面已经有很多的不一致了，你很难写出一个规则来迁移；你还要冒着数据库迁移完了以后、这个数据库就坏掉的风险。

就像我把选课给改成一模一样——因为你在你的测试环境里面做一次迁移，和你把一个学校里面所有的数据都做一次迁移，这个难度是完全不一样的。

> **结论**：所以你们就理解了，为什么到现在为止，软件的设计、实现，ERP 这类的系统——不管是教务系统——它的设计、实现、维护都是**手艺活**。

我调侃这个教务系统做得不好，它确实有做得不好的一面；或者不好意思说错了，它确实有做得不好的那一面。但是你反过来想：它作为一个软件工程的实践者，这个公司可能在 2000 年的时候成立了，然后在 2000 年成立的时候，他做的唯一的选择就是参考一个已有的企业架构，来做一个教务系统，来抢占教育市场的第一桶金。然后他把这个东西做出来了——做出来以后，他就是一个 CRUD 的系统。

那他一旦背上这个技术债，他就要在中国大学教育改革这几十年的时间里面，不断地扛下所有。所以这是一门手艺。

### 我室友接的那二十万

后来这个事维护不下去了。我还记得我们当时刚读 PhD，那是我的室友，我就经常跟他抬杠。我会跟他聊这个研究生院的系统是怎么设计的，然后我就经常喷他，因为他是一个非常典型的 CRUD 架构。我说，你最后会面临各种各样的问题。

果然，就在那几年，我们的研究生发生了巨大的扩招，然后很多管理上又多了很多研究生的类型、培养的类型，然后研究生压力又很大，经常会有这种调整。这都是他们在做需求设计的时候始料未及的。

然后最后那个系统就彻底变成屎山，然后就……反正就不存在了嘛，现在统一变成公司维护的这个系统。他们还是有一些领域知识，知道这些系统应该怎么把屎山给扶起来。

### 重做：先有事实，再有状态

但是如果我要重做一个教务系统的架构，我会怎么做呢？

我就会看到这个 single point of truth 太危险了：它一旦你有任何的不一致，你都不知道应该怎么样把它拿出来。

然后你就想到数据结构。课上讲过一种非常神奇的东西，叫 **persistent data structure**——它可以得到这个数据结构所有的历史。

也就是说你存一个数据结构，你存一棵树——好，这就是 CRUD。你看，数据库也是一个数据结构吗？你当前就是存一个库，然后你对它做一个操作，它就到下一个状态，这就是经典的 CRUD。

但我还有另外一种：我可以一开始只有一个节点；然后有一个节点以后，它这个数不变了，那我就把这个节点放过来；如果我到有一天比如说这个数变了，我要在这个节点上新建一个，那我就把它从根的路径上面长出来一个，然后它的左子树可以指向它。这个数无论多大，我其实都是可以存下来的。

然后我还可以**存状态**，也可以**存操作**，也可以**存状态的这个 delta**——这三种视图是等价的。

你看，我存它的日志——就是一个 write-ahead 的 journal，你们在数据库操作系统课上都学过。然后你存它们的 delta——存 delta 就是 Git、SVN 这样版本管理里面的思想。然后你存这个状态，当前的状态就是 CRUD。但是他们都可以帮你回放历史，得到当前的状态。

| 视图 | 存的是什么 | 怎么拿回当前的状态 |
| --- | --- | --- |
| 状态 | 当前这一个快照 | 不用回放 |
| 操作 | 事件的日志（WAL / journal） | 从头 replay |
| 增量 | 状态之间的 delta（Git / SVN 的版本管理） | 从旧版本一路 apply |

所以如果你想要设计一个更好的架构，最好是先把干的所有的事情都先记下来。

**今天张三退学了，今天张三又复学了。**

你可以假想这个世界是：之前没有"复学"这个操作。就是把张三从这个数据库里面抹掉，好，抹掉了它就抹掉了。他可能有一些记录就删掉了，你要把这些和他、其他部分的关联重新给建起来，那你就得付很大的代价。

那你要加上"复学"这个操作——对吧，他又买到 token 了。然而如果你是用比如说记录所有的操作的方式，你就可以知道：通过 replay 可以知道张三复学前的状态是什么，然后你再把这个状态拿过来——他没有丢。

然后你要注意一点：你的逻辑是**不能减少**的。即便使用记录日志、记录历史的方式，你比如说"复学"这个事情之前没有考虑过，我依然是要为他写一个逻辑。

但是——因为**事实是不可篡改的**，你世界里面所有东西都是对事实的投影——那你好像就有底气了一些，你就不怕错了。你就不会像刚才那样说：我要做一个数据库迁移的时候我手在抖。因为你总知道，你任何一个做错了的，你都可以很快地回到过去的一个快照，然后我把这个逻辑怎么做修复啊，再来。

```text
   事件流（事实，不可篡改）
   ─────────────────────────────────────────────
   E1 入学  ─►  E2 退学  ─►  E3 复学  ─►  E4 结业
        │           │           │            │
        ▼           ▼           ▼            ▼
       S1          S2          S3           S4
   当前状态 = 把相关事件 replay 一遍

   院系调整也是一个事件：E0 计算机系 → E₀ 计算机学院
   「2011 年毕业」= 只 replay 到 2011 年那一刻的事实
```

然后你也可以看到，计算机系、计算机学院的问题相对来说也好解决一些了。

我可以在某一个时刻发生了一个事件，叫这个院系调整。然后你查询一个过去的人的时候，你会查询到他过去的版本，并且你知道他经历了这个。比如说你如果要查询他毕业时候发生的事情，你直接查他毕业时候的那个状态就可以。然后如果你想要得到一个他比较新的信息，你可以投影出和这个人相关的历史：比如说这个同学 2007 年入学，2011 年毕业，然后到这都是计算机系，然后计算机系在 2014 年改为了计算机学院。

你看到，我可以裁出一个……就是总是你总是可以想要得到一个事实：当前的事实你可以裁出一个和事实相关的历史，然后把这个相关历史 replay 得到我现在要的状态。我可以查询过去，也可以查询现在。

> **结论**：这就是一个好的架构设计。然后你祝贺你——你就发明了一个叫 **event sourcing** 的、非常经典的设计模式。

它的想法很简单：**从历史事件生成状态，而不是直接维护这个 CRUD 的状态**。

你们可以回去，在 agent 的带领下去了解一下。

### 一些收尾的话

你马上会反应过来，是不是会有性能问题？因为要大量地 replay。但这都不是很大的问题，我们总可以比如说用快照缓存，各种各样的一些优化技巧。

然后这是一个——比如说，你已经在屎山上了，你把它变成一个 event sourcing 的设计，就会变得很困难；但是如果你从一开始就做 event sourcing 的设计，很多事情、很多问题都不会发生，你就能比较好地解决。

然后这样就有了很多这种 fancy 的软件工程概念。什么 CQRS 啊，这是 Command Query Responsibility Segregation——但这和 event sourcing 是独立的。还有这种什么 Domain Driven Design。

然后其实你们都不需要——你们可以去看——但是你只要回到这个最初的 first principle：你要设计一个五十万行的教务系统的时候，我们跳出这个问题，看到教务系统根源的问题在哪里，你就能做一个正确的架构设计。

> **结论**：哪怕你没有听说过这些，你也能做一个正确的架构设计。

### 本讲提到的题目

明年保研机试，他打算出一道这样的题：**实现二维码的编码，最后打出一个 0/1 矩阵**——一个能直接扫出结果的二维码。他给这道题的评价是：如果考综合能力的话，这是一个不错的测试大家能力的题目。而眼下这个 Excel 场景对同一件事的要求是——必须在 Excel 里落地。

题目的解析在正文里已经给出：整个过程并不长，无非是"数据编码 → 生成纠错码 → 铺进矩阵"这三步。纠错码那一环是 $c(x) = f(x) \cdot x^{26} \bmod g(x)$，在 GF 上对生成多项式取模即可；他当场看到的实现里是 134 个数据码字，算完 ECC 之后一起铺进矩阵。之所以在 Excel 里会变难，不是因为算法变难了，而是因为 **Excel 本身不提供从"算法"到"公式"的那条通路**——没有 py-to-excel 的编译器，PYXL 这个东西不存在。所以真正的考点落在"你能不能自己造出这条通路"：能不能为每个中间语言的算子写出一条翻译成 Excel 的规则，然后用 Python 那条执行路径去验证它的语义。具体的版本号、纠错等级、输入输出格式他当场并没有给定。
