## 从空目录到 Git 仓库：版本控制的第一性原理
> 对应块：BLK05 | 覆盖分集：P04上 | 块标题（分集名）：《软件仓库管理 [03-Raw_26生成式软件工程》

### GPT-6：又惊喜，又要挨骂

前几次课我们讲怎么用 AI，讲怎么把它整合进你生活的流程里。你们在生活中会遇到无穷多这种不顺心的地方，用什么都觉得别扭；但 AI 作为一个非常强大的 assistant，它可以帮你把不顺心的事情给挡掉——你只需要告诉它你的意图，真实的意图是什么就可以了。你甚至还可以把它蒸馏成 skills，让这个过程变得更平顺。

在这个过程当中，我们不断看到新模型的进展。GPT-6 是真的发布了，我用了一下，还是有惊喜的。

先说不太好的那一面。编程上的提升有限。我一直觉得，模型要能真正帮上忙，靠的是两样东西：一个是有经验的软件工程师，另一个是有比较好的品位——品位可以指导 AI 做出更好的东西。但现在 AI 更多的时候只是在完成任务，好像 GPT-6 还没有学会这种非常好的品味，我经常还要骂它。所以我觉得我可能还能再苟活几个月。

但它各方面的能力确实都提升了。而且做更复杂的任务时它变快了，省很多 token——我特意 measure 了一下，还真的是这样。

那为什么我们会觉得它做得不好？这也是我们要在这门课上讨论的问题。因为我们面对的是一个非常开放的 intent / specification 的空间。打个比方：如果你告诉我"给我做一个国民级的应用吧"，那么每一个人——哪怕是顶级的产品经理——脑袋里想的都不一样。AI 是没有办法和人脑去做直接对齐的，所以它总一定会按照自己的方式去漂移。

还有一个我很在意的观察：**AI 写出来的代码，人类越来越难读了。** 我不确定是不是受它思维链变短的影响——GPT-6 的思维链变得非常非常紧凑，然后现在写出来的代码也非常紧凑。你很明显地从 GPT-5 到 5.6 再到六，写代码就写得越来越越来越紧凑，然后你越来越不想看它，人没有办法 review 那个代码。

> **注意**：以前我们会各种各样的 prompt AI，说"你写出符合这个人类工程规范的代码"；但好像现在我们再也不会看 AI 写的代码了。所以就随他去吧，他反正能把代码弄对。

那 GPT-6 给我最大的惊喜是什么？是他的空间感知和理解的能力。

我一直认为 OpenAI 对 AGI 的理解是这样的：**首先 AI 得学会数学**，因为数学是所有人类世界里面最难的那一种语言。数学有一个别的领域都没有的性质——世界上所有人都认同的推理系统。你证明出一个定理，全球的人都会认为这个定理的证明是对还是不对。所以它是一个非常好的、能 grounding 的东西。

而且数学的逻辑推理可以解释我们人类生活里的各种行为。比如你会不会觉得，"今天中午吃什么"是一个人类世界的问题，必须是你的灵魂来给出答案？其实不完全——因为你的大脑里面其实不停地在投票。比如说我就会选择在逸夫楼订饭，因为对我来说这是最快的选项，因为我下午还要开会；如果时间来得及，我中午还能小睡一会儿。你看，我其实是在各种因素之间投票。而在这些因素之间——比如说"什么事情 A imply B，如果我做了 A 就会做 B"——这其实是一个数学的东西，我可以 ground 到你们在离散数学里学的命题逻辑里面的各种东西。

所以 OpenAI 应该是说：我先把数学学好。现在数学它已经学会了，然后学会了以后再强化学习别的能力。

空间感知，我从来不觉得它是绝对学不会的。你看我们小时候做过的那些智力题：给你一个鲁班锁那种很复杂的结构，问你按照什么样的方向可以把第一块东西给抽出来；或者给你一个立方体、一个奇怪形状的投影——benchmark 里就这样的——问哪一块和它一样；或者给你一个六面的骰子，问哪一个展开图对应它。你看到那个骰子，然后就在你脑袋里做这种空间想象。这种空间想象，你只要从简单的任务开始给它强化学习，肯定能做到。

当时我看到这个例子的时候，GPT-6 还没有发布，我就心疼我的 PhD student——我们已经做了小半年的 3D 打印工作了。在 GPT-5.6 空间感知能力很差的情况下，我们可以通过直接对话，生成一个还是很像样、而且各方面都能符合规范的这个 3D 打印模型。我们还是有些比较 killer 的 application。

比如说我们可以做一个小的光栅玩具——不知道你们有没有玩过，就是那种从左边看和右边看是两个不同图案的东西。你可以说"我要做这个"，以前我可以写一个很长的搜索树帮你把它做出来；结果昨天 GPT-6 one-shot 直接就出，直接搞定。

同样是因为他有了空间感知的能力，又有数学的能力以后，他在具身赛道就明显可以做得很好。所以第二天你就看到很多人在小红书上发：他直接用 GPT-6 去控制一个机械臂，去做抓取或者叠衣服这样复杂的动作。而注意，GPT-6 是一个语言模型——虽然他有视觉的能力——它就是一帧一帧地问你"下面要干什么"。还没有解锁提示词工程，就已经做得相当好了，已经达到了 state of the art 的能力范围。

所以模型一定会进步的。这个例子告诉大家：也许我上课上到某一次的时候，我突然就可以说这个课不用上了，大家就可以去做产品了。呵呵。

### 汽车刚发明的时候，每个人都得懂它的底盘

anyway，到今天我觉得我们还是当然需要学习一些软件工程的知识的。因为我刚才说，AI 解锁的是你的执行力。

> **结论**：AI 替代的是执执行力，但它替代不了品位；所以"学会了才能更好地解锁 AI 的创造力"这条逻辑今天依然成立。

我正好被人问到过：我们在 AI 的时代为什么还要不要学数据库、学操作系统、学这些东西？我的答案其实也不是特别的确定，因为我打了这样一个比方。

我们回到 100 多年以前，汽车刚发明的时候，你汽车开个 12 公里就会出故障。所以你的每一个司机、每一个 driver，你都必须对汽车的工作原理了解得非常清楚——因为你的汽车一旦出故障，你就得知道它是怎么工作的。那在那个时代，这是理所应当的事对吧？你想要开车，你就需要掌握汽车的基本原理的知识；你想要学 computer science，你就要去软件工程的工厂，那你就得去学操作系统、学数据库，把这些基础知识做好。

但你想想今天我们怎么开车？我们在地下车库直接说"帮我开到什么地方"，然后自动驾驶汽车就出发了。你已经不可能、或者说你作为一个人已经不理解整个系统栈上面是怎么工作的了。因为最终它的动力还是传递到一个机械装置，和那个 100 多年前的汽车还是有一点相似的；但在这个过程中它经历了所有东西，你都不需要知道，你就可以把汽车开起来。

换句话说，人工智能你也可以想象成是一个类似于汽车这样的东西——当然它比汽车更强，它替代的不仅是人的腿部向前走的能力，它替代的是人的智力。那我们是不是还要学？

我今天答案肯定是要学，因为你们学了以后，可以更好地解锁 AI 的创造力。但是以后该怎么学，我现在暂时还是不知道的。你们也许如果有答案的话，也欢迎和我来探讨。当然这是我个人的观点：你们至少在现在的阶段，学习还是有好处的——你理解了正确的概念，可以帮助你从别的地方借鉴一些知识，来创造更好的东西。

### 一个软件工程项目，从一个空目录开始

好，我今天就进入真正的软件工程了。我们说生成式软件工程。

你如果要开始做软件工程、开始 vibe coding，你干的第一件事情是什么？你不是从网上——或者说比如说做作业的时候——你一定是从课程网站上、或者老师要求在什么地方下载一个东西，然后从那里开始工作。但如果你今天就真的是想要做一个项目，那你做的第一件事一定是先建一个目录。

建一个目录，给它起一个名字，可能起一个中文的名字，叫"我的最酷的 game"，然后你就开始 vibe coding。

那什么是一个软件工程的项目？你创建了以后，面对一个空的目录，你们还记得你们是怎么学会应该做什么的吗？你们可能会看到课堂上有人打开一个工程项目，里面有一些文件，你就在不经意之间记住了一些项目的东西；然后你可能会得到一个 GitHub 链接——可能是别人推荐的——你打开以后那是一个网页，还是非常 human-friendly 的。你看到那个网页上面有一些文件，你就知道"哦，我的一个目录里面会要有一个这样的文件"。

所以当我们说我们要开始一个软件工程项目的时候，你就会建一个这样的目录，它里面有一堆文件，然后这堆文件共同构成了一个可以交付的东西，这个东西最后会变成你的产品。

```text
   人类世界里的需求（一个说不清的 intent）
                    │
                    │  投影
                    ▼
        信息世界里的一个目录
        ├── hello.c      源代码
        ├── hello        编译产物（由 hello.c 生成）
        ├── doc/         文档
        ├── intent.md    意图与规格
        └── test/        测试用例
                    │
                    │  构建 + 交付
                    ▼
            可交付的东西  →  你的产品
```

> **定义**：关于"什么是软件"，有个标准的定义——代码、文档等等，一切和软件相关的东西的集合。但我一直说，软件是人类世界的需求在信息世界里的一个投影；而这个投影今天看到就是一个目录，目录里面有各种各样的东西。

这个目录它可能是直接在你本地运行的。你在你神奇地跟 agent 说"请你帮我运行"的时候，那个窗口就弹出来，或者网页就弹出来。一句著名的笑话：GPT-6 太牛逼了，我又做了多少个 killer 级的产品，它们是 HTTP localhost 下的 5137，然后发一个 twitter。

所以你还是需要懂的：你本机可以打开它，但世界上的其他人打不开它，因为别人不知道 localhost 是你的本机。

当然你可以通过把你的 intent 和 specification 说得更清楚一点。比如你在那个文档里面就说明"我的这样的一个东西要被全世界人看到"。如果你不说这个，GPT 可能会把你当成一个开发者——那开发者最正常的流程一定是在你本地先调试，先起一个本地的 development server，然后你可以看到它的结果，直到你觉得 ready 了，你才会把这个东西送到远端。

但这都是知识。你们作为 computer science 的学生，在各种各样的课上反复地学习这些知识，然后这些知识最后变成"好"，它里面有文件，最后会得到一个可交付的东西。你们从最开始学编程——你可能是点一下某个按钮就一键编译和运行；到后面你们会知道，你的 build 目录里面所有的东西都是由某些命令行的工具创建出来的；你们会开始在大二的时候用一些像 GCC 这样的命令行工具，把一个 hello.c 变成 hello 的一个 binary。这就构成了一个软件工程的项目。

那目录里应该有什么？比如有个 hello.c，然后你可以编译出一个 hello，你就已经在做软件了。当然这个可能不符合现代软件工程的 best practice，但古早的时期——我觉得这甚至是 10 年以前——大家真的是这样。

### U 盘、作业压缩包，和一次丢失代码的事故

我给大家讲一个我的第一个 PhD student 的故事。他应该是 2012 年入学的，进入南大的。

他大一的时候发现了一个非常好的学习方式。因为他经常会去机房——他自己的笔记本电脑屏幕比较小，也不是很舒服，不像现在我相信大家应该都会买一块屏幕，买一块屏幕应该不贵，淘一个二手的屏幕只要小几百块钱，然后你就可以在宿舍获得非常好的编程体验。但那个时候好像我们的标准答案是去机房，屏幕好像没有那么便宜。那去机房的话，就要来回拷贝代码，比较麻烦。

所以他想出了一个妙招：大一的时候把代码保存到 U 盘上。你们多多少少可能也干过这样的事，或者在中学的时候上电脑课的时候，你做的作品你会保存在 U 盘上。

然后结果到他大二的时候，这个 U 盘坏了。U 盘坏了以后，代码全部都没有了，作业不见了，他珍藏的那些启蒙时候的作业也不见了。有一点伤心，但是好像也没有太大的关系。

对我们来说，我们很长时间都是这样管理代码的。比如说我记得我上学的时候，交作业的方式是打一个压缩包发邮件；然后现在好像你们会在一个网页上面上传。这都是管理项目的方式。

| 年代 | 交作业 / 交付的方式 | 拿到更新的方式 |
| --- | --- | --- |
| U 盘时代 | 代码拷在 U 盘上，带来带去 | 物理接触，无所谓版本 |
| 压缩包邮件时代 | 打一个压缩包发邮件 | 给每个人发一份新的包 |
| 网页上传时代 | 在一个网页上面上传 | 重新下载覆盖 |
| Git 时代 | 推送到远端仓库 | `git clone` / `git pull` |

但是当我们谈软件工程的时候，今天是有标准答案的：就是你应该去用 git。

> **定义**：git 是什么？它除了能够保存一个目录——项目是一个目录，目录里有 hello.c、有 hello 这个 binary、还有文档等等——它还能保留和比较、恢复历史的版本。这是一个很重要的软件工程的特性，我后面会详细展开来讲。

有了 git 以后，其实很多事情都变得很容易。比如说我再也不需要发邮件了。我真的很难想象我们过去是这样的：今天是 AI 的时代，我们有了十倍百倍的生产力提升，我只要让他去帮我写一个这个投诉（complain），我就什么也不用管了。我比如说如果我今天是用我的 codex，我就真的选择信任他，我就不管了——甚至看都不会看，我让他做完以后把这个浏览器给关掉。但过去的时候，我们真的还在用邮件管理项目。

然后有了 git 以后，我们发现效率高了很多。我们可以用 `git clone` 去从一个远端获取一个作业；如果作业更新了，我可以在远端更新，我就不需要给每个同学都发一个什么作业包了——我只需要在上课的时候告诉同学们说"哎，我的作业更新了，你们用 `git pull` 去下载"。

以及我上课的时候我有一个 `make submit`，它会自动再用一个脚本把包打好，打好以后上传到我的课程网站，非常方便。这有点像一个现代的 CI/CD 的流程。CICD 我应该专门会有一节课来讲。

### 最重要的其实不是知识，是学习意识

这就引出了一个我几乎每节课都会讲的事情。

**当我们今天学习变容易以后，这门课上讲的知识都不重要，重要的其实是你们的学习意识。**

比如你们都看过很多 git 的项目——看肯定肯定的，因为你哪怕是打开课程作业，你都会看到它有一个 GitHub 的链接。那么你们有没有留意过不同的项目之间细微的区别？比如说有的项目有这个文件，有的项目没有那个文件；有的项目里面文档是这样写的，有的项目文档是那样写的。你在这种不停的有这种信号进入的时候，其实你就能判断出我们应该怎么用 git。

我猜你们中间一定有人有过这种感觉：我上课老是说，这个是不是跟中学的时候有关系？因为在中学的时候，老师说的事情实在是太多了，你必须要听老师的话，你才能把所有的事情做完；如果你不听老师的话，你就不可能把事情做完。

但到了现在，比如你去 GitHub 学习的时候，如果你还带着这个心态——"老师说好，你去把作业拉下来"——那你就有点像 AI 了，有点像今天干活的 AI。你被强化学习成了一个：老师说让你做这件事的时候，你只做这件事，绝对不会多碰一点点，因为这是最省时间的。AI 也被调教成这样了。

但如果你花一点时间——我劝大家愿意多花一点点时间去点进去，看一下里面的各种东西——然后你可能突然间就有个灵光一现："哎呦，这个文档写得很好嘛。"

因为你会马上发现，今天你看到满世界 GitHub 上的项目全部都是巨长无比的 README，然后 README 里面有各种 Unicode 字符组成的什么目录结构框图——就这种 AI slop 的感觉。你们有没有留意过这些细节？然后在你看过这么多 AI slop 的时候，突然你发现了一个什么老项目——哪年几十几年前开始维护的老项目——点进去那个文档清新舒服，README 很短，但是看完以后你想看的东西，三个链接，你就走过去了。你不需要看那么长的 AI slop。你就学会了文档应该这样写。

这也是我理解为什么很多同学们怨气很大、觉得上课耽误学习：因为现在课外的信息量和信息密度，已经远远超过任何一个课堂可以做的事情了。当你打开一个成熟的 GitHub 项目的时候，它是这个工程师十几年的心血——甚至在某一个时间点，10 年以前，这个项目崩溃过一次，他做了一次大版本的重构，他发现以前的那个 practice 不够好——你才呈现到你面前的，是一个现在好好的东西。但是我们传统的教学方法，没有教过大家怎么样把这些海量的、信息密度巨大的东西用好；然后大家也没有准备好去拥抱这样的知识。

可能为什么我现在在做老师，就是因为我有这种惊人的注意力。大家其实要训练的，也是那种惊人的注意力。

我给大家一个具体的画面：你在看到一个东西的时候，快速地有种什么感觉呢？就是——如果你有任何一个问题，你看到东西之前，你的大脑有一种可能有一种能力吧，会先把我看到的所有东西都忽略掉；我会想，如果我要自己来解决这个问题，我会怎么做；然后我会立即比较——我看到这个东西和我脑袋里所想的东西谁更好。如果我做得更好，我就认为这是一个 slop；如果我发现他做得比我好，我就很惊喜，说"诶，他为什么做得比我好"。

如果你养成了这个习惯以后，这是一个非常恐怖的习惯。因为你在任何时候都在疯狂地从外面接收信息，然后你能留意到生活里面各种小细节的时候，你就不停地在提升。

### 一个可以迁移到任何课程上的读法

其实很早的时候大家就有推荐：如果你要读一个 research paper，应该怎么读。这个学习方法其实也适用于大家学任何课程——包括你们的高等数学，包括你们的计算机系统基础——叫 `virtually implement`。

就是你现在有一个具体的问题，或者具体的需求，你先在脑袋里面把这个问题自己做一遍，你会得到一个什么样的结果呢？如果你的方法和作者的方法是一致的，那很好，说明你已经学会了、完全掌握这个知识了。

然后如果你不一致，还有两种情况。

#### 对方的方案确实更好

是成熟的、好的教科书上的方案，比你想象的那个方案要好、要精巧、要简洁。那你就会想"为什么他能想到"，它就变成你知识的一部分。

#### 你比对方还好

那就真的是惊喜中的惊喜。可能你一万次才会有一次这样的体验，但是这个体验给你的正反馈也很强——你突然会想"我能不能去做一个什么什么好玩的"。

所以我觉得在 AI 时代，你们更可以对细节保持注意力。比如说 git，你看到各种各样的 git 的 repo，你读别人的东西，甚至 AI 生成的东西，都有感知细节的方式。

### 一个可以记住的对比：香港的路牌和南京的地铁站

我还想到一个对比，我觉得特别 get impressed。那已经好多好多年以前了，有一次我在香港，我发现我要找路。

我发现在香港找路的时候，每当我有不确定性的时候——比如说我前面有三个口的时候——我正前方一定有一个路牌，告诉我这三个口是什么，从来没有过。它有一个非常复杂的地下系统。

然后你回到南京的时候，你会发现你有时候经常要在地铁站里找我下一步该往哪一个口走——我是不需要环顾四周去寻找，甚至要移动比较远的距离找到一个地图，地图上再去看。

我们有时候觉得中国是一个 developing country，是个发展中国家，意味着我们的提升空间很大——我讲的是基础设施这一个层面。

你其实这就是一个学习的过程：如果有一个范例比你做得好，你就学到了。我就在这个对比当中学到了一个 lesson。

比如说如果我要做一个 UI 设计的话，我的这个 UI 就应该是——任何人站在这个页面上的时候，他会想什么？不同的人他要的 ABC 会趋向不同的方向，我希望用最少的方式把 ABC 全部呈现出来。

你看，这就是一个 README。你们都会用 AI 生成 slop 的 README，但当你看过几个好的以后，你就会写会写 README。

而且因为你有 AI 以后，你马上就可以问他啊："为什么我看到这个项目的 README 没有 AI slop 的感觉？"——它就会告诉你。

### 什么是 Git：面试里的一道题，和一次 merge 冲突

好，那我们可以讲关于 git 的一些具体细节了。首先为什么要 git？

大家有没有想过：当然有了 GitHub 以后，分发代码变得前所未有的方便，这件事情他们创立 GitHub 的时候可能就想到了，但他们没有意识到，这竟然成为了比如今天 AI 时代的一个底层的基础设施——NPM、你的各种配置全部都在、大部分都在 GitHub 上。

我上周末的时候参加了推免的面试——你们应该也会在一年或者两年以后会来到这个场合去面试——我就问大家，什么是 git。大家多多少少都能说两句对吧。"从 git 上面可以下载分发代码"；有的同学可以讲到 git 管理的一些这个项目目录的快照。我说好啊，挺好的。当然我没有必要把所有人都挂掉，你能讲一些就可以，这取决于你能讲多少，来给你一个评估。`git rebase` 之类的，这个也在意料之中。

但我比较意料之外的是：大家有没有观察过——如果 git merge 发生冲突以后，会观察到什么？

就是你比如说你的作业，上游发布了一个更新，然后在你本地已经把这些东西改得面目全非了。那这个时候你还是会跟 agent 说"来来吧"，然后 agent 它就自动"啪啪啪啪"给你修好了，跟你说好了："现在 merge 出错了，还帮你修，最后他说测试都通过了。"然后我看一眼这个东西，看起来 OK 嗯。

这个时候惊人的注意力就有用了。如果你愿意在冲突的时候停下来——尤其是大家作为学生的时候，总是想"我再学一点吧，反正就一秒钟，我学一下也没有坏处"——你会看到一个非常神奇的东西：有好多等号，有好多箭头。

```text
        你本地把第二行改成了 2         远端把第二行改成了 3
                  \                        /
                   \                      /
                    v                    v
             git 不会替你在两者之间做决定
                    │
                    │  它把两边的代码同时摆在你面前
                    │  一串等号分开上下，尖括号标出边界
                    │  两侧分别标出 HEAD 和 incoming
                    │  IDE 上方还会多出 Accept Incoming / Change
                    v
        责任到了你手上 —— 你决定谁进谁出，再创建一次 commit
```

你在 merge 冲突以后，不是冲突立即就被 resolve 了，而是这个责任就到了你手上。

在曾经的时候，这个责任是到了每一个开发者手上。如果开发者发现了冲突，那开发者有义务要把这个冲突给解决掉；他解决掉，就需要能看到这个冲突。他不能说——如果 git 是设计成你——你站在 git 设计者的角度——两边这个，比如说我现在有一个文件，一行原来是 1111，然后有一个人把第二行改成了 2，有一个人把第二行改成了 3，那这个到底是 2 还是 3 呢？

git 不能说"对不起，冲突了，我不能合并了"，然后躺在那。那对人来说负担是非常大的——我到底这行应该是以 2 放进来，还是应该以 3 放进来呢？

你看所有的 first principle 都是连起来的。我刚才无意中举的那个地铁标识的例子，git 也在用这个原则：如果你现在发生了一件事，那最好就是在这个地方，把所有要的信息全部都放进来。

所以你会回想到，你看到了——如果你以文本的方式来看，它有一个等于号，有好多尖括号，然后有些地方有这种 incoming 的标记，然后至少冲突的两部分代码都同时显示在这里。然后如果你们用像 IDE 的话，你还可以看到上面会多出一些按钮，什么 Accept Incoming Change，然后你就可以在这个 IDE 里面自己 resolve，自己决定谁进谁出；完了以后你就可以再创建一个 commit，把它给 resolve 掉。

你只需要一点注意力。其实你只要有一两次，你就会有一个印象：你至少能说出两边这个冲突的代码都会显示在一起。

然后比较惊人的是，这个大家答得不好——那就肯定是第一个没有用过，大家没有开发过。当然我觉得就算用 AI 开发，你也很容易遇到这种 conflict；如果你让 AI 在不同分支开发，还是没有留意。

所以比较重要的是：第一，去多用用；第二，去拥有更好的注意力。

### 你其实可以自己发明一个 Git

在 U 盘上面放一个目录的方式是不行的对吧？每次打一个包。但据我的观察，我上学的时候同学们确实是这样。当然我上学的时候可能比较早了，git 没有 popular：作业 V1、作业 V2、作业最终版，每复制一个目录。

这个其实是一个非常直觉的体验。这个方式可以找回旧的文件——因为你万一有一天手滑了，或者不小心改错了，尤其你们在新手阶段，不小心有一个误操作是非常正常的；你想要回去上一个版本，看一看到底我上一个版本是怎么写的。

诶，这不就是需求吗？

然后就从这样的一个需求，你自己就能发明一个像 git 这样的东西。

```text
   「我手滑改错了，想回去看看上一版到底是怎么写的」
                              │
                              v
        简化版 git：能 list 出所有版本 · 能把当前版本切成另一个版本
                              │
                              v
              用着用着：要跟室友同步同一个项目
                              │
                              v
              你们俩一起改了同一个文件，应该怎么办？
                              │
                              v
          分支 branch  ·  合并 merge  ·  冲突 conflict
```

因为本质上所谓的版本管理。我们说，什么是项目呢？项目就是一堆东西：你的代码、文档，intent、spec、implementation，各种东西，测试用例，全部都搅在一起，没问题，一个目录。

然后你会想：如果我们能够把目录的版本管理起来——我不再是叫作业一、作业二、作业三，我只有一个作业、一个作业的目录，但是我可以提供一个命令行工具说"我能不能看一看 list 作业的版本是什么""我能不能把当前的版本变成另外一个版本，回到过去的一个版本"——你不就发明了一个简化版的 git 吗？虽然你还没有使用任何分支、合并、冲突这些概念。

然后在你用着用着的时候，你自然而然会去发明那些概念。比如说你要跟你的室友同步了，你就会出现：他说你们俩一起改同一个文件的情况。你就坐下来想"诶，一起改了同一个文件应该怎么办呢"，你就可以发明 git。

当然这体现了人类的局限性。

在 git 之前，我们还用过一个你们可能听都没有听过的东西，叫 SVN——check in、check out。然后 SVN 和 git 它的设计是不一样的。

```text
   SVN：存的是「变化」—— 一条越来越长的补丁链
   ───────────────────────────────────────────
        v1 ──patch──▶ v2 ──patch──▶ v3 ──patch──▶ v4
                                                       │
        回到 v2 ？只能一个 patch 一个 patch 往回退 ◀───┘
        （缓存之类的优化能缓解，但模型本身没变）


   Git：存的是「快照」—— 每个版本都独立可达
   ───────────────────────────────────────────
        ● v4        ● v3        ● v2        ● v1
         │           │           │           │
         └───────────┴───────────┴───────────┘
        回到 v2 ？一秒钟切过去
```

SVN 说我们存储的是项目的变化。假如你有一个最初的版本，然后每一次你的文件改了一行，我就存一个 patch；再改一行，存一个 patch；再改一行，存一个 patch——好像没有问题，这是一个非常高效的实现。

但是就是这个高效，随着项目的增长，把大家拖回去了，拖入了泥潭。git 的这个模型要干净得多。first principle：我想要回到过去的某一个版本，马上一秒钟就给我回去。而你如果每次存的都是一个 delta，你想要回到一个早期的版本，你就得一个一个一个一个往回退。当然你可以用一些缓存之类的方法来优化它，但我觉得这确实是走错了路了。

所以 git 基本上就是这样来的。它的作者是 Linux 的作者，Linux 用一个非常简单干净的模型。1991 到 2002 年的时候，如果想要维护 Linux，就是用作业 V1、作业 V2 的方式，在邮件列表上面发补丁：直接在邮件里说"我改了一个 a.c，然后我有一个 a.c 新版"，然后我就在往邮件那边一发，然后会有一个每天看邮件列表的人，把这个放到他的核心仓库里，然后再去 release 这个版本。

然后他们还用了一些其他的工具——`gitk` 啊、`keeper` 这样啊——直到 Linux 终于受不了了。他们觉得我们应该有一个绝对简单、但是又非常好用、概念正确的版本控制工具，所以在 2005 年做了 git。

所以他比我们想象的年轻一点。2005 年，有兴趣的同学可以去看 Linus 那个 proposal。当然直接按 agent 看就可以了，你不需要再去读了——我读书的时候，我们都是看过这些文档的。

所以，that's it：我们需要项目级的时间回溯。我们都会犯错误，所以只要能去 git 的历史里面把它捞回来就可以了。

你们可以试着用这种方式去推导：从已有的经验你知道什么、我想要什么，然后推出下一个概念它应该是什么样的。

然后你发现吧，这就是数学的推理。我上课的时候这样讲下来的时候，我每一句话都是和之前是有逻辑关联的，然后这个逻辑关联多多少少都有一些数学的联系。所以 OpenAI 认为他要把数学先训好，训好以后，他所有问题他可能都能解决。然后这件事情可能就真的要弄成真了。我自己是觉得，品味可能也是能解决的。

### 从 git init 到第一次 commit

那我们还是讲一讲什么是 git。

我还是建一个空的 terminal。你们也都知道，你今天如果要开启一个项目的话，那就 `git init`。当然它不重要，它会告诉你一些奇怪的信息。

那这时候你就有两种选择：第一种是让 agent 来帮你做，帮你解决、帮你回答你不懂的问题；还有一种就是把它忽略掉。显然忽略掉是更高效的学习方法。然后你得到了一个 `.git` 目录——当然 `.git` 目录默认是不显示的，所以你看不到它。这就是全部了。

当你做完 `git init` 以后，你的项目就变成了一个被 git 版本管理的仓库了。然后你可以从远处下载代码，可以把代码推到远端。

> **结论**：仓库（repository）的本质，就是那个被你放进去的目录，加上一个隐藏的 `.git` 目录。

然后你可以用最基础的命令。比如说我有个 `hello.c`——你们喜欢写 C 好。那如果你有一个 hello.c，你就可以：

```bash
git add hello.c      # 把这个文件放进"下一次快照"的候选集合
git status           # 看看工作区现在都有什么，git 还会给你一些提示
```

然后 git 很重要的是创建项目的快照，使得你可以在任意时间之间穿梭。所以我们可以创建一个有消息的快照——这很重要，这体现了软件工程的智慧。

### 不要把 Git 当成"作业 V1"

你看之前我们用复制粘贴的方式，命名为目录一、项目版本 V1、项目版本 V2、项目版本 V3，作业 V1、作业 V2、作业 V3。

git 的世界里面不是这样的。我真的看到很多同学在用 git 的时候，把 git 当成是作业 V1、作业 V2、作业 V3 来用，但这个不是 git 推荐的 practice。

推荐的 practice，或者说在长期的软件工程实践的经验当中：你每一次对这个项目做了任何的改动以后——比如说改了一个文件，修了一个 bug，或者给它增加了一个功能，或者调整了某一个脚本，或者调整了某一个文档——你都应该立即做一次 `git commit`。

```bash
git commit
```

哎呀这怎么是 nano——然后你可以有一个文本编辑器，说说我这是做了什么。Ctrl + O，我可以保存好，那这个提交就成功了。

然后这些你们都可以在现有的项目里面看到对吧，他们是怎么协作的。有些 git 提交可能比较大，他放了一个 feature；有些就比较小，他就是 fix 非常少的东西。

所以当你面对这样一个新鲜的工具的时候，你去理解它的 best practice 还是需要花时间的。所以我还是觉得你可能不能把所有的事情都交给 agent——你多多少少还会知道我们为什么要做这件事：为什么、什么时候应该做 `git add`，什么时候应该做 `git commit`，`git commit` 的 message 应该怎么写。

所以你真正需要的是在任何时候学习。比如说碰到这个新东西的时候追问一下："你刚才做的是不是符合 best practice？"比如我刚才做了一个 git commit，这个符合 best practice 吗？加上豆包输入法真的就是一秒钟的时间，但是他会给你很多解释。他说：这个 commit 不太符合 best practice，主要问题在提交信息；其次代码本身也有问题，提交信息的可读性有问题。

> **易错点**：把 git 当成"作业 V1 / 作业 V2 / 作业 V3"是错的。你只有一份目录，版本是对象，不是文件名。

### 提交信息才是 Git 的灵魂

我故意做了一个 `I added some cool stuff`，完全看不出做了什么。

所以 git 首先，本质上虽然它存储的是每个版本的快照，但是我们的项目本质上还是从一个版本对吧？V1，然后经过一次修改变到 V2。

所以 git 鼓励的是：你需要在 message 里面描述出你改了什么。相当于你如果一直看、一直看，你就知道这个项目是怎么发展、一直走到现在的：修了多少个 bug，加了什么需求，经历了什么样的重构。你可以在 message 里面看到这个项目的历史轨迹。这是他鼓励的，然后这也是一个好的软件工程的 practice，使得别人能够更容易地理解你的项目。

所以如果你的每一个提交都是 `I add some cool stuff`，你想想如果你有一万个提交以后，这会变成什么？你这个 commit message 就变成 slop 了。那如果一万个提交都是 "I did some cool stuff"，那这个 commit message 这个特性就不应该存在——对，你就不要叫 commit message 了，就从 V1 到 V2 就行了。

那什么是好质量的样子？用祈使句、现在时，描述变更动机，比如 `fix off-by-one in …` 这样的写法。再讲究一点，可以考虑社区里常见的 conventional commits 那种带前缀的约定——在更多的项目里面，你会看到这样的 commit 方式。

### 空提交：不是 bug，是有条件的例外

你会在各种时候用不同的 commit message。比如说你这个版本要收尾了，你可能会有一个版本的 commit message，会讲"我要 finalize 这个这个版本"。

甚至 git 也允许你在不改任何代码的时候——V1 和 V2 是完全相同的时候——再做一个提交。这件事情可以吗？你看，他拒绝，拒绝提交你这个空的、没有修改的。

但是 agent 可以。我让他做一个提交，然后要求他在不做任何改动的情况下提交——你看，他知道，他有知识。

所以其实你们需要的是惊人的注意力，然后尝试从理论上问：应该可以的吧？比如说我就说"我要发布一个版本了"。但这个不是 best practice，所以尽量不要做。

那它在什么时候确实有用呢？空 commit 可以在无改动时产生一次提交，用来触发 CI 或者 release。比如上一个 bug fix 的提交里我修完了最后一个 bug，那我就得到了一个我可以 release 的版本。当然 git 是可以在这个点放一个 tag 的，比如说 V0.1，放一个 tag 说"这是 V0.1"；但是我也可以强行做一个提交，说"我要 finalize"——这是没有改动的 finalize，为了把 V0.1 冻结、把所有东西都冻住。那这就是一个没有改动的提交，那我就可以把这种 bug fix 的提交和 finalize 的提交给分开了。

> **注意**：这在偶尔的情况下还是可以允许的，但你显然不能大量地创建这样的空提交。

### 水面下的冰山：best practice 是血和泪

你会看到在 git 里面，虽然你学了、用了 git，`git push`、`git pull` 就可以用了，都会用了，但其实真正水面下的冰山是各种各样的 best practice，而这每一个 best practice 其实都是血和泪的教训。

你反过来想：为什么 message 要这样写？你转手问 AI——你可以跟更有质量的模型讨论一下，这样做有什么好处。

我觉得很多时候模型表现比我好。就可能这个知识我是知道的，内化在我的脑子里面，然后你要给我两个小时的时间去想，我可能也能给你写一个非常好的"为什么要做这件事"。但是我的智力是有限的，我的精力是有限的，我的注意力也是有限的。比如说我现在在上课，为了专注地和大家上课，我大脑里面做思考的那部分容量就有点不够了。所以我上课讲授一个概念的时候，讲的往往不是最好的。

如果你回头把这些问题——比如说为什么 commit message 要这样写——你去跟 ChatGPT 聊，就像我刚开始那样：我求助一个我无法掌控的东西，但它知道这个世界上所有的东西，它能很好地把这些概念给你讲清楚。

然后这些约定俗成的 best practice，我来做一点不是 best practice 的事情举个例子。比如这是你们非常常见的事情，这个应该是可以编译的。假设这时候你有一个 untracked file，然后你们在 tutorial 里面看到有一个命令很好，叫 `git add .`——这样如果你有好多好多的文件，比如改了三五个文件，你不需要 `git add a.c b.c c.c` 了，你直接 `git add .` 就把它提交上去了。

git 是不阻止你做这件事情的，这是完全合法的。

然后那我就问问：git 提交有什么不符合 best practice 的吗？他会看一看，按严重程度排序给出：

| 问题 | 为什么它是个问题 | 应该怎么做 |
| --- | --- | --- |
| 提交信息毫无信息量 | 主观、废话、完全看不出做了什么 | 用祈使句、现在时描述变更动机；可考虑 conventional commits 的前缀约定 |
| 提交粒度和内容混杂 | 一次提交塞了好几件不相关的事，无法单独回滚 | 拆成有意义的、单一职责的提交 |
| `hello` 是编译产物 | 会让版本库膨胀，且极易产生无法合并的二进制冲突 | 加进 `.gitignore`，由构建系统产出 |

他还会告诉你应该怎么做：先说"提交信息毫无信息量"，这个他已经开骂了——主观、废话。

> **易错点**：编译产物为什么不能进版本库？因为 git 有一个"作业 V1"里面那个 exe 一定在里面、"作业 V2"你的 exe 也在里面的这种朴素直觉，但 git 要防止版本库的膨胀。尤其是如果你这个项目里面有 1 万个文件、有 100 个合作者的时候——每一个合作者的环境都是不一样的，你想，每个环境都不一样，他们 build 出来的东西也是不一样的。你们可能不知道，你们的编译每一次那个文件可能都是带一个日期的，它甚至带 hash，带你本机的指纹的，你看每一次这个二进制文件可能都是不一样的。

然后如果你把这个东西放进去了，下一次就会产生冲突。因为你这里有个 hello，对方有个 hello，哪怕是同样的源代码编译出来他都可能不一样，更何况如果是不一样的源代码编译出来的 hello。然后呢，这个就会产生一个二进制的冲突——而二进制的冲突是很难合并的。

你想，如果我编译出来的东西不是这种程序编译出来的，如果我是生成的图片呢？当然图片是一个比较特殊的东西。图片怎么合并呢？合并就是有重叠。

所以这里有很多很多的 best practice。然后我可以让他干，我觉得可能会出乎意料的是，他还花了一些比较长的时间来思考——网没有……哦没有，网没有断开。

他说：**丢弃空提交和编译产物两段历史，新建 main 分支，重写为两个有意义的、单一职责的提交。**

还贴心地发现历史没有 remote——就是说我的仓库没有和另外一边同步，不会有别人。因为如果别人也持有的话，那就比较糟糕了；没有别人，所以他把整个这个项目就给改了。

你看，如果你的注意力注意到，你会发现他换了一套 commit 的方式。他会有一个这样的 headline message，然后在 headline message 的后面，还有一些内容。

这里面还有好多好多好玩的：比如说如果你在这里有一个什么 fix 的 message，比如说你在这个 message 里写一个 `fix #3`，然后 GitHub 会自动把你的这个 issue 给 close。

这里面有很多很多好玩的。你只有反复地使用，反复地使用，反复地使用，你才能获得一个从初学者到有一定经验的人的……

## 用原子变更推进快照：Git 的工程实践与底层原理
> 对应块：BLK06 | 覆盖分集：P04下 | 块标题（分集名）：《软件仓库管理 [03-Raw_26生成式软件工程》

### 提交之前，先让 AI 逐个检查文件

现在是 agent 时代，你们都是 agent native 的人。你们肯定也不会用古法了——说实话，我觉得 `git status` 这种东西，在你们这儿已经算古代手艺了。

但我先把话说清楚：不是说命令你一条都不用记。**你要有概念**——你知道我的 git 能干什么、什么时候该用它。你只要有这个概念，就可以让 agent 用符合 best practice 的方式去干。

当然这会带来一个问题：**你其实分不清自己是真的能干，还是脱节了根本就干不了。** 不过也许我觉得这也不重要。

所以为了提高大家的学习效率，我的建议是：**在任何一次 git 操作之前，都让 agent 逐个检查文件的变化。**

我现场试一下。我这里有一个是编译不过的代码，我让它做一个提交。我也不知道模型会给我什么。

你看，他很聪明，他比你聪明。我们人在改作业的时候都会有这种倾向——"哎呀就改一个字，不要紧的"，就改了，就提交吧，对吧？你一定会这样想的。但模型是有工程 sense 的，他见过很多好的工程项目，也读过很多软件工程的书，所以他知道**当前不建议直接提交**。然后他还给我修好了，还要给我解释：

> 为什么这次不符合 best practice：一次提交应当是一个完整自洽的快照；编译不过的代码提交进去，相当于让仓库处于坏状态。

而且你看他还有更多的东西——**这些是我上课即兴演示的时候没有想到的。**

这里头的关键在哪？**模型见过大量好的工程实践，他不只记得"能编译就行"这一条**，他会给你一个完整的理由。所以你给他加几个 system prompt 效果会更好，比如"要说中文"，或者"我在上课，所以你要讲得详细一点"。

那条最基础的要求大家都听过：**每次提交的代码应该能够通过构建和测试。** 这是一个非常基础的要求，大家会觉得 OK，应该是这样的。但当你反复地强化、潜移默化以后，就 OK 了。

### blame 与二分查找：Git 真正厉害的地方

上面这个"每次提交前先检查"的习惯一旦养成，Git 本身那两个杀手锏就能真正发挥作用了。

#### blame：每一行都有出处

Git 还有一个很有意思的功能叫 `git blame`，我很喜欢。

它会告诉你**每一行代码是在哪一次提交、哪一个地方被改的**。也就是说，哪怕我的历史是完全线性的，我都可以拿它干很多有趣的事情。比如指着一行代码问"这行是谁写的"，立刻就有答案。

#### 二分查找：把提交历史当成一个数组

然后是二分查找。大家都用过二分查找吧？保研或者找工作面试的时候，可能要手写一个。

二分查找的经典设定是：你有一个很长的数组。现在你在当前版本上发现一个 bug，但这个 bug 未必是你引起的，可能是过去的某一个地方引起的。这时候你有一个测试用例，或者任何能够检查出这个 bug 的东西——你就可以对**整个 git 历史记录**做二分查找。

为什么可以？因为本质上，git 的历史里有一些提交是 OK 的，有些是不 OK 的：应该在某一刻引入了一个 bug 以后，从那个时刻起所有提交都跑不过测试，而在那之前的每一个提交应该都是 OK 的。

> **提示**：这不就是一个"所有前缀都是零、后缀都是一的数组里找第一个一"嘛——这正是二分查找能做的事。git 的线性历史天然就是这样一个数组。

所以 bisect 是怎么回事——一句话就解释了。二分查下来，你就知道**是谁改的**（blame）、**发生了什么**。然后 agent 有很多软件工程的实践可以往上套。

> **结论**：软件工程里那么多东西，我觉得没必要在课上讲。你们留着自己的时间，在实践当中由 agent 告诉你们就好了。

### 那些高血压时刻

好消息是：在 LLM 之前，我带新同学的时候，**每次都会有这么一段"高血压时刻"**——就是关于使用 git 的 best practice 的那一次。

我们做一个研究项目，欢迎新同学加入：你去开一个 git repo。第一周的任务非常简单，搭个架子，把一两个东西跑起来。

好——然后我打开这个项目，进入高血压环节。

#### 哪些东西根本不该进仓库

最常见的是**生成的文件**。`dist` 或者日志文件被提交上来了——日志也是生成的文件，它不应该在里面。

**个人的配置**。比如 VS Code 的个人设置。更有甚者，那个配置文件里还硬编码着你 C 盘下的某个路径——这显然在任何一个其他地方都是没有办法复现的。

更高血压的是：**我可以在审稿的时候，看到一些处于 active 状态的 API key。** 而且我一扫那个格式就知道这是一位中国兄弟干的。

再比如**没有 Mac 的同学会不经意间提交上来 `.DS_Store`**。这是 git 的一个特性：你没有 `.gitignore` 的时候，如果你用 Finder 打开一个目录，它会自动留下索引——记录你把哪些子目录展开了——放在一个叫 `.DS_Store` 的文件里。但这个文件因为是点开头的，默认是隐藏的；`ls` 甚至还贴心地给它配一个苹果图标，所以你根本看不见它。看不见，你就在本地 `git add .`，然后 `.DS_Store` 就被 git 追踪了。

这当然也有它的道理：带点的东西往往是约定俗成的配置，比如 `.github` 里的 workflow，所以 git 默认会把带点的都收进来。但这个临时文件**会经常变**，就不应该被提交进来。

#### 为什么又有生成物必须提交

但规则又没有那么简单：**不是所有 generated file 都不应该提交。**

比如你有一个 `package-lock.json`，再比如你会 generate 一个 header。这个 header 确实是可以提交的——**把它放进来，别人可能在不需要下载很多依赖的情况下，依然可以编译这个项目**。你可以用另一套工具链生成这个 header，然后在一个没有这套工具链的别的地方去编译它。

所以：**没有绝对的规则。**

#### 那个检查工具，已经被大模型杀死了

我自己是做软件工程研究的。我做过一个非常标准的软件工程研究工具：去研究你的 git 项目满不满足这些 best practice，不满足的时候给你一个 warning。像 `.DS_Store` 这种东西它就得有一条规则，然后是好多好多规则，最后做成一个小工具，**在 git 提交之前告诉你 OK 不 OK**。

而现在，**所有这些东西都被大模型杀死了。**

因为大模型可以如此耐心地给你检查，还给你个 emoji 让你开开心心、缓和情绪。

举个例子。我作为导师，今天把学生叫到办公室，第一个反应肯定是"我血压上来了"。但我还得装作 nice 一点，说："你提交的这个项目不太符合软件工程的实践。"学生在那儿听的时候也肯定有压力——不管我的情绪多么正常，无论如何我只是在纠正他、只是告诉他一个知识，但"毕竟是老板批评我了"。你看，**AI 真的解放了这个同学们**。

### 用 hook 把规则焊在提交之前

我最近在做一个更严肃的项目，我希望把每一个细节都做好，就面临一个选择。

在这之前先说 hook。我们 git 提交之前有一个机制叫 hook。大家用过吗？各种各样的钩子：你可以 hook 住程序的一个函数调用，在这个函数调用结束的时候干一件事；你也可以在你的 agent 里面加入一个 hook，在某件事发生的时候干一件事。

比如我有一个 hook，会在 agent 完成、需要我输入的时候播放一声"叮"。现在你也可以直接让它配：**"帮我配置一个全局的 hook，在 agent 需要输入的时候叮一声。"** 提醒，完全没问题。你在任何 Claude Code、你的 Codex 里，它都支持这样的钩子。

然后我就可以在 git 的 **pre-commit hook** 上面做一些检查——因为我这个项目的工程标准会更高一些。

于是我就面临一个选择：**我应该选上面还是应该选下面？**

也就是说，我给我的各种规则——可能有几十个 checking rules——我要给这些规则命名，那我应该选这个大写还是小写呢？

从使用的角度上来看，两个都是好的：只要我这里没有 title、这句话里没有 type，就是 OK 的。**但到底是大写还是小写，这就是一个两难的问题。**

而你在学习和生活的过程中，会面临无穷多这样两难的问题。**如果你的每一个问题都稍微问一句，你就会有很长很长的长进和知识。**

我当场就让 GPT 解释了一下。它告诉我这只是一个固定规则的标识，还从 RFC 里给出了相应的引用；更好的是它还顺手分析了我的心理——**为什么我会觉得这个全大写会更强一点**。

如果你们能在学习 git 的过程中多问几句，把每一个细节都做好，那你们一定会成为一个 a lot better person。

### Git 是个持久化的目录树

好，该开始学 git 了。AGENTS.md 有了，接下来就是想学一学 git 到底是怎么工作的、底层原理是什么。完整的原理我在操作系统课上讲过 git 的那一段，就不重复了，这里只讲一个头。

**Git 是一个持久化的数据结构。** 它持久化的是什么？**目录树。**

因为我们说的就是不停地产生快照：版本一、版本二、版本三、版本四。那你就从这个最基础的想法出发。

#### 只复制到根的那条路径

我先举一个最小的例子。目录里有 `a.txt`、`b.txt`，我现在要创建 V2。我需要把所有文件都复制一份吗？

**不需要。**

我现在改的是 `b.txt`，那我肯定是需要再创建一个 `b.txt` 的新版本。假设目录里还有一个子目录 `D`，`D` 里有无穷多个文件——这个 doesn't matter。

那如果我想**以最小的代价记下一整棵树**，我应该怎么办？**把它到根的那条路径复制一份。** 反正我要再复制一份，但是根里面的 `a.txt`，我就可以用一个指针指过来。`D` 我也可以用一个指针指过来。

```text
   V1 快照                     V2 快照（只改了 b.txt）
   +------------------+       +------------------+
   | a.txt  ------> A |       | a.txt  ------> A |   同一个 blob
   | b.txt  ------> B1|       | b.txt  ------> B2|   复制了新的 blob
   | D/      ------> D |       | D/      ------> D |   同一个 tree
   +------------------+       +------------------+
          |
          +-- 新版本只需要复制 "到根的那条路径"，
              其余目录甩一个指针对过去就行
```

A 和 B1 都是在根这一层的，路径已经被复用了；只有 B1 到 B2 这一次是重新写的。

所以即便你的项目很大、里面有 100 万个文件，你也只需要创建一个非常小的增量。因为**目录本身就不可能很深**——没有人会去建一个 1000 层深的目录；从渐进式披露的角度，你也没有必要去建一个巨深无比的目录。只要每一级摊开的东西是有限的，你很快就能把所有的文件分完。

#### 落到磁盘上：blob、tree、commit

在 git 里面，`.git` 底下开始有各种各样的 objects。这个 objects 就是普通的文件，你看，是带 hash 索引的，然后就是各种节点：目录的节点、文件的节点，甚至有 commit 的节点。

它有三大类型的对象：

- **blob object**——blob 就是 binary，字节的序列，就是一串字节；
- **tree object**——目录节点；
- **commit object**——提交节点。

这个数据结构可以不断地**向后生长**——文件只往末尾追加，一直往后长。**这就解决问题了。**

所以你们如果从 first principle 出发，一个大学生想设计出这样一个东西，是完全有可能的。

但我讲完以后自己都有点不踏实：**commit object、tree object、blob object，真有这么回事吗？** 而且如果发生分叉怎么办？分叉以后合并到底会发生什么？根据计算机科学定律，你想要的东西就一定有人做——所以我打开一个浏览器。

### 眼见为实：把 .git 目录摊开给你看

以前上课的时候我会用一个可视化的教学工具（learn git branching 那一类的），它以可视化的方式展示 git 是怎么工作的，甚至模拟了各种各样的命令：`git status`、`git commit`（你看到右边动画了吗，它就多出了一个版本）、`git checkout`（我点这个版本的时候，可以看到版本的变化）。**这大概是古法编程的巅峰之作之一。**

到今天，我觉得就可以直接 web coding 了。虽然 web coding 的质量可能还并没有那么好，但我做了一个**直接可视化整个真实 git repo 的工具**。

我给它的提示词大概是这样的：

```text
实现一个 git 命令行工具，把一个真实的 git repo 完整可视化展示。
可以使用 git 命令，然后把里面主要概念彻底完整地可视化展示。
任何对象之前都从文件系统里的真实文件（原始 bytes）出发，
展示一步一步如何解析、解析成了什么；
要求它可视化，并且持续监听目录中 git 的变化，
发生变化后用动画效果来展示 repo 发生的变化。
```

这里最关键的一点是：**它和刚才那个可视化网站不一样。** 那个是**模拟**出来的，它自己建了一个 git 的模型；我今天这个是**在真正 live 的 git repo 上**直接看到它发生什么——从真实的文件、原始的 bytes 出发，一步一步展示它是怎么解析的。

现场你看，我直接删掉一个文件，右边的文件就没有了。

#### 三十一字节的输入解出二十三字节

我们来看这棵树。这是 `main` 分支。最早的一次提交是 "I did some cool stuffs"，里面有一个空的 `hello.c`。它来自于 `.git` 下的 `objects` 里的一个 object——**这真的是一个 blob object**，而且你能看到它的字节序列。

看到这个字节序列以后，它会帮你解压缩。然后你发现：**对于很小的文件来说，这个压缩反而是浪费**——磁盘上存了 31 字节，解压出来只有 23 字节的东西。但不要紧，这是一个 blob。

再看这个 blob，它是 15 字节的文本，里面是 `int main`。除此以外还有一个 `hello` 的二进制文件，是 158 字节的 blob，开头是 `7F ELF`，一个可执行文件的头。

tree object 同样能看到磁盘上面的原始数据：52 字节，解压出 43 字节。

#### 644、755 和那棵真实的树

解压之后以文本形式看，这个 tree 是这样的：

```text
  Mode 644  name  hello.c
      100644 blob a3f1c0...   hello.c
      100755 blob 7e2b91...   hello

  mode 644 / 755 是文件的权限位
  每个条目 = 权限 + 名字 + 指向一个 blob 的 hash
```

你看 `644` 代表这个文件访问的权限。而这个版本的根目录里有两个文件：一个 `755`（`hello`，是可执行的），一个 `644`（`hello.c`）。**这个 tree object 指向了它们，指针链接是正确保留的。**

视觉效果不完美，是因为我这是 one-shot 直出，没有改；我可能还要再给第二个 prompt 让它去掉一点东西。

#### 分支是一个文件，HEAD 是指针的指针

现在你可以创建分支了。我让它创建两个分支，左右是实时同步的，有动画效果。

这里有个东西叫 `refs`，是 `.git/refs/heads` 下面的。**所谓的分支，就是一个文件、一个指针。**

```text
   .git/refs/heads/main         ---->  [commit object]  --+
   .git/refs/heads/feature-a   ---->  [commit object]  --+--> [tree] --> blobs
   .git/HEAD                   ---->  "ref: refs/heads/main"

   分支 = 一个指向 commit 的文件（指针）
   HEAD = 指向那个分支文件的文件（指针的指针）
```

HEAD 在磁盘上就是几个字节，内容是一个文本，指向一个 tree object。你可以看到 A 分支就是**一棵树**，树里有一个新的 `hello.c`（`int main(void)`）；B 分支指向它改过的那个 `hello.c`。

#### 冲突现场：base、ours、theirs

我还可以让它展示 merge conflict 的状态。

这就回到了我们假设的两个开发者：你们两个都对这段代码不满，都做了重构，那就会进入冲突状态。A 在这，B 在那。当我把那个 A 拉到本地的时候，就会看到这个冲突状态——**冲突现场的 `hello.c` 内容是这样的**，带尖括号的那种冲突标记。

而更有意思的是：你看不到的东西，git 其实**悄悄在 index 里面留了三个版本**。

| 名字 | 指的是哪一份 |
| --- | --- |
| `base` | 分叉的公共祖先上的样子 |
| `ours` | 你这一侧、也就是你当前分支上的样子 |
| `theirs` | 你正在拉进来的那一侧的样子 |

然后我让它 resolve，你看那些临时文件没有了。而且这个 merge **创建了一个新的 commit object**：它的 tree 是这个，它有**两个 parent**（两个祖先），它还有 author，指向的关系被正确地保留下来了——它的 tree 选的是我们期望的那一版。

visualization 的视觉效果不好没关系。我相信我跟他对话几轮以后就能搞定，你就得到了一个近乎完美的 git visualization。

**vibe coding 真的很好用。** 我觉得你们这个年纪、这么有时间，最大的乐趣就是 web coding 完了以后就各种调，跟着它学，知识很快就会爆炸式地增长。

最近因为手头有一个小项目，我们也被迫从外部搞来了一个类似的东西。里面有很多 slop，都是我一句话让 AI 直接生成的；它可能不是一个 IDE 级别的东西，但效果还是不错的。

### 让 AI 守住那些没人会查的细节

> 前面这一整段虽然好像在讲 git，其实我讲的是 best practice。

如果你注意力够好，你会注意到 AI 给我的一些 commit message：**前面的都是英文，一行加一个详细解释**；后来它就有点自由发挥，开始混英文和中文了。但它还是遵循了一个格式——有些带 scope，"我干了什么"，然后一个总结，再有 message body。

#### Conventional Commits：提交信息确实有标准

这个格式你们看到很多，就知道它是有标准的。今天你已经可以找到这样的文档了，叫 **Conventional Commits**。这个 specification 文档很短，它告诉你：**commits must be prefixed by a type**——type 是一个名词（noun），比如 `feature`（我如果引入一个新功能）、`fix`（我要修一个 bug）——**后面要一个冒号，冒号后一定要有一个空格**。这些都是规范。

#### 让我浑身难受的那种不一致

然后是我和同学合作时的高血压时间：如果文档是 markdown，**英文和中文之间要有一个空格**。我不知道从什么时候大家开始用这个 convention，但好像大家都会用。比如"你好，这是 hello.c"——这就对了，这是肌肉记忆。

但如果我看到一个文档里有一些不是这样，**我是浑身难受**。你哪怕全部都是这样，我都会认为你是在遵循某一种 convention，你是保持一致的；但如果不一致的话，我真的是有点头大。

所以 AI 会把这些细节给做好。而这些工程细节其实都是为了：**工程师在面对更大项目的时候，有一种一致性和规范。** 你的代码要以同样的方式排版，很自然地你的文档也要以同样的方式排版，这样人维护起来会更好。

虽然我觉得在 AI 时代可能好像也不重要，AI 都会帮你解决。但我还是喜欢这一点：**所有用 AI 的学生都不会生成那样的 slop**，至少不会。

这里还有很多 best practice。你可以在网上找到各种 commit 约定、好的文档范例——这些东西其实都是有工程实践的经验的。回去读一下这些文档，让 AI 帮你，你就能学到更多。

### 为什么一定要及时提交

我用一个**反直觉**的推论来结束这个话题：**为什么要及时 commit？**

因为在复杂的项目里面，随着你修改的东西越多，你错的东西就越可能多。

你在小项目刚开始的时候其实不要紧，**一次提交个两三千行代码都 OK**。但是一旦这个项目里有错综复杂的关系以后，你的一个大 commit 可能会 break 这个项目里面多处的东西、引入多个 bug，后面再要引入多个 fix 来 fix 它。

这时候你有一个很大的 commit，比如 V2，你有一个 1 万行的 commit，然后后面你修了 100 个 bug，你都说这是 V2 产生的——**这就很糟糕**，甚至修不过来，你也不知道 V2 修好没有。

| 一次提交 1 万行 | 一次提交一个修改 |
| --- | --- |
| 出了问题只能整块回滚 | 可以精确 revert |
| 说不清是哪几行引入的 | **冤有头债有主** |
| 后面补一堆 fix，不知道补完没有 | 引入和修复是配对出现的 |
| bisect 只能一整个 commit 地跳 | bisect 的最小步长就是一次修改 |

而如果你每一次的 commit 都很小、都只做一个修改，那你这个 bug 就是你写的，好，我修完了也就修完了，**这两个 commit 是可以配对的**。

> **结论**：小步提交给了我们审计的能力。

它还给了我们一些别的东西。比如说你改了很多，然后不小心你的电脑物理损坏了，而你还没有来得及推到远端——你做了一个小的提交、立即 push，那么你就得到了一个互联网上的备份，**你的电脑马上坏了也好**。

这些 AI 都是很清楚的：它知道你可以 review、可以 revert、可以 bisect 刚才找到的那个东西。

### gh：让 agent 管到仓库以外

还有一些东西我后面可能会讲，比如 hooks 和 CI。但这里有一个你们如果有"惊人的注意力"应该观察过的现象。

你们的项目可能托管在 GitHub 或者 GitLab 上，那么你的 AI agent 会试图调用一些 `gh` 或者 `glab` 的命令——然后你会看到一个什么 fund 的提示，接着它就**回退到古法编程，又开始一条条写 git 命令**。

为什么？因为 GitHub 实在是太 popular 了、太好用了，所以它值得有一个命令行工具。

Git 的部分你清楚了：**它管理了好多代码的快照。** 但 GitHub 上还有 issue，对吧？我今天可以发一个文本，还可以对你的代码做 comments——**而这些东西都是不随着 git 做 persistence 的**。

那如果我们想要管理它，就做一个命令行工具：我可以去 fetch 一个 issue，可以找 assign 给我的 issue（你要登录，找到 assign 给我的 issue 以后），我还可以把这个 issue close 掉。

> **提示**：这个命令行工具对 agent 来说就很好用了。

你装了 `gh` 以后，我就可以在 agent 里面设置一个 goal：**给我完成一个（很长的任务）**，我会要求它做小步的提交、做可以审计的提交，然后说清楚怎么分支的规则、线性的历史之类的。

你可以看到我的项目里就有大量这样规规矩矩的提交，从我开始写代码起就有。很多时候我都不管它们了。

### 把项目组织成用原子变更推进的快照

这门课讲的还是软件工程，所以最后这一小段总结才是今天更重要的。

> **定义**：**把项目组织成用 atomic change 推进的快照。** 这是你们今天要记住的事情，所有的一切都是从这句话里面推出来的。

你们组织一个软件的项目，你要管理很多的快照。这样就可以随时开启一个新的分支，做一些尝试：**如果失败了，你就可以把它安全地扔掉；如果成功了，你就可以把它合并进来。** 然后你甚至可以同时推进多个主线，以合并的方式让它完成，而不会互相干扰。

因为如果你们做大作业、自己是古法去做大作业，肯定有这个感受：你要改好几个地方的时候，**改着改着很可能就改乱了**——你跟这个部分和那个部分冲突，这个部分和那个部分冲突。

> **结论**：项目管理的本质是**人类没有办法处理一团混沌**。

#### 分解成可以审计的小任务

很多需求、很多代码，依次做一大波，人处理不了。所以很自然地，我们要把需求分解成可以理解、可以审计的小任务，一小步一小步来。

这样出了问题你就可以 bisect，可以 blame；协作的时候可以 blame，发生冲突也容易解决。

**两个小任务发生冲突**——比如我有可能是在这样的一个公共的祖先上面做了好多事，但如果每一个都很小，那么如果发生了冲突，我可能就能知道**哪一个小的提交是冲突的**，剩下的不冲突的部分合并起来可能会比较容易。

#### linear history：现在更流行的那种历史

有些项目会要求 linear history。我们做更严肃的项目时，也会要求 main 上的合并是明确的合并。

```text
   linear:   (c1) ── (c2) ── (c3) ── (c4) ── (c5)
                                    每个 commit 只有一个 parent

   merge:                  (c2)        (c2')
                               \          /
                                \        /
                                 (c3) ── (c4) ── (c5)
                                 ^
                           merge commit：两个 parent
```

但现在好像大家更流行 linear history：**反正都是 AI，反正它 resolve、它 rebase 都很容易**，我就强行要求我的整个 commit history 都是线性的。

当然这个也不完全是好处，但至少对于现在我们维护项目来说，**它会让历史更易于追溯，而且它对 cherry-pick 和 blame 也更友好**。

在无限大能力的模型到来之前，这个事情都是好的：你把 git 记录拆分得非常好，你很容易找到这次修改是由谁引入的；那么 AI 维护项目的效率也会高，也会省 token 一些——**有些文件它就可以不用去读了**。

### 怎么把这件事真的做起来

我还有一些经验可以跟大家分享：虽然我们知道要小步前进，那**我们到底怎么管理一个项目呢？**

#### 架构先行：单线程，配一个高智模型

我会在**架构设计的阶段，先用单线程**，用一个智力比较高的模型跟他讨论。

这个其实很重要。**因为如果你的软件设计得不好，你后面就是无穷的迭代。** 我在第一次课的时候其实就给大家展示过这个。

为什么我这么信任 AI 的代码呢？我这里这个项目里面有很多互相关联的组件，我们的程序会产生结果、会运行产生结果，然后我拖动这个进度条——它不仅要关联到我的程序的编辑器，还要关联到上面这个。

但我把**绝大部分的接口都设置成了 functional**，就是 pure function。包括我的 trace，也是程序的一个 pure function。然后我大概有一个标准的这个程序的 **derivation graph**，我要求你按照这种方式来展开。

#### 共享状态只有十几行

然后**所有全局互相影响的状态，我都要注册到一个全局的地方**。这个全局的状态，比如说我光标的位置可能会怎么样影响这个可视化——全部都包括，这个菜单条。

这个非常干净、非常小的状态。所以你看到的这样一个 playground，基本上**核心的共享状态也就只有十几行**，十几行的共享状态，然后十几行的组装，**剩下所有东西都是黑盒子**。

而这些黑盒子，我的要求是：**agent 在设计这些 visualization 的时候，禁止看任何库函数的实现，只看接口。** 所以他的花费其实非常省——**几万个 token 就可以做一个这样的 playground**。

一旦这样的架构设计完成了以后，我就会开三个、或者开几个 terminal，然后我要求 agent 的 AGENTS.md 有一个明确的协作规则。

比如说我让它**不需要调用视觉模型去检查**——agent 很喜欢做这件事，然后花很多的很多 token；然后我也不调用浏览器任务，我在边上另外一块屏上放一个浏览器，那它是及时刷新的。

然后我就开始开三个 agent，**哪里不满意就骂他**。你就可以肉眼看着右边那个东西不断变好、变好、变好，最后问题就解决了。这是一个 agent 能力之内的项目。

> **提示**：我非常确信的是，agent 的能力会不断地增长，越来越多的项目能够被 agent 以这样的方式来完成——比较轻量的讨论，剩下交给它。

而这也是一个非常可怕的事情：**如果 agent 快了 1000 倍，我们还怎么样管理这个版本控制？** 这个我们可以下节课再来讨论。

### 收尾：把细节做好，那条 bar 会自己长高

在今天，你们真正有价值的品质，就是**你们愿意去花一点时间学习**。

然后你很快就会发现，在求职的市场上，**把细节做好的这个 bar 会不断地提高**——因为一旦有人学会了，招人的单位就会用这个标准来衡量你。

所以我觉得**上课耽误学习是真实存在的**。因为你们很多老师，真正好的东西打开都没有打开过：那些真正好的代码、真正好的项目、符合工程规范的项目，他对着课本讲一遍。和今天你看到的这个 AI 直出的东西比起来——就刚才那个可视化工具的整个框架，我大概两天的碎片时间就全部完成了，包括视觉效果的调整就完成了，就没有任何的成本。

我马上就要被淘汰了。我自己学习的时间是非常有限的，我很想学很多东西，但我不像你们有那么多时间。

需求可以往这几个方向想。

**个人数据库。** 你们这学期会碰上几门比较硬的专业课，计算机网络、概率论之类的。专业课的资料可以放进去。进了研究组以后，组里那些论文、文献、教科书也可以整理成你的个人数据库。形态不限。

**填表。** 我不知道大家是不是已经填表填得很烦了——每次都是给你一个 doc 表格，姓名、学号、身份证号，有时候还要个人简历。我现在这些事情已经全部交给 agent 了。

**把它和你的邮箱关联起来。** 如果有可能的话，比如两周以后我半夜给大家发邮件，你的 agent 把邮件回给我，一个 always on 的后台就跑起来了。你们也许可以买一个很小的嵌入式小设备，一两百块钱，放在宿舍里持续跑你的 agent loop；用你数据库里的信息去办理一号事物——其实也就一句话，直接调一次 agent 就完事了。

**手机端联动。** 做一个网页也行，一个苹果的 app 或者 android 的 app 也行。你只要让 agent 去做，它会自己把需要的东西都下载好，然后把你要的东西做出来。

> **提示**：这些需求都只是参考，它们供你参考。你实现它的时候会有一点点成就感——因为这个东西真的每个人都会需要，我自己也有一个。

### 焦油坑：为什么非得自己走一遍

你可能会问：这些任务看起来全在 AI 的能力范围之内，我直接把这个实验要求丢给它不就行了？

我今天会试，但我没试过。我的判断是：一上来 AI 会替你做出很多它认为看起来也合理的决定，而这些决定会让你的项目越来越难维护，最后陷入一个维护的坑。

所以我觉得每个人有必要亲身体验一次软件工程里的**焦油坑**——那种一旦掉进去就拔不出来的沼泽。什么时刻算掉进去了？当你的 AI agent 开始不断地消耗你的 token，而你终于有一天会下定决心：好，我要把这个项目删掉，从头重做。或者干脆回退到某一个很早期的版本，从头开始做。

这个项目我设计的时候，是相信它对每个人有用的。但我也可以提前预告一下：我的下一个 lab 会和这个 lab 有非常大的关联，而且你们暂时猜不到。你会发现，你 lab1 的实验要求都做完了，它已经变成一个非常非常舒适的个人助手——然后我给你加一个需求，这个需求和前面所有的都是关联的，并且带有一定的冲突。你去改，然后越改越崩溃，越改越崩溃，就有这么一个体验。

所以大家可以期待一下后面的 lab。如果你现在选择躺平，不管它，让 AI 直接做，下一次再把它删掉重写，那你大概就没有这个软件工程的体验了。

### 从 intent 到 spec 到实现：项目里到底装了什么

我们回顾一下上节课。上节课讲的是软件的项目管理。我们说**项目是各种文件的集合**——你的 intent、一些设计文档、你的 README，都在这个项目里。

顺便说一句，我其实不太喜欢 AI 写出来的那种非常非常长的 README。我喜欢的是对我来说有用的那种：就写一下你在设计这个这个项目时最初的初衷，你想做一个什么样的产品，这个产品能达到什么样的效果，可能配两个 screenshots，再加上你最重要的那些设计。

这是什么意思呢？有一天你突然想了一个非常好的点子，你真的想用它去挣一个亿。你要组建一个创业团队，你要说服一个 computer science 的人出来跟你干——比如说你要说服我出来干。那你其实只需要一个比较短的 README 就够了：这是你的 intent，你想做这件事。剩下的是我的事——我有架构的能力，我有写代码的能力，剩下没做完的我给你补出来。

你不需要知道这个软件系统是怎么样，它的 spec 是什么，它用什么样的数据库，怎么样支持你的用户从 1 到 10 到 100 到 100 万到 1 亿。这个定价你可能没有 computer science 的知识，但是你不需要有，你只要有那个最原始的设计，那个 intent。

然后再到 spec，就有我刚才说的那些：我要选什么样的数据库，我甚至要选什么样的编程语言，我的项目的结构是什么。各种各样的，小到比如说每个模块的接口，都属于 spec。再往下就是 code implementation。它们现在都在这个项目里。

有了这样一个项目以后，很自然地你就需要一个容器，把这些各种各样的文件给管理起来。

### 文件系统是个历史惯性，也丢了很多东西

我们说大家用文件系统来管理项目，其实真的就是历史原因。回到 1950 年、1960 年的时候，操作系统给你的存储功能就只有文件，它没有别的——那个时候关系型数据库还没有发明出来。所以所有的程序员他别无他法，只能把你的项目以文件的形式存进来。

> **结论**：所以这更多时候是一个历史惯性。用文件系统来组织项目，很可能并不是正确的组织方式——因为文件系统其实丢失了很多不适合用文件来表达的信息。

哪些信息是容易表达的？比如我的 intent、spec：我一条文档，这个地方我是怎么想的；或者这个测试用例是什么，我输入是什么、输出是什么，我要 assert 在程序的运行过程中什么东西不能被违反。这些都比较好表达。

但是你马上就会发现，项目里面有很多**隐藏的关联**，在文件系统里是没有的。

### 断掉的关联：从 linked list 换成 tree 的那一天

我举个例子。你们经常在 AI 写代码的时候碰到这种情况——现在的 agent 会稍微好一点，有时候也不会。

你跟它说：把这个实现的什么方法，从比如说 linked list 换成一个更高效的 tree 的结构，去优化性能。这是一个很常见的场景——你突然发现这个性能不够了，然后你让 AI 去做，AI 就噼里啪啦给你代码给改了。

但是你没有想到的是：你可能在项目里某一个文件的文档里、在某一个 markdown 里随手写了一句——我这个项目的数据是用 linked list 管理的。

你写文档的时候可能还没有代码，所以你就先写了那个文档，你随手一写，这是个 linked list。但是一旦你的代码实现了，这个关联又没有强行地联系上。

这就是一个技术债（technical debt）。因为以后随着文档和代码不断地向前演进，它们的不一致只会越来越多，不会越来越少。然后这个软件就陷入了一个维护的泥潭。

为什么这么难？因为后面你拿出一份代码——甚至 AI 拿出一份代码——你根本不知道到底是文档说的对还是代码说的对。你跟它聊天的那个历史没有了，你那个 chat 已经消失了；你换了一台电脑。你那个 git reflog 里面可能还有一些 change 的日志，但到最后，你真的就不知道到底是代码对还是文档对。

```text
   +----------------+  +---------------+  +---------------+
   |  design.md     |  |   hello.c     |  |  test_ok.c    |
   |  "用链表管理"  |  |  已经改成 tree|  |  只测了 tree  |
   +----------------+  +---------------+  +---------------+
          \                    |                   /
           \                   |                  /
            \__________________|_________________/
                       文件系统里的世界
```

读图：三个文件同属一个目录，文件系统能告诉你它们在同一个项目里，却没法表达"这份文档描述的正是那个文件里改掉的那段实现、而这份测试只覆盖了改完之后的行为"——这条线一旦没人维护，就再也没人知道它本来存在过。

### 树装不下的那张图：可追踪性

这在软件工程里面，是一个研究了非常非常长时间的问题，叫 **traceability**，可追踪性。你看，这已经是 2014 年的时候还在 review 的一些更老一点的文章了，它就叫 software traceability。

所谓的追踪，就是：一个软件项目当中，各种各样的测试用例、文档，哪怕就文档中间一行代码，它们之间的关联是什么？我们能不能在这个软件系统的演进过程中，仍然维持这个关联？

这是一个非常软件工程的问题。

```text
        设计文档 ──实现──> 代码实现
           │                  │
           │                  └──覆盖──> 测试用例
           │
           └────规定测试范围───────> 测试用例
```

读图：文档规定实现、也规定测试范围，实现覆盖测试；而一旦测试跑挂了，暴露的又可能是文档写错了——四者互相勾连，树的"一个父亲"结构装不下它。

所以很多时候我们觉得蛮有意思：文件系统将错就错，然后大家最后总有一天会发现，你用文件系统来管理代码，你受不了了对吧——打个压缩包发布，打压缩包发给你的合作者，这件事情已经维护不下去了。于是就有了 SVN，有了 Git。

那下一个是什么？对吧，大家有没有想过下一个是什么？我今天会讲 Git 之后的另外一个版本控制工具，它可能甚至比 Git 还要好用一些。

不过我同时觉得，刚才说到 traceability，如果以后我们都不写代码了，那软件它就不应该像现在这样在 Git repository 里面管理——我们有好多文件，什么 README.md，然后是 hello.c，还有一个 docs 下的什么什么文档。

如果所有这些东西我们人都不几乎不管了，那有没有可能把文档变成好多个切片，把它们变成好多的对象（object）或者实体（entity）？比如说这个文档和那个实现之间就有一个关系：它实现了这个文档。然后我可能有一个测试用例，这个测试用例也跟这个文档关联起来了，而这个测试用例又是和代码的这部分实现关联起来的，然后这个文档和那个文档也是关联起来的。

你看，这是一个完全结构化的东西，它没有办法在文件系统里以一个树状的形式表达——这是一个随便连接的图，有 cycle 的图。那这个东西可以放到一个数据库里，就叫这个 repo.db。

> **结论**：显然人类就没有办法用现在的这个 UNIX 世界里面的工具去维护这样的一个 repository。但不要紧，**用魔法打败魔法**——人类理解不了的东西，我们只要训练 AI；只要有强化学习的反馈信号，我们就可以训练 AI 去理解这个 repository。

这就是一个非常大的项目。什么 Linux 内核数据库，或者你们想做的一个价值一个亿的产品。

### 让 AI 当仓库的一致性守护者

那我们以后如果要干的事是什么？

你比如说这个软件系统已经在工作了，那你一般来说就是要给它增加一个功能、修改一个功能，对不对。这就跟 Git 的 philosophy 很像：Git 管理了文件目录、快照和快照之间的关系；Git 希望我们能够小步前进——我每做一件事情，fix 一个 bug，改一个文档，我都产生一个 commit，然后这样我就可以在多个人之间协作。每个人可以自己产生自己的 commit，然后我们可以用 rebase、merge，用 fast forward 或者普通的 merge，创建一个可追踪的整个项目的修改历史。

那如果我们以后也不要文件了，我们要做的就是：**让 AI 自动维护所有的 artifacts 之前的一致性。**

什么叫一致性？代码和文档必须一致——我文档里说这是 linked list，我的实现里面就必须是 linked list；我文档里说我要有 A、B、C 三个方面的测试，那我这个 test case 就必须要有 A、B、C。它们都是关联起来的。

然后呢，Git 教给我们的是小步前进。那当我们谈"要做一小步"的时候，其实我们知道这一小步是干什么的，所以你可以直接跟 AI chat：哎，我现在发现它有个 bug；或者我今天对这个幻灯片的样式不满意。那这就其实就是一小步。

在一个大型的软件系统里面，绝大部分的内容跟这一小步都是没有关系的。比如说我对这个幻灯片的样式不感兴趣的时候，你可以直接看我的 repository 顶层的结构：我有些 assets，然后甚至还有 .cache 这个缓存的系统，然后有各种以 P 开头的一级目录，再有一些脚本等等。那任何一个软件系统，当你只做一小步的时候，你就只需要看到这个软件系统的一小部分，大部分东西应该是无关的。

既然是无关的，那我们可以让 AI 根据我们的 chat，把和我相关的东西给摘出来。

AI 有什么能力？AI 有动态生成任何内容的能力——**everything is code**，content as code，代码可以表达任何东西。所以 AI 可以根据我的 chat，生成一个和我要改的这一小步相关的 **view**。

你们在各种系统里学到的这个概念，还是有用的——不是所有的同学都学过数据库，而数据库里有一个叫 view 的概念，它说我们的数据就在这儿，但我可以创建一个不一样的查询，可以把它以另一个形式展示出来。这就是很简单的想法，我希望把这些数据以另外一个形式展现出来。

但比如说我打开这个 view 的时候，我看到的就不是这些代码、文档、diff，而是**一个可视化的看板**：上面列出了和我这小步相关的一些东西，然后问我要改什么。我一把改完了以后，同样还是从一个 V0 到 V1，它还是一个 repo.db，但是这一小步就会把这些相关联的地方给改掉——比如我要增加一种类型的测试用例，那它就会在这些地方加一些测试用例，有些地方可能要改掉。

从各种复杂的关系这样一个一致的状态，做一次小步的修改，到下一个版本。这样的话，软件工程就又变了，彻底变了。我觉得这是未来有可能发生的——在 AI 内部，它是这样生产软件的，从此以后我们也就再也不要看代码了。

你现在看到的这种现代 IDE，比如 Cursor，我其实还蛮讨厌的：它现在打开默认就是 agent mode，原来那个我们熟悉的 IDE 界面它就没有了，强迫你用一个类似 chat 的方式去跟他沟通。但因为我还是相对来说比较精通古法编程的，有时候我还是对代码有一些掌控欲——这个可能是不好的，这个可能是不对的——但是未来可能会是，这可能是一个途径。

那你们当然会焦虑：如果未来这件事真的有可能发生，而且一两年以后大家就真的有一个公司把这东西做出来了，那我们学那么多东西怎么办？

其实你回头看就会发现，我们在创造这些东西的过程当中，用的都是你们学的那些经典、集大成的 computer science 课程。我刚才说的数据库里的视图，我借用了数据库的概念：实体和关系。我借用了 Git，但这个模型没有变——Git 长期的开发经验告诉我们，我们要一步一步向前。如果在这个模型底下我们是大步向前，那就惨了。

当然也有可能发生：模型非常强，一个非常大型的项目，一步就变成下一个了——这个怎么做，我们现在还并不知道。但是至少在初期，我们可能还是要沿用过去的、大家积累的软件工程智慧去小步向前，然后通往那个极乐的世界。但我还是相信这个极乐世界有可能确实是能到的。

### 一个 valid point，和一条斩杀线

我上上节课问过同学们 `git rebase`，然后大家都知道 `git rebase` 是什么吗？都不知道。然后有一位同学 raise 了一个 valid point，他说：学生时代大多数人是不会和他人共同合作的，也就是做作业，所以 rebase、merge 用的场景就很少。

这个 point 是对的。就你们做作业的时候，确实确实不会。

我的回应是大概这样的：如果你真的去往这个外面的世界去走一走的话，这个互联网开发者社区铺天盖地都是文档，所以你一定会在某一天看到别人的项目里有一个 `CONTRIBUTING.md`——那是仓库根目录下的一份贡献者指南，通常回答"我怎么参与这个项目"。然后你看它里面就有这些：项目的总体结构、分支、提交信息、PR 的规范和流程。

那如果你看过很多项目的 `CONTRIBUTING.md`，你就随手打开看一眼，如果你发现里面东西都知道了，那你就知道了。如果你不知道——你一定会看到一个项目里面写着一句：我们必须要在你自己的分支上 rebase，我们禁止你创建那种分叉的 merge，我们要保持现行历史。到那时候你就会知道 rebase 是干什么的。

有人在底下问过什么是 rebase，没关系，错了就错了。

> **提示**：我觉得有一种状态其实不是批评。学生时代就是这样——在高中时候，老师不教的、考试不考的，就是你不需要会的，为了升学的利益最大化，这个选择是完全正确的，没有错。但是到大学以后，如果你们还带着这个思维的话，你就会有这样的 gap，一种新人类和旧人类之间的 gap。当然我相信每一个同学也还是可以成为新人类的，那你只需要花一点注意力去注意到更多的东西。

因为我现在有一个危机：**AI 时代的斩杀线以下的价值就全部归零。**

当然我觉得斩杀线现在可能还斩不到在座的各位——985 同学、computer science 专业的同学。但是那些低级的智力劳动，比如说会计从业者，我看过一个报道说中国可能有上千万；那这个行业里面顶端的人，暂时肯定还是没有威胁的，但是在底下的这大量的人都面临着被 agent 替代、被斩杀的这种危险。所以你们需要在这些经典的课程上——不管是操作系统、编译器，还是软件工程——这里面的经典智慧你们要学到一些，然后最终形成你们自己的理解。

### merge 丢作者，rebase 改历史

好，回到 Git。Git 管理的是快照，也就是一个目录，整个 Git 可能也就是这样一个东西的一个快照。我可以在快照上面做一个开发，它要求小步。

那我现在有一两个开发者，一个是 A，一个是 B，我们就可以独立地在这两条线上做开发。

```text
        C0 ──┬── A1 ── A2        (A: 先改文档, 再加测试)
            │
            └── B1 ── B2        (B: 先加 feature, 再加测试)
```

读图：两条线从同一个基线 `C0` 出发，各自攒下两个快照；`A1`/`A2` 与 `B1`/`B2` 代表的都是"一次修改"。

如果你要把它们合起来，在 Git 的原始模型里面，rebase 相对来说是不那么提倡使用的。它是说：好，你会创建一个两路的 merge，它有两个 parent，继承了这两边的修改。

但是这又带来一些问题。比如这个 merge 完，比如说 merge 是由 A 来干的，那这个 merge 里面的这个一些内容、由 B 写的这些内容，它的作者就变成 A 了。

它其实有一个隐藏的作者信息：比如说 B 在这儿加了一行，在这个地方可能还能追溯到 B。但是一旦发生冲突，在 resolve 的时候，冲突解完以后，这个提交就是由 A 完成的——这是 A 完成的。那这 B 改的代码，最后 ownership 又归到了 A。所以这会带来一些相对来说有一点点小小的小麻烦。

然后 rebase 解决了这个问题。

rebase 说的是：不是直接把他们两个东西创合成一个"把这两条线并起来"的提交，而是我试图先试试看——有没有可能在这个 A 的后面，把这个 feature 加上。如果加上了，OK，那就成功了，这就成功了。

```text
  merge:
        A1 ── A2 ──┐
                    ├── M      (M 有两个 parent, 署名 A)
        B1 ── B2 ──┘

  rebase:
        A1 ── A2 ── B1' ── B2'
                      (一条直线, 两个新 id)
```

读图：merge 保留了所有旧 id，只多出一个 M，但 M 的作者是执行合并的那个人；rebase 换来一条线性历史，代价是 B 的每一次提交都被重放成了新的 id。

**但这有一个很大的风险。**

第一，我可能在这个里面加入了一个测试用例，然后这个测试用例和这个 feature 就是不兼容的——这是有可能的；或者甚至他们就改了同一个地方，我做了两个完全不兼容的东西，那这个时候是有可能失败的。

第二，一旦冲突，你就需要 resolve，你会进入一个 rebase 的模式。你们如果进入过这个模式，会发现瞬间自己就不知道应该怎么办了。这时候你就打开你的 agent 说：哎，我现在发生了什么。然后 AI 会细心地解释给你。

更麻烦的是，你就算把 feature 搬过来了，你搬 test 的时候又要失败，你还需要再把 test 搬过来。而且每一次你都会创建一个新的提交——每一个 commit 都有 id。Git 里面修改是用 commit 来代替的：好，我现在有一个 commit，然后这个 commit 和它的 parent 之间的关系，就叫一个修改；它没有一个专门的叫 change 的对象。

那如果你是一个两路的 merge，那所有这些 id 都保留了，你会创建一个新的 id。但是因为你是 rebase，每次这样的 rebase 就会创建一个新的 commit——因为这个快照本来这个 base 在这儿，所谓的 rebase 你就知道它要把 base 改掉，要把这个 base 改到这里来，那 rebase 就会创建一个新的 id。然后这个历史就变了。

然后你会感觉到这里有一点点轻微的不一致：就觉得你好像不是完全要这样去管理软件。因为我们关心的是修改——我希望的是把这个修改搬过来，把这个修改搬过来。

> **易错点**：rebase 换来的线性历史不是免费的。每搬一次 commit 就换一个 id，历史被改写；一旦中途冲突被 resolve 掉，作者归属和原始 id 就都找不回来了。

### 把 change 变成一等公民

那如果我们把 change 也变成 first class citizen，会发生什么呢？

那就等于发明了下一代更好用的版本控制系统——把 change 也提升成和 commit 同级的一等对象。底下那套模型没变，但多了一个 change 的概念。

它可以把好多的 change 直接搬过来。比如 rebase 的时候，他会把 change 直接搬过来。change 还是有可能冲突的，冲突是解决不了的——但是因为它有这个 change 的 object，它可以把这些 change 一路带下来，生成一个直接 rebase 到这里的结果，只不过里面引入了好多冲突。它还是运用了 Git 的那个冲突记录，但它有一套自己的记录方式，把所有这些 change 的冲突也都塞进去，然后你可以在这里相当于把它们搬过来，然后在这里再 resolve 它的底层模型。它没有变，但是你用起来会舒服很多。

然后它有一个非常好的特点：**它不需要 staging area。**

你在 Git 里面最讨厌的是什么呢？我上操作系统课的时候会讲这个例子。

你现在有个工作区，你现在有个 repository，然后你现在改了——比如说你有一个 `hello.c`，然后现在把它改到一半，改改改改改到一半，这个时候项目还不能编译，也不能运行，测试也通不过。

突然导师给你打电话："哎，我现在有一个很高很高优先级的项目，这个有个 bug，马上客户那边这个项目就要交不了差了，这个 bug 赶快给我修好。"那你怎么办？你不应该 commit。你现在要把它加到你的这个 index 里面，然后 `git stash`，然后他会压栈。

然后这其实是一个比较讨厌的操作。因为你 `stash` 是一个东西，你要去把原来那个 bug 开始修。你刚修到一半，你的导师又给你打电话："这个 bug 别修了，我还有一个更优先级更高的 bug，你去把它修好。"你这时候要再 `stash` 一次。

那 `git stash` 是一个栈，然后它里面就会有好访问——好多好多个提交，然后你需要去管理那个 stack。

```text
  [ hello.c 改到一半, 不能编译 ]   <- 收工时的现场
         |
         | 导师来电: 先修 P0
         v
  [ stash@{0} ]                   P0 修到一半, 又来电话
         |
         | 再 stash
         v
  [ stash@{0} ]                   P1 ...
         |
         v
  [ stash@{1} ]                   原来那个 hello.c
```

读图：`git stash` 每压一次多一个栈帧，导师连着来电两次，现场就被埋到第二层以下，取回顺序全靠人记。

但是你想想看：如果你想象你在任何时候、随时随地都在编辑这个 repository——**这不就是一个 change 吗？** 你现在把 `hello.c` 改一改，加一行减一行，它都是 change。

所以 jj 好像是在干一件什么事呢：好像是你但凡改了一个字节，它都会立即做一个 commit。当然这个 commit 不会产生好多线性的历史，而是先把上一次的那个提交抹掉——你改了一个字节，那上一次的那个提交就被抹掉了——然后你用当前这个修改去替代这个提交。

也就是说，你永远处于一个"当前有一个 change、当前有一个 snapshot，它是处于一个提交的状态"，那你就很舒服了。你连这个 staging area 也不需要了。

你从"要把 change 作为 first class citizen"开始，你再往后推，你就可以发明自己的版本管理系统。当然这还不是它的全部，然后它还有一些别的路线可以推导出来。

你们适当的时候可以质疑一下：比如说你觉得 Git 哪里做得不够好？如果可以做得更好，还能做怎么样的设计？所以我觉得这是很有趣的、非常有趣的一些设计。你们可以在 agent 的带领下，或者是说我开了一个头、我给你们一些 motivation，你们可以把最重要的这些 prompt 交给 agent，说我想从 change 开始理解。

> **结论**：所以你们作为 AI native 的人类，能够淘汰掉我们这一代人——就是因为我已经形成了 Git 的肌肉记忆了，然后比我更老的一代人已经形成了 SVN 的肌肉记忆。而一旦人形成一个肌肉记忆以后，要把这个习惯掰过来就很困难了。
>
> 就比如说我现在对 Git 是有肌肉记忆的，但是我即便是能够理解 jj 的概念，甚至我可能理解得比你们这些初学者还要更好，我甚至可以从我的 first principle 去思考它、自己相当于 virtually reimplement 这个系统，但是我依然没有足够的时间再去训练另外一个肌肉记忆。
>
> 所以你们是跟我正好反过来的：**你们应该在你们现在还没有形成记忆的时候，就直接去用那个对的东西。** 人类历史都是积累的嘛——SVN 实在用不下去了才用 Git，然后 Git 发现了 Git 的缺点以后有了 jj。所以你们可以先用肌肉记忆记住一个最正确的设计，然后再去理解这个设计是怎么样。等你再回去想的时候：哦，原来 Git 这么蠢。在 Git 出现的时候，大家会觉得它很先进，它是一个不可变数据结构（immutable data structure），而 SVN 从一开始就走的是另一条线。到现在你再回去看的时候，就会发现原来 Git 也犯了一些设计上的错误——当然这是因为它最早的时候没有想过 rebase 会有这么大的 impact，它有 merge 就已经能解决它手上的问题了，所以他没有把这个概念模型想得更加清楚。

但这门课不是软件工程，这门课是**生成式软件工程**。所以我们真正要做的事是：在 agent 的时代，再次重新设计版本管理系统。

### 人是单线程的，Agent 不是

我们一路走过来，SVN 有局限，Git 有局限。那在 agent 的时代，我们的局限在哪里，我们要破掉的改进是什么？

刚才所有的版本控制系统其实都有一个假设：**这个版本控制系统的使用者是人类。**

人类有什么特点呢？人类是一个 **single-threaded** 的生物。

我上操作系统课讲并发程序的时候经常打比方：你就把线程想象成是一个人，然后你的线程可以访问共享内存。那访问共享内存的时候，两个基本的操作是 load 和 store，或者说 read 和 write——我可以从一个变量里读一个值，我把 x 读到我的临时变量里；或者我可以写 x 等于 1。然后这个操作是不能同时进行的，你不能说既读一个又写一个，这样就需要一个原子指令了。

那绝大部分的 shared memory access，你能想象成人是什么呢？

我如果想要观察这个世界——对不起，我手要背在后面，我只能看。然后等我看完了，比如说我看到这个同学在这儿，我想要对他施加一个效果，比如说我用粉笔扔他。那当我真正要 write 一个变量的时候，我必须要把眼睛闭起来。

而我把眼睛闭起来扔的时候，注意：我读到的那个值其实已经失效了，那个值已经是旧的值，就是我上一个时刻读的。那在上一个时刻到这个时刻之间，可能经历了很多的事情——可能我被换 CPU 换下去了，我被中断打断了，然后换了另外一个线程上来执行，可能执行了一秒钟以后我才恢复过来。但我恢复过来以后，我看到我在寄存器里面 x 值上次读等于 1，然后这个时候我就把那个粉笔扔出去了，那很有可能就扔错了。这就是 single-threaded。

当多线程共享内存带来无穷问题的时候，其实人类也是这样的。人和人之间是有这个无法逾越的物理屏障的：你不能理解我的思想，我也不能理解你的思想。我就是一个独立的个体，由分子把我很强地连在一起。所以我们只有一双眼睛、一双手、一张嘴。

那我们在编辑这个代码库的时候，以这种方式编辑代码库、产生 change，那就是以**小时**为单位的。

一个软件公司负责一个模块的开发，可能多也就十几个人，十几个人已经是一个不小的团队了。那十几个人每个人以小时为单位开发，那最多也就是以 10 分钟这样的单位产生一个提交。

好，10 分钟为单位产生一个提交，意味着这个速度会比人和人之间沟通的速度要慢很多。因为尤其是一个 team，他们工位都在一起——你们研究生的工位都在一起。你马上要写一个东西，要写一两个小时，你在写之前你肯定跟师兄说一声："师兄我要干个这个行不行？"二十秒钟、三十秒钟，师兄说"行，你去改吧，我们现在不再改"。或者你们去厂里面打工，厂里面可能每天早上都要开会，每天早上的 leader 都会把任务分配出来：今天我们要干什么事情，你做什么、你做什么。你就提前在大概半小时的时间里划分了一个 scope，把这个项目切开了，你领了其中一部分走，然后你就去产生提交。

当然这是古法编程。

在古法编程的时代，你就看到 stash 是一个合理的设计。因为刚才说的那个情况——导师给你打电话——这件事情是可能发生的。但你在修到一半的时候，导师再给你打电话，这件事情是不太可能发生的，发生概率是很低的。绝大部分时候你的 stash 里面就一层。如果你有好几层，你关起来其实挺麻烦的，还有一点麻烦，你还需要去 rebase stash。所以你会尽可能地保证这个 stash 不要太深。因为你可以拒绝一个工作，或者你会说，我手上有一个更高优先级的工作，我现在对不起，我不能干这个事，然后等你干完了以后，你自己可以排一个队列。

所以 Git 是给人用的。

> **易错点**：但是在 agent 的时代，这件事情变了。如果是一个 agent team，单个 agent 它生产这个的速度就远远快于人。它生成东西以分钟级为单位，甚至更快；有时候你让它 fix 一个东西，它在上下文是热的时候可能就几十秒钟，它干活的时候就几秒钟就做了。那当 agent 以秒级工作的时候，**以秒级就可以产生一个原子提交。** 并且你可以轻易地得到一个十倍、一百倍的 agent team——这时候 Git 或者 jj 这样一个为人设计的模型，就确实是有一点跟不上这个速度了。

就算是可能大型的项目，它也有一些门控——就是我写完了以后、改完这个部分以后，它必须要经历一个测试的流水线，那这个测试可能本身就要运行几分钟，那可以放缓 agent 的提交的速度。但是毫无疑问，agent 加速了这个软件开发的过程。

那如果 agent 加速了软件开发的过程，我们应该怎么样为 agent 设计这个版本管理系统？

### 每个 agent 一台机器

首先我们可以让 agent 沿用人的模型。

每个 agent 都有一个自己的开发计算机——A 这有一个自己的开发计算机。那我们就把 single-threaded 的人类和 agent 做一个严格一一对应的类比：让它有一个独立的电脑，可能是个容器，然后把它连到一个远端 git 仓库上。

然后你直接 instruct agent：

```text
我的这个 remote 仓库是在 git 上的。
你现在就是一个单人开发者。
你可以从 tmux 里面收到命令。
收到命令就可以开干。
```

所以这件事情其实是非常容易实现的。

你看我实际在你们实际开发的时候，这两个 tmux session 都是位于两台不同的机器，或者不同的容器——他是物理上隔离开的，他看不到世界上其他的人。他还故地用了一个可能在中国现在还能用的词，叫 `master`。

```text
      master agent (监工 / 协调)
      |           |           |
      agent A      agent B      agent C
    容器 1       容器 2       容器 3
      tmux         tmux         tmux
      |           |           |
      +------------+-----------+
                   |
          remote: git 远端仓库
```

读图：每个 agent 是一个物理隔离的工作环境（一个容器 + 一个独立的 tmux session），各自连向同一个远端仓库；`master` 只做协调——观看它们的输出、总结报告、往里 inject prompt，本身不直接上手写代码。

然后你看，当 AI agent 变快的时候，你想一想：如果你的指挥发生一点点差错会怎么样？或者就现在一个流行的 paradigm：你有一个监工的 agent，然后你有好多个子 agent。

比如说，为了最大化模型的智力、防止 AI 生成你不想要的东西，你会放两个比较强的模型：由 Codex 来设计，然后让 Claude 来 review，然后让他们互相打架，然后达成一致。你只要开两个 tmux 就行了。然后你的主 agent 负责协调，就观看他们的输出或者总结报告，然后往里面 inject prompt，这样一个多 agent 就转起来了。

然后我看一下这个 repo status，诶，然后你就发现：**如果大家工作在同一个 git 仓库上，就会有一些麻烦；但如果他们工作在不同的 repo 上，就是完全可以的。** 他们可以合到一块，可以去远端拉取别人的提交，冲突了如果冲突了就会自己修复，而且在必要的时候，他甚至还可以给这个 master agent 发消息。

你们立即就可以构建出一个这样多 agent 的系统。

那相应的，我们今天也有一些 work around——比如说 Git 就有 `worktree` 这样的功能。所以我就可以问 agent：

> "Git 的 worktree 可以改进这样并行的工作方式，那能不能让这两个 tmux session 都工作在 worktree？"

**提问其实是关键的。** 你们甚至比如说今天早上走到教室在看微信公众号，上面说起了 Git worktree，或者他提了一个什么样的 sandbox container，你就可以立即让 agent 帮你试一试，然后我来看一看他在做什么。诶，这不是一个相对来说比较容易的任务吗？OK，他确实是在写脚本。

这是当前的 Git worktree。Git 允许我们创建一个工作树——这个工作树你可以想象成就是连接到了一个 remote，就是一个 git repository；然后我可以在这里面，在一个**隔离的环境**里面做独立的提交。

大家都知道 `.git` 是什么：`.git` 是一个目录，然后它里面有一些东西，比如说 `logs`，还有 `objects`。那 worktree 里面的 `.git` 是什么？

## 版本控制的边界：worktree、锁与团队
> 对应块：BLK08 | 覆盖分集：P05下 | 块标题（分集名）：《软件仓库管理 (2) [04-Raw_26生成式》

点开一看，不是目录，是一个普通的文本文件。

这就是今天开场这一幕。`git worktree` 加出来的那一坨东西，`.git` 在新工作区里不再是一个目录，而是一个文件——一个只有一行内容的文本文件。你要是继续追问 agent，它会告诉你：这个我一开始也不知道，`get` 的除了可以是目录以外，还可以是这样一个格式的文件。文件里写着一个 `gitdir`。

```text
main repo/
└── .git/                      <-- 真正的 git 目录
    ├── HEAD
    ├── index
    ├── locks/
    └── worktrees/
        └── wt2/               <-- 一个微型的 git 目录
            ├── HEAD
            ├── index
            └── locks/

worktree2/
├── .git                       <-- 一个普通文本文件（不是目录！）
│     内容只有一行：gitdir: /abs/main/.git/worktrees/wt2
└── src/...                    <-- 你的源码原封不动在这
```

看这个结构就能明白 Git 有多"抠"：worktree 2 的 `.git` 文件里只写了一个路径，指向主仓库 `.git/worktrees/wt2` 那个**微型的 Git 目录**，那个目录里也还是 `HEAD`、`index`、`locks` 这三样。它依附于原有的那个 Git 目录而存在，但因为是独立的一份，所以每个 worktree 都可以有自己的一套索引和锁，谁也不干扰谁。

> **结论**：Git 最大限度上复用了操作系统里的现成机制。worktree 不是新发明，它就是"一个目录 + 一个指向别处的文件"——操作系统早就有的那套"文件即对象"的套路。

那这东西对 agent 有什么用？我之前说过，我开了好几台虚拟机，每台虚拟机里放一个 agent，然后我直接往那个 `tmux` 里面注入任务，这当然完全可以完成。但是 worktree 提供了一种更清晰的合作方式：**在本地直接互相可见，不需要互相 push**。提交就摆在那儿，谁都能看。

> **注意**：但"更清晰"不等于"免冲突"。如果有互相冲突的修改，它仍然需要 `merge` 和 `rebase` 才能合并。乐观的空间是省掉了"传"，没省掉"合"。

好，回到 agent team，甚至 agent swarm。有了今天这些 work-around 之后，我们还要**回头来问一句：为什么我们需要版本控制？为什么需要版本管理？**

### 人十分钟才产出一个 commit

因为版本控制这套东西，说到底是**被人的限制塑造出来的**。

我刚才说了，一个小团队，哪怕只是一个团队，**十分钟才产生一个 commit**。就这个节奏。一个人平均十分钟才提交一次改动——改个 title 也要做一个 commit，做点什么也要做一个 commit。

再往深一层看，版本控制的形状是被**人之间的沟通成本**塑造的。你每天早上都要开一次会，同步各个人的进展，然后再把任务分下去。而且就算做了这样的沟通，你也都知道，有时候你想向你的室友请教一个数学问题，明明你会做，你就怎么都没办法给他讲明白。除非你是一个非常好的老师，能共情别人，能站在别人的角度去思考——而这个能力不是人人都有的。

**沟通的成本就是很高的。**

这就解释了大厂和小厂、尤其是初创公司和初创团队的效率差从何而来：当软件系统大了、人多了以后，沟通效率变低，产出的速度就降下来了。所以一个 100 人的团队，不可能达到 10 人团队效率的 10 倍，可能有两倍、三倍就已经挺不错了。

> **结论**：**团队没有办法变大**，这是硬约束。正因为团队变大不了，我们才需要 Git 里各种各样的 best practice。

这些 best practice 是什么？**快照，然后小步前进。** 改一个 title 也要做一个 commit，做点什么也要一个 commit。而且这些小 commit 每个都可以追溯——因为一旦出了问题，你需要回溯到"那个人做那个 commit 的时间"。为什么回溯到那个时间有用？因为**那个人是有记忆的**。开发者会回想起来：哦，那天早上我们开了一个会，我收到要做这个需求，做这个需求的时候沟通发生了一个问题。大家找到那个时候的沟通记录文档，然后说，这个地方应该怎么修正。

所以 `git bisect`、`git blame` 这些特性，是**专门为人设计的**——它们服务于"追责 + 回忆"这条人类特有的链路。

### agent 不会坐牢，于是我们不再需要 blame

现在把上面那条链路整个拿掉想一想：如果你的项目是由 agent team 或者 agent swarm 来实现的，**我们还需要 `git blame` 吗？**

因为人可以 blame。"这个事情我 blame 你太多了，你就该被开掉了是吧"，实习生你就背锅了。但 agent 没有坐牢、被开除、开除的能力。**当被 blame 的那个实体不会受到任何惩罚的时候，这个模型就变了。**

我们再也不需要 blame 了。我们的项目只要前进就可以了。而且有时候我们甚至不需要知道到底是哪一个提交引入了这个错误——我只要知道这个地方错了就行了。我也不要管历史上是怎么造成这个错误的，我只要把这个错误修了就行了。

> **结论**：**历史的价值，从"谁写错了"变成"我怎么把它修好"。**

这里还有一个更有意思的理由，而且这是我们跟人不一样的地方：我们的每个 agent 用的是**相同的模型**。也就是说，它们是完全相同的克隆体。同一个事情让它们来做——同一个 prompt、做同一件事——它们大概率会收敛到相同的方向。模型确实还有不确定性，可能有点细微的差别，但最终那个方向性的东西很可能收敛到同样的结果。

既然结果会收敛，追究"这是谁干的"就彻底没有意义了。

但是——**快照肯定还是需要的。** 这一点不能跟着 blame 一起被扔掉。因为方向走错了怎么办？如果你没有保留历史上某一个 snapshot，等你一下子往前走了好多以后再回去，可能那个代价比你一点一点地往前修要大得多。所以**保留快照肯定还是需要的**。

那最后剩下的历史是什么？`git` 的 commit 里面只是留了一些 lessons，或者我们这个项目到底经历了什么样的演化。合并、合并、合并，不停地往前走。

> **易错点**：不要把"agent 不需要 blame"理解成"agent 时代不需要历史"。**快照和教训要留，责任归属可以扔。** 一旦出方向性错误，没有 snapshot 你就只能从零重来。

### git 的乐观并发：先都跑，撞了再说

这一段是我讲操作系统和数据库时候埋的伏笔，现在到兑现的时候了。

现在的 Git 模型，**更像数据库里面的并发控制**。你想想我们数据库课上讲的东西：有两条 SQL，对吧，每一条都是一个 transaction，一个很大的 transaction，里面可以混任何代码。你先 `select` 一下，我这里也 `select` 一下；我读完以后可以做代码的计算，比如一段 Python 代码或者 JavaScript 代码——而这个代码是**图灵完备**的，你永远不知道它会根据我读到的结果算出什么；我甚至还可以从外面根据当前的时间再算一个什么东西。算完以后我再 `update`。

`update` 的时候就会产生冲突。两个 update 如果互相要读对方，就产生了循环依赖。有可能是数据的依赖，也有可能是"我要锁你的对象、你要锁我的对象"这种锁的依赖，产生死锁。这时候就会导致这个 transaction abort——对不起，我检测到一个循环依赖，所以我这个就不能做下去了，我要 **roll back**。

那 Git 的模型像哪种？**像乐观的并发控制（optimistic concurrency control）。** 为什么它是乐观的？因为它就假设这两个 transaction 不会冲突：我执行的时候假设它们不会冲突。

> **提示**：这个假设在数据库系统当中是大概率成立的。为什么？想想教务系统——你们每一个同学读的都是你自己的数据，写的也是你自己那块数据。我选课选的是我的课，我查看课表看的是我的课表。所以全局的冲突是不太可能有的。我两个同学哪怕同时开始选课，我也是读我的、写我的，这两个就可以并发地过去。

Git 也完全是这样。我假设我们这样开发：今天早上已经开过会了，所以我可以顺着这条路先做这个，另一个人做那个；然后我合并的时候大概率不会产生冲突。不管是 `merge` 还是 `rebase`，都能顺利完成。

**但这是古法编程时代。** 如果我们的 agent 快 1000 倍，而我们的主 agent 在协调的时候又一下子分了好多任务出去呢？他们就真的会**更频繁地触发 transaction abort**，更频繁地触发这种死锁。

> **提示**：好消息是，在 AI 时代，abort 也不是什么大问题。反正 agent 出错了、或者出了 conflict，他自己就能修好。

### 换成悲观锁：先声明，再动手

那问题就来了：在 agent 的时代，我们可不可以**换一种并发控制的方式**？

回到操作系统。你在操作系统课上学并发控制，用的是什么？**上锁。** 我上课时经常说一句：**"一把大锁保平安"**——做实验你们就知道，这句话是有分量的。

它的逻辑很清楚：当我想要访问一个可能冲突的资源的时候，我会先把它锁住，说"我先要占了一把锁"。这把锁一旦占上，别人想要再 lock 的时候，对不起，就必须等到 release 之后。一个"acquire 的锁"和"release 的锁"的关系建立起来，就必须是**先一后二**——而不是乐观的那种"大家先往前跑、跑了再说"。我必须要在**使用这个资源之前**就 declare 它的使用，上锁的方式。

现在把这两套摆在一起对比一下：

| | 乐观（Git 现在的方式） | 悲观（操作系统的锁） |
| --- | --- | --- |
| 前提假设 | 假设彼此不冲突 | 不假设，先声明 |
| 动作时机 | 先干活，撞了再说 | 动手之前先 acquire 锁 |
| 冲突处理 | 事后 `merge` / `rebase` 重来 | 申请不到就排队等待 |
| 关系 | 可以完全并行 | acquire / release 必须先一后二 |
| 适合什么 | 人之间，冲突罕见 | agent 之间，快 1000 倍，冲突频繁 |

那么按悲观锁的思路，agent 时代应该怎么做？

```text
        ┌────────────────────────────────┐
        │  主 agent：只规划、只分派、只加锁  │
        └───────────────┬────────────────┘
                        │  规划完立刻把项目的某一部分锁上
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
    agent A         agent B          agent C 想要同一块
   锁 src/api/      锁 src/ui/          ✗ 拿不到锁
   独立推进          独立推进             排队等前面那位
    commit           commit          （等待期间去干别的活）
        └───────────────┴────────────────┘
                        │
                        ▼
              冲突几乎被消灭在发生之前
```

具体一点：一个主 agent，我规划完了以后，就立马把这个项目的某一个部分给锁上。我可以把这个 Git 做成"我应该在一个 reflog 或者一个快照上支持一个锁的操作"，把这些 scope 说好：我现在锁住了，我做一件事需要这些，我先上锁，上锁以后做，做完以后 `commit`。然后另外一边也可以上锁，但如果他想要干的事情被另外一个人锁上了，他就必须等到前面那个人释放了锁，才能再上锁。

**这样不就几乎避免了所有的冲突吗？** 比方说我可以在**文件级**上锁，这就避免了两个 agent 同时去写同一个测试、往同一个配置里面做更改。

那这不会把并行度卡死吗？不会——因为 agent 数量足够多、速度足够快，我还是可以保证整体项目的进度往前推，**因为也许还有别的 agent 可以继续运行。**

这跟我们写并发程序是一个道理。如果你"一把大锁保平安"，或者哪怕你的锁设计得再精巧，**互斥锁的本质就是要不要并行，它和多处理器并行是有根本矛盾的**——它不就要把一个能并发并行的程序，退回成一个串行程序吗？

但是，当这个系统里面有很多独立的、互不冲突的线程在运行的时候，我即便每一个线程都持有了一把锁，它还是可以继续高效地推进。**即便是悲观的，依然可以是高效的。**

> **结论**：这些知识关联起来，你就看清了在 AI 时代，版本控制**有可能被重新设计**。从 first principles 出发——我们要管理快照、管理版本、管理 change，还要管理**飞快的 change**。Git 可能是一条线；用另一种方式来管理软件，可能是另外一条线。

有人会怀疑：学数据库还有用吗？AI 都会写数据库了，C 端查询我早就不写任何 SQL 了。**答案是有用。** 数据库里面也有 advisory lock 这样的机制。而且这也是我为什么喜欢上课——我如果不来上操作系统课、不上这门课，我在备课的时候就不会把这些事情在脑子里再过一遍，去问一句"是不是地球上所有人都错了"。因为我要讲给你们，我必须**共情我的听众**：我的听众只能接受比较平实、朴素的逻辑，听众不能直接说"哎这个事务系统是怎么设计的"，我必须把最顶层的 idea 提炼出来，试图让大家共情。当然这个我可能做得不够好，你们可以在 AI 的帮助下重新理解一遍。

### 版本控制是工具，难的是进度

版本管理，从历史动机讲到过去的 Git，讲到现在，讲到未来可能发生的事情，基本就讲完了。

但是——**版本控制本质上还是一个工具**。哪怕是我刚才说的那种基于乐观锁或悲观锁的版本控制，它也还是工具。**真正困难的实际上是在"进度"上，也就是团队的管理上。**

那我们为什么现在觉得还需要软件工程？因为我们现在**没有办法做到一句话就直出一个高质量的产品**。

你想象一下"斩杀线"到了是什么样子。老板有一个想法，随口说一句："我要做一个 agent 用的微信"，或者说"做一个 AI 时代的微信"，这个微信是一个社交爆款，以后这些人社交可能就不用微信了，就用我这个。你可能有一个更具体的想法。

**如果这时候 AI 直接就能出微信级的产品，那软件工程就已经死了，我们也都死了。**

但是现在这个斩杀线暂时还没有到。所以至少在团队管理这一层面，我们可能还要学。

不过我总觉得，也许有一天我也要被拆掉。因为摩尔定律本质上也是 scaling law，它现在还是成立的：模型肯定会更强、更小、更快，然后也许算力有一天能够"唤出"我们的智能。**但今天，至少 AI 还不知道怎么做团队的管理。**

为什么？因为每当你多一个人的时候，**沟通的关系是平方级上升的**。

所以现在软件工程团队里面，最难招的其实不是码农，是**那个能把任务分解的 team leader**。这个人在市场上最稀缺——他能把"我要造一个微信"这样一句话，分成"我这一百个人的团队，分出十个小团队"，然后十个 team leader 各自去干，最后拼起来还能成为一个整体。接下来那个能够带领小团队的人，其实也很稀缺。

《人月神话》里讲的就是这个：**人之间两两之间的沟通关系是平方级的。** 而且就算你能把自己份内的事情做好，正因为这个平方级的沟通关系，别人也在做他的事，你不是百分之百知道别人在做什么事，或者你对整个团队的了解不是很好，最后就会各种冲突——最典型的就是：**你写的测试，我过不了。**

### 当一次主 agent：分解、提交、迈小步

那我们能做什么？如果我们想要管一个团队，或者说你们在今天、想要在毕业的时候具备一定的团队管理能力，那你现在就可以把自己当成那个**主 agent**。

> **提示**：刚才我给了一个不好的示范——我说"我今天创了两个 slave"。但你其实现在也可以立即拥有这个 Codex v4 的 slave。所以你要去想的是：如果你要尽可能最大化两个、三个或者更多 agent 的产出，**你应该怎么把这个任务分解？然后你应该怎么样确定一个提交的策略——什么时候你的 agent 应该提交，什么时候它应该合并？**

你把刚才讲的那些版本控制的概念，带到你自己的开发流程里。

重要的一句话是：**版本控制是工具。** 它蒸馏了人类过去软件工程很多年的经验，得到的是"我们要人类这样开发"。**然后在这个工具之上，你可以开发出属于你自己的软件工程直觉和经验。**

学东西还是有用的。学 Git 是有用的，学 multi-agent 的管理也是有用的——它能让你有一个机会，去想一个**和不太一样的设计**。

### 它照你说的做了，却不是你想要的

我最近看到一个蛮有意思的题目，插一段题外话，回头再讲。先说现场。

项目早期你肯定不能用 multi-agent。**项目早期你就是包工头。** 先找一个——应该是找——一个相对来说能力比较强、你能用到的最强的 agent，然后跟它多轮地对话。所以我决定现在就开始，直接打开课程作业。我不知道会发生什么，完全没有事先准备过。

有两种办法。第一种是直接回车，这个其实每个同学都可以体验一下；当然今天我替大家体验。我觉得更好的方式是**先观察它会做什么**——因为**有时候 AI 的直觉和人的直觉有点不太一样**。

比如一线模型，它会进入一个 plan mode：先跟你再确认，再确认一些事实，然后它再去生成一个 workflow。你们如果看过 Claude Code 就会发现，这还挺好玩的：当他要执行一个比较复杂的任务的时候，**他会生成一段 TypeScript**，这个 script 里面有一个函数叫 `agent`，而这个 `agent` 里面是一个自然语言。当他用这种方式来组织 workflow，他甚至可以有循环——我有好多任务，他可以在循环上面来来解决这个 workflow。

你看到他就直接开干了吗？用魔法打败魔法——每秒钟烧掉 300 token，这个速度实在是太恐怖了。

然后你就发现，**这正是我前面讲的上下文工程、提示词工程里面最危险的一点**：

> **易错点**：**你提示词里面的每一句、每一个词，self-attention 都会看到它。** 而 AI 现在已经被训练成了 prompt 的舔狗，它有一种"没有办法往外拉"的倾向——需要遵循你的指令。

所以当你把一个需求——尤其是一个**讨论稿式的、比较开放的需求**——丢给它的时候，它会**过度遵循**这个指令，最终生成一个**确实满足了指令、但其实不是你想要**的东西。

你回头去看那个实验要求，这个实验要求其实是**言外之意**：其实是"实现一个持续为你工作的个人助手"这一句最重要，其他的话相对来说就没有那么重要——那些只是一些解读。你作为一个好的、为你工作的个人助手，你觉得哪几条比较重要？

那你们觉得，如果要实现一个你的个人助手，什么最重要？你实现的第一个 feature 是什么？你想实现什么？最大的就是——**你可能在一个月以内遇到的最大的痛点问题**。学习。对吧，高效的学习和复习，因为你们要卷成绩，这毫无疑问是最重要的一个方向。所以最好是 agent 能自动从外网收集数据，然后以层次化的方式归档，最终给你一个比较好的界面。这才是你最想要的。

> **提示**：你再看那个结果——我估计他十有八九没有。他这是在做 `database`。他先在搭数据库。

**在没有你精心设想过、讨论过的时候，AI 基本上就只会生成一套 scaffold（脚手架）。** 也就是说，其实你脑袋里所想的那个东西——你的 intent、你的 specification、你的 intention——和产出之间有巨大的 gap。但是当这个模型一看到"你要实现这个"，它就真的是去实现它了，于是做了一些不好的事情。

比如说我提"一号"（教务系统里那个一号）的时候，我真正需要的是一个 **browser-use agent**，它能帮我在各种网页上处理各种事情；**一号只是作为测试的出口**，它能把我的个人信息登到一号上面。所以我第一步实现的时候，就不需要在教务系统上面做太多的设计——**作为过渡设计，反而不好**。

你看，他做的所有的事情，从 `README.md` 来看，**全都是正确的，没有一个错误**，但最终他得到了一个你不想要的东西。

> **结论**：**一个"每一步都对"的过程，完全可以通向一个你根本不想要的结果。** 这就是"照你说的做"的危险。

而且他甚至**都没有创建一个 git repository**。你看，你不跟他讲——当然我觉得如果是 Codex 的话，他可能还是会初始化一个目录，或者他会问你：这个项目应该怎么管理？

如果我是一个成熟的产品经理，老板跟我说这个需求，我**肯定会在写下第一行代码之前**，先跟我的团队沟通一下：项目怎么管、协作怎么做、每天什么时候开会。**而 AI 好玩的地方就在于：它直接上手就做。** 它觉得 OK，这就是一个用一次就丢掉的东西。

感觉他烧了我不少 token，也无所谓了——我参与 DeepSeek 内测的时候，他送了我 1000 块的额度，到现在还没有完全用完。

所以你们在刚开始的时候，还是**要回到项目、回到管理的脑袋里**：要有一个这样的模型。**你不能直接把任务就丢给 agent。** 你现在想的是：第一件事一定是创建一个空的 repo。创建完了以后，你就会想你的下一步要迈向哪里。

> **结论**：**AI 从零开始做一个东西，产出 slop 的难度，比它到一个成熟的项目里面去做一个维护性的任务要大很多。** 因为维护性任务的上下文全在仓库里，而从零开始做，什么都没有。

### MVP：最小版本逼你想清楚什么才是绝对要的

如果你真的要从零开始构建，更符合主流 best practice 的做法，是用一个叫 **MVP** 的框架——minimum viable product，最小的验证版本。

这里有一句话：

> the biggest risk in product development is building something nobody wants

**产品开发中最大的风险，是造出了一个没人想要的东西。**

你看刚才那个东西，他做的东西就是我不要的，这个东西里绝大部分部分其实不是我想要的。我刚才在他读代码的时候已经解释了，我其实真正想要的是什么。

所以如果你要做一个最小的版本，**它其实逼迫的是你要想清楚：什么样的需求才是你绝对要的。**

回到那个个人助手——我刚才已经说了，如果我要做一个个人的助手，我最想要的是它能有让我**提升学习效率**的能力和**提升工作效率**的能力。

你总结出了这两条以后，你可能在**第一个 MVP 里面没有任何的数据库**，对吧。因为你会想到：在任何时候，当你文件系统膨胀的时候，你都可以跟 AI 直接说"按照这个数据的组织帮我提炼出一个数据库"，这个问题就结束了。

所以你不需要在刚开始的时候就做数据库。因为**一旦你带上一个数据库，你每次数据库重构，都需要让 agent 做一次这个 database 的迁移；而文件系统不一样，文件系统你自己就可以在文件管理器里去调整它的目录结构**，一点一点梳理到你舒服的结构上。

你调文件和调 database 的 schema，**心智负担是不一样的**。人类已经被训练过了，对直观的东西训练得非常舒服——文件目录在计算机里操作，你从小学上电脑课开始就在做这件事了。但一旦你要操作一个 database schema，很多同学还没有上过数据库课，你根本不知道它是什么。面对一个未知的东西，你仍然需要强行做一次概念的翻译：这个东西在我脑袋里是这样的概念，我要把它翻译到数据库里是这样的——**那你不如用一个你已经适应了、已经熟悉了的 system。**

我自己的例子：到现在为止，我自己回邮件的那个 agent，**没有用任何的数据库**。它的流程大概是这样的：

```text
邮箱
 │
 ▼
邮件 agent：收信，只取 email id
 │
 ▼
共享云盘（自动同步）
 │   email id 里面装着 AI 解析出来的东西：
 │     · 我回复的草稿
 │     · 这封邮件的分类
 │     · 是不是垃圾邮件
 ▼
下一级流水线：去处理这些产物

全程：没有数据库
```

也就是说，我先要明白的是：**我的系统里面有哪几级流水线，然后这几级流水线之间它们应该怎么协作，哪些东西通过云盘传。**

而因为我很喜欢我的云盘，"是不是引入云盘要做一些架构的修改"——我希望邮件和资料等都和云盘保持同步。**这，就叫需求的更改。**

### 好架构的标准，是需求变了你要改多少

那到底什么是一个好的软件架构？

当然在当前的时候，你有一个需求，现在实现可能满足这个需求。**但是，当你的需求发生变更的时候，你相应做出的那个变化是"摧毁性"的，还是"背上了一个技术债"，还是别的——那就不知道了。**

我真正需要的是一个**能扩展的架构**。你马上就在刚才那个例子里看到了：他要生成一个挣钱的产品，去挣这帮小学生的钱。但当未来有别的需求来了，AI 模型发生了变化——我其实在想的场景是，我的合作模式发生了变化：**AI 助教有可能是文字的助教，有可能是图像的助教，有可能是有交互的，有可能没有交互。** 它各种各样的需求在不断变化的时候，我还有没有可能，让我的架构**以最少的变化去应对需求的变化**？

这个恰恰是大家在软件工程课上学不到的，操作系统课也不教。大家都说好，操作系统就是长这样的、数据库就是这么设计的、并发控制要这么做——**都是有原因的**。但**软件工程讲得最不一样的地方，就是对未来需求的变化。**

那么当我们真的要用一个 team、或者跟一个学生去谈要设计一个什么软件的时候，我的问题就是：**你能不能以不变应万变？** 也就是说你现在设计的这个架构，或者设计的这个流程方法，能不能抵抗未来需求发生的根本性变化？

回到那个生成的设计：它有一个 SQLite 数据库，用户资料放这里，邮件归档也放这里，索引草稿也仍然在 DB 里。**现在看起来还不会引起很大的问题**，因为绝大部分情况都是这样的，数据库确实不会引起特别大的问题。

但是随着项目不断推进，你会发现自己其实只有**两种开发方式**：

- **一种是，你上来就是一个大的**，好几大步就把需求都实现完了，然后**拖着这个技术债不断地往后迭代**，往后加功能、加功能；
- **另一种是，从最小处得到一个特别精巧的架构。**

我为什么这么举例？因为你发现，**当我用 Git 来管理这些学生的提交以后，很多事情都变得非常容易，我自己控制起来也会轻松很多**——直到遇到性能瓶颈之前，我都不想要把它迁移到任何一种数据库。

> **结论**：**你早期那个 prompt，对整个项目走向的影响是最大的。** 你最早直接把 `README` 丢给它说"我要做一个 MVP"，这件事本身就会对项目造成很大的影响。

### 版本管理做的三件事

最后收一下。如果你在这两节课里听我们讲版本管理，你要记得**版本管理做的三件事**：

**记住现在、记住历史、记住教训。**

这三件事在 agent 时代和古法编程时代**都成立**。

第一，**你需要一个 repository**——不管是一个 C/C++ 项目，还是 Python、JavaScript 的项目，你都需要把文件管起来。第二，**记住历史**，是为了有一天这个东西不要了，或者你删掉了一个东西，最终发现它对你是有用的，你还可以把它捞回来。而且在这个提交的历史过程当中，**你能看到你是怎么演进到一个点，然后发现这件事情失败了**——这个失败你可能就会留在这儿，然后你会回到另外一个点，再开始另一条正确的路线。第三，**记住教训**：这些 lessons 不停地警示你，你需要怎么做，你需要怎么样**从第一步开始迈出向后的一小步**。

而你要走的这第一步，特别朴素：**第一件事一定是创建一个空的 repo。** 然后创建完了以后想下一步往哪迈——**不能一下子迈一大步，你要往前再迈一小步。**

### 本讲提到的题目

我最近看到一个蛮有意思的题目，作为一个面试题，在网上刷到的，也不知道为什么就看到了。它是那种小学生奥数难度的题目。

> **题目**：汉诺塔。把 $n$ 个盘子从起始柱移到目标柱，标准规则是一次只能移动一个盘子、大的盘子不能压在小的上面。**额外加一条限制：所有盘子的移动只能往同一个方向进行，不允许折回。**
> 问：$n = 3$ 的时候能完成吗？请输出移动方案，或者输出最少步数。

你要是只有两个盘子，四个方向都可以移，所以你根本看不出问题——随便往哪边挪都是"合法"的。但你**三个盘子的时候就能看出问题**：你想先把两个移到中间，可是在这个单向的限制下，你做不到。

保研面试差不多就是小学生难度嘛。你们要是碰到这个题，你是要输出方案的，或者输出这个数字。

我讲的不是这个汉诺塔的"故事"本身，那个故事是讲递归的：你要把它移过来，先得把它移到这里，让最大的盘子向右移一个，然后再把它移到这里——**讲的是最大的盘子**。你考虑最大的盘子的最优解，它考虑的是：**最大的盘子总是向右移一个，再向右移一个**。

这就是我准备了一个小例子、也写了一个小程序去验证的那个东西。**为什么它是最优的？因为我最大的盘子的那个移动是最少的，这是不可避免的。** 在单向的限制下，最大的盘子必须从起点一路走到终点，它的移动次数有一个谁都绕不过去的下界；而我的方案恰好卡在这个下界上。**剩下的部分就基于归纳法（induction）递归处理**——两个盘子的问题是三个盘子问题的缩影，按同样的规则递归下去，得到的整个方案也就是最优的。

难吧？你很难想象小学生能做出这样的题。

但这不重要。**重要的是我们现在要推出这个产品。** 比如说我现在要把这个东西卖给小学生，那我怎么样才能最好地把这个产品卖给小学生呢？当然是提供付费的增值服务。

首先是一个纯粹的开发 **playground**：他可以在这里写代码，代码可以随时编辑，比如我可以再写一个——他就错了。我的可视化是跟着代码运动的，我就能找到 bug：我找到我这条语句，试图把一个蓝色的小的移到大的上面，同学们就能找到 bug 了。

然后到这个时候，我就要提供一个 **AI 助教**——当然这个是不是不太好啊，开玩笑的，我们还是尽可能以一个便宜的成本提供给小朋友们。**当你实在做不下去的时候，你可以点一个"我要助教"。** 然后这个时候 DeepSeek 的 token 就开始燃烧了，这样我就可以收取比 DeepSeek 原价更贵的 token 费，记在你的账户上。

因为**我的 prompt 是我独门的**。我作为一个有经验的老教师，我可以把我自己蒸馏成 prompt，然后敏锐地知道**这个小朋友的问题在哪里**，给他提供一个个性化的指导。

这个过程中，我就涉及到要做一个信息系统了。而做这个信息系统——因为我有这么大的市场、我有这个钱，我竟然都不想挣——我让我学生来做。我自己没有时间。学生设计完那一版之后，我看了学生和 AI 聊完的那一版设计，也让那个 GPT 来梳理了一下需求。它给的是一个 API 应用、一个关系数据库、一个对象存储，然后需要异步或定时的话再加后台任务进程；数据库存关系和记录，大课程包与完整轨迹放对象存储，任务量小时数据库任务表就够用。

> **易错点**：这是一个**非常正常**的设计——如果你们上软件工程课，那太正常了。GPT 毕竟是一个语言模型。

**但我不喜欢这个设计。** 为什么？因为你们有没有用过 Overleaf、跟别人协作过文档？Overleaf 是有一个功能的，**它可以把它当成一个 Git 仓库导出**。

我最喜欢这个功能的原因是我要给学生改论文。改论文的时候，我就可以直接 agent 启动：把论文克隆到本地，**我就不需要忍受那个网页界面了**。然后我打开我的 Codex，让 Codex 帮我直接给每一个 `.tex` 文件都去修复里面的语法错误，我可以给一个很长的 prompt，让它遵循某个质量标准，改论文就改好了。

那回到这个 playground。我难道不应该是**学生每改一次就自动做一个 Git 提交**吗？比如说我现在 idle 了，或者我点运行了，或者我切换了页面，我就自动做一个 commit。然后当我申请 AI 助教、他在那里转圈圈的时候，我就可以在那个 Git 提交上面产生一个分叉，产生一个新的 commit。

> **提示**：**GPT 没有算到的是：产生这个东西的成本，远远大于把剩下的东西 persist 下来的成本**——这个成本是可以忽略不计的。

所以**在最开始的时候，我甚至可以把代码库和这个东西连在一起**，把它放在我的代码库里：我的小朋友的代码就直接存在我的代码库里，我可以在上面创建**探索性的 Git 历史记录**。然后直到我认为——比如文件目录的格式、commit message 的格式、我怎么样使用这些文件——**都收敛了，我再把它迁移到数据库**。

这都是可以的。我觉得这个就还是挺好玩的。**你们学任何东西都是有用的**：学 Git 是有用的，学 multi-agent 的管理也是有用的——它能让你有一个机会，去想一个**和别人不太一样的设计**。
