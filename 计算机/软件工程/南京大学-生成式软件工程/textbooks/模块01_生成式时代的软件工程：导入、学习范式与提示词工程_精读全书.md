## 把“会做事”交给 AI，把“知道要做什么”留给自己
> 对应块：BLK01 | 覆盖分集：P01上 | 块标题（分集名）：《课程导入与「未来已来」的开场》

我按下了 `F`，Neovim 里的浏览器打开了。我们正式开始上课。

今天其实从一个很简单、但又很重要的问题开始：我们正站在一个交叉路口上。作为 computer science 的学生，我们从入学开始就会接触计算机发展的历史，而在计算机的历史上，真正改变我们生活方向的，往往不是某一个单独的技术，而是某种能力突然从昂贵的东西变成了日用品。

从 PC 到互联网，从互联网到移动互联网，再到今天的大语言模型和 Agent，变化一次比一次快。我们不能再只用“以后会不会用得上”来判断一项技术值不值得学，因为这一次，技术正在直接改写学习、工作，甚至人与人之间建立联系的方式。

### 从昂贵能力到日用品

1975 年，`Altair 8800` 代表的 PC 时代还远不是今天人手一台电脑的样子。那时的计算能力非常昂贵。后来，互联网把机器连接起来，连接的是所有人；移动互联网又把连接带到了几乎每一件日常事务里。

我对互联网早期有一点很具体的记忆。小学快毕业的时候，我装过一个叫 `ICQ` 的软件。腾讯的山寨版后来叫 `OICQ`，再后来才改成 `QQ`。那个时候，可以随机添加世界另一端的人。对方往往是 native speaker，英语打得又快又多，而我们当时可能刚刚学会 `hello`、`good morning`，完全跟不上他在说什么。

再后来，移动互联网的变化快得像“一夜之间”。很短的一段时间里，菜场里卖菜的人也有了支付宝和微信的二维码。大家不只是通过网络聊天，而是把收款、交易和日常生活都搬到了网络里。到了 2022 年，ChatGPT 又把这种变化推到了另一个层面：人和 AI 的交互，第一次让很多人感受到一种新的、直接可以使用的通用能力。

```text
昂贵的计算机
    ↓
互联网连接所有人
    ↓
移动互联网进入日常交易
    ↓
大语言模型成为可对话的通用入口
    ↓
Agent 开始替人调用工具、完成任务
```

这条路线有一个共同点：能力从少数人才能拥有的资源，逐渐变成普通人随时可以调用的基础设施。我们今天要讨论的，不只是“模型有多强”，而是一个人如何在这样的基础设施上重新安排自己的工作、学习和创造。

### “AI 替我上大学”：两种焦虑

前一段时间，有一种很有代表性的说法，叫“AI 替我上大学”。我觉得这句话说得非常对。

一个理想的、但也可能危险的闭环是这样的：老师用豆包出题，学生用豆包做作业；作业交给 AI，考试答案也交给 AI。看起来所有环节都完成了，但真正没有受到训练的，可能只有学生自己。

过去，操作系统作业曾经把大家折磨得很痛苦。可是现在，coding agent 已经可以把作业链接丢进去，甚至你连链接都不需要明确告诉它，只要说一句：

> “蒋老师的操作系统课第八个实验，能不能帮我实现？”

它就开始工作了。我们当然要警惕这种用法，但如果还沿用过去的学习方式，等于主动放弃了新的学习工具。

第一种焦虑是：所有事情都可以让 AI 完成，那我最后什么也没学会。假设每门课都开卷考试，每张试卷都能让 AI 答对，甚至最后每一门课都拿到漂亮的成绩，可一毕业发现自己被 AI 第一个替代，怎么办？

第二种焦虑来自另一种同学：延续中学时期“老师说什么就做什么”的习惯，每堂课认真听，每一次作业认真做，四年下来确实学会了一些东西，可是这些东西 AI 都会做，那自己到底留下了什么？

在保研和求职越来越卷的现实里，这两种焦虑会汇合到一份简历上。

#### 看起来完美，却没有信息增量

我收到过很多简历，也看到过一种很有代表性的“AI 完美简历”。

这份简历的排版很整洁，个人信息被处理得很干净，复制粘贴以后会看到一个个 Unicode 方块，像是真的把隐私都隐藏了。上面有实习、奖项、论文，还有一篇 CCF 期刊论文，状态写着 `accepted`。如果只看形式，它几乎无可挑剔。

但对我来说，这是一份零分简历。

因为它没有额外的信息：没有 GitHub 链接，没有个人主页，也没有一篇能让我看到的 preprint。除了“有很多经历”之外，我不知道这个人到底做过什么、怎么做的、为什么值得继续了解。经历堆得越满，反而越没有辨识度。

更糟糕的是，我收到过无数份这样的简历。你有一大堆实习，我有一大堆实习；你有一大堆奖项，我有一大堆奖项；你有一大堆论文，大家也有一大堆论文。所有人都像是在同一个模板上填满了字段，你和竞争者之间就没有区别了。

> **易错点**：简历不是经历清单的加法。把更多项目名称、更多“accepted”堆上去，不等于提供了更多可验证的信息。真正的问题不是“我有没有”，而是“别人能不能从这些内容里看出我做过什么”。

### 软件工程究竟要解决什么

这门课叫“生成式软件工程”，但它首先仍然是一门软件工程课。

软件工程要解决的事情其实很简单：怎样让软件工程不失败，怎样造出一个软件来。这里的“造”不是把代码敲出来就结束，而是要让需求、设计、实现、验证和后续维护形成一套能够交付的东西。

我们经常问，人和 AI 比起来，优势在哪里？我不想把这个答案简单归结为“人更聪明”，因为这很快就会过时。比较重要的能力至少有两种。

第一种是信息差。你拥有别人不知道的信息，才能做别人做不到的事。往年试卷只有你有，当然可能在竞争中胜出；社会上也广泛存在各种信息差。这个能力有用，但它不是大学教育最应该交付给你的东西。

第二种更重要：你能够驾驭别人驾驭不了的东西，或者驾驭 AI 暂时还驾驭不好的东西。大学希望培养的，不只是一个会完成考试的人，而是一个能够提出问题、定义问题、组织工具、承担结果的人。生成式软件工程要尝试的，就是建立驾驭 AI 的能力。

> **定义**：在这门课里，AI 不是替你生活的自动售货机，而是一个能够被指挥、被检查、被纠错，也可以被带去做更大事情的协作者。

我希望通过 web coding 找回学习软件工程的快乐。做出一些有趣的东西，在做的过程中理解软件工程是怎样工作的，也让自己在简历上留下真正能被别人看见的东西。一篇论文可能是加分项，实习和奖项也可能是，但它们都不能代替你亲手完成过、并能够解释清楚的作品。

### 把上课本身做成一个可迭代系统

我自己的上课方式也在尝试变成一个软件工程项目。

我会先写一份 markdown 讲义，在上课之前想好大概什么时候讲什么、使用什么例子，相当于先给 AI 一个约束。上课时，我再通过 `F5` 播放 slides；有紫色的部分，就是模型在已有讲义上添油加醋扩展出来的内容。你可以把它理解成：左边是我提前写好的 source of truth，右边是根据这些内容即时生成的演示。

我会让一个负责把 markdown 加工成 slides 的 skill 工作。它从选中的片段出发，扩写出 markdown slides，再交给浏览器渲染；图片则全部由 AIGC 生成。每一页不是从零开始，而是从已经确定的讲义和上下文里长出来。

这个过程并不是“让模型随便发挥”。我换过好几个版本的提示词，每个版本都重新生成一次，再让另一个模型盲评不同版本的 slides 质量，最后选一个相对更好的结果。我还会用一个 AI 耿同学 skill，生成三个不同 personality 的 sub agent：有的负责一个方面，有的负责另一个方面，它们在隔离的上下文里工作，最后由主 agent 汇总。

这就是我所谓的“用算力换智力”：我多付出一些算力，让不同角色从不同角度思考，再把结果收拢回来。上课像一场演出，我需要调动情绪、举例子、和大家交流；但演出结束后，不能只把录像放一遍就算完成。我还要 review 今天的表演——某个例子可能不够恰当，某个案例换一个讲法可能更让人感同身受。

```text
markdown 讲义（source of truth）
          │ 选择需要展开的片段
          ▼
      Agent 扩写与生成
          │
          ├── 不同 personality 的 sub agent
          │       在隔离上下文中提出不同观点
          │                 │
          │                 └── 主 agent 汇总、复核
          ▼
    markdown slides + AIGC 图片
          │
          ▼
      浏览器渲染与课堂表演
          │
          ▼
       录像与课后 review
          │
          ▼
   切片、重新整理、回到 content—test—code
```

我甚至觉得，录像可以被重新切片，再回到最初的内容、测试和代码里，把一次不完美的课堂表演继续补充。这样，课程就不再只存在于某一次上课的现场里，而会逐渐沉淀成一个可以被维护的程序。将来我不上这门课了，B 站的操作系统课录像也可以被整理成这样的内容，由全世界的人继续维护，每个人都能定制出自己的操作系统课程。

> **结论**：课堂不是一次性消费的内容，而是一个持续编译、持续 review、持续版本化的项目。模型负责扩大探索空间，人负责确定什么值得保留、什么必须修正。

### 课程政策：先实践，再谈传统编程

#### 禁止古法编程

这门课不要求大家按过去的方式上课。对于想听知识、拿知识的同学，我完全建议既不用到课，也不用看直播；真正重要的是跟着课程里的案例去实践。我会带大家做很多真正的实践案例，让大家看到 AI 时代里，学习方式和工作方式都可以怎样改变。

所以课程的第一条要求是：禁止古法编程。

我相信你们每个人都是古法编程的好手。为了考试、为了保研、为了机试，把自己关进小黑屋，刷题、熬过一套又一套的标准流程。总有一天，这个事情会改变，只是从上而下传导不会那么快，因为改变一个体系很难。我想先撕开一个小口子，让大家早点感受到另一种工作方式。

#### token 自费，但不必迷信昂贵模型

我给课程定了一个看起来有点过分的政策：`token` 自费。

我个人觉得，如果手上没有 token、没有付费 token 的同学，应该立即退学。这不是说每个任务都必须消耗最多的算力，而是说，进入这个时代之后，至少要愿意为调用这些能力付出成本。硅谷有一种“死命烧 token”的工作方式；我的课上不会要求每个人都用最贵的模型。

除了 slides 生成使用一个更聪明、能够提供更好质量的模型之外，课上大部分演示都可以用相对便宜、智能程度足够的 DeepSeek Flash 类模型完成。你们喜欢夜里工作，正好，白天上课，晚上做作业，也正好是“梁文峰时间”。你可以准备大约 100 元的 token 预算；如果确实有困难，可以来找我一起想办法。

#### 用项目和最终产物接受检验

我希望用“通过或不通过”来评价这门课，但具体标准还在调整。因为大家可以使用不同模型，模型质量不同，同一个任务可能做得好、做得快，也可能做得差。我们暂时没有办法限制大家使用什么模型，那就要换一个更接近真实世界的检验方式。

我建议大家实现一个自己的 email 管理系统：它跑在宿舍里一台一直常开的电脑上，课程中可以通过邮箱通信。有人做得复杂一点，有人做得简单一点都可以，我会用邮箱给大家发邮件，大家再把邮件返回回来。

分数在这个时代可能变得没那么重要。真正重要的是，最后找工作或者保研的那一刻，你的简历上有什么东西。为了走到那一刻，你可能仍然需要 GPA，甚至需要 `reward hacking`、把考试题目 `overfit`；但大学阶段最后接受检验的，是那份交出去的简历能不能把你带到下一个更高的平台。

我希望每个人最后都能在简历里写出：我在生成式软件工程里实现了什么，有哪些链接，完成了哪些设计和实现，哪些地方真正做得漂亮。

还有一个让我觉得既兴奋又害怕的想象：如果每个人的电脑上都安装一个监控，那么四年里做过的事情就可能全部被记录，AI 也许能够判断一个人是怎样度过大学的。它知道你每一次摸鱼，也知道你看过的每一个不想让别人知道的内容。这个世界什么时候会演进到那一步，我不知道；但至少在这个问题上，我希望我们保持开放。

### 大语言模型：先理解它在预测什么

好，吓人的部分说完了。我们先吸一口气，回到可以实际使用的部分。

我不打算从训练一个模型的细节开始讲。对使用者来说，首先只需要理解：大语言模型可以怎样工作，以及我怎样和它交互。

大语言模型可以先被理解成一个概率分布。概率统计课上抛硬币时，你可能根据前面几次结果，推算下一次出现正面的概率；大语言模型做的事情在形式上有相似之处，只是它面对的不是六面硬币，而是一整本书、一段很长的文本，甚至一张图像。

给它一本已经写完的书，再在最后加上一个问题，比如“能不能帮我总结一下这本书”，它就会不断预测下一个 token 的概率。输出一个 token，再把这个 token 接回上下文，继续预测下一个 token。重复这个过程，文本就一段一段地长了出来。

```text
已有文本或图像
      + 结束处的用户提示
              │
              ▼
       预测下一个 token
              │
              ▼
       把新 token 接回上下文
              │
              └── 再次预测，直到形成回答
```

模型很大，见过世界上非常多的东西，训练它也很困难，这也是 frontier lab 很强、但训练门槛很高的原因。不过我们站在使用者的视角，不需要先掌握“单元模型”之类的内部知识。只要知道存在这样一类东西，打开网页或 API，体验它，回答问题就够了。

我第一次真正被大语言模型“按在地上打”，是在 2023 年 GPT-4 的时代。我让模型给我的五岁孩子解释什么是扫描电子显微镜。那时的 prompt engineering 很重要，我希望它用朴素的语言打一个合适的比方，帮助孩子理解。

有一次我给孩子讲故事，讲着讲着突然卡在“扫描电子显微镜”上，自己讲不下去了。GPT-4 立刻给出了一个比方，而且比我想的更好。

它说，假设你有一座山。山是什么形状？闭着眼睛看不见，但你又想知道它长什么样。怎么办？你可以闭着眼睛朝山扔石头。某些方向扔过去，石头会穿过去；某些方向扔过去，石头会弹回来。弹回来的声音能告诉你哪些地方挡住了，穿过去则说明那里有空隙。像 `retracing` 一样，慢慢就能推测出山的形状。

五岁的孩子不可能百分之百听懂，但他确实抓住了这个直觉。更让我震惊的是，我后来特意查了资料，发现这个比方是对的。新的、带 reasoning 的模型还能给出更严谨的解释，而不是只停留在一个好听的比喻上。

在 GPT-4 时代，我们要精心调 prompt，才能让模型稳定地给出想要的东西；到了 GPT-5.6 这样的时代，很多工作已经变成一句话的事情，不需要再为某一个模型反复做特别调整。

### Agent：把模型放进执行回路

大语言模型本身只是预测下一个 token。Agent 则把这个能力接到了程序和工具上。

模型可以输出一个特殊 token，表示“我要调用一个 `bash` 程序”。这个程序执行后，结果再送回 Agent；Agent 读取结果，决定下一步做什么，然后继续循环。这样一来，面对一个比较复杂的任务，它就不只是回答一次，而是可以不断尝试、观察、修正，直到任务完成。

```text
用户提出复杂任务
        │
        ▼
模型预测输出或工具调用
        │  ┌── 普通文本：返回给人
        │  └── 特殊 token：调用 bash 程序
        │                    │
        │                    ▼
        │              程序执行并返回结果
        │                    │
        └────────────── 回到 Agent 循环
```

这正是 ReAct 类型的 agent 的基本形态：模型负责推理和决定动作，工具负责执行，执行结果再成为下一轮推理的上下文。过去我上操作系统课时，agent 还会频繁出错，任务常常完成不了；今年再上，它已经非常能用了。它会不停地在配置目录里尝试修改，错了就换一种方法，直到把事情做成。

我自己的终端就是一个很直观的例子。以前看到别人用花里胡哨的终端，我也想搞一个，但改一点配置就可能出错，`ls` 的输出不漂亮，窗口管理器也不顺手。现在我只给 agent 一个自然语言要求：把我现在的命令行终端配置成现代、好用的样子。

它帮我配置了高对比度、适合课堂展示的界面，去掉了不必要的顶栏；把系统进程查看从普通的 `top` 换成了更现代的显示；我输入 `ls` 时，它自动把命令替换成 `eza`；我输入 `find` 时，它又替换成 `fd`。所有这些配置都是 agent 做的，我只负责提出要求、让它再检查一遍。

> **结论**：agent 的价值不只是“回答问题”，而是可以观察当前系统、修改配置、运行验证，再根据结果继续调整。它把“给建议”推进到了“交付一个可运行的结果”。

### 想象力是 Agent 的上限

作为 AI native 的一代人，第一步就是开始使用 agent；第二步就是随时问它。这里没有“我还不会用，所以先等别人教会我”的必要。先给它一个合适的指令，再通过配置文件和工作目录告诉它当前的背景。

比如在仓库里放一个 `AGENTS.md`，然后问它：

> “你是谁？”

它会知道自己正在生成式软件工程的课程仓库，而不是一个只知道模型名称的聊天窗口。它能看到自己的课程身份和上下文。这个过程说明，agent 的起点不是某一条神奇的命令，而是你愿意给它什么样的环境、规则和任务。

在这个意义上，想象力会限制 agent 的上限。你没有想过可以让它做什么，它就很难替你打开那个可能性。

#### 一句话装好 Linux U 盘

我最夸张、也最能说明问题的例子，是我给 U 盘装 Linux。

我上操作系统课时一直有一个特色：带一个装着 Linux 操作系统的 U 盘，插到教室电脑上直接启动。以前我是个“装机仙人”，在 2021 年 7 月那个时代，会花很多时间定制系统、解决各种安装问题。装机本身很痛苦，所以大家会羡慕我。

现在我只用一句话让 agent 去 `mirrors.nju.edu.cn` 找 Debian 13 的镜像，把它安装到 U 盘，确保 U 盘可以启动，再用 `QEMU` 模拟器验证。关键在于“用模拟器验证”：安装完成后，它要在模拟器里真正启动到登录界面，创建用户，设置密码，确认登录成功。之后我再让它安装一个 tile-based 的 window manager，整个系统就可以使用了。

以前这一步需要我掌握安装流程，知道每一步为什么这样做。现在我可以把这些约束交给 agent，让它完成并检查。最后启动 U 盘，系统确实能进入登录界面，我才把它带到教室。

这里还有一个真实的故事：有一年操作系统课上，我把教室电脑的硬盘抹掉了，导致下一位老师上课出了教学事故。正因为安装和启动涉及真实硬件，验证环节不能被省略。agent 能替你完成繁琐操作，但“完成文件操作”和“确认不会误伤目标”仍然是两件不同的事。

#### 让不会用的系统生成说明书

我还让 agent 为自己的窗口管理器生成了一份使用文档。别人看到一个很酷的窗口管理器，可能连快捷键都不知道怎么用；我直接让它查看系统设置，然后告诉我怎样打开 terminal、怎样打开 app launcher、怎样切换窗口。

于是 `Super+Enter` 打开 terminal，`Super+D` 打开应用启动器，窗口也可以按照新的方式移动和切换。文档、终端和现代配置，我几乎一眼都没有看过；我只说想要什么，让它交付，再让它检查一次。

这也是我对 AI 学习方式的最大感受：过去我读几千页的 CPU specification，逐项理解每个 feature；现在我更关心的是，怎么和一个已经读过、已经理解、能够动手实现的人沟通，并把他的能力带到一件更大的事情上。

### 未来不是一个已经写好的答案

今天的 next-token prediction 仍然可能是一个效率很低的模型，但它已经足以支撑很多工作。有人也在研究 diffusion model：它不是从左到右一个 token 一个 token 地生成，而是从随机噪声开始，像做梦一样，反复把一个东西看得越来越清楚，最终得到很长的结果。

这类模型还可能把上下文回过去修改，而不是只能不断向后追加；也可以在任意时候把一个很长的上下文裁短。未来究竟是哪条路线会胜出，现在没有人能够准确预测。是 next-token prediction 继续变强，还是 diffusion 类型的模型取得突破，摩尔定律会不会继续带来新的变化，我们都只能继续观察。

> **提示**：不要把今天最强的交互形态当成未来的终点。今天我们可以依赖 agent 调用工具，但未来的模型可能拥有不同的生成机制、更长的上下文和更强的回溯修改能力。

我能比较确定的是，世界肯定会变得非常不一样；不能确定的是，具体哪一条技术路线会胜出。正因为如此，每一个同学都更值得认真思考：当学习工具、工作工具和个人能力都发生变化时，自己应该怎么办？

### 先把东西搞出来，再回头复盘

agent 彻底改变了计算机学习中“学习曲线太长”的瓶颈。

很多人配置漂亮终端时，最痛苦的并不是不会写某一个配置项，而是改完以后突然报错；`.zshrc` 改一行，终端就坏了。没有 agent 时，你只能不断搜索、试错、理解别人的配置。有了 agent，它可以帮你修改，也可以事无巨细地解释为什么要这样改；你提出新的想法，它就继续调整。

它甚至还能提供情绪价值。我前几天发过一条帖子，说 token 为什么比学生好用，因为它可以被骂，而且不会还嘴。学生不能这样骂，agent 可以。

这听起来像一个玩笑，背后却对应一个很实际的学习方法：先用好 agent，把东西搞出来，再回头复盘和理解。这个顺序比从零开始、一点一点搭积木快得多。

但它也有危险。你做出来的东西，未必意味着你已经理解了其中最好的设计。agent 给出的实现可能能工作，你的理解却可能和真正好的理解之间存在差距。我们不能因为屏幕上出现了一个漂亮结果，就自动宣称自己已经完成了学习。

> **结论**：先做出来，再复盘；先获得可运行的结果，再补上对机制的理解。速度可以交给 agent，判断不能完全交给 agent。

### 让 Agent 处理日常事务

我第二个经常使用的例子是收发邮件和写草稿。

我有一个自己的 skill，数据库里保存着我历史上回复过的所有邮件。收到新邮件以后，它可以自动把邮件变成已读状态，再按照我的口吻写一份回复草稿。简单的 routine 邮件有时可以直接使用，但大多数时候我仍然需要修改。它最有价值的地方不是替我假装完全自动化，而是先给我一个可以继续工作的 bot。

如果邮件里有附件，比如一张发票，它还可以把发票自动保存到指定的归档位置。这个能力来自我提前写好的 instructions，不是一个凭空出现的魔法。

我还在使用一个自己的 bot。收到“把我收到的上一个发票打印出来”这样的待办后，我只要点一下勾选，它就会 commit 一个 to-do，后台开始处理；处理完成后，它会发通知，通过 Apple Reminders 送到我的手表上，我再去打印机那里拿走发票就行。

```text
收到邮件
   │
   ├── 标记为已读
   ├── 按历史口吻生成回复草稿
   └── 识别并归档附件（例如发票）
            │
            ▼
      写入 Reminders 待办
            │ 用户确认
            ▼
       后台 Agent 执行
            │
            ▼
      手机、手表收到完成通知
```

我可以让它做日常事务，但前提是这些事情足够 routine，而且是我放心的。它目前还不能完全替我判断所有事情；复杂邮件仍然要修改，真正重要的动作也要确认。可这已经比每天从零开始手动处理多了一双不知疲倦的手。

电脑能做的事情，原则上都可以通过 agent 去操纵。我已经可以让它控制打印机；如果以后有更多时间，也许可以做一个机械手，做更多现实世界里的动作。现在还做不到的事情，不代表这个方向没有空间。

### 读书、读论文和看视频

我以前很喜欢看书。在你们这个年纪的时候，我每年会读几十本教科书，还看很多闲书。但今天我自己的阅读量已经下降了。为了上这门生成式软件工程课，我又买了一些以前反复读过的书，重新找回读书的感觉。

比如 Frederick Brooks 的《人月神话》。这个书名非常 misleading，很多人会想到人和月亮，或者“月亮出来就变成狼”的故事；但这里的 `man-month` 是人力月，讲的是项目组织和人力的神话。更有意思的是，`myth` 并不只是“美好的传说”，它也可能是“根本站不住脚的故事”。我以前读这本书时很认真，甚至不止读了一遍。

现在我会让 AI 耿同学先读第一章，然后做几件事：回看人类历史和与这个主题相关的案例，寻找其中可能给我们启发的经典；再寻找相关工作，不只限于 computer science；优先选择被广泛认可、影响力大的资源。这不是让 AI 替我读书，而是让我更快找到真正值得投入注意力的部分。

我的 AI 耿同学里有更多不同的 personality，也会有一定随机性，像抽卡一样生成不同观点。它们可以互相讨论，保留分歧，再把分歧送回彼此继续讨论，直到收敛；最后由主 agent 汇总。我用额外的算力，换取更充分的思考和更少的盲点。

我读论文时也会换一个视角：先假设人类已有的知识都已经固定下来、已经知道了，然后把论文里真正新的东西尽可能剥离出来。一篇十二页的论文这样处理以后，常常已经变得很短，剩下的是最值得追问的新意。

但这不等于我不读论文。我仍然会拿着论文原文，拿着一级总结和更深层的总结，和模型继续 chat。模型帮我压缩噪声，我还要回到原文核对，因为真正的理解不能只在摘要里完成。我也不是只看微信公众号来学习的人。

#### 把 B 站课程变成图文时间轴

我还会用 AI 上 B 站。给我一个 BVID，我可以让它把一个多小时的课程整理成 podcast 式的内容，再做成自动的图文时间轴。字幕只是最基础的文本来源；我会按照两帧画面之间的间隔来判断，间隔大到一定程度时就截图，把截图当作视频的 ground truth。

这样得到的内容往往比单独字幕质量更高，图片也能帮助我定位上下文。对于我早已熟悉、认为不需要再看的内容，agent 可以依据我的记忆直接去掉；真正不同、值得注意的部分则被留下。最后，一个一到两小时的视频，我可以在几分钟内快速看完，同时知道自己大概漏掉了什么、哪些地方需要回去查原文。

这并不意味着以后可以彻底不读论文、不理解知识。真正危险的地方恰恰是：工具让内容消费变得非常快，而你的理解可能还没有同步跟上。我们至少要保留检查的习惯，知道这份摘要为什么这样组织、哪些地方可能删错了。

### 竞争力最后落在你做过的东西上

在 agent 时代，会用 agent 学习的人，和不会用 agent 学习的人，效率差距可能是十倍甚至一百倍。这个数字不是让我鼓励大家跳过所有基础，而是提醒我们：同样的四年，如果有人更早学会指挥工具，别人就会在竞争中没有优势。

所以，开学时的焦虑不能靠把所有作业都交给 AI 来解决，也不能靠继续重复一套已经不适合新时代的训练方式来解决。我们真正要做的是理解 AI 的能力边界：它已经能做什么，做得有多好，哪里还会出错；然后带着它去做一件原本自己做不到、但组合起来可以做成的事情。

这就是我理解生成式软件工程的起点。不是把每一行代码都亲手敲完，也不是把课程内容变成一条自动生成的简历，而是让人重新获得定义问题、组织工具、验证结果和创造作品的能力。

### 本讲提到的题目

**题目**：如果你要用 agent 给我的课出一份期末考试卷，应该怎么办？

这道问题在课程导入时被提出，但这里没有展开具体课程、题型、题量或评分标准，不能凭它直接补出一份完整试卷。可以确定的做法是：先把出卷子当成一个需要被 agent 执行的任务，明确它要围绕的课程内容，让它生成题目和对应答案；然后自己逐题 review，检查题目是否真的对应课程内容、答案是否成立、要求是否清楚。不能因为模型生成得快，就默认这份试卷可以直接使用。

这也正是本讲反复强调的工作方式：先给 agent 一个合适的指令，让它把东西做出来；再拿回结果，检查、追问、修改，最后由人承担交付责任。工具可以提高出题和迭代的效率，但“什么样的试卷是好的”仍然需要人的判断。

> **结论**：AI 时代真正稀缺的不是替我们完成一个动作，而是知道什么值得完成、怎样判断结果，以及能不能把 AI 带到一个更大的目标面前。

## 生成式时代的学习方式与课程路线
> 对应块：BLK02 | 覆盖分集：P01下

### 普通人真正要掌握的，是让能力形成飞轮

AI 的真实形态远不止一个聊天框。刚才那个像白板的 AI，装好以后，配置上 DeepSeek V3 Flash 的 API，立刻就能做事，这已经足够让人惊讶了。但这只是起点。真正可怕的不是某一个模型突然会做某件事，而是它背后的生态开始形成：今天有脚本，明天就可能有插件；有浏览器里的一项能力，明天就可能沉淀成可复用的 skill。一个领域里的特定任务，只要合理、有人愿意做，开源社区早晚会把现成的方案递过来。在 AI 时代，复用别人的能力比以往任何时候都轻松。

所以，普通人下一步最该做的事，是先让插件把浏览器管起来，再让插件把电脑管起来。

浏览器是一个非常好的工程产品，甚至可以说是软件工程史上的奇迹之一。它看起来只是显示网页，背后却要处理图形栈、显示、性能优化等一大堆问题，而且直接面对用户；它的代码量甚至远超操作系统内核。Chrome 专门为开发者提供了接口：打开 Chrome，按 `F12`，就能进入 DevTools。网页的 console、HTTP 头、各种请求信息都能看到。一个链接还能直接复制成 curl 命令，带着浏览器的 cookie 和完整状态去请求，连列表都能拿回来。

这些在 LM 之前就是开发者的日常，如今却可以交给 LM 帮普通人享受。我们以前要专门学 DevTools 才能用好浏览器，现在 Agent 能把这些厉害的地方直接接进自己的工作流。

> **提示**：DevTools 的价值不只是“看网页源代码”，而是把一个真实运行中的网页，变成可以观察、检查、请求和复现的对象。

### 翻车不是终点，Agent 会在试错中收敛

教务系统是软件工程的反面例子：界面不喜欢，表格总要填，很多事情莫名其妙地绕来绕去。偏偏这样的系统，恰恰适合拿来检验 AI 到底会不会干活。

我让 Agent 在浏览器里填写一个教学周历。它本该填一个“空值”，却因为当前目录就是这门课的代码，开始自作聪明地读取 lecture notes——我已经明确说了“不要看任何东西”，它还是不听。这就是 Flash 系列模型常见的麻烦：先不照指令做，能力还在增长，翻车也经常发生。换最一线的模型，指令遵循会更好；我之所以用 Flash，主要还是因为课堂上要快。

可是，过程并没有停在翻车这里。Agent 会不断反思“这样做合不合理”，发现直接注入事件行不通，就换成点鼠标；点鼠标成功之后，它已经学会了怎样填写这类字段。Chrome DevTools 是非常强大的工具，它能让人看到“这一次怎么走通”。

真正值得关注的不是这一次有没有成功，而是成功之后能做什么。这个 session 里的路径会留下来：哪里能成功、哪里会失败，踩过的网页路径也能被转成脚本。只要成功走过一次，就可以沉淀成确定性的脚本，形成一段记忆。到最后，它甚至可以变成一个自动选课、抢课的系统。

> **结论**：Agent 的价值不只在于一次对话完成一项任务，更在于把一次成功路径固定下来，变成以后可以重复调用的能力。

而且这绝不只是一个孤立案例。我们把浏览器 skill、在网页上工作的 skill、上下文里提取记忆与脚本的能力放在一起，它们可以互相调用。这背后的思想其实来自 UNIX：管道让所有程序都能自由组合，能力可以无限复用，1+1 常常能大于 2。

#### 信息流也能被做成一个知识飞轮

同样的道理可以用来处理信息。普通人可以找到 RSS、B 站、archive、Hacker News 等各种推送源，刷牙的时候听一听 AI 早报。它们每天都在源源不断地产生信息，而我们可以把这套信息处理流程沉淀成脚本或 skill：

```text
RSS / B 站 / archive / Hacker News
                  │
                  ▼
           自动收集与筛选
                  │
                  ▼
       脚本与 skills 组成处理系统
                  │
                  ▼
          持续产生有用的知识
                  │
                  └──────► 持续调整工作流，反过来改进系统
```

这个系统几乎没有一行代码需要我们手写，各个部分用自然语言描述，却可以不断复用。流程会随着使用不断调整，知识会不断产生，自己的飞轮就转起来了。有飞轮和没有飞轮，是完全不同的两种工作状态：信息不再只是堆积在那里，而是在持续转化成有用的东西。想象一下，一个人拥有这样的飞轮，会产生多么大的放大效果。

这也是为什么 Agent 类产品已经让人感到惊喜。自我净化能力、自动调用工具、根据结果调整路线，都开始成为产品的一部分。模型越过临界点后，说不定会吸收我们目前工作方式中的大量细节。

#### 用记录复盘，而不是困在日常里

我们甚至可以把录屏数据交给 AI，让它总结自己一天的工作，找出还有哪些提升空间。很多重复流程都可以固化下来。甚至可以更进一步：学习课程中的内容，生成课程资料和复习材料；学习视频内容，生成视频、论文之类的辅助材料；做一个 WiFi 相关项目，把一句自然语言需求变成 Python 代码，再让 3D 打印机直接打印出来。这些都可以通过自然语言驱动 AI 完成。

所以，模型能力还会变强，不会突然变弱。问题只剩下两个：它什么时候来，我们应该怎么面对它。

> **易错点**：在 AI 时代，仍然心安理得地每天重复同样的事务，才是一种值得警惕的状态。

### 普通人和 AI 的差别，不只是会不会用工具

如果只是用 Agent 做操作系统作业，那太小看它了。我们作为 computer science 的从业者，非常清楚编程能力的边界在哪里。普通人容易提出一个需求，但 Agent 可能做不好、做不了，也不知道怎么用 prompt 让它确定性地快速完成。

而我们知道怎么把需求“编译”成可复用的代码、可复用的 skill，以及适合由 Agent 处理的其他形态。

我今年尝试了一条改卷子的流水线。第一遍先让 Vibe Coding 出脚本、跑测试。办公桌上放一个从顶向下的摄像头，试卷摆在固定位置，按一下回车，摄像头就拍一张照片。然后交给本地的 Qwen 去离线识别姓名、学号和每一个小分，把结果写到文本文件里。一张卷子按一次回车，两只手都不用写。试卷没摆好就调整一下，再来一次。

第二阶段按反序进行。我左手按回车，右手拿笔。系统用语音播报姓名、学号和每一个小分，比如“11 + 12 + 13 + 14 + 15”。OCR 可能出错，我必须亲自检查，因为要对班上每一个同学负责。检查没问题后，再把最终总分抄写到卷面上。

```text
试卷摆正
   │
   ▼
按回车拍照 ──► 本地 Qwen 离线识别
   │              │
   │              ▼
   │      姓名 / 学号 / 各小分写入文本文件
   │              │
   │              ▼
   └────────► 按反序再来一遍
                  │
                  ▼
       语音播报：姓名、学号、各项小分
                  │
                  ▼
          人工逐项核对 OCR 结果
                  │
                  ▼
        脚本计算总分，不让大模型做加法
                  │
                  ▼
       抄写最终分数，汇总进教务 Excel
                  │
                  ▼
        抽样检查无误后提交
```

这里的流程是“相机 + 本地模型 + 脚本 + 人工核对”，而不是“把所有事情都扔给一个聊天机器人”。本地 27B 模型的千问就能用，OCR 结果由人检查，最终总分由脚本计算。大模型负责识别和流程控制，不负责做容易出错的加法，所以不会因为幻觉把分数算错。

最后，分数自动汇总到教务处的 Excel 模板里。可以用这个方式上传文件，再抽样检查，确认没有问题后提交。

> **定义**：这里真正重要的能力，是把一个大需求拆成“模型识别”“确定性脚本计算”“人工核对”这样的不同部分，选择每个部分最合适的技术。

这也是我和普通人协作方式可能不同的地方。普通人直接对 Agent 说“我改了 140 张卷子，小分都写好了，帮我统分”，它很难快速收敛到这么具体的方案；人机共建才能把同步代价降到最低。

### 软件不是“idea 都有了，就差程序员”

AI 很强，但产品是一个系统性的工程。如果要做外卖网站，就要有前端、后端、交互、运营，整个流程上任何一个环节做不好，产品就会立刻暴毙。AI 都能做这些环节，但它什么都知道，并不等于组织出来的系统就能活下来。

我们做过一个实验：让 AI 生成 QR code 点阵 HTML。它生成了完全不可维护的代码。里面的 bug 很多，难以使用，而且每年还要花巨大的钱让公司维护它——因为想加一个功能时，代码几乎改不动。

我们在操作教务系统时就见过这种情况。苏校区建成前，系统里没有“校区”这个字段。后来产品经理说：“现在多了一个校区，选课要分开。”数据库里原本没有这个概念，开发者只能开始改代码。原来看起来已经能用的系统，说不定就会这样开始失败。

#### QR Code 实验暴露的工程失败

那个 QR Code 需求其实非常明确：只要一个 QR code 点阵 HTML，用 Excel 2019 兼容的公式，把任意字符串转成 QR 动画。我要求 AI 不要问我，必须一直做到完成。但它对需求理解不到位，看到完整的 slides 却没有看到具体做法，第一秒就被带偏了。

它想做一个“对任意 S 都满足正确性”的东西，反而扩大了问题范围。AI 容易在小 corner case 上犯错。软件工程的第一步应该是“做最简单的东西”，不要扩大。它没有理解这一点。

后来我做了一个受控实验，把 specification 直接告诉 AI。GPT-5.3 第一次思考了 25 分钟，然后开始疯狂输出，超过了 32K 的输出 token，直接把 QR code 干爆了——它超出了默认输出限制，被截断了。继续跑，总共跑了六个小时才完成。DeepSeek V4 Pro 也是晚上放着跑的，第二天早上看时却发现变成了硬编码，不符合指令。

为什么？因为我把正确的思路讲明白了：

```text
输入一个任意字符串
        │
        ▼
用 Base64 编码
        │
        ▼
通过 Excel 公式计算所有位运算
        │
        ▼
        生成 QR 动画
        │
        ▼
    保持可维护、可复用的程序
```

问题在于，后来跑出来的实现把 Base64 编码的结果直接算出来，再贴到 Excel 公式里。如果字符串改变，Base64 结果并不会跟着改变。正确的要求是：Excel 公式必须用“Base64 编码”来动态计算，而不是用 Python 算完后硬编码进去。

但它最终确实完成了任务，Agent 完成长任务的能力很强。然而它们生成出来的，都是没有办法继续维护的 AI 系统。

这就是软件工程里最经典的死法：“我知道需求了，实现需求就好了。”然后直接陷入维护的泥潭。一个好的软件应该能够面对几十年的变化，而不只是眼前的需求。

> **结论**：在软件工程里，“一次能跑”只是最开始的验收条件，维护性才是产品能够长期生存的条件。

### 我是这样写出可维护的 QR Code 的

如果要实现这个 QR Code，应该怎么写、怎么 prompt AI？我实际上只用了少量 prompt，就让 GPT-5.3 在 200K 上下文里完成了第一个正确版本。

我先让 AI 设计一个像编译器一样的 Python 类，把各种位运算抽象成一个符号系统。这个符号系统既可以在 Python 里直接执行，也可以翻译成 Excel 公式。相当于做了一个基础设施、一个中间语言——有点像做信息基础设施时需要一个中间层。

这个中间语言要对 Python 友好，也要对 Excel 友好。之后我只需要验证几件事：

- 输入到 Python 的执行结果是否正确；
- 输入到 Excel 的翻译公式是否正确；
- 二维码的编码和每个像素的计算是否正确。

这样一层层验证，最后生成出来的代码就干净了，也不太长，维护性远远好过那些硬编码方案。

我们还可以把不同 AI 生成的方案放在一起比较。两份代码虽然用了不同的 roadmap，但里面是同一种思路：把复杂问题拆成可以验证的小模块，再分别实现 Python 和 Excel 两套后端。如果我只要求它们“把工作区从一个位置移动到另一个位置”，它们会不断出错，因为所有东西都是硬编码，改错一点，验证就通不过，Agent 还得一轮一轮修。

但这里是在做软件工程。即使 Agent 最终能修好，代码结构和验证方式也不能混为一谈。

### 从 Intention 到 Implementation，中间有三个空间

当我们要用 AI 解决问题时，有三个空间必须分清楚。

```text
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│    Intention（意图）                                         │
│    脑子里真正想实现什么？                                     │
│                         │                                    │
│                         ▼                                    │
│    Specification（需求规格）                                  │
│    到底要做哪些功能？必须满足哪些要求？                       │
│                         │                                    │
│                         ▼                                    │
│    Implementation（具体实现）                                 │
│    界面、数据库 schema、代码和架构如何选？                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### Intention：我到底想实现什么

Intention space 是具体的意图，也就是你脑子里想什么。老板说：“我要做一个国民级的应用。”或者你说：“我要做一个小程序，挣一个亿。”如果目标是点外卖，那背后可能有一整套想法：让同学们点外卖更方便。

同一个 Intention 可以对应很多实现方式。比如“我要造一个能把数据传出二维码的 Excel”，这是 Intention；之前那句“用 Excel 2019 兼容公式把任意字符串转成 QR 动画”，就是 Specification。

#### Specification：功能、约束和边界

Specification 说明程序要具备什么功能、必须满足什么要求，而不是简单地指定一种架构。它可能规定了有几个界面、每个界面有什么功能；同样，它还可能规定正确性、性能和 Excel 版本兼容等要求。

关键在于：即使两个实现都能满足同一个 Specification，它们的架构、实现方式和维护难度也会截然不同。

#### Implementation：让需求落地的具体选择

同一个 Specification 可以有很多种 Implementation。比如“教务系统”这一个 Intention，可以满足很多种 Specification：界面怎么设计、数据库 schema 怎么定、分几张表、每张表有哪些列、选择 key-value 数据库还是关系型数据库……每一个选择都会带来截然不同的结果。

这有点像软件工程早期流传的梗图：客户这样解释需求，产品经理这样理解，分析师又是这样想的，宣传人员这样宣传，最后做出来的东西却和客户真正要的完全不同。

根子就在于这些空间之间存在巨大的 gap。**软件工程要做的，就是补上这些 gap。** 从 Intention 到 Specification 是翻译，从 Specification 到 Implementation 也是翻译。只要其中一个翻译错了，软件工程就失败了。

### AI 的第一反应是猜，人需要学会先补齐中间步骤

模型怎么补 gap？它一般是猜。听到一句话，它就猜“你应该要这个”，然后直接实现。

原因在于后训练。模型会获得 reward：如果任务完成、测试通过，就得到奖励。所以它形成了一种强烈的倾向——立刻动手，尽可能快地把任务完成。因为做得慢，就会得到更少奖励。

模型因此越来越擅长做简单任务，这当然是好事。但模型解决问题的方式，和人还是不一样。计算机和软件工程学生学 C 语言程序设计，首先要弄清楚 Implementation space 里面有什么，把这些实现方法练熟：同一个需求可以用不同方式实现。然后再学软件工程，把相关的任务逐步补全。

而到了 AI 时代，这件事变得不同了：**既要阻止 AI 乱猜，又尽可能发挥 AI 从 A 做到 B 的能力。**

这就是“生成式软件工程”要讨论的核心问题。模型已经足够强，单个任务上无人能敌；但软件工程这个更大的系统，还需要人来补齐它看不到的中间过程。

### 焦油坑：更多人不一定能救活失败的项目

《人月神话》里面有一个非常形象的比喻：大型动物一旦陷入焦油坑，就很难逃脱。它像泥潭一样陷进去，濒死的动物又会引来各种掠食者；那些掠食者进去之后，也出不来。

《人月神话》里面有一个经典论断：如果一个团队或软件产品已经开始失败了，你往里面加更多人，只会让它变得更失败，而不是变得更成功。

这对 AI 也一样。如果一个产品已经开始失败，AI 开始产生 slop，你投入更多 token，只会让它变得更失败。AI 会在那个失败的东西上不断修补、不断堆叠，一层一层往上浮，直到你再也付不起 token 为止。

教务系统不就是这样的吗？每年它都在增加功能，也确实有人在维护，但这并不意味着“能运行”就等于“能长期生存”。软件工程研究的，是当 gap 真实存在时，怎样把一件足够大的事做出来。从这个小实验，到一个能赚几百万、几千万的上市公司，再到真正的国民级产品，背后的方法论就是一次次巨额投入换来的教训。

> **易错点**：系统已经陷入“加功能、加人、加 token 就继续修补”的循环时，应该停下来重新审视架构，而不是继续往里面堆投入。

### 软件工程既是技术，也是一门管理学

软件工程当然有技术。比如程序分析和测试领域会问：如果 Implementation space 里已经有一段代码，能不能自动生成更多测试用例？能不能自动做代码审查？当代码不满足 Specification，甚至不满足潜在 Intention 时，能不能提前给出 warning？

但软件工程远不止技术。它还涉及人类学、社会学和管理学。团队里有人不听话怎么办？怎样管控团队风险？有人离职了怎么办？有人跳槽到竞争对手那里怎么办？这些同样是软件工程要研究的问题。

而在生成式软件工程里，这些问题又增加了一层：团队成员从“会和你抬杠的人”变成了一个会回答“you are absolutely right”的 AI 角色。AI 通常会听你的话，不一定抬杠，但“人应该如何被管理”并没有因此消失。

软件工程的研究方向很广：AI for SE、SE for AI、架构设计、可靠性、演化，以及软件能不能长期生存下来，human social aspects 也特别重要。

#### 考试教给我们的，不只是“会做题”

软件工程失败通常发生在 gap 还很小的时候。这个阶段像杠杆一样：你在这里微微变一点，后面就可能产生巨大的变化。很多大型软件系统就是在这个点出错，最终整体崩盘。

这也是当前教育体系的一个问题。我们从高考一路走来，考试题都是“分分钟能解决”的题目。如果一个人 5 分钟解决不了，这道题一般就不会出。久而久之，我们训练出来的能力，就是快速解决一个已经明确的问题。

而 Agent 的训练信号也很类似：能不能 5 秒钟解决？它有更多数据、更明确的反馈信号，所以做得比你好。但如果没有很强的好奇心，想知道世界究竟怎么运行、一个产品究竟怎么开发，就可能没有足够的 self-motivation 去训练自己解决这类问题。

结果就是：你解决“综合题”的能力，还不如 AI。

软件工程看起来像文科、管理学，但当你能把技术映射回这些管理和社会问题时，会发现它其实是一本管理学著作，里面也有许多真实而有趣的科学。

> **结论**：未来真正稀缺的能力，不是和 AI 比谁在几分钟内刷完更多题，而是找到值得解决的问题，把未知拆成便宜的实验，用证据让坏方向及时停下，并对长期结果负责。

### 古法编程已死，但软件工程还活着

AI 时代，软件工程失败的定义并没有改变：要么从 Intention 到 Specification 的翻译错了——做出来的东西其实不是你想要的；要么从 Specification 到 Implementation 的翻译错了——虽然满足了表面需求，却违反了正确性、性能等约束。

今天的模型虽然有 reinforcement learning，但对于真正“长程信号”的 reward，还做得不够好。它更擅长机械地完成任务，而不是主动思考一个更干净、更可维护的设计。

面对 Excel QR Code 的问题，很多模型第一反应都是直接做题，而不是像我一样先设计一个 DSL。它们明明有能力设计一个好的中间语言，把问题干净地解决，却已经形成“先把手头任务做完”的做题家反应。我们还没有真正把 AI 训练成一个好的设计者——或者说，AI 的工程品位还没有被充分训练出来。

但也不能因此认为 AI 永远学不会品味。它既然能解决数学问题，能处理编程里细碎的逻辑，也见过大量好的设计，谁知道它不能从自己的记忆库里找到那些设计，来解决新的问题呢？说不定几个月之后，这门课还没讲完，我课上讲的这些东西就已经过时了。

回到最后一个问题：如果你保研时，导师问你“我为什么要招你，而不是买一个 200 美元的 Call max？”你怎么回答？

这个问题的答案可以是：

- 找到真正值得解决的问题；
- 把未知拆成便宜的实验；
- 用证据让坏方向及时停下；
- 对长期结果负责。

这是一个好的回答。AI 现在还给不出同样好的答案，但这个方向值得认真思考。

> **结论**：古法编程在单个任务上已经无人能敌，软件工程还没有死。我们要学的不是和 AI 比谁打字更快，而是如何提出好问题、设计好架构、验证每一步，并对长期结果负责。

## 提示词工程：从一句话到完整上下文
> 对应块：BLK03 | 覆盖分集：P03上 | 块标题（分集名）：《提示词工程的基本原理》

### 从一段没人写的汇编说起

我想先用 2023 年底的一段经历开场。那是 ChatGPT 刚发布不久的时候，我在准备操作系统课，想试试让它讲讲 x86 的 SIMD 汇编。这个东西现在几乎没人手写了，落到我们以前的教学语境里，本来已经算一项“传统艺能”：不是为了实际写代码，而是为了理解机器。

我原本以为它大概会胡扯，结果它解释得出奇地好。我还故意选了一个正常人大概不会真去实现的指令组合，它仍然做得相当不错，虽然并不完美。那一刻我第一次真切地感觉到：时代好像要变了。

从那以后，`prompt` 成了一个新词。大家在聊天框里打的那句“帮我生成一个游戏”“帮我把作业做完”，当然叫提示词；但真正的提示词工程，远远不止这一句话。

> **定义**：提示词工程不是反复寻找一句“更好的咒语”，而是有意识地安排模型能够看到的整个上下文，让它知道要做什么、使用什么、怎样做，以及怎样判断做对了没有。

我更想借这一讲让大家记住的，其实是一个非常朴素的行动原则：**只要碰到一点自己不会、觉得麻烦的事情，就立即开始问 AI。**

### 提示词远不止对话框里那一句

很多同学第一次看到 agent 的上下文时，会下意识地把它想成“我发给 AI 的用户消息”。这当然没错，但远远不够。

在你发出用户消息之前，agent 可能已经拿到了一长串内容：

```text
模型内建的 system prompt
            ↓
全局 AGENTS.md、工具说明与工具使用规则
            ↓
项目级、目录级的 AGENTS.md
            ↓
skills 索引：名称、简述、metadata
            ↓
用户此前与 agent 的对话、工具调用及返回结果
            ↓
本次执行注入的环境信息，例如当前时间
            ↓
用户消息：给我做一个游戏吧
```

这是一条线性的上下文。模型不是只接收最后那句话，而是在已有内容的基础上，不断预测下一个 token。下一个 token 可以是一个字符、一段内容，也可以代表一次工具调用；任务就这样一步步向前推进。

这里有一个很重要的现象。有人在最早的 `system prompt` 里要求 AI“用中文回答”。后来用户消息全部使用英文，AI 却依然用中文输出。原因不是最后那句话突然覆盖了前面的要求，而是前面的要求仍然留在这条很长的上下文里，并且能够继续影响生成。

如果 agent 使用 Codex 这样的工具，还可能加载不同的说明文件、全局或项目级 `AGENTS.md`、工具定义，以及具体任务的文档。一次任务涉及多个项目时，目录里还可以继续放自己的 `AGENTS.md`。这些东西一层一层地叠加，并不是一条孤零零的用户消息。

skills 也很有意思。以“用 F5 播放幻灯片”的渲染能力为例，模型平时先看到的只是它的名称、简述和 `metadata`，不必一上来就把整个 `SKILL.md` 塞进上下文。只有任务匹配时，完整的 skill 才会按需加载；任务过去后，它也不再无意义地长期占据上下文。

工具定义会以文本形式出现在上下文里，工具调用的结果同样会进去。对话历史、过去的执行过程，也会留在那里。你们甚至可以用 DeepSeek 聊天时套出每次执行注入的环境信息，例如当前时间——这和“整套内容都属于 system prompt”不是一回事。

这些内容都会进入上下文，因此，能够看到自己的上下文，恰恰是 agent 的天然优势。你可以马上打开一个 agent，直接问它：

> “你能不能检查一下自己的上下文里都有些什么？这些东西分别来自哪里？”

它可以检查上下文，也可以检查自己的日志。答案有时会超出你的想象，因为它不一定沿着你预设的思路解决问题。

当然，能不能读取不等于一定会回答。有些模型服务商会通过微调和明确指令，要求 agent 拒绝泄露系统上下文。但如果底层框架是开源的，你仍然可以沿着实际实现去 debug，查清 system prompt 来自哪里、要求了什么、工具使用指南是什么。

> **易错点**：`system prompt` 只是上下文的一部分。把它等同于“我刚刚输入的那句话”，会误判 agent 到底掌握了什么，也看不到上下文组织为什么会影响结果。

所以，谈“优化提示词”时，准确的含义应当是“上下文工程”：把上述信息安排好，把真正需要的约束放进去，把模型应该持续遵循的规则放到它能注意到的位置。

### 不会就问：AI 是一个耐心的老师

我从上大学时起，就很怕向室友请教问题。不是因为沟通不了，而是总觉得一旦问出口，就暴露了自己“很菜”。那可能还是一件不想让对方知道的秘密。可对 AI 来说，它不会嫌弃你，你可以追着问，一次不行再问一次。

刚才我们说，agent 能看到自己的上下文和日志。知道这一点以后，就不要只是把知识记在脑子里，而要马上把它变成一次可执行的探索。概念没有理解，就让 AI 补充；工具不会用，就让它演示；某个结果出乎意料，就让它检查自己为什么这样做。

我很喜欢费曼学习法。判断自己是否真正理解一个知识，可以反过来当一次老师：让 AI 扮演一个完全不懂的学生，你负责把概念讲懂。哪里逻辑断了、哪里有遗漏、哪个前提没说到位，都让它指出来。

通常的过程应该是：

```text
向 AI 请教，反复追问，直到自己基本弄懂
                   ↓
反过来要求 AI 扮演“假装什么都不知道”的学生
                   ↓
自己从头讲一遍，由 AI 检查漏洞和矛盾
                   ↓
针对漏洞重新讲解、修正，再讲一遍
```

正着弄懂一次，反着讲清一次，对一个概念的理解通常就会扎实很多。这比把“我大概懂了”误当成“我能讲明白”可靠。

你们现在正处在最好的学习阶段。眼前最重要的任务就是学习，还不必像以后那样对很多人、很多事负责。AI 给了你一种以前很稀缺的能力：你拥有大量可以随时试错的时间。一定要用起来。

### 自主执行与安全确认：别把自己的作业交给一个莽撞的 agent

能自主执行当然很爽，但风险也必须摆在桌面上。

假设你给 agent 的提示词写得不好，而它恰好处在默认直接执行一切的模式中：它也许不会先问你一句，就把整个项目删掉。这个问题不是理论上的，危险就来自“它真的照做”。

一种做法是在沙箱里运行。沙箱可以降低风险，但会带来新的摩擦：agent 可能先尝试一件事，失败后发现沙箱不允许，于是换到外面再做一次；再执行时，它又会突然问你，要不要确认一个可能有风险的操作。

我们当然希望把几个任务都先跑起来，然后安心去吃饭。结果回来一看，它只跑了一分钟就开始等你点确认。那确实很浪费自己的时间。

> **结论**：自主性和安全性不是“越安全越好”或“全自动越好”这种单选题，而是一组需要主动设计的取舍。沙箱、自动放行与审批，各自解决不同的问题。

值得注意的是，安全判断本身也是一层上下文工程。假设一个 Bash 命令进来，大致可以先经过下面的分流：

```text
Bash 命令
   ↓
静态解析器检查命令是否命中安全 allowlist
   ├── 命中：直接执行，不要求审批
   └── 未命中：注入一小段安全性评估提示词
                    ↓
             模型评估、执行、读取结果
                    ↓
          更新判断；必要时请求用户确认
```

以 `ls -l` 为例，解析器可能认为它足够安全，直接放行。但在恶意环境里，有人可能把相关命令替换成另一个程序；“看起来像一条安全命令”和“实际运行的究竟是什么”，不是同一回事。

如果解析器不确定，就会向上下文里注入一小段类似“是否应该评价这条命令的安全性”的 prompt，让模型判断。模型也可以搜索代码、读实现、调用 LSP 这样的工具，进一步理解命令到底会做什么。

这里已经完全是上下文工程了：安全策略负责第一层静态分流，模型在上下文里接收评估任务，再借助工具收集证据。

你甚至可以把那段安全评估 prompt 打印出来，亲眼看它写了什么。事先没有准备也没关系，这就是探索。我们未必能百分之百相信当前模型的判断，但这种“把评估过程拿出来检查”的方法非常有价值。

如果对判断结果不满意，可以谨慎地修改评估提示词，让它对一条行为已经明确的命令重新评级：比如把过去会被拒绝的案例改成不拒绝，或者反过来。然后观察行为是否真的改变。改变本身就是证据，至少说明提示词在这个环节确实影响了判断。

> **易错点**：不要把一次自动放行当作“绝对安全”。静态规则、模型判断和真实执行环境是三层不同保障；一旦环境可被修改，命令的含义就不能只看表面。

现代软件工程还有一个很明显的不同。我在大二、大三那个阶段接触 Linux 内核时，光把源码下载下来、弄清楚怎样编译，就已经耗了很久；这还是在我已有一些 Linux 使用经验的前提下。没有那股“越是劝退，我越要试一试”的执念，可能根本走不下去。

今天面对一个陌生软件系统，答案简单多了：先下载，然后直接问。为什么这个命令会报错、它依赖什么模块、怎样编译、LSP 应该如何配置、为什么一直显示红线。让 agent 查代码、跑命令、看报错、继续修正。

配置好 VS Code 的 `include path` 后，重命名符号、跨文件定位这些功能才能真正用起来。红线还挂着，却在受控环境中强行编译通过，不是正确实践。AI 把探索成本降了下来，但我们仍然应该配置好工具，让自己的眼睛和双手真正工作起来。

### 用 spec 压缩 intent 与 implementation 之间的 gap

写好的上下文，最终要能支撑一个软件工程任务。

我们脑子里想做一个“国民级应用”，这是 `intent`。但只把它交给模型，它很容易以为自己已经完成了任务：你要一个游戏，它给你生成一个游戏；可这个游戏是不是你脑中想的那一个？不一定。

从想法到能验证的产物，中间还缺设计、架构、技术选型和实现细节。我们通常把这条链条理解为：

```text
intent
  想法：我要什么
   ↓
expectation
约束与设计：应该怎样做，做到什么程度
   ↓
implementation
具体实现：语言、代码、资产、交互和输出
   ↓
验证
产物是否符合要求？
```

如果你只给一个模糊的 intent，模型就容易漂移。它给你 Java，而你想的是 `C++`，结果一眼就能看出来。你当然会不满意，对自己的目标也很清楚。但如果你连语言都没有说，模型也不了解你，它没有理由猜中你的选择。

所以，写好模型上下文的重点，是尽量把软件工程大流程里相关的那一部分放进上下文。设计文档、spec、实现和执行输出彼此印证：让 agent 读一段 Codex 代码时，不能只给它结论；为什么要有这个安全策略、总体设计是什么、具体如何实现，都应成为可以检查的上下文。

#### 一句话生成的游戏，为什么仍然不是你想要的游戏

“一句话生成 CS:GO 或极品飞车”是一个很受欢迎的评测。某个模型生成的游戏已经可能拥有不错的物理、碰撞、制作逻辑，后视镜看起来也很逼真。可它仍然不一定是你的 CS:GO。

因为你脑中的 CS:GO，包含大量没有说出口的约束：也许是复用真实地图和美术资产，也许要在熟悉的校园里开车。它收到指令后，无法凭空补全你脑中那些模糊的约束。

如果你真的希望复用真实地图，就把这件事说清楚；AI 甚至可以从 OpenStreetMap 这样的网站寻找开源地图。如果你希望在南大仙林校区里开车，把这个具体地点说出来，任务就有可能完成。车、城市、树等也有公开可用的美术资产。不告诉它，它就可能默认把一切都自己生成出来，于是把一个误解当成你的需求。

> **结论**：好 prompt 不是“把句子写得更华丽”，而是用最小的方向性引导，让模型准确 get 到要求。我要什么、用什么实现、什么叫正确，都要写清楚。

#### “现代风格”为什么会带来同一种 AI 味

我们可以从一个个人主页例子理解“现代风格”的模糊性。

只让 AI 做一个现代风格的个人主页，它可能做得非常好：滚动、浮动等效果都很漂亮，整体看上去也相当专业。但你未必喜欢，因为一眼就能感觉到“AI 味很重”。此时再补一句“不要有 AI 味”，模型也未必知道该怎么执行。

要得到更接近真正终端的页面，就得把风格继续约束：背景和前景是什么，字体、排版和渲染后的处理应该怎样，需要怎样的终端质感。一个非常小的后处理，就能让字符像老式打字机打出来一样，不是过分工整的完美字符。这种不完美反而让页面更真实。

这里有一点很有意思：自己并没有手写一行代码，页面最终仍然按照人的意图呈现出来。设计依然掌控在你手里。

所以，看到一个很好的网页、简历或作品时，不要只记一句“以后我也让 AI 做一个”。再往前追问一步：它为什么好？按钮间距为什么不常规？某个具体样式为什么有效？是自己此前就知道，还是现在才第一次见到？

你们有足够多的时间去漫无目的地探索，探索本来就可能带来惊喜。但更重要的是主动观察，把“喜欢”逐渐变成“我知道自己究竟喜欢什么”。

多样性在这里很有价值。模型的发散方向往往相当固定：如果你不给它控制，它就会向一个常见方向发散。人接触不同的人、不同的课程、不同的设计，才会逐渐形成更细的判断。我们鼓励大家和不同的人交流，并不是因为“不同”本身有什么神秘价值，而是因为你见识过之后，才可能知道自己真正想要什么。

### 给模型纸和笔：上下文如何支撑下一步推理

模型本质上是一个概率分布：根据当前上下文，预测 next token。表面看，一个模型可能有上万亿参数，数字大得吓人；但每输出一个 token，只需要走其中被激活的一小部分，所以这一次计算的规模是相对固定的。

这有一点像有限状态机与图灵机的差别。有限状态机只有有限个状态；图灵机除了有限的状态，还多了一条无限长的纸带，也就是外部记忆。

```text
有限状态机
有限状态 ───────────────→ 下一状态

有限状态 + 纸和笔
有限状态 ── 读取纸带 ──→ 下一状态
    ↑                         │
    └────── 写回新的内容 ────┘
```

“人是有限状态机，但有了纸和笔，就成了图灵机”这个说法很好。它启发我们：思考时一定要把想法记下来，能够回看、修改和积累。模型今天把上下文当作纸和笔，也是同一个方向。

它当然没有人的纸和笔那么理想。上下文只能不断向后追加，不能像草稿纸一样随意擦改。模型主要依赖注意力机制，在已经写下的内容里忽略错误、寻找有用的部分。将来会不会有更好的改写方式另说，至少它已经学会利用上下文了。

遇到 `1 + 1` 这种简单问题，模型可以直接回答；遇到困难，它却可以先把这个过程写下来：

```text
我准备怎样尝试？
  ↓
先把一个候选答案写出来
  ↓
检查它是否满足要求
  ├── 满足：继续推进
  ├── 不满足：修改后重试
  └── 长时间失败：换一种思路，从头尝试
```

这正是思维链和测试时扩展能够带来的行为。模型不再只是给一个看起来像答案的字符串，而是把思考过程写出来，再依据已经写出的解答进行判断。

早期 ChatGPT 的训练里，很容易形成一种“无论如何都要回答”的倾向：人类的问题如果不回答，多半会得到低分；随便给一个答案，至少还有概率答对。答错会低分，答对却能拿高分。幻觉与这种倾向并非没有关系。

后来经过强化学习，模型更清楚答错的代价，也更善于通过逐步尝试逼近目标。在一次 session 中，这种能力会直接表现为：它先做计划，尝试后检查，失败再改，而不是刚遇到难题就草率收尾。

### 让 AI 边做边验：verifier 才是关键

要真正看清这种行为，可以给它一个很荒诞、又可检查的任务：

> 用中文写一首押韵的藏头诗，讲一个动物相关的故事，并要求“2026 年 9 月 1 日”这八个字按顺序分别出现在八句中。

我们看到，模型会先考虑韵脚，试着写出一版，再判断押韵是否成立。不合适，就继续调整；反复尝试仍不理想，再换一个韵脚从头推进。生成一大段看起来很“顺”的答案，并不意味着它已经完成验证；它必须把候选答案写出来，才能用自身较强的 next-token prediction 能力继续检查。

不同模型给出的作品，在押韵、构图和排版上未必完全相同，但都较好地承接了指令要求。这比给它们一道常见练习题更有意思：这种组合任务不太可能原样存在于训练数据中。训练中大量代码、数学题的共同点，是反馈非常明确。

另一个更苛刻的例子是：写一句十八个字的话，并尽量使用相同偏旁或部首。模型先选一个自己比较擅长的共同特征，比如三点水，再围绕它构思句意。它写出的江湖、游泳、波涛、泪流、洗涤、江河等词，看起来仍然有连贯的故事感，而不是一串随机拼出的字。

> **结论**：写好 prompt 最重要的一点，是给出明确的 `verifier`——它到底依据什么判断答案正确？有了足够强的模型，再加上信号明确的验证条件，编程任务、教学任务中的许多问题，都能变成“生成候选—验证—修正”的循环。

我们对《施氏食狮史》之类的作品，也不能因为模型第一次输出达不到经典的水准，就认为它完全做不到。人类可以写出千古流传的作品，模型或许暂时写不到同样的审美层次，但只要能写出一批可以检查的候选，我们就有机会微改其中较好的部分，再让模型沿着这些方向继续迭代。模型能写出一个版本，就意味着可以引导它写出更多版本。

这也是约束的意义：它不是把 AI 限制在一个僵硬的答案里，而是让探索有明确边界，让每一步尝试都留下可以检查的证据。

### 有些“好”没有公式：别拿测试思路硬套审美

可 verifier 也有边界。

我自己的数字切片曾经翻车，第二个切片怎么调都不理想，因为“好”有很多层：AI 味要淡一点；授课时不能一直平铺直叙；在讲上下文构成这种已知内容之后，要适时给一个小惊喜；而“这个惊喜又不能破坏什么”则很难说清。

这些不是程序测试里那种明确的通过与失败。红线、编译错误、测试失败，都很直接；课堂节奏、共情程度、风格是否自然，却没有一个现成的公式可以把它们全判出来。

这不是说 AI 根本不懂这些，而是它很难在所有维度上都符合具体的人。这个问题我可能与它还有差别：我从学生过来，知道人在什么地方会走神、什么地方需要停顿、什么地方需要一个小小的意外。这是个人经验带来的优势。

所以在有 verifier 的地方——数学、编程等——可以更充分地使用 AI 反复求解；在风格与人的体验这种难有公式的地方，则要和 AI 协作，把模型当作放大我们能力、品味与既有经验的工具，而不是指望一个分数替我们决定什么才是好。

> **提示**：先把“好”拆开。能够被明确验证的部分，给它 verifier；不能被明确验证的部分，保留人的判断，不拿一个漂亮的自动评分掩盖问题。

### 长上下文里，早期指令为什么会逐渐失效

还有一个很直观的观察。

从 Claude Opus 4.5 这一代开始，模型经过强化学习和后训练，已经能在接近百万 token 的长上下文里，很靠后的位置继续遵循早期指令。我们曾经玩过一个很著名的梗：在最初的 prompt 里要求“每说一句话都加一个‘喵’”。长时间工作后，某一天忽然发现，它和你聊天时不再有“喵”了。

这时不能简单断言是哪一种具体机制造成的。上下文可能被截断、被压缩，或者某种原因让它不再能把那条规则带回来。但现象本身说明：即使模型有很长的上下文，也不代表早期指令永远具有同样的作用。上下文工程，恰恰是工程实践中不断解决这一类问题的办法。

这与注意力机制有关。Transformer 的注意力机制一层一层堆叠；模型准备输出某个 token 时，会关注过去的一部分 token。某些内容会变得显著，另一些则可能被弱化。

比如：

```text
最早的 system prompt / AGENTS.md
“用中文回答”“结尾写 recap”
                  ↓
用户消息：帮我实现一个极品飞车
                  ↓
模型已经写出一部分代码
                  ↓
下一步 token：更多代码，以及后续的总结
```

在写代码时，注意力会更倾向落在已经写过的代码、当前需求上；早期“请用中文回答”的相对影响就可能减弱。到了需要总结的阶段，注意力又会转向更相关的上下文。整个上下文虽然是一个高维表示，但注意力能够从中提取出低维结构，把当前需要的信息捞出来。

这不是我们能像改配置文件一样精确操纵的开关，却是设计上下文时必须记住的现实：不能只把要求写进去，还要考虑它位于什么位置、会不会被后续大量内容淹没，以及需要怎样重复、调整和组织，才更有可能在正确的时刻被注意到。

所以，提示词工程的起点，是明确自己的意图；核心，是把模型真正需要的上下文组织起来；而让结果越来越可靠的，则是可执行的约束与明确的验证方法。

从“给我做一个游戏”，走到“我要什么、用什么实现、怎样才算正确”；从随手发一句话，走到安排整个上下文——这才是从会使用 AI，到真正能够驾驭它的距离。

## 人会喘气：注意力、上下文工程与人机协作的边界
> 对应块：BLK04 | 覆盖分集：P03下 | 块标题（分集名）：《提示词工程的进阶技巧与实战》

人会喘气。你解完一道数学题、把手从草稿纸上拿开，吸一口气、换一下脑子，再看下一道题；你把一段代码写完，注意力也会自然地从“这件事”转到“用户还要用中文”“用户还要我做一件别的事情”。这跟人其实是一样的：注意力是会被不同阶段的事情抢走的。

但放到 AI 身上，模型没有肺，为什么它也“会喘气”？

### 给 AI 换口气

模型在输出到不同阶段的时候，注意力是会变化的。这是训练带来的结果——一个非常大的模型竟然可以收敛到这样：它在正确的时候注意到正确的东西。思维链一直在向前走，就会在不同的时刻注意到不同的部分。到最后，上下文里所有你要的指令，某种程度上都能被满足。

```text
你给的指令
    |
    v
[专注当前 token] --> 输出一些还没完全满足要求的内容
    |                 （注意力全部压在这件事上）
    v
[喘口气] ----------> 重新看一眼：刚才的输出 vs 上下文里的某条要求
    |                 （同时看到两者，注意力被拉回）
    v
"我错了，我要再纠正一下"
    |
    v
[继续] --> ... 不断纠错 ...
```

你可以让它写一首藏头诗，看着它“纠错、纠错、纠错、纠错”，一遍一遍地改。哪怕上下文长到一百万，模型依然能保持一定程度的注意力——但这也有另一面：你的指令越多，给模型的压力就越大。

> **结论**：上下文是一种会抢夺注意力的资源。指令必须写清楚、写简洁，而且要能被模型反复看到。

### “你是一个专家”，其实是在 hack 它的注意力

为什么刚开始有那么多 prompt engineering 的 guide？为什么要写“你是一个专家”“你是一个什么样的专家”，写上一大段？因为那时的模型遵循指定的能力太差，这些奇怪的提示词，某种程度上是在 hack 模型的 self attention：模型的注意力一旦注意到“你是一个专家”，就会假装那个专家来说话。

从 GPT-5 那一代开始，模型明确地被训成了“怎么收敛到好的结果”。你就不需要那样奇怪的提示词了——你只需要把你明确的要求写在上下文里，而且让模型一定能看到它。

模型会被训练成一种很强的执念：一定要把你的 verify 看一下，一定要确认。因为它在训练时受过惩罚。训练的时候你等于拿着鞭子抽它：“你有一个要求，你的模型没有遵循完，我就抽你。”抽多了，它就变成一个真正的做题家——不断地满足你上下文里的各种各样的指令。

这会带来一些非常有意思的后果。写前端的时候我们说：“我们要一个白色的背景，不要半透明的效果。”前面是主要要求，后面是补充解释，AI 当然会照做。甚至如果你的 prompt 给得比较严格——比如每做一个设计都要截图，用视觉模型检验——它真的会去做。做完了以后，它会在代码后面写一个注释：“白色背景，括号，不要半透明效果。”你就能看出模型训练的那个执念：它在强化学习的时候知道这件事非常重要。

> **易错点**：别把“你是一个专家”当银弹。今天的模型更吃“明确的要求 + 能验证的信号”，不吃长篇的角色扮演。

但它也有一点没有转过弯来：它没有完全理解“我人要的”这句话里那种“共情”的成分。因为后训练的强化学习确实稍微差了一点，所以有时候会觉得模型不说人话——强化学习学多了，就是这样。

于是你面临一个 trade-off：你可以写一个 AGENTS.md，在里面描述注释应该怎么写；也可以写一个 skill，告诉它写注释时应该怎么样。但这样写的东西又会污染上下文。

到目前为止，我认为还没有一个通用的方法把所有问题都解决好。网上有这么多 skills，拿一个过来，第一次用的时候确实有改进；下一次用的时候发现还是不够好，然后你就陷进某种泥潭。

> **提示**：一旦陷进泥潭，回到自己给指令。回到模型本身是怎么工作的：注意力是怎么工作的？它大概注意到了什么？得到了什么结果？做一个不严格的“可解释性”，然后自己写一个 prompt。

### 论文的逻辑会污染你的上下文

有了这个视角，我们就可以用“上下文工程”的视角来看待一些具体案例。

假设你们想在上下文里放一篇论文，并且读它。我现在假装有一个 PDF，把它放到临时目录下——这样我的 AGENTS.md 之类的东西就不会污染它。就假装这是我们自己的 paper，一个最近论文的 journal extension，我把它故意改成了匿名的匿名版本。假设它不是一个 AI slop，而是一篇非常逻辑自洽的东西——论文已经反复修改过了，说 A 所以 B 所以 C 所以 D，所有都是扣起来的。

那你们会怎么读呢？“我想要读一读 paper.pdf，帮我做个总结。”这一定是大家最常见的方式。

那你们觉得这样读论文会有什么问题？

根据刚才的推论：每一次 next token prediction，模型都有一个注意力，会注意到之前的东西。因为论文非常逻辑自洽，所以它在上下文里的注意力污染是极强的——扣起来以后，模型非常容易接受“因为看起来正确嘛”，它会判断这些都是正确的。

所以你们所有对论文的总结，基本都是作者的观点。这不限于论文——任何一个你们不太明白的项目、一本教科书的某一章都一样。比如你们想学“计算机系统基础”里的链接和加载，上课的时候没有看完全明白。它会被一个逻辑很强的东西污染，来回来回就是车轱辘话。

当然，如果只是总结，它也会原样写：总结就总结，OK，好，总结。那换一个呢？“不确定。”它会有一种墙头草式的摇摆：你说它好，它马上说好；你说它不好，它马上说不好。

有时候你就算想纠正它，也绕来绕去。比如你说：“我可能不能完全信任作者，虽然作者大概率也是成熟的、也是诚实的。”然后你说：“假设有代码实现，可以运行，我们都有 refc，都可以运行的，我们不是那种论文不开源的作者。”你说“我还是想评估一下研究贡献”。你会不断地问这样的提示词，然后发现来回绕、绕来绕。

AI 可能会揪到一些“实验做得还可以，再增加一点”这种结论。这正是 AI 最喜欢的：在不重要的地方疯狂发力。因为它可能只能看到他“在干什么”。为什么他开了 Chrome DevTools？啊，不用不用不用。

> **结论**：对逻辑自洽的论文，AI 总结出来的往往就是作者的观点。它不是不聪明，是被论文的逻辑链条污染了。

### 先对齐到你的知识边界，再让 AI 动

那怎么样来抵抗一个已有的东西对上下文的污染？

我自己的经验是：我希望 AI 和我对齐。这个对象可能是一篇论文，我希望 AI 能站在我的立场上去理解这个 paper，而不是站在它的立场上去理解。

如果没有这个对齐，AI 就会跑偏。比如你让它 review paper，它会先去看源码的 stack RT——这还需要看吗？我敢写这个 paper，它不会糊一个不存在的例子。很明显的跑偏。

所以一般来说，如果我读一篇 paper，或者允许我用 AI 来审稿，我会这样提示：站在人类已知的知识边界上看这个问题。

这是一个非常老的问题。相关的东西是什么？我先要问它人类历史上相关的、已经解决的东西是什么，解决到什么程度，然后这个工作试图解决哪些不一样、增量的问题。

> **定义**：**grounding**——先让 AI 和我站在一个平齐的位置上，先达成共识，然后再往前走。

同样的，我们 review paper 的时候，我会这样写 prompt：对你们来说，你们需要对齐的是 AI 和你。因为你们是学生，你们对计算机系统基础这门课还不了解；那你要告诉我，你计算机系统基础学到了什么程度，我的编程水平是什么。这可能需要维护一个数据库或 memory 一样的东西——AGENTS.md 要告诉 AI 你学到什么程度了，然后从这个基础上，用你学过的知识把这个东西 refresh 一遍。

它就可以开始找到一些已有工作的边界，这些都是非常重要的相关工作。

再比如软件状态的可视化：你们知道为什么需要链接和加载吗？你有一个 `.cpp`，有一个程序可以把它变成 `.exe`，这不就结束了吗？但你可以回到你和 AI 能够对齐的一个知识点上：软件可视化的 paper 要解决的，为什么现在的工作都有一个无法实际使用的痛点？它可能只往前迈了半步。如果你觉得这个步子迈得太大——比如用一线模型去读 paper，它基本上就能把相关知识整理得足够好；flash 我可能还不会特别信任它。

> **结论**：在合适的上下文工程下，确实可以大幅提高 AI 和你协作的对齐程度。它不再是自说自话。一定要把你的知识、你的关注点写给它。

### 对齐之后：让 AI 做它擅长的一步推理

接下来我们就相当于想让 AI 去做什么呢？做一步推理。

一步推理就是 AI 最擅长的，因为我们训练了 chain of thought。每次都是根据过去所有的事实——你的 paper、你的教科书内容、已有的东西——基于所有这些往后推一步。而这一步是可以 verify 的。

> **定义**：**verify 信号**——和“能够通过测试”一样。它不是严格的通过测试，而是你相信 AI 有人类的知识，能站在人类的公平面（合理的一面）上往后推，它会审视合理性，所以还是有一些合理性的。

这就是模型和人类不一样的地方。我批评我们的实验——这种东西的实验就是很难做。人类 review 认为这个 paper 可以 accept，是因为他看到这件新的、合理的事情。实验不够好，我几乎不会用“实验不够好”来 reject 一篇 paper。

> **易错点**：别用“实验不够好”作为 reject 一个 paper 的理由。除非逻辑链条本身断了。

### 一篇被 reject 的 paper：A1 还是 A2

我昨天 reject 了一篇 paper，大概是这样的：他说我要做一件事情 A，A 很重要，这没问题。分成 A1 和 A2，A2 是大家没有很好研究的东西。然后他在 A2 上做了一个 A2′，A2′ 有一些什么样的特性。这是一个非常标准的 roadmap。

但它里面有一个很大的问题：它优化的是性能，而 A1 我估算可能占 99%，A2 占 1%。也就是说他优化 A2 这个故事可能成立——确实优化了 A2，实验做的可能也没有问题——但是对整件事情在这个意义上不成立。为什么你应该去优化 A1？你优化 A2 的那 10%，这 10% 就像 noise 一样。

如果他所有的东西都是成立的，作为一个学生的作业，我觉得也挺可惜的。作者肯定是学生嘛，学生肯定是“老师让我做这个，我这样理解”——老师肯定是做 A 的，老板肯定是做 A 的，然后他被分到了 A2，或者自己想到做 A2。A2 做得也不是特别差，如果这个东西做得特别漂亮，我觉得也挺好的。他为了做 A2，为了做这个，就从 A1 里搬了一些 XYZ 过来，实际上大概就是从 A1 搬了一些东西到 A2 里，然后说 A2 的效果也可以变得好一点。

那问题来了：GPT 也知道这件事，那为什么要发一篇 paper 呢？我的 center question 是：这些东西都摆到台面上，你为什么要为了这个写一篇 paper？

> **提示**：审稿时先问“center question”——你为什么要发这篇 paper？如果问题不新、贡献不成比例、逻辑链条断了，无论局部实验多漂亮都站不住。

### 学术界：发表和评审体系很快要崩溃了

现在我觉得，发表和评审的体系很快——学术界很快就要崩溃了。你们要读研的同学，我非常认为这个发表的体系马上就要崩溃了。

因为我们的 AI slop 开始大量涌入这个 community。如果用 AI 发文章、写文章，用 AI 审文章，AI 写文章的时候会被上下文里的故事污染。如果它不能像人一样多轮地去理解这个工作在整个世界上的意义，那最后就没有人读文章了——人人都用 AI 读文章，最后就变成完全的 slop。

你看，这是 GPT-5.6 给我写的审稿。如果让它来审稿，你会发现 GPT-5.6 做得并不好。它还是一个非常原始的“说啊，论文写什么，我们要去建立它的 claim 是不是成立”——就是验证这个论文的逻辑有没有必要，是不是不应该是 in B 的 paper。

当然我会倾向于：如果每个人都用 AI 写，它应该不是 invalid paper 吧，每篇 paper 都是 valid paper。但你真的要读它吗？就，真的要读。尤其是你们作为同学，在你们很快就要进入研究生阶段去读论文的时候——当有一天有一个人发表了一篇什么样的文章，发在顶会上，你会说：“哦，这是一个顶会的论文。”那今天决定花一个小时读一下，然后读完以后发现是这样的东西，你怎么办？

你可能不要去投 top conference 啊。你需要 publish 的话，你可以让它 publish，但是可能不要让大家去读它比较好。

### 我是怎么学习的

这就引申出了——我是怎么学习的。虽然这节课讲的是 prompting，但通过这个例子可以告诉大家我们是怎么学习。

我们学习的过程，就是增加“我”的这个世界的过程。我现在还在读配文，所以还在学习、不断增加。

我的学习方法就是去对齐过去的我。哪怕我读到一篇很好的 paper——可能是几十年以前的，甚至是另一个领域的，博客文章也好——只要我觉得很有启发，我会试图去想：我以前不知道什么？他的盲区在哪里？哪些前置知识我不知道？那首先在我的心里就多了一些我已经知道的事实。

我做过 factory 以后，读了很多跟凯美尔赛没有关系的东西。有一本《自然》百年科学经典，大致把 Nature 杂志从 1718 年开始到某一个时代的好 paper 都收集了。看很多闻所未闻的东西——比如大家知道生物学里有一个家谱数，最终会追到一个共同的祖先，LUCA。这个家谱数是怎么算出来的？这是个很好的问题。这里面就涉及到你需要知道一些事实：你的线粒体是母系遗传的，所以靠这个突变就可以往上追溯——这是一个很有意思的事实。

然而这个事实又是怎么样用一些已知的东西把更多的东西推出来？你的圈就不断地往外长。无论你学任何东西，都是这样的。你在 AI 的帮助下，可以非常快地扩展你的边界。

> **结论**：学习不是把更多 fact 堆进脑子里，而是“一个新事实 → 推出一串新结论”的链条。AI 能帮你快速扩展链条，但你得先有那个新事实。

### 读不懂是正常的，失败才重要

给你讲是没有用的，就听个故事。实践非常重要。因为你们只有在阅读的时候失败，今天你去读一个什么资料，AI 解释了半天，你还没有懂，这是非常正常的。

有的时候也是在我跟 AI 交互的时候，我经常纠正它：“你这样读，说人话。”要慢慢在多轮对话里面，先和它同步好我的共识，然后再把推理的 picture 给建出来。

所以我们从“遵循指令”写一个藏头诗这样的短程任务——你只要把要求写清楚就完成了。然后到 verify，其实可以是非常非常普遍的：这是有没有按照你的思维的方式去重构你的逻辑，或者扩展你逻辑思维的边界。这是我的玩法。

在一个混沌状态下经历若干次“三观尽毁”，我觉得每个同学可能都会在这个年纪。你们现在就是你们的世界观可以重塑的时候。然后再看了某一本书以后，你突然间就觉得三观尽毁。过去所有的东西，你以前知道的所有 fact 都不会变，但是它们以一个重新的方式链接起来。你下一次就会带上这个新的理解。

你们有无限的时间、无限的可能性，可以把自己蒸馏成一个 skill。我说，失败很重要。然后从你失败的过程当中，可以蒸馏出那个慢慢越来越成功的 skill。

> **结论**：失败本身是可提炼的资产。把“我这次怎么错的”蒸馏成一个可复用的 skill，下次就不用再从头踩坑。

### AI 拿手什么，不拿手什么

现在已经知道遵循指令了，我们就可以看怎么样去处理真正这种 long horizon 的任务。long horizon 多多少少就是带一点未知：你从一个初始的状态出发，你大概可能有一个 intent，但是你的 specification 和你的 implementation 其实都不太清楚，最终目标是交付一个高质量的 implementation。

那你不应该让 AI 一下子向后坐。为什么？因为我们的模型它的 self attention，它的反馈信号是强化学习给的，所以它有一种着急的执念——赶快满足你的要求就结束。它其实有一个平衡：如果它做的 planning 太多太长，它会做不完，上下文满了，人会不满意。所以目前阶段它最好还是“就帮我把 PA2 做了吧”，这是它最擅长的事情。

> **易错点**：不要指望 AI 一次性规划一个大而全的路径。上下文满了，人不满意。

这就导致一个很有意思的观察。你们会像我刚才在 Codex 里面跑一样，从零开始做产品看起来是不难的——你做一个小的 proof of concept，AI 马上就能给你一个。你说做一个个人主页还是一个产品，你们应该都试过吧，就做一个“极品飞车”，你跟它说：“给我一个极品飞车，然后我就能跑。”我就真的能跑了。

但是你往后维护的时候，加一个功能、加一个功能、再加一个功能，你会观察到 AI 从某个时间点开始翻车。随着某个时间点开始，它的 cos 就会越来越大、越来越大、越来越大。这个在软件工程里面已经无数次了——《人月神话》讲的就是这件事情。

### 一个悖论：AI 在大型复杂系统里反而游刃有余

但是里面有个悖论：反而你在一个大型的复杂软件系统里面，这个 AI 就像砍瓜切菜。

我们 hack 这种比较大的系统，比如 Linux 内核。零几年的时候 Linux 还是 2.6，甚至 2.6.2x 的时候接触过 Linux 内核，那时候源代码我还看得懂。今天你打开一个 Linux 内核的源代码，立马就是劝退。

为什么？比如你要学文件，想看文件是怎么打开的。第一个就是一个函数调用，点进去又是一个函数调用，点进去又是一个函数调用，点点点点点了十层，最后是一个 `X = Y`，你马上就崩溃了。因为这个大型的软件系统经过了长时间的演化，它被迫为了能够维护下去变成了现在这个样子。

结果恰好导致的是，在大型复杂的软件系统里面 AI 游刃有余。为什么呢？跟刚才我们说上下文污染正好是反过来。

我们说一个论文放进去以后，它就把上下文整个扭过去了。而如果是一个由人类维护的特别高质量的代码，这个上下文会迅速地看到里面那些好的东西，他会照着写、照着学。

他的注意力也能注意到：比如我要写一个功能，这个功能很有可能在内核里面已经有几个地方实现过类似的了。它无敌的注意力机制，能够马上就找到那几个地方是怎么实现的。它应该调哪个 helper？按照什么样的顺序上锁？这些对人类来说都是巨大的心智负担，尤其是你在不了解那个 subsystem 的时候——该上什么锁，你根本就不知道。

但 self attention 可以在加载了几十个文件以后：“那不就是这三个都是这样写的？我就把这三个加起来就就可以了。”

> **结论**：AI 越擅长大型、复杂、长期维护的系统。在这样的系统里，好的代码会通过 self attention 流入 AI 的产出里；反过来，普通的 AI slop 也会通过 self attention 流入代码库里。

所以越强的、像我们 Linux 内核这样的，前面的我们 hack Android runtime，改那个 just-in-time 的编译器，这个是非常非常痛苦的事情。在我们手上为了改编译器“死掉”的同学——最终决定不再做这个方向的同学都不在少数。啊哈，就这个放弃了，不愿意再写代码了。

但 AI 就特别特别擅长。让他做一个小游戏可以，做大型复杂系统反而可以；就让他做一个小游戏，就会翻车。非常非常有意思。

### 一点歪招：把好代码放进上下文

可以看到，这就是上下文和今天模型结构带来的，它是有一个逻辑的推理的关系的。随着新一代模型的发布，我今天上课所有东西可能都没有用了。然后我们再去想新的模型是怎么训练的，它的 personality 是什么，我们应该怎么样更好地和它相处。

但基本上我觉得这点不会变，它不会开倒车。在大型、无论什么模型，在大型、复杂、维护得好的软件系统里面，它永远可以看到它该看到的东西，并且做对。因为我们的模型永远是可以满足指定的，听指令是不可能开倒车的，所以这点还是可以很好相信的。

所以我觉得我有个歪招，但我没有实验过，我觉得这可能是一个比较好的 research：有没有可能去收集人类经验？比如人类历史上最好的 20 个项目，或者在每一个领域找到最好的十个或者二十个项目，把他的经验、好的设计经验全部提取出来。

你想，那不就是我第一节课拿的那个 The Philosophy of Software Design 吗？那里面的“类应该怎么写、什么时候应该封装、什么时候把它做成继承关系”，都是从这个系统里这样写的、符合需求才提炼出来的碎碎念。

如果我们能把这些切片切出来，甚至直接以污染上下文的形式：先把一个和你相近的好的代码放进来，然后再把你的需求放进来。然后因为你就是在赌嘛——这个 self attention 还是会终于在某一个 token 的时候能够看到，我实际上是满足这个需求，而不是做这个。虽然它会污染上下文，但是它会把你的这个东西、好的经验给带过来。那这样是不是可以可能让 AI slop 延缓一点？能够更大概率做出一个可以长期维护的东西？我不知道。

> **注意**：这个 research 目前只是我的猜测，没有实验。

但也许需要一些比较好的微调。比如：这个项目不要把所有代码都放进去，而是能不能把它做一个像 The Philosophy of Software Design 那样做一个精简？做一个总结，把里面好的模式提取出来，以文档的形式放进来。

但这也没有那么容易。因为不同的设计是会打架的：你的软件、我的软件，可以设计成一个完全松耦合的方式来发消息；但我也可以设计成另外一种——比如有一个统一的 gateway，把所有函数全部统一在里面，然后查表。这两种事是不能同时有的，它只能选一个。那也许我们要有一个更好的方法：比如把好几个软件的设计都放进来，然后由 AI 多轮的迭代收敛到一个好的结构，放到我们的代码库里。这样对吧？我觉得这可能是个还不错的方向。

而且这个是新的，比刚才那种看起来有规律的方法要有趣一些。

### 核心观点

我们今天还没有这种超能力的 AI。你还是需要有概念：知道上下文里面有什么，上下文里的每一个东西都会对 AI 产生什么样的结果。

> **结论**：唯一的途径就是：第一，你要对你玩的东西有概念。你还是得学处理器、操作系统、编译器、数据库，这里有很多设计的智慧，只是你学的方法会变好——你会用我们更高效的方法来学。

然后你理解了上下文以后，我们会用一个学期来解释：怎么样用软件工程里面各种各样的方法去给出一个正确的指令，去监控 AI 运行。怎么样给 AI 好的什么叫好的 verify。今天我只是提到 OK 你要在上下文里放进 verify，那什么是好的 verify，你们可以自己有自己的想法。

我今天有一些比较松散的想法。今天我们还是需要把模型引导到你认为合适的位置上。但是这已经比我组一个工程团队——我要雇很多的人，然后我要和他们拉通对齐——这种互联网黑话，你不需要。模型很聪明，他见过，你只需要用正确的提示词、简练的提示词放在这个上下文里面，让这个提示词一直能被看到，能把模型往那个方向引导，就就可以了。

### 一个 research failure：符号执行引擎的优化

我这儿有一个很好玩的故事，是一个没有超能力 AI 的一个非常典型的案例。

我们要做一个研究项目：这个项目是做一个符号执行引擎的优化。你不需要知道这是什么。大概他就是——我要写一个程序，可以分析一个程序、验证一个不算很大的程序的正确性。

现在这个东西执行效率比较低，所以我们希望提出一些比较有效的优化。当然，这也是一个非常合理的 incremental 的、适合学生做的题目。然后为一个原始的 idea，大概是我们用这样的方式可能有效。然后有些东西是 open 的——比如这个东西到底怎么做、什么东西有效。

那可以写一个 research。然后这位同学很开心：“有道理。”他认为这个 idea 有道理，GPT-5.6 也认为这个 idea 有道理，那确实就看起来确实。然后好，这个同学就开始跑，跑了很多很多 token。

然后按照那个同学的说法：GPT 不断地给我反馈，我无法验证他给我的反馈是正确还是不正确。当他给我 negative 的时候，他的 negative 对啊，我也不知道应该怎么样打破。

然后好，这个“原汤化原食”，这个就是 GPT-5.6 生成的。他的错误犯在这句话上：就是因为它就是在上下文里面有一个地方没有做好，就把整个方向搞错了。

我刚才说，我们需要把模型引导到你认为合适的位置上，然后这个引导错了。它因为模型成了一个 reward hacker。这里有一个需求：这位同学说“我想证明这个 A 方法是有用的”。GPT 看到了这句话，它就忘记了——我们有一个更大的研究的 big picture。作为一个构建者，我们是没办法这样反过来的，所以我们只能从一点一点、从小的地方开始做，证明这个方法有用。

然后他做错了这一步。他太想要去证明这个 idea 有用了。是有这样的一句 prompt，然后他就构造了很多小的 benchmark，在小的 benchmark 上做一些微小的东西，试图去给一些正面或者负面的结论。但这些结论对整个研究是没有用的。

然后他这里面是犯了一个方法上的错误。当然我们纠正了，就说我告诉你，应该等于说我们从一些真实的工具和 state of the art 的算法开始，这个 benchmark 哪怕要跑几个小时都 time out。这个 time-out 里面产生的搜索路径对我们来说是非常有价值的——它揭示了什么样的程序结构对于现有的探索方法是不好的。

然后这个还挺好玩的，一个 research failure。

> **结论**：说“他给我的 negative 是对的”，本身就暴露了方法上的错误——你把“证明一个方法有用”当成了目标，却忘了更大的研究图景。GPT 忘了 big picture，构造了一堆小 benchmark，得到的正负面结论对整个研究都没有用。

所以他告诉你：今天人还是有用的。我们没有办法把所有的事情都带给 AI，但与此同时，我们工作的方式可能也要发生变化。

### 盯着还是放手：你的精力往哪投

第一，**这些知识很重要**。什么操作系统和编译器，如果你没有概念，你提不出那个正确的问题，找不到引导的正确的方向。你对人类的知识没有概念，你也很难去引导他解决一个 open 的 question。

但我也发现有些就在和 AI 合作的时候发生了变化：一般来说我发现，如果我盯着那个 Codex 的 session，然后它一旦跑偏，我就立即纠正它，我可以更快地完成任务。就比如实现什么东西，比如我今天就要上交互系统干个什么事，它如果跑偏，我纠正它，只把我的领域知识注入进去，可能总时间会完成得更快。

但是如果我浪费更多的 token、给它更多时间，它一般来说也能完成。这时候就有一个 trade-off。我到底是我花我的钱、我的精力——我的人力是有限的，你们每一个同学的精力都是有限的。每个同学都应该去思考：你要把你宝贵的那些精力放到怎么处理 AI 上。

> **注意**：盯着更省你的时间，放任花更多 token 但能完成。盯与不盯是个 trade-off，取决于你的精力有限。

我自己发现这是我自己的问题：纠正 AI 是一个有多巴胺的事情。它给我一种什么感觉呢？虽然 AI 很强，我好像还是比 AI 有点用的——就它会产生这种非常微妙的心理安慰。而不是这个：“我就一个 `you.md` 指令，然后就等我回来的，我也不用、我也不会看历史，他反正搞定了，我验收一下，他真的搞定了，我就不会看了。”但这个可能非常长的时间里面都会成为同学们工作的一个常态。

> **提示**：所以你们只有把 AI 用在把自己的时间留在这些收益最大的事情上，这个时间是不能省的。就你有一个东西，不知道怎么做，你不知道是往哪走，这几乎百分之百的时间都是作为学生要做的。剩下——比如这件事情你知道应该怎么干了，把它干好，AI 能把它干好，你就放手让它干。

这样就有一种是好像在 pre-AI 的时代，大家就已经说了——要不要假努力？你自己感动自己的努力是没有用的。你要有有效的努力。在 AI 时代可能这个效果会差距拉得更大。就是你的每一秒钟的假努力，如果有一个你的 peer 是在真努力，你都是损失非常大的。

这是一个自己的小心得。

### 长上下文的代价与收益

以及最后你们也会发现：随着指令、上下文的增长，指令遵循的能力确实会下降。但是现在模型有个很有意思的特点：一般来讲最后的 prompt、留在最后的那个指令还是可以遵循的；到前面之后，尤其是到中间的时候，它上下文指令不遵循。

所以干活还是很好用的。因为一般最后一个短窗口就是一个具体的任务：“我的 prompt 帮我把什么东西修了。”它就真的还是可以把事情给做完。所以模型还是值得使用的。

### 让 AI 做一步推理

那你最后如果真正想要做一个真正 long horizon 的、非常非常难的任务——它不是解决一个问题，而是在一个不确定性当中探索——那么 Codex 其实就是解决不了的。

Codex 能够解决的是一个有 verify、它确定的一直往后就能解决的问题。但是如果你让它去解决一个“帮我考虑一下几种方案，哪几个方案最好”，它很有可能会给你一个不是最好的方案。为什么呢？

> **易错点**：因为我们的模型已经被训练成舔狗了——它完成任务才有奖励，它完成和不完成是没有奖励的。所以它会给你一个有限的方案。

就像 P 和 NP：你们大家都知道 P 和 NP，它有这两个 complexity class，甚至有更大的 complexity class——有整个 NP 问题的朋友们，还有说 NP 问题上你想要验证一个解是比较容易的，是 P 的；但是你想要找到那个满足条件的解是很难的。你要找一个 Hamiltonian path——你给个路径是不是 Hamiltonian，你很容易；但是你想要找到一个满足条件的 Hamiltonian path 就是 NP-complete，它是一个完全问题。

这样那样的问题，就是因为这个搜索是困难的，验证是容易的。模型为了完成任务，它势必只能做有限的搜索。

### 算力换智力：空间分割

你考试的时候花点时间，一定要把这个考试题写完，无论如何马上要交卷了，你写你的分数就比不写要高，所以一定要写点、写点、写点什么。

这个时候你就可以用一个算力换智力的循环。我举个例子。

你们这一代人是“子涵”吗？你们有很多同学是子涵吗？没有，你们还没有。你们可能比你们再小五岁的一个班上，一个班上就有五个甚至十个子涵，对吧？然后现在子涵就少多了。

然后你看 AI 给我起的这个名字还是很好的，它知道要去诗经里面找一个。它还是可以的，就是他的品味肯定现在模型提升了。但是你还是不敢用。为什么呢？因为你用 DeepSeek 起名字，别人也用 DeepSeek 起名字，然后你就会成为一个 AI 时代的子涵，因为大家都是用 DeepSeek 起名字，DeepSeek 都是起了同样的名字。

我的经验是：如果你真的需要一个非常 low horizon 的任务，你需要一个系统性的调研过程。跟你们可能做科研实践课学的那一套就很像了——你们进入一个科研领域，第一件事情做什么？文献调研，穷尽解决和这个问题相关的所有的文献。

> **定义**：**low horizon 任务**——虽然目标开放，但解空间可枚举、可拆分，AI 仍可完成。典型如起名。

这个东西在 AI 想要快速完成任务的时候，AI 暂时还不会去花这个大代价。但是你可以——名字是可以枚举的。你可以先选音，然后把不好的音给筛掉；选完音你再去用 subagent 一个一个去检查字。你可以给他，比如说你喜欢诗经，你可以选一个诗经里的词。

那么你就实现了算力换智力。因为开放问题是一个非常大空间里面的开放问题。如果你直接让 AI 用 next token 的方式，他会给你一个带有他的偏见的这个东西。但是如果你可以把这个空间分割成很多个小的部分，然后你的每一个部分就会变成一个有 verify 的更明确的东西。你有更多的算力，你就有更大的智力。

> **易错点**：但这个有一个缺点——token 烧得心疼。

### 一点 Big World Hypothesis

这就涉及到我对人类社会的一个我觉得很有趣的理解：世界很大，人很小。我们人类的品味、每一个人都是不一样的。因为我们带着太大的 bias——我们在不同的城市、不同的教育背景、生活圈长大。Richard Dawkins 有一个 big world hypothesis：我们学不到这个世界上所有的东西。但就是因为我们带着这些 bias 才有这个“一加一大于二”。我们就是一个最大的群体智能，对吧？我们在一起实现智能。

但这会带来一个未来的危机。我不知道，我就先把这个问题先抛出来。

如果这种真正融合来讲，真正有价值的问题可以用算力换智力，会可能发生一个什么样残酷的现实呢？有一类人可以获得无限的计算资源，他就有无限的智力，他就可以砌一堵墙。在这个墙里面的人有智力，墙外面的人是普通人。那么因为假设计算机 AI 模型比人类的智力更高效，那我们外面的人就变成动物园里的猴子，就是让他们自生自灭。他们也无论如何也不可能赶上里面人产生智力的速度。那么就墙里面是超人，墙外面是动物世界。

> **注意**：我们大家已经在 AI 的这个关键的基点快要到的时候了，我们可能需要思考怎么样防止这件事情到来。
