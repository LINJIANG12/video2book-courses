## 软件从哪里来，又要往哪里去
> 对应块：BLK09 | 覆盖分集：P06上 | 块标题（分集名）：《软件工程的来龙去脉 [05-Raw_26生成式软》

在进入正题之前，先说一件这一周刚发生的事。我觉得它比这学期要学的所有内容加起来，都更能解释我们现在所处的位置。

### 一个能实时玩 DOOM 的模型，和一条被打开的赛道

有个 AI 实验室放出了一个可以实时玩 DOOM 的模型。名字起得很有想法，叫 System 1，意思是"真正人类意义上的即时决策"。

第一次看到它的时候我都愣了一下。我们过去打游戏靠的是人的视觉神经和反应速度，它靠什么？我盲猜，它可能是一个每步只能吐一个 token 的 Transformer，也可能干脆是别的架构。它做的事情朴素得让人意外：把《毁灭战士》的世界状态编码成一个 JSON 文件喂进去，让它给出一个决策，再吐出一个 token——毫秒级到百毫秒级，基本就是一个人类实时的水平。而这个 token 是被专门微调过的：它不说人话，但它真能干活。

```text
  游戏画面 / 敌人位置 / 血量 / 弹药
                │
                ▼
    ┌────────────────────────────┐
    │  把毁灭战士的世界编码成 JSON │  ← 状态不是像素，是一串结构化文本
    └────────────────────────────┘
                │  JSON
                ▼
    ┌────────────────────────────┐
    │       决策模型              │  每步只吐 1 个 token
    │   （System 1 这个量级）     │  该 token 被特调过：不说人话，只做决策
    └────────────────────────────┘
                │  动作 token（毫秒 ~ 百毫秒）
                ▼
      摇杆方向 / 开火 / 换武器
```

读图说明：整条链路里没有"说话"这一步。它不是大语言模型那种一个回合吐一大段话的东西，而是一个被压缩到极致的"决策 → 单 token"映射器，位置就在"大模型"和你们学过的决策树这类小模型之间。

这不是什么新技术。过去这些年，一直有人在做这种极快的模型。这次火了之后，意义在于：**这条赛道被正式打开了。**

而这条赛道一旦打开，对我们这代 AI native 的年轻人意味着什么？我想非常直接。人和人沟通、人和机器沟通，那个体感差别是很明显的——前两天大家还在传一个段子：几个 AI 演员在用英语对话，其中一个突然开始说广东话了。你看，AI 生成的数字人在人与人之间，是有很大延迟的。

但如果你有一个 100ms、200ms 的小决策模型会怎么样？你可以让它做决策，实时生成脸上的微表情，根据你说的话实时反应——你得到的就不再是"一段生成出来的视频"，而是一个非常有实时性、人感的东西。以前的大模型在这个延迟下也许有这个能力，但做得不是那么好；今天你就可以有了。它甚至可以哄小朋友睡觉，婴儿睡不着的难题就被彻底解决了。

所以这不只是一个玩具，它开了一个非常大的赛道。

### 这十年到底跑得有多快

这次课上分享的很多东西，我干脆让 GPT-6 去生成——我特别想看看它到底能编到什么程度。它给我画了一条时间线，我基本认可。

```text
  1956 ──────── 达特茅斯会议：AI 作为一个学科被提出
    │
  1958/1960 ─── 感知与规划的机器走出实验室
    │
  1970–1990 ─── AI 寒冬
    │
  1997 ──────── 搜索算法第一次击败人类世界冠军
    │
  2012 ──────── AlexNet：世界开始变得很快
    │
  2016/2017 ─── 我在现场看直播；那时候还在读 PhD，追 embedding、
    │              Transformer、BERT 这些东西，琢磨它们能拿来干什么
  2020 ──────── GPT-3：为什么要做这么大的模型？
  2022 ──────── 大家终于知道为什么需要它了
  2023 ──────── 多模态、生成视频；开源模型跟上
  2024 ──────── Sora 首次发布；o1
  2024.09 ──→ 今天   开源阵营追上来；GPT-6；
                    甚至有千禧年难题被"暴力、大力出奇迹"式地解决了
```

读图要点：**这条线不是均匀加速的。** 1956 到 1997，用了四十多年才憋出"击败人类世界冠军"这么一刻；而 2012 年 AlexNet 之后到今天，才十四年。中间跨度差了三四倍。

你们现在多大？2017 年那会儿你们在上初中还是高中。到现在已经 2026 年了——这已经是接近十年前的事。2016 年我在现场看直播，第二天一边读 PhD 一边刷 Transformer、BERT 那种论文，心里想的是"挺有意思，不知道能拿来干什么"。我完全没想过十四年后它会变成今天这个样子。

我自己有个很朴素的感慨：**如果素材库足够大，创作任何东西都会变得非常容易。** 你想，YouTube 和 B 哔哩哔哩上的一切，你本来就能用工具下载下来——你等于拥有了这个世界上所有东西的入口。配上生成能力，创作就从一件要押上整个职业生涯的事，变成了随手可为的事。

我特别喜欢《Silicon Valley》第一季第一集那个名场面：几个书呆子凑在一起要去干一件改变世界的事，其中那句台词是——千百年来我们这种书呆子一直都被欺负，在人工智能时代终于可以出人头地。

不管这个时代怎么变，我始终觉得：**我们每个人最终都要面对就业市场上那条不断上移的斩杀线。** 而这个斩杀线毫无疑问会一直往上走。所以今天我真正想说的只有两件事：第一，事情的发展比我们想象的快得多；第二，AI 这件事的进展，比很多人愿意相信的还要快，而且是有具体机制在支撑的，不是玄学。

那我就在这里把那个机制讲清楚。

### Scaling Law 还没停：门道在数据分布

先把"这是不是玄学"这个问题回答掉。The Bitter Lesson 从来没有失效过，到今天它的形态就是 Scaling Law，而且可能还没有停。

#### 短板不在能力，在品位

我最近看到一个访谈很值得说。来自 OpenAI 的 No Brown 有一个判断：**现在模型真正的短板是品位（taste）。** 他的定义是——模型对"接下来应该做什么"的直觉，做得还不够好。

为什么模型没有直觉？看它是怎么训出来的。我们说模型被训练成了 prompt 的舔狗：你要它做什么，它就盯着你那句话疯狂地做。同时它还有明显的 reward hacking 倾向——任务完成就有 reward，那它当然会用最快、最脏的方式把活干完。而且强化学习给它的是即时反馈信号，所以它会执着地去强化那些"立即有反馈"的东西。结果就是，它生产出来的东西，从长期主义的角度看往往是让人不满意的。

> **易错点**：这不是"模型不够聪明"，而是"模型优化的目标函数，和人真正想要的东西不完全一致"。凡是有反馈信号的地方，它就会朝信号最密集的方向优化。

我的看法是，这个推论没有根本上的道理——**我们不能用更多的合成数据去告诉模型"你想远一点"。** 你 chat 的时候，头几个 token 其实就已经决定了你要做什么；后面再长的输出，也是从开头那个约束里长出来的。

他还提到了可验证与不可验证的边界。我觉得品味可能是不可验证的，但也许没那么难；而数学虽然是可验证的，但"可验证"本身也没那么容易。因为你就算把一个问题 formalize 了，**从自然语言描述的问题，到形式语言描述的问题之间还是有 gap 的**。

前段时间有个特别好笑的事情：有人声称证明了黎曼猜想，或者 P≠NP（这两句在这里有点混）。结果后来大家发现，他那个形式化证明里，问题的定义本身是个空的——他定义了一个"不存在的东西"，然后证明了一等于一，写了几千页。

所以可验证性这件事，没有我们想的那么干净。

#### 越往后越省数据：语言、空间与飞轮

看 GPT-6 发布，我最大的感受是：OpenAI 摸到了一个门道。这个门道该叫什么我也不知道，我暂且叫它**数据分布工程**。

我前面说过，GPT-6 有非常惊人的空间推理能力——它能理解一张图里的空间关系，因而在画图、在生成上都做得非常好。毫无疑问，是因为训练时加了这一部分的数据。可能在基模训练时就加了；同时在后训练、强化学习阶段，也有更多数据帮它理解空间，给它反馈：这样做是好，这样做是不好，或者对、错。

另一个维度的 Scaling Law 就是：更大的训练数据能带来更好的基模。所以 Anthropic 去**买书、烧书**——把书买回来烧掉，他就有了绝版的数据，就能比别人更强。

这里有个更让人不寒而栗的推论：**如果我们有一个已经很好了的基模，再加一个它没见过的领域的数据做强化学习，它就会在所有任务上都做得更好。**

我们可以把已经训过的东西列一下。最早的模型完全就是语料——语言的 token。然后训练视觉、做多模态，再训练数学；学会了数学之后，才学会空间感知的关系。

```text
  模型：  语言 token  →  数学  →  多模态  →  空间感知
          （先有语料）   （会推理）  （会看图）  （最后才懂空间）

  人：    世界模型  →  语言  →  数学  →  research taste
          （先摸爬）  （一两年才开口）        （读 PhD 的时候）
```

读图要点：**人和模型正好是反过来的。** 婴儿一出生就和世界交互，先学的是世界模型；训练一两年三年之后才开始说话，幼儿园小朋友说话都还不利索。人是先有世界模型，再训练语言，再训练数学，再比如读个 PhD 训练自己的 research taste。

但这不是重点。重点是：**不管按什么顺序训练，只要你有足够多的数据，Scaling Law 在，这个模型就能训出来。** 模型成功了，人也就成功了。

那为什么说"越往后越省数据"？如果你从零开始训练一个巨物智能，它很容易变成什么样呢？你先要有大量的模拟器数据。而我们的模型是一个 reward hacker，它非常容易从模拟器里找到反馈信号——比如光照的渲染，某个角上的像素点是亮还是不亮，它就能从这拿到 reward。它不能泛化。但如果你的起点是一个基座很大的基模，它既会语言、又会数学、还会写歌写程序，那么在这样的一个好的基础模型上再做空间感知的训练，就不需要那么多数据了。

所以我猜：**你每加一个人类的新领域，需要的数据不是更多，反而是更少。** 这是一件非常恐怖的事情。

#### 当实验室也变成 scale 的一环

所以他们看到的，是数据分布工程上的一个飞轮：只要决定在什么时候、按什么比例给模型注入数据，**架构不重要，算法不重要**。只要训练不崩掉，只要算力和推理是一致的，只要训练时参数不会在推理时莫名改变——这些纯工程性的问题能解决，那么有十倍、一百倍的数据，这个问题就解决了。

用更好的算法、更好的模型结构，当然也会有一定程度的提升。但对他来说，只要这个飞轮还在，只要他有钱，他就可以一直 scale 下去。

```text
        ┌───────────────────────────────────────────────┐
        │                                               │
        ▼                                               │
   发现下一个领域                                  飞轮转起来
  （情感计算 / 化学 / wet lab / 甚至预测老鼠行为）        │
        │                                               │
        ▼                                               │
   在这个领域建立反馈：好 / 不好 / 对 / 错              │
        │                                               │
        ▼                                               │
   优化训练的数据分布与比例                            │
        │                                               │
        ▼                                               │
   以「插件」形式插进基础训练 ─────────────────────────┘

  前提：架构不重要、算法不重要、训练不崩、算力与推理一致
  结果：飞轮 + 钱 = 可以无限 scale 下去
```

我听到消息说 Anthropic 要做一个 wet lab，去做生物工程的实验。那也许生物工程、也许预测老鼠的行为，就成了下一个 scale 的领域：在这个领域上建立反馈，优化训练分布，再把整个领域以插件的形式插进基础训练里，飞轮就转起来了。

这有多恐怖？**他每新建一个实验室，投资几十亿美元，模型能力就往上抬一个台阶。** 这几乎是一个可以预见回报的投资。

对比一下学术界。写一篇 paper 的模式是——我随机想一个 idea，这个有没有用，不知道，然后我去发一篇 paper，接受同行评审。而另一边，头部实验室的人已经不太 care 这些了。他们说，你们在小规模上做的任何实验，对我来说都没有意义，因为我看到的是另一个维度的 Scaling Law。你不在那个体系里，你没有任何资源做这件事，你对这个数据分布一无所知。你就算有一些非常酷的想法，可能你也不需要写 paper——**你只要写一个 blog post 就行。** 他们的 AI 看到你的 blog post，就可以拿到他们的数据上去试一试。

他们有 RSI 的循环（recursive self-improvement，递归自我改进的循环），靠这个 AI 循环就可以去做任何事。一旦这个闭环被探索出来，基本上就接近收敛了。而且在 AI 的帮助下，这个闭环肯定会收敛得很快——因为 AI 比任何一个人类都强。它可以去发现下一个新领域：情感计算？化学？还是别的？我不知道下一个领域是什么。

说实话，我觉得这个体系可能马上就要崩溃了。每个同学都可以想一想：**在崩溃的体系下，我们还能剩下什么？**

我自己也跟 AI 聊了一些，至少下面这些可以当成一个小的、可能很小的领域来做验证：比如在系统架构上训练品位，让它做出好的系统设计。可能到这学期结束，他们突然推出下一版模型，把系统设计加进去了——然后你再去看 AI 生成的代码，就会发现今天我经常在课上笑话的那些事情，永远都不会再发生了。

> **提示**：我经常在课上调侃 AI 生成的代码，说你看它代码写得多糟糕，我 1+1 提个需求它就崩溃了。这类事情可能就永远都不会发生了。这不是玩笑，这是上面这个飞轮的直接推论。

### 斩杀线在往上移，所以我们还是得上课

不管怎么讲，这门课还是要上。

因为你还是不能完全依赖 AI；而且人类是一个竞争性的社会，它和生物的进化很像——**survival of the fittest，适者生存。** 所以斩杀线毫无疑问会不断向上移动。那你要问的就是：我最终怎么样才能逃离这条斩杀线？在最后还没有被斩杀之前，搭上最后一班车。

从人类的角度讲，人类肯定不希望自己消亡。不管是 Anthropic、OpenAI 还是 DeepSeek，他们都希望靠人工智能去推动人类的进步。斩杀线确实会让很多人的生活变得没有意义，但**我们成为更好的人，就可以更好地找到这个意义**。这也是没有办法的事，我们每个人都是这样，包括我。

所以我们还是回到技术上来。

### 意图、规格、实现：中间那道缝

我花了好几次课在讲一件事：我们软件所面临的问题，是 intent、specification、implementation 这三者之间的 gap。

```text
   intent ──gap──> specification ──gap──> implementation

   我想要什么            该怎么把它变成             真正跑起来的
   （需求）               一个可实现的东西           那一行行代码
                        （设计、架构）
```

gap 之所以存在，是因为：

- 客户通常说不清自己要什么；
- 需求会变，中间还夹着大量连提出者自己都没想清楚的 corner case；
- 设计会跑偏，架构总有可以再改进的空间；
- 从设计到代码那一段，还会再漂一次。

**正因为有这个 gap，构造软件才成了一个世纪性的难题，也才有了软件工程。**

上次我们起了个头：如果现在要从零开始构造一个系统，我们需要管理软件，所以我讲了一些版本控制的东西。现在版本管理有了，那接下来——如果我们真的想构造软件，到底应该怎么构造？

我给的答案是：**直接做一个 MVP（Minimum Viable Product），一个最小原型。**

这件事对大家来说非常直观：**我们做得多就错得多，做得少就错得少。** 所以我做一个最少的、但和最终 product 最接近的东西，收益应该是比较大的。

### MVP：做一个最少的、但离产品最近的原型

MVP 为什么划算？因为它能补上 intent、specification、implementation 之间那道 gap：

- 它首先是一片 AI 生成的 slop，所以不怎么花钱；
- 这个 implementation 随时可以扔掉，这不重要；
- 但它能帮我知道：我的 intent 哪里没有弄对？我的 specification（比如架构）还有没有可以改进的空间？
- 然后再做几个版本的迭代。

> **结论**：MVP 的价值不在于它本身，而在于它以最低成本把 intent 和 specification 摊到桌面上，让你在真实可运行的代码上看到 gap 的具体形状。

### 把设备抽象成人愿意用的接口

那天晚上我做了一个东西。所有的代码都是 AI slop——我开着豆包的输入法，开几个终端，然后来回骂，一圈一圈骂过来。

它是一个和物理世界有交互的东西。我有一台标签打印机，之前的各种设备都是用设备自带的软件来用的，而那个软件用起来像吃屎一样。所以我们干脆不要那些软件了——我把所有这些软件都屏蔽掉，**当然，这个屏蔽本身也是 AI 做的。**

这件事里其实有一些软件工程的智慧。我们有一台计算机，总线上连着扫描仪、打印机，各种各样你能想到的东西——这个你们在操作系统课上学过。我上操作系统课的时候，什么是设备驱动？**把一个设备抽象成 read、write、ioctl 的接口。**

那我能不能把它抽象成一个更好用的接口？比如扫描仪，我就是一个 `scan`：我是正面向上还是反面向上？单面还是双面？dpi 是多少？我给他一个更干净的接口。打印机也一样，我的接口就是一个 `print`，一个 `image`。

```text
  真实硬件          厂商驱动层            我们的接口层           应用
 ┌──────────┐    ┌──────────────┐     ┌──────────────┐     ┌──────────┐
 │ 热转印   │    │   read()     │     │ print(image) │     │ 固定资产 │
 │ 标签机   │───>│   write()    │────>│              │────>│ 贴标管理 │
 ├──────────┤    │   ioctl()    │     ├──────────────┤     ├──────────┤
 │ 佳能     │    │ 非标、跨平台 │     │ scan(朝向,   │     │ 资产盘点 │
 │ 扫描仪   │───>│ 驱动成本极高 │────>│  单/双面,    │────>│ 与归档   │
 └──────────┘    └──────────────┘     │  dpi)        │     └──────────┘
                                     └──────────────┘
```

读图说明：**设计和实现在接口层上就完全解开了。** 有了这一层接口，我的软件就可以工作在这个接口层上，而不必关心底下是热转印机、佳能扫描仪还是别的东西。这就是一个非常典型的软件工程里的"设计"。

有了这个抽象，我再也不用去用那些不好用的软件了。这就是个 self-service。

顺便说一个细节。AI 一开始试的是能识别标签内容的路子——它想"看懂"这个码；但后来它自己发现，可以直接用 PCL 的驱动去做 generic 打印，把它当成一台通用打印机来处理，效果反而更好。

还有个更黑的细节。那台照片打印机其实是个非标的东西，就是个杂牌，连它是什么型号都说不清。它里面有一个选项是热转印，就是贴固定资产的那种标签：标签机里有一个碳粉袋，碳粉袋会加热，相当于在有像素的位置加热，把碳粉烫上去。这种打印机有一个参数，大概是加热的程度，也可以理解成图像的深度。我们不知道这个参数是什么意思、应该设成多少。

于是 AI 就开始不停地打标签：先打一张，上面有数字——"15"，意思是第 15 次尝试——然后回来问我：这次是淡了还是浓了？它自己看不到。

```text
   AI 打印第 N 张标签 ──> 上面印着数字 N
          │
          ▼
   回来问：「淡了还是浓了？」
          │
          ▼
   我回答（AI 自己看不见）──> 反馈 ──> 调整热转印深度
          │                                   │
          └───────────────────────────────────┘
                    再打第 N+1 张

   只要把一个摄像头对着标签纸，人就可以完全不参与：
   AI 自己一张一张打，自己判断浓淡，直到搞定
```

这个循环的本质是：**我只问它要一个结果——一个可验收的结果。** 我没有给任何一行代码，也没有监管，它自己一轮一轮地把这个事搞定。前端界面我就是用嘴输出，一句话就开始了。

我特意试的是国产模型，因为正好额度是空的，我就把五个小时额度基本上全部用完。得到的东西看起来相当可用——就跟你在食堂或者宿舍楼下看到的那个自助机器，达到了某种产品级的效果。

> **结论**：所以以后，软件公司可能面临非常彻底的消亡。你想，一台标签打印机，厂商必须给你一个驱动、一个软件，它的开发成本非常高；我那台佳能的扫描仪，软件成本也非常高，要开发跨平台驱动等等。今天这些全都不需要了。

### App 会死，接口不会

再往前推一步。豆包手机也是一个非常好的工程产品，它体现的是同样的软件工程智慧。

它的思路是：那些 app 都不重要了。如果我们有一个 JEFF 这样的模型——它是一个决策，但又接近实时——我觉得 JEFF 和豆包手机真的非常配。它在赌一件事：**模型会在某一个时间点，快到可以和人一样快地操作手机。** 虽然他做豆包手机的时候还做不到，但这一天很快会来。

于是他做的事情其实很简单：**把 app 抽象成各种各样的接口**，然后由 computer use 去调用。我要点外卖，那个 app 就沦为一个"点外卖的接口"；还留下了一个"查询数据"的接口。

所以，app 是不是有一天全都要死掉？**因为它只要提供接口就行了。** app 是给人用的；但只要提供一个 API，就可以给 agent 用了。阿里现在就在疯狂做这件事——把旗下所有服务都整合成 agent，试图用一个千问这样的应用来承接。

> **提示**：千问我觉得有点生不逢时——他太想把这个产品推出来了，而那个时候模型的算力可能也不够，他们自己也没有一个像 JEFF 这样既足够聪明、又足够快的模型来帮你完成各种任务。所以拿出来像一个未来的半成品。但方向不会变：总有一天肯定会来的。

这一下子，整个软件公司就彻底消亡了。你想这条产业链上养活了多少人、多少外包公司。

再回到那个创业的例子。你毕业后想创业，想找一个细分市场：每个学校、每个单位都需要一台这样的标签打印机——不错的市场，几百块钱一台，利润相当可观。硬件上，中国供应链很好，这种成熟硬件你肯定能找到。那就需要软件。而在 AI 之前，软件开发的成本非常高：需要 Windows 的驱动，Windows 驱动完了，还需要 Mac 的驱动，因为现在用 Mac 的人越来越多；他说 Mac 没驱动，他就会抱怨，你的产品就卖不了、卖不好。

**但今天，这些全部直接被 AI 杀死了。**

看那个 `label print` 的界面，我完全没管，全是 AI 自己生成的。它自己 probe 出了打印机的参数，和我现在插进去的这张标签完全定制化。

> **结论**：我想要什么，以我最舒适的方式来帮我定制，不要通用。因为以后生产软件、生产 intelligence 的成本会非常非常低。

### 已经生在软件死掉的时代，为什么还要讲软件工程

你们已经生在这个时代了——已经生在软件死掉了的时代。

那为什么我们还要讲软件工程？因为**曾经的软件工程不是这样的**。你们要透过软件工程的历史，才能理解今天这些东西到底是怎么来的。

顺便说一个下个实验的要求。

我下一个实验会要求大家：**把你第一个实验里的那个 assistant，和一个 physical device 联系起来。** 可以是你的手表，可以是你宿舍里任何一个已有的东西；也可以是你花两百块钱买的一个小设备——它是非标的，可能根本没有 Linux 驱动，但你想把它搞起来。

我办公室里的那个电子墨水瓶就是一个例子。它是一个 Android app 控制，那个 app 极度难用。当然你可以用豆包手机那种 computer use 的方式去用它。

但我做了另一件事：**我用 Claude Opus 4.6，直接把那个 Android app 的 APK 丢进去，让它解包、去逆向那个蓝牙的协议**——因为它毕竟还是一个标准的蓝牙设备——然后从代码里搞清楚它到底是怎么把这个屏写进去的。最后我得到了一个一样的东西。

你们可以借手头的模型来做这样的事。

所以，虽然今天我们生在这个时代，但**软件工程的智慧还是没有消失的**。从今天开始，我会讲一讲你看到的这些软件到底是怎么来的：我们在软件构造的历史当中发明了哪些东西，以及今天怎么用这些理念去和 agent 协作，成为一个更好的 agent-native 的软件开发者。

### 回到 1960：硬件和码农都很贵

先回到 1960 年吧。1960 年有点太早，我们往后退一点。

那个年代，**硬件比码农贵得多**。一台计算机要占一个很大的房间——虽然不至于有一层楼那么高，但确实非常大。而且作为最先进的设备，制造成本也非常高。

那时候的厂家还不敢偷工减料。就像你刚开始造建筑的时候，都是要猛堆料的。

> **提示**：我们对比一下现在。比如 iPhone 18 Pro 据说采用了 QLC 闪存颗粒——好像也没什么关系，因为 iPhone 的主张是：你应该把所有东西都存在 iCloud 上。你的数据坏了，它也就这样，它不会对你的数据负责。保修期内闪存坏了，它给你换一个主板。所以重要的数据应该放到 iCloud 上。

那么码农呢？码农当然也很贵。因为越早，编程的工具越不成熟，码农是一个非常高智力需求的工种。你看《Silicon Valley》那个电视剧——第一季第一集，那个厂区里全是工程师——那个时候仍然是这样的。

那时候写汇编、写机器代码，大家的要求是要画流程图的。你们现在肯定不画流程图了。因为那时候你写的是机器代码，你不画一个流程图，直接写机器代码，是不可想象的。

> **易错点**：今天大模型可以直接吐出二进制序列、直接写汇编，但你做不到——需要过度的预训练才能做到这一点。**工具的成熟度决定了你可以省略多少中间步骤**，这是一条不能违背的规律。

而且各位在 985 大学，是经过层层筛选的高智商人群。你们数学训练得多了以后，多多少少会缺少对客户的同理心、对商业的理解这类软技能——不是说大家就没有，我只是见过很多各方面都很强的"六边形战士"，但我的观察是，在理工科专业里，**这种 nerd 的人会更多一些**。他们可能不 care 业务，只想造世界上最好的操作系统——像 Linux 那样的。他不是一个好的客户经理。

但软件企业依然要承担这样的职责：**把 implementation、specification 和 intent 之间的 gap 补上。**

看公司这一侧。作为一个公司，他要签订合同：客户说，我花一千万美元，你给我开发一个操作系统。这在今天看是个天文数字。而今天 AI 给你报个价，可能只是个零头。

### 客户脑子里的未来，和程序员脑子里的汇编

问题的另一半在客户这一侧：**那个时候，客户也不知道计算机能做什么。**

当然，像 NASA 这样的机构，他们的工程师可能还会有一些概念——比如他们要把人类送上月球；或者是飞机上要做一个飞控系统。但即便如此，他们想的也还是这样的需求，完全不确切。

还有一个时代背景：**程序员是一个非常年轻的职业。** 高德纳（Donald Knuth）1957 年登记结婚的时候要填职业，"程序员"当时还不被承认为一个职业，最后他登记成了"理论物理学家"。

而在那个时候，客户已经对计算机、对软件产生了非常过度的遐想。

我这里有一张 1968 年杂志的截图，是 AI 帮我找的。里面有这样一些设想：终端能及时判分；针对薄弱环节辅导；让学生按自己的节奏学习。

> **提示**：这些东西到今天都没有实现。你们现在还在这里上两节课，每节课 50 分钟。

1968 年 9 月号的《Boys' Life》就已经唱响了这件事情。所以那时候的 gap 越来越大。

一个客户脑子里想的，是软件公司给他画的一个大饼：我要投一千万美元，做一个跨时代的软件系统，他脑子里是那样的东西。而你回到 1968 年，一个程序员脑子里是什么？是汇编，是 `goto`。这个 gap 毫无疑问是非常非常大的。

**正因为有这个 gap**——软件是要实现物理世界需求在信息世界里的投影——软件工程和其他工程才有很大区别。

### 软件为什么和桥梁工程不一样

拿桥梁工程、炼钢这样的工程来对比就很清楚。

|            | 需求从哪来            | 能不能改造            | 演进方式                |
| ---------- | -------------------- | --------------------- | ----------------------- |
| 桥梁 / 炼钢 | 自然界、物理世界     | 只能适应，不能改造   | 模式强，只能小步迭代   |
| 软件        | 拍脑袋想出来的       | 高度定制化、边做边变 | 可能有颠覆性的创新     |

他们（桥梁、炼钢）的需求来自于自然和物理世界，我们只能适应，不能改造。材料的结构、强度有多少，在出厂的时候就已经确定了。楼要盖起来，它要盖几层、要容纳多少人、人有多大——这些都是自然界选择下来的结果，已经决定了的事情。我们只能按照自然规律来，桥就应该做成这样，一代一代迭代，做一些小改进，不断地往上创新。对他们来说，一个彻底推导出来的大改进和创新是非常困难的，所以一直都是比较 incremental 的。

**但软件不一样。软件的需求完全是拍脑袋想出来的。** 1968 年的时候就能想出那种东西。需求是高度定制化的，把它投影到计算机世界里，也一直被认为是一个高度需要人类智慧的活动。

我们一直说"软件是人类智慧的巅峰"，这确实是个事实。你看操作系统、编译器这些非常难的软件，你去学它都需要多年的专业积累，它很复杂。

复杂到什么程度？复杂到**连制定 specification 的人自己都没有想好各种各样的 corner case 应该怎么样。**

举个我们自己的例子。你想做一个选课系统——

- 选课系统到底应该是先到先得，还是抽签，还是按专业保留？
- 不满足先修课要求的时候，老师能不能特批？

这些都很难在需求阶段就答清楚。再往下具体一点：你要选修操作系统，必须先修计算机系统基础——你们在系统里都能看到这条。那就糟糕了，这是个问题：**这是一个硬的限制，还是一个软的限制？谁能 override？** 最后你到毕业前一秒钟、差这门课毕不了业的时候，学校所有的口子都能给你开——那这就是一个例外性的需求。

所以软件的需求是高度定制化的、非常复杂的，它连接了物理世界、连接了社会、连接了人的偏好。

所以做软件很难。

### 软件危机：进度、成本、质量一起失控

在那个时候，大家就发现：**进度、成本、质量是一起失控的。** 开发进度不能预测，软件开发的成本会崩溃，而且要延期交付。

#### go to considered harmful，可 Linux 内核里全是 goto

那个时候，其实搞计算机科学的科学家已经观察到了各种各样软件里的有趣的东西。

Dijkstra 是图灵奖得主，他最有名的文章之一叫 "Go To Statement Considered Harmful"。这个你们在学编程的时候都学过：因为大量的 goto 会让程序变得很难理解。

但你们同时也看到了：**Linux 内核里有好多 goto。**

这是 C 语言里为数不多的几个比较 idiomatic 的用法之一：你最后有一个 `goto release`，在 release 的地方逐个检查你在函数里申请的所有资源，一一释放。这样就可以保证——你在中间任何时候要申请一个资源，你都在 release 的地方加一个释放检查和释放；而你在写代码的时候，永远不能在中途退出，中途想要退出的时候必须 `goto release`。那这个程序基本上就能正确了。

| `goto` 的用法                 | 评价                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| 随意跳转、层层嵌套           | 让程序不可读。Dijkstra 反对的就是这种                       |
| 集中到 `goto release` 统一释放 | C 里为数不多的 idiomatic 用法，解决"随时申请、从不释放"   |

> **易错点**：Dijkstra 讨论的其实不是"goto 到底 harmful 不 harmful"。作为一个正确机制使用、只允许你这样用的话，goto 就不 harmful，它挺好的——它解决了 C 语言里"随时申请、从不释放"的问题，也就是你们做 OJ 时留下的那个坏习惯。

他还说过一句很有名的暴论：**程序员水平随着 goto 的密度上升而下降。** 这句话不绝对，背后是有一定道理的。各种结构化编程的教科书会告诉你应该怎么用 goto。

他背后真正希望的是：**你能写出人能读的代码。** 只有人能读，它才有可能维护得下去；维护得下去，OK，让这个世界还能相对正常一点地去运转。

#### The Humble Programmer：为什么永远会有软件危机

1972 年，就是 Dijkstra 拿到图灵奖之后的那次演讲，叫 "The Humble Programmer"。这个原始文稿现在完全可以直接去读，我们可以在 AI 的帮助下直接阅读它。

他谈到了为什么会有软件危机。

我觉得他讲得非常好：**如果你永远只写 OJ 那种小程序，就不会有软件危机的。** 算完就完了，你一旦把这个程序调对，就永远不需要去维护它。

但是机器变强以后，你的软件需求是不断膨胀的。你机器越强，承担的现实世界的 intent 就越多；intent 越多，不确定性就越多；然后实现就会变得越来越复杂。越来越复杂之后，应该怎么样？他提了一些他对软件的思考，其中一个是 **nicely factored solutions**——良好的分解。

我们在构造任何软件系统的时候都在不断地发现这一点。比如我写的那点驱动标签打印机和扫描仪的小东西，它也是一个 nicely factored solution，一个良好的分解。我们无时不刻都在用这样的想法来组织我们的软件。

他还有一些有意思的观点：**保守力量主要来自教育机构，和舍不得重写旧程序的用户。** 这放到今天，依然是让你觉得醍醐灌顶的。

### 软件工程出生在 1968

我觉得大概就在 1972 年前后那个时期，软件工程就成为了大家关注的一个焦点——**因为软件开始失败了。**

1968 年，有一个 NATO 的软件工程会议。差不多在同一时期，Hamilton 和他的团队提出了"软件工程"这样一个概念。

这个帖子里有一张非常有标志性的照片，我觉得是载入史册的那种：1969 年阿波罗计划的源代码。

```text
  1969 年 7 月 —— 阿波罗 11 号

  经过不懈的排查错误，
  这位最初的软件工程师把宇航员送上了月球。

  〔这位软件工程师有传记〕
  他就是那个坚持写 specification、强调防御性编程的人。
```

看这段摘要，意思很清楚：**1969 年 7 月，经过不懈的排查错误，这位最初的软件工程师把宇航员送上了月球。**

你们今天学 SICP 的时候，第一节就会告诉你：写软件要写 specification、要做防御性编程。他把一个绝对不能发生的假设都当成可能——一种为未来思考的防御性智慧。他假设这个软件在任何时候，哪怕违背了假设，这个软件依然要能够工作，他才算设计了一个成功的软件。

这就是软件工程的起点：让软件能工作，**还包括发生意外的时候它也能工作。**

你再往下看一层：假设硬件也是不可靠的，无论如何都要在这个软件里做一个兜底机制；程序 crash 了以后，整个系统依然要能够工作。

阿波罗 11 号登月下降的时候，舱内发生过警报。但因为这个软件有优先级和 recovery 机制，关键的下降控制任务得以继续。那个时候还没有"软件工程"这个学科，他们就是从 first principle 去思考：**如果我们这个时候要构造一个真正好的、高质量的软件，我们应该怎么做？** 它的 first principle 就是那句话——**the never going to happen can happen**，绝不可能发生的事也可能发生。

> **提示**：我们今天完全可以反过来读这些原始材料。回头去看这些原作，你会发现这些思想在今天反而更容易理解——比教科书上经过一手、二手、三手、四手消化之后要清楚得多。

### 在成本和时间的约束下，把意图变成能活着的软件

软件工程就在那个差不多时间点、在成本、时间、团队等各种约束下交付软件已经成为巨大挑战的时候，诞生了。

那"怎么做这件事"就是软件工程。把它讲清楚就是：

> **定义**：软件工程是——在成本和时间的约束下，把人的意图（你要设计的产品，或者是客户的要求），变成一个**可以工作、可以维护、可以生存**的软件。
>
> "可以生存"的意思是：你随着时间的推演，需求可能会变化。

这个 "never going to happen can happen" 的感觉，是不是很熟悉？回到我们做 OJ 的时候。

> **易错点**：你写 OJ 的时候，隐藏了一个假设：**你假设题目是对的，你假设题目是能做出来的。** 这个假设本身就不对。当你反复强化它，你就是在 overfit 这个假设。
>
> 你应该假设的是：**你面对的是一个开放的世界。** 这个题目可能是错的，这个题目的条件随时可能会变化，这个题目甚至可能变成另外一个题目。那你怎么做一个软件来解决它？

当然，编程是一件事。通过训练 OJ，训练的是你的逻辑思维、算法思维、你的问题求解能力。这些对于设计软件、真正理解这些东西是有好处的。

Dijkstra 有一句话，是把"工程"定义成：**a systematic, disciplined, qualified approach to the development, operation and maintenance of software**——应用于软件的开发、运行与维护的系统化、有纪律、合格的方法。这就是**工程化**：它把软件变成了一个"不再依赖个人英雄主义"的东西。

在 Hamilton 的那个时代，造一个软件需要一个好的 leader；换一个人，这个项目就失败了。

而后来，它变成了**你可以拿到一个 checklist**：如果 1、2、3 到 10 全部都满足了，你不能保证这个软件一定成功，但**失败的概率会小很多**。

> **结论**：这就是软件工程这门学科的方法论内核——**有纪律、可量化、覆盖整个软件的生命周期。** 它不承诺成功，它承诺降低失败概率。

而这个学科，是从大量失败中来的，是从数十亿美金的教训里来的——什么炸一个火箭这种。

### 本讲提到的题目

我下一个实验会要求大家：**把你第一个实验里的那个 assistant，和一个 physical device 联系起来。**

题面里可选的设备：你的手表；你宿舍里任何一个已有的东西；或者你花两百块钱买一个小设备——它是非标的，可能没有 Linux 驱动，但你想把它搞起来。

**做法与依据（都能在正文里找到出处）：**

- 抽象是第一位的。那个标签打印机 + 扫描仪的例子就是标准答案的样子：不要去驱动非标的硬件，而是**把设备抽象成人愿意用的接口**（`print(image)`、`scan(朝向, 单/双面, dpi)`），让设计和实现在接口层上解耦。
- 驱动难搞的时候，可以让 AI 去逆向协议。办公室那个电子墨水瓶就是一个 Android app 控制的设备——把 APK 丢给模型，让它解包、逆向蓝牙协议，从代码里搞清楚它是怎么把内容写进那块屏的。
- 目标形态是**可验收的结果**：不是给你写死一行代码，也不是我坐在旁边盯着。它自己 probe 参数、自己迭代，直到我能验收。热转印那个"第 15 次尝试，浓了还是淡了"的循环，接一个摄像头就可以完全自动。
- 前端就用嘴输出。豆包输入法 + 几个终端 + 来回骂，是完全可行的工作流。

## 从一篇批判瀑布的论文开始：软件工程的来龙去脉
> 对应块：BLK10 | 覆盖分集：P06下 | 块标题（分集名）：《软件工程的来龙去脉 [05-Raw_26生成式软》

### 一个 leader 不会说“大家去干吧”

先从一个画面说起：一枚火箭炸了。

你会去看残骸、读日志、复盘事故——**炸一次也好，成功也好，失败也好，积累下来的都是智慧**。很多时候，一枚火箭为什么炸掉，跟软件工程是直接相关的。而软件工程里绝大多数有用的东西，都是这么攒出来的：某次事故复盘出来的原则，某次延期复盘出来的教训。

再回到还没有今天这些工具的年代，你心里其实一直很清楚一件事：`intent`、`spec`、`implementation` 之间，是有 gap 的。

那接一个开发任务，第一个动作就不是“开工”。你不能说“哎，大家去干吧”——**任何一个 leader 都不应该干这样的事儿**。为什么？因为不同的人看到的不是同一部分东西；软件一旦要拆开，leader 就必须指派：哪一部分由谁来做。

我自己做打印机和扫描仪那两件小事的时候就是这样：两份活同时接到手上了，那我干脆起了两个 agent、开了两个窗口，一个只管打印机，一个只管扫描仪。**这很很正常，需要的是一个划分任务的过程，而不是 self-organized。**

那如果我们真的涉及划分任务，从一个空的 repo 开始，第一步到底该干什么？是不是直接开发，把那一句话需求丢给它做一个 MVP？

你想，1970 年，软件工程刚刚诞生，**那时候还没有 minimum viable product，也没有大语言模型**。那么第一个认真思考“怎么按时、不超预算地交付一个大型软件”的问题的人，就写出了一篇软件工程领域的开山之作——Winston Royce 的《Managing the Development of Large Software Systems》。

### 那张瀑布图，出自一篇批判瀑布的论文

但这里有一个特别反直觉的事实：**软件工程课上人人学的瀑布模型，那张图就出自这篇论文——而这篇论文本身，是在批判瀑布模型的。**

这就是“知识有损压缩”的经典案例。一个东西被层层转述、被反复消化之后，到你手上的版本，可能早就不是原来那个东西了。所以当有人告诉你“软件工程就是学瀑布模型”的时候，你还得回原文去看。

> **易错点**：瀑布模型这个名字、以及教科书里那张从上到下的流水线图，来源都是 Royce 这篇文章；但 Royce 提出的不是“照着这个流程干”，而是“照着这个流程干一定会出问题”。原文和二手转述之间，隔着一次可观的失真。

顺便说说我的读法——和你们读文章的方式有些不一样。昨天备课我要这篇文章，就直接找到链接，跟我的 agent 说“把这个 paper 入库”，它给我一份文字整理版，图片全都以 markdown 嵌进来。我自己有个命令行的工具，能在终端里像 `less` 那样读论文，也能打印文本、抽图片。就这样，一个 700 页量级的东西，让一个很便宜的小模型读完，前后没花多少时间。

然后我就问它一个很具体的问题：**“给我解释一下，瀑布模型在软件工程里到底是怎么被误读的。”**

它的解释还挺 make sense——它把“教科书 → 逐级复述 → 曲解”这整条误读链给我捋了出来，最后告诉我：几乎每一个新方法出来都拿瀑布当靶子，称它是“史上最好用的反派”。它说得对：**这个反派本身就是个被误读的东西，而 1970 年那篇文章早就在告诉你不能瀑布。** 当然你也可以选择不相信 AI，再去追问它几轮，或者换一个联网的模型再问一遍。

而 1970 年的人为什么会去批判瀑布？因为在那个时代，大家真的什么也没有，**只能从 first principle 去思考**。

### 为什么会失败：测试是整条链上第一个物理事件

你站在今天做软件的这个位置上回头看，会发现这篇论文的推理你几乎能一行行对上：需求 → 系统设计 → 编码 → 测试 → 上线，流程和你今天做的完全一样，因为不管你用什么版本控制工具，你都是从一个空项目开始，先想清楚要干什么，再想想大概该怎么做，然后才去写代码——**不管写代码的是软件工程师还是 AI，这个流程都成立。**

而它失败的原因，可以用一句话讲透：**测试是整条链上第一个物理事件。**

在设计的时候，你有的是报告和文档；在程序真正被写出来之前，它是不能运行的。这是一个 first principle。**而凡是“不能运行”的东西，人都是随便做做的。** 文档就是文档——你让我写文档，我就写一个，写完放在那；代码改了，设计改了，文档不跟着改，就那么不一致地摆在那儿。

```text
   requirements          ->  a document, not runnable
        |
   system design         ->  a document, not runnable
        |
   coding                ->  source code, still not runnable
        |
   testing               ->  THE PROGRAM ACTUALLY RUNS
        |                   the first physical reality of the system
        |
   operation
        |
        +-- any drift between intent / spec / design / code
        |    becomes visible ONLY here
        |
        v
   you must go back and rewrite everything upstream
        |
        v
   schedule blown, budget blown
```

你们写实验文档的时候，对它的正确性有 guarantee 吗？当然认真点的同学会说我有一个 best effort guarantee，但实际上你真的没有 guarantee。

而只有到了测试这一步，程序才真正跑起来，你才真正知道它的行为是什么。编码的时候你可能已经隐约觉得有点不对了，但**一旦 `intent` 到 `spec` 到 `implementation` 之间已经发生了漂移，到测试才发现，就意味着你要回头去改前面**——这个回头修改带来的成本，就是超期或者超支的源头。

不过也不是所有程序都这样。Royce 自己给过一个边界：**程序小到一个人当场就能写完、并且当场就能测完，那两步就够了。** 你们想想，这说的不就是你们的 online judge 吗——题面就是 spec，代码写完立刻能跑，你根本不需要先把文档做两遍。

### Doing it twice：把发现问题的时刻整体前移

既然风险最终都在测试这一步爆炸，那么**所有补救的本质，都是把发现问题的时间点往前挪**。

于是有一个非常自然的想法：设计先行，文档做两遍——**Doing it twice**。他在文章里管这个叫 preliminary pilot program：先做一个不完备、但能够体现这个系统功能的设计；这个东西可能会失败，**但它迭代的成本会变得很低**，失败了就可以 reflect 回系统的设计本身。

> **定义**：preliminary pilot program——先造一个不完备但能体现系统功能的东西，让它以很低的迭代成本失败，从而把失败**提前**到设计阶段。这不就是 minimum viable product 吗。

而这条 first principle 到今天都还活着：**缺陷被发现的时间越晚，返工代价就越大。** 你们做 OJ 一定有过这种经验：一开始脑子一热，想了一个算法，觉得不对也先写代码；代码写完一跑样例，发现不对；你对着样例回头一算——完了，整个算法从根上就是错的。这就是一次典型的瀑布式失败。

那在 TDD（test driven development，测试驱动开发）的意义上该怎么办？**设计先行，你就干脆先把测试用例定好**：输入是什么、应该经历什么流程、输出什么——定完之后你马上就能对。

敏捷也是同一件事。你不需要把 pilot 理解成一个完整的流水线，而是这样：**你的第一个版本不是 doing it twice，你是 doing it infinite many times。** 第一个版本哪怕只有一个 hello world，只打印一句 hello；或者每个模块都自报一下家门，能把这个模块串起来——**这也是一个好的 product。** 然后就在这个意义上，不断地把软件往后演进。

```text
   layer 1:   intent -> one thin slice of features  -> RUN    (a "hello world" product)
   layer 2:   intent -> a few more features          -> RUN
   layer 3:   ...                                      -> RUN
                              |
                              +-- every layer runs, so every layer hands you evidence
                                  right where your assumptions live
```

一句话：**让关键假设尽早遇到证据。** 一开始你不确定的东西，因为你有一个原型了，就可以立刻验证它。

所以我们今天做的这些事，**并不完全颠覆过去的经验**：今天正确的 practice 可以映射回过去，过去正确的 first principle 也可以用来映射今天。

我很喜欢那些图灵奖的工作，它为什么能得奖？就是在大家完全不知道的情况下，**确立了一个 first principle，并告诉大家这件事应该这么做**。更好玩的是，你有一天会发现他一开始有个地方方向想错了，然后把全人类都带歪了；**但如果全人类能从某一点换到另一个方向，那全人类也许会立即快速走上正确的道路**——直流电和交流电，爱迪生和特斯拉。

我们这些年越来越看重一件事：**每个人都可以直接读到一手信息。** 你可以回到历史的背景里去，而 AI 既知道过去又知道现在，你还手上有原文。**有些东西你在书上是真的读不懂的**——一本书里两页纸讲瀑布模型，你读了两遍还没搞懂；回去看原文，一下就看懂了。

为什么过去非得经过教材？因为**过去要查证一个知识网络，几乎是不可能的事**：得去图书馆翻大量资料，索引机制建得也不好，想找到那份精确的资料要花掉无穷多的时间。所以那时候你**不可能通过一手资料来学习**，必须经过教科书做一次知识的有损压缩。写得好的教材会共情读者：作者读过一手信息，也知道读者会在哪儿卡住，所以这一层压缩对读者的损失很小。

但今天，其中一部分东西**不需要了**。我不需要再做压缩——**我做压缩对每个人都是有损的，而且对不同的人，损失掉的是不同的部分。** 一对一教学我就能做最合适的压缩；现在你可以直接对你的 agent 讲：我不需要它替我总结，我只要它把知识的脉络拆开，**把知识拆成一个一个的发现点**，你把这个点和它的原文拿给我，我做一个属于我自己的压缩就够了。

这背后是一个很值得思考的现实：一个领域可能投入了几百万、几千万甚至上亿人民币，去建设一批很先进的课程，**但最后就是一个模型，把你的轮子碾掉了。** 你有任何问题都可以直接问他。比如“你给我解释一下，瀑布模型在软件工程里到底是怎么被误读的”——你一产生疑问，就直接跟他对话，他可以在这个过程里找到更多原文，甚至把整条误读链给你找出来。

AI 来的时候我们很焦虑，但今天人类还有一种傲慢：我们希望理解 AI 到底做了什么，能够判断 AI 做得对不对。真到那一天，AI 做出来的东西全都远超人类、全都是对的、只有人会犯错……那我们干脆就放弃理解它吧。**但至少在今天——AI 的能力在增长，而能理解 AI 的人能活下来。** 站在这条不断上移的线上，你就知道自己该怎么用好 AI，也知道怎么从它里面挖出真正值钱的软件工程智慧。

### 我把这套模型翻译成一张 data dependency 图

那我是怎么理解 Royce 那个 pilot model 的？因为我是一个 computer science 的人，我往前走一点、往深一点——我做过一点 PL，也做过操作系统，所以我很自然会用 CS 里的概念去解释这个世界：**我把 Royce 的这个模型理解成一种 data dependency——修改是有代价的。**

具体一点。瀑布的每个阶段——需求分析、系统设计、系统实现、测试验证、交付维护——**每一个都可以想象成一个 program。**

而人呢？**我把人想象成程序。** 人脑就是神经网络，我会做 chain of thought；我先学会了语言、学会了说话，哪怕我不说话，我思考的时候还是会对齐到语言上：“OK，我要这样”“那样会有什么后果”。所以在这一点上，**人和程序是等价的**。

这样一来，所有阶段产出的 program 和 artifact，它们之间的关系就是一张 **data dependency graph，是一个有向无环图（DAG）**。展开一点：我的需求里有好几个点，这些点之间可能有关联，也可能没有关系；我做的设计关联到其中某些需求点；设计之间又有关联；**而且关联关系是会传递的。**

```text
   intent               R1     R2       R3
                        |      |        |
   spec                 D1     D2       D3
                        |      |        |
   design               D1     D2       D3
                        |      |        |
   implementation       C1     C2       C3
                        |      |        |
   test                 T1     T2       T3   <-- the bug shows up HERE
                        |      |        |
                        v      v        v
             everything that depends on it must be rebuilt
```

读图要点：一旦你发现 `test` 错了，往上追溯发现是某个 `design` 错了——**那就惨了，所有依赖它的东西全部都毁掉了。** 这就解释了为什么 cost 会这么高，也解释了为什么这条链上的每一步都要小心。

> **提示**：这也是为什么“把一件事做完再做下一件”在软件上格外昂贵。文档、需求、设计这些看起来互不相干的东西，本质上是一条依赖链上的节点，它们不是邻居，是祖孙。

那怎么办？很自然的一件事：**把它割小。MVP 就来了。** 我们不要一次性产生大量依赖，而是**用 breadth-first search 的方式构建软件**：先做第一层，再做第二层，再做第三层——把那些重要的、优先级最高的 dependency 流程先走通；走通了以后，再不断向右扩展，一个一个迭代。

**这不就是敏捷开发吗。**

回到我们今天这个模型本身：`intent` → `spec` → `implementation` 这条链上，每一段的内部其实都有 gap。需求阶段要把 `intent` 确定下来；设计阶段把 `spec` 基本确定（当然，`spec` 在需求阶段也会被做掉一点）；编码和测试的时候，才是 `implementation`。**而 gap 的含义就是：每一个 intent 都会拆成好多个小点，并且会对后面产生 dependency。**

既然如此，**做 MVP、做敏捷开发、做 TDD，显然是一件正确的事情**——它不是一个“也可以试试”的风格偏好，而是从 first principle 推出来的必然结论。

> **结论**：越是后来的人，越容易把这些东西当成几种互相竞争的“流派”来挑。回到 1970 年那句话就清楚了：它们都是同一件事——**把发现问题的时间点往前挪**——的不同投影。

这也让我更愿意读经典著作。**经典里记录的，往往是一个领域最初遇到的、也是最重要的那个根本性问题，然后他在方向上找到一个出路。** 即便事后我可以援引别的概念把它解释得更好——比如我就很喜欢 data dependency，沿着这个方向我可以在软件工程的发展史上导出更多概念——也不妨碍当初那篇文章的价值。

而且我相信，**每一个人对这个模型的理解都可以是不一样的**。我用的是 CS 里习得的概念去解释它，做过一点 PL 和操作系统的人，可能用的是另一套词。为什么我们非常需要个性化的教学？因为每个人的 diversity 不同，成长经历不同。我用我自己的语言解释这个世界，我觉得是自洽的——**而这基本就是软件工程后来真正采用的那种形式化方式，这也是同一个 first principle。**

### 每个阶段都长出了自己的方法与工具

经过几十年，**软件工程变成了什么呢？为了解决这里的问题，它为每一个阶段都创建了方法和工具。** 这些方法和工具不能消灭风险，但可以减少你返工的概率。

先说 checklist。设计阶段应该有一个 checklist，这应该是 ISO 标准的——不过我对这个标准的印象已经不深了，我也不是做这个方向的。你们上软件工程课，会被要求写一份文档，后面跟一个非常长的 checklist：这个有没有做到，那个有没有做到，有没有沟通过……你是一个做 OJ 题的人，你觉得这就是 nonsense。

但 checklist 实际上是有用的，它减少了返工的概率。比如这个长长的清单最后总有一条：**你是不是和客户最后沟通过了？** 上学的时候你会觉得这一条很讨厌；可当你真的和客户沟通过了，并且给他打上勾，你实际上大幅减少了 `intent` 不符合客户要求的概率。

**这就是一种方法，也是一种工具——一个有人文关怀的工具，它没有任何代码。**

研究这边就更有意思了。今天做软件工程研究，更多时候是在**有了代码以后**：能不能做自动的测试？（无穷多的灌水的 paper）；代码里有没有 bad smell？

bad smell 你们都知道。比如你看到一段代码，它在等号左右从来不写空格，你会认为这是不好的代码。**这个规定在 AI 时代之前都成立。** 但我发现，当模型学会省 token 以后，这件事情变了：它会写出极为难以理解的代码，把很多语句都放到一行里——**然后那个代码就是对的。我不知道他是怎么弄对的，但反正它是对的。** 也许我们永远都不应该去读那样的代码。

再比如研究生选题。你要在软件工程方向读研，你大概率会落在那个非常小的一点上：软件开发流程里、编码这个过程中，Java 代码的某一种类型的 bad smell 的更好的检测。

> **提示**：**你在做深的过程中，不要忘记去看那片树林。** 深度和广度都是必要的——你在深度里面训练，才会有更长的思维链；你在广度里面训练，才会有对整个世界的感觉。

然后是团队视角，因为**人的能力是有限的**。我们上大学学软件工程，总觉得自己要变成世界上最厉害的码农，这个那就够了，我能在软件企业里找到一份很好的工作——这是社会给你的 contract。但从**完成一项任务**的角度看（资本家就是这么算的），更重要的结论是：**没有一个码农能够单独完成他的项目。** 码农有好有坏，我得花多少钱、雇多少码农，最终能不能把我的项目交付出去。

所以你现在看，**每个人其实都在当产品经理**，第一门课就该学做产品。而你接下来要做的是**调动**。假设你手上有好多码农，而且现在马上就有了——**DeepSeek 我觉得绝对算是一个相当资深的码农了，绝对不是本科毕业生级别的**——那你马上就有了 2500 并发的码农。

你打算怎么管？你刚刚高考完的那个时候，做梦都没想过：**接受了高考的训练以后，你马上就能管 2500 个人。** 这个 mindset 可能要改一改。

### 形式化程度要一级一级往上加

还有一件特别有意思的事：**软件工程为了在每一个阶段都有方法学和工具，就必须在不同的阶段用不同的语言。**

我们从一个具体的 gap 说起。checklist 那个年代——尤其是在大语言模型之前——你不太可能用一个编程语言去做一份 checklist。那时候的 checklist 就是一个 docx 文档，你把它打印出来、存档；跟客户沟通的记录，你可能是手写的。然后到了编程阶段，你又有编程语言了。**中间就出现了一个 gap**：那时候没有大语言模型这种万能的编译器，你不能只要一段自然语言，就把它编译成任何一种语言。

设计阶段也一样——我们没有一个语言来帮我们做设计。1970 年做设计，大家用的都是自然语言，就是一份设计文档。我记得我学软件工程的时候也是这样：先写需求文档，需求文档写完写设计文档，follow 瀑布模型。

那文档最大的缺点是什么？**写文档的人人会产生幻觉，人和人之间讲同一件事，是无法对齐的。** 这件事情在你和室友之间已经发生过无数次了：你说的是这个，室友理解成那个，你花很多时间跟他沟通、对齐。（当然，我觉得跟女朋友对齐会比跟室友对齐更困难——这个不重要。）

那怎么办？如果你想从 first principle 出发，为设计阶段创建一个方法、创建一个工具，来减少返工的概率，你要做的是什么？

**你要做一个介于自然语言和编程语言之间的设计语言**，当然它也就是一个 domain specific language。

说到这儿，你们是不是想到软工课上讲的那些东西了？**checklist 就是。** 它虽然写的是自然语言，但它其实也是一种中间语言：它有格式的规范，要求你一条一条地列，**每一条必须打勾或者打叉**。它已经介于自然和形式化之间了，它是有语义的——这个语义当然还是由人来检查的，但**对于“勾”和“叉”的对齐，比我直接写一份文档要对齐得更 formal 一点。**

> **定义**：**formal 的程度，就是它具有确定性语义的程度。** 一个表达里，语义越确定、解释越唯一，它就越 formal。

所以整条链上，**从设计的阶段到下面，是越来越 formal 的**。而这正好迎合了从 `intent` 到 `spec` 到 `implementation` 之间那个 gap 的解决。走到这一步，你就开始真正理解软件工程这个学科了。

| 阶段 | 当时在用的语言 | 靠什么保证 |
| --- | --- | --- |
| 需求 | 自然语言需求文档 | 人 |
| 评审 | checklist、决策表、决策树 | 人按条目逐条打勾或打叉 |
| 设计 | 设计文档，进而是设计语言（DSL） | 人 + 格式约束 |
| 验证 | 有逻辑公式的语言（可以不含代码） | 工具判定逻辑是否成立 |
| 实现 | 编程语言 | 编译器、测试，直至证明 |

还不止 checklist。还有决策表、决策树。最好玩的一个例子是：有个同学觉得自己是个理科生，在软件学院上了一门文科味的课，他拿到一份 checklist，上面写着**只有当所有的勾都打上了，你才能进入下一个阶段**——这是什么？这对我来说是 nonsense。但正是这种形式的语义，**避免了遗漏和矛盾**。它甚至会有条目要求你**把所有文档两两摆在一起审查一遍**。你心想“我靠，我才不想做这个事儿，我是写程序的”——但就是这样的两两对查，避免了 gap 的漂移。

这些都是智慧。不过你也要知道，**这套东西是失败之后、在管理团队的过程中一点点逼出来的管理学经验**。软工人当然可以学它，只是别把它当成不可动摇的公理。

那我们学的时候是怎么学的？是 **bottom-up：先学编程**。因为你看，计算机、软件工程，你的第一件事是先学怎么做一个码农——**你不理解代码，就没有办法理解整个过程。**

但是 AI 来了以后，我觉得变了：**你可以先从产品经理开始做。** 如果我给自己的 computer science 课程改一改，**第一个学期就可以学做产品**。反正后面所有的事情最后都要落到代码上，你不去控制它的质量，你也不需要知道——因为你根本不理解代码、不理解后面是怎么运作的，**但你依然可以设计出好的产品。只要你有好的想法，就可以做。**

（讲到这里我脑子卡壳了一下，“product”这个词我要愣一下才说得出来，我上年纪了。反正不重要。）

### 属性、追踪与契约：让人也能检查的东西

测试领域也有非常经典的工作。**QuickCheck** 大概可以算我们整个测试领域的开山鼻祖之一：让人描述性质（property），由工具生成输入、寻找反例。

这背后是一个很朴素的逻辑：**你做任何事都会错，从上到下的翻译都会错。** 你从 specification 翻译到代码，尤其要注意那些**隐含的 specification**——你的程序不能 crash，不要有 null pointer，资源不能泄露。这些藏在代码里的、没有写出来的 spec，你也得遵守。

那有没有可能，我在代码里面就写一个 property，让它自动变成好多好多测试用例；如果这些全部都通过了，我对我的代码就有更大的信心。你现在做的软件就是这样：**你写一份代码，永远不知道它对不对；但如果你做了测试、观察过它的结果，你对它的信心就会大一点。** 独立做的质量保障越多，你对它的信心越大——除非你最终写出了一个形式化的证明。

再比如需求追踪矩阵。我前面上课的时候讲过一个概念叫 **TRACEABILITY**，这在软件里是一个很重要的概念。它做的是什么呢？**它就是把那张 data dependency graph 显式地画出来。**

以前是没有这个东西的。从文件系统或者项目的角度看，一个软件就是一堆文件：`docs` 底下的什么什么 `.md`，`src` 底下一个什么什么 `.ts`，还有一个 `README`。**文件系统一开始是大家用了之后不得不做的一个 work-around**——但恰恰是这个 work-around，承载了整个软件。

而 traceability 要求你用链接、用文档、用某种方式，让**每一个代码和每一个需求点都能对得上，需求和需求之间也能对得上，需求和设计之间也能对得上**。如果所有这些都能对得上，你就获得了一种独立的、互相的交叉检验，对软件的质量就更有信心。

还有一个是**面向契约的编程（design by contract）**。这里有篇文章我就不打开了：Eiffel 这个语言，大概是 1986 年左右，它说，**我要把 Hoare 三元组直接写到代码里。** 你看这样一段上古语法就知道了——

```text
function 取款(金额)
    Function is ...        -- natural language: what this function is for
    require  ...           -- precondition
    do       ...           -- the implementation
    ensure  ...            -- postcondition: what is guaranteed afterwards
end
```

（Eiffel 里变量后面跟一个冒号这条线，后来很多语言也都走了。）

它鼓励你**先不要急着写控制流**，而是把各个模块的 precondition 和 postcondition 先写出来。比如你写一个账户取款，在写前置条件和后置条件的时候，就会自然地去关联你的设计：**余额不足，到底应该怎么处理？**

而写第一个 MVP 的时候，你一定不会管这些事——你可能就是直接让它 crash，或者干脆假设这件事永远都不会发生，**排除在你的 specification space 之外**。但当你的软件不断向后演进，OK，你的这个 contract 就变得非常重要了。这就是他想在编程语言里引入的东西。

### 在 spec 上横跳：从自然语言到编程语言

你看到这么多年软工人做的事情了吗？**就是在这个 spec 上面横跳。**

从自然语言，到几个半自然的语言（可以接纳设计），到有一些逻辑公式的语言（它可以没有代码，单纯地检验这个逻辑能不能成立——比如我这个函数调用，这个逻辑能不能成立），再到现在的编程语言。

**而到今天，它依然是一个非常活跃的方向。**

### 梦想：把 assert 变成编译期的一道证明

而我觉得，软件工程未来会发生很大的变化，因为 **LLM 来了**。自然语言对不齐的问题解决了，checklist 不好检查的问题也解决了。**我们只剩下这个 gap**——只有是“我没有想清楚”“我没有说清楚”；一旦我想清楚了、说清楚了，可能真的就都能解决了。

现在已经有像 **Dafny**、**Verus** 这样的形式化验证工具了。大家的梦想是：我如果写一个这样的程序，我可以自动地证明——**我的函数在前置条件满足的时候，后置条件就一定满足**，无论我写什么都能证明；而且我还要证明整个系统：把所有函数的前置条件、后置条件连起来，它就能够满足我的 intent。

这个梦我其实很早就预言过。**在 ChatGPT 出来之前**，我上操作系统课的时候就预言过：**30 年以后**——那大概是 2020 年左右，或者说 2022 年左右——那时候如果你一个程序里有个 assert，而且这个 assert 是随便你写的、也可以写成和业务逻辑相关的东西：比如我的函数要满足“这个 linked list 往左走再往后走，或者往后走再往前走，总之能回到自己”——那么**只要你把这个 assert 写出来，它能被证明；它不能被证明，或者说这个东西根本无法被证明，这个程序就不能编译。编译百分之百保证这件事。**

那样的话，代码开发这一段的 gap，我还需要 property-based test 吗？**我不需要。我只要把这个 property 直接写进去，让它帮我证明了就可以了。**

而从现在来看，**可能不需要 30 年**——从那个时间点算起，10 年或者 15 年大概就可以解决了。

### UML：一个想把“说不清”对齐的野心

在这个过程当中，有一个集大成者叫 **UML**，Unified Modeling Language——你们绕不过去的一个名字。

它的想法也很简单：既然这个世界这么复杂，在不同的层次上就要用不同的语言——实现的时候是 C 或者 Java，设计的时候有一些专门用来做设计的领域语言，做需求的时候又是另一种——**那我们能不能有一种中间语言，统一整个面向对象的世界？** 他要做的是一个非常有野心的事情：**对齐。**

而这件事，人类其实是天生做不好的。因为人类靠自然语言，而**自然语言是直接连接大脑的 latent space 的**。我跟你说“我今天看到一个美女”，你们每一个人的 latent space 里都构造了一个美女，但都不一样。要是你要求我们把这个形象用 Blender 3D 建模画出来——这就跟我让这个 GPT 画一个美女、让那个 DeepSeek 画一个美女，他们画出来也是不一样的。（开玩笑）

**这个语言就是很难对齐的，因为它直连人类大脑的 latent space。** 所以人类发明了数学语言。数学语言非常好，因为它全人类都能自然对齐：我们知道什么是自然数，我们是从公理一点一点构造出来的，而**那个公理非常小，小到人类基本上还是可以对齐的**。一旦对齐完成，我们用皮亚诺公理就把整个计算机世界全部都构建起来了。**那在计算机的世界里，看到同样的东西，它的语义就是绝对对齐的。**

UML 想要的，是一个非常有野心的目标：**去对齐自然语言世界里面那些说不清的东西。** 百分之百对齐当然不可能，但他希望把**能对齐的部分和不能对齐的部分给剥离出来**——通过定义模型的元素和它们的语义。

有些东西是有语义的。比如类图：类图的语义就是确定的——我有个 class 叫 `Student`，`Student` 里有个 field 叫 `name`，那它就是 `student.name`，它可以变成源代码里的一个东西，它是有语义的。再比如 sequence diagram，顺序图里说要按照某一个时序来执行，那这个**时序的先后就是绝对对齐的**。你如果用自然语言写先后，那当它发生并发的时候，到底谁先谁后、能不能并发，它就是有歧义的。

**UML 在最大程度上减少了在没有代码时候的语义漂移。**

> **结论**：当然，我觉得今天 UML 已经死了。原因很简单：**它所有的假设都是“自然语言和形式语言不能对齐”**，所以它需要一层一层的中间语言。而今天突然之间，自然语言可以和任何东西对齐了——反正 AI 就可以给你问嘛。所以 UML 也是一个历史里的东西了。**但是它设计时候的这个 first principle，其实一直都在。**

### 让 AI 读一份 796 页的 spec

所以我也特意让它帮我重读了一遍 UML 的 spec。这个有点恐怖了：**一份 796 页的文档。** 我的工具还是可以的——我特别做了一个能 scale 长文档的，**几千页的文档也没有问题**，体验跟 PDF 差不多。

这个 Kimi 我就不说了，这可能算一个广告——他送了我一个 699 的一个月套餐，说看到了我的视频。那我就直接让 AI 帮我读了整个 UML spec：先 dump 成文档，**分 subagent，按 division 让每个 agent 读 50 页**；我把一个非常长的文档切成带 **overlap** 的片段（因为总会有一点衔接上的问题），让每一个都提取里面的软件工程智慧，把不符合 AI 时代的不必要的东西剔掉——我把我的 lecture notes 全部给它了，让它总结成课件。

它读完花了 **18% 的五小时额度，大概折算成这个 699 套餐里的五块三。**

我觉得这是一件非常可怕、也值得思考的事情。**当你拥有了更好的模型**——你现在用一个更省 token 的模型，价格可能差不多，因为它很省 token——**就能在差不多的价格下得到好得多的质量。**

这意味着，学生群体在拥有好模型和没有好模型的时候，学习效率和学习成本会有很大的差距。现在 token 可能也不算太贵：**你有一个一百刀的 Codex，对学习来说我觉得已经够用了。**

什么东西烧 token？**去维护大项目。** 大项目要在大上下文里载入很多东西，你的 100 万上下文马上就填满了，那就很费。但你现在如果是一个学习流程，你的上下文不会像我这样，把整个 UML spec 都放进来——**你可以用它的 digested version。**

但更值得思考的是：**我们以后还学不学得起？** 这是个非常现实的问题。如果要让所有人都教育平权，我们没有那么多算力、没有那么多资源，那怎么办？**we don't know。** 这可能是一个社会性的问题。

### 一份 796 页的 spec 从头到尾只回答了一个问题

anyway，UML 总结出来的那些东西，**796 页的 spec 从头到尾只回答了一个问题：哪些 intention 必须定死，哪些不必定死。**

它构造了一个形式语言、一个半形式的语言，来告诉你：哪些东西可以在语义上确定下来，哪些可以留给它、不用去解决。

就是**对齐**的问题。人和人之间的对齐。你甚至要和**下一时刻的自己对不齐**——你不是 deterministic 的，你今天想的和明天想的就是不一样，所以你跟你自己都对不齐。

所以回到开头：一个 leader 不会说“大家去干吧”；一支团队也不会靠 self-organized 自然长出秩序；一个人更不可能和 1970 年之前的那些失败自动对齐，所以每一代人都得自己重新踩一遍、重新总结一次。**炸掉的火箭不会自动变成智慧，瀑布也不会自动变成 MVP——你得有人把它读一遍、想一遍，把它变成你手里那一个点，再加上它的原文。**

大家可以自己回去看一下这个 slides。今天下课。
