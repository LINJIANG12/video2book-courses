## 让项目拥有记忆：软件仓库管理与协作
> 对应块：BLK05 | 覆盖分集：P04上 | 块标题（分集名）：《软件仓库管理：版本控制与协作流程》

前几次课，我们一直在讲同一件事：怎样把 AI 真正嵌进自己的生活和开发流程里。生活里会有无穷多让人不顺心的细节，AI 作为一个强大的 assistant，你只要把真实的意图告诉它就可以了；再进一步，甚至可以把一套反复使用的做法蒸馏成 skills，让整个过程变得更平顺。

最近新的模型又在不断进步。GPT-6 确实给了我一些惊喜：编程上的提升虽然还没有达到我期待的那种程度，复杂任务却明显变快了，也省 token；我甚至专门 measure 过，结果确实如此。但它还没有真正学会非常好的品味，我经常还要骂它，所以我觉得自己可能还能再苟活几个月。

这也正好把一个问题带到软件工程里：为什么我们会觉得一个模型做得不好？

### AI 越强，为什么还要学软件工程

很多时候，原因不是模型不会执行，而是我们交给它的是一个非常开放的 `intent space`。比如只说“给我做一个国民级的应用”，哪怕是顶级的产品经理，脑袋里想到的东西也完全不一样。AI 没法直接和人脑做这样的对齐，它总会按照自己的理解发生漂移。

还有一个越来越明显的问题：AI 写出来的代码越来越紧凑，人类却越来越难读它了。从 GPT-5 到 5.6，再到 GPT-6，代码似乎越来越紧、越来越紧，紧到我越来越不想 review。过去我们还会用各种 prompt，要求 AI 写出符合人类工程规范的代码；现在回头看，似乎我们越来越不会看 AI 写的代码了。代码可能弄对了，但判断它是否值得维护、是否真的符合工程意图，仍然需要人。

我一直猜测，OpenAI 对 AGI 的理解可能是先把数学学好。数学是人类世界里最难、最容易形成全球共识的一种语言：定理的证明可以被全世界的人共同判断真假，数学因此能成为很好的 grounding。数学的逻辑推理还可以解释生活里的许多行为。

比如中午吃什么，很多人以为这完全依赖“灵魂”，其实大脑一直在各种因素之间投票。我会选择一个订饭选项，是因为它最快；下午还要开会，如果时间来得及，我还会想中午能不能小睡一会儿。做 A 就会做 B，这类关系也能落到离散数学里的命题逻辑上。模型先把这些基础能力学好，再通过强化学习获得别的能力，这条路线是有道理的。

空间感知也是如此。鲁班锁、立方体的投影、骰子的展开图，都会逼着人在脑中完成空间想象。只要从简单任务开始强化学习，这种能力并不是绝对学不会的。我们自己的博士学生已经做了半年 3D 打印，在 GPT-5.6 空间感知能力还很差的时候，通过直接对话就能生成相当像样、符合规范的模型；GPT-6 又把一个很长的搜索过程压缩成了一次 one-shot，直接做出了光栅尺玩具那样的东西。甚至有人已经开始用它控制机械臂抓取、叠衣服。GPT-6 仍然是一个语言模型，它对视觉的理解更像一帧一帧地询问下一步要做什么，还没有解锁完整的提示词工程，就已经做得相当好了。

> **结论**：模型会继续进步，甚至有一天真的可能让我们不需要像现在这样上课；但“会进步”不等于“基础知识不再重要”。

一百多年前，汽车刚发明出来的时候，开大约 12 km 就可能出故障。司机必须非常了解汽车的工作原理，否则一旦坏了，就不知道该从哪里修。今天我们在地下车库告诉自动驾驶汽车“把我开到某个地方”，汽车就出发了；作为乘客的人不可能理解整个系统是怎样运转的，尽管最终的动力仍然会传递到机械装置上。

计算机科学也有自己的类似变化。100 多年前，汽车用户需要懂机械；今天，学习软件工程仍然需要把操作系统、数据库这些基础知识做好。只是现在有一个更强大的“汽车”——AI。它不仅替人走路，还替人处理智力工作。我们仍然要学基础，因为理解正确的概念，才能从其他地方借鉴知识，造出更好的东西；至于以后究竟应该怎样学，我自己暂时还不知道。你们如果有答案，欢迎和我一起探讨。

### 项目从一个目录开始

真正开始做一个项目时，第一件事往往是建一个目录，再给它起个名字。比如“我的最酷的 gao game”，然后开始 web coding。我们平时做作业，常常是从课程网站或老师的要求里下载一个东西；但真正要做一个项目，面对的却是自己创建的目录。

目录里会有代码、文档和其他各种文件。这些文件共同构成一个可以交付的东西，最后可能变成你的产品。目录可以直接在本机运行：让 agent 帮你启动开发服务器，窗口或网页就弹出来了。很多著名的笑谈是，GPT-6 帮我做出了很多 killer 级产品，它们都只存在于本机的 localhost 下，然后我发到社交平台上炫耀。

但本机能打开，不等于世界上其他人也能打开。只有你知道 `localhost` 是自己的机器，别人没有办法访问。如果你把自己的 `intent` 和 `specification` 写清楚，明确说明这个东西要让全世界的人看到，GPT 才会考虑把它送到远端。否则，它通常会把你当成一个开发者：先在本机起 development server，调试结果，等你觉得 ready 了，再考虑远端部署。

这也说明，生成一个文件和交付一个软件并不是同一件事。最早的 `hello.c` 可以通过编译得到一个 `hello` binary；再往后，构建目录里的很多东西由命令行工具创建出来。一个项目目录里的代码、文档、构建结果和说明，合在一起才形成软件工程意义上的项目。

有一个常见的定义把软件说成“代码、文档等等一切和软件相关的东西的集合”。我更愿意把软件理解成：人类世界的需求在信息世界里的一个投影。这个投影今天看起来就是一个目录，目录里面的各种东西共同表达需求、实现和交付。

> **定义**：项目可以先被理解为一个目录；但软件工程还要关心这些文件如何被构建、验证、交付和持续修改。

### U 盘坏掉之后，为什么需要版本管理

我自己的第一个博士生大概 2012 年进入南京大学。他大一时发现了一种看起来非常好的学习方式：自己的笔记本屏幕比较小，不适合长时间编程；现在大家买一块二手屏幕可能只要几百块，在宿舍就能获得很好的编程体验，但那时屏幕还没有这么便宜，标准答案往往是去机房。

去机房就意味着来回拷贝代码，比较麻烦。于是他把代码保存到 U 盘里。你们在中学上电脑课时，大概也做过类似的事情：把自己的作品存进 U 盘。大二时，U 盘坏了，代码全部没有了，作业也不见了，连启蒙阶段珍藏的作业都没有了。那当然会伤心，但也说明一个朴素的现实：代码、文档和项目成果需要被可靠地保存，而且不能只保存“当前这一份”。

我们过去很长时间就是这样管理项目的：交作业时打一个压缩包发邮件，或者把东西上传到网页上。今天我们谈软件工程，已经有一个更标准的答案：使用 Git。

Git 不只是帮我们保存一个目录，还能保留、比较和恢复历史版本。过去如果作业更新了，我不需要给每个同学发一个压缩包，只要在课上说一声，大家从远端获取更新即可。可以用 `git clone` 从远端取得一个项目，作业更新后再用 `git pull` 下载下来。我的课程提交流程还可以用一个脚本自动打包，再上传到课程网站，这已经有点像现代的 CI/CD 流程了，后面也可以专门展开。

这里真正值得学习的，不只是“Git 能下载代码”这一条命令。Git 已经成为 AI 时代的重要基础设施：很多 NPM 依赖和配置都放在 GitHub 上。一个成熟的 GitHub 项目，往往是工程师十几年工作的结果；它可能曾经崩溃过，也可能在某个时间点经历过一次大版本重构。今天我们看到的是一个已经整理得很好的东西，但传统的教学没有充分教会我们，如何使用信息密度如此大的外部材料。

### 真正值得学的，是持续学习的意识

你有没有打开过很多 GitHub 项目，却没有留意不同项目之间的细微差别？有的项目有某个文件，有的项目没有；有的文档这样写，有的文档那样写。这些信号其实一直在告诉我们，应该怎样组织一个项目。

在中学时，老师说“把作业拉下来”，我们就只做这一件事，完成了就算结束。到了 GitHub 时代，如果还带着这种“只听老师一句话”的心态，就会像一个被强化学习成只会干当前任务的 AI：别人说什么就做什么，绝不多碰一点。这样确实最省时间，却错过了很多真正值得学的东西。

现在的 GitHub 项目里，有大量 AI 生成的 README：长得离谱、塞满 Unicode 字符画、结构框图和目录树，看上去很有“AI slop”的感觉。可有时你打开一个几十年前就开始维护的老项目，README 很短，清爽舒服，看完以后想找的东西，三个链接就能走过去。你不需要被一大片装饰包围，就能到达目标。

我以前在香港找路时注意到，前方有三个出口，通常就有路牌告诉你三个出口分别是什么；回到南京，在某些地铁站里，却可能要环顾四周、移动很远去找地图。一个好的标识把人在不确定时刻需要的信息放在不确定发生的地方。一个好的 UI 也一样：人站在页面上时，他想知道什么？不同的 A、B、C 应该怎样用最少的方式呈现出来？这就是从好的项目里可以学到的文档设计。

有了 AI 以后，看到一个成熟的 README，当然可以问它：“为什么这个项目的 README 没有 AI slop 的感觉？”但更值得先做的是自己先观察、自己先写一个版本，再去比较。有人会满足于老师给出的命令；有人愿意多花一点时间点进去，看看别人为什么这样组织文件，差异就会变成自己的直觉。

我以前推荐过一种读 research paper 的方法，叫 `virtually implement`，其实适用于任何课程，包括高等数学和计算机系统基础。拿到一个具体问题或需求时，先在脑中自己做一遍；如果你的方法和作者的方法一致，说明你已经掌握了这个知识。如果不一致，有两种可能。

一种是作者或成熟教科书的方法确实比你的方案更好、更精巧、更简洁。这时不要只记住答案，而要追问：为什么他能想到？还有一种更难得的情况，是你的方法比作者的还好。可能一万次里才有一次，但这种惊喜会给你很强的正反馈，你会突然想：我能不能再做一个更有趣的东西？

这是一种需要训练的注意力。看到一个东西时，先不要被它全部吸住，试着问：如果由我解决，我会怎么做？然后立即比较——如果我做得更好，就把它视为 slop；如果他做得更好，我就追问它为什么好。任何时候都在从外界接收信息、留意细节，人就会不停地提升。

### Git 为什么会出现

你可以试着从需求出发，自己“发明”一个简化版的 Git。

假设项目就是一个目录，里面有代码、文档、intent、spec、implementation、测试用例和很多其他东西。新手阶段，手滑或误操作都很正常。你改错了以后，最自然的需求就是：能不能回到上一个版本？再进一步，你可能想把所有版本列出来，看看项目到底经历了什么。

如果有一个命令行工具，能列出这个作业的版本，还能把当前目录切换到过去的某一个版本，那么即使还没有分支、合并、冲突，你已经发明了一个简化版的 Git。接下来，如果要和室友同步代码，就会自然遇到两个人同时修改同一个文件的问题：到底保留谁的内容？怎样把两条修改路线合成一条？于是分支、合并和冲突也就出现了。

SVN 代表了另一种思路：存储项目的变化。最初有一个版本，文件改一行就存一个 patch，再改一行再存一个 patch。早期看，这似乎非常高效。但项目增长以后，想要回到一个早期版本，就必须把许多 patch 一个一个往回退；当然可以用缓存等方式优化，可这条路线会越来越把人拖入泥潭。

Git 的模型干净得多：先保存项目的快照，当我想回到过去的某一个版本时，可以很快回去。这个对比的重点不是简单地说某一种工具“永远更好”，而是看它是否直接服务于我们最初的需求。

| 关键问题 | SVN 式的变化存储 | Git 式的快照模型 |
| --- | --- | --- |
| 保存什么 | 一次次修改形成的 patch | 项目在某个时刻的快照 |
| 回到早期版本 | 需要沿着变化逐步回退 | 可以直接回到目标历史版本 |
| 项目变大以后 | 变化链条越来越长，重建历史更麻烦 | 历史版本本身就是可寻找的对象 |

Linux 内核的维护也走过类似的路。1991 年到 2002 年左右，维护一个如此庞大的项目时，常见方式还是把补丁发到邮件列表：有人改动一个文件，就把新版 patch 发过去，维护者再把它放进核心仓库，随后 release。中间也用过其他工具，但最终还是觉得需要一个绝对简单、非常好用、概念正确的版本控制工具，于是 2005 年做了 Git。

所以 Git 其实比很多人想象的年轻。它不是凭空出现的抽象，而是从“我怎样找回被改坏的项目”“怎样和另一个人共同修改同一份东西”这些非常具体的问题中长出来的。

### 冲突时，Git 为什么把选择交给你

我曾经在推免面试时问过大家：什么是 Git？什么是 GitHub？很多人能说出下载、分发代码，或者说 Git 管理项目目录的快照，这些回答当然不算错。但有一个问题经常没人答出来：如果 `git merge` 发生冲突，你会观察到什么？

尤其是在 AI 时代，大家可能更少真正遇到这个场景。老师发布了一份新的作业，你已经在本地把内容改得面目全非；这时你让 agent 帮忙 merge，它可能“啪啪啪”地把冲突修好，最后告诉你：好了，测试都通过了。你看一眼，看起来也没问题，于是就接受结果。

这里就需要惊人的注意力。冲突出现时，Git 不会把判断责任一直留在工具里，它会把需要你决定的信息集中放到冲突现场。一个文件的两边都会显示出来，有等号、尖括号以及 `HEAD`、`incoming` 之类的标记；如果在 IDE 里，还可能看到接受 incoming、接受 change 等按钮。

比如同一个文件原来是这样：

```text
共同的文件
├─ 你这一侧（HEAD）：第二行 = 2
├─ 冲突分隔标记
└─ 另一侧（incoming）：第二行 = 3
```

Git 不知道你真正想要的是 2 还是 3。它不能替你说“对不起，冲突了，但我不能替你决定”，然后把问题一直躺在那里。恰恰相反，工具把两边都摆出来，是因为最后的语义判断必须由开发者完成。

这和地铁标识是同一个 first principle：发生不确定性的地方，应该把解决它所需的信息放在现场。以前责任在每个开发者身上，现在仍然在开发者身上，只是 AI 可能把冲突悄悄修掉，让人失去了观察的机会。

所以，遇到 merge 冲突时，不要只接受 agent 的“已经解决”。先停下来，看清楚两边分别改了什么，判断哪一边符合需求；选择之后再创建一个 commit，把这次解决记录下来。只要你认真经历一两次，看到那种标记和两边代码并排出现的样子，就很难再忘记 Git 的责任边界。

### 从空目录到可回溯仓库

现在把一个空目录变成 Git 仓库，事情本身非常简单。打开 terminal，执行 `git init`。它会输出一堆看起来有些奇怪的信息；你可以让 agent 帮你解释，也可以先忽略掉，继续往下走。初始化以后，目录里会出现一个默认隐藏的 `.git` 目录。到这里，项目就成为被 Git 管理的仓库了。

基本流程可以这样记：

```text
远端仓库
   │  git clone / git pull
   ▼
本地项目目录：hello.c、文档、测试……
   │  git add → git commit
   ▼
本地历史：带说明的快照，可以回到过去
   │  git push
   ▼
远端仓库
```

假设目录里有一个 `hello.c`，可以先用 `git add` 把它加入这次要提交的内容，再用 `git status` 看当前工作区的状态。确认以后执行 `git commit`，Git 会打开一个文本编辑器，让你写下这次提交做了什么；提交成功以后，就能在历史里找到这个快照。需要把本地结果送到远端时，再使用 `git push`。

> **易错点**：`git init` 产生的 `.git` 目录默认不可见，所以“目录里什么都没有”不一定表示初始化没有成功；项目目录里真正要提交的文件和 Git 自己的仓库目录是两回事。

`git clone`、`git pull`、`git add`、`git status`、`git commit`、`git push` 这些命令看起来已经足够让我们把 Git 用起来了，但不要在这里停住。水面下的冰山才是工程实践真正困难的地方。

### 提交不是作业 V1，而是项目轨迹

很多同学实际上把 Git 当成了“作业 V1、作业 V2、作业最终版”的电子版。复制目录当然能找回旧文件，但它不是 Git 推荐的实践。

更合适的做法是：只要项目发生了有意义的改动，就立即做一次 `git commit`。修一个 bug、加一个功能、调整一个脚本、修改一篇文档，都可以成为一次清楚的快照。提交不是“今天又保存了一堆东西”，而是在项目历史上留下一个可以解释的节点。

提交消息尤其重要。Git 本质上保存的是快照，但项目仍然是从 V1 经过修改走向 V2 的过程。提交消息要描述你改了什么，最好也让人看出为什么要改。这样连续查看历史时，我们才能知道修了多少 bug、加了什么需求、经历了什么重构，项目是怎样一步步走到今天的。

我故意写过 `I added some cool stuff` 这样的提交消息。它语法没错，也确实记录了一次提交，但完全看不出做了什么。一万个提交以后，历史会变成一团没有信息的废话。那时 commit message 这个特性就失去了意义；如果每条消息都一样，不如从 V1 到 V2 什么都不说。

现在可以在使用 AI 时多问一句：“我刚才做的这个 commit，符合 best practice 吗？”比如把几个文件一次性 `git add .` 是完全合法的，Git 不会阻止你；但这不代表它是一个好的提交。AI 可能会按严重程度指出问题：提交信息毫无信息量、提交粒度和内容混杂、提交了不该进入仓库的文件，还会告诉你应该怎样改。

提交消息可以用祈使句、现在时描述变更动机，比如清楚地说明修复了一个 off-by-one 问题。很多项目还会使用 `Conventional Commits` 这样的前缀约定，遇到成熟项目时可以留意它们。不要把“合法”误认为“推荐”，更不要让所有改动都挤进一个巨大的提交。

### 不要把构建产物提交进仓库

有一个很常见的反模式：改了三五个文件以后，直接执行 `git add .`，把当前目录里所有能加入的东西全部提交上去。Git 允许这样做，所以很多人以为这样做就是正确实践。

但 `hello` 这样的编译产物不应该进入版本库，应该放进 `.gitignore`，由构建系统在需要时重新生成。原因很简单：不同开发者、不同机器和不同环境下，构建结果都可能不同。产物里可能带有日期、hash，甚至本机指纹；即使源代码完全相同，两个合作者编译出来的 binary 也可能不一样。

如果这些产物被提交进去，下一次合并就可能出现无意义的冲突。二进制冲突很难像文本代码那样细粒度地合并；如果产物还是生成的图片，处理起来同样麻烦。项目文件很多、合作者很多时，这类差异会不断积累，仓库也会变得臃肿。

> **结论**：Git 记录的是应该被共同理解和重建的项目内容，不是每个人机器上生成的临时结果。

这也是“作业 V1”思维和 Git 工程思维的一个差别。旧目录里什么都能留下，Git 的目标却是让仓库长期保持可理解、可协作。

### 空提交可以偶尔有用，但不能成为习惯

普通情况下，Git 会拒绝没有任何改动的提交，因为从 V1 到 V2 确实没有发生变化。agent 有时可以强制做出一个空提交，但这不代表空提交就是日常实践。

它在少数情况下有用：例如在没有代码改动时触发一次 CI、在发布版本时留下 finalize 的记录，或者把最后一个 bug fix 和“冻结为 V0.1”的动作分开。版本发布也可以用 tag 来标记 V0.1；有些流程则会用空提交表达一次流程上的动作。

所以，空提交可以偶尔出现，但不能大量制造。否则历史会被无意义的节点淹没。真正的工程判断是：这次没有代码变化，是否仍然需要一个可见的流程事件？如果答案不是，就不要为了“看起来有提交”而硬加一个。

AI 还会做一件更值得警惕的事：它可能直接重写仓库历史。比如它会发现有空提交、有编译产物，于是说要把历史整理成两个有意义、单一职责的提交，创建一个 `main` 分支。这个操作在没有远端、也没有其他开发者持有副本时，可能只是本地整理；但如果别人已经拿到了这个仓库，改写历史就会变成糟糕的事情。

> **提示**：接受 agent 修改提交历史之前，先看它到底动了什么：哪些提交被丢弃，哪些文件被移出历史，是否创建或改写了分支，仓库有没有远端。工具说“测试通过”，不等于历史变更就天然合理。

### Git 是基础设施，判断力仍是核心

GitHub 刚出现时，大家想到的是分发代码变得方便。Git 创作者当时未必意识到，它后来会成为 AI 时代的一项底层基础设施：NPM 依赖、配置文件、很多工程资料，都能在 GitHub 上找到。今天如果一个 AI 工具能够修改代码、运行测试、生成项目，它背后也往往依赖仓库、版本、提交和协作记录。

但会执行几个命令，不等于真正掌握 Git。`git push`、`git pull` 只是水面上的按钮；什么时候应该 add，什么时候应该 commit，提交信息为什么要这样写，构建产物为什么不能进版本库，空提交什么时候才合理，才是水下的 best practice。每一个约定背后都有代价，都是一次次错误之后留下的教训。

所以以后碰到新工具，不要只问“老师让我执行哪条命令”，还要问：它为什么这样设计？它保护了谁？它把什么责任留给了人？你可以把自己的做法告诉 AI，让它按严重程度检查；也可以追问“为什么不这样做”，让它把约定背后的理由讲清楚。我的智力和注意力都是有限的，课堂上讲出来的未必就是最好的解释，遇到这些概念时，完全可以借助一个更强的模型把因果链补全。

AI 越能替你执行重复动作，越需要我们保留对项目、意图和历史的理解。Git 不是一个自动替你做判断的按钮集合，而是一种让项目拥有记忆的方式：它保存快照，记录变化，暴露冲突，让人能够在过去、现在和未来之间来回确认。我们真正要学的不只是如何把代码放进仓库，而是怎样让这个仓库真实、清楚、可协作，并且在模型替你动手之后，仍然知道什么值得相信。

## 从提交到协作：把 Git 当成一套可审计的工程系统
> 对应块：BLK06 | 覆盖分集：P04下 | 块标题（分集名）：《代码评审、分支策略与团队协作规范》

从提交一次代码开始，我们最容易犯的错是：改一个字，觉得不要紧，直接提交。人这样做通常还能勉强承受，交给 AI 就不一样了。模型可能把不能编译的改动也一起提交，可它见过大量工程项目，也读过不少软件工程书，反而会提醒我们：当前改动不应直接提交，仓库需要保持完整自洽；它还顺手把问题修好，并解释为什么。

这件事很有意思。我们在 agent 时代甚至不一定需要背出 `git status` 之后每一条具体命令，概念足够清楚，就可以要求 AI 按最佳实践行动。**概念让你能验收 AI，命令只是可以委托给 AI 的操作细节。** 我们真正不能脱节的，是对 Git 能做什么、为什么这样做，以及仓库内部如何运转的理解。

### 提交前先把仓库带回可用状态

每次提交都应能通过构建和测试。这句话听起来像常识，但只有反复强化，很多人才会真的把它当作提交条件。我们改一个文件时，顺手产生了一个不能编译的版本；这看似只是“少改了一行”，实际上却把整个仓库置于坏状态。完整、自洽的快照才有资格成为一次提交。

> **结论**：一次提交应当是一个完整、自洽、可以构建并通过测试的快照，而不是暂时保存半成品的草稿。

这也是让 AI 执行提交任务时最值得反复强调的约束。它不仅要知道“帮我提交”，还要知道提交前逐项检查文件变化，发现不能编译就停下、修复并解释。不同任务可以配不同提示，例如要求用中文，或把理由讲得更细，但工程约束本身不能丢。

过去，新同学加入一个研究项目，第一周的任务往往只是搭架子、让一两个东西跑起来。我打开他们的 Git 项目，常常会立刻进入“高血压时刻”：`dist`、`log` 等生成文件被交上来，个人编辑器配置被提交，甚至 `VS Code` 里的配置写着某台机器 `C:\Users\...` 的硬编码路径。这样的项目离开那台电脑就无法复现，检查者怎么能放心接受它？

还有更危险的密钥。审阅项目时看到本应处于 active 状态的 API key，如果在仓库里发现，就不能只当成格式问题；个人凭据一旦进入版本历史，删除工作区文件也不够。**密钥和个人环境不能进入可共享的仓库。** 这条线一定要守住。

#### 哪些点文件需要忽略

`.DS_Store` 是一个很典型的误提交来源。macOS 用 Finder 打开目录后，会自动记录哪些子目录被展开，生成 `.DS_Store`；它是隐藏文件，默认 `ls` 不显示，但 `git add .` 仍可能追踪到它。Linux、macOS、Windows 混用时，这类文件特别容易混进提交。VS Code 的个人配置、个人路径以及生成目录，也不应该跟着源码走。

但这里绝不能学成一条粗暴的“所有点文件都忽略”或“所有生成文件都不提交”。Git 追踪点文件本身并没有错，`.github/workflows` 就是点目录，也应该被版本控制。关键不是开头有没有点，而是文件有没有跨机器复现的价值、对构建是否必要、是不是个人环境留下的临时状态。个人设置、日志、`dist` 一类产物通常应当忽略；某些必须纳入构建的生成内容则要另行处理，不宜用一条通配规则一刀切。

规则不是背一个忽略名单就结束了，而是每次提交前逐项检查：

1. 当前改动是否都属于同一件事？
2. 是否有不能构建、不能运行的状态混在里面？
3. 是否有个人配置、绝对路径、日志、缓存或密钥？
4. `git status` 看到的文件，是否都能解释它为什么应该在这里？

把这个问题交给 AI，不是让它用一个忽略规则消灭所有风险，而是让它把每一个文件的理由说清楚。**Best practice 的作用，是在提交前拦住一个坏状态，而不是给坏状态换一个更隐蔽的名字。**

### Hook 让检查发生在正确的时刻

严肃项目里，规则会从“记得检查”升级为“必须触发”。Hook 就是在某个函数调用结束、某件事发生或 agent 等待输入时自动执行动作的机制。agent 需要我输入时播放一声提示音，只是一个小例子；把检查挂到 `pre-commit` 上，才是它对工程更有价值的用法。

规则名称统一用大写还是小写，看上去无关紧要，其实不值得逐条向 AI 确认。团队已经形成的规范就应该直接使用；遇到还没形成规范的细节，再让 AI 解释为什么。项目标准可能更高，检查项可能有几十条，这时统一规则尤其重要。一个很轻量的判断是：

> **提示**：先问“这个项目已有的规范是什么”，再问“这个细节是否值得建立规范”。前者是执行约定，后者才需要讨论和引用资料。

AI 还能给检查加上清楚的反馈，甚至用 emoji 缓和“这里不能提交”的情绪。过去导师检查学生的提交，发现违反软件工程实践时，即使尽量保持 nice，学生还是会因为被批评而紧张。AI 把“告诉你哪里不对”从导师的权威关系里拆出来，变成一次耐心的检查。它减轻了这种压力，也让人更容易接受反馈。

### 一次提交应当是一个不可分割的快照

把 Git 想象成一个在磁盘里不断生长的树。每次 `git commit` 都保存一个版本，而不是覆盖上一版：

```text
V1 ──→ V2 ──→ V3
```

如果只有 B.txt 发生变化，完全复制整棵项目树既慢又浪费。Git 会保存一个新的根，通往新 B.txt 的路径需要重新表示，没有变化的 A.txt 和目录可以继续复用旧对象。假设当前目录是根，下面有 A.txt、B.txt 和目录 D；改 B.txt 时，变化可以简化为：

```text
V1 root ────────┬──→ A.txt（复用）
                 ├──→ B.txt（旧版本）
                 └──→ D（复用）

V2 root ────────┬──→ A.txt（复用）
                 ├──→ B.txt（新建）
                 └──→ D（复用）
```

`V2 root` 不需要包含一百万个新文件。项目再大，也不需要设计一千层深的目录；目录的展开本身是逐层进行的，路径的增量通常很小。这正是“版本就是快照”与“以最小代价保存快照”结合后的结果：保留历史，不等于把每个版本的全部字节再复制一遍。

#### Git 中存下来的三类对象

这套想法落到 Git 的实现里，就是以哈希为索引的普通磁盘文件，以及三类核心对象：

| 对象 | 存的是什么 | 它的作用 |
| :--- | :--- | :--- |
| `blob` | 文件内容的字节序列 | 表示文件内容，不关心文件属于哪个目录 |
| `tree` | 目录项、文件权限和子对象引用 | 把文件和目录组织成一棵树 |
| `commit` | 一次快照对应的树，以及父提交关系 | 指向快照，并记录它从哪里演进而来 |

这三类对象组成可寻址的数据结构。只要对象内容不变，它就可以被多个快照复用；对象本身也能持续加入 `.git/objects`，向前生长。把这些对象组织成 Git，并不是复杂到无法从第一性原理设计的东西。

> **易错点**：`blob` 是文件内容的字节序列，不等同于最终看到的文件名；文件模式、文件名和目录关系由 `tree` 保存。可执行文件和普通文件的权限差异也由 tree 记录，因此一个目录里同时存在可执行文件与普通文件并不意味着出现了两个内容对象。

例如，提交里出现 `Mode 644` 和 `Mode 755` 的文件，不是 blob 混进了两种格式，而是 tree 用不同权限引用了文件。一个很小的文件存储后，解压前甚至可能比原文更大；不要因为压缩后字节数不划算，就据此判断 Git 失效。

#### 从真实仓库看对象、分支与冲突

只看数据结构会觉得踏实，却未必真的相信实现。我们可以直接观察真实 Git 仓库中的 `.git` 目录：提交一个 `hello.c` 后，沿着 tree 指针就能找到它引用的 blob；从 blob 的磁盘字节解开压缩，又能还原文件内容。删除目录中的一个文件，仓库并不是凭空记住“删除了某物”，而是产生了一个不再引用旧路径的新快照。

分支也不是“复制一套项目”。它是一个叫作 `refs` 的引用文件，指向一个提交对象；`HEAD` 则是指向引用的指针。两层关系可以简化为：

```text
HEAD
 │
 ▼
refs/heads/main
 │
 ▼
commit C3
 │
 ▼
tree T3
```

从 `C3` 可以继续访问 `C2`、`C1` 的提交，提交再指向各自的树，树再指向 blob。创建 `feature` 分支，就是再放一个 `refs/heads/feature` 指向合适的提交；切换分支，本质上是移动 `HEAD` 指向哪个引用。

合并时，Git 把两边的发展合并成一个新的 commit。这个提交可以有两个 parent：一边是当前分支原来的历史，另一边是被合入分支的历史。下面的图展示的是两个旧提交如何成为新提交的两个父节点：

```text
             C1
            /  \
          C2    C3
            \  /
             M
          /      \
       C4        C5
```

如果两侧对同一个文件做了互相不兼容的重构，就会产生 merge conflict。把 A 拉到本地时，Git 在 index 中留下 `base`、`ours` 和 `theirs` 三个版本；工作区里的文件会带冲突标记，不能把任何一边直接当成最终答案。解决冲突后，临时文件消失，合并 commit 的 tree 指向你选择或重新整理出的版本，而两个 parent 都被保留下来。

```text
基线：B 修改
      │
      ├── A 分支：重构 A
      │
      └── B 分支：重构 B
                │
                └── merge：产生冲突 → 人工或 agent 解决
```

真实仓库的可视化工具可以把这些对象和指针动画化：监听目录变化，文件从工作区消失、commit 新增、分支分叉、merge 产生双 parent，都能同步显示。我们自己也可以做这样的工具，只要它读取真实文件系统里的 Git 对象和引用，不把动画当作 Git 本身。**模型可以模拟概念，真实仓库才负责验证概念。**

### 用可重复测试把 Bug 二分到具体提交

有了提交历史，排查 Bug 就不必凭印象猜。我们通常有一个测试用例，或者任何能稳定暴露 Bug 的检查方式。它在当前版本失败，那么 Bug 可能是过去某个时刻引入的；我们要找的是“第一个坏提交”。

如果历史足够长，提交序列可以看成一个有序数组：较早的提交能通过测试，较晚的提交不能通过测试。我们要找的正是“前面全为通过、后面全为失败”分界处的第一个失败提交：

```text
提交编号：  0    1    2    3    4    5    6    7    8
测试结果：  P    P    P    F    F    F    F    F    F
                         ↑
                    第一个坏提交
```

只要“此前能通过、从此开始失败”这个假设成立，Git 历史就可以用二分查找缩小范围：每次不必遍历全部提交，只需在中间提交运行测试，根据通过或失败决定往哪一侧继续。测试必须能够稳定复现 Bug，否则得到的只是某个提交碰巧改变了现象。

定位之后还可以运行：

```bash
git bisect
```

Git 会引导我们标记当前提交是 `good` 还是 `bad`，再根据结果继续选择下一段历史。提交被找到后，用 `git blame` 追溯它具体修改了哪一行。`git blame` 把每一行代码关联回引入它的具体提交，因此“哪一行由谁改的、当时发生了什么”有了可核查的入口，而不是只留下一句无法验证的猜测。

`bisect` 负责找到边界，`blame` 负责追到改动，提交消息和提交内容负责解释原因。几个入口组合起来，排查过程才真正变成一条可审计的链路。

### 提交协议与个人工作区的边界

提交不是把文件复制进一个叫 Git 的黑盒。一个好提交至少应同时满足三条约束：改动范围小、主题单一、快照可构建。若代码可构建但提交主题混杂，“可以构建”仍不够；一个同时加入新接口、修改旧逻辑、更新文档的大提交，仍然会拖慢审计和修复。

主题可以由 Conventional Commits 规范表达。以新增功能为例：

```text
feature: add a new capability

Explain the reason for the change, the important implementation details,
and the behavior users should expect.
```

第一行是简短的 `type: summary`，`feature` 表示新增功能，冒号后要留一个空格；后面可以接提交正文，解释为什么改、怎么改、行为有什么变化。`fix` 则用于修复 Bug。规范的作用是让提交标题在列表里足够可读，也让我们知道该按什么方式命名，而不是把所有标题写成“我改好了”。

> **定义**：atomic change 是一个完整、自洽的快照：一个提交聚焦一个目的，能够独立构建、测试和审计。

这里的 atomic 不是“文件数量少”或者“代码行数少”，而是“一个提交只承担一个目的”。一次提交包含几百行代码，不一定差；一次提交同时承担三个目的，即使只有几十行，也很难审计。尺寸要和目的匹配，尺寸本身不是目标。

#### 个人设置不入库

个人工作区仍然有它自己的边界。编辑器用户配置、机器相关的绝对路径、日志、缓存和生成产物不属于公共项目；`.DS_Store` 更是纯粹的 Finder 状态，不应该跟着代码走。它们要么由项目自己的规则排除，要么只保存在提交者自己的环境里。

配置里会混入个人习惯，这一点很隐蔽。编辑器用户设置如果写死本机路径，就无法在另一台机器复现；日志和缓存会不断变化，提交后只会制造无意义的差异；`.DS_Store` 会在使用 Finder 的同学电脑上无意间被加入。`git status` 中出现这些文件时，要在提交前解释它为什么存在，不要等到后面再清理。

`package-lock.json` 不能用“生成文件”三个字被一概排除。它通常由工具生成，但可能需要纳入版本控制，以保证别人可以在不重新下载大量依赖的情况下编译项目。这里没有绝对的规则，具体要问的是：它是否服务于可复现构建，或者是否携带个人环境状态。

### 团队协作需要 Issue 与代码评审

Git 擅长保存代码快照，但真实项目不只有代码。GitHub 上还有 Issue、代码评论、任务分配和讨论，这些信息不会随着一次 commit 自动持久化。GitHub 太过流行又好用，因此值得拥有一个专门的命令行工具，让 AI 也能把协作信息纳入工作流。

`gh` 命令行工具可以帮助我们登录 GitHub、获取 Issue、查找分配给自己的任务，再把已解决的 Issue 关闭。对一个长时间交给 agent 执行的任务，还可以在任务说明中明确要求：小步提交，提交可审计，并遵守既定的分支规则。它和项目已有的协作规范文件是配套的，不替代项目文件。

注意，git 命令无法代替协作平台本身。一个 Issue 里的文本、评论、任务分配和讨论，都属于 Git 之外的协作状态。命令行工具与平台对接，而不是被它们吞没；谁拥有什么任务、谁完成了什么，不能只靠本地 commit 推断。**版本控制支持分叉、合并和溯源，Issue 支持任务与讨论。**

最后才是评审。评审不是提交之后才发现问题，更不是等 agent 说一句“已经完成”才检查。提交前逐个检查文件变化，执行构建和测试，再把可构建、可测试的小提交交给评审。这样，我们审查的就不再是“改一个字没有多少风险，因而直接提交”，而是审查一个可以独立理解、独立构建、独立测试的快照。

#### Hook 与 CI 的分工

`pre-commit` hook 适合放在提交前，作为每次提交都会触发的本地检查。CI 适合放在提交已经进入协作流程之后，依据项目的统一环境运行完整验证。两者不是互相替代：hook 可以让错误在本地就被拦住，CI 可以让所有提交在共同的规则下接受验证。GitHub 上常见的是 CI 流程放在 `.github/workflows` 中；本地检查则可以由 hook 触发。Issue 解决以后可以关闭，测试和评审结果属于协作记录；提交内容、快照状态、parent 关系则保持清晰。

### 为什么要及时提交

为什么一定要及时 commit？项目刚开始、关系简单时，一次提交两三千行代码看起来可能没什么问题。可一旦项目里的关系错综复杂，一个大 commit 就可能同时破坏多个地方，引入多个 Bug；后面再补上多个 fix，已经很难判断问题究竟出在哪里，甚至不知道 V2 到底修好了没有。

如果每一次 commit 都很小、只做一件事，就会“冤有头债有主”：这个 Bug 是你写出来的，我修完了也就是修完了；引入 Bug 的提交和修复它的提交可以配成一对。即使后面又修改了很多地方，我们仍然有审计能力。

及时 push 还有另一个很朴素的好处。电脑物理损坏、工作没来得及同步，是真实会发生的事。小提交后立刻 push，就能得到互联网上的备份；电脑马上坏了，代码也还在。AI 很清楚这些提交可以 review、revert、bisect、blame。版本控制的价值不是把命令变复杂，而是在问题出现时给我们留下足够细的线索。

### 分支、合并与线性历史

项目管理最难的地方，是人没有办法处理一团混沌：很多需求、很多代码一起推进。Git 管理的正是快照。我们可以随时从某个快照开一个分支做尝试，失败就安全地丢掉，成功再合并回来；多个主线也可以同时推进，最后以 merge 的方式合到一起，不互相干扰。

做大作业时我们都会有这种体验：要改好几个地方，改着改着就乱了，这部分和那部分冲突，公共祖先上做的修改又彼此不兼容。如果任务拆成可理解、可审计的小块，出了问题就能 `bisect`、能 `blame`，协作时发生冲突也更容易解决：两个小任务冲突，不冲突的部分仍然可以更容易地合起来。

```text
              C0
            /    \
        A1 ── A2   B1 ── B2
          \          /
           \        /
             M1
```

有些项目会要求 linear history：从 commit 拓扑看，整个历史像一条线，不让日常历史保留分叉又合并的形状。可以先把当前分支上的修改合进来，再让后续提交接在它后面，最后看起来像一条线。一个线性 commit 也会保留 parent 关系，只是展示出来的拓扑不再是明显的分叉：

```text
C1 ──→ C2 ──→ C3
          │
          └──→ F1
```

现在越来越流行强制 linear history，一方面是因为 AI 擅长 resolve 和 rebase，另一方面是它确实更便于追溯，对 cherry-pick 和 blame 也更友好。把 Git 记录拆得足够清楚，容易找到修改由谁引入，AI 维护项目时也能少花一些 token。

> **注意**：线性历史不是所有场景下只有好处。这里的选择仍要服务于项目；真正重要的是每一次改变都能解释、追溯、审计，而不是为了看起来“像一条线”就丢掉历史信息。

### 先设计好架构，再让多个 agent 协作

我自己的一个经验是：虽然知道要小步前进，架构设计阶段仍要先和单线程、智力比较高的模型把问题讨论清楚。这一步很重要。软件设计不好，后面往往就是无穷的迭代。

一个可以信赖的 AI 代码例子，组件之间虽然互相关联，但接口被定得很清楚。组件库的接口要足够好，核心接口尽量使用 pure function；程序本身也按 pure function 去看，trace 是程序的一个 pure function。整个程序有一个标准的 derivation graph，组件按这个图展开。会在更大范围内互相影响的状态——例如光标位置如何影响可视化、菜单栏如何变化——全部注册到一个全局地方；这个全局状态保持得非常小、非常干净。

这样做以后，一个 playground 的核心共享状态只有十几行，组装也只需要十几行，剩下所有东西都是黑盒子。设计 visualization 时，可以要求 agent 禁止查看库函数实现，只看接口。这样既能守住组件边界，也让生成过程更省，几个万能 token 量级就可以做出来；关键是架构让各部分能独立组合，而不是让 agent 在所有实现之间来回猜。

架构确定后，再开几个 terminal，让多个 agent 按明确的协作规则分工。规则可以直接写进 `AGENTS.md`。例如，不必让每个 agent 调用视觉模型检查效果，视觉模型很费 token；把浏览器放在旁边的另一块屏幕上，实时刷新，人直接盯着结果，哪里不满意就让它改。右边的东西不断变好，几个 agent 同时推进，问题也就解决了。

> **结论**：小步提交不是把一个大任务切成很多碎命令；它要求先有可组合的架构，再让多个 agent 在明确的接口、状态和协作规则下各自推进。

当然，不要把全部代码质量都交给“我不管”。AI 直出的东西可能很 slop，架构把控仍然重要；程序逻辑可以不逐行管，但不能让组件互相知道所有实现细节。**结构先清楚，agent 才能在局部工作而不互相踩踏。**

### AI 时代真正要学的是协作与可审计性

Git 只是软件工程的一个切面，但它把一个项目的组织方式说得很清楚：把项目组织成用 atomic change 推进的快照。每一次改变都能构建、测试、评审、回溯；每一次尝试都可以从快照开分支，成功再合并，失败就丢掉。所有后续的 hook、CI、Issue、代码评审、`blame` 和 `bisect`，都建立在这条主线上。

因此，使用 AI 并不等于把工程判断交出去。相反，AI 可以耐心地检查生成文件、提示构建失败、解释提交规范、处理 issue、review、revert、bisect；它甚至可以帮我们做 Git 对象与分支的可视化工具。我们要做的，是把概念吃透，把标准和规则说清楚，再让它承担重复、细致而容易遗漏的执行工作。

一个可视化 Git 工具可以在两天碎片时间里搭出框架，再花时间调整视觉效果；一个面向低年级孩子的 Python 教学环境，也可以很快做出网页界面、极简编辑器、可视化调试器和 3D 打印世界。甚至便宜的模型也可以用来生成课件。AI 很强，但真正有价值的品质依然是愿意花时间学习，把每一个细节做好。

当一个人能回答“`git merge` 以后发生了什么”，能在 AI 指导下真正从零构建这个概念，而不是只听过一个名词，他在项目里的竞争力就不一样了。求职市场会把“把细节做好”的标准不断提高；Git 帮我们把软件组织成可审计、可协作、可回溯的系统，AI 则让这套系统越来越容易学习和执行。

等 agent 再快一千倍，我们怎样管理版本控制？这会是下一道问题。但在它到来之前，先把今天这条主线记住：**用 atomic change 推进快照，让每一次改变都能被理解、验证、合并和追溯。**

## 从文件树到软件仓库：为什么 AI 时代要重新设计版本管理
> 对应块：BLK07 | 覆盖分集：P05上 | 块标题（分集名）：《软件仓库管理（续）：工程化工具链》

上周我们讲了一点版本管理，这周继续。先说个你们都熟悉的场景：填表。每次填表都要打开一个 `.doc` 表格，把姓名、学号、身份证号一份一份抄进去。今年我已经把这些事情全部交给 agent 了，用一句话让它去调用就行。

但这里有个很值得讲的故事。大概是疫情期间，我招过一个研究生，他在我这里做了三年，做的就是一个“自动填表系统”——因为大家都觉得填表很烦。等他毕业的时候，突然来了个 ChatGPT，他一下就慌了，觉得自己做的事情马上就要被替代。我跟他说：不要紧，你赶快答辩，然后就可以毕业了。

**这世界发展得太快。** 我讲这个不是为了让大家焦虑，而是想请你们亲自体会一下：AI 写代码的门槛在下降，但把一堆代码“变成一个能持续维护的东西”，门槛才刚刚开始露出来。

### 会成长的个人助手

先说作业。这门课的作业都是自愿完成，但最后肯定会验收——学校可能会让大家提交一个成绩，然后把链接交给我，由我的机器人来评分。

第一个 lab 是一个比较时髦的需求：做一个“会成长的个人助手”。要求不限，你想怎么做就怎么做，最好还是用 vibe coding 的方式做。我自己今天也会现场做一个，顺便告诉大家：如果你直接让 AI 给你做，会遇到什么样的小坑。

为什么要布置这样的实验？看起来所有任务都在 AI 的能力范围之内，对吧？但如果你直接把这个实验要求丢给 AI，它在一开始就会做出很多“看起来也合理”的决定，而这些决定会让项目的维护变得越来越困难，最后陷入一个维护的坑。

所以我觉得每个同学都有必要体验一下软件工程里的这个坑：什么时候你的 AI is lab 开始不断消耗你的 token，什么时候你终于下定决心“把这个项目删掉，从头重做”，或者“回退到很早以前的版本，从头做”。

这个 lab 就是为了让大家体验到那一刻。

顺便提一下，下一个 lab 会和这个 lab 有非常大的关联，而且你们暂时猜不到。你现在把 live1 做好了，它变成一个非常舒适的个人助手，然后我会给你加一个需求——这个需求和前面所有的东西都关联，并且有一定的冲突。你就改，越改越崩溃，最后体会一下这个过程。

所以如果你这次选择躺平、或者干脆不管它、让 AI 直接做，下一次就只能把这个东西直接删掉，可能就没有这个软件工程的体验了。

**个人助手可以往哪些方向做？** 几个我想到的例子：

- 把专业课的资料放进个人数据库里。这学期可能会上一些专业必修课，比如计算机网络、概率论，比较困难，你可以把资料整理进去。
- 参加研究组课题的时候，把相关文献、教科书整理成个人数据库。
- 把个人信息也放进去。填表很烦，这一项应该深有体会。
- 在个人数据库的基础上，和你的 Gmail 邮箱关联起来。如果有条件，可以让 agent 在后台常驻。
- 手机端联动，可以是一个网页，也可以是苹果的 app 或者 Android 的 app。只要让 AI 去做，它会自己把需要的东西都下载好，然后把结果做出来。

还可以买一个很小的嵌入式设备，一两百块钱，放在宿舍里持续跑你的 agent loop。如果它能访问你的邮箱，假设我在两周以后半夜给你发邮件，你的 agent 可能会把邮件回给我，实现一个 always on 的后台。

你要办理什么事务，也就是一句话的事情。这就是一个“会成长的个人助手”能做的事。

### intent、spec 和 code 不是 README 的全部

回到软件工程本身。上节课我们讲的是软件的项目管理——项目是各种文件的集合：你的 intent、一些设计文档、你的 README 都在项目里。

但我其实不喜欢 AI 写出来的那种非常长的 README。我喜欢的是，对我来说，README 应该写一下你设计这个项目的时候最初的初衷：你想做一个什么样的产品，这个产品能达到什么样的效果。可能可以加两个截图，以及你最重要的那些设计。

有一个画面你可以想象一下：有一天你突然想了一个非常好的点子，想用它去挣一个亿。这时候你要组建一个创业团队，要说服一个懂 computer science 的人出来干，比如说服我出来干。这时候其实你只需要一个比较短的 README，因为这是你的 intent：你就是想做这个东西。至于你有架构能力、写代码能力，剩下的人可以把其他东西补出来。

**你不需要事先知道这个软件系统的 specification 是什么，它用什么数据库，怎么支持用户从 1 到 10 到 100 万到 1 亿。** 你可能没有 computer science 的知识，但你不需要有那个最原始的设计。

所以从一个软件产品的角度，README 到 intent，intent 到 spec，spec 再到 code implementation，这些东西全都在项目里。从 intent 到 spec，就有了一些更具体的东西：我要选什么样的数据库，甚至要选什么样的编程语言，我的项目结构是什么，各种各样。小到每个模块的接口，都属于 spec。然后再到 code implementation。

### 文件系统其实丢了很多信息

有了这样的项目以后，很自然地你就需要一个容器，把这些各种各样的文件管理出来。大家用文件系统来管理项目，其实更多是一个历史的原因。回到 1950、1960 年，操作系统给你的存储功能就只有文件，它没有别的，关系型数据库还没有发明出来。所以那时候的程序员别无他法，只能把项目以文件的形式存进来。

但这更多时候是历史。历史是不停地往后涨的，导致的原因——我个人觉得——文件系统可能不是组织项目的正确方式。因为文件系统其实丢失了很多不适合表达的信息。

有些信息是比较容易表达的，比如我的 intent、spec：我一条文档这个地方是怎么想的，或者这个测试用例是什么、我输入是什么、输出是什么，程序运行过程中什么东西不能被违反，assert 什么。

但你马上就会发现，项目里有很多隐藏的关联，在文件系统里是没有的。

举个很常见的例子：性能不够了，你要把 linked list 换成更高效的 tree 结构去优化性能。你让 AI 去做，AI 啪啪啪给你代码改完了。但是你没想到的是，你可能在项目里某个文件的文档、Markdown 里写了一句：“我这个项目是用 linked list 管理的。”文档和代码之间其实是有关联的——你写文档的时候可能还没有代码，所以你就先写了那个文档，随手一写“这是个 linked list”，但是一旦代码实现了，关联并没有被强行联系上。

**这就是一个技术债（technical debt）。** 因为以后随着文档和代码不断向前演进，它们的不一致只会越来越多，不会越来越少。然后这个软件就陷入了一个维护的泥潭：后面你拿出一份代码，甚至 AI 拿出一份代码，那到底是文档说的对还是代码说的对？你跟它聊天的历史已经没有了，chat 已经消失了，你换了一台电脑，你那个 git repository 里面可能还有一些 change 的日志，但到最后你真的不知道到底是代码对还是文档对。

在软件工程里，这已经是一个研究了很长时间的问题，叫 traceability，可追踪性。所谓的追踪就是：在软件项目当中，各个测试用例、文档、哪怕代码中间的一行，它们之间的关联是什么？我们能不能在软件系统的演进过程中仍然维持它？

所以很多时候我们觉得挺有意思：文件系统“将错就错”了。大家最后总有一天会发现，用文件系统管理代码你受不了了——打个压缩包发布，打压缩包发给你的合作者，这件事情已经维护不下去了。

**所以就有了 SVN，有了 Git。**

### 可追踪性：一个带环的图

那下一个是什么？大家有没有想过？Git 之后可能还有一个更好用的版本控制工具。但同时我也在想 traceability 这件事：如果以后我们都不写代码了，那软件还会像现在这样在 Git repository 里面管理吗？

我们现在的 repository 里面，好多文件：README.md、hello.c、docs 下的什么文档。如果以后这些东西我们人都不管了，那有没有可能把软件、部件之间的关系，变成好多切片，切片变成好多个对象、entity？比如说，这个文档和这个实现之间就有一个关系：这个代码实现了这个文档。然后我可能有一个测试用例，这个测试用例也关联到这个文档，那这个文档和测试用例又关联起来了，然后这个测试用例和这部分代码的实现关联起来，然后这个文档和那个文档关联起来。

你看，这是一个完全结构化的东西。没有办法在文件系统里以一个树状的形式表达，这是一张随便连接的图，有 cycle 的 graph。

```text
             ┌──────────────┐
             │   文档 D1    │
             └──────┬───────┘
        实现         │ 记录测试要求
       ┌──────┐      │
       │ 代码 C │      │
       └───┬──┘      ▼
           │       ┌──────────────┐
           │       │  测试用例 T  │
           └──────►│  覆盖 C·D1  │
     覆盖实现        └──────────────┘
                           ▲
                           │ 需求关联
                    ┌──────┴───────┐
                    │   文档 D2    │
                    └──────────────┘
```

这张图的意义在于：需求、文档、测试、代码不再是“几张互不相干的 Markdown 和 `.c` 文件”，而是一组互相关联、并且在演化中必须保持同步的实体。

那这个东西可以放到一个数据库里，叫一个 repository database。显然人类就没有办法用现在 UNIX 世界里的工具来维护这样的一个 repository 了。但不要紧，我们应该怎么解决？

**用魔法打败魔法。** 人类理解不了的东西，我们只要训练 AI；只要有强化学习的反馈信号，我们就可以训练 AI 去理解这个 repository。

这是一个非常大的项目。Linux 内核数据库，或者你们想做的一个价值一个亿的产品。但这里有个关键的转变：不管这个项目多大，AI 在开发它的时候不会一次就把它变成另一个产品。一旦软件系统已经在工作了，你一般就是给它增加一个功能、修改一个功能。

这跟 Git 的 philosophy 很像：Git 管理文件目录、快照和快照之间的关系，希望我们小步前进。每做一件事情——修一个 bug、改一个文档——都产生一个 commit。这样就可以在多个人之间协作，每个人可以自己产生自己的 commit，然后用 rebase、merge、fast-forward 或者普通的 merge，把整个项目的修改历史创建成一个可追踪的东西。

如果以后我们也不要用文件了，那我们真正需要的是：让 AI 自动维护所有的 artifacts 之间的**一致性**。比如代码和文档必须一致——文档说这是 linked list，我的实现里面就必须是 linked list；文档说要对 A、B、C 三个方面测试，那测试用例里就必须有 A、B、C。它们全都是关联在一起的。

**这就是 traceability 的核心。** 项目难维护的根本原因不是版本管理工具不够多，而是它管的是文件与文件之间“碰巧在同一个目录”，不是实体之间“应该保持怎样的关系”。

### V0 到 V1：AI 如何只看见它需要的那一小部分

既然我们希望小步前进，那“怎么走一小步”就说清楚了。当我们说要做一小步的时候，我们其实知道这一小步是干什么的。所以你可以跟 AI chat：我现在发现它有个 bug，或者我今天对这个幻灯片的样式不满意。

这就是一个小步。

在一个大型的软件系统里面，绝大部分内容跟这个小步是没有关系的。比如我现在对这个幻灯片的样式不满意，你们可以直接看我的 repository 顶层结构：我有一些 assets，有缓存系统 `.cache`，有 P1、P2、P3、P4、P5，还有一些脚本等等。

任何软件系统，当你只做一小步的时候，你只需要看到这个系统的一小部分，大部分东西应该是无关的。既然无关，就可以让 AI 根据我们的 chat，把跟我相关的东西摘出来。它可以知道我现在需要的是这个文件、这个测试用例、这个文档，其他的东西都不需要了。

AI 有什么能力？**Everything is code，content as code，code 可以表达任何东西。** 所以 AI 可以根据我的 chat，生成一个跟我要改的这一小步相关的 view、一个视图。

你们学过的各种系统里面的概念，还是有用的。数据库里面有一个叫 view 的概念：我的数据在这里，但我可以创建一个不一样的查询，把它以另一个形式展示出来。这里就是同一个很简单的想法——我希望把这些数据以另外一个形式展现出来，只不过当我看到的时候，我看到的不是代码、文档、这些文件，而是一个可视化的看板。这个看板列出了和我这个小步相关的一些东西，然后问我要改什么。

一把改完了以后，同样从一个 V0 到 V1。它还是在一个 repository 里面，但是这一小步就会把这些相关联的地方改掉：比如我要增加一种类型的测试用例，那它可能就会在测试用例的地方加一些，在另外几个地方也加一些，还有些地方可能要改掉。它从一个一致的状态——各种复杂的关系——做一次小步的修改，到下一个版本。

这样软件工程就又变了，彻底变了。我觉得未来有可能发生：在 AI 内部，它是这样生产软件，从此以后我们也就再也不要看代码了。

**这不是“以后不用学编程”，而是“以后编程的对象可能变了”。** 你现在看现代 IDE，比如 Cursor，我其实还蛮讨厌的：它打开默认就是 agent mode，原来那个我们熟悉的 IDE 就没有了，强迫你用一种类似 chat 的方式去沟通。但我毕竟比较精通“古法编程”，有时候我还是对代码有一些掌控欲——这可能是不好的、可能是不对的——但未来这可能是一个途径。

你们当然会焦虑：如果未来真的一两年以后有个公司把这东西做出来了，我们学那么多东西怎么办？

其实你会发现，在创造这些东西的过程当中，用的都是你们学习的那些经典、集大成的 computer science 课程。我刚才说的数据库里的 view，数据库里借用的是 entity 和关系，然后我借用了 Git——**用 Git 就说明这个模型没有变。** Git 长期开发经验告诉我们：要一步一步向前。

如果在这个模型底下，我们是大步向前，那就惨了。当然也可能发生：模型非常强，一个非常大型的项目，一步就变成下一个了，这个怎么做我们现在还不知道。但至少在初期，我们可能还是要沿用过去的、大家积累的软件工程智慧去小步向前，然后通往那个“极乐世界”。但我还是相信这个极乐世界确实有可能是能达到的。

### 为什么会有人问：学生根本用不到 rebase？

这就引出了我觉得在大学里面挺有意思的一个评论。有个同学已经毕业了——因为前几节课我问过大家什么是 `git rebase`，结果大家都不知道——他提了一个 valid point：学生时代大多数人不会和他人共同合作，也就是做作业，所以 rebase、merge 的使用场景很少。

这个 point 是对的。你们做作业的时候确实不会。那我的回应是这样的：如果你真的往外面的世界走一走，会发现互联网开发者社区铺天盖地都是文档。你一定会在某一天看到别人的项目里有一个 `CONTRIBUTING.md`，也就是仓库根目录下的一份贡献者指南，通常回答“我怎么参与这个项目”。它里面就有项目的总体结构、分支和提交信息、PR 的规范和流程。

如果你看过很多项目的 `CONTRIBUTING.md`，你随便打开看一眼就会发现，里面的东西都知道了。如果你不知道，有一天你一定会看到一个项目里说“我们必须要在自己的分支上 rebase”“禁止你创建那种分叉的 merge”——那时候你就会知道 rebase 是干什么的。它会告诉你“我们要保持现行历史”，这就是为什么禁止分叉的 merge。

现在社会变得太快了。有一种学生其实不是在批评大家，是因为你们上高中的时候，老师不教那些考试不考的东西，为了升学的利益最大化，这是正确的，没有错。但是你们到大学以后，如果还带着这个思维，就会有这样的 gap，一种“新人类”和“旧人类”之间的 gap。

当然我相信每一个同学都可以成为新人类，只需要去注意更多的东西。因为现在我有一个危机：**AI 时代的斩杀线以下，价值全部归零。** 当然现在斩杀线可能还斩不到各位 985 同大学 computer science 专业的同学，但那些低级的智力劳动，比如会计从业者，好像我看过一个报道说中国可能有 1000 万会计从业者——这个行业里面顶端的人暂时肯定还没有威胁，但底下大量的人面临被 agent 替代的危险。

所以你们需要在这些经典的课程上，不管是操作系统、编译器还是软件工程，学到一些经典的东西，最终形成你们自己的理解。

### 从 merge 到 rebase：修改为何不等于 commit

好，我们继续回到软件工程。我刚才畅想了一下未来会发生什么，但现在我们还是用 Git。

Git 管理的是快照，也就是一个目录、一个整体的一个快照。我可以在快照上面做开发，做开发它要求小步。现在有一两个开发者，一个是 A、一个是 B，我们就可以独立地在两个分支上开发。

这个东西就是 commit。如果你想把它们合起来，在 Git 的原始模型里，rebase 相对不那么提倡。Git 原始的模型是：创建一条两路 merge，有两个 parent，继承这两个修改。

但这又带来一些问题。比如这个 merge 是由 A 来做的，那这个 merge 里面由 B 写的一些内容，作者就变成 A 了——它其实有一个隐藏的作者修改。如果发生冲突，在 resolve 的时候，冲突完了以后这个 change 就变成 A 完成的，B 改的代码最后 ownership 又归到了 A。这会带来一些小小的小麻烦。

rebase 解决了这个问题。让我横过来画。如果我现在有两个历史：A 同学改了两次，做了两次提交，得到两个快照、两个 delta。然后另一个同学 B 开始改。

rebase 做了一件什么事呢？比如说 A 先改了文档，然后加了测试；B 加了一个 feature，然后加了一个测试。rebase 不是直接把他们两个东西创合成一个“把两条线路并起来”的提交，而是我先试试：有没有可能把这个 feature 放在 A 的后面，加上这个 feature。

如果加上了，成功。如果我这次搬 feature 成功，我再把 test 放过来；如果成功，那它就可以一路合并过去，变成一个线性的历史。

但这有一个很大的风险。因为我可能在这个里面加入了一个测试用例，而这个测试用例和这个 feature 是不兼容的——这是有可能的；甚至就是他们改了一个地方，做了两个完全不兼容的东西。那这个时候就有可能失败。

**一旦发生冲突，这是非常危险的。** 为什么？因为一旦冲突，就需要 resolve，会进入一个 rebase 的模式。如果你进入过这个模式，你会发现瞬间自己就不知道应该怎么办了。这时候你就打开你的 agent 问：“我现在发生了什么？”Agent 会细心地给你解释。

更麻烦的是，你就算把 feature 搬过来了，你搬 test 的时候又要失败，还需要再把 test 搬过来。而且每一次你都会创建一个新的提交。每一个 commit 都有 ID。如果你是一个两路的 merge，所有的这些 ID 都保留了，你会创建一个新的 ID。但是因为你是 rebase 的，rebase 每次都会创建一个新的 commit——因为它这个快照的 base 在变。

所谓 rebase，你也就知道了：**rebase 的 base 要改掉，要把这个 base 改到这里来。** 所以它会创建一个新的 ID，每次都创建一个新的 ID，然后这个历史就变了。你会感觉到这里有一点点轻微的不一致。

问题出在哪？是我们关心“修改”，希望把修改搬过来，而不是把快照搬过来。但在 Git 里面，修改是用 commit 来替代的。一个 commit 和它的 parent 之间的关系，就叫一个修改。它没有一个专门的叫 change 的对象，所以它用 commit 来代替修改。

绝大部分情况下这都能满足。但如果把 change 也变成 first class citizen，会发生什么？

### JUJU：把 change 提升为一等公民

你就发明了下一代更好用的版本控制系统：不仅有 commit ID，甚至这个工具和 Git 底层完全兼容，你完全可以直接当 Git 用；但是它增加了一个叫 change 的概念。

每一个 change 都可以 sign 一个 change，然后把好多个 change 串起来。比如 rebase 的时候，它会把 change 直接搬过来。change 还是有可能冲突的——如果我在 rebase 的时候要冲冲突，这是解决不了的。但是因为它有这个 change 对象，它可以把这些 change 一路带下来，生成一个直接 rebase 到这里的状态，里面引入好多冲突。

但底层模型没有变，还是用 Git 的冲突记录机制，只不过它自己有一套记录方式，把所有 change 的冲突也塞进去。你可以在那里把 change 搬过来，然后在这里再 resolve。用起来就会舒服很多。

它还有一个很好的特点：它不需要 staging area。

Git 里最讨厌的是什么？我上操作系统课的时候会讲这个例子。你现在有个工作区，有一个 repository，比如你有一个 `hello.c`，你改到一半，项目还不能编译、也不能运行、测试也通不过。突然导师给你打电话：“我有一个很高优先级的项目，客户就要交不了差了，这个 bug 马上给我修好。”

你怎么办？你不应该 commit。你需要把它加到你的 index 里，然后 `git stash`，然后去修原来那个 bug。你刚修到一半，导师又打电话：“这个 bug 别修了，我还有一个更高优先级的 bug，你修好。”这时候要再 `git stash`。

所以 `git stash` 是一个 stack，里面有好多好多个提交，你需要管理那个 stack。如果你想象随时随地都在编辑这个 repository——这不就是一个 change 吗？你现在把 `hello.c` 改一改，加一行减一行，它都是 change。

所以这个 JJS 好像在干一件什么事：**你但凡改了一个字节，它都会立即做一个 Git commit。** 当然这个 commit 不会产生好多线性的历史，而是先把上一次的那个提交抹掉——上次你改了一个字节，那么上一次的提交就被抹掉了，然后你用当前的修改去替代它。

也就是说：你永远有一个当前的 change 提交的状态。一个 change 提交的状态，你就很舒服了，连 staging area 都不需要了。

这是一个非常好的设计。从“我要把 change 作为 first class citizen”开始，你再往后推，就可以发明自己的版本管理系统。当然这不是它的全部，还有一些别的路线可以推导出来。

你们适当的时候可以质疑一下：Git 有没有哪里做得不够好？如果可以做得更好，还能做怎么样的设计？我觉得这是很有趣的一些设计。你们可以在 agent 的带领下，或者说在我给你们一些 motivation 之后，把最重要的 prompt 交给 agent：“我如果要用 JJS，我想从 change 开始理解。”然后你看它的 tutorial，它其实一上来就会告诉你它没有 staging area 等等。你管理这个版本会更自然。

**它对人类更友好，实际上对 agent 也稍微更友好一点。** 所以我觉得你们作为 AI native 的人类，能够淘汰掉我们这一代人：因为我这一代人已经形成了 Git 的肌肉记忆，比我更老的一代人已经形成了 SVN 的肌肉记忆。一旦人形成肌肉记忆以后，要把习惯掰过来就很困难了。

比如我现在对 Git 是有肌肉记忆的。但是我即便能够理解 JJS 的概念，甚至我理解得比你们这些初学者还要更好一些，我还是可以从我的 first principle 去思考它，自己相当于 virtually reimplement 这个系统。但我即便能够理解，我也没有足够的时间再去训练另外一个肌肉记忆。

**所以你们是反过来的。** 你们应该趁现在还没有形成记忆，有记忆的时候就直接去用那个对的东西。人类历史都是积累的：SVN 实际用不下去了才用 Git，Git 发现了它的缺点以后才有 JJS。所以你们可以先用肌肉记忆记住一个最正确的设计，然后再去理解这个设计。

当你再回去想的时候：“原来 Git 这么蠢。”在 Git 出现的时候，大家会觉得 Git 这么先进——它是一个 persistent data structure。SVN 就是 SVN，从一开始它从纯纯的、从文件那条线就走错了。等到 Git 的时候，大家觉得很先进；到现在再回去看的时候，你才发现原来 Git 也犯了一些设计上的错误。当然，这是因为它最早的时候没有想到 rebase 会有这么大的 impact。它有 merge 就已经很好了，就能解决它手上的问题了，所以它可能没有把这个概念模型想得更加清楚。

**“先记住一个最正确的设计，再去理解为什么它不对”——这是一种更好的学习顺序。** 我刚才说的这些，其实就是我们在创造这些东西的过程当中所做的事情。你们在学东西的时候，尤其在 AI 的辅助下，可以不断地往前走、往前走、往前走。

但这门课不是软件工程，是生成式软件工程。所以我们真正要做的事，是在 agent 的时代再次重新设计版本管理系统。

### Git 的人本假设在 agent 时代失效了

你可以让 agent 用 Git，也可以让 agent 用 JJS。那对人类来说 JJS 是一个很大的进步，但对 agent 来说可能进步相对小一些，因为 agent 很会 rebase 这些操作。

那这个时候，你看我们一路走过来：SVN 有局限，Git 有局限。那在 agent 的时代，我们的局限和要破掉的改进是什么？

**刚才所有的版本控制系统都有一个假设：它们的使用者是人。**

人类有什么特点呢？人类是一个 single-threaded 的生物。我一直在上操作系统课讲并发程序的时候打比方：你把线程想象成一个人，你的线程可以访问共享内存。访问共享内存时，两个基本操作是 load 和 store，或者说 read 和 write。我可以从一个变量里读一个值，我把 X 读到我的临时变量里；或者我可以写 X 等于 1。这两个操作是不能同时进行的——我不能说既读一个又写一个，这样就需要一个原子指令了。

绝大部分的 shared memory access，你都能想象成人是什么。我如果想要观察这个世界，我对不起，我手要抱在背后，我只能看。等我看完了，比如说我看到这个同学在这里，我想要对他施加一个效果——比如我想用这个粉笔导弹射击他——那当我真正要 write、写一个变量的时候，我必须要把眼睛闭起来。

**而我把眼睛闭起来扔的时候，注意我读到的那个值其实已经失效了。** 那个值已经是旧的值，是我上一个时刻读的。从上一个时刻到这个时刻之间，可能经历了很多事情：我可能被换 CPU 换下去了，被中断打断了，换了另外一个线程上来执行，可能执行了一秒钟以后我才恢复过来。但我恢复过来以后，在寄存器里面看到上次读 X 等于 1，就把那个粉笔扔出去了，那很有可能就是扔错了。这就是 single-threaded。

当多线程的时候，多线程共享内存带来了无穷的问题。其实人类也是一样，人和人之间是有无法逾越的物理屏障的：你不能理解我的思想，我也不能理解你的思想。我就是一个独立的个体，由分子把我很强地连在一起。所以我们只有一双眼睛、一双手、一张嘴。

那么，我们在编辑这个代码库的时候，以这种方式编辑代码库产生 change，就是以小时为单位的。一个软件公司负责一个模块的开发，可能多也就十几个人，十几个人已经是一个不小的团队了。那十几个人每个人以小时为单位开发，最多也就是以 10 分钟这样的单位产生一个提交。

好，那 10 分钟为单位产生一个提交，意味着这个速度会比人和人之间沟通的速度慢很多。因为一个 team 工位都在一起，你们研究生的工位都在一起。你马上要写一个东西，要写一两个小时，你在写之前肯定跟师兄说一声：“师兄，我要干个这个，行不行？”十秒钟、三十秒钟，师兄说：“行，你去改吧，我们现在不再改。”或者你们如果去厂里面打工了，厂里面可能每天早上都要开会，每天早上的 leader 都会把任务分配出来：今天我们要干什么事情，你做什么、做什么。提前在半小时的时间里，你划分了一个 scope，把项目切开，你领了其中一部分走，然后你就去产生 change。

当然这是古法编程。在古法编程的时代，你看到前面那个 `git stash` 的例子就是一个合理的设计：导师给你打电话，这件事情是可能发生的；但你在修到一半的时候，导师再给你打电话，这件事情是不太可能发生的，发生概率很低。绝大部分时候你的 `stash` 里面就一层。如果有好多层，你关起来其实挺麻烦的，还有一点麻烦：你还需要去 rebase stash。所以你会尽可能地保证这个 stash 不要太深。因为你可以拒绝一个工作，或者说你手上有一个更高优先级的工作，我现在对不起，我不能干这个事；等你干完了以后，你自己可以排一个队列。

**所以 Git 是给人用的。**

但是在 agent 的时代，这件事情变了。如果是一个 agent team，单个 agent 生产这个 change 的速度远远快于人：它生成 change 就以分钟为单位，甚至更快。有时候你让它 fix 一个东西，在上下文是热的时候，可能就几十秒钟。GPT-4o、Flash 什么的，它干活的时候就几秒钟就做了。

**那以秒级为 agent 工作，以秒级就可以产生一个原子提交。** 并且你可以轻易地得到一个 10 倍、100 倍的 agent team 的时候，Git 或者 JJS 这样的、和 Git 兼容的、为人设计的模型，就有点跟不上了。确实是有一点跟不上这个速度。

就算是可能大型的项目，它有一些门控——我写完了以后，改完这个部分以后，它必须要经历一个测试的流水线，那个测试可能本身就要运行几分钟，那可以放缓 agent 提交的速度。但毫无疑问，agent 加速了软件开发的过程。

**那如果 agent 加速了软件开发的过程，我们应该怎么样为 agent 设计版本管理系统？**

### 两个 tmux session：把 agent 当成独立开发者

首先我们可以让 agent 沿用人的模型。每个 agent 都有一个自己的开发计算机——A 这有自己的开发计算机。我们把 single-threaded 的人类和 agent 做一个严格一一对应的类比：让它有一个独立的电脑，可能是个容器，把它放到某个 `.git` 的 remote 上。然后你直接 instruct agent，说：“好，我的 remote 仓库是在 Git 的。你现在就是一个单人开发者，你现在可以从 tmux 里面收到命令。如果你收到命令就可以开干。”

所以这件事情其实非常容易实现。比如你开一个 tmux session，让 A agent 立刻开干。现在我来讲一个 `AI agent` 时代有点什么意思的事情：

**每个人都是领导。** 我是 master，现在有两个 tmux session。我可以想象在实际开发的时候，这两个 tmux session 都是位于两台不同的机器，或者不同的容器。它们物理上隔离，看不到世界上其他的人。

可以给每一个都起一个名字，比如 `coding agent`。你看他们两个就开始工作了。当 AI agent 变快的时候，你要想一想：如果你的指挥发生一点点差错，或者现在一个流行的 paradigm 是一个监工的 agent，加好几个子 agent——比如说为了最大化模型的智力，防止 AI 生成你不想要的东西，会放两个比较强的模型：由 Codex 来设计，然后让 Claude 来 review，让它们互相打架，达成一致。

你只要开两个 tmux 就行了。你的主 agent 负责协调，观看它们的输出，或者总结报告，然后往里面 inject prompt，多 agent 就这样转起来了。

然后你看一下这个 repo status。如果你让大家都工作在同一个 Git 仓库上，就会有一些麻烦。但如果他们工作在不同的 repo 上，就是完全可以的：他们可以合到远端、拉取别人的提交，冲突了会自己修复，必要的时候甚至还可以给这个 master agent 发消息。

**你立即就可以构建出一个这样的多 agent 系统。** 那么相应的，Git 里也有一些 work around，比如 Git 就有 work tree 这样的功能。所以我就可以问 agent：“Git work tree 可以改进这样并行的工作方式，那么能让这两个 tmux session 都工作在 work tree 吗？”

### 提问本身就是关键

**提问是关键。** 你们甚至可以今天早上走到教室、看微信公众号的时候，看到上面说 Git work tree 或者提了一个什么 sandbox container，你就可以立即让 agent 帮你试一试，然后来看一看它在做什么。

“这不是一个相对来说比较容易的任务吗？” OK，它确实是在写，写脚本。它把 `pwd` 退出来了，应该 OK 了。

### Git work tree：让 agent 各有各的目录

这是当前的 `git work tree`。Git 允许我们创建一个工作树，你可以想象它连接到了一个 remote，就是一个 Git repository。然后我可以在这里面做独立的提交，在一个隔离的环境里做独立的提交。

**请注意最后这个细节：work tree 里的 `.git` 是什么？** 大家应该知道 `.git` 是什么——它其实是一个目录，里面有 `logs`、`objects` 等对象。主仓库的 `.git` 目录装着所有 Git 的历史数据，而每一个 work tree 里的那个 `.git`，指向的都是同一份 Git 历史。

**所以 work tree 的本质是：不同的目录，共享同一份历史。** 你在一个 work tree 里提交，另一个 work tree 能立刻看到新的 commit；但两个目录里的工作文件是隔离的，互不影响。这正是 agent 时代所需要的：多个 agent、多个隔离工作目录、共享一个远端仓库。

到此为止，我们完成了从文件系统、Git、JJS 到 work tree 的一整轮梳理：**版本管理的发展历史，本质上是对“谁在使用软件、谁在修改软件”的不断重新建模。** 从人，到 agent，都是如此。

## 让版本控制跟上多 Agent 的速度
> 对应块：BLK08 | 覆盖分集：P05下 | 块标题（分集名）：《软件仓库管理（续）：规模化协作实践》

做 AI 编程时，我们已经能把几个 agent 放在不同虚拟机里，让它们同时改一个项目，甚至能通过 `tmux` 共享本地会话。做到这一步，接下来该做什么？

再追问 agent，我们就会发现：它还会把 `.git` 当成一个只有特殊格式的文本文件，里面有一条指向 `v-tree` 的记录。初看这像是在讲文件格式，真正值得关注的却是其中的协作机会：多个 agent 的工作可以先在本地彼此可见，不必立即 `pull` 和 `push`。即使如此，真正把结果合到一起时，仍然离不开 `merge` 和 `rebase`。

**Git 尽量复用了操作系统的文件机制。** `worktree` 就像依附于原有 Git 目录生出的微型 Git 目录，里面依然有 `HEAD`、`index`、`lock` 这些部分，但让工作空间与主目录分开。这在 agent 时代突然变得格外有用，因为大家真正需要的正是“并行工作、最后合并”的协作方式。

不过，工作树只是 `workaround`。一旦有多个 agent 组成的 team 或 swarm，我们就必须回头再问：为什么需要版本控制？

### 人的限制塑造了今天的版本控制

人类做事的速度很慢。一个很小的团队，哪怕只有一个团队，大约也要十分钟才能产生一个 commit。人与人的沟通又很贵，所以每天早上要开会同步进展，再把任务分下去。

更麻烦的是，开过这个会也不保证大家真的理解一致。室友向你请教一道数学题，你明明会做，却未必讲得明白；除非你很擅长共情，能够站到对方的角度思考。沟通成本高，就会卡住整体产出。

这也解释了大公司、尤其是初创团队为什么未必随着人数增加而线性变快。系统大了、人多了，沟通效率下降，产出速度自然也会下降。一个一百人的团队，可能只相当于十人团队的两三倍效率，已经很不错了；它无法直接达到十倍。

> **结论**：Git 里的快照、小步前进和可追溯的小 commit，并不是凭空设计的规矩，而是为了在沟通昂贵、协作缓慢的条件下，仍然让项目能够向前走。

我们为什么喜欢小 commit？因为它们都可以追溯。一开始改一个 `title` 也提交一次，做别的事情再提交一次，等出了问题，就能回到某个人做事情的时间。那个人可能还记得：那天早上开过会，自己接到了这个需求，当时沟通在哪里出了问题。大家找到那段沟通记录，再讨论这个地方应该怎么修。`git bisect`、`git blame` 这类特性，本质上就是为人的记忆和协作设计的。

这里很容易搞错：**commit 越小越容易追溯，但不是“改一行就一定值得单独提交”的机械规矩。** 真正重要的是提交能对应一个可以解释和回退的阶段，而不是提交数量越多越好。

### Agent 不需要甩锅，但仍然需要快照

换成 agent team 或 agent swarm 后，模型发生了变化。

人可以 `blame`。这件事做多了，人可能要被开除，实习生也可能背锅；agent 却没有被坐牢或被开除的能力。我们不再需要用 `blame` 去惩罚谁。项目只要向前走就行：某个地方错了，修复它；如果有时连“到底是哪次提交引入错误”都不重要，也就不必一直追溯过去。

现在的 agent 甚至往往是相同模型的克隆体。同一个 prompt 让它们做同一件事，结果可能有些细微差别，但方向性上大概率会收敛到相同结果。于是，历史的价值可以不必停留在“谁写错了”，而转向“我怎么把它修好”。

但是，**快照绝对不能因此删掉。** 如果方向走错，又没有保留历史快照，等你一路往前走了很远再回头，代价可能比从现在开始一点点修还大。要保留快照，要不断向前，也要合并、合并、再合并；历史中值得留下的是教训，以及项目如何一步步演化。

> **定义**：在 agent 时代，版本历史仍然同时承担两件事——保存可回退的快照，以及把失败和修正沉淀为以后能复用的教训。区别只是，记录的目的不再主要是找人担责。

因此，Git 仍然是一个“向前进”的系统。每个项目都需要 repository；不管它使用 C、C++、Python 还是 JavaScript，都需要把文件管起来。未来如果重新设计版本控制系统，目标仍然是管理快照、版本和 change，只是要面对飞快的 change。

### 乐观合并：像数据库事务一样先跑起来

要把这些概念连起来，就得回到操作系统和数据库课里学过的并发控制。

可以想象两条 SQL transaction 同时运行。一条先 `select` 读取数据，另一条也可以读取；随后各自执行 Python 或 JavaScript 这类图灵完备的计算，甚至还会依据当前时间产生不同结果，最后再 `update`。这时就可能产生冲突，甚至形成循环依赖，造成死锁；数据库检测到这种情况，就可能回滚，也就是 `rollback`。

Git 的模型有一点像这种**乐观并发控制**。为什么叫乐观？因为它先假设这些 transaction 不会冲突，等执行或合并时大概率能顺利完成。就像教务系统里，每个学生读自己的课、写自己的数据；两个学生同时选课，碰到的也只是各自的数据，全局冲突并不常见。开发也一样：早上先开过会，把任务分开，merge 或 rebase 时大概率不会撞车。

> **提示**：乐观并不是保证没有冲突，而是先让彼此独立的工作向前运行；等真的相遇时，再处理冲突。对人类时代常见的低并发协作，这个假设往往成立。

但这只是“古法编程”的计算尺度。假如 agent 比人快一千倍，主 agent 一下分出很多任务，transaction 冲突会频繁得多，可能大量触发 `rollback` 和 `conflict`。这些并不是 AI 时代的大问题，agent 出错或冲突后能继续修；可是我们仍然可以重新思考并发控制方式。

### 悲观锁：快得多了，就该管住共享资源

数据库也有更保守的并发控制。操作系统课里我们怎么保护共享资源？上锁。我经常说，一把大锁保平安：访问可能冲突的资源前，先把它锁住；锁未释放前，其他想拿锁的人只能等。

这和乐观控制的“大家先跑，撞上再说”不同。悲观控制要求在使用资源前先声明锁定；释放之后才能建立后续的使用关系，形成确定的先后顺序。

如果 agent 的动作快很多，我们其实更应该偏向这种**悲观并发控制**。假设有一个主 agent，它规划好任务，马上锁住项目的某个部分。我们甚至可以在某个 Git repository 或快照上提供锁操作，把要处理的 `scope` 说清楚：现在锁住了，我做这件事需要这些资源；做完 `commit`，释放锁后，另一边才能继续。另一边如果要访问已被锁住的内容，就必须等待。这样就能大幅减少两个 agent 同时修改同一个测试或配置文件的冲突。

```text
主 agent：规划任务
      │
      ├── 锁定 scope：测试 A、配置 B
      │         │
      │         ├── agent 1 ── 修改 ── commit ── 解锁
      │         │
      │         └── agent 2：等待，直到解锁后再取得锁
      │
      └── 其余互不冲突的 scope 继续并行
```

这正是互斥锁的本质：它不追求所有任务都同时无约束地跑，而是规定同一资源不能被并发修改。如果把整个系统都用一把大锁包起来，当然会损失并行度；可是系统里有很多独立线程或任务，锁住其中一部分后，其他不冲突的工作仍然可以高效推进。**悲观不等于低效**，只要锁的范围足够清楚、还有足够多互不依赖的工作，整体进度就不会停住。

> **易错点**：不要把“让多个 agent 并行”理解为“必须让它们无条件地同时写”。并行调度和共享资源互斥可以同时存在；该并行的部分并行，该互斥的部分互斥。

那是不是应该把这个思想重新放回 Git？可以把锁加在 repository、worktree 或快照上，也可以在文件级加锁。关键不在于哪一把锁的形式，而在于调度层必须先知道：哪些任务要访问相同资源，哪些任务彼此独立。

#### 从数据库课回到软件工程

你可能会说：“AI 都会写数据库了，我为什么还要学？”答案是，仍然有用。数据库里的并发控制正说明了一件事：**速度一改变，合理策略也会改变。** 我们今天认为“假设不冲突就够了”的方式，是按照人的速度和人的协作方式设计的；当执行者变成快一千倍的 agent，必须重新评估并发模型，而不能机械沿用过去的工具。

这也是为什么我宁可花时间讲数据库和操作系统，也不愿意让它们变成“反正 AI 会写”的旁支。只有真正理解了乐观和悲观、锁和回滚的机制，你回来讨论版本控制时，才会重新设计自己的协作直觉，而不是照抄别人的命令。

不过，别把这个结论推到极端。我们**不是**要抛弃快照，也不是要把 `merge` 和 `rebase` 彻底删除。`worktree` 和普通的本地协作仍然有价值；我们真正要做的是重新评估：对于高速多 agent 的协作，快照、锁和合并应该怎样分工。

### 找到 agent 时代的“早上会议”

目前 AI 还不知道怎么做团队管理。哪怕某一天模型更强、更小、更快，算力也许有一天能够复现我们的智能，**今天的系统仍然不会一句话直接生成高质量产品。**

假设老板说：“我要做一个 AI 时代的微信，做一个社交爆款。”如果一句话真能直接吐出微信级别的产品，软件工程就死了，我们也就没有存在的必要了。这个“斩杀线”暂时还没到，所以团队管理仍然需要学。

真正难招的通常不是单纯写代码的人，而是能把任务分解的 team leader。这里的“难”有相当一部分来自协作结构：人越多，沟通关系越稠密。不是简单地说“平方级上升”就结束了——**人越多意味着协作关系越稠密，它描述的是协作结构变复杂，而不是保证严格的比例数字。** 这时要先把一个大任务拆成几个子任务，再让不同的人推进；最后还要把各部分重新组合起来，验证合在一起仍然是一个完整产品。

你也完全可以在学生时代就开始练习。现在就可以把自己当成主 agent，想清楚：

- 任务如何拆给两个、三个或更多 agent；
- 哪个部分可以并行，哪个 scope 应当先加锁；
- agent 什么时候应该提交，什么时候应该合并；
- merge 和 rebase 各自适合什么情况；
- 一条历史要保留到哪一步，才能既支持回退，又不会把不该保留的“责任叙事”带回来。

这就是“早上会议”的 agent 版本。它的核心不是开一个形式化的会，而是先理解整体目标，再建立协作结构；等最后把十个小团队拼起来，架构仍然能成为同一个产品。

> **结论**：版本控制是工具。它把人类过去多年软件工程的最佳实践蒸馏出来；我们要做的不是被命令牵着走，而是在这个工具上逐渐形成自己的软件工程直觉和经验。

### 换个载体：让 Git 进入产品

学 Git 学到能区分乐观与乐观之外的冲突、知道该把 `scope` 落成实际的历史，就不能只把它当作提交代码的工具。我们可以把它放进产品功能里。

先从一个很小、很具体的 playground 开始。儿童可以在里面写代码、可视化会随代码变化，代码错了便能直接定位问题。要把这样的产品卖给小学生，核心是提供成本可控的付费增值服务：基础环境尽量便宜，真正卡住的时候，用户可以点“我要助教”，由 AI 提供个性化指导。

这里的关键不是在页面上多堆几个 API，而是把“学生每次编辑了什么”“什么时候运行了、切换了什么”“助教在某个提交上做了什么”记录下来。Git 本身是天然的历史载体。

我很喜欢 Overleaf 协作文档的一个功能：可以把工程当成 Git repository 导出。改论文时，我能把它克隆到本地，打开 Codex，交给 agent 处理每一个 `.tex` 文本文件里的语法错误，再让它把论文改好。网页协作与本地 agent 协作，都依赖同一份结构化的可追溯文件历史。

把它换成 playground 也一样：学生每编辑一次、运行一次或切换一次，就自动产生一个 commit。助教介入时，不用覆盖学生的代码，而是在当前提交上开一个分支，把 AI 的点评、生成的代码和修改过程放在分支上；助教完成后再通过 merge 回到主线。

```text
主线提交 A ──────── commit B ──────── commit C
                                      │
                                      └── 助教分支：点评 / 建议 / 修改
                                                  │
                                                  └── merge 回主线
```

> **结论**：在产品早期，Git 带来的版本管理能力可以比数据库更重要。Git 提交成本很低，完全可以先在代码库里探索目录格式、commit message 格式和文件的组织方式；等整个结构收敛、性能真的成为瓶颈时，再考虑迁移到数据库。

这也是 GPT 给出的第一版产品设计的启发。GPT 是一个语言模型，可它偏向于“给出一个正常的系统结构”：API 应用、关系数据库、对象存储，再配后台任务和任务表，课程包与完整轨迹放在对象存储里，任务量小的时候数据库任务表就够了。这是一种非常正常的软件工程设计，但并不是每一次都需要。

比如我自己回复邮件的流程，就没有先建关系数据库。我的 agent 先收邮箱，把 `email id` 放到共享云盘；云盘里保留邮件原文、回复草稿和分类结果，再由下一级流水线继续处理。不同流水线之间通过云盘协作，先要弄清楚系统有几级流水线、它们怎样交接数据。

假设后来我特别喜欢云盘，于是希望邮件、资料和云盘保持同步。这个变化可能让所有东西都集中到数据库的方案需要大面积调整；而在文件系统方案里，先改变目录、同步规则和流水线之间的交接方式，通常更容易看清代价。**我们不是要把数据库判成坏设计，而是在需求变化时判断迁移成本。** 在早期阶段，使用文件系统能减少概念翻译，降低人的心智负担。数据库 schema 对我们不熟时，每次重构还可能要求 agent 做数据库迁移；目录结构的调整，我们却能直接看见、直接移动。

所以不要在需求还没有被验证时急着引入最重的组件。先用最小的方式承载真实需求，等结构稳定、性能成为瓶颈后，再决定是否迁移。这个原则也直接回答了“需求变化时，什么叫好架构”：好架构不是当前功能最全，而是需求发生变化时，能用较小的代价调整。

### 随便开一个 Agent，为什么会得到一堆“slop”

我们常说 agent coding，但**项目的早期阶段肯定不能先用 multi-agent。** 早期阶段你就是包工头：先找一个能力最强、你真正用得上的 agent，和它多轮对话，把事情想清楚。现在开始干，比什么都好。

为了观察 AI 的直觉，我曾把它直接带进一个课程作业：一个“持续为你工作的个人助手”。在 AI 的直觉里，一线模型可能先进入 `plan mode`，和你确认一些事实，再生成 workflow；有些工具会生成一段 JavaScript 或 TypeScript，里面有一个 `agent` 函数，用自然语言组织任务，甚至在循环里执行多个工作流。这看起来很厉害，像“直接开干”。

可问题恰恰出在直接开干上。

给模型的每一句 prompt、每一个词，都会进入 self-attention；现在被训练得很好的 AI 有一种强烈的倾向：它会努力遵循你给出的每一条指令。于是你给它一份开放的需求，它可能做出一个**确实满足指令、但其实不是你要的东西**。

在这份作业描述里，真正重要的不是那些接口、表格和目录，而是一句隐藏在字面要求后面的要求：“实现一个持续为你工作的个人助手。”如果我真正想要的是一个学习助手，那最重要的问题就应该是：你最想让它帮你解决什么痛点？对我而言，一个月以内最大的痛点就是高效地学习和复习——从外部收集资料、层次化归档，最后给我一个合适的界面。

因此我会更明确地提出：我要的是浏览器操作能力，能够在各种网页上处理信息；外部信息要能收集、综合、总结，还要根据我的学习进度判断哪些部分已经实现、哪些还没有。交代清楚后，模型才可能真正实现我想要的东西。

> **易错点**：把 `specification`、`intention` 和 `intent` 混合在一起，会让模型逐条满足字面要求，却偏离真正的意图。如果最终要的是学习助手，“浏览器操作能力、外部信息收集、综合总结、进度感知”这些要求都是围绕那个目标展开的，而不是另起一个普通业务系统。

如果用最原始的方式开始一个项目，AI 很容易落入 `slop` 的陷阱：它可能直接做一个“API + 数据库 + 对象存储”的完整业务系统，或者连 Git repository 都没有初始化。对代码进行 review 时，从 README 看，入口层、编排层、能力层、数据层的每件事似乎都做得正确；可这个系统看起来已经像教务系统、教育系统，或者普通业务逻辑系统了。它满足字面要求，却没有满足我的真实意图。

这不是某一个文件写错了，而是**从零构建软件时，最大的风险之一是构建了一个没人想要的东西。** 如果一个模型烧掉不少 token，交付了一个功能齐全但方向错误的产品，那么我们不能靠继续堆功能来修复；先要把 intent 写清楚，把需求收敛到最小的验证版本。

#### 从第一个 Feature 开始，而不是从第一份数据库开始

真正从零开始构建时，要做的不是从零堆出完整系统，而是找到一个 MVP，也就是 `minimum viable product`，做出最小的验证版本。MVP 的作用不是证明所有架构都能工作，而是逼迫我们回答：哪些需求是真正不可省的？

对个人学习助手来说，第一版最重要的可能只有两项：提升学习效率和工作效率。只围绕这两项构造最小版本，第一版可能完全没有数据库。文件系统膨胀后，完全可以再说：“按照现在这种数据组织方式，帮我提炼出一个数据库。”这个问题在那时再解决，迁移是演进的一部分；而不是在第一天就承担 schema 和数据迁移的代价。

当然，`slop` 不是“代码跑不起来”才叫 slop。一个 AI 生成项目的问题往往更隐蔽：README 看起来完整，分层看起来漂亮，功能看起来丰富，结果却在解决错误的问题。**判断 slop 的关键，不是代码量或页面数量，而是意图是否对齐。** 项目越完整，方向错了的时候，误导性反而越强。

从零构建软件的真正要求，可以压成一句话：**以不变应万变。** 你现在设计的架构或流程方法，能不能抵抗未来需求发生根本性变化？比如未来 AI 助教可能是文字的、图像的、有交互的，也可能没有交互；如果核心需求在变化，你还能不能让架构以尽量小的代价适应？

这也解释了为什么“看似规范”的数据库方案不一定合适。它可能遵守很多 best practice，遵守很多初始化时的架构原则，却不一定能承受尚未出现的协作方式、数据组织方式和服务变化。真正重要的不是今天有没有一个漂亮的表结构，而是明天需求变化时，哪一部分需要重写，哪一部分可以保持不变。

### 版本管理要记住什么

数据库课与操作系统课教的是系统如何设计，软件工程还要再问一步：**这些设计如何面对未来的需求变化。** 数据库为什么用这种并发控制，操作系统为什么加锁，Git 为什么保留历史，都有自己的原因。但到了软件工程，不能只满足于“当前结构正确”，还要让系统能以尽可能小的变化适应变化。

无论古法编程还是 agent 时代，版本管理都要记住三件事：

> **记住现在，记住历史，记住教训。**

“记住现在”意味着你有一个 repository，能把文件管起来。“记住历史”是为了某天某个东西看似该被删掉，最后却证明仍然有用时，还能把它捞回来；也能从提交序列里看到项目如何演进、哪里失败、为什么回到另一个点重新尝试。“记住教训”则是让失败和修正留下可复用的经验：下一次该怎么做，应该从第一步开始迈出多小的一步。

版本控制本来只是工具。无论我们采用普通 Git、worktree，还是未来带乐观锁或悲观锁的版本控制，真正困难的仍然是进度，是团队管理。正因为如此，多 agent 项目早期不要把任务直接丢给一群 agent 就宣布开工。先回到管理和协作的脑袋里：选一个最强的 agent，把任务分解、提交策略、锁的范围、merge 和 rebase 的时机都想清楚，再让多个 agent 展开。

本地开发的起步方式也很简单：创建一个空的 repository，先让自己的产品想法有地方沉淀；然后一步一步往前走，保留快照，留下教训，必要时换一个方向重新开始。早期 prompt 对项目走向的影响最大。一次看似随手的“MVP”“数据库”或“直接开干”，可能决定后面很长时间是在修正方向，还是能够顺畅演进。版本管理做得足够好，agent 才真的能持续为你工作。
