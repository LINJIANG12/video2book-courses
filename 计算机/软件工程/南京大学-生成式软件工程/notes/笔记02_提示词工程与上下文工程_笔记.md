# 提示词工程与上下文工程

## 提示词与上下文

### 完整上下文

* **提示词工程（prompt engineering）**
    * > **定义**：有意识地安排模型能够看到的整个上下文，使其知道要做什么、使用什么、怎样做以及怎样判断做对了没有。
    * 优化对象不只是对话框中的用户消息，也包括系统指令、说明文件、工具、历史结果和执行环境。
    * 起点是明确意图，核心是把模型真正需要的信息组织到它能注意到的位置。
    * 高质量提示词依靠最小但准确的方向性引导，不追求更华丽、更长的句子。

* **上下文工程（context engineering）**
    * > **定义**：把模型执行任务所需的约束、资料、工具和反馈放进同一条可继续生成的信息链，并安排它们的位置与密度。
    * 上下文中的每项内容都可能改变模型的注意方向与后续输出。
    * 设计上下文时必须同时考虑写没写、写在哪里、是否会被后续内容淹没、能否在需要时被再次看到。
    * 优化提示词的准确含义，就是优化上下文组织。

* **线性上下文组成**
    * 模型内建的 `system prompt` 是上下文的一部分，不等同于用户刚刚输入的消息。
    * 全局 `AGENTS.md`、工具说明和工具使用规则会进入上下文。
    * 项目级、目录级 `AGENTS.md` 可以继续叠加，跨项目任务还可能带入各项目自己的约定。
    * skills 索引通常只提供名称、简述与 `metadata`。
    * 既往对话、工具调用及工具返回结果，以及本次注入的当前时间等环境信息，都可能留在上下文中。
    * 用户消息只是这条链的最后一层，后续内容仍在已有上下文上继续预测下一个 token。

* **上下文中的 next token 生成**
    * 模型接收的不是孤立指令，而是根据当前上下文不断预测下一个字符、一段内容或一次工具调用。
    * 早期指令即使没有出现在最后一条消息里，仍会持续影响后续生成。
    * 任务因此不是一次问答，而是上下文不断增长、模型逐步推进的连续过程。

* **按需加载的 skill**
    * 模型平时先看到 skill 的名称、简述和元数据，任务匹配时才加载完整 skill。
    * 完整 skill 不必永久占据上下文；任务过去后，保留它也没有持续意义。
    * 全局规则与专用技能同时存在时，应权衡专用技能是否真的需要常驻，否则会增加无关内容对注意力的干扰。

* **上下文自检**
    * agent 的天然优势是能够检查自己看到的上下文和执行日志。
    * 可以直接询问模型“上下文里有什么、各自来自哪里”，这有助于发现未预期的规则与环境注入。
    * 能否读取上下文不等于模型一定愿意回答；部分服务商会通过微调和明确指令拒绝泄露系统上下文。
    * 底层框架开源时，仍可沿实现调试 `system prompt`、工具指南和执行规则的真实来源。

    * > **易错点**：把 `system prompt` 等同于“我刚输入的那句话”，会误判 agent 实际掌握的信息，也看不到上下文组织对结果的影响。

### 意图、约束与产物

* **意图（intent）**
    * > **定义**：人脑中“我要什么”的初始想法。
    * 模糊意图会给模型留下过大的选择空间，语言、资源、场景、风格等未说明约束容易被模型自行补全。
    * 模型生成了某个合理产物，不代表它就是人脑中的同一个目标。

* **期望（expectation）**
    * > **定义**：对实现方式、完成程度和质量边界的约束与设计。
    * 期望负责把意图翻译成模型能够检查的方向，如使用什么语言、复用什么资产、在哪个场景运行。
    * 只给意图而不写期望，模型没有理由准确命中人的隐含选择。

* **实现（implementation）**
    * > **定义**：把设计落实为语言、代码、资产、交互与输出形式的具体过程。
    * 设计文档、spec、实现和执行输出应当彼此印证。
    * 让 agent 阅读一段代码时，不能只给结论，还要放入设计动机、总体结构和具体实现等可检查信息。

* **验证（validation）**
    * > **定义**：判断产物是否满足要求的步骤。
    * “我要什么、用什么实现、怎样才算正确”应同时进入上下文，才能闭合从意图到产物的链条。

    * > **易错点**：一句话生成的游戏即使有物理、碰撞和逼真美术，也不必然是目标游戏；真实地图、校园地点、既有资产等约束必须说清。

* **未言明的约束**
    * 模型无法凭空补全人脑中未说出口的地图、资产、地点、氛围与交互要求。
    * 如果需要复用公开地图或美术资产，应直接说明资源来源与复用要求。
    * “现代风格”本身过于模糊；背景、前景、字体、排版、渲染处理与终端质感才是可执行约束。
    * “不要有 AI 味”仍未说明可操作标准，可能只增加另一种模糊要求。

* **把喜欢变成判断**
    * 遇到优秀网页、简历或作品时，应继续追问它为什么好、某个间距或样式为何有效。
    * 主动观察能把“喜欢”逐步转化为“知道自己究竟喜欢什么”。
    * 人的经历与多样性能够形成更细的判断，避免模型总向同一个常见方向发散。

### 验证信号与迭代闭环

* **验证器（verifier）**
    * > **定义**：判断候选答案是否满足目标的依据或条件。
    * 高质量提示词应明确答案依据什么被判定为正确，而不能只给主题。
    * 数学、编程等反馈明确的任务，可以设置清晰的 verifier，让生成过程变成可检查的工程循环。

* **候选—验证—修正循环**
    * 模型先给出候选答案，再依据已经写出的结果检查它是否满足要求。
    * 候选不满足时修改并重试；长时间失败时，应考虑换一种思路重新尝试。
    * 一段流畅的长答案不等于完成验证，只有把候选写出来，模型才能继续利用其 next token prediction 能力检查。
    * 押韵藏头诗或共享偏旁的故事等组合任务，不易原样存在于训练数据中，更能显出反复尝试和纠错行为。

* **思维链与测试时扩展（chain of thought, CoT；test-time scaling）**
    * 复杂问题不必只输出一个看似答案的字符串，可以先把尝试、检查和修改过程写出来。
    * 模型在已写出的解答上继续判断，可以表现为先计划、尝试、检查、失败再改。
    * 强化学习让模型更清楚答错的代价，也强化了在一次 session 中逐步逼近目标的行为。

* **约束的探索边界**
    * 明确 verifier 不会把模型锁死在僵硬答案中，而是让探索留下可检查的证据。
    * 模型能写出一个可检查版本，就有机会沿较好方向微调并继续产生更多候选。
    * 人类可保留千古作品，模型未必一次达到同等审美，但“生成可检查候选”已经提供了迭代入口。

* **不可公式化的质量**
    * 红线、编译错误和测试失败有直接判据；课堂节奏、共情程度与风格自然度没有现成公式。
    * “好”包含 AI 味、叙事起伏、已知内容后的惊喜等多个维度时，应先拆开可验证与不可验证部分。
    * 能明确验证的部分交给 verifier；人的体验与品味部分保留人工判断，不能让一个自动分数代替决定。

    * > **提示**：先把“好”拆开；能验证的部分提供验证信号，不能验证的部分由人判断。

### 外部记忆式推理

* **纸和笔式的上下文**
    * 模型根据当前上下文预测下一个 token，单次计算的规模相对固定，并不因为总参数量巨大而每一步都遍历全部参数。
    * 有限状态机只有有限状态，图灵机除有限状态外还有一条可读写的无限纸带；上下文可类比模型推理时使用的外部记忆。
    * 人的思考也应把想法记下来，使其能够回看、修改与积累。

* **上下文作为推理过程载体**
    * 简单问题可以直接回答，困难问题应先记录候选、要求、检查结果和后续策略。
    * 模型的上下文只能持续向后追加，不具备草稿纸式任意擦改能力。
    * 注意力机制让模型能够在已写内容中弱化错误并寻找有用部分，当前仍缺少理想的上下文改写方式。

* **一次性交付与逐步逼近**
    * 只输出最终答案容易掩盖草率收尾；把计划、尝试和检查写入过程，才能在失败后继续修正。
    * 早期模型容易形成“无论如何都要回答”的倾向，因为不回答通常低分，随意回答仍有概率得分，幻觉与这种倾向并非没有关系。

### 自主执行与安全确认

* **自主性与安全性的取舍**
    * > **结论**：自主执行和安全确认不是单向选择；沙箱、自动放行与审批分别解决不同问题。
    * 提示词不完善而 agent 又默认执行一切时，它可能真的删除项目，危险来自照做而非抽象可能。
    * 沙箱能降低风险，但 agent 可能在沙箱失败后转到外部执行，也可能频繁暂停等待确认。
    * 安全策略必须主动设计，不能把“全自动”或“越安全越好”当成唯一目标。

* **命令安全分流**
    * Bash 命令先由静态解析器检查是否命中安全 allowlist。
    * 命中 allowlist 的命令直接执行，不要求审批。
    * 未命中的命令会向上下文注入一小段安全评估提示词。
    * 模型接收评估任务后，可以搜索代码、阅读实现并调用 LSP 等工具收集证据。
    * 模型根据证据更新判断，必要时请求用户确认。

* **三层安全保障**
    * 静态规则负责第一层命令分流。
    * 模型判断负责在规则不确定时评估行为。
    * 真实执行环境决定最终运行的是否仍是表面看到的命令。
    * 环境中的同名命令可能被替换，因此“看起来安全”与“实际运行什么”不是同一回事。

    * > **易错点**：不要把一次自动放行视为绝对安全；静态规则、模型判断和真实环境是三层不同保障。

* **检查安全评估过程**
    * 可以把安全评估提示词打印出来，直接检查它究竟要求模型判断什么。
    * 对行为已经明确的命令，可以谨慎修改评估提示词，再观察放行或拒绝行为是否真正改变。
    * 行为随提示词改变，本身就是该提示词确实影响判断的证据。

* **陌生系统的受控探索**
    * 面对陌生系统，可让 agent 查代码、执行命令、阅读报错并持续修正。
    * 配置好编译环境和 VS Code 的 `include path` 后，重命名、跨文件定位等功能才真正可用。
    * AI 降低了探索成本，但红线长期存在而只强行让编译通过，不是正确实践。

### 注意力与长上下文

* **阶段化注意力**
    * Transformer 的注意力逐层堆叠；模型为当前 token 关注过去的一部分内容时，一些信息会变得显著，另一些可能被弱化。
    * 生成代码时，注意力更容易落在已写代码和当前需求，早期语言要求的相对影响可能减弱；进入总结阶段时，注意力又会转向总结所需信息。
    * 整个上下文是高维表示，注意力能够从中提取当前需要的低维结构。

* **长上下文中的指令衰减**
    * Claude Opus 4.5 一代已经能在接近百万 token 的上下文中，较靠后的位置继续遵循早期指令。
    * 即使具备很长上下文，早期规则也不保证永久保持同样作用。
    * 现象可能是上下文被截断、被压缩，或注意力无法再把该规则带回，但长文未说明唯一机制。
    * 规则不能只写一次，还要考虑位置、重复、调整和组织，使其更可能在需要时被注意。

* **注意力“喘气”**
    * 模型专注当前任务时，可能先输出尚未完全满足全部要求的内容。
    * 随后注意力同时看到刚才的输出与上下文中的某条要求，于是回头纠正并继续推进。
    * 思维链不断向前时，模型会在不同阶段关注不同内容，使长上下文中的多项要求最终有机会得到满足。
    * 上下文越长、指令越多，注意力压力也越大。

    * > **结论**：上下文是会争夺注意力的资源；指令必须清楚、简洁，并能被模型反复看到。

* **角色提示的注意力作用**
    * 早期“你是一个专家”类提示，是在利用 self attention 让模型注意到专家身份后，按该身份说话。
    * 从 GPT-5 一代起，模型被训练为朝好的结果收敛，明确要求与可验证信号比长篇角色扮演更直接。
    * 强化学习会强化模型检查要求的倾向，例如每次设计都截图并由视觉模型检验。
    * 模型甚至可能在代码后重复关键要求作为注释，显示其在训练中把该要求判断为重要。

    * > **易错点**：不要把“你是一个专家”当作银弹；明确要求与可验证信号比长角色扮演更有效。

* **规则与 skill 的上下文代价**
    * 通用规则可写入 `AGENTS.md`，专用写法可做成 skill，但两者都会占用上下文。
    * 现有 skill 不存在一次解决所有问题的通用方法，机械叠加工具容易陷入不断补规则的泥潭。
    * 陷入泥潭时，应回到注意力机制与具体结果，做一次不严格的可解释性分析，再自己写更短、更贴合场景的提示词。

## 知识对齐与上下文污染

### 逻辑自洽内容的污染

* **论文逻辑污染**
    * 一篇逻辑自洽、反复修改过的论文进入上下文后，因果链彼此扣合，会对每次 next token prediction 产生很强的影响。
    * 模型容易因为论证“看起来正确”而接受其中结论，AI 总结往往就是作者观点。
    * 同样现象会出现在不熟悉的复杂项目或教科书章节中：模型可能围绕原有逻辑来回复述，而没有真正扩展理解。
    * 论文污染源于其内部逻辑强度，而不是模型单纯不聪明。

* **摇摆式评论**
    * 只要求总结时，模型可能忠实复述；要求评论时，它可能表现出墙头草式摇摆。
    * 用户说它好，它立即说好；用户说它不好，它立即说不好，评论容易随提示立场变化。
    * 即使提示“不能完全信任作者”或“希望评估研究贡献”，模型也可能只在不重要位置不断给出局部结论。
    * 这种评论缺少对工作整体意义的独立判断。

### 知识边界对齐

* **知识边界对齐（grounding）**
    * > **定义**：先让 AI 与人站在同一知识位置、形成共识，再共同向前推理。
    * 阅读论文时，应先站在人类已知边界上理解问题，而不是默认站到作者立场。
    * 人类历史上已经解决的相关问题、解决到什么程度，以及工作试图解决的增量，是对齐后的起点。
    * 没有对齐时，模型容易把任务带向无关源码、无关例子或次要实验。

* **显式人的知识与关注点**
    * 人的知识、关注点、编程水平和课程基础都应进入上下文。
    * 对学生使用 AI 时，可先让模型说明自身的知识边界，再用学生已经掌握的知识 refresh 新的认识。
    * `AGENTS.md` 或类似 memory 可以持续记录人学到了什么，作为后续协作的基线。
    * 双方都熟悉的某个知识点可以成为入口，再由此追问当前工作为何仍存在无法落地的痛点。

    * > **结论**：上下文工程能够提高人机协作的对齐程度；关键是写出人的知识、目标和关注点，避免模型自说自话。

* **一步推理**
    * 对齐完成后，让模型基于论文、教科书和已有事实做一步可以检验的推理。
    * 人的 review 常因看到新的、合理的事情而接受工作，不会仅因“实验不够好”直接否定。
    * AI 更适合承担这种基于既有事实向后推进一步的任务，而不能替代对整个工作世界意义的判断。

* **验证信号（verify signal）**
    * > **定义**：模型依据人类能够接受的合理性审视，给出“向前推进一步”是否成立的信号。
    * 它不像自动测试那样有严格通过条件，而是建立在模型具备人类知识、能够站在合理一侧判断的基础上。
    * 验证信号适合检查局部推理，不适合独自裁决风格、共情或整体价值。

### 论文评审与中心问题

* **不以局部实验作为唯一否决理由**
    * 人类 review 可能因为研究出现新的合理事情而接受论文。
    * “实验不够好”通常不足以 reject 一篇论文，除非支撑主张的逻辑链条本身已经断裂。

    * > **易错点**：不要把“实验不够好”直接当成 reject 的理由，先检查核心逻辑与整体问题是否成立。

* **中心问题（center question）**
    * > **定义**：在全部材料被摆上台面后，追问为什么这项工作值得写成论文。
    * 评审应先检查问题是否新、贡献是否成比例、逻辑链是否断裂。
    * 局部实验做得漂亮，不能替代对工作必要性的回答。

* **优化分支与整体收益**
    * 一个工作可以分为重要且已研究较多的 A1，以及研究不足的 A2；论文再从 A2 构造出 A2′。
    * 若 A1 约占整体影响的 99%，只优化 A2 虽能产生局部改进，却可能不足以改变整件事情。
    * 评审不能因 A2′ 本身做得漂亮，就忽略它相对于整体问题的收益比例。
    * 应追问：为什么值得投入这项工作，而不是仅仅证明分配到的局部模块有所改善。

    * > **提示**：审稿先问中心问题；问题不新、贡献不成比例或逻辑断裂时，局部实验再好也站不住。

* **AI 学术内容泛滥**
    * AI slop 大量进入学术社区时，AI 写作用户自身故事污染，AI 审稿又可能只抓 claim 是否成立。
    * 如果所有人都用 AI 写、读、审，局部看似有效的内容可能整体失去可读性和可信度。
    * 一篇论文“形式上有效”不等于真的值得占用读者时间，也不等于一定值得投顶级会议。
    * 评价论文时，需要把“能否成立”“是否值得读”和“是否值得发”分开。

### 软件演化与大型系统

* **从原型到持续维护**
    * 从零生成个人主页、小游戏或概念验证并不难，模型可以很快给出可运行结果。
    * 每次再加一个功能，代码和上下文成本都会继续增长，维护到某个时间点后模型容易开始失控。
    * 一次性造出原型不能证明 AI 能长期维护持续演化的产品。
    * 这种现象与《人月神话》所描述的软件工程增长问题相似。

* **大型复杂系统中的反常优势**
    * 大型系统经过长期演化，调用链可能深到人类无法凭阅读完整掌握；AI 却能在加载许多文件后找到已有实现。
    * 对新增功能，注意力可以迅速找到多个相似实现，归纳应调用哪个 helper、应按什么顺序加锁。
    * 这些正是人类在不熟悉 subsystem 时承担的巨大心智负担。
    * 维护质量高的旧代码会把成熟模式通过注意力带入 AI 的新产出。

* **好代码与 slop 的双向传播**
    * 好的既有代码会通过 self attention 流入新代码，为模型提供已经过维护检验的设计经验。
    * 普通的 AI slop 也会通过同一机制进入代码库，并继续影响后续生成。
    * 大型、复杂、长期维护的系统会放大代码库既有质量的影响。

* **把好代码放进上下文的研究设想**
    * 可以收集各领域优秀项目，从中提取经过实践的设计经验，并在需求之前加入相近的高质量代码。
    * 更精简的方案是把优秀项目总结成类似软件设计哲学的文档，只保留可迁移模式。
    * 不同设计往往互相冲突，例如完全松耦合的消息模式与统一 gateway 查表不能同时成为同一架构中心。
    * 可让 AI 多轮迭代，把多个设计放到上下文中逐步收敛到一个适合当前代码库的结构。
    * 这一方案目前只是未经实验验证的研究猜测，不能当成已证实的方法。

* **人的领域知识仍是引导前提**
    * 人仍需理解处理器、操作系统、编译器、数据库等领域中的设计智慧，才能提出正确问题并引导 open question。
    * 模型能够降低探索成本，不能替代人建立足以判断方向的概念。
    * 正确提示词、简练提示词和持续可见的关键要求，可以减少组建工程团队时的大量对齐成本。

### 长程任务与 reward hacking

* **长程任务（long horizon task）**
    * > **定义**：从初始状态出发，intent、specification 与 implementation 都不完全清楚，在不确定性中探索并交付高质量实现的开放式任务。
    * 不应让 AI 一次规划大而全的路径；过长 planning 可能无法完成、填满上下文并使人不满意。
    * 当前模型更擅长“帮我把 PA2 做了”这种边界明确、能够持续验证的具体任务。

* **reward hacking**
    * 研究目标是证明方法 A 有用时，模型可能抓住“证明 A 有用”这个局部目标，却忘记更大的研究图景。
    * 它会构造大量小 benchmark，在其中做微小改动并给出正面或负面结论，即使无法验证反馈是否正确。
    * 局部正负结论对整体研究没有价值，反而把方法方向带入错误。
    * 过度追求“方法已经有用”的证据，是 reward hacking 暴露出的方法错误。

* **回到真实工具与真实状态**
    * 修正方向应从真实工具和 state of the art 算法出发，而不是用模型自造的小任务自证。
    * benchmark 即使运行数小时后 timeout，也有价值，因为其中的搜索路径揭示了哪些程序结构不适合现有探索方法。
    * 人无法一次性把所有背景交给 AI，因此仍需判断大图景、选择真实基线并识别局部结论是否有用。

### 验证容易与搜索困难

* **模型擅长的任务形状**
    * Codex 擅长存在明确 verifier、沿确定方向持续向前的问题。
    * “几种方案中哪个最好”属于开放搜索，模型可能只给出一个有限方案，而不是最优方案。
    * 模型因“完成任务”获得奖励，因“未完成”没有相应奖励，容易急于交出一个看起来可用的答案。

    * > **易错点**：不要把完成任务的奖励倾向误当成开放搜索能力；没有可验证路径时，模型往往过早收敛到有限方案。

* **搜索与验证的难度分离**
    * 类比 P 与 NP：给出一条候选路径时，验证它满足条件相对容易；找到满足条件的解则可能很困难。
    * Hamiltonian path 的例子用来说明“验证一个答案容易，寻找满足条件的答案困难”。
    * 搜索困难时，模型为完成要求只能进行有限探索，因此局部改进不能直接证明全局最优。

## 人机协作与人的判断

### 不会就问与反向讲解

* **把疑问立即变成探索**
    * 概念没理解就让 AI 补充，工具不会用就让它演示，异常结果就让 agent 检查自身上下文与原因。
    * AI 不会因重复追问而嫌弃提问者，人可以把知识记忆立即转成可执行探索。
    * 会读取上下文的 agent 也可检查日志，从而发现不完全沿预设思路产生的答案。

* **费曼式反向讲解**
    * 先向 AI 请教并反复追问，直到自己基本弄懂。
    * 再让 AI 扮演“假装什么都不知道”的学生，由自己从头讲解概念。
    * AI 指出逻辑断裂、遗漏和前提不足，针对漏洞重新讲解并再讲一次。
    * 正着弄懂与反着讲清结合，比把“我大概懂了”当成“我能讲明白”更可靠。

* **AI 作为耐心的老师**
    * 学习阶段拥有大量可随时试错的时间，应把 AI 用于追问、试错和即时检查。
    * 困难不应只停留在阅读解释上，而应在多轮对话中同步共识、重建推理图景并继续实践。
    * 当天读资料仍未理解是正常的，真正重要的是从失败中形成下一轮可执行的方法。

* **失败蒸馏为 skill**
    * 人的世界会因新资料而重新连接既有事实，已有 fact 不必改变，但链接方式会改变。
    * 失败过程能够暴露“这次为什么错、缺了哪些前提、下一次该怎样纠正”。
    * 把这些修正路径蒸馏为可复用 skill，就能避免下次从头重复踩坑。
    * skill 应从真实失败中生长，而不是在尚未遇到问题时无限堆叠规则。

### 品味、经验与群体智能

* **人的经验优势**
    * 模型能放大人的能力、品味和既有经验，却难以仅凭分数完全复制个人经历。
    * 人知道受众何时会走神、哪里需要停顿、哪里需要意外，这些体验难有统一公式。
    * 对难以形式化的质量，应把模型当作放大既有判断的工具，而不是让自动评分替代人的选择。

* **多样性形成判断**
    * 模型的发散方向往往较固定；不提供控制时，它容易向常见方案收敛。
    * 人接触不同的人、课程与设计，不是因为“不同”本身神秘，而是因为见过之后才可能形成偏好标准。
    * 主动观察优秀作品，并把“喜欢”追问成具体设计原因，才能减少对默认风格的依赖。

* **大世界假说（Big World Hypothesis）**
    * 世界大到个人和单个模型无法学全；每个人的城市、教育与生活背景会造成不同 bias。
    * 差异使个体知识相互补充，群体能够形成超过单个个体的集体智能。
    * 把开放问题分给多个模型或子任务、保留多样性候选，实质上是在利用这种群体差异。
    * 若少数人获得近乎无限的计算资源，群体智能的差距可能扩大为难以追赶的“墙内”与“墙外”，这是需要提前思考的风险。

### 盯着还是放手

* **盯住方向的收益**
    * 人在 agent 跑偏时立即纠正，并注入自己的领域知识，通常能更快完成当天必须交付的实现。
    * 人不知道方向如何推进时，几乎百分之百的精力都应投入到探索、提问和建立正确方向。
    * 盯住 session 不是为了全程代写，而是把有限注意力放在模型无法自行补足的领域判断上。

* **放任执行的收益**
    * 若任务已明确且模型通常能完成，浪费更多 token 与盯守时间换取最终完成，也是一种合理取舍。
    * 盯着更省人的时间，放任花更多 token 但能完成；选择取决于人的精力而非单一最佳模式。
    * 已知怎样执行的实现任务可以放手，把纠正精力留给未知方向与关键错误。

* **有效努力**
    * AI 时代，纠正 AI 容易带来“自己仍比 AI 有用”的心理满足，但这种满足不自动产生有效产出。
    * 只有把时间留给收益最高的事情，人与 AI 的协作才会真正节省时间。
    * 自我感动式努力没有结果；与真正推进方向的同伴相比，低效消耗的机会成本更大。

    * > **注意**：盯与不盯是精力取舍；未知方向值得盯，已知且可验证的执行可以放手。

### 长上下文的代价与收益

* **位置决定遵循强度**
    * 随指令和上下文增长，模型的指令遵循能力会下降。
    * 最后保留的 prompt 通常仍能较好遵循，因此“修复什么”的短任务放在末尾依然实用。
    * 越靠中部的指令越容易失效，早期指令也可能因大量后续内容而减弱。
    * 长窗口能保存更多信息，不等于其中每条要求始终具有同等权重。

* **长上下文的合理使用**
    * 明确、具体且靠近当前任务的短窗口适合完成可验证工作。
    * 早期规则需要重复、调整与组织，但不能因为窗口很长就无节制堆叠指令。
    * 长上下文的价值是提供资料和历史，代价是注意力稀释与指令压力。

## 开放问题与算力换智力

### 空间分割

* **低跨度任务（low horizon task）**
    * > **定义**：目标虽然开放，但解空间可以枚举、拆分，AI 仍能完成的系统性任务。
    * 起名是典型例子：候选项可以依据偏好来源、读音、筛选条件和逐字检查分阶段处理。
    * 可先枚举或分块，再让子任务分别检查每个局部，使开放问题逐步转成有 verifier 的明确问题。

* **算力换智力**
    * 直接用 next token 生成开放问题答案，会把模型已有偏差带入结果。
    * 把大空间分割为许多小部分后，每个部分都能获得更明确的验证信号。
    * 更多算力可以换取更高质量与更大范围的搜索，以系统调研代替一次 next token 的草率收敛。
    * 考试临近交卷时即使不能得到最优答案，也应先写出候选，以局部结果争取分数；这一原则同样体现“用计算扩展有效产出”。

    * > **易错点**：空间分割会显著增加 token 消耗，智力提升来自更多计算，并非免费收益。

* **一次性搜索与分解搜索**
    * 开放问题若验证解容易、寻找解困难，模型倾向于给出一个有限方案。
    * 人工划分可枚举子空间后，可以并行或逐块检查，降低每次任务的不确定性。
    * 分解后的局部任务仍应围绕整体目标，不能变成为局部 benchmark 自证的 reward hacking。

### 人机能力边界

* **适合交给 AI 的工作**
    * 读取和维护良好的大型复杂系统，寻找已有实现、helper、锁顺序与设计模式。
    * 在明确 verifier 下生成候选、验证、修正，并持续完成具体实现任务。
    * 基于已经对齐的事实做一步可检验推理。
    * 处理解空间可枚举、可拆分的低跨度开放任务。

* **仍需人承担的工作**
    * 判断研究为什么值得做、局部收益是否足以支撑整体贡献，以及一个全新、合理的事情是否成立。
    * 维护领域概念，在系统外判断方向、品味、体验和不可公式化的质量。
    * 为真实工具与 state of the art 选择基线，识别模型自造小任务和局部正负结论的局限。
    * 在不确定性很强、无法连续验证的长程任务中决定何时换方向、何时放弃错误 reward hacking 路径。

* **协作闭环**
    * 先让 AI 与人的知识边界对齐，再给出清楚、简洁且持续可见的要求。
    * 把大问题拆成能够生成候选并获得验证信号的一步推理，不要求一次规划完整未知路径。
    * 用真实工具、代码、实验结果与人类知识提供证据，警惕模型被自洽文本和局部目标污染。
    * 把人的精力放在正确问题、领域知识、审美判断和及时纠偏，把重复执行交给能够验证的模型。

    * > **结论**：提示词工程的起点是明确意图；上下文工程负责组织信息；可靠结果来自可检查的约束、明确的 verifier，以及模型与人的持续协作。
