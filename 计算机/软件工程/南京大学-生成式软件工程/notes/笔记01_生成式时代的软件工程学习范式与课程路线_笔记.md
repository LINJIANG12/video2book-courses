# 生成式时代的软件工程学习范式与课程路线

## 能力从昂贵到日用品

* **能力基础设施化**

    * > **定义**：原本只有少数人能够拥有的计算或智能能力，转变为普通人可以随时调用的基础设施。

    * 能力演进路线是：昂贵的计算机 → 互联网连接所有人 → 移动互联网进入日常交易 → 大语言模型成为可对话的通用入口 → Agent 替人调用工具并完成任务。

    * 判断一项技术是否值得学习，不能只用“以后会不会用得上”，因为技术已经直接改写学习、工作以及人与人建立联系的方式。

    * 互联网早期已经允许人随机添加世界另一端的人；移动互联网把收款、交易和日常生活搬到网络里；大语言模型与 Agent 则让人和 AI 的交互成为可以直接使用的通用能力。

* **大语言模型（large language model, LLM）**

    * > **定义**：把已有文本或图像与用户提示作为上下文，不断预测下一个 token，并将新 token 接回上下文、重复预测直到形成回答的模型。

    * 从使用者视角，先把它理解为一个概率分布即可，不必先掌握训练模型或内部单元模型等细节。

    * 模型规模大、训练困难，前沿实验室因此很强；使用者可以通过网页或 API 直接体验、提问和获取结果。

    * 早期需要精心调 prompt 才能稳定得到想要的结果；能力增强后，许多任务已经可以先用一句话描述，再根据结果继续修正。

* **信息差与驾驭能力**

    * > **定义**：人在 AI 时代更应掌握的不是“比别人更聪明”，而是拥有别人不知道的信息，或能够驾驭别人与 AI 暂时还驾驭不好的东西。

    * 信息差可以带来竞争优势，但不应成为大学教育最主要交付的能力。

    * 更重要的能力是提出问题、定义问题、组织工具、承担结果，并把 AI 带到更大的目标中。

* **AI 协作者（AI collaborator）**

    * > **定义**：AI 不是一个替人生活的自动售货机，而是可以被指挥、检查、纠错，也可以被带去做更大事情的协作者。

    * 工具可以提高执行效率，但“什么样的结果值得完成、结果是否正确、是否值得继续投入”仍然由人判断。

## 生成式软件工程的交付责任

* **软件工程（software engineering, SE）**

    * > **定义**：软件工程要解决“怎样让软件工程不失败、怎样造出一个软件来”的问题；造软件不是敲完代码，而是让需求、设计、实现、验证和后续维护形成可交付的东西。

    * 需求、设计、实现、验证、维护不能被拆成互不相关的动作；任一环节缺失，都可能使软件无法交付或无法持续运行。

    * 课程名为“生成式软件工程”，但首先仍是一门软件工程课，生成式工具改变的是实现和协作方式，不改变交付责任。

* **人的责任链**

    * > **定义**：人在 AI 协作中负责确定目标、补齐中间过程、选择实现、验证结果、发现错误并承担最终结果。

    * 真实竞争力不是把所有事情都交给 AI，也不是继续重复只在几分钟内解决明确题目的旧式训练，而是做出能被别人看见并解释的作品。

    * 亲手完成过、能够说明设计取舍和实现过程的内容，不能被实习名称、奖项名称或论文状态简单替代。

* **简历中的可验证信息**

    * > **定义**：简历的价值不在于经历字段的加法，而在于让别人看出这个人到底做过什么、怎么做、为什么值得继续了解。

    * 只有排版整洁、经历堆叠而没有个人链接、代码、主页、预印本或可见成果的简历，信息增量可能为零。

    * 竞争者拥有相同类型的实习、奖项和论文时，继续填充同类字段不会形成辨识度；应留下能够被验证和继续追问的作品证据。

    * > **易错点**：把更多项目名称和更多“已接收”状态堆到简历上，不等于提供了更多可验证的信息。

* **先做出来，再复盘**

    * > **定义**：先用 Agent 把可运行的结果做出来，再回头检查机制、补上理解并继续修改。

    * 没有 Agent 时，配置终端等任务常常要经历搜索、试错和逐项理解；Agent 可以直接修改、解释原因并响应新的想法。

    * 屏幕上出现漂亮结果，不等于已经理解了其中最好的设计；速度可以交给 Agent，判断不能完全交给 Agent。

    * 典型危险是把“能够运行”直接当成“已经完成学习”，从而跳过对机制、设计和错误的复盘。

## 大语言模型与 Agent

* **下一 token 预测（next-token prediction）**

    * > **定义**：模型根据当前已有内容预测下一个 token，生成一个 token 后把它接回上下文，再继续预测下一个 token，直到形成完整回答。

    * 这与传统概率统计中根据前几次结果推算下一次结果的形式相似，但模型面对的是一整本书、长文本或图像。

    * 使用者可以把它当作可交互的概率分布来使用，不需要先从训练细节开始理解。

* **智能体（Agent）**

    * > **定义**：Agent 把模型接入程序和工具，使模型能够观察执行结果、决定下一步动作、不断尝试并修正，直到完成复杂任务。

    * 模型可以输出普通文本返回给人，也可以输出特殊 token 表示要调用程序；程序执行结果再回到 Agent，成为下一轮推理的上下文。

    * Agent 的基本循环是：预测输出或工具调用 → 程序执行 → 读取结果 → 决定下一步；复杂任务因此不再只是一次性回答。

* **ReAct 式执行回路（reasoning and acting, ReAct）**

    * > **定义**：ReAct 类型 Agent 由模型负责推理和决定动作，由工具负责执行，执行结果再成为下一轮推理的上下文。

    * 价值不只是给出建议，而是可以观察当前系统、修改配置、运行验证，再根据结果继续调整。

    * 终端配置可以作为一个直观例子：Agent 根据自然语言要求调整界面、进程查看方式和命令替换，并接受再次检查。

* **Agent 上下文与想象力**

    * > **定义**：Agent 的起点不是某条神奇命令，而是人愿意提供什么样的环境、规则、背景和任务。

    * 在仓库中提供课程身份、上下文和规则后，Agent 就不再只是一个只知道模型名称的聊天窗口，而知道自己正在处理什么任务。

    * 想象力会限制 Agent 的上限；没有想过可以让它做什么，就很难主动打开相应的可能性。

    * 使用方式应从直接开始提问和交给任务开始，而不是等待别人先教会全部用法；再通过背景、约束和配置持续扩大可做范围。

* **硬件验证与完成操作的区分**

    * > **定义**：对于涉及真实硬件的操作，Agent 可以完成繁琐操作，但“完成文件操作”和“确认不会误伤目标”是两件不同的事。

    * Linux U 盘案例中，人可以把镜像来源、系统版本、可启动、安装到 U 盘和用 `QEMU` 验证等约束交给 Agent。

    * 安装后必须在模拟器中真正启动到登录界面、创建用户、设置密码并确认登录成功，完成这些检查后才能把 U 盘带到教室。

    * 过去需要逐项掌握安装流程，现在可以把约束和验证交给 Agent；真实硬件校准仍不能省略。

* **系统说明书生成**

    * > **定义**：对于已经配置好但他人不会使用的系统，可以让 Agent 查看实际设置并生成操作文档，把配置成果变成可交接能力。

    * 例如让 Agent 说明如何打开终端、打开应用启动器和切换窗口；人只需提出需求、检查结果，再把系统交给他人使用。

    * 这种方式把阅读整套规格、逐项理解每个功能，转化为与已经读过、理解并能实现的人沟通，再把能力带到更大的事情上。

* **未来生成机制的不确定性**

    * > **定义**：今天依赖的交互形态不是未来终点，模型可能采用不同生成机制、更长上下文和更强的回溯修改能力。

    * 除逐 token 生成外，扩散模型可能从随机噪声开始反复生成，也能回过去修改上下文、裁短长上下文；哪条路线会胜出目前无法准确预测。

    * > **注意**：不要把今天最强的模型形态当成未来的终点；学习重点应放在能够持续检查和调整结果的工作方式上。

## Agent 能力飞轮

* **能力复用生态**

    * > **定义**：脚本、插件、浏览器能力和可复用 skill 会在生态中不断沉淀，使一个领域中的特定任务更容易被组合和重复调用。

    * 对普通人而言，合理的下一步是先让插件管好浏览器，再让插件管好电脑。

    * AI 的真实形态不只是一个聊天框；模型能力只有进入工具、脚本、插件和 skill 的生态，才会形成持续可用的工作系统。

* **开发者工具（developer tools, DevTools）**

    * > **定义**：DevTools 把正在运行的真实网页变成可以观察、检查、请求和复现的对象。

    * Chrome 的 `F12` 界面可以查看网页 console、HTTP 头和各种请求信息；一个链接还可以复制为带有 cookie 和完整状态的 curl 请求。

    * 过去普通人需要专门学习 DevTools 才能利用这些能力，现在 Agent 可以把它们接入自己的工作流。

* **试错到脚本化**

    * > **定义**：Agent 的一次成功路径可以被固定为以后能够重复调用的确定性脚本或记忆，而不必每次从对话重新探索。

    * 教务系统案例中，Agent 起初没有按照“不要看任何东西”的指令填写空值，反而读取了 lecture notes；失败后发现直接注入事件行不通，于是改用点击鼠标并走通路径。

    * 成功之后，网页路径、失败位置和可走通的步骤可以沉淀为脚本；重复之后，甚至可以形成自动选课或抢课系统。

    * Flash 系列模型速度快，但常见问题是先不照指令做、能力仍在增长、翻车频繁；更一线的模型通常有更好的指令遵循。

    * > **结论**：Agent 的价值不只在于一次对话完成任务，更在于把一次成功路径固化为可重复调用的能力。

* **UNIX 管道式组合**

    * > **定义**：浏览器 skill、网页工作 skill、记忆提取和脚本等能力可以互相调用，组合成更大的处理系统。

    * 这种组合思想接近 UNIX 的管道：不同能力通过接口连接，能够自由组合和复用，产生超过单个能力简单相加的效果。

    * 能力沉淀后，任务不必每次从自然语言重新摸索，已有脚本和记忆可以直接成为新工作的基础。

* **信息流知识飞轮**

    * > **定义**：把 RSS、B 站、archive、Hacker News 等信息源自动收集、筛选，再由脚本与 skills 组成处理系统，使信息持续转化为知识并反过来改进工作流。

    * 处理链路是：多个推送源 → 自动收集与筛选 → 脚本与 skills 处理 → 持续产生有用知识 → 持续调整工作流并改进系统。

    * 这个系统几乎不需要手写每一行代码，各部分可以用自然语言描述，但必须能够不断复用和调整。

    * 有飞轮时，信息不再只是堆积，而是持续转化成有用的东西；没有飞轮时，信息仍停留在日常接收状态。

* **日常事务 Agent**

    * > **定义**：对足够 routine、且自己放心的日常事务，可以先用 Agent 生成可继续工作的 bot，再由人修改、确认和接管重要动作。

    * 邮件 Agent 可以把新邮件标记为已读，按照历史口吻生成回复草稿，并识别、保存附件；简单邮件有时可直接使用，复杂邮件仍需修改。

    * 打印发票的流程可以由待办触发后台 Agent，处理完成后通过手机、手表等通知；人只需在实际动作前确认并完成最后一步。

    * 这不是完全自动化幻觉，而是先提供一个不知疲倦的辅助 bot；真正重要的动作仍需要确认。

* **录屏与重复流程复盘**

    * > **定义**：可以把录屏交给 AI 总结一天的工作，识别重复流程和提升空间，再把稳定流程固化为脚本或 skill。

    * 课程内容可以被整理成课程资料和复习材料；视频可以被整理成视频、论文等辅助材料；自然语言需求也可以驱动代码生成和 3D 打印等实际工作。

    * > **易错点**：在 AI 时代仍然心安理得地每天重复同样的事务，才是值得警惕的状态。

## 新型学习方式

* **阅读与注意力分配**

    * > **定义**：Agent 可以先帮助寻找、压缩和筛选信息，但真正的学习仍然要回到原文核对，理解不能只停留在摘要中。

    * 阅读《人月神话》时，可以先让 AI 耿同学寻找人类历史、相关案例和跨学科的经典工作，再优先选择被广泛认可、影响力大的资源。

    * 不同 personality 的 AI 耿同学可以互相讨论、保留分歧并继续讨论，最后由主 Agent 汇总；额外算力用于换取更充分的思考和更少的盲点。

    * 阅读论文时可以假设已有知识已经固定，先剥离论文真正的新内容，再用一级总结和更深层总结压缩噪声。

    * 读完摘要后仍要拿论文原文继续对话和核对；不能把 AI 的总结误当成已经完成的理解。

* **视频图文时间轴**

    * > **定义**：把长视频的字幕作为基础文本，同时依据两帧画面之间的间隔决定何时截图，把截图作为视频的 ground truth，生成 podcast 式内容和自动图文时间轴。

    * 字幕是基础来源，但画面截图能够帮助定位上下文，因此图文时间轴往往比单独字幕质量更高。

    * 对已经熟悉、不需要再看的内容，可以依据记忆直接去除；真正不同或值得注意的部分保留下来。

    * 一到两小时的视频可以在几分钟内快速看完，但仍要知道可能漏掉了什么，以及哪些地方需要回到原文检查。

    * > **注意**：工具让内容消费变得很快，但理解可能没有同步跟上；必须保留检查摘要组织方式和判断删减是否正确的习惯。

* **先获取结果再补理解**

    * > **定义**：学习新工具或系统时，先借助 Agent 获得可运行结果，再回头理解其中的机制和设计。

    * 这种顺序可以绕过从零开始逐块搭建的漫长学习曲线，但不能跳过对设计、错误和边界的复盘。

    * Agent 可以解释修改原因并继续响应新想法；人仍需决定结果是否符合目标、是否值得保留。

* **能力差距**

    * > **定义**：会用 Agent 学习的人与不会用 Agent 学习的人之间，效率差距可能达到十倍甚至一百倍；这个差距提醒人尽早学会指挥工具，而不是鼓励跳过全部基础。

    * 同样的四年，如果有人更早学会使用工具，就可能在竞争中没有优势。

    * 解决方案既不是把所有作业都交给 AI，也不是继续重复已经不适合新时代的训练方式，而是理解 AI 的能力边界，再带着它完成原本自己做不到但组合起来可以做成的事情。

## 课程路线与实践政策

* **从导入到执行回路的课程路线**

    * > **定义**：课程先从能力基础设施化和 AI 时代的学习焦虑切入，再进入软件工程责任、大语言模型的下一 token 预测、Agent 执行回路，随后讨论学习方式、能力飞轮、软件失败、意图到实现的翻译以及软件长期生存。

    * 导入阶段要回答“AI 替我上大学”带来的两种焦虑：所有事情都让 AI 完成而自己什么也没学会，以及只按旧方式学习而不知道 AI 之后自己留下了什么。

    * 基础部分要建立“怎样造出一个软件并让它不失败”的软件工程视角，而不是只学习某一条工具命令。

    * Agent 部分要理解模型如何调用工具、如何在执行结果上循环，以及如何把一次成功变成可复用能力。

    * 后半部分要把生成式能力放回产品、架构、团队、演化、可靠性和长期维护中，避免只停留在聊天框或单次任务层面。

* **实践优先**

    * > **定义**：课程不要求沿用过去“到课、听讲、刷题”的古法编程方式；真正重要的是跟着课程案例实践 AI 时代的学习方式和工作方式。

    * 如果目标只是听知识、拿知识，可以不到课、不看直播；如果目标是掌握这门课，应参与实践案例并完成可检验的产物。

    * 禁止古法编程不是反对基础知识，而是先撕开一个小口子，让学习者尽早体验新的工作方式。

* **Token 自费政策**

    * > **定义**：课程要求学生承担调用 AI 能力的成本，但不要求每个任务都使用最昂贵或最强的模型。

    * 课堂大部分演示可以使用相对便宜且智能程度足够的 DeepSeek Flash 类模型；slides 生成等需要更高质量的任务可以使用更聪明的模型。

    * 可以准备大约 100 元的 token 预算；确实有困难时，再与教师一起寻找解决办法。

    * 付费的目的不是追求昂贵模型，而是愿意为调用新的能力付出成本，并学会按任务选择模型。

* **用项目和最终产物检验**

    * > **定义**：课程倾向用“通过或不通过”和最终产物检验学习，而不是只用一个统一分数判断能力。

    * 课程实践可以包括实现一个运行在宿舍常开电脑上的 email 管理系统；系统可以通过邮箱通信，复杂程度可以不同，但必须能够实际运行并被检验。

    * 最终应能在简历中写出在生成式软件工程中实现了什么、有哪些链接、完成了哪些设计和实现，以及哪些地方真正做得漂亮。

    * 成绩在 AI 时代可能变得没那么重要，但保研或求职时真正接受检验的是简历能否把人带到下一个平台。

    * AI 时代仍可能需要 GPA、针对考试做 reward hacking 或 overfit，但这些不能替代大学阶段最终的作品和个人判断。

* **把上课做成可迭代系统**

    * > **定义**：先写 markdown 讲义作为 source of truth，上课时选择片段让 Agent 扩写并生成 slides，课堂表演后继续 review、切片、重新整理，再回到 content—test—code。

    * 讲义先约束内容和例子，避免模型完全自由发挥；选中的片段再由 Agent 扩写成 markdown slides，图片由 AIGC 生成，最后交给浏览器渲染。

    * 可以让负责加工讲义的 skill 工作，也可以生成不同 personality 的 sub agent，让它们在隔离上下文中从不同方面思考，再由主 Agent 汇总和复核。

    * 可以让另一个模型对不同版本的 slides 进行盲评，再选择相对更好的结果；这是一种用额外算力换取更充分思考和较少盲点的方式。

    * 课堂不是一次性消费的内容，而是一个持续编译、持续 review、持续版本化的项目；录像可以被重新切片并补充，一次不完美的表演仍能继续完善。

    * > **注意**：模型负责扩大探索空间，人负责确定什么值得保留、什么必须修正。

## Intention、Specification 与 Implementation

* **意图空间（Intention space）**

    * > **定义**：Intention 是脑中真正想实现的目标，即为什么要做这件事、最终想得到什么结果。

    * “我要造一个能把数据传出二维码的 Excel”属于意图；“让同学们点外卖更方便”也可以是一个具体意图。

    * 同一个意图可以对应很多种 Specification 和 Implementation，因此不能把一句愿望直接当成完整软件需求。

* **需求规格（Specification space）**

    * > **定义**：Specification 说明程序必须具备哪些功能、满足哪些要求以及有哪些边界，而不只是指定某一种架构。

    * Specification 可以规定界面数量、每个界面的功能、正确性、性能和 Excel 版本兼容性等要求。

    * “用 Excel 2019 兼容的公式把任意字符串转成 QR 动画”比单纯表达“做出二维码工具”更接近可执行的需求规格。

    * 即使两个实现都满足同一个 Specification，它们的架构、实现方式和维护难度仍可能截然不同。

* **实现空间（Implementation space）**

    * > **定义**：Implementation 是让需求落地的具体选择，包括界面、数据库 schema、代码、架构和后端方案。

    * “教务系统”这一个意图可以对应很多规格；规格又可以对应不同的界面设计、表的数量、每张表的列以及 key-value 数据库或关系型数据库等实现。

    * 数据库原本没有“校区”字段，后来产品需求增加校区并要求分开选课，原先能用的系统也可能因新增概念而开始失败。

* **翻译与 Gap**

    * > **定义**：从 Intention 到 Specification 是翻译，从 Specification 到 Implementation 也是翻译；软件工程的任务是补上这些空间之间的 gap。

    * 只要其中一个翻译错了，软件工程就可能失败：前者错了会导致做出的东西不是真正想要的，后者错了会导致虽然满足表面需求，却违反正确性、性能等约束。

    * 客户、产品经理、分析师、宣传人员和最终开发实现之间可能各自形成不同理解，根因就是不同空间之间存在巨大 gap。

* **AI 的直接猜测**

    * > **定义**：模型面对一句话时通常先猜“你应该要这个”，然后直接实现；人需要阻止这种乱猜，同时尽可能发挥模型从 A 做到 B 的执行能力。

    * 模型在后训练中会因任务完成、测试通过而获得 reward，因此形成尽快动手、尽快完成任务的倾向；慢就可能得到更少奖励。

    * 这种训练使模型擅长简单任务，但它不等于具备完整的软件设计过程；生成式软件工程要处理的是更大的系统，以及模型看不到的中间过程。

    * > **易错点**：不能把“能快速实现眼前任务”当成“已经完成了软件工程”；从意图到实现的中间步骤仍需要人补齐。

## 复杂需求与可维护实现

* **从想法到产品的系统性**

    * > **定义**：产品是系统性工程，不是一个想法加上程序员就能完成的结果；外卖网站至少涉及前端、后端、交互和运营，任一环节失效都会让产品无法存活。

    * AI 可以参与这些环节，但“每件事都会做”不等于把这些环节组织起来后系统就能长期运行。

    * 软件工程需要考虑需求、架构、测试、演化、可靠性和维护，而不是只让当前版本在一次运行中成功。

* **QR Code 失败案例**

    * > **定义**：AI 直接生成 QR code 点阵 HTML 时，虽然任务表面完成，却产生难以使用、bug 很多、几乎无法维护的实现。

    * 初次需求明确要求用 Excel 2019 兼容公式把任意字符串转成 QR 动画，并要求不要询问、持续做到完成；模型仍因没有理解具体做法而扩大问题范围。

    * 模型容易在小 corner case 上犯错，软件工程的第一步应是先做最简单的东西，而不是为“任意字符串”扩大到不必要的完整正确性系统。

    * GPT-5.3 在一次受控实验里思考 25 分钟后疯狂输出，超过 32K 输出 token 后被截断；继续运行总计六小时才完成。DeepSeek V4 Pro 夜间运行后则变成了硬编码，不符合指令。

* **硬编码错误与动态计算**

    * > **定义**：正确的 QR 实现必须在 Excel 公式中动态计算 Base64 编码，而不是让 Python 先算出 Base64 结果再把结果硬编码进公式。

    * 正确的数据流是：输入任意字符串 → Base64 编码 → 通过 Excel 公式计算所有位运算 → 生成 QR 动画，并保持程序可维护、可复用。

    * 如果字符串改变而 Excel 公式仍使用旧的硬编码结果，程序就不能满足“任意字符串”的需求，即使第一次运行时看起来成功。

* **中间语言与双后端验证**

    * > **定义**：可维护的解决方案是设计一个类似编译器的 Python 类，把各种位运算抽象成符号系统，形成既能被 Python 执行、也能被翻译成 Excel 公式的中间语言。

    * 中间语言要对 Python 友好，也要对 Excel 友好；它把复杂问题变成可以分别验证的小模块。

    * 验证至少包括：输入在 Python 中的执行结果、输入在 Excel 中翻译出的公式、二维码编码以及每个像素的计算。

    * 逐层验证后，生成的代码更干净、长度更短，维护性也高于直接让模型硬编码结果。

    * 不同 AI 方案可以放在一起比较：不同 roadmap 仍可能对应同一种工程思路，即拆出可验证模块，再分别实现 Python 与 Excel 两套后端。

* **一次能跑与长期维护**

    * > **定义**：“一次能跑”只是软件最初的验收条件，维护性才决定产品能否长期生存。

    * 如果需求没有“校区”字段，后来却要求按校区区分选课，原有系统的数据库和代码结构就会暴露扩展困难；能运行不等于能演化。

    * Agent 即使最终能修好硬编码方案，也不能因此把代码结构和验证方式看成同一种事情；结果修好不等于架构正确。

    * > **结论**：软件工程不是“我知道需求了，实现需求就好了”，而是让软件能够面对几十年的变化。

## 人机共建的系统设计

* **需求编译**

    * > **定义**：普通人容易提出一个需求，Agent 却可能做不好、做不了，或不知道如何用 prompt 稳定快速完成；计算机专业者应把需求编译成可复用代码、skill 和适合 Agent 处理的其他形态。

    * 人机协作的关键不是把所有事情扔给一个聊天机器人，而是识别任务中的不同性质，再为不同部分选择合适技术。

    * 需求编译的结果应当能够复用、验证和继续演化，而不是一次性的自然语言请求。

* **改卷子流水线**

    * > **定义**：一个可用的系统可以拆成相机采集、本地模型识别、确定性脚本计算、人工核对和教务表格汇总等不同部分。

    * 试卷摆在固定位置后按回车拍照，本地 Qwen 离线识别姓名、学号和每一个小分，并把结果写入文本文件。

    * 第二阶段按反序进行：系统用语音播报姓名、学号和各个小分，人亲自检查 OCR 结果，确认后由脚本计算总分并抄写回卷面。

    * 最后分数自动汇总到教务 Excel 模板，上传文件后还要抽样检查，确认无误后提交。

    * 相机 + 本地模型 + 脚本 + 人工核对比“所有事情都交给聊天机器人”更可靠；本地 27B 模型的 Qwen 已能完成识别工作。

    * > **注意**：大模型负责识别和流程控制，不负责做容易出错的加法；总分由脚本计算，OCR 结果由人检查。

* **局部自动化与全局责任**

    * > **定义**：系统可以自动化识别、采集、格式转换和重复操作，但重要结果仍需要人工核对、抽样检查和最终提交。

    * 把大需求拆成“模型识别”“确定性脚本计算”“人工核对”等部分，能够降低同步代价，也能避免把可靠性完全寄托在模型生成上。

    * 自动化流程必须保留责任边界：模型可以减少重复劳动，人仍然要对每个结果的可信度和最终交付负责。

## 失败模式与长期演化

* **维护性优先**

    * > **定义**：软件工程要研究的不是只完成一次任务，而是当 gap 真实存在、系统已经发生变化时，怎样把足够大的事做出来并继续维护。

    * 教务系统每年增加功能且有人维护，并不能证明它能长期生存；“能运行”与“能长期演化”是不同判断。

    * 从小实验到能赚几百万、几千万的上市公司，再到国民级产品，方法论来自一次次巨额投入换来的失败教训。

* **加人不救失败项目**

    * > **定义**：大型动物陷入焦油坑后很难逃脱；如果团队或软件产品已经开始失败，继续加入更多人只会让它更失败。

    * AI 也会产生 slop；项目已经失败时继续投入更多 token，AI 会不断在失败对象上修补和堆叠，直到成本无法承受。

    * > **易错点**：当系统已经陷入“加功能、加人、加 token 就继续修补”的循环时，应停下来重新审视架构，而不是继续堆投入。

* **教育与 Agent 的短反馈**

    * > **定义**：传统考试主要训练快速解决已经明确的问题；Agent 的训练信号也偏向短时间完成，因此人和 AI 都可能缺少处理长期未知问题的自我驱动。

    * 高考以来的考试题通常能在几分钟内解决；一个人如果五分钟解决不了，题目往往就不会出现，久而久之会形成解决明确问题的能力。

    * Agent 有更多数据和更明确的反馈信号，常以几秒钟完成为目标；没有好奇心和 self-motivation，就可能不去探索世界如何运行、产品如何开发。

    * 结果可能是人解决“综合题”的能力还不如 AI；软件工程的杠杆往往出现在 gap 还很小、但微小偏差会被放大的地方。

* **AI 的长程信号缺口**

    * > **定义**：模型已经通过 reinforcement learning 擅长许多任务，但对真正长程的 reward 仍不够好，容易机械完成任务，而不是主动追求干净、可维护的设计。

    * 面对 Excel QR Code，模型第一反应通常是直接做题，而不是先设计 DSL 或其他中间表示。

    * 模型见过好的设计，也可能逐渐学会品味；几个月后课程中关于设计的判断甚至可能过时，因此不能把当前模型的局限当成永久边界。

* **古法编程与软件工程**

    * > **定义**：古法编程在单个任务上已经难以与 AI 竞争，但软件工程没有失效；软件工程仍要处理意图到规格、规格到实现的翻译错误。

    * 需求翻译错误会做出不是人真正想要的东西；实现翻译错误会满足表面需求却违反正确性、性能或维护约束。

    * 课程要训练的不是比 AI 更快地打字，而是提出好问题、设计好架构、验证每一步并对长期结果负责。

* **面向未来的个人能力**

    * > **定义**：人在 AI 时代真正稀缺的能力，是找到值得解决的问题，把未知拆成便宜实验，用证据让坏方向及时停下，并对长期结果负责。

    * 面对“为什么不直接买一个能完成任务的 AI 工具”这样的提问，能给出的理由不是个人比工具更快，而是能够持续定义、实验、判断和负责。

    * GPA、实习、奖项、论文和漂亮的生成结果都不能单独替代对问题的定义、设计的解释、结果验证和长期责任。

## 软件工程的管理与社会维度

* **技术与管理并存**

    * > **定义**：软件工程既包含程序分析、测试、代码审查和自动 warning 等技术，也包含团队协作、风险管控、人员流动和社会关系等管理问题。

    * 如果已有代码，可以研究能否自动生成更多测试用例、自动审查代码；当代码不满足 Specification 甚至潜在 Intention 时，可以提前给出 warning。

    * 团队里有人不听话、有人离职、有人跳到竞争对手处，以及怎样管理人和风险，同样属于软件工程要研究的问题。

* **AI 带来的管理变化**

    * > **定义**：生成式软件工程没有消除管理问题，只是把团队成员从会抬杠的人变成了一个通常会回答“你完全正确”的 AI 角色。

    * AI 可能更听话，但“人应该如何被管理”这一问题仍然存在；自动化执行不会自动产生可靠的组织协作。

    * 人类社会学、管理学、可靠性和软件演化仍然需要被纳入系统设计，而不能被归结为模型能力。

* **研究方向地图**

    * > **定义**：生成式软件工程的研究范围包括 AI for SE、SE for AI、架构设计、可靠性、演化、软件长期生存和 human social aspects。

    * 研究方向一端是用 AI 改进软件工程，另一端是用软件工程方法改善 AI；两端都要求关注系统结构与长期结果。

    * 研究对象既包括代码和架构，也包括团队如何理解问题、如何分配责任以及软件如何随时间变化。

## 生成式能力的责任边界

* **人的判断**

    * > **定义**：生成式工具越能完成任务，人越需要保留目标判断、结果检查、错误修正和最终交付的责任。

    * AI 可以快速生成实现、摘要、幻灯片、脚本或考试题，但不能因为生成速度快就默认结果可以直接使用。

    * 对课程材料，应检查其是否真正对应当前内容、要求是否清楚、答案是否成立；对软件，应检查动态计算、可维护性和真实运行结果。

* **出题任务的工作流**

    * > **定义**：让 Agent 出期末试卷时，应先把出卷明确为围绕课程内容执行的任务，让它生成题目和对应答案，再由人逐题 review。

    * 逐题检查至少包括题目是否对应该课程内容、答案是否成立、要求是否清楚；长文没有给出具体题型、题量和评分标准时，不能自行补出一份完整试卷。

    * 工具提高出题和迭代效率，但“什么样的试卷是好的”仍需要人的判断，交付责任不能转移给生成速度。

* **课程终点**

    * > **定义**：生成式软件工程的终点不是把每一行代码都亲手敲完，也不是把课程内容自动变成一份简历，而是让人获得定义问题、组织工具、验证结果和创造作品的能力。

    * 学习者应先做出一件可运行的东西，再通过复盘理解机制、边界和维护要求；最终留下能够被别人看见、验证和继续追问的作品。

    * 人机协作的最终分工是：AI 扩大探索空间并执行大量尝试，人补齐意图与规格之间的中间过程，选择实现，审查结果，并对长期结果负责。
