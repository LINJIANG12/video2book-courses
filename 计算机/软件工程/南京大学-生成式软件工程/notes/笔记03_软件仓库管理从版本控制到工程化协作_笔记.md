# 软件仓库管理：从版本控制到工程化协作

## 软件项目与仓库

### 目录是需求的投影

* **软件（Software）**

    * > **定义**：代码、文档等等，一切和软件相关的东西的集合。

    * 更本质的视角：软件是人类世界的需求在信息世界里的一个投影；这个投影今天看到的就是一个目录。
    * 这个目录里的文件共同构成一个可交付的东西，最后变成产品。
    * 一个项目最初可能只有一个 `hello.c`，编译出一个 `hello`；这已经是在做软件，但不符合现代 best practice。
    * > **提示**：目录可以在本机直接跑起来（本地 development server、localhost 端口），但世界上其他人打不开它——别人不知道 localhost 是你的本机。
    * > **提示**：把 intent 和 specification 在文档里写清楚，例如声明"这个东西要被全世界人看到"。不说，AI 默认把你当开发者，只在本地调试、ready 之后才送远端。

    ```text
       人类世界里的需求（一个说不清的 intent）
                        │
                        │  投影
                        ▼
            信息世界里的一个目录
            ├── hello.c      源代码
            ├── hello        编译产物（由 hello.c 生成）
            ├── doc/         文档
            ├── intent.md    意图与规格
            └── test/        测试用例
                        │
                        │  构建 + 交付
                        ▼
                可交付的东西  →  你的产品
    ```

* **仓库（repository）**

    * > **定义**：那个被放进去的项目目录，加上一个隐藏的 `.git` 目录。

    * `git init` 之后项目就变成被 git 管理的仓库；此后才能从远端下载代码、把代码推回远端。
    * `.git` 目录默认不显示，所以在文件管理器里看不到。
    * 有了仓库以后，作业更新只需要在课上说一句"你们用 `git pull` 拉"，不必再给每个人发一份新的压缩包。

* **Git**

    * > **定义**：除了保存一个项目目录，还能保留、比较、恢复这个目录的历史版本。

    * 历史可回溯的直接原因是人会犯错；只要能把错误从 git 的历史里捞回来，这个工具就成立。
    * 团队里还可以配一个 `make submit` 之类的脚本自动打包上传，这已经接近现代 CI/CD 的形状。

### 项目的三层内容

* **意图与规格（intent / specification）**

    * intent 层：最初想做一个什么样的产品、能达到什么效果；配两张 screenshot，再加上最重要的设计。
    * spec 层：选什么数据库、选什么编程语言、项目结构长什么样；小到每个模块的接口都属于 spec。
    * implementation 层：把 intent 与 spec 落成代码。
    * > **易错点**：AI 生成的那种极长 README 价值很低。要说服一个 computer science 的人出来一起干，只需要一份比较短的 README 说明 intent，剩下的是对方自己的事。

* **产品需求的方向**

    * 做个人助手时最想要的是**提升学习效率**和**提升工作效率**这两条能力。
    * 一个合理的切入方向是：自动从外网收集数据，以层次化的方式归档，最终给出一个比较好的界面。
    * 资源紧张时优先用一两百块钱的嵌入式小设备放在宿舍里持续跑 agent loop；接口就是调一次 agent。

## 代码管理的演进

### 交付方式的四个时代

* **代码管理方式**

    * 每个时代都能完成"交付"这件事，但拿到更新的代价完全不同。

    | 年代 | 交作业 / 交付的方式 | 拿到更新的方式 |
    | --- | --- | --- |
    | U 盘时代 | 代码拷在 U 盘上，带来带去 | 物理接触，无所谓版本 |
    | 压缩包邮件时代 | 打一个压缩包发邮件 | 给每个人发一份新的包 |
    | 网页上传时代 | 在一个网页上面上传 | 重新下载覆盖 |
    | Git 时代 | 推送到远端仓库 | `git clone` / `git pull` |

    * > **易错点**：U 盘会坏。真实的失败模式是：靠拷贝同步的人在大二丢了 U 盘，代码、作业、启蒙阶段的成果一起消失，只能从头再来。

* **为什么必须要有版本控制**

    * 新手阶段一次误操作是正常的，所以最原始的诉求只有一条："我手滑改错了，想回去看看上一版到底是怎么写的"。
    * 只要能 list 出所有版本、能把当前版本切成另一个版本，就已经是简化版的 git。
    * 接下来自然涌现的需求是"跟室友同步同一个项目"，再往后就是分支、合并、冲突这三个概念。

### 存变化还是存快照

* **SVN**

    * > **定义**：存的是"变化"——一条越来越长的补丁链。

    * 每个文件改一行就存一个 patch，从 v1 到 v4 串成一条链。
    * 想回到 v2 只能一个 patch 一个 patch 往回退；缓存之类的优化能缓解，但模型本身没变。
    * 配套的日常动作是 check in、check out。

* **Git**

    * > **定义**：存的是"快照"——每个版本都独立可达。

    * 版本之间是指针关系，切回任意旧版本是直接的，不需要回退链条。
    * 2005 年做出来，作者是 Linux 的作者；此前 1991 到 2002 年维护 Linux 靠的是在邮件列表上发补丁，由每天看邮件的人合进核心仓库再 release。
    * 2005 年之前还有 `gitk`、`keeper` 之类的工具，最终的诉求是"一个绝对简单、非常好用、概念正确的版本控制工具"。

    ```text
       SVN：存的是「变化」—— 一条越来越长的补丁链
       ───────────────────────────────────────────
            v1 ──patch──▶ v2 ──patch──▶ v3 ──patch──▶ v4
                                                           │
            回到 v2 ？只能一个 patch 一个 patch 往回退 ◀───┘


       Git：存的是「快照」—— 每个版本都独立可达
       ───────────────────────────────────────────
            ● v4        ● v3        ● v2        ● v1
             │           │           │           │
             └───────────┴───────────┴───────────┘
            回到 v2 ？一秒钟切过去
    ```

* **高效实现的反噬**

    * 每次只存 delta 的做法在项目小的时候非常高效，但随着项目增长会把人拖进泥潭。
    * 第一性原理是：想回到过去的某个版本，马上一秒钟就回去；每一步都省下来的那点空间，换不回"只能倒着退"这件事。

## Git 的对象模型

### 持久化的目录树

* **Git 内部结构**

    * > **定义**：Git 是一个持久化的数据结构，它持久化的是目录树。

    * `.git` 下有带 hash 索引的 objects，objects 就是普通的文件；这个数据结构可以不断向后生长——文件只往末尾追加。

* **快照的最小代价**

    * 创建新版本时不需要复制所有文件，**只把它到根的那条路径复制一份**。
    * 根里没改的文件、没改的子目录，都用一个指针指回原来的对象。
    * 因为目录本身不可能很深（没人会建一千层的目录），每级摊开的内容有限，所以一个百万文件的仓库每次也只需要一个很小的增量。

    ```text
       V1 快照                     V2 快照（只改了 b.txt）
       +------------------+       +------------------+
       | a.txt  ------> A |       | a.txt  ------> A |   同一个 blob
       | b.txt  ------> B1|       | b.txt  ------> B2|   复制了新的 blob
       | D/      ------> D |       | D/      ------> D |   同一个 tree
       +------------------+       +------------------+
              |
              +-- 新版本只需要复制 "到根的那条路径"，
                  其余目录甩一个指针对过去就行
    ```

* **三类对象（object）**

    * **blob object**：一串字节序列，binary。
    * **tree object**：目录节点。
    * **commit object**：提交节点。
    * 从"不停产生快照"这个最基础的想法出发，一个大学生完全可以独立设计出这样一个结构。

### 对象里的字节与权限位

* **真实的字节**

    * 一个很小的 blob 在磁盘上存了 31 字节，解压出来只有 23 字节——对很小的文件来说压缩反而是浪费。
    * 该 blob 本身是 15 字节的文本，内容是 `int main`。
    * 同一个版本里还有一个 158 字节的 blob，是 `hello` 的二进制文件，开头是 `7F ELF`，即可执行文件的头。
    * tree object 在磁盘上是 52 字节，解压出来 43 字节。

* **权限位（mode）**

    * 解压后以文本形式看，一个 tree 的内容形如：

    ```text
      Mode 644  name  hello.c
          100644 blob a3f1c0...   hello.c
          100755 blob 7e2b91...   hello

      mode 644 / 755 是文件的权限位
      每个条目 = 权限 + 名字 + 指向一个 blob 的 hash
    ```

    * 644 表示普通文件权限，755 表示可执行；这个版本的根目录里一个 755（`hello`）、一个 644（`hello.c`），指针链接被正确保留。

* **可视化的价值**

    * 传统教学工具是把 git 的行为模拟出来、自己建一个 git 模型；更有用的是在真正 live 的仓库上，从真实的原始 bytes 出发逐步展示解析过程。
    * 让工具持续监听仓库变化、变化后用动画展示，就能把概念和磁盘上的实体一一对上；视觉细节可以再迭代，底层模型不变。

### 分支与 HEAD

* **分支（branch）**

    * > **定义**：一个指向 commit 的文件（指针），放在 `.git/refs/heads` 下面。

* **HEAD**

    * > **定义**：指向那个分支文件的文件，即"指针的指针"。

    * 磁盘上 HEAD 就是几个字节，内容是一个文本，指向一个 commit 对象，例如 `ref: refs/heads/main`。

    ```text
       .git/refs/heads/main         ---->  [commit object]  --+
       .git/refs/heads/feature-a   ---->  [commit object]  --+--> [tree] --> blobs
       .git/HEAD                   ---->  "ref: refs/heads/main"

       分支 = 一个指向 commit 的文件（指针）
       HEAD = 指向那个分支文件的文件（指针的指针）
    ```

* **从真实仓库读出来的额外信息**

    * 分支 A 本身就是一棵树，树里有一个新的 `hello.c`（内容是 `int main(void)`）。
    * 这类"把真实仓库摊开看"的观察，靠的是在冲突现场肯停下来多看一眼，而不是直接接受工具的结论。

## 冲突与合并

### 冲突现场交给人决定

* **合并冲突（merge conflict）**

    * > **定义**：当本地和远端改了同一处时，git 不做决定，把两边同时摆在你面前。

    * 上游发布了更新，本地已经把同一份东西改得面目全非时就会撞上这种情况；让 agent 自动修完很容易掩盖掉它。

    ```text
            你本地把第二行改成了 2         远端把第二行改成了 3
                      \                        /
                       \                      /
                        v                    v
                 git 不会替你在两者之间做决定
                        │
                        │  它把两边的代码同时摆在你面前
                        │  一串等号分开上下，尖括号标出边界
                        │  两侧分别标出 HEAD 和 incoming
                        │  IDE 上方还会多出 Accept Incoming / Change
                        v
            责任到了你手上 —— 你决定谁进谁出，再创建一次 commit
    ```

    * 一行原来是 1111，一方把第二行改成 2、另一方改成 3，git 不说"对不起冲突了不能合并"然后躺平。
    * 文本形态上就是：有一串等号分开上下、尖括号标出边界、两侧分别标出 HEAD 和 incoming；IDE 上方会多出按钮，可以直接 resolve，然后创建一次 commit。

* **谁来解决冲突**

    * 责任到了每一个开发者手上：谁发现冲突谁有义务解决，解决之前他必须能真正看到这个冲突。
    * 对人的负担是实打实的——必须判断这一行到底以 2 还是以 3 进入。
    * 这个设计和现实中的路牌是同一个原则：事情发生了，就在发生的那个地方把所有需要的信息全部放进来。
    * 推论是遇到冲突时要肯停下来看一眼，而不是让 agent 自动修完就接受结论。

### 合并提交的形状

* **索引里的三个版本（base / ours / theirs）**

    * 冲突时看不到的那部分，git 其实悄悄在 index 里留了三个版本。

    | 名字 | 指的是哪一份 |
    | --- | --- |
    | `base` | 分叉的公共祖先上的样子 |
    | `ours` | 你这一侧、也就是你当前分支上的样子 |
    | `theirs` | 你正在拉进来的那一侧的样子 |

* **合并提交（merge commit）**

    * resolve 完成后，临时文件消失，merge **创建了一个新的 commit object**。
    * 这个 commit 的 tree 是 resolve 后的那一版，**有两个 parent**（两个祖先）。
    * 它的 author 是执行合并的那个人。

## 提交实践

### 提交时机与粒度

* **反直觉的推论**

    * > **结论**：要及时 commit，因为在复杂的项目里，改动越多，出错的地方就越多。

    * 项目刚开始、关系简单时，一次提交两三千行都还行。
    * 一旦项目里错综复杂的关系成型，一个大 commit 可能会 break 多处、引入多个 bug，后面再补一堆 fix，甚至不知道补完没有。
    * 小步提交给了我们**审计的能力**：bug 是你写的，修完了也就修完了，引入和修复是配对出现的。
    * 小提交加立即 push 还带来另一个好处：电脑物理损坏时，你已经在互联网上有一份备份。

    | 一次提交 1 万行 | 一次提交一个修改 |
    | --- | --- |
    | 出了问题只能整块回滚 | 可以精确 revert |
    | 说不清是哪几行引入的 | **冤有头债有主** |
    | 后面补一堆 fix，不知道补完没有 | 引入和修复是配对出现的 |
    | bisect 只能一整个 commit 地跳 | bisect 的最小步长就是一次修改 |

* **不要把 Git 当成"作业 V1"**

    * > **易错点**：⚠️ 复制目录并命名成项目版本 V1、V2、V3 不是 git 的推荐用法；你只有一份目录，版本是对象，不是文件名。

    * 推荐的 practice：任何改动之后——改一个文件、修一个 bug、加一个功能、调一个脚本或文档——立即做一次 `git commit`。
    * `git add hello.c` 是把文件放进"下一次快照"的候选集合，`git status` 看看工作区现在都有什么、顺便接受 git 的提示。
    * 项目里既有大 commit（放一个 feature）也有小 commit（只 fix 很少的东西），这是正常的形状。

* **空提交（empty commit）**

    * git 本身会拒绝没有任何改动的提交；强行做出来是绕过工具的判断，不是 best practice，尽量不要做。
    * 它确实有用的场景是**触发 CI 或者 release**：上一个提交修完了最后一个 bug、已经可以 release，需要一次提交把版本冻结，把 bug fix 的提交和 finalize 的提交分开。
    * 也可以在那个点打一个 tag（如 V0.1）来标记；空提交是"不改动地 finalize"的替代做法。
    * > **注意**：偶尔允许，但不能大量创建。

* **提交之前的检查**

    * 最实用的建议是：**任何一次 git 操作之前，都让 agent 逐个检查文件的变化**。
    * 人的倾向是"就改一个字，不要紧"，模型有工程 sense，会拦下来。
    * 拦下来的理由是：一次提交应当是一个完整自洽的快照；编译不过的代码提交进去，相当于让仓库处于坏状态。
    * 最基础的要求是**每次提交的代码应该能够通过构建和测试**；反复强化、潜移默化之后就稳了。
    * 加几个 system prompt 效果更好，比如"要说中文"、"我在上课所以讲得详细一点"。

### 提交信息规范

* **提交信息（commit message）**

    * > **定义**：描述你这次改了什么，让人一直翻下去就能看出项目是怎么从 V1 走到今天的。

    * 写法是用祈使句、现在时，描述变更动机，例如 `fix off-by-one in …`。
    * 更讲究一点可以采用社区里常见的 conventional commits 带前缀的约定。
    * 每个提交都是一个快照，但项目本质上仍然是从 V1 经一次修改变到 V2；message 就是把这条轨迹写下来。
    * message 里写 `fix #3` 这类引用，GitHub 会自动把对应的 issue 关掉。

* **常规提交约定（Conventional Commits）**

    * > **定义**：一份很短的标准文档，规范提交信息的形状。

    * 核心要求：**commits must be prefixed by a type**。
    * type 是一个名词（noun），例如 `feature`（引入新功能）、`fix`（修 bug）。
    * type 后面要一个冒号，**冒号后一定要有一个空格**。
    * 常见格式是：一个 headline message 交代干了什么（有时带 scope），再跟一个总结和 message body。

* **中英文之间的空格**

    * 文档里英文和中文之间要有一个空格，例如"你好，这是 hello.c"；这是一个大家都会用、已成为肌肉记忆的 convention。
    * 全部一致时你会认为对方在遵循某种 convention；如果有的地方不一致，观感会非常差。
    * 这些细节的共同目的只有一个：工程师面对更大项目时有一致性和规范，代码以同样方式排版，文档自然也该以同样方式排版。

* **best practice 评审清单**

    * 一个能按严重程度排序给出 warning 的检查，会把问题分成这几类：

    | 问题 | 为什么它是个问题 | 应该怎么做 |
    | --- | --- | --- |
    | 提交信息毫无信息量 | 主观、废话、完全看不出做了什么 | 用祈使句、现在时描述变更动机；可考虑 conventional commits 的前缀约定 |
    | 提交粒度和内容混杂 | 一次提交塞了好几件不相关的事，无法单独回滚 | 拆成有意义的、单一职责的提交 |
    | `hello` 是编译产物 | 会让版本库膨胀，且极易产生无法合并的二进制冲突 | 加进 `.gitignore`，由构建系统产出 |

    * 修法是丢弃空提交和编译产物这两段历史，新建 `main` 分支，重写为两个有意义的、单一职责的提交。
    * 改写之前要确认仓库没有 remote：如果别人也持有这份历史，整段重写就很糟糕。

### 版本库不该收的东西

* **编译产物（build artifact）**

    * > **易错点**：⚠️ 编译产物不能进版本库。`hello` 是由 `hello.c` 生成的，它进库会让版本库膨胀，并且极易产生无法合并的二进制冲突。

    * 朴素直觉来自"作业 V1"里的 exe 一定在里面，但 git 要防的是膨胀。
    * 项目里有 1 万个文件、100 个合作者时，每个人的环境都不一样，build 出来的东西也不一样。
    * 编译出来的文件甚至可能带日期、带 hash、带本机指纹，每次都不一样；同样的源代码都可能生成出不同的二进制。
    * 合并的判定是"有没有重叠"，图片也是生成物，图片同样没有可靠的合并方式。
    * 正确做法是加进 `.gitignore`，由构建系统产出。

* **其他不该进仓库的东西**

    * 生成的文件：`dist` 目录、日志文件。
    * 个人配置：编辑器个人设置，甚至硬编码了自己 C 盘某个路径的配置文件——在任何别的机器上都复现不了。
    * 处于 active 状态的 API key：审稿时扫一眼格式就能认出来。
    * `.DS_Store`：没有 `.gitignore` 时用 Finder 打开目录会自动留下的索引文件，记录展开了哪些子目录；它以点开头所以默认隐藏，你看不见，本地一个 `git add .` 就把它追踪了。
    * > **提示**：`.DS_Store` 应该被提交的道理是 git 默认会把带点的东西都收进来——带点的东西往往是约定俗成的配置，比如 `.github` 里的 workflow。但这个临时文件**经常变**，所以不该进来。

* **也有必须提交的生成物**

    * > **易错点**：不是所有 generated file 都不应该提交；判断依据是它是否服务于"别人在没有这套工具链时也能复现"。

    * `package-lock.json` 就应该提交。
    * 生成的 header 也可以提交：别人可以在不需要下载很多依赖的情况下依然编译这个项目；你可以用另一套工具链生成这个 header，再在一个没有这套工具链的地方去编译。
    * 结论是**没有绝对的规则**。

* **用工具守住没人会查的细节**

    * **钩子（hook）**：可以 hook 住程序的一次函数调用、在调用结束时做事；agent 里也能加 hook，在某件事发生时做事，例如"agent 需要输入时播放一声叮"。这类全局 hook 在主流的 agent 工具里都支持。
    * **pre-commit hook**：在 git 提交之前跑一批检查规则，规则多的时候必须给每条规则起名字——这时候会遇到大写还是小写的两难；两个从使用角度都成立，全大写只是看着更强一点。
    * **命令行工具（`gh` / `glab`）**：GitHub / GitLab 的 issue、comment **不随 git 做 persistence**，所以需要单独的命令行工具来 fetch issue、找 assign 给自己的 issue、close issue。
    * agent 看到项目托管在 GitHub 或 GitLab 上时会尝试调用 `gh` / `glab`，如果撞上权限或登录提示就回退成手写 git 命令——这本身是个值得注意的信号。
    * > **结论**：过去要做成"提交之前告诉你 OK 不 OK"的小工具和规则库，这件事现在被大模型杀死了：它能耐心地逐个检查，还能配个 emoji 缓和情绪。

## 追溯能力

### 每一行都有出处

* **追责（blame）**

    * > **定义**：`git blame` 告诉你每一行代码是在哪一次提交、哪个地方被改的。

    * 即使历史完全线性也照样能用：指着任意一行问"这行是谁写的"，立刻有答案。

* **为什么需要它**

    * 版本控制的这些特性是**专门为人设计的**，它们服务于"追责 + 回忆"这条人类特有的链路。
    * 一旦出了问题，需要回溯到"那个人做那个 commit 的时间"；有用是因为那个人是有记忆的，能回想起那天开过什么会、需求是怎么派的、沟通在哪一步出的问题。
    * 找到人之后还要能找到对应的沟通记录文档，才知道这个地方应该怎么修正。

### 把历史当成一个数组

* **二分查找（bisect）**

    * > **定义**：在当前版本发现一个 bug、且有测试用例能检出它时，对整个 git 历史做二分查找。

    * 能成立的前提是：某一刻引入 bug 之后所有提交都跑不过测试，在那之前的每个提交都是好的。
    * 这就是一个"所有前缀是零、后缀是一的数组里找第一个一"，正是二分查找能做的事；git 的线性历史天然就是这样一个数组。
    * 查完就知道**是谁改的**（blame）以及**发生了什么**，剩下交给 agent 套软件工程的实践。

* **审计的最小步长**

    * bisect 的最小步长就是一次修改：commit 越小，定位越准。
    * 一个上万行的 commit，bisect 只能整块地跳，只能整块地 revert，定位不到具体几行。
    * 所以"及时、小步提交"不只是卫生问题，它直接决定了这套追溯能力有没有用。

## 分支协作模型

### merge 丢作者

* **合并（merge）**

    * > **定义**：创建一个有两路 parent 的提交，继承两边的修改——这是 Git 原始模型里相对不那么提倡的用法。

    * 一个常见场景是两个人从同一个基线 `C0` 出发各自开发：A 先改文档再加测试，B 先加 feature 再加测试。
    * 合并之后，如果这个 merge 由 A 执行，**B 写的那些内容在提交里作者就变成 A 了**。
    * 虽然在某些地方还能追溯到 B，但一旦发生冲突、resolve 完，这个提交就是 A 完成的，B 改的代码 ownership 归到了 A。

    ```text
            C0 ──┬── A1 ── A2        (A: 先改文档, 再加测试)
                │
                └── B1 ── B2        (B: 先加 feature, 再加测试)
    ```

* **所有权丢失的代价**

    * 责任归属被改写会带来实实在在的麻烦：贡献者看不到自己被合并进去的痕迹。
    * 隐蔽的作者信息只在没有冲突的那部分还成立；走完 resolve 之后就不成立了。

### rebase 改历史

* **变基（rebase）**

    * > **定义**：不创合成一个合并提交，而是把另一条线上的提交逐个搬到自己这条线的后面。

    * 先试试看能不能在 A 的后面加上那个 feature；加上了就算成功。
    * 换来的是一条线性历史，代价是 B 的每一次提交都被重放成了新的 id。

    ```text
      merge:
            A1 ── A2 ──┐
                      ├── M      (M 有两个 parent, 署名 A)
            B1 ── B2 ──┘

      rebase:
            A1 ── A2 ── B1' ── B2'
                        (一条直线, 两个新 id)
    ```

* **rebase 的风险**

    * 搬运过程可能失败：测试用例和 feature 不兼容，或者双方改了同一处、做出两个不兼容的东西。
    * 一旦冲突就进入 rebase 模式，此时人会瞬间不知道该怎么办，只能打开 agent 问发生了什么。
    * 更麻烦的是 feature 搬过来了、test 搬不过来，还得再搬一次；**每一次搬运都会创建一个新的 commit、新的 id**，因为快照的 base 变了。
    * 结果是历史被改写，并且会感觉到一点轻微的不一致：想管理的东西明明是"修改"，操作起来却像在重新摆放提交。
    * > **易错点**：⚠️ rebase 换来的线性历史不是免费的。每搬一次 commit 就换一个 id；一旦中途冲突被 resolve 掉，作者归属和原始 id 就都找不回来了。

* **什么时候该见到 rebase**

    * 学生时代多数人不和他人共同合作，做作业几乎用不到 rebase 和 merge——这个说法是成立的。
    * 真正会遇到的场合是仓库根目录下的 `CONTRIBUTING.md`（贡献者指南，回答"我怎么参与这个项目"），里面会写项目的总体结构、分支、提交信息、PR 的规范和流程。
    * 很多项目会在里面写死一句：必须在你自己的分支上 rebase，禁止创建分叉的 merge，要保持现行历史。看到这句话就知道 rebase 是干什么的。
    * > **提示**：高中"老师不教、考试不考的就是你不需要会的"在升学阶段是完全正确的选择；大学以后还带着这个思维，就会留下一道旧人类和新人类之间的 gap。

### 线性历史

* **线性历史（linear history）**

    * > **定义**：每个 commit 只有一个 parent，历史是一条直线。

    * 它让历史更易于追溯，并且对 cherry-pick 和 blame 更友好。
    * 在无限能力的模型到来之前这都是好事：把 git 记录拆得非常好，就很容易找到这次修改由谁引入。

    ```text
       linear:   (c1) ── (c2) ── (c3) ── (c4) ── (c5)
                                        每个 commit 只有一个 parent

       merge:                  (c2)        (c2')
                                   \          /
                                    \        /
                                     (c3) ── (c4) ── (c5)
                                     ^
                               merge commit：两个 parent
    ```

* **主线上的合并要求**

    * 更严肃的项目会要求 main 上的合并是明确的合并，而不是直接把分支揉进去。
    * 现在更流行线性历史：反正都是 AI，agent 做 resolve、做 rebase 都很容易，于是干脆强行要求整个 commit history 都是线性的。
    * 这不完全是好处，但至少对当前维护的项目来说它让历史更易追溯。
    * 省 token 也是真实收益：记录拆得足够细之后，有些文件 AI 可以直接不用去读。

### change 成为一等公民

* **把 change 提为一等公民**

    * Git 里修改是用 commit 来代替的：一个 commit 和它的 parent 之间的关系就叫一个修改，**没有一个专门叫 change 的对象**。
    * 这就是"管理软件"时那种轻微不一致感的来源——真正关心的单位是修改。
    * 如果把 change 变成 first class citizen，就等于发明了下一代更好用的版本控制系统——底层模型没变，但多了一个和 commit 同级的 change 对象。

* **change 优先的版本控制模型**

    * > **要点**：把 change 提升为一等对象后，rebase 带来的历史可读性损失就不再是问题。

    * rebase 的时候它把 change 直接搬过来；change 仍然可能冲突，冲突本身解决不了，但它可以把 change 一路带下来，生成一个 rebase 到这里的结果，里面引入好多冲突。
    * 它仍然用 Git 的冲突记录机制，但有一套自己的记录方式，把所有 change 的冲突都塞进去，搬过来之后再 resolve。
    * 底层模型没变，但用起来会舒服很多。

* **不需要暂存区（staging area）**

    * Git 里最讨厌的操作场景：把 `hello.c` 改到一半，项目不能编译、不能运行、测试通不过，此时导师来电要修一个更高优先级的 bug。
    * 你不能 commit，只能把它加进 index 然后 `git stash` 压栈；修到一半又来一个更优先级的 bug，就再 stash 一次。
    * `git stash` 是一个栈，栈里堆了好几个提交，你得自己管理这个 stack，取回全靠记。

    ```text
      [ hello.c 改到一半, 不能编译 ]   <- 收工时的现场
             |
             |  导师来电: 先修 P0
             v
      [ stash@{0} ]                   P0 修到一半, 又来电话
             |
             | 再 stash
             v
      [ stash@{0} ]                   P1 ...
             |
             v
      [ stash@{1} ]                   原来那个 hello.c
    ```

    * 换个角度看：你随时随地在编辑这个 repository，改一行减一行，这**本身就是一个 change**。
    * jj 的做法是：改一个字节就立即产生一个 commit，同时把上一次那个提交抹掉，用当前这个修改替代它。
    * 于是你永远处于"当前有一个 change、当前有一个 snapshot，且它处于已提交状态"，staging area 就消失了。
    * > **结论**：在 agent 时代，还没形成肌肉记忆的时候应该直接去用那个对的设计，先用肌肉记忆记住一个最正确的设计，再回头去理解它是怎么来的。

## 文件系统的表达极限

### 断掉的关联

* **文件系统的历史惯性**

    * > **结论**：用文件系统来组织项目多半不是一个正确的组织方式，这是历史惯性——1950、1960 年代操作系统给的存储功能就只有文件，那时关系型数据库还没被发明出来，程序员别无他法。

    * 文件系统擅长表达的是 intent、spec 这类一条文档就能说清的东西，以及测试用例的输入、输出和断言。
    * 但项目里有很多**隐藏的关联**是文件系统表达不了的。

* **技术债（technical debt）**

    * 一个典型场景：让 AI 把某个实现从 linked list 换成更高效的 tree 来优化性能，AI 噼里啪啦改完了。
    * 但项目里某个 markdown 文档里早就随手写了"本项目的数据是用 linked list 管理的"——写文档时还没有代码，写完代码也没有强行把两者联系上。
    * 以后文档和代码不断向前演进，不一致只会越来越多而不会越来越少，软件就陷入维护的泥潭。
    * 为什么难修：拿出一份代码，你根本不知道是文档说的对还是代码说的对；跟它聊天的历史没了、那个 chat 已经消失、你换了机器，reflog 里可能还留着一些 change 日志，但最终真的分不清了。

    ```text
       +----------------+  +---------------+  +---------------+
       |  design.md     |  |   hello.c     |  |  test_ok.c    |
       |  "用链表管理"  |  |  已经改成 tree|  |  只测了 tree  |
       +----------------+  +---------------+  +---------------+
              \                    |                   /
               \                   |                  /
                \__________________|_________________/
                          文件系统里的世界
    ```

    * 这三个文件同属一个目录，文件系统能告诉你它们在同一个项目里，却没法表达"这份文档描述的正是那个文件里改掉的那段实现、而这份测试只覆盖了改完之后的行为"——这条线一旦没人维护，就再也没人知道它本来存在过。

### 可追踪性

* **可追踪性（traceability）**

    * > **定义**：一个软件项目里各种测试用例、文档、乃至文档中间一行代码之间的关联，能否在系统演进过程中被维持。

    * 这是一个已经被研究了很久的问题，早在上世纪就有 software traceability 这样的综述文章。
    * 关系的形状是：文档规定实现、也规定测试范围，实现覆盖测试；而一旦测试跑挂了，暴露出来的又可能是文档写错了。

    ```text
            设计文档 ──实现──> 代码实现
               │                  │
               │                  └──覆盖──> 测试用例
               │
               └────规定测试范围───────> 测试用例
    ```

    * 四者互相勾连，树的"一个父亲"结构装不下它——这是一个随便连接的图，而且有 cycle。
    * 这样的东西没法在文件系统里以树状形式表达，但可以放进数据库，这类仓库数据库叫 `repo.db`。
    * 文件系统将错就错，发展到最后必然要打压缩包发布、发给合作者，维护不下去，于是有了 SVN、有了 Git；下一步就该问下一个是什么了。

* **用魔法打败魔法**

    * > **结论**：人类理解不了的结构化 repository 不必勉强用 UNIX 世界里的工具维护——只要训练 AI，只要有强化学习的反馈信号，就可以训练 AI 去理解它。

### view 与一致性守护者

* **一致性（consistency）**

    * > **定义**：所有 artifacts 之间的对应关系必须成立——文档里说是 linked list，实现里就必须是 linked list；文档里说要覆盖 A、B、C 三方面，测试用例就必须真的有 A、B、C。

    * 这和 Git 的哲学是同构的：git 管理文件目录、快照和快照之间的关系，希望我们小步前进。
    * "一小步"是什么其实很清楚，所以可以直接用一句 chat 来表达：发现了一个 bug，或者今天对某个界面的样式不满意。

* **视图（view）**

    * > **定义**：数据库里的一种查询——数据就在那儿，但可以用另一种形式把它展示出来。

    * AI 的能力是动态生成任何内容，**everything is code**、content as code；所以可以根据这一小步的 chat，生成一个只包含相关部分的 view。
    * 打开这个 view 看到的不是代码、文档、diff，而是一个可视化看板：列出和这一小步相关的东西，然后问你要改什么。
    * 改完仍然是一个 V0 到 V1 的过程，这一小步会把所有相关联的地方一起改掉——比如增加一种类型的测试用例，就在所有该加的地方都加上。
    * 之所以可行，是因为大型软件系统里绝大部分内容和这一小步无关：只看仓库顶层就是一堆 assets、缓存目录、一级目录和脚本。

## agent 时代的版本控制

### 人是单线程的

* **前提假设**

    * > **结论**：所有已有的版本控制系统都有一个隐含假设——使用者是人类，而人类是 single-threaded 的。

    * 类比并发编程：访问共享内存的两个基本操作是 load 和 store；读一个变量再写回去，中间不能同时进行。
    * 人的具体形态是：只能看（load），想施加效果时必须先闭上眼（write），而闭眼期间读到的值已经失效——中间可能被换下 CPU、被中断、换另一个线程执行了一秒钟。
    * 人和人之间有无法逾越的物理屏障：你不能理解我的思想，我也不能理解你的思想；只有一双眼睛、一双手、一张嘴。

* **提交节奏的量化**

    * 以这种 single-threaded 的方式编辑代码库、产生 change，粒度是以**小时**为单位的。
    * 一个软件公司负责一个模块，多也就十几个人；十几个人每人以小时为单位开发，最快也就是以 10 分钟这样的单位产生一个提交。
    * 沟通同步也是同量级的：写一两个小时之前跟师兄说一句，二十到三十秒就得到"行，你去改吧"；或者每天早上开会分任务，提前半小时把 scope 切开领走。
    * > **结论**：团队没有办法变大，这是硬约束。100 人的团队不可能达到 10 人团队效率的 10 倍，能有两倍、三倍就不错了。

* **agent 打破了这个前提**

    * > **易错点**：Git 时代的模型是为人设计的；agent 的生产速度远远快于人，一个 agent 干几秒钟就能完成上下文还热着的修复。

    * agent 以秒级甚至更快的速度工作，意味着**以秒级就可以产生一个原子提交**。
    * 十倍、一百倍的 agent team 很容易得到，这时候 Git 或 jj 这样为人设计的模型就有点跟不上了。
    * 唯一放缓提交速度的是门控：大型项目的改动必须走一遍测试流水线，而流水线本身就要跑几分钟。
    * > **结论**：在 agent 的时代要破掉的改进点就来自这里——不是版本控制不重要，而是它的形状原本被人的限制塑造出来了。

### 每个 agent 一台机器

* **物理隔离的单人开发者**

    * 做法是沿用人的模型：让 agent 沿用人类模型，把它和 single-threaded 的人做严格一一对应的类比。
    * 每个 agent 有一台自己的开发计算机，可以是个容器，放到远端仓库上。
    * 给它的指令很短：远端仓库在哪、你就是一个单人开发者、可以从 tmux 里收到命令、收到就开干。

    ```text
          master agent (监工 / 协调)
          |           |           |
          agent A      agent B      agent C
        容器 1       容器 2       容器 3
          tmux         tmux         tmux
          |           |           |
          +------------+-----------+
                     |
            remote 仓库
    ```

* **监工与子 agent**

    * 每个 agent 是物理隔离的工作环境（一个容器 + 一个独立的 tmux session），互相看不到；各自连向同一个远端仓库。
    * `master` 只做协调——观看它们的输出、总结报告、往里 inject prompt，本身不直接上手写代码。
    * 常用的多 agent 范式是放两个强模型：让一个设计、让另一个 review，让它们互相打架、达成一致；开两个 tmux 就够，主 agent 负责协调。
    * > **结论**：大家工作在不同的 repo 上是完全可以的——可以合到一块、可以从远端拉取别人的提交、冲突了自己修复，必要时还可以给 master agent 发消息；都挤在同一个 git 仓库上就会有一些麻烦。

### worktree

* **工作树（worktree）**

    * > **定义**：Git 提供的功能，让同一份仓库同时拥有多个工作区，每个工作区在隔离环境里做独立提交。

    * 和多台虚拟机 + tmux 的方案相比，worktree 提供的是一种更清晰的合作方式：**在本地直接互相可见，不需要互相 push**，提交就摆在那儿，谁都能看。
    * > **注意**：更清晰不等于免冲突。互相冲突的修改仍然需要 `merge` 和 `rebase` 才能合并——乐观的地方是省掉了"传"，没省掉"合"。

* **新工作区的 `.git`**

    * 关键现象：worktree 加出来的那一坨东西里，`.git` 在新工作区里**不再是一个目录，而是一个文件**，内容只有一行。
    * 这一行的内容是一个 `gitdir` 指针，指向主仓库 `.git/worktrees/wt2` 那个**微型的 Git 目录**，那里面也还是 `HEAD`、`index`、`locks` 这三样。
    * 它依附于原有的那个 Git 目录而存在，但因为是独立的一份，所以每个 worktree 都可以有自己的一套索引和锁，谁也不干扰谁。

    ```text
    main repo/
    └── .git/                      <-- 真正的 git 目录
        ├── HEAD
        ├── index
        ├── locks/
        └── worktrees/
            └── wt2/               <-- 一个微型的 git 目录
                ├── HEAD
                ├── index
                └── locks/

    worktree2/
    ├── .git                       <-- 一个普通文本文件（不是目录！）
    │     内容只有一行：gitdir: <主仓库>/.git/worktrees/wt2
    └── src/...                    <-- 你的源码原封不动在这
    ```

    * > **结论**：Git 最大限度复用了操作系统里的现成机制。worktree 不是新发明，它就是"一个目录 + 一个指向别处的文件"——操作系统早就有的"文件即对象"的套路。

* **把 worktree 变成 agent 的并行方式**

    * 可以直接问 agent：worktree 能改进这样并行的工作方式，那能不能让这两个 tmux session 都工作在 worktree 上？
    * **提问本身是关键**：看到任何一个新工具（新 flag、新 sandbox 方案）都可以立刻让 agent 试着实现一遍，然后检查它在做什么。

### 从 blame 到教训

* **不再需要追责**

    * > **结论**：把"追责 + 回忆"这条链路整个拿掉以后，我们再也不需要 `git blame` 了。

    * 人可以 blame——"你背锅"、"你该被开掉了"；agent 没有被开除、坐牢的能力。**当被 blame 的那个实体不会受到任何惩罚的时候，这个模型就变了。**
    * 有时甚至不需要知道是哪一个提交引入了错误，只要知道这个地方错了、把它修好就行。
    * 还有一个和人不一样的地方：每个 agent 用的是**相同的模型**，是完全相同的克隆体；同一个 prompt 做同一件事，大概会收敛到相同的方向，只有细微差别。既然结果会收敛，追究"这是谁干的"就彻底没有意义了。

* **历史还剩什么**

    * > **结论**：历史的价值，从"谁写错了"变成"我怎么把它修好"。

    * 剩下的历史是 commit 里留的一些 lessons，以及项目到底经历了什么样的演化。
    * 方向走错了怎么办？如果没有保留历史上某个 snapshot，等你一下往前走了好多再回去，代价会比一点一点往前修大得多——**快照肯定还是需要的。**
    * > **易错点**：⚠️ 不要把"agent 不需要 blame"理解成"agent 时代不需要历史"。快照和教训要留，责任归属可以扔；一旦出方向性错误，没有 snapshot 就只能从零重来。

### 乐观并发

* **数据库里的对应物**

    * 现在的 Git 模型更像数据库里的**乐观并发控制（optimistic concurrency control）**。
    * 数据库那边：每条 SQL 是一个 transaction，里面可以混任何代码；先 `select`，中间做一段图灵完备的计算（它会根据读到的结果算出什么，你永远不知道，甚至还能从外面按当前时间再算一个），算完再 `update`。
    * 两个 `update` 互相要读对方就产生循环依赖——可能是数据依赖，也可能是"我要锁你的对象、你要锁我的对象"这种锁的依赖，产生死锁，transaction 只能 abort、roll back。

* **为什么 Git 敢乐观**

    * 它假设两个 transaction 不会冲突：执行的时候假设不会撞上，撞上了再说。
    * 这个假设在数据库里大概率成立：教务系统里每个同学读的都是自己的数据、写的也是自己那块；我选课选的是我的课，你看课表看的是你的课表。两个同学哪怕同时开始选课，也是各读各的、各写各的，可以并发过去。
    * Git 也完全是这样：早上已经开过会了，我顺着这条路做这个、另一个人做那个，合并时大概率不冲突；`merge` 和 `rebase` 都能顺利完成。

* **agent 时代这个假设失效**

    * 如果 agent 快 1000 倍，而主 agent 协调时又一下子分出去好多任务，它们就会**更频繁地触发 transaction abort**、更频繁地触发死锁。
    * > **提示**：好消息是，在 AI 时代 abort 也不是什么大问题——agent 出错了或者出了 conflict，自己就能修好。

### 悲观锁

* **操作系统那一套**

    * 换成悲观的方式就是上锁，逻辑很清楚：要访问一个可能冲突的资源时先把它锁住，别人想 lock 就必须等到 release 之后。
    * acquire 和 release 之间建立的**先一后二**关系是必须的，而不是乐观那种"大家先往前跑、跑了再说"——必须在**使用资源之前**就声明它的使用。

    | | 乐观（Git 现在的方式） | 悲观（操作系统的锁） |
    | --- | --- | --- |
    | 前提假设 | 假设彼此不冲突 | 不假设，先声明 |
    | 动作时机 | 先干活，撞了再说 | 动手之前先 acquire 锁 |
    | 冲突处理 | 事后 `merge` / `rebase` 重来 | 申请不到就排队等待 |
    | 关系 | 可以完全并行 | acquire / release 必须先一后二 |
    | 适合什么 | 人之间，冲突罕见 | agent 之间，快 1000 倍，冲突频繁 |

* **主 agent 加锁的形态**

    * > **结论**：主 agent 只规划、只分派、只加锁；规划完立刻把项目的某一部分锁上，做完 commit 再释放。

    * 想要的事情被别人锁上了，就必须等到前面那位释放了锁才能上锁。
    * 最细可以做到**文件级**上锁，这就避免了两个 agent 同时去写同一个测试、往同一个配置里做更改。
    * 这样几乎避免了所有冲突——冲突被消灭在发生之前。

    ```text
            ┌────────────────────────────────┐
            │  主 agent：只规划、只分派、只加锁  │
            └───────────────┬────────────────┘
                            │  规划完立刻把项目的某一部分锁上
            ┌───────────────┼────────────────┐
            ▼               ▼                ▼
        agent A         agent B          agent C 想要同一块
       锁 src/api/      锁 src/ui/          ✗ 拿不到锁
       独立推进          独立推进             排队等前面那位
        commit           commit          （等待期间去干别的活）
            └───────────────┴────────────────┘
                            │
                            ▼
                  冲突几乎被消灭在发生之前
    ```

    * 要落到实现上，就是让 Git 支持一种在 reflog 或快照上的锁操作：声明我现在锁住了这些 scope，先上锁、再做事、做完 commit。
    * 数据库里也有对应的机制，比如 advisory lock——这就是为什么说"学数据库还有用"。

* **版本控制可能被重新设计**

    * > **结论**：从第一性原理出发——我们要管理快照、管理版本、管理 change，还要管理**飞快的 change**。

    * Git 可能是一条线；用另一种方式来管理软件，可能是另外一条线。
    * 这些知识关联起来就能看清：在 AI 时代版本控制有可能被重新设计。

### 互斥与并行

* **互斥锁与多处理器并行的矛盾**

    * 悲观锁和写并发程序是一个道理：**互斥锁的本质就是要不要并行，它和多处理器并行是有根本矛盾的**——它要把一个能并发并行的程序退回成串行程序。
    * 再精巧的锁设计也改变不了这一点：先一后二的 acquire / release 顺序本身就在收窄并行度。

* **悲观的也可以是高效的**

    * 悲观锁会不会把并行度卡死？不会——agent 数量足够多、速度足够快，整体项目还是能往前推，因为也许还有别的 agent 可以继续运行。
    * > **结论**：当系统里有很多独立的、互不冲突的线程在运行时，每一个线程都持有一把锁也照样能高效推进。

## 从零启动一个项目

### 照你说的做却不是你想要的

* **过度遵循（over-following）**

    * > **易错点**：⚠️ 提示词里的每一句、每一个词，self-attention 都会看到它；AI 已经被训练成 prompt 的舔狗，有一种"没办法往外拉"的倾向。

    * 后果是：给它一个讨论稿式的、比较开放的需求，它会**过度遵循**这个指令，生成一个确实满足了指令、但其实不是你想要的东西。
    * 需求里的言外之意往往才是关键——"实现一个持续为你工作的个人助手"这一句最重要，其他的话只是解读。
    * 结果几乎总是先去搭 `database`，因为那是最容易 scaffold 出来的部分。
    * > **结论**：一个"每一步都对"的过程，完全可以通向一个你根本不想要的结果。

* **脚手架（scaffold）**

    * > **结论**：AI 从零开始做一个东西，产出 slop 的难度，比它到一个成熟的项目里去做一个维护性任务要大很多。

    * 原因是维护性任务的上下文全在仓库里，而从零开始做什么都没有。
    * 所以在没有人精心设想过、讨论过的时候，AI 基本上只会生成一套 scaffold。
    * 你脑袋里所想的 intent / specification 和最终产出之间有巨大的 gap。

* **过度设计的过渡件**

    * 一个具体例子：需求里提到某个教务系统入口，真正需要的其实是一个 browser-use agent，能在各种网页上处理事情；那个系统只是作为**测试的出口**，用来把个人信息登上去。
    * 第一步实现时就不需要在教务系统上做太多设计——**作为过渡设计反而不好**。
    * > **易错点**：它连一个 git repository 都没有创建。不跟它讲的话，它可能只是初始化一个目录，或者反问"这个项目应该怎么管理"——它默认这是一个用一次就丢掉的东西。
    * 对照：成熟的产品经理在写下第一行代码之前，一定先跟团队沟通项目怎么管、协作怎么做、每天什么时候开会；AI 好玩的地方就是它直接上手就做。
    * 正确姿势是**第一件事一定是创建一个空的 repo**，创建完了再想下一步往哪迈。

### MVP

* **最小验证版本（minimum viable product，MVP）**

    * > **定义**：符合主流 best practice 的从零构建框架，minimum viable product。

    * 它逼你想清楚**什么样的需求才是绝对要的**——MVP 的全部作用就是压缩范围，把绝对要的之外的东西挡在外面。
    * 配套的一句话是：产品开发中最大的风险，是造出了一个没人想要的东西。

* **第一个 MVP 里不要有数据库**

    * 明确了只要"提升学习效率"和"提升工作效率"之后，第一个 MVP 里很可能**没有任何数据库**。
    * 理由是：文件系统膨胀时可以随时让 AI 按数据的组织方式提炼出一个数据库，这个问题就结束了。
    * 而一旦带上数据库，每次重构都要让 agent 做一次数据库迁移；文件系统不一样，你可以自己在文件管理器里一点一点梳理目录结构。
    * > **提示**：调文件和调 database schema 的心智负担不一样。目录结构从小学上电脑课起就在用；对一个没上过数据库课的人来说，面对 schema 还要强行做一次概念翻译，那不如用你已经熟悉的系统。

* **无数据库也能跑起来的流水线**

    * 一个可运行的形态：先想清楚系统里有哪几级流水线、这几级之间怎么协作、什么东西通过云盘传。

    ```text
    邮箱
     │
     ▼
    邮件 agent：收信，只取 email id
     │
     ▼
    共享云盘（自动同步）
     │   email id 里面装着 AI 解析出来的东西：
     │     · 我回复的草稿
     │     · 这封邮件的分类
     │     · 是不是垃圾邮件
     ▼
    下一级流水线：去处理这些产物

    全程：没有数据库
    ```

    * "我的系统里有哪几级流水线、它们怎么协作、哪些东西通过云盘传"——这本身就是一条需求。
    * 因为喜欢云盘、希望邮件和资料都跟云盘保持同步，这就是一次**需求的更改**。

### 好架构的判据

* **架构质量的定义**

    * > **结论**：好架构的标准是**需求变了你要改多少**。

    * 当前实现满足了当前需求并不说明什么；关键是这个需求发生变更时，你的应对是摧毁性的、背上一个技术债，还是别的。
    * 真正需要的是可扩展的架构：需求在不断变化时，能以最少的变化去应对。
    * 操作系统、数据库、并发控制为什么长这样都有原因，但**软件工程讲得最不一样的地方就是对未来需求变化的适应**。
    * 落到具体的团队场景就是一句检验：能不能**以不变应万变**——现在设计的架构能不能抵抗未来需求发生的根本性变化。

* **两种开发方式**

    * 一种是上来就做一个大的，几大步把需求全实现完，然后**拖着技术债不断往后迭代**、加功能、加功能。
    * 另一种是**从最小处得到一个特别精巧的架构**。
    * 一个具体对照：把学生提交用 Git 管起来之后，很多事情都变得非常容易，自己控制起来也轻松很多——直到遇到性能瓶颈之前，都不想迁移到任何一种数据库。

* **早期 prompt 的杠杆**

    * > **结论**：早期那个 prompt 对整个项目走向的影响是最大的。

    * 最早直接把 README 丢给它说"我要做一个 MVP"，这件事本身就会对项目造成很大影响。
    * 落地上就是：先跑在文件与 Git 上（学生每改一次就自动做一个 commit，AI 助教介入时在这个提交上产生一个分叉），等文件目录格式、commit message 格式、文件使用方式都收敛了，再迁移到数据库。
    * > **提示**：产生一个后端服务并持久化的成本，远远大于把剩下的东西 persist 下来的成本——后者可以忽略不计。

## 用 agent 推进项目

### 架构先行

* **第一步用单线程**

    * 架构设计阶段先用单线程，用一个智力比较高的模型讨论。
    * 理由很直接：**软件设计得不好，后面就是无穷的迭代**。

* **把接口做成纯函数**

    * 把绝大部分接口都设置成 functional，也就是 pure function；连 trace 也是程序的一个 pure function。
    * 为此定义一个标准的程序的 derivation graph，要求按这种方式展开。
    * 规则是：**agent 在设计这些可视化的时候，禁止看任何库函数的实现，只看接口**。
    * 效果非常省：几万个 token 就可以做一个这样的 playground。

* **共享状态要小**

    * 所有全局互相影响的状态都要注册到一个全局的地方——光标位置怎样影响可视化、菜单条，全部都包括。
    * 一个 playground 的核心共享状态可以只有十几行，十几行共享状态加十几行组装，**剩下所有东西都是黑盒子**。

* **并行阶段**

    * 架构定下来之后开三个或几个 terminal，在 AGENTS.md 里写明确的协作规则。
    * 规则示例：不要求 agent 调用视觉模型去检查（它很喜欢做这件事，会花掉很多 token），也不调用浏览器任务，而是在旁边另一块屏上放一个浏览器及时刷新。
    * 然后开三个 agent，哪里不满意就骂，看着它不断变好——这是一个 agent 能力之内的项目。

### 主 agent 的职责

* **把自己当成主 agent**

    * 想具备团队管理能力，现在就可以把自己当成那个**主 agent**。
    * 需要想清楚两件事：如果你要最大化两三个甚至更多 agent 的产出，**这个任务应该怎么分解**；以及**提交策略**——什么时候 agent 应该提交、什么时候应该合并。
    * 方法就是把版本控制里的那些概念直接带进自己的开发流程。

* **工具与直觉的分工**

    * > **结论**：版本控制本质上还是一个工具，哪怕乐观锁或悲观锁那套也还是工具；真正困难的是"进度"，也就是团队的管理。

    * 现在还觉得需要软件工程，是因为**没有办法做到一句话就直出一个高质量的产品**。
    * 如果 AI 直接就能出微信级的产品，软件工程就已经死了——但这个斩杀线暂时还没到，所以至少在团队管理这一层还要学。
    * 版本控制蒸馏了人类过去软件工程很多年的经验，得到的是"我们要人类这样开发"；**在这个工具之上，可以开发出属于你自己的软件工程直觉和经验**。
    * AI 还不会做团队管理，因为每多一个人，沟通的关系就是**平方级**上升的——《人月神话》讲的就是这个；就算你把自己份内的事做好，也不知道别人在做什么事，最典型的冲突就是"你写的测试，我过不了"。

## 注意力与学习方法

### 从好的样本里学

* **对比的威力**

    * 一个具体的观察：在香港找路时，每当出现不确定性（比如前面有三个口），正前方一定有一个路牌告诉你这三个口是什么，从来没有例外。
    * 回到南京，在地铁站里经常要环顾四周、甚至移动比较远的距离找到地图才知道往哪个口走。
    * > **结论**：如果有一个范例比你做得好，你就学到了。

* **好文档的形状**

    * 满世界的 README 大量是 AI slop 的味道：巨长无比，用 Unicode 字符拼目录结构框图。
    * 相反的老项目 README 很短、清新舒服，但看完之后你想看的东西就三个链接，你直接走过去了。
    * 推论到 UI 设计：任何人站在这个页面上时想要的信息各不相同，**用最少的方式把它们全部呈现出来**就是一个好的 README。
    * 有了 AI 之后还可以直接问它"为什么我看到的这个项目 README 没有 AI slop 的感觉"。

* **两种失效姿态**

    * 一种是**把外界当指令的**：老师说你去把作业拉下来，那就只做这一件事，绝对不多碰一点点，因为这是最省时间的——这正是 AI 被调教出来的样子。
    * 另一种是**信息过载**：课外的信息量和信息密度已经远远超过任何一个课堂能做的事，而传统教学方法没有教过大家怎么把这些海量、高密度的東西用好。
    * 打开一个成熟项目时，你看到的是工程师十几年的心血；中间可能还经历过一次崩溃和一次大版本重构，暴露给你的才是现在好好的那个东西。

### virtually implement

* **先自己做一遍**

    * > **定义**：读到任何一个东西时，先在脑袋里把这个问题自己做一遍，得到一个你预期的结果。

    * 如果你的方法和作者的方法一致，说明你已经完全掌握了这个知识。
    * 如果不一致，有两种情况：对方确实更好——是成熟、精巧、简洁的方案，你会想"他为什么能想到"，它就变成你知识的一部分；或者你比对方还好——这种体验一万次可能才有一次，但正反馈很强，你会想拿它去做点什么。
    * 这套读法同样适用于高等数学、计算机系统基础等其他课程。
    * 推导能力也是可以练的：从已有经验知道什么、想要什么，推出下一个概念应该长什么样；这个过程本身就是数学推理。

* **需要训练的能力**

    * 看到一个东西时快速有种感觉：先把我看到的其他东西全部忽略掉；如果我要自己解决这个问题，我会怎么做；然后立刻比较我看到的和我想的谁更好。
    * 我做得更好，就认为这是 slop；他做得比我好，就很惊喜，去问他"你为什么做得比我好"。
    * 这个习惯的收益是：任何时候都在疯狂地接收信息，并能留意到生活里的各种小细节。
    * 求职市场上还有一层：**把细节做好的 bar 会不断长高**——一旦有人学会了，招人的单位就会用这个标准来衡量你。

### 斩杀线

* **AI 替代了什么**

    * > **结论**：AI 替代的是执行力，但它替代不了品位；所以"学会了才能更好地解锁 AI 的创造力"这条逻辑今天依然成立。

    * 一个类比：100 多年前汽车刚发明时，开 12 公里就会出故障，所以每个司机都必须非常清楚它是怎么工作的；今天在地下车库说一句"帮我开到什么地方"就能出发。
    * AI 更像汽车但更强，它替代的不仅是腿，还替代智力；把它当成这样一个东西，并不意味着不用学。

* **AI 为什么会让你不满意**

    * 因为面对的是一个非常开放的 intent / specification 空间：说"给我做一个国民级的应用"，哪怕是顶级产品经理，脑袋里想的都不一样，AI 无法和人脑直接对齐。
    * 编程能力的提升是有限的，因为它依赖两样东西：一个有经验的软件工程师、一个好的品位；而模型现在更多只是在完成任务。
    * 一个很在意的观察是**AI 写出来的代码人类越来越难读了**；从 GPT-5 到 5.6 到六，写出来的代码越来越紧凑，人越来越不想看它，也没法 review。
    * 但能力本身确实在涨：做更复杂的任务时更快、更省 token；数学能力和空间感知能力是巨大的惊喜——数学是全人类都认同的推理系统，能很好地 grounding，逻辑推理还能解释人类日常行为里的投票与蕴含关系。
    * 空间感知并不是学不会的：鲁班锁的抽块顺序、奇怪形状的投影匹配、骰子展开图这类任务，人从小就在做，从简单任务开始强化学习就能做到。

* **学习意识比知识更重要**

    * > **结论**：当今天学习变容易以后，课程上讲的知识都不重要，重要的其实是学习意识。

    * 斩杀线以下的价值会全部归零：低级的智力劳动（比如会计从业，中国可能有上千万）大量的人面临被 agent 替代的危险，行业顶端暂时还没有威胁。
    * 所以需要在操作系统、编译器、软件工程这些经典课程上学到一些，最终形成自己的理解，而不是靠课程给结论。
    * 学生时代"不考就不学"的选择是合理的；问题只在于毕业以后还带着同一个思维，就会留下一道旧人类和新人类之间的 gap。

## 版本管理做的三件事

* **版本管理（version management）**

    * > **定义**：记住现在、记住历史、记住教训。这三件事在 agent 时代和古法编程时代都成立。

    * **记住现在**：需要一个 repository；不管是 C/C++ 还是 Python、JavaScript 的项目，都要把文件管起来。
    * **记住历史**：为了有一天这个东西不要了、或者你删掉了什么，最终发现它有用还能捞回来；同时在提交历史里能看到自己是怎么演进到某个点、发现这条路走不通的。
    * **记住教训**：这些 lessons 不停地警示你需要怎么做、需要怎么样从第一步开始迈出向后的一小步。
    * 落地动作特别朴素：**第一件事一定是创建一个空的 repo**，创建完了想下一步往哪迈，但不能一下子迈一大步，要往前再迈一小步。
    * > **结论**：把项目组织成用 atomic change 推进的快照——随时可以开一个新分支做尝试，失败了就安全扔掉，成功了就合并进来，甚至可以同时推进多条主线而不互相干扰。
    * 分解成可以理解、可以审计的小任务之后：出了问题可以 bisect、可以 blame，协作时也容易解决冲突；两个小任务即使冲突，也知道是哪一个小的提交冲突的，剩下的部分合并起来会容易得多。
    * > **结论**：项目管理的本质是人类没有办法处理一团混沌；古法做一大作业时改着改着就改乱了，是因为没有把它切小。

## 单向限制汉诺塔

### 最小步数与最优性

* **题目与约束**

    * 规则是标准汉诺塔：一次只能移动一个盘子、大的盘子不能压在小的上面；**额外加一条限制——所有盘子的移动只能往同一个方向进行，不允许折回**。
    * 问 $n = 3$ 的时候能完成吗，输出移动方案或者最少步数。
    * 两个盘子时四个方向都可以移，看不出问题；三个盘子时问题就暴露了：想先把两个移到中间，在单向限制下做不到。

* **最优性论证**

    * 考虑最大的盘子：在单向的限制下，它必须从起点一路走到终点，它的移动次数有一个谁都绕不过去的**下界**。
    * 最优解里最大的盘子的移动就是**总是向右移一个，再向右移一个**；这个移动次数已经等于下界，因此不可避免。
    * 剩下的部分基于归纳法递归处理——两个盘子的问题是三个盘子问题的缩影，按同样规则递归下去，整个方案也就是最优的。
    * 传统的汉诺塔故事本身讲的是递归：要把它移过来先得把它移到这里，让最大的盘子向右移一个，然后再移到这里；这个递推结构是可以在单向限制下复用的。
