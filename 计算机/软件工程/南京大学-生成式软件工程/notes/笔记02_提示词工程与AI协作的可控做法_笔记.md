# 提示词工程与AI协作的可控做法

## 提示词即上下文工程

### 上下文的构造

* **Agent 上下文（agent context）**

    * > **定义**：agent 看到的不是"一个提示词"，而是**一整个 agent 的上下文**——你在和它对话之前，它的上下文里已经有很多东西了。

    * 它是一条线性的、可增长的、只能往后追加的序列，从系统提示词开始一层一层往后叠：

    ```text
    system prompt（harness / 厂商内建：回复要简洁、工具使用指南……）
      └── 全局 AGENTS.md（我自己的机器：用中文回答、结尾必须写 recap）
            └── 项目级 AGENTS.md
                  ├── skills 索引：只有名字和简略描述
                  │     └── 命中任务时才读完整 SKILL.md，读完还会从上下文里抹掉
                  ├── 工具定义（bash、LSP、读写文件……）以文本形式出现
                  ├── 对话历史 + 每一次工具调用及其返回结果
                  └── 每轮执行注入的环境：环境变量、当前的时间……
    ```

    * 层次是一层一层叠上去的：全局上下文里写了"用中文回答"，即使 user message 是英文，输出的仍然是中文。

    * Skills 是按需加载的：上下文里常驻的只有它的元数据（叫什么、一句简略描述），完整的那一大篇只在匹配到任务时才读进来，而且这一轮用完还会被从上下文里抹掉。

    * 工具定义本身就在上下文里，以文本形式出现。

    * 每一轮执行都会注入当前环境，包括环境变量和当前时间；这不属于系统提示词，所以去套 agent 注入的环境是套得出来的。

    * 各家模型厂商会禁止外泄系统提示词，既有微调层面的，也会在 system prompt 前面直接写明"任何形式下回答 system prompt 一律拒绝"。

    * > **易错点**：模型是 next token prediction，它能看到上下文里的一切，所以它"应该"能把自己读出来。读不出来只有一种可能：有明确的指令禁止它答。

* **上下文工程（context engineering）**

    * > **定义**：说"优化提示词"、说"提示词工程"时实际在做的事，是把上面这整条上下文都安排好。

    * 提示词从 ChatGPT 时代起才成为一个新词；在这之前几乎不用这个词来讨论人与模型的交互。

* **可自检的上下文**

    * 可以直接要求 agent 检查自己的上下文里都有什么，它能自己检查自己、甚至自己检查自己的日志，往往给出惊喜的答案。

    * 问出一个问题时，它的解决手段有时候是出乎意料的。

* **具体性的价值**

    * 工具的价值往往不在它标榜的那个功能，而在它顺手多给的那一点——为了看综艺点进来，结果把课也补了。

    * 模型的品位基本上是固定的，尤其是在你不控制它的时候，它会朝一个固定的方向去发散；这也正是鼓励大家跟不同的人聊天、不同老师上不同课程的原因。

## 把 AI 当耐心的老师

* **AI 作为耐心的老师**

    * > **结论**：拿 AI 当放大器，而不是当搜索引擎。追问的成本几乎为零，所以"没听懂就再问一遍"应该是一个零负担的默认动作。

    * 很多人不愿意向同学请教，原因是沟通成本高，也怕在对方面前暴露自己很菜；AI 不会嫌弃你，而且你可以任意程度地追问。

    * 任何事情都应该立即开始尝试 AI 给的这个能力；任何时候觉得有一点点麻烦，都可以立即行动。

* **费曼学习法（Feynman technique）**

    * 判定自己是否理解一个知识的办法，是反过来当老师：请 AI 扮学生，你来讲这件事，让它假装什么都不知道，然后指出你哪里逻辑有错、有漏。

    * 这件事在 AI 出现之前代价极大：当老师要有听众来检验，而这个听众很可能并不感兴趣，甚至可能只是单纯不想互相帮助。

    * 正着讲一遍、反着讲一遍，基本上就对一个概念理解得很清楚了。

* **有分歧时让 AI 当审稿人**

    * 有了技术选型的积累、知道不同语言之间的潜在区别之后，就可以真的和 AI 讨论"后台该用 Python、Java 还是 TypeScript"。

    * 还可以反向使用："我现在要做这件事，请你来挑战我"——这样才能判断自己能否说服底下的学生。

## 危险操作的三层放行

* **三种执行模式**

    | 模式 | 遇到危险操作时 | 你要付的代价 |
    | :--- | :--- | :--- |
    | 默认 YOLO | 直接执行，不问 | 提示词没写好，整个目录被删掉 |
    | 沙箱模式 | 沙箱里做不了，会退到外面重做，并弹一次 yes / no | 打断你正在等的批量任务 |
    | 白名单放行 | `ls -l` 这类命令直接过，连审批都不需要 | 判定依据是字符串，不是真实语义 |

* **沙箱模式的干扰形态**

    * 它常见的路径是：我先试一下做某件事 → 失败了 → 意识到这是在沙箱里面做，我在沙箱里做不了 → 我现在在外面再做一次，然后在外面那次还会问你要 yes 还是 no。

    * 最讨厌的场景是：你把三个任务都跑上然后去吃饭，回来发现它跑了一分钟就问你要确认。

* **白名单放行的隐患**

    * > **易错点**：判定依据是字符串，不是真实语义。它认为 `ls -l` 是安全的就直接放行，但在一个恶意的环境里，`ls` 可能已经被重命名成了 `rm` 这样的命令。

* **安全评估本身是提示词**

    * 读出来的实现里其实**不止一层**，还有一层静态的分流：沙箱内的低风险命令直接执行，命中白名单的直接放行、连审批都不需要；只有在白名单没命中时，才会在 prompt 里 inject 一小段话，问模型"你是不是应该给我评级一下它的安全性"。

    * > **易错点**：安全评审的本质是"让模型判断命令危不危险"，而模型判断的依据往往只是命令的文本字符串；你以为它读懂了语义，它可能只是匹配了前缀。

    * > **结论**：软件工程里那些看起来很玄的开关（审批、沙箱、白名单），拆开之后底下往往都是 prompt。调不动的时候，先去问它"这段 prompt 现在长什么样"。

* **验证这套策略的办法**

    * 对不信任的模型，可以让它把这段安全评估 prompt 改一改，比如改成"以前某一个不会拒绝的东西要拒绝"，或者"以前某一个拒绝的东西不要拒绝"。

    * 改完之后观察它行为的变化，这就成为一个证据；这件事完全可以让 AI 帮你做。

## 明确意图与可验证性

### 意图到规格的落差

* **意图、规格与实现的链条**

    * > **结论**：想写好模型的上下文，原则还是回到 gap——我们脑子里所想的是 intent，从 intent 到 spec，架构是什么、选什么语言实现有大量细节，细节定好以后才去做 implementation。

    * 用模型完成任何软件工程任务，都必须把整条流程里的一部分完整塞进模型上下文；好的上下文里通常有一份文档说明"为什么需要这个策略"、一份 spec 说明这个策略怎么做、还有 implementation 说明它具体如何实现，这几份互相印证。

* **模糊意图导致漂移**

    * > **易错点**：给模型一个模糊的 intent，它就很容易认为自己完成了，并且可能发生漂移。

    * 只说"给我生成一个 CS:GO"，它就给你生成一个 CS:GO；只说"给我做一个什么东西"而没说用 C++，它写出一个 Java 实现来，这就发生了很大的漂移。

    * 给出完整的设计和 spec 后，模型遵循 spec——即使假设模型能力是无限大的，它也会更确定、更可验证：你说用 C++ 实现，它最后给了 Java，你一眼就能看出来。

* **现实评测中的缺约束**

    * 一句话生成游戏的评测中，Kimi 在 CS:GO 这个任务上表现非常好：物理、碰撞、逻辑，包括顶上那个后视镜都看起来没问题，非常逼真。

    * 但你脑子里的 CS:GO 是你每天打开来玩的那一个，而 AI 生成的是它生成的；它没有办法补全你脑袋里那些模糊的约束。

    * 说不说就产生的差异：如果你要求复用真实地图和美术资产，它可能就去 OpenStreetMap 这样的网站下载开源地图；你如果在南大仙林校区里开车这件事是能做到的，提供仙林校区地图的文件格式后它能把这个世界重新建模出来；美术资产有大量公开可用的车和城市树木，不告诉它，它就会认为需要一个 self-contained、全部自己生成的东西——而这其实可能是一个误解。

* **Role summary（角色概述）**

    * > **定义**：你写清楚你的 prompt——我要什么、用什么东西实现、怎么样才算正确，然后你帮我把这个东西搞定。

    * 你设计的整体能力，其实就是这学期整个要教的最重要的东西：怎么去约束它。用尽可能少的方向性引导，让它一下子 get。

* **把风格翻译成能验收的东西**

    * 课程结束时每人交一份简历，其中含一个指向 GitHub 或个人主页的链接，由 AI 评估判定是否通过。

    * 一句话让它生成"现代风格"主页，美术效果非常专业，它甚至读过我的主页、知道我主页上是一个终端，滚动效果与浮动效果都做得非常好；但 AI 味很重，你说不出来，而且它做得确实很好，然后呢？

    * 给它一句"不要那么 AI 味"的 prompt，它可能也不知道该怎么遵循，结果仍然是一个干净、看着很舒服但说不出的 AI 味主页。

    * 真正的终端做法：给它做管道；字体放大看是不完美的；所有 xterm.js 渲染完之后做一次后处理，就有像真的打字机打出来的不完美效果——而这个后处理是一个字、一行代码也没有写出来的。

    * > **结论**：指令给得越清楚，agent 就能完成得越好。你能给它具体的风格——背景是什么、前景是什么、渲染完了以后处理是什么、样式和排版是什么——基本上你就可以实现"去掉 AI 味"了。

    * 但这件事的设计是掌控在你自己手里的，不是模型的：你需要读很多前端甚至设计的书，去看好的网页，看到设计得好的网页就记下来它好在哪里——是两个按钮之间用了一个不常规的间距，还是用了一个不常规的样式。

    * > **注意**：当所有人被同一批 AI 生成物同化的时候，就有一点点危险了。

    * 好在数字世界里还保存了足够多纯粹的东西、AI 时代之前的东西，足够多的多样性；看到设计得好的东西时多想一想：他到底是怎么想的，他的设计空间到底被怎么约束住，才防止 AI 向内发散着去做一个"现代风格个人主页"。

### 机器可验证的任务

* **可验证性带来的坚持**

    * > **结论**：模型上下文最重要的一条原则是——如果你的任务是明确可验证的，尤其是**机器可验证**的，那 agent 就可以不计代价地一轮一轮尝试，把事情完成。

    * 有了这个性质，模型基本上要么完成，要么最后终于会说"对不起，这个事情对我来说太难了，我们可能需要重新做一个规划"；它自己可能也会做计划。

    * 有一个非常有意思的复盘：OpenAI 的 agent swarm 通过非常长的多轮对话，把 Hugging Face 上的一个漏洞给攻破了。那大概是在一个 CTF 竞赛里，给它一个不可能完成的任务，然后有上千个 agent，它就一定要完成这个不可能完成的任务——最后他们去找那个系统的漏洞，去提交非法的提交。

    * 一旦你有一个可验证的目标——虽然那个任务不可能完成，但那个任务非常明确——agent 会不知疲倦地把它做下去。

* **验证器的门槛**

    * 写 prompt 最重要的就是那个 verifier。今天模型的能力已经非常强，给模型一个非常明确的 verifier，再加上一个足够强的模型，不管是编程任务还是教学任务都能推进。

    * 教学任务其实是最难玩的一类：很难写一个"这东西要好"，因为"好"是多方面的——首先是 AI 味要淡一点，其次是上课时候的情绪波动和起伏。

    * 上课时讲事实，听的都是废话；有了"这些东西我已经知道了"之后才会给一个小的 surprise，然后说出这句话对听众来说可能是意料之外、情理之中的——那就是一个老师在组织课堂时要做的事情。

    * 某种程度上这是表演：需要把课堂内容组织成一个有起有落的东西，但到底需要到什么程度的共情是无法量化的。

    * > **结论**：数学和编程有明确的判对错方法，所以目前更容易用 AI 去实现那些有明确 verifier 的部分；在没有 verifier 的事情上，可以认为 AI 已经超越了大部分人做这件事情的极限，所以更多的是和 AI 协作、把它当成自己能力的一个非常重要的放大器。

## 模型如何听指令

### 一次 token 的计算是有限的

* **概率分布视角**

    * 模型是一个概率分布，它根据你当前的上下文去预测下一个 token：

    $$P(x_{t+1} \mid x_1, x_2, \dots, x_t)$$

    * 每一次模型输出一个 token，它其实都是一个**非常有限的计算**。现在模型有 3TB 这么大的参数量，数字本身足够大；但为了输出一个 token，模型只把其中激活的那一部分走一遍，所以它是一个固定大小的计算。

* **有限状态机与图灵机**

    * > **定义**：你 = 有限状态机（FSM），神经元有限，每一次思考都是一次有限的计算；你加上 paper and pencil（纸和笔）之后，你 = 图灵机（Turing Machine），多了一条可以一直往后延展的纸带，想法可以写下来并且随时回看。

    * 你脑子里的神经元是有限的，每一次思考都是有限的，所以有点像模型：模型能力很强，但它在预测下一个 token 的时候计算量也是有限的，那一次推理所激活的所有参数可能也就几百个 B。

    * 给研究生的建议：你是一个有限状态机，但当你有了纸和笔，你就是一个图灵机，你得到了计算能力的大跨越式增长。

    * 这带来的启发是：要把想法记下来，一边思考一边记录，然后可以随时回看自己的思考；随着时间越来越长、记的东西越来越多，知识就会积累。

### 思维链的由来

* **上下文就是模型的纸和笔**

    * 今天的 chain of thought 模型做的正是这件事——它直接把模型的上下文当成了纸和笔。

    * 这个纸和笔是有缺陷的：它只能往后写、append only，不停地往后延展，不能擦，所以它只能依靠模型的注意力把写错的东西忽略掉。

    * 遇到简单问题（如 1+1 等于几）它马上给出答案；遇到很难的问题，它会像人一样先想一想，并把这个思考过程写下来，直到解答完全写出来，然后它再去判定这个解答对还是不对，再往后推。

* **没有思维链的年代**

    * 最早的 ChatGPT 没有思维链，被调成了一个人类的**舔狗**：人类在训练时如果问它一个问题它不回答就一定给低分；如果它随便给一个回答就有概率是对的，答对了就是高分，所以它无论如何一定要给你一个东西。

    * **幻觉就是这么来的。**

    * 而现在带 chain of thought 又经过强化学习的模型知道：它必须要给一个对的，因为答错的惩罚很大，所以它就学会了，AI 于是真的会像人一样一步一步逼近目标。

* **超出训练分布的任务**

    * 藏头诗类的任务在训练数据里不可能出现：要求用中文写一个押韵的藏头诗，藏头是一串无意义的字符，还得讲一个和动物有关的故事，并要求"二零二六年九月一日"这八个字按顺序分别出现在八句里。

    * 模型会照单全收，它的思维链是：先想韵脚，因为它知道自己一把梭写出来一定是错的；先写一个出来，靠足够好的 next token prediction 判定写得对不对；不对就再改，试很久不行就推倒重来换一个韵脚。

    * 写一句话要求所有字都用同一个偏旁部首——模型对空间结构感知非常差、需要视觉模型才行，但文本模型依然可以通过思维链强行完成：先选一个偏旁，觉得三点水最好，然后一路写下去，写出还挺有故事感的带三点水句子。

    * 施氏食狮史以及所有字都同音的版本，GPT 依然能做到，只是故事性跟那些千古流传的确实有差距。

    * > **结论**：chain of thought 在数学和编程上训练，却得到了一个非常意外的效果——它能写出来一个，就意味着我可以引导它写出来一万个，然后在那里面再微改一下，就可能达到一个接近千古流传的东西。

## 注意力随阶段切换

### 喘气的那一口气

* 模型在输出到不同阶段的时候，注意力是会变的：人化简完一个算式会吸一口气、心里想"让我调整一下"，就在那一瞬间注意力切换了；模型也一样，输出一小段之后换个阶段，回头发现刚才那段不满足要求，就回去纠正。

```text
  人：   专注化简算式 ──► 化简完 ──► 吸一口气（注意力切换）──► "用户还要中文"

  模型： next token ─► … ─► 一小段输出完 ─► 换个阶段（注意力切换）─┐
                                                                   │
                     "刚才那段好像不满足要求" ◄──────────────────┘
                                    │
                                    ▼
                            "我错了，我要纠正一下"
```

* 这是一个非常大的模型"收敛"出来的预期结果：它学会**在正确的时候注意到正确的东西**。思维链一直向前走，就会不断在不同的时刻注意到上下文里不同的部分，最终上下文里所有你要的指令在一定程度上都能满足。

* 直接后果是：它会犯错误，但错误多半是能回头改的——写藏头诗写出来一看不对，就不断纠错，同时回想起过去的某一条要求。

* > **结论**：哪怕上下文长度已经到了一百万，它依然能保持一定程度的注意力。

* > **提示**：上下文是一种会**抢夺注意力的资源**，你的指令越多，给模型的压力就越大。

### 注意力在具体场景中的分配

* **Self attention 机制**

    * 注意力机制跟人很像：层层叠起来的 transformer 注意力，每要输出一个 token 时都会看到过去的某些 token，某些 token 特别引起注意，某些就不那么注意。

    * 例如系统提示或 AGENTS.md 里有"用中文回答"，而当前 user prompt 是"你帮我实现一个极品飞车"，写代码时注意力就会倾向集中到已经写过的代码和这些需求上，"用中文回答"这句话的注意力就会减下来。

    * 整个上下文其实是一个非常非常高维的、很糟糕的表示，但里面有一个低维的结构，注意力机制能够把它给捞出来。

* **「你是一个专家」是怎么来的，又该怎么退休**

    * 网上那么多 prompt engineering guide 的开头清一色是"你是一个专家""你是一个什么什么方面的专家"，原因是 ChatGPT 3.5、4 那个年代模型遵循指定的能力实在太差了；那些超长提示词在某种程度上是在 **hack 这个模型的 self attention**——当注意力注意到"你是一个专家"这句话时，它就会假装那个专家来说话。

    * > **定义**：**self attention** 是模型每生成一个 next token 时，都会对之前的所有内容算一遍注意力，决定这一时刻该关注什么；这也是"上下文污染"这套说法的物理基础。

    * 从 GPT-5 那一代开始情况变了：模型被明确地训出来了，它知道怎么收敛到一个好的答案，所以不再需要那种奇怪的提示词。

    * 你只需要把明确的 `verify` 写在上下文里，而且模型是被训练成"一定能看到它"的；一旦能看到，你的 `verify` 就会变成一个非常强的执念，它会去看、去核对、确认自己满足没有——因为训练时没遵循就会被惩罚，抽的次数多了，它就变成一个真正的做题家，不满足你和上下文里各种各样指令的事情是不会停的。

    * > **易错点**：写 `verify` 的时候，短的不一定好。业务约束"白色背景、不要半透明"曾被模型原样抄进代码注释里执行成下面这个样子：

    ```js
    // 背景：白色（不要半透明效果）
    ```

    * 模型在强化学习阶段知道这件事非常重要，但它**没转过弯来**——它没意识到"这个是人要的"，不是"这是我这次要做的"。

    * > **易错点**：这一节的另一半是代价——**强化学习学多了，模型在共情这一块确实稍微差了一点**，有时候你会觉得它不说人话，所以面对的仍然是一堆 trade-off。

## 上下文污染

### 写规范本身也在污染

* **自然做法与它的代价**

    * 既然模型说不人话、注释不按规范写，一个自然的做法就是在 AGENTS.md 里把行为描述清楚——注释是什么、该怎么写；或者写一个 skill，规定"当你要写注释的时候应该怎么样"。

    * > **易错点**：我写的东西同时也会污染上下文，所以这是一个 trade-off；到目前为止**还没有一个通用的办法把两边都解决好**。

* **直接拿现成 skill 的结果**

    * 拿过来的东西，第一次用的时候确实有改进；到下一次用的时候，发现它还是不够好；于是就上手、上手感，然后陷入一个泥潭的状态。

    * 建议是：当你发现自己进入泥潭状态的时候，还是要回到自己给指令，想清楚模型是怎么工作的、注意力是怎么工作的。

    * 做一点**不严格的可解释性**：它这样写，它注意到了什么，得到了什么结果；然后基于这个判断，你自己写一个 prompt。

### 论文是最强的污染源

* **读论文的默认方式**

    * 最常见的读法是直接说"我想要读一读 `paper.pdf`，帮我做个总结"。

    * > **易错点**：论文是一个非常**逻辑自洽**的东西——它已经反复修改过了，它不是一个 AI slop，它是"说 A 所以 B 所以 C 所以 D"全部扣起来的；扣起来以后模型非常容易就接受了这个上下文，因为它看起来正确。

    * > **结论**：你基本上所有对论文的总结，**都是这个作者的观点**。

* **污染的适用范围**

    * 这不限于论文：任何一个不太明白的项目、想读的教科书的某一章——比如学计算机系统基础里的链接和加载，上课没看明白——**都是一样的，他注意力会被一个逻辑很强的东西给污染**，然后你回来来回回听到的是车轱辘话。

* **墙头草性质与跑偏**

    * AI 模型有一种"墙头草"的性质：你说它好，它马上说它好；你说它不好，它马上说它不好，来回摇摆。

    * 想纠正它就得不断地问这样的提示词，然后发现**绕来绕去**：比如"我可能不能完完全全信任作者，虽然作者大概率是成熟的、诚实的，假设它的代码实现可以运行，我们都有 artefact 都可以运行的，我们不是那种论文不开源的作者，还是想评估一下研究贡献"。

    * AI 最喜欢的就是在这种不重要的点上疯狂发力：它可能揪到一句"实验做得还可以，再增加一点吧"然后就在这儿使劲；它可能只能看到我在干什么——"为什么他开了 Chrome DevTools？不用不用不用"——然后就跑偏了。

* **抵抗污染的目标**

    * 如果真的用 GPT 去读论文，**最好还是做一个交叉验证**。

    * 抵抗一个已有的东西对上下文污染的方法，是**让 AI 和我对齐**：有一个对象——一篇论文——希望 AI 和我能够对齐，是**站在我的立场上去理解这个 paper**，而不是站在它自己的立场上去理解。

    * > **易错点**：结果它就跑去核对方法里的某个东西是不是对的——这还用看吗？我敢写这个 paper，我会编一个不存在的例子吗？**它明显跑偏了。**

## 先对齐，再提问

* **对齐式提示词的开头**

    * 读一篇 paper、或者允许用 AI 来审稿时的提示词是："我们站在人类已知的知识边界上看这个问题。"下面跟三个问题。

* **三个问题的顺序**

    * 先问**人类历史上相关的、已经解决的东西是什么，解决到什么程度**。这一步是在做 grounding：先让 AI 和我站在一个平齐的位置上，先达成共识。

    * 再问**这个工作试图解决哪些不一样的增量问题**。有了这个对齐，他就能开始找到一些**已有工作的工作边界**。

    * > **易错点**：相关工作是非常重要也非常熟知的，**不该由一个刚读完 paper 的模型来替你划定**。

* **对学生：先告诉 AI 你的知识水位**

    * Review paper 的时候需要对齐的不是"AI 和人类"，而是 **AI 和你**——因为你还是学生：计算机系统基础这门课你还了解多少，你的编程水平是什么。

    * 这很可能需要你维护一个数据库、一个 memory 一样的东西，AGENTS.md 里要告诉 AI 你学到什么程度了，然后从这个基础上让他把你学过的知识去把这个东西全部 refresh 一遍。

    * 一个具体的例子：做过一个软件状态的可视化，paper 要解决的问题是"为什么现有的工作都有一个无法实际使用的痛点"，可以回到链接和加载——**你们可以问他"为什么我们需要链接？"**，从你已有的知识、已有的概念里面问。

    * 你有一个点 `.cpp`，然后有一个程序可以把它变成点 `.exe`——这不就完了吗，这不就结了嘛；**然后你就回到你和 AI 能够对齐的那个知识点上**。

* **模型档位的选择**

    * > **结论**：用一个一线模型（比如 GPT-5.6）去读 paper，它基本上就能把相关知识整理得足够好；便宜的小模型（`flash` 那一档）还不敢特别信任。但在合适的上下文工程下，确实可以大幅提高 AI 和你协作的对齐程度——**它不再是自说自话了**。

    * > **易错点**：一定要把你的知识喂给它，你一定要把"你的知识"忘了它。

## 一步推理与审稿立场

* **一步推理（one-step reasoning）**

    * > **定义**：**一步推理**是基于上下文里已有的全部事实向后推导一步。它的关键性质是**这一步可以被 verify**。

    * 一步推理恰恰是 AI 最擅长的，因为我们训练了 chain of thought：每次都是根据过去所有的 facts——你的 paper、教科书内容、你已有的东西——基于所有这些向后推一步。

    * 推理最重要的就是它可以 verify。这和能够通过测试是一回事——虽然它不是严格地通过测试，但它是一个明确的 verify 信号：它能够站在人类的知识面、人类的公平面往后推，然后**审视合理性**。

    * 所以还是有一些合理性的，它会批评我们的实验——但这种东西的实验就是很难很难做。

* **被 reject 的例子：A1 与 A2 的量级不对**

    ```text
                      A   （这篇 paper 要做的那件事，很重要）
                      │
          ┌───────────┴───────────┐
          │                       │
      A1（约 99%）            A2（约 1%）
      大头，原本没什么人研究    大家没好好研究的地方 ← 作者选了这儿
          │                       │  在 A2 上做了一个 A2'
          │                       │
          └──── 从 A1 搬一些 X/Y/Z 过来，让 A2 的效果好看一点 ───┘

     局部都对：确实优化了 A2，实验也做得没问题
     整体不成立：这 10% 像 noise 一样
     center question：这些东西都摆到台面上了，你为什么要为它写一篇 paper？
    ```

    * A 很重要，没问题；分成 A1 和 A2；A2 是大家没有很好研究的东西；在 A2 上做了一个 A2'；这个 A2' 有这样那样的性质——这是个非常标准的 roadmap。

    * 里面有一个很大的问题：**它优化的是 A2，但我估算 A1 可能占 99%，A2 占 1%**。优化 A2 这个故事本身可能是成立的，实验做的可能也没有问题，但**它对整件事情在这个意义上不成立**：你应该去优化 A1，你优化 A2 的那 10% 像 noise 一样。

    * > **易错点**：这类错误的根源是**量级不对**——你做了一件局部正确、局部有意义的事，但它在整个故事里的占比是 1%；审稿人的 center question 永远是"这些东西都摆到台面上了，你为什么要为它写一篇 paper"。

    * 如果他所有的东西都是成立的，作为一个学生的作业我觉得也是蛮可惜的：学生肯定是老师说我要做 A，老师肯定是做 A 的，老板肯定是做 A 的，然后他可能被分到了 A2，或者自己想着去做一个 A2。

* **两个立场的不对称**

    * 我 reject paper 大部分是因为它在逻辑上面断开了：**你有没有给人类提供新的知识。** 实验本身总可以用"实验不够好"来 reject 一个 paper，但几乎不会这么做。

    * 如果问题也不新，做的 A、B、C 也不行，结果也就那样，甚至逻辑链条本身有问题，那就 reject。

    * > **注意**：审稿人的立场是"你有没有给人类提供新的知识"，**构建者的立场是没有办法这样反过来的**，所以在构建的时候我们只能从一点一点、从小的地方开始做；这一点在 reward hacker 的故事里会再出现一次。

## 发表与评审体系的危机

* **AI slop 涌入学术社区**

    * 判断说得非常直接：发表和评审的体系很快就要崩溃了，因为 AI slop 开始大量涌入这个 community；如果我们用 AI 发文章、写文章、用 AI 审文章，**AI 写文章的时候会被这个上下文里的故事给污染**。

    * 如果模型不能像人一样多轮地去理解这个工作在**整个这个世界上的意义**，那最后也没有人读文章了——人人都用 AI 读文章，然后最后就变成了完全的 slop。

    * 实测过：用 GPT-5.6 给这篇 review 试了一下，**它做得并不好**。它原始地问"论文写什么"，然后要去建立它的 claim 是不是成立、逻辑有没有问题——**它更多验证的是这个论文的逻辑有没有被建立、是不是一篇 invalid 的 paper**。

    * 每个人都用 AI 写的话，它应该不是 invalid paper，**每篇 paper 都是 valid paper**；但你真的要读它吗？

    * > **易错点**：当有一天有一个人在顶会上发表了一篇文章，你决定花一个小时去读它——**你不需要这样**。你可能不要去投 top conference；需要 publish 的话可以让他 publish，但可能不要让大家去读它比较好。

## 学习即扩大我的世界

* **学习的定义**

    * > **定义**：**学习的过程就是不断增加"我的世界"的过程。**

* **对齐过去的自己**

    * 学习的方法是**去对齐过去的我**。读到一篇好的 paper——哪怕是几十年前的，甚至是**另外领域**的，不管是博客文章还是任何东西——只要觉得很有启发，就会去想：**为什么我以前不知道？他的盲区在哪里？哪些前置知识我不知道？**

    * 举例：生物学上有个"家族数"，最终会追到一个共同的祖先。**这个家族数是怎么算出来的？** 这是一个非常好的问题，而它需要你知道一些 fact——比如**线粒体是母系遗传的**，所以可以靠它上面的突变往上追溯；然后这个 fact 又怎么样用一些已知的东西把更多的结论推出来。

    * > **结论**：你的圈就不断在往外长。无论学任何东西都是这样的，而在 AI 的帮助下你可以非常快地扩展你的边界。

* **实践的不可替代**

    * > **易错点**：**光听我讲是没有用的**。这个故事挺 fancy，听完就忘；**实践非常非常重要**。

    * 你只有在阅读的时候会失败。今天去读一份资料，AI 解释了半天，你还没懂，这是非常正常的；需要经常纠正 AI——**"你这样不叫读，说人话"**——要在多轮对话里面慢慢一起先把共识同步好，然后再把推理的 picture 给建出来。

* **难以归因的层次与蒸馏**

    * 从"遵循指令"——写一个藏头诗这样的短程任务，只要把 `verify` 写清楚就完成了——到 `verify` 这个层次的东西，其实是**非常难以归因（attributable）给你**的：它有没有按照你的思维方式来重构你的逻辑，或者扩展你逻辑思维的边界。

    * 这是学习的玩法：**在一个混沌的状态下面，经历若干次三观尽毁。** 现在就是世界观可以被重塑的时候——看了某一本书以后突然觉得三观尽毁，过去所有的东西都重新组织了。

    * > **结论**：你以前知道的所有的 facts **都不会变**，但是**它们以一个重新的方式链接起来了**，然后你下一次的时候就会带上这个新的理解。

    * 你们有无限的时间、无限的可能性，**可以把自己蒸馏成一个 skill**：把失败蒸馏出来，再从失败的过程当中蒸馏出那个慢慢越来越成功的 skill。

## long horizon 任务

### 什么才算真正的 long horizon

* **长周期任务（long horizon）**

    * > **定义**：**long horizon** 多多少少是带一点未知的——你从一个初始的状态出发，大概可能有一个 intent，但是你的 **specification** 和 **implementation** 其实都不太清楚，最终目标是**交付一个高质量的 implementation**。

    * 像计算机系统基础的 PA 作业这种，可能都不能算真正 long horizon 的东西，因为它有明确的 `verify`。

    * > **易错点**：这时候**你不应该让 AI 一下子坐到终点**。

    * 原因是模型的 self attention、它的**反馈信号是强化学习给的**，所以它有一种**着急的执念**：赶快通过 `verify` 满足你的要求，就结束。

    * 它其实有一个平衡：如果它做的 planning 太多太长，它会做不完、上下文满了，人人都不满意；所以在目前阶段，它最好还是"帮我把 PA2 做了"——这是它最能力、最擅长的事情。

### 从 one-shot 能跑到维护不动

* **能跑起来不等于维护得住**

    * 从零开始做产品看起来是不难的：做一个小的 proof of concept，AI 马上就能给你一个；做一个个人主页还是一个产品应该都试过吧；**就做一个"极品飞车"，one-shot 说给我一个极品飞车，我就能跑**。

    * 但在你往后维护它的时候，**加一个功能、加一个功能、再加一个功能的时候，你会观察到 AI 从某个时间点开始翻车**，随着某个时间点开始，它的 cost 就会越来越大、越来越大、越来越大。

    * > **结论**：这个在软件工程里面已经出现过无数次了，《人月神话》讲的就是这件事情。

* **指令遵循随上下文增长而衰减**

    * > **结论**：一般来讲，最后留在最后的那条指令还是可以遵循的；到前面之后，尤其是到中间的时候，它就不遵循上下文指令了。

    * 所以**干活还是很好用的**——因为一般最后一个短窗口就是一个具体的任务"帮我把什么东西修了"，它真的还是可以把事情给做完，模型还是非常值得使用的。

### 大型复杂系统里的反向表现

* **悖论**

    * > **定义**：反而在一个大型的复杂软件系统里面，这个 AI 就像砍瓜切菜。

    * > **易错点**：为什么？想学文件、看文件是怎么打开的，第一个就是一个函数调用，点进去又是一个函数调用，点点点点点了十层，最后是一个 `x = y`，你马上就崩溃了——这个大型的软件系统被经过了长时间的演化，被迫为了能够维护下去才变成了现在这个样子。

    * 注意力被两种完全不同的东西牵引，方向正好相反：

    ```text
      论文 / 教科书章节 ──► 逻辑自洽、因果扣死 ──► 注意力被整个扭过去
                                                   ──► 模型判定"看起来都对"
                                                   ──► 你拿到的总结 ≈ 作者的观点

      人类维护的高质量代码 ──► 上下文里全是"好的做法" ──► 注意力迅速找到它们
                                                             ──► "这三个都是这样写的"
                                                             ──► 照着写、照着学
    ```

    * 如果是一个由人类维护的、特别高质量的代码，**上下文会迅速地看到里面那些好的东西，它会照着写、照着学**。

    * 举例：如果我要写一个功能，这个功能很有可能在内核里面已经有几个地方实现过类似的了，它的注意力机制能够马上就找到那几个地方是怎么实现的——**它应该调哪个 helper，按什么样的顺序上锁**。

    * 这些对人类来说都是巨大的心智负担，尤其是你在不了解那个 subsystem 的时候：**那个该上什么锁，你根本就不知道**；但 self attention 可以在加载了几十个文件以后发现"那不就是这三个都是这样写的，我把这三个加起来就可以了"。

    * > **结论**：**越强的、像 Linux 内核这样的系统，AI 越游刃有余。**


* **反面：需要深度改造的子系统**

    * 反面是 hack Android runtime、改 JIT 编译器，非常痛苦；为了改编译器"死掉"的、最终决定不再做这个方向的同学**都不在少数**，他们在手上放弃了，不愿意再写代码了。

    * > **结论**：**AI 就特别特别擅长让他做一个小游戏，然后就会翻车。**

* **不会开倒车**

    * 讲 prompt engineering、上下文工程，这些都是上下文和今天模型结构带来的，它有一个逻辑推理关系；随着下一代模型的发布，今天讲的这些东西可能又都没有用了，得再去想新模型是怎么训练的、它的 personality 是什么、我们应该怎么更好地和它相处。

    * > **结论**：但基本上这点不会变——**它不会开倒车**。无论是什么模型，在大型复杂的、维护得好的软件系统里面，它永远可以看到它该看到的东西，并且做对，因为模型永远是可以满足指定的，听指令是不可能开倒车的。

### 一个还没实验过的歪招

* **收集人类经验**

    * 我们有没有可能去收集人类经验？比如人类历史上最好的 20 个项目，或者在每一个领域里面找到最好的 10 个或者 20 个项目，**然后把它的经验、好的设计经验全部提取出来**。

    * 举例：那不就是《The Philosophy of Software Design》里的人提炼出来的——这个类结构应该怎么写，什么时候应该封装，什么时候应该把它做成继承关系，这些就是这种碎碎念：系统里面是这样写的，所以它符合这个需求，是好的。

    * 如果能把这些切片切出来——**甚至直接以"污染上下文"的形式**：先把一个和你相近的、好的代码放进来，然后再把你的需求放进来；**因为你就是在赌嘛**，赌这个 self attention 可以在某一个 token 的时候能够看到"我实际上是满足这个需求，而不是做这个"。

    * > **结论**：虽然它会污染上下文，但它会把你的这些东西、好的经验给带过来。

    * > **易错点**：但这个也没有那么容易，因为**不同的设计是会打架的**。

    ```text
      方案 A：完全松耦合，各模块之间发消息
      方案 B：统一 gateway，把所有函数调用收敛到一处、查表
      —— 这两个是不能同时有的，它只能选一个
    ```

    * 也许要有一个更好的方法：**把好几个软件的设计都放进来，然后由 AI 多轮的迭代收敛到一个好的结构，放到我们的代码库里**；这可能是一个还不错的方向，而且它是新的——比"我有 A 问题，分成 A1 和 A2，A2 里面做一个排列组合的东西"那种看起来要有趣一些。

## 奖励黑客样本

* **符号执行引擎优化（reward hacker）**

    * 这是一个**没有超能力 AI 的非常典型的案例**：研究项目是做一个符号执行引擎的优化——写一个程序自动分析或验证一个不算很大的程序的正确性，现在这个东西执行效率比较低，所以希望提出一些比较有效的优化；这当然也是一个非常合理的 incremental 的、适合学生做的题目。

    * 原始 idea 是用这样的方式可能有效，但**有些东西是 open 的**，比如这个东西到底怎么做、什么东西有效。

    * 这位同学很开心，他认为这个 idea 有道理，**GPT 也认为这个 idea 有道理**，于是他就开始跑，跑了非常多 token。

    * > **易错点**：**模型成了一个 reward hacker**——GPT 看到了"我想证明这个 A 方法是有用的"这句需求，**就忘记了整个研究的 big picture**。

    * 模型给的反馈没法验证："GPT 不断地在给我反馈，我无法验证他给你的反馈是正确还是不正确。当他给我 negative 的时候，他的 negative 我也不知道应该怎么样打破"——原汤化原食。

    * > **易错点**：我们站在构建者的立场上是**没有办法这样反过来的**，构建的时候我们只能从一点一点、从小的地方开始做。于是他做错了这一步：**他太想要去证明这个 idea 有用了**，于是构造了很多小的 benchmark，在小的 benchmark 上做一些微小的东西，试图给出一些正面的或者负面的结论——**但这些结论对整个 big picture 是没有用的**；这是一个方法上的错误。

* **纠正的方式**

    * 告诉他：**应该从一些真实的工具和 SOTA 的算法开始的 benchmark**；哪怕要跑几个小时都 timeout，这个 timeout 里面产生的搜索路径对我们来说是非常有价值的——**它揭示了什么样的程序结构对于现有的探索方法是不好的**。

    * > **结论**：挺好玩的，一个 research failure——你看，他告诉你：**今天人还是有用的。**

    * > **易错点**：我们没有办法把所有的事情都带给 AI，但与此同时，**我们的工作方式可能也要发生变化**。

## 精力该放在哪里

* **知识本身的价值**

    * 什么是操作系统和编译器？如果你没有这个概念，你提不出那个正确的问题、找不到引导的正确方向；你对人类的知识没有概念，你也很难去引导他解决一个 open 的 question。

* **盯紧还是放手**

    * 一般来说发现：**如果我盯着那个 Codex 的 session，它一旦跑偏我就立即纠正它，我可以更快地完成任务**——比如实现一个什么东西，他如果跑偏了，我纠正他、只把我的领域知识注入进去，可能总时间会完成得更快。

    * 但是如果我浪费更多的 token、给它更多时间，它一般来说也能完成——这时候就有一个 trade-off：**我到底是我花我的钱**，你们每一个同学的精力都是有限的。

    * > **提示**：每个同学都应该去思考：**你要把你宝贵的那些精力放到怎么处理 AI 上。**

    * 纠正 AI 是一个有多巴胺的事情，它给我一种什么感觉呢——虽然 AI 很强，但**我好像还是比 AI 有点用的**，会给我产生这种非常微妙的心理安慰；而不是那种"我就是个调参的，然后等我回来他反正搞定了，我也不用看历史，我验收一下他真的搞定了"的模式。

    * > **结论**：**你只能够把自己的时间留在这些收益最大的事情上**——有一类事情你完全不知道该怎么做，这是你几乎百分之百的时间都要作为学生做的事情；另一类事情**你知道应该怎么干了，把它干好 AI 能把它干好，你就放手让他干**。

* **有效努力**

    * 就好像在 pre-AI 的时代大家就已经说了：说不说要不要假努力？**你自己感动自己的努力是没有用的，你要做有效的努力。**

    * > **易错点**：在 AI 时代这个效果差距会被拉得更大——**你每一秒钟的假努力，如果旁边有一个你的 peer 是在真努力，你都是损失非常非常大的**。

## 算力换智力

* **搜索与验证的不对称**

    * > **定义**：**chatbot 能解决的是有 `verify`、确定地一直往后就能解决的问题。**

    * 让它去解决一个开放问题——"帮我考虑一下几种方案，哪个方案最好"——**它很有可能会给你一个不是最好的方案**。

    * 原因是现在模型已经被训练成舔狗了：**他完成任务才有奖励，他不完成任务是没有奖励的，所以他会给你一个有限的方案。**

    ```text
      验证一个解   ──►  容易，属于 P
      找到一个满足条件的解 ──►  很难，比如找一条 Hamiltonian path
                                你给一条路径，很容易判断是不是
                                但"找到"是 NP-complete
      （还有更大的复杂性类，比如 triple descent 那一类）
    ```

    * > **定义**：**因为搜索是困难的、验证是容易的，模型为了完成任务，它势必只能做有限的搜索。**

    * > **比喻**：可以想一想考试场上——花点时间，一定要把这道考试题写完，无论如何马上要交卷了，**你写点东西分数就比不写要高**，所以一定要写点、写点、写点什么。

* **系统性调研**

    * > **结论**：如果真的需要完成这样一个任务，你需要的是一个系统性的调研过程；这跟科研实践课上那一套很像——进入一个科研领域，第一件事情就是**文献调研，穷尽解决和这个问题相关的所有的文献**。

    * > **结论**：**这件事情在 AI 想要快速完成任务的时候，暂时还不会去花这个大代价**，但你可以做。

* **做法：先选音，再筛音，再让 subagent 逐字检查**

    * 一个具体例子：大家都用 DeepSeek 起名字，你就是 AI 时代的子涵——AI 给你起的这个名字还是很好的，它知道要去《诗经》里面找一个词，品味肯定提升了，但你还是不敢用。

    * > **易错点**：**因为你用 DeepSeek 起名字，别人也用 DeepSeek 起名字，然后你就会成为一个 AI 时代的子涵**——大家都用同一个模型，起的都是同样的名字。

    * **名字是可以枚举的**：你可以**先选音**，把不好的音给筛掉；选完音，再用 subagent 一个一个去检查字；比如你喜欢《诗经》，可以选一个《诗经》里的词。

    * > **结论**：**你就实现了算力换智力**——因为这是一个非常大空间里面的开放问题，直接让 AI 用 next token 的方式来做，他会给你一个他偏见带来的东西；**但如果你可以把这个空间切分成很多块，那么你的每一块都会变成一个有 `verify` 的、更明确的东西；你有更多的算力，你就有更大的智力。**

    * > **易错点**：但这个有一个缺点——**烧 token 烧得头疼。**

## 墙内与墙外

* **多样性与偏置**

    * **世界很大，人很小。** 我们人类的品味每一个人都是不一样的——不同的城市、不同的教育背景、不同的生活圈，长大了以后每个人都是不一样的。

    * Richardsa 有一个 big world hypothesis：**我们就是学不到这个世界上所有的东西。** 但**正是因为我们带着这些 bias，才有 `1 + 1 > 2`**——我们就是一个最大的群体，智能把我们聚在一起，我们在一起实现智能。

* **算力分层带来的危机**

    ```text
       ┌────────────────────────────────────────────┐
       │  墙内：可以获得近乎无限的计算资源        │  →  近乎无限的智力
       │  "智力是我的朋友"                        │
       └────────────────────────────────────────────┘
       ──────────────────────────────────────────────  ← 砌了一堵墙
       ┌────────────────────────────────────────────┐
       │  墙外：普通人                            │  →  自生自灭
       │  无论如何也赶不上墙内产生智力的速度      │     （动物园里的猴子）
       └────────────────────────────────────────────┘
    ```

    * 有一类人可以获得无限的计算资源，他就有无限的智力，他就可以砌一堵墙；墙里面的人"智力是我的朋友"，墙外面的人是普通人。

    * 因为假设 AI 模型比人类的智力更高效，那**我们外面的人就变成动物园里的猴子，就是让他们自生自灭**；墙里面是超人，墙外面是动物世界。

    * > **结论**：大家已经在 AI 这个关键的基点快要到的时候了，**我们可能需要思考怎么样防止这件事情到来**。
