# 软件仓库管理与版本控制体系

## 项目、软件与版本控制

### 项目从目录到交付

   * **软件项目（software project）**

       * > **定义**：人类需求在信息世界中的一个投影，初始形态是包含代码、文档、意图、规格、测试和构建材料的目录。

       * 目录中的代码、文档、构建结果和说明共同表达需求、实现与交付，生成一个文件并不等于交付一个软件。

       * 本机能够运行只证明开发服务器或程序在当前机器可用；若意图明确要求面向外部用户交付，还必须考虑远端部署与他人访问。

   * **软件工程中的项目维护**

       * 真实项目不是一次性生成物，而是需要持续构建、验证、交付和修改的工程对象。

       * 版本管理要同时保存可靠副本、比较变化和恢复历史；“只保留当前一份”无法应对介质损坏、误操作和错误实现。

   * **从成熟项目学习工程惯例**

       * 成熟仓库中的目录有无、文档写法、配置方式和入口组织都是项目设计信号，不能只执行眼前命令而忽略差异。

       * 好的标识与文档会在使用者产生不确定性的地方提供最少但足够的信息；堆叠目录树、字符画和装饰不等于文档更好。

       * 可先对同一问题独立设计，再与作者方案比较：作者更优时追问其原因，自己的方案更优时检查是否遗漏约束。

       * Git 概念用于验收 AI 的操作，命令细节可以委托；模型可以模拟结构，真实仓库才用于验证对象、引用和合并行为。

### 意图、规格与实现

   * **产品意图（intent）**

       * > **定义**：产品最初想解决的问题、希望达到的效果以及真正面向的用户价值。

       * 简明说明可以只写初衷、目标效果、少量截图和最重要设计，不必让说明文档替代后续工程规格。

       * 开放式意图容易产生漂移；若只说“做国民级应用”，执行者无法从字面推断数据库、用户规模、功能边界和验收标准。

   * **规格（specification，spec）**

       * > **定义**：把产品意图具体化为可实现、可验证约束的工程描述。

       * 规格可以包含编程语言、数据库、项目结构、模块接口、输入输出、测试要求和不可违反的约束。

       * 产品构思者不必预先掌握全部底层设计，但意图、规格与实现都应成为项目中可持续维护的内容。

   * **意图一致性**

       * > **易错点**：把规格陈述、意图描述和真正目标混在一起，会得到逐条满足字面要求、整体却偏离用户价值的系统。

       * 功能完整、分层漂亮和运行成功都不能证明意图对齐；应先明确最重要的痛点，再围绕它约束最小版本。

## Git 的快照模型

### Git 出现的原因

   * **恢复旧版本与同步协作**

       * 新手最直接的需求是找回误改前的项目；进一步需要列出历史版本，并在多人同时修改同一文件时合并两条发展路线。

       * 只有版本列表、快照切换、分支、合并和冲突处理，尚不需要其他复杂能力时，就已经得到一个简化版 Git。

   * **变化存储与快照存储**

       * SVN 式模型保存一次次修改形成的补丁，回到早期版本需要沿变化链逐步回退，项目越大，变化链越长。

       * Git 直接保存项目在某个时刻的快照，目标历史版本本身即可定位，不必临时重放此前全部变化。

       * 两者的关键差别不在工具名，而在数据模型是否直接服务于“找回版本”和“共同修改”的原始需求。

   * **基本仓库流程**

       * 空目录执行 `git init` 后成为本地仓库，默认隐藏的 `.git` 保存仓库元数据，与项目工作文件不是同一类内容。

       * `git clone` 从远端取得项目，`git pull` 获取更新，`git add` 暂存改动，`git status` 检查工作区，`git commit` 保存快照，`git push` 发布本地历史。

       * > **易错点**：初始化后看不到目录内容变化，可能只是 `.git` 默认不可见；不能据此判断初始化失败。

### 快照的增量存储

   * **提交快照（commit）**

       * > **定义**：一次提交保存项目在某一时刻的完整状态，而不是覆盖上一版本或只保存一个作业文件。

       * 新快照可以复用未变化文件，只为变化路径创建新对象；保留历史不等于复制每个版本的全部字节。

       * 删除文件也不是额外记录一个“删除动作”，而是产生一个不再引用旧路径的新快照。

   * **Git 三类核心对象**

       * > **定义**：Git 以内容哈希为索引，把文件内容、目录结构和版本演进分别表示为 `blob`、`tree` 和 `commit`。

       * `blob` 保存文件内容的字节序列，不关心文件位于哪个目录，也不保存最终看到的文件名。

       * `tree` 保存目录项、文件权限和子对象引用，负责文件名、路径关系以及可执行权限。

       * `commit` 指向一次快照对应的树，并记录父提交关系，从对象图中保留版本从哪里演进而来。

       * 内容不变的对象可以被多个快照复用；对象内容不变，其标识也不变，因此仓库能够持续向前增长而不重复保存全部数据。

       * > **易错点**：`blob` 不等于完整文件条目。同一内容可由不同路径引用，权限差异也由 `tree` 表达；对象压缩后体积不小于原文不能证明 Git 失效。

   * **引用与分支**

       * 分支不是复制项目，而是 `refs` 下指向某个提交的引用；`HEAD` 是指向当前引用的指针。

       * 典型关系是 `HEAD → refs/heads/main → commit → tree → blob`；创建功能分支只需增加一个引用，切换分支本质是移动 `HEAD` 的指向。

       * 提交对象可沿父关系访问更早版本，因此分支共享已有历史，而不是从零复制对象。

### 合并产生的提交图

   * **合并提交（merge commit）**

       * 把两条发展路线合合时，Git 可以创建一个具有两个 parent 的新提交：一侧保留当前分支历史，另一侧保留被合入分支历史。

       * 两边共同祖先及各自后续提交都被保留，合并结果再由新提交的树指向。

       * 这种结构准确表达“结果同时继承了哪两条历史”，但日常拓扑会出现分叉与汇合。

   * **冲突的三方材料**

       * 两侧对同一文件作出不兼容修改时，Git 在索引中保留 `base`、`ours` 和 `theirs` 三个版本。

       * 工作区用冲突标记并排呈现两边内容；解决后，临时冲突状态消失，合并提交指向开发者选择或重新整理的结果。

       * 工具可以缩小冲突范围、整理候选方案和运行验证，但不能从标记本身得知哪一边符合真实需求。

## 提交协议

### 原子提交

   * **完整、自洽的快照**

       * > **定义**：合格提交应能独立构建、通过测试并说明一个明确目的，而不是临时保存仓库的半成品状态。

       * 顺手产生不能编译的改动时，应先修复并验证，再形成提交；仅修改一行不代表整体仓库仍然可用。

       * 尺寸不能代替目的：几百行且只完成一个目的的提交未必差，几十行却混合多个目的的提交仍然难以审计。

   * **原子变更（atomic change）**

       * > **定义**：一个只承担单一目的，能够独立构建、测试、理解和回退的提交单位。

       * 新接口、旧逻辑修改和文档更新若属于同一个目的，可以放在同一提交；互不相关的目的不应挤进一个大提交。

       * 提交前要确认改动是否都属于同一件事，以及快照是否处于可构建、可运行状态。

   * **及时提交与及时推送**

       * 有意义的 bug 修复、功能、脚本调整或文档修改应尽快形成可解释的快照，使引入问题与修复问题都有明确对应。

       * 大提交同时破坏多个位置后，后续多个修复很难判断问题来源，也难以确认修复后的整体状态是否正确。

       * 小提交后及时推送可获得远端备份，避免电脑物理损坏或未及时同步造成工作丢失；远端历史还能支持评审、回退、二分和追溯。

   * **提交消息（commit message）**

       * 消息应说明改了什么，最好同时解释为什么改，使连续历史呈现需求、缺陷和重构的演化过程。

       * 可用祈使句和现在时描述变更，例如明确说明修复了边界差一错误；“添加了一些内容”语法合法，却没有审计价值。

       * 成熟项目可能采用 `Conventional Commits`：第一行使用 `type: summary`，冒号后留空格，正文再解释原因、实现要点和用户可观察行为。

       * `feature` 用于新增能力，`fix` 用于修复缺陷；前缀规范的作用是让标题列表可读，并统一提交命名方式。

### 空提交与历史改写

   * **空提交（empty commit）**

       * 普通情况下没有文件变化时不应提交；只有流程事件本身需要留下可见记录时，空提交才有意义。

       * 合理场景包括在没有代码变化时触发一次 CI、在发布时留下 finalize 事件，或把修复 Bug 与冻结版本拆成两个节点。

       * 发布版本也可以使用标签标记；不能仅为了显得持续工作而大量制造空节点。

   * **改写历史**

       * AI 可能通过整理、压缩或删除旧提交来制造“更整洁”的历史，但工具测试通过不能证明改写合理。

       * 接受改写前必须检查哪些提交被丢弃、哪些文件离开历史、哪些分支被创建或改写，以及仓库是否存在远端和他人副本。

       * 没有远端和共同开发者时，本地整理与已经共享后的历史破坏不是同一风险等级；已有副本时不能把改写当成普通清理。

### 提交前检查

   * **仓库卫生（repository hygiene）**

       * 编译产物、个人编辑器配置、绝对路径、日志、缓存和本机状态通常不应进入可共享仓库。

       * 构建产物可能包含日期、哈希或机器指纹；相同源代码在不同环境生成的二进制或图片仍可能不同，提交后容易产生无意义冲突并使仓库臃肿。

       * 忽略规则应针对个人环境与可重建产物，而不是按“点开头”或“生成文件”粗暴归类。

   * **点文件与生成内容**

       * 隐藏文件可以具有跨机器复现价值，自动化工作流配置就应纳入版本控制；是否追踪取决于构建必要性、复现价值和环境状态。

       * 操作系统文件管理器产生的目录展开状态属于个人环境，应由忽略规则排除，即使普通目录列表默认不显示它。

       * 工具生成的锁文件不能一概排除；若纳入它能避免重新下载大量依赖并支持可复现构建，就应提交。

       * > **提示**：提交前对每个出现在状态中的文件解释“为什么应该在这里”，比维护一张僵硬的忽略名单更可靠。

   * **凭据与个人环境**

       * API key 等个人凭据一旦进入版本历史，只删除工作区文件不够；密钥和个人环境不能进入可共享仓库。

       * 写死本机路径的配置会破坏跨机器复现，日志和缓存会持续制造噪声，个人配置不应随源码传播。

   * **提交前四项核对**

       * 当前改动是否都属于同一件事。

       * 是否混入不能构建或不能运行的状态。

       * 是否包含个人配置、绝对路径、日志、缓存或密钥。

       * 状态中出现的每个文件是否都能解释其存在理由。

       * > **易错点**：最佳实践应在提交前拦住坏状态，而不是给坏状态换名、隐藏起来或等待以后清理。

## 冲突、分支与历史形态

### 合并冲突的判断责任

   * **冲突现场（merge conflict）**

       * Git 会把冲突双方、共同基线和分隔标记集中放在现场，IDE 还可能提供接受任一侧等操作入口。

       * 冲突说明同一位置存在不兼容修改，不说明哪一侧在业务上正确；工具能够组织信息，不能替代语义判断。

   * **开发者与 agent 的责任边界**

       * agent 可以解释两侧变化、提出合并方案并运行测试，但“测试通过”只证明候选结果满足测试，不证明它符合隐藏需求。

       * 遇到冲突时应先查看双方分别改了什么，再决定保留、组合或重写；解决后创建提交，把这次判断记录进历史。

       * > **易错点**：不要仅凭 agent 宣布“冲突已解决、测试已通过”就接受结果；未观察冲突现场会丢失版本控制刻意暴露的判断责任。

   * **不可兼容性判定**

       * 同一文件的文本不同不一定产生冲突；只有两侧修改无法自动组合时才需要人工判断。

       * 大规模重构、无关文件拼接和混合目的提交会增加冲突范围；按单一目的形成小快照可以让不冲突部分更容易合并。

### 功能分支与线性历史

   * **分支（branch）**

       * 分支让开发者从某个已有快照继续实验；尝试失败时可以丢弃该路线，成功后再把结果合回主线。

       * 多条主线可以同时推进而不持续干扰彼此，最终通过合并形成统一历史。

       * 功能分支的价值不是复制目录，而是隔离尝试、保留共同祖先并提供可审计的汇合点。

   * **线性历史（linear history）**

       * 线性历史要求日常提交拓扑看起来像一条线，避免频繁保留分叉再合并的形状。

       * 线性提交仍然保留 parent 关系；可以先把当前分支修改合入，再让后续提交接在它之后。

       * AI 擅长解决冲突和执行变基，线性拓扑也更利于追溯、挑选提交和定位修改来源，并能减少 AI 维护历史时的 token 消耗。

       * > **注意**：线性历史不是所有场景都只有好处。目标是让每次改变可解释、可追溯、可审计，不能为了视觉上像一条线而丢掉真实历史信息。

   * **项目贡献规范**

       * 成熟项目的贡献者指南会说明总体结构、分支与提交要求、合并请求流程以及是否要求在个人分支上变基。

       * 看到“禁止分叉合并”或“必须变基”时，背后是在要求保持现行线性历史；命令应服从项目既有规范，而不是套用个人习惯。

       * 团队已经形成的规则应直接执行；只有尚未形成标准的细节，才需要进一步讨论并形成规范。

### 变基与修改对象

   * **变基（rebase）**

       * > **定义**：把一条历史中的修改重新放到另一个新基线上，并因基线和提交身份变化而重写相关提交。

       * 变基逐个重放 feature 和 test；某一修改与新基线不兼容时会进入冲突解决，成功后可继续形成线性历史。

       * 每次重放都会创建新的提交标识，原历史标识不再保持不变；多个修改可能分别冲突并需要多次解决。

       * 变基在共享历史上有风险，因为改写会改变其他协作者已经依赖的提交关系，不能把它当普通保存动作。

   * **修改不等于提交**

       * Git 没有独立的 `change` 对象，工程师关心的修改由“一个提交相对其 parent 的差异”承担。

       * 变基实际搬运的是提交表达出来的修改；因为每次移动都会获得新基线，提交标识随之改变，这使“修改本身”与“承载修改的提交身份”纠缠在一起。

   * **修改作为一等公民（first-class citizen）**

       * 下一代模型可以把 `change` 提升为独立对象，底层仍兼容 Git 的对象与冲突机制，但上层可以签名、组合和直接搬运修改。

       * 这种模型在变基时不必把每个提交整体伪装成新提交，修改冲突也能被单独记录和反复解决。

       * > **定义**：一等公民表示某类概念拥有独立身份、状态和操作，而不是只能依附其他对象间接表示。

       * 该路线还移除了暂存区的必要性：工作区每产生一个修改，就立即形成当前修改状态；后续修改替换尚未封存的当前状态，而不是堆积多层暂存。

       * 对已经形成 Git 肌肉记忆的人，重新训练成本可能抵消设计改进；对尚未形成固定习惯的使用者，先理解更自然的模型可能更容易形成正确直觉。

## 审计与团队协作

### 二分与逐行追溯

   * **二分查找（bisect）**

       * > **定义**：在“较早提交通过、较晚提交失败”的有序历史上，通过测试中点不断缩小范围，定位第一个坏提交。

       * 前提是存在能够稳定暴露缺陷的测试或检查，并且“从此开始失败”的假设成立。

       * 测试不稳定时得到的是某次碰巧改变现象的提交，不能据此建立可靠边界。

       * `git bisect` 引导开发者把候选提交标为 `good` 或 `bad`，并根据结果继续选择历史区间。

   * **逐行归因（blame）**

       * `git blame` 把每一行关联到引入该行的具体提交，为“哪一行由谁修改、何时修改”提供可核查入口。

       * 二分负责找到好坏的边界，追溯负责定位改动，提交内容和消息负责解释原因；三者组合才形成完整审计链。

   * **可审计快照**

       * 每个快照都可构建、测试、评审、回退，二分和追溯才有稳定依据。

       * 如果提交长期混合多个目的，测试失败后即使能定位提交，也难以独立理解和验证其中的具体变化。

### Issue、任务与代码评审

   * **问题跟踪（Issue）**

       * > **定义**：Git 外部的协作空间，用于保存任务文本、评论、分派、讨论和解决状态。

       * 版本控制保存代码快照和演进关系，但不能从 commit 推断谁拥有任务、讨论为何作出某个决定。

       * Issue 支持任务与讨论，版本控制支持分叉、合并和溯源，两者不能互相替代。

   * **命令行协作工具**

       * GitHub 命令行工具可完成登录、获取 Issue、查找分配给自己的任务，并在问题解决后关闭 Issue。

       * 长时间交给 agent 的任务可以在说明中写明小步提交、可审计和既定分支规则，但工具应配合项目已有规范，不能替代规范本身。

   * **评审前条件**

       * 评审不是提交后或 agent 宣布完成后才开始；提交前应逐项检查文件、执行构建和测试。

       * 交给评审的对象应是可构建、可测试、主题单一且可独立理解的快照，而不是“只改一个字所以风险很低”的侥幸判断。

       * 大型或混合目的提交会拖慢审查、定位和修复，即使其当前测试通过也不能弥补审计困难。

### Hook 与持续集成

   * **钩子（Hook）**

       * > **定义**：在函数调用结束、某件事发生或 agent 等待输入等时机自动执行动作的机制。

       * `pre-commit` 可在每次提交前触发本地检查，使格式、规则或项目约束成为必经步骤，而不是依赖记忆。

       * 统一检查可以给出一条清楚的阻止原因，也可把规则交给 AI 按现有项目规范执行，减少人工评审时的关系压力。

   * **持续集成（Continuous Integration，CI）**

       * CI 在提交进入协作流程后，依据项目统一环境运行完整验证，使不同提交接受一致规则检查。

       * Hook 适合在本地提交前拦截错误，CI 适合在共同环境中执行更完整的验证，两者不是替代关系。

       * 自动化工作流配置本身需要版本控制，因为它表达项目协作规则，不是个人环境噪声。

   * **规则优先级**

       * > **提示**：先询问项目已经形成的规范，再判断某个细节是否值得建立新规范；已有约定用于执行，未有约定的细节才进入设计讨论。

## 可追踪性与仓库模型重设计

### 文件系统丢失的关联

   * **技术债（technical debt）**

       * 文档先于实现写下“项目使用链表”，后来代码改成树形结构时，文件系统不会强制文档、代码和测试建立关联。

       * 文档与代码继续演化而不一致，最终无法判断哪一方权威；聊天历史消失、换机器或只剩部分变更日志后，原始判断更难恢复。

   * **可追踪性（traceability）**

       * > **定义**：在系统演化过程中持续维持需求、文档、测试、代码及其他工程实体之间关系的能力。

       * 文件系统擅长表达目录中的文件，却不能自然表达“代码实现文档”“测试覆盖实现”“文档关联需求”等关系及其同步约束。

       * 项目难维护不只是版本控制工具数量不足，而是普通文件管理只记录“碰巧同处一个目录”，没有记录“实体之间应当保持什么关系”。

   * **关联图（traceability graph）**

       * 需求、文档、测试和实现可以成为实体节点，以实现、覆盖、记录要求和需求关联等边连接。

       * 这类关系可能形成环，无法用单一父子树完整表达，因此需要图结构而不是继续把所有关系塞进目录层级。

       * 图模型要求相关实体在演化中保持同步：文档声明的数据结构、行为或测试范围必须在实现和测试中找到一致对应。

   * **仓库数据库（repository database）**

       * > **定义**：把工程实体及其关系显式存入数据库，而不是只把项目当作一组文件路径的设想。

       * 大型复杂项目可能不再适合仅靠传统目录工具维护，AI 可通过反馈信号学习理解仓库结构和关系。

       * 核心职责不是单纯保存文件，而是自动维护 artifacts 之间的一致性，让代码、文档和测试同步演化。

### 面向单次修改的仓库视图

   * **小步修改（V0 到 V1）**

       * 开发者修复一个缺陷或调整一个局部样式时，明确知道本次修改目的；大型仓库中绝大多数内容与这一步无关。

       * AI 可以根据当前意图，从仓库中筛出相关文件、测试、文档和实体关系，为本次任务生成一个局部视图。

       * 视图只改变观察与组织方式，不改变底层实体必须一致的要求；修改完成后，本次涉及的全部关联位置应共同更新到下一状态。

   * **内容即代码（content as code）**

       * > **定义**：工程意图、规格、关系、测试和实现都可以被表示为 AI 可读取、生成与维护的代码化内容。

       * 数据库中的 view 提供了“底层数据不变、查询与展示形式可变”的思想；仓库视图也可把复杂底层关系投影成与当前任务直接相关的看板。

       * AI 先看到与当前小步有关的切片，再在其上修改，可以减少无关上下文，但不能借视图隐藏受影响的其他关系。

   * **小步一致性**

       * 增加一种测试类型，可能同时要求修改测试定义、相关接口、实现和文档；一致性检查应覆盖整个影响集合。

       * 未来编程对象可能从直接编辑代码转向维护实体、关系和视图，但这不意味着经典系统思想失效；数据库视图、实体关系和小步演进仍可复用。

## 多 Agent 并行与并发控制

### 面向人的假设

   * **单线程使用者假设**

       * 传统版本控制隐含使用者是单线程的人：一个人观察共享状态后作出修改，期间其他人的变化会使先前读到的值过期。

       * 人类开发速度较慢，小团队约以十分钟产生一次提交；沟通和任务分配成本高，团队通常先协调范围，再让成员分别推进。

       * 人员增加会迅速增加协作关系密度，产出不一定按人数线性增长；一百人团队达到十人团队两三倍效率已经可能很可观。

   * **提交节奏的真实目的**

       * 小提交便于回退、二分、追溯和重新尝试，但“改一行就提交”不是机械规则。

       * 提交大小应与一个可解释、可回退的阶段匹配，提交数量本身不是质量指标。

   * **Agent 改变速度尺度**

       * agent 在上下文热时可能几十秒完成修改，主流快速模型有时几秒即可交付，变化速度远高于以分钟乃至十分钟为单位的人类协作。

       * 当 agent 速度提高数十倍、数百倍乃至设想中的约一千倍时，原本依靠低冲突和人工协调成立的版本控制假设需要重新评估。

       * 大型项目中的测试流水线可能需要运行数分钟，从而降低提交速度，但不会消除 agent 明显快于人的事实。

### 工作树隔离

   * **工作树（worktree）**

       * > **定义**：从同一 Git 仓库创建的独立工作目录，各目录拥有隔离的工作文件，同时共享同一份历史和对象数据。

       * 主仓库的 `.git` 保存全部历史；每个工作树中的 `.git` 指向这份共同历史，而不是复制一套对象库。

       * 各工作树都有 `HEAD`、`index` 和锁等局部状态，因此一个工作树中的文件修改不会直接覆盖另一个工作树的文件。

       * 一个工作树提交后，其他工作树能够看到新 commit；这提供了“隔离编辑、共享历史”的并行结构。

   * **Agent 与工作树的一一对应**

       * 可把每个 agent 视为独立开发者，为其配置独立机器、容器、远程仓库或工作树，通过会话接收任务。

       * 不同隔离目录可以先各自提交，再从远端拉取、合并或变基；冲突时重新解决，必要时向协调者报告。

       * 主 agent 可以观察多个执行单元的状态、总结输出并注入新任务，但协调本身不能替代目录隔离和历史合并。

   * **共享仓库目录的局限**

       * 多个 agent 如果直接在同一工作目录工作，会相互看到并覆盖未提交文件；工作树解决的是文件隔离，不自动解决语义冲突。

       * Git 已有的工作树机制可以先充当并行协作方案，但它仍是当前设计下的 workaround，不等于高速 agent swarm 的最终仓库模型。

### 乐观与悲观并发控制

   * **乐观并发控制（optimistic concurrency control）**

       * > **定义**：先假设并行工作不会冲突，让各方独立读取、计算和修改，等到执行汇合或合并时再检查冲突。

       * 数据库中的并发事务可能先各自读取，再依据时间或业务计算写回；发生循环依赖时可能回滚，Git 的独立分支推进也采用类似思路。

       * 乐观不代表保证无冲突，只代表先让独立工作前进；低并发的人类协作中，这一假设通常成立。

   * **悲观并发控制（pessimistic concurrency control）**

       * > **定义**：访问可能冲突的资源前先取得锁，建立确定的先后顺序，释放后其他任务才能继续。

       * 高速 agent 团队可能频繁修改相同测试、配置或接口，若仍先写后冲突，维护成本会随并行度上升。

       * 主 agent 可以先规划任务，再锁定明确 `scope`，例如“测试 A、配置 B”；执行者修改、提交并释放后，等待者才能取得同一资源。

   * **互斥与并行并存**

       * 悲观锁不要求整个项目串行；互不依赖的范围仍可并行，只有共享资源必须互斥。

       * 锁粒度必须清楚：全系统一把大锁会损失并行度，文件级、快照级、工作树级或仓库级形式要服从实际资源边界。

       * > **易错点**：多 agent 并行不等于让所有 agent 无条件同时写；应并行的部分并行，应互斥的部分互斥。

   * **调度层的前置责任**

       * 锁机制生效前，调度层必须知道哪些任务访问相同资源、哪些任务彼此独立。

       * 速度改变后要重新划分快照、锁和合并的职责，而不是机械沿用面向低速单线程使用者的规则。

       * > **注意**：重新设计不等于抛弃快照，也不等于彻底删除合并和变基；工作树与本地协作仍有价值。

## Agent 时代的工程组织

### 先架构后并行

   * **多 Agent 前置设计**

       * 小步提交不是把一个大任务切成大量碎命令；前提是组件可组合，接口、共享状态和协作范围已经清楚。

       * 架构阶段适合先与单线程、能力较强的模型多轮讨论；设计失稳后，后续并行只会放大返工。

   * **可组合边界**

       * 核心接口尽量使用纯函数，程序可视为标准推导图，组件按该图组合。

       * 会在更大范围互相影响的状态集中到一个小而清晰的全局位置，其余组件作为可独立组合的黑盒。

       * 让生成代理只依据接口工作，可以守住组件边界，减少其在全部实现之间来回猜测和消耗上下文。

   * **协作规则显式化**

       * 架构确定后，再让多个 agent 在明确接口、状态和规则下分别工作。

       * 昂贵检查不必让每个 agent 重复执行；可以把结果放到可实时观察的外部界面，由人直接判断并反馈。

       * 组件互知所有实现细节会破坏局部工作边界，即使程序逻辑不逐行管理，结构仍必须清楚。

### Agent 版“早上会议”

   * **任务分解与组合**

       * 大任务应先拆成边界明确的子任务，再交给不同执行者推进，最后重新组合并验证整体仍是完整产品。

       * 真正困难的是设计协作结构和判断组件边界，不只是让更多执行单元同时运行。

       * 人越多、agent 越多，关系越稠密；不能把规模化简单理解成无条件增加并发数量。

   * **主 Agent 的职责**

       * 主 agent 负责理解整体目标、拆分任务、确定可并行范围和需要加锁的共享范围。

       * 还要决定提交时机、合并时机、变基适用场景，以及历史保留到何处才能支持回退而不重新引入无意义的责任叙事。

       * 主 agent 可以协调多个会话、读取状态、汇总结果并注入后续指令，但最终组合仍要接受整体功能验证。

   * **管理能力仍不可省略**

       * 更强、更快或更小的模型不会自动等同于高质量团队管理；当前系统仍不能只凭一句产品描述直接生成完整高质量产品。

       * 稀缺能力是理解目标、构造协作结构和把局部结果重新组合成一致系统，而不只是生成局部代码。

### 项目早期与生成式 slop

   * **早期单 Agent 优先**

       * > **易错点**：项目早期直接让多个 agent 并行，会把尚未收敛的意图和架构迅速放大成相互冲突的产物。

       * 早期更有效的做法是选一个真正用得上的强 agent，多轮对话并把问题想清楚，再决定是否扩大并行团队。

   * **先收敛意图**

       * 开放需求会诱导模型遵循每条显式指令，先构造接口、表格和目录，却忽略隐藏在字面要求后的核心目标。

       * 若真正目标是学习助手，浏览器操作、外部信息收集、综合总结和进度感知都应围绕学习与复习效率这一痛点组织。

       * 从零构建的最大风险之一不是代码无法运行，而是功能完整的系统根本没人需要；继续堆功能无法修复方向错误。

   * **最小验证产品（minimum viable product，MVP）**

       * > **定义**：围绕不可省略的核心需求构造的最小验证版本，用于确认产品方向而不是证明完整架构都成立。

       * MVP 强迫团队回答哪些需求真正不可省；只围绕最重要的价值构造第一版，可以推迟尚无必要的数据库和重组件。

       * 当文件系统中的组织方式变得难以维护时，再从真实数据提炼数据库模型，迁移是需求演进的一部分。

   * **生成式 slop**

       * > **定义**：代码可以运行、结构看似规范、功能也丰富，但整体没有解决真实用户问题的生成式项目。

       * 判断标准不是代码量、页面数量或失败测试数量，而是实现意图是否对齐；项目越完整，方向错误时的误导性越强。

       * 面对 slop，应停止继续堆叠功能，重新写清意图并把需求收敛到最小验证版本。

### 为变化保留架构余地

   * **好架构的判定**

       * > **定义**：需求变化时，能够以较小代价调整系统的架构，而不是在当前功能最全时预置所有未来组件。

       * 初期看似规范的系统可能遵守大量最佳实践，却无法承受尚未出现的协作方式、数据组织或服务变化。

       * 需要追问未来哪些部分可能根本改变、哪些部分应保持不变，架构才能抵抗需求根本变化。

   * **文件系统与数据库**

       * 产品早期可以用文件系统或目录结构承载真实需求，先探索文件组织、提交消息和交接规则。

       * 需求变化时，目录调整通常能直接看见并移动；过早引入不熟悉的数据库模式会额外承担 schema 和数据迁移成本。

       * 当结构收敛、性能成为真实瓶颈时，再迁移到数据库；先验证需求、后优化承载方式。

       * > **注意**：文件系统与数据库不存在绝对优劣；判断依据是需求变化时的迁移成本，而不是组件看起来是否高级。

## 版本控制作为产品能力

### Git 进入学习产品

   * **自动提交产品行为**

       * 教学产品可以记录学生每次编辑、运行、切换以及助教在某个提交上的操作，Git 能直接承载这种结构化历史。

       * 每次关键编辑或运行自动产生提交后，产品能够定位问题发生在哪个状态，不必只保留最终页面。

       * 这比单纯在页面上增加接口更有价值，因为产品需要的是可追溯的操作与修改过程。

   * **助教分支**

       * 助教介入时不应覆盖学生主线，而应在当前提交上创建分支，保存点评、生成代码和修改过程。

       * 助教完成后再通过合并回到主线，使学生原有提交和 AI 介入范围都保持可见。

       * 网页协作与本地 agent 协作可以依赖同一份结构化、可追溯历史，导出为 Git 仓库后即可在本地继续处理。

   * **早期选型**

       * Git 提交成本低，产品早期可以先在代码库中探索目录、消息和文件组织，不必因日志需求立即引入数据库。

       * 目录与提交结构收敛后，如果性能和查询需求成为瓶颈，再迁移到更重的存储；先让真实需求证明复杂度。

## 记住现在、历史与教训

   * **版本历史的双重职责**

       * > **定义**：Agent 时代的版本历史既保存可回退快照，也把失败与修正沉淀为可复用教训；记录目的不再主要是追究个人责任。

       * 逐行归因仍可帮助理解变化，但 agent 不会因犯错承担人的组织后果；项目目标是修正并前进，而不是通过历史惩罚执行者。

       * 即使相同 prompt 的多个 agent 结果可能略有差异，历史仍要保留方向、失败点、修复路径和快照。

       * > **易错点**：不追究责任不等于删除历史；方向错误后没有快照，走得越远，回头修复的代价越大。

   * **记住现在**

       * 仓库负责保存当前项目，让代码、文档和测试有统一可管理的载体。

   * **记住历史**

       * 历史让看似应删除的内容仍可找回，并展示项目如何演进、在哪里失败、为何回到某个点重新尝试。

   * **记住教训**

       * 失败和修正应成为下次可复用的经验，帮助决定一次修改应迈出多小的一步、何时提交、何时锁住范围以及何时换方向。

   * **本地启动与持续演进**

       * 从空 repository 开始，先让产品意图有地方沉淀，再通过可构建、可测试、可审计的快照逐步前进。

       * 早期 prompt 会长期影响项目走向；一个随手加入的“最小验证产品”、过早数据库或直接多 agent 决策，都可能决定后续是在持续修正还是顺畅演进。

       * 版本控制只能提供记忆与协作结构，真正的团队管理仍要求明确目标、组件边界、任务范围、锁、提交和合并时机。
