# 需求与架构：把方向和复杂度钉死

## 软件工程困难的来源

* **软件生命周期**

    * 经典阶段路径是 intent → spec → implementation，但这条路只画了一半：implementation 做完之后还得维护，生命周期并没有结束。

    * 走完这条向下的路，自然长成一条瀑布式的过程，每一段都会向下一段沉淀东西。

    * intent 与需求阶段对软件形成的认识逐渐进入 specification space 并形成依赖关系。

* **依赖网络（data dependency）**

    * > **定义**：实现阶段的各种 artifacts（模块、函数、代码、测试）之间既有直接依赖也有间接依赖，织成的交错网络。

    * 后面某处发现一个错，会沿着依赖关系一直反推、回溯到前面的某一个决策上。

    * 若该决策在事后被证明是错的——设计不合理、实现达不到预期、需求或设计做错——被污染到的下游一大片全部失效。

    * 后果是需要重做，并带来大量成本；对这种开发模式的批判，逻辑就来自 data dependency。

      ```text
          intent ──▶ spec ──▶ implementation ──▶ 运行与维护
                        │
               模块 ─┬─ 函数 ─┬─ 代码 ─┬─ 测试   ← artifacts 交织成网
                      └────────┴────────┘
                                │
                   data dependency（直接 + 间接）
                                │
                                ▼
              后端发现一个错 → 沿依赖反推回上游某个决策
                                      │
                                      ▼
                     那条决策被证明是错的（设计不合理 / 实现达不到预期）
                                      │
                                      ▼
                   下游一大片被污染、全部失效 → 重做 → 大量成本
      ```

* **逻辑制品**

    * > **定义**：软件是一个纯粹的逻辑制品，它有形式语义（formal semantics），容不下任何细微的差错。

    * 物理世界里"软"的东西摁下去会瘪、做完又弹回来，下次还是好的；软件不具备这种自我修复性。

    * 极端例子：程序从 STDIN 读入 N，N 等于 1，循环接下来从数组读一个元素到寄存器。若程序运行在卫星上、有一个宇宙射线击中内存，unsigned integer 的最高位翻转，1 变成巨大无比的数，整个程序彻底 collapse，无限制地继续从输入读数据。

    * 也可能不是当场挂住，而是读了一千个、一万个数字之后才产生一个 memory error。

    * > **易错点**：写代码时从来没有考虑过"程序里的内存可能发生一个 bit 的翻转，你的程序还对吗"——肯定不对。

* **silent error（静默错误）**

    * 处理器制程越先进，热噪声下有些指令——特别是密度特别大的那些——可能产生静默错误。

    * 表现是同一条指令在这台机器上执行和在那台机器上执行结果不一样，且可能要这台服务器运行一段时间之后才出现，是制造时候就带上的缺陷。

* **可追踪性（traceability）**

    * > **定义**：理想情况下，每一个测试用例、每一段代码都能够关联到、追溯到过去发生的事情和做过的设计。

    * 提出的背景：人和人很难对齐；不写文档很可能最后只剩一份代码；出错了都不知道应该追溯到过去的什么时候。

    * 要能回答：这个系统里到底发生了什么、我改它会影响谁、我改这个设计会影响哪些测试用例。

* **UML（Unified Modeling Language，统一建模语言）**

    * 动机是可追踪性还不够——如果有一个结构化的、有语义的语言来表示它，显然更好。

    * 它的目标是去对齐整个世界上的软件工程实践。

* **学科入口**

    * 软件工程研究的是：做需求分析、做系统设计、做系统实现的时候，有什么样的方法。

    * 既包括带人文关怀的方法（用 checklist 说清楚产品经理该怎么管人），也包括写代码时怎么写测试、能不能做自动化测试与自动化分析。

    * 软件工程关乎整个软件生命周期，但你被迫从写代码这一层开始学：不懂代码是什么、没有码农开发软件的痛苦，就做不好产品经理，对"这件事能不能办到、花多少成本能办到"的判断只能是空的。

    * > **提示**：所以先学一门最基础的、已经过时但还有人用的语言，再在这条基线上不断产生新知识——知道世界是怎么失败的、新语言是怎么创造出来的、为什么要有它。

    * intent 到 spec 这个阶段，决定了一个软件系统从零开始走向的最关键的部分；所以先讲版本管理（怎么从空项目出发），接下来要把控软件执行的方向。

## 方向：AI 时代什么变便宜了

* **三段杠杆**

    | 杠杆 | 回答什么问题 | 差异带来的后果 |
    | :--- | :--- | :--- |
    | 需求 | 我到底要一个什么功能的代理 | 需求要分版本，不同版本软件走向肯定不同 |
    | 产品设计 | 这个产品只有我自己用，还是给另外一个人用 | 自己的知识和偏好，别人可能不习惯 |
    | 架构 | 这个软件会变成什么样 | 几个字的 prompt 就会膨胀成一整套技术栈，需求一膨胀就进维护的泥潭 |

* **需求（intent）要分版本**

    * 同一个"代理"需求，可能是做一个不帮助你学习的 agent，也可能是你已经进了课题组、对"读研究论文"有很强需求——不同需求下软件走向肯定不同。

    * 需求上的极端取值，会对 AI 生成的东西的走向、技术债的累积带来非常大的影响。

* **产品设计**

    * 直面最终产品：这个产品是只有你自己用，还是想给另外一个人用。

    * 很多自己用的东西非常顺手，但给别人用就不那么舒服：你有自己的知识和偏好，对别人来说可能受不了、不习惯（比如你喜欢的命令、内行的工作，普通人肯定不要）。

* **技术债（technical debt）**

    * > **定义**：你做任何决定的时候就已经背上的债务——做这个决定时，你在做 MVP 阶段不可能知道后面会怎样。

    * 生成路径：同一个 MVP 需求 + 几个字的 prompt（"用 client–server" / "做成命令行程序" / "做成网页应用"）→ 架构选择一路落成具体技术栈决定（有 CRUD 就涉及数据库选型，命令行程序涉及命令行库，网页应用涉及前端框架）→ 第一个文件写出来就进入 agent 的上下文 → 每做下一个需求都带上之前所有的历史 → 技术债开始累积。

    * 它们功能上都差不多，看起来都实现了你的需求，但每个都会膨胀。

    * 今天的 AI 不会主动从需求、产品设计、架构的角度看这件事；哪怕只是几个字的 prompt（零开始的项目用 client–server 还是 CLI 架构），同一个 MVP 需求也会得到完全不同的 MVP。

* **日志缺失也是技术债**

    * 实践上出了问题要去看日志，这意味着写软件时需要输出足够多的日志。

    * > **易错点**：不告诉 AI 的话它不会主动做，它会生成一个没有任何日志的软件系统——这同样是技术债，而且你不确定自己能不能找到这个问题。

* **MVP（minimum viable product）**

    * 作用是快速找到一个从 intent 到 specification 再到 implementation 的切片，在切片上把整个软件流程走完；有了它，你看到一个产品马上就知道哪个地方设计错了，返工成本比较低。

    * 做法是优先实现最重要的功能；这个本能本身是对的。

    * > **易错点**：MVP 不完备。做 MVP 时不要去纠结那个按钮、那个样式应该长什么样——样式是 dependent 的，整个界面设计 depend 到所有功能的实现；上面设计一改，你调出来的样式很可能就作废了。

    * 原则：不要做无用功，不要去研究一个你即将会扔掉的东西。

* **没有银弹（there is no silver bullet）**

    * 银弹的本义是：吸血鬼和狼人没有办法普通杀死，必须有一把 silver bullet。

    * 随着软件增长，最早、第一个时刻定下来的那些决策会不断失效。

    * 课程作业可以随时清零、从零从头再做一遍；软件一旦上线就开始和物理世界交火，必须持续背着 technical debt 维护下去，前面做得不够前瞻，成本会不断变得更糟糕。

    * > **易错点**：做 MVP 容易会产生一种"驾驭 AI"的错觉——AI 确实可以往后修，迭代三个版本都行。但一旦在真实系统里运行足够长时间（比如计算机系改成计算机学院），面对这些事而原来的设计不起作用时，麻烦就来了。

## 需求工程

* **调研范围**

    * 真实案例是《南京大学本科教学服务平台需求说明书》：让一个 agent 只探索教务系统里**与教师相关**的功能后得到。

    * 在软件工程课上可以看来自真实企业的需求说明书片段，而这个是完整真实的一份——身边随手可得的案例同样能变成需求说明书。

* **需求说明书的目录骨架**

    ```text
    《南京大学本科教学服务平台需求说明书》
    │
    ├── 调研方法
    ├── 证据边界
    ├── 业务目标
    ├── 成功标准
    ├── 详细用例规约
    ├── 功能需求目录            ← 每条带编号 ID，traceability 就挂在这里
    │   ├── 门户与身份
    │   │   ├── 检索和应用入口
    │   │   └── 身份选择：服务支持多种已分配身份时，
    │   │                  提供身份选择并显示当前身份
    │   └── ……
    ├── 验收场景
    ├── 需求清单（结构化 checklist）
    └── 术语文档与配套文件
    ```

    * 从调研方法、证据边界到业务目标、成功标准，再到详细用例规约、功能需求目录，最后是术语文档与配套文件。

* **术语与 traceability**

    * 在我们看来写这么多像 slop，但面对真实客户时术语就很重要——客户看不懂的时候可以去查一下术语 thereby 就对齐了。

    * 功能需求目录是有 traceability 的：每一条需求前都有"角色"、参与者、业务目标之类有形式语义的东西，这个形式语义可以帮你建立 traceability。

    * 对比是明显的：说"我这个教学班是和学生管理有关的"是自然语言；用有编号、有形式意义的 ID，就一定程度上帮你做了 traceability。

* **假教务系统**

    * 让 GPT 起一个 sub agent，不看任何真实的教务系统，只根据这份需求说明书实现一个假的教务系统。

    * 产出真的和真系统很像：返回到全部教学任务、我的教学任务、本科教材管理、软件工程实践者的研究项方法、编辑记录；能编辑、能保存记录（"记录已保存"）、有学生名单。

    * 命名偏文雅，是 GPT 的偏好。

    * 它没有阻止你记录一个缺课次数——这个数字已经超过了这学期上课次数的总和，本身不合理。

    * 需求说明书里居然真的包含了"缺课次数"这个功能点，所以 AI 会原样把它实现出来。

    * 当需求清楚、需求文档写到那个程度时，编码、traceability、测试的事情其实 AI 都能帮你搞定，你只需要一份需求。

* **验收场景与需求清单**

    * 验收场景加上一个非常结构化的需求清单，构成一个非常好的 checklist。

    * 这个 checklist 最终可以按条分掉：前 20 个需求分给这个团队，后 20 个分给另一个团队，就能 track 每个人的进度，知道哪个团队落后于实现需求、落后于进度。

    * traceability 有了以后，作为管理者就可以把团队管起来。

* **教务系统是史诗级的需求爆炸**

    * 搜索栏可以自然语言问"教学楼的灯一直没有解决"，系统答"我正在理解您的问题"，但提交后被基建处打回说"不归我们管"。

    * 出现了一个你不知道存在的功能（教师课表/本科），显然是后来加上的。

    * > **易错点**：学生名单里能看到电话号码，显然是一个比较糟糕的 feature。

    * 教学周底可以直接用 AI 填满，没有人管、没有任何审计；作者认为他们更应该把这个教室的灯给修好。

* **条件性功能**

    * "期末考试签到表"只在期末考试期间可以点击；没有到发布的时候，会弹出一个窗口告诉你无法打印。

    * "我的助教"里搜到教学班名称里带"JX"的教学班；点新增助教时提示"请在可维护时段内操作课内教学班"——已经不能申请助教了。

    * 交互本身有设计感：服务页面明确当前学年学期，允许在授权范围内切换，留一个 dropdown 供选学期、教学周次、课程与大纲、教材选用。

* **疫情带来的叠加**

    * 慕课功能在疫情之前是没有的；疫情时领导说需要为老师添加慕课，添加完慕课以后需要慕课的助教，而慕课的助教不要当成普通教学班的助教，要当成慕课的助教。

    * 结果就是一个史诗级的 bug，删除与新增都受限于可维护时段。

* **实际点出来的 bug**

    * "查看大纲"只展示最新一个教学班，等了很久页面才刷新出来，不满足功能性需求里的"要求状态正常"。

    * "编辑教材"进入另一个页面后弹出"再试一次"——编辑教材曾经好像是可以的。

* **软件工程为什么曾经很难讲**

    * 学生不会去见真正的客户，也做不了需求级的软件系统：从最刚开始学编程语言到毕业，能力增长不足以面对真正的软件客户。

    * AI 之前只有很少量的精英独立开发者，经过几年开源社区的洗礼才觉得自己可以独立；现在独立开发者爆炸了。

    * 承接合同意味着要承担"逾期交付、达不到功能要求、达不到非功能要求"的责任；作为成年人你可以成立公司去签这样的协议，但不敢，agent 敢。

## 需求永远说不清楚

* **需求定律**

    * > **定义**：需求永远不可能说清楚。第一，你永远不可能真的把用户的需求说清楚；其次，需求不是一成不变的。

    * 需求无非就是通过无尽的和客户的沟通，把客户想要什么给想清楚；小到界面上要不要放当前学期和学年、某个地方要不要有一个修改按钮，这些都要跟用户对齐。

* **同理心**

    * 做设计、尤其做需求时，是计算机专业同学普遍缺乏的那种软技能：你要假设所有人都会写程序是不成立的。

    * 典型用户是那位教务员：本科学历，今年已经 53 岁，还有两年就要退休，上大学时可能甚至都没有操作过电脑；系统要为她设计，也要同样为"我"和年轻人设计。

    * 怎么从她那里得到那一张需求表，完全是另外的一个问题。

* **行业壁垒**

    * 有行业资质、在这一行摸爬滚打 20 年的公司有大量领域知识，知道教务员想要什么，知道学位授予的流程应该怎么样变成需求文档列表。

    * 毛头小伙子、本科生不知道这个教务员到底想要什么，设计出来的软件和需求很有可能有偏差。

    * 做软件都是被迫的：空项目时没有任何东西漂移，但一旦写出一个需求列表，AI 或人类马上给你实现一版——那一版一出来，你就背上了技术债。

* **离散数学拆课引发的裂缝**

    * 事件：离散数学这门课被拆成上下学期两门，理由是第一门课没有教会大家那个数学的语言。

    * 后果是准出结果变了、保研要求变了，新旧衔接不上。

    * 第一版需求在写下时非常合理：界面上有一个叫"毕业要求"的地方，给教务员一个下拉框、一个"增加一条"按钮，按钮可以选一门课程。

      ```text
       第一版需求：「毕业要求」= 必须选修《离散数学》
              │
              │  离散数学 1 门  →  2 门（拆成上下学期）
              ▼
       需求裂缝 ①：得加一个「或」
              │  毕业 = 选过离散数学  ∨  选过离散数学一
              ▼
       需求裂缝 ②：转专业的课能不能抵扣？
              │  抵扣「离散数学一」，还得再上「二」？
              │  还是一门抵扣「一 + 二」？
              ▼
       需求裂缝 ③：重修的算不算？交换的算不算？
              ▼
       裂缝一直叠，叠到无穷多
              ▼
       系统里没有的东西，最后还是有个 override
              ▼
       打电话给工程师，直接改数据库里这个同学的毕业条件
       —— 而且这个是档案可查的
      ```

* **裂缝的代价**

    * 改需求会破坏你做出来的整体一致的设计；一旦需求中间产生一个裂缝，它会传递到系统里的各个部分。

    * 当一个看似很小的需求要改、牵动整个系统各个部分时，你就会一团乱麻；屎山就是这样累积的。

* **override**

    * 系统里没有的东西最后还是可以暗箱操作，最终总是有个 override。

    * 例子：一个学生 6 年了拿不到本科学位，就是因为离散数学这门课，而离散数学刚好被拆成两门；现在是秋季或春季学期，马上要毕业，那门课不会再开了。

    * 教学主任认为这两门课之间可以存在替代关系，最终办法是打电话给工程师，直接改数据库里这个同学的毕业条件把它改成满足——而且这个是档案可查的。

    * 人类世界意义上也有一个合理的解释：这个同学学了旧的离散数学，还是可以抵扣新的离散数学。

* **规则的不可穷举**

    * 除了"或"，还有重修、交换、抵扣。

    * 抵扣这一类就可穷举不完了：一个从别的院系转过来的同学，别的院系也有离散数学课，这门课能不能抵扣计算机学院的离散数学？抵扣一和二，还是只抵扣一、他还要再上一个二？

    * 一旦面对开放的物理世界就没有办法了，1 万个、1 万个。

* **缺课次数**

    * 这是 2018 年上课第一天发现的老师端功能：可以给同学设置缺课次数，作者以前都是学生端，第一次用老师端，觉得很好玩。

    * 作者认为这个需求本来不该做：同学缺课就缺课，不需要在系统里留证据；只要老师有签到表、点名表留证据、扫描一下就可以开除，学生手册里已经写了无故缺课达到多少次可以开除。

    * 绕过了前端校验：想输入一个非常大的缺课次数时被直接拒绝，说明 AI 实现的前后端都会做校验；把一位同学的缺课次数从零改成了一，好像也不是什么有害的操作。

* **一次 500 事故**

    * 改完之后立马发现：所有只要能选出这位同学的、这个选课记录的页面全部 crash，直接 500。

    * 只好打电话给教务说交互系统崩溃了；第二天工程师登录数据库，把那个"一"的条目修复了。

    * 这就是真实面临的软件系统的需求。

## 架构就是控制复杂性

* **架构（architecture）**

    * > **定义**：架构本质上就是怎么样去控制一个东西的复杂性。

    * 它并不玄学、不高大上：从你第一次设计任何代码、任何系统的时候，无论它多小，里面都有这种架构思维。

    * 第一步要回答的是：软件第一步迈向哪里，对软件的长期生存有最好的效果？第一步实际上是软件的架构。

    * 目标是做一个最小的软件，使它能够随着需求的膨胀和改变，依然有一定程度上的一点韧性——哪怕是最小的代码，它都是有架构的。

* **两种起手式**

      ```text
      ✗ 一步到位：所有东西塞进一个数据库
         ┌────────────────────────────────────────────┐
         │  需求 · 课表 · 教材 · 助教 · 成绩 …        │
         └────────────────────────────────────────────┘
         快，能 work，AI 也能很快给你做出来；
         但只要需求一膨胀，你就进维护的泥潭。

      ✓ 留出余地：先把耦合解开
         需求 ──▶ [需求表]        课表 ──▶ [课表表]
         教材 ──▶ [教材表]        助教 ──▶ [助教表]
         每块独立演化，改动不会互相传导。
      ```

    * 说白了就一个：把耦合解开。

    * 一开始就用一个数据库存放所有需求，能快速得到一个能 work 的原型，AI 也能很快做出来；但如果不去仔细思考这个系统里到底哪些概念是可以分开的，就很容易进入软件维护的泥潭。

    * > **提示**：这里说的"架构"不只是一个 MVP——已经算一个小小产品原型的东西维护起来会变得非常困难。

* **parsing state**

    * > **定义**：把外部世界不可控的复杂输入，先归约成你自己可控的简单状态，再在简单状态上做业务逻辑。

    * 它是一种抵抗需求变化的方式：argv 可以有各种各样的变化，但 parsing state 把这个问题给解决了。

* **getopt 与 POSIX 约定**

    * `getopt` 背后是 POSIX 标准里的**一整套约定**，它把"参数长什么样才算合法"这件事整个接了过去。

    * 穿过这一层交给你的，是一个干净的 parsing state；剩下你要写的只有两样东西：一个 `while` 循环，一个 `switch case`。

      ```text
            argv：原始字符串
            （长短选项混排、顺序不定、平台差异全在这一层）
                              │
                              ▼
            ┌──────────────────────────────────────┐
            │        getopt / POSIX 约定             │
            │  把「字符串」消化成「参数序列」          │
            └──────────────────────────────────────┘
                              │
                              ▼
                  parsing state（几个干净的变量）
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        while + switch case              你的业务逻辑
        （参数怎么组合都已经处理完了）      （只面对简单状态）
      ```

    * 真实代码里几乎见不到有人从零写 parser，因为已经有人替我们把这团复杂性隔开了。

* **argv 的复杂性**

    * `main` 里的 `argc` 和 `argv` 是操作系统和进程之间的约定，参数以字符串形式传过来。

    * 逐个 string compare 的结果是规则越堆越乱；保研机试现场遇到处理 `argv` 的题目也不会去 string compare，因为世界上有个东西叫 `getopt`。

    * `argv` 本身非常复杂：敲一条 `npm run dev` 就有很多参数，还有些支持 UNIX 风格的长短参数；C 时代要写这样一个 parser 是很复杂的。

* **压缩就是智能**

    * 架构能力从你学过的每一个东西上来；如果它是好的、它是优雅的，它促使了你对这个问题的思考。

    * 把它压缩了，你的第一性原理（first principle）就出来了，你总是从 first principle 去推导"应该怎么样"。

    * 所以这些能力是学校和社会的积累共同赋予的。

* **共情别人的能力**

    * 架构能力里有一块叫共情别人的能力，任何编译器都教不了你。

    * 获得它必须和教科书、做题之外的人打交道：那个马上就要退休的、很优雅的教务老师是怎么看待教务系统的，他的想法可能和你不一样。

    * 你的想法总是最好的——数据库最高的性能、什么什么都行；但他来说，他只是想要那个字大一点，点鼠标的时候不要手滑到旁边那个按钮上。

* **从模式中学习**

    * 在 GitHub 上找到一个好的项目、读它的 Readme，或者看到一个 `getopt`，都要再往后想一想：这确实是一种模式。

    * 这个模式就是把一个复杂的字符串最后变成一个简单的 parsing state；任何好代码背后都有架构设计，架构背后都映射到需求。

    * 作为 unsupervised learner，你看得多了自然就能泛化，但要有意识地去看好的东西并追问"为什么要这样"。

    * > **易错点**：把一个语法点念出来，不等于让学生知道这个语法点为什么存在、什么时候该用——讲 lambda 就是 `a`、`b`、`return a + b`，这种讲法和没讲没有区别。

* **跳出问题看问题**

    * 代码之外有数学的规律，数学之外有社会的规律，社会之外有宇宙的规律；在任何一个小的地方，都能看出架构水平的高低。

    * 教 C++ 应当讲清 C++11、14、17 里的特性以及这些特性应该怎么用。

## 十行代码：非递归汉诺塔

* **四个答案**

    | 答案 | 落在哪儿 | 评价 |
    | :--- | :--- | :--- |
    | GPT | 步号二进制末尾零的个数 → 盘号 | 数学上是对的，highly optimized |
    | DeepSeek V4 flash | 递归即栈，任务留在杆上 | 非常优雅，基本是标准答案 |
    | 豆包 | 同上 | 思路对，代码有瑕疵 |
    | CSDN 那篇 | 自己定义了一个 `move` | 比 AI slop 还严重 |

* **GPT 的说法**

    * 盘号等于 1 加上步号二进制末尾零的个数，$peg = 1 + \text{末尾零的个数}$，并把每个盘子的移动方向也给出来；这个移动方向是固定的吗？不知道，但它应该是对的。

    * 它说得很狂："即便我不做人类了，你也写不出来，是因为你的数学不如我好"——在他看来他找到了 Hanoi 的数学性质，数学上是对的，那我就是对的，毫无破绽。

* **递归即栈**

    * DeepSeek V4 flash 的思路是递归的真相就是栈：把"还没搬完的那一堆任务"留在杆上当成栈底，每一轮只执行栈顶的那一个任务。

    * 每一轮弹出一个任务，搬运一个盘子，再把剩余任务压回去。

    * 百度上搜"非递归汉诺塔"，第一个条目居然还是递归汉诺塔；往下找到 CSDN 的第一篇非递归汉诺塔，代码里有一个 `move`——可 `std` 里本来就有 `move` 了。

    * > **易错点**：CSDN 那份甚至比 AI slop 还要严重，而评论区还有 AI 在帮你营造"这个 CSDN 博客质量很高"的感觉；被这种 slop 污染过，还不如直接跟 AI 学。

* **C 语言就是状态机**

    * 提问"为什么大家写不出来"背后的答案，是对递归这件事理解得不够深。

    * C 语言是一个状态机，一个 single step 就是它的 operational semantics（操作语义）；小步语义里比如"汉诺塔减一"，是一个 well-defined 的、程序语言世界里的一步操作。

    * 既然它是 well-defined 的，那只需要模拟这个操作——完全可以写一个 C 语言的解释器。

    * 当你理解了 C 语言的解释器，就很容易写出把任何 C 代码变成状态机的实现：把 C 语言的小步语义翻译成一个状态机的表示。

* **四步推导**

      ```text
           C 语言程序（递归写法）
                    │
                    │  翻译
                    ▼
           小步语义（operational semantics）
           每一步都是 well-defined 的状态转移
                    │
                    │  模拟
                    ▼
           状态机表示（显式的、可回退的）
                    │
                    │  simplification
                    ▼
           非递归的十行实现
      ```

    * 这两步是等价的：你可以把任意程序翻译成它，也可以做一次 simplification、从它变回来。

* **等价性与 overkill**

    * 如果你觉得这个代码不够优雅，对 Hanoi 来说这是 overkill 了，因为它对任意程序都成立。

    * 这也是理解 C 语言形式语义的好机会。

* **四层落点**

    * GPT 跳到了数学规律那一层——一切都是数学规律，把程序世界里的数学规律理解清楚就没有解决不了的问题。

    * DeepSeek 跳到了编程语言世界那一层——"递归是栈"这句话它在语料里学过，它只是把人类反复说的话投射成了代码。

    * 作者往外多走了一步——把对编程语言世界的理解投射成递归和非递归的区别，再投射成这样一份代码。

* **强化学习能不能引导**

    * 有较强的信心认为，强化学习可以把这个 GPT 往状态机这个方向引导；它一旦学会，在适当的时候也能做出这样的实现。

    * 保研研究生被要求写非递归汉诺塔时写不出来——这十行代码背后联系到的架构，正好回答了大家"为什么写不出来"这个问题。

## 两千行：Excel 里的二维码

* **需求本身**

    * 把任意长的字符串编码成一个能直接扫描的二维码：Excel 里一个输入单元格、一些输出单元格，任务非常 deterministic。

    * 需求看起来明确，但其实有很多坑。

* **坑一：Excel 本身在演化**

    * Excel 是有版本的，从 2019 到 2023 不断增加新功能。

    * "去查找学号对应的成绩"以前是一个叫 VLOOKUP 的函数，微软后来推出了更方便的 XLOOKUP。

    * Excel 在演化，需求马上就变得模糊不清：到底是兼容旧版本标准（发给教务老师，他也能打开这个二维码），还是做一个自己用一用即抛的（可以用最新语法实现最简单的公式）？

    * > **易错点**：AI 给你 vibe code 了一个"Excel 2023 公式"的实现，突然有人说"2023 不行，要改成 2019"，再改"改成 2003 这样的老版本"——设计和实现从头回到原点，全部重新再做一遍。

* **坑二：单元格位置是需求**

    * 如果对最后出来的位置不满意，要把它整体往右移一格；所有单元格都是硬编码的，就会立即崩溃。

    * 这就是它对需求变更的抵抗很糟糕的地方。

* **规模的放大**

    * 对一个 2000 行的项目来说，重做是 OK 的。

    * 但一个 2000 万行的项目已经嵌入到巨大无比的需求里、嵌入到教务系统里面、和其他部分产生了关联时，作为项目经理只能提一个要求：我要加人，我要加钱。

    * 这显然就是一个架构没有设计好的标志。

* **Excel 的定位**

    * Excel 本身不提供从"算法"到"公式"的那条通路。

    * Excel 本质上是为了财务、报表这些而设计的；管理学生成绩只是个小数据库，它本身就不是为了做 Turing complete 计算而做的。

* **agent 的能力自估**

    * agent 对自己的能力到底到什么程度是有估计的：任务足够困难的时候它会"不做了"。

    * 比如两个 sheet，第二个是学生实验成绩、第一个是你填好的期末考试成绩，要写个公式把学号对应的实验成绩拉过来——这在它能力范围内，它会一把梭。

    * 明显超出它能力范围的，它还是会试图去分解这个问题，它也会做架构；不过至少今天的模型，在做架构这件事上稍稍是有一些落后的。

* **二维码编码三步**

    * ① 数据编码：确定版本、纠错等级、掩码、大小，把字符串变成 n 个码字。

    * ② 生成纠错码：把 data 乘以 $x^{26}$，在生成多项式上取模，$c(x) = f(x) \cdot x^{26} \bmod g(x)$，在 GF 上对生成多项式取模即可。

    * ③ 铺进矩阵：当场看到的实现里是 134 个数据码字，算完 ECC 之后一起铺进矩阵。

      ```text
       字符串
         │  ① 数据编码（版本 / 纠错等级 / 掩码 / 大小）
         ▼
       n 个码字
         │  ② 生成纠错码  c(x) = f(x)·x^26 mod g(x)
         ▼
       数据码字 + ECC
         │  ③ 铺进矩阵
         ▼
       0 / 1 矩阵  →  扫码枪一扫，字符串回来了
      ```

    * 二维码是完全有规范的，容易用算法描述；用一个 Python 实现再容易不过，最后打出一个 0/1 矩阵，如果考综合能力这是一个不错的题目。

* **难点的真正位置**

    * 简单的算法在 Excel 里实现困难，gap 不在算法难度上。

    * 不存在任何一个翻译器、一个编译器，可以把一个 Python 编译成 Excel——这个显然也做不到，所以没有一个 py-to-excel 的编译器，PYXL 这个东西不存在。

    * 直接把伪代码或自然语言交给 LM 去编译：LM 直接上手就做，做了；然后需求漂移的时候会遇到很大的问题。

    * 如果 AI 直接给你写成一条 Excel 公式，公式会太长、Excel 的计算能力又有限——因为我们"偷"了一个 Lisp 程序；好比用 brain 去实现一个毁灭战士级别的游戏。

* **中介语言（intermediate language）**

    * 思路是在 Python 和 Excel 之间构造另外一个语言：它既可以很容易地翻译成 Excel，又可以继承一定的 Python 的功能。

    * 形态就是刚才那份伪代码——一个表达式树，一个小的编程语言，支持描述这些运算需要的东西，比如"异或"、加 AB、或者取出一个字符串里的某一个字符。

* **两条翻译路径**

      ```text
            需求：Excel 里生成一个可扫描的二维码
                            │
                            ▼
              LLM 生成「中间语言」程序（表达式树）
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
        翻译成 Python                 翻译成 Excel 公式
      （逐节点递归，验证语义）     （每个算子一条「落格」规则）
              │                           │
              ▼                           ▼
       公式写对了吗？                 交付给用户
              │                           │
              └──────► 对了才往下走 ◄──────┘
      ```

    * 翻译成 Python：直接把它 dump 出来，递归地左子树、右子树，然后根据这个节点拼起来。

    * 翻译成 Excel：要求每一个节点都有一条翻译成 Excel 的规则，就能把这个结果放到一个格子里（任意格子都可以），两个格子拼起来也就有了。

    * Python 那条路径同时用来验证语义：公式写对了才往下走，再交付给用户。

* **架构同构**

    * 这个架构和最小的例子里讲的 `getopt` 是一样的设计：写一个命令行工具，第一件事情先 `getopt` 得到一个 parsing state，再从那个 parsing state 出发去做下一步。

    * 好的架构可以承载需求的变化：未来 Excel 版本改了，无非就是把一些算子用另外一个方式去实现。

* **承载优化**

    * 有了这个语言，如果觉得某个地方生成了太长的代码，就有改写规则，可以把一个程序从一个形态改写成另一个形态。

    * 一个变量在循环里每次都计算但值都一样，就可以把它提到循环外面；编译器能自动做这件事，语言模型可以手工做这件事，而有了中间语言，就可以让大语言模型去优化它。

* **profiling guided optimization**

    * 先知道性能瓶颈在哪里，然后再用性能的 profile 去指导你的代码应该写成什么样。

    * 人类的优势正在于有很多领域知识，领域里有非常多好的设计；今天的 AI 推理其实也在干"算子"这件事。

## 五十万行：CRUD 架构的天花板

* **AI 交出来的教务系统**

    * 形态上是一个 83KB 的 TSX 加一个 38KB 的 services，仍然是 monolithic；GPT 还很贴心地用代码格式化工具帮它格式化完了，看起来正常一些。

    * 架构是经典三层单体、前后端分离，而且有几个生产级横切设计：乐观锁、幂等、事务、审计、统一错误；它有软件工程的直觉，做了那些摸爬滚打几年才理解的设计。

    * 还自评有数据驱动、横向扩展、扩展性很好；另开一个独立 session 问它"这个软件能维护吗"，它说"能，能，能"，只不过把业务逻辑挤在几个大文件里。

    * > **结论**：跳出问题看问题，这还不是一个非常好的架构——本质上是一个 CRUD 的架构。

    * 很快 AI 生成生产软件的方式就要超过人类了。

* **CRUD（增删改查）为什么让人放心**

    * 前提是：软件是物理世界过程在信息世界里面的投影，而物理世界是有状态的——everything is a state machine。

    * 所以软件系统很容易建模成一个 state transition system：持久的状态用数据库存，比如一张表表示学生（学号、姓名、院系），一张表表示学院，一张表表示选课。

      ```text
       物理世界（有时间、有历史、会变）
                  │
                  │  投影
                  ▼
       信息系统：持久化的「当前状态」= 一组二维表
                  │
                  ▼
       任何时刻打开网页 → 当前状态的一个 consistent 视图
      ```

* **normal form 与冗余**

    * 数据库要求消除表里所有的冗余，把数据库 factor 成 normal form。

    * 最好不要在学生表里放课程；引用一个学生时尽量用 id 而不是姓名——姓名可能重名，就算不重名也会带来麻烦。

    * 更好的做法是把姓名的这一列去掉，换成一个学生 id（相当于一个链接），它指向学生的信息，这个学生还可以再指向别的表里的某些信息。

    * 这就是把冗余给铲除、把冗余的 dependency 铲除掉：一个地方改了不需要改另外一个地方。

    * 例子：学生改名在中国是合法的，分解后你把这个名字改掉就行，记一个曾用名；如果两份名字存了两份，那两个地方都要修改，这是很大的代价。

* **consistent 视图**

    * 一般来说会把这样的世界建模成状态：任何时候这个状态就代表了在现在这个时间点上，南京大学有哪些学生、有哪些学生选了哪些课、有哪些老师。

    * 前后端分离是一个非常经典的架构；今天我选择退学（因为没有买到 token），那就是一个 update 数据库的过程，状态 A 还在迁移到下一个状态里 A 就没有了。

    * 这就是一个始终 consistent 的视图：永远在交互系统里打开网页，就看到当前状态的一个投影，非常经典，没有任何错误。

* **有损投影**

    * > **结论**：看当前状态时看到的是一片祥和的景象，但当前状态把所有的历史都丢掉了；计算过程丢掉之后，这个软件又是现实世界物理过程的一个有损的投影。

    * 退学（没买到 token）在 CRUD 里只是一次 UPDATE，从状态 S0 到状态 S1，A 在变成 A 不在了，一切正常、视图一致，但 S0 和 S1 之间到底发生了什么，没有留下任何痕迹。

* **是否允许毕业**

    * 学生表里有一个 column 叫"是否允许毕业"：学分修够就允许毕业，没修够就不允许。

    * 这个值是由很多其他状态算出来的：每当你修了一个学分、或者毕业设计状态改变时，都要重新计算一遍能不能毕业。

    * 这是个很典型的需求点：教务员、辅导员老师必须能在教务系统里导出到现在还毕不了业的学生，才能一个一个谈话。

    * 这样的东西是历史上的计算的 dependency，随着当前状态都没有了——你知道这个学生可以毕业，但不知道他为什么可以毕业；知道不能毕业，也不知道为什么不能。

* **系统没建模的物理事件**

    * 物理世界建模不了的东西，全部需要通过其他途径解决。

    * 政策更新了、领导批准了，但新的培养方案还没有导入到教务系统——物理事件已经发生（培养方案通过了、学期开始了、我已经上课了、教室的灯没修），系统里没有建模。

    * "这个教室还不能用"——第一周整个仙林这一片都还在修、教室不能用，教务系统没有建模；这一点最后靠他们手改、重新安排教室。

    * 慢慢积累，系统里会有大量不一致的数据，时间变成无法解释的黑洞：明明这个同学没交学费、应该毕不了业，他为什么毕业了呢？明明这个同学不该毕业，他为什么毕业了呢？

    * 结论：面对这种需求的时候，CRUD 就会死。

* **改与不改都错**

    * 院系发生调整时，CRUD 架构就瑟瑟发抖，因为它是一个 point of truth——所有的事实都在这儿。

    * 把"计算机系"改名成"计算机学院"：要，也不对；不改，也不对。

    * | 改：把对象改名 | 不改：保留历史对象 |
    | :--- | :--- |
    | 计算机系 → 计算机学院 | 计算机系保持原名 |
    | 当前状态确实对了 | 历史状态确实对了 |
    | 但 2011 年的毕业记录变成「2011 年毕业于南京大学计算机学院」→ 事实不符 | 但所有 department id 仍指向旧对象，仍得做一次数据库迁移，并想清楚新旧对象的关联关系 |

    * 改的话，select 出来的毕业记录就是"2011 年毕业于南京大学计算机学院"，属于事实不符——2011 年时系统生成打印的证明上并不是这个名字。

    * 不改的话，你现在所有的 department id 都指向这个学生的 department id，都指向计算机系，还是得把它改过来：创建一个新对象，并考虑清楚新对象和旧对象之间的关联关系。

* **迁移的代价**

    * 只要你假设这个需求会发生摧毁性的变化，每次都会涉及一次数据库的迁移和业务逻辑的重写。

    * 做一次数据库迁移要考虑历史上所有可能发生的情况；何况数据库里已经有很多不一致，很难写出一条规则来迁移。

    * 还要冒着迁移完了以后这个数据库就坏掉的风险。

    * 在测试环境做一次迁移，和把一所学校里的所有数据都做一次迁移，难度完全不一样。

    * 代码可以重写，但历史消失了吗——它只是一个 database 的 transaction，update 完就彻底挪到了新的状态。

* **手艺活**

    * 到目前为止，软件的设计、实现，ERP 这类系统的设计、实现、维护都是手艺活。

    * 例子：某公司 2000 年成立，唯一的选择是参考一个已有的企业架构来做教务系统，抢占教育市场的第一桶金，做出来就是一个 CRUD 系统。

    * 一旦背上这个技术债，就要在中国大学教育改革这几十年的时间里，不断地扛下所有。

* **研究生院那二十万**

    * 读 PhD 时软工组隔壁的软件工程组接了学校研究生院教务系统的订单，大概二三十万；看起来是大订单，实际上在定制化软件里是比较小的订单，因为要不停地维护。

    * 那个系统是非常典型的 CRUD 架构，室友的技术是够的，但作者一直喷他"最后会面临各种各样的问题"。

    * 果然：研究生发生巨大的扩招，管理上多了很多研究生类型、培养类型，研究生压力大、经常有调整——这些在做需求设计时都是始料未及的。

    * 最后系统彻底变成屎山，然后就不存在了，现在统一变成公司维护的系统；他们还是有领域知识，知道这些系统应该怎么把屎山扶起来。

* **重做的出发点**

    * single point of truth 太危险了：一旦有任何不一致，你都不知道应该怎么样把它拿出来。

    * 于是想到数据结构——课上讲过一种可以保留所有历史的数据结构。

## event sourcing

* **persistent data structure（持久化数据结构）**

    * > **定义**：可以保留这个数据结构所有历史的一种数据结构。

    * 实现方式：存一棵树；一开始只有一个节点，有节点以后值不变就把这个节点放过来，到有一天值变了，就在根的路径上长出一个新节点，它的左子树可以指向原来的节点；这个数无论多大其实都是可以存下来的。

    * 存这个结构的日志，就是一个 write-ahead 的 journal；存它们的 delta，就是 Git、SVN 这样版本管理里面的思想；存当前状态，就是经典的 CRUD。

* **三种等价视图**

    | 视图 | 存的是什么 | 怎么拿回当前的状态 |
    | :--- | :--- | :--- |
    | 状态 | 当前这一个快照 | 不用回放 |
    | 操作 | 事件的日志（WAL / journal） | 从头 replay |
    | 增量 | 状态之间的 delta（Git / SVN 的版本管理） | 从旧版本一路 apply |

    * 这三种视图是等价的，都可以帮你回放历史、得到当前的状态。

    * 结论：想要设计一个更好的架构，最好是先把干的所有的事情都先记下来。

* **event sourcing（事件溯源）**

    * > **定义**：从历史事件生成状态，而不是直接维护这个 CRUD 的状态。

    * 想法很简单，但由此你发明了一个非常经典的设计模式。

* **复学的例子**

    * 之前没有"复学"这个操作时，只能把张三从这个数据库里抹掉；他的一些记录就删掉了，要把这些和他、其他部分的关联重新建起来，你得付很大的代价。

    * 有了"复学"这个操作（他又有 token 了），如果用记录所有操作的方式，就能通过 replay 知道张三复学前的状态，再把这个状态拿过来——他没有丢。

    * > **注意**：你的逻辑是不能减少的——即便使用记录日志、记录历史的方式，"复学"这件事之前没有考虑过，你依然是要为他写一个逻辑。

* **事实不可篡改**

    * 世界上所有东西都是对事实的投影，而事实是不可篡改的。

    * 有了这个你好像就有底气了，不怕错了：做错了可以很快回到过去的一个快照，再来修复逻辑——你不会在做数据库迁移的时候手在抖。

      ```text
       事件流（事实，不可篡改）
       ─────────────────────────────────────────────
       E1 入学  ─►  E2 退学  ─►  E3 复学  ─►  E4 结业
            │           │           │            │
            ▼           ▼           ▼            ▼
           S1          S2          S3           S4
       当前状态 = 把相关事件 replay 一遍

       院系调整也是一个事件：E0 计算机系 → E₀ 计算机学院
       「2011 年毕业」= 只 replay 到 2011 年那一刻的事实
      ```

* **院系调整也是事件**

    * 在某一个时刻发生一个事件叫"院系调整"，查询一个过去的人会查询到他过去的版本，并且你知道他经历了这个。

    * 查询他毕业时候发生的事情，直接查他毕业时候的那个状态；想要他比较新的信息，可以投影出和这个人相关的历史：这个同学 2007 年入学、2011 年毕业，到这都是计算机系，计算机系在 2014 年改为了计算机学院。

    * 总是可以裁出一个和事实相关的历史，然后把它 replay 得到我现在要的状态——既可以查询过去，也可以查询现在。

* **代价**

    * 会有性能问题，因为要大量地 replay；但这不是很大的问题，总可以用快照缓存等优化技巧。

    * 你已经在屎山上，把它变成一个 event sourcing 的设计就会变得很困难；而如果从一开始就做 event sourcing 的设计，很多事情、很多问题都不会发生。

* **相邻概念**

    * CQRS（Command Query Responsibility Segregation，命令查询职责分离）——它和 event sourcing 是独立的。

    * Domain Driven Design（DDD，领域驱动设计）。

    * 其实你都不需要先学过这些；只要回到最初的 first principle——设计一个五十万行的教务系统时跳出这个问题，看到根源在哪里，就能做正确的架构设计，哪怕你没听说过这些名词。
