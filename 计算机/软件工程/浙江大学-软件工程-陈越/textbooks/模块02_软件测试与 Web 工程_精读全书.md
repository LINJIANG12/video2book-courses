## 软件测试：策略、方法与用例设计
> 对应块：BLK05 | 覆盖分集：P17-P20

你们的 design 还没通过最后的验收，可是现在就得开始动手写 testing plan 了。为什么？因为测试是软件工程里非常重要的一个环节，所以我们专门分两次课讲：先讲战略，从整体上看测试策略大体是什么样子、要分哪几块、你是自顶向下测还是自底向上测、有哪几种类型的测试；再讲战术，也就是在每个具体的测试阶段，你到底该用什么技术。先看大的，再看细节。

在讲策略之前，先看几个历史上的真实事故——它们都是测试不完备造成的。

### 两个流血的事故

1963 年，美国人向火星发射了一颗火箭，结果挂掉了，损失一千万美元。你每次看到这种新闻，先看那个绿色的数字——这是 1963 年的一千万美元。错在哪儿？就错在 Fortran 程序里一个字符敲错了。

那一句是 Fortran 里相当于 C 的 for 循环。用 C 写就是：

```c
for (i = 1; i <= 3; i++)
```

Fortran 的写法不一样，它在行首有一块标号区域，可以用标号表示循环体到哪一行结束。原来那句类似 `DO 5 I = 1, 3`，最后那个 `5` 标的就是循环体结束的位置。据说程序员写好之后复印了一份交给另一个人敲进去，复印过程中那个逗号糊掉了，看上去像一个点，于是被敲成了 `I = 1.3`——循环语句变成了一句赋值。更糟的是，当年的 Fortran 编译器诊断不出来，不报错，程序照跑，一千万美元就这么没了。

> **提示**：`DO 5 I = 1, 3` 里的 `5` 是循环体结束行的标号，逗号用来分隔循环的起止值；一旦逗号被误读成小数点，整条语句就不再是循环，而是一个把 1.3 赋给 `I` 的赋值语句。这就是最典型的"少测了一个地方"。

第二个例子，那次飞机坠毁：全机只有 4 个人活下来，163 减 4，159 个人没了。事故是怎么回事？飞机装了自动导航系统，可那位机长以前没有导航系统时，靠的是纸质地图。地图上 Cali 这个城市有它对应的字母代号，他熟得不能再熟，于是直接把这个字母敲了进去。可在这套自动导航系统里，这个字母对应的不是 Cali，而是 Bogota，而且方向正好相反。敲完之后，飞机直接撞到山上了。

地面导航也有责任。事后调黑匣子能听出来，地面发现他方向不对——怎么往反方向飞？可地面没有直接了当地告诉他"你飞错方向了"，而是用了一句比较幽默的话："我建议你以比较直接的方式飞向你的目的地。"机组没听懂，等听懂的时候山已经在眼前了。

这两件事的教训是什么？民航系统后来建议所有飞行员不能完全相信 computer，不能完全相信自动导航，还得靠自己的飞行经验判断方向。而地面人员提醒了半天人家没听懂，也有不可推卸的责任。更要命的是，这个软件本身没坏——是**测试的人**漏了一样东西：一致性测试（consistency）。设计软件时我们强调要分析用户的 profile：他的背景、受教育程度、习惯用的东西。像自动导航这种系统，你当然要分析飞行员在没用你这套系统时是怎么工作的，你设计的那套字符必须跟他以前用的 charts 一致，才不会出错。人家默认的心态是"我原来看着纸质地图，现在只不过多了个键盘让我按一下，那我原来怎么按现在还怎么按"。你让他专门再记一套，他很可能记错。这个问题本该由测试人员提出来：设计时没考虑到，测试时也没去想，整个一致性就这样被放过去了。所以测试有很多东西要测。

### 测试的目的：为了找错，不是为了证明没错

第一个问题：What is testing for？我们测试的根本目的是什么？——为了发现问题。

> **结论**：我们测试不是为了证明软件是对的，而是为了发现错误（for finding errors）。

别以为这是一句废话。我们教数据结构时就让大家写过 project report，里面专门有一节写测试。作为第一次做测试的小朋友，很多人当年写的测试现在回头看看实在看不过去：只写了几个特别简单的 case，证明这几个 case 都过了，就说程序是对的。这就是立场站错了。你要站在程序员的对立面，不是站在他同一阵营；你要做的是想方设法去破坏它。如果你用尽所有办法都不能破坏它，那才是对它最大的帮助。公司里给测试员的奖金，是"你找到更多错误我给更多奖金"，而不是"你测完证明程序是对的、我保护了它"给你奖金。你什么都没测出来，可能只是测试太弱，并不能说明它没有错。

> **易错点**：测试团队的立场只有一个——finding errors，不是为了 protect the programmer。

那测试团队最后要交出什么？

- 首先要有一份 **bug 清单**，这跑不掉。
- 然后是 **test cases**。就像我们要求大家在数据结构报告里列的那张表：一栏列所有 test case，一栏 expected output，一栏 the actual output，再加一栏 status——不符就是 bug，再看它是 corrected、pending 还是什么状态。
- 一份对 program 质量的**评估**，也就是要设计一个评估指标。这个指标不只是跟 bug 数量有关，还要跟需求对一下：很可能每一个功能都是对的，合在一起却不是你要的那个软件。你要检查最终做出来的是不是 requirement 里描述的那个软件。
- 如果有安全性、performance（效率）方面的要求，这些指标也要一个一个对。
- 最后给出一个 overall 的 **indicator**，总体评价这个被测软件的质量如何。

也就是说，你的 test plan 里要把"打算怎么测"这些都准备好。

### 测试从什么时候开始，由谁来做

真正执行测试是从 component 开始的。component 做完以后，写它的人自己肯定要做 unit testing，测完交上来，然后从 component level 走向 integration，再走向整个 system，一点一点完成。测试是从小到大进行的。

在不同的时间点，你采用的测试技术不一样——这是下一次课的内容。这里先给个大概：unit testing 时一般用白盒测试，到了 integration、system testing 就用黑盒测试。什么是白盒、什么是黑盒、白盒要细到什么程度、有哪几种逻辑覆盖，下次课讲。

什么人来做测试？至少两种人。写程序的人自己肯定要参与；最好还有独立的、不写你这个程序的测试人员来帮你一起测。为什么？后面再说。

#### 测试与调试

先提醒一件事：testing 和 debugging 不是一回事。

| 活动 | 回答的问题 | 做什么 |
| :--- | :--- | :--- |
| Testing | 哪里有错？ | 发现错误，出一份报告指出某处错了 |
| Debugging | 怎么改？ | 把错误改过来 |

一个是测试，一个是调试。测试只负责发现哪里有错；debugging 想办法把错误改过来。这是两种不一样的 strategy，后面分别介绍。

#### Verification 与 Validation

测试团队要做两件事：verification 和 validation。查字典会发现这两个词好像都翻译成"验证"，其实有微妙的不同，中文一般译作"验证"与"确认"。

| 概念 | 回答的问题 | 检查什么 |
| :--- | :--- | :--- |
| Verification | Are we building the product right? | 每个模块是不是都在以正确的方式实现它号称的功能 |
| Validation | Are we building the right product? | 一堆正确的功能放一起，是不是我真正要的那个软件 |

Verification 检查每个模块功能的正确性；validation 检查各功能合起来是不是你要的软件。我用一幅漫画打过比方：一个人画一张人脸，眉毛、眼睛、鼻子、嘴单独看，每一个器官都是美人的形状，可放在一起就不是一张人脸——因为位置全放错了。把它遮住其他部分单看，每个器官都很漂亮。

```text
              每个模块的功能都对（verification）
                        |
                        v
          合起来是不是需求要的那张"脸"（validation）
```

读图：verification 逐块检查"画的每个器官是不是都漂亮"，validation 检查"放到一起是不是一张人脸"。这是 SQA 团队最关注的两个环节。

这里要澄清一个观点：**software testing is only one element of SQA**。SQA 是 Software Quality Assurance（软件质量保证），公司里要专门有一拨人做这件事。你不能把最后软件质量的责任全推到 testing team 身上。

> **结论**：Quality must be built into the development process；one cannot use testing to add quality after the fact.

整个软件的质量取决于开发过程的管理与执行有多严格。如果每个管理环节都没有质量监控，就指望最后一关 testing team 全包，质量一塌糊涂还都怪到测试头上——那不公平。管理流程本身不符合质量保证的要求，从一开始就注定了这个软件的质量高不了；已经做成烂样子，再指望最后全靠测试团队解决是不现实的。

#### 测试团队该由谁组成

有两类人。

一类是交给 developer，也就是写程序的人自己测。好处是程序是他自己写的，他对内部结构特别清楚，不用花很多时间理解程序，能很快针对性地设计出 test case 直接测。

| 方案 | 好处 | 问题 |
| :--- | :--- | :--- |
| Developer 自测 | 熟悉内部结构，上手快、成本低 | 有心理盲点；受利益驱动（怕过 deadline 被罚、奖金没了），不会严格测自己 |
| 独立测试组 ITG | 与开发方利益对立，会全力抓 bug | 要花更多时间，意味着更多成本 |

开发者的毛病在于：大家多多少少有点骄傲——"我的程序没调好不会交出去，既然上交了肯定是没问题的"，再让他做 formal test 就觉得"怎么会有问题呢"。而且一旦测试不过要改，改不及过了 deadline 要挨罚，利益驱使下他不太会严格地测自己的东西。还有一个更显然的问题：**每个人都有盲点**。你自己死都看不出来的东西，换一个人看就特别容易。

我们组就有个同学信心满满地说要重构，"砰"一下就跳进坑里，重构完当然一堆 bug，自己痛苦地查了半天查不出来，最后都要放弃，说想放一个礼拜假干点别的。我出的主意是找另外一个人，两个人 pair programming 坐到一起查。为什么强调坐在一起，而不是直接把程序丢给另一个人？因为后者得从头学这个系统的架构，要花相当多时间先看懂再查错。坐在一起，写的人当场讲我这是在干什么，两个人一起往下看。一周下来两个人都很兴奋，收获大大的，各种错误都找出来了——换一个人看，感觉完全不一样。两个人各自有盲点，但盲点重合在同一点上的可能性比较小。

所以给你的建议是：代码卡在什么地方，找一个好朋友请人家吃顿饭，一起看，什么都能看出来。

公司里让独立的测试组（ITG）来做测试，缺点是费时间、费钱，要付人家这段时间的工资；但因为独立，两边利益有点对立，测试的按抓到多少 bug 拿奖金，就会全力以赴抓尽可能多的 bug，从质量保证的角度看效果会更好。

#### 三个要避免的误区

- **不要说 developer 就完全不该碰 testing**。不对。起码前期的 unit testing 和初期的 integration，developer 都要参与。这里有一个过渡：integration 阶段 ITG 进来，两方密切合作；到后面 system testing，independent testing group 才慢慢把事接过去。
- **不要以为软件可以 tossed over the wall**。很形象——我把东西写完、submit、丢过墙就不管了，那不行。最起码人家发现错误还得你来改。一般不是 testing team 来做 debugging 的，改错终究是开发方的事。
- **不要以为测试组在轮到测试之前就闲着**。你代码还没写出来，测试组就没事干？当然不是。理论上来讲你们的 design 还没验收，代码应该还没开始，但 test plan 今天回去就可以做。事实上 testing team 要从 analysis 阶段就在旁边看着，了解软件整个成型过程，才能充分了解它最薄弱的、最容易出错的环节在哪里。拿到 design，就可以针对它开始做测试计划：我要测哪几个环节、重点测哪些部分。这些都事先就能做。

> **提示**：需求有了以后，黑盒测试的策略基本就能定下来；设计有了以后，部分白盒测试的策略也能出来。所以 test plan 和设计几乎是同步进行的。

### 传统架构的测试策略：四步走

对传统的结构化软件架构，测试大体分四步：

1. **Unit testing**：一个 component 一个 component 地测。前面讲过任务拆解，基本上一个 component 属于一个 team，team 内部去做 unit testing。每个 component 下面又分很多小 component，一个一个测。
2. **Integration testing**：把它们一点一点集成起来，每集成一步做一次 verification——集成进来的这块功能是不是还正确。
3. **Validation testing**：所有东西都做好后，照着需求规格说明书里那份非常重要的 validation criteria 来验收。当初写需求时就要写清楚：验收时达到这些标准我就给钱。功能、性能，其他标准一条条列出来，然后照着测。
4. **System testing**：安装调试，把它装到要用它的那个大环境、大系统下面，做一个整体的 system testing。

### 什么时候才算测完

对传统和 OO 两种思路，最后都落在同一个问题上：**When are we done？** 什么时候测试是个头，可以宣布不测了、可以交了？

理想主义的回答是 never。对一个足够复杂的软件系统，穷尽测试不可能，既然不能穷尽，你就永远不敢说软件里没有 bug。大家都明白这个道理，可具体到自己的东西上就变了——"你这个东西得给我一个备份，万一坏了怎么办""不会坏的"。程序员都是这样，越牛的程序员越这样。这其实是很不成熟的表现：你不可能做过完备的测试，凭什么说这句话？源于强大的自信罢了，你只能说"希望这个 bug 在有生之年别出现"。

从实际角度讲：**when you run out of time, or you run out of money**。没时间、没钱了，也就不测了，交出去大家先用着。

> **结论**：testing 只是发现错误的过程，你永远不能证明这个软件没有错误；即使一个错误都没测出来，也不能说明它没有错误，只能说可能你的测试太弱了（当然也可能是程序质量确实不错）。

### 策略层面要盯住的几件事

#### 用可量化的方式说清楚需求

设计测试时，要尽可能用可量化的方式（in a quantifiable manner）来描述。也就是说，需求规格说明书里那份 validation criteria 要尽量量化，最后都设计成一系列指标：达到这个指标就怎样。

测试过程本身也要有一个量化的过程。这里有一个讨论题：老板想知道测试进行到什么程度了，有的公司在 report 里说"我们目前已经找到了 90% 的 bug"。你不觉得好奇吗——这 90% 是怎么得到的？你既然不知道全部有多少 bug，凭什么算得出 90%？肯定是个毛估估的数据，可毛估估也得有根据，不能一拍脑袋说"我觉得测完 90% 了"。这 90% 到底用什么方法量化出来？答案绝对不唯一，你自己想，但得讲出道理：我打算怎么算、怎么获得数据、为什么这么算比较合理。

日本有一家公司的办法很好玩：根据以往经验设计 N 个错误，悄悄植入到软件里，丢给测试人员去测；每周看报上来的错误清单里，有多少是他植入的错误被找出来了。如果植入的错误都被找出来，就认为该查的都查得差不多了；所谓"90% 找出来"，指的是植入的错误 90% 被找到，于是他说测试完成了 90%。这办法当然成本相当高，也有风险——你植入的错误会不会很干净、对软件有什么影响，你其实未必有把握。总之这是一种方法，quantifiable manner 有很多很多种做法。

> **提示**：从公司做的第一个 project 开始，就要随时度量、收集这些数据，留给后面的项目用。

#### 把测试目标写明白，把用户画像画出来

做 testing 之前，一定要把 testing objectives 清楚明白地写进测试计划。比如要测可用性，那可用性包含哪几个功能、哪几方面；要测 performance，是哪几个点的效率、测到什么指标。每一个测试目标都要写清楚。

还要分析、了解你的用户，写清楚：Identify categories of users and develop a profile for each——用户群分几类，每一类的 profile 写出来。目的是测试时能模拟用户的习惯去用这个软件。前面那套飞机自动导航系统，如果认真做了这件事，就不会出那种悲剧。

顺带说一句"客户是上帝"这句话不是随便说的。我们看大家写的那些关于网站制作的小说，大多数同学都很厚道——出了需求没做到位的问题，就认栽，咬咬牙自己扛下来，还是按质量把东西做好；要真都这样做，市场就太好了，客户会很开心。也有个别组把责任推给客户、跟客户找茬，甚至歪曲事实把黑白颠倒过来——跟你的上帝打官司，后果就不止这一笔生意做不成，你业内的口碑都会成问题。需求这一环没做好，测试这一环也补不回来。

#### 快速迭代地把测试做起来

**test plan 最好采用 rapid cycle**，也就是快速、渐增、迭代式的测试流程，而不是一次性想测得特别完整才来总结。一般是一个功能加进来测一下，再一个功能加进来再测一下，很快地迭代。

同时希望开发团队把软件本身做得比较 robust：Build robust software that is designed to test itself。你没经历过蓝屏吧？——当年那个 Windows 动不动不知道按了哪儿就"砰"地蓝屏。如果软件本身就是动不动蓝屏的那种，测试根本没法往下测。所以设计系统时就要考虑各种异常，自己做异常处理，抛出比较有用的异常信息，让人知道我走到了哪条路、这条路走得对不对。

#### 用 formal review 当过滤器

在正式去测代码之前，先用 formal review 这种机制过滤一遍。formal review 的意思是我不是去运行你的代码，而是你给大家讲一下：这个程序打算怎么从上到下走、有几个分支怎么走，有一帮人在那儿听——实际上相当于有一帮人在帮你做抽象的 testing。它可以过滤掉大部分关键错误。过完这一关，大面上都对了，剩下的就是实现细节的问题了。

再往下，要 conduct formal technical review to assess test strategy and test cases：你打算怎么测、你设计的每个 test case——每个 test case 都要有一个测试目的，要测哪一块。这些也要有一个 formal technical review 的环节帮大家检查一下，后面的工作会更有效率。

#### 不断积累，不断改进

最后是 develop a continuous improvement approach for testing process：不断积累经验，随时采集数据、积累数据，使以后做其它 project 时测试越来越有效、越来越好。

### 单元测试：driver 与 stub

对传统软件工程来说，第一步是 unit testing。做法是：给它一个 module——这是要测的对象；你设计好一堆 test cases 喂进去；它给你列出一份 bug 清单（results）。

test cases 要覆盖哪些方面？后面细讲，先说大概：测 interface、data structures、boundary conditions（边界条件）、independent paths、error handling paths，这些是下一次课的具体内容。针对这些设计好 case，再去做这一个 module 的测试。

在 unit testing 这里有两处要花工作量，要写两种东西。

一是 **driver**（驱动）。它有点像 Online Judge 软件——你去做 ZOJ、PAT 的时候，Judge 软件就是一个 driver，你写的东西就是一个 module，solution 交上去由它让程序跑起来。更准确地说，像我那门数值分析课，你只交里面一个函数，main 函数是我写的，那个 main 就是真正的 driver：因为你要测的是那个函数的功能，我得写一个能把它运行起来的东西。

driver 要做的事情是：接收所有 test cases，调用这个 module，把它产生的结果打出来，检查有没有问题。通常 driver 的模板是这样的：

```text
driver 的骨架：
  读入 input
  循环：
      读进一个 test case
      调用被测 module
      得到 result
      输出 result
  检查 result 是否符合预期
```

读图：driver 负责把 test case 一个个喂给被测模块，再把结果打出来比对。

但有时候没那么简单。driver 调用这个 module 时，发现 module 里面还调了一个 sub-module。那如果结果错了，你不知道到底是谁错了——是你要测的这个模块错了，还是它下面调用的模块错了？要让错误清清楚楚地归属到这个 module 而不是它的 sub-module，你还需要写另一个东西：**stub**（存根）。

stub 是一个**假的 sub-module**：它的接口跟真正的 sub-module 一样，但内容是假的、是个空壳子。做法是——你传进来一个参数，先把它打出来看（确认我调用它时传进去的参数是对的）；然后写一个类似 switch-case 的结构，不进行任何真实计算，只做判断：输入的是哪个 case，就直接返回那个"正确的值"。因为你事先知道有哪些 test case，也知道对于这些 case，sub-module 正确执行时该返回什么。这样一来，module 里调用的所有 sub-module 都没有产生任何错误、返回的都是正确值；如果 driver 最后输出的结果还不对，那只能是这个 module 自己的问题。

```text
        driver              <- 读入 test case、比对结果
          |
          v
     +-------------+
     |  被测 module |     <- 真正要测的东西
     +-------------+
        |       |
        v       v
     stub A   stub B        <- 假子模块：接口一致，按 case 直接返回预设的正确值
```

读图：driver 在上面喂数据、收结果，stub 在下面把子模块"替换"成永远返回正确值的空壳，从而把错误来源隔离在被测模块本身。

这其实是个不小的工作量。一个模块比较复杂、调用很多底层模块时，每个底层模块都要写一个相应的 stub，针对每一个 test case 返回它正确的值。所以你的策略——是自底向上测还是自顶向下测——都各有工作量：一种是你要写很多 stub，一种是你要写很多 driver。

### 集成测试：为什么"一把合起来"必翻车

到了 integration testing，有一种策略叫 **big-bang testing**：每个模块分头测好，最后"啪"一下全合到一起。我们这门课最后有点像 big-bang——大家提交的 Version 1、Version 2 是每组分别验收都对，到期末考完 72 小时之内，你们得把几个组合成一个系统给我测。那个当然是我最后的验收测试；至于你们几个组内部要怎么测，你们自己定。

你觉得 big-bang testing 好用吗？真敢这么干，肯定要悲剧。它造成的局面英文叫 **chaos**（别念成"靠死"）——一团混乱。为什么乱？因为最后啪一下合到一起，发现整个系统运行不正常，你不知道是谁的错，好几拨人的工作混在一起，大家开始互相 finger-pointing："这肯定是他的，显然是他的，一定不是我的，我都测过了。"每个人都觉得自己那部分没问题。

很多年前我留数据结构 project，让三个人各负责一个功能模块，最后合起来，能合成的小组打分起点高一点。有几个组胆子很大去挑战了，凡是去 challenge 的，没有一个合成成功。那个 project 其实就是一个最小生成树：要用到最小堆（每次拿最便宜的边）、并查集（判断新加的边会不会成环），还要维护图的结构，最后输出整棵最小生成树。三个人分工，每个人号称自己这块是好的，凑成一个程序时各种乱七八糟，最后一分钟还搞不定。所以你就知道，integration testing 其实是件非常讨厌的事情。

它最大的问题是 **isolation of causes is complicated**——你不知道到底是谁的错。改进的典型策略有两种。

| 策略 | 先测什么 | 要写什么 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- | :--- |
| Top-down | 最顶层的控制模块 | 很多 stub | 主要的 control/decision point 最早被测到 | 往上流的数据一直是假的，真实的底层数据复杂，可能到最后才发现 |
| Bottom-up | 底层模块 | 很多 driver | 从下往上流的都是真实数据，不用写 stub | 最关键的顶层控制模块最后才测，万一错，下面全白干 |

**Top-down**：从最顶端那个控制模块先测，先写两个 stub 返回一下，再用真实模块替换掉 stub，一层一层往下替，直到测到底层。它的好处是主要的 control、decision point 最早测到——领导的方向要是错了，底下员工再努力也没用，越努力错得越厉害，所以大方向先测对。缺点是下面流上来的数据一直是假的，真实的底层数据可能比你想象的复杂得多，别到最后一天才发现。

**Bottom-up**：先把底层测了。把底层模块分成堆，逐个测好（每个都要写 driver），再用真实模块替换 driver，继续写上层的 driver，一层层往上走，最后测顶端。它的优缺点跟 top-down 正好相反：往上传的都是真实数据，不用写 stub；但最重要的顶层控制模块最后才测到，万一它错了，下面全白干。

```text
top-down：先测顶层，往下用真实模块替 stub      bottom-up：先测底层，往上用真实模块替 driver
        M1 (先测)                                     M1 (最后测)
       /        \                                    /        \
    M2(stub)   M3(stub)                          M2(driver)  M3(driver)
                                            M4 M5 一组，M6 M7 一组 (先测)
```

读图：两种策略方向相反，测的顺序互为镜像，谁先谁后决定了你要写多少 stub、多少 driver。

> **提示**：实际测试很少极端到只用 top-down 或只用 bottom-up，一般综合着用。还有一种叫 **sandwich testing**（三明治测试，夹心面包）：一部分人从上往下测，一部分人从下往上测，在中间某一层汇合。

#### 回归测试

还有一个很重要的 **regression testing**（回归测试）。它基本发生在：已经测过一遍，发现 bug 改了之后，不能只测改动的那一块，还要考虑改动可能影响哪些模块，把以前虽然 pass 过的相关 case 再重复执行一遍。注意——不是把以前所有 case 都重跑（那太费钱费时间），而是挑一些比较重要、比较相关的重新测一遍。

回归测试没做好会出事。曾经有个电话局的系统升级，升级后没做回归测试，结果区号搞错了。美国的电话按州分区号，像杭州是 0571 开头，每个州有区号；但有的州很大，比如加州，一个州内有几个不同区号。通常从一个区号打到另一个区号算长途电话，会被转给长途电话公司，长途和 local 是两个不同部门、出不同的账单。可如果你在加州以内，虽然区号不同，也应该算 local。这次升级是给 local company 做的，结果把这件事搞错了：本来加州以内的 local 电话，变成了长途的账单。客户去找 local 电话局 complain，local 说是长途搞错了、该找长途公司；长途查半天说不是我们的错，是 local 的错。客户被两种公司踢皮球，感觉非常差。问题就在于升级后回归测试该测完的没测完——你不可能做完全的回归测试，但比较重要的那部分没做，就出了这样的问题。

当年美国几家长途电话公司（AT&T、Sprint 等至少三家）互相抢着降价，后来不光降价还贴钱，你这个月转到我这儿我送你多少钱，打到几败俱伤，最后财力最雄厚的那家站住，另外两家被灭，客户就开始倒霉——打仗时到处占便宜，只剩一家老大时就任他宰割。

#### 冒烟测试

传统软件里还有一个 **smoke testing**（冒烟测试）。为什么叫冒烟？名字来自硬件测试：我有一块板子，做好一个零件往上一插——插进来没事、都好的，那这个零件是好的；如果一插进来"砰"一下板子冒烟了、短路炸了，就说明很大可能是你新插进来的这个零件是坏的。这就叫冒烟测试。

放到软件测试里，"板子"就是一个 **build**——一个已经测过的东西的集合，包括源代码、数据库等等相关的、所有测过的部分放在一起。然后每天往里面插不同的 component：加一个 component 全跑一遍，再加一个再全跑一遍。如果哪个 component 加进去后跑不通，通常就是它有问题。每天把不同的 build 都测好，再集成一下、再测一遍。

这里的策略是：**build 不能太大**。你要把整个软件当成一个 build，每天测一下就很费劲；所以要巧妙地划分 build 到合适的 size，每天往里头插一个、插一个。这种策略通常用在 time-critical 的项目上——事情要得特别急，得迅速测一些东西。

#### 测试判据

一般的 test criteria 有这么几类：考虑 **interface integrity**（接口完整性），要有一类测试专门测接口；有一类测试测功能的正确性；还要测 local、global data structure 定义得对不对；当然还需要测 performance。书上用两页内容给了怎么写 test specification 的建议——也就是你们下一次要交的那份 report，仔细去看。

### 面向对象：好写，难测

OO（object-oriented）的方法刚推出来时非常时髦，大家都说特别好、什么都好——不可能什么都好，肯定有弱点。最麻烦的地方就在于：**测起来很麻烦**。

OO 的理想是让软件容易理解：按普通人的观点，世界就是由一个个对象互相作用在运转，于是系统也理解成一个个对象互相作用。可你要怎么测才能把所有关系测清楚、保证它运转正确？它不是一个结构化的东西，测起来非常痛苦。大面上它也分 Unit、Integration、System 几类；其中 Integration 尤其复杂——你要把 class 与 class 之间的关系尽可能覆盖清楚，如果用全排列做完全测试，试它全部的组合，你会测死，根本测不完。要在有限时间精力下测到主要东西，需要技巧。

#### 单元测试测的是一个 class

Unit testing 里，unit 相当于一个 class，但 class testing 跟普通 unit testing 不同。普通的一个 unit 基本上就完成一个功能，是一个功能模块，测它功能对不对就行。可一个 class 不止一个功能，它是一个对象，这个对象干好多事情。你不太可能把一个功能一个功能单独拎出来测——即使每个功能单独都正确，也不代表这个 class 的实现就正确。一个 class 相当于一个小软件，所以你要测的不仅是它的 operations，还要根据它的 **state behavior** 去测。

还记得我们讲 state transition diagram 时说过有两种，一种大的、一种小的吗？大的讲整个系统在运行中处于哪几个状态、怎么转换；小的针对每一个 class——一个 object 在系统运行中哪几个不同状态、由哪几个动作触发状态迁移。这些就是你要测的点，而不仅仅测功能算法是否正确。它是基于 state behavior 来测的，不是基于数据流图。

#### 集成测试的三种策略

为了尽可能测全面，书里建议了三大类策略。

- **Thread-based testing**（基于线索）：给一个输入，系统里各个对象开始互相协作、做一系列动作，最后完成一个任务、给出一个输出。从输入到输出，加上中间这一系列动作，就是一条线索（thread）。要测的就是这条线索执行过程中每一个 class、每一个 object 的表现是不是都对。一条线一条线测过来——其实这就是 use case，一个 use case 一个 use case 地测。
- **Use-based testing**：有点像传统的自底向上。先找一些比较独立、不太用到别人、做自己事、被别人调用的 class，把它们先测好；再去测用它的那些 class，一圈一圈往外扩。传统架构是层次往上走，OO 不是这种结构，它是乱七八糟的一张图、互相调用，所以更复杂——但这也是一种策略。
- **Cluster testing**：还记得 CRC cards 吗？它最重要的是第二个 C——collaborators。一张 CRC card 描述一个 class，还描述了跟它相关的 class 有哪些。于是一拎就拎起一串：你抓一张卡片，它链接到其它卡片，把所有相关的全抓出来，抓出一坨，这就是一个 cluster。然后论墩测，一堆一堆地测，把它们之间的 collaboration 都测清楚。

#### 验收测试：alpha 与 beta

Validation testing 要看需求规格说明里最后的 validation criteria，用到里面的 use case、behavior（state）、event flow diagram 来跑一遍；还要检查 configuration——文档、数据库等各种东西是不是都配齐。这里有两种测试：

- **Alpha testing**：把 TA 叫到你那儿，但不许他碰你的机器，他在后面看着，你操作软件给他看——这功能这么用、那功能那么用，做一遍，然后问他可不可以。
- **Beta testing**：你靠边站，TA 坐下来自己用这个软件，你在后面看着，不能说"抓住他的手，这里不能乱动"。他想怎么动就怎么动。就像推出一个游戏的 beta 版放到网上，你还能管得住玩家？

当然，一定要有一个文档人员在旁边记录 **deficiency list**（错误清单）。

#### 系统测试：从恢复到压力

System testing 分这么几种，多数跟 OO 无关，是通用的：

- **Recovery testing**：95 年我们学校主办 ACM-ICPC 亚洲区赛时，比赛前很重要的一项就是 recovery testing——要想到比赛中间系统崩溃了怎么办。得有备用系统，崩溃时立刻切换过去，还要保证不丢任何东西，原来的 submission 全部都在，立刻迁移到备用系统让大家继续比赛。当时我们的场地主裁判亲自做了一个备用系统。怎么测？现场一百多台机器，每台装一个机器人，一声令下所有志愿者启动机器人疯狂提交，系统一下被冲垮、服务器挂了；挂了就马上启动备用系统、迁移数据，看恢复程度如何。结果一直弄到快半夜 12 点才搞定——他的系统在自己笔记本上一点问题都没有，放到赛场服务器就不对。最后的错误在于服务器上装的 Linux 版本跟他笔记本上的就差了一点点，差那么一点就死都不对。这就是 recovery testing：先让它垮掉，再让它恢复，看恢复得怎么样。
- **Security testing**：比较好理解，试各种黑客攻击，看你的防御能力。
- **Stress testing**：通常跟 recovery testing 合在一起做，回答"这个系统到底能承受多大的冲击量"——所有机器人一起攻的时候，看到什么程度服务器就挂了。也就意味着比赛中间要设一个门槛，比如一秒钟之内不能提交超过多少次，这个数要根据 stress testing 的数据算出来，做事先防范。
- **Performance testing**：测效率，比较好理解。

最后建议：测试过程中如果找到规律，可以抽象出一些 **testing patterns**，以后可以 reuse。

> **结论**：testing never ends。即使活儿交出去了，测试也没完——只不过从你手里交到了客户手里，他会继续替你测。

### 面向对象的测试用例设计

OO 对 testing 是个很大的麻烦。它的 test case design 跟传统的是两个概念。

传统的 test case，一个 case 就是一套输入，有一个测试目的、对着一个输出，仅此而已。可对 OO 来说，我设计的不是一个 case，而是**一套动作**：一个 test case 不是一组数据的输入，而是一组动作的执行过程。所以一个 OO 的 test case 包括：

- 一个名字、一个单独的 ID；
- 写清楚它要测哪个 class（把 class 名字写上）；
- 写清楚测试目的是什么；
- 最关键的是 a list of testing steps——测试的步骤。

对每一个 case，你要测的是：这个 class 有哪几个状态、是不是都测到了；在测状态的过程中，哪些 message、接口、操作（operations/methods）被执行到；执行过程中要做哪些步骤；测试的外部准备条件是什么；如果还要用到其它 class，那些 class 该怎么配合。这是很复杂的事情。

> **结论**：Unlike conventional test case design which is driven by an IPO view of software or the algorithm detail of individual modules，OO testing focuses on designing appropriate sequences of operations to exercise the states of a class.

传统测试把软件看成 input-process-output，给一个 input、检查 output，就知道 process 对不对。OO 不同：它测的是一个 class，定义的是一系列动作，这些动作要 cover 这个 class 所处的不同状态——对测试的理解完全是另一个角度，一个 test case 因此非常复杂。

有几种测试方法：

- **Fault-based testing**：公司里很有经验的老测试员会有这么一套做好的 test case——不管什么东西拿过来闭着眼睛执行一遍，如果这套都过了，绝大多数问题就没了。它其实是先想"软件最常出错的地方都有哪些"，针对这些错误设计 test case，过一遍就说明这方面的错误肯定没了。
- **Class testing 与 class hierarchy**：这是最让人痛苦的地方。OO 程序一般都有 inheritance（继承），编程时可以非常容易地扩展、裁剪、修改，好处很多；测的时候你就惨了。你以为测完父类，子类里父类的功能就不用测了吗？不是，它会变的。你以为把子类都测完，父类就不用测了吗？也不是。你其实省不了事。**编程时给你省的事，测试时只会让你变得更复杂。**
- **Scenario-based**：把 use case 拿出来，一个 use case 一个 use case 地走一遍。它关注的不是软件内部执行过程，而是用户的使用过程——要保证用户使用过程正常（使用过程正常，内部逻辑仍可能是错的）。不同角度，最好结合着用。
- **Random testing**：class level 太复杂时的一种办法。首先要定一个最小的测试集合，最低限度把这些 cover 了；剩下的分支、扩展就 random combination，瞎猫抓死耗子乱碰一下——不太好。
- **分类测试**：最好做事有点规律。它跟传统软件工程里的 equivalence partition 道理一样，只不过等价类怎么定义没那么容易看。等价类可以是 **state-based**（哪些功能让这个 class 从一个 state 换到另一个 state，这一类功能放一起测）、**attribute-based**（哪些功能集中在改某个 attribute，跟某个 attribute 相关的操作放一类）、**category-based**（根据这个 class 要完成的几大功能，把相应操作绑在一起测）。
- **Inter-class testing**：class 之间的测试，更麻烦。你把 class 理解成 client 与 server 的关系——一个使用、一个被使用。先把几个 class 的关系划分成 client 和 server，然后它们之间交互的 message 和 operator 要测好，还有它们之间的 collaboration、相关的 collaborator class 也要做相应测试。基本也是基于 random 的，没有特别好的办法。
- **基于 state transition diagram**：如果 behavioral 非常清楚、state transition diagram 画得清楚，就可以基于它来设计 test case。图里画的是 state，箭头上画的是"做了什么动作导致变成这个状态"。你的 test case 就沿着线走：某个动作做一下、某个动作做一下；几个动作可以排列组合——比如什么都不做直接做下一个动作然后结束，这是一个 case；走到这儿做一个动作往下走结束，又是一个 case；两个组合做一下再往下走，又是另一个 case。**随时记住：OO 的 testing 不是一个 case，而是一组动作，一个 case 描述的就是一组动作。**

另外还有一些，比如 graphical user interface testing、client-server，还要测一下你的 help；如果是 real-time systems，performance 是非常重要的测试。

### 什么是好的测试用例

讲战术之前，先按这本书的习惯把审美观建立起来：What is a good test？什么样的测试才是好测试？

先说一个体会：出一道题，有一个 idea 是非常简单的事——编程、数据结构那么多知识点、那么多算法，拍脑袋就能想一个故事出来。出题花时间的地方在哪里？在 **test case 的设计**。难就难在那儿，最大的技术含量就在那一套 case 上。

那什么样的 case 算强、算好？它得**覆盖得比较全面**——你要测的那个模块应该有的性质、该测的点都要 cover 掉。像 PAT 系统很麻烦，它分 case 给分，每个 case 都要 run 一遍，run 的时候还开一块虚拟空间把你包起来以保证安全；所以如果你出好几十个 case，系统就挂掉了。这就引出另一个要求：**每个 case 要有充分的代表性，不能冗余**。

什么叫冗余？你说输入数据范围是 1 到 100 的整数，然后测了 n=5、n=10、n=18、n=86——有意思吗？我可以把 1 到 100 全测一遍，这叫完备测试，至少对输入来说测完备了，可为此设计 100 个 test case，系统就挂掉了，没有必要。

> **定义**：一个好的测试用例，首先要有很大的可能找到错误。一个 case 通过了一点用都没有、很多错误还被掩盖着，那这个 case 就不好。

就像竞赛题上印的 sample input/sample output，只是让你看清输入输出格式。国际竞赛题的 sample 给得特别少、特别"傻"——你过了这个 sample 什么都不表示，程序可能 80% 是错的照样能过；它只是说"你连 sample 都过不了就别提交了"。而 PAT 考试的 sample 是有技术含量的，一般能 cover 掉一半以上的测试点：sample 过了，你的程序起码有 60% 的可能是对的，剩下 40% 边边角角的点再用其它点测。

再看几条标准。

- **Good test is not redundant**（没有冗余）：在公司里工作，你分分钟老板都在付你工资，做很多没有意义的劳动，就等于老板的钱花在没有意义的事情上，这不能接受。
- **A good test should be best of breed**：这个词原意来自狗的全类比赛——各个品种里决出一个最好的，就是 best of breed。测试里同理：你不可能把 1 到 100 全测一遍，要选几个有代表性的、最好的。打个比方，给你一个很大的面包，告诉你"你只有时间咬一口"，你咬哪儿？肯定咬你最好吃、最想吃的那一口。测试很多时候就是这个样子：你有一个 deadline，只想花这么多时间、这么多精力、这么多人，但要测的东西非常多，所以得精打细算，想好测哪些、保证软件拿出去不至于太丢人，同时把预算控制在范围内，并尽可能多地发现错误。
- **Good test should be neither too simple nor too complex**：太简单是什么？最好一个 case 就为了检查一个错误而设计——如果这个 case 对了，说明程序里肯定没这个错误；如果错了，那一定是这个地方错。目标特别明确，debug 时就简单，一看错就知道是这里。可要是真做到"一个 case 只查一个问题"，你就要好多好多 case，要好多好多人执行，就不合算了。所以比较合算的是像 PAT 的 sample 那样，一个 case cover 50% 到 60% 的测试点，攻克掉它就说明那一堆东西基本都过。但也别走到另一个极端：一个 case cover 太多测试点，结果老也过不了；一发现错了，里面有十几种可能，到底哪里错？debug 就很困难，还得补其它 case 定位。所以好的 case 要适中。

设计 test case 时，脑子里要常记三件事：测试的目的是 **uncover errors**；希望设计得 **in a complete manner**，尽可能覆盖全面；约束是 **with a minimum of effort and time**，用最少的时间、人力、物力达到最好的效果。如果真能做完备测试，就没有技术含量了——全覆盖，不可能有 bug；可事实上大多数情况下做不到，所以才需要技术，设计 test case 才是一门很有意义的技术。

### 可测试性

软件设计出来以后，它的 **testability**（可测试性）怎么样？它不像 reliability、availability 那样能给你一个公式算出一个百分比，而是由很多 ability 组成的：

| 指标 | 含义 |
| :--- | :--- |
| Operability | 软件是否可操作；操作越方便，测试越容易 |
| Observability | 执行时你能多大程度看到它的内部情况 |
| Controllability | 测试人员能多大程度控制这个软件（关系到自动化测试） |
| Decomposability | 能多大程度把它分块；块越小越好测 |
| Simplicity | 被测软件本身有多复杂；越简单越好测 |
| Stability | 开发过程是否稳定（需求老变、版本乱改，谁都抓狂） |
| Understandability | 设计文档与代码在多大程度上可读、可理解 |

比如 observability：如果软件整个是一个黑盒子，就比较没法测。我们现在另一个组在跟医院合作做一个系统，以前有机构做过类似的东西，为了版权保护把它做成了完全的黑盒子——只有一个接口、一根网线，卖给你一个小型服务器，界面上就一个按钮，你点一下它把结果给你，中间完全碰不到。如果让你测这个盒子，你就痛苦了：什么都看不到，出错了有 N 多可能，可你根本不知道它的内部结构和算法流程，只知道按了一下按钮出了个结果——对测试团队来说这非常恐怖。所以 observability 指的是软件执行时你能多大程度看到它的执行情况。

Controllability 则是你能多大程度控制它。权限足够大，就能比较好地设计自动化测试。像 PAT、ACM 竞赛，裁判直接控制你提交上来的代码，写一个 judge 程序自动跑一下，什么都搞定了。Decomposability、simplicity、stability、understandability 都好理解：让一个程序员发疯很容易——你只要改三次需求他就疯了。

> **提示**：testability 这里只告诉你它由哪些 ability 组成，每一个指标怎么设计都是一门学问。

### 为什么不能穷尽测试

那我们干嘛不干脆做一个穷尽测试（exhaustive testing）？书上给了一个例子：一个程序流程图，有 5 个 if-else 分支（一个、两个、三个、四个、五个），里面还有一个循环，循环 20 次。每一次循环都有几种分支走法，要设计完备的 test case，把所有可能性都测到，要多少个？排列组合：$5^{20}$。就为了测这么小的一个程序，差不多要花 3000 多年。所以穷尽测试是不可能的。

这么简单、这么短的几行程序，穷尽测试都做不到，更别说复杂的系统，想都不要想。所以你一定要有策略，忽略掉一些情况，选最有代表性的情况去测。两大最常见的技术就是 **white-box testing**（白盒）和 **black-box testing**（黑盒）。

| | 白盒 White-box / Glass-box | 黑盒 Black-box |
| :--- | :--- | :--- |
| 盒子 | 透明，看得到内部 | 不透明，只看外部表现 |
| 阶段 | 单元测试、debug，testing in the small | integration 之后，testing in the large |
| 关注 | 程序内部的路径、逻辑覆盖 | 功能、行为、性能、输入分类、边界 |

> **结论**：不管怎么测，只要不是穷尽测试，你就永远不能说"这个软件里没有 bug"。**Testing cannot show the absence of errors and defects.**

你只能说：以你现在的能力和经验、在有限时间范围内，你查不出来了。

### 白盒测试：从流程图到环形复杂度

White-box 也叫 glass-box testing，顾名思义，你是看得见程序内部的，非常清楚那个程序流程图。所以它是 **testing in the small**，只对小段代码用。

白盒测试要检查什么？重点是每个 **path**（执行路径），希望达到尽可能好的路径逻辑覆盖。设计白盒测试时，脑子里要回答下面几个问题：

1. **Can you guarantee that all independent paths within a module will be executed at least once？** 什么是 independent paths？学线性代数时，什么叫线性无关（independent）的向量组？就是这个组里任何一个向量都不能被其它向量组合出来，它总有自己独特的一个点是别人 cover 不了的。independent path 道理一样：流程图里有很多路径可以组合，一个独立路径就是不可能由其它路径组合出来的路径，它一定有至少一个边是别人没 cover 的。最低要求是：你设计的 test case 进去走一遍，能不能保证所有 independent path 都至少被执行一遍——也就是图里每条边至少被走一遍。这是一个非常弱的要求。
2. **Can you exercise all logical decisions on their true and false branches？** 凡是 if-else、switch-case 这种控制节点，yes 和 no 两种可能是否都测到了。
3. **Will all loops execute at their boundaries and within their operational bounds？** 循环的边界是什么？进去和跳出来的两个点就是边界。比如循环从 1 到 100，1 和 100 就是边界。你要设计一个 case 让它只循环一次就跳出，再设计一个让它循环满 100 次最后跳出，这就是 boundaries。
4. **Can you exercise internal data structures to ensure their validity？** 比如你定义了一个固定大小的数组，就要设计一个 case 让它被用到最大极限，看它会不会溢出、会不会 run-time error 崩溃。你定义了一个 struct，里面有字符串、数组、指针，就要测这些内部结构在程序执行过程中会不会出现诡异情况。

前两个问题关于逻辑覆盖，后两个关于数据结构和边界（boundary 后面还会反复用到）。

#### 路径与节点覆盖

白盒测试里最重要的是路径覆盖。有路径覆盖，也有节点覆盖。最弱的是 **execute every statement at least once**——每句话至少执行一遍，保证没有哪段是冗余的、被直接跳过去、没有意义存在的。

这里有个技巧：把顺序执行的语句缩成一个点，看成图里的一个节点并编号，把程序简化成一张 flow graph（二维平面上的有向图）。看的时候要仔细：像有些判断分支节点里其实包含了两个逻辑关系，比如 `total < 1000 and a != 0`，它有 and，测的是两方面东西，这种 compound condition 最好拆成两个节点。

有了图，做 basis path testing 时要算一个数据：**cyclomatic complexity**（环形/圈复杂度）。学图论的话应该见过，它有三个等价的定义：

- 平面图把它把整个平面切成几个连通域，连通域的个数；
- 边数减节点数加 2（$E - N + 2$），这两个可以证明相等；
- $P + 1$，P 是 predicate node（分支节点）的个数，也就是出去的箭头不止一个的节点个数。

举个例子：一个程序有 3 个分支点，$3 + 1 = 4$；整个平面也确实被它分成 4 个连通域，所以它的环形复杂度是 4。

这个 4 有什么用？它表示"路径测试的难度"——分支点越多，数越大，可能有多少条 independent path 要测。更准确地讲，**它给的是上限**：

看一个例子：给你一段带 compound 条件的程序，先把 compound 拆成两个点，画出图，算一下环形复杂度。答案是 5——也就是说最多设计 5 个 case 就能让每个 statement 至少执行一次。

但**语句（statement）覆盖非常弱**：我只保证每句话被执行一遍，没说每个分支都要被执行一遍。所以有时一个 case 就够了——让它从头走到尾。可这样一来，如果程序里本该写 `and` 结果写成了 `or`，你查得出来吗？查不出来，你的 case 是对的，但程序可能是错的。原因就是你还有一个分支没测到；走一下那个分支，就会发现这里写错了。所以更强一点的覆盖是 force execution of each path，而不是 each statement。

#### 条件覆盖

要覆盖每一个 path，其实就是：每一个分支节点的 true 和 false 都要测到，这叫 **condition testing**——test every condition at least once。

如果条件很简单、就一个条件，事情很简单；问题是它经常不简单。比如一句复合条件（两个分支 B1、B2 用 and 连接），要把这句测完备、每个条件的 true 和 false 都至少测到一次，怎么系统地、有规则地设计 case、保证不漏？一个窍门是先把它们当成一个整体、两个分支去看，设计能让整体同时取 true 和 false、又能让每个分支都取到 true 和 false 的 case。比如设计三组：两个都 T；一个 F 一个 T；一个 T 一个 F。这样整体结果有 true 也有 false，B1 有 true 有 false，B2 也一样。你当然也可以只写两个 T、两个 F，可以是可以，但不太好。

然后进一步细化：每个 T 意味着什么、每个 F 意味着什么。比如对 `E1 > E2`，T 翻译成"大于"，F 翻译成"小于一个、等于一个"。一步步展开、替换，最后就得到一个具体的取值集合，这里一步步展开下来是 5 组测试取值。

> **提示**：考试里很愿意出这种题——给你一个比较复杂的 compound statement，要求你用**最少的 test case** 把每一个 true 和 false 都执行过，看你怎么设计。这就是 condition testing。

还有 **data flow testing**：它关注一个数据（变量）在程序里取值的变化过程，就像 debug 时一步步看这个变量取到多少。做法是把程序拆解，对每一个变量找它在哪些地方被定义、在哪些地方被用到。

- **def of S**：S 是一个 statement，这句话的 def 集合，是所有在这句话里被定义了（赋值、初始化）的变量的集合。
- **use**：这句话用到了哪些变量的值（没有改变它的值，但用到了它）。

于是它定义了一系列 **DU chain**：一个 D（定义）、一个 U（使用）。对每个变量找它的 DU chain，就是看这个变量在哪几个语句里被定义、在哪几个语句里被使用，而且要求顺序往下走——上面的定义在中间没被改过，在下面被用到时用的是上面给的定义。最终给出的就是变量 X 的值的变化过程：在哪些地方被改动过、哪些地方被使用过、顺序如何。你设计的 test case 就是让**每一条 DU chain 都覆盖一次**，以 DU chain 为单位一条一条测过来。

#### 循环测试

控制结构里还有 **loop testing**。循环有几种不同的类型。

- **Simple loop**（简单循环）：至少要做边界测试。比如从 1 到 n 循环，那么循环一次、循环 n 次肯定要测；还要测非法的循环——直接跳过的 **0 次循环**，以及有没有可能让它 **n+1 次循环**、会怎么样；再测正好在边界附近的 **n-1 次**。循环在边界附近最容易出错。最后在中间随便取一个数循环一下。注意这里 n 不是说事先给好、你让它循环多少次，而是指你输入数据的 size：我输入的数据 size 可能是 1、可能是 100，那 1 要测一下、100 要测一下。
- **Nested loops**（嵌套循环）：技巧是先让外循环不执行或只执行一次，把内循环测完备；内循环测完后，就把它当成一个已经被完整测过的模块，不再管它，再用普通策略去测外循环。
- **Concatenated loops**（串联循环）：没什么好说的，一个一个顺着测下去就好。
- 还有一种循环——你如果碰到那种结构，**直接踢回去说我不测，程序不能这么写**：把这个程序直接踢回给程序员，拒绝测。

### 黑盒测试：只看外部表现

白盒测试叫 testing in the small，基本上在单元测试阶段、程序还没交出去、程序员自己测或者 debug 时做。**黑盒测试**基本上是在 integration testing 后面、集成的时候用：我不关心程序内部结构，只关心它的外部表现是不是正常。这是 **testing in the large**。

设计黑盒测试的 test case 时，脑子里要想这些关键问题：

- 所有这个模块应该有的**功能点**都要测到；
- 它的 **behavior**——表现、几个状态，是不是正常地达到了那几个状态；
- **performance**（效率），如果有要求的话；
- **classes of input**——输入怎么分类，要有代表性（后面细讲）；
- 系统对什么样的 input 特别**敏感**——这个地方要非常小心地测，因为一旦这个数据错了，系统可能整个崩溃；
- 每一类数据的**边界**怎么确定；
- 系统能承受多大的 data rates 和 data volume——这就要做 **stress testing**（压力测试）；
- 各种输入数据的**排列组合**对系统表现的影响，怎么设计这些 combinations。

书里介绍了四种技术，我们重点讲后两种：

- **Graph-based testing**：把整个系统映射到一个图，通过分析图的复杂性来做测试——这是研究生更高级的内容，这里不讲。
- **Orthogonal array testing**：专门测排列组合的技术。比如输入是三个不同种类的参数，每个都有取值范围，你不仅要测各自的范围，还要有效地排列组合地测。穷尽排列组合工作量很大，选择性地测又一定会 miss 掉一些组合。哪几种组合比较有代表性，就靠这套技术来确定——也不讲。
- **Equivalence partitioning**（等价类划分）和 **boundary value analysis**（边界值分析）：这两件是**所有软件测试里都必须要有的**，也是我们的重点。实际上这两件事连在一起：先划分等价类，类一划好，边界就有了，然后你再有效地在边界上做重点测试。

#### 等价类划分

什么叫等价类（equivalence class）？关键在定义的最后一句：There is no particular reason to choose one element over another as a class representative——在这个集合里随便挑哪一个都一样。比如 1 到 100 的整数范围，挑 18、挑 39、还是挑 97，没区别；那这些整数的集合就叫一个等价类，因为在测试方面它们是等价的。

书里给了一些划分 guideline：

- 合法输入是一个 **range**：设计一个 valid 类，再加两个非法类。比如合法是 1 到 100，那 1 到 100 中间选一个数是合法类，小于 1 的整数一类，大于 100 的整数一类——至少三个等价类。
- 合法输入是一个 **值**：正确的那个值一类，大于它的、小于它的各一类。
- 定义是一个 **集合**：比如"教师"是一个集合，那么所有教师属于一个等价类，所有非教师人员属于另一个等价类。
- 是一个 **Boolean condition**：yes 一类，no 一类。

#### 边界值分析

等价类划分好之后就做 **boundary value analysis**，边界值分析几乎所有的测试里都必须用到。

没考过 PAT、没玩过竞赛的人第一次上网站做题，总会哭诉："为什么我 sample 都过了，程序还有错？"答案很简单——绝大部分程序都错在**边界**上。

上个月底我们三个老师组队参加了一下校赛，一道简单题，何老师瞬间写了个十行不到的小程序，一交上去就 WA。我们瞪着眼睛看半天：这么简单的程序怎么可能错？看不出来错在哪儿，一个技巧就是设计一个 test case 让它去跑。我设计了一个 boundary case，直接取到它的最大值——转一下它就崩溃了。为什么？答案超出长整型了。一道简单题居然卡了 long long。你看程序是看不出错的，可你怎么知道边界数据一进去就超过整型呢？

这种 bug 就喜欢在墙角呆着，边边角角的地方最容易出错。书里的 guideline：如果给的是一个 range，是 a 和 b，那么 case 里一定要有 a、有 b，同时还要有正好大于 a、正好小于 a、正好大于 b、正好小于 b 这些边界附近的 case。剩下的自己去细看边界测试该怎么设计。

### 调试：找到错误之后

Debugging 的过程是：执行 test case，发现有错；先估计这个错误是由什么造成的；为了验证确实是这个原因，加一些 additional test、新的 test case 去验证；如果证明的确是这里错，就把它改过来；改完还要做一定的回归测试。

Debugging 有很多技巧，它是 **the art of debugging**——调试的艺术。大致有这么几种：

- **Brute-force**：很古老、很"牛"的做法。最牛的是 memory dump：把程序出错那一瞬间的内存全部打印出来（八进制的 code），然后读，从里面找错误。我还没老到那个程度，我最多用过 spy points。跟老一辈程序员比起来，你们现在真是弱爆了——现在有那么多好的调试工具。
- **Backtracking**：如果程序不是很大，策略是：最后结果错了，就在程序中间插一个断点，看这时它是对的还是错的；如果这时就错了，说明错误在上面；如果这时数据是对的，说明错误在下面。可以理解为二分的这么一个过程。
- **Induction**：很多公司里用的方式。我以前的美国学生暑假去微软打工，每天领一张表——上面告诉你这些输入应该得到这些输出，你就一项一项做，是体力活：输出来，写记录，对还是不对。如果不对，要填一张表，三个 W 一个 H：What、Where、When、How。就是说"有哪些、没什么；在哪里有、在哪里没有；什么时间发生、什么时间没发生"——凡是有东西的放这一栏、没有的放那一栏，填这么一张表。交给程序员后，他根据你描述的现象来猜、来分析大概有哪些 causes。
- **Deduction**：跟侦探的推理一样——先有很多怀疑的嫌疑人，然后在调查过程中一个一个排除，最后剩下的那个就是真正的 cause。

改 bug 时还要注意三点（bug removal consideration）：

1. 产生这个 bug 的原因，在程序的其它地方是不是也出现？会不会别处也有类似的错？
2. 把这个错误改过来以后，下一个 bug 有可能是什么？
3. 总结一下经验教训：我为什么会犯这样的错？下次怎么才能不重复犯这个错？

### 本讲提到的题目

#### 给二分查找出裁判数据

这是一道 PAT 考题，题目非常简单——查找：在一串整数里找一个给定的整数。但我给的条件是：**给定的是有序整数**。这就意味着你心里总应该用一下二分查找；如果你用不用二分查找的蠢办法，比如线性查找从头到尾扫一遍，我肯定要在某个 case 上把你卡住。

输入分三行：

1. 第一行给一个正整数 n，不超过 10 万（$n \le 100000$）；
2. 第二行给出 n 个整数，每个整数不超过长整型——这里不用 long long，用 int 就可以；
3. 第三行给出一个整数 X，你要找的就是它。

我保证这 n 个整数是按**从小到大**的顺序给的。输出是：如果 X 在这串整数里，回答 `yes`，否则回答 `no`。这里有个细节学生当场问了：从小到是不是不减？我说是不减——只保证非递减，不保证严格递增，也就是说**允许重复的数字出现**。因为只回答一个 yes/no，不回答位置，所以允许重复。

我要你做的是：**帮我把这道题的裁判测试数据设计出来**。前提是 PAT 系统不能测太多 case，你的 case 无论如何不要超过 10 个，10 个太多了，越少越好。要记得我们设计测试数据的原则——尽可能多地 cover 错误、找得出错；测得尽可能全面，但用最少的时间和精力；用最少的 case 测到最多的事情。

别忘了还要替我设计 sample input / sample output。给分原则是：**sample 过了至少可以得一半的分**——比如这道题 20 分，sample 过了我就给 10 分，剩下 10 分分给其它 case。每个 case 你要告诉我它的测试目的（到底要测哪个点），最好连分数也一起写清楚。另外 sample 应该给两组，一个 yes 的 case、一个 no 的 case。

**解析与答案**：这道题的本质是"有序整数的存在性查找"，所以测试数据要围绕二分查找最容易出错的地方来设计——也就是**等价类划分 + 边界值分析**（前面讲过的两件必备工作）。

- **等价类**：答案只有"找到"和"没找到"两类，所以 sample 至少要一个 yes、一个 no（题里也说了 sample 给两组）。这两个是最基本的等价类代表。
- **边界值**：二分查找的边界最容易出事，所以要专门测：
  - X 正好等于序列的**最小值**（第一个元素）、正好等于**最大值**（最后一个元素）——命中两端；
  - X **小于最小值**、**大于最大值**——没找到，且在序列的两侧越界；
  - n = 1 的**最小规模**，以及 n 取到上限 10 万附近的**最大规模**（大数据要靠专门的 generator 生成，不要手写）；
  - 序列里**有重复元素**、且 X 恰好等于重复值——测非递减而非严格递增这个约定；
  - X 出现在中间位置；
  - **卡线性查找**的 case：大数据 + 目标靠近尾部或不存在，让 $O(n)$ 的线性查找超时，逼出二分查找。
- **sample**：给两组即可，一组 yes、一组 no，约占一半分数（10 分）；其余分数分给上面的边界类 case，每个 case 标注测试目的与分值。

> **提示**：这题看着简单，做起来你会发现——为了让二分查找的边界和大数据都被覆盖，你其实得专门写一个 generator 去生成大数据，光靠手写输入输出是不够的。

#### 给复合条件设计最少的测试用例

课上还提到一类考试常出的题：给你一个比较复杂的 compound statement（复合条件语句），要求你用**最少的 test case** 把它测完备——保证每一个条件的 true 和 false 都至少被执行过一次，然后看你怎么设计。做法就是前面"条件覆盖"里讲的那套：先把整句当成一个整体、把并列的分支拆开，一步步把每个 T/F 细化成具体的比较取值，系统地展开，不漏掉任何一种真假组合。

## Web 工程：应用特点、项目启动、需求分析与设计
> 对应块：BLK06 | 覆盖分集：P21-P24

上一次课我们把需求分析收了个尾，按原计划，接下来该讲设计了。我中间先停一下，插进来聊一类专门的软件——Web App，也就是 Web Engineering 要对付的东西。这一类东西在这一版教科书里是第一次被单拎出来当成一个额外的主题，说明它有自己一整套与众不同的 attributes（特点）。也正因为这些特点，我们后面做分析、做设计、做测试，针对 Web App 的路子跟针对普通软件就会有点不一样。

想搞清楚哪里要做得不一样，先得搞清楚 Web App 到底在哪几个方面跟普通软件典型地不同。这个问题我不直接给答案，先在课上抛给你们——你们来说，Web App 有什么与众不同的特点？知道它的特点的意义在于：以后做任何事情，你都要照顾到这些特点。

### Web App 凭什么被特殊对待

顺着课堂上的思路，一条一条捋。

它首先是**基于网络的**，严重依赖网络，这是最根本的一条。

第二是**跨浏览器、讲兼容性**。不同的浏览器显示出来的东西可能不一样，所以你得格外注意页面外表的美观。

第三是**本地存储少**。本地存得少，就意味着它必须快，performance 很重要。

第四是**开发要敏捷**。这类需求通常变得快，迭代周期也要短。一般接到一个 Web App 的任务，人家不会说给你三年去把它做出来，那不可能；给你三个星期就已经很长了，最好是一周赶紧弄出来。这就注定了你的 process model 必须非常敏捷、非常快。

第五是**用户交互性强，而且用户不可控**。交互要考虑得周到，最麻烦的是你不知道来的是谁，各种稀奇古怪的人都有。这里有个很典型的对照：你给一家小银行做一套只给员工用的系统，用户群是固定的，你可以训练他们别犯错，他们的行为都在监控之下；可支付宝一上网，你根本不知道谁在用。刚才那位同学举的支付宝其实就是很大程度上的一种基于 Web 的 application。

第六是**数据存在服务器上**。传统软件的数据存在用户自己电脑里，Web 应用通常存在服务器的数据库里，于是用户数据安全就成了**非常重要**的因素。这也决定了你搭团队时要挑什么样的人：除了编码强的人，还得有一帮对 security 很懂行的人。

第七是**大并发、workload**。放到网上的东西，你得有很强的并发处理能力。这一点我印象特别深。当年北京办奥运会，抢奥运会门票的网站开放的一瞬间就崩了、死掉了。正好我有一个表弟在那个技术组，过年见着他，我嘲笑他说你们做的是什么土网站。他说不是我的错，我们要自己开发，领导说不要，领导说引进美国当年办奥运会时用的那套软件。我当时就说，美国才多少人，你严重低估我们中国人民的热情。后来我替他算了一下参数，算下来那软件大概每秒能处理五个并发——每秒五个，这不可思议。每秒五百个还不一定够，每秒五个并发，那不是瞬间就崩溃？所以它崩溃是很正常的。

第八是**unpredictable load**。你不知道软件的访问量会怎么变，它可能是季节性的，一阵子疯抢，过了就没人用；每天跟每天、哪个小时到哪个小时段，都各不相同。

第九是**performance**。访问效率要特别注意。人家打开半天打不开、页面一直 loading，就不耐烦走掉了。尤其一个想吸引人来访问的网站，效率做不好就没人气。

第十是**availability**。挂到网上的东西，大家都默认你应该是每天 24 小时、一周 7 天、一年 365 天都可用，不该有太多挂掉的时间。这就要求你有一个非常强大的维护团队。

第十一是**data-driven**。大多数网站是数据驱动的，一个基本、共通的功能就是把某一类数据展示给用户——视频、音频、文本还是别的什么，总之要展示。所以设计时你要知道这是以数据展示为主的网站。

第十二是**内容质量要求高**。如果网站靠内容吸引人访问，那它对内容质量的要求比一般软件高得多。内部员工用的软件，措辞、美观程度都是次要的，能支持工作流程就行；可挂出去给不知道什么人看的东西，想吸引尽可能多的人来用，内容质量与美观程度就相当重要。

第十三是**continuous evolution（持续演化）**，这是 Web App 一个非常重要的特征。你组好团队之后，不是开发一个星期就散伙，绝不是这种团队结构。

第十四是**immediacy（即刻性）**。就是要快。人家今天说要个网站，最好你明天就做出来，不行最多给一星期；我今天规划了个网站、三年以后交付，那是想都不要想。这跟传统软件很不一样，也就决定了整个 process model 的设计要以快为主。

第十五是**security**。security 在 Web App 里扮演非常非常重要的角色。当然你们现在知识有限，我们做支付宝这个大作业时对 security 就不做特别高的要求，要求到什么程度你们去跟 TA、跟你们的客户谈；但真正的支付宝，security 是没得商量的。

第十六是**美观**。美观可能是别的软件不那么看重的，但一个网站漂亮不漂亮，是你吸引人的一部分，你要有一个很漂亮的包装。这就意味着团队里要有一个强大的美工。美工其实很难找——做界面和做美工是两种人。像我们自己的学生，做功能开发的人很多很多，但做 UI 的人就很少；我们默认 UI 包含了美工，其实不对，UI 跟美工可以是两个人。这一点后面专门讲 UI 时还会再提。

> **提示**：记住这十几条，不是为了背，而是为了在做分析、设计、测试时，随时对照着照顾它们。整个 Web 工程流程，都是围绕这些特点设计的。

顺带说一句，为了这门课，我把支付宝这个大作业按某种原则分成了五个组给你们。你回头想一想：这个划分的界限是不是很干净？是不是有很大的问题？这个留给你们自己琢磨。

### Web App 的十种类型

了解特点之后，书上又把 Web App 大概分成几大类。这个分类你可以同意、也可以不同意，它不一定特别有道理，但它有它的道理；你看完觉得别扭，那就可以保留你的看法。真有兴趣，可以写一篇小 essay 论述自己的观点，我很欢迎看到新的观点。

| 类型 | 说明 | 课上举的例子 |
| :--- | :--- | :--- |
| informational | 基本是静态网站，发通知、发新闻，read-only，没有互动，只是发布消息用 | — |
| download | 专门给你提供资源下载 | 源网、高清电影下载站 |
| customizable | 允许根据自己的个性做定制 | 博客 |
| interaction | 交互用 | CC98、飘渺水云间、QQ |
| user input | 让你在网上填表 | — |
| transaction-oriented | 事务/流程型：你提一个请求，它走一个流程把这件事处理掉，起交易中心的作用 | — |
| service-oriented | 提供某种服务 | 学校里的服务类网站，自己去想 |
| portal | 门户网站 | — |
| database access | 访问数据库 | — |
| data warehouse | 数据仓库 | — |

最后这个 data warehouse 值得多说两句。知道 warehouse 是什么吗？我们国内好像没有美国那种 warehouse 商店——它是像仓库一样的商店，卖东西都跟批发差不多。你去普通商店买饼干，买一小盒；你去 warehouse 里，人家不卖你一小盒，要么一打、一包，你要买就扛一大箱走。所以 data warehouse 你可以理解成 database 的集合，而且是好多不同 database 里数据的集合。当然它不是简单拼凑，它要把不同 database 里的数据整理一下、重新归类、重新组织，规模比单个 database 大很多。

> **提示**：分类本身不是目的。我在课上留过一道题——整个支付宝属于哪一类？为什么？你自己负责的那个模块是不是具有 Web App 的特征？如果有，属于哪一类？如果没有，说说为什么它显然不具有这些特征？再挑出两种类型，各举一两个现在市面上非常著名的、属于这一类的网站，并且要讲道理：这网站是干嘛的、有什么特点，所以属于哪一类。做我们这一行的人，这十类最好都能举出例子来。

### 层次化技术与敏捷过程模型

普通软件我们说软件工程是一个 layered technology（层次化技术），Web 工程也一样。不管哪一种，最底层都是 quality focus——做什么都要以质量为中心。Web App 虽然要求你什么事都做得匆忙，但匆忙不代表就不做质量，你还是要注意控制 quality。

在此之上，我们选择的 process model 通常是 agile（敏捷）。敏捷开发这个 process 我会放在最后一节课才讲，为什么放最后到时再说。总的特点就是快。为了达到快，它要做的一些方法，大面上看其实跟普通软件一样：要注重 communication，要做 requirements and analysis，要做 design，要做 testing，都得做，只是它自己有它的一套方法。工具上就是 HTML 这一类常用的，针对性更强一点。

```text
    ┌──────────────────────────────────────┐
    │  工具 Tools（HTML 等）                 │
    ├──────────────────────────────────────┤
    │  方法 Methods                          │
    │  communication / requirements          │
    │  & analysis / design / testing         │
    ├──────────────────────────────────────┤
    │  过程模型 Process Model：Agile（敏捷）  │
    ├──────────────────────────────────────┤
    │  质量 Quality Focus（一切的中心）       │
    └──────────────────────────────────────┘
```

读图说明：从下往上，质量是地基，过程模型承在其上，再上面是具体方法与工具，越往上越靠近具体怎么做。

Web App 的 process model，有两点一定要抓牢：一个是快，一个是 continuous evolution——连续演化、持续更新、不断推进。网站不会说过了三五个月才给你推出一个新版本，正规网站一般不这么干，它随时随地在更新版本。所以你做的时候根本不要想一步到位，它一般是一个 incremental delivery（渐增模型），肯定是一点一点交出来的。同时变化经常发生，timeline 又非常短，这就决定了你要选一个增量式的、敏捷式的过程模型，大多数情况下都适用。

```text
   第 1 轮迭代      第 2 轮迭代      第 3 轮迭代
   ┌─────────┐     ┌─────────┐     ┌─────────┐
   │ 构造     │────▶│ 构造     │────▶│ 构造     │────▶ ...
   │ 重构     │     │ 重构     │     │ 重构     │
   └────┬────┘     └────┬────┘     └────┬────┘
        ▼               ▼               ▼
    increment       increment       increment
```

读图说明：一圈一圈迭代，每一轮里"构造"的同时持续做"重构"，迭代出去一个 increment；如此反复。这个示意图有的人喜欢顺时针画、有的人喜欢逆时针画，这里是逆时针画的。

> **提示**：重构（refactoring）是个大坑，做之前一定要想好、要小心，这个后面再说。

### 开工前一定要搞清楚的问题

在开始做事情之前，你们这个 team 一定要搞清楚下面几个最起码的问题。

- 你要做的这个 website home page 到底有多重要？它对内容有多敏感——是给国防部做的，还是我们这门课做个网站给大伙玩玩的？
- 这个网站是内部学生自己用用玩玩的，还是要放到外面让全国学生、全国高校的学生都能看到？内容的敏感程度不一样。
- 这个特定的 Web App，最有效的 page layout 是哪种套路？上面横着一条 menu、下面放内容？还是横着一栏、竖着一栏（竖栏放左边还是右边）？整个页面怎么布局？
- 内容用什么形式展示？简单文字，还是视频、音频、Flash？哪种效果最好？
- 用户来访问这个网站，想做成什么事？为了这件事他有多大耐心？最多几步操作？主要面向的用户群是什么人？给老年人做是一种风格，给大学老师做是一种风格，给幼儿园小朋友做是另一种风格。
- 这个网站到底有多复杂？页面导航这件事是不是非常重要？要不要做 search，或做一个导航图？
- 如果有提交表单（一般来说都会有，起码得注册个账户），注册表该让用户填多少？商家希望填得越多越好，但填太多用户没耐心，一句"这么烦，我不注册了"就走了。这个度是非常 delicate（微妙）的一件事，你要找到平衡点。
- 网站要不要照顾残疾人，做到无障碍访问？你有没有可能做到？

> **提示**：这些都是动手干活之前必须大致搞清楚的。认准做的是什么事、为什么要做、再想怎么做，这是贯穿整门课的东西。

### 启动阶段：formulation

现在换个话题：把 Web App 当成一个 project 来启动时，你要考虑哪几方面的事。具体的需求、设计下次课细讲，这里先大面上说。这一步叫 initiating，启动一个 Web App 的 project。

第一步是 formulation。这个词查字典找不到一个很合适的词来描述它，大意就是"先大概规划一下"。formulation 阶段到什么为止？到你拿到一个大致需求为止。

举我的例子。我说我要给这门课程做一个课程网站，现在的网站我做得不太满意，想重新做一个。我把消息发布出去，在酒吧挂个帖子说征人做网站，你来应征。你来应征就得来找我谈、问我问题，一直问到一个大致的需求搞清楚——这个过程就是 formulation。

那如果你来应征，你要怎么准备、来问我什么问题？书上没有，我直接给场景：我要征人做软件工程的课程网站，你来应征，你打算问我什么？而且这些问题要**有顺序**：先问什么、再问什么，顺序不同会得到不一样的效果。刚开始的信息量很少，我甚至没说要招一个人还是招一个团队。

把这些问题排好序之后，大体会落到下面几个关键点上。

先是 **identification of business need（业务需求的识别）**：你为什么要做这个网站？老师做这个网站是干嘛用的，是为了报奖，还是申请教育部的什么项目，还是学校要求的，还是压根儿吃饱了撑的想做一个？其实你隐约还要想一层：做这件事对我能带来什么好处，我愿意为它付多少代价。我自己做着玩的，你就别指望我掏十万二十万。

然后是 **objectives（目标）**：做这个网站到底干嘛用。一个课程网站有很多种——只把课件放上去方便学生下载？放点课外的 reference 参考资料供下载？要不要组织一个论坛？要不要布置作业？要不要打分（我们现在这个网站原来就有打分功能）？而且它是给谁用的——只给我一个人用、你们就下载，还是给整个课程组五六个老师一起用？

> **易错点**：现在在用的这个网站，当年做的学长就犯了一个很严重的错误，少问了这么一句话，我也少说了这么一句话。他默认这网站是给我一个人做的，所以里头只有一个用户，其他老师都不能用。他当时的想法是：用课程组的钱请人做，肯定是给课程组用；而他是我当时的 TA，目标就是给 TA 提供一个方便的打分、收集、统计的东西，所以给自己做了。我们俩都觉得自己的目标很显然，结果谁都没把这句话说出来。后来要改成多用户，才发现他当初的设计很不好，改起来很麻烦。**两个"很显然"撞在一起，就等于没人说。**

接下来是 major features and functions——到底需要哪些功能；再有 requirements gathering——要有一种方式把需求收集整理起来，做一个 analysis model。最后，所有 stakeholders 包括开发人员坐到一起，达成一个共识：common set of goals and objectives，也就是要做的东西到底干嘛、达到什么总体目标、完成哪些功能，这些是大家都同意要做的。因为在这么短的 timeline、这么点钱的条件下，胃口太大是不可能的，最后大家要达成一个协议：到底做什么。

不管你用什么样的问法，**总归要覆盖三个方面**：用户为什么要做这件事；他想做成哪些事；做好了以后到底谁来用。这三个问题不 cover 掉，问题就不全面。

从用户的回答里，你要抽取两大类信息：

- **information goals**：网站要提供哪些内容？数据、内容以什么形式展现？
- **obligative goals**：有哪些功能？有哪些任务可以通过网站来完成？（一个是数据，一个是功能。）

requirements gathering 里头，有几件事要特别关注。

- **user categories（用户分类）**：做别的软件也要做，但没那么重要；做 Web App 就显得非常重要。对每一类用户都要给详细描述——不仅包括这个用户用网站要干什么（他的 objectives），还包括他的 background（教育背景、识不识字、是哪一类人），甚至他的习惯。比如面对的是年轻人、是 90 后，他们平时喜欢的网络环境是什么样，就决定了你给他设计时界面风格大概是什么样；他在什么场合、什么情况下会到这儿来用你的软件；他们这群人特别喜欢什么、特别不喜欢什么。给很新潮的人设计和给很传统的人设计，方法不一样。你不可能给幼儿园小朋友设计一个基调蓝黑稳重的东西，小朋友会觉得没劲——给小朋友做我肯定要花花绿绿的，最好没多少文字，各种动画图片，他拿手过去点点戳戳就能用。你要把这套风格搬到银行网站上，那就很奇怪了。所以你要做的东西面向什么人群，要专门分析。
- **communicate（沟通）**：用各种办法尽可能充分地拿到需求。对传统人士，用传统方法——开会、面对面谈；也可以发 email；还可以做 survey（调查表），发到特定的用户群里。如果你做的是一个以前没人做过的 great idea，前期一个很重要的工作就是设计调查问卷，到你认为的目标人群里发——比如你是面向学生的，就到各个校园去，同学打扰两分钟帮我填一下。要采集足够多的数据，你才能看得出这种类型的 service 在人家心目中应该是什么样子。
- **scenario building（场景构建）**：关键是要在脑子里慢慢成形——这群人用你这个东西的时候是怎么个用法，对他最吸引、最好用。然后做分析，从各种信息里抽取你的 **content object**（要展示的数据、输入输出）和 **operations**（要做哪些操作、完成哪些功能）。
- 最后得到**一套一套的 use cases**。做网站基本都是以 use cases 为核心：先把 use case 一个一个搞清楚，人家怎么用你的网站，后面从建模、设计到测试，use case 都是非常重要的依据。

### 轻量级的计划

formulation 之后，你还要做一个 plan。这个 plan 非常不正式、非常短、比较草，但还是得做。

书上给了一张表，对照 traditional projects（传统项目）、小型的 e-projects、major e-projects（大型复杂 Web 项目）三类项目的特点。要计划的事情包括 requirements gathering、technical specifications（技术规格）、时间、testing 与 QA、risk management 等。

> **提示**：这张表你其实不用逐格细看，**只要看颜色**。红色表示跟传统软件工程不太一样的地方。如果是规模大、功能多、非常复杂的大系统，它的基本流程跟传统软件工程差不多——一样严格、按部就班，唯一的区别在最后 customer feedback 那个方向。如果是小型的轻量级 Web App，那几乎全是红的。

| 要计划的事 | 传统项目 / 大型 Web 项目 | 小型 Web 项目 |
| :--- | :--- | :--- |
| requirements gathering | 严格、一步接一步，反复开会，最后写需求规格说明书 | 不需要那套，但大致要有一段 descriptive overview，三言两语说清 |
| 时间周期 | 相对宽松 | 非常非常短 |
| testing / QA / risk management | 按部就班去做 | 重点强调 risk control，随时盯"做不做得完" |
| 用户反馈 | 面向固定用户群，可直接获取 | 面向全网，只能设计自动获取机制，或到处发问卷 |

大型 Web 项目跟传统的唯一区别就在用户反馈这一条：传统项目在比较封闭的环境、比较固定的公司内部人群里，你可以直接获得反馈；而 Web App 的用户是全世界所有能上网的人，你没法在特定范围内获取反馈，所以只能尽量设计一种自动获取反馈的机制，或者到处发调查问卷——"你知道我这个网站吗？用过它吗？什么地方好用、什么地方不好用？"

小型 Web App 就完全不一样了，基本特点就是快。requirements gathering 在传统里很严格，一步一步做、仔细设计要问什么问题、开好几次会、最后写一份需求规格说明书；做小型 Web App 全都不需要，但你还是要有那么一段 descriptive overview。时间周期要求非常短。testing、QA、risk management 这个过程重点强调 risk control，随时想的是"做不做得完"，也希望团队的人对要用的技术非常熟练。

> **结论**：一共只有 7 天，你不可能用两天做准备工作、剩下 5 天放手不管、5 天后再来看——那多半得到一句"没做完"。要保证 5 天做完，其实你**每天都要 track、每天都要盯牢**，这就是一个 risk control 的过程。既要强调快，又不能放松质量；可又不可能做很好的质量监控，你要在中间做平衡。

### 团队里有哪些角色

接下来要组一个队。这个 team 不单指开发团队，web engineer 绝对是团队里的重要人物，但除了他们，你还需要哪几种角色？这个 team 不一定都是你自己人。除了开发团队，还要有谁？我要问的就是：**stakeholder 有哪些？**

开发好之后，你还得教会人家怎么用。拿课程网站来说，我肯定得是你们 team 里的一员、紧密参与你们的工作——我是给钱的，也是提需求的。进入开发阶段，你需要一个 admin；我不一定做 admin，但通常来说我就是那个 admin。再看一个更清楚的例子：学校的办公网。网站做好了，team 就撤了、没人管了？那网站不是迅速就死掉了？要一直活着，它需要几拨人——一拨开发、一拨维护。

- **support team / support specialist**：办公网站那边，办公室的人发现哪里死掉了、数据库好像乱掉了，反正就是弄不进去，他得打电话找谁？你总得有一个联系人守在电话那边，随时说"这个坏了"，你就派人去搞定。support team 一定要有，而且**它不一定是开发的那拨人，通常是两拨人。**
- **administrator / web master**：这是后台管理员这类角色。你自己人里一般没有 administrator，你得在用户那边找一个来做。
- **content developer / provider**：谁负责给网站提供内容？比如办公网挂的通知从哪来？谁负责把通知写好、准备好往上挂？网站只接受哪些来源的信息、谁有权提供内容，这要说清楚。不可能随便什么人都打个电话说"你给我挂个东西"，就挂上去。
- **web publisher**：提供内容的人不一定是把内容挂出去的人。学校里有一个稍微懂点技术的人，在后台操作，把内容发布到相对应的正确位置。
- **business domain experts（业务领域专家）**：不要一看到 business 就想到赚钱、想到市场。给计算机学院做网站，办公室主任一定是你 team 里的一员——他知道整个办公流程、哪个部门管什么事、哪部分内容该放哪里、什么东西可以放、什么不可以放，他掌握所有跟这个 domain 相关的知识。如果开发的是给学校做选课网站（含成绩管理、退学警告之类），那教务处处长、学籍管理处处长就是相应的 business domain experts，或者他们派的代表。content provider 只管把课挂上去、把选课学生导进去，他不一定知道整个流程的规矩；整个选课流程、成绩控制流程、各种通知发布流程，处长们最清楚。这些人你要请到团队里来。

| 角色 | 是谁 / 干什么 |
| :--- | :--- |
| Web engineer | 你的开发团队，核心干活的 |
| support specialist | 维护、守电话、坏了派人修；通常与开发是两拨人 |
| administrator / web master | 后台管理员（常常要从用户方找），如课程网站里管打分、统计的人 |
| content developer / provider | 内容来源方，决定谁有权提供内容 |
| web publisher | 把内容发布到正确位置的、懂点技术的人 |
| business domain expert | 最懂领域流程规矩的人，如学院办公室主任、教务处处长、学籍管理处处长 |

> **提示**：你自己人大概就是 web engineer 和 support specialist；administrator 往往得在用户里面找一个；business domain expert 更要从业务方请过来。这几种角色可能集中在一个人身上。

### 自己做，还是外包

开发管理的策略，你可以做 outsourcing（外包），也可以做 in-house（自己做）。

```text
   In-house（自己做）                 Outsourcing（外包）
   ────────────────────              ──────────────────────
   开发团队                           你的团队（需求、粗设计、进度）
   用户代表                                 │  通过 liaison 联络员传递
   其他 stakeholder                         ▼
        │                             ┌──────────────┐
        ▼                             │ 外包商内部     │
   全部坐一张圆桌，                    │ 核心内容封在   │
   核心问题全透明                      │ 里面，改动要   │
                                      │ 经联络员       │
                                      └──────────────┘
```

读图说明：in-house 时，这么多角色连同外部 stakeholder 的代表，都直接坐在一张圆桌上讨论软件的核心问题，对大家全透明；outsourcing 时不一样，软件核心内容封在外包商内部，你要改东西、做讨论，得通过他提供的 liaison（联络员）机制收集意见再传进去。

关于外包，我前不久在微博上看到一个挺搞笑的事：美国哪个公司的一个中国职员，每次把老板派给他的活直接外包到国内一家企业，然后这人每天上网、喝咖啡、玩游戏，到点就从外包企业把东西拿过来交差，只要把工资的一部分付过去就行。外包看起来这么轻松愉快，可能吗？这种事有可能发生，但如果直接把任务丢过墙、什么都不管，事情就能做得很好，我觉得这里头肯定有夸张。outsourcing 不是那么简单的事——不是说你大概知道要做什么，然后把大概知道的东西丢给承包商，就等着他把好东西拿出来。

我举个自己的例子。你们看我这个头发，现在长这么长了。我本来每年剪一次头发：夏天头发长长了盘上去，夏天结束就剪短，第二年再盘上去，每年剪一次，每次都去一个地方。前年我去剪头发时换了个地方，进去就跟理发师那个小帅哥说：你把马尾巴给我剪成羊尾巴。我的意思是马尾巴这么长，你给我剪成羊尾巴，你起码得见过羊尾巴有那么长吧？我说"马尾巴剪成羊尾巴"，他也没什么疑问，好嘞，就开始动手。我把眼镜一摘——近视眼理发的痛苦——闭目养神，过一会儿他说理好了。戴上眼镜一看，我说你管这个叫羊尾巴？这不是兔子尾巴吧？太短了，给我剪没了。他要是说这是小羊的尾巴，那也没错，我们没说那个羊有多大。于是悲剧了。所以搞到我一直到现在这头发都不用剪，夏天盘上去正好——你们就知道当时他给我剪得有多短。

这其实就是一个 outsourcing 的过程：我的任务是想把头发剪短一点，我自己也能剪，但嫌麻烦、剪不好，所以外包给一个专业理发师。这里面我也犯了错误，理发师也犯了错误，最后演成一个悲剧。把这个当练习：作为外包方和作为承包商，我们分别犯了什么错？这类错误本来可以怎么避免？如果做的是软件而不是剪头发——我给了对方一个很简短的说明，相当于"把马尾巴剪成羊尾巴"，对方什么也没问就说好嘞开干，我中间闭上眼睛什么也不管，就等着一个结果，结果出来是个兔子尾巴——双方都犯了哪些错、该怎么避免？

最关键的一点，**千万不要以为外包了你就可以没事干**。

- 你在外包之前，一定要自己内部先把事情搞清楚：自己还是要 gather requirements，自己要知道到底要做的是个什么东西；自己心里要有一个 rough design——虽然 rough，它也是一个 design，大模样你得知道；还要有一个大概的 schedule。这样出去跟人家谈条件、谈价钱时才不至于太离谱。
- Web App 不是一次性交付就没事了，它每次要交一个 increment，每个 increment 到什么程度，你自己大概要有个定义。
- 搞清楚责任划分：自己人负责哪些事，外包商那批人负责哪些事，一定要划清楚，否则最后就打起来了。
- 双方要有一个联络机制，联络员机制要定义好。
- 大概准备好之后，才出去找外包商。找的时候要注意：**多找几个，别盯死一家**。要关注他报的价钱，以及这个价钱到底有多可靠——他报了个很低的价格、很短的时间，你就要考察他这个团队以前的声誉，他做不做得完、做得了吗。资质和报价都要先搞清楚。
- 想清楚交给他以后，你在多大程度上还能掌控这个 project，在什么程度上你还能对它做 management。
- 最后看一下 schedule 是否合理——前提是你自己知道一个真正合理的 schedule 长什么样。要有 management，但外包商一般不会让你把手伸进他公司里管那么细的进度；不过 scope 你是要管的，大致的进度也要管一下。

in-house 呢，其实跟传统差不多：要知道 scope（大概范围）、哪里最常要改、有什么限制条件；要 incremental 化，定义每一个 increment；risk analysis 是最重要的一点；还要有一个宏观的 estimation——这个软件大概是什么规模、需要多少人力物力，毛估估就可以；再定义一个 task set，把它分解成若干任务，并控制任务进度。怎么知道完成了百分之多少？最常见的一个做法是 **count use cases**——看有多少个 use case 已经走完了。当然这不一定是准的，取决于你的开发策略，你不一定按 use case 的线索来开发，这个到时候再说。最后还要有一个 change management，后面专门再讲。

### 最佳实践与最差实践

回到 Web 工程的做法本身。做得比较好的团队，通常是怎么干的？

前提是：时间很紧，要在很短的时间里做很多事情。在这个前提下——

- **要花时间 take the time to understand the business needs and product objectives**：大方向先搞清楚，这个时间不能省。细节问题可以慢慢来，但看准大方向这个时间省不得。
- **用 scenario-based approach**：做一系列 user scenarios、一套一套的 use cases，然后根据这一套套 use case 来做整个规划和开发。
- **先有一个 plan**：虽然时间短促，也要先有个 plan。它跟传统软件工程里那种非常严格的 plan 不是一个数量级，它是轻量级的，但你必须要有，不能直接动手就干。
- **动手之前稍微做一下 modeling**：哪怕你的团队很轻巧、很小巧、人很少，也要想到后期是一个长期维护的过程——开发用了一个星期，你总不希望这个网站只活几个月，也不希望它只有两三年。就说我们的 ZOJ，那个 online judge，玩 ACM 竞赛的同学都很熟悉。它最早是 2001 年投入使用的，现在多少年过去了，早就不可能是原来那个团队在维护了；当然它也换过好几个版本，2.0 版本是 2008 年上线的吧，到现在多少拨学生毕业了，当年开发团队的人早走得一干二净。所以后期维护你还是需要留一定的文档、留一点东西给后面的人看。modeling 可以写得简单，但一定要有。
- **有一个大致的检查**：consistency 和 quality 方面——一致性，以及模型的整体设计质量，要有一个把握。
- **尽可能找已经做好的、可重用的模块**：这是"快"的根本。我们有个学长毕业以后自己开公司，专门给老师们做各种课程网站，因为他专注这一个领域，很多共性可以保留下来重用，后面就做得越来越快。
- **上线之前，内部一定要做过很好的、充分的测试**：不能把测试留给用户——直接挂出去让用户一用就挂掉，瞬间挂掉之后，至少一大半人不会再来了。这个测试跟普通软件测试还不太一样，也更困难一点，难在哪后面专门讲。

最差的实践，也就是不要犯的错误：

- "we have a great idea，所以就开始干吧"——你得先想好钱在哪；做出来有没有人用、能不能赚到钱，这些先想清楚，然后再开始做。
- "反正需求总是要变的，所以没必要把需求搞得特别清楚"——你如果太不清楚，后面不必要的变更（unnecessary changes）反而会更多。
- "传统软件开发做得很好的那批人，直接拿过来做 Web 开发，不需要经过任何新培训"——书上认为不太可能，说这两样东西 they are different。这一点我个人没有特别深刻的感受，留给你们将来去验证。
- 作为 manager/领导，什么都官僚、程序化，走固定的流程——你在 IBM 那样的大公司里也许可以，但如果开发的是小型轻量的 Web App，最好是鼓励大伙加油，然后你靠边儿，别捣乱，以快为准。
- "testing web bother"——自己内部测试做不好，就拿出去让用户去测，那可能是一个很大的悲剧。

### 需求分析：任务一样，松紧不同

上一节我们把 Web App 分析了一圈。因为它要求快，所以它的 analysis model 不要求特别严肃、正式，不要求特别详细、严谨，有就可以。这一节重点看它不一样在什么地方。

需求分析的主要目标，跟普通 project 没有两样：一开始要有一个 formulation，大概了解要做什么，很快；然后有一个 requirements gathering，所有人坐到一起，说清我们到底要做一个什么样的东西；然后给出一个 analysis model。这些任务看上去一样，**但要求的程度不一样**。

formulation 里，除了要知道 goals and objectives——一个是大的目标（我们为什么要做这件事），一个是 objectives（我们要做成哪些事，具体一点的目标）——不一样的地方是它要特别做一个 **categories of users**，做出一个 user hierarchy（用户层次）的图。因为上网你不知道会有什么人来用，但你心里要有数，要把用你系统的用户大约分一分类。

书上继续举 SafeHome 那个家居保安系统的例子：它给保安系统在网上做了一个商店，你可以到网上去定制、购买。这个网上商店，总的来说顶层是 SafeHomeAssure.com user，往下分三大类。

```text
                  SafeHomeAssure.com User
                  ┌─────────┼──────────┐
                  │         │          │
               Guest    Registered   Customer
              （访客）    User       Service
                        （注册用户）  （客服）
                            │
                     ┌──────┴──────┐
                  Novice        Experienced
                （新手用户）     （老用户）
```

读图说明：顶层是网站用户；第一层分访客、注册用户、商场服务人员三类；注册用户还可以再细分新手与老用户，给他们提供的 service 略有不同。当然，如果你的网站很简单、新手和老用户进去看到的界面和权限都一样，那就没有必要再分。要做细致一点，是可以给两类人提供不一样的 service 的。

### use case 是一切的基础

对 Web App 来说，最重要的事情是 use cases。Web App 后面很多东西都依赖于你这一套 use case 的设计。对前面分出来的每一类 user，你设计一套它自己的 use cases。

use case 会用在什么地方？写程序时照着它写吗？肯定不是。设计的时候要用到它；analysis 那一部分也要用到它——写需求时里面有至少四大类模型，其实每一类模型都跟它有关系，都能从里面得到很多信息；测试的时候也用它测——黑盒测试就是一个 use case 一个 use case 地走。

它还是判断进度的最简单指标：你怎么知道一个模块完成了百分之多少？数 use case。我一共设计了 100 个，现在走完 60 个，那就说进度是 60%。当然这不很准确，因为每个 use case 难度不一样——注册一个新账号非常简单，可进去以后做一大堆操作、最后买了个东西走，这一串测起来就比较复杂。但总体来说，use case 是所有事情的一个基础。

书上给了一个设计 use case 的例子：一个 new customer（新手）注册进来，大概要做这么几件事——log in；查看要买的东西的描述性内容（展示部分）；建立 configuration（他是新手，先要配好自己想要的 SafeHome，挑好几个模块，存一下）；recall saved configuration（回头看一下刚才存的东西）。

其中两个功能比较复杂：customize SafeHome（定制一个个性化的 SafeHome 系统）和 purchase configuration（把配置定好之后来买）。它们在图上画不下，就各用一个信封口袋装起来，这叫一个 **package**。如果一个 actor 要做的事情比较复杂、画不下，你就把复杂功能各放进一个 package，介绍的时候再一个一个包打开，讲里面详细是什么内容。这就是 use case 大致的画法。

> **易错点**：use case 要做得全面、保证没漏掉什么，是一个比较复杂的过程。我们这个课只告诉大家"有什么"，具体怎么做，你自己先去摸索着。

画 use case 有几个原则。首先，每一个圆饼对应的都是一个模块——你要实现它的一个操作，就可以认为这是一个模块。

- **comprehensible**：你画的图要让人看得懂，别画得太乱、太复杂，取名也别含糊。
- **cohesive（内聚性要强）**：一个 package 里的东西基本都比较集中，服务于同一个任务、目标比较集中，而不是把几个互不相干的目标零七八碎地塞在一起。
- **loosely coupled（耦合要松）**：package 与 package 之间、功能模块与功能模块之间，最好不要太紧密。一个 package 里面关系要密切，package 之间不要有太多千丝万缕的关系，这样大家的分工会分得比较干净。

> **提示**：内聚和耦合这两个词，后面讲设计时还会详细展开，这里先记住有这两条原则，顾名思义地体会一下。

- **hierarchically shallow**：层次不要太深。use case 最好不要有太深的层次。层次太深意味着什么？用户真的去用的时候，是一条线索一条线索走下来、要完成一件事；层次非常多，就意味着他想完成这件事，中间要点点点好几个环节才终于做成，这很烦人。尤其对 Web App，这一点更重要——你不能让用户觉得很烦。再叠加上网络带宽的影响，如果访问还很慢，我点一个链接要等半天，还要点 10 个链接才做成一件事，大家就不用了。一个线索设计得太深，测试起来也很痛苦，会很麻烦。

### 分析模型要建哪几种

有了 use case 做基础，就可以在上面做 analysis models，大概有这么几个方面。

#### 内容模型

content objects：基本上就是把什么东西作为你的 class、作为系统里的 object 存在。你可以从 use case 里抽——你觉得哪些东西是。然后把它们之间的 relationship 搞清楚。除了做数据库用的 ER diagram，书上还介绍了一种叫 **data tree** 的东西，其实很简单，就跟一个 struct 差不多：定义一个 struct，叫 component（家居系统里的一个模块）。

```text
        component
        ├── part number    （数字）
        ├── part name      （字符串）
        ├── price          （数字/字符串）
        └── description    （真正的 data object）
```

读图说明：白框里那些（part number、part name、price 等）其实不是复杂的 object，就是一个数字或字符串；黑底的 description 才是真正的 data object，是你要专门去设计的东西。把 data tree 画出来，就能一目了然地看出最后要设计的 data object 有哪些。

如果系统比较复杂、你想弄得比较全，还有一个办法：写一个 parser（词法分析器），把 use case 整个过一遍，把里面相对应的名词抽出来，去掉那些一个数字、一个字符串就能解决的，剩下的再考虑是不是要设计成系统里要处理的 data object。

#### 交互模型

interaction model 要描述用户跟你这个网站之间的交互，一共有 four elements（四个元素）。回想一下我们在 analysis model 里学过的那些图，有哪些可以用来描述 interaction？

- **use cases**：这是必须的。
- **sequence diagrams（时序图）**：随着时间推进从上往下走，每个动作涉及哪几个角色，像游泳的泳道一样一道一道排着几个 actor，往下走时看谁做了哪个动作、产生了什么。
- **state diagrams（状态图）**：描述状态迁移。对 Web App 来说，就是你做了一个什么动作，它从一个页面转到另一个页面——也就是页面之间的跳转。
- **user interface prototype（界面原型）**：最直观的一个。你把 prototype 做出来，就知道这个 interaction 是什么样了。

> **提示**：别把 control flow 跟 data flow 搞混。data flow 是你内部功能与功能之间的转换、数据怎么变；control flow 才是系统在几种状态之间转换——对 Web App 就是页面之间的跳转。

我们给老先生做的那个东西虽然不是典型的 Web App，但 interaction 这一部分比较复杂；这些图我们其实都画，use case 也没写，可我们做了一个很有用的 interface prototype，这就把问题都解决了。

#### 功能模型

functional 比较传统。但你要注意到一点：Web App 做需求收集时，你收集到的基本是 user observable functionality——用户看得到的功能，是用户跟你说的他要的功能。可你整个系统真要做到这些事，后台还有一些动作要做，这些后台动作你也要准备好。所以这里你基本上要准备**两个层次的 functional**：一个是用户可见的，一个是背后支持的（contained within），那些 operations 也要准备好。一般用一个 activity diagram 去描述 functional model。

> **提示**：说 Web App 的时候，所有这些 model 都没要求那么严格，因为你要快。大概画个草图，小团队大家沟通一下，你能看懂、我能看懂就可以了。

### 配置分析与导航分析

#### 配置分析

configuration analysis 是 Web App 比较特殊、比较重要的一个部分，传统软件不太讲这个。因为传统软件就是给这家公司做的，环境固定，我事先知道就行；网站不一样，你不知道你的客户端是什么样子，不知道客户用什么操作系统、什么浏览器，所以要保证各种人打开都好用。这其实是一件很痛苦、很不容易做到的事情。

configuration 分两个端来考虑。

- **server side**：需求分析阶段不用特别具体，但要大概说清——对硬件要求是不是特别高、服务器性能要到什么程度、在什么操作系统上、是不是还要用到别的什么应用和数据库及版本、它们之间的通信协议是不是网络通信协议等。
- **client side**：先要列一个清单，我要照顾到哪些浏览器。你肯定不能照顾周全，只能说肯定照顾哪几类。比如 `IE6` 我干脆就不管了。我们现在开发 OJ 新版本的同学就直接说 `IE6` 太讨厌了，不要它；所以你要是用 `IE6` 打开，页面上会出现一行字，说检测到你用的版本居然是 `IE6`，建议你重新安装一个新的浏览器，下面还给一个链接。好多地方都开始鄙视 `IE6` 了。你做新网站时，现在用的浏览器早晚也会过时，所以照顾哪些、不照顾哪些，要有个规划。操作系统也要考虑，`Windows` 是一种解决方案，用 `Unix`、`Linux` 打开会不会有影响？还取决于你要展示的东西——比如需要 `Flash`，本地没装 `Flash` 就显示不出来，那时候怎么办？所有这些都是做 Web 应用时要考虑的：想让它正常显示、正常使用，客户端需要什么配置；没有这个配置，我怎么检测出来；检测到没有，又怎么解决。
- 另外，你基本上要有一个**测试计划**：怎么把你要照顾到的这些环境全部测一遍。

#### 导航分析

navigation 是 Web App 比较特殊的一个问题。一个非常复杂的普通软件也有导航问题，但没这么明显，也不需要做得那么傻瓜——因为普通软件一般给固定的单位做，你可以训练他的员工，告诉他你这个角色要做什么工作就点哪几个键，训练熟练就好。网站没法训练任何人，所以你得做得充分傻。

navigation 的意思就是：让人家在你网站里跑来跑去的时候不能跑丢。一是他得非常容易地找到想找的东西；再一个，他找了一圈之后想起来"我要前面那个"，退不回去了，不知道自己现在在哪，刚才明明见过、记得在哪见过，就是找不着了——退回首页，然后死都找不着原来要找的那个东西，这就很恶心。这方面需要一个专门的 navigation analysis。书上的建议缩写叫 RNA，大概有这么几部分活：

- 先分析你所有的 stakeholders，也就是分类；
- 再分析大概有哪些数据、哪些功能；
- 比较重要的是分析 relationships：网页与网页之间是怎么跳转的，不同种类用户的交互之间有没有互相影响；
- 然后决定这个网站浏览的复杂程度，有没有必要做什么特别的工具来辅助导航。

导航设计后面讲用户界面设计时会专门讲，它有一些特别的技巧。除了技巧之外，还要不要一个 map？有些 BBS、有些网站做得比较好，有 map，你直接调出整个地图，所有分支一目了然。有的是树形结构，树形结构是程序员比较喜欢看的；可要是给幼儿园小朋友看，他不一定喜欢——给小朋友的网站做地图是另一种画法，要画得真像地图一样，再准备各种链接跳到他想去的地方。至于要不要做这种东西，是你在分析阶段把各种 relationship 分析完、看清复杂程度之后再做个决定。

#### 评价分析

最后还有一个 evaluation analysis。网站做得越友好，说明你照顾到的人群越多；可你要照顾到越多人群，工作量就越大，会给自己找好多事。时间有限、人力有限，做完之后要算一下投入产出比、合不合算，也就意味着你这个 navigation 要做到什么程度就差不多了。

所有这些都是 analysis 阶段最好都做的事，但并没有要求你写一个 100 页的文档出来——通常也没人这么干。可这些事情你都要**考虑过**。至于用什么图去描述这些 relationship、怎么设计 navigation，到设计阶段再讲得更详细，这里大概分析一下要不要做这些事情就可以了。

> **结论**：Web App 需求分析最重要的就是这两件事——一套套 use cases，以及在它基础上建立的各种模型（内容、交互、功能、配置、导航）。它们要做到什么程度，由"快"这个总基调决定。

### 设计阶段要盯紧的特性与目标

上一次课我们介绍了普通青年的架构设计怎么做。这本书始终把 Web application 当成一个"文艺青年"来特殊对待，所以我们用一节课来讨论 Web App 在设计上有什么特殊、它的 design model 怎么建立；之后还会停下来讲一点 project management。

同样是 web application 那一大串特点（十几条），在 design 阶段要特别强调、重视的是哪几条？做个 online judge 网站（PAT、ZOJ），特别要紧的是哪几件？

- **security**：跑考试、跑竞赛，不能被人考前进去把题目直接拿出来，要防各种攻击、防黑客。
- **并发/scale**：好几百人疯狂提交的时候，你怎么处理这种大规模的并发？（我考 PAT 时，考场纪律里总会宣布一句：按照国际惯例，最后 10 分钟系统崩溃我们是不补时的——你就知道这种事情有多实在。）
- **availability**：基于网站的东西一般不能三天两头挂掉，偶尔挂可以容忍，三天两头挂大家就不来了。
- **scalability**：一两个人你能弄，一两百人你就挂掉，那不行；你要知道访问量的变化范围，能不能应付。
- **time to market**：网站一般都要求得比较急，时间很短。这也意味着设计时要尽量简单，把主要功能完成。

于是 design goals 有这么几点：

- **simplicity**：尽量简单，不要把事情搞得很复杂。
- **consistency**：内容、美工、整体架构、interface、navigation 都要设计，可能交给不同的人、不同的组去完成，但你从始至终要保持一致。
- **identity**：设计要使软件呈现出来的风格符合 domain image——符合这个领域给人家固有的形象。你不能把银行系统做得五彩斑斓，那看上去就不像一个银行，人家会怀疑这银行靠不靠谱。
- **robustness**：健壮性，Web App 特别重要。
- **navigability**：导航性——不需要有人教，他自己就能在你系统里跑来跑去还不迷路，Web App 特别重要。
- **visual appeal**：网站要做得漂亮，这没什么好说的。
- **compatibility**：因为用户群不可控，他用什么的都有，什么操作系统平台都有，用 `IE6` 的老古董也可能有（比如我），所以要清楚你的设计要照顾到哪些层面的人。

> **提示**：robustness 和 navigability 在普通软件里也是要的，但它们的重要性没有在 Web App 里这么高。为什么？这是个我留给大家的思考题。

答案其实就两句话：**因为你的用户群不可控**。

robustness 要做到位，是要花钱、花人力的——你要做到什么程度。两个东西都要 robustness，可要求显然不一样。比如给你一套银行柜员用的系统，用户群可控、就这么几个人，我可以少花时间在 robustness 和 navigability 上，做完以后给内部人员做个 training 就够了：手把手教你怎么用，告诉你什么键一定不能点错、什么东西在哪，这套培训材料还能留给新员工照着学。所以 robustness、navigability 差一点不要紧——你说什么东西不太好找，我告诉他在哪儿。

可支付宝是上网用的，你根本不知道坐在电脑前面的是美女还是个抠脚大汉，甚至不知道是个人还是一条狗；你不知道他会按什么键，也不知道他是什么样的搜索习惯。所以你的 robustness 要求就特别高，要应付各种各样、甚至各种各样的变态用户；你还得让各种"白痴"都能在你网站里进出自如、容易找到他要找的东西。这一点特别重要。

web design 有这么多东西要设计，它画了一张金字塔。

```text
                    ┌──────────┐
                    │   User   │   用户
                    └────┬─────┘
              ┌──────────┴──────────┐
              │   界面设计 / 美工设计  │
              └──────────┬──────────┘
         ┌───────────────┴───────────────┐
         │      内容设计 / 导航设计         │
         └───────────────┬───────────────┘
                    ┌────┴─────┐
                    │Technology│   工程师
                    └──────────┘
```

读图说明：顶端是用户，下面是界面设计、美工设计，再往下是内容设计、导航设计，越往下越靠近工程师，最底下是 technology——真正干活的人。下面把它们一个一个过一遍，先从 interface design 开始。

### 界面设计：让用户随处答得上三个问题

interface design 对 Web App 特别重要的一点是：你设计的整个系统里所有页面，都要能让用户在任何一点停下来的时候，都很清楚、很轻易地回答三个问题。

- **Where am I?（我在哪儿）**：要让人很容易知道、不迷路——随时告诉他，他在整个系统里处于什么位置。常见的办法你看行政办公网：随便点一个链接进去，上面有一行小字"当前位置"，比如"首页 > 学术机构"。它不但告诉你你是点了学术机构进来的，还告诉你学术机构是放在首页下面的一个链接，路径也告诉清楚。办法还有很多种，我觉得最有效的办法是：你要开发一个网站时，先去找若干跟你相似的网站，看人家是怎么做的，学习人家的风格。
- **What can I do now?（我现在能干嘛）**：在这个位置、这个页面，提供给他可以点击的东西，并且很清楚地展示 what functions available、what links are live、what content is relevant。你回想一下，这不就是句废话吗？你要把一个按钮做得像按钮，把链接做得像链接，把下拉框做得像下拉框——把每个东西做得像它本该是的样子。你觉得这是废话？那只能说你互联网逛得还不够多。你会看到各种奇葩设计：看上去明明不是链接，一点居然是个链接（有的还故意藏起来）；告诉你点某个按钮，你找哪儿都找不着，最后发现原来那坨东西才是按钮；看着是文本框、该输账号了，鼠标点上去光标闪啊闪，敲什么都没反应，仔细一看旁边有个很小的小箭头，一按原来是个下拉框。**不是说这件事很显然。** 你要做的是：把它应该是什么、用户大多数人在互联网上逛习惯了认为它应该是什么样，做成那个样子。
- **Where have I been? / Where am I going?（我去过哪、还能去哪）**：最简单的机制，就是现在不管用什么工具做网页都默认的——点过的链接变紫、没点过的蓝色，这就是一种告诉你"哪些访问过、哪些还能去"的机制。太复杂的网站能提供一个 map 就更好，当然 map 也不是人人都喜欢，map 本身的设计也很有学问。

总的来说，interface design 的原则就是：让用户访问到每一个页面时，都有很清楚的一些指示，告诉他我在哪、我在这页面能做哪些事、哪些是我已经走过的地方、我还可以去哪些地方。这三个问题是重要的问题。

跟普通青年的 interface 相比，Web App 的界面设计有几个很重要的特点：

- **effective interface：visually apparent and forgiving，give users a sense of control**。让用户很快看到自己有多少选择的余地（breadth of options），能 grasp how to achieve their goals and do their work。事情要清楚明白，而且还要允许他点错、允许他犯错误。有一条设计原则就是：**把你的用户当成白痴**——如果白痴都会用，那不白痴的用户应该用得更舒服。（顺带说，iPhone 其实违反了很多设计原则，但它不是 Web application，所以我不在这儿批判它。）
- **effective interfaces do not concern the user with the inner workings of the system**。普通软件里你可以随时提醒他"你改了什么地方，存一下"，专门弹个窗问 do you want to save your change？在网站里，要求更高——你根本不要提醒他，默默就替他存了，而且还要让他在任何时刻可以反悔。这是非常高的要求。
- **perform a maximum of work while requiring a minimum of information from users**。让用户做的事越少越好，用最小的精力完成尽可能多的工作。普通软件也最好这样，但对 Web App 特别重要——因为你在网上让他多点一下，不仅依赖你服务器的反应速度，还依赖网络速度。赶上哪天网络抽风，本来点开一个链接就很慢，你还让他多做一步完全不需要做的事，人家就不能容忍。所以让用户完成一个目标的动作，一定要尽可能少。

用户，尤其是互联网上的用户，你可以想象得要多白痴就多白痴——起码在计算机专业这方面，他可能是完全彻底的电脑小白，但他也有权利使用你这个系统，因为你是 published 给全世界、对所有人公开的。所以不要说他故意捣乱；如果他很容易就犯了错误，那是你设计得不好。**你不想让他破坏的东西，就绝不要给他破坏的机会——根本不要让它出现在你的页面上。**

控制机制（control mechanisms）最简单的就是 navigation menus（导航菜单）；除此之外，`graphic icons`、`graphic images` 都可以作为你跳转控制的界面，还有更 fancy 的东西。

### 界面设计的推进流程

界面设计大概的流程是这样：

- review analysis model，做 refinement——看一下你的需求分析。
- 先动手画一个 **rough sketch of the interface layout**。为什么叫 rough sketch？因为你没时间，开发时间很短，你大概粗略地画一下界面整体布局：要不要一个 banner？横着要不要一条功能带？竖着要不要一栏、放左边还是放右边？中间到底放什么东西？
- **map user objectives into specific interface actions**：做一个一一对应——这个网站给用户提供哪几件事可以完成，每一件事在你网页上对应的是哪个链接或按钮，用户通过点哪一个可以达成这个目标。
- 再往下：用户点了一个按钮进去以后，为了完成这件事，他后面还要做好几件事。比如"buy a component"，点进去之后他还要查看、选择、放进购物车、结账，然后填各种信息、银行卡信息、邮寄地址等等。这一系列动作是什么，要一条一条理出来。
- **storyboards of screen images for each interface action**：storyboard 就像拍电影导演画的分镜头脚本，大概说明跟这个界面交互时，屏幕上会出现什么状态。不同导演画分镜头的风格差别很大，有的人很草、有的人很精致。
- refine：根据美工的设计再做一个细化。
- 抽取 **interface objects**：面向对象的开发通常这么做——把跟 interface 相关的对象抽出来，开始做模型。
- 画什么图取决于你。时间很紧，不要求画非常正式的图；不管画什么图，你都要用一种方式去描述用户跟 interface 做交互的流程，还要有一种东西去描述它的 behavior，也就是动态模型（相当于我们以前说的 state transition、状态迁移图之类）。每一种状态下 interface 长什么样、是什么样的布局，也要有描述。
- 然后 refine、review，不断把它细化。

> **提示**：这几步里，**map user objectives into specific interface actions** 和"点进去之后的一串动作"这两步最重要，其余是包围着它们的铺垫与细化。

### 美工设计

美工设计听上去跟我们没什么关系——仿佛应该是工业设计专业或者艺术类同学帮我们干的事。但我得说，我接触的大多数工科学生实在非常没有审美观。不是设计网站那种审美，而是写论文时排版都不知道什么叫丑：画了个结构图、一个方框，文字却写到方框外面去，一直冲破那个框。我把一个学生叫到办公室，把他论文放我电脑上，说你看看这一页，不觉得有什么问题吗？我们可怜的孩子瞪着屏幕看半天，没看出来，说哪里错了？我说你把字写到方框外头，不觉得难受吗？他不觉得，说还好啊。我说那你画那个框干什么呢？干脆别画那个框也好一点啊。我不知道我算不算强迫症，但看着实在难受。

这一节不可能用一两分钟就马上培养出什么样的审美观，只讲一些必须注意的事情——你最起码要有一点品味。

- **don't be afraid of white space**：不要老想着把整个屏幕的边边角角全部填得满满当当。留点白，留白不是坏事，留白是一种品味。留多少可以商量，但总之不能全填满——有密集恐惧症的人看着很难受。
- **emphasize content，不要喧宾夺主**：你要知道这一页重点展示的是什么。本来要展示一段文字，你却做了一个特别 fancy 的 banner，上面还有个 flash，结果人家访问完，所有人都记住了那个 flash，网站到底干嘛的没印象——这就叫喧宾夺主。
- **organize layout elements from top-left to bottom-right**：绝大多数人的阅读习惯是从左上角往右下角看，所以你放东西的顺序也从左上往右下。当然，如果你存心要吸引眼球、从右下角开始往左上堆，那是另一回事。
- **group navigation, content and function geographically within the page**：凡是跟 navigation、内容、功能相关的东西，相同功能的东西最好在几百个页面里都放在差不多的位置。举一个极端例子：你有个"下一页"按钮，通常在上面读完了、读到下面发现有下一页就点它；结果进到下一页，下一页按钮跑到上面去了，再下一页又跑到左边去——那个按钮在屏幕上跳来跳去，你的第一反应是"这个设计师好萌，在跟我玩捉迷藏"，让我满屏幕去找下一页的链接在哪。如果几百上千个页面分给不同人做、风格没统一，就会造成这种后果：人家用你网站的过程中风格不断变、位置不断变，用得很累。**这是不专业的一个表现。**
- **don't extend real estate with the scrolling bar**：一页显示太长就得用下拉条。你特别想炫耀、觉得特别重要的东西，最好不要让它一直拉到后面。虽说有句时髦话叫"亮点总在最后"，但不是所有人都有耐心等到最后去看你的亮点。你特别想表现的东西，要想办法让它出现在最上面、最醒目的位置；哪怕它的位置适合出现在下面，也可以在前面先放一个提示性的东西，用一个链接连到下面去，人家关注就直接跳过去看。总之最好一上来就让人看到你最想让他看到的东西。
- **consider resolution and browser window size**：不同的浏览器、不同的分辨率，做美工设计的时候都要考虑到。

### 内容设计与架构设计

content design 其实没有太多好说的：基本上就是用 UML，把跟内容相关的东西抽取出来、设计成一个 class 或者 object，然后定义好它们之间的关系。

architecture design 有两大类。

一类是 **content architecture**：一个 content object 差不多相当于一个网页，整个网页与网页之间的整体结构有几种。

```text
  linear（线性）        grid（网格）
  ○──○──○──○           ○──○──○
                       │  │  │
                       ○──○──○

  hierarchical（层次）   network（网状）
        ○                  ○─────○
       ╱ ╲                ╱ ╲   ╱
      ○   ○              ○───○───○
     ╱ ╲                  ╲ ╱ ╲ ╱
    ○   ○                  ○─────○
```

读图说明：linear 是一条线走到底；grid 是行列式的网格、节点风格；hierarchical 是层次感非常强的树形；network 是关系比较复杂的网状。

另一类是整体的 **application architecture**。普通软件我们说整体架构时，是从一个数据流图翻译成 call and return structure 之类；网站不是这样。比较流行的一种架构风格叫 **MVC（Model View Controller）**——经常听人家说"我这个网站是 MVC 架构的"。它的意思就是你把整个系统分层来设计，至少分三层：一个前台、一个后台，再加一个中转的 controller。controller 衔接前台跟后台：它接受用户从前台输进去的需求，由前台传给它，它去调用后台的程序、从后台获取数据，再传到前台展示给用户。

```text
   用户
    │  输入请求 / 看到页面
    ▼
  ┌──────────┐   请求    ┌────────────┐   调用    ┌──────────┐
  │  前台 View│────────▶│ Controller │────────▶│ 后台 Model│
  │          │◀────────│  控制器     │◀────────│          │
  └──────────┘   展示    └────────────┘   数据    └──────────┘
```

读图说明：用户只跟前台打交道，前台把请求交给 controller，controller 调后台取数据，再把结果交回前台展示——搭架构时就是一个后台、一个前台、中间一个 controller。

### 导航设计：语义层与语法层

navigation 是 Web App 比较重要的一个特点，大概有两个层面的东西要考虑：一个是语义方面的，一个是语法方面的。

**语义层面**有一个工具叫 navigation semantic units，缩写 **NSU**（不是 NUS）。它官方的定义是 a set of information and related navigation structures——描述一套跟信息以及信息之间的导航关系。实际上，你要对每一个 use case、每一个 actor 的行为，去对应一套 NSU。

书上给了一个例子，字比较小、你不用看清那些字，看结构就行。它对应的就是你一个 use case 里的描述：用户到网上购买 SafeHome 家居保安系统几个模块的购物流程。

```text
  (actor)
     │  首页上的一个链接
     ▼
  [select room] ──▶ Room 页面
                       │  链接：recommend components
                       ▼
                  [推荐的模块] ──▶ Product Component 页面
```

读图说明：actor 在某个位置，箭头表示一个 navigation link——首页上有个链接点了要完成什么事（先 select room），点完进入 room 页面；room 页面上有好多链接，点了其中一个 recommend components（推荐这个房间装哪几个模块），就进入它推荐的某个模块，打开描述 product component 的网页。全部通过链接去完成功能、跳转到某个网页。通过这张图你能清楚看到：用户要完成一个 objective，会涉及哪几**类**页面（不是哪几个页面——room 有很多种，room 是抽象出来的 content object），以及在这些 content object 之间用什么链接做跳转。这是 navigation design 一个很重要的工具。

**语法层面**就是：你有什么机制可以去实现这些？最普通的就是 **individual navigation link**——做一个链接，不管是文字的、icon 的、按钮的还是别的；再有就是 **navigation bar**，水平方向的一条，建议放你比较重要的几大类功能，最好不要超过 7 个、大概 4 到 7 个；垂直方向还可以有一个 **navigation column**，不管你习惯放左边还是右边，里面可以放基本上所有的 major content objects、重要的链接和功能。

这里有个问题：为什么水平方向建议最好不超过 7 个，而竖着放多少都可以？

> **提示**：因为鼠标滚轮是竖着的。你当然也可以设计成竖着滚却产生横向移动的效果，但用户的动作是垂直的、看到的却是横向移动，动作跟看到的结果不一致，会觉得很难受。所以**横向一般要在一个屏幕宽度里面解决，纵向可以上下滚**。

除了这些，还有 **tabs**——像很多卡片摞在一起，上面有一个个标识，一般也不超过 5 个、3 到 5 个页面。还有 **site map**，也是帮大家随时知道自己在哪里的机制。

### 组件级设计

component-level design 其实没有太多要说的，基本上跟我们普通青年的 component-level design 差不多，只不过对 Web App，大概把它分成了四大类 functionality：

- 需要**动态生成内容**的 component；
- 提供**计算功能**的 component；
- 做**数据库查询**功能的 component；
- 跟**外部系统做沟通**的 component。

详细设计后面专门再讲。关于 web application 的 design，大概就说这么多。

## Web 应用软件测试
> 对应块：BLK07 | 覆盖分集：P25-P27

前面我们把普通软件的测试整块讲过一遍了，今天又回到 testing，讲的是 testing for web apps。普通软件的测试，算是"普通青年"的测试；Web 应用的测试，算是"文艺青年"的测试。它到底哪里不一样？不一样的地方，一定取决于 Web 应用相对于普通软件，有哪些特别要强调的特性——那些特别的地方，就是测起来会不一样的地方。

所以在讲怎么测之前，我们先得回答一个问题：一个好的 Web 应用，质量到底要从哪几个方面来考察？

### 一个 Web 应用好不好：质量维度

把 Web 应用的质量拆开，大致是这么九块。内容得好；功能得齐全、稳定；结构得合理，整个组织架构要有充分的扩展性；可用性（usability）要过关；可导航性（navigability）重要；性能（performance）重要；兼容性（compatibility）是 Web 比较特殊的一块；互操作性（interoperability）指它跟其它应用软件、跟数据库的交互；最后是安全性（security），把一个东西放到网上，你不怕丢钱吗，这是必须的。

| 维度 | 关注点 |
| :--- | :--- |
| 内容 content | 内容本身要正确、完整 |
| 功能 function | 功能齐全、稳定 |
| 结构 structure | 组织架构合理，扩展性充分 |
| 可用性 usability | 用户能不能自己学会并把界面走通 |
| 可导航性 navigability | 页面之间的跳转是否顺畅 |
| 性能 performance | 各种负载下服务器的表现 |
| 兼容性 compatibility | 不同客户端环境都能用 |
| 互操作性 interoperability | 与其它软件、数据库的交互 |
| 安全性 security | 抵御攻击、保护用户与数据 |

这里要专门说一下 usability。普通软件里的可用性，往往和 availability 混着谈——一年宕机不超过多少分钟，就算够用。但 Web 应用的 usability 强调的不是这个，它说的是界面的设计要达到一个目标：**Each actor can learn and apply all required navigation syntax and semantics of the interface**——每一个使用者都能自己学会，并且运用界面里全部必需的导航语法与语义。

为什么 Web 要这么强调？因为放到网络上的东西，你不知道谁来用。用户群是分散的、不可控的，你没有机会把他们集中起来统一培训一遍。所以你只能指望界面本身做到：用户自己很容易学会上手，并且能顺着自己的想象把界面走通。这就是 Web 的可用性。也正是这种"不知道谁来用"，让导航（navigation）在 Web 里格外重要。

### Web 测试难在哪：环境、配置与错误定位

九条质量维度，几乎每一条都有 Web 独有的味道。但真正让测试、维护团队最头痛的，往往不是内容、也不是功能，而是 configuration 这一块。

问题出在哪？通常你在客户端看到的那个错误现象，并不一定就是错误本身，很大可能是由那台机器的系统配置引起的。用户对你说：我在我的机器上做了什么操作，然后就成了这个样子。可你在自己的机器上怎么试都重现不出来——基本上，**几乎不可能在他的运行环境之外的任何一台机器上重现这个错误**，这个现象就只在他那一台机器上成立。

这就引出一个很关键的事实：很多错误都是由配置引起的，于是 configuration testing 成了整块测试里最费劲、最难做的地方。

再往下想，Web 系统的结构天然把它分成了三层：客户端、服务器端，中间还夹着一个网络。一旦出了问题，你很难判断这个 bug 究竟发生在哪一层，debug 的时候要一层一层去甄别。

```text
  ┌──────────┐        ┌──────────┐        ┌────────────┐
  │  客户端   │  --->  │   网络    │  --->  │  服务器端   │
  │  client  │  <---  │ network  │  <---  │   server   │
  └──────────┘        └──────────┘        └────────────┘
     症状在这里冒出来       通信链路            数据与业务逻辑在这边
```

错误诱因还可以再分两类：一类是静态的配置，比如各种软硬件的配置不当；另一类是动态的运行环境，比如瞬时流量特别大的时候，会冒出一些很诡异的错误。所以，**environment 在 Web 应用测试里扮演着一个非常重要的角色**。

这里容易有一层误解，我拿个感冒的例子说清楚。一个人感冒发烧、流鼻涕，你一眼看到的是鼻子在流鼻涕，难道就是鼻子的毛病吗？不是，深层的病因是身体受了病菌侵扰，鼻子只是症状露出来的地方。测 Web 应用也一样：你看到一个症状，得顺着往深处找，症状所在的层，未必是错误所在的层。比如有人反馈"进某个页面很慢"，这未必是服务器的问题，也可能就是客户端自己在那边算、在那边处理，才慢下来的。

### 总体测试策略：顺着设计模型自上而下

那总体上怎么测？思路其实是从我们做设计时就埋好的那些模型顺下来的。

回想 Web 应用设计，我们有一组设计模型，排成一个自下而上的金字塔：最底下是最接近实现技术的构件设计，往上依次是系统架构、导航设计、内容设计、美工设计与界面设计，越往上越接近最终用户。

```text
  最靠近用户
  ┌───────────────────────────────┐
  │   界面设计 / 美工设计           │
  ├───────────────────────────────┤
  │   内容设计                     │
  ├───────────────────────────────┤
  │   导航设计                     │
  ├───────────────────────────────┤
  │   系统架构设计                 │
  ├───────────────────────────────┤
  │   构件设计                     │
  └───────────────────────────────┘
  最靠近底层实现技术
```

测试就对着这组模型自上而下地做：

- 先测内容（content testing），从 content model 拿过来做测试计划；
- 再测界面（interface testing）——测界面时，光有 interface model 是不够的，还要把美工设计一起拿进来，这两块是一个整体；
- 接着测导航（navigation testing）——除了 navigation design，你还得有一个整体架构的观念，才能把导航测到位；
- 然后是构件测试（component testing），对应 component design。

这四大块是表层的东西。表层测完，进入跟技术直接相关的底层特性测试：configuration、compatibility、security、performance，这几项要专门测。

最后还有一步，是 Web 应用几乎绕不开的：不是说技术人员测完就直接挂到网上。真一挂上去就 crash，用户就不会再回来了。所以上线前还要有一个"内部公测"——在一个你还可控的环境里，挑一部分 end users，对整个系统做一遍完整的黑盒测试。我们的 ZOJ、那些 online judge 系统，正式上线前都会先让集训队那帮人上去"虐"一遍，就是这个道理。

```text
   content  ──►  interface  ──►  navigation  ──►  component
   （表层，对应设计模型）

        ──►  configuration / compatibility / security / performance
             （底层，与实现技术直接相关）

        ──►  内部公测：可控环境下选部分真实用户做整体黑盒测试
```

### 内容测试

内容测试（content testing）的目标是检查内容本身对不对。内容的问题起码分两块：一块是语法，一块是语义；除此之外，还要看内容的组织和结构。

#### 语法、语义与结构

语法方面，最典型的就是 typos，也就是拼写错误、错别字，还有语法错误、句子不通顺这一类。

语义方面就不一样了：拼写、语法都没问题，但你提供的信息是不是准确、是不是正确？举个很实在的例子——你要给学院做个网站，网站上的学院介绍，你拿的是十年前的版本，那就不对了。这里还包括政治上的因素：表述必须准确、不能有歧义，操作细节上的任何差别都不允许。内容测试就是要让它一看就是准确、无歧义地表达出来。

除了对错，还有结构：哪些内容和哪些内容放在一起出现，哪些先出现、哪些后出现，这种组织顺序和结构是不是正确。最终目的是让这些内容能井井有条地呈现给用户，让用户导航的时候能精确地走，不会遇到模棱两可、容易被误导的内容。

> **定义**：语法错误关乎"写得对不对"，语义错误关乎"说得对不对"，结构错误关乎"摆得对不对"。

#### 数据库测试：分层交互

内容测试里最复杂、最难测的一块，其实是数据库测试。原因很简单：绝大多数的 Web 应用，都是以数据库为中心来架构的，所以对数据库的操作必须测；而它之所以比普通软件里的数据库操作更难测，是因为**中间要经过的层数太多**。

我们顺着一次查询走一遍。用户在网页上有个文本框，输了个词，点了查询按钮。从他输词、点按钮，到系统把搜索结果返回给他，中间经历了多少个环节？

1. 先读到的是网页的 HTML 代码；
2. 从这段代码里解析出，哪个字段是用户输入、要拿去查的东西；
3. 判断这是什么样的操作——查询、写入，还是别的；
4. 把它转换成数据库能懂的语言，比如 SQL 指令，再传给数据库；
5. 数据库执行操作，把数据返回；
6. 但客户端给的原始请求，基本不会直接就是 MySQL 或 SQL 语句的形式，所以第 4 步那个翻译是必须的；而且数据库未必就在本机上，服务器和服务器之间还有一个通信问题；
7. 数据库返回的是 raw data，不能就这么直接丢回给用户，要一路返回 Web 应用服务器，再转换成合适的、可以展示的格式（proper format for display），最后在界面上渲出来。

一层套一层，所以对数据库的交互要做分层处理，每一层各自设计相应的测试。书上建议把它分成五层来对待，每层做每层的测试。

```text
   用户输入(文本框 + 查询按钮)
        │  ① 读取 HTML，解析出用户填的字段
        ▼
   Web 应用服务器层
        │  ② 判定操作类型(查询/写入)，翻译成 SQL
        ▼
   DBMS / 数据库（可能远端，需服务器间通信）
        │  ③ 执行操作，返回 raw data
        ▲
   服务器层
        │  ④ 转换成可展示的格式 proper format for display
        ▲
   用户界面：把结果呈现到屏幕上
```

如果还涉及动态内容，往往还要跨对象地做格式转换，才能适合展示，这里又牵涉到格式化和兼容性问题。层数一多，复杂性就上来了，这也是数据库测试麻烦的根子。

### 界面测试

内容测完，接着测用户界面。界面测试的第一个重点是测试各种 interface mechanisms——界面上的各种机制。

什么叫 interface mechanism？就是界面上不同种类的交互元素：链接、按钮、一个 form 表单、一个表格、pop-up windows 弹出框，还有 cookie，等等。每一个这样的东西，都算一种机制。界面上每一种机制，都要针对性地设计相应的测试。

这些机制存在的目的是什么？是为了实现导航、实现某些功能、实现内容的展示。所以界面测试的总体目标就是：考察这些机制是否**在语义上正确地实现**了它本该实现的导航、功能与内容展示。

对应的测试策略有这么几步：

- 先整体看 interface features：它是否符合我们在界面设计时讲过的一系列设计原则，有没有违背；再从美工角度做第一眼测试——table 的大小怎么样、行间距合不合适、边框和留白好不好看，整体看上去舒不舒服。
- 再做单元测试：把每一种机制单独拿出来做局部测试，比如每一类表格都要测一下。
- 单元测试之后是整合测试：把每一个 use case，或者更管用的 NSU 拿出来，把涉及的界面机制整体串一遍。这相当于普通测试里的 integration test。
- 然后是验证性测试（validation testing）：把某些 use case、NSU 或模型组合在一起，把整个界面整体走一遍，看它是不是正确。这就很像最后的黑盒、功能验证性测试，检查的是整个界面的语义有没有被正确实现。
- 最后还有 Web 特有的：对各种不同的环境做兼容性测试，比如换不同浏览器、不同的服务器与数据库组合，看还兼不兼容。

> **定义**：NSU 是 Navigation Semantic Unit（导航语义单元），来自导航设计那一章。它长得和 use case 很像：一头有个 actor，描述的是这个 actor 为了完成一件（对应某个 use case 的）事情，过程中要经过哪些页面——点哪个链接进哪个页面、再点哪个链接进哪个页面，最后在那个页面做什么操作。它就是一页一页串起来的。

界面机制的种类很多，除了链接、表格，还有客户端/服务端的脚本、动态 HTML、弹出窗口（弹到哪里、弹多大都是要测的点）、CGI（Common Gateway Interface，公共网关接口，是 Web 上应用的一种程序接口）、动态链接，以及 cookie。

拿电商里最常见的购物车举个例子：购物车里能装的最小数量、最大数量各是多少；如果一件商品都没选就直接点结账，会不会算出一个错误的金额；如果超过购物车上限又会怎样——这些特殊的界面机制，都要一一测过。

### 可用性测试

可用性测试（usability testing）和普通软件里的定义略有不同，它主要测的是：一帮你不认识、不可控的人，能不能自己把界面用起来。

这也决定了它的组织方式——**测试是由你们 Web 工程团队设计的，但执行者必须是真实最终用户**。所以通常要找一个有代表性的用户群，或者从各类用户群里挑几个有代表性的人来实际操作。

执行步骤大致是这样：

- 先明确这次到底要测哪几个方面的 usability。usability 只是一个词，它背后其实是一堆 abilities；
- 对每一个要测的目标，设计对应的 test case，并且设计出一种让它**可以被评估**的方法——这一点其实相当难做。

可选的测试目标有一长串，比如：交互性（interactivity）、布局（layout）、可读性（readability，字体、大小、颜色，字色和背景色几乎糊成一团，屏幕稍微暗一点就看不清，就是可读性问题）、美工、展示特性（display characteristics）、时间敏感性（time sensitivity，什么东西响应慢、什么对响应速度特别敏感）、个性化（personalization）、无障碍访问（accessibility，有没有考虑残疾人或有能力障碍的人怎么用）。你的软件是干什么的，就重点挑对应的几项来测，先定目标，再设计用例。

难就难在"怎么证明它好"。举个交互性的例子：有师姐的毕业论文做的是鼠标单点手势——当时没条件买触摸屏，就用鼠标模拟单点手势，希望将来有触摸屏时一根手指就能把东西拖来拖去、画个叉就把新建的东西删掉，设计了一整套手势交互。她写毕业论文，把原则、设计、实现都写了，这就算完了吗？最后一章必须回答的是：**凭什么说明这套手势比传统的点菜单更好用**？

那就要设计实验来证明。比如找几位同学来做测试：

1. 先把任务讲清楚——有几个任务、每个任务要完成什么；
2. 让他用传统方式（鼠标一格格点菜单）去完成，用秒表记时间；
3. 再教他这套手势，让他用手势完成同样的任务，同样记时间；
4. 一次还不够，还要看学习曲线——让他重复做很多次，观察时间怎么变化，看多快能上手；
5. 再配上调查问卷，做主观评判：哪些地方好用、哪些不好用。

这样客观指标加主观评价，才算对 interactivity 有个交代。换到别的特性也一样：每一个你都要设计出一个明确的指标，先说清什么叫好、什么叫不好。不能只是自己用一下，然后说"嗯，不是很好，给你打 60 分"——你这 60 分是从哪来的？我说 61 分行不行？这些都是要动脑筋的地方。

测试时还要选好相应的用户群，请他们来做，你在旁边看着，适当给点帮助和指导，观察他们的接受程度。对每一种交互机制，都要设计出这样一种评审机制，最后才能有根有据地说清楚可用性到底是什么样。

### 构件测试与导航测试

构件级测试（component-level testing）跟普通软件没有太大区别，主要是基于功能的测试，黑盒、白盒都能用。而 Web 应用通常以数据库为中心，所以数据库测试一般不单独做，而是和单元测试、功能测试合在一起进行。

导航测试（navigation testing）则要测两个方面：一是导航的**语法**，二是导航的**语义**，看它们是否正确。

语法方面，有这么几类东西要测：

- links 链接：是不是有断掉的死链接；
- redirects 重定向：网页地址可能被删掉、不再更新或取消了，这时该怎么处理？一般要给出提示，比如"这个网页已经不存在了"，并建议用户按某个键回到主页——这是很常见也很必要的处理；
- bookmark 书签；
- frame、frame sets 框架；
- site map 网站地图（如果有的话）；
- internal search engines 站内搜索引擎（如果有的话）。

语义方面，书上的 20.6.2 节列了一系列 testing questions。它的意思是：你在设计 test case 的时候，要确保你的用例能够覆盖、并且能够正确回答这一系列问题。这些内容这里就不展开讲了，需要自己去看一看。

### 配置测试

配置测试（configuration testing）是一件很头痛的事，要分服务器端和客户端两个方面来测。

| 端 | 要操心的内容 |
| :--- | :--- |
| 服务器端 server-side | 操作系统版本是否兼容；系统文件、目录、数据库在运行时能否被正确创建；安全（防火墙、加密配置，以及防火墙会不会拖慢响应速度）；分布式服务器环境；与数据库的整合；数据库的版本与平台；server-side scripts 能否正确运行；administrator 角色的误操作后果；代理（proxy）服务器的配置 |
| 客户端 client-side | 硬件（CPU、GPU/显卡、内存、打印设备）；操作系统（Windows、Linux、Mac OS、Android 等）；浏览器（IE、Mozilla、Netscape 等）；界面构件（ActiveX、Java applet）；插件（QuickTime、RealPlayer）；网络连接方式（cable、DSL、modem、T1 等） |

服务器端这边，最容易忽略的是 administrator 这个角色。他的权限通常比普通用户大得多，能干的实事也多。你设计安全防范时，会把他当成友好用户，对他宽松很多；可他要是误操作了，会对系统产生什么后果？这必须提前考虑。另外，如果用了代理服务器，代理那份配置也要相应测过。

客户端这边，你要面对的是一群你用不了的终端。你也许默认大家都用某种分辨率的屏，可现在还在用 800×600 的、还在用 IE6 的，你都不该当他不存在。浏览器不能只在一台机器的一个 IE 上试过就算——各种操作系统、各种浏览器、还有 iPad 之类的各种屏幕，都得测。硬件层面也一样，拿网游打比方，要能玩你这个游戏，人家的显卡得在某个档次以上，显卡不够就是玩不了；如果有打印功能，打印设备能不能正确设置也是一项。如果再花哨一点，用到插件，还得考虑用户没有插件时怎么给他一个安装文件。

连接方式这里可以顺带记几个数字：modem 的带宽大概 56K；T1 在美国是 1.544 Mbps 的标准，在欧洲是 2.048 Mbps；更大的 T2、T3，T3 能承担大约 T1 的 44.28 倍带宽，也就是 42 Mbps 左右。DSL 也有很多种，像 HDSL、SDSL、ADSL、VDSL 等等，各家运营商都有。

### 安全性测试

安全性测试要关心的是 vulnerability，也就是系统最薄弱、最容易被攻击的地方。这些薄弱环节分三个层面：客户端、服务器端，还有网络通信。

```text
  ┌──────────┐        ┌──────────┐        ┌────────────┐
  │  客户端   │        │   网络    │        │  服务器端   │
  │ browser  │  <==>  │ 网络通信  │  <==>  │   server   │
  │ 邮件/IM  │        │  GET/SQL │        │   DoS 等   │
  └──────────┘        └──────────┘        └────────────┘
```

客户端最容易出问题的是它用的浏览器——有一些致命缺陷，这也是为什么大家会说不要再用 IE6 了；此外还有邮件系统，以及 QQ、MSN 这类通信软件，都可能带着安全隐患。移动终端同样是重灾区：终端可能被植入木马，木马能监听、截获甚至调用屏幕上的虚拟键盘输入，你在没做认证或测试的情况下敲进去的账号密码，就可能随时被监听、被截获。所以终端上应该有一套反监听机制，测试的时候就去看看，能不能把输入的账号密码截获走——这很可能就是终端的一种漏洞。

服务器端最常见的是 DoS（拒绝服务）攻击，以及恶意脚本攻击。恶意脚本可以借由客户端反推过去，使服务器的操作泄露出来，甚至被任意运行。

网络这一层有个很典型的例子：客户端和服务器有时候用 GET 来传指令、取信息，而 GET 会把变量直接显示在 URL 上，变量名是看得见的；有经验的黑客就能修改 URL 里的参数，去访问本不该让他拿到的文件和别的用户的隐私，这对服务器安全的影响很大。这个问题从缓冲区溢出的角度也能理解。

做安全测试，思路之一就是模拟黑客的手段主动去攻击，把隐患尽量消灭在前端——在交付之前消灭，损失才小；等到交货以后被攻破，那代价就大了。

### 性能测试

性能测试（performance testing）是 Web 应用另一个特别头痛的地方。说到底，Web 测试最头痛的就两件事：一个是配置环境，查错、改错都很麻烦；另一个就是性能，因为你的 real-world loading——真实使用起来的那个流量——你是没法控制的。所以只能对各种流量给系统带来的影响，做各种各样的测试。

性能测试基本上要回答这么几个问题：

- 服务器的响应时间，会不会退化到一个明显、不能忍的程度？
- 如果会，那么在什么点上性能变得不可接受？并发到什么程度、数据流量到什么程度，服务器就顶不住了？
- 到了不可接受的时候，到底哪些模块是瓶颈？是服务器太少（那就加服务器），还是带宽不够（那就申请带宽更高的服务）？
- 在不同的负载条件下，平均响应时间大致是多少？比如 100 人、1 万人、100 万人同时访问，反应时间各是多少？
- 当流量很大、系统接近崩溃时，系统的安全性会不会受影响？（被混水摸鱼，就会产生安全隐患。）
- 当并发量很大时，某部分功能的可靠性、它产生的数据的精确性和准确性会不会受影响？（我们的 online judge 就有这种问题。PAT 的考场规则里，最后一条通常就是：如果在最后 10 分钟系统崩溃，我们就不补时，按系统崩溃那一刻的排名为准。系统接近崩溃边缘时，运行时间可能就测不准，而最难测的是内存使用，它也会测不准、出各种问题。）
- 崩溃之后会怎么样？这就是压力测试要回答的。

#### 负载测试与压力测试

性能测试分成两大块，其实是连续的：先是 load testing，再是 stress testing。

负载测试是在正常值的范围内，不断改变 loading conditions——也就是流量、访问量——看 Web 应用和它服务器端的环境会怎么反应。压力测试则是负载测试的继续：去找它的临界点，再把它 push 过去，让系统满负荷、甚至超过极限，看整个系统会发生什么、会不会瘫痪。

```text
  正常范围内改变负载           推过临界点
  ───────────────────►  ┃  ───────────────────►
     load testing        临界点    stress testing
  （看系统如何响应）              （看崩溃与崩溃后的表现）
```

#### 吞吐量公式

负载测试里有个术语叫 overall throughput，也就是总的吞吐量，记作 $P$。它由三个元素乘在一起得到：

$$P = N \times T \times D$$

其中 $N$ 是并发用户数（the number of concurrent users），$T$ 是每个用户在单位时间里要完成的在线事务数（online transaction），$D$ 是每件事务产生的数据量。三者相乘，得到的就是**单位时间内冲进你服务器的总数据量**。

拿一场 NBA 直播的评论来算算。假设昨天东部决赛（比如热火对篮网）总访问量有两万，$N = 20000$；每个用户平均每两分钟提交一条评论，也就是每秒提交 $T = \frac{1}{120}$ 次；每条评论平均 3 KB，即 $D = 3\text{KB}$。那么

$$P = 20000 \times \frac{1}{120} \times 3\text{KB} \approx 500\text{KB/s}$$

一个大型体育类网站，就得能达到这个量级。达不到，用户在你这里看比赛、发评论的体验就崩了。

公式里的三个因素，也正好提示了你测试时该去调控什么：你可以设非常大的并发量、但每个用户的操作用很简单、产生的数据量也小；也可以设中等规模的并发、但中间的操作很复杂、数据量很大。各种排列组合都值得试。有句玩笑话说，玉米是服务器最好的测试员——什么时候抢票，你就知道谁家的服务器好不好了。

### 本讲提到的题目

#### 讨论题一：Web 应用测试最难的地方

**题干**：我们现在开发的是一个在线的、简化版支付宝（在线支付）。请对照另一个软件——某个机构委托银行定制的、专门给它内部用的银行系统操作软件。作为测试员，你觉得测 Web 应用时，哪些方面特别难？请挑一个方面，说清楚你为什么觉得它难、会出现什么情况。没有唯一答案，能仔细说清一个方面就可以。

**解析**：这九条质量维度，每一条其实都有 Web 应用特别的地方，怎么写都行，只要写得有道理。但如果你有经验，最该点出来的是 configuration。客户端看到的错误现象往往不是错误本身，而多半由那台机器的系统配置引起；用户描述的操作你很难在他机器以外重现，"几乎不可能在他环境之外的任何机器上重现"。再加上系统分客户端、服务器、网络三层，debug 时很难判断 bug 在哪一层；诱因又分静态配置与动态（瞬时大流量）两类。所以 environment 在 Web 应用测试里扮演着非常重要的角色。

#### 讨论题二：如何证明"能支撑百万级并发"

**题干**：支付宝这个在线支付系统的测试任务交给你。它要面对的接近真实的情况是：至少支持 100 万在线用户；每天并发量大约 10 万，分分钟并发访问 10 万人次；每天大约产生 1TB 级的数据。你要考虑并发、存储，以及数据库对 100 万用户数据的支持。请说明，你用什么方法去证明这个系统真的做得到。

**解析**：这个问题的关心点很明确，就是 performance。做法是围绕 $P = N \times T \times D$ 做负载测试与压力测试：改变并发数、事务频率和数据量，测出在什么点上响应时间变得不可接受、瓶颈是服务器数量还是带宽、不同负载下的平均响应时间是多少；再看接近崩溃时安全性是否受影响、高负载下数据的精确性和准确性是否受影响，以及崩溃之后会怎样。

这里要记住一条硬道理：形容词不能凭嘴说。你号称能"毫无困难地支持大规模并发"，那就得拿证据来——曾经有学生做在线系统，号称支持多大的并发量，可测试那一章里只测了 10 个并发，那能叫测过并发吗？那什么叫不大规模的并发？每一个形容词，都要有根据、有证明。
