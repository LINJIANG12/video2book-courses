## 数据结构与算法基础：从数据组织、空间开销到效率度量

### 从三个生活与程序实例谈起

#### 图书摆放：数据组织与操作的权衡
第一个例子：如何在一排排书架上摆放图书？
场景非常单纯：给你一些书架，陆陆续续有一大堆书运送进来，你打算怎么把它们妥善安置到书架上去？
如果把这道题翻译成计算机专业术语，其实就是：给你一堆原始数据，给你分配了一定大小的物理存储空间，你该怎样在空间中组织并存储这些数据？

一上来问“怎么放书”，其实并不科学，因为遗漏了一个核心变量——数据的规模。
面对一个只有两三层、藏书几十本的小书架，和置身于一座藏书数百万册的巨型书城，处理问题的难度有着天壤之别。
更深层的实质在于：摆放图书本身绝不是目的，存放图书是为了日后提供借阅与流通。
因此，图书的摆放方式，必然与两项核心操作紧密绑定：
- 新书插入：新采购了一批书，如何将其放入书架？
- 指定图书查找：读者要借阅某一本特定的书，如何快速定位其物理位置？

针对这两个操作，我们来看看三种截然不同的组织策略：

策略一：随便放（哪里有空放哪里）。
- 新书插入极度简便：图书一本挨着一本顺次排放，新来一本书，直接贴在书架当前末尾的空档处，一步到位。
- 查找图书极度痛苦：如果是在藏书几万、几十万册的巨型书城，读者要找某本冷门书籍。偏巧这栋书城根本没有采购这本书，但店员事先并不知道，为了确认到底有没有，只能硬着头皮从书架第一本开始，逐本肉眼翻阅核对，一直扫到最后一本，才能精疲力竭地叹口气说：“不好意思，我们真的没有这本书。”

策略二：按书名的拼音字母顺序规范排放。
- 查找图书极其高效：引入拼音字母序后，可以直接使用著名的二分查找（Binary Search）。
  假设整排书架按字母序整齐排列，我们要查找拼音以 S 开头的《数据结构》：
  先抽出这排书正中间的一本（例如是拼音 L 开头的《离散数学》）；
  在字母表中，S 排在 L 的后面，这意味着《离散数学》左侧所有 A 到 L 开头的图书全都不用看了，查找范围瞬间砍掉一半；
  接着在剩余的后半段中间抽查一本书（例如是拼音 W 开头的《网络技术基础》）；
  S 恰好落在 L 与 W 之间，搜索区间再次折半缩小；
  每一次比对都能排除一半范围，只需极少数几次中间比对，就能迅速收敛到目标图书上，快速确定书架上究竟有没有这本书。
- 新书插入沦为梦魇：新买入一本拼音 A 开头的《阿Q正传》，按照字母序它必须排在最开头。此时惨了，为了腾出第一个位置，书架上原本存放的几千上万本书，几乎全部都要一本挨着一本依次往后挪动错位，工作量极其庞大。

策略三：分级分类摆放，类内拼音排序。
这正是现代实体书店与图书馆通行的管理方案。我们走进任何一家大型书城，想要买一本《数据结构》，绝对不可能从大门第一架书逐本翻找，也绝不可能随机走到中间摸一本书盲目二分。
我们的真实寻书路径是先抬头看导引指示牌，寻找图书大类：社会科学类、文学艺术类、理工科类……在工科大类下进一步细分找到计算机类专架。
在物理书架上划定专区对应各个大类与细分类别，在具体类别内部再按照拼音字母顺序排放。
这种策略的核心优势，在于将海量数据的庞大搜索空间，在第一阶段直接打散降维到规模可控的局部子集。查找图书时，先定位类别，再在局部小范围中做二分查找；插入新书时，同样先定类，在类内二分定位，即便需要错位挪动空档，受影响挪动的图书数量也仅局限在当前类别之内，相比全局挪动大幅缩减。

```text
[策略一：无序平铺]
书架: [书B][书Z][书A][书M][空] -> 插入新书直接贴末尾；查找需逐本穷举遍历

[策略二：全局有序]
书架: [书A][书B][书C] ... [书Z] -> 查找可用二分折半；插入《阿Q正传》全架后移

[策略三：分级分类]
书城 -> [工科大类] -> [计算机细分专架] -> [类内二分查找 / 局部挪位插入]
```
读图说明：字符画展示了图书摆放的三种演进形态，从无序的简单追加，到全局有序的二分折半，再到分级分类将规模局部化。

然而，分类方案又带来了两项必须直面权衡的现实工程难题：
- 空间分配难题：各类别的藏书量各不相同且动态变化。每个类别预留几个书架？如果平均分摊，冷门类别书架空置积灰，造成空间闲置浪费；热门类别书架迅速塞满，进新书时不得不频繁添置柜子、重新调整整体布局。
- 分类粒度难题：类别划分多粗多细为好？划分太粗，单类内部藏书依然庞大，类内维护工作量依旧沉重；如果划分过细，比如在大型书城中搞出整整 3 万个细分类目，读者进门找一本书，面对浩如烟海的分类清单，光是判断目标图书属于哪一个类目就已经彻底茫然了。

> **结论**：解决问题方法的效率，跟数据的组织方式是直接相关的。

#### 数字打印：空间使用与递归调用栈的陷阱
第二个例子：编写一个极为基础的函数 `PrintN(int N)`，功能非常纯粹——传入一个正整数 $N$，在屏幕上打印出从 1 到 $N$ 这整套正整数序列。
面对这样一个看似毫无技术门槛的简单需求，依然至少存在两种截然不同的实现思路。

第一种思路：循环迭代实现。
```c
void PrintN_Iterative(int N) {
    int i;
    for (i = 1; i <= N; i++) {
        printf("%d\n", i);
    }
}
```

第二种思路：递归调用实现。
```c
void PrintN_Recursive(int N) {
    if (N > 0) {
        PrintN_Recursive(N - 1);
        printf("%d\n", N);
    }
}
```

对比两段代码的外观：两者代码行数旗鼓相当。从某些角度看，递归版本连临时循环变量 `i` 都无需声明，结构紧凑利落。
作为人类程序员，在编写程序时往往很偏爱递归风格：只要掌握了递归边界与自相似递推的核心思想，递归代码往往显得通透精炼，逻辑清晰优美。
然而，计算机硬件在底层跑起递归代码来，却可能极其吃力与痛苦。

不妨在主函数中分别调用这两个版本，逐步增大 $N$ 的取值进行压力测试：
让 $N$ 从 10、100、1000、10000 逐步提升到 100000。
- 循环版本：当 $N = 100000$ 时，屏幕开始飞速滚屏输出数字，虽然输出 10 万行文本需要占用一小段 I/O 时间，但程序平稳运行，最终准确在 100000 处圆满结束。
- 递归版本：当把 100000 作为参数输入后，控制台不仅没有按部就班打印数字，甚至连 1 这个数字都还没来得及露面，整个程序就毫无预警地直接异常中断退出（“罢工了”）。

这背后究竟发生了什么？
其根源在于：递归程序对物理存储空间的占用方式非常苛刻。
当程序执行函数调用时，系统必须在内存中开辟一块专用的内存区域——函数调用栈帧（Stack Frame），用来保存当前函数所处的所有现场状态，包括参数、局部变量以及函数返回后的执行指令地址。
在递归版 `PrintN(100000)` 的执行链路中：
传入参数 100000，检查 $N > 0$ 成立，但在执行当前数字的打印之前，它必须先调用 `PrintN(99999)`；
为了在子函数返回后能接着执行 `printf("%d\n", 100000)`，系统必须先把 `PrintN(100000)` 的完整现场状态压入系统栈中保存好；
进入 `PrintN(99999)` 后，同样不能立刻打印，又要把 99999 的现场压栈，转而去调用 `PrintN(99998)`……
如此层层递进，直到最深层的 `PrintN(0)` 触底返回之前，系统调用栈里已经从底到顶密密麻麻塞满了从 100000 到 1 全部 10 万层调用的运行状态。

```text
[系统调用栈增长示意]
高地址
|  ...                         |
|  PrintN(1)   现场状态 (参数/返回地址) |
|  PrintN(2)   现场状态 (参数/返回地址) |
|  ...                         |
|  PrintN(99999) 现场状态      |
|  PrintN(100000)现场状态      |  -> 栈空间持续耗尽，直至 Stack Overflow 崩溃跳出
低地址
```
读图说明：字符画展示了递归函数在尚未触底返回时，每一层调用都在内存栈区叠加保存现场，栈空间消耗随参数规模线性激增。

在内存管理中，递归调用占用的空间规模与原始输入规模 $N$ 严格成正比。若将空间复杂度记为 $S(N)$，则其表现为线性增长函数：
$$S(N) = c \cdot N$$
操作系统为每个进程分配的默认调用栈空间是非常有限的（通常仅有几兆字节）。当 $N$ 膨胀到 10 万级别时，累积的调用栈帧彻底撑爆了预设的栈空间上限，引发了致命的栈溢出（Stack Overflow），程序被操作系统强制杀死。

反观循环实现的版本：整个生命周期内仅仅开辟了一个整型临时变量 `i`，循环的推进只是对同一个物理内存单元的值进行递增覆写，完全不涉及额外的函数栈帧申请。无论 $N$ 设定为 10、10 万还是 10 亿，其空间占用始终恒定为常数级别：
$$S(N) = c$$
因此循环版本永远不会遇到栈空间枯竭的问题。

> **结论**：解决问题方法的效率，跟空间的利用效率是直接相关的。

#### 多项式求值：算法巧妙程度与时间效率的飞跃
第三个例子：多项式在指定点处的求值问题。
给定一个 $n$ 阶多项式：
$$P(x) = \sum_{i=0}^n a_i x^i = a_0 + a_1 x + a_2 x^2 + \dots + a_n x^n$$
要求编写程序，计算该多项式在给定点 $x$ 处的具体函数值。

针对该数学表达式，最直观也是最容易信手写出的实现方式，就是对公式进行逐项直译：
```c
double f1(int n, double a[], double x) {
    int i;
    double p = a[0];
    for (i = 1; i <= n; i++) {
        p += (a[i] * pow(x, i));
    }
    return p;
}
```
这段代码逻辑直白：先把常数项 $a_0$ 赋给累加器 $p$，然后开启一个 for 循环，每次循环通过 C 标准库 `<math.h>` 提供的 `pow` 函数计算 $x^i$，与系数 $a_i$ 相乘后累加进 $p$。
然而，如果在工业级软件工程或严谨的技术面试中写出这样的实现，往往会被资深程序员严重挑剔。这种写法看似朴实，实则隐藏着巨大的性能劣势。

早在中国南宋时期，杰出的数学家秦九韶在其著作中就提出了一种极其精妙的多项式计算方法（在西方数学史中被称为霍纳法则 Horner's Rule）。
秦九韶算法的核心思想是巧用结合律，将多项式中的公共因子 $x$ 逐层向外提取：
$$P(x) = a_0 + x \left( a_1 + x \left( a_2 + \dots + x (a_{n-1} + x \cdot a_n) \dots \right) \right)$$
在程序实现上，计算过程转变为由最内层括号向外层括号层层递推计算：
```c
double f2(int n, double a[], double x) {
    int i;
    double p = a[n];
    for (i = n; i > 0; i--) {
        p = a[i - 1] + x * p;
    }
    return p;
}
```
从最高阶系数 $a_n$ 开始，每次先与 $x$ 相乘，再加上前一项系数 $a_{i-1}$，然后将结果代入下一轮循环继续乘 $x$ 累加，直到加入常数项 $a_0$ 为止。

凭什么断定第二种算法就一定优于第一种算法？
口说无凭，最严谨的方式就是通过基准性能测试（Benchmark）跑分实测。
在 C 语言中，标准库 `<time.h>` 提供了精准测量程序耗时的工具函数 `clock()`：
- `clock()`：捕捉从当前程序启动运行，到该函数被调用的那一刻所消耗的硬件时钟打点数（Clock Ticks），返回值的类型为 `clock_t`。
- 常量 `CLK_TCK`（现代 C 标准宏规范为 `CLOCKS_PER_SEC`）：表示当前机器硬件时钟每秒钟包含的打点数。
将两次调用 `clock()` 采集到的打点数相减，再除以每秒打点常数，即可算出以秒为单位的精确耗时：
$$\text{duration} = \frac{\text{stop} - \text{start}}{\text{CLK\_TCK}}$$

编写一个标准的性能测试框架：
```c
#include <stdio.h>
#include <time.h>
#include <math.h>

clock_t start, stop;
double duration;
#define MAXN 10   /* 9阶多项式，共包含10项系数 */

double f1(int n, double a[], double x);
double f2(int n, double a[], double x);

int main() {
    int i;
    double a[MAXN];
    for (i = 0; i < MAXN; i++) a[i] = (double)i;

    /* 测试函数 f1 */
    start = clock();
    f1(MAXN - 1, a, 1.1);
    stop = clock();
    duration = ((double)(stop - start)) / CLK_TCK;
    printf("f1: ticks = %f, duration = %f seconds\n", (double)(stop - start), duration);

    /* 测试函数 f2 */
    start = clock();
    f2(MAXN - 1, a, 1.1);
    stop = clock();
    duration = ((double)(stop - start)) / CLK_TCK;
    printf("f2: ticks = %f, duration = %f seconds\n", (double)(stop - start), duration);

    return 0;
}
```
> **提示**：专业代码规范中，对于完全并列的重复测试逻辑通常应封装为高阶测试函数或宏，这里为了纯粹聚焦测量原理，保留直观平铺的书写方式。

将上述程序在计算机上编译运行，终端打印出的输出却可能出人意料：
两个函数输出的 ticks 打点数全部都是 0，最终计算出来的耗时全都是 0.000000 秒。
程序真的没有耗时吗？并非如此。
根本原因在于现代计算机处理器的运行速度极快，面对区区一个 9 阶多项式的单次计算，两个函数的执行时间都远远低于时钟打点所能分辨的最小时间片（不到 1 个 tick），因此 `clock()` 根本无法捕捉到底层微秒甚至纳秒级别的细微变化。

如何解决微小耗时的测量难题？
解决方案在于：重复循环放大法。
单次运行捕获不到，就让被测函数在计时刻度内重复跑 1 万次、10 万次乃至 1000 万次（记为 `MAXK = 1e7`），让微小的耗时通过大量累加沉淀出清晰可辨的物理时钟打点。最终计算单次运行时间时，只需将总耗时除以重复执行的总次数 `MAXK`：
$$\text{单次耗时} = \frac{\text{总耗时}}{\text{MAXK}}$$

```c
#define MAXK 1e7  /* 被测函数最大重复调用次数 */

/* 改进后的循环放大测量核心片段 */
start = clock();
for (i = 0; i < MAXK; i++) {
    f1(MAXN - 1, a, 1.1);
}
stop = clock();
duration = ((double)(stop - start)) / CLK_TCK / MAXK;
```

引入大循环放大后再次运行，真实的性能差异瞬间显露：在不同配置的主机上实测，尽管具体绝对时间数值各异，但两组耗时数据的相对大小，稳稳展现出了整整一个数量级（约 10 倍）的悬殊差距。朴素算法明显比秦九韶算法慢得多。

深入机器底层执行机理，剖析背后的数学必然性：
现代计算机在算术逻辑单元（ALU）中，处理浮点加减法的速度极其迅速，而浮点乘除法的时钟周期开销远高于加减法。因此在评估这类纯代数运算的运行效率时，核心就是精确数出算法到底执行了多少次乘法运算。

对于朴素直接法 `f1`：
代码内部看起来只有一个显式的乘号 `a[i] * pow(x, i)`，但 `pow(x, i)` 本身要计算 $x$ 的 $i$ 次方。
采用普通的累乘计算，$x^i$ 需要执行 $i - 1$ 次乘法；再加上与系数 $a_i$ 相乘的那 1 次，第 $i$ 轮循环实际共需执行 $i$ 次乘法。
整个循环从 $i = 1$ 累加到 $n$，乘法的总次数呈现等差数列求和：
$$\sum_{i=1}^n i = 1 + 2 + 3 + \dots + n = \frac{n(n + 1)}{2} = \frac{1}{2}n^2 + \frac{1}{2}n$$
如果用时间复杂度函数 $T(n)$ 表达，其耗时模型为：
$$T(n) = c_1 n^2 + c_2 n$$

对于秦九韶算法 `f2`：
每一轮递推循环 `a[i-1] + x * p` 中，确实只包含 1 次显式的浮点乘法。
整个递推一共遍历执行了 $n$ 轮循环，乘法总次数精确恒等于 $n$ 次。
其时间复杂度函数 $T(n)$ 表达为：
$$T(n) = c \cdot n$$

对比两者的高阶项：
尽管具体硬件环境会影响常数项 $c_1, c_2, c$ 的绝对大小，但在数学上，随着多项式阶数 $n$ 的持续增长，平方项 $n^2$ 的膨胀速度将以不可阻挡的势头彻底碾压线性项 $n$。当阶数提升到 90、1000 甚至更高时，秦九韶算法的吞吐效率将呈现出降维打击般的优势。

> **结论**：解决问题方法的效率，跟算法的巧妙程度是直接相关的。

### 数据结构的核心内涵

经历了上述三个生动案例的洗礼，我们终于可以清晰、准确地提炼出数据结构的完整面貌：
> **定义**：数据结构（Data Structure）是数据对象在计算机中的组织方式。
> 任何数据对象都绝非孤立静态地堆积在内存中，它必然与绑定在其上的一系列操作紧密共存；而具体实现这些操作所采用的步骤与方法，就称为算法（Algorithm）。

描述数据对象的具体组织方式，必须将其切分为两个不可分割的维度：逻辑结构与物理存储结构。

#### 逻辑结构：线性、树与图
逻辑结构指的是数据元素之间逻辑上的前驱后继、父子从属或网络关联，完全脱离任何具体的计算机底层硬件与物理内存地址。根据元素间关联维度的不同，主要分为三大范式：
- 线性结构（一对一）：
  如同图书摆放中的单列书架，每一本书（除两端边界元素外）的前面只有唯一的一本书，后面也只有唯一的一本书。给每一个数据元素编一个序号，序号与数据元素严格呈现一对一的映射关系。
- 树形结构（一对多）：
  如同图书的分级分类目录体系。一个顶级学科分类（如工科）可以向下辐射出多个专业子类（计算机、机械、土木），一个专业子类下又涵盖多本具体的图书。数据呈现树枝状的层级分支展开，是一对多的层级管理模型。
- 图形结构（多对多）：
  如同实体书店背后的读者借阅与购买网络关系。一本书籍往往被成百上千位不同的读者购买过，而一位读者在一年内也会跨类别借阅采购几十本不同的书。数据节点与数据节点之间纵横交织，是一对多与多对一深度复合的多对多复杂网状拓扑。

```text
[线性结构: 一对一]
[节点1] <---> [节点2] <---> [节点3]

[树形结构: 一对多]
      [根节点]
      /      \
  [子节点A]  [子节点B]
   /    \        \
[叶1]  [叶2]     [叶3]

[图形结构: 多对多]
[节点A] ----- [节点B]
   |    \     /   |
   |      \ /     |
[节点C] ----- [节点D]
```
读图说明：字符画展示了三种逻辑拓扑的本质差异：线性结构沿单一轴线延伸，树形结构自顶向下单向分叉，图形结构各节点多维度自由互联。

#### 物理存储结构：数组与链表
逻辑结构构想得再完美，终究需要真实落盘在物理内存中。逻辑结构在计算机内存中的具体存放机制，被称为物理存储结构（Storage Structure）。
最基础的核心物理形态主要有两种：
- 连续存储（数组 Array）：将数据元素连续不间断地塞入一段物理地址相邻的内存区块。其优势在于可以通过数组下标基地址直接计算出任意元素的物理地址，实现 $O(1)$ 时间极速随机访问；缺陷在于中间插入或删除元素需要大动干戈地前后错位搬迁整段内存。
- 链式存储（链表 Linked List）：数据元素散落分布在物理内存的不相连碎片区域中，每个节点额外开辟一个指针字段，显式记录下一个邻居节点的物理地址。其优势在于插入或删除节点只需修改几个指针指向，极度灵活；缺陷在于无法直接下标跳转，必须顺藤摸瓜按序遍历。

#### 抽象数据类型：把“是什么”与“怎么做”彻底拆开
为了能够站在高层架构上清晰定义和分析复杂的数据组织，现代计算机科学确立了抽象数据类型（Abstract Data Type, ADT）这一强大工具。
这个概念由两个关键词构成：
- 数据类型（Data Type）：它明确规范了“数据对象集”以及“施加于其上的操作集”。正如图书摆放不能只谈书本实体，必须同插入、查找两项操作捆绑考量。在面向过程的 C 语言中，数据对象声明（结构体）与操作实现（函数指针或外部函数）往往是分离声明的；而在 C++、Java 等面向对象范式中，语言提供了“类”（Class）这一机制，在语法层面把数据属性集与方法操作集严密封装在一体。
- 抽象（Abstract）：核心要义在于“不具体”。描述数据类型时，完全摆脱对具体物理实现细节的依赖：
  与运行程序的物理机器型号无关；
  与在内存中到底采用数组还是链表等物理存储结构无关；
  与实现具体操作所选用的算法流派和编程语言无关。
简而言之：抽象数据类型只向外庄严宣告“我拥有什么数据、我能提供什么操作”（What），绝不过早掺和与泄露“底层究竟如何实现”（How）。

以数学中的矩阵（Matrix）为例，其抽象数据类型的标准规格描述如下：

> **类型名称**：矩阵（Matrix）  
> **数据对象集**：一个 $M \times N$ 的矩阵由 $M \times N$ 个元素构成，每个矩阵元素表示为一个三元组 $\langle a, i, j \rangle$，其中 $a$ 代表元素取值，$i$ 代表所在的行号（$1 \le i \le M$），$j$ 代表所在的列号（$1 \le j \le N$）。  
> **操作集**：对于任意矩阵 $A, B \in \text{Matrix}$ 以及正整数 $M, N, i, j$：  
> - `Matrix Create(int M, int N)`：创建并返回一个 $M \times N$ 的空矩阵；  
> - `int GetMaxRow(Matrix A)`：返回矩阵 $A$ 的总行数；  
> - `int GetMaxCol(Matrix A)`：返回矩阵 $A$ 的总列数；  
> - `ElementType GetEntry(Matrix A, int i, int j)`：返回矩阵 $A$ 在第 $i$ 行第 $j$ 列处的元素值；  
> - `Matrix Add(Matrix A, Matrix B)`：若 $A$ 与 $B$ 的行数列数一致，则返回相加之和矩阵，否则返回错误状态；  
> - `Matrix Multiply(Matrix A, Matrix B)`：若 $A$ 的列数等于 $B$ 的行数，则返回两矩阵相乘之积，否则返回错误状态。

这一套规格定义到底“抽象”在哪些关键之处？
第一，数据元素值的类型抽象。在数据对象集与 `GetEntry` 的返回值中，元素值被定义为一个泛化的 `ElementType`。这个矩阵里装的到底是一个 `int`、`float` 还是双精度的 `double`？在 ADT 声明中完全不予绑定。在 C 语言实现中，只需要在头文件顶部定义宏或类型别名：
```c
typedef float ElementType;
```
需要调整为整型时，改动这一行声明，全套矩阵算法逻辑无需更动即可全面复用。试想如果一开始就写死为 `int`，后续需求变更需要换成 `double`，若在编辑器中进行全文盲目查找替换（Replace），稍不留神就会把 `int i, j;` 这种原本货真价实充当行列索引的整型变量误改成 `double i, j;`，引发灾难性语法或逻辑错误。

第二，物理组织结构的抽象。ADT 声明中只规定这是一个 $M \times N$ 的二维矩阵数学实体。至于底层具体是申请一段平铺的一维数组 `ElementType array[M * N]` 通过行优先映射，还是声明动态二维指针数组 `ElementType**`，亦或是针对稀疏矩阵采用十字链表（Orthogonal List）存储，ADT 的使用者完全不需要过问。

第三，运算逻辑的抽象。在矩阵加法 `Add` 操作中，声明只保证“返回两矩阵相加之和”，它完全没有限定底层实现代码究竟是先遍历行、再遍历列，还是反过来先列后行；更没有限定必须用 C 语言还是 Fortran 语言实现。

这种将规格说明与具体实现解耦的抽象设计，正是软件工程中高内聚、低耦合架构设计的思想基石。

### 算法的概念与度量体系

#### 算法的定义与核心特征
搞清了数据结构，紧随其后的问题就是：究竟什么是算法？
算法的定义比数据结构更加明晰与严谨：
> **定义**：算法（Algorithm）是一个有限的指令集。它接受零个或多个输入，必须产生至少一个输出，并在有限步骤之后正常终止。

一个合格的算法必须具备以下五项核心特征：
- 有穷性（Finiteness）：算法必须在执行有限个步骤后终止退出。
  > **注意**：算法与程序（Program）有着本质区别。计算机中的某些系统程序（例如操作系统内核）被设计为常驻内存的无限循环事件监听，只要计算机不切断电源，它就会一直运转下去；但在数据结构所讨论的算法范畴中，任何可能陷入无限循环死锁的过程都不能被称作合法算法。
- 确定性（Definiteness）：算法中的每一条指令步骤都必须拥有充分清晰、毫无二义性的明确含义，杜绝任何模棱两可的模糊表述。
- 可行性（Effectiveness）：算法所规定的每一条基本运算，都必须在目标计算机硬件可执行的算力与精度范围之内，目标不可脱离现实技术条件。
- 输入与输出（Input & Output）：算法可以接受外界传入的零个或多个输入参数；但算法必须产生至少一个明确的输出结果（哪怕只是一个状态返回值）。如果一个算法忙碌半天不产生任何对外输出，其存在便毫无实际计算意义。
- 抽象性（Abstraction）：算法的执行逻辑独立于任何具体的程序设计语言以及硬件运行环境。

#### 伪代码与算法的抽象性：以选择排序为例
为了清晰脱离具体语言语法的细枝末节，算法通常使用伪代码（Pseudocode）进行抽象阐释。
以经典的选择排序（Selection Sort）算法为例：
其核心逻辑非常朴素：在一组尚未完成排序的元素集合中，挑选出数值最小的那个元素，将它与未排序子序列的最前端位置（即紧邻已排序子序列末尾的下一个位置）进行交换对调；如此周而复始，已排序序列逐步扩充，直到全部元素完成排序。

```text
未排序状态:   [ (已排序区间) | (未排序区间: 查找全局最小元) ]
                     |                  |
                     +--- 交换对调 <-----+
```
读图说明：字符画展示了选择排序的动态推进机制，未排序区间中检索出的最小元与待排序首位发生交换，有序边界逐步向右延伸。

早期可以用自然语言混杂控制结构书写初级伪代码：
```text
void SelectionSort(int List[], int N) {
    for (i = 0; i < N; i++) {
        从 List[i] 到 List[N-1] 中找一个最小元;
        记录其位置为 min_pos;
        将该最小元换到有序部分的最后位置 (即 List[i]);
    }
}
```
但上述描述中“有序部分的最后位置”等用词不够精准，容易引发边界理解偏差。可以将其进一步提炼为层次分明、规范清晰的模块化伪代码：
```c
void SelectionSort(ElementType List[], int N) {
    int i, min_pos;
    for (i = 0; i < N; i++) {
        /* 从未排序子序列 List[i] 到 List[N-1] 中扫描寻找最小元的物理下标 */
        min_pos = ScanForMin(List, i, N - 1);
        /* 将扫描所得的最小元交换至未排序首位 List[i]，使有序区间边界向右扩展 */
        Swap(List[i], List[min_pos]);
    }
}
```

这段看似贴近 C 语言语法的伪代码，其深层依然保持着极高的抽象度：
- 表结构抽象：虽然语法上写成了类似数组下标访问的形式 `List[i]`，但如果传入的数据载体是一个双向链表，只要在此基础上实现对应的元素扫描与指针交换，整个选择排序的算法逻辑依然完全成立；
- 操作行为抽象：`Swap` 在此看似是一个普通函数调用，但在实际编码落地时，开发者完全可以将其写成预处理带参数的宏指令，或者内联位运算。算法规范本身并不限制具体的指令展开形式。

#### 什么是好算法：时间与空间复杂度
针对同一个计算问题，往往能够构想出五花八门的不同算法。这些算法有的思路愚钝，有的精巧绝伦。我们凭借什么客观量化标准来分出高下？
计算机科学建立了两个维度的核心度量指标：
- 空间复杂度 $S(n)$（Space Complexity）：依据该算法编写的程序，在运行全生命周期中所占用的系统存储单元总长度。
- 时间复杂度 $T(n)$（Time Complexity）：依据该算法编写的程序，在运行全生命周期中所耗费的物理时间总长度。

为什么必须把资源开销明确表达为输入规模 $n$ 的数学函数？
因为资源消耗绝非固定数值，它与所要处理的数据量级 $n$ 呈现直接联动。
要求程序输出 10 个数字，几乎任何机器都能在千分之一秒内瞬时给出结果；但如果要求程序输出 1000 万个数字，哪怕只是简单的遍历打印，也需要可观的耗时。在这里，10 和 1000 万就是问题的数据规模变量 $n$。

在系统架构与算法设计过程中，必须时刻死磕这两个复杂度指标：
- 若空间复杂度失控：程序在运行时会疯狂侵吞系统内存或调用栈空间，导致物理资源耗尽，触发系统保护机制，程序异常崩溃退出（正如递归版 `PrintN` 在 $N=100000$ 时的栈溢出崩盘）；
- 若时间复杂度失控：程序运算步骤随规模爆炸式剧增，运算耗时拉长到人类无法容忍的地步，甚至等到宇宙尽头也跑不出最终结果。

回顾前面的两个案例，其背后的复杂度差异一目了然：
在空间维度：`PrintN` 循环版本的空间复杂度为 $S(n) = O(1)$，常数空间坚如磐石；而递归版本由于多达 $n$ 层的系统调用栈帧滞留，空间复杂度恶化为 $S(n) = O(n)$，在大规模输入下脆弱不堪。
在时间维度：多项式直接求值法由于循环嵌套了幂次方的计算，浮点乘法总次数高达 $\frac{1}{2}n^2 + \frac{1}{2}n$，时间复杂度为 $T(n) = O(n^2)$；而秦九韶算法巧妙收敛至 $n$ 次乘法，时间复杂度压低到 $T(n) = O(n)$，随着数据规模攀升，两者耗时相差数个数量级。

#### 最坏情况复杂度与平均复杂度
在理论分析与工程评估算法的时间开销时，面对千变万化的输入数据样本，主要有两种最核心的复杂度考察视角：
- 最坏情况复杂度 $T_{worst}(n)$：在数据规模为 $n$ 的所有合法输入实例中，算法所消耗的最大时间上界。
- 平均复杂度 $T_{avg}(n)$：在所有可能出现的合法输入实例中，依据各实例出现的概率分布加权计算出的数学期望耗时。

在数学逻辑上显而易见：平均耗时必定不会超过最坏极限耗时，即：
$$T_{avg}(n) \le T_{worst}(n)$$

然而，在计算机算法分析的日常实践中，学者与工程师们压倒性地偏向于分析最坏情况复杂度 $T_{worst}(n)$。
这背后有极其现实的两大原因：
- 绝对可靠的安全防线：最坏情况复杂度为系统运行提供了坚不可摧的保底承诺。它向系统架构师保证：无论外界输入多么刁钻极端、无论遇到什么样的数据形态，系统的运算耗时绝对不会突破 $T_{worst}(n)$ 划定的红线。对于航空航天、工业控制、金融结算等关键领域，这种有确定上限的安全保障是不可或缺的。
- 平均情况在现实中极其难以定义与证明：要计算平均复杂度，前提是必须先准确获知输入数据在现实世界中的真实概率分布。可是在实际工程中，现实输入数据究竟服从均匀分布、正态分布还是长尾分布？其分布规律往往极端复杂甚至随时间动态漂移，导致数学建模与概率积分分析困难重重。

因此，“我们捡容易的做”——抓住了最坏情况复杂度，既避开了概率分布的泥潭，又锁定了最具指导意义的系统性能安全边界。

## 算法复杂度渐进分析、最大子列和问题与线性表顺序存储
> 对应块：BLK02 | 覆盖分集：P07-P14 | 块标题（分集名）：《7_1.2.3 复杂度的渐进表示》

在评估一个算法的好坏时，我们真的有必要像钟表匠一样，一步一步去清点它把哪一行操作具体执行了多少次吗？答案是完全没有必要。真正有意义的指标，是随着处理数据规模 $n$ 的持续增大，算法所耗费时间的增长趋势与本质特征。

如果比较两个算法，当输入规模 $n$ 变得极大时，前者的耗时主要由 $n^2$ 决定，而后者主要由 $n$ 决定。只要 $n$ 充分大，$n^2$ 的增长速度就必然将 $n$ 远远甩在身后，前者的执行速度必然慢于后者。抓住主要增长阶数、忽略次要项与常数因子的粗略分析方法，构成了复杂度渐进表示法的基石。

---

### 复杂度的渐进表示与阶梯分析

#### 渐进符号与上下界界定

在算法分析中，我们使用三种标准的数学符号来刻画算法复杂度的渐进性质：大 $O$、大 $\Omega$ 与大 $\Theta$。它们不仅适用于时间复杂度 $T(n)$，也完全适用于空间复杂度 $S(n)$。

> **定义**：大 $O$ 记号（渐进上界）
> 若存在正常数 $c$ 和非负整数 $n_0$，使得当 $n \ge n_0$ 时，恒有 $T(n) \le c \cdot f(n)$，则记作 $T(n) = O(f(n))$。它表明当数据规模充分大时，$f(n)$ 构成了 $T(n)$ 在渐进意义上的某种上界。

> **定义**：大 $\Omega$ 记号（渐进下界）
> 若存在正常数 $c$ 和非负整数 $n_0$，使得当 $n \ge n_0$ 时，恒有 $T(n) \ge c \cdot g(n)$，则记作 $T(n) = \Omega(g(n))$。它表明当数据规模充分大时，$g(n)$ 是 $T(n)$ 的某种下界。

> **定义**：大 $\Theta$ 记号（渐进等价）
> 当且仅当 $T(n) = O(h(n))$ 且 $T(n) = \Omega(h(n))$ 同时成立时，记作 $T(n) = \Theta(h(n))$。这表明 $h(n)$ 既是 $T(n)$ 的渐进上界，又是其渐进下界，二者的增长阶数在本质上完全等价。

在实际使用这些符号时，必须认清一个关键事实：**一个函数的上界和下界不是唯一的，而是存在无穷多个。**

如果一个算法的实际执行次数是线性增长的，我们可以写成 $O(n)$；但纯从定义上讲，写成 $O(n^2)$、$O(n^3)$ 甚至 $O(2^n)$ 也全部成立——因为 $n$ 确实被 $n^2$ 所界定。下界同样如此，线性算法的下界可以写作 $\Omega(1)$。然而，脱离实际的过大上界或过低下界，对工程实践与算法选型毫无指导意义。

> **准则**：在算法效率分析中，我们书写大 $O$ 表达式时，一律选取能够明确证明的**最小上界**；在书写大 $\Omega$ 表达式时，一律选取能力范围内能够确定的**最大下界**，使边界尽可能贴合算法的真实运行开销。

#### 常见函数增长率与阶梯跨度

为了对不同算法复杂度建立直观感受，下表呈现了典型复杂度函数在输入规模 $n$ 从 1 缓慢增加到 32 时的数值变化：

| 函数类型 | 记号 | $n=1$ | $n=2$ | $n=4$ | $n=8$ | $n=16$ | $n=32$ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 常数阶 | $1$ | 1 | 1 | 1 | 1 | 1 | 1 |
| 对数阶 | $\log n$ | 0 | 1 | 2 | 3 | 4 | 5 |
| 线性阶 | $n$ | 1 | 2 | 4 | 8 | 16 | 32 |
| 线性对数阶 | $n \log n$ | 0 | 2 | 8 | 24 | 64 | 160 |
| 平方阶 | $n^2$ | 1 | 4 | 16 | 64 | 256 | 1024 |
| 立方阶 | $n^3$ | 1 | 8 | 64 | 512 | 4096 | 32768 |
| 指数阶 | $2^n$ | 2 | 4 | 16 | 256 | 65536 | 4294967296 |
| 阶乘阶 | $n!$ | 1 | 2 | 24 | 40320 | $2.09 \times 10^{13}$ | $2.63 \times 10^{35}$ |

> **提示**：为什么在算法分析中写对数 $\log n$ 时通常省略底数？
> 根据对数换底公式，$\log_a n = \frac{\log_b n}{\log_b a}$。以 2 为底、以 10 为底或以自然常数 $e$ 为底的对数之间，仅仅相差一个与 $n$ 无关的常数乘数因子 $\frac{1}{\log_b a}$。由于大 $O$ 记号自动吸收一切常数系数，因此底数并不影响渐进阶数，教科书中均直接简记为 $\log n$。

观察上述函数阶梯可以得到两条深刻结论：

1. **对数函数 $\log n$ 是极其理想的增长速度**：当输入规模翻倍时，它仅仅增加 1；当输入规模达到 32 时，对数值才仅仅增长到 5。
2. **避免指数与阶乘算法**：当 $n$ 仅仅为 32 时，$2^n$ 已经接近 43 亿，而 $n!$ 已经膨胀到 $10^{35}$ 量级。在日常算法设计中，必须极力避免设计出阶乘级或高底数指数级的算法。

各典型函数随规模增长的直观分层可以用如下关系图概括：

```text
增长速度极慢 <-------------------------------------------> 增长速度灾难
1  <  log n  <  n  <  n log n  <  n^2  <  n^3  <  2^n  <  n!
[最优区间]       [工程可用区间]    [需警惕区间]    [不可行区间]
```

*图解说明：从左至右函数增长率急剧上升。在实际系统开发中，算法设计的目标是尽可能将算法压制在 $n \log n$ 及以内区间。*

> **核心工程素养**：作为一个专业的程序员，在构思算法时，每当发现初步方案的时间复杂度是 $O(n^2)$ 时，下意识的本能反应必须是：**我有没有办法把它优化到 $O(n \log n)$？**
> 设想当数据规模达到 $n = 10^6$（一百万）时：$n^2 = 10^{12}$，而 $n \log_2 n \approx 10^6 \times 20 = 2 \times 10^7$。二者的运算步数相差整整 5 万倍！这直接决定了程序是在数秒内返回结果，还是需要连续运行数天。

假设一台计算机每秒能够稳定执行 $10^{11}$ 条指令，不同复杂度算法处理不同规模数据所需的理论运行时间对照如下：

| 数据规模 $n$ | $n$ 耗时 | $n \log_2 n$ 耗时 | $n^2$ 耗时 | $2^n$ 耗时 |
| :--- | :--- | :--- | :--- | :--- |
| $10$ | $10^{-10}$ 秒 | $3.3 \times 10^{-10}$ 秒 | $10^{-9}$ 秒 | $10^{-8}$ 秒 |
| $10^2$ | $10^{-9}$ 秒 | $6.6 \times 10^{-9}$ 秒 | $10^{-7}$ 秒 | $1.3 \times 10^{19}$ 年（无法完成） |
| $10^3$ | $10^{-8}$ 秒 | $10^{-7}$ 秒 | $10^{-5}$ 秒 | 宇宙级天文学时间 |
| $10^4$ | $10^{-7}$ 秒 | $1.3 \times 10^{-6}$ 秒 | $10^{-3}$ 秒 | 不可计算 |
| $10^5$ | $10^{-6}$ 秒 | $1.7 \times 10^{-5}$ 秒 | $0.1$ 秒 | 不可计算 |
| $10^6$ | $10^{-5}$ 秒 | $2 \times 10^{-4}$ 秒 | $1.7$ 分钟 | 不可计算 |

这里要留个心眼：这张表上其实印着一个错误，而且是留给大家自己发现的——表格里有一列的表头被标成了 $\log n$，可它对应的运行时间居然比 $n$ 还慢。这显然不可能，因为 $\log n$ 比 $n$ 要快得多。它比 $n$ 慢、又比 $n^2$ 快，恰好介于两者之间，所以它真正的身份只能是 $n \log n$。这个辨析我们放在文末的《本讲提到的题目》里正式展开。

#### 复杂度分析的实用规则

在分析实际代码段时，可运用以下几条通用法则快速锁定算法的渐进阶：

1. **加法规则（顺序执行）**：如果代码由两个先后执行的独立模块拼接而成，总时间复杂度为两部分开销之和，其渐进阶取决于增长较快的那一部分：
   $$T_1(n) + T_2(n) = \max(O(f_1(n)), O(f_2(n)))$$
2. **乘法规则（嵌套执行）**：如果代码存在嵌套调用或内外层循环，其渐进阶为内外层开销的乘积：
   $$T_1(n) \times T_2(n) = O(f_1(n) \times f_2(n))$$
3. **多项式主部规则**：若时间复杂度可表示为关于 $n$ 的 $k$ 阶多项式 $T(n) = a_k n^k + a_{k-1} n^{k-1} + \dots + a_0$（其中 $a_k > 0$），则其渐进复杂度严格由最高阶项决定，所有低阶项与常数系数均可直接忽略：
   $$T(n) = O(n^k)$$
4. **循环结构分析**：一个 `for` 循环的时间复杂度，等于循环迭代的总次数乘以单次循环体内部代码的复杂度总和。
5. **分支结构分析**：对于 `if-else` 条件判断结构，其时间复杂度取决于条件判断表达式、`then` 分支代码段与 `else` 分支代码段这三者复杂度的最大值。

把这几条用顺了，我们就可以来试试看。下面就看一个应用实例——最大子列和问题。

### 经典案例：最大子列和问题的四种算法演进

> **问题描述**：
> 给定由 $n$ 个整数构成的序列 $\{A_0, A_1, \dots, A_{n-1}\}$，求连续子列和的最大值：
> $$\max_{0 \le i \le j < n} \sum_{k=i}^j A_k$$
> 规则约束：如果该序列的所有连续子列和均为负数，则规定最终的最大子列和返回 0。

#### 暴力枚举：立方阶算法

最直观、最不假思索的解法就是穷举法：枚举所有可能的连续子列边界 $(i, j)$，再通过内层循环逐一累加求和，并在遍历中实时记录最大值。

```c
int MaxSubsequenceSum1(int A[], int N) {
    int ThisSum, MaxSum = 0;
    int i, j, k;

    for (i = 0; i < N; i++) {          /* 子列左端位置 */
        for (j = i; j < N; j++) {      /* 子列右端位置 */
            ThisSum = 0;               /* 初始化当前从 A[i] 到 A[j] 的子列和 */
            for (k = i; k <= j; k++) {
                ThisSum += A[k];
            }
            if (ThisSum > MaxSum) {    /* 若发现更大的和，则予以更新 */
                MaxSum = ThisSum;
            }
        }
    }
    return MaxSum;
}
```

该算法由三重嵌套的 `for` 循环构成：外层循环 $i$ 遍历 $N$ 次；中层循环 $j$ 从 $i$ 遍历到 $N-1$；最内层循环 $k$ 从 $i$ 遍历到 $j$。

虽然说后两重循环的边界并不是从 0 一直到 $n$，不能简单地把三个 $n$ 乘在一起，但用中学的求和技巧一算，整个运算量仍然是 $n^3$ 乘以一个常数，答案就是大 $O$ 的 $n$ 立方。

我们想象一下当 $n$ 等于 10 万的时候，$n^3$ 是什么概念——那是相当恐怖的一个景象。

#### 记忆累加：平方阶算法

这个算法到底不聪明在哪里？我们来演示一遍：先从 $i$ 等于 0 开始，加了一个数；然后算第二个子列的时候，又从 0 一直加到 1；算第三个子列的时候，从 0、1 一直加到 2；点点点一直到最后一个循环从 0 一直加到 $n-1$。然后 $i$ 往前进了一位，我们从 1 开始，加 1、加 2，点点点一直加到 $n-1$；然后 $i$ 等于 2 的时候又继续。

看到中间有一个很大的问题了吧？当我们已经知道当前从 $i$ 到 $j$ 的和的时候，接下来要计算下一个 $j$ 的时候，我有必要从头开始往后加吗？**没有必要！** 所以当 $j$ 增加了一的时候，我们其实只要在前面那个 $i$ 到 $j$ 的部分和基础上，再加一个元素就好了。$k$ 循环完全是多余的。

这样呢就有了我们的算法二：外面依然有一个 $i$ 循环作为子列左端位置，依然有 $j$ 循环作为子列右端位置，不同的是当前的这个部分和 `ThisSum` 归零是从这里开始的，每增加一个值的时候，只是在当前部分和的基础上加一个 $A_j$ 就可以了。也就是说对于相同的 $i$、不同的 $j$，只要在前一次循环的基础上累加一项就可以。

```c
int MaxSubsequenceSum2(int A[], int N) {
    int ThisSum, MaxSum = 0;
    int i, j;

    for (i = 0; i < N; i++) {          /* 子列左端位置 */
        ThisSum = 0;                   /* 对于同一个 i，每次向右延伸前清零 */
        for (j = i; j < N; j++) {      /* 子列右端位置 */
            ThisSum += A[j];           /* 在已知前项和的基础上直接累加 A[j] */
            if (ThisSum > MaxSum) {
                MaxSum = ThisSum;
            }
        }
    }
    return MaxSum;
}
```

很显然，这回是两重循环的嵌套，所以答案应该是大 $O$ 的 $n$ 平方。这个算法比前面那个已经聪明很多了——前面是 $n$ 立方，这个是 $n$ 平方，$n$ 有 10 万这么大的时候，这两个算法的效率就差了 10 万倍，是一个很大的进步。

但是它可不是最好的。专业的程序员设计了一个算法，发现这个算法是 $O(n^2)$ 的时候，下意识的本能就应该想：有没有可能把它改进成为 $n \log n$？那可还要快很多。

#### 分而治之：线性对数阶算法

怎么做呢？这就是我们的第三个算法。

我们的第三个算法有一个很高大上的名字，叫做**分而治之**。分而治之的思想可以用来解决很多的问题：把一个比较大的复杂问题切分成小的块，然后分头去解决它们，最后再把结果合并起来，这就叫分而治之。

在这个问题上怎么工作呢？首先我们假设问题是放在一个数组里面的。算法第一步是**分**，也就是把这个数组从中间一分为二，然后递归地去解决左右两边的问题。递归地解决左边，会得到左边的一个最大子列和；递归地解决右边，会得到右边的一个最大子列和。然后就可以了吗？这两个数中间最大的一个就一定是结论吗？那可不一定。还有一种情况，就是**跨越边界的最大子列和**。

把这三个结果找到以后，我们真的可以说最后的结果一定是这三个数中间最大的那一个。所以这个就叫做分，最后的合成就叫做治，总体来说叫做分而治之。

```text
原数组 A[0 ... N-1]
+-----------------------------------+-----------------------------------+
|             左半部分              |             右半部分              |
+-----------------------------------+-----------------------------------+
                  \                                   /
                   \                                 /
        递归求得：左侧最大和               递归求得：右侧最大和
                   \                                 /
                    \       跨越中线的最大子列和    /
                     \     +--------------------+   /
                      ---> | 左跨界和 + 右跨界和 | <---
                           +--------------------+
                                     |
                                     v
                       最终解 = max(左, 右, 跨界)
```

*图解说明：最大子列和在分治体系下必然且仅可能出现在三个区域之一——完全落在左半边、完全落在右半边、或者横跨中线切分边界。*

跨越边界的最大子列和怎么求？以 8 个元素的序列为例走查一遍：先从中间把它一分为二，递归地先解决左半边；递归进入左半边的时候，继续一分为二，继续递归到左半边，继续分。分的时候，从这个左边我们会得到最大子列和，显然就是 4；而这边它是个负数，所以应该返回 0；那跨越这个边界的最大和呢，也是 4。于是我们知道解决这个子问题它返回的解应该是 4。

完全类似地，我们去解决它的右半边，返回的结果应该是 5。然后对于这四个数字而言，我们还要算一个跨越边界的最大和：想一下，我们只是从中间这个切分线开始，先从中间往左边扫描，我们会得到 -3、得到 1，然后就会发现最大左边的是 1；往右边呢，我们会得到 5，然后把这个包进去，我们会得到 3。于是我知道最大的子列和是 5。

两边加在一起，跨越边界的这个最大子列和是 6。所以当我们从左边这四个数的这个递归函数返回的时候，我们应该返回 6。

然后你知道怎么去解决右半边的问题了对不对？那我们快一点来说：先把它对分，然后左边得到 2，右边得到 6，跨越边界的最大子列和是 8。那么对于最后这个问题，我们还需要算一个跨越边界的最大子列和——这边呢要一直扫描到底，发现这个数是最大的；这边呢扫描到 6 的时候就可以停下来了。总体来说这个和是 11。

于是我们比较一下 6、8 和 11 这三个数，返回 11 作为我们这个问题的最终的解。

看上去呢其实也不是很复杂，但是那个程序呢写起来还蛮长的，所以我们就不在这展示那个程序了，我们的教科书里面有，大家可以自己去看。**难点呢是在于怎么样分析它的算法复杂度。**

你现在能不能先猜一猜它的复杂度会是多少呢？我们在算法二结束的时候曾经说了，算法二的复杂度是 $n$ 平方，我们嫌它不够好，我们说本能的应该把它提高到 $n \log n$。那么这个算法它真的是 $n \log n$ 的复杂度吗？

分析这种递归的算法略微有一点难度。他的想法是什么呢？想象当我解决整个问题、有 $n$ 个数字的时候，如果我的复杂度把它记作 $T(n)$ 的话，那么我得到这半边数字的时间复杂度就应该是 $T(n/2)$，因为我的规模减半了；同样的道理，我得到这一半递归结果的时间复杂度也应该是 $T(n/2)$。

而我是怎么得到中间这个跨边界最大子列和的呢？我们的做法就是从中间开始往左边扫描，然后往右边扫描，每一个元素都被扫描了一次，所以得到这个结果的复杂度应该是 $n$ 的一个常数倍。由此呢我们就得到了关于 $T(n)$ 的一个递推公式：

$$T(N) = 2 T(N/2) + c \cdot N, \quad T(1) = O(1)$$

$n$ 等于 1 的时候它是常数，然后我们要怎么递推呢？把这个 $n$ 换成 $n/2$，再带到这里面去：

$$T(N) = 2 \left[ 2 T(N/4) + c \frac{N}{2} \right] + c N = 2^2 T(N/4) + 2 c N$$
$$T(N) = 2^2 \left[ 2 T(N/8) + c \frac{N}{4} \right] + 2 c N = 2^3 T(N/8) + 3 c N$$

如果你还觉得这个规律不够清楚的话，你就再展开一步看看。我们这个可以一直往下展开，展开到 $T$ 里面的这个数等于 1 为止。过了 $k$ 步以后呢，我们这边应该是 $2 \times 2 \times 2 \cdots$ 乘了 $k$ 个 2，然后中间这一项变成 1 了，所以变成了一个常数 $O(1)$。

这个呢就是每展开一层就多一个 $cN$。所以展开了 $k$ 步以后呢，我们就是 $c$ 乘以 $k$ 乘以 $n$。其中 $k$ 和 $n$ 是什么关系呢？就是 $n$ 除以 2、除了 $k$ 次以后最终它会得到 1，它可能不一定正好整除乘 1，但是也差不多，道理是一样的。两边乘以 $2$ 的 $k$ 次方，我们知道这一项是得 $n$ 的，$2$ 的 $k$ 次方就是 $n$。那什么是 $k$ 呢？$k$ 就是以 2 为底的 $\log n$。

所以在分析复杂度的时候，我们就有了两项，一项是大 $O$ 的 $n$，一项是大 $O$ 的 $n$ 乘以 $\log n$。我们之前有学过，当两个复杂度加在一起的时候我们取的是比较大的那一项，于是呢我们就得到了整个这个算法的复杂度是大 $O$ 的 $n$ 乘以 $\log n$。

#### 在线处理：线性理论最优解

看明白了吗？然后我要说的是，这仍然不是我们最快的算法。我们前面说 $n \log n$ 已经是很快的算法了，但是在解决这个问题来说，它仍然不是最快的。我们还有一个更快的算法，叫做**在线处理算法**。

这个算法的伪码描述现在出现在屏幕上。你不需要去理解它为什么是正确的，你只要很快的速度告诉我，它的时间复杂度是多少。很显然这个算法描述里面只有一个 `for` 循环，`for` 循环里面所有的 `if-else` 这些东西，它都是常数数量级的复杂度，所以很显然这个算法的复杂度就是 $O(n)$，是线性的。

这个必须是我们可能得到的最快的一个算法了，因为无论如何我们总得把每一个元素看一遍吧，就我读输入也需要 $O(n)$ 的时间。所以解决整个问题居然可以用 $O(n)$ 的速度，那已经是我们可以想象的最快最好的算法了。

当然一个算法的效率这么高，一般来说是有副作用的。副作用就是什么呢？它的正确性不是特别的明显，也就是说别人要理解这个程序到底是怎么工作的，略微有点困难。

为了更好地理解它，我们还是先来看一个例子。这仍然是有八个数字，我们一个数字一个数字地开始处理，走一遍这个程序。那最开始我们仍然是有 `ThisSum` 当前的子列和、`MaxSum` 最大的子列和，都初始化为零。然后我们就进入了这个很重要的 `for` 循环。

第一件事做了什么呢？就是把当前这个数加进当前的子列和里。那我们看到的第一个数字是 $-1$，$-1$ 加进来。那 $-1$ 呢并不能使当前的最大和变大，所以这一块被跳过去了。重要的是这一条：**如果当前的子列和是负的，那么我们就直接把它抛弃，把当前子列和重新归零**，把这个 $-1$ 直接扔掉。

为什么可以这么做呢？因为我们是要求连续的子列和，所以如果当前子列和到这里是负的，下一步我们是要顺着往后去求和的。如果现在的和是负数的话，往后面不管加什么数，它都只能让后面的数字越变越小，不可能越变越大。所以我还不如从头加起，因为它不可能使后面的部分和增大，所以就抛弃之。

然后进入 `for` 循环的第二轮。我们开始读下一个数字，读进来的是 3，然后我们发现当前的这个 3 比 `MaxSum` 要大，于是当前的最大子列和我们先记一下，更新为 3。然后因为 `ThisSum` 是正的，所以我们进入下一个循环，再加一个，再加一个是 $-2$。于是当前和呢是正 1，正 1 比 `MaxSum` 要小，所以最大和是不动的。而这个 `ThisSum` 当前的和也不会被抛弃，因为它是正 1，总有可能使后面的和变得更大的。于是我们继续进入下一轮，读下一个数字 4。

果然他是把下一个数变大了，现在当前和是 5，比现在的最大和要大，所以最大和要更新一下，变成了 5。

```c
int MaxSubsequenceSum4(int A[], int N) {
    int ThisSum = 0, MaxSum = 0;
    int i;

    for (i = 0; i < N; i++) {
        ThisSum += A[i];               /* 向右累加当前元素 */
        if (ThisSum > MaxSum) {
            MaxSum = ThisSum;          /* 发现更大和则刷新纪录 */
        } else if (ThisSum < 0) {
            ThisSum = 0;               /* 核心准则：累加和一旦转负，立即归零重置 */
        }
    }
    return MaxSum;
}
```

为什么这个算法叫**在线处理**呢？我们看到整个的处理过程是什么样的呢？就是一个数字一个数字地读进来。而我的输入如果说到现在为止我突然停住，后面的输入不读了，那么现在这个程序就应该给我返回 5 作为当前的最大子列和，而这个结果是对的，就对于前四个数字而言，这个结果是对的。这个就叫做在线处理。

那我们继续往下走啊。现在是 5，然后往下加一个 $-6$，于是当前的子列和变成了 $-1$，它是负的了，我们就把它抛弃掉，重新归零，开始考虑下一个。下一个是 1，什么都没变化；再下一个是 6，加起来等于 7，它比原来的最大和要大了，所以最大和更新一下；然后再加一项进来是 $-1$，什么都没改变。

输入结束了，我们跳出来，返回的这个结果是 7。

所以为什么它会快呢？它就是充分利用了这一点：**一旦发现当前的子列和是负的，它其实就没有用了，直接就把它抛弃掉，我们扫描后面的就可以。** 在线的意思就是指每输入一个数据就及时地进行处理，在任何一个地方终止输入，算法都能给出正确的当前的解。

接下来这张表是在某一台机器上跑出来的结果，有兴趣的话呢你可以真的把这四个算法全部都实现一下，然后跑一下，看看他们的时间怎么样。那这一列呢是 $n$ 从 1 一直到 10 万。$n$ 立方的这个算法呢，跑到 $n$ 等于 1 万的时候它已经跑不动了，表里的 N/A 的意思是 not available啊，就不算了。$n$ 平方呢，算到 10 万的时候它也算不下去了。而我们看 $n \log n$，虽然最后也多花了几秒钟，但是仍然是在几秒钟以内给出结果的。而表现最好的当然是线性的算法，$n$ 等于 10 万的时候，仍然是在小于一秒的时间内给出结果。当然我们这个结果里头没有算输入输出的。

### 线性结构与一元多项式的表示抉择

线性结构是数据结构里面最基础、也是最简单的一种数据结构类型，其中典型的我们叫线性表。

那么什么是线性表呢？我们举一个简单的例子给大家看一下——关于一元多项式的表示的问题。大家知道一元多项式的基本形式是 $a_0 + a_1 x + \cdots$，其中的每一项是叫 $a_i x^i$。这样的一个多项式呢，它的基本运算就包括两个多项式相加、相乘、相减等等。这些运算我们就碰到了一个问题：怎么用程序设计语言来表示这样的一个多项式，以及实现相应的操作。

#### 问题的抽象与关键信息提取

首先我们来考虑一下多项式如何进行表示。在程序设计语言里面要表示一个问题，首先我们要分析一下这个问题的关键数据、关键信息在哪里。对多项式来讲，它的关键信息主要有这么几个：

1. 一个是它的**项数**，包括它的**最高指数**；
2. 另外我们很重要的是要表现多项式的**每一项**。而多项式的每一项的关键信息呢，又是每一项的**系数**和**指数**。

#### 下标即指数的数组直接表示法

多项式的一种表示我们有很多方法，其中一种最简单的方法呢，就是我们称之为顺序存储的一种直接表示。首先一个的话，我们可以用一个数组来表示多项式的有关信息。多项式的每一项我们可以用一个分量来表示，这个分量呢主要表示每一项的系数。那么指数怎么表示呢？**指数我们可以对应于这个分量的下标。**

比方说我们用 `A` 这个数组来表示一个多项式，`A[i]` 就可以表示相应的项的系数，而这个 `i` 呢就是对应的指数。所以用这样的一种表示方法，打个比方来说，我们有这样的一个多项式叫 $4x^5$ 减 $3x^2$ 加 1，我们可以很直截了当地用这样一个数组来表示：

```text
数组下标 Index (对应指数 Exponent) :  [0]   [1]   [2]   [3]   [4]   [5]
数组元素 Value (对应系数 Coeff)    :   1     0    -3     0     0     4
对应多项式项                     :  1*x^0  0*x^1 -3*x^2  0*x^3  0*x^4  4*x^5
```

*图解说明：数组连续分配 6 个空间，通过下标天然隐式表达指数，数组内显式存放系数。*

这样子表述方法呢是非常简单的，而且它做的有关的一些操作也容易实现，比方说两个多项式相加，它就变成两个对应数组的对应分量的相加。

但是这里面呢也有一些问题。比方说我们看这个例子，我们这个多项式呢是 $x$ 加上 $3x^{2000}$，我们要用多大的数组来表示这样的一个多项式呢？显然我们要用至少 2001 个分量的这样的一个数组来表示。而且这 2001 个分量我们可以看得到，其实只有两项是非零的，其他全是零。这样的一种表示方法呢，显然会造成空间的巨大浪费。而且做加法运算的时候呢，你怎么说也要做一个循环，从 0 开始一直做到 2000，实际上的话很多计算是又在加无效的零。

所以这种表示方法呢虽然方便，但是呢也有很大的问题。

#### 只存非零项：结构数组表示法

所以我们在想有没有可能用更好的方法：为什么要把所有指数项系数为零的非零项全都要表示进来呢？有没有可能我只表示非零项？

这就引入了第二种方法，它的基本思路是这样的：**我只表示非零项**。那么非零项有什么东西？每个非零项实际上有两个信息，一个是系数，一个是指数。所以的话我们可以把多项式看成一个由系数和指数二元组组成的一种集合，所以我们也可以用数组来表示。那么数组的每个分量是什么呢？跟前面就不一样了——前面每个分量是系数，现在呢我们这里的每个分量就不能简简单单是系数了，而且要包含指数。

那用什么样的类型呢？可以用结构数组。所以我们可以用结构数组来表示这样的多项式，数组的分量呢是由系数和指数所构成的一种结构，它对应的是我们一个非零项这样的一种表示方法。

举个例子来说，我们现在有两个多项式，一个 `P1` 有三项，一个 `P2` 有四项，我们可以很简单地用这样的一种数组来进行表示。用这样的一种表示方法呢，显然我们只要表示非零项就可以了，很多零的项呢我们可以省下来。所以对于前面我们看到的 $x$ 加上 $3x^{2000}$，我们只要用两个分量来表示就行了，空间显然大大节省了。

那这样的表示方法运算方便吗？我们同样可以做到运算方便地进行，其中要点就是：**我们的每一项按照指数大小的有序进行存储。** 在我们这个例子里面呢，我们把指数大的排在前面，指数小的排在后面，按照这个顺序进行排列。

那么这样的一种做法，他怎么做加法运算呢？我们来看一下。就前面这个例子，我们的 `P1` 实际上是三项，`P2` 有四项，我们按照指数递降的这样一个顺序进行排列，那我们的加法过程可以从头开始比较。

- 比较的第一项，`P1` 的第一项是 $x^{19}$，`P2` 的第一项也是 $x^{19}$，这两个一比较呢，我们就要看指数谁大，显然是 19 大。所以和多项式的第一项一定是 $x^{19}$，所以和的第一个结果就是 $x^{19}$，`P2` 的第一项作为我们和的结果第一项输出了；
- 接下来我们继续比较，比较 `P1` 的第一项跟 `P2` 当前的这一项，也就是说比较 $x^{12}$ 和 $x^8$，显然又是 12 大，所以接下来呢 $x^{12}$ 这个输出，`P1` 的下一项，也就是说是 $x^8$，跟 `P2` 的 $x^8$；
- 当它两个系数不一样，一个是 15，一个是 -4，这显然这两个指数一样，就系数相加，加后的结果呢是等于 11，所以我们输出了和的第三项；
- 接下来我们再比较 `P1`、`P2` 的各后面这一项，它们分别是 $x^2$ 这一项跟 $x^6$ 的这一项，显然 $x^6$ 大，所以我们继续输出；
- 这个时候呢，接下来的会比较 `P1` 这一项的 $x^2$ 跟我们的这个 $x^0$，输出的是 $x^2$；
- 这一项 `P1` 已经结束了，所以下面的话就只剩下 `P2` 的剩下的内容输出就可以了。

所以这就是我们两个多项式相加的结果。它的基本方法就是从头开始比较，看哪个指数高，那个指数高的那项出来；指数相等，对应系数相加。

所以我们用指数系数构成的结构存储在数组里面来表示非零项，这样的一种方法是一种节省空间的方法，而且它的操作效率呢也不算差。

#### 链表表示法

同样的表示非零项的这样一种方法，我也不一定说一定要用数组来做，我们可以用另外一种方法——**链表**。所以这就引入了我们的第三种方法，我们可以用链表结构来存储我们的非零项。

同样的道理，在这个链表里面每个节点也是包含两个最主要的信息，一个是指数，一个是系数，然后用一个指针域把不同的节点串起来。同样排列的时候呢，我们仍然可以按照指数递降的顺序进行排，或者递增，也可以按照一定的顺序有序地进行排列就可以了。

对于这样的一种表示方法呢，对应的这个结构定义呢可以写成这样子：

```c
typedef struct PolyNode *Polynomial;
struct PolyNode {
    int coef;              /* 系数 */
    int expon;             /* 指数 */
    Polynomial next;       /* 指向下一个非零项节点的指针 */
};
```

所以的话，我们前面的两个多项式如果用链表存储的形式呢，可以表示成这样的两个列表，它也是按照指数递降的顺序进行排列的。同样的它的两个加法运算，它的整个逻辑过程跟前面的两个数组的运算是一样的：也就是说我们分别指向两个列表的头，然后比较指数的大小，大的输出，相等的话系数相加。

所以这就是我们给大家看到的同样的一个问题——多项式这样的一个问题，可以有多种的表示方法。可以用数组实现，也可以链表实现。用数组实现呢，还有两种方法，一个的话是直接的表示，还有一个呢只表示非零项。

前面这个多项式的问题给我们什么启示呢？**首先，同一个问题可以有不同的表示方法。** 那么一般来说我们在数据结构里面最常见的就是两种方法：要么用数组来存储，要么用链表来存储。

实际上不仅仅是多项式这个问题，还有很多其他一系列问题，更多有价值的问题是有共性的：也就是我们的目标是想管理一个有序的一种线性序列，我们就把它归结为一个线性表这样的一个问题。

### 线性表抽象数据类型与顺序存储实现

那么什么是线性表？线性表是由同类元素所构成的一个有序序列这样一种线性结构。表中的元素个数呢，我们称为线性表的长度；当表中没有元素的时候，我们称为空表；这个表的起始位置的那个元素呢，我们称为**表头**；最后一个位置的元素呢我们称为**表尾**。

#### 线性表定义与 ADT 规格

对线性表来说，我们可以用一种抽象数据类型来进行描述。前面介绍过，所谓抽象类型实际上包含了两个要素：一个是这个类型所包含的数据对象集是什么，另外一个是在这个对象集上面有什么操作。

那么对线性表来说，它的对象集呢是由 $n$ 个元素所组成的一个有序的序列。假定说线性表类型叫 `List`，对于其中的一个具体的线性表我们叫 $L$，它里面的元素 $x$ 它有个类型叫 `ElementType`，这个类型可以是整形，也可以是实型，也可以是个结构啊，那我们这里统称为 `ElementT`。

其实我们还用整数来表示一个元素在表中的所在的位置。主要操作有哪些呢？有这么一些：一个是建立一个空表；另外一个呢，在这个表里面去找位序为 $k$ 的这个元素；还有一个呢，给你一个元素，让你去在这个表里面找它第一次出现的位置在哪里；还有呢，就是在线性表的前面插入一个新的元素；还有就是指定删除某一个元素；这个元素所在的位置是 $i$；还有呢，返回线性表的长度。

这是我们给出的一种抽象数据类型的描述。我们接下来更关心的是：一般的线性表是怎么存储的，以及我们列的这几个操作是怎么实现的。

#### 顺序存储结构定义与空表初始化

那么线性表怎么存储呢？根据我们前面多项式的这个例子来讲，我们可以想象得出来，其中一个最简单的一种存储方法就是顺序存储，就是用数组的方法来进行实现。

前面刚才讲的线性表，它是一个序列 $a_1, a_2, a_3, \dots, a_n$ 这样的一个序列，我们可以按这个顺序就把它放在数组里面，从下标为零开始的这样的一个地方。这样的一种存取方法呢，我们相应的一些数据结构的定义应该是怎么样呢？在这样的存储方法里面，显然我们有两个东西需要知道的：

- 一个是这个数组是什么。因为数组你可以放不同长度的这样一个线性表，它是连续存放的，那它最后一个元素在哪里，所以我们要有一个指针 `Last` 来指示在这个数组里面放的线性表的最后一个元素所在的位置；
- 数组呢，我们这叫 `Data`，定义一个数组它的类型分量类型是 `ElementT`；再定义一个 `Last`，代表线性表最后一个元素。

这样构成的一个结构，那么这个结构呢就可以抽象了，实现我们的一个线性表。那么利用这样的一个线性表这个类型，我们可以定义一个变量 $L$，还有个 `PtrL`。

打个比方说我们想访问下标为 $i$ 的元素，按照这样的一种实现方法是很简单的，就是 `L->Data[i]` 或者 `PtrL->Data[i]` 就可以了。

线性表的长度呢？那直接取 `Last` 的值就可以了。因为我们是从零开始的，所以长度是 `Last` 加一。

```c
#define MAXSIZE 1000                  /* 数组预分配的最大容量 */
typedef int ElementType;              /* 元素类型别名，按需定制 */

typedef struct LNode *List;
struct LNode {
    ElementType Data[MAXSIZE];        /* 连续存储元素的物理数组 */
    int Last;                         /* 关键游标：指示线性表中最后一个元素的数组下标 */
};
```

```text
数组物理索引:   [0]       [1]       [2]     ...    [Last]    [Last+1] ... [MAXSIZE-1]
线性表逻辑元素:  a_1       a_2       a_3     ...     a_n       空闲         空闲
               ^                                   ^
               表头                                表尾 (由 Last 精准锁定)
```

*图解说明：线性表元素从数组下标 0 开始连续存放，游标 Last 始终指向当前实际最后一个元素的存储下标。*

> **易错点**：游标 `Last` 的物理意义与边界
> 必须时刻警惕数组下标与逻辑长度的对应关系：数组从下标 0 开始计数。
> - 当表中存在 1 个元素时，该元素存放在 `Data[0]`，此时 `Last = 0`；
> - 当表中存在 $n$ 个元素时，末尾元素存放在 `Data[n-1]`，此时 `Last = n - 1`，表长计算公式为 `Length = Last + 1`；
> - 当表为空表（没有元素）时，`Last` 必须初始化置为 `-1`。

#### 空表的初始化

首先一个初始化 `MakeEmpty`，它的实现方法显然是比较简单的。前面提到过我们表的表示呢是用结构来表示，它包含了数组，还有代表最后一个元素的 `Last`。

所以我们首先呢就想要去申请这样的一个结构。所以建表呢，第一个是通过 `malloc` 这个函数申请这样的一个结构，然后把结构的 `Last` 呢设为 $-1$。因为 `Last` 的是代表最后一个元素，所以 `Last` 是 0 呢是代表这个表里面有一个元素放在第一个位置，没元素呢就是为 $-1$，然后把这个结构的指针呢返回回来。

```c
List MakeEmpty() {
    List PtrL;
    PtrL = (List)malloc(sizeof(struct LNode));   /* 动态分配结构体容器 */
    PtrL->Last = -1;                             /* 空表标记：末项游标置为 -1 */
    return PtrL;
}
```

#### 元素查找操作

接下来我们要说 `Find`，他是给你一个 `PtrL`，它是一个线性表结构的指针，通过这个结构我们知道这个数组是谁、`Last` 是谁。然后呢，我要在这个线性表里面找 $x$ 它所在的位置，可以通过一个循环来实现。

这个变量是 $i$，我们从零开始一个个地往后找，一直找到最后一个元素 `Last` 这个位置。然后呢在找的过程当中呢，比较一下我们的 `Data[i]` 是不是等于 $x$。如果等于 $x$ 说明找着了，如果不等于，那么这循环不断地做，`i` 不断地往后挪。

当这个循环退出来的时候，有两种可能：第一种可能呢是 `Data[i] != x` 这个条件被破坏了，也就是说找到一个 `Data[i]` 等于 $x$ 了；还有一种呢是 `i <= Last` 这个条件被破坏了，那么也是 $i$ 大于 `Last` 的。那么这两种情况实际上对于找到和没找到这两种情况。所以的话如果 $i$ 大于 `Last`，说明是没找着，那就 `return` 一个 -ERROR；否则的话就找着了，那么 $i$ 就是我们相应的这样的一个位置。

```c
int Find(ElementType X, List PtrL) {
    int i = 0;
    while (i <= PtrL->Last && PtrL->Data[i] != X) {
        i++;
    }
    if (i > PtrL->Last) {
        return -1;                     /* 遍历越界，说明表中不存在该元素，返回未找到标记 */
    } else {
        return i;                      /* 成功匹配，返回该元素首次出现的数组下标 */
    }
}
```

这样的一种走法呢，可以知道他的操作成功的平均比较次数是 $\frac{n+1}{2}$，也就是运气好，第一个就找着了；运气不好，最后一个找着的。那么平均就是一加上 $n$ 次除以二。

#### 元素插入操作

接下来我们介绍第三个操作，就是插入。插入它的目标呢，是要在这个线性表的第 $i$ 个位置上面插入 $x$ 这个元素。这里的第 $i$ 个位置呢指的是 $i$ 的值是从 1 到 $n+1$，就插在线性表头上，$n+1$ 插在线性表最后。

那么线性表是在数组里表示的，下标是从零开始的，所以实际上就意味着我们要把我们的这个元素呢放到 $i-1$ 这个位置。你要把新插入的元素 $x$ 放在 $i-1$ 这个位置，那怎么办？它是连续存放的，所以你首先要做的事情是要把 $i-1$ 之后的这些元素全部往后挪一位，腾出 $i-1$ 这个位置来，然后再往里面放。所以这个操作呢，第一个要想做的事情是先移动，也就是说每个元素都往后挪。

显然有一个循环就可以做了。但这个循环怎么写？是从 $i-1$ 挪到 $i$，$i$ 挪到 $i+1$ 一个往后挪，还是倒过来挪？$n$ 挪到 $n+1$，$n-1$ 挪到 $n$，显然应该是**从后面开始挪**——把最后一个往后挪，倒数第二个往后挪。否则的话你从前往后挪，那么这个算法是不对的。

```text
原始状态 (在位序 i 插入，对应下标 i-1):
下标:     ...   [i-2]      [i-1]        [i]      ...     [Last]      [Last+1]
元素:     ...   a_{i-1}     a_i        a_{i+1}   ...      a_n          (空闲)
                             |          |                  |
数据平移方向:                 |          |    从后往前倒序平移 |
                             v          v                  v
腾挪后:   ...   a_{i-1}    [空位]       a_i      ...     a_{n-1}       a_n
                             |
填入新项:                    v
新状态:   ...   a_{i-1}      X          a_i      ...     a_{n-1}       a_n
```

*图解说明：必须从最末尾的 Last 元素开始由后向前依次覆盖右侧邻位。若由前向后移动，右侧已有元素将被瞬间覆盖销毁。*

> **核心陷阱**：移动循环的遍历方向
> 移动循环必须严格**从后向前倒序推进**！控制变量 $j$ 从 `PtrL->Last` 开始，逐次执行 `Data[j+1] = Data[j]`，最后减至 $i-1$。如果错误地由前向后从 $i-1$ 开始移动，执行 `Data[i] = Data[i-1]` 会导致原位置 $i$ 的数据被瞬间冲刷覆盖，进而造成后续所有数据全部变成同一重复值的灾难性后果。

所以我们这样的话，一个具体的算法呢就可以写成这样子：

```c
void Insert(ElementType X, int i, List PtrL) {
    int j;

    /* 校验一：判定存储空间是否已满 */
    if (PtrL->Last == MAXSIZE - 1) {
        /* 表空间已满，无法容纳新元素 */
        return;
    }

    /* 校验二：判定插入位序 i 的合法性 (合法区间: 1 <= i <= Last + 2) */
    if (i < 1 || i > PtrL->Last + 2) {
        /* 插入位置不合法，越界阻断 */
        return;
    }

    /* 核心步骤：从后向前依次倒序后移元素 */
    for (j = PtrL->Last; j >= i - 1; j--) {
        PtrL->Data[j + 1] = PtrL->Data[j];
    }

    /* 填入新元素并维护表尾游标 */
    PtrL->Data[i - 1] = X;
    PtrL->Last++;
}
```

接下来的一个 `for` 循环呢就是一个个往后挪。那么大家看到了，控制变量是 $j$，它从哪里开始做呢？**从 `Last` 开始做。** 你不能从 $i+1$ 开始，不能从 $i-1$ 开始做；可以从 `Last` 最后一个元素开始做。每次循环呢就是把第 $j$ 个元素移到第 $j+1$ 这样一个位置，这样的一种做法每次 `j` 减减减减减，然后一直挪到 $i-1$ 这个位置。那么这样的一个 `for` 循环就是把下标为 $i-1$ 的实际上是第二个元素之后的所有元素都往后挪了。

挪完之后呢，腾出来 $i-1$ 这个位置，也就是第二个位置。当然由于你放进去了之后呢多了一个元素，所以 `Last` 也加加。那么这样的一种平均移动次数呢，整个算法的时间复杂性就是在这个 `for` 循环里面，也就是说平均移动的次数它是 $\frac{1}{2} n$。

#### 元素删除操作

那么接下来我们来介绍一下另外一个操作，叫删除。就是要删除第 $i$ 个位置上的元素，也就是这个 $i$ 呢也是 1 到 $n$ 之间，第一个元素和最后一个元素。当然它所对应的数组的下标就是 0 到 $n-1$ 了。

那么这个怎么做？我们要把第 $i$ 个元素移掉，意味着整个连续存放空间里面这个位置空出来了，所以必须把 $i$ 之后的这些元素全部往前挪。因为我们要删掉的是第 $i$ 个位置上的元素，也就是下标为 $i-1$ 的元素，所以这个时候挪呢，要把它后面的那个元素挪到前面来，也就是说下标为 $i$ 的元素挪到 $i-1$。挪到 $i$ 是按照从左往右的顺序往前挪。

那么具体的算法实现呢是这样的。我们已知一个 `PtrL` 这样的一个线性表，然后要删除第 $i$ 个元素。那么首先我们要判别一下你要删除的这个 $i$ 值对不对啊，你别给我上一个不在这个表里的位置的一个元素啊，所以先是做这个合法性判断。

接下来一个 `for` 循环是从 $i$ 这个位置开始，一个个地往前挪：也就是说一开始是 $i$ 挪到 $i-1$，接下来 $i+1$ 挪到 $i$，再下来 $i+2$ 挪到 $i+1$，所以是这样的一个循环。所以这个循环的顺序呢，跟前面我们插入的时候是不一样：插入的时候那个 $j$ 是从 `Last` 这个地方开始循环，这个从 $i$ 这个地方开始循环。

那么这个循环过程当中呢，每次做的这个事情呢，就是把 `Data[j]` 的这个元素呢把它挪到前面去。那么因为挪掉了之后，所以我们整个的元素呢就少了一个，所以最后呢 `Last` 减减。同样的它的平均移动次数是 $\frac{1}{2}(n-1)$。

```c
void Delete(int i, List PtrL) {
    int j;

    /* 校验：检查删除位序 i 的合法性 (合法区间: 1 <= i <= Last + 1) */
    if (i < 1 || i > PtrL->Last + 1) {
        /* 删除位置不存在，越界阻断 */
        return;
    }

    /* 核心步骤：从前向后依次正序前移元素 */
    for (j = i; j <= PtrL->Last; j++) {
        PtrL->Data[j - 1] = PtrL->Data[j];
    }

    /* 元素减少，表尾游标递减 */
    PtrL->Last--;
}
```

> **性能分析**：插入与删除的平均移动次数
> - 插入：设线性表现有长度为 $n$，新元素插入到第 $i$ 个位置的概率均等为 $\frac{1}{n+1}$。若插入在末尾 $i = n+1$，移动 0 个元素；若插入在表头 $i = 1$，需要移动全部 $n$ 个元素。平均移动次数为：
> $$\text{Average Move} = \frac{1}{n+1} \sum_{i=1}^{n+1} (n - i + 1) = \frac{1}{n+1} \times \frac{n(n+1)}{2} = \frac{n}{2}$$
> - 删除：设线性表现有长度为 $n$，删除各个位置元素的概率均等为 $\frac{1}{n}$。若删除表尾项 $i = n$，移动 0 个元素；若删除表头项 $i = 1$，需要前移剩余的 $n-1$ 个元素。平均移动次数为：
> $$\text{Average Move} = \frac{1}{n} \sum_{i=1}^n (n - i) = \frac{1}{n} \times \frac{n(n-1)}{2} = \frac{n-1}{2}$$
> 两者的平均时间复杂度同样都是 $O(n)$。

### 复杂度表格辨析思考题

**题干**：

在分析计算机执行指令时间的表格中，某一列在输入规模 $n = 10$ 时耗时约为 $3.3 \times 10^{-10}$ 秒，在 $n = 10^6$ 时耗时约为 $2 \times 10^{-4}$ 秒。该列运行时间比 $n$ 慢，但比 $n^2$ 快。然而表格的表头将其标注为 $\log n$。请判断该表头是否存在错误，若有错，其真实的复杂度函数是什么？

**解析**：

该表头标注存在根本性错误。

由常见函数的增长阶可知，对于任意底数 $b > 1$，当 $n$ 充分大时恒有 $\log n < n$。如果在同一台机器上运行，$\log n$ 算法的指令执行步数与运行耗时必然远低于线性算法 $n$ 的耗时。既然该列实测耗时介于线性阶 $n$ 与平方阶 $n^2$ 之间，根据复杂度函数的阶梯分布，其理论复杂度函数必然是线性对数阶 $n \log n$。

**验证**：$n = 10$ 时 $10 \log_2 10 \approx 33.2$，取 $10^{11}$ 条指令/秒的机器，耗时约 $3.3 \times 10^{-10}$ 秒；$n = 10^6$ 时 $10^6 \log_2 10^6 = 10^6 \times 20 = 2 \times 10^7$，耗时约 $2 \times 10^{-4}$ 秒——两个数据点都与表中数值精确吻合，反过来也证明了它只能是 $n \log n$。

## 链式线性表、多重广义表与堆栈机制深度解析
> 对应块：BLK03 | 覆盖分集：P15-P20 | 块标题（分集名）：《15_2.1.4 链式存储及查找》

前面我们学习了线性表的顺序存储实现，也就是用数组来管理数据。在数组中，元素在逻辑上相邻，在物理内存中也必须紧挨着。这种紧密绑定的物理结构带来了一个显而易见的代价：每当我们要插入或删除一个元素时，就必须把该位置后面成百上千的元素整体往前挪或者往后挪，搬迁成本极高。

那么，有没有一种办法能打破这种物理相邻的强行约束？这就是链式存储。链式存储的核心思想是：两个元素在逻辑上虽然相邻，但在物理内存上可以天各一方，彼此之间完全靠一条“链”——也就是指针——连接在一起。在这种结构下，插入和删除只需要轻巧地改动指针指向，而不需要挪动任何具体的数据元素。

然而，天下没有免费的午餐。用数组存储时，我们要找第 $i$ 个元素极其直接，写个 `A[i-1]` 瞬间就能定位；表长也有一个专门的标记可以直接获知。但在链表中，如果我们手里仅仅拿着一个指向链表开头的指针，想要知道第 $i$ 个元素在哪里、整张表一共有多长，就不能一步登天了。我们必须沿着链条一个结点一个结点地往下摸索。

---

### 线性表的链式存储与基本查找

链表是由若干个在内存中离散分布的结点链接而成的线性结构。每个结点都是一个结构体，里面至少包含两个分量：一个分量负责存储该结点的数据，称为数据域；另一个分量负责记录下一个结点的内存地址，称为指针域。

#### 链表结点定义与表长统计

在 C 语言中，一个标准的单向链表结点可以定义如下：

```c
typedef int ElementType;
typedef struct LNode *List;
struct LNode {
    ElementType Data;
    List Next;
};
```

整个链表的结构可以用下图直观表示：

```text
PtrL
  │
  ▼
┌──────┬──────┐    ┌──────┬──────┐    ┌──────┬──────┐
│ Data │ Next ├───►│ Data │ Next ├───►│ Data │ NULL │
└──────┴──────┘    └──────┴──────┘    └──────┴──────┘
```
图中每个结点由数据域 `Data` 与指针域 `Next` 组成，最后一个结点的 `Next` 为空指针 `NULL`。

由于单向链表没有像数组那样维护全局连续的物理下标，如果我们想知道链表里究竟有多少个元素，唯一可靠的方法就是把整张链表从头到尾完整遍历一遍，直到最后一个元素为止。

求表长的具体实现思路非常清晰：首先设立一个临时的游标指针 `p`，让它一开始指向链表的头指针 `PtrL`；再设立一个整型计数器 `j`，初始值赋为 0。随后进入循环，循环的推进条件就是链表尚未结束，即 `p != NULL`。每遍历到一个有效结点，就把计数器 `j` 加 1，同时通过赋值语句 `p = p->Next` 让指针顺着链条向后移动一位。当指针最终指到最后一个结点的下一个位置时，`p` 变成了 `NULL`，循环退出。此时 `j` 的数值恰好就是整个链表的长度。

```c
int Length(List PtrL) {
    List p = PtrL;
    int j = 0;
    while (p != NULL) {
        p = p->Next;
        j++;
    }
    return j;
}
```

> **结论**：链式存储求表长必须线性扫描每一个结点，其时间复杂度为 $O(n)$。

#### 按序号与按值查找的遍历机制

在数组中查找第 $K$ 个元素只需要通过下标随机访问，时间复杂度是 $O(1)$。但在单向链表中，我们必须采用遍历的策略逐个后移。

按序号查找第 $K$ 个元素的操作定义为 `FindKth(int K, List PtrL)`。我们用临时指针 `p` 指向表头，同时用一个整数变量 $i$ 来记录当前遍历到了第几个结点。刚开始时，`p` 指向第一个结点，因此 $i$ 初始化为 1。接下来进入循环，要继续向后找，必须同时满足两个条件：第一，当前结点有效，即链表没有结束（`p != NULL`）；第二，我们还没有数到第 $K$ 个结点（$i < K$）。

```c
List FindKth(int K, List PtrL) {
    List p = PtrL;
    int i = 1;
    while (p != NULL && i < K) {
        p = p->Next;
        i++;
    }
    if (i == K) {
        return p;
    } else {
        return NULL;
    }
}
```

这个循环退出的时刻，必然代表上述两个条件中至少有一个被破坏了，因此退出时只有两种可能：
1. $i == K$：说明我们已经成功数到了第 $K$ 个结点，此时直接返回该结点的指针 `p`。
2. $p == NULL$：说明链表已经遍历完了，但计数值 $i$ 依然没有达到 $K$（例如 $K$ 超过了实际表长，或者传入的本就是空表），说明查找失败，直接返回 `NULL`。

除了按序号查找，另一种常见需求是按值查找，即已知一个数值 $X$，寻找链表中哪个结点存储了这个值，并返回该结点的地址。

```c
List Find(ElementType X, List PtrL) {
    List p = PtrL;
    while (p != NULL && p->Data != X) {
        p = p->Next;
    }
    return p;
}
```

按值查找同样从表头 `PtrL` 出发。循环维持的条件是：链表没有结束（`p != NULL`），并且当前结点的数据不是我们要找的 $X$（`p->Data != X`）。只要没找到且表未尽，指针就通过 `p = p->Next` 不断后移。当循环终止时，如果找到了目标值，此时 `p->Data == X`，循环因后半条件不满足而退出，返回的 `p` 正好是目标结点的地址；如果整表找遍了都没有该值，指针最终变为 `NULL`，退出时返回的 `p` 恰好就是 `NULL`。因此只要调用者发现返回值等于 `NULL`，就能断定查找未命中。

### 链表的插入、删除与动态内存管理

链式存储最大的优势在于插入与删除不需要大批量搬运内存中的数据元素。但单向链表的单向传导性带来了一个严格约束：要改变某个位置的连接，必须拿到被操作结点的前驱结点。

#### 结点的插入与指针重组次序

我们希望设计一个插入函数，把一个新值 $X$ 插入到链表的第 $i$ 个位置上，也就是说，新结点插入完成之后将成为新的第 $i$ 个结点，原本的第 $i$ 个结点则后退成为第 $i+1$ 个结点。这意味着新结点必须挂在原第 $i-1$ 个结点的后面。

在单向链表中，指针只能从前向后指，无法逆向寻找。因此，插入操作必须先找到待插入位置的前驱结点，也就是第 $i-1$ 个结点。整个插入的基本操作过程分为三步：
1. 调用动态内存分配函数 `malloc` 申请一块新结点的内存空间，用指针 `s` 指向它，并将数据域赋值为 $X$；
2. 找到链表的第 $i-1$ 个结点，用指针 `p` 指向它；
3. 修改指针，将新结点 `s` 穿插到 `p` 与其原有后继结点之间。

```text
        p (第 i-1 个结点)       原本的第 i 个结点
      ┌──────┬──────┐          ┌──────┬──────┐
      │ Data │ Next ├───┐      │ Data │ Next │
      └──────┴──────┘   │      └──────┴──────┘
                        │             ▲
                  (②)   │             │ (①)
                        ▼             │
                      ┌──────┬──────┐ │
                      │  X   │ Next ├─┘
                      └──────┴──────┘
                            s
```
图中箭头①与②标示了指针修改的次序，必须先让新结点的 `Next` 指向后继，再让前驱结点的 `Next` 指向新结点。

把结点穿插进去需要修改两个指针，可以用以下两条核心赋值语句完成：
```c
s->Next = p->Next;  /* 步骤 ①：新结点的 Next 指向原第 i 个结点 */
p->Next = s;        /* 步骤 ②：前驱结点的 Next 指向新结点 */
```

> **易错点**：这两条指针赋值语句的先后顺序绝对不能对调！大家必须想想为什么不能反过来写。如果先写 `p->Next = s;`，那么原本指向第 $i$ 个结点的指针瞬间被覆盖掉了，我们手头上将彻底丢失后面所有结点的地址；接着若再执行 `s->Next = p->Next;`，实际上是把刚刚赋给 `p->Next` 的 `s` 又赋给了 `s->Next`，导致新结点自己指着自己形成了死循环死锁，而链表后半段全部脱节丢失。因此，必须先让新结点挂上前方的后继，再把前驱结点的链断开连向新结点。

在处理具体逻辑时，还有一个极为特殊的边界情况：如果要在链表的最开头插入新元素，即 $i = 1$ 时该怎么办？如果要插在第 1 个位置，那么它前面的第 $i-1$ 个位置就是第 0 个位置，而在我们的链表定义里根本不存在第 0 个结点。

因此，表头插入必须作为特殊分支单独处理：直接将新结点的 `Next` 指向原本的表头 `PtrL`，此时整个链表的入口地址发生了改变，必须把新结点的指针 `s` 作为新的表头返回。完整的插入代码实现如下：

```c
List Insert(ElementType X, int i, List PtrL) {
    List p, s;
    if (i == 1) { /* 新结点插入在表头 */
        s = (List)malloc(sizeof(struct LNode));
        s->Data = X;
        s->Next = PtrL;
        return s; /* 返回新的链表头指针 */
    }
    p = FindKth(i - 1, PtrL); /* 查找第 i-1 个结点 */
    if (p == NULL) { /* 第 i-1 个结点不存在，插入位置非法 */
        return NULL;
    } else {
        s = (List)malloc(sizeof(struct LNode));
        s->Data = X;
        s->Next = p->Next;
        p->Next = s;
        return PtrL; /* 表头未变，返回原表头指针 */
    }
}
```

因为在表头插入时链表的头指针会改变，所以外部调用者在使用该函数时，标准规范的写法应该是：
```c
PtrL = Insert(X, i, PtrL);
```
通过接收返回值来及时刷新链表头指针。在平均情况下，寻找第 $i-1$ 个结点平均需要查找 $\frac{n}{2}$ 次，整体时间复杂度为 $O(n)$。

#### 结点的删除与内存安全释放

删除操作的目标是把链表中第 $i$ 个位置的结点摘除，并保证前后断裂的链条重新拼接完整。

与插入类似，要删除第 $i$ 个结点，我们必须找到它的前驱结点（第 $i-1$ 个结点），并用指针 `p` 指向它。我们需要让 `p` 的指针越过第 $i$ 个结点，直接连接到第 $i+1$ 个结点上。

```text
        p (第 i-1 个结点)         s (待删除结点)          第 i+1 个结点
      ┌──────┬──────┐          ┌──────┬──────┐          ┌──────┬──────┐
      │ Data │ Next ├───┐      │ Data │ Next ├────►     │ Data │ Next │
      └──────┴──────┘   │      └──────┴──────┘          └──────┴──────┘
                        │                                      ▲
                        └──────────────────────────────────────┘
                                          (①)
```
图中指针绕过结点 `s` 直接与后继相接，随后结点 `s` 的内存必须显式释放。

然而，仅仅修改指针绕过它是不够的。我们在创建结点时是通过 `malloc` 向操作系统动态申请的堆内存，现在这个结点不再需要了，如果只是简单地把它从链表中断开而不加处理，这块内存将永远孤立在堆区无法被系统回收，从而造成严重的内存泄漏。因此，必须调用 `free()` 函数把被删结点的空间显式归还给操作系统。

删除操作的标准流程如下：
1. 设立指针 `s`，先指向即将被删除的结点：`s = p->Next;`；
2. 修改指针越过待删结点：`p->Next = s->Next;`；
3. 释放被删结点占用的内存空间：`free(s);`。

对于删除第 1 个结点的特殊情况，同样需要特殊判定：若链表本就是空的，删除无法执行，直接返回 `NULL`；若不为空，则将表头指针后移一位指向原本的第 2 个结点，并释放原头结点的内存：

```c
List Delete(int i, List PtrL) {
    List p, s;
    if (i == 1) { /* 删除表头结点 */
        if (PtrL == NULL) return NULL;
        s = PtrL;
        PtrL = PtrL->Next;
        free(s);
        return PtrL;
    }
    p = FindKth(i - 1, PtrL); /* 查找第 i-1 个结点 */
    if (p == NULL || p->Next == NULL) { /* 前驱不存在或待删结点不存在 */
        return NULL;
    } else {
        s = p->Next;
        p->Next = s->Next;
        free(s);
        return PtrL;
    }
}
```
删除操作平均同样需要扫描 $\frac{n}{2}$ 个结点，时间复杂度亦为 $O(n)$。

### 线性结构的推广：广义表与多重链表

我们在前面学习的一元多项式，每一项只包含一个变量 $x$，各项的系数都是确定的常数。但是，现实世界中的问题往往更加复杂。如果面对的是一个含有两个变量的二元多项式，我们该如何用链表进行表示？

#### 二元多项式与广义表的联合体实现

考虑如下一个二元多项式：
$$P(x, y) = (9y^2 + 4)x^{12} + (15y^3 - y)x^8 + 3x^2$$

面对两个变量纠缠在一起的表达式，一种极其优美的解题思路是：**把二元多项式看成关于 $x$ 的一元多项式**。在上面的式子中，多项式按 $x$ 的降幂排列，主变量是 $x$。此时，各项中原本属于常数系数的位置，变成了关于 $y$ 的一元多项式（例如 $x^{12}$ 的系数是 $9y^2+4$，$x^8$ 的系数是 $15y^3-y$）。

这样一来，我们就可以仿照一元多项式的链表组织形式：主链表的每一个结点代表 $x$ 的一项，包含指数项和后继指针；而原本存放纯数字系数的域，现在改由一个指针来充当，这个指针指向另一个关于 $y$ 的独立一元多项式链表。

```text
主链表 (变量 x):
┌───┬───┬───┐    ┌───┬───┬───┐    ┌───┬───┬───┐
│ 12│ • │ • ├───►│ 8 │ • │ • ├───►│ 2 │ 3 │NULL│
└───┴─│─┴───┘    └───┴─│─┴───┘    └───┴───┴───┘
      │                │
      ▼                ▼
  子链表 (变量 y)   子链表 (变量 y)
  9y^2 + 4         15y^3 - y
```
图中主链表结点的系数位置既可能是单值常数，也可能是一个指向子表的指针。

这种特殊的链表结构，在计算机科学中被称为**广义表**（Generalized List）。

> **定义**：广义表是线性表的一种推广。对于一般的线性表，其内部的所有元素都是不能再分的单元素（原子）；而在广义表中，元素不仅可以是单元素，还可以是另一个广义表（称为子表）。

广义表带来了一个底层实现的难题：链表结点中的某个域，有时存储的是不能分解的单元素数据（如整型数值），有时存储的却是一个指向子表的内存指针。如何在 C 语言中用一套统一的结构体来容纳两种截然不同类型的数据？

C 语言提供的核心手段是**联合体**（`union`）。联合体允许把不同类型的数据成员叠加在同一块内存空间上，由程序员根据上下文来决定如何解读这块内存。为了在程序运行时明确区分当前域到底是单元素还是子表指针，我们通常在结构体中额外引入一个标记变量 `Tag`：

```c
typedef struct GNode *GList;
struct GNode {
    int Tag; /* 标记域：0 代表单元素，1 代表子表指针 */
    union {
        ElementType Data;
        GList SubList;
    } URegion;
    GList Next; /* 指向同一层的下一个结点 */
};
```

当 `Tag == 0` 时，程序去读取 `URegion.Data`；当 `Tag == 1` 时，程序则将该域作为 `URegion.SubList` 指针继续向子表递归展开。这种结合标记与联合体的方式，是处理异构递归数据结构的标准范式。

#### 多重链表辨析与稀疏矩阵的十字链表

广义表的结构实际上已经引出了一个更广泛的概念——**多重链表**（Multilist）。

> **定义**：多重链表是指链表中的结点可能同时隶属于多个不同的链表。换言之，结点内部会包含多个指针域，分别属于不同的逻辑链条。

> **易错点**：千万注意，**一个结点包含多个指针，并不等价于多重链表**！比如我们熟知的双向链表，每个结点确实都有向前（`Prior`）和向后（`Next`）两个指针，但这两个指针串联起来的本质上是同一张链表，只是遍历的方向相反而已，因此双向链表绝对不是多重链表。多重链表的本质特征在于结点必须同时属于两个或两个以上相互交织的逻辑链表。

多重链表在后续的树和图结构中有着极其广泛的应用，而它最经典的初级应用就是稀疏矩阵的表示。

如果要表示一个常规矩阵，最直接的方法是用二维数组。但二维数组有两个致命的缺陷：第一，数组大小必须预先固定；第二，如果矩阵是一个稀疏矩阵（即绝大多数元素都是 0，非零元素极其稀少），二维数组会造成灾难性的空间浪费。

举一个生动的现实案例：一所综合性大学要记录全校学生的选课情况。行代表课程（约 3000 到 4000 门），列代表学生（约 10000 到 20000 人）。如果用二维数组表示选课矩阵，矩阵的单元格总数高达几千万甚至上亿。但在实际情况下，一个学生一学期最多选几门到十几门课，整个巨型矩阵中 99% 以上的位置都是 0。如果简单用二维数组强行存储，绝大部分空间都被 0 占据，不仅内存爆仓，处理效率也极其低下。

因此，我们的目标是：**只存储非零项**。要精准记录一个非零项，核心要素有三样：行坐标 `Row`、列坐标 `Col` 以及具体的数值 `Value`。

但矩阵不仅有数据，还包含严格的行列拓扑关系。为了维持这种网状关系，我们为每个非零项结点设计两个指针域：
- `Right` 指针：把属于同一行的元素串成一条链；
- `Down` 指针：把属于同一列的元素串成一条链。

这样，每个非零项结点既属于某一行链表，又属于某一列链表，纵横交错，形成了一张二维网格。这种存储结构被称为**十字链表**（Cross List）。

```text
               Col 0        Col 1
                 │            │
                 ▼            ▼
             ┌───────┐    ┌───────┐
Row 0 ────►  │(0,0,1)├───►│(0,1,2)├───► (循环回行头)
             └───────┘    └───────┘
                 │            │
                 ▼            ▼
             ┌───────┐
Row 1 ────►  │(1,0,3)├───► (循环回行头)
             └───────┘
                 │            │
                 ▼            ▼
             (循环回列头)  (循环回列头)
```
图中每个非零项结点同时被行链表（`Right` 水平指向）与列链表（`Down` 垂直指向）贯穿，并构成循环链表。

在十字链表中，通常涉及两类结点：
1. **普通项结点（Term 结点）**：存储非零元素，包含 `Row`、`Col`、`Value` 以及 `Right` 和 `Down` 两个指针。每一行的所有项结点通过 `Right` 指针串联成一个循环链表，每一列的所有项结点通过 `Down` 指针串联成一个循环链表。
2. **表头结点（Head 结点）**：用来作为每一行、每一列循环链表的入口。
3. **全局入口总头结点**：结构与普通项结点完全相同，位于整张网的最左上角。它的 `Row` 记录整个矩阵的总行数，`Col` 记录总列数，`Value` 记录非零项的总个数（例如一个 4 行 5 列、共有 7 个非零项的稀疏矩阵，该结点的三元组即为 `(4, 5, 7)`）。通过它的指针，可以顺藤摸瓜遍历到所有行和列的表头结点。

由于普通项结点与表头结点的内部信息存在差异，但又共同具备 `Right` 和 `Down` 两个方向指针，我们在工程实现中同样可以通过 `union` 将它们统合成一种标准结点类型，从而实现对整张稀疏矩阵的精简表达。

### 堆栈的抽象特征与后缀表达式求值

讨论完广义表与多重链表，我们来研究一种非常关键的受限线性结构——堆栈。堆栈在计算机科学中无处不在，函数调用、递归实现、深度优先搜索以及算术表达式的求值，底层全靠堆栈来支撑。

#### 中缀表达式的困境与后缀求值策略

为了讲透为什么需要堆栈，我们来看一个计算机处理算术表达式求值的真实场景。考虑下面这个极为平常的算术表达式：
$$5 + 6 / 2 - 3 \times 4$$

计算机如果从左向右扫描这个式子，会遇到巨大的麻烦。我们平时书写的这种运算符号位于两个运算数中间的式子，称为**中缀表达式**。中缀表达式之所以难处理，是因为运算符号存在优先级。当计算机扫描到加号 `+` 时，左边看到了操作数 5，右边看到了操作数 6，但此时**绝不能**执行加法运算！因为紧跟在 6 后面的除号 `/` 具有更高的优先级，6 必须先和后面的 2 结合做除法，算出来的结果才能倒回来与 5 相加。

也就是说，在中缀表达式中，我们必须把前面的运算悬挂延后，等待后面的高优先级运算完成。

但如果我们换一种组织方式，把运算符号直接放在参与运算的两个操作数后面，情况就彻底改变了。这种运算符写在后面的表达式称为**后缀表达式**（Postfix Expression，也称逆波兰表达式）。例如，中缀表达式 $a + b \times c - d / e$ 对应的等价后缀表达式为：
$$a\ b\ c\ \times\ +\ d\ e\ /\ -$$

后缀表达式最大的优越性在于：**运算符的出现次序就是其实际执行计算的次序，完全消除了括号和优先级的干扰**。当我们从左往右扫描，一旦遇到一个运算符，参与它运算的两个操作数在前面就已经准备好了，立刻就能进行计算！

让我们以一个具体的后缀表达式为例，推演其计算机求值过程：
$$6\quad 2\quad /\quad 3\quad -\quad 4\quad 2\quad *\quad +$$

计算机从左向右逐个字符扫描处理：
1. 读入操作数 `6`：记住；
2. 读入操作数 `2`：记住；
3. 遇到除号 `/`：说明紧邻的前两个数要做除法，取出最近记住的两个数，计算 $6 / 2 = 3$，并将计算结果 `3` 记住；
4. 读入操作数 `3`：记住；
5. 遇到减号 `-`：取出最近记住的两个数，计算 $3 - 3 = 0$，将结果 `0` 记住；
6. 读入操作数 `4`：记住；
7. 读入操作数 `2`：记住；
8. 遇到乘号 `*`：取出最近记住的两个数，计算 $4 \times 2 = 8$，将结果 `8` 记住；此时手头记着的两个数是 `0` 和 `8`；
9. 遇到加号 `+`：取出最近记住的两个数，计算 $0 + 8 = 8$，将最终结果 `8` 记住；
10. 表达式扫描结束，此时最后记住的那个数 `8`，就是整个算术表达式的最终值。

整个求值过程只需要对表达式从头到尾进行一次单向扫描，时间复杂度是极其理想的线性时间 $O(n)$。

#### 堆栈的抽象数据类型与出栈序列规律

回顾刚才后缀表达式求值的全过程，计算机对运算数的操作规律表现出极强的共性：
- 碰到数就按顺序存进去；
- 碰到运算符时，需要把**最后存进去的两个数**取出来做计算。

这种“**后放进去的先拿出来，先放进去的后拿出来**”的数据存取规律，就是所谓的**后入先出**（LIFO, Last In First Out）。能够完美胜任这项任务的数据结构，正是堆栈（Stack）。

> **定义**：堆栈是一种受到操作约束的线性表。它只允许在表的一端进行插入和删除操作。
> - 允许操作的一端称为**栈顶**（Top）；
> - 固定不动、不允许操作的另一端称为**栈底**。
> - 向栈顶插入新元素的操作称为**入栈**（Push）；
> - 从栈顶删除并返回元素的操作称为**出栈**（Pop）。

在日常生活中，堆栈随处可见。最生动的类比就是食堂餐桌上叠放的一摞碗：洗好的碗只能往这一摞碗的顶上放（Push），大家要用碗时也只能从最顶上拿走（Pop）。最晚放上去的碗，一定最先被人拿走。

堆栈的抽象数据类型（ADT）主要包含以下五种基础操作：
- `CreateStack(int MaxSize)`：创建并返回一个最大容量为 `MaxSize` 的空堆栈；
- `IsFull(Stack S)`：判断堆栈 `S` 是否已满；
- `Push(Stack S, ElementType item)`：将数据项 `item` 压入栈顶；
- `IsEmpty(Stack S)`：判断堆栈 `S` 是否为空；
- `Pop(Stack S)`：删除并返回当前的栈顶元素。

在实际运行过程中，入栈和出栈操作往往穿插进行。不同的入栈出栈交替次序会产生不同的输出序列。

假设我们把三个元素按 `a, b, c` 的固定次序入栈：
- 如果操作次序是：`Push(a), Push(b), Push(c), Pop(), Pop(), Pop()`，那么依次弹出的元素是 `c, b, a`；
- 如果操作次序是：`Push(a), Pop(), Push(b), Push(c), Pop(), Pop()`，那么 `a` 刚进去就出来，接着 `b` 和 `c` 进栈后再依次弹出，最终得到的输出序列是 `a, c, b`。

这里引发了一个经典的思考：如果元素按照 `a, b, c` 的顺序依次入栈，通过中途穿插 `Push` 与 `Pop`，出栈序列是否可以穷尽 `a, b, c` 的全部 6 种全排列？输出序列 `c, a, b` 是否可能产生？

答案是：**绝对不可能产生**！我们可以给出严密的逻辑证明：
要让 `c` 在出栈序列中排在第一个，意味着 `c` 必须是第一个被 Pop 出来的元素。由于元素必须按 `a, b, c` 的顺序先后到达，要让 `c` 能够入栈，在此之前 `a` 和 `b` 必须已经进栈了。此时堆栈内部的排布自底向上必定是：最底下是 `a`，中间是 `b`，最顶上是 `c`。现在 `c` 出栈了，此时露在最顶上的元素毫无疑问是 `b`！下一个被弹出的元素只可能是 `b`，绝不可能是深压在栈底的 `a`。因此，输出序列中 `c` 的下一个必定是 `b`，绝不可能出现 `c, a, b` 这样的排列。

### 堆栈的顺序存储与对撞双栈设计

理解了堆栈的抽象机理后，我们来看工程落地。实现堆栈最朴素、最高效的手段之一是用一维数组。

#### 单数组堆栈的基本操作

用数组实现堆栈时，我们不仅需要一块连续的存储区域来存放数据，还需要一个变量来记录当前栈顶到底停留在数组的哪一个位置。

```c
#define MaxSize 100
typedef int ElementType;
typedef struct SNode *Stack;
struct SNode {
    ElementType Data[MaxSize];
    int Top;
};
```

> **注意**：结构体中的 `Top` 并不是一个内存指针，而是一个整型变量，它代表当前栈顶元素在数组 `Data` 中的**数组下标**。

约定状态机如下：
- 当堆栈为空时，由于下标 0 还没有任何元素，我们规定 `Top = -1`；
- 当栈中压入第一个元素放入 `Data[0]` 时，`Top` 变为 0；
- 当 `Top == MaxSize - 1` 时，意味着数组的所有位置都已经被占满，堆栈处于“栈满”状态。

在进行入栈（Push）操作时，必须先检查堆栈是否已满。如果已满，再强行放入会导致数组越界崩溃；若未满，则将 `Top` 加 1，并将新元素放入该位置：

```c
void Push(Stack PtrS, ElementType item) {
    if (PtrS->Top == MaxSize - 1) {
        /* 堆栈已满，报错返回 */
        return;
    } else {
        PtrS->Data[++(PtrS->Top)] = item;
    }
}
```
这里的 `++(PtrS->Top)` 采用前置自增，精炼地完成了两件事：先让 `Top` 向后挪一个格子，再把 `item` 存入新格子。

出栈（Pop）操作则完全相反：必须先判别堆栈是否为空（`Top == -1`）。如果不空，先取出 `Top` 处的元素作为返回值，再把 `Top` 向下减 1：

```c
ElementType Pop(Stack PtrS) {
    if (PtrS->Top == -1) {
        /* 堆栈已空，报错返回错误标志 */
        return -1;
    } else {
        return PtrS->Data[(PtrS->Top)--];
    }
}
```
这里的 `(PtrS->Top)--` 采用后置自减，先返回当前下标处的数据，随后再让栈顶指针回退。

#### 空间最大化复用：两头向中间增长的对撞双栈

在实际工程中，经常会遇到同时需要两个堆栈的情况。如果为每个堆栈单独开辟一个固定数组，或者把一个数组从中间对半劈开（左半边给栈 1，右半边给栈 2），会出现极大的空间浪费。

试想，如果栈 2 业务繁忙，很快就把分配给它的右半边全部填满了，此时栈 2 发生溢出无法继续工作；而与此同时，栈 1 业务清闲，左半边还空着大片内存。明明整个数组还有充足的剩余闲置空间，系统却因为硬性切分而报错，这显然是非常低效的设计。

因此，我们提出一个绝妙的优化方案：**让两个堆栈共享同一个一维数组，分别从数组的两头向中间对撞增长**！

```text
       Top1 ──►                         ◄── Top2
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│  S1  │  S1  │      │ 闲置 │ 闲置 │      │  S2  │  S2  │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
  0      1      2                    MaxSize-2 MaxSize-1
```
图中栈 1 从下标 0 往右增长，栈 2 从下标 `MaxSize-1` 往左增长，两栈顶相遇时判定栈满。

架构设计如下：
- 栈 1 的栈底设在数组的最左端（下标 0），其栈顶指针 `Top1` 向右递增移动，初始空栈时设定 `Top1 = -1`；
- 栈 2 的栈底设在数组的最右端（下标 `MaxSize - 1`），其栈顶指针 `Top2` 向左递减移动，初始空栈时设定 `Top2 = MaxSize`；
- 只要中间还有空余格子，无论哪个堆栈需要空间，都可以自由向中间延伸。

> **易错点**：如何判别这种对撞双栈已经满了？很多同学脱口而出：“是不是 `Top1 + Top2 == MaxSize`？”**这种理解显然是完全错误的！**
> 大家一定要认清本质：`Top1` 和 `Top2` 都是数组的绝对物理下标。`Top1` 代表的是从下标 0 到当前位置的偏移；而 `Top2` 代表的是从下标 0 到右边位置的绝对坐标。把这两个数组下标生硬地加在一起，在物理和几何上没有任何数学意义！

真正判定栈满的唯一物理条件是：**两个栈顶指针在中间相遇，彼此紧挨着**。也就是说，栈 2 的位置正好在栈 1 的后一个位置：
$$Top2 - Top1 == 1$$

基于该机制的双栈结构体及 Push/Pop 完整操作如下：

```c
struct DStack {
    ElementType Data[MaxSize];
    int Top1;
    int Top2;
};
typedef struct DStack *DualStack;

void PushDual(DualStack PtrS, ElementType item, int tag) {
    if (PtrS->Top2 - PtrS->Top1 == 1) {
        /* 两个栈顶指针相遇，整个数组全满 */
        return;
    }
    if (tag == 1) { /* 压入第一个堆栈 */
        PtrS->Data[++(PtrS->Top1)] = item;
    } else if (tag == 2) { /* 压入第二个堆栈 */
        PtrS->Data[--(PtrS->Top2)] = item;
    }
}

ElementType PopDual(DualStack PtrS, int tag) {
    if (tag == 1) {
        if (PtrS->Top1 == -1) {
            /* 堆栈 1 为空 */
            return -1;
        } else {
            return PtrS->Data[(PtrS->Top1)--];
        }
    } else if (tag == 2) {
        if (PtrS->Top2 == MaxSize) {
            /* 堆栈 2 为空 */
            return -1;
        } else {
            return PtrS->Data[(PtrS->Top2)++];
        }
    }
    return -1;
}
```

这种两头对撞的算法设计极其优雅，只要数组内部还有哪怕一个闲置单元，无论是栈 1 还是栈 2 的入栈请求都能顺利完成，真正实现了内存空间的最大化动态共享。

### 堆栈的链式存储实现与表头栈顶抉择

顺序存储虽然执行速度快，但必须受限于数组的固定容量 `MaxSize`。如果我们无法预估程序运行过程中堆栈的最大深度，使用单向链表来实现堆栈就是更自然的选择。

#### 栈顶位置的权衡：为什么表头是唯一解？

堆栈本质上是一个只能在一端进行插入和删除的受限线性表。而一条单向链表天生拥有两端：一端是链表头，另一端是链表尾。

究竟应该把单向链表的哪一端选作堆栈的栈顶 Top？这是一个至关重要的结构抉择。我们对两端分别做严密的推演：

**假设方案一：把单向链表的尾巴作为 Top**
- **入栈操作**：当前尾结点指向新申请的结点，尾指针顺势后移，操作非常简便；
- **出栈操作**：把尾结点删除后，栈顶指针必须回退指向它的前驱结点。但因为这是**单向链表**，结点中只有向后走的 `Next` 指针，根本找不到前驱结点的地址！要找前驱，只能从链表头重新开始遍历 $n$ 个结点。这意味着每次 Pop 都必须花费 $O(n)$ 的时间复杂度，这在效率上是完全不可接受的。因此，**链尾绝不能作为栈顶**。

**假设方案二：把单向链表的表头作为 Top**
- **入栈操作**：新结点直接插在表头前面，成为新的表头，复杂度 $O(1)$；
- **出栈操作**：直接删除第一个元素结点，将栈顶指针后移一位指向其后继，释放被删结点，复杂度同样是完美的 $O(1)$。

> **结论**：当使用单向链表实现堆栈时，**栈顶 Top 必须且只能设在单向链表的表头**！

#### 带头结点的链栈操作实现

为了消除表头插入与普通插入的边界差异，我们在实现链栈时通常引入一个空的**头结点**（Dummy Head Node）。头结点本身不存放有效业务数据，它的主要职责是作为稳定的栈顶锚点。

```text
Top (头结点)          栈顶有效元素           第二有效元素
┌──────┬──────┐      ┌──────┬──────┐      ┌──────┬──────┐
│  -   │ Next ├─────►│ Data │ Next ├─────►│ Data │ NULL │
└──────┴──────┘      └──────┴──────┘      └──────┴──────┘
```
图中链表头结点作为栈顶锚点，其 `Next` 始终指向栈顶第一个真实元素，栈空时 `Next` 为 `NULL`。

链栈的结点结构与空栈创建函数如下：

```c
typedef int ElementType;
typedef struct SNode *Stack;
struct SNode {
    ElementType Data;
    Stack Next;
};

Stack CreateStack() {
    Stack S;
    S = (Stack)malloc(sizeof(struct SNode));
    S->Next = NULL;
    return S;
}

int IsEmpty(Stack S) {
    return (S->Next == NULL);
}
```

> **提示**：为什么在链式堆栈中，执行 Push 操作时不需要判别堆栈是否已满？
> 因为顺序栈受限于数组的固定大小，必须时刻提防数组越界；而链式栈每次入栈都是通过 `malloc` 向操作系统动态申请一块全新的孤立结点挂入链表，只要操作系统的可用物理内存没有耗尽，链表就可以无限生长，因而在逻辑层面上根本不存在“栈满”的概念。

入栈操作的本质，就是把新结点插入到头结点的后面（经典的头插法）：

```c
void Push(Stack S, ElementType item) {
    Stack TmpCell;
    TmpCell = (Stack)malloc(sizeof(struct SNode));
    TmpCell->Data = item;
    TmpCell->Next = S->Next;
    S->Next = TmpCell;
}
```
这个过程用两句赋值语句完成：先让新结点的 `Next` 接管原栈顶元素（`TmpCell->Next = S->Next`），再让头结点的 `Next` 导向新结点（`S->Next = TmpCell`）。

出栈操作则是将头结点后面的第一个有效结点剥离，并严防内存泄漏：

```c
ElementType Pop(Stack S) {
    Stack FirstCell;
    ElementType TopElem;
    if (IsEmpty(S)) {
        /* 栈空，报错返回 */
        return -1;
    } else {
        FirstCell = S->Next;          /* 锁定待删的栈顶有效结点 */
        S->Next = FirstCell->Next;    /* 头结点跨过它，连接下一位 */
        TopElem = FirstCell->Data;    /* 提取数据值 */
        free(FirstCell);              /* 彻底释放内存，防止内存泄漏 */
        return TopElem;               /* 返回出栈元素 */
    }
}
```

出栈逻辑严谨地遵循了“保存引用 $\rightarrow$ 指针跨接 $\rightarrow$ 取出数据 $\rightarrow$ 释放空间 $\rightarrow$ 返回数值”的标准工业级安全生命周期，保证了内存使用的高度安全与规范。

### 本讲提到的题目

#### 题目：输入序列为 a, b, c 时的出栈合法性判定

**问题描述**：
设输入数据元素按 `a, b, c` 的顺序依次到达堆栈，在入栈过程中允许随时执行出栈操作。试判定出栈序列是否可能为 `c, a, b`？并给出严格的逻辑证明。

**解析与答案**：
该出栈序列是**不可能**产生的。

**严密分析**：
若出栈序列的第一项为 `c`，说明在整个执行生命周期中，`c` 必须是第一个被 `Pop` 出栈的元素。
由于输入流的到达次序严格限定为 `a, b, c`，要想让 `c` 能够入栈，其前驱元素 `a` 和 `b` 必须已经处于栈内。根据堆栈“后入先出”的物理规则，此时栈内的垂直堆叠拓扑自底向上必定是：
- 栈底：`a`
- 中间：`b`
- 栈顶：`c`

当执行 `Pop()` 操作将 `c` 弹出后，暴露出当前新的栈顶元素必定是 `b`。
因此，紧接着能够被弹出的元素只能是当前处于栈顶的 `b`，而绝不可能是被压制在最底层的 `a`。
所以，以 `c` 开头的出栈序列只可能是 `c, b, a`，绝对无法生成 `c, a, b` 序列。

#### 思考题：四个元素 a, b, c, d 进栈时的全排列合法性

**问题描述**：
如果输入元素增加到四个，按 `a, b, c, d` 的次序先后进栈（中途允许任意穿插 `Push` 与 `Pop` 操作），在 $4! = 24$ 种可能的全排列中，哪些序列是合法的出栈序列？哪些序列是不合法的？

**解析思路**：
根据堆栈出栈的基本定理（任意一个元素出栈时，在其之后出栈且在它之前就已经进栈的元素，必须呈现逆序弹出），我们可以逐一排查。例如序列 `d, a, b, c` 或 `c, a, b, d` 均包含非法的逆序违规。合法出栈序列的总数满足卡特兰数（Catalan Number）：
$$C_4 = \frac{1}{4+1}\binom{8}{4} = \frac{70}{5} = 14$$
即在 24 种排列中，共有 14 种序列是合法的，剩余 10 种序列是不可能的。该思考题旨在启发大家举一反三，进一步掌握堆栈状态转移的本质规律。

## 栈与队列的核心应用及多项式实现
> 对应块：BLK04 | 覆盖分集：P21-P25 | 块标题（分集名）：《21_2.2.4 堆栈应用_表达式求值》

前面我们讲了后缀表达式的求值方法，也就是用堆栈来进行计算：从左到右读入表达式各项，把运算数依次压入堆栈；一旦碰到运算符，就从栈中弹出运算数进行计算，再把计算结果压回堆栈。整个过程非常流畅，后缀表达式在计算机内部极容易求值。

但在日常生活和实际工作中，我们最熟悉、最习惯书写的，其实是中缀表达式，比如 $2 + 9 / 3 - 5$。中缀表达式里运算符夹在运算数中间，存在不同优先级的约束，甚至还有括号来改变计算顺序。计算机如何处理中缀表达式？最自然的思路就是：我们能不能把日常写出的中缀表达式，自动转换为计算机最擅长计算的后缀表达式，然后再去求值？

---

### 中缀表达式转后缀表达式与栈的扩展应用

#### 中缀转后缀的推导与优先级机制

要实现中缀表达式到后缀表达式的转换，我们先来观察一个具体的算术例子：

中缀表达式：$2 + 9 / 3 - 5$
对应后缀表达式：$2\ 9\ 3\ /\ +\ 5\ -$

仔细对比这两个表达式，可以立刻发现一个至关重要的规律：不管是中缀表达式还是后缀表达式，**运算数的相对先后顺序是完全不变的**，两者都是 $2, 9, 3, 5$。发生变化的，仅仅是运算符出现的位置。

既然运算数的顺序没有变，我们能不能顺着表达式从左往右读，边读边处理？我们来一步步推演：

1. 读到运算数 $2$：既然运算数顺序不变，直接输出 $2$；
2. 读到加号 $+$：这个加号能不能立刻输出？我们不知道。因为加法能不能立刻做，取决于它后面的运算符优先级高不高。如果后面紧跟着乘除法，加法就必须延后计算。所以加号不能直接输出，我们必须把它先记下来、等一等；
3. 读到运算数 $9$：直接输出 $9$；
4. 读到除号 $/$：除号能不能立刻输出？虽然除号的优先级比前面暂存的加号高，但此时能不能立刻把 $9$ 和后面的数相除？也不一定。如果后面还有一个更高优先级的运算（比如乘方或指数运算 $3^5$），除号此时依然不能出来。所以看到除号时，依然要把它保留下来等待；
5. 读到运算数 $3$：直接输出 $3$；
6. 读到减号 $-$：此时情况变了。当前减号的优先级比刚才保留下来的除号要低。既然除号后面没有更高优先级的运算了，这就意味着除号可以拿出来计算并输出了；
7. 那么前面的加号呢？减号与加号优先级平级，按照从左往右结合的原则，加号也应该出场输出了。最后才轮到减号以及后续项。

由此我们可以总结出这样一种处理策略：

- 碰到运算数，直接输出；
- 碰到运算符，我们不能立刻输出，必须把它暂存起来。当读到下一个运算符时，拿它跟之前暂存的运算符做优先级比较：如果前面暂存的运算符优先级比当前运算符来得高，说明它已经可以拿来计算了，予以输出；如果前面暂存的运算符优先级比当前的低，那么当前的运算符还不能拿来运算，因为后面可能还有一个优先级比它高的，所以仍然要保留起来。

在整个过程中，运算符是按扫描顺序暂存进去的，而比较和弹出时，总是先拿最新存入的那一个运算符来比较。这种"后存入先比较、后存入先出场"的特性，正好对应了堆栈（Stack）这种数据结构。

如果表达式中带有括号，情况又会怎样？我们再看一个包含括号的经典例子：$a * ( b + c ) / d$。

基本策略依然不变：碰到运算数直接输出，碰到运算符存入堆栈等待比较。但括号有其特殊性：

- 遇到运算数 $a$：直接输出 $a$；
- 遇到乘号 $*$：暂时不能确定后面运算，乘号压入栈中；
- 遇到左括号 $($：我们可以把括号当作一个运算。那么大家看看这个左括号的优先级高，还是乘号的优先级高？显然左括号的优先级高，所以在堆栈外面的时候它的优先级比乘号要高，放到堆栈里去；
- 遇到运算数 $b$：直接输出 $b$；
- 遇到加号 $+$：加号是一个运算符号。刚才讲了，左括号优先级比乘号高，乘号又比加号高，是不是这个时候这个左括号优先级比较高呢？我们想一想，好像不是这么回事情。当把一个左括号放在堆栈外面的时候，那么这个时候就意味着这个括号要先进行计算；然后呢，当它放到堆栈里去的时候呢，这个时候必须要把括号的内容先算完，而这个时候不能把左括号就拿出来做计算了。**所以左括号一旦扔到堆栈里去，它的优先级就降到最低。** 所以在这种情况下面呢，我们不应该认为左括号优先级比较高，而是认为优先级比较低。那么把加号继续扔进去。所以同样一个运算符，它在堆栈外面跟堆栈里面，它的运行优先级是不一样的，那主要指的就是左括号；
- 遇到运算数 $c$：直接输出 $c$；
- 遇到右括号 $)$：这个时候怎么办？这个时候意味着这个括号这一堆东西已经全部处理完了。那么我们这种处理方法呢，就是把堆栈顶的运算符号一个一个地抛出来，直到碰到左括号为止。所以呢就把加号抛出来，那么这个时候呢堆栈里面就只有一个乘号了；
- 接下来我们继续往后看，碰到了这个除号。那么除号优先级跟乘号比，谁有优先级高？优先级是一样的。但这里算术运算里面还有一个规则：**同一个优先级的时候呢，它的顺序是从左到右**，也就是说乘号和除号碰上的时候呢，它的顺序是左边的优先。所以呢就乘号要先运算，那么这个时候呢乘号就可以出来了，就把除号放进去；
- 遇到运算数 $d$：直接输出 $d$；
- 再往后面看了，没了没了，就把堆栈的这个运算符呢也抛出。

所以这样的话就得到了对应的这个后缀表达式。

```text
输入项    操作动作与优先级比较判定          运算符栈 (栈底 -> 栈顶)    当前输出序列
--------------------------------------------------------------------------------------
a         运算数，直接输出                  [ ]                       a
*         栈空，乘号压栈                    [*]                       a
(         栈外优先级最高，压栈              [*, (]                    a
b         运算数，直接输出                  [*, (]                    a b
+         栈内(优先级最低，加号优先级高，入 [*, (, +]                 a b
c         运算数，直接输出                  [*, (, +]                 a b c
)         括号结束，弹栈直到左括号，丢弃(   [*]                       a b c +
/         同级左优先，弹出*输出，/压栈      [/]                       a b c + *
d         运算数，直接输出                  [/]                       a b c + * d
(结束)    表达式读完，排空栈内残留运算符    [ ]                       a b c + * d /
```

*图解说明：表格完整展示了中缀表达式转换为后缀表达式的全流程追踪，运算数直接进入输出流，运算符依据栈内与栈外优先级的动态比较规则进出堆栈。*

从这个过程当中可以看到，它的时间复杂性是线性的，每次循环一次处理一个运算数或者运算符号。

#### 算法通用流程

把上述推导过程抽象出来，中缀表达式转换为后缀表达式的通用算法流程如下：

从头到尾依次读取中缀表达式的每一个对象，这个对象有几种情况：一个是运算数，一个是运算符号，一个是左括号，还有一个呢是右括号。那么我们根据这个不同的情况做不同的处理：

- 如果我们碰到的是一个**运算数**，那么直接输出；
- 如果碰到的是**左括号**，把它压到堆栈里去；
- 如果碰到的是**右括号**，就把堆栈顶的运算符号一个一个地弹出来，一直碰到左括号为止。当然这个左括号是不用输出的，就扔掉，不要了；
- 如果是个**运算符**呢，那么我们要比较一下它的优先级，跟栈顶运算的一个优先级：如果它的优先级大于栈顶运算符的优先级，那么我们这个时候就把外面的这个运算符号压到堆栈里去；如果它的优先级小于栈顶运算符的优先级，就把栈顶的运算符号弹出来，然后继续比较，继续把外面的运算符跟栈顶的运算符再做比较，一直到外面的运算符优先级大于栈里面的这个运算符的优先级为止，这个时候就把外面的往里压。

我们的第一列呢是待处理的表达式，就是我们后面还有多少个元素需要处理的；然后后面那一列呢是代表当前堆栈的状态；然后最后一列呢是代表当前输出的状态。大家可以课后好好看一下这个过程，他到底是怎么做的，就是用我们刚才讲的那种方法：碰到运算数怎么处理，运算符号怎么处理，左括号怎么处理，右括号怎么处理。

#### 栈的其他经典场景

堆栈除了求表达式之外，还有别的很多用途，很典型的比方说它用在我们编译实现、函数的调用以及递归的实现过程当中。

我们知道在程序设计语言里面，我们可以从一个函数去调用另外一个函数，等那个函数执行完了之后再回过头来。那么这里需要解决一个问题：**那边调用完了回到哪里？还有回来的时候，原来的状态让你恢复出来。** 所以这个时候呢，我们需要把调用之前的一些变量的状态，以及调用回来之后准备要执行的程序的地址，把它保存起来。

那么我们从这个函数调那个函数，到那个函数的时候呢，他可能还会再调下一个函数，下一个函数呢还可能再调下一个函数。如果是有一系列的函数调用过程，我们就需要保存一系列的东西。函数调用回来的时候呢，就是倒过来一步一步地返回：$a$ 调用 $b$，$b$ 调用 $c$，然后 $c$ 回到 $b$，$b$ 再回到 $a$。所以我们需要有一个管理的机制，能够把我们调用之前的一些变量的状态，以及我们准备要返回的地址保留起来。而这个过程可能是系列执行的，所以你要一系列能恢复过来。

那么这样的一种能够保存这些变量和返回地址的这样一种数据结构的组织方式呢，它必须要有一个特点：**就是按照顺序地存，然后按倒过来地顺序还回应。** 这个特点呢实际上就是对照着堆栈来。

除了在函数调用里面呢，更重要的是它实现了一种递归、实现函数调用的一种实现机制。如果没有堆栈这样的一种机制，递归函数要实现是非常困难的。

除了这个之外，在**回溯算法**的实现当中，堆栈也发挥了重要作用。回溯法是算法设计的一种主要思想，我们教材里面举了一个例子叫做老鼠走迷宫。老鼠从一个路口进去，要找到一条路径从一个出口出来。在这个过程当中呢，没有什么特别的算法能做这个事情，只能不断地试探，试探各种可能性：从这一步试探下一步哪个地方可以走，然后到下一步再来试探各种可能性；当到某一步的时候，各种可能性试探都走不通的时候，他要回到上一步的位置，然后在上一步这个位置进一步地再去试探。

所以这个过程呢，要把我们试探的路径保存起来，等到哪一步是他不成功的时候呢，要回到最近一次试探的状态。所以这个呢实际上也是一种堆栈的特性，所有的回溯算法呢就可以很容易地实现。

另外还包括我们在图里面**深度优先搜索**的实现，也是借助于堆栈来实现的。当然表现形式很可能是一种递归，实际上它就是堆栈。

### 队列与循环队列的顺序存储实现

#### 队列的基本概念与操作集

队列跟堆栈一样，也是一种受限制的线性表。其实我们在日常生活当中经常会碰到排队。我们来观察一下什么是队列，它里面有最主要的有两个操作：一个叫做**入队**，一个叫**出队**，也就是说你能加入到这个队伍，还有呢，你受到服务之后离开这个队伍。

我们观察一下就可以发现，你加入这个队伍呢必须站在**队尾**，然后你接受服务呢，从**队头**开始。队列呢，它是以这个我们叫做受操作约束的一种线性表，它两个最主要的操作插入和删除呢，分别发生在队列的两头啊。

一般的线性表呢都可以在任何位置进行插入、删除。对比于堆栈，堆栈也是一个受限的线性表，但是我们知道堆栈它的插入删除只能在一端进行；而队列呢是分别在两端，数据的插入呢我们称之为**入队**，数据的删除呢我们称之为**出队**。所以由于它是从一端插入、另外一端删除，所以它表现出来的一个特点呢叫做**先来先服务**，所以他这种表呢又被称为**先进先出表**、队列。

它的操作那就涉及到队列 $Q$，还有里面的一个 `item`，它的类型是 `ElementType`。主要操作有这么五种：一个是建立一个队列；判别一个队列是不是满了；然后往这个队列里面加入一个元素；判别这个队列是不是空的；另外呢从这个队列里面删除一个元素，当然这个元素一定是位于队列的头，同时把它返回队列的存储。

#### 顺序存储与假溢出问题

实现呢也是一样的，有两种方式，一个是顺序存储，一个是链式存储。

顺序存储呢就是用我们这个数组来进行表示，也就是说我们用一个数组来存储我们队列的元素。因为队列有两头，我们在一头插入、另外一头删除，所以我们用两个变量来指示这两头。

队列的头呢我们叫 `front`，队列的尾呢叫 `rear`。我们对比一下堆栈，堆栈是一个数组再加上一个 `top`，因为他只在一端进行操作，用一个变量就够用了；而我们队列是在两头，所以要用 `front`、`rear`。那么这就形成了我们队列的这样的一个结构。

```c
struct QNode {
    ElementType Data[MAXSIZE];
    int front;
    int rear;
};
typedef struct QNode *Queue;
```

我们举一个例子。假如说我们有一些工作需要处理，那么我们按照这个工作到来的先后顺序进行处理，所以我们准备要处理的这些工作呢就形成了一个队列。

一开始的时候队列也是空的，这个时候 `front` 指向哪里呢？一开始我们可以把它们都设为 $-1$，那么大家都等于 $-1$，那么这个队列就是空的了。接下来我们往里面加入一个工作，那么这个时候呢 `rear` 呢是指向了 0，`front` 也指向 0。再加一个工作，`rear` 呢再往后挪，往后挪就是加一，下标往后挪一位。

接下来操作呢，我们要从队列里面删除一个元素了。我们连续加入三个元素，然后要删除一个元素了，那么这个时候呢 `front` 呢只是等于 $-1$——因为没有删除，所以 `front` 一直保持不动。所以实际上这个 `front` 呢是指向这个队列的**头一个元素的前一个**。那么连续加入三个元素以后 `front` 仍然是 $-1$，再前面一个 $-1$……所以这个时候 `front` 只是等于 $-1$。然后我们删除了一个元素，那么就挪走了一个，现在的话队列头在下标为 1 的位置，但是我们的 `front` 相当于 0。

所以整个队列操作就是：当你加入一个元素的时候呢 `rear` 加一；删除一个元素的时候呢 `front` 加一。

好我们再加一个元素，我们到了这个状态。这个状态我们看到了，这个队列已经排到了数组的最后了，这个时候你想加入一个元素就加不进去了。而实际上我们队列呢前面还是空的，但是你加不进去了，因为你已经排到最后了。所以这个时候要想个办法来解决这个问题。

我们很自然地就想到：**后面排不了，你排到前面去嘛，不就可以了。** 接下来如果来了个新的元素的时候呢，我们可以把新的元素放在这个位置，那么这就形成了我们后面称之为的叫做**循环队列**。就是说我们把这个数组把它搬过来，形成一个环，所以的话你一直放，从 0 的这个位置开始放，放到 5，放满了，接下来再回过头来再放到 0，这就形成了我们循环队列的这样一种组织结构。

```text
        下标环绕规则：(5 + 1) % 6 = 0

                 0  -------->  1
               /                \
              5                  2
              |                  |
              4  <--------  3

        指针前进方向： ... 3 -> 4 -> 5 -> (5+1)%6 = 0 -> 1 ...

        [ 空 ]  front = rear = 0
                数组里有位置，但队列本身一个元素都没有

        [ 满 ]  (rear + 1) % MAXSIZE == front
                牺牲 1 个单元：6 个数组位置最多只放 5 个元素
                本例中 rear = 5，于是 (5+1)%6 = 0，正好撞上 front
```

*图解说明：左半部分给出循环队列的"环"与下标环绕规则；右下角是空状态，右下方是牺牲一个存储单元后判定为满的状态。*

#### 循环队列空满判别的核心矛盾与化解

在循环队列中，一开始的时候呢 `front`、`rear` 都指向某个位置，**`front` 和 `rear` 相等的时候是空的**。因为按照我们前面的组织方法，`rear` 是指向这个队列的实际上的最后一个元素的位置，而 `front` 是第一个元素的前一个，所以当 `front` 和 `rear` 相等的时候，就意味着这个队列里是没有元素的。

接下来我们开始加入一个元素，那么 `rear` 挪到这个位置了，`front` 保持不动，还在 0 这个位置，所以这个时候队列有一个元素。紧接着又加了一个元素，再加，我们不断地操作。好到这个位置了，总共这个数组分量是六个，我们现在已经放了五个元素了。

如果这个时候我们再想放一个元素，会发生什么？这个数组本身有个空位，照道理是应该能加进去的。但是**加进去之后产生什么结果呢？** 加进去之后 `rear + 1 = 1`，`front` 也等于 1，`front` 和 `rear` 相等了。按照这样的一种组织方法，`front` 和 `rear` 相等是代表队列是空的，现在呢被你加了一个元素，队列满了，`rear` 也等于 1。那么倒过来说，`front` 和 `rear` 如果相等，我问你队列是空的还是满的？你就搞不清楚了。因为空的时候相等，满的时候也相等。所以这就是我们碰到的一个问题。

那么为什么会出现这种情况？我们判别队列的状态，也就是说这个队列到底是空、还是一个元素、还是两个元素、还是满，我们是怎么判别的？**我们是根据 `front` 和 `rear` 的相对关系，也就是他们之间的距离来判别的。**

而 `front` 和 `rear` 的取值范围是 0 到 $n-1$，对我们这个例子来讲是 $0 \sim 5$，所以 `front` 和 `rear` 的差距是六种情况，也是这六种情况：$0 \sim 5$。也就是说我这个数组如果是大小是 $n$ 的话，`front` 和 `rear` 之间的差距的情况呢就是 $n$ 种。

那么我们来看一下队列有几种情况。对于我们这个六个元素组成的数组来讲，队列的情况有这么几种：什么元素也没有，这是一种情况；一个元素；两个元素；三个元素；四个元素；五个元素；六个元素。所以**数组大小如果是等于 $n$ 的话，队列的装载元素的情况有 $n+1$ 种。** 而我们要判别队列空、或者他的这个队列放多少元素的状态，是根据两方面的差距，这个差距呢只有 $n$ 种情况。

也就是说，你想用 $n$ 种的状态来区分实际上存在的 $n+1$ 种情况，怎么可能不矛盾？就像我们用一个比特位、用一个 0 1 来区分三种情况，做不到。所以这是它的根本原因。

解决的方案有两种。**第一种我们增加一个额外的标记：**

- 比方说我们用一个变量 `size` 或者 `tag`。`size` 呢是用来记录当前队列的元素的这个数，当你加入一个元素的时候呢 `size` 加一，删除一个元素的时候呢 `size` 减一。所以我只要根据 `size` 是等于 0 还是等于 $n$，就可以知道是空的还是满的；
- 或者说我用一个标记 `tag` 0、1，当你插入一个元素的时候呢 `tag` 设为 1，删除一个元素的时候 `tag` 等于 0。所以当你 `front` 和 `rear` 相等的时候，你搞不清楚是空还是满的时候，你就要去看这个 `tag`。这个 `tag` 就代表了最后一次操作是插入还是删除，那么你就知道了到底是空还是满。

**另外一种解决方法呢，我这个数组大小虽然是 $n$，但是我不放 $n$ 个元素，最多只放 $n-1$ 个元素。** 就像我们这个一样的数组有六个，但是我最多放五个，到了目前这个状态就认为是满了，不能再放了。所以这个时候也不会出现 `front` 和 `rear` 相等、不知道是空还是满的情况。

那么具体来讲呢，我们可以采取第二种方案，就是说不要把它全放满，就最多放 $n-1$ 个元素。那么按这样的一种原则呢，我们可以设计出相应的入队函数。

我们有一个 `item`，我们要放到队列的里面去，这个队列我们用一个 `PtrQ` 这个结构指针来进行表示。那么这个时候呢我们要看一下啊，队列是不是满的？怎么判别队列是不是满的呢？从我们前面这个地方这个例子也看到，当前这个状态就是满的了，我们要加入一个元素，那么 `rear` 加 1，`rear+1` 的时候，那个 `front` 碰上了，所以这个时候呢我们就认为它是满的。

前面我们还讲到过了，我们这是一个循环队列，是一个一个的就是一直放，从 0 开始放，放到 5，5 的下一个位置是 0。那么在程序上面怎么实现 5 的下一个又变成 0 呢？我们**用求余函数**，`(5+1)` 对 6 求余就是等于 0 了。所以这是我们实现循环队列的这样一种方法，用求余函数。

所以的话我们的入队的操作，那首先要判别队列是不是满了。怎么判别呢？就是 `(rear + 1) % MAXSIZE` 是不是等于 `front`，如果等于就是说明是满了；如果不等于，那么这个时候我们 `rear` 加一再求余，所以一般情况下就是 6 加 1 了，到最后一位的时候呢，一求余就变成 0 了，然后我们把我们的 `item` 放进去，放到数组里去。这是我们的入队啊，非常简单。

出队出队也一样的，我们要判别一下队列是不是空的。怎么判别是不是空的呢？就是我们前面看到的就比较 `front` 和 `rear` 是不是相等，如果相等就是空了；否则的话就出队。

出队怎么做呢？就是 `front` 加一，同样的我们也求余，所以一般情况下就是 `front` 加 1，到最后一位的时候呢，这样一求余就变成 0 了。我们知道这个 `front` 是指向队列头上元素的前一个，所以 `front` 加 1 的时候呢，`front` 的值指向的正好是队列头上那个元素的位置，所以就 `return` 这个 `Data[front]` 就可以了。

```c
void AddQ(Queue PtrQ, ElementType item) {
    if ((PtrQ->rear + 1) % MAXSIZE == PtrQ->front) {
        printf("队列满");
        return;
    }
    PtrQ->rear = (PtrQ->rear + 1) % MAXSIZE;
    PtrQ->Data[PtrQ->rear] = item;
}

ElementType DeleteQ(Queue PtrQ) {
    if (PtrQ->front == PtrQ->rear) {
        printf("队列空");
        return ERROR;
    } else {
        PtrQ->front = (PtrQ->front + 1) % MAXSIZE;
        return PtrQ->Data[PtrQ->front];
    }
}
```

*代码解析：入队前先做满队检查——如果 `rear` 加 1 对 `MAXSIZE` 求余的结果恰好等于 `front`，说明再放一个元素 `rear` 就会和 `front` 重合，此时拒绝写入；若未满，将 `rear` 下标环形推进一位，然后把元素写入数组对应位置。出队前先比较 `front` 与 `rear` 是否相等，若相等说明队列为空；若非空，将 `front` 下标求余后移一位——因为 `front` 本来指向队头元素的前一个位置，后移一位后正好指向真实的队头元素，直接返回该位置的数据即可。*

### 队列的链式存储实现

#### 单向链表里头尾指针的摆放之争

队列的另外一种实现方法呢就是链表，这跟我们堆栈是一样的，所以同样的我们可以用单向链表来实现我们的这样一个队列。

这个时候同样的问题就冒出来了。比方说我们这是一个单向链表，我们有两个东西，一个叫 `front`，一个叫 `rear`。那么链表有个头、有个尾，那么我们到底 `front` 是在链表的头，还是 `rear` 在链表的头？或者 `rear` 在链表的尾，还是 `front` 在链表的尾？

这个问题呢跟我们前面堆栈的时候我们讨论过的问题是一样的。

我们说 `front` 是要做删除操作的，`rear` 是要做插入操作的。而链表的头——也就是这个位置——做插入或者删除，多方便呢？删除很快，因为可以找到下一个、知道这个位置了，所以也方便了从链表末尾做插入。做插入没问题，做删除有问题：因为这是单向链表，你删了之后呢，不知道前面一个在哪里。

**所以的话，这个位置是不能做 `front` 的。** 所以我们如果这样做的话，只能这里做 `front`，这里做 `rear`，这里前面做删除，后面就炸了。

加入你不能倒过来。如果在后面坐这个 `front` 的时候呢，删掉了就不知道前面一个在哪里了。所以这是我们链表实现的时候呢，它的一个设计的要注意的这样的一点。

```text
单向链表 + 队列的插入删除要求

   head                                        tail
    |                                            |
    v                                            v
  [A] ---> [B] ---> [C] ---> [D] ---> [E] ---> NULL

  出队要删表头： 删掉 [A] 后 knew 下一个就是 [B]   -> 知道位置，O(1)  ✓
  入队要插表尾： 顺着 next 走到 [E]，把它挂上     -> 可行             ✓
  出队要删表尾： 删掉 [E] 后找不到前驱            -> 单向链表做不到  ✗
  入队要插表头： 可以做，但没有意义                 ->                 

  结论：front 必须放在链表头，rear 必须放在链表尾
```

*图解说明：单向链表删除表头节点后能立刻知道新的表头在哪，删除表尾节点后却丢失了前驱，因此 `front` 与 `rear` 的摆放位置由此确定。*

#### 链式队列的数据结构定义

那么这是我们具体的这个数据结构啊。在这个链表里面，每个节点啊都有两个域：一个叫 `data`，是这个节点本身的信息；还有一个指针 `next`，是把节点串在一起啊。这是链表的节点结构。

接下来我们要有一个结构好来代表这个队列啊。代表队列呢最主要的就是两个指针啊：两个指针一个是 `front`，一个是 `rear`，分别指向链表的这个头和尾。

```c
typedef struct QNode {
    ElementType data;
    struct QNode *next;
} QNode, *Queue;

typedef struct {
    QNode *front;      /* 指向链表的头，即队头 */
    QNode *rear;       /* 指向链表的尾，即队尾 */
} Queue;
```

所以这边的话这里的每一个节点呢就是我们这里定义的 `QNode`，然后我们这里定义的这个结构呢就是 `front` 和 `rear`。所以每个链表它是一个结构，这个结构实际上是两个指针，分别指向单向链表，就是队列的头跟队列的尾啊。

#### 链式队列的出队实现

所以我们这边定义了这两个结构。这里显示的是链表队列出队的一个操作，已知的是一个队列，那么这个队列呢用 `PtrQ` 就是我们刚刚才讲的、包含 `front` 和 `rear` 的这个结构的指针 `PtrQ` 来指示。

那么我们的第一步要做的事情呢，就是判别队列是不是空的。那么什么情况下队列也是空的呢？从这里我们看得到，当你的 `front` 是不指向任何东西、等于 `NULL` 的时候，队列就是空的。所以如果等于 `NULL` 的时候呢，就是队列是空的。

否则的话，让这个 `front` 找到队列的头上一个元素。所以我们这里看到了 `frontCell`，它就是队列找到队列的头头个元素，就是这个元素。那么这个位置这就是我们的 `frontCell`。那么找到它，接下来我们要做什么事情呢？要删除一个元素呢，接下来很关键的一步，就是要把这个指针能挪到这个地方来，然后把这个空间把它释放掉——就要把这个节点把它删掉，所以要 `free` 掉这个 `frontCell`。

```text
出队之前：

   PtrQ->front ---> [head] ---> [A] ---> [B] ---> NULL
                             ^ 队列真正要出队的数据在 A
                             |
                        frontCell = front->next

   ┌── 删除前：把 PtrQ->front 指向 A
   │
   │      PtrQ->front ---> [head] ---> [A] ---> [B]
   │                                  ^
   │                                  └── 移到这里
   │
   └── 删除后：再把 head 的 next 跨过 A 接到 B，然后 free(A)

              PtrQ->front ---> [head] ---> [B] ---> NULL
```

*图解说明：出队要删掉的其实是队头元素的前驱节点所指向的下一个节点；`front` 指针顺次前移，跨过被删除的节点后释放其空间。*

一开始呢要把这个链表的头节点把它找着，就是 `frontCell`；然后呢改变这个 `front` 的这个指针的这个值。然后在这里面呢我们要判别一下队列是不是只有一个元素：**当 `front` 和 `rear` 相等的时候**，就是我们这边的这个情况，当 `front` 和 `rear` 相等的时候，这个队列只有一个元素被你删了，那么这个 `rear` 也要改变。

如果队列不止一个元素，你把头节点删掉了之后，队列头拿掉了之后，那 `rear` 是不动的，仍然指向最后一个元素。所以当你队列只有一个元素的时候呢，`front` 和 `rear` 都把它设为 `NULL`；否则的话只要改变 `front` 指针就行了。

接下来把第一个节点的这个元素的值啊，通过我们这个赋值先保存到一个变量里面，我们 `free` 掉这个第一个节点，最后啊最后 `return` 出这个变量的值。

```c
ElementType DeleteQ(Queue PtrQ) {
    QNode *frontCell;
    ElementType item;

    /* 第一步：判别队列是否为空 */
    if (PtrQ->front == NULL) {
        printf("队列空");
        return ERROR;
    }

    /* 第二步：让 front 指向队列的头一个元素 */
    frontCell = PtrQ->front->next;

    /* 第三步：关键一步，把值先存下来，再把 front 指针挪到这个地方来 */
    item = frontCell->data;
    if (frontCell == PtrQ->rear) {
        /* 队列只有一个元素，删掉之后 front 和 rear 都置空 */
        PtrQ->front = PtrQ->rear = NULL;
    } else {
        PtrQ->front = frontCell->next;
    }

    /* 第四步：释放这个节点的空间 */
    free(frontCell);

    return item;
}
```

*代码解析：出队要删掉的节点其实是队头前驱所指向的下一个节点。四步走下来——判空、定位队头元素节点、先把数据存进变量再让 `front` 指针跨过该节点、最后 `free` 释放——整个过程只做了常数次指针改写，因此出队的时间复杂度是 $O(1)$，比顺序存储下的移动代价低得多。*

那么这里给大家看到的是用链式队列出队操作的这样的一个例子。反过来根据这样的一个思想，大家我想也很容易地能够实现入队的操作。

### 链表实现一元多项式的加法运算

#### 多项式的数据结构定义

在数学运算中，两个多项式相加的基本规则非常直观：如果有两项的指数相同，就把它们的系数相加；如果指数不同，就把各自的项直接抄录过来。

观察多项式的数学表示，为了便于程序处理，各项都是**严格按照指数递降的顺序排列**的，例如：
$P_1 = 3x^5 + 2x^4 - x^3 + 2x$
$P_2 = 4x^4 + x^3 + x^2 + x - 1$

在计算机中，我们可以采用一个**不带头节点的单向链表**来表示一元多项式。链表中的每一个节点对应多项式的一个非零项，节点包含三个分量：一个是 `coef`，该项的系数；一个是 `expon`，该项的指数；还有一个是 `link`，指针，指向按照指数递降排列的下一个项节点。

```c
struct PolyNode {
    int coef;
    int expon;
    struct PolyNode *link;
};
typedef struct PolyNode *Polynomial;
Polynomial P1, P2;
```

#### 多项式加法算法流程与指针推进

有了链表结构，两个多项式相加的算法思路如下：

用两个指针 `P1` 和 `P2` 分别指向两个待加多项式的第一个节点，也就是最高项。随后启动循环，不断比较当前两项的指数大小：

1. **若 `P1` 当前项的指数大于 `P2` 当前项的指数**：说明在另一个多项式中不可能有同类项能与 `P1` 当前项合并了，直接将 `P1` 当前项复制并挂接到结果多项式的尾部，同时 `P1` 指针后移一位；
2. **若 `P2` 当前项的指数大于 `P1` 当前项的指数**：直接将 `P2` 当前项复制并挂接到结果多项式的尾部，同时 `P2` 指针后移一位；
3. **若两项的指数相同**：说明属于同类项，将其系数相加（`sum = P1->coef + P2->coef`）。若相加结果不为 0，以该和作为系数、当前指数作为指数，生成一个新节点挂到结果多项式尾部；若相加结果为 0，说明两项相互抵消，不生成新节点。无论是否抵消，`P1` 和 `P2` 指针都必须同时向后移动一位。

循环持续进行，循环条件是 `P1 && P2`（即两个多项式都还有未处理完的项）。当循环退出时，意味着必有其中一个多项式已经全部扫描处理完毕，而另一个多项式可能还剩下若干项。此时，只需要把剩下的那个多项式后续的所有节点，依次全部追加到结果多项式的末尾即可。

我们具体来看这个例子。`P1` 和 `P2` 一开始分别指向这两个多项式的第一个，也就是指数最高项的这个节点。然后我们来看一下 `P1`、`P2` 的这个指数，一个是 5 一个是 4，那么 5 大，那么 5 拷贝过去，就 3、5，拷贝到我们结果对象这里去，然后 `P1` 往后挪。

再比较 `P1`、`P2` 都等于 4，指数都等于 4，系数相加 2 和 4 相加等于 6，再拷贝过来，然后 `P1`、`P2` 同时往后挪。然后再比较指数都等于 3，那么就是系数 $-1$ 和 1 相加等于 0，零嘛就不用拷贝了啊，但是 `P1`、`P2` 也一样的都往后挪。

那这个时候呢我们一个指数是 2，一个指数是 1，那么把 2 这个拷贝过来，然后 `P2` 往后挪。然后这个时候呢两个指数都等于 1 了，系数相加，一个 2 加强等于 3，那就拷贝过来，同时 `P1`、`P2` 都往后挪。

挪完了之后，`P2` 就等于空了，那么这个时候呢就把后面所有的东西都接到这个结果多项式的后面去，那就形成最后的这样的结果。

```text
P1: [ 3 | 5 ] -> [ 2 | 4 ] -> [ -1 | 3 ] -> [ 2 | 1 ] -> NULL
      ^
P2: [ 4 | 4 ] -> [ 1 | 3 ] -> [  1 | 2 ] -> [ 1 | 1 ] -> NULL
      ^
比较指数: 5 > 4，将 (3, 5) 挂入结果链表，P1 后移
结果链表: [临时头] -> [ 3 | 5 ]
                       ^ rear
```

*图解说明：`P1` 与 `P2` 指针逐项对比当前指数，较大者优先挂接至结果链表尾部 `rear` 之后，若指数相同则系数相加合并，两指针同步后移。*

#### 临时头节点技巧与 attach 核心实现

在将节点逐一追加到结果多项式时，我们需要返回结果链表的头指针，同时还需要一个尾指针 `rear` 不断在末尾接入新节点。为了避免每次插入节点时都要判断"链表是否为空、是给头指针赋值还是修改尾指针 link"这类繁琐的特判逻辑，我们采用一个极其优雅的编程技巧：**构造一个临时的空间点，作为结果多项式的表头。**

在加法函数一开始，通过 `malloc` 申请一个临时的空节点，让表示结果链表头部的 `front` 和尾部的 `rear` 都先指向它。后续所有新项直接统一挂在 `rear` 后面推进。在算法结束返回前，进行清理扫尾工作，有这么几步：

- 最后一项挂接完毕后，将 `rear->link` 设为 `NULL`；
- 令临时指针 `temp = front`；
- `front = front->link`，使 `front` 指向真正多项式的第一项；
- `free(temp)`，将最初申请的临时空间点释放掉；
- 最后直接 `return front` 即可。

下面看关键的节点挂接函数 `Attach`。`Attach` 函数接收系数 `c`、指数 `e`，以及当前结果链表的尾指针位置：

```c
void Attach(int c, int e, Polynomial *pRear) {
    Polynomial P;
    P = (Polynomial)malloc(sizeof(struct PolyNode));
    P->coef = c;
    P->expon = e;
    P->link = NULL;

    (*pRear)->link = P;
    *pRear = P;
}
```

> **易错点**：注意 `Attach` 的第三个形参定义的是 `Polynomial *pRear`，也就是指针的指针（二级指针）。
> 为什么必须用二级指针？因为 C 语言的函数参数传递是严格的**值传递**。在 `Attach` 函数内部，我们不仅要把新节点 `P` 挂在当前尾节点的后面（`(*pRear)->link = P`），而且必须让主调函数中的尾指针 `rear` 往前挪，指向这个新节点（`*pRear = P`）。如果我们只传递普通的单级指针 `Polynomial rear`，在函数内部修改形参的值根本无法改变外部真实的尾指针，尾指针就会永远停留在原地无法推进！

具体来讲，`Attach` 里面做的三件事是：先通过 `malloc` 申请这个节点，节点的类型就是 `struct PolyNode`；接下来对这个节点的关键信息赋值，把 `c`、`e` 都赋给它；接下来它的 `link` 就把它设为 `NULL`。最后两句话把新申请的这个节点 `P` 插到 `rear` 的后面——原来我们的 `pRear` 呢是一个指针的指针，所以我们这里呢星号的 `pRear` 就代表指针了，它指向的是我们当前链表的最后一个节点；然后我们来了一个新节点，里面的值赋好了。那么我们要把这个节点挂到它的后面，所以呢就是通过这两句话把 `*pRear` 赋给新 `P` 的 `link`，然后再把 `*pRear` 赋给新 `P`，就是把尾指针的值改掉，让它知道了这个点。这就完成了我们的 `Attach` 的过程。

### 实践设计：一元多项式的乘积与和运算

#### 题目理解与多项式运算机理

在实际编程题目中，题目要求我们设计程序，分别求出两个一元多项式的**乘积与和**。

因为是一元多项式，表达式中只有一个未知数变量 $x$。输入的所有多项式项均已按指数递降顺序排列。

我们先来理解一下这题目的意思。题目要求设计函数，分别求两个一元多项式的乘积与和。那么来看一下我们所谓的一元多项式是什么，这里大家看到的是两个多项式的例子。因为是一元多项式，所以这个多项式的变量只有一个。那么在我们这个多项式里面呢，我们是按照指数递降的顺序进行排列的。对于这样的两个多项式，我们要求做的是这两个多项式的乘积与和。

进来看一下两个多项式的和什么意思？两个多项式的和呢，就是把两个多项式的每一项相加在一起。当把两个多项式的每一项相加在一起的时候，我们还需要做一件事情呢，就是同类项的合并。那么我们这两个多项式呢一个有四项，一个有三项，加在一起是七项。但这里呢有两对它的指数是一样的，也就是说必须进行项的合并，那分别是 $3x^4$ 和 $-7x^4$，合并完后的结果呢就是 $-4x^4$；还有一个是 $6x$ 跟 $3x$，合并完了之后呢是 $9x$。所以四项加三项合并在一起的时候是七项，然后进行同类项合并之后呢，就剩下五项。所以这是两个多项式的和。

接下来我们讲讲多项式的乘积。在代数里面，两个多项式的乘积是指它的每一项跟另外一个多项式的每一项相乘，然后加在一起。同样的在这里面呢也需要同类项的合并。那么我们这两个多项式呢一个是四项，一个是三项，两两相乘呢就会 $4 \times 3 = 12$ 项。但这里呢我们看到其中有一对它的 $x$ 的指数是一样的，那就是 $x$ 的五次方：$3x^4$ 乘以 $3x$ 是 $9x^5$；另外一个呢 $-7x^4$ 乘以 $6x$ 得到的是 $-42x^5$。所以这两项呢要进行合并，合并完后的结果呢就是少了一项，那么两项的乘积呢就是等于 11 项。

第一项是 $15x^{24}$，它是怎么得来的呢？就是我们这两个多项式的第一项相乘——系数相乘，指数相加，所以 $3 \times 5$ 得到的系数是 15，指数呢是 $20+4$ 得到 24。

第二项 $-25x^{22}$，它就是第二个多项式的第一项跟第一个多项式的第二项相乘，所以是负的 25，然后呢一个是 $x$ 的二次方、一个是 $x$ 的平方，所以是 $x$ 的二次加二次方。

第三项 $30x^{21}$，就是第一个多项式的第三项 $6x$ 跟第二个多项式的第一项 $5x^{20}$ 相乘，等于 30，然后指数相加是 $20+1$，所以 $x$ 的 21 次方。

所以最后这个结果呢总共是 11 项。理解了两个多项式相乘和相加到底什么意思的时候，我们再回到这个题目上来。这个题目的要求是这样的：它的输入是这两个多项式的信息，每个多项式的信息是怎么构成的呢？比方说我们这边的第一行，`4` 就代表第一个多项式的项数，它总共有四项，这四项的系数指数按顺序把它列出来，比方 `3 4` 就是 $3x^4$，`-2` 就是负 $x$ 的平方。第二行是第二个多项式有关的信息，那就是有多少项，接下来系数指数一对一对的出现啊，总共是三对。

那么他输出什么呢？要求输出的是**乘积之后**的多项式信息。乘积多项式的信息呢前面讲过，主要的是用系数指数这一对一对的进行表现的，而且是按照指数递降的一种方式。所以呢根据我们前面讲的乘积的结果呢，这两个多项式相乘是 $15x^{24}$、$-25x^{22}$ 等等，那么它所对应的要求的输出呢，就是这些总共 11 项、每一项的系数指数，所以就是 `15 24`、`-25 22`、`30 21` 等等，那么这是输出的第一行。

要求输出的第二行是什么呢？就是这两个多项式相加的结果。那这两个多项式相加的结果呢，前面我们讲过了，就是 $5x^{20}$ 减 $4x^4$ 等等，然后同样的也输出每一项的系数指数，也就是 `5 20`、`-4 4` 等等。

#### 存储结构选型：数组、动态数组与链表

接下来我们来看看这个程序怎么设计。首先一个，我们这个多项式怎么表示的；第二个，我们这个程序的框架大概是怎么样。那么在这个程序框架下面，我们需要解决很多细节的问题：第一个怎么读多项式，两个多项式怎么相加，两个多项式怎么相乘，然后最后的结果怎么输出。所以这个是我们解这道题呢，我们所需要关心的这么几个问题。

首先我们来看一下多项式怎么表示。多项式的表示方法，最核心的就是要表现多项式的关键信息。什么是多项式的关键信息呢？就是它的非零项的系数指数，一对一对的，这个系数要把它表示出来啊。这是一个线性的序列。那么这种线性序列呢有两种在计算机上面存储实现的方式：**第一种呢就是数组的方法。** 相对来说它编程比较简单，而且调试也比较容易。但是用数组来表示这些非零项，很重要的一个东西呢，我们必须要事先确定数组的大小，因为我们事先要定义这个数组。当你这个多项式的项数事先不知道的时候，我们就只能以最大可能的项数来进行表示，实际上项数可能会没那么多，那就会造成空间的浪费。

**另外还有一种方法呢就是链表。** 链表的方法呢正好克服了数组这个特点：它不需要事先知道有多少项，你来一个我给你处理一个，来一个处理一个；来另一项样的信息，我就把它作为一个节点插到这个链表里去。所以它的优点呢是动态性比较强。但是编的程序呢就会比较复杂，涉及到的指针调试也比较困难。

这两种表示方法呢，在我们数据结构设计里面都有它各自的用途、特点不一样。我们要根据应用的场景来确定到底用什么比较合适。那么对于我们这道题来讲，其实我们有个很重要的信息就事先告诉你了：我有多少项。所以对这道题来讲呢，有一种比较好的实现方法呢，就叫**动态数组**——你告诉我有四项，我就通过空间申请 `malloc` 申请四个结构的这样的一个数组，然后把后面四个信息呢都放到这个结构数组里面去。对这道题来讲，比较简单的实现方法就是用动态数组。

我们为了训练大家的链表方面的编程能力，所以后面例子实现的时候呢，我们还是介绍用链表的表示方法。

#### 求解整体框架与核心模块划分

用链表进行表示的时候呢，首先我们要进行数据结构的设计。链表它是由若干个节点所构成的，那么这个节点的信息是什么呢？多项式的关键数据来讲，一个是系数，一个是指数；既然作为一个链表，它的节点呢还有一个域是作为指针指向下一个节点。所以的话链表中的节点呢，就由这三个信息所构成的——系数、指数跟一个指针。

```c
typedef struct PolyNode *Polynomial;
struct PolyNode {
    int coef;
    int expon;
    Polynomial next;
};
```

那么这个指针呢就是这个结构。指针一开始呢把这个结构指针定义成一个新的类型，叫 `Polynomial`。对于前面这样的一个例子啊，$3x^4$、$-5x^2$ 这样四项所构成的多项式，我们用链表来表示呢，大概就形成这样的一个链表，其中的表头我们用一个变量 `P1` 指向这个节点，然后呢每个节点都有一个指针指向下一个节点，每个节点里面都包含两个关键的信息，就是系数跟指数。那么同样的这个第二个多项式呢就是 `P2`，我们也可以用对应的这样的一个链表来进行表示。

在这个程序框架下面，我们需要解决很多细节的问题：第一个怎么读多项式，两个多项式怎么相加，两个多项式怎么相乘，然后最后的结果怎么输出。

### 本讲提到的题目

#### 一元多项式的乘积与和运算

- **题目描述**：
  设计函数分别求两个一元多项式的乘积与和。
- **输入格式**：
  输入分 2 行，每行分别先给出多项式非零项的个数，随后以指数递降方式输入一个多项式非零项的系数和指数（绝对值均为整数）。数字间以空格分隔。
- **输出格式**：
  输出分 2 行，分别以指数递降方式输出乘积多项式以及和多项式非零项的系数和指数。数字间以空格分隔，且行尾不得有多余空格。若为零多项式则输出 `0 0`。
- **输入样例**：
  ```text
  4 3 4 -5 2 6 1 -2 0
  3 5 20 -7 4 3 1
  ```
- **输出样例**：
  ```text
  15 24 -25 22 30 21 -10 20 -21 8 35 6 -33 5 14 4 -15 3 18 2 -6 1
  5 20 -4 4 -5 2 9 1 -2 0
  ```

#### 样例推演与算法依据

1. **多项式代数表达式还原**：
   - 多项式一：$P_1(x) = 3x^4 - 5x^2 + 6x - 2$
   - 多项式二：$P_2(x) = 5x^{20} - 7x^4 + 3x$
2. **和运算推导验证**：
   - 指数 20 项：$5x^{20}$（来自 $P_2$）
   - 指数 4 项：$3x^4 + (-7x^4) = -4x^4$
   - 指数 2 项：$-5x^2$（来自 $P_1$）
   - 指数 1 项：$6x + 3x = 9x$
   - 指数 0 项：$-2$（来自 $P_1$）
   合并后得到：$5x^{20} - 4x^4 - 5x^2 + 9x - 2$，按降序排列共 5 项，系数指数对输出为 `5 20 -4 4 -5 2 9 1 -2 0`。
3. **乘积运算推导验证**：
   $P_1$ 的 4 项与 $P_2$ 的 3 项进行交叉相乘：
   - $5x^{20} \times (3x^4 - 5x^2 + 6x - 2) = 15x^{24} - 25x^{22} + 30x^{21} - 10x^{20}$
   - $-7x^4 \times (3x^4 - 5x^2 + 6x - 2) = -21x^8 + 35x^6 - 42x^5 + 14x^4$
   - $3x \times (3x^4 - 5x^2 + 6x - 2) = 9x^5 - 15x^3 + 18x^2 - 6x$

   在指数为 5 的项上发生同类项合并：$-42x^5 + 9x^5 = -33x^5$。其余各项指数互不相同，按指数降序最终得到 11 项：
   $$15x^{24} - 25x^{22} + 30x^{21} - 10x^{20} - 21x^8 + 35x^6 - 33x^5 + 14x^4 - 15x^3 + 18x^2 - 6x$$
   其系数指数序列与样例输出严格一致。

### 多项式运算的程序主框架设计

#### 整体控制流程与功能划分

面对一个复杂程序，我们绝不能提笔就写细节，而是必须先搭建起顶层的 `main` 函数骨架。对于一元多项式的乘法与加法运算，输入输出的交互流程非常明确：

1. 读入第一个多项式；
2. 读入第二个多项式；
3. 计算两者的乘积并输出；
4. 计算两者的和并输出。

基于自顶向下的模块化设计思想，主函数只需要协调几个独立功能模块，分别负责输入、乘法、加法与输出：

```c
int main()
{
    Polynomial p1, p2, pp, ps;

    p1 = ReadPoly();
    p2 = ReadPoly();

    pp = Mult(p1, p2);
    PrintPoly(pp);

    ps = Add(p1, p2);
    PrintPoly(ps);

    return 0;
}
```

从这段骨架代码可以看出，我们需要实现四个核心函数：
- `ReadPoly()`：负责从标准输入解析数据，构造出单链表表示的多项式，并返回表头指针；
- `Mult(p1, p2)`：接收两个多项式链表，完成逐项相乘与同类项合并，返回乘积多项式链表；
- `Add(p1, p2)`：接收两个多项式链表，完成降序归并相加，返回和多项式链表；
- `PrintPoly(p)`：接收多项式链表，按照题目严格要求的空格与换行规范输出。

#### 链表数据结构定义

多项式中的每一项由“系数”与“指数”两个关键分量构成。由于多项式的项数未知且可能随时增删，采用动态单向链表是最自然的存储选择：

```c
typedef struct PolyNode *Polynomial;
struct PolyNode {
    int coef;               /* 系数 */
    int expon;              /* 指数 */
    Polynomial link;        /* 指向下一个节点的指针 */
};
```

在这里，`Polynomial` 被定义为指向 `struct PolyNode` 结构的指针。后续所有的多项式传递，本质上都是在传递该链表首节点的地址。

### 多项式的读入与尾插构建

#### 输入数据规范与解析循环

根据实际输入规范，多项式的数据组织遵循以下约定：
- 第一项为一个非负整数 $N$，代表该多项式包含的项数；
- 随后紧跟 $N$ 对整数，每一对分别对应一个单项式的“系数（$c$）”与“指数（$e$）”；
- 输入数据已经保证严格按照指数从大到小的递降顺序给出。

例如，输入 `4 3 4 -5 2  6 1  -2 0`，代表共有 4 项，对应的多项式为 $3x^4 - 5x^2 + 6x - 2$。

因此，`ReadPoly()` 的基础读取流程必须先读取整数 $N$，随后借助一个 `while (n--)` 循环依次读取每一对系数与指数：

```c
Polynomial ReadPoly()
{
    Polynomial P, rear, t;
    int c, e, n;

    scanf("%d", &n);
    /* 随后在循环中读取每一项并追加到链表末尾 */
    while (n--) {
        scanf("%d %d", &c, &e);
        /* 将系数 c 和指数 e 构造成新节点，追加至 rear 之后 */
    }
    ...
}
```

因为输入数据本身已经按指数递降排列，我们每读入一对新的 $(c, e)$，就必须将其接在当前链表的末尾。若每次插入都从表头重新遍历到表尾，构造长度为 $N$ 的链表时间复杂度将高达 $O(N^2)$。为了保证 $O(N)$ 的高效构造，必须引入一个始终指向当前结果多项式最后一项的尾指针 `rear`。

#### 尾部追加与二级指针传参

每当读入新的一项，我们都需要调用一个名为 `Attach(c, e, ...)` 的追加函数。该函数的核心任务包括：
1. 动态申请一个新节点，将系数 $c$ 与指数 $e$ 赋值给它，并将新节点的 `link` 置为 `NULL`；
2. 将该新节点挂接在当前尾指针 `rear` 所指向节点的后面；
3. **将尾指针 `rear` 更新为指向这个刚刚加入的新节点**。

这里蕴含着 C 语言中最容易出错的指针陷阱。

> **易错点**：C 语言的函数参数传递是严格的“值传递”。如果我们将 `rear` 作为一级指针 `Polynomial rear` 传入 `Attach`，函数内部执行的 `rear = P` 仅仅修改了形参副本所保存的地址，调用者作用域中的实参指针 `rear` 丝毫不会发生改变！下一轮插入时，`rear` 依然停留在原位，新节点将直接覆盖前一个插入的节点。

为了在函数内部真正改变调用者作用域中的指针变量本身，我们必须传递指针的地址——也就是**二级指针**：

```c
void Attach(int c, int e, Polynomial *pRear)
{
    Polynomial P;

    P = (Polynomial)malloc(sizeof(struct PolyNode));
    P->coef = c;
    P->expon = e;
    P->link = NULL;

    (*pRear)->link = P;     /* 将新节点接在原末尾节点之后 */
    *pRear = P;             /* 将尾指针本身的值修改为新节点的地址 */
}
```

在调用时，必须显式传入尾指针变量的地址：`Attach(c, e, &rear);`。

```text
调用前状态:
[ *pRear (即实参 rear) ] ----> [ 末尾节点 RearNode ] -> NULL

Attach 内部执行:
                   P ----> [ 新节点 NewNode (c, e) ] -> NULL
(*pRear)->link = P:
[ 末尾节点 RearNode ] ----> [ 新节点 NewNode ] -> NULL

*pRear = P:
[ *pRear (即实参 rear) ] ----> [ 新节点 NewNode ] -> NULL
```

上图展示了二级指针解引用修改尾指针指向的全过程：通过解引用 `*pRear`，代码成功修改了调用者内部尾指针的内存指向，使其平滑移动到新节点上。

#### 哑节点的工程妙用与内存清理

解决了指针传参问题，我们紧接着面对初始化难题：在读入第一项之前，`rear` 的初值应该是什么？

通常有两种截然不同的处理思路：

1. **直接置空法（`rear = NULL`）**：
   一开始令 `rear = NULL`。在 `Attach` 内部必须进行判断：若 `*pRear == NULL`，说明当前插入的是全表第一个节点，必须直接将新节点赋给 `*pRear`，而不能执行 `(*pRear)->link = P`（否则将导致空指针解引用崩溃）；若 `*pRear != NULL`，才走正常的尾插逻辑。这种方式迫使 `Attach` 在每插入一个节点时都要做一次非空判断，代码分支繁琐。

2. **临时哑节点法（Dummy Head Node，推荐）**：
   在正式读入任何数据前，先由系统通过 `malloc` 临时分配一个无数据的“空节点”（哑节点），并让初始的 `rear` 和临时表头指针 `P` 都指向这个哑节点。
   
这样一来，无论是插入第一项还是后续的任意一项，当前 `rear` 都必定指向一个合法节点，`Attach` 内部完全不需要判断空与非空，统一执行标准的尾插两行代码。

```text
初始阶段 (申请临时哑节点):
P, rear ----> [ 临时哑节点 (空) ] -> NULL

读入第一项 (c=3, e=4) 调用 Attach:
P ----------> [ 临时哑节点 ] -> [ 3, 4 ] -> NULL
                                 ^
                                rear

循环结束时:
P ----------> [ 临时哑节点 ] -> [ 3, 4 ] -> [ -5, 2 ] -> [ 6, 1 ] -> NULL
                                                          ^
                                                         rear

释放哑节点后:
               t 指向并释放
              [ 临时哑节点 ]
                    |
P -----------------> [ 3, 4 ] -> [ -5, 2 ] -> [ 6, 1 ] -> NULL (真实链表头)
```

上图清晰描绘了哑节点在生命周期中的角色变换：它像一个临时的脚手架，支撑起统一的插入逻辑；而在整个构建流程彻底结束时，我们必须将脚手架拆除。

拆除哑节点并返回真实链表头的标准操作如下：

```c
t = P;              /* 记住哑节点地址，准备释放 */
P = P->link;        /* 让表头指针 P 指向真正的第一个有效数据节点 */
free(t);            /* 彻底释放哑节点内存，杜绝内存泄漏 */
return P;           /* 返回真正的多项式首节点地址 */
```

将上述细节熔铸于一炉，得到严谨规范的 `ReadPoly()` 完整实现：

```c
Polynomial ReadPoly()
{
    Polynomial P, rear, t;
    int c, e, n;

    scanf("%d", &n);

    /* 构造临时哑节点 */
    P = (Polynomial)malloc(sizeof(struct PolyNode));
    P->link = NULL;
    rear = P;

    while (n--) {
        scanf("%d %d", &c, &e);
        Attach(c, e, &rear);
    }

    /* 释放临时哑节点 */
    t = P;
    P = P->link;
    free(t);

    return P;
}
```

### 多项式相加、相乘与格式化输出

#### 多项式相加的归并架构

由于参与运算的两个多项式链表在读入后均已严格保持指数递降，多项式相加的本质就是一个经典的**双指针降序归并**过程。

我们定义两个游标指针 `t1` 和 `t2` 分别指向多项式 $P_1$ 和 $P_2$ 的当前节点。为了处理方便，相加函数同样采用临时哑节点技术构造结果链表。整个处理框架由三个顺序排列的 `while` 循环构成：

1. **双链表非空比较循环**：
   当 `t1` 和 `t2` 均未走到末尾时，比较当前两节点的指数 `expon`：
   - **指数相等**：两项系数相加。若相加之和不为零，调用 `Attach` 将和系数与该指数追加到结果末尾；若相加之和恰好为零，则该项在数学上抵消，不进行任何追加。随后 `t1` 和 `t2` 同时后移一步。
   - **`t1` 指数较大**：说明 $P_1$ 的当前项在结果中无人能与之合并，调用 `Attach` 将该项原样拷贝追加到结果末尾，并将 `t1` 后移一步。
   - **`t2` 指数较大**：同理，调用 `Attach` 将 $P_2$ 的当前项追加到结果末尾，并将 `t2` 后移一步。

2. **剩余节点收尾循环**：
   当主循环因其中一个多项式遍历完毕而退出时，另一个多项式中可能还残留若干指数更小的项。此时分别用两个简单的 `while` 循环，将尚未处理完的链表剩余项依次 `Attach` 到结果链表末尾。

3. **释放哑节点并返回**：
   相加完毕后，跳过哑节点并将哑节点内存 `free`，返回结果多项式首指针。

#### 多项式相乘的两种实现路径

两个多项式相乘，数学要求是将第一个多项式的每一项与第二个多项式的每一项两两相乘，并将乘积结果累加合并同类项。在算法设计上，存在两种截然不同的架构路线：

- **路线一：将乘法转化为一系列加法**
  设 $P_1 = a_1 + a_2 + \dots + a_m$。我们可以将乘法分解为：
  $$P_1 \times P_2 = (a_1 \times P_2) + (a_2 \times P_2) + \dots + (a_m \times P_2)$$
  单项 $a_i$ 乘以多项式 $P_2$ 的逻辑极为简单：只需遍历 $P_2$，对每一项做“系数相乘、指数相加”，即可得到一个局部的新多项式。随后，我们反复调用已经写好的 `Add` 函数，把这些局部多项式累加到最终结果中。
  这种方法极大地复用了加法代码，但在每一次调用 `Add` 时都会产生大量临时节点的动态申请与释放，带来不必要的内存开销。

- **路线二：逐项插入法（双重循环直接维护有序链表）**
  无需中途构造临时的完整多项式，而是直接维护一个初始结果链表。外层循环遍历 $P_1$ 的每一项，内层循环遍历 $P_2$ 的每一项。两项相乘得到的新项 $(c, e)$，立即在当前结果链表中寻找合适应插的位置：
  - 若链表中已存在指数相同的项，直接就地累加系数；若系数相加后为零，顺手将该节点从链表中删除并释放；
  - 若链表中不存在该指数，则动态申请一个新节点，将其插入到保持指数递降的正确位置上。

在实际工程开发与笔试面试中，**逐项插入法**对指针操作和边界控制的考察极为深刻，是必须攻克的硬核实现。

#### 逐项插入相乘算法的深度推导

我们来逐步推导逐项插入法的完整实现细节。

##### 第一步：特殊边界判断
如果输入的 $P_1$ 或 $P_2$ 本身为空多项式（指针为 `NULL`），相乘结果必然为空，直接返回 `NULL`：

```c
if (!p1 || !p2) return NULL;
```

##### 第二步：构造初始结果多项式
为了让后续的新项有基准可供插入，我们首先用 $P_1$ 的第一项去乘 $P_2$ 的每一项。因为 $P_2$ 本身是严格指数递降的，单项乘进去之后，生成的初始结果自然也是严格指数递降的。我们借助临时哑节点和 `Attach` 快速将其构建出来：

```c
t1 = p1; t2 = p2;
P = (Polynomial)malloc(sizeof(struct PolyNode));
P->link = NULL;
rear = P;

while (t2) {
    Attach(t1->coef * t2->coef, t1->expon + t2->expon, &rear);
    t2 = t2->link;
}
t1 = t1->link;      /* t1 推进到第二项，准备进入后续的逐项插入 */
```

##### 第三步：双重循环与定位插入
接下来，$t_1$ 从第二项开始外层循环，$t_2$ 每次重新回到 $P_2$ 的表头进行内层循环。对于每一对相乘产生的新项：
- 新系数 $c = t_1\text{->coef} \times t_2\text{->coef}$；
- 新指数 $e = t_1\text{->expon} + t_2\text{->expon}$。

现在的问题转化为：**如何将一个已知项 $(c, e)$ 插入到一个已经严格指数递降的有序链表中？**

我们令临时指针 `rear` 重新指向结果链表的最前端（即哑节点 `P`）。我们要比较的是 `rear` 的**下一个节点**的指数：
只要 `rear->link` 存在，并且 `rear->link->expon > e`，就说明我们要找的位置还在更后面，`rear` 必须不断后移：

```c
while (rear->link && rear->link->expon > e)
    rear = rear->link;
```

当这个 `while` 循环停下来时，只可能面临两种局面：
1. `rear->link` 存在且其指数恰好等于 $e$：
   说明遭遇了同类项！此时绝不能插入新节点，而是直接在 `rear->link` 上进行系数合并：
   - 若合并后系数非零：`rear->link->coef += c;`
   - 若合并后系数恰好为零：说明该项抵消消失了。必须从链表中删除该节点并释放内存：
     ```c
     t = rear->link;
     rear->link = t->link;
     free(t);
     ```
2. `rear->link` 为 `NULL`，或者 `rear->link->expon < e`：
   说明链表中不存在指数为 $e$ 的项，且此时 `rear` 恰好是新项的前驱节点。我们动态申请一个新节点存放 $(c, e)$，将其精准插入到 `rear` 与 `rear->link` 之间：
   ```c
   t = (Polynomial)malloc(sizeof(struct PolyNode));
   t->coef = c;
   t->expon = e;
   t->link = rear->link;
   rear->link = t;
   rear = rear->link;  /* rear 顺势后移 */
   ```

##### 第四步：释放哑节点并返回
遍历结束后，释放最初的哑节点 `P`，返回真正的有效链表头。

将上述逻辑整合，完整的乘法函数代码如下：

```c
Polynomial Mult(Polynomial p1, Polynomial p2)
{
    Polynomial P, rear, t1, t2, t;
    int c, e;

    if (!p1 || !p2) return NULL;

    t1 = p1; 
    t2 = p2;
    P = (Polynomial)malloc(sizeof(struct PolyNode));
    P->link = NULL;
    rear = P;

    /* 用 p1 的第一项乘以 p2 的所有项，构造初始有序结果链表 */
    while (t2) {
        Attach(t1->coef * t2->coef, t1->expon + t2->expon, &rear);
        t2 = t2->link;
    }
    t1 = t1->link;

    /* 两重循环：逐项相乘并就地插入 */
    while (t1) {
        t2 = p2;
        rear = P;
        while (t2) {
            c = t1->coef * t2->coef;
            e = t1->expon + t2->expon;

            /* 寻找插入位置的前驱节点 */
            while (rear->link && rear->link->expon > e)
                rear = rear->link;

            if (rear->link && rear->link->expon == e) {
                /* 指数相同：合并同类项 */
                if (rear->link->coef + c) {
                    rear->link->coef += c;
                } else {
                    t = rear->link;
                    rear->link = t->link;
                    free(t);
                }
            } else {
                /* 指数不同：在 rear 后面插入新节点 */
                t = (Polynomial)malloc(sizeof(struct PolyNode));
                t->coef = c;
                t->expon = e;
                t->link = rear->link;
                rear->link = t;
                rear = rear->link;
            }
            t2 = t2->link;
        }
        t1 = t1->link;
    }

    /* 释放哑节点并返回 */
    t = P;
    P = P->link;
    free(t);

    return P;
}
```

#### 满足输出边界规范的格式化输出

多项式的输出看似只是遍历链表打印 `printf("%d %d", p->coef, p->expon)`，实则暗藏评测系统中最严苛的格式要求：
- 每一对系数和指数之间有一个空格；
- 各项之间由一个空格分隔；
- **最后一项的末尾绝对不能有多余的空格**；
- 若多项式本身为空（例如零多项式），规范输出为 `0 0\n`。

初学者往往试图在循环内部判断“当前节点是不是最后一个节点”（即检查 `p->link == NULL`），若是则不打空格。这种做法不仅加重了每次循环的判断成本，而且逻辑拖沓。

我们可以运用一个绝妙的**逆向思维**：
> 不要纠结于“最后一项后面不输出空格”，而是将规则理解为——**第一项的前面不输出空格，除第一项之外的后续所有项，在输出自身之前先输出一个前导空格**！

借助一个初值为 0 的标志变量 `flag`，我们可以用极简的代码完美达成这一目标：

```c
void PrintPoly(Polynomial P)
{
    int flag = 0;

    if (!P) {
        printf("0 0\n");
        return;
    }

    while (P) {
        if (!flag)
            flag = 1;       /* 第一项：不打印前导空格，仅翻转标志位 */
        else
            printf(" ");    /* 后续项：在数据输出前补打一个分隔空格 */

        printf("%d %d", P->coef, P->expon);
        P = P->link;
    }
    printf("\n");
}
```

这种写法彻底消除了对链表尾部的冗余探测，是处理各类带分隔符输出题目的标准工业写法。

### 从静态查找走向层次结构

在完成多项式的线性链表操作后，我们必须把视野进一步放大。线性表（数组、链表）擅长处理具有严格先后前驱关系的平铺数据。然而，随着管理规模的爆炸式增长，纯粹的线性结构开始遭遇性能天花板。

#### 现实世界中的层次关系与组织哲学

仔细观察人类社会与物理世界中的信息，事物与事物之间普遍存在的并非简单的单向排队关系，而是天然的**层次关系（Hierarchical Relationship）**：

- **家谱树（Family Tree）**：从祖先出发，逐代向下衍生出各个支系与子孙；
- **行政管理架构**：国家下设省、自治区、直辖市；省下设地级市；地级市下辖县级市与区县；区县再下辖街道与乡镇。没有任何一个现代化大国会采用扁平的一级管理结构来治理数亿人口；
- **计算机操作系统的文件系统**：在庞大的磁盘驱动器上，通常存储着成千上万甚至数以亿计的文件。操作系统的设计者绝不会把所有文件平铺在一个根目录下，而是以盘符（如 `C:`、`D:`）为根，建立分层级的子目录，各级子目录下再嵌套目录与文件。

人类社会与工程系统之所以不约而同地选择层次结构，核心原因在于：**层次化管理能够带来无与伦比的管理效率**。

在数据管理领域，最核心、最频繁的三个基础操作是：
1. **查找（Search）**：给定某个特征，快速定位记录；
2. **插入（Insert）**：在集合中新增一条记录；
3. **删除（Delete）**：从集合中移除一条失效记录。

为了深刻理解层次结构对操作效率的质变提升，我们首先必须彻底剖析最基础的操作——**查找**。

#### 查找问题：静态查找与动态查找的鸿沟

> **定义**：**查找（Searching）** 是指给定某个关键字（Key），在指定的记录集合中找出其关键字等于该给定值的数据元素（若存在）。

根据数据集合在操作过程中的状态变化，查找问题被泾渭分明地划分为两大家族：

| 查找类型 | 集合状态特征 | 允许的操作集合 | 典型应用场景 |
| :--- | :--- | :--- | :--- |
| **静态查找（Static Search）** | 集合固定不变，既不增加新元素，也不删除旧元素 | 仅执行查找操作 | 查阅纸质英文字典、查阅物理常数表、查询系统内置静态路由表 |
| **动态查找（Dynamic Search）** | 集合状态时刻在发生动态改变 | 查找、插入、删除交替穿插发生 | 数据库表管理、电商平台商品库、操作系统进程控制块管理 |

查英文字典是静态查找的典型代表：整本字典印制出厂后，数万个单词集合就是静止的，我们反复在其中翻查单词释义，并不会往纸张里写新词，也不会撕掉旧词。而在动态查找中，集合犹如一个活水池，系统在频繁查询的同时必须高效支撑增删。显而易见，动态查找的技术挑战远大于静态查找。

#### 顺序查找与哨兵技巧

我们先来看静态查找的最朴素形态。假设集合中的元素存放在连续的数组空间中，查找某个元素最直观的办法就是从头到尾（或从尾到头）挨个核对，这就是**顺序查找（Sequential Search）**。

在传统实现中，每一轮循环都必须同时检查两个条件：
1. 当前下标是否已经越界（是否跑到了边界外）；
2. 当前元素的值是否与待查关键字相等。

这意味着每一次比较都要付出两次判断的代价。为了在极度高频的底层循环中抠出极致性能，先贤们发明了著名的**哨兵（Sentinel）**技巧。

```c
typedef struct {
    int *Element;       /* 存放数据的数组指针 */
    int Length;         /* 元素总个数 */
} *StaticTable;

int SequentialSearch(StaticTable Tbl, int K)
{
    int i;

    /* 将下标 0 作为哨兵，存放待查关键字 K */
    Tbl->Element[0] = K;

    /* 从数组末尾向前遍历，注意循环体完全为空 */
    for (i = Tbl->Length; Tbl->Element[i] != K; i--)
        ;

    return i;           /* 返回 0 说明未找到；返回 >0 说明命中对应下标 */
}
```

这段代码的设计极为精巧：
我们将实际数据从数组下标 `1` 开始存放，而将下标 `0` 刻意空出来作为“哨兵”。查找开始前，直接把待查关键字 $K$ 写入 `Element[0]`。随后，循环从数组最末端倒序向前扫描：
- 若在数组的有效区间（$1 \sim n$）内找到了与 $K$ 相等的项，循环因 `Element[i] == K` 成立而立即退出，此时 $i \ge 1$，成功命中；
- 若有效区间内没有任何元素等于 $K$，循环也不会越界崩溃，因为当它一路减到 $i = 0$ 时，必然会与事先埋伏在那里的哨兵相遇，从而必定退出！

```text
数组存储结构:
下标:    [ 0 ]   [ 1 ]   [ 2 ]   ...   [ n-1 ]   [ n ]
数据:    [ 哨兵K ] [ a1 ]  [ a2 ]  ...   [ an-1 ]  [ an ]
           ^                                       |
           |                  <---- 从后往前扫描 ---|
    若无匹配项，最终停在此处
```

读图说明：上图展示了顺序查找的哨兵布局。0 号单元埋下待查值 $K$，循环无需在每一次迭代中判断下标是否到达左边界，当且仅当命中目标或撞上哨兵时自然刹车。

哨兵机制直接消除了每次循环中对下标越界的条件分支判断，让机器指令精简到极致。然而，这依然无法挽救顺序查找在时间复杂度上的疲软：
- 运气最好时，第一下就查中（比较 1 次）；
- 运气最差时，查到最后一个甚至不存在（比较 $n+1$ 次）；
- 平均比较次数为 $\frac{n+1}{2} \approx \frac{n}{2}$ 次，时间复杂度牢牢锁定在 $O(n)$。

如果集合中有 100 万个数据，平均每次查找要进行 50 万次内存比较；若查找操作被调用 1000 次，累计比较次数将达到惊人的 5 亿次！面对海量数据，线性顺序查找显然不堪重负。

### 二分查找与判定树的逻辑跃迁

#### 折半排障：从电线杆维修谈起

有没有可能把查找效率提高几个数量级？有，这就是**二分查找（Binary Search）**。

在深入公式之前，我们先来看一个生动的现实生活案例：
在早期的长途有线通信时代，两地之间铺设架空电话线，沿途在公路旁每隔 50 米立一根电线杆，将线路架在杆顶。假设从杭州到上海距离为 150 公里，沿途竖立着数以千计的电线杆。某天两地电话线突然中断，说明中间某处线缆断裂了，维修工人必须找出发生故障的具体区间。

如果采用“顺序查找”策略：
维修工爬上杭州出发的第一根电线杆，接入仪器往上海拨号，发现不通；下来跑到第二根杆爬上去再测，还是不通；再爬第三根、第四根……假定沿途有 100 万根电线杆，维修工平均要爬 50 万次杆才能锁定故障点！这种做法在现实中荒谬至极。

真正聪明的排障策略是**二分折半**：
维修工直接开车直奔杭州与上海的正中间位置，爬上中点的电线杆：
1. 往杭州方向打，通了；
2. 往上海方向打，不通。

就凭这一次测试，他就以绝对的确定性断言：断点必定位于该中点到上海之间的后半段！杭州到中点的数十万根电线杆在一瞬间被彻底排除，查找范围瞬间**缩减了一半**。

```text
全局区间 (150 公里):
杭州 [===================== 中点 =====================] 上海
                             |
                   测试: 杭州通，上海不通！
                             |
缩小范围至后半段:
                      中点 [========== 新中点 ==========] 上海
```

读图说明：上图直观展示了折半排障的核心威力，通过在中点进行单次双向连通性测试，故障排查范围立即被硬性斩掉一半。

接着，维修工把车开到后半段的正中间，重复这一策略。每测一次，排查区间就削掉一半。对于 100 万根电线杆的庞大阵列：
- 顺序查找：平均爬杆 **500,000 次**；
- 二分查找：$\log_2(1,000,000) \approx 20$ 次！

从 50 万次降到 20 次，这就是二分查找带来的震撼效率。

#### 二分查找的前提条件与算法实现

如此高效的二分查找并非免费的午餐，它对底层存储施加了两个苛刻的先决条件：

1. **必须采用顺序存储结构（数组）**：必须支持 $O(1)$ 常数时间的随机下标访问。链表由于无法直接定位中点节点，即便有序也无法直接开展二分查找；
2. **数组元素必须按关键字严格有序存放**：例如从小到大递增排列。没有预先的有序性，就无法根据中点大小比较判定目标必定落在左半段还是右半段。

设数组存放在 `Element[1]` 到 `Element[Length]` 之中，升序排列。我们用左右两个游标指针 `left` 和 `right` 界定当前的查找搜索空间，初始时 `left = 1`，`right = Length`。

完整的算法实现如下：

```c
int BinarySearch(StaticTable Tbl, int K)
{
    int left, right, mid;

    left = 1;                   /* 初始左边界 */
    right = Tbl->Length;        /* 初始右边界 */

    while (left <= right) {
        mid = (left + right) / 2;   /* 取中点下标 */

        if (K < Tbl->Element[mid]) {
            right = mid - 1;        /* 目标更小，调整右边界至前半段 */
        } else if (K > Tbl->Element[mid]) {
            left = mid + 1;         /* 目标更大，调整左边界至后半段 */
        } else {
            return mid;             /* 命中目标，返回对应下标 */
        }
    }

    return 0;                   /* 循环退出说明区间倒错，查找失败 */
}
```

> **易错点**：注意 `while` 的循环终止条件是 `left <= right`。当待查元素不存在时，区间会持续缩窄，直至最后 `left == right`。若在该点依然不匹配，`left` 或 `right` 将会越过对方，出现 `left > right` 的**边界错位**现象，此时方可完全确信该元素在整个集合中不存在。

#### 判定树与平均查找长度推导

二分查找每次都将搜索空间除以 2，其最坏时间复杂度为 $O(\log_2 n)$。然而，为什么事先将数据有序化之后，会产生如此高超的查找威力？

为了洞察其内在本质，我们可以将二分查找的所有比较路径抽象为一棵**判定树（Decision Tree）**。

假设数组中有 11 个元素，下标从 1 到 11。无论数组中存放的数值具体是什么，只要它们是有序递增的，二分查找的比较顺序就完全是确定死板的：
- 第一次比较：必选中点 `(1 + 11) / 2 = 6` 号元素；
- 若目标小于 6 号元素，下一次必比较前半段中点 `(1 + 5) / 2 = 3` 号元素；若大于 6 号元素，下一次必比较后半段中点 `(7 + 11) / 2 = 9` 号元素；
- 依次类推，所有可能的查找轨迹，凝固成如下结构：

```text
                     [ 6 ]                   <--- 第 1 层 (比较 1 次)
                    /     \
              [ 3 ]         [ 9 ]             <--- 第 2 层 (比较 2 次)
             /     \       /     \
          [ 1 ]   [ 4 ]  [ 7 ]   [ 10 ]       <--- 第 3 层 (比较 3 次)
             \       \      \       \
            [ 2 ]   [ 5 ]  [ 8 ]   [ 11 ]     <--- 第 4 层 (比较 4 次)
```

读图说明：上图是以 11 个元素为例构造的二分查找判定树。树中的每个节点标注的是数组下标，节点所在的层数精确等于查找到该下标元素所需的比较次数。

观察这棵判定树，我们可以得到两条至关重要的数学定理：

1. **查找特定节点所需的比较次数，恰好等于该节点在判定树中所处的层次**；
2. **全树的最大深度（总层数），决定了二分查找在最坏情况下的比较次数**。
   对于包含 $n$ 个元素的有序数组，判定树的高度为：
   $$h = \lfloor \log_2 n \rfloor + 1$$
   对于 $n = 11$，$\lfloor \log_2 11 \rfloor + 1 = 3 + 1 = 4$ 层，最坏只需比较 4 次。

进一步，我们来精确计算这 11 个元素的**平均成功查找次数（Average Search Length, ASL）**。
假设查找每个元素的概率均等（均为 $\frac{1}{11}$），从判定树各层节点分布可知：
- 第 1 层有 1 个节点（比较 1 次）：节点 6；
- 第 2 层有 2 个节点（比较 2 次）：节点 3, 9；
- 第 3 层有 4 个节点（比较 3 次）：节点 1, 4, 7, 10；
- 第 4 层有 4 个节点（比较 4 次）：节点 2, 5, 8, 11。

将各层节点数乘以对应层数求和，除以总元素数：
$$ASL = \frac{1 \times 1 + 2 \times 2 + 4 \times 3 + 4 \times 4}{11} = \frac{1 + 4 + 12 + 16}{11} = \frac{33}{11} = 3$$
这意味着在这 11 个数中查找任意一个数，平均仅需比较 3 次！

#### 二分查找的局限与二叉搜索树的萌芽

此时，一个重大的思维跃迁摆在我们面前：
二分查找通过在数组上强制施加顺序，将线性的比较过程硬生生映射成了一棵高效的**判定树**。然而，这一设计存在一个致命的软肋——**它只适合静态查找**。

一旦进入动态查找场景（需要频繁插入新项、删除旧项）：
数组这种连续顺序存储结构，若要在中间插入一个新元素，必须将后续所有元素整体向后挪动一位，删除时同样要整体向前平移，单次插入或删除的时间复杂度高达 $O(n)$！为了享受 $O(\log n)$ 的查找效率，我们却在增删维护上付出了巨大的 $O(n)$ 代价。

这时，一个充满创造力的设想自然浮现：
> 我们为什么非要把数据死板地硬塞进连续数组里，再去虚拟出一棵判定树呢？
> **我们能不能直接用指针把数据组织成一棵货真价实的“树”？**

如果直接把数据存储为这种层次结构的节点（即后续即将重点研讨的**二叉搜索树 / 查找树**）：
- 在查找时，顺着指针层层向下，能够完全保留二分查找 $O(\log n)$ 的极致效率；
- 在插入和删除时，得益于链式结构的指针灵活性，修改指针只需局部操作，插入与删除同样能在 $O(\log n)$ 内优雅完成！

正是为了彻底征服动态查找这一工程终极难题，计算机科学家们正式把“树”推向了数据结构的核心舞台。

### 树的定义、性质与术语体系

#### 树的递归定义与非树判定

要系统驾驭树结构，必须首先建立严密的基础理论与术语坐标。

> **定义**：**树（Tree）** 是 $n$（$n \ge 0$）个节点的有限集合。
> - 当 $n = 0$ 时，称为**空树**；
> - 对于任意一棵**非空树**（$n > 0$），它具备以下性质：
>   1. 集合中有且仅有一个特定的称为**根（Root）**的节点；
>   2. 当 $n > 1$ 时，其余节点可被划分为 $m$（$m > 0$）个**互不相交**的有限集 $T_1, T_2, \dots, T_m$，其中每一个集合本身又是一棵树，称为根节点的**子树（Subtree）**。

请注意：树的定义本身就是**递归（Recursive）**的！树是由子树构成的，子树下面又有子树，这种自相似的嵌套性质，决定了后续绝大多数树算法（如遍历、求深度）都可以天然地用递归优雅表达。

```text
                   根节点 [ A ]
             /        |        \        \
          [ B ]     [ C ]     [ D ]    [ E ]    <--- 各互不相交的子树根
         /     \                |
       [ F ]  [ G ]           [ H ]
               |             /  |  \
             [ I ]         [ J ][ K ][ L ]
```

读图说明：上图展示了一棵以 A 为根的标准多叉树。除根节点 A 外，其余节点划分成以 B、C、D、E 为根的 4 个互不相交的子树集合。

为了加深理解，我们必须审视什么**不是**树：

```text
非树形态 1 (子树相交):          非树形态 2 (多父节点环路):
       [ A ]                           [ A ]
      /     \                         /     \
   [ B ]   [ C ]                   [ B ]   [ C ]
      \     /                         \     /
       [ D ]                           [ D ]
 (B、C 子树在 D 处相交)            (D 同时认 B、C 为父，形成回路)
```

读图说明：上图列出了两种典型的非树结构。左图中子集相交违背了子树互不相交的前提；右图中 D 节点同时拥有两条向上的连线，破坏了除根外每个节点只能有一个父节点的铁律。

#### 树的拓扑性质与最小连通性

通过对树结构的拓扑分析，我们可以提炼出三条硬核事实：

1. **子树之间绝对互不相交**；
2. **除了根节点没有父节点之外，树中的每一个节点有且仅有一个唯一的父节点**；
3. **节点总数与边数的关系**：
   在一棵包含 $n$ 个节点的树中，边的总数必定恰好等于 $n - 1$ 条。

> **推导**：每个节点（除了根节点）往上都有且仅有一条边连接到它的父节点。因此，树中所有连向父节点的边汇聚起来，数量正好等于所有非根节点的数量，即 $n - 1$ 条。5 个节点的树必有 4 条边，100 个节点的树必有 99 条边，绝无例外。

这揭示了树在图论层面的本质：**树是保证所有节点完全连通的最经济连接方式（最小连通图）**。在树中随机拔掉任意一条边，整棵树必定瞬间断裂为两个互不连通的碎片；而在任意两个节点之间添加一条边，树中就必定立刻产生回路。

#### 树的核心术语辨析

为了建立标准的技术交流语汇，必须全面厘清以下核心术语：

| 术语名称 | 英文对应 | 精确定义与内涵 |
| :--- | :--- | :--- |
| **节点的度** | Degree of Node | 该节点拥有的**子树数目**（即从该节点直接向下引出的分支边数） |
| **树的度** | Degree of Tree | 树中所有节点的度的**最大值**（即全树分叉最多的节点的度） |
| **叶节点** | Leaf Node | **度为 0** 的节点，也称终端节点（其下方不再挂接任何子树） |
| **分支节点** | Branch Node | 度大于 0 的节点，也称非终端节点 |
| **父节点** | Parent | 某节点的直接上层节点（对牢在上面的那个节点） |
| **子节点** | Child | 某节点直接下引的子树的根节点 |
| **兄弟节点** | Sibling | 拥有**同一个父节点**的所有同层节点 |
| **路径** | Path | 节点序列 $n_1, n_2, \dots, n_k$，满足 $n_i$ 是 $n_{i+1}$ 的父节点 |
| **路径长度** | Path Length | 路径上经过的**边的条数**（即节点数减 1） |
| **祖先节点** | Ancestor | 从根节点到该节点路径上的所有其他节点（父、祖父等） |
| **子孙节点** | Descendant | 以某节点为根的子树中的所有下层节点（子、孙等） |
| **节点的层次** | Level | 规定**根节点为第 1 层**，其子节点为第 2 层，依此类推 |
| **树的高度/深度** | Height / Depth | 树中所有节点层次的**最大值** |

我们结合一个具体的图例进行对照辨析：

```text
第 1 层:                     [ A ]
                        /      |      \
第 2 层:             [ B ]   [ C ]   [ D ]
                    /     \            |
第 3 层:          [ E ]   [ F ]      [ G ]
                          /
第 4 层:                [ H ]
```

读图说明：上图用于术语对照。根节点为 A，处于第 1 层；H 处于第 4 层，决定了全树高度为 4。

针对上图进行术语实战核对：
- **度**：节点 A 拥有 3 个子树，度为 3；节点 B 度为 2；节点 F 度为 1；节点 E、C、H、G 度均为 0。全树最大度为 3，因此**树的度为 3**；
- **叶节点**：E、H、C、G 均为叶节点（度全为 0）；
- **亲缘关系**：B、C、D 互为兄弟节点（父节点均为 A）；E、F 互为兄弟节点；
- **路径与长度**：从根 A 到 H 的节点序列为 $A \to B \to F \to H$，路径上共有 3 条边，故**路径长度为 3**；
- **祖先与子孙**：节点 H 的祖先包括 F、B、A；而反过来，B 的子孙包括 E、F、H；
- **层次与高度**：A 在第 1 层，B、C、D 在第 2 层，E、F、G 在第 3 层，H 在第 4 层。全树所有节点的最大层次为 4，因此**树的高度为 4**。

至此，我们不仅在代码级完成了多项式链表系统的高质量工程落地，更在理论认知上打通了从顺序存储、静态顺序查找、二分查找判定树，直至动态树形层次结构的演进全脉络。这为我们后续深入二叉树的存储表示、四种遍历算法以及二叉搜索树的工业级实现，奠定了坚如磐石的技术底座。
