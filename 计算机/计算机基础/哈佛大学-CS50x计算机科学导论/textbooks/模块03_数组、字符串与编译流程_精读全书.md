## 先学会自己找 bug，再掀开编译器的引擎盖
> 对应块：BLK07 | 覆盖分集：P03上 | 块标题（分集名）：《数组入门与调试器逐行追踪》

开场是一段朗读：

> 那是四月里一个晴朗而寒冷的日子，时钟敲响了十三下。Winston Smith 的下巴紧贴着胸口，试图躲避那刺骨的寒风。他快步穿过胜利大厦的玻璃门，但动作还是不够快，一股夹着沙砾的尘土随着他一起卷了进来。

### 一句朗读，三种阅读水平

我们要解决的第一个现实问题，是**阅读水平评估**。

你大概从小就被按年龄划分过阅读水平：一年级水平、五年级水平、十年级水平，取决于你对读到的文字理解到什么程度。刚才那段朗读的三个版本，正好对应三个层级。

第一位是 Leah，一年级新生。她读的是：

> 一条鱼，两条鱼，红色的鱼，蓝色的鱼。

台下很快就给出了判断——幼儿园水平。理由也一致：她用的句子非常简短，结构非常简单。确实如此，靠本周习题集里会探讨的一种科学评估方法，我们可以说 Leah 处在学前阶段。

第二位是 Maria，她在考虑读应用数学。她读的是：

> 恭喜你。今天是你大显身手的日子。你将踏上精彩的旅程。你已启程，前路广阔。

台下有人猜二年级或三年级。为什么？因为她开始用**押韵**了，而且引用的内容本身更有实质，不再是几个词凑成的短句。按前面那个衡量标准——它本身就是一个数学函数，用来分析刚才这段内容——她的水平相当于三年级。

第三位是 Omar，大一新生，正在考虑读计算机科学。他读的是开头那段 Winston Smith。

"这进展得有点快啊。"——我们一下子就被甩开了。八年级。这是什么让你这么认为？"句子结构更复杂，词汇也更高级。"

而按照同一把尺子，屏幕上这段完整的段落，因为语法结构更丰富，复杂度更高，阅读难度会被判定为**十年级水平**。同一个人，同一档能力，起点不同，你给出的估计就差了两年。这就是我们今天要面对的问题：怎么用一套方法，客观地判断一段文字的难度。

但要判断，就得先把文字拿到手、存进内存、拆开来分析。所以今天要做的第一件事是：

> **我们需要一种能在内存里表示文本、并把它按阅读等级拆开的数据结构——字符串。上周我们碰过字符串，但只是整体打印或显示在屏幕上；今天要把它们真正拆开。**

同时，今天还有第二个目标，也是更重要的那个：把计算机的"引擎盖"掀开，看看字符串这样的数据结构究竟是怎么在底层工作的。

> **结论**：本周我们要同时啃两头——一头是现实世界的问题（阅读水平、后面的密码学），一头是计算机的内部机制。这不是两门课，是同一门课的两个方向。

至于密码学，先预告一下它长什么样：屏幕上就摆着一条加密过的消息，末尾还带着一个提示。今天先记住它的存在——**到本周课程结束时，你会发现这条加密消息其实是可以被解开的**。这就是 CS50 的核心问题：为什么能解开，靠什么能解开。接下来的几周，我们会把这件事从头到尾走一遍。

### bug 这个词，是从一只飞蛾开始的

在进入今天的主体之前，先说一个词：bug。

你在 Scratch 里肯定撞过，在 C 里更是躲不掉——如果你写的第一个 C 程序连编译都过不去，完全不用沮丧，那太正常了。程序里的错误和疏漏本来就极其普遍。

CS50 一直给你们准备了 CS50.AI 里的虚拟橡皮鸭，也集成在 cs50.dev 的 VS Code 里，随时可以问。但今天要给你的，是一批**终身受用**的工具：没有橡皮鸭、没有助教、身边一个人也没有的时候，你自己怎么调试。

"bug"这个词最有名的推广者，是格蕾丝·霍珀博士。她是美国海军少将，也是早期大型计算机"哈佛马克一号"的原始程序员之一。如果你穿过查尔斯河走到科学与工程综合楼，还能在大厅里看到这台机器的一部分展品；后来它被哈佛马克二号取代，哈佛马克二号又继续往前走。

她和她的小组做完一轮大规模计算后，把发现记在了日志本上，这张照片非常有名。放大看会发现：机器出了故障，电路里真的卡进了一只虫子——一只飞蛾。日志本上写的是："这是首次发现实际存在的 bug 案例。"

从那以后，我们排查和解决代码问题时，就越来越频繁地使用"bug"和"调试"这两个词。

好，开始干活。

### 亲手把程序写坏：编译器的第一道防线

我们到 VS Code 里**故意**制造一些错误——很可能就跟你无意中犯过的那些一模一样。目标不是找出这些 bug，而是顺手把工具教会你。

新建一个文件 `buggy.c`。先写熟悉的部分：

```c
int main(void)
{
    printf("hello, world")
}
```

有几处不对，你自己多半已经看出来了：**没有包含标准输入输出头文件**。`.h` 文件很重要，它告诉编译器"我打算用这里的函数"——比如 `printf`，而我显然正在用它。

不过在改之前，先去终端里跑一下 `make buggy`，看看报错的阵仗。

屏幕顶端一行是 `buggy.c:3`，也就是第 3 行。错误信息说：调用了未声明的库函数 `printf`。信息到这里就开始有点绕了，但有一点很清楚——它把注意力集中在了 print 上。

所以，从这周开始（如果上周还没形成这个直觉的话），你的第一反应应该是："哦，好吧，我犯傻了。"我忘了包含声明 `printf` 的头文件。这不是什么大问题，练多了你就会本能地知道答案。

把这个补上：

```c
#include <stdio.h>

int main(void)
{
    printf("hello, world")
}
```

还有一个问题：第 5 行末尾少了个分号。

```c
    printf("hello, world");
}
```

这个错误比较细微，严格说不算程序错误，更算美观上的细节。再看还有什么——我忘了加反斜杠和换行符 `
`，这样光标才能移到下一行，提示符才会单独出现在新的一行。这同样主要是美观考量，但确实是对的。

```c
#include <stdio.h>

int main(void)
{
    printf("hello, world\n");
}
```

现在再 `make buggy`，编译成功。但如果我们把刚才的修复逐个撤销，回到最初的版本呢？

屏幕会刷出一大串看起来很吓人的消息，滚回顶部你会看到**第一条错误**。这就是重点：**编译过程中，只要有一条错误，后面全部代码都不会被编译**。所以我修完分号之前，编译器根本没看到我加的 `
`；同理，`#include <stdio.h>` 也要先解决。

> **易错点**：错误信息不是一份"待办清单"的全部，而是"编译器放弃之前最后看到的东西"。按报错顺序从上往下修，一次只改一个。

清屏，重跑。第一个错误没了，冒出第二个：`buggy.c:5: 表达式后缺少分号`。信息非常明确，去修它。

修完之后编译能过、程序能跑，但还有一个缺陷：运行 `./buggy` 时，提示符出现在了错误的位置上，因为我本来是想让光标移到下一行的。

这就引出了本讲第一个关键区分：

> **定义**：**语法错误**（programming error）直接让程序无法编译；**逻辑错误**不会阻止编译。前者是程序运行的"致命障碍"，后者只是逻辑层面不对。
> **易错点**：程序能编译通过 **不等于** 程序是对的。编译成功只说明你写的符号符合 C 的语法规则，一点也不说明它符合你的意图。

再改一次，让它更像上周的例子。上周我开始动态地获取用户姓名，写了 `name = get_string(...)` 这种代码——`get_string` 是我们介绍过的函数：

```c
#include <stdio.h>

int main(void)
{
    name = get_string("What's your name? ");
}
```

问号后面加个空格，光标就会向右挪一格。语句末尾那个分号我很清楚。`make buggy` 一下：

> `buggy.c:5: 错误：使用了未声明的标识符 'name'`

这个错误你可能还没遇到过。**我忘了吗？我到底错在哪？**——对，我忘了声明这个变量的类型。对有经验的人这几乎是肌肉记忆，但在 Python 这样的语言里确实不用显式声明类型；在 C、C++、Java 里，你必须明确告诉编译器要实例化一个变量，就是在内存里造一个变量时得指定它的类型。

这里我要的不是整数，所以不能写 `int`；我要的是文本类型——我们现在叫它 **string**。

```c
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
}
```

`make buggy` 一下：

> `buggy.c:5: 致命错误：使用了未声明的标识符 'string'`
> `did you mean 'stdin'?`

**我是不是想输入 `stdin`？**——这有点误导人了。编译器只是在它自己认识的所有词里找了个最像的给你，而 `stdin` 恰恰和 `string` 只差一个字母。我真正的错误是：忘了包含 **CS50 的头文件**。

`string` 这个类型、`get_string`、`get_int` 这些函数，全都是 CS50 库提供的东西。所以解法是往上翻，加上 `#include <cs50.h>`：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
}
```

> **易错点**：标准库和 CS50 库是两回事。`printf` 属于标准库，`string`、`get_string`、`get_int` 属于 CS50 库，少一个 `#include` 编译器就会报"未声明的标识符"。
> **注意**：我们习惯**按字母顺序**排列头文件。技术上不是强制的，这是代码风格问题，但按字母顺序扫一眼，你更容易看出某个功能到底包没包含进来。

而且要注意，编译器这里撒了个小谎：它明明报错说 `string` 不存在，可它随后又建议你是不是想写 `stdin`。我们同时包含了 `stdio.h` 和 `cs50.h` 之后，`cs50.h` 做了两件事——**声明了 `get_string` 让编译器知道它存在，并且真正定义了 `string` 这个类型**。

这里就得说一句善意的谎言：**字符串现在存在，纯粹是因为 CS50 库让它存在。** 我们就像从自行车上拆下辅助轮，目的就是帮你保持平衡，别太早撞上复杂的东西。再过一两周我们就会揭开这层面纱、拆掉辅助轮，给你看看背后真正的机制。到那时字符串依然存在，只是会换一个名字来称呼。

> **提示**：但不要因此以为"字符串"是 CS50 造出来的概念。现实世界里每一位软件开发者都在用"string"这个词，这是个真实存在的概念。**只不过 C 语言本身没有 `string` 这个词**——我们是自己主动定义它的。

再清屏，`make buggy`，编译通过。`./buggy` 一下，输入名字——

```
hello
```

没了。只有 "hello"。

**这不是语法错误**——我没把代码本身搞砸，它编译通过了，语法上一点问题都没有。但从逻辑和设计意图看，这显然不是我要的结果。我本来想输出的是 `hello, David`。

如果当时你跑的是 CS50 自带的 `check50`，它会自动评估并告诉你这个输出是错的。但**编译器完全无法理解你的意图**——它只认识 C 的规则，只关心语法。

> **结论**：逻辑错误没有任何工具能"自动判定"对错，因为没有 ground truth 交给工具。这一步只能靠你自己的脑子：好吧，这显然不是我想要的。

修法就在第 7 行——用**格式化代码**：一个百分号，再加一个参数。逗号，然后填入变量名（这里确实该用 `name`，不过你也可以随便叫别的名字）：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
    printf("hello, %s\n", name);
}
```

`make buggy`，再跑一次，正常了。

这一串错误虽然大部分是我故意犯的，但它完整地展示了两种错误的分工：**语法错误会直接让编译器停下，你不修就连编译都做不到；即使语法全对，代码里仍可能藏着缺陷**，而这类缺陷往往要等你真的输入了东西、亲眼看见程序"跑起来"的样子，才会暴露。那时候调试就不再是"读懂报错信息"那么简单了——屏幕上根本没有报错，只有一句不完整的 "hello"。

### 让 printf 兼职当调试器

解法是：当你怀疑逻辑有问题、想把程序内部摊开看清楚的时候，`printf` 就是你的得力助手。

到目前为止我们用 `printf` 都是在屏幕上显示 "hello, Kelly" 这类最终产物。但你完全可以临时插几行 `printf`，把程序内部的中间结果打出来，这对你理解代码的执行过程帮助极大。搞清楚、修好之后，把这些临时代码删掉，重新编译，继续干活。

> **提示**：`printf` 调试法不是"作弊"，它是标准手段。核心纪律只有一条：**调试语句只是临时的，修完必须删**。

回到 `buggy.c`，清空重写，换一类错误。这次程序足够简单，好让你把注意力全放在调试技巧本身，而不是这个 bug 有多难找。

我们要写一个 `for` 循环，打印出马里奥那种三层砖块的堆叠——假设马里奥要跳过一堆砖，我们只想打印三块：

```c
#include <stdio.h>

int main(void)
{
    for (int i = 0; i <= 3; i++)
    {
        printf("#\n");
    }
}
```

`make buggy`，`./buggy`——**没打出三块砖，打了四块。** 1、2、3、4。

你看出来了，问题是 `i <= 3`：循环条件应该是"小于 3"，而不是"小于等于 3"。

但我不想只是"看出来"，我想演示**诊断的方法**。调试输出语句是其中最实用的一个：为什么是 4 块而不是 3 块？这显然跟循环有关。那就在打印每一块砖之前，把变量 `i` 的值也打出来：

```c
    for (int i = 0; i <= 3; i++)
    {
        printf("%i ", i);
        printf("#\n");
    }
```

`make buggy` 之后再跑：

```
0 #
1 #
2 #
3 #
```

结果一目了然：循环本身完全正常，是**条件让我多走了一步**。

修法：写成 `i < 3`；或者如果你想像正常人一样从 1 开始数，就把初始值设成 `i = 1`，然后 2、再到 3。但正如上周说过的，最规范、最常见的写法还是**从 0 开始计数，递增到 2，永远不会达到你心里想的那个总数**。

> **易错点**：这是初学者 bug 的头号来源。`i < 3` 打三次，`i <= 3` 打四次。就这一个字符的差别。

### 抽象出 print_column 之后

把例子再抽象一层。删掉 `for` 循环，改成向用户询问高度：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int h = get_int("Height: ");
    print_column(h);
}
```

> **提示**：`get_int` 不是 C 标准库的函数，同样来自 CS50 库，所以这里**又**需要 `#include <cs50.h>`。上一节的教训立刻用上了。

现在假设存在一个叫 `print_column` 的函数，接收一个数字 `h` 作为输入，表示你想打印多少块砖。这个函数还不存在——但 `get_int` 是存在的，所以这次我不会再犯同样的错误。

这个函数我自己写：

```c
void print_column(int height)
{
    for (int i = 0; i <= height; i++)
    {
        printf("#\n");
    }
}
```

我又一次故意犯了同样的错：故意保留 `i <= height`，然后编译。`make buggy` 顺利通过，`./buggy`，输入 3——**还是 4 块砖**。

先说一句代码风格上的事：在文件顶部、`main` 之外放东西通常不是好做法。但如果我现在把辅助函数 `print_column` 挪走（我管它叫辅助函数，就是因为它是为了帮 `main` 解决另一个问题才被造出来的），代码就编不过了：

> `buggy.c:7: 错误：使用未声明的标识符 'print_column'`

编译器处理到第 7 行就中止了，因为直到第 10 行我才告诉编译器 `print_column` 是什么，而它读到第 7 行的时候还不知道。

> **提示**：这里是我全讲唯一一次说"复制粘贴"合理的地方——选中函数第一行，复制，粘到 `main` 上方，**末尾加分号**，这就叫**函数原型（prototype）**。它只声明三件事：函数名、输入参数（如果有）、返回值类型（如果有）。这些输入输出参数我们后面会专门细讲。

```c
#include <cs50.h>
#include <stdio.h>

void print_column(int height);

int main(void)
{
    int h = get_int("Height: ");
    print_column(h);
}

void print_column(int height)
{
    for (int i = 0; i <= height; i++)
    {
        printf("#\n");
    }
}
```

> **定义**：**函数原型**是函数在实现之前的"预告片"。它存在的唯一目的是解决顺序问题——函数可以写在你使用它的位置之后，但编译器读到使用处时必须已经知道它长什么样。这正是头文件在干的事。

`make buggy` 还能编译，输入 3，还是那个老错误。

但现在问题变了：**代码更复杂了。** 我本意是把打印一列这件事抽象成独立函数，让结构更清晰，结果调试时要管的代码量反而变多了。我完全可以进到函数里加 `printf`，但到了一定程度纯靠 `printf` 就非常原始了——加调试语句、重新编译、运行、改 `printf`、再编译、再运行，屏幕上代码一多，很快就烦人。

那我能不能像助教在小班课或讨论课上那样，**逐行单步执行**我的代码？——可以。这就是另一个工具。

### debug50：让程序停下来等你

它叫 **`debug50`**，是一个 CS50 命令，会启动一个行业标准的调试器。调试器就是现实世界里真正在用的软件，能让你**放慢甚至暂停**程序的执行，逐行跟踪代码，从而调试代码。

> **注意**：我们之所以叫它 `debug50`，是因为在 VS Code 里直接启动调试器有点麻烦。我们只自动化了"启动"这一步，之后的所有操作**都与 CS50 无关**，是完全标准的软件工程实践。

在终端里输入 `debug50 buggy`——`buggy` 是**命令行参数**，告诉 `debug50` 我要调试哪个程序。

第一次跑会看到一条提示：

> 看起来你还没有设置任何断点。请点击某行代码左侧的行号来设置至少一个断点，然后重新运行 debug50。

> **定义**：**断点（breakpoint）**就是告诉调试器"在哪儿把程序叫停"的地方。没有断点，调试器根本不知道你想从哪一步开始看。

在 VS Code 里把鼠标悬停在行号左侧，会看到一个小红点，像个迷你停止标志。点一下，红点就钉在那儿，悬停提示写着"点击以添加断点"。

那就点 `main` 的第一行加个断点——`main` 是程序入口，是默认会被调用的函数。断在入口，立刻中断。

重新开终端、清屏、再跑 `debug50 buggy`。屏幕会快速刷过一大堆内容，然后自动清干净——调试器一旦启动就绪，就可以开始了。

#### 断在哪儿，看得见

此时屏幕上**没有任何输出**。为什么？因为代码已经暂停在 `main` 内部了，但暂停在函数的**第一行**——那一行本质上是函数名和大括号，没有任何实际作用。真正有意思的起点是下一行，第 8 行才是代码里真可能做有用事情的地方。

第 8 行被**黄色高亮**，光标停在这一行，意思就是：**程序已经在这一行中断了，但这一行还没被执行**。所以终端里当然还什么都没有——连 "Height:" 那个提示都还没打印。

#### 垃圾值：没存进去的东西也在那儿

屏幕左侧（平时放文件资源管理器或课程资料的地方）出现了一栏变量信息。调试器里你可以查看计算机内存中**任意变量的当前值**。

有点奇怪的是：**在第 8 行执行之前，`h` 好像已经有个默认值 32764。** 这个值是凭空出现的。

> **定义**：这叫**垃圾值（garbage value）**。它是变量所在内存位置里的残留内容——那块内存之前被存过别的东西。

计算机内部有大量内存，也就是 RAM。可以想见，我的电脑和正在用的任何云端服务器都已经运行了一段时间了；`h` 即将占用的那些位，很可能早就随机地处在开/关两种状态上，凑出了一个随机的位模式，恰好就是 32764。但**等这行代码一执行**，那个值就会被改成我真正想要的值——用户输入的那个数。

调试器界面顶部还有一排彩色图标。最左边那个像播放按钮，点它就继续跑、不再单步；**第二个是带圆点的弯箭头，叫"单步跳过"**——执行当前行然后往下走，一次一行。

点它。终端出现了 `Height: ` 提示，输入 3，回车。

执行现在停在**第 9 行**，局部变量 `h` 的值如预期是 3。到这里为止没什么启发性，主要是为了演示我可以在任何想停的地方停下。再点一次"单步跳过"，这一列就打印出来了，屏幕底部是**四个井号**。

可惜——**刚才那次我们并没有真正进入函数内部**，只是闪电般确认了一句"我输入了 3，内存里存的也是 3"。现在这还没什么特别有意思。

#### 单步进入：钻进函数里

这次我们把断点留在第 6 行，`debug50 buggy` 重跑，界面一开始有点乱，但第 8 行再次高亮。我直接单步跳过它获取 `h`，输入 3，但这次**不**单步跳过第 9 行让 `print_column` 整个跑掉——而是点**旁边那个"单步进入"按钮**。

程序跳进了 `print_column` 函数内部，暂停在第 14 行。左上角能看到变量 `i` 的默认值，**一个完全随机的垃圾值**。不过只要第 14 行执行一次，`i` 就会变成 0。

点"单步跳过"——这行没调用别的函数，不需要单步进入——左上角的 `i` 立刻变成 0，第 16 行高亮。再单步跳过，终端里出现了**第一个井号**。

再单步跳过、再单步跳过，**第二个井号**出现了，`i` 变成 1。

再单步跳过、再单步跳过，**第三个井号**，`i` 变成 2。

再单步跳过、再单步跳过——

> **这就是 bug 的气味：出现了第 4 个井号，但 `i` 的值是 3。**

3 确实 `<= 3`，所以屏幕上出现了第 4 个井号。归根结底，**你还是得用自己脑子去分析判断**。但调试器的价值在于：它允许你暂停程序、按自己的节奏一步步分析、钻进代码内部探查，从而更清楚地理解程序的状态。这比"编译运行后只凭表面现象猜根源"高效太多了。

现在我知道问题在哪了，直接让程序跑完，把 `<=` 改成 `<`。砖块变回三块。

#### 调试器里到底在显示什么

```text
┌──────────────────────────────────────────────────────────────┐
│  ▶   ⤳ 步进跳过   ⤵ 步进进入   ⤢ 继续   ⏹ 停止   ⟳ 重新启动 │  ← 调试控制条
├──────────────┬───────────────────────────────────────────────┤
│  变量面板     │  buggy.c                                      │
│              │  5  int main(void)                            │
│  h = 32764   │  6      print_column(h);                      │
│              │  7                                           │
│  i = 2       │  8 >    int h = get_int("Height: ");  ← 高亮   │
│  （垃圾值）  │  9      print_column(h);                       │
│              │ 16 >    printf("#\n");                ← 高亮   │
├──────────────┴───────────────────────────────────────────────┤
│  终端：$ ./buggy                                             │
│  Height: 3                                                   │
│  #  #  #  #                                                  │
├──────────────────────────────────────────────────────────────┤
│  调用栈：main (buggy.c)  ← 暂停在这一帧                       │
└──────────────────────────────────────────────────────────────┘
```

右侧那一栏就是**调用栈**。后面几周我们会专门讲它，但眼下你可以看到：**我们正暂停在 `buggy.c` 的 `main` 函数里**。等你单步进入 `print_column`，栈里就会多一层，表示当前正在执行的是哪个函数、调用的又是谁。

### for 循环的四个阶段

单步的过程里藏着一个容易被误解的地方，趁热打铁说清楚。

有人问：当 `i` 从 0 循环到 3 时，下一次到 4 时发生了什么？——问题出在 `for` 循环的**执行顺序**。第一次进入 `for` 循环时：

```text
        ┌──────────────┐
        ▼              │
  ① 初始化             │  只做一次：for (int i = 0;
  int i = 0            │         第一个分号之前)
        │              │
        ▼              │
  ② 条件判断  i <= 3 ? ├──── 否 ────► 退出循环
  （布尔表达式）         │
        │ 是            │
        ▼              │
  ③ 执行循环体内所有代码  │
   printf("#\n");       │
        │              │
        ▼              │
  ④ 更新  i++           │
        └──────────────┘
```

执行完 `i++` 之后，会**再次**检查条件；条件为真就再执行循环体，再更新，再检查，如此往复。

这也解释了前面看到的现象：第 4 次循环体执行时 `i` 是 3，`3 <= 3` 成立，井号就打出去了；然后 `i++` 变成 4，`4 <= 3` 不成立，循环结束——**一共四次**。

**能不能调换 `i++` 和 `height` 的位置？** 简短的回答是：不能，因为顺序是被语言定死的。

```text
for ( ① 初始化 ; ② 条件 ; ③ 更新 ) { 循环体 }
```

永远是①→②→③。第一次一定是初始化，第二次一定是条件判断，第三步总是更新。**这个顺序不可协商。**

> **提示**：顺便一提，`for` 的三个位置其实都可以写多条语句，用逗号隔开——多个初始化、多个布尔条件、多个更新都可以。我们现在先保持最简单的那种标准写法。

还有一个必须留意的点：**调试器只会高亮整行代码，它不会告诉你这一行内部执行到哪一步了。** 上面那四个阶段是 `for` 的定义带来的，不是调试器在提示你。你不能指望看着高亮就以为"哦它刚做完初始化"。

### 橡皮鸭，以及别把思考外包出去

工具箱里还有一样东西。你可以奇怪，为什么我身后站着一只 7 英尺高的鸭子，地上还摆着一堆小橡皮鸭。

根据第零周的内容，**橡皮鸭调试法确实是一种有效的方法**。这个方法被多年前的一本书推广开，核心理念是：当你被程序里的某个错误或漏洞卡住，或者对某个概念感到困惑时，经验表明，**只要把问题向一个对象倾诉出来——比如桌上那只橡皮鸭——往往就足以让你灵光一闪**。因为当你亲耳听到自己把困惑所在、逻辑漏洞说出口时，甚至不需要助教、人工智能或任何人来回答，问题往往就解决了。

所以，今天课程结束我们准备了**数百只鸭子**，一人带一只回家。在 CS50 或者别的任何课上，你都可以把它当作另一种调试技巧。

而在人工智能时代，你可以用 CS50.AI 平台上的 AI 驱动虚拟橡皮鸭，以及 cs50.dev 的 VS Code 里集成的同类工具。

但有几点必须说清楚：

- 这是一种**求助机制**，适用于那些你认为自己无法独立解决的问题。所以当你看不懂一条错误信息时，向"橡皮鸭"求助是完全合理的做法。
- **不要**把代码直接复制粘贴给"橡皮鸭"，然后问一句"我的代码哪里有问题？"——这样提问不合适。
- 你应该与 AI 进行**协作式互动**。这门课乃至任何课程的核心意义，在于培养编程直觉、构建思维模型、掌握实际技能。
- 请在**过度依赖"橡皮鸭"**和**自己动手用工具**之间找到平衡。在找真人或"橡皮鸭"帮忙之前，先试试 printf 调试法，甚至在桌上摆一只实体橡皮鸭。

> **结论**：工具是有优先级的——先 `printf`，再 `debug50`，再实体鸭子，最后才是 AI。把顺序颠倒，你就永远不会自己长出调试能力。

工具箱齐了。现在，去看看那些程序运行的底层机制。

### make 不是编译器

上周我们建立过一个思维模型：你用 C 写的源代码，计算机**根本看不懂**。它只认识 0 和 1，也就是机器码。所以编译器就是那个把源代码翻译过去的程序。

更广义地说：**编译器就是一个把一种语言翻译成另一种语言的程序**，在我们这个场景里，就是源代码 → 机器码。

本周的一个学习目标，就是从更底层的视角去看这件事，这样以后遇到更棘手的问题时，你能从**第一性原理**出发推理，而不是把计算机当成某种魔法。到学期结束，你会建立起一种自底向上的理解：当今任何一台计算机——笔记本、台式机、手机——内部的一切是怎么跑起来的。

先拿上周最简单的程序开刀：

```c
#include <stdio.h>

int main(void)
{
    printf("hello, world\n");
}
```

目标：把它变成机器码——那些 0 和 1。

先澄清一件我上周说得有点含糊的事：**`make` 不是编译器。** `make` 是一个命令，作用是"生成"你的程序——它通过编译来生成程序，但严格说 `make` 本身不编译。你们一直在用的真正编译器叫 **`clang`**（针对 C 语言），它非常流行，免费开源，你甚至可以在网上读别人写编译器的代码。`make` 做的本质上是**自动执行 clang 命令**。

我们平时写完 `hello.c`，敲的两条命令是：

```bash
make hello     # 编译
./hello        # 运行
```

其实我一直可以直接运行：

```bash
clang hello.c
```

这么做的结果也"看起来运行成功了"——但如果你 `ls` 一下，会看到多出来一个叫 **`a.out`** 的程序。它和 `hello` 是同一个程序，只是用了默认名 `a.out`（assembler output，汇编器输出）。运行 `./a.out` 也确实能跑。

第一周不这么干，是因为它会平白多出一个需要你记住的奇怪名字，纯属徒增烦恼。

> **易错点**：养成看到 `a.out` 就知道"这是我 clang 出来的东西"的意识。它出现在目录里不是意外，是你漏写了 `-o`。

再往前一步，加上 CS50 库：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
    printf("hello, %s\n", name);
}
```

现在如果我运行 `clang hello.c`：

> `链接器命令执行失败，退出代码为 1`，原因是存在对 `get_string` 的**未定义引用**

注意这个错误和以前的区别。以前 `get_string` "未声明"是因为少了一行 `#include`。可这次那行明明就在文件里。问题在于：`clang hello.c` 默认以为它知道去哪里找 CS50 版的 `get_string`，**但它并不知道**。得显式告诉它：

```bash
clang hello.c -lcs50
```

`-lcs50` 乍看有点神秘，其实就是说："请链接 CS50 库。"这样编译器才能找到 `get_string` 对应的二进制代码。按下回车，错误消失，`./a.out` 就能正常问名字、打印 `hello David`。

### 命令行参数

一直在说"参数"了，这里讲清楚。

**命令行参数 = 你在终端里输入程序名之后的所有单词**，无论是 `make`、`code` 还是别的程序。

- `code hello.c` → `hello.c` 是命令行参数
- `make hello` → `hello` 是传给 `make` 的命令行参数
- `clang hello.c -lcs50` → 我传了**两个**命令行参数：`hello.c` 是要编译的代码，`-lcs50` 是"请使用 CS50 库"

还可以再加一个：

```bash
clang -o hello hello.c -lcs50
```

`-o` 就是给生成的可执行文件**指定名字**。`-o hello` 里的 `hello` 正是这个参数的取值。编译完 `ls` 一眼，得到的程序集合跟之前用 `-o` 命名时完全一样。

> **定义**：`-o name` 里的 `name` 是**参数**，`-o` 本身是**选项/开关（option）**。文档里写作 `-o <file>`，尖括号里的就是你要替换的位置。

（想清理目录的话：`rm a.out` 删掉默认名那个，`rm hello` 删掉自定义名的那个。）

但你看清这里的滑稽之处了：`clang -o hello hello.c -lcs50`，再 `ls`、再 `./hello`——**这个练习的全部意义就是让你亲身体会这些命令有多烦。** 你得记住顺序、记住参数怎么写，纯属浪费时间和精力。第一周的学生基本上就是在死记这些看起来很神奇的指令。

而 `make hello` 之所以好用，正因为它把这些全自动化了——由于我们在 cs50.dev 里已经预先配置好，`make` 会在后台悄悄做完这一切。**它一点都不神奇**：

```text
make hello
    └── 实际等价于 ──▶  clang -o hello hello.c -lcs50
                          │       │      │       └── 使用 CS50 库
                          │       │      └───────── 编译这段代码
                          │       └──────────────── 输出文件命名为 hello
                          └──────────────────────── 调用编译器 clang
```

**只不过 `make` 帮我们一次性解决了一堆本来要手写的东西。**

### 预处理这一关：头文件到底做了什么

不过"编译"这个词里其实有点门道。

> **定义**：严格来说，**"编译"（compile）指的是四个独立的流程**，它们依次自动执行，功能各不相同。

我们今天只过第一个：**预处理（preprocessing）**。

看这个程序——我们上周简要写过：

```c
#include <cs50.h>
#include <stdio.h>

void meow(int times);

int main(void)
{
    for (int i = 0; i < 3; i++)
    {
        meow(3);
    }
}

void meow(int times)
{
    printf("meow\n");
}
```

`meow` 什么都不接收、什么都不返回，只打印一行 "meow"；`main` 里的 `for` 循环迭代 3 次，每次调用 `meow`。

那行 `void meow(int times);` 就是**函数原型**，它是必要的：**我们必须在使用 `meow` 之前先告诉编译器它存在**，尤其是在实现还没写到的时候。把函数的声明复制粘贴到使用点之前，问题就解决了。

> **这正是头文件在替我们做的事。** 在我调用底下的 `printf` 之前，编译器需要知道它是什么、输入参数是什么、输出是什么。而 `printf` 的函数原型就住在 `stdio.h` 里——`#include <stdio.h>` 这一行一直以来干的就是这件事。

再看一个更简单的例子，我们一直在用的那个：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
    printf("hello, %s\n", name);
}
```

现在用 `make`（实际调 `clang`）**预处理**这个文件，会发生什么？

1. 编译器在服务器的硬盘上找到 `cs50.h` 这个文件。
2. `cs50.h` 的内容被**逐字复制粘贴**进我的代码里。
3. 于是我的代码中出现了 `get_string` 的函数原型（虽然我们之前没见过它的具体内容——但可以合理推断：括号里的 `"What's your name? "` 是**输入参数**，函数名前面那部分是**返回值**，也就是一个字符串）。
4. 同样地，`stdio.h` 里的 `printf` 函数原型也被复制粘贴进来。

```text
预处理之前（你写的）              预处理之后（编译器看到的）
────────────────────────         ──────────────────────────────
#include <cs50.h>          ┐
#include <stdio.h>         │
                          ├──▶   string get_string(string prompt);
int main(void)                    int printf(const char *format, ...);
{                                int main(void)
    string name = get_string(     {
```

## 编译、内存与数组：从预处理到 NUL
> 对应块：BLK08 | 覆盖分集：P03中1 | 块标题（分集名）：《编译流程与 CS50 库函数》

休息回来，我把上周那张编译流程图重新调了出来，指着第一格说："这就是预处理阶段。"然后问了那个绕不过去的问题——**编译，在技术层面上究竟意味着什么？**

### 编译这四个字背后，是四个步骤

答案的第一步，是把预处理后的代码转换成一种叫**汇编代码**的形式。

这门课不会深入讲汇编代码，但它值得被知道：那是 C 和 Python 出现之前，程序员们写代码的方式。在更早之前，程序员是靠打孔卡在大型计算机上直接输入 0 和 1 的——工具就是那些带着孔洞的纸片。这套办法一点都不有趣，而且极其繁琐，于是人们发明了汇编语言。汇编还是不够便捷，于是又有了 C。C 还是不够便捷，于是又有了 Python 这样的高级语言。我们在这条路上一步步往前走，但技术层面发生的事其实一直没变：**编译器把源代码翻译成更低层的指令**。

屏幕上那份汇编代码看起来晦涩难懂，"但这完全在预期之中"。不过里面仍然有一些你认得的东西：提到了 `main`，提到了 `get_string`，提到了 `printf`；再往下是一串别的指令——移动、压栈、异或、调用。

> **定义**：汇编指令是中央处理器（CPU）能够理解的最低层级指令。CPU 就是英特尔、AMD、苹果这些公司造出来的核心运算部件。

能用 `main`、`for`、`printf` 这样的词来写代码，当然比翻手册去背那些晦涩指令方便得多。差别就在这里。

再往下走一步，是**汇编**：`hello.c` 经过汇编之后，汇编代码变成 `hello` 里那些实实在在的 0 和 1。屏幕上那个文件名 `a.out` 就是这么来的——`a` 是 assembler（汇编器）的 `a`，`out` 是输出。它内部装的本来就是汇编器吐出来的东西。

然后是**链接**，也是最后一步。

这里有一个必须讲清楚的事实：你的 `hello.c` 并不是最终程序的全部。你的代码要和 CS50 库里的代码、和别人写的标准输入输出库代码整合在一起。我和团队写了 CS50 库的代码，全世界其他开发者写了 `printf` 的实现。所以严格来说，服务器上躺着四样东西：CS50 的头文件、stdio 的头文件、你的 `hello.c`、我们的 `cs50.c`，再加上真正装着 `printf` 具体实现的那份文件。

> **提示**：它其实并不叫 `standardio.c`——严格说不是这个名字。但核心要点完全一样，这算是个善意的谎言。

这些文件已经提前为你编译好了。汇编把每一段代码都变成 0 和 1，链接做的事就是把**三段**二进制拼在一起。

还记得上周你不加 `-lcs50` 编译时，系统跳出来的那一串链接报错吗？那就是这里出了问题：链接失败意味着计算机没法把你的代码和 CS50 的库代码连起来，因为少了那个"指令"——它本来是告诉编译器去硬盘的某个位置找库文件的。

所以完整的四步是：**预处理、编译、汇编、链接**。程序员们为了图省事，把这整个过程统称为"编译"。说"编译"确实方便得多，你不必操心底层细节。但知道这几个词的差别，能让你在报错里真的读出信息：报的是哪个环节的问题。

### 0 和 1 的花样：架构、分工与逆向

有个学生提了个很关键的问题：一串 0 和 1，在不同上下文里可以代表完全不同的东西——它可以是文本字符，也可以是别的数据。计算机怎么知道眼前这 8 位代表的是哪种类型？

答案分两层。眼下能说的是：屏幕上那一大串 0 和 1 遵循着某种模式，顶部的比特位承担特定功能，底部的比特位承担别的功能，它们按特定模式组织在一起。这**不是**一团杂乱无章的 0 和 1，而是有一套编码规范。至于这个规范到底是什么，我们到第 4 周再详细拆开讲。

另一个学生问到了预处理：它是不是把头文件的内容直接复制粘贴到你的代码里？

是的，就是这么"暴力"。你不用手动重复写一遍 `get_int` 的声明，源头上省下来的都是重复劳动。

然后是个关于 CPU 的追问，值得多说几句：编译的时候，是从 C 代码转成汇编代码，而**生成的汇编代码模式是针对特定 CPU 架构的**。

> **结论**：同一段 C 代码，为 iPhone 编译和为安卓编译，输出的指令集是不一样的。所以你不能把 Mac 的程序光盘直接拿到 PC 上跑，反过来也不行——指令模式不兼容。

那你可能会问：这么麻烦的分层，为什么还有人要搞？因为它让分工成为可能。也许现在有 14 个不同的开发者，分别去实现预处理器、编译器、汇编器、链接器。把流程拆成这些标准化步骤，一来不同团队可以各干一环，二来两个团队可以分别写针对 iPhone 和安卓的编译器——而我们所有人仍然在上层用同一种语言编程。这种复杂性背后全是有道理的考量。日常写代码用不上这些，但**支撑起今天如此复杂的计算世界的，恰恰是这些底层机制**。

#### 能不能把编译反过来做

有人接着问了更有意思的问题：Word、Excel 这种软件，我买下来或者下载下来，拿到手的不就是一大堆 0 和 1 吗？我能不能反着走一遍，逆向工程出别人的代码？

这确实是个实实在在的威胁，而且常常牵扯到法律和知识产权。因为要让你的计算机跑起来，这些 0 和 1 必须对你、对你的机器可访问。

但说起来容易做起来难。屏幕上这一串比特模式代表什么？它打印出来的是 "hello world"，可我一眼看不出来，更别说凭记忆直接说出来了。真人答不上来这个并不奇怪。

但是——如果我知道这段代码是为哪种架构、哪种 CPU 编译的，而且我在第 4 周认真听了课，了解这些 0 和 1 的不同排列方式，我就可以把它们拆成 8 位、16 位、32 位、64 位的片段，艰难地逐一解读出每段模式代表什么。64 位是最常见的计量单位。

即便如此，这活儿也得花上极其漫长的时间。通常的判断是：如果你足够聪明、足够强，并且有充足的闲暇干这件事，那你还不如老老实实用常规方式重新开发一个微软 Word——直接重构整个程序反而更省时。逆向所需的时间，比正向开发长得多。

> **易错点**：就算你真的一行一行逆回去了，也**不可能完美还原**。想象这段代码里有个循环，在重复打印"喵、喵、喵"。我们都知道有时可以用 `for`，有时可以用 `while`，它们在功能上完全等价——选哪个更多是风格问题，取决于你更习惯哪种写法。但你无法从这些 0 和 1 里判断它原本是 `while` 还是 `for`，因为最终生成的二进制模式是**完全相同**的。仅凭 0 和 1 的序列，你根本看不出源代码最初长什么样。

#### 并非所有语言都要编译

不过，也并非所有编程语言都这样。先透露一点：几周后我们讲用于网页编程的 JavaScript 时，你会发现 JavaScript 的源代码是从网络服务器直接发送到浏览器里的。这意味着你可以查看互联网上任何网站的源代码——Harvard.edu 的、Gmail.com 的，全都看得见。

所以并非所有语言都像 C 一样需要编译。有时候源代码就是由底层计算机直接执行的。

### 每个类型要吃掉多少字节

回到正题。我们写代码时必须明确指定变量里存什么类型的值——这也是为什么今天我修第一个 bug 时，得在变量名 `name` 前面补上 `string` 这个类型声明。

C 的数据类型其实相当丰富。上周我快速列过一遍：布尔型、整型、长整型、浮点型、双精度浮点型、字符型、字符串型。现在我们换个角度：每种类型到底占多少内存？理解了这些，你就知道调试器之前显示的那些数字是怎么来的了。

先看 `bool`。它占 1 个字节——这有点不合理，因为从技术上讲，真或假其实只需要 1 个位就能表示。结果发现，直接占用整个字节反而更高效、更方便，尽管其中 7 个位实际上并没有被用到。

`int` 通常占 4 个字节。用它去数很大的数，上周说过最大值大约是 40 亿；除非你要表示负数，那样最大值就大约是 20 亿——因为得在正负范围之间做某种平衡分配。

`long` 是它的两倍，8 个字节，能表示的取值数量比 40 亿多出十几个数量级，而且是在同时包含负数的前提下。

`float` 是带小数点的实数，默认 4 个字节；`double` 提供两倍的比特位，从而达到更高的精度。归根结底，浮点数的精度问题是一个根本性挑战，在科学计算、金融以及其他对精度要求极高的领域尤其关键。

`char` 至少从我们目前所见，是专门用来存单个 ASCII 字符的一个字节。

`string` 我要打个问号，因为它占多少完全取决于你实际存了什么。存一个 4 个字符的词，和存一个 5 个字符的词，数字是不一样的——晚一点你会看到，字符串末尾还藏着一个额外的字节。

| 类型 | 占用字节 | 说明 |
| --- | --- | --- |
| `bool` | 1 | 真/假本只需 1 位，但整字节更高效方便，7 个位闲置 |
| `int` | 4 | 无符号时最大约 40 亿；带上负数后约 20 亿 |
| `long` | 8 | `int` 的两倍，含负数时取值数量大出十几个数量级 |
| `float` | 4 | 带小数点的实数 |
| `double` | 8 | 两倍比特位，精度更高 |
| `char` | 1 | 单个 ASCII 字符 |
| `string` | 取决于内容 | 每字符 1 字节，末尾另加一个终止字节 |

### 内存：一张按字节编号的画布

那么这些数据到底存放在哪里？

把内存条想象成一根存储棒。插进笔记本、台式机或别的设备，上面那些小小的黑色芯片里，实际上就塞满了用来存放 0 和 1 的空间。内存本质上是个电子设备，但它内部就是无数个 0 和 1 组成的东西，我们的数据就存在这些二进制位里。

放大观察内存的结构，原理就显而易见了。为了方便讨论，假设这块芯片是 1GB，也就是 10 亿字节。那么我们可以很自然地给这些字节编上地址：从 0 开始，一直编到 10 亿。编号顺序是从上往下、从左往右还是别的，其实都不重要——我们现在只在概念层面讨论。

那就把内存想象成一张网格、一块画布，用来存放各种类型的数据。

```text
address  ->    0        1        2        3        4        5        6        7
              ┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
              │        │        │        │        │        │        │        │        │
              └────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘

char  c = 'H' [   'H'   ]
int   i = 72   [   72    ][        ][        ][        ]
long  l = 72   [   72    ][        ][        ][        ][        ][        ][        ][        ]
```

读图：网格上每一格就是一个字节，也就是 8 个比特，按地址从 0 编到最后一个字节。存一个 `char` 只用 1 格；存一个 `int` 要占 4 格，而且**必须连续**——你不能随意挑几个散落在各处的比特位凑数。`long` 和 `double` 同理，要占 8 格。

> **结论**：当你有一个 4 字节的值，它们在内存中就是这样连续紧密排列的；`long` 和 `double` 则是 8 个字节排在一起。往硬件的物理位置里放一个值，说到底只是用了一些 0 和 1，通过改变它们的排列组合、开启或关闭某些位，来表示你想要的数值。值大还是值小，都一样。

### 三个分数，和一个被吃掉的 0.333

抽象够了，我们写点真的。

先造一段代码，里面放三个分数，就当是问题集的得分：72 分、73 分、33 分。我特意挑了这三个数字，因为它们是熟悉的老朋友——等一下你会看到它们再次出现，这样就不用引入新的随机数字了。

```c
#include <stdio.h>

int main(void)
{
    int score1 = 72;
    int score2 = 73;
    int score3 = 33;

    printf("average: %i\n", (score1 + score2 + score3) / 3);
}
```

这个程序叫 `scores.c`，能快速算出我在问题集上的平均分。先输出一个提示，让人知道接下来打印的是什么；然后在分号之前，传一个简单的数学表达式进去：平均分就是（分数 1 + 分数 2 + 分数 3）除以 3，把三个分数放在分子里，还要加上括号，像小学学的那样先加后除，最后以分号收尾。

跑一下。显示的平均分是 59。

不错，但我认为这不是我真正想要的结果。我哪里做错了？

——是的，这是无意的，我确实没有把最差的成绩算进去，是个失误。而且从技术上讲，我认为我的分数在数学上应该是 59.13。我好像被坑了那三分之一分。

问题出在整数运算上。除以 3 时，小数点后的部分被直接截断了——这就是第一周最后提到过的**整数除法会直接舍弃小数部分**。

解决办法之一，是把格式代码里的 `%i` 换成 `%f`，这个格式代码专门用来打印浮点数。我们来看是不是只改这一处就够了。`make scores`，哎呀，还是不行——我刚才是太心急了，没往回滚看错误信息：

```text
格式说明符要求 double，但传入的参数是 int
```

原来 `%f` 也能用于 `double`，所以这里显示的是 `double`，而我本意只是想要 `float`。我传入的是 `int`，类型对不上。

那就把这些分数转换成浮点数。干脆全都改掉，每个数字末尾加个 `0.0`，这样就能明确表示它们是浮点数了。

```c
    printf("average: %f\n", ((float) score1 + (float) score2 + (float) score3) / 3);
```

不过还有一种方法，而且更省事：**直接把分母改成 `3.0`**。

```c
    printf("average: %f\n", (score1 + score2 + score3) / 3.0);
```

原理是：只要运算中涉及到一个浮点数，整个表达式就会被"提升"为浮点运算，不会停留在整数计算上。我不需要把所有数字都转一遍。结果出来了，那三分之一的分值也回来了。

顺便提一句，其实还有第三种办法，如果你确实想坚持用 `3` 当分母——从语义上说，直接除以 `3.0` 有点奇怪，那更像一个实现细节，而你实际算的是三个数的平均值。技术上你可以用括号把 `3` 强制转换成浮点数，明确指定目标类型，编译器也能顺利通过：

```c
    printf("average: %f\n", (score1 + score2 + score3) / (float) 3);
```

结果大致相同，也仍然能看到一点浮点数精度问题——但这完全由浮点运算的特性决定，对我们的目标来说够用了。

### 三个变量，十二个字节

现在来看，计算机内存里到底发生了什么。

回到最简单的例子：假设 `72` 落在了内存网格的左上角。按比例画的话，`score1` 明显占用了 4 字节，它是一个整数。严格来说这取决于你用的具体系统，但如今可以合理地假设，在大多数现代系统上整数通常是 32 位的。`score2` 大概在那儿，`score3` 大概在更远的地方——总共 12 字节，每个值 4 字节。

而内存里实际存的是什么？严格来说，每个变量就是由 32 个 0 和 1 组成的二进制序列。三组 32 位的序列，共同构成了那些数字。

好消息是：**我不需要操心这个，编译器基本上已经帮我搞定了变量在内存中的存放位置。**

坏消息是——好吧，也不算坏消息——但从这周开始，用这种方式设计代码会让你觉得别扭。计算三个分数的平均分，这样做没什么大不了的。但想想最极端的情况：如果不是 3 个，而是 30 个、300 个分数，这真的是最佳方法吗？

你觉得不是，那前辈们肯定早就想出了更好的办法，毕竟到学期末变量数量会越来越多。这种粗糙感，往往就是判断设计好坏的标准。

### 从三个变量到一个数组

办法当然有。我们可以把那块内存画布——也就是字节网格——划分成一块块叫**数组**的内存。

> **定义**：数组是一块连续的内存，其中的元素一个接一个地紧密排列。你想存 3 个数据，就向计算机申请一块能容纳 3 个数据的空间；要存 30 个，就申请 30；要存更多，就申请 300。这里说的"块"不是专业术语，只是我用来解释数组的通俗说法——它是一块或一段内存空间。

编译器提供了一个新语法来观察它的效果：

```c
int scores[3];
```

这一行的意思拆开看很清楚：编译器，请为我创建一个名为 `scores` 的变量，请分配能容纳**三个整数**的空间。`int` 指定了所有元素的类型，`scores` 是数组名，方括号里指定这块内存要存多少个整数。

> **提示**：我特意用了复数形式命名——现在叫它 `scores` 比叫它 `score` 合理。

这一行会自动分配 12 字节，而且这 12 字节全部通过 `scores` 这个名字来引用。把它接进代码里：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int scores[3];
    scores[0] = 72;
    scores[1] = 73;
    scores[2] = 33;

    printf("average: %f\n", (scores[0] + scores[1] + scores[2]) / 3.0);
}
```

看起来和声明三个变量没太大区别，对吧？但现在从技术上讲，**我只有一个变量**，只是通过索引访问它的不同位置——位置 0、1、2。

从 0 开始计数，因为计算机领域通常从 0 开始计数。`scores[0]` 存 72 分，对应第一份作业；`scores[1]` 对应 73 分那一份；`scores[2]` 是我最弱的一项，33 分。

顺便说一个编辑器细节：你输入 `scores` 和左方括号时，VS Code 会弹出自动补全，帮你省掉一些按键，还神奇地把光标定位到该输数字的位置。**但这和 C 语言本身无关**，只是 VS Code 在提供便利功能而已。

现在跑 `make scores` 和 `./scores`，结果完全相同，但设计明显更优了：一个变量顶掉了三个，更别提数据更多的时候。如果想调整成绩总数，只要改初始化时方括号里的数字就行。

那内存布局变了什么？其实结构完全一致，只是不再需要三个独立的变量名：

```text
scores  ┌────────┬────────┬────────┬────────┐
        │   72   │        │        │        │   <- scores[0]
        ├────────┼────────┼────────┼────────┤
        │   73   │        │        │        │   <- scores[1]
        ├────────┼────────┼────────┼────────┤
        │   33   │        │        │        │   <- scores[2]
        └────────┴────────┴────────┴────────┘
        4 bytes   4 bytes   4 bytes
```

读图：三个元素各占 4 格，在内存里连续紧密排列，**这一点尤其重要**。屏幕宽度有限，字节会换行显示到下一行，但计算机本身没有上下左右的空间概念——硬件本质上只是一块拥有大量可用字节的空间，这些字节可以从第一个字节一直寻址到最后一个字节。换行只是屏幕上的视觉呈现。

### 让分数从键盘进来

不过分数还硬编码在代码里，程序只对这三个人有效。现在引入 CS50 头文件库，用上 `get_int` 这样的函数，动态地获取这些分数：

```c
    int scores[N];
    scores[0] = get_int("Score: ");
    scores[1] = get_int("Score: ");
    scores[2] = get_int("Score: ");
```

跑一下，输入 72、73、33。程序现在具备了一定的交互性，它不再只适用于我预设的三个分数——它可以适用于班级里任何人的分数。

但这依然暗示着设计上的缺陷。我之所以引入数组，是因为一个变量现在能代替三个了，可第 8 行和第 9 行之间有些地方让你觉得不太对劲：**代码有重复**。我是手动输入的，但本质上和复制粘贴完全相同。

有什么编程结构能优化这段代码？`for` 循环或者 `while` 循环都可以，不过 `for` 循环通常就能搞定，这也是我最常用的方法：

```c
    int scores[N];
    for (int i = 0; i < N; i++)
    {
        scores[i] = get_int("Score: ");
    }
```

这里方括号的作用就体现出来了：`scores[i]` 拿到对应位置的值。我在循环里只调用一次 `get_int`，因为 `i` 会不断递增——就像我们之前实现"喵喵叫"之类功能时反复做过的那样。第一个输入存到位置 0，为什么？因为 `i` 的初始值是 0；第二个存到位置 1，因为我执行了 `i++` 继续下一轮迭代；第三个自然落到位置 2。这样我就用不着手动逐个输入了。

不过我对目前的实现还是不太满意。**这里用了一个"魔法数字"。**

数字 `3` 确实在两个地方被硬编码了：第 6 行用它作数组大小，第 7 行又用它作循环迭代次数。但这两个地方指的是同一个概念，现在全靠我手动输入 `3` 来保证它们一致——这完全依赖于人的自觉性。凭什么要依赖自觉？

```c
const int N = 3;
```

然后数组声明和循环条件里都用 `N`。这样我只需要在一个地方修改这个值。

```c
#include <cs50.h>
#include <stdio.h>

const int N = 3;

int main(void)
{
    int scores[N];
    for (int i = 0; i < N; i++)
    {
        scores[i] = get_int("Score: ");
    }

    printf("average: %f\n", (scores[0] + scores[1] + scores[2]) / 3.0);
}
```

> **结论**：当一个变量的值**不应该**被改变时，就把它声明为常量——在类型前加上 `const` 关键字。无论是你自己、同事还是其他协作者，都无法再修改它。而且按照惯例和代码风格，常量通常采用**全大写字母**命名，这样别的程序员一眼就能看出这个变量有些特殊、确实不可更改。

好了，稍微好一些了。不过你翻到程序底部，会发现还有个问题：我仍然硬编码着 `0`、`1`、`2`——不过这个我们稍后再来处理。

### 写一个真正能复用的 average 函数

接下来我们加快速度，主要是为了说明这个程序还能变得更动态灵活。

先假设我们已经有了一个现成的函数 `average`，只要把想算平均值的分数传给它就行。但这样的函数并不是现成的——我不能直接调用某个现成的库来实现它，看来得自己动手。

在文件开头部分定义它。这个函数需要接收……一个数字数组作为参数。语法可能有点陌生，我用 `numbers` 来命名，避免 `array` 这种太通用的名字。

那它该返回什么类型？具体来说是一个浮点数。也可以返回 `int`，但那样我会损失小数点后三位的精度；返回 `double` 更保险，不过在这里似乎有点小题大做。

函数内部怎么算平均值？这其实就是个数学问题。声明一个叫 `sum` 的变量，初始化为 0，然后写循环把数组元素一个个加起来：

```c
float average(int n, int numbers[])
{
    float sum = 0.0;
    for (int i = 0; i < n; i++)
    {
        sum += numbers[i];
    }
    return sum / n;
}
```

`numbers` 就是我的数组，`numbers[i]` 表示访问索引为 `i` 的位置。循环从 0 开始，就意味着先访问位置 0，然后 1、2，以此类推；如果数组里还有更多分数，`i++` 会让它一直往上递增。

这里我犹豫过，所以留了个 TODO 提醒自己：**我应该迭代到什么时候为止？** 如果你在学 CS50 之前就有编程经验，通常可以直接问数组（也就是向量）的长度，Java 和 Python 都能这么干。

> **易错点**：**C 语言里没法直接获取数组的长度。** 如果我想知道这个数组有多长，就得让函数告诉我。所以这个求平均值的函数不能只接收数组作为参数，还必须再接收一个参数，比如命名为 `length`，用来告诉我数组的长度。这也意味着调用的时候有点麻烦——你不仅要传入数组，还得单独把它的长度传进去。

回到调用处。这样写有点过于冗长了，我们回头把 `sum = sum + numbers[i]` 简化成 `sum += numbers[i]`，这算是一种语法糖。

最后一件事是实际算出平均值：所有分数的总和除以分数的总个数。有了总和，用总和除以长度就得到平均值——总和是分子，长度是分母。

我想把这个值**传回去**，而不是用 `printf` 直接打在屏幕上，因为我不想产生这种视觉上的副作用。返回值的语法我们之前做过一两次了。

完整的样子是：

```c
float average(int n, int numbers[]);

int main(void)
{
    int scores[N];
    for (int i = 0; i < N; i++)
    {
        scores[i] = get_int("Score: ");
    }

    printf("average: %f\n", average(N, scores));
}
```

> **定义**：定义函数时，如果参数是数组，你需要指定数组中元素的类型，可以给这个参数任意命名，然后用**空方括号**表示——`int numbers[]`。你不需要在里面填写数字或其他内容，只需要告诉编译器："我的 `average` 函数会接收一个数组，但无需指定具体长度。"

另外还有两件必须做的事。

一是调用方也得如实交代长度，`average(N, scores)` 这样。而那个数组本身是在 `main` 里创建的，就在我们写 `int scores[N];` 这一行的时候。

二是函数原型。我一直强调 `main` 应该放在代码顶部，这是习惯问题，没什么大不了的。但如果 `average` 定义在文件底部、而 `main` 在顶部，编译器在读到 `average` 的时候还不知道它是什么，就会报错。解决办法是把第一行代码——也就是所谓的**函数原型**——复制粘贴到最上面。

现在编译运行。输入 72、73、33，回车。

哎呀，就差一点点——我遇到了一个回归问题。**我又犯了同样的错误，只是方式不同。**

> **易错点**：第 11 行的 `return` 语句里，我用的是整数除以整数，于是又遭受了整数截断。如果返回的是整数，就没有空间容纳小数点及其后的数字了。

解决办法有很多种：可以把 `sum` 改成浮点数（最终我就是这么做的），也可以用类型转换的技巧，把长度也转成浮点数。改完之后重新输入分数，平均分大约是 59.333——可能还有一点精度误差，但对大学成绩这种场景，精度已经足够了。

> **结论**：这一节看着细节很多，但本质上都是必要的步骤。真正**新增加**的内容只有一条——**这就是如何向一个函数传递一个已在别处定义好的数组：不是通过数组名，而是通过方括号内的内容**。`%c%c%c`、`s[0]` 这些语法大家已经很熟了；`int numbers[]` 才是新东西。

### 字符就是数字

我们可以用刚学到的这些知识做点实际的事情——既能提升理解，也能更清楚地看透计算机内部在干什么。

回到内存网格的视角。这次我们不存数字，改存三行代码：三个字符型变量。虽然你可能已经猜到我要说什么了，但这样的设计确实不理想，因为我用了三个命名很随意的变量 `c1`、`c2`、`c3`。

先强调一个关键点。第一个变量的值是引号内的 `'H'`，第二个是 `'I'`，第三个是感叹号 `'!'`。为什么这里改用**单引号**而不是双引号？字符用单引号，字符串用双引号——稍后我们会看到它们之间的区别。

如果这程序只有这 3 个字符变量，它们在内存中很可能会这样连续排列：

```text
c1 c2 c3   [  72 'H' ][  73 'I' ][  33 '!' ]
```

现在新建一个 `hi.c`，来点真正有意思的：

```c
#include <stdio.h>

int main(void)
{
    char c1 = 'H';
    char c2 = 'I';
    char c3 = '!';

    printf("%c%c%c", c1, c2, c3);
}
```

`%c` 表示字符类型。`make hi` 然后回车——瞧，`HI!` 显示出来了。这并没有什么神奇之处，我只是简单地把三个字符变量打印了出来。中间那些空格其实并不需要，去掉后重新编译，程序照样正常。

但正是在这里，对数据类型的理解能让你获得掌控力和辨别能力，满足一些好奇心。**如果我把 `%c` 换成 `%i` 会怎样？**

`make hi` 然后运行——看起来有点难以理解，好像显示的是 `727333`。在每个占位符之间重新加上空格：

```c
    printf("%i %i %i", c1, c2, c3);
```

72、73、33，我们熟悉的老朋友又出现了。

> **结论**：这里**没有**使用显式的类型转换。因为编译器和 `printf` 足够智能——如果你传入一个字符类型的值，它们本质上已经知道这会被视为整数。你甚至不需要显式转换，我们实际上是通过使用这些格式代码，**隐式**地把它转成了整数。

这就证明了我之前说的：字符与数字之间的这种等价关系，在计算机内存中确实成立。尽管你存储的是 `HI!`，从技术上讲你实际存储的是三个 8 位模式，分别对应十进制数 72、73 和 33。

### 字符串就是字符数组，末尾藏着一个 NUL

那字符串究竟是什么？这里才是事情变得更有趣的地方。

字符串，正如我们一直使用的，可以是一个完整的单词、一个短语，甚至像今天课程开始时那样是一整段文本。所以它包含了**多个值**——这就引出了一个很有意思的问题。

先写一行代码，把它当作一个字符串来处理：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string s = "HI!";

    printf("%s\n", s);
}
```

注意这里是**双引号**。而且因为 `string` 只是我们前几周用的一个辅助工具，还得加上 `#include <cs50.h>`，这样编译器才能认识 `string` 这个类型。跑一下，整个字符串被打印出来。

那么这次内存里发生了什么变化？内容还是 `HI!`，但它已经是一个字符串了。**它在内存中的布局和之前完全一样**——只不过这里没有提到 `c1`、`c2`、`c3`，因为那些变量并不存在。现在只有一个变量，但它指向内存中的 3 个字节。

看起来是个字符串，你大概已经猜到它实际上是什么了——**剧透一下：它其实就是一个字符数组**。这正是我们今天要串联起来的那条线索。

既然是个数组，我敢打赌可以用方括号表示法来验证。这次我们不用 `%s`，改用 `C`、`C`、`C`，分别输出 `s[0]`、`s[1]`、`s[2]`：

```c
    printf("%c%c%c", s[0], s[1], s[2]);
```

输出还是 `HI!`——因为我明白底层究竟发生了什么，才敢这么干。再把 `%c` 换成 `%i` 并加空格，72、73、33 又一次出现。**而这仅仅是因为我用了双引号。**

但这里还剩一个更要命的问题：计算机在执行 `printf` 时，怎么知道该打印什么内容？更准确地说，`printf` 使用 `%s` 时，怎么知道**在这里停下**，而不是继续把内存里其他位置的字符也打印出来？随着变量和代码量增加，内存里必然会出现别的东西。

来做个实验，大胆一点——添加第四个字母，直接访问 `s[3]`。这个位置本来不该存在，但下标 `3` 对应的确实是第 4 个存储位置，而 `HI!` 实际只包含 3 个字符。看看数组末尾之后是什么。

有意思——看起来，也许只是运气好坏——第 4 个字节似乎是一个 `0`。

其实这很大程度上是**设计使然**。按照惯例，编译器会自动用**一个由 8 个 0 位组成的模式**来终止我们放在双引号里的任何字符串。更简洁地说，它就是数字 `0`——8 个 0 位算出来正是十进制的 0；从更专业的角度说，它通常写作 `\0`，因为它并不是我们想在屏幕上看到的那个数字 `0`。反斜杠 `\0` 类似于反斜杠 `
`，是一种特殊的转义字符，它指的是 8 个 0 位，而不是你在电话号码里看到的数字 0。

> **结论**：尽管我们说字符串等于 `"HI!"`，看起来是 3 个字符，但一个长度为 3 的字符串在内存中实际占用的是 **4 个字节**，这一切都是自动完成的。双引号替你实现的功能就是：告诉编译器这不只是一个字符，而是一个字符序列，请自动用一个特殊的 8 位 0 模式终止它。

这个特殊的 8 位 0 模式有一个名字，叫**空字符，简称 NUL**——一个 8 位全 0 的字节，表示字符串的结束。你其实早就见过它了，虽然只是很简短地：两周前我们看的 ASCII 表，ASCII 字符 0 就是 NUL，它一直都在那里。

那么计算机究竟是怎么在内存里输出内容的？它总得知道在哪停。`printf` 其实挺笨的——很可能在打印函数内部，它只是用一个循环，从第一个字符开始输出，然后是下一个、再下一个……直到找到字符串的结尾。

```text
s = "HI!"  ┌────────┬────────┬────────┬────────┐
           │  72 'H'│ 73 'I'│  33 '!'│    0   │  <- '\0' = NUL
           └────────┴────────┴────────┴────────┘
           s[0]    s[1]    s[2]    s[3]
```

读图：双引号里的 3 个字符占了 3 格，编译器额外补上的第 4 格就是 NUL。`s[3]` 之所以"看起来"是个 0，是因为它正好落在了这个终止字节上——这既说明 NUL 存在，也说明访问 `s[3]` 属于越界，程序行为并不可靠。

最后再补一个画面。如果你的程序里不止一个字符串，而是两个呢？把它们都放进去，一个一个 `printf` 出来（`%s` 是字符串占位符，`s` 和 `t` 只是变量名，我们并不需要用 `%t`）：

```c
    string s = "high";
    string t = "bye";

    printf("%s\n", s);
    printf("%s\n", t);
```

跑一下，结果如我们上周所预期的那样，输出了 `high` 和 `bye` 两行。

那计算机内存内部到底发生了什么？程序创建了两个变量 `s` 和 `t`。很可能的情况是，`high` 被存储在这里，也就是 `s` 的位置；因为这个程序中没有其他内容，`bye` 很可能被存储在 `t` 的位置，只不过在当前屏幕上显示时发生了换行。

`high` 占 4 个字符再加 1 个 NUL，`bye` 占 3 个字符再加 1 个 NUL——**两个字符串都各自带着一个自己的终止字节**。编译器会自动为每一个都补上 `\0`，好向其他函数明确标示这个字符串在哪里结束。

那么，这在实际情况中究竟意味着什么？为什么这里显示的是 `0` 呢？

## 字符、比特模式与字符串
> 对应块：BLK09 | 覆盖分集：P03下

### 八个零定下的规矩

为什么是 0 呢？

这个问题是从前面接着问下来的。因为说到底，计算机里所有的数据最终都是由比特（bits）构成的；对于字符（char）类型，我们用的是 8 位来表示。你必须挑一种特定的位模式（bit pattern）来代表它——我们本可以选择全 1 的模式，也可以选择全 0 的模式，或者干脆任意挑一种。多年前，一群专家在会议室里共同做出了决定：8 个 0 就用来表示空字符。

这个"空字符"不是随便一个概念，它是**字符串的终止符**。结合我们新的语法规则，这意味着什么？意味着我们对字符串也可以像对待数组那样去探索、去操作：尽管第一个变量是 `s`、第二个是 `t`，但从技术上讲，你完全可以访问 `s[0]`、`s[1]`、`s[2]`、`s[3]`，以及 `t[0]`、`t[1]`、`t[2]`、`t[3]`、`t[4]` 等等。

> **提示**：这个决定听着任性，分量却极重——今天要讲的字符串长度、逐字符遍历、大小写转换，全都是靠这个"8 个 0"撑起来的。

### 字符串就是字符数组

那就把话说透：字符串本质上一个字符数组。就今天讨论的目的而言，**字符串就是数组**。

回到 VS Code 里实际看一下。现在手上有两个字符串，我可以像之前那样输入 `s[0]`、`s[1]`、`s[2]`，然后 `t[0]`、`t[1]`、`t[2]`、`t[3]`。我这样做只是因为单词 "hi" 比 "by" 长一点。执行之后，同样的原理依然成立。

不过我们不妨加个转折。如果我在内存里存着这些值，就可以把它们当作数组使用，而不是像 `s`、`t`（或者"单词 1""单词 2"）那样分开处理——**我其实可以把字符串放进数组里**：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string words[2];
    words[0] = "high";
    words[1] = "by";

    printf("%s\n", words[0]);
    printf("%s\n", words[1]);
}
```

这里唯一的新变化是：我创建的是一个**字符串数组**，而不是整数数组，但所有语法都完全一样，打印也还是老样子的 `printf` 加换行符。这已经是这个程序的第六个版本了——我这样来回切换，只是为了展示这些是看待同一事物的不同视角，是同一个概念。

如果这些值本身都是字符串呢？既然字符串本质上就是数组，那么即使语法看起来有点复杂，我们实际上可以分两层索引：先用一组方括号索引到单词数组里的某个单词，再用另一组方括号索引到这个单词里的具体字母。

```c
printf("%c%c%c", words[0][0], words[0][1], words[0][2]);
printf("%c%c%c%c", words[1][0], words[1][1], words[1][2], words[1][3]);
```

`words[1][0]` 是第二个单词的第一个字符，`words[1][3]` 是它的最后一个字符。

```text
words[0]    h    i    g    h    \0
words[1]    b    y              \0
```

读图：数组占两个内存位置，0 和 1；每个位置里装的不是数字，而是一串字符，并且都以那个 8 个 0 收尾。

顺便回答一个必然会冒出来的问题：把 `words[0]` 整个当字符串打印是一回事，把它拆成一个个字符打印是另一回事。执行 `make high` 之后，我们就完全掌控了所有正在进行的操作——**如果你现在同意并理解了数组可以通过方括号索引访问，那么字符串也同样可以**。

### 数组是怎么来的：类型、大小和花括号

有人举手：怎么建立或创建一个数组？

好问题。我们回到 VS Code 的第 6 行——那里定义了一个大小为 2 的数组，一个包含两个字符串的数组（如果你愿意这么理解的话）。之前讨论 `scores.c` 时，第 9 行定义的是一个包含 N 个整数的数组。所以这一行代码就是在内存中创建这个数组，你需要指定**名称、大小和类型**，就这三样。

今天唯一的新知识点依然是方括号表示法。在这个上下文里它用于创建指定大小的数组；但一旦数组创建完成，你也可以通过方括号访问内存中这块数据区域。

再追问一层：是不是必须逐个索引地把数据存进去？

简短的回答是：不需要。在我程序的早期版本里，我本来可以这样写：

```c
int n = 3;
int scores[3] = {72, 73, 33};
```

用这种花括号（curly braces）的方式，可以在一行内初始化数组。这种情况下你甚至不需要指定数组大小，因为编译器可不傻——右侧写了 3 个数字，它就知道左侧只需要分配 3 个元素来存放它们。

不过我还是把这个改动撤销了，保持原来的写法。总结一下：如果你提前就知道所有数值（而不是像用 `get_int` 那样动态获取），就可以静态初始化数组。

### 数长度：一直数到空字符

既然大家理解了字符串本质上是数组、并且总是以空字符结尾，我们就可以去解决一些简单的问题了——以及前人早就解决过的问题。

打开 `length.c`，目标是计算字符串的长度。提示用户输入姓名，假设今天输入的是 Colin，接下来计算这个名字的长度，就像之前处理 D-A-V-I-D 那样。结果应该是 5，对 K-E-L-L-Y 也应该是 5。

该怎么计数呢？字符串本质上是数组，而这个数组以空字符结尾。我用一个变量 `n` 来存长度，先初始化为 0，因为现在还不知道具体长度。虽然用 `for` 循环也能实现，但这次我倾向于用 `while`：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");

    int n = 0;
    while (name[n] != '\0')
    {
        n++;
    }

    printf("%d\n", n);
}
```

这里的逻辑其实并不复杂，一旦明确了目标，实现起来就会很顺畅，多加练习你也能很快掌握这种写法。

> **定义**：空字符（`'\0'`）就是那个值为 0 的字符。在 C 语言里，`get_string` 会自动在字符串末尾加上它；`printf`、`strlen` 这类函数也都是靠它来标记字符串"到此为止"。

这个布尔表达式其实是在反复问同一句话：**这个字符是空字符吗？** 如果不是，就继续循环，检查下一个字符。这是一种很巧妙的技巧——我用变量 `n` 兼任了"当前检查位置"和"已经数过的字符数"两件事。检查到 D 时，D 不等于 `\0`，`n` 变成 1，于是去检查 `name[1]`；那是 A，同样不等于 `\0`，`n` 变成 2；接着 I，接着 D，直到抵达名字末尾——那个空字符。因为 `get_string` 会自动补上它，而空字符确实等于零，所以 `n` 不再增加。

所以在这行代码执行到末尾时，`n` 仍然是 5，因为我并没有把空字符算进去。屏幕上就会显示 5。

跑一下：输入 David，结果是 5；输入 Kelly，结果也是 5。更长或更短的名字，同样应该得到正确长度。我们再试个边界情况——干脆什么都不输入，直接按回车。这个人的名字长度应该是多少？

0。这个结果并没有错。严格来说这是对的：那其实是一个空字符串，但即使在内存中它没有任何可见字符，它仍然占用一个字节的空间，因为 `get_string` 仍然会在末尾放一个空字符。

这其实是一种非常机械化的检查：检查、检查、再检查，逐步推断出长度。而字符串的长度，说到底就是**直到遇到那个 `\0` 为止所经过的字符数**。

### 别自己造轮子：string.h 与 strlen

不过你并不需要自己重新发明轮子。除了标准输入输出库和 CS50 库之外，还有别的库——你在问题集里可能已经见过数学库，此外还有字符串库本身。如果你去查 CS50 手册，能找到名为 `string.h` 的头文件文档，里面是一系列实用函数的原型说明。

其中最重要的、接下来几周会频繁使用的，就是字符串长度函数 `strlen`。早在几十年前就有人写好了实现类似功能的代码，把它封装成一个函数供你我使用——这样我们就不必再为计算字符串长度而重复这些繁琐步骤了。

把上面那些代码全删掉，只要在文件顶部包含 `string.h`：

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    string name = get_string("What's your name? ");

    printf("%d\n", strlen(name));
}
```

坦白说，从设计角度我现在连变量 `n` 都不需要了——就像之前处理平均数时那样嵌套函数，直接在这里调用 `strlen(name)` 就完事。编译运行：David，5；Kelly，5；空输入，0，现在看起来 0 也正常工作了。这是一个我们无需重复造轮子的功能。

> **结论**：如果你在解决一个很可能别人已经解决过的问题，先去找找有没有现成的库函数；CS50 库、标准库、Make 工具都已经把这类小事准备好了。

### 逐字符打印里的效率陷阱

用上这个库，我们再做点别的。新建 `strings.c`，写一个逐个字符打印字符串的程序：

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    string s = get_string("Give me a string: ");
    printf("output:  ");
    for (int i = 0; i < strlen(s); i++)
    {
        printf("%c", s[i]);
    }
    printf("\n");
}
```

它做的事很简单：提示用户输入一个字符串，输出 "output" 这个词（我特意加了空格让上下对齐），然后逐个字符地打印，直到 `strlen` 返回的长度。用 `for` 循环写，`while` 也行。最后一个 `
` 只是把光标移到新的一行。

这里有个小细节：我特意在提示里打了两个空格，好让输入和输出完全对齐，这样你就能清楚地看到发生了什么。

那这个程序虽然功能正确，为什么设计上未必合理呢？

第一，它在做一件完全没必要的事——你并不需要逐字符输出，这只是我出于教学考虑才这么做的。第二，还有第二个更蠢的地方，而且它相当隐蔽。

回想一下 `for` 循环的工作原理：

```text
      i = 0                       ← 初始化，只做一次
      ↓
   i < strlen(s) ?  ──否──→  退出循环
      │ 是
      ↓
   printf("%c", s[i])             ← 循环体
      ↓
      i++                         ← 更新
      ↓
   回到条件判断
```

读图：布尔表达式每轮都会被重新求值一次。而这里的表达式是一个**函数调用**——每评估一次，就等于反复问计算机："字符串 s 的长度是多少？长度是多少？长度是多少？"它不会改变，无论怎样结果都一样。像着了魔一样。

怎么优化？把长度先存进变量，只算一次：

```c
for (int i = 0, n = strlen(s); i < n; i++)
```

这里我用了个语法技巧：想一次初始化多个变量（比如两个），可以都写在第一个分号之前。第 9 行里我声明了变量 `i` 并初始化为 0，同时声明了第二个同类型变量 `n`，设为 `strlen(s)` 的结果。字符串长度不变，变量值也不变，于是可以反复使用。

> **易错点**：这个"一次声明两个变量"的写法要求**所有初始化用同一种数据类型**，所以最好这种情况只需要整数；否则就得把 `n` 单独声明一次，就像我之前做的那样。

> **提示**：这个优化其实有点像个善意的谎言——现在的编译器非常智能，能识别出你在循环里反复调用 `strlen`，然后自动帮你把这个问题优化掉。但你可能根本没意识到它。这类问题应该靠你自己的观察发现并完全避免：省下的可能只是微秒，可一旦循环不是跑 3 次或 5 次，而是百万次、千万次，这些微秒、毫秒累积起来就非常显著了。

趁这里把两个常见疑问一起答掉：

**空格什么时候会被考虑？** 空格其实就是字符编号 32，它并没有什么特殊之处。它看起来隐形，但确实存在，和其他字符的处理方式完全一样，不需要任何特殊处理。

**那空字符呢？** 空字符同样不可见，但它很特殊——`printf`、`strlen` 这些函数会用它来标记字符串值的结束位置。

> **易错点**：`'\0'`（值为 0 的终止符）和 `'
'`（换行符）完全不是一回事，`get_string` 在你按下回车时自动补上的那个，是前者。

### 把小写变大写：ASCII 码上的算术

接下来用 `uppercase.c` 做一件很具体的事：把用户输入的字符串转成大写，看怎么从"能用"优化到"更好"再到"最佳"。

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    string s = get_string("Input a string: ");
    printf("output:  ");

    for (int i = 0, n = strlen(s); i < n; i++)
    {
        // if lowercase
        if (s[i] >= 'a' && s[i] <= 'z')
        {
            printf("%c", s[i] - 32);
        }
        // else if not lower case
        else
        {
            printf("%c", s[i]);
        }
    }

    printf("\n");
}
```

先看那个判断。字符用单引号表示；从第 0 周的 ASCII 码表我们就知道，码表里既有代表大写字母的数字，也有代表小写字母的数字，而且小写字母 `a` 的编码是 97，之后所有小写字母连续排列。所以我们可以像之前一样把字符当整数、把整数当字符，从而提出一个数学问题：`s[i]` 是否落在 `'a'` 到 `'z'` 之间（含两端）？这可以说是一种非常巧妙的方式来表达"它是否为小写字母"。

如果它确实是小写，我们想把它转成大写。这里有个小技巧：直接做数学运算，把 `s[i]` 减去某个值。这个值是多少？回想第 0 周那张 ASCII 码表，重点看大小写两段——所有大写字母和小写字母之间的差值是 **32**，而且小写字母的数值更大，所以这个结论完全合理。把小写字母的数值减去 32，立刻就得到对应的大写字母。

至于 `else` 分支：不是小写字母就原样输出，不做任何数学运算，我会用一条注释把这个逻辑写清楚。

跑 `make uppercase` 看看。输入全小写的名字，输出已经是全大写了。这里其实有几个错误需要处理——格式间距、"output" 后面是不是还该再空一格、以及程序末尾应该补一个换行符。调整之后重新运行：输入 `DAVID`，全部被转成 uppercase；再输入首字母大写的名字，其他字母也照样被转成大写。

这算是个小技巧，但确实有点繁琐，对吧？像 Microsoft Word 和 Google Docs 那样，它们都具备切换大小写的功能，可以来回转换。明明看起来这么简单、这么常见的一个功能，却要写这么多代码，确实有点烦人。

### 让库函数替你干活：ctype.h

不过其实有更好的办法。除了字符串库之外，C 语言还提供了字符类型库：`ctype.h`，里面有一大堆与字符处理相关的实用函数——顺便说一句，这些函数在人工智能领域也很有用。

引入它，我们就可以自己验证那些条件。在新版本里，那些虽然巧妙却相当冗长的数学运算全都不需要了：调用 `islower` 传入 `s[i]`，返回真就转换；转换仍然需要减去 32，但你知道吗，我甚至不需要在脑子里或代码里做这个计算——`ctype.h` 里还有另一个函数 `toupper`，接收 `s[i]` 这样的字符，让别人的函数来替我完成转换。

再往深一层翻文档，你会发现可以对**任何**字符直接用这个函数，它非常智能：只有字符确实是小写时才做转换，如果是大写字母就直接原样返回。这意味着我连 `else` 分支都可以整个去掉：

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>
#include <ctype.h>

int main(void)
{
    string s = get_string("Input a string: ");
    printf("output:  ");

    for (int i = 0, n = strlen(s); i < n; i++)
    {
        printf("%c", toupper(s[i]));
    }

    printf("\n");
}
```

清屏、`make uppercase`、输入 `DAVID`，一切正常。

所以很多年前就有人写过那段"检查字符是否在 a 到 z 之间"的条件代码；现在你查文档，就会发现连判断都不必自己写了。这再次说明：**如果你觉得编码变得繁琐，或者你在解决一个很可能别人已经解决过的问题，那很可能确实存在现成的解决方案**——无论是 CS50 库还是标准库。

> **注意**：CS50 库是 CS50 特有的，这也是为什么 Clang 需要知道 `-lcs50` 这个参数；而像字符串库、`ctype.h` 这类标准库则是自动生效的，你不需要额外写链接参数。Make 工具已经把这些步骤全配置好了。

### main 为什么必须长这样

在最后几分钟里，我们来揭示一些关于 `main` 函数一直避而不谈的细节。第一周我就让你们先相信这些写法：必须用 `void`，必须用 `int`，等等。现在看看背后的原因。

`main` 之所以特殊，是因为在 C 语言中，它是唯一一个在你编译并运行代码后会被**自动调用**的函数。并非所有编程语言都标准化了这个函数名，但 C、C++、Java 以及其他一些语言确实这样做。而 `int main(void)` 就是 `main` 最标准、最简单的形式。

括号里的 `void` 是什么意思？它表示 `main`（以及我们到目前为止编写的所有程序）不接受任何参数——不接收命令行参数。从 "hello" 到 "scores"，每一个程序都是如此。在课堂上写程序时，我从没在程序名后面输入过任何其他内容，就是这个原因。

不过 C 语言里 `main` 还支持另一种语法，看起来复杂一点，实际含义只是：它可以接受零个参数，也可以接受两个参数。如果接受两个，那么第一个参数是一个整数，第二个参数是一个字符串数组。按照惯例，这两个输入参数通常叫 `argc` 和 `argv`——`argc` 是参数个数，`argv` 是参数向量，也就是实际输入的字符串数组。

### 命令行参数：argc 与 argv

有了数组这套工具，我们现在可以写真正支持命令行参数的程序了。建一个 `greet.c`，先按老样子用 `get_string` 问名字、用 `printf` 打印"你好，%s"，和上周的程序完全一样：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string name = get_string("What's your name? ");
    printf("hello, %s\n", name);
}
```

运行后，屏幕上提示输入名字——注意，**我没有使用任何命令行参数**，运行的唯一命令就是 `greet`，后面没有其他单词。

现在我们把这个机制倒过来用：让用户在运行程序时就把名字写在命令行上，省去提示输入这一步。改动其实只有一处——把 `main` 的头换成另一种写法，然后直接打印 `argv[1]`：

```c
#include <cs50.h>
#include <stdio.h>

int main(int argc, string argv[])
{
    if (argc == 2)
    {
        printf("hello, %s\n", argv[1]);
    }
    else
    {
        printf("hello, world\n");
    }
}
```

> **易错点**：这里一定要保留 `#include <cs50.h>`。字符串类型 `string` 正是在 CS50 库中定义的，第 4 周我们才会真正删掉那一行，并向大家展示 `string` 的实际定义。（顺便重申：字符串是一个专业术语，但它并不是 C 语言的关键字。）

顺带也把之前不小心犯的错纠正一下：中途我删掉了 CS50 库就急着 `make`，结果编译不过——原因就是它。字符串是一个专业术语，但不是 C 的关键字，这个我们过几周就会明白它真正的含义。

现在 `make greet`，然后在提示符后输入自己的真实姓名，按回车，屏幕上就出现"你好，David"。改成 `greet Kelly` 再回车，就是"你好，Kelly"。但如果只输入 `greet` 然后回车，会看到"你好，null"。

这里的 `null` 和前面说的 NUL（空字符）**不是一回事**：这是 `NULL`，空指针，区别我们以后再详细解释。不过显然 `printf` 已经察觉到异常了——那里本来就没有任何单词。

那为什么要写 `argv[1]`？因为这里有个 C 语言的特性：如果你重新编译并输入 `./greet` 而不加任何其他内容，会看到一件挺有意思的事——屏幕上是"你好，./greet"。因为 **`argv[0]` 会自动包含程序自身的名称**。

这有什么实际用处？当你需要程序自引用的时候很有用：比如显示"感谢运行本程序"，或者展示一段使用说明，而说明里需要包含程序名——无论文件实际叫什么名字，你都可以直接用 `argv[0]`，它始终保存着当前程序的名称。

至于空值问题，现在有几招了。既然 `argc` 记录的是命令行里单词的总数，那就可以先检查：如果 `argc == 2`，就继续执行并打印名字；否则就设置一个默认处理方式——比如输出 "hello, world"，或者干脆什么都不打印。上面那段代码就是这么做出来的，现在这个版本变得更聪明了：`./greet David` 完全按预期执行；如果忘了输入名字、只跑 `./greet`，程序输出 "hello, world"；甚至输入 `David Malan` 也会被忽略，因为此时参数数量不再是 2 了——变成了 3 个。

```text
命令行：   ./greet   David
            ↑         ↑
            argv[0]   argv[1]   argc = 2
```

读图：位置 0 永远留给程序自己，从位置 1 开始才是用户输入的单词；数一数总共有几个，就得到 `argc`。

至于"为什么会有这个信息"，答案很简单：**因为 C 语言的定义就是如此**。查阅 C 语言的官方文档，你会发现 `main` 有两种定义方式，一种用 `void` 表示不接受参数，另一种明确指定它可以接收两个参数；此时编译器和操作系统会确保当你提供命令行参数时，`argc` 和 `argv` 自动被赋予相应的值。这是语言设计者定的规则，我们只是遵循它的机制。你不能随意加参数——不能放 3 个，也不能放 4 个；你可以修改这些变量的**名字**，但它们的**类型**是固定的。

### 退出状态码：程序留下的暗号

`main` 还有一个最后的特点：它实际返回的值。到目前为止，我写的每个程序都从 `main` 开始，却从没用过它返回什么。

严格来说，`main` 返回的值叫**退出状态码（exit status）**，是一个表示程序成功还是失败的数值状态。在计算机的世界里，数字无处不在。举个例子，这是 Zoom 的一张截图，当 Zoom 出问题——比如网络连接不佳——你可能会看到一个错误代码，比如 1132。这对普通人毫无意义，除非你去搜一搜或查文档；但对写这段代码的工程师来说意义重大，因为他们知道 1132 对应某个特定错误，很可能还有一张表专门把这些代码翻译成人话。坦白说，在更理想的情况下，他们应该直接告诉你问题出在哪，而不是只让你报一个数字。

这个你可能很熟悉：**404**，文件未找到，一个表示出错的数字代码。退出状态码虽然不完全等同于这类错误码，本质上是类似的东西。在 `main` 里你可以返回 0、1、2 或者其他数字，用来表示程序是否成功。按照惯例，一切顺利时返回 0。于是你就有上百种可能的错误情况可以表示：1 表示一种错误，2 表示另一种，3 表示又一种——只要你有张表或备忘单记录，程序员就能知道每个码对应什么。

实际怎么做？写一个 `status.c`：

```c
#include <cs50.h>
#include <stdio.h>

int main(int argc, string argv[])
{
    if (argc != 2)
    {
        printf("Missing command-line argument\n");
        return 1;
    }
    else
    {
        printf("hello, %s\n", argv[1]);
        return 0;
    }
}
```

这次我不设 "hello, world" 那种默认值了，直接告诉用户他们没有正确使用我的程序。为了表示出错，返回 `1`——返回值也可以是 2 或 3，但这是第一个可能出现的错误，先从简单的 1 开始。反过来，如果 `argc` 确实等于 2，就打印 `argv[1]`，然后 `return 0` 告诉计算机和操作系统：程序成功执行了。

怎么看到它？在终端里运行完程序后输入下面这条命令（助教平时就是这么干的）：

```bash
./status David
echo $?
```

输出 "hello David"，`echo $?` 显示 0。再跑一次 `./status`，这次不输入名字，会看到"缺少命令行参数"——`echo $?` 这时显示 1。

> **结论**：0 表示成功，任何其他值表示出错。即使只学了一周的 CS50，如果你好奇 check50 如何判断你的代码写对了没有，其中一种方式就是检查这个半隐藏的状态码。它也不算秘密，只是对普通用户没什么启发意义。

### caesar：命令行参数玩出花样

命令行参数其实无处不在。刚才跳过的那个程序原本接受命令行参数，接下来这个没有学术价值，但计算机圈里相当有名，多年来一直存在于各种系统中——`caesar`。

```bash
caesar moo          # 输出一头说着 "moo" 的小奶牛
caesar -f duck       # 换成一只说着 "quack" 的小鸭子
caesar dragon -r     # 再换一只张牙舞爪的龙
```

它不仅接受你想让它说出的文字，还接受你希望它呈现的外观——先是 moo，然后我把参数改成 `-f duck`，屏幕上换成一只说着 "quack" 的小鸭子（顺带说一句，刚才那句显示成 "mu" 其实是我自己敲错了）。

这里没什么学术价值，就是玩玩各种选项。但我们不妨想想 CS50 到底是怎么实现它的：有人用 C 语言写了代码，通过 `argc` 和 `argv` 拿到参数值，然后判断——如果第一个参数是 `dragon`，就打印龙的图形；否则如果是 `duck`，就打印另一个图形。归根结底用的还是第 0 周讲的那些基础概念：函数、条件、循环、布尔表达式，只不过现在这些基础元素被组合成了越来越有趣的东西。

### 预告密码学：明文、密文与凯撒密码

最后，为了形成完整的闭环，本周我们还会探讨另一个有趣的主题：**密码学**——一门通过打乱信息来实现安全通信的艺术。如今它至关重要，密码、信用卡号、你可能想发出去的个人信息，都离不开它。我们会通过代码带大家实现一些加密算法。

思路其实都基于同一个模型：你有一段想发出去的消息，需要以某种方式加密或编码，确保没人能看懂——把**明文**（人类可读的英文或其他语言）转换成**密文**。但你不能只把明文丢进算法就得到密文，因为加密通常需要一个**密钥**。

打个比方。如果我要给后面的人发消息，完全可以事先约定一个规则：每个 A 改成 B，每个 B 改成 C，每个 C 改成 D，Z 则绕回 A。这方法一点都不复杂，但哪个中学老师会在截获课堂上传递的纸条后，花时间去破解它呢？——可这确实预设了双方有一个共享的秘密。在这个例子里，秘密就是数字 1，因为我把每个字母都移动了一位。

具体怎么实现？拿 "HI" 这个词试一下，密钥是 1，我该发出的密文就是 "IJ"。

接收方看到纸上的 IJ，怎么知道我说的是什么呢？他会使用**相同的密钥，但做减法操作**：B 变回 A，C 变回 B，A 变回 Z，以此类推。这本质上就是把密钥从正 1 取反。

当然，用 -1 当密钥也不见得有多安全。密钥是 13 呢？在计算机领域，13 这个数字有特殊含义——**ROT 13**，一种被使用了很多年的算法，常见用途是避免剧透，比如让 Reddit 之类的网站把内容先转成乱码，你得花点功夫才能看到。同样是 13，你就不会得到 IJ，而是得到 UV，因为 U 和 V 分别距离 H 和 I 13 个位置；当然，点一下按钮或写几行代码就能还原。

不过我们仍然没有处理标点符号——你说得对，那或许有利有弊，但至少字母部分被加密了。也可以发一些更私人的内容，比如"我爱你"，加密后就是另一串字符。说到"稍微安全一点"，有人会提议用 ROT 26——不过这不对，为什么？因为结果完全一样：A 变成 A，B 变成 B，它其实整整绕了一圈，什么都没加密。

但更关键的是，这恰恰说明这种加密的强度究竟如何。站在攻击者的角度想：教室里的老师截获了那张纸条，他需要付出多少努力才能破解？他只需要把所有可能的密钥都试一遍——密钥 1、密钥 2、密钥 3……一直到 25，总有一个会成功；他能一眼看出自己猜中了，那就意味着这种密码并不安全。

我们讨论的这种做法在历史上被称为**凯撒密码**。根据传说，早期凯撒与将军们通信时就是这么干的——如果你是世界上第一个想出加密方法或这种特定密码的人，那么即便它并不复杂，只要其他人都不懂其中的原理，就几乎无关紧要。而如今，用 C 语言或任何其他语言实现它已经一点不难，谁都可以暴力破解它；所以今天我们很快会看到远比"旋转字母表"复杂得多的算法。

至于解密，其实只需把加密过程反过来操作即可：把这段密文里的所有字母往相反方向旋转一位（减一），就能读出今天的最后一行字。这里还有个小提示会揭示它——当时钟指向 4 点 15 分时，你就会明白。

他开始一个字母一个字母地往回退：T 变成 I，I 变成 H……

"我，是唯一觉得这有趣的人。"

最后落到屏幕上的那串字符，收尾正指着 CS50 自己。我们下次再见。
