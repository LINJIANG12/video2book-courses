## 第一个 C 程序：从拖拽拼图到命令行
> 对应块：BLK04 | 覆盖分集：P02上 | 块标题（分集名）：《C 语言起步：编译与命令行》

### 这套语法，你上周已经学过了

这是我们一起学习的第二周。上周我们泡在 Scratch 里——一款最终以图形化方式呈现的编程语言，代码像拼图一样拖拽，只有在逻辑上说得通的时候，这些模块才能相互拼接组合。很多人在中学甚至更早的时候就开始玩它了。

但对我们来说，Scratch 的价值不在于它本身，而在于它替我们装了一个思维模型：函数、返回值、参数、变量、循环、条件语句……这些基础结构今天会以另一种语法在 C 里反复出现，几周后我们学 Python 时还会再遇到一次，甚至在之后的学习中一直伴随着我们。

信息量确实大。MIT 有个传统叫"黑客恶作剧"（hacks），学生们每年都会搞些相当疯狂的活动：有一年他们碰巧把一个真正能用的饮水喷泉接到了消防栓上，旁边的告示牌像素感十足地写着——"在麻省理工学院接受教育，就像试图从消防水带里喝水一样。"

这确实就是计算机科学、编程，以及这门课有时会给人带来的感受。但请记住，最终最重要的并非你当前所处的位置，而是三个月后你相对于仅仅一周前——也就是所谓的"第零周"——所感受到的进步。

那么让我们回顾一下第零周时的情形：当时我们编写了一个最简单的程序，让那只小猫说出 "hello world"。今天，同样的代码会开始呈现出这样的面貌——这也是上周给大家展示过的一瞥，只不过这一次我特意用颜色做了编码，想传达这样一个信息：**我们仍然身处 Scratch 的世界**。那些淡黄色的拼图块负责启动程序，它本身并没有实际功能，真正的工作是由紫色部分完成的，里面的白色文本才是干活的东西。今天的情况也是如此，我会花一点时间讲解屏幕上这些淡黄色的代码，但真正起关键作用的还是那条紫色代码行以及其中的白色文本。

在接下来的几周里，我们会逐步解析这些代码行的具体含义；但有时候，如果某些细节在现阶段不那么必要，我们可能会暂时略过。现在我先把颜色标记去掉，大家会看到代码本质上就是这样的形式——这种用 C 语言编写的代码，从今天开始我们将在未来几周内逐步学习和使用它。

它代表了我们通常所说的**源代码**。源代码就是程序员编写的内容，是你们之前写过的那些东西，只不过以前是通过拖拽拼图块完成的。从本周开始，你们将更多地使用键盘，并开始编写源代码。

这些代码经过一些学习和练习后，我们人类就能理解。但机器能理解什么语言呢？根据上周的内容，计算机最终能理解的只有二进制的 0 和 1。虽然这些 0 和 1 很可能表示的是 "hello world"，但我们把机器实际使用的这种形式称为**机器码**。所以从今天开始，你和我都可以编写源代码，代码的形式大概像前面那样——虽然看起来可能有点神秘难懂，但肯定比一大串 0 和 1 要好得多。

### 从源代码到机器码，中间是编译器

上周我曾非常简短地提到过这一点，我们还是采用相同的思维模型：我们编写的源代码可以作为解决某个问题的输入，而我们希望从中得到的输出将是机器码。

今天我们会在这个众所周知的"黑箱"中，为你配备相应的工具。黑箱的核心是一个特殊的软件，它以源代码作为输入、生成机器码作为输出，这类程序被称为**编译器**。

```text
   hello.c                     make hello                   hello
   源代码    ───────────▶  ┌──────────────┐  ───────────▶  机器码
                        │    编译器     │                 （0 和 1）
                        └──────────────┘
```

读图：左边这段人能读懂的 C 代码，需要经过中间那道"翻译"工序，右边才是 CPU 真正能执行的比特。

世界上存在多种不同的编译器，我们将让你使用其中最流行的一款。它本质上是由他人编写的软件，只不过它的工作是实现不同语言之间的转换，例如把 C 语言写的源代码转换为机器码——那正是你的 Mac、PC、手机以及其他所有设备真正能够理解的语言。

### VS Code：一个图形界面里的命令行

正像我上周承诺的那样，本周我们会见到今年的新工具：Visual Studio Code，简称 VS Code，在业界非常受欢迎，可以说如今真正的程序员每天都在使用它。当然也存在其他替代选择——如果你们中有人之前有过编程经验，可能用过别的工具——但这一款确实非常常见，即使 CS50 课程结束后你也会经常见到它。

你可以免费在自己的 Mac 或 PC 上安装它，这样到课程结束时，你就完全可以独立于 CS50 以及任何与 CS50 相关的工具。不过在课程开始的时候，我们实际上已经为大家提供了一个基于云端的版本：你只需要在任意一台 Mac、PC 或类似设备上使用网页浏览器，所有软件都已预先安装并配置妥当，完全不必去处理那些烦人的技术问题。学期初就不必为技术支持问题头疼了，因为这套系统理应开箱即用；等到学期末，当你对编程更加得心应手时，你完全可以脱离这套工具，在自己的机器上安装一份几乎完全相同的开发环境，并且完全由你自己掌控。

从今天开始，你会经常看到一个类似这样的界面。我们将在右上方区域编写代码，那里可以存放一个或多个代码文件，以标签页的形式呈现。比如这里有一张截图，显示的是我们今天要创建的第一个文件，名为 `hello.c`——之所以这样命名，是因为它使用的是 C 语言，我们马上就会见识到，这可不是什么文字游戏。

代码恰好是彩色的，VS Code 和其他编程环境都具备这类功能，它叫**语法高亮**。你无需费心甚至不必在意这些颜色，但当你用某种已知语言编写代码时，工具会自动为代码的不同部分着色，让各种特性一目了然；今天我们会逐步了解这些特性具体指什么。

你也会花不少时间待在屏幕右下角这个所谓的终端窗口里，就像上周我简单演示的那样——这里将是你运行编译好的程序、以及编写命令的地方。左侧这里，你会看到我们逐步创建的文件和文件夹；最左侧是活动栏，它本质上是一种现代化的菜单形式，你可以通过它打开和关闭各种功能。就我的使用需求而言，我通常会把这两处都隐藏起来，这样当我们一起学习时，就能几乎完全专注于代码和命令。

另外你会逐渐感受到的一件事是：你将开始减少使用鼠标和点击操作，更多地使用键盘和打字操作。一开始减少使用那些"用户友好"的工具，可能会让人感觉像是退步，但事实上，大多数程序员最终都会发现，比起传统的鼠标或触控板，更频繁、更快速地使用键盘能让他们效率更高、能力更强。

所以综上所述，这里其实只是一些术语。我在这里描述的整个集成环境通常被称为**图形用户界面**——它本质上以图形方式呈现，包含图标、按钮等元素，简写是 GUI。但正如之前提到的，在这个图形界面里，右下角会有一个终端窗口，我们将在那里输入大部分命令，这通常被称为**命令行界面**，简称 CLI。简单来说，你是在那个界面中输入命令。计算机软件世界基本上就分为图形用户界面和命令行界面两类，有时一个软件可能同时具备这两种界面。

> **定义**：GUI 是靠图标、按钮等图形元素操作的用户界面；CLI 是靠输入命令操作的用户界面。VS Code 两样都有——窗口是 GUI，底部那个 `$` 是 CLI。

### 三条命令，跑通第一个程序

好了，我们直接开始。这是能写出的最简单的 C 程序，我们看看到底怎么编译并运行它。

我已经隐藏了带有所有图标的文件资源管理器，也隐藏了活动栏，现在我这里就只剩代码标签页和底部的命令提示符窗口了。我称之为"命令提示符"，因为我会在这个美元符号处运行一些命令——按照惯例它显示为 `$`，这与货币无关，只是计算机领域的一个惯例，表示"请在此处输入命令"。有些系统会使用脱字符号 `^`，有些则使用大于号 `>`，意思都一样。

第一个命令，我输入的是：

```text
code hello.c
```

中间有一个空格——我在文件名中没有使用任何空格，也没有做任何大写处理，这只是一个约定俗成的做法。不像在 Mac 或 PC 上你可能习惯使用空格和大写字母来命名文件，一般来说，只用小写字母且完全不使用空格，会让你的操作更简便。

按下回车，一个全新的标签页出现了，名为 `hello.c`，光标在首行闪烁——这就是 VS Code 在等待我输入代码的第一行。注意命令已经完整执行了，所以我在这里又得到了一个光标；如果我把终端窗口点击成前台，光标就会在那里闪烁，表示我准备好时可以输入下一个命令。

现在我们快速把代码写出来（我已经做过很多次了，所以可以打得相当快）：输入 `#include <stdio.h>`，然后写 `int main(void)`，接着在所谓的花括号内缩进 4 个空格，输入 `printf("hello world
");`——就这样，我用 C 语言写好了第一个程序。在这类课程里不需要把我写的每一行代码都记下来，课程网站上会提供我们所有内容的副本，课程笔记里也有摘录；当然欢迎你跟着我实时输入，但这并不是必须的。

> **结论**：这个程序里的三样东西各司其职——`#include <stdio.h>` 引入工具，`int main(void)` 是程序的入口，而 `printf` 才是真正干活的。

就在一个真实的 Mac 或 PC 上，如果我只做了这些，桌面上会出现一个可双击运行的程序图标。但因为我目前所处的编程环境结合了图形用户界面和命令行界面，我实际上需要点击终端窗口并首先**编译**这个程序——因为它目前仅以源代码的形式存在。为此，我将通过输入：

```text
make hello
```

来编译代码。（念出"空格"只是为了说明，实际上我只需要按下空格键。）这个写法其实暗示着某种含义：它将生成一个名为 `hello` 的程序。注意我并没有再次输入 `hello.c`，因为编译器——我们暂且称之为 Make，虽然这算是个善意的简化说法——会自动推断：如果我想生成名为 `hello` 的程序，它就会自动在当前目录中寻找名为 `hello.c` 的文件。所以这有点像魔法般便捷。

按下回车。值得注意的是，当你在执行这类命令后没有看到任何输出时，这通常反而是个好现象——一般来说，编译时看到输出信息，通常意味着操作出现了问题。这次我可能并没有出错，所以没有输出反而是好事。

现在我可以运行这个程序了。操作方式有点隐晦：不是通过双击或点击任何地方，而是直接输入 `./hello`（注意中间没有空格）。这听起来可能有点奇怪，但这里的斜杠表示：在刚刚生成名为 `hello` 的程序后，这个程序会保存在我当前的文件夹中。没错，它就在云端某个位置——稍后我们会详细讨论这一点。总之，这个名为 `hello` 的程序就存储在我当前文件夹的某个地方。

现在，就像我常做的那样，我会默默祈祷自己没有搞砸任何步骤。屏幕上确实打印出了 "Hello world"。

简单回顾一下这三条命令：`code hello.c` 是 VS Code 特有的操作，它创建一个名为 `hello.c` 的文件，之后我就可以用键盘开始编写代码了；`make hello` 把源代码编译成机器码；`./hello` 用来运行那个刚生成的程序。无论你给程序起什么名字，这种模式我们都将反复见到，所以即使你之前没做过类似的事情，很快也会觉得熟悉起来。

问答时间里有两个很关键的问题。

**输入 `make hello` 时，计算机怎么知道要把哪些代码分配给 hello 这个程序上？** 它实际上会读取 `hello.c` 文件的全部内容，并以某种方式将其转换为一个程序。

**文件名必须是 hello 吗？** 不必，你可以把它命名为 `goodbye`、`myfirstprogram` 或任何其他名称，只要相应地修改命令里的这些词即可。但它必须保持一致：文件名和代码中的引用需要匹配——你在那里改了文件名，就需要相应地调整命令。

### 从绿色旗帜到 printf

好了，让我们仔细分析一下刚才的操作，以及为什么这段代码会以这样的方式运行。回想一下，在 Scratch 中我们曾编写过这样的程序：当绿旗被点击时，在屏幕上显示 "hello world"。这次的对应关系是刻意设计出来的，就是为了帮助大家在脑海中建立一种思维模型——从上周开始我们沿用相同的概念，但从本周起我们将改变的是语法形式。

| Scratch 里 | C 里 |
| --- | --- |
| "当绿旗被点击"的触发帽 | `int main(void)`：启动程序，本身不产生输出 |
| 紫色积木里的白色椭圆：say "hello world" | `printf("hello, world
");` |

当我们在 C 里看到这样一个函数时，请记住：函数本质上就是一个动作或动词，它在代码中完成一小段工作。具体到 C 语言，你输入的不是紫色拼图块，而是单词 "print"——更准确地说，是 `printf`，其中的 "f" 代表 "format"，即格式化打印；它比单纯打印原始文本的功能更强大，所以严格说来它做的是"输出"。

接着，你可以使用左右括号来包裹内容。请注意，MIT 这样设计并非偶然——他们选择用椭圆形来表示函数的输入，是因为它大致看起来像括号的开头和结尾，也就是左右括号。那么，在对应的 C 代码中，括号里应该放什么呢？归根结底，至少得放 "hello, world"，因为这正是我们想要打印到屏幕上的内容。

但在 C 语言中，与 Scratch 不同，你需要一些额外的语法开销，必须处理这些细节，才能让计算机清楚地知道你想要打印什么：

- 你需要用双引号把要打印的内容括起来，以明确表明 "hello" 并不是某个特殊的函数、变量或其他东西——这里用双引号开头、那里用双引号结尾，表示这就是我要打印内容的起止范围；
- 你还会发现需要在结尾加上一个换行符 `
`，在大多数情况下要把它放在要打印的单词或语句的末尾；
- 最后，可能最让人头疼的是，你必须用分号来结束你的语句，就像英语中要用句号一样。

C 语言的关键恰恰在这里：如果你搞砸了我刚才提到的几乎任何一个细节，程序就会出问题。所以你并不孤单——你第一次尝试编写或编译程序时，很可能不会成功，因为你需要逐渐培养肌肉记忆，才能注意到所有这些看似微小、实际上也确实微小，但对计算机至关重要的细节。

如果你熟悉数学中的函数表示法，那么代码里的函数其实与数学中的函数概念是一样的：函数 $f$ 接收某个输入，比如 $x$，然后通常会产生一个输出。如果你有数学背景，会发现我们在这里做的事情大致相同。但在代码中请注意，我们可以有不同类型的输出——设想我们有一个函数，在它的黑盒内部，函数接收参数，也就是它的输入，有时可能会产生**副作用**。副作用通常是指由此产生的可见效果：它们可能显示在屏幕上，或者从扬声器中播放出来。这通常是一种短暂发生的事件，但它确实存在，只是不一定像我们稍后会提到的另一种函数（返回值）那样实用。上周我们回顾过，当输入是 "hello world" 时，我们让带有对话气泡的小猫出现在屏幕上，并在气泡中显示 "hello world"，而对应的函数是 `say`。

### 把 `
` 删掉试试：转义序列是怎么救场的

既然已经走到这里，让我们试着逐步分析一下我们编写的代码究竟在为我们做什么。我建议稍微分解一下这个程序——先把这个换行符删掉，毕竟乍一看，谁知道或者在意它在做什么呢？既然我们不明白它的作用，那就先把它去掉：

```c
#include <stdio.h>

int main(void)
{
    printf("hello world");
}
```

回到终端窗口，再次输入 `./hello` 并回车，看起来没有任何变化。很好，看起来我没有搞砸程序。但我刚才其实有点误导大家了——为什么看起来没有任何变化？因为我并没有重新编译它。回想一下，编译器的作用是把源代码转换为机器码，而我几分钟前已经编译过了；如果我修改了源代码，按理说我需要重新编译才能真正看到修改后的效果。

于是我执行 `make hello`，看起来一切正常；再运行 `./hello`，这次差异很细微，实际上让我放大一下看看——这基本上只是一个视觉上的小瑕疵。从功能上讲，程序在技术上仍然打印出了 "Hello world"，但看起来哪里不对劲呢？或者说，那个 `
` 到底起到了什么作用？——它确实起到了换行的作用：反斜杠 n 就表示在这里换行。

那我为什么要加上它呢？主要是为了视觉效果更美观。就好比美元符号代表我输入命令的提示符，如果程序运行结束后提示符还跟在输出内容的同一行，看起来会有点别扭。当然你也可以说那本来就是我的设计意图（虽然这次并不是），但这样显示确实显得不太对劲。

那有没有其他更好的处理方式呢？你在这里看到的实际上通常被称为**转义序列**——它们是一种特殊的符号组合，比如这里的反斜杠加 n，能实现一些不同寻常的效果：

| 转义序列 | 效果 |
| --- | --- |
| `
` | 把光标移动到新的一行 |
| `\r` | 回车符：把"打印头"移回左侧起始位置，是水平移动而非垂直移动 |
| `\"` | 输出一个双引号字符本身 |

`\r` 这个挺有意思的——如果你见过或用过老式打字机就知道它指的是把打印头移回左侧的过程。

那为什么会有 `\"` 这种模式呢？回想我们之前尝试打印的那句话 "hello, world"。如果出于某种原因你不想说 "hello world"，而是想带点讽刺意味地说 "hello \"world\"" 之类的话，那么你不能直接连续使用引号，然后指望计算机能分辨出哪个引号对应什么内容——这确实存在歧义。所以，如果你确实想在双引号内打印出实际的引号字符，就要用 `\"` 这个转义序列来告诉计算机：这不是用于界定我想法起止的引号，这本身就是一个双引号字符。我们还会遇到类似情况，比如单引号或撇号的处理方式也是一样的；还有一些更棘手的情形，比如你想打印一个反斜杠，但反斜杠本身已经有特殊含义——这些都有相应的解决方案，不过我们暂且不必深入探讨这些细节。

> **易错点**：如果你不知道有 `
` 这个转义序列，可能会本能地想通过直接按回车键把光标移到下一行，比如把双引号、括号和分号都挪到下一行去写。但这首先违背了大多数编程语言的一项基本原则——大多数语言都是**基于行的**，你基本上是在一行内开始并完成一个完整的逻辑表达，理想情况下一个完整的语句应该写在同一行内；其次，即使你是第一次看代码，把一句话的一部分硬挪到下一行，看起来也会显得很马虎，事实上也确实如此。

所以 C 语言和许多其他编程语言（包括 Python 在内）通过引入转义序列来解决这个问题：如果你需要在某个位置换行，只需输入反斜杠加 n，就能在那里实现换行效果。不过我之前说得可能有点绝对了——实际上有时代码行确实会很长，以至于不得不折行显示，但通常来说我们会尽量避免这种情况，这是一种约定俗成的编程习惯。

另外，养成一个随手清屏的习惯吧：可以按 `Ctrl+L` 快捷键，或者直接输入 `clear` 命令。虽然这并不影响程序功能，但我经常会这么做，只是为了保持屏幕整洁。

### 让编译器骂你一次

好的，还有哪些可能出问题的地方呢？让我们来看看这个例子——先清空终端窗口，然后假设我忘了写完代码，漏掉了分号，除此之外代码是完美的。现在执行 `make hello`，回车。

我们不会立刻回到命令提示符，因为这里出现了一条错误信息，它的长度几乎和我尝试编写的代码一样长。别担心，让我拆开看看它到底在说什么：

```text
  hello.c        出错的是哪个文件，很自然地就是它
      5           第 5 行，正好对应着编辑器里的那一行
      29          第 29 个字符
   ^              一个小小的脱字符号，正指向出错的位置
```

读图：错误信息由文件名、行号、列号和一个指向嫌疑位置的脱字符号组成。消息本身明确指出"表达式后应输入分号"。从左往右数到第 29 个字符附近，肯定有什么地方不对劲，或者漏掉了什么。

所以这个错误信息提示得相当清楚。它也再次体现了编译器的实用价值：它不仅懂得如何将源代码转换为机器码，还非常擅长发现代码中的错误，并试图引导你注意到这些问题。

那该怎么修复呢？关键点在于，你只需要回到代码中加上那个分号。清屏，重新 `make hello`，程序恢复正常；执行 `./hello`，屏幕上又显示出了 "Hello world"。

那我们再来制造一个错误。假设我忘了在代码开头加上这一行——这种情况大家偶尔会遇到，下周我们会更清楚地理解这行代码的作用。现在直接省略它开始写代码，你可能会觉得这样就够了，只是打印出 "Hello world"。再次运行 `make hello`，这次我会看到一个**完全不同的**错误信息。

问题仍然出在 `hello.c` 文件上，这说得通。第 3 行——好吧，看来问题出在 `printf` 这里，尽管分号和换行符都已经加回去了。错误信息说：**调用了未声明的库函数 `printf`**，其类型为……后面跟着一长串复杂的描述。

这是一个错误信息的例子：除非你已经习惯了理解它的含义——并且之前见过——否则它确实相当晦涩难懂，让人不清楚问题的解决方案是什么，尤其是当代码的其他部分实际上都正确的时候。我只是忘了某个很基础的东西，但我该怎么思考这个问题呢？

### 头文件：把别人写好的代码借进来

C 语言的另一个特点是它附带了一系列头文件，这些文件的扩展名不是 `.c` 而是 `.h`。这些所谓的头文件包含了他人编写的代码，可以在自己的程序中直接使用。

例如在这个具体案例中，头文件让我们能够访问更广泛的功能。在计算机领域，这被称为**库**：库就是他人编写的代码，你可以直接使用。实际上，我上周在导入代码行并提到 OpenAI 这家公司时，就已经用到了一个库——我提前在编程环境中自动下载并安装了该公司提供的库，因为如果不借助他们的成果、不使用他们编写的大量代码，我自己并不知道如何实现一个聊天机器人。

这里的原理完全一样。虽然 `printf` 是 C 语言的功能，但如果你想使用它，就必须通过包含头文件的方式告诉程序要引入对应的库。这个函数的具体定义，你只能通过学习、查阅书籍或参考文档才能了解。

在这个例子中，我想使用一个名为 `stdio.h` 的头文件——**不是** `studio.h`，如果你发现自己输入了 studio，这是网上非常常见的一个错误。它实际上是 `stdio.h`（标准输入输出头文件），而 `printf` 函数正是在这个文件中定义的。

所以，回到代码，解决问题的办法其实就是撤销我刚才的删除操作。因为现在第一行代码的作用是告诉编译器：请从另一个名为 `stdio.h` 的文件中包含 `printf` 的定义。这一点并不显而易见，但这类问题通常很快就能查到。

### 字符串、变量与类型

我们先具体来看其中一个函数：`get_string`。

在编程术语中，**字符串**指的是文本，即零个或多个字符组成的文本，比如 H E L L O W O R L D。在计算机术语中，这是一段文本字符串——它显然不是像 50 这样的数字，而是你可以在键盘上输入的实际文本。接下来我们还会看看需要获取哪些其他类型的数据，但首先从字符串开始。

这个函数可以帮我们快速复现上周在 Scratch 中实现的另一个程序，那个程序其实更具交互性：我用了另一个蓝色的积木——"询问"——来获取用户的输入。回想一下，与今天的 `printf` 以及上周用过的那个相同的积木不同，这次我们仍然遵循相同的输入输出模型；但如果我们向即将介绍的函数传递参数，有时你不仅能得到副作用，还能获得**返回值**——比如一个有用且可重复使用的值，就像我们马上会看到的那个名字。

在 C 语言中，最接近的类比是 CS50 库中的一个函数，叫做 `get_string`——C 语言本身并没有内置这样的函数，我们特意将它命名为 `get_string`，就是为了让它能清楚地表达其功能：

```c
string answer = get_string("你叫什么名字？ ");
```

我们一行一行拆开看。在 Scratch 里，"询问 [你叫什么名字？] 并等待"这个积木里也有一个参数——"并等待"的意思是它会一直等到用户输入完毕。翻到 C 这一边，括号里放提示语，跟 `printf` 里放字符串一模一样：用双引号括起来，表明这不是特殊的独立单词，而是一句完整的、希望显示给用户看的话。末尾那个空格是为了美观——我希望用户看到问题，同时光标留在那里闪烁等他输入，但我不想让光标紧挨着问号，所以特意留了一个空格把它稍微挪开，至少在我眼里是这样。

那用户输入的值放到哪里去呢？在 Scratch 里，那个变量直接被定义为 `answer`，而且你无法重命名它。在 C 里则不同：如果你想保留函数的返回值，直接使用等号即可，然后在等号左边写上你想用来存放返回值的变量名。数学里我们通常用 X、Y 和 Z 作为变量，同样在编程中——就像在 Scratch 里一样——你可以随意为变量命名；按照惯例，变量名通常使用小写字母、不包含空格，这和文件名类似。

不过，C 语言在这方面要求更精确一些：你不能只给变量起个名字就完事，你需要告诉编译器，你打算在这个变量里存放**什么类型**的值。如果是文本字符串，你就用 `string` 类型；如果是数字，就得用其他类型。就目前这个函数而言，根据函数名来看，它会返回一个字符串。

然后别忘了最后还得用分号来结束这个语句。

如果你已经有点明白了——这也是我们为什么从 Scratch 开始教学的原因之一——你很快就能建立起直觉。虽然右边的内容本身并不特别难，但就是有这些琐碎的小细节需要你慢慢内化。在这个例子里，虽然针对的是 C 语言，但许多编程语言都会遵循类似的模式。而本课程的目标之一，恰恰是展示编程语言最终是如何演进的：几周后我们学习 Python 时就会看到，其中一些语法实际上已经消失了——因为随着时间推移，人类不断地改进，对这类老式语言的繁琐之处感到厌烦。明明我已经换行了，为什么还得加上一个分号？所以在 Python 这类语言中，我们会发现可以省去一些类似的功能。不过目前来说，关键是要记住这些语法规则分别用在什么地方。

### 从"你叫什么名字"到 hello David

接下来我们沿着把 Scratch 转换为 C 语言的思路，实际运用这段代码来实现一些功能。

我会保持文件名不变，但你们在 CS50 网站上会看到，我会为每个示例添加版本号，这样即使文件名没变，你们也能清楚地看到这些程序的演进过程。具体操作是：首先把原来那句 "Hello world" 删掉；这次我要在代码开头引入 CS50 库，头文件现在不是一个而是两个了；然后在花括号里，也就是我们即将称之为 `main` 函数的地方，输入和屏幕上之前显示完全相同的代码行。

顺便提一下，这行代码很快就会在屏幕上显示"你叫什么名字？"，这说明 `get_string` 函数内部实际上也调用了 `printf` 来输出这条提示信息。我不需要自己调用 `printf` 来在屏幕上显示那条消息，因为我查阅了 CS50 库中 `get_string` 函数的文档，知道它内部已经帮我调用了 `printf`。

现在来试一个看似直观但不太正确的做法。如果我想打印出这个答案，让输出的内容不是 "hello world" 而是 "hello David" 或 "hello Kelly"，我可以这样写：

```c
printf("hello answer");
```

这不太对劲，即使你从未编程过，或许也能看出这里出错了——从语法上看似乎没什么问题，但逻辑上不太对劲。我需要重新编译程序（源代码已修改，需要生成新的机器码），然后运行它：系统会先问"你叫什么名字？"，我输入 `David` 并回车，然后你会看到程序输出了 "hello answer"。计算机完全按照我写的指令执行了——我写的是"打印出 hello answer"，这显然不是我的本意。

那么该怎么解决？在 Scratch 中，我们通过堆叠积木块、或者说把它们嵌套起来，一个套一个。在 C 语言中不能直接这样操作，至少我们今天要讲的函数里没有对应的做法，所以我们得换个方式来处理。

告诉计算机先输出 "hello, "，然后留一个占位符，等知道名字后再填进去——因为在我写代码的时候，根本不知道谁会来玩这个游戏：是我、Kelly 还是其他人。那么，如果我们用特殊语法来标记出我想插入人名的地方呢？`%s` 是一个占位符，用于表示你在写代码时还不知道具体内容的字符串，但当其他人运行代码时，这个位置会被实际内容替换。所以 "hello %s" 是我们能最接近实现这个效果的方式。不过我仍然需要一些其他语法来实现这个功能：确实需要在左右两边加上引号，这样看起来更美观；我打算在末尾加一个换行符，让光标移到下一行。

现在我在括号里还留了一个位置，我应该在括号里传入什么作为第二个参数，好让 `printf` 知道那个"其他内容"具体是什么呢？是变量名，就是存储用户姓名的那个变量。通常的做法是：在引号后面加一个逗号，然后写上那个变量的名称，它的值会替换掉占位符：

```c
printf("hello, %s\n", answer);
```

现在请注意这里的语法和文法冲突：**引号内的逗号只是英语文本的一部分**，而**引号外的逗号是有实际意义的**，它区分了第一个输入（参数）和第二个输入（参数）。在 C 语言中我们之前还没遇到过这种情况——到目前为止我们只传递过一个参数，但实际上你可以传递 2 个、3 个甚至 4 个参数，这完全取决于函数设计时预期接收的参数数量。

整合起来：回到 VS Code，把 `answer` 从引号里挪出来（此前我们直接打印的是这个变量），在引号外面加上逗号和 `answer`。回到终端窗口清空屏幕，再运行一次 `make hello`，看起来运行成功了；执行 `./hello`，屏幕上打印出了 "hello, David"。

问答时间里还有几个问题，都值得记下来。

**这些头文件是从哪儿来的？** 你在这里看到的是一个图形用户界面，它部署在云端的 cs50.dev 上。这个软件运行在一台计算机上，而该计算机配备了硬盘驱动器（或者固态驱动器）；像 `cs50.h` 和 `stdio.h` 这样的头文件已经预先安装在服务器上，存储在标准路径中，以便编译器能够准确找到它们的位置。这些都是我们提前为大家准备好的。

**为什么反斜杠 n 不能创建新的一行？** 它确实打印了换行符，其效果是将美元符号推至下一行；否则美元符号将停留在倒数第二行。

**为什么这里没有换行符？** 这是我作为程序员的个人选择——我只是想看看这个句子的显示效果：用户（也就是我）能像这样紧接着问号输入名字，但我其实不必非得那样做，我只是想让你看看其中的区别。

**是不是总需要写开头那几行？** 今天请相信我，先照着做：写这行、写这行、写这行、再写这行，下周我们会更深入地理解这几行代码的作用。不过有一点需要注意：只有在使用我们提供的函数时，才需要包含 `cs50.h` 头文件；如果只是像第一个例子那样打印输出，你并不需要包含它。

**第一个输入和第二个输入都是"输入"吗？第二个输入是我作为用户输入的内容，但第一个输入对我来说并不太像"输入"，因为那只是程序提出的问题。** 总结来说：右侧这个输入实际上是由用户提供的，而第一个输入则是由我提供的。但它们都是输入，因为它们都被作为函数的输入参数提供——区别只在于来源不同。第一个输入我事先就知道，作为程序员，我知道我想向某人问好；第二个输入我无法事先确定，因此使用了一个占位符，也就是一个变量，来存储稍后调用 `get_string` 时将要获取的值。输入的来源完全取决于我想实现什么目标，但它们都是输入，只是使用方式不同。

### Linux，和那些短得不能再短的命令

既然我们已经完成了这一步，不妨回到刚才那个问题：这些文件到底在哪里？

实际上，尽管你们大多数人都在使用 Mac OS 或 Windows，但世界上还存在其他操作系统：手机有 iOS，iPad 有 iPadOS，Android 设备则运行 Android 系统，它本身就是一个独立的操作系统。

**操作系统**是设备上执行最基础操作的软件，比如开机、关机、发送内容到打印机、在屏幕上显示信息、管理窗口和图标等通用功能——这些功能也会被其他软件所使用。

在编程领域、云端服务器以及互联网世界中，有一个非常流行的操作系统叫 **Linux**，它是 Unix 系统的衍生版本。Unix 系统已经存在很长时间了，许多程序员——甚至可以说是大多数程序员——都会根据他们的工作环境选择使用它。由于 Linux 的性能非常出色，在运行此类操作系统的服务器上可以支持数以千万计的用户。它通常不依赖图形界面，但也可以支持图形界面，这意味着在需要时系统能够以更高效的方式运行；所有这些图形界面主要是为了便于人类使用，并非专为网页浏览器或其他设备设计。Linux 通常或经常以命令行界面的形式使用，它附带了一整套命令，随着时间的推移你会逐渐开始使用并熟悉它们。

到目前为止我已经用过一些命令了：`code` 命令，这是 VS Code 的功能；`make`，就今天而言它充当了我们的编译器，但这算是个善意的简化说法，下周我们会详细解析这一点；至于 `hello`——它其实不是一条命令，它是我们创建了一个名为 hello 的程序之后，自然而然就能运行的东西。

还有很多其他命令：

| 命令 | 作用 |
| --- | --- |
| `ls` | 列出当前文件夹中的内容 |
| `mkdir` | 创建一个新文件夹，也就是目录 |
| `rm` | 删除目录，或删除文件 |
| `mv` | 移动文件（重命名也用它） |
| `cp` | 复制文件 |
| `cd` | 切换目录，也就是进入另一个文件夹 |

读图：这就是 Linux 命令行速查表里最常用的一批命令。它们都短得不能再短——命令行界面的核心目的就是让人们能快速操作，这两个命令只需要花点时间和练习就能记住。

### 把文件夹理清楚

让我回到 VS Code，重新打开左侧的文件资源管理器。你的界面看起来会略有不同，你的用户 ID 会显示为不同的数字，但通常你会看到自己已经创建的文件和文件夹。

我今天创建的第一个文件叫 `hello.c`；接着通过使用 make 工具，我生成了第二个文件 `hello`。所以 hello 能运行，是因为确实存在一个名为 hello 的程序——它是在将源代码编译成机器码时生成的，就在我当前的文件夹里。

现在假设，对于问题集一以及未来的问题集，我希望将每个编写的程序都保存在单独的文件夹中，以便保持条理清晰，尤其在学期不断推进的过程中。假设这种情况很快就会变得混乱，因为我们在课堂上和习题集中创建的程序越多，这个主文件夹里的文件就会变得一团糟。那我们来创建一些子文件夹吧，就像你可能在 Mac、PC 或 Google Drive 等平台上习惯做的那样。

这可以通过多种方式实现：我可以在文件资源管理器上右键点击或按住 Ctrl 键点击，然后会看到一个有些熟悉的上下文菜单，可以直接选择新建文件夹、或者重命名文件、也可以通过拖放来移动它们。但今天让我们更专注于 CLI。

首先，让我删除机器码。这个例子就到这里，我不想把这些位数据毫无必要地保留在这里——注意，我要删除的是 `hello`，**不是** `hello.c` 文件，而是编译后的那个程序：

```text
$ rm hello
remove regular file 'hello'? Y
```

读图：`rm` 会先向你确认，输入 `Y` 即可。我按下 Y 键并回车，然后观察终端窗口左上角——文件已被删除，它消失了。我本可以右键点击或按住 Ctrl 键点击它来删除，但使用命令行界面也能达到同样的效果。

好，接下来我创建一个名为 `hello` 的新文件夹——所以，我并不想创建一个名为 hello 的程序，我想创建一个名为 hello 的文件夹。根据速查表，创建目录的方法是：

```text
$ mkdir hello
```

回车之后，左上角立刻多出一个带文件夹图标的新条目。

现在我可以走点捷径：点击并拖动 `hello.c`，直接把它拖进 hello 文件夹里。不过我们还是坚持使用命令行界面，用简写 `mv` 来移动文件：

```text
$ mv hello.c hello
```

这是第一个命令，我在命令后面输入的不是一个单词（比如 `code hello.c` 或 `make hello`），而是两个单词，因为 `mv` 命令的设计是：第一个单词指定源文件，第二个单词指定目标位置。

> **易错点**：你可以在目标路径的末尾加上一个斜杠 `mv hello.c hello/`，这样就能明确表示你想把文件放进一个文件夹里，而不是把 `hello.c` 重命名为 `hello`。不过因为 hello 文件夹已经存在，不加斜杠通常也能被正确识别——Linux 知道你想做什么，它会自动判断你的意图。

注意看左上角的变化：`hello.c` 看起来好像消失了，但点击这个小三角，啊，它就在里面，现在已经移动到那个文件夹里了。

现在我给自己做个预测：先清空终端窗口，然后输入 `ls`——你会看到只有一个名为 `hello` 的文件夹。为了让它更醒目，系统用颜色进行了高亮显示，并且末尾还带有一个斜杠，这样就能清楚地表明它是一个文件夹。这些都是由 Linux 操作系统自动为你完成的。

等等——我那个 hello 程序去哪儿了？那 `hello.c` 文件去哪儿了？原来它在那个文件夹里。所以我需要进入那个文件夹（或者说目录）。根据速查表，我们可以使用 `cd` 命令来进入目录：

```text
$ cd hello
```

现在你会看到这个提示符——虽然看起来有点隐晦，但我的命令提示符已经变了：虽然还是以美元符号结尾，但前面会一直显示我当前所在的文件夹路径，提醒我身处哪个目录。我们把这个作为约定俗成的惯例来使用，很多系统也采用类似的做法，只是格式上可能略有不同。这样你就能随时知道自己当前在哪个目录，而不需要额外输入命令去询问操作系统。

那么，现在我在这里，如果输入 `ls` 并回车，应该会看到什么？只有 `hello.c` 文件，因为这是该文件夹里唯一的内容。

在这个文件夹里执行 `make hello` 命令，没问题——注意左上角刚刚发生了什么变化，两个文件都恢复回来了。

好的，假设我想删除其中一个文件，我可以再次使用 `rm hello` 命令。

### 删掉又后悔：Linux 里的搬家、复制与删除

先从一个我亲手制造的小混乱说起。我把这个文件夹里的东西删了个干净，输入 `Y` 确认删除原因，屏幕又回到了刚才的样子。然后我盯着这个版本的 `hello.c`，不太满意——不，是相当不满意。

留着它，但改个名字吧。于是 `mv hello.c old.c`。你只需要记住这一件事：`mv` 命令不只是把文件从一个位置搬到另一个位置，当你对同一个目录里的两个文件名使用它时，它就直接替你完成了重命名。**你并不需要一条专门的 `rename` 命令。**

结果刚改完名我就后悔了——这个程序其实没问题。于是 `mv old.c hello.c`，文件名又变回来了，左上角的显示跟着刷新。

不过稳妥起见，我还是得留个备份。`cp hello.c backup.c`——"以防万一我把事情搞砸了，我得留个备份以防万一"。现在左上角两个文件都在那儿了，`ls` 一敲，两个都列出来。所以图形界面里发生的事情，和命令行界面里发生的完全一样；说实话，这一整段只是演示而已。

既然是演示，我把备份文件也删了。接下来是把 `hello.c` 移出这个文件夹。直接拖拽当然可以，但怎么"移到所谓的父文件夹里去"？`mv hello.c ../`。

> **提示**：`.` 是一个特殊表示法，指的就是所谓的**当前文件夹**；`..` 表示**向上移动一级**。没有三个点、四个点这种表示法，要实现更复杂的路径得用别的语法，这个我们以后再详细讨论。

注意左上角的缩进变了——它已经不在原来的文件夹里了。

那怎么回来？如果遇到不确定的情况，或者不小心把自己绕晕了，只要输入 `cd` 然后直接按回车，你就能神奇地回到默认文件夹，也就是你的主目录。不过严格来说，这其实也算是个善意的谎言——主目录本身也是一个文件夹。这操作就是把你带回主目录。你每次登录 CS50.dev（也就是 VS Code）时都是从这里开始的。

最后 `rm hello`，把之前所有的操作彻底撤销，我们又回到了故事开始的地方。

重点在于：**通过这些基础而核心的命令，你就能完成多年来在 Mac 和 PC 上用鼠标习以为常的所有操作。**

目录长这样——左边是刚编译完的样子，右边是搬走之后：

```text
~/pset3/
└── hello/                 ← 文件夹
    ├── hello.c            ← 源码
    └── hello              ← make 编译出来的可执行程序

~/pset3/

│   └── hello              ← 可执行程序还在
```

#### 同一个名字的麻烦

有人问：文件夹里有 5 个不同的文件，该怎么选择打开哪一个？

当然，你可以输入 `code` 加空格，再跟上你想打开的文件名。或者我们还会看到其他技巧，比如用星号 `*` 作为所谓的"通配符"，一次性打开这个文件夹里的所有文件；你甚至可以使用比这更精确的匹配模式。等到手头的文件越来越多，我也能用上这类技巧。

更妙的是另一个问题。刚才在 VS Code 里操作时，其中一步是进入了 Hello 文件夹——为了方便演示，我之前把 `hello.c` 就放在了这里面。接着我运行了 `make hello` 重新编译它。

这个例子确实有点容易混淆，我是故意这样设计的：我有一个名为 `hello.c` 的文件，它放在了一个同样叫 `hello` 的文件夹里；由于我编译了 `hello.c`，所以同时又生成了一个名为 `hello` 的可执行程序，那个可执行程序就在这个文件夹里，而这个文件夹本身也叫 `hello`。这其实是想说明：**你完全可以这样做，但不能在同一个位置让文件和文件夹重名**，因为那会产生冲突。在 Mac 或 PC 上你同样无法这样做。名称必须唯一，但把一个文件夹放进另一个文件夹里就完全没问题了。

### 条件语句：程序里的岔路口

接下来我们介绍一些新的基础构件。编程语言还有很多其他功能，我们在 Scratch 里已经见过一些，现在要把它们对应到 C 语言。

条件语句就像是传说中的**岔路口**，让你能根据一个问题的答案——也就是所谓的**布尔表达式**——来决定执行这个、那个还是其他操作。

在 Scratch 里，你可以拖出一个橙色的积木，写上"如果 X 小于 Y"。假设我们已经创建了变量 X 和 Y，并给它们赋了某些值（具体是什么值并不重要，幻灯片里只放了条件判断这一部分）。

在 C 语言中，实现相同功能的写法是：先写 `if`，加一个空格，然后跟一对圆括号。

> **注意**：这里这对括号和函数调用毫无关系。`if` 并不是函数，而是 C 语言中实现条件语句的关键字——就像 Scratch 里的橙色积木块一样，它是语言本身的功能特性。

在圆括号里，你放入同样的布尔表达式。假设我在上面已经定义了变量 X 和 Y，我完全可以在条件语句中使用它们，并且可以像数学课上那样使用小于运算符来提出这个问题。虽然用的是小于号，但它的结果实际上是一个布尔值——**要么是真，要么是假，也就是"是"或"否"。要么小于，要么不小于。**

在必须使用的花括号内，我直接写上代码。老朋友 `printf`，这里除了新内容 "X is less than Y" 以及换行符、分号和括号外，没什么特别之处。这是有意为之的，就像在 Scratch 中一样，那个"说"语句有点缩进，并且被橙色的"如果"积木包裹着。

> **提示**：顺便提一下，在 C 语言中花括号并非总是必需的。如果只有一行代码，从技术上讲你可以省略花括号。不过在 C 中、尤其是在 CS 150 这样的课程里，我们通常会提倡一种特定的编码风格——就像现实世界中任何一家公司所做的那样，这样协作编程的开发人员才能写出风格一致的代码，避免因为每个人都有自己的习惯而导致代码变得混乱不堪。所以这确实是你应该遵循的编码规范。

我缩进了 4 个空格，以便在逻辑上清晰地表明：这行代码仅在满足条件——也就是为"真"——的情况下才会执行。

在 Scratch 中，if-else 就像一条分岔路：如果 X 小于 Y，就执行相应操作；否则执行 X 不小于 Y 时的操作。在 C 语言中就是 `if` 加上 `else`，花括号之间写两个不同的 `printf` 就行。唯一的新内容是 `else` 和另一对花括号——它们就像我们用两个橙色形状包裹住那两个紫色积木一样。

#### 三条路，其实只需要问两个问题

我们来看一个稍微复杂一点的例子。它之所以看起来一下子变复杂，只是因为 Scratch 的积木太大了：如果 X 小于 Y，就说 X 小于 Y；否则，如果 X 大于 Y，就说 X 大于 Y；否则，如果 X 等于 Y，就说 X 等于 Y。

C 里的思路几乎一样，而且在我们揭示花括号里的内容之前，需要先说明一点：**这里用的正是那个我们已经见过的单个等号**——就像之前把 `get_string` 的返回值存储到变量中那样。

等等，几十年前程序员们就决定了：当需要把右侧的返回值复制到左侧的变量中时，使用等号在视觉上显得很合理，因为你最终希望这两者相等——尽管代码的阅读方向是从右到左的。我只能想象当时同一批人聚在一起设计条件语句语法，然后突然意识到："哎呀，我们已经用等号来表示赋值了。"那我们该用什么符号表示相等呢？在 C 以及许多其他编程语言中，解决方案就是——**两个等号**。

花括号里的内容没什么特别，就是一堆 `printf`。但这里不仅有机会对比 Scratch 与 C 的等效代码，还揭示了一个上周短暂讨论过的设计疏漏。

虽然这段代码功能正确，但从设计角度来看确实存在优化空间：**我们其实不需要第三个布尔表达式**。从逻辑上讲，如果我们使用常规数字进行比较，结果要么小于、要么大于，否则默认就是等于。问这第三个问题，只是在浪费计算机的时间，进而也浪费了用户的时间。

所以稍微好一点的写法是，只保留一个默认情况，也就是所谓的 `else`：

```c
if (x < y)
{
    printf("X is less than Y\n");
}
else if (x > y)
{
    printf("X is greater than Y\n");
}
else
{
    printf("X is equal to Y\n");
}
```

如果逻辑上只有三种可能性，实际上你只需要检查其中两种即可。这只是一个微小的优化，但你可以想象，在代码中反复进行这样的优化会带来显著的累积效果。**能优化的代码就应该去优化，我们不应该浪费计算机或用户的时间。**

### 一个等号的历史误会

C 语言提供了丰富的运算符。为了让您能一览全貌，这里不仅列出了赋值、小于、大于和等于运算符，还包含其他一些常用运算符。

在 Microsoft Word 和 Google Docs 这类工具中，你也能直接输入大于号或小于号这类符号。但在 C（以及大多数编程语言）中，要输入"大于等于"或"小于等于"，实际上只需要连续按两次键盘上的对应按键：输入 `<=` 或 `>=` 就表达了"小于等于"或"大于等于"。

有人想猜一下感叹号加等号 `!=` 是什么意思吗？它通常被读作 "bang equals"——**不等于**。在编程中，感叹号通常表示对某个条件的否定或取反，所以你不希望它等于某个值，而是希望它不等于该值。

你可能会想，难道不应该是"不等于等于"吗？是的，但设计者是为了减少按键次数，所以这就是它的否定形式：尽管看起来不太像，它只用了两个字符而不是三个。

| 运算符 | 怎么读 | 含义 |
| --- | --- | --- |
| `=` | 等于 | 赋值：把右边的值复制到左边的变量里 |
| `==` | 等于 | 相等判断：两边是否相等 |
| `!=` | bang equals | 不等于 |
| `<` `<=` | 小于、小于等于 | 左边是否小于／不大于右边 |
| `>` `>=` | 大于、大于等于 | 左边是否大于／不小于右边 |

> **易错点**：在 Scratch 里，一个等号就表示相等判断，因为它是给儿童用的、没有这种混淆；但在 C 和大多数编程语言中，单个 `=` 是**赋值**，双等号 `==` 才是**相等**。这个纯粹是历史原因造成的，不是随手定的。

### C 里装得下哪些数

值得注意的是，在 C 语言中除了字符串（我们所说的文本字符串）之外，还有其他类型的数据——比如从用户获取或需要存储的数据。布尔变量只能取真或假两个值，仅此而已，这与布尔表达式密切相关：变量本身可以取真或假值。

字符类型不一样：它不像字符串那样包含多个字母或单词，而是指**单个字符**。与其他一些语言不同，C 语言确实区分了单个字符和多个字符。

浮点数，也就是带有小数点的数字，可以说是实数。如今浮点数通常使用总共 32 位来表示这些数字。这里的关键在于：32 位大约能表示多少个不同的数值呢？这是少数几个值得记住的数字之一，大约有 **40 亿**种可能。但根据数学课上的知识，世界上有多少个实数呢？无穷多个。看来，我们能在代码中表示的数字数量与实际存在的数字数量之间存在一个不匹配。

不过不必担心。如果你需要更高的精度、更多有效数字，可以把变量从浮点数升级为**双精度浮点数**，它使用 64 位，精度高得多，位数是原来的两倍。但这并没有从根本上解决问题，因为 64 位表示的数值仍然是有限的，而不是无限。今天课程的最后，我们会探讨这一限制在现实世界中会带来哪些实际影响。

除了浮点数，还有简单的整数：0、1、2 以及它们的负数。按照常规，计算机使用 32 位来表示整数，这意味着最大值是有限的：使用 `int` 类型，最大值大约是 40 亿；但如果你需要处理负数，范围会缩减到大约正负 20 亿，也就是你可以表示从负 20 亿到正 20 亿之间的整数——以现在的标准来看，这个范围并不算大。而 `long` 类型使用 64 位，能表示的范围要大得多，但它仍然是有限的。

| 类型 | 装的是什么 | 位数与范围 |
| --- | --- | --- |
| `bool` | 真 / 假 | 只有两个值 |
| `char` | 单个字符 | 不含多个字母或单词 |
| `float` | 浮点数（实数） | 32 位，约 40 亿种可能 |
| `double` | 双精度浮点数 | 64 位，精度翻倍，仍是有限值 |
| `int` | 整数 | 32 位，约 ±20 亿 |
| `long` | 长整型 | 64 位，范围大得多，但仍有限 |

除此之外还有其他数据类型可选。这些只是我们可以在程序中存储和操作的数据类型，但其中有一些现在就可以开始使用了。

### 从 CS50.h 到 printf：拿到值，再打印出来

这些类型中有一部分需要从用户那里获取，而其中一些——特别是来自 `CS50.h` 头文件的那些——现在就能用。在你的代码中包含 `CS50.h`，不仅能让你使用 `get_string`，还能使用其他一些辅助函数。我们稍后会开始使用它们，比如获取整数或字符输入：`get_int`、`get_char`，以及获取双精度浮点数或单精度浮点数的函数。

我们没有提供 `get_bool` 函数——通常直接获取一个真或假的值并不太实用，不过我们原本也可以设计这个函数，只是决定不这么做。你只需包含那个头文件就可以调用它们。

但我们该把这些值存放到哪里，又该如何显示它们呢？其实占位符不止 `%s` 这一种：

| 占位符 | 对应类型 |
| --- | --- |
| `%s` | 字符串 |
| `%c` | 单个字符 |
| `%f` | 浮点数 |
| `%i` | 整数 |
| `%li` | 长整型（`long`） |

简而言之，这些问题都有对应的解决方法。它们并非什么高深莫测的细节，但都是实用的小技巧，随着时间推移慢慢掌握就好。

### 变量：赋值、自增和一点小魔法

在 Scratch 中，我们可以创建自己的变量来存储各种数值，只需拖拽一个新的积木块。举个例子，假设我们想记录某一个人的分数——用一个计数器来实现：创建一个名为 `counter` 的变量，初始值设为 0，然后随着他们往垃圾桶里扔垃圾，逐渐给它加 1、加 2，依此类推。

在 C 语言中，你几乎会采用同样的做法。你可以自由选择变量的名称——就像我之前给变量取名 `answers` 那样——先给它赋一个初始值。但根据之前的讨论，在 C 中你必须在等号右边做些什么：指定它的类型。既然它是数值类型，就不会是文本字符串；而且如果只是像数手指那样简单计数，我觉得不需要考虑小数部分，所以用 `int` 就足够了，至少对你的使用场景来说，那 20 多亿的取值范围完全够用。最后别忘了用分号来结束这个语句。

```c
int counter = 0;
```

右边这段代码就相当于 Scratch 左边实现的功能。

假设你想让计数器递增——把分数依次增加 1、增加 2——Scratch 里的"将 counter 增加 1"默认是递增，除非你输入负数，那样就会递减。C 里有几种方式可以实现，但先看这一段：

```c
counter = counter + 1;
```

这段代码看起来有点问题：**计数器怎么可能等于它自己加 1 呢？** 这本身并不表示相等关系——单个等号表示赋值操作，含义是"将右侧的值复制到左侧的变量中"。因此，无论计数器当前的值是多少（假设为 0），都会先加 1，然后把结果（即 1）存储回 `counter` 变量中，于是它的值变为 1。如果再次执行此操作，它会增加到 2，然后是 3、4，依此类推。

但递增操作非常常见，所以有更简洁的写法：

```c
counter += 1;
counter++;
```

乍一看可能有点奇怪，但这两个写法实现的效果完全一样。你可以用更少的按键来完成；实际上在 C 语言中这种做法非常普遍。

> **注意**：没有 `+++` 或者 `++++` 这种更多加号的写法，`counter++` 仅用于将单个变量的值递增一。

话说回来，这个版本虽然更冗长，但某种程度上也更清晰一些——因为这样你就可以一次性加 2、加 3 甚至更多。同样地，你也可以进行递减操作，或者更一般地使用减号符号。

### compare.c：三个问题与一棵决策树

让我们把这些技巧用到实际代码中去。回到 VS Code，关闭文件资源管理器，我们创建一个新程序 `compare.c`——一个非常基础的计算器，或者更准确地说，甚至算不上一个完整的计算器，只是简单比较几个数值。先写基础代码框架，引入 `CS50.h`、引入 `stdio.h`，然后写 `int main(void)`——为什么一直采用这种写法，我们下周会详细讨论。

```c
#include <CS50.h>
#include <stdio.h>

int main(void)
{
    int x = get_int("X's value? ");
    int y = get_int("Y's value? ");

    if (x < y)
    {
        printf("X is less than Y\n");
    }
}
```

> **提示**：提示语里问号后面加一个空格，这样可以把光标稍微向右移动一点，看着舒服一些。

`make compare`，回车。`ls` 一下确认：目录里有 `hello.c`（没有 `hello` 可执行文件，因为我几分钟前用 `rm` 删掉了）、有 `compare.c`，还有一个带星号标记的 `compare`。

> **定义**：那个星号是个视觉提示，表示这个文件是可执行的——这是一个可以运行的程序，它不仅仅是一个普通的旧文件。即使我没有手动输入那些命令，在这样的上下文里 `hello` 旁边也会有同样的星号标记，但在文件资源管理器里你是看不到这个的。

跑一下：输入 1 和 2，输出 "X is less than Y"。再输入 2 和 1——**我什么也没看到。** 为什么？因为我并没有设置检查"大于"的条件，更不用说"等于"的情况。

那就来完善一下：加一个 `else`，输出 "X is not less than Y"。重新 `make compare`，1 和 2 的结果完全一致，2 和 1 的输出也更清晰了。当然这仍然不够完善：如果我重新运行并输入 1 和 1，程序会输出 "X is not less than Y"——**这不算错，但表述不够精确。**

于是结合前面的方法：加一个 `if (x > y)` 输出 "X is greater than Y"，再加一个 `else` 输出 "X is equal to Y"。但这里也有人指出，这种做法其实效率很低——第 17 行那个判断可以直接去掉，因为从逻辑上讲，此时情况已经明确了：前面两个判断都不成立，就只剩下相等这一种可能。

去掉它，重新 `make`、重新运行，输入 1 和 1，现在程序已经能正确处理所有三种情况了。

> **易错点**：不要把三个判断写成三个互相独立的 `if` 依次排列。这样即使第一个条件已经满足，它仍然会继续检查第二个和第三个条件——你其实已经知道答案是否定的，却还在浪费时间问"那么，X 大于 Y 吗？""X 等于 Y 吗？"三个条件语句在逻辑上是互斥的，但无论实际情况如何都会全部检查一遍。这又是一个糟糕设计的例子。

所以我们最初那个只问一个问题的版本，反而更接近理想。事实也是如此：为了展示两者在代码密度的差异，我会回到只检查 `x < y` 的那个版本。

#### 把代码画成决策树

如果你更倾向于视觉学习，其实可以把代码画成流程图的形式：程序从这里开始，理想情况下在这里结束，中间这些图形分别代表代码中的逻辑组成部分。**菱形代表布尔表达式**，也就是条件语句的起点——如果 X 小于 Y，我就需要做一个判断，是或否，真或假。

上面那个只有一条 `if` 的程序，它的树长这样：

```text
          开始
            |
       [ x < y ? ]        ← 菱形：布尔表达式
         /     \
       是        否
        |         |
   "X is less    （什么也不做，程序直接结束）
    than Y"
        |
       结束
```

当条件为真时，程序继续执行，输出 "X is less than Y"，然后结束；为假时程序直接结束。注意，这里**并没有一个叫做 "stop" 的关键字**，只是没有代码来处理那种情况而已。

加上 `else` 之后，形状立刻变得不一样：

```text
          开始
            |
       [ x < y ? ]
         /     \
       是        否
        |         |
   "X is less  "X is not
    than Y"     less than Y"
        |         |
        +----+----+
             结束
```

而那个"问三次"的版本虽然更长，核心判断逻辑却恰恰是浪费的：

```text
          开始
            |
       [ x < y ? ] --是--> "X is less than Y" ---> 结束
            | 否
            v
       [ x > y ? ] --是--> "X is greater than Y" --> 结束
            | 否
            v
       [ x == y ? ] --是--> "X is equal to Y" ---> 结束
            | 否
            v
           结束
```

改回 `if` 和 `else if` 之后，流程图就不一样了，因为现在有了类似"快捷路径"的设计：

```text
          开始
            |
       [ x < y ? ]
         /     \
       是        否
        |         |
   "X is less    +-- [ x > y ? ]      ← 只在"否"的分支上继续追问
    than Y"        /         \
        |        是           否
        |         |            |
        |   "X is greater   "X is equal
        |    than Y"         to Y"
        |         |            |
        +---------+------------+
                   |
                  结束
```

第一个问题为真，条件成立，执行完就很快完成了；第一个问题为假，我们才再多问一个问题 `x > y`；成立就直接跳到末尾输出结果。那么"X 等于 Y 吗"这个条件需要检查吗？**No，这个条件不需要检查。** 检查完前两个之后，现在我们就可以输出 "X is equal to Y"，因为从逻辑上这必然是成立的。

这种情况已经被多次观察到，这是在浪费大家的时间。所以我们可以进一步精简，只保留一个问题或两个问题，就足以让程序更紧凑高效。如果你更倾向于视觉学习，几乎任何代码块都可以转换成这种图示形式——但这本质上表达的是相同的内容，**这种逻辑流程正是代码中的缩进和语法结构所要表达的核心意图。**

### agree.c：字符、重复的代码和逻辑或

我们再用另一种类型来做个最终练习。回想一下，上面列出的都是我们可用的数据类型，而这里则是我们可以调用的函数列表。

接下来让我们编写一个能体现当今常见场景的程序，不过这次要使用不同的数据类型。创建 `agree.c`——如今我们经常需要同意各种条款和条件，公平地说这通常以弹窗和点击按钮的形式出现，但我们也可以在命令行中用代码实现同样的功能。

同样先包含 `CS50.h` 和 `stdio.h`，写 `int main(void)`。对于只需回答"是"或"否"的情况，获取单个字符就足够了，不需要读取整个字符串：

```c
#include <CS50.h>
#include <stdio.h>

int main(void)
{
    char c = get_char("Do you agree? ");

    if (c == 'Y' || c == 'y')
    {
        printf("Agreed.\n");
    }
    else
    {
        printf("Not agreed.\n");
    }
}
```

> **易错点**：第 8 行和第 12 行我用的是**单引号**。因为这是一个单字符，而在 C 语言中单引号就是表示单个字符的标准写法。当需要比较单个字符时，使用 `char` 类型并用单引号；当需要处理由多个字符组成的文本（单词、句子、段落）时，就应该使用字符串类型和双引号。

注意我们用的仍然是 C 中相同的基础构件，只是用不同的方式来解决不同的问题。

坦白说，第一个版本里那个 `if (c == 'y') ... else if (c == 'n')` 是可以处理得更高效一些的：直接去掉 `if` 改成 `else` 并默认处理其他情况——如果你不给我任何答复，那我至少会默认最坏的情况，也就是你不同意。即便如此，这个程序的设计依然不够完善。

`make agree`，运行 `./agree`，输入 `Y`——成功。但如果我输入其他任何字符，比如 `N`，甚至明确输入 `no`——**等等，为什么这没起作用？**

非常正确。CS50 的 `get_char` 这类函数的特点之一在于，**它会强制限定你获取的数据类型**：因为使用的是 `get_char`，如果用户不配合并输入了多个字符，函数就像我们其他一些函数一样，其设计机制会要求用户重新输入。这样反复提示直到用户配合，这很有用，因为你就不需要处理那种错误检查了。

而输入大写 `N` 在第一个版本里是没有处理的。我打算输入 `Y` `Y`，你可能会希望这样也能起作用——这感觉像是一个程序漏洞。如果我们不想支持 "yes" 和 "no" 的输入，这也没问题，我们只想支持 Y 和 N，但不支持大写版本确实有点不合理。

那该怎么解决？加一个 `else if (c == 'Y')`，同样输出 "Agreed.
"。这样修改确实可行。但即使你之前从未接触过编程，这种写法是否也让你觉得有些别扭？确实存在冗余：第 14 行和第 10 行完全一样，**这跟复制粘贴没什么区别，通常来说这不是好的编程习惯**——如果我想修改那个情况下的提示信息，就得改两次。这种重复操作本身就是糟糕的设计。

#### 同时问两个问题：`||` 与 `&&`

我们可以通过一些尚未介绍的其他运算符来解决这个问题。如果想同时询问两个问题，这完全可以：

> **定义**：**逻辑运算符**把一个布尔表达式拆分为两个更小的布尔表达式，并且只需要其中任意一个条件为真即可。

上面代码里的那两个竖线符号 `||` 表示逻辑"或"（它可能不是您经常输入的字符，它在键盘上的位置因美式、英式或其他布局而异）。于是小写 `y` 和大写 `Y` 现在都能正常运行；其他任何字符则默认视为不同意。

虽然这里用不到，但某些情况下你也可以使用两个与号 `&&` 表示逻辑"与"。那为什么在这两个条件之间使用"与"明显不正确呢？因为同一个变量不可能**同时**既是小写字母又是大写字母——这完全不合逻辑。所以这里如果使用 `&&` 就会产生程序错误（表达式永远为假），而使用 `||` 才是正确的做法。

### 循环：让一段代码反复执行

我们最后再来看一个循环结构的示例。所谓循环，就是让一段代码能够反复执行多次的结构。比如在 Scratch 中，我们可以让小猫连续叫三声。

#### `while`：条件为真就再来一次

在 C 语言中实现循环功能有几种不同的方式，其中一种是这样的：

```c
int i = 3;
while (i > 0)
{
    printf("meow\n");
    i--;
}
```

C 语言中没有 `repeat` 关键字，所以无法逐字翻译那个结构，但我们可以把 `while` 循环理解为：只要这个布尔表达式为真就执行循环体。为什么？因为从逻辑上讲，这正是我想要实现的效果——如果从 3 开始计数，我可以每次递减 1，直到值变为 0 时停止。

执行效果是：从 3 递减到 2，再到 1，最后到 0。一旦数值变为 0，这个布尔表达式就不再成立，循环自动停止，因为条件不再满足。

不过这里有个值得注意的地方：虽然我建议的计数方式是 3、2、1，但我本能地数成了 1、2、3。那能不能换个思路，比如从 0 开始往上数，而不是从 3 往下减？当然可以，只需要调整几处：把 `i` 初始化为 0，把布尔表达式改成反复检查 `i` 是否小于 3，在循环体中用 `i++` 递增。

```c
int i = 0;
while (i < 3)
{
    printf("meow\n");
    i++;
}
```

同样地，如果你习惯视觉化思考，我们也可以这样从 0 开始计数：

```text
       [ i < 3 ? ]
         /      \
       是        否
        |         |
   "meow"       结束
        |
      i++  （回到顶部）
```

首先检查 `i` 是否小于 3；由于初始值为 0，条件成立，输出"喵"；接着递增 `i`，然后再次返回到布尔表达式进行判断——这正是 `while` 循环的工作原理，条件会不断被反复检查。当 `i` 从 0 递增到 1、2，最终达到 3 时，条件 `i < 3` 不再成立，结果为 `false`，循环便会终止。

#### `for`：把三件事写进一行

循环特定次数的情况实在太常见了，所以严格来说你并不一定非得用 `while` 循环。`for` 循环是另一种选择，只不过它的语法有点特别：记起来稍难一些，但能让你少写点代码。

```c
for (int i = 0; i < 3; i++)
{
    printf("meow\n");
}
```

理解它的方式本质上和 `while` 是一样的：第一个分号之前的部分是**初始化变量**；接着**检查条件**；如果 `i < 3` 成立，就执行花括号内的代码，然后自动执行第二个分号右边的操作。

逐轮走一遍：`i` 从 0 自增到 1，检查 `1 < 3` 成立，再打印一次 "meow"；C 语言将 `i` 从 1 自增到 2，`2 < 3` 成立吗？成立，于是 `i` 再次自增到 3；`3 < 3` 成立吗？不成立，因此 `for` 循环停止执行。**所以这完全是一样的效果，只是第一行里包含了更多"魔法"**——比你自己实际需要写的代码要多一些，而这可以说是更常见的编程惯例。两种做法都完全正确。

顺带说一个值得琢磨的问题：如果我想像普通人一样从 1 数到 3，还有另一种方法——从 1 开始，条件写成"小于 4"或者用另一个运算符写成"小于或等于 3"，这样也能实现同样的效果。但这样有点让人困惑，因为现在你得琢磨"小于 4"到底是什么意思。

> **结论**：编程中的惯例通常是**从 0 开始计数，一直递增到目标值但不包含该值本身**。你可以按自己的需求来设定，这样屏幕上至少能同时看到循环的起点和终点。

#### 死循环和那只烦人的猫

有时候你可能想实现一个无限循环的效果——就像我们在 Scratch 里做过的那样，当时我们让一些物体在墙壁间来回弹跳，用的就是这种无限循环结构。在代码中你同样可以实现。

C 中没有像 Scratch 里那样的"永久循环"积木块，但 `while` 循环完全能满足需求。要注意，`while` 循环需要一个布尔表达式来控制。如果我想实现永久循环，我只需要在这里放一个始终为真的表达式——比如 `while (2 > 3)` 或者 `while (1 < 2)`，用一个永远不会改变的事实作为条件，循环就会一直运行下去。但既然目标就是让循环永久执行并且让这个布尔表达式始终为真，编程中的惯例就是直接写 `while (true)`，这本身就意味着永久循环。

**从功能上讲，这意味着循环会一直执行下去，除非你通过某种方式提前跳出这个花括号包裹的代码块**——关于如何提前跳出循环，我们稍后会详细讨论。

来真的写一个。稳妥起见先引入 `CS50.h`——主要是因为它也为我们提供了像布尔类型这样的功能支持，然后写一个 `while (true)` 循环，在花括号里直接输出 "meow"。`make cat`，然后运行——

**这就像那个烦人的猫叫游戏，一直不停地"喵喵喵"叫。我现在好像有点控制不住终端窗口了。** 记住我的话，说不定哪天你也会遇到这种情况。不过咱们先好好休息个十分钟，外面走廊上有一些美味的蓝莓麦芬。十分钟后我们再回来解决怎么让这只"猫"停下来。

好了，差不多十分钟了。现在的状况是：VS Code 的代码空间占用率飙升，感觉快要崩溃了，检测到 CPU 使用率异常，建议结束一些进程以获得最佳体验。

> **结论**：无论是有意还是无意，一旦出现无限循环，就会发生这种情况——因为一直在不停地打印"meow"。长时间运行可能导致我们完全失去对环境的控制。**解决问题的答案就是按下 `Ctrl+C`。**

如果我及时按下了 `Ctrl+C`，情况就会不同。看来我们是重新掌控了这片代码空间。

#### 次数交给用户决定

怎么让这个"喵喵叫"程序更灵活呢？我们可以开始询问用户希望猫叫多少次——当然，与其让它无限循环，甚至也不仅限于固定的 3 次。

现在删除 `main` 函数体内的所有内容。声明一个变量，就命名为 `n` 代表数字（如果想更明确些，也可以起更长的名字），把它设成 `get_int` 的返回值，这个函数会从用户那里获取一个整数，并向用户提问，比如"N 的值是多少？"。

然后用 `for` 循环，把条件从 `3` 换成 `n`：

```c
int n = get_int("N's value? ");

for (int i = 0; i < n; i++)
{
    printf("meow\n");
}
```

这个变量在循环中充当占位符，表示我想重复执行 `n` 次而不是 3 次。（当然，如果我喜欢倒着数，也可以用递减的方式，但递增更符合常规做法：每次加 2，但不会达到你实际关心的那个上限值。）

`make cat` 然后运行——这次程序会提示我输入 `n` 的值。输入 3，输出 3 次 "meow"；再运行一次输入 4，自然就输出 4 次。

那么 `get_int` 具体为我实现了什么功能呢？它的作用与 `get_char` 类似：假设我没有正确输入一个数字，而是输入了一些随意的内容，比如 "dog"——这不是一个整数，因此 `get_int` 的设计目的是**隐式地拒绝**我的输入，并会反复重新提示，直到获得有效输入为止。我输入 "bird"，函数再次执行相同的处理流程。

因此在 `get_int` 的实现代码中，我们编写了一个循环来替你执行这类错误检查。但它的功能并非面面俱到，因为"整数"本身涵盖的范围相当广泛——从负无穷到正无穷，包含无数种可能。假设我想排除其中的某些可能性呢？让猫"喵" -1 次是毫无意义的，但程序却会接受这个输入。虽然程序不会出错或执行任何操作，但**一个设计更完善的程序应该拒绝这种输入**，比如明确提示"-1 这个值没有意义"。

#### 自己加检查：`continue`、`break` 与作用域

那该怎么开始添加自己的错误检查机制，引导用户输入有效值呢？先拿到 `n` 的值之后，检查它是否小于 0；如果是，就重新提示用户输入。

先别急着往下走——这里有两个细节值得单独说。

**第一，第 6 行做了两件事。** 我不只是在从用户那里获取一个整数，不仅将结果存储在变量 `n` 中，实际上也**同时创建了变量 `n`**。在 C 语言中，当你指定变量的类型和名称时，你实际上是在计算机内存中的某个位置创建了这个变量，指定类型是必要的步骤。但如果你只是想稍后重新使用并修改一个已经存在的变量，那么第 9 行这样的写法就足够了：只通过变量名引用它即可，再次指定类型显得多余，因为 C 语言已经知道它的类型了。

**第二，也是更重要的一个坑：作用域。**

现在让我们看看把检查加进去之后发生了什么。

先说一个明显的坏办法：在第 9 行往下再写一遍 `if (n < 0)` 然后重新调一次 `get_int`，如果还是小于 0 就再问一次，如此往复。这算什么呢？**我是在重复写代码。** 虽然我是重新输入，但本质上和复制粘贴没什么区别——这样下去就没完没了了。你打算给用户多少次机会呢？从理想情况来说，你希望用户不会这么多次都不配合，但真正正确的做法是我们应该反复提示用户，直到他们输入正确的值为止。

不过我们现在已经掌握了循环的概念，完全可以在循环中实现这个功能：先问一次问题，然后反复询问同一个问题。

```c
int n;
while (true)
{
    n = get_int("N's value? ");

    if (n < 0)
    {
        continue;
    }
    else
    {
        break;
    }
}
```

这里出现了一种新语法。如果 `n` 小于 0，那好办的——`continue` 的意思是**回到循环开头，再次执行完全相同的操作**。否则，如果你改用 `break` 语句，就意味着**跳出循环，并继续执行与该循环对应的花括号之后的代码**。

> **结论**：简单来说，`continue` 会把你带回循环顶部，而 `break` 则会让你跳出循环、继续执行循环之后的代码。

从逻辑上看，我觉得这是对的，但奇怪的是——这段代码并不能正常运行，也为我计算不出 `n` 的值。`make cat` 报错：

```text
cat.c:19: error: use of undeclared identifier 'N'
```

为什么会这样？看起来是没声明，确实。这确实是个细节问题：我在这个循环**内部**声明了 `n`，就在第 7 行到第 17 行的花括号之间。

> **定义**：这就是所谓的**作用域**问题。由于 C 语言的工作原理，一个变量仅存在于声明它的那一对花括号（作用域）内。你在 `while` 循环的花括号内部声明了 `n`，那么它就只存在于那个 `while` 循环的作用域中。

> **易错点**：所以如果第 19 行（在循环外面）要用 `n`，而第 8 行把 `int n = get_int(...)` 写在循环内部，编译器就会报"未声明的标识符"。**先声明，后赋值**，是这里最关键的一步。

那该怎么真正解决？最好的方式可能是把 `n` 的声明、也就是 `n` 的创建，移到花括号外部——塞到 `main` 函数的第 5 行下面，让它仍然在 `main` 的花括号内部（关于作用域的完整规则我们下周会详细讨论，但确保它和其他所有内容都在同一对花括号内）。单独新起一行写：

```c
int n;
```

这就**声明**了一个名为 `n` 的变量——它创建了这个变量，但最初并没有给它赋值，所以里面存储的值是未知的（这一点我们稍后再详细讨论）。然后在第 9 行就不需要重新声明了，我只需要给它赋一个值。由于 `n` 已经在第 6 行声明并位于 `main` 的花括号内，可以说 `n` 的作用域覆盖了我编写的这段代码的整个范围。

`make cat`——错误信息消失了。`./cat` 运行起来：输入 3，输出三声"meow"。

但更棒的是，由于我现在处于循环中，注意看：我可以输入 -1、1、1123、50 等任意数值，程序会一遍又一遍地重新问我，直到我最终配合输入一个类似 3 的值——这个循环在设计上可能会无限次运行，直到用户真正配合并允许我跳出循环为止。正是那个循环。

> **结论**：严格来说，我现在并不需要同时使用 `continue` 和 `break`。我原本想展示这两种语句都存在，但这样一来代码量就变成了实际所需的两倍。如果从逻辑上讲我只想在 `n` 大于等于 0 时跳出循环——因为我勉强能接受零只老鼠的情况，但负数就毫无意义了——那么只需反转逻辑判断即可：

```c
int n;
while (true)
{
    n = get_int("N's value? ");

    if (n >= 0)
    {
        break;
    }
}
```

代码就简洁多了。从技术上讲，我还可以采用其他方式。

## 循环写到头：do-while、嵌套循环，和那些装不下的数字
> 对应块：BLK06 | 覆盖分集：P02下 | 块标题（分集名）：《循环结构：while、do-while 与 for》

先把上一节的尾巴收完。那个循环我写成了 `while (true)`，靠 `break` 跳出来，里面有一句 `if (N < 0)`——可这不是我要的条件，我要的正好是它的反面。写法有两种：

```c
while (true)
{
    // 问用户要一个数字

    if (N >= 0)
    {
        break;
    }
}
```

或者把条件整体取反：在外面套一对括号，前面加个感叹号，`!(N < 0)`。逻辑上一模一样，但读代码的人得多绕一下。我宁可多花一行把“我要的不是负数”讲明白，也不想让读的人愣一下。

问题在于，`while (true)` 加 `break` 这种写法本身就有点土。C 里其实有一种循环天生就是给这种情况用的。

### do-while：先做事，再问条件

语法上只改了一个关键字的位置：从 `while` 换成 `do`，然后把布尔表达式搬到花括号**后面**去。

```c
do
{
    N = get_int("Number: ");
}
while (N < 0);
```

和之前那个 `while` 版本逐字对比一下，循环体一模一样，连那句提示文字都一样；唯一的区别就是条件被挪到了末尾。

```text
while（先问再做）
    判断条件
       ├── 假 ──▶ 退出
       └── 真 ──▶ 执行循环体 ──▶ 回到判断条件

do-while（先做再问）
    执行循环体 ──▶ 判断条件
                     ├── 真 ──▶ 回到执行循环体
                     └── 假 ──▶ 退出
```

> **定义**：`while` 是“先问再做”，条件写在循环体前面；`do-while` 是“先做再问”，条件写在循环体后面。正因为如此，不管条件一开始是否为真，`do-while` 的循环体**至少会执行一次**。

那这种“条件只在循环结束时才被检查”的写法，到底有什么实际用处？答案朴素得有点好笑：当你需要**至少做一次**的时候。你显然至少要问用户一个问题——一次都不问，那这个程序就没有意义了。至于 `while (true)`，你当然也可以硬写成那样，只不过多绕了一圈而已。

要说最好的例子，是那对活宝：路跑鸟跑起来步步为营，每一步落脚前先探一探，只要没到悬崖边就一直跑；郊狼才不管那么多，埋头往前冲，直到最后才想起来检查——可惜已经太迟了。`do-while` 就是那只郊狼：先跑完，再回头看是不是已经站在悬崖边上了。

这个梗在懂的人那里会心一笑；结论是“最终你会明白它，只是可能还是不好笑”——而这恰好说明了 `do-while` 的特点。

### 把“喵”变成一个函数

现在我们不再只是摆弄条件语句和循环结构了，得把软件设计得更合理一些。这就回到了上周提过的那个和“问题处理”有关的概念：**创建你自己的函数**。

因为 C 语言本身并没有包含你可能需要的所有功能，CS50 库也无法涵盖所有你可能需要的功能。归根结底，编程很大程度上是把想法**抽象化**：解决一次，之后就能反复复用、复用、再复用；你甚至可以把它打包成所谓的库——就像我们已有的库那样——让别人也能用。

一个熟悉的例子。上周在 Scratch 里，实现“喵喵叫”是这样做的：让小猫播放“喵”的音效，直到播放完毕；然后把它抽象成一个神奇的新拼图块，就叫“喵”。而在 Scratch 里让“喵”重复 N 次，也不过是把积木套进“重复执行 N 次”。

到了 C 里，今天的写法会有点奇怪，但下周这些细节就开始清晰起来。

先写函数签名：

```c
void meow(void)
```

`void` 表示它不返回任何值——这就是函数的返回值。括号里再写一个 `void`，表示它不接受任何输入，这就是函数的参数。什么都不收、什么都不返，只干一件事：在屏幕上打印一个 `meow`。这正是我们上周说过的**副作用**。

用一下它：

```c
#include <stdio.h>

void meow(void)
{
    printf("meow\n");
}

int main(void)
{
    for (int i = 0; i < 3; i++)
    {
        meow();
    }
}
```

编译、运行，`meow`、`meow`、`meow`——和上周的 Scratch 版本效果完全一样。这一步的意义在于：“喵”这个概念现在有了名字，你可以复用它，而不是每次都把那行 `printf` 重新敲一遍。

当然这还不够，我还可以再抽象一层。在 C 里创建变量时，你需要指定类型和名称；**自己定义函数、让它接收一个或多个输入（也就是参数）时，同样要为这些参数指定类型和名称**。所以“重复喵叫 N 次”写成这样：

```c
void meow(int n)
{
    for (int i = 0; i < n; i++)
    {
        printf("meow\n");
    }
}
```

它仍然不返回任何值，仍然只产生听觉或视觉上的副作用，但现在它确实接收了一个输入。第一版里那个写死的 `3`，被换成了变量 `n`。括号内不需要分号，用练习你会习惯这个约定。

剩下的代码部分完全一样，只是数字变成了变量——本质上还是上周 Scratch 里那套一模一样的思路，只不过这周看起来晦涩得多。练得多了自然会熟。

### 函数原型：给编译器的一个承诺

演示的时候，我把 `meow` 的定义一路拖到了文件最底下（差不多第 100 行附近），再滚回顶部看 `main`——眼不见心不烦，“喵”这件事已经和我没关系了。

然后编译就报错了：

```text
...:9: error: implicit declaration of function 'meow'
```

第 9 行，报的是**调用了未声明的函数 `meow`**，后面还跟着一堆相当晦涩难懂的内容。编译器明明知道——我就在下面写着呢——它就是不肯往下翻。

这其实是 C 编译器的工作方式：它相当简单直接，**严格按照字面意思、从上往下解析代码**。读到第 9 行的时候 `meow` 还不存在，那就是你的问题。这确实是一个错误。

撤销掉就好了。但我真正想说的是另一件事：一般来说，`main` 函数放在文件开头是合乎情理的——打开文件时，你最想看到的就是你关心的主程序，把其他函数全堆在顶部会把 `main` 挤得越来越靠下，这确实有点烦人。

所以解决办法来了，而且我敢说这是唯一适合复制粘贴的一处：**复制 `main` 函数的第一行**——那一行叫**函数签名**——然后只把这一行（仅这一行）加上分号，放到 `main` 上方：

```c
void meow(void);   // 函数原型
```

> **定义**：**函数原型**就是给编译器的一个提示、一个承诺：“嘿，后面会有一个叫 `meow` 的函数，它不接收参数，也不返回值（以分号结尾）。” 它本身不含任何实现，完全基于信任——承诺这个函数最终会在文件后面被定义。

顺手说一个和错误无关的东西：第 4 行那种以斜杠开头的内容，通常被称为**注释**。在 C 里，任何以斜杠开头的东西都只给人看，不给计算机看，就像 Scratch 里的便签，是提醒自己、TA 或者同事“这几行在干嘛”用的。我在这里写一句“让‘喵’叫若干次”，纯粹是为了让屏幕和我嘴里的描述对得上；不过反正也用不着，我还是把它删掉了。

### 参数、作用域，和那个“我明明定义了 n”

既然函数能收参数，那就让它收点有用的。

```c
int main(void)
{
    int n = get_int("How many meows? ");   // 提示语随你写

    meow(n);
}
```

程序这就变得动态了：我问用户需要喵多少次，然后把那个值传进去。

但这里有个坑，而且是我**故意**留着的。`n` 明明在 `main` 里定义了，`meow` 却看不见它。于是我很天真地直接把函数写成 `void meow()`——想当然地认为 `n` 反正已经在 `main` 里定义好了，函数拿去用就行。编译果然报错：

```text
...:14: error: 'n' undeclared (first use in this function)
```

为什么？问一个具体的问题就清楚了：`n` 定义在第 9 行，它的作用范围在哪里？**在哪个作用域内？** 答案是：只在那一对花括号之间有效。执行到第 14 行时，`n` 已经出了作用域，可以这么说，因此它就无法正常工作了——其他函数根本看不见它。

解决方案就是我一开始采用的那个：把 `n` 作为参数**传进去**。顺手把 `meow` 内部的参数改名叫 `times`，因为到处都用 `n` 表示次数会引起混淆：

```c
void meow(int times)
{
    for (int i = 0; i < times; i++)
    {
        printf("meow\n");
    }
}
```

注意两件事：调用时传进去的叫 `n`，函数内部接住的叫 `times`——**这两个名字可以不一样，完全取决于你的设计选择**。你传入的是一个值，函数内部可以给它起一个完全独立的名字。我也可以用 `m` 或者别的字母，但 `times` 更清晰，因为它直接说明我希望猫叫几次。

归根结底，这本质上就是一个**作用域**的问题。

### 好代码的三条尺子：正确性、设计与风格

退一步，做一次更宏观的回顾。在编写优质代码时，CS50 乃至整个业界通常都会关注这几个维度：

| 维度 | 它在问什么 | 谁能给你打分 |
| --- | :--- | :--- |
| **正确性** | 代码跑出来的行为，是不是预期的行为 | `check50` |
| **设计** | 有没有白白浪费机器的时间、浪费用户的时间 | 助教当面评估、discussion、`design50` |
| **风格** | 别人读不读得动：缩进齐不齐、变量名像不像人话 | `style50` |

**正确性**在课程背景下的意思是：代码是否按照预期的方式运行，是否完全按照作业（习题集）的要求来执行。在现实世界中，它意味着完全按照产品经理、CEO 等决策者所确定的软件功能来执行。行为符合预期，仅此而已。

但行为符合预期，和**设计**好不好，完全是两件事——我们已经多次看到这一点。我写过一些过于简单的例子，逻辑上百分之百正确，却浪费了计算机的时间：问太多不必要的布尔表达式，诸如此类；也浪费了用户的时间。所以设计更像是关于现实世界中的考量：**英语里不仅要把话说对，还要说得漂亮**——要提出一个有力、有说服力的论点，而不仅仅是碰巧正确的论点。

**风格**是我们评估代码质量的第三个维度，这更多关乎代码的美学：代码是否排版美观、缩进是否整齐？变量命名是否恰当，而不是随手就命名为 `x`、`y`、`z`？

> **结论**：风格真正影响的是**其他人**，而不是计算机——但对其他人来说很重要。

从第一个问题集开始，你会看到我们提供了一系列工具。

`check50` 用在每个 C、Python 和其他语言的问题集任务中。你可以运行 CS50 团队写的 `check50` 命令，接着指定一个所谓的 **slug**——也就是该作业题目的唯一标识符——然后就能快速获得关于**正确性**的反馈。但这并不意味着你的代码实现得很好、设计得很出色，或者说风格是否优雅；它只是提交优质代码的**第一道关卡**。

`design50` 是基于 CS50 Duck 构建的：打开一个程序标签页点一下 `design50`，它会像 ChatGPT 一样为你提供改进建议。它并不验证代码的正确性，而是评估代码的**设计**与质量——这部分更为主观，其评估标准模拟了优秀助教可能给出的反馈。

`style50` 是第三个工具，它为你的**风格**提供反馈：左栏显示你当前的代码样式，右栏展示代码应有的规范样式，确保它符合课程教学要求，并与 CS50 的官方风格指南保持一致。那些有编程经验的同学，毫无疑问会一眼注意到这些差异——它们和现实世界中代码规范之间的差异是一回事。在典型的企业环境中，通常就有一套官方风格指南或工具供所有开发者遵循：这样即使每个人对问题的解决方案各不相同，最终呈现出来的代码风格却能保持统一。

### 再抽一层：只收非负整数的输入函数

程序现在已经是正确的解决方案，风格也算规范。我承认它确实可以再多加一些注释：比如在 `meow` 上写一句“让‘喵’叫若干次”，在输入那行写一句“从用户那里获取一个数字”——这是写给我自己、助教或同事看的。

但在**设计**上还能更好：现在这个 `get_int` 会把负数也收进来，而喵的次数不该是负数。

有两个办法。一个是像之前那样，在调用处加一堆代码：先 `n = get_int("n? ")`，然后当 `n < 0` 时继续执行一个循环。这确实能工作，但每个需要输入的地方都得抄一遍。**代码里出现两次以上的东西，就该给它一个名字**。

另一个办法是自己实现一个专门拿非负整数的函数：

```c
int get_n(void)
{
    int n = get_int("n? ");

    while (n < 0)
    {
        n = get_int("n? ");
    }

    return n;
}
```

有三件事值得停一下。

**返回值第一次明确地出现了。** 注意它的签名是 `int get_n(void)` 而不是 `void ...`——这个 `int` 就是在说“我返回一个整数”，而这个返回值正是这个函数存在的全部意义。

**`while (n < 0)` 的循环体里，我们不直接操作 `n`**，只是再问一次；这就是**输入验证 + 重复提示**的逻辑。

**`return n;`** 把结果交出去，函数结束。

有了它，`main` 里那一整段都可以删掉：

```c
int main(void)
{
    int n = get_n();

    meow(n);
}
```

别忘了在文件顶部再加一个函数原型——和刚才一样，这是目前唯一一处我会真心建议你**用复制粘贴**的地方。

回头看这两个函数的差别挺有意思：`meow` 接收参数、**没有返回值**，只有副作用；`get_n` 不接收参数、**有返回值**，没有副作用。这是两种完全不同的形状，我们现在都已经会写了。我们基本上把上周用 Scratch 实现的功能翻译成了 C 语言版本——这就是我们现在可以如何**模块化代码**：把底层细节抽象出来，最终创建我自己的函数。

### 用今天学的零件，搭一个文本版马里奥

经典游戏《超级马里奥兄弟》：横向卷轴，马里奥可以在其中上下左右跳跃移动、收集金币，并努力通关。屏幕上有很多障碍——马里奥需要跳过坑洞，而那些通常藏在问号方块后面的金币，他可以通过跳起顶撞方块来获取并累积分数。

我们暂时还不会碰任何图形化的内容，那部分继续留给 Scratch。但通过 C 语言，我们同样可以实现其中的一些核心概念。比如，我要编写代码来生成这一排 4 个问号。换句话说，让我们看看能否利用今天学过的所有基础模块，在一个名为 `mario.c` 的文件中，开始实现我们自己的简化版《超级马里奥兄弟》。

#### 一行四个问号

最简单的版本其实根本不需要循环：

```c
#include <stdio.h>

int main(void)
{
    printf("????\n");
}
```

`make mario`，运行，屏幕上就是四个问号。很简洁，也很取巧——因为我把 4 直接写死了。

但如果我想要三个、五个，或者任意数量的问号呢？那就得用循环：

```c
#include <stdio.h>

int main(void)
{
    for (int i = 0; i < 4; i++)
    {
        printf("?");
    }

    printf("\n");
}
```

第一次改完运行，出来的是**竖着的一列**，不是横着的一行。我犯了什么错？在每个问号后面都加了 `
`——一行一个问号，当然是一列。

把它去掉，重新编译再跑，四个问号终于横着排成一行了。至于换行符本身，我把它放在**循环外面**：打印完所有问号之后，再单独输出一个 `
`。换行符本身就是一个可以单独输出的转义序列，不需要依附于任何字符。

> **易错点**：循环体里少写一个 `
`，输出形状就从一行变成一列；多写一个 `
`，就反过来。**换行是整个循环的收尾动作，不该在循环体里反复执行。**

#### 一列砖块

再往地下一层——其实还是地面场景——你会看到一列砖块，马里奥需要跳过去。这一列该怎么生成？其实我们之前已经找到几乎一模一样的解决方案了。

```c
#include <stdio.h>

int main(void)
{
    for (int i = 0; i < 3; i++)
    {
        printf("#");
    }

    printf("\n");
}
```

用 `#` 是因为它看起来有点像方块。三行、每行一个井号——非常朴素，但已经够我们继续往下玩了。

#### 3×3 的砖块网格

第三个、也是最后一个马里奥问题：打印一个由井号组成的 3×3 砖块网格。

这个问题有意思的地方在于，我们**从来没有处理过二维空间的问题**。水平方向处理过（那行问号），垂直方向也处理过（那列砖块），但把这两个概念**组合到同一个问题**里，还是第一次。

怎么逐行打印它们？如果你对编程有一定了解，可能会想到一个熟悉的东西：**老式打字机**。你打印完一行砖块，回到起始位置，再打印下一行——而 `printf` 一直在替我们做的就是这件事：它逐行打印文本内容，不会随意跳转位置。我们可以顺着这个特性往下写：

```c
#include <stdio.h>

int main(void)
{
    const int n = 3;

    for (int row = 0; row < n; row++)
    {
        for (int column = 0; column < n; column++)
        {
            printf("#");
        }

        printf("\n");
    }
}
```

```text
row = 0  →  column 0 1 2  →  # # #   ← 在这一行的最后一列之后换行
row = 1  →  column 0 1 2  →  # # #   ← 在这一行的最后一列之后换行
row = 2  →  column 0 1 2  →  # # #   ← 在这一行的最后一列之后换行
```

换行那句 `printf("
")` 的位置很讲究：放在**内层循环之后、外层循环体之内**。放得太早（挪进内层循环里），每一列之后都换行，就又变回竖着的一列；放到外层循环外面去，三行会挤成一行；只有现在这样才对。

关于变量名，先说嵌套循环本身的规矩：外层循环和内层循环的写法本身都没问题，但**最好不要让内层循环的变量与外层循环的变量重名**，以免造成混淆。在代码里，当你需要另一个整数变量、而 `i` 已经被占用时，使用 `j` 是相当常见的做法；`i`、`j`、可能再加个 `k`，通常是可行的。但如果你开始用 `l`、`m`、`o` 这样的变量名，那很可能说明你的代码设计本身有问题——虽然并没有硬性规定，但变量名用得太随意会显得很荒谬，这时你就该考虑起个更合适的名字了。

然后是我自己更喜欢的一点：其实用 `i` 和 `j` 反而**让代码显得更复杂了**。我完全可以给这些变量起更好的名字——`row`，然后或许叫 `column` 或者 `col`，如果完整拼写出来更清楚的话就全拼。这样就能让我自己、助教和同事更清楚地理解这些变量的具体含义。老式打字机打一行字，不正是“行”里包含“列、列、列、列”吗？嵌套循环在逻辑上实现的正是这个效果。

> **提示**：把 `i`、`j` 改名成 `row`、`column`，仅仅是改变了变量名称，除此之外不会产生任何功能上的影响。但可读性是实打实的收益，这一点稍微微妙、却不容忽视。

还有一个地方不对劲：数字 `3` 被我硬编码了**两次**——两个循环条件里各写一遍。这倒不是什么大问题，课堂上的小练习嘛，如果我只是手动输入一个 3，谁会在乎呢？但如果我想让这个方块随着时间的推移变得越来越大，就得在两个不同的地方修改它——而这个问题我上次和今天都提到过，它迟早会回过头来困扰你：你可能会犯些低级错误，或者同事根本没意识到你在多个地方硬编码了数字 `3`，这本身就是糟糕的设计。

那么该怎么解决？声明一个变量，让它在两个地方都被复用：

```c
int n = 3;
```

这确实更好，因为现在我们复用了这个值。但其实**我们还能做得更进一步**。在 C 语言以及许多其他编程语言中，有一个**常量**的概念：如果你想把某个值存储在变量中，却又想向编译器表明这个值永远不应该被改变——更重要的是，你想防止自己（或者同事）不小心修改了这个值——那么你可以把它声明为常量，或者说，确保它是常量：

```c
const int n = 3;
```

这样，`n` 就是一个具有恒定值的整数。如果我后续代码里做了些蠢事，比如试图把 `n` 重新赋值为其他值，编译器就会直接拦下我。这样就能防止我犯低级错误，**这本身也是一种更好的设计实践**。

### 先做一个只会加法的计算器

换个方向，我们来看看计算机**本身**有哪些难以完美处理的问题——不是我们的代码写得不好，而是它自己存在的局限。

我们到目前为止用过的运算符都在这张速查表里：加法、减法、乘法、除法，以及取模运算符——它本质上就是求余数。一个命令、一个运算符，就能完成一次操作。

那就用它们来制作自己的计算器，看看这个计算器能做什么、又不能做什么。先从最简单的功能开始：把两个数字相加。

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int x = get_int("x? ");
    int y = get_int("y? ");

    printf("%i\n", x + y);
}
```

`%i` 是整数的占位符，这里只需要用 `x + y` 替换它。虽然之前没有完全这样做过，但这其实只是我们学过的一些概念的组合应用。运行一下：x 是 1，y 是 2，结果确实得到了 3。

所以这个计算器还不错，看起来它运行正常。但设计上或许还有改进的空间——我一开始还老老实实声明了第三个变量：

```c
int z = x + y;
printf("%i\n", z);
```

一般来说，如果只打算使用一次，创建一个像 `z` 这样的变量是不太推荐的：就为了用一次、而且只用一次就创建一个变量，这岂不是在浪费我的时间？有时候，如果能让代码更易读或更清晰，这样做是可以接受的——比如我把它命名为 `sum`，可能确实会提高可读性，我能向读者清晰地表明这是两个变量的和，这可以说是一个净收益。但即便如此，我还是有点吹毛求疵：我完全可以去掉那个第三个变量，直接在这里写 `x + y`，这完全没问题，也很合理，尤其是因为代码行本身仍然相当简短。

> **提示**：“难以阅读”这个判断听起来很合理，但这又回到了之前的观点：**设计往往是主观的**，这里没有一成不变的硬性规定。有些助教可能不认同我的看法，但我觉得这样处理没问题——代码可读性才是最重要的，这一点毋庸置疑。

顺便一提，如果你好奇我为什么打字这么快：其实我有时候会耍点小聪明，用的是**自动补全**。如果我知道自己要创建一个名为 `calculator` 的程序，而且 `calculator.c` 文件已经存在，那我就可以输入前几个字母再按 Tab 键，系统会自动补全剩余的文件名（前提是这个文件确实存在）。更棒的是，如果想找回之前输入过的命令，用上下方向键就可以翻看历史记录——连续按上箭头，就能看到最近输入的所有命令。这些快捷键虽然不起眼，却能大大提升操作效率。

### 把计算器改成一个梗

别只局限于加法了。我们试试乘法：这次只提示用户输入一个数字，然后乘以 2——C 语言里乘法就是 `*`。

```c
int x = get_int("x? ");
printf("%i\n", x * 2);
```

输入 1 得 2，输入 2 得 4，输入 3 得 6，依此类推。没问题，看起来可行。

不过我们可以借鉴一个近一两年很流行的梗来设计它——边做边看，看你能否认出来。我把整段代码删掉，改成这样：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int in_dollars = 1;

    while (true)
    {
        printf("%i dollars. Double and pass to the next person?\n", in_dollars);

        int c = getchar("y/n? ");

        if (c == 'y')
        {
            in_dollars *= 2;
        }
        else
        {
            break;
        }
    }
}
```

几个细节值得拆开看。

**占位符**：和 `printf` 类似，`getchar`、`get_int`、`get_string` 都留了占位符。我们之所以把它们设计成这样，就是为了让你能传入占位符并填入相应的值——为什么这么做？同样是为了这个梗的效果：我想在问“你想翻倍并传给下一个人吗？”时，顺带告诉他们我将要交给他们多少钱。想显示金额数值，而美元符号只是因为我们讨论的是美元；使用 `%i` 是因为我们处理的是整数。

**翻倍**：`in_dollars *= 2` 是我们表示翻倍的简写形式。也可以更严谨地写成 `in_dollars = in_dollars * 2`，但为了省事还是用前者；没有自增运算符，也没有星号叠加的技巧，你必须至少用这种方式来实现。

**无限循环**：`while (true)` 是我**故意**制造的。敲 `y` 就翻倍再问一次，敲 `n` 就跳出循环。

编译、运行。屏幕上先出现 1 美元（第 6 行 `in_dollars` 的初始值），然后问“翻倍后传给下一个人？”——敲 `y`，得到 2 美元；再敲 `y`，4；再敲……我得加快速度了，效果越来越好。

到这里你就看出**指数运算**的威力了：数值已经相当高了。我们继续——虽然过程有点枯燥，也确实有点过头了，但这可不是表情包里会出现的情况。

### 溢出：钱多到装不下那一天

这里发生了什么？

因为计算机分配给每个整数的**位数是有限的**。我之前推测过：整数通常占用 32 位，也可能是 64 位；但不管多少，位数是有限的，这就意味着数值能表示的范围有上限，大约在 40 亿左右。而且别忘了，默认情况下整数既可以是负数也可以是正数，所以范围大约是 20 亿——这和我们刚才看到的数字非常接近。

实际上，我们导致了内存中的**整数溢出**。这是一个专业术语：当试图存储一个过大的数值时，就会发生整数溢出。

要更清楚地说明它，得理解计算机内部长什么样。笔记本、台式机或其他设备里有内存芯片，那些小小的黑色芯片中包含大量比特（实际上是字节），它们能以电子方式存储信息。系统分配这些比特时，是以 8 位、16 位、32 位或 64 位为单位的，每个数值能使用的比特数量是有限的——**无论是 32 位还是 64 位系统，只要比特数量有限，能表示的数值就有上限**。上周那个简单的灯泡实验，我们已经在小规模场景下看到这个问题了：

```text
3 个比特（3 个灯泡 / 3 个晶体管）能表示的范围：

    位置    2   1   0
     7      1   1   1
     6      1   1   0
     5      1   0   1
     4      1   0   0
     3      0   1   1
     2      0   1   0
     1      0   0   1
     0      0   0   0

  8  →  需要第 4 个比特。没有它，8 就只能是 0。
```

这也解释了我们刚才看到的现象：如果最高位那个 `1` 在某种表示方式下意味着“数字本身是负数”，那么溢出的表现就是**回绕**——那个 1 最终让我们实际上回到了零。所以在 VS Code 里我们其实同时看到了这两种情况：先是负数，因为逻辑上发生了回绕，就像那个 1 让我们回到了零一样；然后是 0，因为最终确实回到了 0。

那该怎么解决？最直接的办法：换个更大的类型。改用**长整型 `long`**，它占用 64 位，这样至少在这个场景中，我们能给出更多的钱。

占位符也要跟着换——不能用 `%i` 了，现在需要用 `%li`（long integer）。

重新编译，然后一直按 `y`。由于现在用的是 64 位，这个数值会变得极其巨大，远超之前的范围：大到我不可能一直点击 `y` 然后回车，因为我们永远也触及不到边界。但如果最终在循环中**自动**执行这个操作，它肯定会溢出归零。

果然生效了。我本以为点击次数不会达到那个程度，但同样的问题还是出现了——**即便使用这么多比特位，我们仍然让这个长整型溢出了**，因为我操作时间太长，按 `y` 的次数多到连这种长整型都容纳不下。

所以这不只是一个玩具问题，它在现实世界中确实会发生。

### 现实世界里的溢出：波音 787 与吃豆人

先说一个几年前真实发生过的。这张图片是一架波音 787，远在最近出现的各种问题之前。

在航空业中，飞机通常要保持**连续供电 248 天**——这其实是一种行业常态，毕竟时间就是金钱：航空公司希望飞机尽可能多地在空中飞行，这意味着它们需要尽可能长时间保持开机状态，连夜间也不会关机。

几年前《纽约时报》曾报道，一架波音 787 在连续运行 248 天后出现了问题：在持续供电 248 天后，可能会因**发电机控制单元同时进入故障安全模式而导致所有交流电源中断**。这种情况是由发电机控制单元内部的一个**软件计数器**引起的，该计数器在持续供电 248 天后会发生溢出。波音公司当时正在开发发电机控制单元的软件升级来解决这个安全隐患。

翻译成人话就是：如果这些飞机一次性持续运行超过 248 天，它们的电源就会直接关闭——而飞机长时间保持最大功率运行恰恰是常见情况。

那怎么办？波音修复这个问题需要一段时间，**短期方案**是什么？如果症状是“飞机在连续运行 248 天后会在飞行途中突然关机”，你会怎么做？

**关机再重启**——就像你可能学过怎么处理手机、电脑或其他偶尔出问题的电子设备那样。重启飞机。

为什么这样能行？因为每次重启手机、笔记本电脑或飞机时，所有变量都会重置为默认值。如果像我的某些示例那样，代码的第一行把变量设为零，那么这些变量就会重新归零；而代码是从上到下顺序执行的。问题解决。

等他们最终推出修复方案后，就不再需要这么做了。但问题的根源其实很朴素：他们可能使用了 32 位整数**并包含负值**，因此实际可用的只有 31 位用于计数正数。248 天大约对应着**以十分之一秒为单位的计数上限**——也就是说，以十分之一秒为单位连续计数 248 天后，整数会发生溢出，最终某个值归零，系统电源被强制关闭。当时有很多营销术语或技术术语的描述，但归根结底，这只是一个简单的整数溢出问题。

再说一个更老的、几乎所有人都玩过的：**《吃豆人》存在一个历史性的漏洞**——无论你玩的是哪个版本，玩家最多只能玩到**第 255 关**。由于缺少一个检查当前关卡的 `if` 条件，如果你技术超群打到了超出上限的关卡，屏幕上就会显示乱码：游戏同样发生了整数溢出，导致屏幕上出现随机字符。所以能通过这个漏洞打到第 256 关，反倒成了一种**荣誉的象征**。

### 除法的两个坑：截断与浮点精度

回到计算器。把这些临时代码清掉，换成除法：

```c
int x = get_int("x? ");
int y = get_int("y? ");

printf("%i\n", x / y);
```

（顺便说，我本意不是要处理那个缺失的终止符——写的时候少了一个双引号，这是个意外的错误，编译器一眼就抓住了。）

运行。输入 1 和 3，结果显示 **0**，这很奇怪。输入 2 和 3，结果还是 0，而不是 0.66。输入 3 和 3，倒算出了正确结果。但输入 4 和 3，本应得到 1.33，结果却显示 **2**，这显然不对。

又是比特位数有限带来的问题：**截断**。由于比特位数有限，即使你想进行带小数点的浮点数运算，只要使用的还是整数类型，小数点后面的部分都会被直接丢弃。这个问题我们之前已经隐约提到过。

现在把数值从整数改为浮点数、把格式说明符从 `%d` 换成 `%f`，重新编译，1 除以 3 就能正确计算了。

但这里还潜藏着另一个现实中常见的问题。我要把 `%f` 调整成一种略显晦涩的形式：在小数点后跟一个数字（比如随意写个 50），就能控制显示多少位有效数字。于是——

```text
0.333333333333333314829616256247390992939472198486328125
```

与小学课堂上学到的知识完全相反，这个计算器似乎认为 1 除以 3 **并非**无限循环的 0.33333333……，末尾还跟着一堆莫名其妙的数字。

道理还是同一个：计算机只能使用有限数量的比特，而浮点数可能存在无限种数值，所以它无法精确表示所有可能的浮点数。我们看到的本质上是 1/3 的**近似值**，这种现象在实际应用中其实相当常见。除了增加比特位数（例如用双精度浮点数代替单精度），或者至少尝试检测并处理这种情况，实际上没有其他根本性的解决方案。这就是**浮点数精度问题**。

### 从 Y2K 到 2038

这类问题其实一直都在发生。就在我即将毕业的时候，曾出现过所谓的**“千年虫问题”或“Y2K 问题”**。几十年来，为了图方便，计算机一直只用**两位数字**来表示年份，而不是四位——这样效率更高，因为用两位数字表示年份（比如 1999 年）比用四位节省了一半的内存空间。

可当时间从 1999 年跨入 2000 年时，如果内存中存储的年份数字位数不足，系统就很可能会把 2000 年误判为 1900 年。我们当时确实搞砸了，幸好全世界都紧急行动起来——去翻当时的维基百科和新闻报道，你会发现大家都以为世界末日可能真的要来了，但最终并没有发生。

你可能会以为我们从此吸取了教训。遗憾的是，另一个类似的问题即将在 **2038 年**出现。

由于历史原因，自上世纪 70 年代及更早时期以来，计算机通常使用 32 位整数来记录日期和时间。具体来说，系统通过计算**自 1970 年 1 月 1 日以来经过的秒数**来记录时间，所有相关计算都基于这个起始日期——可以说，这个时间点标志着计算机真正开始登上历史舞台。

遗憾的是，从 1970 年 1 月 1 日开始，你最多只能数到大约 40 亿个值；如果把负数范围也算上，就只能数到约 20 亿。因此：

```text
1970-01-01              0  秒
      ...               每经过 1 秒，计数器 +1
      ...
2038-01-19   2147483647  ← 2^31 - 1，32 位有符号整数的上限
                    ↓ 溢出
                  归零、回绕
                    ↓
        系统把当前时间误认为  1901-12-13
```

所以在 **2038 年 1 月 19 日**，32 位计数器将会发生溢出。如果这个问题得不到解决——如果你和其他人没有在 2038 年之前修复它——你的电脑、手机和其他设备很可能会错误地把时间显示成 **1901 年 12 月 13 日**。

> **提示**：把上面那个 248 天和这个 2038 放在一起看就明白了：它们其实是同一件事的两副面孔，一个把电源关掉，一个让时钟回到 1901 年。知道这两个日期，比死记它们的定义更有用。

针对这些问题，其实是有解决方案的，而 CS50 课程的核心目标，就是让大家掌握解决这类问题的方法。不过，如果你想记一下这个日期，这里有个二维码——扫描后，这个日期就会自动添加到你的谷歌日历或 Outlook 日历中。记得留意一下。
