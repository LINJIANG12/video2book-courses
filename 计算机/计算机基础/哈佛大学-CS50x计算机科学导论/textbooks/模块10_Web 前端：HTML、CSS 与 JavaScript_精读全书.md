## 从"信封"到网页：一次 HTTP 请求的来龙去脉
> 对应块：BLK25 | 覆盖分集：P10上 | 块标题（分集名）：《Web 基础与 HTTP 请求响应》

### 从黑白终端走到浏览器

开学到第八周，我们写的作业集清一色是命令行代码：那种黑白终端窗口，所有操作靠键盘，非常文本化。但我们每天真正在用的东西——网页浏览器、手机 App——完全不是那个样子。

从这一讲开始，接下来整个学期，我们要把过去几周攒下的所有基础零件重新部署一遍，放到网页应用的语境里（如果你愿意，移动应用也行），为期末项目做准备。

今天要介绍三种语言：HTML，写网页用的语言；CSS，美化样式的语言；还有 JavaScript——这三种里只有它是真正意义上的编程语言。不过别因为这个就把前两个看轻了：JavaScript 的语法和功能跟 C、Python 这些我们已经学过的语言非常像，反倒是不用花多少力气。

而在那之前，我们要先弄清楚一件更基本的事：互联网到底是怎么运作的，它又是从哪儿来的。

### 互联网，是一张连起来的网

先从最朴素的定义开始：**网络，就是计算机之间的互联**，无论是有线还是无线。

今天大多数家庭都有自己的网络，学校有网络，公司有网络。当这些网络再互相连起来——如果还没连的话——它们就构成了**互联网**。就这么简单：全球性的计算机、服务器、设备，以及如今许许多多别的东西的互联。

那它从哪儿来的？往回倒到 1969 年左右，互联网最初的形式叫 **ARPANET**，即高级研究计划局网络。那是美国国防部的一个项目，目的是把当时数量极其有限的超级计算机连起来。因为在那个年代，这些机器在地理位置上对许多研究人员来说是根本够不着的。

最早的 ARPANET 什么样呢？只有加州大学洛杉矶分校和另外少数几个节点，用某种方式互相连着。仅仅大约一年之后，东海岸的哈佛、麻省理工这些机构也加进来了。

快进到今天：世界上几乎任何地方都能找到并路由数据。事实上，现在世界各地遍布着一种叫**路由器**的设备——路由器本质上就是一台计算机，它负责把数据向上、向下、向左、向右地路由，无论是地理上还是实际物理连接上。现实世界里，数据可能从这根线出去，也可能从那根线出去，或者从别的线出去。

所以要理解互联网，最快的办法不是看图，是看人。过去几年里，我们邀请了一些助教在 Zoom 上演了一个小短剧。你可以把台上每一位——每一个人，想象成一台路由器，也就是网络上的一个设备。他们的使命是路由数据。

他们路由的对象叫**数据包**（packet）。打个比方，你可以把它想象成一个小小的白色信封，就像我们通过邮政寄信件用的那种，国内国际都寄。

> **定义**：**数据包**就是信息的载体。它足够小，可以被拆开走不同的路；它又带着足够多的地址信息，能被独立地送到终点。

### 一个信封，从右下角寄到左上角

那个短剧要表达的事其实很简单。我用大约一分钟给你讲清楚在互联网上发一个数据包意味着什么：从右下角的 Phyllis 发送到左上角那张熟悉的脸——Brian。

```text
        [Phyllis]                                  [Brian]
            |                                         |
        (路由器)-----------------------------------(路由器)
            |            \                /             |
        (路由器)------(路由器)--------(路由器)          |
            |            /                \             |
        (路由器)-----------------------------------(路由器)
            |                                         |
        [手机 / 笔记本]                            [服务器]
```

顺便说一句，屏幕上这一版看起来近乎完美，但他们全都在微笑鼓掌——因为我们拍了太多次，才终于把那个协调动作做到位。

现在假设它确实是正确的。哪怕只是这么短短一个小品，你也能捞出几个关键结论。

**第一，从 Phyllis 到 Brian 的那个"信封"，可能经过任意多个路径节点。** 它可以先向上再向左，也可以先向左再向上，甚至可以走之字形、绕来绕去。这恰恰就是今天互联网的真实写照：无论是有线还是众多无线连接，数据从起点到终点**存在多条可能的路径**。

**第二，数据甚至不一定走最短的那条路。** 它可能选成本最低的路径，也可能只是某些人工设置、或者服务器自动配置出来的路由规则的结果。

这就是为什么"包交换"这件事在概念上如此重要：你不需要一条预先铺好的专属通路，你只需要一个会转发的中间人网络，剩下的事数据包自己扛。

### 协议：我们都同意的一套规矩

简而言之，所有这些路由器、互联网上所有设备——包括你口袋里的手机和膝上的电脑——都使用同一种语言，更正式一点说，是同一种**协议**。今天这套协议叫 **TCP/IP**，它其实是一组协议的组合，规定了计算机在互联网上通信的行为规范。

人类社会中也有行为规范。我第一次见到某人时，常常会本能地伸出手，期待对方也伸手跟我相握——这就是一种人类社会的行为规范，规定了人们在这种情境下如何互动、如何交流。服务器之间遵循类似的规范，只不过它们基于文本或二进制数据，而不是肢体接触。

但 TCP 和 IP 是两种不同的协议，解决的是不同层面的问题。我们先讲后面那个——IP。

### IP：先给每台机器一个唯一的地址

**IP（Internet Protocol，互联网协议）的核心作用，是为全球每台联网设备分配一个独一无二的地址。**

这其实就是我们常说的 IP 地址。现实世界里我们也有地址——我们所在的这座建筑，纪念堂，地址是美国马萨诸塞州剑桥市昆西街 45 号，邮编 02138。这个唯一的标识符，理论上能让一个实体世界的信封从全球任何地方准确寄到这儿。IP 地址干的是同一件事，只不过它服务的是 Mac、PC、手机和网络上的所有其他设备。

IP 地址是一个数字，通常用**点分十进制**表示，格式是「某数.某数.某数.某数」。这里有个有趣的小知识：每一段的值都在 0 到 255 之间。那它到底占多少比特？

我们算一下。0 到 255 一共 256 种可能，而 $256 = 2^8$，所以每一段是 8 比特。四段加起来就是 $8 \times 4 = 32$ 比特。

> **结论**：一个 IPv4 地址是 **32 比特**。上限是 $2^{32}$，我们粗略估计为**约 40 亿**。

这个数字为什么重要？因为它直接限制了全球能接入的设备总数。40 亿听起来很多，但今天人口众多，你一个人至少就有两台设备——一部手机、一台上课用的笔记本；如果再加上智能家居这些物联网设备，只会更多。我们分配出去的 IP 地址数量已经非常庞大了。

所以全球正逐步从 **IPv4** 过渡到 **IPv6**。IPv6 不再用 32 位，而是 **128 位**的地址空间，这个数字大到足以满足可预见未来的所有需求。说句公道话，从 IPv4 到 IPv6 的过渡我们讨论了大概二三十年了，到今天还在逐步推进。不过为了课程和理解上的简便，我们还是拿 IPv4 举例——它的概念相对容易掌握。

### 拆开一个 IP 数据报

这张图看起来确实有点晦涩，但它可以说是 IP 数据报的"官方艺术图"——直接来自定义 IP 数据报的官方技术规范文档。用更通俗的话说，这就是一个数据包的**实际结构**。

```text
     0    1    2    3    4    5    6    7    9  ...  30   31
   +----+----+----+----+----+----+----+----+ ... +----+----+
   |             这一行同样是 32 比特                          |  ← 第 0 行
   +----------------------------------------------------------+
   |             同样的 32 比特 × N 行，一直排到第 31 位       |  ← 每一行都如此
   +----------------------------------------------------------+
```

我们具体在看什么呢？本质上就是一个由比特组成的网格：这里总共表示 32 个比特，从第 0 位到第 31 位，索引一直延伸到最右侧；而每一行都代表另外 32 个比特，这样逐行叠加。

也就是说，每当像 Phyllis 这样的计算机在互联网上发一个"信封"时，她的信封结构就是这样的。它至少包含这些信息——一整串比特被分解成多个字节。今天我们重点关注的是这一部分：

```text
   +----------------------------------------------------------+
   |  源地址  5.6.7.8        Phyllis 自己的 IP 地址           |
   +----------------------------------------------------------+
   |  目标地址 1.2.3.4        Brian 的 IP 地址                 |
   +----------------------------------------------------------+
   |  ……还有大量其他有用的比特信息，今天先不展开……            |
   +----------------------------------------------------------+
```

用现实世界来比喻，这就像取出那个白色信封：Phyllis 会在"信封"中间写上 Brian 的地址 `1.2.3.4`（当然这里只是方便讨论），这样这个信封才能寄到他手上。

但她肯定希望 Brian 能回复——确认收到，或者发回他自己的消息。所以她还会把自己的 IP 地址（比如 `5.6.7.8`）写在信封的**左上角**。这样当 Brian 准备发出他自己的数据包时，就知道该回复给谁。

归根结底，这一切都只是一串按特定模式发送的比特流，并且有一份正式的规范文档。这就是所有比特实际通过有线或无线方式传输时所遵循的顺序。

> **小结这一层**：IP 协议做的事情就是——确保我们每个人都有唯一的 IP 地址，数据可以通过这个地址从我们这里发出去，或者发送到这里。仅此而已。

当然，这只是众多问题中的一个。一台服务器还能做很多别的事：处理电子邮件、聊天、视频会议、游戏服务器，天知道还有什么。一台服务器能同时干多件事当然再好不过——而这恰恰就是今天的普遍情况。

顺带把两个术语交代掉：现在说的"服务器"只是一个专业术语，指一台**向他人提供信息的计算机**。相对地，我们的笔记本或台式机通常叫**客户端**，因为它们只服务我们个人，而不是很多人。但说到底，它们都还是计算机。

### TCP：一个 IP 地址还不够

IP 协议仅确保我们能在互联网上唯一地**寻址**计算机。但 TCP/IP 协议族里还有另一个协议——TCP 部分——它让计算机能够唯一地标识**它向外界提供的服务**。

TCP 协议允许一台计算机区分：发给我的这个数据包，是电子邮件？聊天消息？视频会议片段？还是别的什么？换句话说，在这些"信封"外部，除了 IP 地址之外，还有更多信息。

**端口号**。它们同样是数字，通常在 0 到 10^3 或几千以内，并且这些数值是**标准化**的。

举几个你天天在用、却从不知道的例子。当你用 HTTP 协议请求网页时——斜杠，这个符号你肯定熟悉——在你不知情的情况下，你电脑随后发出去的那个虚拟信封外部，会标上**端口号 80**。服务器收到这个请求时立刻明白：哦，这位用户是在请求网页，不是邮件，也不是别的。

如果你用的是 **HTTPS**（URL 里那个 S 代表 secure，安全），那你用的实际是**端口 443**。

这只是一个任意数字，多年前一群人在某个会议室里决定用它来标准化这个流程，仅此而已。

```text
   +--------------------------------------------- 目标地址 1.2.3.4 --+
   |  +---- 目标端口 443（紧跟在 IP 地址之后）                        |
   |  +---- 源端口（Phyllis 写在左上角，Brian 靠它回信）               |
   |  +---- 32 比特序列号                                             |
   |  +---- 另外 16 个比特用来指定端口号，所以端口总数数以万计         |
   +---------------------------------------------------------------+
```

这就是传输控制协议（TCP）的比特序列结构。除了我们刚才看到的那些标准化 IP 的几十个比特之外，TCP 还额外附加了 **16 个比特**来指定端口号，这意味着你实际可以有数万个可能的端口号——目标端口号，以及另外一些信息。

### 一个巨大的猫，被撕成四份

这里还有一个**序列号**——一个 32 位的值，实际上非常重要。

为什么？因为在互联网上发消息时，数据量通常很大。假设这只非常开心的猫是一张**非常大的 JPEG 图像**。假设 Phyllis 要把这张图发出去——如果她不把它塞进一个巨大的信封一次性传完，那就更好了：那样会妨碍其他许多用户在同一时刻使用互联网。

所以我们大胆一点：把这只猫**撕成两半**，分片，分别封装传输。

```text
   信封 1                  信封 2                  信封 3
  +-------------+        +-------------+        +-------------+
  |  左下角     |        |  左下角     |        |  左下角     |
  |  序列号 1/4 |        |  序列号 2/4 |        |  序列号 3/4 |
  +-------------+        +-------------+        +-------------+

   信封 4
  +--------------+
  |  左下角      |
  |  序列号 4/4  |
  +--------------+
```

序列号写在信封的左下角——1/4、2/4、3/4、4/4。这样当这些数据包（以及其他数据包）陆续到达目的地时，接收方的计算机就能**核对并重组**。这是一个相当大的文件，那我到底有没有收齐？能从序列号推断出来，因为我们已经把它们标注在信封的备注字段里了。

这里还可以实现许多其他功能，比如数据优先级处理。但归根结底，TCP 的意义就在这儿：**通过在这些信封外部做记录管理，来确保数据能够可靠送达**。如果接收方只收到了 4 个包中的 2 个或 3 个，因为包上有序列号，它可以立刻反馈："我缺少第 1、2、3 个包，请重发。"剩下的 3 个就补上了。

> **结论**：**IP 让我们能唯一地标识计算机；TCP 确保数据可靠传输，并允许在同一台设备上复用多种服务。**

到这里缩写词确实有点多了。什么问题都没有，那我们再讲一个。

### DNS：让你记住名字而不是数字

想想看：如果每次访问网站，Phyllis、Brian、我们所有人都得在浏览器里手动输入 IP 地址，那会非常繁琐。事实上，我们大多数人从来不需要手动输入 IP 地址。

我们访问的是 Google.com、Harvard.edu 这样的**域名**——它们对人比那些数字地址好记得多。

DNS 全称是**域名系统（Domain Name System）**。这是一种特定类型的服务器。**每个家庭实际上都拥有一台**，即使你可能没意识到；每个校园、每家公司也都有。全球有无数台 DNS 服务器，而它们的功能非常简单：**把域名翻译成对应的 IP 地址**。

这些服务器内部本质上就像一张两列表格：

```text
   +-------------------------+-------------------------+
   |  域名                   |  IP 地址                |
   +-------------------------+-------------------------+
   |  google.com             |  某个 32 比特数字       |
   |  harvard.edu            |  某个 32 比特数字       |
   |  ...（全世界的域名）    |  ...（对应的地址）      |
   +-------------------------+-------------------------+
```

真实情况是这样的：当你的 Mac、PC 或手机尝试访问 Google.com 时，设备本身——尤其是在刚启动时——**根本不知道对应的 IP 地址**是什么。苹果或谷歌公司可不会在我们的设备里预装几十亿个 IP 地址。

但你的设备足够聪明。它会向家庭、校园或工作场所的**本地网络**发出查询请求：Google.com 的 IP 地址是多少？Harvard.edu 的 IP 地址是多少？等你从本地 DNS 服务器拿到答案之后，设备实际执行的操作就是：**把对应的 IP 地址标注在数据包的"信封"外部**。

这项实用的服务让互联网对我们来说好用太多了。

#### 域名是怎么来的

从技术上讲，这些名称叫**完全限定域名**。它们从哪儿来？你们当中可能有人已经有自己的个人网站了，那你就已经经历过这个流程。

获取域名其实没那么难。你可以去任意一家**域名注册商**付一笔钱——本质上这是一种**租赁服务**。按年租也行，一次性租 3 年、5 年也行。费用可能低至每年 1 美元，也可能高达每年数千美元，取决于这个域名有没有被别人抢注、或者被人囤积着。

付了钱，你就获得这个域名的使用权。然后在技术层面，你需要配置全球某处的 DNS 服务器，让它指向真正为你提供网页的服务器 IP 地址。

#### 根服务器与层层缓存

我之所以说"你家里、办公室、校园里都有 DNS 服务器"，是因为这个结构是**高度层级化**的。

全球分布着一些所谓的**根服务器**，它们掌握着所有 `.com`、`.edu` 等顶级域名的信息——但我的 Mac 电脑并不知道这些信息。所以 Mac 通常会**先问本地网络**：在家就问家里的 DNS 服务器（在那个集成在路由器里的小盒子中），在学校就问哈佛的 DNS 服务器。

整个设计是**递归**的。借用几周前我们提到过的一个术语：如果哈佛的服务器也不知道答案，查询就会被一路提升到那些根服务器，拿到结果，然后**把结果缓存起来**——沿途所有其他 DNS 服务器都会记住它。

```text
   [你的 Mac / PC / 手机]
          │  「google.com 的 IP 是什么？」
          ▼
   [本地网络里的 DNS]
   家里：集成在家用路由器里的小盒子
   校园：哈佛的 DNS 服务器
          │  我也不知道 → 继续往上问
          ▼
   [根服务器]  掌握 .com / .edu 等顶级域名的信息
          │
          ▼  答案沿路返回，沿途每一台都把它缓存下来
   google.com  →  1.2.3.4
```

所以这是一个非常优雅的层次化设计，但归根结底它做的事就这么点：一张庞大的域名与 IP 地址对照表，服务器在为我们做查询响应。

### DHCP：开机时那句"Hello world"

那我怎么知道我的 Mac 该用哪个 IP 地址？我怎么知道该向哪台 DNS 服务器查询、以及**它的** IP 地址是什么？我又怎么知道该把数据转发给哪台路由器、**它的** IP 地址又是什么？

我们刚才讨论的整个流程里，其实隐含了一堆前提假设。答案呢，说来有点无奈——**又得提到一个缩写词了**。

**DHCP，动态主机配置协议**，就是解决所有这些问题的关键。不过它并非从一开始就存在。

在我那个年代，我们得**手动**配置这一切：手动输入电脑的 IP 地址（这地址通常还是别人口头告诉我们的），手动输入 DNS 服务器的地址，还要手动输入路由器的网关地址。

现在，DHCP 已经作为一项服务，普遍部署在家庭网络、校园网和企业网络中。它的核心功能就是自动响应设备提出的这类配置请求。

当你首次启动 Mac、PC 或手机时，设备本质上会广播一条"Hello world，**我的 IP 地址是什么？**"式的请求。不管是有线还是无线，本地网络中通常都会有一台 DHCP 服务器在运行。它会依据哈佛、康卡斯特、威瑞森，或者某个家庭用户的预设配置，回答你的设备：

- 你的 IP 地址是多少；
- 本地路由器的 IP 地址是什么；
- DNS 服务器的 IP 地址是多少。

正因如此，今天我们只要连上 Wi-Fi 或者插上网线，设备就能自动配置好并开始正常工作。

> **提示**：DHCP 不是一直就有的东西。它出现之前，"能上网"这件事的前提是先有人会手配参数。今天它已经是网络连接中不可或缺的组成部分——这真是件好事。

关于网络外围配置就讲到这里。今天接下来的内容，我们深入网络通信的核心机制：实际发送和接收的数据报文长什么样，怎么构建网页结构，怎么设计从服务器返回给客户端的完整内容。

### 把一个 URL 拆开来看

那么，让我们深入这个缩写词：**HTTP，超文本传输协议**。它的核心功能就是请求网页、接收网页内容。它是一种通信协议，主要对网络通信中数据报文的**内容格式**做了标准化。电子邮件有邮件专属的协议，Zoom 有 Zoom 的，Discord 有 Discord 的，各类互联网服务都有自己的协议标准。我们今天聚焦 HTTP——它通常使用 80 和 443 端口。

这是一个典型的 URL 结构：

```text
   https      www.example.com                     /file.html
   └─ 协议 ─┘  └───── 主机名 ─────┘  └─ 顶级域名 ┘  └── 路径 ──┘
```

URL 的作用是帮我们**定位到正确的地方**。但我们还得知道每个零件叫什么、各自负责什么。

#### 路径：斜杠、根目录与 index.html

当你访问 `https://www.example.com/` 时，实际上是在请求该网站的**根目录**——也就是默认文件夹。这里高亮显示的那个斜杠表示的就是这个意思：请求获取默认网页。

从技术角度说，浏览器在后台实际接收的是一个**具体的文件**。按照惯例，这个文件通常被命名为 `index.html`，也可能是 `index.htm` 或别的名字。但如果每次访问网站都得手动敲文件名，那显然非常不方便。所以服务器默认直接返回根目录的内容，也就是网站的默认页面。

如果你访问的是网站内的某个文件夹，或者点击了指向特定文件的链接，域名后面通常就会跟一个完整的路径。这个路径可以包含零个或多个文件夹名，加上零个或一个文件名：

```text
   file.html              只指定一个文件
   folder/                只指定一个文件夹
   folder/file.html       文件夹 + 文件
```

其实即使你平时没特别留意，这类路径格式在你上网时可能已经见过成千上万次了。

#### 顶级域名：.com、.edu 与那些被抢走的

再说域名左侧。`something.something.com` 里的 `.com` 代表商业用途，更具体地说，`.com` 叫**顶级域名**，简称 **TLD**。

过去顶级域名的种类非常有限：`.gov`（政府）、`.com`（商业）、`.net`（网络）、`.org`（组织）、`.edu`（教育），等等。如今顶级域名的数量已经大幅增加——即使没有上千种，至少也有数百种。

其中许多在实际应用中并不常见，但也有一些**不在最初列表里、却被广泛使用**的域名。比如 CS50 就经常用 `.io`。这个后缀**并不是**指输入输出（Input/Output）——实际上 `.io` 是一个双字母的国家代码域名，本质上已被租用为通用顶级域名。我们以及所有用同一个顶级域名的人选它，只因为在英语世界里 `.io` 听起来确实挺酷，隐约传递出一种科技感。

`.tv` 是个类似的例子：它原本属于某个国家的域名，但在英语中恰好和"television"的缩写撞上了，于是也被广泛用作相关领域的顶级域名。

总的来说，这类顶级域名确实存在：有些如今已经是完整的单词，有些则用两个字符表示它所属的国家。

#### 主机名：Www 背后可能是几百台服务器

许多 URL（但并非全部）在域名左侧还包含一个**主机名**。从技术角度说，主机名特指你请求的**具体服务器名称**。

它不一定非得是字面意义上的一台服务器。`www` 可以指代数十、数百、乃至数千台服务器。

你访问任何一个热门网站——比如 gmail.com 之类的——尽管你只输入了一个域名，但从技术层面说，它实际指向的可能是由**数百甚至数千台服务器组成的集群**。这些服务器集群的设计，正是为了确保能够处理所有可能访问该网站的用户流量。

#### 协议：http 与 https

最后是**方案**，也就是我们今天讨论的重点。

它通常会是 `https`，这很理想，因为它通过某种方式实现了安全加密。当然也可能是 `http://`。

```text
   https://   →  443 端口，加密传输
   http://    →   80 端口，明文传输
```

现在我们已经养成了不手动输入协议前缀的习惯，但浏览器在你输入 `http://` 的情况下会确保——可以说——自动把你重定向到该网站的安全版本。这一点我们马上就能实测。

### 信封里写的不是代码，是被规范好的文本

那么这些"信封"内部究竟长什么样？URL 只是帮我们定位到正确的地方——我们该怎么用某种形式的代码来表达"我想以这种加密方式，从这个服务器拿到这个 file.html"？

在 Phyllis 发给 Brian 的那些虚拟信封里，装着这样的消息：**GET**、**POST**，以及一系列其他的请求方法。HTTP 支持一系列操作或请求方法，主要包括 GET、POST 以及其他几种。

我们只用得上 GET。Phyllis 最初放进信封的正是 GET，用来实现她脑子里那个请求——拿一张猫咪图片。

具体来说，她的信封内部包含这样一条**文本消息**：

```text
   GET / HTTP/2
   Host: www.harvard.edu
   （可能还有其他一些信息行）
```

**这本身并不是代码**。里面没有函数、没有循环、没有变量。它之所以叫"协议"，是因为多年前人们就把这些消息的格式标准化了。你想从服务器拿网页，就得往信封里放对应的消息。

为什么要指定 `Host`？因为 Brian（现在成了 www.harvard.edu）可能在同一台物理服务器上同时处理多个任务、托管好几个域名，所以 Phyllis 得说明自己实际想访问的是哪一个。

如果一切顺利，Brian 会用一个装着 HTTP 响应的信封回复：

```text
   HTTP/2 200 OK
   Content-Type: text/html
   Date: ...
   （以及其他一些相关信息）
```

Brian 会在自己的信封里注明返回给她的**内容类型**，因为那可能是 HTML 格式，也可能是 JPEG 格式、GIF 格式，或者其他多种文件格式。这只是给 Phyllis 的浏览器一个提示：告诉你接下来收到的信封里装的是什么。

尽管其中一些细节在视觉上并不直观——如果你之前从未真正思考过这个问题，可能会觉得有点陌生——但事实是，我们这些有抱负的程序员**完全可以查看并探索这些基础构建模块**，而且今天就能用上它们。

### 用 curl 把信封拆给你看

接下来你会看到一个叫 **curl** 的程序，它的名字是 client URL——连接 URL。它已经安装在 CS50.dev 这样的 Linux 系统里，通常也预装在 Mac 和 PC 上，或者你很容易装上。

本质上它是一个**无头浏览器**：它模拟浏览器的行为，通过实际发送上面那种信封内容，去获取服务器的响应。

curl 有个非常好用的开关，就是 `-I`——**只显示响应头部信息**，也就是我们刚才讨论的那些文本内容，而不真正下载页面的任何正文。

```bash
curl -I https://www.harvard.edu
```

如果我在浏览器里输入这个网址，我看到的是哈佛大学的主页。但用 curl，我只看到信封内容以黑白文本的形式显示在屏幕上——**只有前几行**，服务器响应的所谓"头部信息"。

回车之后你会看到，返回的**每一项都带着 200 OK**。这是一种约定俗成的惯例，200 意味着一切确实正常。这里还有许多其他信息：服务器返回响应的具体日期和时间，内容部分——包含类型、文本行、HTML——以及一大堆附加信息。

> **提示**：想看真实的头部信息，其实你一直都可以用自己常用的浏览器做到。现在大多数浏览器都内置了开发者工具。后面我们马上就会用上它。

### 状态码：服务器用数字回话

200 OK 显然是最理想的结果，但绝不是唯一的。服务器还能返回一系列其他状态。

| 状态码 | 通俗含义 | 谁的锅 |
|---|---|---|
| `200 OK` | 一切正常，页面在这儿 | —— |
| `301` | 资源**已永久移动**，请去新地址 | 服务器的指示 |
| `300` 段 | 各种"跳转到别处去" | 服务器的指示 |
| `404` | 文件未找到 | 路径/地址写错了 |
| `400` 段 | 客户端请求有误 | 你，或者你写的代码 |
| `500` 段 | 服务器那边出问题了 | 可能是服务器不可用，或程序员埋了 bug |
| `418` | 愚人节玩笑，不是正式规范 | 纯属内部梗 |

#### 301：一次自动发生的重定向

我们先看 301 到底意味着什么。**301 表示"资源已永久移动"**。当服务器向浏览器返回 301 时，意思是：这里没有你要找的内容，请前往这个新位置。这就像在服务器上挂了一个绕行标志。

我们可以直接复现。先访问非安全版本：

```bash
curl -I http://www.harvard.edu
```

这一回，哈佛的服务器没有直接返回 200 OK，而是给出了 **301 永久重定向**。往下看输出行，能看到我应该实际访问的目标地址——有一个细微的差别：它**强制把我重定向到 HTTPS** 协议，而没有直接显示哈佛网站的内容。

我自己可能不会注意到这个变化，因为我们早已养成了不手动输入协议的习惯。但浏览器会替我们把这事办了。

#### 404：一个意外地广为人知的数字

下一个状态码，你可能在网上见过很多次了：**404**——文件未找到。它成了一个奇怪地广为人知的神秘代码。

我们也来造一个。我假设哈佛大学有一个专门研究猫的院系——但它其实并没有：

```bash
curl -I https://www.harvard.edu/cats
```

返回的是 **HTTP 404**，表示这个网站其实并不存在。如果我在浏览器里访问这个地址，很可能会看到一个错误页面。这个页面**可能**会显示 404 提示，也可能不显示——不过很多网站（甚至可以说大多数网站，无论好坏）都会把这个状态码展示出来，以至于在座的各位可能都对它很熟悉。

可要回想一下，404 的最初身份是什么？它不过是一个深藏在 HTTP 头部信息里、非常底层且晦涩的状态码，就像封装在这些数据包里的秘密代码。

#### 500 和 418

`500` 段就严重了，这意味着**服务器那边**出了问题：可能是服务器暂时不可用，也可能是程序员在代码里埋了 bug 导致服务器崩溃——出现"内部服务器错误"这类情况。

我们还加了个 `418`。它其实不是正式规范，但挺有意思：多年前的一个愚人节玩笑，一群觉得好玩的人正儿八经地写了份规范，规定服务器返回 418 时该表示什么意思。是个内部梗，现在看可能没那么好笑了，但它已经算是互联网文化的一部分了。

#### 一个付了 20 年租金的玩笑

说到玩笑，我们来试一个：

```bash
curl -I http://safetyschool.org
```

天啊，看看我们到哪儿了。

它是怎么实现的？把刚才没说完的话讲完：只要查看我的浏览器在过去大概 20 年里发给 safetyschool.org 的那个信封内部的 HTTP 头部信息，你就能看到——**某位哈佛校友一直在支付这个域名的租金**，目的就是为了实现这个小把戏：让"301 永久重定向"生效，把访问者永远送到 `yale.edu` 去了。

如果你去 Reddit 之类的地方深挖一下，还能发现不少类似例子，比如斯坦福和伯克利。东海岸与西海岸之间确实存在着良性的竞争——但归根结底，这全都源于对 HTTP 协议，也就是那个规范"数据如何从浏览器传到服务器"的协议，有着非常深入的理解。

### 把浏览器拆开看

当然，你其实一直都能用自己的浏览器做这些事。我现在用的是 Chrome，不过现在大多数浏览器都内置了开发者工具——通常能在菜单里找到开启选项。对于稍微懂点编程的人来说，这非常方便，你可以借此深入到浏览器底层看具体发生了什么。

我特意用了**无痕模式**（原因下周会讲到）：这样会自动清除所有的 Cookie 和浏览记录。今天我假装自己是第一次使用，浏览器行为就会完全符合预期。

在无痕窗口里打开开发者工具——Safari、Edge 和其他一些浏览器里界面看起来也几乎一样——你会看到几个标签页：

- **元素（Elements）**：网页一加载完，这里就显示该页面的**所有元素**，包括我们即将编写的 HTML 代码；
- **控制台（Console）**：有时错误信息会显示在这里，它的作用类似 VS Code 里的终端窗口；
- **网络（Network）**：浏览器正在向服务器发起请求。这正是我认为我们应该开始关注的地方。

我点开"网络"标签，并且**勾选"保留日志"、禁用缓存**，这样所有内容就不会被自动清掉，行为完全符合预期。

现在，在这个无痕窗口里第一次访问 `http://safetyschool.org`。回车后你会看到一系列输出，包括一条警告——如今不支持 HTTPS 的网站出现这种情况越来越常见了，而这位一直没付那笔钱（没配 HTTPS）的校友还在坚持。警告通常会明确告诉你：全世界——至少是你与目标服务器之间的所有节点——都可能知道你正在访问什么。

我可以点"继续访问"忽略它。一旦这么做，底部会刷出更多输出，看起来相当繁杂。

请注意左下角：**仅仅访问 safetyschool.org 这一个地址，就产生了 61 次 HTTP 请求**——相当于来回传递了 61 个数据信封。

不过我把目光放在最顶部的几条记录上。服务器返回的信息是**"301 永久重定向"**，请求方法是 **GET**，这里还提到了相关的 IP 地址，以及一大堆我们今天暂时不深入的内容。所以一直以来，你看到的都是同一套东西。

我们再用猫试试。点"捉鬼敢死队"图标清空开发者工具里的全部记录，缩小窗口，访问 `https://www.harvard.edu/cats`——按 curl 的反馈，这个路径并不存在。

回车后确实看到了一个网页。有意思的是：哈佛选择用一种**相当隐晦的方式**向访客显示 404——这个数字本身除了状态码的含义之外没有别的意义。

但如果我滚动查看生成这个高度图形化页面所涉及的全部 **59 个请求**，然后回到最顶部，点开第一行对应 `cats` 本身的那条记录，你就能看到：我的确用 GET 方法请求了 `cats` 这个最终 URL，而服务器返回的的确是 **404 未找到**。

> **提示**：这类有趣的东西你完全可以自己去挖。只要揭开浏览器一直以来对你隐藏的那层技术面纱就行。

### 在别人的网页上动手改一个字

接下来我们要深入一种实际的语言——不是编程语言，而是一种**标记语言**：**HTML，超文本标记语言**。它的唯一使命，就是告诉浏览器应该在屏幕上显示什么内容。

我访问 stanford.edu，屏幕上会快速闪过一大堆内容。这次我切到"元素"面板，你看这里显示的**所有内容就是所谓的 HTML 代码**。这些代码是由某些人、团队或软件生成的——斯坦福大学的工作人员编写了这些代码，从而创建了斯坦福的主页。截至今天，这个主页看起来非常美观。

不过斯坦福编写用于生成这个网站的代码，有一个有趣之处：**它是作为副本发送给我的。**

这与我们迄今为止写的代码截然不同。当你在 Scratch 里写代码时，代码实际上存在于浏览器中，并存储在麻省理工学院的服务器上；当你写 C 代码并运行时，代码是在 codespace 内部执行的，不会提供给任何可能访问它的用户。

然而网络的工作方式略有不同。这些信封里装着的，是服务器上那些内容的**副本**，被发送到浏览器。因此，**是你的浏览器——也就是所谓的客户端——在从上到下、从左到右地读取这些 HTML 代码，并解析出该如何显示它们**。它本身并不是在服务器上执行的。

不过下周这个故事会有些变化：当我们开始用 Python 动态生成 HTML 时，就不再需要像这一周这样手动编写所有代码了。但就目前而言，你所看到的一切都是代码运行的结果——这是浏览器执行斯坦福编写的代码所产生的结果。

这意味着我们可以用同一套开发者工具玩点花样。我在斯坦福主页正中央的 **Stanford** 那个词上按住 Control 键点击（或者右键），选择"检查"。

开发者工具的一个优点是：它们会**直接跳转到创建这个元素的那一行代码**。这是一个极佳的教学与学习工具——接下来的日子里，当你学着理解更多 HTML 知识时，你可以对互联网上的**任何网站**这么做。如果有人实现了一个你非常喜欢的设计，你就能通过观察别人的网站去理解他们是怎么构建出类似效果的。

你会看到 "Stanford" 这个词就躺在页面的源代码里。为了好玩，我把它改成 "Harvard"，按下回车——现在斯坦福的网站看起来就像我们去过那里，甚至像是被我们"黑"过一样。

当然，要真正黑进斯坦飞的网站可没那么容易。**我只是修改了该网站在我本地设备上的那份副本。** 如果我点刷新图标，斯坦福的网站看起来还是原来的样子，无论好坏。

但这恰恰说明了：我们在浏览器中其实拥有一定的控制权，能够实际动手操作并学习它的底层运行机制。

### HTML：一种不需要运行的语言

那么让我们深入了解 HTML 这门语言。

它**不是**编程语言——没有循环，没有条件语句，变量方面也没有真正的复杂性。整门语言其实只有**两个**核心术语：标签和属性。大部分情况下它更像一种实践练习：归根结底，就像查阅其他现成的标签一样，读文档、摸索着怎么用它们来构建网站。虽然这些构建模块背后确实蕴含着一些有趣的设计理念。

现在来看一个可能是最简单的网页。

```html
<!DOCTYPE html>
<html lang="en">
    <head>
        <title>hello title</title>
    </head>
    <body>
        hello body
    </body>
</html>
```

这就像是斯坦福团队在他们服务器上写的那份代码的**迷你版**——只有十几行，而不是成百上千行。

如今编写的任何网页，只要用的是最新版本的 HTML（目前恰好是第 5 版，即 **HTML5**），代码的开头部分都长这样：

```html
<!DOCTYPE html>
```

这个基本上属于"需要你记住或者直接复制粘贴"的内容。它看起来有点不同，因为我们平时**不会**用感叹号——在大多数情况下，感叹号语法只在 HTML 注释里出现。所以 HTML 也有注释，就像 Python、C 和其他编程语言一样。

### 元素、标签与属性

我们把注意力集中到这个更核心的部分上。你在这里看到的就是 HTML 里所谓的**元素**：一个元素包含一个**开始标签**和**一个结束标签**，或者说开标签和闭标签。

以 `<html lang="en">` 为例。浏览器从上到下、从左到右读到这个文件时，这行本质上在告诉它：好的，浏览器，接下来是我网页的 HTML 内容，并且这个页面的内容是用**英语**写的。

拆开看这三个部分：

- `html`（全小写）是**标签名**，同时也是元素名；
- `lang` 是**属性名**，它用来修改元素的默认行为；
- `en` 是**属性值**，英语的缩写。大多数人类语言都有对应的缩写表示。

所以这里就是一个标签名加一个带值的属性。我们在字典、哈希表或者许多其他上下文里已经见过无数次这种**键值对**形式。在 HTML 中，键值通过等号分隔，值通常用引号括起来——**双引号或单引号都可以，但要保持一致**。

而文件末尾那个对称的部分，作用是**闭合标签 / 结束标签**，它在告诉浏览器：我的 HTML 内容到此结束。其他所有内容都遵循类似的模式，位于这些标签内部。

于是整个文件读起来就像浏览器在跟你对话：

```text
   浏览器，接下来是我页面的头部内容。          <head>
   浏览器，页面的头部内容到此结束。            </head>
   浏览器，在头部里面，接下来是标题。          <title>
   标题部分到此结束。                        </title>
   浏览器，现在来的是页面的主体部分。          <body>
   主体部分的内容就到这里。                  </body>
```

标题就是 `hello title`——正如我在 codespace 里写的那样。主体部分的内容则真的就只有 `hello body` 这一句，它会占据屏幕大约 **95%** 的空间，也就是所谓的**视口**；而页面标题显示在上方的标签页里。

> **易错点**：缩进整齐、排版美观是值得坚持的。我用了 **4 个空格**缩进，这是常见做法，虽然并非严格必需。事实上在我自己的 codespace 里，我甚至懒得把它们拆成三行来写，直接写成一行——这完全没问题，因为**浏览器通常会忽略空白字符**。缩进是为了让我们人类读起来舒服，不是为了让机器看。

### 把 hello.html 挂到网上

上面这份代码大概率会被存放在一个叫 `file` 的文件里——无论叫 index.html、Stanford.html，还是别的什么名字，它本质就是**文件内部包含的内容**。你可以把它存在自己的 Mac 上，双击，浏览器就会加载它。

但如果这个文件只存在你的 Mac 或 PC 本地，那**全世界只有你一个人**能看到这个网页。所以我们当然要把 HTML 写在服务器上——这样你自己、以及理论上（尤其是对你们的期末项目来说）全世界任何能连上互联网的人，都可以访问相同的内容。

在 CS50.dev 里，我们要用到一个新命令：**`http-server`**。它的核心功能就是**通过 HTTP 协议来提供文件服务**。

这里有个挺有意思的设计。如果我们用的是 CS50.dev（也就是 GitHub Codespace），那么这个网站本身**已经**有一个 Web 服务器在跑着了。因为当你访问 CS50.dev 并登录后，会被重定向到一个更长的网址——那时你用的其实是一个 Web 应用，也就是 **VS Code**，它让你能在云端写代码。

默认情况下，这个应用运行在 **80 端口和 443 端口**上，所以无论你通过 HTTP 还是 HTTPS 访问都一样。但这也意味着我们今天写的代码、以及你们接下来要完成的习题集或期末项目，**都不能占用 80 或 443**——托管这个环境的 GitHub 已经占用了它们。

不过我们可以使用其他任意端口号。之前提过，端口号有成千上万个。

实际流程就是这样：

```bash
# 1. 新建一个文件
touch hello.html

# 2. 在里面写上那十几行 HTML

# 3. 起一个 HTTP 服务器，提供当前文件夹的内容
http-server
```

屏幕上会刷出一大串文本，其中有一个绿色的 **"Open Browser"** 按钮——点它就能用网页浏览器打开当前文件夹的内容。

我提前准备好了今天的代码文件夹（`source8`，包含今天所有预先准备好的示例），这就是我刚才创建的文件。现在我的 URL 变了。点开它，就能看到 `hello` 的内容；如果我只点文件夹本身，看到的是一个**目录列表**——我 codespace 里所有文件的索引。

> **注意**：`http-server` 启动后**不会**占用默认的 80 或 443，因为 GitHub 已经占用了。它默认选的是另一个常见的**开发端口 8080**。这个数字有趣的地方仅在于它看起来像两个 80 摆在一起——但这只是人为约定俗成的惯例，它本可以是成千上万种其他数字中的任意一个。

终端里那个你可能见过但从未在意过的 **"端口"（Ports）** 标签页——今天我特意没把它藏起来——正是在这里。跑完 `http-server` 之后，你会看到一行提示，大意是："嘿，你刚刚在 8080 端口上启动了一个 Web 服务器，要不要打开一个新标签页？"如果点那个绿色按钮，它就自动帮你完成了。

> **易错点**：别把 8080 当成某种规定。它就是个人为约定。换任何一个没被占用的端口，功能完全一样。真正要紧的是记住前面那条结论——**端口号是标准化的数字**，80 是网页、443 是安全网页。

### 浏览器里那棵树

现在回头看我们写的那份 HTML。它看起来是一段线性的文本，但浏览器做的事不是"照着文本念"。

> **结论**：当浏览器从上到下、从左到右读完这个文件之后，它其实**在内存里构建了一棵树形结构**。

```text
   html
   ├── head
   │   └── title
   │       └── "hello title"
   └── body
       └── "hello body"
```

所以我们又回到了前面某一周讨论**树形结构和其他层次结构**时的那个概念。HTML 文档不是一段扁平的字符串，而是一棵树；元素可以嵌套元素，而浏览器会把这棵树忠实地渲染成你眼前那个占了 95% 视口、正上写着 `hello body` 的页面。

这个念头先放在这儿——下周我们开始写和 Web 服务器交互的代码时，这棵树会变成可以编程操作的东西。

## 把网页拆成一棵树：HTML 的结构与语义标签
> 对应块：BLK26 | 覆盖分集：P10中1 | 块标题（分集名）：《HTML 文档结构与语义标签》

先想象屏幕上只画了一个椭圆——它代表全部内容，代表整个文件。按惯例，一个文档以单个根元素开始，通常就是 `<html>`，而且每个页面只能有一个这样的元素。那它里面装什么呢？装 `<head>` 和 `<body>`：`<head>` 里通常放一个 `<title>` 标签，标签中间是真正会显示在标签页上的文字，比如 `hello title`；`<body>` 里则是用户在页面上看见的正文。

就这么简单。可就是这么一个椭圆，我要用一整讲把它拆开。

### 一棵树就是整个文档

上面那套结构，用一棵树画出来大概是这样：

```text
hello.html
└── <html>                 ← 唯一的根元素
    ├── <head>
    │   └── <title>
    │       └── "hello title"
    └── <body>
        └── 文本内容
```

关键在于：浏览器拿到这个文件之后，**并不是**把它当成一个扁平的字符串存起来。我前面反复提到浏览器在下载文件时——它确实是从上到下、从左到右地读取文件内容的，这没有疑问；但与此同时，它会在内存里动态地分配节点、节点、节点，一个接一个，逐步构建出这样一棵**树形数据结构**，然后把这棵树存在浏览器的内存、也就是 RAM 里。

所以这里有两件并行的事：一边是磁盘上一个按字符顺序排列的文件，一边是内存里一棵有结构、有层级的树。你在网页里看到的任何一个标题、每一段文字，在内存里都不是一段文本，而是树上的一个节点——它们有父节点、有兄弟节点、有祖先。

> **提示**：这一点和我们之前讨论过的内容直接相关。内存、指针、结构化数据，这些概念今天又用上了。网页不是"一堆文字"，是"一棵树"。

今天剩下的内容，结构上都和这棵树类似，只是再多介绍几个标签和属性，让你们对大多数网站的基本构建模块有个概念。说实话，很快你就会发现手写这些东西开始有点乏味了——所以我今天会大量用复制粘贴来提速。

但这恰恰引出我们下周要重新引入 Python 的原因：**用 SQL 之类的语言自动生成 HTML**。如今几乎所有网站和许多移动应用都是用 HTML 写成的，但人们越来越少手动写这类代码了；相反，人们写的是能够精确生成这些内容的代码。所以理解这些基础知识依然很有用——不然你不知道下周以及以后，该让程序生成什么。

### 浏览器不认换行，只认标签

我们来实现一个不止一行文字、而是包含几个段落的网页。新建 `paragraphs.html`，然后回到 `hello.html`，全选、复制、粘贴，把每个页面的标题改成和文件名一致（这是我个人的习惯，好让我随时知道自己在哪个页面）。

我实在不想浪费时间去手写完整的段落，所以我在终端里请了个忙，让它生成三段关于计算机科学的文字，具体写什么无所谓，我想要的只是动态生成的文本。顺带还附送了一个教学性的答案，不过今天我们真正关心的只有这三段文本本身。把它们选中，回到 `paragraphs.html` 的 `<body>` 里粘贴进去——段落太长，文字都滚动起来了，我至少缩进两次，让排版看起来整齐一些。

回到浏览器，点击目录列表里的 `paragraphs.html`。哪里看起来有问题？

**没有段落显示。它只是一大段连在一起的文本。** 文字内容完全相同，但第一段的结尾和第二段的开头混在了一起，第三段也一样。

这是怎么回事？浏览器其实并不太在意空白字符，你可以随意添加任何空白字符，这种情况下它会直接忽略这些空白，最终至少会在每个文本段落之间保留一个空格。所以这里确实非常讲究细节：如果你想要更多的段落，你需要明确告诉浏览器——"这里放一个段落，那里放一个段落"。

幸运的是，实现这一点并不难。进入主体部分，打开一个标签，简称为 `<p>`，代表段落。

```html
<p>
    第一段：这里放一个段落。
</p>
<p>
    第二段：这个段落到此结束。
</p>
<p>
    第三段。
</p>
```

顺便说一句，VS Code 在这个具体场景下有点烦人：它试图帮我自动补全闭合标签，但它不知道我已经写好了这段文本，所以我直接删掉它自动加的那部分，再手动缩进。现在，实际上是 `<p>` 标签重复了三次——开始、结束、开始、结束、开始、结束，一共三次。

回到浏览器，看起来似乎还没有任何变化？**这是因为你现在看到的还是刚才下载到本地的那份副本**——这也是我们为什么需要刷新网页来获取最新版本。刷新，瞧，三个真正的段落出现了。浏览器会自动为段落插入空白（默认的上下外边距），至少现在看起来更美观了。

> **易错点**：改完代码一定要刷新。不刷新，你看到的永远是旧版本——这个毛病我待会儿还会犯一次，你就等着看吧。

### 标题把重要性写进了结构

当然，如果我们要写论文、博客文章或者类似的东西，通常会希望页面有不同层级的标题：章节标题、小节标题、更细分的子标题等等。HTML 在这方面也能帮忙。

新建 `headings.html`，同样先粘 `hello.html` 的骨架，然后干脆把段落内容复制过来（保留同样的文字内容，效果看起来更好），再把标题改成 `headings`，开始动手：

```html
<h1>1</h1>
<h2>2（讨论部分）</h2>
<h3>3</h3>
```

回到浏览器目录列表点进去：文字还是那些段落，但现在你看到了一些大号粗体的文字，很像章节标题、小节标题、子标题，或者新闻网站、博客网站上常见的那种标题样式。

我们有 H1 到 H6 这六个标题标签，从最大最粗一直到较小但仍然保持粗体，**所有样式设置都由浏览器自动决定**——你不需要告诉浏览器"标题该多大"，它自己知道。

但对我来说，这带来的其实是**语义上的清晰度**：页面上最重要的内容（至少一开始是这样）很可能就是那个 H1，而其他所有内容——支持性的段落、论点等等——都围绕它展开。这里隐含着一种层级结构。所以标题不只是一件视觉上的事，它同时是一句关于"什么更重要"的声明。

> **提示**：我并不太在意这些标签具体叫什么名字，我只想展示一下它们的功能。但请你记住：**H1 到 H6 是有顺序、有层级含义的**，写的时候别把它们当成六种一样的东西随便用。

### 列表：让计算机替你数数

我们还能用网页做些什么？要不我们直接列个值列表怎么样？列表在互联网上随处可见。新建 `lists.html`，粘好骨架，把 `<body>` 里刚才做的全部删掉，重新来。

之所以复制粘贴，纯粹是为了避免一遍又一遍地重复编写那些样板代码（`<html>`、`<head>`、`<body>` 之类），好让我们集中精力看新内容。新内容是一个值列表：单词 foo、bar、baz。这有点像数学家常用的 X、Y、Z 那种表示方式——作为占位符，计算机科学家通常会选用像 foo、bar、baz 这类没有实际意义的单词。

在浏览器里点开这个文件，会看到什么？是一大团连在一起的文本。"看起来像不像列表"其实并不重要，它只会变成一段接一段的文本，中间仅用一个空格分隔，而不是我之前那种多行的格式。所以这里我们又得讲究得细致一点。

如果我想要一个值列表，就需要使用**能表达此含义的标签**：

```html
<ul>
    <li>foo</li>
    <li>bar</li>
    <li>baz</li>
</ul>
```

`<ul>` 是无序列表，它会生成带项目符号的列表；在它内部，我声明一系列列表项 `<li>`（list item），内容可以是任何你想放进列表的东西。回到浏览器刷新——熟悉的项目符号列表出现了，这种样式你在很多网站、**Google 文档**里都能见到。

Google 文档是怎么实现的？在底层，他们其实就是用了 `<ul>` 标签，并在其中嵌套了一些 `<li>` 标签，从而呈现出项目符号列表的效果。当你点击 Google 文档这类工具中的相应按钮时，这一切就自动完成了。毕竟说到底，Google 文档本身也只是一个网站而已。

那如果我想给这些内容加上序号呢？当然可以直接手动标上 1、2、3，这没问题。但说实话，计算机本身就能快速计数，而且配合循环功能效率更高。如果之后我想在某些元素之间插入新内容，手动调整序号会有点麻烦——我得手动把所有序号重新调整一遍。我是说，这正是计算机擅长处理的事情之一。

不妨猜猜看：如果我不想要无序列表，而是需要一个带编号的有序列表，你觉得应该改哪里？没错，把开始标签和结束标签都换成 `<ol>` 就行。刷新，列表显示为 1、2、3。

而且你完全可以用它来生成完整的目录结构：可以使用子项目符号或子编号，就像目录里那样，HTML 能在这里自动帮你实现这些功能——嵌套的 `<ul>` / `<ol>` 里再放 `<li>`，编号和层级全部由浏览器替你维护。

### 表格：行、列和表头

那如果是要用行列形式展示表格数据呢？这个我们也能实现。新建 `table.html`，粘骨架，清空 `<body>`，然后手动创建一个简单的表格：

```html
<table>
    <tr>
        <td>1</td>
        <td>2</td>
        <td>3</td>
    </tr>
    <tr>
        <td>4</td>
        <td>5</td>
        <td>6</td>
    </tr>
    <tr>
        <td>7</td>
        <td>8</td>
        <td>9</td>
    </tr>
    <tr>
        <td>*</td>
        <td>0</td>
        <td>#</td>
    </tr>
</table>
```

在一个 `<table>` 标签内，我用 `<tr>` 表示表格行（table row）；在这一行里，我放表格数据标签 `<td>`（table data），里面写上数字 1、2、3。在表格行之外再放一行、放第二行、第三行——略显繁琐，对吧？

猜猜看，我们这是在用 HTML 做什么呢？**就像电话键盘一样。** HTML 本身不会让页面变得很美观，但我敢说，这和你打开手机拨号应用、开始输入号码时看到的界面几乎一模一样：这就像一个数字键盘，通过行列布局自动为我排列好了。

现在它看起来有点平淡无奇，所以让我打开一个我事先准备好的文件 `favorites.html`，它更巧妙地运用了表格：

```html
<table>
    <thead>
        <tr>
            <th>timestamp</th>
            <th>language</th>
            <th>question</th>
        </tr>
    </thead>
    <tbody>
        <!-- 前几天大家通过表单提交进来的每一行 -->
    </tbody>
</table>
```

它仍然使用了 `<table>` 标签，但这次还包含了 `<thead>` 标签来定义表头，以及 `<tbody>` 标签，里面包含了所有的表格行。我之所以知道这些，是因为我查阅了相关文档然后注意到了这一点。在 `<thead>` 里的第一个 `<tr>` 中，包含三个 `<th>`（表头单元格）：时间戳、语言和问题。这听起来是不是有点熟悉——前几天我们通过那个谷歌表单收集大家数据时，用的就是这些字段。

这些就是你们所有人通过表单提交的内容：最喜欢的编程语言、最喜欢的问题。虽然看起来不算特别美观，但它确实是以行和列的形式呈现的，这让人联想到谷歌在实际版的 Google Sheets 中使用的 HTML——它也是通过同样的行和列来为你展示数据表格。

> **结论**：`<td>` 装数据，`<th>` 装表头，`<thead>` 和 `<tbody>` 把表头区与数据区分开。屏幕上看到的那条加粗的表头行，就是浏览器读到了 `<th>` 之后的产物。

### 图片、视频与「空元素」

接下来试试有点视觉效果的东西。我用课上一直在用的那张桥的照片来做——它原始的样子其实有点像……算了，反正就它吧。

问题来了：我该怎么在网页中插入一张图片，以便在互联网上展示它？

新建 `image.html`，在 `<body>` 里嵌入那张图片：

```html
<img src="bridge.png" alt="哈佛大学">
```

这样不仅能展示图片，还可以在图片周围按需要添加段落文字和标题——说不定还能加个表格，或者我们之前见过的其他功能。`<img>` 是 image 的缩写，`src` 也是缩写（source），值就是图片文件名。

回到浏览器点开 `image.html`——看起来和实际图片没什么区别，因为我没有添加其他内容。但当我点击这个图片时，你会看到全屏显示的图像，它甚至有点太大了，超出了页面主体部分的视口范围。不过这类问题我们稍后解决。

我应该做得更好一点：如果图片加载缓慢，或者有视力障碍的用户无法看清内容，最好能提供一些替代文本，这样屏幕阅读软件就能朗读出来。所以这个标签还有一个属性叫 `alt`，表示替代文本（alternative text）。我填的是"哈佛大学"这样的内容，至少能给用户一个文字描述，让他们知道正在看的是什么样的照片。

`alt` 的作用在三种情况下都会体现出来：图片正常加载时，细心的用户和屏幕阅读器能读到这段描述；图片加载缓慢或完全损坏、只显示一个破损的图片图标时，你会看到这段文字而不是一片空白，它至少会附带一些说明，告诉你开发者原本希望你在那里看到什么。

那如果我回到 `image.html` 重新加载，页面内容完全不会改变——屏幕阅读器或细心的用户最终会在浏览器中看到这个效果。

不过这里有些不同，而且这次**可不是什么错误**。这个特定的图片标签有些新颖或值得注意的地方：**它没有闭合标签**。

对，它没有像 `<img />` 这样的闭合标签，而这是我们为其他所有标签（比如 `<html>`、`<head>`、`<body>`）所遵循的模式。我在这里根本看不到任何结束标签，而且它确实不需要。

> **定义**：原来有些 HTML 元素是**自闭合**的，或者叫**空元素**（void element）。像图像这样的元素，要么存在要么不存在，用开始标签和结束标签把它包起来，在语义上是没有意义的。因此只要浏览器能明显判断出图像应该放置的位置，就不需要结束标签。

而我们嵌入的内容并不局限于图像，我们还可以嵌入视频。新建 `video.html`，这里不用图像标签，而是用视频标签：

```html
<video controls muted>
    <source src="video.mp4" type="video/mp4">
</video>
```

设置 `<video>` 标签会稍微复杂一点，但根据文档说明：在 `<video>` 内部，我可以指定多个 `<source>`，这是为了确保浏览器能根据需求选择不同版本、不同分辨率或不同画质的视频文件。

这个标签的名字有点让人困惑，它实际上就叫 `<source>`——没有缩写形式。但奇怪的是，这个标签有一个属性叫 `src`，它是 source 的缩写。这个属性等于你要嵌入的文件名；今天准备的示例里有一个叫 `video.mp4` 的视频文件。

我还可以告诉浏览器这个视频的具体类型：`type` 属性声明内容的类型，这里它是一个 MPEG-4 视频（`video/mp4` 就是它的 MIME 类型）。

不过 `<video>` 还有其他特性。当你在网页上看到视频时，通常能看到播放图标、暂停图标，可能还有其他一些控件。实际上，你可以在 `<video>` 上添加一个名为 `controls` 的属性来启用这些控件——如果不启用，你无法启动或停止视频，也无法直观地看到这些控制界面。

但这个属性和其他属性略有不同：**它实际上不需要赋值，它只需存在即可**，浏览器看到 `controls` 这个词就会明白。

而考虑到如今广告无处不在，如果你想自动播放视频（或者至少不打扰用户），可能还需要默认静音——根据文档说明，你还可以设置视频以静音状态开始播放，只有当用户点击时才能真正听到声音。

这里正好可以总结一下属性写法的两种形态，后面还会反复遇到：

| 属性 | 写法 | 含义 |
| --- | --- | --- |
| 源文件 | `src="video.mp4"` | 必须给值：这个文件在哪 |
| 控件 | `controls` | 不给值：出现即启用 |
| 请求方法 | `method="get"` | HTML 里写小写，信封里是全大写 `GET` |

> **易错点**：把 `controls` 写成 `controls="true"` 虽然很多情况下也能工作，但规范的做法就是不写值。**布尔属性的存在本身就是全部信息。**

### 链接：文字和去向可以是两回事

现在，让我们真正实现 HTML 中 "H" 所代表的含义——**超文本**，也就是从一个页面链接到另一个页面的能力。这是我们尚未涉及的一个功能。

顺便说一句，我完全忘记了语言属性（`lang`），尽管这个属性主要是为了 SEO（搜索引擎优化），或者像谷歌翻译这类工具，以便它们知道要翻译的源语言是什么。

新建 `link.html`，标题改成 `link`，然后在 `<body>` 里创建一个所谓的超链接，写上"访问哈佛"这样的文字。

现在我回到目录索引页面点开这个文件——**这当然还不是一个链接**。所以我可能需要把它变成一个链接。嗯，与其只说"访问哈佛"，或许我应该说 `harvard.edu`？刷新——现在有一个 `harvard.edu` 按钮的样子了，但我可以选中它，**它还不能点击**，没有像链接那样显示下划线。

好吧，也许我需要写成 `www.harvard.edu` 这样。重新加载。**还是没有任何反应。**

好吧，也许我需要完整的 URL，加上协议方案 `https://`，再加上斜杠，末尾可能还要加个斜杠。再次重新加载。还是没有任何反应。

所以这里也一样，**HTML 对格式要求很严格**：除非你明确告诉它创建链接，否则它不会自动生成链接。

而如今，当你在社交媒体或谷歌文档上发布内容时，系统会自动为你生成超链接——这是通过代码实现的功能，通常使用 Python、JavaScript 或其他编程语言，由开发人员编写代码来检测你输入内容中的特定模式，如果发现内容看起来像网址，系统就会自动把它转换为超链接。

那么，要显式创建一个链接标签：

```html
<a href="https://www.harvard.edu/">访问哈佛</a>
```

`href` 代表超链接引用（hypertext reference），把它的值设为你想链接到的网址；然后在开始标签和结束标签之间，填入你希望**显示为链接的文字**。

回到页面重新加载，看起来就像我最初尝试的效果——只显示"访问哈佛"，但它实际上是一个超链接，这一点非常微妙。不过当我把鼠标悬停在这种默认显示为蓝色下划线的文字上时，你会在浏览器左下角看到即将跳转的目标网址，尽管这个提示确实非常隐蔽。

现在看起来，我确实成功创建了一个指向哈佛大学网站的实际超链接。我也可以直接链接到完整的网址，但那样会显得有些重复——尽管看起来似乎没必要这么做，但这确实是 HTML 的工作原理：**`href` 属性指定链接的目标地址，开标签和闭标签之间的文本是用户实际看到的内容。** 所以如果你希望用户看到完整的网址，就需要把它放在标签之间。

但这里其实可以引出一个关于网络安全的讨论。你觉得这个功能可能会被如何滥用呢？

没错，就是这个看似简单到有点傻的功能。攻击者可以设置显示一个链接，但实际指向另一个地址：

```text
屏幕上显示：    访问哈佛
实际跳转地址：  https://www.yale.edu
```

对于已经诱骗你访问其网页的攻击者来说，这并不难实现。但如果你刷新页面，显示的内容看起来不会有任何变化——**除非用户足够敏锐，注意到浏览器底部状态栏里那行不起眼的提示文字**，或者直接点击链接后被瞬间跳转到其他页面。

这听起来像是个恶作剧式的玩笑，但完全可以想象，攻击者会利用这种手法伪装成 PayPal 或各类银行的网址，目的就是为了骗取用户的个人信息。而且如果伪造的网站做得和真实网站几乎一模一样……它看起来和用户预期的网站几乎一样，但实际上只是攻击者伪造的副本。这种所谓的**钓鱼攻击（phishing）** 实施起来非常容易——攻击者通过伪造看似真实的网站，诱骗用户输入用户名、密码、信用卡信息等敏感数据。

归根结底，这类攻击手法本质上都是基于这些基础的网页构建元素来实现的。

> **易错点**：`<a>` 标签里的文字和它的 `href` 是**两个独立的东西**。正因为它们独立，才能被用来骗人——所以链接文字绝不能被当成"它要去哪里"的证据。

### 顺手捋一句：http-server 与 8080 端口

刚才有同学问了一个很好的问题：我是怎么让网页"展开"显示的？重新梳理一下。

在创建完 `hello.html` 之后，我们做的第一件事就是——HTML 部分完成后，我打开了一个终端窗口，具体来说运行了一条命令 `http-server`。它会在我的代码空间里启动我自己的网络服务器，但**并非使用默认的 80 和 443 端口**，因为那是 CS50 开发环境已经在使用的端口；相反，它特意选择了 **8080** 端口，这是开发者构建网站时常用的端口。

然后我就把终端窗口最小化了，因为一直盯着它看有点意思——不过那个网络服务器其实还在我的代码空间里跑着。每次我说"咱们回到这个标签页"的时候，它都在后台工作。我现在访问的是一个不同的网址，这是我在代码空间里点击那个绿色按钮得到的结果，它把我带到了自己的网站。

如果你不小心迷路了或者关掉了那个标签页，别担心，没什么大不了的：如果你转到终端的"端口"标签页，可以悬停在链接上，点击同样的 URL，就能打开你自己网站的内容。

至于端口标签页里那串名字——是不是有点毛茸茸的梗图风格？问得好：**这些是 GitHub 随机生成的名称**。GitHub 是以这种方式托管 VS Code 的公司，他们这样做是为了确保名称的唯一性，同时避免生成晦涩难懂的随机字母数字组合——于是就把随机的英文单词拼接在一起。

### 问号之后：URL 里的参数

好的，让我们继续。即使只是这些 URL，我们还能做更多事情。

一个 URL 里包含了协议方案、主机名、域名和顶级域名；在 URL 之后，除了文件夹名和文件名，其实还有更多值得探讨的内容。事实上我们经常会在 URL 中看到一个问号，后面跟着一系列键值对——这似乎是计算机科学中无处不在的概念，在 URL 的语境下也不例外。当你需要**传递信息**时，这种结构就派上用场了。

向 Web 服务器传递输入的一种方式，就是直接在 URL 本身中实现。举个例子：你访问 google.com 想搜索某些内容时，通常都习惯于直接在搜索框里输入关键词。**但这个搜索框究竟是如何把数据传送到谷歌服务器的呢？**

打开 Google.com，直接按回车——这是最快捷的访问方式。虽然我最终到达了 Google 的主页，但请注意，地址栏显示的 URL 实际上比 `google.com` 更长。我把 URL 中与今天内容无关的部分都删掉，它还是会强制跳转回来——看来谷歌试图通过添加这个参数来追踪我的访问。没问题。

然后我搜索 "cats"，按回车。请注意看，如果我放大屏幕顶部的网址栏，会发现这个 URL 长得离谱，因为谷歌很可能在进行大量追踪、广告投放和数据分析，不过从技术角度来看，这些内容与我们今天的主题无关。但请注意这个结构：

```text
https://www.google.com/search?q=cats&后面一大串
└────┬─────┘└──────┬───────┘└─┬─┘└──┬──┘└─────┬─────┘
   协议方案          主机名+顶级域名  路径     键      值
                                              │
                              问号后面是 HTTP 参数（键值对）
```

在 `www.google.com` 之后出现了斜杠和 `search`，这对应着谷歌服务器上的**路径**，指向他们工程师编写的搜索程序；接着是一个问号，后面跟着的就是所谓的 **HTTP 参数**——更准确地说，这种在 URL 中出现的键值对结构就是 HTTP 参数。键是 `q`，等号后面的值正是 `cats`。至于后面那一大串内容，我完全不清楚具体是什么。

我直接删掉后面所有内容然后按下回车——这些参数确实消失了，但搜索结果依然显示 "cats" 相关的内容。所以我认为这可以算是一种典型的做法，这是谷歌 URL 最简洁且实用的形式。

实际上，如果我想搜索 "dogs" 而不是 "cats"，**根本不需要使用搜索框**：我完全可以手动输入自己的 URL，按下回车，然后缩小页面就能看到谷歌返回的关于 "dogs" 的搜索结果。

所以这个 URL 体现了 URL 运作的核心原理，特别是其中的 **GET 方法**——也就是那个全大写的关键词，它实际上位于 HTTP 请求的"信封"内部。这正是我的浏览器在所有示例中一直在发送的信息。

不过，接下来才是真正有趣的地方。如果我了解谷歌服务器（也就是**后端**）的运作原理——这部分负责处理互联网上所有关于 "cats" 和 "dogs" 的信息——那么我只需要掌握一些 HTML 知识，就能实现自己的前端界面。

### 徒手搭一个谷歌搜索框

新建 `search.html`，粘骨架，改标题，然后我来创建自己的谷歌版本：

```html
<form action="https://www.google.com/search" method="get">
    <input type="text" name="q" placeholder="query" autocomplete="off" autofocus>
    <input type="submit" value="谷歌搜索">
</form>
```

我使用一个表单标签 `<form>`，并在其中指定一个输入标签 `<input>`，它的名称与我之前看到的完全一致——**谷歌使用 `q` 作为参数名，这恰好代表 query（查询）**。接下来再加一个输入框，这个输入框的类型是文本类型；下一个输入框的类型是提交按钮。

回到浏览器点开 `search.html`：虽然看起来不够美观，但这正是我自己的搜索引擎的起点。遗憾的是，当我输入 "cats" 时，请注意我的 URL 会随之改变，变成 `search.html?q=cats`——查询参数 `q` 等于 "cats"。

我对猫一无所知。我并没有关于猫的数据库。我还没有实现任何后端功能。目前只实现了**前端**功能——前端是用户直接看到和交互的部分，后端负责为前端提供数据支持。

那我为什么不把这个表单提交给我自己，而是把它的 `action` 属性设置为指向 `https://www.google.com/search` 呢？因为这正是我在浏览器地址栏里看到的那个网址，我只是在猜测谷歌的搜索机制是如何运作的。另外，虽然 `get` 是默认设置，但我还是要较真一下：虽然有点容易混淆，但我要指定表单使用的方法是 `method="get"`，注意这里要小写，尽管在 HTTP 请求信封内部，它实际会以全大写 `GET` 的形式出现。

刷新页面——还是完全一样的搜索框。但现在当我搜索 "cats" 并提交时，注意看，我的网址变成了谷歌自己的搜索地址。就像变魔术一样，我好像自己实现了一个谷歌搜索，虽然跳过了最复杂的后端处理部分。

其实我只是完成了更简单的前端部分，而且这里还有一些其他不错的功能可以添加：

- 我可以把输入框的 `type` 改成 `search`；
- 我可以修改按钮上显示的文字，不采用默认的"提交"，改成"谷歌搜索"；
- 我可以设置 `autocomplete="off"` 来关闭输入时的自动补全；
- 我可以设置 `autofocus`，让光标自动落在文本框里，不用再先点击一下激活它；
- 我还可以用 `placeholder="query"` 这样的占位符，让用户至少知道该输入什么——刷新后会看到灰色的提示文字。

> **易错点**：说好了我又犯了。设置完 `autocomplete="off"` 之后自动补全还在？我是不是忘了刷新页面？——**对，我忘了刷新。** 每改一次都必须重新加载页面。改完自动补全确实关掉了，另外还有个不明显的小细节：把这个文本框的类型改成 `search` 之后，会多出一个小小的 `X` 按钮，可以一键清空所有内容。

你可以看出来，这其实可以说不是谷歌的主营业务——他们在后端投入的精力远多于前端。但仅凭这些基础构件，我们能不能实现同一网站的雏形呢？

### 用正则表达式给输入上一道锁

顺便，我还想让那个文本框不再空荡荡的，让人不知道该输入什么——所以加个 `placeholder` 就行。除此之外，HTML 还能做更多值得深入探讨的事。

在计算机科学中，有一种被称为**正则表达式**的技术，它非常强大。这是一种**描述模式**的方法，在验证输入时特别有用。比如你要求用户输入一个包含 `@` 符号和顶级域名（TLD）的电子邮件地址，那么最好能确保他们在跳过该字段或输入错误时，系统会给出警告。

在正则表达式的世界里通常简称为 regex，有一整套文档向你介绍一些非常强大的语法。我们今天不会花太多时间深入探讨，但这种语法不仅存在于网络开发领域，在 Python 和许多其他编程语言中同样适用——所以这只是一个快速的入门介绍。

如果你想在网站中定义一个模式，以确保用户输入的是电子邮件地址，就可以使用这些文本构建块：

| 符号 | 含义 |
| --- | --- |
| `.` | 任意一个字符（**不代表句号**） |
| `*` | 出现零次或多次 |
| `+` | 出现一次或多次 |
| `?` | 出现零次或一次（可能存在也可能不存在） |
| `{n}`、 `{a,b}` | 出现指定次数，或落在某个次数区间 |
| `[abc]`、`[a-z]` | 这些字符中的任意一个，或某个范围 |
| `\d` | 任意一个数字 |
| `\D` | 任意一个非数字字符 |

长话短说，多年来人们发明了正则表达式这种简写符号，通过它可以定义模式。这很有用——如果我想制作一个网页，要求用户输入电子邮件地址，我可以在一定程度上强制实施这一要求。

新建 `register.html`，来模拟某个网站的注册页面。标题改掉，保留表单，但这次不再用 Google，所以简单一点。我添加一个输入框，名称设为 `email`（因为我要收集的就是邮箱信息），占位符设为 `email`。然后再加一个模式验证——输入类型仍然是文本，但我额外指定 `pattern` 属性：

```html
<form>
    <input type="text" name="email" placeholder="email" pattern=".+@.+\.edu">
    <button>注册</button>
</form>
```

我希望用户在这对引号之间输入的模式是：任意字符出现一次或多次（也就是他们的用户名），然后是一个 `@` 符号，接着又是任意字符出现一次或多次，然后是字面意义上的句点——就像我们之前提到的，当你需要转义特殊字符时（比如你想表示 "harvard.edu" 里那个真实的点），可以用反斜杠加句点来表示一个实际的句点，最后是域名或顶级域名，比如 "edu"。另外，HTML 中也有一个 `<button>` 元素，它的功能和之前提到的提交按钮类似。

回到浏览器，输入 "Mailen" 然后点击注册——您会看到提示信息："请按照要求的格式填写"。也就是说，在我正确输入类似 `main@harvard.edu` 这样的邮箱地址之前，系统一直不会通过。现在输入正确了，它终于接受了。

手动输入这些正则表达式模式确实有点繁琐，不过有一些简写方式可以更方便地使用它们——实际上我可以去掉这个 `pattern` 属性，因为 **HTML 本身就提供了一个 `type="email"` 的输入框类型**，它会自动帮你完成所有这些格式匹配验证：

```html
<input type="email" name="email" placeholder="email">
```

用上它之后，系统仍然要求我输入一个有效的电子邮件地址才能注册，而且这次给出的提示信息更加明确具体。

> **提示**：不过要清楚，验证电子邮件地址实际上相当复杂。我实现的是一个非常简化的版本，只验证"用户名 @ 域名 . 顶级域名"这种格式——而像 `main@harvard.edu` 这样的地址，电子邮件实际允许的语法规则复杂得惊人。正则表达式到这里就开始变得有点吓人了，不过就我们今天的目的来说，我们只需要知道它们确实存在。

你可能会发现它们在 HTML 中很有用，在 Python 中也很有用，而在**从网页中提取信息**时，正则表达式的作用简直无可替代。如果你在做数据科学、热衷于收集和分析数据，你不仅可以用正则表达式来验证数据，还能在实际的网站或文档中寻找数据模式，并提取这些数据，以便对它们进行进一步的操作或分析。它虽然复杂，却是一个极其有用的工具。

### 浏览器里的验证为什么靠不住

不过，这里有个关键点需要注意：即使我使用了 `type="email"` 属性，系统仍然要求我输入一个有效的电子邮件地址才能注册——**可网页存在一个关键问题：我们不能完全信任它们**，因为这些 HTML 代码是从服务器端发送过来的，然后被下载到用户的 Mac、PC 或手机上，**用户本地会有一份副本**。

我可以像之前那样，通过右键点击或按住 Ctrl 键点击，选择"检查"之类的选项，打开开发者工具，直接查看这个页面的元素，也就是 HTML 代码本身。如果我不想输入邮箱地址，而只是想随便输入一些文本、看看能不能让你的网站出问题——**我直接把它修改掉就行了**。现在就没有这样的警告了。

也就是说，即使你在使用 HTML 的某些特性（不仅是今天，未来几周你还会接触到更多功能），从安全角度来说，它们通常都是不可靠的。

```text
你写的：        <input pattern="...">     ← 服务器发来的那份
用户拿到的：    完全相同的一份本地副本
用户做的事：    打开开发者工具 → 删掉 pattern 属性 → 绕过全部校验
```

这就像我们之前在讨论 **SQL 和 SQL 注入攻击**时提到的一样，这也是一种攻击手段。设想两个人合作开发一个网站，一个人负责数据库部分，另一个人负责 HTML 部分。负责数据库的人可能会想："我不需要担心转义字符的问题，因为负责 HTML 的人已经在那里用了 `pattern` 属性。"这种想法很危险，因为攻击一个网站其实非常简单——你甚至可以直接在自己的浏览器里删除网页上的某些功能代码，就能轻松绕过网站的安全防护措施。

下周我们会探讨如何在服务器端防御这类攻击，但现在要强调的是：

> **结论**：**绝对不能完全信任用户输入的数据。**

### 用 validator.w3.org 检查语法

那么，我们如何确保自己的 HTML 代码是正确的呢？确实有多种方法，但有个工具值得了解：**validator.w3.org**。这个网站由负责制定 HTML 等语言标准的组织维护，专门用于代码验证。

点击进去，选择"验证直接输入"标签页，从我的示例里挑出最简洁的一段代码——`hello.html`——直接复制粘贴到他们的网站上，点击"检查"按钮，他们编写的程序就会自动验证我写的 HTML 代码是否正确：所有需要闭合的标签是否都正确闭合了，有没有犯拼写错误、遗漏括号或引号之类的低级错误。

这是一个非常实用的工具——它能验证你的代码在语法上是否正确，**尽管在屏幕上看起来可能还是一团糟**。这至少能帮你检查底层的 HTML 代码是否正确。

### 换一层皮：CSS 登场

到目前为止，我所做的一切都相当枯燥：界面都是黑白的，页面设计得相当简单。实际上，我们可以通过另一种语言来完善最终效果——**CSS**，这是我们今天要介绍的三种语言中的第二种。

虽然 CSS 本身并非编程语言，但有趣的是，随着功能的不断丰富，它正变得越来越像编程语言（不过这个话题我们以后再详谈）。**CSS 全称为层叠样式表（Cascading Style Sheets）**。如果说 HTML 是网站的**骨架**，负责结构搭建，那么 CSS 就像是**皮肤**，负责美学呈现：它通过精确控制元素的位置、颜色、字体大小等视觉细节，实现最终的页面美化效果。

CSS 的语法略有不同，但本质上依然是通过**键值对**来实现样式控制。CSS 支持的键值对组合非常丰富，我们今天无法全面涵盖；这类知识最终需要通过查阅参考手册、专业书籍或在线资源来深入学习，从而掌握更多实用技巧。

那为什么 CSS 里对同一个东西的叫法和 HTML 不一样？这本质上就是键值对，只不过 CSS 这一侧有自己的术语：HTML 里键值对叫**属性**（attribute），CSS 里一个键值对叫一个**声明**（declaration）。之所以用不同的词，是因为 **CSS 和 HTML 是由不同的团队各自独立开发的语言**。

#### 三种把样式接进来的方式

定义 CSS 属性（声明）的方式有多种，这里列举几种常见方法，我们会在具体示例中逐一了解：

1. **直接写在元素上**——给元素加一个 `style` 属性，里面就是键值对；
2. **写在页面头部的一个 `<style>` 标签里**——可以放很多条声明，对整个页面生效；
3. **单独写在一个 `.css` 文件里，再用 `<link>` 标签关联**。

前两种我们马上就会看到，第三种我们稍后也会讲到。先看第二种，在 `<head>` 里引入一个所谓的样式标签：

```html
<head>
    <title>...</title>
    <style>
        /* 这里的键值对 */
    </style>
</head>
```

如果你想把它们提取出来放入单独的文件中，可以使用 `<link>` 标签：

```html
<link rel="stylesheet" href="styles.css">
```

> **易错点**：需要说明的是——**这个 `link` 标签与超链接或可点击文本毫无关系**，它仅用于关联另一个文件。这里的文件是 `styles.css`，关联类型 `rel` 被定义为 `stylesheet`（样式表）。这类复制粘贴的核心关注点其实在于文件名：也就是你实际存放样式的文件名。链接到网页用 `<a>`，链接到样式表用 `<link>`，别搞混。

#### 给 John Harvard 做一个主页

现在动手。新建 `home.html`，为 John Harvard 创建一个简单的主页：粘贴模板，把标题改成"主页"，在 `<body>` 里写三段——一段介绍这是谁，一段是"欢迎来到我的主页"（我们把它放在页面中央），最后一段是版权信息，比如"关于 John Harvard 的说明就在下方这里"。

所以这是一个基础网站：它只有三个段落，可能不太美观，但我先确认一下有没有出错的地方。关闭开发者工具，点击返回，再点击主页，我们就得到了为 John Harvard 创建的最简单的页面。

我们至少得开始对这个页面进行一些控制：调整字体大小和文本的对齐方式。回到 VS Code，先添加一个 `style` 属性，暂时不用样式标签：

```html
<body>
    <div style="font-size: large; text-align: center;">
        John Harvard
    </div>
    <div style="font-size: medium; text-align: center;">
        欢迎来到我的主页
    </div>
    <div style="font-size: small;">
        版权归 John Harvard 所有
    </div>
</body>
```

注意，CSS 里属性之间又得用**分号**隔开了。严格来说，在最后一个键值对后面你不需要加分号，但为了保持一致性，建议还是加上。

回到页面刷新：看，刚才所有的文字都是左对齐、字号也一样；现在变化虽然有点细微，但文字明显居中了，而且分别是大号、中号和小号字体。即使你以前从没见过 CSS，但根据过去几周的内容，你觉得这个设计哪里不对劲？

**对，每一行都这样——我一直在重复写 `text-align: center;`。** 而且如果我们要抠细节的话，这些其实也不算是真正的段落，对吧？这连短语或完整句子都算不上，更别提段落了。

#### 从 p 换成 div：语义和空白

所以我们可以用很多标签来布局页面。接下来我要换一个比段落标签更通用的标签，那就是 `<div>`，它能在页面上为我创建一个分区。虽然这没有实际的功能影响，但从语义上来说更清晰，因为它明确表示我在这里创建了一个分区。另外还有页眉标签 `<header>` 用于页头区域，主内容标签 `<main>` 用于主体部分，页脚标签 `<footer>` 用于底部区域——这只是另一种组织页面的思路，这些只是页面上不同的矩形区域。

我先重新加载一下这个改动，因为改用 `<div>` 标签替代 `<p>` 标签后，可能会产生一些我们需要注意的副作用。

**糟糕，文本之间那些美观的空白间距消失了。** 现在页面上只剩下一个个紧挨着的矩形区域了。

原因就在刚才的观察里：`p` 标签作为段落，浏览器默认给了它上下外边距，正是这些外边距让三段文字之间有了呼吸感；而 `div` 是纯粹的分区容器，默认没有任何外边距，于是它们就贴到了一起。

> **易错点**：所以当你把一个标签换成另一个标签时，不要只盯着"我想让它变什么样子"——**你可能同时丢掉了旧标签默认带来的东西**。想要间距，要么继续用 `p`，要么在 CSS 里显式给 `div` 加 `margin`。

顺便提一个元素面板里的实用技巧：按住 Ctrl 键点击或右键点击可以再次打开开发者工具；当你把鼠标悬停在元素面板里的某个元素上时，页面上对应的区域会以彩色高亮显示。那么，如果我们点击小三角展开 `body` 元素……

到这里为止，我们已经知道了网页是怎么被结构化、被标注、并且**在浏览器内存里长成一棵树的**。我们知道了段落、标题、列表、表格、图片、视频、链接各自该用哪个标签，也知道了表单如何把输入通过 URL 里的键值对送到服务器上去——以及为什么服务器那一端，绝不能因为前端"已经校验过了"就放心。骨架已经搭好，接下来要做的，就是给它换上一层皮。

## CSS 与 JavaScript：一个 hello 页面如何长成会回话的网页
> 对应块：BLK27 | 覆盖分集：P10下 | 块标题（分集名）：《CSS 样式与 JavaScript 函数》

### 在浏览器里检查自己的代码

先从一个再朴素不过的页面说起。左边是 VS Code 里的源文件，右边是浏览器里的成品——顶部一行 John Harvard，中间一句"欢迎来到我的主页"，最下面一行版权信息。三块内容，三个 `div`。

在浏览器里对着任意位置右键、选"检查"，开发者工具就会打开，元素面板里是这个页面真实存在的标签树。点一下左边的源码标签，页面上的对应区域立刻被高亮；再点第二个、第三个——头部的矩形、主体、页脚，一块一块点亮过去。这就是我们说的页面分区，调试时极其好用。

> **提示**：注意，你在这里看到的是浏览器里的**副本**，不是磁盘上的原始文件。你在 Elements 面板里改的东西，刷新即失效。想改，改源文件。

顺手在这里做一件小事。这三个 `div` 各自写着同样的 `style`，让人烦躁。于是我把 `style` 挪到 `body` 上：

```html
<body style="text-align: center;">
    <div>John Harvard</div>
    <div>Welcome to my home page</div>
    <div>(c) 2026</div>
</body>
```

这就是"层叠样式表"里**层叠**两个字的来历：写在 `body` 上的这串键值对，会向下层叠，作用到它内部的每一个标签上。之所以能生效，是因为这三个 `div` 都是 `body` 的子元素——借用家族树甚至更广义的树结构那套词来说，谁是祖先，谁就替后代兜底。刷新一下，视觉上一点变化都没有，但代码明显更合理了。

不过更值得做的一件事，是让语义自己说话。

### header、main、footer：让搜索引擎读懂你

在 HTML 里添加更多提示，让 Google、必应这类服务器能更准确地理解它们正在处理的内容——如今的技术术语叫"**语义网**"。

上面这几个 `div` 语义太笼统了。但一眼就能看出，页面顶部的 John Harvard 应该是最重要的部分，页面中部的"欢迎来到我的主页"次之，底部那条版权信息最不重要。HTML 专门为这种"重要性层级"准备了标签：

```html
<body>
    <header>John Harvard</header>
    <main>Welcome to my home page</main>
    <footer>&#169; 2026</footer>
</body>
```

等网站公开、搜索引擎来抓取时，它们会知道 John Harvard 很重要，因为它位于页眉；"欢迎来到我的主页"很重要，因为它位于主体；而版权信息在页脚，就可能不太关注。这些标签主要是为这类服务提供更多提示信息。

> **定义**：`<header>` 定义页面的页眉部分，`<main>` 定义页面的主体内容，`<footer>` 定义页脚部分。它们的作用不是"长得不一样"，而是**告诉机器这块内容是什么**。

版权符号我原先是拿括号加字母 C 凑合的。HTML 里其实有专门的机制叫"**实体**"——输入这个神奇的符号组合（注意结尾的分号）：

```html
<footer>&#169; 2026</footer>
```

VS Code 会立刻认出你写的是一个 HTML 实体。重新加载，你得到一个真正的版权符号，而且是**用当前页面所使用的字体**显示的。

### 样式该有自己的地方

写到这里，这个问题已经变得刺眼：我的数据，和它的呈现方式，是混在一起的。"John Harvard"、"欢迎访问我的主页"、"版权所有"，这些才是我真正关心的**数据**；可我把 CSS 和 HTML 放进了同一个地方。

明确说一下边界：到目前看到的全部内容里，所有标签和属性都属于 **HTML 语法**；而 `style` 里面引号包着的那些，才是 **CSS 语法**。这个先例我们其实见过——就像在 Python 代码里嵌入 SQL 语句，只不过方向反过来：这里是 HTML 里嵌 CSS。

> **结论**：既然 CSS 语法只占引号里的那一小块，为什么不把它抽出去？让我能在一个地方集中查看，甚至最终提取到另一个文件里。

在头部标签内部，加一个 `<style>` 标签：

```html
<style>
    body {
        text-align: center;
    }
    header {
        font-size: large;
    }
    main {
        font-size: medium;
    }
    footer {
        font-size: small;
    }
</style>
```

```text
<style>
  └── 选择器   {  属性: 值;  属性: 值;  }
      ↑              ↑
      │              └── 这些键值对作用到谁身上，由选择器决定
      └── body 匹配到的那一个元素
```

花括号前面那个词，就是所谓的**选择器**。想改页面主体的样式，就写 `body`；花括号里的所有键值对（这个例子只有一个）全都作用于页面主体。刷新，效果和刚才基本一样——我只是把这些键值对搬了个家。

行数确实变多了，这不算最理想。但这一步为进一步优化打下了基础：接下来，就可以把内容**完全放进另一个文件**了。

### 类：把一组属性封装起来

到目前为止有个隐患：我把所有与特定 HTML 标签相关的键值对都堆在一起，其实一点都谈不上可重用。`text-align: center` 被绑死在了 `body` 上——假如我想在一个更大的项目里让页面上多个元素居中，就得复制粘贴三遍。

于是我给自己造一个关键词，比如"居中"这个概念，它本身并不存在，但如果在前面加上一个点——我刚刚创建的就是所谓的 **CSS 类**。

```css
.centered {
    text-align: center;
}

.large  { font-size: large; }
.medium { font-size: medium; }
.small  { font-size: small; }
```

使用的时候，在标签上写 `class` 就行：

```html
<body>
    <header class="large">John Harvard</header>
    <main class="centered medium">Welcome to my home page</main>
    <footer class="small">&#169; 2026</footer>
</body>
```

> **定义**：一个类就是**一组键值对**，也就是一组属性。你可以把同一个类和任何一个 HTML 标签关联起来。

这么做的理由，和我们在 Scratch 和 Python 里实现的模块化精神是一脉相承的，也是那句"创造自己的乐趣"。

> **提示**：类不是函数，但它是一种把一个或多个属性打包、拿到网页任何位置重复使用的方法。在这个例子里看不出有多惊人，但它为将来更有趣的功能打下了基础。

顺带把选择器的谱系补齐——之前提过，属性可以应用于不同的 HTML 选择器：类型选择器、类选择器、ID 选择器、属性选择器。下面几种，后面都会亲手用到。

| 写法 | 名称 | 选中什么 |
| --- | --- | --- |
| `a` | 类型选择器 | 页面上**所有**的 `<a>` 标签 |
| `.centered` | 类选择器 | 所有标了 `class="centered"` 的元素 |
| `#Harvard` | ID 选择器 | 那一个 ID 为 `Harvard` 的元素 |
| `a:hover` | 伪类选择器 | 鼠标悬停时的那一刻，那个 `<a>` |
| `[...]` | 属性选择器 | 按属性挑（语法存在，这一讲没细演示） |

### 外链一个 CSS 文件

现在把 `<style>` 标签里高亮的全部内容剪切到剪贴板——连标签本身一起去掉。回到源文件目录，新建一个 `home.css`，把内容整个粘进去，顺手把缩进整理成左对齐。

然后，头部里那个塞满杂物的 `<style>` 标签，被替换成一行链接代码：

```html
<link href="home.css" rel="stylesheet">
```

`rel` 用来定义当前文件与被链接文件之间的关系，这里声明的关系是"样式表"。这个标签不需要闭合，它本身就是一个自闭合标签。回到浏览器刷新，除了字体上的一点微调，视觉上没有任何变化——但现在多出来一个独立文件，设计就变得更好了。

### 站在巨人的肩膀上：Bootstrap

几周前我们用那个谷歌表单收集了一批数据，存在 `favorites0.html` 里。那份文件里有一张简陋的表格结构，而事实证明，在 HTML 和 CSS 的世界里还会遇到所谓的"**框架**"——这其实是"**库**"的一种更时髦的说法。

框架本质上是一种通过使用**他人编写的库**来实现特定功能的方式，并且按照他们的方式来。你只需要读他们的文档，然后按具体情况采用他们的函数（在代码层面），或者采用他们的 CSS 类（以这个例子来说）。

如今最流行、文档也最简洁完善的一个，叫 **Bootstrap**。它提供了一系列 CSS 类，因为开源，你可以直接用在自己代码里。

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/bootstrap/dist/css/bootstrap.min.css">

<table class="table table-striped">
    <tbody>
        <!-- 每个人都提交的那一行，原封不动 -->
    </tbody>
</table>
```

链接指向的是第三方站点 **jsDelivr**，这是一个 CDN（内容分发网络），也就是专门为他人提供内容服务的服务器；不过这一行我是**直接从 Bootstrap 的官方文档里复制**过来的。

为什么在表格标签上加 `table` 再加一个空格和 `table-striped`？因为我翻文档时很喜欢他们的表格样式：白灰相间的漂亮条纹，让整体格式好看得多。

打开 `favorites1.html`——完全相同的数据，只改了两行代码，效果就大不一样了。这看起来就像你在任何美观网站上见到的表格，比如你的 Gmail 收件箱，而这**仅仅通过修改 CSS 实现，HTML 本身几乎没变**。

> **结论**：引入这些类的目的，是代码的可重用性。更棒的是，我们可以站在巨人的肩膀上，直接使用他人编写的代码。

到这里我想插一句总结：说好了，这就是你们正式学习 HTML 和 CSS 的**全部**内容了。就像其他所有内容一样，后续知识都遵循完全相同的模式——只是不同的类、不同的属性、不同的标签名称，靠实践、潜移默地的学习和查阅参考资料来掌握。基础知识确实就这些了。

### 给那个链接换一身衣服

我们之前做过一个链接页面，那次它曾面临钓鱼攻击的风险。我把它恢复成安全版本：显示为"访问哈佛大学官网"，指向哈佛的实际网址。

默认情况下，浏览器会把它渲染成**蓝色带下划线**。假设我想对这个链接做超出默认设置的美化。我可以用多种方式，先看最直接的——在同一个文件里，给锚点标签写样式（我打算继续在同一个文件里操作，而不是教条地搬到另一个文件去）：

```css
a {
    color: #FF0000;
    text-decoration: none;
}

a:hover {
    text-decoration: underline;
}
```

`#FF0000` 是十六进制颜色代码：红色分量最高，绿色和蓝色分量均为零。如果你想对颜色有如此精细的控制权，就靠它。

如果你不太喜欢这个下划线，`text-decoration: none;` 就把它去掉。但**只在悬停时**显示下划线，效果更好。这靠**伪类选择器**实现——在标签名后加上 `:hover` 这样的关键字，浏览器能识别这个语法：当鼠标悬停在链接上时，临时把文本装饰改回下划线。刷新后平时看不出变化，鼠标移上去，下划线就冒出来了。

> **提示**：想学别人网页是怎么做效果的？打开开发者工具的 Elements 面板。我把右侧面板调大一点，往下滚到我这个链接——**这些内容一直都在那儿，只是直到现在才被注意到**。这里能直接看到当前所选元素（也就是这个链接）所应用的所有 CSS 样式：颜色 `#FF0000`，文本装饰 `none`。

这个面板的用处有三个：一是学习其他网站的实现方式；二是快速迭代——把鼠标悬停在属性上，点击或取消点击，就能即时开关某个效果；三是随手试验，比如把颜色改成 `00, FF, 00, E`，屏幕就变绿。你可以临时修改浏览器里的 HTML 或 CSS 来快速试效果，反正刷新就没了。

> **易错点**：想只给**某一个**特定标签写样式，常规做法是给它一个唯一的 ID。约定是：不要给这个页面里其他任何元素用相同的 ID。而写规则时改成 `#Harvard`——井号表示"这是一个 ID"。但在**实际的 HTML 代码里，ID 值前面不需要加井号**。加了反而不合规。

### 为什么还需要一门 JavaScript

我们今天要介绍的最后一种语言。哪怕只是浅尝辄止——毕竟它如今几乎无处不在。

大多数你使用的网站不只有 HTML 和 CSS；如果它们有任何交互功能，很可能还用了 **JavaScript**。开发者会在服务器端写好代码，你的浏览器把它下载到客户端，最终在你的 Mac、PC 或手机上运行。话虽如此，JavaScript 如今在服务器端也非常流行——它并不仅仅是一门基于浏览器的语言。

而它最强大的能力，是**能在内存中实时修改这棵树**。

拿你的 Gmail 或 Outlook 收件箱举例：按老规矩，一封接一封的邮件，很可能是某个表格标签用表格行、表格行、表格行拼出来的——效果其实不怎么样。实际发生的事是：

```text
【过去】点刷新 → 整页重新下载 → 服务器 → 整棵 DOM 被换掉
             <tr><td>…</td></tr> × N

【现在】点刷新 → 事件触发 → JS 取新邮件 → 往现有 DOM 上再挂一个节点
             <tr>…</tr> × N   +   <tr>新到的这一封</tr>
```

我那个年代就是这么运作的——那时候连 Gmail 都还没出现，你访问的是自己的邮箱收件箱：从服务器下载一个塞满表格标签的网页，里面有表格行和表格数据元素，那就是你的收件箱。想看有没有新邮件？重新加载整个页面，它会下载新内容，直接把新的 HTML 显示给你。

而 JavaScript 在过去二十多年间逐渐登上舞台。你可以**在初始时一次性下载数据**，然后通过代码每隔 30 秒抓取一些新数据，几乎在任何邮件到达时就能拿到更多。

> **定义**：这棵树在浏览器里叫做 **DOM**（Document Object Model，文档对象模型）。简而言之，通过 JavaScript 你可以动态地修改这棵树，从而实现网页内容的动态更新。

### 一眼扫过它的语法

今天点到为止，不会深入语法细节。快速浏览一下有哪些特性，然后演示其中一些。

条件语句，Scratch 里是积木形状的，JavaScript 里则是花括号，和 C 语言基本相同。缩进在 JavaScript 中**不影响程序执行**，它只关乎代码风格——这跟 Python 形成鲜明对比。变量方面，Scratch 里是"把 counter 设为 0"，JavaScript 里最合理的方式是 `let counter = 0;`，你不需要指定变量类型。

> **提示**：`let counter = 0;` 更像是一种**礼貌地向浏览器提出请求**：请创建一个名为 counter 的变量，默认值设为 0。

关于分号——严格来说这并不完全准确，浏览器足够智能，能判断分号在哪些地方真正重要。但为了我们的学习目的，**可以假设分号始终存在**。

| 想做的事 | Python | JavaScript（≈ C） |
| --- | --- | --- |
| 条件 | `if x:` 靠缩进 | `if (x) { … }` 靠花括号 |
| 循环 3 次 | `for i in range(3):` | `for (let i = 0; i < 3; i++)` |
| 死循环 | `while True:` | `while (true)` |
| 加 1 | `counter += 1` | `counter += 1;` 或 `counter++;` |

加法有"加等于"这个略显冗长的技巧，也有更简洁的"加加"运算符——就像 C 里一样，Python 里可没有这种写法。循环就和 C 几乎一模一样，只是**不需要声明数据类型**。

### 让页面回应你：表单与 greet 函数

现在动手。把链接页面关掉，直接改进 `hello` 这个文件，让它互动起来：当我输入名字时，在屏幕上弹出一个提示框。

```html
<body>
    <h1>Hello</h1>
    <form onsubmit="greet()">
        <input id="name" placeholder="name" type="text" autocomplete="off" autofocus>
        <button type="submit">Submit</button>
    </form>
</body>
```

`autocomplete="off"` 关掉自动完成，免得干扰操作；`autofocus` 开启自动聚焦，省得我再点一下。我要给这个 HTML 元素设置一个唯一的 ID，就叫 `"name"`；占位符也设为 `name`，这样用户就知道该填什么；字段类型定为文本。我想要的效果是：输入名字、点击提交后，屏幕上某个地方能看到"你好，某某"——换句话说，和第 0 周、第 1 周练习里做过的程序一模一样。

`onsubmit` 是给表单标签添加的一个新属性，顾名思义：当这个表单提交时，就调用以下函数。我打算调用一个名为 `greet` 的函数。

```javascript
function greet() {
    let name = document.querySelector("#name").value;
    alert("Hello, " + name);
    return false;
}
```

逐段拆开看：

- `document` 是一个**全局变量**，它随浏览器中的 JavaScript 一同提供，允许我编写涉及整个文档（即网页本身）的代码；
- `querySelector` 是一个函数，名称听起来很专业，它允许我**使用 CSS 选择器**来选取页面中的特定元素——我们刚才看到的那些带点号、井号的语法，在这里又派上用场了；
- `"#name"` 里的 `#` 仅表示 ID 选择器；我之所以用 `name`，是因为刚才在 HTML 里设置的唯一标识符就是 `name`。改成 `Foo` 也行——只要两边一起改；
- `.value` 属性取出这个文本框里的值。

这种点号语法我们见过两次：在 C 语言里，点号用来访问结构体成员；在 Python 里，点号用于访问对象的属性。所以这里的点号，就是通过全局变量 `document` 访问文档对象，再调用它内部的 `querySelector`——取到那个 ID 为 `name` 的元素，然后深入这个文本框内部，把它的值抽出来。

说白了，这就是把用户的输入存进一个名叫 `name` 的变量。接下来用 JavaScript 内置的 `alert` 函数，把字符串 `"Hello, "` 和 `name` 的值用加号拼起来（这个加号我们在 Python 里也见过）。

> **易错点**：我还得在这里烦人地加上 `return false`。不加的话，`greet` 确实会被调用，但浏览器**仍然会尝试把表单提交到服务器**，那就会打断我自己写的代码执行。目前这种做法有点临时凑合的解决方案。加了它，提交表单时唯一发生的事，就是执行我定义的函数。

现在如果我没搞错什么，重新加载页面应该就能看到效果：输入名字、点提交，弹出一个虽然简陋但功能正常的警告框，里面显示"你好，David"。

> **结论**：我这段脚本会**监听这个表单的提交事件，并在触发时调用那个函数**。这通常是 JavaScript 典型的模式——在网站开发中，存在大量可能发生的事件，你可以对任意数量的事件编写监听代码，并在事件发生时执行相应操作。

### 事件：Scratch 绿旗的网页版本

"事件"这个概念，我们自第 0 周学 Scratch 以来就再没提过了。回想一下，Scratch 里有"当绿旗被点击时"这样的事件，点击绿旗，你就可以执行操作来响应。网页编程里也是一样的：用户可以**更改**某些内容、**点击**某个元素、**拖拽**对象、**松开按键**（键盘抬起）、**按下鼠标**，或者其他操作。

两个真实的例子：你在 Gmail 里点击刷新图标去取新邮件，实际上是一些 JavaScript 代码在跑，它与 Google 的服务器通信、获取更多邮件并更新你的页面。你在谷歌地图上点击并拖拽想看更高纬度的地方，实际上是有代码在监听你的按下与拖拽，好去获取更多地图图块——也就是更多矩形地图图片，无论你往哪个方向拖。

如今网站上任何类似的交互功能，都是这么实现的：**通过监听你或其他人实际执行的操作来工作**。

### 三条路，同一个目的

回到 HTML，怎么把 JavaScript 塞进一个网页？有几种方式，我们一条条走，你会看到它们殊途同归。

**先说一个坑。** 你可以在网页的头部放一个 `<script>` 标签，就像用 `<style>` 那样。但这样做可能带来问题，原因你可能已经想到了：如果把 JavaScript 放在这里，试图用它修改网页内容——可网页的实际结构直到下方才定义完成，这会导致一种**竞态条件**：代码执行时，数据可能还不存在。

所以推荐的做法是：把 `<script>` 标签放在页面末尾、`</body>` 结束标签之前，这样能确保整个网页内容已经加载完成，从而避免这个问题。

> **提示**：这与我们之前在 Python 中遇到的默认参数问题、C 中遇到的原型声明问题，本质上是相似的——都是"你用到的东西，可能还没准备好"。当然，针对这个问题其实有多种解决方案。

**第一条路：写在页面底部。** `hello2.html` 就是这么做的：script 标签放在页面底部，确保表单及其内部的所有内容都已加载完成。而且我在这里不再使用 `onsubmit` 属性——就像我之前把 CSS 从 HTML 中分离出来一样，现在我也把 `greet` 函数从 HTML 里移出来：

```javascript
document.querySelector('form').addEventListener('submit', function() {
    alert('Hello, ' + document.querySelector('#name').value);
});
```

`document.querySelector('form')` 的作用是**获取页面中实际表单元素的引用**。如果你想象一下，在计算机内存中这个结构被绘制成一棵树，那这段代码就是让我定位到树中的那个表单节点。

`addEventListener` 是**添加事件监听**：监听器是一个函数或方法，你可以将其应用到任何元素，用于告诉该元素"后续请监听指定事件，并在监听到时执行这段"。这里调用的是**匿名函数**，也就是常说的 Lambda 函数——这种语法意味着：当该元素上发生 submit 事件时，就执行这对花括号之间的代码。

这段代码实现了完全相同的功能，但采用了纯 JavaScript 方案，没有使用 `onsubmit` 属性。

顺便说个惯例：我一直遵循在 JavaScript 中使用**单引号**的惯例，因为在 JavaScript 社区里，人们通常更倾向于单引号而非双引号。**为什么？** 因为这意味着在 JS 社区里，人们需要按 Shift 键输入双引号的次数，比其他语言的使用者要少得多。这只是一个惯例——只要你保持一致，用单引号或双引号都可以，前提是文本内容里没有真正的撇号（比如所有格符号或缩写）这类字符。

**第二条路：写在顶部，但等 DOM 就绪。** 像 `hello3` 示例那样处理：

```html
<script>
    addEventListener('DOMContentLoaded', function() {
        // 其余代码与 hello2 完全一致
    });
</script>
```

这个事件名看起来有点奇怪，但既然你已经简单了解了 DOM，它指的是文档对象模型，也就是内存中的那个树状结构。`DOMContentLoaded` 的意思就是：**当树状结构加载完成后，才执行后续操作**。这样可以确保浏览器从上到下、从左到右读取所有代码时，只有在整个 DOM 完全加载进计算机内存之后，才会真正执行这些代码。

**第三条路：外链。** 把这些代码整个移到 `hello.js` 文件里，在 HTML 中只留一行 `<script src="hello.js"></script>`。`hello4` 就回到了纯 HTML 结构——因为我完全可以把所有复杂逻辑都放进这个 script 标签指向的文件里。

```text
<script> 在 head 里 ──▶ DOM 还没建好 ──▶ 竞态条件，代码扑空
<script> 在 </body> 前 ──▶ DOM 已就绪 ──▶ 安全
DOMContentLoaded ──────▶ DOM 就绪才执行 ──▶ 安全（位置随意）
外链 .js 文件 ─────────▶ 由上面任一方式引入 ──▶ 逻辑与结构彻底分离
```

本质上，代码逻辑完全没有改变。

### 边打字边回应：模板字符串与那棵会长大的树

我们把复杂度稍微提一点点。打开 `hello5`。

这个 HTML 看起来内容有点多，不过稍后你就会明白它的逻辑。它没有提交按钮——当你搜索 "C" 这样的内容时，这个巧妙的设计效果就出来了；或者输入完整的 "David"，效果一样。注意看，**这些变化都是直接在网页内部实时发生的**。

```javascript
addEventListener('DOMContentLoaded', function() {
    let input = document.querySelector('input');

    input.addEventListener('keyup', function() {
        let name = document.querySelector('p');

        if (input.value !== "") {
            name.innerHTML = `Hello, ${input.value}`;
        } else {
            name.innerHTML = 'Hello, whoever you are';
        }
    });
});
```

第一行我们已经熟悉了：确保在整个 DOM 加载完成之前，不执行后续操作。接下来声明一个名为 `input` 的变量，让它指向页面上的那个文本框——是的，`document.querySelector` 又出场了。然后**为它添加一个事件监听器**，监听的是 `keyup` 事件，也就是键盘按键弹起，就像我的手指从键盘上抬起那样。当这个事件发生时，就调用后面这个**没有名称的函数**，执行花括号里的代码。

花括号里的第一行，声明了一个名为 `name` 的变量，它显然指向页面上的段落标签。然后是一个 `if`：如果输入框的内容——它的 `.value`——不等于空字符串（引号里空着就表示空值，不过在 JS 里空字符串会被隐式当作假值，所以其实简写成 `if (input.value)` 也一样），就把那个 `name` 元素的内容设置为"你好"加上输入框的值。

> **定义**：这里用到的 `` `Hello, ${input.value}` `` 叫**模板字符串**。它本质上类似于 Python 中的 f 字符串——可以在一段文本里嵌入表达式的结果。

这个语法看起来可能有点奇怪，我之所以展示它，是因为你在网上查文档时很可能遇到这种写法：它不太美观，又是美元符号又是花括号，更糟的是还用了反引号。不过这其实反映了 JavaScript 社区的一种理念：**如果你希望这门语言持续发展演进，就必须确保新版本能够向后兼容旧版本的语言特性。** 所以他们选择了那些在现有代码中几乎不会出现的字符和语法结构。于是有时候这些语法看起来会比预想的更别扭一些——我推测，这就是原因所在。

```text
按下 D      按下 A       按下 V       停止输入
 <p></p>  →  <p>A</p> →  <p>AV</p> →  <p>你好 David</p>
   │           │            │              │
   └───────────┴────────────┴──────────────┴── 每按一次 keyup，树上就多长出一块
```

现在让我用开发者工具看看具体发生了什么。右键 → "检查"，展开下方的 `body` 部分，重新加载页面。默认情况下页面里只有一个空的段落标签——但请注意屏幕底部的变化。等我开始输入名字，比如输入字母 "D" 时，把画面放大，展开那个三角形标记：你现在看到的，正是一棵实际树状结构的实时变化。你看到的这个经过缩进排版、语法高亮的 HTML 结构，就是**内存中那棵树的可视化呈现**。

如果我回到这里并删除我的名字，注意看——结果又回到了默认状态。

### 改的不是文字，是样式

接下来是**第一个展示如何用 JavaScript 代码动态修改 CSS 样式的示例**。打开 `background.html`，页面非常简单，但它是我们第一个交互式网站：三个按钮，分别标为 R、G 和 B。点击 R，页面变红；点 G，变绿；点 B，变蓝。

刷新页面让背景恢复成白色，然后打开开发者工具，专门观察 `body` 标签。初始状态下，body 除了浏览器默认的边距等样式，并没有其他自定义样式。但当我点击 R 按钮——背景颜色突然被**动态添加**为深红色，然后绿色，然后蓝色，同时注意左下角的 HTML 代码也在同步更新。

回到 VS Code 打开源文件。HTML 部分看起来有点复杂，但实际结构很简单：三个按钮，为了能够唯一标识它们，我分别给它们设置了 ID——`red`、`green`、`blue`。这段代码有些重复，坦白说如果设计得更优雅些我本可以避免，但为了确保逻辑清晰，我还是保留了这种写法。

```javascript
let body = document.querySelector('body');

document.querySelector('#red').addEventListener('click', function() {
    body.style.backgroundColor = 'red';
});

document.querySelector('#green').addEventListener('click', function() {
    body.style.backgroundColor = 'green';
});

document.querySelector('#blue').addEventListener('click', function() {
    body.style.backgroundColor = 'blue';
});
```

`let body = ...` 直接取到当前文档树中的 `body` 元素节点；后面这三行，分别处理三个按钮的点击事件——告诉文档选择 ID 为 `red` 的元素、监听 click 事件，每当点击发生，就去设置之前定义的 `body` 变量的 `style` 属性。

> **定义**：在 JavaScript 中，任何元素都可以通过 **`style`** 属性来设置样式。`body.style.backgroundColor = 'red'` 做的事情，和你在 CSS 里写 `body { background-color: red; }` 是一回事。

看这里——我们现在监听按钮的点击事件，但改变的不是按钮本身的内容，而是**整个页面的样式**。

顺带一提，这里有个小知识：这就是所谓的**驼峰命名法**，就像骆驼背上有个驼峰——单词中间有个大写字母突然出现，把两个词分开。而在 CSS 里，回想一下，我们写的是 `background-color`；有人想猜猜为什么在 JavaScript 里不能这么写吗？

因为在 CSS 中，连字符是合法的**标识符字符**；但在 JavaScript 里，**减号是一个数学运算符**。就像左手没跟右手沟通好，然后大家就抱怨：这样一来，`background-color` 就变成了 `background` 减去 `color`，但这显然不对。于是业界决定用首字母大写来解决——就是原本连字符所在位置的那个字符。

### 已删除的闪烁标签，和 setInterval

CSS 还能实现哪些功能？回到我那个年代，我们有一个叫做 **HTML 闪烁标签**的标签，它是 HTML 世界中为数不多的标签之一。**实际上，这个标签已被弃用，从语言中移除了。** 通常来说，人们不会从语言中移除东西——但闪烁标签实在太糟糕了。紧随其后的是**滚动标签**：就像我自己的主页，当年大一新生那样毫无理由地写着"欢迎来到我的主页"，从左到右在屏幕上滚动，就像一个丑陋的滚动横幅，类似如今的数字标牌。

不过我们可以通过别的方式让它重现。打开空白页面——这就是闪烁标签在过去实现的效果。现在这个版本改用 JavaScript：

```javascript
let body = document.querySelector('body');

function blink() {
    if (body.style.visibility === 'hidden') {
        body.style.visibility = 'visible';
    } else {
        body.style.visibility = 'hidden';
    }
}

setInterval(blink, 500);
```

这里还有一个我们之前在 JavaScript 中没见过的全局变量，叫做 **`window`**，它指的是浏览器窗口本身——不一定是页面的具体内容。你可以在它上面调用一个名为 **`setInterval`** 的方法，告诉它去定时执行特定的函数：**每隔指定的毫秒数执行一次**。所以我每隔 500 毫秒调用一次 `blink` 函数，用的就是这一行。

至于 `blink` 函数本身——`body` 是一个变量，它只是指向 DOM 中的 `body` 节点，这个说法可能有点绕口。如果该节点的 CSS `visibility` 属性是 `"hidden"`，就把它改为 `"visible"`；否则就改回 `"hidden"`。

> **易错点**：你可能会以为 `visible` 的反义词是 `invisible`。**但在 CSS 中，`visible` 的反义词是 `hidden`。** 这种琐碎细节只能死记硬背。

```text
                  每 500 毫秒翻转一次
        ┌────────────────────────────────┐
        ▼                                │
  ┌─────────────┐                 ┌─────────────┐
  │   hidden    │ ──────────────▶ │  visible    │
  │  （看不见） │ ◀────────────── │  （看得见） │
  └─────────────┘                 └─────────────┘
```

所以你在这里看到的闪烁效果是——如果我同时打开开发者工具，你会看到左下角的 HTML 和右下角的 CSS 都在自动变化，因为每 500 毫秒就执行一次切换。

### 自动完成：用一个字符串拼出一份列表

自动完成功能，这个我们在 `hello5` 里已经向这个方向迈进了一步。不过在谷歌和现在的几乎每个网站上都非常普遍。

这如何实现？这不仅仅是 HTML 和 CSS 的功劳——其中还加入了 JavaScript 的参与。打开 `autocomplete.html`，我在这里借用了一个名叫 `large.js` 的文件。`large.js` 是一个庞大的 JavaScript 数组，包含了问题集 5（拼写检查问题集）中的所有单词——一个超过 10 万个单词的文件。我们通过使用这样的全局变量，将它转换为 JavaScript 代码。

页面上有一个文本框，然后是一个空的无序列表，接着是这段代码：

```javascript
let input = document.querySelector('input');

input.addEventListener('keyup', function() {
    let html = "";

    if (input.value) {
        for (let word of words) {
            if (word.startsWith(input.value)) {
                html += '<li>' + word + '</li>';
            }
        }
    }

    document.querySelector('ul').innerHTML = html;
});
```

我创建了一个名为 `input` 的变量引用那个文本框，然后监听了 `keyup` 事件——和我们之前做过的一样。接着把一个名为 `html` 的变量设置为空字符串，然后检查输入框是否隐含有任何值。

如果有值，就执行下面这些。**这挺有意思的：它的语法有点像 Python 和 C 的结合体。** 对于 `words` 数组中的每个单词，JavaScript 用的是 **`of`** 关键字，而不是像 Python 那样用 `in`——习惯就好。然后判断：那个包含 10 万个单词的大文件中，当前这个单词是否**以用户输入的内容开头**。如果是，就用**加等于**（`+=`，其实就是字符串连接，我们之前已经见过加号的用法了）把一个 `<li>` 标签拼到 `html` 字符串后面，标签里放上那个具体的单词。

```text
输入 "C"                      输入 "ATS"
┌──────────────────────┐     ┌──────────────────────┐
│ <ul>                │     │ <ul>                │
│   <li>cat</li>      │     │   <li>ats</li>      │
│   <li>car</li>      │     │   <li>cats</li>     │
│   <li>camp</li>     │     │   <li>catski</li>   │
│   …                 │     │   （只剩 4 个匹配）  │
│ </ul>               │     │ </ul>               │
└──────────────────────┘     └──────────────────────┘
      每次 keyup 重建                匹配越来越窄
```

现在你能看到的，就是如今几乎每个网站都在用的做法。他们并不像我们今天大部分时间那样手动编写 HTML——他们编写的是**动态生成 HTML 的代码**，因为程序员们理解 HTML 的本质：他们明白无序列表包含 `<li>` 子元素，于是连续创建了一个又一个 `<li>` 元素，动态更新内部 HTML 内容。

> **结论**：`<ul>` 元素的内容，被设置成了那个变量 `html` 的值。这就是自动完成功能通常的实现原理。

我输入字母 `C` 来搜索 "cats"，系统就从那份 10 万词的词典中筛选出所有以 C 开头的单词；同时观察底层——每匹配到一个单词，就生成一个 `<li>` 元素。而每当你访问 google.com、输入 CATS 看到那些搜索结果时，有人编写了 JavaScript 代码监听你的键盘输入，然后动态生成一个列表来展示匹配结果。**就是这样的。**

### 菜单、地图，和最后那盏灯

最后几个例子。使用 Bootstrap 不仅能获得可用的 CSS，它还提供了一整套 JavaScript 功能，让你可以轻松实现下拉菜单等交互效果——在即将到来的习题集以及你的最终项目中，你可能会用到类似的 Bootstrap 组件。

这段代码是我直接从 Bootstrap 官网复制粘贴过来的，就像企业网站的样板代码，包含定价功能和部分禁用的菜单选项。回到示例里，你会看到一个相当简洁的网站界面，包含一个所谓的**导航栏**，列出了企业网站常见的主菜单选项。注意，当我开始调整窗口大小——窗口变得非常窄时，由于 JavaScript 的作用，界面会自动切换到**移动端显示模式**：它会监听这个**汉堡菜单**的点击事件，并通过这种方式展开菜单选项。这与 CS50 官网以及众多其他网站的实现方式非常相似。

另一个：你们已经习惯了使用谷歌地图、Uber Eats 等需要获取你位置信息的应用。同样的功能也是通过 JavaScript 简单实现的。

```javascript
navigator.geolocation.getCurrentPosition(function(position) {
    document.querySelector('#map').innerHTML =
        position.coords.latitude + ', ' + position.coords.longitude;
});
```

浏览器中的 JavaScript 提供了一个名为 **`navigator`** 的全局对象，它包含一个 `geolocation` 属性对象；该对象有一个 `getCurrentPosition` 方法，它接收一个**匿名函数**作为参数。这意味着当系统准备好获取坐标时（因为 GPS 定位可能需要一些时间），就会执行这段代码。一旦定位完成，这个简单的示例就会把坐标信息写入页面文档——返回的位置信息包括纬度和经度。

我切到另一个标签页重新打开这个示例，出于隐私保护，浏览器会请求授权。选"允许"——这显然是我笔记本电脑的 GPS 坐标。打开 Google 地图网站，把坐标粘进去按回车……严格来说我并没有在室外，所以定位精度有限，系统很可能映射到了建筑拐角处的某个 Wi-Fi 接入点。但定位结果已经相当接近了，基本能满足我叫外卖或网约车的需求。
