### 第七周，换一种语言

欢迎来到 CS50 的第七周。这一周我们介绍另一种编程语言——结构化查询语言，SQL。

先说清楚它为什么值得单独花掉一整周。C 和 Python 在很大程度上都属于**过程式编程语言**：你要一步一步地写出过程、写出函数，告诉计算机该做什么，包括循环、条件语句等等。而 SQL 是**声明式编程语言**，这是完全不同的一个范式——当你想要解决某个问题时，你只需声明你想要解决的问题是什么、你想提出什么问题，而编程语言会负责利用循环、条件语句这些底层构建模块，去找出如何为你提供答案。

```text
过程式（C / Python）
    打开文件 -> 逐行读取 -> 解析逗号 -> 计数 -> 打印
    每一步都要你亲手写出来

声明式（SQL）
    我只要结果：SELECT language, COUNT(*) FROM favorites
    怎么算出来，由数据库负责
```

这也是一次很好的机会，让你再练一次"如何自学一门新语言"。等你修完 CS 15 这样的课程，或者真的进了工作里，你会发现学习新的编程语言其实并没有那么困难——尤其是当你已经接触过过程式、面向对象式，以及今天要介绍的声明式这几种不同的范式之后。

不过话说回来，今天的主题归根结底还是关于**数据**。所以我们不从语法开始，而是先收集一点真实世界的数据。

### 平面文件数据库：CSV 到底长什么样

你现在看到的这个，就是我们常说的**平面文件数据库（flat-file database）**。说它非常轻量，是因为它能存储大量数据；说它平面，是因为它本质上就是一个纯文本文件。

按照惯例，这种文件中的数据确实是通过逗号来分隔各个值的。当然还有其他格式——**TSV**（制表符分隔值）也很常见，还有 **PSV**（竖线分隔值）。本质上，这些文件格式都在做同一件事：试图使用一个在实际数据中不太可能出现的字符来分隔，从而避免混淆，把行与列区分开来。

回到 VS Code 看这个文件：谷歌表格导出来的是三列——时间戳（系统自动生成）、语言以及问题。这里显示有几位参与者提前提交了反馈，看来大家对今天的数据主题非常期待；其他大部分数据是从东部时间下午 1:30 开始记录的。

```text
timestamp,language,problem
2023-09-05 13:30:12,Python,...
2023-09-05 13:31:07,C,hello world
2023-09-05 13:32:44,Scratch,...
```

第一个逗号之前的所有内容代表时间戳；第一个逗号和第二个逗号之间的内容，代表大家提交时选择的编程语言；第二个逗号之后的所有内容，则对应具体的问题描述。这些数据通过逗号分隔，实际上就形成了三列信息。

现在数据的边缘看起来有些参差不齐——有些答案较长，有些较短，列没法整齐地排列——但没关系，逗号足以让代码正确解析这些信息。我们用逗号来标记一列的结束和下一列的开始，这就够了。

### 用 Python 把数据读出来

那么，我们该怎么编写这样的代码呢？假设我们现在想对数据提出一些问题：哪种语言最受欢迎？哪道题最常被提及？或者反过来，看看这些数据里哪些是最不常见的。

谷歌是怎么计算出最受欢迎的答案、决定画哪些饼图的呢？他们很可能编写了与我们即将要做的类似的代码。不过我们还是会像往常一样，先从命令行环境开始。

在 VS Code 里打开一个叫 `favorites.py` 的程序，让它做这样一件事：打开这个 CSV 文件，从上到下、从左到右读取它，然后进行一些计算，找出这些问题中最受欢迎的答案。

```python
import csv

with open("favorites.csv") as file:
    reader = csv.reader(file)
    for row in reader:
        print(row[1])
```

第一行导入的是 Python 自带的一个名为 `csv` 的库。这个库非常方便——它实际上是别人多年前写好的代码，专门用于从文件中读取数据并通过逗号进行分隔，这样我们就不必自己从头实现这些功能了。

`open("favorites.csv") as file` 是 Python 的惯用写法。如果我想明确表示只打算读取这个文件（这也是默认行为），我会明确写上 `"r"`，就像我们在 C 语言中使用 `fopen` 打开文件并指定读取模式时一样。

`reader = csv.reader(file)` 也是一种惯用写法：`reader` 是 csv 库自带的一个函数，它在这里接收的唯一参数就是一个已打开的文件。这个函数会自动识别文件中所有逗号的位置，于是我就可以通过循环遍历这个 reader 对象逐行获取数据，而无需自己编写代码去解析逗号的位置。

`print(row[1])` 打印第二列，也就是语言列。原因是 reader 会为每一行返回一个列表，索引 `[0]` 对应第一列，`[1]` 对应第二列，`[2]` 对应第三列——Python 中所有索引都是从 0 开始计数的。

运行 `python favorites.py`，成功。这里按时间顺序从上到下依次列出了大家在表单中提交的所有语言选项。

不过这里有个小问题：输出里**意外地包含了表头**。我原本只想查看语言数据，但代码确实执行了我编写的指令——打印出每一行内容。

我们可以用几种方法来忽略这个问题。最简单的：创建读取器之后，直接跳过第一行数据。

```python
import csv

with open("favorites.csv") as file:
    reader = csv.reader(file)
    next(reader)
    for row in reader:
        favorite = row[1]
        print(favorite)
```

这样我们直接跳到下一行，实际上就是忽略表头，然后从第二行开始遍历所有数据。重新运行，向上滚动到程序输出的起始位置，第一行内容确实是 `Python、Python、Python……` 依此类推，不再显示带引号的 `"language"` 字样。

这是怎么做到的呢？这是我们之前没有详细讨论过的一个特性，但它很重要：**这个读取器是具备状态保持能力的**——实际上所有文件输入输出操作都具有这种特性。我们之前没有明确说明的是，当你使用 `fread` 或其他函数读取文件数据时，系统会记录当前读取位置，这样就不会反复读取相同的字节内容。

这更像是老式磁带机的工作方式——想象一下盒式录音带或磁带播放器的磁头定位机制，又或者视频播放器的进度条：当你持续读取数据时，系统就按顺序获取下一个数据块、再下一个数据块，同时在计算机内存中持续记录当前的读取位置。

```text
[第 1 次 next(reader)]  ->  表头行（这一行被丢掉了）
[第 2 次 next(reader)]  ->  提交记录 1
[第 3 次 next(reader)]  ->  提交记录 2
[第 4 次 next(reader)]  ->  提交记录 3
位置由 reader 自己记住，你不用手动维护任何下标
```

所以，当执行 `next(reader)` 时，读取器会跳转到下一行。由于它具有状态记忆功能，连续调用四次之后，你就获得了除首行之外的所有数据行。

目前这样做的实用性有限，因为我只是单纯输出数据。现在让我们让它变得更实用一些：我在这段循环中做的事情是确定当前行数据对应的收藏项，所以创建一个名为 `favorite` 的变量并赋值为 `row[1]`，然后输出这个变量。虽然这不会改变程序的功能，但通过定义一个变量来明确 `row[1]` 的实际含义，能让未来阅读这段代码的人（包括我自己）更清晰地理解代码的意图。

### 索引很脆弱，换成字典读取器

但仅靠变量名来理解数据是有限的。想象一下：如果我再次用 Microsoft Excel、Apple Numbers 或 Google Sheets 打开这个 CSV 文件，可能会遇到这样的情况——有人通过拖动列来调整数据顺序，导致原本的"时间戳、语言、问题"变成了"时间戳、问题、语言"，甚至可能只剩下"时间戳"这一列而把语言挪到了最右侧。

你可以想象，我们使用的索引（0、1、2）会变得有些脆弱。因为如果有人现在更改了数据，我的代码就会出错——我盲目地假设第二列（即索引 1）是语言列，但这可能已不再成立。

不过我们还有另一种方法。把这里改成**字典读取器**（`DictReader`），而不只是普通的读取器：

```python
import csv

with open("favorites.csv") as file:
    reader = csv.DictReader(file)
    for row in reader:
        favorite = row["language"]
        print(favorite)
```

使用字典读取器的好处在于：每次我遍历这个循环逐行读取数据时，reader 返回的每一行将不再是一个用数字索引（0、1、2）表示的列表，而是一个**字典**，也就是一组键值对。这意味着我们现在可以用**单词**作为索引，而不仅仅是数字。也就是说，无论语言列在什么位置——在最左边、中间还是最右边——我都可以明确指定"我要 language 那一列"。

总的来说，使用字典读取器通常会更加鲁棒，因为它能有效应对实际数据中列顺序的变化。

> **提示**：既然换成了字典读取器，之前那个 `next(reader)` 就可以删掉了。那个调用只在 `csv.reader` 里才是必需的，因为它会反复返回每一行、包括第一行；而字典读取器需要通过第一行来确定各列的名称，所以它会自动把首行处理掉。删掉之后，这反而是一个更好的字典读取器实现。

### 数一数谁最受欢迎

我先暂停一下，看看大家对这个练习有没有什么问题——这个练习的目的主要是演示如何下载 CSV 数据，然后逐行遍历它，目前还不需要进行实际的数据分析。

好，那我们来问一个最自然的问题：有多少人更喜欢 Python？那么，有多少人更喜欢 C 语言或 Scratch 呢？换句话说，我们该如何在自己的代码中重现 Google Forms 通过饼图为我们实现的图形化功能？

我这里正好可以利用一系列键值对——如果我想知道 Python 出现了多少次，以及 C 语言和 Scratch，那么这三个就可以作为**键**，对应的**值**应该是数字，比如 3，表示每种语言的受欢迎程度计数。

在黑板上画的话，就是这样一个两列表格：

```text
键（favorite）    值（计数）
"scratch"        24
"C"              58
"Python"         109
```

但别忘了，这种思维模型完美对应了 Python 字典的概念，因为字典正是键值对，我们已经见过它了，因为字典读取器就是这样工作的。当然我们也可以使用自己的字典来做同样的事。

先来一版直白的：

```python
import csv

scratch, C, Python = 0, 0, 0

with open("favorites.csv") as file:
    reader = csv.DictReader(file)
    for row in reader:
        favorite = row["language"]
        if favorite == "scratch":
            scratch += 1
        if favorite == "c":
            C += 1
        if favorite == "Python":
            Python += 1

print(f"scratch: {scratch}")
print(f"C: {C}")
print(f"Python: {Python}")
```

如果你之前没见过，这里其实可以用一些 Python 的简洁写法：如果有三个变量想同时初始化、而且初始值都这么简单，那么 `scratch, C, Python = 0, 0, 0` 也能达到和写三行 `x = 0` 一样的效果，而且看起来更简洁，只用了一行。

那接下来该做什么呢？在开始用真正的字典优化之前，我们先做一个简单的条件判断：`if favorite == "scratch"`，就用之前见过的 `+= 1` 给 scratch 加一；`if favorite == "c"`，就给 C 加 1；`if favorite == "Python"`，就给 Python 加 1。

理论上这里我可以用 `else` 来处理，但这次我有意**不做过度的优化**。因为如果将来有人修改了表单内容——比如下学期课程调整之类的——而我们询问的是第四种语言，我不希望我的代码默认所有非 `"scratch"` 或 `"C"` 的情况都一定是 `"Python"`。将来可能还会有第四种语言出现，所以这样处理会更稳妥：只统计 scratch、C 或 Python，其他的都忽略掉。

（另外提醒一句：我第一次写的时候忘了格式化输出，得用 f-string，所以每个字符串前面都得加上小写的 `f`，否则花括号会被原样打印出来。）

运行这个版本，期待看到的不是重复显示每一行数据，而是输出 3 行结果。结果和我们之前在 Google 表单里看到的比例基本吻合：有 109 位同学喜欢 Python，其次是 58 位喜欢 C 语言，还有 24 位同学更喜欢 Scratch。

### 为什么三个变量还是不够理想

但为什么这个做法可能让你觉得不太对劲呢？

**仅仅用三个变量来存储数据确实不太理想。** 没错，正是这样。如果我们还要添加更多编程语言——比如第四种、第五种、第六种，甚至第十种、第二十种——用那么多变量来存储的话，代码肯定会变得臃肿不堪，而且根本没法高效管理。

这时候我们确实应该升级到更合适的数据结构了：用 C 语言的话是数组，而在 Python 中，我们可以用——用真正的字典结构。

```python
import csv

counts = {}

with open("favorites.csv") as file:
    reader = csv.DictReader(file)
    for row in reader:
        favorite = row["language"]
        if favorite in counts:
            counts[favorite] += 1
        else:
            counts[favorite] = 1

for favorite, count in counts.items():
    print(favorite, count)
```

`counts = {}` 创建了一个空字典——只需一对花括号就能实现。或者如果你想更严谨一些，也可以直接调用 `dict()` 函数，它同样会返回一个空字典；不过我觉得大多数人还是更习惯用双花括号来表示空字典。

我们不需要再更新三个独立的变量了。一旦确定了当前行中语言对应的偏好值，就可以通过 `counts[favorite]` 来访问——这里用当前字符串作为字典的索引，所以会是 `"scratch"`、`"C"` 或 `"Python"` 这样的字符串，然后将其对应的计数加 1（也就是递增）。字典在这里，本质上就是上面那个两列表格的代码实现形式：键是收藏的字符串，值是实际的计数。

> **易错点**：遗憾的是，这段代码无法正常运行——一运行就出现了**键错误（KeyError）**。
>
> 为什么？如果这是程序第一次处理这个文件，字典里根本不存在 `"Python"` 这个键，也不存在 `"C"` 和 `"Scratch"`，因为程序还没往里面添加过它们。而要记住，`+=` 这个操作符的意思是：直接定位到字典中的那个位置，然后盲目地对其值进行递增。但那个位置的值是什么呢？它甚至连垃圾值都算不上，因为那个键根本不存在。

解决这个问题可以通过几种方式，它们都相当合理：

- **先问再动**："如果这个 favorite 在 counts 字典里"——用 Python 的习惯说法就是，这个键在这个字典里吗？如果是，就可以像之前那样安全地递增它；如果不在，那就把 `counts[favorite]` 设为 1，因为我要么是将当前计数加 1，要么这是第一次看到这个 favorite，所以需要将其初始值设为 1。
- **不存在就先归零**：一个 `if` 写成"如果 favorite 不在 counts 中，就令 `counts[favorite] = 0`"——如果它不存在，就始终将其初始化为 0。这样我就可以放心地直接把计数加 1，因为无论怎样，一旦执行到这一行，这个计数肯定已经存在了。
- **预判它可能会出错**：先尝试执行这个操作，但如果出现键错误，那就直接将该键的值初始化为 1。简而言之，这甚至可以说是更符合 Python 风格的写法——先尝试执行某个操作，同时预判到它实际上可能会出错。

简而言之，解决同一个问题已经有大约四种不同的方法了，无论你选择哪种方式都是相当合理的，这仅仅是另一种实现方式。

用这个版本的代码重新运行，先把终端窗口清空。结果出来了：Python 和 Scratch 的数量都有。有意思的是这次顺序变了，这取决于我向字典中插入数据的顺序——不过我们接下来会看看如何更好地控制这一点。

顺便提一下我们上周简单讨论过的键错误：每当遇到这类指向特定异常的追踪信息，先别慌，它意味着的往往是"可能发生的极端糟糕情况"，你也可以修改代码，先尝试执行某个操作，然后捕获可能出现的异常。

### 该换数据库了：关系模型

所以，像这样写这么多代码，就为了回答一个相对简单的问题——比如这个文件里哪种语言最流行——确实有点麻烦，对吧？这感觉有点像从谷歌表格、苹果 Numbers 和微软 Excel 那种便捷操作退了一步：在那些工具里，你通常只需要选中一列，答案就会自动显示在右下角，或者直接用内置函数就能解决同样的问题。

所以现在感觉，光是写差不多 20 行代码，可能就有点……我敢肯定存在更好的方法，而不是继续跟平面文件数据库较劲。让我们直接升级到业界所说的**关系型数据库**。

关系型数据库本质上是一种能让你定义数据间**关联**的数据存储方式。现在听起来可能不太直观，但举个例子：每条时间戳记录不仅对应着一个编程语言，同时也关联着用户偏爱的题目类型。数据集可以变得更大、更复杂，而这样的结构会很有价值——我们可以表达多个数据片段之间的关系。

### CRUD：SQL 只做四件事

现在我们具体来介绍一种名为**结构化查询语言**的编程语言，简称 SQL（也常读作 sequel）。

SQL 本质上只包含四种基本操作。所以，即使我们今天要过渡到一门新语言，也会发现它的核心很快就能掌握，因为它的功能范围非常明确。和任何语言一样，掌握 SQL 确实需要时间和练习才能熟练运用——不过请放心，它只支持四种基本操作。

这四种操作对应的通用缩写是 **CRUD**：

| 缩写 | 全称 | 含义 |
| --- | --- | --- |
| **C** | Create | 创建数据 |
| **R** | Read | 读取数据 |
| **U** | Update | 更新数据 |
| **D** | Delete | 删除数据 |

也就是说，在使用关系型数据库时，你可以创建数据、读取数据、更新数据或删除数据——这些操作基本涵盖了所有可能的数据处理需求。

那么，究竟什么是真正的数据库呢？一般来说，数据库本质上是一个运行在计算机上的软件，它内部存储着大量数据，并为你提供访问这些数据的途径。无论何时，无论是在你本地的 Mac 或 PC 上，还是在云端，甚至是在整个网络服务器集群中——随着我们后续从命令行工具转向网页应用，这些概念都会在接下来的几周内详细探讨。

从技术层面来说，在 SQL 中用于实现这些操作的命令几乎与 CRUD 一一对应。不过出于某些原因，业界选择了使用 `SELECT` 命令来对应读取操作，而其他三个选项当然指的是写入数据、修改数据：从技术上讲，我们能够向数据库中插入数据，也能够完全删除数据——不仅仅是删除单行数据，还可以删除整个数据表，也就是整组数据行。

在 CS50 中，我们会使用一种名为 **SQLite** 的特定 SQL 版本。它就像 SQL 的轻量版，在网页应用和移动应用中非常常用。当然它不具备 Oracle、SQL Server、Microsoft Access、PostgreSQL、MySQL 等数据库产品的所有高级功能或扩展性——这些只是不同的数据库产品，无论是开源还是商业，它们都代表着更强大、更快速的 SQL 数据库版本。不过我们确实会使用它的轻量版，也就是 SQLite。

### 建库导表：SQLite 3 与点号命令

如果要手动把一批数据加载到适合用 SQL 查询的数据库中，实际上会使用这样的代码：我会直接输入 `CREATE TABLE`，为这个表起个名字，然后逐一指定要放入表中的每一列。

接下来就是术语转换的地方了。在电子表格的世界里，我们使用包含行和列的**工作表（sheet）**或**标签页（tab）**；而在数据库的世界里，我们使用的是同样由行和列构成的**表（table）**。虽然术语不同，但它们在概念上指的是同一个东西。

我们要运行的命令是 `sqlite3`，这是该命令的第三个版本，我们已经提前为你们在代码空间中安装好了。

```bash
sqlite3 favorites.db
```

运行它将创建我的第一个 SQLite 数据库，然后我们把从 Google 表单下载的 CSV 文件导入到这个数据库中。换句话说，我把同样的数据集加载到了另一个程序——一个真正的数据库中，这样我就可以使用一种完全不同的编程语言来查询数据，而不是像刚才那样编写 Python 代码。（`sqlite3 favorites.db` 里的 `.db` 后缀就是数据库的惯用命名。）

系统会提示我确认是否要创建这个新文件，输入 `Y` 表示确认，回车——现在我已经进入数据库环境了。提示符下显示的是 `SQLite`，后面跟着一个大于号 `sqlite>`。

我会使用数据库的交互式解释器，通过直接输入命令来交互式地执行所有需要的操作：输入命令、分号、回车，反复操作；你也可以把所有这些命令保存在单独的文件里，就像你在问题集中见过的那样。

> **提示**：在 SQLite 中，任何以点号开头的命令都是 SQLite 特有的指令；任何**不**以点号开头的命令都具有通用性，可以在世界上几乎所有的 SQL 数据库上运行，无论你使用哪种产品。

那么，我该如何把这个 CSV 文件实际导入到数据库中呢？为此我将执行三条命令：

```text
sqlite> .mode csv
sqlite> .import favorites.csv favorites
sqlite> .quit
```

第一条把模式切换为 CSV 模式，这样就能告诉数据库我要加载一些 CSV 格式的数据；第二条指定数据来源文件（就是我们之前下载并拖进代码空间的那个 `favorites.csv`）以及表名——我打算把这个表命名为 `favorites`，以保持命名的一致性。既然没有出现错误提示，那很可能一切运行正常；第三条是退出程序。

退出之后再输入 `ls`，你会看到目录里不仅有我上传的 `favorites.csv` 和几分钟前创建的 `favorites.py`，现在还多了一个 `favorites.db`——这正是那个 CSV 文件的数据库版本。

现在我还无法直接查看它的内容。如果尝试用 `cat` 命令打开 `favorites.db`，我会看到它无法在文本编辑器中正常显示，因为它要么是二进制格式，要么采用了不支持的文本编码方式。这种情况很正常，因为数据库本质上是以**二进制**形式存储的，也就是由 0 和 1 组成的数据结构，只有 `sqlite3` 程序能正确读取这种格式。VS Code 这类文本编辑器无法直接展示其中的完整内容。总的来说，用二进制格式存储数据通常比纯文本方式更高效，因为这样就能运用我们讨论过的各种数据结构和算法，处理起来方便得多。

那么，这条导入命令具体做了什么？重新运行 `sqlite3 favorites.db`——这次直接进入了，因为文件已存在。输入另一个 SQLite 特有的命令 `.schema`：数据库的**模式（schema）**就是数据库的设计结构，它里面有哪些表、哪些行、哪些列。

```text
sqlite> .schema
CREATE TABLE IF NOT EXISTS "favorites" (
  "Timestamp" TEXT,
  "Language" TEXT,
  "Problem" TEXT
);
```

`"favorites"` 是表的名称，括号内列出三列：第一列名为 Timestamp，第二列名为 Language，第三列名为 Problem，且每一列的数据类型都是纯文本。这是我使用 `.import` 命令时 SQLite 为我创建的默认表——我们很快就会看到，它并不一定只能是文本类型，我可以对存入这个数据库的数据类型有更多的控制。

不过，`.import` 命令真正方便的地方在于，它能极其轻松地将 CSV 文件转换为 SQLite 数据库。这样一来，我们接下来就能直接使用 SQL 来操作数据，而无需依赖 Python 或其他编程语言了。

### 第一条查询：SELECT、COUNT 与 DISTINCT

好的，那么我们该怎么从这个数据库中获取数据呢？我们要探索的第一个命令就是 `SELECT`——它意味着从数据库中读取数据。

从这个意义上说，SQL 是一种声明式语言：我只需要声明要从数据库中选择哪些数据，而不再需要操心如何打开文件或进行迭代操作。我不再需要编写 `for` 循环或 `while` 循环，也不需要定义相关变量，只需通过语法声明我想要选择的内容即可。

```sql
SELECT * FROM favorites;
```

在 SQL 代码中，分号又回来了——这是我们当前编写查询时必须遵循的语法规范。按下回车键，我们会看到一个类似 ASCII 字符画风格的表格显示结果；这样的呈现方式，甚至比直接查看原始 CSV 文件中输入到这个表里的所有数据还要直观清晰。

`SELECT * FROM favorites` 这条语句的作用显然是选取所有数据。这里的星号在某种程度上相当于一个**通配符**，代表的是表中的所有列，而这个表本身的名字就是 `favorites`。结果按时间顺序排列，因为这正是数据被加载进数据库时的原始顺序。

既然星号是通配符，我们还能用它做些什么呢？如果你不需要获取所有列，完全可以指定得更精确一些：

```sql
SELECT language FROM favorites;
SELECT language, problem FROM favorites;
```

第一条只从 `favorites` 表中选取 `language` 这一列，每一行对应一次提交，但不会显示时间戳或该用户填写的"最喜欢的题目"；第二条如果我不需要时间戳，查询结果就只显示两列。

想想这个对比：我们之前用 Python 写了十几行代码来打开文件并用读取器遍历数据，而现在只需从这个数据库中直接选取我们想要的数据即可。

更强大的是，SQL 内置了丰富的函数，这很像我们日常使用的电子表格软件，比如 Excel、Numbers 和 Google Sheets。SQLite 内置了平均值函数、计数函数、去重、小写转换、最小值、最大值、大写转换等一系列功能，足足有一整张清单可供参考。

**计数。** 假设我只想获取 `favorites` 表中的总行数，也就是在我下载文件的那个时间点，那个文件里最终有多少条记录（即使当时并非所有人都已提交数据）：

```sql
SELECT COUNT(*) FROM favorites;
```

现在我会得到一个单元格的结果：在我下载该文件时，已有 272 份提交记录。

**去重。** 假设我想确认一下有没有人提交了无效数据、实际输入了哪些编程语言呢？那我只查询不重复的数据：

```sql
SELECT DISTINCT language FROM favorites;
```

这样会得到一个唯一的语言列表，其中包含每个人提交过的所有编程语言，无论每种语言被提交了多少次。如果我想统计一下有多少种不同的编程语言，而结果不像显示出来的 3 种语言这么明显，我可以直接查询不重复编程语言的数量：

```sql
SELECT COUNT(DISTINCT language) FROM favorites;
```

3 就是在那次提交中出现的不同编程语言的总数。

所以，虽然直接看数据也能轻松得出答案，但通过编写这些从左到右类似英语的简单语句，我就能快速筛选出这些问题的答案。

### WHERE：把条件写进查询

我们还可以往 SQL 命令里添加一些关键字，以便进一步控制返回的数据。我们可以根据相似的值对数据进行分组；我们不仅可以检查字符串是否完全匹配，还能进行模糊匹配，检查某个内容是否接近我们要找的字符串；我们可以限制返回的总行数；我们可以按特定列对数据进行排序；并且我们实际上可以使用类似 `WHERE` 子句的谓词条件来筛选数据——它类似于条件判断语句，但书写形式更为简洁。

先回到最直接的问题：直接查询有多少人选择了 C 语言作为最喜欢的编程语言，而无需重新统计所有选项的数量。

```sql
SELECT COUNT(*) FROM favorites WHERE language = 'C';
```

当查询条件设置为 `language = 'C'` 时，系统返回了简洁的结果：共有 58 位参与者选择了 C 语言。

有多少位参与者**同时**喜欢 C 语言，并且特别钟爱那道名为 `"hello world"` 的题目呢？

```sql
SELECT COUNT(*) FROM favorites
WHERE language = 'C' AND problem = 'hello world';
```

当查询条件设置为 `problem = 'hello world'` 时，结果显示有 5 位参与者表示自己最喜爱的编程语言是 C，同时最钟爱的程序是 `"hello world"`。

现在情况开始变得更有趣了。那么，另一个版本的 "Hello World"——也就是我们命名为 `"hello it's me"` 的那个——情况如何呢？

这个例子很有意思，因为它可能会打破我在 SQL 中惯用的单引号规则。当我们处理原始字符串时，通常使用单引号是标准做法。不过现在——

```sql
SELECT COUNT(*) FROM favorites
WHERE language = 'C' AND problem = 'hello, it''s me';
```

乍看之下，中间那个撇号究竟属于第一个引号还是第二个引号呢？这种情况确实会产生歧义，而且显得很别扭。在 C 语言中，我们通常会在它前面加上一个反斜杠、也就是所谓的转义字符来解决这个问题；不同的编程语言有不同的约定俗成。这个做法有点特别，但在 SQLite 中，你实际上需要将单引号写成**两个连续的单引号**。因此，使用两个单引号是转义单个单引号的惯例——在实际工作中，这类细节要么靠记忆，要么就得随时查阅资料。要是记不住的话。

结果：看来你们当中并没有人既喜欢 C 语言，又特别喜欢那道题。

那么，如果我们想稍微放宽条件，把包含 `"hello"` 的问题也纳入进来呢？

```sql
SELECT COUNT(*) FROM favorites
WHERE language = 'C'
  AND (problem = 'hello world' OR problem LIKE 'hello, %');
```

（括号里的写法有点长、跨了两行，看起来有点乱，但逻辑上就是在筛选"用 C 语言答题、且题目为 hello world 或 hello it's me"的记录。之所以用这种语法，是因为它能让查询语句更清晰一些。）

结果应该和之前一样，因为你们都没有选择 `"hello it's me"` 这个题目。

之前我用等号来检查字符串是否**完全匹配**——比如那些具体的题目名称；而现在使用 `LIKE` 运算符，它允许我使用通配符。不过这里的通配符和之前我们见过的星号用法不太一样：在 SQL 中，当你在字符串中使用通配符时，**百分号 `%` 代表零个或多个字符**。所以 `'hello, %'` 这个模式应该能匹配这条记录，或者任何其他以 `"hello, "` 开头的题目。这就是 SQL 处理这类查询的方式，而它确实展示了如何通过模式匹配实现更灵活的查询表达。

> **易错点**：用 `=` 进行字符串精确匹配时**区分大小写**，但使用 `LIKE` 时**不区分**大小写，无论大写还是小写都能匹配。

那 SQL 中关键字的大小写风格呢？我认为这是一种 SQL 风格惯例，不仅在 CS50 课程中，全球许多企业和社区也普遍采用——**建议将 SQL 关键字全部大写**，这样能让你自己定义的标识符（比如表名列名这样的 `favorites`、`language`）与关键字形成清晰区分。这只是一个约定俗成的惯例，坦白说这样确实能让代码更易阅读：SQL 关键字会凸显出来，而小写部分则专属于你的数据集。一如既往地，保持风格的一致性就好。

### GROUP BY：把相同的值归成一堆

我们来看另一组关键字，`GROUP BY`。万圣节快乐——这里只是该表格的一个节选片段。

假设我们有这样一个数据集：就编程语言偏好而言，1 人喜欢 C 语言，3 人喜欢 Python，而现在我们开始学习 SQL，不妨想象一下，有 2 人现在更喜欢 SQL 了。这就是该数据集的全部内容。

如果能统计出你们中有多少人喜欢 C 语言、Python 或 SQL，是不是会很有用呢？我可以写一些 Python 代码，打开文件，用变量和字典来遍历它，大概也就 20 行左右吧——我们之前写的那些代码行，就是为了回答这个问题。但直接让 SQL 来统计，会不会更方便呢？

我们可以**按相同值对这些单元格进行分组**：把所有包含 Python 的行归为一组，所有包含 SQL 的行归为一组，即使只有一个也归为一组，把包含 C 语言的行单独归为一组。

```sql
SELECT language, COUNT(*) FROM favorites GROUP BY language;
```

这个操作需要稍加练习才能熟练掌握，不过简单来说："选取所有的 `language`" 意思是查看所有编程语言，本质上就是将相同的编程语言归类分组，然后统计出每种语言在分组后的行中对应的总数量。

```text
  Python ┐
  Python ├─▶ Python | 3
  Python ┘
  C      ┐
  C      ├─▶ C      | 1
  SQL    ┐
  SQL    └─▶ SQL    | 2
```

回车之后得到的结果，就像运行那 20 行 Python 代码一样。而数据库内部的实际处理过程，其实就有点像上面画的那个样子——请注意这里只有一个版本的 C，Python 有 3 个版本，SQL 有 2 个；我构建这个表，本质上就是为了将所有相同值的数据分组，然后在这里输出它们的总计数。

而在收到 200 多份回复之后，我们得到了更全面的答案，比如这里就出现了 Scratch，而不是 SQL。顺带一提，所有这些数字都只是"某个时间点的快照"——回复还在陆续进来，所以同一个问题在不同时间跑出来的数自然不一样。

但这恰恰说明了：如果你想提出类似的问题，尤其是在数据集超过几百行的情况下，使用这种方法会方便得多。比如在现实工作中，如果你的老板有一个 CSV 数据集需要你分析，你完全可以下载它、导入到 SQLite 中，然后运行一条命令——砰！分析结果就出来了。如果分析的目的只是对数据进行分组和统计，看看数据集中有哪些类型的账户，那就更划算了。

### 排序、别名与 LIMIT

我们可以对这些结果再深入探索。比如对这些结果进行排序，而不是仅仅使用默认的显示方式：

```sql
SELECT language, COUNT(*) FROM favorites
GROUP BY language
ORDER BY COUNT(*) DESC;
```

这确实有点拗口，需要多加练习才能记住所有这些语法。但现在当我按下回车键时，我得到了相同的答案，只是这次 Python 位于列表的最顶端。

说实话有点烦人的是，我必须在 `ORDER BY` 里、以及整个语句的开头都写上 `COUNT(*)`——这个名称并不一定那么直观易懂。**原来 SQL 也支持别名功能。** 如果你想临时把列名改成其他名称，比如用 `n` 来表示数量，那么实际上可以在末尾使用关键字 `AS` 来定义一个别名：

```sql
SELECT language, COUNT(*) AS n FROM favorites
GROUP BY language
ORDER BY n DESC;
```

执行这条语句后按下回车，同样会返回相同的结果。

如果这还不够直观的话，其实每一条 `SELECT` 命令本质上都会返回一个**临时表**。它并不会像现在这样被保存到任何地方——一旦我得到答案，它就会从计算机的内存中消失。但它本质上返回的是计算机内存中实际存在的那个表的子集，因为导入命令的作用正是把整个数据集加载到了内存中；现在这些临时表只包含我关心的那个问题的答案。

如果你只关心排名第一的语言，那么也可以使用 `LIMIT` 关键字——完全可以就在完全相同的语句末尾加上 `LIMIT 1`，然后回车执行：

```sql
SELECT language, COUNT(*) AS n FROM favorites
GROUP BY language
ORDER BY n DESC
LIMIT 1;
```

现在，我得到了问题的唯一答案：一行数据显示 Python 是最受欢迎的语言，有 190 人选择了它。

## 从 favorites 到 IMDb：把增删改查写对，也把数据设计对
> 对应块：BLK22 | 覆盖分集：P08中1 | 块标题（分集名）：《SELECT 查询：条件排序与聚合》

### 插一行，顺便认识 NULL

关于 SELECT 的内容差不多够了。虽然还剩几个关键词，但那本质上只是把这几块基础积木组合起来的问题，我们直接往前走，看看插入数据。

在 SQL 里往一张表里插入一行，标准写法是：`INSERT INTO` 加表名，然后在括号里指定要插入的一列或多列，接着是关键字 `VALUES`，在另一组括号里按同样的顺序列出对应的值，逗号分隔。

回到 VS Code。就在几分钟前我们分发这张表的时候，习题集 7 还没布置。但里面有一道题叫 "50ville"，我猜一周之内它就会成为某些人最喜欢的题目。既然如此，我们现在就提前把这一行插进去。

```sql
INSERT INTO favorites (language, problem) VALUES ('SQL', '50ville');
```

列只有两个：language 和 problem。至于时间戳，我不想费心去搞清楚它的具体格式，干脆就省略这一项了。

执行 `SELECT * FROM favorites;`，新行确实出现在表格底部了。但是——这里不是一片空白。

> **定义**：`NULL` 不是空指针，虽然字面相同，这里它特指数据的缺失。

我们熟悉的老朋友 NULL 出现了。而这其实是一个非常好的特性。如果你们中有人用过电子表格——苹果的 Numbers、微软的 Excel——当你看到一个空白的单元格时，你真的知道那里"什么数据都没有"吗？还是说你只是暂时没有那里的数据，或者数据以某种形式缺失了？

电子表格给你的只是一个临时补救办法：写个 "N/A"，表示"不可用"。但用 "NA" 就要付出代价——你从此再也不能在单元格里真的输入 "NA" 这几个字母作为答案了。

而 SQL 的做法干净得多：NULL 表示数据被**有意识地**省略了，它不仅仅是一个缺失值，而是一个被明确设置成"此处无值"的状态。这样我就能把 NULL 和其他一切值区分开来。

### 一个 WHERE，抹掉一整间办公室

删除数据也一样简单：`DELETE FROM` 加表名，再跟上 `WHERE` 和条件。

```sql
DELETE FROM favorites WHERE timestamp IS NULL;
```

`WHERE` 是另一个 SQL 关键字，它把范围限制在"时间戳为 NULL 的那些行"。执行刚才那条 `SELECT * FROM favorites;`，瞧，那一行现在已经消失了。

> **易错点**：使用 DELETE 时，务必、务必、务必格外小心。

如果我当时愚蠢地这样做了呢——只写 `DELETE FROM favorites;`——猜猜结果会怎样？它会删除所有数据。你可以上网搜搜，能看到一些真实案例：某公司实习生权限过高，操作公司数据库时因为忘记添加筛选条件就执行了类似的 `DELETE FROM`，手快一按回车，砰，所有数据瞬间就没了。

所以这些命令的破坏性极强。就像在现实世界中一样，如果你没有为这些表做好备份、没有保留版本，数据就是真的可能永久丢失。千万别那样做。请始终确保你的 `WHERE` 子句存在，并且条件设置正确。

### UPDATE、DELETE 与 DROP：不可逆的几步

更新表中行的通用语法也很直接：`UPDATE` 加表名，然后是关键字 `SET`，后面跟一系列键值对——把你想更新的列设置为目标值，并加上你要满足的条件。

假设我们姑且认为 50ville 会在学生中变得非常热门，热门到一夜之间就成了所有人最喜爱的题目。

```sql
UPDATE favorites SET language = 'SQL', problem = '50ville';
```

这里我再次没有添加任何谓词来过滤数据，直接按了回车。看起来没有发生什么异常。但现在执行 `SELECT * FROM favorites;`，所有人似乎都会喜欢 50ville，而且**无法恢复到表格的先前版本了**——除非我退出当前操作，重新导入整个 CSV 文件，可能还需要先把现有数据完全删掉。

那怎么删光呢？

```sql
DELETE FROM favorites;
```

好，我们执行一下，来确认这确实是个糟糕的主意。数据库里现在确实一条数据都没有了。但当然，我们还能从真正的 CSV 文件恢复数据。

所以到这里，我们已经完整地学过了 `SELECT`、`INSERT`、`UPDATE`、`DELETE`。

再看看 `DROP` 吧。虽然 favorites 表里的那些 ID 是 SQLite 3 自动生成的，但我们现在就可以演示 DROP 的用法：先用 `.schema` 命令看到数据库中的所有表，然后执行

```sql
DROP TABLE favorites;
```

再跑一次 `.schema`，你会发现这个数据库里现在什么都没有了。

> **注意**：除非你清楚自己在做什么并且确实需要，否则 `DROP` 是一个比 `DELETE` 更危险的命令。

至此，CRUD——创建、读取、更新、删除——四块拼图齐了。

### 三个当场被问到的问题

**为什么 NULL 周围不用引号？** 因为 NULL 是一个特殊的关键字。如果你给它加上引号，那就变成在查找字面值 "NULL" 这个字符串了——那可能只是 CSV 文件里某个语言、问题或类似东西的名称，字面意思就是 "NULL"。而我们真正想找的，是那些完全缺失的数据。

**第二个问题问得特别好**，因为像这样误删数据实在太容易了：大家平时都有在主动备份自己的数据吗？简单来说，是的，绝对有。比如 CS50 的所有 web 应用及相关系统，都会按计划自动备份。即便如此，我们仍需确定备份的具体频率——如果只是每天夜里备份一次，那在最坏的情况下，我们仍可能损失将近 24 小时的数据。因此许多公司会采用更密集的数据版本控制策略，比如每 5 分钟甚至每分钟备份一次；这会占用更多存储空间，但这正是计算机领域中常见的权衡取舍，在数据安全性和存储成本之间找到平衡点。

**访问控制呢？** SQLite 是一个轻量级的数据库，它本身并不支持用户名或密码的概念——只要你能访问到那个数据文件，就能操作其中的所有内容。但实际应用中，无论是商业数据库（如 Oracle、SQL Server）还是开源数据库（如 PostgreSQL、MySQL），它们都支持用户名、密码以及细粒度的权限管理。这样你就可以为不同用户（比如实习生）分配特定权限：允许他们查询数据，但不允许更新、删除或插入，或者根据需求灵活组合。这些数据库确实提供了安全防护机制。

### 三次失败的数据建模

命令部分到此为止，接下来我们用一些真实世界的数据来实际操作一下。相信很多人都听说过 IMDB（互联网电影数据库），它是一个非常棒的数据资源库，收录了大量电影、电视剧、演员等相关信息。在它的网站上你实际可以下载 TSV 文件，也就是制表符分隔值文件；我们已经提前把这些数据下载好了，并转换成了多个 SQL 表，这样我们就可以在电视剧的背景下开始操作。

不过我们先从一个更根本的问题开始：如何为电视剧本身的数据建立模型。

《办公室》这部剧非常受欢迎——美国版，由史蒂夫·卡瑞尔等人主演。如果我想象一下自己用一张 Google 表格记录"谁出演了哪部电视剧"，我大概会这样做：第一列是标题，写《办公室》；如果主演只有一个人，就在下一列写史蒂夫·卡瑞尔；作为第二位主演，我可能会一列接一列地填入雷恩·威尔逊、约翰、珍娜或 B.J. 诺瓦克等人；然后继续添加一部又一部剧，每部剧占一行，每行包含该剧的所有主演。

这个数据结构有什么不太合理的地方？

**这种"主演、主演、主演……"的重复列结构确实有点奇怪，仅此而已。重复通常不是好的设计——每当我们需要复制粘贴时，都应该意识到这可能是设计上的问题。**

还有一点：目前我只设置了五个主演列，但电视剧的主演人数可能更少或更多。我可以一直添加"主演、主演、主演……"这样的列，然后数据集就会变得非常不规整，成为一个高度稀疏的数据集——演员阵容较小的剧集会出现大量空白单元格，阵容庞大的剧集则需要创建大量列。随着演员数量（更不用说剧集数量）的增加，这会越来越混乱。**这应该让你觉得设计上存在问题。**

于是我整理了另一个版本。列的数量不再随剧集任意变化了：和之前一样只保留一个标题列，但现在只有一个演员列——如果一部剧有多位主演，就把每位演员的名字都列出来，并在其左侧注明他们所属的剧集。

看起来稍微好一些，我似乎解决了一些数据冗余的问题。但我这就**像是堵住了漏水管上的一个洞，结果另一个地方又冒出了新的漏洞**。现在我有《办公室》、《办公室》、《办公室》……这同样让人觉得在浪费存储空间。而且如果我手动输入这些内容，很可能最终会出错，某个条目迟早会拼写错误，然后某些功能就出问题了。

### 第三个版本：一张全是整数的交叉引用表

第三个也是最终版本的数据模型，虽然看起来有点晦涩，但至少从学术角度来说，这是正确的方法；而且它会引导我们走向实际数据库中类似的设计结构。

我在一个电子表格里做了三个独立的工作表：

```text
   shows（节目表）        people（人员表）        stars（主演表）
   id   | title          id | name   | year      show_id | person_id
   -----+---------------  ---+-------+------      --------+----------
         | ...              ...                      ...
```

在节目表里我保留了标题列，但决定为《办公室》这部剧分配一个唯一标识符。这很像哈佛学生拥有唯一的学号，也类似于公司员工通常会有唯一的工号。给《办公室》分配的标识符恰好与它在 IMDB 中的编号相同：386676。

与此同时，对于电视剧世界中存在的所有人物，比如那五位演员，我记录了他们的姓名以及各自的唯一标识符。这些整数标识符是人物独有的，目前与剧集标识符本身还没有建立关联。

而第三个表作为一种交叉引用表，用来关联剧集和人物。乍一看，这可能是三个表中最晦涩的，因为它只包含数字，全是整数。但我们正是通过 386676 这个标识符，把这部剧和史蒂夫·卡瑞尔关联了起来，其他关联也依此类推。

> **结论**：我在这里所做的是对数据进行规范化处理——除了保留一些必要的冗余整数外，已经消除了所有冗余信息。

为什么值得这么做？至少从我们学 C 语言的经验来看，**整数类型的长度是固定的**——它可能是 32 位，也可能是 64 位，但位数总是固定的。这很好，因为任何固定位数的数据都便于存储在数组中，也便于二分查找，因为每个数据项之间的距离是可预测的。相比之下，像 `Steve Carell` 或 `John Krasinski` 这样的字符串，其名称长度可能各不相同。而这些用于剧集标题和人物信息的 ID，不会因为都是整数就在长度上有所变化。

代价当然也很直观：这个电子表格的实用性大大降低了。如果我想查《办公室》这部剧有哪些演员，首先得弄清楚这部剧对应哪个 ID，然后还得逐个查每个演员 ID 究竟对应谁。

> **提示**：这些"这个 ID 到底对应哪个演员，那个 ID 又对应谁"的问题，正是 SQL 能够大显身手、帮我们解决的地方。

### shows.db：六张表和它们之间的箭头

确实，SQL 是当今网络应用和移动应用大规模存储海量数据最常用的方式之一。他们很可能不会使用简单的 CSV 文件，使用的是 SQLite、MySQL、PostgreSQL、Oracle 或其他商业及开源的 SQL 数据库实现。IMDb 本身大概也是如此。

我预先创建了一个名为 `shows.db` 的文件，里面包含来自 IMDB 的数十万行数据，涵盖电视剧、电视明星及其他相关信息。如果把它的结构以图表形式展示，大致如下：

```text
   people (id, name, year)   ←── n : n ──▶   shows (id, title, year, episodes)
            ▲                          ▲
            │                          │
            └── stars (show_id, person_id)

   shows.id ── 1 : 1 ──▶ ratings (show_id UNIQUE, rating, votes)
   shows.id ── 1 : n ──▶ genres  (show_id, genre)
   shows.id ── 1 : n ──▶ writers (show_id, person_id)
```

读图要注意三件事。一夜之间，我们从只有一个 "favorites" 单表的情况，迅速扩展到了包含 6 个表的真实世界数据集：people、shows、stars、writers、ratings、genres。其次，这些箭头所暗示的正是关系型数据库中"关系"的体现——几张表之间存在关联关系。最后，关系是有形状的：ratings 挂在 shows 的一侧（1:1），genres 挂在 shows 的一侧但可以是多个（1:n），而 stars 处在 people 和 shows 之间（n:n）。

以 people 表为例，稍后我们会看到，在 IMDb 的世界里每个人物都有一个 ID 号、一个姓名以及一个出生年份；每个节目也有唯一的 ID、标题、首播年份以及总集数。

> **提示**：注意这里**并没有**提及节目与人物之间的关系。两个表各自都完整了，但它们之间毫无关联。为了建立这种关联，才出现第三个表 `stars`，它将以某种方式把节目 ID 与人物 ID 联系起来——这就是关键所在，也正是关系型数据库真正强大的地方：它能解决所有冗余问题，并且实际上让你能够更快速地查询数据。

### 先摸清手里的数据：.schema、LIMIT 与 COUNT

不过我们先从简单的内容开始。用 SQLite 3 打开 `shows.db`，输入 `.schema shows` 就能看到创建这个表的命令，现在内容已经变得更有意思了：这个表有四列——每个节目的 ID、每个节目的标题、每个节目的首播年份，以及剧集数量。

> **结论**：理解一个新数据集的最佳方式——无论是别人给你一个 SQL 数据库，还是你把 CSV 文件导入到 SQL 数据库中——就是先查询一些数据。

```sql
SELECT * FROM shows;
```

屏幕上一下子涌出了大量数据，看起来不太方便：有些节目名称显然特别长，导致文本换行，而且数据还在不断滚动显示。Ctrl+C 中断掉它——和终端操作一样，Ctrl+C 是个好帮手。

```sql
SELECT * FROM shows LIMIT 10;
```

这次清爽多了：10 行记录，看起来最早的大概能追溯到 20 世纪 70 年代，这就是 IMDb 数据集的起始部分。

那总共有多少数据呢？

```sql
SELECT COUNT(*) FROM shows;      -- 250087
SELECT COUNT(*) FROM people;     -- 704315
```

这个数据库里总共有 25 万零 87 个节目，人员表里有 70 万 4 千 315 条与该年度数据集关联的明星记录。这才叫真实世界的数据量。

### 五种类型、两个约束、两种键

在往下走之前，先弄清楚 SQLite 支持哪些数据类型。和 C 语言类似，SQL 中也有一份显式类型列表（到了 Python 里，这种显式列表就消失了），但总共只有 5 种：

| 类型 | 含义 |
| --- | --- |
| `INTEGER` | 整数 |
| `NUMERIC` | 数值——更像一个通用类别，可以涵盖时间、日期以及其他实用的现实世界数据 |
| `REAL` | 实数，类似于浮点数 |
| `TEXT` | 文本，这个我们已经见过很多次了 |
| `BLOB` | 二进制大对象（Binary Large OBject），名字很贴切 |

`BLOB` 让你可以在数据库中存储原始的 0 和 1，比如文件。通常来说在数据库中存储文件是不被推荐的，但有些情况下你确实需要存储二进制数据，而不仅仅是纯文本。而在 Oracle、MySQL、PostgreSQL 这些商业和开源数据库中，数据类型甚至比这还多，所以使用它们还能获得更多额外功能。

创建表时，有几个关键词值得注意。

**`NOT NULL`**：你可以明确指定某一列不能为空。比如如果你不希望时间戳字段允许空值，就在建表时写清楚；之后如果我试图插入包含空值的数据（比如不提供时间戳），插入操作就会失败。

> **提示**：这就是它和单纯编写 Python 代码或使用电子表格不同的地方——你实际可以设置内置的防护机制，让你自己和其他人都无法通过一次意外插入虚假或空白数据来破坏你的数据。

**`UNIQUE`**：你还可以进一步要求数据必须唯一，也就是某一列中的每个单元格都必须是独一无二的。这样可以确保你不会意外地插入两个具有相同 ID 的数据，比如重复的哈佛学号或重复的员工号。

但更重要的是，关系型数据库支持**主键**和**外键**这两个核心概念，而真正的神奇之处正是从这里开始。

> **定义**：**主键（primary key）**是表中每一行的唯一标识符，主键列中的值能唯一标识表中的每一行。它通常是节目 ID、人员 ID、哈佛 ID、员工 ID 这类具有唯一性的值，且多为数值型，通常是整数。

> **定义**：**外键（foreign key）**是当相同的 ID 出现在另一张表中、用于交叉引用时的叫法。因为同样的键值存在于另一张表中，所以是"外部"的；但在定义它的原始表中，它仍然是唯一标识行的主键。如果这个键出现在其他表中，那么它就被视为外键。

### 一对一：ratings 表的 UNIQUE 约束

先看评级数据的结构：

```sql
.schema ratings
```

表里确实有一个 show_id 字段，此外还包含 rating（评分）和 votes（总投票数）字段。类型和其他语法细节我们稍后再讨论，先看数据长什么样：

```sql
SELECT * FROM ratings LIMIT 10;
```

普通人乍一看这些数据可能不太直观，因为我们无法直接看出这些 show_id 具体对应哪些影视作品。不过稍后我们会看到，如何通过把这些表关联在一起来重新整合这些数据——**正是通过这些 ID，我们才能实际解答各种查询问题。**

> **结论**：SQL 数据库（更广义地说，关系型数据库）支持一对一关系，即一个表中的某一行可以映射到另一个表中的唯一一行。这与一对多关系形成对比，也是"关系型"数据库中"关系"的又一层含义。

顺便提一句，这两组数据**本可以放在一起**。由于这个例子旨在展示一对一的关系（每个节目都对应一个评分），我们本可以直接把评分和投票数放入节目表中——但我们选择不这样做：IMDb 把评分数据存储为一个独立的 TSV 文件，为了与其数据格式保持一致，我们也就只把下载的那个 TSV 导入一张独立的评分表中。不过这同样也是一种可行的解决方案。

### 嵌套查询：从"评分 ≥ 6.0 的十部剧"说起

现在来做几条实际的查询。如果我想查询评分相关的信息：从 ratings 表中选取所有列，筛选出评分不低于 6.0 的记录，并限制只显示满足条件的前 10 条。

```sql
SELECT * FROM ratings WHERE rating >= 6.0 LIMIT 10;
```

我得到了一个三列的临时表：节目 ID（目前只是个无意义的标识符，因为我不知道它对应什么节目）、评分值，以及参与投票的总人数。

**那么，如何准确获取评分在 6.0 及以上的那十部剧呢？** 其实我们不需要选择所有列。如果只关心排名，可以把这条命令简化为仅查询节目 ID：

```sql
SELECT id
FROM shows
WHERE id IN (SELECT show_id FROM ratings WHERE rating >= 6.0)
LIMIT 10;
```

> **提示**：就像小学算术里一样，我们使用了括号——括号内的部分会先被执行。

所以这个嵌套查询分成两步。括号里先执行：从 ratings 表中获取所有评分在 6.0 及以上（也就是优秀评分）的节目 ID，这会返回给我一列数值。外层再执行：从 shows 表中选取所有列，条件是节目 ID 必须落在这个数值列表中，并限制只显示 10 条记录。

现在我终于看到了有用的数据——评分很高的 10 个节目。如果我只关心节目名称，同样可以做到：这次不使用星号选择所有列，而是只选 title 列。

```sql
SELECT title FROM shows
WHERE id IN (SELECT show_id FROM ratings WHERE rating >= 6.0)
LIMIT 10;
```

我看到了完全相同的结果，但这次精准地只显示了所需的信息。

**那这些节目的评分是多少呢？** 这正是你会去 IMDb、烂番茄这类网站查询的原因——你想查看的是具体的评分数值，而不是仅看标题或笼统的"评分很高"。这就需要另一种技术：把两张表连接起来的能力。

### 连接：把两列 ID 对齐，再拉到一行

不妨先透露一点：把两张表连接起来，正是接下来要探讨的核心技巧。

这里有两张表的示例片段，左边是节目表，右边是评分表（或者说它的一个子集）。如果我想找出某个特定节目的评分，如果能以某种方式把这两张表**对齐——就像指尖对齐一样，让这边的值与那边对应的值一一匹配**——形成某种交叉参照，岂不是方便多了？

```text
   shows                            ratings
   id    | title                    show_id | rating | votes
   62614 | The Office                  62614 |  8.8  |  41205
   62615 | Dawson's Creek             62615 |  9.1  |  83312
```

标出共同值之后，把它们并拢在一起：

```text
   id    | title          | show_id | rating | votes
   62614 | The Office     | 62614   |  8.8   |  41205
   62615 | Dawson's Creek | 62615   |  9.1   |  83312
```

我们注意到两个表之间存在一些共同点：节目 ID 实际上出现了两次。用一些新的术语来说，在一个表里它就是**主键**；而在另一个上下文里——也就是当它出现在另一个表中时——它被称为**外键**。**这正是我们将这两个表关联起来的方式。**

那么，如何查询所有电视节目及其对应评分呢？回到 VS Code 的 SQL 提示符下执行：

```sql
SELECT *
FROM shows JOIN ratings ON shows.id = ratings.show_id
WHERE ratings.rating >= 6.0
LIMIT 10;
```

这句话有点长，但拆开看就是：**从结果中选择所有数据；把节目表的这一列与评分表的那一列匹配；其余筛选条件与之前保持一致**（评分仍需大于等于 6.0，并只取前 10 条）。所以，连接操作本质上就是执行这个匹配过程。

按下回车，我会得到一个完整的表，包含节目表的所有字段和评分表的所有字段，并且这些唯一标识符已经正确对齐了——这里的主键 `id` 的值是 62614，而这里来自评分表的 `show_id` 同样是 62614。

不过如果我原本的目标只是查看评分，现在显示的大部分数据就显得不太相关了。去掉这些冗余信息，最终只保留标题列和评分列：

```sql
SELECT title, rating
FROM shows JOIN ratings ON shows.id = ratings.show_id
WHERE ratings.rating >= 6.0
LIMIT 10;
```

一列是这些节目的标题，另一列是节目的评分——**尽管这两组数据原本完全独立地存储在两个不同的表中**。

顺便把命名约定也说了。按照惯例，任何以 `id` 命名的字段都意味着它是主键；任何以下划线加 `id`（`show_id`）命名的字段都表示它是外键。如果表名是复数形式（`shows`），那么外键就使用单数形式加 `_id`。这种命名惯例其实相当普遍，不同的公司、不同的社群会有各自的实践规范；不过在我们所有的表格中，我们一直遵循着下划线加全小写的命名惯例，保持了一致性。

有同学问：这些 ID 是如何正确生成并相互关联的呢？老实说，在我们这个案例里，我也搞不清楚——IMDb 的工作人员以某种方式生成了这些唯一标识符，我们只是把它们整合进数据集。他们实际采用的做法，很可能也是你以后处理数据集时（后续的习题集中）会用到的方法：**简单地分配一个从 1 开始的任意整数，然后依次是 2、3、4、5，让它自动递增，并让数据库确保永远不会出现重复值。**

还有同学注意到命令里那个尖括号：它只是 SQLite 3 特有的**续行提示符**，表示我故意提前按了回车键，想把所有内容挪到下一行，这样就不会因为换行而显得杂乱。**这不是 SQL 语法。**

**最后一个问题问得也很好："当结果被限制为 10 条时，它显示的是最早的那些记录吗？"** 答案是：你只会直接获得表中的前 10 行数据。如果你没有使用 `ORDER BY` 关键字，结果通常会按照数据在表中的原始顺序返回，所以我们看到的只是符合"评分大于等于 6"这个条件的任意前 10 条记录——我们并没有按评分排序，所以得到的不一定就是评分最高的那 10 部剧集。我取评分大于 6 的前 10 部，目的很简单：让结果能完整显示在屏幕上，而不是一次展示成千上万条数据。

至于 SQL 究竟是如何完成所有这些搜索的、它的时间复杂度是多少——这个问题问得非常好，我们在今天课程的最后会讨论它。在最简单的实现方式中，SQL 本质上就是从表头到表尾进行**线性搜索**；而作为程序员，我们将有能力优化这些查询，使数据库能够实现类似**二分查找**的高效搜索。

### 一对多：genres 给出的三行答案

回到更宏观的视角：我们不仅要关注节目表和评分表，还要聚焦于"类型"表。它之所以特别，是因为它不再是一对一的关系了。一部剧集可能既属于剧情片又是音乐剧，或者既是喜剧又是其他类型，甚至同时属于多个流派的任意组合。于是我们用一个独立的 genres 表来实现这种关系——虽然这个设计并非完美无缺，这里仍存在一些我们尚未消除的冗余，但它确实表明我们可以支持与每一部剧集相关联的多个这样的值。

```sql
.schema genres
```

genres 表有两列：`show_id`（INTEGER，不允许为空）和 `genre`（TEXT，同样不允许为空）。而且这终于让我们第一次真正用上了之前介绍过的专业术语——建表时指定了以下约束：`show_id` 列被设置为外键，并引用 `shows` 表的 `id` 列。

> **提示**：必须承认，创建表的语法确实有点拗口——就连我也经常需要查阅资料，才能记住所有语法的顺序。

那这个外键约束从哪里来的呢？回到 `shows` 表的 schema：

```sql
.schema shows
```

`id` 是整数类型且为主键（怎么知道的？因为括号里的最后一项明确指出，这张表中的 ID 列是主键）；`title` 是文本类型且不能为空；`year` 是数值类型（就是我提过的那种统称，涵盖不完全是整数或纯浮点数的其他数值类型）；`episodes` 是整数类型。后两列都可能为空值——可能是因为 IMDb 对一些年代较久远的剧集没有收录相关数据。

再把 genres 和 ratings 对比一下。ratings 在设计思路上与 genres 非常相似：都有一个 ID 列用来关联剧集表，然后是各自的另一列。但 ratings 多了一个额外的约束条件：我特意指定了 `ratings` 表中的 `show_id` 必须具有唯一性。

> **结论**：因为我们确实希望建立一对一的关系，同一个 `show_id` 不能出现多次，否则就无法实现一对一关联。而对 genres 表，我们允许出现重复值，所以那里没有指定唯一性约束。

现在直接看数据：

```sql
SELECT * FROM genres LIMIT 10;
```

看起来包含了一些喜剧、漫威系列、家庭动作、科幻片等等。我们直接查询某个具体节目：

```sql
SELECT * FROM shows WHERE id = 63881;
```

这个节目是 1970 年播出的《猫鼬》，总共 26 集，而 63881 确实是它的唯一标识符。

**但《猫鼬》到底属于哪些类型呢？** 它不一定是简单的一对一——它不只是冒险类，还同时属于喜剧和家庭类。如果你回头看刚才的查询结果，63881 对应的类型确实是冒险、喜剧和家庭，之后 ID 才变成其他节目的。那我们该如何筛选出这三个答案？

```sql
SELECT genre FROM genres WHERE show_id = 63881;
```

这就是问题的答案了，但这显然不是最佳的实现方式：因为你得先手动查找你关注的剧集 ID，再复制粘贴它，或者把它手动输入到查询语句里。

> **结论**：虽然实际的 IMDB 网站需要用这些唯一标识符来存储所有信息，但一般来说，**人类既不需要知道这些标识符具体是什么，也没必要去关心它们**。标识符的作用本质上就是为了实现这种交叉引用。

我们当然可以做到这一点，虽然查询语句会稍微冗长一些：

```sql
SELECT genre FROM genres
WHERE show_id = (SELECT id FROM shows WHERE title = '猫鼬');
```

返回的结果完全一样，而且我根本不需要知道或者操心那些数字具体是多少。

还有一个完全不同的方法：把这两张表连接起来。这回显然可以像处理评分那样把两列对齐，不过区别在于，**由于现在是一对多的关系，所以不能简单地直接连接这些行**——我需要在这里、这里和这里都接上，数据库可以帮我完成这个操作，尽管这会在冗余方面带来一些代价。

```text
   shows                    genres
   id    | title             show_id | genre
   63881 | The Mongoose        63881 | Adventure
                              63881 | Comedy
                              63881 | Family
```

但不可能返回一个直接缺失数据的临时表——在一个网格中，每一处的行数和列数都必须保持一致。所以当我把这两个表连接起来、且它们之间存在一对多关系时，数据库会复制必要的数据，让每一行看起来都保持一致：

```text
   id    | title        | genre
   63881 | The Mongoose | Adventure
   63881 | The Mongoose | Comedy
   63881 | The Mongoose | Family
```

缺点是这确实可能会占用一些额外的空间，除非数据库足够智能，能够在底层通过指针等方式避免存储层面的数据冗余。但就我最终的需求而言，这其实相当方便——如果像我们在 Python 中那样遍历这些行，能够把所需的所有数据都包含在每一行中会非常实用，尽管这显然"看起来"有冗余。**但数据本身并没有在存储层面产生冗余，这只是临时呈现给我的一种冗余形式。**

在代码中就是：

```sql
SELECT title, genre
FROM shows JOIN genres ON shows.id = genres.show_id
WHERE shows.id = 63881;

SELECT genre
FROM shows JOIN genres ON shows.id = genres.show_id
WHERE shows.id = 63881;
```

第一条返回《猫鼬》的 3 个流派信息，每次迭代都同时拿到标题和流派；第二条则只返回所需的数据。

简单来说，我们刚才看到了什么？**第一，你可以把两个表连接起来，再把临时表精简至仅包含你关心的数据。第二，如果你愿意，也可以采用完全不同的嵌套查询方式，依然能得到相同的结果。**

我认为，当你初次学习 SQL 时，通常更简单的方法是分多个步骤、用嵌套查询，因为你可以从内到外逐步推进，像婴儿学步一样循序渐进地解决问题。拿"给我某部特定电视剧的所有类型"这个例子来说：首先我需要了解情况——我知道数据在数据库中的具体结构，所以需要先获取剧集的唯一标识符，这部分相当直接，因此就有了内层查询；一旦获得这个标识符，就可以将其用括号括起来，然后在外部进行查询你真正想问的问题：哪些类型与该剧集 ID 匹配。简而言之，嵌套查询可能更容易上手，尤其是在初次学习时；但连接查询同样非常强大，它们能达到完全相同的效果。有时你需要使用连接查询，有时嵌套查询就足够了。

### 多对多：stars 与 2005 年的《办公室》

现在让我们聚焦最核心的部分：把节目与人物关联起来，也就是谁出演了哪些节目。回想我最初在 Google 表格中模拟的场景——我希望能够以正确的方式，把《办公室》与史蒂夫·卡瑞尔、约翰·卡拉辛斯基、詹娜·费舍尔等演员关联起来。

people 表包含一个 ID 主键，以及每个人的姓名和已知的出生年份；shows 表同样包含主键、节目名称、年份以及集数信息。

而 stars 表在涉及电视剧演员时，引入了第三种也是最后一种关系类型：**多对多**。因为很显然，一个人可以参演多部剧集，而一部剧集也可以有多位演员参演。简单回顾一下：ratings 表是一对一关系，genres 表是一对多关系，而现在的 stars 表将是多对多关系。

这些查询语句会稍微冗长一些，但它们依然遵循着循序渐进的原则。假设我想查询已知的关于《办公室》的所有信息：

```sql
SELECT * FROM shows WHERE title = 'The Office';
```

这有点意思——结果包含很多部名为《办公室》的剧，其中有英国原版，还有其他几个版本。但我们现在讨论的、有这些明星参演的版本，应该是 2005 年开播、共 188 集的那一部，也就是美国版。

更精确一些：

```sql
SELECT * FROM shows WHERE title = 'The Office' AND year = 2005;
SELECT id FROM shows WHERE title = 'The Office' AND year = 2005;   -- 386676
```

这个版本的《办公室》的 ID 就在我眼前，386676。现在我可以偷懒直接复制粘贴或记住它，但我们将以更动态的方式执行：先查出有哪些演员参演了那部剧。

```sql
SELECT person_id FROM stars
WHERE show_id = (SELECT id FROM shows
                 WHERE title = 'The Office' AND year = 2005);
```

这是我的第二个小步骤：**最内层的括号动态地找出我所关注的《The Office》这个版本的唯一 ID**；外层查询根据 stars 表找出与该剧集关联的所有人员 ID。stars 表只有两列——`show_id` 和 `person_id`，这就是仅通过这两个整数字段实现关联的方式。

现在我得到了一列包含该版本所有演员人员 ID 的结果。那么，如果我想获取他们的姓名而非随机的人员 ID 呢？继续从 people 表中选取 `name`，条件是人员 ID 属于上面那个集合：

```sql
SELECT name FROM people
WHERE person_id IN (
    SELECT person_id FROM stars
    WHERE show_id = (SELECT id FROM shows
                     WHERE title = 'The Office' AND year = 2005)
);
```

> **提示**：当处理单个值时，用等号 `=` 匹配就够了；只有当需要匹配一组值时，才需要 `IN` 和外层那对括号。

## 把 SQL 写进程序：连表、索引、注入与竞态
> 对应块：BLK23 | 覆盖分集：P08下 | 块标题（分集名）：《多表连接与 sqlite3 编程》

我们先换个角度问一个问题：**除了《办公室》之外，Steve Carell 还出演过哪些节目？**

别急着敲代码，先记住这个问题的形状。它跟刚才那个"《办公室》里都有谁"正好互为镜像：前一个是从剧集找人，后一个是从人找剧集。而当你真的打开 IMDb.com，在搜索框里敲下 "Steve Carell" 的时候，网页上跳出来的那一长串节目，本质上很可能就是一句 SQL 查询的结果。

这就是这一讲真正的主题。到这里为止，我们写的都是"在终端里手敲一句 SQL、看一眼结果"的玩具程序；而从现在开始，我们要学的是**怎么把 SQL 写进真正的程序里**——让它接受用户输入、返回真实数据、被成千上万人同时使用。顺带解决的还有两件事：怎么让查询跑得快，以及怎么在跑得快的同时不被用户一句话就黑掉。

### 三层嵌套：从剧集一路挖到人名

先接上刚才那一段。当我们要匹配的是**一整列数据**而不是单个值时，SQL 里的介词就不再是 `=`，而是 `IN`——"当人员 ID 位于以下数据集中时"。

把《办公室》的例子展开成完整的一坨，是这样的：

```sql
SELECT name
FROM people
WHERE ID IN (
        SELECT person_id                     -- 中层：该节目牵涉哪些人
        FROM stars
        WHERE show_id IN (
                SELECT ID                    -- 内层：《办公室》2005 的节目 ID
                FROM shows
                WHERE title = 'The Office'
                  AND year = 2005
        )
);
```

我们从外往内读一遍这个结构，就知道我刚才说的"从外到内三个小步骤"分别干了什么：

- **最内层**只干一件笨事——去 `shows` 表里问一句：哪一部剧的标题是 "The Office"、年份是 2005？它交回来的是**一个**节目 ID；
- **中层**拿着这个节目 ID 去 `stars` 表，把所有在这个节目里露过脸的人的 ID 全捞出来，**很多个**；
- **最外层**才是点睛之笔：它拿着中层那一大摞 ID，去 `people` 表把对应的**姓名**全部取回来。

注意最外层是**必须**的：外层负责画人名，但它自己并不知道 ID 是多少，ID 得从中层那串列表里来。有同学问"最外层怎么知道要查谁"，答案就是——它知道的是"那一整摞"，不是"某一个"。

那 Steve Carell 呢？先从 `people` 表里查他的全部信息：

```sql
SELECT * FROM people WHERE name = 'Steve Carell';
```

好，IMDB 里只有一位 1962 年出生的 Steve Carell，没查错人。但我真正关心的只是他的 ID，所以我把查询范围收窄：

```sql
SELECT ID FROM people WHERE name = 'Steve Carell';
```

136797。这个数字我可以记住，也可以复制粘贴——**但通常不建议这么做**，硬编码进去的 ID 一旦数据变了就悄悄错掉。正确做法是把它原封不动地塞回嵌套查询里，于是整条语句长这样：

```sql
SELECT title
FROM shows
WHERE show_id IN (
        SELECT show_id                     -- 他参演过的所有节目
        FROM stars
        WHERE person_id IN (
                SELECT ID                   -- 他的 ID
                FROM people
                WHERE name = 'Steve Carell'
        )
);
```

跑完一屏全是节目名。他参演过很多电视节目——但刚才那列孤零零的整数你根本看不出是什么，加了这一层"点睛之笔"才变成人能读的信息。这就是为什么每一层都得写：整数是机器的，标题和姓名才是人的。

信息量可能有点大，但我要说的是：**嵌套查询在概念上是最简单直观的写法**，而且实际应用里我也建议你优先考虑它。不过既然有同学想看别的路数，那就走一遍 JOIN。

### JOIN：不用嵌套，也能把三张表摆到一条线上

如果我已经知道牵涉的是 `shows`、`stars`、`people` 三张表，我其实可以**一气呵成**地查完，中间不套任何子查询。三张表的对齐关系其实非常简单，就是"主键对上了外键，外键又对上了主键"：

```text
shows.ID  ────────►  stars.show_id      节目表的主键 = 明星表的外键
stars.person_id ─►  people.ID          明星表的外键 = 人员表的主键
people.name ──────────────────────────►  'Steve Carell'   只留下这一位
```

读图就是一句话：**先用第一条等式把 `shows` 挂到 `stars` 上，再用第二条等式把 `people` 挂上来，最后用 `people.name = 'Steve Carell'` 把范围收窄到他一个人。** 概念上你已经知道有三张表，想拼起来只需要理清怎么对齐它们。

#### 显式 JOIN：把主键对上外键

写法上分两种。先看显式的：

```sql
SELECT shows.title
FROM shows
JOIN stars ON shows.id = stars.show_id
JOIN people ON stars.person_id = people.id
WHERE people.name = 'Steve Carell';
```

`JOIN ... ON ...` 就是把"两张表怎么接"明明白白写出来：节目表的主键等于明星表的外键，明星表的外键等于人员表的主键。查出来的结果和嵌套查询一样——只是会多出一些重复行。

#### 隐式 JOIN：逗号加谓词

同一条逻辑也可以用第三种、也是最"省事"的方式表达：在 `SELECT` 里用逗号把三个表名列出来，然后全靠 `WHERE` 里的谓词告诉数据库该怎么对齐。

```sql
SELECT title
FROM shows, stars, people
WHERE shows.id = stars.show_id
  AND stars.person_id = people.id
  AND people.name = 'Steve Carell';
```

是的，这跟上一段是**完全相同**的逻辑，只是没写 `JOIN` 关键字而已。结果同样带重复行。

刚才同学问的两个问题很值得记下来。

一个问的是：那我怎么知道该按什么方式 JOIN？答案是——**你必须了解数据库的内部结构**。不管这个库是你自己建的，还是跟设计数据库模式的同事一起做的，这种"需要知道表之间怎么连"的情况在实际工作中非常常见。另一个同学提到的 ORM（对象关系映射）也是这条路的延伸：你当然可以用那些库，让它替你自动处理所有连接。所以这些 JOIN 写起来并不难；但在 CS50，我们是从**自底向上**的角度让大家看懂它到底怎么工作——而正因为有 ORM 的存在，这套操作其实也很容易被自动化。

还有一个问题：SQL 里的缩进重要吗？技术上不重要，但就像我们讨论过的所有语言一样，良好的缩进对开发者非常有益，教学场景里尤其如此——我们讨论过的语言里，Python 对缩进要求最严格，代码结构完全靠缩进定义。SQL 里我只是为了视觉上更清楚。别把缩进当成语法，它是给人和眼睛看的。

另外要提醒一句：刚才那两个 JOIN 查询确实**比嵌套查询慢一点**，而且结果里带重复行——嵌套查询里可没有这些重复。慢的问题我们下一步解决；至于写法选择，我还是那句话：**处理第 7 题这类问题的时候，尽量优先考虑嵌套查询，概念上更简单。**

### 慢一点没关系，能不能快点：给查询建索引

回到 VS Code，我们实际测一下"查所有叫《办公室》的剧集"要多久。我把 sqlite3 的一个类 SQL 命令 `.timer` 打开，这样每条命令的耗时都会显示出来。

```text
sqlite> SELECT title FROM shows WHERE title = 'The Office';
The Office
Run Time: real 0.042 user 0.000000 sys 0.000000
```

0.042 秒。快得离谱，连一秒都不到，所以"没什么大不了的"——但我敢打赌，连这个查询我们也能再优化。

> **结论**：关系型数据库相对电子表格的又一项优势，就是**你可以提前告诉数据库如何针对特定查询做优化**，而电子表格没有这个能力。

既然已经这么快了，优化还有什么意义？想象一下这个查询被频繁执行的场景：有人访问 IMDb 网站搜索《办公室》或别的剧，这是**最常见**的用法。用户搜剧、搜电影、搜演员，我们当然希望响应时间越短越好。原因有两个：一是用户体验，答案来得更快用户更满意；二是**省钱**——你买了一台 1000 美元的服务器，内存、CPU、处理器速度都是固定的，它每秒钟能处理的搜索量是有上限的。响应时间砍掉一半，意味着同样硬件能同时服务的用户可能从 1000 人变成 2000 人甚至 5000 人。

那怎么优化？`CREATE` 这个关键字还有另一个用途：**创建索引**。

```sql
CREATE INDEX title_index ON shows(title);
```

索引可以随便起名，`title_index` 本身没有任何含义，重要的只有后面两件事：在**哪张表**上建、在**哪一列**上建。这句话翻译过来就是——"请加快对 `shows` 表中 `title` 列的搜索速度"，毕竟我刚才搜的就是这个字段。

执行这一次花了大概半秒钟，但这是一个**只需要建一次**的标签。当然，如果之后你执行大量更新和删除操作，维护这个索引本身是要花时间的；只是眼下，创建索引就是一次性成本。

现在把历史记录往上翻，**执行一模一样的查询**：

```text
sqlite> SELECT title FROM shows WHERE title = 'The Office';
The Office
Run Time: real 0.001 user 0.000000 sys 0.000000
```

0.001 秒。**42 倍。** 同一个数据库，同一条查询，能扛的用户量直接乘以 42。

那索引到底是什么？这就绕回我们第 5 周左右讲过的东西了——数据库里的索引通常用一种叫 **B 树（B-tree）** 的结构来实现。

> **易错点**：B 树**不是**二叉树。它只是理念上跟二叉树相似：树的高度通常比较浅，节点可以有很多个子节点，不一定只有两个。而且子节点越多，所有叶节点就越能被"向上提拉"，整棵树的高度就越低——对查找来说这至关重要。

```text
                 ┌──────────┐
                 │   root   │
                 └────┬─────┘
        ┌───────────┼───────────┐
   ┌────▼────┐ ┌────▼────┐ ┌────▼────┐
   │ 内部节点 │ │ 内部节点 │ │ 内部节点 │   ← 每个节点可有多个子节点
   └────┬────┘ └────┬────┘ └────┬────┘
   ┌───┬┴──┐    ┌─┬┴┬──┐    ┌───┴──┐
  ┌──▼─┐┌─▼┐  ┌─▼┐┌▼┐┌─▼┐  ┌─▼──┐┌─▼──┐
  │ 标题 ││标题│ │标题││标│ │标题 ││标题 │   ← 叶节点：排好序的标题
  └────┘└───┘  └──┘└──┘└──┘  └────┘└────┘

  没有索引：从顶上一路逐行扫下去   →  O(n)   全表扫描
  有了索引：沿树一路二分下去     →  O(log n)
```

读完这张图就明白索引的意义了：以前搜 "The Office"，数据库只能**全表扫描**——从顶部开始一行一行往下比，那种低效的线性搜索。有了 `title_index`，数据库已经把所有标题组织成一棵树摆好了，可以以对数时间复杂度（$\log_2 n$ 或者别的底数，反正很快）直接定位到目标。这就是那 42 倍从哪来的。

### 从十七行 Python 到一行 SQL

现在进入这一讲的关键转折：我们不再只是在不同编程语言之间做选择，而是要**综合使用多种语言来协同解决问题**。接下来几周转向 Web 开发时，你们会同时用到 Python、SQL、JavaScript，还有 HTML 和 CSS——**五种语言**。为什么？因为不同的语言擅长不同的事，这就是现实世界软件开发的真实生态环境。

为了搭这座桥，CS50 提供了 Python 版的库，里面有 `get_string`（跟内置的 `input` 差不多，实用价值有限）、`get_int`、`get_float`，还有一个专门模块，让你能在 Python 代码里舒服地使用 SQL。

先回到刚才中断的地方。我们之前的 `favorites.py` 只是用一个字典统计大家选了 Python、C 还是 Scratch，结果是 190、58、24。

问题来了：这个结果**顺序不对**。按字母排的话 C 应该在最前面；按数字排的话 190 也该在 C 前面。我当时没深究，因为用 Python 处理这个问题很快就变得很繁琐。我们来看看有多繁琐。

第一步，把遍历改成 `sorted(counts)`：

```python
for favorite in sorted(counts):
    print(f"{favorite}: {counts[favorite]}")
```

这个还行，`sorted` 传一个字典进去，会按**键**（字母）排序。

第二步，如果我想按**值**排序，也就是按 190、58、24 来排呢？还是用 `sorted`，但要告诉它排序键是谁——就是计数字典的 `get` 方法：

```python
for favorite in sorted(counts, key=counts.get):
    print(f"{favorite}: {counts[favorite]}")
```

跑出来是按值排了，但顺序**反了**：scratch(24)、58、190。要反转，就再加一个命名参数：

```python
for favorite in sorted(counts, key=counts.get, reverse=True):
    print(f"{favorite}: {counts[favorite]}")
```

这才对了。

> **结论**：用这么多代码去解决一个相对简单的问题，实在太繁琐了。**这正是我们今天转向 SQL 这类声明式语言的原因**——直接告诉它我要数据里真正需要的部分就行。

于是回到 SQLite 里的那个 `favorites` 表。同样一件事：

```sql
SELECT language, COUNT(*) AS n
FROM favorites
GROUP BY language
ORDER BY n DESC;
```

一行。不是十七行（还不算空行）。

这里顺手记一个真实的教训。我刚才顺手敲了一句 `SELECT COUNT(*) FROM favorites GROUP BY favorite;`，结果它抱怨字段名不对——我改成了 `SELECT language, COUNT(*) FROM favorites GROUP BY favorite;`，然后想删表重建，敲了 DROP，结果发现**表没了**。看吧：**这就是为什么不该随便用 `DROP TABLE` 之类的命令**。所以我不打算再演示一遍那个重建过程，但请回想一下，休息前我们最后查这批数据用的就是 `GROUP BY` 按语言分组，拿到对应的计数。

要接着往 Python 里走，得先把数据库恢复回来：把 `favorites.db` 这个文件删掉，重新 `sqlite3 favorites.db` 建一个新库，把模式切成 CSV，用 `.import favorites.csv favorites` 把文件导进一张叫 `favorites` 的表，然后 `.quit`。`ls` 一看，`favorites.db` 回来了。重新打开跑一句 `SELECT * FROM favorites;` 验证——数据都在，只是少了我们之前手动添加和删除的那几条。语法上记住一个点：聚合出来的计数列想拿来排序，最好**起个别名**（比如 `AS n`），然后直接 `ORDER BY n DESC`，比再写一遍 `COUNT(*)` 清楚得多。

### 用 Python 驱动 SQL

好了，两个世界可以合起来了。回到 `favorites` 表，我们写一个"优化版"——不再用字典、不用 `for` 循环、不用 `try-except`。

```python
from cs50 import SQL

db = SQL("sqlite:///favorites.db")

rows = db.execute("""
    SELECT language, COUNT(*) AS n
    FROM favorites
    GROUP BY language
    ORDER BY n DESC
""")

for row in rows:
    print(row["language"], row["n"])
```

几件事值得拆开看。

`SQL("sqlite:///favorites.db")` 这个写法有点特别。路径写成 `sqlite:///favorites.db`，这种语法叫 **URI（统一资源标识符）**，意思是"请用 SQLite 协议打开这个文件"——正是我刚才在终端里手动打开的那个文件。按惯例我们把返回的对象命名为 `db`（叫别的也行）。

CS50 库里真正实用的就是 `execute()`：我可以直接把一句 SQL 字符串塞进去——`SELECT language, COUNT(*)`，按语言分组，按计数降序，**一行搞定**。这就是我们所谓的"一种语言嵌套在另一种语言中"的场景：注意 SQL 是作为**字符串参数**传进去的，所以最后要把引号和括号都闭上。

那 `execute()` 到底返回什么？按设计，它返回一个**包含多行数据的列表**，而**每一行本身是一个字典**（由键值对组成）。所以 `for row in rows` 其实就是在遍历一个列表——这个操作过去几周我们已经练过无数次了。循环体里那两个临时变量 `language` 和 `N`，只是为了让你看清这一点才写的：**因为每一行是字典，我可以用字符串来索引它**，索引的 `"language"` 和 `"N"` 正好就是我在上面 SELECT 出来的列名。

严格来说，那两个变量根本不需要，我完全可以直接写 `row["language"]` 和 `row["N"]`。改成这样再跑一遍 `favorites.py`，结果完全一致，还是 190、58、24。

> **提示**：CS50 的这个库虽然有点"拐杖"的味道，但确实比其他方案好上手——市面上功能相同的库往往复杂得多。我们教学时间有限，现阶段还会继续用这个拐杖。

掌握了这个，就可以做**交互式**程序了。

```python
favorite = input("What's your favorite TV show? ")

rows = db.execute("""
    SELECT COUNT(*) AS n
    FROM favorites
    WHERE favorite = ?
""", favorite)

print(rows[0]["n"])
```

几处细节：这里用 Python 的 `input`（等价地，CS50 的 `get_string` 也行）问用户最喜欢的节目，显示并保存到同一个变量。注意我们查的是 `COUNT(*)`——**有多少人选了这个项目**，不是查这个节目本身。因为理想情况下我们只要一个结果，所以下面不需要任何迭代，直接取"第一行"即可：`rows` 是列表，`rows[0]` 就是这个列表里的第一个（也是唯一一个）元素，所以打印 `rows[0]["n"]`。

跑一下 `python favorites.py`，我输入 `hello world` 回车——和课前一模一样，**42 位同学**喜欢这个。

### 用户输入一旦拼进去，就成了别人的命令

可是各位，刚才那段代码**绝对不是、绝对不是、绝对不是**在 Python 里写 SQL 的正确方式。它这次没出问题，但潜在风险是什么？

有同学已经说了：**用户输入**。更简单地说——如果我把用户输入直接拼进那句 SQL 里，会出什么问题？

试着换一个输入。假设用户输入的是 `hello, it's me`——**这里面有一个单引号**。如果直接插进 `WHERE favorite = '这里'`，这个引号会跟 SQL 语句原本的引号配对错乱，结果完全无法预料。最理想的情况是程序直接报错——这对用户一点也不友好，因为他什么也没做错，程序却失去了实用性。

最糟糕的情况呢？如果开发者完全无视这个问题，用户就能**执行极其恶意的操作**——比如输入 `delete`、`drop`、`update` 这些我们前面见过的破坏性关键字；或者输入一个分号再接一条删除语句；或者分号加上一条 `DROP TABLE`。

这就叫 **SQL 注入攻击**：攻击者，或者只是不小心的用户，能以某种方式把恶意代码注入到你的数据库里。在所有数据库相关的操作中，盲目信任用户输入是最严重的威胁之一。

### 一个单引号如何让 GitHub 放你进去

来看真实场景。这里有个登录界面，就拿 GitHub.com 来说吧——我相信他们底层确实用了 SQL 和其他多种语言，虽然不一定用在这个场景上。为了讨论方便，**假设**他们用的是 SQLite（实际上并没有，因为 SQLite 不适合处理那么庞大的数据集）。

登录时你会被要求输入用户名或邮箱，还有密码。那么如果我稍微懂一点 SQL，出于恶意在用户名栏输入：

```text
mailin@harvard.edu' 之后跟着 -- 
```

那个单引号在这里。注意，在这个场景里我扮演的是攻击者：我可以通过**提前闭合他们代码里的引号**来扰乱他们的程序逻辑。而 `--` 在 SQL 里是**注释符号**——就像 Python 里的 `#`，或者 C 语言里的 `//` 一样，**右边的所有内容都被忽略**。

这就是 GitHub 底层可能正在跑的东西：

```python
db.execute(f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'")
```

`f` 表示这是一个格式化字符串。看看问题出在哪。请注意那两个包裹用户名的单引号，密码那里的单引号也是同样的作用。

那么当我输入 `mailin@harvard.edu'` 的时候会发生什么？让我们实际演示：

```text
f"SELECT * FROM users WHERE username = 'mailin@harvard.edu'  -- ' AND password = 'xxx'"
                                                        ↑ 语句在这里提前结束
                                                        ↑ 剩下的全部变成注释，编辑器里直接灰掉
```

看，编辑器把后面所有内容都**变灰了**——因为它们已经被注释掉了。结果就是：GitHub 最终执行的是

```sql
SELECT * FROM users WHERE username = 'mailin@harvard.edu';
```

**完全不管他的密码是什么。** 假设下面有条件逻辑写着"如果返回了行，说明这是个注册用户，那就放他登录"——我们不知道真实代码长什么样，这只是推测——那么你刚刚让**互联网上的任何人**只要在自己输入后面加一个单引号，就能以你或任何其他人的身份登录。

而这还只是我们**最不担心**的那种情况。如果再往前一步，把 `'` 换成 `'; DELETE FROM users; --`，或者 `'; DROP TABLE users; --`，我们就能对他们的数据库造成毁灭性打击。

> **结论**：这类事情**至今仍在发生，就在今年也发生过**。你可以上网搜一下，找到一些公司因为没有适当净化用户输入而引发问题的案例。而且这**不只是实习生会犯的错误**——这相当于让网上的陌生人恶意访问甚至破坏他们的数据。

### 答案：用库，用问号

那这类问题的解法是什么？

首先，在 Python 里**不要用格式化字符串直接插入用户输入**。但更重要的是一条铁律：**永远不要相信用户的输入**，不管他是无意中出错还是蓄意破坏。

而解法就是——**使用库**。几乎总是要依赖库来处理。这不是你该自己重新造轮子的事情。

如果你用的是 CS50 这样的库，而不是光用 F 字符串，你会用**问号占位符**：

```python
db.execute("SELECT * FROM users WHERE username = ? AND password = ?", username, password)
```

接下来发生的事很有意思：当用户输入 `malin@harvard.edu'` 时，**这完全没问题**——库允许他们在输入里包含单引号这样奇怪甚至令人不安的字符。库会负责**转义**这些内容，把危险字符转换掉，比如把单个引号变成两个引号（我们今天早些时候已经见过转义是怎么做的）。最终得到的结果是安全的。

```text
用户真正想输入的：   malin@harvard.edu'
转义之后进到 SQL：  malin@harvard.edu''
查询实际找的是：    名字真的叫 "malin@harvard.edu'" 的人  →  查无此人，返回 0 行
```

这其实也不是一个真实的邮箱地址、不是真实的用户名，所以它只会返回 `false`，不会有任何行返回——**正确**。

> **提示**：这不是 CS50 特有的做法，而是**行业惯例**。问号占位符意味着"不管这个变量的值是什么，都会被安全地填进这个位置，而且系统会自动帮你补上单引号、自动转义任何危险字符"。

在 `favorites` 那个程序里就是这么改的：不要用 f-string，把 `favorite` 的值改成占位符，然后把它作为参数传给 `execute()`——一个或多个参数，会被替换到问号的位置。

现实世界里到处是这个做法留下的痕迹。比如网站会告诉你"密码太简单，不行"——这我们凭直觉都知道，密码该够长、难猜，最好有字母数字标点。但有时候网站会**非常愚蠢地禁止你使用某些标点符号**，这简直让人抓狂：从技术角度说，根本没有理由把清洗输入的责任推给用户。但这些网站很可能已经从教训里学到，有些字符（比如分号、单引号）在 SQL 里可能有风险，于是干脆禁掉。**其实这个问题有更好的解法**——直接用那些由经验更丰富、技术更精湛的前辈们编写并验证过的库。那些库是开源的，多年来经过无数人的审查和测试，你完全不必担心。

至于问"这些所谓的 SQL 注入攻击到底是什么"的同学——是的，我们今天讨论的正是这个核心问题。同时你也无意中**泄露了自己的技术栈**：如果你告诉别人哪些字符不能用，聪明的攻击者会想"既然他们不让我用这个符号，那他们很可能在用这种语言或这项技术"。**向外界透露超出必要范围的信息，从来不会有好结果。**

### 抢牛奶，也抢点赞

在回到别的内容之前，还有一个 SQL 和关系型数据库自身的挑战需要了解：**竞态条件（race condition）**。

如果你只是在自己电脑上写个小程序，这不算什么大问题。但在真实世界、在云端运行的数据库里就不一样了。像 Meta、谷歌、微软这样的大公司，甚至 CS50 自己的一部分应用，都会用集中式 SQL 数据库。当多台服务器同时跟数据库交互、大量用户通过网页服务器发起请求时（比如同时提交作业、同时运行 Check50），如果多人同时尝试做同一件事，就会撞上竞态条件。

#### 一冰箱塞不下两罐牛奶

什么是竞态条件？我当年上数据库和操作系统课时，老师是这么讲的。

想象你的宿舍。你和室友共用一个小冰箱，你们俩都特别喜欢喝牛奶。某天下课你回到宿舍，打开冰箱发现牛奶没了，于是决定去街对面的 CVS 买点回来。与此同时室友也回来了，他打开冰箱一看："牛奶喝完了，我也去买点吧。" 假设你们去的是不同的商店，所以路上没碰上，问题看起来自己就解决了。

然后你们各自买回了牛奶。先后到家——一个人把牛奶放进冰箱，另一个人到一看："糟了，牛奶已经买回来了。"这罐牛奶冰箱里放不下了；或者现在牛奶太多，我们其实没那么爱喝，牛奶会变质。这是个很糟糕的结果。

这故事也太蠢了吧。那教训到底是什么？

我们怎么会落到买多牛奶的境地？因为**我们不知道对方在做什么**——说得专业一点，我们**检查了一个正在被其他人更新的变量状态**。这问题在计算机领域由来已久，甚至能追溯到 Scratch：单个角色可以同时运行多个脚本，因为 Scratch 本质上就是多线程的，一个角色能一边跑这个动作一边跑那个动作。这里也一样，宿舍是多线程的，两个独立个体同时去商店、并行解决同一个问题。如果一方不知道另一方已经在处理，就可能做出不明智的决定。

那现实世界里的正确做法是什么？第一位室友检查完冰箱、意识到"牛奶没了"之后，**应该给另一位室友打个电话**。或者门上留张便条，或者干脆把冰箱锁上。在数据库领域这有个专业术语：**锁（lock）**——当你要更新数据库里的某个值时，先把它锁住，让其他人看不到这条数据，从而避免做出错误决定。

#### 几十万人同时按下的那个心形图标

现在来看这个问题**真的**在哪儿发生。有一类社交媒体帖子到现在还很流行——截至今天，那还是 Instagram 上最受欢迎的帖子之一。想象它刚发出时：点赞数从几百、几千，一路飙升到几十万。可能所有人都在**同一时间**点击了那个心形图标。

背后是 Meta（我们假设他们只有一个数据库——当然这并不是事实，但即使有多个数据库，风险依然存在）。所有这些不同的网络服务器都在跟同一个数据库通信，假设它们跑的是 Python 代码，并且——嘿——还有 CS50 库。为了决定如何更新这条帖子的总点赞数，代码可能会长这样：

```python
rows = db.execute("SELECT likes FROM posts WHERE id = ?", post_id)
likes = rows[0]["likes"]
db.execute("UPDATE posts SET likes = ? WHERE id = ?", likes + 1, post_id)
```

第一行：从 `posts` 表里取出当前的点赞数，条件是帖子 ID 等于某个值（比如 123456）。注意这里**不可能**发生 SQL 注入，因为我用的是占位符，不是 F 字符串。第二行只是把结果存进变量，让代码更好读。第三行：我们想做自增，本质就是给总数加一，然后用刚才那个值更新回去。CS50 库支持在 SQL 字符串后面传多个参数，所以 `likes + 1` 和 `post_id` 都能安全地填进去。

为了实现"更新一下点赞数"这么个小目标，跑两次数据库查询、写三行代码，**这完全合理**。

现在问题来了。如果这段代码在**多台网络服务器上同时运行**会怎样？

```text
时间  服务器 A                          服务器 B
──────────────────────────────────────────────────────────────
 t1   SELECT likes → 读到 100
 t2                                     SELECT likes → 也读到 100
 t3   UPDATE SET likes = 101
 t4                                     UPDATE SET likes = 101
                                              ↑
                                    最终点赞数 = 101，但正确答案是 102
```

当用户几乎同时按下点赞按钮，完全可以想象：一台服务器先跑了第一行、拿到结果，假设正好是 100；纯属巧合地，另一台服务器也跑了同一行，拿到的**也是 100**。与此同时第一台服务器继续往下执行，把点赞数从 100 更新成 101。但第二台服务器并行地做着同样的数学决策，也把点赞数从 100 更新成 101。这个时刻正确答案明明应该是 102。

**我们丢了一次数据。** 这就是竞态条件的风险之一：最终结果不准确。对 Meta 来说他们绝不愿意丢掉点赞数据——点赞直接驱动用户参与度这种关键指标，这不只是技术问题，甚至可能变成商业问题。

这不就是放大版的"牛奶问题"嘛。

解决方案有很多种，但从概念上讲只有一个：**执行这段逻辑的时候把数据库锁住**，这样当一台服务器正在更新点赞数时，其他服务器就不能同时改这个计数。

对 Meta 那种规模的公司来说，直接这么做有点极端——因为它等于把所有点赞操作**串行化**，会严重拖慢系统。所以现在有了更精细的控制方式：**事务（transaction）**。通过事务，你可以**只锁定特定的数据行**，不需要锁住整张表，更不用说锁住整个数据库。在 SQL 里对应的是这样的命令序列：

```sql
BEGIN TRANSACTION;         -- 开始一个事务，从这里开始的语句构成一个整体
    UPDATE posts SET likes = 102 WHERE id = 123456;
COMMIT;                    -- 提交：保存这些更改
-- 如果中途出错或被中断：
ROLLBACK;                  -- 回滚：整个事务一笔都不生效
```

它保证的是数据操作的**原子性和一致性**：那三行代码、或者严格说是那两个数据库查询，**要么全部执行，要么完全不执行**，不会被中途打断。这就是解决这个问题的根本方法——跟给冰箱上锁、留便条、给室友打电话是一回事：**防止他们做出相同的决定。** 具体到竞态条件的技术细节（锁和事务的使用），在 CS50 可能不是重点，但概念你必须带走。

### 一个流传多年的经典：Bobby Tables

最后再用一点时间收尾。如果我们不介绍一些计算机科学领域的经典内容，那还算不上是真正的 CS 课程。

这里有个流传多年的梗，关于**光学字符识别（OCR）**——比如收费站想自动识别你的车牌。有人想用一个老掉牙的恶作剧骗过城市系统：只要扫到车牌就直接把数据喂进系统，**即使你用了正经的库来转义输入内容，数据库照样有可能被整个清空**。顺便提一句，真有人干过类似的事——我记得有人把车牌设成了 **NULL**，最后把系统搞得一团糟，因为程序员们不明白为什么在控制红绿灯的时候，到处都是空值。

而在计算机科学圈子里，XKCD 漫画里有一个非常著名的角色——就是这位。

经典的计算机科学笑话。现在你们知道小 Bobby Tables 是谁了吧。
