## 从 C 到 Python：把那些烦人的部分删掉
> 对应块：BLK18 | 覆盖分集：P07上 | 块标题（分集名）：《从 C 到 Python：语法初探》

### 从两块拼图到一行代码

现在到第六周了，我们要从 C 语言转向一种叫 Python 的语言。

先说清楚一件事：过去几周学的东西并没有跑出课程目标。学 C 的时候，我深信你们在这门课结束时会得到一个自底向上的理解——计算机到底怎么工作，编程语言到底怎么运作。正因为有了这个底座，你们以后再碰 Python、Java、C++、Swift 乃至更多语言时，会真正看懂它们在今天的软件世界里是怎么跑起来的。所以 C 不是弯路，是地基。

但这一周确实让人兴奋的地方在于：当你真的想让计算机说 "hello world" 的时候，前面那些代码会**真的消失**，最后浓缩成一行。这就是"更高级语言"的字面含义。

回想一下路线图。几周前我们从 Scratch 开始，`Hello World` 太容易了——把两个拼图块拼起来，小猫就开口说话。随后过渡到 C：第一周我们请大家暂且相信，跳过 `#include` 和 `int main(void)` 那一行样板，专注在程序的核心上。虽然换了函数、换了更新的语法，骨架还是 `Hello World`。现在，这一行也要被收走了。

为什么会变成这样？几十年来人类不断总结：哪些做法行之有效，哪些不然。计算机越来越快，内存越来越大，于是你能把更多资源投进去，让机器替你承担更多活儿。既然如此，你在语法上就别再那么抠细节了——不用写那么多代码，选对工具就能更快地开始解决自己感兴趣的问题、造出自己想要的产品。

现实世界里，CS50 之后你继续写代码，C 有时是对的工具，Python 有时是，有时又得是别的语言，甚至是你在学校里从没学过的。第六周最吸引人的一点就在这里：完成这门课后你会接触过大约 12 种（可能更多）不同的编程语言。到那时你就有自学新语言的能力了——因为你会开始看出新语言和你学过的语言之间那些共通的范式与语法结构。是的，具体写法会变，但结构会认得出来。真到了那时候，解决问题的路子就是 Google 一下，或者问 ChatGPT，只要你对相关知识有足够的了解、真正能完成手上的活儿。

所以本周以及后续课程（包括本周的习题集）的目标之一，就是让你在键盘前面对未知时更从容。我们不会把 Python 需要的全部知识掰碎了喂给你，而是希望你在探索里长出能力：学会查官方文档，学会用调试工具，最终能独立掌握一门新语言。

### hello.py：第一个 Python 程序

先动手。回想 C 语言里的流程：最早我们习惯用 `make hello`，它会自动去找 `hello.c`，神奇地生成一个叫 `hello` 的可执行文件，之后敲 `hello` 就能跑。一周之后我们揭穿了 `make` 的真面目——它其实只是在自动化编译。

真实编译器（以 clang 为例）要你手动做这些事：把 `-o hello` 传给命令行指定输出文件名（而不是默认的 `a.out`），再把要编译的源文件传进去，需要链接标准库之外的库时还要带上对应的库参数。编译完，运行时敲的命令完全一样。

Python 这里这些全免了。你写完 Python 代码想跑它，直接执行 Python 程序本身。

这里有个值得停下来想的点：**Python 不只是一种编程语言，它本身就是一个程序**。它是一个能理解 Python 代码的程序，就像 clang 是 C 语言的编译器一样。所以，写在 `hello.py` 里的代码当然能被它执行——只是动作和 clang 不太一样，我们很快就能看到差别。

动手写。切到 VS Code，执行 `code hello.py` 创建最简单的、也是第一个 Python 程序。这个文件里不需要包含任何头文件，不需要 `main` 函数，只写一行：

```python
print("hello world")
```

不编译，直接 `python hello.py`。祈祷一下——第一个 Python 程序跑通了。

就这么一行，已经能看到一堆明显差别：

- 没有 `#include`，没有 clang；
- 没有 `int main(void)`，没有花括号，只剩一对小括号；
- 没有 `printf`——注意是 `print`，不是 `printf`。`printf` 里那个 `f` 指的是格式化输出，我们在后面会看到 Python 也把这个能力保留了下来，只是做得更顺手；
- 不需要手动敲换行符 `
`，我光标已经自动跑到下一行了。人们慢慢意识到，多数时候我们其实更希望自动换行而不是手动控制，于是就把默认行为改成了自动换行；
- 行末不需要分号。意思表达完整了，不用再显式用分号收尾。

> **结论**：这就是"更高级"的具体含义——你不必再为机器的底层细节买单，注意力可以全部放在程序本身的功能上。

### 十九行重写拼写检查器

烦人的部分拿掉了，接下来看看 Python 到底能省多少事。当然这不只是 Python 独有的优势，任何比 C 更高级的语言都有这个优势。为了好玩，我干脆当场把习题集 5 用 Python 重写一遍。

回到 VS Code，关闭 `hello.py`，清空终端。我先把终端分成左右两半：左边 `cd` 到今天准备的习题集 5 **C 语言**参考答案目录，右边 `cd` 到一个叫 `Python` 的目录——里面放着习题集 5 的 Python 版实现，我已经准备好了 `speller.py`（相当于 C 版 `speller.c` 的 Python 实现）和对应的字典文件。遗憾的是 `dictionary.py` 还没有填上具体实现。现在就在这个文件里把它写出来，看看要花多少时间。

先声明一个全局变量，我叫它 `words`，赋值为 Python 内置函数 `set()` 的返回值：

```python
words = set()
```

`set()` 创建一个集合对象，能存大量单词、并且自动去重。所有细节 Python 替我处理了——这相当于我自动实现了一遍在习题集 5 里要手写的哈希表。

然后定义 `check` 函数，参数叫 `word`，毕竟 C 版就是这么写的。但语法变了：Python 用 `def` 定义函数，不指定参数类型，`word` 不声明类型，返回类型也不指定。

```python
def check(word):
    return word.lower() in words
```

函数体就这一行——先把 `word` 转成小写，再问"这个小写形式在集合里吗"。在是一个布尔表达式，成立返回 `True`，不成立返回 `False`。`check` 就完成了。

接着是 `load` 函数——把一个字典加载进内存：

```python
def load(dictionary):
    with open(dictionary) as file:
        words.update(file.read().split("\n"))
    return True
```

`open(dictionary) as file` 就相当于 C 里的 `fopen`。文件打开后，更新那个一开始还空着的集合：把文件全部内容读进来（从上到下、从左到右），按换行符切分成一份份字符串，每一份就是一个单词，一次性灌进集合。做完之后我假设一切运行正常，直接 `return True`——因为要我自己操心的事实在少了很多。

然后是 C 版习题集 5 里的 `size`，告诉我加载了多少词。Python 里这非常简单，直接返回集合的长度 `len()`：

```python
def size():
    return len(words)
```

最后是 `unload`——释放我手动分配的所有内存。可我在 Python 里根本没手动分配过任何内存，这些现在都由 Python 自动管理了，所以照样 `return True`，什么都不用做：

```python
def unload():
    return True
```

就这样，大约 19 行（其中大半还是空行）就重写完了习题集 5。我宣布：用 Python 重新实现了习题集 5。

### 权衡：1.87 秒对 1.32 秒

那就看看代价在哪。把终端窗口最大化，跑 `python speller.py`，目标是最大的字典文件 `holmes.txt`。回车。

屏幕上滚出一大堆"疑似拼写错误"的词——其中一些确实拼错了，一些只是字典没收，还有一些是字典里单词的所有格形式。输出最后除了计数，还有总耗时：**1.87 秒**。考虑到我实际动手只花了一两分钟，这成绩相当不错。

但这里有笔账要算。在左边那个 C 语言目录里，把 C 版编译出来，跑 `./speller holmes.txt`。屏幕上出现的是同样一批词。输出速度有时偏慢，可能是云端环境的影响，但 CPU 真正花在处理上的总时间——不含把所有东西打印到屏幕那部分额外开销——**只有 1.32 秒**，而 Python 版要 1.87 秒。

只差半秒，可放在各自的窗口里看，占的比例相当可观。所以：用 Python 解决问题确实更容易，代价是代码跑得更慢。

原因在于语言的执行方式。写 Python 时你运行的代码被称为**解释型**代码，计算机会逐行、从左到右地"读"你的代码，就像人读书一样，只不过是在两种语言之间做转换。设想两个人其实不会说同一种语言，其他人就得慢慢地把一种口语一句句译成另一种——这个翻译开销就是解释的开销。

```text
  C                                Python

  hello.c                          hello.py
     |                                 |
     v                                 v
  clang / gcc  (compile)          compiled to bytecode
     |                                 |
     v                                 v
  machine code (0s and 1s)        Python VM executes it
     |                                 |
     v                                 v
  CPU runs it directly            CPU runs the VM
```

不过，Python 社区长期以来一直在努力对付这个开销。实际用的解释器在底层会替你做优化：它会把你的代码**半透明地编译成一种叫字节码的中间形式**，然后直接运行这些字节码，这比一遍遍重新解释源代码高效得多。这块我们会随着时间慢慢深入。

再来看两个更简单的例子——相比用 C 解决，用 Python 处理它们会更短更快。

### 四行代码做模糊和边缘检测

打开习题集 4 里那张桥的位图照片，当时我们是用几种类似 Instagram 的滤镜去处理它。先做模糊。

新建 `blur.py`，程序我"可以"写得出来，但这次真快。在文件开头用关键字 `import` 把 PIL（Python 图像库）拉进来——导入 `Image` 和 `ImageFilter` 两个对象，它们是这个库的两个功能模块。真正解决问题就容易多了：

```python
from PIL import Image, ImageFilter

before = Image.open("bridge.bmp")
after = before.filter(ImageFilter.BLUR(10))
after.save("out.bmp")
```

`before` 是处理前的版本；`after` 是同一个图经过滤镜后的版本。为了效果更明显，我把模糊程度调到比习题集 4 要求的更大，设成 `10`。最后 `after.save` 把结果存成 `out.bmp`。

**4 行代码**，我在 C 里做的模糊功能就实现了。

跑之前我先祈祷一下——果然我犯了个错，而且哪怕你从没写过 Python 大概也看得出来：在第 4 行我用了 `after`，可这个变量是在上一行才创建的。作者在这行写下它的时候还不存在。回到文件把 `after` 改成我真正想用的那个变量名，重新跑，这次我交叉手指——没问题了。打开 `out.bmp`，对比原始的 `bridge.bmp`：确实相当模糊。

再来点更炫的。上周已经比较熟练的同学可能在 C 里实现过边缘检测，用 Python 试试有多快。`edges.py`：

```python
from PIL import Image, ImageFilter

before = Image.open("bridge.bmp")
after = before.filter(ImageFilter.EDGES)
after.save("out.bmp")
```

`BLUR` 换成 `EDGES`，它和方框模糊不同，是用来检测图像边缘的。跑 `python edges.py`，很快。打开 `out.bmp`——原图里清晰的桥缘，现在整幅图像的边缘都被勾了出来。

这就是从 C 换到 Python 之后，同一件事可以短到什么程度。

### 换了语言，什么没变

那我们能从 C 里学到什么？C 当然有函数——执行特定操作或动作的模块。我们像之前对比 Scratch 和 C 那样并排看。

左边还是我们最早的老朋友 Scratch。一个紫色的 "说" 拼图块，它本身就是一个函数，功能是输出参数的值，在这里就是 "hello world"。我们已经在 Python 里见过对应物了：看着像 C 版的 `printf`，但不再是 `printf`、不再有分号、不再要显式换行。Python 里就这么简单。

那"库"呢？C 里我们只有头文件，头文件让你能访问库中函数的原型，也就是你想调的那些函数的签名。Python 用的词略有不同，它有**模块（module）**和**包（package）**，而包其实就是模块的集合。很多时候在 Python 语境里，模块就等于库。所以每次听到有人讨论 Python 的模块或包，他们其实在聊使用库。

库有两类：语言自带的标准库，和需要你自己下载安装的第三方库——比如几周前我装过的 `cowsay`，好让我能在屏幕上画一头牛。

C 里对应的是 `#include <CS50.h>` 这种写法。至少这一周，我们会准备一个与 C 版 CS50 库对应的 Python 版本，让你从 C 过渡到 Python 时轻松些。不过这两个版本的 CS50 库**就像辅助轮**——你完全可以、也应该尽快把它们卸掉，大概一周就够了。它们的作用只是让过渡更顺滑，把"哪些相同、哪些不同"这件事标出来。

那 Python 版的 CS50 库里也有 `get_string`，作用同样是获取字符串。用它不需要 `#include <CS50.h>`，那是 C 的写法。Python 里是：

```python
from CS50 import get_string
```

语法稍显冗长，但好处是能更精确地指定你想从库里导入什么——特别是你不想把整个库都塞进内存的时候。

### 拿到用户输入：get_string、input 与 f 字符串

来写个比打印 "Hello World" 更有意思的，这是我们第一个真正获取用户输入的程序。先快速回忆 C 版：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string answer = get_string("What's your name? ");
    printf("hello, %s\n", answer);
}
```

`get_string` 问用户"你叫什么名字？"，末尾那个空格是为了让光标跳过去。C 里我还必须加分号。插入 `answer` 就能打印"你好，David""你好，Kelly"。`make hello` 一遍，输出正常。

Python 版简洁得多：

```python
answer = input("What's your name?")
print("hello, " + answer)
```

`printf` 变成 `print`，分号没了，还有两处明显不同。第一处：**不需要任何占位符**，`%s` 不见了。第二处：我特意用加号来连接字符串。学过 Java 或别的语言的人可能已经见过这种用法；即使你只学过 CS50 的 C，大概也能猜出这个加号是干什么的——它在把左边和右边的内容**连接、拼接**起来。

这其实我们在 Scratch 里就干过：那个拼接积木把 "hello, " 和 `answer` 变量里的值接在一起。Python 里的加号是完全一样的功能。

> **易错点**：如果你是从占位符的思路过来的，务必转过来。"先在这儿摆个占位符，稍后再把变量值填进去"是 C 的习惯。人们慢慢发现，直接拼接比折腾占位符简单得多——当然占位符在别的场景仍然有用。

这两行代码和 C 版之间还有一个更细微的差别：Python 里又不需要 `
` 了，自动换行已经处理掉了。还有一处：**不需要声明 `answer` 的类型**。C 里你得告诉编译器这是字符串——上周我们会把 `string` 改写成 `char *`，但那个声明省不掉。Python 里可以直接省略，解释器会根据上下文自己推断：`get_string` 返回字符串，那这个变量显然就存字符串；返回整数，那就存整数。它替你做了更多这样的决策，帮你省时间省精力。

顺带回答一个很自然的问题：`input` 也只能拿字符串吗？是的，它目前只从键盘取输入并返回一个字符串，和 `get_string` 一样。我们稍后会谈为什么这可能不是个理想设计。

不过我们还能再往前走。Python 里解决这类问题的方式更多，即便只是这么简单的问题。`print` 可以接受多个参数——把加号换成逗号、引号里的空格去掉，直接给两个要打印的东西：

```python
answer = input("What's your name?")
print("hello,", answer)
```

哪个更好？我觉得其实差不多，算等效的。但它体现了 Python 在字符串打印上比 C 更灵活。还能再进一步，代价是刚开始看有点难受：

```python
answer = input("What's your name?")
print(f"hello, {answer}")
```

最明显的变化是——那些奇怪的大括号又出现了。它们当然不属于程序逻辑，位置在双引号内部。还有一个关键区别：引号前面多了一个奇怪的字母 `F`，紧挨着双引号。**只有加上这个 `F`，你得到的才是 f 字符串（格式化字符串），而不是一个普通的文本字面量。**

把变量名放进花括号，意味着该变量的值会被直接替换到那个位置，作用和 C 里的 `%s` 类似。但区别很实在：用百分号你得记住它对应的是哪个变量，挺烦人的；用花括号就直接写明了你打算把哪个值放在这里。从技术上说，解释器对 `answer` 做了**插值**——把它的值直接嵌进那个位置。

我特意先写漏了那个 `F` 再跑一次。程序输出了字面的 `hello, {answer}`，还附带一个报错——因为它把 `{answer}` 当普通字符打印了。看清楚现在缺的是什么：`F`。补上，再跑，值就被正确插值替换了。

到这里我们可以卸掉一个辅助轮了。`get_string` 之所以还留在库里，主要是为了平滑过渡，说实话它本身并不复杂。Python 自带 `input`，功能本质上和 `get_string` 一样，所以这个程序已经可以把 CS50 库整个删掉了：

```python
answer = input("What's your name?")
print(f"hello, {answer}")
```

跑一遍，输入名字，输出正常。`input` 通常就是你获取用户输入的方式。

顺便再说清两个在 Python 里显得奇怪的现象。第一，**为什么没有 `main` 函数**？我们之前写的每个程序里它都存在，可到目前为止所有 Python 程序都没有。后来人们发现，人们几乎总是希望自己正在编辑的那个文件成为程序的主要部分，这太常见了。如果你只想写两行代码完成一件事，何必多此一举加上 `int main(void)` 之类的额外语法？何必浪费时间添加所有那些样板代码？

说实话，我在这里写的确实是一个程序，只是现实中人们也常把它叫**脚本**。脚本是一种轻量级程序，基本上就是从上到下、从左到右顺序执行。它可能相当轻——这和"写程序"其实是同义的说法。这也再次体现了 Python 这类语言的吸引力：你可以直接上手，快速解决问题，然后收工。就连 Java 近年来也朝这个方向发展了——熟悉 Java 的人应该知道，你现在不必把代码全塞进一个类里、不必再写 `public static void main` 那种结构，直接写 `System.out.println` 就能干活了。

第二，**参数怎么传**。到目前为止我们在 C（以及 Scratch）里传给函数的每一个参数都是**位置参数**。形参和实参本质上是同一个概念：站在函数角度它接受的是形参，你调用时传进去的值叫实参，但指的东西一样。位置参数意味着顺序至关重要——第一个、第二个、第三个，依次对应。

以 `printf` 为例，第一个参数必须是带引号的字符串（可能含占位符），逗号后面才是第二个、第三个。Python 多给了你一个选择：**命名参数**，不必只依赖顺序。

> **提示**：这在实际开发中极有用。当你开始使用别人写的、功能丰富的库时，一个函数可能接受 4 个、10 个甚至更多参数，要记住所有参数的确切顺序非常麻烦；万一顺序搞错了，或者同事把签名调乱了，麻烦就大了。命名参数让你按实际名称明确告诉函数"我要传的是这个"。

看一个最简单的用法：覆盖 `print` 调用时自动出现的那个换行符。把程序简化到最初版本：

```python
print("hello")
print("this", end="")
```

第二行给了一个名字：`end=""`。把 `print` 的 `end` 参数设成**空字符串**，就覆盖了它的默认行为——那意味着输出到那里之后什么都不接。跑一下，提示符会难看得和 `$` 符号挤在同一行，就像我第一周写 C 时忘记换行符犯的错一样。没错，`end` 的默认值就是 `
`，现在我们把它显式改掉了。

改回 `print("hello", end="")` 再跑，光标就回到下一行了。覆盖默认值本身没什么大用，但你可以用它玩出些有趣效果——比如让输出结尾带个感叹号，或者在 `end` 里放一个 `
`，同时看到这两种效果。不过通常用 `end` 就是为了覆盖默认值。

### 去 docs.python.org 读 print 的原型

想了解这类东西怎么办？去查 Python 的官方文档。这一点比 C 语言突出得多——Python 有一个社区维护的、被公认权威的官方文档，地址是 `docs.python.org`。它有点类似 C 里的 man pages，但 man pages 有多个互相矛盾的版本，Python 不一样。

比如访问一个以 `functions.html` 结尾的页面，你会看到一份详尽的列表，列的是 Python 自带的所有函数，而不只是 `print`。往下滚到 `print` 的部分，会看到一些看起来挺晦涩的内容——那就是它的表示方式。这是一个 Python 原型，你也可以叫它**函数签名**，只告诉你函数名、它接受几个参数、参数是什么类型。

```python
print(*objects, sep=' ', end='\n', file=None, flush=False)
```

怎么读？`print` 接受**一些对象**作为参数。`*objects` 这种写法在 Python 里表示零个或多个对象，无论什么类型——数字、字符串、别的都行——就是你想打印的东西。之后 `sep` 是命名参数，指定打印参数之间的分隔符：回想一下，我写 `print("hello,", answer)` 时并没有在引号里手打空格，系统就用一个空格把它们分开了，因为 `sep` 的默认值就是一个空格。`end` 的默认值是 `
`。最后那个和文件、重定向输出有关的部分，留到以后再说。

顺便把引号的事也讲清楚。Python 里字符串既能用双引号也能用单引号，而 C 管得严得多：双引号是字符串，单引号是字符——`char` 只表示单个字符。Python 里你选哪种都行，**关键是保持一致**：从代码风格角度，你应该选一种然后坚持用。唯一需要交替使用的情形，是字符串本身里要包含撇号，比如在人名的所有格里包着的那一个 `'`，这时双引号串里用单引号，或者反过来。

总体来说你的自由度高得多。Python 社区（至少官方文档里）偏向单引号，JavaScript 社区也是这个偏好；CS50 统一用双引号，好和我们日常读写看到的代码保持一致。不管哪个社区、哪家公司，一般都会有自己的风格指南明确该用哪种——哪怕只是为了全项目风格统一。

### 变量与数据类型：Python 砍掉了什么

我们用过好几次变量了，现在仔细看看它和 Scratch 里的变量有什么区别。要创建一个叫 `counter`、初始值为 0 的变量，Scratch 里用那个橙色拼图块。C 里这样写：

```c
int counter = 0;
```

声明类型、变量名、等号赋初值、分号收尾。Python 有点类似，但你大概已经能猜到后面怎么发展了：

```python
counter = 0
```

类型声明——以及更一般的"数据类型"这件事——整个消失了。我们直接写 `counter`，因为一个聪明的解释器完全能根据上下文推断出你放进去的是个 `0`，明显是个整数。分号也没了。就这么简单。同样一件事，Python 里的代码量少得这么明显，这正是这类语言对程序员更友好的原因：写更少的代码，做同样的事。

想给计数器加 1 呢？Scratch 里用那个 `+1` 拼图块。C 里 `counter++` 或者 `counter = counter + 1`；Python 里也是 `counter = counter + 1`，当然不用分号；缩写成 `counter += 1` 同样在两边都能用。

> **易错点**：C 里的 `++` 和 `--` 在 Python 里没有。Python 语法上允许你写它们，但它们根本不存在，所以你会更常看到 `+= 1` 这种写法。别去试，它们只会报错。

那 Python 到底有哪些数据类型？因为声明时不用写类型，但类型在底层是真实存在的，知道一些很有必要——否则会遇到某些难以察觉的错误。

| C | Python |
| :--- | :--- |
| `bool` | `bool` |
| `char` | 没有对应物 |
| `double`、`float` | `float` |
| `long` | `int` |
| `string`（其实是 `char *`，来自 CS50 库） | `str` |

C 那一列里那个 `string` 要归功于 CS50 库——上周我们已经开始改口叫它字符指针，那同样是一种数据类型：某个字符的地址。Python 这边把列表精简成了一个子集：布尔、浮点、整型、字符串，实现方式和 C 都不同。字符串在 Python 里直接就叫 `str`，不是 CS50 库特有的概念。而**这一列里完全没有指针**，更不用说字符指针了。

> **提示**：Python 里没有指针。第 4 周和第 5 周的内容非常强大，但我敢说你们也感到极其沮丧和挑战重重，代码里因此出现了不少 bug。内存管理的强大伴随着一整套可能犯错的模式——这不仅对 CS50 的学生如此，对全世界的程序员、成年程序员、全职程序员都是一样。Python 这类语言的特性之一，就是试图移除 C 里那些**过于危险**的功能：它们可能非常强大，能帮你更快更精确地解决问题，但如果带来的麻烦多于价值，那就得不偿失了。把这些细节抽象掉是值得的。Java 也是一样的思路——它有引用（references），但没有指针（pointers），你没法像 C 那样随手去访问内存里的任意位置。

### 计算器 0.0 的 Python 移植

实际体验一下这些类型，看看哪些相同、哪些不同。我把之前用过的一个老计算器翻出来——`calculator.c`，之前同时包含了 CS50 库和标准输入输出库，然后在第一周就用 `get_int` 取两个整数直接相加：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    // Get user's input
    int x = get_int("What's x? ");
    int y = get_int("What's y? ");

    // Do the math
    printf("x + y is %i\n", x + y);
}
```

把它转成 Python 版 `calculator.py`。把 C 代码复制过去，保留需要的、砍掉不需要的：注释惯例从 `//` 换成 `#`（按键次数直接减半，挺爽的）；把 `int main(void)` 和这对大括号删掉——不需要 `main`，也就不需要所有这些缩进了，把它们全部左对齐；`#include` 那几行也不要。

然后是那三行核心代码。对着 C 版你已经能猜出来了：输入的 `get_int` 换成……先留着，之后再去掉这个辅助轮；分号全部删掉；`printf("%i", x + y)` 这种写法有几种替代方案，最直接的是把格式代码整个去掉，让 Python 直接打印 `x + y`：

```python
from cs50 import get_int

# Get user's input
x = get_int("What's x? ")
y = get_int("What's y? ")

# Do the math
print(x + y)
```

`python calculator.py`，输入 `x=1`、`y=2`，输出 3。正常。

现在拆辅助轮。先去掉 C 版把注意力全放在 Python 上，然后问：用什么函数来获取用户输入？`input`——名字更直白。把 `get_int` 换成 `input`，整个程序变成：

```python
# Get user's input
x = input("What's x? ")
y = input("What's y? ")

# Do the math
print(x + y)
```

简洁多了。跑一下，输入 `1`、输入 `2`——

> ```text
> 12
> ```

等一下，`1 + 2` 等于 12？这显然是退步了。

这是怎么回事？在字符串的语境里，`+` 表示连接，把左右两侧拼起来。这里正是如此——结果不是数字 12，而是更字面意义上的 `"1"` 和 `"2"` 拼在一起。根子出在 `input` 上：**它返回的是字符串**。这些是用户敲下的按键字符。在我们看来那可能是阿拉伯数字 1 和 2，但它被当字符串处理了。更准确地说，底层涉及的其实是字符指针那一套，只是不是用同样的术语来描述。

那在不用 CS50 库那个 `get_int` 的前提下，怎么解决？想一想 CS50 库里的 `get_int` 本身可能是怎么实现的。答案是类型转换。C 里我们能把某些类型转成另一些类型，通常是整数转字符、或字符转整数。但这里没那么简单：底层有一整个 `1` 加一个空字符、一整个 `2` 加一个空字符，并不是字符转整数那种直接的活儿。所以我们需要更准确地把**字符串转换成整数**。这不是在"强制转换"（cast），而是在"转换"（convert）——后者通常意味着要完成更多额外工作。

幸运的是 Python 能帮我们做。`x = int(x)`、`y = int(y)`，语法上很相似。细看很有意思：同样写着"类型名"，在 C 里做类型转换你是在括号里指定数据类型；在 Python 里，**数据类型本身变成了一个函数**，接收一个参数，就是你想转换的那个字符串。

```python
# Get user's input
x = input("What's x? ")
y = input("What's y? ")

# Do the math
print(int(x) + int(y))
```

跑一遍，输入 1、输入 2，答案 3，恢复了。既然我知道 `input` 返回的是字符串，那就把它的输出直接当 `int` 的输入——这才是更符合 Python 风格的做法，嵌套函数调用我们在 C 里也干过。

还有一个小问题我暂时不深究：我输入的是真正的数字 `1` 和 `2`，但如果你跟着在家做、输入了 "cat" 和 "dog"，就会出问题。我们很快会回到这里。

### 内置的数据结构

除了数据类型，Python 还提供了很多东西，其中一些我们这周就会用到。

| Python 类型 | 它替你解决了什么 |
| :--- | :--- |
| `range` | 数字范围，内置 |
| `list` | 数字列表，像数组的升级版，解决了上周讨论数组时提到的所有缺点 |
| `tuple` | 元组，用来表示像 x、y 这样的坐标点 |
| `dict` | 字典，直接提供键值对，不用自己写哈希表 |
| `set` | 集合，存唯一值集合，检查元素是否存在非常方便 |

这才是 Python 这类语言真正强大的地方。在 C 里，我们主要只能从语言本身拿到数组这一种数据结构，其他所有结构要么自己实现，要么至少要在课上讨论怎么构建。现在这些连同更多东西全都内置在语言里了。

Python 版的 CS50 库里也提供了大量现成函数，都是 C 版函数的对应实现。我们需要的函数比 C 版少（因为 Python 的数据类型更少），但 `get_float`、`get_int`、`get_string` 确实都存在。欢迎、也鼓励大家用这个库——习题集 6 的目标之一，正是用 Python 重新实现一部分你之前用 C 做过的问题。你可以参考自己当时的 C 代码，试着逐行翻成 Python。不过你也已经看到了，辅助轮可以很快甩掉。

导入方式有几种。多个函数可以分开导入：

```python
from cs50 import get_int, get_float, get_string
```

也可以直接导入整个库，这在一些代码里会看到，然后通过稍有不同的语法调用其中的函数。

### 条件语句：冒号、缩进与 elif

来看另一个从 C 移植过来的基本结构。如果要比较两个变量、判断 `x` 是否小于 `y`：Scratch 里是那么一串拼图块；C 里是这样：

```c
if (x < y)
{
    printf("X is less than Y\n");
}
else if (x > y)
{
    printf("X is greater than Y\n");
}
else
{
    printf("X is equal to Y\n");
}
```

Python 呢？变化有哪些？F 字符串里的 F 没了（这里没用），换行符没了，分号也没了。但真正要留意的是语法上的差异：**括号和花括号都不见了**。括号在逻辑上没增加多少实际意义，所以去掉；花括号也去掉——虽然 C 里条件只有一行时技术上可以省略花括号，但为了风格一致我们通常还是保留。Python 完全不要求花括号，取而代之的是**强制要求缩进**。

必须缩进正确。如果你以前写程序时习惯把所有代码左对齐、搞得一团糟直到 style50 帮你自动整理，在 Python 里你不能再这么干了。这是程序员群体一个普遍问题，新手和专业人士都会遇到。所以 Python 在语言层面直接要求：如果你希望某行代码在某个布尔条件下执行，就必须用缩进明确它归属哪个代码块。如果布尔表达式为真，按惯例把那行缩进 **4 个空格**。你不能偷懒全部左对齐、想着以后再整理。

> **结论**：正因为这些要求来自语言本身，Python 代码可以说更具可读性。括号和花括号能省，省下来的注意力就投给结构本身。

从 Scratch 的 `if` 结构过来，对比更明显：Scratch 里为了表达一个简单的逻辑用了相当多的代码行，所有那些积木块在 Python 里全都消失。Python 只用冒号引出后续缩进块——

```python
if x < y:
    print("X is less than Y")
elif x > y:
    print("X is greater than Y")
else:
    print("X is equal to Y")
```

C 里的 `else if` 那部分在屏幕上只是一闪而过，但有一个细节值得注意——**那不是打字错误**。`else if` 被缩写成 `elif`。说实话这么多年过去了，我到现在都记不清它到底该不该写成一个词还是两个词——不同语言对这个短语的缩写形式不一样。Python 里写作 `elif`，这可能是最紧凑的写法。你当然也可以老老实实写成 `else` 加 `if` 两个词，其他部分完全一样，**包括这次也需要冒号**。

这里还有一个好问题：Python 是用什么语言写的？我们在 VS Code 里用的这个解释器本身是用 **C** 写的，也就是 CPython。不过实际上你可以用任何语言实现一个 Python 解释器——甚至如果你有足够耐心用汇编语言去写，用纯 0 和 1 写也行（那正是我们几周前简单接触过的东西）。真想玩"元编程"的话，用 Python 来写一个 Python 解释器完全可以，用 C++ 或 Java 也行。编程语言有意思的地方就在这儿：**你可以用任何一门语言为另一门语言编写编译器或解释器**，区别只在于实现的难易程度，以及因此要花多少时间。

### 逐行对照：把 compare.c 改写成 compare.py

最后做一件不一样的事：把之前看过的比较程序并排打开，把一种语言逐行翻译成另一种。

先回顾它做什么。它包含 `cs50.h` 和 `stdio.h`，用 `get_int` 提示用户输入两个整数存进 `x` 和 `y`，然后做一次非常简单的比较——判断 `x` 是小于、大于还是等于 `y`。（这个版本是加了注释的，第一周那个可没有。）

新建 `compare.py`：

```python
from cs50 import get_int

x = get_int("What's x? ")
y = get_int("What's y? ")

if x < y:
    print("X is less than Y")
elif x > y:
    print("X is greater than Y")
else:
    print("X is equal to Y")
```

和左边那份对照着看。我认为这两段代码是等效的：行数明显减少了，因为之前很多行其实是注释；而且我们省掉了花括号和一些额外语法，比如那些在 C 里撑起条件的括号。

## Python 字符串、循环与异常处理
> 对应块：BLK19 | 覆盖分集：P07中1 | 块标题（分集名）：《Python 条件循环与 range》

### 字符串相等这件事，Python 一步到位

先把 `compare` 跑一遍。输入 1 和 2，屏幕上打出 `X is less than Y`；换成 2 和 1，变成大于；再来一次 1 和 1，两个数相等。功能上没什么可挑的。

但它只是个小练习。回想一下我们当初为什么要写 compare：第 1 周引入 ants 那个例子的时候，那一周的语法对我们来说完全是陌生的，所以特意挑了逻辑最简单的一份程序来练手，想用它的简单去对冲语法的陌生。结果一动比较，就撞上墙了——字符串。

C 语言这边，我们比的是什么？是 `char *`。第 2 周我们最终掀开了字符串的底牌：它本质上就是字符指针；一直熬到第 4 周才算真正把它摆平，靠的是 `strcmp`——这个函数的作用就是逐个字符地比较两个字符串是否相等。它凭什么做得到？因为它懂得指针怎么用，也知道字符串末尾那个空字符 `\0` 停在哪儿，这些本事全部来自我们熟悉的 `string.h`。

到了 Python 那里，麻烦小得多。打开终端，新建一个 `compare.py`——这次我甚至不打算用 CS50 的任何辅助函数，直接拿内置的 `input()` 来接收用户输入：

```python
s = input("s: ")
t = input("t: ")

if s == t:
    print("Same")
else:
    print("Different")
```

跑一遍：输入 `cat` 和 `dog`，Different——在 C 里我们同样会得到这个结果；再输入两次 `cat`，Same。

> **易错点**：Python 的 `==` 在字符串上不会像 C 那样直接比地址。它比的是字符串的内容，也就是那些字符的实际值，这才是程序员真正关心的东西。顺带一提，双等号背后其实藏着一个循环（for 也好 while 也好），逐个字符地把两个字符串走一遍，才给出你看到的那个答案。

把两个版本并排放在一起看，差别挺刺眼：

```text
compare.c  (C)                    compare.py  (Python)
----------------------------      --------------------------------
string s = get_string("s: ");     s = input("s: ")
string t = get_string("t: ");     t = input("t: ")

if (strcmp(s, t) == 0)            if s == t:
    printf("Same\n");                 print("Same")
else                              else
    printf("Different\n");            print("Different")
```

为了判断两个字符串是否相同这么一件事，C 版本要拉进 `string.h`、要理解指针、还要知道 `strcmp` 返回 0 才代表相等；Python 版本就是一行 `s == t`，连 CS50 库都不用碰。第 1 周挡在面前的那块石头，在这里根本不成其为问题。

### or 关键字、列表，与那个还没修好的 bug

接下来处理 `Agree.c`。在 C 里它长这样：用 CS50 库的 `GetChar` 要来一个字符，期望是 `Y` 或 `N`，分别代表"是"和"否"；然后用两个竖线 `||` 把两个布尔表达式接起来，问"输入字符是不是大写的 Y，或者是不是小写的 y"；是就直接打印 Agreed，否则打印 Not agreed。

Python 版该怎么写？在 `agree.py` 里：

```python
s = input("Y or N? ")

if s == "Y" or s == "y":
    print("Agreed")
else:
    print("Not agreed")
```

有三处不一样。第一处最显眼：我写的是单词 `or`，不是两个竖线。Python 的设计理念本来就偏英语的自然表达，让代码从上到下、从左到右都更易读，而 `or` 这个关键字恰好把这一点落到了实处。

第二处：`s` 不是字符。Python 里压根没有 `char` 这种数据类型，能拿到的最短单位就是"含一个字符的字符串"。这里也正好说明为什么这次连 CS50 库都用不上——内置的 `input()` 已经足够。

第三处是真正的坑。上面这版其实不健壮：用户要是输入 `yes`、`YES` 或者别的大小写组合呢？把条件一路写成 `s == "y" or s == "yes" or s == "YES" ...` 当然也能跑，但扩展性很差——真要覆盖所有大小写组合（还要考虑大写锁定键开着或关着的差异），要枚举的东西立刻膨胀起来。

换个思路：把所有可能都收进一个列表。C 里确实有数组，Python 里对应的东西叫列表，其底层实现正是我们第 5 周讨论过的链表结构——能动态地长，也能动态地缩，而背后的内存管理 Python 全包了。哪怕我们眼下只是把它当成一个静态初始化的值列表来用，也完全够：

```python
s = input("Y or N? ")

if s in ["y", "yes"]:
    print("Agreed")
else:
    print("Not agreed")
```

`in` 正是用来问"这个值在不在这个列表里"的关键字。跑一下：输入小写 `y`，Agreed；输入小写 `n`，Not agreed；输入全大写的 `YES`——咦，还是 Not agreed。

> **易错点**：这是 bug，不是巧合。Python 是严格按字面值查找的，列表里写的是小写 `y` 和小写 `yes`，那它就只认这两个。

修法有两个方向，都对。一种是在把输入存进变量之后立刻规范化：

```python
s = input("Y or N? ")
s = s.lower()

if s in ["y", "yes"]:
    print("Agreed")
else:
    print("Not agreed")
```

另一种是反过来：把用户的输入统一转成大写，列表里就写 `["Y", "YES"]`。从技术上讲，多出来的那一行甚至可以省——Python 允许把函数套起来用，`input().lower()` 一步到位，input 的返回值会被强制转成小写；或者干脆在做比较的那一刻才转，`if s.lower() in ["y", "yes"]:`。用 `.lower()` 把输入规范化之后，再拿它去和我们预先定义好的规范形式（全小写）比较。选哪种，取决于你想把"规范化"这件事放在流水线的哪一段。

### 方法：长在对象里的函数

`s.lower()` 这一行值得停下来看一眼，因为它是 Python 的一道分水岭。

在 C 里，我们要转大小写，做法是调 `toupper` 或 `tolower`，把需要转换的那个字符当参数递进去。在 Python 以及大多数现代语言里，语言的设计者意识到：有些功能天生就黏在它所操作的那个值上——你拿到一个字符串，就必然会想把它转成大写、小写、首字母大写，或者做点别的，这太合理了——那干脆把它们直接做进类型里。

这就是通常所说的面向对象编程，简称 OOP。在 Python 以及许多其他现代语言中，变量和数据类型不仅具有关联的值（比如 `"y"` 或 `"yes"`），还内置了相应的功能。Python 的字符串类型里内置了 `lower()` 以及其他一系列相关功能——实际上所有字符串操作 Python 都内置了，你可以在官方文档里查到。

> **定义**：当一个函数被内置在某个数据类型内部，并且你通过点运算符 `.` 去调用它（而不是调用某个全局函数再把参数递进去），你用的就是所谓的"方法"（method）——说白了，方法就是对象内部的函数。此时讨论的那个对象本身就是一个字符串。

那这里到底发生了什么？字符串本质上就是内存中的一个对象，它不仅装着用户敲进来的字，还内置了一批方法。这些方法是当初发明字符串数据类型的那帮人写的。

> **提示**：语法其实和 C 非常相似。熟悉 C 的人看到 `.` 会想到访问结构体成员；只是 C 里你只能取到结构体内部的数据，而 Python 允许你走进对象内部——不光能取它的值，还能调用它的内置方法。

刚才那句 `s.lower()` 还漏了一句：Python 的字符串不只有 `lower()`，还有 `upper()`、`capitalize()`、`isnumeric()` 等等一大票。后面我们还会撞见更多类似的例子。

#### 复制一份，再把首字母大写

我们在 C 里为字符串复制折腾了好几周（助教版 `copy5.c` 里还留着当时写的注释），过程大致是这样：用 CS50 的 `get_string` 提示用户输入要复制的字符串，再做错误检查，确认内存分配足够、程序运行正常；然后 `malloc` 分配空间——除了字符串本身的长度，还得额外多分配一个字节，放结尾的空字符 `'\0'`；检查 `malloc` 的返回值确保分配成功；再逐字符把 `s` 的内容复制到新分配的内存块 `t` 里，当然最后我们直接用内置的 `strcpy` 把那串循环复制全都包办了；接着做一次有效性检查，确认 `t` 的长度大于 0，否则没东西可大写；然后用 C 标准库里的 `toupper`，把 `t[0]` 递进去，并直接把结果写回 `t[0]`；最后打印这两个字符串，`free` 掉自己分配的那块内存。二十来行。

这里展示的是一个标准的面向过程编程例子：把需要大写的那个参数递给 `toupper`，而不是像面向对象编程那样通过点运算符直接让字符对象"把自己大写掉"。

Python 版：

```python
s = input("s: ")
t = s.capitalize()

print(f"S: {s}")
print(f"T: {t}")
```

`capitalize()` 的文档写得很清楚：它把用户输入的单词首字母转成大写。打印那两行用的是 f 字符串——在引号里写 `f"S: {s}"`，通过花括号把变量的值嵌进来。

跑一下，输入 `cat`：S 那行仍是全小写的 `cat`，复制出来的 T 那行确实变成了 `Cat`。原串没动，副本才被大写。

> **提示**：f 字符串不只是"把变量塞进字符串"这么点本事。在后半段我们会看到，在花括号里的变量名后面加一个冒号、再加一个点号、指定一个格式，就能像 C 的 `printf` 里用 `%f` 那样控制小数位数。

#### 把整个字符串变成大写

几周前那个"全大写"程序我们是用循环写出来的：先 `get_string` 提示输入，再打印"转换前的字符串"，然后用循环从 0 迭代到字符串长度，每次 `i++`，循环体里把当前字符转成大写后**直接打印出来**。严格说我们并没有真的修改那个字符串，只是把每个字母转成大写后立刻输出。

Python 里当然也可以先照着这个思路写：

```python
before = input("before: ")
print("after:  ", end="")

for c in before:
    print(c.upper(), end="")

print()
```

开头那行 `print("after:  ", ...)` 是故意多打一个空格，好让 `after:` 和后面的结果对齐；`end=""` 表示打印完不换行，整个字符串挤在同一行上，循环结束后再单独打一个换行符。`for c in before` 会自动把 `before` 里的每个字符依次交给 `c`——我们不需要索引、不需要长度、不需要下标运算，这就是 Python 遍历字符串的方式。输入 `cat`，三声 `CAT` 出来。

但既然 Python 是面向对象的，字符串自己就带着方法，压根不需要一个字符一个字符地磨。直接换成三行：

```python
before = input("before: ")
after = before.upper()
print(f"after: {after}")
```

同样的输入，一次到位。二十行变三行——这不只是行数的事，中间那堆"怎么把字符取出来"的问题根本就不存在了。

### while 循环：几乎原样搬过来

在 Scratch 里想让屏幕出现三声"喵"，往脚本里拖一个"重复执行"积木就够了。在 C 里这就略显笨拙：声明一个变量 `i` 并初始化为 0，然后设一个布尔表达式"i 是否小于 3"，条件成立就打印，再用我们熟悉的 `i++` 递增。

Python 几乎可以照抄，只是用最精简的语法——不用再指定数据类型了，分号也不要了，括号不要了，花括号不要了，`++` 也没了，换成 `+=`；剩下的只有那个冒号和随后的缩进：

```python
i = 0
while i < 3:
    print("meow")
    i += 1
```

无限循环也一样。Scratch 里我们用"永久循环"积木；在 C 里没法直接实现完全相同的结构，最接近的是 `while (true)`——这个布尔表达式按定义恒为真，所以循环永远不会停止，屏幕上就会无限重复显示"喵"，直到你受够为止。Python 几乎原样：

```python
while True:
    print("meow")
```

> **易错点**：C 里用小写的 `true` 和 `false`，Python 用首字母大写的 `True` 和 `False`——这个大写的 `T` 确实得写。花括号、分号、圆括号、反斜杠 n 都不再需要了，但**缩进必须始终保持一致，冒号也必须留着**。这两点一旦错位，语法错误或者死循环就来了。要中断循环，和 C 一样，`Ctrl + C` 掐掉进程。

### for 循环：四行变两行

`cat.py` 当然还有更简单的路子：直接写三行 `meow`，复制粘贴完事。能跑，但这种做法有很多问题，程序确实完成了任务。（顺便，`print` 写在循环外面的话，就只会叫一声——这个坑几乎人人都踩过。）

刚才那个 `while` 版本已经很精简了，但它终究只是"几乎一样"。Python 里真正顺手的是 `for`：

```python
for i in [0, 1, 2]:
    print("meow")
```

两行。Python 的 `for` 循环和 C 的 `for` 在结构上很不一样——C 那一套要你把初始化语句、布尔表达式、更新语句分别写在括号里、用两个分号隔开；Python 这些全都不用写，你只要用更接近自然语言的说法表达，比如"对于列表中的每一个 i"。剩下的交给它：第一轮把 `i` 设成 0，第二轮设成 1，第三轮设成 2；由于列表中只有三个元素，循环到这里就结束了。

这里的方括号看着眼熟吧？和之前那个 `["y", "yes"]` 一样，它写起来像 C 的数组，但在 Python 里我们创建的是一个列表，元素是任意对象。`[0, 1, 2]` 里的三个数没有引号包围，所以显然不是字符串，是整数；真写成 `[1, 2, 3, 4, 5, 6]` 或者 `["cat", "dog", "bird"]` 也一样能跑——这里用 `[0, 1, 2]`，只是为了让循环变量和 C 版本的实现保持一致。

可你马上就会发现这个写法的不足：如果要执行超过 3 次操作，难度就大得多。虽然在 C 里我们既可以直接用字面量表达，也可以轻松地把 3 改成 30 或者 300，写起来虽然烦人，但改动本身非常简单；在 Python 里，你就得老老实实把 30 个甚至 300 个数字敲进去。

Python 为此准备的东西叫"范围"——`range`。严格说它不是一个普通的数据类型，更准确地说它是一个函数，你可以调用它生成一个从零开始的一系列数值。所以把那个包含三个值的列表换成一个函数调用，传入你想要的元素数量：

```python
for i in range(3):
    print("meow")
```

按文档，`range(3)` 返回的正是 0、1、2。而 Python 在这方面处理得相当聪明：**它不会一次性返回所有数字**，无论是 3 个、30 个、300 个还是 300 万个，它实际上都是逐个返回的，这样即使迭代次数增加，也不会占用更多内存。想跳着数当然也行——遍历所有奇数、遍历所有偶数、调整递增的步长都可以；只是最标准、最常见的方式，就是这样一个一个地递增。

> **提示**：还有个细节。上面这段我根本没用到 `i`。但这是 Python 语法强制的：使用 `for` 循环时必须为它指定一个变量，来遍历某个列表或数值范围。既然声明了又不打算真的拿来用，不妨干脆把它命名为下划线 `_`：

```python
for _ in range(3):
    print("meow")
```

下划线在 Python 中确实是有效的变量名。这样写是一种符合 Python 风格的做法：既向自己或同事表明"此处声明变量是语法需要，但实际不会用在别处"，又保持了代码的简洁。这是个细微但常见的编码习惯，虽非强制要求，却在实际开发中被广泛采用。

### 先定义，再调用：NameError 是怎么来的

`cat.py` 我们还可以再抽象一层。第 12 版的 C 程序允许我在 `main` 函数中调用一个 `meow` 函数，该函数接受一个参数用于指定"喵"的次数，返回类型是 `void`（它不返回任何值），然后在函数内部用一个 `for` 循环打印相应次数的"喵"。这就是我们在 Scratch 和 C 里自定义函数的方式。

Python 里该怎么实现？关键字是 `def`，代表 define，后面加上函数名和括号：

```python
def meow():
    print("meow")
```

我们先实现一个不需要参数的简单版本，之后再给它加上参数。即使函数不需要任何输入，你也不需要 `void` 关键字。猫是怎么叫的呢？它实际上就是在屏幕上输出"喵"这个声音。

第一遍写的时候，我几乎必然要撞一次墙，屏幕上会出现这样的报错：

```text
line 1   for i in range(3):
line 2       meow()          <<-- called here
line 3
line 4   def meow():         <<-- the name is born here
line 5       print("meow")

=> NameError: name 'meow' is not defined
```

> **定义**：这类错误信息通常被称为"回溯"（traceback），因为系统会沿着代码执行的路径一步步追溯错误的源头，把程序在崩溃前尝试过的所有步骤都摊给你看。如果你调用了一个函数，而这个函数又调用了另一个函数，依此类推，你会在屏幕上看到所有这些函数调用的记录。我这里只是尝试调用了一个函数，所以这份回溯相对较短。

报错说 `meow` 未定义，可它明明就写在下面。这件事即使你第一次接触 Python 也会觉得费解。

因为 Python 虽然在语法上很智能，但处理这件事的时候仍然有些"天真"：它是**从上往下逐行执行**的，在第 4 行之前，`meow` 这个名称都还不存在。你在第 2 行就过早地调用它，当然会出错。

C 语言里我们的老办法是"临时拼凑"：先在文件顶部声明一下（函数原型），再把具体实现挪到下面去。这种做法完全合理，事实上把调用挪到文件末尾，程序立刻就能跑通了。但我觉得这种做法撑不了下去，尤其是当函数数量多起来的时候——你肯定不希望把程序的核心部分、比如这个循环，推到屏幕最底部，毕竟那才是你最关心的内容。C 语言的解决方案是在文件顶部放置函数原型，可这在 Python 里行不通：你不能把第一行代码复制到文件顶部、加个分号，然后指望它能运行。

于是 Python 的解决方式（无论该说好还是不好）是：**把代码放在一个 `main` 函数里**，然后在文件末尾调用 `main()`：

```text
def main():              1. define main first
    meow(3)              2.   it calls meow ...
def meow(n):             3. define meow right below
    for i in range(n):
        print("meow")
main()                   4. only now is main() called
```

读法是：先把 `main` 定义出来（里面的调用此刻并不会执行），再把 `meow` 定义在下面，最后才真正调用 `main()`；到了那个时间点，这两个函数都已经存在了。

这里的 `main` 在 Python 中没有任何特殊含义，这只是沿用其他编程语言惯例、借用它们主函数的命名方式罢了。但这个方案确实有效——这样你就能先定义 `main` 函数，再定义 `meow` 函数。

写完这版我又犯了错。运行，什么都没执行。为什么？因为我压根没调用主函数。在 C、Java、C++ 以及许多其他语言中，`main` 函数是特殊的，根据定义会被自动调用；Python 没有这种特殊的"魔法"，它不会仅仅因为你创建了一个叫 `main` 的函数就自动调用它。我甚至没有把那个主函数命名为 `main`，但这只是约定俗成的做法，解决方案正是如此。

> **注意**：在 C 里我们通常不会在末尾手动调 `main`，但在 Python 中这是常规做法。

> **提示**：最后再补一刀——几乎所有你会在网上看到的文档或 Python 教程，通常都不会让你直接在底部调用 `main()`，而是包一层看起来很奇怪的语法：

```python
if __name__ == "__main__":
    main()
```

这段确实有点拗口，就连我在输入时也得仔细核对，确保所有下划线都正确无误。长话短说：这种在调用 `main()` 前加条件判断的惯例，能让你在 Python 中编写更具模块化的代码——有些文件除了定义函数之外实际上什么都不做，这些定义好的函数可以被导入到你编写的其他文件中使用。写法本身是对的，只不过在 CS50 里我们大概不会真撞上这个场景。

还有个好问题：为什么我在 Python 的函数之间留了两行空行？正如你通过 Style 50 所看到的，在代码中用两行空行分隔函数是 Pythonic 的做法，也就是 Python 的编程规范；相比之下，C 语言中并没有这样的惯例。我正努力遵循这个业界通用的规范。

倒着数行行不行？当然可以，换一种方式使用 `range` 函数就行——从一个较大的数值开始，然后递减计数。你当然也可以用 `while` 循环来实现，虽然技术上可行，但我一般不建议，除非它确实能解决实际问题。

### C 语言里的那些毛病，Python 修好了几个

歇十分钟、今天大家可以随意添菜之后，我们把注意力转到 Python 相比 C 能更便捷解决的问题，以及——有些挑战它并没有解决。

#### 除法的截断

我们早期讨论 C 语言时曾撞上一个奇怪的漏洞：一个很简单的计算器，做除法 `x / y`。当时 1 除以 3 的结果奇怪地显示为 0，4 除以 3 则奇怪地显示为 1，小数点后的部分全部丢失了。即使我们尝试使用浮点数，这个问题依然存在——截断机制会直接舍弃所有小数部分。

那么在 Python 里，这个问题是否依然存在？我们把那个程序改一改，让它执行除法而不是加法，输入 1 和 3，分数结果又回来了。

> **易错点**：在 Python 中，即使你操作的是整数，当一个整数除以另一个整数、结果在逻辑上应该是一个浮点数值时，你拿到的就是浮点数结果。你不需要像在 C 里那样费尽周折地强制转换类型再来一遍浮点运算。

真想要旧版的行为它也仍然存在：用两个斜杠 `//` 就是整数除法，而不是我们现在看到的这种除法。但我敢说，如今的典型程序员大概都希望它的行为方式完全一致。这么看，截断问题对我们来说似乎不那么严重了。

#### 浮点精度

当时我们还遇到了什么问题？浮点数精度。比如即使只是 1 除以 3——小学里我们就知道那是 0.333333... 无限循环——但当时结果的末尾会出现一些奇怪的数字，而不是 3。

遗憾的是，这个问题至今仍然存在。我们用同一个程序，先把结果存进一个叫 `z` 的变量，再用 f 字符串打印出来：

```python
z = x / y
print(f"{z}")
```

现在使用 f 字符串来打印 `z` 的值、而不是直接 `print(z)`，看起来完全是多此一举，但这样能更清楚地展示接下来要用的格式化技巧。结果是 0.333，这里只显示了大约 10 位左右的数字。

如果想查看大约 50 位数字、真正探究一下所表示的内容，该怎么办？语法有点奇怪，但在 Python 中使用 f 字符串时，你可以做一些类似于我们在 C 中使用 `printf` 和 `%f` 格式符的技巧：在花括号中的变量名后面加一个冒号，然后加上一个点号，再指定一个任意的格式：

```python
print(f"{z:.50f}")
```

跑 1 除以 3——真糟糕，我们仍然陷入了和之前一模一样的困境。

> **易错点**：那这是为什么？因为我运行代码的计算机和之前是同一类型，内存仍然是有限的。即使我明确处理的是浮点数，Python 也只分配了大约 64 位给这些浮点变量，精度也就只能达到这个程度了。我们看到的本质上是用二进制浮点数表示法所能表达的、最接近无限循环小数 0.333... 的近似值。

（顺便，那句"咒语"我其实也是偷瞄了面前的笔记。不过格式化字符串确实就是这么用——至少我是这么理解的。）

不过值得庆幸的是，在 Python 中你会发现有更多第三方库和软件可供使用，它们不仅来自语言本身，还来自其他开发者。这些库可以实现更高精度的科学计算，本质上是自定义了浮点数的表示方式，让你在需要特定精度时使用 128 位甚至更多位数，而不仅仅是 64 位。

#### 整数溢出

至少有一个问题已经为我们解决了，那就是整数溢出。当年如果你尝试计数超过 40 亿，或者在有负数表示的情况下超过 20 亿（因为负数会占用正数范围的一部分），我们就会遇到一种情况：数值会莫名其妙地回绕，变成负数，甚至最终变为零。

如今 Python 非常出色地为你提供了越来越多的位数：当你的整数变得越来越大时，它会根据需要动态调整。这是一个非常棒的特性，因为 C 语言里那个根本性的限制，是被语言本身解决掉的。

### 不只靠返回值：Python 的异常

Python 还有一项相当实用的功能，就是所谓的异常处理机制。

在 C 里，返回值是函数向程序员反馈错误情况的唯一途径。如果某个操作出错了，通常的做法是返回一个特殊值——比如最常用的 `NULL`，它就是一个特定的哨兵值，从技术上讲它是零地址 `0x0`，通过检查这个值，你就能确认返回的是不是一个有效指针。而在其他函数中，如果出了问题，你可能同样需要检查返回值，比如检查是否为 0、-1、1 之类的特定值。

> **易错点**：这套办法有个绕不开的别扭。假设你要实现一个函数，它本应返回一个整数，可能是正数、负数或零，有时候这确实不太理想，因为你不得不占用其中一个值来表示"这个值不可用"。在指针的世界里这倒还好，因为业界多年前就约定俗成，永远不会使用实际的地址 `0x0`；但从技术上讲，它仍然占用了你一个或多个字节的空间。总之，如果你的函数无法返回所有可能的值，这就确实有点令人困扰。

以 `get_string` 这样的函数为例：它执行过程中出了问题，应该返回什么值呢？我们在 CS50 里已经见过这个概念——库函数实际上会返回 `NULL`。但一般来说，如果函数能以某种方式"带外"地发出错误信号，岂不是更好？

带着这个问题，我们写一个新程序 `integer.py`，摆弄一下整数。先用最直接的方式判断：

```python
n = input("Number: ")

if n.isnumeric():
    print("integer")
else:
    print("not integer")
```

`isnumeric()` 来自 Python 字符串的文档——字符串不仅包含 `upper()`、`lower()` 等方法，还提供了 `isnumeric()`，用来判断字符串本身是否为数字，也就是说它看起来像是一个数字。如果 `n` 是数字，那就可以断定它实际上是一个整数；否则它可能是 `"cat"`、可能是 `"dog"`、也可能是数字和字母的混合体，但根据本例中十进制数字序列的定义，它肯定不是一个整数。

跑一下：输入 1、输入 2、输入 0，全是 integer；输入 `cat`，not integer。方法确实有效。

但我不想每次都先问一句再转，想直接一步到位地转成整数——那就在赋值时直接指定为整数类型：

```python
n = int(input("Number: "))
print("integer")
```

这里顺便打印一条声明，确认这确实是一个整数：因为如果我们能执行到第 2 行，显然就已经正确处理了用户的输入。

跑一遍：输入 1、2、0 全部正常。输入 `cat`——注意，这次出现了问题。上一次见到这种回溯错误信息，是因为我过早使用了 `meow` 函数名导致名称错误；而这次是一个**值错误**（`ValueError`），含义是 `int()` 函数无法将输入转换为以 10 为基数的整数。这句话确实有点拗口，所以很遗憾，Python 的错误信息在这方面并没有比之前好多少。但显然，解释器不喜欢我传递给 `int()` 的内容——它与 10 进制转换有关，而这里输入的是 `"cat"`。处理这类错误最好的办法就是意识到："cat" 显然不是一个整数，把它转成整数时遇到了问题，这在逻辑上根本说不通。

那问题的核心是什么？在于我只是**盲目地**将用户的输入转换为整数，即使输入的内容根本不是整数。

好吧，那我可以回退到上一个版本，先用 `isnumeric()` 判断然后再转换——但我正试图摆脱这种不断检查函数返回值以确保符合预期的做法。要是能捕获这个 `ValueError` 并在它发生时直接处理，岂不是更好？

Python 的异常处理机制就能做到这一点，其他语言（比如 Java）也有类似的功能：你可以通过异常处理机制来监听函数内部发生的错误，而不仅仅依赖返回值。

```python
try:
    n = int(input("Number: "))
    print("integer")
except ValueError:
    print("not integer")
```

它的语义其实很直白：请尝试执行这两行代码，但如果冒出 `ValueError` 这样的错误，就改去输出"非整数"。你可以理解成"尝试执行这几行代码，除非发生错误，否则就执行其他操作"——这样你就不需要检查任何返回值了。`input()` 的输出可以无条件地直接递下去作为 `int()` 的输入，即使内部出了问题，Python 也会转而执行异常处理那一段。

跑一遍：输入 1，第 2 行代码成功执行，第 3 行代码成功执行，因此第 4、5 行的异常处理代码实际上并未触发。输入 `cat`，第 2 行执行失败，第 3 行永远不会被执行，Python 会立即跳转到异常处理器，抓下这个错误，打印 `not integer`。

```text
  n = int(input("Number: "))
  print("integer")          line 2 fails -> ValueError
                             line 3 never reached
          |
          v
  except ValueError:        line 4
      print("not integer")  line 5
```

> **提示**：这种写法确实有点反直觉，这与我们处理 C 语言的方式不同，但如今许多现代编程语言都采用了这种机制，因为它能更优雅地处理那些在绝大多数情况下应该正常运行的代码逻辑——只有当异常情况真的出现时（内存不足、用户输入错误等等），你才用 `except` 关键字来统一处理这些"异常"状况，而不必让程序直接崩溃。

至于 `except` 后面要不要把可能出错的情况都预先定义一遍——简短的回答是：**是的**。实际上需要处理的情况并不多。有一些标准的异常类型，它们通常采用这种大写格式，首字母大写，比如 `ValueError`、`TypeError`；通常，你甚至可以自定义异常。良好的编程实践是预先枚举你认为自己可能出错的各种情况：`ValueError` 确实很实用，虽然通用，但也可能存在与内存相关的错误，还可能出现文件未找到相关的错误。Python 文档中列出了许多不同的异常类型，你可以根据需要进行捕获处理。

话虽如此，Python 的文档整体上非常出色，但在记录特定函数会抛出哪些异常这件事上却有所欠缺。多年来我一直不理解，为什么始终没有人系统地整理出每个函数可能抛出的具体异常类型，文档中已经详尽列举了所有可能出错的情况。在实际开发中这种情况经常出现——我自己的代码也未能幸免——当你遇到一个意料之外的异常，就需要回头修改代码、在异常处理逻辑中补充对应的捕获子句。不过也有一些第三方库在异常说明方面做得更好。

> **结论**：基于这些考量，我倾向于建议在 CS50 的 Python 库中，为 `get_int` 和 `get_float` 增加更完善的异常处理机制。它们的功能与 C 语言版本完全一致：当你输入 `"cat"`、`"dog"` 或 `"bird"` 这类非数值内容时，这些函数会自动重新提示用户输入，直到你给出有效输入。简单来说，这就是我们在 Python 中编写的代码类型：尝试获取用户输入，若出现异常则重新提示，直至获得有效输入——尽管 C 语言中无法实现这样的功能，我们依然在 Python 中精准地运用了这些特性。

### 同一件事，两种写法

这一讲零散地对照了很多地方，收拾一下放进一张表，方便横向看：

| 想做的事 | C 语言里的写法 | Python 里的写法 |
| --- | --- | --- |
| 判断两个字符串是否相同 | `strcmp(s, t) == 0`，还要 `#include <string.h>` | `s == t` |
| 转成小写 | 调 `tolower` / `toupper` 并递参数 | `s.lower()` / `s.upper()` |
| 复制一份并把首字母大写 | `malloc` + `strcpy` + `toupper(t[0])` + `free` | `t = s.capitalize()` |
| 把整个字符串变成大写 | 循环逐字符调用 `toupper` | `after = before.upper()` |
| 装一组值 | 数组 | 列表（底层是可动态伸缩的链表） |
| 重复 N 次 | `for (i = 0; i < 3; i++)` 写全三段 | `for i in range(3):` |
| 自定义函数 | 顶部声明原型 + 下面写实现 | `def` 定义，调用写在哪儿都行 |

### 三层砖块：把循环用起来

最后回到一个我们都写过的东西：马里奥。几周前我们用 ASCII 艺术字符和一些简单的文本，打印出高度为 3 的金字塔。

在 Python 里该怎么实现？简单得很：

```python
for i in range(3):
    print("#")
```

三层砖块垂直堆叠的效果就出来了。

但在 C 里我们后来写的那个马里奥程序要灵活得多：它会提示用户输入墙体的高度，这样打印出来的不止 3 层，而是 4 层、5 层都行。我们打开第一周写的那个版本看看——在引入了必要的头文件之后，我们在 `main` 函数中声明了一个名为 `N` 的变量，接着用到了一个新结构：`do-while` 循环。它会持续调用 `get_int` 来获取输入，直到用户输入的 `n` 大于等于 1 为止；换句话说，只要 `n` 小于 1，程序就会反复提示用户重新输入。

## 循环、作用域与字典：把 C 的写法搬进 Python
> 对应块：BLK20 | 覆盖分集：P07下 | 块标题（分集名）：《Python 函数、作用域与字典》

### 没有 do-while，只有 while True

Mario 那个程序我们在 C 里写完了。核心是 `do { ... } while (cond);` 这一个结构：先把墙的高度问一遍，问完再判断合不合法，不合法就接着问。

为什么非要用 do-while？因为这个场景有个很具体的要求——**你至少要让用户输入一次**。如果写成 `while (某个判断)` 写在前面，那么第一次进循环之前你就得先拿到一个高度来做判断，而这个高度还不存在。用普通 while 就得先问一句、判断、再决定要不要进循环，代码会绕。do-while 一句话就把这件事说清楚了：至少执行一次操作，并且可能会反复执行多次。

现在把同一件事搬到 Python，问题立刻冒出来了：**Python 没有 do-while**。

只有 `while` 和 `for`，而 `while` 的语法又和 C 基本一样。我们得自己想个办法把"至少问一次"这个语义补回来。

```python
while True:
    n = int(input("Height: "))
    if n > 0:
        break

for i in range(n):
    print("#")
```

几个细节值得停下来看。

第一，`True` 的大写 `T`。这是我第一次把这个循环写出来时自己先绊了一下、然后专门强调一遍的地方。

第二，`n = int(input("Height: "))` 这一行，我们暂时假设用户会老老实实输入一个整数——我暗自希望他们不会输入"猫"或者"狗"。

第三，我们刻意引入了一个**故意无限执行**的循环。它当然会永远转下去，但只要拿到我们想要的答案（一个正整数），`break` 就会立刻把它打断。这就是 Python 风格获取用户输入的方式：先问一次，不满意就继续问。

第四，下面那个打印井号的 `for` 循环，和 C 版本几乎一模一样，只有一处不同：

```python
for i in range(n):     # 不是 for (int i = 0; i < n; i++)
    print("#")
```

C 里那个 `for` 的三段式——初始化、继续条件、每轮之后做什么——在 Python 里被拆成了两件事：`range(n)` 说清楚"转几圈"，循环体说清楚"每圈干什么"。

> **结论**：`do { } while (c);` 在 Python 里的等价物是 `while True:` 配合一个 `break`，先执行再判断的语义靠"无条件进循环 + 拿到就跳出来"手动补上。

不过我第一次把这个程序跑起来的时候，遇到了一件很典型的事。

我顺手把条件也塞进了 `while` 那一行，做成 `while n:` 这样的写法。运行，输入 `2`，回车——程序不动了。我一边敲一边说"是的，我有 2"，然后才反应过来：**所以它并不正确**。

问题在于，Python 的 `while n:` 判断的是 `n` 这个对象本身是不是真值，而整数 `2` 恒为真。于是这个"循环"永远不会结束。

> **易错点**：Python 里 `while 2:`、`while 5:` 是合法的，含义是"永远为真"。整数不会像 C 那样被隐式转换成 0/1 来做真假判断，只有 `None`、`False`、`0`、空容器这类才为假。想写条件就老老实实写 `while n > 0:`。

> **提示**：这其实是 Python 少掉 do-while 之后最省事的一个写法。想强制至少执行一次，套一层 `while True:`，永远比"把条件写两遍"清晰。

```python
# 不推荐：条件写两遍
while True:
    n = int(input("Height: "))
    if n <= 0:
        continue
    break
```

上面这个是"没想清楚"的写法，虽然也对，但读起来是"先无条件进来，再想办法出去"，绕了一圈。我们真正要的形状就是最前面那段：条件短到只有一条 `break`，一眼就知道会停。

### 花括号不管作用域

同一个程序里还藏着第二个值得单独拿出来讲的问题。

看这段代码：`n` 是在第 2 行、`while True:` 的循环体里面赋值的，但第 6 行、循环外面，我们又用到了 `n`。

```python
while True:
    n = int(input("Height: "))
    if n > 0:
        break

for i in range(n):     # n 定义在上面的循环里
    print("#")
```

如果你从 C 过来，第一反应一定是"这不对"。至少从缩进看，`n` 明明待在 `while` 循环的内部，这和 C 里"变量被花括号圈住、超出花括号就没了"的规则是一模一样的。定义在第 2 行，用在第 6 行——这在 C 里过不了编译。

**但在 Python 里这么写完全没问题。** 今天我们讲的作用域这件事，Python 并没有像 C 那样严格框死。

这个设计是有道理的：**如果当前作用域里没有更具体的同名变量，就往上找，找到就用。** 那个 `n` 会被找到，所以在下面的 `for` 循环里照样能用。

还有一个更根本的差别，我在课上也专门点了出来——`n = int(input(...))` 这一行，赋值号左边同时干了三件事：创建这个变量、给它定类型、给它赋值。

> **定义**：Python 的变量不是"先声明、后赋值"，而是**在第一次赋值的那一刻被创建出来**。类型也随之确定。你没有办法只写一个空的声明让它先存在着。

```c
// C：声明和赋值可以分开
int n;
n = 5;
```

```python
# Python：没有这个写法
n          # NameError
n = 5
```

> **易错点**：不要在 Python 里找 C 的"先声明一个变量占位"这种写法。`n` 单独占一行在 C 里是合法的，在 Python 里是 `NameError`。

所以那个"看起来怪怪的"程序，语法上一点问题也没有，而且大概率比你手写一堆声明加赋值还要短。

### 打印：end 参数与字符串乘法

回到之前那个需求：并排打印 4 个问号。这个我们在 C 里已经用循环做过了，现在在 Python 里重做一遍。

最直接的做法：

```python
for i in range(4):
    print("?")
```

跑到终端一看，四个问号各占一行。我们需要的是并排，所以问题出在 `print` 默认每次结尾都会换行。Python 的 `print` 提供了一个名叫 `end` 的命名参数，让你自己指定结尾用什么：

```python
for i in range(4):
    print("?", end="")

print()
```

现在四个问号都在同一行了，但光标停在最后面没有往下走。这在逻辑上很好解决：**在下面加一条空的 `print()`**。不带任何参数的 `print()` 做的事情就是换行。

```python
for i in range(4):
    print("?", end="")

print()
```

> **提示**：`print` 里的 `end` 和 `sep` 都是命名参数，`end` 决定"每次打印完之后接什么"，`sep` 决定"多个参数之间用什么隔开"。传 `end=""` 就是"什么都不接"，连成一片。

引号用双引号还是单引号？官方文档统一用单引号，但从代码风格的一致性出发，我在整个文件里都用双引号。

如果你在学 Python 的过程中发现自己有点极客倾向——我确实看到过有人这么写——还有更漂亮的一种：

```python
print("?" * 4)
```

`"?" * 4` 就是让问号重复四次。这和用加号拼接字符串是同一个思路，只是乘法在这里天然表达了"重复"。

**同一个问题，一个 for 循环版本，一个乘法版本，后者在 Python 里显然更对。**

那如果要在二维空间里做呢？回想我们之前模拟的《超级马里奥兄弟》地下关卡，那个 3 乘 3 的砖块网格。C 里我们用变量 `i` 和 `j` 写嵌套的 for 循环，Python 里的做法是一样的：

```python
for row in range(3):
    for column in range(3):
        print("#", end="")
    print()
```

这里有两条经验。

一条是**教训**：内层循环里不要忘了覆盖 `end`，否则每打印一个井号就换一行，网格会碎成一列。同时每打印完一行又得换行，所以内层循环之后要补一条 `print()`。

另一条是**命名**：我特意把变量名从 `i`、`j` 改成了 `row` 和 `column`。这里同样没有显式的"行"和"列"的概念，但语义上这样命名能让代码逻辑更清晰，让读的人一眼知道自己在做什么。

不过我们还可以更简洁。既然最外层循环固定转 3 圈，而每次要打印的是同一串东西，那内层其实完全不需要：

```python
for row in range(3):
    print("#" * 3)
```

> **结论**：循环打印二维图形时，如果每一行的内容完全相同，就用"字符串乘法"替掉内层循环。代码从 4 行缩到 2 行，而且更好读。

### 列表：len、sum 与 append

接下来是我们真正要展开的东西：列表。

在 C 里，数组有一个很讨厌的性质——**你必须自己记住它有多长**。因为 C 的数组只是内存里连续的一块地方，运行时它并不知道自己几个元素，所以从课程一开始我们就教你，在声明数组的同一行声明一个 `length` 变量，每次往里塞东西都记得 `length++`。

**Python 的列表不需要这样。** 因为在 Python 里，列表是一个**对象**——它不只是数据，它还自带一堆函数。Python 直接把"这个列表多长"和"把这些加起来"这两件最常做的事做成了内置能力。

先看一个我们几周前算过的例子：计算班级里学生的平均测验分数。

```python
scores = [72, 73, 33]

average = sum(scores) / len(scores)
print(f"Average: {average}")
```

小学算术里求平均数就是"全部加起来除以个数"，这里就是这两行。`len` 是 length 的缩写，`sum` 把列表里所有元素相加。跑出来是 `59.3333`，末尾带一点精度上的小数误差，属于浮点数的正常表现。

顺手纠正一下命名：变量名用复数 `scores` 比单数 `score` 准确，毕竟里面装的是一堆分数。

顺便说一句，我把 72、73、33 直接写死在代码里，这其实没什么意思。真正想做的是**让用户自己输入**。

那就得先把列表初始化成一个空的。空列表就是一对空的中括号：

```python
scores = []

for i in range(3):
    score = int(input("Score: "))
    scores.append(score)

average = sum(scores) / len(scores)
print(f"Average: {average}")
```

这里有两件事值得停下来。

**第一，我暂时先让用户输 3 个分数。** 当然完全可以先问"你想输几个分数"，然后用那个数字替掉这里的 `3`——那样就真正做到"不预先决定大小"了。

**第二，也是更关键的一点：怎么把用户输的那个分数放进列表里？**

在 C 里这一步很啰嗦：要用方括号表示法，要记下标，而且还得记得自己已经写到第几个了，否则就越界。

Python 不需要这样。因为列表是个对象，你直接调用**每个 Python 列表都自带的一个方法**，叫 `append`：

```python
scores.append(score)
```

`append` 就是"追加"。它是通过我们之前说过的**点运算符**访问到的：先是变量名，然后一个点，然后方法名，最后把要追加的值作为参数传进括号里。

其余代码一行都不用改。运行 `scores.py`，依次输入 72、73、33，拿到的平均值和之前一模一样——**但这一次，我们没有在代码里预先决定这个列表有多大。**

> **提示**：`int(input(...))` 是这里的固定套路。用户在提示符后面输入非数字内容时，`int()` 会直接抛异常把程序炸掉。严谨的写法应该包一层 `try` / `except` 处理异常，不过为了专注于核心逻辑，我这次先跳过错误检查。真正要写的时候别忘了。

```python
# 严谨一点的版本
try:
    score = int(input("Score: "))
except ValueError:
    print("Not a number.")
    continue
scores.append(score)
```

### 线性搜索：for-else 与 in

现在我们拿一个更完整的例子把前面的东西串起来。做一个电话簿，先从简单的开始——只有名字，暂不考虑号码。

```python
names = ["Kelly", "David", "John Harvard"]

name = input("Name: ")

for n in names:
    if n == name:
        print("Found")
        break
```

运行，搜 Kelly、David、John，都能找到。搜一个不存在的 Brian，什么都不打印。

一个程序什么都不说，其实是很糟的体验——你根本不知道它是"没找到"，还是"根本没去找"。所以这里必须补上"未找到"的分支。

在 C 里你想这么干，要么用一个变量记录"到底找到没有"，要么在函数里提前 `return` 掉。**但 Python 的 `for` 循环可以带一个 `else` 子句。**

```python
names = ["Kelly", "David", "John Harvard"]

name = input("Name: ")

for n in names:
    if n == name:
        print("Found")
        break
else:
    print("Not found")
```

从语义上看这有点奇怪——`else` 怎么会和 `for` 扯上关系？但它的规则很干净：

> **定义**：`for` / `while` 循环的 `else` 子句，只有在循环**自然跑完**时才执行。只要循环过程中执行过 `break`，`else` 就被跳过。

所以这里的意思是：我把整个列表从头到尾走了一遍，一次 `break` 都没调用过，说明真的没找到，那就打印"未找到"。

```text
for n in names:
    if n == name:
        print("Found")
        break          ← 命中走这条，else 被跳过
    # 继续往下遍历
# 循环自然结束（一次 break 都没有）→ 执行 else
else:
    print("Not found")
```

这个模式在实践中非常常见：**在循环里跟踪某个事件是否发生，发生了就 A，没发生就 B。** 这可能是我们在循环相关特性里见过的最独特的设计之一。

不过——既然我实现了线性搜索，总觉得有点重复繁琐。我们能不能做得更好？

**其实可以。**

```python
names = ["Kelly", "David", "John Harvard"]

name = input("Name: ")

if name in names:
    print("Found")
else:
    print("Not found")
```

一行 `if name in names` 就干掉了整个循环。

那 Python 到底怎么判断"这个姓名在不在名单里"？**它内部做的还是线性搜索**——从头到尾遍历整个列表，找到就返回 `True`，走完还没找到就返回 `False`。底层逻辑一点没变。

变的是**你不需要手写那个遍历**。你直接表达你的意思就行。整套代码读起来已经非常接近自然英语了：`if name in names`，然后 `print Found`——这比 C 里的表达直观太多。

> **结论**：`x in 集合` 是一个真正的语言特性，不是一个语法糖。它把"遍历 + 比较 + 返回布尔值"这一整套固定套路收进了运行时。

| 我想做什么 | C 里怎么做 | Python 里怎么做 |
|---|---|---|
| 计数循环 | `for (int i = 0; i < n; i++)` | `for i in range(n):` |
| 至少执行一次 | `do { } while (c);` | `while True:` + `break` |
| 元素在不在列表里 | 手写循环 + 标志位 | `if x in names:` |
| 找出全部匹配项 | 手写循环收集 | `[x for x in names if ...]` |

### 字典：键值对与字符串索引

说完 Python 里的字典对象——准确地说，字典就是**一组键值对的集合**。

我们之前在 C 里见过这种结构图，比如姓名对应号码、姓名对应其他信息：

```text
姓名（键 key）      号码（值 value）
────────────────────────────────────────
  "Kelly"        →   "+1-617-495-1000"
  "David"        →   "+1-617-495-1000"
  "John Harvard" →   "+1-949-468-2750"
```

在 C 里，要用哈希表这类结构在内存里存储大量数据，是一项相当复杂的任务——习题集 5 里让我们自己实现拼写检查，那种痛苦大家都还记得。

**在 Python 里，我们可以自己定义一个字典。** 方括号通常用来表示列表，但我也可以用花括号来开启一个全新的东西：把一系列键值对写在里面。

```python
people = {
    "Kelly": "+1-617-495-1000",
    "David": "+1-617-495-1000",
    "John Harvard": "+1-949-468-2750"
}
```

（我俩都在这儿工作，所以号码先借用了同一个；另外那个 949 的号码打过去或者发短信都挺有意思的。）

> **定义**：Python 的字典**本质上就是一张哈希表**。它让你能把某些数据与其他数据关联起来——在数据结构里，字典是那把瑞士军刀。

这基本上等于用 Python 自己的语法手搓了一张哈希表，前面那张结构图里的每一行，代码里就是一行。

那现在该怎么用它？

用法和刚才判断存在与否完全一样：

```python
name = input("Name: ")

if name in people:
    print("Found")
else:
    print("Not found")
```

`in` 这个介词，Python 理解为**成员关系检查**。键在字典里就返回 `True`，不在就 `False`。

但这样还不够。运行一下，输入 David，屏幕上只显示"Found"——可我真正想要的是那个号码啊。

在 `if` 块里加一行就解决了：

```python
name = input("Name: ")

if name in people:
    number = people[name]
    print(f"Found: {number}")
else:
    print("Not found")
```

这里出现了我们之前没见过的一种写法，但在 C 里处理数组时其实用过——**方括号表示法**，用来索引某个特定的值：`array[0]`、`array[1]`、`array[2]`、`array[3]`。

区别在于：

> **易错点**：数组用**数字索引**，字典用**字符串索引**。`people["David"]` 里的 `"David"` 是一个键，不是一个位置。

具体地说，这里的 `name` 是用户输入的。我输入 David，那 `name` 就等于 `"David"`，`people[name]` 就等价于 `people["David"]`，把对应的号码取出来，存进 `number`；剩下的就是用一条 f-string 把它打印出来。

现在整个程序能用了：输入 David 出号码，输入 Brian 出"未找到"，输入 Kelly、John 也都能出号码。

字典的强大不限于 Python，其他语言也一样——**你可以像索引数组一样索引字典，只是键从数字变成了字符串。** 用如此简洁的语法来查找数据，既实用又强大。

---

### 字典的列表：一张电子表格

其实我们还能做更多。

想一想键值对还能是什么形状，你会发现**键值对无处不在**。比如电子表格——这是一张 Google Sheets 的截图：

```text
┌────────────────────┬──────────────────────┐
│ name               │ number               │
├────────────────────┼──────────────────────┤
│ Kelly              │ +1-617-495-1000     │
│ David              │ +1-617-495-1000     │
│ John Harvard       │ +1-949-468-2750     │
└────────────────────┴──────────────────────┘
```

用过电子表格的人都知道：**每一行代表一条不同的记录**，一个不同的数据片段——这是 Kelly，这是 David，这是 John，以此类推。

而这张表里还缺什么？**元数据。** 现在的模型只有两个属性：姓名和号码。但你可以想象再添加第三列，比如电子邮件地址、家庭住址，甚至任意数量的其他数据。

字典加列表就能表达这个想法。语法一开始会有点怪，但写出来就顺了：

```python
people = [
    {"name": "Kelly", "number": "+1-617-495-1000"},
    {"name": "David", "number": "+1-617-495-1000", "email": "malan@harvard.edu"},
    {"name": "John Harvard", "number": "+1-949-468-2750"}
]
```

读法是这样的：

- 外层的方括号 `[]` 表示这是一个**列表**；
- 列表里的元素是三个**字典**，用逗号隔开；
- 第一个字典有两个键值对：键 `"name"` 对应姓名，键 `"number"` 对应号码；
- 第二个字典多了一个键 `"email"`；
- 第三个字典结构和第一个一样。

注意现在**逗号是在同层的键值对之间做分隔**的。所以如果我有三个人的邮箱，就可以继续往每个字典里加 `"email": "..."` 这样的键值对，因为字典就是键值对的集合——把姓名和 David 关联，号码和号码关联，邮箱和地址关联，依此类推，这完全合乎逻辑。

> **结论**：数据库里的一行数据，本质上就是一个字典；一张表，就是一个字典的列表。Google、微软、苹果这些公司屏幕上那些带图形界面的精美表格，底层写的就是这个结构——等我们开始动手搭自己的数据库时，还会再回到这里。

不过现在有个现实问题：**没法直接查了。** 刚才 `if name in people` 那一行现在不成立，因为 `people` 是一个列表，不是一个字典——名字藏在每个小字典的 `"name"` 键里面，Python 没法直接比。

所以我们还得遍历，但遍历方式稍微换了一下：

```python
name = input("Name: ")

for person in people:
    if person["name"] == name:
        number = person["number"]
        print(f"Found: {number}")
        break
```

每次迭代里，`person` 被依次赋值为第一个字典、第二个字典、第三个字典。我们检查的是"**当前这个 `person` 字典里键 `"name"` 对应的值，等不等于我要找的姓名**"；如果是，就把 `number` 赋值为该字典中键 `"number"` 对应的值，直接打印出来。

**这里用到的语法，全是我们之前在小规模示例里见过的。** 没有新东西，只有嵌套。

而且它的好处立刻兑现了：**想找邮箱地址？把代码里的 `"number"` 改成 `"email"` 就行。想找别的信息？改那一处就行。** 数据加了几列，查询代码改一个词。

顺便回应一个课上提的问题："如果想在屏幕上同时显示姓名和号码，需要把它们拼接起来吗？"

当然可以，你也可以给 `print` 传逗号分隔的多个参数分别打印，或者按任意你想要的格式组织。想怎么排就怎么排。

还有一点关于可读性：我在 `if` 里面专门起了一个叫 `number` 的变量，下一行只用它一次，之后再也不用了——严格说有点多余。技术上来讲，用 f-string 完全可以把右边的表达式直接塞进花括号里，彻底省掉这个变量。

```python
print(f"Found: {person['number']}")
```

但某些情况下，当引号嵌套在引号里时，f-string 会变得有点难以阅读。**所以我个人更倾向于稍微严谨一些：明确地把它放入一个变量，然后只插入这个变量。** 当然你仍然可以用别的方式写。

### 命令行参数：sys.argv 与 sys.exit

讲完了数据结构，我们来给 Python 补几个"库"层面的能力。Python 自带了很多库——即使它们不是第三方库，你也需要**导入**才能使用。不过不用安装，只要一句 `import` 把它们加进你的代码就行。

第一个是 `sys`。它提供访问命令行参数的功能。毕竟由于默认情况下不再有 `main` 函数，我们失去了访问命令行参数的途径——没有 `int main(void)` 这样的结构了。但这些功能并没有消失，只是搬到了 `sys` 库里。

先做一个简单的程序 `greet.py`：用命令行参数来问候用户，而不是用 `get_string` 或 `input`。

```python
from sys import argv

if len(argv) == 2:
    name = argv[1]
    print(f"hello, {name}")
else:
    print("hello, world")
```

`argv` 本质上就是一个列表——用户在命令行里输入的所有参数组成的列表。既然是列表，就可以直接用 `len()` 拿长度，**所以不再需要 `argc` 了**。

运行 `python greet.py`，什么都没多输，得到 `hello, world`。运行 `python greet.py David`，出错了——屏幕上是一段回溯信息。

```text
Traceback (most recent call last):
  File ".../greet.py", line 5, in <module>
    printF(f"hello, {name}")
          ^
NameError: name 'printF' is not defined
```

我哪里做错了？**`printF` 这个写法是不对的。** 我大概是顺手把 C 的 `printf` 拼进来了。这个问题很好解决，删掉就行。

改完再跑 `python greet.py David`，`hello David` 出来了。

但这里有个地方有点奇怪：**我在命令行里输入了 3 个单词，代码里检查的却是 2 个。**

原因是：在 Python 的 `sys.argv` 里，**解释器本身是被忽略的**。不言而喻，你是用 Python 解释器来运行 Python 程序的，所以真正被计入的只有解释器之后输入的那些单词。输入 `greet.py David` 时参数数量是 2，只输入 `greet.py` 时就是 1。

> **提示**：这个"少算一个"的坑几乎人人踩过一次。`sys.argv[0]` 是脚本名本身，第一个用户参数是 `sys.argv[1]`。C 里 argc 会把程序名算进去，Python 这里不算——迁移时记得把下标和计数都对齐。

那**退出状态**呢？最近的 C 程序里我们一直让大家在成功时返回 0、出错时返回 1。Python 里还能这么做吗？

能，`sys` 库也管这个。写一个 `exit.py`：

```python
import sys

if len(sys.argv) != 2:
    print("Missing command-line argument")
    sys.exit(1)

print("hello, " + sys.argv[1])
sys.exit(0)
```

语法比 C 版复杂一点，但我们能做的事完全一样：

- 第 3 行仍然可以访问 `argv`——虽然这次是 `import sys` 整库导入，没有写 `from sys import argv`。我也可以写 `from sys import argv`，但没必要把库里的每个变量和函数都单独列出来。**先给我全部访问权限，稍后我再告诉你具体需要哪些功能。**
- 第 4 行问的是"长度**不等于** 2"。因为如果用户在解释器名称后没有提供两个参数，我就提示"缺少命令行参数"并退出，返回状态码 1。**我不会再默认输出 hello world**——我需要用户提供他们的姓名。
- 如果程序执行到这里还没退出，就打印 `sys.argv[1]` 的值。在我之前输入的例子中这会是 "David"，表示程序成功运行。`sys.exit(0)` 表示程序成功执行。
- 中间那个 `argv` 变量我们其实根本不需要处理。

> **结论**：`import sys` 之后，通过 `sys.argv` 访问列表、通过 `sys.exit(n)` 设置退出码——这两个能力把 `int main(void)` 的作用又还给了我们，而且完全不用写 `main`。

### 写文件：open、with 与 csv.writer

下一个例子：做一个能**持久化保存数据**的电话簿。

#### 先把一行写进文件

前面所有的 Kelly、David、John 都硬编码在代码里，程序一关就没了。这次我们让用户像在 iPhone 或 Android 手机上那样，自己输入姓名和电话号码，然后把它们追加到一个类似 CSV 文件的文本文件里——就是我们之前用过的那种逗号分隔值格式。

Python 自带了一个专门处理 CSV 的库。我们**不需要**通过手动加逗号这种临时拼凑的方式来实现自己的 CSV 支持，直接导入就行。

```python
import csv

file = open("phonebook.csv", "a", newline="")
writer = csv.writer(file)

name = input("Name: ")
number = input("Number: ")
writer.writerow([name, number])

file.close()
```

这跟 C 里几乎一样，只不过把 `fopen` 换成了 `open`，而且：

- `open(..., "a")` 的 `"a"` 是**追加模式**，跟 C 的模式串一个意思；
- `csv.writer(file)` 是在告诉 Python：把这个文件包装成一个可以写入 CSV 的东西，然后交给我；
- `writer.writerow([name, number])` 是一个**方法**——也就是跟这个 writer 对象关联的函数（我知道这一点是因为我确实读了 CSV 库的文档）。参数是一个值的列表，一个名字、一个号码，方括号在这里是告诉 `writerow` "这是两个值"；
- `file.close()` 关掉整个文件。

跑一下，输入 Kelly 和她的号码，回车——它就写进 CSV 文件了。再跑一次，输入我的信息——也追加进去了。再跑一次，John，也追加进去了。**代码量比上次用 C 实现时还少一些。**

不过在 Python 里这么写，其实还不算真正符合 Python 的风格。

问题在于：我不需要一开始就打开文件。先把变量值拿到手，写文件那一段可以放到后面，甚至整个文件都可能一个字节都不写。

#### 用 with 替掉手写的 close

用 `with` 语句就能做到：

```python
import csv

with open("phonebook.csv", "a", newline="") as file:
    writer = csv.writer(file)
    name = input("Name: ")
    number = input("Number: ")
    writer.writerow([name, number])
```

一行代码完成了"以追加模式打开文件并绑定到变量"，执行操作，然后——**一旦缩进结束，无论后面还有没有代码，文件都会自动关闭。**

这在 C 里是做不到的。我们得手动 `fclose`，而且忘记关是常犯的愚蠢错误。这类问题在 C 里通常不易察觉，除非你跑 Valgrind 之类的工具才能检测出来，也就是所谓的内存泄漏。Python 试图用一个新关键字来从根上避免这种情况。

> **易错点**：`with` 的语义确实不太直观，除非你结合上下文理解：**用 `with` 打开文件，出了这个块它就替你关掉。** 在 Python 里请默认使用 `with`，别再手写 `close()`。

```text
with open("phonebook.csv", "a") as file:   ← 进入块：打开并绑定
    writer = csv.writer(file)
    name = input("Name: ")
    writer.writerow([name, number])
# 缩进结束 → 无论块内是否抛异常，文件都被自动关闭
```

#### 表头行：为什么 DictWriter 更健壮

到这里 Python 版已经够好了，但还有一个坑。

**Python 自带的 CSV 模块功能相对基础：它缺少一个能够明确标识每列内容的表头行。**

看现在的 `phonebook.csv`：里面只有 Kelly、我、John 各一行数据。而理想情况下，它应该更接近 Google 表格那一版——首行明确标注"name"和"number"作为表头，用于描述后续数据，之后才是三行实际记录。

最简单的方法是什么？坦率地说，**就是在文件开头直接写一行 `name,number` 作为表头**，然后假设 `phonebook.py` 会不断往后面追加新数据。

> **提示**：我本可以一开始就这样做。这其实比在 `phonebook.py` 里写代码去输出表头行更好——因为如果你反复运行这个程序，你不希望表头行重复出现。除非你把程序稍作复杂化，确保表头只写一次。

既然表头已经在文件里了，那 `phonebook.py` 也可以改进——因为我们**可以利用"表头存在"这个事实**。我的字典写入器能读懂同样的表头信息。

从 `csv.writer` 切到 `csv.DictWriter`（字典写入器）：

```python
import csv

with open("phonebook.csv", "a", newline="") as file:
    writer = csv.DictWriter(file, fieldnames=["name", "number"])
    name = input("Name: ")
    number = input("Number: ")
    writer.writerow({"name": name, "number": number})
```

多出来的那个参数叫 `fieldnames`。我知道这个参数存在，是因为我查了文档——它的值应该是一个列表，包含我们即将写入的 CSV 文件中**预设存在的字段名称**。

关键变化在最后一行。**我们传的不再是列表，而是一个键值对组成的字典**，让字典写入器自己判断这些值应该写到哪一列。

对比一下：

| | `csv.writer` | `csv.DictWriter` |
|---|---|---|
| 额外参数 | 无 | `fieldnames=["name", "number"]` |
| 每行写什么 | 列表，按列顺序排 | 字典，按键名自己找列 |
| 隐含前提 | 默认 name 在第 0 列、number 在第 1 列 | 文件里必须先有表头行 |
| 用户在表格软件里调换列顺序 | 立刻写错列 | 照样正确 |

`csv.writer` 那套其实相当脆弱：它盲目地假设姓名在前、号码在后。**如果有人用 Excel、Google 表格或者任何工具在电子表格里调整了数据顺序，我的代码就崩了。**

而有了表头行、并把表头信息告诉了 dict writer，每个值应该落到哪一列就有了明确的依据——我们**并没有显式指定每个值的位置**，可它就是落对了地方。跑一遍，输入 Kelly 和号码，她的信息就进去了；再跑，我的信息也进去了；最后把 John 也补上（+1-949-468-2750，如果你还没打过电话或者发过短信，随时欢迎联系）。

即便后续再做调整，这段代码的健壮性也强得多。

### 装库：pip、cowsay 与二维码

最后再添些点缀，用上我们之前瞥见过的一类 Python 功能：**安装我们自己选择的库。**

到目前为止，在 CS50.dev 里我们 CS50 团队已经预先安装了你们所需的大部分工具，包括课程最初几周里我写的那个 `cowsay` 程序——它用到了一个我提前装进代码空间的第三方库。

如果你用的是自己的 Mac 或 PC，也可以装到本地设备上，前提是这些库作为开源资源在线可用、并且能从 Python 的代码仓库里获取。**用一个叫 `pip` 的程序就能把 Python 包装进你的代码空间。**

#### 先假装忘了安装

新建一个 `cow.py`：

```python
import cowsay

cowsay.cowsay("This is CS50")
```

屏幕上就会出现一只可爱的小牛图案。

不过我今天"假装"忘了安装它。运行一下：

```text
Traceback (most recent call last):
  File ".../cow.py", line 1, in <module>
    import cowsay
ModuleNotFoundError: No module named 'cowsay'
```

这个错误比我们之前看到的名称错误和值错误都要直观——它明确告诉你：**没有名为 `cowsay` 的模块。**

这正是使用 `pip` 的时候：

```bash
pip install cowsay
```

只要拼写正确、且这个库是公开可用的，按下回车，pip 就会自动下载并安装它。这种情况下它会把最新版本装进你的代码空间，从而有望解决这个问题。再运行一次——**看，最可爱的小牛图案出现了。** 如果把终端窗口全屏，能清楚地看到它确实在说 "This is CS50"。

#### 云端放不出声音

还有更有意思的库，我甚至要换一台电脑来演示。

我准备试试**文本转语音**。这个在 CS50.dev 里做不到，因为它是一个基于浏览器的云端开发环境——**当你在云端运行代码时，音频无法传输到你本地电脑的扬声器上。** 但如果我在我自己的 Mac 上（或者你们自己的 PC 上）跑 Python，音频就真的能从扬声器里出来。

先 `pip install pyttsx3`，然后用经典的编辑器写上这么三行：

```python
import pyttsx3

engine = pyttsx3.init()
engine.say("This is CS50 course.")
engine.runAndWait()
```

第二行是必须的，因为文档说明首次使用这个库时需要先做一次初始化。第三行让它把字符串念出来——**虽然不像 Scratch 那样用图形化的积木呈现，但原理是相似的**。最后 `runAndWait()` 类似 Scratch 里某些积木块的作用：确保整段话完整播报之后，程序才结束运行。

在自己的 Mac 上跑，声音出来了："This is CS50 course."

（语速确实很仓促，但第一次运行的那段长初始化过去之后，反复运行加上优化，完全能让它快得多。）

#### 生成属于我自己的二维码

最后一个库好玩，而且不只是好玩——它能启发你在 Python 里还能做多少事。

大部分人应该都养成过扫二维码的习惯，但你以前生成二维码，多半是随便在网上搜个在线生成器——那些都是别人写好的工具。**我完全可以自己动手，真正生成属于自己的图像。**

先 `pip install qrcode`（这个名字是我在网上查到的），然后写 `qr.py`：

```python
import qrcode

image = qrcode.make("https://youtu.be/xvFZjo5PgG0")
image.save("qr.png")
```

第二行创建一个叫 `image` 的变量，让它等于这个库的 `QRcode.make` 函数（跟 C 里的 `make` 没有任何关系），生成一个包含某节讲座视频链接的二维码。

第三行调用 `image.save` 把这个 URL 保存成一个叫 `qr.png` 的文件。**PNG 就是它的格式**——便携式网络图形（portable network graphics），和 JPEG、GIF 是同类，但特性不太一样。

运行 `python qr.py`，代码空间里就生成了一个 PNG 文件，打开就是一个可以用手机扫的二维码。
