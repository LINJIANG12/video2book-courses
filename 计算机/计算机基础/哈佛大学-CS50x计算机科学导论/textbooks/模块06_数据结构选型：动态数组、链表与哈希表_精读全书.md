### Jack 的箱子

在进入代码之前，我们先看看你在现实世界里几乎一定会遇到的几样东西——栈和队列。如果可以的话，请把灯光调暗一点，营造点氛围。

从前有个叫 Jack 的家伙。说到交朋友，Jack 在这方面可没什么天赋。于是他去找了他认识的最受欢迎的人。

他走到 Lou 面前问道："我该怎么办呢？"

Lou 看到他朋友真的非常苦恼，说道："先看看你穿成什么样。你就没有其他风格的衣服吗？"

### 抽象数据类型：先谈能做什么，再谈怎么存

从更专业的角度说，我们刚才看到的正是所谓的**抽象数据类型**。

它们当然涉及数据结构，但更核心的是其**设计理念**——这些结构提供哪些特性、功能或操作，而不必关心它们在底层实现细节上的具体方式。

这正是我们接下来要反复看到的：队列和栈可以通过多种方式来实现，而这些不同的实现方式，会直接影响你在实际应用中如何使用它们、又能用它们解决哪些类型的问题。所以一个"栈"和一个"队列"到底是什么？它们是行为契约，不是内存布局。

### 队列：先来先服务

队列这种结构，其实你无时无刻不在体验它。每当你去商店，或是参加某个需要排队的活动时，你自然希望这个队列能体现一定的公平性——**如果你是第一个排队的，就应该第一个进入商店**，这样你就能第一个结账，或者实现其他类似的目标。与之相对，最后到达的人自然就排在队伍末尾，因此会在最后才被服务或入场。

> **定义**：队列具有"**先进先出**"（FIFO）的特性。谁先进来，谁就先离开。

对许多需要讲公平的问题来说，这确实是个很好的方案。但更专业地说，队列只有两种操作：

- **入队**（enqueue）：加入队列，从队尾进入；
- **出队**（dequeue）：从队列前端离开。

### 把队列写成代码：容量与大小

那么，队列能不能用不同的具体方式来实现？完全可以。这里有一种在 C 语言中实现队列的方法，适用于需要排队等候的人群。

我们规定这个队列**最多容纳 50 人**，这相当于一个物理容量上限。然后定义一个结构体——我们之前已经做过几次类似的设计：

```c
typedef struct
{
    int people[50];
    int size;
} queue;
```

这个结构体不仅包含一个名为 `people` 的人员数组，数组大小与容量一致（一个能容纳 50 人、大小为 50 的数组）；同时还记录当前队列的实际大小。

> **易错点**：一定要分清**容量**（capacity，队列最多能容纳多少人）和**大小**（size，当前实际排队的人数）。有了 size，我们才知道数组里哪些位置实际上还是空着的。否则你根本不知道队尾停在哪儿。

把这个完整的结构体称为 `queue`。但这种实现和代码有一个必须面对的固有限制——**我看到你点头表示理解了，你对此的第一反应是什么？**

没错：它最多只能容纳 50 个人。如果第 51 个人想要排队，这个数据结构根本没有办法记录他。

那怎么解决？我们可以修改代码，把 50 改成 51、500 甚至 5000，然后重新编译。但这就带来了一个**权衡**：

- 如果上限设得不够高，在极端情况下（比如一场大型演唱会），仍然会低估实际排队的人数；
- 如果你在内存中分配了 5000 个位置，结果只有几个人到场，这些内存就被白白浪费了。

> **结论**：说到底，计算机的内存总量是有限的。你必须在**编译代码之前**就预先决定好这个数据结构要开多大、会浪费多少空间——这挺不合理的。

理想情况下，我们应该能让队列根据需要**动态扩容或收缩**，像上周开始做的那样，直接向操作系统申请更多内存；不再需要时就及时归还。也就是说，我们必须放弃这种"静态意义上的数组"——所谓静态，就是指在编译时就预先确定数据结构的大小。

顺便提一个用数组实现队列的额外麻烦：你得想办法追踪**队首**（队列最前面）的位置。因为一旦开始从队列中移除元素，就必须准确记住下一个该轮到谁。好在这个问题我们完全可以用代码解决。

### 栈：最后放进去的先拿出来

那么，队列的另一种替代方案是**栈**，它具备截然不同的特性。

在之前的动画里，Jack 正是用栈来整理衣物：把衣服一件件放进箱子，每次穿衣时都从最上面取。结果可能就是，他永远只穿得到最上面的那件黑色毛衣——如果他在拿到蓝色或红色毛衣之前就把衣服洗了。

> **定义**：栈具有"**后进先出**"（LIFO）的特性。最后放进去的，最先被取出来。

想象我洗了一堆衣服，然后又往这堆衣服上扔了几件毛衣。那么我很可能会先穿最后放进去的那件，而不是把衣服堆翻得一团糟、硬要从最底下抽出那件来——毕竟直接从最上面拿要省事得多。

所以后进先出有时无法满足你在其他问题中追求的公平性，但它确实能带来**效率**，当然还有**便利**。这或许会很有吸引力。

而且栈实际上无处不在。如果你最近打开过 Gmail 或 Outlook 查看收件箱，新邮件默认会出现在哪里？**最上面**，最上面，还是最上面。我敢说我们都有过这样的经历：那些被挤到下一页的邮件往往就被忽略了。我们总是更关注最新收到的邮件，然后优先回复它们——这对那些邮件的发件人来说可能不太公平，但这就是许多用户界面的默认实现方式，除非你手动调整设置。

从技术层面说，栈需要实现两个核心操作，与"入队""出队"对应：

- **压栈**（push）：把元素添加到栈顶；
- **弹栈**（pop）：从栈顶移除元素。

食堂和餐厅的工作人员整天都在做这件事。任何食堂或餐厅里那些堆叠起来的餐盘架就是典型例子：你总是把第一个餐盘放在最底下，然后依次往上叠放第二个、第三个，以此类推。那么你们所有人会先取用哪个餐盘？当然是放在最上面的那个——因为相比从最底下抽一件毛衣，要从最底下抽出餐盘可要困难得多。

这样一来就可能出现一些不太理想的情况：最底下那个脏兮兮的餐盘可能永远没人会用，因为我们总是在不断补充顶层的干净餐盘。但**正因为有重力作用**，这种结构恰好成了现实世界中分配物品（比如食堂餐盘）最合适的数据结构。

那代码怎么写？说来有趣，我们几乎可以完全照搬队列的思路，采用相同的结构——把 `Q` 改名为栈就行了。说到底，我们需要追踪一定数量的人（虽然用"人"来类比餐盘有点奇怪），既然其他部分都保持不变，那这个命名调整又有何不可呢？

> **提示**：用这种方式实现栈甚至比队列更简单一些，因为你可以始终从数组的**末尾**进行删除操作，而最先入栈的元素——也就是最早进来的那个——可以始终保持在位置 0。

但归根结底，我们虽然可以用这种方式实现，却依然摆脱不了那个恼人的上限：你仍然只能往这个栈里放 50 件毛衣、50 个托盘，或者 50 个人。所以这**仅仅是一种实现方式**，并不意味着栈和队列本身必然存在这样的限制。从抽象的角度看，我们完全可以做得更好——不再静态定义数组的总大小，而是**动态地进行内存的分配与释放**，实现动态的扩展与收缩。

换句话说，通过具体的实现，我们可以让这些抽象数据类型变得不那么抽象。

### 字典：键与值

让我们回顾一个早期接触过的数据结构，或者说抽象数据类型——虽然当时我们可能没有明确地这样称呼它。

**字典**是另一种无处不在的抽象数据类型。它字面意义上就像现实世界中的词典，包含单词及其释义。如果要在黑板上抽象地描绘它，你可以将其想象成一个简单的两列表格：左边是单词，右边是释义。如果是实体书，本质上也是相同的结构——左侧通常以粗体显示多列单词，右侧紧邻着对应的释义。你还可以在电话簿中看到类似的结构，这正是我们在第 0 周课程开始时提到的例子，只不过它是一张由姓名和号码组成的字典。

计算机科学家会进一步概括这个概念：把左侧的内容统称为**键**（key），右侧的内容称为**值**（value）。

> **结论**：这两个概念在计算领域无处不在。从今天开始，到下周乃至未来，你会越来越频繁地遇到它们。如果你需要将一组数据与另一组数据关联起来，所谓的"键值对"或字典，将成为你最常用的数据类型。

即便是字典，也有不同的实现方式，原因和队列、栈一样：如果使用数组来实现字典，其容量可能会受到固定大小的限制；换一种实现方式，查询速度可能非常快；再换一种，运行效率可能比较低。

想想你的 iPhone 或安卓手机——如果苹果或谷歌把通讯录应用设计成基于数组的实现，导致你只能存储 50 个联系人，这种限制显然会令人非常困扰。所以他们很可能采用了更动态的实现方式。这也正是我们今天要真正动手做的东西。

### 先从三个数开始

好，让我们聚焦到第二周介绍的第一种数据结构——**数组**。

我们回忆一下：数组本质上是一块**连续的内存空间**，可以依次存储多个值。这些值在内存中连续存储，并且正如我们所知，通常需要预先确定数组的大小。

例如，假设我们要存储三个数值。在图示上它可能是这样：

```text
  +----+----+----+
  | 1  | 2  | 3  |      连续、紧凑、可以靠 ++ 一个接一个地走
  +----+----+----+
  [0]  [1]  [2]
```

现在让我们用代码实现这个思路，并花点时间思考一下。动手写第一个程序，就命名为 `list.c`。这里我们简单地使用数字 1、2、3 作为示例——你可以想象它也可以是三个人的姓名、三件毛衣、三个人，或任何其他类型的数据。

```c
#include <stdio.h>

int main(void)
{
    int list[3];
    list[0] = 1;
    list[1] = 2;
    list[2] = 3;

    for (int i = 0; i < 3; i++)
    {
        printf("%d\n", list[i]);
    }
}
```

数组的索引从 0 开始，所以第一个值放在位置 0。这个程序本身并不特别实用，但它给了我们一个可以操作的数组示例。编译运行：输入 `make list` 然后回车，程序开始运行，屏幕上显示出 1、2、3。

**但如果现在我们需要调整设计呢？** 比如突然发现需要存储第 4 个数字，或者买了第 4 件毛衣，或者有第 4 个人要排队，又或者想在通讯录里添加第 4 个联系人？

理想情况下，我们自然希望直接把第 4 个值放在内存的下一个位置，这样所有数据就能保持连续存储。你仍然在使用数组，除了长度需要调整，你的代码基本无需改动——这本质上还是相同的实现方式，只是多占用了一点内存空间。

### 内存是一张画布

但请回想一下：**当你声明一个固定大小的数组时，系统只保证分配给你那一块连续的内存空间，从概念上讲，并不会在它的右侧、左侧、上方或下方预留任何额外的内存。**

你可以把计算机的整体内存想象成一张画布，每个位置代表一个字节，而画布上可能已经存储了大量实际数据，或者是一堆随机值（我们叫它"垃圾值"，可以理解成曾经被用过、现在可以再利用的内存）。

在更复杂的程序里，数字 1、2、3 最终可能存储在这块区域上，而如果我在这个程序中也创建了一个字符串，比如 `"HELLO, world"`，它可能恰好紧邻着存储在内存中：

```text
   整片内存就是一张画布，每一格代表若干字节：

   ...  [ 'H' ][ 'e' ][ 'l' ][ 'l' ][ 'o' ][ ... ][ 1 ][ 2 ][ 3 ][ ... ][ ... ]
                         别人的 "HELLO, world"          int list[3]
                                                         右边看起来空着，但那些格子
                                                         不属于你，也不能随便拿来用
```

看，这里还有很多其他内存空间可以使用，那些"垃圾值"目前并未被占用，过去也曾被使用过。但我**不能**简单地把数字 4 塞进紧挨着 1、2、3 的那一格去——如果程序的其他地方还在使用那个字符串，你就是在强行占用不属于自己的内存：你把那个 `'H'` 字节当成了自己的，实际上它并不属于你的数组，改动它只会破坏别人的数据。

那么，如果能把 1、2、3、4 直接放进右边这块空着的内存，岂不是更好？我完全可以做到这一点，但当然，如果我想这么做，就必须**先复制前三个值，然后把第四个值放进去，接着再把不再需要的内存空间归还给操作系统**。

> **结论**：在数组末尾追加一个元素，是一个"复制 + 追加 + 释放"的完整操作，而不是一次赋值。理解了这一点，你就理解了我们接下来要写的那一坨代码为什么会那么长。

### malloc：把数组搬到堆上

让我回到 VS Code 里。既然要添加第 4 个值，就不再是给这个数组**静态**分配内存了——我说的"静态"是指字面意义上的硬编码，也就是在这里永久性地写死数字 3。

让我删除之前静态分配的那个数组，运用过去一周对指针和内存管理的初步理解，先动态分配一块初始估计所需的内存：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *list = malloc(3 * sizeof(int));

    if (list == NULL)
    {
        return 1;
    }

    list[0] = 1;
    list[1] = 2;
    list[2] = 3;

    for (int i = 0; i < 3; i++)
    {
        printf("%d\n", list[i]);
    }
}
```

> **提示**：整数通常占用 4 个字节，但为了保险起见，用 `sizeof` 来精确计算所需的大小。无论 `int` 是多大，这就是我需要的总字节数。理论上应该是 3 × 4 = 12 字节，但我这里用通用的方式来计算。

现在来看这行代码的几个要点。

第一，**`malloc` 返回的是那块内存的地址，也就是第一个字节的地址**。所以我不能在左边写 `int list`；我现在这个 `list` 变量实际存储的是一个整数的地址，声明成指针，把 `malloc` 的返回值赋给它。右边做的事情是：请求操作系统在内存中分配 12 个连续的字节（它们当然可以用数字地址表示，比如 0x123、0x124、0x125）。根据定义，`malloc` 会返回第一个字节的地址，而"分配了 12 个字节"这件事，就得由我自己记住。

第二，**C 语言在某种程度上允许指针和数组的互相转换**。回想一下上周的内容：有时可以把指针当作数组来用。所以我现在可以在这里使用和之前完全相同的语法，写 `list[0] = 1`、`list[1] = 2`、`list[2] = 3`——尽管我用了第四周才学的那行新代码，但之后的语法可以保持不变。

这三行方括号写法其实只是上周所学内容的语法糖。更准确地说：

```c
    *(list + 0) = 1;    // 找到 list 指向的地址，把数字 1 放进去
    *(list + 1) = 2;    // 访问地址 list + 1，把值 2 放进去
    *(list + 2) = 3;    // 访问地址 list + 2，把数字 3 放进去
```

但这看起来太别扭了。即使是经验丰富的程序员，如果可以用更少的按键、写出更易读的代码，通常也不会这么做。就像我最开始那样，直接把这部分内存当作数组来用，功能完全一样，但简洁明了得多——计算机本质上会执行必要的指针运算，来决定 1、2 和 3 该放在哪里。

所以，虽然这看起来像是上周刚学的新知识，但其实和我们上周捣鼓的那些东西完全一样。唯一的区别是：现在这块内存不再由编译器替你安排在栈上，而是由你自己在运行时向操作系统申请。

### 手写一次扩容

假设过了一段时间，我意识到——为了剧情需要——哎呀，糟了，我需要的不止 3 个整数了。

当然，我完全可以删掉所有代码，把 3 改成 4，重新写一遍，重新编译，再运行。但我想提议的是：让程序在**运行时**能够动态调整实际需要的内存大小。

想想这个场景：如果你认识了一个新朋友，想把他加到通讯录里，你显然不会愿意为了多存一个联系人，就等着苹果公司重新编译通讯录应用，还得重启手机。你希望程序能直接向操作系统申请更多内存，用来存储这个新联系人。

那我就直接这样写：

```c
    list = malloc(4 * sizeof(int));
```

我不需要重新声明 `list`，因为它已经在上面存在了——但这样做是有问题的。我在第 13 行做错了什么？我浪费了第 5 行分配的所有内存，因为我实际上已经**丢失了它的地址**。

> **易错点**：如果 `list` 指针就像一个泡沫手指，指向内存中的某个位置，那么上面这句话的实际含义是"现在让它指向这里"——而原来那块内存里 3 个整数的踪迹，就彻底丢了。这正是我们上周讨论过的**内存泄漏**，Valgrind 之类的工具可以帮你发现这类问题。如果不修复它，随着时间推移，计算机和程序最终会变得越来越慢。

单方面改变主意，直接说"不，不，不，忘了那块内存吧"当然不行。给我一块新的内存，特别是当你需要把旧内存中的数据复制到新空间时。

那该怎么做呢？**临时变量**通常是我们首选的解决方案——每当我们除了已有的信息外，还需要额外记住某些内容时。按照惯例，我给自己定义一个临时变量，就叫 `temp`：

```c
    int *temp = malloc(4 * sizeof(int));
    if (temp == NULL)
    {
        free(list);   // 先把第一块还回去，再报告错误
        return 1;
    }

    for (int i = 0; i < 3; i++)
    {
        temp[i] = list[i];   // 把旧列表复制到新列表中
    }

    temp[3] = 4;              // 再加上第四个值
```

这几行代码的作用就是：通过循环把 1、2、3 复制过去，然后第 20 行这里暂时只是添加了第四个值。

> **注意**：这种写代码的方式其实不太高明——既然要把 4 放进去，一开始就该直接处理。我只是假设程序运行了一段时间后，中途改变了主意，想让用户往内存里添加一些值而已。

但在继续之前，我们得先修正一些其他错误。上周我强调过一条铁律：**每次使用 `malloc` 之后，你应该总是检查返回的指针是否为 `NULL`**。如果返回 `NULL`，通常意味着内存分配失败——比如内存不足或其他问题。如果不做这项检查，你的程序很可能会崩溃，并出现我们之前简单提到过的**段错误**。

这确实会让代码看起来臃肿很多，但这是良好的编程习惯。

> **易错点**：注意第二次 `malloc` 失败时的处理顺序。如果我在第二次分配失败后直接 `return 1`，我首先还应该回过头去释放第一块内存。因为如果第 5 行执行时一切正常（意味着第一个指针不是 `NULL`），那我就已经成功获得了一块存 3 个整数的内存，而这块内存在第 19、20 行时**依然存在**。释放那个原始的指针，就是告诉操作系统"这是还给你的内存"。

> **提示**：严格来说，这一步其实并非必要——一旦程序本身退出，计算机就会自动将内存归还给操作系统。所以当程序退出时，内存泄漏问题会随之消失，但你的代码仍然存在缺陷。通常我们运行的软件并非只运行一瞬间，而是会持续运行数分钟、数小时甚至数天；在这种情况下，及时清理这些内存才是最佳实践。**先释放、再返回**这个顺序，是让你永远不会真正遇到内存泄漏问题的习惯。

好，我们继续深入一点。复制操作完成后，我们同样需要释放原始那块内存。但在释放之前，要记住**新列表已经接管了数据**——这是我们第二次分配内存时创建的内容。所以，尽管这个程序变得有点长，请注意我刚才的操作顺序：先释放 `list` 原本指向的那块区域（里面装着 1、2、3），然后让 `list` 这个变量指向新内存块（里面装着 1、2、3、4），而不是原来的位置。

```c
    free(list);
    list = temp;
```

滚到代码底部，我把手动的 `3` 改成 `4`，这样就能证明我已经成功存储了全部 4 个值；然后在程序最后，再次释放 `list` 指向的内存——因为现在 `list` 的泡沫手指已经指向了那块更大的内存区域——最后 `return 0`。完整的程序长这样：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *list = malloc(3 * sizeof(int));
    if (list == NULL)
    {
        return 1;
    }

    list[0] = 1;
    list[1] = 2;
    list[2] = 3;

    for (int i = 0; i < 3; i++)
    {
        printf("%d\n", list[i]);
    }

    // 变主意了：改成能容纳 4 个整数
    int *temp = malloc(4 * sizeof(int));
    if (temp == NULL)
    {
        free(list);
        return 1;
    }

    for (int i = 0; i < 3; i++)
    {
        temp[i] = list[i];
    }
    temp[3] = 4;

    free(list);
    list = temp;

    for (int i = 0; i < 4; i++)
    {
        printf("%d\n", list[i]);
    }

    free(list);
    return 0;
}
```

让我重新打开终端窗口，编译这个版本。**看来我在这里犯了不少错误。** 我们往上滚动，查看第一次调用未声明的库函数 `malloc` 的地方。

我到底哪里做错了？或者我漏掉了什么？

——在标准库头文件 `stdlib.h` 中，`malloc` 函数实际上是在那里声明的。那我们赶紧把它加上。`make list`，再运行，1、2、3、4 全都显示出来了。

到目前为止，我们只是写了一个小得不能再小的程序：先为三个整数分配内存，然后改变主意，分配了四个整数的内存，把前三个复制过去，加上第四个值，然后释放原来那块。

**但这个过程确实有点繁琐。** 让我们提出一个改进方案：回到 VS Code 里的 `list.c`，你会发现至少那个复制循环其实并不是必需的——更不用说我们已经有了一个专门用来打印的循环。

### realloc：把搬迁这件事交给标准库

其实还有一个函数我们上周没讲到，它就在 `stdlib.h` 里，叫做 **`realloc`**。

顾名思义，它是用来重新分配内存的，但它比你自己写的那一坨更聪明：

- 如果你现有的内存块**末尾正好还有空间**，它会尝试直接在原处扩展——效率非常高，你只需要把第四个值放到末尾；
- 如果那个位置刚好没空间（可能是因为程序的其他地方已经存了 `"Hello, world"` 之类的数据），它会在内存的其他地方重新分配一块更大的空间（这次是原来大小的 4 倍，而不是 3 倍），**然后自动帮你完成所有的复制工作**。

所以最终你得到的结果是：一个指向新内存块的指针，其中包含了所有原始数据。

```text
  情况一：原块后面正好有空间 —— realloc 就地扩展，指针根本不用变

      0x100  0x104  0x108  0x10C
       [ 1 ]  [ 2 ]  [ 3 ]  [ 4 ]          ← 1 2 3 一个字节都没搬

  情况二：原块后面被别人占了 —— realloc 另开一块，并把数据全搬过去

      0x100  0x104  0x108  0x10C  0x110  0x114
       [ 1 ]  [ 2 ]  [ 3 ]  [ HELLO, world ... ]
      0x200  0x204  0x208  0x20C  0x210
       [ 1 ]  [ 2 ]  [ 3 ]  [ 4 ]          ← 返回值指向这里

  情况三：整个内存里没有连续的 4 个字节可用 —— realloc 失败，返回 NULL

      这里剩 3 字节    那里剩 2 字节    另一个地方剩 1 字节
```

我们**仍然需要检查返回的指针是否为 `NULL`**：如果过程中出现问题，我们仍然需要释放原始那块内存，然后 `return 1`。我们**仍然需要添加第 4 个值**，因为 `realloc` 并不知道我们还想在列表中存入什么数据。但我们可以**删掉那个复制循环**了，因为它的唯一作用就是把旧数组中的所有整数复制到新数组中——而这正是 `realloc` 已经替我们做过的事。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *list = malloc(3 * sizeof(int));
    if (list == NULL)
    {
        return 1;
    }

    list[0] = 1;
    list[1] = 2;
    list[2] = 3;

    for (int i = 0; i < 3; i++)
    {
        printf("%d\n", list[i]);
    }

    int *temp = realloc(list, 4 * sizeof(int));
    if (temp == NULL)
    {
        free(list);
        return 1;
    }
    list = temp;
    list[3] = 4;

    for (int i = 0; i < 4; i++)
    {
        printf("%d\n", list[i]);
    }

    free(list);
    return 0;
}
```

好，先暂停一下，大家有什么问题吗？

#### realloc 怎么知道该搬哪一块、搬多少？

第一个问题问得很好：realloc 是如何知道它应该在原内存块的基础上进行重新分配的呢？它难道不应该先检查一下之前分配的那块内存吗？

——那是因为我在代码里写了一个 bug，而我们没发现它（因为我没编译这个版本的代码）。问题的答案是：**你需要告诉 realloc 你想重新分配的那块内存的地址**。也就是说，realloc 的第一个参数——我确实传了——就是那块内存的地址。你只需要传入之前通过 `malloc` 分配的那块内存的地址，realloc 才知道该去哪里检查。

而"它怎么知道要复制多少数据"这个问题，答案也在同一个地方：把它理解成标准库（`stdlib.h`）吧——**标准库会记录你之前分配的内存情况**。当你传入相同的地址时，它会通过一张查找表（或者你可以理解成一张字典）来查到已分配的内存信息，这样你就不需要操心这些细节了。

#### 为什么不直接写 list = realloc(...)？

原因和之前一样：**必须用临时变量**。

因为如果直接写成 `list = realloc(list, 4 * sizeof(int));`，一旦出问题，realloc 会返回空指针——但**它不会释放原来的内存块**。这样一来，我们就丢失了指向原始内存块的指针，再也找不到它去打印、修改或者释放它了。整块内存就此泄漏。所以我们必须在这个中间步骤上使用 `temp`：只有当 `temp` 拿到了有效的新地址之后，我们才敢让 `list` 指向它。

#### 为什么最后 free 的是 list 而不是 temp？

这个问题也很好。让我把代码翻回刚才的位置。

当我们给 `temp` 添加了第 4 个值之后，我继续释放了 `list`——此时 `list` 仍然指向最初的那块内存，也就是存着 1、2、3 的那块。然后我进行更新，把 `list` 这个变量指向新的内存块。接着我打印出其中的所有整数，然后释放 `list` 当前所指向的内存。

所以，严格来说，我并没有多次释放同一块内存地址，因为在这期间我已经移动了指针。

那么在这里直接使用 `temp` 是否正确？在语法上当然没错，`temp` 仍在作用域内，它确实指向同一个东西。**但我倾向于认为这在语义上是错误的**：因为在这个代码节点上，真正需要关注的变量是 `list`。`temp` 本质上是一个用后即弃的临时变量——如果它在超出程序员预期的范围之后还被继续使用，很容易引发问题。想象一下你的同事也这么操作：天知道在这段时间里，他对那个临时变量做了什么改动。

### 这些问题在别处已经有人解了

好，这部分内容确实不少。在其他编程语言中，你并不总是需要声明数组的长度——下周要讲的 Python 就是一个很好的例子。这是因为发明那种编程语言的人，已经替你写好了所有这类代码。

事实上，我们第 5 周和第 6 周之间的过渡目标之一，就是展示**所有这些问题的解决方案依然存在，只是不再需要你我亲自动手去实现了**。我们正站在巨人的肩膀上——那些聪明人不仅创造了新代码，还发明了新的编程语言、新的编译器，或者像我们即将看到的，为这些语言开发了解释器，从而把所有这些底层细节隐藏起来。

说实话，正如你已经看到的，仅仅为了在 Python 中讨论数字 1、2、3、4，就需要写这么多行 C 代码，这确实挺烦人的——在那边我们可以精简到大概两行，甚至一行。没问题的。

所以我们今天的目标之一，就是要展示：**实现这些数据类型其实有很多种不同的方法**。

让我们更具体地谈谈所谓的"数据结构"——它指的是**如何利用计算机内存来组织和存储数据的具体定义**。通过使用数据结构，你可以实现栈、队列、字典，以及其他各种数据结构。

> **结论**：你并不需要每次都亲自实现所有这些结构。但当你使用 Python、Java、C++ 或其他语言的功能时，你通常是在**选择他人已经编写好的数据结构实现**，从而直接享受其功能和特性带来的便利——比如我们之前讨论过的先进先出或后进先出——而无需自己深入底层细节。

### 三个你已经用过的运算符，以及一个新箭头

目前我们已经掌握了 C 语言的一些新语法，今天我们将再补充一个重要概念。

上周我们学习了 `struct` 关键字，这个知识点我们已经接触了好几周：每当我们想要创建自定义的数据结构时，都可以直接使用 `struct` 关键字来实现。

之前我们已经学过：

- 可以使用**点运算符**（`.`）访问结构体内部的成员，比如获取一个人的姓名或电话号码；
- 上周还学习了**星号运算符**（`*`）的用法——解引用指针，即通过地址访问实际位置，例如进入结构体内部。

令人欣喜的是，今天我们将看到，在某些情况下，你可以把这两个运算符**合并成一个由两个字符组成的运算符**：

```c
    (*n).value = 1;    // 先解引用指针进入结构体，再访问成员
    n->value = 1;      // 一个字符的等效写法
```

这个运算符看起来就像一个箭头，它恰好呼应了**过去几周我们在屏幕上绘制的那些黄黑相间的图示**——那些用箭头指向特定位置的示意图。这个实实在在的箭头符号，代码将与这一概念完全对应。

### 当内存不再连续：链表

那么，让我们来介绍数组的第一个替代方案。

> **结论**：数组的问题在于其大小是静态固定的——它在分配时就被限定为特定大小，可能是 3 个元素，也可能是 4 个元素，但总归是个固定值。这就会带来问题，因为看看我们之前写的那些代码，我们就不得不反复为数组重新分配空间。

那如果我们尝试**预先规避**这种麻烦，直接构建一个通过链接组合而成的列表会怎样呢？这样无论数据存储在何处，都能将它们连接起来，让数据摆脱"所有元素必须连续存放"的限制。

这个想法其实有非常具体的动机：就像我刚才提到的，如果计算机在内存的不同位置都有可用空间，这些空间的总和完全足够，但其中**没有任何一个连续区块能单独满足数组所需的大小**，那该怎么办？至少我们应该尝试利用所有可用的内存，把数据结构拼接起来，而不是固守数组必须连续紧密排列的限制。

这就是**链表**。它利用上周学到的语法，加上今天的一些新知识，在同样的内存画布上构建出来。

为了便于讨论，假设我们想在链表中首先存储数字 1。我们都知道，为了讨论方便，这个数字很可能存储在类似 0x123 这样的地址中——总之它就在内存的某个位置。

现在假设你还想存储第二个值，但一开始没有考虑到这一点，所以没能像这样聪明地安排：紧挨着 1 存放，下一个值再紧挨着它。通过 `malloc` 或类似函数，你可以把数字 2 存放在别的地方，比如地址 0x456（仅为举例说明）；同样地，这里也有空间存放数字 3，比如地址 0x789。

```text
  内存画布上现在是这样的：

  0x123  [ 1 ]                    0x456  [ 2 ]        0x789  [ 3 ]
         ↑                                ↑                     ↑
     相隔很远、字节间隔各不相同，所以不能靠 ++ 一个接一个地跳过去
```

那么，如果我们想解决"从一个值走到下一个值"这个问题呢？

做法是：**与其只为每个数值分配一个字节，不如稍微"浪费"一点内存**——为我们的数据关联一些元数据。数据就是你关心的那个值；元数据是帮助你维护你所关心的数据的数据。

于是我们为每个值分配两块内存，使得每块内存的顶部代表我们真正关心的数值 1、2、3，而我为每个值分配的第二块内存，可以作为一个**指针，指向下一个值**。如果这是链表的末尾，我们可以用老朋友 0x0，也就是空指针（`NULL`），并默认将其视为链表的结束。

```text
  list ──┐
         ▼
      +---+------+        +---+------+        +---+------+        +-------+
      | 1 | 0x456 ──────►| 2 | 0x789 ──────►| 3 | 0x0   ────────►| NULL  |
      +---+------+        +---+------+        +---+------+        +-------+
       0x123               0x456               0x789
         │                   │                   │
      ┌──┴──┐             ┌──┴──┐             ┌──┴──┐
      │数据 │ │← 元数据    │数据 │ │            │数据 │ │
      │  1  │ │  下一个    │  2  │ │            │  3  │ │
      └─────┘ └──┬────────┴─────┘ └──┬────────┴─────┘ └──┬────────┘
                  ▼                   ▼                   ▼
  （图示并非按比例绘制：int 通常是 4 字节，指针在技术上占 8 字节，
    我们只是把它们画成简单的方块，看起来更美观）
```

尽管这些节点在内存中的位置可能是任意的，但通过在每个值旁边存储下一个值的内存地址——这就像创建了一张**藏宝图**，或者一条**面包屑路径**——我们就能从一个节点走到另一个节点。

> **定义**：我们开始使用"**节点**"（node）这个术语。它只是一个通用的结构体，包含数据和元数据，通常包括你关心的数值，以及一个指向下一个节点的指针。

那么，这究竟意味着什么呢？谁会真的在意 0x123456789 这个地址呢？我们可以把它想象成一幅带箭头的示意图。

为了追踪这个包含三个值的链表，我建议我们还需要引入一个额外的变量——我把它也叫 `list`，在这个变量中**存储一个指针**，指向第一个节点的地址。为什么呢？因为第一个节点可以引导我找到第二个节点，第二个节点又能引导我找到第三个节点，依此类推。

这样做有什么优势呢？如果我想在屏幕上的某个位置添加第四个值，我可以把它放在这里、这里、这里，或者任何有足够空间的地方，只需要确保更新箭头，让它指向下一个数据块即可。**无需复制数据。** 1、2、3 现在可以一直保留在那里，直到程序退出（并且我们确实会释放它们），而我们可以不断添加、添加、再添加，在内存中扩展这个数据结构。

> **提示**：这个结构你其实并不陌生——这正是 Python 中的 `list` 在底层的样子。在 C 里我们习惯把"能自动扩展和收缩的数组"叫做 `vector`，但本质上两者解决的是同一个问题，只是实现策略不同。而链表，就是把"数据在哪儿"这件事和"数据有几个"这件事彻底解耦了。

### 把节点写成结构体

实现这类功能的代码是怎样的？让我来介绍一下我们熟悉的朋友——之前几周我们提到过，每个人物都有一个名字和一个与之关联的编号。我们知道，从技术上讲，C 语言中并没有"字符串"这个关键字，所以实际上它只是 `char *name` 和 `char *number`，但概念是相同的。这就是我们之前定义的 `person` 结构体。

现在我需要实现与这些节点对应的代码：每个节点包含一个整数，以及一个指向下一个同类值的指针。

我建议删除这个结构体内部的内容，将名称从 `person` 改为 `node`——这又是一个用于表示"值的容器"的通用术语。然后，在这个新的 `node` 结构体中直接放入一个 `int` 类型来表示我们真正关心的数值（这里将存放我的 1、2、3 或 4）。然后——这部分有点新内容——让我们在这个结构体中包含一个指向下一个同类节点的指针：

它是一个指针，从概念上讲就像是一个箭头，指向下一个节点的地址，所以这里我们使用 `node *` 来表示。我可以随意命名它，但从语义上讲，将其命名为 `next` 非常合理，因为它指向下一个同类节点；不过由于一些恼人的技术原因，命名为 `next` 并不完全正确，所以我们改用一个不会撞名的说法。

另外还有一件事：从技术上讲，我需要给这个结构体起一个**临时名称**——我们之前还没有这样做过——所以这里要明确写上 `struct node`：

```c
// 定义一个节点类型
typedef struct node
{
    int value;
    struct node *next;
} node;
```

> **易错点**：为什么指针那一行必须写成 `struct node *`，而 typedef 出来的名字明明就叫 `node`？因为 **C 语言和编译器是按从上到下、从左到右的顺序读取代码的**。编译器在读到花括号内部那一行的时候，还从来没有见过 `node` 的定义，这个名称在字面上还不存在，所以代码根本无法编译。我们之前在函数中也遇到过类似的情况，解决方案是一样的：把"先用到、后定义"的东西往前挪。于是有两种写法——要么在文件更靠前的位置先声明一次 `struct node;`，要么干脆像上面这样，在定义处保留 `struct node` 这个标签。你也可以把这看成和"把函数原型放在文件更靠前的位置"是同一种做法。

好，现在我们已经把这段代码写好了，就可以开始尝试在内存中实际存储这些数据了。让我们切回代码窗口，不再使用基于数组的实现方式，而是来实现我们的第一个链表——我会稍微激进一点，基本上把所有内容都放在 `main` 函数里完成。

顺便提一下，现在引入 CS50 库。这倒不是因为字符处理功能，而是**正如我们上周讨论的，它在获取整数、字符串等方面仍然非常实用**——除非你使用 `scanf` 函数，否则这些操作会变得相当麻烦和繁琐。

```c
#include <stdio.h>
#include <stdlib.h>
#include <cs50.h>

int main(void)
{
    node *list = NULL;
}
```

按照惯例，在花括号内部我们为每个这样的节点分配一个数字，并为每个节点设置一个指向下一个节点的指针；整个结构我们统称为"节点"。

而在 `main` 函数内部，让我们一步一步地来。创建链表的第一步应该是：它初始时应该是**空的**。那么——我该怎么表示一个空链表呢？

```text
  空链表：没有任何节点，"从第一个节点出发"这件事要有个说法

      list
        │
        ▼
      NULL            ← 0x0：没有第一个节点，也就没有第二个、第三个
```

答案就藏在上周学过的内容里，也藏在这一讲更早的地方：链表的末尾用 `0x0` 表示，而如果连第一个节点都还没有，那个"第一个节点的地址"自然就是 `0x0`。一个 `NULL` 指针，就是一条零长度链表的完整表示。

> **承前启后**：上一节讲完「动态数组、realloc 与链表」，下一节接着讲「链表：一个指针撑起一整条链」。

## 链表：一个指针撑起一整条链
> 对应块：BLK16 | 覆盖分集：P06中1 | 块标题（分集名）：《链表的结构与操作》

那链表到底是什么呢？按定义讲，**链表其实就是链表中第一个节点的地址**。就这么一句——这就是第一个需要留意的细节。

### 链表到底是什么

我们可以把变量命名为 `list`，并将其设置为 `null`。那链表的数据类型是什么呢？回想之前展示的那张示意图，实际上我们只需要一个指针就够了：在最左侧，用一个指针来表示链表中第一个节点的地址。我敢说，我们只需要声明 `list` 的类型为 `node *` 即可。

```text
node *list;

        list
          │
          ▼
  ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
  │ number │ next │──▶│ number │ next │──▶│ number │ next │──▶ NULL
  └───────────────┘   └───────────────┘   └───────────────┘
        节点 1              节点 2              节点 3
```

这样一来，我脑海中浮现的图景里就没有其他节点了——它只是给了我一个初始化为空值的单一指针。链表里那些节点并不住在 `list` 里面，它们各自在内存里别的地方，`list` 手里攥着的只是"第一个在哪儿"这一个地址。

一个节点要占多少字节？末尾（数值字段）占 4 字节，指针占 8 字节，很可能是 12 个字节。但**这重要吗？用 `sizeof` 就能得到答案**。结构体才是决定申请多少内存的唯一因素，别把 12 记成什么必须背下来的常数。

现在，为了与之前的例子保持一致，我们同样重复执行某个操作三次。那么，在这个与前例结构完全相同的 `for` 循环中，我们开始进行内存分配：

```c
for (int i = 0; i < 3; i++)
{
    // 为新节点分配内存
    node *n = malloc(sizeof(node));

    if (n == NULL)
    {
        return 1;
    }

    // 存入用户输入的数字
    n->number = get_int("Number: ");

    // 先把 next 设为空
    n->next = NULL;

    // 前插：接到链表开头
    n->next = list;
    list = n;
}

return 0;
```

具体该怎么做呢？我可以使用我们新认识的朋友 `malloc`，分配一个节点所需的内存空间。`malloc` 会交回这块内存的地址，我建议用一个临时变量来存放它，把它命名为 `n`，类型就是 `node *`——因为它将指向一个节点。

#### 第一行赋 NULL 到底做了什么

这是第一行代码，即使还没有赋值操作。如果你只是声明一个名为 `list` 的变量，它是一个指向节点的指针，那么本质上你得到的内存空间就像这样：

```text
[ list | 垃圾值 ]
```

不过，它是一个**垃圾值**——因为没有赋值操作，所以没人知道这个指针里到底存了什么。

这就是为什么在我的实际代码中，我将其设置为 `null`。这实际上在内存中创建了同样的存储空间，但去掉了那个垃圾值，并放入了 `null` 值。这样我们就知道它不是垃圾值，而是一个被称为 `null` 的指针。

#### malloc 交回来的那块内存里躺着什么

接下来我要做的是**为一个完整的节点分配足够的内存，而不是为一个节点指针（`node *`）分配**。我希望在内存中获得一整块矩形的存储空间，`malloc` 将返回该内存块首字节的地址，我会把这个地址存储在一个名为 `n` 的临时变量中。

那么在这个阶段，`n` 本身也会成为一个指针，它最初也是一个存储单元。它最初会是一个随机值，但由于我使用了赋值运算符，它将指向 `malloc` 函数（如果成功执行）在计算机内存中为我分配的那块内存空间。因此，无论从哪个角度看，`n` 都指向同一块内存区域。

但这块内存里的**内容仍然是随机值**，因为它只是一块未经初始化的内存空间。谁知道它之前被用来存储过什么数据呢。正因为如此，在这行代码之后，我特意从用户那里获取了一个整数输入，然后将 `next` 指针初始化为空值。

为了方便讨论，我们暂时不考虑 `get_int` 函数的具体实现，假设用户最初输入了数字 1。这相当于先将 1 放入 `n` 的地址，从而将其存入 `number` 字段。然后分别使用星号和点运算符进行解引用操作，这意味着沿着指针找到目标位置，然后将 `number` 的值修改为 1。接着，`n->next` 将 `next` 设置为 `null`，这就相当于访问 `n`，沿着指针找到 `next` 字段，并将其修改为 `null`。

至此，我们已经分配了节点，并在其中存储了数值 1 和指针 `null`。**但链表仍为 `null`**——本次操作的核心目标是把节点接入链表，现在还没做到。

#### list = n：语义上别扭，但完全正确

最终我会执行类似 `list = n` 这样的操作。从语义上看这似乎有点奇怪，但请记住 `n` 是一个指针。它指向的是地址 `0x123`（或实际分配的地址），因此要让 `list` 指向同一个节点，就相当于执行 `list = n`，这样我们就能让 `list` 的箭头（与 `n` 完全相同）指向那个新节点。

```text
执行 list = n 之前：

  list ──▶ NULL
  n    ──▶ [ 1 | NULL ]      ← 新节点已经建好，但和链表没关系

执行 list = n 之后：

  list ──▶ [ 1 | NULL ] ──▶ NULL
  n    ──▶ [ 1 | NULL ]      ← n 和 list 指向同一块内存
```

此时，我甚至不再关心 `n` 本身是什么了。它原本就只是一个临时变量。**现在，这就是我的链表。**

### 箭头运算符：-> 和 (*n). 是一回事

`n->number` 与 `n->next`，读作"访问节点 `n`，分别指向其数值字段或下一个节点字段"。

它其实**完全等同于**先解引用 `n`、再访问其内部成员——只是每次都这么写实在太麻烦了：

```c
// 完整写法
(*n).number
(*n).next

// 箭头运算符
n->number
n->next
```

> **结论**：箭头运算符 = 星号（解引用）加括号，再配合点运算符。

> **提示**：这里为什么非要那个括号？因为运算符优先级。如果写成 `*n.next`，点运算符的优先级高于星号，含义会变成"先访问 `n` 的 `number` 字段，再解引用那个整数值"——完全不是我们想要的。括号不是装饰。

所幸，C 语言的语法与我们之前绘制的图示完全吻合：`n->number` 表达的正是"访问 `n`，沿着指针找到 `number` 字段"。

### 前插的顺序，写反了就泄漏

在继续讲解第 2 轮和第 3 轮之前，先停一下。假设我们针对第 2 轮和第 3 轮再分别操作两次，我们又回到了分配新节点的那一行，新内存块出现了，`n` 指向它；然后访问 `n` 所指向的内存块，顺着箭头找到 `number` 字段并设为 2；再找到 `next` 字段设为 `null`。到这里都和第 1 轮一模一样。

**然后问题就来了。** 如果我把 `list` 更新为指向 `n` 所指向的同一个节点，注意接下来会发生什么——**我丢失了指向原节点的箭头**。

```text
第 1 轮结束后：  list ──▶ [ 1 | NULL ]

第 2 轮里，如果先写 list = n：

  list ──▶ [ 2 | NULL ]      ← 头指针被改写
         节点 1              ← 程序里已经没有任何东西指向它
```

我让第一个节点变成了孤节点。我造成了重复：两个指针短暂地指向了同一块内存，随后其中一个被覆盖。这个东西，尽管我们作为人类显然还能看到它，但**在代码中我们已经失去了对它的追踪，这意味着它已经成为了一个内存泄漏**——在程序本身最终退出之前，我永远无法取回那块内存，也无法将其归还给操作系统。

所以，我觉得需要更聪明一点，暂时先不要这样写这行代码。我已经回退到之前的状态，现在 `list` 仍然指向原始链表，而 `n` 只指向新节点。

#### 顺序：先接旧链，再改头指针

```text
第 1 步：n->next = list

  n    ──▶ [ 2 | ·  ] ──────┐
  list ──▶ [ 1 | NULL ] ◀───┘     新节点先挂到旧链表前面

第 2 步：list = n

  list ──▶ [ 2 | ·  ] ──▶ [ 1 | NULL ] ──▶ NULL
  n    ──▶ [ 2 | ·  ] ──▶ [ 1 | NULL ]
```

关键操作是：**将这个指针指向现有链表的首节点**。如果现有链表指向这里，那就意味着让这个指针指向完全相同的目标——因为现在我可以安全地更新链表了，让它指向与 `n` 相同的目标，这样它的箭头现在就指向这里。但**即使我移除了 `n`，整个链表依然完美地连接在一起**。

注意我们并没有改动数字 1，却成功把数字 2 加了进来。我们稍后可以继续添加数字 3，你可能已经看出这个模式的走向了。尽管这些节点在内存中可能分布得比较分散，但由于这些指针的存在，我可以从一个节点跳转到另一个节点，从而更高效地利用计算机内存中的所有资源。

#### 爆米花串：绝不能松开链条的任何一部分

我常常联想到一个比喻，就像**圣诞节期间，古时候人们会把爆米花串在一起那样**。你在这里用一根线串起它们，使得一个能引导你找到下一个，再下一个，再下一个——但你**绝不能松开这条链的任何部分**。

绳子的一头系在衣架上（那就是 `list`），每颗爆米花上写着数字，每颗爆米花还拖着一根短线指向下一颗（那就是 `next`）。你把新买的爆米花塞到最前面，重新把线系紧——一颗都不许掉。

> **易错点**：这两行的顺序不可交换。必须先 `n->next = list`，再 `list = n`。写反了就丢掉旧链，泄漏一个节点。

### 遍历：再借一根泡沫手指

既然建好了链表，接下来自然是想办法遍历它，把内存里的值打印出来。为此我们再引入一个临时变量，简称它为 `PTR`——**这就好像多了一个泡沫手指，指向链表的起始位置**。

```c
node *ptr = list;
while (ptr != NULL)
{
    printf("%d\n", ptr->number);
    ptr = ptr->next;
}
```

**它并不是指向 `list` 变量本身，而是指向 `list` 所指向的那个节点。** 这就好比我们临时用另一个泡沫手指指向链表中的第一个元素。

虽然语法对我们来说还比较陌生——毕竟我们上周才刚刚开始接触内存操作的相关内容——但它表达的就是同一件事：

- 设置一个循环条件：只要 `ptr` 不为空，就继续执行循环体中的操作；
- 打印当前节点的值，用 `printf` 和格式字符串 `%d` 沿路走一遍；
- 把 `ptr` 更新为 `ptr->next`，也就是当前节点 `next` 字段里存着的那个地址。

具体在内存里跑一遍：

```text
list ──▶ [ 3 | 0x456 ] ──▶ [ 2 | 0x789 ] ──▶ [ 1 | NULL ]

ptr = list          ptr = [ 3 | · ]      打印 3
ptr = ptr->next     ptr = 0x456          打印 2
ptr = ptr->next     ptr = 0x789          打印 1
ptr = ptr->next     ptr = NULL           循环终止
```

最后我把 `ptr` 更新为指向 `next` 字段的值，也就是 `NULL`，这意味着 `ptr` 本身变成了 `NULL`，从而**巧妙地让循环终止**。

顺便提一下，如果你更喜欢 `for` 循环的写法，本质上这里并没有什么新内容：

```c
for (node *ptr = list; ptr != NULL; ptr = ptr->next)
{
    printf("%d\n", ptr->number);
}
```

我完全可以用 `for` 循环来实现同样的功能，这样可以在一行里表达大量逻辑，写起来更紧凑。但**坦白说，我确实认为第一个版本（`while`）的可读性反而更强**——它的"看一步"和"走一步"分成两行，你一眼就知道指针什么时候动。课程网站上这两个版本你都会看到，`while` 那个在逐步执行的操作上略显繁琐，但胜在好懂。

> **结论**：`for` 和 `while` 在功能上是等价的——你能用其中一种循环实现的功能，用另一种循环同样可以实现。

> **易错点**：别把 `ptr` 指向 `list` 变量本身。`ptr = &list` 得到的是"链表变量住在哪儿"，而不是"链表头节点住在哪儿"，那会立刻跑飞。正确写法就是 `ptr = list`，因为赋值会把指针**值**复制过去。

### free 并不认识链表

节点是我们用 `malloc` 一个一个申请来的，用完就得还回去。所以要遍历链表，把每个节点都释放掉。

**但释放整个链表并不像直接调用 `free` 那么简单。** `free` 并没有那么智能——它根本不知道什么是链表，也不了解你的数据结构具体是什么。**即便你调用了 123 次 `malloc`，最终也必须真正调用 123 次 `free`。** 你不能只是把链表的开头传给它，然后指望它知道该删除什么。

所以这个循环之所以有点复杂，是因为这三行代码本质上是在**遍历我的链表**，并且确保我始终有一个指针指着下一个：

```c
while (list != NULL)
{
    node *tmp = list;   // 先记住下一个
    list = list->next;
    free(tmp);
}
```

走一遍你就明白了：

```text
手里：指针 → 节点1     另一根手指 → 节点2
       释放节点 1， 手指挪到节点 2
       释放节点 2， 手指挪到节点 3
       释放节点 3， 手指挪到节点 4
       释放节点 4， 手指空了，结束
```

这里需要一些技巧，以确保在逐步操作时不会遗漏任何节点。如果先释放再取 `next`，那根手指当场就断了——**必须先把下一个节点救出来，再放手**。

> **易错点**：顺序不能反。先 `list = list->next;` 再 `free(list);` 释放掉的是**下一个**节点，链表里会留下一个野指针。

### 头插的复杂度账本

好，现在我们回过头来算账。这里有一份常见（但并非详尽）的运行时间速查表。我们先从最简单的几种链表操作谈起：插入一个数字、搜索一个数字、遍历链表，以及删除一个数字。

我的链表最初是完全空的。假设我现在要插入数字 1，接着插入数字 2，然后插入数字 3——用的就是我们刚刚编写的这段代码。我非常喜欢这种方法，因为**尽管它乍一看可能有点吓人，但这可能是实现链表插入最简单的方式了**。为什么？因为我只是不断地在链表头部插入下一个元素，一个接一个地前插，这意味着我所有的操作都集中在链表的开头部分。

| 操作 | 头插实现的复杂度 | 为什么 |
| --- | --- | --- |
| 插入 | O(1) | 全部动作都发生在最左侧的几个指针上 |
| 搜索 | O(n) | 最坏情况目标在链表末端 |
| 遍历 / 打印 | O(n) | 要访问全部 n 个元素 |
| 删除 | O(n) | 最坏情况目标在链表末尾 |

**为什么插入是 O(1)？** 严格来说，它并非只需一步操作，但确实只需要**固定数量**的步骤。逐行数一遍：先分配内存，判空，填 `number`，把 `next` 指向 `list`，最后把 `list` 更新为 `n`——搞定，整个过程就完成了。**我当前的代码完全不关心这个链表的整体长度**，因为在执行插入操作时，我完全不需要遍历整个链表。即使这个链表有 1000 个元素，我也只是在最左边改动一些指针，所以速度非常快。

**为什么搜索是 O(n)？** 嗯，没错。这确实是个关键问题，因为在最坏的情况下，目标元素可能位于链表的最末端——而我们之前已经遇到过这种情况了。所以搜索是 O(n)。遍历或打印整个链表的时间复杂度显然也是 O(n)，这很好理解：如果你想打印每个元素，自然需要访问所有 n 个元素。删除同理，最坏情况下目标在末尾，所以也是 O(n)。

> **结论**：只有插入操作（按当前的前插实现）是 O(1)，因为我们可以完全控制新元素的插入位置，而不受元素实际值的影响。搜索、删除、遍历**全部是 O(n)**。

这种方法的缺点在于，**整个链表的输出顺序完全是倒过来的**——完全没有对这些元素的顺序做任何处理。

> **易错点**：可别看到"倒序"就慌着去"修复"。每次插入都插在头部，最后一个插入的自然离头最近，这就是前插的直接后果。

### 尾插，以及更有用的插入位置

那么，我们还能用什么其他方法来构建这个链表呢？或许我们可以将新元素添加到链表的末尾。让我们试一试，看看是否能带来更好的效果。

```text
从空链表开始：

  插入 1     list ──▶ [ 1 | NULL ]
  插入 2     list ──▶ [ 1 | · ] ──▶ [ 2 | NULL ]
  插入 3     list ──▶ [ 1 | · ] ──▶ [ 2 | · ] ──▶ [ 3 | NULL ]
```

这样很棒，因为现在碰巧它完美地按顺序排列了——但**这只是因为我选择了 1、2、3**。现在插入操作的大 O 时间复杂度是多少？**O(n)**。这实际上反而更差了，因为现在它总是要跑到链表末尾。

现在我可以稍微聪明一点来处理这个问题：我可以再分配一个指针，让它**始终指向链表的末尾**，就像我已有的那个指向链表开头的指针一样。如果你愿意多用一个指针，这完全没问题——这点开销微不足道，确实是个可行的方案。但我想探讨的是另一种思路。

无论用户以何种顺序输入数字——无论是 1233212、13、3312 还是其他任意顺序——我们都要始终保持链表的有序排列。我想构建一种数据结构，使得数据始终能保持有序排列。就像 iPhone 或安卓手机里的通讯录那样，无论怎么操作，联系人都会按照预设的顺序自动排序。那我们该如何实现这个功能呢？

这里我们仍然需要考虑时间复杂度的问题。让我们在纸上画图来试：

```text
插入 2        [ 2 ]
插入 1   →    [ 1 ] ──▶ [ 2 ]
插入 4   →    [ 1 ] ──▶ [ 2 ]       [ 4 ]
插入 3   →    [ 1 ] ──▶ [ 2 ] ──▶ [ 3 ] ──▶ [ 4 ]
```

尽管用纸笔画图来拼接这些节点看起来相当直观，但现在这个逻辑步骤的数量变得相当烦人了，因为过程中有**太多地方可能出错，导致一个或多个节点被孤立**。

#### 四个独立的小问题

关键的一步是换一种提问方式：不要问"怎么维护有序链表"（问题定义不明确），而是问"新节点可能要落在哪"。

答案是四个位置，而每个位置其实都是一个独立的小问题：

1. 链表为空——直接让头指针指向新节点，完事；
2. 新值比最小值还小——前插，我们已经知道前插极其简单；
3. 新值比最大值还大——后插到末尾，走一遍链表找到尾节点；
4. 新值介于中间——**最麻烦的情况**，但此时"最小"和"最大"都已经被排除，剩下的只能是它。

**现在你只需要解决四个独立的小问题，而不是一个庞大复杂的整体难题。** 而第 4 种（插到中间）需要同时维护新节点和它的前驱，是要动两次指针外加跳出循环的——这里先按下不表，习题集里再逐步推敲。

#### 从 list.c 到 list9.c：九个版本

我们把这段代码写了一遍又一遍。我先打开一个**预先准备好的程序版本**——就像 Julia Child 的烹饪风格那样，先端出一个虽然一开始可能有些小问题、但最终能提供一个可运行解决方案的版本。

这个版本的开头部分和我们之前一模一样：相同的头文件引用、相同的结构体定义、相同的 `main` 函数、链表初始化为 `null`，插入三个值 1、2、3，然后分配节点、判空、填数值、把 `next` 设为 `null`，最后执行前插操作。接着打印这些数字——这就是我们上次停下的地方。这个版本已经放在课程网站上，方便大家参考。

往下滚动，除了新增的注释外，你会看到我现在开始做一些判断了。顺便提一句，我其实**并不需要严格地把 `next` 指针字段初始化为空值**，因为就像我们之前所有例子中做的那样，最终我都会更新这个指针字段。不过，由于这个节点现在可能会被放在链表的末尾，为了编程更稳健，我倾向于在准备好赋值之前，先将指针初始化为空值。**总的来说，这是个好习惯。**

然后是第一个问题：**如果我正在插入新节点的这个链表是空的**——那么这就是整个过程的起点，非常简单，只需将链表的头指针指向这个新节点的地址，就完成了。这和我们之前插入数字 2 时的情况是一样的。

如果链表非空，程序就会执行到这里。我们先采用简化方案：暂时将这个新节点追加到链表末尾。这里我使用了一个 `for` 循环，能让我遍历现有的链表——无论链表里有一个节点还是多个节点。接下来我要进行一个判断：**如果当前节点的 `next` 字段指向 `NULL`，也就是链表的末尾**，那么我们就将链表的末尾更新为这个新节点。

```text
从 [ 2 ] 出发插入 1：

  ptr ──▶ [ 2 | NULL ]        next 指向 NULL，说明走到尾了
         把这里的 next 改成新节点

  ptr ──▶ [ 2 | ·  ] ──▶ [ 1 | NULL ]
```

这和之前完全一样，但这次我是在**确认自己确实已经到达链表末尾的情况下**，有条件地执行它。

这个版本只负责将节点添加到链表末尾。它仍然没有按顺序处理数据，但**我们已经看到了其中两种情况的处理方式**：链表要么为空，要么已有数据而我们需要末尾添加。

再往后就是那个更完整的版本了。如果链表为空，就按之前的方式直接把它设为链表的头节点。如果待插入的数字应该位于链表开头——也就是新节点 `n` 中的数值**小于当前头节点的值**——那么就将新节点的 `next` 字段指向现有的链表，然后将链表头指针更新为指向这个新节点：

```text
[ 2 ]  插入 1，因为 1 < 2

  插入前：  list ──▶ [ 2 | NULL ]
  n->next = list
  插入后：  list ──▶ [ 1 | ·  ] ──▶ [ 2 | NULL ]
```

如果它不是链表中唯一的元素，也不属于链表的开头，那么它必然属于链表中靠后的某个位置——这引出了最后两种可能的情况。用 `for` 循环遍历链表，如果指针变量最终变为 `null`，说明我们已经遍历到了链表末尾，这时候执行前面那个 append 代码。中间那种情况则需要动两次指针和一个 `break`，才能把数字正确插进两个节点之间。

> **提示**：这部分代码今天先简化掉，但"更仔细地逐步推敲这个过程"正是习题集里会要求你做的事。因为这些指针的微调非常繁琐，而且**操作顺序确实至关重要**。

### 写这套代码时踩过的坑

**我的天，我们光是实现数字 1、2、3、4 就已经写了 80 行代码了**，而且目前这里面还有一些不易察觉的 bug。

#### 每次 malloc 都要判空

这基本上是一种样板代码，每次使用 `malloc` 时都应该养成这样的习惯：如果 `n` 等于 `NULL`，我们就无法继续执行了，直接返回 1。哪怕只是返回一个指针，也必须检查。

#### 中途失败，前面分配的谁来还

举个例子，假设在这个 `for` 循环内部，`malloc` 出现了问题，而且这还不是第一次循环迭代——可能在第二次或第三次循环迭代时出了问题。为什么我这样实现后，这个错误检查突然就出问题了？

**因为我没有释放前一次迭代中分配的内存。** 如果你想实践我一直强调的原则——释放所有已分配的内存——而你已经分配了一个，甚至可能两个节点，因为 `malloc` 再次失败，也许是在最后一次迭代这里，你就必须回头去释放所有这些内存。

这本身没问题，我文件底部那段代码可以遍历整个现有链表并一次性释放所有内存，所以我可以直接复制粘贴那段代码，把它加进去。

#### 复制粘贴是设计发臭的信号

但**到了需要复制粘贴代码的地步，很可能说明你的做法有问题**。

所以让我提出最终版本作为参考——这是第 9 个也是最后一个版本，文件版本号从 0 开始计数。我快速复制代码，粘贴到 `list9.c` 里。现在我的函数中实现了卸载逻辑：我在主函数里已经自行实现了一个 `unload` 函数，这样我既可以在主函数开头调用它，也可以在结尾处调用它。

从程序设计规范的角度来说，就是**单独实现了一个删除链表的函数**。这样一来，我就可以在任意位置、任意多次地调用它了。

> **易错点**：`free` 不是递归的，不会顺着 `next` 往下走。释放链表必须自己写循环；指望 `free(list)` 一劳永逸，是在泄漏。

### 动态的代价：用空间换什么

有同学问了一个非常好的问题。我一直在强调，我们不想造成内存泄漏，不想造成内存泄漏，但在这里，我其实相当"奢侈"地使用了**双倍内存**来维护这个数据结构。

这将成为我们讨论所有数据结构时都会涉及的一个核心主题：**如果你想获得一些好处，比如数据结构的动态增长和收缩，你就必须付出一些代价。** 在这种情况下，代价就是需要允许我使用更多的空间。

我们确实希望这些算法能运行得更快。嗯，这没问题，但你也需要相应地付出一些代价——你需要消耗更多的空间来换取代码运行速度的提升。因此，**时间、空间、财务成本、人力时间以及其他各种资源，都是作为程序员或管理者需要权衡的因素**，你需要判断哪些对你来说最不重要，或者最重要。而目前，相较于空间开销，我更关注的是要解决动态性问题。

回到那个 `list9.c`。现在来思考一个问题：经过以上所有步骤，向链表中插入节点的运行时间复杂度是多少？他们通常会说是 O(n)。**真是的，这样看来并没有更好啊。** 搜索链表呢？还是 O(n)，真是的。从链表中删除节点呢？也是 O(n)。

所以你看，基本上**所有操作的时间复杂度都是 O(n)**。这就是我们突然要付出的代价。

而且我敢说，尽管我们今天没有实际操作，也不会在今天完成，但**通过释放不需要的节点，我们同样可以实现链表的动态收缩**。因此，我们获得了动态性，并且能够更高效地利用内存——即使内存变得非常碎片化，这里几字节、那里几字节。

但我们为此付出了代价。回想之前的电话簿例子，我们至少还能用二分查找，运行时间是 O(log n)。而现在是 O(n)。**天啊，我们不仅占用了更多空间，这玩意儿还变慢了！**

显然，我们的手机通讯录肯定不是这样实现的。显然，栈和队列也肯定不是一直这样实现的。

> **结论**：链表换来的是动态性——不必提前决定大小、只在需要时分配、收缩就是释放节点；付出的代价是搜索、插入、删除全部退化成 O(n) 的线性复杂度，以及更零碎、更难回收的内存布局。

> **提示**：另一个被问到的问题——为什么用 `ptr` 而不是复用 `n`？我可以在这一步复用 `n`，程序也不会出错。我特意选择新变量主要有两个原因：其一，在这里使用它出于不同的考虑；其二，在一个地方用变量实现特定功能后，又在下面复用同一个变量名，这种做法未必是最佳选择，况且它此时已经超出作用域了。不过用不同的变量处理不同的任务，会让我感觉更清晰。

顺带一提，被问到的另一个问题也很重要：**`ptr` 本身是临时的吗？** 不一定。我们正在内存中构建链表，这个数据结构之所以能存在并保持完整，是因为我们使用指针来构建它，并且**只要程序在运行，它就会一直存在**。在这个例子中，我的临时变量 `n` 和 `ptr` 确实是临时性的，我只是暂时用它们来把各个部分连接起来。

### 为什么二分查找救不了链表

数组的速度来自哪里？来自**连续存储**。连续存储意味着我们可以做非常简单的算术运算：先算出数组的长度，然后除以 2 得到中间位置，再除以 2 得到四分之一位置，以此类推。尽管可能需要处理一些四舍五入的问题，但数组非常适合二分查找。

链表呢？虽然我们最新实现的这个链表是按从小到大排序的，而这正是执行二分查找的前提条件——但**即使我们人眼能一眼看出中间位置大概在那里，计算机要如何确定这个位置呢？**

#### 找到中点本身就是 O(n)

遗憾的是，我们通过指针将链表连接起来的方式存在一个局限：**虽然可以找到中间节点，但你必须从头开始遍历整个链表来确定其长度，然后根据计算出的中间位置再遍历一次，在到达一半位置时停止。**

```text
4 个值的链表，binary search 找 6：

  ① 数长度：   1 → 2 → 3 → 4        从头走一遍，知道 n = 4     O(n)
  ② 算中点：   n / 2 = 2
  ③ 走到中点： 1 → 2               再从头走一遍，走一半停下     O(n)
  ④ 想在右半边继续二分：把整个过程再重复一遍                     O(n)
```

一层一层地重复，**即便只是想使用二分查找，光是找到中间节点就已经花掉了 O(n)**。

> **结论**：**排序并不能把链表的搜索变成 O(log n)。** 有序只是前提，而找到中点这个动作本身就要线性时间。

#### 那我记一个中间节点的指针行不行

这想法完全没问题——你可以额外占用一些空间来记录链表的起始、中间和末尾位置。**但这样做的边界在哪里呢？**

如果进行二分查找时，你不仅需要定位中间节点，还需要进一步找到中间节点的中间节点，甚至更深层的中间节点，该怎么办呢？**难道要为每个元素都维护一个指针吗？** 因为如果这样做，本质上就又回到了数组的形式——如果每个位置都需要对应一个独立的存储地址。

即使我们确实可以做一些微小的优化，但整体上还是会逐渐变得混乱不堪。

#### 双向链表：让代码好写一点，不改速度

我们目前使用的就是**单向链表**，它通过节点之间的单一指针进行连接。计算机科学家也经常讨论**双向链表**，这种链表的指针可以双向移动：

```text
单向：  [ 2 | • ] ──▶ [ 1 | • ] ──▶ NULL

双向：  [ 2 | ⇄ ] ⇄ [ 1 | ⇄ ] ⇄ NULL
```

这能简化我们之前看过的一部分代码，因为我不需要提前查看下一个节点来决定要释放哪个节点，或者在哪个位置插入新值。**但这本质上并没有改变运行速度，只是让代码编写起来稍微容易一些。**

### 数组的长与链表的短

好，我们回来了，让我们来回顾一下我们是如何走到这一步的。

数组是第 2 周的老朋友。它的魅力在于**相对简单**——当然现在回头看更是如此——但更重要的是，**它的速度确实非常快**。就像数组那样，它们的元素是连续存储的，连续存储意味着我们可以进行非常简单的算术运算，从而实现对数级别的时间复杂度 O(log n)。

但数组有一个实打实的缺点：**你必须提前决定它的大小。** 如果你估计错误，申请的内存太小，那就必须重新分配内存。虽然这也能通过 `malloc` 或 `realloc` 解决，但把旧内存中的所有数据复制到新内存需要花费时间。**无论你是用 `for` 循环手动复制，还是让 `realloc` 自动处理，这个过程都无法避免。**

目前我们处理的只是 3 个或 4 个值。但想象一下，如果 300 万个值需要重新分配更多空间，你将浪费大量时间把 300 万个值从旧位置复制到新位置。**这种做法通常并不理想。**

链表则相反：**只在需要时才分配内存**，从而避免预先分配过多空间的问题。我们无需担心内存分配不足或过剩导致浪费，只需为每个新节点分配一块内存，整个结构就能持续动态扩展。节点一旦分配就可以保持原位，只需更新指针即可——我们避免了把数据在内存中搬来搬去的效率损失。

代价，就是前面反复出现的那句：搜索、插入新元素、删除旧元素的运行时间都达到了 O(n)。

> **结论**：**使用链表能带来动态性**——现在我们可以在不浪费时间去复制数据的情况下，动态地扩展或收缩数据结构。然而，我们也因此**失去了二分查找的能力**——这种能力从第零周开始就非常吸引人，因为它能让我们快速完成某些操作。

### 下一站：树

确实不是。这只是一个过渡步骤，接下来我们要**将不同数据结构的优点结合起来**——取数组之长，补链表之短，融合创造出更新、更优的数据结构。就像拼凑成一个弗兰肯斯坦式的数据结构，看看我们能否既获得数组的速度优势，又保留链表的动态特性。

因此，我向你们介绍**树**。想象一下家谱的样子：通常会有父母、子女、孙辈等等，层层延伸。

```text
                  grandparent          ← 根（root）
                 /          \
           parent              child
             |
        grandchild
```

这是一种树状结构，尽管按照惯例它是**自上而下**绘制的，而不是像现实中的树木那样自下而上生长。家谱的顶端我们称为树的**根节点**——它恰好是向下生长的。

树是一种非常常见的数据结构，有趣的是，相对于数组和链表而言，**它是我们遇到的第一个二维数据结构**。数组本质上只是一个从左到右的单维结构；链表本质上也是如此，尽管在内存中它的实际分布可能上下左右都有，它仍然只是在单一维度上连接在一起的结构。

**树结构引入了第二个维度**，对我们特别有用的是**二叉搜索树**——剧透一下——它将让我们重新获得使用二分查找的能力，但我们会以一种比单纯使用数组更巧妙的方式来存储数据。

```text
7 个数字，连续存放：

  [ 1 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ][ 7 ]
              ▲
              第 1 跳：正中间

  [ 1 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ][ 7 ]
                          ▲
                          第 2 跳：右半边的中间
```

如果我对这些数字（或者几周前我们在舞台上展示的那些储物柜）进行二分查找，我会先跳到中间，然后是中间的中间，依此类推。

**但关键在于实现方式。**

## 数组链表之辩与哈希表：一次不断逼近常数时间的努力
> 对应块：BLK17 | 覆盖分集：P06下 | 块标题（分集名）：《数组链表之辩与哈希表》

### 数组插入之痛，和一个二维的想法

如果我要往数组里追加一个新值，会发生什么？

运气好的时候，8、9、10 往末尾一放就完事了，内存恰好还留着空位。可运气不好呢？那就得走那套繁琐的步骤：要么重新分配一块内存，要么把已有的数据全部复制到新位置上去。**这当然可行，但确实很麻烦。** 前面我们在代码里解决过这个问题，可数据集一大，这就慢得离谱。

那能不能不这么干？

> **提示**：我特意用这样的颜色编码是有原因的。问题的答案，往往就藏在讲师把哪一块涂成了醒目颜色的地方。

如果换一种存法呢？不要把这七个数摆成一条直线，而是按一种家谱的样子竖着挂起来——像一棵沿 y 轴展开的树。

讲义上的这七个数，4 在最顶上。4、2、6 曾经是"一维数组里的中间元素"，现在 2 和 6 分别挂在 4 的左右两侧；再往下的那些节点，我们借用了现实里树的名字，叫**叶节点**——它们自己没有子节点，处在数据结构的边缘，是一层层二分找下来的终点。

> **易错点**：叶节点只是没有子节点，**数据一个都没丢**。它们不是被裁掉的残余，而是"查到这里就不用再往下走了"的位置。

数据结构从一维变成了二维。而我们前面已经掌握了指针，是时候把指针用在更复杂的地方了。C 语言里指针用箭头表示，我打算用一串指针把这七个数串起来。为了讲清楚，先把每个节点简化成一个方框：它不再只装一个整数加一个指针，而是最多装两个箭头指向的指针。于是节点结构从**「一个数值 + 一个指针」升级为「一个数值 + 两个指针，分别指向左子节点和右子节点」**。

### 二叉搜索树：把问题一次砍掉一半

现在，在这样一棵二维的树里，怎么找一个数？假设我要找 5。

从根节点开始。我们一眼就能看见答案在哪儿，但别用这双眼睛——**二叉搜索树的关键性质在这里起作用**。

到根节点，看见 4。4 大于 5，这意味着什么？这意味着我可以采用**分治**策略：我知道 5 必然在这个节点的左边。

把整棵左子树丢进垃圾桶。就好像把电话簿撕成两半——我知道 5 在右边那一半里，那么左边那半页我一个字都不用看。如果从根走到右子节点看见 6，5 小于 6，于是那个方向上的分支同样被剪掉。

> **定义**：二叉搜索树不是一棵树长得像数字的随机家谱。它服从固定模式——**每个节点都大于它的左子节点、小于它的右子节点**（先假设没有重复值）。

而且这个性质是**递归**的。回想我们在几周前学过的递归：调用自身的数据结构，就像马里奥里一层层叠上去的金字塔，可以用自身定义自身。二叉搜索树同样如此——如果这个性质对当前节点成立，它就对子节点成立。节点 2 大于 1、小于 3，性质成立；节点 6 大于 5、小于 7，性质成立；到了叶节点，性质也不会被违反，因为叶节点压根没有子节点。正是这种递归模式，构成了"二叉搜索树"这个名字。

**那么，在二叉搜索树里找一个值要多久？**

这是本讲最该记住的一个数字。如果目标数字是 5，几步就够了。但把它推广开：如果这里有 $n$ 个元素，查找效率的规律是什么？

$$h = \lceil \log_2 N \rceil$$

**对数时间复杂度。** 你也许对具体的数学推导不熟，但直觉是有的：每走一步，问题规模就砍掉一半，走完全程的步数就是这棵树的高度。而这棵树的高度，本质上就是 $\log_2 N$。

> **结论**：二叉搜索树的高度是 $\log_2 N$，所以查找的时间复杂度是 $O(\log N)$。

算几个数感受一下：$N = 7$ 时，$\log_2 7 \approx 2.8$，经过适当取整，高度基本就是 2 附近；$N = 8$ 时，$\log_2 8 = 3$（因为 $2^3 = 8$），高度就是 3。

**插入呢？** $O(\log n)$。它具体插到哪里——这里、那里、还是别的什么地方——取决于数值的大小，但整条查找路径的长度与树高成正比。**删除呢？** 大致也是同一个数量级。

太好了，我们又回到了高效操作的状态，而且这个数据结构**能自己伸缩**：想插 8，它就准确地被放在那个位置；想插 5.5，也能清楚地判断出它该待在哪儿。加一个新节点只需要更新几个指针，不需要像数组那样把内存里的东西全搬一遍。

```text
            4
          /   \
         2     6
        / \   / \
       1   3 5   7
```

### 用递归写出搜索：四种可能，一次判定

这种结构可以很自然地落到代码上。回头看链表节点——它存一个数值，外加一个指向下一个元素的指针。二叉搜索树沿用了这个思路，只需要把**一个指针换成两个**，我叫它们 left 和 right。代价是每个节点关联了三个元素：两份元数据（两个指针）加一份我们真正关心的数据（数值）。

怎么写搜索函数？假设我用 C 写一个 `search`，功能简单到不能再简单——只回答"是"或"否"：你要找的这个数字在这棵树里吗？这在算法里是很常用的一步检查。它接收两个参数：待查的数字，和一个指向树的指针；第一次调用时传进来的，就是指向根节点的指针。

递归在这里又一次派上用场。看看怎么走：

```c
bool search(int number, struct node *tree)
{
    // 基线条件：空树
    if (tree == NULL)
    {
        return false;
    }
    else if (number < tree->number)
    {
        return search(number, tree->left);
    }
    else if (number > tree->number)
    {
        return search(number, tree->right);
    }
    else
    {
        return true;
    }
}
```

- **基线条件**。如果树本身是空的——你给了我一个空指针——我立刻给出答案：false。空树里当然没有你要找的数。这个基本情况可以说是代码里最笨拙的部分之一，但你只需要检查这一个值。
- **小于当前节点的值**。顺着指针访问节点，读出它里面存的数字；要比它小，就舍弃整个右子树，钻进左子树里继续找同一个数。
- **大于当前节点的值**。对称，去右子树里继续找同一个数。
- **等于**。找到了，返回 true。

如果你还记得我们前几周的设计讨论——在总共只有四种可能的情况时，还专门把"是否等于"拎出来另问一句，其实是浪费大家的时间。从设计角度看：要么节点为空，要么目标在左子树，要么在右子树，要么就是找到了。就这样。

> **结论**：无论你是否认同，在你编程生涯的这个阶段，这段代码有一种大多数程序员都会认可的美感。你已经明确定义了函数的行为，又把递归调用放在结构完全相同（或其子集）的数据上遍历——这正是递归之美的绝妙体现。数据在内存的哪个位置都无所谓。

**问题：如果这个数字压根不存在呢？** 我们会一路回溯。如果一直搜到树的底部，落在某个叶节点上，而这个节点既不是我们要找的数字，自己又没有左子节点也没有右节点，那么 `tree == NULL` 那一支就会被触发，最终返回 false。反过来，只要它在树的顶部、中间某处还是叶节点里被碰到，就会返回 true。

**"你叫它树，可左子树右子树不也是树吗？"** 说得很对。我称它为"树"，至少在第一次调用时是成立的——那时候传进来的是指向整个结构的指针。但仔细想想，左子树和右子树本质上就是**规模更小的树**，像是依附在这个父节点上的"子树苗"。所以直接拿这个子节点当参数递归调用是完全合理的：左子节点下面挂着的，就是一整棵完整的左子树；右子节点同理。

至此，我们其实是在链表的基础上又改进了一次，赢回了一些性能——查找回到了 $O(\log n)$。

### 代价：三倍的内存账单

但我必须承认一件事：**我其实不太满意内存占用涨了大约三倍。** 为了换取这种动态性和速度，我们付出了什么？

每个方框都是一个整数加两个指针，大约相当于 16 到 20 字节；而在数组里，一个整数通常只占 4 字节。换句话说，我现在用了**三倍的内存**。

不过话说回来，如今存储空间已经相当廉价了——谁还没有个巨大的 Dropbox 文件夹、iCloud 文件夹？多占几个字节真不算什么。7 个数字当然无所谓；但要是 700 万个数字，即使速度很重要，二叉搜索树也未必是最佳选择。**最终你得根据实际使用场景来判断：什么因素更关键。**

简而言之，你可以把二叉搜索树看成链表的变体或混合体——只不过每个节点最多挂两个指针而不是一个，正是这个设计给我们引入了第二个维度。

### 精心安排的插入顺序，和一次精心设计的退化

上面那棵树只画了 7 个元素，可这 7 个元素是怎么来的？从头捋一遍。假设树一开始是空的，用户插入第一个数 2，它成了根节点。我们的目标一直是维持二叉搜索树的性质：每个节点的值大于其左子树的所有值，小于右子树的所有值。接着用户插入 1——很简单，它直接成为左子节点。再插 3——也很简单，它待在该待的位置。我特意把例子调成这个顺序，虽然树变小了，但它依然是一棵二叉搜索树，而且可以说是相当平衡的。

可如果用户偏偏给出一组更别扭的输入呢？最糟糕的那种。

> **易错点**：二叉搜索树的"平衡"不是它自带的性质，而是**插入顺序的副产品**。顺序不对，定义照样满足，性能却全丢了。

先给 1，根节点；再给 2，放到右子节点；然后给 3，为了保持二叉搜索树的性质，它只能挂到 2 的右边。要是接下来他们不按常理出牌，来的不是 4、5、6……我在内存里无意间造出来的是什么？

```text
1 ──> 2 ──> 3 ──> 4 ──> 5 ──> 6
```

**一条链表。** 我们在前面讨论过的所有坏处它全占了：动态性是有了，可时间复杂度退化成了 $O(N)$。我刚才那"先插 7 个、再插 3 个"的顺序，是**精心安排**出来让树看起来漂亮的；除非你刻意设计内存中树的构建方式，否则它极其容易从二维的树结构，退化成一维的链表。

注意，它**没有违反二叉搜索树的定义**，只是显然不平衡——一个又长又细的形状。顺带一提，如果你接触过更高级的编程语言以及数据结构和算法，就会知道二叉搜索树其实有很多替代方案：它们在算法中内置了一些结构调整机制。比如当你插入 3 的时候，你会多花一点时间，把整个结构整理一下——本质上是**围绕这个节点进行旋转**，让 2 成为新的根节点，然后 1 挂在它下面，3 也依然挂在它下面。这样每次插入或删除时，你都会根据需要重新平衡这棵树。虽然这会多花一点时间，但能避免它再次退化成 $O(N)$。

**我们不会在代码里实现这个。** 所以这个问题是可以解决的，前提是你别像我刚才那样（至少口头上）用最简单直接的方式去实现它。

### 我们的终极目标：常数时间

那么，我们能不能做得比 $O(\log N)$ 更好？

说实话，我们为什么要满足于 $O(\log N)$ 呢？它确实完全有可能退化成 $O(N)$，这可不是什么好事，在处理大规模数据集时尤其是个大问题。但如果我们能相信可以按需重新平衡那棵树、维持它对数级的高度，那么回到 $O(\log N)$ 就已经非常理想了。

**数据结构的终极目标，其实是 $O(1)$**——常数时间。

> **结论**：$O(1)$ 意味着，无论数据结构里存了多少数字、名字或者毛衣，查找或插入操作都只需要固定的步数——可能是 1 步、3 步，甚至 100 步。关键是，这个步数**完全独立于数据结构中实际存储的数据量**。也就是说，即使结构里已经存了成千上万甚至几百万个元素，它的操作速度也丝毫不会变慢。

它的吸引力让人回想起第一周课程里展示过的那张早期示意图。那时的算法——在电话簿里找人、或者清点教室里学生人数——都是线性的，直观来看就是一条直线。那是**对数曲线**，把视野拉远看，它在时间效率上已经极具吸引力了。而**常数时间**则更加理想：它是一条位于单步或双步标记处的**水平线**，无论这个常数步数具体是多少。

> **易错点**：从渐进复杂度的理论意义上说，任何算法的耗时仍会无限增长——但常数时间的**定义**决定了它永远不会改变，而这正是我们真正追求的东西。

所以，当你在手机里搜索联系人、在谷歌上查找信息，或是向 ChatGPT 提问时，系统都能以常数时间复杂度给出回应——无论后台实际存储的数据量有多大。**那么，我们如何才能实现像 $O(1)$ 这样的常数时间复杂度呢？**

### 哈希：把无限的定义域映射到有限的值域

为此，我们至少需要引入一个新的基础构件，一个专业术语——**哈希**。

> **定义**：哈希做的事，是把一个（形式上无限的）输入值域，映射到一个有限的值域上。用高中数学的概念说，定义域是输入值，值域是输出结果。哈希的目标，正是把无限的定义域映射到有限的值域。

其实我们在现实生活中也会遇到类似情况，比如玩游戏或收拾游戏道具的时候。想象这里有一些我们从网上买的超大号扑克牌，假设你想把它们按顺序整理好。你可以非常费力地手动整理：这里总共有 52 张牌，你把它们全部摊开，然后开始一张张筛选，把 2 放在这边、4 放在那边，红桃和梅花也各自归类，依此类推。

或者你也可以先观察这些牌，然后**按类别进行分桶整理**。首先，将一个规模为 52 的问题，拆成 13 个规模为 4 的子问题来处理。这里可能是第一张方块牌的放置位置，梅花放这儿，黑桃放那边，方块放这边。我可以这样反复操作，实际上就是不断进行分桶处理。所有这些数值都遵循一条非常简单的**启发式规则**，让我能够把牌放入对应的桶中；每个桶里都会包含一部分数值的子集——这样我就把一个大问题分解成了更容易处理的小问题。

假设我把这 52 个数值都分桶处理完毕，那么接下来就只剩下 4 个子问题了。我敢说，这时候问题会变得简单一些，因为每个桶里的元素都具有相同的特征。这样一来，我就能轻松地将它们从 A 到 K（或按其他顺序）进行排序，因为到了这一步，它们本质上就只是一些数字而已。

> **结论**：哈希的本质，就是把无限范围内的数值映射到有限的空间中。在这个例子里数值范围恰好是有限的，实际情况也确实如此；但更一般地处理数字，你只需要将其映射到 1、2、3、4 这样一个有限集合里。通过把数值分配到有限数量的桶中，你就可以采用完全不同、也更高效的方法来解决问题。

这个思路和我们讨论的主题有什么关系？如果我们希望在内存中组织数据，并且朝着实现常数时间访问的理想目标迈进，那么哈希技术很可能也是解决方案中的关键要素之一。通常，我们会用一个称为**哈希函数**的过程来决定输入值对应到哪个输出位置——这是一个数学过程，接收输入（比如一副牌中的某张牌、词典里的某个单词），然后输出一个代表其应归属桶的数值。

#### 通讯录里的哈希

以通讯录这个应用为例：在它的图形界面里，你所有的亲友信息通常会按字母顺序从上到下排列。理想情况下，我们希望能在常数时间内快速找到目标联系人。苹果或谷歌可能采用的最简单实现方式就是**线性查找**——从上到下逐个扫描所有联系人，直到找到目标为止。这当然准确。

但如果他们改用数组，然后利用**二分查找**，就能在对数时间内找到目标联系人，这确实很棒。可如果你的通讯录里有很多亲友，或者数据集更大，能一步到位直接跳到答案，而不是经过对数级的几步，岂不是更好？这正是我们的目标。

于是，通过哈希函数，我们又遇到了一个熟悉的问题解决思路。如果我要查找 Mario 的号码，我现在既不用从上到下遍历，也不是采用分治法在中间区域反复跳跃查找——我**直接确定 Mario 所在的存储桶位置**。

规则简单得可爱。英文字母表共有 26 个字母，从 A 到 Z，可以是大写或小写形式。假设我需要确定 Mario 对应的存储桶位置：如果把所有以 A 开头的人名放入第一个存储桶，B 开头的放入第二个，以此类推直到 Z 开头的放入最后一个——这样处理是否更合理？

按照这个逻辑推断，如果我把 `"Mario"` 作为参数传递给用 C 语言或其他语言实现的哈希函数，我希望得到返回值 **12**，因为字母 M 在字母表中是第 13 个字母。但由于我们的存储桶本质上是一个数组，且索引从 0 开始计数，因此实际对应的索引位置是 12 而非 13。同样地，如果输入是 `"Luigi"`，我希望得到返回值 **11**。

> **结论**：在这个例子里，我的哈希函数接收字符串作为输入，并返回一个整数。理论上说，英语世界中的人名数量是无限的，但该函数只能输出 26 种可能的结果（0 到 25）——这意味着我们把无限的定义域映射到了有限的值域，**这次是 26 个值，而非之前的 4 个**。

#### 把哈希函数写成代码

虽然哈希函数这部分看起来有些神秘，但实际上它的原理相当直观。若要把这一思路用 C 语言实现，你可以引入 `ctype.h` 头文件（我们之前已多次使用），以调用 `toupper` 这类函数——这能确保程序对字母大小写不敏感。

```c
#include <ctype.h>

unsigned int hash(const char *name)
{
    return toupper(name[0]) - 65;
}
```

该函数将返回一个整数值，这正是我们预期的目标；它接收一个字符串作为输入参数，我们把这个参数命名为 `name`。它运用了一些巧妙的算术运算技巧：

- **先把人名首字母转换为大写形式**。无论输入字母原本是小写还是大写，我都统一转成大写。因为后续需要减去 65（大写字母 `'A'` 的 ASCII 码值），如果直接用小写字母的 ASCII 码进行计算，就会导致数学运算出错。我必须统一做这个减法。
- **再减去 65**。这样函数就会返回一个介于 0 到 25（含）之间的数值：首字母是 `'A'` 就得到 0，若是 `'Z'` 则返回 25。
- **参数加上 `const`**。根据上周的讨论，这里存在一个风险：现在这个函数的调用者——也就是使用这个函数的人——会告诉你到哪里去找 "Mario"、到哪里去找 "Luigi"。问题在于，**即使你不应该这样做，你仍然可以访问那个地址，并在内存中实际修改他们的名字**，而你本应该只是使用这个名字。所以你可以使用类似 `const` 这样的关键字，它表示：即使我没有通过值传递的方式给你一个副本，你也不应该能够修改这个值。
- **返回类型收紧为 `unsigned int`**。目标是为数组设计一个哈希函数，它应该返回一个从 0、1、2 开始向上的值，**绝不能是负数**。所以我们可以更严格地声明：它不仅仅是一个 `int` 类型，而是一个 `unsigned int` 类型。

> **易错点**：目前这段代码**还没有加入错误检查机制**。如果输入是非英文字符，程序就会出错。为简化起见，我们暂且假设输入的都是标准的英文姓名。

这些看似微小的改进，实际上能让你的代码设计得更加出色，因为它们减少了可能出现的错误或问题。这个函数还可以再做一些优化，具体的健壮性防护措施，我建议在 C 语言课程的最后一周围绕这个方向展开深入探讨。

### 哈希表：数组里装着链表

假设我们已经实现了这样的函数，现在就可以用它来决定把数据放进哪个桶里——把这些人名存进去。

> **定义**：这种数据结构叫**哈希表**。它堪称数据结构界的"瑞士军刀"，正如一些计算机科学家所说，它功能强大、用途广泛。如果被困在荒岛上、只能选择带走一种数据结构，他们很可能会选择哈希表。

它之所以如此通用且实用，主要是因为它能非常高效地将**键与值关联起来**。这实际上又回到了我们最初讨论的那个核心概念。如今，哈希表常被用于实现字典结构：从底层实现来看，我们课程开始时讨论的字典——即键值对的集合——正是基于哈希表构建的。**毕竟，电话簿本质上就是一本字典**：姓名对应号码，这就是键与值的对应关系。真正的英语词典，比如《牛津英语词典》，也是基于这种键值对的结构——它包含大量单词及其定义。这种把一组数据与另一组数据关联起来的能力，在编程中非常实用。

那么，它到底长什么样？比如，你可以把它设置为一个大小为 26 的数组，这样就有 26 个桶，分别对应字母 A 到 Z。

> **结论**：哈希表就是一个数组，其中每个元素都指向一个链表。它是链表与数组结合后的升级版数据结构。

```text
  哈希表 = 一个数组，数组的每个元素都指向一条链表

  [ 0]  A ──> Mario
  [ 1]  B ──> (空)
  [ 2]  C ──> (空)
   ...        ...
  [11]  L ──> Luigi ──> Link ──> (空)
  [12]  M ──> Mario ──> (空)
   ...        ...
  [25]  Z ──> (空)
```

这就是一个包含 26 个指针的数组，每个指针指向一个节点。我会创建一个指针数组，最终用来存储一系列类似这样的 `person` 对象——比如这里有一个字符型名称和一个数字（电话号码），用来表示一个人的信息。不过我们今天不会给任何人打电话，所以先简化：只存姓名，外加一个指向下一个姓名的指针，依次指向下一个、再下一个。

那么这些方格分别代表什么呢？它们最初都只是指向节点的指针，**全部为空值**。但当我把 Mario 插入这个所谓的哈希表时，并不会直接把他放在这个位置。我会在内存中创建一个新节点，把 Mario 放进去，然后把它接上——因为如果以后再有其他以 M 开头的名字，我会继续把它们一个个串连起来。

> **易错点**：桶里放的是**链表的头指针**，不是数据本身。名字本身活在内存里别处，哈希表只负责"门牌号"。忘了这一点，后面所有对桶的想象都会错位。

### 冲突：哈希表的原罪

任天堂宇宙中有非常多的角色。Mario 进入这个数据结构了，Luigi 也进来了，第三个角色 Peach 也进来了。一切运行得都很顺利。遗憾的是，特别是对于粉丝来说，确实还有其他名字以 M、L 及其他字母开头的角色。

于是我们可能遇到所谓的**冲突**。这是使用哈希函数的一个缺点：

> **定义**：把无限的数据映射到有限的空间，那么根据定义，就必然会产生大量的潜在冲突。比如会有多个以 M 开头的名字、多个以 L 开头的名字，等等。

如果在现实生活中遇到一个名字以 M 开头的人，而你的手机里已经存了 Mario，你可以删除 Mario，把新朋友的联系方式存进去——但这样处理就有点笨了。你可以覆盖掉原来的值；也可以把 M 开头的朋友存到这个位置，等这个位置满了，再存到下一个位置；如果又遇到一个名字以 M 开头的人，就继续往后放。

但这样一来，整个结构就会变得一团糟，最终谁在哪个位置就毫无规律可循了。**它退化回了类似线性的结构。** 如果仅仅因为理想位置已满，就不得不翻遍整个结构来寻找那个 M 开头的朋友，那效率就太低了。

所以，将数组与链表结合使用的巧妙之处就在这里：**你可以通过哈希函数把名字映射到目标位置**（比如这里的第 12 个格子），然后只需要用链表把它们串连起来。只要冲突数量不太多，这个方案就能高效运行。而且至少现在，你无需删除数据、也无需破坏数据结构本身。

### 它比链表好吗？比数组好吗？

**我敢说它比链表好。** 因为如果只是一个从 A 到 Z 的链表，查找任何一个人的运行时间会是相当耗时的操作——即使链表已经按字母顺序排列，你也得从头开始，可能一直遍历到末尾，才能找到像 Zelda 这样以字母 Z 开头的名字。

但在这里，我们拥有的是一个**由链表组成的数组**。那么这里的实际运行时间究竟是多少？

它并不会像 N 步那么糟糕。因为**如果我们假设名字是均匀分布的**——比如在任天堂的世界里，以 M 开头的名字和以 L 开头的名字数量差不多，以 A 开头的和以 B 开头的也差不多——那么我们可以认为，虽然这里有一系列链表连接在一起，但它们的长度大致是相同的。你的通讯录里或许确实有以 Z 开头的人名，但这些链表的长度是有限的，因为你的通讯录里总共就那么多名字。

> **结论**：假设你有 $k$ 个桶（比如 26 个，或者本例中的 4 个），并且姓名在 A 到 Z 的范围内均匀分布，那么每个链表的长度理论上**不会超过** $N$ 除以 $k$，也就是 $N$ 除以 26。写成大 O 就是 $O(N/K)$——确实更快。但在使用大 O 表示法时，高阶项的处理原则告诉我们：$K$ 是个常数，所以**它仍然属于 $O(N)$ 的范畴**。

这就是矛盾所在：**速度确实会更快——比链表快大约 26 倍——但时间复杂度仍然是 $O(N)$**，因为所需时间依然与数据集大小 $N$ 成正比，这仍然是线性复杂度。所以我们似乎又一次偏离了常数时间搜索的目标。

走到这里，手上已经攒下了四把工具。把它们的账摊开算一次，每一笔的代价都清清楚楚：

| 数据结构 | 查找 / 插入的代价 | 每个元素的内存代价 |
| --- | --- | --- |
| 数组 | 插入可能需要重新分配，或把数据全部复制 | 每个整数 4 字节 |
| 链表 | $O(N)$，从头走到尾 | 一个数值 + 1 个指针 |
| 二叉搜索树 | $O(\log N)$；插入顺序不巧会退化成 $O(N)$ | 一个数值 + 2 个指针，约 16–20 字节，约 3 倍 |
| 哈希表（按首字母分桶） | 实际约快 26 倍，但渐进仍是 $O(N)$ | 桶数组 + 一条链表，比名字总数还多一点 |
| 字典树 | $O(1)$，步数只与名字长度有关 | 每节点 26 个指针 + 布尔标记，绝大部分为空 |

### 更"聪明"的哈希函数，以及它的账单

那么根本目标是什么？我们可能需要采用一种**更智能的哈希函数**。

前面我们只取了每个人名字的**首字母**；现在换一种方法——取这个人名字的**前三个字母**作为哈希值，这能显著降低冲突的概率。在这个模型里，我敢说任天堂宇宙里没有其他角色的名字是以 "LIN" 开头的，于是 Link 在内存中就有了自己专属的位置；同样，Luigi 的 "LUI" 前缀在任天堂宇宙里也是独一无二的，因此我们避免了冲突。

遗憾的是，虽然在这个小例子中似乎确实消除了冲突，**但我们为此付出了什么代价？**

**需要占用更多的内存空间。** 我甚至无法在屏幕上完整显示大部分内容了——这是 LAA，这是 LUG。字母表中所有其他字母以及各种可能的组合又该如何处理？其中一些组合在英语或任天堂的游戏世界里根本没什么实际意义——我认为应该不会有人名字是以 AAA、AAB 或 AAC 开头的。

> **结论**：我们浪费了大量空间，只为了降低冲突的概率。所以代价是什么？代价就是需要占用多得多的内存空间。使用哈希表时面临的一个关键矛盾在于：你需要设计一个**良好的**哈希函数——它应该比单纯取首字母更复杂一些，但又不能过于浪费，以免需要大量桶、导致内存占用过高。

### 字典树：把常数时间真正做出来

理想解真的存在吗？其实是有可能的——**前提是允许我占用更多的存储空间。**

> **定义**：世界上有一种叫做**字典树**（trie）的数据结构。这个名字有点奇怪，因为它其实是 "retrieval"（检索）的缩写，尽管我们平时并不说"检索树"。字典树是一种由数组构成的树形结构。

对，计算机科学家们有时就像弗兰肯斯坦那样，把各种东西拼凑在一起——先是链表和数组，而现在我们又有了树和数组的组合。**你们也可以尝试把不同结构组合起来，创造出自己的设计。**

先看字典树到底是什么。根节点在这儿——你可以把字典树中的**每个节点都看作一个由 A 到 Z 的字母组成的数组**。具体做法是，将这个数组的索引范围设为 0 到 25，对应字母 A 到 Z，而数组中的每个元素都是一个指针，指向字典树中的另一个同类节点。

插入的机制是：根据名字的第一个字母找到数组中对应的位置，然后通过指针指向代表名字第二个字母的节点，再通过该节点指向第三个字母，依此类推——**从而隐式地存储数据结构中的所有名字**。

#### 插入 "toad"、Toadette 和 Tom

假设我们首先想插入 "toad"（任天堂游戏中的一个角色名）。如果我们计算字母 T 在字母表中的位置——这里的指针会从空值改为指向一个新节点，这个节点代表 Toad 名字的第二个字母，也就是 O。接着，为了插入 TOA，我们再创建一个节点；从 A 节点会指向 D 节点。为了便于示意，我会用绿色标出这个节点，虽然在实际内存中它可能是一个布尔值或其他类型的标记——**这表示 Toad 的名字在此处结束**。

换句话说，这个字典树在内存中现在有 4 个节点。每个节点本质上都是一个大小为 26 的数组，但单词 "toad" 并没有被明确地存储在这个结构中。这里并没有存储字符 "toad"，它是通过**隐式方式**构成的——因为 T 指针非空、O 指针非空、A 指针非空，而 D 指针此时实际为空。这构成了常用的实现方法。

接下来，我可以继续插入任天堂宇宙中的其他名字，比如 "Toadette"：因为可以从这里继续指向 E 节点，再到 T 节点，接着是另一个 T 节点，最后到 E 节点——这个节点我也会用绿色标记。通过沿途设置这些非空指针作为标记，你甚至可以处理互为子串或超串的名称。

与此同时，如果宇宙中还有第三个名字，比如 "Tom"，原理完全相同——最终我们可以**复用同一份数组结构**：

```text
root ──[T]──► [O]──┬──► [A]──► [D] ●  ← toad
                   │              └─► [D] ─► [E] ─► [T] ─► [T] ─► [E] ●
                   │                                   ← toadette
                   │
                   └──► [M] ●  ← tom
```

注意最后这个：Tom 和 Toad **共享了 `T → O` 这段前缀**——我们并没有复制一份新的 `[T]` 和 `[O]`，而是在复用同一个数组。"非空指针、非空指针、空指针"的路径，或者在终点处设一个标记为 True 的布尔标志，就表示某个名字在这里结束。

> **结论**：每个节点都对应着单词或名称的第 $i$ 个字母。通过巧妙地运用空指针、非空指针以及布尔标志，你可以在这个结构中**隐式地**存储名称。

#### 在字典树里查找

用图示形式描绘大量名称会变得非常困难。所以请想象一下，在你的脑海中，有几十个、几百个甚至几千个名字——在这个结构中，只是多了更多的箭头和更多的数组而已。

那么，该如何在这个数据结构中实际查找某个人呢？如果你问"**Toad 是否在这个数据结构中？**"，或者查找其他任何人，你可以像处理任何树结构一样，从根节点开始：

1. 对 Toad 的第一个字母 **T** 做哈希运算，这会指向一个特定位置，然后检查该位置是否为空——不是空的，那么 "T" 就隐含在其中了。
2. 沿着这个指针来到这里，对第二个字母 **O** 做哈希运算，检查这个指针，并沿着箭头继续前进。
3. 对第三个字母 **A** 做哈希运算，检查指针，继续前进。
4. 处理第四个字母 **D** 时，你看到了那个用绿色表示的布尔值——**Toad 确实存在于这个数据结构中**。

注意一下这里的情况，有个细节需要注意：

> **结论**：无论这个字典树里存了 3 个名字还是 300 万个名字，要确认或否定 Toad 是否在其中，我总共需要 1、2、3、4 步——这基本可以看作是常数时间操作。

虽然名字长度可能有所不同，但任天堂的角色名最长也不会超过多少呢？大概 10 个字符、20 个字符，最多可能 30 个字符吧。**名字长度存在一个合理的有限上限**——任天堂不太可能给游戏角色起一个长得离谱的名字。所以无论是查找 Toad、Toadette、Tom、Mario、Luigi、Peach，还是我们讨论过的其他任何名字，实际上都能在常数时间内完成。

也就是说，字典树能让你快速回答这类问题：*Toad 是否存在于这个数据集中？* 或者换个问法：*在这个数据集中，Toad 对应的电话号码是多少？* 因为如果你现在假设每个指针不仅仅表示"是"或"否"的布尔值，而可能指向一个包含姓名和电话号码的实际人物结构，那么你甚至可以存储这样的数据——也就是**键值对，其中姓名作为键，电话号码作为值**。

#### 一个节点的构造

为了让这一点更清晰，严格来说，字典树的节点并不完全只是一个数组：它是一个大小为 26 的**子节点数组**（存储该节点的所有子节点，类型为 `struct node *`），此外还可以再挂上标记位或一个 person 结构（装着这个人的电话号码）。利用这样一个结构和相应的代码，你就可以仅用如此简单的结构实现一个字典树。

```c
typedef struct node
{
    struct node *children[26];  // 子节点数组：A-Z，每个元素指向另一个同类节点
    bool is_word;               // 某个名字在这里结束
    // 还可以再挂一个 person 结构：姓名 + 电话号码
} node;
```

最初，你的字典树只是一个指向节点的指针，你可以将其初始化为空指针，以明确表示其中尚未存储任何姓名。每次分配一个新节点时，就根据姓名的第一个、第二个、第三个、第四个直到最后一个字符依次做哈希映射，按需分配节点，将布尔值切换为真或假，或者用星号标记出他的电话号码，以表示我们已成功找到该联系人。

#### 那为什么实践中不更频繁地用字典树呢？

在我们今天讨论的所有数据结构中，**字典树确实能达到 $O(1)$ 的时间复杂度**。但有趣的是，**第五个问题集中，你们不会实现字典树，而是要实现哈希表**——那个数据结构的瑞士军刀，几乎每个程序员都知道它。

那么，为什么在实践中不更频繁地使用字典树呢？当然可以，但这里存在什么权衡呢？

**它占用大量内存。** 从课程开始到现在，情况一路升级：我们从最初那个每个整数只占 4 字节的数组开始，然后增加了一个指针变成了链表，接着又增加了 2 个指针变成了二叉搜索树，现在我提议使用 **26 个指针，再加上一个布尔值或一个名为 `person` 的数据结构**。内存占用确实大幅增加了。

> **易错点**：字典树最大的问题——就像屏幕上显示的 Toad、Toadette、Tom 这些例子一样——是**存在大量内存浪费**，这和我们在哈希函数中看到的情况类似。这些数组中的大部分指针都只是空值、从未被使用，这往往导致你虽然正确解决了问题，却使用了远超实际需求的内存。这种方式不仅会拖慢计算机运行速度，还会造成大量内存浪费。这个问题是可以控制的，你们将在习题集中进一步探索。

### 现实中的哈希表：Sweetgreen 的货架

话虽如此，正如我们今天一开始讨论的，现实世界中确实存在栈和队列这样的数据结构，**现实世界中甚至也存在哈希表**——你们将在习题集 5 中实际用代码实现它。

在座的各位有没有人在哈佛广场（或者美国其他地方）的 Sweetgreen 餐厅吃过沙拉？大概 12 个人里有两三位吧。

好的，所以不难想象，走进这样的店铺、排队等候时，你会看到类似这样的货架。因为 Sweetgreen 这类餐厅在提供自取服务时，他们会把你的沙拉通过哈希算法分配到类似这样的货架上——所以在 Sweetgreen 店里，你确实能看到这样的木质货架：

```text
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │    A – E     │    F – J     │    K – N     │    O – Z     │
  ├──────────────┼──────────────┼──────────────┼──────────────┤
  │  按名字首字母  │  按名字首字母  │  按名字首字母  │  按名字首字母  │
  │  哈希分配沙拉  │  哈希分配沙拉  │  哈希分配沙拉  │  哈希分配沙拉  │
  └──────────────┴──────────────┴──────────────┴──────────────┘
```

如果你的名字恰好落在某个字母范围内，他们就会通过哈希算法把你的沙拉分配到对应的区域。

但当然，即便在现实场景中，这种哈希表系统也存在一些限制和潜在问题，可能有人已经经历过这种情况。想象一个极端情况——比如某个区域堆积了大量数据，这样空间就不够了，对吧？

确实，这种情况我以前也遇到过，尤其是在采用这套系统之前。他们过去会把 A 开头的词条放在这里，B 开头的放这里，C 开头的放这里，D 开头的放这里，依此类推。后来有人发现：**A 区经常溢出到 B 区，B 区又经常溢出到 C 区，而 Q、Z 这类字母开头的词条几乎没人使用。** 这就导致空间既被浪费、又不够用。

于是他们决定干脆去掉字母表里的大部分字母，把剩下的桶扩大。这样一来，K 到 Z 这些字母开头的词条数量就不太可能多到让书架溢出了。

> **结论**：我们在代码里实现的一切——哪怕涉及那些看起来很晦涩的指针表示和解引用操作——本质上都是在**把他人已提出的现实解决方案实现到代码中，并将其转化到新的应用领域**。
