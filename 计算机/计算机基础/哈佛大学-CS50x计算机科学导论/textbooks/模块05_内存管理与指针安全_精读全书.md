### 一张便利贴拼出来的猫，和一盆解压球

欢迎来到第 4 周。这一周我们要把象征意义上的"辅助轮"卸下来——也就是 CS50 库——然后直接往计算机内存的内部看。卸掉辅助轮之后，我们还会聊文件，以及信息到底怎么被长期存下来：不管是你下载来的文件，还是你自己新建的文件。

开始之前先分享两位同学课前画的画，Avery 和 Marie 做的。他们用便利贴拼了一幅画，只有绿色和紫色两种颜色。从你们的位置看过去，整体像什么？是一只猫。他们只用 0 和 1，或者说只用两种颜色的便利贴，就拼出了一只猫的图案。

这幅画横纵两个方向都只有很少几个像素点，分辨率低得可怜——但它恰恰就是计算机在底层存储图像的真实方式。

讲台上这盆解压球已经摆了一阵子了。给它拍一张好看的照片，出来就是这个效果。照片的分辨率也是有限的。所谓分辨率，说的是横向有多少个像素点、纵向有多少个像素点。把这两个数字相乘，就是总的像素数量，文件体积单位可能是千字节、兆字节，更大的图还要往上走。尺寸总是有限的：放大可以看得更清楚，但继续放大，就会发现细节终究是有限的，放到极致你看到的就是一个个真正的点，也就是像素。几乎任何屏幕都是这样，把手机举到眼前，或者把脸贴到电视屏幕上，你看到的是成千上万、成百上百万个微小的点，每个点有自己的颜色，这些颜色凑在一起就成了你看到的图像——无论是这盆解压球，还是那幅便利贴猫。

这周有一件事和这个问题集有关，就是让你写代码处理自己的图像：既要理解它在底层怎么跑起来，也要用上当下最常见的那些滤镜。

如果把这张图拆到底，它当然不止一个颜色。我们看到白色、红色，还有介于两者之间的一大堆色调。但为了把问题简化，我们先不看像素，只看 0 和 1。假设在这类图里，每个 0 解读为黑色，每个 1 对应白色——如果这串数字小到你能看清的话。这张图画的是什么？

是笑脸。只盯着那些 0、把那些 1 忽略掉，你就会发现图里藏着一个笑脸。这可以算是一种单比特图像：每个点要么是 0，要么是 1。可现代技术里，我们会给每种颜色分配 16 位、24 位甚至更多位，这样才能呈现彩虹里的每一种颜色，而不只是黑白两色。

不管怎样，你在 Mac、PC 或手机上打开一个由 0 和 1 组成的图像文件时，屏幕上呈现的就是这么回事：一个简单的 X 和 Y 坐标网格，上面有些点是白的，有些点是黑的。

### 把颜色写成数字：RGB、00 与 FF

说到表示方式，这里可能牵涉到我们第 0 周就提过的东西。RGB——红、绿、蓝——是计算机内部表示颜色最常用的方式之一。如果你们中间有人用过 Photoshop 之类的编辑软件，或者更早的时候在高中折腾过自己的网页，那你们大概已经熟悉我们今天要反复见到的这套写法了。

在知识层面这并不算新东西，它只是介绍一种常见的惯例：数字还可以有别的写法。

看这张 Photoshop 颜色选择器的截图——Photoshop 是一款用来编辑照片和文件的流行软件——我在这里选中的颜色在人眼看来是黑色，我把它的输入方式高亮出来了。我输入 `000000` 选了黑色：0 红、0 绿、0 蓝。但你注意看，它把 `000` 转换成了 `000`，而不是别的什么东西。

换一种颜色，比如白色，在 Photoshop 里、也就是今天的代码里，你可以用 `FFFFFF` 来表示，等价于 255 红、255 绿、255 蓝。红色是 `FF0000`，绿色是 `00FF00`，蓝色是 `0000FF`。

### 为什么全世界都在用十六进制

用 8 位能表示从 0 数到 255——255 正是 8 位所能表示的最大值。可我们看到的这些 255 和字母 F 之间，似乎存在着某种对应关系。

答案和进制有关。十进制系统用 0 到 9 这十个数字，二进制只有 0 和 1。假设我们需要更多数字：0 到 9 不够用了，那就在后面加上 A、B、C、D、E、F，大小写都算。当计算机科学家需要超过 10 个数字时，他们就是这么干的。但数量是有限的——16 个数字，16 种可能，这就叫十六进制，也就是以 16 为基数。

进制系统有无穷多种，三进制、四进制、十五进制、十七进制都行，这只是计算领域里少数几种常用约定之一。我们仔细拆一下，因为你以后会经常撞见这种数字。幸运的是，这其实还是你熟悉的那套系统：列和占位符的结构一模一样，只是每一列代表的基数不同。十进制里我们用 10 的幂，二进制里用 2 的幂，十六进制里就用 16 的幂——$16^0 = 1$，$16^1 = 16$，$16^2 = 256$，以此类推。

用十六进制开始计数：两位数的十六进制 `00` 当然就是十进制的 0，因为 $16 \times 0 + 1 \times 0 = 0$。表示 1 你会写 `01` 而不是光写 `1`，好让两位数的格式显出来。接着是 `02`、`03`、`04`、`05`，然后 `06`、`07`、`08`、`09`。

现在事情开始有意思了。在十进制里我们马上就要进位，得到 `10`；但在十六进制里，我们还能继续往下数——下一个是 `0A`，然后 `0B`、`0C`、`0D`、`0E`、`0F`。就算你从来没接触过十六进制，猜猜 `0F` 后面应该是什么？还是一样进位，轮到 `10`。

那为什么这样设计是对的？因为我们刚才从 `00` 数到 `0F`，一共 16 种组合。`0F` 是最大值，它是 $1 \times F$，而 F 代表 15——可用的数字就是 0 到 F 那一串，共 16 个。

于是 15 在十六进制里写作 `0F`（$16 \times 0 + 1 \times 15 = 15$），16 写作 `10`（$16 \times 1 + 1 \times 0 = 16$）。注意，在十六进制里读作"10"的那个数不是十进制的 10，它就是 16。

那 `FF` 呢？$16 \times 15 + 1 \times 15 = 255$。其实你根本不用算，只要回忆一下我们刚才的思路就行——我们在 Photoshop 截图里看到的那一对 F，正是计算机用来表示十进制 255 的写法。

**那我们为什么要关心十六进制？** 因为用两个十六进制数字来表示一个值实在太方便了：1 个十六进制数字刚好表示 4 个二进制位，一口气就是 4 个 bit。

举例说明。F 是 15，而 15 的二进制是 `1111`——第 8 位上的 1 加上第 4 位、第 2 位和个位上的 1，正好等于 15。所以一个 F 就够：我一直能数到 15，一个 F 把它装下了。

而前面提过，通常我们一次用 8 个 bit，也就是 1 个字节来存放任何值，因为这是一种非常实用的通用计量单位。所以在十六进制里，想表示 4 个 1 就写 F，想表示另外 4 个 1 也写 F。两个 F 连在一起，就相当于 8 个 1 连在一起，加起来是 $1 + 2 + 4 + 8 + 16 + 32 + 64 + 128 = 255$。如果你把这 8 个 bit 按每 4 个一组切开，只用 0 到 F 就能表达从 0 到 15 的全部可能。

> **结论**：一个十六进制数字 = 4 个 bit，两个十六进制数字 = 8 个 bit = 1 个字节。正是这个便利，让全世界都倒向了十六进制——讨论颜色的时候是这样，接下来讨论内存地址的时候也是这样。

### 给内存里的每一格编号

接下来我们真正进入内存。

这就是我上次提到过的那个"内存画布"的比喻。我们可以以一种合理但任意的方式给这些字节编号：这是字节 0、1、2、3、4、5、6、7，也许这个位置是字节 15。这没什么问题，没什么不对。

但在真实实践中，任何程序员都不会用十进制去想内存位置，而会用十六进制——纯粹因为刚才说的那个便利。所以我们实际上从 0 开始编到 9，然后继续用 A、B、C、D、E、F 往后接。这里是 `10`，这里是 `11`、`12`；这里是 `19`，接下来是 `1A`、`1B`、`1C`、`1D`、`1E`、`1F`。

这里就有歧义了。如果你只是扫一眼白板上写的 `10`，这是十进制的 10，还是十六进制的 10？在十六进制里它表示 16，可这并不明显——如果你不知道正在用哪套进制的话。虽然看别处也许能猜出来，但确实有歧义。

所以在十六进制的世界里，人们习惯在任何十六进制数字前面加一个前缀 `0x`。那个 `0` 本身没有任何含义，`x` 也没有，它只是宣布"接下来是十六进制"。有了 `0x`，`0x10` 的含义就毫不含糊了：换算成十进制是 16，而不是 10。

> **提示**：今天你会看到大量以 `0x` 开头、以及大量两位、四位、八位的十六进制数字。多数时候我们并不真关心它们具体等于多少，不需要做大量心算，但这种写法会一直在你眼前晃。

好了，回到正常的节奏。来看这行代码：

```c
int n = 50;
```

我们声明了一个叫 `n` 的变量，把 50 存进去。我们把它写进一个叫 `addresses.c` 的文件里，从最简单的部分开始：引入 `stdio.h`，写 `main` 函数（这里先不处理命令行参数），声明 `n` 并赋值为一个随意但熟悉的 50，然后用 `%d` 把 `n` 的值打印出来。没什么新东西，不过是照部就班地声明一个变量并打印它的值。

### 取地址：& 和 %p

但 `n` 到底存在内存的哪里？

这是我的内存画布图。为了讨论方便，我们假设 50 最后落在下面这个位置。程序里也许还有别的东西在跑，所以内存的这块地方已经被占用了——50 存在这儿完全合理：

```text
        0x0120  [  int n = 50        ]  占了 4 字节
        0x0121  [                    ]
        0x0122  [                    ]
        0x0123  [                    ]
        0x0124  [  程序里的其他内容  ]
        0x0125  [                    ]
```

关键问题来了：我到底给 `n` 分配了多少字节？4 个字节，因为前面提过，整数通常占 4 字节，也就是 32 位。所以这至少是 2 的幂次规模的——虽然我只是想象它最终会落在内存的哪个位置。

于是 50 确实存在 0x0120 这里。当我调用 `printf` 并把 `n` 传进去时，计算机会访问内存的这个位置，把它读出来，打印出 50。但这个值是待在某个具体地址上的。它不会是什么 0x0 或 0x1 这种简单地址，也不会是个很小的数字，它可能是 `0x123` 这种任意地址——这是我随便编的，但确实是个用十六进制写起来很好读的数字。

那拿到这个信息能干什么？到目前为止好像没什么用，但我们之前写的程序其实一直在利用这个特性。只要再掌握一点语法，我就能在代码里直接看到类似这样的东西，而不只是打印在屏幕上。

我建议引入两个新的运算符。一个是单独的 `&` 符号，另一个是单独的 `*` 符号。`*` 我们会发现有很多种用途，而 `&` 的用法简单直接：获取变量在内存中的地址。如果你有一个变量 `n`，把它写成 `&n`，你实际上是在问计算机：这个变量存在哪个地址上。你可以确认它是不是 `0x123` 这样的地址，或者完全是另一个地址。

回到 `addresses.c`，我们把打印的内容从 `n` 换成 `&n`。还有一个改动要顺手做掉：地址确实是个数字，从技术上讲可以用 `%i` 来显示，但一般不会那么用，我们有另一个格式码——一个你平时不太用得到的格式码。我得说，这个更多是演示性的，而不是特别实用。但当你真的想打印出内存中某个东西的地址时，你就用 `%p`。

```c
#include <stdio.h>

int main(void)
{
    int n = 50;
    printf("%p\n", &n);
}
```

```bash
make addresses
./addresses
```

跑出来是 `0x7ff3c34ecc`。这些全是十六进制数字，要心算换算出它的实际数值非常麻烦。但我们确实看到了这种常见的十六进制表示法——虽然这种格式对我们人类来说通常没什么实际用处，但计算机已经用了它很长时间了。

### 指针：把地址装进另一个变量

接下来要介绍的概念，可以说是计算机科学里、尤其是 C 语言里相当复杂的概念之一了：指针。

我得提前说一句：今天的内容可能会让你觉得信息量大到像被消防水枪对着冲。这么多年过去了，我依然记得自己真正理解这个概念的那一天——不是在课堂上第一次碰指针的时候，而是在埃利奥特宿舍楼餐厅右后方的角落里，当时我正和助教在办公时间一起坐着讨论，最终是他帮我把这件事彻底弄明白。那一刻我恍然大悟。所以如果今天的内容让你觉得有点晕，别担心，它和这里所有别的知识一样，都需要时间和练习。

那么指针到底是什么？

> **定义**：指针是一种变量，它能存储地址。地址从技术上说就是个数字，和整数一样。但我们需要区分两种数字：一种是我们真正关心的数值，比如 50，我们会对它做数学运算；另一种是指针，它存的是某个变量（或者说内存中某个值）的地址。

那么我们可以开始做这件事：像之前一样声明 `n` 并赋值为 50，同时获取 `n` 的地址，再把这个地址存进另一个变量——这个变量就是指针。

```c
int *p = &n;
```

`p` 是这个变量的名字，它存的是 `n` 的地址，而 `&` 就是取地址运算符。这里还有一个语法细节：星号 `*`。星号表示这个变量 `p` 存的是**一个整数的地址**，而不是整数本身。

这语法看起来有点怪，它长得有点像乘法，但它不是。纯粹是几十年前 C 语言的开发者们决定用星号，虽然它确实不直观、没法一眼看出作用。不过在这种上下文里，当你看到星号紧跟在数据类型后面，比如 `int *`，它只是说明"我声明的这个变量本身不是一个整数，而是一个整数的地址"。

实际验证一下，回到 VS Code，引入这个额外的变量 `p`，把它设成 `&n`，然后做一件完全一样的事：不打印 `n`，直接打印 `p` 的值。

```c
#include <stdio.h>

int main(void)
{
    int n = 50;
    int *p = &n;
    printf("%p\n", p);
}
```

我这次会顺手犯个低级错误：漏了分号。这种错误我照样会犯。清屏，重新 `make addresses`，再跑 `./addresses`——现在我们看到的就是变量 `n` 的地址了，只不过我这次临时把它存进了一个叫 `p` 的变量里。

> **提示**：你可能会在网上的参考资料里看到不同的写法。这是声明指针的标准写法：先写类型，空一个空格，星号，星号后面紧跟变量名，中间不加空格。不过即使把星号放在类型后面（`int* p`），或者放在变量名前面（`int * p`），代码也照样能跑，这两种写法你确实都会见到。从代码风格上，我们还是建议把星号紧挨着变量名写。不过说实话，我觉得把星号放在类型这一边会更清楚一些——这样它更明确地表示自己跟类型有关，而不是跟变量名有关。这只是约定俗成的写法。

那如果不写星号会不会报错？会。删掉 `p` 前面的星号，重新 `make addresses`，报错是"不兼容的指针到整数的转换"初始化。术语听着挺复杂，意思其实很直白：你试图把右侧的指针赋给左侧的整数，这在这里不合适。归根结底它们都是数字，但更准确地说，右边是一个指针或地址，而左边现在却错放了一个普通整数。改回去就好了。

关于这个新语法还有别的问题吗？有——就算现在讨论的不是数组，我们等一下也会回头讨论其他数据类型，那时候你仍然会用 `*`，这个语法对所有情况都是通用的。

**那能不能反过来，告诉计算机"我想把这个变量存在这个地址里"？** 这正是我们接下来要讨论的。既然我们现在有能力找出某个东西的地址，按理说我们也可以自己找一个地址，甚至往那儿存点东西进去。

那代码里到底发生了什么？看回内存画布。假设 50 存在变量 `n` 里，就在右下角那个位置，地址是 `0x123`（真实地址会长得多，为了方便就这么假设）。当我在代码里声明 `p` 并赋值时，内存里实际发生的是：

```text
        p 这个指针自己也要占地方 —— 通常 8 字节
        0x0130  [  0x0120          ]  int *p
        0x0131  [                    ]
        0x0132  [                    ]
        0x0133  [                    ]
        0x0134  [                    ]
        0x0135  [                    ]
        0x0136  [                    ]
        0x0137  [                    ]

        p 里装着的那个 0x0120，指向下面这 4 个字节
        0x0120  [  50               ]  int n
        0x0121  [                    ]
        0x0122  [                    ]
        0x0123  [                    ]
```

换句话说，`p = &n` 就是把 `n` 的地址存进 `p`。而 `p` 本身占的空间其实相当大。

> **为什么指针是 8 字节？** 按照大多数系统的惯例，存地址的变量占 8 个字节，也就是 64 位。原因是今天的计算机内存容量实在太大了，动辄几十亿字节，我们必须能够寻址超过 40 亿个地址。如果只用 32 位来寻址，指针能覆盖的最大范围就只有 40 亿左右——40 亿个地址正好对应 4 GB 的寻址空间。那意味着你的计算机装不下 8 GB 或 16 GB 内存，你的服务器也不可能拥有几十 GB 内存。所以今天我们用 64 位（8 字节）来表示指针，因为机器的内存容量已经远超从前。

这里还有一个问题：谁会在意这种细节？通常来说，作为程序员，了解底层原理是有益的，但我们很少真会关心数据具体存在内存的哪个位置。今天讲这些，主要是为了带大家看看底层到底发生了什么。

> **易错点**：既然我们只关心指针 `p` 和变量 `n`，那就完全可以把内存的大部分细节抽象掉。`0x123` 只是 `n` 恰好待的地方。程序员和计算机科学家在设计讨论时——不管是在白板上，还是在办公时间的白板上——通常就是这么处理的：我们很少关心具体地址是什么，直接用箭头来表示指针就好。

```text
        p  ────────►  n
                      │
                      └──► 内存里那个 50
```

这仅仅意味着"p 是一个指向变量 n 的指针，而 n 指向内存里的数字 50"。这个心智模型够字面吧？它就是一个非常字面意义上的指针。

### 邮箱、门牌与哈佛的泡沫手指

既然大家认可这个心智模型，我们不妨再往前推一步：这些东西在物理层面上可能是什么样子？

我们这里有几个邮箱，可以用它来把事情讲得非常清楚。变量 `p` 的物理表示就是这样一个邮箱：邮箱上贴着一张标签，里面很可能存着某个实际值的地址。最终那个值会是 `n` 的值，而我们记得这个地址是 `0x123`。

```text
        [ p ] ──►  [ 0x0120 ] ──►  [ 50 ]

        邮箱 p      信箱 p        信箱 0x0120
        贴着标签    上写的地址    门后那个 50
```

你可以把计算机内存想象成成百上千个小邮箱——更接近公寓楼的那种布局，只有一排排、一列列的邮箱，而不是独栋住宅门口的那种。每个邮箱都可以存内存中某个值的地址。所以如果这是 `p`（没有按比例绘制，因为真实邮箱就那么大），`p` 里面存着的将是一个地址，比如 `0x0120`。

而为了更有戏剧效果——毕竟这周末有一场盛大的橄榄球赛——这里就摆着一个哈佛的泡沫手指。就好像这个指针指向了那边的那个值。

**我们真的能访问内存中的某个地址吗？** 目前还没有相应的语法，但很快就会有。是的，你可以做到：顺着 `p` 指向的位置打开内存中这个地址，看，这就是我们说的那个 50。

所以每当我们讨论数值或者它们的地址时，你都可以把它们想成实际的邮箱：一个装着有用的数字，比如 50；另一个装着那个数字的地址。现在我们已经有了对应的语法，能看到如何从一个走到另一个。

### 解引用：顺着泡沫手指走过去

回到程序里。我取了 `n` 的地址存进 `p`，然后直接打印 `p` 本身——这就是我们看到那个大得多的十六进制数的原因。这通常没什么实际用途，不过看一眼还挺有意思。

现在来介绍星号的另一种用法。**解引用运算符**让我们能够真正访问那个地址。

在这个版本里，我保持 `n = 50`，让 `p` 指向 `n` 的地址，但要做的是：用语法打印出 `n` 的值，而不是 `p` 的值——通过使用 `p`。就像那句俗语说的，顺着泡沫手指的方向。

```c
#include <stdio.h>

int main(void)
{
    int n = 50;
    int *p = &n;
    printf("%i\n", *p);
}
```

直接偷懒打印 `n` 当然也行，就像第一个版本那样，但那展示不出什么有趣的东西。可在这个故事的节点上，我手里只有 `p`。事实证明，星号还有另一种用法：在变量名前直接加一个星号，这就是解引用运算符，意思是"前往 `p` 中存储的那个地址"。

`make addresses` 一下，跑 `./addresses`，回车——我们拿到了 50。

背后发生了什么？在第 5 行，和过去几周一样，我们声明了一个名叫 `n` 的变量，初始化为 50。接着第 6 行，我声明 `p` 是某个整数的地址，并把 `n` 的地址直接存进去。然后第 7 行，我指示程序打印一个整数，用 `%i`，和我们过去几周一直用的格式符一样——但具体是哪个整数？是"前往 `p` 中存储的地址，并打印出在该地址处找到的值"。

这又相当于那根泡沫手指，它指向那边，也就是我要打印的那个地址。

### 字符串在内存里长什么样

我们可以通过审视一个我们一直默认成立的"善意谎言"来理解这些的实用性。把注意力转向字符串。

到目前为止，字符串在计算机内存里一直被表示为一系列字符。在编程中"字符串"是个很普遍的概念，但在 C 语言里，严格来说并不存在名叫"字符串"的数据类型。你当然可以在 C 里用字符串，只是没法直接声明一个叫"字符串"的类型。

从这段熟悉的代码开始：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string s = "HI!";
    printf("%s\n", s);
}
```

加上 `cs50.h` 是因为这个版本里我要声明一个字符串变量并初始化为 `"HI!"`，然后用 `%s` 打印它，和第一周做的一模一样。`make addresses`，跑 `./addresses`，屏幕上显示出 `HI!`。我们一直把这些当作理所当然，现在深挖一下：这样一个简单程序的底层到底发生了什么？

我们在内存里声明的字符串，存储在内存的某个特定位置，`string s = "HI!"` 这个赋值最终可能会把数据写在内存靠下的某个地方（为了简洁，我不再把每个内存格都画出来）。里面存的是 `H`、`I`、`!`，再加上我们几周前讨论过的那个空终止符 `\0`，它表示"字符串到此结束"。

> **易错点**：即使这个词只有三个字符，它实际上占了 **4 个字节**。因为总是需要那个空终止符。

我们可以通过名字 `s` 来访问这个字符串——这种用法我们早见过。`s[0]` 是第一个字符，`s[1]` 是第二个，如果你非要去探究还可以访问 `s[3]`，但你很可能会看到那个空终止符。屏幕会显示出来，编译器或计算机也会以某种方式提醒你：你其实并不想看那个位置。

这套数组语法让我们能访问到 3 个字符。但现在我们知道，内存里的每一个位置都是可寻址的。假设这个 `H` 恰好存在地址 `0x123`：

```text
        0x123  [  'H'  ]   <- s[0]
        0x124  [  'I'  ]   <- s[1]
        0x125  [  '!'  ]   <- s[2]
        0x126  [  '\0' ]   <- s[3]，字符串到此为止
        0x127  [       ]   <- 再往后就是别的内容了
```

这些具体数字是多少并不重要，关键是字符串在内存里是以连续字节的形式存储的：一个接一个紧密排列，一个字符紧挨着一个字符，中间没有任何间隔。所以这些地址本身必须是连续的。

> **结论**：`s` 本质上就是一个字符数组。

### S 其实是一个 char *：CS50 的"善意谎言"

那这个 `s` 到底是什么？

在我们之前所有用过字符串的程序里，我们一直把 `s` 当作一个字符串，也就是一个字符序列。但更准确地说，它其实是一个数组的名称——而这本身也是一种善意的简化，因为 `s` 代表着一个更具体的值。

猜猜看：`s` 里实际存的是什么？这里有四个选项，选哪个数字存进名为 `s` 的变量里才算合理？

是 `0x123`。我们通常不会在第一周就讨论这个，因为第一周光记住分号就已经够难的了。老天保佑，可别一开始就让大家去琢磨具体的地址。

`0x123` 为什么对？因为 `s` 指向的是字符串里**第一个字符的地址**，这就已经够了。为什么只要第一个字符的地址就够了？因为空终止符这个约定会告诉计算机字符串在哪里结束。指针告诉计算机字符串从哪里开始，终止标记告诉它到哪里结束——这样中间的一切，我显然可以用一个循环全部找出来。

所以 `s` 确实是个字符串，但从技术上讲，从第一周开始 `s` 就一直是（并且始终是）一个指针，一个指向字符数组的指针。

现在可以揭示那个"善意谎言"了：从第一周开始你就认识的"字符串"这个类型，其实一直都是 `char *` 的别名。这就是关键。之前看到 `p` 时显示的 `char *` 到底是什么意思？`s` 虽然是变量名、虽然它确实表示一个字符串，但它的本质是一个字符的地址。

在课程第一周，我们通过 CS50 库里的类型别名善意地简化了这个概念：

```c
typedef char *string;
```

一个分号，从此以后 `string` 就等同于 `char *`。这样我们就不必在课程初期就纠结十六进制、地址、指针、解引用这些复杂的东西。CS50 库其实抽象掉了字符串的本质——它就是一个字符指针。

这个技术手法我们其实已经见识过了，只是形式更复杂一点。上周我们举例说过怎么建一个电话簿：用 `person` 结构体存姓名和电话号码，通过 `typedef` 自定义数据类型，那个类型其实是一个包含姓名和号码的完整结构体——复杂度就在这里——而我们只是给了这个结构一个新名字。归根结底，关键词就是 `person`。所以我们在课堂上早就创造过自己的虚构数据类型，用来实现 C 语言本身并不提供的结构。

而且 `typedef` 的用途比这更广：它本质上允许你定义自己的数据类型。比如我们想给 `int` 造个同义词——毕竟谁老记着它的全名呢——改用 `integer` 来指代，只要写一句 `typedef int integer;`，编程环境里就多了一个名叫 `integer` 的数据类型，它其实就等同于 `int`。这个例子本身没什么实用价值，但 CS50 库里的确就是用 `typedef` 让计算机把 `char *` 认成 `string` 类型的。

回到 VS Code，我们把程序大幅简化回最初的版本：用 `%s` 直接输出字符串变量 `s` 的值，也就是 `"hi!"`。程序照常运行，屏幕上直接打印出这个字符串。但如果我移除 CS50 库再重新编译，错误就来了：

```text
error: use of undeclared identifier 'string'
Did you mean 'standard input'?
```

不是这个意思——几周前我无意中犯过这个错，也不是这个意思。编译器确实不认识 `string` 这个关键字。

这没什么大不了。即使我的电脑上没装 CS50 库，我也可以把 `string` 这个词直接去掉——它只是个概念，不是 C 语言里真实存在的关键字——然后改写成 `char *`：

```c
#include <stdio.h>

int main(void)
{
    char *s = "HI!";
    printf("%s\n", s);
}
```

`make addresses`，跑 `./addresses`：它照常工作，而且完全没有依赖 CS50 的任何辅助工具。

### %s 与 %c：printf 凭什么知道该打多少

那字符指针、或者说字符串的实际本质，还有别的问题吗？有的，我一路都在等这个问题。

**`printf` 怎么知道要一直打印直到空终止符呢？这是由格式码决定的吗？**

因为我一直用的是 `%s` 格式码来打印字符串，而不是用 `%c` 打印单个字符。如果我传的是 `%s`，就意味着"请用一个循环把字符一个一个打出来，直到遇到空终止符为止"；如果传 `%c`，它打一个字符就停。

**那为什么不通过解引用来打印它呢？为什么我——或者之前任何一周——都不需要在这里写星号？**

第一个答案是，`printf` 已经替你处理了这些了：它接收的是地址，会自动根据地址去访问相应内容。那个星号（解引用操作）是在 `printf` 函数的实现代码里。

不过从概念上说，这种讲法其实不准确。`s` 代表字符串，更严谨地说是字符串中第一个字符的地址。在这种情况下，我真正需要传给 `printf` 的是**地址**，而不是具体的字符——因为我希望它被当作字符串处理，而不是单个字符。所以用 `%s` 就能达到目的，用 `%c` 则只会打印出单个字符。

我们直接从语法层面直观演示一遍：沿用我们第 2 周学过的数组语法，把 `s` 当数组来打印。

```c
    printf("%c\n", s[0]);
    printf("%c\n", s[1]);
    printf("%c\n", s[2]);
```

本身不会有什么特别有趣的结果，但它确实证明我们拿到了 `H`、`I`、`!`——它们在内存中是连续存储的。如果我愿意，可以把换行符去掉，把它们全打印在同一行。

### 指针算术，以及数组只是语法糖

用这种语法我还能做些什么？

从字面上理解：`s` 就是内存中第一个字符的地址，所以技术上我可以直接访问 `s` 指向的地址，而不必用第 2 周介绍的那套数组表示法。`*s` 表示访问那个地址；根据 `s` 的定义，你能直接定位到第一个字符。所以我可以用 `*s` 打印第一个字符，而不是用 `s[0]`：

```c
    printf("%c\n", *s);
```

要打印第二个字符，则大致相当于"定位到 `s`，然后向前移动一个字符的位置"。这里可以借一个更普遍的事实用起来：指针和地址本质上是数字，而你可以对指针本身做算术运算——这个概念叫**指针算术**，意思是给定一个地址，你可以对它做加减。你甚至可以拿指针做乘除，只不过多数情况下看起来会很奇怪；但在地址上加数字是我们肯定会做的。

写成 `*(s + 1)`，像数学课上那样记得加括号，保证运算顺序正确。往前移两个字符就是 `*(s + 2)`，两个字节的偏移量。

> **易错点**：写 `*(s + 1)` 的时候别忘了括号。刚才我又犯了个新错误，纯属手滑——最后忘了加括号。

生成地址，再生成地址：现在通过指针算术，而不是我们熟悉的数组表示法，我们又看到了 `HI!`。

那么数组到底是什么？它就是我们所谓的语法糖——这个说法有点怪，但意思就是：它只是更简洁的语法形式。说实话，没人真想写那种又解引用又加括号的代码，光是读和解析就已经让人费神了；直接写 `s[0]` 直观得多。实际上计算机是在帮我们把这种括号写法翻译成更晦涩但更准确的版本。

**就当找点乐子吧**（虽然这个"乐子"的定义可能有点特别），我们继续打印三个不同的字符串。别忘了，字符串本质上就是从某个内存地址开始的一连串字符：

```c
    printf("%s\n", s);
    printf("%s\n", s + 1);
    printf("%s\n", s + 2);
```

结果有点奇怪，我看到的是 `HI!`、`I!`、`!`。为什么？因为我是把字符串当成它本来的样子在处理——一个字符序列——但我传给 `printf` 的是第一个字符的地址，然后是第二个，接着是第三个。这三条语句都能正常工作，因为这三个"字符串"碰巧都以同一个空字符结尾，尽管 `I!` 和单独的 `!` 并不是我原本的意图。但这并不妨碍我这么做。

### 什么时候 == 有效，什么时候它骗你

最后来看一个想法的应用。我们先从两个整数开始：内存里有两个变量 `i` 和 `j`，都给它们赋值为 50，它们可能真的就存在那儿，每个占 4 个字节。

在第一周我们做过很多这样的比较，第 0 周用 `if` 和 `else` 也做过大量比较。直接试就好了：

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int i = 50;
    int j = 50;

    if (i == j)
    {
        printf("same\n");
    }
    else
    {
        printf("different\n");
    }
}
```

`make compare`，跑 `./compare`——它们确实是相同的。

那为什么上次我们想比较字符串的时候这招不管用？

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    string s = get_string("s: ");
    string t = get_string("t: ");

    if (s == t)
    {
        printf("same\n");
    }
    else
    {
        printf("different\n");
    }
}
```

一编译就报错。

> **提示**：现在回头看就完全说得通了。`s == t` 里的 `==` 比较的是两个数字，而 `s` 和 `t` 里装的不是内容，是**地址**。两个字符串碰巧内容一样、存在内存里两个不同位置时，`s == t` 拿到的就是 `0x123 == 0x456`，结果当然是 false。整数能这么比，是因为 `i` 和 `j` 里装的确实是数值本身。

也正因为如此，解决办法是引入 `strcmp` 这个字符串比较函数——它比较的是两个字符串的内容，而不是它们碰巧住在哪儿。

## 堆内存管理：malloc、free 与内存泄漏
> 对应块：BLK13 | 覆盖分集：P05中1 | 块标题（分集名）：《堆内存分配与内存泄漏》

先给大家看一条错误信息。

我在调试的时候无意中犯了个错：我获取了一个字符串，却试图把它存到一个整数里去。这种做法确实不妥——编译器当场就拦下来了。那我这就把它改成一开始就该输入的正确代码：给我一个字符串 s，再给我一个字符串 t。

改完之后执行 `make compare`，程序能正常跑了。我输入点东西试试，比如 s 和 t 都输入 "hi"。这显然是相同的。

结果程序告诉我：不同。

### 两个都是 "hi"，为什么比出来却不相等

我们前面也遇到过这个问题，当时回想起来，解决方案确实是引入一个叫 `strcmp` 的函数，我之前已经大致解释过它的作用。为什么会这样？因为你不能只比较两个值，而是需要逐个字符地比较下去，而这正是 `strcmp` 函数所实现的功能。

那就来做吧。回到文件里，在代码顶部引入字符串库 `string.h`，然后我们不再用 `s == t` 这种写法，而是改为：如果字符串比较函数 `strcmp(s, t)` 的结果恰好等于 0——根据该函数的文档说明，这表示两个字符串相等，而不是返回 1 或 -1 之类的值。

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    string s = get_string("s: ");
    string t = get_string("t: ");

    if (strcmp(s, t) == 0)
    {
        printf("Same!\n");
    }
    else
    {
        printf("Different!\n");
    }
}
```

再执行 `make compare`，输入完全一样的内容，这一次它们确实一样了。为了证明这不是偶然现象，我输入 "hi" 和 "by"，它们确实不同。所以很明显，`strcmp` 函数确实起到了作用。

### 字符串其实是个地址

那它具体是如何实现的呢？这里有第一个必须先想明白的点：**上周我们所说的字符串，从技术上讲，这周它实际上是一个字符指针**。所以我可以去掉 `string` 这个辅助轮了。我仍然会包含 CS50 库，因为正如我们今天课程结束时将看到的，`get_string`、`get_int` 以及 CS50 库中的所有那些 `get_` 函数实际上仍然很有用——在 C 语言中，如果不使用这类函数，获取用户输入会非常麻烦。但我打算去掉我们之前认为存在的那种数据类型 `string`。这样操作仍然会和之前一样有效。

那字符串在计算机内存中究竟是怎么运作的呢？我认为它很可能像这样存储：

```text
        s                                       t
        |                                       |
        v                                       v
   +-------------+                        +-------------+
   | 0x0000123   |                        | 0x0000456   |
   +-------------+                        +-------------+
        |                                       |
        v                                       v
   +----+----+----+----+                 +----+----+----+----+
   | h  | i  | g  | h  |                 | h  | i  | g  | h  |
   +----+----+----+----+                 +----+----+----+----+
    0x123 124  125  126                 0x456 457  458  459
```

请注意，现在的 s 具有双重含义。它是一个地址，这意味着它占用 8 个字节或 64 位，但实际的字符最终会存储在计算机内存的其他位置。这就是它与整型变量的不同之处。

> **结论**：整型变量 i 和 j 的值恰好存储在它们命名的变量位置中。但对于字符串，变量本身并不包含字符串内容，而是存储了该字符串第一个字符的地址。这个地址可能位于计算机内存中的任何位置。

> **提示**：s 里装的是 0x123 这 8 个字节；"high" 这 4 个字符在 0x123 之后另外占地方。把"变量"和"变量指向的东西"分开看，这是 C 里最该早点养成的习惯。

当我创建 t 的时候，它可能占用另外 8 个字节的空间，存储的是我输入的第二个字符串——它并不在相同的地址，而是位于 0x456、0x457、0x458 和 0x459。

如果计算机真的足够智能且慷慨，它或许能注意到："哦，等等，这个内容你之前已经输入过了，我可以直接让你指向另一块内存区域。"但实际情况并非如此。当你调用 `get_string` 函数时，无论用户输入什么内容，系统都会为其分配独立的内存块，即使巧合之下输入的内容完全相同也不例外。所以 t 里的值应该是 0x456，因为这是字符串 t 中第一个字符的起始地址。

至此，我们已经在内存中存储了两个字符串，并且也分配了两个指针。从抽象层面来看，这实际上相当于 s 指向左侧的内存块，而 t 指向右侧的内存块。

那为什么字符串比较在实际操作中是必要的呢？因为 `strcmp` 接收的是 s 和 t 的地址。这个由几十年前其他人编写的函数，内部包含一个 `for` 循环或 `while` 循环，它会从每个字符串的起始位置开始，逐个字符地进行比较。这正是它的设计目的。

### 那 s == t 到底比较了什么

相比之下，刚才以及上周我错误地使用双等号来比较字符串时，实际比较的是什么呢？

嗯，如果你直接比较 `s == t`，这就像是在问：地址 0x123 是否等于地址 0x456？这显然是不成立的，因为这两个地址字面上就是不同的。所以我上周和今天得到的结果其实是正确的——这些地址确实不同，但从概念上讲，我原本希望程序比较的是字符串中的实际字符，而不是简单地比较地址本身。

那么，我们该如何解决这类问题呢？使用 `strcmp` 函数可以让我们逐字符比较字符串，而无需自己编写 `for` 循环或 `while` 循环。`strcmp` 函数就是专门来做这个的。

这一点我们也能直接看出来。如果我回到 VS Code 这里，获取这两个字符串，并且为了验证一下，直接用 `printf` 配合 `%p` 格式符把它们两个的地址打印出来：

```c
printf("s is at %p\n", s);
printf("t is at %p\n", t);
```

即使我输入完全相同的字符串，运行这个版本的程序时，我们也会看到两个不同的地址。这是我的第一个输入，这是我的第二个，这两个地址——虽然差别很细微，但确实完全不同。第一个地址以 B0 结尾，第二个以 F0 结尾，两者都是十六进制数值。

刚才有同学提了一个非常好的问题：当你为字符串或整数分配内存时，计算机是如何决定把它存放在哪个位置的呢？

计算机会为不同的用途分配不同的内存区域。事实上，我们今天休息后要讨论的主题之一正是这个：计算机如何决定数据在内存中的布局。内存分配通常是有意设计的，并且地址往往会自动递增，因此在可能的情况下，数据会一个接一个地连续存放。但随着程序运行，内存布局会逐渐变得混乱，尤其是在大型程序中，因为数据会频繁地在内存中进行增删操作。后续我们会深入探讨。

### 赋值不是复制

休息之前我们来看另一个例子，它或许能说明如果不理解这些底层构建模块可能会导致什么问题。

这次我们来创建一个程序，目标是复制两个字符串。乍一看这似乎很合理，毕竟复制两个整数确实很简单——直接让一个变量等于另一个就行了。但字符串的情况可不一样。

我们来打开一个名为 `copy.c` 的新程序：

```c
#include <cs50.h>
#include <ctype.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    // 获取用户输入的字符串 s
    string s = get_string("s: ");

    // 尝试把 s 拷贝到新变量 t
    string t = s;

    // 把 t 的首字母改成大写
    t[0] = toupper(t[0]);

    printf("s is %s\n", s);
    printf("t is %s\n", t);
}
```

包含 `ctype.h` 的原因我们稍后会看到，其实几周前我们就接触过了；`string.h` 留给 `toupper` 之外的字符串处理；`stdio.h` 照例包含；CS50 头文件是为了 `get_string`。

现在我们可以把复制后的 t 当作数组来处理，这在第二周的学习内容中是允许的。第 12 行代码的右侧，实际上是在调用 C 类型库中的 `toupper` 函数——这个函数我们在几周前已经使用过了——传入复制字符串 t 的第一个字符，然后更新 t 的实际第一个字符。这样我们就能将 t 的首字母大写，而不会影响 s。至少我们以为是这样的。

运行 `make copy`，我输入小写字母 "high"。我们先输入小写字母 e 的 high。

然后我们发现一个有趣的现象：**尽管我只修改了 `t[0]` 这一个字符，但 s 和 t 的首字母都变成了大写。** 在进行这次复制操作后，我并没有修改 s 的内容。

### 为什么改一个字母两个字符串都变了

我们不妨去掉其中一个辅助轮？严格来说，字符串其实并不存在。它始终是一个字符指针。

现在更清楚了，s 就是字符串的地址。呃，那是用户输入的内容，但它实际上复制了什么呢？用户输入内容的地址——这两者实际上是同一个地址。

所以实际上，我们可以这样来形象地理解它：

```text
        s = 0x123                 t = 0x123
          |                         |
          +------------+------------+
                       v
                  +----+----+----+----+
                  | h  | i  | g  | h  |
                  +----+----+----+----+
                   0x123 124  125  126

  执行 t[0] = toupper(t[0]) 之后：

                  +----+----+----+----+
                  | H  | i  | g  | h  |
                  +----+----+----+----+
                   0x123 124  125  126
```

因为 s 和 t 指向同一块内存区域，所以当我访问 `t[0]` 并定位到 t 的第一个字符（索引为 0）时，实际上访问的正是 s 所指向的那块内存区域。当那个小写字母 "h" 被改为大写 "H" 时，就相当于 s 和 t 同时指向的字符发生了改变。

如果你对语法感兴趣，回想一下，我确实使用了数组下标表示法，但同样可以说成是"访问 t 所指向的地址、访问第一个字符的地址"，这在功能上完全等效。我们只是没有使用方括号这种语法糖而已。

> **易错点**：`t = s` 复制的是**地址**，不是内容。改副本的字符就是在改原件——这就是为什么看似两个版本的 "high" 都被大写了，无论是原字符串还是拷贝字符串。

### malloc 与 free：给副本一块自己的内存

那么，我们该如何解决这个问题呢？

我们需要引入几个新的解决方案，具体来说就是这里要介绍的两个新函数。`malloc` 是一个用于动态分配内存的函数。所以，内存分配函数（即 `malloc`）和内存释放函数（`free`）是功能相反的两个函数——当你不再需要新分配的内存时，可以通过 `free` 将其归还给计算机，以便用于其他用途。

那么，仅凭这两个函数，我敢说我们现在就能解决这个问题了：通过在内存中实际复制字符串的概念，将 "HI!" 和空字符复制到内存的其他位置，这样我们就能真正操作这个副本了。

#### 该申请多少字节

如果我想创建 s 的一个副本，我需要向计算机申请与 s 所占内存大小相同的一块空间。

那么，"high" 这个字符串在内存中占用了多少字节呢？没错，是 4 个字节，因为还需要包含空字符。

我们该如何计算这个大小呢？让我再声明一个字符指针 t，不过现在我们不需要再用那个善意的谎言了。然后把它赋值为 `malloc` 的返回值，这个函数会返回一块内存的地址给我。

严格来说，我只需要 4 个字节，所以我可以调用 `malloc(4)`，这实际上会向运行在 VS Code 云端的操作系统申请 4 字节的内存，分配在我屏幕上一直画的那个黑黄网格的某个位置。我不知道它具体会分配在哪里，但这并不重要，因为 `malloc` 的返回值就是这块内存首字节的地址。

现在这样写死代码有点蠢，因为我们不知道用户会输入什么。但我们可以采用更动态的方式，利用我们熟悉的老朋友 `strlen` 函数，让计算机直接告诉我们字符串 s 的长度，然后再加上 1：

```c
char *t = malloc(strlen(s) + 1);
```

虽然实际中 "high" 的长度是 3，但在底层实现中，我们实际上需要第 4 个字节来存放空字符，所以这里要加 1。

现在要使用 `malloc` 函数，我实际上需要在这里引入另一个头文件，也就是标准库头文件 `stdlib.h`：

```c
#include <stdlib.h>
```

这样我就能访问到 `malloc` 的函数原型，进而使用它了。

#### 怎么把字符一个一个搬过去

有了这块分配好的内存，接下来就需要由我来复制这个字符串了。

我该如何将字符串从 s 复制到 t 呢？实现这个功能有多种方法，不过我这里建议可以这样写循环：

```c
int n = strlen(s);
char *t = malloc(n + 1);

for (int i = 0; i <= n; i++)
{
    t[i] = s[i];
}
```

在循环内部，我们只需要这样赋值：`t[i] = s[i];`，将 s 的值赋给 t，这样就能逐字逐句、非常机械地把 s 中的每个字符复制到 t 里。接着在下面这里，我们继续用 `toupper` 函数将 t 的第一个字符大写，和之前一样。

在程序的最底部，为了确保这次我们没有搞砸，我们输出 s 本身的值作为验证，同时也输出 t 的值。

不过，我还没完全做完。这里存在一个设计缺陷和错误，不过比较隐蔽。有谁想指出其中哪一个问题吗？style50 肯定不会喜欢这个写法。

没错，因为 `strlen` 函数返回的是字符串的实际长度（不包括空字符），所以这里似乎意外地漏掉了复制空字符。

我可以通过几种不同的方式来解决这个问题。比如，我可以在循环的底部，手动添加类似 `t[4] = '\0'` 的语句来终止字符串，因为我知道它必须以空字符结尾。这种做法也不太推荐——我不应该硬编码数字 4，这些写法都太随意了。所以不要这样做。

那么，我可以把循环条件改成 `i <= n`：因为如果 s 的长度是 3，但使用小于等于条件，循环自然会执行 4 次，毕竟我们总是从 0 开始计数。这样我觉得就解决了那个问题。

但现在还存在一个设计缺陷，虽然很细微。干嘛要问计算机 s 的长度是多少呢？s 的长度是多少？s 的长度是多少？而且每次循环都这样。所以这就是我们引入这个小技巧的原因：你可以设置另一个整型变量 n，让它等于字符串的长度，然后在分号后面继续将 i 与 n 进行比较。这样一来，你就不会像之前那样浪费地反复调用函数了。

那为什么要写 `i <= n` 而不是 `i < n + 1`？因为两者在这里完全等价，但 `i <= n` 少做一次加法，而且 n 的含义直接对应 `strlen` 的返回值，不用在脑子里再换算一次。这种"把语义直接写进条件"的小心思，读代码的人会感谢你。

好，如果我没搞错其他部分的话，让我进终端看看。

哎呀，我是不是哪里搞错了？我……没错，我确实搞错了。这个我也应该放回去才对。谢谢你。

现在执行 `make copy`，我要输入全小写的 hi 并按回车键。现在你会看到，字符串 s 没有发生变化，它再次以小写形式打印出来，但这里的 t 实际上已经是大写的了。

#### 复制完的那块内存里原来是什么

那么，为什么会这样呢？

在这种情况下，发生的是：我在内存中已经有了 s，但这次，当我分配 t 时，我使用了 `malloc` 函数来获取一整块内存空间。这块内存最初只包含一些我们之前称为"垃圾值"的未知内容。我就先让它们保持空白状态，但实际情况就是如此。

```text
        s = 0x123                 t = 0x456
          |                         |
          v                         v
   +----+----+----+----+       +----+----+----+----+
   | h  | i  | g  | \0 |       | H  | i  | g  | \0 |
   +----+----+----+----+       +----+----+----+----+
   0x123 124  125  126       0x456 457  458  459
```

为了便于讨论，假设这块内存的地址是 0x456、0x78、0x9。当我将 t 设置为 `malloc` 函数的返回值时，实际上就相当于 t 指向了这块内存区域。接着，在我的循环中，当我从零开始遍历到 n 时，这意味着先复制 h，再复制 i，再复制 g，最后因为等号的存在还会复制空字符——只不过不打印它。

必须承认，仅仅为了复制几个字符串，这样做确实有点繁琐，工作量不小。我们能不能稍微优化一下这个方法呢？

实际上，我们可以做得更好，因为通过引入相关库，C 语言本身就提供了用于复制字符串的函数。所以如果我回到这段代码，我根本不需要这个 `for` 循环——只要我为字符串分配了足够的内存（我认为我已经做到了），我实际上可以直接使用一个名为 `strcpy` 的函数，并按照目标地址和源地址的顺序传入参数：

```c
strcpy(t, s);
```

这感觉有点反直觉，但这就是将 s 的字节复制到 t 中的标准做法。很容易搞混，但根据文档说明，**目标地址在前，源字符串在后**，千万别弄反了。

> **易错点**：`strcpy(t, s)` 是"把 s 抄进 t"，参数顺序和"赋值号"的直觉正好相反。写反了不会报错，只会把一片垃圾值和半个 s 搅在一起——这种 bug 往往要到打印的时候才炸。

### NULL：被永久留空的地址

这里我想指出，这里可能会出问题，而且实际上这会让程序看起来比感觉中复杂得多。理想情况是这样，但我这里有点偷懒了。

这里有很多可能出错的地方，因此了解这些函数的返回值是很有必要的。

所以一直以来，我们使用的某些函数（比如 `get_string`）可能会返回一个令人困惑的值：`NULL`。几十年前，人们决定将其中一个称为 NUL，而另一些人则决定将这个新事物命名为 NULL。

这两个东西非常容易混，我们现在就把它们彻底分清楚：

| | NUL | NULL |
| --- | --- | --- |
| 是什么 | 空终止符 | 一个特殊的内存地址 |
| 本质 | 由 8 位组成的单字节，所有位均为零 | 地址 `0x0`，这个地址上不应该存放任何内容 |
| 用途 | 标记字符串到此结束 | 表示"这里没有值"或"出错了" |
| 长什么样 | `'\0'` | 指针的值为 0 |

NUL（读作 null）其实就是空终止符，它是一个由 8 位组成的单字节，所有位均为零。这一点我们已经了解了几周。

NULL 实际上是一个特殊的内存地址，即 `0x0`，这个地址上不应该存放任何内容。

为什么非要留一个空地址出来呢？每当我描述左上角时，我会说这是地址 0，这是地址 1，这是地址 2——这是人类多年前的约定，就这么定了。你知道吗？那我们就干脆把地址 0 的位置空出来，永远不在那里存放任何内容。这样一来，我们就有了一个特殊值，可以用来在程序出错时发出信号。所以，人们干脆决定：不要使用内存地址 `0x0` 以及紧随其后的几个字节。

> **结论**：一个全零的字节有 NUL 这个角色，一个值为 0 的指针有 NULL 这个角色。前者是数据，后者是"这里没有数据"的信号。名字长得像，类型完全不同。

### 那些从第一周起就该写的检查

所以这意味着什么？说实话，从第一周开始，我的代码就一直存在潜在问题。

在 VS Code 里，我用了 `get_string`、`malloc` 和 `strcpy` 这些函数，还加了一堆打印语句，但其实我并没有像应该做的那样，添加足够多的错误检查。

其实，如果你去查一下 `get_string` 的官方文档——虽然我们之前一直没提过这点——就会发现，当出现错误时，`get_string` 可能会返回 NULL。

如果用户输入了一大段文本，怎么还会出错呢？会不会是因为计算机内存不够，装不下他们输入的所有内容？没错。你肯定不希望只拿到部分文本，却完全不知道哪里出了问题。`get_string` 的设计就是返回一个特殊的哨兵值、全大写的 NULL，这意思就是我没法满足你的要求——我无法返回一个正确的值给你，这里返回的是一个错误。

所以，从第一周开始我就应该一直这么做，但我们有意识地没有这样做，因为它会增加太多开销。就是检查：

```c
string s = get_string("s: ");
if (s == NULL)
{
    return 1;
}
```

如果 s 等于 NULL，那么我们应该完全中止程序，比如像我们之前做的那样返回 1，来表示错误，意思是由于 `get_string` 没有正常工作，我们无法继续执行。

这一点对于 `malloc` 函数也同样适用。严格来说，我们应该说如果 t 中的地址也等于 NULL，也就是 `0x0`，我们也应该返回 1，因为某些原因——嗯，出错了。

```c
char *t = malloc(n + 1);
if (t == NULL)
{
    return 1;
}
```

不过还有另一个问题。即使是 `toupper` 函数也默认假设用户确实输入了某些内容。

如果用户直接按了回车键呢？嗯，那也是一个有效的字符串，这就是所谓的"空字符串"。但"空"的长度是多少呢？长度会是 0，这就带来了问题：如果你试图访问第一个位置的字符，那里实际上有什么呢？实际上，那里是空字符（null character），看起来你甚至不应该尝试对它进行大写转换。

所以，我们真正应该做的也是检查字符串 s 的长度是否大于 0。你还需要费心去大写那个首字符吗？我的意思是，首先，这至少是毫无意义的，因为如果没有字符串，就谈不上大写转换。最糟糕的情况是，我可能会因为访问了不该访问的内存而引发问题。

> **易错点**：返回 0 表示成功，返回 1 表示失败。程序正常跑到底才 return 0，中途任何一步拿不到需要的东西就 return 1——这不是多余的仪式，而是让调用者知道结果可信的唯一办法。

### 内存泄漏：借了不还

在第 15 行，我向计算机申请内存，它会分配给我那 4 个字节，但从技术上讲，我从未归还这些内存。

因此，尽管这个程序非常简短，很快就会结束运行，这算不上什么大问题——但在像服务器这类需要长时间运行的程序中，计算机将自动回收这些内存。如果你使用 `malloc` 申请了内存却从不释放，换句话说，就是从不将其归还给计算机，你的电脑可能会变得越来越慢。

本质上是内存正在耗尽。并非物理上耗尽，而是计算机认为它正在使用所有内存，即使这些内存实际上并未被有效利用。

作为开发者，你最清楚何时不再需要内存。因此，当程序完全处理完变量 t 后，你应当相应地调用 `free(t)` 来释放内存，传入先前分配的内存地址，这样操作系统就能回收这部分内存。

```c
    printf("s is %s\n", s);
    printf("t is %s\n", t);

    free(t);
}
```

如果不这样做，就会导致所谓的"内存泄漏"。如果你用过 Mac、Windows、iPhone 或 Android 上的程序，有时会发现它们变得越来越慢。这通常是因为开发者没有及时释放不再需要的内存，导致程序运行效率逐渐下降。

休息期间有人提出了一个问题：我是否也应该对字符串 s 调用 `free` 函数，因为 s 实际上是从 `get_string` 函数返回的。

简单来说，答案是不需要。这是过去几周我们有意为之的设计：CS50 库中 `get_string` 函数的实现机制，会在你不再需要它返回的内存时自动释放这些内存。所以这一点需要注意——这是底层实现的巧妙设计。不过，一旦你不再使用这个功能，这种自动内存管理机制就会失效。但由于我确实使用了 `malloc` 函数为 t 分配了内存，所以我必须手动释放这部分特定的内存。

> **结论**：谁分配的谁负责。`malloc` 拿来的内存必须由你自己 `free`；`get_string` 替你分配的，你不要插手。

稍后我们会详细揭示这些问题何时以及为何会导致严重后果。不过，在继续之前，我们先来看一段斯坦福大学朋友制作的黏土动画短片。

### Valgrind：让隐藏的错误现形

好在有一些工具可以帮助我们检测与内存相关的错误。接下来，我们简要介绍另一个工具——Valgrind。它是 debug50、printf 和 duck 等调试工具的有力补充，特别适合用于追踪内存相关的错误。

现在，让我切换到 VS Code，打开一个我事先写好的程序。虽然这个程序本身没什么实际用途，但它能很好地演示一些常见的错误情况。

#### memory.c 里已经埋好的两个错

在 `memory.c` 文件中，我们有以下代码。我们引入了 `stdio.h` 和 `stdlib.h` 这两个标准库头文件。这里需要提醒一下，当你需要使用 `malloc` 函数时，就必须引入这个头文件，相应地，`free` 函数也需要它。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *x = malloc(3 * 4);

    x[0] = 72;
    x[1] = 73;
    x[3] = 33;
}
```

这里有三件事值得停下来看。

第一，我以一种比较特别的方式分配了 3 个整数的内存空间。这是因为 `malloc` 函数需要传入的参数是你希望分配的字节数。据我所知，在大多数系统中，一个整数确实占用 4 个字节。因此，如果我需要为 3 个整数分配空间，我可以直接计算 3 乘以 4 等于 12，然后传入 12 作为参数。`malloc` 的返回值被赋给左侧的变量 x，而 x 本身是一个指向整数的指针，更具体地说，它指向的是一块能够容纳 3 个整数的连续内存空间。

但这里写 `3 * 4` 虽然能算对，却通常不建议这么做，因为这样会降低代码的可移植性——在其他系统中，整数可能不是 4 个字节。实际上，你可以使用 `sizeof` 运算符来直接询问计算机：在当前系统中，某个数据类型到底占用多少字节。

```c
int *x = malloc(3 * sizeof(int));
```

而对于 `char` 类型，你总是会得到 1。对于 `int` 类型，通常会返回 4，其他数据类型也是如此。但如果你需要获取 3 个整数的空间，使用 `sizeof` 是更灵活、更动态的查询方式。

第二，索引是从 0 开始的。即使你不清楚第 8 行发生了什么，我犯的第一个错误是什么？那么第 9、10、11 行呢？我哪里做错了？我的索引用错了。就像我们这几周一直强调的，无论是数组还是使用方括号语法，计数总是从 0 开始，然后是 1、2，而不是 1、2、3。

第三，既然我已经分配了这 12 个字节，这个版本的程序里我还犯了什么其他错误？还缺少内存释放函数。所以我实际上没有调用 `free`，因此这个程序存在内存泄漏——它申请了内存却从不归还。

#### Valgrind 到底说了什么

现在这样已经很不错了，要知道我们几个人只是粗略看了看代码就把它调试出来了。但并非所有人都能做到这样，也并非所有程序都这么简单，尤其是当程序规模变大、逻辑变得更复杂时。所以 Valgrind 的存在意义就是帮助你发现这类错误。

比如，当我执行 `make memory` 编译这个程序，然后执行 `./memory` 时，乍一看程序似乎完全正常——毕竟编译和运行过程中都没有出现任何错误提示。但我确信，我们刚才看到的代码里至少存在两个错误。只是我们运气不错，程序目前还没有因为这些错误而崩溃。因此，这是一个更隐蔽、更难发现的程序缺陷。

接下来我执行 `valgrind ./memory`。这个程序类似于 debug50，但现在使用的工具名称是 Valgrind。这不是 CS50 课程特有的工具，这是程序员普遍使用的一款工具。

说实话，按下回车键后，输出的内容会相当混乱。它的复杂程度远远超出了实际需求。他们在这里放了这个数字，虽然它有特定含义，但每行输出都显示它实在有些多余。所以乍一看会让人眼花缭乱。但当你训练自己学会捕捉关键信息后，就能从中发现一些有价值的线索：

```text
==1234== Invalid write of size 4 at 0x...
==1234==    at 0x...: memory.c:11
...
==1234== 12 bytes in 1 block are definitely lost in loss record 1 of 1
==1234==    at 0x...: memory.c:8
...
==1234== HEAP SUMMARY:
==1234==     in use at exit: 12 bytes in 1 blocks
==1234==   total heap usage: 1 allocs, 1 frees, 12 bytes allocated
```

这两行是最值钱的信息，我们逐条拆开看。

**第一处：一个大小为 4 字节的非法写入错误，看起来与第 11 行代码有关。** 我们直接定位到那一行看看——"写入"在这里指的是修改某个内存位置的值；读取是获取值，写入是修改值，它们确实是相反的操作。了解数据类型的大小（比如 4 字节）通常很有用，因为内存操作错误往往与访问错误大小的内存区域有关：你正在尝试以错误的方式写入 4 字节数据。

那么为什么第 11 行是无效的呢？确切地说，是因为索引越界了——我访问了不该访问的内存区域。如果我向计算机申请存放 3 个整数的空间，每个整数占 4 字节，那么我应该获得索引 0、1 和 2 的位置，而不是索引 3 的位置。

所以要想有效利用这些信息，你仍然需要具备一定的编程知识基础。无效的 4 字节写入权限——但当你逐渐训练自己的思维和观察力，能够敏锐地捕捉到这类问题时，比如"哎呀，我真糊涂，得赶紧修复这个漏洞"，情况就会不同了。

**第二处：这份内存泄漏报告确实令人担忧。** 确认存在一个内存块泄漏，大小为 12 字节。虽然我现在还不清楚"1 个内存块"具体指什么，但 12 字节这个数字应该很熟悉。因为通常我们知道一个整数占 4 字节，而如果你申请了 3 个整数所需的空间——哦，这就对应上 12 字节了。

所以程序在运行过程中，我以某种方式"丢失"了 12 字节的内存——这里不是字面意义的丢失，而是指程序结束时，这部分内存既未被释放，也未通过 `free` 函数归还给系统。你申请的内存，一块都没还。

有时你在这里会看到略有不同的输出信息，描述很详细，但关键信息是——**第 8 行代码正是这个错误的具体源头**。第 8 行是什么？是我们调用 `malloc` 的那一行。所以这同样是一个线索，像面包屑一样指引我找到修复这个问题的解决方案。

> **提示**：Valgrind 报"第 8 行"不代表第 8 行写错了。第 8 行分配了内存，真正的问题是分配之后没人还。顺着分配点往后找，就能找到漏掉的 `free`。

#### 改完之后

既然我在第 8 行进行了内存分配，那么可能出错的操作其实很有限。看来我确实需要在后续操作中释放这块内存。那我们来同时解决这两个问题。

第一个问题只是索引计算错误，把 `x[3] = 33` 改成 `x[2] = 33`。接下来我们解决第二个问题：只需在程序最后释放变量 x，这样就能确保万无一失。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *x = malloc(3 * sizeof(int));
    if (x == NULL)
    {
        return 1;
    }

    x[0] = 72;
    x[1] = 73;
    x[2] = 33;

    free(x);

    return 0;
}
```

不过 Valgrind 未能检测到"忘记写 NULL 检查"这个错误，因为它并非每次都会发生。

但还存在另一种可能出错的情况，这与第 8 行代码有关。我该怎么做？嗯，我正在处理数组，但别忘了我们可以对内存块使用数组语法。严格来说，第 8 行代码执行的操作是这样的：它从计算机中分配了 12 字节的内存空间，仅仅是为了演示 `malloc` 的工作原理，并将该内存块首字节的地址存储在名为 x 的变量中。

方括号表示法只是一种语法糖，它允许我修改 x 地址处的值。我也可以直接使用指针操作：

```c
*x = 72;
*(x + 1) = 73;
*(x + 2) = 33;
```

这样就是让指针定位到 x 所在位置，然后在那个地址存入 72；定位到 x + 1 的位置，将 73 存入该地址；定位到 x + 2 的位置，将 33 存入该地址。使用指针算术实现。

但这两者其实是完全相同的操作，并非不同。一般来说，大多数人都会选择使用方括号表示法，因为它更简洁、更易于阅读和编写。

还有，根据我们前面的示例，每当调用 `malloc` 获取字符串（以及其他一些类似函数）时，您都应该进行相应的处理：检查是否为空指针，没错。因为如果 `malloc` 出现错误，就说明内存不足了。malloc 出错意味着内存不足了。无论出于何种原因，您都不应继续访问该内存，因为它可能指向空地址，即 `0x0`。

您真正应该检查的是：如果 x 等于 NULL，那么这里就没有更多工作可做了。我们只需在这里返回 1，而只有当程序执行到最底部时，才可能返回 0 来表示成功——明确表示操作确实成功了。

现在重新编译内存程序，编译器没有报错，内存检查也正常，不过第一次运行时它本来就是正常的。现在让我们运行 Valgrind。

这结果其实相当不错。虽然乍一看同样吓人，但这次的输出内容短多了，大部分都是些无关紧要的细节，没什么实质性的发现。

```text
==1234== HEAP SUMMARY:
==1234==     in use at exit: 0 bytes in 0 blocks
==1234==   total heap usage: 1 allocs, 1 frees, 12 bytes allocated
==1234== All heap blocks were freed -- no leaks are possible
==1234== ERROR SUMMARY: 0 errors from 0 contexts
```

你看，所有堆内存块都已被释放，不可能存在内存泄漏。"堆"这个概念我们稍后会详细讨论，但这里的结果表明程序没有问题。实际上，零错误是个好消息。

简而言之，Valgrind 是我们将要使用的最神秘难懂的程序之一。它的输出结果实际上是为那些更熟悉底层细节的人设计的。但其中仍然蕴含着宝贵的见解：如果你仔细查看那些指向特定文件和行号的线索，很可能就会发现最隐蔽的程序错误。

### 垃圾值：从来没有被写入过的内存

实际上，另一种常见的错误类型是：我们确实访问了本不该访问的内存区域。

那么，让我新建一个名为 `garbage.c` 的程序，演示我们通常所说的"垃圾值"——即内存中残留的、并非由我们主动写入的数据。

我引入标准输入输出头文件。我引入标准库头文件——然后，我继续编写代码——实际上这次不需要标准库了。

```c
#include <stdio.h>

int main(void)
{
    int scores[1024];

    for (int i = 0; i < 1024; i++)
    {
        printf("%i\n", scores[i]);
    }
}
```

在主函数内部，我打算声明一个数组，比如用来存放大量考试成绩之类的数据。我们以前通常只处理少量数据，但这次假设有 1024 个元素。然后用 `for` 循环遍历，输出每一个分数。

当然，我显然忘记在这段程序中做一件事了：我实际上还没有真正输入任何分数数据。就像我让计算机分配了一个能容纳 1024 个整数的数组，但我既没有用 `get_int` 输入，也没有像以前那样手动输入任何测验分数。

这是我有意想展示的：内存中的垃圾值。现在第 8 行的这个循环，实际上会依次输出第一个、第二个、第三个，直到所有 1024 个整数，但它们应该都是垃圾值，因为我还没有在这些地址中存入任何数据。

那我们这就来生成一些垃圾值吧。输出了大量垃圾值。所以当我们抽象地讨论垃圾值时，比如这里出现了一些随机的零、一个 25、一个 32000、一个负数等等，这本质是因为计算机内存中残留了之前可能发生过的操作痕迹——不一定是此刻由我产生的。也就是说，你根本不应该去触碰那些内存区域。

> **易错点**：`int scores[1024];` 只是**腾出**1024 个格子，没有往里面放任何东西。声明不等于初始化。你读到的不是"零值"，是这块内存上辈子的住户留下的东西。

### 未初始化的指针会指向哪里

让我们来看另一个程序的例子。它可能存在内存错误，我们也来仔细分析一下。

所以这里我们有一个程序，它不需要命令行参数：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *x;
    int *y;

    x = malloc(sizeof(int));

    *x = 42;
    *y = 13;
}
```

上面这两行代码声明了两个指针，但尚未将它们初始化为任何变量，这是可以的——你不需要用等号给它们赋任何变量值。你最终只需要给它们赋个值就行。但这两行代码只是告诉计算机：给我一个变量 x，它用来存储一个整数的地址；再给我另一个变量 y，它用来存储另一个整数的地址。

接下来会发生什么？就在 `x = malloc(sizeof(int))` 这行代码里。在这个简单的例子中，我们只为一个整数分配了足够的内存空间，因为这是一个基础练习，这么做只是为了演示 `malloc` 函数的工作原理，暂时没有其他实际意义。`malloc` 函数返回的是那块内存的地址，所以这个地址就被赋给了变量 x。所以现在 x 指向了内存中的某个位置——一个 4 字节的空间，完全可以用来存放一个值。

我们该怎么操作呢？嗯，如果你使用解引用运算符 `*` 对 x 进行操作，就意味着访问那块内存，并将数字 42 存入其中。这完全没问题。

这意味着，访问 y 中存储的地址，并将那个不吉利的数字 13 存放到该地址对应的内存位置。说它"不吉利"可一点不夸张，因为此时此刻 y 到底指向哪里呢？

**它指向的只是一个随机的垃圾地址。**

为什么？因为如果你不初始化 y，谁知道它会指向哪里呢？可能是 0，可能是 25，也可能是 32000 甚至负数，就像我们之前看到的例子一样。除非你自己把值放进去，否则你根本不知道 x 和 y 里会是什么值。

所以这里用红色高亮显示，因为如果你解引用一个无效或伪造的指针，后果会比访问可能没有值的变量更严重。如果你解引用一个地址并试图访问某个随机位置，计算机通常不会接受这种行为。

### Binky 与那根解引用魔杖

事实上，我们斯坦福的朋友们精彩地再现了这个特定场景。虽然这个例子为了能一次性在屏幕上展示而显得有些刻意，但如果我们不检查这些值并赋予有效的值，确实会导致糟糕的后果。

那么现在，我给大家展示一个 Binky。这是来自我们斯坦福的朋友 Nick Parlante 的黏土动画作品。如果我们可以把灯光调暗，营造出不必要的戏剧效果的话。

"嘿，Binky，醒醒。该玩指针游戏了。"

"那是什么？学习指针。"

"哦，太棒了。要开始的话，我想我们得先准备几个指针。"

"好的，这段代码分配了两个指针，它们可以指向整数。"

"嗯，我看到这两个指针了，但它们好像没指向任何东西。"

"没错。一开始，指针并不指向任何东西。它们指向的对象被称为指针目标，而设置指针目标是另一个独立的步骤。"

"哦，对对对，我知道指针目标是独立存在的。"

"那么，如何分配一个指针目标呢？"

"好的，这段代码分配了一个新的整数指针目标，而这一部分则将指针 x 指向它。"

"嘿，这样看起来好多了。那么，让它执行一些操作吧。好的，我将通过解引用指针 x，将数值 42 存储到它指向的目标中。要完成这个操作，我需要用到解引用的'魔法棒'——你的解引用魔法棒。啊，嗯，这，这真是太棒了。"

"哦，我明白了。现在 y 指向了和 x 相同的位置。等等，这么说现在 y 的问题解决了，它有了指向的目标。那么你可以再次使用解引用魔杖，把 13 传过去。"

"好的，开始吧。嘿，快看这个。现在对 y 进行解引用操作成功了，而且由于两个指针共享着同一个目标对象，它们都能看到数值 13。"

"是啊，共享就共享吧，无所谓了。那我们现在要交换位置吗？哎呀，时间到了。"

Nick，我简直不敢想象这得花多长时间。但关键细节在于：**当我们执行这行代码——解引用一个未分配真实值的无效指针时，Binky 就遭殃了。**

那不过是个垃圾值罢了。

那现在该怎么解决呢？就像 Nick 建议的那样，别那么做，至少得采取些合理的措施——比如把 x 设为指向 y，这并非要复制什么内容，而是直接让 x 指向内存中的同一位置。让指针指向与 x 相同的内存位置，那么这样的代码就完全没问题了。你可以访问那个地址——它恰好与存储 42 的地址相同，这就是为什么在黏土动画演示中，我们看到 42 变成了 13。

> **结论**：指针的三个动作要分清楚——① 声明一个指针变量；② 让它指向某个目标；③ 通过解引用往目标里存值。`int *y;` 只做了第 ① 步，第 ③ 步就崩。少一步都不能省。

### 三个杯子，和一次注定不成功的翻译

在现实世界里交换两杯液体，是全世界小朋友都会的事。唯一的难点是：没有第三个杯子，你根本没法动手。

桌子上摆两只杯子，一只装蓝色液体，一只装橙色液体。我请 Olivia 上台把这两杯对调。她站在那儿愣了两秒——因为她手上只有两只杯子——于是我递给她一只空杯子，让她拿来当临时变量。于是就有了那个谁都不会忘掉的瞬间：蓝色液体倒进空杯，橙色液体倒进原来装蓝色的那只杯子，空杯里的蓝色液体最后倒进原来装橙色的那只杯子。掌声。

> "在你来之前，我们这儿已经小小庆祝过了。"

这就是"交换需要临时变量"的全部秘密。它同时也是这门课里最经典的一次翻车现场——我们会把它逐行翻译成 C 代码，逻辑上一步没错，跑出来却是错的。

先看那个我们亲手写出来的程序。它的唯一目的就是交换两个变量的值，文件名 `Swap.c`，`make swap` 就能编译。文件顶部包含标准输入输出头文件，这样我们才能用 `printf`。函数原型是 `void swap(int a, int b)`——在这个例子里我们不妨说它就是替我们干活的 Olivia——接收两个整数参数，说白了就是两个"杯子"。

`main` 里的逻辑也很直白：声明 `x` 赋 1、`y` 赋 2，先打印一次当前值，调用 `swap` 去交换它们，再打印一次看效果。

```c
#include <stdio.h>

void swap(int a, int b);

int main(void)
{
    int x = 1;
    int y = 2;
    printf("x is %i, y is %i\n", x, y);

    swap(x, y);

    printf("x is %i, y is %i\n", x, y);
}

void swap(int a, int b)
{
    int temp = a;   // 蓝色液体倒进空杯子
    a = b;          // 橙色液体倒进蓝色液体原来的杯子
    b = temp;       // 空杯子里的蓝色液体倒进橙色液体原来的杯子
}
```

函数体也完全是刚才那套动作的逐行翻译：第一行创建一个叫 `temp` 的"空杯子"，把 `a`（蓝色液体）倒进去；第二行把 `b` 的值赋给 `a`；此刻 `a` 原本的值看上去已经丢了，但好在它早就被复制进了 `temp`；最后把 `temp` 赋给 `b`。收工时 `temp` 在技术上还留着一份副本，但它是"空"的——任务完成了，杯子擦干放回架子上。

`make swap`，运行，输出：

```text
x is 1, y is 2
x is 1, y is 2
```

预期应该是先 `1, 2`、再 `2, 1`。但事实是，我们完全按 Olivia 的动作逐行翻译了每一句，程序却没有交换。

### 作用域：被交换的只是两个副本

> **结论**：问题出在作用域上。`a` 和 `b` 与 `x` 和 `y` 根本不在同一层花括号里。

我们之前聊过作用域——它本质上关乎变量在程序中的"生存空间"，通俗地说，变量的作用域就是包裹它的最近一层花括号。这条原则在这里依然成立，而且正是它惹的祸。

`x` 和 `y` 活在 `main` 的花括号里；`a`、`b`、`temp` 活在 `swap` 的花括号里。`swap` 确实把 `a` 和 `b` 换了个个儿，但 `x` 和 `y` 站在完全不同的作用域里，对副本的改动传不回去。

那为什么连值本身也没跟着走？因为在 C 里，每次调用函数传参，本质上都是**按值传递**。

> **定义**：**按值传递（pass by value）**——你交给被调用函数的是变量的副本。函数里改副本，改的只是那个副本。

所以进入 `swap` 的时候，`a` 是 `x` 的副本，`b` 是 `y` 的副本。`temp = a` 拿到 1；`a = b` 拿到 2；`b = temp` 拿到 1。函数内部 `a`、`b` 确实交换成功了——如果你把 `a` 和 `b` 打印出来，你会看到它们已经对调。而 `temp` 仍然保存着 1 的副本，这跟液体交换那套比喻不完全一样：那只杯子并没有被真的倒空，它还留着 1。

当 `swap` 返回时（何况我一句打印都没写），`x` 和 `y` 一个字节都没变。副本换了，原件没动。

这正是这个例子的核心问题：**如果你手上只有值传递这一个工具，交换函数在 C 里根本写不出来。**

### 内存地图：机器码、全局、堆与栈

副本为什么会住在另一片内存里？休息前提到的一个问题正好揭开了这件事：计算机的内存分配其实是按某种固定模式铺开的。

我们把整块内存抽象成一个矩形，从上到下看：

```text
        高地址 ↑
   ┌──────────────────────┐
   │      机器码区域      │   ← 编译出来的二进制代码
   ├──────────────────────┤
   │      全局变量区      │   ← 定义在 main 之外的变量
   ├──────────────────────┤
   │                      │
   │   堆 (heap)  ↓       │   ← malloc 的地盘
   │                      │      一块接一块往下排
   ├──────────────────────┤
   │   ↑ 栈 (stack)       │   ← 局部变量与函数调用
   │                      │      像叠餐盘一样往上长
   │                      │
   └──────────────────────┘
        低地址 ↓
```

（"上""下"只是示意图——计算机内部并没有真正的上下概念。）

先说最上面那块。双击运行一个程序，Mac、PC 上的也好，手机里的也好，由开发者编译生成的全部二进制代码都会被加载到内存的边缘区域，也就是我们俗称的机器码所在位置。它们是从硬盘或固态硬盘里复制过来的：无论你怎么叫那块持久存储设备，数据最终都进 RAM（随机存取存储器），一种更快的存储器，程序运行时数据就暂存在这里。

紧挨着机器码正下方的是全局变量区。这里的"全局"就是字面意思：变量定义在 `main` 之外，而不是在 `main` 或别的函数内部。按惯例它们被放在这里，这样整个程序都能访问到。

再往下是堆。`malloc` 给你分配的内存全部来自这里。第一次调用 `malloc`，它给你这一块；第二次给你那一块；第三次又一块，块与块在内存中连续排列。这些分配全部由 `malloc` 替你管理，你不用操心具体来自哪儿。堆会朝一个方向扩展——在这张图里是向下。

最下面是栈，存局部变量和函数调用。`malloc` 从上面那片区域分配，函数和变量用下面那片——这纯粹是因为很多年前，有一群人在一间会议室里开会决定了计算机内存长什么样。栈在垂直方向增长，就像食堂里叠餐盘：叠一个就往高里走一层。

| 区域 | 放什么 | 谁来分配 | 增长方向 |
| --- | --- | --- | --- |
| 机器码区域 | 编译好的二进制代码 | 程序启动时由操作系统加载进 RAM | 固定 |
| 全局变量区 | 定义在 `main` 之外的变量 | 程序员 | 固定 |
| 堆 (heap) | `malloc` 分配出来的内存块 | `malloc`，一块接一块连续排列 | 向下 |
| 栈 (stack) | 局部变量、函数调用的栈帧 | 运行时自动完成 | 向上 |

> **结论**：`main` 的参数（包括命令行参数）和局部变量待在 `main` 那一块内存里；`main` 调 `swap` 时，`swap` 占用的是紧挨着的"上一个可用内存块"。

那块内存更正式的说法叫**栈帧（stack frame）**。`swap` 执行完毕后，那些装着 0 和 1 的二进制数据其实还留在内存里，但那段空间**好像消失了一样**——程序不再使用它，计算机可以随时拿去干别的。当同一个函数被反复调用，内存块就概念性地一上一下地移动，于是你会在内存里看到之前残留的数值，也就是**垃圾值**。

回到 `main`：它声明了 `x = 1` 和 `y = 2`，然后调用 `swap`。`swap` 拿到自己的一整个栈帧，里面是参数 `a`、`b` 和局部变量 `temp`。因为是值传递，画出来是这样：

```text
  main 栈帧                  swap 栈帧
  ┌────────────┐   ┌────────────┐
  │  x = 1     │──▶│  a = 1     │  ← 副本
  │  y = 2     │──▶│  b = 2     │  ← 副本
  └────────────┘   │  temp      │
                   └────────────┘
```

副本住在另一个栈帧里。交换副本，等于什么也没交换。

### 传地址：把藏宝图交给函数

好消息是，到今天为止我们手上有新工具了。如果放在几周前，我让你写一个交换两个值的函数，你根本写不出来——因为你没有表达这个解法的语法手段。现在我们有了指针、有了地址，可以告诉函数"到这个地址去做一件事，再到那个地址去做一件事"。

改法其实很直接。原型里的 `a`、`b` 从"整数本身"改成"整数的地址"：

```c
void swap(int *a, int *b);

void swap(int *a, int *b)
{
    int temp = *a;   // 去 a 说的那个地址，把那里的值取出来
    *a = *b;         // 去 a 说的地方，把 b 说的地方的值写进去
    *b = temp;       // 去 b 说的地方，把 temp 写进去
}
```

调用处也要跟着改。原来是 `swap(x, y)`，现在要把**地址**递过去：

```c
swap(&x, &y);
```

> **提示**：`&x` 取出 `x` 在内存中的位置。传给函数的从此不再是"1 和 2"这两个数字，而是两张写着"1 在这儿、2 在那儿"的**藏宝图**。

声明 `a` 的那一行只是告诉计算机：`a` 将是一个指向整型变量的指针，也就是一个整型变量的地址。`b` 同理。

于是示意图变成这样。地址严格说可能是 `0x123`、`0x456` 这样的十六进制数，但谁在乎具体数字呢，我们直接用箭头抽象：

```text
  a ───────────▶ ┌──────────┐
                 │  x = 1   │
                 └──────────┘
  b ───────────▶ ┌──────────┐
                 │  y = 2   │
                 └──────────┘
```

`temp` 现在存的是 `*a`——对 `a` 解引用，"跳转"到那个位置，就像玩蛇梯棋一样顺着箭头一路找到目标，最后拿到值 1。于是 `temp` 变成 1。

下一行 `*a = *b`：先通过 `a` 找到"目标位置"，再通过 `b` 找到"存着 2 的那个地址"，把这个 2 写进 `a` 所指的位置——`x` 那一格当场被改写成 2。

最后 `*b = temp`：定位到 `b` 指的地址，把 `temp` 写进去，`y` 那一格变成 1。简单。

交换完成后，`swap` 的栈帧从概念上说被释放了——那些 0 和 1 的二进制数据其实还在内存里，只是程序不再使用它们。**但 `x` 和 `y` 的真实值被改掉了**，因为我们递进去的不是副本，而是它们的地址。

希望你从这一屏里读到了"这些东西到底有什么用"：现在你解决的是一整类全新的问题，下周会有更多挑战等着你。

| | 传值（旧写法） | 传址（今天的新写法） |
| --- | --- | --- |
| 传的是什么 | 变量当前值的副本 | 变量所在位置的地址 |
| 形参拿到的是 | 一个和原变量无关的拷贝 | 一张"藏宝图" |
| 改得动外面的变量吗 | 改不动 | 改得动 |
| 函数返回后 | 副本连同栈帧一起消失 | 原变量的新值留了下来 |

### 星号的三重身份

`int temp = *a;` 是个绝佳例子，示范了星号运算符怎么用、以及怎么用过头——坦白说，在认知上它非常容易混淆。

星号同时扮演三个角色：用它表示**乘法**，用它**声明指针**，理想情况下还用它**解引用指针**。

> **易错点**：星号左边有没有数据类型，含义完全不同。
> `int *a` 里的星号说的是"这是一个指针"；`*a` 里的星号左边只有 `a`，它说的是"去这个地址，把那里的值拿出来"。其他所有类似用法也都是这个意思。

很多年前我们本可以在美式键盘上另外设计一个符号，把这几件事区分开——"这不是乘法吗"这个疑问，正是有同学在问"为什么文件操作非要用这个看起来不起眼的小字符"时得到的回答。现实就是这样：同一个星号，在不同语境里穿着不同的马甲。

### 栈与堆：能力越大，责任越大

会用了不等于用对了。回头看一眼刚才那张内存图，它有一个非常明显的重大缺陷：我们设计了堆朝一个方向长、栈朝另一个方向长，而它们长着长着必然撞在一起。

原因很直白：`malloc` 调用得越多，上面那块占用越大；函数调得越多、尤其是那些迟迟不肯返回的，下面那块占用越大。内存是有限的。

```text
        栈 ↑（像叠餐盘）              堆 ↓（malloc 一块接一块）
        ┌──────────────┐              ┌──────────────┐
        │  swap() 栈帧 │              │              │
        │  main() 栈帧 │              │  malloc() #1 │
        │              │              │  malloc() #2 │
        │              │              │  malloc() #3 │
        │              │              │              │
        └──────────────┘              └──────────────┘
                 ▲                             ▼
                  \                           /
                   └─────── 撞在一起 ────────┘
                        （内存就这么多）
```

> **结论**：撞车没法根除，我们只能把内存占用压到最小。

具体做法有两条：只在必要时才 `malloc`，不要因为"可能用得上"就先申请一百万字节——只分配你确实需要的；以及尽量避免反复、无休止地调用函数却不让它们返回。

如果你几周前写过递归，不小心漏了基准条件、没有分而治之、问题的规模也压根没缩小，那么光是用掉了太多内存帧，就足以导致**栈溢出**，或者类似的**堆溢出**。这不是什么神秘故障，就是程序员自己的问题。

> **结论**：任何资源最终都可能被耗尽。到那一刻，程序会崩溃，或者出别的严重问题。

你或许听说过"堆溢出""栈溢出"这些词，还可能见过一个非常流行的网站叫 **Stack Overflow**——名字的词源就在这儿。栈溢出指的就是计算机内存里一个非常典型的大问题。

而**缓冲区溢出**（buffer overflow）是更具体的一类：像数组这样的一块内存区域，因为存进了过多的值而溢出——比如分配了一个很小的数组，却硬要往里面塞进太多数字。

### 让 scanf 直接写进变量

是时候看看缓冲区溢出长什么样了。CS50 库给我们准备了 `get_int`、`get_string` 这类函数，想彻底摆脱这些"辅助轮"其实并不容易——因为 C 语言本身并没有让内存管理变得容易。所以我们不妨自己写一个 `Get.c`，功能跟 `get_int` 一样：提示用户输入一个整数，把它存进 `n`，再原样打印出来。

```c
#include <cs50.h>
#include <stdio.h>

int main(void)
{
    int n = get_int("n: ");
    printf("n: %i\n", n);
}
```

`make get`，输入 50，一切正常。但这仍然是在用辅助轮。

> **提示**：`get_string` 和 `get_int` 的内部，本质上干的就是 `scanf` 这种事——从键盘读取数据到内存中。（这说法有点过于简化了，但我们先用它。）

那就换掉 `get_int`。这次我们只声明 `n` 而不赋值，让 `scanf` 去做读取工作，用 `%d`（等会儿我们就换成 `%i`）这个老朋友格式码告诉它"把用户输入的整数存进 `n`"。

```c
int n;
printf("n: ");
scanf("%i", &n);
printf("n: %i\n", n);
```

> **易错点**：这里必须写 `&n`，不能只写 `n`。
> 这跟 `swap` 是同一个道理：一个想要修改变量的函数，光把变量本身递进去，它拿到的只是**变量当前值的一份副本**。你必须明确告诉它——"把这个结果存进 `n` 所在的那个地址"。

`make get`，输入 50，程序把它原样吐了出来。`get_int` 被彻底移除。顺便把一件事说清：`printf` 用 `%i` 指定输出格式，`scanf` 用的是**同一套**格式码，两个函数的设计文档都白纸黑字写着这一点，所以两边都用 `%i` 完全合法。

### 那个装着垃圾值的指针

现在换成字符串，麻烦就大了。再来一个程序，试试从用户那里取一个字符串而不只是一个整数。

`char *s` 声明一个用来存字符串的变量，打印提示，然后用 `scanf` 以 `%s` 读入。注意下面这件小事——我**特意没有**在这个 `s` 前面写 `&`：

```c
char *s;
printf("s: ");
scanf("%s", s);
printf("s: %s\n", s);
```

> **易错点**：同一个程序里，`n` 前面要 `&`，`s` 前面却不要。
> 因为 `n` 是整数，它自己并不是地址；而 `s` 按定义**本身就是某个字符串的地址**。更精确地说，`char *` 表示一个字符的地址，而我们知道，只要函数找到第一个字符，它就能顺着空字符一路走到字符串的结尾。
> 要是这里再加一个 `&`，`s` 就变成了"地址的地址"——那叫指向指针的指针，这个概念我们今天先不碰。

先别急着下结论，跑跑看。`make strings`，输入 `high`，成了。再按住某个键输入一大串 `hi`——"这总像是一场赌博，看我输入的够不够长。不过……它没有崩溃。"

那我们就用 **Valgrind** 好好照一照。屏幕上刷出来一堆错误：

```text
Conditional jump or move depends on uninitialised value(s)
Use of uninitialised value of size 8
Use of uninitialised value of size 8
...
```

问题出现在程序里相当靠前的位置，也就是第 4、5 行那一带。来对照代码：第 5 行打印的是什么？是一个叫 `s` 的变量。那是字符型变量的**地址**——可是 `s` 自己当前的值是什么？里面存的是什么？是个**垃圾值**，因为这行压根没有等号参与赋值。

> **定义**：所谓"垃圾值"，就是内存里之前留下的、跟你毫无关系的旧数据。指针变量本身要占 8 个字节（64 位）来存放地址；你不给它赋值，它里面就是 8 个字节的垃圾，共同拼出一个"当前时刻的地址表示"。

而那句 `printf("s: %s")` 就有意思了。格式化输入函数会**写**内存，所以 `scanf("%s", s)` 的意思是：拿着这个垃圾地址，去"那个地址"把用户输入的字符存进去。它沿着我们之前在屏幕上画的那条**波浪线**一路走——谁也不知道 `s` 指向哪儿，可能是这里、那里、或任何地方。

```text
  char *s;              // s 自己就是 8 字节垃圾
  scanf("%s", s);
             │
             └╌╌╌╌╌╌▶  ?  ?  ?  ?  ?  ?  ?  ?
                 波浪线：谁也不知道这块内存归谁管
```

> **易错点**：你把字符串写进了一块**你根本没有分配过的内存**。你其实没有为它申请空间，打印时也仅仅是在盲目地相信"一会儿还能访问到那块地方"——那块你以为归你所有的地址。

我没有触发崩溃，只是因为我输入的字符串还不够长。继续试下去肯定会崩：你在访问一段既不是 `malloc` 分配的、也不是通过别的机制为自己占有的内存。

> **结论**：`n` 那次之所以没事，是因为整数**永远**占 4 个字节，我们告诉 `scanf` 去 `n` 的地址写 4 个字节，它写 4 个字节，正好装得下。可字符串呢？用户可能是敲了 3 次键、4 次键，也可能是一百万次。

那怎么办？有几条路。

第一条：真的去分配大约 4 个字节的空间，让用户能安全地输入 `high` 这样的词，并且还留得下容纳空字符的位置。

第二条——这个更漂亮——把变量改成一个大小为 4 的**数组**。我们可以把数组看成地址，也可以把地址看成数组，事实证明这种语法糖是**双向**的。

第三条，也最省事：**根本不要用格式化输入函数去做这件事**。

### 字符串到底有多长：这不是你能猜的

为什么第三条才是正解？因为你根本不知道用户会敲多少个字符。

```text
  "hi"  + '\0'  →  4 字节    刚好
  "will" + '\0' →  5 字节    放不下了
  更长的单词    →  6、7 字节？
  非常长的句子  →  100？1000？100000？100 万字节？
```

有时候你得划条线、定个界限，规定输入不许超过这个长度。这在各种应用里都很常见——网页上的输入框、很多表单，都有这样一条规矩，理由不止一个，内存安全就是其中之一。

但 `get_string` 几乎能处理任意长度的字符。道理在于我们实现它的方式：它是**逐步读取输入**的。调用一次 `malloc`，看一眼够不够，不够就再要一点点，一遍又一遍，直到装得下为止。你完全不必操心这些底层细节。

可一旦你要自己写、又不打算用 CS50 库或者任何类似的库，你就必须自己拍板：允许分配多少字节，并且**得相信用户不会乱来**，不会输入超出你预期的数据量。

> **结论**：除非你准备好处理这一整套复杂性，否则不要用 C 做这类用户输入。用 CS50 库，或者其他现成的库。
> 顺便预告一下：两周后我们就转向 Python，因为在处理用户输入这种基础操作上，Python 让事情简单得多，许多现代语言都是如此。它们之所以方便，是因为背后有人替你写好了那些棘手的代码——问题依然存在，但会被一层层封装起来，你不必直接面对。

### 文件 I/O：让数据活过进程

好，现在我们终于可以谈真正想要的东西了：亲手访问文件。

> **定义**：文件 I/O（file input/output）里的 I/O 就是输入与输出。文件本质上就是**存储在磁盘上的一堆字节**。

"磁盘"可能指传统硬盘，那种靠旋转盘片存下大量 0 和 1 的机械装置；也可能指固态硬盘（SSD），一种没有活动部件、如今普遍使用的长期数据设备。RAM 则负责临时存取。

> **结论**：我们之前画的所有代表内存的图都是**易失性**的——一旦断电或电池耗尽，里面的一切全部消失。而硬盘/SSD 上的数据是**持久的（非易失性）**存储，断电也不丢。
> 幸运的是，无论你的 Mac、PC 还是云端，都不会因此让你丢掉所有文档和论文。

而到目前为止，我们写的所有程序——包括上次那个电话簿示例——只要程序一退出运行，你刚输入的姓名和号码就立刻被删除了。有了文件 I/O，我们终于能创建、保存、编辑和删除文件了。这就像你在 Google 文档、微软 Word 里操作"文件"菜单。

C 提供了一整套函数：打开文件（`fopen`）、关闭文件并输出内容（`fclose`）、从文件读取数据（`fread`）、往文件里写（`fwrite`、`fprintf`）。数量不少，其中一些这周就会碰到。

先拿电话簿开刀。新建 `Phonebook.c`，做上面那个例子的**持久化**版本：程序退出时，数据不再只是从内存里消失。CSV 是逗号分隔值，很多人在实际工作里用过它——它就是极轻量的电子表格，数据按行按列存，列与列之间只用逗号隔开。

```c
#include <cs50.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    FILE *file = fopen("phonebook.csv", "w");

    char *name = get_string("Name: ");
    char *number = get_string("Number: ");

    fprintf(file, "%s,%s\n", name, number);

    fclose(file);
}
```

`fopen` 会打开一个文件——不管它此前存不存在——并且以**允许写入**的方式打开，这正是引号里那个 `"w"` 的含义。返回值存进一个按惯例全小写命名的变量 `file`；但从技术上说，`file` 实际是一个叫 `FILE`（全大写）的结构体。是不是很怪？它是 C 里少数几个完全大写的标识符之一。**这并不意味着它是常量或什么别的东西**——这纯粹是当年某位开发者敲代码时采用的命名方式。

它本质上是一个指向该文件内容的指针。严格说这是个善意的谎言：它真正返回的，是指向"代表这个文件的那块内存"的数据结构的指针。但就目前而言，你尽可以把它当成指向文件本身的指针。

接下来用 `get_string` 拿姓名和号码（这次连 `string` 类型都省了，尽量把已经用不上的辅助轮踢掉），然后用 `fprintf` 写进文件——要写文件就不能用 `printf`。第一个参数是"写到哪个文件"，这样同时开着好几个文件时才不会搞混；后面跟的是格式串，输出一个字符串、再一个字符串、然后换行，也就是每行给出两个逗号分隔的值，最后把 `name` 和 `number` 的值传进去。收尾 `fclose(file)`，确保文件被有效保存。

先演示一下 `phonebook.csv` 确实还不存在，它是空的。然后 `make phonebook`，输入名字和 `617-495-1000`，看着屏幕右上角，数据被写进去、被关闭。再跑一次、第三次——然后电话簿被删掉了。

> **结论**：它没有持久保存。写文件实际上意味着**从第一个字节开始完全重写整个文件**。

这其实挺反直觉的：你明明只是"添加一条联系人"，感觉上应该像在 iOS 或 Android 应用里加联系人一样。想更灵活一点，就别用 `"w"`。按 `fopen` 的文档说明，想**追加**内容应该用 `"a"` 模式。这种约定在别的编程语言里也很常见。

改成 `"a"` 之后重新编译运行：第一次写入 `David, 617-495-1000`，第二次追加 `Kelly, 617-495-1000`。这次它留下来了。打开 `phonebook.csv` 确认——David 和 Kelly 都在。如果把它下载到 Mac 或 PC 上，右键或双击，很可能就能直接在 Microsoft Excel 或 Apple Numbers 里打开，也能整个导入 Google Sheets 或任何电子表格工具。**我们现在真的能自己创建和保存文件了。**

顺便把一个我们跳过的检查补上：就像任何涉及指针的地方，这里也可能出问题——比如存储空间不足，导致操作系统没法真正打开这个文件。所以应该检查 `file` 是不是 `NULL`。

```c
if (file == NULL)
{
    return 1;
}
...
return 0;   // 能走到这里，说明一切确实正常
```

> **结论**：**只要涉及指针操作，就应该检查返回值**，确认一切确实顺利。

### 缓冲区：视频进度条背后的数组

关于文件操作，还有个问题问得好：**为什么非要用指针？** 很简单——因为 C 就是这么设计文件操作的。

严格来说，我们确实没法在第一周、第二周、第三周就介绍文件和文件 I/O，因为基础还没打好。得先介绍那个看起来不起眼的小字符，你们还会问"这到底是什么意思？这不是乘法吗？"

因为文件 I/O 的运作方式就是这样：当你打开一个文件，系统实际给你的，是那个"代表文件的数据结构"在内存中的地址（这个说法同样过于简化了，那个数据结构再指向真正存在磁盘上的文件）。从实用角度你只需记住——你拿到一个指向文件内容的指针；想写进去就得用格式化输出函数，而且必须指明写的是哪个文件，系统才能定位到它、把填充好值的字符串存进去。

> **结论**：在 C 里，不使用指针你根本无法做文件 I/O——除非有某个库替你把这些细节抽象掉了。

好，再来一个问题：**"缓冲"到底是什么意思？** 大概你们都熟悉这个词，因为 YouTube 和别的应用在网速慢的时候会显示"正在缓冲"。

> **定义**：**缓冲区（buffer）**就是一段内存区域；更具体地说，在 C 这样的语言里，它通常是一个**固定大小的数组**，用来存字节。

```text
  播放头
     ↓
  ┌────────────┬────────────────┐
  │  已播放    │  缓冲区：字节  │  ← 新字节正陆续下进来
  └────────────┴────────────────┘
                       ↓
        播放头追到这里时，下一批早就下好了
```

理想情况下，网络够快，你一点播放，这些字节就持续下载并追加进缓冲区里；等已下载的部分播完，新的字节已经就位，播放就不会中断。缓冲区的本质就是一段内存区域，在 C 里就是一个数组。

### 自己写一个 cp

那我们干脆用上这些函数做点实事。写一个我们自己的 `cp`——复制文件的小程序，能在终端里把一个文件复制到另一个文件。思路和进度条一模一样，只不过这里是一字节一字节地搬运，是**复制**而不是播放。

```c
#include <stdio.h>

typedef unsigned char byte;

int main(int argc, char *argv[])
{
    FILE *src = fopen(argv[1], "rb");
    FILE *dst = fopen(argv[2], "wb");

    byte b;
    while (fread(&b, sizeof(byte), 1, src) != 0)
    {
        fwrite(&b, sizeof(byte), 1, dst);
    }

    fclose(dst);
    fclose(src);
}
```

`main` 这次接收参数：`argc` 是命令行参数的数量，`argv` 是我们的老朋友——字符串数组。现在我们可以揭露它的真面目了：`argv` 本质上就是一个**字符指针的数组**，所以真要写出来就是 `char *argv[]`。既然已经离开了 CS50 库，`string` 类型本身就不复存在了——而这，其实就是一直以来背后的真相。

按惯例把源文件简称为 `src`、目标文件简称为 `dst`。`argv[1]` 和 `argv[2]` 才是用户输入的两个单词——因为 `argv[0]` 是程序自己的名字，那一般不是我们关心的。

C 里没有专门表示"单个比特"或"8 个比特（也就是一个字节）"的数据类型。常见做法是用我们刚认识的 `typedef`，把 `byte` 定义成一个具有特定含义的别名：理想情况下它就是一个 `char`，因为一个 `char` 正好占 1 字节、8 比特。但别忘了，字符类型也可以被当作整数处理，而整数当然可以是正数、也可以是负数。所以虽然这听起来有点晦涩，从技术上讲，我们想定义的是 `unsigned char`——一个你可能还没见过的关键字，它的作用是告诉编译器"这个字符类型、也就是这 8 位数据，不能被解释为负数"。我并不打算拿它做数学运算，这些就是原始的字节、原始的 8 位数据。

> **提示**：这里特意用 `unsigned char` 而不是 `char`，正是因为我们要的是"这 8 位就是 8 位"，而不是一个可能被解读成负数的整数。

循环的思路和 YouTube 播放器完全一致——逐字节地遍历文件，边读边写：`fread` 从源文件里一次读一个字节的量，读不到了就停；`fwrite` 再把这个字节写进目标文件。我得承认，这段代码确实有点复杂，你们在下一个问题集里会越来越熟悉它。但它本质上只是在说第 12 行的"只要我还能一次读到一个字节"和第 14 行的"把这个字节写进文件"——那条红色进度条就是这么一格一格往前爬的。

这里还有一个小改进点：严格来说，当你打开文件时，如果知道它们是**二进制文件**（由 0 和 1 组成，而不是 ASCII 或 Unicode 文本文件），你可以在 `fopen` 时以二进制模式打开以便读写，这样就不会把比特数据误当成原始数据、图像或其他格式以外的东西。上面代码里的那个 `"b"` 就是干这个的。

`make cp`，把 `phonebook.csv` 复制成 `copy.csv`——用的是我今天才学到的新语法，不是系统自带那个 `cp`。打开副本，4 个字节，David 和 Kelly 都在。成了。

### 接下来几周：把字节玩出花样

那么，这些折腾的意义在哪？

与其只在文本文件和小型示例里打转，不如直接拿真实的东西上手，那才有意思得多。在接下来的问题集里，你们会去操作 **BMP 位图文件**——本质上就是一张从上到下、从左到右排列的像素网格，每个像素用一个红值、一个绿值、一个蓝值来描述。志愿者 Atlas of Star 给我们创作的那只猫，还有查尔斯河畔那座美丽桥梁的照片，都是这类素材。

现在你们已经理解——或者很快就能理解——怎么从上到下、从左到右走遍文件里的每一个字节，再改写它们，让同一张照片看起来完全不一样：

- **灰度**：把每个像素的 RGB 三个值都调成更小的、彼此接近的数值，只留下黑、白和灰。
- **棕褐色调**：同样逐像素换算，给整张照片加上老照片那种复古味。
- **镜像翻转**：沿垂直轴把左边的字节搬到右边、右边的搬到左边，图像就翻了过来。
- **模糊**：对每个像素做一点数学计算，让它像蒙上一层薄雾，人眼看过去舒服自然——这在很多照片编辑软件里都是标配功能，既能模糊也能去模糊。
- **边缘检测**：找出桥梁这类显著特征，把它们和天空区分开来，识别出滤镜的边缘。

以上只是你们接下来几周要解决的部分问题，它们最终都会落到这类文件和 JPEG 图像的操作上。
