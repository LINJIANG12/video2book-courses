### URL 里的东西，不再是一个文件

到目前为止，我们做过的任何与网络有关的操作，比如上周你跑起来的那条 HTTP 服务器命令，其实都是字面意思上的功能：它启动了一个所谓的 HTTP 服务器，也就是一个网络服务器，其存在的目的仅仅是提供内容——把你当前文件夹及其子文件夹中的任何文件原样端出去。

所以那时的 URL 通常遵循特定的格式。如果你的 URL 是 `example.com`，回想一下，它仅表示网络服务器的根目录，因此默认情况下你通常会看到一份目录索引。今天我们会发现这种待遇消失了：通常当你访问某个网站的主页（`something.com/`）时，你希望看到的是实际的网站内容，而不是服务器上所有文件的列表。这就是我们今天要开始解决的问题。

更一般地说，那时你引用的是服务器上的某种路径——由一系列文件夹组成，最终可能以一个文件名结尾。文件夹路径只表示该文件夹或其中文件的内容，而 HTML 就是这个文件夹里的某个文件，你还可以根据需要任意嵌套这些路径。

今天，我们会在术语层面把这件事收拢一层，开始更多地谈论**路由**。上一周 URL 还直接对应服务器上的某个文件；但我们会在代码里看到，实际上我们可以直接解析域名之后的那一部分，把它作为通用输入传给服务器，由服务器决定生成什么输出。

约定还是沿用同一套：如果你想传递特定的参数，也就是键值对，就在所谓的路由后面加上问号，然后写上键等于值；如果还有更多参数，用 `&` 符号把它们分隔开。

```text
https://example.com/greet?name=David&lang=zh
                    |    |
                    |    +-- 查询字符串：每一对 键=值 就是一个参数，& 分隔多个
                    |
                    +------- 路由 greet：交给 app.py 里的函数，不是磁盘上的文件
```

回想一下：如果我们在 Google.com 上搜索 "cats"，实际发送给服务器的请求是 `/search?q=cats`——请注意，这里并不是 `search.html`，那里实际上并没有一个对应的文件夹，甚至没有对应的文件。`search` 只是运行在谷歌服务器上的一个程序名称，而这个程序的真名，就叫做**路由**。问号后面的 "cats" 是**查询参数**——也就是来自网页表单的输入，在这个具体例子中它包含的就是 "cats" 这个词。

### 为什么不自己写一个服务器：Flask 与"框架"

那我们具体要怎么做呢？我来演示一下。我们当然可以用 C 语言来实现我们自己的网络服务器，但如果使用像 C 语言这样底层的语言，去实际处理像"为网络编写代码"这样高层级的事情，那简直会是一场噩梦。

所以我们主要还是选择 Python，主要是因为它的抽象层级要高得多。但即便如此，如果我们想从头开始实现这些功能，可能还是需要编写大量 Python 代码——比如解析这些数据包的内容，弄清楚服务器接收了哪些输入，然后才能在 Python 代码中访问这些数据。要让一个网络应用启动并运行起来，这本身就需要大量的工作。

因此，业界通常的做法是**不重复造轮子**：不会自己编写网络服务器，而是使用现成的、相当通用的网络服务器，或者也可以称之为应用服务器。我们要用的这个框架叫 **Flask**。

正如业界所说，Flask 是一个框架，更具体地说，是一个**微框架**。这意味着它是一个由他人编写的代码库，旨在帮助我们更轻松地实现网络应用。他们投入了时间，研究如何在服务器上处理 GET 请求和 POST 请求，以及如何从 URL 中提取键值对——这些几乎是互联网上每一个网络应用都必须处理的基础性工作。这样我们就不必自己重新走一遍这些步骤，可以专注于实现真正关心的问题。

> **定义**：**框架（framework）**不只是别人替你写好的一个库，更像是一套约定俗成的规则——你得遵循这些规则，才能以推荐的方式使用这个库。它很像 Bootstrap：既包含库本身，也包含一套使用规范。

那么，你如何知道如何使用它们呢？只需要阅读相关文档，或者参加一门课程——就像我现在要给你们介绍的这些内容一样。

### 第一个 Flask 应用

我们不再用那个只能提供静态内容的 HTTP 服务器，而是运行命令 `flask run`。它会在当前目录中查找我们编写的代码；如果代码符合刚才说的那套框架约定，就会在某个 TCP 端口上启动我们的 Web 应用，比如我们上周讨论过的 8080 端口。

要实现这一点，我们只需要在当前文件夹中至少有一个默认名为 `app.py` 的文件。这是一个用 Python 语言编写的应用程序，我们需要在其中编写相应的代码，马上就会看到。

按照惯例，我们最好再创建一个名为 `requirements.txt` 的文本文件，其中每行只列出一个我们想让这个 Web 应用程序包含的库的名称。换句话说，即使没有这样一个文件也能跑，但如果我想用像 Flask 这样的框架，只要输一句 `pip install flask` 就行——这和几周前我们安装那个有趣的 "cowsay" 库一样。而如果我想用 `requirements.txt` 来统一管理，只要在里面列出库名，再运行一条稍微不同的 PIP 命令，就能把文件里列出的所有库一次装齐。

```bash
pip install flask
pip install -r requirements.txt
```

关于 `requirements.txt` 的具体内容，这里先简单带过，后续再详细说明。它的作用就是列出这个 Web 应用需要使用的所有库，这样你就不用费心去记忆或手动逐个输入了。

那么 `app.py` 里到底要写些什么呢？创建一个能在浏览器中输出 "Hello world" 的 Web 应用，所需要的最简代码是这样：

```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def index():
    return "hello world"
```

这里有一些新的语法，但并不多。

第一行 `from flask import Flask` 其实是一种有点特别的写法，意思就是"让我能够使用 Flask 这个库"。**大小写在这里很重要**：我们使用的这个包叫 `flask`（全小写），但我们想调用的是它里面一个名为 `Flask`（首字母大写）的类。所以这行代码基本上就是直接复制粘贴过来的。

第二行 `app = Flask(__name__)` 看起来有点奇怪，但它的作用其实是：创建一个名为 `app` 的变量，并将当前文件转换成一个 Flask 应用。我们之前还没见过这种写法，不过几周前我们确实在部分 Python 代码的底部加过那个看起来有点奇怪的 `if __name__ == "__main__":` 条件语句——所以 `__name__` 这个用法我们见过，而且对我们很有用。`__name__` 指的是当前文件的名称，无论我给它起什么名字，你都可以通过这个特殊的全局变量来访问当前文件。所以这一整行的整体意思是：**把这个文件作为主程序来运行**，将其转换为一个 Flask 应用，并把结果存储在一个名为 `app` 的变量中；这样我就可以开始使用 Flask 的功能了。

接着往下看，我先指出一处**熟悉的**语法：我定义了一个函数，按照惯例把它命名为 `index`，但其实我可以随意命名它——这个函数的唯一作用就是返回 `"hello world"`，也就是这个网络应用将要显示的超级简单的内容。

但这里我使用了一种新的语法，通常被称为 **Python 装饰器**。它是一种特殊类型的函数，本质上会影响紧随其后的函数的行为。通过 `@app.route("/")` 这行代码，我在告诉 Flask 框架：将 `index` 函数与这个路由（即单个正斜杠 `/`）关联起来。通过这种方式，我们就能接管 URL 中斜杠部分的默认行为，让它返回这个函数所返回的内容。

### 浏览器收到的，可能比你以为的少

回到 VS Code，我在名为 `hello` 的目录里把这些搭起来：重新创建一份 `requirements.txt` 以明确告知系统我打算用 Flask，然后创建 `app.py`，把上面那段代码输进去。

那我们该怎么运行它呢？回到终端窗口，先清空屏幕，执行 `flask run` 然后回车。会看到一些看起来有些晦涩的输出，但熟悉的弹窗出现了，上面有一个绿色的按钮提示是否要打开这个应用。上周的 HTTP 服务器默认用的是 8080 端口，**Flask 默认使用 5000 端口**——现在我们已经成功启动了。

打开之后，浏览器像渲染网页一样显示了这些内容。但是，请注意一件很关键的事：如果你在屏幕上任意位置右键（Mac 上是按住 Control 键点击）然后选择"查看页面源代码"，你会发现——**这个页面上并没有实际的 HTML 代码**，只有一行文本 `Hello, world`。关闭那个窗口，再次右键选择"检查"（就是我们上周打开过的开发者工具），你会发现浏览器实际上已经替我填充了一些空白内容：它只是按应有的方式渲染了一个最简单的网页。**我实际发送给浏览器的内容，真的只有 "hello world" 这几个字。**

那怎样才能真正发送一个自己编写的网页，而不是让浏览器这样自动补全呢？我可以不返回纯文本字符串，而是返回一个 HTML 字符串。虽然这看起来可能不太美观，但让我继续操作：

```python
@app.route("/")
def index():
    return '<!DOCTYPE html><html lang="en"><head><title>hello</title></head><body>Hello world</body></html>'
```

输入左尖括号、`doctype`、HTML、右尖括号，然后是 HTML 标签，接着是 head 标签、title 标签（为了简单我就命名为 hello）、`</title>`、`</head>`、左尖括号 body、Hello world、`</body>`、`</html>`。这已经是一个完整的网页了，和我们上周看到的一样，这就是最精简的内容。实际上为了更规范些，最好再加上 `lang` 属性——这里我用单引号包裹其实是件好事，因为这样里面就可以放双引号了。虽然这段 HTML 没有经过美化排版，整段代码都挤在一行里。

回到浏览器重新加载页面，再次查看页面源代码，这次浏览器接收到的确实是完整的 HTML 代码了。

那这个练习的目的是什么呢？感觉我好像只是花了更多时间、增加了更多复杂度，却实现了上周仅通过创建 `index.html` 就能完成的效果——完全不需要任何 Python 代码，我自己就能写出 HTML。

但我敢说，我们正在做的是为构建一个功能完备的交互式网站打下基础。这个网站可能包含表单，我们可以将其提交给应用程序，从而不仅能生成一个页面，还能生成两个、三个乃至任意数量的页面。所以你现在看到的其实只是一个起点。无论是谷歌搜索应用、Gmail 本身、Facebook，还是你能想到的任何网络应用，它们的起点都是一小段代码——理论上，这些代码看起来和我们现在写的这些有些相似。

问题在于：把 HTML 代码硬编码成一个长字符串直接塞进应用程序里，这种做法确实有点笨拙。我们试着把它提取出来。

### render_template：把 HTML 从 Python 里搬出去

上周我们讨论过，要把 JavaScript 和 CSS 代码提取出来单独管理。对实际的 HTML 代码，我们同样可以采用这个做法。

这里我不只导入 Flask 函数，还要导入另一个 Flask 自带的函数——根据文档，它叫 `render_template`，中间带一个下划线。这个函数的作用，简单来说就是**渲染一个 HTML 模板**。"模板"在这里的具体含义我们稍后解释。现在我先把下面所有这些代码删掉，假设我会把相同的代码放到一个名为 `index.html` 的文件里（只是 HTML，我上周做过），然后改为返回 `render_template("index.html")` 的调用结果。

当然，这个文件现在还不存在。打开终端新开一个终端（这样就能让服务器保持运行的同时还能查看当前情况），进入同一个 `hello` 目录，输入 `ls` 命令，结果只看到 `app.py` 和 `requirements.txt`。但根据 Flask 的文档说明，如果你想创建自己的 HTML 文件，按照惯例只需添加一个名为 `templates` 的目录。所以除了 `app.py` 和 `requirements.txt`，我还需要一个名为 `templates` 的文件夹（注意大小写，全部小写）。进入它，用 `code` 命令创建 `index.html`，把那个最精简的 HTML 敲进去：文档类型声明、语言属性设为 en、head 里的 title 叫 hello，body 里写 `Hello, world`。自动完成功能确实能帮我快速输入代码。

回到浏览器，关掉开发者工具，简单地点击重新加载——**没有明显的变化**，它运行得和之前完全一样。但我已经为文件布局打下了更实用的基础，这样我就能将逻辑（Python 代码）和 HTML 稍微分离开来。

### 从 URL 里取值：request.args

好，那么我们怎样才能让这个项目变得更有趣呢？我建议从接收一些实际的用户输入开始。

如果能通过 URL 传递类似 `?q=cats` 这样的参数，或者像 `?name=David`、`?name=Kelly` 这样，然后实际看到输出的名字，岂不是很好？

那我又该如何实际获取问号后面的所有内容呢？嗯，这正是像 Flask 这样的框架（以及其他众多替代方案）开始大显身手的地方——**它会自动为我提供那个答案**。

在 Flask 中，一旦你使用了它，就可以访问一个特殊的全局变量，我们称之为 `request`；其中 `args` 指的是传入这个 HTTP 请求的参数。代码长这样：

```python
from flask import Flask, render_template, request

app = Flask(__name__)

@app.route("/")
def index():
    name = request.args.get("name")
    return render_template("index.html", placeholder=name)
```

在最顶部的代码行中，除了导入 `Flask` 和 `render_template`，我们还需要导入 `request`——这是 Flask 框架自带的一个全局变量。中间那行做的事是：创建一个名为 `name` 的变量，把全局变量 `request` 里名为 `args` 的字典中、键为 `"name"` 对应的值，存进这个变量。所以如果问号后面的参数是 `name=David`，这里就会返回 `"David"` 给我；如果参数是 `name=Kelly，这里就会返回 `"Kelly"`。

接下来渲染模板这行，我额外传入了一些命名参数。我们之前在第 6 周介绍过：Python 不仅可以接收用逗号分隔的参数列表，其中一些参数还可以带有名称。所以 `render_template` 的一个参数可以命名为 "placeholder"。目前这段代码还不会产生任何实际作用——回到浏览器点刷新，即使 URL 中包含我的名字，你看到的仍然是 "Hello, world"。

```text
地址栏  ?name=David
          │
          ▼
     Flask 收到请求
          │  request.args  →  {"name": "David"}
          ▼
     app.py:  name = request.args.get("name", "world")
          │
          ▼
     render_template("index.html", name="David")
          │  Jinja 把 {{ name }} 换成 "David"
          ▼
     浏览器收到完整 HTML，200 OK
```

接下来事情就变得有趣了，这也正是我们所说的"模板"的含义所在。回到 VS Code 打开 `index.html`，这次我不打算用 "world" 这个词，而是希望看到 `hello {{ placeholder }}`。但如果我真的直接输入这个词，屏幕上就会显示 "placeholder" 这个字面内容——除非我像这样用一对花括号把它括起来。

通过使用这对花括号，我是在告诉 Flask，我想要"**插值**"这个变量，我想用它的值来替换这个占位符。所以这又是 Python 中的另一种语法：之前我们见过 f 字符串，在 C 语言中使用 `printf` 函数时见过 `%s`，而在 HTML 文件里、用 Flask 框架时，我们用这对花括号来表示占位符——它的值需要被填入。

现在回到浏览器：URL 中已经传入了 `?name=David`，点刷新，瞧，现在我看到的是我自己的名字了。

这里有个和上周那些完全在客户端执行的 JavaScript 示例不同的地方，请务必注意：如果我右键（或 Control 点击）选择"查看页面源代码"，今天的 `David` 实际上是**从服务器端传来的**，不是在客户端渲染的。服务器发送了这段 HTML 代码，特别是这段文本。把 David 改成 Kelly 再回车，查看页面源代码时，服务器确实发送了 "Hello, Kelly"。

> **结论**：URL 通过 `?键=值` 这种格式向应用程序提供输入，也就是所谓的 **GET 字符串**，它被一路传递到服务器端。跑着的 `app.py` 从 URL 中提取那个名字，然后将它传递到 `index.html` 文件中，接着由 Jinja 为我填入实际的值。

### Jinja：Flask 背后那个真正干活的库

那么这些花括号是用来做什么的呢？实际上，这里我们正在使用一个库——**Flask 内置了另一个名为 Jinja 的库**。Jinja 是一种模板库，而世界上存在许多这样的模板库。Jinja 实际上相当简单，这很好，也正是 Flask 选择使用它的原因。目前你可以将 Jinja 理解为这样一个库：它知道如何在成对的花括号中插入变量。

那为什么我们还要引入另一个框架或库呢？Flask 的开发者们认为，重新发明一种模板语言——也就是那种能让你知道该在何处插入什么值的语言——并不值得投入时间。因此他们直接采用了别人多年前编写的另一个库，以避免重复造轮子。

> **结论**：框架的作用就是如此——**一个框架可能使用多个库**。Flask 负责路由、请求、响应这些 HTTP 层的事情，模板这一块则直接交给了 Jinja。

那么什么是模板呢？你现在看到的这个 `hello {{ placeholder }}` 就是模板。它本质上是我希望用户看到的网页**蓝图**，而实际页面会通过动态插入值的方式，基于这份蓝图来生成。占位符就放在这对花括号里面。

这也解释了为什么从今天开始，HTML 文件都会放进一个名为 `templates` 的文件夹里：因为这些不再是像上周那样编写的静态 HTML 了，而是我们希望浏览器最终输出的实际 HTML 的蓝图。

### 修掉 400：判存在、给默认值、定好名字

但这里有个 bug，注意接下来会发生什么。如果我访问这个 URL，并且**完全去掉 name 参数**——只访问根路径，不带任何键值对，然后按回车——这有点糟糕，属于错误请求。这是一个 **HTTP 400 错误**：它表示用户操作有误，因为没有传入必要的参数，缺少了预期的参数。

而且，如果用户必须手动在 URL 中输入内容，这种设计确实有点不太理想。说实话，现实中几乎没人会手动输入这些内容，总的来说这对业务或客户体验都不利。

#### 先判键存在，再去取值

好，我可以回到 `app.py` 中添加一些条件判断代码——**这正是让这个页面成为一个动态应用、而不只是静态页面的关键所在**：

```python
@app.route("/")
def index():
    if "name" in request.args:
        name = request.args["name"]
    else:
        name = "world"
    return render_template("index.html", placeholder=name)
```

`if "name" in request.args` 只是 Python 中检查某个键是否在字典里的语法。如果 name 参数存在于 `request.args` 中，我就继续定义 `name` 变量并赋上对应的值；否则，如果请求中没有提供 name 参数，我就设置一个默认值 `name = "world"`。仅凭这个逻辑，就能确保**只有在键确实存在时**，我才会去访问 `request.args["name"]` 的值。

回到浏览器，在不带任何参数的情况下重新加载，页面正常显示 "Hello, world"；但如果在地址栏中加上 `?name=David` 再回车，页面同样可以正常工作。

> **结论**：它之所以是一个 Web 应用，不仅在于它包含了函数调用和变量，还在于我们引入了**基于布尔表达式的条件逻辑**。

有同学问了个好问题：如果我只在 URL 中输入 `?name=`，也就是指定了参数名却不给它值，会怎么样？回去试一下：把名字删掉，只留下 `?name=` 然后回车，页面上显示的是 "Hello,"。为什么？因为现在 `name` 这个键**已经存在于**请求参数中了，只是它对应的值为空，条件判断的逻辑结果仍然相同。没错，name 确实存在于 `request.args` 中，只是它没有关联任何具体的值。

这里再次体现了使用像 Flask 这样的框架所带来的价值：我可以直接导入 `request` 这个全局变量，然后直接查询参数是否存在于字典中——**这意味着我完全不需要编写任何代码来解析 URL 结构**，比如去拆分问号、等号，或者中间那个 `&` 符号。这类逻辑属于所有 Web 应用都需要处理的通用底层逻辑，Flask 框架实际上帮我处理了这些底层工作，让我能更专注于实现真正关心的业务逻辑。

#### 顺便：变量名到底该叫什么

这里有一个简单的约定。我在这里使用 "placeholder" 这个词，是为了直击要点、明确表示这是一个占位符。但坦率地说，从代码可读性的角度考虑，与其直接写 "hello generic placeholder"，不如写成类似 "hello common name" 这样的表达——这样无论是同事还是未来的自己，在查看这个文件时都能立刻明白：这里是要输出用户的名字。

你可以随意修改这些变量的名称。虽然写成 `name=name` 看起来有点奇怪，但在 Flask 框架中，通常的惯例就是这么写。而这两个 "name" 的含义其实并不相同：左边这个是我要在**实际模板中使用的占位符名称**，右边这个是我要**赋予它的实际值**。直接复用相同的名称（而不是用 "placeholder 1"、"placeholder 2" 这类通用标签），反而能让代码逻辑更清晰，减少不必要的混乱。虽然看起来有点奇怪，但这样写反而更清晰明了——这样一来，我就能在模板中写 `hello {{ name }}` 了。

#### 四行变一行：get 的默认值

先判断参数是否存在、再根据情况决定是否进行后续处理，这种操作非常常见。而 Flask 框架内置了一些逻辑来处理这种情况，所以我可以删掉那四行代码，直接放心地声明一个名为 `name` 的变量：

```python
name = request.args.get("name", "world")
```

严格来说，这个 `.get` 与 HTTP 使用的请求方法无关，它字面意思就是"获取以下内容"：你想获取名为 name 的参数，直接输入引号内的 `"name"` 即可。不过如果不存在名为 name 的参数，你还可以给这个函数设置一个默认值，比如 `"world"`。

这样一来，我们就把原本的 4 行代码精简成了 1 行，功能完全不变的逻辑：获取名为 name 的 HTTP 参数，如果参数不存在，它会返回默认值 "world"；因此无论哪种情况，`name` 变量都会包含我所需的值。回到浏览器再试一次：输入 `name=David` 回车，参数就会生效；什么都不输入直接回车，现在同样可以正常运行。

### 两条路由，和一张真正的表单

好，那么接下来我还能做些什么呢？我建议我们可以进一步深入，并引入第二条路由。就像谷歌和大多数网络应用一样，我们可以设置两个不同的 URL 路径——目前我所有的东西都集中在根路由（`/`）下实现。

怎么调整？很简单：在 `index` 函数下方，我再定义一个 `@app.route("/greet")`，这样就创建了我想要的第二条路由。按照惯例，我把函数命名为和路由相同的名称（`greet`），但你并不一定要这么做，这只是为了减少我需要做的决定。函数体里返回 `render_template("greet.html")`——文件现在还不存在，后面解决——并把姓名传进去。我打算直接简化成一行 `request.args.get('name', 'world')`，不必单独用一行代码来定义那个变量，效果和 `index` 函数中实现的一样。

而 `index` 函数现在只做一件事：渲染一个表单页。那为什么要用表单？与其仅仅打印出用户姓名、然后寄希望于他们手动在 URL 中输入姓名（这本身就不是常规操作），不如直接向用户展示一个表单，让他们能够通过表单来完成这一操作：

```html
<form action="/greet" method="get">
    <input type="text"
           name="name"
           placeholder="Enter your name"
           autocomplete="off"
           autofocus>
    <button type="submit">greet</button>
</form>
```

逐项拆开看：

- `method="get"`，这样所有参数都会显示在 URL 中；
- 输入框的 `name` 属性设为 `"name"`，因为这里要输入的是用户的姓名。注意这里可能有点混淆：左边这个 `"name"` 指的是我们上周学过的 **HTML 属性**，它和我们刚才在 Python 中使用的变量名虽然都叫 "name"，但其实是完全不同的概念；
- `type="text"`，文本类型；
- `placeholder="Enter your name"` 这样的占位符文本，让用户知道该输入什么内容；
- 关掉 `autocomplete`，这样就不会显示之前在这个文本框里输入过的内容；
- 加上 `autofocus`，让光标默认就在这个输入框里闪烁；
- 一个 `type="submit"` 的按钮，点它就真正提交表单了；我把这个按钮命名为 "greet"，因为我想让用户通过点击这个按钮来打招呼；
- `action` 属性指定表单提交到哪。我们之前唯一一次使用 `action` 属性，是在实际访问 `www.google.com/search`；不过今天这个例子不适用，因为我要实现的是打印 "Hello, David"，而不是搜索猫咪之类的内容。但这确实是我可以控制的地方：假设我的应用中有一个名为 `/greet` 的路由，当你访问 `example.com/greet?name=David` 时，就会向用户显示"你好，David"之类的问候语。设置成简单的 `/greet`，就默认指向我自己的服务器。

回到浏览器刷新，页面上现在显示的是一个网页表单，而不是之前那种"你好，某某"的静态内容。我输入名字——注意观察当前的网址，严格来说网址是存在的，就是那个斜杠 `/`，不过 Chrome 和现在大多数浏览器都会尽可能隐藏那些不太重要的部分。

但当我点击"问候"按钮时，网址会自动跳转到 `/greet` 这个路径，问号后面跟着 `name=David`。这和上周我们模仿 Google 搜索功能时实现表单的方式完全一样：那次 `action` 属性被设置成 `google.com/search`，用户就被直接带到了 Google 的服务器；今天我仍然停留在同一个服务器上，因为我设置的 `action` 只是简单的 `/greet`。

### 500：终端里才是完整的故事

**但显然我搞砸了某些地方**，因为我面前出现了一个严重的内部服务器错误，你们很快也会遇到同样的问题。状态码 **500** 意味着问题出在你自己这边。

从这条通用到极致的黑白错误信息中，我们无法直接看出具体原因。不过作为开发者，我可以回到 VS Code 打开终端窗口——现在我开着两个终端，一个可以输入命令，另一个还在运行之前的程序——把窗口最大化，就能看到一大堆令人困惑的错误信息，但其中最关键的可能只有一条：`raise ... Jinja2 TemplateNotFound: greet`。

问题的根源其实很简单：**我刚刚搞砸了，我忘记创建 `greet.html` 了**，所以服务器找不到这个文件。

> **易错点**：模板路径写错或忘了建文件，浏览器只会给你一个毫无信息量的 500 页面——真正的原因永远在**服务器终端**里。这是有意为之的设计：从网络安全角度看，向用户展示服务器上发生的所有错误信息通常是不利的，因为这可能暗示攻击者可以利用这些错误及其隐含的线索入侵系统。但这些错误信息确实会显示在**你的终端窗口**里，供你查看和调试。养成习惯：看到 500 就去看终端。

那就补上它。我创建一个 `greet.html` 文件，放在 `templates` 目录下。有趣的是，它和 `index.html` 完全一样：`index.html` 没有任何花括号或动态内容，它直接输出表单的 HTML；`greet.html` 则直接输出 HTML 和实际的问候内容 `Hello, {{ name }}`。而 `app.py` 负责决定向用户展示哪一个——如果用户访问的是 `/` 斜杠路由，就显示 index.html；如果他们通过提交表单自动跳转到 `/greet` 路由，就显示 greet.html。

现在回到刚才那个内部服务器错误，重新查看表单：表单本身没有变化，但现在当我输入 David 并点击"问候"时，URL 会变为 `/greet?name=David`——我终于看到了预期内容。

### layout.html：把样板代码只写一次

好了，现在正好可以分析一下当前实现的问题。我把 `index.html` 和 `greet.html` 这两个模板都打开。即使你之前从未接触过网页编程、从直观感受来看，你觉得这个设计有什么问题？

确实存在大量重复代码。虽然技术上我没有直接复制粘贴，但效果和复制粘贴差不多。请注意当我来回切换这些文件时——除了表单部分的有无，以及 "Hello," 后面的内容不同之外，几乎所有代码都一模一样。比如那些高亮显示的样板 HTML 代码，它们完全重复了。

而这正是我们真正开始讨论**模板**的意义所在。如果能把两个文件中共有的 HTML 代码提取出来，放到一个真正的模板里、让两个路由都能使用，那我就能只写一次样板代码，而不是反复重复。想象一下：如果我有 3 个路由、4 个路由，甚至 5 个路由，那我岂不是要把同样的 HTML 代码重复输入 3 次、4 次，甚至 5 次？这显然很愚蠢，而且肯定有解决办法，就像我们在其他编程语言中看到的那样。

语法可能有点奇怪，但这种东西你很快就能习惯。我在 `templates` 目录下创建第三个 HTML 文件，按照惯例命名为 `layout.html`——因为 Flask 官方文档就是这么建议的。在里面，我把所有固定不变的样板 HTML 代码都放进去：文档类型声明、`<html lang="en">`、`<head>`、`<title>hello</title>` 作为所有页面的统一标题，然后是 `<body>`。

接下来才是真正有趣的地方。在这两个示例中，唯一发生变化的部分就是主体内容：`index.html` 的主体是一个网页表单，`greet.html` 的主体只是一个显示 `Hello, {{ name }}` 的简单字符串。所以我想告诉 Flask 的是，主体部分的所有内容都将是一个**动态代码块**：

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <title>hello</title>
</head>
<body>
    {% block body %}{% endblock %}
</body>
</html>
```

```text
templates/
├── layout.html    固定的样板 HTML 全在这里，body 位置挖了一个坑
│                     {% block body %}{% endblock %}
├── index.html     {% extends "layout.html" %}   坑里填：表单
└── greet.html     {% extends "layout.html" %}   坑里填：Hello, {{ name }}
```

你会看到另一种类似 HTML 语法的示例，但 Flask 使用的模板引擎 Jinja2 使用**花括号加百分号**来开启标签，然后用对应的符号来闭合它。所以这里实际上有两个我们称之为 Jinja 标签的结构：`{% block body %}` 这个标签叫做 **block**，我在这里定义了一个自定义名称（我本可以把它命名为 foo、bar 或 baz，但由于我希望这个块对应 body，按照惯例就这么写了）；而 `{% endblock %}` 仅表示结束你刚刚开启的代码块——这种"闭合标记"的特殊语法，在其他语言中也出现过。

> **提示**：合理的观点存在分歧。HTML 的发明者采用了简洁的尖括号和这类关键词，而设计 Jinja 模板引擎的人则选择了花括号和百分号。为什么？因为这些符号很可能不是人们编写代码（至少是 HTML 代码）时会正常输入的字符——选一套**不太可能与用户实际想使用的语法冲突**的符号，是模板引擎的常规做法。

这也意味着，现在的占位符不再只为一个词或值（比如 name）预留了位置，而是可以放入**一整段代码**。

### 继承与填充：extends 与 block

那么我该如何让 `index.html` 使用这个布局呢？我把布局模板中表单上方和下方的所有内容都删掉，然后用一点 Jinja 语法：

```html
{% extends "layout.html" %}

{% block body %}
    <form action="/greet" method="get">
        <input type="text" name="name" placeholder="Enter your name" autocomplete="off" autofocus>
        <button type="submit">greet</button>
    </form>
{% endblock %}
```

这个模板需要花点时间记忆或复制粘贴，但逻辑其实很短：`{% extends "layout.html" %}` 的意思是"我想让 `index.html` 使用这个布局模板的蓝图"，然后从 `{% block body %}` 到我手写的 `{% endblock %}` 之间，就是"我想插入到那个布局中的内容"——也就是表单本身。这已经提炼出了 `index.html` 的精髓：相对于欢迎页面唯一会变化的内容。

`greet.html` 的处理完全一样。顶部写上 `{% extends "layout.html" %}`，告诉 Flask greet 这个模板继承自布局；然后说明名为 body 的块在 greet 模板中应该是这样：

```html
{% extends "layout.html" %}

{% block body %}
    Hello, {{ name }}
{% endblock %}
```

从这些略显奇怪的地方，你可以看出我们会反复看到的一种模式：**真正核心的内容都被关在那个 body 块内部**。回到布局模板看，它现在完全就是这个样子——一个占位符，不再只服务于像 name 这样的单个变量，而是准备好了迎接来自一个文件的一整块代码。

> **易错点**：上面这两段我特意做了缩进，网页看起来会因此"难看很多"，但这正是为了让结构在 VS Code 里一眼可读。浏览器完全不在意你多写或少写空格——它在"查看页面源代码"里拿到的就是未经美化的那一份。我做缩进纯粹是为了自己识别代码结构：能清楚地看出哪些内容属于 body 块。

现在回到浏览器，点返回按钮回到网页表单并刷新，你又看到了那个熟悉的表单。但如果现在查看开发者工具或页面源代码，你会发现所有内容都出现了——**它们全部都是从服务器返回的网页中获取的**：上面就是那段样板代码，下面也是那段样板代码，而中间这部分才是这个页面独有的内容。

### GET 的隐私代价，与改成 POST

好，那我们再来看一下这个 URL。到目前为止我们所有的示例都要求我把名字或 Kelly 的名字直接放在 URL 地址栏里，我不太满意这一点。为什么？

想象一下，如果我有个爱管闲事的兄弟姐妹，他们只要打开我的浏览器，就能看到我访问过的所有 URL，包括我问候了谁的名字。这还不算太严重，但想象一下，如果表单里填的是用户名和密码呢？如果提交的是信用卡号，或者只是你不想让别人知道的搜索关键词呢？**这些信息最终都会出现在地址栏里。**

这是因为你在表单中使用了 `method="get"`。GET 方法确实会把所有 HTTP 参数都塞进 URL 里——这在处理像谷歌搜索框这类**低风险**操作时非常实用；或者当你希望直接生成可点击的超链接时也很合适。换句话说，如果我把这个链接放进 `<a href="...">` 这样的锚点标签里，就能让用户通过**深层链接**直接跳转到一个永远显示"你好，David"的页面。

> **结论**：GET 请求的查询字符串包含了渲染页面所需的所有信息，但这确实**不利于隐私保护**。

好在 HTTP 不只有 GET 方法，还有一种叫做 **POST** 的方法。POST 是另一种 HTTP 动词，本质上——用上周提到的虚拟信封来比喻——它把信息更深地**藏在信封内部**，而不是直接写在 URL 地址栏里，但服务器依然能够获取这些数据。

改起来很简单：回到 VS Code 重新打开 `index.html`，这里有一个表单，只需把 `method` 属性从 `get` 改为 `post`。回浏览器返回表单页并重新加载（这样表单才知道方法已经更改），输入 David 点击 "greet"。请注意：URL 确实发生了变化，我当前位于 `/greet` 路径，但并没有向外界或任何能物理访问我浏览器的人透露我刚才输入的具体内容——他们只知道我访问了 `/greet` 路径，却无法得知具体传递了哪些键值对参数。

#### 405：方法不允许

**显然，这个方法目前还没有生效。**我收到一个 HTTP 状态码 **405**，表示"方法不允许"。

这是因为 Flask 在默认情况下定义路由时，会直接假定你希望使用 GET 方法而非 POST 方法。对于默认页面来说，GET 确实很合适——这相当于我直接在浏览器中访问了根路径 `/`，首页通常就该支持 GET；但 `/greet` 路由应当支持 POST。

最简单的实现方式是为路由函数传入另一个参数——这是我们之前不需要的，因为默认就是 GET。现在我可以明确告知 Flask，通过一个用逗号分隔的 HTTP 方法列表来指定该路由支持哪些请求方法。列表需要用到方括号，这是 Python 中表示列表的方式，相当于 C 语言中的数组：

```python
@app.route("/greet", methods=["POST"])
def greet():
    return render_template("greet.html", name=request.form.get("name", "world"))
```

默认情况下，这个参数是 `methods=['GET']`，所以刚才那条路由只支持 GET 请求；现在我将其改为仅支持 POST 方法。

不过我还需要做另一个调整。**如果你查阅官方文档就会发现：当通过 POST 而非 GET 方式获取 HTTP 参数时，需要把 `request.args` 改为 `request.form` 来获取表单数据。**这确实不太直观——`request.args` 对应 GET 请求参数，而 `request.form` 对应 POST 请求的表单数据。两种参数都可能来自表单，所以这种命名容易让人困惑。你要记住的就两条：

| 要取的东西 | 该用哪个 |
| --- | --- |
| GET 请求 URL 查询字符串里的参数（`?name=David`） | `request.args` |
| POST 请求提交上来的表单数据 | `request.form` |

所以接下来只需要把那里改成 `request.form` 即可。现在我的 Web 应用就能支持通过 POST 方法提交的表单了。再输入一次名字：这次 URL 虽然会再次变成 `/greet`，但看不到明显的参数；不过我仍然会收到问候，因为服务器知道要**深入查看那个"信封"里的内容**。

#### 用开发者工具看见"信封"

为了更清楚地诊断这个问题，我返回上一步，在桌面上右键点击（或按住 Control 键点击）选择"检查"打开开发者工具——它在当前场景下也能发挥巨大作用。因为我打开了**网络面板**（就像上周操作的那样），它会显示浏览器向服务器发送的所有请求。

```text

     └──────────────  参数直接写在 URL 里，地址栏/历史记录/截图都能看见

POST  /greet                    ←  URL 干干净净，状态码 200
```

点开这条记录，显然请求成功了，因为返回了状态码 200。切到"**载荷**"标签页，在这里我会看到提交的表单数据包含 `name` 字段，其对应的值正是 "David"。这样你就能清楚看到自己提交的具体内容了。

所以今天你们就可以尝试这个操作：比如当你想登录某个网站（比如 Gmail 或其他网站）时，你实际上可以查看自己通过键盘提交给服务器的所有数据——**即使网站使用的是 POST 方法**。因为你自己控制的浏览器，当然能看到这些信息。

### 一个路由能不能兼管表单与结果

好，那么我们还能用这个功能做些什么呢？

在开始实际解决一些现实问题之前（就像我多年前用某个案例演示的那样），我们先来补充几个基础模块。假设我不太喜欢目前这个实现方向：**每次我设计一个包含表单的页面时，表单都会提交到另一个完全独立的路由。**

那如果我的页面上有两个表单呢？那我现在就需要 4 个路由了。如果我有 3 个表单，就需要 6 个路由。用一个路由来显示表单，再用另一个路由来处理表单提交，这种做法确实有点麻烦——时间长了会变得很烦人，因为需要的路由数量几乎是理想情况的两倍。

那么，有没有办法能两全其美，把这两个路由合并成一个，让所有与用户问候相关的操作都集中在一个地方处理呢？

嗯，你可以这样做。

## 表单、Jinja 与第一个真数据库

### 把 greet 和 index 合成一个函数

先把上节课留下的尾巴收拾干净。我把 greet 路由整个删掉，也把 index 路由里的大部分代码删掉了，然后提出了一个问题：怎么把「显示表单」和「处理提交」这两件事合并？

答案不复杂。路由本身可以声明自己支持哪些方法，用逗号分隔的列表写出来；然后在处理函数内部判断 `request.method` 是什么。

```python
@app.route("/", methods=["GET", "POST"])
def index():
    if request.method == "POST":
        # 假定表单已提交
        return render_template("greet.html", name=request.form.get("name", "world"))
    else:
        # 隐式处理 GET：假定没有表单提交，直接显示表单
        return render_template("index.html")
```

这里有个小地方值得停下来想一想：为什么 `else` 分支里不再写一句 `elif request.method == "GET"`？没必要。我只声明支持这两种方法，所以落到 `else` 就一定是 GET。为了效率起见，直接假设「另一种情况」，比再比较一次字符串更干净。

> **提示**：`request.form.get("name", "world")` 里的 `"world"` 是默认值——用户提交了就用用户给的名字，没提交（比如直接敲网址进来）就用 world。这正是刚才合并的逻辑能成立的原因：两个分支最终都只需要一个名字。

这两段代码逻辑上完全一样：之前两个函数里各自处理的东西，现在靠一个条件判断合到了一起。**让服务器去判断用户是不是点了按钮、通过 POST 到达这里**。用户只有点了那个按钮、表单真的被提交了，才可能用 POST 进来；否则，他们就是直接输入网址、以 GET 方式访问的，那我们就给他们看模板。

> **结论**：每个功能模块仍然有自己的模板，模板之间只存在细微差异；我只是在 app.py 里根据应用的真实逻辑，决定这一趟该渲染哪一个。这一点设计仍然是好的，没有为了合并而牺牲清晰度。

那 `index.html` 要改什么？回到那个文件，表单里有一个 `action` 属性，指定数据要提交到哪个 URL。现在 `/greet` 已经不存在了，所以我把 `greet` 删掉，改成提交到根路径 `/`。这其实等价于**完全省略 action 属性**——不写 action，表单就默认提交到它当前所在的页面地址。当然，如果你想把话说得更明确、更严谨，也可以老老实实把 action 写成 `/`，一样能用。

测试一下。回到另一个标签页，表单现在是空白的，输入 `David`，点 `greet`，功能正常。返回页面再刷新，GET 也一样跑得通。

但注意一件事：**URL 里不会留下任何数据**，因为我用的是 POST。这通常也是出于隐私保护的考虑，是个不错的做法。

### 模板里的 if：Jinja 借来的 Python 语法

进入下一个主题之前，我再展示一个实用的技巧——它源自真实应用场景的改进。

在 app.py 里我一直把 `"world"` 写死当默认值，这没问题，尤其当它简短明了时。但既然现在逻辑要挪到模板里处理，我就可以做得更好：让**模板自己**决定，是显示 `Hello, [名字]`，还是名字为空时显示 `Hello, world`。

进到 `greet.html`，确保我会收到一个叫 `name` 的变量，然后在模板里输出：

```jinja
Hello, {% if name %}{{ name }}{% else %}world{% endif %}
```

`{% if name %}` 成立的条件是 name **既非空字符串也非 None**。这套语法确实有点特别——Jinja 用 `{% endif %}` 来结束 if 语句块，而不像 Python 那样靠缩进。但这就是它的规则，而且说实话，这是一种巧妙而实用的方式。

这里藏着一个视觉细节，你可能已经注意到了：`"Hello,"` 后面跟着一大堆空白字符，对不对？如果是，它们会让段落或文本显得非常杂乱。

那为什么不会出问题？因为 **HTML 会忽略多余的空白字符**，任何超过一个的空格都会被规范化、压缩成单个空格。

> **提示**：这不是我编的。上一周我们偶然撞上过这件事——我当时写了三段关于鸭子的文本，本意是让它们明确分成不同段落，但所有空白字符都被忽略掉了，三段硬是没分开显示。直到我真的加上段落标签（`<p>`）才解决。现在这段逻辑被搬到了模板里处理。

所以，针对所有这些逻辑以及更多功能，去查 Flask 的官方文档，特别是 Jinja 自己的文档。绝大部分功能我们这一路已经见识过了。

回来。现在的目标是为 Frosh IMs 搭一个基础版本：学生能访问一个表单，填写并提交到服务器完成注册。暂时忽略那些花哨的图形效果，保持界面简洁明了。

我提前建好了一个叫 `froshims` 的目录，里面有 `app.py`、`requirements.txt` 和一个 `templates` 文件夹。这些文件本质上和之前创建的完全相同，只是我把跟 hello 和 greeting 相关的具体内容都删掉了。

先快速介绍一下我提前准备好的内容：

`app.py` 非常简单，只是一个最基本的应用，功能就是渲染首页。`index.html` 目前看起来也很简单，但稍后我们会让它变得更有意思。`requirements.txt` 里只列出了 Flask，已经安装好了，这一点没什么好多说的。

### 一个真表单：姓名输入框和下拉菜单

从这里开始，先做一个**至少能让用户提交信息到服务器**的表单，然后再逐步改进。

在 `index.html` 的 body 里写 HTML，它会扩展我们之前创建的 layout 模板。先加个标题，用 `<h1>` 向学生明确他们需要做什么——「注册」。然后添加一个 `<form>` 标签。

表单的 action 属性可以设成任何值，但既然我希望用户进行注册，就让它指向 `/register`。这比之前的 `/greet` 更符合当前场景，因为我们现在处理的是不同的功能。另外我让学生用 POST 方法——主要是不希望他们的室友通过浏览器历史记录看到他们报了什么。POST 的参数会被藏在「虚拟信封的更深处」，不会留在浏览器的历史记录里。

表单内部先加一个输入框填学生姓名。恰当地命名为 `name`，把 HTML 的 name 属性也设成 `"name"`，类型明确写成文本类型。为了界面更友好，加一个 placeholder 显示「姓名」，让用户知道该填什么。关掉自动完成——以防几个室友共用同一台电脑注册时信息互相干扰；再打开自动聚焦，让光标直接落在姓名输入框里。

```html
<form action="/register" method="POST">
    <input type="text" name="name" placeholder="姓名" autofocus autocomplete="off">
</form>
```

这个 `autofocus` 你们上周还没见过。但如果你曾好奇网页上的下拉菜单是怎么实现的——如果你自己从来没动手做过——它们在网页里叫做**选择菜单**。如果我想让用户选择要注册的运动项目，就把这个输入框命名为 `sports`。相比让用户手动敲运动项目名，这是更好的替代方案：手动输入容易出现拼写错误和大小写不一致，而下拉菜单天然就把可选项的范围规范住了。

```html
<select name="sports">
    <option value="basketball">篮球</option>
    <option value="soccer">足球</option>
    <option value="ultimate frisbee">极限飞盘</option>
</select>
```

选项标签默认会把开始标签和结束标签之间输入的文字当作它的值。但为了更严谨，我要明确写出每个选项对应的 `value`——「篮球」「足球」「极限飞盘」。

回浏览器，之前显示的还是 Hello 程序，因为我停掉又重启了 Flask（`Ctrl+C` 可以中断它）。重新加载，现在应该能看到一个稍微有趣一点的表单：有一个姓名输入框，光标正在那儿闪烁；还有一个下拉菜单，里面三个选项。

不过默认选中「篮球」有点武断，这很容易导致用户误操作——填完姓名没仔细看，就不小心注册了篮球。所以我要在顶部添加一个**空选项**，它的值是空值，标签是「运动项目」，并且让它默认选中。

> **定义**：`<option>` 标签不只支持 `value` 属性，它还支持 `selected` 属性——设置了 `selected` 就意味着这个选项是默认选中的。

回到页面重新加载，拿到新的一份 HTML。看起来好一些了：左边仍然是姓名，右边下拉菜单现在是这样。

这一改还有个副作用好处：后端特意把运动项目的初始值设成空，理论上这能帮我判断用户是**真的选了**运动项目，还是**直接点注册**把这个下拉菜单忽略了。

理想情况下，用户需要通过点击按钮来完成注册。于是我添加一个按钮，类型设为 `submit`，标签是「注册」。

```html
<button type="submit">注册</button>
```

现在这个表单是完整的了——虽然外观不太美观。David 可以通过它注册篮球项目。

### 404 与 500：两条走不通的路

哎呀，结果出现了 404 Not Found。

**为什么会这样？为什么找不到 `/register` 这个路径？** 因为——是的——我还没有把这个选项关联到任何功能上。表单已经关联好了，它正在指示浏览器跳转到 `/register`；但我回到 `app.py`，发现我确实**没有为 `/register` 这个路径定义任何路由**。所以当然显示「未找到」，因为理论上存在无数条未定义的路由路径，而 `/register` 目前恰好是其中之一。

我可以自己来定义它。明确声明这个函数支持的方法是 POST，而不是默认的 GET；再定义一个实际的函数，按惯例命名为 `register`（当然名字可以随便取）：

```python
@app.route("/register", methods=["POST"])
def register():
    ...
```

在函数内部，先偷个懒：我至少得检查用户是否提供了姓名和运动项目。怎么检查？由于我已经导入了 Flask 自带的全局 `request` 对象，可以直接查询它。

```python
if not request.form.get('name') or not request.form.get('sport'):
```

`failure.html` 现在还不存在，问题不大。进 templates 目录创建它，声明它继承自 `layout.html`，里面定义一个 body 块，先放点简单的占位内容：您尚未注册，因此已被阻止访问。这就是一个已经存在的错误页面了——我这就把它关掉，眼不见心不烦。

现在 app.py 完善了：注册路由设置好了，当用户通过 POST 访问时会被调用；我会检查 `request.form`（这是获取 POST 变量的地方）来验证是否提供了姓名或运动项目，然后根据结果渲染相应的模板。

来测试。回到表单页，输入名字 David，但**不填运动项目**，点注册——

```python

```

听起来像是用户操作失误，所以这次尝试失败了。HTML 代码中你能大致看出问题在哪，因为 **Flask 实际上已经用下划线帮我标出来了**。我到底犯了什么低级错误？我只是忘了闭合引号。真是新手级别的失误——看来我还是得打开文件才行，这有点讽刺。切到另一个终端打开那个文件，HTML 代码就在那里，距离正确只差一个愚蠢的字符。

> **易错点**：下次看到 Flask 在终端里打出带下划线的那一行，就是它替你做了行号定位。先看终端，再猜代码。

把引号闭合，切回浏览器再试。这次输入名字 David，还是不选运动项目——「您尚未注册」。我不知道原因，但我知道自己确实没有注册。再试一次，这次**不填姓名但选一项运动**——「您尚未注册」。为了确保全面测试，两个都不填——「您尚未注册」。

看来这个功能运行正常。现在以 David 的身份注册篮球项目。拜托，一定要成功啊——

**又出现了内部服务器错误。** 让我们从过去的错误中吸取教训，仔细分析一下。我试了两次，虽然都不是直接复制粘贴，但两次都失败了，目前是零胜两负。

这里可以顺带说一个浏览器行为：我现在可以直接点刷新，因为浏览器足够智能，能记住我刚才向服务器提交的内容——所以它会提示我确认是否要**重新提交表单**，免得我在涉及信用卡或其他敏感信息的网站上不小心重复提交。在这个例子中我不介意重复提交我的篮球名字，所以我点继续。这次成功了：「您已成功注册」。

我目前没有对学生的数据做任何处理，但至少我验证了他们确实提供了一些输入。

### 永远不要相信用户输入

不过这里有个需要注意的地方。问题在于，**HTML 代码完全是在客户端执行的**。

假设有个学生对我们只提供篮球、足球和极限飞盘感到非常不满——她可能真的很想报名排球，尽管我们并没有开设排球课程。这里可以说存在一个安全漏洞：从技术上讲，我当前的代码会接受**任何**用户输入，即使它不在下拉菜单里。毕竟，我可以直接右键点击页面，或者按住 `Ctrl` 点一下打开开发者工具。

现在让我以黑客型学生的身份来操作这个表单。让我进入这个下拉菜单——好吧，这没什么大不了的。如果我想让「排球」这个选项出现，只需要懂一点 HTML。我右键点击那个元素，选择「编辑为 HTML」，这实际上允许我直接编辑页面的 HTML 代码。我给自己添加一个自定义选项，值设为 `"volleyball"`，关闭括号，`Volleyball`，回车。

关闭开发者工具，哇——如果我想的话，就可以注册排球项目了。选择排球项目，输入「Kelly 正在尝试破解网站」，注册。她成功注册了排球项目。看起来一切正常。

> **结论**：永远不要相信用户输入的数据。这一点我们在讨论 SQL 时已经有所体现，而在处理 Web 应用时更为关键，因为你永远不知道用户会**无意中**、**错误地**、还是像 Kelly 这样**恶意地**提交你未曾预料的数据。

那防御措施是什么？假设我现在正把 Kelly 登记进排球队名单里，逻辑上的解决方案是什么？——是的，做一些**服务器端验证**。我们不能仅仅盲目地检查用户是否提供了值，实际需要验证它是否属于那些预设的运动项目之一。

我回到 `app.py`，可以用几种方式处理。第一反应大概是这么写：

```python
if request.form.get('sport') != 'basketball' \
   and request.form.get('sport') != 'soccer' \
   and request.form.get('sport') != 'ultimate frisbee':
    return render_template('failure.html')
```

回到表单再以 Kelly 的身份注册——「您尚未注册」。我成功拦截了这次注册，因为排球当然不在我预设的运动项目列表中。

### 但硬编码的验证本身就是坏味道

但这种方法可能存在哪些不足？即使你之前从未接触过 Web 开发，这个方法有什么问题？

我现在不仅要在**服务器端**硬编码所有运动项目来验证用户输入的有效性，而且别忘了，**下拉菜单本身也是从 `index.html` 生成的**——所以我还得在 HTML 里重复列出所有的运动项目。像这样重复代码显然不够理想。

更好的做法是在文件开头直接创建一个全局变量。在这个 Web 应用的上下文里这完全合理，这样我就能在任何地方访问它。命名成全大写的 `SPORTS`——这样命名是为了表明它是一个全局变量和常量，尽管 Python 不像 C 语言那样有真正的常量概念，但这是遵循一种约定俗成。如果你看到一个全大写的变量，请不要随意修改它，用它就好，但别去改动它。

```python
SPORTS = ["basketball", "soccer", "ultimate frisbee"]
```

那么与其写那一长串，我可以直接问一个更简单的问题：**如果运动项目不在支持的列表中，就直接返回失败页面。** 顺带还能精简一下——我不需要把失败处理写两遍，我何不直接复用这段代码。

```python
sport = request.form.get("sport")
if sport not in SPORTS:
    return render_template("failure.html")
```

抱歉，我不小心删多了——实际上应该是 `sport = request.form.get("sport")`。别让 Kelly 或者其他任何人就这样注册进去。

### 模板里的 for：让选项自己长出来

不过既然有了这个全局变量，在模板里我就可以做得更聪明一点。我不需要在这里手动把三个运动项目都写出来。相反，当我渲染 `index` 模板时，我何不直接传入一个名为 `sports` 的变量，把它设成那个全局列表的值？

`index.html` 里的做法是：删掉所有选项，只保留默认的空白值，然后这样写——

```jinja
<select name="sports">
    <option value="" selected>运动项目</option>
    {% for sport in sports %}
        <option value="{{ sport }}">{{ sport }}</option>
    {% endfor %}
</select>
```

原来 **Jinja 也支持类似 Python 的循环语法**。在 `sports` 循环中，通过花括号和百分号，我现在可以动态生成任意数量的选项。`value` 等于当前循环变量 `sport`——这有点冗余，但 HTML 的语法就是这样：一个是用户看到的内容，一个是提交给服务器的值，以防你希望它跟显示内容不同。然后在这行下面写上 `endfor`，虽然看起来奇怪，但这就是 Jinja 中结束循环的方式。

> **结论**：现在无论我有 3 项运动还是 30 项运动，所有选项都会由这个模板动态生成。我只在 `app.py` 里更新那个全局列表，就能集中管理所有运动项目——这才是我们开始节省时间的地方。

回到浏览器刷新表单，下拉菜单依然正常，而且所有选项都是**动态生成**的。确实，如果我在浏览器里查看页面源代码，会发现这里有一些多余的空格——因为循环在每次迭代时都添加了一些空格。这没关系，我仍然有 3 项运动，**但没有排球**，正如我之前设定的那样。逻辑会拦下 Kelly 即使她手动输入 `"volleyball"` 来攻击这个版本的网站，因为只有那三项在列表里。

### 单选按钮：同样的数据，换一种控件

好的，那我们来试试另一种表单类型。下拉菜单确实很方便，但你可能也见过网站上的**单选按钮**——就是那些互斥的小圆圈，点一个另一个就自动取消。

我们不用下拉菜单，而是创建一系列 `type="radio"` 的输入框，为每个运动项目都输出一个，在开始标签和结束标签之间插入当前运动：

```jinja
{% for sport in sports %}
    <label>
        <input type="radio" name="sports" value="{{ sport }}">{{ sport }}
    </label>
{% endfor %}
```

看清楚了：这其实就是**另一种类型的输入框**。上面两行代码里的文本输入框上周你已经见过，还见过搜索框、邮箱输入框——文本输入框其实有好几种不同的类型，只不过这个会显示成一个单选按钮，而用户会看到旁边的标签文字。

回到浏览器，点返回再点重新加载，界面依然不够美观，但它已经是一个单选按钮了——这意味着这些选项是互斥的。

**浏览器是怎么知道这些选项只能让我选一个的呢？** 因为我在每个单选按钮上都用了**相同的 name 属性**。浏览器正是通过这个相同的 name 来判断这些选项是互斥的。如果你查看页面源代码，你会发现这三个输入框都是动态生成的，`type` 都是 `radio`，而它们的 `name` 完全相同。

就这样，一个改动就够了。输入名字点注册，系统依然正常运行——因为服务器从 request 对象中获取的数据格式和之前**完全一致**。无论用户在浏览器里选择哪种控件类型，表单都能正常提交，你依然可以通过 name 或 sport 字段拿到数据。

### 把「注册失败」说得具体一点

关于这些技术实现，有什么问题吗？——确实，这个网站的用户体验有点糟糕。比如你忘了填姓名但选择了运动项目，网站只会笼统地提示「注册失败」。如果能明确告诉用户**具体哪里出了问题**，让他们能有针对性地修正，这样会更友好。

有很多方法可以实现。我建议直接着手：创建一个名为 `error` 的模板，它唯一的作用就是更清晰地告诉用户他们具体做错了什么。

```html
{% extends "layout.html" %}
{% block body %}
    <h1>错误</h1>
    <p>{{ message }}</p>
{% endblock %}
```

这次吸取了之前的教训，记得把引号闭合了。`<p>` 里是 `{{ message }}`——因为我确信 Flask 会在我指定的位置动态输出这条消息。

回到 `app.py`，**app.py 本身是知道哪里出错了的**，它比模板知道得多。所以删掉那两行笼统的失败页面，改成更具体的处理：

```python
name = request.form.get("name")
if not name:
    return render_template("error.html", message="missing name")

sport = request.form.get("sport")
if not sport:
    return render_template("error.html", message="missing sport")

if sport not in SPORTS:
    return render_template("error.html", message="invalid sport")
```

`if not name` 覆盖了姓名为空或 None 两种情况。最后那个 `if` 很可能拦下的就是 Kelly 试图注册的项目——排球；既然执行到这一步用户应该已被确认通过了，那没通过的原因就只剩一个：**不是有效的运动项目**。

回浏览器，不填姓名直接点注册——

「遇到了未知标签 body」的错误。又是低级错误。这个错误很隐蔽：我把两个词的位置搞反了。正确的写法应该是 `{% block body %}`，而不是 `{% block %} body`。

改好。重新加载，它提示我再次确认是否要提交完全相同的表单——回想一下，这个表单既没有姓名也没有运动项目。刷出来的错误提示是件好事：**这不是服务器错误，是我这边出的错，缺少姓名字段。** 现在这个提示虽然对用户不太友好，但至少给出了更详细的说明。

逐一验证：加上姓名但没有运动项目 → 提示缺少运动项目；有运动项目但没有姓名 → 提示缺少姓名。如果我像 Kelly 之前那样通过修改 HTML 添加「排球」选项，系统同样会提示无效的运动项目，因为它不在预设的允许列表里。

### 全局字典：先把数据放进内存

好的，虽然这个注册网站的功能看起来挺有趣，但实际上它只是把提交的信息**直接丢弃**了。

我几年前的做法甚至更偷懒——当时我写的代码只是自动给校内体育活动的管理员发一封邮件，里面包含注册者的姓名和他们选择的运动项目。但很快我就用一个更好的功能取代了它，那就是**实际存储这些数据**，把数据存在服务器本身上进行跟踪管理，而不是仅仅通过邮件发送出去。

我们先初步尝试一下，实际存储所有体育项目注册者的信息。往上翻，我创建一个全局变量来简化操作，就叫它 `registrants`，设为一个空字典：

```python
registrants = {}
```

那对字符具体代表什么？——这是一个字典，Python 中的 `dict` 类型。你也可以显式写成 `dict()`，但更符合 Python 风格的做法就是直接用一对花括号。这只是一个空字典。

> **提示**：字典存的是键值对。我需要存储每位学生的两项信息——他们的**姓名**以及**注册的体育项目**，那我就让姓名当键、体育项目当值。

在 `register` 函数里实现起来非常简单。之前我只是简单显示「您已成功注册」，实际上没对用户提交的信息做任何处理；但这很容易解决：

```python
registrants[name] = sport
```

姓名信息仍然通过 `request.form.get` 获取，运动项目也是通过它获取，所以这里只是把键值对存起来。数据已经存在计算机的**内存**中了。

### 表格与 Jinja 循环的合谋

那怎么实际查看这些数据？如果注册后能看到网站的实际注册者名单是不是会更好？确实，如果你就是负责组织体育活动的管理员，这功能会很有用。

那就再创建一个路由，比如 `/registrants`，它返回所有注册者的列表，并把全局字典里的数据传进去：

```python
@app.route("/registrants")
def registrants():
    return render_template("registrants.html", registrants=registrants)
```

然后是模板 `registrants.html`。这里会比之前的复杂一些，但我们可以沿用上周的部分 HTML。先加一个 `<h1>`「注册者」，让监考人员清楚他们看的是什么，然后放一个表格，两列：姓名和运动项目。

```html
{% extends "layout.html" %}
{% block body %}
    <h1>注册者</h1>
    <table>
        <thead>
            <tr><th>姓名</th><th>运动项目</th></tr>
        </thead>
        <tbody>
            {% for name in registrants %}
                <tr>
                    <td>{{ name }}</td>
                    <td>{{ registrants[name] }}</td>
                </tr>
            {% endfor %}
        </tbody>
    </table>
{% endblock %}
```

先解释一下表格本身的结构。`<table>` 里用 `<thead>` 定义表头，表头只包含一行，用 `<tr>` 表示，每个单元格用 `<th>` 定义——一个叫「姓名」，一个叫「运动项目」。在表头之后用 `<tbody>` 定义表格主体，并在其中填充内容。

**这正是 Jinja 模板引擎派上用场的地方**：我可以对注册者占位符中的每一个姓名写一个循环，每次迭代输出一个 `<tr>` 表格行，里面放两个 `<td>`——第一个放学生姓名，来自当前循环变量，就像 Python 一样；第二个从注册者占位符里以学生姓名为键取出运动项目。这样每位学生的姓名和所选运动项目就并排显示在同一行。

> **结论**：表格结构完全由 HTML 负责，表格里有多少行完全由 Python 负责。这正是模板引擎的核心价值——**结构是固定的，数据是动态的，两者互不干扰**。

这让我想起上周我们讨论过的一个概念。当时我们谈到栈结构，我提到像 Gmail 或 Outlook 这样的收件箱本质上就是一个栈，最新的邮件显示在最顶部。我当时还推测，我们上周开始讨论 HTML 的时候，这种界面很可能就是通过一行接一行、连续不断地行来呈现的——这就是 Google、微软这些公司很可能一直在采用的做法：当页面中存在表格化信息时，他们在内存中存一些数据（比如注册者信息），然后使用 Jinja 这样的模板引擎，通过类似刚才的代码逐行输出表格行。想象一下，如果这是你的电子邮件收件箱，背后的原理是完全一样的。现在我们**已经能够表达这种逻辑了**。

回浏览器，刷新 `/registrants`，一个非常不美观但功能完整的 HTML 表格出现了，两列：姓名和运动项目，表头区域里能看到 David 和篮球。再返回表单为 Kelly 注册足球，刷新名单——Kelly 和 David 都在了。

> **注意**：如果我在浏览器里查看页面源代码，会发现所有表格行都是**在服务器端动态生成好的**，在以当前形式发送到浏览器之前就已经完成了。

### 别让用户自己找链接

接下来是关于这个示例当前实现的功能及其运作原理的问题。**要把注册者页面限制为仅特定人员访问，理想的做法是为该页面设置密码保护。** 事实上，我们接下来要演示的示例之一就是登录页面，正是出于这个目的。

目前我们暂时采用信任机制——只有相关监考人员会访问这个网址。但为了讨论方便，我们假设你确实希望公开注册名单，哪怕只是为了展示已经注册的人员名单。直接告诉人们去访问 `/registrants` 这个路径并不是一个好主意。

我们可以通过几种不同的方式把用户链接到那个网址。比如我可以翻到 `success.html`，设置一个 `href` 等于 `/registrants`——现在我能控制 HTML 和路由了，所以 `/registrants` 这个路径就会生效。

```html
<a href="/registrants">看看谁已注册</a>
```

鼠标悬停在链接上时，虽然显示区域非常小，但左下角会浮现链接地址。点进去，John 的名字已经出现在表格的底部了。

还可以更优雅一些——我其实不一定非得用这种 HTML 的临时方案。**为什么不直接自动显示已注册的用户呢？** 这其实也是 Web 应用一个很实用的功能特性。

除了导入 Flask、`render_template` 和 `request` 之外，我还需要导入 Flask 内置的一个名为 `redirect` 的函数：注册成功后，直接返回一个重定向结果，把用户引导到 `/registrants` 路径，而不是仅仅显示「成功」页面。

```python
from flask import Flask, redirect, render_template, request

@app.route("/register", methods=["POST"])
def register():
    ...
    return redirect("/registrants")
```

点完注册之后，浏览器顶部地址栏的 URL 会直接变成 `/registrants`——我被自动带到了名单页。成功页面这个模板现在其实可以删掉了。

### 内存会蒸发，数据库不会

不过代码改了一版，数据库里只有一个人，这实际上暗示了一个我们确实应该解决的问题。

问题在于：**如果这个服务器一旦离线**——可能是因为需要更新、崩溃，或者你按下 `Ctrl+C` 回到终端——服务器就会重启，Flask 服务器已停止运行，这意味着那个名为 `REGISTRANTS` 的全局变量也随之消失了。就好比内存被释放了。所以如果我现在重新运行 Flask（就像服务器本身重启时会自动发生的那样），回到注册页面一刷新，会发现**没有任何人注册过**。

实际上刚才 Doug 遇到的就是这种情况，因为我修改了我的实际应用代码。Flask 很智能，它意识到「等等，代码已经变了」，于是重新加载程序——这样我就得到了一个全新的全局变量版本，一个全新的空字典。

> **结论**：显然，比在服务器内存的变量里存注册者信息更好的方式是什么？是的，没错，**应该使用真正的数据库**。

这就是所有内容形成一个完整循环、又和第 7 周的 SQL 连起来的地方。回到 `app.py`，我对我实现的逻辑还算满意——不满意的是它只是把注册者信息存在一个全局变量里，而这个变量只住在计算机的**易失性内存**中。我们不如把这些数据存到数据库里。

去掉那个全局字典，从 CS50 自带的库中导入 SQL 模块。尽管我们已经逐渐移除了 CS50 提供的几乎所有辅助工具，但在最终项目里继续用 CS50 的 SQL 库，确实能让 SQL 和 Python 的结合变得轻松许多。当然你也可以用第三方库。

```python
from cs50 import SQL
db = SQL("sqlite:///froshims.db")
```

除了创建我的应用，我还要创建一个数据库（DB），设置为 SQLite，文件名叫 `froshims.db`。然后，既然我已经有了一个数据库变量，就不要通过字典来存储学生信息了，我们来实际执行一行 SQL 语句。

`db.execute` 插入数据——插到哪个表里？别担心，我早有准备。打开 `sqlite3`，用 `.schema` 查看结构：一张 `registrants` 表，包含 `id`、`name`、`sport` 三列，主键是 `id`（整数类型）。

> **结论**：这里我特意加了一些**约束条件**。我需要用户提供姓名和运动项目，所以这两列不仅要是文本类型，而且 **NOT NULL**——不允许插入空值。

> **易错点**：这里**绝对不能用 f-string，也不能直接拼接字符串**，不能盲目地把用户输入直接插进去。这就是 CS50 库以及现实世界许多库使用**占位符**的原因：由库自动对用户输入做安全处理，过滤掉可能引发问题的特殊字符，比如单引号、分号等。

```python
db.execute("INSERT INTO registrants (name, sport) VALUES (?, ?)", name, sport)
```

这一行代码就实现了你建议的效果：把注册信息存储在服务器上的**实际数据库**中，而不只是易失的临时内存里。

不过确实需要调整一个地方——「读取所有注册者」这一行现在不再有效了，因为我们已经没有那个全局变量了。多数网络应用会采用以下方式：定义一个变量并把它赋值为 `db.execute` 的执行结果，从 `registrants` 表中选取所有列。

```python
registrants = db.execute("SELECT * FROM registrants")
```

这样就能轻松地从数据库中获取所有注册者信息。现在不再使用全大写的全局变量，而是改用小写的 `registrants` 变量。**明确来说：在注册路由中，我把用户插入数据库；而在注册者列表路由中，我从数据库中选择用户数据。** 其余部分的代码可以保持不变。

回到 `registrants.html`，由于现在传入的不是单个字典而是一个字典列表，语法上要换个思路——用循环：

这段代码遍历注册者列表，其中**每个 registrant 都是一个字典**。所以现在我使用字典索引来访问这个字典对象中的 `"name"` 键和 `"sport"` 键。这和之前那个版本有本质区别：之前循环变量是**键**（姓名），值要用 `registrants[name]` 再查一次；现在循环变量是**整个字典**，直接用键名取值。

### 按 ID 取消注册

这个版本已经越来越接近多年前 Frosh IMs 网站实际使用的数据库功能了。

现在来提出下一个改进。我们已经有注册者信息表了——假设上次踢足球时 Kelly 的表现不太符合体育精神，所以我们想**取消她的足球注册**。在这个包含姓名和运动项目的 HTML 表格里，如果能添加一个按钮，让我可以取消 Kelly 或任何人的注册，那该多方便啊。

当我点击那个按钮时，理想情况下，为了从数据库中移除像 Kelly 这样的用户，浏览器应该向服务器发送哪些信息？——**用户的 ID**，而不是姓名。

**为什么？** 因为 ID 在 SQL 表中能唯一标识用户。

回到 VS Code，重新审视第 7 周的内容。打开 `sqlite3`，用 `.schema` 看表结构，然后直接 `SELECT * FROM registrants`，就能看到 4 位注册者的 ASCII 字符表格，以及他们的唯一 ID 和对应的数值。回顾第 7 周，这就是所谓的**主键**。

> **定义**：主键以最小的数据量唯一标识每个用户。因为如果另一个 Kelly 也注册了 Frosh IMs，我们就能避免误删错误的 Kelly，或者同时删掉两个 Kelly。我们只需要删除 **ID 为 2** 的那个 Kelly。

因此，添加到注册者页面的按钮需要包含目标删除人员的 ID 信息——因为**只有传递了 ID 参数，才能准确定位要删除的对象**。服务器可以根据这个 ID 号执行查询或删除操作，从而精准删除对应的数据行。

在当前的注册者路由页面里，我们可以为每个用户生成一个虽然简陋但功能完整的表单，把目标删除人员的 ID 传递给服务器。

差的那一点，其实横跨了这一整块内容：从一个表单怎么把 ID 悄悄带在身侧，到为什么删数据绝不能挂在 GET 上；再到静态资源为什么要单独住进 `static`，复选框取回来的为什么是一个列表；最后一路走到"你明明关掉了电脑，网站怎么还记得你是谁"这个我们每天都在用、却几乎没人细想过的问题。

### 把 ID 藏进表单

注册者页面现在要加第三列，专门放 HTML 表单。这个表单的 `action` 指向 `/deregister`，方法用 POST（等下就知道为什么必须用 POST），表单里放一个 `type="submit"` 的按钮，按钮上写着"取消注册"。

那么 ID 怎么传过去？最省事的办法是加一个输入框：

```html
<input name="id" type="text">
```

刷新一下，还真的能看到每个注册者旁边都多了一个按钮。可这就有点怪了：这等于要求用户自己动手，输入他想删掉的那个人的 ID。出现一堆一模一样的表单，而且完全依赖用户的自觉性。

这正是动态生成 HTML 的用武之地。把这个输入框的类型改成 `hidden`，值直接填成当前这次循环迭代拿到的那个注册者的 ID：

```html
<form action="/deregister" method="post">
    <input type="hidden" name="id" value="{{ registrant.id }}">
    <button type="submit">取消注册</button>
</form>
```

于是文本框不见了，按钮还在，信息一条不少。

中途还闹了个小插曲：页面上一片空白，查看源代码才发现，我在 `for` 循环里用的变量是 `registrant`（单数），却一时手滑写成了复数。改回单数之后往下滚，源代码里清清楚楚：David、Kelly、John 他们的 HTML 和之前一模一样，只是多了一列，列里装着一个表单，表单里藏着一个 hidden 的 `id`。1 号是我，2 号是 Kelly，再往下 3 号是 John，4 号是 Doug。

> **结论**：这个表单已经包含了足够的信息——即使用户除了点击按钮之外什么都不填，也能告诉服务器该删谁。

### 服务器端：一条 DELETE 加一个占位符

接下来只要加一个路由就够了。回到 `app.py`，在 `index` 路由下方新建一个：

```python
app.route("/deregister", methods=["POST"])
def deregister():
    id = request.form.get("id")
    if id:
        db.execute("DELETE FROM registrants WHERE ID = ?", id)
    return redirect("/registrants")
```

三点值得停下来看：

- 先用 `request.form.get("id")` 把 ID 从表单里取出来；
- 做个简单的合理性检查，ID 存在且不为空才动手，这样随便发一个无效参数过来也删不掉任何人；
- 问号是占位符，来自第 7 周的 SQL 知识，实际的 ID 单独作为参数传进去，交给数据库去执行删除；
- 不管执行没执行，最后都重定向回注册者页面，让你直接看到结果。

回到浏览器再试，Kelly 被移除了；再点一次，我自己也被移除了。打开终端 `SELECT * FROM registrants`，两个人都不在表里了。

### 删数据，为什么不能用 GET

问题就出在 `methods=["POST"]` 这一处——别小看它。

我特意用了 POST 而不是 GET，最初给的理由是"我可不想让 Kelly 的 ID 或者我自己的 ID 出现在浏览器的地址栏里"。但说实话，这个理由并不那么有说服力：ID 本身目前只是一些不透明的整数，并不直接关联到个人身份信息。

真正微妙的是另一件事：**GET 请求在理论上只需要输入一个 URL 或点击一个超链接就能访问到那个资源或路由**。

设想一下，如果允许用 GET 删除用户，攻击者只要构造一个像 `/registrants?id=4` 这样的 URL，通过邮件发出去——发给负责管理 Frosh IMs 项目的主管。那位主管如果没多想，顺手点了一下这个链接，而我这里恰好是用 GET 实现的，会发生什么？仅仅因为主管点了一封邮件里的链接，Doug 就被意外注销了。这其实也暗示着网络钓鱼攻击可能利用类似手段。

规则其实很清晰：凡是那些可以直接点击、可以手动输入的简单网址（也就是 GET 请求），都不应该导致服务器端的数据被修改。相比之下 POST 安全得多——你不可能仅靠点一个链接就触发 POST，通常都得点一个按钮。这种设计至少给了一层保护：主管会先收到邮件，点开链接后，页面上明确标着"注销"或类似功能的按钮摆在那里，不点就没事。

> **结论**：只要涉及任何个人身份信息，或者任何可能造成破坏的操作——比如像这样实际修改数据库里的数据——通常都更推荐使用 POST 请求。

### 错误页面也需要一张图

Frosh IMs 到这里已经能往数据库里加人、也能从数据库里删人了。本质上，这和大多数具备这类交互功能的网站非常相似。

接下来做点睛之笔。现在我们故意不填任何信息，直接点注册按钮，就会看到"姓名为空"的错误提示。要是能在页面上放一张图片让界面友好一点，是不是更好？

需要做的是在网页里嵌入一张图，最朴素的写法是：

```html
<img src="cat.jpeg" alt="grumpy cat">
```

`alt` 里的替代文本得加上，这样屏幕阅读器的用户、或者网速很慢的人至少知道这里本来该是什么。遗憾的是这样行不通：刷新并重新提交同一个表单，替代文本出现了，图却没出现——因为服务器上根本没有 `cat.jpeg` 这个文件。

那我提前准备的猫呢？我从另一个文件夹里把 `cat.jpeg` 复制过来，`ls` 一下，它确实和 `app.py` 躺在同一个目录里了，看起来完全没问题。可回到浏览器刷新，猫还是没显示。

这是使用框架的一个副作用，也是组织结构上的约定：任何你想在页面上显示的图片、任何你想嵌入的 CSS 文件、JavaScript 文件，只要它们属于**静态资源**，就应该放在一个叫 `static` 的文件夹里。这里的"静态"就是指内容不会改变的资源——你或者其他人一次性写好，它们不会像应用那样动态生成。

```bash
mv cat.jpeg static
ls
```

现在 `ls` 里 `cat.jpeg` 已经不在当前目录了。还要记得改 HTML 里的路径，源地址得明确写成 `static/cat.jpeg`，以表明它就在那个文件夹里：

```html
<img src="/static/cat.jpeg" alt="grumpy cat">
```

再次刷新，一只非常不高兴的猫出现了，至少让错误信息不再那么单调。

> **易错点**：从头到尾我们都没提过 `templates` 目录，因为 `render_template` 会自动去 `templates` 里找模板文件，你只需要提供文件名，不该（也没必要）写 `templates/` 这样的前缀。但反过来，HTML 模板里引用静态资源时，`/static` 这一段路径必须由你自己写上去。

顺手可以清掉一些已经用不上的东西：`success.html` 不再需要，布局模板也可以删掉，那个首页文件同样可以删除了。

### 从单选到复选：getlist

现在升级一下功能：允许用户注册多个运动项目，而不只是像单选按钮那样只能选一个——要报名一两次不同的运动项目却反复填写姓名，实在有点烦人。

```python
sports = request.form.getlist("sports")
```

```python
sports = request.form.getlist("sports")
if not sports:
    abort(400, description="缺少体育项目")

for sport in sports:
    if sport not in SPORTS:
        abort(400, description="无效体育项目")
```

报错还是走之前那套错误页（就是刚才那只暴躁猫出场的那个）。逻辑只是稍微繁琐了一点，但它换来了一个实打实的好处：可以遍历用户勾选的每个复选框，确保他们没有像之前 Kelly 那样随便编一个运动项目提交给我。

### MVC 回望：我们一直在实现的那个范式

在往下走之前，先回头看一眼整个项目的形状。我们其实一直在遵循一种相当常见的模式，它并不是 Flask 特有的。

先看文件结构：

```text
froshims/
├── app.py             控制器：所有逻辑、变量、函数、条件、循环
├── requirements.txt   依赖库清单
├── registrants.db     模型：持久化数据
├── static/            静态资源：图片、CSS、JavaScript
│   └── cat.jpeg
└── templates/         视图：用户看得见、并且与之交互的一切
    ├── index.html
    └── registrants.html
```

`app.py` 装着我们所有的逻辑需求；`requirements.txt` 只是列举我们想在项目中用到的库；`static` 文件夹装着所有静态文件（图片、JavaScript、CSS）；`templates` 文件夹存放实际的模板文件。

然后是三个角色。如果这张图代表人类或用户，他持续交互的对象通常被称为**视图**（view）——这是个专业术语，指的就是用户界面本身。但这个视图是由特定类型的代码生成的，也就是**控制器逻辑**（controller）。从技术上讲，`app.py` 就是业界通常所说的控制器逻辑或业务逻辑：它负责处理所有的逻辑、变量、函数、条件判断、循环，并生成一个或多个视图。

还有第三个关键部分，是我们刚刚引入的，通常被称为**模型**（model）。最初我的模型只是一个非常简单的内存字典，后来它逐渐演变成了 `froshims.db`。你的模型通常指的就是持久化数据，也就是存储与应用程序相关数据的地方。

```text
        +-------------------+
        |     controller    |  app.py
        |  逻辑 / 变量 / 循环 |
        +---------+---------+
                  | 生成
                  v
        +-------------------+
        |       view        |  templates/*.html
        |   用户看得到的一切  |
        +---------+---------+
                  | 读写
                  v
        +-------------------+
        |       model       |  froshims.db
        |     持久化数据     |
        +-------------------+
```

读图：控制器负责所有逻辑，生成视图；视图和控制器之间再通过模型读写持久化数据。

这就是 **MVC 范式**（模型、视图、控制器），一种非常常见的 Web 应用开发方式。它最大的用处不是代码模板，而是让你可以把要解决的不同问题分开思考：我需要实现控制器，它负责所有逻辑、变量、函数、条件、循环；我需要实现视图，它包含用户看到并与之交互的所有内容（比如 HTML）；最后我还需要实现模型，它涵盖所有后端数据之类的东西。

> **易错点**：但这条界限并不清晰。因为很明显，在视图里我们同样见过变量、循环和条件判断（`registrants.html` 和 `books.html` 里不都写了 `for` 和 `if` 吗）。所以这是一种通用的思维方式；而在实际开发中，如果你继续探索 Web 应用，会发现这些概念常常相互交织。而且这张图并没有按照正确的顺序来展示各部分。

### Gmail 是怎么"记得"你的

现在来解决一些更实际的问题。

当你登录 Gmail 或者其他需要用户名密码的网站时，通常会看到这样的界面：它只是一个网页表单，看起来比我的表单漂亮得多，他们用了一些精美的 CSS 让界面呈现蓝色、整齐缩进之类，但本质上它仍然是 HTML，很可能就是用 `input type="text"` 生成的那个文本框。

关键在于，你输入密码登录之后，系统通常会**记住你的登录状态**，这种状态可能持续数天甚至几周。这究竟是怎么实现的？

你第一次登录并点击提交或下一步按钮时，浏览器会向 `accounts.google.com` 的某个路径（例如 `/login`）发送一个 POST 请求，地址正是 Google 通常用于处理登录的 URL。请求里包含你的用户名、密码以及其他提交给服务器的信息。理想情况下，服务器返回 `200 OK`，并显示你的收件箱页面。你已成功登录——但系统在后台还执行了另一个动作：**在你的电脑上设置了一个 Cookie**。

Cookie 的名声不太好，因为它常被用于追踪用户行为、投放广告，某种程度上确实像是在"监视"你。但从本质上讲，Cookie 只是 HTTP 协议的一项功能，它非常实用，能解决一些典型问题。

> **定义**：Cookie 是另一个 HTTP 头部信息，通常包含在服务器返回给浏览器的虚拟数据包中。它除了告知浏览器数据包里的内容类型之外，还可能指示浏览器："请设置以下 Cookie。"

Cookie 本质上就是一个键值对。它可能类似于 `session=某个值`，而那个值通常是一个随机字符串——可能是 `123456` 之类，但总之是一个唯一标识符。

> **易错点**：如果 Google 在实现 Cookie 时处理不当，他们理论上可以指示你的浏览器在电脑上存储一个包含**用户名和密码**的 Cookie，这样你明天打开 Gmail 就不用再看到那个烦人的登录表单了。但用 Cookie 存用户名和密码是糟糕的做法，因为它把非常敏感的数据放进了浏览器的内存里——任何路过你电脑的兄弟姐妹或室友，只要查看你的 Cookie，就能轻易找到你的用户名和密码。

所以实际的做法更接近另一张截图：服务器所做的，只是在你的电脑上存储一个**大型随机值**，本质上是一个装着该随机值的文本文件。

### 手戳：Cookie 的本质

这实际上相当于一种"手戳"机制，就像你去某些场所获得的入场凭证一样。去酒吧、俱乐部或游乐园，通常你入场时出示一次门票，之后如果想反复进出，只需展示手上的凭证即可。

我现在的手还没有被盖章——等会儿应该会在我手上贴一个可爱的笑脸贴纸。这样我随时想返回酒吧、俱乐部或游乐园时，他们就知道我们已经核实过你的身份了，而这应该是在你第一次入场时就完成的。

**这就是 Cookie 的全部作用：它是在你的浏览器中放置了一个虚拟的"手部盖章"。**

浏览器和服务器正是通过这套机制来回记住你的身份：

```text
     browser                                    server
     -------                                    -------
        |                                         |
        |    GET /login  +  username + password   |
        |  ---------------------------------->  |   check credentials
        |                                         |
        |    200 OK  +  Set-Cookie: session=8f3a |
        |  <----------------------------------  |   hand out a stamp
        |    (store "session=8f3a" locally)      |   (== the hand stamp)
        |                                         |
        |    tomorrow: GET /inbox                 |
        |    Cookie: session=8f3a  ------------->  |   read the stamp,
        |                                         |   find server-side data
        |    200 OK  +  inbox HTML               |
        |  <----------------------------------  |
```

读图：`Set-Cookie` 是服务器发出来的，等于给你手盖个章；`Cookie` 那一行是浏览器每次都自动带上来的，等于每次都出示手上的那个印章。所以你明明关掉了电脑，服务器却"知道"你昨天登录过。

这也解释了广告商追踪你的方式：他们在某个时间点在你电脑上放了一个 Cookie，你不知情的情况下访问这个网站、那个网站、另一个网站，你的浏览器一直在展示这个"手印"。广告商一看：哦，又是 David。又是 David，还是 David，因为他们看到的是同一个"手印"。

所以我理解隐身模式了。通常如果你想做点私密操作、不希望这些记录留在电脑内存里，就会用隐身模式；它在关闭窗口时会清除所有 Cookie，这就像下次访问同一个网站时，把"手印"彻底擦掉。

### 无状态协议里的"会话"

我认为这是今天最核心的概念：**会话（session）**。

会话是一种功能，它让浏览器和服务器之间能够建立起持久的连接，尽管 HTTP 本身是所谓的"无状态"协议。"无状态"就是指没有持续的状态记录——你与服务器之间并没有持续不断的连接（虽然现在情况并非总是如此，有时确实能保持稳定、持久的连接）。

但 Cookie 的作用在于：即使你合上笔记本电脑、甚至关机，第二天再回来，仍然能产生一种"连接从未中断"的错觉，就像前一天一样。

更具体地说，你可以把会话理解成 Python 里的一个键值对字典，你可以为每个用户关联一组这样的键值对。当我登录一个用 Cookie 实现会话的网站时，服务器可以在它的内存里存储关于我的任意数量的键值对，而我出示的那个"手印"（Cookie）会确保服务器知道：哪些键值对应的是我。

### Flask-Session：把上面那套当功能用

我们做一个小得多的 Flask 应用来演示登录功能。`login` 目录里 `ls` 一下，是几个熟悉的老朋友：`app.py`、`requirements.txt`、`templates` 文件夹。

但这次要特别注意一个我们**现在开始使用**的库：**Flask-Session**。它是一个第三方库，让我们能够在应用中轻松使用 Cookie，而无需理解或处理刚才那些 HTTP 请求头里的底层细节。

说白了，已经有人把 Cookie 的工作原理搞清楚了，我现在只想把它当作一个功能来使用：这样当用户访问我的网站时，我就能把数据与他们关联起来，比如他们的身份、用户名，从而确认他们已经登录。

设计上保持极简，目前只使用用户名，不设密码。

```python
from flask import Flask, redirect, render_template, request, session
from flask_session import Session

app = Flask(__name__)
app.config["SESSION_TYPE"] = "filesystem"
Session(app)
```

逐段看：

- 从 `flask` 导入 `Flask`、`redirect`、`render_template`、`request`，还有一个新成员 `session`。你可以把 `session` 想象成一个字典，可以为每个用户存储键值对，而 Flask 会确保你的代码能正确管理这些数据。**每个访问网站的用户都会拥有自己独立的 `session` 副本**——你可以像只处理单个用户那样去用它，但 Flask 会保证用户来的时候各自拿到专属的那一份。
- 单独一行从 `flask_session` 导入大写的 `Session` 类；
- 把这个文件转换为一个 Flask 应用（`app = Flask(__name__)`，老规矩没变）；
- **新增的一行**，需要复制粘贴：`app.config["SESSION_TYPE"] = "filesystem"` 配置这个应用使用会话功能，具体方式是把 cookie 数据以文件形式存储在服务器上，而不是存入数据库或别的地方——这是我们这个示例采用的默认配置；
- `Session(app)`。

接着看首页 `/` 的路由：

```python
@app.route("/")
def index():
    return render_template("index.html", name=session.get("name"))
```

`index` 函数的核心作用就是渲染一个名为 `index.html` 的模板，然后传入一个名为 `name` 的占位符，其值是 `session.get("name")`。无论会话里存了什么名字（如果有的话），都会被传给模板。

打开 `index.html` 看看，这才是刚才那两个不同版本首页的实现逻辑：如果 `name` 有值（不为空），就显示"您已以 David 身份登录"，并给出一个登出链接；如果 `name` 为空（比如你登录之前，默认就是如此），就显示"您尚未登录"，并给出一个登录链接。**这就是通过条件逻辑检查当前到底有没有用户实际登录。**

登录路由：

```python
@app.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "POST":
        session["name"] = request.form["name"]
        return redirect("/")
    else:
        return render_template("login.html")
```

> **定义**：会话是一种特殊的全局变量，每个用户都会分配一个独立的实例，其底层实现正是靠 Cookie，或类似"手部盖章"的机制完成的。

这里藏着一个值得琢磨的分岔。如果你到达 `/login` 是通过 POST 请求，那很可能是因为你点了我提供的登录按钮——那么我就在会话字典里存入一个名为 `name` 的键，值就是用户在表单里输入的任何内容（David、Kelly、John 还是别的名字），这些数据会从表单返回，我只需把它存进去。然后重定向到根路径 `/`。

**否则**，如果请求方法不是 POST，那意味着用户是手动访问、直接输网址进来的，那我就向他展示登录页面 `login.html`。它相当简单：一个文本框加一个提交按钮，关键之处在于它会提交到 `/login` 这个路径，也就是我们刚刚查看过的那个路由。

`flask run` 起来看看效果。默认情况下，网站先告诉你"您尚未登录"，这里有一个登录链接，字有点小；如果你查看页面源代码，URL 是以 `/login` 结尾的，能看到一个通过 POST 提交到 `/login` 路由的表单，唯一特别的地方是它包含一个文本框和一个登录按钮。

点击登录——注意页面瞬间跳转回了根路径 `/`。Chrome 把斜杠藏起来了，但网站已经知道我是以 David 的身份登录的。查看页面源代码，它不再显示"您未登录"，而是显示"您已以 David 身份登录"，并根据条件给出了一个登出链接。我认为这就代表了任何允许用户登录和退出的网站的基本机制。

**登出是怎么做的？** 简单到有点好笑：调用 `session.clear()` 就能清空会话内容。点击"退出登录"时，服务器其实处理得非常迅速，你甚至来不及看地址栏发生变化。`session.clear()` 让我退出了登录——此时我电脑上存储的 Cookie 实际上已被删除，更准确地说，是与该 Cookie 关联的服务器端数据被清除了，所以我完全看不到任何相关记录了。

> **结论**：Facebook、Gmail、Outlook 或者任何其他网站，本质上就是这样让你保持登录状态的——当然，它们还会在流程里加入密码和其他安全措施。

### 购物车：会话最直观的用处

再来一个例子。回到终端，`cd store`，一个最简单的网店功能——就像那种带有实际购物车功能的电商网站。这里除了模板文件，还有一个数据库文件 `store.db`。

直接 `sqlite3 store.db` 打开它，`.schema` 看看结构：只有一张表，看起来像一家书店，有点像最早的亚马逊版本——两列，一列 `ID`，一列 `title`，存这家书店要卖的所有书。`SELECT * FROM books;` 一看，只有 5 本书，其中包括《银河系漫游指南》及其续作。

如果能有个网站展示这个目录里的所有内容，并且允许我把商品"添加"到购物车，是不是就方便多了？

这里有一个更贴切的比喻可以解释什么是会话：**会话本质上让你能够实现购物车这样的功能**。当然，现实世界中的购物车是每个用户专属的。

设想一下：我在 Amazon.com 上购物，Kelly 也在 Amazon.com 上购物，而且我们都已登录，我们显然不会看到对方购物车里的内容。这是因为我们各自拥有独立的 Cookie，Flask 或 Amazon 使用的技术营造出了这种"专属"的假象——我们各自都有一个名为 `session` 的全局字典，服务器可以在里面存储任何它需要的键值对，比如我们购物车里的商品信息。

### 书店页面：一个 for 循环生成整页按钮

启动起来，刷新页面。界面非常简陋，因为我只是用最简单的 HTML 快速搭的，但你会看到这里列出了数据库中的每一本书，以及一个"加入购物车"按钮。

用 HTML 能做的事情其实并不多，主要就是通过表单，可能再加一些隐藏元素。这里有一个 `h1` 标签写着"书籍"，然后是一个 `for` 循环，为每一本书生成一个 `h2`（字体比 h1 小一点）和一个表单标签，表单里有一个 hidden 的输入，值等于当前这本书的 `ID`：

```python
@app.route("/")
def index():
    books = db.execute("SELECT * FROM books").fetchall()
    return render_template("books.html", books=books)
```

模板里那个循环生成出来的表单长这样，表单的 `action` 指向 `/cart`：

```html
<h1>Books</h1>
{% for book in books %}
    <h2>{{ book.title }}</h2>
    <form action="/cart" method="post">
        <input type="hidden" name="id" value="{{ book.id }}">
        <button type="submit">Add to Cart</button>
    </form>
{% endfor %}
```

（书名里那个类似弯引号或撇号的字符，在页面源代码里显示为一个 HTML 实体——那是 Flask 为我输出的，尽管在数据库里它并不是那个样子。）

每个表单都有一个"添加到购物车"按钮。和 Kelly 的注销示例一模一样的套路：每样东西都可以通过它唯一的 ID 加入购物车，而不是靠用户在文本框里自己输入。

### 购物车路由：会话里放一个列表

点击《银河系漫游指南》的按钮，那本书就成功加进去了；再点《宇宙尽头的餐馆》，购物车里有两本书了。**这些数据究竟存到哪里去了？**

焦点切到购物车路由。这个路由同时支持 GET 和 POST：

```python
@app.route("/cart", methods=["GET", "POST"])
def cart():
    if "cart" not in session:
        session["cart"] = []

    if request.method == "POST":
        id = request.form.get("id")
        if id:
            session["cart"].append(id)
        return redirect("/cart")

    books = db.execute("SELECT * FROM books WHERE ID IN (...)").fetchall()
    return render_template("cart.html", books=books)
```

一个键值对就能记一整个列表，原理就这么简单。我可以往 `session` 里放入任何我想要的键值对；如果我希望购物车能有效记录用户添加的所有书籍，那么合理的做法就是：**当用户首次访问时，购物车默认应该只是一个空列表**。

如果用户是通过点击提交按钮来到这里的，就执行下面那段：从表单里拿到他提交的书籍 ID，确认这个 ID 确实存在（而不是像 Kelly 那样随便发送无效参数来捣乱），把它追加到会话中的购物车列表里。

> **易错点**：任何时候进行重定向，都应当使用 GET 方法，而不是 POST。所以提交后 `return redirect("/cart")`，等我稍后再次访问这个购物车路由时，就不会用 POST，而是 GET。而 GET 分支才是真正查书、渲染购物车的那一段。

这段查询用的是 `IN`：

```python
# IN 的括号里放 session["cart"] 中的 ID 列表
books = db.execute("SELECT * FROM books WHERE ID IN (...)").fetchall()
return render_template("cart.html", books=books)
```

回想一下第 7 周学的 `IN`：它允许我一次性查询多个 ID，只要我选择这样做。页面上之所以显示两个条目，打开开发者工具看源码就很清楚了——那是一个有序列表（带编号的列表）里包含两个列表项，正是购物车里的内容。

### 从等值到 LIKE：给自己的节目写个搜索引擎

既然我们现在能利用会话来记录登录状态、追踪购物车了，那么更广泛地说——即使不使用会话机制——Web 应用还能实现哪些功能？我来演示最后一组。

`cd shows`。这个目录名让人联想到我们过去用 IMDB 的经历，里面有 `requirements.txt`，以及 `shows.db`——这正是我们前几周用过的那个数据库，里面存了大量来自互联网电影数据库（IMDb）的影视信息。

这里实现了一个非常简单的程序：一个索引页，再加一个搜索路由——它类似于我们之前用 Google 搜索猫狗时的那种功能，只不过这次是我第一次为自己的电视节目（而不是猫狗）实现一个搜索引擎。

```python
@app.route("/search")
def search():
    shows = db.execute(
        "SELECT * FROM shows WHERE title = ?", request.args.get("q")
    ).fetchall()
    return render_template("search.html", shows=shows)
```

它使用一个 `shows` 变量，执行 `SELECT * FROM shows WHERE title = ?`，然后就像 Google 那样传入 `q` 参数（代表查询内容），最后渲染一个名为 `search.html` 的模板，把这些 `shows` 作为占位符传进去。

跑起来试：在根路径 `/` 的搜索框里输入 `The Office`（注意首字母大写）然后点搜索，返回的结果信息量不大，但会列出一个**无序列表**，列出所有标题完全匹配的节目。查看页面源代码你就会发现，数据库里既有英国版、美国版，还有其他一些版本。

但如果我输入小写的 `the office`，表单就无法正常工作了，得不到任何结果——倒不是说功能有问题，只是目前这里的功能还不够完善。

**来把它改完善。** 下一个版本里，我不再使用简单的等值查询，而是用上了 `LIKE` 关键字，因为我需要检查它是否"包含"office：

```python
shows = db.execute(
    "SELECT * FROM shows WHERE title LIKE ?", f"%{request.args.get('q')}%"
).fetchall()
```

这个设计初看可能有点巧妙，也可能有点令人困惑：我明明有一个问号占位符，却又不想仅仅搜索用户输入的内容。我需要通过 SQL 通配符来允许左侧和右侧出现零个或多个任意字符——所以在用户输入的内容前后各拼接一个百分号。大家还记得第 7 周学 SQL 时讲过的内容：`%` 表示任意长度的任意字符。于是这就变成了以不区分大小写的方式，查找任何包含这些字母的内容，无论这个字符串出现在文本的哪个位置。

输入小写的 `office` 现在也能正常工作了，而且它还能搜索任何提及 office 的内容。

那它是怎么知道要把这些内容渲染成带项目符号的办公室列表的呢？打开搜索路由用的 HTML 模板，你看到的还是那个 Jinja2 循环：为每个搜索结果输出一个列表项。实际上和我之前的做法完全一样。

### 从整页 HTML 到 JSON API

不过，我还可以采用另一种完全不同的技术，这通常能为我们的期末项目（甚至更长远）开辟更多可能性，本质上就是**创建我自己的 API**。

与其仅仅开发一个直接输出完整 HTML 页面给用户看的 Web 应用，不如尝试创建一些直接输出所需数据的路由接口。这样一来，不仅我自己，甚至第三方开发者也能利用这些数据，把我的应用功能整合进他们自己的网站中。

> **定义**：API（应用程序编程接口）本质上是一种基于网络的功能接口。你可以通过调用 API 从他人的服务中获取数据，通常使用 HTTP 协议。返回的数据可以是文本格式、HTML 格式，或者称为 JSON（JavaScript 对象表示法）的格式。JSON 看起来有点像 Python 的语法，它结合了数组和字典的结构。

#### 返回原始 HTML 片段

第一个改造版（`shows2`）里，搜索框还在，但**不再有搜索按钮**，因为它的设计目标是高度交互性——我可以搜索 `THE OFFICE`，这实际上就是自动完成功能，我们上周在 JavaScript 里已经初步体验过了。

怎么做到的？重新加载页面并打开开发者工具，这次重点看**网络面板**：当我输入字母 `T` 时，网页立即向我的 `/search` 路由发送了一个请求。点开返回的响应，你会看到 `/search` 路由返回的并不是一个完整的网页，而是一大堆 `<li>` 标签。

回到 VS Code 看代码就明白了：之前那一版的 HTML 代码会扩展我的布局模板，把整个无序列表嵌进去；而这一次我只输出了原始的 HTML 代码，因为我假设可能有人（包括我自己）想通过 `/search` 路径直接获取一堆列表项，以便把它们放进自己的 `<ul>` 标签中。

所以这里实际发生的情况是：**每当我输入一个字母时，就会有一个新的 HTTP 请求通过网络发送出去，而每个这样的请求都会返回一组与我所输入的查询相匹配的列表项。**

> **提示**：但这可能有点不够严谨——到目前为止，我返回的是一段脱离上下文的 HTML 代码片段。强制要求用户必须使用列表项，这并不理想。如果能直接发送原始数据会更好。

#### 返回 JSON

第三个版本（`shows3`）就真的返回原始数据了。运行起来，回到浏览器搜索一个字母 `T`，再点那一行——现在开发者工具的响应标签页里，收到的是一大块有价值的信息：一大块 JSON 格式的数据。

注意看：这里的**方括号**表示接下来是一个列表或数组，里面出现了一个**字典（dict）**，这正是我所看到的。它看起来像 Python，但从技术上讲它是 JavaScript，更准确地说，是 JavaScript 的对象表示法。它仅仅意味着：我收到的是这些有价值的数据，来自服务器。

> **提示**：回想一下第 0 周，甚至我们关于人工智能的那个家庭周末讲座——当时我编写了与 OpenAI 所谓的 API 进行通信的代码，以从我们服务器端的那只猫获取响应。他们发送给我们的正是这种 JavaScript 对象表示法，而我当时只是提取了我真正关心的数据，也就是猫的实际回复。

那这次是怎么做到的？打开 `app.py` 里的搜索路由，会发现它并没有返回模板，而是使用了一个名字有点特别的函数——`jsonify`。它是 Flask 自带的功能，作用是把从 SQL 数据库返回的 Python 字典列表，以 JSON 格式进行序列化。

```python
@app.route("/search")
def search():
    shows = db.execute(
        "SELECT * FROM shows WHERE title LIKE ?", f"%{request.args.get('q')}%"
    ).fetchall()
    return jsonify(shows)
```

这样我就能把它作为一个服务提供给互联网上的任何人，包括我自己，让我和别人都能利用这些数据来开发他们自己的 Web 应用。

### 三个 shows 版本放在一起看

| 版本 | 关键 SQL | 路由返回什么 | 交互形态 |
| --- | --- | --- | --- |
| shows（初版） | `WHERE title = ?` | 扩展布局的完整 `search.html` | 搜索框 + 搜索按钮，严格等值匹配 |
| shows1 | `WHERE title LIKE ?` 配 `%q%` | 完整模板 | 搜索框 + 按钮，大小写不敏感的包含匹配 |
| shows2 | 同上 | 原始 `<li>` 片段，不套模板 | 无按钮，边输入边请求（自动完成） |
| shows3 | 同上 | `jsonify(shows)` 返回 JSON | 同样的自动完成，数据格式与展示彻底解耦 |

读表：从上到下只做了三件事——匹配方式从等值放宽到包含、返回内容从完整页面收窄到数据片段、交互从"点一下"变成"边输入边请求"。而其中真正属于 Flask 的只有 `render_template` 和 `jsonify` 这两个出口。
