# 数组、字符串与程序调试

## 调试工具箱

### 工具的分工与优先级

* **工具箱总表**

    | 工具 | 什么时候用 | 能回答什么 |
    | --- | --- | --- |
    | 编译器报错 | 代码压根编不过 | 哪个符号、哪一行不合语法 |
    | `printf` 调试法 | 编译过了但结果不对 | 中间变量到底是什么值 |
    | `debug50` 单步 | 想知道执行流 | 每一行执行时，内存里到底是什么 |
    | 橡皮鸭 / AI | 逻辑绕住了，说不清 | 我到底卡在哪一步 |
    | 编译器 `clang` | 想看清"翻译"这件事 | 我的代码到底被变成了什么 |

* **工具使用顺序**

    * 优先级是硬性的：先 `printf`，再 `debug50`，再实体橡皮鸭，最后才是 AI。

    * 把顺序颠倒，就永远不会自己长出调试能力。

* **橡皮鸭调试法（rubber duck debugging）**

    * > **定义**：卡在某个错误、漏洞或困惑的概念上时，把问题向一个对象倾诉出来，往往就足以让你灵光一闪。

    * 有效的原因在于你亲耳听到自己把困惑所在、逻辑漏洞说出口，甚至不需要助教或 AI 回答，问题往往就解决了。

    * 它是一种**求助机制**，适用于那些你认为自己无法独立解决的问题；看不懂一条错误信息时求助是合理的。

* **AI 辅助的纪律**

    * 不要把代码直接复制粘贴给 AI，再问一句"我的代码哪里有问题"。

    * 应该与 AI 进行协作式互动；课程的核心意义在于培养编程直觉、构建思维模型、掌握实际技能。

    * 在过度依赖外部求助和自己动手用工具之间找到平衡：找真人或"橡皮鸭"之前，先试 `printf` 调试法，甚至在桌上摆一只实体橡皮鸭。

* **bug 一词的由来**

    * "bug" 与"调试"这两个词由格蕾丝·霍珀博士（美国海军少将、哈佛马克一号原始程序员之一）推广。

    * 哈佛马克一号的计算日志本上记录着：机器电路里卡进了一只飞蛾，日志写的是"这是首次发现实际存在的 bug 案例"。

    * 那台机器的一部分展品在科学与工程综合楼大厅里；它后来被哈佛马克二号取代。

## 语法错误与逻辑错误

### 语法错误（syntax error / programming error）

* **定义与拦截机制**

    * > **定义**：语法错误直接让程序无法编译，是程序运行的"致命障碍"。

    * 编译过程中只要有一条错误，后面全部代码都不会被编译。

    * 因此编译器根本没看到你在修好第一条错误之前写的那些修改——它们被彻底忽略了。

* **典型报错与对应错误**

    * 缺少 `#include <stdio.h>`：`buggy.c:3: 错误：调用了未声明的库函数 'printf'`。

    * 语句末尾缺分号：`buggy.c:5: 错误：表达式后缺少分号`。

    * 漏写 `'\n'` 换行符：能编译能跑，但提示符会出现在错误的位置上。

* **易错点**

    * > **易错点**：错误信息不是一份"待办清单"的全部，而是"编译器放弃之前最后看到的东西"。按报错顺序从上往下修，一次只改一个。

### 逻辑错误（logic error）

* **本质与不可判定性**

    * > **定义**：逻辑错误不会阻止编译，缺陷只存在于逻辑和设计意图层面。

    * 例：写 `string name = get_string(...)` 但 `printf("hello, %s\n", name);` 漏写，程序编译通过，运行时只输出 `hello` 而没有名字。

    * > **易错点**：程序能编译通过**不等于**程序是对的。编译成功只说明符号符合 C 的语法规则，一点也不说明它符合你的意图。

    * > **结论**：逻辑错误没有任何工具能"自动判定"对错，因为没有 ground truth 交给工具，只能靠自己的判断。

    * `check50` 能自动评估并指出输出错误，但**编译器**完全无法理解你的意图——它只认识 C 的规则，只关心语法。

* **缺陷暴露的时机**

    * 语法全对之后，代码里仍可能藏着缺陷，往往要等你真的输入了东西、亲眼看见程序跑起来的样子才会暴露。

    * 那一刻屏幕上根本没有报错，只有一句不完整的输出，调试不再是"读懂报错信息"那么简单。

## 头文件与函数原型

### 标准库与 CS50 库

* **两个库是两回事**

    | 类别 | 典型成员 | 链接方式 |
    | --- | --- | --- |
    | 标准库 | `printf`、`strlen`、`islower`、`toupper` | 自动生效，不需要额外写链接参数 |
    | CS50 库 | `string`、`get_string`、`get_int` | `clang` 需显式加 `-lcs50` |

* **错误的两种面貌**

    * 漏 `#include <cs50.h>` 时的报错是 `buggy.c:5: 致命错误：使用了未声明的标识符 'string'`，后面还跟一句 `did you mean 'stdin'?`。

    * 这条建议是误导：编译器只是在它认识的词里找了个最像的，`stdin` 恰好和 `string` 只差一个字母。真正的错误是忘了包含 CS50 的头文件。

    * 同时包含 `stdio.h` 和 `cs50.h` 之后，`cs50.h` 做了两件事：声明了 `get_string` 让编译器知道它存在，并且**真正定义了 `string` 这个类型**。

* **易错点**

    * > **易错点**：`printf` 属于标准库，`string`、`get_string`、`get_int` 属于 CS50 库，少一个 `#include` 编译器就会报"未声明的标识符"。

    * > **易错点**：`string` 现在存在纯粹是因为 CS50 库让它存在，字符串只是"换了个名字称呼"的辅助轮，现实中每一位开发者都在用 string 这个词，但**C 语言本身没有 `string` 这个关键字**。

* **书写习惯**

    * 习惯**按字母顺序**排列头文件。技术上不是强制的，属于代码风格问题，但按字母顺序扫一眼更容易看出某个功能到底包没包含进来。

* **对未声明标识符的处理**

    * 在 C、C++、Java 里必须明确告诉编译器要实例化一个变量，指定它的类型；Python 之类的语言则不需要显式声明类型。

    * `name = get_string(...)` 报 `使用了未声明的标识符 'name'`，就是因为忘了声明变量类型；文本类型要写 `string name = get_string(...)`，不能写 `int`。

### 函数原型（function prototype）

* **定义**

    * > **定义**：函数原型是函数在实现之前的"预告片"，存在的唯一目的是解决顺序问题。

    * 函数可以写在你使用它的位置之后，但编译器读到使用处时必须已经知道它长什么样。

* **声明的三个要素**

    * 函数名、输入参数（如果有）、返回值类型（如果有）。

    * 例：`void print_column(int height);` 声明一个返回 `void`、接收一个 `int` 的函数。

    * > **易错点**：把辅助函数 `print_column` 挪到 `main` 下方会报 `buggy.c:7: 错误：使用未声明的标识符 'print_column'`——编译器读到第 7 行就中止了，因为它直到第 10 行才知道这个函数是什么。

* **头文件干的正是这件事**

    * 在调用底下的 `printf` 之前，编译器需要知道它是什么、输入参数是什么、输出是什么，而 `printf` 的原型就住在 `stdio.h` 里。

## printf 调试法

* **原理**

    * 怀疑逻辑有问题、想把程序内部摊开看清楚时，`printf` 就是得力助手。

    * 到目前为止 `printf` 都只用来显示最终产物；完全可以临时插几行，把程序内部的中间结果打出来，这对理解代码的执行过程帮助极大。

* **标准范式：在循环体里打印计数器**

    * 用 `for (int i = 0; i <= 3; i++)` 打印三层砖块，结果打了**四**块。

    * 在打印每一块砖之前把 `i` 的值也打出来：

        ```c
        for (int i = 0; i <= 3; i++)
        {
            printf("%i ", i);
            printf("#\n");
        }
        ```

    * 输出为 `0 #`、`1 #`、`2 #`、`3 #`，一眼看出循环本身完全正常，是**条件让人多走了一步**。

* **抽象之后纯 printf 就原始了**

    * 把打印一列抽象成 `print_column` 函数后结构更清晰，但要管的代码量反而变多。

    * 加调试语句、重新编译、运行、改 `printf`、再编译、再运行，屏幕上的代码一多很快就烦人。

* **纪律**

    * > **提示**：`printf` 调试法不是"作弊"，它是标准手段。核心纪律只有一条：**调试语句只是临时的，修完必须删**。

    * 搞清楚、修好之后删掉临时代码，重新编译，继续干活。

## 调试器单步追踪

### debug50 与断点

* **debug50 是什么**

    * `debug50` 是一个 CS50 命令，会启动一个行业标准的调试器。

    * 之所以叫这个名字，是因为在 VS Code 里直接启动调试器有点麻烦；只自动化了"启动"这一步，之后的所有操作都与 CS50 无关。

    * 用法是 `debug50 buggy`，`buggy` 是**命令行参数**，告诉 `debug50` 要调试哪个程序。

* **断点（breakpoint）**

    * > **定义**：断点是告诉调试器"在哪儿把程序叫停"的地方。

    * 没有断点，调试器根本不知道你想从哪一步开始看；第一次运行会提示"看起来你还没有设置任何断点"。

    * 在 VS Code 里把鼠标悬停在行号左侧会看到一个小红点，像个迷你停止标志，点一下就钉在那里。

* **断点位置的选择**

    * 断在 `main` 的第一行会立刻中断，但那一行本质上是函数名和大括号，没有任何实际作用。

    * 真正有意思的起点是下一行，代码里真可能做有用事情的地方。

* **高亮的语义**

    * 当前行被**黄色高亮**表示：程序已经在这一行中断了，但这一行还没被执行。

    * 因此屏幕上没有任何输出，连提示都还没打印——这正是预期的行为，不是故障。

* **变量面板**

    * 屏幕左侧出现一栏变量信息，调试器里可以查看内存中**任意变量的当前值**。

    * 单步进入 `print_column` 后，左上角能看到变量 `i` 的默认值，是一个完全随机的垃圾值；只要初始化那行执行一次，`i` 就会变成 0。

### 单步跳过与单步进入

* **两个按钮的分工**

    * 最左边像播放按钮的图标：继续跑，不再单步。

    * **单步跳过**（带圆点的弯箭头）：执行当前行然后往下走，一次一行。

    * **单步进入**：钻进被调用函数的内部；单步跳过的本行没有调用别的函数时不需要它。

* **单步走查记录**

    * 断点留在读入 `h` 那行，重跑后单步跳过它获取 `h`，输入 3，停在下一行，局部变量 `h` 的值如预期是 3。

    * 此时再单步跳过会**让整个 `print_column` 一次跑完**，屏幕底部直接出现四个井号，并没有真正进入函数内部。

    * 改用单步进入后，程序跳进 `print_column` 内部暂停：单步跳过初始化行，`i` 立刻变成 0，再单步跳过，出现**第一个**井号。

    * 再单步跳过两次，**第二个**井号出现，`i` 变成 1；再两次，**第三个**井号，`i` 变成 2。

    * 再单步跳过两次——**出现了第 4 个井号，但 `i` 的值是 3**。这就是 bug 的气味：3 确实 `<= 3`。

* **调试器的价值与边界**

    * 它允许你暂停程序、按自己的节奏一步步分析、钻进代码内部探查，比"编译运行后只凭表面现象猜根源"高效太多。

    * 但最终判断"为什么多打了一块"仍然得用自己脑子去分析；调试器给你的是状态，不是结论。

* **调试器界面显示什么**

    ```text
    ┌──────────────────────────────────────────────────────────────┐
    │  ▶   ⤳ 步进跳过   ⤵ 步进进入   ⤢ 继续   ⏹ 停止   ⟳ 重新启动 │  ← 调试控制条
    ├──────────────┬───────────────────────────────────────────────┤
    │  变量面板     │  buggy.c                                      │
    │              │  5  int main(void)                            │
    │  h = 32764   │  6      print_column(h);                      │
    │              │  7                                           │
    │  i = 2       │  8 >    int h = get_int("Height: ");  ← 高亮   │
    │  （垃圾值）  │  9      print_column(h);                       │
    │              │ 16 >    printf("#\n");                ← 高亮   │
    ├──────────────┴───────────────────────────────────────────────┤
    │  终端：$ ./buggy                                             │
    │  Height: 3                                                   │
    │  #  #  #  #                                                  │
    ├──────────────────────────────────────────────────────────────┤
    │  调用栈：main (buggy.c)  ← 暂停在这一帧                       │
    └──────────────────────────────────────────────────────────────┘
    ```

    * 右侧那一栏是**调用栈**：正暂停在 `main` 函数里；单步进入 `print_column` 后栈里就会多一层，表示当前正在执行哪个函数、调用的又是谁。

* **易错点**

    * > **易错点**：调试器只会高亮整行代码，它不会告诉你这一行内部执行到哪一步了。`for` 循环的四个阶段是语言定义带来的，不是调试器在提示你；不能指望看着高亮就以为"它刚做完初始化"。

### 垃圾值（garbage value）

* **定义与来源**

    * > **定义**：垃圾值是变量所在内存位置里的残留内容——那块内存之前被存过别的东西。

    * 现象：在读入那行**执行之前**，`h` 已经有个凭空出现的默认值 32764。

    * 计算机有大量内存即 RAM；`h` 即将占用的那些位很可能早就随机地处在开/关两种状态上，凑出了一个随机的位模式，恰好就是 32764。

* **边界**

    * 等这行代码一执行，那个值就会被改成真正想要的值——用户输入的那个数；垃圾值只是执行前的瞬时状态。

## for 循环的四阶段

### 执行顺序不可协商

* **四个阶段**

    ```text
            ┌──────────────┐
            ▼              │
      ① 初始化             │  只做一次：for (int i = 0;
      int i = 0            │         第一个分号之前)
            │              │
            ▼              │
      ② 条件判断  i <= 3 ? ├──── 否 ────► 退出循环
      （布尔表达式）         │
            │ 是            │
            ▼              │
      ③ 执行循环体内所有代码  │
       printf("#\n");       │
            │              │
            ▼              │
      ④ 更新  i++           │
            └──────────────┘
    ```

* **规则**

    * > **定义**：结构是 `for ( ① 初始化 ; ② 条件 ; ③ 更新 ) { 循环体 }`，永远是①→②→③。

    * 第一次一定是初始化，第二次一定是条件判断，第三步总是更新；这个顺序由语言定死，不可协商。

    * 执行完更新后会**再次**检查条件，条件为真就再执行循环体、再更新、再检查，如此往复。

    * 能不能把更新提到条件前面？不能，顺序是被语言定死的。

* **语法边界**

    * `for` 的三个位置都可以写多条语句，用逗号隔开——多个初始化、多个布尔条件、多个更新都可以。

### 循环边界的 off-by-one

* **一个字符的差别**

    * 条件 `i < 3` 打三次，`i <= 3` 打四次。

    * 第 4 次进入循环体时 `i` 是 3，`3 <= 3` 成立，井号被打出去；然后 `i++` 变成 4，`4 <= 3` 不成立，循环结束——一共四次。

* **规范写法**

    * 最规范、最常见的写法是从 0 开始计数、递增到永远不会达到你心里想的那个总数。

    * 想从 1 开始数也可以，把初始值设成 `i = 1`，然后 2、再到 3。

* **易错点**

    * > **易错点**：`<` 与 `<=` 的混淆是初学者 bug 的头号来源。

## 数组的创建与访问

### 三要素

* **创建一行需要指定的东西**

    * 你需要指定**名称、大小和类型**，就这三样。

    * 例：`string words[2];` 创建大小为 2 的字符串数组；`int scores[N];` 创建包含 N 个整数的数组。

    * 方括号在这个上下文里用于创建指定大小的数组；一旦数组创建完成，方括号还可以用来访问内存中这块数据区域。

* **访问**

    * 可以像 `s[0]`、`s[1]`、`s[2]` 那样逐个索引。

    * 同意并理解了数组可以通过方括号索引访问之后，字符串也同样可以。

### 花括号静态初始化

* **写法**

    ```c
    int n = 3;
    int scores[3] = {72, 73, 33};
    ```

* **规则**

    * 用花括号（curly braces）可以在一行内初始化数组。

    * 这种情况下甚至不需要指定数组大小——右侧写了 3 个数字，编译器就知道左侧只需分配 3 个元素。

    * 适用前提是提前就知道所有数值（而不是像用 `get_int` 那样动态获取），这时可以静态初始化数组。

    * 不需要非逐个索引地存数据。

* **与整数数组的差异**

    * 创建字符串数组只是把元素类型从整数换成字符串，所有语法完全一样，打印也还是老样子的 `printf` 加换行符。

## 字符串即字符数组

### 空字符与 NUL 约定

* **八个零的决定**

    * > **定义**：计算机里所有数据最终都由比特构成，字符（char）类型用 8 位表示；必须挑一种特定的位模式来代表它，多年前一群专家共同决定用 8 个 0 表示空字符。

    * 这个"空字符"不是随便一个概念，它是**字符串的终止符**。

    * 意味着对字符串可以像对待数组那样去探索和操作：尽管第一个变量是 `s`、第二个是 `t`，但技术上完全可以访问 `s[0]`、`s[1]`、`s[2]`、`s[3]` 以及 `t[0]`……`t[4]`。

    * 字符串长度、逐字符遍历、大小写转换全都靠这个"8 个 0"撑起来。

* **由谁补上**

    * 在 C 语言里，`get_string` 会自动在字符串末尾加上它。

    * `printf`、`strlen` 这类函数也都是靠它来标记字符串"到此为止"。

* **内存布局**

    ```text
    words[0]    h    i    g    h    \0
    words[1]    b    y              \0
    ```

    * 数组占两个内存位置，0 和 1；每个位置里装的不是数字，而是一串字符，并且都以那个 8 个 0 收尾。

    * 字符串长度说到底就是**直到遇到那个 `\0` 为止所经过的字符数**，所以索引访问的合法上界由 `\0` 界定。

* **易错点**

    * > **易错点**：`'\0'`（值为 0 的终止符）和 `'\n'`（换行符）完全不是一回事，`get_string` 在你按下回车时自动补上的那个，是前者。

### 字符串数组与两级索引

* **本质**

    * 字符串本质上一个字符数组；就讨论的目的而言，**字符串就是数组**。

    * 我其实可以把字符串放进数组里，而不是像 `s`、`t`（或"单词 1""单词 2"）那样分开处理：

        ```c
        string words[2];
        words[0] = "high";
        words[1] = "by";

        printf("%s\n", words[0]);
        printf("%s\n", words[1]);
        ```

* **两层索引**

    * 既然字符串本质就是数组，可以分两层索引：先用一组方括号索引到单词数组里的某个单词，再用另一组方括号索引到这个单词里的具体字母。

        ```c
        printf("%c%c%c", words[0][0], words[0][1], words[0][2]);
        printf("%c%c%c%c", words[1][0], words[1][1], words[1][2], words[1][3]);
        ```

    * `words[1][0]` 是第二个单词的第一个字符，`words[1][3]` 是它的最后一个字符。

* **视角的等价性**

    * 把 `words[0]` 整个当字符串打印是一回事，把它拆成一个个字符打印是另一回事；两种方式最终揭示的是同一件事。

## 字符串长度

### 一直数到空字符

* **手写实现**

    ```c
    #include <cs50.h>
    #include <stdio.h>

    int main(void)
    {
        string name = get_string("What's your name? ");

        int n = 0;
        while (name[n] != '\0')
        {
            n++;
        }

        printf("%d\n", n);
    }
    ```

* **技巧**

    * 布尔表达式反复问同一句话："这个字符是空字符吗？"不是就继续，检查下一个字符。

    * 变量 `n` 兼任了"当前检查位置"和"已经数过的字符数"两件事。

    * 走到名字末尾时遇到空字符，因为 `get_string` 会自动补上它、而空字符确实等于零，`n` 不再增加。

* **边界**

    * 什么都不输入直接回车，长度是 0，这并没有错：它其实是空字符串，即使在内存中没有任何可见字符，仍占用一个字节的空间，因为 `get_string` 仍然会在末尾放一个空字符。

    * 整个过程非常机械化：检查、检查、再检查，逐步推断出长度。

### strlen

* **库的位置**

    * 除了标准输入输出库和 CS50 库之外还有别的库，字符串库本身是 `string.h`，里面是一系列实用函数的原型说明。

    * `strlen` 早在几十年前就有人写好并封装成函数，不必为计算字符串长度重复繁琐步骤。

* **用法**

    ```c
    #include <cs50.h>
    #include <stdio.h>
    #include <string.h>

    int main(void)
    {
        string name = get_string("What's your name? ");

        printf("%d\n", strlen(name));
    }
    ```

* **结论**

    * > **结论**：如果在解决一个很可能别人已经解决过的问题，先去找找有没有现成的库函数；CS50 库、标准库、Make 工具都已经把这类小事准备好了。

## 循环条件里的效率陷阱

* **陷阱的位置**

    ```c
    for (int i = 0; i < strlen(s); i++)
    {
        printf("%c", s[i]);
    }
    ```

    * 布尔表达式每轮都会被重新求值一次，而这里的表达式是一个**函数调用**。

    * 每评估一次就等于反复问计算机"字符串 s 的长度是多少？"，它不会改变，无论怎样结果都一样。

* **优化写法**

    * 把长度先存进变量，只算一次：

        ```c
        for (int i = 0, n = strlen(s); i < n; i++)
        ```

    * 这里用了个语法技巧：想一次初始化多个变量可以都写在第一个分号之前；字符串长度不变、变量值也不变，于是可以反复使用。

* **易错点**

    * > **易错点**：一次声明两个变量要求**所有初始化用同一种数据类型**，所以最好这种情况只需要整数；否则就得把 `n` 单独声明一次。

* **边界的取舍**

    * > **提示**：现在的编译器非常智能，能识别出你在循环里反复调用 `strlen` 并自动优化掉这个问题。这类问题应该靠自己的观察发现并完全避免——省下的可能只是微秒，但一旦循环跑的是百万次、千万次，微秒、毫秒累积起来就非常显著。

## 字符编码与大小写转换

### ASCII 码上的算术

* **判断条件**

    * 字符用单引号表示；ASCII 码表里既有代表大写字母的数字，也有代表小写字母的数字。

    * 小写字母 `a` 的编码是 97，之后所有小写字母连续排列。

    * 把字符当整数、把整数当字符，从而提出一个数学问题：`s[i]` 是否落在 `'a'` 到 `'z'` 之间（含两端）。

* **转换的差值**

    * 所有大写字母和小写字母之间的差值是 **32**，而且小写字母的数值更大。

    * 把小写字母的数值减去 32，立刻就得到对应的大写字母；不是小写字母就原样输出，不做任何数学运算。

    ```c
    for (int i = 0, n = strlen(s); i < n; i++)
    {
        // if lowercase
        if (s[i] >= 'a' && s[i] <= 'z')
        {
            printf("%c", s[i] - 32);
        }
        // else if not lower case
        else
        {
            printf("%c", s[i]);
        }
    }
    ```

* **评估**

    * 这是个小技巧但确实有点繁琐；像 Microsoft Word 和 Google Docs 那样都能来回切换大小写，这么常见的功能却要写这么多代码。

### ctype.h

* **提供什么**

    * 除了字符串库之外，C 语言还提供字符类型库 `ctype.h`，里面有一大堆与字符处理相关的实用函数。

    * `islower` 传入 `s[i]`，返回真就转换；转换仍然需要减去 32，但不必自己计算——`toupper` 接收字符，让别人的函数替我完成转换。

* **更进一步**

    * 对**任何**字符直接用 `toupper` 都可以，它非常智能：只有字符确实是小写时才做转换，如果是大写字母就直接原样返回。

    * 这意味着连 `else` 分支都可以整个去掉：

        ```c
        for (int i = 0, n = strlen(s); i < n; i++)
        {
            printf("%c", toupper(s[i]));
        }
        ```

    * > **结论**：如果觉得编码变得繁琐，或者在解决一个很可能别人已经解决过的问题，那很可能确实存在现成的解决方案——无论是 CS50 库还是标准库。

* **注意**

    * CS50 库是 CS50 特有的，这也是为什么 Clang 需要知道 `-lcs50` 这个参数；而像字符串库、`ctype.h` 这类标准库则是自动生效的，不需要额外写链接参数，Make 工具已经把这些步骤全配置好了。

### 不可见字符

* **空格**

    * 空格就是字符编号 32，并没有什么特殊之处；它看起来隐形，但确实存在，和其他字符的处理方式完全一样，不需要任何特殊处理。

* **空字符**

    * 空字符同样不可见，但它很特殊——`printf`、`strlen` 这些函数会用它来标记字符串值的结束位置。

## 编译流水线

### make 不是编译器

* **make 与 clang 的分工**

    * > **定义**：编译器就是一个把一种语言翻译成另一种语言的程序，在这里就是把源代码翻译成机器码。

    * `make` 不是编译器，它是一个命令，作用是"生成"你的程序；它通过编译来生成程序，本质上是**自动执行 clang 命令**。

    * 真正在用的编译器叫 `clang`（针对 C 语言），它非常流行、免费开源，甚至可以在网上读别人写编译器的代码。

* **命令行**

    ```bash
    make hello     # 编译
    ./hello        # 运行
    ```

    ```bash
    clang hello.c
    ```

    * 直接 `clang hello.c` 结果"看起来运行成功了"，但目录里会多出一个叫 `a.out` 的程序。

    * `a.out` 是 assembler output（汇编器输出）的缩写，它和 `hello` 是同一个程序，只是用了默认名，运行 `./a.out` 也确实能跑。

    * 第一周不这么干，是因为它会平白多出一个需要记住的奇怪名字，纯属徒增烦恼。

* **链接 CS50 库**

    * 文件里有 `#include <cs50.h>` 时运行 `clang hello.c`，会得到 `链接器命令执行失败，退出代码为 1`，原因是存在对 `get_string` 的**未定义引用**。

    * 这次的错误和以前不同：以前 `get_string` "未声明"是因为少了一行 `#include`，这次那行明明就在文件里。

    * 问题在于 `clang hello.c` 默认以为它知道去哪里找 CS50 版的 `get_string`，**但它并不知道**，得显式告诉它。

    ```bash
    clang hello.c -lcs50
    ```

    * `-lcs50` 的意思就是"请链接 CS50 库"，这样编译器才能找到 `get_string` 对应的二进制代码。

* **易错点**

    * > **易错点**：养成看到 `a.out` 就知道"这是我 clang 出来的东西"的意识。它出现在目录里不是意外，是你漏写了 `-o`。

### 命令行参数、选项与 make 的自动化

* **命令行参数**

    * > **定义**：命令行参数是"你在终端里输入程序名之后的所有单词"。

    * `code hello.c` → `hello.c` 是命令行参数；`make hello` → `hello` 是传给 `make` 的命令行参数。

    * `clang hello.c -lcs50` → 传了**两个**命令行参数：`hello.c` 是要编译的代码，`-lcs50` 是"请使用 CS50 库"。

* **选项与参数**

    * `-o` 是给生成的可执行文件**指定名字**的开关，`-o hello` 里的 `hello` 正是这个选项的参数取值。

    * > **定义**：文档里写作 `-o <file>`，尖括号里的就是要替换的位置；`-o` 本身是**选项/开关（option）**，`-o name` 里的 `name` 是**参数**。

    * 清理目录：`rm a.out` 删掉默认名那个，`rm hello` 删掉自定义名的那个。

* **make 自动化了什么**

    ```text
    make hello
        └── 实际等价于 ──▶  clang -o hello hello.c -lcs50
                            │       │     │       └── 使用 CS50 库
                            │       │     └───────── 编译这段代码
                            │       └─────────────── 输出文件命名为 hello
                            └─────────────────────── 调用编译器 clang
    ```

    * 死记 `clang -o hello hello.c -lcs50` 的顺序和参数写法纯属浪费时间和精力；`make` 之所以好用，正因为它把这些全自动化了。

    * `make` 一点都不神奇，只不过帮我们一次性解决了一堆本来要手写的东西。

### 编译的四个流程与预处理

* **编译不是一步**

    * > **定义**：严格来说，"编译"指的是四个独立的流程，它们依次自动执行，功能各不相同。

* **预处理（preprocessing）做了什么**

    1. 编译器在硬盘上找到 `cs50.h` 这个文件。
    2. `cs50.h` 的内容被**逐字复制粘贴**进代码里。
    3. 于是代码中出现了 `get_string` 的函数原型：括号里的 `"What's your name? "` 是**输入参数**，函数名前面那部分是**返回值**。
    4. 同样地，`stdio.h` 里的 `printf` 函数原型也被复制粘贴进来。

    ```text
    预处理之前（你写的）              预处理之后（编译器看到的）
    ────────────────────────         ──────────────────────────────
    #include <cs50.h>          ┐
    #include <stdio.h>         │
                              ├──▶   string get_string(string prompt);
    int main(void)                    int printf(const char *format, ...);
    {                                int main(void)
        string name = get_string(     {
            "What's your name? ");        string name = get_string(
        printf("hello, %s\n", name);          "What's your name? ");
    }                                   printf("hello, %s\n", name);
                                    }
                              ┘
    ```

* **意义**

    * 一切都是为了让你不必自己去找文件、复制粘贴、或者手打函数原型。

    * > **结论**：预处理之后，文件顶部已经装满了所有 `#include` 指令所指向的真实内容，此时编译器才算真正"认识"了 `get_string` 和 `printf`。

## 命令行参数与 main

### main 的两种签名

* **main 为什么特殊**

    * > **定义**：在 C 语言中，`main` 是唯一一个在你编译并运行代码后会被**自动调用**的函数。

    * 括号里的 `void` 表示 `main` 不接受任何参数——不接收命令行参数。

    * 并非所有编程语言都标准化了这个函数名，但 C、C++、Java 以及其他一些语言确实这样做。

* **两种形式**

    | 签名 | 含义 |
    | --- | --- |
    | `int main(void)` | 不接受任何参数，最标准、最简单的形式 |
    | `int main(int argc, string argv[])` | 接受两个参数：第一个是整数，第二个是字符串数组 |

* **规则的来源**

    * 查阅 C 语言的官方文档会发现 `main` 有这两种定义方式；编译器和操作系统会确保当你提供命令行参数时，`argc` 和 `argv` 自动被赋予相应的值。

    * 不能随意加参数——不能放 3 个，也不能放 4 个；可以修改这些变量的**名字**，但它们的**类型**是固定的。

    * > **易错点**：用 `string argv[]` 时一定要保留 `#include <cs50.h>`，字符串类型 `string` 正是在 CS50 库中定义的。

### argc 与 argv

* **两个参数的含义**

    * 按惯例这两个输入参数通常叫 `argc` 和 `argv`：`argc` 是参数个数，`argv` 是参数向量，也就是实际输入的字符串数组。

* **argv[0] 的保留位置**

    * `argv[0]` 会自动包含程序自身的名称：只跑 `./greet` 不加其他内容时，打印出来的是"hello, ./greet"。

    * 程序自引用时很有用：比如显示"感谢运行本程序"，或展示一段使用说明而说明里需要包含程序名——无论文件实际叫什么名字都可以直接用 `argv[0]`。

    ```text
    命令行：   ./greet   David
                ↑         ↑
                argv[0]   argv[1]   argc = 2
    ```

    * 位置 0 永远留给程序自己，从位置 1 开始才是用户输入的单词；数一数总共有几个，就得到 `argc`。

* **用 argc 兜底**

    ```c
    #include <cs50.h>
    #include <stdio.h>

    int main(int argc, string argv[])
    {
        if (argc == 2)
        {
            printf("hello, %s\n", argv[1]);
        }
        else
        {
            printf("hello, world\n");
        }
    }
    ```

    * `./greet David` 完全按预期执行；忘了输入名字只跑 `./greet` 输出 "hello, world"。

    * 输入 `David Malan` 也会被忽略，因为此时参数数量不再是 2 了，变成了 3 个。

    * 旧写法只问名字时，运行命令是 `greet` 后面没有任何单词；新写法把名字直接写在命令行上，省去提示输入这一步。

* **NULL 与 NUL 不是一回事**

    * 只跑 `./greet` 又没有 `argc` 保护时，会看到"hello, null"。

    * 这里的 `null` 是 `NULL`，空指针，和前面说的 NUL（空字符）**不是一回事**；`printf` 察觉到了异常——那里本来就没有任何单词。

* **caesar 式玩法**

    * 命令行参数无处不在：既接受想让它说出的文字，也接受你希望它呈现的外观。

    ```bash
    caesar moo          # 输出一头说着 "moo" 的小奶牛
    caesar -f duck       # 换成一只说着 "quack" 的小鸭子
    caesar dragon -r     # 再换一只张牙舞爪的龙
    ```

    * 实现方式就是通过 `argc` 和 `argv` 拿到参数值，然后判断：如果第一个参数是 `dragon` 就打印龙的图形，否则如果是 `duck` 就打印另一个图形。

## 退出状态码

* **定义**

    * > **定义**：`main` 返回的值叫**退出状态码（exit status）**，是一个表示程序成功还是失败的数值状态。

    * 本质上类似 404 这种错误代码：对普通人毫无意义，除非去搜或查文档；对写这段代码的工程师意义重大，因为他们知道它对应某个特定错误。

    * 在 `main` 里可以返回 0、1、2 或者其他数字；按惯例一切顺利时返回 0。

    * 于是你就有上百种可能的错误情况可以表示：1 表示一种错误，2 表示另一种，3 表示又一种——只要有张表或备忘单记录，程序员就能知道每个码对应什么。

* **实现**

    ```c
    #include <cs50.h>
    #include <stdio.h>

    int main(int argc, string argv[])
    {
        if (argc != 2)
        {
            printf("Missing command-line argument\n");
            return 1;
        }
        else
        {
            printf("hello, %s\n", argv[1]);
            return 0;
        }
    }
    ```

* **查看方式**

    ```bash
    ./status David
    echo $?
    ```

    * 跑一次带名字的，`echo $?` 显示 0；再跑一次不带名字的，输出"缺少命令行参数"，`echo $?` 显示 1。

* **结论**

    * > **结论**：0 表示成功，任何其他值表示出错。`check50` 判断代码写对了没有，其中一种方式就是检查这个半隐藏的状态码；它也不算秘密，只是对普通用户没什么启发意义。

## 凯撒密码

### 明文、密文与密钥

* **三个角色**

    * **明文**是人类可读的英文或其他语言，**密文**是加密后的样子。

    * 但不能只把明文丢进算法就得到密文，因为加密通常需要一个**密钥**。

* **轮转一格的例子**

    * 约定规则：每个 A 改成 B，每个 B 改成 C，每个 C 改成 D，Z 绕回 A。秘密就是数字 1。

    * 明文 "HI"、密钥 1，密文就是 "IJ"。

    * 接收方看到 IJ 无法直接知道内容，他会使用**相同的密钥但做减法操作**：B 变回 A，C 变回 B，A 变回 Z，本质是把密钥从正 1 取反。

    * 解密只需把加密过程反过来：把密文里的所有字母往相反方向旋转一位，就能读出最后一行字。

* **标点与强度**

    * 这种做法并没有处理标点符号，字母部分被加密了而已。

    * 攻击者只需要把所有可能的密钥都试一遍——密钥 1、密钥 2、密钥 3……一直到 25，总有一个会成功，而且他一眼就能看出猜中了。

    * 历史上这种做法被称为**凯撒密码**；据说早期凯撒与将军们通信时就是这么干的。

### ROT 13 与无效轮转

* **ROT 13**

    * 密钥 13 在计算机领域有特殊含义——**ROT 13**，一种被使用了很多年的算法。

    * 常见用途是避免剧透，比如让 Reddit 之类的网站把内容先转成乱码。

    * 明文 "HI" 加密钥 13 不会得到 IJ，而是得到 UV，因为 U 和 V 分别距离 H 和 I 13 个位置；点一下按钮或写几行代码就能还原。

* **ROT 26 是无效的**

    * 有人会提议用 ROT 26 稍微安全一点——这不对，因为结果完全一样：A 变成 A，B 变成 B，它整整绕了一圈，什么都没加密。

* **用 C 实现它**

    * 实现凯撒密码用 C 语言或其他任何语言都不难，谁都可以暴力破解它。
