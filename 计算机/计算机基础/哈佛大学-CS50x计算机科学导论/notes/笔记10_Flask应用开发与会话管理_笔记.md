# Flask Web 应用开发与会话管理

## 路由与请求参数

* **路由（route）**
    * > **定义**：域名之后的那段 URL 不指向磁盘上的文件，而是作为通用输入传给服务器，由服务器决定生成什么输出。
    * 更早的 HTTP 服务器只是把当前文件夹及其子文件夹中的文件原样端出去，访问 `example.com` 看到的是目录索引。
    * 在 Google 搜索 "cats" 时实际发出的请求是 `/search?q=cats`，`search` 是运行在服务器上的一个程序名称，这个程序的真名就叫路由。
    * `something.com/` 这种首页应该显示实际的网站内容，而不是服务器上所有文件的列表。
    * 处理器函数名可以任意取；按惯例与路由同名（`greet`）只是减少需要做的决定。

* **查询字符串（GET 字符串，query string）**
    * > **定义**：路由后面加问号写上的键值对，每一对 `键=值` 就是一个参数，多个参数用 `&` 分隔。
    * 问号后的值是查询参数，即来自网页表单的输入。
    * URL 通过 `?键=值` 把输入一路传递到服务器端，而不是停在客户端。

* **框架（framework）与微框架（micro framework）**
    * > **定义**：由他人编写、用来帮我们更轻松实现网络应用的代码库，同时也是一套约定俗成的规则——必须遵循这些规则才能以推荐的方式使用它。
    * 很像 Bootstrap：既包含库本身，也包含一套使用规范。
    * 业界做法是不重复造轮子，不自己写网络服务器，而用现成的通用网络服务器（也叫应用服务器）。
    * 用 C 语言这类底层语言处理"为网络编写代码"这样高层级的事情会是一场噩梦；即便用 Python 从头实现，也要写大量代码去解析数据包、弄清服务器接收了哪些输入。
    * > **结论**：一个框架可能使用多个库。Flask 负责路由、请求、响应这些 HTTP 层的事情，模板这一块直接交给 Jinja。

* **Flask 应用骨架**
    * `from flask import Flask`：包名 `flask` 全小写，要调用的类名 `Flask` 首字母大写，大小写有严格要求。
    * `app = Flask(__name__)`：创建一个名为 `app` 的变量，把当前文件转换成一个 Flask 应用；`__name__` 指的是当前文件的名称。
    * `@app.route("/")` 是 Python 装饰器，本质上会影响紧随其后函数的行为，把该函数与这个路由关联起来。
    * 约定要求当前目录至少有一个默认名为 `app.py` 的文件，`flask run` 会在当前目录查找代码并在某个 TCP 端口上启动。
    * Flask 默认使用 **5000** 端口，而此前那个只提供静态内容的 HTTP 服务器默认用的是 8080。

* **requirements.txt**
    * 按惯例创建的文本文件，每行只列出一个想让这个 Web 应用包含的库的名称。
    * 没有这个文件也能跑，装单个库用 `pip install flask`。
    * 统一管理时在里面列出库名，再跑 `pip install -r requirements.txt` 把文件里列出的所有库一次装齐。

* **返回值与页面源代码**
    * 返回纯字符串时，浏览器实际只收到那几个字，页面源代码里没有任何 HTML，只是浏览器替你补全了最简网页。
    * 返回 `'<!DOCTYPE html><html lang="en">...</html>'` 这样的 HTML 字符串，浏览器收到的才是完整 HTML。
    * 给 `html` 标签加 `lang` 属性更规范。
    * 硬编码整段 HTML 塞进 Python 字符串很笨拙，应当把它抽出去单独管理。

### request.args

* **request.args**
    * > **定义**：Flask 提供的特殊全局变量，其中 `args` 指向这次 HTTP 请求传入的参数。
    * 取值写法 `request.args.get("name")`，键不存在时返回 `None`。
    * 加上默认值后，`name = request.args.get("name", "world")` 一行即可把原来 4 行"判存在再取值"的逻辑精简完，功能完全不变。
    * `.get` 与 HTTP 请求方法无关，字面意思就是"获取以下内容"：先写参数名，参数不存在时再给一个默认值。
    * 完全不需要自己写代码解析 URL 结构——不用拆问号、等号或中间的 `&`；这类所有 Web 应用都要处理的通用底层逻辑由框架代劳。

* **缺参数导致的 HTTP 400**
    * > **定义**：Bad Request，用户操作有误，没有传入必要的参数、缺少预期的参数。
    * 只访问根路径、完全去掉 name 参数就会触发。
    * 修法一：`if "name" in request.args` 先判键存在，存在则取值，否则赋默认值 `"world"`。
    * 只写 `?name=`（指定参数名但不给值）时，键依然存在，只是值为空，条件判断结果不变，页面显示 "Hello,"。
    * > **结论**：页面之所以成为 Web 应用而不只是静态页面，关键是引入了基于布尔表达式的条件逻辑。

* **变量名约定**
    * 传入模板的命名参数，左边是要在模板中使用的占位符名称，右边是要赋予它的实际值，两个同名并不奇怪。
    * 写 `name=name` 而不是 `placeholder1`、`placeholder2` 这类通用标签，逻辑反而更清晰。
    * > **易错点**：HTML 里的 `name` 属性和 Python 里的变量名都叫 name，但属于完全不同的概念，别混淆。

## 模板与 Jinja

* **render_template**
    * > **定义**：Flask 自带的函数，作用是渲染一个 HTML 模板。
    * 写成 `render_template("index.html")`，把逻辑（Python 代码）和 HTML 稍微分离开来。
    * 按 Flask 文档，自建 HTML 文件要放在名为 `templates` 的目录下（注意大小写，全部小写）。
    * 可以像 Python 接收带名参数那样额外传入命名参数：`render_template("index.html", name=...)`。

* **Jinja**
    * > **定义**：Flask 内置的模板库，知道如何在成对的花括号中插入变量。
    * 世界上存在许多模板库，Jinja 相当简单，这正是 Flask 选择它的原因。
    * Flask 开发者认为重新发明一种模板语言不值得投入时间，于是直接采用别人多年前编写的库。
    * 模板本质上是我希望用户看到的网页的**蓝图**，实际页面通过动态插入值基于这份蓝图生成，占位符放在花括号里。
    * 也正因如此，HTML 从这时起都放进 `templates` 文件夹，它们不再是静态 HTML，而是浏览器最终输出的实际 HTML 的蓝图。

* **插值语法**
    * `{{ placeholder }}` 告诉 Flask 要"插值"这个变量，用它的值替换占位符。
    * 不加花括号直接写，页面上就会显示 "placeholder" 这个字面内容。
    * 这与 Python 的 f 字符串、C 语言 `printf` 的 `%s` 属于同一类"填值"语法。
    * 填入的值是从**服务器端**传来的：查看页面源代码能看到服务器确实发出了这段文本，而不是客户端渲染的结果。

* **继承与填充（extends 与 block）**
    * > **定义**：`layout.html` 把各模板共有的样板 HTML 抽出来，`{% block body %}{% endblock %}` 在 body 位置挖一个坑。
    * 命名成 layout.html 是因为 Flask 官方文档就是这么建议的。
    * 布局模板的 head 里放统一的 `<title>hello</title>`，作为所有页面的统一标题。
    * 子模板顶部写 `{% extends "layout.html" %}` 表示"我想让这个模板使用布局的蓝图"，`{% block body %}` 到 `{% endblock %}` 之间是填进坑里的内容。
    * `{% endblock %}` 只是闭合标记；block 名字是自定义的，本可叫 foo、bar、baz，因为对应 body 就按惯例这么写。
    * 占位符从此不再只为一个变量预留位置，而是可以放入**一整段代码**。
    * > **结论**：真正核心的内容都被关在那个 body 块内部。

* **Jinja 标签的符号选择**
    * Jinja2 用**花括号加百分号**开启标签 `{% %}`，再用对应符号闭合。
    * > **提示**：HTML 发明者选了简洁的尖括号，Jinja 选花括号加百分号，是因为这些符号很可能不是人们写代码时正常会输入的字符——选一套不太可能与用户想用的语法冲突的符号，是模板引擎的常规做法。
    * > **易错点**：模板里为了让结构在编辑器里一眼可读而加的缩进，浏览器完全不在意，页面源代码里拿到的就是未经美化的那一份。

## 表单提交与请求方法

### 表单元素

* **action**
    * > **定义**：指定表单提交到哪个 URL，不写 action 就默认提交到它当前所在的页面地址。
    * 写成 `action="/greet"` 就默认指向自己的服务器，而不是别的站点。
    * 表单页改用 POST 后目标路由消失，此时可以把 action 改成根路径 `/`，或者干脆完全省略。

* **其他属性**
    * `name` 决定这个值提交到服务器时的键名，HTML 里它是属性，和 Python 变量名是两回事。
    * `type="text"` 是文本类型，文本框还有搜索框、邮箱等不同类型。
    * `placeholder="Enter your name"` 提示用户该填什么。
    * 关掉 `autocomplete` 可以避免几个共用一台电脑的人看到之前输入过的内容。
    * 加 `autofocus` 让光标默认就在输入框里闪烁。
    * `type="submit"` 的按钮点下去才真正提交，按钮文字就是用户点的东西（如 greet、注册）。
    * `value` 是提交给服务器的值，可以和用户看到的文字不同。

* **HTML 忽略多余空白**
    * 一段文本后面跟一大堆空白字符不会让页面显得杂乱。
    * > **定义**：HTML 会忽略多余的空白字符，任何超过一个的空格都会被规范化、压缩成单个空格。
    * > **提示**：想真正分成不同段落必须加 `<p>` 标签。此前写过三段关于鸭子的文本，本意是要明确分段，却因为全是空白而没能分开显示。

### GET 与 POST

* **GET 的隐私代价**
    * > **结论**：GET 请求的查询字符串包含了渲染页面所需的所有信息，但这确实不利于隐私保护。
    * 所有参数都会出现在地址栏里，打开别人浏览器的人就能看到他访问过哪些 URL、问候了谁的名字。
    * 用户名密码、信用卡号、不想被知道的搜索词都会同样暴露。
    * GET 适合低风险操作（如谷歌搜索框），也适合把链接放进 `<a href="...">` 锚点标签做**深层链接**，直接跳到一个永远显示同样内容的页面。

* **POST**
    * > **定义**：另一种 HTTP 动词，把信息更深地藏在"信封内部"而不是直接写在 URL 地址栏里，服务器依然能获取这些数据。
    * 改法只是把表单的 `method` 从 `get` 改成 `post`。
    * 提交后 URL 会变成 `/greet` 但看不到任何键值对参数，而问候语照样能显示，因为服务器知道要去"信封"里看。
    * 选 POST 也出于隐私考虑，参数不会留在浏览器历史记录里，室友翻历史看不到。

* **request.args 与 request.form**

    | 要取的东西 | 该用哪个 |
    | :--- | :--- |
    | GET 请求 URL 查询字符串里的参数（`?name=David`） | `request.args` |
    | POST 请求提交上来的表单数据 | `request.form` |

    * 官方文档明确写着：通过 POST 而非 GET 获取 HTTP 参数时，需要把 `request.args` 改为 `request.form`。
    * 这不太直观——两种参数都可能来自表单，所以这种命名容易让人困惑。
    * 用开发者工具的网络面板能直接看见"信封"：GET 那条的参数写在 URL 里，POST 那条的"载荷"标签页里才有 `name=David`。
    * 即使网站用的是 POST，登录时你仍能在自己的浏览器里看到通过键盘提交给服务器的所有数据。

* **HTTP 405**
    * > **定义**：Method Not Allowed，方法不允许。
    * 原因：Flask 定义路由时默认假定你希望使用 GET，这个参数默认就是 `methods=['GET']`。
    * 首页这类默认页面用 GET 合理（直接访问根路径），但表单目标路由应当支持 POST。
    * 修法：给路由传入一个用逗号分隔的方法列表，方括号是 Python 表示列表的方式，相当于 C 语言的数组。

### HTTP 状态码

| 状态码 | 含义 | 触发场景 |
| :--- | :--- | :--- |
| 200 | OK | 请求成功，如 POST 提交被正常处理 |
| 400 | Bad Request | 缺少必要参数（如完全不带 name 参数） |
| 404 | Not Found | 表单指向的路径没有定义任何路由 |
| 405 | Method Not Allowed | 路由默认只支持 GET，却收到 POST |
| 500 | Internal Server Error | 服务器端出错，模板不存在、漏写引号等 |

* **HTTP 500**
    * > **定义**：Internal Server Error，问题出在你自己这边。
    * 浏览器只给一条通用到极致的黑白错误页，从上面看不出具体原因。
    * 真正的原因在运行 Flask 的那个终端窗口里，常见形态是 `Jinja2.TemplateNotFound: greet`，因为忘了创建模板文件。
    * > **易错点**：⚠️ 看到 500 就去看终端——这是有意为之的设计，从网络安全角度看向用户展示服务器上发生的所有错误信息通常不利，因为这可能暗示攻击者可以利用这些错误及其隐含的线索入侵系统。
    * > **易错点**：Flask 会把出问题的那一行用下划线标出来，替你做了行号定位。先看终端，再猜代码。

* **HTTP 404**
    * > **定义**：Not Found，未找到。
    * 常见原因是表单已经指向 `/register`，但 app.py 里没有为这个路径定义任何路由。
    * 理论上存在无数条未定义的路由路径，`/register` 目前恰好是其中之一。

* **隐蔽的模板错误**
    * > **易错点**：`{% block %} body` 这种把两个词位置写反的写法是隐蔽错误，正确写法是 `{% block body %}`。

## 一条路由兼管表单与结果

* **方法声明加分支**
    * > **定义**：路由用 `methods=["GET", "POST"]` 声明支持哪些方法，函数内部判断 `request.method` 决定渲染哪个模板。
    * POST 分支渲染结果页，else 分支渲染表单页。
    * else 里不必写 `elif request.method == "GET"`：既然只声明支持这两种，落到 else 就一定是 GET，比再比较一次字符串更干净。
    * 这个设计能成立的原因是两个分支最终都只需要一个名字——`request.form.get("name", "world")` 里的 `"world"` 就是"没提交就用它"的默认值。
    * 服务器去判断用户是不是点了按钮、通过 POST 到达这里；否则就是直接输网址、以 GET 方式访问的。

* **合并的动机**
    * 一个页面一个表单就要两个路由，页面上有两个表单就需要 4 个路由，三个表单就需要 6 个路由，几乎是理想情况的两倍。
    * 合并后让所有与该功能相关的操作集中在一处处理。

* **合并的代价评估**
    * > **结论**：每个功能模块仍然有自己的模板，模板之间只存在细微差异；只是在 app.py 里根据应用的真实逻辑决定这一趟该渲染哪一个，没有为了合并而牺牲清晰度。

## 表单控件与数据生成

### 文本框之外的控件

* **选择菜单（select 与 option）**
    * > **定义**：网页上的下拉菜单，在网页里叫做选择菜单。
    * 比让用户手动敲运动项目名更好：手动输入容易出现拼写错误和大小写不一致，下拉菜单天然就把可选项的范围规范住了。
    * `<option>` 默认把开始标签和结束标签之间的文字当作它的值，更严谨的做法是明确写出每个选项的 `value`。
    * `<option>` 还支持 `selected` 属性，设置了 `selected` 就意味着这个选项是默认选中的。
    * 在顶部添加一个值为空、标签为「运动项目」的空选项并让它默认选中，避免默认选中第一项导致用户误操作。
    * 这还有副作用好处：后端特意把初始值设成空，理论上能据此判断用户是真的选了项目，还是直接点提交忽略了下拉菜单。

* **单选按钮（radio）**
    * > **定义**：`type="radio"` 的输入框，显示成互斥的小圆圈，点一个另一个就自动取消。
    * 用 `{% for sport in sports %}` 为每个项目输出一个，配 `<label>` 显示旁边的文字。
    * 浏览器正是靠这些输入框**相同的 name 属性**判断这些选项是互斥的；查看页面源码能看到它们都是动态生成的，`type` 都是 `radio`，`name` 完全相同。
    * 这其实就是另一种类型的输入框——文本框也有好几种不同类型，只不过这个显示成单选按钮。

* **复选框（checkbox）**
    * 把 `radio` 改成 `checkbox`，选项之间不再互斥，可以同时勾选多个项目，一次性报名多个项目。
    * 让用户填一次姓名就能报一两次不同项目，比反复填写强。

* **控件换了，取数不变**
    * 无论用户在浏览器里选择哪种控件类型，表单都能正常提交。
    * 服务器从 request 对象拿到的数据格式完全一致，依然能通过 name 或 sport 字段拿到数据。

### 让数据自己长出控件

* **全局列表 SPORTS**
    * 在文件开头建一个全局变量 `SPORTS = ["basketball", "soccer", "ultimate frisbee"]`，这样在任何地方都能访问。
    * 命名成全大写是为了表明它是全局变量和常量；Python 不像 C 语言有真正的常量概念，但这是约定俗成——看到全大写变量不要随意修改。
    * 替代方案是用一长串 `and request.form.get('sport') != ...` 逐个比较：既在服务器端硬编码了所有项目，下拉菜单本身又从 index.html 生成，HTML 里还得重复列出所有项目，重复代码显然不够理想。
    * 收束后只剩一个问题：**如果运动项目不在支持的列表中，就直接返回失败页面**。

* **模板里的 for（endfor）**
    * 渲染 index 模板时直接传入名为 `sports` 的变量，值设为那个全局列表。
    * 模板里 `{% for sport in sports %}` 动态生成任意数量的 `<option value="{{ sport }}">{{ sport }}</option>`，然后用 `{% endfor %}` 结束循环。
    * `value` 等于当前循环变量 `sport`——这有点冗余，因为 HTML 语法本就是这样：一个是用户看到的内容，一个是提交给服务器的值，以防你希望它跟显示内容不同。
    * > **结论**：无论有 3 项运动还是 30 项运动，选项都由模板动态生成，只在 app.py 里更新那个全局列表就能集中管理。
    * 页面源代码里会看到多余空格，因为循环每次迭代都会添加一些；这没关系。

* **结构固定，数据动态**
    * > **结论**：表格结构完全由 HTML 负责，表格里有多少行完全由 Python 负责。结构是固定的，数据是动态的，两者互不干扰。
    * 这正是模板引擎的核心价值。

### 移动端适配

* **viewport**
    * 在 head 里加 `<meta name="viewport" content="width=device-width, initial-scale=1.0">`，这一行基本上可以直接复制粘贴到自己模板里。
    * 它帮助页面内容自适应调整，对移动设备更友好，让浏览器真正匹配手机、笔记本、台式机之间的宽度差别。
    * > **注意**：缺了它，等用手机访问自己网站时，所有内容看起来都会相当混乱——字体过小、布局错乱。

## 输入校验与错误反馈

* **永远不要相信用户输入**
    * > **结论**：用户会**无意中**、**错误地**、还是**恶意地**提交你未曾预料的数据。
    * HTML 代码完全是在客户端执行的，所以只写"检查是否提供了值"的话，当前代码会接受**任何**用户输入，即使它不在下拉菜单里。
    * 只要懂一点 HTML，在开发者工具里右键选中元素选择"编辑为 HTML"，就能给自己添加一个自定义选项，比如 `value="volleyball"`。
    * 于是就可以注册一个我们根本没开设的项目，看起来一切正常。
    * > **定义**：防御手段是**服务器端验证**——不能仅仅盲目检查用户是否提供了值，实际需要验证它是否属于那些预设的项目之一。

* **把失败说得具体**
    * 笼统的「注册失败」体验糟糕，用户无法有针对性地修正。
    * 建一个 `error.html` 模板，里面放 `<h1>错误</h1>` 和 `<p>{{ message }}</p>`；`<p>` 里用花括号是因为确信 Flask 会在指定位置动态输出这条消息。
    * app.py 本身比模板知道得多在哪出错，所以逐项判断并渲染不同的 message：缺姓名、缺项目、非法项目。
    * `if not name` 一次性覆盖姓名为空或 None 两种情况。
    * 走到最后一步的用户已被确认通过了姓名检查，没通过的原因就只剩一个：**不是有效的运动项目**。

* **HTML 报错也能定位**
    * 漏写一个闭合引号就会触发内部服务器错误，Flask 在终端里用下划线标出那一行。
    * 模板里 `{% block %} body` 写反会报"遇到了未知标签 body"。

## 静态资源

* **static 目录**
    * > **定义**：任何属于静态资源的内容——页面上要显示的图片、要嵌入的 CSS 文件、JavaScript 文件——都应该放在一个叫 `static` 的文件夹里。
    * 这里的"静态"指内容不会改变的资源，写好之后不会像应用那样动态生成。
    * 即使把 `cat.jpeg` 和 `app.py` 放在同一个目录里、刷新后图片也不显示，因为这是使用框架的一个副作用，也是组织结构上的约定。
    * 解决办法是 `mv cat.jpeg static`，再把 HTML 里的源地址明确写成 `/static/cat.jpeg`。
    * <img> 标签的 `alt` 替代文本得加上，这样屏幕阅读器的用户、或者网速很慢的人至少知道这里本来该是什么。

* **两条路径规则不对称**
    * > **易错点**：`render_template` 会自动去 `templates` 里找模板文件，你只需提供文件名，不该也没必要写 `templates/` 这样的前缀。
    * > **易错点**：反过来，HTML 模板里引用静态资源时，`/static` 这一段路径必须由你自己写上去。

## 数据持久化

### 先放内存

* **全局字典 registrants**
    * 建一个全局变量 `registrants = {}`，它是 Python 的 `dict` 类型；也可以显式写成 `dict()`，但一对花括号更符合 Python 风格。
    * 字典存的是键值对：需要存每位学生的两项信息，让**姓名当键、体育项目当值**。
    * 一行 `registrants[name] = sport` 就把键值对存好，数据已经存在计算机的**内存**中。

* **用循环渲染名单**
    * 新增 `/registrants` 路由，把全局字典作为占位符传给 `registrants.html`。
    * `<table>` 里用 `<thead>` 定义表头（只含一行 `<tr>`，每个单元格用 `<th>`），表头之后用 `<tbody>` 定义主体。
    * 在 tbody 里 `{% for name in registrants %}` 每次迭代输出一个 `<tr>`，里面两个 `<td>`：第一个放当前循环变量（姓名），第二个用 `registrants[name]` 再查一次取出项目。
    * > **注意**：所有表格行都是在**服务器端**动态生成好的，在以当前形式发送到浏览器之前就已经完成了。
    * 这套机制和 Gmail、Outlook 收件箱背后的做法一致：在内存里存数据，再用模板引擎逐行输出表格行。

* **redirect**
    * Flask 自带 `redirect` 函数，注册成功后直接返回一个重定向结果，把用户引导到 `/registrants`，而不是只显示成功页面。
    * 更简单的替代方案是在成功页里放 `<a href="/registrants">` 这样的锚点，但直接告诉人们去访问某个路径并不是好主意。
    * > **易错点**：任何时候进行重定向，都应当使用 GET 方法而不是 POST；所以提交后写 `return redirect(...)`，稍后再次访问该路由时用的就是 GET，而 GET 分支才是真正查数据、渲染页面的那一段。

* **内存会蒸发**
    * 服务器一旦离线——需要更新、崩溃，或者你按下 `Ctrl+C` 回到终端——服务器重启意味着那个全局变量也随之消失，就好比内存被释放。
    * Flask 很智能，代码一改就自动重新加载程序，于是得到一个全新的空字典。
    * > **结论**：应该使用真正的数据库，而不是把注册者信息存在服务器内存的变量里。

### 接上 SQL

* **连接数据库**
    * `from cs50 import SQL` 后 `db = SQL("sqlite:///froshims.db")`，创建一个名为 froshims.db 的 SQLite 数据库。
    * CS50 库能让 SQL 和 Python 的结合轻松许多，当然也可以用第三方库。
    * 表结构是一张 `registrants` 表，包含 `id`、`name`、`sport` 三列，主键是整数类型的 `id`。

* **NOT NULL 约束**
    * > **结论**：name 和 sport 这两列不仅要是文本类型，而且标了 **NOT NULL**——因为需要用户提供这两项，不允许插入空值。

* **占位符**
    * 插入语句写成 `db.execute("INSERT INTO registrants (name, sport) VALUES (?, ?)", name, sport)`。
    * 问号是占位符，库会自动对用户输入做安全处理。
    * > **易错点**：⚠️ 这里绝对不能用 f-string，也不能直接拼接字符串，不能盲目地把用户输入直接插进去——由库过滤掉单引号、分号等可能引发问题的特殊字符，才是安全处理的方式。

* **db.execute 返回什么**
    * > **提示**：`db.execute` 返回的是**字典对象列表**，不是单个字典；只有一位注册者时看到的就是他那一条记录的字典。
    * 读取全部用 `registrants = db.execute("SELECT * FROM registrants")`，因此不再用全大写的全局变量，改用小写的 `registrants`。
    * 注册路由负责把用户插入数据库，注册者列表路由负责从数据库中选出用户，其余部分代码保持不变。

* **字典列表带来的模板改写**
    * 传入的不再是单个字典而是一个字典列表，循环变量变成**整个字典**。
    * 模板里改用 `{{ registrant["name"] }}` 和 `{{ registrant["sport"] }}` 的字典索引取值。
    * 这和之前那个版本有本质区别：之前循环变量是**键**（姓名），值要用 `registrants[name]` 再查一次。

* **验证持久化**
    * 切到第一个终端窗口按 `Ctrl+C` 停止 Flask 服务器再重新启动，注册者页面刷新后数据仍在。
    * 服务器在内存里重新运行，但数据库仍然是持久化的。

### 按 ID 取消注册

* **主键**
    * > **定义**：主键以最小的数据量唯一标识每个用户。
    * 如果另一个 Kelly 也注册了 Frosh IMs，就能避免误删错误的 Kelly，或者同时删掉两个 Kelly——只需要删 **ID 为 2** 的那个 Kelly。
    * ID 在 SQL 表中能唯一标识用户，这是它比姓名更可靠的原因。

* **把 ID 藏进表单**
    * 最省事的办法是加一个输入框，但那等于要求用户自己动手输入他想删掉的人的 ID，出现一堆一模一样的表单且完全依赖用户自觉。
    * 正确做法是把输入框类型改成 `hidden`，值直接填成当前这次循环迭代拿到的那个注册者的 ID。
    * 于是文本框不见了，按钮还在，信息一条不少。
    * > **结论**：这个表单已经包含了足够的信息——即使用户除了点击按钮之外什么都不填，也能告诉服务器该删谁。
    * 表单的 action 指向 `/deregister`，方法用 POST。

* **DELETE 语句**
    * 先用 `request.form.get("id")` 把 ID 从表单里取出来。
    * 做个简单的合理性检查，ID 存在且不为空才动手，这样随便发一个无效参数过来也删不掉任何人。
    * 实际删除是 `db.execute("DELETE FROM registrants WHERE ID = ?", id)`，问号是占位符，实际 ID 单独作为参数传进去，交给数据库去执行。
    * 不管执行没执行，最后都重定向回注册者页面，让你直接看到结果。

* **为什么删数据不能用 GET**
    * > **定义**：GET 请求在理论上只需要输入一个 URL 或点击一个超链接就能访问到那个资源或路由。
    * 设想用 GET 实现删除：攻击者构造一个像 `/registrants?id=4` 这样的 URL 通过邮件发给项目主管，主管没多想顺手点一下，Doug 就被意外注销了。
    * 这其实也暗示着**网络钓鱼攻击**可能利用类似手段。
    * 规则很清晰：凡是那些可以直接点击、可以手动输入的简单网址，都不应该导致服务器端的数据被修改。
    * POST 安全得多——不可能仅靠点一个链接就触发 POST，通常都得点一个按钮；主管会先收到邮件，点开链接后页面上明确摆着"取消注册"按钮，不点就没事。
    * > **结论**：只要涉及任何个人身份信息，或者任何可能造成破坏的操作——比如实际修改数据库里的数据——通常都更推荐使用 POST 请求。

## MVC 范式

* **文件结构**

```text
froshims/
├── app.py             控制器：所有逻辑、变量、函数、条件、循环
├── requirements.txt   依赖库清单
├── registrants.db     模型：持久化数据
├── static/            静态资源：图片、CSS、JavaScript
│   └── cat.jpeg
└── templates/         视图：用户看得见、并且与之交互的一切
    ├── index.html
    └── registrants.html
```

* **视图（view）**
    * > **定义**：用户持续交互的对象通常被称为视图，指的就是用户界面本身。
    * 由 `templates` 文件夹里的模板文件承载。

* **控制器（controller）**
    * > **定义**：从技术上讲 app.py 就是业界所说的控制器逻辑或业务逻辑，负责处理所有的逻辑、变量、函数、条件判断、循环，并生成一个或多个视图。
    * 它由特定的视图生成——视图不是自己长出来的，是控制器渲染出来的。

* **模型（model）**
    * > **定义**：模型指的就是持久化数据，也就是存储与应用程序相关数据的地方。
    * 最初的模型只是一个非常简单的内存字典，后来逐渐演变成 `froshims.db`。

* **MVC 范式**
    * > **定义**：MVC 范式指模型、视图、控制器，是一种非常常见的 Web 应用开发方式。
    * 它最大的用处不是代码模板，而是让你可以把要解决的不同问题分开思考。

```text
        +-------------------+
        |     controller    |  app.py
        |  逻辑 / 变量 / 循环 |
        +---------+---------+
                  | 生成
                  v
        +-------------------+
        |       view        |  templates/*.html
        |   用户看得到的一切  |
        +---------+---------+
                  | 读写
                  v
        +-------------------+
        |       model       |  froshims.db
        |     持久化数据     |
        +-------------------+
```

* **范式的裂缝**
    * > **易错点**：这条界限并不清晰——视图里同样见过变量、循环和条件判断，模板里不也写了 `for` 和 `if` 吗。
    * > **易错点**：上面这张图并没有按正确的顺序展示各部分。
    * 这是一种通用的思维方式；在实际开发中，这些概念常常相互交织。

## Cookie 与手戳

* **Cookie**
    * > **定义**：Cookie 是另一个 HTTP 头部信息，通常包含在服务器返回给浏览器的虚拟数据包中；它除了告知浏览器数据包里的内容类型之外，还可能指示浏览器"请设置以下 Cookie"。
    * 名字不好听，常被用于追踪用户行为、投放广告，但本质上只是 HTTP 协议的一项功能。
    * 它本质上就是一个键值对，形式类似 `session=某个值`，那个值通常是一个随机字符串（`123456` 之类），总之是一个**唯一标识符**。
    * 服务器所做的，只是在你电脑上存储一个大型随机值，本质上是一个装着该随机值的文本文件。

* **手戳机制**
    * 这相当于去酒吧、俱乐部或游乐园时的入场凭证：入场时出示一次门票，之后想反复进出只需展示手上的凭证。
    * > **结论**：Cookie 的全部作用是在你的浏览器中放置一个虚拟的"手部盖章"。
    * 浏览器和服务器正是通过这套机制来回记住你的身份。

```text
     browser                                    server
     -------                                    -------
        |                                         |
        |    GET /login  +  username + password   |
        |  ---------------------------------->  |   check credentials
        |                                         |
        |    200 OK  +  Set-Cookie: session=8f3a |
        |  <----------------------------------  |   hand out a stamp
        |    (store "session=8f3a" locally)      |   (== the hand stamp)
        |                                         |
        |    tomorrow: GET /inbox                 |
        |    Cookie: session=8f3a  ------------->  |   read the stamp,
        |                                         |   find server-side data
        |    200 OK  +  inbox HTML               |
        |  <----------------------------------  |
```

    * `Set-Cookie` 是服务器发出来的，等于给你手盖个章；`Cookie` 那一行是浏览器每次都自动带上来的，等于每次都出示手上的印章。
    * 这就是为什么你明明关掉了电脑，服务器却"知道"你昨天登录过。

* **广告追踪与隐身模式**
    * 广告商在某个时间点在你电脑上放了一个 Cookie，你不知情地访问各个网站，浏览器一直在展示这个"手印"。
    * 广告商看到的是同一个手印：哦，又是 David。
    * 隐身模式在关闭窗口时会清除所有 Cookie，相当于下次访问同一网站前把"手印"彻底擦掉。

* **不要用 Cookie 存密码**
    * > **易错点**：服务器理论上可以指示你的浏览器存储一个包含用户名和密码的 Cookie，这样明天打开 Gmail 就不用再看到登录表单；但这是糟糕的做法，因为它把非常敏感的数据放进了浏览器的内存里，任何路过你电脑的兄弟姐妹或室友只要查看你的 Cookie 就能轻易找到。
    * 实际做法是只存一个随机值。

## 会话

* **会话（session）**
    * > **定义**：会话是一种功能，让浏览器和服务器之间建立起持久的连接，尽管 HTTP 本身是"无状态"协议。
    * "无状态"指没有持续的状态记录，你与服务器之间并没有持续不断的连接。
    * 会话可以理解成 Python 里的一个键值对字典，为每个用户关联一组这样的键值对。
    * 服务器可以在它的内存里存储关于你的任意数量的键值对，而"手印"（Cookie）确保服务器知道哪些键值对应的是你。
    * Cookie 的作用在于：即使你合上笔记本电脑甚至关机，第二天回来仍能产生"连接从未中断"的错觉。

* **每个用户一份副本**
    * > **定义**：会话是一种特殊的全局变量，每个访问网站的用户都会分配一个独立的实例，其底层实现正是靠 Cookie 或类似"手部盖章"的机制。
    * 你可以像只处理单个用户那样去用它，但框架会保证用户来的时候各自拿到专属的那一份。

## Flask-Session 登录

* **Flask-Session**
    * > **定义**：一个第三方库，让我们在应用中轻松使用 Cookie，而无需理解或处理那些 HTTP 请求头的底层细节。
    * 说白了，已经有人把 Cookie 的工作原理搞清楚了，现在只想把它当作一个功能来用。
    * 从 `flask` 导入 `Flask`、`redirect`、`render_template`、`request`，还有一个新成员 `session`。
    * 另外单独一行从 `flask_session` 导入大写的 `Session` 类。
    * 必须加的一行是 `app.config["SESSION_TYPE"] = "filesystem"`，把 cookie 数据以文件形式存储在服务器上；`Session(app)` 完成初始化。

```python
from flask import Flask, redirect, render_template, request, session
from flask_session import Session

app = Flask(__name__)
app.config["SESSION_TYPE"] = "filesystem"
Session(app)
```

* **首页按会话状态分支**
    * `render_template("index.html", name=session.get("name"))` 把会话里存的名字传给模板。
    * 模板里如果 `name` 有值就显示"您已以 X 身份登录"并给出登出链接，如果为空就显示"您尚未登录"并给出登录链接。
    * > **结论**：这就是通过条件逻辑检查当前到底有没有用户实际登录。

* **登录路由**
    * 用 `@app.route("/login", methods=["GET", "POST"])` 声明两种方法，再按 `request.method` 分支。
    * POST 分支说明你点了登录按钮，于是 `session["name"] = request.form["name"]` 把用户输入的任何名字存进会话字典，然后 `redirect("/")`。
    * else 分支说明是手动输网址进来的，就展示登录页 `login.html`——一个文本框加一个提交按钮，提交到 `/login` 路径。
    * 登录页面上 URL 以 `/login` 结尾，页面源代码里能看到一个通过 POST 提交到 `/login` 的表单。
    * 设计上保持极简，目前只使用用户名、不设密码；正式站点当然还要加入密码和其他安全措施。

* **登出**
    * 登出简单到有点好笑：调用 `session.clear()` 就能清空会话内容。
    * 更准确地说，是与该 Cookie 关联的服务器端数据被清除了，电脑上实际存储的 Cookie 也已被删除。
    * > **结论**：Facebook、Gmail、Outlook 或者任何其他网站，本质上就是这样让你保持登录状态的。

## 购物车

* **会话的直观用处**
    * > **结论**：会话本质上让你能够实现购物车这样的功能。
    * 现实世界中的购物车是每个用户专属的：在 Amazon 上你和 Kelly 都不会看到对方购物车里的内容。
    * 这是因为我们各自拥有独立的 Cookie，各自都有一个名为 `session` 的全局字典，服务器可以在里面存储任何它需要的键值对，比如我们购物车里的商品信息。

* **books 表与首页**
    * `store.db` 只有一张像书店的表，两列 `ID` 和 `title`，`SELECT * FROM books;` 只有 5 本书，其中包括《银河系漫游指南》及其续作。
    * 首页 `books = db.execute("SELECT * FROM books").fetchall()` 后渲染 `books.html`。
    * 模板里一个 `for` 循环为每本书生成一个 `h2` 和一个表单，表单 action 指向 `/cart`，里面放一个 hidden 的 id 输入。
    * 和取消注册示例一模一样的套路：每样东西都通过唯一的 ID 加入，而不是靠用户自己在文本框里输入。

* **购物车路由**
    * 路由同时支持 GET 和 POST。
    * 先判 `"cart" not in session` 则 `session["cart"] = []`，即用户首次访问时购物车默认是一个空列表。
    * POST 分支从表单拿到书籍 ID，确认这个 ID 确实存在（防止有人随便发送无效参数来捣乱），然后追加到会话中的购物车列表，最后重定向。
    * 一个键值对就能记一整个列表。

```python
@app.route("/cart", methods=["GET", "POST"])
def cart():
    if "cart" not in session:
        session["cart"] = []

    if request.method == "POST":
        id = request.form.get("id")
        if id:
            session["cart"].append(id)
        return redirect("/cart")

    books = db.execute("SELECT * FROM books WHERE ID IN (...)").fetchall()
    return render_template("cart.html", books=books)
```

* **用 IN 查多个 ID**
    * 购物车是一串 ID，查询时用 `IN`，括号里放 `session["cart"]` 中的 ID 列表。
    * `IN` 允许一次性查询多个 ID，只要选择这样做。
    * 页面上显示的条目是一个带编号的有序列表（`<ol>`）里的若干个列表项（`<li>`）。

## 搜索：从等值到 LIKE

* **等值匹配的问题**
    * 最初版本的搜索路由执行 `SELECT * FROM shows WHERE title = ?`，传入 `q` 参数后渲染完整的 `search.html`。
    * 输入首字母大写的 `The Office` 能列出一个无序列表，查看页面源码会发现数据库里既有英国版、美国版还有其他版本。
    * 但输入小写的 `the office` 就得不到任何结果——倒不是说功能有问题，只是功能还不够完善。

* **LIKE 与通配符**
    * 改用 `LIKE` 关键字，因为需要检查标题是否"包含"office。
    * SQL 通配符允许左侧和右侧出现零个或多个任意字符，所以在用户输入内容的前后各拼接一个百分号：`f"%{request.args.get('q')}%"`。
    * `%` 表示任意长度的任意字符，于是这变成了以不区分大小写的方式查找任何包含这些字母的内容，无论这个字符串出现在文本的哪个位置。
    * > **提示**：这个设计初看有点令人困惑——明明有问号占位符，却又不想只搜索用户输入的内容，所以要在占位符参数外面自己拼百分号。

* **仍由 Jinja 渲染**
    * 搜索结果渲染成带项目符号的列表，用的还是那个 Jinja 循环，为每个搜索结果输出一个列表项。
    * 实际上和之前的做法完全一样。

## 从整页 HTML 到 JSON API

* **API**
    * > **定义**：API（应用程序编程接口）本质上是一种基于网络的功能接口，你可以通过调用 API 从他人的服务中获取数据，通常使用 HTTP 协议。
    * 返回的数据可以是文本格式、HTML 格式，或者称为 JSON（JavaScript 对象表示法，JavaScript Object Notation）的格式。
    * > **定义**：JSON 看起来有点像 Python 的语法，它结合了数组和字典的结构。
    * 这样做通常能为期末项目开辟更多可能性：不仅自己，第三方开发者也能利用这些数据，把应用功能整合进他们自己的网站。

* **返回原始 HTML 片段**
    * 第一版改造保留搜索框但**不再有搜索按钮**，因为设计目标是高度交互性——输入 `THE OFFICE` 实际上就是自动完成功能。
    * 每当输入一个字母，就会有一个新的 HTTP 请求发往 `/search` 路由，每个请求都返回一组与输入查询相匹配的列表项。
    * `/search` 返回的不是完整网页，而是一大堆 `<li>` 标签，假设可能有人想直接获取列表项放进自己的 `<ul>` 标签中。
    * > **提示**：但这还不够严谨——返回的是一段脱离上下文的 HTML 代码片段，强制要求用户必须使用列表项并不理想，直接发送原始数据更好。

* **jsonify**
    * > **定义**：`jsonify` 是 Flask 自带的功能，把从 SQL 数据库返回的 Python 字典列表以 JSON 格式进行序列化。
    * 搜索路由不再 `render_template`，而是 `return jsonify(shows)`。
    * 响应里方括号表示接下来是一个列表或数组，里面出现了一个字典，看起来像 Python，但技术上它是 JavaScript 的对象表示法。
    * 有了它就能把应用作为一个服务提供给互联网上的任何人。

### 三个版本放在一起看

| 版本 | 关键 SQL | 路由返回什么 | 交互形态 |
| :--- | :--- | :--- | :--- |
| shows（初版） | `WHERE title = ?` | 扩展布局的完整 `search.html` | 搜索框 + 搜索按钮，严格等值匹配 |
| shows1 | `WHERE title LIKE ?` 配 `%q%` | 完整模板 | 搜索框 + 按钮，大小写不敏感的包含匹配 |
| shows2 | 同上 | 原始 `<li>` 片段，不套模板 | 无按钮，边输入边请求（自动完成） |
| shows3 | 同上 | `jsonify(shows)` 返回 JSON | 同样的自动完成，数据格式与展示彻底解耦 |

* **演进的三步**
    * 从上到下只做了三件事：匹配方式从等值放宽到包含、返回内容从完整页面收窄到数据片段、交互从"点一下"变成"边输入边请求"。
    * 其中真正属于 Flask 的只有 `render_template` 和 `jsonify` 这两个出口。
