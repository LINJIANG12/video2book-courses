# 内存管理与指针安全

## 十六进制与内存编号

### 十六进制

   * **十六进制**

       * > **定义**：以 16 为基数的计数系统，列与占位符的结构和十进制完全一样，只是每一列代表的基数不同。

       * 数字集是 0 到 9 再加 A、B、C、D、E、F，大小写都算，共 16 种可能；进制系统本有无穷多种，十六进制只是计算领域里少数几种常用约定之一。

       * 占位符用 16 的幂：$16^0 = 1$、$16^1 = 16$、$16^2 = 256$。

       * 从 `00` 数到 `0F` 刚好 16 种组合，`0F` 是最大值，$0F = 1 \times 15 = 15$；进位后的 `10` 表示 16，读作"10"的它不是十进制的 10。

       * $FF = 16 \times 15 + 1 \times 15 = 255$。

       * 1 个十六进制数字正好表示 4 个二进制位：F 是 15，二进制是 `1111`；2 个十六进制数字 = 8 位 = 1 字节。

       * 日常一次用 8 位即 1 字节存值，所以两个 F 相邻就是 8 个 1，$1 + 2 + 4 + 8 + 16 + 32 + 64 + 128 = 255$。

       * 讨论颜色时用十六进制、讨论内存地址时也用十六进制，根源都在这个便利。

### 颜色的十六进制写法

   * **RGB 约定**

       * RGB（红、绿、蓝）是计算机内部表示颜色最常用的方式之一，通常写成 6 位十六进制。

       * 黑色是 `000000`，白色是 `FFFFFF`（等价于 255 红、255 绿、255 蓝），红色是 `FF0000`，绿色是 `00FF00`，蓝色是 `0000FF`。

       * 单比特图像里每个点不是 0 就是 1，0 解读为黑、1 对应白；现代技术会给每种颜色分配 16 位、24 位甚至更多位。

       * 分辨率指横向像素点数乘以纵向像素点数；尺寸总是有限的，放到极致看到的就是一个个真正的像素点。

### 内存编号与 0x 前缀

   * **内存画布**

       * > **定义**：内存被抽象成一张可以逐格编号的画布，从字节 0、1、2、3 一直往后编。

       * 编号方式合理但任意；实际编程中程序员一律用十六进制写地址，而不是十进制。

       * 十六进制里读作 `10` 的数字和十进制的 10 容易混淆，惯例是在任何十六进制数字前加前缀 `0x`。

       * 那个 `0` 和 `x` 本身没有任何含义，只负责宣布"接下来是十六进制"，于是 `0x10` 明确等于 16 而不是 10。

       * 屏幕上会大量出现 `0x` 开头、两四位或八位的十六进制数字，多数时候不需要心算换算成十进制。

## 地址、取地址与解引用

### 取地址运算符

   * **`&`**

       * > **定义**：把变量写成 `&n`，就是向计算机提问"这个变量存在内存的哪个地址上"。

       * `int n = 50;` 在大多数系统上占 4 字节也就是 32 位，因此会连续落在 4 个地址上。

       * 打印地址用格式码 `%p`；地址确实是个数字，技术上也能用 `%i`，但一般不这么写。

       * 实测输出形如 `0x7ff3c34ecc`，全是十六进制数字，换算成实际数值非常麻烦。

```c
#include <stdio.h>

int main(void)
{
    int n = 50;
    printf("%p\n", &n);
}
```

### 指针

   * **指针（pointer）**

       * > **定义**：一种能存储地址的变量；它存的是某个变量（也就是内存中某个值）的地址，而不是那个值本身。

       * 声明写法是 `int *p = &n;`，标准形式为类型、空格、星号、星号后紧跟变量名。

       * 把星号放到类型后面（`int* p`）或变量名前面（`int * p`）代码也照样能跑，这两种写法现实中都会见到。

       * 约定上建议把星号紧挨变量名写；也有人更倾向 `int* p`，因为它更明确地表示星号跟类型有关，而不是跟变量名有关。

       * 漏掉星号会编译报错"不兼容的指针到整数的转换"初始化：右边是一个指针，左边却错放了普通整数。

       * 这个语法对所有情况通用，不限于 int，等讨论数组和其他数据类型时同样用 `*`。

       * 指针通常占 8 字节也就是 64 位，因为今天的内存容量动辄几十亿字节，必须能寻址超过 40 亿个地址；只用 32 位寻址最多覆盖约 40 亿个地址、对应 4GB 空间，装不下 8GB 或 16GB 内存，服务器更不可能有几十 GB。

       * 具体地址是任意的，讨论设计时可以把内存细节抽象掉，直接用箭头表示指针。

       * 物理比喻是把内存想成成百上千个小邮箱、像公寓楼那种一排排一列列的布局，每个邮箱里存着某个地址的标签。

       * 但这个运算符本身就想回答相反的问题：既然能找出某个东西的地址，按理说也能自己找一个地址并往那儿存东西。

```text
  p  ────────►  n
                 │
                 └──► 内存里那个 50
```

### 解引用运算符

   * **`*`**

       * > **定义**：写在指针变量名前的星号表示"前往这个指针中存储的地址，取出那里的值"。

       * `printf("%i\n", *p);` 打印的是 `n` 的值 50，而不是 `p` 里那个大得多的地址。

       * 对字符串同样成立：`printf("%c\n", *s);` 直接访问 `s` 指向的第一个字符，等价于 `s[0]`。

       * 直接偷懒打印 `n` 当然也行，但那展示不出任何有趣的东西。

### 星号的三重身份

   * **星号的三个角色**

       * 同一个星号同时扮演乘法、声明指针、解引用指针三种角色，认知上极易混淆。

       * > **易错点**：判定只看星号左边有没有数据类型。`int *a` 左边是类型，意思是"这是一个指针"；`*a` 左边只有变量名，意思是"去这个地址，把那里的值拿出来"。⚠️

       * 很多年前本可以在键盘上另设符号把这几件事区分开，但现实就是同一个星号在不同语境里穿着不同的马甲。

## 字符串的本质：字符指针

### 空终止符与连续存储

   * **空终止符（null character）**

       * > **定义**：字符串末尾必定跟着的一个特殊字节，表示"字符串到此结束"。

       * 字符串在内存里以连续字节的形式存储，一个字符紧挨一个字符，中间没有任何间隔，所以它们的地址必须连续。

       * C 语言里严格来说并不存在名叫"字符串"的数据类型，无法直接声明一个叫字符串的类型。

       * `"HI!"` 看着是三个字符，实际占 4 个字节，因为总要给空终止符留位置。

       * `s[3]` 已经取到空终止符，再往后就是别的内容了；可以访问它，但多半不是你真想看的东西。

```text
  0x123  [  'H'  ]   <- s[0]
  0x124  [  'I'  ]   <- s[1]
  0x125  [  '!'  ]   <- s[2]
  0x126  [  '\0' ]   <- s[3]，字符串到此为止
  0x127  [       ]   <- 再往后就是别的内容了
```

### string 是 char * 的别名

   * **string 类型别名**

       * > **定义**：`s` 里存的从来不是字符串内容，而是字符串里第一个字符的地址。

       * 只要第一个字符的地址就足够了：指针告诉计算机字符串从哪里开始，空终止符告诉它到哪里结束，中间的一切可以用一个循环全部找出来。

       * `typedef char *string;` 让 `string` 成为 `char *` 的别名，从此两者完全等同。

       * `typedef` 本质上允许定义自己的数据类型，比如 `typedef int integer;` 之后环境里就多了一个等同 `int` 的 `integer`。

       * 用结构体电话簿时 `person` 也是一个 `typedef` 出来的类型，里面装着姓名和号码这样一个完整结构，复杂度都在里面，只是给了它一个新名字。

       * 去掉 CS50 库再编译 `string s = "HI!";` 会报 `error: use of undeclared identifier 'string'`，因为编译器不认识 `string` 这个关键字，它只是个概念不是 C 的关键字。

       * 改写成 `char *s = "HI!";` 并去掉辅助轮，程序照常工作，完全不依赖 CS50 库。

       * > **结论**：`s` 本质上就是一个字符数组。

### printf 的 %s 与 %c

   * **格式码决定打印多少**

       * 传 `%s` 意味着"用一个循环把字符一个一个打出来，直到遇到空终止符为止"；传 `%c` 打一个字符就停。

       * 调用处不必写解引用星号，是因为 `printf` 接收的是地址并自动按地址去访问内容，那个解引用操作发生在它的实现代码里。

       * 概念上更严谨的讲法是：`s` 代表字符串里第一个字符的地址，真正需要传给 `printf` 的是地址而不是具体字符，这样它才被当作字符串而非单个字符处理。

       * `printf` 用 `%i` 指定输出格式，`scanf` 用的是同一套格式码，两个函数的设计文档都写明这一点，所以两边都用 `%i` 完全合法。

       * 用数组语法逐个打印 `s[0]`、`s[1]`、`s[2]` 本身没什么有趣的结果，但确实证明拿到了 `H`、`I`、`!`，它们在内存中确实是连续存储的。

### 指针算术与数组语法糖

   * **指针算术**

       * 指针和地址本质上是数字，可以对指针本身做加减，这叫指针算术。

       * `*(s + 1)` 表示"定位到 `s`，然后向前移动一个字符的位置"；`*(s + 2)` 就是偏移两个字节。

       * 指针也能做乘除，只是多数情况下看起来会很奇怪；在地址上加数字是肯定要做的。

       * > **易错点**：写 `*(s + 1)` 千万别漏掉括号，否则运算顺序不对。

       * 数组下标就是这套写法的语法糖：`s[0]` 等价于 `*s`，`s[1]` 等价于 `*(s + 1)`。

       * 没人真想写那种又解引用又加括号的代码，光是读和解析就够费神，是计算机在帮我们把方括号翻译成更晦涩但更准确的版本。

       * 打印 `s` 得到 `HI!`，打印 `s + 1` 得到 `I!`，打印 `s + 2` 得到 `!`；这三条都能正常工作，是因为这三个"字符串"碰巧都以同一个空字符结尾。

       * 内存块上也能用数组语法，`*x = 72;`、`*(x + 1) = 73;`、`*(x + 2) = 33;` 与 `x[0]`、`x[1]`、`x[2]` 是完全相同的操作，一般人选方括号是因为它更简洁、更易读易写。

### 字符串比较

   * **`s == t` 失效的原因**

       * `==` 比较的是两个数字，而 `s` 和 `t` 里装的不是内容是地址。

       * 两个字符串碰巧内容一样、却存在内存里两个不同位置时，`s == t` 拿到的就是 `0x123 == 0x456`，结果必然是 false；用 `s == t` 比较字符串会直接编译报错。

       * 整数能直接 `i == j`，是因为 `i` 和 `j` 里装的确实是数值本身。

       * 正确做法是 `strcmp(s, t) == 0`，需要引入字符串库 `string.h`；返回 0 才表示两个字符串相等，不是返回 1 或 -1。

       * `strcmp` 接收的是两个字符串的地址，内部是一个 `for` 或 `while` 循环，从各自起点逐个字符比较下去，所以不需要自己写循环。

       * `printf("%p\n", s);` 与 `printf("%p\n", t);` 会打出两个不同地址，哪怕输入内容完全一样。

       * `get_string` 无论用户输入什么都会分配独立的内存块，即使内容完全相同也不例外。

## 作用域、值传递与内存布局

### 按值传递

   * **按值传递（pass by value）**

       * > **定义**：交给被调用函数的是变量的副本，函数里改副本，改的只是那个副本。

       * C 里每次调用函数传参本质上都是按值传递。

       * 进入 `swap` 时 `a` 是 `x` 的副本、`b` 是 `y` 的副本，函数内部 `a`、`b` 确实交换成功，但返回时 `x` 和 `y` 一个字节都没变。

       * `temp` 在函数结束时仍然保存着 1 的副本，杯子并没有被真的倒空。

       * 把 `a`、`b` 打印出来会看到它们已经对调，这也印证了副本确实存在。

       * > **结论**：如果手上只有值传递这一个工具，交换函数在 C 里根本写不出来。

### 作用域

   * **作用域（scope）**

       * > **定义**：变量的作用域就是包裹它的最近一层花括号，也就是它在程序中的"生存空间"。

       * `x` 和 `y` 活在 `main` 的花括号里，`a`、`b`、`temp` 活在 `swap` 的花括号里，两者不在同一层作用域，对副本的改动传不回去。

### 内存四区域

```text
     高地址 ↑
┌──────────────────────┐
│      机器码区域      │   ← 编译出来的二进制代码
├──────────────────────┤
│      全局变量区      │   ← 定义在 main 之外的变量
├──────────────────────┤
│                      │
│   堆 (heap)  ↓       │   ← malloc 的地盘
│                      │      一块接一块往下排
├──────────────────────┤
│   ↑ 栈 (stack)       │   ← 局部变量与函数调用
│                      │      像叠餐盘一样往上长
│                      │
└──────────────────────┘
     低地址 ↓
```

   * **四个区域**

       * 图上的"上""下"只是示意图，计算机内部并没有真正的上下概念。

       * 机器码区域：开发者编译生成的全部二进制代码，双击运行时由操作系统从硬盘或固态硬盘复制进 RAM（随机存取存储器）这种更快的存储器。

       * 全局变量区：定义在 `main` 之外的变量，按惯例放在这里，整个程序都能访问到。

       * 堆：`malloc` 分配的内存全部来自这里，第一次调用给一块、第二次给另一块，块与块连续排列，全部由 `malloc` 替你管理，扩展方向朝下。

       * 栈：存局部变量和函数调用，运行时自动完成，扩展方向朝上，像食堂里叠餐盘。

       * 这种布局纯粹是因为很多年前有一群人在一间会议室里开会决定了计算机内存长什么样。

       * `main` 的参数（包括命令行参数）和局部变量待在 `main` 那一块内存里；`main` 调 `swap` 时，`swap` 占用的是紧挨着的上一个可用内存块。

       * 内存分配通常是有意设计的，地址往往自动递增，数据尽可能一个接一个连续存放；但随着程序运行、尤其在大程序中频繁增删数据，布局会逐渐变得混乱。

| 区域 | 放什么 | 谁来分配 | 增长方向 |
| :--- | :--- | :--- | :--- |
| 机器码区域 | 编译好的二进制代码 | 程序启动时由操作系统加载进 RAM | 固定 |
| 全局变量区 | 定义在 `main` 之外的变量 | 程序员 | 固定 |
| 堆 (heap) | `malloc` 分配出来的内存块 | `malloc`，一块接一块连续排列 | 向下 |
| 栈 (stack) | 局部变量、函数调用的栈帧 | 运行时自动完成 | 向上 |

### 栈帧与残留数据

   * **栈帧（stack frame）**

       * > **定义**：一次函数调用所占的那块独立内存，里面装着形参和局部变量。

       * 函数执行完毕后那些二进制数据其实还留在内存里，但那段空间"好像消失了一样"——程序不再使用它，计算机可以随时拿去干别的。

       * 同一个函数被反复调用时内存块概念性地一上一下地移动，于是会在内存里看到之前残留的数值。

```text
  main 栈帧                  swap 栈帧
  ┌────────────┐   ┌────────────┐
  │  x = 1     │──▶│  a = 1     │  ← 副本
  │  y = 2     │──▶│  b = 2     │  ← 副本
  └────────────┘   │  temp      │
                   └────────────┘
```

### 传地址改写交换

   * **传址版 swap**

       * 原型从"收两个整数"改成"收两个整数地址"：`void swap(int *a, int *b);`

       * 调用处必须递地址：`swap(&x, &y);` 递过去的从此不再是两个数字，而是两张写着"值在这儿"的藏宝图。

       * 函数体三步依次是 `int temp = *a;`、`*a = *b;`、`*b = temp;`。

       * `temp = *a` 是对 `a` 解引用，像玩蛇梯棋一样顺着箭头找到目标，拿到值 1。

       * `*a = *b` 先通过 `a` 找到目标位置，再通过 `b` 找到存着 2 的地址，把 2 写进 `a` 所指的位置，`x` 那一格当场被改写成 2。

       * `*b = temp` 定位到 `b` 指的地址把 `temp` 写进去，`y` 那一格变成 1。

       * 交换完成后 `swap` 的栈帧从概念上说被释放，0 和 1 的二进制数据还在内存里只是不再被使用，但 `x` 和 `y` 的真实值被改掉了。

| | 传值（旧写法） | 传址（新写法） |
| :--- | :--- | :--- |
| 传的是什么 | 变量当前值的副本 | 变量所在位置的地址 |
| 形参拿到的是 | 一个和原变量无关的拷贝 | 一张写着"值在这儿"的藏宝图 |
| 改得动外面的变量吗 | 改不动 | 改得动 |
| 函数返回后 | 副本连同栈帧一起消失 | 原变量的新值留了下来 |

### 交换为什么需要临时变量

   * **临时变量（temp）**

       * 现实中交换两杯液体唯一难点是没有第三个杯子：蓝色倒进空杯，橙色倒进原来装蓝色的杯子，空杯里的蓝色再倒进原来装橙色的杯子。

       * 不给任何临时的落脚点就不混在一起地交换，这现实中无解，在内存里恰恰就是 `t = s` 那种"我以为拿到了内容、其实只拿到一个地址"的结构。

       * 写成 C 就是三行：`int temp = a; a = b; b = temp;`，每行对应一次倒液体的动作。

       * 缺了 `temp` 这一步，原值一旦被覆盖就彻底没了，所以它是整个交换里唯一不可省的中转。

## 堆内存：malloc 与 free

### 赋值不是复制

   * **`t = s` 复制的是地址**

       * > **易错点**：`t = s` 复制的是地址不是内容，改副本的字符就是在改原件。⚠️

       * 复制后 `s` 和 `t` 里装的是同一个地址，`t[0] = toupper(t[0]);` 访问的正是 `s` 所指的那块内存。

       * 于是只修改 `t[0]` 这一个字符，`s` 和 `t` 的首字母却都变成了大写。

       * 用方括号下标和“访问 `t` 所指向的地址、访问第一个字符的地址”来说，功能完全等效，区别只在于有没有套上这层语法糖。

```text
        s = 0x123                 t = 0x123
          |                         |
          +------------+------------+
                       v
                  +----+----+----+----+
                  | h  | i  | g  | h  |
                  +----+----+----+----+
                   0x123 124  125  126

  执行 t[0] = toupper(t[0]) 之后：

                  +----+----+----+----+
                  | H  | i  | g  | h  |
                  +----+----+----+----+
                   0x123 124  125  126
```

### malloc 与 free

   * **内存分配函数 malloc 与内存释放函数 free**

       * > **定义**：`malloc` 是用于动态分配内存的函数，返回一块内存的地址；`free` 把不再需要的内存归还给计算机，二者功能相反。

       * 使用 `malloc` 必须引入标准库头文件 `stdlib.h` 以拿到函数原型，`free` 同样依赖它。

       * 严格来说复制 `s` 只需要 4 个字节，但写死 `malloc(4)` 有点蠢，因为不知道用户会输入什么。

       * 正确做法是用 `strlen` 让计算机直接告诉长度再加 1：`char *t = malloc(strlen(s) + 1);`

       * 加 1 是因为 `strlen` 返回的实际长度不包括空字符，而 `high` 长度虽为 3、底层实现仍需要第 4 个字节存空字符。

       * 申请 3 个整数的空间应该写 `malloc(3 * sizeof(int))`；写 `malloc(3 * 4)` 虽然算得出 12，却会降低代码可移植性，因为其他系统中整数可能不是 4 个字节。

       * `sizeof` 运算符可以直接询问计算机某个数据类型在当前系统占多少字节，对 `char` 总是得到 1，对 `int` 通常返回 4。

       * 严格来说 `malloc` 分配的区域可能落在任何位置，但这并不重要，因为返回值就是这块内存首字节的地址。

### 把字符搬过去

   * **逐字节复制**

       * 手动复制要连空终止符一起搬：先 `int n = strlen(s);` 存下长度，再 `for (int i = 0; i <= n; i++) { t[i] = s[i]; }`。

       * 循环条件必须是 `i <= n` 而不是 `i < n`：长度是 3 时用 `<=` 才会跑 4 次，把 `'\0'` 也抄过去。

       * 提前把长度存进整型变量 `n` 而不是在每轮循环里重新调 `strlen`，是为了不浪费地反复调用函数。

       * 写 `i <= n` 而不是 `i < n + 1` 是因为两者在这里完全等价，但前者少做一次加法，而且 `n` 的含义直接对应 `strlen` 的返回值，读代码的人不用在脑子里再换算一次。

       * 不要用 `t[4] = '\0';` 这种硬编码下标来收尾，因为不该把数字写死。

       * 更好的办法是不写循环：先分配足够内存，然后 `strcpy(t, s);` 直接把 `s` 的字节抄进 `t`。

       * > **易错点**：`strcpy` 的参数顺序是目标在前、源在后，和赋值号的直觉正好相反；写反了不会报错，只会把一片垃圾值和半个 `s` 搅在一起，往往要到打印时才炸。⚠️

       * `malloc` 刚返回的那块内存最初装的是从未被主动写入的垃圾值，复制动作本身就是把它逐字节覆盖掉。

### 内存泄漏

   * **内存泄漏**

       * > **定义**：用 `malloc` 申请了内存却从不释放归还，程序结束时这部分内存既未被释放也未交回系统。

       * 在服务器这类需要长时间运行的程序里后果严重，电脑会变得越来越慢；Mac、Windows、iPhone、Android 上的程序同样会随着运行效率下降。

       * 本质上是内存正在耗尽——并非物理上耗尽，而是计算机认为它正在使用所有内存，即使这些内存实际上并未被有效利用。

       * 开发者最清楚何时不再需要内存，程序完全处理完变量 `t` 之后就应调用 `free(t)` 传入先前分配的地址。

       * `free` 之后这块内存就能被操作系统回收，用于其他用途。

### 谁分配谁释放

   * **释放责任的划分**

       * `get_string` 返回的内存不需要自己 `free`，这是有意为之的设计：CS50 库的实现会在你不再需要它返回的内存时自动释放。

       * 这种自动内存管理只在该功能内部有效，一旦你把内容复制到 `malloc` 来的内存里，那部分就归你自己负责。

       * > **结论**：谁分配的谁负责。`malloc` 拿来的内存必须由你自己 `free`；`get_string` 替你分配的，你不要插手。

       * `get_string`、`get_int` 以及 CS50 库里所有那些 `get_` 函数在 C 里仍然很有用，不用这类函数获取用户输入会非常麻烦。

## NULL 与 NUL

   * **空终止符 NUL**

       * > **定义**：由 8 位组成的单字节，所有位均为零，写作 `'\0'`，读作 null，作用是标记字符串到此结束。

   * **空指针 NULL**

       * > **定义**：一个特殊的内存地址 `0x0`，这个地址上不应该存放任何内容，表示"这里没有值"或"出错了"。

   * **为什么名字长得很像**

       * 几十年前一部分人把全零字节称为 NUL，另一部分人把这个新事物命名为 NULL，两者极易混淆。

       * 地址 0 是人类多年前定下的约定，于是干脆把地址 0 的位置空出来永远不放任何内容，程序出错时就有了一个特殊值可以发出信号。

       * 人们决定连地址 `0x0` 以及紧随其后的几个字节都永远不使用。

       * > **结论**：一个全零的字节有 NUL 这个角色，一个值为 0 的指针有 NULL 这个角色；前者是数据，后者是"这里没有数据"的信号，类型完全不同。

| | NUL | NULL |
| :--- | :--- | :--- |
| 是什么 | 空终止符 | 一个特殊的内存地址 |
| 本质 | 由 8 位组成的单字节，所有位均为零 | 地址 `0x0`，这个地址上不应该存放任何内容 |
| 用途 | 标记字符串到此结束 | 表示"这里没有值"或"出错了" |
| 长什么样 | `'\0'` | 指针的值为 0 |

## 错误检查与退出码

   * **从第一周起就该写的检查**

       * `get_string` 在出错时可能返回 NULL，例如用户输入的文本长到计算机内存装不下。

       * 它返回的 NULL 是一个特殊的哨兵值，意思是我没法满足你的要求，我无法返回一个正确的值给你，这里返回的是一个错误。

       * 你不会希望只拿到部分文本却完全不知道哪里出了问题，所以这个哨兵值必须检查。

       * 写法是 `string s = get_string("s: "); if (s == NULL) { return 1; }`，等于 NULL 就完全中止程序。

       * `malloc` 出错意味着内存不足，同样要检查 `char *t = malloc(n + 1); if (t == NULL) { return 1; }`。

       * `malloc` 失败后不应继续访问那块内存，因为它可能指向空地址 `0x0`。

       * 还要检查字符串长度是否大于 0：用户直接按回车得到的是一个长度为 0 的空字符串，那里实际上是空字符，不该对它做大写转换，最坏情况是访问了不该访问的内存引发问题。

       * `toupper` 这类函数默认假设用户确实输入了某些内容。

       * > **结论**：返回 0 表示成功，返回 1 表示失败；程序正常跑到底才 `return 0`，中途任何一步拿不到需要的东西就 `return 1`，这是让调用者知道结果可信的唯一办法。

       * 之前一直没加这些检查是有意识的，因为会增加太多开销，但那些代码其实从第一周起就一直存在潜在问题。

## 常见内存错误

### 垃圾值

   * **垃圾值**

       * > **定义**：内存里之前留下的、跟你毫无关系的旧数据，既不是零，也不是你主动写进去过的任何东西。

       * `int scores[1024];` 只是腾出 1024 个格子，什么都没往里面放；循环读出来的 0、25、32000、负数都是这块内存上辈子的住户留下的痕迹。

       * 声明不等于初始化，你读到的不是"零值"。

       * `malloc` 刚返回的内存同样装满垃圾值，只不过复制动作会把它逐字节覆盖掉。

       * 栈帧被回收复用后重新分配，也会读到上一次残留的数值。

       * > **易错点**：你根本不应该去触碰那些从未被自己占有的内存区域。⚠️

### 未初始化的指针

   * **未初始化指针**

       * `int *x;`、`int *y;` 声明指针而不赋任何值是允许的，这两行只是告诉计算机给我一个用来存整数地址的变量。

       * 不初始化 `y` 的话谁也不知道它会指向哪里，可能是 0、25、32000 甚至负数。

       * `*y = 13;` 会直接崩溃，因为解引用一个无效或伪造的指针后果比访问一个可能没有值的变量更严重。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *x;
    int *y;

    x = malloc(sizeof(int));

    *x = 42;
    *y = 13;   // y 从未指向任何实际目标
}
```

### 指针的三个动作

   * **三步走**

       * 一开始指针并不指向任何东西，它们指向的对象被称为指针目标，而设置指针目标是另一个独立的步骤。

       * 声明一个指针变量、让它指向某个目标、通过解引用往目标里存值，这三步必须分开做。

       * `int *y;` 只完成了第 ① 步，第 ③ 步就崩。

       * 让 `y` 指向和 `x` 相同的目标不是复制什么内容，只是让一个指针指向另一个指针所指向的相同位置，这样代码就完全没问题；此后两个指针共享同一个目标，都能看到最新写入的值。

       * "能读指针的地址"和"能把值写进那个地址"是两回事，前者是安全的，后者才有风险。

### 索引越界

   * **越界写入**

       * 索引从 0 开始，申请 3 个整数的空间就只能使用索引 0、1、2，写 `x[3]` 就是访问了不该访问的区域。

       * Valgrind 会报出一个大小为 4 字节的非法写入，因为整数占 4 字节、越界索引指向的正是下一个 4 字节的块。

       * 把 `x[3] = 33;` 改成 `x[2] = 33;` 就能解决。

### 栈溢出与堆溢出

   * **撞车**

       * 堆朝一个方向长、栈朝另一个方向长，长着长着必然撞在一起：`malloc` 调用得越多上面占用越大，函数调得越多、尤其是那些迟迟不肯返回的，下面占用越大，而内存是有限的。

       * 撞车没法根除，只能把内存占用压到最小：只在必要时才 `malloc`，不要因为"可能用得上"就先申请一大片；尽量避免反复、无休止地调用函数却不让它们返回。

       * 递归时不小心漏了基准条件、没有分而治之、问题规模压根没缩小，光是用掉太多栈帧就足以导致栈溢出或类似的堆溢出。

       * 那个非常流行的网站 Stack Overflow，名字的词源就在这里；栈溢出指的就是计算机内存里一个非常典型的大问题。

       * > **结论**：任何资源最终都可能被耗尽，到那一刻程序会崩溃或出别的严重问题。

### 缓冲区溢出

   * **缓冲区溢出（buffer overflow）**

       * > **定义**：像数组这样的一块内存区域，因为存进了过多的值而溢出，比如分配了一个很小的数组，却硬要往里面塞进太多数字。

       * 是比栈溢出、堆溢出更具体的一类问题。

## 格式化输入与输入长度

### scanf 的取地址规则

   * **`scanf`**

       * `scanf` 是老朋友，它做的事是"从键盘读取数据到内存中"；`get_string` 和 `get_int` 的内部本质上干的就是这种事。

       * 读整数写 `scanf("%i", &n);`，这里必须写 `&n`，不能只写 `n`。

       * 这跟 `swap` 是同一个道理：想要修改变量的函数，光把变量本身递进去，它拿到的只是变量当前值的一份副本；必须明确告诉它"把这个结果存进 `n` 所在的那个地址"。

### char *s 为何不写 &

   * **`scanf("%s", s)`**

       * 同一个程序里 `n` 前面要 `&`，`s` 前面却不要，因为 `s` 按定义本身就是某个字符串的地址。

       * 更精确地说 `char *` 表示一个字符的地址，而只要函数找到第一个字符，它就能顺着空字符一路走到字符串结尾。

       * 要是这里再加一个 `&`，`s` 就变成了"地址的地址"——那叫指向指针的指针。

       * 没有 `&` 时 `s` 自己当前的值是个垃圾值，那行 `printf("s: %s")` 就是拿着这个垃圾地址去访问内存；格式化输入函数会**写**内存，所以 `scanf("%s", s)` 沿着一条谁也不知道归谁管的路径一路写下去。

       * 没有崩溃只是因为输入的字符串还不够长，继续试下去肯定会崩，你在访问一段既不是 `malloc` 分配的、也不是通过别的机制为自己占有的内存。

```text
  char *s;              // s 自己就是 8 字节垃圾
  scanf("%s", s);
             │
             └╌╌╌╌╌╌▶  ?  ?  ?  ?  ?  ?  ?  ?
                 波浪线：谁也不知道这块内存归谁管
```

### 字符串到底有多长

   * **长度不可猜测**

       * 用户可能敲 3 次键、4 次键，也可能是一百万次，字符串长度不是你能猜的。

       * 整数那一次之所以没事，是因为整数永远占 4 个字节，告诉 `scanf` 去 `n` 的地址写 4 个字节正好装得下。

       * 有时候得划条线、定个界限，规定输入不许超过某个长度；网页输入框和很多表单都有这条规矩，理由不止一个，内存安全就是其中之一。

       * `get_string` 几乎能处理任意长度的字符，靠的是逐步读取输入：调一次 `malloc`，看一眼够不够，不够就再要一点点，一遍又一遍直到装得下。

       * 自己写又不打算用任何类似的库，就必须自己拍板允许分配多少字节，并且得相信用户不会输入超出预期的数据量。

       * > **结论**：除非准备好处理这一整套复杂性，否则不要用 C 做这类用户输入，用现成的库。

       * 许多现代语言在处理用户输入这种基础操作上简单得多，是因为背后有人替你写好了那些棘手的代码，问题依然存在，只是被一层层封装起来。

### 三条可行出路

   * **缓冲区大小怎么定**

       * 第一条：真的去分配大约 4 个字节的空间，让用户能安全地输入 `high` 这样的词，并留得下容纳空字符的位置。

       * 第二条：把变量改成一个大小为 4 的数组；数组可以看成地址、地址也可以看成数组，事实证明这种语法糖是双向的。

       * 第三条，也是最省事的：根本不要用格式化输入函数去做这件事。

## 缓冲区与文件 I/O

### 易失与非易失存储

   * **存储的持久性**

       * > **定义**：内存是易失性的，一旦断电或电池耗尽，里面的一切全部消失。

       * 硬盘和固态硬盘上的数据是持久的（非易失性）存储，断电也不丢；RAM 只负责临时存取。

       * "磁盘"可能指靠旋转盘片存储 0 和 1 的机械硬盘，也可能指没有活动部件的固态硬盘。

       * 到此为止写过的所有程序，包括那个电话簿示例，只要程序一退出运行，刚输入的姓名和号码就立刻被删除了。

### 文件 I/O

   * **文件 I/O（file input/output）**

       * > **定义**：文件本质上就是存储在磁盘上的一堆字节。

       * C 提供的一整套函数是：打开文件 `fopen`、关闭文件 `fclose`、从文件读取 `fread`、往文件里写 `fwrite` 与 `fprintf`。

       * 写文件不能用 `printf`；`fprintf` 的第一个参数是"写到哪个文件"，这样同时开着好几个文件时才不会搞混，后面再跟格式串和要输出的值。

       * 打开文件时系统实际给你的是"代表这个文件的数据结构"在内存中的地址，从实用角度只需记住你拿到一个指向文件内容的指针，想写进去就得用格式化输出函数并指明写的是哪个文件。

       * > **结论**：在 C 里不使用指针根本无法做文件 I/O——除非有某个库替你把这些细节抽象掉了。

### FILE 与检查

   * **FILE**

       * `FILE *file = fopen("phonebook.csv", "w");` 的返回值按惯例存进全小写命名的变量 `file`。

       * 但 `file` 实际是一个叫 `FILE`（全大写）的结构体，是 C 里少数几个完全大写的标识符之一。

       * 这并不意味着它是常量或什么别的东西，纯粹是当年某位开发者敲代码时采用的命名方式。

       * 它本质上是一个指向该文件内容的指针，严格说这是个善意的谎言：真正返回的是指向"代表这个文件的那块内存"的数据结构的指针。

       * 任何涉及指针的地方都该检查返回值，文件操作也一样——比如存储空间不足导致操作系统没法真正打开这个文件时，`file` 就是 `NULL`。

```c
FILE *file = fopen("phonebook.csv", "w");
if (file == NULL)
{
    return 1;
}

char *name = get_string("Name: ");
char *number = get_string("Number: ");

fprintf(file, "%s,%s\n", name, number);

fclose(file);

return 0;   // 能走到这里，说明一切确实正常
```

### 缓冲区

   * **缓冲区（buffer）**

       * > **定义**：一段内存区域；在 C 这样的语言里通常是一个固定大小的数组，用来存字节。

       * 播放器的进度条就是缓冲区模型：网络够快时字节持续下载并追加进缓冲区，等已下载部分播完时新字节已经就位，播放就不会中断。

       * 播放头追到缓冲区末尾时，下一批字节早就下好了；把数组这样的内存区域塞进过多的值而外溢，就是缓冲区溢出。

### 写入模式 w 与 a

   * **`"w"` 与 `"a"`**

       * `"w"` 表示以允许写入的方式打开文件，不管它此前存不存在。

       * 写文件实际上意味着从第一个字节开始完全重写整个文件：连着跑两三次把联系人"添加"下去，最终文件里只剩最后一次，电话簿等于被删掉了。

       * 这挺反直觉，明明只是添加一条联系人，感觉应该像手机应用里加联系人那样；想更灵活就该按 `fopen` 的文档说明用 `"a"` 模式追加。

       * CSV（逗号分隔值）是很轻量的电子表格格式，数据按行按列存，列与列之间只用逗号隔开。

       * 追加后把文件下载到本地，很可能直接用 Microsoft Excel 或 Apple Numbers 打开，也能整个导入 Google Sheets 等电子表格工具。

### 复制文件的 cp

   * **逐字节复制**

       * `argc` 是命令行参数的数量，`argv` 是字符串数组；它本质上就是一个字符指针的数组，写出来就是 `char *argv[]`。

       * `argv[0]` 是程序自己的名字，一般不是关心的对象；用户输入的两个词是 `argv[1]` 和 `argv[2]`。

       * C 里没有专门表示"单个比特"或"8 个比特也就是一个字节"的数据类型，常见做法是用 `typedef` 造一个别名。

       * 理想情况下别名就是 `char`，因为一个 `char` 正好占 1 字节 8 比特；但字符类型也可以被当作整数处理，而整数可以是正数也可以是负数，所以真正要的是 `unsigned char`。

       * `unsigned char` 的作用是告诉编译器这 8 位数据不能被解释为负数，因为要的是原始的 8 位数据而不是拿它做数学运算。

       * 循环思路和播放器完全一致：`while (fread(&b, sizeof(byte), 1, src) != 0)` 从源文件一次读一个字节，读不到了就停，`fwrite` 再把这个字节写进目标文件。

       * 知道文件是二进制文件（由 0 和 1 组成，而不是 ASCII 或 Unicode 文本）时，`fopen` 加 `"b"` 以二进制模式读写。

```c
#include <stdio.h>

typedef unsigned char byte;

int main(int argc, char *argv[])
{
    FILE *src = fopen(argv[1], "rb");
    FILE *dst = fopen(argv[2], "wb");

    byte b;
    while (fread(&b, sizeof(byte), 1, src) != 0)
    {
        fwrite(&b, sizeof(byte), 1, dst);
    }

    fclose(dst);
    fclose(src);
}
```

## Valgrind

### 工具定位

   * **Valgrind**

       * Valgrind 是 debug50、printf、duck 等调试工具的有力补充，特别适合用于追踪内存相关的错误，不是 CS50 课程特有的工具，程序员普遍都在用。

       * 编译和运行都没有报错、程序也没有崩溃，代码里却藏着索引越界和内存泄漏时，就靠它照出来。

       * 输出内容相当混乱，复杂度远超实际需求，每行都显示进程号实在多余；但只要训练自己捕捉关键信息，指向特定文件和行号的线索最有价值。

       * 读这些信息仍然需要编程知识基础：无效的 4 字节写入之所以无效，是因为索引越界、访问了不该访问的内存区域。

### 两类关键输出

```text
==1234== Invalid write of size 4 at 0x...
==1234==    at 0x...: memory.c:11
...
==1234== 12 bytes in 1 block are definitely lost in loss record 1 of 1
==1234==    at 0x...: memory.c:8
...
==1234== HEAP SUMMARY:
==1234==     in use at exit: 12 bytes in 1 blocks
==1234==   total heap usage: 1 allocs, 1 frees, 12 bytes allocated
```

   * **非法写入**

       * `Invalid write of size 4` 里的"写入"指修改某个内存位置的值，与获取值的读取正好相反。

       * 知道数据类型的大小（比如 4 字节）通常很有用，因为内存操作错误往往与访问了错误大小的内存区域有关。

   * **泄漏报告**

       * `12 bytes in 1 block are definitely lost` 指程序运行时"丢失"了 12 字节，不是字面意义的丢失，而是这部分内存既未被释放也未通过 `free` 归还给系统，申请的内存一块都没还。

       * 12 这个数字应该很熟悉：整数通常占 4 字节，申请 3 个整数就是 12 字节。

       * 报告里出现的行号是分配点，不是说那一行写错了；顺着分配点往后找就能找到漏掉的 `free`，像面包屑一样指引修复方向。

### 修好之后

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *x = malloc(3 * sizeof(int));
    if (x == NULL)
    {
        return 1;
    }

    x[0] = 72;
    x[1] = 73;
    x[2] = 33;

    free(x);

    return 0;
}
```

```text
==1234== HEAP SUMMARY:
==1234==     in use at exit: 0 bytes in 0 blocks
==1234==   total heap usage: 1 allocs, 1 frees, 12 bytes allocated
==1234== All heap blocks were freed -- no leaks are possible
==1234== ERROR SUMMARY: 0 errors from 0 contexts
```

   * **修好的信号**

       * `All heap blocks were freed -- no leaks are possible` 表示所有堆内存块都已被释放，不可能存在内存泄漏。

       * `in use at exit: 0 bytes in 0 blocks` 加上 `ERROR SUMMARY: 0 errors from 0 contexts` 说明零错误。

       * 修好后的输出明显更短，剩下的内容大多无关紧要。

       * 但 Valgrind 检测不到"忘记写 NULL 检查"这个错误，因为它并非每次都会发生。

## 性能与风险的取舍

   * **为什么 C 把内存交给你**

       * C 是性能极高的编程语言之一，非常贴近硬件，让你能高度掌控内存和操作，从而写出极其高效、速度极快的代码。

       * 正因如此，即便数十年过去它依然是全球应用最广泛的编程语言之一。

       * 与此同时你也可能把事情搞得一团糟；如今许多软件被黑客入侵或意外崩溃，往往正是因为开发者忽略了这类看似简单却与内存管理相关的错误。

       * Python、Java 这类更现代的语言对计算机内存的控制权限就相对有限，内置了更多防护机制避免开发者因失误出问题，代价往往是性能上有所妥协、运行速度相对较慢。

   * **为什么绕不开地址**

       * 处理文件、或者想在内存中构建比数组更复杂的数据结构时，就必须了解内存地址以及数据存储位置。

       * 数组能实现二分查找这类功能，但有些功能是数组无法实现的，尤其在速度要求较高的时候。

       * 接下来的做法是在计算机内存中构建二维结构，比如表示家谱或更通用的树形结构，从而更高效地存储数据。

## 位图上的滤镜

   * **BMP 位图**

       * BMP 位图文件本质上就是一张从上到下、从左到右排列的像素网格，每个像素用一个红值、一个绿值、一个蓝值描述。

       * 灰度：把每个像素的 RGB 三个值都调成更小的、彼此接近的数值，只留下黑、白和灰。

       * 棕褐色调：同样逐像素换算，给整张照片加上老照片那种复古味。

       * 镜像翻转：沿垂直轴把左边的字节搬到右边、右边的搬到左边，图像就翻了过来。

       * 模糊：对每个像素做一点数学计算，让它像蒙上一层薄雾，既能模糊也能去模糊。

       * 边缘检测：找出桥梁这类显著特征，把它们和天空区分开来，识别出滤镜的边缘。

       * 掌握从上到下、从左到右走遍文件里每一个字节并改写它的能力之后，同一张照片就能被玩出完全不同的花样。
