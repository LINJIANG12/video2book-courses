# SQL 关系数据库与多表查询

## 编程范式

### 过程式与声明式

* **过程式编程语言（procedural）**

    * > **定义**：C、Python 这类语言要求你一步一步写出过程与函数，包括循环、条件语句，由程序员规定「怎么做」。

    * 典型链条是打开文件、逐行读取、解析分隔符、计数、打印，每一步都要亲手写出。

* **结构化查询语言（Structured Query Language，SQL）**

    * > **定义**：声明式编程语言，只声明想解决的问题与想问的问题，由数据库利用循环、条件语句等底层积木自行寻找答案。

    * 选定列、按列分组计数这类需求，一句话即可表达，不写 `for` 或 `while` 循环，也不定义中间变量。
    * 读过过程式、面向对象、声明式三种范式之后再学新语言，成本明显下降。

* **两种范式的落差**

    * 统计「哪种语言最受欢迎」这一件事，Python 需要十几到二十行代码，SQL 只需一条查询。
    * > **结论**：用这么多代码解决一个相对简单的问题实在繁琐，这正是转向声明式语言的原因。

### 平面文件与关系型数据库

* **平面文件数据库（flat-file database）**

    * > **定义**：本质上就是一个纯文本文件，用在实际数据中不太可能出现的字符分隔行列。

    * CSV 用逗号、TSV 用制表符、PSV 用竖线，三者做的是同一件事。
    * 列长不齐、答案长短不一都不妨碍解析，逗号足以标记一列的结束与下一列的开始。
    * 只要有人用电子表格拖动调整列顺序，按下标读取的代码就会悄悄失效。

* **关系型数据库（relational database）**

    * > **定义**：能定义数据之间关联关系的数据存储方式，用于数据集变大变复杂后表达多个数据片段之间的关系。

    * 电子表格的工作表（sheet）与标签页（tab）对应数据库的表（table），概念上都是行与列的集合。

* **数据库文件**

    * 数据库是运行在计算机上、内部存储大量数据并提供访问途径的软件，`.db` 是数据库文件的惯用命名后缀。
    * 数据以二进制形式存储，只有 `sqlite3` 程序能正确读取，文本编辑器与 `cat` 无法正常显示。
    * 以点号开头的命令是 SQLite 特有指令；**不**以点号开头的命令在世界上几乎所有 SQL 数据库上都能运行。

## 建库与模式

### sqlite3 交互式环境

* **创建与进入**

    * 运行 `sqlite3 favorites.db` 创建数据库，文件已存在时直接进入；提示符显示为 `sqlite>`。
    * 每条命令以分号结束、回车执行；也可以把所有命令写进单独的脚本文件。

* **导入 CSV 的三条点号命令**

    * 三条命令依次完成切换输入模式、导入文件并指定表名、退出程序：

    ```text
    sqlite> .mode csv
    sqlite> .import favorites.csv favorites
    sqlite> .quit
    ```

    * 导入后目录中同时存在原 CSV 文件与新生成的数据库文件。

### 模式与自动建表

* **模式（schema）**

    * > **定义**：数据库的设计结构，说明里面有哪些表、哪些行、哪些列。

    * `.schema` 打印全部建表语句，`.schema 表名` 只看某一张表。

* **`.import` 自动生成的默认表**

    ```sql
    CREATE TABLE IF NOT EXISTS "favorites" (
      "Timestamp" TEXT,
      "Language" TEXT,
      "Problem" TEXT
    );
    ```

    * 三个列名按 CSV 表头生成，数据类型全部被推断为 TEXT。
    * 这只是默认值，`.import` 真正方便之处在于能极轻松地把 CSV 转成可查询的数据库。

* **上手新数据集的顺序**

    * > **结论**：理解一个新数据集的最佳方式就是先查询一些数据，无论数据库是别人给的还是自己导入的。

    * 直接 `SELECT * FROM shows;` 会涌出大量换行与滚动内容，Ctrl+C 中断；加 `LIMIT 10` 才清爽。
    * `SELECT COUNT(*) FROM shows;` 得到 250087，`SELECT COUNT(*) FROM people;` 得到 704315。

### SQLite 数据类型

| 类型 | 含义 |
| :--- | :--- |
| `INTEGER` | 整数 |
| `NUMERIC` | 数值，涵盖时间、日期等现实世界数据 |
| `REAL` | 实数，类似于浮点数 |
| `TEXT` | 文本 |
| `BLOB` | 二进制大对象（Binary Large OBject） |

* 和 C 语言类似，SQL 有一份显式类型列表（到了 Python 中这种列表消失），SQLite 总共只有这 5 种。
* `BLOB` 用来存储原始的 0 与 1；在数据库中直接存文件通常不被推荐，但有时确有必要。
* Oracle、MySQL、PostgreSQL 的类型比这更多，也因此能获得更多额外功能。

### 列约束

* **`NOT NULL`**

    * 建表时声明某列不能为空，之后插入包含空值的数据（如不提供时间戳）会失败。
    * 这是数据库内建的防护机制，区别于用 Python 代码或电子表格时只能事后检查。

* **`UNIQUE`**

    * 要求某列的每个单元格都独一无二，可避免插入重复的哈佛学号、员工号或节目 ID。

## 查询：SELECT

### 列的选择

* `SELECT * FROM 表名;` 中的星号是通配符，代表表中所有列。
* 不需要全部列时直接列出列名：`SELECT language FROM favorites;`
* 多列用逗号分隔：`SELECT language, problem FROM favorites;`
* 结果默认按数据载入表中的原始顺序返回，加 `ORDER BY` 才会改变次序。
* > **结论**：每条 `SELECT` 返回的都是一张临时表，不会被保存到任何地方，拿到答案后就从内存中消失。

* **大小写风格**

    * 惯例是把 SQL 关键字全部大写，与 `favorites`、`language` 这类自定义标识符形成清晰区分。
    * 这只是约定俗成的风格，作用是让关键字凸显、可读性更好。

### 内置函数

* **`COUNT(*)`**

    * 统计表的总行数，`SELECT COUNT(*) FROM favorites;` 得到 272 份提交记录。
    * 配合 `WHERE` 可只统计满足条件的行。

* **`DISTINCT`**

    * `SELECT DISTINCT language FROM favorites;` 得到不重复的语言列表。
    * `SELECT COUNT(DISTINCT language) FROM favorites;` 得到 3，即不同编程语言的总数。
    * SQLite 还内置平均值、最小值、最大值、大小写转换等一整张清单上的函数。

### 条件

* **`WHERE`**

    * 类似条件判断的谓词子句，用于把返回结果限制在符合条件的行。
    * `SELECT COUNT(*) FROM favorites WHERE language = 'C';` 得到 58。
    * 多个条件用 `AND` 连接：`WHERE language = 'C' AND problem = 'hello world';` 得到 5。

* **单引号与转义**

    * 字符串用单引号包裹；值本身含单引号时写成两个连续单引号，如 `'hello, it''s me'`。
    * SQLite 用两个单引号转义单个单引号，不同于 C 语言的反斜杠转义。

* **`LIKE` 与通配符**

    * `=` 做完全匹配，`LIKE` 允许通配符，其中 `%` 代表零个或多个字符。
    * 混合条件用括号明确优先级：`WHERE language = 'C' AND (problem = 'hello world' OR problem LIKE 'hello, %')`。

* > **易错点**：⚠️ 用 `=` 做字符串精确匹配时**区分大小写**，用 `LIKE` 时**不区分**大小写。

### 分组、排序与限量

* **`GROUP BY`**

    * 把相同值的单元格归成一组，即使组内只有一行也单独成组。

    ```text
      Python ┐
      Python ├─▶ Python | 3
      Python ┘
      C      ┐
      C      ├─▶ C      | 1
      SQL    ┐
      SQL    └─▶ SQL    | 2
    ```

    * `SELECT language, COUNT(*) FROM favorites GROUP BY language;` 一次给出每种语言及其总计数。
    * 分组结果可以同时作为聚合结果输出，等价于先用 Python 遍历二十行再做同样的统计。

* **`ORDER BY`**

    * `ORDER BY COUNT(*) DESC` 把计数从大到小排列，不写方向时为升序。
    * 若只想看排名第一的语言，在完全相同的语句末尾加 `LIMIT 1` 即可。

* **`AS` 别名**

    * `SELECT language, COUNT(*) AS n ...` 定义别名后，排序可写 `ORDER BY n DESC`。
    * 聚合出来的计数列排序时最好起别名，比在开头与排序处重复书写 `COUNT(*)` 清楚得多。

* > **结论**：分组统计的数字都只是「某个时间点的快照」，数据还在陆续进来，同一问题在不同时间跑出的数自然不同。

## 增删改

### 插入与 NULL

* **`INSERT INTO`**

    * 写法是 `INSERT INTO 表名 (列1, 列2) VALUES (值1, 值2);`，列与值按相同顺序逗号分隔。
    * `INSERT INTO favorites (language, problem) VALUES ('SQL', '50ville');` 只写两列，时间戳留空。

* **`NULL`**

    * > **定义**：NULL 不是空指针，它特指数据被**有意识地**省略，即「此处无值」的状态。

    * 电子表格只能写 "N/A" 作临时补救，代价是从此再也无法把 "NA" 当作真实答案输入。
    * SQL 的做法干净得多，可以把 NULL 与其他一切值明确区分开。
    * 插入后 `SELECT * FROM favorites;` 仍会显示这一行，缺失的时间戳位置不是空白。

* **NULL 的比较写法**

    * 判断缺失要用 `WHERE timestamp IS NULL`，不能给 NULL 加引号。
    * 加引号就变成查找字面字符串 "NULL"，那可能只是 CSV 里某个语言或题目的名称。

### 删除

* **`DELETE FROM`**

    * 写法是 `DELETE FROM 表名 WHERE 条件;`，`WHERE` 把范围限制在符合条件的行。
    * `DELETE FROM favorites WHERE timestamp IS NULL;` 只删掉刚插入的那一行。
    * 不带条件的 `DELETE FROM favorites;` 会让数据库里一条数据都不剩，但数据仍可从原 CSV 恢复。

* > **易错点**：⚠️ 省略 `WHERE` 的 `DELETE` 破坏性极强，真实案例中有公司实习生因忘记加筛选条件、一按回车就丢掉全部数据。

### 更新

* **`UPDATE`**

    * 写法是 `UPDATE 表名 SET 列 = 值, ... WHERE 条件;`，后面跟一系列键值对。
    * 不带谓词的 `UPDATE favorites SET language = 'SQL', problem = '50ville';` 会让所有人看起来都喜欢 50ville。
    * 这种误改无法恢复到表格的先前版本，除非退出当前操作、彻底删掉现有数据后重新导入整个 CSV。

### 删表

* **`DROP TABLE`**

    * 执行前后各跑一次 `.schema` 就能确认整张表已被移除。
    * 与 `DELETE` 的差别在于删除的是表结构而非其中的行。

* > **注意**：`DROP` 比 `DELETE` 更危险，除非清楚自己在做什么并且确实需要，否则不要执行。

* > **易错点**：⚠️ 顺手敲一句列名写错的 `GROUP BY`，再敲一条 `DROP` 就会连表带数据一起消失，恢复时必须先删掉数据库文件再重新导入 CSV。

### 备份与访问控制

* **备份**

    * 没有为表做好备份、没保留版本时，数据是真的可能永久丢失。
    * 实际系统会按计划自动备份；只做每夜备份的话，最坏情况下仍可能损失将近 24 小时的数据。
    * 更密集的版本控制可到每 5 分钟甚至每分钟一次，代价是占用更多存储空间，这是数据安全与存储成本的典型权衡。

* **访问控制**

    * SQLite 本身不支持用户名或密码的概念，能访问到数据文件就能操作其中所有内容。
    * Oracle、SQL Server、PostgreSQL、MySQL 支持用户名、密码与细粒度权限，可为实习生分配「允许查询、不允许更新删除插入」之类的组合。

## 数据建模

### 两个失败版本

* **重复列**

    * 用「一列一个主演」记录谁出演哪部剧，列数要随主演人数任意变化。
    * 只设五个主演列时，阵容小的剧出现大量空白单元格，阵容大的剧需要不断加列，整个数据集高度稀疏。

* **重复行**

    * 改成「一行一部剧加一位主演」后，《办公室》会在表中反复出现，浪费存储空间。
    * 手工录入这些内容迟早会拼错某个条目，相关功能随之出问题。

* > **结论**：每当我们需要复制粘贴时，都应该意识到这可能是设计上的问题。

* > **结论**：把「主演、主演、主演……」铺开又改成重复行，像是堵住漏水管上的一个洞，另一个地方又冒出新漏洞。

### 三表交叉引用

* **结构**

    ```text
       shows（节目表）        people（人员表）        stars（主演表）
       id   | title          id | name   | year      show_id | person_id
       -----+---------------  ---+-------+------      --------+----------
             | ...              ...                      ...
    ```

    * shows 只保留标题列并为剧集分配唯一标识符，people 记录姓名与各自唯一标识符。
    * stars 是三者中看起来最晦涩的，因为它只包含整数，全靠 386676 这样的 ID 把剧集和人物关联起来。
    * 同一个值在一张表里是主键，出现在另一张表中做交叉引用时就是外键。

* **为什么用整数标识符**

    * 整数类型的长度固定（32 位或 64 位），便于放进数组，也便于二分查找，因为每项之间的距离可预测。
    * `Steve Carell`、`John Krasinski` 这类字符串长度各不相同，提供不了固定间距。
    * 剧集与人物的 ID 都是整数，长度不会因为内容而变化。

* **代价**

    * 电子表格的实用性大大降低：查一部剧有哪些演员，得先弄清这部剧的 ID，再逐个查人物 ID 对应谁。
    * > **提示**：这些「这个 ID 到底对应谁」的问题正是 SQL 能大显身手的地方。

* **规范化**

    * > **结论**：这一版是对数据的规范化处理——除了保留一些必要的冗余整数外，已经消除了所有冗余信息。

## 关系类型

### 关系形状总览

* **六张表**

    * 数据库包含 people、shows、stars、writers、ratings、genres 共 6 张表，数据来自数十万行 IMDB 记录。

    ```text
       people (id, name, year)   ←── n : n ──▶   shows (id, title, year, episodes)
                ▲                          ▲
                │                          │
                └── stars (show_id, person_id)

       shows.id ── 1 : 1 ──▶ ratings (show_id UNIQUE, rating, votes)
       shows.id ── 1 : n ──▶ genres  (show_id, genre)
       shows.id ── 1 : n ──▶ writers (show_id, person_id)
    ```

    * people 有 ID、姓名、出生年份；shows 有唯一 ID、标题、首播年份、总集数。
    * 两个表各自已经完整却毫无关联，stars 才是把节目 ID 与人物 ID 联系起来的关键。
    * > **结论**：关系是有形状的，箭头所暗示的正是关系型数据库中「关系」的体现。

* **三种形状**

    | 关系 | 相关表 | 形状 |
    | :--- | :--- | :--- |
    | 一对一 | ratings | shows.id 1 : 1 ratings.show_id |
    | 一对多 | genres、writers | shows.id 1 : n 子表行 |
    | 多对多 | stars | people n : n shows |

### 一对一：ratings

* **约束来源**

    * ratings 列为 show_id、rating、votes，其中 show_id 被指定为 `UNIQUE`。
    * > **结论**：因为确实希望建立一对一关系，同一个 `show_id` 不能出现多次，否则无法实现一对一关联。

* **对比 genres**

    * ratings 与 genres 在设计思路上非常相似：都有一个 ID 列关联剧集表，然后是各自的另一列。
    * genres 允许 show_id 重复出现，所以那里没有指定唯一性约束。
    * 这两组数据本可以放在一起，把评分与投票数直接并入剧集表；之所以独立成表是为了与 IMDB 的 TSV 数据格式保持一致。

* **连接效果**

  ```sql
  SELECT title, rating
  FROM shows JOIN ratings ON shows.id = ratings.show_id
  WHERE ratings.rating >= 6.0
  LIMIT 10;
  ```

    * 尽管标题与评分原本完全独立地存储在两个不同的表中，连接后被对齐到同一行。
    * 连接操作本质上就是执行这个匹配过程，拆开看就是：选所有数据、把两张表的对应列匹配、其余筛选条件不变。

### 一对多：genres

* **表结构**

    * genres 有 `show_id`（INTEGER，不允许为空）与 `genre`（TEXT，同样不允许为空）两列。
    * `show_id` 被声明为引用 shows 表 `id` 列的外键，这是第一次真正用上外键约束。

* **shows 的各列**

    * `id` 是整数类型且为主键，`title` 是文本类型且不能为空，`year` 是数值类型，`episodes` 是整数类型。
    * `year` 与 `episodes` 都可能为空值，因为 IMDB 对一些年代较久远的剧集没有收录相关数据。

* **多类型实例**

    * `SELECT * FROM shows WHERE id = 63881;` 得到 1970 年播出、共 26 集的剧，其类型是冒险、喜剧、家庭三项。
    * 直接 `SELECT genre FROM genres WHERE show_id = 63881;` 也能得到这三个答案，但需要手动查 ID 再复制粘贴。

* **子查询替代硬编码**

  ```sql
  SELECT genre FROM genres
  WHERE show_id = (SELECT id FROM shows WHERE title = 'The Mongoose');
  ```

    * 返回结果与手写 ID 完全一样，而且完全不需要知道那些数字具体是多少。
    * > **结论**：人类既不需要知道这些标识符具体是什么，也没必要去关心它们，标识符的作用本质上就是为了实现交叉引用。

* **连接后的表观冗余**

    ```text
       id    | title        | genre
      63881 | The Mongoose | Adventure
      63881 | The Mongoose | Comedy
      63881 | The Mongoose | Family
    ```

    * 网格中每处的行数与列数必须保持一致，所以一对多连接时数据库会复制必要的数据让每行看起来一致。
    * > **结论**：数据本身并没有在存储层面产生冗余，这只是临时呈现时的一种冗余形式；数据库足够智能时可用指针等方式避免实际复制。

### 多对多：stars

* **为什么需要中间表**

    * 一人可以参演多部剧，一部剧也可有多位演员参演，因此 stars 处在 people 与 shows 之间。
    * stars 只有 `show_id` 与 `person_id` 两个整数字段，仅靠它们完成关联。

* **定位具体版本**

    * `SELECT * FROM shows WHERE title = 'The Office';` 会返回多部同名剧，包括英国原版和其他版本。
    * 加上 `AND year = 2005` 才能定位到美国版：2005 年开播、共 188 集，其 ID 是 386676。

## 嵌套查询与连接

### 执行顺序

* 括号内的部分先执行，就像小学算术里的运算顺序。
* 内层先取出符合条件的一列 ID，外层再以 `IN` 在这些 ID 中筛选。

  ```sql
  SELECT id
  FROM shows
  WHERE id IN (SELECT show_id FROM ratings WHERE rating >= 6.0)
  LIMIT 10;
  ```

* 只关心排名时外层不必取 title，只取 id 即可。
* 处理单个值时用等号 `=` 匹配就够，只有需要匹配一组值时才需要 `IN` 和外层那对括号。
* > **结论**：嵌套查询可能更容易上手，尤其是初次学习时，可以从内到外逐步推进；连接查询同样非常强大，有时需要连接、有时嵌套就足够。

### 三层嵌套

  ```sql
  SELECT name
  FROM people
  WHERE ID IN (
          SELECT person_id                     -- 中层：该节目牵涉哪些人
          FROM stars
          WHERE show_id IN (
                  SELECT ID                    -- 内层：《办公室》2005 的节目 ID
                  FROM shows
                  WHERE title = 'The Office'
                    AND year = 2005
          )
  );
  ```

    * 内层只干一件笨事：从 shows 取出标题为 The Office、年份为 2005 的那一个节目 ID。
    * 中层拿着这个 ID 去 stars 把所有在这个节目里露过脸的人的 ID 全部捞出来，很多个。
    * 外层拿着中层那一大摞 ID 去 people 把对应的姓名全部取回来，它是必需的，因为它自己并不知道 ID 是多少。
    * > **结论**：整数是机器的，标题和姓名才是人的，每一层都得写。

* **反向查询**

  ```sql
  SELECT title
  FROM shows
  WHERE show_id IN (
          SELECT show_id                     -- 他参演过的所有节目
          FROM stars
          WHERE person_id IN (
                  SELECT ID                   -- 他的 ID
                  FROM people
                  WHERE name = 'Steve Carell'
          )
  );
  ```

    * 从剧集找人改成从人找剧集，只是把 people 提到最外层、shows 沉到最内层。
    * 从人找剧集与从剧集找人互为镜像，在搜索框里敲下一个名字弹出的一长串结果，本质上很可能就是一句 SQL 查询的结果。
    * > **结论**：嵌套查询在概念上是最简单直观的写法，实际应用里应优先考虑它。

* **不要硬编码 ID**

    * 查到的 `136797` 可以记住或复制粘贴，但硬编码的 ID 一旦数据变了就悄悄出错。
    * 正确做法是把它原封不动地塞回嵌套查询，让数据库自己去取。

### 显式连接

  ```sql
  SELECT shows.title
  FROM shows
  JOIN stars ON shows.id = stars.show_id
  JOIN people ON stars.person_id = people.id
  WHERE people.name = 'Steve Carell';
  ```

    * 对齐关系是一句话：先把 shows 挂到 stars 上（节目表主键 = 明星表外键），再把 people 挂上来（明星表外键 = 人员表主键），最后用 `people.name` 把范围收窄到一个人。
    * `JOIN ... ON ...` 把「两张表怎么接」明明白白写出来，结果与嵌套查询一样，只是会多出一些重复行。

### 隐式连接

  ```sql
  SELECT title
  FROM shows, stars, people
  WHERE shows.id = stars.show_id
    AND stars.person_id = people.id
    AND people.name = 'Steve Carell';
  ```

    * 在 `FROM` 里用逗号列出三个表名，对齐方式全靠 `WHERE` 里的谓词表达。
    * 这与显式连接是完全相同的逻辑，只是没写 `JOIN` 关键字，结果同样带重复行。

* **写法选择的依据**

    * 怎么知道该按什么方式 JOIN：必须了解数据库的内部结构，知道表之间怎么连，这在实际工作中非常常见。
    * ORM（对象关系映射）正是这条路的延伸，可以让库自动处理所有连接，因此这套操作其实很容易被自动化。
    * SQL 缩进技术上不重要，只是为了视觉上更清楚；`>` 是 SQLite 特有的续行提示符，不是 SQL 语法。
    * > **易错点**：⚠️ 这两种 JOIN 查询比嵌套查询慢一点，且结果里带重复行，嵌套查询则不会有这些重复。

* **LIMIT 的返回顺序**

    * 没有 `ORDER BY` 时结果通常按数据在表中的原始顺序返回。
    * 所以「评分 ≥ 6 的前 10 条」并不等于「评分最高的 10 部」，取前 10 条只是为了让它能完整显示在屏幕上。

### 命名约定与 ID 生成

* `id` 命名的字段表示主键；`show_id` 这种「下划线 + id」表示外键。
* 表名用复数（`shows`）时，外键用单数形式加 `_id`。
* 不同公司、不同社群各有实践规范，保持一致性即可。
* > **结论**：唯一标识符的常见做法是简单地分配一个从 1 开始的任意整数，然后依次 2、3、4、5 自动递增，并让数据库确保永远不会出现重复值。

## 索引

### 建立索引

* **`.timer`**

    * 打开后每条命令都会显示耗时，`Run Time: real 0.042` 表示那条查询只用了 0.042 秒。

* **`CREATE INDEX`**

  ```sql
  CREATE INDEX title_index ON shows(title);
  ```

    * 索引可以随便起名，`title_index` 本身没有任何含义，重要的只有两件事：在**哪张表**上建、在**哪一列**上建。
    * 翻译过来就是「请加快对 `shows` 表中 `title` 列的搜索速度」。
    * 执行这一次花了大概半秒，但只需要建一次；之后大量更新和删除会花时间维护索引。

* **优化效果**

    * 同一条查询的耗时从 0.042 秒降到 0.001 秒，快了 42 倍；能扛的用户量直接乘以 42。
    * > **结论**：关系型数据库相对电子表格的又一项优势，就是可以提前告诉数据库如何针对特定查询做优化，而电子表格没有这个能力。

* **为什么值得优化**

    * 搜剧、搜电影、搜演员是网站最常见的用法，响应时间越短用户体验越好。
    * 也更省钱：买了一台 1000 美元的服务器，内存、CPU、处理器速度都是固定的，每秒能处理的搜索量有上限。
    * 响应时间砍掉一半，意味着同样硬件能同时服务的用户可能从 1000 人变成 2000 人甚至 5000 人。

### B 树

* **结构**

    * 数据库里的索引通常用 B 树（B-tree）实现。

  ```text
                   ┌──────────┐
                   │   root   │
                   └────┬─────┘
          ┌───────────┼───────────┐
     ┌────▼────┐ ┌────▼────┐ ┌────▼────┐
     │ 内部节点 │ │ 内部节点 │ │ 内部节点 │   ← 每个节点可有多个子节点
     └────┬────┘ └────┬────┘ └────┬────┘
     ┌───┬┴──┐    ┌─┬┴┬──┐    ┌───┴──┐
    ┌──▼─┐┌─▼┐  ┌─▼┐┌▼┐┌─▼┐  ┌─▼──┐┌─▼──┐
    │ 标题 ││标题│ │标题││标│ │标题 ││标题 │   ← 叶节点：排好序的标题
    └────┘└───┘  └──┘└──┘└──┘  └────┘└────┘

    没有索引：从顶上一路逐行扫下去   →  O(n)   全表扫描
    有了索引：沿树一路二分下去     →  O(log n)
  ```

    * 子节点越多，所有叶节点就越能被「向上提拉」，整棵树的高度就越低，这对查找至关重要。
    * 没有索引时数据库只能全表扫描，从顶部开始一行一行往下比，$O(n)$；有了索引则以对数时间复杂度直接定位，$O(\log n)$。

* > **易错点**：⚠️ B 树**不是**二叉树，它只是理念上跟二叉树相似，节点可以有很多个子节点，不一定只有两个。

* **查询复杂度的可优化性**

    * 在最简单的实现方式中，SQL 本质上就是从表头到表尾的线性搜索。
    * 作为程序员，有能力优化这些查询，使数据库实现类似二分查找的高效搜索。

## 用程序驱动 SQL

### 排序的代价

* `sorted(counts)` 传一个字典进去，会按**键**（字母）排序。
* `key=counts.get` 改为按**值**（190、58、24）排序，但方向是反的，需要再加 `reverse=True`。
* 统计 Python 190、C 58、Scratch 24 这件事，Python 要十七行还不算空行，SQL 只要一行：

  ```sql
  SELECT language, COUNT(*) AS n
  FROM favorites
  GROUP BY language
  ORDER BY n DESC;
  ```

* 聚合出来的计数列想排序，最好起个别名（如 `AS n`）再 `ORDER BY n DESC`，比再写一遍 `COUNT(*)` 清楚得多。

### 库与执行接口

* **库提供的输入函数**

    * 提供 `get_string`（跟内置 `input` 差不多，实用价值有限）、`get_int`、`get_float`。
    * 还有一个专门模块，让人能在 Python 代码里舒服地使用 SQL。

* **连接写法**

    * `SQL("sqlite:///favorites.db")` 中的 `sqlite:///` 属于 **URI（统一资源标识符）**，意思是「请用 SQLite 协议打开这个文件」。

  ```python
  from cs50 import SQL

  db = SQL("sqlite:///favorites.db")

  rows = db.execute("""
      SELECT language, COUNT(*) AS n
      FROM favorites
      GROUP BY language
      ORDER BY n DESC
  """)

  for row in rows:
      print(row["language"], row["n"])
  ```

    * `execute()` 接收一句 SQL 字符串，返回一个**包含多行数据的列表，而每一行本身是一个字典**。
    * 因为每行是字典，可以用字符串索引，`row["language"]`、`row["n"]` 正是上面 SELECT 出来的列名。
    * SQL 是作为**字符串参数**传进去的，所以最后要把引号和括号都闭上，这正是「一种语言嵌套在另一种语言中」。

* > **提示**：这个库虽然有点拐杖的味道，但比其他方案好上手——市面上功能相同的库往往复杂得多；教学时间有限，现阶段还会继续用这个拐杖。

* > **结论**：接下来转向 Web 开发时会同时用到 Python、SQL、JavaScript、HTML 和 CSS 五种语言，因为不同语言擅长不同的事。

### 交互式查询

  ```python
  favorite = input("What's your favorite TV show? ")

  rows = db.execute("""
      SELECT COUNT(*) AS n
      FROM favorites
      WHERE favorite = ?
  """, favorite)

  print(rows[0]["n"])
  ```

    * 查的是 `COUNT(*)`——有多少人选了这个项目，而不是查询这个节目本身。
    * 理想情况下只要一个结果，所以不需要任何迭代：`rows` 是列表，`rows[0]` 就是其中第一个也是唯一一个元素。
    * 多个参数会被依次替换到问号的位置。

## SQL 注入

### 拼接输入的后果

* **一个单引号就够了**

    * 用户输入 `hello, it's me` 直接插进 `WHERE favorite = '这里'`，这个引号会跟 SQL 语句原本的引号配对错乱。
    * 最理想的情况是程序直接报错，这对什么也没做错的用户一点也不友好。
    * 最糟糕的情况是用户能执行 `delete`、`drop`、`update` 等破坏性关键字，或者输入分号再接一条删除语句。

* **真实场景**

  ```python
  db.execute(f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'")
  ```

    * 用户名栏输入 `mailin@harvard.edu' --` 时，那个单引号提前闭合了代码里的引号。
    * `--` 在 SQL 里是**注释符号**，就像 Python 的 `#`、C 语言的 `//`，右边的所有内容都被忽略，编辑器里直接灰掉。
    * 实际执行的是 `SELECT * FROM users WHERE username = 'mailin@harvard.edu';`，**完全不管密码是什么**。
    * 若下面写着「返回了行就说明是注册用户，那就放他登录」，那么任何人在自己输入后加一个单引号就能以任何人的身份登录。
    * 再进一步，把 `'` 换成 `'; DELETE FROM users; --` 或 `'; DROP TABLE users; --`，就能对数据库造成毁灭性打击。

* > **定义**：攻击者，或者只是不小心的用户，能以某种方式把恶意代码注入到你的数据库里，这就叫 **SQL 注入攻击**。

* > **结论**：盲目信任用户输入是所有数据库相关操作中最严重的威胁之一，而且这不只是实习生会犯的错误，这相当于让网上的陌生人恶意访问甚至破坏数据。

* **两条铁律**

    * 在 Python 里不要用格式化字符串直接插入用户输入。
    * 永远不要相信用户的输入，不管他是无意中出错还是蓄意破坏。

### 问号占位符

* **写法**

  ```python
  db.execute("SELECT * FROM users WHERE username = ? AND password = ?", username, password)
  ```

    * 问号占位符意味着「不管这个变量的值是什么，都会被安全地填进这个位置，系统会自动补上单引号、自动转义任何危险字符」。
    * 用户输入 `malin@harvard.edu'` 时完全没问题，库负责把单引号转义成两个引号。

    ```text
    用户真正想输入的：   malin@harvard.edu'
    转义之后进到 SQL：  malin@harvard.edu''
    查询实际找的是：    名字真的叫 "malin@harvard.edu'" 的人  →  查无此人，返回 0 行
    ```

    * 这不是真实的邮箱地址或用户名，只会返回 0 行，这才是正确结果。

* > **结论**：解法就是使用库，几乎总是要依赖库来处理，这不是该自己重新造轮子的事情；问号占位符是行业惯例，不是 CS50 特有做法。

* **现实痕迹**

    * 有些网站会非常愚蠢地禁止使用某些标点符号，很可能是从清洗输入的教训中学来的；从技术角度说根本不必把清洗输入的责任推给用户。
    * > **结论**：告诉别人哪些字符不能用等于泄露技术栈——聪明的攻击者会想「既然他们不让我用这个符号，那他们很可能在用这种语言或这项技术」。

## 竞态条件

### 牛奶问题

* **场景**

    * 你和室友共用一个小冰箱，两人都特别喜欢喝牛奶；某天同时发现牛奶没了，各自去街对面的店买了回来。
    * 先后到家时，一罐牛奶放进冰箱就放不下第二罐了；或者牛奶太多其实没那么爱喝，放着会变质。
    * 根源是**我们不知道对方在做什么**——说得专业一点，我们**检查了一个正在被其他人更新的变量状态**。

* **多线程的普遍性**

    * 这问题由来已久，甚至能追溯到 Scratch：单个角色可以同时运行多个脚本，因为 Scratch 本质上就是多线程的。
    * 宿舍同理，两个独立个体并行解决同一个问题；一方不知道另一方已经在处理，就可能做出不明智的决定。

* **锁（lock）**

    * 正确做法是给另一位室友打个电话、门上留张便条，或者干脆把冰箱锁上。
    * 数据库领域的对应术语是锁：当你要更新数据库里的某个值时，先把它锁住，让其他人看不到这条数据，从而避免做出错误决定。

### 丢一次点赞

* **朴素实现**

  ```python
  rows = db.execute("SELECT likes FROM posts WHERE id = ?", post_id)
  likes = rows[0]["likes"]
  db.execute("UPDATE posts SET likes = ? WHERE id = ?", likes + 1, post_id)
  ```

    * 第一行取出当前点赞数，第二行存进变量让代码更好读，第三行做自增。
    * 用的是占位符而非格式化字符串，所以这里不可能发生 SQL 注入。
    * 为「更新一下点赞数」这么个小目标跑两次查询、写三行代码，完全合理。

* **同时执行会发生什么**

  ```text
  时间  服务器 A                          服务器 B
  ───────────────────────────────────────────────────────────────
   t1   SELECT likes → 读到 100
   t2                                     SELECT likes → 也读到 100
   t3   UPDATE SET likes = 101
   t4                                     UPDATE SET likes = 101
                                            ↑
                              最终点赞数 = 101，但正确答案是 102
  ```

    * 点赞数从几百几千飙到几十万时，可能所有人都在同一时间点击那个心形图标。
    * 两台服务器读到同一个 100，各自算出自增，又各自写回 101，**丢了一次数据**。
    * 点赞直接驱动用户参与度这类关键指标，这不只是技术问题，甚至可能变成商业问题。

* **这在真实世界里很常见**

    * 自己电脑上写个小程序不算大问题，但 Meta、谷歌、微软乃至 CS50 的一部分应用都用集中式数据库。
    * 多台服务器同时交互、大量用户同时提交作业或同时运行 Check50 时，就会撞上竞态条件。

### 事务

* **概念**

    * 直接加锁相当于把所有点赞操作串行化，会严重拖慢系统，所以需要更精细的控制方式。
    * **事务（transaction）** 可以只锁定特定的数据行，不需要锁住整张表，更不用说锁住整个数据库。

  ```sql
  BEGIN TRANSACTION;         -- 开始一个事务，从这里开始的语句构成一个整体
      UPDATE posts SET likes = 102 WHERE id = 123456;
  COMMIT;                    -- 提交：保存这些更改
  -- 如果中途出错或被中断：
  ROLLBACK;                  -- 回滚：整个事务一笔都不生效
  ```

    * > **结论**：事务保证数据操作的原子性和一致性——要么全部执行，要么完全不执行，不会被中途打断。
    * 这跟给冰箱上锁、留便条、给室友打电话是同一件事：**防止他们做出相同的决定**。

* **概念比 API 更重要**

    * 具体到竞态条件的技术细节（锁和事务的使用）在教学中可能不是重点，但概念必须带走。

## 现实案例

### 光学字符识别

* **车牌识别**

    * 收费站想自动识别车牌时，只要扫到车牌就直接把数据喂进系统。
    * > **注意**：即使用了正经的库来转义输入内容，数据库照样有可能被整个清空。

* **梗的来源**

    * 计算机科学圈子里流传着一个 XKCD 漫画角色，是计算机科学课的经典收尾素材。
    * 知道这个梗，就知道小 Bobby Tables 是谁了。
