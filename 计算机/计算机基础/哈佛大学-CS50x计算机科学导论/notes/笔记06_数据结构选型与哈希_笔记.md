# 数据结构选型与哈希

## 抽象数据类型与数据结构

* **抽象数据类型（Abstract Data Type，ADT）**

    * > **定义**：一份行为契约，规定这套结构提供哪些特性、功能或操作，不规定底层实现细节。

    * 核心是设计理念——"能做什么"，而不是"怎么存"。

    * 同一个抽象数据类型可以有多种实现，实现方式直接影响它能用来解决哪些类型的问题。

    * 一个栈和一个队列是行为契约，不是内存布局；通过具体的实现，可以让这些抽象数据类型变得不那么抽象。

* **数据结构（Data Structure）**

    * > **定义**：利用计算机内存来组织和存储数据的具体定义。

    * 通过数据结构可以实现栈、队列、字典，以及其他各种数据结构。

    * 你不需要每次都亲自实现这些结构；使用某种语言的功能时，通常是在选择他人已经编写好的实现，直接享受它的行为特性而无需深入底层细节。

    * 权衡是贯穿始终的主题：换到更高级的语言能让人写得更快，但代码在机器上跑起来未必更快。

## 队列与栈

* **队列（Queue，FIFO）**

    * > **定义**：先进先出，谁先进来谁就先离开，第一个排队的人第一个被服务。

    * 队列只有两种操作：入队（enqueue）从队尾进入，出队（dequeue）从队列前端离开。

    * 用数组实现时必须额外追踪队首的位置，一旦开始移除元素，就要准确记住下一个该轮到谁。

    * 用数组实现时还必须同时区分容量与大小。

* **栈（Stack，LIFO）**

    * > **定义**：后进先出，最后放进去的最先被取出来。

    * 栈的两个核心操作是压栈（push，添加到栈顶）和弹栈（pop，从栈顶移除）。

    * 用与队列完全相同的结构体即可实现；因为可以始终从数组末尾删除，最先入栈的元素可以一直保持在位置 0。

    * 现实对应物：餐厅里叠放的餐盘架、先放最底下后取最上面；Gmail 与 Outlook 收件箱中新邮件默认出现在最上面，被挤到下一页的邮件往往被忽略。

    * 后进先出放弃了公平性，换来的是效率与便利。

* **用数组实现队列的结构体**

    ```c
    typedef struct
    {
        int people[50];
        int size;
    } queue;
    ```

    * `people` 是大小与容量一致的数组，`size` 记录当前队列的实际大小。

    * > **易错点**：一定要分清容量（capacity，队列最多能容纳多少人）和大小（size，当前实际排队的人数）；有了 size 才知道数组里哪些位置还是空的，否则根本不知道队尾停在哪儿。

* **静态分配的固有上限**

    * 上限设得太低，在大型演唱会这类极端情况下仍会低估实际排队人数。

    * 上限设得太高，只有几个人到场时多分配的内存被白白浪费。

    * > **结论**：内存总量是有限的，你必须在编译代码之前就预先决定这个数据结构要开多大、会浪费多少空间——这挺不合理的，正是要放弃静态数组的理由。

```text
  同一摞东西，两种取用规则

  按栈用（Jack 的箱子）                按队列用（Lou 的衣柜）
  +------------------+                 +----+----+----+----+
  | 内衣 C（刚放）   | ← 取走 / 放回    | 1  | 2  | 3  | 4  |
  +------------------+                 +----+----+----+----+
  | 内衣 B          |                  ↑              ↑
  +------------------+                  队首          队尾
  | 内衣 A          |               早上从这取      晚上往这放
  +------------------+
   永远只穿得到最后放进去的那件
```

## 字典与键值对

* **字典（Dictionary）**

    * > **定义**：键值对（key-value pair）的集合，左侧的内容统称为键（key），右侧的内容称为值（value）。

    * 现实对应物：词典是单词与释义，电话簿是姓名与号码——第 0 周提到的电话簿就是一张由姓名和号码组成的字典。

    * 需要把一组数据与另一组数据关联起来时，键值对或字典会成为最常用的数据类型。

* **字典同样有多种实现**

    * 用数组实现会让容量受到固定大小的限制。

    * 换一种实现，查询速度可能非常快；再换一种，运行效率可能比较低。

    * 把通讯录设计成基于数组的实现、导致只能存 50 个联系人，这样的限制显然令人困扰，因此实际产品采用的是更动态的实现。

## 数组的连续存储与容量

* **数组（Array）**

    * > **定义**：一块连续的内存空间，可以依次存储多个值，索引从 0 开始。

    * 元素在内存中连续存储，可以靠指针自增一个接一个地走。

    * > **提示**：整数通常占用 4 个字节，但用 `sizeof` 来精确计算所需大小更保险；3 个 `int` 理论上是 3 × 4 = 12 字节。

    * 想加入第 4 个值时，理想做法是把它放到内存的下一个位置以保持连续，代码基本无需改动，只多占一点内存。

* **内存是一张画布**

    * 声明固定大小的数组时，系统只保证分配那一块连续内存，从概念上讲不会在它的右侧、左侧、上方或下方预留任何额外内存。

    * 右边看起来空着的格子不属于你，不能随便拿来用——那可能是别处正在使用的字符串数据，改动它只会破坏别人的数据。

    * > **结论**：在数组末尾追加一个元素是"复制 + 追加 + 释放"的完整操作，而不是一次赋值。

    * 内存画布上每一格代表若干字节，未被占用的地方堆着过去用过、现在可再利用的"垃圾值"。

```text
  ... [ 'H' ][ 'e' ][ 'l' ][ 'l' ][ 'o' ][ ... ][ 1 ][ 2 ][ 3 ][ ... ][ ... ]
                    别人的 "HELLO, world"        int list[3]
                                                   右边看起来空着，
                                                   但那些格子不属于你
```

* **静态分配与动态分配**

    * 静态分配就是字面意义上的硬编码，把大小永久写死，例如永远写 3。

    * 理想情况下应让结构根据需要动态扩容或收缩：向操作系统申请更多内存，不再需要时及时归还。

    * 把 50 改成 51、500、5000 再重新编译并不解决问题——程序应当在运行时直接向操作系统申请内存来容纳新数据。

## 动态内存与 realloc

* **malloc**

    * > **定义**：向操作系统申请一块动态内存，返回这块内存第一个字节的地址。

    * 返回的是地址，所以左边必须声明成指针：`int *list = malloc(3 * sizeof(int));`。

    * "分配了多少字节"这件事得由程序员自己记住，库不会替你记在变量里。

    * C 语言在某种程度上允许指针与数组互相转换，`list[0] = 1;` 只是 `*(list + 0) = 1;` 的语法糖，功能完全相同。

    * > **注意**：每次使用 `malloc` 之后都要检查返回指针是否为 `NULL`，否则内存不足时程序很可能崩溃并产生段错误。

* **内存泄漏（Memory Leak）**

    * > **定义**：丢失了某块内存的地址，程序再也无法访问它，也无法归还给操作系统。

    * 典型触发方式是直接写 `list = malloc(4 * sizeof(int));` 覆盖旧指针——这个 `list` 就像一根泡沫手指，这句话的实际含义是"现在让它指向这里"，而原来那块内存就此失联。

    * Valgrind 之类的工具可以发现这类问题；不修复它，随着时间推移计算机和程序最终会变得越来越慢。

    * > **提示**：程序退出时操作系统会自动回收内存，泄漏随之消失，但代码依然存在缺陷；软件常常连续运行数分钟、数小时甚至数天，及时清理才是最佳实践。

* **手写扩容的固定顺序**

    ```c
    int *temp = malloc(4 * sizeof(int));
    if (temp == NULL)
    {
        free(list);   // 先把第一块还回去，再报告错误
        return 1;
    }

    for (int i = 0; i < 3; i++)
    {
        temp[i] = list[i];   // 把旧列表复制到新列表
    }
    temp[3] = 4;              // 再加上第四个值

    free(list);
    list = temp;
    ```

    * > **易错点**：第二次分配失败时不能直接 `return 1`。第一块内存此时依然存在，必须先 `free(list)` 再返回——先释放、再返回这个顺序，是让你永远不会真正遇到内存泄漏问题的习惯。

    * 顺序上还必须先释放旧块，再让 `list` 指向新块，因为新列表已经接管了数据。

    * 把 `3` 改成 `4` 时其实一开始就该直接处理；这样写是假设程序运行一段时间后中途改变主意。

* **realloc**

    * > **定义**：`stdlib.h` 中用于重新分配内存的函数，比手写的"分配—复制—释放"那一坨更聪明。

    * 原块末尾正好还有空间时，就地扩展，指针根本不用变，一个字节都没搬。

    * 原块后面被别人占用时，在内存的其他地方重新分配一块更大的空间，并自动完成全部复制工作，返回值指向新块。

    * 整个内存里找不到足够连续的可用空间时，分配失败并返回 `NULL`。

    * realloc 知道该搬哪一块，是因为第一个参数传的就是之前 `malloc` 分配的地址；它知道该搬多少，是因为标准库会通过一张查找表记录此前的分配情况。

    * 用上 `realloc` 后仍然要检查 `NULL`、仍然要自己赋新值（`realloc` 并不知道你还想往列表里存什么），但可以删掉整个复制循环。

* **realloc 必须配临时变量**

    * > **易错点**：不能直接写 `list = realloc(list, 4 * sizeof(int));`。一旦失败，`realloc` 返回空指针但**不会**释放原来的内存块，覆盖 `list` 之后就丢失了指向原始内存块的指针，整块内存就此泄漏。

    * 结尾释放时应释放 `list` 而不是 `temp`：语法上都对，`temp` 确实仍在作用域内并指向同一块内存，但这在语义上是错误的——这个代码节点上真正需要关注的变量是 `list`，`temp` 是用后即弃的临时变量，超出程序员预期范围后继续使用它很容易引发问题。

## 链表结构与节点

* **链表（Linked List）**

    * > **定义**：链表中第一个节点的地址，一个指针就够了。

    * 链表里的节点并不住在链表变量里，它们各自散落在内存别处，链表变量手里攥着的只是"第一个在哪儿"这一个地址。

    * 动机很具体：如果内存各处都有可用空间、总和也足够，但没有任何一个连续区块能单独满足数组所需的大小，就该把这些可用内存拼接起来，而不是固守"所有元素必须连续存放"的限制。

    * 这正是 Python 中 `list` 在底层的样子；C 里把"能自动扩展和收缩的数组"叫做 `vector`，两者解决的是同一个问题，只是实现策略不同。

    * 链表把"数据在哪儿"这件事和"数据有几个"这件事彻底解耦了。

* **节点（node）**

    * > **定义**：包含数据和元数据的通用结构体，通常包括你关心的数值，以及一个指向下一个节点的指针。

    * 数据就是你关心的那个值；元数据是帮助你维护你所关心的数据的数据——所以宁可稍微"浪费"一点内存，也要为数据关联元数据。

    * 每个值分配两块内存：顶部是真正关心的数值，第二块是指向下一个值的指针；末尾节点的指针用 `0x0`（`NULL`），默认视为链表结束。

    * 数值字段通常 4 字节、指针 8 字节，合计很可能 12 字节，但结构体才是决定申请多少内存的唯一因素，用 `sizeof` 求答案即可，不必把它当成必须背下来的常数。

    * 节点在内存中的位置彼此相隔很远、字节间隔各不相同，所以不能靠自增一个接一个地跳过去，只能靠存的地址逐个走——像一张藏宝图或一条面包屑路径。

* **结构体定义与 struct 标签**

    ```c
    typedef struct node
    {
        int value;
        struct node *next;
    } node;
    ```

    * > **易错点**：指针那一行必须写成 `struct node *`，尽管 typedef 出来的名字明明就叫 `node`。编译器按从上到下、从左到右的顺序读取代码，读到花括号内部那一行时 `node` 这个名称在字面上还不存在，代码根本无法编译。

    * 两种解法：把 `struct node;` 提前声明到文件更靠前的位置，或者干脆在定义处保留 `struct node` 这个标签——与把函数原型前置是同一种做法。

    * 指针字段命名为 `next` 语义上很合理，但出于一些恼人的技术原因容易撞名，所以实际用的是不会撞名的说法。

* **箭头运算符**

    ```c
    (*n).value = 1;    // 先解引用指针进入结构体，再访问成员
    n->value = 1;      // 两个运算符合并后的等效写法
    ```

    * 箭头运算符 = 星号（解引用）加括号，再配合点运算符；它读作"访问节点 `n`，指向其数值字段或下一个节点字段"。

    * > **提示**：这里为什么非要那个括号？因为运算符优先级——写成 `*n.next` 时点运算符的优先级高于星号，含义会变成"先访问 `n` 的 `next` 字段，再解引用它"，完全不是我们想要的。括号不是装饰。

* **空链表与未初始化内存**

    * 一个 `NULL` 指针就是一条零长度链表的完整表示：没有第一个节点，也就没有第二个、第三个。

    * 只声明 `node *list;` 而不赋值，得到的是一个垃圾值——没有赋值操作，没人知道这个指针里到底存了什么。

    * `malloc` 交回的那块内存里，内容同样是随机值，因为那只是一块未经初始化的空间，谁知道它之前被用来存过什么。

    * 因此拿到新节点后要先填入数值，再把 `next` 指针初始化为空值。

```text
  list ──► [ 1 | 0x456 ] ──► [ 2 | 0x789 ] ──► [ 3 | 0x0 ] ──► NULL
            0x123           0x456           0x789
              │                │                │
           ┌──┴──┐         ┌──┴──┐         ┌──┴──┐
           │数据 │ │        │数据 │ │        │数据 │ │
           │  1  │ │ 下一个 │  2  │ │ 下一个 │  3  │ │
           └─────┘ └──┬─────┴─────┘ └──┬─────┴─────┘ └──┬────────┘
                       ▼                ▼                ▼
              每节点：数值 4 字节 + 指针 8 字节（实际大小以 sizeof 为准）
```

## 链表插入

* **前插（头插）**

    * 顺序固定：先 `n->next = list;`，再 `list = n;`。

    * > **易错点**：这两行顺序不可交换。先写 `list = n` 会把头指针改写，让节点 1 成为孤节点——两个指针短暂指向同一块内存后其中一个被覆盖，代码里已经彻底失去对它的追踪，这就是内存泄漏，在程序最终退出之前永远取不回来。

    * 先把新节点接到旧链表前面，再更新头指针，即使随后移除临时变量 `n`，整条链表依然连接完好。

    * 这个结构很适合一直往前加：1、2、3 可以一直保留在那里，新增的节点只要挑一块有足够空间的位置放好并更新箭头，无需复制数据。

    * 爆米花串的比喻：一根线串起所有爆米花，线的一头系在衣架上（那是链表变量），每颗上写着数字并拖着一根指向下一颗的短线（那是 `next`），把新爆米花塞到最前面后要重新系紧，一颗都不许掉。

* **有序插入要拆成四个独立问题**

    * 关键的提问方式不是"怎么维护有序链表"，而是"新节点可能要落在哪"。

    * 链表为空：直接让头指针指向新节点，完事。

    * 新值比最小值还小：前插。

    * 新值比最大值还大：遍历到末尾找到尾节点后插。

    * 新值介于中间：最麻烦的情况，"最小"和"最大"都已被排除后只剩它；需要同时维护新节点和它的前驱，要动两次指针外加一个 `break`。

    * 这样只需要解决四个独立的小问题，而不是一个庞大复杂的整体难题；用纸笔画图拼接节点很直观，但逻辑步骤一多就容易出错，导致一个或多个节点被孤立。

    * > **注意**：这部分微调非常繁琐，而且操作顺序确实至关重要，把"插到中间"更仔细地逐步推敲正是练习的价值所在。

* **尾插与排序的取舍**

    * 逐个插到末尾时链表碰巧按顺序排列，但这只是因为恰好选了 1、2、3；这种插入的复杂度是 $O(n)$，因为总要跑到末尾，反而更差。

    * 额外分配一个始终指向链表末尾的指针是可行方案，这点开销微不足道。

    * 无论用户以何种顺序输入（1233212、13、3312 或其他任意顺序）都保持有序，需要像手机通讯录那样自动排序，代价就是必须处理上面那四种情况。

    * > **易错点**：可别看到"倒序"就慌着去"修复"。每次插入都插在头部，最后一个插入的自然离头最近，这就是前插的直接后果。

## 链表遍历与释放

* **遍历**

    ```c
    node *ptr = list;
    while (ptr != NULL)
    {
        printf("%d\n", ptr->number);
        ptr = ptr->next;
    }
    ```

    * 额外引入的临时指针像多了一根泡沫手指，指向链表的起始位置；它并不指向链表变量本身，而是指向链表变量所指向的那个节点。

    * 循环条件是"只要 `ptr` 不为空就继续"；打印当前节点的值后，把 `ptr` 更新为 `ptr->next`，它最终变成 `NULL`，从而巧妙地让循环终止。

    * > **易错点**：别把 `ptr` 指向链表变量本身。`ptr = &list` 得到的是"链表变量住在哪儿"而不是"链表头节点住在哪儿"，那会立刻跑飞；正确写法是 `ptr = list`，因为赋值复制的是指针的值。

    * `for (node *ptr = list; ptr != NULL; ptr = ptr->next)` 与之完全等价；`while` 版本虽然略显繁琐，但"看一步"和"走一步"分成两行，可读性反而更强。

    * > **提示**：能用其中一种循环实现的功能，用另一种循环同样能实现，没有必要只用其中一种。

* **释放整条链表**

    ```c
    while (list != NULL)
    {
        node *tmp = list;   // 先记住自己，再取出下一个
        list = list->next;
        free(tmp);
    }
    ```

    * `free` 并没有那么智能，它根本不知道什么是链表，也不了解你的数据结构；即便调用了 123 次 `malloc`，最终也必须真正调用 123 次 `free`。

    * > **易错点**：顺序不能反。先 `list = list->next;` 再 `free(list);` 释放掉的是**下一个**节点，链表里会留下一个野指针；必须先把下一个节点救出来再放手。

    * > **易错点**：`free` 不是递归的，不会顺着 `next` 往下走。释放链表必须自己写循环，指望一次 `free(list)` 一劳永逸就是在泄漏。

* **把释放逻辑抽成函数**

    * 在循环内部 `malloc` 中途失败时——可能是在第二次或第三次迭代——前几次迭代分配的内存也必须回头释放，否则"释放所有已分配内存"这条原则就失效了。

    * 可以在文件底部写一段遍历并释放现有链表的代码，复制粘贴到错误处理分支里。

    * 但到需要复制粘贴代码的地步，很可能说明你的做法有问题。

    * 正确做法是单独实现一个删除链表的函数，这样既可以在程序开头调用，也可以在结尾调用，还能在任意位置任意多次调用。

    * > **结论**：为了实现数字 1、2、3、4 就要写 80 行代码，而且里面还藏着不易察觉的 bug——这本身就是"指针操作用临时变量兜底"的必然代价。

## 链表复杂度与二分查找失效

* **头插实现的复杂度账本**

    | 操作 | 复杂度 | 原因 |
    | :--- | :--- | :--- |
    | 插入 | $O(1)$ | 全部动作都发生在最左侧的几个指针上 |
    | 搜索 | $O(n)$ | 最坏情况目标在链表末端 |
    | 遍历 / 打印 | $O(n)$ | 要访问全部 $n$ 个元素 |
    | 删除 | $O(n)$ | 最坏情况目标在链表末尾 |

    * 严格来说插入不止一步，但只需要固定数量的步骤：分配内存、判空、填数值、把 `next` 指向 `list`、把 `list` 更新为 `n`。

    * 当前实现完全不关心链表的整体长度，即使链表有 1000 个元素，也只是在最左边改动几个指针，所以速度非常快。

    * > **结论**：只有插入操作是 $O(1)$，因为可以完全控制新元素的插入位置而不受元素实际值影响；搜索、删除、遍历全部是 $O(n)$。

    * 但把所有操作都算一遍账就会发现：有序链表的插入、搜索、删除全是 $O(n)$，动态性是以线性复杂度为代价换来的。

* **有序也救不了二分查找**

    * 数组的速度来自连续存储：先算出数组长度，除以 2 得到中间位置，再除以 2 得到四分之一位置，以此类推，因此非常适合二分查找。

    * 链表即使已经排序，即使能一眼看出中间位置大概在那里，计算机也无法直接跳过去。

    * 遗憾之处在于：虽然可以找到中间节点，但你必须从头遍历整个链表来确定长度，再根据算出的中间位置遍历一次，走到一半时停下。

```text
  4 个值的链表，二分查找找 6：

  ① 数长度：   1 → 2 → 3 → 4        从头走一遍，知道 n = 4     O(n)
  ② 算中点：   n / 2 = 2
  ③ 走到中点： 1 → 2               再从头走一遍，走一半停下     O(n)
  ④ 想在右半边继续二分：把整个过程再重复一遍                     O(n)
```

    * > **结论**：排序并不能把链表的搜索变成 $O(\log n)$。有序只是前提，而找到中点这个动作本身就要线性时间；一层一层地重复，光是找到中间节点就已经花掉了 $O(n)$。

    * 额外记录起始、中间和末尾位置的指针也可行，但边界立刻出现：二分还需要找到中间节点的中间节点，难道要为每个元素都维护一个指针吗？那样每个位置都要对应一个独立的存储地址，本质上就又回到了数组的形式。

* **双向链表**

    * > **定义**：指针可以双向移动的链表；单向链表则只通过节点之间的单一指针连接。

    * 它能简化一部分代码——不需要提前查看下一个节点来决定释放哪一个节点，或者决定新值插在什么位置。

    * > **结论**：但它本质上并没有改变运行速度，只是让代码编写起来稍微容易一些。

* **动态性是有代价的**

    * 用双倍内存来维护这个数据结构是可以接受的奢侈——想获得动态增长和收缩这样的好处，就必须付出代价。

    * 时间、空间、财务成本、人力时间以及其他各种资源，都是需要权衡的因素。

    * 链表带来动态性：不必提前决定大小、只在需要时分配、收缩就是释放节点，即使内存很碎片化也能更高效地利用。

    * > **结论**：代价是搜索、插入新元素、删除旧元素全部退化成 $O(n)$ 的线性复杂度——不仅占用了更多空间，速度还比数组慢；手机通讯录和栈队列显然都不是这么实现的。

## 数组与链表的取舍

| 维度 | 数组 | 链表 |
| :--- | :--- | :--- |
| 存储方式 | 元素连续紧凑存放 | 节点分散在内存各处，靠指针串联 |
| 查找 | 可二分查找，$O(\log n)$ | 无法有效二分，$O(n)$ |
| 插入 | 末尾追加要"复制 + 追加 + 释放" | 只改几个指针，无需搬数据 |
| 大小 | 分配时就固定，估错必须重新分配并全量复制 | 按需分配，可持续扩展，释放节点即收缩 |
| 内存占用 | 紧凑，一个整数 4 字节 | 每节点一个数值加一个指针 |
| 顺序 | 物理顺序即逻辑顺序 | 需要插入时自行维护有序 |

* **数组的长处与短处**

    * 长处是相对简单，而且速度确实非常快；连续存储意味着可以做非常简单的算术运算，从而实现对数级别的时间复杂度。

    * 短处是必须提前决定大小；申请得太小就必须重新分配，而把旧内存中所有数据复制到新内存需要花费时间，无论手动写 `for` 循环还是让 `realloc` 自动处理，这个过程都无法避免。

    * 目前处理的只是 3 个或 4 个值无所谓，但 300 万个值需要扩容时，就会浪费大量时间把数据从旧位置搬到新位置。

* **链表的长处与短处**

    * 只在需要时才分配内存，避免了预先分配过多空间的问题，不必担心分配不足或过剩导致浪费。

    * 节点一旦分配就可以保持原位，只需更新指针即可，避免了把数据在内存中搬来搬去的效率损失。

    * 短处就是搜索、插入新元素、删除旧元素的运行时间全部达到 $O(n)$，并且失去了从第 0 周开始就非常吸引人的二分查找能力。

* **下一步的方向**

    * 接下来的目标是把不同数据结构的优点结合起来——取数组之长、补链表之短，既保留数组的速度优势，又获得链表的动态特性。

    * 树是遇到的第一个二维数据结构：数组本质只是单维结构，链表虽然节点在内存中上下左右分散，逻辑上仍然只是单维连接。

    * 树引入了第二个维度，其中二叉搜索树能重新获得二分查找的能力，但存储方式比单纯使用数组更巧妙。

```text
                  grandparent          ← 根（root）
                 /          \
           parent              child
             |
        grandchild
```

## 二叉搜索树

* **二叉搜索树（Binary Search Tree，BST）**

    * > **定义**：每个节点都大于它左子节点的值、小于它右子节点的值（先假设没有重复值）。

    * 这个性质是递归的：对当前节点成立，就对子节点同样成立；节点 2 大于 1、小于 3 性质成立，节点 6 大于 5、小于 7 性质成立，到了叶节点也不会被违反，因为叶节点压根没有子节点。

    * 节点结构从"一个数值 + 一个指针"升级为"一个数值 + 两个指针"，分别指向左子节点和右子节点；每个节点关联三份内容——两份元数据加一份真正关心的数据。

    * 它可以看成链表的变体或混合体，只不过每个节点最多挂两个指针而不是一个，正是这个设计引入了第二个维度。

* **查找的高度公式**

    $$h = \lceil \log_2 N \rceil$$

    * > **结论**：二叉搜索树的高度是 $\log_2 N$，所以查找的时间复杂度是 $O(\log N)$。

    * 直觉是每走一步问题规模就砍掉一半，走完全程的步数就是这棵树的高度，而树高本质上是 $\log_2 N$。

    * $N = 7$ 时 $\log_2 7 \approx 2.8$，取整后高度基本在 2 附近；$N = 8$ 时 $\log_2 8 = 3$（因为 $2^3 = 8$），高度就是 3。

    * 插入是 $O(\log n)$，插到哪里取决于数值大小，但整条查找路径的长度与树高成正比；删除大致也是同一数量级。

    * 加一个新节点只需要更新几个指针，不需要像数组那样把内存里的东西全搬一遍；想插 8 它就准确地被放在那个位置，想插 5.5 也能清楚判断出它该待在哪儿。

```text
            4
          /   \
         2     6
        / \   / \
       1   3 5   7
```

* **递归搜索函数**

    ```c
    bool search(int number, struct node *tree)
    {
        // 基线条件：空树
        if (tree == NULL)
        {
            return false;
        }
        else if (number < tree->number)
        {
            return search(number, tree->left);
        }
        else if (number > tree->number)
        {
            return search(number, tree->right);
        }
        else
        {
            return true;
        }
    }
    ```

    * 四种可能一次判定：树为空返回 `false`；目标小于当前值就舍弃整个右子树、钻进左子树；大于则对称钻进右子树；等于则找到并返回 `true`。

    * 在总共只有四种可能的情况下还专门把"是否等于"拎出来另问一句是浪费时间；改成四条互斥分支才是好的设计。

    * 左子树和右子树本质上就是规模更小的树，把子节点直接当参数递归调用完全合理。

    * 目标数字压根不存在时会一路下探，落在某个叶节点上后，因为该节点既不是要找的数字、自己又没有左右子节点，`tree == NULL` 那一支就会被触发并返回 `false`。

    * 至此我们是在链表的基础上又改进了一次，赢回了一些性能，查找回到了 $O(\log n)$。

* **叶节点与退化**

    * > **易错点**：叶节点只是没有子节点，数据一个都没丢；它们不是被裁掉的残余，而是处在数据结构的边缘、"查到这里就不用再往下走了"的位置。

    * > **易错点**：二叉搜索树的"平衡"不是它自带的性质，而是插入顺序的副产品。顺序不对，定义照样满足，性能却全丢了。

    * 按 1、2、3、4、5、6 的顺序插入，为了保持定义只能一路挂到右边，得到的就是一条链表：动态性有了，时间复杂度却退化成 $O(N)$。

```text
  精心安排的插入顺序（平衡）      最糟糕的插入顺序（退化）

            4                    1 ──► 2 ──► 3 ──► 4 ──► 5 ──► 6 ──► NULL
          /   \                                    ↑
         2     6                        退化成一条链表，查找退化为 O(N)
        / \   / \
       1   3 5   7
```

    * 它并没有违反二叉搜索树的定义，只是一个又长又细、显然不平衡的形状；先前那棵漂亮的树是被精心安排出来的插入顺序。

    * 更高级的实现会在算法中内置结构调整机制，比如插入 3 时多花一点时间围绕这个节点做旋转，让 2 成为新根，1 和 3 挂在它下面；每次插入或删除都按需重新平衡，虽然多花一点时间但能避免退化成 $O(N)$。

    * 课程里不实现这些机制——问题是可以解决的，前提是别用最简单直接的方式去构建它。

* **内存账单**

    * 每个节点是一个整数加两个指针，大约相当于 16 到 20 字节；而在数组里一个整数通常只占 4 字节。

    * 也就是说，为了换取动态性和速度，内存占用涨了大约三倍。

    * 如今存储空间已经相当廉价，多占几个字节不算什么；但要是 700 万个数字，即使速度很重要，二叉搜索树也未必是最佳选择。

    * > **结论**：最终得根据实际使用场景判断什么因素更关键。

## 常数时间与哈希

* **常数时间 $O(1)$**

    * > **定义**：无论结构里存了多少数字、名字或者毛衣，查找或插入操作都只需要固定的步数——可能 1 步、3 步，甚至 100 步，而这个步数完全独立于实际存储的数据量。

    * 演进轨迹是：线性（一条直线）→ 对数曲线（把视野拉远看，在时间效率上已极具吸引力）→ 常数时间（位于单步或双步标记处的一条水平线）。

    * > **易错点**：从渐进复杂度的理论意义上说，任何算法的耗时仍会无限增长；但常数时间的**定义**决定了它永远不会改变，而这正是真正追求的东西。

    * 在手机里搜索联系人、在搜索引擎中查找信息时，系统都能以常数时间复杂度给出回应，无论后台实际存储的数据量有多大。

* **哈希（Hash）**

    * > **定义**：把一个（形式上无限的）输入值域映射到一个有限的值域上。

    * 分桶类比：把 52 张牌全部摊开逐一筛选很费力，也可以按类别分桶——把规模为 52 的问题拆成 13 个规模为 4 的子问题，每个桶包含一部分数值的子集。

    * 分桶之后再从 A 到 K 排序就轻松多了，因为每个桶里的元素已经具有相同特征，本质上就只是一些数字。

    * 哈希函数是决定某个输入值对应到哪个输出位置的数学过程，接收输入、输出它应归属的桶号。

* **按首字母的哈希函数**

    ```c
    #include <ctype.h>

    unsigned int hash(const char *name)
    {
        return toupper(name[0]) - 65;
    }
    ```

    * 先用 `toupper` 把首字母统一转成大写，因为要减去的是大写 `'A'` 的 ASCII 码 65，直接用小写字母的码值会导致数学运算出错。

    * 返回值落在 0 到 25（含）之间：首字母是 `'A'` 得 0，是 `'Z'` 得 25。

    * 例如 `"Mario"` 返回 **12**（M 是字母表第 13 个字母，而索引从 0 开始计数），`"Luigi"` 返回 **11**。

    * 英语世界中的人名数量是无限的，而该函数只能输出 26 种结果（0 到 25）——这就是把无限的定义域映射到有限的值域。

    * 参数加 `const` 表示：即使没有按值传递副本，也不允许调用者去访问并修改那个地址上的名字。

    * 返回类型收紧为 `unsigned int`，因为为数组设计的哈希函数应该返回一个从 0、1、2 开始向上的值，绝不能是负数。

    * > **易错点**：这段代码还没有加入错误检查机制，如果输入是非英文字符程序就会出错；这里暂且假设输入的都是标准的英文姓名。

* **哈希表（Hash Table）**

    * > **定义**：一个数组，其中每个元素都指向一条链表——链表与数组结合后的升级版数据结构。

    * 它堪称数据结构界的"瑞士军刀"，因为能非常高效地把键与值关联起来，因此常被用来实现字典；电话簿本质上就是一本字典，真正的英语词典也是大量单词及其定义的键值对集合。

    * 设置成大小为 26 的数组，就有 26 个桶分别对应字母 A 到 Z。

    * > **易错点**：桶里放的是链表的头指针，不是数据本身。名字本身活在内存里别处，哈希表只负责"门牌号"。

    * 插入时并不会把人名直接放进格子，而是在内存中创建一个新节点把它放进去，再挂到对应桶上，为以后其他同首字母的名字留出串连的空间。

```text
  哈希表 = 一个数组，数组的每个元素都指向一条链表

  [ 0]  A ──► (空)
  [ 1]  B ──► (空)
  [ 2]  C ──► (空)
   ...
  [11]  L ──► [Link | ·] ──► [Luigi | 0x0]        ← L 桶下有冲突，用链表串起来
  [12]  M ──► [Mario | 0x0]                      ← 期望位置
   ...
  [25]  Z ──► (空)
```

* **冲突（Collision）**

    * > **定义**：把无限的数据映射到有限的空间，那么根据定义就必然会产生大量的潜在冲突，比如多个以 M 开头的名字、多个以 L 开头的名字。

    * 覆盖掉原来的值、或者这个位置满了就往后顺次放，一开始也许管用，但整个结构很快变得一团糟，最终谁在哪个位置毫无规律可循，退化回了类似线性的结构。

    * 数组与链表结合的巧妙之处在于：用哈希函数把名字映射到目标位置（例如第 12 格），然后只用链表把它们串连起来；只要冲突数量不太多就能高效运行，而且至少无需删除数据、也无需破坏数据结构本身。

    * 现实中的货架分格也是同一套办法——按名字首字母把沙拉分配到 A–E、F–J、K–N、O–Z 四档；后来发现 A 区经常溢出到 B 区、B 区又溢出到 C 区，而 Q、Z 这类字母开头的词条几乎无人使用，于是干脆去掉字母表里的大部分字母、把剩下的桶扩大。

* **按首字母分桶的实际代价**

    * 如果只是一个从 A 到 Z 的链表，即使已经按字母顺序排列，查找 Zelda 也可能要从头一直遍历到末尾。

    * 在由链表组成的数组里，假设名字在 A 到 Z 范围内均匀分布，那么每条链表的长度理论上不会超过 $N$ 除以 $k$（本例 $k = 26$）。

    * > **结论**：写成大 O 就是 $O(N/K)$，确实更快，比链表快大约 26 倍；但高阶项的处理原则告诉我们 $K$ 是个常数，所以它仍然属于 $O(N)$ 的范畴——时间依然与数据集大小成正比，于是又一次偏离了常数时间的目标。

* **更"聪明"的哈希函数**

    * 改取人名的前三个字母作为哈希值能显著降低冲突概率；在这个小例子里没有其他名字以 "LIN" 开头，Link 因此有了专属位置，"LUI" 前缀同理让 Luigi 避开了冲突。

    * 但字母表中所有其他字母以及各种可能的组合又该如何处理？像 AAA、AAB、AAC 这类前缀在英语或游戏世界里根本没什么实际意义。

    * > **结论**：代价就是需要多得多的内存空间。使用哈希表的关键矛盾在于——需要设计一个**良好的**哈希函数，它应该比单纯取首字母更复杂一些，但又不能过于浪费，以免需要大量桶、导致内存占用过高。

## 字典树

* **字典树（trie）**

    * > **定义**：一种由数组构成的树形结构，名字是 "retrieval"（检索）的缩写。

    * 每个节点都可以看作一个由 A 到 Z 的字母组成的数组，索引范围设为 0 到 25，数组中每个元素都是一个指针，指向字典树中的另一个同类节点。

    * 插入机制是按名字的第一个字母找到数组中对应的位置，通过指针指向代表第二个字母的节点，再指向第三个字母，依此类推，从而隐式地存储所有名字。

    * 严格来说节点并不完全只是数组：它是一个大小为 26 的子节点数组，此外还可以挂上标记位或一个装着电话号码的 `person` 结构。

    ```c
    typedef struct node
    {
        struct node *children[26];  // 子节点数组：A-Z，每个元素指向另一个同类节点
        bool is_word;               // 某个名字在这里结束
        // 还可以再挂一个 person 结构：姓名 + 电话号码
    } node;
    ```

    * 最初它只是一个指向节点的指针，可以初始化为空指针，以明确表示尚未存储任何姓名。

* **名字是隐式存储的**

    * 插入 "toad" 后树里有 4 个节点，但代码里并没有存储字符串 "toad"——它是由"T 指针非空、O 指针非空、A 指针非空、D 指针此时为空"这条路径隐式构成的。

    * 沿路设置非空指针作为标记，还可以处理互为子串或超串的名称，比如 "Toadette" 在共享前缀之后继续延伸并在自己的终点打标记。

    * "Tom" 和 "Toad" 共享了 `T → O` 这段前缀，并没有复制一份新的 `[T]` 和 `[O]`，而是在复用同一个数组。

    * > **结论**：每个节点都对应名称的第 $i$ 个字母；通过空指针、非空指针以及布尔标志的组合运用，可以在这个结构中**隐式地**存储名称。

```text
  root ─[T]─► [O]─┬──► [A] ──► [D] ──► [E] ──► [T] ──► [T] ──► [E] ●  toadette
                  │                                  ● toad（D 处标记）
                  │
                  └──► [M] ──► [O] ──► [M] ●  tom

  Tom 与 Toad 共享 [T] → [O] 前缀，不复制新节点；● 表示名字在此结束
```

* **查找的步数**

    * 从根节点开始逐个字母处理：对第一个字母做哈希运算找到对应位置，检查该位置是否为空，非空就说明该字母隐含在其中，然后沿箭头继续前进。

    * 处理第四个字母 D 时看到了标记为真的布尔值，就确认 Toad 确实存在于这个数据结构中。

    * > **结论**：无论树里存了 3 个名字还是 300 万个名字，确认或否定 Toad 是否在其中总共只需要 1、2、3、4 步，基本可以看作是常数时间操作。

    * 步数只与名字长度有关，而名字长度存在一个合理的有限上限——游戏角色不太可能起一个长得离谱的名字，所以查找任何名字实际上都能在常数时间内完成。

    * 如果指针不只是布尔标记而是指向装着姓名和电话号码的实际人物结构，那么"这个数据集中 Toad 的电话号码是多少"同样能在常数时间内回答，键值对就这么存了下来。

* **不更频繁使用它的原因**

    * > **易错点**：字典树最大的问题是存在大量内存浪费，这与在哈希函数中看到的情况类似——这些数组中的大部分指针都只是空值、从未被使用。

    * 内存占用一路升级：从最初每个整数只占 4 字节的数组，到加一个指针的链表，到加两个指针的二叉搜索树，再到 26 个指针加一个布尔值或一个 `person` 结构。

    * 这样做不仅会拖慢计算机运行速度，还会造成远超实际需求的内存浪费。

    * 尽管在讨论的所有结构中字典树确实能达到 $O(1)$，但实际工程中更常被实现的是那个"瑞士军刀"哈希表——如果被困在荒岛上只能带走一种数据结构，人们很可能会选它。

## 数据结构成本对照

| 数据结构 | 查找 / 插入的代价 | 每个元素的内存代价 |
| :--- | :--- | :--- |
| 数组 | 插入可能需要重新分配，或把数据全部复制 | 每个整数 4 字节 |
| 链表 | $O(N)$，从头走到尾 | 一个数值加 1 个指针 |
| 二叉搜索树 | $O(\log N)$；插入顺序不巧会退化成 $O(N)$ | 一个数值加 2 个指针，约 16–20 字节，约 3 倍 |
| 哈希表（按首字母分桶） | 实际约快 26 倍，但渐进仍是 $O(N)$ | 桶数组加一条链表，比名字总数还多一点 |
| 字典树 | $O(1)$，步数只与名字长度有关 | 每节点 26 个指针加布尔标记，绝大部分为空 |

* **核心权衡**

    * 想获得动态增长和收缩这样的好处，就必须付出空间代价；想换来速度，就得消耗更多的空间。

    * 每个结构都解决了上一个结构的一个问题：数组解决了链表查找慢，链表解决了数组大小固定，二叉搜索树兼得两者，哈希表把常数时间往前推了一步，字典树则真正做出了常数时间。

    * 时间、空间、财务成本、人力时间以及其他各种资源，都是作为程序员或管理者需要权衡的因素，得判断哪些对自己最不重要、哪些最重要。

    * > **结论**：在代码里实现的一切——哪怕涉及晦涩的指针表示和解引用操作——本质上都是在把他人已提出的现实解决方案实现到代码中，并将其转化到新的应用领域。

* **配套练习**

    * 习题要求实现的是**哈希表**而不是字典树。

    * 还要实现自己的拼写检查器：把一个包含超过 10 万个英文单词的大型文件加载到内存，需要设计巧妙而高效的方法，并用提供的工具测量运行速度与内存使用情况。

    * 有序链表插入中"插到中间"那种最麻烦的情况，要求逐步分析清楚，因为指针的微调非常繁琐，而且操作顺序确实至关重要。
