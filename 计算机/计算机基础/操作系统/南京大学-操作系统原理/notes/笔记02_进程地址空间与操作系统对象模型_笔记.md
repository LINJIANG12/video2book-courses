# 进程、地址空间与操作系统对象模型

## 程序、进程与状态机

### 状态机模型

* **计算机（state machine）**

    * > **定义**：一台计算机就是一个状态机，它的状态就是内存（memory）与寄存器（registers）的全体。

    * CPU Reset 之后每一个寄存器的初值由手册规定好，随后 firmware 开始执行；在此之上操作系统是一段存在磁盘上的代码，被 firmware 加载进内存，所以操作系统本身也是一个普通程序在运行。

    * 状态转移的方式是取一条指令、执行、再取一条、再执行；除内存与寄存器外，机器还通过 RS232 串口、并行口这类接口与物理世界打交道。

    * 设备在总线上表现为地址与读写使能的组合，最终都归结为「送一个地址过去、读或写一个值」。

* **上下文切换（context switch）**

    * > **定义**：把一个进程当前的状态加载到 CPU 上运行，运行一段时间后换另一个进程的状态上来，从而实现时间片的轮转。

    * 每个程序是二进制文件，本身就是指令序列，因此可以把整份状态直接装载到 CPU 上；`P1`、`P2` 交替执行，在较长时间尺度上看就是并发。

    * 虚拟化（virtualization）、并发（concurrency）、持久化（persistence）是操作系统的三大主题，虚拟化讲的是如何把一台物理计算机抽象成很多台虚拟计算机。

* **用一个解释器把操作系统跑起来**

    * 思路是把每个程序当成一个状态机：为它准备一份 `CPU_state` 和一份 memory，主循环里挑一个进程出来单步执行一条指令，遇到 `ecall` 就按系统调用编号分发处理。

    * 调度用 round-robin：主循环维护进程数组，每次把指针加一、对进程数取模，公平地让每个程序往前推一条指令。

    * 系统调用编号放在 `a7` 寄存器里（例如 42 表示 putchar），参数放在 `a0` 里；`putchar` 不立即输出，而是先写进本进程私有 buffer，写满或遇到换行时才真正输出。

    * 这种模型下同一份程序可以加载多份，两份 `p2` 会打印出 1、1、2、2、3、3 这样的交替序列；执行更慢的那个程序（如打印数字更长的 `P1`）进度会被拉开，说明并发只是假象、推进速度并不相同。

### 程序与进程

* **程序（program）**

    * > **定义**：程序是对一个状态机的静态描述，是一串字节序列，像一份配方——从某处开始，依次做动作、调用系统调用。

    * 程序本身不持有运行资源；`p1.c` 这样的源码和编译出来的 ELF 二进制都只是描述。

* **进程（process）**

    * > **定义**：进程是正在运行中的程序，程序被加载运行时操作系统为它分配资源，它就成为一个进程。

    * 操作系统给进程分配的资源包括：一份自己的内存副本（每一个字节的值）、一份自己的寄存器现场，以及操作系统内部与它相关的状态数据（如进程编号、输出 buffer）。

    * 同一份程序可以加载多次，得到多个互相独立的进程；进程运行起来后，操作系统做时分复用，遇到系统调用就执行对应的契约。

    * 程序与进程的差别只在「静态描述」与「运行实例」：程序是语义，进程是这份语义正在被这台机器执行的那一份状态。

## 进程持有的状态

### 进程状态的清单

* **进程标识类状态**

    * `PID`：进程的编号；`PPID`：父进程的编号；`PGID`：进程组编号。

    * `UID` / `EUID` / `GID` / `EGID`：用户与组的身份标识。

    * `PPID`、`PGID` 属于历史遗留的字段。

* **运行信息类状态**

    * 进程启动时的命令行调用方式会被操作系统保存下来，所以用 `./proc-info`、`./././proc-info` 启动同一个程序，进程看到的 identity 会不同。

    * 调度信息（scheduling information）包括进程运行了多久、消耗了多少内存等一组整数；还有 nice 值代表的调度优先级、out-of-memory 相关的信息、内存映射信息。

    * 进程打开的文件，在操作系统看来就是它持有的操作系统对象的指针。

    * 操作系统维护的进程状态远多于进程自己能看到的内存与寄存器，本课程只涉及其中一部分，不涉及全部。

### 读取自身状态的途径

* **通过系统调用**

    * > **定义**：进程只能看到自己的内存与寄存器，一切关于自身、也就是这个状态机之外的信息，都必须通过系统调用取得。

    * 直接获取自身信息的系统调用有 `getpid`、`prctl` 等；要确认某段行为究竟走了哪些系统调用，用 `strace` 追踪得到完整日志。

* **通过 procfs**

    * > **定义**：procfs 是操作系统提供的一个文件系统，把进程与内核的信息以文件形式暴露出来，挂载在 `/proc`，每个进程在其中有以自己的进程号命名的目录。

    * `/proc/<pid>/cmdline` 记录进程启动时的命令行参数；`/proc/<pid>/status` 里能读到 `VmRSS` 这类字段，也就是进程占用的物理内存。

    * `/proc/self` 是当前进程自己的目录；进程想知道任何关于自身的事情，都可以先定位到自己的进程号，再进对应的目录查看。

## 进程创建

### spawn

* **spawn**

    * > **定义**：从程序的初始状态开始创建一个新进程的系统调用，参数是待执行二进制文件的路径以及传给它的参数。

    * 执行后系统里多出一个新进程，它与调用者构成父子关系（新进程的 PPID 等于调用者 PID）；Windows 上的对应 API 就是指定一个 `.exe` 文件并给 `main` 传参。

    * 在概念模型里，`spawn` 与「开局创建一个进程」的初始化动作做的是同一件事：申请一个进程结构体，为它准备内存与寄存器，并设置正确的初始 PC。

* **Unix 的选择**

    * Unix 没有采用 spawn 式的接口，而是给出 `fork` 加 `execve` 的组合；`fork` 负责复制状态，`execve` 负责把状态复位到另一个程序的初始状态。

### fork

* **fork**

    * > **定义**：把调用它的进程此刻的全部状态原封不动复制一份，得到一个与父进程在复制瞬间完全相同的新进程。

    * 复制的范围包括内存的每一个字节、寄存器的每一个字节，以及操作系统内部关于该进程的状态字节。

    * 不是完整的深拷贝：指向终端（tty）这类对象的指针只是把指针本身复制一份，于是父子进程以共享的方式持有同一个对象——这正是子进程默认输出到同一个终端的原因。

    * 实现只需几行：找一个空闲的进程结构体，把旧进程的全部信息整份拷过来，再区分两侧的返回值。

* **fork 的返回值**

    * 父进程一侧返回新创建的子进程的 pid；子进程一侧返回 0；返回 -1 表示失败，需要做错误处理。返回类型是 `pid_t`。

    * 标准写法是判断 `pid == -1` 走错误处理、`pid == 0` 走子进程分支、否则走父进程分支。

    * 这是区分父子两条执行路线的唯一手段；复制之后两份状态机都会经过同一个程序点，只要按返回值分叉就能让它们走不同逻辑。

    * > **易错点**：子进程拿到的 0 不是「fork 成功」的状态码，而是「你是孩子」这个身份标记；父进程拿到的那个数才是孩子的编号。

* **fork bomb**

    * `while (1) fork();` 的效果类似链式反应：一个变两个，两个变四个，指数级增长，瞬间耗尽系统资源。

    * 在进程表是静态数组的模型里，进程数量上限消耗光之后就再也创建不出新进程，系统直接卡死。

    * 现代 Linux 内核有 out of memory 机制：整个系统没有内存与资源时会杀掉一部分进程，并且能识别出是哪个进程组的问题，因此能把 fork bomb 处理掉。

### fork 与输出缓冲

* **libc 缓冲区的两种模式**

    * 标准输出对着终端时默认是行缓冲：看到换行就执行一次 `write`，把缓冲区里的内容交出去。

    * 标准输出是文件、管道或者其他东西时会更加激进地缓冲，攒够若干 KB（例如 4KB、8KB）才一次性写出，这样 `write` 系统调用更少、它认为性能更高。

* **缓冲区是进程状态的一部分**

    * fork 复制进程状态时缓冲区一起被复制，于是同一段文本可能被写出多遍。

    * 一个两次调用 fork、两次打印 Hello 的循环，在终端上得到 6 个 Hello，重定向到文件或管道则得到 8 个 Hello。

    * 逐程序点推演（把循环展开成 i=0、fork、printf、i=1、fork、printf 六步）：第一次 fork 产生两份，第一次打印各出一个共 2 个；第二次 fork 让两份变四份，第二次打印各出一个共 4 个；2 + 4 = 6。

    * 全缓冲下多出的 2 个来自复制的缓冲区：第一次 fork 发生在任何输出之前，两份缓冲区都是空的；第一次打印只往各自缓冲区放了 "Hello"；第二次 fork 把带着 "Hello" 的缓冲区一起复制成四份；第二次打印后每份缓冲区变成 "HelloHello"，退出时四份各自写出，于是数出 8 个。

    | 程序点 | 终端（行缓冲） | 文件 / 管道（全缓冲） |
    | :--- | :--- | :--- |
    | 第一次 fork | 两份，缓冲区空 | 两份，缓冲区空 |
    | 第一次打印 | 立刻 write，合计 2 个 | 只进缓冲区，各带一个 "Hello" |
    | 第二次 fork | 四份，缓冲区仍为空 | 复制缓冲区，四份各带一个 "Hello" |
    | 第二次打印 | 立刻 write，合计 4 个 | 各变成 "HelloHello" |
    | 合计 | 2 + 4 = 6 | 退出时一次写出 4 份 "HelloHello" = 8 |

* **看不到输出的原因**

    * 打印了带换行的 "Hello" 再崩溃，能看到 Hello；忘了打换行再崩溃，什么也看不到。

    * 即使程序后面停在死循环里，也百分之百确定 printf 执行过，却依然看不到输出；原因是行缓冲要看到换行才 `write`，而进程没有正常退出，缓冲区没有机会 flush，字符跟着进程一起消失。

    * 能被肉眼看到的、真正写进操作系统的输出统统通过 `write` 系统调用，也就是说在 `printf` 与 `write` 之间还夹着一层库函数。

### 用子进程隔离崩溃

* **用共享内存收集子进程输出**

    * 对每一个注册的测试用例，先用 `mmap` 创建一块共享 buffer，它既能给子进程喂输入，也能收集子进程的输出，于是子进程的输出可以被拿来 assert。

    * 父进程等子进程结束后读这块 buffer，再检查输出是否符合预期。

* **把可崩溃的用例放进子进程**

    * 每个用例都在自己的子进程里跑，子进程给自己设一个闹钟当 timeout，超时就被杀掉，写出的死循环也能被逮住。

    * `assert` 会把整个程序打崩，但崩掉的只是那个子进程，父进程毫发无伤，可以继续跑下一个用例、最后统一汇报结果。

## 进程复位与销毁

### execve

* **execve（execute with vector and environment）**

    * > **定义**：把当前进程的状态就地全部销毁，替换成另一个程序的初始状态，也就是状态机的复位。

    * 名字里的 `v` 代表参数向量（vector），`e` 代表环境变量（environment）；它一次能往新程序里送命令行参数向量与环境变量两样东西。

    * 它是 Unix 世界里唯一能执行程序的系统调用，因此任何程序被 `strace` 追踪时，看到的第一条系统调用都是 `execve`。

    * 如果没有 `execve`，系统里只能不停 fork 出同一个程序，永远只有一个程序可跑。

* **常见的启动流程**

    * `fork` 复制出子进程、`execve` 让子进程变成另一个程序、`exit` 结束进程，三者配合完成原生启动；父进程可以与子进程分离，也可以用 `waitpid` 等它结束。

    * 需要按时、按周期启动的程序，单靠 fork 做不到，必须借助 execve 把新程序装载起来。

### 命令行参数与环境

* **main 函数的完整签名**

    * 完整形态是 `int main(int argc, char *argv[], char *envp[])`：`argc` 是参数个数，`argv` 是参数向量，`envp` 是环境变量。

    * `argv[0]` 总是被调用命令的名字，敲 `./a.out 1 2 3` 时 `argv[1]`、`argv[2]`、`argv[3]` 分别是 1、2、3；这些就是进程在 procfs 里那一项 command line 的内容。

    * 环境变量除了从 `envp` 取，还可以通过 C 的全局变量 `environ` 直接访问；完全不用这两个参数也合法。

* **PATH 的解析过程**

    * `PATH` 是用分隔符切开的路径列表，找一个可执行文件时从第一个目录开始找，第一个目录里找到就运行那一个，没找到就试下一个，直到成功。

    * 把 `PATH` 设成 `.` 就找不到 gcc；把 `PATH` 改回正确值 gcc 立刻恢复，说明程序确实从环境变量里读 `PATH` 并据此解析路径。

    * 汇编器等外部工具的运行过程可以在 `strace` 里看到：依次在每个目录下查找，失败返回 -1 与 `ENOENT`，一直往后试直到某一次 `execve` 成功。

    * `PWD` 表示当前工作目录；`TERM` 表示当前终端类型，一台 foot 终端会伪装成 `xterm-256color` 这样的兼容终端。

### 环境变量的继承风险

* **环境变量的继承链**

    * 环境变量在 fork 时被继承，在 execve 时也必须传一份给新程序；用 `execl` 这类库函数执行程序时默认继承环境变量。

    * 复位一个状态机时，操作系统内的资源本来就大部分是继承的，环境变量只是其中最先暴露问题的一项。

* **把密钥放进环境变量的风险**

    * 把 API key 放在环境变量里，就意味着所有子进程都拿到了它；行为不端的子进程可以把 key 泄露出去。

    * 在 `.bashrc` 里 `export` 密钥让所有应用可用的做法很糟糕；一旦这样做过应当尽快把密钥禁用。

### 进程的销毁

* **exit**

    * > **定义**：销毁当前进程，让这个状态机从世界上消失，是状态机的销毁接口。

    * 进程一旦 exit，就再也没有任何感知这个世界的机会，可以类比全身麻醉。

* **三件套构成的世界**

    * 有了 fork 复制、execve 复位、exit 销毁这三个系统调用，就能构造出整个计算机世界里可见的全部 Unix 进程，也就有了进程树。

    * 常驻后台的小程序同样只是这三件事的组合。

## 进程树与亲属关系

### 进程树

* **进程树**

    * 不管是 fork 还是 spawn，创建出来的进程都与调用者构成父子关系，于是所有进程构成一棵树；一个进程能继续 fork，子进程也能再 fork。

    * 一个终端模拟器进程之下可以有 shell，shell 之下再有其他程序；这种层级就是进程树的实际形态。

* **共同的祖先**

    * `pstree` 显示所有进程有一个共同的祖先（在 Linux 上表现为 1 号进程）；操作系统启动后最初只有一个 1 号进程，用户看到的任何东西都是由它一级一级孵化出来的。

    * 早期 Unix 里 fork 是创建进程的唯一途径，今天的创建方式更多了；实现操作系统有一个规律：每增加一点点功能都会带来很多麻烦。

### 孤儿与托孤

* **托孤（reparenting）**

    * > **定义**：父进程先退出时，孤儿进程被 1 号进程收养，成为 1 号进程的孩子，从而保证每个进程的 `ppid` 总是合法的。

    * 1 号进程永远不会终止；孤儿向 1 号进程发送的任何信息都会被直接忽略。这是今天广泛使用的 workaround。

* **编号复用**

    * 进程编号是有限的，旧编号过一段时间会被新进程复用；如果孤儿仍然记着旧编号，它的父亲就会莫名其妙换人。

    * Linux 里另有一个专门的子系统处理 unique pid，用另一种方式保证进程标识符唯一。

    * 让进程树随机退出若干节点的实现在执行后可以观察到：有些进程的父亲被杀死，它们就变成 1 号进程的孩子，并且还能继续有自己的子进程。

## 进程地址空间

### 地址空间的本质

* **进程地址空间（address space，虚拟地址空间）**

    * > **定义**：操作系统为每个进程提供的一套独立的、连续的虚拟内存地址范围。

    * 需要它的理由有三条：隔离与保护（各进程内存互相不干扰，两个进程写同一个地址实际写到不同物理内存）、便于扩展与管理（程序可以以为自己占有一大片连续内存）、以及在隔离的前提下允许有限的共享。

    * 等价的直观理解是：进程能访问的全部字节序列就是它的地址空间，因为 `load`、`store` 本质上都是按字节寻址地取一个值或写一个值。

    * 在编程语言里访问地址空间靠指针；任何一个 64 位整数都是合法的指针值，但在操作系统意义上未必允许访问——第 0 页默认不可访问，空指针被解引用立刻崩溃，这是为了让你知道程序里有 bug。

* **三条公理**

    * 机器永远是对的：指令集的实现遵照规格说明，即便有 bug 也是稳定的 bug，可以查明原因。

    * 你没有测试过的代码都是错的。

    * 但凡能想到一件对人有意义的事，就一定能在计算机上做到；计算机科学是人造科学，从逻辑门开始完全由人设计，所以不存在魔法。

    * 推论是：地址空间里每一个字节应该是什么，都应当是规定好的、可以理解的。

### 字节的含义与来源

* **字节不带类型**

    * 字节就是字节，它是什么取决于指令把它解读成什么：PC 指在它上面就被译码执行，`load`、`store` 命中它就当作数据读出或写入。

    * 类型由 CPU 的指令集体系结构决定，不是字节自带的。

* **位置由链接与可执行文件格式决定**

    * `readelf -a` 看到的 program header 里有许多 `PT_LOAD` 段，就是要被加载进地址空间的东西。

    * 静态链接的二进制要加载到完全确定的地址；PIE（position-independent executable，位置无关可执行文件）可以被加载到地址空间的任意位置，由操作系统决定放在哪儿。

    * text（代码）、已初始化数据、未初始化数据、只读数据各自落在什么位置，由链接、可执行文件格式以及操作系统的地址布局随机化共同决定。

* **地址空间随机化（address space layout randomization，ASLR）**

    * 程序每次被加载到一个略有不同的地址，但都在相近的区间内，目的是让缓冲区溢出之类的攻击更难实施。

    * 用 gdb 运行时每次地址都一样，是因为调试器关闭了随机化。

* **加载器与 ABI**

    * 程序真正运行起来后，每个字节是什么由操作系统的加载器与 ABI 共同规定：它们决定进程初始状态里有什么。

    * 进程初始化好后有一个初始堆栈，栈里放着所有参数与环境变量，还有一些别处会用到的信息，例如随机数种子——这在 System V 的 ABI 里叫辅助向量（auxv）。

### 真实布局

* **各区域的排布**

    * 从一个静态链接的、正在死循环的程序看，低位有一段可读可执行区域，来源标着 file mapping，映射的正是该程序自身；再往上依次是数据段与 BSS 段，最高处是栈。

    * 文本段是代码，数据段是已初始化的全局变量，BSS 是未初始化数据；`int x = 1` 中的 1 会出现在二进制文件里，`int x = 0` 或超大数组则待在 BSS 段。

    * 高地址处接近栈的位置还有两段映射，它们地址比栈低，分别叫 `vvar` 与 `vdso`；栈向下生长。

    * 栈与数据区之间存在谁碰谁崩的 dead zone。

* **vvar 与 vdso**

    * > **定义**：内核在每个进程地址空间里放进的一段代码页（vdso）与相邻的一页数据（vvar），用来让某些系统调用不必陷入内核就能完成。

    * 典型用法是 `gettimeofday`：操作系统维护秒级的墙钟时间，加上 CPU 里一个非常精密的计数器，就能在用户态算出「现在几点」。

    * 同理可以把当前 CPU 编号、乃至进程号放在用户态能读到的页里，让 `getpid` 也不必进内核。

    * 即使是用最小方式链接出来、只有一个节的程序，地址空间里也不只有栈和自身，还会多出这两样东西。

### 观测地址空间

* **/proc/<pid>/maps**

    * 打开任意真实进程的 `/proc/<pid>/maps`，能读到完整的内存区域：每一块从哪里开始、到哪里结束、访问权限是什么。

    * 从文件映射来的区域能看到被装进地址空间的库的各个部分，也能看到 `vvar` 与 `vdso`。

* **探针程序**

    * 用指针分别指向代码、数据、栈并打印地址，可以拿到 `main` 的地址（落在某一固定区间）、全局变量地址（比代码略高）、数据段地址与很高的栈地址。

    * 任何合法符号都能变成指针，把 `main` 的前若干字节打出来并与二进制文件核对，能得到一致的指令字节（例如 ARM64 小端下的 `fd 7b bd a9`）。

    * 扫描整个地址空间可以找出哪些位置能合法 `load`、哪些不能，从而把「地址空间就是可访问字节序列」这件事落到实测上。

### 内存修饰符

* **const 与 volatile**

    * > **定义**：两者都用来修饰「有内存地址的东西」，`const` 管只能读不能写，`volatile` 管对这段内存的访问不许被优化。

    | 修饰符 | 修饰内存地址时的含义 |
    | :--- | :--- |
    | `const` | 这段内存只能读，不能写 |
    | `volatile` | 对这段内存的访问一律不允许被优化 |

    * 要连指针本身一起修饰，就写成 `volatile char *volatile p;`；凡是能出现 `volatile` 的位置都能出现 `const`。

* **volatile**

    * > **定义**：禁止编译器把对该内存的访问优化掉。

    * `*p;` 这一行读出来的值没有赋给任何人、也没有传进系统调用，编译器认为它没有可观察效果就会把整行删掉；加上 `volatile` 这次读才真的发生。

## 修改地址空间

### MMU

* **内存管理单元（memory management unit，MMU）**

    * > **定义**：挡在进程与物理内存之间的地址翻译硬件，操作系统通过配置它决定进程能看到什么。

    * 可以把它理解成操作系统给用户态进程强制套上的一副摘不掉的 VR 眼镜：进程只能用自己地址空间里的计算、`load`、`store` 和系统调用，不能配置 MMU、不能执行特权指令。

    * 因为所有访存（包括取指译码）都要经过它，操作系统可以让某个 `load`、`store` 产生异常，也可以把它路由到任意一个物理页面上。

    * 想让一个地址被访问就配置成可访问，想拒绝就配置成不可访问；「分配内存」这类系统调用正是建立在这个能力之上。

* **视野只有几个字节**

    * `load`、`store` 一次只能看到几个字节，取一条指令也只能读到一条指令的长度。

    * 因此操作系统修改地址空间时只做标记，真正等到访问某一页时才把物理页交出来。

### brk 与 sbrk

* **brk / sbrk**

    * > **定义**：手册上功能写作 change data segment size，是最早能改变进程地址空间的系统调用。

    * 早期可执行文件的布局只有 code、data、bss 三段，可访问内存的上界叫 break；break 之后的内存不合法。

    * 想要更多内存就把 break 往上移，想释放已用过的部分就把 break 往下移。

* **早期可执行文件的段**

    | 段 | 内容 |
    | :--- | :--- |
    | code | 代码，也就是指令 |
    | data | 初始化过的数据，例如 `int x = 1` 里的 1 |
    | bss | 没有初始化过的数据 |

    * 这个模型只够覆盖数据段增长一种需求，今天已由更通用的 `mmap` 取代。

### mmap 与 munmap

* **mmap（memory map）**

    * > **定义**：在地址空间上添加一段合法的地址空间，并配置它的大小、来源与权限。

    * 它做的事就是从地址空间里找一块出来，可以指定大小、指定用途与权限；用途可以是新分配一段内存，也可以是映射某个文件的一部分。

    * 写起来只有几行的代码，申请 8GB 只要 1.62 毫秒返回，返回的指针可以随便读写——2GB 处写 1、4GB 处写 2、7GB 处写 3 都合法。

    * > **易错点**：`mmap` 返回成功不等于物理内存已经就位；它登记的是「这块地址归你」，物理页要等你真的 `load`、`store` 到那一页上才落到手里。8GB 之所以瞬间返回，是因为它一页都没真给。

    * 用 `strace` 能看到那一行确实是 `mmap`，权限为可读写，映射标志是 `MAP_PRIVATE` 与 `MAP_ANONYMOUS`，长度 8GB，返回值与程序打印出的地址完全一致。

* **munmap**

    * > **定义**：回收 `mmap` 建立的映射，可以整段回收，也可以只回收其中的一部分。

    * 例如用匿名映射要了 1GB，还可以把前面 512 兆单独 `munmap` 掉；整个地址空间的映射关系都可以随意修改。

### mprotect

* **mprotect**

    * > **定义**：修改一段已经持有的内存的访问权限。

    * 典型用法是把只读内存改成可读写，或者把 `mmap` 分配来、`malloc` 分配来的可读写内存改成可执行，从而让运行时动态生成的代码可以跳进去执行。

    * 为了安全，普通数据页通常不可执行，避免 PC 不小心跳进数据区执行到恶意代码。

    * > **提示**：同一段字节，PC 跳进去当指令取就是代码，按数据 `load` 出来就是数据；区分它们的不是字节内容，而是所在页的权限标记。

* **即时编译器（just-in-time compiler，JIT）**

    * 后端把较慢的脚本语言一边运行一边编译成机器码，生成后需要 `mprotect` 把存放代码的页标记成可执行，才能跳转过去继续执行。

    * 浏览器里的 Java、JavaScript 引擎就是最典型的例子，都依赖这一组与内存映射相关的功能。

### mmap 的用途

* **一次性申请极大内存**

    * 一台总共只有 8GB 物理内存的机器上，可以直接向操作系统要 8GB；这张饼画得比物理内存本身还大，而完成只需一瞬间。

    * 映射的大小几乎没有任何限制，可以分配一块和物理内存一样大的内存随便访问。

* **把文件与设备映射进来**

    * `mmap` 多出一个文件描述符参数：先 `open` 打开文件，再用 offset、length 把文件的一部分直接映射到进程地址空间里。

    * 可以把整块磁盘映射进来。左移 10 位是 KB 级、左移 20 位是 MB 级、左移 30 位是 GB 级，所以 `128 << 30` 是 128GB；32 位机做不了这件事，64 位机可以把 1TB 的设备直接映射到内存里。

    * 映射后它就是一个指针，用 `memset` 就能把整块磁盘的内容抹掉，这类操作极其危险，设备还原卡也未必挡得住。

    * 内存映射 I/O（memory-mapped I/O）也是这条路：把 `/dev/gpiomem` 这样的设备文件映射进来，就能用一个指针写 0 和 1 控制某个引脚。

* **共享内存**

    * `shm_open` 返回的文件实际上是一段共享内存；另一方拿这个文件描述符配上 `mmap`，就能让多个进程共享同一段内存。

* **msync**

    * > **定义**：把一段映射内存里写进去的数据同步到被映射的文件上。

### mmap 的参数

* **mmap 接收的参数**

    | 参数 | 作用 |
    | :--- | :--- |
    | `address` | 可以指定一个期望的地址，但只是建议；该处已有数据时会腾挪，不保证从这个地址分配，另有 flag 可以强制在指定地址分配 |
    | `length` | 要申请的这段内存映射的长度 |
    | 权限 | 为这段映射分配权限，例如可读、可写、可执行 |
    | 映射方式 | 匿名（anonymous）相当于分配一大段初值全 0 的内存，也可以给出文件描述符与 offset，把文件的一部分搬进地址空间 |

* **三者构成全部地址空间**

    * 进程里看到的一切——第三方库函数、`malloc` 分配的内存、可执行文件里指定的段——理论上都可以用 `mmap`、`munmap`、`mprotect` 这一组系统调用实现。

    * 有 map 就有 unmap，有 unmap 就还有改权限的 `mprotect`，这三个系统调用构成了进程所有的地址空间。

## 入侵进程地址空间

### 调试器的断点实现

* **断点的三步**

    * 先把放着目标指令的那一页从只读可执行改成可读可写可执行。

    * 把目标指令改掉——x86 上通常替换成一字节的 `int 3`。

    * 让程序继续执行，PC 走到这条 `int 3` 就陷入操作系统，由 `ptrace` 把这个陷阱事件截获，控制权转交给调试器；调试器再把指令 patch 回去，然后放它继续跑。

* **需要两个系统调用配合**

    * 改目标页的权限需要 `mmap` 那一组内存相关系统调用，拿到另一个进程陷入内核的事件需要 `ptrace`；是这两者合起来才能修改另一个进程的内存。

    * 能从命令行接受一个进程号、解析它的地址空间并读出里面的数据，本质上就已经具备调试器的核心能力。

### 扫描内存的修改器

* **多轮扫描定位变量**

    * 第一轮扫描整个内存，把值等于当前经验值（例如 4950）的内存单元全找出来，会得到上百个候选，因为代码与数据里也可能偶然是同一个数。

    * 改变这个值之后再只回头看那些候选：值跟着变的极可能就是目标变量，值没变的是指针之类的无关单元，可以排除。

    * > **易错点**：候选里可能包含某个指针的一部分，把它当成经验值改掉会让指针飞掉、程序立刻崩溃，所以要先靠多轮观察收敛范围再动手。

* **读写另一个进程的内存**

    * `/proc/<pid>/mem` 这个文件的内容就是该进程整个的地址空间，文件大小与地址空间一样大。

    * 用 `lseek` 把文件游标移到目标位置，然后 `read` 或 `write` 就能读写那段内存；打开这个文件需要 root 权限。

    * 按数据宽度搜索（16 位程序就按 16 位宽度搜）实际上就是地址空间扫描；一轮扫描可能命中数百个位置，随便改会破坏进程状态。

    * 如果变量不是固定在某个地址上，而是每轮逻辑更新都新建一个状态对象，地址就会变，扫描法会失效，这时必须真正理解程序语义。

### 改变时间感知

* **时间感知的来源**

    * 程序只能做 `load`、`store` 与计算，要感知时间必须通过操作系统，相关调用是 `gettimeofday`、`sleep`（或 `usleep`）、`alarm`。

    * 在这几个函数的入口插一个断点，或者干脆把它们替换成自己的实现，就可以改变程序对时间的感知。

* **虚拟时间轴**

    * 睡眠与闹钟的时长要缩短（参数除以倍数），而「现在几点」的读数要往前跑：启动时记下 $T_0$，让 `gettimeofday` 返回 $T_0 + (T - T_0) \times 10$。

    * 两边配合起来程序才会看到一条自洽的、被加速的时间轴；一次移动的计算耗时相比睡眠耗时很小，所以可以一直加速到某个极限为止。

### 硬件旁路

* **总线级劫持**

    * 更早的个人电脑没有 MMU，作弊设备直接劫持物理内存：卡带与主机之间的总线上插入一段可编程逻辑，抢下 firmware 的第一跳。

    * 它维护一张查表式的匹配表，规则是「当地址等于 X 并且数据等于 Y 时，把数据改成 Z」；作弊码是一组字符，被写进这张表。

    * 这类设备需要为每个游戏做逆向工程，本质是在内存意义上给卡带打补丁；改了 `lives = 3` 这个立即数就能得到 99 条命。

* **绕过操作系统的采集**

    * DMA 外挂把自己挂在内存总线上，持续做 memory copy，按固定频率（例如每秒 30 次）把游戏内存镜像到另一块 FPGA 板子或另一台机器上，完全不经过操作系统接口，几乎无法预防。

    * CXL 这类高速内存可以做成双写镜像：写入先落 DRAM 本体，再经第二个接口送到镜像副本，用于数据中心做多副本容错，同样也能用做旁路采集。

### 观测与写入接口

* **/proc 下的两个关键文件**

    * `/proc/<pid>/maps` 给出整个地址空间的映射情况；`/proc/<pid>/mem` 就是该进程的整个地址空间本身，文件大小与地址空间一样大。

* **能观测带来的能力**

    * 只要进程能注视另一个进程的地址空间，就能实现调试器乃至游戏外挂这类工具。

    * 能截获一个程序的控制流或数据流、又能改动它任意一个内存值时，就可以在合适的入口点插入自己的代码去改变它的行为，这是各类游戏外挂的共同原理。

## 文件与文件描述符

### 文件对象

* **文件（file）**

    * > **定义**：文件是一个有名字的数据对象，它的模型就是一个字节序列。

    * 字节序列足够普适：它可以表示数据流（键盘每按一键就追加一条记录）、表示数组（图片、JSON 都可以变成数组）、表示网络上传来的内容（页面一个字节一个字节发给你，前面还有头部与空行）。

    * 打印机、终端、显卡、锁、管道都可以假装自己是文件；如果所有东西都是文件，就能用同一套工具处理它们。

* **内核里的打开文件**

    * > **定义**：内核里表示一个「被打开的文件」的结构，包含一块缓冲区、它的长度、以及当前写到哪儿的偏移。

    ```text
      struct file {            /* 内核里一个“被打开”的文件 */
          char  *buf;          /* 缓冲区 */
          size_t length;       /* 这个文件有多长 */
          size_t pos;          /* 现在写到哪儿了 */
      };
    ```

    * 所谓写一个字符到文件，在内核看来就是往缓冲区当前位置填一个字节，然后把写指针往后推、把长度更新。

    * 这个结构可以直接嵌进进程结构体，于是最小模型里的 `putchar` 与操作系统实现文件的方式是同一件事；从标准库的角度看就相当于 `struct FILE`。

### 文件描述符

* **文件描述符（file descriptor，fd）**

    * > **定义**：应用程序用来访问操作系统对象的编号，是一个指向操作系统对象的间接指针。

    * 进程本身只有内存与寄存器，拿不到内核里那个指向文件结构体的指针，所以只能用一个整数编号，并且必须通过系统调用把这个编号传下去，不能解引用。

    * 因为 Unix 的设计是一切皆文件，文件描述符其实就是 everything descriptor。

    * 最早的最小程序向终端输出字符用的 `write(1, buf, size)`，第一个参数就是这个编号；编号为 1 的默认就是标准输出。

    * 编号 0、1、2 在进程刚启动时分别指向标准输入、标准输出、标准错误输出。

* **使用方式**

    * 进程不能解引用这个编号，但可以在系统调用里指定它：`read` 0 就表示从 0 号对应的文件读。

    * 这一点和 x86 的 I/O 端口类似：要先指定一个端口，再往端口里写数据。

### 文件相关的系统调用

* **基本操作**

    * `open` 相当于在进程里新分配一个指向文件对象的结构体；`close` 把这个结构体丢掉，不再指向那个文件。

    * `read`、`write` 就是按偏移量读写字节并推进偏移：写一个字节、游标后移一格，再写一个、再后移一格。

    * `lseek` 全名是 reposition read/write file offset，用来重新摆放读写位置；起点有三个宏：`SEEK_SET` 从头算、`SEEK_CUR` 从当前位置算、`SEEK_END` 从尾巴算。

    * `dup`（duplicate）再创建一个新的打开文件结构，指向同一个文件。

    * > **提示**：`struct FILE`、`fopen`、`fread` 属于用户态库的抽象，是后来加的一层；先有系统调用才有 C 标准库那层 API，不要把包装当成本体。

* **open 的写法与失败处理**

    * 典型写法是以可读可写打开并检查返回值，打开失败时用 `perror` 打出原因：

    ```c
    int try_open(const char *path) {
        int fd = open(path, O_RDWR);   /* 以可读可写的方式打开 */
        if (fd < 0) {
            perror(path);              /* 打开失败，打印原因 */
        }
        return fd;
    }
    ```

    * 返回 -1 说明打开失败，`perror` 会按当前语言设置打出失败原因（例如 No such file or directory，或对应的中文）。

    * `open` 的各种标志都在参数里：追加写入、异步方式、文件不存在时创建等；其中 `O_CREAT` 是 create 的拼写错误，当年为了省一个字节写成这样，后来改不掉了，后来的实现为了兼容一直沿用。

    * > **提示**：接口一旦发出去就再也收不回来，做系统的人会经常遇到这种历史遗留。

### 描述符的分配规则

* **永远挑最小的空位**

    * 如果 0、1、2 已被占用，`open` 会从 3 开始挑一个还没有被分配过的最小编号，让它指向新打开的文件。

    * 关掉某个编号之后再次打开，拿回来的还是那个最小可用的编号：关掉 3 再 open，得到的仍然是 3。

    * 编号空间从 0 开始，所以小于 0 的返回值都表示失败。

* **空间大小**

    * 大多数时候只会用到 0、1、2；命令行里 `wc`、`grep` 组合起来时甚至不会再打开文件。

* **句柄（handle）**

    * > **定义**：Windows 里对同一类东西的叫法，它更像一个指向操作系统的指针，除了对象编号之外还带着权限等信息。

    | 维度 | Unix 的文件描述符 | Windows 的 handle |
    | :--- | :--- | :--- |
    | 形态 | 从 0 开始的整数编号 | 一个 handle 值 |
    | 对象编号 | 编号本身 | 包含在 handle 里 |
    | 权限信息 | 主要留在操作系统内部，要用额外系统调用去查 | 与对象编号一起放在 handle 里 |
    | 更像什么 | 指向对象的一个编号 | 一个带权限的指针 |

    * 「句柄」这个中文词来自一次错误翻译：一本编译原理教材里把 sentence handle 译错并沿用下来，后来被 Windows 官方翻译采用。

### fork 之后的共享游标

* **两种可能的设计**

    * 复制进程时把打开文件结构体连同偏移一起拷贝，两个偏移各写各的，追加写只会留下一个字符。

    * 只做一次浅拷贝，让第二个进程的同一编号指向同一个打开文件结构体，两个指针共享一个偏移，于是两次写各占一个位置、文件里出现两个字符。

* **Unix 的选择**

    * Unix 选浅拷贝，父子进程共享同一个偏移，写出两个 2。

    * 理由是不希望父子进程在共享一个文件、以追加方式写入时互相覆盖或丢掉数据；覆盖一般来说都不是想要的。

    * 想要一个深度独立、互不干扰的偏移，唯一的办法是把这个文件再 `open` 一次：每次 open 都得到一个新的打开文件结构与新的偏移。

### 继承与最小权限

* **默认全继承的后果**

    * fork 会产生「复制」这个动作，任何被进程持有的资源都要重新考虑复制之后的语义是什么。

    * 父进程持有一个敏感的文件描述符，创建子进程后用 `execve` 执行另一个程序；如果忘了把那个描述符关掉，子进程就拥有了该文件的访问权限。它可能连安全漏洞都算不上，只是一个 bug，却足以让别人的程序误写系统里的文件。

    * Windows 的 handle 默认不继承，与 Unix 正好相反：可以在创建时设置继承，也可以在之后决定它将来要不要被继承，这是最小权限原则。

* **O_CLOEXEC**

    * > **定义**：让一个文件描述符在创建子进程并 exec 的时候不被继承的标志。

    * 它是为了修补默认继承带来的问题而后来加入的；发展到今天，这套 API 实际上已经千疮百孔。

## 管道与进程间通信

### 内核中的共享对象

* **需要共享对象的原因**

    * fork、execve 创建出来的两个进程完全分离，各自持有独立的内存与寄存器，谁也看不见谁的数据。

    * 要让 128 个进程各算出一个数、最后把结果加起来，就必须由操作系统在内核里创建一个新的对象，让父子进程都能访问它。

* **进程持有的对象**

    * 应用要发网络请求、写文件、和别的进程通信，本质上都是去访问操作系统里面的对象，而这些访问都通过系统调用完成。

### 管道

* **管道（pipe）**

    * > **定义**：内核里一段有容量限制的缓冲区，有写口与读口，用 `write` 往写口写、用 `read` 从读口读。

    * 管道就是一个文件，甚至可以真的创建一个管道文件。

    * 阻塞语义是它最有价值的地方：管道为空时 `read` 会等，等到有数据为止；容量有限、写不下时 `write` 会等，等到里面空出足够位置才继续。

    * 用它可以等待进程把事做完：每个算完的进程往写口写一句 `number 1 OK` 这样的信息，主管进程读到就知道谁已经完成，从而在进程之间传递数据。

* **容量与等待**

    * 管道容量有限这件事在实际使用中基本可以当成容量无限来处理。

    * 没有人在读时，往管道里写数据不会立即返回，要等到读端真的读走才结束；读端先启动时就会一直等在那里。

### 命名管道

* **命名管道（FIFO）**

    * > **定义**：在文件系统里有名字的管道，用 `mkfifo` 创建，`ls` 列出来时会看到一个 `p` 标记。

    * 先跑读的那一头会什么也不做地等在原地；从另一边 `write` 一个 hello，`write` 立刻返回，读的那头就读到了 hello。

    * 反过来，没有人在读时写数据也不会立即返回，要等到读端真的读走，这次 `write` 才结束。

* **它适合的场合**

    * 因为它在文件系统里有名字，不同的进程可以各自按路径打开它，不要求有亲缘关系。

    * 做 `ls | wc` 这类流水线不需要创建命名管道，用匿名管道就够。

### 匿名管道

* **匿名管道**

    * > **定义**：没有名字的管道对象，由 `int pipe` 系统调用在内核里创建，并返回两个文件描述符。

    * 用法是准备一个长度为 2 的数组：`int pipefd[2]; pipe(pipefd);`；`pipefd[0]` 是读口，`pipefd[1]` 是写口。

    * 内核在创建管道对象后打开两个文件，在 0、1、2、3 已被占用的情况下会找到两个最小的空闲编号（例如 4 和 5）分别指向读口与写口。

    * API 在 C 里不太好看，每次都要写 `pipefd[1]`；更好的做法是给它一个有意义的名字：

    ```c
    int write_end = pipefd[1];
    int read_end  = pipefd[0];
    ```

* **fork 与描述符腾挪**

    * fork 会继承所有文件描述符，父子进程各有一份完全一样的描述符表，读口写口都一样。

    * 要实现 `ls | wc`，需要一侧保留写口、关掉读口，另一侧保留读口、关掉写口，再用 `dup` 系列调用做文件描述符的腾挪。

    * 简单例子里父子各关掉自己不用的那一头之后，父进程用 4 号往管道写、子进程用 3 号从管道读，数据就从父进程流到了子进程。

* **观察描述符状态**

    * `ls -l /proc/*/fd/` 能列出每个进程打开的文件以及每个编号指向哪个文件，能看到有些进程打开着终端、有些打开着管道。

    * 用调试器调试任何管道程序，把每一步的文件描述符状态导出成一份关系图，就能直接看清父子进程各自打开了什么、哪一个是读口哪一个是写口。

    * 用 `echo hello > /dev/pts/5` 可以打开别人终端对应的伪终端设备并写数据，别人的终端上就会出现这些内容。

## 一切皆文件与 Unix philosophy

### everything is a file

* **一切皆文件（everything is a file）**

    * > **定义**：把操作系统里的对象直接以文件的形式暴露出来，并提供一组统一的工具，用工具组合的方式管理这些对象。

    * 文件系统里再放进目录、一层层套起来，于是每一个操作系统对象都有一个名字；整个文件系统就是一堆带路径名字的文件的集合。

    * 进程的状态、进程的内存、整个系统的状态都变成了文件，和 `.c`、`.md` 这些普通文件是同一类东西，可以用同一套命令行工具处理；最神奇的是管道，把一个程序的输出直接作为另一个程序的输入。

* **复用已有 API 的路线**

    * 除了专门提供一个 `get_memory_map` 这样的系统调用，还可以把进程信息以文件形式放在 `/proc` 里，复用已经实现好的文件和目录 API：`open`、`read`、`write`，目录则打开后用读目录项的方式扫描。

    * 打印进程地址空间映射的工具背后就是打开 `/proc/<pid>/maps`、把文本解析一遍再加工。

    * 代价是两次表示转换加一次文本解析：信息在内核里本来是一个数据结构，为了做成文件要先序列化成文本，用户态工具读出来又要解析回来。

* **另一条路线**

    | Linux 的 /proc 路线 | Windows 的 API 路线 |
    | :--- | :--- |
    | 内核数据结构序列化成文本 | 内核按 API 契约直接填充用户态要的结构体 |
    | 用户态工具读入并解析文本 | 用户态直接拿到结构体字段 |
    | 代价是两次表示转换与一次文本解析 | 代价是接口必须由设计者预先定义 |
    | 创建文件、写、移动指针、访问进程都复用文件语义 | `CreateFile`、`WriteFile`、`SetFilePointer`、`OpenProcess`、`ReadProcessMemory`、`VirtualQueryEx` 等直接给内核 |

    * Windows 的理念是开发者要什么就给什么，接口直接对应需求，因此效率更高；Unix 用户的定位是黑客，需要一个把对象以简单舒服的方式暴露出来、并能复用小型工具的办法。

### 目录树

* **文件系统层次标准（Filesystem Hierarchy Standard，FHS）**

    * > **定义**：规定文件系统里有哪些目录、各放什么东西的标准。

    | 目录 | 内容 |
    | :--- | :--- |
    | `/home` | 用户的家目录 |
    | `/dev` | 设备 |
    | `/boot` | 启动相关 |
    | `/usr` | 用户程序与数据 |
    | `/sys` | 虚拟文件系统：设备与内核信息 |
    | `/proc` | 虚拟文件系统：进程与内核的信息 |
    | `/srv` | 服务数据 |

    * 文件系统是构建任何信息系统的好抽象：一门课的所有提交、结果、日志都能用文件表示，不需要数据库。

* **统一标准的收益**

    * 大部分 Linux 遵循它，但也不是全部，甚至有的非常不遵循，比如 macOS。

    * 有统一标准的好处是：你在一个系统上获得的知识，在另一个系统上也找得到对应的文件。

### Unix philosophy

* **KISS principle（keep it simple, stupid）**

    * 每一个工具只做一件事，并且把它做好。

    * 让这些工具能够互相配合（work together），组合起来使用。

    * 把文本流当作通用接口（handle text stream as a universal interface）。

* **文本接口（text interface）**

    * > **定义**：操作系统对象以文本流的形式暴露出来，所有工具都读写文本流，于是任何一个工具的输出都能成为另一个工具的输入。

    * 好处是既机器可读也人类可读：读到一段文本就能明白里面有什么，而不像拿到一个结构体还要再找别的东西解析它。

    * 代价是性能不那么高；在 1970 年代敢做这个取舍是很大胆的决定，因为当时每个时钟周期都很贵。

    * 一条把通配符、字段过滤与管道拼起来的命令，就能求和系统里所有进程占用的物理内存；系统剩余内存的信息也是从文本文件里读出来的。

### 文本接口的代价

* **解析带来的问题**

    * 文本接口必然要求解析，解析就会带来各种问题，最典型的是空格。

    * 使用 Unix/Linux 的人普遍不在文件名里引入空格，改用减号；否则字符串粘贴到 shell 里会被拆成两个参数。

    * `Makefile` 至今不能很好地处理空格，GNU 的 make 与旧版 make 都不行，还得在上面再叠一层别的办法。

* **quick and dirty 的取舍**

    * > **提示**：这些诡异行为来自它是 quick and dirty 的 hack——目标是让黑客快速写出一条大致正确的命令把事办完，而不是让每一处细节都规整漂亮。

    * 为了 1970 年代的算力、算法与工程能力，当时只能实现几百行的系统，后人就只好将错就错。

    * 文本接口的历史使命在今天多了一层：这些命令行工具成了大语言模型的语料。

### 用文件系统构建信息系统

* **用文件实现的在线评测**

    * 学生本地打包，网页后端把压缩包写进一个目录的某个位置；**文件名就是提交的日期**，同一秒交两次会覆盖掉上一次。

    * 评测程序不断 watch 这个目录，评测完生成一个结果文件写回去；**没有 result 的提交就是要重评的提交**，想 rejudge 只要把结果文件删掉即可。

    * 想删一份提交就直接删掉文件，一秒完成，不需要管理端界面；想给每份提交加 AI 点评，也只是在结果文件里多填一个字段。

    * 不用数据库的理由是：一旦用了数据库，想 hack 它就变得前所未有地困难，每个操作都要为它实现一个工具或封装好的接口。

    * > **易错点**：文件系统没有很强的一致性保证。写三个文件、写到第二个时程序崩溃，系统就进入不一致、不正确的状态，文件系统本身不提供这个保证。

* **可复用的参考实现**

    * 先用文件系统实现一个性能很低但正确的版本，再让模型把它翻译成带数据库或云上 serverless 的实现，两个版本交叉检查，就像做差分测试一样。

### 谁在用这套接口

* **Windows 的用户定位**

    * Windows 的用户被当成程序员，所以提供的是符合软件工程规范且高效的接口。

    * 它的用户不直接操作系统里的对象，不会打开终端去删掉某个东西或看某个文件有多少行。

* **Unix 的用户定位**

    * Unix 的用户是黑客，会直接敲这类命令，所以需要把对象以简单舒服的方式暴露给所有用户。

    * 它还要能让用户复用那些小的命令行工具，把工具组合起来管理对象。

## 终端

### 打字机遗产

* **打字机的机构**

    * 最早的键盘来自水风琴与管风琴，1500 年左右出现钢琴原型：按下键，小锤子打到琴弦上发声。

    * 把击弦机构与擒纵机构拼起来就得到打字机：按下键时字锤打到带墨水的色带上，把字母印到纸上；松开键时擒纵机构把字车向右推固定的一格。

    * 这套机械结构引出一个副作用：两个键几乎同时按下时两根字锤会抢同一个击打位置，容易卡住，于是在 1860 年代出现了 QWERTY 布局，它的设计目的本来就是降低打字速度。

* **键盘上的功能键由来**

    * `Shift` 与 `Caps Lock`：打字机的字锤上下排着两个字符，按下 `Shift` 就把整排字锤的档位向上抬一格，于是打出上面那个字符；`Caps Lock` 是把档位锁定在上面。

    * `\r`（carriage return）与 `\n`（line feed）：`\r` 是把打印头移回行首，`\n` 是往下走一行。

    * `space` 把当前位置向右移一格，`backspace` 把当前位置向左移一格，两者互为逆操作；这也是退格键不叫 delete 的原因。

    * 打错了只能不停退格，再打若干减号、斜杠把原来的字划掉；老照片里打字稿上那一道道横杠就是这么来的，换一个颜色的色带划掉也可以。

    * `Tab` 是制表符：字车一直往右走，直到碰到一个制表位才停下，因此表格对齐是自动的，不靠打空格。今天 `Ctrl+Tab`、`Alt+Tab`、`Win+Tab` 用的还是这个键。

    * 等宽字体（monospace）来自打字机：每打一个字符，字车向右移动的距离完全确定，这个习惯一直延续到今天的终端。

* **一个覆盖的例子**

    * 要打印 `hello` 但在中间插一个 `\r`，字符序列是 h、e、l、\r、l、o；打完前三个字符后光标回到行首，后面两个字符盖在前两个位置上，第三个位置还留着原来的 l。

    * 结果这一行显示为 `lol`；在打字机上这个覆盖是物理的，色带把新字符直接印在旧字符上，擦不掉。

### 电传打字机

* **电传打字机（Teletypewriter）**

    * > **定义**：与打字机功能相同，但按键之后不是在本地打出字来，而是在导线另一端把字打出来。

    * 只要有维护良好的导线与中继站，就能把一张纸的内容实时送到很远的地方，只需要给每个字符编一个码、编一个号。

    * 1920 年用的是 5-bit 编码，装不下全部字符，靠「进入大写模式」「进入小写模式」这类特殊编码切换大小写；编码表里没有美元符号，说明不是美国人设计的。

* **TTY 这个名字**

    * TTY 是 Teletypewriter 的缩写，而 Teletypewriter 又是从最早的 typewriter 继承下来的。

    * 后来出现 Video Teletypewriter，从计算机硬件的角度看，这个设备给操作系统的接口就是 `putchar`：计算机生成一个字符，把字符送进去。

    * 可以把它想象成内存映射的 I/O 端口：往那个地址写一个字符，打字机就把它打出来；送 `\r` 就回到行首，送 `\t` 就跳到下一个制表位。

### 终端与操作系统的接口

* **双向字符流**

    * 作为输出设备，终端收到字符就打印出来；作为输入设备，它按下键就把一个字符送进计算机。

    * 终端只是一个很傻的设备：按下一个键，它就给出一个字符；至于要不要显示、显示成什么，全由操作系统和应用程序决定。

    * 按 `ESC` 就真的给出一个 ESC 字符，它的编码是 033；操作系统可以原样打印出来，也可以什么都不显示。

    * 终端与计算机之间只有这一条双向字符流，别的约定一概没有。

* **VT100**

    * VT100 是里程碑式的产品，后来成为事实上的行业标准，支持完整的 ANSI escape sequence（escape code），可以有颜色、做屏幕控制与滚动。

    * 它延续了打字机「滚纸」的模型，就像一张无限长的纸可以上下滚；80×24 个字符的显示从此成为终端布局的标准。

    * 有了 Unicode 之后终端能玩的花样更多：把不同高度、不同填充的矩形块与线条叠起来，可以拼出任意形状；emoji 也被编码进 Unicode。

### ASCII 与按键编码

* **ASCII 的由来**

    * ASCII 的设计是和电传打字机共同完成的，那些看起来莫名其妙的编码，正是终端设备真实需要的动作。

    * 大写 `A` 是 65、小写 `a` 是 97，前面的编号留给控制字符，例如 ESC 是 033。

* **按键送出的字节**

    | 按键 | 终端送给操作系统的字节 | 说明 |
    | :--- | :--- | :--- |
    | `Ctrl+C` | `0x03` | 不是「Ctrl 加 C」两个字符，就是一个 03 |
    | `Ctrl+D` | `0x04` | 表示输入到此为止 |
    | 回车 | `0x0D`（`\r`） | 是回车，不是换行 |
    | `Tab` | `0x09`（`\t`） | 制表符 |
    | 空格 | `0x20` | 空格本身 |
    | 退格 | `0x7F`（DEL） | 因此常被程序当作 delete，苹果键盘该位置也印 delete |
    | 方向键 | ESC 序列，末字节 `0x41`/`0x42`/`0x43`/`0x44` | 分别对应上、下、右、左 |

    * ASCII 里根本没有上下左右，也没有编码「颜色是什么」，所以这些信息被迫用 escape sequence 表达。

    * > **易错点**：`Shift` 从来不会作为一个按键被送进计算机。它只改变「下一个真正敲下去的键送什么字符」，状态留在终端上，就像打字机上按 `Shift` 只是把字锤整排换挡。

    * 一个把终端字符原封不动读出来的程序里，`Ctrl+C`、`Ctrl+Z`、`Ctrl+反斜杠` 都退不出去，因为没有让操作系统的驱动去解释它们；能退出靠的是程序自己留的后门。

### 规范模式

* **规范模式（canonical mode）**

    * > **定义**：操作系统终端驱动的行编辑模式，它把按键攒成一行、处理退格等编辑动作，等回车才把整行交给应用程序的 `read`。

    * 驱动内部有一个行缓冲区：每个按键先变成字符进缓冲区，退格由驱动把上一个字符去掉，整行编辑都是驱动模拟出来的。

    * 驱动还会把字符回显到屏幕上，回显可以开也可以关：输入密码时字符不显示，但行编辑照旧正常工作。

    * `cat` 执行 `read` 时按 `aaaaaa` 没有反应，要按下回车 `read` 才返回；这不是模型矛盾，而是按键先交给了操作系统而不是直接交给应用程序。

* **终端配置**

    * `stty -a` 可以看当前终端支持哪些配置，也可以改它们。

    | 配置项 | 默认按键 | 含义 |
    | :--- | :--- | :--- |
    | `interrupt` | `Ctrl+C` | 中断，送 `SIGINT` |
    | `quit` | `Ctrl+\` | 退出，送 `SIGQUIT` |
    | `eof` | `Ctrl+D` | 文件结束（end of transmission） |

    * `Ctrl+C` 正常退出，`Ctrl+\` 得到的是 `terminated by SIGQUIT` 这样的异常退出；这个映射不是写死的，interrupt 可以配到别的按键上。

    * > **提示**：`Ctrl+C` 能终止程序，不是终端有特别的能力，而是操作系统在收到那个 03 之后额外模拟出来的行为。

### 伪终端

* **伪终端（pseudo-terminal，PTY）**

    * > **定义**：由操作系统按需分配的虚拟终端，每一个都有自己的设备名，用完可以销毁、名字还能被复用。

    * 不再受限于物理终端数量，终端想要多少就有多少；`tmux` 分屏出来的每一个都是独立终端。

    * 分配方式是打开 `/dev/ptmx` 这个 master 设备，再依次调用 `grantpt` 与 `unlockpt`，拿到对应的路径与文件描述符。

    * 作为 master 持有这个 PTY 之后就可以读写它里面的数据，它就是一个完整的终端设备，在上面可以做任何事情。

* **终端中的终端**

    * 把外层终端的输入转发进新终端、再把新终端的输出搬回外层终端，就在一个终端里长出了另一个终端。

    * 这类工具的输入输出全部被劫持到新建的伪终端上，因此可以完整记录一次终端会话。

    * 终端与操作系统之间只有字符进出，所以只要知道每个字符是什么以及它出现的时间戳，就能完整恢复一次终端运行；回放工具依赖的就是这一点。

### 图形扩展

* **Sixel**

    * > **定义**：在 escape code 上做的扩展，用字符编码一列六个像素，从而在字符终端上显示位图。

    * 6 这个数字有讲究：$2^6 = 64$，正好能被所有可显示的 ASCII 字符覆盖；例如 `?` 表示这一列六个像素全都不亮，`@` 表示最上面一个像素亮起来。

    * 若干列并排就是一条六像素高的色带，很多色带拼起来就是一张图；后来还扩展出调色板，可以指定每一块是什么颜色，没有指定颜色的位置变成 mask。

* **它的前提与边界**

    * 终端本来只能显示固定行列的字符，把字符做大也还是字符终端；随着芯片能显示更细粒度图像，才在 escape code 上做这个扩展。

    * > **提示**：在不支持 Sixel 的终端上什么也看不见，把那段输出丢进文本文件就是一堆看不懂的字符。

### 系统启动时的终端

* **getty**

    * > **定义**：由 init 在每个终端上分别启动的程序，负责打开对应的终端设备、把标准输入输出接上去、提示用户登录。

    * 系统刚启动时第一个进程并没有文件描述符 0、1、2，init 也不知道自己处在哪一个终端上，因为系统上可能有五六个终端。

    * getty 打开对应终端（例如 `/dev/tty1`）后把 0、1、2 都指向它，并做配置与初始化。

    * 波特率（baud rate）是接口真实传输速率；面对真的 VT100 时必须给一个有意义的数值才能正确握手，如今终端是模拟出来的，这个数值不那么重要，但查看伪终端时仍会模拟出 38400。

    * 在 Linux 里按 `Ctrl+Alt+F1`、`F2`、`F3` 分别能看到不同终端上的登录提示；`Ctrl+F7` 对应的第七个屏幕就是图形界面所在的终端。

* **login 与远程登录**

    * `login` 的作用是在系统上开始一个新会话，一个会话里都有一个控制终端。

    * 远程登录时由 `sshd` 分配一个伪终端，再 fork 一个自己的程序、创建伪终端并完成初始化，然后执行 `login`——更准确地说是一次权限切换，因为它本身运行在高权限上，可以把自己变成另一个程序。

## 会话与作业控制

### 进程组

* **进程组（process group，PGID）**

    * > **定义**：从进程树上看不出来的一层分组，Shell 在启动一个新程序时会为它分配一个新的进程组。

    * 正因为有了这个隐藏的分组编号，不同的应用程序才会被分开，中断字符才能只影响该影响的那一组。

* **继承与修改**

    * 默认情况下创建出来的进程继承父进程的进程组。

    * 操作系统也提供系统调用去修改自己的进程组。

### 中断字符的归属

* **Ctrl+C 发给谁**

    * 操作系统会给前台的进程组里的所有进程发送 `SIGINT`；只要进程不忽略 `SIGINT`，前台那一组里每一个进程都会收到。

    * 这解释了为什么按 `Ctrl+C` 时旁边的编辑器安然无恙：它们不在同一个前台进程组里。

    * `Ctrl+Z` 会给前台进程组发 `SIGSTOP`，之后可以用 `fg`、`bg` 恢复。

* **配置决定行为**

    * 只有在规范模式、走行编辑这条路时，中断字符才会被操作系统识别并按终端配置转换成一个 interrupt。

    * 如果配置成「驱动什么都别管，字符直接送到程序里」，那么任何键都退不出来。

### 作业控制

* **作业控制（job control）**

    * > **定义**：在终端里实现「像 Windows 用 Alt+Tab 切换窗口」的一整套机制，包括把任务放后台、暂停、恢复、杀掉的完整流程。

    * `jobs` 列出当前的任务，相当于 Windows 上按 `Alt+Tab` 时看到的窗口列表；`fg %2` 把 2 号任务放回前台，`bg` 让它继续在后台跑。

    * 按 `Ctrl+Z` 相当于把当前应用最小化：程序没有终止，发的是 `SIGSTOP`；要恢复就把它放回前台。

    * 终端里一次只能显示一个应用，这是它与窗口管理器唯一的区别。

* **前台与后台的标记**

    * 做前后台切换时用 `tcsetpgrp` 这个系统调用标记哪一个进程是前台；只有前台的那个才收得到 `Ctrl+C` 带来的 `SIGINT`，后台的收不到。

    * 如果没有前台进程，按 `Ctrl+C` 谁都影响不到，后台任务照样在输出。

    * 这套机制已成为 POSIX 标准的一部分：任何声称 POSIX 兼容的实现都必须实现它，才能与依赖这个标准接口的软件保持兼容，不实现就用不上整个开源生态。

### 会话与控制终端

* **会话（session）**

    * > **定义**：登录时引入的一个最大分组，子进程继承父进程的 session ID；每一个会话关联一个控制终端（controlling terminal）。

    * 当会话的 leader 退出时，整个会话里的所有进程都会收到 `SIGHUP`，而这个信号的默认行为就是退出。

    * 这就是网络连接一断、正在跑的长任务也一起终止的原因——这叫 hang up；必须从头再跑一遍。

* **应对挂断的手段**

    * `nohup` 的意思是请忽略那个 hang up 信号，忽略之后程序才能继续执行。

    * `tmux` 走的是另一条路：它不会收到那个 `SIGHUP`，所以可以继续在后台运行。

* **相关系统调用**

    * 会话与作业控制对应的系统调用是 `setsid`、`getsid`、`setpgid`、`tcsetpgrp`。

    * `setsid` 在系统调用手册里的描述是 creates a session and sets process group ID。

    * 为了让这些功能可用，操作系统里被打了无穷多的补丁：进程结构体里多了 uid、effective uid、saved uid 等字段。

### 换一套设计的可能

* **不把进程绑定到设备上**

    * Android 的设计是每一个 app 都是一个不同的用户，借用操作系统的权限隔离；「强行终止」就是遍历属于这个 uid 的所有进程，全部发一个 `SIGKILL`。

    * 它完全不需要 controlling terminal，因为 Android 本身面向图形界面。

    * 也可以这样想：不需要进程组，今天有容器、虚拟机、namespace、cgroups，程序启动时就处在一个虚拟机里，想杀掉就把这个虚拟机关掉；虚拟机内部创建的程序仍继承 PGID，逻辑照样说得通。

* **历史包袱的来源**

    * 当年设计进程组、会话的时候还没有想到未来会有容器、Docker 这类东西，所以只能做一个 workaround，而它一直活到了今天。

    * > **提示**：如果给你一次重新设计系统的机会，你可以做得更好；大厂与维护老代码的人必须遵守旧标准，而破坏旧世界、建立新秩序的地方可能有机会。

    * 这条第一性原理仍然成立：终端只是在和计算机操作系统交换字符，其他所有行为都是可以定义的，最终收敛到某个方案而已。

## Shell

### 最小 Shell

* **骨架只有一个循环**

    * 不做作业控制时，Shell 就是一个同步流程：`while (1)`，先用 `printf` 打一个提示符，再用 `read` 系统调用从标准输入拿到一行，然后 `execve` 它。

    * 最早的 shell 真的就是这样，可以做到零依赖，连库函数都不依赖。

* **它到底在做什么**

    * 它把你敲的任何一条命令翻译成一组系统调用的序列：启动进程、打开文件，需要 `fork`、`execve`、`waitpid`、`pipe`，以及文件描述符的腾挪。

    * 操作系统无非就是启动进程、打开文件这些东西，Shell 的语法成分也是围绕这个思路设计的。

### 一门只有字符串的语言

* **文本替换式的极简语言**

    * > **定义**：Shell 是一门基于文本替换的编程语言，它连整数也没有，把你敲的每条命令当作一个表达式或程序解释执行。

    * 坐在终端前面时，你按下的每一个字符都是在编程。

    * 要和 C 里的预处理器类比：两者都在做字面意义上的文本替换。

* **没有算术类型**

    * 早期在 Unix 里算 1+2 得把两个数字变成字符串，然后起一个进程调用外部命令 `expr`。

    * `expr 1 + 2` 得到 3，而写成 `1+2` 算不出来，因为那只是一个字符串。

    * 必须用空格：只有 1、`+`、2 被空格分开，Shell 才会把它们切成三个字符串放进 `argv`，`expr` 匹配的是 `argv` 的第二个字符串，看它是不是加号；`expr 1 '<=' 2` 同样能得到正确结果。

    * > **易错点**：`expr 1+2` 不是算术，它只是一段字符串传给了一个程序；Shell 这一层没有整数，没有算术类型。

### 重定向

* **重定向的本质**

    * > **定义**：把文件描述符换一个位置。因为 `execve` 时新程序继承父进程的文件描述符，父进程先 fork 一份自己、把编号为 1 的描述符替换成指向目标文件的描述符，再 execve。

    ```text
     shell: read line "ls > a.txt"
       fork()
         child:
           fd = open("a.txt", O_WRONLY|O_CREAT|O_TRUNC)
           dup2(fd, 1)            # fd 1 现在指向 a.txt
           execve("/bin/ls")      # ls 往 fd 1 写，就写进了 a.txt
         parent:
           waitpid()              # 前台任务，等一下它
    ```

    * execve 执行的是什么命令都无所谓，可以是很长的一条命令；但凡它往编号为 1 的文件描述符里写数据，就会写到那个文件里。

    * 用大于号重定向标准输出、用小于号重定向标准输入、用一个难看的语法把标准错误重定向到 `/dev/null`，都是同一个套路。

* **追加与更多花样**

    * 手册里有把标准输出追加到文件（append the standard output to file）的写法，也可以把编号为 2 的标准错误追加到文件。

    * Shell 还可以把一个程序的输出以字符串形式贴进来，甚至把一个程序的结果包装成一个文件描述符、把它的路径贴进来，例如 `/dev/fd/63`，再用 `cat` 读这个路径拿到全部输出。

    * 这条路径很有用：有些工具（例如 `diff`）必须要输入文件，不能把两个文件都放进标准输入，于是用这种办法生成路径来完成比较。

### 控制流

* **短路求值**

    * Shell 支持命令一运行完就运行命令二，并支持短路求值，道理和 C 里的 `&&`、`||` 一样：左边已经是假，右边就不算。

    * 常见写法是「如果左边成功就执行右边」，反过来也常用：想试一试某个工具能不能用，能用就结束，不能用就再试下一个，直到有一个能用为止。

* **脚本头部的解释器**

    * 脚本头上的解释器一般写 `/bin/bash` 或 `/bin/sh`。

    * 不用 fish 的原因是它不标准，虽然好用但会让脚本翻车。

### 管道的实现

* **拼接两个程序**

    * 用 `pipe` 系统调用创建两个文件描述符，一个指向读口、一个指向写口，它们在 fork 之后同样被继承。

    * 把一个进程的写口留下、读口关掉，另一个进程的读口留下、写口关掉，再腾挪一下描述符，就实现了把一个程序的输出接给另一个程序当输入。

    * 写出来的代码并不优雅：有一个输入 fd、一个输出 fd，要 fork，然后到处腾挪文件描述符。

* **边缘情况**

    * `ls > a.txt | cat` 这类写法属于未定义行为，不同 shell 实现不一样：有的什么也看不到，有的会像 `tee` 一样既写文件又让标准输出显示。

    * 设计者大概自己也没想清楚，只是觉得那样对用户更好，就这样实现了。

### 手册里的宝藏

* **man sh**

    * 手册的标题是 command-line interpreter，里面有控制流与循环、变量与参数，还有 special parameters。

    * 建议把手册非交互地直接打印出来看，而不是在命令行里分屏交互；更好的做法是把它管道给一个 AI agent 让它总结。

    * 手册的价值在于扩大想象力：你没有办法做自己想象不到的东西，而扩大想象力的方式就是去看别人想到了什么。

* **这套设计的裂缝**

    * 它是为 1970 年代的算力、算法与工程能力做的一次无奈取舍，当时只能实现几百行的系统。

    * 有个反直觉的例子：在某类重定向场景下 `sudo` 是不起作用的。

    * 脚本语言会走向历史的看法也有其理由：模型可以直接调用 API 从内核拿到绝对准确的数据，再翻译成想要的任何形态，不必依赖文本接口。
