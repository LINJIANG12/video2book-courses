# 并行算法、轻量协程与异构计算

## 可扩展性与锁的代价

   * **累加计数器模式（sum++）**

       * > **定义**：多个线程在互斥锁保护下反复执行 `sum++` 的并发编程常见 pattern；被锁保护的部分在真实系统中往往是一个数据结构的操作，而不是一个整数。

       * 现实对应：`printf` 时两个线程共享进程的一个 buffer，锁上之后才能往里面写东西，`stdout` 才能看到不被打乱的正确数据；一个 key-value 字典只要锁保护住整个数据结构，在它上面做更新就是安全的。

       * 四种实现的单次 `sum++` 开销随线程数增长的变化：

| 实现 | 随线程数增长的单次开销 | 说明 |
| :--- | :--- | :--- |
| 汇编写的原子 `sum++` | 最快 | 连获取锁、释放锁的过程都没有 |
| 互斥锁（mutex） | 基本保持不变，但也不会变好 | 串行化，阻止了并行 |
| 手写的自旋锁 | 随线程数增加而变慢 | 不断地试图去桌上拿那把钥匙 |
| 用 futex 系统调用进内核 | 随线程数增加而变慢 | 每次操作都要进操作系统内核 |

   * **互斥锁的两项硬保证**

       * 完整的 serializability：第一个线程的 lock/unlock、第二个线程的 lock/unlock，可以清楚地排出每一次上锁和解锁之间的顺序。

       * acquire/release 之间的数据可见性：写了 `x = 1` 然后 `unlock`，另一个线程 `lock` 之后一定能看到 `x = 1`，即 `x = 1` happens-before 这次 lock；锁的实现会使用特别的指令（或一堆指令）告诉 CPU，读 `x` 时必须读到 `x = 1`，而不能读到更旧的值。

       * 这两项保证都要付出代价，代价就是 scalability——性能没有办法随着 CPU（线程或者机器）的增长而增长。

   * **可扩展性（scalability）**

       * > **定义**：多一个 CPU 就能多分一份算力——原来要 1 秒钟，两个 CPU 就应该花 0.5 秒，4 个 CPU 就应该花 0.25 秒；一个真正好的实现应该能把 CPU 的计算力 100% 用起来。

       * 实测观察：一个操作在 1 个 CPU 时最快，2 个 CPU 时变慢，4 个 CPU 更慢，8 个、16 个开始饱和就不再变；mutex 与原子操作最好也只是到某个地方到顶、不下降，但它是串行的、阻止了并行，所以不是想要的东西。

       * **scale up**：一台计算机内部，随着线程数增长性能不断增长。

       * **scale out**：再来一台计算机、再来一台，随着计算机数量的增加性能依然可以增加。

       * 这两件事是这些年（尤其大数据与 AI 时代）最核心的引擎：正因为信息系统可以 scale up、可以 scale out，才能支撑全国人民都在发抖音的数据量、都在调大语言模型 API 的流量。

## 计算图与并行算法

   * **计算图（computation graph）**

       * > **定义**：任何一个并行计算问题的本质都是一张计算图，每一个节点是一次计算，每一条边是一个依赖关系。

       * 例子：矩阵上的动态规划里 `dp[i][j]` 是 `dp[i-1][j-1]`、`dp[i-1][j]`、`dp[i][j-1]` 这几个值的函数，于是得到一张依赖关系图。

       * 只要每个节点上的计算量很大，而这段计算又不需要上锁（本身不涉及共享变量），那么这个算法就可以让「上锁和解锁之间」被串行化的区域变得很小；一旦它变得很小，系统就可以 scale up，也可以 scale out。

       * 切分的必要性：若让每一个 `dp[i][j]` 都作为一个节点，这张计算图设计得很糟糕——有三个前驱就要在执行前 P 三次、算完之后再对后继各 V 一次，付出了这么多同步代价之后只做了一个 `dp[i][j] = dp[i-1][j] + 1` 这样一两步算术运算。

       * 切分方式：最上面那个小三角形整块串行算（只有几百个东西，不值得为它付同步的代价）；并行度上来以后按对角线切，把一层切成两份、三份，随着并行度提高切得越来越细；本质上只要算完这一层就可以算下一层。

            ```text
               +-----------------------+
               |           A           |
               +-----------+-----------+
               |     B     |     C     |
               +-----+-----+-----+-----+
               |  D  |  E  |  F  |  G  |
               +-----+-----+-----+-----+

               最上面的 A 就是那个小三角形，整块串行算；
               越往下切得越细，块与块之间只剩边界上的依赖。
            ```

   * **高性能计算（High Performance Computing，HPC）**

       * > **定义**：利用超级计算机或计算机集群的算力，去解决需要 massive computation 的复杂问题的技术。

       * 源于各种各样的数值密集型科学计算任务：有牛顿力学就可以模拟任何粒子系统，只要把它拆得足够小、足够细；天上的气流、核武器的爆炸、流水都可以模拟，所以再也不需要真的去做地下核试验。

       * 投入多少计算量就获得多大精度，算得越慢最后的结果离真实结果就越准，是非常典型的 require massive computation 任务。

       * 在天气预报、航天、制造、能源、制药这些领域都是毁灭性的战斗力，一直是给高性能计算买单的最大客户；之后又加入了两股新力量——矿场（blockchain 本质是一条由地球上所有参与者共同维护的分布式 append-only list，要记账就需要 proof-of-work，要证明算力就需要大量 GPU 矿卡）与 AI 算力。

   * **物理网格切分**

       * 最早驱动高性能计算的科学计算问题恰好利用了一个特点：总是可以把物理的世界切分成网格。要模拟的不是一座建筑顶上的天气而是全世界顶上的天气，切出 100 万份、1000 万份就轻轻松松，切完之后每一份都可以独立计算。

       * 每两份之间只有边界上的值相互影响；可以不切成方块网格，而是切成六边形的网格，这样每一个格子有六个相邻格子、更科学一些，于是只需要在算边上少量的点时做同步。

       * 块内计算基本可以并行，于是同步与上锁的时间很小，绝大部分时间都在做本地运算，机器与集群就能既 scale up 又 scale out。

   * **Linpack 与线性方程组**

       * Linpack 是评估 HPC 用的基准程序，简单来讲就是求解一个稠密矩阵的线性方程组 $Ax = b$；这个矩阵可以非常大，它本身也是一个可以分块计算的任务，所以能跑在超级计算机上。

       * 重要性来源：所有的非线性系统（比如用微分方程来定义的系统）都可以用牛顿法变成一个线性的系统，就像有限元那样；哪怕是稀疏的矩阵，它的局部最后也会分解成很多稠密的线性方程组，稠密的解完再拼起来。

   * **令人尴尬的并行（embarrassingly parallel）**

       * > **定义**：整个计算图几乎不需要什么同步和通信的并行问题。

       * 与时间步模拟的对比：时间步模拟先算 $t=0$、再算 $t=1$、再算 $t=2$，每个点的计算可能和相邻网格有依赖，所以是一层一层的；embarrassingly parallel 则可以放出几百万、几千万个计算任务，算完以后最后收一个结果就行。

            ```text
               分层依赖（时间步推进）              令人尴尬的并行

                t=0   A  A  A  A                    +--> 任务 1 --+
                      |  |  |  |                    +--> 任务 2 --+
                t=1   A  A  A  A                    +--> 任务 3 --+--> 汇总
                      |  |  |  |                    +-->  ...      |
                t=2   A  A  A  A                    +--> 任务 N --+
            ```

       * 典型实例：tree search（围棋第一步十种下法、第二步又有十种，几十层就有上百万棵搜索子树，可以分配到机器上；fork-based DFS 在 20 核上快十倍就意味着本来一分钟的任务只要六秒钟）；Monte Carlo（每次采样独立，采样一千万份求均值可以平摊给多台机器）；视频编解码（关键帧切好之后，关键帧与关键帧之间的一段视频完全独立）。

## 分形迭代：从 Julia 集到 Mandelbrot 集

   * **迭代 $x_n = x_{n-1}^2$ 的收敛性**

       * $x_0 = 1/2$ 时序列是 $1/2, 1/4, 1/16, \dots, 1/256$，越来越小、不停地往左跳。

       * $x_0$ 靠近 $-1$ 时类似：第一次会跳到一个接近 $+1$ 的地方，然后才往 0 的方向跳；$x_0$ 往其它地方走就发散。

       * 结论：$|x_0| \le 1$ 收敛（$x_0 = \pm 1$ 对应 1 这个不动点），$|x_0| > 1$ 发散。

   * **Julia 集（Julia set）**

       * 把完全一样的序列放到复平面上，区别在于复数的乘法是带旋转的：它一部分是标量计算，一部分是旋转。

       * 收敛判定：只要 $x_0$ 位于单位圆（半径为 1 的圆）里面，这个序列就是收敛的。

   * **Mandelbrot 集（Mandelbrot set）**

       * 规则换成 $x_n = x_{n-1}^2 + c$：迭代的规则不动，把迭代的起点固定下来，改一改参数 $c$ 在复平面上的位置，就得到完全不一样的图形。

       * 图有一大块是收敛的，另有一些地方发散，而在收敛与发散的边界上情况非常复杂；把边界上的任意一小块无限放大，图案依然精细，放大非常非常多倍之后里面还是无穷精细的图案。

   * **这类图形的并行方式**

       * 每个像素都是一次独立的计算，甚至可以把每个像素分配给某一个线程去算；没必要这么极端，分成一块一块、每个线程负责其中一部分像素就够了，块与块之间没有任何共享状态。

       * 自己写线程库走生产者消费者：把图像切成一百万个、一千万个甚至更多的任务块，每个任务块里装几万或者几十万个像素，消费者每次从队列里取出一个任务，把那些像素填进一个巨大的数组。

       * 对非专业人士友好的做法是 OpenMP：只写串行程序，把循环并行化只需一行 pragma，不用知道系统里有多少个 CPU。实测画一张 6400 × 6400 的图，1 个线程约 18 秒，16 个线程约 3 秒。

            ```text
               1 个线程    :  ~18 s   一条一条扫描像素
               16 个线程   :  ~3 s    同样的代码，只多了一行 pragma
            ```

       * 一个学过 C 的物理系同学不需要知道任何线程概念，只要记得一句"魔法咒语"，就能把超级计算机里的 128 个线程都利用起来。

   * **让 AI 并行化代码时的提示**

       * 直接要求并行化，AI 大概率给一个 Pthreads 实现（它默认你的机器上不一定装了 OpenMP），会往代码里加入各种同步，改完可能变得自己都看不懂。

       * 在 prompt 里多加一句"你可以用 OpenMP"，它就有可能在尽可能少改动代码的前提下完成并行化，dirty work 交给编译器去做。

## 并行数据结构：从一把锁到锁的拆分

   * **锁的拆分（lock splitting）**

       * > **定义**：为数据结构的不同部分分别上锁，而不是用一把大锁盖住整体；最好情况下绝大部分时候线程都是并行的，只有在确实要访问同一个元素的时候才会去争抢同一把锁。

       * 前提是所有数据结构天生都有局部性：它们在内存里是分散存储的，不管是很大的数组还是二叉树，要么描述一个集合（ordered set、map、dictionary），要么描述一棵树或一个图，越大越是一个有局部性的结构。

       * 所以两个线程同时访问一个数据结构时，很可能访问的是两个不同的元素，它们之间根本没有冲突——一个线程问 5、一个线程问 7，或者一个线程删 2、一个线程读 7，都可以并行执行；但一个线程想删 7、另一个线程想询问 7，就一定得有一把锁保护起来。

   * **三种常见做法**

| 做法 | 用的东西 | 划算在哪里 |
| :--- | :--- | :--- |
| 用原子指令 | 一条原子指令，比如原子的 `sum++` | 临界区小到只剩一次计数、一次 slot 分配 |
| 区分读锁和写锁 | `pthread_rwlock_t` | 读多写少：读与读之间本来就不冲突 |
| 把锁做划分 | 为数据结构的不同部分分别加锁 | 数据结构各部分的访问本来就互不相关 |

       * 如果你能用一条原子的指令，就尽可能用原子指令。

       * 读写锁的不对称在于：允许同时有多个线程持有读锁（集合是 `1, 3, 7` 时两个线程都想读 3 完全 OK），但只有一个线程能持有写锁，并且一旦有人持有写锁，读锁也不能获得。

       * 读写锁与原子指令都比较难用，使用的时候要谨慎——读写锁没问题，原子指令需要更多的并发编程知识。

   * **原子指令分配 slot 的例子**

       * 维护一块非常大的日志内存，任何线程执行一次分配就在数组里放一条日志；每个线程都产生日志但不上锁，只用一个原子的计数器 `n`：原子地把 `n` 加一就得到一个空的 slot，拿到空 slot 之后再把数据写进去。

       * 相当于有两个指针：一个不停地往后跑（分配），一个从前往后跑（回收），于是会在线程里回收另一个线程分配的单元——这是非常常见的 bug 来源。

       * 这个程序实际上是有 data race 的，但这个 data race 在实际中是正确、安全的。

   * **松散计数器（sloppy counter）**

       * > **定义**：牺牲掉一定的、会带来延迟的精度（即放松其它线程看到 `sum++` 的及时性），把计算留在本地，从而让程序能够 scale up。

       * 做法：为每一个线程创建一个本地的 `sum_local`，所有的 `++` 都打在自己的 `sum_local` 上；每当本地的 sum 加到 100，就上锁把这个 100 加回全局的 sum，然后把自己的本地 sum 变成 0。

            ```text
               +-------------------+                    +----------------------+
               | local = local + 1 |   flush a batch    | lock; global += n    |
               | 99 of 100 times   | -----------------> | local = 0; unlock    |
               +-------------------+                    +----------------------+
            ```

       * 收益：一百次自增里有九十九次只碰线程自己的本地变量，不产生任何跨 CPU 的传播；只有攒够一批才去抢一次锁，把这批增量一次性并进全局。

       * 代价与边界：没有人能够看到一个真实准确的 sum。load 到 sum 的那一刻，不管上没上锁，看到的是 100 还是 101 都没有意义，等执行下一条指令时已经不知道 sum 是多少了——看到的 sum 永远是旧的值，除非持锁做 `sum = sum + 1`。

       * 回写触发条件可以是"攒够一个值"，也可以是按时间：每过一毫秒或者设一个一毫秒的 timeout，只要超时了、哪怕没攒够也把本地 sum 加回去，从而保证任何人读到的都是 1 毫秒之内的值。

       * 现实应用：现在看到的点赞数就是这么实现的，它不代表那个真实精确的点赞，可能需要延迟一会儿才会变精确。

       * 与数据结构的对应：把 `sum` 想象成一个 list 的 append——每加 1 就是往 list 上 append 一个节点，问 sum 是多少就等于问这个 list 的 size；本地攒一个 list，攒到 100 就对全局的 list 上一把锁，把这 100 个节点一并拼上去。

   * **为什么放松可见性能换到性能**

       * 每一个 CPU 都是独立的，每个 CPU 都有自己独立的 L1 cache。缓存不是可有可无的：如果让每一条指令都去访问内存，那个内存非常非常慢，CPU 根本不可能运行在 3 GHz、5 GHz 上。

            ```text
                    CPU0                      CPU1
                +-----------+             +-----------+
                |  L1 SRAM  |             |  L1 SRAM  |
                +-----+-----+             +-----+-----+
                      |                         |
                      +------------+------------+
                                   |
                            +------+------+
                            | shared L2   |
                            +------+------+
                                   |
                            +------+------+
                            |     RAM     |
                            +-------------+
            ```

       * 一次 store 要让别的 CPU 看见，就必须沿着总线把新值传播出去（不同 CPU 实现不同，可能是一个环，也可能是一个目录），而且大家改的是同一个地址上的同一个变量，还要有额外的协议让别人知道我改过这个内存地址。

       * 所以还有另一条路线：不要着急让别人看到这个 101。

## 线程局部存储

   * **线程局部存储（thread local storage，TLS）关键字**

       * `thread_local` 从 C++11 开始有，C23 正式引入，所以 C 语言里面也有了；以前只能用 `__thread`。

       * 语义：`thread_local` 类型的变量会自动在**线程创建的时候**得到一份拷贝；它可以是任何类型（可以是一个 struct、一个指针），也可以赋初值。

       * 用法：只要定义一个 `thread_local int sum_local;` 并在 worker 里用它，每个线程就都有自己的 `sum_local`，不必再写 `sum_local[tid]` 这种难看的形式。

       * 实验：`thread_local int x = 100;` 然后在 worker 里 `x++`，四个线程取出的 `x` 地址各不相同，而加 1 之后的值都是 101；如果写成普通的 `int x = 100;` 就是 data race，可能看到 101、102、103、104。

       * > **易错点**：⚠️ 在函数的作用域（非全局作用域）里定义 `thread_local int`，编译器会直接报错。因为 `thread_local` 的含义是每一个线程一份，而定义在函数里意味着每一个栈帧、每次函数调用都有一份，这两个含义本身是冲突的。

   * **TLS 的寻址方式**

       * 编译器清楚地知道每一个变量定义成什么样（包括 `const`、`volatile` 这些 modifier），于是访问不同存储位置的变量用的寻址方式也不同：

| 变量 | 存放位置 | 访问方式 |
| :--- | :--- | :--- |
| 全局 `int x` | 全局数据区 | RIP（PC）相对的寻址 |
| 函数里的局部 `int y` | 当前栈帧 | RSP 相对的寻址 |
| `thread_local int x` | 线程自己的局部存储 | 相对于线程局部存储的一个 offset |

       * 对一个 `thread_local` 变量来说，要的就是一个"相对于当前线程"的基准，寄存器不够用了，x86 里面就"偷用"了 FS 寄存器。

       * 用 `objdump` 看自己编译出来的这段演示代码，会看到访问被翻译成 `FS + 一个常数偏移量` 的 load 或者 store。

       * 把 `gcc` 换成 `musl-gcc` 再加上 `-static`，用 musl 的 gcc 和静态链接可以编译出更干净的代码，它能运行，地址不太一样但行为还是一样的。

   * **`thread_local int x = 42` 的 42 是谁写的**

       * 42 本身必须存在于 ELF 里，它落在 ELF 的 `.tdata` 段（TLS 数据段）中。

       * 对照全局变量：如果数据区里有一个 `.data` 的 `x = 42`，ELF 文件里就有一处存着 42，loader 在 load 的时候把 ELF 整个搬到内存里，这个 42 就被搬进去了，搬一次就够。

       * 对照局部变量：函数里的 `int y = 42`，编译器会在这个函数的头部编译出一条 `mov` 之类的指令，把 42 写进 `y` 里。

       * 线程局部的初值不能只做一次：内存里等于 42 的那个 `x` 必须在每一次线程创建的时候都被执行一遍——每创建一个新线程，就要有一个 42 的拷贝。

       * 真正做这件事的是创建线程的那个线程：`pthread_create` 先 mmap 分配一个线程栈、同时分配 TLS 的区域，然后调用一个叫 `copy_tls` 的函数，把 ELF 里的 `.tdata` 复制到这个线程的 TLS 区域里去。

            ```text
               struct pthread (每线程一个)              TLS 区域 (每线程一个)
               +--------------------------+             +------------------+
               |  ...                     |             |  x = 42  (拷贝)  |
               |  pointer to TLS data ----+-----------> |  ...             |
               |  ...                     |             +------------------+
               +--------------------------+

               pthread_create: mmap 线程栈
                             + 分配 TLS 区域
                             + copy_tls: 把 ELF 里的 .tdata 拷进 TLS 区域
            ```

## malloc 与 free 的性能工程

   * **性能指标要和 workload 绑在一起看**

       * 算法与数据结构课上的习惯是死盯 worst case，而真实的系统要的是在真实的一个分布下的表现：业务系统收到的内存分配序列、集合收到的 insertion/deletion 序列，都符合现实物理世界中的概率分布。

       * > **结论**：实用的性能指标 = 真实分布下的表现 + 一个可以接受的 worst case 上界，两边都要，缺一个都不行。

       * worst case 不能太坏还有一个安全上的理由：如果你的算法有一个指数级的 worst case，别有用心的攻击者就可以通过发那种特别差的请求让系统变得非常非常慢。

       * 哈希表的复杂性攻击（algorithmic complexity attack）：HTTP 请求可以带查询参数，请求里的 `a=b&c=d` 这种请求字符串会被插入一张哈希表；只要精心构造这些字符串让所有的 key 都映射到同一个桶里，就可以让服务器变得很慢。它打的不是加密，而是"你的数据结构在构造出来的输入下会退化成什么复杂度"，这条也解释了为什么实用系统里的哈希表实现要考虑防碰撞、甚至要随机化哈希种子。

   * **malloc/free 的 workload 分布**

       * 大对象不是凭空出现的：哈希表 resize 之后装不下了要乘 1.5 倍大小，就得分配一块很大的新内存或者回收一块很大的内存；或者需要映射磁盘上的一个大文件作为非常大的缓冲区块。

       * 推论：一旦分配了一个很大的对象，之后一定会读写它很多次；反之，分配一个 100 兆的对象只读写里面几个字节然后 free 掉，这是一个 performance bug——开一个能装 100 万的哈希表只用三个元素就 free 了，就应该用一个更紧凑的 set 或者 map。

       * 对象越小，创建和分配越频繁、生命周期越短；对象越大，越倾向于稳定地长期停留在内存里。

       * 小对象是临时的字符串，可能会在这次请求里被贴到最终的文本里然后再也不用了，很多、很琐碎、生命周期很短；中等大小对象比如要生成的一个 HTML 请求字符串，生存期比那些零散的小对象再长一些；大对象是几兆到几百兆、用来维护整个系统全局状态的大数据结构，越大越稳定、停留时间越长。

       * 所以想通过这个实验几乎只要管好小对象就可以了：小对象的分配回收的 scalability 是主要瓶颈，这与 `sum++` 是同一个问题。

   * **slab 分配**

       * 大块内存直接用 mmap 分配就好，这样在整个内存里可以得到很多块 slab；slab 的大小定得比较随意，1 兆、4 KB、8 KB 都是 OK 的，浪费一点内存并不很糟糕。

       * 核心目标是让小对象的分配和回收都能直接在本地完成：每个线程（真正实现时一般还会做成 per-CPU 的池子）都可以持有一些 slab，要分配就直接从自己的 slab 里拿，slab 内部是空闲链表、二叉树等任何一个传统经典的结构都可以。

       * 只有"自己的 slab 用完了、去找系统要一块新的 slab"这条慢路径才需要一把全局的大锁。

       * 这个 slab 的锁上锁非常快，因为绝大部分对象都是线程自己分配、自己回收的——比如为了贴进 response object 里的那个临时字符串就是如此；只有别的线程试图 free 这个 slab 里分配出来的对象时才需要来碰这把锁。

       * 这就是一个非常安全、也非常典型的设计：像一张属于自己的桌子，钥匙就摆在桌上，一般别人都不会拿，绝大部分时候分配或回收都是 $O(1)$ 的。

   * **分离空闲链表（segregated free list）**

       * 更快的一种做法是浪费空间换极简：把 slab 切成等大的小块（按 16 字节算就 16 字节一块地切下去），把所有空闲小块串成一条空闲链表；再准备 32 字节的切块，同样用一条 free list 串起来，以此类推，于是每一个线程就持有各种不同大小的 slab。

            ```text
              size class 16B :  [free] -> [free] -> [free] -> ...   pop / push 都是 O(1)
              size class 32B :  [free] -> [free] -> ...             malloc(17) 落到这一档
              size class 64B :  [free] -> ...
                    ...
              每个线程持有若干种 size class，每一种一条 free list
            ```

       * `malloc(17)` 会落到 32 字节那一档，直接从对应链表里 pop 一个空闲块就得到了空闲空间，要归还就往对应链表里插入——找到大小对应的那个桶再做一次链表操作，所有操作都是 $O(1)$，是一个非常非常高效的 fast path。

       * 慢路径只在某一档的所有内存都被分配完时才走：去问系统要一个新的 1 兆 slab（这时候上一把大锁），然后再返回来切分使用。

       * 这种 segregated free list 的做法 1964 年就提出来了。

   * **先自己摸一遍工具，再交给 AI**

       * 做性能调优时"一把大锁保平安"能过几个 easy test case，但那个 hard test case 过不了；在正确的基础上，始终记得 premature optimization is the root of all evil。

       * 用 `sperf` 这类 profiler 和 trace 自己去找并行计算里面最 intensive 的那部分；自己用过之后才会对这个工具有印象，下一次会告诉 AI"你也用一下"，而不是让它直接帮你逃课。

## 用户态轻量线程：协程

   * **线程不是免费的**

       * 线程需要内存，线程的栈就在地址空间里：用 `pmap` 去看一个多线程的程序，能看到一块一块的线程栈；Linux 里一个最简单最小的线程默认有 8 兆的栈，但这个栈是按需分配的，实际只使用栈顶上的一小部分。

       * `/proc/PID` 下的所有文件，都是操作系统内核为这个线程或者进程维护的数据结构的一次反射：command line、environment 这些信息都是内核帮我写进去的，每一条都需要内存。`/proc/PID` 下还有一些目录可以 `cd` 进去、在里面却看不到，有些线程就藏在这后面——操作系统不保证"目录列表"和"能否进入"这两者一致。

       * 每一个进程其实也是一个线程；如果系统里有 1 万个、甚至 100 万个线程，每一个线程都有一个 PID、都有一个线程号，为了维护这些内核里的全局数据结构，操作系统也需要付出代价。

       * 实测办法：一个几乎不占用任何额外内存的最简单程序，从命令行读入 $n$ 并创建 $n$ 个线程；在进程启动之前先看一遍系统里各种资源的状态，创建完再看一遍，变化量除以线程数量就是每一个线程的资源使用量。创建 1000 个线程算出每一个线程大约要 16.9 KB，这个资源包括内核里各种数据结构增长所需要的开销。

       * > **注意**：1 万个内核线程已经不是小数目了，别一上来就试 100 万个。

       * 切换的代价：线程切换要么发生中断，要么因 `read` 之后发现系统里没有数据而让出，这些切换都要去操作系统里面走一圈，涉及保存寄存器、恢复寄存器；因为 CPU 只有一组寄存器，必须先把当前线程的寄存器保存下来，再把另一个线程的寄存器放到当前的 CPU 上。

   * **两条把计算图跑好的路线**

| 路线 | 做法 | 代表 |
| :--- | :--- | :--- |
| 把线程做轻 | 保留多线程编程模型，把 spawn/join 的代价压到接近函数调用 | 协程 coroutine、goroutine |
| 改变执行模型 | 让语言本身能描述计算图，在程序里直接写并行与依赖 | promise、future、async/await |

       * 想要的东西是：计算图想怎么写就怎么写，写完以后几乎没有任何额外的开销，无论计算图的每一个节点上面做多少事情，系统都能帮我们很好地调度它们。

       * 问题所在：计算图的一个节点就是一次计算，而编程语言里面对计算的抽象就是函数，计算节点的开销却远远大于一个函数调用的开销。

       * 现实约束：函数调用是**指令集**支持的一条 `call` 指令，所以一个线程的开销不可能和函数调用完全一样小。

   * **Python 的 generator：一个线程里的许多个栈**

       * 前提问题：在操作系统没有任何线程库（没有 `pthread_create`、没有 `mutex_lock`）的时候，依然有可能实现 spawn 和 join。

       * 关键观察：`[TWorker(k) for k in range(1000000)]` 只是把 100 万个 generator 对象创建出来，它们还没有运行；而 `current.send(None)` 相当于一次"函数调用"——控制流进入那个 generator，从上次 `yield` 的地方继续往下执行，直到再一次遇到 `yield`，又把控制权交还给调用者。

       * `TWorker` 是一个死循环（`i = 0`，然后 `i = i + 1`，无穷无尽），所以它真的是一个"线程"；`yield` 把当前函数的执行状态暂存下来、直接返回到调用者，下一次再 `send` 同一个 `TWorker`，它就会从这个状态继续往下执行。

       * 运行效果：创建完 100 万个之后才开始调度，每一个 `TWorker` 都有自己的线程号、自己的名字，有的 `i = 1`、有的已经到 `i = 2`、有的已经到 `i = 3`——看起来就好像是线程一样；唯一的区别是线程的切换不是由操作系统强迫的，而是主动 `yield` 的，而且整个程序里只有一个线程。

       * 与 Simple C 模型的对应：C 语言里每一个函数有一个栈帧，每个栈帧里都有一个 P-program counter（PC），另外还有一份 globals；Simple C 的每一次执行就是从 top-most frame 的 PC 上取一条语句来执行。

            ```text
               单线程的 Simple C                多线程的 Simple C = 有好多个栈
               +------------------+           +-------+  +-------+  +-------+
               |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
               |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
               |  frame:  PC      |           |  PC   |  |  PC   |  |  PC   |
               +------------------+           +-------+  +-------+  +-------+
                    globals                       globals（外加数据竞争的困扰）
            ```

       * 命名上的区别：如果它是操作系统实现的，我们一般叫它线程；如果是自己模拟出来的，可以叫它一个协程；而在 Python 里面它是一个 generator。

   * **有栈协程：汇编与 `setjmp`/`longjmp`**

       * 原理简单得有点过分：C 语言的程序编译成汇编以后，每一次函数调用就是一条 `call`、每次函数返回就是一条 `return`，它根本不管你这条栈是在哪儿的；所以完全可以用 `malloc` 去分配一段栈的空间，然后用一条 `move` 指令把栈顶指针 `rsp` 挪到另外一个地方。

            ```text
               切换前                              切换后
               rsp ---> [ 栈 A 的栈顶 ]            rsp ---> [ 栈 B 的栈顶 ]
                        ...                                  ...
                        栈 A 原封不动留在那里                栈 A 原封不动留在那里，等下次切回
            ```

       * 用 `setjmp` 保存寄存器现场，用 `longjmp` 跳回去，再配上一次栈切换，就可以实现和 Python 版本完全一样的功能；x86-64 和 ARM64 都可以工作。

       * 写法：写一个 `coroutine_create` 创建协程，创建好以后调用这个协程的 entry；entry 里可以 `i++`、可以给协程分配一个 buffer，本地计算做完以后就做一个 `yield`，而 `yield` 调用 `longjmp` 跳转到另外一个协程去工作。

       * 代价：这时线程的切换不是被动的、不是由中断驱动的，而是主动的；如果程序在 `while (1)` 里死循环、不做 yield，那就再也不会切换，其他所有的"线程"都会饿死。

   * **无栈协程：能写闭包就够了**

       * C++20 专门引入了一个关键字 `co_yield` 来实现完全一样的功能；理论上任何一个现代的编程语言，只要它能实现闭包——也就是说它可以捕获作用域里面的变量、生成一个函数对象——就都有能力去实现这样的堆栈切换。

       * 原因还是那个：任何能做闭包的编程语言，都可以在函数执行到某个时间点的时候创建一份这个函数状态的快照，把本地的 `x`、`y` 放到内存里；一旦 `x`、`y` 放到内存里，再把函数的 PC 记下来，这个函数的运行状态就封存了。

       * 封存以后就可以做一次栈切换，或者甚至不做栈切换、只做一个跳转跳到别的地方去执行——C++ 的 coroutine 和 Python 的 generator 就是这样"无栈"的实现。

       * > **易错点**：⚠️ 无栈协程并不是没有状态，而是不持有独立的栈——状态被搬到了堆上的对象里；而为每一个自己实现的线程真的分配了一段栈的，是有栈协程。

   * **用户态线程的两个麻烦**

       * 麻烦一（I/O 会把所有人拖住）：T1 执行 `read` 会执行一条 `syscall`（ARM 上是 `ecall`）指令进入内核，内核发现要读的文件或管道里面还没有数据，这个线程就要等待；在操作系统里面等待的时候 T1 就没有办法执行 `yield`，哪怕 T2 可以继续执行计算，T2 也得跟着一起等。

       * > **易错点**：如果我创建的是两个真正的操作系统线程，T1 进入 `read` 等待的同时 T2 的计算依然可以继续；但当这个"线程"是在用户态模拟出来的、整个进程只有一个真线程时，一旦 `read` 进入内核睡眠，别人就都算不了了。

       * 麻烦二（互斥锁一用就死锁）：线程里有一张桌子、桌上有一把钥匙，而桌子是在这个线程里——现在只有一个真线程，虽然模拟出了好几个栈。T1 `lock` 把钥匙拿走，然后 `lock` 之后会 `yield`，控制流到另外一个"线程"去执行；那个线程也执行 `lock`，拿不到就进入操作系统去等待。于是这个真线程正在等一把它自己已经拿在手里的锁，程序永远停在那里。

       * > **结论**：互斥锁是操作系统为线程设计的同步原语，在操作系统眼里用户态模拟出来的这几个协程全都属于同一个线程，所以在协程里面不能用互斥锁来实现同步。

       * 唯一的缓解：只要隔一段时间就加一个 `yield`，就能构造出一个"它们都在均匀并发、雨露均沾地执行"的假象；但互斥锁依然不能用。

   * **出路：`O_NONBLOCK` 的 read 与 epoll**

       * 用 `O_NONBLOCK` 打开文件之后，所有 `read` 系统调用的行为就变了：

| 打开方式 | 管道里没有数据时的 `read` |
| :--- | :--- |
| 默认（阻塞、同步） | 一直等到有数据来为止 |
| `O_NONBLOCK` | 立即返回，返回值为 `-EAGAIN` |

       * 如果读到了数据，它照样返回读到了多少个字节；而如果返回值是 `EAGAIN`，就可以 `yield` 出去，之后应该再跳转回来重新 `read` 一次——因为做的是一个 non-blocking 的 `read`，期间可以切到另一个可以计算的协程上去。

            ```text
               T1 计算 ---> read 管道 ---> 返回 -EAGAIN ---> yield 出去
                                                               |
                                                               v
                                                    T2 继续计算（不再被 T1 拖住）
                                                               |
                                                               v
                                          再次轮到 T1 ---> 重新 read 一次
            ```

       * 这种 non-blocking I/O 和模拟出来的线程组合在一起，在一个线程里面就几乎可以得到任意多个线程的效果和行为。

       * `epoll` 支持的功能是：让手上拿一大把文件描述符，只要任何一个文件描述符上有数据了，它就会返回；它意味着手上多了一个能同时和一整批并发活动打交道的东西——可以同时监听多个文件描述符，谁来数据谁就放我继续往下走。

       * 换个角度看，这其实就是一种同步：同步就好像信号量，可以一口气 P 好几个信号量，任何一个来了都可以继续；文件描述符给的是同一种能力。

       * 而文件描述符比信号量还多一层好处：它不是"每个线程一个"的东西，而是操作系统里一个实实在在的对象，不管是在一个线程里模拟出来的那一堆协程，还是别的进程里的某个线程，都可以访问同一个 fd。

       * > **结论**：`mutex_lock` 是绑在线程上的，文件描述符不是；正因为 fd 是一个能被多方共同引用的对象，它才有资格充当协程之间、甚至跨进程的同步手段。

       * 多路复用机制会在操作系统里维护一份数据结构，用一份结构同时盯着上百万个文件描述符也没有问题；`eventfd`、`timerfd` 这类更专门的机制无一例外都建立在 fd 之上——一个线程准备好之后往自己的 `eventfd` 上写一下相当于对这个文件描述符做一次 V 操作，另一边的主线程用 `epoll` 等着这个 fd，就收到了这个信号。

## goroutine：同步的写法，异步的执行

   * **让编译器替我改写**

       * 出发点：所有的编程机制，出发点都是让人用得更好；如果一套 API 反而给你增加了心智负担，那就该改语言、改操作系统、改系统的设计，把它变成不难用的样子。

       * 假设语言由自己设计：写出来的代码和原来一模一样，还是 `spawn(Tworker)`，`Tworker` 里该 `sleep` 就 `sleep`、该 `read` 就 `read`，而且这个 `read` 就是阻塞语义的 `read`；区别在于编译器在我的控制之下。

       * 遇到 `sleep`，编译器把它改写成"把我放进一个队列，并且标记我：至少一秒钟之内不要再调度我"，然后 `yield` 让别人去跑。

       * 遇到 `read`，编译器把它改写成一段循环——循环里做的是非阻塞读，一旦返回 `EAGAIN` 就 `yield`。

       * > **结论**：我写的是彻彻底底的多线程代码，但它在运行时变成了一个高性能的轻量级线程——同步的写法，异步的执行。

   * **worker 线程与可运行队列**

       * 借助操作系统的 `spawn`，仍然可以为一个共享内存的进程创建多个线程，这些是真正的 worker；同时在它们之上，再创建很多个用"编译器帮你改写"的写法写出来的执行体，这就是 goroutine。

       * 每一个 worker 线程上跑的都是一个死循环，循环里只做一件事：不断从队列里取出当前可以运行的 goroutine 来执行。

       * 一个 goroutine 执行到"把自己标记为睡眠"这一步时，会被从可运行队列里摘掉，一秒之后再放回去；执行到异步的 `read` 而暂时没有数据时同样被移出队列，只是会额外记下它在等哪个 fd，调度程序用 `epoll` 盯着这些 fd，哪个 fd 上有数据了就把对应的 goroutine 重新放回队列。

            ```text
               goroutine 在某个 worker 线程上执行
                          |
                          +-- 遇到 sleep -----------> 移出可运行队列
                          |                                |
                          +-- 遇到 async read -------> 移出可运行队列
                          |      (记下它等的 fd)           |
                          |                                |
                          |      条件满足（sleep 到期 /
                          |      epoll 发现 fd 有数据）
                          |                                |
                          v                                v
                    重新入队 --> 等一个空闲的 worker 取走
            ```

       * 得到的轻量级线程和自己用 C/C++ 模拟出来的协程一样轻，同时又真的能像线程一样在多个 CPU 上并行——这是模拟协程做不到的，那个版本只有一个进程、一个线程，靠 `yield` 在多个协程之间切换，天然用不上多核。

       * 前提是用标准库：如果偏偏自己用汇编写一个阻塞的 `read`，或者在库里硬塞一个阻塞实现，那个在它上面跑的 goroutine 就真的会把底下的线程占住。

       * 于是，一个进程里就出现了一个"小操作系统"：内存是共享的，成千上万个执行体被送到少数几个真正的 worker 线程上去运行。

   * **用通信来共享内存**

       * Effective Go 的说法是：Do not communicate by sharing memory; instead, share memory by communication.

       * 互斥锁、信号量确实实现了同步，但数据的交换依然是通过共享内存完成的：生产者消费者里要有一个 buffer，还得手工维护它——生产者产生一个东西、P 一下，然后再上一把互斥锁，把这个数据放进 buffer。同步和通信是分开的两件事，这带来很大的问题。

       * Unix 时代早就有一个非常好的并发编程机制，在多处理器时代也能并行，它描述的就是一个计算图——管道。

            ```text
               cat *.txt          cat *.cpp           wc
               +--------+         +--------+       +--------+
               | 逐行产出 |--管道-->| 逐行产出 |--管道->| 逐行读入 |
               +--------+         +--------+       +--------+
                    |                  |                |
                    +- 一行数据出来了，下游节点才能工作 -+
            ```

       * Go 把这个抽象搬了进来：可以在任意 goroutine 之间建立 channel，channel 就是管道；可以建很多很多个管道，就像 Unix 里进程可以随意创建管道一样，命名管道还能让两个进程往里写、一个进程从里面读，用管道来管理进程之间的同步。

       * Go 的实现方式是 `go` 关键字，它干的就是 `spawn` 的事；因为创建计算图节点非常轻量、根本不用考虑开销，想创建新节点就直接 `go` 一份。

            ```text
               for i := 0; i < nthreads; i++ { go worker(...) }
               go monitor(...)
            ```

       * 主线程本身也是一个 goroutine：它从管道里收到的消息要么是时间的 tick、要么是 done，等到最后一个线程也结束、收到 done，就把图片文件写出来。

       * Mandelbrot 的 Go 版 worker 有一个 `low`、一个 `high`，负责算图像里被切出来的一条竖带，计算图的切分方式与前面一致，把图像切成若干竖条、每条竖条各自开算；开到 4000 个 goroutine 时同步出了问题，但出问题的不是 goroutine 的数量，而是同步没写对上。

       * > **结论**：这就是"把线程做轻"这条路的答案——线程的创建代价、管理代价、切换代价都可以变得非常低，全部在用户态实现，甚至还可以借助操作系统的线程机制来跑。

   * **术语上的易混**

       * "线程"这个词在前面是在两个意思上用的：一种是用 `spawn` 从操作系统那里要来的真线程；另一种是在用户态模拟出来的轻量级线程，上下文里它们都被叫做"线程"。

## JavaScript：在语言里画计算图

   * **AJAX 与 DOM 操作**

       * 1999 年诞生的 `XMLHttpRequest` 允许在 JavaScript 代码里随时随地请求任何一个其他的网页；这项技术后来被称为 AJAX（Asynchronous JavaScript and XML），当时 Java 的后端应用广泛使用 XML，所以从远程 HTTP 服务器上拉回来的就是 XML。

       * 在 HTTP/1.0 的时代，一个网页就是一个完全静态的页面，想访问另一个网页就得点一个超链接、然后从零开始重新加载一个页面；有了这种异步 API，网页终于可以后台刷新。

       * 再加上 JavaScript 能任意改变文档里的元素（改一改一个浮动小窗的绝对位置 `x`、`y`，就能看到一个东西一路走），两件事凑齐了：可以向后端请求数据、不停地查询整个应用程序后台的状态，也可以改变图形界面，于是任何应用程序能做的事网页也都能做了。

       * jQuery 的 `$` 本质上是一门 DOM 查询语言，现在浏览器里也内置了等价的东西，就是 `document.querySelector`：`$(document).ready(...)` 注册"文档加载结束以后执行这段代码"，`$(...)` 按 id、按元素类型选中某一个或某一类元素，选中之后可以改样式、改文本，甚至直接往里塞新的 HTML，浏览器会帮你渲染好。

       * 早期 HTTP 协议是非常简单的纯文本：客户端发一段文本给服务器说要 `/mypage.html`，服务器把这个文本文件找出来返回一段 HTML，返回里写着 `HTTP/1.1`、服务器是 nginx、状态码是 200。

       * 那个时代的前端甚至还没有 CSS，只能用 `table` 把网页划分成很多个二维网格、精细控制每一个像素的位置，于是诞生了"切图工程师"这个岗位。

   * **基于事件的并发模型（event-based concurrency）**

       * 选型的背景：网页的请求天生会消耗很多时间，而 JavaScript 是一个被鼠标点击驱动、被框的移动驱动的东西，所有事件都是动态的——事件就意味着你不知道它什么时候会到达。

       * 语言定位决定了答案：这门语言任何人都能快速入门，一个 HTML 里直接写一行代码就能工作、零门槛，连编译过程都没有；而写线程、写协程需要理解什么是 data race、什么是 atomicity violation，对一个没有这些知识的人很难用好。

       * > **结论**：需要一个非常简单的、描述计算图的模型——它既并发，又不并发。JavaScript 做了这个决定：基于事件的并发模型。

       * 具体语义：网页加载的时候创建一个事件，鼠标点击的时候创建一个事件，发起网络请求的时候创建一个事件，请求回来的时候又创建一个事件；这个模型选择永远不要和任何人并行，而且永远不能在中间被切换出去——不像线程随时都会被打断切换，也不像协程可以 `yield` 到别的协程。

       * 一个事件一旦开始执行，就必须等到它返回。`$.ajax` 会立即返回、剩下的部分继续执行，等请求真的回来了，浏览器再创建一个新事件去调用回调函数。

       * > **易错点**：⚠️ 这就是为什么 JavaScript 里一个不小心写出的死循环，或者一个真的有性能问题的长计算，会让整个网页失去响应、点什么都点不动——一个事件开始执行，就一定要等它把所有代码都执行完，才能轮到下一个事件。

       * 配套特征：因为跑在浏览器里，这门语言才可以做这样的设计——禁止并行，而且没有任何阻塞式 I/O，操作系统课上学到的那些 `read` 系统调用在 JavaScript 里统统是不存在的。

       * 计算图的形状：不是"先做这件事、等它完成了再创建下一个节点"，而是事件完成之后动态地创建新节点；这张图还有两条分支，success 执行一个函数、fail 执行另一个，实际只会走其中一条。

            ```text
               网页加载 --> 事件 --> 事件 --> ...
                              ^
               鼠标 click -----|
                              |
               $.ajax 发起 ---|  立即返回，代码继续往下跑
                              |
                     +--------+---------+
                请求返回 success     请求返回 fail
                     |                  |
                调用 success 回调    调用 fail 回调
                     +--------+---------+
                              v
                 新事件：run-to-complete，独占执行完
            ```

   * **回调地狱（callback hell）**

       * 假设要做三件事：先登录，登录之后拉 friend list，第三步拉某个 friend 的 feeds；这三件事之间有依赖关系，是计算图天生如此。

       * 写的时候只能先请求登录，登录会有成功和失败，失败了就处理，成功了再去做下一件事，而每一件都是一个函数；一个顺序的 A、B、C 流程必须被拆成三个函数，而且往往是一层套一层——在 ajax 的 success 里创建下一个函数，再调用下一个 API，再来一个函数。

       * 结果是每要做下一件事就多出两级缩进，很快这段代码就没有办法维护了，你也不知道这些回调最后到底长什么样，调试的时候会花掉非常多的时间。

       * 本质问题：一个非常经典的顺序逻辑、一张顺序的计算图，硬生生被拆成了几个部分——它不能用编程语言里的顺序结构来描述"先 A 再 B 再 C"。

   * **Promise：在代码里画计算图**

       * 给定一个 URL，`fetch` 会返回一个 Promise；注意 `fetch` 在执行的时候是立即返回的——JavaScript 里没有同步的 I/O 调用，永远不能等一件很长的事情结束再执行下一个，所以它必须立即返回。它返回一个 Promise（更严格地说是一个 Future），告诉你未来会有一件事情完成。

       * 刚拿到的时候这个 Promise 还是 pending，过一会儿再看它已经 fulfilled，这时就可以去读它的 response。

       * `Promise.all` 可以一次收进去好几个 Promise，它本身就是一个现成的 join；Promise 还可以写 `.then` 和 `.catch`；`Promise.all(...).then(...)` 里 `.then` 这个节点 happen after 前面那几件事，而它们各自也有可能出错。

            ```text
               fetch A --+
                         +--> Promise.all --> .then（后续节点）
               fetch B --+          |
                                    +--> .catch（出错分支）
            ```

       * 写这些的时候每一句都是立即返回的，而计算图一旦被构建出来，里面的 HTTP 请求其实就已经开始工作了；理论上只要等到最后一个 Promise（比如那个 `.then` 或 `.catch` 返回的）完成，就能确保整张计算图里的节点都完成了。

   * **async/await：把计算图写回顺序结构**

       * 就算写了一个很长的 Promise，它还是立即返回的；还是想在编程语言里有顺序结构、选择结构、循环结构这种最符合程序员直觉的写法，于是有了 `async` 和 `await`。

       * 这又是一个编译器替我干活的地方：一个 `async` 函数，编译器会把它包装一下，它不再是普通的函数，而是会 `return` 一个 Promise，所以像异步函数一般不再直接使用，而是被 `await`。

       * `await` 是"什么东西都能 await"的：在网页里直接 `await 1` 它就等于 1，`await "hello"` 就返回 `"hello"`，`await Promise.all(...)` 可以，`await fetchData` 也可以。

       * 编译产物：`a = await f; b = await g;` 会被翻译成一个一个执行的 Promise——先执行 `f`，`f` 执行完了以后 `Promise.resolve(f)`，然后 `.then`，把后面所有的东西都塞进这个 `.then` 里面；接着对 `b` 再递归地做同一件事。

       * 它生成的代码会非常难看，一层一层缩进就像回调地狱一样，但这件事是编译器做的，而我写的时候保持住了计算图的顺序逻辑。

   * **JavaScript 长出的生态**

       * 1995 年 Brendan 加入 Netscape 后被委以重任：设计一门嵌入在网页里的脚本语言，他花了 10 天把 C、Java、Scheme、Self 的各种语言特性融合进去，主要目的是设计一门像 Java 的语言。

       * 因为他的主要兴趣是函数式编程，"函数是一等公民"被放进了 JavaScript 里，编程模型非常灵活，想在上面做什么都可以；同时也留下了很多糟糕的设计，比如 `this` 是动态绑定的，语义和 C++、Python、Java 完全不一样，`0` 可以等于空的 list、可以等于字符串 `'0'`、可以等于空白字符串，而这些值彼此之间又是不等的。

       * 新标准的 JavaScript 是用 JavaScript 自己写的一个 transpiler 实现的：把带 `async/await` 的新版本 JavaScript 编译成老版本的 JavaScript，这样就能在所有浏览器里兼容运行。

       * 在它之上生长出了一个完整的应用生态：从早期的 Angular、Bootstrap，到现在的 Express、Next、Nest；Electron 是把网页变成应用程序的框架（VS Code 就是这么来的），Ink 让人用写 React 的方式写命令行程序。

## 并发执行模型的两条路线

   * **四种并发模型的对照**

| 模型 | 是否并行 | 是否会被中途切换 | 共享内存与数据竞争 | 阻塞式 I/O |
| :--- | :--- | :--- | :--- | :--- |
| 操作系统线程 | 是 | 是，随时被打断 | 共享内存，有 data race | 有 |
| 用户态模拟的协程 | 否，单线程靠 `yield` 切换 | 是，自己 `yield` | 共享内存，有 data race | 有 |
| goroutine | 是，多个 worker 线程并行 | 是 | 共享内存，有 data race | 有，但标准库会把同步写法改写成异步 |
| JavaScript 事件 | 否，事件串行 | 否，run-to-complete | 事件原子，不会并行 | 不存在 |

   * **路线一：把线程做轻**

       * 保留多线程编程模型，把 spawn/join 的代价压到接近函数调用，让编译器把同步的写法改写成异步的执行；Go 走的就是这条路——写法一点不变，代价压到极低。

       * 你写代码的时候还是像写多线程程序一样：spawn 一个函数（当然是一套别的 API），函数放出去它就开始执行了，然后可以 join 这些函数，多线程编程的模型完全没有变；唯一的区别是不能用互斥锁那些同步机制。

   * **路线二：在语言里画计算图**

       * 改变程序的执行模型，让代码能直接描述计算图；JavaScript 走的就是这条路——用事件模型禁止并行、消灭阻塞式 I/O，再用回调、Promise、`async/await` 一层层把计算图写顺。

       * 现在的编程语言里没有计算图的概念，因为语言在设计的时候就没有这种东西：C 语言沿袭的是更早的 B、Fortran、Pascal，是为了描述一个顺序的程序执行而设计的，那个时候的 CPU 是顺序的。

       * 用法上和线程还挺像：相当于把一个 job、一个带了代码的函数丢到队列里，然后可以等待它们完成。

## 指令级并行与功耗墙

   * **顺序执行只是 CPU 精心维护的假象**

       * 回顾计算模型：一个单文件就能装下的计算器有一个状态 `state`，每一次都可以执行一小步往前走，这就是 CPU。

       * 根本原因在于**逻辑门天生就是可以并行的**：信号从左边过来一路走到右边的时候，所有的逻辑门是同时执行的。

       * 因此原理上没有任何本质困难挡着我们去同时执行两条指令：可以一次从内存里取出 64 个 bit 或者 128 个 bit（一条 load 指令就能做到）；可以同时取出两条指令送到两份复制的电路上去译码；可以再加一块电路判断这两条指令能不能并行执行、有没有互相等待的数据依赖；可以用双口 register file 把两个值同时写到两个寄存器里。

       * 所以现在的 CPU，每一个都是一个编译器：CPU 里面有一条非常非常长的队列，每个时钟周期它都会固定地往队列里塞进三条、四条或者更多的指令；指令进了队列之后，CPU 里有一个很大的数据流分析器，它知道哪条指令要等到哪条指令算出来的结果才能继续执行。

       * 只要分支预测一直正确、指令执行的速度又能跟得上（有的指令快，有的指令慢，比如 cache miss 就会特别慢），就可以始终保持一个非常非常高的执行速度。

   * **BogoMIPS**

       * > **定义**：Bogo 就是 bogus（估出来的），它是估出来的百万条指令每秒（million instructions per second）。

       * 用途：标准的计时机制可以读到一个纳秒级精度的时间戳（记录了从 CPU 启动到此刻经历了多少），但在早期、或者 CPU 刚启动、这些处理器特性还用不上的时候，要大致估算时间就麻烦了——比如写操作系统内核或者固件代码时，要实现一个 `delay 20ms`。

       * 做法：假设 CPU 频率是固定的，用一个循环来计数（比如一个 `while` 循环，里面调用 `cpu_relax`，也就是一条确定的指令如 `nop`），只要算出一秒钟有多长，就能算出执行一次 `cpu_relax` 循环大概需要多少时间，进而估出这个值。

       * 观察：这个数值往往大于处理器的主频——处理器可能是 2 GHz，但测出来的 BogoMIPS 比它更大，这某种程度上说明处理器在一个时钟周期里是可以执行多条指令的。

   * **IPC 与指令级并行（instruction-level parallelism，ILP）**

       * > **定义**：IPC 是 instructions per cycle，每个时钟周期完成的指令条数。

       * 测法一：不断地给 `W0` 这个寄存器加 1，因为下一条指令一定要等上一条的结果、下一条又要等下一条，没有任何办法并行；理论上如果 CPU 实现得非常好，这种程序的 IPC 可以接近 1，实现得不好（比如五段流水线）可能还到不了 1。

       * 测法二：不写同一个寄存器，而是 `R0`、`R1`、`R2`、`R3` 各写各的，这就应该能触发指令级并行——同时发射四条指令、同时执行。

       * 实测结果：那个有依赖、最头上不断 `W0 = W0 + 1` 的程序居然也能跑到 1.5 的 IPC；混合了一些指令之后，一个时钟周期甚至可以执行三条指令。

       * 工具：靠 `perf` 拿到程序执行的 instruction counter（指令数量）、cycles（总时钟周期数）这些数据；`perf` 还可以度量 cache miss 的数量、帮助诊断性能问题。计算机系统里也天然存在这样的 counter，比如自己实现 RISC-V 处理器时的计数器——每个时钟周期减 1、减到 0 的时候就发生一次时钟中断。

       * 证明"一个时钟周期里确实可以执行超过一条指令"的完整思路：从 `/proc/cpuinfo` 里读出 CPU 型号与主频 → 查手册知道时钟周期有多长 → 用汇编写没有冲突的指令、尝试各种指令组合实测 → 用工具数指令 → 指令数除以时钟周期数得到 IPC，若大于 1 就说明一个时钟周期确实执行了超过一条指令。

   * **动态流水的账单**

       * 一次加法只需要一个超前进位加法器，乘法、加法都是 ALU 里的固定电路，位运算更省电路，浮点会稍微大一点；但如果要在 CPU 里面塞一个编译器，代价完全不同。

       * 要维护一个 1024 项的 FIFO 队列，队列的每个格子都得有 bit 去维护"这里面有没有东西"，还需要知道队列头在哪里，而且它实际上是循环的（不停地往后长，长到头又回到前面）。

       * 数据流分析器要分析队列里任意两条指令之间存不存在数据关系，理论上这是 $O(n^2)$ 的。

            ```text
                    取指 --> 译码 --> +---------------------------+
                                     |   很长的指令队列（1024 项） |  每周期塞 3~4 条
                                     +-------------+-------------+
                                                   |
                                         数据流分析 / 依赖判断
                                         （队列里任意两条指令，O(n^2)）
                                                   |
                                                   v
                                     执行单元：ALU / 浮点 / 访存
                                                   ^
                                 分支预测正确 ------+  （预测错了就前功尽弃）
            ```

       * 还有更直接的代价：功耗。如果一块电路不动，比如时钟信号没来、或者 enable 信号不在，它就没有功耗；可只要任何一个逻辑门从 0 变成 1、或者从 1 变成 0，它就要发热。

       * 所以整个编译器和动态流水线部分的功耗，比真正去算这条指令（比如把一个 1 写进寄存器）要大得多；这些能量其实是被浪费掉的——它没有参与到实际的计算里，只是为了让计算在时间域上更快。

   * **功耗墙**

       * 整个计算机芯片的热功耗有三个因素：电容（基本没有办法，它跟制程有关，制程变好了这个系数就下降）、频率（不让它动就没有功耗，只要 CPU 跑起来就要耗功）、电压的平方（依靠更先进的制程可以用更小的电压把功耗压下去）。

       * $$P \;\propto\; C \cdot f \cdot V^{2}$$

       * 一旦制程不能变得更先进了，$C$ 和 $V^2$ 基本上就定下来了：没有办法继续加大 buffer size，没有办法让这个编译器变得更复杂，因为封装散热能力是有限的，也就 100 多瓦——就算能把电路做得更大，散热也已经跟不上了。

   * **系统里各种各样的墙**

| 墙 | 卡在什么地方 |
| :--- | :--- |
| 功耗墙 | 封装散热就只有 100 多瓦，再多的电路也散不出去 |
| 频率墙 | 频率不能再往上提了 |
| 内存墙 | 内存带宽有限，缓存与内存之间的带宽成了瓶颈 |
| I/O 墙 | 输入输出的能力到顶 |

       * 内存墙最直观：有的程序写得非常好，几乎每一条都是 load，而且每条 load 之间互相独立、可以并行执行，那很快缓存和内存之间的带宽就成为瓶颈，指令再也发不出去、只能等。

   * **交税**

       * systems 这个圈子里的黑话：收到一份好处，就必须额外付出一些东西。

       * 淘宝上下一个单要发一个 HTTP 请求，那个 HTTP 请求才是真正要的东西；可为了把它从我这台机器发到那台机器，会一层一层经过 TCP/IP、经过本地以太网或者是无线的以太网协议，每一层协议都要在头上和尾巴上加一些东西。

            ```text
               你要发的东西：
                 HTTP 请求（真正的载荷）
                     |  + TCP 头
                     v
                     |  + IP 头
                     v
                     |  + 以太网帧头 …… 帧尾
                     v
                 网线上的比特流  <-- 一路加出来的这些头，就是你交的税
            ```

   * **两条路径：把核做复杂，或者把核做多**

       * 面对功耗墙的关键观察：有没有可能压榨出更多的 performance per watt，让每一个逻辑门的翻转都有意义、都参与到实际的计算当中，而不是像刚才那样用来在"编译器"里算有没有数据依赖、在队列里做 bookkeeping。

       * 同样大小的电路、同样的功耗，可以选择放两个大的，也可以放四个小的，或者 8 个、16 个更小的。

            ```text
               同一份面积 / 同一份功耗，两种选择：

                 [   大核   ] [   大核   ]        [小][小][小][小][小]
                 复杂的动态流水线，编译器复杂        核很简单，编译器很小
                 单核性能强，但浪费的功耗多          单核性能弱，但核多
            ```

       * 放两个大的意味着编译器更复杂、单核性能更强，但有更多功耗被浪费掉；放小的，同样的功耗下就能多塞几个 CPU，单核性能下降，完成同样的工作功耗降低了，如果是并行任务就能在更短的时间里完成。

       * Intel 基本上在 2005 年左右推出了第一款双核处理器：它发现靠"让编译器更复杂"这条路已经要到头了，只能在 CPU 数量上扩展来维持摩尔定律。

       * 后来发现没法让芯片里每一个核都一样大：2011 年左右 ARM 有了 **big.LITTLE** 架构，一块芯片上既塞大的、也塞几个小的，甚至还可以塞一些超小的，当系统处于不活动状态的时候就在能效比非常高的核心上启动。

       * 道理是一致的：同样的面积上处理器越简单、能放的数量就越多，理论上就能把更多的逻辑门翻转投入到实际的计算上。

## SIMD：让一条指令处理更多数据

   * **单指令多数据（single instruction multiple data，SIMD）**

       * > **定义**：让一条指令做更多的事。

       * 动机：动态流水线调度的单位是**指令**，而一条指令只能做非常非常小的一件事——这时候指令做的事情非常小，但 bookkeep 这条指令的代价非常大，相当于收入 100 块有 99 块都交了税。

       * 做法：让一条指令里面操纵更多的寄存器。假设有这么一条把"所有寄存器都加一"的指令，它可以执行很长时间，原来要 32 条指令才能做完的事，现在一条指令放在队列里就做完了（实际的 CPU 设计者当然不会这样设计，这会彻底改变微架构）。

       * 收益：税被分摊成了三十二分之一，而且它依然只占队列里的一个格子，对整个动态流水线的复杂性几乎没有显著增加，这笔账非常划算。

       * > **结论**：SIMD 有一点特别好——它不改变你的编程模型。你依然写一个单线程的程序，但用 AVX-512 就可以用一条指令完成很多数据的写，就好像有好多个线程在同时给你工作一样。这就是 CPU 内部的并行。

   * **MMX（MultiMedia Extension）**

       * 1997 年在 32 位机上引入：为 32 位机增加一组 64 位的寄存器，这个 64 位寄存器可以当成四个 16-bit 的整数来用，然后增加一组指令集；光 MMX 就有 57 条指令。

       * 关键在于它允许同时对这四个数字做某一个操作：给两个 MM 寄存器做加法，第一个通道加第一个通道、第二个通道加第二个通道，四个通道各自相加。

       * 这和 64 位整数加法完全不同：64 位整数相加的时候，低位相加产生的进位会溢出到高位去；而 MMX 这一组指令不会跨通道溢出——两个通道里的数加溢出了，它会保留一个最大值，有点像浮点数的 overflow 和 underflow。

       * > **易错点**：⚠️ 用 SIMD 寄存器做四个 16-bit 加法是四条互不干扰的通道，用 64 位整数做加法有一条进位链把它们串起来；前者不会把累加"串味"到相邻通道。

            ```text
               一条 64 位 MM 寄存器（四个 16-bit 通道）

                 +----------------+----------------+----------------+----------------+
                 |   16-bit #3    |   16-bit #2    |   16-bit #1    |   16-bit #0    |
                 +----------------+----------------+----------------+----------------+
                         +                +                +                +
                 +----------------+----------------+----------------+----------------+
                 |   16-bit #3    |   16-bit #2    |   16-bit #1    |   16-bit #0    |
                 +----------------+----------------+----------------+----------------+

                 四条通道各自相加；溢出被截在本通道内（饱和到最大值），不会进位到隔壁通道
            ```

   * **bitset 用的是同一招**

       * 把一个 32 位整数当成 32 个 1-bit 来用：要维护一个集合，集合刚好只存 0 到 31 的元素（比如 {0, 1, 2, 6, 7}），可以从右往左数——第 0 位对应元素 0，某元素在集合里就把对应的那一位写成 1。

       * 更进一步：用 32 位整数建一个数组，`array[0]`、`array[1]`……就能做一个很大的 bit vector；要查询 `x` 在不在集合里，就先把它除以 8 找到那个格子，再找出格子里对应的那一位。

   * **popcount 的两种实现**

       * 分治位运算：`0x55` 是 `0101`、`0xAA` 是 `1010`，于是 `x & 0x55555555` 取出从第 0 位开始的偶数位，`x & 0xAAAAAAAA` 取出奇数位；把后者右移一位就对齐了，两个数一加相当于每两位一组地加在一起，得到每两个 bit 里有几个 1。

       * 再对这个结果做同样的操作，加着加着就形成了 divide-and-conquer 的过程，最后剩下的就是整个 32 位的 popcount，指令数远比一个 `while` 循环要少。

       * 这种 clever 的位运算实现在现代处理器上性能很差：它对动态流水线非常不友好，里面有大量计算依赖，每一个下一步都要等上一步的结果。

       * 快的做法是查表：把这个 32 位整数分成四个 8-bit 整数，预先处理好每一个 8-bit 整数对应的 popcount 值，这样只需要四次 load——虽然 load 的是不同地址，但只要缓存足够大，这些常用的值在缓存里是热的，四个 load 几乎是并行完成的，或者几个周期内就能拿到，再做几个加法就得到了结果。

   * **寄存器越来越宽**

| 名字 | 宽度 | 含义 |
| :--- | :--- | :--- |
| `mm` | 64 bit | multimedia，多媒体的时代引入；今天已经没有人提多媒体了，但寄存器的名字被永远保留了下来 |
| `xmm` | 128 bit | extended mm |
| `ymm` | 256 bit | 128 变 256 的时候，他们发现没有名字可用了 |
| `zmm` | 512 bit | AVX-512 |

       * 演进路线是 MMX → SSE → AVX → AVX-512；看 `/proc/cpuinfo` 会看到 `sse`、`avx` 这些字样。

       * 这确实是一个平摊每条指令开销的好办法：不管怎么样它都是一条指令，只占队列里的一个格子，而这一个格子可以实现原来要 4 条、8 条甚至更多指令才能完成的数据操作。

       * AVX-512 在短期内基本就是极限了：512 个 bit 这么宽的一个寄存器已经足够分摊掉指令的开销；而且实际上支持 AVX-512 的处理器已经撞上功耗墙、碰到了热密度的极限——只要开启 AVX-512，整个封装的功耗就扛不住，处理器会被迫降频。

       * 指令集支持了更多的数据类型：早期只有整数，后来支持 `float32`、`float64`，完整的 IEEE 754 浮点都装进来了，这很大程度上得益于先进的制程。

       * 支持了更多的运算，像 shuffle 类的运算，一条指令还可以做很多次内存 load；还有 FMA（fused multiply-add），用一条指令实现 $A \times B + C$，这在矩阵乘法里是非常常用的操作。

   * **SIMD 没能解决的问题**

       * SIMD 寄存器还是会参与到 CPU 微架构里的每一样东西：SIMD 寄存器的 load 和 store 依然要经过缓存，而且是和别的指令同一个缓存；它也要参与动态流水线的调度——虽然一条指令分摊下来的计算代价降低了，但这依然占着那个 buffer 里的一个格子，动态流水线本身没有改变，那部分功耗还在。

       * 最终结果是 SIMD 指令会和你的其他指令抢缓存、抢功耗，它可能不是我们真正想要的那个终极方案——真正想要的是大规模并行，让指令调度的代价接近于 0。

   * **超长指令字（Very Long Instruction Word，VLIW）**

       * 想法：不在处理器上做动态的指令调度，而是把指令打包——每一条指令有 256 个 byte，在里面 pack 8 条、16 条甚至可变数量的指令；一个指令 pack 里面的所有指令都是可以并行执行的，由编译器保证它们之间不存在依赖。

       * 收益：译码器可以做得非常简单，看到这里面是什么指令就直接执行，不做任何依赖判断；整个指令序列也都是由编译器生成的，如果某处有个跳转、编译器要保证跳过去之后不会导致动态流水线的问题，一旦会导致问题就要插入一些 `nop` 之类的指令。

       * 结局：Intel 花很大的代价做了一个叫 IA-64 的 VLIW 指令集，结果失败了、没有市场——因为那个时候指令级并行带来的收益和先进制程带来的收益都很大，而且没有迁移成本。

       * 复活前景：它是一个真正能够让指令调度的代价接近于 0 的方案，只是在它诞生的时候编译器技术还有点跟不上；今天在一些特殊的加速器上还能看到它的影子。

   * **活下来的方案：让每个核简单到不留一点浪费**

       * 把一个大的、复杂的 CPU 不断地变简单、变简单、变简单，然后塞进更多的 CPU；如果每一个 CPU 都是一个单周期的 CPU，那就不浪费电路——每一个 CPU 都运行得很慢，但每一次逻辑门的翻转几乎都用在有意义的事情上：指令的译码、指令的执行、load、store。

       * 再激进一点就是让 CPU 里面的一部分是共享的：只有绝对需要的东西才会由多个副本，ALU 必须每个 CPU 有一份，但甚至连译码器也可以让多个 CPU 共享同一个，因为指令集越复杂、译码器越占电路。

            ```text
                         +--------------------------------------+
                         |       共享的译码器 / 调度电路          |
                         +---+--------------+--------------+----+
                             |              |              |
                        +----v----+    +----v----+    +----v----+
                        |  ALU 0  |    |  ALU 1  |    |  ALU 2  |   <- 每个核只保留
                        | 寄存器  |    | 寄存器  |    | 寄存器  |      最必要的执行单元
                        +---------+    +---------+    +---------+

               核越简单，同一块面积上能放的核越多；被共享的部分，开销只交一次。
            ```

## GPU 与 SIMT：从贴块到线程束

   * **图形计算危机的账**

       * 一台机器要跑 60 FPS，也就是把 1 秒钟切成 60 份，每一份里要把屏幕上六万个像素全部渲染出来；而同时期 CPU 能拿出来的预算差不多 10,000 条指令。

       * 摊下来每画一个像素连四分之一条指令都分不到，IPC 小得可怜——连 1 都不到。这笔账怎么算都还不上，可游戏就是跑起来了。

       * 唯一能解释这件事的，是图形绘制本身的性质：它是一个 embarrassingly parallel 的计算——每个像素要算什么跟旁边那个像素几乎没关系，把它们全都轰到并行单元上去做，谁也不用等谁。

       * 1983 年的 NES 用的是一颗 MOS 6502，它的 IPC 是 0.43（小于 1）：它没有任何动态流水线，要去 load 就得等内存控制器、内存总线里那个值回来；它可能连流水线都没有，或者只有一个两级的、非常简单的流水线，一次 load、store 可能就要花三个周期。

       * 但它却有一块非常漂亮的屏幕：六万一千个像素、几百种颜色，所有 NES 游戏都跑在 60 FPS 上。

       * > **结论**：整个体系结构上最重要的一句话是——把"要画什么"和"到底怎么画"分开。CPU 只负责产出一个叫场景描述的数据结构，写清楚这个画面里有些什么东西；剩下的"怎么把它变成像素"，交给一块专门为此设计的硬件。

   * **NES 的场景描述**

       * 所有图元都存在 ROM 里，每一个图元就是一个 $8 \times 8$ 的小贴块；这里一个小贴块只允许有 4 种颜色，4 种颜色意味着每个像素只要 2 bit，于是一个 $8 \times 8 \times 2\,\text{bit}$ 的图元几个字节就装下了。

       * 省到这个地步是因为那 4 种颜色里只有两种是自定义颜色，另外还有一个前景色、一个背景色，甚至还可以留一个是透明色。

       * 更省的一招是**调色板**：贴块本身只存 2 bit 的索引，真正决定它长什么颜色的是给它配的那张调色板；红衣服的 Mario 和绿衣服的 Luigi 用的是完全相同的贴块，只是配了不同的调色板。

       * 描述一个画面只需要两样东西。一个是背景：一大块由规则排列的贴块拼成的东西，比实际显示的区域要大一些；告诉硬件"这一次真正要显示的是这一块"，把显示窗口从左往右移，移到最右边的时候把左边这几列贴块换成新的，屏幕上就出现了卷轴效果——这也是那个年代的游戏基本只能往右走、不能回头的原因，往回卷需要额外换一批贴块。

       * 另一堆是精灵（sprite）：在背景之上还可以把很多个 $8 \times 8$ 的小块摆到画面上的任意位置，这时候位置就不再受"规则排列"的约束。

   * **精灵的属性字节**

       * 每个精灵要交代的信息是：它是哪一个 tile、用哪张调色板、摆在屏幕的哪个 $x$、$y$ 上；此外还有一个 8 bit 的属性。

       * 这 8 位的分配是：有两位选调色板，有几位没有实现，有一位是优先级（相当于 Z 轴的顺序），还有两位是水平翻转和垂直翻转。

            ```text
               ROM 里的贴块表 (每个 8x8, 每像素 2 bit -> 4 色)
                               |
                               |  取 tile 号 + 调色板号
                               v
               +-----------------------------------------------+
               |  背景: 规则排列的贴块图, 比显示屏更大           |
               |        视野窗口在图上滑动 -> 卷轴               |
               +-----------------------------------------------+
                               |
                               |  叠上位置任意的前景
                               v
               +-----------------------------------------------+
               |  精灵: 最多 64 个 8x8, 每个带一个 8 bit 属性   |
               |        [调色板 2b][未实现][优先级 1b][H/V 翻转 2b]
               +-----------------------------------------------+
                               |
                               v
                  line 计数器逐行扫过, 每行切成若干 chunk 并行处理
            ```

       * 翻转位的玩法：想画一个圆不用准备 4 个 tile，一个 tile 做一个垂直翻转、再各做一次水平翻转，四个象限就凑出来了。

       * Mario 里那种碰到就会死的蘑菇"走路"并不是真的让它走起来：蘑菇有两只脚，一只画短一点、一只画长一点，两只脚分别在两个贴块上；程序只要交换这两只脚的位置，再顺手做个镜像翻转，就得到一个只有两帧的动画，然后让它缓慢地向前移动。

       * 全屏动画的做法还是调色板：屏幕上的东西一个都没动，变的是颜色——把调色板整张换成一张全黑的，画面就全黑了，而显示的内容本身完全没有变化。

   * **图形渲染的本质是一个描述加一台翻译机**

       * 图形渲染就是：我们有一个描述，由另一块硬件专门负责把这个描述变成图形。描述的形式有很多种，可以用寄存器（比如一对 XY 寄存器），也可以把一部分东西放进内存（比如一个 sprite buffer，CPU 直接读写那块内存，也就是内存映射）。

       * 所谓的数据结构说到底就是内存里平铺的一堆数据：写过一个 `struct CPU state`，这次不是 CPU 了，这是 `struct GPU state`。**GPU 就是一个程序，它负责把这个 state 翻译成像素**，只不过它是一个 embarrassingly parallel 的程序。

   * **line 与 chunk：逐行扫描的并行**

       * 硬件内部有一个寄存器叫 `line`，它从 0 开始一直往上扫；0 的事情做完了才做 1，1 做完了才做 2——从抽象角度看就是一个设计好的时序逻辑电路。

            ```text
                       line = 0, 1, 2, ... 逐行推进
                               |
                               |  对当前这一行
                               v
               +------------------------------------------+
               | 先算背景: 在贴块图上做加法, 取出该点的   |
               | 背景色                                   |
               +------------------------------------------+
                               |
                               v
               +------------------------------------------+
               | 再遍历 64 个精灵, 看这个像素被几个精灵   |
               | 覆盖, 谁的优先级最高就取谁的颜色         |
               +------------------------------------------+
                               |
                               v
                  若没有任何精灵覆盖这个像素 -> 用背景色
            ```

       * 扫到某一个像素时，先确定它在背景上是什么颜色（做一个加法就取出来了），再对每一个 sprite 去匹配这个像素上到底叠了几个精灵、谁的优先级最高就取谁的颜色——这有点像今天的 Z-buffer，一层一层一层，永远只能看到最上面那一个。

       * 既然逻辑门在电路上本来就是并行的，这里就可以并行地处理多个像素；它也未必一次就处理完一整行像素，可以另外有个寄存器叫 `chunk`——行从 0、1、2 往后扫，同时把每一行切成 10 个 chunk（0 到 9），每进一个 chunk 就知道这个 chunk 要算比如 20 个或者 32 个像素，然后并行地算。

   * **把固定逻辑固化进电路**

       * 关键在于：如果逻辑是完全确定的、写死的（因为数据结构就这么规定，处理逻辑也就这么写死），那理论上完全可以把这部分计算固化到电路里去。

       * > **结论**：你能用固定的电路实现并行化，就能把画图这件事从 CPU 里彻底解脱出来。

       * 最典型的例子是矿卡：把 Hash 的那部分固化到电路里。想明白了，可能就发大财了。

   * **图形引擎长大了：从贴块到贴图**

       * 对图形处理器来说它干的活只是"把一个数据结构变成一幅图像"，没有人规定这个数据结构一定要长成"一块紧密排列的背景加 64 个前景小块"；任何描述方式都行，只要满足两个条件——CPU 有足够算力在一帧时间里生成这样一个描述，硬件能把描述变成真正的图片。

       * 线性变换像黏纸：一张贴图有四个点，可以把它想象成一张黏黏的、有弹性的纸，揪着一个角往外拉纸被拉大了，上面的像素就跟着一起被拉大，于是可以把任意一张贴图放大、缩小、裁剪再拼到画布上。

       * 描述随之改变：不再是"一块一块的贴块"，而是"我有一个 bitmap，我要把它移到屏幕上的 $(x_1,y_1)$ 到 $(x_4,y_4)$ 这四个角去"；这同样是一个 massive parallel 的问题——对每一个像素去迭代过每一个 bitmap，找到对应位置上最上面那层的颜色。

       * 用二维挤压出三维：把一个矩形往某个方向挤压，用 2D 贴图模拟出 3D 的观感——它根本没有深度信息，只是被强行挤压成了那个样子，所以不能转得再大一点，再大一点就要穿帮。

       * > **易错点**：那个梯形看起来是"挤压"出来的，但真实的透视效果其实是深度造成的——你把纸往后放了，于是有了近大远小，才看到梯形。如果没有深度信息，你就无法区分"我是把它挤进去的"还是"因为深度把它放下去的"。

       * 平移不是线性变换，差一个平移就加一个维度：在二维平面上没办法用一个 $2 \times 2$ 矩阵让一个点集整体平移，但把它放进三维空间、给每个点补一个 1 的坐标，就可以用齐次坐标表示。

       * $$\begin{pmatrix} x' \\ y' \\ z' \\ 1 \end{pmatrix} = \begin{pmatrix} \cdot & \cdot & \cdot & t_x \\ \cdot & \cdot & \cdot & t_y \\ \cdot & \cdot & \cdot & t_z \\ 0 & 0 & 0 & 1 \end{pmatrix} \begin{pmatrix} x \\ y \\ z \\ 1 \end{pmatrix}$$

       * 最后一行是 $0,0,0$，平移量写在最后一列；乘的时候这一行和最后一列那一项就把前三个分量消掉，只剩下那个 $t$，其余的变换照常写在这个矩阵里。于是三维世界里的一切变换都变成了"乘一个 $4 \times 4$ 矩阵"，相机投影在齐次坐标底下也是线性的。

   * **着色器（shader）**

       * 观念上的转变：不再提供数据结构，而是直接有一个编程语言——反正都是描述，用数据结构来描述和写一段程序来描述，编译完之后在 GPU 上并行执行，有什么本质上做不到的呢。

       * 顶点着色器（vertex shader）：程序 $P$ 可以理解成一个 `TVertex`，它接收所有的 vertex（当然有一个匹配过程决定哪些 vertex 归它），允许你修改这些顶点——程序里就是几条指令，比如给 `this.x` 赋值、给 `this.y` 赋值，也可以改别的信息比如顶点的颜色。

       * 用法：先用 CPU 构造出一个基础场景，把这个程序（一般是事先写好、经过编译的）烧到 GPU 里，然后显卡每看到一个顶点就执行一遍这段固定的程序，把这个顶点改掉。

       * 顶点的 killer application 是极其轻微的扭动：因为可以改顶点的坐标，就能实现水面的波纹、毛发的摆动——这些东西本来要在 CPU 里算，但每个顶点做的是完全相同的事情，就跟算 Mandelbrot set 一模一样。

       * 像素着色器（pixel shader / fragment shader）：顶点处理完之后得到的是像素 $x, y, r, g, b$，在着色之上再挂一个程序，输入就是 $x, y, r, g, b$，为每一个像素修改它的颜色值，比如 $r \leftarrow r \times 0.9$。

       * 会用调色软件的人更熟：可以做一个蒙版（mask），然后只对蒙版里面对应的像素做调整，写成一段 `if` 判断——你对照片的所有操作都是这样的数值型运算，不管是拉高亮部还是压暗部，背后都有一个数值公式。

       * 法线贴图（normal map）：瓷砖墙要精确描述几何特征需要非常非常多的三角形，显卡扛不住；改成给每一个像素一个光反射的法线，然后在 pixel shader 里根据这个法线和光照方向的夹角做一次内积，算出这个点上的光照应该变强还是变弱。

       * 效果差别很大：没有法线贴图的时候就像把砖墙拍成一张照片、印成一张纸贴在那里再打光，得到很平面的效果；有了法线之后，在不增加任何多边形的情况下就能有非常真实的打光感——缝和面的法线不一样，受到的光也就不一样。

       * > **易错点**：法线贴图只能骗光。你远看基本不穿帮，凑近了还是穿帮——真凑到瓷砖跟前，你会看到凸出来的部分能遮挡凹进去的部分，而这件事法线反映不出来，所以它适合用在中远景上，帮你省多边形。

       * shader 是一段受限的程序：本质上它甚至就是一个字符串，把它交给一个图形库，请图形库编译之后作用到每一个 pixel 上；肯定不能在里面做操作系统的 system call（会直接给一个编译错误），但可以做计算、做分支、做条件判断，甚至可以 load 和 store 去访问贴图上的法线向量这类数据。

   * **把科学计算塞进图片**

       * 大概在 2001 年，有一篇论文用 general-purpose 的 GPU、用可编程的 shader，把科学计算的问题变成图片处理的问题——把矩阵乘法变成一张图片，一旦变成图片就可以用渲染管线里的 vertex shader、pixel shader 去做计算。

       * 变形方法：把矩阵乘法分解成**行列向量外积的和**。外积用得非常少，因为它很浪费——我有一行、有一列，做一次外积就得到一个完整的矩阵，而这个矩阵的 rank 是 1，它里面只有这两个向量的信息，我却要为它付出整整一个矩阵的存储和计算。

            ```text
               矩阵乘法  =  若干"行向量 x 列向量"外积之和
                             |
                             v
                   每个外积 -> 一张 .bmp 图片 (rank = 1)
                             |
                             v
                   送到显卡上, 图片的叠加用 pixel shader 完成
                   (对每个像素做一次加法)
            ```

       * 只要能把它变成 .bmp 送到显卡上运行，而显卡又比 CPU 快很多，这件事就可能是有收益的：一旦变成外积，矩阵就是图片，图片显卡就能处理，最后再把几张图片叠加起来，而图片叠加本身也是一个 for each pixel 的相加操作。

   * **CUDA 与线程束（thread warp）**

       * shader program 的本质是：为一大堆同样的东西，执行同一段代码。

       * kernel 就是那个 pixel shader：在 device 上分配一块内存（比如一块 1920×1080 的 screen 数组），希望显卡为每一个像素 spawn 一个线程，给这个线程参数 row 和 column，它用 row 和 column 算出一个 $f(color)$ 得到颜色，再把这个颜色写到它对应的那个像素上。

            ```text
               device 内存:  screen[1920 * 1080]
                                ^
                                |  写回
               kernel(pixel shader):
                    row, column  --f-->  color  --store--> screen[row*1920+column]
                                ^
                                |  每个像素 spawn 一个线程
               device 上同时活着 1920*1080 ≈ 200 万个线程
            ```

       * 硬性要求是这些线程必须运行同样的代码，所以"每个像素运行同样的代码"这件事在图形上成立，在 CUDA 里也成立。

       * 轻量化的代价取舍：一个线程就算只花 1KB 的开销，乘以 200 万也根本不可能；所以 CUDA 允许你创建非常非常多的线程，但会非常小心地把它们调度到实际的硬件上。

       * 省不掉的与能省的：ALU 肯定得有，寄存器也必须有——没有寄存器就没办法计算、没办法执行指令，所以每个 T-worker 都有自己的寄存器（比如放 pixel 编号、最终算出来的 color、循环变量 `i`）；但程序要执行还缺 program counter，而对 CPU 来说 PC 在自己的核心里面，这也意味着每一个 CPU 里都有一个取指令和译码的部件。

       * 译码是要浪费电路的：指令就那 32 个字节，译码完了以后就是一大堆 if-else——是不是 jump 指令？是不是 load、store？load 的是一个 bit、两个 bit、一个 byte、两个 byte 还是四个 byte？这些信息全部都是一根线，每一根线都要占逻辑门、占触发器。

       * 线程束的做法是：这一捆线程不各自拥有 PC，它们共享一个 PC；在现代 NVIDIA 的实现里一个 thread warp 里是 32 个线程，这 32 个 T-worker 执行一样的代码、共享一个 PC，只有一个 PC 就只需要一个译码单元，电路就省下来了。

            ```text
                  单个 CPU 上的三个线程            一个 thread warp
               +--------+--------+--------+    +-------------------------+
               |   PC   |   PC   |   PC   |    |   共享的 1 个 PC        |
               +--------+--------+--------+    +-------------------------+
               | 译码器 | 译码器 | 译码器 |    |   共享的 1 份取指/译码  |
               +--------+--------+--------+    +-------------------------+
               |  寄存器|  寄存器|  寄存器|    |  寄存器  寄存器  寄存器   |  <- 省不掉
               +--------+--------+--------+    +-------------------------+
               |  ALU   |  ALU   |  ALU   |    |   ALU    ALU    ALU      |  <- 省不掉
               +--------+--------+--------+    +-------------------------+
            ```

       * > **结论**：绝对省不掉的电路（寄存器、ALU）留着，能省的 PC 和译码器只放一份，这样"交的税"相对于真正参与计算的部分就变得非常非常小。

       * 这个编程模型叫**单指令多线程（single instruction multiple threads，SIMT）**：只有一个 PC，但一次把很多个 T-worker 一起往前执行一步。

   * **SIMT 的访存收益**

       * 假设把参数是 30、31、32 的几个 T-worker 放进同一个线程束，所有线程 PC 相同、执行的动作自然也相同：先把 `row` 载入一个寄存器，或者直接算出 `row * 1920` 写到一个寄存器里——对这几个线程来说 `row` 都是 3，所以这个临时寄存器的值是一样的；下一步加上 `column`，寄存器的值就不一样了。

            ```text
               T-worker 30:  temp = 3*1920 + 0
               T-worker 31:  temp = 3*1920 + 1
               T-worker 32:  temp = 3*1920 + 2
                    |
                    |  下一步依然是完全相同的操作:
                    |      store screen[temp], color
                    v
               add 之类的指令: 只是寄存器内部的操作, 无所谓
               load/store 指令: 变成了一条非常长、非常连续的访问
            ```

       * 连续意味着我们可以用好内存控制器的带宽，这就回到了 SIMD：AVX-512 可以一次 load 512 字节的内存到同一个 ZMM 寄存器里，也可以把一个 ZMM 寄存器 store 到 512 字节的内存里；在 SIMT 里这个效果是自然而然就实现了的——32 个线程、每个 4 字节就是一次 $32 \times 4 = 128$ bit 的 store，如果存的是 64 位浮点数那就乘 8、一次 256 bit 的 store。

       * 这个计算模型在内存访问连续的时候就能获得最佳性能；哪怕内存不连续它一样能照做，只是这时候内存要等内存了，没法连续地写，它会先写一部分、再写一部分、再写一部分。

       * 每一个 stream processor 都相当于有一个内存控制单元，它和内存控制器交互，一次最多写 32 个地址和对应的数据，然后负责把这件事办完。

   * **一个流多处理器手里的束不止一束**

       * 实际在 NVIDIA 做的时候，一个流多处理器（stream multiprocessor）可以管理不止一组 32 个线程的线程束，并且可以在多个线程束之间切换。

       * 为什么需要切换：有可能这次 store 打到的是一块全局内存，这次访问不在 cache 里，要等很长时间；为了降低延时，它不是用动态流水线的方式去调度，而是"我手上还有另外 32 个线程"，就把这另外 32 个线程拿来做。

       * GPU 上的编程模型就是用海量的线程，鼓励你创建 200 万个线程，然后靠 GPU 内部高效的调度把这些线程塞满执行单元；这里面有一点点编译器调度的味道，也有一点 VLIW 的那种感觉。

   * **SIMT 的代价**

       * CUDA 程序非常难写：一旦写得有一点点不好，性能就会爆炸。就说 `row * 1920 + col`，如果是连续的，这一次就能生成一条连续的 store、拿到最佳性能；稍微改写一下性能立刻就变得非常差，因为内存访问全部不连续了，内存控制器只能一个字一个字地写，要花非常非常多的时间。

       * 分支非常讨厌：SIMT 只有一个 program counter，写 `if A else B` 时，它会先为这个 if 算一个条件、把条件放到一个寄存器里，然后根据这个寄存器的值，把条件不满足的线程 **disable** 掉。

            ```text
               if A:  ...     编译后 ->  算 condition, 放进寄存器
                                          disable 掉所有 condition 不满足的线程
               else:  ...                -> 线性逻辑
                                          enable 回 condition 满足的那些线程
            ```

       * 所以 `if/else` 就没有了，它变成了一段线性的逻辑——SIMT 不是没有代价的，你没有办法随意地去写任何程序。

## 进程、文件描述符与调试常识

   * **文件描述符（file descriptor，fd）**

       * > **定义**：一张表加一个整数。操作系统把进程的地址空间隔离了，所以进程不能直接访问别人（或者内核里的对象），于是不能用指针，也不能用名字。

       * 进程持有的、编号为 0 的文件（对象）是 stdin，编号为 1 的对象是 stdout，以此类推；`fd = 3` 只是一个数组下标，它背后是操作系统里的一个对象，因为 everything is a file，所以这个下标就叫文件描述符。

   * **fork 之后文件描述符与打开的文件**

       * 有两个设计选择：父子进程各自独立有一个偏移量，或者父子进程共享同一个"打开的文件"、也就共享偏移量；实际的答案是第二个。

       * 理由：如果父子进程都要写文件，只有共享偏移量才是正常的——不然两个进程同时写日志，日志就会被覆盖掉；而且让它们共享同一个打开的文件，shell 里用分号或 `&&` 连起来的两个命令的输出才是**合并**的，而不是交叉错乱的。

       * 结论：共享状态是协作的前提。fork 之后两个 fd 指向的是同一个打开的文件对象，父进程写掉 100 字节之后，子进程接着从第 100 字节往后写。

   * **execve**

       * 函数原型（function prototype）就是一个函数签名一样的东西。

       * `execve` 做的事情是换掉代码、数据和栈，但保持 fd 和 pid 不变。

   * **fork 对 buffer 和 lock 的影响**

       * 一个锁的实现（比如用 futex 实现的互斥锁）在用户空间一定有一个 `int lock`，就是这个变量位于进程自己的地址空间里；正因为它位于进程的地址空间里，所以它会被复制。

       * 于是 buffer 会复制，lock 的整数值也会复制。

       * > **易错点**：⚠️ 如果 fork 的时候锁正被别的线程持有，子进程就会死锁，不能正常运行。

   * **多线程下的 fork**

       * 每一个线程都是异步的、默认情况下相互不同步；执行 `fork` 的时候，每一个线程都可能在执行任何一条指令，它就在 CPU 上跑，你没有办法把它直接停下来。

       * POSIX 对 fork 的选择是：只有调用 `fork` 的那个线程存活，其他线程好像不存在一样。

       * 基本上推荐的、也是唯一安全的选择，就是 fork 之后就做 `exec`——fork 和线程本身是有失配的。

   * **诊断与调试手段**

       * 判断一个二进制文件运行时是否需要加载 `.so`：去看那个 ELF 文件，`ldd` 之类的命令行工具也能干这件事；在 gdb 里可以看，也可以直接读 ELF 的 `.interp` section，它记录了动态链接器的路径。

       * 想知道哪一个环境变量是被哪一条指令改的：用 watchpoint——gdb 提供了一个机制，可以在某一个地址被修改的时候让你停下来。

       * 环境变量存在哪里、和栈有什么关系：先 `print environ[0]` 拿到地址，然后去这个地址所在的 mapping 里查它在地址空间中的位置。

       * 定位执行 `mmap` 的那条 system call 指令：trace 所有的指令，甚至可以单步——写一个 hook，每一次停下来的时候单步执行，并且在每个 hook 停下时都检查一下；从 `_start` 到 `main` 都执行了哪些东西可以用同样的方式处理。

       * 数指令条数可以借用 gdb 的 reverse execution 机制：它的代价是要记录每条指令，而正因为它的代价是记录每条指令，当你想知道一共执行了多少条指令时，正好可以借用这个机制。

       * 动态链接每次要多执行几万条指令，这就是 `ld-linux` 动态加载的代价，而它是值得的——在整个系统里面你都只有一份 `libc` 代码的拷贝。

       * 搜 `struct FILE` 什么都找不到，是因为它实际上是 typedef 出来的 `_IO_FILE`；如果假装没有这个知识也依然有办法——写一个引用这个结构体的 `.c` 文件，用 `gcc -E` 看预处理的结果，定义就露出来了。

       * 要在终端里做一个 UI（Vim 或者 Claude Code 这样的程序），第一件事是能画界面：Unicode 只是其中一部分，真正实现终端主要功能的是 Escape code——因为有 Escape code 才能控制光标的位置、才能擦除屏幕的一部分，有了这些才能绘制一个动态的界面；此外还需要 PTY 这个机制，以及信号的机制（大语言模型在吐 token 的时候要能 Ctrl+C）。

       * 实现 `popen`（读）用的就是管道：文件描述符在父子进程之间是会复制的，只需要关掉合适的文件描述符、腾挪合适的文件描述符就可以了。
