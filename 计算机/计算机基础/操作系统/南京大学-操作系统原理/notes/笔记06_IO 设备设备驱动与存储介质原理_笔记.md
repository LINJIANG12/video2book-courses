# I/O 设备、设备驱动与存储介质原理

## 并发编程的谱系

* **spawn / join**
    * > **定义**：并发编程的最小原语集——spawn 把一个执行流放出去，join 等它回来；有了这两个就能表达任何计算图。
    * 互斥锁、条件变量、信号量用于给计算图补上同步的边。
    * coroutine 配 non-blocking I/O 提供更轻的切换代价，但 I/O 语义要自己处理。
    * goroutine 既能像协程一样轻量切换，又能在多处理器上并行执行，适合写后端业务代码。
    * Promise 与 async/await 把计算图写成数据流。
    * 这些模型本质都是某种 spawn 与 join 的变体，区别在于"怎么并行"被移进了运行框架，不再由编程语言承担。

* **SIMD（单指令多数据）**
    * > **定义**：在一条指令里操纵一个很宽的数据（如 512 bit），把它切成若干块同时做同一个操作。
    * 它摊薄了取指与译码的开销：一条指令做完原本需要多条指令做的多份工作。
    * 代价是要求被处理的数据排布规整，且各份数据执行同一操作。

* **SIMT（单指令多线程）与线程束（thread warp）**
    * > **定义**：多份 ALU 与多份寄存器共用一个 program counter 的执行模型，即 CUDA 的编程模型。
    * 每个线程的 ID 存在自己的寄存器里（如 `index.x`，以及 `x`、`y`），据此算出坐标或数组下标。
    * 遇到 `if (a) ... else ...` 时两个分支被顺序执行一遍，执行某一支时只激活满足条件的线程，其余线程不做任何事。
    * 高性能来自"寄存器里的值各不相同"：各线程算出不同下标后，整束的一次 store/load 落在很长一段连续内存上，内存控制器可以发一个 burst 的读或写。

* **处理器内部指令重排**
    * 从 1990 年代到 2000 年代撑起摩尔定律持续增长的关键技术：在单核内部重排指令，榨出更多并行度。
    * 约 2005 至 2006 年前后失效——单处理器继续做大收益递减，必须在一颗硅片上放更多处理器才能救回能效比。
    * 路线因此从"把一颗核做快"转向"放很多核"，再往后是最大化计算密度与能效比，理想情形是译码部件及其电路的能耗降到零。

## 一次请求在用户态与内核之间

* **环境变量的继承**
    * > **定义**：`execve` 的 `envp` 参数在进程加载时被放到栈上，并在子进程之间继续继承。
    * 在 shell 里设置一个环境变量，它会一路向下传递；因此后续执行的 curl 等子进程同样能读到 API key。
    * 这是"配置不需要重新登录就生效"的机制来源。

* **用 curl 调用远端模型的完整链路**
    * 请求发给 `api.deepseek.com`，给它的是一段 JSON，收到一个 HTTP response，里面是 chat 完成的结果。
    * 环境变量里放 API key，是最常见的配置方式。
    * 很多安装方式（如 Homebrew）也是把一段脚本从服务器下载后管道给 shell 执行；`make submit` 同理，停用它既可以在后台拒绝请求，也可以直接改掉服务器上那个脚本文件。

* **strace 的作用与风险**
    * `strace` 可以把一个程序执行过的系统调用抓出来，包括网络相关的调用，因此能反推程序做了什么。
    * 抓到的序列可以和网络课的 DNS、TCP、路由知识一一对上。
    * > **易错点**：直接打开 strace 的文本输出，极有可能把环境变量里的 API key 打印出来——追踪工具本身会泄露被追踪进程的敏感数据。

* **请求路径上的系统调用**
    * DNS 解析用 53 端口；TCP 建连走 `connect`，目标是某个 IP 的 443 端口，随后是三次握手。
    * `send`、`recv`、`connect`、对文件描述符的 `read`，构成了这一整套应用的底层。
    * 应用最终在命令行里看到的仍是一段文本形式的数据。

* **DNS 与一个域名多个 IP**
    * 大型服务商使用分布式的 DNS，同一个域名会返回多个可用 IP，且在不同地理位置查询可能得到不同结果。
    * 说明该请求并非直连源站，而是走到 CDN 节点。
    * `traceroute` 靠操纵 time-to-live 的值逐跳探查链路经过的路由器：TTL 长一跳，就能往更远一个节点走一跳。

* **负载均衡器（load balancer）**
    * > **定义**：一台只做请求映射、不实际处理请求的代理机器。
    * 一秒钟收到多个请求后，按随机或某种映射方式把它转给手下的 16 个或 32 个 worker。
    * 核心原理是**转发的代价远远小于处理的代价**，一层层转发就能扛住非常大的业务量。

* **分层封装带来的"网络税"**
    * 应用数据往下走时依次被加上应用层头、传输层头、网络层头、链路层头尾，每一层包裹都要加头加尾。
    * 到达业务节点的请求里，包含 header 中的 API key 与 body 中的 JSON。
    * 拆封回来后，应用程序收到的仍是一段文本形式的信息。

## 数据中心：职责、规模与不可兼得

* **数据中心（data center）**
    * > **定义**：a network of computing and storage resources that can enable delivery of shared applications and data——一套承载共享应用与数据的算力与存储资源网络，关键词是"共享"，因为它是被全世界的人一起用的。
    * 它是一个产业链：建数据中心需要土地、水、电、人，是任何个体都无法完全掌握全部细节的复杂工程。
    * 真实的网络体验由它兜底：微信小程序对网络延时和网络故障的容忍度，明显不如原生 app。

* **业务节点要做的事**
    * authorization：判断 API key 是否合法，不合法直接返回 401 并结束。
    * 计费：一次 API call 收多少钱，缓存是否命中，应按哪一种 pricing 计算（峰或谷）。
    * 审计：对敏感或不合适的输出做处理——生成到一半的内容可能突然消失，就是后端在介入。
    * 增删改查（CRUD）：下单、发帖、查聊天记录、发弹幕（在第几分第几秒显示）都属于这一范畴。

* **半离线与离线处理**
    * 半离线指周期性、允许延时的处理：分布式数据库上的记账要汇总成日账单、月账单才算准；还有定期备份与数据大看板。
    * 离线指非常大量的处理：神经网络的训练（每一轮都要几百万美元）与内容索引——把整个互联网存下来之后，还需要跑程序把它变成搜索索引。
    * 并发数据结构想做好很难：连一个 `sum++` 想做到 scalable 都很困难。

* **数据中心的上下半场**

| 维度 | 上半场（1990s ~ 2022 前） | 下半场（2022 ~ 现在） |
| :--- | :--- | :--- |
| 核心负载 | 后端应用、数据库的增删改查 | AI 推理、per token 的参数计算 |
| 数据形态 | 消息、图片、订单、聊天记录 | 上下文、token、attention 的中间量 |
| 规模驱动力 | 用户规模与移动互联网 | 参数规模与算力成本 |
| 典型指标 | 吞吐、延时、可靠性 | 单 token 成本、推理延时、可弹性 |

* **规模数字**
    * Flash 版本是 284 billion 参数，每次 activation 是 13 billion；Pro 是 1.6T 参数，activation 是 49B。
    * 这些都只是 per token 的计算量，**不包含 attention**。
    * attention 的成本单算——上下文越长，这部分越显著。

* **C10K 问题**
    * 1999 年由 Dan Kegel 提出：concurrent 1 万个 client。
    * 当时的机器勉强能扛住这个计算量（服务器领域已经有多处理器系统），扛不住的是编程语言的机制与写得不好的软件。
    * 按最朴素的写法，每来一个连接就建连、`pthread_create` 一个线程去跑，就无法支撑这个量级。

* **select 与 epoll**
    * 两者功能基本相当：监听多个文件描述符，任何一个里有数据就继续。
    * `select` 的 API 设计并不是为 C10K 准备的，用它解决这个问题会有严重的性能问题。
    * C10K 这个动机催生了 `epoll` 这个系统调用，也催生了 Nginx、事件驱动架构、goroutine 这类并发模型。

* **C10M**
    * 服务 1 万个 client 之后自然会想服务 1 亿个，于是有了 1000 万并发的问题。
    * 摩尔定律以年、以 18 个月为单位缓慢推进，从 10K 到 10M 的跨度不是同一个问题，还叠加了高吞吐、低延时、高可靠的要求。
    * 光有协程或异步事件编程不够；对数据中心来说产品的体验就是一切的生命。

* **大锁与延时的代价**
    * 一个已经几十兆大的并发 hash table 做 resize：重新 allocate 一块几十兆的新内存，做一次几十兆的 memory copy（遍历代价还更高），再释放旧内存。
    * 这次 memory copy 的延时可能接近几十毫秒到上百毫秒，期间几万到十几万个并发 client 都要一起等，对 P99 latency 是毁灭性伤害。
    * 延时的调研结论：延时每增加 100 毫秒，用户就会有成倍的流失。
    * 海量请求突然到达时理论上没有东西扛得住——全国范围内同时唤醒的智能音箱，就是一次类似 denial-of-service attack 的效果。

* **弹性的目标**
    * 在一个很大的弹性范围内，用户突然增长时系统能接得住；峰值过去后资源又能还出来。
    * 不能说无论多少 client 都能扛住，但至少要有这样一个弹性范围。
    * 同时还要保证超高可靠性，谁都不希望聊天记录发生丢失。

* **CAP 定理（CAP theorem）**
    * > **定义**：在一个分布式系统里，consistency（一致性）、availability（可用性）、partition tolerance（分区容错性）三者不可兼得。
    * availability 指收到请求就要马上返回，不能用无限延时折磨用户。
    * partition tolerance 指必须容忍机房之间的网络被挖断或因物理、算法、延时等原因不可用——区与区之间是物理线缆连接的。
    * consistency 指一件事不管在哪个地方做，全局看起来就是按顺序完成的结果。

* **同时拉黑与发朋友圈的失败**
    * 第 1 步设置"朋友圈不可见"（一次 CRUD），接口立即返回"已拉黑"，实际上在后台悄悄同步。
    * 第 2 步从校园网切到 5G，走不同路由，朋友圈被写进另一个数据中心。
    * 若拉黑还没同步到那个数据中心，妈妈就会看到这条朋友圈——先拉黑后发帖的顺序在全局看来被破坏了。
    * > **易错点**：如果既要求 availability（刷完立即返回）又要求 partition tolerance（容忍两边暂时不一致），那网络一发生分区就永远等不到同步，consistency 必然被牺牲。
    * 同一堵墙也出现在 API key 上：key 被多台机器使用、随时可以 disable，一边要请求 inference，一边要下线 key。计费同样有延时，response 已经返回，刷新 dashboard 可能要等几秒到一分钟才看到数据。

* **三种取舍**

| 你想要的 | 你放弃的 | 结果 |
| :--- | :--- | :--- |
| consistency + availability | partition tolerance | 单机；假设它可信，一台机器既一致又可用 |
| availability + partition tolerance | consistency（某种程度上） | 可以做超大规模分布式系统，但要接受短时间不一致 |
| consistency + partition tolerance | availability 的一部分 | 请求要等到前一件事被确认之后才能完成 |

* **感受不到 CAP 的原因**
    * 实际系统的设计者从最早的分布式系统做到今天，花了大约十年时间，让使用者完全感受不到这个不可能三角。
    * 数据放在云端很安全、服务稳定、几乎感受不到卡顿，靠的是系统设计对 CAP 的隐藏，而不是 CAP 不存在。

## 分布式系统的编程抽象

* **机器会消失**
    * 一台机器从机架上断开，可能是电源断了，也可能是网络断了；机器足够多时这些都是不可避免的。
    * 每个线程不但不知道别的线程会不会访问它的共享内存，它自己还随时随地会消失——在执行到任何一个时刻都会消失，而系统依然要能正常运转。

* **从"把数据带到程序"到"把计算带到数据"**
    * Unix 的模型以 program 为中心：`cat`、`grep` 与自写业务逻辑由管道连起来，程序带着算法等数据。
    * 分布式模型让程序随时可能消失，所以反过来以数据为中心：把 program 送到存放那个 chunk 的机器上执行，结果写到新的文件里。
    * 分支点在于：单机用 `open`、`read`、`write` 已经工作得很好，但把容错交给用户不行。

* **分布式文件系统与 MapReduce**
    * 文件是 byte array；一个文件可能有 1 PB，没有单台机器存得下，于是把它分片存到不同机器上，却完全不把机器暴露给程序员，程序员只看到文件。
    * 在文件之上构建 key-value database 以解决增删改查；有了 database，C10M 问题一定程度上就被"查一个分布式的库"化解了。
    * MapReduce 为超大文件上的计算提供大数据处理系统；这几篇论文把实现细节留给分布式系统，对外暴露的接口不再是底层的 `open`、`read`、`write`。

* **Serverless（serverless computing）与 FaaS**
    * > **定义**：无服务器的计算——以数据为中心，程序员只描述计算图，图怎么执行、分发到哪台机器全交给底下的 system implementation。
    * 数据就是状态：有多少用户、哪些是 active 的、哪些 API key 是 inactive 的、每个 API 用了多少量；业务逻辑基本都是事件驱动。
    * 典型函数体：从 `event.headers` 取出 authorization 找到 API key，问数据库这个 key 是否 valid，不 valid 就返回 401 结束，通过就去做 LLM inference。
    * 好处是 write once, planet-scale：涌入大量请求时云厂商动态分配服务器，并按 function call 计费，相当于按需租用。

* **幂等（idempotent）**
    * > **定义**：一个操作做几次结果都一样。
    * 必要性来自 serverless 会重启代码、让它从头再运行一次：这段代码随时随地可能消失，运行到一半可能就不正确了。
    * 读—改—写计数（`load` → `T = T + 1` → `store`）一旦 `store` 完成机器就 crash，重跑会把账记两次。
    * 幂等写法是改用集合计数：进入系统时分配一个唯一的 idempotent key，把它加进 set，`sum` 取集合大小，重跑结果完全不变。

| 写法 | 核心操作 | 崩溃重跑一次的结果 | 是否幂等 |
| :--- | :--- | :--- | :--- |
| 读—改—写计数 | `load` → `T = T + 1` → `store` | 账被记两次 | 否 |
| 集合计数 | 生成唯一 key → 加入 set → 取集合大小 | 结果完全不变 | 是 |

* **存储与计算分离**
    * 租用的服务器上存储和计算分开计费；带 CPU 和内存的计算节点通过超高性能网络连到 SSD 集群。
    * 你在云上写一个 `a.txt`，看上去写进文件系统连续的一段，实际是写进 SSD cluster，并且自动写两份或三份副本。
    * 云厂商的独门秘笈是压缩与去重：不同虚拟机里的同名同版本 libc 内容完全一样，SSD cluster 发现后不再存一遍，只是给引用计数加一。
    * 于是在有三个副本的情况下，存储的写放大比例甚至小于一——收 1 GB 存储的钱，实际占用总存储不到 1 GB。

## 一次推理的链路

* **前向传播（forward pass）**
    * 大语言模型是从一个学到的很大数学函数上采样；推理就是一个循环，循环的每一层都是一层 Transformer。
    * 一层 Transformer 就是一大堆数字之间的长串乘加运算：输入好多数字，算出下面一堆数字，写回内存再算下一次。
    * 最耗时的两个函数是矩阵乘法与 attention，优化它们就抓住了主要矛盾。
    * 这些函数的实现都极其工整，就是巨大的多重循环（`for b`、`for t`、`for h`），与渲染 Mandelbrot set 时 `for x = 0..W`、`for y = 0..H` 的代码形状一致。

* **张量（tensor）**
    * > **定义**：维数更高的数组——一个数字是 scalar，一个数组是 vector，二维数组是 matrix，更高维的数组就是 tensor。
    * 图像本身就是二维数组；深度网络处理图像时是一堆大小相同的矩阵进出，每个矩阵有 R、G、B 三个 channel，池化之后 channel 越来越多。
    * 一个 batch 里又会有好多份数据，于是形状变成 `W × H × C × B`（宽 × 高 × channel 数 × batch 数）。
    * 需要 tensor 不是因为它神秘，而是实现这类系统时自然而然地就会用到。

* **Self-Attention（自注意力）的比喻**
    * 模型做的是 next-token prediction，要补全的东西叫 Q（Query），它是动态的，每次都不一样。
    * K 是这本书的目录，V 是书里具体的内容；把 Q 与 K 放在一起运算，以较高的权重从 V 里取出有用的部分，不重要的部分权重低相当于删掉。
    * 运算结果做一次 SoftMax 再乘以 V，形成一个很大的向量，这就是"瞬时记忆、短时记忆"。
    * 再用几层 dense 运算把它重写成新的 Q 传给下一层——每过一层，信息密度就越接近要输出的那个 next token。
    * 越往后的层，输出越不再像是你认识的那些 token；书里的每一部分也都是学出来的。

* **KV cache 与 PD 分离**
    * 每一层的 Q 如果以前用过，对应的 K 和 V 就可以保存到 KV cache 里。
    * 计费上因此有 cache hit 与 cache miss 两个价格：cache hit 意味着 KV cache 还没被挤掉，prefill 之前已经为你做过且可能还是热的；隔得太久被挤掉，就相当于 cache miss。
    * prefill 需要相当多的开销，decode 也需要另外一部分开销——它会读取完整的 KV cache，再根据当前的 Q 生成下一个 token。
    * PD 分离即 prefill 与 decode 的分离，是今天推理基础设施普遍的做法；集群里还会用到 tensor parallelism、pipeline parallelism 与 expert（MoE）策略。

* **小模型与大模型的分野**

| | GPT-2 1.5B / 1K 上下文 | 1.6T / 1M 上下文 |
| :--- | :--- | :--- |
| 显存 | 一张卡装得下 | 一张卡绝对装不下 |
| 计算 | 起一个 kernel 跑完整个推理 | 必须切到多张卡，还要对付 $n^2$ 的 full attention |
| 类比 | HTTP 请求进业务节点做一次增删改查 | 需要整套推理基础设施：PD 分离、各种并行策略 |

* **token 回来之后**
    * 拿到 next token 后仍要继续做审计、记账、更新 dashboard，最后生成 HTTP event stream 的 response。
    * 返回的数据第一个 chunk 里有推理系统的指纹与 cache 相关信息，然后才开始吐 token。
    * 这个旅程没有终点：token 回来后又在数据中心里兜了一圈。

## 从 kernel 排队到 Tensor Core

* **kernel 的排队执行**
    * 写了带尖括号的代码，这段代码就运行在 GPU 上：矩阵乘法所需的 `out`、`input`、`weight` 等参数立即被发到 GPU，GPU 立即开始执行。
    * 但 GPU 会把所有 kernel 调用排队，第一个执行完再执行第二个、第三个、第四个。
    * 这相当于 CPU 把一个计算图交给 GPU；一个 SIMT kernel 内部极度并行，但要等所有 SIMT 线程都执行完，这个 kernel 才结束，下一个 kernel 才能开始。
    * 一个 kernel 结束时都要等最慢的那几个线程，等于给 GPU 留下等待尾巴。

* **FlashAttention**
    * 动机是消除串行排队留下的等待尾巴：当可以创建 100 万个线程时，总会有几个线程因随机原因（比如调度）跑得特别慢，只剩一两个线程在跑时 GPU 利用率就低下来了。
    * 做法是把相邻 kernel 的计算图融合成一个 kernel，中间结果不出显存，让 GPU 一直被喂饱。
    * 一旦有了"把计算图拼起来"这个想法，就可能发明出真正在现实中用到的技术。

* **Tensor Core（张量核心）**
    * > **定义**：把两个矩阵的乘积累加压成一条指令的硬件单元——$A_{m \times k} \times B_{k \times n} = D_{m \times n}$。
    * 它解决的问题是：SIMT 里为了算出访问下标，还要执行像 `base + row * stride + column` 这样的计算指令，而这条指令同样需要电路、需要译码、消耗能源。
    * 既然要能效比尽可能高，就连这条地址计算指令都不想要，直接要一条矩阵乘法的 FMA；它最核心、用得最多的功能就是做这个 FMA，也可以加，也可以不加。
    * 名字虽然叫 tensor，做的其实就是矩阵乘法。

* **分块（tiling）与内存布局**
    * 矩阵乘法是一行乘以一列；无论用行优先还是列优先存储，总有一个矩阵要牺牲访问的连续性，因为内存是线性编址的，没有二维结构。
    * 解法是把大矩阵切成一个个小块，让每一块正好能装进缓存——这样访问才是高效的。
    * tile、CuTile、TileLang 这些词都来自硬件的本质限制：必须分成整块，且每块要正好待在缓存里。
    * Tensor Core 真正解决的是多维寻址、稀疏数据的搬运、压缩解压缩、跨步访问、异步同步与内存布局转换；`cp.async.bulk.tensor` 支持稀疏数据拷贝与 zero-overhead 的转置（因为取出的两个矩阵中有一个要先转置才能改写成连续的 inner product）。

* **GPU 软件栈**
    * cuBLAS，Basic Linear Algebra，基础线性代数库，主要就是矩阵乘法；它的角色相当于处理器的扩展指令集发布后，必须有人为它写汇编。
    * DeepGEMM，General Matrix Multiplication；NCCL，Communication Library，通信库。
    * 内存布局、访问模式、两个大矩阵相乘时分块分多大，都与底层硬件相关；为下一代 GPU 应当编译出不同的代码——Tensor Core 更大更多，分块大小就要变，所以这类库一直随 CUDA 更新。
    * 高层框架用更高阶的方式描述计算图，计算图最终被编译（如 FlashAttention）、调用 cuBLAS，变成 kernel 上执行的复杂程序。
    * 与 Unix 世界一一对应：用户程序 → coreutils → libc → 系统调用 → 硬件；对应到 AI 侧是应用与界面（Ollama、Open WebUI、ComfyUI）→ 高层框架（PyTorch、TensorFlow）→ 算子融合（FlashAttention）→ 基础库（cuBLAS、DeepGEMM、NCCL）→ 指令与硬件（CUDA、PTX、Tensor Core、GPU）。

* **性能压榨的教训来源**
    * 直接看手册或问 AI，会被一次性甩来海量信息而难以接受，因为需要的前置概念太多。
    * 更有效的做法是把时间倒回 1997 年，看 Intel 做 MMX 时的经验与教训，会发现历史惊人的相似。
    * 硬件体系结构更新后，上层库也会跟着更新——就像编译器会用 XMM、YMM 寄存器做很长的 load 与很长的 store 来降低多次访存的开销。

## 设备即寄存器：从一盏灯到磁盘

* **LED 灯是最标准的 I/O 设备**
    * 打开文件系统里的一个 LED 路径拿到 fd，用 `write` 往里面写值，灯就开始闪；把频率调成 1000，闪的速度明显变慢。
    * 用户态看到的是一次 `write`，落到内核里就是一块内存映射的地址——往那个地址写 0 或 1，就是给引脚一个低电平或高电平。
    * GPIO 上的电压是 0 还是 VCC（一般是 3.3 伏）；能驱动一颗 LED 就能驱动一个继电器、一个马达，也就能用电路驱动物理世界里任何一个状态变化。
    * > **提示**：这类路径不是"特殊魔法"，它背后仍然是寄存器的读写；`sysfs` 只是内核给这组寄存器套的一层外壳，内核里看到的是地址，用户态看到的是文件。

* **串口（UART，Universal Asynchronous Receiver-Transmitter）**
    * > **定义**：CPU 眼里就是 status / command / data 几个寄存器，写 data 把字节送出去，读 status 判断有没有收到。
    * 写一个字符就是往 data 寄存器里丢一个字节；读数据则不断从 `+5` 的寄存器读，有数据就从 data 里取一个出来，没有就说明此刻没有数据。
    * 配置 UART 要给不同偏移的寄存器写正确的值（如 `COM1+2`、`COM1+3`、`COM1+0`），基础端口是 `0x3f8`。
    * 有了串口，就能实现一个终端，计算机才真正可用；在数字电路与计算机系统基础课上做的那个"小东西"和真正的计算机非常接近。

* **memory-mapped I/O 与 port-based I/O**
    * > **定义**：访问设备寄存器的两条不同通路——前者把设备寄存器映射进 CPU 的内存地址空间，读写设备寄存器与读写内存没有区别；后者走一套独立的 I/O 端口空间，要用专门的 I/O 指令访问。
    * x86 有独立的 I/O 地址空间，每一个端口有编号（`0x0060` 是 PS/2、`0x01F0` 是 ATA、`0x03F8` 是 COM1），要用 `in`、`out` 指令访问。
    * ARM、RISC-V 只有一块内存地址空间，所有设备寄存器都直接映射到某个内存地址，用普通的 `mov`、`ld`、`st` 就够了。

* **键盘与 PS/2**
    * PS/2 一共 6 根线：data、clock、VCC、ground，加上两根预留、无功能、厂商可自定义的线。
    * 它映射到 I/O 地址空间上的两个端口：`0x60` 是 data，`0x64` 是 status 和 command；往 command 写特殊字节可以配置键盘鼠标，比如让 caps lock 灯亮灭、调按键重复的延迟。
    * 历史差异在于职责划分：以前"按住键要重复"由键盘控制器按写在控制器里的固定间隔自己发；现在键盘只上报按下与松开，重复节奏与延迟由操作系统软件决定。
    * 变化的原因是 CPU 变快之后，把功能放在设备端以减轻 CPU 负担的做法不再必要。

* **ATA 控制器（Advanced Technology Attachment）**
    * 连到 IDE 磁盘接口，映射到 `0x1f0`–`0x1f7` 与 `0x170`–`0x177` 两个端口区间。
    * 读数据的步骤：先从 status 寄存器等磁盘 ready，然后往正确的寄存器写上要读的 sector 数与块编号，再把读命令写到正确的寄存器。
    * 命令发出后，就可以四个字节四个字节地把数据读出来。
    * 也可以让磁盘先把数据送到自己的缓冲里，再从端口逐四字节读取。

* **经典设备的接口落点**

| 设备 | 接口形态 | 在 x86 上的落点 |
| :--- | :--- | :--- |
| LED | 内核里的一块内存映射地址，用户态是一个文件 | 由 GPIO 寄存器承载 |
| 串口 | status / command / data 一组寄存器 | COM1 基础端口 `0x3f8` |
| 键盘、鼠标 | 6 根线，data / clock / 电源 / 预留 | PS/2 端口 `0x60`、`0x64` |
| 磁盘 | 命令、块号、块数、数据一组寄存器 | ATA 端口 `0x1f0`–`0x1f7`、`0x170`–`0x177` |
| 摄像头 | 标准化的数据流协议 | UVC 标准 |

* **打印机是程序的解释器**
    * > **定义**：本质上是一台解释程序的机器——CPU 上生成一个由具体指令组成的 program，通过 data 寄存器一个字节一个字节送给打印机，打印机内部的缓冲与小计算机执行这段指令序列。
    * 最早的形态是绘图仪：一个卷纸筒提供 Y 轴自由度，一个机械臂提供 X 轴自由度，再加上抬笔与落笔；任意直线都可分解为 X 与 Y 方向的位移，所以能画线段，靠提笔落笔切换就能画出任何图形。
    * 指令可以很底层（抬起、放下、移动），也可以高级一点（`line X1, Y1, X2, Y2`、`string X, Y, ...`），于是需要更强大的语言来描述"到底要把什么打到纸上"。

* **PCL 与 PostScript**
    * PCL 5 及更早的命令形式是往 data 寄存器送一个程序，程序里先是 escape（ESC）再跟一个命令，用于设置 resolution、打印模式、打印宽度等，之后可以把 binary 图像送过去接着打印。
    * PostScript 是为了方便交换可打印文件而出现的，和今天的 SVG 很像；它本质是用图形的状态机构造路径，路径不一定是直线，可以是二次曲线，还能做填充、设置字体、打印文字。
    * PostScript 是一个图灵完备的编程语言：可以循环，有一个基于 stack 的 machine。
    * PDF 成为它的继任者：兼容性更好，而且去掉了 PostScript 里图灵完备的部分，是一个更安全的 container 格式，但留下了描述形状的那些功能。

* **PDF 的位置与打印链路**
    * LaTeX、Markdown 都可以编译成 PDF，再送到打印机；现在很多打印机也支持直接打印 PDF 文件。
    * 早期系统里就有 `lp`、`lpr` 这样的命令，直接把文件送到打印机——在没有图形界面的年代，一切都用编程语言做，一层层编译成打印机理解的语言。

* **摄像头与 UVC（USB Video Class）**
    * > **定义**：把"怎么枚举系统里的这类 USB 设备"标准化的协议，所以在 Linux 里会出现 `video0`、`video1` 这样的设备节点。
    * 摄像头会与操作系统或应用程序协商捕获图像的格式、分辨率、帧率、压缩方式等参数。
    * 协商完成后 UVC 提供逐帧读取数据的功能：可以读未压缩图像，也可以是压缩的，比如 Motion JPEG 或 H.264 的一帧。
    * 它仍然是字节流的交换；行车记录仪、显微镜、内窥镜、平板扫描仪、眼球鼠标本质上都是 UVC 设备。

* **DMA（Direct Memory Access）**
    * > **定义**：一个只会做 memcpy 的 CPU——指令集极其受限甚至可以说没有指令集，但和 CPU 共享内存（甚至共享 I/O 端口地址空间）。
    * Intel 8237 DMA 有四个通道，每次挨个通道看过去：哪个通道待拷贝的字节数还大于零，就拷贝一个字节。
    * CPU 只负责读写 DMA 的寄存器：起始地址是什么、端口是什么、要搬多少字节、什么时候开始和停止，还可以取消一个正在进行的 DMA 任务。
    * 一旦启动，搬运就是 DMA 自己的事，CPU 的算力被释放出去，从又麻烦又耗时的 I/O（比如读 1 兆数据时代价很大的循环等待）里解脱出来。

* **共享内存的加速器：GPU 与 NPU**
    * GPU 有自己的显存，认为它比 CPU 的内存更快，所以要把东西搬进显存；也可以在 host 上分配与 GPU 共享的内存，但速度会慢一些。
    * 流程是：CPU 通过 GPU 的寄存器告诉它要做什么、做什么配置，把编译好的 kernel 代码与 `cudaMemcpy` 的数据通过 DMA 送进显存，全部拷贝好之后再告诉 GPU"请你运行显存里那个地址上的程序"。
    * 这确实有点像启动一个程序：GPU 像另一台电脑，但要受 CPU 控制来启动 kernel，真正"按下启动键"的是 CPU 的寄存器写操作。
    * NPU 是共享内存的，不像 NVIDIA 的 GPU 有独立显存，只要告诉它执行什么样的程序，它就会共享着内存开始执行。
    * 协处理器未必以共享内存方式接入：早期 CPU 没有浮点指令（如 80386 没有），配一颗 80387 浮点协处理器，CPU 去访问它上面的寄存器就行。

## 总线与设备发现

* **总线的由来**
    * IBM PC 时代每个端口都写死并绑定到具体设备，因为当时要做标准化，设备也少，没人想到未来会有各式各样的设备。
    * 解决方案是做一个像虚拟地址空间一样的东西：一组寄存器可以 memory map 到系统的地址空间里，插到 `2、3、4` 就是这台设备，插到 `6、7、8` 就是另一台。
    * 总线本身也是一个特殊的 I/O 设备——它的寄存器比具体设备更多，而且可以动态分配。

* **总线的职责**
    * 枚举总线上有哪些设备，并让 CPU 询问设备信息。
    * 设备变化时通知 CPU（可以轮询总线，总线也可以给 CPU 发中断）。
    * 自带 DMA：CPU 只要跟总线上的 DMA 说好从哪一个端口开始、把哪些内存搬到内存的哪里，事情就完成了。
    * 总线还支持设备命名：扫描 PCIe 总线时能得到设备号，据设备号可知厂商，进而加载相应驱动。

* **PCIe 为什么受优待**
    * CPU 的 specification 说明它有多少条 PCIe lanes，比如 40 条，可以分配为 16 条给显卡、4 条给 NVMe，让每一类高速设备都拿到足够带宽。
    * PCIe 6.0 ×16 的带宽可以到 128 GB/s，也就是可以得到一个 800 Gbps 的网卡。
    * 总线自带 DMA，游戏加载时长主要不是 GPU 算初始场景，而是把高清贴图从硬盘读出来再通过 DMA 传送，所以高速 SSD 会明显加快加载。
    * 总线默认支持 75 瓦供电，更高功率的显卡就需要 6 pin 或 8 pin 的供电口。
    * 真正高速的设备——FPGA、显卡、网卡、NVMe——都是连在 PCIe 总线上的。

* **内存一致性（memory coherence）**
    * PCIe 总线可以和内存直连，而 CPU 有 cache hierarchy，于是产生一致性问题。
    * PC 的做法是直接把 PCIe lane 放在 CPU 里，由 CPU 负责总线与内存的连接；ARM 系统则是内存和 PCIe 都挂在一个高速总线上，由该总线完成 coherence。

* **CXL（Compute Express Link）**
    * > **定义**：基于 PCIe 物理层诞生的、面向数据中心的总线协议，有三个 protocol：IO、cache、memory。
    * 它的野心在于不再把 canonical device（靠寄存器和 host 交换数据的较慢设备）当作唯一形态，而是希望总线可以直接在远端共享内存。
    * 可以本地和一块显卡共享高带宽内存；最夸张的能力是共享另外一台计算机上的内存，两者之间通过高速网络互联传送数据。
    * 由此得到解聚的数据中心（disaggregated data center）：本地只保留够快的小内存，远端有一个 16T 的共享大内存，每个字节都可寻址；allocate 4T 就进入自己的地址空间，命中 memory hierarchy 就本地取，未命中就要付一次网络 round trip，可能有几百纳秒的延时。

* **设备接口的枚举工具**
    * `lspci` 用来列出 PCI 设备；在 x86 系统上 USB 总线是挂在 PCI 总线上的，即 PCI 总线有一部分接了一个 USB 总线控制器，USB 还可以一层层往后接。
    * `lsusb -t` 给出树状的 USB 列表；打开摄像头后能看到它落在某个 port 上，Class 等于 Video，Driver 等于 uvcvideo，还有 480 兆的传输速率。

* **驱动栈的复杂度**
    * 插入设备后应用程序不会看总线；操作系统收到中断后去轮询总线找出哪个设备是新的，然后自动加载、自动安装驱动程序。
    * 驱动里的 bug 或时序问题会在内核态代码里运行，足以让整个系统 crash；这正是 Windows 的 driver 子系统到 Windows 7 时经历大幅重构的原因。

## ioctl 与设备驱动

* **为什么应用程序不能直接碰寄存器**
    * > **定义**：设备是"懂某种语言"的，只有内核里的驱动才知道怎么和设备对话，这道门就由设备驱动把守。
    * 设备功能的绝大部分都要依赖 `ioctl` 这个系统调用来完成，它承载了访问操作系统内部对象和子系统的复杂性。
    * 例子：CUDA memory copy 会先做一个 ioctl，把当前需要拷贝的 buffer 地址送给内核，内核里的驱动再启动 DMA 把这个 buffer 拷到 GPU 上——因为只有驱动知道 GPU 应该拷到哪、该用什么样的命令、和哪些控制寄存器通信。

* **read/write 与 ioctl 的分工**

| 接口 | 主要承担的事 | 说明 |
| :--- | :--- | :--- |
| `read` / `write` | 搬运数据 | 主要是数据的接口 |
| `ioctl` | 请设备完成某一项功能、访问子系统内部对象 | 设备功能的实现基本都走它 |

* **V4L2 摄像头为什么用 ioctl**
    * 从打开设备到拿到一帧，中间所有的协商与等待都发生在 ioctl 上，真正"写数据"的动作只剩最后那一下 `write`。
    * 典型序列是：`open("/dev/video0")` → 一长串 query 与配置（`querycap`、`s_fmt` 等，由 UVC 驱动代你和设备对话，比如问它支持哪些分辨率、刷新率、视频模式）→ `mmap` 分配缓冲区（例如四块）→ ioctl 告诉驱动"缓冲区准备好了，有数据就送到这个内存地址"→ `stream on` → 等一帧就绪（也是 ioctl）→ 写文件。
    * 程序处理快慢与摄像头速度快慢之间有生产者消费者关系，由摄像头的 subsystem 处理。
    * Linux 的摄像头 subsystem V4L2 不是用 `read`、`write` 实现的，而是用 ioctl。

* **GPU 侧的分层封装**
    * 用 `mmap` 把进程的内存交给设备驱动或设备，甚至可以直接把进程里的指针送给驱动；然后通过 ioctl 提交命令，比如一个 doorbell，让 kernel 从 GPU 里面开始启动。
    * 处理器空闲时什么都不做，必须接受 CPU 的指令才会加载程序。
    * 用户态层层封装：Mesa 封装 OpenGL、Vulkan 的实现，libdrm 封装 ioctl 并提交渲染命令，内核态是 Direct Rendering Manager（DRM）。
    * 从游戏到 GPU 隔着好几层，但越往下越薄，最后落到内核 DRM 上的还是那一条 ioctl。

* **`/dev/kvm`：用 ioctl 造一台虚拟机**
    * `open("/dev/kvm")` 成功就拿到 kvm fd；失败则说明系统里没有 `/dev/kvm`。
    * 对 kvm fd 执行 `KVM_CREATE_VM`，就在操作系统内核里悄悄创建出一台虚拟机。
    * 用 `mmap` 在进程地址空间分配一块内存（例如 128M），再用 `KVM_SET_USER_MEMORY_REGION` 把这段内存交给虚拟机。
    * 用 `KVM_CREATE_VCPU` 创建 vCPU（可以创建多个）并做大量配置，把 code、data 送进这段内存，再给 vCPU 设一个初始寄存器。
    * 对 vCPU 的 fd 执行 `KVM_RUN` 后，当前进程就变成了虚拟机，一条一条指令连续地执行；里面的特权指令（比如关中断）不被干涉，就像真的关中断一样。
    * 执行到不是系统调用的特殊指令时触发 VM-exit 回到进程，可以看到 `exit_reason`；如果是 memory I/O（`KVM_EXIT_MMIO`），就可以模拟一个虚拟 I/O 设备给它送一个值；还可能因 hypercall、shutdown 等原因退出。
    * 虚拟机的创建、交内存、建 vCPU、启动、拿退出原因，全部是同一套 ioctl 接口上的不同命令，用户程序一次都没有碰到虚拟机内部。

## 磁与坑：机械存储介质

* **磁带**
    * 现代磁带不是可转动的"磁针"，而是直接结晶成完全固化的固体；写入时给它一个非常强的磁场，改变里面磁畴的自旋方向。
    * 改变的是磁化方向，晶体的物理结构不动，所以它非常硬、非常坚固，而单元却非常小，以纳米计，比如几十纳米。
    * 密度可以达到 300 GB 每平方英寸，一卷磁带做到 30 TB 是很现实的。
    * 价格低（本质上只需要结晶，比集成电路一层层做结构容易得多）、容量高、可靠性高（全是固体，放几十年几百年可能都不坏）、顺序读写性能也不错。

* **磁带的致命缺陷**
    * 它是先天一维的：bit 排成一条线，要读哪个位置都得让带子卷过去，没法跳。
    * 为了容量必须尽量长，于是盘成一大卷；读写头固定在原处，读某个位置要卷、卷、卷，若下次访问靠近带尾还得倒、倒、倒。
    * > **易错点**：能把 `/dev/sda` 直接映射进地址空间，前提是设备支持随机访问；一维、需要长距离卷带的介质一旦被这样映射，指针随手挪一下就是一次巨大的延迟。

* **磁带适合的场景**
    * 冷数据的存档与备份：大批档案要存几十年，金融交易数据要终身追责，这类冷得不能再冷的数据放在磁带上是不错的选择。
    * 音频和视频：听音乐、看电视都是顺着看的，跳着看不是常见操作；读写头读取速度与数据密度差不多匹配，可以一边慢慢转一边慢慢读。
    * 磁带分单面与双面：单面磁带要再听一遍得听完、倒带回开头再放；双面磁带听完第一面可以直接往后倒，而倒的过程里听到的是另一面的内容。

* **磁鼓**
    * 要随机访问的两条思路是避免长时间卷带、并让卷带速度尽可能快，两者都指向放弃"卷起来的带子"这种结构，也放弃那点容量优势。
    * 一维介质绕成一个圈并绕好多圈，中间放一根转轴让它旋转，同时在每个位置都配一个读写头。
    * 介质用比较硬的、做得大一些，用 16 个或 32 个读写头并行去读；这样的机械装置每分钟转上千转是现实的。
    * 定位延迟被压住：读写延迟不会超过旋转周期——最坏情况是数据刚刚错过读写头，那就再等它转整整一圈。
    * 它相当于把"一维内卷的材料"变成"1.5 维内卷的材料"：好多根"磁带"排在同一个盘上一起转。

* **磁盘**
    * 在二维平面上铺上一圈一圈的"磁带"，同心圆地铺满整个盘面，转轴还在，盘片照常旋转。
    * 读写头有两个自由度：盘片旋转把目标 bit 送到读写头下面；读写头自己可以稍微径向挪一点，切换它对着哪一圈。
    * 结构高效的原因是整个盘片是硬封装的：盘片非常硬，上下表面都配读写头，还可以好几个盘片并排叠放，装在基本密封、几乎没有灰尘的环境里，所以能转得非常快——市面上常见的是 5400 转和 7200 转。
    * 厂商一直在往一个盘片里塞下更多 bit：磁畴不是横着排而是竖着排，读写头的磁场方向也随之改过来；材料不断改进以缩小每个 bit 的尺寸；再加双面与多盘片。

* **读写头定位方式的技术线**

| 设备 | 介质排布 | 读写头怎么定位 | 随机访问的代价 |
| :--- | :--- | :--- | :--- |
| 磁带 | 一维排成一条线 | 卷带，把目标位置送到读写头下 | 可能要卷或倒很长一段带子 |
| 磁鼓 | 一维介质绕轴缠成多圈 | 轴转，多个读写头并行读 | 最多等它转一整圈 |
| 磁盘 | 同心圆铺满二维盘面 | 盘片旋转 + 读写头径向寻道 | 寻道 + 最多等它转一整圈 |
| 软盘 | 与磁盘相同，但盘片裸露 | 同上，机械结构更松散 | 同上，而且整体更慢 |

* **机械硬盘的脾气**
    * 和磁带一样便宜、密度高、容量高、可靠性也很高。
    * 唯一的缺点是对振动敏感：读写头需要给出很强的磁场，尖端又非常尖，一旦发生很大的机械振动，尖端的微小位移就可能划伤盘片，晶体结构被破坏，那部分数据就读不出来了。
    * 它并不怕"磁"：磁力很强、甚至可能伤人的磁铁直接划在磁头表面都没有任何影响，因为机械硬盘怕的是机械位移而不是磁场；这种情况一般发生在笔记本电脑跌落的时候，放在机柜里的服务器只有非常轻微的振动，就非常稳定。
    * 顺序读写没有问题；随机读写最坏情况是数据刚从读写头下面转过去，必须再等它转一圈，比如等上八毫秒。

* **可恢复性：机械硬盘与 SSD 的差别**

| | 机械硬盘 | SSD |
| :--- | :--- | :--- |
| 存储结构 | 磁介质盘片，机械读写头 | 存储颗粒，全部封装在一起 |
| 部分损坏后 | 介质稳定，可拆盘用别的方式恢复大部分数据 | 可能连带损坏，基本无法恢复 |

* **八毫秒为什么可以接受**
    * 随机读写有明显延时，但只要绝大部分读写是顺序的，这八毫秒就会相对平摊在很多次数据读写上，几乎消失。
    * 也可以通过改写程序来规避，所以机械硬盘到今天仍然是计算机系统的主力存储之一。
    * 云上数据可以始终保持三个副本，一块盘坏了再补一个副本就行，所以性能好得多的 SSD 才能用来存海量数据；消费级手机、电脑里已经越来越难看到机械硬盘，服务器上因为它便宜还在继续用。

* **寻道（seek）与电梯算法**
    * > **定义**：寻道是把读写头移动到目标磁道的那段时间；它与等待数据旋转到位的时间合在一起，构成机械硬盘随机访问的主要延时。
    * 最经典的调度类比是电梯：最里圈是第 1 层、往外是第 2 层、第 3 层，读写某个地方等于在那一层按了呼梯按钮；读写头先走到有请求的最内圈，再走到有请求的最外圈，然后回来、再过去，上下上下往返，比在盘面上随意乱窜省得多。
    * 这些算法现在已经全部集成到磁盘的控制器里：磁盘上面其实也有一台电脑，而转一圈需要多少时间、有几个读写头、读完这份数据后还来不来得及读另一个磁道上的数据，这些参数只有生产厂商掌握。
    * 从我们这一侧看过去，磁盘就是一个很大的字节序列，只要告诉它要读哪些数据，盘就负责把数据读出来。

* **软盘（floppy disk）**
    * 与硬盘原理完全相同，只是形态不同：硬盘把读写头、驱动器、控制电路全部封装在盘体里所以卖得贵；软盘的盘体只有塑料、铁片、弹簧和盘片，驱动器在机器里面，盘本身成本很低。
    * 5.25 英寸软盘能直接看到盘片，普通磁铁贴着划也不会改变里面的数据；但它同样怕划伤——盘套上开着一个小窗口，驱动器里突出的部件顶住盘片带着它旋转，读写头从窗口位置开始读写。
    * 3.5 英寸软盘有保护盖，插进驱动器后才被机械装置打开；还有一个叫写保护（Write Protect）的设计——盘角上的小孔用塑料片拨过去就通了，驱动器用灯加光电传感器判断这个孔是空的还是被挡住的；写保护的盘不能写入，防止意外覆盖。
    * > **提示**：3.5 英寸软盘其实并不软，"软盘"这个名字来自最早引入的 8 寸和 5.25 英寸盘，那两代盘片确实是软的；3.5 英寸只是继承了名字，本身是一块硬塑料。

* **软盘为什么统治了那么久**
    * 介质密度低（盘片裸露、没法放在受控环境里），但密度低也有好处——反而不那么容易损坏，可靠性还可以；读写性能不高，因为机械结构本身就不精密，盘片是松的。
    * 在不谈互联网的年代，它是整个计算机世界里传递数据最主力的介质：把文件拷进软盘，带着盘走到对方那里。
    * 一整套 DOS 操作系统就在一张 1.44 兆的软盘上；几十 KB 的 BASIC 程序就已经非常复杂，解释器能帮你执行它。
    * 需要发布 Windows 更新时会邮寄一张软盘；90 年代的游戏软件也通过软盘发行，游戏跑到某个点会说"请你插入下一张软盘"，目录里很多分块的数据文件就是为了把不同部分放在不同的盘上。
    * 它今天并没有消失——软件里那个保存按钮上的图案就是它的实物。

* **用坑存下一个 bit**
    * 罗塞塔石碑就是跨越千年的持久存储：在稳定的介质上挖一个坑就创建出一个 bit——不挖是 0，挖一个就是 1，持久性（persistence）也就实现了。
    * 挖坑容易，填坑困难；古代留下的碑文也是挖坑，而现代工业总能挖出越来越精密的坑。
    * 光盘的坑肉眼根本看不到，用显微镜也依然没有办法看清那一个个坑的结构，需要足够的分辨率；机械硬盘盘片上一个 bit 的尺寸还要更小，是纳米级的存储单元。
    * 读坑的思路和磁盘很像，只是换了一个"读"的物理量：拿激光器把一束光打到坑上，坑的深度在一定的范围内会产生干涉，光射到坑里和没射到坑里，接收器收到的信号不同，0 和 1 就被区分出来；光盘和硬盘一样要旋转，盘心有孔卡在驱动器上转起来，转动中把内容读出来。

* **光盘的容量来历与编码**
    * 最早发明光盘的是索尼和飞利浦，目的很单纯——存储数字音频、发唱片；容量被定在"正好能装下一部贝多芬第九交响曲"，74 分钟，大约 700 兆。
    * 更早的黑胶刻的是连续的凹槽：声音本质上是震动，就在一条槽里刻出声波震动的形状，读写头跟着走，后面接一个杠杆把震动放大，声音被原样还原——这是一个纯模拟的过程。
    * CD 是数字时代的东西，有坑和没坑直接对应 0 和 1；但它把 8 个 bit 的数据编码到 14 个坑位上，多出来的余量用来做纠错，为的是在坑的尺寸、间距上留出工艺余量，也为了读错时能纠回来。
    * 光盘表面漂亮的彩虹是衍射出来的效果，跟数据没关系；数据真正所在的坑在一层透明塑料片上。

* **压盘**
    * 要先做一个母盘：需要挖坑的地方留凸起，用母盘做出钢模；钢模一旦做好，每复制一份只要压一下。
    * 塑料片被母盘压一下，几秒钟之内几百兆的数据就进去了，之后在透明塑料膜上再镀一层反射膜才有成品效果。
    * 三秒钟能压出一张 100 GB 的蓝光盘，折算下来写入带宽约 33 GB/s。
    * 同一个道理也适用于跨数据中心传数据：把整个数据中心的数据并行写进磁盘，再用一辆卡车把磁盘拖过去，带宽很可能比网络更快。

* **光盘的优劣**
    * 优点是三条：价格极低（本质就是一片塑料）；容量其实不低（坑可以挖得非常细）；可靠性很高（数据刻在另一面，这一面随便划都是塑料划痕）。
    * 顺序读还可以，随机读就露出和软盘一样的毛病：它不像硬盘封在密闭空间里，它是开放的，需要驱动器带着它旋转，在空气里旋转就不可能转太快，速度上不去。
    * 写入很难：可写的 CD-RW、DVD-RW 有各种不同技术，有用相变材料（phase-transition material）做的，也有不是相变材料、只能顺序往后写的。
    * 今天它不再是一个好的数字内容分发媒介：母盘压好之后再也不能改，而现在的软件随时随地都在更新，一个不能改、还要靠快递送到手上的介质显然没有网络方便。

## 追加写与持久化数据结构

* **追加写加随机读足以实现任何数据结构**
    * > **定义**：设想介质是随机读的（可以像访问巨大数组那样直接访问任何一个 `A[i]`），但写入是 append-only 的（唯一能做的写入是往后追加，只有一个 buffer 位置不停 `position++`，不能回头改过去的 `A[i]`）。
    * 结论是只要有 random read 加 append-only write，理论上就能实现任何随机读写的数据结构——list、set 都可以，因为这个位置上是可以有指针的。

* **持久化数据结构（persistent data structure）**
    * 以二叉树为例：查找是 $O(\log n)$，从根往下走最多 $\log n$ 层就到叶子；每个节点能存更多数据则分叉更宽、深度更浅。
    * 要插入一个节点 $n$（即执行 `x.left = n`）时介质不允许改已经写下去的部分，$x$ 的 left、right 早就定死，树就长成这样，改不动。
    * 办法是把从根到 $x$ 的这一整条路径复制一份、新建节点；所有没被碰到的子树原封不动，旧树上指过来的指针照旧指过去，无论子树里有多少节点都不用动。
    * 代价是路径上每一个节点各复制一份，总共 $O(\log n)$ 个节点——花 $\log n$ 的空间插入一个节点。
    * 旧树的指针还在，历史全留着：拿到某个指针就知道那是上一次的这棵树，换一个指针就是这一次的这棵树。

* **Project Silica**
    * 一句话概括：如果要 persist data，就应该用玻璃——用激光聚焦到玻璃内部改变那里的晶体结构，这样写入一个 bit。
    * 它不是一个 bit 一个 bit 之外还先做母盘再一次性封上去，而是本质仍然挖坑：坑挖完就不能动，这就是 persist，然后继续往前挖，等价于 append-only 写。
    * 一整块玻璃写满以后必须永久地放回架子上存档；存档之后这个东西是 random read 的，它做了一套图书馆式的机器人设备来实现随机访问。
    * 因为本质上是三维结构，机器人要定位到某个架子的某一块上的某个位置，把玻璃取出来、读出 bit、再放回去，这些动作甚至可以并行。

## 闪存与设备里的计算机

* **为什么轮到电**
    * 磁盘——不管是哪种磁盘——都有一个旋转的机械部件，你要等它转一圈，这本质上带来毫秒级的延时。
    * 挖坑的效率低、填坑困难；虽然它有 random read，但随机读也要付出定位的代价。
    * 对今天的高性能电子计算机来说理想的存储系统要有电子的密度、电路的速度，才能和跑在 5 GHz 的 CPU 匹配上，能满足这一点的只有电路。

* **闪存（flash memory）与浮栅（floating gate）**
    * 想法并不惊天动地：在一个电路里挖一个坑，把电子填进去是一个状态，把电子放跑是另一个状态。
    * 器件和 MOSFET 非常像，只是在它上面多了一层 floating gate（浮栅），另外还有 control gate、隧穿氧化层、channel；往浮栅上充电、放电就是用充放电表示 0 和 1。
    * 为了压榨一个坑里能存的数据，可以精确控制放进去多少电子，让它产生一个可测量的电势差，靠测量电势差决定这个 bit 是几——于是单元里能塞进多个 bit：两个、三个（TLC）、四个（QLC）。

* **闪存的优点**
    * 便宜：本质上和制作集成电路没有区别，就是一个大规模集成电路，只要集成电路能把成本打下来，闪存也可以。
    * 容量高：因为本质上就是集成电路，可以做得非常小。
    * 可靠性非常高：集成电路的封装一层一层封下去封得非常死，不怕水、不怕摔、不怕晒，物理上灰尘进不去，水也进不去。
    * 读写性能不讲道理：整个电路的每一个逻辑门都是并行的，所以能有很好的读写性能。
    * 可扩展性也不讲道理：闪存有颗粒（die），颗粒与颗粒之间并行工作，多一份颗粒就多一倍的带宽——所以 512 G 机型比 256 G 机型的磁盘性能好接近一倍，1 T 又比 512 G 好一倍，就像往电脑里插两块盘得到两倍的读写速度。

* **Jim Gray 的预言**
    * 2006 年 SSD 还没普及时他就说：Tape is dead, disk is tape, flash is disk, ram locality is king.
    * 即磁带已死，磁盘就是新的磁带，闪存就是新的磁盘，而 RAM 的局部性才是王道。
    * 今天数据中心里的存储在成本还可以接受的前提下基本都换成了 flash。

* **擦除饱和（erase saturation）**
    * 往浮栅里充电、放电有一个致命缺点：放电放不干净，每一次放电总会有一些电子留在里面，没办法完全放掉。
    * 放电需要 20 伏左右这么高的电压，即便这么高的电压也做不到彻底放干净。
    * 放电几千次、几十万次以后，这个 cell 看起来就像一直处于充电状态，不能再用了，也就是 wear out 了；今天的 QLC flash cell 大概只有 1000 次左右的写入寿命。
    * 物理的限制不可能突破，但物理的限制有一个办法弥补，那就是用软件。

* **FTL（Flash Translation Layer，闪存翻译层）**
    * > **定义**：每块闪存里都跑着的一台完整计算机上所跑的软件——SSD 的封装上不只有闪存颗粒（NAND），还有 control（主控，是一个 CPU）和 DRAM，是一个 system-on-chip。
    * 你的 NVMe SSD、U 盘、树莓派上那张小得可怜的 TF 卡，里面都藏着一台完整的计算机系统。
    * FTL 维护一张很大的 logical to physical 映射表：在操作系统或设备驱动这一侧看，它还是一个大字节数组，被切成一块一块的，比如 16 KB 一个 page。
    * 映射关系意味着逻辑上的第一块不一定对应物理上的第一块；这次往逻辑 1 号块写 16 KB 可能写到物理 1 号，下一次再往逻辑 1 号写就不覆盖同一个物理块了，而是分配一个新块并改映射表——这有点像 MMU 里的 page table。

* **磨损均衡（wear leveling）**
    * 每个物理块都维护自己的写入次数；改完、写过之后物理块的写入次数加一。
    * 通过挑写得少的块并只改映射表，就能把所有写均匀分摊到颗粒的每一块上。
    * 漂亮的呼应在于：**FTL 这张映射表本身也必须是 persistent 的数据结构**——它也在闪存里，也要服从 append-only。
    * 如果把它当成普通 hash table，不停往某一项上写 100 万次，`hash(1)` 指向的那个表项就被写坏了，所以这张表也必须用 append-only 的持久化结构来实现。

* **U 盘让闪存普及**
    * 让 flash memory 真正普及的并不是高速 SSD，而是 U 盘，这是朗科的专利，名字很朴素："用于数据处理系统的快闪电子式外存储方法"。
    * 它算不上很技术——核心就是把 USB 接口和芯片封装在同一块电路板上，使闪存不需要一个深入计算机的接口，而是直接通过 USB 接进来。
    * 大约 2000 年前后 U 盘开始替代软盘，成为人与人之间交换数据最重要的媒介：128 兆的容量比 1.44 兆的软盘大一百倍，可以放视频、放图片。
    * USB 2.0 有 480 Mbps 的带宽，拷些图像、视频是可以接受的。

* **容量是可以伪造的**
    * U 盘、SD 卡、SSD 从特别小的到性能比较高的 NVMe SSD 存储原理完全一样，但软件、硬件的系统复杂程度完全不一样；哪怕一张 SD 卡上面也会有一台计算机系统、有一个 ARM 的 CPU，只是它的 RAM 大小、缓存大小、CPU 算力远远不如一块 SSD。
    * 颗粒本身没什么办法偷工，颗粒之外的所有东西都可以偷工减料。
    * 设备连接上计算机后，驱动会问它是什么型号、支持什么协议、容量有多少——canonical device 是一组寄存器，计算机送一个特殊的数据结构或 packet 询问容量，闪存盘回一个 packet 说容量是多少，**这一切都是可以伪造的**。
    * 很有可能买回来的是一个伪装成 1 TB SSD 的 64 GB U 盘：主控被改过，对外宣称 1 TB，实际只能存 64 GB，超过的部分直接扔掉；刚拿到手时看起来是好的，继续往后写，后面的东西就开始丢了。

## 块数组与定位的代价

* **从 byte array 到 block array**
    * 所有这些存储设备在计算机系统看起来实际上是一个 byte array，而怎么把这个 bit 找出来需要定位、寻址的操作，寻址的代价在设计硬件时就要付出。
    * 对电路来说需要额外的行选通信号、列选通信号等寻址电路；对磁盘来说需要读写头、需要转轴。

| 介质 | 定位靠什么 | 代价 |
| :--- | :--- | :--- |
| 电路（闪存） | 额外的行选通、列选通电路 | 最低 |
| 磁盘、软盘 | 读写头 + 转轴，等它转到位 | 毫秒级延时 |
| Project Silica | 机器人到架子上把玻璃取出来 | 更慢，但可并行 |

* **让一块数据共享一个定位组件**
    * 为了减少定位代价，所有这类存储设备虽然逻辑上是一个 byte array，都希望让尽可能多的 byte 共享一个定位组件。
    * 在 SSD 里它组织成 page：内部从 die 到 plane 到 block 一层层组织下去，直到一个 16 KB 的 page（不是固定尺寸，一般讲是 16 KB）。
    * 这 16 KB 要读就一起同步、并行地读出来，要写也是一次写 16 KB，要擦除甚至是更大的单位，可能 4 MB 一起擦掉。
    * 这样就减少了寻址开销——不必为里面的每一个 bit 单独做一根行选通线和列选通线。
    * 磁盘、软盘也一样，以 512 字节为单位存储：盘片上连续的一段 512 字节叫一个扇区（sector），一旦开始读就把这 512 字节连续读出来，而不是转到任意一个位置只读一个字节。

```text
  Flash 封装
    └── die
         └── plane
              └── block        ← 擦除单位，约 4 MB
                   └── page    ← 读 / 写单位，约 16 KB

  文件系统看到的：   byte array   → 映射进进程地址空间，按字节寻址
  设备层看到的：     block array  → [块1][块2][块3]… 每块 4 KB / 16 KB
  硬件层看到的：     page / sector / 坑串 —— 共享同一套定位机构
```

* **局部性与块读写的互相成就**
    * 因为在写程序时我们有办法写出具有访存局部性（memory access locality）的代码，硬件才敢以块为单位收放数据。
    * 反过来，硬件按块读写，也要求你把程序写得有局部性。
    * 所以设备层看到的是 `struct block` 的数组，计算机系统要用这个存储设备就指定一个编号："请把三号块读出来"、"请把这 16 KB 数据写到第八号块"——这就是操作系统里存储设备的抽象：读一块、写一块。

* **读放大与写放大**
    * > **定义**：读放大是你想读一个数据、实际读了更多；写放大是你想写一个数据、实际写了更多。
    * 例如把整个磁盘映射到进程地址空间后写一个字节：哪怕只写一个字节，也需要把这一整块先读出来，读出后把这个字节改掉，再把整块写回去；本来根本不想看那 16 KB，结果被拖着读了 16 KB。
    * 现在的接口也开始解决这个问题：NVMe 2.0 允许不再用 block array 的方式访问设备，而是允许直接操作闪存里面那种 append-only 的数据结构，从而避免读写放大的开销。

* **存储设备的驱动接口**
    * 因为模型就是"读一个 block、写一个 block"，非常简单，只要为存储设备实现一个 `struct block_device_operations` 就够了。
    * 它有点像 `file_operations`，但有一个关键差别：`file_operations` 是对任意 offset 读写的，可以用 `lseek` 把游标跳到文件的任意位置再读写；block device 不支持这个操作，它要么读一块，要么连续读多少块，要么连续写多少块。
    * 只要实现读写块的操作、知道怎么在设备上读块写块，剩下的像 `read`、`write`、`mmap` 这些系统调用全都是 Linux 帮你实现的。

* **用 eBPF 把块读写抓出来**
    * 系统里发生任何磁盘或存储系统的 block 读、写时把它直接打印出来，这件事靠的是 eBPF。
    * first principle 是：操作系统也是一个程序；既然是个程序，就没有任何道理不能 debug 它，也没有任何道理不能在它执行关键操作时把这个关键操作拉出来——因为"读一个 block 或者写一个 block"这件事一定是由代码实现的。
    * 拿到整个系统里所有 block read 和 write 的序列之后，就可以做一个命令行工具展示当前系统里发生的磁盘读写，还能给出各个进程 I/O 延迟的分布、哪些进程花去了最多的 I/O，以及 I/O 的类型（蓝色是读，黄色是写，橙色是同步）。
