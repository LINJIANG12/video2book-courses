## AI 时代，我们为什么还要学操作系统
> 对应块：BLK01 | 覆盖分集：P01上 | 块标题（分集名）：《Agentic AI 时代的操作系统课：绪论（上）》

欢迎大家来上操作系统。今天是新学期的第一节课，从去年到今年，我觉得计算机世界发生了很大的变化，我甚至深深地感觉到，我差不多可以退休了。所以今年我把课程又做了些修改——没更新课程主页的同学看到的还是上一版那门"还在玩 coding"的课，而现在这一版已经不太一样了。今天是第一次上课，我们先讲简介，然后按 why、what、how 三条线说清楚：学操作系统，到底要学什么，到底要怎么学。

### 第一节课，这门课已经不是原来那门课了

先自我介绍。我教操作系统，也做编程语言，算是软工院里有点跨界的人。很久以前我做过十年比赛题，所以身上大概还留着四分之一"理论"的血，也曾经是职业选手，成绩还算凑合，工资发得也挺多。但在 AI 的时代，我觉得所有这些都变成了浮云。

真正让我在意的是另一件事：从上这门课开始，我看到了一个可能的未来——人工智能会把所有老师都杀死。感谢大家投票把我选成最受喜爱的老师，而我今年操刀了新版的教学立法。从你们下一届的师弟师妹开始，必修课里几乎绝大部分必修课都被砍掉了一部分课时，包括我自己的操作系统课。所以这个学期，每个双周的四节课里，我会用三节课讲正课内容，另外一次课讲与 OS 相关的额外内容；我最想要的，是把每个双周周四那节课变成 typing day，大家可以分享自己用 coding agent 的经验，也可以让助教来给大家变一变 Unix 里有意思的东西。

为什么要这么改？因为在今天这个 AI 时代，一个老师把同样的内容讲了十年二十年，那些内容早就变成 common sense 了。所以我们先把学分和学时砍掉，砍完再看怎么办——坦白说，现在还不知道应该怎么办。

### 为什么我把内核从课里删掉了

这门课的目标，是带你真正去理解操作系统到底是什么、到底给我们带来了什么。所以除了第一节课以外，我希望每一节课都带着"实现一点什么"的目标：理解操作系统为我们提供了什么样的功能，你能用这个功能做到什么，它背后的设计理念又是什么。就像你看着一个 coding agent 的对话一轮轮往下跑时会发现，Unix philosophy 的含义还在不断增加。

另一个角度是：在 AI 时代，我们也许不需要每个同学都去写一个自己的操作系统内核。如果你有足够的软件支撑起计算机科学的体系，在 AI 之下你自己也能写一个内核——最近一年就有新闻说，有人用 Cursor 自己写了一个操作系统内核。我去看了那份代码，写得非常糟糕，非常"AI"。但我也相信终有一天这些事情是可以实现的。

所以我从去年开始做了一个违背祖宗的决定：我作为一个教操作系统的老师，把操作系统内核的所有内容都从课里抠掉了。这门课只讲操作系统和应用之间的内容，也就是操作系统的 API。当然我会讲得稍微深一点，你会知道怎么创建容器、怎么做 overlay 文件系统，这些东西你之前大概没做过，而它们恰恰是操作系统给你提供的底层功能，也是实现像 coding agent 这样的东西非常重要的组成部分。说到底，也是因为我相信 99.9% 的人不需要知道写操作系统内核的细节。

> **易错点**：不要把"操作系统"和"内核"划等号。这门课里我把内核内容全删了，讲的是操作系统与应用程序之间的那层接口；接口设计得怎么样，才是我们要反复琢磨的问题。

### 现在是 ChatGPT 诞生之后的第五年

在讲技术内容之前，也就是在我讲操作系统发展历史之前，我想先跟大家回顾一下我们所处的这个时代。我把它叫作「AC 05」——从 ChatGPT 出来之后，我就私自把计算年代的算法改了，现在是 2025 年，这是 ChatGPT 诞生以后的第五年。

五年时间好像并不漫长，你们五年之前应该还在上初中或者刚上高中。但这五年里，逻辑上发生了巨大的变化。我记得 ChatGPT 3.5 刚出来的那一天晚上，我在外面，想办法搞到了号，然后开始跟它聊天——我发现你让它从 50 数到 100，它会 50、51、52、52、52、52、52……你得给一个好的 prompt，它才能从 50 数到 100。你很难想象 GPT 3.5 五年前是这个样子。然后专家们都在说：不要恐慌，AI 的逻辑推理能力不行，大语言模型本质上做不了推理。然后有了 o1，有了强化学习，大家可以看到强化学习有多要命，把它的能力给提上来了。

到了 2025 年，AI 已经完全不同了：它拿到了 IMO 和 IOI 的金牌，而且在 ICPC World Finals 里用很短的时间击败了最强的人类选手。这是一件非常离谱的事——如果你参加过竞赛、了解一点这些事情的难度，你就知道这有多离谱。让你去拿一块 IMO 金牌，你肯定做不到；如果你做得到，你现在不会坐在这儿，你应该在清华或者北大，或者在 MIT。

也是大概一年以前，我自己实现了一个 agent，在 agent 背后接了一些模型。那时候的模型还是 GPT-4o、DeepSeek、DeepSeek-R1，能力都非常弱：经常做着做着就不听指令，开始乱做；哪怕你开一个 agent，基本上没有一个能用的。从那个时候完全没有 coding agent，到现在非常成功、能把一件事做到极致。今天我毫不客气地说，它的逻辑比我的博士生好用——除了那些需要领域知识、我必须用 prompt 把领域知识告诉模型的问题以外，其他事情它可能比我的博士生还好用。这是一件很糟糕的事情：那我们还要博士生干什么？

更可怕的是，不仅能力大了，速度也大了。前几天有一个新闻，三大顶会的推特——那三个不是正式的顶会，就是智东西、新智元、量子位这几个公众号——说有一家公司做了一款芯片叫 Cerebras，创造出了 15,000 tokens/s 的生成速度。虽然它是以 Llama 为底座、已经经过比较严重的量化的模型。你们有没有试过 chat.cerebras.ai？15,000 tokens/s 是什么感觉？你让它帮你写一段什么代码，或者丢给它一篇两三页纸的论文说"请帮我翻译成中文"，你按下回车以后，它可能卡一下，然后瞬间就把所有东西给你贴出来了。也就是说，仅仅一秒钟的时间，它可以写两三屏的代码。这是非常可怕的事情。

当 AI 做得这么好、这么快的时候，实时交互就变得极其重要。比如做数学题、做逻辑推理，逻辑是要尝试的——你试得越快，做出来的概率就越大。这非常像下围棋，你思考得越快、推理得越快，效果就越好。如果他们把稍微再大一点的模型，像最近发布的 o3、DeepSeek-R1 也做到这个速度，那我觉得人类就真的没有什么希望了。

### 聊天窗口里的 AI，和能动手的 coding agent

在能力和速度齐头并进的时候，我们就看到了现象级的应用。你们平时日常用 coding agent 吗？看起来还挺多的。你们常用哪一个——Cursor？挺好用的，不过 Cursor 容易封号。用 Claude 也可以。

用了 coding agent 之后你会发现，它和一两年以前在聊天窗口里跟 AI 对话的模式完全不一样：

| | 聊天窗口里的 AI | coding agent |
| :--- | :--- | :--- |
| 能接触什么 | 只有对话文本 | 它所在的环境：文件、命令、网络 |
| 能做什么 | 给你一段答案 | 改你的文件、跑脚本、去网上拉数据 |
| 风险 | 说错话 | 能把你的所有文件都删掉跑路 |

它能干危险的事情，反过来说，意味着它能干更多的事情，理论上它能干很多很多离谱的事情。

在 Claude Code 出现之前、甚至在那之前很久，我就一直在用 Claude 管理我个人的数据库。我的做法是：把所有个人信息以 Markdown 的方式、以目录的方式放在一个超级大的数据库里。你们上学的时候填表是不是很烦？辅导员让你填一个表，姓名、民族、身份证号码、个人简历，每填一次就想：这些事情我前天刚填过，能不能不要再填一遍？有了 agent 之后，你就可以直接把表格往里面一丢，agent 会去读你的数据库，然后把所有需要填的东西给你列出来，我只要 Ctrl+C、Ctrl+V 就行——虽然我还没调好让它直接把表格填进去。这样我就把一个本来要花几十分钟的事情，变成了十几秒钟就能完成的事情。

我也试过把这个小 agent（有点像 Claude Code）接入微信。去年有一件很有趣的事：我调好之后就人就不在了，然后微信的客服系统——因为我注册的是小号，怕封号——发了一条消息，我的 agent 回一条，它再发一条，agent 再回一条。等我看到的时候已经过了几千条，然后号就被封了。

这些现象级的应用正在改变我们的生活，改变我们每一个人做的每一件事。所以我们不知道未来应该怎么应对，因为现在也没有想好大模型最后会变成什么。你可以看到很多工业界已经聊不下去了，尤其是硅谷。在国内，我们 Computer Science 的学生还能第一时间接触到这些事情，但如果你身边是一个普通人，他完全没有意识到这次 AI 革命会带来什么。所以我们要谈一谈：从过去到现在到底发生了什么变化，我们应该怎么应对。

### 计算机过去只会解「良构」的问题

我们现在处在飞速变化的时代，这对我们意味着什么？先回想一下，你们在小学、初中阶段，计算机科学的老师一定会讲什么是计算机科学——你们会说：我们要编程，用算法去解决问题。而在 AI 时代以前，我们作为 Computer Science 的学生和老师，是怎么解决问题的？我们只能解决数学上良构的问题。

最短路径就是最好的例子。什么是最短路径？最短路径是：我定义一个集合，这个集合就是图。图是什么？离散数学学过——用一个集合表示顶点，再用另一个集合表示边，边是顶点集合上的一个子集，也就是 $V$ 是一个集合，$E \subseteq V \times V$，这是一个纯数学的定义。基于图，你才能定义出最短路径。

> **定义**：良构的问题（well-formed），是指能被数学语言严格定义出来的问题。只有这类问题，计算机才有办法求解。

坦白说，我们的同学对数学的敬畏并不是很多。保研面试、期末面试的时候经常问一个问题："什么是图的最短路径？"基本上还算凑合。但如果你真要用数学语言把它表达出来，你马上会发现：好像忘了，或者得想一下——用集合论的语言严谨地说出"什么叫图的最短路径"，并不那么容易。而计算机就只能解决用这种数学语言定义出来的问题，其他问题它没有办法解决。

可是我们真实世界里的问题呢？做一个室内导航软件，实现一个信息系统，写一个手机 App，点个外卖——所有真实物理世界的东西都是非常不规则的。怎么把不规则的东西变成良构的数学问题？这就需要程序员。所以我们软件工程、计算机科学这个专业，一直都在培养这样一种能力：把现实世界中各种各样杂七杂八的问题，翻译成计算机可以理解、可以求解的数学问题。

我们老先生还在的时候，老师曾经问过一个问题：什么叫软件？这个问题到现在还是要问，因为它的答案深不可测，和我刚才说的"计算机科学与软件工程的学生这些年都在做什么"有很大关系。

> **定义**：软件，是物理世界的过程在信息世界里的投影。而这个投影，基本上只有受过专门训练的软件工程师会做，地球上没有经过这种训练的人都没有办法做。

### 现在，AI 也会做这件事了

到了今天，AI 可以做这件事了。AI 非常擅长把自然语言这种不规则的东西——哪怕你给的是 ill-formed 的问题、连需求都说不清楚——拿来给你猜一个。甚至，AI 还能从这个 ill-formed 的问题里面把 well-formed 的部分提取出来：它能写代码，也能把它变成一个数学化的表达，去真正解决这个问题，再调用另外一个数学工具来做一做。

它甚至具备动态生成一切内容的能力。你想想，跟 AI 聊天的时候，有时候你并不是很喜欢它的文本输出：用字符给你输出 Markdown，列个表格，或者用字符拼成图形。但如果 AI 每次输出都是一张 HTML 卡片，甚至是可以交互的卡片，你的体验就会大幅提升。

顺着这个想下去：在 AI 的时代，也许我们所有的手机应用都不存在了。打个比方，如果我是一家手机厂商，我就扶持一群专门提供打车、地图、位置这些服务的后台公司，它们给我一个 API；而我所有的东西都以手机作为跟 AI 聊天的界面。比如你要点杯奶茶，你直接跟 AI 说"能不能给我点杯奶茶"，点完以后，手机操作系统直接把这个请求转发给数据提供商，数据提供商把哪家店能给你什么样的奶茶、有什么优惠券发给我，然后再让前端帮我动态生成一张 HTML 卡片——完全为你个人定制。

```text
   我：「给我点杯奶茶」
        │
        ▼
   手机上的 AI（唯一的聊天界面）
        │  转发请求
        ▼
   数据提供商（哪家店 / 有什么奶茶 / 优惠券）
        │
        ▼
   前端动态生成 HTML 卡片（为你定制）
```

再也不需要"老人机"了。你们家里如果有老人，尤其是爷爷奶奶或者更年长的长辈，会发现他们用智能手机遇到巨大的困难：打开一个 App，字又小、功能又多，根本搞不清哪儿是哪儿。而在 AI 时代，所有内容都是个性化定制的：如果我知道你是一位老人，我就把字给你大一点；如果我知道你是红绿色盲，我就给你生成一个蓝绿底的界面。完全不需要像现在这样，让每一个软件工程师把物理世界的每一个过程以及自己的想法通通变成某个应用——所有东西都 personalized。所以这是非常可怕的一件事情：除了 AI，很多很多行业最后都要被消灭。

### 那我们怀疑自己，还剩下什么

在这个时刻，学 Computer Science 还有意义吗？我们还花那么长的时间学编程——从大一开始学，学得嗷嗷痛苦。一旦轮到你写，你极其痛苦；一旦让你把问题抛给 AI，头皮发麻，直接一下就过去了。你们肯定会怀疑：学这个东西还有意义吗？

这种怀疑我们每个人都有。AI 已经使顶级廉价劳动力在市场上的价格降低了。什么是顶级廉价劳动力？比如 PhD student。我作为老师一直有这种感觉：我一直带着同学发 paper，你们最后可能也想读研，也想发很牛的论文，走向人生巅峰。但我跟博士生讨论的时候，我也感觉我和 ChatGPT 没有什么区别——我说的每一句话，都是根据我过去对这个博士的了解，从听到他说的话里，一个很自然地能够从逻辑上推导出来的下一句话。我能做，ChatGPT 也能做。那还要我干嘛？我在这儿干什么？每一个在 AI 身边待得很久的人，都会怀疑自己的价值。

但到今天为止，AI 还是有局限性的。可能因为现在数据不够，它在做复杂任务的时候、做一件真正复杂的事情的时候，还是做得不够好，可能不如我们的博士生。我不知道哪一天这个问题能不能被攻克，我相信 AI 能攻克它。但至少在今天，AI 还没有学会一件事——可能是因为 Transformer 的原因，可能是因为数据不够，可能是还没有找到好的形式化解决方法——AI 没有办法做复杂系统的抽象和理解。

> **结论**：AI 到今天还做不到的，是复杂系统的抽象与理解，也就是真正好的顶层设计。想要超过 AI，你唯一能学的，就是怎么样做顶级的顶层抽象。

### 操作系统：支撑百万应用的那个接口

我们人类想要解决一个真实世界里非常非常复杂的问题，就叫操作系统。做操作系统不是让你去写一个内核，而是要成功地支撑一整个你看到的应用生态。谈到操作系统，你们会想到很多：手机上的 iOS、Android，平时交互的 Mac OS、Windows。这样复杂的系统，要做的是支撑上面一整个百万级、千万级的应用。

那么下一个问题就是：如果你要支撑百万千万级的应用，你应该给这个应用提供一个什么样的接口？

比如说，我觉得大家读 Computer Science，最想做的就是游戏。可是你刚开始写 C++、做第一个习题的时候，你根本不知道怎么做一个游戏，因为你只会用 cout 打字符。要做一个游戏，你需要有一个抽象层——有点像操作系统，但大家通常把它叫作游戏引擎。你需要游戏引擎给你提供一些抽象的接口、一些 API，然后你用这些 API 就可以写游戏。那么下一个问题就是：你应该设计一个怎么样的 API，才是对广大开发者友好的？从简单的 Pygame，到更简单的、我自己在另外一门课里做的一个小游戏引擎，再到更复杂的工业级游戏引擎，它们都是怎么设计的？AI 现在很不擅长做这件事。

这可能是人类的智慧，或者说是 Computer Science 里你们作为学生、人类智慧的最后一幅画卷：AI 还做不了这种真正好的顶层设计。我们在做研究的时候也一样，如果顶层设计想不出来，基本上只能刻苦想想办法，才能做出顶级的顶层设计创新。所以在今天，你想要超越 AI，唯一能学的就是怎么样做这种顶级的顶层抽象——而操作系统就是这样的一个范本。操作系统非常核心的一点就是：你怎么样设计一个好的抽象层，让上面也能跑，让下面也能跑。

```text
   应用：百万、千万级的 App
        │  只依赖这一层接口
        ▼
   操作系统提供的抽象接口（API）
        │
        ▼
   操作系统 + 硬件资源（CPU、内存、磁盘、网卡）
```

操作系统就是一个接口：它最上面是什么，最下面是什么，这个接口要设计得恰到好处——既好实现，对上又非常友好，还能一层层再搭建出一个完整的生态世界。人类其实走了很多弯路，最后才走到今天这样的一个接口。

### 操作系统是 AI 的手和脚，也是我的最后一门编程课

操作系统作为一层抽象，它其实是 AI 的手和脚。AI 为了能做各种各样的事情，就必须能够显示界面、能够在网络上通信、能够创建虚拟隔离的环境，而这些底层接口都由操作系统提供。如果没有操作系统一层层叠加出来的抽象工具，那 AI 就相当于手和脚被砍断了，做不了这些复杂的事情。你们如果去看 coding agent 的日志，经常会看到它写一段脚本，脚本还可能去网络上拉一些数据，或者对你本地做一些修改——它之所以能这么做，靠的就是操作系统提供的这些能力。

同时，操作系统还为我们提供安全、可靠、高效方面的保障，支撑了我们整个现代的应用生态。你手机上的每一个应用，应用身后就是你手机本身，它就是一个操作系统，支撑你手机的运行；在你应用的背后、在互联网上还有云端的服务器，那上面也有操作系统，它们一起支撑了整个应用生态。

而对我们每个人来说，学操作系统的意义在于：它是你的最后一门编程课。你已经走了很长一段路，你学过数据结构、学过算法，它们在某种程度上也是一种编程课，但操作系统是真正意义上的最后一门。你会知道一个计算机程序、一个软件到底能做什么、什么样的软件能做、到底为什么能做。为什么能有一个窗口？为什么我能在网页上看到内容显示出来？为什么我能创建一个窗口？还有——为什么有的时候 Ctrl+C 退出不了程序？

比如我打开一个终端，按下 Ctrl+C，它只回我一句"Press Ctrl+C again"。这门课要讲清楚的，正是这类问题的来龙去脉。

今天我做了一个有趣的改动——我所有的内容都在一份代码里。这一页幻灯片就是一个 Python 函数，写完之后输出到某个目录下，我就能把它变成命令行前端，也能把它变成网页。我现在甚至在用一台树莓派来跑它。做到这一页之后，我就做到了真正的前后端分离：我只要用写代码的方式，就能描述我今天上的一节课，然后把它任意地渲染成前端——你们要是对命令行这种上课方式不满意，我下次可以改成网页，用 CSS 渲染成一个还不错的样式。

我终极的目标是要退休。为了退休，我就要把上课的东西以一种可以传承的方式放到公开领域，顺水推舟。现在还没有完全开源，因为我的代码比较乱。有了这样一份上课的日志和记录，我就可以变成一个数字人，我就可以退休了。

### 把一节课写成代码

今天我在做一个尝试，我叫它 content as code——这应该是现在最时髦的概念：你可以用代码表达任何东西。图形不够画可以用 SVG，可以用 Python 写一个 matplotlib；甚至可以用它做视频，Remotion 最近很火，有兴趣的同学可以去看一下；幻灯片当然也完全可以用 HTML、CSS 这样用代码的方式表达出来。

content as code 最大的好处是：**当我写成代码以后，人类、AI 和机器都能读懂**。对人类友好，因为我是程序员，我能写代码也能读代码；AI 也能写能读；机器可以执行。而机器执行代码只需要花一个很低的代价——不需要叫一个大模型，也不需要叫一个程序员，代码自己就可以把 Markdown 变成 HTML、套上一个 CSS。

于是在现在的操作系统上，我就可以根据日志自动给上课的记录生成一份讲义。等到我的模板都做好、什么时候讲什么都放到日志里之后，还可以做更激进的事：

- 这门课不适合某位听众，比如他缺了某一部分背景，我可以让 AI 帮我裁剪、帮我补充；

所以我觉得大学教师这条路线已经非常清楚了：作为一个教书匠，其实是没有什么生存空间的，在 AI 时代尤其如此。只要少数专家写出顶层设计，表达交给 AI 就够了。注意顺序——**如果你直接让 AI 给你搞一套操作系统课，它肯定会搞出一个比较平庸的操作系统课；但你一旦有了一个好的顶层设计，所有的执行 AI 都可以做得非常非常好**。

### 命令行与管道：Unix philosophy 的威力

这门课真正想要表达的 take-home message，其实是**会编程你就拥有全世界**。

操作系统教给你们的，不只是“我们可以在操作系统上实现一个 Logisim”，也不只是 `printf`、`write`、`read` 这些系统调用。我在操作系统课上的第一讲就讲 Unix philosophy，你们可能也听我说过我很喜欢回到命令行——那是对程序员非常友好的一个接口。

你们第一次见识 Unix philosophy 的威力，是我给你们看的一个数字逻辑电路的模拟器。它很简陋，看起来挺蠢的：它唯一能做的就是把 `a b c d e f g` 输出出来，也就是数码管每一段的亮和暗，对应 1248 的七段译码器。但如果我把这个输出传递给另外一个程序做输入，再加上一个几行的 Python 程序，我就得到了一个真的点亮的数码管。

那个 Python 程序做了什么？它从标准输入里一行一行地读，读到 `a b c d e f g` 的值，再把值填进一个模板：是白格就填虚的，是红格就填实的。于是数字逻辑电路的模拟器和这个小小的 Python 程序一对接，屏幕上就真的出现了一个数码管。我今天是让 AI 帮我把那段逻辑改掉的，它一次就写对了——虽然做得比较丑。

```text
  +----------------------+        +--------------------------+
  | 数字逻辑电路模拟器    |  pipe  | 几行 Python：读 a..g     |
  | 输出 a b c d e f g   | ---->  | 填进模板，画出一个数码管  |
  +----------------------+        +--------------------------+
```

一个程序的输出就是下一个程序的输入，两个本来毫不相干的程序被拼成了一个新东西。这就是管道。

管道讲起来非常直白，但它可以不断地跨、跨、跨，搭出各种各样的东西来。Unix 特别经典的地方在于，**它设计了一组可以复用的工具，然后每个工具可以任意地组合和复用**。

> **易错点**：AI 时代有各种 skills，有 MCP，但它们恰恰缺少编程语言里最重要的那个特性——任意组合、无限复用，而且复用的代价极低。大语言模型必须把所有东西都丢进上下文里，然后再实现一遍。这是编程语言相对于“把一切塞给模型”的结构性优势。

所以命令行是一个非常有趣的设计，这门课里我们会反复地说它。

### 硬件是状态机，软件也是状态机

回到正题。刚才我们说硬件就是一个状态机：它每次取一条指令出来，然后执行它。那什么是软件呢？回顾一下计算机系统基础到底学了什么——你们花了那么大的力气把那么大的一个东西跑起来，究竟是为了什么？它要告诉你的是**软件是什么**。

一个 `a.c`，就像刚才说的那种老式设备一样，实际上是往里面塞进去一个 `a.c`，然后它会经历一个漫长的过程变成一个 `a.out`，变成一个 binary，这个 binary 就可以直接在 CPU 上运行。

而这个 binary，这个程序，**也是一个状态机**。换句话说它也是一个 memory，跟硬件长得一模一样：memory、register，再加一个 CPU。你们都在 gdb 里调过程序，所以应该能接受这一点。

> **结论**：程序的模型和硬件的模型完全一样，也必须完全一样——不然程序怎么可能运行在硬件上面？

我很喜欢的一个例子是汉诺塔。这是大家都很熟悉的例子，你们学 C 语言递归时都写过，但我觉得应该有不少同学至今没有完全理解它。你们有多少人能写一个非递归的汉诺塔，而且不借助它的数学？下节课我会讲，这节课我先讲基础版的汉诺塔。

当我在 gdb 里调试汉诺塔的时候，你会有一种“软件也是一个状态机”的感觉。打印 `backtrace`，这里显示的就是当前程序的状态。而当前程序状态里还有一个很重要的部分，就是你们学计算机系统基础时见过的特殊寄存器——PC，program counter，它代表当前执行到哪儿。在 gdb 的窗口里，我们的 program counter 就在那黑色高亮的一行上。所以程序总是从 PC 所在的地方取出一条语句来，把这条语句执行掉，然后我用 single-step 推进到下一条，继续执行。

接下来是见证奇迹的部分。我用 gdb 一步一步调试这个汉诺塔：我递归了好多次，终于可以让木偶的调试台去移动它，我要把柱子从 A 移到 B，然后我 step 进入——你看到这个柱子真的从 A 移到 B 了。因为 everything is a state machine：硬件、软件都是状态机，所以在任何时候，我都可以把软件的状态通过一个函数转换成任何一个其他状态，比如一个真正的汉诺塔的状态。

> **定义**：**状态转换器（state visualizer）**——写一个函数，把程序内部那一堆内存和寄存器的取值，翻译成人类更能够接受、更直观的形式展示出来。

今天 code is cheap, show me the talk，我只需要把我想干什么表达出来。这个技术在接下来的课程里我们会反复用到：当我们遇到特别难以理解的代码时，我可以用这样一个转换器把状态以人类更适合接受的方式表达出来。这件事是完全可以做得到的。我们去年发过一篇 paper，题目叫 **Understanding the Linux Kernel with Visions**，拿了去年 USENIX ATC 的 Student Paper。这篇论文说的就是：Linux kernel 的状态非常复杂，但如果你只关注其中一小部分，也可以在一个屏幕上面把它显示出来。

所以你们可以看到，在 AI 时代，教大家的方法、学东西的方法都发生了根本性的变化。你们需要的是了解几个重要的 first principles：硬件是什么？软件是什么？它们是状态机；而操作系统，就是夹在硬件和软件中间的那个中间件。

### 操作系统是夹在中间的中间件

因为软件是状态机，所以整个学期我都会反复讲：操作系统是好多程序的管理者，它管理着一个一个正在运行的软件的当前状态，此外它还有一大堆操作系统对象，并且把这些对象交给软件去访问。

从软件这一侧看，操作系统就是**一组 API**。应用程序通过调用这些 API 来访问操作系统里面的各种各样的对象：我们打开的文件、磁盘、显卡、显示器等等。也包括里面的其他软件——我们可以通过操作系统把另外一个软件杀掉，比如刚才就试图把那台 web 服务器杀掉。

```text
  +----------------------------------------------------------+
  |  software : also a state machine                         |
  |  memory + registers + program counter                    |
  +----------------------------+-----------------------------+
                               |  call APIs
  +----------------------------v-----------------------------+
  |  operating system (= middleware)                         |
  |   - manages the state of every running software          |
  |   - exposes one set of APIs                              |
  |   - objects: files, disks, GPU, display, other software  |
  +----------------------------+-----------------------------+
                               |  instructions drive state
  +----------------------------v-----------------------------+
  |  hardware : a state machine with its own PC              |
  +----------------------------------------------------------+
```

操作系统把硬件做一层抽象，为上层的软件提供服务；软件通过 API 访问操作系统里的对象，因为软件自己也是状态机，所以这一层抽象才成立。

这个“抽象出一组 API”的概念可以被推广到各种各样的系统上去：如果我们把很多台机器抽象出来、做一组 API 去访问一个机器集群，那就是分布式系统；我们可以把 GPU 也做一层抽象，GPU 有好多好多核心，我不用手工去写，我只要说我要算什么，它的编译器就帮我编译成 GPU 上能高效执行的代码；再比如把存储设备抽象成存储系统，等等。

而如果我们想要真正理解操作系统是什么，一个很有效的办法是**把操作系统底下和上面发展的历史重新倒一遍**——你就能很清楚地看到操作系统到底是什么。

### 从 1946 年 2 月 14 日开始

1946 年 2 月 14 日，一个新的时代诞生了，世界上第一台计算机。它其实和今天我们平时用的计算机还不太一样，我们今天叫它冯·诺依曼机（von Neumann machine）。它是图灵机在物理上的一次尝试实现，也是一个状态机的模型，它也有 PC 的概念。

它真正做的事情，非常像你们在数字电路课上画的那种状态图：如果你让你们设计一个计数器或者时序电路，你会画一个状态图——这里有若干个状态，当 x=1 的时候跳到这个状态，x=2 的时候跳到另一个状态，就是这样的状态转移图。ENIAC 基本上就是实现了这样一个东西，只不过它真的用导线接了线：它当前处于某个状态，这个状态上的操作执行完以后，它会根据接线的接法来确定下一个状态是什么。有趣的是，也有人把整台 ENIAC 完整地画了出来，包括模拟器；如果你感兴趣，完全可以在 AI 的帮助下了解一下。

我觉得 1940 年代是非常非常天才的设计。首先，逻辑门这个东西那个时候已经有了；冯·诺依曼机提出了二进制，而二进制跟我们今天的与或非门没有本质区别。只是今天我们不管用 FPGA、还是用集成电路、芯片上的电路，都比 1940 年代那种真空电子管要小得多——那时候一个真空管、一个三极管就有一个椅子那么大，为了把它们接起来还用很粗的导线。

```text
        1940s 硬件的一个横切面

   真空管 / 三极管                          导线
    [ 一个就有椅子那么大 ]  ----粗导线----  [ 用来决定下一个状态 ]
```

你们明天要想实现内存，最常用的电路是晶体管，比如你们在 CS152 里搭的是 SRAM，用一大堆晶体管。但在那个年代，用这种方式来构建电路实在太贵了，工程上也太困难。那时候有一个非常天才的发明，叫**延迟线内存**。

延迟线内存是什么呢？你想存很多个 bit，就想像这里有一根线，你可以在这根线上调出一个波：调得密一点是 0，调得疏一点就是 1，然后再密是 0、再疏是 1。这完全可以——就像两个人甩一根绳子，你甩得快是 0，甩得慢是 1，波慢慢往前推进。然后你只要在末端接一个放大器把信号反馈回来，数据就一直保存在里面了：进来的数据反馈回去，再回到起点，数据就不停地在里面流动，我们就把数据暂时保存下来了。然后你在这里加上一个读写的门控电路——想要写入的时候就不要再把反馈的结果送回去，而是把外部接口的数据放进去，你就可以写入了。

```text
      write gate                            read gate
          |                                     |
          v                                     v
  ------->  oo.o.oo.o.o.oo.o.o.o  ---------->  [amp] --+
                       wave travels ->                 |
          ^                                            |
          +---------------- feedback ------------------+
               data keeps circulating inside the line
```

那时候的输入输出就是打孔的纸带。打孔是机械结构，它可以读纸带上的孔，也可以往纸带上打孔。这一切都非常天才——但是你不会想用那样的方式去运行操作系统吧？

那时候的硬件，刚刚把计算机的模型实现出来：一个状态机，指令驱动它到下一个状态，冯·诺依曼计算机，硬件的模型已经有了。那上面能跑什么样的软件呢？最早的一批软件包括打印对数表、打印射击表、计算弹道轨迹这类很小的、有实际需求的问题。

> **提示**：这其实解释了我们程序设计课上一些经典习题的来源。你们应该都有过疑问：为什么循环的第一个例子永远是打印对数表？这是历史原因——最早的一批计算机就是用来算这个东西的，它展示了计算机可以做循环这一类事情。

在 1940 年代，大家还在为真正的 bug 犯愁。世界上第一个 bug 真的就是一个蛾子，卡在继电器里；继电器不工作了，程序就不能正常运行，`bug` 这个词从那时开始。

那 1940 年代有操作系统吗？**没有操作系统。**那时候的软件，就是我们直接在打孔纸带上打出来的二进制代码：人先在纸上把这些东西想好、算好，然后打成孔、戳到打孔纸带上，再把纸带送到计算机里去。为什么不需要操作系统？因为你是机器的主人，程序能力也很小，所有程序直接用指令操作硬件就行——只要有一条给打孔机的指令。比如计算机系统里常见的 out 指令，io out 是写 8 个 bit 的数据到一个端口，它把对应一个字节的电平送到打孔机上，打孔机根据那个电平驱动排针，继电器咔哒一下打一个孔，打完纸带往前挪一格，这台计算机不就搞定了嘛。

> **提示**：今天你们身处 agents、CLI、skills 的时代，读一读每个行业的历史都会很有趣。太阳底下没有新鲜事，我们不过是在重复 1940 年代的场景。

### 从算对数表到能读懂字符

人们很快就意识到，这样的结构、这样的软件，一开始可能很简单，但它可以用来做各种各样的事情。

如果我能算对数表，那么我只需要给每一个字符一个数字的对应：比如说 A 就是 0，B 就是 1，C 就是 2。我在内存里放一个数组，这个数组里存放的不再是速度这样的整数，而是 A、B、C 这样的字母——我是不是就可以处理字符串了？我能处理字符串，是不是就意味着我可以开始处理现实世界中的真实需求了？

再看打孔纸带：它就是一个一个的孔，对人类不好读。但如果我不是一个字节一个字节地打孔，而是打成 8×8 或者 16×16 的阵列，那我打出来的就能是字符，人类可以看得懂了。

于是只要我的内存变得更大，只要我的 CPU 变得更快，IO 设备——磁带、打孔机、打印机、键盘，很多都是机械的——计算机就真的可以搞定它们。只要我能编程序，计算机就可以变得非常非常通用，可以做表格。凡是人类社会人能想到的事情，理论上都可以用编程来做。

1950 到 60 年代，我们的 CPU 和内存发生了非常大的变化。比如那个时候开始有了 **core memory，磁芯内存**，不再是那种延迟线内存。磁芯内存跟我们现在的 DRAM 很像：DRAM 有行电容和列电容的行列信号，行、列信号的每一个交叉点上都有一个电容，你读的时候就可以把它读走。那时候还没有那么先进，还没有集成电路，它不是电容，而是一小块磁铁——极小的一块磁铁，这块磁铁可以在电磁感应下改变方向，而这个方向就是 0 和 1。

> **提示**：不要忘了今天电容的充电和放电状态也是一样的道理。一个 bit 只需要一个可以表示 0 和 1 的状态就够了；磁芯内存同样可以在二维平面上把这个 bit 铺开。

同时 CPU 有了更好的晶体管，也变得更快了。这时候像打孔纸带这样的输入输出设备，速度就远远慢于处理器了。**这个时候操作系统才开始登上历史舞台。**

到了 1950 年代后期，我们还在使用打孔纸带，但这个纸带已经可以表示字符了。一行 Fortran 代码就等于一张纸片、一张卡片，用打孔机按照脱落的方式戳孔。所谓编程，你先在草稿纸上写好，比如写 `x = y + 1`：我算 x，它有一个编号，比如 x 可能是 24，等号是 28（我随便写的，不重要），y 是多少也有编号；然后每个符号对应一段二进制，在对应二进制的位置上戳孔。戳完孔，你把一个程序几十张、甚至几百张卡片排好，送进计算机，计算机就一张一张卡片读进去，然后执行这个程序，结果甚至还可以写回到这样的卡片上。那时候也有打印机了，可以打一些比较复杂的东西。

**所以 Fortran 这样的编程语言已经足够好用了。**到了这个时候，就有了操作系统。

### 作业、操作员与 operating system 的由来

为什么会有操作系统呢？刚才说到，Fortran 代码是一张一张的卡片，这些卡片是需要人送到计算机里的：需要操作读卡机、打孔机。那时的计算机系统通常有两名操作员，而与操作员相关的软件系统，自然而然就叫 operating system。所以 operating system 在繁体里、在台湾的翻译里叫**作业系统**，它是管理 job 的。

原因很实在：**那时的计算机非常贵**。1950 年代，一台计算机可能要 50 万到 100 万美元，通常一个学校里可能就只有一台，整个大学可能只有一台。既然只有一台，那大家都要用：计算机系要用，大气系要用，甚至国防部还要插几个课题进来。

这么多任务摆在面前，它就得排队：

- 一个程序执行完了，最好能自动执行下一个，下一个执行完再执行下一个；
- 如果这个程序异常退出了，我可能还要打印出来一些信息；
- 这些都是公共的、通用的需求，需要一些通用的软件。

整个计算机系统在硬件之上同一时刻只能运行一个程序，跑完一个再跑一个，那就需要一个服务于软件切换的系统。这就是操作系统出现的位置：**若干公共的程序（从硬件上读数据、往打印机或打孔机上写数据），再加上一些诸如作业开始、作业终止这样的控制函数，构成了操作系统。**

也正因为手上同时有好多程序而机器只有一台，历史上就诞生了很多作业调度的策略。比如跟我关系比较好的人，我先让他跑。比如短作业优先——越快跑完的程序我越先让你跑，这样可以把所有人的平均等待时间降下来。这个策略是可以证明为平均等待时间最低的。当然这些都是历史了：因为计算机可能真的就只有一台，一次只能跑一个程序，所以才诞生了作业调度这样的概念。

Fortran 那个读整数的例子，跟我们熟悉的接口是一脉相承的。程序里写 `READ 5, 10` 加上 `i1, i2, i3` 这样的变量，读三个整数：这里的 `5` 是文件单元 5，也就是标准输入；`10` 是格式，我猜这是十进制。这类 read 命令，很大程度上就是操作系统为应用程序提供的——一台计算机上要跑很多个程序，每个程序都会有一些需要复用的功能，比如从计算硬件上读数据，或者往打印机、打孔机上写数据。

### 内存比程序大的那一刻

时间走到 1960 到 1970 年代，计算机变得更快，已经非常接近今天的计算机了：我们有向量了，有总线了，和你们在数电课、计算机系统结构课上学的东西很接近。这时候迎来了一个新的转折点。

1950 年代的时候，程序是一个一个跑的：跑完一个程序再跑下一个。而到了 1960 到 1970 年代，因为集成电路、因为 DRAM，我们的内存开始比程序更大了。

在内存还很小的时候，内存几乎和程序一样大，程序几乎总是把内存用满，所以一次只能跑一个程序。但当内存变大之后，我们就可以**把多个程序同时载入内存**。这带来了一个意想不到的好处。

假设内存里同时有 P1、P2 等等。机器可能只有一个 CPU，P1 在运行。运行一会儿之后 P1 可能要执行一个 write——我夸张一点，按今天的尺度来：P1 说我要写 1TB 的数据，那可能要花几分钟的时间。而这几分钟里 P1 其实不需要再用 CPU 了，因为数据已经在内存里，另外一个部件可以一点一点地把这数据写到一个更大的存储器上。

这意味着什么？P1 让出 CPU，它不要 CPU 了，那 P2 就可以在 CPU 上跑。P2 如果现在也要 write 1TB，那它也让出 CPU，P3 就可以跑。等到这些写操作都结束了，操作系统再继续恢复 P1 的执行。

```text
  CPU:   |------ P1 ------|--- P2 ---|--- P3 ---|---- P1 恢复并继续 ----|
  I/O:                   |========= P1 写 1TB 数据 =========|
```

于是操作系统的职责变了。以前它只需要负责 load、exit——能够加载程序、退出程序；现在它还需要在一个程序执行某个操作的时候，把另外一个程序换到 CPU 上执行，等这个操作执行完，再恢复原来那个程序。**操作系统有了切换和恢复的功能。**这已经和今天的操作系统越来越接近了。

### 通往今天的路：高级语言与个人电脑

在 60 到 70 年代，更多的高级语言和编译器出现了：COBOL、APL、BASIC、Pascal。然后 1972 年立下了一个丰碑，一直用到今天——我们讲代码的时候，用的还是 1972 年的 C 语言。

计算机科学家在今天是难以想象的低的算力下，开发着各种各样新奇的程序，从游戏到图形学。比如 Sketchpad，一个可交互的图形界面，它在一块像示波器一样的最早的显示器上显示出来，做矢量图像的绘制。它和今天的 SVG 很像——如果你们用过 SVG 画图，基本上就可以把它理解为一个交互式的 SVG 绘图系统。

然后，个人电脑登上了历史舞台。1975 年，Altair 8800 是**第一台掀起商业市场的个人微型计算机套件**（first personal mini-computer kit to spark a commercial market），这背后有很多传奇故事。

当时 Bill Gates 和 Paul Allen——Microsoft 的两位创始人——传说，而且应该是真的：他们在哈佛的大机器上，自己写了一个 Altair 8800 的**全系统模拟器**。注意，那时候第一台 Altair 8800 还没有被生产出来，一台机器都没有，但设计已经有了，图纸也有了。他们就是在这个“还不存在的机器”的模拟器上，开发了上面的第一个 BASIC 解释器。传奇的地方在于，他们带着纸带，坐飞机从东海岸飞到西海岸，在一个旅馆里把纸带装到那第一台 Altair 8800 的原型机上，BASIC 成功地运行起来了。

把三段历史放在一起看，操作系统的角色变化就很清楚了。

| 年代 | 硬件 | 软件形态 | 操作系统的职责 |
| :--- | :--- | :--- | :--- |
| 1940 年代 | 真空管、延迟线内存、打孔纸带 | 直接打在纸带上的二进制 | 没有操作系统 |
| 1950–60 年代 | 磁芯内存、更快的 CPU | 汇编与 Fortran，一卡一行 | 加载与结束程序，作业调度 |
| 1960–70 年代 | 集成电路、DRAM、总线 | C 等高级语言与编译器 | 切换与恢复，多个程序同时在内存 |

而谁也没想到，40 年以后，我们在全系统模拟器里面再写一个操作系统。

### 回到那句话

所以操作系统课教的不仅是“我们可以用 Logisim 去编一个普通的程序，让它用 `printf` 打印”，也不只是 `write`、`read` 这些系统调用。它实际上是一种 philosophy：**操作系统支撑了整个应用的生态，它不是一个人在战斗。**Unix 特别经典的地方，就在于它设计了一组可以复用的工具，而每个工具都可以任意组合、无限复用。

这门课真正想要表达的 take-home message，就是最开始那句：会编程你就拥有全世界。

## 程序即状态机：应用视角的操作系统
> 对应块：BLK03 | 覆盖分集：P02上 | 块标题（分集名）：《应用视角的操作系统（上）》

上一讲我们把操作系统的发展史快速过了一遍，我多少也劝了你们一句：在人工智能的时代，仍然值得坐下来好好学一遍操作系统。今天换个视角，也是这一学期看操作系统最重要的视角——应用程序眼里的操作系统，就是一组 API。

操作系统有一个很经典的描述：Operating systems, the body of software, in fact, that is responsible for making it easy to run programs. 它让程序去共享资源，让程序去和设备交互，此外还负责各种各样有意思的事情。换成你能直接感受到的说法：操作系统给你提供的这些 API，给了你非常大的能力，让你去做以前在 C 的控制台里只会用 `printf` 时做不到的事情。你了解操作系统的这些 API，就意味着你可以用操作系统来干更多的事。所以学一学还是值得的——尤其是在你知道操作系统可以做什么以后，你就可以指挥 AI 去调用这些 API，把它真正做起来。AI 很强，这话不假，但你没有合适的 prompt，它就呆在那儿什么也不动。

今天我们就把"什么是程序"彻底讲清楚，精确到程序里的每一个 bit 都是 well-defined 的。顺便，你们今天会第一次感受到什么叫计算机程序的形式语义；这个概念我不讲，你们自己感受。

### 为什么这一学期还是用 C

这一整个学期我们只用一个非常经典的编程语言，C。道理很简单：如果用一个更高级的编程语言，它绝大部分的部分都和操作系统没有关系。它在操作系统的基础上做了一层库函数的包装，语言本身关心的却是别的东西——比如你们写前端代码时的 JavaScript，很多语言设计是围绕着整棵 DOM 树怎么处理展开的；TypeScript 的类型系统也是很有意思的特性，但这些都和操作系统没有太大关系。

我们要讲的操作系统，是硬件和软件中间的那一层。所以要选一个离操作系统尽可能近的语言。最理想当然是汇编：在汇编里你可以直接和操作系统交互。可汇编没法拿来开发应用程序。于是只能取中间那一个——比汇编（乃至直接写机器码）高，又比"依据自然语言跟 AI 说话"低，是离机器最近、但仍然可以写应用程序的语言。也正因为如此，它才是最早把整个应用生态构建起来的语言，那就是 C。

### 把任何 C 程序改写成"每行只做一件事"

你们都学过 C++，进校第一个学期学的其实是"带了 struct 的、有一种面向对象的 C 语言"。学完之后你大概会有一种感觉：C 是高级语言，能写很多方便的写法，比如 `x = y + z + w` 这种很长的表达式；赋值右边甚至可以嵌函数调用，写任意复杂度的表达式。但你总是可以把它改写成每一行只做一小件事情的形式：

```c
t1 = y + z;
t2 = t1 + w;
x  = t2;
```

任何一个写在条件里的复杂表达式、任何一个塞在函数调用参数里的复杂表达式，都能这样提出来。提完之后，任何 C 程序都写成了"每行只做一件事"的样子；那么理论上，你对每个语句单步执行，一个语句就能对上几条指令。

这正好和你们在计算机系统基础课上写过的全系统模拟器对上了。那个模拟器里，你有一个 CPU state，包含每一个寄存器的值和内存里每一个单元的值；你根据 program counter（PC）处的指令取指、译码，知道这条指令要干什么——比如把两个寄存器的值加起来放回第三个寄存器。C 程序的结构和它几乎一模一样：

- 你有一个 PC，也就是 gdb 里高亮的那一条；PC 停在哪，你就知道当前这条语句要做什么，把它做掉；
- 遇到分支，同样处理。任何一个 C 程序都可以改写得足够简单，让每个条件判断里直接就是一个布尔变量，不是的话就提到外面；于是 PC 在这个位置时，从变量里取一个值，是 true 就把 PC 跳到这边，是 false 就跳到那边——这个语法行为和一个跳转完全一样；
- 循环就是带条件的跳转。`while` 和 `if`，解释执行起来你甚至会觉得它们是同一件事。

这就是为什么我说 C 是一种"高级的汇编语言"：把 C 改写成上面那个形式以后，C 语言里所有的语法成分都可以用几条非常显而易见的汇编指令写出来，你几乎可以原样把 C 代码翻译成汇编代码。C 语言的编译器因此非常容易构建。

> **结论**：C 之所以是"高级的汇编语言"，不是修辞，而是因为它可以被逐语句地对上指令序列。

对比一下 C++ 就知道这件事多不容易：在 C++ 里写 `pointer->foo()`，它干的事会比你想象的多——如果 `foo` 是个虚函数，你得先反应出对象里有一张 vtable（函数表），这次调用还要去查表。这样一行代码会被翻译成什么样的指令序列，你一下子反应不过来，编译器的行为比 C 的编译器复杂得多。

顺着这个想法，还可以更省事：既然 C 能改写成"每行只做一件事"的 simple C，那写一个编译器来做这件事当然可行，也确实有人做了。有一个叫 CIL 的项目，十几年的老项目了，能把符合 C99 标准的程序再编译成一个更简单的 C，据我所知是用 OCaml 写的；我们以前做 research 还用过它。有了它，就可以做程序分析、做编译，或者干点别的。但今天写编译器未免太复杂——我可以让大模型来帮我做这个改写。

### 程序的执行就是一个状态迁移系统

我们拿最熟悉的例子开场：一个 Hello World，一个非常典型的 C 程序，也是一个非常典型的操作系统上的应用程序。今天我真正想让你相信的是——你看到的所有应用程序，包括编辑器、包括我刚打开的 Cloud Code、包括显示这个桌面的程序，本质上都和这个 `hello.c` 没有区别。你从学习编程的第一课就被告知了这一点，但可能一直到今天，我才会真正打开一个复杂程序告诉你它是怎么和操作系统交互的。

这个程序当然可以改写成 simple C。不信可以单步调试：每个语句都是简单的（`putchar` 就跳过去，它无非打印一个字符）。比如说在第 18 行打个断点、继续，就进到 `print_number` 里。正常人不会这样写程序，显得很冗余，但我确实确信：每一行都能改写成只做一个赋值，就和你学过的指令集一样。

这意味着什么？计算机硬件是 everything is a state machine——上一次课我说过，它是 register 和 memory 这个状态驱动下的指令的状态迁移。一个 simple C 程序其实也是这个模型：一个 `.c`，从执行一条语句走到下一个状态。gdb 跑起来的样子，就好像它解释执行了刚才这个程序。

那能不能把这个程序的状态和迁移全都打印出来？以前做这件事挺麻烦、挺费事的；有了 AI 以后，我发现比想象中简单。我准备了一个小脚本：上面是我写的 prompt，剩下部分都是 AI 帮我生成的，我一眼都没看，后来为了上课效果稍微改了一下。它告诉我要用 `gdb -q -x` 加一份命令脚本去跑任意一个程序，比如跑这个 hello。跑起来后它还会 crash 一下——我猜是 error handle 没做好——但跑完就得到一个 `trace.log`。

看里面 `print_number` 那一段：一个状态里是 `c` 等于某个值、`d` 等于某个值、`format` 是一个指向某处的指针（当然也可以把它指向的字符串打出来）；再跟它对话几次，这些东西都能修好。接下来那条是 `n < 0` 的判断，此时 `n` 是 42；然后再执行 `q = n / 10`，执行完就是 `n` 等于 42、`q` 等于 4——完全就像调试器一样。

> **提示**：硬件是状态迁移系统这件事，你们花了整个计算机系统基础课实现一个虚拟机才相信；而 C 语言同样是状态迁移系统，一开始你们是不太信的。现在一个 prompt 加一个小脚本，就能把任意程序运行时的状态提取出来。

### 函数调用：真正不熟悉的那一步

`x = y + z` 这种语句大家都熟。但我普遍发现，不是所有同学都对函数调用有把握：如果这条语句是一个函数调用，状态到底发生了怎样的迁移？为了验证你们是不是真的理解这一点，我这里有道题。

写一个非递归的 Tower of Hanoi。汉诺塔大家都会：为了把 n 个盘子从 A 柱子移到 B 柱子，先把 n-1 个盘子移到 C 柱子，再把一个盘子移过去，再把 n-1 个盘子移回来。代码就是这么写的。你们在学 C++ 的时候，对这段代码应该都感到过困难。

困难在哪里？拿 Fibonacci 对照。`f(n)`：如果 n 小于等于某个数就 return 1，否则 `return f(n-1) + f(n-2)`。这和你们高中在数学里学的函数是一样的，你写 `return f(n-2) + f(n-1)` 也行——两个调用的顺序不影响程序的结果。因为数学上的函数就是这样：给它一个输入，无论给多少次同样的输入，它一定给你同样的结果。汉诺塔不是。把两个调用的顺序换掉，输出的就不是正确结果了。这就是为什么大家普遍在把它改写成非递归时遇到困难。

我非正式地调查一下：假设期末考试上机不能用 AI、什么也没有，闭卷让你写一个非递归的汉诺塔，同时不允许你推导它的数学性质（其实你完全可以按当前状态判断哪个碟子在哪里、能算出可以把谁挪到哪里去，但假设不许用这种数学方法），有多少同学有自信在考场的一个小时或者一个半小时里写对？

没有人举手。这个我有点惊讶，但其实也很正常——老早几年以前我们经常问来保研的研究生，他们也写不出来。

还有一个加强版的题目，比汉诺塔再复杂一点：`f` 和 `g` 互相调用，`f` 会调 `g`，`g` 会调 `f`。你看，我调 `f` 的时候是 `f(n-1) + g(n-2)`，可调 `g` 的时候它又会调回 `f(n+1)`。你会说这好办，动态规划或者 memoization 就行——每当有一个 `f` 或 `g` 算出来就从小到大算，叠起来改写成二重循环。但是如果我要求你：在这个 `f` 里加一句 `printf` 打印 `f`、在 `g` 里加一句 `printf` 打印 `g`，然后写一个非递归的程序，把这个递归程序运行时的 `f`、`g` 函数调用序列打印出来——这题就难了。能考上南大、保送南大的研究生里，能把这道题写对的几乎很少。它一直以来也是我考 AI 的一道考题。

所以考题有三个版本：第一版是写一个非递归的汉诺塔；第二版是写对非递归的 `f` 和 `g`（AI 有时会讨巧，用一些出乎我意料的奇怪方法做对，结果确实对、也确实非递归，但好像并不是我们想要的那种完整的模拟）；最难的是第三版，输出函数调用的序列。

这几年 AI 的能力在实实在在地增长，我一路试过来：

| 模型阶段 | 非递归汉诺塔 | `f`、`g` 互调 | 打印调用序列 |
| :--- | :--- | :--- | :--- |
| GPT-3.5 | 能做对，我很吃惊；但可能训练数据里见过 | 做不对 | 做不对 |
| GPT-4 | 能做 | 还是做不对 | 做不对 |
| DeepSeek-R1（能推理的模型） | 能做 | 第一次做对了 | 投了非常多的 token，写了一些伪代码，估计它自己也觉得搞不定；但方向和思路基本是对的 |
| 今天的模型 | 能做 | 能做 | 做对了 |

DeepSeek-R1 是第一个能把 `f`、`g` 调用序列做对的模型，因为它能推理。顺便说一句我的感受：DeepSeek 那个 app 上的模型明显"降智"了，有些你原本预期它能答对的问题现在答不对，还会产生幻觉；但就是这样，这道题它做对了。据说现在跑的是一个 200B 的比较小的模型，也还在等一个更大号的模型发布，不过没人知道传闻是真是假。

### C 程序的状态到底是什么

看简单例子的时候，你们很容易产生一种错觉。当我说程序是 state machine，它有一个状态，那状态是什么？是不是我现在这个 lexical scope 里有一些全局变量——比如全局变量 `stdin`，它肯定有一个值；然后当前作用域里还有一些别的变量，比如 `n` 等于 42、`q` 等于 4。于是就有一种课上的说法：你当前有一个状态，执行一个语句，比如 `if (q != 0)`，如果 q 不等于 0，你就到下一个状态，PC 可能就变了；如果这条语句是 `x = 1`，那 `x` 的值就变了。

这不是对 C 语言程序状态的完全精确的理解。

我说 everything is a state machine 的时候，意味着我们讨论的这个对象有严格的数学定义，非常非常精确——你可以用离散数学课的知识把它写出来：所有东西都是集合、关系、函数，用这些最基本的对象去定义什么是 C 语言的状态、什么是 C 语言的状态迁移，而状态迁移本身也是一个函数。理论上这是可以办到的。你们暂时不做形式化方法，不需要做得那么彻底、不必真的用集合论的语言把它全部定义出来；但你背后要知道：计算机世界里哪怕是一个非常复杂的、操作系统上真实存在的对象，它背后都有一个严格的数学理解。

那么真正的状态是什么？不谈"把一个 C 程序真正载入硬件跑起来"涉及的那套 Application Binary Interface，就回到 C 语言课本身：一个 C 程序从哪里开始执行？从 `main` 开始。于是这个状态机的初始状态里，一定有一个函数调用栈，栈上有一个叫 `main` 的栈帧（stack frame）。`main` 的栈帧里有它所有的局部变量，比如 `argc` 等于 1、`argv` 是一个指向外面某处的指针；再加上全局变量，比如 `stdin`，每个全局变量都有值。

下一个问题：程序运行时那个"当前语句条"——调试时亮起来的那一条——在哪里？**PC 在栈帧里。** 这是最重要的一个区别。我一开始画的那张图上单独有一个 PC，那是错的：模型上比较典型的、也是大家能接受的定义是，每一个栈帧上各有一个 PC。

于是执行规则就一句话：从 topmost frame 的 PC 上取出一条语句来执行。取出来以后，PC 移到下一个 PC，执行完，就这样，没有别的了。如果这条语句是 `x = x + 1`，PC 走到下一条语句，`x` 的值变化。

如果这条语句是函数调用呢？假设 topmost frame 的 PC 当前指向的正在执行的语句是一次函数调用，调用 `foo`，那么函数调用的行为是：在顶上**创建一个新的栈帧**。所有旧的栈帧一个都不动，全部保留，无论它有多少个；新栈帧的 PC 是这个函数的入口，旧的 PC 变成 next PC。这就是函数调用。

```text
   调用 foo() 之前                    调用 foo() 之后

   +---------------------+            +---------------------+
   |  main               |            |  foo                |  <- topmost
   |  PC = next line     |            |  PC = entry         |
   |  locals: argc, ...  |            +---------------------+
   +---------------------+            |  main               |
                                      |  PC = next PC       |  <- 旧的 PC
                                      |  locals: argc, ...  |
                                      +---------------------+
```

读图：调用发生时旧栈帧原封不动留在下面，新的栈帧压在最顶上并把 PC 指向函数入口，而旧栈帧里保存的 PC 就是函数执行完要回去的那条语句。CPU 上真正干活的就是最顶上那一帧，所以"取语句"永远只发生在 topmost frame 的 PC 上。返回就是把这个栈帧弹掉。

把这个模型和硬件模型并排看：

| 状态机的部件 | 硬件（指令级） | C 程序 |
| :--- | :--- | :--- |
| 状态 | 寄存器 + 内存 | 全局变量 + 函数调用栈 |
| 当前位置 | PC 指向的指令 | topmost frame 的 PC 指向的语句 |
| 一步迁移 | 取指、译码、执行 | 取出一条语句并执行 |

如果你还不信，就去看非递归的汉诺塔：去调那个程序，你就真正知道我说的"计算机世界里你看到的东西都是没有魔法的"。所谓 `call`，就是往栈上 push 一个 frame，它的 PC 是 0；我 push 什么值就是什么值。所谓 `return`，就是 pop 一个值出来。写一个非递归的汉诺塔，我先 `call`"把 n 个盘子从 A 经过 C 移到 B"，注意这个 CALL 调用的是我定义的一个宏，做的事就是把一个栈帧压上去；接下来我的"C 语言模拟器"就开始执行了，它从这样的状态出发，每次机械地遵循上面那条规则——从 PC 上取一条语句出来，取出什么就执行什么，是函数调用就按函数调用处理。

于是你看到，我写出了一个和递归汉诺塔长得一模一样的非递归汉诺塔：

- 如果当前的 PC 是 0，说明我在函数的入口，那我就做入口要做的事；如果 `n` 是 1，我就 return；
- 如果 PC 到了第二条语句，那我就直接去调用 n-1 个盘子的那一次移动，把 n-1 个盘子从一根柱子移到中间那根柱子上；
- 最后我还能把总共走了多少步加起来——这是带返回值的汉诺塔，`int` 返回类型。第一次递归调用得到的步数存下来，第二次也存下来，返回 `c1 + c2 + 1`。

注意 `c1` 和 `c2` 是在栈上的，在这个 frame 里、是它的局部变量；就像 `main` 里的 `argc`、`argv` 是 `main` 的局部变量一样。所以在你写出来的非递归版本里，每个 stack frame 里你会看到：一个 PC，所有的参数（参数也是局部变量），以及你的局部变量。

```text
   Frame {
       PC             <- 0 表示"在函数入口"，其余值表示"执行到第几条"
       args           <- 参数，也是局部变量
       locals         <- c1, c2, ...
   }
   CALL  = push 一个 Frame
   RETURN = pop 一个 Frame
```

这样你就真正知道为什么 C 语言是一种高级的汇编语言：因为你真的可以这样解释执行 C 语言。理论上所有编程语言都可以这样解释执行，但最容易把它翻译成机器指令的，还真的只有 C。所以 C 给了我们一种非常好的掌控感，让你能彻底掌控整个计算机的完整行为。

> **结论**：计算机世界没有任何魔法，它都是数学，都是你能用离散数学定义出来的东西。既然唯一要做的事就是"从 topmost frame 的 PC 取一条语句执行"，那么 `f` 调 `g`、`g` 调 `f` 这种互相调用也就自然而然解决了——我根本无所谓这个 PC 是什么，它指到 `f` 就执行 `f` 的语句。你只要严格遵循 C 语言的形式语义去执行，所有东西都应该是对的。

### 什么是编译器

讲清楚了什么是程序，就可以问什么是编译器了。编译器是把一个 `.c` 翻译成某个 `a.out` 之类的东西——这是广义的编译器，它把汇编器、链接器都包括进来。不管产出什么，`a.out` 的执行模型就是计算机系统基础课上那个 memory 和 register 的指令执行模型。一句在上面是语句，一句在下面是指令，你马上就有感觉了。

#### 从"原样翻译"到"可以改程序"

最早的时候，C 语言的编译器不像今天这么复杂。今天有人说你去看一看 GCC 的源代码，你可能会说不要不要。那个时候的编译器和今天的 transpiler 很像——你们有同学用 JavaScript，JavaScript 满地都是 transpiler，它做的就是一些简单的语法变换，把新版本的 JavaScript 变成旧版本的。

最早期的编译器，就是把语句原样翻译成指令，一条一条翻译过去。那时候大家甚至还没有意识到别的事情：所谓编译器，不就是把一个语句原样翻译成指令吗？翻译完了就一定等价——只要我的程序没有 bug、只要写解释器的那个模拟器没有 bug（就像你们写的那个虚拟机，假设它能没有 bug），那所有事情就做完了。

但不完全是这样的。我们发现，编译器是可以改变这个程序的。比如我写了 `x = 1 + 2 + 3`，然后这个 `x` 我根本不用——这就是死代码，我是可以把它删掉的。

#### 编译器允许做什么、不允许做什么

接下来的问题就很有意思了：到底编译器可以做什么样的优化，什么样的优化不能做？上完这节课，你应该能回答这个问题。

设想我有一个 `a.c`。理论上，我可以定义出一个集合——所有可能的 `a.out` 的集合。可以吧？可能是无穷的，或者是有穷的（比如某个大小之内的所有 `a.out`）。那么 `gcc -O0` 会编译出某一个 `a.out`，它是对的；`gcc -O2` 也会编译出某一个 `a.out`，它也是对的。问题就来了：我能不能定义所有 `a.out` 的一个子集，即"哪些指令序列是允许的"？

抽象的逻辑看一眼例子就有感觉了。同样的函数，人手动写：最笨的写法是把常数一格一格 load 进寄存器、做乘法、再写回，好几条指令。但你作为人看到这段代码，肯定有一种不由自主的冲动——直接 `move #25` 然后返回，如果我没有把那个底层的东西算错的话。这一版就应该落在我预期的"正确集合"里。而如果你写一个 `return 24`，它就不在这个集合里。

那实际编译器怎么做？看真实编译产物：`-O0` 的版本已经开始做优化了，所有的常数表达式它都会直接计算出来。同一段代码，`-O0` 先把那个常量折叠成 24、剩下的 `+1` 被保留下来，而 `-O2` 直接算出了 25——八条指令对两条指令的距离。

再看 `f4`（这些汇编看不懂没关系，大概看一下就行）：`f4` 里 `x = 1` 这件事做了两次，所以 `-O0` 会先把 1 移进一个寄存器，再 store 给 `x`，老老实实写两遍；到了编译优化后的版本，store 就只剩一条了。编译器知道：你对同一个变量连续赋两次值，前一次的效果是不变的，可以消掉。

> **提示**：现在这个时代，也不需要像以前那样硬啃汇编了。直接让它解释一下就行——它像一个活生生的人，会先去列一下文件、把每个文件都读一遍，就在重复我刚才做的事情。同理，我这次上课用的是树莓派，那是 ARM64 的系统，和你们的手机、和现在这台在推流的电脑都是同一套 ARM 架构；它的汇编指令你们很不熟悉，比如 `LDP`、load/store 之类。但这些都不重要：只要你学过任何一个机器结构，你就知道每条指令大概有哪几类——有些 move 可以访存，有些做数据移动，有些做算术，有些是系统指令。你在 x86 或者 RISC-V 里学过一次这些概念，碰到 ARM 的时候，可以让它用 x86 的方式给你解释一遍。

（说到机器，插一句题外话：小霸王学习机是我的童年回忆，它长得和这台树莓派几乎一模一样，只是大很多；你们肯定没听说过，但你们大概有任天堂的 Switch，插一张卡带就能玩，我家小朋友也玩。那个时候不能卖游戏机，必须卖"学习机"，里面内置了很多学习软件，可以打字，还有 BASIC 编程。另外，你们的计算机系统基础课是 x86 吧？我们是应该把那门课全部改成 RISC-V。）

回到正题。**什么是编译器？编译器就是你的状态机的执行。** 所有状态机的执行都是内部变量的数据变化。那么你想想：如果你不打印任何数据，并且假设你的程序会终止，编译器应该把你的程序优化成什么？优化成一个空程序。无论你做多少事情，只要你这个程序永远不会往外输出任何东西，编译器理论上就可以把它全部优化掉，也应该这么做。

所以编译器里唯一不能优化掉的，是一些比较特殊的语句——相当于编译器看不到的语句，也就是向外部调用的语句。这是对今天的编译器来说的：假设我编译这段代码，而其中有一条语句是调用一个外部函数，比如 `printf`，这个函数是之后链接进来的，那你就不知道它的行为是什么。它可能是用汇编语言写的，那它就有可能让整个世界毁灭——就好像执行一个动作，核弹就飞出去了。当我把一个电平、一个数据、一个电信号真的从计算机送到计算机外面的时候，你就不知道到底会发生什么后果；真的只要一个电信号，就可以驱动物理世界里的变化。

所以：所有我知道它行为是什么的东西，我原则上都可以改动它；但对外界的调用是不能改的。比如我 `printf(x)`，把当前这个 `x` 变量作为参数传给 `printf`，那这个 `x` 在这次运行的时候等于 1，我调用到外边的时候就**必须**等于 1；我的程序按解释执行的写法输出的都是低电平，那编译优化完了以后，也必须输出低电平。

```text
   +------------------------------------------------------+
   |  程序内部状态（变量、栈）                            |
   |  没有外人能观测 -> 编译器可以任意重写、合并、删除     |
   +------------------------------------------------------+
                          |
          +---------------+----------------+
          |                                |
    外部调用（printf 等）              其余内部语句
          |                                |
          v                                v
   编译器看不到它的行为              编译器知道全部语义
   只能原样保留这次调用的参数        -> 改写成任何等价形式
   外部可观测的输出必须一致
```

读图：左边是编译器可以随便动的内部状态，右边分出的两条路说明了优化的边界——凡是会离开这台机器的效果（外部调用、外部可观测的输出）都不许改，凡是只活在程序内部、之后不再被观测的东西都可以任意处置。

> **结论**：什么叫编译正确？就是在任何输入下，它的输出序列都完全相同，这就叫编译正确。

这句话的含意比较丰富，我说得也不是很严谨，你们真正学到编程语言的形式语义时会再学一次；刚才没反应过来完全不要紧，有个"好像是这么个道理"的感觉就够了。这也正是我们要用状态机的视角去理解操作系统、去理解编程语言的原因——状态机视角是编程语言这个学科从诞生一开始就一直在用的视角。我甚至觉得它不应该在我的课堂上才第一次被提出来：语言是这样构建的，机器也是这样构建的，它天生就有这样的映射，你只要稍微往前多想一点，就能想到更多更有趣的东西。当然，什么是编译正确性我是不会考的，你们就当我什么也没说。

### 最小的 Hello World

你们都是从 `printf` 开始的。你们也知道，如果你试图去调试 `printf`，会发现 `main` 函数执行之前，机器其实已经执行了很多很多别的指令，那些都在库函数里。

那你能不能写一个最小的程序，它能打印出 Hello World？现在这样的程序，gcc 可能已经会直接拒绝掉；如果是纯标准的 C89，也许还能过。

我这样写 `gcc hello.c`，它能正常工作，能输出 Hello World，但这肯定不是最小的：光是这个文件就有 70 KB。用 `objdump` 去看，里面有好多好多东西，那些代码你都不知道是干什么的。你当然可以直接把这个文件打开、问一句里面有什么——我不干这事。但你可以确信，这不是一个最小的 Hello World。

那能不能这样：先用 `-c` 选项编译这个 `hello.c`，它不就变成一个目标文件了吗？这不就小了吗？然后直接用 `ld` 去链接它，会发生什么？——对不起，链接器拒绝了你：`undefined reference to puts`。链接器还把 `printf` 优化成了 `puts`，这不重要；重要的是你没有办法这样把它链接起来。

那如果你真的想写一个最小的程序，并且能让这个程序在你的机器上运行起来，这可以吗？应该可以。你们大概有一个印象：在 C 里，约定俗成的 `_start` 才是整个程序真正的入口，链接器默认要找的也是它，而不是 `main`；而刚才那条链接失败的报错则告诉你，这个最小程序对 libc 的依赖也得由你自己处理。

### 本讲提到的题目

#### 汉诺塔的三个版本

**题干**。第一版：写一个非递归的 Tower of Hanoi，把 n 个盘子从 A 柱移到 B 柱（提示：等价地，从 A 经过 C 移到 B）。第二版：`f` 与 `g` 互相调用——`f` 调用 `f(n-1) + g(n-2)`，`g` 又会调回 `f(n+1)`；要求写一个非递归的版本，并注意 AI 有时会用一些出乎意料的讨巧办法做对，虽然也确实非递归，但并不是我们想要的那种完整的模拟。第三版（最难）：在 `f` 里打印 `f`、在 `g` 里打印 `g`，要求写一个非递归的程序，把递归版本运行时的 `f`、`g` 函数调用序列打印出来。讲师给的现场条件：闭卷、不能用 AI、不允许使用"按当前状态直接算出能挪哪个碟子"的数学方法。

**解析**。这三题的要害都是正文里的 C 状态机模型，而不是什么数学技巧。状态是全局变量加函数调用栈，每个栈帧上各有一个 PC，执行的唯一规则是从 topmost frame 的 PC 取出一条语句执行；函数调用就是在顶上新建一个栈帧（旧栈帧全部保留、新栈帧的 PC 置为函数入口、旧 PC 记为 next PC），返回就是弹掉这一帧。把递归改写成非递归，就是把这件事显式做出来：自己定义一个 frame（含 PC、参数与局部变量），`CALL` 是 push 一个 frame（PC 置 0 表示"在入口"），`RETURN` 是 pop；用 `PC` 的值来区分"该做入口的事"还是"该做第几条语句"，函数返回值也一并存在帧里（例如汉诺塔返回步数，第一次、第二次递归的结果分别存下来，返回 `c1 + c2 + 1`）。

第一版只需要把栈和 PC 显式化即可。第二版多出来的困难与汉诺塔同源：`f`、`g` 互相调用时，谁在栈顶上、下一步该执行谁的哪一条语句，全部由帧上的 PC 决定，一旦显式建帧，指向 `f` 还是指向 `g` 都无所谓。第三版的难处在于调用序列本身是一个外部可观测的输出：每一步 push、每一次调用的进入都必须按顺序打出来，所以你必须真正完整地模拟出调用过程，而不能用动态规划或二重循环那样的数学改写绕过去——这与正文所说的"编译可以改变程序、但外部可观测的效果必须一致"是同一个道理。

**解析**。讲师在现场只推进到这里，没有给出完整写法，可依据的事实都记在正文里：`gcc hello.c` 能跑，但产出的文件有 70 KB，`objdump` 里全是看不出用途的代码；加上 `-c` 之后得到的目标文件确实小了，但直接用 `ld` 链接会被拒绝，报 `undefined reference to puts`（链接器把 `printf` 优化成了 `puts`）；而 C 里约定俗成的真正入口是 `_start`，不是 `main`，所以这个最小程序还需要自己接管入口以及对 libc 的依赖。这一点与"向外部调用是编译器唯一不能优化掉的东西"相呼应：一个最小程序要自己定义那些会被外部观测到的边界。

## 从一条 syscall 垒起来的应用世界
> 对应块：BLK04 | 覆盖分集：P02下 | 块标题（分集名）：《应用视角的操作系统（下）》

什么是程序、程序怎么从高级变成低级、什么东西是真正不可优化的——这些前面都交代过了。但还有一件最基础的事一直没讲清楚：一个程序的第一条指令，究竟是从哪来的？

我先把一个 C 文件 `ld` 了一遍，居然成功了；再 `gdb` 上去，用一个叫 `starti` 的东西从第一条指令开始执行。我的程序的第一条指令就停在了 `hello.c` 的第二行，第二行是一条跳转指令，于是我就死循环了。能确认的是：我写的代码，我是真的能控制住的。

顺便把另一半也试了：如果我想要程序返回，它会正常返回吗？它不会，它会 crash。下面就从这个 crash 讲起。

### 从 main 返回会 crash

我们对 C 程序的刻画一直是这样的：从 `main` 函数开始，每一步执行栈顶那个 topmost frame 上 PC 指向的语句。

那么如果 `main` 有一天返回了呢？状态就空了——栈顶上不再有 frame，PC 也就取不出来了。下一个状态是什么，我们没有定义过。当然，我们肯定是需要一个定义的：要把它写成一个数学化的表达，你可以允许它"到此终止"，这就叫终止。但在"编译器把它翻译出来的、直接在硬件上执行的那个状态机"里，初始状态并不是这样的。

每一个进程在被加载的时候，都有一个加载时刻的初始状态：一份 register 加一份 memory。一个 `.c` 文件对应着一个 register 与 memory 的初始状态，然后它每执行一条指令，就往后走一步。函数返回这件事落到指令上，就是一条 pop：把栈顶保存的那个 PC 装回到 PC 上。所以进程被初始化的时候当然也是有栈的，也有一个 stack pointer——你们熟悉的 `rsp`。

拿一个只有 `nop` 和 `return` 的 `a.out` 试一试就很清楚：`nop` 执行完什么也没发生，接着执行 `return`，而我们能从栈上 pop 出来的值是 0，于是 PC 就变成了 0。0 那一页是非法的内存，所以这个程序立刻 crash，报 segmentation fault。这就是"空的 `_start`"为什么会崩的完整解释——每一条指令都只是机械地做它该做的事。

> **结论**：真实的编译器工具链不是从 `main` 开始的。System V 的 ABI 规定了整个进程的初始状态是什么：初始 PC 指向的是一段初始化代码，这段代码把所有事情都做好，然后 `call main`；`main` 总有一天会返回，返回之后这段代码还要继续执行下去，而它自己是不能返回的——它会去执行一条系统调用。

这个"非返回不可、却又不能返回"的启动代码，就顺手把我们今天真正的主角引了出来。至于进程在二进制层面对应的完整初始状态，那是另一节课专门要讲的内容，今天先放一放。

```text
System V ABI 规定的初始状态（register + memory）
              │
              ▼
   启动代码（初始 PC 指向这里）
              │   把所有事情做好
              ▼
        call main            ← C 程序从这里才被"开始"
              │
              ▼
        main 返回
              │
              ▼
   启动代码继续执行（它自己不能返回）
              │
              ▼
        系统调用 exit
```

读图：进程的第一条指令不是 `main`，而是一段启动代码；它负责准备好一切、调用 `main`，并在 `main` 返回后用一条系统调用彻底结束这个进程。

### 写一个真正的最小 Hello World

顺着这条路走下去会得到一个很有意思的结论：如果你真的想写一个能打印 Hello World、并且能正常退出的程序，你不会那样写。

因为 C 语言本身根本没有"退出"这件事。只有请求操作系统，你的程序才能退出。

而在操作系统和 C 之间，我们约定了一条指令。上一讲我说过，从应用程序来看，操作系统就是一组 API；这组 API 就是用一条系统调用的指令实现的。x86 上这条指令是 `syscall`（你们做实验的时候可能用的是 32 位时代的 `int 0x80`，64 位系统我们都用 `syscall`），ARM 上是 `svc`，也就是 software interrupt、软件中断，RISC-V 上是 `ecall`。

调用的方式非常机械：把系统调用的编号放进指定寄存器，再把参数一个一个放进后面的寄存器，然后执行这条指令。

| 体系结构 | 系统调用编号 | 参数 1 | 参数 2 | 参数 3 | 陷入指令 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| x86-64 | `rax` | `rdi` | `rsi` | `rdx` | `syscall` |
| ARM | `x8` | `x0` | `x1` | `x2` | `svc` |

读表：编号决定"要请操作系统做哪件事"，参数决定"这件事怎么做"。这份对应关系不是我随手定的规矩，手册里有明文规定——各个体系结构下，一个请求操作系统的动作应该怎样传递参数，都写在里面。你只要把合适的值放进合适的寄存器，就可以去请求操作系统。

要打印 Hello World，只需要两个系统调用。`write` 要三个参数：文件描述符（往哪里输出）、缓冲区地址（写什么）、字符数（写多少），相当于你要把这个缓冲区送到操作系统里去。`exit` 的参数就是程序的返回值。

> **注意**：`syscall` 相当于一次很长的跳转。它跳过去之后，操作系统干什么就不受你控制了——它可以往外面写数据；等 `syscall` 回来，你的程序再继续往后执行。但操作系统完全有可能改变你程序内部的状态，甚至直接把这个程序干掉。

我准备了 x86-64 的版本，也准备了 ARM 的版本（我的机器要跑 ARM）。写成汇编之后，还是用 `gcc` 走一遍 assemble 和 link，执行出来就得到一句 `hello os world`。打印它的返回值，确实是 1。

你们回去可以试：把那句汇编里 `exit` 的常数从 1 改成 10，整个程序返回给外部的返回编号就变成 10。这就是系统调用指令的全部秘密。

### 在 GDB 里单步这条指令

为了防你们不信，我把这个最小程序放进 GDB 里调了一次。

`400000` 是这个二进制文件头部的位置，我这个二进制文件加载的地址是 `400078`。我把缓冲区指针交给 `x1`，文件描述符交给 `x0`，需要打印的大小交给 `x2`，把系统调用的编号交给 `x8`，然后执行 `svc`。单步调试——就这一条指令——它执行完就跳到下一条指令，而 `Hello World` 已经打出来了。

也就是说，操作系统在背后做了很多事情，可能执行了几万条指令，但它把这个东西打印出来了。接着继续单步：这是 `sys_exit`，当我最后一次执行完 `svc`，这个程序就退出了。

> **结论**：我确实得到了一个最小的、能直接在操作系统上跑的程序——它的第一条指令就是我自己写的那两条汇编。执行 `exit` 之后就再也没有醒过来。

### 唯一能把控制权交出去的一条指令

这是今天最要紧的一条区别。

你在 C 里见过的其它指令——数据移动、访存、赋值、分支、循环——本质上都只能改变当前进程的 memory 和 register。你的程序没有办法去改变另一个进程的状态，没有任何一条指令做得到。只有 `syscall` 可以。

而 `syscall` 的前提是：你要把控制权完全交给操作系统。

我打两个比方。

一个是做手术。你先跟你的手术医生签好一份 contract，写清楚要做什么；签好之后你躺到床上、眼睛一闭，等你醒来的时候——可能什么事也没发生，可能你已经变成女生了，也可能你再也没醒过来。

另一个是祈祷。在一个科幻幻想的世界里有一个全能的上帝，你想做什么事，只要对天祈祷；祈祷完，下一秒钟这件事就突然实现了。至于这中间发生了什么，你完全没有感知。

落到指令上就是：你在任何一个状态上执行一条 `syscall`（ARM 是 `svc`，RISC-V 是 `ecall`），后面的执行对这个程序来说就完全看不见了，因为跑的是操作系统的代码，操作系统也访问不了你这个程序。操作系统照着那份 contract 办事——参数是你事先写进寄存器的，它知道你想干什么；它会检查这件事合不合理、有没有越权：越权就拒绝，返回一个失败；合理就照做，做完再返回。

`read` 是个好例子。如果你在那块 buffer 上执行的是一个 `read` 的系统调用，操作系统就可能在返回的时候把 buffer 给你填上：比如从键盘里读进来一个 hello，那是 5 个字符，于是这个系统调用的返回值就是 5，buffer 里也相应填上了内容。

`exit` 则是另一头。如果我调用的是一个 exit 的系统调用，我这个程序就永远不会再回来了——这个程序所有的资源，所有这些东西在操作系统里都不存在了，这个进程就没有了。

```text
     我的程序                                操作系统
     ────────                                ────────
   把编号写进 rax
   把参数写进 rdi / rsi / rdx
        │
        │  syscall（一次很长的跳转）
        └──────────────────────────────▶  照着 contract 检查：
                                             合不合理？有没有越权？
                                               │            │
                                         越权 → 返回失败    合理 → 照做
                                               │            │
       ◀───────────────────────────────────────┴────────────┘
        │
   取操作系统改过的状态（比如填好的 buffer），继续下一条指令
   ——也可能再也没醒过来：如果这条 syscall 是 exit
```

读图：`syscall` 之前是你，`syscall` 之后是操作系统；它按你写进寄存器的参数判断你的意图，检查通过就替你办，办完再把结果放回你可见的状态里，你才继续往下走。

> **结论**：如果你假设 `syscall` 是应用程序和操作系统之间唯一的接口，那么除了 `syscall` 之外的所有东西都是可优化的——只要对所有的输入，这个程序产生的 `syscall` 序列都完全相同，你的优化就是对的。你只需要优化到这个程度就够了。

（这个说法不是绝对严谨：你们后面学下去会发现，应用程序和操作系统有时会共享内存，那就比较麻烦了。）

这一页幻灯片，是整门操作系统课最重要的一页。

### 操作系统面前，众生平等

操作系统上所有的程序，都和我们刚才那个 minimal 没有本质区别：它们共享完全相同的一套 system call。

你现在看到的这整个桌面——可以显示图形的终端、上面的窗口管理器、我打开的 VS Code——在操作系统面前，众生平等。所有运行的进程看起来都是一样的。当然会有调度策略上的区别，比如有一个叫 `nice` 的机制：越"好"的人，得到的 CPU 越少，它会把资源向一些进程倾斜，还会做其它有意思的事情。但从概念上说，你看到的所有程序都是一样的，都和那个最小的程序完全一样。

那这个世界上到底有哪些应用程序？平时每天用的：GCC、Clang、Node.js、GDB（我今天上课一直在用它们），再往应用层走，OBS（我现在直播推流用的）、VLC（你们看电影用的）、Firefox，还有各种编辑器和 AI 编程工具。第一次意识到这些东西和那个 minimal 一样，可能会有一点吃惊——我今天上课就是为了说服你们：它们真的是一样的。

说到写应用，就免不了说到今天怎么写应用。你们没有 VS Code Copilot、没有 Cursor 就没办法编程了，而我现在觉得没有 Claude Code 已经不会编程了。不过我认为现在的编程还没有进化到完全体。我很少调前端，也很少玩前端，但为了上课，我被迫要调前端；调的时候才发现 Next.js 有一个非常好的特性——我对代码库的任何修改都会立即反映到页面上。也就是说，如果 Claude Code 改了我的 CSS，它刚把文件改完，我下一秒钟就能看到展示的效果。我一开始什么都没有，是一个没有任何样式、只有文字的光板；我说"让我做一个什么样的幻灯片"，它给我做了一个，但是不对——幻灯片和幻灯片之间的间隔不对；我说"把这个间隔拉大一点"，按下回车几秒钟，间隔就被修好了。大概三分钟我就把这个东西调好了，调得简直觉得太舒服了。

后端编程现在还没做到这一步。如果我要开发 GCC、Clang 这样的东西，现在还不行；我最多只能说"你每次改完以后都运行一遍测试用例"，然后我能看到这次测试通过没有。如果测试用例没通过，还得让它自己去修。

### 应用世界是一层层垒起来的

从应用视角看，操作系统就是一组 API，今天讲清楚了，它差不多就是一条 `syscall` 指令（ARM 上是 `svc`，RISC-V 上是 `ecall`）。应用程序只能看到这个。但在这个 API 之上，有一层一层高得多的东西。

最底下那一层，是直接使用这些 API 就能独立工作的一批工具，叫 Coreutils。你们看到的基本命令行工具都在里面：`ls`、`cp`（拷贝文件的）、`mv`（移动文件的）、打印文件的、`grep`。`grep` 其实是单独的一个项目，不过像 `busybox` 这样的东西也会自带一个这样的 `grep`。这些也是 Claude Code 经常调用的命令行工具。

再往上是 Binutils（binary utilities）。我上课用 `gcc` 编译、用 `ld` 链接，`ld` 这个 linker 就是 binutils 里面的一部分。你要分析一个 ELF 文件，用 `objdump`；`strings` 可以从二进制文件里提取出可打印的字符串——原来二进制文件里面还有这个；`size` 可以查看文件里各个部分的大小。这些都是比较早期的 Unix 时代就已经留下来的工具。

再往上是后台的 daemon。你们如果有一个 U 盘插到电脑上，桌面上会自动出现一个图标，双击那个图标就能看到 U 盘里的内容；但如果你是一个真正什么也没有的操作系统，插上 U 盘是不会有任何反应的。你在操作系统这个世界里看到的一切，都是某一个程序和操作系统交流过之后由它做出来的。拿当前系统里跑着的进程看：`bluetoothd` 管蓝牙；cron 管定时的工作，比如你可以设置一个每天或者每隔几天做一次全系统备份的任务；刚才说的 U 盘挂载，是由 `udisksd` 完成的——名字里的 d 就是 daemon 的意思。它们在后台，大部分时候自己独立工作，有时也和那些工具程序交互。窗口管理器在某种意义上也是这样一个给你提供服务的程序。在这些程序之上，才是我们看到的 application。

图形这部分更是套了好几层。如果每个程序都直接问操作系统"我能不能往 (x, y) 这个坐标画一个 pixel"，那就乱套了：每个程序都好像自己拥有整个屏幕，每个程序都直接往屏幕上输出，最后怎么把它管起来？所以我们在操作系统之上又做了一层又一层的抽象。就用我现在用的这个窗口管理器来说：它下面有一个图形层叫 Wayland，Wayland 上面有一个 Sway；我的应用程序想要显示一个窗口，要先把"我要显示什么"交给 GTK 这样的库，这个库再发给 Sway，Sway 再发给 Wayland，Wayland 才真正和操作系统通信，把图形显示出来。这是一个很漫长的过程。

年复一年，有些软件被创造出来，有些软件死掉了；很多很多年以后，才终于到了今天——你想做一个应用程序变得很简单，有各种各样的工具程序，有帮你配置网络的、配置磁盘的、在后台自动更新的。这层生态就长成了这个样子：

```text
     应用程序   VS Code / Firefox / OBS / VLC / gcc / clang / node / gdb
   ─────────────────────────────────────────────────────────────────────
     图形与窗口：窗口管理器、Wayland、Sway、GTK 等库
     后台 daemon：bluetoothd / cron / udisksd / 窗口管理器
     工具程序：coreutils（ls、cp、mv、cat、grep）
               binutils（as、ld、objdump、strings、size）
   ─────────────────────────────────────────────────────────────────────
     操作系统 API：只有一条指令 syscall（ARM 是 svc，RISC-V 是 ecall）
   ─────────────────────────────────────────────────────────────────────
                              硬件
```

读图：从下往上看，每一层都只跟它下面那层打交道；应用程序从来不直接碰硬件，它最终都落在最底下那条 `syscall` 上。

但不管堆了多少层，它们本质上是同一种东西。用 `file` 看那个 minimal：它是 ELF 64-bit——因为我这是一台树莓派，所以是 ARM；你们看到的会是 x86_64。系统里的 `/usr/bin/as` 也一样，也是 ELF 64-bit executable，也是 ARM64。整个世界里面你看到的所有程序都是同一种东西。当然它们的复杂程度肯定不相同：能打印 Hello World 的 minimal 就很小。

### 让 AI 当那本你永远读不完的手册

我很建议大家至少和 AI 对话一下。

以前我们上课，我总是鼓励同学们去这些软件的官方网站读手册，手册会告诉你这个工具集里有哪些工具、各自干什么。但今天因为你有 AI 了，它会很有耐心地给你解释：什么是 Coreutils，Coreutils 里有哪些常用的工具。如果你对这里面的任何一个东西有兴趣——比如 binutils——你再也用不着去翻官方文档了，你只要加一个能让它读网页的 skill，然后问它：binary utilities 到底可以帮助我们做什么？

模型在这方面真的很强。对于世界上已经有的东西，尤其是在开发者之间被广泛使用的东西，它了解得比我还好——因为它把那些文档、那些开源项目里的所有用法全部读了一遍；我知道的可能只是我自己的理解，需要的时候还得回去翻一眼手册，而 AI 是真的把所有的东西都看过了。它马上就告诉你 binutils 可以干什么——上计算机系统基础课的时候这个用得很多，你要分析一个 ELF 文件；它还会告诉你 `strings` 可以从二进制文件里提取可打印的字符串，`size` 可以看文件里各个部分的大小。

以前想学任何一个东西，都得哼哧哼哧地啃英文材料。我知道你们对大批量的文件、一个很大的手册，第一反应就是"我不想读，明天再读吧"；到了明天又说后天再读吧，然后你这一辈子就不会去读它了。这对大家来说很正常。但 AI 给了我们一个好的起点：只要你对这里面的东西有兴趣，你总是可以现在就开始做。

### 亲手改一个二进制文件

我说这是一个 minimal 的 binary，请它 change its return value。

它很聪明：它先运行了这个程序，看到返回值是 1；接下来它开始调用 Coreutils 里的工具了——先用一个叫 `hexdump` 的工具。`hexdump` 可以把任何一个文件的字节序列打印出来，文本文件当然也可以，你直接在命令行里执行这个命令就行。然后它开始读输出，在找 `Hello World`，找到了 `Hello World` 所在的位置。

想了一会儿，它找到了：在某个位置有一条设置返回值的 `mov` 指令，和紧随其后的一条 `return`——它居然还能读懂 ARM 的机器码，这个我人都读不懂。它知道要把这个数反改成 42，于是又写了一条命令去改。我允许它运行，它还想再来一次；第一次它做错了，不过它显然有办法可以改回来。你看，最后它修对了。

> **结论**：计算机世界里面是没有任何魔法的。当我们说一段汇编或者一段 C 代码变成一个 binary file，这个二进制文件就是一个字节序列；这个字节序列里的每一个字节，都对应着程序里的某一部分，都存在一个合理的解释。你真的去改它，你就真的能把它改对。

这让我想起一些以前的经历。刚才我给你们看的是一种二进制的逆向，这是你们学过计算机系统基础课之后完全可以做的事情。几十年前，在还"五块钱就可以买一张游戏光盘"的时代，我在看起来人畜无害的《大富翁 4》上面找到了一个隐藏的神秘文件夹，里面有非常神秘的游戏。那个游戏难度太高了——但我惊奇地发现里面有一个文件叫 `game.save`，里面是一串神秘的东西，`0x00 0x00 0x01 0x00` 这样，代表进度。当我把这个二进制文件 hack 过以后，只要把一个字节从 `00` 改成 `01`，或者把末尾那个 `01` 改成另外一个数字，这个程序的行为就变了。那是我第一次二进制逆向。做过那一次之后，我再也没有做过二进制逆向，直到后来接近读 PhD 的时候才又做过一点。

但今天世界真的变了。**"Curiosity is all you need"**——只要你知道这个世界上有什么，知道这个世界是由 `syscall` 之上每一层的工具构建起来的，你就可以问 AI 有哪些工具，知道这些工具组合起来能干什么，然后让 AI 带着你干。而只要你能干成的事情，AI 都能干。

如果我穿越回去，把同样的方式告诉过去的我自己——那时候我还挺小的——我也能去 hack 那个存盘文件，也能去 hack Windows 的 binary：任何一个 Windows 的可执行文件也可以用同样的方式来 hack。如果你觉得某个东西太复杂，也一定有办法：就像今天用 AI 一样，可以一点一点把这个文件拆开、一点一点把它弄清楚。

在 coding agent 的辅助下，每一个人——哪怕刚来上操作系统课的初学者——和顶尖人类的差距都已经几乎是零了。刚才那个逆向能力，对一个熟悉 ARM 指令集的资深的人来说当然是很简单的事情，但它做得快，它懂得在正确的时候用正确的工具。工具是可以自由组合、无限复用的：一旦有一个好工具被拿过来，AI 马上就能学会怎么用，只要你给出正确的 prompt。

所以在这门课上，比起我教了什么概念——什么是 syscall、什么是 file、什么是 file descriptor，这些其实没那么重要——更重要的是教大家一种用工具的思维：你在操作系统世界里看到的所有应用程序，和命令行里的程序都是一样的。

### 用 strace 看穿 gcc 与 xedit

话是我说的，我是你们的老师，在这个领域里还有一定的知识储备，应该不会故意说一句错话来忽悠你们，那是违背师德师风、要被开除的。但这不意味着我说完这句话，故事就到此为止了。你们总是可以再问一句：真的吗？是这样的吗？这件事还能不能解释得更好？

下一步就是：我们有没有可能把任何一个真实的应用程序打开看一看，证明它真的就是在调用系统调用、在完成一些事情？

用到的工具叫 `strace`，system call trace（还有别的 trace，比如 library call trace 之类；你也可以做自己的 trace）。它可以把一个程序运行过程当中所有的系统调用打印出来——当然这还不是全部，还要再加一个选项 `-f`：我所有创建的子进程也要一起追踪。

先用 `gcc` 编译一个空程序，这件事你们在计算机系统基础课上面做过无数次。它生成了一个合法的二进制文件叫 `a.out`，然后也能执行，事情就过去了。但把 `strace` 打开以后，它就变得很长：你可以看到它开始读写文件，开始往一些临时文件里做事——它会创建一个临时的 `.o` 文件，弄好之后再把这个 `.o` 文件删掉，那里有一条叫 `unlink` 的系统调用。

这就顺便回答了一个问题。教科书上写着，`gcc` 会经过编译、链接这些过程，包括汇编，那它到底是调用了一个外部工具，还是它自己就把这件事情做了？从实现的角度，两者都可以：我完全可以实现一个自己的编译器，在中间把所有的东西都在内存里准备好，最后直接输出一个 `a.out`；我也可以以调用外部进程的方式来处理它。`strace` 帮你把这个系统调用序列打开，你就知道它真正是怎么发生的：你能看到 `execve`——那是启动另外一个程序所用的系统调用——`gcc` 确实在启动一些其它的程序，它试图去找一个汇编器，一个路径一个路径地找，找不到就换一个路径，直到有一个路径找成功了，这个汇编器就执行了。

那在 AI 还没有出现的史前时代，面对这种日志该怎么办？一个最简单的程序，`gcc` 编译它所执行的 2249 个系统调用，就是这么长，你绝对不会愿意看的。Unix philosophy 在这里起作用：任何一个文本，都可以经过一个工具把你不需要的东西给去掉。比如你对所有的文件操作都没兴趣，就把当前区域里所有的文本用管道传给 `grep`，把带 `AT_FDCWD` 的行都去掉——2249 行被 filtered 之后，现在只剩下 1700 个了。然后你对某一个系统调用感兴趣，就可以 `grep execve`。

今天再也不需要这样了。你只需要说：`trace all system calls generated by gcc a.c with all subprocesses`。你会发现最近的模型对 Unix philosophy 理解得非常好：它知道怎样从一个环境、从一个路径里找出相关的信息，不管是调用一个工具也好，还是直接把那个文件拿过来也好；它也能动态地生成脚本。它用了 `strace -o strace.log`，把输出更安全地写进文件，然后分析这个输出文件，在各种系统调用里翻。

而且它做得比我上课讲的好得多。我上课最多只能把那个日志给你们分析一下，分析完了以后还要花五分钟在黑板上给你们写；它把图都画好了：进程的父子关系——`gcc` 先调用编译器前端，再调用汇编器，再调用链接器，各是用什么系统调用做的。你还可以继续追问，因为所有的日志都在上下文里。

同一个方法可以用在图形程序上。有一个相对更简单的图形化编辑器叫 `xedit`（当然功能本质上和 VS Code 是一样的）：我可以在里面输入文本，也可以保存文件，可以有键盘和鼠标的操作，程序收到了键盘和鼠标的操作以后，就可以做它想做的任何事情，那就是写应用程序的人自己的事。我随便做一点什么，然后退出，同样得到一个 `xedit.log`。

有意思的是：这样的程序，虽然自己是图形界面的，它并不会一个像素一个像素地往屏幕上直接绘制——如果所有图形界面程序都这样绘制，屏幕就完全乱掉了。它是用发消息的方式。所以你看它绝大部分的系统调用都是 `poll` 之类的收消息、发消息：它告诉另一个有权限管理整个系统所有窗口的程序说，"你能不能在我负责的窗口上的某一个位置画一个什么东西？"或者反过来，它收到"我这个窗口的哪一个位置得到了一个点击"。这些都是相对的，所以我把这个窗口从一个地方拖到另外一个地方也完全没有问题，由底下那个渲染器去把它渲染到正确的位置。

> **结论**：所有程序的实现，今天都是一个——通过 system call。这也正是整个操作系统这门课这一学期要讲清楚的内容。

### 本讲提到的题目

**一、把最小程序的返回码改掉。** x86-64 版本的最小 Hello World 里，把 `exit` 那个系统调用参数中的常数改成 10，整个程序的返回编号会变成多少？

解析：`exit` 的第一个参数就是程序的返回值，而系统调用的参数是通过寄存器传给操作系统的。把汇编里那个常数从 1 改成 10，程序返回给外部的编号就是 10；不改就是 1。

**二、`gcc` 到底是自己完成了编译、汇编、链接，还是调用了外部工具？** 教科书上写着 `gcc` 要经过编译、链接这些过程，那么从实现上看，它是自己把这件事做完然后输出 `a.out`，还是调用外部进程来帮忙？

解析：两种实现方式都成立——完全可以自己实现一个编译器，在中间把所有的东西都在内存里准备好，最后直接输出 `a.out`。但现实中 `gcc` 走的是第二条路：用 `strace -f` 打开它的系统调用序列就能看到，它通过 `execve` 启动别的程序，一个路径一个路径地去找汇编器，找到就执行；还会创建临时的 `.o` 文件，用完之后再 `unlink` 掉。
