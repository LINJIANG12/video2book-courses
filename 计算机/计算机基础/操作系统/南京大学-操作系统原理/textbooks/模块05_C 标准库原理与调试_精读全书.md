### 系统调用已经够用，但生态不建在这上面

我们前面花了好多时间一直在讲操作系统，到底在讲什么？从一开始那个最小的、minimal 的、自己都没有办法退出的程序：只有一个函数叫 `_start`，在 `_start` 里写一个死循环，这个死循环可以无限地运行下去。我真的可以用 `ld`、`as` 这样一套工具链，把它最终变成一个 `a.out`，它真的能在操作系统上跑起来。就是这样一段汇编代码。

汇编代码里可以使用系统调用相关的指令，于是它就能访问操作系统、访问操作系统里的对象。所以我们讲了很多 system call：`fork`、`execve`、`exit`——做进程状态的复制，做进程状态的 reset，挑一个可执行文件去执行它，以及把一个进程的状态整个从世界上消灭掉。因为进程不管用 C 还是用汇编，都有指针和内存地址的概念，我们还用 `mmap`、`munmap`、`mprotect` 去改变进程的地址空间：原本不能访问的内存，我直接向操作系统申请，之后它就变成可以访问的内存。

除此之外，Unix 还给了我们访问操作系统里各种各样对象的能力。比如我的 fish 的 pid 是 6587，那我就能去看 `/proc/6587/maps`，看到一个进程实际的地址空间映射：从哪一个地址到哪一个地址，是什么。甚至还有一个文件叫 `mem`，`/proc/<pid>/mem`。它看起来是个文件——文件就是一个很大的字节序列，是一个操作系统的对象——但这个文件恰好就是这个进程的内存。所以我可以读内存、写内存，实现 hacking，实现一个游戏修改器，类似地也能实现一个调试器。

这也引出了为什么操作系统以前教起来一直很难，大家觉得里面琐碎的东西太多。比如前面有一节课我讲了 pts，也就是终端：4 号手册里有 pts，pseudoterminal 的 master、slave，你要创建一个新的 pseudoterminal、那个终端模拟器，它是怎么做的。这里有个很省事的办法：用 `man 4 pts` 这样的命令把手册全部打印到标准输出，然后按 Unix philosophy，以管道的形式把它完整地丢给 AI，让 AI 帮你读一遍。它读过以后，整份手册就在它的上下文里了。我先让它给我一个 summary，总结完以后就可以任意和它对话，因为手册和它输出的总结都在上下文里。接着我就可以问：我还是不太清楚 pseudoterminal 是怎么创建的，如果我想用这个功能实现一个 pseudoterminal，该怎么实现？给我一段伪代码也好、一段真实的代码也好。它是可以做到的，然后你可以从这里继续和它对话。

类似地，`man 5 proc` 里有很多有用的信息；7 号手册的 pipe 我也讲过——怎么创建一个匿名的管道，怎么腾挪文件描述符。管道里还有很多复杂的细节，比如读写者消失的时候，它可能会给持有另一端的进程发一个信号。这些都很难在上课的时候事无巨细地交代清楚。有兴趣的同学，也不是所有人都对 IPC 这种底层细节感兴趣，如果你们确实感兴趣，可以在 AI 的帮助下去读这些手册。刚才一闪而过的还有一个细节：管道里有个 non-blocking 的选项，可以让管道在没有数据的时候不在那里等待，用来实现其他类型的进程间通信。

我昨天准备这节课的时候，直接让 AI 给我 vibe code 了一个工具：它把所有的手册以树状的形式展现出来，然后我可以随便浏览、随便搜。我记得当时有 50000 多个手册。你也可以用现成的工具搜一些关键字——真的就是一行的 shell script 就能遍历所有的手册。这就是 AI 前时代和现在的区别：那时候你必须自己花时间把东西读完，而现在你只需要知道这个世界上有什么，然后能快速找到正确的方法，把想要的东西提取出来。

说到系统调用，我这里基本上讲完了。这三大类系统调用基本上就可以实现应用世界里面看到的所有东西。你想实现一个浏览器，也完全没有问题：你只要知道操作系统里应该有一个 API 能帮你画一个像素。比如 tty，你可以实现在 terminal 里面的浏览器，像 `links` 这些浏览器，你就可以在终端里上网。要写浏览器，无非就是用类似 `open` 这样的系统调用去打开一个网络远端的连接——当然，问 AI 它会告诉你，你需要一个 socket 才能得到和远端的连接。拿到远端连接以后，从远端拿到一个 HTML 网页，把它解析、渲染出来；剩下的都是普通的计算，像解析一个表达式、解析一个程序那样写一个 HTML 解释器，必要的时候向终端输出。所以理论上你已经可以用这些系统调用实现任何东西了。

但是，整个应用软件生态的世界，并不完全构建在这么底层的 API 之上。你们写 Python 的时候喜欢用 `pathlib`，也会用 C++。所以今天要讲的是：我们怎么在 C、或者说 Unix 这样一个非常小的 system call 核心之上，一层一层一层累出一个大家比较满意、开发者也比较舒适的生态。

> **结论**：这个生态的第一个入口就是 libc。底下程序如果是汇编，它第一可以执行指令，第二可以使用系统调用，而这两样东西都非常难用——想打印一个字符串，你得用 `write` 一个字符一个字符、或者一个 buffer 一个 buffer 地打，所有代码都手写的时候你会觉得很难受。所以你需要一个复用的机制，而这第一个复用的机制就是 libc。

### C 语言里与计算有关的那一半

在讲 libc 之前，先复习一下 C 编程语言，也就是我们的 Simple C。

我们说，可以把任何一个 C 语言的程序改写成一种简单的形式：如果有赋值，等号左边是一个变量，等号的右边是只有一个操作的式子——我总是可以这样写。`if`、循环也可以写得很简单。这样我们的 Simple C 基本上就可以直译成汇编语言。你看到一段 Simple C 的代码，可以直接把它翻译成——甚至用手写成——一段汇编指令，不管是 x86、ARM 还是 RISC-V。你只需要有跳转、寄存器的腾挪、`load`、`store` 这些指令，就可以完成这件事。像指针、数组、结构体、函数调用，都是对内存和寄存器的直接操作。

但这个 Simple C 只定义了 C 语言里面和计算相关的部分：load、store。这还不是 C 语言的完全体。

### 跨语言调用：FFI

> **定义**：所有的编程语言基本上都有这样一种能力，叫跨语言调用，叫 foreign function interface，FFI。它允许你在一种编程语言里，去访问用另一种语言写出来的代码。

打个比方，Python 里有一个叫 `mmap` 的模块，它真的就可以做内存映射；你 mmap 以后它给你一个像 handle 一样的东西，可以访问那个字节对象。那你就知道，它背后一定有一个 `mmap` 系统调用。但 Python 本身没有"系统调用"这个概念，它没有这样一个函数，你都是用 `pathlib` open 一个东西，或者用 `print` 打印一个东西。

而所有的编程语言在设计的时候，都会留出这样一个接口：允许你在适当的时候——一般来讲不会特别多——去访问一个用其他语言写的文件，比如一个二进制的、或者直接用汇编写的文件。像 Python，它的 CPython 是用 C 实现的，所以它很自然地可以和 C 语言互相调用：你可以在 Python 里调 C，也可以在 C 里调 Python。有兴趣的同学可以让 AI 回头写一段代码把这件事搞定。

对 C 来说，它作为一门比较底层、可以写任何东西的语言，就提供了和汇编、或者说和二进制代码连接的能力。这里面有两种方式。

#### 直接与汇编实现的函数链接

一种是可以直接和汇编实现的函数链接。因为本质上那就是一个符号：汇编里写一个函数就是一个符号，你可以写 `void foo`，声明说在另外一个地方有一个 `foo`，它有两个参数，一个 `int` 一个 `int`。然后你的汇编代码只要遵循 application binary interface——也就是计算机系统基础课上讲过的那套约定——就可以了。说好如果是 x86-64，我们的汇编代码就会认为 `x` 放在 `rdi` 寄存器里，`y` 放在 `rsi` 寄存器里，以此类推。这叫 calling convention。

汇编只要跳过来，就知道当前的栈上是什么样子：栈上会有一个返回地址，参数放在哪里，汇编就可以直接用指令去访问这些参数。

```text
    C 侧                  ABI 约定                    汇编侧
  foo(int x, int y)  --->  x 放 rdi             --->  从 rdi/rsi 取参数
                           y 放 rsi
                           栈顶是返回地址              执行完跳回调用点
```

这张图说的是：C 和汇编之间没有魔法，全靠 ABI 这一纸合同把参数放哪、返回地址在哪规定死，双方照着做就能互相调用。

所以 C 和汇编是可以互相调用的，有 ABI 规定好的调用规范。一旦 C 可以直接调用汇编实现的函数，那就可以调用系统调用了：像 `pipe`、像 `fork` 这些函数，背后最后可能都会落到一段汇编实现的代码上。

#### 内联汇编：把一段汇编塞进 C 的语法里

除了直接调用一段汇编代码，我们还可以用 inline assembly，内联汇编，来做 FFI。比如现在的 C 里，你可以定义一个 `register asm` 的变量，强制指定某个变量绑定到哪一个寄存器，编译器会帮你搞定这一点。以及你可以直接写一段汇编代码：比如这段代码在 x86 上，在 `_start` 以后就会执行，它把相应的系统调用号和 exit status 写到正确的寄存器里，然后执行一条 `syscall` 指令。在 x86-64 上，这段代码可以正确编译，并且正确地退出。

但因为是汇编，这段代码会原封不动地丢给汇编器。丢给汇编器就意味着，如果你在 ARM 上试图编译这段代码，它会直接告诉你编译错误——汇编器会拒绝你，找不到这条指令。

关于内联汇编，我还有一些很有意思的点评。最早我们在操作系统课上，是会硬让大家写一点点内联汇编的，那是一个非常非常痛苦的体验。你们看手册就知道了——我给大家准备了内联汇编的手册，很长，而且有很多看起来很奇怪的东西。内联汇编是一个 DSL，一个 domain-specific language。它为什么要这样设计呢？

首先，编译器尤其是最早的时候，设计者想省事：他还是希望你能够在 C 里面直接嵌一段汇编，这算是比较自然、比较正常的需求。然后他就说，好，那我就必须兼容 C 语言的语法，因为他不想把 C 语言的 parser 大改。我们不直接把汇编指令嵌在里面，而是希望这段代码看起来像一条合法的 C 语句。它确实像合法的 C 语句：汇编指令写在字符串里，写在字符串里就会按字符串去解释，这就是一个合法的字符串；中间它的括号也必须是配对的；你还可以在这里引用 lexical scope 里面的各种变量。

内联汇编本质上想做的事情是：这里有一段我写的指令序列，但这个指令序列又想和 lexical scope 里面的东西交互。打个比方，我在 C 里定义一个 `int x`、一个 `int y`，我想在这段指令序列里引用 `x`，有时候想把某一条指令的结果写到 `y` 里，最后还可以 `return y`。这是它设计时想要做到的事情，但为了做到这个设计，它付出了很大的代价。

你们想，如果要在 C 语言里、在一个字符串里引用一个别的东西，你怎么办？你就想到了 C 的 `printf` 那个 format string：想用 `%d` 打印一个 integer，想用 `%s` 打印一个 string，所以你也可以用 `%0`、`%1`、`%2` 来代表外面的东西。接下来你就得在后面写上它们的约束。这个语法设计得很随意。比如你要把汇编里的某个东西写到 C 的世界里，你就要写 `=r`，`r` 代表我希望把它丢到某个寄存器里，以任意的方式放进一个寄存器，然后写入 result；以及我会读里面的东西，比如读 `a`。`%0` 是第一个，`%1` 是第二个，你看起来就很难读，想半天也想不清楚。

这里面还有无穷多隐藏的细节。比如一个寄存器、一个变量又读又写：在这段指令序列里，你先把 `x` 的值读出来放到随便一个寄存器里，接下来又要把 `x` 的值写回去、还写回 `x` 里，应该怎么写？你是在这里写两份吗？正确的写法是把那个等号换成加号，写成 `+r`。所以你会觉得，他们都是拍脑袋：今天想加一个功能，就在这个语法上添一笔；再要加一个功能，再添一笔。

更麻烦的事情还在后面。我们的编译器会编译出非常优化的指令序列，这就意味着编译器可以随便用寄存器。你手上所有的寄存器，编译器某种意义上都可以用；它用了以后，因为所有代码都是编译器负责的，有些时候它也不需要回收、不需要把值恢复成原来的样子。这意味着我们的汇编代码里不能随便用寄存器。但有时候你确实又要用那些寄存器，比如 `syscall`：调一个系统调用的时候，在手册里——比如我这台 ARM64——系统调用的参数就是放在 `x0`、`x1`、`x2` 到 `x5` 这些寄存器里。也就是说，你想做一次 system call，就必须把 `x0` 到 `x5` 都写上值。

你当然可以在内联汇编里面写一段汇编，把这些值保存到内存里，等内联汇编调完了再把值恢复出来——但这又违背了编译优化的初衷。你的内联汇编理论上应该是可以和编译优化协同合作的：你可以指定我某一个东西要放在某个寄存器里，但这个寄存器可以由编译器来决定；你又可以说我这段代码破坏了 `x0` 到 `x5` 这几个寄存器，希望编译优化绕开它们，到你这儿的时候就不要用这些寄存器。你有很多需求。就是因为这些需求，它才变成大家看到的这样一个非常复杂的 DSL。

你马上就会知道，这玩意儿地球人肯定写不对。

#### 编译器不解析字符串里的语义

那些指令是以字符串的形式交给汇编器的。我们编译器对里面指令序列的行为是完全不负责的：编译器本身也不知道你这里面是什么指令集体系结构，也不知道这条指令到底是什么意思——甚至可能是你自己定义的一条指令，只要汇编器能认识就行。所以编译器完全不负责解析这里面的语义。

这就导致，如果你不小心漏掉了一个副作用——比如你明明把 `x5` 改掉了，却漏写了这个副作用——你就出大事了。因为你今天这个编译器编译的时候刚好没有用到 `x5`，你的程序就是对的；而且你怎么测都是对的，因为它生成的那段汇编代码确实是对的，它没有用 `x5`。但等到下一次编译器升级了，升级以后更 aggressive 地内联了、或者做了别的事情，那个 `x5` 被编译器用上了，用了以后又被你改写了，后面又被用到，你的程序就会非常奇怪地出现问题。

> **易错点**：内联汇编漏写副作用（破坏了某个寄存器却没说），在当次编译里可能完全测不出来；等到编译器版本或优化策略一变，同一个错误才换一副面孔冒出来。所以这类 bug 的共同特征是"换台机器、换个编译器就诡异复现"。

这样的问题不要笑，在 Linux kernel 里面也有。我们在 2019 年的时候做这个内联汇编的工作，结果手慢了，被别人先做了。当时我们看到那篇论文的摘要，上面写着 "we are the first to…"，我的心就在流血，因为我们没有做完。当然那位同学最后还是顺利博士毕业了，挺好的。我们开始做这个工作，是因为找到了很多很多 inline assembly 的 misuse，我本来想写一篇文章，就叫《Inline Assembly Demystified》。

但我突然发现，到了今天，我们的操统课上再也不用讲这个了。你们只需要知道，这个概念很重要：C 语言里面、或者说任何一个编程语言里面，都有一个叫 foreign function interface 的机制，允许你在一种编程语言里调用另外一种编程语言。而对 C 来说，你是可以在里面嵌入汇编代码的；这段汇编代码可以从它的上下文里读取数据、引用它上下文里的变量，也可以把上下文里的变量写回去。

它是一块"豆腐块"，也可以理解成一块钢板——这块钢板最终会经过一些预处理，比如 `%0`、`%1` 变成实际的寄存器名字，然后被丢到汇编器里，一个字符一个字符原样粘贴进去。你一旦建立了这个正确的概念，所有 tedious 的细节对你来说都不重要了。因为只要有足够的示例，AI 就能学得会；你甚至让它去做强化学习、self-play，它自己也能学得会。学会以后，你只要告诉它你想干什么，它就能干到。

#### 内联汇编真正派上用场的地方

打个比方，内联汇编在什么时候有用？当你需要做极致优化的时候。你有一段程序，比如要做一个矩阵的乘法，或者求两个向量的点积。向量点积，你们在 Online Judge 上做题会这么写：

```c
sum = 0;
for (i = 0; i < n; i++)
    sum = sum + a[i] * b[i];
```

这段代码在优化的编译器上其实会被优化得比较好。但不是所有的代码都能被优化得那么好，这时候你就可以和 AI 对话，让它在适当的时候把你的代码写成一段非常优化的代码——尤其是可以针对你那台机器，如果你的机器刚好有某一个指令集的话。所以只要知道这件事情可以做，就可以了。

### C 的完全体

那么这就是 C 的完全体了：它有指针、数组、结构体、函数调用这些最基本的语言成分，也就是一个 Simple C；Simple C 再加上一个 foreign function interface，就可以实现世界上所有的东西。我可以调用一个系统调用；当我可以使用系统调用以后，你在应用世界看到的所有东西都是可以实现的。

> **结论**：Simple C 负责"算"，FFI 负责"连"，两者合起来就是 C 的完全体。

所以就有了我们一层一层、像洋葱一样的整个应用生态世界。这和计算机系统发展的历史也很像。

1950 年代的时候就只有汇编语言，所有人被迫用汇编语言、或者说用戳孔的方式写代码。到了 1970 年代，你用汇编语言编程就是行为艺术了，是没有必要的，可能只有少量那种和机器相关的代码才需要用汇编；绝大部分代码，在那个时候 C、Pascal 都开始普及了。有一个叫结构化程序设计的东西，你们可能听说过——我觉得在今天 AI 的时代，结构化程序设计又重新——不能叫死灰复燃，应该叫复活了。它告诉我们，设计一个软件要先把它分成比较抽象的几部分，然后再逐渐 refine、refine、refine，而这特别适合 vibe coding。1970 年代也有了 UNIX，也有了 C 语言，所以在那个时候 C 语言是一个非常重要的生态入口：你只要用 C 语言写代码，就可以在 UNIX 上运行，这是一个非常好的特性。

到了 2010 年代又有意思了，C 语言又变成"古法编程"了：只有在学 computer science 的人才用，就像只有学汽修的人才去学那些东西，开汽车的人再也不知道汽车是怎么构造的。虽然 C 语言在 2010 年代还是一个相当好用的编程语言、经久不衰，但在 C 的上面已经长出了 Python；C 上长出 C++，在 C++ 上长出 Java、JavaScript，C 上又长出 Python。语言长啊长，更多的程序员就不需要再用那么底层的方式编程了。到今天，用高级语言编程都已经成为行为艺术，大家都调侃自己每天在做古法手工编程，是非遗技能。今天我们绝大部分时候都用自然语言来编程。

但我们不要忘记：我们今天能做自然语言编程，是因为 C 语言给我们构建了一个一层一层的世界。你看，我们有一个 assembly，有 foreign function interface，有一个 Simple C 的模型，而就是这样一个非常非常小的模型，它已经被标准化了。

```text
   自然语言编程 / Python / JavaScript / Android …
                    ^
        C++ / Java / 各类运行时生态
                    ^
      libc（C 标准库）        POSIX
                    ^
   Simple C（指针/数组/结构体/函数调用）
          +  Foreign Function Interface
                    ^
        汇编 / 系统调用指令
                    ^
                操作系统
```

从下往上读这张图：越往底层越靠近机器，越往上越靠近我们今天写代码的方式；C、libc 和 POSIX 这三层，是支撑上面所有东西的底座。

### 标准：ISO C 与 POSIX

C 语言是有标准的，有 ISO/IEC 的标准。它告诉你 Simple C 的语法、语义，以及不仅是 Simple C、还有更复杂的 C。在这个上面还有 libc，还有 POSIX，也就是 Portable System Interface。这些就是那个世界的底座，底座上面又长出了 Python、JavaScript 各种各样的东西，以及上面所有的比如 Android 这些生态、Java，Java 上面还有 Android。

我们的 C 世界是有 ISO 标准的。这意味着什么呢？一旦有了标准，大家都会倾向于努力去遵守这个标准；而且这个标准的制定也不是为了为难你，是为了让大家能够在一个共同的体系下说话。而这个稳定可靠的标准，你就不用担心升级版本会破坏你的实现。

如果你用 JavaScript、Python，你今天开发一个东西很爽，等到明天它的 dependency 就 break 了；当你迁移到新的 dependency 的时候，你的程序可能就跑不起来了，然后你还得让 AI 给你修，修成了什么样你自己也不知道。你的软件其实处于一种失控的状态——能用，但又失控。但 C 不是。

C 代表了这个传统世界非常经典的一层一层抽象的最低端，你有世界上最好的一致性。比如如果你只用 C 里面最小的那一些部分，那么你的程序写一份，比如说你写一个 breadth-first search 算法，或者写一个甚至一个图形界面库——你可以从一个数据结构出发去渲染出一个图形界面，当然可能你是像素级的渲染，最后你需要一个什么样的后端——但如果它用 C 语言写，它就有世界上最好的一致性：从你的电脑、超级计算机，到手表、手环，到那个非常非常小、只有 1KB 内存的设备，它都可以运行。

前提是你用符合这个 ISO C 的方式、以一个 portable 的方式去写程序。比如你不会假设一个 `int` 是几个字节——一个 `int` 实际上在有些小型的机器上可能是两个字节、16 个 bit；当然在今天的机器上，不管是 32 位还是 64 位，它都是四个字节、32 bit。C 的标准为了移植性规定了很多东西。

在 C 的上面还有 POSIX。比如你的 `unistd.h` 里面有 `fork`、`pipe` 这些函数，它们的行为都是 POSIX 标准所规定的。几乎所有能用的操作系统——比如 Linux、我的 Mac、你们的鸿蒙 OpenHarmony（我不知道有没有同学用不太好用的华为手机，生态上稍微差一些）——但是你看到的所有这些系统基本上都兼容。首先它必须要有 C 编译器，因为有了 C 编译器就意味着它可以编译别人写的东西，而且别人写的东西几乎不用修改，就可以在它的系统上面完整地运行起来。然后它自己再给一个 POSIX 层，像 `pipe`、`execve` 这些函数；有了这些函数，它就可以跑一些应用程序，不管是服务类的，还是像 coreutils 里面那些核心的命令行工具。

我上课的时候讲过一个叫 BusyBox 的小工具集。在 Android 和你们的鸿蒙系统上，包括 HarmonyOS 上，都有一个 toybox，一个小小的命令行工具集，它就是在 C 和 POSIX 这个接口上实现的。所以基本上，你可以在世界上任何一个还有一定复杂性的设备上找到 C 的身影，即便你可能不是直接用 C 来编程。

### 让 AI 写 libc，还是去读一个 libc

我去年的时候干了一件事：我想有没有可能让 AI 帮我生成一个 standard C library 呢？成功了，但没有完全成功。去年还是 Sonnet 3.7 的时候，各种翻车：它实现了一个东西，但那个东西各种不能用，包括栈的对齐也不对，我需要手工去 fix 它。在那个时候我觉得自己可能还有点用，我好像还有一些知识。结果到 2026 年，我觉得小丑就是我自己：大号的模型在实现一个完整的教学级 libc 上完全没有问题；它哪怕偶尔有地方做错了，运行一下，看到那个 error message，很快也能修复。

但是，我觉得我们还是有必要去学习一些已有的 libc 实现。你们想到的是系统里面会有一个默认的 libc，也就是 glibc。你可以在网上下载到一份 glibc 的所有调试符号，于是你就可以真的在自己的机器上调试 glibc 的每一行代码。以前我上操作系统课的变态版本的时候，真的会有一些函数，比如锁、互斥锁，我真的会到 glibc 里面去调一下。但今天你们完全没有必要——虽然可以，但没有必要，因为 glibc 的代码有非常沉重的历史包袱。就像我刚才说的内联汇编：每当有一个新的需求来的时候，开发者就打一个补丁；每当一个指令集有什么新的东西，开发者就想把它用进来，说这样也许能提升软件的性能。最后就导致代码库的膨胀、维护的困难，以及新手阅读体验的变差。

> **提示**：基本原则就是你总会有办法的，只要问就行了。你问 AI "有没有比 glibc 更适合学习的 libc 实现"，它就知道——它会提到 musl，还会提到 Bionic，那些许可证更友好的 libc。

我给大家准备了一份 musl-libc 的代码。你只要看到大模型给你的提示，就可以去网站上把 `musl-1.2.6.tar.gz` 直接下载下来。如果你不会解压缩也不要紧。以前我上操作系统课的时候都会有一个梗，说大家有用过 `tar` 这个命令吗？`tar` 的命令行参数因为它太古老了，甚至都不完全符合 UNIX、POSIX 后来标准规定的那种参数风格。比如所有的参数都应该是 `-` 开头，你可以 `-p`、`-x` 什么；它是直接写在那儿的，你要干什么由一个参数写在这儿，然后你可以选一个文件把它解压缩。有一个笑话说：你现在有一颗核弹，10 秒钟之后就要爆炸，你需要输入一个合法的 `tar` 命令把一个文件解压缩，否则核弹就会爆炸——大概没有人能写对一个这样的 `tar` 命令。

但今天这都不是问题了。你只要把它解开，就可以得到一个目录。我准备的时候因为稍微比较花时间，所以没有再自己做一次，直接在 Claude Code、而且是豆包的模型里说：你能不能帮我把这个项目编译了，并且帮我生成调试信息？也就是说，我希望它编译一个能调试的 musl libc。这个 libc 就是我上课讲的，C 语言里面除了语法语义之外它所有的运行时库。

### 打开 musl：一个真正的 libc 长什么样

你可以看到，这是一个真正的 libc。比如 `ctype.h`——它真的是把 C 的函数直接定义在这里的。你们熟悉的有没有 `stdio.h`？如果我想看 `stdio.h`，真的就直接写在这儿。而且 musl libc 是一个比较现代、维护得比较工整的实现：它不像 glibc 那样背着包袱，它想把这些包袱都扔掉，基于 Linux 的 API 实现，而不是古老的 POSIX API。

它这里的宏定义，你看就容易多了。你的 `fseek`、`lseek` 需要三个宏：你要选择你的文件打开以后，那个游标是从头开始走，还是从尾巴开始走，还是从现在的位置开始走——那就是 `SEEK_SET`、`SEEK_CUR` 和 `SEEK_END`，它们就是三个宏，就是这样定义出来的。计算机世界里没有魔法。你的 `BUFSIZ`，它的 buffer 的大小，你的文件名长度是 4096，全部都是直接这样定义出来的。就像你看 `fopen`、`freopen`、`fclose`，无非也就是你们在 C 编程课上面学过的东西。

我让它把这份代码编译了，编译完以后就可以得到一个能用的 `musl-gcc`：一个专门用这个 libc 来编译的命令行工具，用来编译我用来展示 libc 功能的那些小程序——比如一个 `int main` 然后 `return 1` 的程序。Makefile 用的是 `musl-gcc`，`CFLAGS` 里有 `-g3`，我要带上调试信息，而且要以静态的方式编译。这样就得到了一份静态编译的代码，看起来还是比较多，但是它比 glibc 编译出来的东西要少不少，而且它带有调试信息，一会儿我们就能看到它的源代码，也可以调试它。这就是今天要讲的 libc 里面的所有程序。接下来我们会走过 libc 里面各种各样的封装。

### 哪些库不需要操作系统：hosted 与 freestanding

首先，`int` 类型和你的机器字长是相关的。或者 `long` 这个类型：在 32 位机上 `long` 是 4 个字节，在 64 位机上 `long` 是 8 个字节。如果你要定义像 `int64_t` 这样的东西，C 里是允许的；还有 `int32_t`，以及 `intptr_t` 这些重要的、和机器相关的定义。再比如 `float`，不同的机器对浮点数的实现也是不一样的；再比如 `limits`，它可以告诉你各种整数的范围。

这些库全都可以在不使用任何系统调用的情况下使用。这类环境在 C 里就叫 freestanding。

| 环境 | 依赖什么 | 典型例子 |
| :--- | :--- | :--- |
| hosted（有宿主） | 通过 FFI 落到汇编、再落到操作系统，没有操作系统就跑不起来 | 执行一次 `fopen` 要先持有文件描述符，就必须走 `open` 系统调用 |
| freestanding（独立） | 不需要操作系统 | 只用内联汇编发一条指令直接访问硬件，用 C 写操作系统内核 |

看手册就更清楚了。我这里翻的是 cppreference；我觉得它里面讲 C 的部分比较齐全，你们有兴趣课后也可以看。这里讲的不仅是 C，C 和 C++ 这部分一定程度上是共享的。

> **定义**：你们的程序有两种模式。hosted 就是"有宿主"：它实际上有很多 FFI，有点像对汇编的调用，然后这些汇编会再调到操作系统，所以它必须依赖操作系统才能运行。freestanding 就是"独立"：C 语言是可以用来实现操作系统的，如果我只用内联汇编去发一条指令、直接访问硬件，那我就可以用 C 语言开发一个操作系统内核，这时程序不需要操作系统也能跑。

### 打印一个整数有多难：inttypes 与那些宏

比如这里有 `inttypes.h`。打个比方，你现在想要用 `printf` 来打印一个 64 位整数，你马上就会发现这件事情是做不到的。或者说你打印一个 32 位整数，你到底应该用 `%d` 还是 `%ld` 呢？`%d` 可以用来打印 `int`，`%ld` 可以用来打印 `long`。但这个是随着你的机器变化的：你换到一台 32 位机上，这个 `long` 就是 4 个字节；你换到 64 位机上，`long` 就是 8 个字节。所以如果你想要打印一个 `int32_t`，你到底应该用什么样的格式字符串来打印呢？这些就是在 freestanding 的环境里、或者在你需要兼容性的时候所需要的宏，答案就在 `stdint`、`inttypes` 里面。

比如有一个 PRId 系列的 macro：`PRId32`，还有 `PRIu64`、`PRIx` 等等。运行它，你就能把正确的类型打印出来。我也可以用 `gcc -E`、或者 `musl-gcc -E inttypes.c` 把它们展开来看：比如 `uint64_t` 那一行，宏展开以前是 `uint64_t: ` 加一个宏、再加一个宏、然后一个 `
`；展开以后就变成了字符串的拼接。

在 C 里面，包括在 Python 里面，你都可以直接把两个字符串写在一起，它会帮你把字符串常量做拼接。所以你可以看到，编程语言里面的各种机制都是环环相扣的：预编译允许在 C 里写两个相邻字符串的写法，这个写法在很多地方都真正用得上，你就可以写出这样的代码。

> **易错点**：`%d` 对应 `int`、`%ld` 对应 `long`，而 `long` 的宽度是随机器的——32 位上 4 字节、64 位上 8 字节。所以"打印一个定宽整数该用什么格式串"不能凭习惯猜，得用 `PRId32` 这类宏把类型和格式串绑在一起。

### offsetof：从地址零处"长"出一个结构体

在 freestanding 的环境里，还有很多很多这样的功能。比如还有一个很有趣的 `offsetof`。如果你们回去看手册的话——今天我就不带大家看手册了——看 `offsetof`，它可以告诉你一个结构体的某一个 member 相比于结构体头部的 offset。

比如你写一个 `struct foo`，里面有 `int x`、`int y`，你想知道 `y` 在结构体里排在哪儿，它会按照从左到右的顺序排列这些 members。如果你想要知道 `y` 相比于这个对象头部的地址，你可以用 C 语言实现它：把任何一个地址——比如说 0——cast 成 `struct foo *`，就好像在 0 这个位置有一个 `struct foo`，然后你就可以得到它的 member 的地址；而这个地址本身，就是那个成员相对于结构体头部的偏移量。这就是 `offsetof` 干的事情。

## 从 freestanding 的怪宏到 C runtime
> 对应块：BLK18 | 覆盖分集：P09下 | 块标题（分集名）：《C 标准库原理（下）》

你甚至可以试着去引用一个成员的地址，然后拿这个引用本身算出它相对于对象头的 offset。做法是：把 0 号地址当作一个对象，去引用它的成员，再把这个成员地址取出来、转换成整数。注意，**这个指针只是被挪了一下，并不会真的被解引用**；因为 0 的位置上放着一个对象，所以成员地址的数值本身，就是它离对象头有多远。编译器也许有某些 builtin 的方式能更好地实现它，但这个操作在 C 语言里是完全合法的。

libc 里像这样有意思的宏还有很多。我像你们这么大的时候，就喜欢课后翻这些稀奇古怪的东西；有些记住了，有些记不住，但久而久之，就有了一些概念上的积淀。

### 变参数与那些随手能写的标准函数

freestanding 环境提供的各种库函数里，还有一个非常特别的头文件，用来处理变参数。写 `printf` 的时候，我实际上可以写任意多个参数，一个、两个……一直到七八个都行。问题是：这个机制是怎么实现的？

#### 变参数：32 位靠栈，现代靠寄存器

在 32 位机器上这件事比较简单。32 位的 calling convention 是把所有参数都往栈里压——你要调用一个函数，就把所有参数放到栈上，于是栈上就会出现一个数组：这是第一个参数，这是第二个参数，一直排下去。所以在 x86 上你只需要给第一个参数取一个指针、取一个地址就够了。假设声明是

```c
int printf(const char *fmt, ...);
```

那么只要 `fmt` 的类型是正确的，把第一个参数的地址取出来，就能顺着这段内存往后走。

但在现代体系结构上，这个 hack 不管用。原因很清楚：参数大部分是由寄存器传递的（`rdi`、`rsi`……），所有参数都不在内存里，你根本取不到一个"参数数组"的地址。这时候就要由标准库和编译器协作，在变参数的情况下生成正确的汇编代码，把需要的东西放到内存里，我们才能用 `va_list`、`va_arg` 这一套宏去正确地访问多个参数。

#### rand、atoi 与 memcpy 这些基本功

除了这些机制性的东西，freestanding 环境上还很容易随手实现一些可以当练习的函数，比如 `memcpy`、`memmove`、`strcpy`——我想这都是你们刚开始学 C 或者 C++ 的时候想做过的习题，用循环就能实现。

`rand` 是个更有意思的例子：**它其实并不随机**。C 的 `rand` 需要你先给一个 seed；如果你给的 seed 相同，那么每一次运行程序生成的随机数序列又完全是相同的。

> **定义**：这种"同样输入必得同样输出"的东西，完全就是一个数学上的函数，也就是伪随机数生成器（pseudorandom generator）。

再比如 `atoi`，可以把整数和字符串互相转换。

#### qsort：谁用谁知道

有没有人用过 C 语言的 `qsort`？谁用谁知道，一点也不好用。看它那个函数的参数就明白了——这纯粹是在难为 C 语言。C 语言是一门"高级的汇编语言"，如果你写真正的程序要做 quicksort，一般而言你会自己做一个结构体：

```c
struct element {
    /* 你想要比较的数据 */
    int (*compare)(const void *, const void *);
};
```

元素里带上一个 compare 函数，这样你想要什么东西都可以往里加，总是能写出很好的代码。但 C 语言提供给我们的语法机制很有限，它要想在标准库里实现一个**通用**的 quicksort，那就只能干成那样。所以 `qsort` 你几乎不会用——不是说绝对用不起来，但最后写出来的代码可读性会比 C++ 差一点，比 Python 就更差一点。

#### 数学库水很深

数学库（`math`）里的东西，像 `sin`、`cos` 这些，你其实也都是可以自己实现的。但数学库的水也很深，里面藏着一个奇怪的问题：**存在一个数，它既不满足 a 大于 a，也不满足 a 小于 a，也不满足 a 等于 a**——这世界上存在这样的数吗？

在整数域和一切能够合法表示的数域里肯定不存在：一个 IEEE 754 能合法表示的浮点数，就应该自己等于自己，1 就等于 1，2 就等于 2。那什么东西自己不等于自己呢？数学里专门有一个 "Not a Number"。

> **提示**：NaN 与任何数的比较——包括与它自己比较——结果都是"不成立"。所以写浮点比较时，`x != x` 反而是判断 NaN 的常用写法。

可以定义三个变量 x、y、z，把它们打印出来，再逐个比较一遍，运行一下就能确认：它对一切比较都说"不"。整个浮点数和整个数学，都是一个非常大的坑。

### setjmp 与 longjmp：一次跨栈的跳跃

在指令集与计算的封装上，还有一个非常特殊的函数，我要着重讲一讲。先回忆一下 Simple-C 的计算模型：我们有一个 stack frame 的栈，最底下是 `main` 的调用，然后可以调用 `f1`、`f2`，随便怎么调用；每一个栈帧上都有它自己的 PC，也就是"当前执行到哪里"；所谓的函数调用，就是在这上面再放一个新的栈帧，所谓的函数返回，就是把最上面那个栈帧 pop 出来；每执行任何一条语句，都是从这个 top frame 的 PC 取一条语句，走到它的下一个状态。

`setjmp` 和 `longjmp` 就在这个模型上做了一个非常有趣的 hack。

#### setjmp 记下的是栈深与 PC

`setjmp` 允许你放一个 buffer（它完全可以是一个全局变量）。执行一条 `setjmp` 时，它会在 buffer 里记住当前栈帧栈的高度——比如高度 h 等于 3——以及当前的 PC。执行完 `setjmp` 之后，`setjmp` 正常返回，我就接着往后执行随便什么代码，好像什么都没发生过；但它已经悄悄把栈的深度记下来了。

在计算的意义上记住"栈有多深"是可以办到的，但在纯粹的 C 里面其实办不到：你无法知道底下到底有多少层函数调用。实际操作上它也并不需要真的去数，**只要有一个指针，指向那个栈帧的位置就可以了**。

然后你的程序可以任意地往后执行，调用 100 个函数、10000 个函数都行。可是当你有一天执行 `longjmp`，把那个 buffer 拿出来用的时候，它会一下子把栈上不管几百层、几千层的东西全部弹掉。

#### longjmp 就是一个大号 goto

这个行为像什么？像一个**大号的 goto**。

C 里的 `goto` 可以在函数内随便跳转：哪怕是在一个循环里、在一个分支里，我都可以 `goto` 到外面去。这也是 C 语言里一个非常经典的好用法。设想你的这个 C 函数很大，里面有分支、有循环，而在循环和分支里都可能申请内存、申请别的资源。如果你在 `for` 循环里面不小心 `return` 了，这份资源就漏了、忘记释放了——你们每个人都干过这样的事，C 和 C++ 太容易犯这种错误了。所以 C 里面有一种非常 idiomatic 的写法：要出去了就 `goto out`，或者 `goto release`，然后在 `release` 那里检查你所有可能申请资源的点，把它们逐个释放掉。这看起来不是效率最高的写法，因为你可能会做一些额外的、不必要的检查，但它比较安全。

`setjmp` 就相当于把 label 写进了 buffer，而且这个 label 还额外包含了当前栈的深度；`longjmp` 则是那个大号的 goto——不管你在中间积累了多少层栈帧，一执行 `longjmp`，就回到记下来的那个位置、回到记下来的那个 PC。

这个函数非常有用，我们会在有一个实验里让你们用它来实现**协程**。它甚至不需要任何系统调用，只要编译器配合生成正确的指令序列就可以。

#### 演示：三层栈帧怎样被一次弹掉

我这里有一个小的演示程序。它会先执行 `setjmp`；如果返回值等于 0，就继续往后执行 `first`，执行完 `first` 再执行 `second`。这时候我的函数调用已经一层一层累积起来了，而在 `second` 里面会执行 `longjmp`，于是它就会跳回刚才 `setjmp` 的地方，跳回 `main`。

```text
   setjmp 时             走完 first、second 之后        longjmp 之后

   +-------------+       +-------------+               +-------------+
   |             |       |   second    |               |             |
   +-------------+       +-------------+               +-------------+
   |             |       |    first    |               |             |
   +-------------+       +-------------+               +-------------+
   |    main     |       |    main     |               |    main     |
   +-------------+       +-------------+               +-------------+
```

读图说明：左边是执行 `setjmp` 的那一刻，栈上只有 `main`；中间是继续走过 `first`、`second` 之后，栈帧一层层压了上来；右边是执行 `longjmp` 之后，中间那些更深的栈帧被一次性弹掉，只剩下 `main`，而它的 PC 已经被改写成 `setjmp` 那里记下的位置。

调试一遍就能看到这三步都是真的。第一次 `setjmp` 如期返回 0，程序就好像什么也没做过一样继续往后执行，打印出 `setjmp return 0`；然后进到 `first`，打印；再进到 `second`。这个时候如果看函数调用栈，我在 `second` 里，`second` 上面是 `first`，再上面是 `main`，整整三层的函数调用栈。但直接 next 一下，`longjmp` 就跳回来了。

这个特性可以用一个很好懂的比喻记住：我先在宿舍里 `setjmp` 一下，然后今天去教学楼上课，上完课去逸夫楼上课，上完课再去食堂吃饭；吃完饭直接一个 `longjmp`，我就回到宿舍了。不管这段时间里你干了什么，`longjmp` 直接就把这段历史全部清掉，回到刚才那个位置——当然，你可以带一个 return value 回来，这个值会作为 `setjmp` 的返回值返回到 `main`。

顺便说一句，实际实现的时候它还会保存一些寄存器，使它能够和编译器一起正确地跳转回来。这个细节大家不需要知道，你只需要知道：我确实是可以通过一个 `longjmp` 跳回来的。

### stdio 是文件描述符的封装

除了这些 freestanding 里都能用的、对指令集体系结构和计算的封装以外，libc 的一个很重要的功能就是**封装文件描述符**。

#### struct FILE 里有什么

在我们的 `struct FILE` 里面，其实是包含了一个文件描述符的。所以你会看到，C 语言里 stdio 的这些 API 和 Unix 文件操作的 API 之间，几乎有一个一一对应的关系：

| stdio 里的 API | 对应的文件描述符操作 |
| :--- | :--- |
| `fopen` | `open`（前者返回 `FILE *`，后者返回一个文件描述符） |
| `fread` | `read` |
| `fseek` | `lseek` |
| `ftell` | `lseek`（取当前位置也可以用 `lseek` 实现） |

除此之外还有 `feof` 之类，它们其实都对应着那个文件描述符的状态。只要你持有那个文件描述符，就可以对它做 `lseek` 这样的操作，等等。

真正去看实现，musl libc 里面 `struct FILE` 的实现比 glibc 干净得多，你们自己就可以看懂。里面最重要的两个是 `fd` 和 `pipe_pid`：它包含了一个文件描述符，甚至还有一个和管道相关的 pid，这些都是和操作系统相关的。通过这两个整数，我们就可以访问到操作系统里面的对象。

绝大多数别的东西都是纯 libc 自己的事。比如里面有一个 `buffer` 指针——你知道 stdio 是可以带缓冲的，缓冲区就是这个指针指向的东西。以及它用了 C 语言里实现出来的"面向对象"：里面有几个函数指针，一个 `read`、一个 `write`、一个 `seek`、一个 `close`，就跟我前面说的、要在自己的项目里定义一个 `struct element` 并且让它支持比较时会用的方式一样。

这样一来，一个 IOFILE 就可以对应到多个不同的后端实现：可能是一个操作系统里的文件，也可能就是一个 buffer——比如 `sprintf` 的时候你是往一个 buffer 里打印的，那就可以相应地为一个字符串缓冲区实现一个对应的 `struct FILE`，你只要把 `close`、`read`、`write`、`seek` 这几个函数相应地实现好就行。

既然 `struct FILE` 里面有一个文件描述符，那么我们基本上就可以把 libc 里的 `fopen`、`fread` 这些全部转译成对那个文件描述符的系统调用。

#### printf 家族只有一份实现

如果大家对底层的库函数有兴趣，真的可以自己去编译一份带调试信息的 musl libc，然后用 gdb 去调试它。调完以后你会发现，`vfprintf` 真的就和你们脑子里构想的一样：你会实现一个小的 parser，拿到一个 format string，里面有什么 `%d`、`%s`，然后从左到右遍历这个 format string，解析出你要打印的东西，再把它路由到相应的处理函数——`%d` 的函数、`%s` 的函数——最后都是往 `FILE` 里面写。

你还会看到 `printf` 是一级一级调到 f 的：`printf` 实际上就是 `fprintf` 一个 `stdout`。它用到了 `stdarg.h` 里的 `va_list`——这个参数列表本质上就是一段内存，可以从第一个参数一个一个往后走；这个对象在调用过程中不停地被传递下去。里面就是一个死循环，外加一个不停往后走的 parser。如果你去调试它，会学到很多 C 语言该怎么写。虽然我觉得现在再去学"C 语言该怎么写"也不是那么必要了，但你至少可以看到一些有趣的设计。

更值得学的是它的结构：`printf`、`sprintf`、`fprintf` 这一族是**没有 code clone** 的。真正负责打印的只有一份代码，就是那个 printf core。

> **结论**：把功能收敛到一份实现里，代码重复变少了，项目的维护就会容易得多。

### 进程的退出与协同

libc 里面还封装了很多和进程管理相关的功能，包括 `abort`、`exit` 和 `atexit`。

#### atexit：正常退出时帮我收尾

用 `atexit` 可以注册一个 exit handler。也就是说，我希望程序在**正常退出**的时候，还能再调用一个我自己的函数。

设想你的 C 程序创建了一个临时文件。你们做 Online Judge 做得多了，会习惯性地认为所有资源都是只管分配、不管回收的——因为当你点击提交按钮以后，什么事情都不是你的了，Online Judge 会负责回收一切。但在实际的系统中其实不完全是这样的：你不管在哪里创建一个临时文件，如果它真的不再用了，你最好还是把它删掉，哪怕你是在 `/tmp` 目录底下。

你这样想：如果你每次都会创建一个很大的临时文件，而你这个工具又会被调用很多很多次，你用着用着不就把它的存储空间给占满了？`/tmp` 的空间是有限的。你把它占满了以后，管理员在执行别的东西时就没空间了，他一看：产生了这么多、不必要的临时文件。

`atexit` 就是帮你干这件事的——当然是在正常退出的时候。如果异常退出，偶尔留一两个，那他也就选择忍一忍；或者足够老的文件会被（清理机制）删掉。

#### abort 与 core dump 的来历

进程管理里面还有一个退出方法叫 `abort`。`abort` 的行为是给自己发送 `SIGABRT`。因为它其实是发一个信号，就像 `SIGINT` 一样：上次说 Ctrl+C 的时候，我们的终端会给前台进程组里面的每一个进程都发一个 `SIGINT`。

这个信号会触发一次 core dump。

> **易错点**：`assert` 失败的时候，`assert` 终止调用的**不是** `exit`，它并不是替你调用了一个 `exit 1` 来告诉你出错了。`assert` 调用的是 `abort`。

也正因为如此，`assert` 失败时你看到的退出状态是一百多，在补码的意义上是一个负数：它是 134，也就是 $128 + 6$，其中 6 正是 `SIGABRT` 的信号编号。

如果你配置了 core dump 的 size，那么这里就会产生一个叫**核心转储文件**的东西：它会把进程的内存 dump 下来，这样你还可以用调试器去调试它。

`core dump` 这个词是怎么来的呢？它来自以前的 core memory，也就是早期的那种磁芯内存——你可以用一个磁铁的方向来表示 0 或者 1。而你需要把 core memory 的状态转储到另外一个永久的存储器上，所以这就叫 core dump。现在这个词就用来指"把进程内存放到一个文件里面去"的过程。

#### system 与 popen

libc 也提供了非常有限的、和其他进程协同的功能。`system` 大概是你们用得最多、也是最好用的一个。

举个人人都碰得到的例子：你的程序想要清屏。你们学过，用一个正确的 ANSI escape code 就可以清除屏幕；当然现在你也可以直接让 AI 帮忙——在 Cursor 里把光标停在那儿，让它在这儿做一件什么事，它马上就能帮你写了。但手边真的没有 AI 的时候，直接 `system("clear")` 也行。你只要知道用 `sprintf` 拼出一个什么样的命令字符串，然后把它执行掉，还是挺方便的。

`system` 的背后会启动一个 shell，在 shell 里面执行你的命令。所以它相对来说会重一些，但确实比较好用。

另外还可以 `popen` 和 `pclose`，它们返回一个 `FILE *`。这两个函数属于标准库（standard C library）的手册部分。它有一个缺点：**是单向的**，你只有一个方向能写、一个方向能读。这不像你们在 Python 里用 `subprocess.Popen`，两端可以互相读写，两个程序可以互相读写。C 的这个管道是单向的，因为你的 `pipe` 可以返回两个文件描述符，但 C 语言的 `FILE *` 里面只有一个文件描述符；如果它也要返回两个 `FILE *` 的话，这个 API 就会难看得不成样子。最终 API 的设计者选择了一个妥协——我觉得这是一个比较糟糕的、带着历史包袱的妥协。

> **提示**：单向管道虽然憋屈，但大部分时候也挺有用。如果你要调用另外一个程序、并且把它的结果拿回来，`popen` 会比 `system` 更好用——因为用 `system` 你根本没有办法控制它的输出。

### 出错之后：errno 与 perror

#### 每个系统调用都有自己的 ERRORS

所有的系统调用被封装以后，都会返回错误。你们有没有留意过：每一个系统调用 API 的手册里，都有一节叫 ERRORS，它会告诉你这个系统调用到底为什么会出错。

比如看返回值：`fork` 成功的时候，如果是父进程，它会返回子进程的 PID；如果是子进程，它会返回 0。还有一种情况，它会返回 -1，-1 就代表失败了。但是 -1 的失败有很多种可能性。`fork` 的失败可能相对还比较少：比如 `EAGAIN`，它说你现在的资源暂时可能不行，下一次可以再试一次；再比如 `ENOMEM`，比如你确实在 fork bomb 的时候，它会返回这个。

很多系统调用都可能**暂时性失败**，也就是现在失败了、过一会儿可能就会成功，这时它就会返回一个 `EAGAIN`。如果我们换一个别的调用来看，比如 `open`，到 `open` 的手册里去找 ERRORS，那可能的错误就多了，有那么多种错误情况，而且每一个都有一个编号。

| 错误号 | 什么时候出现 |
| :--- | :--- |
| `EAGAIN` | 暂时不行，下一次再试一次也许就可以了 |
| `ENOMEM` | 确实没有内存了，比如 fork bomb |
| `EACCES` | the requested access to the file is not allowed, or permission is denied，权限被拒绝 |
| `EEXIST` | 路径已经存在，而你又用了 `O_CREAT` |

每一个系统调用的错误，在 libc 里面也都必须要得到非常好的处理。这和你们写程序时的假设不一样：你们做 OJ 遇到的一个问题，就是它从来不让你们处理错误——因为错误是 OJ 的事，OJ 会告诉你"你错了"，而你的程序 100% 都必须是对的。但在实际中，这种情况是不可避免的：用户的输入是错的，我 `gcc` 一个不存在的程序，它就必须要给我一个好的错误提示。

#### 同一个 ls，两套错误信息

比如 `ls` 一个不存在的文件，`ls` 会告诉我不能访问它，是没有 such file or directory。

但我可以做一件事：加一个环境变量叫 `LANGUAGE`。加上它以后，`ls` 的行为完全一样，可是那个 error message 完全变了。这就解释了为什么有的同学看到的那条错误信息是中文，而我的是英文。

更有意思的是：这其实是同一个 `ls` 程序，访问的也是同一组系统调用。`ls` 试图去 `open` 那个文件，`open` 失败了——那下一个问题是：为什么 `ls` 可以区分出不同的语言？答案就是 libc。

> **结论**：错误信息用哪种语言说出来，是 libc 的事，不是 `ls` 的事。

#### perror 与 errno

libc 里面有一个函数叫 `perror`。它会打印一条 system error message：首先打印你给它的那个字符串，同时它会得到**上一个系统调用或者上一个库函数调用失败的原因**，并把那个原因的字符串打印出来。而打印这个字符串的过程，是 libc 里面的代码根据当前**语言环境的配置**来输出一条友好的 message。

所以你看到的那条 `ls` 的错误信息里，`ls:` 是我们自己打的，剩下的部分是由 `perror` 这个库打印出来的——哪一个东西不存在、没有那个文件或者目录。

什么时候该用它呢？如果某个错误是你要容忍的——比如你依次尝试打开三个文件，第一个不存在就打开第二个，第二个再打开第三个，都不存在程序就直接退出，那你也可以不打任何 error message。但如果你是在做一个给别人用的工具，像我刚才说的 `ls`、`gcc`，当一个文件不存在时你需要把这个 error message 打印给用户，那你就应该用 `perror`。

这里面的机制是这样的：libc 里有一个变量叫 `errno`（error number），你在 C 里面可以直接访问那个 error number 变量，它就对应了相应的错误类型。

> **提示**：`errno` 是 libc 提供的一个 portable 的机制。用它来输出错误信息是好习惯——你甚至可以实现自己的工具，并且用正确的语言输出错误信息。

### 环境变量：environ 是谁赋值的

#### 环境变量会被子进程继承

libc 还封装了进程的运行环境。刚才那个 `LANGUAGE` 的例子，就是通过一个环境变量来影响程序的行为的。

`environ` 的手册告诉我们，libc 里面有一个变量叫 `environ`，通过它你就可以得到一个 key=value、key=value 的环境变量表。大家也都知道，在 `execve` 这个系统调用里，我们可以给 `main` 函数传递 `envp` 参数：一个 C 程序的初始状态，除了 `argc`、`argv` 以外还有一个 `envp`，而这个 `envp` 是在 `execve` 的时候指定的。

这其实是一个非常有趣的设计。用来 execute a file 的系统调用有一整个系列，有些带 e，有些**不**带 e；带 e 的那些函数，里面都有一个参数叫 `envp`。而在大部分时候你并不需要带 e 的那个，比如做 `execl` 或者 `execvp` 的时候，我可以执行一个路径对应的文件，把 `argv` 传进去。那这个时候环境变量是什么样呢？

Unix 为环境变量做了这样的一个设计：**默认的时候，子进程会继承父进程的环境变量**。也就是说，最底层那个系统调用当然必须给出完整的参数和环境变量，但你在用 libc 的 API 调用的时候，比如刚才看到的那几个 API，默认子进程就会继承父进程的环境变量。

这会带来什么样的效果呢？如果我这个进程设置了一个 `LANGUAGE`，这个 `LANGUAGE` 就会传递给我所有的子进程。这样，比如我现在 login 的时候，我就已经知道这个用户的语言是什么，我把当前用户的语言放到环境变量里；那我后面生成的 shell、shell 再 fork 出来的 shell、shell 再 fork 出来的应用程序——整个进程树里面所有的东西都带上了这个 `LANGUAGE`，只要你不改它。

于是这个环境变量就会导致：这个用户看到的所有 error message 都是英语；如果你 login 另一个用户，他的配置是法语，那么他看到的（同一个程序的）错误信息就是法语。就用这样一个简单的机制，得到了意想不到的效果。

刚才我讲环境变量的时候，你们大概觉得：哦，这就是一个操作系统用来传递参数的东西嘛。但你没有想到，这个机制在不断地被使用。所以 Unix 是一个千锤百炼的系统：它虽然有些机制是被滥用的，但这些微小的设计——环境变量的继承，还有进程树的机制、托孤的机制——都是在反复的淬炼当中，最终收敛到了一个大家都觉得也还算好用的状态。

#### 关于 environ 的几个问题

`environ` 这个变量和 `stdout`、`stderr` 一样，是由 libc 提供的。而 libc 提供的时候只提供了**这个符号**，所以理论上说，你可以用任意的方式来定义 `environ`——当然，正确的定义方法要符合它的类型。我甚至把 `environ` 声明成别的类型、乃至给它赋成 `NULL`，程序照样正常终止、没有 crash；因为 libc 的初始化代码后来会给它赋上正确的值。

但这里其实藏着几个非常有趣的问题。

首先，`environ` 是一个变量，那它就一定在进程的地址空间里，一定有一个地址。它是一个 `char **`，所以它是一个 8 字节的指针，它在进程的地址空间里有一个自己的位置。

然后，**它是谁赋值的**？你马上细想一下，这事情就不对了。因为我们知道，根据 ABI（Application Binary Interface），在进程状态初始化以后，参数、环境变量这些都是放在**栈**上的。而你也知道我们有地址空间随机化：栈的地址是不确定的；或者说整个地址空间里面，除了 binary 自己指定"我就要加载到那个固定位置"的东西以外，所有东西的位置都是不确定的。

不确定就意味着这个指针——尤其是它每次运行的时候参数和环境都不一样——**每次的值也不一样**。

如果你还不放心，我还可以把这个代码改一下，或者取它的地址会发生什么？打印 `environ` 会发生什么？打印 `*environ` 又是什么意思？这些操作都是合法的：

- 取 `environ` 的地址，得到一个像 `0x420108` 这样的值。**这才是**那个 8 字节的 `environ` 变量本身所在的地址——它是一个变量，它在数据区，或者说在 bss 区。
- 而在进程刚刚启动的那一刻，如果我打印 `environ`，你会发现这个地方放的是 0。

这是对的。为什么呢？因为每一次进程被加载到地址空间以后，你还根本不知道 `environ` 在哪。

#### watchpoint 停在 __init_libc

所以其实我们的 libc 干了很多脏活和累活。在这里打一个 watchpoint 就能看到是谁写的。

答案是这个函数：`__init_libc`。可惜今天翻车了，这个源代码我没有提前准备好——不过这些都是 musl libc 里面的代码，你可以自己看到、自己调。这些代码实际上都是 C 代码。在 musl libc 里，`_start` 接管了第一条指令以后，最终就会调用到这里的 `__init_libc`。我们的 `environ`、也就是那个环境变量，就是由这段代码赋值的。

> **结论**：计算机系统里面没有任何魔法。在 C 的世界里，当我们有了 Simple-C 的模型以后，所有的一切都是围绕 Simple-C 的模型来的。

除了在 System V ABI 里面规定了那个 initial process stack（进程初始的时候栈长什么样）以外，剩下的东西都是这样的 C 代码。你看，就在 `__init_libc` 的第一行，有一句

```c
__environ = envp;
```

刚在 watchpoint 的时候，程序其实就已经停到了这一句话上。停在这句话上，我们的 `environ` 这个指针就有一个值了，它指向栈上那个正确的环境变量。

### C runtime：程序的真正起点与终点

#### _start 与 initial process stack

顺便，我们也就引入了 `C runtime` 这个概念。我们的程序终究还是从 `_start` 开始运行的，而 `_start` 也是 libc 的一部分。`_start` 是一段最小的汇编代码，那段最小的汇编代码会跳到 `_start_c`。

`_start_c` 是一段非常有意思的代码。它大致是这样的：我有一个 `long *p`，我从这个 `long *p` 上面读出了一个 `argc`——`p` 的第一个元素就是参数的数量；然后 `argv` 就是 `p + 1`。

```c
int argc = p[0];
char **argv = (char **)(p + 1);
```

如果你去读 System V ABI 的手册，你会看到那个 initial process stack 就是长这个样子的：

```text
   高地址
   +-------------------+
   |       ...         |
   +-------------------+
   |       NULL        |   环境变量数组到此结束
   +-------------------+
   |     envp[n-1]     |
   |       ...         |
   |      envp[0]      |
   +-------------------+
   |       NULL        |   参数数组到此结束
   +-------------------+
   |    argv[argc-1]   |
   |       ...         |
   |      argv[0]      |
   +-------------------+
   |       argc        |  <-- 进程刚启动时，栈指针 sp 指向这里
   +-------------------+
   低地址
```

读图说明：进程刚被 exec 起来的时候，栈指针指向的第一个字就是 `argc`，紧挨着它上面依次排着 `argv[0]` 到 `argv[argc-1]`、一个空指针、`envp[0]` 到 `envp[n-1]`，再一个空指针。这也解释了为什么环境变量可以用 `argv + argc + 1` 算出来。

所以这一小段汇编代码会找到正确的栈指针，从它上面取出参数的个数和所有的参数，然后再跳到 `__libc_start_main`；`__libc_start_main` 直接就调到了 `__init_libc`。而你回去对照手册上画的那个 initial process stack，会发现和这里的布局完全一模一样。最后就到 `__init_libc`——就是我刚才看到的那段代码，`environ` 等于 `envp`。所以真的是没有任何魔法。

#### libc 到底提供了什么

到这儿你就会发现一个东西，它叫 **C runtime**，简称 CRT。刚才那个文件，它的名字叫 `crt1.c`——这个 `rt` 就是 runtime。如果你再回去让大语言模型把整个编译的过程都打开，你还会看到一些别的什么 `crtbegin.o`、`crtend.o`、`crtn.o`，这些都是和 runtime 相关的。

到这里我们就可以清点一下，libc 到底提供了哪些东西：

| 层次 | 内容 |
| :--- | :--- |
| freestanding 的环境 | `setjmp`、`longjmp`、知道整数有多长、怎么打印一个整数 |
| 系统调用的封装 | 文件描述符、进程、甚至错误的编号 |
| 必要的代码 | 负责初始化、负责收尾的那部分 runtime 代码 |

这些必要的代码可以在 ELF 的头上看到。ELF 头上面有一个 entry：你们在计算机系统基础课上做过这个操作，用 `readelf` 去看一个二进制的文件，可以看到我这是一个 amd64 的 ELF，entry point address 是 `0x400168`。这个地址是链接器最后填进去的——链接器会找到那个 `_start` 的符号，把它的地址填到 ELF 的头里。而这段代码就是我们 `crt1.o` 里面的代码。

所以 libc 里面就是这些东西：它有定义、有宏定义，还有用于最初初始化的代码（比如设置 environment 的代码）。以及尾巴上、你结束的时候、`main` 返回的时候——你看到那个 `__libc_start_main`，它会调用 stage2。你终于看到了这一行代码：

```c
exit(main(argc, argv, envp));
```

也就是说，如果你要实现一个 libc，你要干的就是这件事：先 `exit`，然后调用 `main`，把 `argc`、`argv`、`envp` 交给它。在这之前的事情在 `__init_libc` 那里，在这之后的事情在 `exit` 里。

而 `exit` 会调用 `atexit` 注册的 handler：它会调用 functions on exit，调用 `libc_exit_finish`，最后 flush buffer，最后调用一个 `_exit`。这个 `_exit` 是一个系统调用，它调用了 `syscall`——当然这里假设的是 Linux，因为 musl 假设的是 Linux。

这就是我们看到的一个 C 语言程序的全部。

### libc 站在 system call 之上

在操作系统和应用程序之间，其实只有一层非常小的接口，叫 system call。操作系统里面有好多对象：进程、文件，以及你能想象到的任何在编程中用得到的设备，比如显卡，它们都是操作系统里面的对象。你但凡想要访问操作系统里面的对象，就必须通过 system call。

不过今天我要调的代码，和"进入内核的一条系统调用指令"（`svc` 或者 `syscall` 这样的指令）不太一样。所有的访问操作系统内部对象、使用操作系统功能的需求，都要通过 system call；但你如果直接用 system call 写程序，那是一件很难受、很糟糕的事，你会把程序写得非常冗长。

最典型的例子是 `write`。你们看过 `write` 的原型，它是 write to a file descriptor，需要三个参数：一个是文件描述符，一个是 buffer，一个是 count。你想要正确地写进去，就必须每次都算一遍长度。你不想每次都算一个长度，所以你希望用更高阶的语言机制去写代码——libc 就是这么来的。

libc 和 C 是深度绑定的，C 又是和 Unix 深度绑定的，所以你在 libc 里面到处都能看到 Unix 的影子。一个 `struct FILE`，它其实和一个文件描述符是紧密相关的。

```text
+---------------------------------+
|  Application                    |   应用：写 fopen / fseek / ftell
+---------------------------------+
|  libc                           |   平台无关的抽象层
+---------------------------------+
|  C 的 FFI / inline assembly     |   靠 C 的函数调用约定去够下面一层
+---------------------------------+
|  system call ( svc / syscall )  |   访问操作系统对象的唯一入口
+---------------------------------+
|  OS objects                     |   进程、文件、显卡、各种设备
+---------------------------------+
```

读图说明：从上往下是"我们写代码的地方"到"操作系统真正持有对象的地方"。上面三层都在用户态，程序通过 C 的函数调用去用 libc，libc 再通过调用约定去发系统调用，最后落到底下的对象上——所以 libc 就是把 system call 包了一层。

> **提示**：这个分层不特别严谨，因为你的二进制文件也可以直接访问 system call，不走 libc。但作为心智模型，你可以接受它。

libc 是一层很好的平台无关抽象。它虽然和 Unix 的设计深度绑定，比如 `struct FILE` 和文件描述符是绑定的，但你又会想：任何一个操作系统，只要觉得这个操作系统还是给人用的，它总应该有一个访问文件的功能。所以像 `fopen`、`fseek`、`ftell` 这些函数，本质上操作系统都应该能提供一个方式实现。

所以不管底下是什么操作系统——可以是 Linux、Windows，也可以是你那种微控制器上面非常非常小的操作系统。你们有这样小一点的设备吗？手表或者手环？如果有的话，它们基本上都是有 libc 的；你买一个树莓派 Pico 那种非常小的设备，它们也都有 libc。它底下的 system call 可能不是像 Linux 这样的 system call，但它对上暴露的那一套接口基本上完全一样。

这就给了我们世界上一个非常好的万能抽象层：我们可以在 C 的基础上构造自己的应用世界。有了 C 以后，你就可以去编译一个 Python，编译别的什么等等等等。

### 自己实现一个 libc 并不难

如果让你自己实现一个 libc，原理对大家来说也是不太困难的。我最早的时候给大家实现过一个 `void _start`：你其实是可以控制程序的入口的。用这个方式，你就能控制程序的入口；再用上合适的编译选项——豆包可以给你一个合适的编译选项，`-ffreestanding` 的编译选项——那我就可以不链接任何的库函数。

你的那个 minimal 的二进制文件里面，除了这个函数的代码以外就什么也没有，真的什么也没有。程序就会从这个地方开始执行。从这儿开始执行的时候，你就真正意义上从零开始接管了这个程序。

你其实想要调用的是 `argc`、`argv`、`envp`，你其实想做的是这件事情。当然你为了能做到这件事，还需要知道 `argc` 是多少、`argv` 在哪里、`envp` 在哪里。

main 函数的签名大家还记得吗？我有一年期末考试考过这个，让你写一下 main 函数，做一个补全，然后竟然有同学写不出来，我有点尴尬。

```c
int main(int argc, char *argv[], char *envp[])
```

写成两个星号 `char **argv` 也是对的。因为你只要在另外一个地方有一个 main 函数，你在这里就可以做一个函数调用：函数调用会遵循这个指令集体系结构的 calling convention，也就是函数调用的规则，把正确的指针 argv、envp 放到正确的寄存器里，argc 也放到正确的寄存器里，然后执行一条跳转的指令，跳转到 main 函数执行。

然后 main 函数会正常返回，也可能会从系统调用返回。如果正常返回的话，它就回到这里，到 `exit`；它也可以调用 libc 里面的 `exit`，main 函数就会翻转。

所以这就是那句话：因为你控制了 `_start`，你就控制了一切。

在 C 语言里面是可以有 FFI（foreign function interface）的，我们有两种方式：

- 一种是 C 语言直接调用一个符合 calling convention 的汇编代码。你那段汇编只要函数调用的规则是 C 语言能够接受的，我的 C 就可以直接跳过去——我可以把任何一段汇编指令都声明成它是一个 `void f`，它接受两个参数 `int x, int y`，那个函数只要从正确的寄存器里读出正确的值、实现正确的功能就可以；
- 另一种是可以在 C 里面直接写 inline assembly，内联的汇编，这样我们的 C 代码就可以执行系统调用了。

所以在 syscall 上面有一层是 libc；libc 是通过 C 的 FFI 去调用系统调用，然后访问操作系统里面的对象。在这之上，我们就得到了一个平台无关的抽象层。

### 让 libc 带上调试信息

上节课我翻车的时候，我要做的是生成一份有 debug info 的代码。我是怎么翻车的？我调试到那个代码里，比如说 `gdb test-debug`，我在调试这个 main 的时候，GDB 告诉我没有可用的源代码，然后我就翻车了，因为我再也调不下去了。

你想要编译一个可以调试的程序，大家都知道可以这样：

```bash
gcc -g test-debug.c
```

然后我在 `gdb a.out` 的时候，就能看到这个代码了。当然如果我再 step 进去，现在调试的是动态链接的那个 glibc 里面的代码，所以我又看不到源代码了。这就是我上节课翻车的现场。

翻车的原因是我没有 libc 的编译，而这个编译要在二进制文件里面打包一份源代码。Debug info 某种意义上就是在你的二进制文件、你那个 lib 里面——你的 lib 可能是 `.a`，可能是 `.so`，甚至就是 `.o` 文件——你自己一份源代码：对应我的 main，我的 `test-debug.c` 会变成一个 `.o` 文件，然后这个文件被链接（这是计算机系统基础里面讲过的），我会把源代码的信息塞进去，使得我在调试的时候可以根据行号返回一个源代码。

```bash
musl-gcc -static -g test-debug.c
```

加上 static 和 `-g` 之后再看，你看到的就是一份有调试信息的东西：我现在就可以看到这是 CRT 下的 crt1.c，这是 musl-gcc 的 libc 里面的代码，你就看到它了。

然后我那天还要加一个 `-Og`。当然我那天实际加的是 `-O1`，再加 `-g`。后来为了保全起见我加了个 `ASFLAGS`，后来发现没有用，那是我事后的 hotfix。我没有意识到的是：应该加在 `CFLAGS` 上。

> **易错点**：把优化与调试选项加到 `ASFLAGS` 是没用的，编译 C 代码要加在 `CFLAGS` 上。这不是风格问题，加错了就真的不会有调试信息——我上节课就是栽在这种"看起来脚本跑完了"的地方。

### 调试信息到底是什么

下一个问题，有没有人想过或者好奇过这个问题：调试信息到底是什么？因为你们在上 ICS 课的时候，老师就会告诉你们：加上 `-g` 这个选项，你这个程序就变得可以调试了。那 `-g` 到底做了一件什么事？

你可以去问豆包，然后豆包会告诉你：`-g` 会在你的程序的 ELF 文件的某一个节里面塞入一些额外的信息。我们可以看一下：

```bash
readelf -a a.out
```

用 `readelf` 看这个文件里面有的调试信息，你会看到一些很特别的名字，像 `.debug_frame`、`.debug_line`、`.debug_str`、`.debug_line_str`，这些都是一个一个的节。在这个 section header 里面，你看它还有一些像 GOT（Global Offset Table）、GOT.PLT 这样的节——你们还记得计算机系统基础课讲过这个吗？记得，但是你不知道这是什么了，对吧？有点不记得了。我上操作系统课的时候会再讲一次。

你们比较熟悉的是 `.text`、`.data`、`.bss`，这些是加载器会把它们从二进制文件里面搬到内存的节。但我 `-g` 了以后，你的二进制文件里面还多出了这么多的东西。

你看一眼就走了，因为你不知道这是什么。正确的方法是把这段文本直接丢给一个大语言模型。我因为 `readelf -a` 了，我已经把所有的信息都丢给它了，它就知道：从输出中可以看到以下和调试相关的 section，这些都是 DWARF 调试信息的标准 section。

| 节 | 作用 |
| :--- | :--- |
| `.debug_aranges` | 从内存地址到编译单元的映射表 |
| `.debug_info` | 核心调试信息：类型、变量、函数 |
| `.debug_frame` | 调用栈展开（unwind）需要的信息 |
| `.debug_line` | 行号表：PC 与源代码行的对应 |
| `.debug_str` / `.debug_line_str` | 调试用的字符串表 |
| locations | 变量在 PC 范围内的位置信息 |

> **定义**：编译单元就是一个 `.c` 文件——一个 `.c` 在编译的时候是一个编译单元，`.debug_aranges` 这张表就是拿内存地址去找它属于哪个编译单元。

它提到的 DWARF 是一个调试的标准。有兴趣的同学可以去下载一个读网页、读手册的 skills，它可以去遍历一个网上的手册；我上课的时候不会再去花时间整这个手册了。

你们看到这里面的起名梗了吗？DWARF 是矮人，ELF 是精灵。这个梗在里面有很多。DWARF 很有意思，它是一个有 bytecode 的指令集。

### 不用调试信息也能调试：符号表与 addr2line

甚至可以不需要任何的 debug info，你也可以在 GDB 里面一定程度上知道你的程序运行到哪儿了。为什么呢？因为你的 ELF 文件里面有符号表。

```bash
nm a.out
```

我用 `nm` 就可以找到符号表。这个符号表是一个一个的入口，比如说我知道 main 在 `.text` 的 `400218` 这个位置。那所以当我的 PC 走到 `400218` 的时候，是不是我就知道 main 函数开始执行了？

不相信的话我可以在调试里试一下：我在 main 上面打一个断点，它打在 `2f8`，这个比 `218` 要聪明一点。因为生成的 debug info 给了我们一个更精准的程序的位置，它把程序前面的那个入口忽略掉了，它有一个更好的从汇编语言到源代码的对应。但其实因为我们有符号表，所以根据符号表，你就知道现在是 main 加 16 的位置：`400218` 就是 main 加 0 的位置。

所以你至少在调试的时候，只要有 PC 指针和符号表，你就可以知道你现在在哪个函数里。你其实就可以实现一个调试器了——只是你不知道 PC 继续往后的时候，你现在在 main 函数的哪一个位置。你可以实现一个这样的调试器："我现在在 main，在做这件事。"

> **提示**：断点没有落在函数的第一个字节，而是落在入口之后一点的位置，这正是调试信息在起作用——它知道哪一条指令才是第一条语句真正的开始，因此跳过了编译器插在函数开头的序言（prologue）。

如果你想要一个更精准的、像长成那样的调试，你就需要知道一条语句对应了哪一段 PC 的范围。当然这是假设编译器没有优化的时候；如果编译器允许指令重排、内联，把语句执行的顺序打乱，这个对应就变得比较困难了——你们调试优化过的代码会遇到一些小困难。不过如果你不优化，你基本上是可以把一条 C 里面的语句对应到连续的一块汇编代码的。这也是我前面讲 Simple C（那个简化版的 C）的时候它给你带来的能力：从 C 语言直接翻译成汇编语言。

你可以想象我们的 binutils 里面有一个 `addr2line` 的工具，它可以把 PC 的一个地址转换成源代码里面的一行。

```bash
addr2line -e a.out -f 400218
```

以前我们都需要读手册：比如系统里面有一个工具叫做 `addr2line`，那你们就会去读它的手册，然后花很多时间去做一些实验确认它真的是这样。但是现在我们完全可以让 AI 来帮我做这件事情——你只要知道这件事情是合适的，比如 `addr2line` 这个工具是有用的，你马上就可以让它帮你去做这个实验。

它开始做 `addr2line -e a.out -f`——以前 `-e` 和 `-f` 实际上是我们自己读手册得到的，现在不需要了——`400218` 就是我刚才看的 main。它找到这个 `400218` 是在 main 的 `test-debug.c` 的第三行，这个应该是没问题的。然后它还试了 `400594`、`libc_start_main`，它也找到了，这是我这份 musl libc 上面的 `libc_start_main`。

接下来你就可以实现自己的调试器了。你有这个工具，就可以实现一个自己的调试器，它确实找到了正确的结果。

### DWARF 里的那台虚拟机

DWARF 里面其实包含了一个小的解释器，它是一个有点像编程语言的东西。这个小的解释器、这个小的编程语言，能够允许你通过访问寄存器——因为有的时候它需要从寄存器里面取一个地址出来，它有这种 frame pointer，比如 EBP、RBP 这样的寄存器，它会标记这个栈、一个栈帧的位置——然后有的时候你就需要对它做算术，才能得到一个变量的值。

所以它甚至是一个图灵完备的指令集，它有分支。理论上说你可以用它来写程序，来恢复出任何一个变量的值。当然，DWARF 的设计本身不是为了让你做这件事情的，它是为了描述：在某个 PC 范围内，变量的值在哪里、怎么把它算出来。

因为我们在调试的时候，比如说 `int x`，这个 x 有可能是存在寄存器里，有可能是存在内存里，有可能它已经被优化掉了、不存在了。然后这些信息都必须在 DWARF 里面写清楚。因为你们调试的时候有的时候会看到一个变量的值被 optimize out，它说被优化掉了，你看不到那个值。

> **提示**：调试信息一定程度上的义务，就是把这样被优化掉的东西给捞回来。有的时候生成得好的调试信息——比如换一个编译器去编译——它可能能够捞出更多的调试信息来，有些时候你就能看到那个变量的值。

这个 DWARF 的 bytecode 指令集也用于实现 C++ 异常的 stack unwinding。C++ 程序抛出异常的时候会弹出栈帧，这个时候要恢复到上一个调用者的位置，就需要——有点像我们上节课讲 longjmp 的时候——也需要 debug info 里面的东西。

> **定义**：一个"调试信息"为什么需要一台虚拟机？因为 C 里面有 bit-field：你可以在一个 struct 里面指定 32 个变量，每个变量都有名字，每个都是一位。调试的时候你可能要去打印那个结构体中的某一位。所以它需要一个指令集，来算出怎么从一个 32 位的整数里面提取出一位来，可能是从寄存器里面拿出某一位。比如我知道 argc 是 int，它在 rdi 寄存器的低 32 位——debug info 就会帮助你恢复这样的信息。

### 调试信息不只属于 C：JavaScript 的 source map

刚才我们说，调试信息主要是为了我们能把一个 PC 指针映射回源代码。然后在每一个编程语言里面，基本上都有这样的调试信息。

C 和 C++ 刚才我们用 `addr2line` 试过，它给了我们一个答案。但 `addr2line`、或者说调试信息本身是没有源代码的：它需要一个点（`.c` 文件）在正确的位置，你的 gdb 才能读到它。但不是所有的语言都是这样的。

有些语言为了方便你调试，尤其是像 JavaScript，它有一个有意思的特点。打比方，我可能是写 TypeScript 的，但这个 TypeScript 最后是不能直接在 JavaScript 虚拟机里面运行的，它不认识这个语法。然后 JavaScript 有一层一层的、叫 transpiler 的东西——有点像 compiler，叫转译器，我不知道这个中文应该翻成什么——它可以把 TypeScript 转译成没有类型标注的 JavaScript，再把一个新版本的 JavaScript 转译成一个 20 年前浏览器也能运行的老版本的 JavaScript，然后那个东西再到底层的浏览器里运行。所以也相当于是从高级语言一层一层翻译到了汇编语言。

翻译到汇编语言以后，你还得能把调试的位置映射回去。尤其是调试的时候你出问题了嘛，那个地方你在 console 里面看到一个红叉，说这个什么什么不能是 null，对吧？你经常看到这种，甚至你直接调试任何一个网页、打开你们的教务系统，很有可能就会看到这样的红叉。所以你如果想要调试的话，也需要类似的 debug info，从底层那个 JavaScript 的某一行映射回我们源代码里面的某一行。

为了方便，这个 debug info 是可以在脱离原始的源代码 repo 的情况下工作的，这个设计也是很合理的：

| | C / C++ | JavaScript |
| :--- | :--- | :--- |
| 调试信息在哪 | ELF 文件里的 DWARF 节 | 独立的 source map 文件 |
| 要不要磁盘上的源码 | 要：gdb 按路径去找 `.c` | 不要：源码可以直接存在 map 里面 |
| 为什么这样设计 | 有操作系统、有目录，假设目录里有源码是正常的 | 浏览器是沙盒，没有整个项目的目录结构 |

对于 C 来说，你要 gdb 调试，你是有操作系统的、你是有目录的，所以 gdb 假设你那个目录里面有一份源代码，这个是正常的。但是 JavaScript 一旦进了浏览器里，这个浏览器是没有你的整个项目的目录结构的，浏览器是一个沙盒。那这个时候它为了方便，可能要把出错的那一行、甚至那个代码都直接存放在 debug info 里。

比如说我自己课程网站在调试的时候，我的 Next.js 都会给我一个非常友好的框框：我的页面如果出错以后，它直接就告诉我哪一行出错了、哪一个变量出错了，然后会给我一个函数调用栈，顺便还有那个代码也展示在下面。有时候我看一眼那个代码，哦我就知道什么问题了，直接去修复了。这时候 JavaScript 的 debug info 就是可以直接存储在这里的。相当于在 C 里面你 `readelf -a a.out` 的时候，看到这个地方有完整的所有的源代码。

于是就有了我下载下来的那个 50 几兆的 `cli.js.map`。这里面就是所有的 Claude 代码的源代码，这两天发生的最大的事件。我粗略地看了一下，我觉得还是挺屎山的。虽然网上有很多文章在吹它的设计，但我看了一下觉得都是比较正常的设计，而且很多地方我看到了很多屎山。

里面当然也有一些很有意思的东西。比如这里有一行叫 `checks if input matches negative keywords patterns`，你就可以知道这个程序员是怎么在他出错的时候骂他的。这显然不是一个好的做法；而且我似乎没有找到这个函数的调用链，就是没有函数会调用它，这像是一个死代码。我不确定到底发生了什么。包括你去看它的整个 UI 是怎么实现的，它是一个 React 实现的 text UI，代码蛮好玩的。你们有兴趣可以看它怎么处理 LLM 的 tokens，它全部都是异步的，等等等等。

> **注意**：有了这个 `cli.js.map` 以后，它不是完整的项目——比如它没有 `package.json`，所以你没有办法把它 build 运行起来。然后光速就有人弄出能运行的版本，而这里面其实很危险：你看起来这个能运行的版本，如果你 build 它，build 是会运行脚本的。如果这个人不怀好意地在它的依赖里面投一些毒，就会引入一个恶意的包，然后恶意的包会执行一个脚本，可能会把你重要的信息、甚至你的 LLM token 泄露出去。所以这些项目你在下载运行的时候，尽量在一个干净的沙盒里面去处理，不要直接在自己电脑上。

### 有了调试信息能做什么

Debug info 给我们的是在汇编语义上恢复出 C 语义的能力。汇编上都是 register 和 memory，比如说我们有一条汇编指令是 `call main`（当然 main 是一个地址），那么这个时候在汇编语义上我们的程序是有状态的：它有什么 rdi、rsi 等等等等，有 pc，也就是 rip，等等等等。

而 a.out 的 debug info 它就能够帮助我们恢复出：比如说在 `call main` 的时候，我们就知道 rdi 是 argc，然后它是 int 类型的——包括类型信息，debug info 里面也全部都是有的。

从一个汇编二进制的状态，重构到一个源代码的状态，这个能力就让我们能做很多有趣的事情。

#### 把地址映射回源码，把调用栈整个还原

一个是刚才讲过的 `addr2line`：从一个 PC 指针回返到源代码的一行。

还有一个是做 stack unwinding，做一个 backtrace。我们在 gdb 的时候都调过：你有好多层的函数调用的时候，我可以用一个 `bt`（backtrace）看到函数调用谁调了谁、调了谁、调了谁，一路一路调过来的。而这是以瞬间完成的——我不仅可以把 top frame 的东西恢复出来，我也可以把整个完整的函数调用栈，就是 C 编程语言的模型，给它恢复出来。这样我就可以在 GDB 或者一个可视化的调试器里面很好地理解程序的功能。

#### 采样出火焰图

我们还可以实现很多 trace 和 profiler。大家都知道 `strace`，我都用过很多次了，它可以 trace 到程序所有的 system call。

```bash
strace ./a.out
```

你看用 musl libc 编译出来的程序，它的 system call 是非常简短的：`execve` 完了以后只有一两个可能和系统相关的 system call，后面直接程序就开始运行了。

| | musl libc 编译出来的程序 | gcc 编译出来的程序（哪怕 `-static`） |
| :--- | :--- | :--- |
| `execve` 之后的 system call | 只有一两个与系统相关的 | 明显多得多 |
| 典型多出来的调用 | 没有 | `readlinkat`、`getrandom` 等 |

system call trace 某种程度上是操作系统给你提供的功能。但是当你有 debug info 的时候，你就可以干这样一件事：你可以隔一小段时间就把这个程序给停下来、暂停一下。可以是操作系统来做这件事，也可以是你在应用层做这件事——就像那个游戏修改器一样，你隔一小段时间，就可以去看一看当前程序的状态。

那你想，如果每隔 1 毫秒、或者更短，比如每隔 1 毫秒，你去采样一下这个程序的执行，通过 debug info 恢复出程序的调用栈，你最后就得到了这样的一幅 flame graph，就叫火焰图。

```text
   |<------------------- 时间轴 ------------------->|
   +---------+---------+---------+---------+--------+
   |                  main                           |  main 一开始就在栈上，
   +---------+---------+---------+---------+----------+  直到程序快结束才 pop
   |   func_b          |   func_c          |
   +---------+---------+-------+-----------+
   |   f_d   |   f_e   |  f_g  |  ...      |  进来一个函数就垒一层，
   +---------+---------+-------+-----------+  返回就出来一层
```

读图说明：横轴是时间轴，纵轴是函数调用栈。每调用一个函数、函数进来了，我上面就会垒一层；再进来就垒一层、垒一层；如果有函数返回了，这里就会出来一层、出来一层。通过采样的方式，你就可以大概知道整个函数调用的分布，哪一个函数调用占的时间最长。

函数调用栈里面有一些部分在底下是一直没动的，比如说 main：它进入 main 从一开始就会在函数调用栈上，然后它直到几乎要到最后、程序要结束的时候，它才会从栈上面 pop 出来。

这样一来，如果你是采样、而不是像 `strace` 那样把所有的系统调用都拿到，你就可以大概分析这个程序的性能。因为你采样是均匀的，而如果你的程序确实绝大部分的时间都是花在一个函数上的话——一般来说也是的，就是大部分的时间都是花在少部分的函数上——就可以找到程序的性能瓶颈。这里面有很多有趣工具，你可以跟大模型聊天；也可以真正导出 trace，并且有相应的 profile 的标准。

#### 崩溃快照与 sanitizers

以及如果程序 crash 了，你有这个程序的快照——同样也是汇编意义上的快照——你也可以调试这个快照，一定程度上调试这个快照。甚至你还可以改变里面的一些值，比如说改变一个 PC 让这个程序继续往后执行，这些都是可以的。

你们有用过那个 sanitizers 吗？我已经不太会合法编程了。看这么一个程序：它表面上看是正确的，你运行了它也对，但这个程序其实是不对的。因为你已经把 p 给 `free` 了；`free` 了以后就有可能会有——如果你的程序多线程的话，后面会讲到——另外一个线程。这个叫 use-after-free：你在 free 了一个指针以后再使用它。

但是其实 p 没有变，对吧？p 没有变，所以你在 `free(p)` 完了以后，那块内存其实在地址空间的意义上它还是可以用的。所以这个程序可能并不会 crash，但可能会是一个非常严重的问题，这是 undefined behavior，而且它可能会导致潜在的安全漏洞。

但如果你带上 `-fsanitize=address` 的时候，这个程序它就不是这样的了：它告诉我有一个 heap-use-after-free on address 这个什么什么什么。

```bash
gcc -fsanitize=address test.c
```

> **易错点**：use-after-free 里那个指针 p 的值没有变，在地址空间的意义上那块内存也还"能用"，所以程序往往不会 crash。不 crash 绝不等于正确——它是 undefined behavior，是潜在的安全漏洞。

AddressSanitizer、ThreadSanitizer 这些 sanitizers，它们的诊断报告都可以利用到调试信息，然后帮你能够恢复出更多的关于源代码的知识。

### 亲手调试启动流程：从 _start 到 main

既然有了 debug info 以后我们可以调试程序了，今天我们就可以真正来调一下各种各样的程序。

我的第一个调试程序就是 crt1.o 的程序和初始化，所以我直接调试一个最小的程序 `dummy.c`。这个 dummy.c 就是 `return 1`。如果你 `strace dummy` 的话，看到确实是用 musl libc 编译的，然后它在 `execve` 以后就做了很小的几件事，然后调用 exit，它就退出了。

```bash

```

我可以直接从它的第一条指令开始调试，这是它的 `_start`。不过 `_start` 的这一小段代码应该是一段汇编，所以如果我 `layout src` 的话，我没有找到它的源代码。但是一旦我进入第一个函数 `_start_c`，就有的看了。

`_start_c` 有一个参数，是一个 `long *p`，一个指针。然后这个指针我上节课讲过了：从这个指针部分，我就可以逆向工程（reverse）出初始的进程栈。我们甚至也可以让 AI 来帮我读 crt1.c，让它给我初始的进程栈。

因为我们知道现在栈上有一个指针，然后我们说 `argc = p[0]`，argc 在这儿，所以这就是 `p[0]`；然后 `argv` 是 `p + 1`，这就是 argv，然后那这里就应该是一些字符串。我应该 step 进去——当然我现在可以看到 argc 是 1，打印 `argv[0]`，这些数值都是对的，那我就可以 step 进去。

我们又知道这个 `envp` 是 `argv + argc + 1`，所以这就是 envp。那我就可以打印这个 `envp[0]`——真的就是一个环境变量。如果我这个时候来看一下 `env`，你看它有这些和 VS Code 相关的环境变量。

我也可以打印 `envp[-1]`：我在这里是可以访问这个在 C 意义上是非法的地址的。因为 p 在这儿，然后 `p[0]` 是参数，一个 `NULL`，然后上面是环境变量。所以我们是真的可以在程序里面完整地看到这一点的。所以至少我确实确定了初始的进程栈是这样的。

```text
低地址
    argc                        <-- p，也就是 _start_c 拿到的那个指针
    argv[0] ... argv[argc-1]    <-- argv = p + 1
    NULL
    envp[0] ... envp[n-1]       <-- envp = argv + argc + 1
    NULL
    辅助向量 auxv
高地址
```

读图说明：从下往上地址递增。`_start_c` 拿到的指针 p 正好指向 argc；紧接着是 argv 数组，用 NULL 结尾；再往上就是环境变量数组，也用 NULL 结尾，而它的起点正是 `argv + argc + 1`（那个 `+ 1` 跳过的就是 argv 结尾的 NULL）；再往上就是辅助向量 auxv。所以 `envp[-1]` 落在 argv 数组的结束符上——按 C 的语义这是越界访问，但它确实是进程栈上一块有效的内存，我们在调试器里能把它打出来。

顺着这个思路，AI 也没有假设架构是 x86，它认得出来我这份二进制是 arm64 的，还指出了这些代码到底是在哪里。

然后我们可以接着调 `init_libc`。在 init_libc 的时候它有一个 envp 参数。上次课我们看到了，第 26 行的时候有个 environment 复制，就在这个地方把全局的那个 `environment` 变量复制给了 envp。然后它会跳过：`for (i = 0; ...)`，只要这个 `envp[i]` 还是一个合法的字符串，它就会跳过所有的环境变量——你看这边每个东西都是一个指针，每一个参数都是一个指向了某一个 NULL-terminated 字符串的指针。跳过所有的环境变量以后，然后继续把剩下的这个辅助向量一个一个给处理了。

处理完了以后，它就会调用一个 `stage2`。我在这儿也可以打印一下 stage2：stage2 是一个函数指针，它指向了这个 `__libc_start_main_stage2`。我跳到这儿，就跳到下面。然后还有一个 `__libc_start_init`，不过这一段代码应该没有执行什么实质性的内容。

然后就到了我们 libc 最经典的地方：如果你自己要实现一个 libc，你其实就去尝试写这句话。写这句话，然后这句话就真的存在了，真的存在。存在以后，这个跳转就会跳到我的 main，然后 main 会 `return 1`。`return 1` 以后，会执行 `exit 1`；`exit 1` 会真的把那些逻辑执行掉，包括 stdio 的 exit。最后一个 exit，然后这个 exit 会直接调用 syscall。

```text
_start                        <- 汇编入口，gdb 从这里开始
  |
  +-> _start_c(long *p)       <- p 指向初始进程栈
        |
        +-> init_libc(envp)
        |     |  把全局 environment 复制给 envp
        |     |  跳过全部环境变量字符串
        |     +  逐个处理剩下的辅助向量 auxv
        |
        +-> stage2 (函数指针) == __libc_start_main_stage2
              |
              +-> __libc_start_init    <- 本程序里没有实质工作
              |
              +-> main(argc, argv, envp)  ->  return 1
                    |
                    +-> exit(1)
                          |  stdio 等清理
                          +-> 最后一个 exit 直接调用 syscall
```

读图说明：整条链路从汇编入口 `_start` 开始往下走，libc 在 `_start_c` 里把初始进程栈解出来交给 `init_libc` 收拾干净，再用一个函数指针 stage2 拐到 `__libc_start_main_stage2`，最后真正调用 `main`；main 返回以后由 `exit` 接管，走完 stdio 等收尾，最后一次 exit 直接落到 syscall 上。

所以你看，我们说 libc 是包在 system call 外面的一层，这不是一句抽象的口号：从 `_start` 到 `main` 的每一步都是实实在在的代码，你现在可以一层一层地把它们调出来。

## 从 printf 到 malloc：把 C 标准库拆开看

libc 把 system call 包装了一层。它把 system call 的细节屏蔽掉，这样在它底下你就不需要再关心底下到底是什么操作系统了——这就是一个参数的 syscall，然后最后调用到汇编的 syscall，程序就结束了。

现在我们已经知道，怎么从第一条指令开始：从刚 `_start` 拿到第一条指令的控制，沿着 initial process stack 一点一点走到 `main`；也知道走到 `main` 之后再回来是怎样的流程。既然走到了这一步，下面就可以调试真正的函数了。

### 从 `_start` 到 printf：开始调试真正的函数

如果你真的想调试比较大一点的代码，我强烈建议大家不要用 GDB，而是在 VS Code 里配一个 LSP。这样你可以在代码之间任意跳转，会舒服很多。任何一个你喜欢的 IDE 都有调试功能，未必一定是 VS Code。

我可以给 `printf` 打一个断点——注意这是我那个 musl-demo 里面的。当你做了正确的配置以后，就可以直接调试进入这段代码。我的键盘上没有 F11，也没改它的 key binding，所以就点鼠标的 Step Into (F11)。

这样我就进入了 musl libc 的 `printf`，你看到确实是 musl-1.2.6 里面 `src` 下 stdio 的代码。`printf` 的实现很短，基本上就是把参数取出来：它的变参数里面有一个 format，这一次 format 确实就是 `x=%d`。当你有鼠标的时候，很多操作会更舒服——如果 IDE 够大，往左边一拖，format string 你一眼就能看到。

`printf` 调用了 `vfprintf`，把 `stdout` 传进去。`stdout` 是一个封装好了的结构体，我把鼠标移上去也能看到：里面有一些 flag，有一个 buffer（现在 buffer 是空的），`buf_size` 是 1024，`fd` 等于 1。它里面包含了文件描述符、缓冲区和好多其它信息。

再 step into，就进入了 `vfprintf`。它的实现很有意思：它会先做一次 `printf_core`，这一次实际上只是试探性的，看要不要返回失败；检查完以后发现不失败，它才真正进行实际的 printf，执行 `printf_core(f, format)` 并把手上的其它参数传进去。这里的 `f` 还是刚才那个 `f`，fd 还是 1，打印的是向 `stdout` 输出一个 format 字符串，也就是刚才那个 `x=%d`。然后是变参数，还有一个解析的循环。

```text
   main
    │  printf("x=%d", 1)
    ▼
   printf          取出变参数，拿到 format
    │
    ▼
   vfprintf        摆好 stdout（fd=1、buf_size=1024、buffer）
    │
    ├─ printf_core(…)          第一次：试探，看要不要返回失败
    │
    └─ printf_core(f, format)  第二次：真正解析 format，写进 buffer
             │  解析循环
             ▼
           writev       一次系统调用，把 buffer 里的东西打出去
```

一次 `printf` 在 libc 里要经过取变参数、试探、真正解析、缓冲这几步，最后收敛成一次系统调用。

> **提示**：如果你用 `strace` 去看 `printf`，你会看到它只有一次系统调用，打印的就是 `x=1`。中间那一长串准备与解析，在系统调用这一层是完全看不见的。

### printf 的变参数是怎么实现的

#### 只在 x86-32 上成立的取巧

`printf` 里面用了一个 C 语言的语法特性，叫变参数。也就是你在声明定义一个函数的时候，可以写 `void foo(n, ...)`。如果你学过 x86 版本的计算机系统基础，你会说可以写一个这样的程序：因为 x86 会按逆序把参数顺序压栈，最后所有参数就会像一个数组一样躺在栈里；那你就可以取出第一个参数的地址，然后像访问数组一样，用 0、1、2、3 一个一个访问所有的变参数。

> **易错点**：这样一个 hack 只对 x86-32 的 cdecl calling convention 成立。在像 x86-64、ARM、RISC-V 这种寄存器很多的体系结构上，它都是不能工作的，因为传参的时候大部分参数都是经过寄存器传递的——第一个、第二个、第三个、第四个参数都走寄存器。

#### 寄存器里的参数怎么回到栈上

我给大家准备了一份代码。里面的 `foo` 函数就是把所有的参数都读一遍，它没有实际上做任何事（比如用 `printf` 去打印它），但是我阻止了编译器优化它。`main` 函数里则分别调用不同数量的参数：比如一个参数，传 1、11；再一次传 5、1、2、3、4、5、10、10、20、30、40。

从源代码的意义上调试，这个函数调用没什么了不起。但在汇编上你可以看到，它把 1 写到了 `w0` 这个寄存器里，把 11（`0xb`）写到了 `w1` 里；它甚至还把 60 和 70 写到了另外的 w 寄存器里——这是一个编译优化。而实际上用来传参数的，就是 `w0` 和 `w1` 这两个。然后我们 call 这个 `foo`，走到 call 的时候，registers 里 `x0` 和 `x1` 分别是 1 和 11。

`foo` 还要访问第一个参数、第二个参数。这部分汇编代码是在编译器和 libc 共同的帮助下生成的，它生成了一系列奇怪的汇编：它把 `x1` 和 `x2` store 到了 `sp+56` 的位置（用的是一条一次可以 store 两个寄存器的指令），又把 `x3` 和 `x4` store 到了 `sp` 加 72 的位置。这些值你都不知道它是什么，但你可以明确地看到，在这段代码里面，我们的汇编把放在寄存器里的参数 store 到了栈上。

> **结论**：变参数并不是「栈上天然就躺着一串参数」，而是函数序言主动把寄存器里的参数搬到栈上，凑出一块连续的数据结构，`va_arg` 才能顺着一个一个取下去——这是编译器和 libc 协同的结果。如果你只想了解一点 libc 的细节，这一步不重要；但如果你想知道变参数的宏到底是怎么实现的，内部代码给了一些解释。

### 用两次刷漆看清 setjmp 与 longjmp

更有意思的是，我们还可以看一看 `setjmp` 和 `longjmp` 里面在寄存器意义上到底发生了什么。所以我让 AI 帮我写了一段代码。

先回忆一下 `setjmp` 和 `longjmp`：`setjmp` 可以在程序运行到任何一个地方的时候设一个点，标记一下这个位置；后面我可以任意函数调用，调一层、两层、三层、四层，但在 `longjmp` 的时候都可以跳回这个标记的点上。我打的比方是：你们在宿舍做一个标记，然后就出来上自习、出来吃饭，突然哪一个时候想回宿舍了，你直接执行一个 `longjmp` 就回到宿舍了，之前走过的轨迹就全部都没有了。

我干的事情是这样的：先试图把所有的寄存器都刷成一个值，都刷成红色，假装这是红色；接下来执行 `setjmp`；执行完 `setjmp` 以后，我再把所有的寄存器都刷成蓝色；然后我再执行一个 `longjmp`。`longjmp` 理论上应该回到那个状态——那是不是所有的寄存器都会变成红色呢？

所以我让 AI 写了这样一段代码：我有两个不同的数字，把 `x0`、`x1`、`x2`、`x3` 一直到 `x28` 全部都写成这个数字。这时候我需要用命令行的 GDB 去调我的 `setjmp_aarch64`，在汇编意义上看看这段代码会发生什么。

执行到某一刻，所有的寄存器都被刷上漆了：你看到底下从 `x0` 一直到 `x28`，全部都刷上漆了。剩下几个不能刷——刷了以后你的程序就 crash 了，这是为了函数调用等等需要保留的，比如栈顶指针这些寄存器，我不能随便把它刷掉。

接下来，我们的编译器是可以随便使用像 `x0`、`x1` 这些寄存器的，这些用于参数传递的寄存器本身编译器就可以任意使用，所以马上这个 `x0` 就变成别的值了。

然后是 `setjmp` 的代码：它把 `x19`、`x20` 存到了一个 buffer——`x0` 是 buffer 的地址，也就是第一个参数；它把 `x19` 一直到 `x30` 全部存下来，保存到内存里，用的是那种一次可以存两个寄存器的 store 指令；然后又存了一些额外的其它东西，反正最后都是 store。store 完了以后，return。

函数返回以后，你看 `x0`、`x1`、`x2` 的值都已经变了。然后我再刷一次漆，把所有的这些寄存器都刷成这个新值。这时候我再看寄存器：`x0`、`x1` 又被编译器生成代码改掉了，但是 `x2`、`x3`、`x4` 都已经变成我刷过的新颜色了。

好，这时候我执行 `longjmp`。`longjmp` 做的事情是 `setjmp` 的相反：把一大堆寄存器的值重新 load 回寄存器里。我们再看 register——`x0` 到 `x18` 还是我刷过以后的颜色，但是 `x19`、`x20`、`x21`、`x22`、`x23`、`x24`、`x25`、`x26`、`x27`、`x28` 又被刷回来了。

> **结论**：在 ARM 上，`setjmp` 和 `longjmp` 做的事情就是——`setjmp` 时把 `x19` 到 `x28` 这一批寄存器保存到内存的 buffer 里，`longjmp` 时再把它们 load 回寄存器。`x0` 到 `x18` 全程没有参与这个保存与恢复。

跳回来以后，我们的函数其实就执行到那个位置了，它就直接打印 `return from longjmp`。这当然也可以 step 进去，看到 `fputs` 最后掉到一个系统调用，把要打印的字符串送出去。

### 从这个小实验逆推 ARM64 的 calling convention

#### 为什么 x0 到 x18 不用保存

为什么不需要保存 `x0` 到 `x18` 呢？因为所有的这些寄存器在函数调用的时候编译器都可以随便用。当我调用 `setjmp` 的时候，一旦调用这个函数，就意味着这些寄存器全部都可以腾出来了，编译器可以随便使用它们。而编译器会保证这一点：它会各种调整寄存器的使用顺序，使得我在调用任何一个函数的时候，从 `x0` 到 `x18` 里面的值我在返回以后再也不会用到。

所以理论上说，我们就是从刚才那个小实验里，逆向出了部分 ARM64 的 calling convention：在函数调用的时候，`x0` 到 `x18` 的寄存器可以随便用。通过观察一个小实验来观察它的行为就可以逆向出 calling convention，这也是一个比较有意思的例子。

#### 绕口的名词：caller-saved 与 callee-saved

这里有一个很绕的名词，叫 caller-saved 和 callee-saved，也就是调用者保存和被调用者保存。还记得被计算机系统基础期末考试支配的恐惧吗？相比之下，我更喜欢的一个名词叫 call-clobbered。

`x0` 到 `x18` 就叫 call-clobbered：意思是我的函数调用一旦进来以后，这些寄存器就是我的，我可以随便用，我不需要为它负责，把它改掉就改掉。剩下的寄存器如果我要用，我就不能随便改——比如我前面的十八、十九个寄存器不够用了，我确实想用 `x20`，那我要动它，就必须先把它的值保存到内存里，等到我用完了，再把内存里的值恢复回来。这就是 caller-saved 和 callee-saved 这套说法要表达的事情。

> **提示**：这套命名绕人的地方在于，它是按「谁负责动手保存」来给寄存器命名的，而不是按「谁被保护」：被调用者必须自己保存、返回前恢复的那一批，对调用者来说就是「跨调用仍然可信」的一批；而调用者自己要用就必须先保存的那一批，正是可以随便被覆盖的一批。名字和直觉是对着来的，翻译成「调用者保存/被调用者保存」以后更容易绕晕。

### 两次 gettimeofday 之间睡了 200 毫秒

下一个例子更有意思。这里有一个 `gettimeofday`，也是大家平时写 C 的时候经常会写的：你可以定义一个 `struct timeval`，然后有 `t1` 和 `t2`；在最开始的时候在某个时间点调用一次 `gettimeofday`，然后在另外一个时间点再调用一次，就得到了两个时间的值。这个时间的值里面有一个 second，有一个 microsecond（微秒）。如果你要知道两个时间点之间到底花去了多少时间，就把过去的秒数和微秒数加起来。

这个程序就是在两次获取时间之间睡 200 毫秒。运行它，确实打印出了 `t1` 是多少、`t2` 是多少，中间过去的时间大概是 200.062 毫秒。中间肯定会有一些误差，因为调用系统调用也需要时间，系统调用返回也需要时间——虽然睡眠刚好是 200 毫秒，但你实际得到的会比它稍微大一点。多运行几次，结果都差不多。

进程的进程状态就是寄存器和内存，一个进程里面是没有时间的概念的，进程自己是不能感知时间的。所以时间只能通过系统调用来拿。

> **提示**：这就是游戏修改器里面以前那个叫「变速齿轮」的工具能成立的原因。理论上说，只要改变对时间相关的系统调用的参数和返回值：每次 `usleep` 的时候把它拦下来，把睡眠时间改成十分之一；每次 `gettimeofday` 的时候按十倍的速度重新校准这个时间轴——我就可以给它一个假的时间。

### strace 里为什么没有 gettimeofday

那么用 `strace` 看这个程序，你会发现什么呢？你会发现这里有 `nanosleep`，有一个 sleep，但是没有任何 `gettimeofday`。这就有点让人恍惚了：`gettimeofday.c`，不对吗？

那能不能再看一次：我先睡 200 毫秒，再睡 200 毫秒。程序执行一切正常——我看到了三个 `nanosleep`，隔了 200 毫秒被打印出来，中间没有 `gettimeofday`，但打印出来的 `t1`、`t2` 又都是对的。

因为现在的 libc 是我们的，所以也就可以去调试它了。先看 `usleep`：它在 musl 里面的实现非常干净，就 200 毫秒，它构造了一个 `timespec`：second 是 0，nanosecond 是对应的值，然后 `return` 到 `nanosleep`。这里就掉到了一个系统调用：调了一个 `clock_nanosleep`，直接是系统调用。

这一段是直接调到了系统调用里面，用了一段内联汇编，里面有一个 `register` 关键字。`register` 在现在的 C 和 C++ 里面，意义和以前老的标准是不一样的：在有了 `__asm__` 以后，`register` 意味着编译器会强行把它绑定到指定的寄存器里。你会看到在这个函数里面，参数分别被绑定到相应的寄存器上，传递给内核——这是按照 syscall 手册里面规定的 calling convention（系统调用的 calling convention）来的。

### 不陷入内核的系统调用：vvar 与 vdso

下面就是 `gettimeofday`。现在我们知道它没有执行系统调用，但是不管它有没有执行系统调用，所有执行的代码和指令都是真的，这一点你们是可以确定的。

#### 内核留给每个进程的一小段代码

它会走到一个 `clock_gettime` 的函数里去。这里有一个条件编译，有个叫 `vDSO_cgt_sym` 的东西。我前面有一次课的时候说过，在我们的进程的地址空间里面，有两块非常神秘的东西：一个叫 `vvar`，一个叫 `vdso`。`vdso` 就是操作系统内核给每一个进程提供的一小段代码——这是代码；`vvar` 是数据，每一个 CPU 共享。

所以这里面的数据就包括比如当前的 CPU 是多少号、当前的 clock 是多少。现在你们知道，现在的操作系统可能每一秒钟有一千次时钟中断，也可以配置成一百次、250 次的中断；每一次时钟中断来了以后，这个 clock 都会加一，这个 CPU 上都会把自己的 clock 加一。这时候如果我需要一个不是那么精确的时钟时间，我就可以直接从这里得到，得到一个大概千分之一秒精度的时间。然后再配合 CPU 里面有一些指令——你在 RISC-V 的 CPU 上实现过的话，CPU 里面有那个比较精确的 cycle count，那个精确的时钟 cycle count——配合起来就可以算出当前比较精确的时间。

> **结论**：`vvar` 里是内核随每次时钟中断更新的、所有 CPU 共享的数据（CPU 号、clock tick 之类），`vdso` 里是内核提供的一段代码。两者都躺在进程地址空间里，于是「读一个大概的时间」这件事可以不进内核。

#### 顺着辅助向量找到 __kernel_clock_gettime

第一次调用到这里的时候，我走的是这条路径：它先调 `cgt_init`，这是一个 lazy 的加载，一个懒加载；然后调了一个 `vdso_sym`。这个 `vdso_sym` 从哪里找到 Linux 2.6.39 里的 `__kernel_clock_gettime`？它直接在解析 ELF 的文件——program header 直接指向这个位置的一个指针。

那它又从哪里得到 vdso 的位置呢？在 `auxv`，auxiliary vector，也就是辅助向量里。还记得我们在加载的时候说的吗：进程在初始化的时候，除了 `argc`、`argv` 那个参数的数组，还有环境变量以外，后面还有一大堆叫辅助向量的东西，都被包裹进去了。那辅助向量里到底有什么？里面有可以用的随机数种子，一个真随机数种子；然后里面有 vdso 的位置。

```text
   auxv（进程初始化时内核摆好的辅助向量）
     │  遍历，找 AT_SYSINFO_EHDR
     ▼
   vdso 的 ELF 程序头表
     │  像加载器一样遍历符号表
     ▼
   __kernel_clock_gettime    （这次解析到 7fff7fc2d0）
     │  一个 call 直接跳过去，执行 vdso 里的代码
     ▼
   返回 tv_sec / tv_nsec —— 全程没有陷入内核
```

它在这里遍历辅助向量，找 `AT_SYSINFO_EHDR`，找到这个 vdso 的程序头表；然后它就可以在这个程序头表里面做一个像加载器一样的东西——这些都是 ELF 里面你熟悉的：它要遍历符号，有点像遍历符号表一样的功能。遍历完符号表，它就真的把那个函数找出来了：`p` 指向 `7fff7fc2d0`，是 `__kernel_clock_gettime`。

这时候我就可以调这段汇编代码了。我现在暂时不调，就随便往后走一走，然后 `finish`——这里没有任何的系统调用，但是这次「系统调用」完成了，而且给了我这个 `tv_sec` 和 `tv_nsec` 两个东西，`gettimeofday` 就返回了。

所以它的行为，musl 告诉我们：它实际上是去 `auxv` 里面找到一个可以加载的 ELF 的文件头，然后像加载器一样解析了里面的符号表，解析完以后直接跳转到一个正确的函数去运行。这就是「不陷入操作系统内核的系统调用」的实现方式。

### 从指令序列里读出实现：读两次 clock count

你们可能觉得我是不是故意隐藏了一些实现细节。我确实怕你们太麻烦，不想对着那个汇编讲——因为上课讲汇编非常浪费时间。所以我特意让 AI 帮我生成了一段代码，只要跑一下就能得到一段指令的日志，这就是 `gettimeofday` 执行的所有指令序列。

我觉得大家以后上操作系统课真的可能不需要我这样的老师来讲了，我真的不如人工智能。我只要告诉大家：现在存在这样一个机制，叫做不陷入操作系统内核的系统调用，它不需要进入操作系统内核，反正就是在进程地址空间里面的代码，一个跳转直接跳过去，一个 call 指令 call 过去，它就能正确运行。

然后我就真的能在调试器里面把这里面完整的代码跑完。我甚至可以装 Linux 内核的 debug_info，装了以后就真的可以调试到源代码级的这部分代码；但也可以不调源代码级，而是直接用一个 gdb script，让它帮我把所有执行的指令序列记下来。我给的 prompt 是：把进入 `__kernel_clock_gettime` 的时候开始记录的指令序列，到出来的时候停止。

然后你们看到我刚才执行这个程序的时候翻车了：这个函数一直往后执行指令序列，而且在循环，一直在执行相同的指令序列。我翻车了吗？没有，我可以问 AI：为什么 `gettimeofday` 在我 debug、trace 指令序列的时候没有终止，但我正常运行的时候它却能正确终止？

我们的 CPU 每次时钟中断的时候都会给这个 clock 加一，相当于是一个 clock tick 的 count：一次、两次、三次、四次。因为调用 `gettimeofday` 的代码其实非常短，所以你几乎不会出现「我在调用 `gettimeofday` 的时候中间发生了 clock 加一」这种情况。它会先读一次这个 clock tick，记下来放到寄存器里，然后再读一次；如果两次读到的数值相同，相当于我就没有跨过一个 clock tick 加一的过程，那我就认为我读到了正确的数值，得到了稳定的数值，然后我就可以根据这个算出精细的时间。但如果我两次读到的是两个不同的 clock tick，那我就再试一次就行了。

它是一个类似于 sequential lock 的东西：实际上读的是这个 clock count，它会先读取一个 sequence count，然后再读取一次。第一次是在第 32 行读 `W7`，第 92 行读 `W4`，然后会 compare，会做比较：读到两次 tick 不相等的时候它就重试，相等的话它就可以继续。

> **提示**：单步执行的时候，每条指令之间有巨大的延迟，所以这个循环一直都出不来——循环不是写错了，而是调试本身太慢，让「读两次、比对」的窗口被时钟中断反复打断，于是只能一直重试。

顺便，你还直接从二进制上的指令序列就知道了 `gettimeofday` 的实现。

### malloc 与 free：从小字节到大内存

`malloc` 和 `free` 大家都用过：`malloc` 一个 size，`free` 可以把生成的内存释放掉。我刚才已经展示过一个不正确地使用 `malloc` 和 `free` 的例子了：你在 `malloc` 以后 `free`，`free` 以后这个指针就不能再使用了。

C 标准库里面其实提供了不止 `malloc` 和 `free`。虽然 `calloc`、`realloc` 都可以用这两个来实现，这两个是最基础的机制，但还有一些比较方便的：比如 `calloc`，它保证了 memory set to zero。虽然现在为了安全起见，`malloc` 基本上也会给你返回是 0 的内存，libc 一般都会这样实现，它哪怕牺牲一点性能。

#### malloc 能分配多小、多大

`malloc` 和 `free` 是一个数据结构题。你们在数据结构课的时候可能会有一个习题说：哎，你们来实现 `malloc`。当然你们也知道，`malloc` 和 `free` 是小的内存也能分配，大的内存也能分配。你可以分配小到一个字节，甚至 0。

> **提示**：手册里面已经提到了，`malloc` 是允许你分配一个 0 的——"If size is 0, then malloc returns a unique pointer value that can later be successfully passed to free."。它甚至可以是一个 0。当然我们尽量不要依赖这个行为。

它也可以分配非常大的内存，你要 `malloc` 一个 1GB 内存完全可以。

#### libc 为什么要自己维护内存池

但是操作系统是不支持分配那么小的内存的。我们说有两个系统调用：一个是 `brk`，理论上你可以 `brk` 两个字节、四个字节；另一个是 `mmap`，它能够分配的内存就是和整个你的系统的配置相关的。比如你的内存页是 4KB，那你 `mmap` 最终得到的内存就必须是页面大小的整数倍，因为操作系统没有办法把半页分配给你。所以你没有办法跟 `mmap` 要两个字节、四个字节、八个字节这样的内存。

于是在操作系统和 libc 的意义上，分层是这样的：

```text
   应用程序        malloc(4) / malloc(8) / free(p)
                     │  从池子里切一小块出来
   libc 内存池      向内核一次要一大块，自己维护空闲区间
                     │  mmap（更早的实现可以用 brk）
   操作系统内核      以页为单位分配（比如 4KB 一页）
```

`malloc` 支持小内存：libc 里面会自己分配一些相对来说比较大的内存的池子、小内存的池子，这些是它用 `mmap` 实现的，或者更早可以是 `brk` 实现的。它在地址空间里面挖出来一大块可用的内存，然后 libc 自己维护这样比较大块的内存；等到 `malloc` 的时候，比如你 `malloc 4` 或者 `malloc 8`，它就会从这里面找出一小块，比如这个四字节的，然后把这个指针返回给你。

你马上就可以让 AI 去生成一段代码，让它随机地 `malloc`，然后用 `strace` 去看它到底是怎么分配、怎么使用系统调用的——马上你就能够证明它确实是使用了这些系统调用。

### 被 malloc 带出来的麻烦

但我觉得 `malloc` 和 `free` 本质上是一个设计得很有问题的 API。Tony Hoare 在最近去世了，1934 到 2024，他号称自己犯了一个 billion-dollar mistake：他发明了空指针，因为空指针是一个 bug 的来源，一个很重要的 bug 的来源。类似于空指针，`malloc` 和 `free` 也是的。

#### 和 write 比起来，malloc 多要求了什么

`malloc` 和 `free` 在 libc 的意义上和系统调用有点像：提供一个最小的完备性，让机制和策略分离。比如操作系统提供 `write`、`read`、`open` 这些文件描述符的系统调用，至于你怎么访问文件、文件里面写入的到底是有 Unicode 还是 ASCII、你用什么编码，这些事情操作系统统统都不管，它只管字节序列，由你上面的应用程序负责。像 `write` 这套系统调用这样设计其实没有太大的问题：它把这个 API 做得最简单、做得最小，你总是写一段字节、写一段字节、写一段字节，操作系统选择不去理解这个字节序列的含义，还是 OK 的。

但是 `malloc` 和 `free` 这样的机制就不一样了。它引入了一个额外的要求：它要求在任何可能的路径上，我的 `malloc` 都必须得有一个配对的 `free`，否则你的内存就浪费了；以及我 `free` 了以后，这个指针立马就变成了非法，以后再也不能使用。

| 对比项 | 文件描述符的 API（write/read/open） | malloc / free |
| :--- | :--- | :--- |
| 内核/库提供的完备性 | 只认字节序列，不理解内容 | 分配与释放必须成对 |
| 上层要负责的事 | 字节的编码与含义 | 每一条可能的路径上的释放时机 |
| 违反约定的后果 | 写进去什么就是什么 | 泄漏，或指针立刻失效后的非法访问 |

所以有 bug 的代码是非常危险的：我可以 `free(p)` 以后马上 `*p = 1`。这在程序意义上、C 语言意义上是合理的，但是在 `free` 的语义意义上是不可以的。

> **易错点**：`free(p)` 之后写 `*p = 1`，编译器不拦你、语法也不拦你，但指针已经被交还，这就是典型的 use-after-free。同样，在作用域中途 `return` 掉一个还能走到的 `free`，就是泄漏。

#### 人类为此走过的弯路

所以这个代码最好、最理想的情况应该像 Rust 一样：它拒绝编译这样的代码。任何时候我的指针已经被别人拿走了，我就再也没有办法在这个作用域里访问它了。而 C 语言里就充满了各种各样的安全漏洞，都是由内存引起的。尤其在 AI 的黑客能力增强了以后，尤其 Coding Agent 以后，它发现这种系统里面漏洞的能力也变得更强了——你经常会看到说 AI 又发现了什么 zero-day 的漏洞在 Linux 内核里，而这很大程度上都是因为这种指针导致的。

所以很多 coding standard 都要求你 free 了以后立马把它变成空。这样就可以阻止 use-after-free，因为你如果再 use 的话它就会 crash。但这又变成了 Tony Hoare 那个 billion-dollar mistake：你的程序如果有一个地方确实错了，违反了一个你对指针使用、对 `malloc` 使用的约定，你的程序就会 crash，就不提供服务了。

为了能够满足 `malloc` 和 `free` 的这个要求，人类不知道走了多少弯路：

- 从 Java 语言、JavaScript 里面，我们再也没有指针了，没有指针的语言；
- 到 C 和 C++ 里面有 RAII（Resource Acquisition Is Initialization）：你可以用一个对象，比如用得比较多的锁，`locked_object` 这样在作用域里面定义的一个变量，它初始化构造的时候会上锁，析构的时候会解锁。这样我可以保证我在 `if` 什么什么什么的时候就把它 `return` 掉——这个 `return` 是非常危险的，你想如果这里有一个 `malloc`，你在这里就 `return`，这不就是一个泄漏吗？你必须在这个地方也 `free`。地球人都没有办法把这个代码写对，所以你会知道实际的系统里面有非常非常多这样的 bug；
- 直到现在，Rust 有这个 ownership、borrowing。

`malloc` 引入的这个要求和像文件描述符是不一样的。文件描述符的 `write` 是说好我写进去它就写进去了，游标往后移，这个行为是简单的，要求也是简单的；但是 `malloc` 和 `free` 对你程序员带来了一个巨大无比的心智负担。

### 如果让你实现 malloc

不管怎么样，如果要我们做一个作业的话，你基本的想法都是：如果我要 `malloc` 一个很大的内存，你就直接用 `mmap`，直接问操作系统要就行了；比如我要 100 兆，那稍微头头上尾上浪费一点也没关系，直接问操作系统要就行了。但是当 n 不大的时候，其实就是一个数据结构题：它是一个数据结构，维护了很多不相交的小区间的集合。你的 `malloc` 每次就是从空闲的区域里面找一块空间足够的，然后把它给割出来，那块空间就被删掉了；删掉以后你可以在这个区间上做操作。所以你们学算法会得到一个 balanced binary search tree 的 solution——但这不是现在的 memory allocator 的实现。
