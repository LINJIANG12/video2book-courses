## 零钱兑换 II：从暴力递归到顺序优化
> 对应块：BLK24 | 覆盖分集：P99-P102 | 块标题（分集名）：《进阶数据结构和算法-253-零钱兑换II-递归-》

这节课我们来看两道力扣题目，两道题目的名字都叫零钱兑换。

### 两道零钱兑换，差别只在最后一句

先把题目读一遍。给你一个整数数组 `coins`，代表不同面额的硬币——比如下面这个例子中，`coins` 里有一分、两分、五分这几种硬币；再给一个整数 `amount` 代表总金额。接下来让你用 `coins` 里这些不同面值的硬币凑足前面的总金额，每种都有无限个，随便凑，只要凑足总金额就可以。

那这个题目最后问的是什么呢？问的是**有多少种凑法**。

对于一分、两分、五分这三种面额，要凑足总金额五，一共四种凑法：

| 凑法 | 组合 |
| --- | --- |
| 第一种 | 一个五分硬币 |
| 第二种 | 两个两分硬币 + 一个一分的硬币 |
| 第三种 | 一个两分的硬币 + 三个一分的硬币 |
| 第四种 | 五个一分的硬币 |

当然，如果任何硬币组合都没办法凑出这个总金额，返回的凑法数就是零。就比如说只给你一种硬币，是两分面额的，结果总金额是三，那无论如何都凑不足，所以这种就输出一个零。最后一个，给了一个十分硬币，结果总金额也是十，那这个方法是不是只有一种走法？

这是我们这道题目的一个说明。

刚才看到的那道题叫 518 题，零钱兑换二。还有一道跟它非常类似的题目叫零钱兑换，是 322 题，它的解题思路跟我们前那道题是差不多的，只不过它最后求的不是"你有多少种凑法"，而是这些凑法里哪种需要的硬币数最少。

我们不看 322 自己的例子，还是看 518 这个例子：对于一分、两分、五分，要凑足总金额五，一共有四种凑法，我们都看过了。那 322 题是说，这四种凑法里你要找一个硬币数最少的凑法——显然是不是第一个？它只要一个硬币就能凑足我的总金额。所以 322 题它应该返回一，就是最少的硬币数需要一个。

这就是两道题目的不同。

> **结论**：两道题共用同一副骨架——都是"拿 `coins` 里的硬币去凑 `amount`，能凑就返回一条路径"。区别只在最后一步：518 数路径条数，322 在所有路径里挑硬币数最少的那一条。

待会我们就来求解 518 题。至于 322 题，因为跟它差不多，就留给同学们来练习。

### 先看暴力递归跑出来的过程

这回我准备先用一种笨办法，也就是先用暴力递归的方式来求解，这样有助于我们理解它的工作过程，然后后面再用更好的方法对它进行优化。

并且这次讲解的时候，我们先看结果。我其实已经实现了，我们先看结果，从结果来看一下这个暴力递归的工作过程。

其实所谓的暴力递归，就是我不断去尝试它所有的硬币组合，一旦找到解了，那我就把这个解记录下来。

比如说我先放五个一分的硬币——这五个一分显然是满足解的，对吧，因为我的总金额是五，所以就得到了一个解。然后我再尝试四个一分的硬币加上一个两分的硬币，显然这是无解的，因为 4 + 2 已经超过总金额了，这个可能咱就排除了。接下来再尝试四个一分的硬币和一个五分的硬币，显然这也是无解的，它也超过了总金额是吧。

四个都尝试完了，那我们就再尝试三个一分的硬币。三个一分硬币跟一个两分硬币，结果是优解的，那就把它记下来；继续尝试三个一分的硬币和一个五分的硬币，是不是不行？超过总金额了。三个一分的硬币尝试完了，那我们再尝试两个一分硬币。两个一分硬币跟两个两分硬币，总金额加起来是六，超过总金额了，跳过去；再尝试两个一分硬币和一个两分硬币、一个五分硬币，显然也是无解，跳过去；继续尝试两个一分硬币——注意啊，还是两个一分硬币，这回跟一个五分硬币，显然也是无解。

接下来再尝试一个一分硬币跟两个两分硬币，这个是不是正好凑上了？这是一个解。再尝试一个一分硬币跟一个两分硬币、一个五分硬币，无解。最后尝试一个一分硬币跟一个五分硬币，这个也是无解。

至此为止，以一分硬币开头的，从五个一分到四个、三个、两个，一直到最后一个一分，是不是都尝试过了？尝试过了以后呢，我们再来看以二分硬币开头的。先是三个二分硬币不行；两个二分硬币加一个五分不行；一个二分硬币加一个五分也不行。二分硬币开头的这几种也尝试过了。最后再尝试一个五分硬币开头的，显然这个可以。

所以我们一共找到了四个解。这是我们的暴力递归的一个求解过程。

### rec 的三个参数与三种情况

接下来我们看一下这个代码该怎么编写。首先我准备了一个用来递归的方法，就叫 `rec`。这个 `rec` 呢看着比较复杂，有五个参数，但实际上后两个参数大家先不用管，因为它俩是我为了刚才演示整个执行流程加的两个参数，一个是 `stack`，一个是布尔值，它们实际上在正式解题的时候都用不到，我们只会用到前三个参数。

那前三个参数它们的意思分别是什么呢？

第一个参数 `index`，代表的就是你当前处理的这个硬币索引，比如说它的初始值是零，表示我正在处理哪个硬币。来处理一个硬币，没问题吧。

第二个参数 `coins`，它代表的就是我们整个这个硬币面值的数组。因为每次递归的时候都要用到它，所以我们也把它当成了一个参数。

第三个参数就比较重要了，`remaining` 就代表的是剩余金额。刚开始这个剩余金额就是我们的总金额五。

这里有一个核心的思想：每次递归之前，我会把这个剩余金额减掉我当前处理的这个硬币面值。比如说我剩余金额刚开始是五，我要处理的硬币面值假设也是这个五，那你想 5 - 5 是不是等于零？等于零。那下次我递归的时候，我只要判断出来这个剩余金额剩零了，说明什么？说明它凑足了这个金额。

当然剩余金额是零，这只是其中一种情况，一共三种情况：

| 剩余金额 | 含义 | 接下来怎么办 |
| --- | --- | --- |
| 小于零 | 加多了，没凑成 | 不用再递归了，返回解的个数 0 |
| 等于零 | 正好凑足，找到一个解 | 不用再递归了，返回解的个数 1 |
| 大于零 | 还有其他可能 | 继续凑，继续递归 |

大于零这种情况是什么意思呢？表示还有其他的可能，也就是我要继续凑，看看能不能再在这个剩余金额的基础上再减一个，比如说减一个一，看看它能不能减成零。所以遇到大于零的情况呢，我们应该怎么办？继续递归。

一共这么三种情况。大家先把这三个参数的含义理解了，我们根据刚才分析的这三种情况，先把代码架子给它写出来。

### 把代码架子搭起来

第一种情况，剩余金额小于零，刚才说了代表是没有找到解。没有找到结果，是不是不需要继续递归了？那我只要返回一个结果就可以。那这个结果返回什么呢？因为没有找到解，解的个数就是零，我们返回一个零就可以了，因为我们的返回值代表的是解的个数。

第二种情况，再写一个 `else if`，当剩余金额等于零的时候，我们返回解的个数是一，怎么找到一个解，返回的解的个数是不是就是一。当然最后我们会把这个解的个数给它累加起来，就是最终它的解的总数。

那么这两种都比较简单，最复杂的呢其实是第三种，也就是剩余金额大于零的情况，这时候我们要继续递归。这个代码我先把它写出来，然后我们再来解释。它得写在一个循环内，这个循环的初始条件呢是 `i` 等于 `index`，那结束呢是循环到 `coins` 的 `length` 减一，小于 `coins.length`。然后循环内我们就去递归就可以了。

那这个递归的代码呢就是调用 `rec`，然后把 `i` 作为第一个参数传进去，第二个参数还是传我们这个 `coins` 数组，第三个参数我们说了，递归之前是不是要用我们当前的剩余金额减掉我们要处理的这个硬币面值。

```java
public int rec(int index, int[] coins, int remaining) {
    if (remaining < 0) {
        // 剩余金额小于零：没有解，解的个数是 0
        return 0;
    } else if (remaining == 0) {
        // 剩余金额等于零：找到一个解
        return 1;
    } else {
        // 剩余金额大于零：还有可能，继续递归
        int count = 0;
        for (int i = index; i < coins.length; i++) {
            count += rec(i, coins, remaining - coins[i]);
        }
        return count;
    }
}
```

这个循环翻译成式子就是，当前状态能凑出的解数等于所有可选下一枚硬币分支的解数之和：

$$\text{count} \;=\; \sum_{i=index}^{coins.length-1} \text{rec}\big(i,\; coins,\; remaining - coins[i]\big)$$

那最后两个参数啊，我们说过没啥用，你就随便传一个就可以了，就把它原封不动传过去。这个方法返回的是他解的个数，那我们应不应该把这个数给它累加起来？应该。所以我们定义一个变量就是他的 count，刚开始这个数是零，然后我们返回到解的个数跟这个 count 做一个累加，最终解的个数是不是这个 count，那我们就返回这个 count 就可以了。

好这段代码呢是我们截止到目前为止大家会见到的一个比较复杂的递归。我们下面就来分析一下这个递归它的一个执行流程。

### 递归树：一层循环，三条支流

在分析执行过程之前我先说明一下，我们代码其实到这已经都实现完毕了。你看我们三种情况是不是都考虑了：剩余金额小于零的时候返回解的个数是零；剩余金额等于零的时候表示找到解了，返回解的个数是一；那剩下的还没找到解的情况，我们继续递归的时候会拿到每次递归它返回的这个解的个数，把它累加起来，这就是我们最终的结果。

我们先来验证一下这个结果对不对啊。你看我们硬币面值分别是 1、2、5 的情况下，总金额五，是不是我们前面分析过他的解的个数一共有四个呀。我先验证一下，最后求得解的个数是四，说明我们这个代码是 ok 的。

好代码没问题，那接下来我们再来看看这个递归的过程。我们就从第一次 `rec` 调用开始看。

第一次 `rec` 调用它传过来的 `index` 是零，代表的是我正在处理哪个硬币——正在处理 1 号硬币，是这样吧。所以这我就直接写一了，我就不写 `index` 了，我们直接写他正在处理的硬币，这样大家可能脑子里更好对应一些。接下来我再来写一个参数，就是他剩余金额。剩余金额这时候是五。

所以这是我就把我们的方法调用简写成这个样子啊，只写了他的正在处理的硬币和他的剩余金额：

```text
rec(1, 5)
```

接下来这个 `rec` 方法是不是就进入了我们方法的内部。方法内部它会走到哪个情况呢？是不是应该走到 `else`？因为剩余金额是五，是大于零的，所以就走到了 `else`。好走到 `else` 以后，我们来看这里就有一个比较复杂的动作了，就是一个循环。因为它是在循环内去调这个递归函数的，所以这是一个多路的递归啊，复杂就在这了。

那我们来看一下这个循环产生了几层递归。首先 `rec` 处理的这个 `i` 是从哪开始呢？是不是还是从零开始，所以第一次循环它还是处理 1 号硬币，没问题吧。但是这个时候它的剩余金额会变化啊，你看剩余金额下次递归的时候，是不是应该是我当前剩余金额五减去你正在处理的硬币一？是这样吧。所以下次处理的时候这个剩余金额就会变成四。

好这是我们第一次循环。那第二次循环呢，第二次循环它就处理 2 号硬币了吧。那处理 2 号硬币，这个剩余金额是不是应该是当前的金额 5 减 2 号这个面值，应该是三呀，那下次他递归的时候这个剩余金额就会变成三。

那第三次循环呢？第三次循环是处理 5 号硬币，当然这回呢就是 5 - 5 啊，下次剩余金额就是零了。

好分析到这儿，我先问同学们一句：**你觉得这只会有三次递归吗？**

其实并不是。因为我们这个 `rec` 第一次循环的时候，这个 `rec` 它的内部是不是又会走我们刚才这三个情况？如果它再次走到 `else` ，是不是它的内部还会继续循环、继续递归？所以这个过程是相当复杂的，我们接着来继续分析。

```text
rec(1,5)
├─ rec(1,4)          4 > 0 → 三次循环
│   ├─ rec(1,3)
│   │   ├─ rec(1,2)
│   │   │   ├─ rec(1,1)
│   │   │   │   ├─ rec(1,0)   → 1   找到解
│   │   │   │   ├─ rec(2,-1)  → 0   加多了，无解
│   │   │   │   └─ rec(5,-4)  → 0   加多了，无解
│   │   │   ├─ rec(2,0)       → 1   找到解
│   │   │   └─ rec(5,-2)      → 0   加多了，无解
│   │   ├─ rec(2,1)
│   │   │   ├─ rec(2,-1)      → 0
│   │   │   └─ rec(5,-4)      → 0
│   │   └─ rec(5,-2)          → 0
│   ├─ rec(2,2)               → 从 index 开始，只剩 2 和 5
│   │   ├─ rec(2,0)           → 1   找到解
│   │   └─ rec(5,-3)          → 0
│   └─ rec(5,-1)              → 0
├─ rec(2,3)                   → 从 index 开始，只剩 2 和 5
│   ├─ rec(2,1)
│   │   ├─ rec(2,-1)          → 0
│   │   └─ rec(5,-4)          → 0
│   └─ rec(5,-2)              → 0
└─ rec(5,0)                   → 1   找到解
```

读图说明：左边标正在处理的硬币，右边标剩余金额；走到 `rec(1,0)`、`rec(2,0)`、`rec(5,0)` 这三条线的末端就是四个解，其余全是负数、直接返回零的枝桠。

好接下来这个 `rec(1,4)` 呢，它的剩余金额是不是还是大于零的啊，所以他进来以后还会走到 `else`，只要走到 `else` 它就会来三次循环，是这样吧。好那么它就来一个 `rec(1,3)`，因为 4 - 1 是三；`rec(2,2)`，这回是 4 - 2 是二；再来一个 `rec(5,-1)`，因为 4 - 5 是 -1。

这是 `rec(1,4)` 的内部又进行了三次递归。那我们继续，`rec(1,3)` 呢，它的内部是不是仍然这个剩余金额是大于零的，所以它的内部又到 `else` 了，只要到 `else` 它就会进入我们这个循环，所以它的内部是 `rec(1,2)`、`rec(2,1)`，还有一个 `rec(5,3-5 = -2)`。

下面这个需要注意一下。你看我们这里以二开头的递归的时候，进入循环时还会不会说从 1、2、5 再变一遍？不用了吧。以二开头的它接下来遍历的时候，循环的时候只会循环二和五了啊，这一点大家要注意一下。其实就是因为我们 1 跟 2 的组合是不是已经组合过了，你这回再过来如果再从一开始，那就相当于是二跟一去组合，就相当于重复了。

好，接下来这个剩余金额是零啊，不用看了，直接返回结果一。剩余金额是负数的也不用递归了，直接返回无解。

那这样呢我们就找到了四个解，中间执行了多少次递归操作？n 多次。这个过程还是非常复杂的。

### 用一个栈把每种组合打印出来

我们做一个小效果，就是我希望把每种硬币的组合给它打印出来——甭管你有解还是没解，把硬币组合的那些可能都打印出来。

那这一点怎么做呢？就要用到我们传过去这个 `LinkedList` 这个参数了，它是一个栈，它呢就用来记录这些硬币的组合。

具体怎么做呢？我们对照着上节课这个递归图咱们来分析一下。我们就从 `rec(1,4)` 这块开始。`rec(1,4)` 呢相当于是处理一这个硬币，对吧。但是我们都知道啊，他这个递归调用跟我们的深度优先遍历是类似的，它是一条道，先要走到头才会往回走。

所以呢它继续递归，走到 `rec(1,3)`，相当于这时候就组合了 2 个一的硬币了，但这时候剩余金额还是大于零的，所以它继续递归，组合 3 个一的硬币，再继续——这个呢就相当于组合了 4 个一的硬币。再递归的话就相当于 4 个一的硬币跟接下来的这几个 1、2、5 的硬币进行组合了：4 个 1 加 1 个 1 是 5 个 1，4 个 1 加 1 个 2，4 个 1 加 1 个 5，是不是这几种可能相当于都尝试过了。

好，那执行完了以后呢，这个 `rec(1,1)` 是不是他就调用结束了。调用结束它就向上返回，向上返回的话就回到了 `rec(1,2)` 这块。那 `rec(1,2)` 呢它相当于组合了 3 个一，但 3 个一它还有一条线，大家来看就是沿着这条线它还会向下走，也就是 3 个一跟谁组合？跟二组合，跟五组合。

好这样一段，`rec(1,2)` 也结束了。继续向上返回返回到 `rec(1,3)`，这时候相当于剩了 2 个一的硬币了。这 2 个一的硬币呢我们再看他这条线，2 个一要跟谁组合？跟二组合——当然 2 个 1 加 1 个 2，这个还是大于零的，所以它继续递归，又走到这条线，也就是 2 个一的硬币跟 2 个两分的硬币组合了，2 个一的硬币跟 1 个二、1 个五组合了。

好这是这个 `rec(1,3)` 就掉完了，掉完继续向上返回，返回到 `rec(1,4)`。返回到 `rec(1,4)`，这一块它还有条线。到这儿也就剩了 1 个硬币对吧，1 个硬币跟谁组合呢？跟这条线上的硬币组合——1 个一的硬币跟 2 个两分的硬币组合，1 个一的硬币跟 1 个二、1 个五进行组合，最后呢还有一个 1 个一的硬币跟这里的五进行组合。

好，等到 `rec(1,4)` 调用结束，它是不是就尝试了这么多种组合呀。这个看明白了吧。好那下面调用就跟刚才的 `rec(1,4)` 差不多了，`rec(1,4)` 其实是在一个循环内，在 1 到 5 的那个循环内。第一次循环完了，它循环到第二个循环就处理这个 `rec(2,3)` 了。好那他也是尽可能地向里走，先来一个二的硬币组合，结果剩余金额还是大于零，所以继续进入。好这块我就不一一化了，也就是相当于 2 个 2 号硬币跟接下来的第 3 个 2 号硬币组合，2 个 2 号硬币跟 5 号硬币组合。那等组合结束了，`rec(2,1)` 就相当于调用完了，返回到我们的 `rec(2,3)`。`rec(2,3)` 呢相当于只有 1 个二这个硬币，他接下来还要跟下面的这个五进行组合。

最后呢还有一个 `rec(5,0)`，它呢因为第一次去减的话，减的就是一个五分的硬币，就减成零了，它就没有继续递归了。

#### 每进入一次调用就往栈里塞一枚硬币

好，这是我们整个这个递归的调用流程。那这个调用流程大家清楚了之后呢，我们来看我们刚才的功能怎么实现啊。

你看每次递归调的时候，我们是不是能拿到当前正在处理的这个硬币啊？那这个硬币怎么拿到呢？是不是 `coins[index]` 就可以拿到当前正在处理的这个硬币了，因为 `index` 是硬币的索引嘛。

那这个硬币我想把它记录到哪去呢？是不是记录到我们的栈里。刚开始第一次调用 `rec(1,4)` 的时候，那么往这个这里吧，我们这个一这个硬币加进去；好等继续递归再调用到第 2 个 `rec(1,3)` 的时候，我们再往这个栈里加一个一，这个硬币是这样的。

所以我们每次进入递归方法调用的时候，我们可以把这个硬币加入到刚才这个栈里，所以代码我们就可以写成 `stack.add` 是刚才的硬币。

这样一直加一直加，比如说加到第 5 个一这个硬币了，哎这个时候我们相当于是找到解了啊——因为这时候加了 5 个一嘛，结果这时候他的剩余金额又是零，所以找到解了。那找到解，我们就把这时候的栈打印出来。

好，我大概写了一个 `print` 方法，它的第一个参数是一个提示信息——有解，那第二个参数呢就是传我们的栈，这样就把栈内容会打印出来。

#### 三处都要弹栈

但是打印完了需要大家注意一件事啊，就是这时候栈里存储的是什么？是不是 5 个一这个硬币啊。但是最后这个一相当于已经组合过了，他留着是不是就没用了啊？

所以我们发现有解之后应该做什么？我把最后加入的一是不是要删掉啊？删掉，然后恢复成栈里只有 4 个一的状态，然后呢我才跟下面的二啊、五啊这些进行组合。那怎么把栈顶的元素删掉？简单吧，我们只要调用栈的 `pop` 方法是不是就可以删掉了。当然这里啊保险起见，我们可以先做一个判断，如果这个栈不为空我们再删啊，调用一下 `isEmpty` 判断为空，我们再去 `pop` 删除。

好，这是有解的情况。那我们刚才删掉一个最后这个第 5 个一之后，是不是栈里剩了 4 个一啊？那下次再去组合、调用 `rec(2,1)` 的时候，是不是栈里又加了个二啊？就相当于是 4 个一和一个二。那这是一个无解的情况，那无解情况呢我们也去打印一下。无解情况也打印。

那这个二需不需要删掉？是不是也需要删掉啊，它跟有解一样，你处理完了你把它删掉，剩下的 4 个一才能跟其他的这个硬币去做组合。所以这行代码仍然需要把它加过来。

那刚才我们 4 个一跟 1、2、5 都组合完了以后，就相当于这个循环是不是结束了。这个循环内处理的是 1、2、5 嘛，那循环结束以后，这时候我问栈里剩了哪些内容？是不是还剩下 4 个一啊。好，但是循环结束了，那我留着 4 个一有用吗？是不是最后这个一就没用了啊？最后这个一应该删掉，然后剩 3 个一再进入下一轮的递归处理。

所以我们循环结束之后仍然要做的一件事也是删除栈顶元素，那这个代码呢跟刚才一样，我们就把它拷贝过来。

#### 首次调用不能入栈

那我们来测试一下啊，直接去运行看看它的输出结果。好像是对的，但是呢我们发现这个栈打印出来的内容好像多了一个一啊。你看刚开始打印的是 6 个一对吧，接下来呢是 5 个 1、1 个 2；5 个 1、1 个 5；4 个 1、1 个……好像每次都多了个一。

那多出来这个一是从哪来的呢？其实问题出在我们最外层这个 `rec(1,5)` 这了。`rec(1,5)` 其实它还没有算是我们去捡钱那个操作，没有去做那个捡钱操作——因为你想，我这个剩余金额是刚开始是五，对吧，然后这时候处理的硬币呢是 1 号硬币，也就是 `rec(1,5)` 这种情况，他其实还没有真正去执行那些组合操作，是从 `rec(1,4)` 这块才开始做的这些组合。

所以我们应该对于首次调用啊做一个特殊处理，也就是第一次调用我们不应该把它 `push` 进来。所以呢我这加了一个布尔变量啊，它刚开始是 `true`，表示它是第一次调用，那不是第一次调用我们是不是才应该 `push` 啊。所以我们判断一下，如果这个 `first` 是假、不是第一次，那么才去做这个 `push` 操作。当然呢后续递归的时候，我们就把这个 `first` 改成假。

```java
public int rec(int index, int[] coins, int remaining,
               LinkedList<Integer> stack, boolean first) {
    // 每进入一次调用，就把当前这枚硬币记录到栈里；首次调用除外
    if (!first) {
        stack.add(coins[index]);
    }

    int count = 0;

    if (remaining < 0) {
        print("无解", stack);
        if (!stack.isEmpty()) {
            stack.pop();
        }
    } else if (remaining == 0) {
        count = 1;
        print("有解", stack);
        if (!stack.isEmpty()) {
            stack.pop();
        }
    } else {
        for (int i = index; i < coins.length; i++) {
            count += rec(i, coins, remaining - coins[i], stack, false);
        }
        if (!stack.isEmpty()) {
            stack.pop();
        }
    }

    return count;
}
```

好这回我们再来运行一遍，这回就对了吧。5 个一有解；刚才我应该打印个无解啊，就是刚才走到 `remaining` 小于零了，这应该打一个无解答案，印错了啊，重来一遍。好这回对了吧：5 个一有解；4 个 1、1 个 2 无解；4 个 1、1 个 5 无解；下面就是类似的，我们不一过了。

至此为止呢，我们这个需求就实现了。

### 少写三段重复代码

当然这个代码呢还有一些可以优化的地方。你看我们无论是无解还是有解还是循环结束，是不是都要从栈里把那个栈顶元素删掉啊？这段代码重复了。

那这段代码重复，我们怎么把它减少重复呢？我们可以这样做：把整个这个弹栈的代码呢咱们移到方法的最后。一到方法最后，但是我到方法最后呢，我们是不是得把 `return` 放在这个弹栈之后，他都是在 `return` 之前要弹栈，所以我们把这个 `return` 的值啊咱们抽取成一个外层的变量。

比如说我还是叫 `count`，它的初始值是零。那如果是无解，那我们的 `count` 值是不是不用变啊，还是保持零；那如果有解呢，我们就把这个 `count` 改成一；那如果是递归的情况呢，这个 `count` 只要去累加就可以了。这个也不要了，那最终我们弹栈之后 `return` 那个 `count` 是不是就可以了。

```java
public int rec(int index, int[] coins, int remaining,
               LinkedList<Integer> stack, boolean first) {
    if (!first) {
        stack.add(coins[index]);
    }

    int count = 0;

    if (remaining < 0) {
        // 无解：count 保持 0
        print("无解", stack);
    } else if (remaining == 0) {
        // 找到一个解
        count = 1;
        print("有解", stack);
    } else {
        for (int i = index; i < coins.length; i++) {
            count += rec(i, coins, remaining - coins[i], stack, false);
        }
    }

    // 无解、有解、循环结束，三处共用的弹栈逻辑
    if (!stack.isEmpty()) {
        stack.pop();
    }

    return count;
}
```

好，这是我们对刚才的一个优化处理啊。

### 拿到力扣上跑，为什么会超时

代码呢我们已经写完了，这个正确性呢也可以得到保障。但是呢，如果我们把这个代码放到力扣上去跑，你会发现它会超时，也就是我们的这个代码的执行效率上是比较低的，没达到人家预期的这个时间。

那问题出在哪呢？主要的问题就出在整个这个递归过程上。你看我们整个这个递归里面有没有一些重复的方法调用啊？有吧。你看比如说这里的 `rec(2,-1)` 是不是重复调用了三次啊，还有这里的 `rec(5,-4)` 是不是也重复调用了，包括下面这些很多都出现了重复。

那如果是我们这个钱币的种类比较多，将来组合的数量就非常庞大，这里面重复的递归调用就更多了，造成我们整体这个算法的执行性能非常的低。

那怎么优化呢？其实我们前面讲过一种优化的策略，叫做**记忆化优化**：第一次递归的时候发现这个递归方法没有执行过，那我们就把它进行执行，但是把它的结果啊咱们缓存起来；那下次呢我遇到了相同的递归方法，我就不用再重复执行了是吧，直接从缓存里面拿到这个结果。

当然了，还有一种优化呢，是我们还没有讲到用动态规划的方式进行优化。那我们这节课先不考虑记忆化以及动态规划的优化，我们先从另外一个角度对我们这个递归流程啊做出一个简单的优化。

### 由小到大，还是由大到小

那我们先来观察一个规律啊。你看刚才我去进行这些钱币组合的时候，都是由小到大来组合的啊。先去用一跟其他钱币做组合，然后呢再用二这个钱币跟其他钱币做组合，最后才是五跟其他钱币做组合，是这样吧？

那其实我们由小到大去完成这个组合，你越到最后越容易失败，大家想是不是这样。比如说你已经 4 个一了，再来一个更大的二，很容易就超过他的总金额了啊；已经 4 个一了，再来一个更大的五，那更容易超过它的总金额了，是不是这都是增加了一些失败的几率啊。包括啊 3 个一，3 个一跟二正好凑成我们的总金额了，但是 3 个一跟五是不是就超过总金额了？

所以呢按照我们生活中的经验，我由小到大这样去凑啊，其实这种失败的几率高。那如果反过来呢？反过来我们由大到小来凑这个总金额呢，我们试一下啊。

你看我把上面这个 `1 2 5` 打开这个注释掉，最后呢我们是先去考虑面值大的钱币啊，最后呢再考虑面值小的钱币：

```java
int[] coins = {5, 2, 1};   // 由大到小
int amount = 5;
```

好我们运行一下。我们先来看一下最终得没得到正确的解。得到了吧，我还是找出了一共有四种解。但是这回失败的几率是不是变低了？只有一次发现无解了，其他的都是直接拿到了有解的情况。我们发现好像由大到小是不是我们效率更高啊。

#### 降序之后的递归树

好，那接下来我们就来分析分析这种由大到小的递归执行流程。这回呢我们就按照面值 5、2、1 这个顺序去处理。

首次进入 `rec` 的时候，那 `index` 0 处是不是面值最大的那个五分硬币啊，首先是 `rec(5, 5)`，然后剩余金额呢刚开始也是五。这是我们第一次调用，它内部进来之后会进入到情况三吧，因为剩余金额大于零，那接下来它内部会做三次循环。

第一次循环的时候，处理的是 5，所以剩余金额减 5 得到的是零；然后第二次循环呢处理那个硬币二，剩余金额减二得到的是三；最后才是处理这个 1 号硬币，5 - 1 = 4。

那循环内的每个 `rec` 是不是有可能继续递归啊？我们把这个递归都给他写出来。当然第一个不用了啊，因为它的剩余金额是零了，它已经找到解了，所以直接返回一表示已经找到解。

那第二个 `rec(2, 3)` 我们看它还是要继续递归的。它这回剩余金额是三，进入了 `else` 以后，那需要从 5、2、1 这样一个顺序去循环嘛，它是不是一开始那个五就不用处理了，他只要从二开始处理就可以。那处理二分硬币的时候是 3 - 2，剩余金额是一；处理一分硬币的时候是 3 - 1，剩余金额是二。

好继续把它写完。

```text
rec(5,5)
├─ rec(5,0)      → 1   找到解
├─ rec(2,3)              从 index 开始：五不用处理，只剩 2 和 1
│   ├─ rec(2,1)
│   │   ├─ rec(2,-1)     → 0
│   │   └─ rec(1,0)      → 1   找到解
│   └─ rec(1,2)
│       └─ rec(1,1)
│           └─ rec(1,0)  → 1   找到解
└─ rec(1,4)              从 index 开始：五、二不用处理，只剩 1
    └─ rec(1,3)
        └─ rec(1,2)
            └─ rec(1,1)
                └─ rec(1,0)  → 1   找到解
```

读图说明：左边标正在处理的硬币，右边标剩余金额；降序之后整棵树瘦成了一条主链加两个短分支，找到 4 个解，只踩中一次负数。

好接下来 `rec(1,4)` 这一块它其实相对还是比较简单的，它也是五分、两分的都不用处理了，直接处理一分这个硬币，那处理一分硬币的时候就是 `rec(1, 3)`。然后 `rec(1,2)`、`rec(1,1)`，最后 `rec(1,0)`，这就找到解了，找到解呢返回最终的解。

#### 规模对比：二十三行与十三行

那我们来看整个这个递归数的规模，是不是比之前要小很多啊。当然也是找到了一个解、两个解、三个解、四个解，那找失败的只有一次。

那你看我们这棵由大到小的树是 19 到 32 这一段，这样一减的话只有 13 行对吧。那你看我们之前由小到大这个递归过程有多少行，72 到 95，95 - 72 是 23 行啊。或者直接看看这个高度，是不是显然后面这个递归的规模要比前面递归规模少很多啊。这是我们由大到小它带来的好处。

> **易错点**：顺序只是"减少失败分支"，并没有消除重复调用——`rec(1, 0)` 在降序的树里依然出现了三次。真正的复杂度问题要靠记忆化或动态规划解决，那两条路我们下节课再走。

322 题 零钱兑换，这节课留给同学们练习。

**题干**：给定一个整数数组 `coins` 代表不同面额的硬币，和一个整数 `amount` 代表总金额。每种硬币数量无限，可以任意凑，凑不出则无解。返回凑足总金额所需的**最少硬币数**。

**题目里的数据**：面额 `1、2、5`，总金额 `5`。这四种凑法中硬币数最少的是哪一种？

**解析**：正文里我们已经把这两道题的分岔点说清楚了——322 与 518 的解题思路差不多，只不过它最后求的不是"你有多少种凑法"，而是这些凑法里哪种需要的硬币数最少。还是沿用 `coins = [1, 2, 5]`、`amount = 5`，枚举出的四种凑法是：一个五分；两个两分加一个一分；一个两分加三个一分；五个一分。

**答案**：显然是不是第一种？它只要一个硬币就能凑足我的总金额，所以 322 题应该返回一，就是最少的硬币数需要一个。

练的时候把上一节那个暴力递归的骨架搬过来，把最后一环"返回解的个数"换成"在所有能凑成的路径里挑硬币数最少的那一条"就行了。

## 零钱兑换与哈夫曼树
> 对应块：BLK25 | 覆盖分集：P103-P106 | 块标题（分集名）：《进阶数据结构和算法-257-零钱兑换-递归》

### 从 518 到 322：把"有几种凑法"换成"最少几个硬币"

前面几节课我们啃的是力扣的 518 题：给你若干种硬币，你要凑成一个总金额，它问的是**一共有几种凑法**。

这节课我们再来看一道几乎孪生的题——力扣 322 题。题干跟 518 像得不能再像了：还是那几种硬币，还是凑同一个总金额，还是求"最少硬币数"。唯一变的是它要的结果：不是"有几种凑法"，而是在这若干种凑法里挑出一种，硬币个数**最少**的，然后问你需要几个硬币。

> **提示**：为什么说是"几乎孪生"？因为 518 和 322 的遍历框架基本一模一样——都是拿硬币数组去递归，每一枚硬币都试"用"与"不用"，直到剩余金额归零就记一种解。差的只是"记一种解"这个动作之后怎么办。

举个例子。还是 5 分、2 分、1 分三种硬币凑 5，我们都知道一共有四种凑法。那这四种凑法里，哪一种需要的硬币数最少？显然只用一个 5 分硬币就够了，硬币个数是 1。322 题要的就是这个数。

所以整套代码不用重写，我们只要在 518 的框架上做改动就行。这一节我们就把改动的地方拎出来，一个一个说清楚。

#### 多出来的一个静态变量

改动一，我增加了一个静态变量，它代表我们最终要求的最少硬币个数。

```java
static int min = -1;
```

初始值给的是 `-1`，为什么给 -1？因为题目里规定了 -1 代表没找到解。很好理解：假如我现在手里的硬币只有 2 分，而要求凑的总金额是 3，这就根本凑不成，那返回什么？返回 -1。

反过来，如果将来找到了解，就去更新这个值，它代表我们最终的最少硬币数。

#### 多出来的一个 count 参数，以及它为什么用 AtomicInteger

改动二，是给递归方法加了一个参数，就叫 `count`，它代表**某一种硬币组合中钱币的总数是几**。

什么意思？回到刚才那个 5、2、1 凑 5 的例子，一共有四种解。第一种组合的钱币数是 1，那我就把这个 1 记录到 `count` 里；第二种组合的钱币数是 3，我就把 3 记录到 `count` 里。这就是 `count` 的作用。

至于后面的两个参数——我加进去纯粹是为了把每种组合都打印出来，方便我们理解整个过程，属于辅助作用，把它们去掉也不影响这道题本身。

> **易错点**：`count` 跟前面那个 `min` 不一样，`min` 我是全程只读只写最后拿结果用的，`count` 却是每一层递归都要改的。所以它不能用 `int` 这种基本类型，也不用 `Integer` 包装类型，而是用了 `AtomicInteger`——一个可变的整数对象。

#### 进来自增，出去自减：count 数的是"当前这条路径"

`count` 在哪儿被改？进出各一次。

- 进入方法的时候执行一次 `incrementAndGet()`，相当于把 `count` 内部维护的硬币数加一、自增；
- 退出这个方法的时候执行一次 `decrementAndGet()`，相当于把它自减回去。

有同学问了：为什么进来要自增、出去要自减？

看递归流程就懂了。我们结合递归的执行流程图来看：首次调用时初始值是 -1，进入时 -1 加一，正好被初始化成零，从零开始数。继续往下递归的时候，再次进入时这个值被加一，说明"我又用掉了一枚硬币"，这样它就知道自己有一种组合、找到解了，需要几枚。

> **定义**：`count` 记录的其实是**当前这条递归路径上已经用掉的硬币个数**，而不是"总共找到了几种解"。这是理解自增自减的关键。

等 5 分这一路试完、这个方法调用结束了，是不是应该把 `count` 减一？减回零，是为了接下来执行下面那些组合时**再从零开始计数**。

举例：凑 5 的第二种组合是 2+2+1。第一次用到 2 分，硬币数从零加到一；第二次又用到 2 分，加到二；第三次用到 1 分，加到三。于是我们知道这第二种组合总共用了三个硬币。这轮递归走完，方法逐层退出，就逐层减回去，最后回到零，下次再尝试下一种组合。

一句话：进来自增是为了**正确计数**，出去自减是为了**正确归零**。这两个动作缺一不可。

#### 三种情况，以及更新最少的那段逻辑

剩下的代码跟 518 题几乎一样，方法内部也是分成三种情况：

- **剩余金额大于零**：说明还能凑，继续递归，这是第一种情况；
- **剩余金额等于零**：说明找到解了，把这时候的 `stack`（也就是当前这条路径上的组合）打印出来；
- **剩余金额小于零**：表示这条路走不通、凑过头了，属于无解。322 题里无解不需要额外处理，所以我干脆没把这个 `else` 写进来。

无解的时候，`min` 这个静态变量始终没被更新，它最终就还是 -1。

找到解的时候，就要更新 `min`，逻辑落在这两行上：

```java
if (min == -1) {                          // 找到的是第一个解
    min = count.get();                     // 无所谓有没有更小的，直接记下
} else {                                   // 说明之前已经有解了
    min = Math.min(min, count.get());      // 之前的解和当前的解，挑硬币数更小的
}
```

为什么第一个解可以直接赋值？因为它前面根本没有解，当前这个就是最好的，谈不上"挑一个更小的"。等到后面再找到解，才需要在"之前的解"和"当前的解"之间挑一个硬币数更小的去更新。

所有递归执行完，最后返回这个静态变量，就是我们最终要的最少硬币数。

#### 跑四组数据看看

代码写完，我们直接拿数据验证。

- **5、2、1 凑 5**：四种凑法全部打印出来，最终最少硬币数是 1，也就是只用一个 5 分硬币。
- **2、1 凑 3**：面额只有 2 分和 1 分，怎么也凑不出 3，最后返回 -1。
- **15、10、1 凑 21**：能看出六个 1 加一个 15 能凑成 21，一个 1 加两个 10 也能凑成 21，一共四种凑法，硬币数最少的是哪一种？显然是 10+10+1，只需要三个硬币。
- **25、10、5、1 凑 41**：这一组凑法就非常多了，但最少的那个是四个硬币各取一个——25+5=30，30+10=40，40+1=41，四个硬币就够了。

到这里，这道题的暴力递归解法就算做完了。但它仍然是暴力递归，我们接下来用贪心算法优化它。

### 用贪心再解一次

#### 十八块钱，先备三个五分

换一个例子。总金额是 18，硬币种类还是 5 分、2 分、1 分，要求硬币数最少，该怎么做？

我们最自然的想法就是——**从大面值的硬币开始去凑**。

为什么？因为五分硬币看起来"好像快凑够了"，比你从 1 分开始凑肯定要经济。虽然 18 个 1 分也能凑足 18，但硬币数一下子就上去了。所以我们应该从大面值的硬币开始，往总金额凑。

我们可以准备三个 5 分硬币，15 分，还差 3 分。这个 3 分怎么凑？用一个 2 分硬币，剩 1 分，最后再准备一个 1 分硬币就够了。剩余金额归零，凑齐了。总共用几个硬币？3+1+1 = 5 个。

那其他凑法还用看吗？其实就不用看了。我们用之前的穷举办法把所有凑法都列出来对比一下，可以看到凑法非常多，但从结果上大概能看出来，硬币数最少的就是这五个硬币的组合——三个 5 分、一个 2 分、一个 1 分。

所以我们这个从大往小凑的思路确实能得到一个正确的结果，而且**只用了一次就完成了**，后续再不用去试其他组合。

这个思路，就是贪心思路。

#### 贪心的两条原则

我们回忆一下贪心的两个原则。

**第一个原则：每次去做处理的时候，都要选取当前的一个最优解。**

对照刚才的算法。第一步我为什么选 5 分硬币，不选 2 分、不选 1 分？因为在第一步这个位置上，选 5 分硬币硬币数肯定是最少的，这属于当前的一个最优解。等我第三次循环以后，第四次为什么不再选 5 分硬币了？因为再选 5 分就是 15+5=20，超过总金额 18 了，肯定不行。于是退而求其次选谁？选 2 分。那为什么不选 1 分？显然在第四步这个情况下，选 2 分肯定比选 1 分硬币数更少。所以很明显，我们体现了第一个原则。

**第二个原则：向前看，别回头。**

什么意思？我们前面已经选中了三个 5 分硬币，接下来要跟剩下的 2 分、1 分硬币去做组合。但我会不会为了找出所有的可能，再退回去，比如说我选中两个 5 分硬币，然后呢再跟 2 分、1 分的硬币做组合呢？不会了吧。相当于这三个 5 分硬币如果已经选定了，它们三个就不会再动了，不会再倒回去了——这就是"向前看，别回头"。

> **定义**：贪心只顾眼前，之前选中的结果就算定下来了，不会再变。你要是能倒回去，那就不叫贪心了。

#### 原则二翻车之一：21 块钱，凑出七个硬币

但是，"向前看别回头"这个原则，会导致我们的贪心解法**有可能得到一个错误的解**。我们举两个例子。

第一个：总金额换成 21，硬币种类是 15 分、10 分、1 分。

按贪心算法怎么凑？首先你得来一个最大的 15 分硬币。剩余金额是 6。接下来 6-10 显然是负数，这个 10 分用不上对吧？那我就去凑 1 分，六个 1 分硬币凑成 6，剩余金额变成零。总共用几个硬币？六个 1 分加一个 15 分，结果是**七个硬币**。

但这个结果对吗？其实不对。我们肉眼都能看出来：如果你用两个 10 分硬币，再加一个 1 分硬币，是不是也能凑成 21？20+1=21，它只需要**三个**硬币就行了。

所以我们看到，虽然用了贪心，却因为回不了头，发现了一个更糟的结果——你的七个硬币比人家最优的三个硬币要多很多。

#### 原则二翻车之二：20 块钱，直接无解

第二个例子：总金额是 20，硬币面额只有 15 和 10 两种。

按贪心原则走：首先我准备一个 15 分硬币，剩余金额 20-15 是 5。但是由于我们不能回头看了，所以这个 15 分硬币就定下来了。在 15 分定下来的基础上，10 分硬币根本凑不足我剩下的 5 分。

所以我们发现，如果这里用贪心算法，它就**无解**了。

但实际上有没有解？有解。如果能把这个 15 倒回去、不用这个 15 分硬币了，那我用两个 10 分的硬币，是不是就直接凑出 20？

所以你看，上一个例子里是没倒回去，导致得到了一个更差的解；这一个例子里是没倒回去，直接变成了无解。如果能倒回去，从 10 开始去凑，是不是就能得到更少的硬币数？

#### 那现实里的货币系统会有这种面值吗

大家也不用太过担心。为什么？因为一个正常的货币系统，它不会设计出 15、10、1 这几种面值的硬币——它肯定是更为合理的 5、2、1 这种面值，实际在各个国家的货币系统里应该不会存在。这是我们贪心算法的问题，大家也要知道。

#### 动手写：两个变量加一个降序 for

好，接下来我们用贪心的解法去求解 322 题。

先提前说明一点：贪心解法**速度很快**，但前面也说了，它有可能得到错误的解。如果你给出一些不太好的面值硬币组合，它就有可能得到错误的结果。所以这个贪心解法求解 322 大家自己玩玩就行了，扔到力扣上去跑，肯定有些测试用例通不过，这一点要知道。

现在讲贪心最重要的原则：每次循环时都要找到这次循环的当前最优解。我们前面分析过，最优解实际上就是——**找到面值最大的那枚硬币**，用剩余金额减掉它，将来凑出的硬币数肯定是这一次最少的。

先做准备工作，准备两个变量：

- 一个是 `reminder`，代表我们的剩余金额，初始值是 `amount`；
- 另一个是 `count`，顾名思义就是我们最后这个硬币的数目，初始值是 0。

然后对 `coins` 数组做一个循环，这个循环应该是**由大到小**，按面值由大到小依次处理。这里我假定传入的数组已经按由大到小排好序了，我就不自己去做降序排序了——因为 Java 里基本类型的 int 数组做降序排序比较麻烦，我懒得写成代码。所以假定它传过来的顺序就已经是由大到小排好的。

循环内的代码怎么写？第一次进来时 `reminder` 是 18，遍历出的第一个硬币是面值最大的 5。只要剩余金额大于这个 5，我们就减掉它，硬币计数加一。

但是第二次循环，如果像这样写，`coin` 就变成 2 了；我们现在希望先把所有的 5 尽可能处理完，再处理面值为 2 的硬币。怎么写呢？其实我们只要把这里的 `if` 改成一个 `while` 循环就行了。

```java
static int coinChange(int amount, int[] coins) {
    int reminder = amount;   // 剩余金额
    int count = 0;           // 硬币总数
    for (int coin : coins) { // 假定 coins 已按面值由大到小排好序
        while (reminder > coin) {
            reminder -= coin;
            count++;
        }
        if (reminder == coin) {  // 查漏补缺：正好被当前硬币凑足
            reminder = 0;
            count++;
            break;                // 找到解，直接退出外层 for
        }
    }
    return reminder > 0 ? -1 : count;
}
```

走一遍 18：18 大于 5，`reminder` 减成 13，`count` 变成 1；下次再进 while，13 也大于 5，再减成 8，`count` 变成 2；再循环，8 仍然大于 5，又减成 3，`count` 变成 3，也就是找到了三个 5 分硬币。下次 `reminder` 是 3，3 就小于 5 了，相当于 5 分的硬币就算找完了，接下来去处理外层循环里的 2 分硬币。

#### 查漏补缺的那个 if

这里有个特殊情况必须考虑。比如总金额是 15。

一开始定出来的最大面值还是 5。15 大于 5，进入 while 循环，减掉 5，剩余金额变成 10，`count` 从 0+1 变成 1，也就是找到了第一个 5 分硬币。第二次再循环，10 仍然大于 5，又进 while，剩余金额减成 5，`count` 加成 2，也就是找到了两个 5 分硬币。

但是大家注意看，我这儿**故意把这个比较条件写成了大于号**。所以第三次再循环时，剩余金额是 5，5 大于硬币 5 吗？这个条件就没成立，相当于他就没有再进入这个 while 循环。

那没进 while，下面是不是又走外层这个循环了？下次处理的是 2 分硬币。这就不对了——因为我们发现，待会儿我们如果再循环一次，循环到第三个 5 分硬币的时候，15 就正好凑足了。

所以我们要在 while 循环结束以后，加一个查漏补缺的部分，也就是加一个 `if` 条件：看这个剩余金额是不是能被当前这个硬币凑足。如果他俩相等，就表示正好凑足。剩余的是 5，当前处理的硬币金额也是 5，那就凑足了。凑足以后剩余金额就可以更新成零，相当于找到解了，这时候 `count` 也应该加一。

找到解了，还要不要进入下一轮循环去处理那个 2 分硬币？不需要了吧。所以走到这个 `if` 里、找到解，我们就可以 `break` 退出外层的 for 循环。

退出外层循环以后，又分两种情况：

- `reminder` **大于零**：不管是从 `if` 退出的还是从 `for` 退出的，只要 `reminder` 大于零，说明没凑够，应该返回 -1，等于零才是表示凑够；
- `reminder` **等于零**：说明凑够了，返回 `count` 就可以了，因为 `count` 就是我们的硬币数。

#### 为什么判断不写在 while 里面

这段代码我再啰嗦两句解释一下。有些同学问了：为什么不把那个等于的条件写在 while 循环里，在 for 循环内部去处理凑足的情况，也就是 `reminder` 被减成零的情况？

是因为如果你在 while 里发现 `reminder` 被减成零，就表示找到解了；找到解我们希望退出这个循环。那如果我在这里写一个 `break`，它退出的是哪个循环？是不是退出的是这个 while 循环，它并不能退出最外层这个 for 循环啊。那你就得写一个比较不好的、跳出循环的语句——所以我不想用这种办法，采取了一个折中的办法：把代码分成两部分，一部分 while 循环，一部分是收底的这个 `if` 判断。这是我为什么这样写的原因，大家要知道一下。

#### 十八块钱再走一遍

最后回到最开始总金额是 18 的例子，我们把执行流程再分析一遍。

- 一上来处理最大面值的硬币，是 5。18 大于 5，进入 while，做减法更新成 13，`count` 加一变成 1。
- 第二次又能进入循环，13 再减 5 变成 8，`count` 被更新成二。
- 第三次还能进来，8 再减去 5 变成 3，`count` 被更新成三。
- 第四次，3 小于 5，条件不成立，凑不足了，while 循环不执行。
- 看一下是不是真的凑足了：这时候 3 并不等于 5，所以得继续尝试面值更小的硬币，这个 `if` 条件没成立，再次进入外层循环，处理面值为 2 的硬币。`reminder` 是 3，3 大于 2 成立，进入 while，减去变成剩余金额 1，`count` 更新成四。
- 1 大于 2 吗？不大于，所以 while 循环就不再执行了。当然 1 也不等于 2，相当于没有找到解，再次进入外层循环，去尝试面值 1 的硬币。
- 最后一次，1 不大于 1，所以没有进 while 循环，但我们有个收尾的 `if`：剩余金额 1 == 1 成立，说明找到解了，这时候把 `reminder` 更新成零，`count` 加加变成五。
- 最后 `break` 退出外层的 for 循环，执行到最后的判断：`reminder` 等于零，说明找到解了，就 `return` 这个 `count` 就可以了。

也就是最终硬币的最少硬币数是五个。

跑一下实际效果：18 这组，找到的最小硬币数是 5。再换一个，25、10、5、1 凑 41，最少硬币数是 4，每个硬币各取一个正好凑 41。下面这个用两个面值为 2 的硬币凑 3，怎么也凑不到，所以返回 -1。

再看两个我们有问题的情况：第一个，15、10、1 凑 21，按我们现在的算法凑出来的最少硬币数是 7，但实际上两个 10 加一个 1 只需要三个硬币——这是贪心算法得出错误结果的一种情况。最后一个，15 和 10 去凑 20，贪心结果得出的是无解，但我们也知道用两个 10 是能凑足的，所以它是有解的。

至此，贪心算法的求解以及它最后的一些例子，就给大家演示到这里。

### 哈夫曼树：出现得越多的字符，编码越短

#### 编码就是字符和数字的对应关系

这节课我们来学习一个知识，叫哈夫曼编码，也叫霍夫曼编码。

那么什么是编码呢？其实我们计算机里并不能直接存储字符。你要往计算机里存字符，其实都是存一个数字。所以编码的目的，就是建立**字符和数字的一个对应关系**。

比如大家熟知的 ASCII 编码表，它就建立了我们一些常见的英文字符、包括一些英文符号跟数字的对应关系。比方说大写的字符 A，它对应的 16 进制数字就是 41——咱们看，这张表横轴是 4，纵轴是 1，加起来就是 41。大写字符 B 对应的就是 42 这个 16 进制数。

这样我们就知道了字符跟一个数字的对应关系。将来计算机如果真的要存储这个字符了，它实际上存的就是 42；将来读取的时候也是类似，比如它读到了一个 42，那它要把它恢复成字符显示出来，它就再查这张表——42 原来对应的是一个大写的 B，它就把这个 B 显示出来。

这就是我们编码的一个含义。

#### 十个字符，二十个字节

刚才我们介绍了什么是编码表——就是建立字符和数字的对应关系。但是有的时候，我们可能需要不同的编码表。为什么呢？我们举一个例子。

大家都知道 Java 中是用 `char` 类型来代表一个字符的，那这个 `char` 类型，每个字符是不是固定都是两个字节？现在我想把这些字符进行一个传输，传输到另外一台计算机。你是不是得先把字符编码成数字，然后进行传输？如果我还是采用上述的规则，就是每个字符两个字节，这样传输一个 A、两个 B、七个 C 这十个字符，需要多少个字节？

我们还是按刚才这张表去查。比如 A 对应的数字是 16 进制的 61——横轴是 6，纵轴是 1，加起来 61。但是注意，Java 中这个 61 你得前面再带一个 00，也就是 0061。每个字符要占两个字节，00 占一个字节，61 占一个字节，总共两个字节代表这里的 A。类似的，两个 B 我们就用两个 0062，下面七个 C 就来七个 0063。

将来我要传输的时候，把这么多的字节传输过去就行了。当然我这都是用 16 进制表示。一共多少个字节？每个字符两个字节，十个字符就是 **20 个字节**。

你觉得效率高吗？肯定占用的字节数太多了，不经济。所以接下来我们想一想，有没有办法改进——就是让传输时采用别的编码表，让传输的字节数更少，更节省流量。

#### 手工设计一张编码表：省了字节，却解不回来

我们先做一个假设：假设我们传输的字符种类比较少，就 A、B、C 这三种字符，也就是我们前面这个例子，没有其他字符了。

有的同学就重新设计了一张二进制的编码表。他怎么表示的呢？他用一个二进制的 0，就是一个比特位，来表示一个字符。A 可以用二进制的 0 来表示，B 用 1，C 用二进制的 10。你看这样是不是比较节省？一个比特就能表示一个字符，C 呢也只是用了两个比特。

我们还是传递一个 A、两个 B、七个 C 这 10 个字符，那总共需要多少比特？算一算：一个 A 就是 0，两个 B 是两个 1，前面这两个一共 3 个比特；后面七个 C 是七个 `10`，七个 `10` 是不是 14 个比特？14 + 3 = **17 个比特**。一个字节是 8 个比特，17 个比特也就是两个字节多一点。

你看这个字节是不是节省了很多？原来那种编码需要 20 个字节，现在我只需要两个字节多一点，一下子缩小了十倍。好像挺好，对不对？

**但我们这样去编码行不行呢？** 大家思考一下。

答案是不行。因为我们不光要考虑编码，我们还得考虑**解码**——也就是我得把这个数字序列能还原成它原来的这些字符。那我们反过来试一试。

你看刚才我们编码后的结果，是这么一堆二进制的数字。计算机遇到了第一个 0，是不是可以把它还原成 A？没问题。接下来又遇到了一个 1，能把它还原成 B。再遇到一个 1，还原成 B。前三个字符都正确还原了。

不过接下来咱们看行不行。它遇到了一个 1，但它不会那么聪明，把 `10` 连在一起去看——它遇到 1 就把它翻译成 B 了。接下来又遇到一个 0，是不是又把它翻译成 A 了？这就翻译错了。本来这个 `10` 如果连在一起看，我们应该把它翻译成 C，结果现在错误地把它翻译成了 `ba`。那如果他把所有的结果都翻译完，就会得到最后有七个 `ba`——而我们最后要的是原始字符，是七个 C。结果翻译错了，这就不对了。

> **结论**：这个问题的本质在于——我们得让计算机翻译的时候，能够把编码后的数字区分开，让它们互不冲突、互不干扰。

#### 用二叉树来编码：向左 0，向右 1

怎么去区分编码后的数字呢？这里我们需要用到一种二叉树的结构来去编码，就可以保证前缀不重复了。

而且这个二叉树的结构是一种叫**满二叉树**的结构。什么叫满二叉树？就是每个节点它左右孩子都存在，不存在"只有一个孩子"这种情况。当然叶子节点就可以没有孩子。

```text
          o
        /   \
       o     o
      / \   / \
     o   o o   o     <-- 叶子节点可以没有孩子
```

我们待会儿用这棵树来编码，就能确保我们的前缀不会重复，也就是编码后的数字不冲突。

具体看这个例子，它的规则是：**向左走就取一个数字 0，向右走就取一个数字 1**。什么时候走到叶子节点了，那么就能得到这个字符的编码——我们每个叶子节点其实都存储着这些字符，走到叶子节点时，这个路径里累计起来的 0 和 1 加在一块儿，就是这个字符的二进制编码。

举几个例子大家就明白了：

- 找 A 的编码：只需要向左走一步就走到 A 了，它经过的这一步是向左走的，取到的数字是 0，所以 A 的编码就是 0。
- 找 B 的编码：向右走一步、再向左走一步找到 B，整个路径中这些数字累计起来是 `10`，所以 B 的编码就是 `10`。
- C 的编码则是 `11`。

对应到树上就是这样的结构：

```text
            o
          /   \
         o     o
        / \     \
       a   b     c

    a = 0
    b = 10
    c = 11
```

我们按现在这个情况去编码：A 是 0，B 是 `10`，C 是 `11`，最终它就不会冲突，将来就能正确地解码。

我们还是传递一个 A、两个 B、七个 C 这 10 个字符，它会编码成什么样子呢？A 编码成了一个 0，B 编码成了两个 `10`，最后 C 编码成了七个 `11`。总共的字节数并不多：1 + 4 + 14 = **19 个比特**，也是两个字节多一点。

关键是我们这样编码能不能正确地解码。我们来看：

- 先遇到的 0 跟其他的有没有歧义？没有歧义，所以它只能被翻译成 A，解码成 A。
- 接下来遇到一个 1，这个编码表中有单独的 `1` 吗？没有。因为你只走一个 1，你没走到头，还没走到叶子，说明这个 `1` 不能翻译成一个字符，所以它得接着向后继续走。接下来再找到一个 0，是不是走到头了？`10` 就能走到头，走过头能够把它翻译成 B，也不会跟其他的干扰。
- 接下来又是一个 `10`，翻译成 B。
- 接下来的 `11` 是不是翻译成 C？因为 `11` 走到头了，它应该被解码成 C。后续的都没有问题，都可以正确地把这些 `11` 解码成 C。

这回我们的解码确实是没有问题了。

#### 十九比特，能解了，但还是不够短

但是呢，它编码后生成的这些数字并非是最少字节。

为什么？你就想，C 的出现频次是不是最高？因为 C 出现了七次，而 A 这个字符只出现了一次。所以我如果把 C 编码成 0 是不是更好？它要编码成 `11`，得占用 14 个比特；但是它要编码成 0 的话，只需要占七个比特。所以我们把那些出现频次高的字符编码成更短的数字，是不是更划算呀？

#### 频次高的走左边：哈夫曼树登场

所以呢，我们就有了下面这棵树。这棵树频次高的字符数字更少，频次低的字符数字更多——你看 A、B 是不是都需要两个数字，而频次高的 C 它只需要一个数字。

```text
            o
          /   \
         o     c
        / \
       a   b

    a = 00
    b = 01
    c = 1
```

我们刚才那些原始字符，用 `00` 表示 A，`01` 表示 B，最后一个 `1` 表示 C。

这样我们再来看一下编码：刚才这十个字符会怎么样呢？A 变成了 `00`，然后两个 B 是 `0101`，最后七个 C 是七个 `1`。

总共用了多少个比特呢？前面这是 6 个比特，加上后面的 7 个比特，**总共只有 13 个比特**，比我们之前的 19 个比特少多了。13 个比特就是一个字节多一点，不到两个字节。

所以这种是不是最好啊？这种最好的解法我们有一个称呼，把这棵树称之为**哈夫曼树**，就是我们今天的主题。用这棵树对我们的字符和数字进行编解码，我们就称之为**哈夫曼编解码**。这就是我们哈夫曼的由来。

> **提示**：整条思路其实是一句话——**让出现频次越高的字符，在树上的位置越靠近根，它的编码就越短**。因为所有字符的编码总长度，就是所有叶子的深度之和。让重的叶子浅一点、轻的叶子深一点，总长度才会最小。20 字节 → 17 比特（手工表，解不出来）→ 19 比特（树，解得对但不是最优）→ 13 比特（哈夫曼树），这条路就是不断往这个方向逼近的过程。

## 哈夫曼树：从"给两个节点找个爹"到算出编码占了多少比特
> 对应块：BLK26 | 覆盖分集：P107-P110 | 块标题（分集名）：《进阶数据结构和算法-261-Huffman-Tr》

先把例子摆出来，还是那个用了好几遍的字符串：`a` 出现 1 次，`b` 出现 2 次，`c` 出现 7 次。

前面我们论证过一句话——**频次高的，希望它的路径短；频次低的，希望它的路径长**。这句话听着顺，但怎么让程序真的干出这件事来？这节课就把这句话变成一行行代码。

我把整个构建过程分成了四步，我们逐一来看。

### 四步动作，一个循环

第一步，统计每个字符的出现频率，然后把这些字符以及它们的频率放入优先级队列。拿我们的例子来说，就把 `a:1`、`b:2`、`c:7` 塞进队列。

> **注意**：这个优先级队列里，我们认为**频次低的优先级更高**。所以在这个例子里，优先级最高的就是 `a:1`。别搞反了。

第二步，循环开始。每次从队里取出**两个频次最低的元素**。眼下最低的就是 `a:1` 和 `b:2`，把它们出队。

出队之后干什么？给这两个元素**找个爹**——`a:1` 当左孩子，`b:2` 当右孩子。爹的频次记成**两个孩子频次之和**，也就是 $1 + 2 = 3$。

第三步，把这个新造出来的爹重新放回队列。

第四步，重复这个步骤。队列里现在剩 `3` 和 `c:7` 两个，还是它俩出队，再找个爹，频次记成 $3 + 7 = 10$，然后放回队列。

循环什么时候退出？**当队列里只剩一个元素的时候**——没有两个可取的了，我们就停下，把这唯一剩下的元素出队，它就是我们最终的哈夫曼树的根节点。整棵树构建完成。

```text
第 1 轮：出队 a:1, b:2   →  新建父节点 (3)   →  放回队列
         队列：[c:7]  [(3)]

第 2 轮：出队 (3), c:7   →  新建父节点 (10)  →  放回队列
         队列：[(10)]

剩 1 个元素：出队 → root = (10)
```

最终的树长这样：

```text
              (10)
             /    \
           (3)    (7)
          /   \     |
        a(1) b(2)  c(7)
```

读图：根节点频次 10，左孩子是 3、右孩子是 `c:7`；3 的两个孩子是 `a:1` 和 `b:2`。注意 `c` 一路向右只走了 1 层，而频次最低的 `a` 走了 2 层——这就是"频次低的路径长"落地后的样子。

### 为什么要给它俩"找个爹"

有同学问了：我们为什么要给 `a:1` 和 `b:2` 找个爹呢？

你回头想一下，给他俩找了个爹，说明它的路径是不是变得更长了？而我们前面论证过，频次低的我们希望它的路径长。找了个爹，自然就加了一层路径。这正是我们要的效果。

**找爹的目的，就是让频次低的字符在树上多挂一层，从而拥有更长的编码。**

### 先把要交付的功能列清楚

树建出来只是第一步，接下来还有几件事要做，一共四件：

1. **构建哈夫曼树**：根据一个原始字符串，把这棵树创建出来。
2. **找到每个字符对应的数字编码**：在这个例子里，`a` 全程向左走，所以编码是两个 `0`；`b` 先左后右，编码是 `01`；`c` 编码是 `1`。
3. **统计比特数**：原始字符串编码之后，一共占用多少个比特。
4. **编解码**：把原始字符串编码出去，再能正确还原回来。

第 4 件的效果大概长这样：原始串里，`a` 被编码成 `00`；两个 `b` 被编码成两段 `01`，也就是 `0101`；七个 `c` 被编码成七个 `1`。解码只要能把它正确还原回来就行。

### 节点类：叶子上存字符，父节点上存频次

在动手之前，先把工具准备好。哈夫曼树的本质也是一棵二叉树，而构建二叉树我们学过两种做法：

- 一种是定一个节点对象，里面有左孩子、右孩子，还可以存一些数据值——比如存它是哪个字符、出现频次是多少；
- 另一种是用数组来存树中每个节点。因为哈夫曼树是**满二叉树**，满二叉树的性质跟之前学过的堆的那种完全二叉树的性质是类似的，所以用数组也能构建。

这里我选择第一种，建立一个节点对象。

节点类里需要什么属性？一个是 `Character ch`，存对应的字符——不过对父节点来说这个字符可以不存，存个 `null` 也行；一个是频次，就用缩写 `frequency`，不过我后面会把它改名；再来 `left` 和 `right`，这两个孩子是必须的。

最后还有 `code`，记录它对应的实际编码，比如 `a` 是 `00`、`b` 是 `01`、`c` 是 `1`。

> **提示**：这里我用 `String` 作为编码字段，是为了拼接方便。实际编码应该是一串 0 和 1 的二进制位，实现起来会复杂一些。我们这里简化，用字符串存储 `0`、`1` 来表示。

构造方法加两个：一个根据字符来构造（叶子节点用），另一个根据频次和左右孩子来构造（父节点用）。

另外提供一个判断是不是叶子的方法——**看它有没有左孩子**，左孩子是 `null` 就表示它是叶子。比如 `a`、`b`、`c` 都没有孩子，所以是叶子；而 3 和 10 的左孩子不为空，所以是非叶子。

> **易错点**：有同学问，只判断左孩子够不够？**够的**。因为哈夫曼树是满二叉树，它有左孩子，肯定也同时会有右孩子，所以我们判断一个就够了。

```java
public class Node {
    // 字符
    private Character ch;
    // 频次
    private Integer freq;
    // 左孩子
    private Node left;
    // 右孩子
    private Node right;
    // 编码
    private String code;

    // 叶子节点：根据字符构造
    public Node(Character ch) {
        this.ch = ch;
    }

    // 父节点：根据频次 + 左右孩子构造
    public Node(Integer freq, Node left, Node right) {
        this.freq = freq;
        this.left = left;
        this.right = right;
    }

    public Integer freq() {
        return freq;
    }

    public void setFreq(Integer freq) {
        this.freq = freq;
    }

    public String getCode() {
        return code;
    }

    public void setCode(String code) {
        this.code = code;
    }

    // 满二叉树，有左孩子必然也有右孩子，所以只看左边就够了
    public boolean isLeaf() {
        return left == null;
    }

    @Override
    public String toString() {
        return "Node{ch=" + ch + ", freq=" + freq + "}";
    }
}
```

`get` 方法、`toString` 这类样板代码大家自己补全一下。我这里 `toString` 打印的就是字符和它的出现频次。

> **提示**：我比较器的写法用的是方法引用，看到 `getFrequency` 这个名字我就烦，所以把这个方法稍微重构了一下——前面的 `get` 不要了，首字母 `f` 改成小写，就叫 `freq()`。

### 统计频次：一个 Map 搞定

先实现第一个功能：统计每个字符出现的频次。

我们给外层的哈夫曼树类加一个构造方法，把原始字符串作为参数传进来，同时把它存成我们的成员变量——**编码时还要用到它**。

拿到原始字符串之后，调用它的 `toCharArray()`，拿到一个 `char` 数组，然后去遍历，字符串里的每个字符就遍历出来了。

那遍历出来以后，怎么统计出现次数呢？借助一个 `Map` 集合最简单，速度也快。我们准备一个 `HashMap<Character, Node>`，`key` 是字符，`value` 是对应的 `Node` 节点对象。这个 `map` 将来编码时也会用到，所以同样做成成员变量。

逻辑是这样的：先检查这个 `map` 中有没有这个字符；如果还没有，就把字符作为 `k`、新建的初始 `Node` 作为值放进去；如果已经有了，那就拿到它的 `Node` 对象，让它的频次加一。

#### 先看基础写法：containsKey 与 get

```java
public class HuffmanTree {
    // 原始字符串，编码时还要用到
    private String original;
    // key 是字符，value 是对应的节点，编码时还要遍历它
    private HashMap<Character, Node> nodes;

    public HuffmanTree(String original) {
        this.original = original;
        this.nodes = new HashMap<>();

        for (Character c : original.toCharArray()) {
            if (!nodes.containsKey(c)) {
                nodes.put(c, new Node(c));
            }
            Node node = nodes.get(c);
            node.setFreq(node.freq() + 1);
        }
    }
}
```

跑一下，`a` 出现了 1 次，`b` 出现了 2 次，`c` 出现了 7 次，结果全对。刚开始这几个 `Node` 对象就是叶子节点的状态，我们把它们打印出来，看看字符和频次统计对了没有。

#### computeIfAbsent 的等价写法

刚才这几行代码还有另一种等价写法，我更喜欢用 `computeIfAbsent`。

它接受两个参数：第一个参数就是我们要处理的 `k`，也就是这个字符；第二个参数是一个 `Function`，当你 `map` 中还没有这个 `k` 的时候，它就返回一个值。这个返回值我们可以用方法引用的格式写，就是 `Node::new`。

整行的意思就是：如果 `map` 中缺失了这个 `key`，就创建一个 `Node` 对象放进 `map`；如果没有缺失，就不会执行第二个参数里创建 `Node` 的操作，而是直接返回已有的值。

返回 `Node` 值以后，我们拿到这个 `Node`，直接去增加它的频次就行了。**两行代码就搞定了**，跟上面几行的作用完全一致。

```java
for (Character c : original.toCharArray()) {
    Node node = nodes.computeIfAbsent(c, Node::new);
    node.setFreq(node.freq() + 1);
}
```

### 排个队：PriorityQueue 加比较器

频次统计完了，接下来构造哈夫曼树。前面已经给大家看过一遍了，我们一条条来做。

第一步，把这些字符以及它们的频率放入一个优先级队列。咱们准备一个 `PriorityQueue`，队列里直接放 `Node` 节点对象就可以了——因为节点里面字符、频次都包括了，往这个队列里放节点就行。

创建好队列以后，把 `map` 中所有的节点都放进去。这里我们不自己写循环，直接拿到 `map` 的 `values`，把一个集合直接传给队列的 `addAll`，让它内部循环着放好。

> **注意**：别忘了给优先级队列一个**比较器**，来规定它的比较规则。现在我们想按节点的哪个属性来比？答案是**频次属性**，所以方法引用就是 `freq`。

```java
PriorityQueue<Node> queue =
        new PriorityQueue<>(Comparator.comparingInt(Node::freq));
queue.addAll(nodes.values());
```

到这里，所有节点就都进入队列了。接下来写循环。

循环条件是什么？每次都要出队两个元素，所以你得保证队列里至少有两个元素；什么时候队列里就剩一个元素了，就退出循环。所以条件是队列的 `size` **大于等于 2**。

第二步，每次出队两个频次最低的元素，调用两次 `poll`，第一个出队的叫 `x`，第二个叫 `y`。要给 `x` 和 `y` 找个爹，爹的频次就是两个孩子频次之和——先把频次算出来，然后创建节点对象，调用那个带三个参数的构造：第一个参数传频次，第二、第三个参数分别传它的左右孩子，`x` 是左、`y` 是右。

> **提示**：对于这种父节点对象，它的字符是什么就不重要了。因为只有叶子节点存的这些字符才有编码，父节点可以不存字符，所以它的字符即使是个 `null` 也完全没问题。

第三步，把这个父节点放回队列，调用 `offer`。

循环结束后，队列里就剩一个节点了，我们最后再做一次 `poll`，拿到的就是整棵树的根节点 `root`。

```java
PriorityQueue<Node> queue =
        new PriorityQueue<>(Comparator.comparingInt(Node::freq));
queue.addAll(nodes.values());

while (queue.size() >= 2) {
    Node x = queue.poll();
    Node y = queue.poll();

    // 爹的频次 = 两个孩子频次之和，x 是左孩子，y 是右孩子
    Node parent = new Node(x.freq() + y.freq(), x, y);

    queue.offer(parent);
}

Node root = queue.poll();
```

打个断点跑一遍：最终生成的 `root` 频次是不是 10？展开以后左孩子是不是频次 3 的那个父节点、右孩子是不是 `c:7`？再展开左边，两个孩子是不是 `a:1` 和 `b:2`？都对上了，说明这棵树已经正确生成。

### 走一趟树：路径就是编码

现在做第三个功能，计算每个字符的编码。

怎么做？对这棵二叉树做一次遍历，等遍历到叶子节点的时候，我们根据它一路走来的路径就知道它的编码了。

所以可以用一次**深度优先遍历**。深度优先遍历最简单的方式就是递归，我们写一个方法 `dfs` 用来递归，刚开始把根节点传给它。

#### 递归的骨架：叶子就是终点

先看递归的终点：**只要递归到叶子节点就可以返回了**。到达叶子节点时，就去做最终处理——找到它的编码。

如果不是叶子节点，比如这里的 3，我们就分别递归它的左孩子、右孩子。就这么简单。

#### 编码从哪来：向左记 0，向右记 1

那怎么知道编码是几位呢？先回忆一下深度优先遍历在这些节点中的行走顺序：从根节点开始先向左走，没走到头就继续向左走；向左走到头了，向回走；发现右边还有，就继续向右走；向右走到头了，也向回走；接下来回到根节点，发现右边还有一个，就再向右走；最后回来。

在这条路线里，我们可以利用一个 `StringBuilder`：刚开始它是空字符串。**向左走**就在尾部追加一个 `0`，继续向左走就再加一个 `0`，这样走到叶子节点，我们就知道 `a` 的编码是 `00`。**向回走**的时候，就把刚才加的那个 `0` 减掉。

如果又向前走，发现是向右走，这时候就该加个 `1`——所以走到 `b:2` 这个叶子节点时，我们就知道它的编码是 `01`。同理，`b:2` 向回走时把刚加的那个 `1` 减掉；当它从 3 这个节点回到 10 这个节点时，把最开始加的那个 `0` 也减掉。

**一句话总结：向回走就减掉一个字符，向前走就根据向左还是向右加上 `0` 或者 `1`。**

当它从 3 回到 10 时，`StringBuilder` 里的内容就减完了，发现右边还有一个，向右走就加一个 `1`，到达叶子节点，这时候知道 `c` 的编码是 `1`。再向回走就把刚才那个减掉。完了。

```text
          10
        /    \
       3      7
      / \     |
     a   b    c

动作              进入时 code    到达叶子时的 code
根 → 左(3)        ""              ""
  3 → 左(a)       "0"             "00"     ← a 落袋
  回溯(减末位)     "00"            "0"
  3 → 右(b)       "0"             "01"     ← b 落袋
  回溯(减末位)     "01"            "0"
回根(再减末位)     "0"             ""
根 → 右(c)         ""             "1"      ← c 落袋
  回溯(减末位)     "1"             ""
```

读图：编码就是从根到该叶子的路径上，每一步"向左记 0、向右记 1"拼出来的字符串——`a` 走了左左得 `00`，`b` 走了左右得 `01`，`c` 只走了右得 `1`。

写成代码非常简单：给 `dfs` 加一个参数，`new` 一个 `StringBuilder`，刚开始里面什么都没有，我们把这个参数就叫 `code`。

- 如果还没到叶子节点，向左走就在 `StringBuilder` 后面加一个 `0`，用 `append` 向尾部追加；
- 向右走就复制这一行，把 `append("0")` 改成 `append("1")`；
- 只要向回走的时候，也就是每次递归方法调用结束之后，就把最后面那个字符减掉。怎么减掉最后的字符？调用它的 `deleteCharAt`，找到它最末尾那个字符删掉就行。索引应该是 `code.length() - 1`，因为它的长度减一就是它最后那个字符。

```java
public void dfs(Node node, StringBuilder code) {
    // 递归终点：叶子节点
    if (node.isLeaf()) {
        node.setCode(code.toString());
        return;
    }

    code.append("0");
    dfs(node.left, code);
    if (code.length() > 0) {
        code.deleteCharAt(code.length() - 1);
    }

    code.append("1");
    dfs(node.right, code);
    if (code.length() > 0) {
        code.deleteCharAt(code.length() - 1);
    }
}
```

> **易错点**：最后这个 `deleteCharAt` 的索引要加前置条件——只有 `code.length() > 0` 时才删。因为当整趟遍历走到最外层回溯收尾时，`StringBuilder` 已经被减空了，这时候再执行 `deleteCharAt(code.length() - 1)` 等于去删下标 `-1`，会直接越界。加了这个前置条件，就保证它不出错。

调用一遍：`a` 对应的编码是 `00`，`b` 对应的编码是 `01`，`c` 对应的编码是 `1`，都正确。

#### 把编码存回节点，而不是打印

其实我们知道了叶子节点的编码以后，**不用把它打印出来**，把它记录到那个节点对象里就可以了——节点对象里我们不是专门留了一个 `code` 属性吗。

所以找到编码之后，我们就不打印了，直接把当前这个叶子节点的 `code` 值存成 `StringBuilder` 当前的 `code.toString()`。调用结束之后再统一打印：遍历 `map` 的 `values`，打印 `Node` 以及它对应的编码——编码刚才已经存进 `code` 里了，现在把它打印出来。这样第三个功能就算完成了。

### 顺手算一笔账：一共占多少比特

再做一个小的功能：统计这个字符串编码以后，总共占用多少个比特位。

思路我们前面就有了——每个字符的编码是多少、每个字符的出现频次是多少，都已经知道了。`a` 的编码是 `00`，出现 1 次，占用 $1 \times 2 = 2$ 个比特；`b` 出现 2 次、编码是 `01`，占用 $2 \times 2 = 4$ 个比特；`c` 出现 7 次、编码是 `1`，占用 $7 \times 1 = 7$ 个比特。最后把这些结果累加起来，就得到所有字符编码后总共占用的比特位：

$$\text{bits} = \sum_{\text{字符 } x} \text{freq}(x) \times \text{len}(\text{code}(x))$$

代入我们的例子：

| 字符 | 频次 | 路径 | 编码 | 编码长度 | 占用比特 |
| --- | --- | --- | --- | --- | --- |
| a | 1 | 左 → 左 | `00` | 2 | $1 \times 2 = 2$ |
| b | 2 | 左 → 右 | `01` | 2 | $2 \times 2 = 4$ |
| c | 7 | 右 | `1` | 1 | $7 \times 1 = 7$ |
| **合计** | **10** | | | | **13** |

要完成这个功能，代码还是在刚才那个深度优先遍历里做就行。

先定义一个变量 `bits`，初始为零。对叶子节点来说，它的值应该更新成**节点的出现频次乘以编码的长度**——这就是找到一个字符占用的比特数。

> **易错点**：有同学问，在这个位置直接 `return` 这个比特数可不可以？**注意不行**。如果你在这里就 `return` 了，那么下面那个删除字符的操作就不执行了。所以我们这里先不能着急 `return`，得在方法的最后再 `return`。另外，这个方法的返回值类型也要跟着改成 `int`。

对叶子节点来说，比如 `a` 返回 $1 \times 2 = 2$；`b` 这边是两个 `b` 字符、编码长度也是 2，返回 $2 \times 2 = 4$。

对于这种**非叶子节点**，它应该累加由它的两个子节点返回的数——比如 3 这个节点的 `sum` 初始是零，但它得负责把 `a` 返回的 2 和 `b` 返回的 4 加起来。所以非叶子节点这里要做的是一个累加操作。

```java
public int dfs(Node node, StringBuilder code) {
    int bits = 0;

    if (node.isLeaf()) {
        // 叶子：频次 × 编码长度
        bits = node.freq() * code.length();
        node.setCode(code.toString());
    } else {
        code.append("0");
        bits += dfs(node.left, code);
        if (code.length() > 0) {
            code.deleteCharAt(code.length() - 1);
        }

        code.append("1");
        bits += dfs(node.right, code);
        if (code.length() > 0) {
            code.deleteCharAt(code.length() - 1);
        }
    }

    // 只能在方法最后 return，否则上面的回溯删除就执行不到了
    return bits;
}
```

测试一下，把返回值拿过来打印：总共占用 13 个比特。`a` 占 2 个，`b` 占 4 个（$2 \times 2$），`c` 占 7 个，加起来正好 13，正确。到此为止，第四个功能也实现完毕。

## 局部最优怎么堆成全局最优：哈夫曼编解码、活动选择与分数背包
> 对应块：BLK27 | 覆盖分集：P111-P114 | 块标题（分集名）：《进阶数据结构和算法-265-Huffman-Tr》

### 编码：一趟遍历就够了

哈夫曼树的代码写到这儿基本就完工了，最后补两个功能：编码和解码。

先看编码，你会发现它简单得有点意外。因为在构造这棵哈夫曼树的时候，我们已经把原始字符串存进成员变量了——构造过程本身就得先拿到原始字符串才能统计频率。所以编码的时候根本不用重新分析频率，只要把整个字符串再遍历一遍就行。

遍历的时候问每个字符一句：它的编码是不是已经知道了？`a` 的编码、`b` 的编码、`c` 的编码，在建树的过程中全部都已经算出来、并且塞进 `map` 集合里了，怎么查？把当前字符作为 key 去 `map` 里找，拿到的 value 就是一个节点对象，而这个节点对象里我们专门留了一个属性存这个字符的编码，所以直接调它的 `code` 就拿到编码了。

每个字符的编码都有了，最终只要把这些编码拼到一块儿就完事。准备一个 `StringBuilder` 做拼接，循环走完 `return sb.toString()`。

```java
public String encode() {
    StringBuilder sb = new StringBuilder();
    char[] chars = source.toCharArray();
    for (char ch : chars) {
        Node node = map.get(ch);
        sb.append(node.code);
    }
    return sb.toString();
}
```

测试一下。原始字符串先得到这棵哈夫曼树，再调用它的 `encode` 方法，结果是这样的：

```text
原始字符    a       b       b       c       c
字符编码    00      01      01      111     111
-----------------------------------------------
拼接结果    000101111111
```

`a` 编码成 `00`，接下来两个 `01` 是对应的 `b`，最后六个 `1`（两个 `111`）对应的是两个 `c`。

> **易错点**：这里 `a` 拿 `00`、`b` 拿 `01`、`c` 拿 `111`，全长 13 位——记住这个长度，下面踩坑的时候要用。

> **提示**：编码函数返回的是字符串，但严谨地讲，编码应该返回一个二进制数字，数字里存的是 `0101` 这些位。这里为了简单，才退化成"字符串里存着 0101"。

### 解码：跟着比特流在树上走

解码就是把我们刚才编码出来的 `0010`、`0010` 这些位依次处理，找到它们原本对应的字符。工具还是那棵哈夫曼树——**从根节点出发，拿比特当路标往下走**。

规则特别简单：遇到 `0` 就向左走，遇到 `1` 就向右走。

拿实际的比特串走一遍就明白了：

- 第一个 `0`：从根节点向左走一步，索引 `i` 自增。没走到头，还不是叶子，那就继续处理下一个数字。
- 第二个 `0`：再向左走一步，`i` 又自增。这回走到头了——当前节点是叶子，说明这两个 `0` 找到了一个对应的字符，就是这个叶子节点上的 `a`。
- 找到一个字符以后，把当前节点**重置为根节点**，再从根开始处理后面的数字。
- 接下来又是一个 `0`，向左走一步，`i` 自增，没走到头；接着遇到 `1`，同样先 `i` 自增，加完以后发现走到头了——又找到一个字符 `b`。所以这两个位 `01` 对应的是 `b`。
- 以此类推，剩下的位就能全部转换成对应的字符。

整个循环的骨架就是这么个状态转移：

```text
  node = root
      │
      │   i < chars.length 就继续转
      ▼
  node 非叶子 ──── 是 ────► append(node.ch)，node = root ──┐
      │                                                    │
      否                                                   │
      ▼                                                    │
  '0' → node.left    '1' → node.right                      │
      │                                                    │
      ▼                                                    │
  i++ ────────────────────────────────────────────────────►┘
```

准备阶段的代码架子是这样的：先把解码字符串也当成字符处理，拿到 `char[] chars`；准备一个索引 `i`，因为我们是一个字符一个字符往下啃的，处理过程肯定得循环，循环条件就是 `i < chars.length`——`i` 等于数组长度时说明处理到头了，就退出；最终结果又要拼回字符串，所以最外层还是准备一个 `StringBuilder`。

> **提示**：解码的入参按理也该是一个二进制数字，把数字的每一位逐一处理。现在同样为了简化，还是当作字符的 `0101` 来处理。这一句得多啰嗦一句——别在真实项目里这么写。

循环内就分两种情况：**遇到的都是非叶子节点**，和**遇到了叶子节点**。前一种就是上面那张图里走的路。

`node` 这个变量代表"当前节点"，一开始等于根节点。向左走就是把 `node.left` 赋给 `node`，向右走就是把 `node.right` 赋给 `node`。走完一步别忘了 `i++`。

第二种情况：既然碰到叶子了，就找到了解码后的字符，把这个字符 `append` 到 `StringBuilder` 里，拼好了；同时因为下一个位要从头开始处理，把当前节点重置为根节点。

写到这里我发现之前的代码少做了一件事：**应该把整棵哈夫曼树的根节点记录成成员变量**。之前在构造方法里只找到了这个数组的分界点，并没有把它存成当前这棵哈夫曼树的成员变量。现在补一个 `root`，构造时直接记录根节点，解码的时候先把它取出来，存到一个 `node` 变量里。

### 少掉的那个字符：if 与 else 的顺序坑

代码写完，测试解码——把刚才编码出来的 `000101111111` 再解回去，看能不能恢复成原始的 `a`、`b`、`b`、两个 `c`。

结果**少了一个字符**。原始串里最后一个 `c` 没被解出来。

咱们把状态逐步摊开看。我们处理的比特串长度是 13，所以最后一个 `1` 的时候 `i` 是 12，而当前节点已经被重置成 `root` 了：

| 时刻 | `node` 指向 | `i` | 发生了什么 |
|---|---|---|---|
| 进入本轮循环 | `root` | 12 | `root` 不是叶子，进入 `if` 分支 |
| 右移之后 | `c` 的叶子节点 | 12 | `chars[12] == '1'`，走 `else if` 的右移分支，这没问题 |
| 自增之后 | `c` 的叶子节点 | 13 | `i++` 把 `i` 推到了数组长度 |
| 叶子分支 | `c` 的叶子节点 | 13 | 本轮走的是 `if`，**不会再进下面的 `else`** |
| 回到 `while` | `c` 的叶子节点 | 13 | `i == chars.length`，循环直接退出 |
| 结果 | — | — | 最后一个 `c` 没被 `append` 进去 |

症结就在第 4 行：`if` 和 `else` 是互斥的，一次只能走一个分支。我们把叶子节点的判断写成了 `else`，可最后这一位偏偏是先走了 `if`（右移）、再走了 `else if`（`i++`），根本没机会掉进 `else` 那个叶子分支。等下一次循环开始时，`i` 已经是 13，循环直接退出，那个叶子就永远没被读出来。

针对这个问题我没有什么特别优雅的解决方式。我的做法是：**把最后那个 `else` 去掉**，改成"走完之后重新判断"。既然当前节点在走完这一步之后已经变了，那就在**这一次循环里**把它是不是叶子重新判一遍——如果已经是叶子了，就不用等下一轮再走一遍 `if-else` 的叶子逻辑了，直接把这段处理逻辑原样拷贝过来。

```java
public String decode(String encoded) {
    StringBuilder sb = new StringBuilder();
    char[] chars = encoded.toCharArray();
    int i = 0;
    Node node = root;

    while (i < chars.length) {
        if (!node.isLeaf()) {
            if (chars[i] == '0') {
                node = node.left;
            } else {
                node = node.right;
            }
            i++;

            // 走完之后重新判断当前节点是不是叶子
            if (node.isLeaf()) {
                sb.append(node.ch);
                node = root;
            }
        }
    }
    return sb.toString();
}
```

跑一遍，最后两个 `c` 都回来了，数量正确。

> **结论**：循环里如果一次迭代可能完成"移动 + 产出"两件事，就别把产出挂在互斥的 `else` 上——`while` 的条件一变，这部分逻辑会被整段跳过。在这次迭代里重新判断一次，比赌下一轮还能进来稳得多。当然同学们如果找到了更好的解决办法，也可以留言告诉我，我对这段代码再做改进。

至此为止，哈夫曼树的编解码就讲完了。

### 活动选择：一个会议室怎么排才不冲突

换一个题目：现在我要在一个会议室举办 `n` 个活动，每个活动有各自的起始和结束时间，我希望找出在时间上互不冲突的活动组合，最充分地利用会议室——**办的活动次数越多越好**。

先看两个例子。

第一个例子，三个活动：

| 活动 | 开始 | 结束 |
|---|---|---|
| 活动 1 | 1 | 3 |
| 活动 2 | 2 | 4 |
| 活动 3 | 3 | 5 |

这个肉眼就能看出来：应该选活动 1 和活动 3，它们在时间上并不冲突——活动 1 结束了，活动 3 正好能开始，选它俩能办 2 个活动。但你要选中间那个活动 2，就只能办 1 个，因为它跟其他两个都冲突。

第二个例子，六个活动。最优解是 `1~2`、`3~4`、`5~7`、`8~9` 这四个，它们在时间上不冲突，活动次数能达到 4。

但如果你选中间这个比较长的 `1~6` 的活动呢？`1~2`、`3~4`、`5~7` 以及最后那个就全选不成了，只能跟 `8~9` 组合，一共 2 个活动。如果选最后那个呢？它跟 `5~7`、`8~9` 以及这个最长的都冲突，只能跟 `1~2`、`3~4` 组合，活动次数是 3 次。所以最优解还是那 4 次。

这个问题的最好解法其实是**贪心解法**。但在下结论之前，得先想一个问题：贪心要求每一步都找一个局部最优解，可这个问题里**局部最优解有好几种选择方式**，哪一种才能堆叠成最终的最优解？

### 三种局部最优，逐个被否

#### 优先选持续时间最短的

这是第一种比较自然的直觉：活动持续时间越短，跟其他活动冲突就越少嘛。

反例很好找。三个活动：

| 活动 | 开始 | 结束 | 持续时间 |
|---|---|---|---|
| 活动 1 | 1 | 5 | 4 |
| 活动 2 | 4 | 6 | 2 |
| 活动 3 | 5 | 9 | 4 |

按"优先选持续时间最短"的策略，第一轮应该选中持续时间只有 2 的活动 2。但选它不行——第一个和第三个都跟它冲突，最终活动总数只有 1 个。而如果先选活动 1 再选活动 3，`1~5` 和 `5~9` 在时间上不冲突，活动总数能达到 2。

所以"优先选择持续时间最短的活动"达不到最终解的效果，**否掉**。

#### 优先选冲突最少的

第二种思路是：每次选一个跟其他活动冲突最少的，当作局部最优。

拿前面那 11 个活动先做一遍统计，把每个活动各自冲突了几次都数出来。比如活动 1，在它没结束之前活动 2、3、4 就都已经开始了，所以它的总冲突次数是 3；下面的活动也都是类似地统计出来。然后按约定，每轮选冲突次数最少的那个。

- 冲突次数最少的是 6 号活动，它只冲突了两次，第一轮选中。
- 第二轮选冲突次数为 3 的那个，它跟已经选中的 6 号不冲突，选中。
- 剩下里面冲突次数最少的是 3 号活动，它跟前面的 2 号、以及上面那个 3 号都不冲突，选中。
- 最后，冲突次数为 4 的那一批：2 号不行，3、4 号不行，5 号不行（跟 6 号冲突），7 号跟 6 号冲突，8、9、10 号跟 3 号活动冲突——一个都选不了。

结果选中了 3 个：1 号、2 号、11 号。

**但这个解不对。** 真正的最优解是 1 号、5 号、7 号、11 号，一共 4 个活动：1 号结束了，5 号开始；5 号结束了，7 号开始；7 号结束了，11 号开始。3 个 vs 4 个，第二个贪心策略**也否掉**。

#### 优先选开始最早的

实在没招了，又想了一个办法：优先选开始最早的活动。

也不行。举一个例子，里面一共有四个活动，第一个活动确实是最先开始的，但显然它也是最后结束的，跟下面三个都会冲突——你要选了它，活动总数就只能有一个。而如果选择下面这三个，活动数可以达到三个。

第三种办法**也被否掉**。

> **结论**：持续时间最短、冲突最少、开始最早，这三种局部最优都没办法堆叠成最终的最优解。

### 第四种策略：优先选最早结束的活动

答案是：**优先选择最先结束的活动**。

道理在哪呢？最先结束意味着我能把会议室腾出来给别的活动用。就这么一点，但它恰好能让局部最优解最后堆叠成一个最终的最优解。

按这个策略把前面的例子重走一遍。

第一个例子（`1~3`、`2~4`、`3~5`），这三个活动其实已经按结束时间排好序了：`1~3` 最先结束排最前，`2~4` 第二，`3~5` 最后。逐一来看：

- 活动 1：直接选中。
- 活动 2：跟选中的活动 1 冲突，排除。
- 活动 3：跟活动 1 没有时间冲突——活动 1 已经结束了，活动 3 才开始，选中。

最优解就是选中 1 和 3，共 2 个活动。

第二个例子（那 11 个活动），同样是按结束时间排好序的：

| 轮次 | 活动 | 判定 |
|---|---|---|
| 1 | 活动 1 | 结束时间最早，直接选中 |
| 2 | 活动 2、3、4 | 都与活动 1 冲突，排除 |
| 3 | 活动 5 | 与活动 1 不冲突，选中 |
| 4 | 活动 6 | 与活动 5 冲突，排除 |
| 5 | 活动 7 | 与活动 5 不冲突，选中 |
| 6 | 活动 8、9、10 | 都与活动 7 冲突，排除 |
| 7 | 活动 11 | 与活动 7 不冲突，选中 |

得出最优解，4 个活动。

最后再看一个反直觉的例子：活动 1 的结束时间最后结束，按结束时间排序它应该排在最后，所以排序之后第一个被选中的是活动 2。接着活动 3 跟活动 2 并没有冲突，也被选中；活动 4 跟上面的活动 3 也没有冲突，也被选中；而剩下的最后那个活动跟活动 4 冲突，被排除。最优解是 3 个。

> **结论**：优先选最早结束的活动作为局部最优解，就能达到最终的最优解。

### 活动选择的代码实现

先看活动类：里面有活动的编号，还有活动的起始和结束时间 `start`、`finish`，一个构造方法，一个 `toString` 方法。

测试数据也准备好了：一个活动数组里三个活动，编号分别是 0、1、2，起始结束时间分别是 `1~3`、`2~4`、`3~5`。

按前面的讨论，我们得**按结束时间由小到大依次处理**——结束时间早的先处理，最后处理的排在后面。排序是一种选择，你也可以把它们塞进优先级队列，总之顺序必须是按 `finish` 排。这里我选排序。

```java
// 第一个参数传要排序的数组，第二个参数给比较器
Arrays.sort(activities, Comparator.comparingInt(Activity::getFinish));
```

因为我们比较的是对象中的某一个属性，所以可以用之前学过的 `Comparator.comparingInt` 的方法引用，指定一个 `getFinish` 方法，告诉它"我要根据 activity 对象中的 `finish` 属性排序"。

测试的时候我会先把顺序打乱，再看排序之后会不会按 `3、4、5` 这样的结束时间排好序。跑完果然是：结束时间最早的排在最前面，然后是结束时间 4 的 1 号活动，最后是结束时间 5 的 2 号活动。输入数据处理好了。

接下来实现 `select` 方法，它接受两个参数：活动数组和数组长度。

```java
public static List<Activity> select(Activity[] activities, int n) {
    // 保存被选中的活动
    List<Activity> result = new ArrayList<>();

    // 结束时间最早的那个一定被选中，不用去比较它跟谁冲突
    result.add(activities[0]);

    // 上一次被选中的活动，最开始就是 activities[0]
    Activity previous = activities[0];

    for (int i = 1; i < n; i++) {
        Activity current = activities[i];  // 当前正在处理的活动
        if (current.getStart() >= previous.getFinish()) {
            // 没有冲突，选中
            result.add(current);
            previous = current;
        }
        // 有冲突就跳过，继续处理下一个
    }

    return result;
}
```

这段代码背后的思路就三句话：

- `activities[0]` 肯定被选中，处理它的时候不用考虑它跟其他活动冲不冲突；
- 后面的每个活动，都拿它的**开始时间**跟**上一个被选中活动的结束时间**比：`>=` 说明没有冲突，选中；小于说明有冲突，跳过；
- 选中了它，它就成为"上一个被选中的活动"。

> **易错点**：判断冲突时，只能把当前活动的**开始时间**跟上一次被选中的活动的**结束时间**做对比。不要拿它去跟 `activities[0]` 的结束时间比——那是不准的，活动多了之后会漏掉中间被选中的那个。

跑一遍：对于 `1~3`、`2~4`、`3~5` 这组数据，选中的是 0 号和 2 号活动，因为 `1~3` 和 `3~5` 确实不冲突。这个题目就解答完毕了。

### 分数背包：按单位价值往里塞

再换一个。现在有 `n` 个物品，都是液体——水、牛奶、五粮液、可乐、茅台。每种液体都有各自的重量和价值，比如水总共 4L，价值 24 块；牛奶 8L，价值 160 块，等等。

现在让我取走 10L 液体。每次取的时候，这些液体都可以不拿、也可以全拿、也可以只拿其中一部分。问最高能拿到的价值是多少。

看几个拿法：

- 4L 的水 + 6L 的可乐 = 正好 10L，总价值 `24 + 108`；
- 8L 的牛奶 + 2L 的五粮液 = 10L，总价值 `160 + 4000`；
- 对某些液体你也可以只拿一部分，比如 6L 的可乐 + 2L 的五粮液，再拿 2L 的水，同样凑够 10L。

总之凑够 10L，问最终能拿到的最高价值是多少。

这个问题的最好解法还是贪心。而局部最优怎么选，我在这些液体的**名字**上已经给了大家足够的暗示：肯定先拿最贵的茅台，然后拿次贵的五粮液，等它们拿完了再挑第三贵的，直到拿够 10L。只有缺心眼的才会说最先去拿水——这个想都不用想，我们肯定不拿水。

翻译成能落地的规则就是一句：**每轮只拿单位价值最高的那个液体**，作为局部最优。

走一遍这个例子：

- **第一轮**：茅台，1L，4000 块。
- **第二轮**：五粮液，2L，4000 块——看起来它肯定是第二贵的。
- **第三轮**：牛奶和可乐，不知道哪个更好，算一下单位价格。牛奶 `160 ÷ 8`，1L 是 20 块；可乐 `108 ÷ 6`，是 18。18 比 20 便宜，所以第三轮应该选牛奶。
- 茅台和五粮液已经拿了 3L，所以牛奶只能拿 7L，也就是它 8L 中的 7/8。
- 总价值：`4000 + 4000 + 140 = 8140`。

> **提示**：我刚才举例的时候简化起见，给出的数据都是能整除的，不会出现小数的情况，这样算起来容易一些。真实数据里单位价值几乎一定会出现小数。

#### 数据准备

先把物品整理成一张表：

| 编号 | 液体 | 重量（L） | 总价值（元） | 单位价值（元/L） |
|---|---|---|---|---|
| 0 | 水 | 4 | 24 | 6 |
| 1 | 牛奶 | 8 | 160 | 20 |
| 2 | 五粮液 | 2 | 4000 | 2000 |
| 3 | 可乐 | 6 | 108 | 18 |
| 4 | 茅台 | 1 | 4000 | 4000 |

#### 排序：按单位价值降序

`select` 方法要选出总共拿 10L 的物品，以及它的最大价值。做的第一件事，就是根据物品的**单位价值**做好排序。排序是一种选择，用优先级队列也行。

为了排序，得先给 `Item` 加一个计算单位价值的方法，就叫 `unitValue`：总价值除以重量，简单得很。

```java
// 单位价值：总价值 / 重量
public int unitValue() {
    return value / weight;
}
```

> **提示**：这里我全选了 `int`，你也可以换成 `double`，都是可以的。

然后排序：

```java
Arrays.sort(items, Comparator.comparingInt(Item::unitValue).reversed());
```

> **易错点**：`comparingInt` 默认是**升序**，直接这么写会把水排在最前面、茅台反而排在最后，方向正好反了。解决办法是在比较器之后再调一个 `.reversed()`，把它降下来。

跑一下遍历打印验证顺序：排在最前面的是 4 号物品茅台，第二是 2 号物品五粮液，第三是 1 号物品牛奶，第四是 3 号物品可乐，最后 0 号物品水排在最后。顺序确定了。

#### 主循环：两种拿法

定一个变量 `max` 代表最大价值，最开始设置为 0。循环内处理每件物品时可以分成两种情况。

**情况一：这件物品能全部拿完。** 判断条件是剩余重量 `total` 大于等于当前物品的 `weight`：

- 剩余重量 `total` 减掉当前物品的重量；
- 把这件物品**所有的总价值**直接累加到 `max` 上（因为是全拿完了嘛）。

**情况二：一次拿不完。** 这时候 `total` 已经小于当前物品的重量了，比如剩余重量剩 7L，处理到牛奶，而牛奶的重量是 8，只能拿一部分。

注意这时候**不能**把它的总价值直接累加到 `max` 上，而应该是**单位价值乘以真正拿的那个数量**——剩多少就拿多少，也就是 `total` 乘以当前物品的单位价值。前面剩 7L，牛奶单位价值 20，`7 × 20 = 140`，这就是这一次拿到的价值，累加到 `max` 上。

而且处理到这儿就可以结束了——牛奶都没拿完，接下来就不用再循环到可乐和水了，所以直接 `break` 退出循环。

```java
public static int select(Item[] items, int n, int total) {
    // 按单位价值降序：最贵的先处理
    Arrays.sort(items, Comparator.comparingInt(Item::unitValue).reversed());

    int max = 0;   // 最大价值

    for (int i = 0; i < n; i++) {
        Item current = items[i];
        if (total >= current.weight) {
            // 拿得完：整件拿走，总价值直接累加
            total -= current.weight;
            max += current.value;
        } else {
            // 拿不完：只拿剩下的 total 升，按单位价值折算
            max += total * current.unitValue();
            break;
        }
    }

    return max;
}
```

把 `max` 打印出来验证，跟我们刚才手算的一致——都是 8140。分数背包问题就解答完毕了。

## 贪心撞墙之后：0-1 背包、降维与 Bellman-Ford

上一节的分数背包，我们用贪心解得干干净净：先算单位价值，谁贵先拿谁，实在装不下就把这件物品切开，只拿装得下的那一部分。这个结论我们下得很顺，因为"物品可以被切开"这件事，本身就把贪心救活了。

这一节换个题目：0-1 背包。题目长得跟分数背包几乎一模一样，还是 n 个物品、每个有重量和价值、背包有容量，还是问最多能拿多少价值。而且最优解的算式我们一眼就能看懂——差异小到让人放松警惕。可我们把上一次的贪心代码原样抄过来跑一遍，答案却是错的。

错在哪，今天把它彻底讲清楚。顺带把贪心算法的适用边界一起盘一盘，然后进到动态规划：先把一维数组降成两个变量，再拿最短路径问题把 Bellman-Ford 搭起来。

### 固体的背包

题目描述和分数背包几乎逐字对应。

还是 n 个物品，只不过这回它们**都是固体**了——没办法把它们分开拿。每个物品还是有一些重量和它的价值。举几个例子：

| 物品 | 重量 | 价值 | 单位价值 |
| :--- | :---: | :---: | :---: |
| 钻石 | 1 克 | 100 万 | 100 万 / 克 |
| 黄金（一小块） | 4 克 | 1600 | 400 / 克 |
| 红宝石 | 8 克 | 2400 | 300 / 克 |
| 白银 | 5 克 | 30 | 6 / 克 |

现在让你取走**不超过** 10 克的物品。注意，是不超过，不必拿满 10 克——拿 9 克、8 克都行。每次拿的时候只有两种选择：不拿，或者全拿。最后问：能拿到的最高价值是多少。

#### 差的就是"能不能切开"

两种背包摆在一起对比，差别只有一处，却足以决定算法的生死。

| | 分数背包 | 0-1 背包 |
| :--- | :--- | :--- |
| 物品形态 | 可以切分 | 固体，不可切分 |
| 拿一件的方式 | 不拿 / 拿一部分 / 全拿 | 不拿 / 全拿 |
| 贪心是否最优 | 是 | 否 |

> **定义**：0-1 背包问题——n 个不可分割的物品，第 $i$ 件重 $w_i$、值 $v_i$，背包容量 $W$。每件物品至多选一次，求 $\max \sum_{i \in S} v_i$，约束 $\sum_{i \in S} w_i \le W$。

有同学一定会想：既然这么像，我能不能拿上一次的贪心来解？

不行。**贪心解法只适合分数背包**，拿它来解 0-1 背包，有可能（在这个例子里是必然）无法达到最优解。不信我们算一遍给你看。

### 照抄分数背包的贪心

还是老策略：按单位价值从高到低依次考察物品，谁的单位价值最高就先处理谁。

#### 按单位价值一路选下去

显然第一个是钻石——一克 100 万，不选它选谁。选完，剩余容量 9 克。

接着黄金和红宝石比单位价值。黄金 4 克 1600，一克 400；红宝石 8 克 2400，一克 300。黄金更贵，选黄金。选完剩余容量 $10 - 1 - 4 = 5$ 克。

轮到红宝石了，8 克 > 5 克，装不下。红宝石落选。

那就只剩白银了：5 克 ≤ 5 克，正好塞进去。选完剩余 0 克。

```text
重量账本（容量 10 克）

  钻石    1 克   ──▶ 拿        余 9
  黄金    4 克   ──▶ 拿        余 5
  红宝石  8 克   ──▶ 放不下     余 5
  白银    5 克   ──▶ 拿        余 0

  总价值 = 1000000 + 1600 + 30 = 1001630
```

#### 最优解藏在"没拿满"里

总价值 1001630。这个解最优吗？

不是。仔细看就能看出来：**最优解不是"钻石 + 黄金 + 白银"这个组合，而是"钻石 + 红宝石"。**

```text
最优解（容量 10 克）

  钻石    1 克   ──▶ 拿        余 9
  红宝石  8 克   ──▶ 拿        余 1      只用了 9 克，不必拿满

  总价值 = 1000000 + 2400 = 1002400
```

$1 + 8 = 9$，没超过 10 克，价值 1002400。跟贪心那个 1001630 一比，差了 770。

> **结论**：0-1 背包上贪心拿不到最优解。原因不在于贪心"算错了"，而在于贪心的排序依据（单位价值）在"物品不可切分"的前提下不再是正确的比较标准。分数背包里，"把最后一点容量给单位价值最低的物品切开"永远不会亏；0-1 背包里，为了塞下一个高价值物品而放弃的，可能恰恰是全局最优的组合。

#### 代码跟分数背包比，只少了一个 else

虽然结论是"不能用"，但这个反例代码我们还是写一遍看。`select` 方法跟分数背包的几乎一模一样——直接把分数背包的代码拷过来，粘贴的时候选按纯文本粘贴。改动的地方只有一处。

**能拿完的情况：跟以前一样。** 遇到钻石时，剩余容量 10 克，钻石只有 1 克，拿得动。只要在最大价值上累加当前物品的价值就行了。

**拿不完的情况：跟以前不一样了。** 比如剩余重量是 5 克，遇到红宝石，重量 8 克，剩余容量已经小于当前物品的重量，进了 `else` 分支。这时候你能说把这个红宝石切开吗？不行。所以"切开拿"那一行代码整个不要了。

同理，**`break` 也不需要了。** 以前切分逻辑用完了就直接跳出循环，现在当前物品没办法切分，但我们还可以尝试下一个物品——看看下一个物品的重量有没有超过我的剩余重量，进入下一次循环就行。

所以这个 `else` 整个不要了：

```java
public int select(int[] weight, int[] value, int totalWeight) {
    int count = weight.length;
    int maxValue = 0;
    int remaining = totalWeight;

    // 贪心策略：按单位价值从高到低依次考察物品
    for (int i = 0; i < count; i++) {
        // 拿得完：整件拿走，价值直接累加
        if (weight[i] <= remaining) {
            remaining -= weight[i];
            maxValue += value[i];
        }
        // 拿不完的分支整个删掉了：
        // 物品不能切开，所以不能按比例拿，也不能 break——
        // 直接进入下一次循环，尝试下一个物品
    }

    return maxValue;
}
```

跑一下：贪心得到的最大价值是 **1001630**，不是最优解；最优解是 **1002400**。

> **易错点**：改这段代码时最容易漏掉的是那个 `break`。只删切分那一行、留着 `break`，红宝石装不下就直接退出了，后面的白银根本不会被考察，结果会比 1001630 还小，而且现象很隐蔽——代码看起来"合理"，结果只是偏小，不报错，很容易被当成数据问题。

### 贪心在哪里失效

到这里为止，我们已经学过不少跟贪心相关的算法了，正好把它们的适用性一起盘一盘。

| 算法 / 问题 | 贪心能不能拿到最优解 |
| :--- | :--- |
| 迪克斯拉（Dijkstra） | 没有负权边时可以；一旦出现负权边就不行 |
| 普里姆（Prim） | 可以 |
| 克鲁斯卡尔（Kruskal） | 可以 |
| 哈弗曼树（Huffman） | 可以 |
| 活动选择问题 | 可以 |
| 分数背包 | 可以 |
| 零钱兑换问题 | 不行 |
| 0-1 背包 | 不行 |

打叉的这几个怎么办？就得换一种解法。

迪克斯拉我们都知道，可以用**贝尔曼福特（Bellman-Ford）**替换掉它——它就能处理负权边，这是一个替换。零钱兑换问题和刚才的 0-1 背包，将来都可以用**动态规划**来替换解决，动态规划我们马上就讲。

> **提示**：这张表不是知识点背诵清单，而是一张"看到题目先自检"的表。拿到一个求最优解的题目，先扫一眼它在不在"可以"那一列；如果在，贪心就是首选；如果不在，就别在贪心上耗时间，直接换解法。能省下的都是debug的时间。

### 动态规划：把大数组砍成两个变量

先看一个已经讲过的例子——斐波那契。

斐波那契的递推是 $F(n) = F(n-1) + F(n-2)$，初值 $F(0) = 0$、$F(1) = 1$。用动态规划求解时，我们用一个一维数组保存之前所有子问题的计算结果，避免重复计算。

但这件事还可以再进一步优化。

#### 为什么一维数组还能再降

看这个递推的依赖关系：算第 13 项的时候，它需要用到**前面的第 11 项和第 12 项**。再往前的计算结果——第 1 项到第 10 项——留着有用吗？

没用。所以我们完全可以只保存最近两项的计算结果，不需要用一整个大数组把前面所有项都存下来。

这就是降维的思路：**二维数组降成一维数组，一维数组降成零维——也就是用一个或者几个变量来记录之前子问题的计算结果。**

斐波那契这个例子正好是降得最狠的：一维数组可以完全不要，两个变量就够。

#### 三个变量往前挪一格

先把跟一维数组相关的代码全部去掉。有两段判断可以保留：`n == 0` 时返回 0，`n == 1` 时返回 1。这两个是边界，跟降维无关。

那用什么来保存前两次的计算结果呢？用三个变量：

- `A` 代表前两项的值，初始值应该是 0；
- `B` 代表前一项的值，初始值应该是 1；
- `C` 用来装当前项的值，在循环内定义成临时变量，初始值就是 `B + A`——前一项加上前两项。

循环本身不用变。每轮循环结束的时候要做一次更新。假设这一轮 `A`、`B`、`C` 分别是 0、1、2，那进入下一轮循环之前，`A` 要往前移一格（取上次的 `B`），`B` 也要往前移一格（取上次的 `C`），`C` 则变成下一轮要计算的当前项。

```java
public int fib(int n) {
    if (n == 0) return 0;
    if (n == 1) return 1;

    int a = 0;  // 前两项的值
    int b = 1;  // 前一项的值

    for (int i = 2; i <= n; i++) {
        int c = a + b;  // 当前项 = 前一项 + 前两项
        a = b;          // 两个变量整体往前挪一格
        b = c;
    }

    return b;
}
```

这几轮挪动摊开看就是：

| 时刻 | `a` | `b` | `c` |
| :--- | :---: | :---: | :---: |
| 循环开始前 | $F(0)=0$ | $F(1)=1$ | — |
| 第 $i$ 轮开头 | $F(i-2)$ | $F(i-1)$ | 待算 |
| 本轮算完后 | — | — | $F(i)$ |
| 更新之后 | $F(i-1)$ | $F(i)$ | — |

那最后返回哪个？`C` 是循环内的局部变量，出不了循环。我们等循环结束后、把 `b` 更新成 `c` 之后，直接返回 `b` 就行——最后一次循环结束时 `b` 恰好就等于 `C`。

> **易错点**：这里最容易写错的就是 `a = b; b = c;` 的顺序。必须先把旧的 `b` 赋给 `a`，再把 `c` 赋给 `b`。顺序反了写成 `b = c; a = b;`，`a` 拿到的就是新 `b`，两个变量都被污染成同一个值，下一轮直接算错。

跑一下测试：求斐波那契第 13 项，输出 **233**，正确。省掉了一整个一维数组，$F(n)$ 原本要 $O(n)$ 空间，现在只要 $O(1)$。

### Bellman-Ford：最短路径也是动态规划

最短路径问题我们前面解答过，但它是动态规划的一个典型案例，所以拿出来再讲一遍。

顺便说个小知识：贝尔曼福特算法里的**贝尔曼**，就是提出了 Dynamic programming（动态规划）的人。

#### 先看它能不能拆成子问题

动态规划解题的套路是固定的：先找一个递推公式，然后把当前问题分解成子问题、分阶段求解；求解过程中把子问题的解缓存到一维或二维数组里，避免重复计算。

最短路径套不套得上？以这张图为例，起点是 $V_1$，现在要求从 $V_1$ 到 $V_4$ 的最短距离。

```text
         7             15
   V1 ────────▶ V2 ───────────▶ V4
    │                            ▲
    │ 9                          │ 11
    ▼                            │
   V3 ───────────────────────────┘

   V1 → V3 → V4 ： 9 + 11 = 20    ← 更短
   V1 → V2 → V4 ： 7 + 15 = 22
```

要到达 $V_4$，一条路线是从 $V_3$ 来，另一条是从 $V_2$ 来。所以思路就来了：先求出 $V_1 \to V_2$ 的最短路径，再求出 $V_1 \to V_3$ 的最短路径，然后在这两个结果的基础上比一比——从 $V_3$ 到 $V_4$ 更短，还是从 $V_2$ 到 $V_4$ 更短。

这就是把"求 $V_1 \to V_4$ 最短距离"这一个整体问题，拆成了两个子问题，可以分阶段求解。**套得上。**

#### 递推公式怎么读

用函数 $F(V)$ 表示"从起点出发到达顶点 $V$ 的最短距离"，$V$ 是图中的任意顶点。初始情况分两种：

- 当 $V$ 就是起点自己时，自己到自己，距离已知，是 0；
- 当 $V$ 不是起点（比如图里的 $V_2$、$V_3$、$V_4$、$V_5$、$V_6$）时，距离是未知的，初始值设成无穷大。

之后每一次更新按这个式子走：

$$
F(to) = \min\Big(\, F(to),\ \min_{from \to to}\big[\,F(from) + weight(from, to)\,\big] \Big)
$$

逐块拆开看。`from` 就是从哪来、从哪个顶点来；`to` 就是我到哪去、到达的那个顶点；外层的 `min` 是在两个值里挑一个更小的。

连起来读：比如要求 $F(V_4)$，从 $V_1$ 出发到 $V_4$ 的最短距离。它怎么来呢？先拿 $F(V_4)$ 的旧值做底——一开始旧值是无穷大——然后跟后面这个式子比，取最小值。

后面这个式子要做的事是：找到所有能到达 $V_4$ 的 `from`（这里是 $V_3$ 和 $V_2$），写一个循环一个一个试。假设 $F(V_3)$ 已经求出来是 9，再加上 $V_3 \to V_4$ 的距离 11，得到 20；20 跟无穷大比，当然 20 更小，于是把 $F(V_4)$ 更新成 20。

但 20 还不一定是最终的答案，我们得试试下一个 `from`。这回是 $F(V_2)$ 过来，$F(V_2) = 7$，加上 15 得 22；22 跟 20 求最小值，还是 20 赢，22 没能把它更新掉。经过这两次运算，$V_1 \to V_4$ 的最短距离就定下来了：**20**。

一句话概括这个式子：**在 `F(to)` 的旧值基础上，跟它所有 `from` 的 `F(from) + weight` 逐个对比，只要找到更小的，就用更小的值更新 `F(to)`。**

#### 代码落下来

先把边准备好。每个边有三个属性：`from` 顶点、`to` 顶点、以及从 `from` 到达 `to` 的距离。比如第一条边就是从 $V_6$ 出发到达 $V_5$，中间的距离是 9。

然后定一个一维数组 `dp` 用来缓存子问题的解。数组的每个元素代表某个顶点的最短距离，数组的索引对应顶点编号：`dp[1]` 代表 $V_1$ 的距离，`dp[2]` 代表从起点到 $V_2$ 的最短距离，以此类推。

一共 6 个顶点，但下标 0 我们不用——因为编号是从 1 开始的，为了让编号和索引一一对应，数组长度定为 7。

```java
public class BellmanFord {

    // 边：from 顶点、to 顶点、从 from 到 to 的距离
    static class Edge {
        int from;
        int to;
        int weight;
    }

    public static void main(String[] args) {
        int[] dp = new int[7];

        // 初始化：起点距离是 0，其余顶点都还不可达
        dp[1] = 0;
        for (int i = 2; i < dp.length; i++) {
            dp[i] = Integer.MAX_VALUE;
        }
        print(dp);

        // 为了演示递推公式，只留两条通向 V4 的边，其余的先注释掉
        List<Edge> edges = new ArrayList<>();
        edges.add(new Edge(3, 4, 11));
        edges.add(new Edge(2, 4, 15));
        // edges.add(new Edge(6, 5, 9));
        // ...

        // 套用递推公式更新最短距离
        for (Edge edge : edges) {
            int from = edge.from;
            int to = edge.to;
            dp[to] = Math.min(dp[to], dp[from] + edge.weight);
        }

        print(dp);
    }

    private static void print(int[] dp) {
        for (int v = 0; v < dp.length; v++) {
            if (dp[v] == Integer.MAX_VALUE) {
                System.out.println("V" + v + " -> ∞");   // 整数最大值即无穷大
            } else {
                System.out.println("V" + v + " -> " + dp[v]);
            }
        }
    }
}
```

这里用了 `Integer.MAX_VALUE` 来代表无穷大。`print` 方法存在的意义就是把这个整数最大值特殊处理一下，打印成无穷大的符号，看起来更直观。

第一次打印就能看到初始状态：下标 0 相当于没用；起点是索引 1，距离是 0；索引 2 到索引 6 的距离一开始全都是无穷大。

顶点编号和数组索引一一对应，所以找 `to` 顶点在 `dp` 里的位置，直接 `dp[to]` 就行。公式里要跟"旧值"和"新的候选值"比大小，调用 `Math.min`——第一个参数是 `dp[to]`（也就是它上次的最短距离），第二个参数是 `dp[from] + edge.weight`（from 的最短距离加上这条边的距离，边里的 `weight` 就代表 from 到 to 的距离）。

对应得很整齐。但跑出来的结果不对。

#### 无穷大加了个 11，答案变成了负数

`V_4` 确实被更新了——但被更新成了一个**负数**。

为什么？因为刚开始不管是 `from` 还是 `to`，它们的值都是无穷大，也就是 `Integer.MAX_VALUE`。一个整数最大值再加上后面的 `weight`，会怎么样？

$2147483647 + 11 = -2147483638$——直接超过了整数的表示范围，从正数变成了负数。这个负数一旦被写进 `dp[4]`，后面的结果就全被它带偏了。

> **易错点**：这是 Java（以及所有定长整型语言）用 `Integer.MAX_VALUE` 模拟无穷大时的经典陷阱。数学上"无穷大加任何数还是无穷大"，但在机器上无穷大只是一个具体的最大值，加法会溢出。语义上说得通的式子，落到代码里就是一次整数溢出。

那怎么办？

我们遇到了最大值，就**不应该执行这个更新操作**。你想，无穷大加上一个距离有意义吗？没有意义。在这个例子中无穷大代表的是"未知"——你连 $V_3$ 的最短距离都还不知道，在未知的基础上再加上 11，最终的结果还是未知。

所以应该加一个判断：只有当 `dp[from]` 不等于无穷大的时候，才做这个更新操作。这也更合理——现在我们既不知道 $V_3$ 的最短距离，也不知道 $V_2$ 的最短距离，那这次对 $V_4$ 的更新就没必要做。

```java
for (Edge edge : edges) {
    int from = edge.from;
    int to = edge.to;
    // from 还没被访问过（dp[from] 还是无穷大），跳过这次更新
    if (dp[from] == Integer.MAX_VALUE) {
        continue;
    }
    dp[to] = Math.min(dp[to], dp[from] + edge.weight);
}
```

跑一下，这回 $V_4$ 保持它的无穷大，不再被错误地更新成负数了。

——当然，$V_4$ 现在还是无穷大，是因为通向 $V_3$ 和 $V_2$ 的边还都注释着。也就是说，`dp[from]` 这个判断一加，真正能推进的那些边就生效了，多轮松弛才能把最短路径一层层"推"到远处。Bellman-Ford 的完整实现，就是把这个"一轮松弛"重复足够多次，让最短路径收敛。

这一节的实现只是第一步：先把 DP 数组、初始值、递推公式和一个不可省略的判断搭起来。剩下的，留到下一节。
