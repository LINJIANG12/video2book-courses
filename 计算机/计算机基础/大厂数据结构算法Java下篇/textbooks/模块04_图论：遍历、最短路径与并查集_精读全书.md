## 图：顶点与边，以及走遍一张图的两种方式
> 对应块：BLK18 | 覆盖分集：P73-P77 | 块标题（分集名）：《进阶数据结构和算法-227-图-基本概念》

先摆一张图出来。图里的 a、b、c、d 是**顶点**；把这些顶点连在一起的线，我们称之为**边**。

```text
        a
       ↙ ↘
      b   c
       ↘ ↙
        d
```

读图：a→b、a→c、b→d、c→d，一共四个顶点、四条边。

### 顶点、边，以及边的方向

这张图还有个说法，叫**有向图**。为什么叫有向？因为它的边是有方向的——你仔细看，边上带箭头。从 a 到 b 是可以的，但反过来从 b 到 a 呢？不行，不行。这种有方向的，我们就称之为有向图。

既然有有向图，那肯定还有一种叫无向图。它们俩的区别其实主要在**边的定义**上：有向图里这个边是单向的，而无向图这边是双向的。

那怎么理解这个双向呢？很简单。从顶点 a 到顶点 b 是可以的，反过来从顶点 b 到顶点 a 也是可以的。这种没有箭头了，它就无所谓从谁到谁了，反正它们都是连通的——这种边我们称之为双向的边，这种图就是无向图。

| | 边 | a 到 b | b 到 a |
| :--- | :--- | :--- | :--- |
| 有向图 | 单向，带箭头 | 可以 | 不可以 |
| 无向图 | 双向，没有箭头 | 可以 | 也可以 |

### 度：数一数顶点身上挂着几条边

> **定义**：度（degree）是顶点的一个属性，表示的是与这个顶点相邻的边有几条。

我们换一个图来看，这回是一张无向图。

```text
        a
       / \
      b   c
       \ /
        d
       / \
      e---f
```

读图：a 往下数有一条、两条相邻边，所以 a 的度数是 2；b 也是一条两条，度数是 2；c 和 f 同样都是 2；轮到顶点 d，相邻边明显就多，一条两条三条四条，那它的度数就是 4。

对于有向图，我们还可以把度细分成**入度**和**出度**：

> **定义**：入度是指这个箭头进来的数量；出度是指这个箭头出去的数量。这样理解就可以了。

还是上面这一批顶点，换成有向的样子：

```text
        a
       ↙ ↘
      b   c
       ↘ ↙
        d
       ↙ ↘
      e ───▶ f
```

读图：d→e、d→f、e→f 这三条边带了箭头方向，其余按无向的连法理解。

| 顶点 | 入度 | 出度 |
| :--- | :--- | :--- |
| a | 0 | 2 |
| b | 1 | 1 |
| c | 1 | 1 |
| d | 2 | 2 |
| e | 1 | 1 |
| f | 2 | 0 |

一个顶点一个顶点核对过去：对 a 来讲，从 a 进来的箭头有几个？没有，箭头没有指向顶点 a，所以入度是零；出去有两个箭头，出度是二。b 的入度是一，出度也是一；c 也是入度一出度一；d 进来两个箭头、出去两个箭头，入度二出度二；e 入度一出度一；f 进来两个，但是出去的是零——没问题吧。

### 权：让边带上业务含义

> **定义**：权，也称之为权重，是边的一个属性，代表的就是两个顶点之间的一些业务含义。

它可以是距离、费用、时间，或者是其他任何度量都行，具体看你的业务来定。

举个例子。下面有四个顶点，北京、武汉、广州、上海，四个顶点代表四个城市，那么连接这两个顶点之间的边它就有一个权。大家一看也明白，它的业务意义就代表两个城市之间的距离：

```text
  北京 ──1900── 广州
  北京 ──800─── 武汉
  北京 ──1200── 上海
  武汉 ──700─── 上海
```

读图：北京跟三座城市都直接相连，武汉还额外连着上海，其中北京到广州是 1900 千米，北京到武汉是 800 千米。两个顶点之间的距离，就是它们这条边的权，也叫权重。

### 路径与路径长度

> **定义**：路径是从一个顶点到另一个顶点的一系列连续的边。

光看这个定义好像挺难理解的，但是你结合图就非常容易理解。还是上面那张城市图：北京是一个顶点，上海是另一个顶点，那我就问，从北京到上海有哪些路径？

- 北京直接到上海——这实际上就是一条路径；
- 北京到武汉，然后武汉再到上海——这又是第二条路径。

这跟我们现实生活中的路径是一样的。

路径还有一个配套的概念，叫**路径长度**：

> **提示**：不考虑权重时，路径长度就是边的数量；考虑权重时，一般就是把沿途的权重累加起来。

- **不考虑权重**：北京直接到上海只有一条边，路径长度是 1；北京到武汉、武汉再到上海经过了两条边，路径长度就是 2。
- **考虑权重**：权重本身就带业务意义，累加出来才有意义。北京直接到上海是 1200 千米；北京到武汉再到上海这条路径的长度就是 $800 + 700 = 1500$ 千米。

### 环：出发之后又回到原地

> **定义**：在有向图中，如果从一个顶点开始，经过了若干条有向的边，又回到该顶点了，那么就形成了一个环。

```text
  a ──▶ b ──▶ c ──▶ d ──▶ e
  ▲                        │
  └────────────────────────┘
```

读图：顺着箭头从 a 走到 b、c、d、e，最后 e 又指回了 a 顶点，这时候就形成了一个环。这跟我们脑海中的概念也是类似的——只要是从顶点出发又回来了，这种就构成了一个环。

### 连通性与连通分量

> **定义**：如果两个顶点之间存在路径，就认为这两个顶点是连通的。

比如我们这里的 a 和 c 是连通的，那么 c 和 d、b 和 e、e 和 b、b 和 a 都算是连通的；但是 a 跟下面那一块是不是就没有连通？因为他俩之间并不存在任何的路径。

> **定义**：如果所有的顶点都是连通的，那这个图就被称之为**连通图**。

当然，我这个图目前不是连通图，因为这张图里面有部分的顶点并没有跟其余顶点连通。

> **定义**：如果是子图有连通的，也就是图的一部分连通了，那么这个连通的这部分称之为**连通分量**。

```text
   连通分量 ①        连通分量 ②        连通分量 ③
  ┌──────────┐     ┌────────┐      ┌──────────┐
  │ a  b  c d│     │  e  f  │      │  ……      │
  └──────────┘     └────────┘      └──────────┘
```

读图：整个图里有三块互不相连的部分——a、b、c、d 是第一个连通分量，e、f 是第二个，剩下的那几个顶点是第三个。同一块分量内部两两之间都存在路径，三块之间一条边都没有。

### 邻接矩阵：用二维数组装下一张图

> **定义**：邻接矩阵其实很简单，就是**一个二维数组**，行对应顶点、列也对应顶点，我们可以用一个二维数组来表示一张图。

规矩只有一条：**如果两个顶点之间有边相连，就给它一个 1；如果这两个顶点之间没有边相连，就给它一个 0**。

还是回到前面那张 a、b、c、d，a→b、a→c、b→d、c→d 的图。先把二维数组画出来，然后一格一格填：

```text
        a b c d
    a [ 0 1 1 0 ]
    b [ 1 0 0 1 ]
    c [ 1 0 0 1 ]
    d [ 0 1 1 0 ]
```

第一行：a 跟 a 之间有边相连吗？没有，所以给个零；a 跟 b 大家看是不是有一条边相连？是的，给一个一；a 跟 c 也是一条边，给一个一；最后 a 跟 d 并没有相连，给个零。第二行 b，b 跟 a 有边相连给 1，b 跟 b 自己没边相连给 0，b 跟 c 没连着给 0，最后 b 和 d 有边相连给 1。第三行 c，c 跟 a 相连给 1，c 跟 b 没相连给 0，c 跟 c 自己没相连给 0，c 跟 d 相连给 1。最后一行 d，d 跟 a 没相连给 0，d 跟 b 相连给 1，d 跟 c 相连给 1，d 跟自己没相连给 0。

> **提示**：无向图的邻接矩阵，从这个对角线开始看是**对称的**——因为 a 连到 b，b 就必然也连到 a。记住这一条，后面和有向图一对比就非常清楚。

我们再看一个有向图的例子。同样先用邻接矩阵来表示：

```text
        a b c d
    a [ 0 1 1 0 ]
    b [ 0 0 0 1 ]
    c [ 0 0 0 1 ]
    d [ 0 0 0 0 ]
```

第二行注意一下：b 到 a 有连线吗？没有，那个箭头不存在，所以 b 到 a 是 0——**这是跟之前那个无向图不太一样的地方**。b 到 b 是零，b 到 c 是零，b 到 d 是有箭头的，给个一。第三行 c 跟 b 差不多，到 d 是 1，到 a、到 b、到它自己都是零，也是 `0 0 0 1`。最后第四行 d，到 a、到 b、到 c、到 d 全是零。

它跟之前无向图的区别在哪？图虽然长得差不多，但是无向图最后画出来的邻接矩阵是**对称的**，而有向图可以看到**并不对称**。

### 邻接表：一维数组加链表

我们还可以用邻接表的方式来表示刚才这张图。邻接表就不是用二维数组了，而是用**一个一维数组加链表**的方式来表示图。

一维数组这一排，还是对着我们的顶点 a、b、c、d；接下来你就看每个顶点跟谁相连：

```text
  a ──▶ [ b, c ]
  b ──▶ [ a, d ]
  c ──▶ [ a, d ]
  d ──▶ [ b, c ]
```

读图：a 跟 b 和 c 相连，所以 a 底下我们可以让它连个链表，链上 b 然后再链上 c。当然 b 和 c 它俩的次序并不重要，b 在 c 前面也行，c 在 b 前面也可以。b 相邻的是 a 和 d，那 b 这边来一个 a 再链一个 d；c 和 a 还有 d 相连，那就 c 连上 a、链上 d；最后 d 跟 b 和 c 相连，d 连上 b、链上 c。

还是有向图的例子，这回用邻接表来表示它，这个就更简单了——只记它**出去**的边：

```text
  a ──▶ [ b, c ]
  b ──▶ [ d ]
  c ──▶ [ d ]
  d ──▶ [ ]        ← 空的，没有出边
```

读图：a 到 b 和 c 都有连线，所以 a 里边给它一个链表，链到 b、链到 c；b 只能连到 d；c 也只能连到 d；d 没有跟任何顶点相连，所以 d 这边的链表就是空的。

### 为什么还是推荐邻接表

针对这两种图的表示方式，我们一般建议大家用**邻接表**来表示这张图，而不是用邻接矩阵。

邻接矩阵呢可能看起来更直观、更简单一些，这一点没错；但是它的缺点是**占用的空间比较大，而且对空间的浪费也比较多**。为什么这么说呢？你想，如果将来顶点数非常多，而边又非常少的话，那是不是相当于那些没连接边的顶点之间，取值应该全是零——整个这个二维数组里很多东西全是零，只有很少数几个 1，就造成了大量的空间浪费。

因此用邻接表是一种比较经济的存储方式，推荐大家使用邻接表。

### 用 Java 把一张图写出来

> **提示**：当然还是可以用邻接矩阵（一个二维数组）来表示，但还有一种更面向对象一些的做法，就是用邻接表来表示。

我们抽取了两个类，一个呢是顶点类，一个呢是边。

顶点类这边暂时两个属性就够用了：一个是顶点的名字，就是这里大家看到的 a、b、c、d；还有一个 `edges`，就是顶点关联的边的集合。比如说 a 这个顶点有两条边，从它出去的有两条边；b 从它出去有一条边；c 从它出去也有一条边；d 就没有边了。当然以后随着图的相关问题要求变多，我们还会给它加更多的属性，目前这两个暂时够用。

边这个类目前也加了两个属性：一个是 `link`，就是将来你这个边它的终点对应的是哪个顶点——比如说这条边它的终点是不是指向 b 这个顶点，将来它的 `link` 就是 b；另一个是 `weight`，代表这个边它有可能具备的权重。当然我这张图里没有画出来，如果你这边有权重的话，我们可以用一个 `weight` 来代表。

```java
// 顶点：名字 + 出边集合 + 是否被访问过
public class Vertex {
    private String name;              // 顶点的名字：a、b、c、d
    private List<Edge> edges;          // 从这个顶点出发的所有边
    private boolean visited = false;   // 是否被访问过

    public Vertex(String name) {
        this.name = name;
        this.edges = new ArrayList<>();
    }
}

// 边：终点 + 权重
public class Edge {
    private Vertex link;               // 这条边指向哪个顶点
    private int weight;                // 这条边可能带的权重

    public Edge(Vertex link) {
        this(link, 0);
    }

    public Edge(Vertex link, int weight) {
        this.link = link;
        this.weight = weight;
    }
}
```

`visited` 这个属性现在先放在这儿，它是等会实现深度优先搜索时才真正用得上的——为什么非要有它，到那一节再讲。

#### 先建一张最简单的图

这张图里有四个顶点 a、b、c、d，还有四条边，我们用一段 Java 代码把它写出来：

```java
// 先创建四个顶点对象
Vertex a = new Vertex("a");
Vertex b = new Vertex("b");
Vertex c = new Vertex("c");
Vertex d = new Vertex("d");

// a 有两条出边：第一条指向 b，第二条指向 c
a.getEdges().add(new Edge(b));
a.getEdges().add(new Edge(c));

// b 只有一条出边，指向 d
b.getEdges().add(new Edge(d));

// c 也只有一条出边，同样指向 d
c.getEdges().add(new Edge(d));

// d 一条出边都没有，给它一个空的集合
d.setEdges(new ArrayList<>());
```

为什么两条边要分别 new？因为每条边指向的顶点不一样——我们在调用构造方法的时候把 `link` 传给它，第一条边它的 `link` 就是 b，第二条边的 `link` 就是 c，这样将来 a 的两条边就都齐了。

#### 带权重的图

我们再来看一个稍微复杂一点的例子，这回图里有 v1 到 v6 六个顶点：

```text
   v1 → v3(9)    v1 → v2(7)    v1 → v6(14)

   v2 → v4(15)

   v3 → v4(11)   v3 → v6(2)

   v4 → v5(6)

   v5 → （没有出边）

   v6 → v5(9)
```

读图：每个顶点只列出它自己的出边，括号里是权重；v5 没有出去的边。对应的代码就是这样：

```java
Vertex v1 = new Vertex("v1");
Vertex v2 = new Vertex("v2");
Vertex v3 = new Vertex("v3");
Vertex v4 = new Vertex("v4");
Vertex v5 = new Vertex("v5");
Vertex v6 = new Vertex("v6");

// v1 有三条出边，权重分别是 9、7、14
v1.getEdges().add(new Edge(v3, 9));
v1.getEdges().add(new Edge(v2, 7));
v1.getEdges().add(new Edge(v6, 14));

// v2 就一条边，指向 v4，权重 15
v2.getEdges().add(new Edge(v4, 15));

// v3 出去的有两条边
v3.getEdges().add(new Edge(v4, 11));
v3.getEdges().add(new Edge(v6, 2));

// v4 就一条边，指向 v5，权重 6
v4.getEdges().add(new Edge(v5, 6));

// v5 没有出去的边
v5.setEdges(new ArrayList<>());

// v6 有一条边，指向 v5，权重 9
v6.getEdges().add(new Edge(v5, 9));
```

> **提示**：v1 的三条边权重都不一样，分别是 9、7、14。更关键的是——**边集合里元素添加的顺序，会直接决定深度优先搜索的访问顺序**，这一点下一节马上就会撞上。

### 深度优先搜索：一条路走到黑

> **定义**：深度优先搜索（DFS，Depth First Search）是图的一种遍历方式，它要求遍历图的所有顶点，所有顶点都要走一遍。所谓"深度优先"，就是我遍历的时候要**尽可能地走得更远**。

我们还是拿上面那张六个顶点的图，从 v1 开始。

#### 手推一遍遍历过程

v1 是起点，它有三条路可以走，我们就假设从 v3 开始向前走。

v1 先走到 v3。到了 v3 先别着急走 v2 或者 v6，你先看看 v3 能不能继续向前走。如果能继续向前走，那你就沿着 v3 继续往远了走。

v3 好像也有两条路，一条到 v6、一条到 v4，我们假设它就先走 v4。走 v4。同样 v4 这边也是继续看能不能向前走——尽可能地向前走。v4 发现可以走，那当然只有一条路了，走到 v5。到了 v5 以后是不是就没路了？因为 v5 没有出去的边，所以 v5 就必须向回走了。

v5 回到 v4，回到 v4 以后看 v4 还有没有其他路，发现是没有其他路了，那继续向回走，回到 v3。回到 v3 以后，发现 v3 这还剩一条路没走，所以 v3 呢就继续去走到 v6。

v6 前面确实也有一条路，那就继续走，走到 v5——但这个节点已经访问过了，而且它自己也是没路的，往回走。回到 v6，看 v6 有没有其他路，没有了，那 v6 继续向回走，回到 v3。这时候 v3 的两条路是不是都走完了？走完了，那 v3 就向回走，回到 v1。

回到 v1 之后，看看 v1 还有没有其他的路，显然 v1 这边还有两条路，一条到 v2、一条到 v6，所以接下来再走 v2 这条路。同样 v2 这条路它也会继续向前走——因为它那条路 v4 其实已经走过了，v4 这个顶点访问过了，所以这一段我就不画了；发现 v4 已经访问过了，回来，继续向回走。

回到 v1 以后，v1 还剩下最后一条路，那就是 v6，当然 v6 也访问过了，向回走又回到 v1。最终 v1 这边没有更多的路了，整个遍历结束。至此所有顶点都被遍历了一遍。

```text
  v1
  ├─ v3
  │   ├─ v4
  │   │   └─ v5      （没路了，回退）
  │   └─ v6
  │       └─ v5      （已经访问过）
  ├─ v2
  │   └─ v4          （已经访问过）
  └─ v6              （已经访问过）

  访问顺序：v1 → v3 → v4 → v5 → v6 → v2
```

读图：这就是 DFS 走出来的形状——一条路走到黑，走不通了才回退到上一层，把上一层剩下的路走完。所有顶点都被访问了一遍，一个不落。

#### visited：没有它就会死循环

> **易错点**：实现 DFS 之前，一定要给顶点类再补一个属性，就是用来区分这个顶点**是不是已经被访问过**的。

它是布尔类型的，就叫 `visited`，含义就是是否被访问过。刚开始它是 `false`，表示没有被访问过；将来只要你被访问过，我们就把它改成 `true`。

为什么非有它不可？你回到刚才分析的过程里看：从 v3 可以访问到顶点 v6，但后来从 v1 也是可以去访问到 v6 的。那我就得有一个属性来判断这个顶点 v6 是不是已经被访问过了——**如果已经访问过了，你就不要继续再递归了**，否则是不是就有可能出现了一个死循环呀。

#### 递归版 dfs

代码其实很简单。我们写一个 `dfs` 方法，它接受的参数就是将来你的起点，我们假设现在把 v1 作为起点传进去：

```java
public void dfs(Vertex start) {
    start.setVisited(true);                  // 进来一个顶点，说明它正在被访问
    System.out.println(start.getName());    // 访问动作：打印顶点的 name

    for (Edge edge : start.getEdges()) {     // 遍历这个顶点相邻的边
        Vertex next = edge.getLink();        // 每条边都关联着一个顶点
        if (!next.isVisited()) {            // 取个反：没被访问过才继续
            dfs(next);                      // 递归，就地重复这一套动作
        }
        // 已经被访问过了，就无需继续递归
    }
}
```

拆开讲就很清楚了：进来以后，先把它的 `visited` 设成 `true`，表示它已经被访问过了；然后所谓的"访问"就简单一些，我们就去打印顶点的 `name` 这个值。接着找到这个顶点相邻的边，看这些边对应的顶点是不是可以继续重复这个操作；遍历出来的每条边都关联着一个顶点，把它取出来判断一下——如果这个顶点没有被访问过，取个反发现是 `true`，那我们是不是继续对它进行一个 DFS 就就可以了。

我们来跑一遍，看看它跟刚才分析的遍历顺序是否一致：最先访问的是 v1，然后依次是 v3、v4、v5、v6、v2，跟我们手推的完全一致。

> **提示**：这个顺序是跟**边的定义顺序**有关的。他是先去遍历第一个集合，第一个集合里第一个元素是 v3，所以接下来他又到 v3 上去看它有没有相应的边；遍历到 v4 的时候，发现 v4 还可以继续向前走，所以接下来去遍历 v5，而 v5 已经走到头了，所以它就向回走。

#### 栈版 dfs2

刚才我们是使用递归的方式来实现了 DFS，那还有一种办法，就是我们用**非递归**的方式来实现 DFS——当然这种办法就需要我们自己准备一个**栈**。

栈呢，我们就用 `LinkedList` 来做，它可以作为栈；这个栈里面放的都是顶点，所以泛型类型我们就选择顶点类型：

```java
public void dfs2(Vertex start) {
    LinkedList<Vertex> stack = new LinkedList<>();
    stack.push(start);                            // 起点先放进栈里

    while (!stack.isEmpty()) {                    // 栈不为空就一直遍历
        Vertex current = stack.pop();             // 每次从栈里 pop 一个元素
        current.setVisited(true);                 // 拿出来就相当于访问过它了
        System.out.println(current.getName());

        for (Edge edge : current.getEdges()) {
            Vertex next = edge.getLink();
            if (!next.isVisited()) {
                stack.push(next);                 // 压栈，下一轮循环访问到它
            }
        }
    }
}
```

一样可以把六个顶点都遍历一遍。但有同学会发现，**这个顺序好像跟刚才我们用递归方式打印的不一样**是吧？这个没关系，我们来分析一下原因。

问题其实就出在我们使用的这个自定义栈这块。因为我们去遍历这些边的时候，假设遍历的顺序是 1、2、3，那他压栈就是按 1、2、3 来压的，**但是弹出的时候顺序是不是就反过来了？** 就变成 3、2、1 了，所以这个顺序上就有所不同。

| 步骤 | 做了什么 | 打印 | 栈（底 → 顶） |
| :--- | :--- | :--- | :--- |
| 1 | 把起点 v1 压栈 | — | v1 |
| 2 | pop v1，标记并打印；把 v3、v2、v6 压栈 | v1 | v3 v2 v6 |
| 3 | pop v6，标记并打印；把 v5 压栈 | v6 | v3 v2 v5 |
| 4 | pop v5，标记并打印；没有出边 | v5 | v3 v2 |
| 5 | pop v2，标记并打印；把 v4 压栈 | v2 | v3 v4 |
| 6 | pop v4，标记并打印；v5 已访问 | v4 | v3 |
| 7 | pop v3，标记并打印；v6、v4 都已访问 | v3 | 空 |

访问顺序是 v1 → v6 → v5 → v2 → v4 → v3。

我们对照着再走一遍：刚开始访问的是 v1，这没问题。第一个顶点是 v1，那我接下来压栈的顺序是按 v3、v2、v6 的顺序去压栈的，**但是出栈的顺序是不是 v6 先出来？** 对，v1 这个顶点访问完了以后，接下来访问的就是 v6 这个顶点，倒着来的。六这边看能不能走到头呢？结果发现 v6 这边确实还有一个边，就是 v5，所以接下来访问 v5；v5 走到头了，这个就该往回走了，也就是回退，然后又回到 v1。

回到 v1 以后，再遍历集合里的第二个元素，第二个元素是 v6，v6 遍历完了，接下来是 v2 了，所以接下来我们看到的是去访问的顶点 v2。v2 这边其实就一个方向，就是 v4，所以接下来访问 v4；v4 因为接下来走的是 v5，而 v5 已经访问过了，所以这条线我就跨了，v4 就该往回走了，往回走又回到 v1。这边还剩一个 v3，所以接下来他就去访问这个顶点 v3。刚才打印了 v4，然后 v3 的话，那 v3 因为接下来的顶点 v4 已经访问过了，所以这条线我也不画了，v3 就相当于往回走了，所以最后打印的是 v3。

> **提示**：你要想让顺序跟我们递归方式一样，那遍历的时候是不是就得**倒着遍历**，从后往前遍历，就能保证顺序一样了。

### 广度优先搜索：一层一层往前推

> **定义**：广度优先搜索（BFS，Breadth First Search）说白了就是**按层来遍历**——先把第一层完了，再遍历第二层，这样以此类推。

还是拿之前这张六个顶点的图举例，我们从 v1 这个顶点开始。

先把与 v1 相邻的几个顶点都给它遍历完——按代码的顺序，首先遍历与它相邻的 v3，再遍历与它相邻的 v2，最后遍历与它相邻的 v6，这算是相当于把第一层遍历完了。

遍历完第二层以后，第二层这些节点再去找它们相邻的：v3 有两个相邻的 v4 和 v6，那就一起来啊，遍历 v4，再去遍历 v6；当 v6 已经遍历过了，那就不重复画这条线了。第二个顶点 v2 它就有一条路，也是 v4，当然这个也是遍历过了，我就不画了。第二层还有最后一个是 v6，v6 在遍历的话是不是可以走到 v5？好，第二层到这里就结束了。

第三层的话，刚才这个 v4 再看它——当然它已经遍历过 v5 了，没有其他路了；第三个层还有 v5，v5 呢也没有路了，这就算遍历结束了。

```text
    第 1 层            v1

    第 2 层        v3     v2     v6

    第 3 层                v4         v5

    遍历顺序：v1 → v3 → v2 → v6 → v4 → v5
```

读图：同一层的顶点横向排开，下一层的顶点排在下面一层——BFS 就是这样一层一层往前推的。

### 用队列实现 bfs

我们来实现这个广度优先搜索的代码，也就是这里的 `bfs` 方法，它的参数就是我们要遍历的图的起点。广度优先搜索需要用到一个队列，那我们就先把队列创建好，用 `LinkedList` 来当这个队列：

```java
public void bfs(Vertex start) {
    LinkedList<Vertex> q = new LinkedList<>();

    q.offer(start);                   // 先往队列里放一个初始元素：起点
    start.setVisited(true);           // 放进去以后就可以标记为访问过了

    while (!q.isEmpty()) {            // 只要队列不为空就不断处理
        Vertex current = q.poll();    // 取出下一个要处理的元素
        System.out.println(current.getName());

        for (Edge edge : current.getEdges()) {   // 遍历它的这些相邻顶点
            Vertex next = edge.getLink();
            if (!next.isVisited()) {
                next.setVisited(true);          // 先标记为访问过
                q.offer(next);                  // 再把它加入队列
            }
            // 已经访问过的顶点就不用再放进来了
        }
    }
}
```

> **提示**：注意 BFS 标 `visited` 的时机跟递归版 DFS 不一样。DFS 是函数一进来就标记；BFS 是在**入队的那一刻**就标记。这样才能保证同一个顶点不会被重复塞进队列里——这是 BFS 实现里最容易被写错的一行。

试一下，运行之后可以看到，我们就把所有的顶点遍历了一遍，顺序也正是刚才分析的顺序：先是 v1，然后是 v3、v2、v6，然后是 v4，最后是 v5。

## 拓扑排序与最短路径
> 对应块：BLK19 | 覆盖分集：P78-P82 | 块标题（分集名）：《进阶数据结构和算法-232-图-拓扑排序》

这节课我们来学拓扑排序。

什么是拓扑排序呢，我们先来看这张课程表。

这张课程表中的课程，它的学习是有先后次序的。比如说我们要学 JavaWeb，那你必须先学了网页基础，再学了 Java 基础，有这两个基础了，我们才能学习 JavaWeb 这门课程。类似的，我们要学 Spring 框架，你必须先学习数据库跟 JavaWeb，这两个课程都学完了，才能学习 Spring 框架。类似的还有，你要学微服务框架呢，必须先学 Spring 框架；你要做最后的实战项目呢，先得把这个前面的微服务框架学了。

可以看到这些课程之间，它是有一定的学习的先后次序的。那么如果我们能够按照这种课程之间的依赖关系，把它的先后次序给它确定好，按照学习的先后顺序把它排好序，那么这就是拓扑排序。

课程依赖说白了就是一张有向图：先修课指向后修课。

```text
  v1 网页基础 ──┐
                ├──► v3 JavaWeb ──► v4 Spring框架 ──► v5 微服务框架 ──► v7 实战项目
  v2 Java基础 ──┘                          ▲
  v6 数据库 ───────────────────────────────┘
```

七个顶点，六条依赖。课程表看着是一张表，落到代码里就是一个 `List<Vertex>` 装顶点、每个顶点挂一个出边集合的邻接表结构。

> **定义**：**拓扑排序**——把一张有向无环图的全部顶点，按边的方向排成一个线性序列，使得对任意一条边 $u \to v$，$u$ 都排在 $v$ 前面。

### 思路：先排入度为零的顶点

这个拓扑排序的思路是怎样的呢，其实我们来观察这张图，我们可以找到图中入度为零的那些顶点是谁呢？

是网页基础、Java 基础，还有数据库，他们呢都是入度为零，也就是没有箭头指向它。没有箭头指向它意味着什么？意味着他们不需要前置的知识了。

所以呢，待会儿排序的话，其实就应该先排谁啊？肯定是入度为零的这些个顶点啊，网页基础、Java 基础以及数据库，他们排在前面就可以了。至于他们三个呢，倒是没有什么顺序之分，谁排在前，谁排在后都无所谓，也就是说这三门课你先选哪一个都行，理解了吧。

当他们排好序之后呢，我们就可以把它们从这个图中给它删除掉。删除掉以后我们再来看，这时候有没有入度为零的顶点呢？有吧。因为网页基础跟 Java 基础移除之后呢，刚才的 JavaWeb 它是不是变成入度为零的了。所以接下来我排序的话应该排这样，是不是应该是数据库跟这个 JavaWeb 啊。好，排他俩。

一旦他俩排好了，那接下来也把他俩从我们整个图中删掉，剩下的呢，就剩下 Spring 框架、微服务框架和实战项目了。那这三个里面继续重复这个过程呗。看一下谁入度为零呢？这回是 Spring 框架了，所以接下来要排的话就排谁啊？排这个 Spring 框架。类似的，它排好了再把它从图里面删掉，重复这个过程，我们就能够把所有的顶点都给它排好序。

整个过程用一张表走一遍就很清楚了：

| 轮次 | 图上还剩的顶点 | 本轮排出去的顶点 | 排出去之后入度的变化 |
| --- | --- | --- | --- |
| 第一轮 | v1 ~ v7 全部 | v1 网页基础、v2 Java 基础、v6 数据库 | v3 入度 $2 \to 0$ |
| 第二轮 | v3、v4、v5、v7 | v3 JavaWeb | v4 入度 $2 \to 1$ |
| 第三轮 | v4、v5、v7 | v4 Spring框架 | v5 入度 $1 \to 0$ |
| 第四轮 | v5、v7 | v5 微服务框架 | v7 入度 $1 \to 0$ |
| 第五轮 | v7 | v7 实战项目 | v7 没有出边，结束 |

> **结论**：**拓扑排序的核心动作只有一个**——"找一个入度为零的顶点排出去，然后把它的邻居入度减一"。减到零了，说明这个邻居的前置知识全部学完了，它就能排了。

### 第一步：把每个顶点的入度数出来

好，那么先来看一下这个数据的准备啊。这里啊我一共有 1、2、3、4、5、6、7，是不是七个顶点对象，所以我的代码里也准备了七个顶点对象，它们都是一一对应的。

那接下来还要准备这些边。第一个顶点的边呢只有一个，也就是网页基础，它的边指向的是我们 v3 JavaWeb。然后第二个顶点是 Java 基础，它呢它的边也是指向的 JavaWeb。第三个顶点呢是 JavaWeb，它指向的边是 v4 Spring 框架。还有 v6 数据库，数据库它的边也指向的是 Spring 框架，也就是这里的 v4。v4 它有一条边指向的是 v5，也就是这个微服务框架。然后 v5 它有一条边指向的是 v7，也就是指向的实战项目。最后 v7 呢它没有边了。

好，最后呢用了一个集合代表整个图，这个集合里面就有我们刚才这七个顶点。

数据准备好了，那接下来我们看看怎么去拓扑排序。

我们先要做的第一件事是，先统计一下每个顶点的入度啊。比如说网页基础没有箭头指向它，它的入度是零；像这个 JavaWeb 呢有两个箭头指向它，那它的入度是二。我先把这个每个顶点它的入度数先给它统计出来。当然呢我们需要给这个顶点呢加一个属性来记录这个入度，所以我们回到 Vertex 类、Graph 类里面，我们先给它加一个 `indegree` 这个属性，代表它的入度。当然啊刚开始初始，入度都是零。

那统计逻辑其实非常简单。我们观察一下这些边的集合：v1 它的边的集合里有一个边指向了 v3 JavaWeb，那既然它指向 v3 了，那 v3 我就问，它是不是那个入度应该加一啊？没问题吧。那接下来 v2 Java 基础，它也有一条边指向的也是 v3，那这时候 v3 它的入度是不是又应该加一啊？没问题吧。所以你发现，待会我们去遍历前两个顶点的边的集合以后，我就知道了，对于 JavaWeb 来讲它的入度就是二啊，因为它总共加了两次嘛。

类似的下面呢有两条边指向了 v4 Spring 框架，那将来 v4 它的入度就应该是二。加一变成二。没问题吧。好，那有一条边将它指向 v5 微服务框架，那微服务框架呢，它的入度就是一啊，因为只有一条边指向它。还有就是有一条边将来指向 v7 实战项目，所以呢 v7 它的入度也是一。至于像数据库、网页基础、Java 基础，那这几个节点呢都是没有边指向它，所以它们的入度都是初始值零。

把每个顶点、每个顶点的出边集合都遍历一遍之后，入度就统计好了：

| 顶点 | 对应课程 | 入度 | 入边来自 |
| --- | --- | --- | --- |
| v1 | 网页基础 | 0 | —— |
| v2 | Java 基础 | 0 | —— |
| v3 | JavaWeb | 2 | v1、v2 |
| v4 | Spring 框架 | 2 | v3、v6 |
| v5 | 微服务框架 | 1 | v4 |
| v6 | 数据库 | 0 | —— |
| v7 | 实战项目 | 1 | v5 |

具体写成代码呢就非常的简单了。我们对整个这个图做一个遍历，遍历出来的每个顶点呢，我们再去遍历它边的集合。边的集合遍历出来之后呢，我们刚才已经分析过了啊，它指向的这个顶点，它入度是不是加一就可以了。入度加一，入度呢是刚才我们定义的这个 `indegree` 这个属性啊，加加就可以了。当所有的顶点，还有所有的边的集合遍历完一遍，这个入度它的个数就统计好了。

```java
// 第一步：统计每个顶点的入度
for (Vertex vertex : graph.getVertices()) {
    for (Edge edge : vertex.getEdgeList()) {
        Vertex to = edge.getTo();          // 这条边指向的顶点
        to.setInDegree(to.getInDegree() + 1);
    }
}

// 循环结束顺手打印一下每个顶点的名字和入度
for (Vertex vertex : graph.getVertices()) {
    System.out.println(vertex.getName() + " 的入度是：" + vertex.getInDegree());
}
```

运行一遍看一下，对了吧？网页基础、Java 基础，包括数据库，它们的入度都是零；那 JavaWeb 跟 Spring 框架入度都是二啊，微服务框架还有实战项目，入度分别都是一。这样我们的第一步，统计每个顶点的入度就完成了。

### 第二步和第三步：入队、出队、把邻居的入度减一

接下来呢我们再来看第二步。第二步呢，就是将入度为零的顶点加入到队列去。就把数据库、网页基础、Java 基础啊，这些入度为零的顶点先加到一个队列去。那么先准备一个队列啊，`LinkedList` 啊，把这个队列先准备好。

好，接下来再次遍历我们刚才这个图，然后拿到每个顶点，看一下它的入度，如果它是等于零的话，那就表示啊要把它加到我们的队列去。好，用 `offer` 把它加入到队列。这是我们第二步就做好了。

```java
// 第二步：把入度为零的顶点全部加入队列
LinkedList<Vertex> queue = new LinkedList<>();
for (Vertex vertex : graph.getVertices()) {
    if (vertex.getInDegree() == 0) {
        queue.offer(vertex);
    }
}
```

好，接下来呢我们要做的第三件事，就是从这个队列中不断去移除入度为零的那些个顶点。那每次移出的顶点呢就相当于已经排好序了。那移除的顶点呢，需要把它们相邻的顶点的入度减一。

什么意思呢？就比如说网页基础被移除了，那它相邻的这个 JavaWeb 它的入度就减一。Java 基础移除了，那这个 JavaWeb 它的入度再减一。好，比就像这个样子啊，网页基础、Java 基础都被移走了，那 JavaWeb 它的入度就应该减成零。没问题吧。那什么时候减成零了啊？某个顶点的入度减成零了，那我们就把这个顶点进行入队，进行下一轮的这个入队的处理。这个要清楚了吧？

写成代码呢，我们就可以这样来写。先来一个 `while` 循环检查一下，如果这个队列它不为空啊，那么就不断去从队列里去移除顶点啊，那就去调用它的 `poll` 方法，提出一个个的顶点。那移除的这个顶点呢，我们就把它的 `name` 打印出来，相当于它已经被排好序了啊。

好，除了打印这个顶点以外，我们还要把它相邻顶点的入度减一。它的相邻顶点是不是在它那个 `edgeList` 那个集合里啊，所以我们去遍历它的 `edgeList` 集合，然后拿到它相邻的顶点，这是它相邻顶点，然后相邻顶点的入度是不是要减一啊。减完之后呢，我们再检查一下什么时候它被减成零了啊？减成零了，那是不是应该把这个相邻的顶点也加到我们的队列中去啊？所以判断一下，如果它被减成了零，那么就把它加到我们的队列里去就可以了。

```java
// 第三步：不断出队，把邻居的入度减一，减到零就入队
while (!queue.isEmpty()) {
    Vertex current = queue.poll();
    System.out.println(current.getName());          // 出队 = 已排好序

    for (Edge edge : current.getEdgeList()) {       // 遍历它的出边
        Vertex next = edge.getTo();                 // 相邻顶点
        next.setInDegree(next.getInDegree() - 1);    // 相邻顶点入度减一

        if (next.getInDegree() == 0) {              // 减到零了，才能排
            queue.offer(next);
        }
    }
}
```

最后呢我们来测试一下，看一下它的执行效果啊。可以看到没有问题吧，先是网页基础、Java 基础、数据库，因为他们的入度都是零。那接下来呢，由于网页基础、Java 基础被移除了以后呢，JavaWeb 它的入度被减成零了，所以他被入队。接下来我们下一次遍历的时候，就是从这个队列里拿到的就是 JavaWeb。那 JavaWeb 跟数据库被移走了以后呢，那这个 Spring 框架它的入度就被减成零了，所以 Spring 框架继续入队。那 Spring 框架移除以后，微服务框架它的入度就被减成零，微服务框架入队。最后微服务框架它移除以后，实战项目它的入度就被减成了零，最后把实战项目入队。最终实战项目被取出来了以后，这个队列就空了，空了以后它就退出了整个这个循环。这是我们这个拓扑排序的整个过程。

> **易错点**：出队顺序不是唯一的。网页基础、Java 基础、数据库这三个入度为零的顶点，谁先谁后都行；但它们**必须都在同一轮里被排出去**，因为它们之间没有依赖关系。真正会卡住顺序的，是那些必须"等到某一门课学完才能学"的课程。

那我们再来看拓扑排序第二种办法，就是我们可以配合深度优先搜索的方式来实现这个拓扑排序。

但还是以我们这个图为例啊，我们对这个图里所有没有访问过的节点，咱们做一次深度优先搜索啊。从谁开始都可以啊，只要他没有访问过，我们就对它做一次深度优先搜索。

### 三档状态，第三档专门留给环检测

这里啊我给顶点类里又加了一个属性叫 `status`，它呢代表我们这个顶点的一个访问状态。那有同学说为什么不用之前的 `visited` 呢？`visited` 不就是去表示这个顶点有没有被访问过吗？是因为待会我们这个状态呀得有三种状态，而一个 `visited` 它是个布尔值，只能表示两种状态啊。

好，那这个状态呢初始值是零，表示未访问；二呢表示这个顶点已经访问过了；一呢表示这个顶点在访问中啊。这是我们给顶点啊加了这么一个状态属性。

```java
public class Vertex {
    private String name;             // 顶点的名字
    private List<Edge> edgeList;     // 该顶点的出边集合（邻接表）
    private int indegree;            // 入度，拓扑排序用
    private int status;              // 0 未访问 / 1 访问中 / 2 已访问，DFS 用
    private int dist;                // 到起点的最短距离，Dijkstra 用
}
```

好，那下面呢我们就来用 DFS 来实现一下这个拓扑排序啊。首先呢咱们拿到图以后，对里面所有的顶点呢做一个遍历，然后针对里面的每一个顶点，是不是都要做一次 DFS 的搜索啊，所以我们调一个 `dfs` 这个方法，对每一个顶点啊都要做一个深度优先遍历。当然呢我们需要一个栈来保存最终的遍历结果，所以我们准备好一个栈啊，写在循环外，大家都来用同一个栈，这样呢我们就用一个 `LinkedList`，里面呢都是装的是字符串，也就是顶点的名字。

好 DFS 方法呢我们前面其实写得比较简单。那首先呢我们先判断一下，看看这个顶点是不是已经遍历过了啊。如果他的这个 `status` 已经是二，表示他已经访问过了，那没必要继续递归了是吧，所以我们先做这个判断啊，判断一下，如果这个顶点它的 `status` 已经等于等于二了，那直接 `return`。

那如果还没有等于二，那我们要去找到它相邻的顶点啊，对这个相邻顶点啊在做 DFS 的递归调用。所以接下来我们对相邻顶点做一个遍历，拿到这个相邻的顶点之后呢，哎我们再次 DFS，好，把相邻的顶点传过去，这个栈也传过去就行了。

那等我当前这个顶点是不是就相当于已经处理完了？等所有的相邻的点都完成之后，我当前的顶点就算处理完了。处理完了，那我就把他的 `status` 是不是改成二，改成二，并且呢这个顶点的值，我们就给它压入到栈里。

> **注意**：压栈呢应该是最后压啊，因为我们是说了把这些相邻顶点处理完了，往回走的时候才压栈。所以呢我们应该是顶点相邻顶点都处理完了，往回走的时候，也就是在最后这个位置，我们做一个压栈。

```java
public static void topoSortByDfs(Graph graph) {
    LinkedList<String> stack = new LinkedList<>();
    // 写在循环外，所有顶点共用同一个栈
    for (Vertex vertex : graph.getVertices()) {
        dfs(vertex, stack);
    }
    System.out.println(stack);
}

private static void dfs(Vertex vertex, LinkedList<String> stack) {
    if (vertex.getStatus() == 2) {
        return;                              // 已经访问过，不用再递归了
    }

    vertex.setStatus(1);                     // 进入递归前，先标记自己"访问中"

    for (Edge edge : vertex.getEdgeList()) { // 遍历相邻顶点
        dfs(edge.getTo(), stack);            // 递归调用，把栈也传下去
    }

    vertex.setStatus(2);                     // 当前顶点彻底处理完了
    stack.push(vertex.getName());            // 往回走的时候才压栈
}
```

改完之后呢我们运行一下。好大家看这个拓扑排序的结果是不是已经有了？数据库、Java 基础、网页基础啊，他们排在最前面，所以他们三个的顺序无所谓好。接下来是 JavaWeb、Spring 框架、微服务框架、实战项目。没问题吧？好这样我们的拓扑排序的结果已经出来了。

### 状态一其实是用在环的检测上

好那有同学可能注意到了，我们刚才这个 `status` 其实也只用到了二这个状态，也就是访问过，至于前面这个一"访问中"好像没用着对吧？那它用在哪呢？

哎，其实它用在环的检测上。比如说我们还是看之前这个反例啊，微服务框架跟实战项目，这是不是已经出现环了？哎出现环了。那我把我的代码也稍微改一下啊，故意出现一个环。

那加上以后我们来考虑这么一个场景。比如说这个 DFS 调用的时候，这时候执行到的当前处理的顶点是 v5 微服务框架了，可以吧？那我们就可以这样啊，我们在它处理 v5 相邻的这个顶点的时候，我们把它的 `status` 设置为一吧，就是在处理相邻的这些个顶点之前啊，先把它的 `status` 设置为一。

然后接下来他是不是就开始做这个相邻顶点的循环啊，这时候他就开始处理这个实战项目。但是等到处理实战项目的时候，那实战项目它的邻居里是不是也有这个微服务框架啊，所以接下来实战项目的一次 DFS 调用里，它的内部是不是又再次进入了一个循环，这个循环里面处理的就是微服务框架。那微服务框架他再次递归调用的时候，他如果发现这时候的 `status` 等于一，表示什么？

是不是就表示这时候微服务框架我自己还没有处理完的过程中，又有实战项目又来处理我的微服务框架，是不是相当于就检测出了环呀？那检测出了环了，那我们就没必要继续向下运行了，直接告诉他啊，出现环，我报一个错不就行了。因此我们每次进入这个 DFS 递归调用的时候，做一个判断，如果发现一进来你这个 `status` 等于等于一了，那说明已经有在别的地方正在处理我的这个顶点啊，这时候就相当于已经有环了，我们这时候 `throw` 一个异常。

```text
  处理 v5 微服务框架：先把自己标成 1（访问中）
      │
      ▼
  处理它的邻居 v7 实战项目 → 递归 dfs(v7)
      │
      ▼
  处理 v7 的邻居，里面又有 v5 微服务框架 → 递归 dfs(v5)
      │
      ▼
  dfs(v5) 一进来就发现 status == 1
  说明我自己还没处理完，就又被别人递归回来了  ──►  有环，抛异常
```

```java
private static void dfs(Vertex vertex, LinkedList<String> stack) {
    if (vertex.getStatus() == 1) {
        // 我自己还没处理完，就又被递归回来了 —— 说明有环
        throw new RuntimeException("发现了环，拓扑排序失败！");
    }
    if (vertex.getStatus() == 2) {
        return;
    }
    // ... 下面不变
}
```

这个异常呢我们就告诉他啊，发现了。好这样就相当于把环给检测出来了。当然了，如果你这个图没有环的话，那它被处理完了以后，它的 `status` 会被改成二，这样相当于下次进来它就发现没有环，就不会走这个抛异常的逻辑了。

好那我们来测一下吧，运行啊，当然我们现在这是有环的情况啊。可以看到啊，它就出现了我们刚才的异常，就发现了环对吧。那我把那个环再去掉啊，把这个环去掉，去掉之后呢，它现在就不会再进入这个条件了，还是能保持以前的这个正确的一个拓扑排序的结果。所以我们这个 `status` 将来取值为一，就主要就是用来判断这个是否存在环。

> **提示**：注意这个"访问中"的判断必须放在 `status == 2` 的判断**之前**。顺序反了的话，一个正在访问中的顶点会被当成"已访问"直接 return，环照样漏过去。

### 最短路径：只从一个顶点出发

这节课呢我们来看一个叫 Dijkstra 的单源最短路径算法。

那什么是最短路径算法呢，其实很简单，就是我从一个顶点出发，到其他顶点，它们的最短路径你分别求出来啊。比如说从 1 到 6 最短路径是多少，从 1 到 2、从 1 到 3、从 1 到 4，还有从 1 到 5。我从一个顶点出发，到其余顶点，它的最短路径。

那这里的"单源"啊，就是指我们的起点是只有一个。

下面呢我们就来看看这个算法的一个描述。算法呢还是比较简单的，一共就五条啊，那我们逐一来看。

先看第一条。第一条呢就是将所有的顶点，刚开始呢都是设置为未访问，然后它们呢组成一个未访问顶点的集合，也就是我们一开始这里的 1、2、3、4、5、6 啊，大家都是在这个未访问顶点的集合当中。

接下来看第二条啊，第二条呢相当于是做了一个初始化的动作，就是每个顶点啊，他们需要有一个临时的距离值。那这个距离值啊对于初始顶点，也就是我们这里的 1 来讲，它的临时距离值是零——我们要求的就是 1 到其他顶点的距离。那其他顶点呢这个距离值都是无穷大。那我们给大家标注一下，这个初始顶点它的距离是零，那其他的呢这个距离都是无穷大，2 是无穷大，3 是无穷大，4 是无穷大，5 也是无穷大。

接下来的 3、4、5 呢是在一个循环里来完成啊。那三呢是说每次啊，我要选择一个这个临时距离最小的未访问顶点，把它作为当前顶点。那大家来看我们刚开始这些所有顶点里，临时距离最小的是谁呢？哎，是不是就是顶点 1 啊？哎，把它作为当前顶点，然后用一个红色把它标记出来。好，这是找到了当前顶点。

那接下来第四步呢就是找他的邻居，去遍历它的邻居，遍历邻居的时候去更新这个距离。那怎么更新呢？很简单，你看从 1 到 3 这个邻居，它的距离是不是刚开始是无穷大，但是显然它有一个更短的距离，这个更短的距离是不是显然是 9 啊？所以我们把它的距离更新成 9。那这个从 1 到 2 这个邻居呢，同样把它的这个距离更新成 7。没问题吧？好，从 1 到 6 这个距离呢，好，把它更新成 14。这是把当前顶点到它邻居的这些距离先做一个更新，这是我们第四步要做的事情。

那第五步呢，就当他的邻居都处理完了，那我们就可以把当前顶点从未访问的集合中删除了，也就是这个 1 啊就算处理完了，下次再去处理的时候，1 这个顶点就不用考虑了。

好，3、4、5 处理完了又回到 3，重新完成这个过程。

### 五条步骤，手算一遍

那这回再来看，把 1 排除掉以后，剩下这些点，谁的那个临时距离最小？哎，是不是顶点 2，它的临时距离只有 7，是这里面最小的。所以接下来我们就把 2 把 2 当成是当前的顶点，对它进行处理。处理的方式也是一样啊，就看它有没有邻居，有邻居了就去更新它邻居的距离。那你看它现在就一个邻居，就是这个 4 嘛，那它到邻居的距离应该是 7 加上它到邻居的距离 15，显然这个距离应该被更新成 22 呀，15 加 7 等于 22。哎，它也被处理完了，没问题吧？再把它从我们的未处理集合中删掉。

好，剩下的这 2、3、4 这四个顶点里面，谁的临时距离最小的？哎这回是不是轮到 3 了？哎它的临时距离是 9，所以接下来我们再去把 3 当成是这个当前节点，再处理 3 的邻居。那 3 的邻居是不是有一个是 4，有一个是这里的 6 啊。好先来看这个 4 吧，那么它到 4 的距离是 9 加 11 等于 20，是不是比我们上次从 2 过来的这个 22 要更小一些？哎如果你发现一个更短的距离，那你就做一个更新；那如果没有发现更短的呢，就保留上次这个距离不变。好，显然我们这次呢应该把这个 9 加 11 等于 20，更新到这里的 4 的临时距离。没问题吧？

好接下来 3 到 6，3 到 6 呢，它的这个距离是 9 加 2 等于 11，是不是也比从原来过来的这个 14 要更小了啊？所以我们把这个临时距离也更新成新的，9 加 2 等于 11，就把刚才的 14 更成一个更小的距离 11。好，这样呢 3 这个顶点也处理完了，把它的两个邻居都处理完了，好把 3 从这个未访问的集合里给它删掉。

好继续重复这个过程。那剩下的呢是 4、5、6，4、5、6 的距离里最小是 11，那我们来把它当成是当前节点。它的邻居呢只有一个，就是这个 5，那显然它的整个这个距离应该把它无穷大更新成这里的 11 加 9 等于 20。这里就不保留无穷大了，将来 5 的距离就应该是 11 加 9 等于 20 啊。好这样 6 也处理完了。

最后呢我们来处理这里的 4 和 5。当然他俩的这个距离都一样啊，你随便挑一个处理就行，比如说吧我们 5 这个没啥处理的，因为它没邻居了，我们就处理 4。好那么 4 把它当成我们的当前节点，然后看一下它的邻居啊，20 加 6 是 26，但是原来人家的这个距离是 20，是不是人家原来这个 20 比你现在的 26 更小啊？所以不用更新。好，这样我们的 4 这个顶点也处理完了，把它从这个未处理这个集合中给它去掉。最后就剩一个 5 了，最后一个 5 了，也把它从这个未访问的顶点集合中给它去掉。

现在我们整个未访问的顶点集合中全部都走了一遍了，也就是大家所有的顶点都处理完了，这时候我们这个算法就结束了。算法结束呢，我们可以看到每个顶点它的这个最小距离其实就已经记录好了：

| 顶点 | 从 1 出发的最短距离 |
| --- | --- |
| 1 | 0 |
| 2 | 7 |
| 3 | 9 |
| 4 | 20 |
| 5 | 20 |
| 6 | 11 |

> **提示**：整个循环里最关键的一句话是——**"有更短的就更新，没有更短的就保留不变"**。Dijkstra 允许一条顶点的距离被改写好几次（3 的邻居 6 就被从 14 改成了 11），这正是它能修正早期错误估计的原因。

```java
// 在集合中查找临时距离最小的顶点，并把它返回作为当前顶点
private static Vertex findMinDistanceVertex(List<Vertex> vertexList) {
    Vertex minVertex = vertexList.get(0);       // 先假定下标 0 处的最小

    for (int i = 1; i < vertexList.size(); i++) {
        Vertex vertex = vertexList.get(i);
        if (vertex.getDist() < minVertex.getDist()) {
            minVertex = vertex;                 // 找到更小的，就更新最小值
        }
    }
    return minVertex;
}
```

好，这是我们这个方法。那现在把它创建出来。好先通过当前的顶点去拿到它邻居的集合，然后来一个遍历啊。好这样呢，我们先拿到它邻居的顶点啊，简称 n，然后检查一下，如果这个顶点在我们 `list` 集合内，我们才需要做接下来的更新距离的处理。好判断一下，如果 `list` 集合里 `contains` 刚才这个邻居，那我们才去做更新距离的处理。

那更新距离的话，那么就要找到当前顶点它的这个距离加上他的 `weight`，加上他的 `weight`，这是一个新距离。如果这个新距离比他上一次邻居的距离要小，那我们就更新；如果这个距离太大了，那我们就不去更新。没问题吧？啊这是我们的要更新的那个新距离。新距离如果比原来邻居它的距离要小的话，那就相当于我们找到一个更小的距离，对不对？这个时候我们就把邻居的距离更新成这个更小的值。没问题吧？

```java
// 更新当前顶点所有邻居的距离
private static void updateNeighborDistances(Vertex current, List<Vertex> vertexList) {
    for (Edge edge : current.getEdgeList()) {
        Vertex n = edge.getTo();                // 先拿到邻居的顶点

        // 邻居还在集合里，说明它没处理完，才需要更新
        if (vertexList.contains(n)) {
            int newDist = current.getDist() + edge.getWeight();  // 当前顶点距离 + 边的权值
            if (newDist < n.getDist()) {        // 找到更短的距离，就更新
                n.setDist(newDist);
            }
        }
    }
}
```

好这样循环一遍，那么所有邻居它的这个距离值就会得到一个更新了，这是我们的第四步就做完了。

啊最后这个第五步啊就非常简单了，它只要把当前顶点移除就可以了，从我们这个 `list` 集合中把它移除，好可以调用 `list.remove`，然后传过去我们当前的顶点，把它移除掉就 OK 了。

## 从记录路径到扛住负边：Dijkstra 的改进与 Bellman-Ford
> 对应块：BLK20 | 覆盖分集：P83-P86 | 块标题（分集名）：《进阶数据结构和算法-237-图-Dijkstra》

### 距离知道了，路径还不知道

前面我们已经能算出从 v1 到其他所有顶点的最短距离了。但这里要再加一个补充的需求：我想知道详细的路径。

就拿 v1 到 v5 来说吧，最短距离是 20。

```text
V1 ──9──► V3 ──2──► V6 ──9──► V5        9 + 2 + 9 = 20
```

20 这个数字是怎么来的？v1 先到 v3，然后 v3 到 v6，最后 v6 到 v5。我真正想要的不是这个结果，而是"它到底是从哪条路走过来的"。光有距离，这个信息是不完整的。

先别急着写代码，我们想一下这件事该怎么办。

来看"更新邻居距离"这个方法——在这个方法里，当前节点跟它挨着的这些邻居节点，我们是不是本来就知道？比如当前顶点是 v6，那它挨着的邻居就是 v5。那这个 v5 是从哪来的？知道的，它肯定是从当前节点来的啊。

既然来源是已知的，那就给 Vertex 加一个属性，告诉它"你从何而来"就够了。属性的类型还是 `Vertex`，就叫 `previous`，初始值给一个 `null`。

```java
public class Vertex {
    private String name;
    private int dist;
    private Vertex previous;      // 新增：上一个顶点是谁
    private List<Edge> edges;
}
```

然后在更新距离的地方顺手加一行：一旦发现有更小的距离，就把邻居节点的 `previous` 更新成当前节点。

```java
private static void updateDist(Vertex v, int dist, Vertex prev, Set<Vertex> unvisited) {
    if (unvisited.contains(v) && v.getDist() > dist) {
        v.setDist(dist);
        v.setPrevious(prev);       // 顺手把来源记录下来
        unvisited.remove(v);
    }
}
```

这样就相当于把它从何而来记录下来了。打印的时候先判断一下：

```java
for (Vertex v : graph.getVertices()) {
    System.out.print(v.getName() + "  dist=" + v.getDist() + "  ");
    if (v.getPrevious() != null) {
        System.out.print(v.getPrevious().getName());
    } else {
        System.out.print("null");
    }
    System.out.println();
}
```

> **易错点**：为什么要加这个不为 null 的判断？因为对于起点 v1 来说，它的 `previous` 本来就该是 null——它前面没有更前面的节点过来了。所以先判一下，不为 null 就打印来源的名字，否则就打一个 null。

测试一下可以看到：v1 的 previous 是 null；对于 v2，它的最短路径是从 v1 过来的；对于 v3，它也是从 v1 过来的，最短距离 9；对于 v4，它是从 v3 过来的，而 v3 的前面我们刚才也能找到，是 v1，也就是 v1 → v3 → v4，这就是到 v4 的最短路径；对于 v5，它是从 v6 过来的，v6 呢也是从 v3 过来的，所以它应该是 v1 → v3 → v6 → v5，也就是 9 + 2 + 9 = 20。

用 `previous` 记录将来这个最短路径是从何而来，这样我们相当于把这个路径就描述出来了。

### 判断邻居：也可以靠 visited

其实还有一个地方可以稍微改进一下。

之前我们在判断这个邻居节点的时候，是"如果发现他还在这个未处理的集合中"才做处理，每次都要去集合里 `contains` 一遍。除了这种判断方式以外，我们还可以用一个更有效率的判断方法。

我们处理完一个顶点以后，就把他的 `visited` 设为 `true`——这是我们之前用过的一个属性，表示这个顶点已经被处理过了。那么在执行更新邻居距离的时候，我们判断一下：如果这个邻居它已经被处理过了，那是不是就不用再做距离的更新了？

判断逻辑就可以改成：只有邻居的 `visited` 为 `false`、还没有被处理过的时候，才做下面的距离检查和更新。

```java
private static void updateDist(Vertex v, int dist, Vertex prev) {
    if (!v.isVisited() && v.getDist() > dist) {
        v.setDist(dist);
        v.setPrevious(prev);
    }
}
```

这样一改，这个参数就可以不要了——方法签名上的那个集合参数可以不要，调用处的这个参数也可以不要。当然最终的效果跟刚才执行的是一样的，还是 0、7、9、20、20、11。但是因为我们不用每次都去那个集合里用 `contains` 去判断了，所以这个判断在性能上会得到一定的提升。

### 用优先队列替换集合

#### 瓶颈在"每次都要扫一遍集合"

我们把注意力集中在第三步——第三步的逻辑是要选取一个当前顶点，他选举的思路是要到未处理的集合中去找一个距离最小的顶点作为当前顶点。

但是整个算法它的效率并不是很高，因为它要遍历整个集合，才能得到这个距离最小的点。

那这块可以怎么改进呢？我们在多个元素里去选一个最小值，可以用堆这种数据结构，所以可以把它的时间复杂度降低。接下来我们用一个最小堆，也就是一个优先级队列，来改写我们的代码。

#### 改动清单

我把改动前后的逻辑先列出来，我们过一遍。改动之前我们是用了一个集合来存储这些未访问的顶点，改动之后这个集合就不需要了，我们直接把它替换成优先级队列。

| 环节 | 改动前（集合） | 改动后（优先级队列） |
|---|---|---|
| 容器 | `Set<Vertex> unvisited`，只装未访问的顶点 | `PriorityQueue<Vertex> q`，装所有待处理的顶点 |
| 判断邻居是否未处理 | `unvisited.contains(v)` | `!v.isVisited()` |
| 选当前顶点 | 遍历整个集合找距离最小的 | `q.poll()`，堆顶天然就是最小的 |
| 距离变小之后 | 从集合中 `remove` | 再 `q.offer(neighbor)` 一次 |
| 处理完当前顶点 | 从集合中把它删除 | 从队列中把它 `poll` 出来 |

其中第四步稍微有些不一样：现在用了优先级队列以后，除了更新邻居的距离以外，我们还需要把更新后的顶点重新给它加入到队列里去。

> **为什么更新完还要重新 offer 一次？**
> 其实主要是因为我们 Java 中的优先级队列，如果它的距离发生了变化，它并不会自动去调整这个顶点在队列中的位置。所以我们把这个顶点再给它重新加入到队列里，重新加入的时候它就会调整它的位置了。
> 虽然说将来这个顶点在队列中会有重复，但是位置更为重要——因为我们要从这个队列中选取距离最小的那个。这是跟以前不一样的地方。

队列的创建很简单，换成 Java 自带的 `PriorityQueue`，队列的名字叫 `q`，里面放顶点对象。优先级队列需要一个比较器来比较元素在队列中的大小，我们显然不应该直接用顶点本身去比较，所以用一个泛型的比较器对象，用 `Comparator` 的 `comparingInt` 方法——它能够拿到对象的一部分，用这一部分进行比较。那我们现在显然是要拿到顶点的距离部分作为比较的依据：拿到顶点对象以后，进一步拿到它的距离，根据这个距离进行比较。Java 中的优先级队列默认就是一个小顶堆，所以距离更小的会放在队列的头部，或者说堆的顶部。

```java
PriorityQueue<Vertex> q =
        new PriorityQueue<>(Comparator.comparingInt(v -> v.getDist()));
```

```java
public static void dijkstra(Graph graph, Vertex source) {
    // 第二步不用动：起点距离为 0，其余顶点距离一开始都是无穷大
    source.setDist(0);
    for (Vertex v : graph.getVertices()) {
        if (v != source) {
            v.setDist(Integer.MAX_VALUE);
        }
        q.offer(v);          // 把所有顶点都加到队列里去
    }

    // 只要队列不为空就一直循环，队列空了表示所有顶点都处理完了
    while (!q.isEmpty()) {

        // 第三步：找距离最小的顶点——现在非常容易，都不用调方法了，
        //         直接 poll 队列的头部就是它
        Vertex current = q.poll();

        // 第四步：更新邻居的距离
        for (Edge edge : current.getEdges()) {
            Vertex neighbor = edge.getTo();
            updateDist(neighbor, current.getDist() + edge.getWeight(), current, q);
        }
    }
}

private static void updateDist(Vertex v, int dist, Vertex prev, PriorityQueue<Vertex> q) {
    if (!v.isVisited() && v.getDist() > dist) {
        v.setDist(dist);
        v.setPrevious(prev);
        q.offer(v);            // 距离变了，必须重新入队才会调整位置
    }
}
```

原来那个"到集合里去遍历找最小值"的方法因为用不上了，可以直接删掉。第五步处理完当前顶点要把它移除，移除的话我们这回调的是队列的 `poll` 方法，而不是从集合中删除。

改完之后测试一下，看它跟改动前后有没有发生变化。结果仍然是正确的：v1 的最小距离是 0，v2 是 7，v3 是 9，v4 和 v5 都是 20，v6 是 11。这个结果跟我们改动之前是一致的。

#### 队列里的重复条目，以及 visited 的真正用途

我们把每次循环时队列的内容都打印出来看一下（每个顶点我都重写了它的 `toString`，这样能看得更清楚），走一遍就明白了。

刚开始队列里有所有的顶点，v1 的距离是 0，除了 v1 以外其他顶点刚开始的距离都是整数的最大值。第一次循环我们就选取了距离最小的 v1 作为当前顶点，去更新他邻居的距离——就是 v2、v3、v6 这几个顶点的距离，它们被更新成了 7、9、14。

这里同学们就会发现，我们这个队列中的顶点是不是有重复的了？v2 出现了两次，v3 也是两次，v6 也两次。

```text
v3（dist 还是 MAX）本来就在队列里
  │
  │  ← v1 当选，v1 → v3 这条边松弛成功，v3.dist 改成 9
  ▼
q.offer(v3)   把同一个对象又塞了一份引用进去

队列里就变成：   ……   v3(9)   ……   v3(9)   ……
```

为什么会这样呢？因为一开始 v2、v3、v6 都在我的队列当中，但是后来我去找他们的邻居的时候，发现邻居的距离需要更新——v2、v3、v6 的距离都要更新。而我们现在的逻辑就是：一旦发现了更小的距离，除了更新这个距离以外，就把这个顶点又加了一份，加到队列当中。所以我们看到了两个 v2、两个 v3、两个 v6。当然它俩其实是同一个对象，只不过这个队列里加了两个引用。

我们继续往下走。执行到"从队列中移除当前顶点"这一行，第一次循环相当于就把我们的 v1 移除了。移除以后第二次循环再进来，队列中剩下的这些顶点里，我们再选一个距离最小的对它进行处理——这回选中的是 v2，因为它的距离 7 是最小的。

不过我们也看到了，对于 v2 来讲有重复的引用，也就是接下来第一次循环会处理一个 v2，第二次再循环又处理一个 v2。那显然接下来的更新 v2 的邻居这段逻辑被执行了两遍。当然多执行一遍也不会对我们的结果产生影响，结果仍然是正确的，但是显然没有必要。

那怎么让这段逻辑只执行一次呢？其实我们可以利用上这个 `visited`：如果 `visited` 是 `false`，表示他还没有处理过；只有还没有处理过的时候，我们才去根据他的距离去更新邻居，并且把它的 `visited` 设为 `true`。那下次再遇到一个相同的引用时，这个 `visited` 已经是 `true` 了，我们就不会进入这个 if 语句块里边去执行更新邻居距离这段逻辑了。

```java
while (!q.isEmpty()) {
    Vertex current = q.poll();
    if (!current.isVisited()) {           // 重复的引用会被这一层挡掉
        current.setVisited(true);
        for (Edge edge : current.getEdges()) {
            Vertex neighbor = edge.getTo();
            updateDist(neighbor, current.getDist() + edge.getWeight(), current, q);
        }
    }
}
```

这样再运行一遍，虽然表面上看起来跟刚才没有什么区别，但是避免了一些不必要的代码执行，结果还是跟之前一样的。

剩下的都差不多，每次都是选一个距离最小的去执行相应的处理。队列里有重复的也没关系，我们只要判断一下首次执行的时候去更新它的邻居距离就行了，后续再遇到重复的引用，这个逻辑实际上是不会执行的。

### 有负边时，Dijkstra 错在哪

Dijkstra 有一个隐含的前提：整个图里没有负权重。如果图中没有这种负权重，它的工作是没有问题的；但是如果 Dijkstra 算法的途中出现了负权重的边，那么它有可能就工作不正确了。

来看一个例子。还是这张图，起点 v1 的初始距离设置成 0，其他顶点初始距离都设置成无穷大。

```text
   ┌───────── 1 ────────┐
   ▼                    │
   V1 ──2──► V2 ──-2──► V3 ──1──► V4
```

#### 一遍错误的推演

我们过一遍。首先拿到 v1，看看他邻居的距离需不需要更新。那显然是可以更新的：v1 到 v3 这个距离是 1，比它初始设的无穷大小，所以把 v3 的距离更新成 1；到 v2 也类似，它的距离是 2，比无穷大小，所以把它的距离更新成 2。这样 v1 就处理完了，以后不再处理它。

接下来在剩下的顶点里，我们要在未处理的顶点集合里找一个距离最小的顶点。按照 Dijkstra 算法我们认为 v3 它的距离最小，所以接下来处理 v3。v3 的邻居呢就一个，就是这里的 v4。那它的距离是不是也可以更新？1 + 1 = 2，比初始的无穷大小，所以把 v4 的距离更新成 2。这样 v3 也处理完了。

v3 处理完之后，未处理的顶点集合里还剩下 v2 和 v4，他俩距离一样，所以随便挑一个处理，比如说处理 v2。当然对 v2 来讲他没啥可处理的，因为它的邻居 v3 已经处理过了，所以他不会走那个更新逻辑了，还是保持距离是 2。最后 v4 也是一样，他也没有其他出边，所以也没有邻居可以处理，最终也被处理完了。

于是我们得到的最短距离是：v1 到 v2 是 2，v1 到 v3 是 1，v1 到 v4 是 2。

```text
Dijkstra 给出的答案：   V1→V2 = 2    V1→V3 = 1    V1→V4 = 2
```

#### 这个结果是错的

大家可以先思考一下，看这个结果是否正确。

我们发现这个结果其实是不正确的。从 v1 到 v3 距离是 1，这没错；但是如果他从 v2 过来呢？先到 v2，再从 v2 到 v3，这个距离是 2 + (-2) = 0，是不是比 1 更小？所以从 v1 到 v3，它的最短距离其实应该是 0。

同理，我们到 v4 的话，如果是从 v1 到 v2、到 v3，然后再到 v4，那这个最短距离是不是应该是一，而不是这里的二。

所以我们发现，整个图里有负边存在的情况下，Dijkstra 算法就得出了一个错误的结果。

#### 根因：局部最优不等于全局最优

那问题到底出在哪呢？我们把步骤回退到之前的某一步——就是 v1 已经处理完了，它两个邻居 v3、v2 的距离也都更新了，到这一步。接下来我们要做什么呢？也是要在未处理的这几个顶点里选择一个距离最小的。我们选择的应该是距离最小的 1，也就是 v3 这个顶点。

问题就出在这儿。然后对他的邻居做更新以后，我们还会再处理它吗？就不会了。我们会认为这个 v3 会被从未处理的顶点集合中移除，以后再不会对它进行处理了。

那我们为什么会有这样一个假设呢？就是因为我们认为 Dijkstra 算法里所有的边都应该是正的。是正的情况下，你想我找到的 1 肯定是最小的，其他的边不可能有比它更小的。

但是矛盾就在于，我们现在存在负边。如果是从 v1 到 v2 再到 v3 来的话，他俩整个加起来是 0，是不是比你的 1 更小？所以我们在这一步做出了一个错误的判断：我们选择了一个局部最优的最短距离，但实际上没选对。没选对以后呢，我们对它的距离就不做更新了——其实它的距离以后是不是应该再更新一次才对。所以就在这一步出现了问题。

> **结论**：Dijkstra 的正确性依赖"边权非负"这个前提。一旦出现负权，"当前距离最小的顶点不可能再被更优路径改善"这个假设就塌了。

### Bellman-Ford：不挑最小，边边都过

知道了问题的原因，我们就知道怎么解决。这就是我们接下来要介绍的 Bellman-Ford 算法。

对比一下两个算法的思路。Dijkstra 是：每一轮我都要挑一个距离最小的顶点，然后对它邻居的距离做更新处理。而 Bellman-Ford 呢，他说我也不去挑什么距离最小的顶点了。每次我都拿到所有的边——你看我这个图里一共有四条边，每次我都拿到所有的这四条边，然后对这四条边指向的顶点都做距离的更新。这样经过若干轮的更新操作，肯定不会有疏漏。这就是他的一个思想。

初始状态跟 Dijkstra 是类似的：起点距离设置成 0，其他几个顶点的距离设置成无穷大。我们给所有的边给它一个编号（这个编号其实谁先谁后无所谓），这张图里是这样：

```text
   ┌────────── ③ 1 ─────────┐
   ▼                       │
   V1 ──④ 2──► V2 ──② -2──► V3 ──① 1──► V4
```

我们待会就按 1、2、3、4 这个顺序来处理每一条边。

```text
初始：  V1=0    V2=∞    V3=∞    V4=∞

第 1 轮
  ①  V3→V4    V3=∞    ∞ + 1  = ∞      不更新
  ②  V2→V3    V2=∞    ∞ - 2  = ∞      不更新
  ③  V1→V3    V1=0    0 + 1  = 1       更新：V3=1
  ④  V1→V2    V1=0    0 + 2  = 2       更新：V2=2
轮末：  V1=0    V2=2    V3=1    V4=∞
```

1 号边的起点距离是无穷大，无穷大加 1 你看是不是小于终点的距离？无穷大加 1 跟无穷大比，其实没有谁大谁小，都是无穷大，所以这个距离我们可以暂不更新——没找到更小的距离就不更新。2 号边也是同样的道理，两边只要都是无穷大的这种，我们就跳过去。

一共要进行几轮呢？就是跟顶点的数目有关。我们四个顶点的话，总共做三轮处理就可以。我们已经进行了第一轮，接下来看第二轮。

```text
第 2 轮
  ①  V3→V4    V3=1    1 + 1  = 2       更新：V4=2
  ②  V2→V3    V2=2    2 - 2  = 0       更新：V3=0
  ③  V1→V3    V1=0    0 + 1  = 1       1 不比 0 小，不更新
  ④  V1→V2    V1=0    0 + 2  = 2       2 不比 2 小，不更新
轮末：  V1=0    V2=2    V3=0    V4=2

第 3 轮
  ①  V3→V4    V3=0    0 + 1  = 1       更新：V4=1
  ②③④                                   都不更新
轮末：  V1=0    V2=2    V3=0    V4=1      ← 最终答案
```

至此为止，所有的边都处理了三遍，我们得出的最终最短距离是：v1 到 v3 是 0，v1 到 v2 是 2，v1 到 v4 是 1。这回我们的最短距离都计算正确了。

> **提示**：为什么是"顶点数减一"轮？因为在不存在负环的前提下，最短路径不会绕着环再回到同一个顶点——没有负环，绕一圈只会更亏，把它剥掉不会让路径变长。所以最短路径最多由 |V| - 1 条边组成。每轮把所有边过一遍，每过一遍至少有一条边的信息被确定下来，|V| - 1 轮就足够走完全程。

### Bellman-Ford 的代码实现

顶点还是刚才那些顶点，边也跟那张图是一致的。我写了一个方法，它接受两个参数：第一个参数就是顶点的集合，包含了我们这里的 v1、v2、v3、v4 这四个顶点；第二个参数呢就是起点，就是这里的 v1。

先设置初始距离：起点 source 的初始距离设置成 0，其他几个没设置的 v2、v3、v4，它们的初始距离都是无穷大，也就是整数的最大值。

按照我们刚才的算法描述，要进行几轮循环是跟顶点数目有关的。四个顶点我们就要进行三轮循环，所以我们先拿到顶点的数目 `size`，然后写一个循环，从零循环到 `size - 1` 次，这就是我们外层的循环代码。

那每次循环的时候做什么事呢？是要处理所有的边呀，1、2、3、4 这四条边都得处理。那所有的边呢，其实我们通过顶点就可以拿到它里面这些所有的边了——先遍历顶点的集合，然后针对每个顶点，我们再去遍历每个顶点边的集合。做了这两次遍历以后，是不是就能拿到所有的边了。

```java
public static void bellmanFord(Graph graph, Vertex source) {
    List<Vertex> vertices = graph.getVertices();

    // 初始距离
    for (Vertex v : vertices) {
        v.setDist(v == source ? 0 : Integer.MAX_VALUE);
        v.setPrevious(null);
    }

    // 外层循环：顶点个数 - 1 轮
    int size = vertices.size();
    for (int i = 0; i < size - 1; i++) {

        // 两次遍历拿到所有的边：先顶点，再该顶点的边
        for (Vertex s : vertices) {              // s = start
            for (Edge edge : s.getEdges()) {
                Vertex e = edge.getTo();         // e = end

                // 起点距离为无穷大时直接跳过，后面的比较没有意义
                if (s.getDist() != Integer.MAX_VALUE
                        && s.getDist() + edge.getWeight() < e.getDist()) {
                    e.setDist(s.getDist() + edge.getWeight());
                    e.setPrevious(s);
                }
            }
        }
    }
}
```

处理每一条边其实很简单：起点的距离加上这条边的权重，如果小于终点的距离，那就做一次更新，把终点的距离更新成前面这个更小的值。

我把变量名改了一下——这里的 `v` 实际上是这条边的起点，所以起点换一个变量名叫 `s`（start）；这条边还有一个终点，也换一个更有意义的变量名叫 `e`（end）。这样边的起点和终点就都有了。

这里有个特殊情况要单独考虑：如果起点距离是无穷大，你拿它做加减乘除再跟别的数比较，是不是就没有意义了？所以只有当起点的距离不是无穷大时，我们才做后面的检查距离的操作。

写完之后我们最后对它的结果做一个验证，遍历我们的顶点集合，看一下求出来的最短距离是多少。走一遍：v1 到自己最短距离是 0，v1 到 v2 最短距离是 2，到 v3 最短距离是 0，最后到 v4 最短距离是 1。就跟我们刚才的分析结果是一致的。你看 Bellman-Ford 算法他的逻辑是比较简单的。

还有一个小的需求，这个我们之前也做过。比如从 v1 到 v4，这个最短距离是 1，那它是从哪条路来的呢？我们从图上可以看出来，是他先从 v1 到 v2，然后到了 v3，再到了 v4，这样得到了整个这个最短路径 1。那我们怎么拿到整个这个路径呢？

其实也简单，我们前面也做过：当时我们给这个顶点加了一个属性叫 `previous`，是表示将来你是从何而来。所以我们在更新那个最短路径时，只要把这个 `previous` 做一个正确的更新就可以了。因此我们一旦发现最短路径需要更新了，那么就把它的 `previous` 也顺便更新一下。就比如说现在这个 `e` 是这里的 v4，那它的 `previous` 是不是应该是这里的 v3？把它更新成我们这边的 start 这个顶点就行了。

最后遍历的时候要把它打印出来检查一下，也还是判断一下：如果它的 `previous` 不等于 null，就去打印一下这个 `previous` 的名字；如果等于 null，我们就打印一个 null。

```java
for (Vertex v : graph.getVertices()) {
    System.out.print(v.getName() + "  dist=" + v.getDist() + "  ");
    System.out.println(v.getPrevious() != null ? v.getPrevious().getName() : "null");
}
```

测一遍可以看到：v4 的最短路径是从 v3 来的；那 v3 这个最短路径 0 又是从哪来的呢？是从 v2 来的；那 v2 呢是从 v1 来的；那 v1 呢它前面没有了，就是个 null。这样我们就知道了这个最短路径，整个这个形状也就有了。

### 负环：唯一没有解的情况

Bellman-Ford 可以在求最短路径时处理负边，但是有一种情况他也是没有解的：一旦我的图中出现了一种叫负环的情况。

#### 什么是负环

什么叫负环呢？第一，这个路径它构成了一个环。你看 v1 到 v2，v2 到 v3，结果 v3 呢又能回来回到 v1，这是构成环了对吧？第二，除了构成环以外呢，整个这个环中的所有边的权重加起来，如果是负数的话，那我们就说出现了负环。

```text
   ┌────────── ③ 1 ─────────┐
   ▼                       │
   V1 ──① 2──► V2 ──② -4──► V3 ──④ 1──► V4
```

你看这里的 2 加上 -4 再加上 1，这个结果是 -1，就表示这个环里权重加起来是负数。那这叫负环，负环的情况下，我们的求最小路径是没有解的，它的解相当于是个负无穷大。

#### 为什么没有解：再走一遍

那为什么会这样呢？我们先按正常的 Bellman-Ford 算法走一遍流程，先看下大概的效果。这里呢仍然是 v1 这个起点，它的距离是 0，其他几个顶点的距离都是无穷大，然后路径的顺序我们按 1、2、3、4 这个顺序来处理。

```text
初始：  V1=0    V2=∞    V3=∞    V4=∞

第 1 轮
  ①  V1→V2    0 + 2  = 2       更新：V2=2
  ②  V2→V3    2 - 4  = -2      更新：V3=-2
  ③  V3→V1    -2 + 1 = -1      更新：V1=-1
  ④  V3→V4    -2 + 1 = -1      更新：V4=-1

第 2 轮
  ①  V1→V2    -1 + 2 = 1       更新：V2=1
  ②  V2→V3    1 - 4  = -3      更新：V3=-3
  ③  V3→V1    -3 + 1 = -2      更新：V1=-2
  ④  V3→V4    -3 + 1 = -2      更新：V4=-2

第 3 轮
  ①  V1→V2    -2 + 2 = 0       更新：V2=0
  ②  V2→V3    0 - 4  = -4      更新：V3=-4
  ③  V3→V1    -4 + 1 = -3      更新：V1=-3
  ④  V3→V4    -4 + 1 = -3      更新：V4=-3

三轮跑完：  V1=-3   V2=0   V3=-4   V4=-3
```

我们 Bellman-Ford 算法三轮完成以后，就把最小距离算出来了，是 -3、0、-4 和 -3。但是这个结果对吗？显然是不正确的。因为我们如果再继续运行下去的话，你会发现这个最小距离还有更小的。我们不妨接着来看一下，同学们再看一轮就能看出这个问题来：

```text
第 4 轮
  ①  V1→V2    -3 + 2 = -1      <  0      更新：V2=-1
  ②  V2→V3    -1 - 4 = -5      < -4      更新：V3=-5
  ③  V3→V1    -5 + 1 = -4      < -3      更新：V1=-4
  ④  V3→V4    -5 + 1 = -4      < -3      更新：V4=-4
```

我们发现经过一轮以后，我们又找到了比上一轮更短的距离。这样我们就可以无限地执行下去，直到这个距离是负的无穷大。因此我们发现，一旦出现了负环，我们就没有解了，最终这些最短距离都会被变成负无穷大。

#### 怎么检测

那我们怎么去检测出有这种负环的情况呢？

其实也简单，这个规律你应该已经发现了：按照正常的道理，我们进行"顶点个数减一轮"循环，就能求出最后的最短距离。我们现在四个顶点，循环三轮就能把这个最短距离给他求出来。但是三轮过后，如果他还能找到更短的距离、还能进入这个 if 条件，是不是就相当于出现了负环？

> **结论**：跑完 |V| - 1 轮之后再加一轮，如果这一轮仍然发生了松弛，说明存在负环——正常情况下最短路径这时早就定型了，它没定型，只能是被某个负环一遍遍往下拉。

所以这个代码就留给你自己去实现了：你只要在正常的三轮过后——顶点个数减一轮过后——你又能进入这个 if 条件，就说明它出现了负环。这时候我们就可以不要继续执行下去了，告诉它"出现负环了，没有解"。

### 本讲提到的题目

**怎么判断图中有没有负环？**（讲负环时我抛给大家、也留在代码里的那个问题）

思路：正常跑完 |V| - 1 轮之后，最短距离就该定型了。所以在这之后再来一轮，只要还有边能走进那个 `if`——起点距离不是 `Integer.MAX_VALUE`，并且 `start.dist + weight < end.dist`——就说明存在负环。这时候立刻停止，返回"出现负环，没有解"，不要让它继续往负无穷大跑。

正文里已经把这个 `if` 的条件和轮数一轮一轮推演过一遍了，直接在上面那段 `bellmanFord` 的 `for (int i = 0; i < size - 1; i++)` 之后再补一轮带标志位的检测就可以了。

## 全源最短路径：把弗洛伊德算法从手推到代码
> 对应块：BLK21 | 覆盖分集：P87-P90 | 块标题（分集名）：《进阶数据结构和算法-241-图-Floyd-Wa》

### 一次算完所有顶点对

前面几节课我们学的最短路径算法——迪克斯特拉那个被他戏称为"龟兔赛跑"的算法——都是**单源**的：源点固定，我一次只能求出一个顶点到其他所有顶点的最短路径。

这一节换成**全源**。所谓全源，就是我把算法跑一遍，所有顶点到其他顶点的最短路径全给我算出来，一次性的。v1 到别人、v2 到别人、v3 到别人、v4 到别人，一趟全齐。

> **定义**：只指定一个源点、求它到其余所有顶点最短路径的算法，叫单源最短路径；一次把所有顶点对之间的最短路径全求出来的，叫全源最短路径算法。

这个算法叫**弗洛伊德（Floyd）算法**，全称 Floyd-Warshall。说到这儿插一段人物八卦：迪克斯特拉和弗洛伊德，两个人都是图灵奖得主。有意思的是，我们前面学的那个最短路径算法也是同一个人发明的——他和迪克斯特拉，一个搞出了龟兔赛跑，一个搞出了今天这个。

先把使用前提说清楚，不然等下看例子会懵：

> **注意**：弗洛伊德算法可以处理**负权边**，但遇到**负环**照样不行。这两条我们拿例子当场验一遍。

我们即将举的这个图里是有负边的（`v1 → v3` 的权重是 -2）。再看有没有负环：有一条环是 `v2 → v1 → v3 → v4 → v2`，权重加起来是 4 + (-2) + 2 + (-1) = 3，不是负数；另一条环是 `v2 → v3 → v4 → v2`，3 + 2 + (-1) = 4，也不是负数。

所以虽然这个图里有环，但没有负环，算法照常工作。

那这个例子图长什么样？就五个顶点为 v1 v2 v3 v4，四条边加上五条——对，五条边：

```text
出边清单（adjacency）：

v1 ──(-2)──▶ v3
v2 ──(4)────▶ v1
v2 ──(3)────▶ v3
v3 ──(2)────▶ v4
v4 ──(-1)───▶ v2
```

读图说明：箭头是有向的，从左端出发指向右端；这五条边就是后面初始化那张表的全部依据。

### 先有这张二维表：初始化就是先认直连的边

这个算法需要一张二维表格，用来记录顶点到顶点之间的最短距离。横轴是 v1 到 v4，纵轴也是 v1 到 v4——行是"从谁出发"，列是"到谁那儿去"。

先做初始化，一格一格来：

- `v1 → v1`：自己到自己，距离初始化成 **0**。自己到自己总归是零；
- `v1 → v2`：图上没有从 v1 指向 v2 的箭头，不连通，初始化成 **∞**；
- `v1 → v3`：连通，权重是 **-2**，就写 -2；
- `v1 → v4`：又不连通，**∞**。

v1 这一行有了。接着 v2：`v2 → v1` 通，距离 **4**；`v2 → v2` 是 **0**；`v2 → v3` 通，距离 **3**；`v2 → v4` 不通，**∞**。

v3：`v3 → v1` 不通 **∞**，`v3 → v2` 不通 **∞**，`v3 → v3` 是 **0**，`v3 → v4` 通，距离 **2**。

v4：`v4 → v1` 不通 **∞**，`v4 → v2` 通，距离 **-1**，`v4 → v3` 不通 **∞**，`v4 → v4` 是 **0**。

于是初始表长这样：

```text
        v1     v2     v3     v4
  v1 [   0      ∞     -2      ∞  ]
  v2 [   4      0      3      ∞  ]
  v3 [   ∞      ∞      0      2  ]
  v4 [   ∞     -1      ∞      0  ]
```

读图说明：行是起点，列是终点；`∞` 表示当前还"此路不通"，不是真的距离，是"暂时没找到路"。

> **提示**：这张初始表记录的是"从一个顶点直接能连通到其他顶点"的最短距离——注意是直连的边。走弯路的那些可能性，全靠后面的循环一层层补进来。

### 四轮循环：每一轮借助一个顶点中转

接下来的活儿就是：**再经过顶点 k 的循环**，把整个算法做完。k 从 1 走到 4，一共四轮，每一轮干的是同一件事——看看这些顶点借助 v1（换成 v2、v3、v4）能不能到别的顶点去，如果能，而且距离更短，就把这个距离更新掉。

动之前先在心里把表格复制一份，留着对照。

#### 借助 v1

从 v1 自己开始先跳过：v1 借 v1 去别的地方，跟 v1 自己出发没有任何区别，没意义。

看 v2：v2 能不能借 v1 到 v3、v4？

- v2 先到 v1，这条路是通的，距离 4；
- 接过 v1 之后能不能到 v3？看图，通的，权重 -2；
- 总路径长度：4 + (-2) = 2。

比原来 v2 直接到 v3 的 3 近了吧？近了。那就把 `dist[v2][v3]` 从 3 更新成 2。

再问 v2 借 v1 能不能到 v4？到不了——v1 到 v4 是 ∞，此路不通，那就不用管了。

看 v3：v3 到 v1 是 ∞，不通，压根借不上 v1，v2、v4 都别想了，这行不更新。

看 v4：v4 到 v1 也是 ∞，同样借不上，这一行也不用看。

所以 k = 1 这一轮，唯一被更新的是 `dist[v2][v3]`：3 → 2。

#### 借助 v2

- v1 这行：v1 到 v2 是 ∞，借不上 v2，这行跳过；
- v2 这行：自己借自己没意义，跳过；
- v3 这行：v3 到 v2 是 ∞，借不上，跳过；
- v4 这行：**有戏**。v4 能到 v2，距离是 -1。

既然借上了 v2，就接着问：借 v2 能不能再到 v1？可以，v4 经 v2 间接到 v1，整条路径长度是 -1 + 4 = 3。原来 v4 根本到不了 v1（是 ∞），所以更新，把 ∞ 改成 **3**。

再问：借 v2 能不能到 v3？也可以，v2 到 v3 那格现在是 2，总长度 -1 + 2 = **1**。原来 v4 也到不了 v3（∞），同样更新。

这一轮更新了两个值：`dist[v4][v1] = 3`、`dist[v4][v3] = 1`。

#### 借助 v3

- v1 能到 v3，距离 -2。借 v3 能不能到 v2？不行，v3 到 v2 是 ∞，不看。能到 v4？可以，权重 2。总长度 -2 + 2 = **0**，原来 v1 到不了 v4，把 ∞ 更新成 **0**；
- v2 能到 v3，距离 2。借 v3 能到 v1 吗？不行，∞。能到 v4 吗？可以，权重 2。总长度 2 + 2 = **4**，原来 v2 到 v4 是 ∞，更新成 **4**；
- v3 自己借自己，跳过；
- v4 能到 v3，但 v3 到 v1、v3 到 v2 都是 ∞，两头发不通，这行等于没处理。

这一轮也更新了两个距离。

#### 借助 v4

- v1 能到 v4，距离是 **0**——注意这个 0 不是凭空来的，它是先到 v3（-2）再到 v4（+2），-2 + 2 = 0 攒出来的。借 v4 到 v2？可以，权重 -1，总距离 0 + (-1) = **-1**，原来 v1 到 v2 是 ∞，更新。借 v4 到 v3？也可以，0 + 1 = 1，但原来 v1 到 v3 已经是 **-2**，比这个 1 小，所以**不更新**，留着 -2；
- v2 能到 v4（先 v2 → v1 → v3 → v4，整条是 4）。借 v4 到 v1？路径长度 3 + 4 = 7，比原来 v2 到 v1 的 4 大，**不更新**。借 v4 到 v3？长度 5，也比原来的 2 大，**不更新**；
- v3 能到 v4，距离 2。借 v4 到 v1 和 v2 都可以，而原来这两个都是 ∞，那就更新：2 + 3 = **5**（`dist[v3][v1]`），2 + (-1) = **1**（`dist[v3][v2]`）。

到此为止，表格里的数字填满了，一个 ∞ 都不剩：

```text
        v1     v2     v3     v4
  v1 [   0     -1     -2      0  ]
  v2 [   4      0      2      4  ]
  v3 [   5      1      0      2  ]
  v4 [   3     -1      1      0  ]
```

读图说明：这张表就是最终答案，任意格 `(i, j)` 就是从 vi 到 vj 的最短距离。

> **结论**：跑完 k = 1, 2, 3, 4 四轮，`dist` 表里记录的就是所有顶点到其他顶点的最短距离。以 v1 为例：到 v2 是 -1，到 v3 是 -2，到 v4 是 0；v2 到 v1 是 4，到 v3 是 2，到 v4 是 4；以此类推，全源的答案一次性齐活。

### 落到代码上：三层循环怎么表达"借助"

思路前面已经掰开揉碎讲完了，现在看怎么用代码写。

#### 初始化：两层循环加一个 map 提速

先准备四个顶点和五条边，跟图上完全对应：v1 有一条指向 v3 的边权重 -2；v2 有两条边，分别指向 v1 和 v3，权重是 4 和 3；v3 有一条权重为 2 的边指向 v4；v4 有一条权重 -1 的边指向 v2。

方法签名就一个，把顶点集合传进去。进来第一件事拿到顶点的个数 `size`，按它开一张二维表。我在旁边还准备了一个 `print` 方法，专门打印这张二维表，遇到无穷大就打个无穷大的符号，看着舒服一些。刚开出来的时候表里全是一堆 0，这是准备工作。

正式初始化用两层循环：外层 `i` 从 0 到 `size`，遍历每一行的顶点；内层 `j` 从 0 到 `size`，遍历每一列的顶点。外层的点记作 `v`，内层的点记作 `u`——注意这个命名，`v` 是行（起点），`u` 是列（终点）。

拿到 `v` 和 `u` 之后分两种情况：

1. 俩是同一个顶点（`v == u`），比如 v1 到 v1，把距离置 **0**；
2. 俩不是同一个顶点，那就看它们连不连通——不通置 **∞**，通就置成**权重**。

那怎么快速判断连不连通？其实只要看外层这个顶点的**边的集合里有没有内层这个顶点**。外层循环到 v1 了，内层循环到 v2，就去 v1 的边集合里找 v2，找不到说明不连通；内层到 v3，找到了，说明连通，直接把权重写进去。

> **易错点**：可别直接拿 List 去 `contains`，边集合是个列表容器，得一个个比，效率太难看。这里用 map 提速——**key 放顶点，value 放权重**，查找快得多。

```java
public void floydWarshall(Graph graph) {
    int size = graph.getVertices().size();
    int[][] dist = new int[size][size];

    // 外层 i 遍历每一行的顶点，内层 j 遍历每一列的顶点
    for (int i = 0; i < size; i++) {
        Vertex v = graph.get(i);

        // 把外层顶点的边集合转成 map：key 是边指向的顶点，value 是权重
        Map<Vertex, Integer> edgeMap = v.getEdges().stream()
                .collect(Collectors.toMap(e -> e.getTo(), e -> e.getWeight()));

        for (int j = 0; j < size; j++) {
            Vertex u = graph.get(j);
            if (v == u) {
                // 同一个顶点：自己到自己，距离为 0
                dist[i][j] = 0;
            } else {
                // 找得到就是连通，返回权重；找不到给个默认值 Integer.MAX_VALUE 当无穷大
                dist[i][j] = edgeMap.getOrDefault(u, Integer.MAX_VALUE);
            }
        }
    }
    print(dist);
}
```

这里有个坑必须提醒一句：既然用了 map 当 key，那 key 的哈希值和相等性就要靠 `hashCode` 和 `equals` 撑着，这两个方法一定得给上，千万别忘了写。顶点的这两个方法就拿 `name` 来生成——因为 name 是唯一的，靠它就能把我们这些顶点区分开。

```java
@Override
public int hashCode() {
    return Objects.hash(name);
}

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Vertex vertex = (Vertex) o;
    return Objects.equals(name, vertex.name);
}
```

#### 三层循环与那个转手的加法

第二个阶段的核心思想刚才说了：看能否通过借助 k 到达其他顶点，途中遇到更短的距离就用更短的更新表格。四个顶点就四轮，借助 v1 一轮、v2 一轮、v3 一轮、v4 一轮。

难点在于：有些同学想不到用代码怎么表达"借助"这回事。说穿了很简单——**三层循环**。最外层循环变量是 `k`，从 0 循环到 `size`，对应的就是我们说的第一轮、第二轮、第三轮、第四轮；里面再来两层，分别循环 `i` 和 `j`，体现的是每次做操作都要把每一行、每一列都处理到。

怎么表达"借助"？从一个具体例子看。假设内层循环已经走到 v2 这一行了，我要借 v1 到别的顶点去。第一步得先找到 v2 到 v1 的路径吧？v2 的下标是 1，所以 `dist[1][0]` 对应的就是 v2 到 v1，这一段有了。

那 v1 到其他顶点怎么表示？看 v1 那一行：v1 到 v1 是 `dist[0][0]`，v1 到 v2 是 `dist[0][1]`，v1 到 v3 是 `dist[0][2]`，v1 到 v4 是 `dist[0][3]`——右边这一列体现的就是从 v1 到其他所有顶点。

两边一连起来看就明白了：我先到 v1，然后通过 v1 间接到其他顶点，中间把两段距离加起来，这个加法就是"v2 经由 v1 走到了别的地方"。

再把式子和变量挂上钩：那一串"0"（第二行那个 1，以及 `dist[1][0]` 里的 0）对应的是**行** `i`；中间那一堆 0 对应的是最外层的 `k`，因为我要借助第 k 个顶点；最后那排 0 1 2 3 对应的是**列** `j`。合起来就是：

```text
  第一段（行 i = 1，即 v2 → v1）：  dist[1][0]
                |
                |  把 v2 交给 v1 之后，下一段由 v1 说了算
                v
  第二段（行 k = 0，即 v1 → 所有）：  dist[0][0]  dist[0][1]  dist[0][2]  dist[0][3]
                                       v1→v1     v1→v2     v1→v3     v1→v4

  两段一加 =  dist[i][k] + dist[k][j] = v2 经 v1 到了 vj
```

读图说明：上面一段是"起点 v2 到中转点 v1"的距离，中间一段接的是"中转点 v1 到各个目的地"的距离；下面四格各自对应一个终点 j，把它们和上面那一段加起来，就是 v2 借道 v1 到各个地方的长度。

> **提示**：记住这个对应关系，后面就不会写错——**i 是行（起点），k 是中转（那个被借的顶点），j 是列（终点）**。中间那一堆 k，一个都不能少。

另一个式子就更好懂了，`dist[i][j]`：不借助 k 顶点，我从第 i 行的顶点直接到第 j 列的顶点。

两个式子一联系：要是借 k 绕过去更短，那就用更短的更新原来的。于是代码就写成——判断一下，如果借 k 到达目标的距离比直接到达更短，就把 `dist[i][j]` 更新成 `dist[i][k] + dist[k][j]`。

#### 路不通就别算了

代码写到这基本就成了，但有个特殊情况必须处理：**路不通的时候没必要硬算**。

比如循环到 v3，v3 要借 v1 去别的地方，可 v3 到 v1 是 ∞，此路不通——那后面拿 v1 到 v2、v3、v4 那些距离去算，全是白算。路不通的时候，后续的距离判断和更新操作一律没必要做。

而且"不通"有两种可能：可能是**起点到中转点**不通（v3 到 v1），也可能是**中转点到目标**不通（v2 到 v1 明明通了，但 v1 到 v4 是 ∞）。所以条件得写成：只有 `dist[i][k]` 不等于无穷大、**并且** `dist[k][j]` 也不等于无穷大，我们才做后续的判断和更新。

```java
// 第二阶段：k 必须在最外层，i 是行（起点），j 是列（终点）
for (int k = 0; k < size; k++) {
    for (int i = 0; i < size; i++) {
        for (int j = 0; j < size; j++) {
            // 两头都得通，否则没有继续算的必要
            if (dist[i][k] == Integer.MAX_VALUE || dist[k][j] == Integer.MAX_VALUE) {
                continue;
            }
            // 借 k 更短，就更新
            if (dist[i][k] + dist[k][j] < dist[i][j]) {
                dist[i][j] = dist[i][k] + dist[k][j];
            }
        }
    }
    print(dist);
}
```

对应的状态转移公式写成数学形式就是这样：

$$
dist[i][j] = \min\bigl(dist[i][j],\ dist[i][k] + dist[k][j]\bigr)
$$

前提是 `dist[i][k]` 和 `dist[k][j]` 都不是 ∞。

#### 跑一遍，跟手推对答案

写完就跑一下，每一轮结束都把整张数组打出来，和前面手动分析的对照。

- **k = 0（初始化完）**：`0 ∞ -2 ∞ / 4 0 3 ∞ / ∞ ∞ 0 2 / ∞ -1 ∞ 0`——跟手推的第一张表一模一样；
- **k = 1（借 v1）**：`0 ∞ -2 ∞ / 4 0 2 ∞ / ∞ ∞ 0 2 / 3 -1 1 0`——只有 v2 到 v3 那个 3 变成了 2；
- **k = 2（借 v2）**：`0 ∞ -2 0 / 4 0 2 4 / ∞ ∞ 0 2 / 3 -1 1 0`——多了 v1 到 v4 的 0、v2 到 v4 的 4；
- **k = 3（借 v4）**：`0 -1 -2 0 / 4 0 2 4 / 5 1 0 2 / 3 -1 1 0`——全表填满，一个 ∞ 都不剩。

> **结论**：程序的运行结果和手动分析的结果完全一致，算法实现完成。

### 距离知道了，路径长什么样：previous 数组

二维表只记了最短距离，可我还想知道这条最短路径的**详情**——到底是怎么走的、经过了谁。那就再来一张二维数组，类型是顶点类型，里面存的都是顶点引用，记录的是：这个路径是从哪个顶点走过来的，也就是**上一个顶点**。这个数组叫 `previous`，宽高都还是顶点的个数 `size`。

它要更新的地方只有两处：**初始化的时候**更新一次，**借助（更新距离）的时候**再更新一次。

#### 两处更新：初始化时和更新距离时

`previous` 一开始所有元素全是 `null`，这个是合理的——我一开始压根不知道它上一个顶点是谁、从哪儿走过来的。

初始化时，写在原来那个 `else` 的位置，也就是原来那段判断连不连通的逻辑里：先去 map 里 `get` 一下内层顶点 `u`，检查它在不在外层顶点的边集合中；**如果存在**（返回值不等于 `null`）说明是连通的，那就把"上一个顶点"更新成 `v`——它是从 v 走到 u 的，当然是 v；**如果不连通**，那就保持 `null` 不变。

```java
Map<Vertex, Integer> edgeMap = /* 见前文 */;

if (v == u) {
    dist[i][j] = 0;
} else {
    Integer weight = edgeMap.get(u);
    dist[i][j] = weight == null ? Integer.MAX_VALUE : weight;
    // 连通就记下"上一个顶点是不通就不记"
    previous[i][j] = weight == null ? null : v;
}
```

初始化跑完之后的 `previous` 长这样（打印时遇到 `null` 就打 `null`，否则打顶点名字）：

```text
        v1      v2      v3      v4
  v1 [  null   null    v1     null ]
  v2 [   v2    null    v2     null ]
  v3 [  null   null   null     v3  ]
  v4 [  null    v4    null   null  ]
```

读图说明：每格记的是"到这一列的顶点，是从左边哪个顶点走过来的"。比如 v1 那一行第三格写着 v1——v1 到 v3 是通的，所以对 v3 来说它的上一个顶点就是 v1，它是从 v1 走过来的。v1 到 v2、v1 到 v4 不通，两格都是 `null`；v1 到 v1 是自己，也不算数。其余几行一个道理。

借助的时候，是在 `if` 条件成立之后更新。看一个例子就明白了：某次循环循环到 v2，v2 要借 v1 到 v3——这条路是通的，v2 先到 v1 距离 4，v1 再到 v3 距离 -2，整条路径 4 + (-2) = 2，比原来直接从 v2 到 v3 的 3 要小，于是进了 `if` 条件，触发 `dist` 的更新。

那 `previous` 相应怎么更新？原来 v2 是直接到 v3 的，也就是对 v3 来讲它的上一个顶点是 v2；现在 v2 借 v1 到了 v3，而且更短，那对 v3 来讲，它的上一顶点就该更新成 **v1**——它是从 v1 过来的更短。所以就把这里原来的 v2 改成 v1。

代码就是这么一行：

```java
if (dist[i][k] + dist[k][j] < dist[i][j]) {
    dist[i][j] = dist[i][k] + dist[k][j];
    // 从借助 k 到达 j 的路过来，就是 previous 数组 k 行 j 列那一格
    previous[i][j] = previous[k][j];
}
```

所有轮次跑完，最终 `previous` 的第一行长这样：

```text
        v1      v2      v3      v4
  v1 [  null    v4      v1      v3  ]
```

读图说明：v1 到 v1 是自己，`null` 不看；v1 到 v2 是从 v4 过来的，说明 v1 要绕一圈到 v4 再拐到 v2；v1 到 v3 是直接过来的，上一顶点就是 v1 自己；v1 到 v4 是经由 v3 过来的，上一顶点是 v3。下面的几行都是同样的道理，同学们可以自己去理解每一行的含义。

#### 把路径打印出来

很多同学比较感兴趣的是把整条路径打印出来，方便观察。这块我提前准备了一个 `path` 方法，它接收这几个参数：`previous` 数组（存的就是最终结果）、顶点集合，还有 `i` 和 `j` 两个数，分别代表起点和终点——从哪个顶点到哪个顶点。

准备好之后直接写两层循环调用它：第一层 `i` 从 0 到 `size`，第二层 `j` 从 0 到 `size`，在循环里不断调用 `path(previous, 顶点集合, i, j)`，这样从 i 到 j 的所有路径就全被遍历出来打印了。

```java
for (int i = 0; i < size; i++) {
    for (int j = 0; j < size; j++) {
        path(previous, graph.getVertices(), i, j);
    }
}
```

对照着打印结果看：前面这几行说的是以 v1 作为起点，到 v1、v2、v3、v4 的路径分别是什么，后面跟的就是具体的路径串。

- v1 到 v1，直接走一个 v1 就行；
- v1 到 v2，是先经过 v1 到 v3，再到 v4，再到 v2——这就是 v1 到 v2 的最短路径；
- v1 到 v3，还是直接过来的；
- v1 到 v4，是 v1 先到 v3，再到 v4。

这样就能看到从 v1 出发到其他顶点的最短路径各自长什么样。下面依次显示的是以 v2 出发、以 v3 出发、以 v4 出发到其他四个顶点的路径，跟上面是同构的，我就不一一带着解读了。

到这儿，最短路径的距离和它的详情就都显示好了。

## 负环检测、最小生成树与并查集
> 对应块：BLK22 | 覆盖分集：P91-P94 | 块标题（分集名）：《进阶数据结构和算法-245-图-Floyd-Wa》

最后我们来看一个问题：**如果图里出现了环，弗洛伊德算法能不能把它判断出来？**

答案是能。而且你不用额外写任何检测逻辑，三层循环跑完，扫一眼对角线就完事了。

### Floyd 的收尾：从对角线上揪出负环

#### 先看这张有负环的图

四个顶点 v1 到 v4。v1 可以到 v2，v2 可以到 v3，v3 又回到 v1——一个环出现了。而且这个环是负环：$2 + (-4) + 1 = -1$，小于零。

> **结论**：出现负环，最短路径最终就没有解了。绕着这个负环多走一圈，距离就少一圈，答案是负无穷大。

那怎么让算法自己把它发现出来？先把这个图的二维表格准备好。

#### 先把距离表填出来

行是起点 v1 到 v4，列是终点 v1 到 v4。不直接连通的，一律先填无穷大；连通的填上权重，自己到自己填 0。

| 起点 ＼ 终点 | v1 | v2 | v3 | v4 |
| --- | --- | --- | --- | --- |
| v1 | 0 | 2 | ∞ | ∞ |
| v2 | ∞ | 0 | -4 | ∞ |
| v3 | 1 | ∞ | 0 | 1 |
| v4 | ∞ | ∞ | ∞ | 0 |

记住这张表的读法：**行是"从哪儿出发"，列是"到哪儿去"，中间那一格就是这两个点之间当前的最短距离。**

#### 第一轮：借道 v1

k 等于 0，就是问一句——我能不能借道 v1 到其他顶点。一行一行过。

- **v1 这一行**：借自己到其他点，没什么可看的，跳过。
- **v2 这一行**：v2 到 v1 是不通的，它压根就借不到 v1，这一行不用看。
- **v3 这一行**：v3 到 v1 是通的，距离是 1。先到 v1，再借 v1 到 v2，权重是 2，加起来是 3。原来 v3 直接到 v2 是无穷大，3 显然比无穷大小，那就更新——`dist[3][2] = 3`。至于借道 v1 到 v3、到 v4，后面那两格都是无穷大，路不通，不看。
- **v4 这一行**：一上来就是无穷大，借不到 v1，不看。

第一轮跑完，确实有一个距离被更新了。

#### 第二轮：借道 v2，对角线塌成 -1

k 等于 1，借道 v2。

- **v1 这一行**：v1 到 v2 是通的，借 v2 能不能回到 v1？v2 到 v1 是无穷大，不行。再借 v2 到 v3：$2 + (-4) = -2$，比原来那个无穷大小，更新成 -2。到 v4 不通，不看。
- **v2 这一行**：借道自己没意义，不看。
- **v3 这一行**：v3 到 v2 是通的。借 v2 到 v1？v2 到 v1 不通，不看。

> **重点**就在接下来这一格。v3 借道 v2 回到 v3 自己，看行不行？

行。它先到 v1，距离 1；v1 再到 v2，距离 2；v2 再到 v3，距离 -4。加起来 $1 + 2 + (-4) = -1$。

本来 v3 到自己就是 0。而 -1 比 0 还小！所以 `dist[3][3]` 这个本该是 0 的对角线格子，被更新成了负数。问题到这儿就暴露出来了。

#### 跑完之后：扫一眼对角线就够

后面的轮次我就不一格一格分析了——再分析下去它只会越减越少，这正是负环的可怕之处。

结论其实一句话就能说完：**只要存在负环，某一次运算就会把对角线上的 0 改成负数。**

所以等正常的三层循环跑完，我们去检查 dist 数组的对角线：

```java
for (int i = 0; i < dist.length; i++) {
    if (dist[i][i] < 0) {
        throw new RuntimeException("发现负环，最短路径没有解");
    }
}
```

只要有一个值是小于零的，你就可以推断出出现负环了。抛一个异常出去，告诉它最小路径没有解，给它第一个提示就行了。

### 最小生成树要解决的是哪一件

换个话题，我们来看最小生成树的问题。

还是那张图，这回里面有七个顶点，有若干条边都可以把这七个顶点连通。但是我现在的需求不是要所有的边——我想在这些边里找**六条边**。连接七个顶点，六条边是不是就够了。

我要找的这六条边还必须满足第二个条件：每条边都有权重，这六条边的权重加起来是最少的。

> **定义**：n 个顶点里挑出 n-1 条边，把它们全部连通，且权重总和最小——这就是最小生成树。

这个需求在现实生活中也很有意义。你想啊，这是你家里的七个开关，现在要铺设电线把这七个开关都连通。铺设方式有很多种，但我想找一个成本最低的。没问题吧，这就是最小生成树的问题。

接下来我们看看最小生成树的相关算法。

### Prim：从最近的顶点一圈圈长出去

Prim 算法在思想上跟我们之前学过的迪克斯拉（Dijkstra）算法非常相似，待会儿学的时候可以对比着看。

还是刚才那张七个顶点的图。我们挑 v1 作为起点，把它的距离设置成 0，除了起点以外的顶点，距离全部设置成无穷大。这是一个初始状态。

#### 从 v1 把第一轮铺开

接下来从这个起点开始处理：找到它相邻的顶点，去更新这个距离，遇到有更小的距离就更新。同时还要记录这个距离是从谁来的——对 v2 来讲，它的来路是 v1，那就把它的 previous 记成 v1。

- v2：无穷大 → 更新成 2，来路 v1
- v4：无穷大 → 更新成 1，来路 v1
- v3：无穷大 → 更新成 4，来路 v1

v1 这个顶点就算处理完了。

#### 剩下的顶点一个一个被选中

处理完一轮，就在还没处理的顶点里挑一个距离最小的。v4 的距离是 1，比其他什么 2、4、无穷大都要小，所以第二个处理它。

处理 v4 的时候规则跟刚才一样：找到它相邻的顶点去更新距离。遇到已经处理过的顶点就不用管了，比如 v4 到 v1 那一格——它已经处理过了，我们只看还没处理的那些：

- v2：现在算出来是 3，比原来记录的 2 还大，不更新。
- v3：原来记的是 4，现在 v4 到 v3 是 2，更新成 2，previous 改成 v4。
- v5：更新成 7，来路 v4。
- v6：更新成 8，来路 v4。
- v7：更新成 4，来路 v4。

v4 处理完，我们就得出了一条路径——它跟 v1 之间的这条路径就确定了。

接下来这几个顶点里谁的距离最短？是 v2 和 v3，它俩的距离都是 2，随便挑一个就行，我们就按顺序来，处理 v2。它相邻的没处理过的顶点只有 v5，但 v5 现在是 10，比 v4 给的 7 还大，不用更新。v2 处理完，确定它跟 v1 的路径——它这个距离 2 就是从 v1 来的。

接下来就该 v3 了。它相邻的 v1、v4 都处理过了，只看 v6。一看有个更短的距离 5，就用 5 把那边的 8 替换掉，previous 也跟着更新成 v3。v3 处理完，确定它跟 v4 的路径。

剩下的三个顶点里，v7 最近，处理 v7。v7 相邻的顶点有 v6、v4、v5，v4 已经处理过了。v6 更新成 1（来路 v7）；v5 更新成 6，比 7 要小（来路 v7）。v7 处理完，确定它跟 v4 的路径。

还剩 v6 和 v5，显然 v6 的距离更短。其实 v6 都不用处理了——它相邻的几个顶点都已经处理过了，我们只需要把它那条路径找出来画出来：它是从 v7 过来的。最后一个顶点 v5，相邻的也都处理过了，从 v7 连过来。

整个过程跑下来，距离表是这样的：

```text
[v1 处理完]
    顶点:  v1    v2    v3    v4    v5    v6    v7
    距离:   0     2     4     1     ∞     ∞     ∞
    来路:  --    v1    v1    v1    --    --    --

[v4 处理完]
    顶点:  v1    v2    v3    v4    v5    v6    v7
    距离:   0     2     2     1     7     8     4
    来路:  --    v1    v4    v1    v4    v4    v4

[v3 处理完]
    顶点:  v1    v2    v3    v4    v5    v6    v7
    距离:   0     2     2     1     7     5     4
    来路:  --    v1    v4    v1    v4    v3    v4

[v7 处理完]
    顶点:  v1    v2    v3    v4    v5    v6    v7
    距离:   0     2     2     1     6     1     4
    来路:  --    v1    v4    v1    v7    v7    v4
```

至此为止，七个顶点的六条路径就连接好了：

```text
v2 - v1 - v4 - v3
        |
        v7 - v5
        |
        v6
```

#### 和 Dijkstra 只差一行代码

写 Prim 的时候你会发现，它跟迪克斯拉几乎一模一样：

| 步骤 | 迪克斯拉（Dijkstra） | Prim |
| --- | --- | --- |
| 起点距离 | 置 0 | 置 0 |
| 其他顶点距离 | 置 ∞ | 置 ∞ |
| 选下一个顶点 | 在未处理的顶点集合里选距离最小的 | 在未处理的顶点集合里选距离最小的 |
| 更新距离 | 当前顶点距离 + 权重 | 只看权重本身 |
| 顶点处理完 | 从集合移除，标记 visited = true | 从集合移除，标记 visited = true |

差别就在"更新距离"那一行。迪克斯拉算的是**累加值**，要把当前顶点的距离跟那个 weight 加在一起；而我们的 Prim 每次去更新距离的时候，只要考虑这个权重就行了，不用考虑之前这个距离。

所以接下来写 Prim 的代码就非常简单了——直接把迪克斯拉的代码复制一份，包括"更新邻居距离"和"选择最小距离顶点"这两个方法，这两个都不用动，拿过来就行。唯一要改的就是刚才说的那个计算距离的地方：

```java
// 迪克斯拉：距离是累加值
int newDist = dist[current] + weight;

// Prim：只看权重本身，不加之前那个距离
int newDist = weight;
```

最终运行结果，输出的六条路径分别是：

- v2 的 previous 是 v1
- v3 的 previous 是 v4
- v4 的 previous 是 v1
- v5 的 previous 是 v7
- v6 的 previous 是 v7
- v7 的 previous 是 v4

（v1 是起点，它的 previous 是空的。）

六条路径全部找到。只要你会迪克斯拉算法，稍微改造这么一行代码，Prim 就能够实现了。

### Kruskal：按权重捡边

Prim 是以顶点为核心的：每次去找顶点相邻顶点的最短距离，然后依次处理每个顶点去更新这个最短距离，最终所有顶点都处理完一遍，整个最小生成树也就有了。

Kruskal 是最小生成树的另一种算法，它**以边为核心**，去逐一处理每条边，来得到最后的最小生成树。

#### 先把边按权重排队

Kruskal 的做法是：先把所有的边根据它们的权重排个序，由小到大，咱们依次处理好。

图里权重最小的边是谁呢？是 v1 到 v4，还有 v6 到 v7。

那我们看看这两条边能不能用上。首先前提是：**这两条边的顶点，它们原来并不相交**，换句话说就是它们原来是没有连通的，那我们就可以利用这条边。

注意，一开始我们认为这些顶点都是不连通的。所以 v1 跟 v4 原来不连通，我们就可以用上刚才这条权重为 1 的边，把他们俩连在一起——这是第一条边。同样，v6 和 v7 原来也不连通，通过这条权重为 1 的边把它们连到一起——这是第二条边。

接下来找权重为 2 的边。v1 跟 v2 这条边能不能用上？可以，它可以把一个尚未连接到当前网络里的 v2 连接进来，因为 v2 跟 v1、v4、v6、v7 都是不连通的——第三条边。再找一条权重为 2 的边，也可以用：v3 也没有被连接到当前网络里来，通过它把 v3 也连进来——第四条边。

还差两条边。权重为 3 的边能用上吗？用不上，因为它要连接的顶点 v2 和 v4 其实已经是连通的了，跳过去。

权重为 4 的边有两条。上面那条连接 v1 和 v3 的用不上，已经连通了，跳过。下面那条连接 v4 和 v7 的可以用——它连接的两个顶点尚未连通——这是第五条边。

权重为 5 的边用不上，它那两端已经连通了，跳过去。

权重为 6 的边可以，它对应的一个 v5 顶点还没有被连进来，用上它。

六条边找够了，就不用继续找了，其他权重更大的边我们也一并跳过去。

| 权重 | 边 | 两端是否已连通 | 取不取 |
| --- | --- | --- | --- |
| 1 | v1 - v4 | 否 | 取（第 1 条） |
| 1 | v6 - v7 | 否 | 取（第 2 条） |
| 2 | v1 - v2 | 否 | 取（第 3 条） |
| 2 | v3 - v4 | 否 | 取（第 4 条） |
| 3 | v2 - v4 | 是 | 跳过 |
| 4 | v1 - v3 | 是 | 跳过 |
| 4 | v4 - v7 | 否 | 取（第 5 条） |
| 5 | v3 - v6 | 是 | 跳过 |
| 6 | v5 - v7 | 否 | 取（第 6 条） |

七个顶点的六条边，就把它们连在一起了。

#### 动手写之前：准备边集合

我这里已经准备好了七个顶点，把顶点放在一个集合当中。因为 Kruskal 要以边为核心来实现代码，所以我就把所有的边放在了一个优先级队列当中。

之前那个边的类我们不用了，我新写了一个。新写的这个边的类里有这么几个主要属性：一个是顶点的集合，还有边的起点、终点和权重。

> **注意**：这回的起点终点呢，它是一个索引值，代表的是我们这个顶点集合中它的索引值。

我们看一个例子。v1 到 v2 这条边，它的起点是 0，也就是说我们到集合里找到索引为零的那个顶点，是 v1，这是它的起点；终点是 1，到集合里找到索引为一的顶点，是 v2。所以这条边就是：我要从 v1 到 v2，然后它的权重是 2。

再看 v1 到 v3 这条边：索引 0 就是 v1，索引 2 其实就是 v3，从 v1 到 v3，权重为 4。

所有的边我都放在一块了，一共有 12 条边，放在一个优先级队列当中。因为放到优先级队列，所以我们要实现它的一个 Comparable 接口，这个接口就是根据边的权重来进行排序的——将来我优先级队列里权重越小的，会排在队列的前面。

好，这是我们这个边的集合就准备好了。

#### 退出条件、find 与 union

接下来我们实现一个叫 Kruskal 的方法，方法接受两个参数：一个是顶点的个数，第二个就是我们这边的边集合。

方法内我们先准备一个用来存储结果的集合。因为我们最终的目标是找到这六条边，所以用一个 List 集合来存储最终找到的边对象，这是我们代表结果的一个集合。

接下来肯定要写循环。那这个循环什么时候应该结束？大家想一想，我们一共七个顶点，最终是不是应该找到六条边？只要找够六条边了，就不用再循环了。

那这个边的个数我们怎么知道？它会传过来顶点的个数，顶点个数减一就是我们要找的边的个数。所以只要结果集合还没找够，也就是它找的边的个数还小于 size 减一、还小于 6，说明还没找够边，那我们就不断循环；什么时候等于了 size 减一，就表示六条边都找够了，退出循环。

每次循环的时候，我们都从这个优先级队列里拿到那个权重最小的那条边来进行处理，调用 poll 方法。

> **难点**：拿到这条边以后，前面也说过，如果这条边连接的两个顶点原来已经连通了，那这条边是不是就用不上了？只有这两个顶点还没有连通，我们才能用上它。那我们怎么判断这条边的两个顶点是否连通呢？

这里有一个比较方便的数据结构，就是我们接下来要用的这个**不相交集合，也叫并查集**。这个集合的实现我们先不看，先用它。

```java
public List<Edge> kruskal(int size, PriorityQueue<Edge> edges) {
    List<Edge> result = new ArrayList<>();
    DisjointSet disjointSet = new DisjointSet(size);

    while (result.size() < size - 1) {
        Edge edge = edges.poll();

        int i = disjointSet.find(edge.start);
        int j = disjointSet.find(edge.end);

        if (i != j) {
            result.add(edge);
            disjointSet.union(i, j);
        }
    }

    return result;
}
```

怎么判断呢？我们需要调用这个集合的一个叫 find 的方法，把边的两个顶点——我们这边有起点和终点——分别拿到这个集合里去找。第一个返回值我们起个变量名叫 i，第二个返回的起个名叫 j。

判断的方法很简单：

- 如果 `i != j`，表示它俩尚未相交，或者说未连通，一个意思。未相交该怎么办？这条边我们就可以用上，用上的话把它加到这个结果集合里不就可以了，`result.add(edge)`。
- 加完之后呢，还要做一件事：刚才这个不相交集合，我们需要做一个叫 union 的操作，把刚才的这两个顶点给他连到一起——你刚开始是不相交的，但是我这条边已经用上了，我就要表示这两个顶点把它们连起来，就调这个 union 方法，传过去 i 和 j 就可以了。union 的本意就是求并集的意思，就相当于把这两个集合给它连起来了。
- 如果它们返回的结果相等了，说明它们是连通的、已经相交了，那这条边就应该被跳过去。

什么时候等边的个数已经等于我们要找的边的个数了，我们就退出这个循环。

#### 验证：打印出来的六条边

最后我们来验证一下这个结果。要找的边最后都被放到这个结果集合中了，所以我们循环一下这个结果集合，就能看一下我们要找的边对不对。我已经重写了边的 toString，直接打印就可以了。

打出来是这样的：

- v1 - v4
- v6 - v7
- v3 - v4
- v1 - v2
- v4 - v7
- v5 - v7

跟我们之前手动分析的结果是一样的，说明我们这个算法是正确的。拼出来的树跟 Prim 那棵一模一样：

```text
v2 - v1 - v4 - v3
        |
        v7 - v5
        |
        v6
```

### 并查集：一个数组记录谁跟谁连通

这节课我们来讲解不相交集合。之前讲解 Kruskal 算法的时候我们用到了它，用它去判断图中的两个顶点是不是已经相连了；但是当时只是用了它的方法，并没有讲它的代码如何实现，这节课我们来看一看。

顺便说一下它的另一个名字——为啥叫并查集？因为这个集合内有两个比较重要的方法，一个叫 union 方法，union 的本意就是合并的意思；还有一个重要的方法叫 find，find 的本意就是查询的意思。所以基于这两个方法，我们经常也把它叫并查集，这是它名字的由来。

> **定义**：不相交集合（Disjoint Set）内部维护一个数组，数组的索引对应着我们图中的顶点；两个核心方法是 union（合并）和 find（查询）。

我们待会要实现三个方法：一个是 find 查询，第二个是 union 合并，还有第三个是它的构造方法。构造方法是对我这个集合中的一个数组进行初始化的操作。集合中它会维护一个数组，数组就对应着我们图中的这些元素。

#### 一个数组：索引是顶点，值是它跟着谁

先对这个数组做初始化。将来这个数组的大小呢，就由我们构造方法的 size 来决定，size 其实就是对应我们图中的顶点个数。

先把这个数组创建出来，创建出来以后呢，我们对数组中的元素做一个初始化。一般我们就把它初始化成这个 i——让每个元素的值就是我们这里的 i。

```java
public DisjointSet(int size) {
    s = new int[size];
    for (int i = 0; i < size; i++) {
        s[i] = i;
    }
}
```

创建出来一个集合，大小是 7，跟我这个图是对应的七个顶点。打印出来很简单，就是 0 是 0，1 是 1，以此类推。

那怎么去理解它内部维护的这个数组呢？注意，数组中每个索引就对应着我们这里的顶点，比如说索引 0 就对应着顶点 0，索引 1 就对应着顶点 1。但是索引里面的这个元素值呢，它是用来表示与它有关系的顶点的。

拿图上说：黑色的 0、1、2、3、4、5、6 对应着我们数组的索引，也就是我们的顶点；红色的 0、1、2、3、4、5、6 对应的是这个数组中的元素值。当然刚开始他们是一致的。

```text
索引:  0  1  2  3  4  5  6
元素值: 0  1  2  3  4  5  6
```

那元素 0 的值是 0，什么意思呢？意思是与顶点 0 有关系的顶点就是它自己——只跟他自己有关系，与其他顶点没有关系。索引 1 也是一样，跟谁有关系呢，也是只跟他自己有关系。所以一开始，我们整个这个数组就表示：这些顶点之间是没有联系的，它们都与自己有关系。

#### 要连两个顶点，改老大，不是改它

现在来看一种需求：我想把 0 和 3 这两个顶点连到一起。那连到一起我怎么表示它俩相连呢？

其实我们可以这样做。一种做法呢，就是我把 0 它的这个数组值改成 3——这样的话将来你找到 0 了，我一看它的值是 3，我就知道他跟另外一个顶点 3 有联系了。这是一种做法。

当然你也可以反过来，因为他们的这个关系是对等的，我们也可以把 3 它的数组值改成 0。这也是可以的：将来你找到 3，然后你一看它的值是 0，他就知道顶点 3 跟另外一个顶点 0 是有联系的。

再来看一个例子：比如说我们希望把 5 和 6 这两个顶点连到一起，那怎么做呢？我们可以把 5 它的这个值改成 6，或者把 6 这边它的值改成 5，是不是也行啊。

现在来一个容易搞错的：下面的需求是把 3 和 5 连到一起去，那我们改谁啊？

有同学说了，那我就把 3 它的这个数组值改成 5，这样行不行呢？

> **易错点**：注意不行，这样就错了。

我们要把 3 跟 5 连在一起，我们的修改内容不是随意的。我们得在这一组里找个老大，下面这组里也找个老大，**我们要改也是改老大它对应的数组值**。

现在的状况是：3 跟 0，他俩的老大是谁？是 0，因为你看它们是不是都是以 0 为准的，所以这边的老大我给他画个圈儿。5 跟 6，老大是谁？是不是老大是 5，好所以五这边我们也给他画个圈。

那待会儿我要把 3 跟 5 连到一起，你将来改动的值要改谁呀？改老大这边的值。要么改 0 的值，要么改 5 的值，**你不能改 3**。

具体的改法是一种做法，就是我把 0 它的那个数组值改成 5。当然反过来也行：把 5 这个老大它的数组值改成 0。这样也可以。

所以遇到了这种有多个的情况，我们得找到他的老大，然后改动老大对应的数组值，这一点大家要切记。

整个状态是这样：

```text
初始化          s = [0, 1, 2, 3, 4, 5, 6]      每个元素都指向自己

s[3] = 0        s = [0, 1, 2, 0, 4, 5, 6]      把 0 和 3 连到了一起
s[6] = 5        s = [0, 1, 2, 0, 4, 5, 5]      把 6 和 5 连到了一起

索引 == 元素值  →  老大（0 和 5）
索引 != 元素值  →  小弟（3 跟着 0，6 跟着 5）
```

#### union：把两个老大合成一个新老大

有了前面的基础，我们来看 find 和 union 这两个方法怎么实现。先来看 union。

比如说我要连接 0 和 3，那我是不是这两个顶点里要挑一个老大呀？假设我们挑 0 是老大，也就是 x 对应着老大 0，y 对应着小弟 3。

那现在代码怎么体现它这个过程呢？是不是相当于 3 它的值要以老大为准——找到索引 3 这个位置，把它的值改成 0。代码就是先找到数组中 y 它存储的位置，然后把它的值改成 x。

```java
public void union(int x, int y) {
    s[y] = x;
}
```

当然我们再看一个例子。比如说我 x 是 5，然后 y 是 6，是不是类似的呀？我也是这两个里面找个老大，以左边的 x 作为老大，然后找到 6 存储的位置，把它的值改成 5——改成 5 就对应着我们这边的 x。所以这一行代码就可以体现这个 union。

> **易错点**：但大家要记住一点，union 其实并不代表连线。
> 比如说我要把 3 和 5 连到一起，那我们的 union 方法实际上应该对应调用谁呀？对应调用的是两边老大，把他们连到一起，也就是 0 和 5。把 0 和 5，注意，不是 3 和 5。能理解吧？union 并不对应着那个连线操作。

它的作用就是让两个原本不相交的集合给它相交。其实说白了，就是在这两个集合里选出一个新的老大：原来 0 是老大，原来 5 是老大，但是你要让他们相交的话，相当于你得找一个新老大。比如说 0 是最终的新老大，那原来这个 5 它的值就得改成 0。

当然大家要知道它的方法参数：这里的 x、y 是原本那两个集合中的**老大索引**。

#### find：索引等于值，就是老大

find 方法其实就是在**一个集合里去找到那个老大的索引**。比如说上面这个集合，我找到老大索引 0；下面这个集合呢，老大索引是 5。

那有同学说了，我怎么知道谁是老大呢？其实大家看一下规律。上面这个集合里，索引跟值不相等的是小弟，索引跟值相等的这个就是老大。索引 0 的值是 0，是老大；索引 3 的值是 0，索引和值不相等，那它就不是老大。下面也是类似的，索引 5 值 5 是老大，索引 6 值 5 不相等，这是小弟。

> **结论**：索引等于元素值的那个元素，就是老大。

对应到代码上怎么去找呢？其实很简单。我们刚才已经总结了，传过来的都是索引值。所以值 x 如果等于它的数组值 s[x]，它俩相等的话，表示什么？表示找到了。找到了我们就返回这个 x。

那如果他传过来的 x 是个小弟的索引呢，比如传过来的是个 3，遇到这个 3 我们怎么找？我们是不是拿到它里面的这个值，再根据值再找一次？那再找一次这个动作是不是就是一个递归的动作？把 s[x] 当作索引，再做一次递归查询。

```java
public int find(int x) {
    if (x == s[x]) {
        return x;
    }
    return find(s[x]);
}
```

这就是我们的第二个方法，它的目的就是找到某一个集合中的老大。

回头再看 Kruskal 里那段判断：`i` 和 `j` 是两个顶点各自所在集合的老大索引。`i != j` 说明它们本来不在一个集合里，中间那条路现在是通的，可以用；`i == j` 说明绕了一大圈发现它俩本来就连着，这条边只能跳过去。整件事就这么简单。

并查集的代码写完了，那就拿一个完整的例子把它跑通。还是咱们之前学过的克鲁斯卡尔算法——它是按边为单位来处理的，目标是最小生成树。边我已经全部列在这儿，也已经按权重排好序了，接下来一条一条来处理。

### 克鲁斯卡尔里的并查集

处理的过程是这样的：找到这条边的两个顶点，看它们是不是在同一个集合内。如果不在，就把它相连；当然如果已经在同一个集合内了，这条边直接跳过去。

> **定义**：`parent[i] == i` 表示顶点 i 自己就是老大；否则 `parent[i]` 指向它的老大。于是"i 和 j 在不在同一个集合"这个问题，就等价于"find(i) 和 find(j) 是不是相等"。

#### 一条边的判断：先问老大，再决定连不连

代码怎么体现呢？先找到 0 这个顶点在集合中的老大，再找到 3 这个顶点在集合中的老大，也就是调用 `find` 方法。老大值我们分别起变量名 `x` 和 `y`。

```java
int x = find(0);        // 0 这个顶点所在集合的老大
int y = find(3);        // 3 这个顶点所在集合的老大
System.out.println("x=" + x + " y=" + y);

if (x != y) {
    union(x, y);                         // 不相等才相连
    System.out.println(Arrays.toString(parent));
}
```

相连其实就是让其中一个顶点加入另一个顶点，组成一个新集合。

我们把这条边集走一遍：

| 边 | `find` 出来的一端老大 | `find` 出来的另一端老大 | 判断 | 数组变化 |
| --- | --- | --- | --- | --- |
| 0–3 | 0 | 3 | 不同集合，连 | `parent[3] = 0` |
| 5–6 | 5 | 6 | 不同集合，连 | `parent[6] = 5` |
| 0–1 | 0 | 1 | 不同集合，连 | `parent[1] = 0` |
| 2–3 | 2 | 0 | 不同集合，连 | `parent[0] = 2` |
| 1–3 | 2 | 2 | 同一集合，跳过 | 不变 |
| 0–2 | 2 | 2 | 同一集合，跳过 | 不变 |
| 3–6 | 2 | 5 | 不同集合，连 | `parent[5] = 2` |
| 2–5 | 2 | 2 | 同一集合，跳过 | 不变 |
| 4–6 | 4 | 2 | 不同集合，连 | `parent[2] = 4` |

表格自上往下读，就是这轮克鲁斯卡尔把边从短到长过一遍的全过程：两条老大相等的边直接被跳过，根本不会去执行 `union`；每条被留下的边都会让一个顶点改认新老大。跑完最后一组 2、3、4、5、6 五个顶点的老大全部是 4：

```text
索引 :  0   1   2   3   4   5   6
值   :  2   0   4   0   4   2   5
```

六个顶点（0 到 6 共七个点）只需要六条边就能撑起一棵生成树，到这一步最小生成树就有了。这就是不相交集合（Disjoint Set）在克鲁斯卡尔里的一个使用示例。

#### 小弟会不会找错老大

刚才处理 2–3 这条边的时候，有同学就问了：这时候 1 和 3 这两个小弟，将来会不会找错老大？

不会。你看对于 1 来讲，它的内容是 0，跟它的索引 1 不等，相当于没找到，所以它继续找 0 这个顶点；找到 0 以后，0 跟它的值也是不等的，所以它继续查找；这次再找不就找到 2 了，这时候相等，说明老大找到了。

```text
find(1) :  1 → 0 → 2 → 2      命中 2 == 2，老大是 2
find(3) :  3 → 0 → 2 → 2      命中 2 == 2，老大是 2
```

读图就是：小弟的内容指向的不是老大，而是另一个小弟，`find` 会顺着这条链一路走，直到内容等于索引为止。所以 1 和 3 虽然离老大隔了两层，但它们最终找到的老大都是 2。

### 路径压缩：find 顺手把路修短

这一节课我们对并查集做一些优化的处理。先看一个比较糟糕的情况：我的目的是通过 `union` 把这些顶点都连在一起，但我连得很讲究——先是 0 和 1 相连，再让 1 和 2 相连，然后 2 和 3、3 和 4、4 和 5、5 和 6。落到数组上就是三里存的是二、四里存的是三、五里存的是四、六里存的是五。

这个缺点是显而易见的。比如我想找 6 在整个集合中的老大，他得先找到 5，通过 5 找到 4，通过 4 找到 3，找到 3 找到 2，找到 2 找到 1，最后找到 0，我才知道 6 的老大是零。这个查找效率是不是比较低？

> **结论**：改进可以从两个方面入手——一个改 `find` 方法，另一个改 `union` 方法。

先看对 `find` 方法的优化，它有个名字叫**路径压缩**。单看这个名字是不是很高大上？其实没有我们想的那么复杂，非常简单，举一个例子大家就明白了。

比如说我要执行一个 `find(2)`，也就是找到 2 这个顶点它的老大是谁。二这个顶点它的索引跟内容二者不等，不等的话就往下执行递归调用；递归调用根据它的内容再进行查找，也就是执行 `find(1)`。`find(1)` 这边同样索引跟内容不一样，所以继续递归调用，执行 `find(0)`。这次它的索引跟内容二者相等了，就不用继续递归，我们可以返回了。

把这个 0 返回给刚才的 `find(1)`，`find(1)` 继续把这个 0 向上返回，返回给它最外层的调用者，也就是返回给 `find(2)`。这样对于 `find(2)` 这个方法来讲，我当然知道最终谁是老大——零就是老大。

但是大家想，`find` 方法执行完了以后，对于 2 这个顶点来讲，它就知道自己的老大是零。那我们何不把它的内容做一个更新呢？原来它得先找到 1，再从 1 找到老大 0；那现在既然知道了它的老大是 0，我们何不直接把它的内容改一下，让它直接变成 0，也就是这条线咱们就不要了。这样相当于他下次就去找老大 0 了，就不用中间再做这个 `find(1)` 的操作了——找到的路径是不是就短了？

这就是**路径压缩**。

代码实现起来也非常简单。还是刚才这个例子，假设我们的 x 等于 2，它递归调用的这个 `find` 方法最终会给我返回一个 0，也就是找到它的老大 0。那我们的目的就是把 2 这个索引位置的内容更新成 0。

```java
public int find(int x) {
    if (x != parent[x]) {
        // 让 x 自己的槽位直接存递归返回的老大，中间的线就断了
        parent[x] = find(parent[x]);
    }
    return parent[x];
}
```

就这一行 `parent[x]` 的赋值——它要复制为递归返回的这个结果，我们做一个复制动作就可以了。

接下来测试一下。我们执行完这些代码之后，执行一个 `find(2)`，`find` 方法执行完了以后，其实它的这个路径已经更新了，我们可以再次打印一下这个集合。现在 2、1、0 他们的这个值是不是都是零了？这样相当于我们就对路径做出了一个更新。

再看一个例子，执行一个 `find(6)` 会怎么样？执行了 `find(6)` 以后，他会把这个路径上的所有顶点都做更新。

```text
执行前 :  0 ← 1 ← 2 ← 3 ← 4 ← 5 ← 6      （parent[6]=5, parent[5]=4, ...）
执行后 :  0 ← 0 ← 0 ← 0 ← 0 ← 0 ← 0      （整条路径被拍平到一层）
```

为什么会这样呢？其实不管这里的 6、5、4、3、2 这些顶点，他们最终的老大都是零。所以我们每次递归调用的时候，都会把相应 x 位置的内容更新成我们找到的老大值。这样我们的顶点路径都被更新成他们的老大了，这样我们再次使用的时候，效率是不是就变高了？

> **结论**：路径压缩只改 `find`——查找一次，顺手把整条查找路径上的所有顶点都指向最终老大，效果立竿见影。

### Union by size：老大由块大的一方来当

接下来的一个优化针对 `union` 方法。同样先看一个场景：现在这个集合中已经有两个连接起来的集合了，一个是 0，它是单独一个；还有一个是 1、2、3、4，这四个已经连起来了——2 和 3 存的都是 1，4 存的是 3。

现在我的需求是把这个 0 跟这个 1、2、3、4 再给它连到一起，连到一起就会调用 `union` 连接两个集合中的老大。0 这边老大就是 0 自己，1、2、3、4 这边老大是 1，所以我连接 0 和 1。但是如果我反过来连接 1 和 0，这两种是不是都可以把两个集合连到一起？

都能连上。那哪种连接的结果更好一些呢？我们来对比一下。

| | `union(0, 1)` | `union(1, 0)` |
| --- | --- | --- |
| 谁成为老大 | 0 | 1 |
| 谁改认老大 | 1 的内容改成 0 | 0 的内容改成 1 |
| 查 4 的老大要走几步 | 4 → 3 → 1 → 0，三步 | 4 → 3 → 1，两步 |

从表格右列就能看出来：下面这个明显更好，因为它整个所有顶点的路径相对都比较短。以 4 为例，上面这种连法它要走一步两步三步才能找到，下面这种只要一步两步就找到了。所以上面这个显然不太好。

那问题就来了：我们怎么去改进 `union` 方法，让它不管你传的参数是怎么样，最后都按 `union(1, 0)` 这种方式去完成连接？

我们说上面那个不好，是因为它把一个顶点个数多的集合连接到了一个顶点个数少的集合——下面这个集合有四个顶点，而 0 呢只有一个顶点，我们是把个数为 4 的集合连接到了个数为 1 的集合上。反过来，如果我们把顶点个数少的集合连接到顶点个数多的集合，这样得到的效果是不是就比较好？

所以我们需要根据集合中的顶点个数来决定谁是老大，顶点个数多的把它当成老大就比较合适。

> **易错点**：原来的 `union` 固定让左边的参数当老大。`union(0, 1)` 和 `union(1, 0)` 在它眼里是两回事，于是一个不小心就会把一棵大树挂到一棵小树底下，让所有小弟的查找路径集体变长。

因此我们要对代码做改进，需要一个新的数组，这个新数组就是记录个数的，用来记住个数。我们把数组的名字就叫 `size`，大小跟我们传过来这个顶点个数也是一致。

```java
private int[] size;

public UnionFind(int n) {
    parent = new int[n];
    for (int i = 0; i < n; i++) {
        parent[i] = i;
    }

    // 刚开始每个集合互不相连，所以每个集合的个数都初始化成 1
    size = new int[n];
    Arrays.fill(size, 1);
}
```

这个 `size` 初始化成 1，是因为刚开始每个集合都是互不相连的，每个集合里只有它自己一个顶点。

接下来我们去改进 `union` 方法，看看怎么利用这个 `size` 找到一个顶点个数更多的集合，把它作为合并后的老大。原来的代码就这么一行：x 复制完成以后它就变成新的老大了，这个复制动作完成以后，y 是不是就从原来的老大变成小弟了。

当然我们现在这个逻辑不一定是说 x 是老大，要看哪个集合中元素个数更多。那我们先不考虑谁多谁少，先把元素个数更新一下。比如两个集合合并了，一个集合中元素个数是 1，另一个集合元素个数是 4，他俩合并之后是不是应该把元素个数更新一下？我们去更新老大的元素个数就可以了——合并之后老大是 1，那我们就把它对应的元素个数更新成 5。

```java
parent[y] = x;                   // y 挂到 x 底下，x 当老大
size[x] = size[x] + size[y];     // 老大的个数把小弟的个数吃进来
```

这行代码大家先把它理解好：更新成它上一次的元素个数加上小弟 y 它的元素个数。上次是 4、小弟这边原来是 1，两个加起来是 5。

接下来我们就可以根据这个元素个数做出不同的判断了。如果 x 它的元素个数是少于 y 的元素个数，那这时候谁作为老大？这个情况下应该是 y 作为老大，y 是老大，x 就是小弟。那这个代码跟刚才就反过来了：x 是小弟放在前面，y 是老大放在后面；下面是更新那个老大的元素个数，老大是 y，所以这里改成 y 没问题吧。

```java
if (size[x] < size[y]) {
    parent[x] = y;                  // x 是小弟，放在前面；y 是老大，放在后面
    size[y] = size[y] + size[x];
} else {
    // x 的元素个数比 y 多或者等于，走原来的逻辑
    parent[y] = x;
    size[x] = size[x] + size[y];
}
```

这样我们的 `union` 代码就写完了：一种是 x 的元素个数少，那就 y 作为老大；一种是 x 的元素个数多，或者是等于了，那就是 x 仍然作为老大。

测试一下。我把集合的 `toString` 方法改了一下，不光是会打印这个内容，还会打印大小的集合。我们来测试两种情况：先来看 `union(0, 1)`，看看结果是不是 1 是老大；再来看一个 `union(1, 0)`，看看结果是不是仍然是 1 当老大。

之前的状态里面，一个集合是 0（大小为 1），另外一个集合老大是 1，它的大小被存储在了老大那一格，大小是 4。当我们完成了 `union(0, 1)` 以后，最终还是把 1 作为老大，0 它的内容被更新成为 1，最终 1 的大小也更新成 5。

反过来再运行一次 `union(1, 0)`，效果跟刚才一样：仍然是 1 是老大，因为他就不看你先后顺序了，而是看那个元素个数，最后大小也被正确更新了。

最后我们再多啰嗦两件事儿。第一件事，if 里的逻辑跟 else 的逻辑是不是非常像？只不过这边是 x，这边变成了 y 和 x。

这段代码我们可以这么优化一下：如果 x 小于 y，这个条件成立了，那我们把 x、y 俩交换一下位置——先把 x 复制给临时变量 t，然后让 x 等于原来的 y，再让 y 等于 t，这就相当于把他俩的内容交换了。交换之后，我们这个代码就可以统一成一行了。

```java
public void union(int x, int y) {
    if (size[x] < size[y]) {
        int t = x;      // 集合个数少的一方挪到后面去当老大
        x = y;
        y = t;
    }
    parent[y] = x;
    size[x] = size[x] + size[y];
}
```

为什么交换之后就可以统一成一行代码呢？因为如果 x 小于 y，把他们俩交换了之后，原来的 x 是不是就变成 y、原来的 y 就变成 x。如果这个条件不成立，x 和 y 相当于保持原来的内容不变，x 还是原来的 x，y 还是原来的 y，所以还是执行下面这个逻辑也可以。

这两个代码是等价的，你觉得哪个好理解，你就用哪个。

第二件事，我们刚才介绍的这种优化方式叫 **union by size**，就是根据每个集合的元素个数来进行判断。当然了，还有另外一种优化叫做 **union by height**，就是根据两个集合中这棵树的高度——我们每个集合其实都可以看成一棵树——来决定哪个集合作为最终的老大集合。但是 union by height 跟 union by size 的实现非常的像，那我这里就不讲了，这个留做一个扩展的知识，大家可以下去去查阅一下 union by height 的实现。

> **结论**：路径压缩改的是"找得快"，union by size 改的是"挂得好"。两者都往 `parent` 数组里写，互相独立，可以同时用。

### 贪心算法：只看当前这一步

关于并查集的优化就讲完了，这节课我们来学习贪心算法。贪心算法也称之为贪婪算法，它其实是一类算法的统称。就比如说我们之前学过的迪杰斯特拉算法，它就属于贪心算法；还有像 Prim 算法，以及咱们刚学过的克鲁斯卡尔算法，它们实际上都可以归类为贪心算法。

有同学就问了：究竟这个算法有哪些特征，才会被叫做贪心算法呢？

#### 贪心原则：只考虑当下这一步

首先我们要明确一点，这个贪心算法它是用来寻找最优解问题的。你看我们的迪杰斯特拉算法算不算是寻找最优解问题？算吧，他是要找一个最短的路径。还有我们的 Prim 算法以及克鲁斯卡尔算法，算不算这种寻找最优解问题？也算吧，他们也是找一个相当于最短的距离。

因此我们贪心算法的适用场景就是这种寻找最优解问题。而在这个寻找最优解的过程中，我们要把整个过程分成若干个步骤，每一步骤只要你采用的都是这种贪心的原则，那我们这个算法就算是贪心算法。

> **定义**：贪心原则其实很简单，就是在当前这个步骤里找到最优解。也就是他的眼光放得不那么长远，他只考虑当前这个步骤里的最优解；至于后续的步骤里它是不是最优，我不考虑。

这个怎么体现呢？我们举几个例子。迪杰斯特拉算法在循环的时候，每一步骤要干的事情是：一上来先选一个当前顶点。那这个当前顶点怎么选呢？它要在所有顶点里选一个距离最小的作为当前顶点。这一步实际上体现的就是一个贪心——它是在我这次循环里找到一个距离最小的顶点。那至于这个顶点在将来的循环里是不是真的是距离最短，它不考虑。

Prim 算法也是类似的，每次循环的时候也是把所有顶点里找一个当前距离最小的顶点，当然他的这个距离是跟邻居之间的距离。迪杰斯特拉算法的这个距离是一个累加的距离。两个都是距离，但是稍微有些区别。

还有像我们的克鲁斯卡尔算法，他每次循环的时候要做的事情是选择一条边，那他是怎么选这条边的呢？他也是选一个距离最短的边。

所以你看我们这几个算法里，是不是都体现了一个每步我要找到一个当前最优的解：我要选一个当前最短距离的顶点、当前最短距离的边，是吧，都体现的是这个贪心原则。这个贪心就是他只考虑当下，不考虑长远。

#### 每步最优堆起来，未必全局最优

最后大家要注意一个问题：我们的贪心算法它并没有考虑所有的可能性。我们在每一步骤选取了当前这个步骤的最优解，但是把这些所有的步骤的最优解给它堆叠起来，并不一定能得到最终的最优解。

怎么理解这句话呢，其实是一个很典型的例子，就是我们前面讲过的迪杰斯特拉算法，它在处理负权边的时候就会出现我们刚才说的这个问题。我们回忆一下这个过程。

比如说现在要求 v1 这个顶点到其他顶点的最短距离，那我把 v1 的距离初始化成了零，其他顶点呢，这个距离初始化成了无穷大。按照这种贪心的思想，每一步是不是要找一个距离最短的顶点来处理？那第一步呢，找到的距离最短的是这个距离为零的 v1，对它进行处理。然后找到它的邻居，看这个距离是不是要更新。结果 v2 应该更新一下，这个距离更新成 1；v3 这个距离是不是应该更新成 1。这是我们的第一步就做完了，其实第一步没有发现问题。

好，接下来第二步。我们在剩余的顶点里再找一个距离最短的——这还是贪心的思想，我在剩余的顶点里找一个距离最短拿来处理。那我就选中了这个 v3。选中 v3 了以后，其实这一步就会导致最终的结果错误。

因为你看我这个 v3 选中之后，他去更新邻居，把他邻居的距离也是 1 + 1 = 2 更新了对吧。然后 v3 问题就在这了：v3 以后还会不会去处理它？不会了。也就是 v3 的距离我们认为已经找到最短的就是 1，但实际上我们都知道，他如果从看得更长远一些的话，这个距离从 v2 过来的话是 1 加上 -1 是 0，是不是比你的 1 更短呀。

但是由于我们的目光短浅，我们这个贪心思想就是说我只考虑当下，所以我处理完这个 v3，他以后就不会再处理了，它的距离就不会更新了，从而呢就得到了一个错误的结果。

你看我们把这个流程走完，接下来这两个顶点里它们的距离都一样，随便处理一个，比如说我们还是处理 v2。但是你想，处理 v2 的时候，他还会去更新它邻居的距离吗？不会了。因为他认为 v3 已经处理过了，所以他就不会再去考虑更新这个距离了，他不会再去更新 v3 的距离。所以就这一步出现问题了。当然最后这个 v4 呢，它的距离也不对啊，它的距离也没有更新，还是保持这个 2。

所以我们发现，贪心算法确实能保证每一步得到当前步骤的最优解，但是这些最优解最后给它堆叠起来，不一定能让我们最终的结果最优，这一点大家一定要记住。

> **易错点**：贪心算法并没有考虑所有的可能性。每一步虽然选了当前步骤的最优解，但把所有步骤的最优解堆叠起来，并不一定能得到最终的最优解。

与它作为对比，我们再回忆一下贝尔曼福特算法。它算不算是贪心算法？不算。它每次啊并不会说"我要找一个距离最短的顶点去更新它的邻居"，它每次都是处理所有的边，所以他考虑了所有的可能，最终的结果就不会出错了，他在处理刚才那种负权边的情况下就不会出错。

当然你想这个效率谁高谁低，肯定是迪杰斯特拉算法效率更高。那贝尔曼福特算法就效率会相对比较低了，因为他没有做出这种相应的优化，他是每次都要处理所有的边。相当于我们的这种贪心，它是一种在穷举所有可能的情况下做的一个优化——我不穷举所有可能了，我每次是找一个局部的最优解。

#### 贪心不只有图算法

接下来我们再来看几个贪心的例子，有我们见过的，也有没有见过的，我们过一下。

见过的例子有这样几个，都属于贪心算法。比如说我们的选择排序，它的思想是每一轮循环都要找比如说最小的值，给他交换到被排序的区域——每一轮循环都要选一个最小的，是不是体现的是贪心。

再比如说我们的堆排序算不算贪心算法？也算。堆排序我们先要构造一个大顶堆，那每轮排序的时候都要把堆顶元素，也就是那个最大的元素，给它交换到数组的尾部。每次也是要找一个堆顶的最大值，这也体现的是贪心。

还有拓扑排序，我们讲过一种按热度来排序的方法，那他每次呢都是找到一个入度最小的顶点，把它从图里面给它删掉。这是我们的拓扑排序，也体现的是贪心。

再比如说我们刚学过的并查集中的 `union` 操作，就是我们那个合并操作，`union` 操作要合并两个集合，那每次合并的时候，我要挑一个元素更大的作为老大来进行合并——这也体现的是贪心。

那么没有学过的，我们看一下名字，后面会讲到：哈夫曼编码、钱币找零、任务编排、近似算法，他们都可以使用我们贪心的思想。

关于贪心的介绍，我们就先介绍到这儿，接下来我们会举一些更多的贪心算法的例子。
