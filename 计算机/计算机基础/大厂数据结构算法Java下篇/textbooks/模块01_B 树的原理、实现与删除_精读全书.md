## B 树：把树高压到三层，磁盘才肯给你好脸色
> 对应块：BLK01 | 覆盖分集：P01-P05 | 块标题（分集名）：《Java数据结构与算法导学课程（下篇）》

讲概念性问题的时候，我们已经不看讲义、也不翻 PPT 了，直接向 AI 提问——它回答概念性问题是非常靠谱的。为了节约时间，问题我早就提前准备好了，开场第一个问题就是：B 树的历史是什么？

AI 给的回答大致是三句话：B 树是一种自平衡的树形数据结构；它最初由两位科学家在 1972 年提出；提出来的目的，是解决在磁盘中存储大量数据时如何减少磁盘 IO 操作次数、提高数据访问效率。

注意，这三条里第二条和第三条其实是一体的——B 树天生就是为磁盘而生的结构。而第一条更有意思，它把我们直接带回到一个熟悉的场景。

> **结论**：B 树是一种自平衡的树形数据结构，1972 年由两位科学家提出，目标是减少磁盘 IO 次数、提升数据访问效率。

自平衡的树形数据结构，我们前面已经学过两种了——AVL 树和红黑树。它们同样能存储大量数据，同样支持高效的查询、插入和删除。效率也都是对数级别。

那问题就来了：它们效率也不低，为什么还要再来一个 B 树？

### 效率高低，最后是树高说了算

先想清楚一件事：AVL 树和红黑树的效率，取决于什么？

取决于**树的高度**。树越低，比较次数越少；树越高，比较次数就多起来。最糟的情况，你得一路比较到叶子节点，才能找到目标数据。

拿 100 万条数据举例——这个数据量已经不算小了。我们用 AVL 树来存，树高是多少？$\log_2 10^6 \approx 19.93$，约等于 20。

如果要操作的是它的叶子节点，那就得比较 20 次才能找到数据。这 20 次本身不算什么，关键是这 20 次发生在哪儿。

如果这 100 万条数据在**内存**里，20 次比较是人类完全感觉不到的。内存的读写速度大约是纳秒级，乘个 20，压根儿感觉不出来。

但如果它存在**磁盘**上，尤其是比较早期那种机械硬盘，一次数据读写大概要几十毫秒甚至上百毫秒。20 次磁盘读写乘上去，人马上就能感觉到明显的卡顿——这个延迟是没法忍的。

| 操作对象 | 单次读写耗时 | 连做 20 次的体感 |
| --- | --- | --- |
| 内存 | 纳秒级 | 完全感觉不出来 |
| 机械硬盘 | 几十毫秒到上百毫秒 | 明显卡顿，无法忍受 |

所以结论很明确：AVL 树和红黑树适合做内存中数据的增删改查，而 B 树更适合做磁盘上数据的增删改查。这不是谁更优的问题，是场景不同。

### 换成 B 树，树高只有三

同样的 100 万条数据，这回存进 B 树。我先做一个假设——这个 B 树的最小度数是 500，这在整个 B 树的语境里是很正常的取值。再问一次 AI：树高大概是多少？

AI 第一次给的答案是四。

这个答案不太对，应该是三。我们重新问一遍。

这回对了，它改用英文回答的：100 万条数据、最小度数 500，树高大约是 3。这个数怎么来的？有一个公式，套进去就能算出来，我们后面会讲到；这一节先关心它的结论。

同样是 100 万条数据，放在磁盘上意味着什么：

| | AVL 树 | B 树（最小度数 500） |
| --- | --- | --- |
| 100 万条数据的树高 | 约 20 | 3 |
| 最坏情况下找到数据的磁盘访问次数 | 20 次 | 3 次 |

磁盘读写次数越少——更专业地说，IO 次数越少——数据访问性能就越高。这就是我们在磁盘中存储数据时选择 B 树的原因。

> **定义**：B 树最大的特点，是树高能够降到非常低。低树高是它一切优势的根源。

### 先把 degree 和 order 这两个名词说清楚

在介绍 B 树的特性之前，有两个名词必须先交代，否则看别人的资料会晕。

之所以要交代，是因为不同的文献在描述 B 树时用的词不一样：有的文献用 **degree** 来描述，有的文献用 **order** 来描述。两套说法指的是同一件事的不同侧面。

> **定义**：degree（度），指一个节点的孩子数目。

拿前面那棵树来说：根节点 4 有两个孩子，它的度就是 2；节点 2 也有两个孩子，度同样是 2；像 1、3 这样的叶子节点没有孩子，度就是 0；而节点 6、8 有三个孩子，度就是 3。

```text
                    [ 4 ]
                   /     \
                [ 2 ]   [ 6 | 8 ]
               /   \    /   |   \
            [ 1 ] [ 3 ] [ 5 ] [ 7 ] [ 9 | 10 ]
```

读图：方括号里是节点的关键字，竖线分隔多个关键字（6 和 8 是同一个节点的两个关键字），斜杠下面对应它的孩子。注意 `[ 6 | 8 ]` 下面挂着三个孩子——关键字 2 个，孩子 3 个。

> **定义**：order（阶），指整棵树所有节点中，孩子数最多的那个值。

上例中孩子数最多的节点是 `[ 6 | 8 ]`，有 3 个孩子，所以这棵 B 树的阶就是 3。

这两个概念我就不去问 AI 了——它给出的答案里前后矛盾、前后不一致的地方太多，所以直接给结论。概念这东西一旦被绕晕，后面的公式就全崩了。

### 一棵什么样的树才配叫 B 树

接下来该问正题了：究竟要符合哪些特性的一棵树，才能叫 B 树？

这个问题可以丢给 AI。它这次列了七条。不过它每次给的答案也不太一致，那没关系，随便挑一条我们来解读；解读过程中如果发现有遗漏，再补充就好。这一版回答我觉得比较满意，七条都说到了要点，所以也不额外补充了。

**第一条**：每个节点最多有 $m$ 个孩子，这个 $m$ 称为 B 树的"界"。我们前面用 order 来描述 B 树，你查其他资料时会看到用 $m$ 来描述的，都是一回事。

**第二条**：除了根节点和叶子节点以外，也就是那些中间节点，它们至少要有 $\lceil m/2 \rceil$ 个孩子。

`ceil` 就是向上取整。举个例子，我们这棵 B 树的阶是 3，也就是最多 3 个孩子，那 $\lceil 3/2 \rceil = \lceil 1.5 \rceil = 2$，代表中间这些节点至少得有 2 个孩子。你不能说只有一个孩子——那样树就不平衡了。

**第三条**：如果根节点不是叶子节点，它也至少要有两个孩子。这跟第二条在描述孩子数下限这件事上有重复的地方。

**第四条**：所有的叶子节点都在同一层。

什么叫叶子节点？就是没有孩子的那些——上图里的 1、3、5、7、9、10 都是叶子节点。

"在同一层"怎么理解？很简单，就是它们的高度相同。从根 4 到 1、到 3，再到其他这几个叶子节点，高度都是 3，所以它们在同一层。这一条也很重要，它是 B 树是否平衡的一个前提条件。

**第五条**：非叶子节点由 $n$ 个关键字和 $n+1$ 个指针组成。

这条要拆成两半看。前面这一半说的是"组成"。我们以前学的二叉搜索树，一个节点里就一个关键字；但 B 树中，**一个节点里可以有多个关键字**。上图中的 6、8 其实是同一个节点，它里面就有两个关键字。

那 $n$ 个关键字、$n+1$ 个指针，这 $n+1$ 个指针其实就意味着它有 $n+1$ 个孩子。一个关键字的孩子是 2 个，两个关键字的孩子就是 3 个。孩子数永远比关键字数多 1。

#### 关键字个数的上下限

后面这一半说的是：关键字的个数 $n$ 也是有上限和下限的。

$$n \in \left[\ \lceil m/2 \rceil - 1,\quad m - 1\ \right]$$

这个式子不是凭空来的，我们顺着第二节的思路倒推一遍就明白了：

孩子数的**下限**是 $\lceil m/2 \rceil$——刚才说过的，不能太少，否则树就不平衡；
孩子数的**上限**是 $m$——第一条说的，最多 $m$ 个孩子。

而关键字数比孩子数少一个。所以关键字数的范围，就是孩子数的范围整体各减 1：下限 $\lceil m/2 \rceil - 1$，上限 $m - 1$。

> **提示**：所有关于孩子数上下限的结论，把"孩子"两个字换成"关键字"，数值再减 1，就全部迁移过来了。这一步以后还会反复用到。

#### 顺序：从左到右一路升序

最后第六条和第七条，我合在一块说。

**第六条**：整棵树里，所有的关键字要做升序排列。这跟我们之前学的二叉搜索树是类似的——左边比它小，右边比它大。

只有一个关键字的时候很好懂：2 这个节点左边是 1，比它小；右边是 3，比它大。4 也是，左边整棵左子树都比它小，右边都比它大。

那有多个关键字、多个孩子的节点呢？这样看：6 的左边是 5，比 6 小；6 和 8 这两个关键字中间还夹着一个孩子，是 7，它比 6 大、比 8 小；8 的右边的孩子是 9 和 10，都比 8 大。

规则还是那一条：**左边的比它小，右边的比它大，中间夹着的落在两者之间**。只不过多关键字的时候，中间可以夹不止一个孩子。

**第七条**：整个这棵树里的所有关键字，合并起来看，还是一个升序的排列。我们这棵树就是 1、2、3、4、6、7、8、9、10 这样一个数据。

### Node 类：先把五个属性定下来

概念讲完了，开始写代码。第一步当然是把 B 树的节点类定义出来，我们还是叫它 `Node`。

大家先自己想一想：一个 B 树的节点类，都应该有哪些属性？从图上其实很容易看出来。

**第一个属性，关键字 `keys`。**

节点里的关键字可能有多个，所以不能用 `int` 来表示，得用一个 `int` 数组来表示。当然你也可以用集合来表示，这里我暂时选择数组。

**第二个属性，孩子 `children`。**

孩子也可能超过两个——不像二叉树有个左右孩子就够了，B 树的节点可能有三个乃至更多的孩子。所以孩子同样用数组表示，类型是 `Node`。

**第三个属性，`keyNumber`。**

这个属性是跟着前两个数组来的。我们用的是静态数组，大小一旦分配就固定不变了，不是那种动态数组。为了简单起见，将来所有节点里这个数组的大小设成一样的，比如都是 4。

可大小是 4，不代表一开始就真的存了 4 个数据。你看图上这个节点只存了一个 key，那个节点存了两个 key，它们刚开始可能还没存满。那没存满的情况下，你总得告诉代码——这个数组里哪几个位置是有效的数据。

所以我们需要一个变量来记录有效关键字的个数，就叫它 `keyNumber`。

> **提示**：如果这里用的是 `ArrayList` 这类集合，就不用额外记这个数了，直接调 `size()` 就知道里面实际有多少个 key。正因为我们选了静态数组，才必须自己维护 `keyNumber`。

**第四个属性，`isLeaf`。**

这是个布尔值，表示这个节点是不是叶子节点。因为叶子节点将来在处理的时候，跟非叶子节点的处理方式不同。

默认呢，我们刚把一个节点创建出来的时候，默认它是叶子节点。等以后它的孩子增多了，要进行分裂操作，分裂之后它才可能变成非叶子节点。所以初始值是 `true`。

**第五个属性，最小度数 `t`。**

也就是节点孩子数的一个下限——前面提过的那个概念。这个值一般用 `t` 来表示，代表整棵树将来的最小度数，得由我们提前给定。

五个属性定完，加上构造方法和调试方法，节点类的骨架就有了：

```java
import java.util.Arrays;

public class Node {

    // 关键字，一个节点里可以有多个
    private int[] keys;

    // 孩子数组
    private Node[] children;

    // 有效关键字的个数：数组中哪几个位置是有效的
    private int keyNumber;

    // 是否是叶子节点
    private boolean isLeaf;

    // 最小度数：整棵树中节点孩子数的下限
    private int t;

    public Node(int t) {
        this.t = t;
        this.keys = new int[2 * t - 1];
        this.children = new Node[2 * t];
        this.isLeaf = true;
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(this.keys, this.keyNumber));
    }
}
```

#### 构造方法：t 决定两个数组的长度

构造方法主要就是给最小度数赋一个初值。这个 $t$ 由我们指定，为什么必须由我们指定？因为你指定的这个度数，直接决定了将来树的高度——最小度数给得越大，树的高度就越低。所以它得根据实际情况来定。

$t$ 也不能随便给。它的最小值是 2，你给它赋值时至少要大于等于 2。因为你要是小于 2，就意味着它的最小孩子数只能有一个——那肯定不行，最小孩子数也得有两个。

知道了 $t$，我们就能进一步确定两个数组该留多大：

- **孩子数组**：`2 * t`。因为最小度数乘以 2，就是它最多可能拥有的孩子数——这也是 B 树里的一个约定。
- **关键字数组**：`2 * t - 1`。因为前面刚说过，关键字比孩子数少一个。

#### toString：只打印有效的那一段

最后提供一个调试方法，这不是必须的，就是一个 `toString`，目的是把这个节点里所有的 key 打印出来。

要打印的是**有效**的 key。比如这个节点你刚开始只放了一个 k，你不能把后面那些没初始化的元素也打印出来吧。

做法是：把原来那个 `keys` 数组拷贝一部分，从 0 拷到 `keyNumber`，正好就是有效的那一段，然后把这个数组用 `Arrays.toString` 转成字符串。这样将来调试的时候，就能很方便地打印出当前节点所有有效的 key 了。

这个方法只是辅助的，它并不是必须的。

### 多路查找 get

接下来给节点类加几个方法：一个查找方法，两个插入方法。这些在后续代码中都会用到，所以先提前实现掉。我们先看这个所谓的多路查找方法。

先回忆一下以前在二叉搜索树里怎么查找：把待查找的 key 跟当前节点的 key 比较，相等就返回；比它小就往左找；比它大就往右找。它只有两个孩子，所以每次只有两个方向可选。

但现在不一样了。当前这个节点有五个 key 的话，是不是应该有六个孩子？

```text
            keys = [ 5 | 10 | 15 | 20 | 25 ]
             下标     0     1     2     3     4
            children
              [0]    [1]    [2]    [3]    [4]    [5]
               |      |      |      |      |      |
             < 5   5..10 10..15 15..20 20..25   > 25
```

读图：children 数组的下标和 keys 数组严格对齐——下标为 0 的孩子装的是小于 5 的 key，下标为 1 的孩子装的是 5 到 10 之间的 key，以此类推，下标为 5 的孩子装的是所有大于 25 的 key。

那这种情况下怎么找？其实道理是类似的。

先看最简单的一种：我要查找 2。那就从左到右依次比较，把当前节点中这些 key 跟待查找的 key 比一遍，找到了就直接返回。在当前节点中能找到，就返回。

再看复杂一点的。我要查的是 21。

- 21 比 5 大——0 号孩子不用看了。
- 21 比 10 大——5 到 10 之间的那个孩子不用看了，那里面是 6、7、8、9。
- 21 比 15 大——10 到 15 之间的孩子不用看了。
- 21 比 20 大——15 到 20 之间的孩子也不用看了。

所以我们最后要去的是，20 到 25 之间的那个孩子里面继续查找。这个孩子里面我们还是从左向右依次比较，找到了就返回，找不到就再去找它的孩子，以此类推。

那如果找到的是一个叶子节点呢？叶子节点里都没有了，还用继续往下找吗？不用了，直接返回一个 `null`，表示没有找到。

这就是多路查找的完整过程。方法名叫 `get`，返回值先让它返回节点对象——找到了就把当前节点返回；参数就是待查找的 key。

#### 为什么是第 i 个孩子

把 `get` 写出来之前，最关键的一个问题还没解决：非叶子节点里，我们到底该到**哪个**孩子里去继续查？

我们来找规律。想执行到非叶子这段代码的时候，肯定是退出了上面那个循环，而退出循环的条件无非就两个：要么当前这个第 $i$ 个 key 已经大于待查找的 key 了，要么这个 $i$ 已经出了有效范围（比如有效 key 数是 5，$i$ 已经等于 5，出了有效索引范围）。

就这两种情况。我们分别代入验证一下。

**情况一：查找 16。** 能退出循环，说明找到了一个比 16 大的 key，找到的是 20，在 20 这个位置退出循环，退出时 $i$ 的值是 3。接下来再看这一堆孩子——到 3 这个索引的孩子数组里看一下，它里面存储的 key 是不是就在 15 到 20 之间。没错，所以退出循环时的 $i$ 等于几，我们就到同样索引为几的孩子里去继续查。

**情况二：查找 22。** 能退出循环，说明找到了一个比 22 大的 key，找到的是 25，退出时 $i$ 的值是 4。那就去索引为 4 的孩子里查找，这个孩子里装的就是 20 到 25 之间的 key。

**情况三：查找 30。** 能退出循环的时候，$i$ 已经等于 5 了——循环走完了，出了有效索引范围。这时候就去索引为 5 的孩子里找。30 肯定在那里，当然也可能没找到，因为它可能是个叶子。

所以规律就很简单了：

> **结论**：非叶子节点，去它的第 $i$ 个孩子继续查找。

第 $i$ 个孩子里的查找逻辑，跟我们刚才在当前节点里查找的逻辑一模一样，所以直接递归调用 `get` 方法就行了。

主要就是这个 $i$，大家一定要理解为什么要在第 $i$ 个孩子里继续查。

#### get 的完整实现

```java
public Node get(int key) {
    int i = 0;

    // 在本节点内从左向右逐个比较
    while (i < this.keyNumber) {
        if (this.keys[i] == key) {
            // 最理想的情况，找到了，返回当前节点
            return this;
        } else if (this.keys[i] < key) {
            // 节点内 key 是升序排列的，接着往右比下一个
            i++;
        } else {
            // keys[i] > key，说明当前节点里没有
            break;
        }
    }

    // 叶子节点且没找到，整棵树里也没有
    if (this.isLeaf) {
        return null;
    }

    // 非叶子节点：去第 i 个孩子里递归查找
    return this.children[i].get(key);
}
```

三种退出方式记牢：**等于，找到了，返回 `this`；小于了，`i++` 继续循环；大于了，`break` 退出循环**。退出之后分两种情况处理——是叶子节点就返回 `null`（没有孩子了、没有 key 了，既然退出了循环还没找到，说明整棵树里也没有了），非叶子节点就去 `children[i]` 里递归。

### 往节点里插入元素

#### insertKey：往 keys 的指定索引插一个 key

第一个插入需求是：向节点的 `keys` 数组的指定索引位置插入一个新的 key。

比如现在已经有一个 `keys` 数组，里面的 key 是 1、3、5。我想在索引 1，也就是原来 3 的那个位置，插入一个新的 key 2，该怎么做？

答案很简单：把 3 和 5 向后移动一位。原来索引 1 的位置就空出来了，然后就可以把新的 key 2 插进去。

这个功能我们以前也做过类似的练习、写过类似的代码，属于比较基础的部分了，所以代码我就不从头写了。这个活可以交给 AI 来干。

具体做法是：我把代码复制一份——我不想让它破坏我原来写的代码，复制一份以后，按快捷键 Ctrl+K，把需求粘过去。**需求写得详细一些更好**。让它写一个方法，向 `keys` 数组的指定索引 `index` 处插入一个新的 key，一回车它就会生成代码。

生成出来看一下对不对：方法名叫 `insertKey`，挺好；两个参数，一个是 key，一个是索引 `index`；它还贴心地加了个注释——从后往前移动元素，把 $i$ 索引处的元素移动到 $i+1$ 处，相当于把 3 和 5 向后移动了一位；位置空出来以后就往 `index` 位置加入新的 key；最后把 `keyNumber` 加加，因为新插入一个 key，有效 key 的数目应该加一。

这个代码就写好了，直接拷贝过来就能用。

不过它移动元素的时候是自己写了个 for 循环，我们希望改成 `System.arraycopy`，这个性能会高一些。按 Ctrl+L 告诉它："这个方法的拷贝元素是否能改成 `System.arraycopy`？" 它就会去帮我们调整。代码生成以后，直接复制过来用就行了。

```java
public void insertKey(int key, int index) {
    // 把 index 及其后面的元素整体后移一位，把 index 位置腾出来
    System.arraycopy(this.keys, index, this.keys, index + 1, this.keyNumber - index);
    this.keys[index] = key;
    this.keyNumber++;
}
```

`System.arraycopy` 的第三个参数是拷贝的元素个数。这里 `keyNumber - index` 正好是"从 index 到末尾"这一段的长度，把这一段整体搬到 index + 1 开始的位置，中间就空出了一个位置。

#### 往 children 的指定索引插一个孩子

第二个插入需求是：向 `children` 数组的指定索引位置，插入一个新的孩子节点元素。

需求还是让它来生成。这回我在提需求的时候明确说了一句：请用 `System.arraycopy` 来实现，这样它的代码就写完了。

不过它生成的代码，大家一定要检查一下。

你注意看，它在插入孩子的时候，也把 `keyNumber` 做了个加加。这个有没有必要？没有必要。`keyNumber` 我们通过 `insertKey` 来维护就行了——新加入一个 key 的时候，它的 `keyNumber` 加一；但新插入一个孩子的时候，我们不用去考虑再增加这个 `keyNumber` 了，所以把那行去掉。

```java
public void insertChild(Node child, int index) {
    // 把 index 及其后面的孩子整体后移一位
    System.arraycopy(this.children, index, this.children, index + 1,
                     this.children.length - index - 1);
    this.children[index] = child;
    // 注意：这里绝对不能动 keyNumber，它只由 insertKey 维护
}
```

> **提示**：让 AI 生成代码可以，但**一定要先检查合法性再拿来用**。这次它多给了一个 `keyNumber++`，直接跑起来未必立刻报错，但你后面查关键字个数的时候就会莫名其妙地对不上。改动的地方越少越好，多的那几行往往就是埋雷的地方。

到这里，节点类就写完了：五个属性、一个构造方法、一个调试用的 `toString`，以及三个比较重要的方法——多路查找的 `get`、往 `keys` 里插入新 key 的 `insertKey`、还有往 `children` 里插入新孩子的这个方法。所有重要的方法都实现完毕了。

## 把 B 树写出来：容器属性、contains、put 与 split
> 对应块：BLK02 | 覆盖分集：P06-P10 | 块标题（分集名）：《基础算法-160-B树-contains》

节点类已经写完了，接下来该轮到 B 树这个容器本身了。先看看它需要添加哪些属性。

### 先给 B 树这个容器定属性

根据经验，我们能想到的第一个，肯定是有个根节点对吧，所以定一个 `root`。

另外呢，我们说过 B 树中一个节点它有一个最小度数。既然是 B 树里所有节点，最小度数应该是一样的吧？既然所有节点它们的最小度数都是一样的，那我们可以给这棵树一个统一的最小度数定义，我们也叫做 `t`，它是代表这棵树中节点的一个最小度数。将来我这棵树只要创建新的节点，它是那个新节点，它的最小度数根据谁来呢？就根据我们树的最小度数来，可以吧。

> **定义**：`t` 是整棵 B 树统一使用的最小度数。新建节点一律跟着树的 `t` 走，全树节点的 `t` 值必须一致。

然后我们根据它给一个构造方法。当然了，如果你没有给他一个带参的构造，我们希望默认它的最小度数是二。前面我们说过最小值啊，你得有两个孩子啊，不能再少了。所以如果没有传参，也就是无参构造，我们就让它去调用刚才的有参构造，并且把二作为默认值。

> **提示**：默认 `t = 2` 不是随手写死的——B 树至少得有两个孩子，`2` 正好是"至少两个孩子"的最小取值。

这个根节点呢，我们一直在构造方法里把它创建出来，也就是 `root` 等于 new 一个节点。这个节点它的最小度数是由这个 `t` 来决定的。这样我们基本的架子就有了。

接下来呢我们还需要用到两个常量，这两个常量呢就决定了我们 B 树节点的、最小的 k 的数目和最大的 k 的数目。一个呢咱们叫 `MIN_KEY_NUMBER`，另外一个呢叫 `MAX_KEY_NUMBER`。因为他俩呢会在我们将来树的分裂和合并时都会用到。

那他俩的值从哪来呢？其实我们说过，这个 k 的 number 是不是孩子的数目减一？那孩子的最大数还记得吧，是不是 `2t`，所以我们孩子的最大数是 `2t`，那 k 的最大数是不是 `2t` 减一啊，它就是二乘以 t 减一。那最小的这个 k 的数目呢？孩子的最小数是 `t`，然后 k 呢要比我们的孩子数要少一，所以最少的 k 数应该是 `t` 减一。

这两个值呢，它是这棵树一旦被创建就固定不变了，所以我把它做成一个常量，也就是前面我们加上一个 `final` 以后就不能变了。

> **结论**：一个节点的孩子数落在 $[t, 2t]$ 里，k 的数目比孩子数少一，于是 k 的数目范围就是 $[t-1, 2t-1]$。这两个端点一次定死、全树通用。

```java
public class BTree {

    // 根节点，构造的时候就已经创建出来了
    private Node root;

    // 最小度数，整棵树的节点共用同一个 t
    private int t;

    // 节点中最小的 k 的数目
    private final int MIN_KEY_NUMBER;

    // 节点中最大的 k 的数目
    private final int MAX_KEY_NUMBER;

    public BTree(int t) {
        this.t = t;
        this.MIN_KEY_NUMBER = t - 1;
        this.MAX_KEY_NUMBER = 2 * t - 1;
        // 根节点提前创建好，它的最小度数由 t 决定
        this.root = new Node(t);
    }

    public BTree() {
        // 默认最小度数为 2：一个节点至少要有两个孩子，不能再少了
        this(2);
    }
}
```

> **易错点**：这两个常量是**实例常量**，不能加 `static`。它们的值依赖具体的 `t`，只能在构造方法里赋值。

到这里，B 树这个类的属性我们就定义好了。接下来呢我们主要来实现三个方法：第一个方法就是判断一个 k 在树中是否存在，第二个方法呢是新增一个 k，第三个方法呢是删除一个 k。

### contains：一次查找就够了

好那我们先来看判断是否存在，也就是所谓的 `contains` 方法，返回的是一个布尔值，参数呢是我们要判断的 k。

那其实呢它是不是就对应着一个查找了？那么将来去调用之前写的这个 `get` 方法查找，如果查找到了，这个节点不为空，那是不是应该返回真啊？那如果没查找到，返回了 `null`，没查找到，那我们这个 `contains` 返回一个 `false` 是不是就行了？

```java
public boolean contains(int key) {
    return this.root.get(key) != null;
}
```

这个代码就非常容易写了。注意这里对 `root` 不用做非空判断，因为我们构造方法里已经创建了一个不为空的节点对象。所以只要返回这个 `root` 的查询结果不等于 `null` 就 OK 了。

### 新增 put：规则、流程与实现

那我们先来熟悉一下新增它的流程和一个规则。刚开始呢，我这棵树里只有一个根节点，这个根节点里也没有任何的 k，因为刚开始创建出来这个根节点里面是没有任何 k 的。

好那我就比如说新增一个 k，比如说新加一个 1。那 B 树里新加一个 k 的话，如果你这个节点是叶子节点，那我们直接插入就可以了，按照它的大小顺序把它直接插入进来就可以了。

那如果我再加入一个 2 呢，也是类似的，它也可以把这个 2 加入进来。并且呢咱们以前也说过 B 树中的一个节点它是可以有多个 k 的，所以刚才的 1 和 2 其实都放在了同一个节点里，就在 `keys` 这个数组里。

但是呢我们也说过，这个 k 的数目不是说越多越好，因为 k 的数目多了它就影响我们的查询效率，对不对，比较的次数就多了。所以当 k 的数目超过一个最大值，我们就要对这个节点做一个分裂的处理。

那这个最大值是什么呢？其实是我们之前可以由自己来指定的。大家还记不记得我们刚才写 B 树属性时，给了他一个叫 `MAX_KEY_NUMBER` 的常量，它是代表我们节点中最大 k 的数目。那等于这个最大 k 数目，我们这个节点就要分裂，分裂之后形成多个节点，这样每个节点中 k 的数目就相应地减少了。

那这个最大的 k 数目跟谁有关系呢？前面我们的代码中大家也能看出来，它就跟 `t` 有关系，它最大的 k 数目就是 `2t` 减一。比如说我这个右边这个树啊，我在创建它的时候我的 `t` 取值为 2，所以 2×2-1 是不是它的最大 k 数目是 3。

#### 跟着例子走一遍

所以接下来我再加入一个新的 k 3，这个时候是不是我们这个节点中 k 的数目已经到达它的最大值了？到达它最大值，我们就要对它进行一个分裂。那这个分裂的细节我们先把它略过去，我们只看结果。结果呢就是把它分成了三个节点：小的留在左边，中间的那个作为了父节点，大的分到右边的新节点。

```text
插入 1、2
    [1, 2]                 两个 k 都落在同一个节点的 keys 里

插入 3 → 到达 MAX_KEY_NUMBER = 2t-1 = 3，触发分裂
    [1, 2, 3]  ──►   小的留左边，中间的上浮，大的去右边

                        [2]
                       /   \
                     [1]  [3]
```

那如果我要继续再插入呢，比如说我再加入一个 4。现在不是叶子节点了，它就得继续向下找，找到叶子节点。比如说 4 呢比这个 2 大，他就看看是不是有相对应的孩子节点，找到了右边这个 3 这个节点，然后 3 这个节点还没有满呀，没有满他就可以直接把 4 加入进去，理解了吧。

那如果我再加入一个 5 呢？加入 5 之后是不是这个节点又满了，这个节点满了它再做一个分裂操作。当然这回分裂的结果细节我们也是暂时先不看，先看结果，结果呢就把它拆成了这样四个节点了：根节点是有两个 k，是 2 和 4；比 2 小的 1 在最左边，2 和 4 中间的 3 在中间，比 4 大的 5 在右边。

```text
插入 4：不是叶子，得往下找 → 4 > 2，走到右边的叶子 [3]，它没满，直接放进去
    [2]
   /   \
 [1]   [3, 4]

插入 5：右叶子又满了，再分裂一次
    [2]
   /   \
 [1]   [3, 4, 5]   ──►    [2, 4]
                          /   |   \
                        [1]  [3]  [5]
```

总之呢从我们刚才的演示这个效果里啊，我们看到了几个基本的规则：就是遇到了叶子节点，它就可以直接加入这个新的 k；那加入新的 k 以后，k 如果到达了它的最大值，那我们就要执行一个分裂；然后我们重复这个过程。

#### 归纳成几条规则

把我们刚才分析的流程用文字来描述的话呢，就这么几条。

首先，我们应该去当前节点中去找一个插入位置 `i`，因为当前节点的这些 k 它也要符合一个升序的顺序对吧，所以你新来的 k，你得找到自己在哪个位置去插入才比较合适。当然了，如果遇到了重复的 k，那我们现在的策略就是走更新的逻辑了，我们现在是这个 B 树里不允许有重复的 k，遇到相同的我们就走更新。

那如果是没有找到重复的啊，那我们才做下面的插入。那插入的时候呢还要分两种情况啊：如果是叶子节点，那么就直接插入了；那如果是非叶子节点呢，我们要去递归操作啊，去找他的孩子，看看在孩子里重复做这些判断处理，然后找到一个合适的位置完成这个插入。

最后还要考虑，我们应该限制每个节点的 k 的数目，如果已经插入后它到达了这个节点 k 数目的最大值了，那这时候我们应该做一个节点的分裂操作。

#### doPut：先找位置，再决定往下还是往右

接下来呢我们就把这个代码，根据刚才的分析和文字描述，咱们来写一下。

首先呢我们提供一个 `put` 方法。`put` 方法的参数按理来说应该有两个吧，你至少有一个键、有个值对吧。现在呢我们这个代码呢咱们做了一个简化，就是没考虑值了，因为我们在设计这个节点类的时候也没有加上那个 `values` 这个值。所以这里我们做了个简化，我们就考虑只插入 k。

那因为待会儿呢我们要做递归的操作，递归的方法需要的参数跟我们这个 `put` 方法的参数啊会差一个，所以我们再专门来写一个方法完成递归，方法呢咱们叫个 `doPut` 好吧。然后它接收的两个参数呢，一个就是你从哪个节点来来完成这个插入，然后第二个参数才是我们刚刚的这个新 k。那我们第一个 `put` 方法里只要调它就可以了，刚开始是从 `root` 开始去完成这个操作对吧，然后 k 传过去就 OK 了。

```java
public void put(int key) {
    this.doPut(this.root, key);
}

private void doPut(Node left, int key) {
    // 第一步：在当前节点中找到 k 的插入位置 i
    int i = 0;
    while (i < left.keyNumber) {
        if (left.keys[i] == key) {
            // B 树里不允许重复的 k，遇到重复走更新逻辑；
            // 当前实现还没有 value，所以这里直接返回
            return;
        } else if (left.keys[i] > key) {
            // 当前节点的 k 已经比待插的 k 大，插入位置就是 i
            break;
        }
        i++;
    }

    // 第二步：叶子节点直接插入，非叶子节点递归到第 i 个孩子
    if (left.leaf) {
        left.insertKey(key, i);
    } else {
        this.doPut(left.children[i], key);
    }

    // 第三步：插入后如果 k 的数目到达了 MAX_KEY_NUMBER，就做节点分裂
}
```

那我们先来看第一步啊。第一步呢就是要找到这个当前节点中它的一个插入位置 `i`。比如说吧现在我的当前节点里面已经有 2 个 k 了，是 1 和 3，那我要先插入一个 2，那将来这个 2 呢在我们这个例子中，是不是你得找到它的插入位置，也就是索引 1 这个位置？3 呢他原来在索引 0，他应该向后移动，然后我们的 2 呢放在原来 3 的那个位置。

那这个查找过程呢，我们其实前面已经做过类似的，就是我们做那个 `get` 方法时做过类似的：先定一个临时变量 `i`，初始值是零，然后我们去循环，把我们待插的 k 拿过来，跟当前节点的 k 做一个比较。只要这个 `i` 还在有效的范围内，那么就不断循环，每次 `i` 加加；每次拿到当前节点的第 `i` 个 k 以后呢，我们就把它跟待插的 k 做一个比较。

- 如果二者相等了，那我们是不是就相当于找到了一个重复的 k？我们现在的逻辑是走更新，我们不允许有重复的，遇到重复的我们就走更新，目前呢我们也没有什么 value，所以这里就直接 return。
- 如果当前节点的 k 比待插的 k 小，比如说这里的 1 比待插的 k 小，那我是不是继续向后找啊，继续 `i` 加加继续向后找。
- 最后一种情况，就是当前节点的 k 比待插的 k 大了，比如说我已经遍历到 3 了，3 是不是比我待插的 2 要大了？这时候我们就应该退出循环。退出循环时，那个 `i` 的值是不是就是我们的插入位置？没问题吧，这时候我们的 i 就是插入位置。

等退出了这个循环以后，这时候 `i` 其实就已经是我们找到的那个插入位置了。那接下来就分成两种情况啊，就看一下当前这个节点，它如果已经是叶子节点了，那我们是不是就可以直接插入了？比如说刚才我这里找到插入位置 `i` 是索引 1，那我就直接往当前这个叶子节点插入这个新的 k 就可以了。那我们这里就直接去调用咱们以前写过的那个方法——节点类的 `insertKey`，把 k 和插入位置 `i` 传过去，它就完成了插入。

那 else 如果是非叶子节点呢，我们就要找它的孩子进行插入了，因为非叶子节点不能直接插入，得找孩子。那找孩子是找哪个孩子呢？就比如说啊你看我现在这个例子中，我要再插入一个 4，刚开始也是从根节点开始对吧，根节点这边找到它的插入位置是索引 1，因为 4 比 2 大，所以在索引 1 这个位置要插入 4。但是由于我们根节点它是一个非叶子，因此我们要继续找孩子啊，不能插入到非叶子节点。

那找孩子找哪个孩子呢？是找孩子 0 啊，还是孩子 1 啊？其实我们看出来规律了：我插入位置是 1，那就到 1 这个孩子，到 1 这个孩子里面继续递归查找就行了。也就是说我们到第二个孩子去递归完成插入，也就是这个 4 将来应该被插入到索引 1 的、也就是 3 这个节点这边，理解了吧？当然它的插入逻辑你就再走一遍就行了，在这个 3 这个节点里再找到他合适的插入位置，完成这个操作。

写成代码呢就是递归来调用我们的 `doPut` 方法，在当前节点第 1 个孩子里递归完成这个插入，然后插的 key 是我们刚才这个 k 啊。

> **结论**：非叶子节点不能直接插入，得递归；插入位置是 `i` 就进第 `i` 个孩子，两个 `i` 永远对齐。
>
> **提示**：这个 `i` 是整个递归过程里唯一的线索——它在当前节点里表示"插入位置"，到了下一层就变成"第几个孩子"，本质上是同一件事。

### split 的规律：一个节点如何一分为三

刚才呢我们已经初步实现了这个插入的方法。那插入完了以后呢，接下来有个事情比较重要，就是我们前面也说过，当一个节点中我们插入一个新的 k 以后，那这个 k 的最大数目它是有一个上限的对吧？那当它到达这个上限的时候，我们就要对节点进行一个分裂。那我们就来看一下这个分裂的一些规律。

我这张图呢先解释一下，因为我把它稍微改了。图里面黑色的大字还是我们的 k，k 呢可能有一个或者是多个；那这个小字呢是 k 的索引、k 的下标；红色的呢就表示它作为孩子时孩子的一个下标啊。比如说这里的 1，它就是我们根节点它的 0 号孩子；这里的 345 这个节点呢，它下面这个下标就是表示它是我们根节点 1 号的孩子。

那我们先来看一下什么时候分裂，然后分裂的一个规律。首先呢这个什么时候分裂，这个跟 `t` 有关，这个其实咱们前面说过一个式子啊：每个节点 k 的最大值等于 `2t` 减一。所以当 `t` 等于 2 的时候，`2t` 减一是 3 呀。比如说我现在这个树它的 `t` 就是等于 2，所以咱们看这个节点，这个节点里 k 的数目是不是已经到 3 了，已经到他的这个 k 的最大值了，那 345 这个节点接下来它就要分裂了。

#### t 等于二：最小的例子

就是首先大家要搞清楚，当我们一个节点中 k 的数目到达 `2t` 减一的时候，我们就要分裂了。那这个分裂的过程又是怎样的呢？

接着来看一下啊，那么我们需要把这个节点啊，其实有一个核心思想，就把这个节点它的 key 进行一个一分为三。怎么个一分为三呢？我们先新建一个节点，然后把把这个节点中最大的那个 k 给它挪到、或者说移动到新节点中。你看最大的 k 这个 5 对吧，把它移动到新节点中。那中间这个 k 呢就是 4 呢，移动到它的父节点中。那最后剩下的这个 3 呀留给他自己，这个最小的 k 留给他自己。大家看是不是一分为三了啊：小的留给自己了，中间的转移给了父亲，那最大的呢给了一个新节点。

```text
分裂前                              分裂后

        [2, 4]                          [2, 4]
       /   |   \                        /   |   \
     [1]  [3]  [5]     ────►        [1]  [3]  [5]
          被分裂的 [3, 4, 5]

left = [3, 4, 5]，t = 2，index = 1（它是根的第 1 号孩子）
    k[2] = 5   ──►  搬进新节点 right，插到 parent 的 index + 1 = 2 处
    k[1] = 4   ──►  上浮到 parent 的 index = 1 处
    k[0] = 3   ──►  留在 left 自己身上，keyNumber 也变成 t - 1 = 1
```

当然这个新节点呢，大家想他是不是也要作为我父亲的一个孩子啊？相当于父亲这边分裂出来以后，父亲这边就会多一个孩子，也就是这个 5 要作为 2、4 这个节点的孩子。那他应该作为哪个孩子呢？是作为 0 啊、1 啊，还是作为 2 号孩子？哎显然他应该作为 2 号孩子，因为他在这里边相对较大，是不是应该作为这个 2、4 这个节点的右侧来的？所以接下来 5 呢作为了右侧的孩子，原来这个分裂之前的节点啊，他是处于中间的孩子。

大家看现在它符不符合这种 k 的一个升序规则？符合的吧：左边的这个还是最小的 1，然后我们根节点是 2 和 4，中间夹着的呢是不是我们这个 3 呢？好那右边的是这个 5。这是它的一个分裂的效果啊，所以对于这种 `t` 等于 2 的一个分裂效果，这个很简单，就是把数据、把这个 k 啊一分为三：大的呢交给一个新的节点，中间的交给父节点，然后小的呢留给自己。

#### t 等于三：看得更清楚

好那我们再多看一个例子啊，这回呢我把这个树的 `t` 改成了三。那我先问一下，那 `t` 等于 3，它每个节点最大的 k 数目应该是几？是不是 `2t` 减一，应该是 5 呀。哎那我们现在这个还没到分裂的那个上限啊，我们再加一个，比如说我们再加一个 8，是不是应该加在我们这个叶子节点上。先把它加进来，加进来以后呢大家看现在这个节点是不是它满了？相当于它满满了，它已经达到了上限，它 k 的数目已经等于 5 了，这时候我们要分裂。

那它这个怎么分裂呢？其实跟我们刚才 `t` 等于 2 那棵树分裂时是类似的，它也是要把这个数据一分为三。那它怎么一分为三呢？大家来看啊，也是先创建出来一个新的节点。那你觉得应该把谁分给新节点呢？其实大家能猜到了，就是我把右边一半较大的啊，也就是 7 和 8，他俩是不是较大一些，把这个较大的 7 和 8 给它移动到新节点。然后还是中间的这个 6 呢给它移动到父节点，剩下的小的留给自己，把 4 和 5 较小的留给自己。是不是跟刚才类似啊？然后呢，当然这个新节点呢，我们将来把它作为父亲的一个新的孩子。

```text
分裂前                                分裂后
        [1, 2, 3]                           [1, 2, 3, 6]
          /  |  |   \                         /  |  |   |   \
       ...  ... ...  [4,5,6,7,8]  ──►      ... ... ... [4,5] [7,8]
                                             留下        搬去

t = 3，MAX_KEY_NUMBER = 5，叶子节点已经满了
    从索引 t = 3 开始的后半段（7、8）──►  right，一共 t - 1 = 2 个
    索引 t - 1 = 2 的 6               ──►  上浮到父节点
    剩下的（4、5）                      ──►  留给 left，keyNumber 变成 t - 1 = 2
```

#### 归纳成三条文字

好那我们刚才也看了 `t` 等于 2、`t` 等于 3 这个节点的一个分裂规律，那我们就来看一下把它总结成文字描述是怎样的。我一共总结了这么三条。

先给我这个图中这几个节点啊，咱们给几个称呼啊：首先这个待分裂的节点，我们给他个称呼叫 `left`，因为待会呢它是位于左侧的一个节点，叫做 `left`。然后新创建出来这个节点呢，因为他待会要位于右侧，那我们就把它叫做 `right`。当然他们还有个父亲啊，这个咱们就叫 `parent`。

先来看第一条：第一条呢就是把这个新节点 `right` 先创建出来，然后从这个旧节点 `left` 里面，我们要把一部分 k 啊，也就是分成三份嘛，中间这一份、右侧的这一半，咱们要移动到新节点中去，对不对。那现在有一个细节啊：那右侧从索引几开始算是右侧这一半呢？有没有规律？其实有啊，你看我们右侧的，我们一眼肉眼看出来是不是就是 7 和 8 呀？7 的索引是几啊？7 的索引是 3，这个 3 跟谁有关系啊？其实就是我们这个 `t` 啊。你看当我们 `t` 等于 3 的时候，那就从 3 这个索引开始，向后数的这些个 k 就是我们右边一半的 k，把它们呢要移动到新节点中。这是我们的第一条。

当然我们刚才第一条里啊，待会儿大家还会看到一个特例啊：我现在这个旧的节点是个叶子节点，将来它如果不是叶子节点，那我们还得考虑把他的孩子也要移动到新节点去去啊。至于有孩子的情况，我们遇到时我们再讲，现在先别着急。

那我们第二件事，是不是就要把中间这个 k 要移动到父节点去啊？中间这个 k 6 要移动上去。那我怎么知道哪个索引处的 k 是中间的 k 呢？有没有规律呀？哎也是有的，这个索引位置其实就是 `t` 减一。大家看是不是这样的？你看我现在这个 `t` 是不是等于 3 呀，3-1=2 呢，是不是就是我们中间这个 k 的索引？哎我们可以通过 `t` 减一就能找到中间的 k，然后把它移动上去。

但是移动上去之后啊，这个索引可能会变——你看移动前它的索引是 2 对吧，那移动后了变成 1 了。那移动后的这个索引有没有规律呢？也是有的。这个规律啊，大家可能不容易看出来，我说一下。但实际上这个规律啊，跟我们的这个被分裂节点它是第几个孩子有关系啊。比如说我们这个被分裂节点它是第一个孩子，那将来你中间的 k 移动上去以后，它的索引就是 1 啊；当然如果我们被分裂节点它的这个是第二个孩子，那中间这个 k 移动上去以后，它的索引就是 2 啊。所以我们这里有一个 `index` 啊这样一个称呼，它呢就代表的是我们被分裂节点 `left`，它是父节点的第几个孩子。这是我们的第二条。至于第二条这个规律啊，大家下去可以要自己试验一下，验证一下啊。

> **提示**：第二条为什么成立？因为被分裂节点是父节点的第 `index` 个孩子，它这一整棵子树里所有的 k，都大于父节点第 `index - 1` 个 k、又小于父节点第 `index` 个 k。所以中间那个 k 插进父节点时，不偏不倚正好落在第 `index` 个位置——它上浮之后索引不会变。

好最后第三条：第三条呢就是我们新的这个节点，那新的节点它将来是不是也要作为一个孩子插入到 `parent` 去啊？那它是作为第几个孩子呢？其实你看啊，我们被分裂节点是第一个孩子的话，那新的这个节点是不是应该是第二个孩子啊？他肯定是在被分裂节点的右边嘛，所以我们应该把它插入到 `index` 加一的地方。

> **结论**：三条口诀——右半边（从索引 `t` 起，共 `t - 1` 个）搬给 `right`；中间的（索引 `t - 1`）上浮到 `parent` 的第 `index` 位；`right` 挂到 `parent` 的第 `index + 1` 个孩子位。

### split 的实现：三步走

好那接下来呢我们就把这个分裂的方法咱们来实现一下。先把方法声明出来，方法呢叫做 `split`，都需要哪些参数呢？是不是你得首先有一个这个待分裂的节点啊，这个待分裂节点我就跟刚才的文字保持一致啊，咱们起个名字叫 `left`。还应该有什么参数呢？还应该有一个 `parent`，因为待会儿呢我们要把中间的 key 插入到 `parent` 去，所以你得需要知道这个 `parent` 节点是谁。那第三个参数呢，就是我们刚才在文字里提到的 `index`，也就是你被分裂节点，你是第几个孩子啊？你是第 0 个孩子，那就传过来 0；你是第 1 个孩子就传过来 1。这是我们的 `index`，`split` 的方法架子啊就有了。

#### 第一步：右半边的 k 搬进 right

有了以后呢，我们就按照他这些文字描述，我们一条一条实现啊。首先第一条呢我们要创建一个 `right` 节点，好，那么就来创建一个名字叫 `right` 的节点对象。那这个 `right` 节点创建的时候需要一个带参构造，这个参数呢就是我们的 `t` 啊，那这个咱们直接选择整棵树的 `t` 是不是就行了？因为我们说过整个这个树里所有节点它的 `t` 值应该是一样的，所以把这棵树的 `t` 传给他就可以了。

```java
private void split(Node left, Node parent, int index) {
    // 第一条：创建 right，把 left 中较大的一半 k 搬进去
    Node right = new Node(this.t);

    // 新节点和 left 是同一层的，所以 leaf 属性直接照抄
    right.leaf = left.leaf;

    System.arraycopy(left.keys, t, right.keys, 0, t - 1);
    right.keyNumber = t - 1;
    left.keyNumber = t - 1;

    // 非叶子节点还要把右半边的孩子搬过去，这个下一节展开
}
```

那新节点有了，我们需要先来考虑一个问题啊，就那个刚创建出来的节点，它应该是叶子节点呢，还是非叶子节点的？其实都有可能啊。我们刚才给大家这个场景下，将来它最后分裂完了，新节点是不是就应该是叶子节点，但是也有可能它是非叶子。那这个规律怎么找呢？

其实大家来看啊，这是我们分裂前的一个节点，这是我们的一个新节点。我就问分裂前的节点跟新节点，它俩是不是同一层的？是的吧，它俩都有同一个父亲嘛，肯定在同一层。所以呢我们分裂的这个节点它是叶子节点，那新节点肯定也是叶子节点对吧？那这个分裂前的节点它是非叶子节点，那我们的新节点是不是也是非叶子节点呀？所以新节点它的 `leaf` 这个属性应该跟 `left` 它的 `leaf` 属性是一样的。

接下来再看那个拷贝那块啊。下面呢我要把我们 `left` 它里面一部分的 k 要给它移动到我们的新的节点。正确，是不是就是两个数组之间的拷贝啊？从 `left` 的 `keys` 数组里拷贝一些元素，到这个 `right` 的 `keys` 数组里去。这个呢我们用哪个方法呢？就用 `System.arraycopy`。这个方法我们已经用过很多次了，它有五个参数：

- 第一个参数呢就是原始数组是谁啊？原始数组就是我们的 `left.keys`。
- 那从原始数组哪个索引位置开始拷贝呢？刚才说了，就是从 `t` 这个索引位置开始拷贝就可以了。
- 第三个参数就是说目的数组是谁？目的数组是不是我们这个 `right.keys`。
- 拷贝到目的数组哪个索引呢？你就想我 7 和 8 拷贝过去以后，是不是它的索引应该从零开始啊？所以第四个参数就是说目的数组应该拷贝到它的零索引位置。
- 最后一个参数是拷贝的元素个数。那我们刚才是拷贝过去几个元素？是不是两个呀。那这两个怎么来的呢？是不是就是 `t` 减一呀，对吧，`t` 减一就是它一半的元素个数。

好这样我们就把刚才较大的这些 k 啊，7 和 8 拷贝到新的节点的 `keys` 数组中去了。当然注意啊，我们拷贝过去以后，这个有一个细节就是新的这个节点，它的 `keyNumber` 是不是应该变一下啊？因为 `keyNumber` 表示它的有效的 k 的数目嘛，那刚才拷过去 `t` 减一个，所以它的有效 k 的数目也应该是 `t` 减一。

还有，被分裂的这个旧节点自己也要减：`left` 把 6 分出去了、把 7 和 8 也分出去了，它的有效 k 的数目也是不是应该减少啊？减少到几？也是减少到 `t` 减一啊，也就是 `left` 它的 `keyNumber` 也应该减少一下。它原来已经满了嘛，但是我们调整之后，它的 k 的数目应该是变成了 `t` 减一。

> **提示**：`System.arraycopy(src, srcPos, dest, destPos, length)`，第五个参数是"个数"而不是"结束位置"。我们搬 `t - 1` 个，是因为中位数自己不上阵——它要上浮到父节点去。

#### 第二、三步：中间的 k 上浮，right 挂到父节点名下

好接下来第二步呢是比较简单的，就是我们要拿到中间那个 k，然后把它插到父节点中去。那中间的 k 呢，它的索引位置我们前面都分析过了，就是 `t` 减一这个索引处的 6，所以出的这个 k 就是我们中间的 k。所以呢我们先把中间的 k 咱们拿到啊，也就是 `left.keys[t - 1]`，这是不是就拿到我们中间那个 k 了？起个名字叫 `middle`。

那要把它插入到哪去呢？插到父节点那父节点里面。他那个插入方法我们之前都实现过，直接调用就行了。第一个参数就是我们中间这个 k 啊 `middle`；第二个参数呢是要插的索引位置，这个索引位置是不是参数？这已经传过来了，传过来了，好，第二个参数就是我们的 `index` 啊。这是我们第二步，把中间的 k 插到父节点就做好了。

好最后呢我们把第三步也一起做了。第三步呢就是把我们刚创建出来这个 `right` 节点，它呢要作为父亲的一个孩子插入啊，插入的位置呢是 `index` 加一。这个也很简单啊，我们就是调用父亲的一个叫 `insertChild`，哎插入的孩子是谁呢？孩子是我们新的这个 `right` 节点；插的索引是谁呢？索引位置是不是应该是 `index` 加一啊？作为刚才它原始分裂节点它的索引位置加一处，把我们新节点加进去，这里我们写上 `index` 加一就可以了。

```java
    // 第二条：中间那个 k 上浮到父节点
    int middle = left.keys[t - 1];
    parent.insertKey(middle, index);

    // 第三条：right 作为 parent 的第 index + 1 个孩子
    parent.insertChild(right, index + 1);
}
```

### split 的两种特殊情况

好那我们的 `split` 方法初步的架子就写好了。但是接下来我们再来考虑两种特殊的情况。

#### 非叶子节点：孩子也得跟着搬

好那接下来我们就来看一种比较特殊的情况，就是非叶子节点它的一个分裂。

之前我们举的例子里都是一个叶子节点分裂。好那么来看这个例子，现在啊这棵树它的 `t` 等于 2，然后这个节点呢它的 k 已经有三个了，是不是已经满了啊？因为 `2t` 减 1 = 3 啊，它已经满了，满了的话那我们就要把它进行一个分裂。注意啊，它现在是不是属于非叶子啊？

那它的分裂过程跟之前叶子分裂有什么不一样呢？其实就多了一个步骤，那就是他得处理他的孩子了。

```text
分裂前                                分裂后
        [4, 8]                               [4, 8]
       /   |    \                            /   |    \
     [5]  [6]   [10]       ────►         [5]  [6]   [10]
        /  |   \                              |   /  |   \
       5  7   9  11                           7   9   11

t = 2，被分裂节点 keys = [6, 8, 10]，children = [5, 7, 9, 11]
    k[2] = 10                        ──►  搬进 right（t - 1 = 1 个）
    k[1] =  8                        ──►  上浮到 parent
    children 从索引 t = 2 起、搬 t = 2 个：9 和 11 ──► right 的 0 号、1 号孩子
    剩下的 k = [6]、children = [5, 7] 留在 left
```

好那么来看一下啊，哪个不一样啊？第一步就是要把这个新节点创建出来，这个跟以前一样的，然后呢把我们的较大的这个 k 复制过去，哎较大的 k 10 复制过去。但 10 复制过去以后，大家来看，那这里的孩子，也就是这里的 9 和 11 这俩孩子怎么办？其实这两个孩子应该作为新节点的两个孩子了，也就是把 9 和 11 要转移到新节点中去。你看啊，原来我这个 6、8 这个节点啊，它有 5、7、9、11 是不是有四个孩子？其实孩子数也多了，我要把这些孩子也分一点分给这个新的节点。分过去的是谁呢？肯定也是较大的 9 和 11 啊，分过去了。那 6 和 8 呢？还剩下了原来的小小的 5 和 7，这两个孩子没问题吧？

其实就是多了这一步啊，就分裂之后啊，我们不光是把较大的 k 给它移动到了新节点，还要把较大的这几个孩子也要移动到新节点。就这不一样了，那之后的都一样啊。

那我们把这个流程走完吧。好接下来还是找到分裂节点中间的这个 k，然后也就是这个 8 啊，把它移动到父节点去啊，8 被移动到父节点了。那接下来我们这个新节点怎么办呢？新节点是不是要作为父节点的孩子？而且呢它应该作为他的 2 号孩子啊，0、1 已经被这两个孩子占了对吧，将来我这个 10 呢在作为 4 和 8 的孩子的时候，就作为索引 2 处的孩子。大家看是不是它是作为索引 2 的孩子啊，他把刚才的 9 和 11 这两个更底层的孩子也一起带过去了。6、5、7 这一组对吧；9、10、11 这一组。

> **结论**：非叶子分裂比叶子分裂只多一件事——把右半边的孩子也搬到 `right`。别的步骤一模一样。

那我们把刚才这种情况它的代码咱们先补全。其实就是判断一下，如果我当前这个 `left` 啊被分裂的节点，它不是叶子节点，也就是它的 `leaf` 是 `false`，不是叶子，那我们是不是要多拷贝一些孩子过去啊。

那拷贝孩子是不是跟刚才拷贝 k 是类似的啊？你看我们刚才是把这个 k 也就是一个 k 10 拷过去了，那拷贝孩子是不是就相当于拷贝的数组不一样，以及拷贝的个数不一样吧。这个 k 只需要拷贝一个就行了，那我们这个孩子数是不是比 k 的数目要多，一个 k 对应两个孩子，都得拷过去啊，所以就是数组变一下，然后数目变一下不就行了。

好所以我们如果是非叶子节点，那么就来一个 `System.arraycopy`，数组呢是拷 `left` 它的 `children` 数组，把它的孩子数组进行拷贝。拷贝的起始位置跟刚才一样啊，跟拷贝 k 的那个起始位置也一样，都是从 `t` 开始；拷贝到哪去呢？拷贝到我们新节点它的 `children` 这个数组中去。拷贝过去以后啊，它的索引肯定是从零开始的对吧，你看 9 和 11 拷贝过来以后，索引从零开始。那拷贝的个数是几个呢？刚才我们拷贝 k 拷贝了 `t` 减一个，那拷贝孩子比 k 要多一个，是不是就是 `t` 啊？`t` 个就 OK 了。

> **易错点**：孩子比 k 多一个。拷 k 拷 `t - 1` 个，拷孩子要拷 `t` 个——起始索引都是 `t`，只是个数差一。

#### 根节点：得先造一个新根出来

好最后呢我们再来看一种特殊的情况，就如果分裂的是根节点会怎么样。

好大家来看这个例子，这个 `t` 呢还是等于 3，然后根节点已经放满了，已经有 5 个 k 了，那接下来它是不是要分裂了？好那它的分裂啊，就比我们普通节点的分裂稍微复杂一点啊，因为它得创建出来两个新的节点了。

哪两个呢？一个是新的根节点，我们原来这个分裂节点呢作为新的根节点的 0 号孩子；然后另外一个新节点呢，就对应着我们原来这个 `right`。这样创建出来两个新节点，这之后的所有步骤就跟以前一样了。

怎么做呢？就是把我们待分裂节点中的数据、分成三份对吧：4 和 5 较大的移动到下面的新节点中去，中间的 3 呢移动到父节点中去，他自己留着剩下的 1 和 2，然后再把 [4,5] 这个节点呢作为 [3] 的孩子啊。当然他作为孩子以后，它就是第一个孩子啊，原来这个 [1,2] 是作为第 0 个孩子。

```text
分裂前                                分裂后

     [1, 2, 3, 4, 5]     ────►          [3]
                                          /     \
                                     [1, 2]   [4, 5]

t = 3，根节点已经满了（5 = 2t - 1）
    大的 4、5  ──►  新节点 right，作为 new root 的第 1 号孩子
    中间的 3   ──►  成为 new root 自己的 k
    剩下 1、2  ──►  留在旧根节点，作为 new root 的第 0 号孩子
```

> **结论**：根节点分裂要多创建一个节点。普通分裂只产生 1 个新节点（`right`），根分裂产生 2 个（`newRoot` + `right`），旧根降级为 `newRoot` 的 0 号孩子。

那我们把最后这种如果分裂的是根节点，它的对应代码咱们实现一下啊。那怎么判断将来我这个 `left` 它是不是根节点啊？其实很简单，一种判断方法，你就检查一下它是不是等于 `this.root` 对不对。或者你也可以通过判断这个 `parent` 如果等于 `null`，哎是不是表示他没有父亲？没有父亲，就表示它是根节点嘛。所以我们先来提前做个判断啊。

那这个根节点怎么处理呀？其实从 `right` 以下的这些逻辑，也就是创建下面这个新节点啊，以下的逻辑都跟以前一样，只是我们要把这个新的根节点是不是创建出来。所以我们得创建一个新的根节点，那起个名字叫 `newRoot`。那这个新的根节点它的 `t` 啊，跟其他节点都一样，还是我们当前树的一个 `t`。

那它是不是叶子呢？那肯定不是叶子了，你想啊他都有孩子了，将来他的孩子是这个旧的根节点啊，所以他肯定不是叶子了，所以 `newRoot` 它的 `leaf` 属性应该设置为 `false`。没问题吧？

那我们这个旧的根节点，它是不是要作为新的根节点它的 0 号孩子呀？因此呢我们用 `newRoot` 它的一个叫 `insertChild` 啊，给他加一个孩子，加的孩子是我们原来的这个 `left`，也就是旧的根节点，然后加到索引 0 处。好，其实就咱们图中看到这个样子，新节点创建了，并且我们旧的根节点作为新节点的 0 号孩子。

那既然新的节点有了，那我们是不是用它代替掉原来旧的 `root` 啊，也就是 `this.root` 应该等于 `newRoot`。没问题吧？当然了，接下来大家哪里我要用到 `parent` 的话，那这个 `parent` 是不是就是我们刚刚的这个新节点了？所以 `parent` 也应该赋值为我们的 `newRoot`。

### 拼起来的完整 split

好这样我们这个代码就写完了，就是我们啊分裂的是根节点这种情况的一个处理。好到目前为止呢，我们这个 `split` 的方法就完全实现了。

那我们把刚才这个代码咱们再稍微梳理一下。

首先呢我们处理一种特殊情况，就是如果你分裂的是根节点的话，那它要比分裂其他普通节点要多做一件事。多做什么事呢？哎你就得创建一个新的根节点，然后用新的根节点呢取代掉原来的根，那原来根呢是作为新根的一个孩子。这些事做完了，我们对原来的根继续做分裂就可以了。好这是一种特殊情况啊。

好那对于这种其他的不是根节点，我们要做哪些分裂的活呢？哎第一件事就是要创建一个 `right` 这个新节点，`right` 新节点里其实放的就是我们分裂后较大的一半 k 啊，就是我们把原来这个节点中较大的一半 k 复制到这个 `right` 新节点中。那如果原来这个分裂节点它是非叶子的情况，你不光是要把 k 复制过去，你要把一些孩子也复制过去啊，把较大的一些孩子也复制作为新节点的孩子。下面这两行代码，就是因为你的这个 k 发生了变化了对吧？那所以我们要把新节点的 k 的有效数目，以及原来旧节点 k 的有效数目做一个更新。

这是我们做的这些事情啊。那下面呢就是找到中间的 k，中间的 k 要放哪去啊？哎要放到父节点上去。最后呢把我们刚刚创建出来 `right` 这个新节点，作为父节点的孩子。

把这几段拼起来，`split` 就是这个样子：

```java
private void split(Node left, Node parent, int index) {
    // ---------- 特殊情况：分裂的是根节点 ----------
    // parent 为 null，说明没有父亲，我们分裂的就是根节点
    if (parent == null) {
        Node newRoot = new Node(this.t);
        newRoot.leaf = false;
        // 旧的根节点 left，成为新根节点的 0 号孩子
        newRoot.insertChild(left, 0);
        this.root = newRoot;
        // 接下来要用到的 parent 就是这个新根
        parent = newRoot;
    }

    // ---------- 第一条：右半边较大的 k 搬进新节点 right ----------
    Node right = new Node(this.t);
    // 新节点和 left 同一层，leaf 属性照抄
    right.leaf = left.leaf;

    System.arraycopy(left.keys, t, right.keys, 0, t - 1);
    right.keyNumber = t - 1;
    left.keyNumber = t - 1;

    // 非叶子节点还要把右半边的孩子搬过去，比 k 多一个
    if (!left.leaf) {
        System.arraycopy(left.children, t, right.children, 0, t);
    }

    // ---------- 第二条：中间那个 k 上浮到父节点 ----------
    int middle = left.keys[t - 1];
    parent.insertKey(middle, index);

    // ---------- 第三条：right 作为 parent 的第 index + 1 个孩子 ----------
    parent.insertChild(right, index + 1);
}
```

回头再看一眼，最容易记混的其实就三个数字：`t` 是"右半边从哪儿开始搬"，`t - 1` 是"搬几个 k"和"中间 k 在哪儿"，`index` 贯穿"中间 k 上浮到哪儿"和"新节点挂到哪儿"。把这三个数字摁住了，`split` 就没有第二个难点了。

```text
分裂前
            [ 5 ]
           /     \
     [ 1 | 2 | 3 ]   [ 6 ]
        ↑ 要分裂的节点
          它是 root 的 0 号孩子
```

然后我要调用的就是：分裂的节点是那个 `1、2、3` 的节点，它的父节点是 `root`，它是 `root` 的 0 号孩子。这三个参数跟 `split` 的形参完全对得上，传过去，观察结果对不对。

#### 用 debug 把每一步走一遍

我们在 `split` 方法里打个断点，单步进入，边走边看。

第一件事：这次分裂的节点不是根节点，是 `root` 下面的那个节点，所以「分裂的是根节点」这个场景的第一个条件不成立，直接跳过去。这一点你得清楚——**这个测试用例覆盖不到根节点分裂**，那个场景另有测试用例负责。

跳过去以后，方法要在被分裂节点的右边创建一个新节点 `right`，然后给它把 `live` 属性赋好值。核心的这几行是：把 `left` 里较大的一部分 key 复制到新节点 `right` 里去。

这里有个特别容易懵的地方，我第一次看也懵了一下。执行完"复制较大的一半"这一步之后，debug 面板里 `right` 显示是空的——是不是没复制成功？不是。

原因是我们给 `left`、`right` 这些节点都重写了 `toString`，重写之后调试时只打印**有效的 key**，受 `keyNumber` 限制。这时候 `right` 的 `keyNumber` 还没改，还是初始值，所以你盯着面板看，怎么看都是空。把面板展开看数组本身，其实较大的那个 key `3` 已经复制过去了。

紧接着才改 `right` 的 `keyNumber`。一改完，`toString` 立刻就变了，面板上清清楚楚显示新节点里已经有了 `3`。然后回头把 `left` 的 `keyNumber` 也改成 1——它将来只保留较小的那一半，也就是 `1`。

接下来拿中间那个 key：这里是 `2`，要把它插到父节点里去。父节点原来那个 key 是 `5`，那插到哪个索引呢？**索引 0**。为什么？

> **提示**：因为我们分裂的这个节点本来就是 0 号孩子，将来它里面的东西一定比父节点这个 `5` 要小，往上移当然只能加到父节点的下标 0 上去。

插进去之后父节点变成了 `2、5`，索引位置也查到了。接着是最后一步：新建的 `right` 节点要挂回父节点的孩子数组里。父节点原来只有 `1` 和 `6` 这两个孩子，新的 `right` 插到哪？**`index + 1` 的位置**，也就是原来 0 号孩子的右侧。

```text
分裂后
            [ 2 | 5 ]
           /   |     \
        [ 1 ] [ 3 ]   [ 6 ]
```

`1、3、6`，对了。

所以这一遍 debug 走下来，大部分逻辑是被验证过的。但有一处**没有被覆盖到**：这次被分裂的节点是个叶子节点，它没有孩子，所以"复制孩子"那段代码根本没执行。这地方你得心里有数。

#### 用 assert 只看结果

debug 观察每一步是最细致的，但也最繁琐——每改一行代码都要重新走一遍，逐行比对。所以还有第二种办法：**只看结果对不对**。

思路很简单：分裂之后每个节点里面的 key，跟我心里想的是不是一致。而我们既然重写了 `toString`，就可以直接拿字符串比。

```java
assertEquals("2, 5", root.toString());
assertEquals("1", root.children[0].toString());
assertEquals("3", root.children[1].toString());
assertEquals("6", root.children[2].toString());
```

> **易错点**：`toString` 我用的是 Java 的 `Arrays.toString`，它会在多个元素中间加一个空格。所以你期望的字符串得写成 `"2, 5"`，中间那个空格千万别漏，不然断言死活不通过，你会以为是 split 写错了。

一个节点检查完，剩下的节点挨个检查就是了。四个断言全过，说明分裂结果跟预期完全一致，这个测试用例就过了。

剩下那些用例我就不在这儿演示了，但你们下去要自己补齐——**根节点分裂**的用例、**分裂的节点是非叶子**的用例，再加一个 `t` 等于 3 的用例等等。我只测了 `t` 等于 2 时的部分场景。

> **结论**：测试用例写得越全，你的代码出错的概率就越低。B 树这种结构，边界多、指针多，光靠"我觉得它是对的"是不作数的。

### 把 split 接进 put

#### 到底该在哪几个位置调用 split

先想清楚一个问题：`put` 方法的哪些位置，应该去调 `split`。

第一个位置最明显：**当我们往叶子节点里新插入了一个 key 之后**。新插的这个 key 有可能让这个节点的 key 数目达到上限。

```text
t = 2，往叶子节点再插一个 7

插入前                 插入后（满了）
      [ 2 ]               [ 2 | 4 ]
     /   |   \           /   |   |   \
   [1] [3] [5]   →     [1] [3] [5 | 7]
                                  ↑ keyNumber 到达上限
```

满了之后怎么办？一分为三：大的那部分放进一个新节点，中间的 key 上提到父节点，较小的部分留给自己，新节点也作为父节点的一个孩子挂上去。

那是不是只有叶子节点要分裂？**不是**。

叶子节点分裂完，它把中间的 key 上提到了父节点——父节点这时候**也有可能超过它的上限**。非叶子节点同样要分裂。所以不管是叶子还是非叶子，也不管是插完 key 之后还是递归从孩子返回之后，**统一都要检查一次：当前节点的 key 数目有没有到达上限**。

所以这个检查就放在 `if...else` 的**外面**，不用分别写在两个分支里：

```java
// 前面是叶子节点插 key / 非叶子节点递归的 if...else

// 统一检查：当前节点的 key 是不是满了
if (node.keyNumber >= MAX_KEY_NUMBER) {
    split(node, parent, index);
}
```

`MAX_KEY_NUMBER` 就是我们之前写过的那个常量。到了就是满了，直接调 `split`。

#### split 缺的两个参数，从 put 里给它补上

`split` 要三个参数：要分裂的节点是谁——这个好说，就是当前这个 `node`；但它还需要 `parent`（分裂节点的父节点）和 `index`（分裂节点是父节点的第几个孩子）。

问题来了：现在的 `put` 方法里根本没有这两个参数。

> **提示**：`split` 是被 `put` 调用的，那缺的这两个参数，最自然的来源不就是 `put` 自己吗？谁调我，我自然从调用方那里拿。

所以给 `put` 补上 `parent` 和 `index` 两个形参。补完之后一改，调用它的地方立刻报错——一共两个地方：递归调用那处，和最开始调用的那处。这两个地方我们分别把参数正确传进去就行。

**递归调用处**：我要去处理第 `i` 个孩子节点对吧。那这个孩子的父亲是谁？就是这个节点自己，`parent` 传 `node`；它是我处理的孩子里第几个？就是当前的 `i`，`index` 传 `i`。

```java
this.put(node.children[i], key, value, node, i);
```

**最开始调用处**：从 `root` 开始，`root` 的 `parent` 是 `null`，`root` 是第 0 个孩子。

```java
this.put(root, key, value, null, 0);
```

这样 `split` 缺的参数就补齐了，`doPut` 和 `split` 这两个方法正式结合起来。

#### 插 1 到 11，走一遍完整闭环

现在做一个完整测试：往这棵 B 树里依次添加 1 到 11，`t` 等于 2，然后检查预期结果。我们看几个关键步骤。

```text
                 [ 2 | 4 | 6 ]
```

### 删除之前，先给 Node 装九个工具方法

这节课正式开始讲 B 树的删除。

一提到树的删除，大家应该都有感觉——**复杂**。AVL 树的删除复杂，红黑树的删除复杂，B 树的删除也复杂。

为了让待会儿实现删除方法的时候更顺畅、代码更容易读懂，我先给我的 `Node` 节点类加了一些工具方法。这些方法都见名知意，就是为了让写代码的过程顺畅一点、易懂一点。

一共九个方法，从 `removeKey` 开始。看着是多，但每一个实现起来都非常简单，我们快速过一遍。

| 方法 | 干什么 | 返回 |
| --- | --- | --- |
| `removeKey(int index)` | 删掉 `index` 处的 key，它后面的 key 整体左移一位 | 被移除的 key |
| `removeLeftmostKey()` | 移除最左边的 key，即 `removeKey(0)` | 被移除的 key |
| `removeRightmostKey()` | 移除最右边的 key，即 `removeKey(keyNumber - 1)` | 被移除的 key |
| `removeChild(int index)` | 移除 `index` 处的孩子 | 被移除的子节点 |
| `removeLeftmostChild()` | 移除最左边的孩子 | 被移除的子节点 |
| `removeRightmostChild()` | 移除最右边的孩子 | 被移除的子节点 |
| `childLeftSibling(int index)` | `index` 处孩子左边的兄弟，即 `children[index - 1]`；`index == 0` 时左边没人，返回 `null` | 兄弟节点或 `null` |
| `childRightSibling(int index)` | `index` 处孩子右边的兄弟，即 `children[index + 1]`；已是最右则返回 `null` | 兄弟节点或 `null` |
| `moveToTarget(target)` | 把当前节点所有的 key 和 child **追加**到 `target` 上（不覆盖 target 原有的） | 无 |

前三个是一组，都是移除 key 的。`removeKey` 的代码最简单：先找到 `index` 处的 key，把它记到一个临时变量里，最后返回它；然后把 `index + 1` 处的 key 移到原本 `index` 处，也就是整体向左移动一位。`removeLeftmostKey` 和 `removeRightmostKey` 其实就是间接调用它，一个传 `0`，一个传 `keyNumber - 1`。

中间三个是一组，都是移除孩子的。跟移除 key 一一对应，也是移除指定位置、最左边、最右边。`removeChild` 返回的是被移除的那个节点对象。

再往下面两个是找兄弟的。以 `childLeftSibling` 为例：给你一个 `index`，先找到 `index` 处的孩子，但我真正要的是它的兄弟。如果 `index > 0`，说明它左边有人，那返回 `children[index - 1]` 就是它左侧的兄弟；如果 `index == 0`，说明它左边没有了，它自己就是最左边的，这时候只能返回 `null`。右兄弟完全对称。

最后一个 `moveToTarget`，把当前节点的所有 key 和 child 都复制到 `target` 节点去。这个名字起得不太好，将就看。里面也很简单：先检查一下当前节点是不是叶子节点，不是的话说明它有孩子，那就把它的孩子**追加**到 `target` 的孩子数组后面；然后 key 也追加过去。

> **易错点**：这里是"追加"，不是"覆盖"。`target` 原来已有的孩子不能覆盖掉，是接在它后面的。

这九个方法不难，加它们纯粹是为了让 `remove` 的实现更顺畅。

### 删除的六种情况

先声明一件事，这里说的删除，是**删除 B 树中某个节点的 key**，不是把节点删了，是在节点里找一个 key 来删掉。这点先明确。

整个删除我分成六种情况，逐个来看。

#### 叶子节点：没找到直接返回，找到直接删

`case 1` 和 `case 2` 都是叶子节点的情况。叶子节点的删除比较简单，就分"找到了"和"没找到"两种。

比如我要在叶子节点里删一个 key 为 5 的，这个节点里有吗？没有。那我们需要继续查找吗？**不需要了**。为什么？因为我是叶子节点，我没有孩子了，不可能在别的地方再找到这个 5 了。所以直接返回就行。这是 `case 1`。

如果是找到了呢？比如要删的是 3，3 在这个叶子节点里能找到，找到了——叶子节点的删除也很简单，**直接删**。把这个 3 删掉，剩下 `1、2、4`，完事了。这是 `case 2`。

```text
删 3 之前        删 3 之后
[ 1 | 2 | 3 | 4 ]   [ 1 | 2 | 4 ]
```

#### 非叶子节点：没找到往下找，找到了就用后继顶替

`case 3` 和 `case 4` 是非叶子节点。

先看这棵树，我想删除 6。从根节点开始找，根节点里有 6 这个 key 吗？没有。那我们是不是在这儿就停下来直接返回、不继续查找了？**不行。**

```text
        [ 3 ]
       /     \
[ 1 | 2 ]   [ 5 | 6 ]
```

因为现在这个根节点它是非叶子节点。在非叶子节点里，当前节点没有找到这个 key，**并不意味着这个 key 一定不存在**——你还得继续看它的孩子里有没有。小于 3 的去左边这个孩子，大于 3 的去右边这个孩子，继续查找。这是 `case 3`。

`case 4` 是：我想删的是 3，3 在根节点里已经找到了，可它又是非叶子节点，这时候我们不能直接删，怎么办？

> **提示**：讲红黑树的时候我们提过这个取巧的办法——**找它的后继 key**。3 的后继 key 是谁？是 4。那就用这个后继的 key 4，把刚才待删除的 key 3 替换掉。

替换完之后，删除动作就变了：变成我要删除后继的这个 4。接下来找到那个后继 key 4，把它删掉就可以了。整个效果看起来就相当于把 3 删了。这是 `case 4`。

```text
        [ 3 ]           [ 4 ]
       /     \         /     \
[ 1 | 2 ]   [ 5 | 6 ]  [ 1 | 2 ]  [ 5 | 6 ]
                       待删的 key 顺延成 4
```

#### key 数目低于下限就要重新平衡，根节点另说

`case 5` 是：删除以后 key 的数目小于一个下限了，这时候意味着这棵 B 树**不平衡**了，我们就要对树重新进行平衡性的调整。

这个下限还有印象吧？我们讲插入的时候提过一个上限，等于上限了就分裂。现在删除的时候，key 的数目不能太少——如果太少了，小于这个下限，同样要做一次平衡调整。

下限的值是多少？就是 $t - 1$。

我们现在这棵树 `t` 是 3，$3 - 1 = 2$。也就是说，如果某个节点的 key 数目小于 2，就意味着不平衡了。

```text
        [ 3 ]
       /     \
[ 1 | 2 ]   [ 5 | 6 ]
   2 个 key    2 个 key
   不小于 2    不小于 2
              → 平衡
```

在这个基础上，如果再删一个 5：叶子节点直接删掉，但删除后它的 key 数目变成 1 了，1 小于 2，就匹配到 `case 5` 了，这时候要对它做平衡处理。

```text
        [ 3 ]              [ 3 ]
       /     \            /     \
[ 1 | 2 ]   [ 5 | 6 ]  [ 1 | 2 ]   [ 6 ]
                        只剩 1 个 key < t - 1 = 2
                        → 不平衡，需要调整
```

> **注意**：这里有个例外——**根节点**。除根节点以外，其他节点的 key 数目如果小于 2，就意味着这棵 `t = 3` 的树不平衡了。根节点不用做 `case 5` 的检查。

这个平衡处理具体讲起来相对比较复杂，又分成三种情况：左旋、右旋、还有一个合并。这个我们讲到时再细讲。目前你只需要知道：**如果删除后 key 的数目小于下限值，就要重新对它做平衡调整**。

最后 `case 6` 是对根节点做一些特殊处理。`case 5` 那个"删除后 key 数目小于下限"的检查只是针对非根节点来讲的，根节点有它自己特殊的地方，这个也是讲到时再说。

所以整个 B 树的删除总结成六句话：`case 1`、`case 2` 是叶子节点，没找到直接返回，找到直接删；`case 3` 是非叶子节点没找到，到孩子继续找；`case 4` 是非叶子节点找到了，先用后继 key 替换掉，再转去删除那个后继 key；`case 5` 是删除后数目太少，不平衡，做平衡调整；`case 6` 是平衡调整时针对根节点的特殊处理。

### doRemove 的索引查找与六分支骨架

#### i 退出循环时的两层含义

接下来我们写删除方法。跟插入一样：一个公开的、带一个参数的 `remove`，再提供一个私有的、带两个参数的 `doRemove` 用来做递归。公开的 `remove` 间接调 `doRemove`，刚开始也是从根节点开始找待删除的 key。

重点当然在 `doRemove`。我能先想到的第一步是：**先在当前节点里找到这个 key 的索引位置**。

```java
private void doRemove(Node<K, V> node, K key) {
    int i = 0;
    while (i < node.keyNumber && node.keys[i] < key) {
        i++;
    }
```

它的意思就是：从 0 开始找，只要第 `i` 个 key 还在有效范围内、并且比待删除的 key 小，就 `i++` 继续往下找；**一旦遇到一个大于等于待删除 key 的值，就停下来**。

停下来的时候，`i` 有**两层含义**，这一点你一定要搞清楚：

```text
当前节点 key：  [ 1 | 2 | 3 | 5 ]        待删除：3

i = 0 → keys[0]=1 < 3 → i = 1
i = 1 → keys[1]=2 < 3 → i = 2
i = 2 → keys[2]=3 >= 3 → 停

i = 2，两层含义分别是：
  含义一：我找到了，i 就是待删除 key 的索引位置
  含义二：我没找到，i 就是要去查找的那个孩子的索引位置
```

我们拿两个例子对照着看，就彻底清楚了。

**例子一：节点里有 `1 2 3 5`，要删 3。** `i` 循环到 2 的时候停下，`keys[2]` 就是 3。**含义一**成立——找到了，`i` 是待删除 key 的索引位置。

**例子二：同一个节点里有 `1 2 3 5`，要删 4。** 4 不在这个节点里。是不是有可能在它的孩子里？有。那该到哪个孩子去继续找？

`i` 循环到 3：`keys[3]` 是 5，5 大于 4，停下。

我们手动把这五个孩子都排查一遍，看哪个才是对的：

```text
当前节点 key：  [ 1 | 2 | 3 | 5 ]
孩子：          [  ] [  ] [  ] [  ] [  ]
              0     1     2     3     4

0 号孩子：全 < 1 的 key          → 排除
1 号孩子：1 ~ 2 之间的 key      → 排除
2 号孩子：2 ~ 3 之间的 key      → 排除
3 号孩子：3 ~ 5 之间的 key      → 命中
4 号孩子：全 > 5 的 key          → 排除
```

所以我们应该到 **3 号孩子**里继续查找。而这个 3 是怎么来的？循环停下来时，遇到的是那个比我待删除 key 大的值，也就是 5，而 **5 的索引正好是 3**。

> **结论**：循环退出时停下位置的下标 `i`，就是接下来要查找的孩子的索引。**含义二**成立。

> **易错点**：`i` 退出循环后有两层含义，用之前一定要判断清楚是哪一层，否则后面找错孩子，B 树结构就乱了。

#### 把"找到没找到"抽成一个方法

既然循环退出后又可能有"找到"和"没找到"两种情况，那我们想在循环外再把这两种情况区分开，就还得再做一次条件判断：判断 `i` 是否仍在有效范围内（`i < node.keyNumber`），并且再比较一遍第 `i` 个 key 是否等于待删除的 key。

```java
    // i 仍在有效范围内，且 keys[i] == key，说明在当前节点找到了
    if (i < node.keyNumber && node.keys[i] == key) {
```

为了这段代码可读性更好一点，我把刚才这个判断条件**抽成一个方法**——IDEA 里是 `Ctrl + Alt + M`，然后给方法起一个更有意义的名字，就叫 `found` 吧。

#### 六种情况落到 if/else 上

代码写到这儿，就可以把六种情况的架子先写出来了。

先判断当前节点是不是叶子。如果是叶子，又分成找到和没找到：把条件取反，`!found(...)` 就是"没找到"，对应 `case 1`；能执行到 `else`，那就是"叶子并且找到了"，对应 `case 2`。

如果不是叶子，在外面再写个 `else`，把刚才那两个条件再拿过来用：`!found(...)` 是"不是叶子、没找到"，对应 `case 3`；"不是叶子、找到了"，对应 `case 4`。

```java
private void doRemove(Node<K, V> node, K key) {
    int i = 0;
    while (i < node.keyNumber && node.keys[i] < key) {
        i++;
    }

    if (node.leaf) {
        if (!found(node, i, key)) {
            // case 1：叶子节点，没找到 —— 直接返回
        } else {
            // case 2：叶子节点，找到了 —— 直接删除
        }
    } else {
        if (!found(node, i, key)) {
            // case 3：非叶子节点，没找到 —— 到孩子继续查找
        } else {
            // case 4：非叶子节点，找到了 —— 用后继 key 顶替
        }
    }

    // 无论叶子还是非叶子，操作完之后都要做这一次检查
    if (node.keyNumber < MIN_KEY_NUMBER) {
        // 重新调整平衡（case 5 / case 6）
    }
}
```

`case 1` 到 `case 4` 的架子都有了。

最后那一句检查同样重要：**不管是叶子还是非叶子，整个代码操作完了之后，都要判断一下它的 key 数目是不是小于下限了**。如果小于下限，我们就要重新调整平衡。

这个判断条件很容易写：`node.keyNumber < MIN_KEY_NUMBER`。这个下限常量我们以前写过的，`MIN_KEY_NUMBER`，它是怎么来的？在构造方法里，`t - 1` 就是我们 key 数目的下限。

至于"调整平衡"具体怎么调，我们待会儿单独再写一个方法，在这个方法里面再去区分 `case 5` 和 `case 6`——毕竟根节点的调整方式跟我们这些普通节点稍有不同。它们两个也可以写在同一个方法里。

这样，针对刚才那六种 case 的代码架子，我们就搭好了。

## B 树删除：四种情形与删完之后的平衡修复
> 对应块：BLK04 | 覆盖分集：P15-P18 | 块标题（分集名）：《基础算法-169-B树-remove-case1》

前面几讲我们把 B 树的删除在纸面上推了一遍——四种情形、每种情形该怎么走，心里其实都有数了。这一块就落到代码上，一行一行把它写出来。

写着写着你就会发现，真正麻烦的其实不是"找到之后怎么删"。删就一刀的事，麻烦的是删完之后某个节点的 k 数目掉到了下限以下，怎么把它补回来，而且还得保证整棵树的中序遍历依然是升序。

### 叶子节点上的两种情形

先看最省事的两种，都发生在叶子节点上。

**没找到要删的 k，直接 return。** 这里要特别强调"直接 return、不要让它继续往下走"，为什么？因为一旦让它往下走，它就可能走到调整平衡的那个方法里去。一个本来什么都没干的节点，你凭空去调一次 balance，纯属给自己找麻烦。所以 case 1 到这儿就写完了，一行代码。

**找到了就调节点的 removeKey，把索引 i 处的 k 删掉。** 这个工具方法前面写过——删除指定 index 处的 k。索引是哪来的？就是我们查找循环退出时的那个 i；找到的时候，i 天然就是待删除 k 的下标。

但这里有个坑：删完**不许 return**。因为删完之后，这个节点的 k 数目有可能低于下限，接下来还要再做一个判断，一旦小于下限就得做平衡调整。所以 case 2 执行完这一行，要继续往下走。

> **易错点**：这两个分支长得几乎一模一样，一个 return 一个不 return，差别就在这。case 1 中断，case 2 继续。

### 非叶子节点没找到，往第 i 号孩子递归

非叶子节点、并且没找到，那就得继续往孩子里找。落到第几个孩子呢？正是查找循环退出时的那个 i。

对着图看就很清楚了，举两个例子。

- 查找并删除 2：从根节点开始，退出循环时 i 是 0——因为第 0 个 k 比要删的 2 大，所以该到 0 号孩子里继续查找并删除。
- 查找并删除 6：第一次循环时 3 小于 6，不退出；第二次循环时 i 已经等于 k 的数目、超出了有效范围，循环退出时 i 是 1，那就到 1 号孩子里继续找 6。

写成代码就是一次递归调用：`doRemove(children[i], i, parent)`。k 不变，还是原来那个要删的 k。

> **提示**：往下传的这个 i 是"孩子编号"，也就是"我是第几个孩子"，不是"我在自己 keys 里的下标"。子节点自己算出来的 i 才是它自己的位置，别把这两层索引混了。

### 非叶子节点找到了，先换成后继 k

非叶子节点、并且找到了——这是最复杂的一种。前面分析过：不能直接删，得先把它替换成后继的 k。我们一步一步来。

#### 怎么找后继 k

讲二叉搜索树的时候，后继怎么找来着？从右孩子出发一路向左走，走到头就是后继节点。多路查找也是一样的道理，只是把"一路向左"换成了"一路取 0 号孩子"：

1. 起点是当前这个待删除 k 的**右邻孩子**，也就是索引加一处的那个孩子 children[i+1]。以九为例，九的索引是 0，0+1 就是 1 号孩子，里面的 k 肯定都比九大；
2. 只要它还不是叶子节点，就一直取它的 0 号孩子往左走，也就是一直找最左侧的孩子；
3. 走到叶子节点为止。走到头了，说明后继 k 就在这个节点里，而它里面可能有多个 k，最左侧的那个——第 0 个 k——就是后继 k。

写成代码就是先定一个 s 表示后继 k 所在的节点，起点是 children[i+1]，然后：

```java
while (!s.isLeaf()) {
    s = s.children[0];
}
Node successor = s.keys[0];
```

循环退出时，s 就是后继 k 所在的那个叶子节点，它的最左侧 k 就是我们要的后继 k。

#### 三步走

第一步，找到后继 k sk；第二步，把当前节点 keys[i] 处的待删除 k 替换成 sk；第三步，把"删除 k"转化成"删除 sk"——递归调用 doRemove，起点是刚才那个 children[i+1]，但这次删的 k 是 sk，不是原来的 k 了。

九被十替换上去，十自己就该被删掉了，所以最后要删的是十。三步做完，case 4 就完了。

### 删完之后余额不足：三种修法

case 1 找不到直接 return，剩下 case 2、case 3、case 4 执行完，**都有可能造成当前节点的 k 数目变少**。变少了以后，如果小于下限，就要对它进行一个重新的平衡调整。

以 t = 3 的这棵树为例，下限是 2。平衡的目的说白了就一个：让这个节点的 k 数目回到下限以上。

非根节点的情况我分成三种：右旋、左旋、合并；根节点的情况单独拎出来做特殊处理。整块判断串起来是这样一条链：

```text
删除之后，x 的 k 数目 < 下限
            │
            ├─ x 是根 ──────────────────▶  case 6：用 0 号孩子替换旧根，然后 return
            │
            └─ x 不是根
                 │
                 ├─ 左边兄弟存在，且它的 k 数目 > 下限 ──▶  case 5-1：右旋，然后 return
                 │
                 ├─ 右兄弟存在，且它的 k 数目 > 下限   ──▶  case 5-2：左旋，然后 return
                 │
                 └─ 两边都没有富裕的 k              ──▶  case 5-3：合并（向左合并）
```

#### 左边兄弟富裕，来一次右旋

看这张图。这棵树是平衡的，t 等于 3，下限是 2，两个节点的 k 数目分别是 3 和 2，都没有低于下限。现在我把 5 删掉，被调整节点的 k 数目就太少了，低于下限，得修。

那能不能向左边的兄弟借一个 k？可以，左边兄弟的 k 数目是富裕的。但**不能直接借**：兄弟那边最大的 k 是 3，你把 3 直接搬过来，它就小于父节点的 4 了——右边的 key 都必须大于父节点，这是我们一开始就定死的。

怎么办？转个弯：**先把父节点的 4 旋转下来，再把兄弟的 3 旋转上去。**

```text
   (1) 删前          (2) 删掉 5     (3) 右旋之后
     [ 4 ]                [ 4 ]          [ 3 ]
   /       \            /       \      /       \
[1,2,3]  [5,7]      [1,2,3]    [7]   [1,2]    [4,7]
 3个k                3个k              2个k      2个k
```

第三步里，被调整节点重新有了 2 个 k，兄弟那边也还剩 2 个 k（刚好等于下限，没问题），整棵树又恢复平衡了。

> **结论**：右边孩子缺，左边兄弟富裕 → 右旋。而且必须是严格的大于下限，等于下限不行——借走一个它自己就不够了。

#### 右边兄弟富裕，来一次左旋

另一种情况。删掉的是 1，删完之后这个节点不平衡了，k 数目小于 2。这回它没有左边的兄弟，但有个右边的兄弟，而且右边兄弟的 k 数目是富裕的——就算借走一个，它自己也不少于 2。

那就从右边兄弟借一个，借的方式是来一次**左旋**：把父节点的 3 旋转下来，把兄弟那边的 4 旋转上去。

```text
   (1) 删前          (2) 删掉 1     (3) 左旋之后
     [ 3 ]                [ 3 ]          [ 4 ]
   /       \            /       \      /       \
[1,2]  [4,5,6]      [ 2 ]  [4,5,6] [2,3]    [5,6]
 2个k                 2个k              2个k    2个k
```

左边没有兄弟，那就往右边看；右边兄弟富裕，一次左旋就完事了。

#### 两边都借不到，只能合并

刚才两种能靠旋转解决的，都有一个共同的前提：你得有左边的兄弟或者右边的兄弟，而且这个兄弟的 k 数目必须足够富裕，能借给你。

可要是下面这种场景就不行了。左边借走一个，左边自己就不够了，所以不能从左边借；右边呢，根本没有，无从借起。两边都不能借，旋转这条路就走不通了。

那就得换一个新办法——**合并**。

合并的目的是让节点的数目减少一个，把这些多出来的键值放到一起去，这样存活的这个节点的 k 数目就满足要求了。

具体怎么合并？这里我们统一采用一个**向左合并**的策略：位于右侧的这个节点我们就不要了，把它从父节点那里删掉，然后把它和父节点的一些 k 都合并到左侧那个节点上去。

```text
   (1) 删前          (2) 删掉 5         (3) 向左合并之后
     [ 4 ]                [ 4 ]                    [1,2,4,7]
   /       \            /       \                  /
[1,2]    [5,7]      [1,2]    [7]             （节点少了一个）
 2个k     删掉        2个k     1 < 2
          5 之后              借不到
```

顺序是有讲究的：**先把父节点的 4 追加到左侧节点的最右边，再把这个节点自己的 5 追加过去**。这样合并出来的 k 才是升序的。合并完成以后，之前 5 所在的那个节点就没用了，节点总数少了 1，存活下来的那个节点 k 数目就够了。

还有一个例子也一样：删掉 2 之后同样左边没得借、右边也没有兄弟，还是向左合并，右边那个节点将来删掉，把父节点的一个 k 追加到左侧节点里去，再把它自己的两个 k 追加过去，节点就少了一个，合并后的节点 k 数目也就够了。

#### 根节点：一个 k 都不剩就换人当根

根节点要做特殊处理。刚才那次合并之后，大家看根节点——它没有 k 了。这时候原来的根我们就没必要留着了，怎么办？**用它的 0 号孩子替换掉这个旧的根**，根节点就会有一次替换的操作。

### balance 的三个参数与骨架

概念上理清了，接下来把用来调整平衡的 balance 方法实现出来。

它需要三个参数：第一个是被调整的节点，是哪个节点要进行调整；第二个是这个节点所在的索引，也就是它是第几个孩子——这个参数本来应该叫 index，我图省事简称成 i；第三个是父节点 parent，前面讨论旋转和合并的时候都用得到它。

```java
private void balance(Node x, int i, Node parent) {
    if (x == root) {
        // case 6：根节点特殊处理
        return;
    }

    Node left  = parent.childLeftSibling(i);
    Node right = parent.childRightSibling(i);

    if (left != null && left.keys.length > lower) {
        // case 5-1：右旋
        return;
    }
    if (right != null && right.keys.length > lower) {
        // case 5-2：左旋
        return;
    }

    // case 5-3：合并
}
```

几个点值得停下来说一下。

**根节点先拦一道。** 如果被调整节点就是根，那就走 case 6 的特殊处理，处理完直接 return，不用再走下面左旋、右旋、合并这些逻辑了。

**左右兄弟怎么拿？** 还记不记得我一开始给节点类加了九个方法？其中两个就是找左右兄弟的方法——通过父节点，加上被调整节点的索引 i，就可以找到 i 这个孩子左边的兄弟 childLeftSibling，以及右边的兄弟 childRightSibling。直接拿来调用就行。

**判断条件里的那个"大于"是硬要求。** 左边兄弟不为空，并且它的 k 数目要大于下限；等于下限也不行，等于下限你借走一个，它自己就不够了，所以必须是严格大于才够借。右边同理。右旋完就平衡了，不用再往下走，直接 return；左旋完也一样直接 return；只有左右都不够借，才落到最后的合并分支。

### 右旋要做的三件事

先回忆一下右旋。假设现在把 9 这个 k 删掉，删完它所在节点的 k 数目太少，不平衡了。左边有没有兄弟？有，而且兄弟的 k 数目也是富裕的，于是匹配到 case 5-1，来一次右旋。

右旋具体做哪几件事呢？父节点里可能有多个 k，哪个该旋转下来？**要旋转下来的是被调整节点的前驱 k**，也就是比它小、而且离它最近的那个 k。

这里索引的推导要跟紧：被调整节点的索引是 i，那么它的前驱就在父节点 keys[i-1] 这个位置。被调整节点里的所有 k 都大于 keys[i-1]，而左边孩子里的所有 k 都小于它——所以它恰好就是最近的那个。旋转下来之后，它比被调整节点里所有 k 都小，所以要排到索引 0 的位置去。

比方说被调整节点的索引是 2，父节点里索引 1 处的那个 k 才是它的前驱。你要是把 11 旋转下来，或者把 4 旋转下来，1、2、4、5、6、7、8 都比它小，但都不是最近的，整棵树的升序就被破坏了。

另外还有一件事：左兄弟可能有孩子。这个我一开始嫌麻烦就没有加，后来还是补上了。想象一下——左兄弟本来有 3 个 k，就有 0、1、2、3 四个孩子；它最大的 k 旋转上去以后就只剩 2 个 k，两个 k 留着 0、1、2 这三个孩子就够了，那多出来的这个、也就是最右侧的那个孩子，就该过继给被调整节点，成为它最小的孩子。

所以右旋一共做三件事，文字描述就是：

1. 把父节点中前驱的 k 旋转下来，插入到被调整节点的最左侧（索引 0）；
2. 如果左兄弟不是叶子节点，把它最右侧的孩子移除，插入给被调整节点，作为被调整节点最左边的孩子；
3. 把左兄弟中最大的 k 旋转上去，覆盖掉父节点中刚才旋转下去的那个位置。

写成代码很短：

```java
// ① 父节点中前驱的 k 旋转下来，插到 x 的索引 0
x.insertKey(parent.keys[i - 1], 0);

// ② 左兄弟有孩子的话，最右孩子过继给 x，成为 x 最左边的孩子
if (!left.isLeaf()) {
    x.insertChild(left.removeRightmostChild(), 0);
}

// ③ 左兄弟最大的 k 旋转上去，覆盖父节点 i-1 处的位置
parent.keys[i - 1] = left.removeRightmostKey();
```

第 ③ 行是取 left 兄弟最右边的 k 把它删掉——因为 7 旋转上去以后它就没了，不要了——然后放到父节点里去，放到父节点 k 的 i-1 处，也就是刚才那个被旋转下来的 k 所在的位置，覆盖掉它。

### 左旋要做的三件事

右旋理解了，左旋就是它的镜像。这回我先把文字描述写出来，再写代码。

删除的是 5，删完之后这个节点不平衡，左边不够借，右边构建（够借），所以来一次左旋。三件事：

1. 把父节点中**后继的 k** 旋转下来，插入到被调整节点的最右侧；
2. 如果右兄弟不是叶子节点，把它最左侧的孩子移除，插入给被调整节点，作为被调整节点最右边的孩子；
3. 把右兄弟中最小的 k 旋转上去，覆盖掉父节点中刚才那个位置。

索引同样要跟紧：后继 k 在父节点里的索引**正好就是 i**，不是 i+1。被调整节点 children[i] 里的所有 k 都小于父节点的 keys[i]，而右边孩子里的所有 k 都大于它，所以 keys[i] 恰好是它的后继。比方说被调整节点的索引是 1，父节点索引 1 处的 k 就是它的后继。

旋转下来的这个后继 k，比被调整节点里所有 k 都大，所以要插到最右侧，索引就是 x.keys.length。

```java
// ① 父节点中后继的 k 旋转下来，插到 x 的最右侧
x.insertKey(parent.keys[i], x.keys.length);

// ② 右兄弟有孩子的话，最左孩子过继给 x，成为 x 最右边的孩子
if (!right.isLeaf()) {
    x.insertChild(right.removeLeftmostChild(), x.keys.length);
}

// ③ 右兄弟最小的 k 旋转上去，覆盖父节点 i 处的位置
parent.keys[i] = right.removeLeftmostKey();
```

第 ② 行这里要注意：孩子最右侧的索引比 k 最右侧的索引要多一，所以插入位置是 x.keys.length，而不是 x.keys.length - 1。图上没法体现，这一步只有代码。第 ③ 行就是右兄弟调 removeLeftmostKey 把最小的 k 删掉，然后旋转上去给 parent，覆盖 parent 的索引 i 处的 k。

### 合并：向左合并的三行代码

最后看 case 5-3。合并的规则是：**如果它有左兄弟，就把多出来的这些 k 向左合并到左兄弟去**——父节点的那个 k，加上我这个节点的所有 k，一起合并过去。

但也有另一种场景：删掉 2 之后，节点 k 数目不够了，左边没得借、右边也没得借，可是它没有左兄弟。没有左兄弟怎么合并？那就反过来，把它的右兄弟以及父节点的一个 k 合并到它自己这边，它自己就是最终合并的目标。

所以合并还得再分子情况：left 不为空是向左兄弟合并，else 是向自己合并。

#### 有左兄弟：三行

有左兄弟的情况下，大家想，被调整节点将来就不要了，所以应该从父节点那里把它删除掉。这就对应第一行代码：

```java
// ① 从父节点删掉被调整节点自己
parent.removeChild(i);

// ② 父节点的一个 k 合并到左兄弟（先父节点的 k，再自己的 k，升序才对）
left.insertKey(parent.removeKey(i - 1), left.keys.length);

// ③ 被调整节点剩下的所有 k 和所有孩子，都移到左兄弟
x.moveToTarget(left);
```

三行再过一遍。第一行，把被调整节点从它的父节点删掉；第二行，父节点这里拿一个 k 合并到左兄弟这边；第三行，把被调整节点剩下的 k 包括孩子，都移动到左兄弟这边。

第 ② 行的索引还是有规律的：被调整节点的索引是 i，待移过去的那个 k 的索引是 i-1，所以从父节点中被调整节点索引减一处的 k 移除掉，插入到左兄弟这边，插入位置就是左兄弟自己的 key number——它的最右侧。

顺序不能颠倒。先合并父节点的 4，再合并我自己的 7，才能是 1、2、4、7这样一个升序。你要是先把自己的 7 塞进 1、2 后面，再把 4 塞进去，中间就断开了。

第 ③ 行的 moveToTarget 是我们以前写过的方法：把当前节点所有的 key 和 child 都复制到 target。这里 target 就是左兄弟 left。

最后演示一下结果：把被调整节点 7 它的 k 合并过去以后，左兄弟就变成了 1、2、4、7，合并完成。

#### 没有左兄弟：注意索引变了

没有左兄弟的时候，向自己合并。找到它的右兄弟——右兄弟的索引肯定是 i+1 呗——把它从父节点这里移除掉，然后向它自己来完成这个合并。

```java
// ① 从父节点移除右兄弟
parent.removeChild(i + 1);

// ② 父节点的一个 k 合并到被调整节点自己
x.insertKey(parent.removeKey(i), x.keys.length);

// ③ 右兄弟所有的 k 和孩子都合并过来
right.moveToTarget(x);
```

> **易错点**：这一回父节点移除的 k，索引是 **i**，不是 i-1。为什么？因为此时被调整节点自己是父节点的 0 号孩子，它自己没有 k 了，要往自己这边合并，所以取的是紧贴着自己的那个分隔 k。大家注意看，索引位置有所不同，不要弄错了。

第 ② 行这回调的是 x.insertKey，插入位置是 x.keys.length，也就是被调整节点的最右侧。第 ③ 行是右兄弟调 moveToTarget，target 是我们的 x。合完就是 1、4、5、7 这样一个升序的 k。

至此，删除后调整平衡的几种情况就说完了。如果删除后这个节点的 k 数目小于下限：左边有兄弟且 k 数目富裕，就来一次右旋；右边兄弟存在且 k 数目富裕，就来一次左旋；左右都没有富裕的 k，就做一次合并；最后一种，合并之后根节点的 k 数目变成零了，就用它的 0 号孩子替换掉旧的根节点。

## B 树删除的最后一块拼图，与哈希表的由来
> 对应块：BLK05 | 覆盖分集：P19-P22 | 块标题（分集名）：《基础算法-173-B树-remove-case6》

前面 case 1 到 case 5 的代码，我们都实现得差不多了。最后还剩一个 case 6——被调整节点是根节点的情况。B 树的删除讲到这里就算收尾了，收完尾我们顺手把哈希表开个头。

### 删到根节点：唯一的失衡情形

先说结论，免得后面绕远路：**根节点绝大多数时候根本不需要我们动手。**

> **结论**：根节点的 key 数目是允许小于下限的。它就站在树顶，查数据的时候压根不需要靠兄弟借 key，所以前面那套"左旋 / 右旋 / 合并"的调整，对它统统不适用。

既然如此，那根节点什么时候会不平衡呢？只有一种情况。

我们来看这个例子。现在我删除了这个 k2，删完之后先别急着管 k2 自己，先看它落在哪一层——就是根节点那一层，根节点手里只有一个 k4，下面挂着四个孩子。删掉 k2 之后：

- k2 所在的这个节点，key 数目低于下限了；
- 左边不够借，右边也不够借；
- 那就只能合并，而且**它没有左兄弟可依**，只能"向自己合并"——右兄弟整个摘掉，父节点的 key 4 合并下来，右兄弟的 key 也并过来。

于是 1、4、5、7 合并到了一起，k2 所在的那个节点这下没问题了。

但麻烦在这儿：

```text
   合并完成后，根节点把仅有的那根 key 4 送了下去

        [ 4 ]  四个孩子        ⇒        [   ]  一个孩子
                                               ↑
                                    k 数目归零，只剩一条腿
```

> **易错点**：根节点失衡的唯一情形，就是它的 key 数目等于 0（换个说法，孩子数等于 1）。因为孩子数永远比 key 数目多一，只剩一个孩子，就意味着它只剩一条腿，站不住。

调整方法也很简单：拿它唯一那个孩子，顶替掉原来那个旧根，让这个孩子成为新根。代码就是这么写的：

```java
if (root.keyNumber == 0) {          // 唯一会失衡的根节点情形
    if (root.children[0] != null) { // 整棵树被删光时，别把 null 顶上去当新根
        root = root.children[0];
    }
}
```

#### 别把 null 顶上去当新根

为什么外面还要套一层 `root.children[0] != null`？这是一个特别容易漏掉的边界。

设想我不断地删，一根一根地把 1、4、5、7 全给它删光。删完之后大家来看——**这个时候 `keyNumber == 0` 这个条件是不是仍然成立？** 成立；根节点的 key 数目也确实变成零了。那这时候我们应不应该执行 `root = root.children[0]`？

不应该。因为这时候它连孩子都没了，我们把 `null` 替换上去，这个根节点就不对了，根节点必须留着。所以条件得改成：**只有当它的第 0 个孩子不等于 `null` 时，我们才把它作为新的根。**

> **提示**：`keyNumber == 0` 只回答了"会不会失衡"，没有回答"该不该动"。这两件事请务必分开写，否则删空一棵树的时候你会亲手把树删没了。

### 把 balance 接进 doRemove

到这里，用来调整平衡的 `balance` 方法就全部实现完毕了。接下来要干的事，是把它跟前面那个 `doRemove` 结合起来：**当我们发现某个节点的 key 数目小于下限时，就调用 `balance` 去重新调整平衡。**

#### balance 的三个参数

`balance` 需要三个参数：

| 参数 | 含义 |
|---|---|
| `parent` | 父节点 |
| `node` | 被调整的节点 |
| `index` | 被调整节点在父节点里的下标（第几个孩子） |

麻烦来了。回看这三个参数，前两个在 `doRemove` 里根本没有——`doRemove` 当时只接收一个参数，就是当前被删除的这个节点。剩下两个参数没有，怎么办？给他补上吧。

于是 `doRemove` 也得补充两个参数：一个是 `parent` 父节点，还有一个是当前节点 `node` 的索引位置，也就是它是第几个孩子。

#### 三处调用，三种补法

调用点一共有三处，每处的补法都不一样，得挨个儿看。

**第一处是首次调用**，从外部进 `doRemove` 的时候。这时候当前节点就是根节点，根节点没有父亲，所以 `parent` 传 `null`，`index` 给一个 0 就可以了：

```java
doRemove(null, root, 0);
```

**第二处**是非叶子节点上没有找到目标，要继续到它的孩子里去查找并删除。这时候我们处理的节点变成了孩子节点，它的父节点是谁？父节点就是这个 `node`。索引位置呢？我们是要到第二个孩子继续查找并删除，那位置当然就是 1：

```java
// key 比 node 的第 0 个 key 还小，到第 1 个孩子继续查找并删除
doRemove(node, node.children[1], 1);
```

**第三处**是用后继节点的 key 替换掉待删除节点的 key，然后去删除后继节点。这时候我们要到 `i + 1` 这个孩子那儿作为起点，去找那个后继 key 并把它删掉。父节点显然还是这个 `node`，索引位置也是 `i + 1`：

```java
doRemove(node, node.children[i + 1], i + 1);
```

> **易错点**：这三处最容易写混。判断标准只有一条——**下一个要被处理（被删除）的节点是谁，`parent` 就是谁，`index` 就是它在 `parent` 里的下标。** 递归往下走一层，就换一次爹。

### 单元测试替我抓出的那个笔误

`doRemove` 和 `balance` 都实现完毕了，那接下来就测试一下。我把从 case 1 一直到 case 5 的各种情况都准备好了测试用例，另外还有几个综合情况。我们先跑一遍。

一跑，发现其中有一个测试用例挂了，是左旋那个。

#### 先把预期结果推出来

在动手改代码之前，先解释一下我这个预期结果。原始的树是：根是 3，然后有两个孩子，一个是 `[1,2]`，一个是 `[4,5,6]`。现在我要删除 2。

那大家想，它这个流程应该怎么样？把 2 删掉以后，剩下这个节点 `e` 是不是就不平衡了？是不平衡了。但是这时候右边孩子的 key 数目是**富裕**的，所以我们可以左旋一次，向右边借一个。

左旋的效果是：把 3 旋转下来，把 4 旋转上去。所以最终平衡后的效果就是——根节点应该是 4，左边这个孩子是 `[1,3]`，右边这个孩子是 `[5,6]`。这是我们的预期结果。

可刚才它报错说根节点不对。我们期望的是 4，但返回的是 1。

#### 断点停在左旋里

那肯定是我的代码有写错的地方。我加个断点debug 一下——因为它已经告诉我问题出在左旋，那就直接在左旋这儿加断点。

进去以后先看这个条件，确实进到左旋这个条件里了。然后逐步走：

- **第一步**，把父节点的 key 旋转下来。父节点刚开始是 3，被调整节点是 1，3 旋转下来以后，这边应该变成 `[1,3]`——看起来是对的。
- **第二步**，要把他右兄弟最小的孩子换个爹，也就是 `[4,5,6]` 这个节点如果有孩子的话，把最左边那个换爹过来。但是现在这个 4、5、6 没有孩子，所以这个条件不成立，跳过——也是对的。
- **第三步**，最后要把右兄弟最小的 key 旋转上去，也就是把 4 旋转上去。旋转上去以后变成 1 了。

找到原因了：**是我代码这里写错了。是右兄弟的最左 key，也就是 right 的最左 key 要旋转上去，但我代码写的时候写成了 `x`。**

那问题就简单了，把这个 `x` 换成 right 的最左 key 就行了：

```java
// 写错了：把被调整节点自己的 x 顶了上去
parent.keys[index] = x;
// 应该是右兄弟最左边的 key
parent.keys[index] = right.leftMostKey();
```

改完之后重新跑一遍，是不是就通过了？通过了。我们把剩余的测试也全部跑一遍，可以看到所有的测试用例都通过了。

### 顺着删：综合一

B 树的删除操作讲完了，但整个删除流程还是比较复杂。我带着大家再看几个综合的例子，来加深一下印象。

这几个综合例子里我选取的 `t` 都等于 2（不是 3，别看错），下限就是 $t - 1 = 1$。

先看综合一。一棵有 11 个 key 的 B 树，key 从 1、2、3一直到 11。我们**从右边倒着删**——先删除 11，再删除 10，再删除 9，一直删到 1，把它删完。我们一起走一遍。

| 删除 | 是否失衡 | 做了什么 |
|---|---|---|
| 11 | 失衡 | 左兄弟不够键、右兄弟也不够 → 向左兄弟合并；父节点挪一个 key 下来 |
| ↑ 向上递归 | 父节点也失衡 | 继续向左合并；这一回被合并的节点**还带着孩子**，孩子也得一起挂到左兄弟下面 |
| 10 | 不失衡 | 删完还剩 9，key 数目没有小于下限，直接删 |
| 9 | 失衡 | 向左兄弟合并，父节点的 8 合并下来 |
| 8 | 不失衡 | 直接删 |
| 7 | 失衡 | 向左兄弟 5 合并，父节点的 6 合并下来；父节点再次失衡，继续向左兄弟 2 合并，父节点的 4 合并下来；被调整节点自己没有 key 可合并，但它有个孩子（存 5、6 的节点）要挂过去，得到 k = [2, 4]、孩子 = [1]、[3]、[5, 6]；随后根节点触发 case 6 |
| 6 | 不失衡 | 直接删 |
| 5 | 失衡 | 向左兄弟 3 合并，父节点的 4 合并下来；它没有 key 可合并，合完即可 |
| 4 | 不失衡 | 直接删 |
| 3 | 失衡 | 向左兄弟 1 合并，父节点的 2 合并下来；根节点再次触发 case 6，用 0 号孩子（1、2）替换旧根 |
| 2 | 不失衡 | 直接删 |
| 1 | 不失衡 | 会进入 case 6 的判断，但这次条件不成立——已经没有 0 号孩子了，所以不做任何处理 |

这里面有两处特别值得停下来看一眼。

**第一处，是删 11 之后的"有孩子合并"。** 合并这件事我们前面演示删除的时候并没有演示这种场景。被调整的节点自己是有孩子的，所以合并的时候，除了 key 要并过去，**它的孩子也得跟着并过去**。左兄弟接过来以后自己少了一个孩子，把这个补上，正好没问题。

**第二处，是父节点也会跟着失衡。** 这一点在代码里是有体现的。我们沿着 `doRemove` 一路往下删，删完叶子上的 11 之后，**最后还是会走到检查下限那段代码**，发现原来存 10 的那个节点，key 数目也小于下限了。

> **结论**：平衡调整是**递归的、由底向上的**。它从叶子一路上来，递归要走一遍，每一层都要重新检查一次。所以哪怕底层的一次合并看起来"很干净"，也可能连着触发上面好几层的合并，不能只盯着出问题的那一层看。

### 从中间删：综合三

再来看一个综合三。还是刚才那棵树，只不过这回咱们从中间来删，看看从中间删它的一些流程。

从中间删，第一件事绕不开：**4 所在的节点是非叶子节点，不能直接删。** 那怎么办？我们要先找到它的后继 5，用 5 替换掉 4，然后把删除的操作变成删除 5。所以接下来我们从 6 开始往下找，去删除 5。

5 被删掉以后，是不是不平衡了呢？是不平衡的。但是它左边没得借，右边也没得借，所以又是一个合并。那这回这个合并应该怎么合并？是不是向它自己合并？因为它没有左边兄弟了，向自己合并。把父节点的 6 先合并下来，右边这个兄弟 7 整个不要了，把 7 合并过来。合并完成了。

合并完成以后，它原来这个父节点这儿是不是又再次触发了不平衡？我们递归进行处理。这个父节点左兄弟也有、右兄弟也有，但是也是不够借，所以又是一次合并操作，向左合并。那我们这个 6、7 的分支就不要了，向左边兄弟 2 进行合并，把父节点的 5 挪下来一个。然后 2、5 这边现在有两个 key 缺一个孩子，那第三个孩子是不是就是我们刚才剩下的 6、7？给它挪过来，这样就恢复平衡了。

> 你看我们删了一个 4，做了多少次操作？两次合并操作，还有一个找后继的操作。一点都不简单。

后面几轮更能说明问题，因为**修复方式是在合并和旋转之间来回切换**的：

| 删除 | 用后继替换 | 删掉以后怎么修 |
|---|---|---|
| 8 | 后继 9 替换 8，转成删 9 | 9 删掉后两边都借不到 → 向自己合并（父节点的 10 下来、11 并过来）；父节点这次**左兄弟的 key 富裕** → 改用右旋 |
| 5 | 后继 6 替换 5，转成删 6 | 6 删完仍然满足平衡，直接删 |
| 6 | 后继 7 替换 6，转成删 7 | 左边没有，但右边够借 → 左旋（父节点的 9 下来、右边兄弟的 10 上去） |
| 7 | 后继 9 替换 7，转成删 9 | 不够借 → 向自己合并；父节点再次不够借 → 向左、向 2 合并，随后触发 case 6，用根节点 0 号孩子替换旧根 |
| 2 | 后继 3 替换 2，转成删 3 | 左边不够借，右边够借 → 左旋（父节点的 9 下来、右边兄弟的 10 上去） |
| 3 | 后继 9 替换 3，转成删 9 | 左右都不够 → 向左、向 1 合并，父节点的 9 合并下来 |
| 10 | 后继 11 替换 10，转成删 11 | 兄弟（1、9）的 key 富裕 → 右旋（父节点的 11 下来、9 上去） |
| 9 | 后继 11 替换 9，转成删 11 | 向左合并，得到 1、11；随后触发 case 6，用 1、11 替换旧根 |
| 1、11 | 直接删 | 都不会导致失衡 |

这三种修复动作摆在一起对比，会清楚很多：

```text
【右旋】左边兄弟有余，就向左借一个

    ① 本 吞下父的 key，本 变胖
    ② 本 最右边的那个孩子，改挂到新的父 底下
    ③ 兄 最左边的 key 上浮，接替父 原来的位置

    结果：  [ 兄' ]  [ 父' ]  [ 本' ]
            兄' 少一根 key       本' 多一根 key，右孩子被移走


【左旋】右边兄弟有余，就向右借一个

    ① 本 吞下父的 key，本 变胖
    ② 本 最左边的那个孩子，改挂到新的父 底下
    ③ 兄 最左边的 key 上浮，接替父 原来的位置

    结果：  [ 本' ]  [ 父' ]  [ 兄' ]
            本' 多一根 key，左孩子被移走


【向左合并】两边都借不到，把本整个并进左兄弟

    ① 父 少一根 key，并下沉进 兄
    ② 本 的 key 与孩子，全部并进 兄
    ③ 本 整个摘掉，退化为新的 [ 兄' ]

    结果：  [ 兄' ]  [ 父' ]
            兄' 多一根 key、多一批孩子
```

从中间删这一遍还能看出另一件事：**先旋转还是先合并，取决于兄弟手里有没有余量，而不是取决于你在树的哪一层。** 同样是非叶子节点引起的失衡，兄弟富裕就是旋转，兄弟不富裕就是合并，判据始终是同一个——回到前面那套判断里去看就是了。

### 别被我这套实现绑住手脚

关于 B 树的删除，我最后再提点大家几句。你去看网上的一些 B 树实现代码，可能会发现有些地方跟我的实现不太一样。会有哪些地方不一样呢？

**第一个地方，是删除非叶子节点上的 key 这种情况。** 我的做法是：如果我删除的 key 在非叶子节点上，不能直接删，我的做法是找到后继的 key，先用后继的 key 替换掉待删除的 key，然后把删除操作变成删除后继 key。那大家想一想，有没有其他办法呢？肯定有。我能不能用**前驱的 key** 来替换？思路是一样的，当然最后实现出来的效果可能稍有差异。所以网上有些实现，就是用前驱 key 替换掉非叶子节点中被删除的 key，然后把删除操作变成删除前驱 key。

**第二个地方，是做平衡处理时的合并操作。** 我这里统一是向左合并。那我就问，能不能统一向右合并？也可以的吧。我们所有合并操作都以右边为准向右合并，同样也能让树恢复平衡，当然最终合并出来的效果可能跟我的实现有所差异。

> **结论**：所以大家写代码的时候不要拘泥于我的实现。你可以在熟练了以后，尝试用新的思路去改写它——能改写，说明你真的懂它了。

### 哈希表从一个很朴素的需求开始

好，接下来我们开始学哈希表。

先不碰哈希表的概念，咱们先来看一个需求：**我如何能更快速地找到我的数据？**

就比如我们以前学过的红黑树、B 树，它们的查找速度已经很快了，它们是对数时间。但我希望比它更快，怎么办呢？

#### 给每个数据发一个编号，再配一张表格

我们来看这么一个思路。我先给所有的数据分配一个编号。比如说我有一堆人物的数据，那其中这个"肖"给他一个编号 0，这个"牛"给他一个编号 1，以此类推。

接下来呢，我再准备一张表格。当然在我们程序中，表格我们就可以用一个一维数组来表示。

然后我再去建立编号与表格索引之间的一个关系：刚才我们编号为 0 的数据，我将来就把它放在索引 0 的位置；编号为 1 的数据呢，就给它放在索引 1 的位置。这样把编号和数组的索引一一对应好，将来我知道了编号，就可以快速找到这个数据了。

```text
   编号                      表格（一维数组）

   [0] ─── 肖 ──────────→    索引 0 | 肖 |
   [1] ─── 牛 ──────────→    索引 1 | 牛 |
   [2] ─── 李 ──────────→    索引 2 | 李 |

   已知「编号 = 1 的数据」 →  直接跳到索引 1  →  一步到位
```

这种思路的查找时间复杂度是多少？它跟数据的规模有没有关系？没有。我们前面说过，如果是通过数组的索引来定位数据的话，它跟数据的规模没有关系。所以用了这种思路以后，我们查找数据的时间复杂度是 $O(1)$。

而且不仅仅是查询。我们找到这个数据以后，对它去做修改、或者要做删除，**增删改查的时间复杂度都是 $O(1)$**。

#### 理想很美，现实很贵

理想情况是这样的：这个编号是不是唯一的？那是最好了。并且呢，这个数组也是越大越好，如果能大到容纳所有的数据，那是最好了。

但是现实情况是怎样的？第一个问题：你不能说为了容纳所有的数据，我就造一个超大的数组。因为数组对内存还是有一定要求的，它要求数组中数据的**存储是连续的**，也就是要一块连续的内存。那如果我的数据量比如说是 100 万，那我的数组要求的连续内存长度也是非常大的，这对内存的分配来讲有点苛刻了。这一点不太现实。

第二个问题：这个编号也不能说绝对能保证它不重复，编号还是有可能重复的。

那怎么去解决我们刚才理想跟现实中的这个矛盾呢？大家先思考一下，我们先来看第一点。

#### 拉链法：一个索引下面挂一条链

我的数组长度是有限的。在这种有限长度的情况下，怎么让它存储更多的数据呢？

就比如说，我现在这个数组长度是 8，而且这个大小假设已经不能增长了，固定成 8 了，并且我现在给这八个索引都已经填满了数据。现在这个数组已经放满了。那如果我接下来再想放入第 9 个数据——有同学说，是不是就放不下了？放不下了。

那怎么办呢？我们可以这样来做：我们让即将放入这个数组的第 9 个数据，**也映射到一个索引**，比如说接下来这个数据还是映射到索引 0。

那有同学又说了，我放入了索引 0，它不就把前面这个编号为 0 的数据给覆盖掉了吗？

我们可以这样做，不让它覆盖。怎么做呢？我让后放入的数据跟前面放入的数据，它俩串成一个链表。你看，编号为 0 的"盐"，跟这个后放入的编号为 8 的"盐"，他俩串成一个链表。这样的话是不是就不会产生覆盖的效果了？

```text
   索引 0  ──→  [ 编号 0 的「盐」 ] ──→  [ 编号 8 的「盐」 ] ──→  nil
   索引 1  ──→  [ 编号 0 的「令」 ] ──→  nil
   索引 2  ──→  …

   第 9 个数据照样映射到索引 0，
   只是接在同一条链的尾巴上，谁也不覆盖谁。
```

这种方式我们称之为**拉链法**——用拉链法让一个有限长度的数组，存储更多的数据。

当然这样做也是有弊端的。什么弊端呢？**它会带来性能上的降低。**

你看，没有引入链表之前，我们要到这个数组里找一个数据，它的时间复杂度是不是 $O(1)$？我们无需比较，只要知道了编号，能通过编号定位到索引，那直接就拿到这个数据了，不需要做进一步的比较了。

但是有了链表以后呢？有了链表以后，你通过编号定位到这个索引，**并不能唯一确定它**——所以你要顺着链表，逐一地对链表的元素做一次比较，才能找到我们要的数据。所以这个时间复杂度就不再是 $O(1)$ 了，而是跟链表的长度有关。链表越长，你需要比较的次数就越多。

因此我们用了这种拉链法以后，虽然它能够解决我们之前的问题，但是它带来了性能上的降低。我们去具体实现的时候，大家就会看到我们要在**节省数组的占用空间**跟**增删改查的效率**之间，求一个平衡。

#### 编号重复了也不慌

第二点呢，是说将来理想情况下这个编号最好是唯一的，对吧？但是如果我们要通过算法去生成这样一个唯一的编号，那实现的难度是比较大的。

所以呢，我们为了降低生成编号时的算法难度，我们允许这个编号有适当的重复。不是说他绝对不能重复。

那有同学要问了，那万一这个编号重复了，我们怎么去区分数据呢？比如说我接下来又有一个编号为 0 的数据，加到我们这个表格里去了，那怎么进一步区分这个数据呢？

没关系，我们就通过数据本身是不是就能区分？你看，虽然编号都是 0，但一个数据是"盐"，一个数据是"令"，是不是还是能够把它确定出来的。所以编号重复了没关系，我们可以通过数据自身来进行区分。

#### 名字的由来：哈希表

有了前面的铺垫，我们回到今天的主题。我们今天要讲的数据结构叫**哈希表**。

哈希表中这个"哈希"是什么呢？其实就是我们刚才提到的编号。这个编号呢，将来我们给它一个称呼，叫做**哈希码**。连同它的数据一起放入表格，整个这个整体，我们就叫作哈希表——这就是"哈希表"这个名字的由来。

它的特点是什么呀？它的特点就是：只要我们把编号跟表格索引的关系给他建立好了，就可以通过这个编号快速查找到我们想要的数据。有多快？$O(1)$。

当然了，前面提到的那些理想跟现实中的矛盾，我们还是需要解决的：数组不能无限地长，怎么办？我们可以结合链表，来让这个有限长度的数组存储更多的数据。那这个编号呢，也不是说绝对要让它唯一，我们允许编号适当地重复，将来不行，就通过数据自身对它进行区分就行了。

这些是关于哈希表的一些概念性的知识。那接下来，我们去看看哈希表的具体代码实现。

- 真正落到叶子上的删除之后，如果该节点的 key 数目掉到 $t - 1 = 1$ 以下，就去判断兄弟：左边有余就右旋、右边有余就左旋；两边都不够借，就合并（我这套实现统一向左合并，统一向右合并也对）；

- 合并会让父节点少一根 key，所以调整是**自底向上递归**的，每一层都要重新检查一次；
- 如果最后根节点被摘空了，走 case 6，拿它的 0 号孩子顶上；如果整棵树都删空了，什么都不做。
