# 基础算法-165-B树-split-测试

## split 的验证次序

* **先测 split 再接 put**

    * > **定义**：把 `split` 测扎实之后才让它与 `put` 结合的固定次序。

    * 实现完了不等于就敢用；顺序反了，后面出了 bug 连往哪儿怀疑都不知道。

* **注释画草图**

    * > **定义**：手上没有那张分裂前后对照网页时，在测试方法里先画出分裂前、分裂后的树形，再照着草图写测试用例。

    * 草图要标出要分裂的是哪个节点，以及它在父节点里是第几个孩子。

    * 这个习惯值得一直保持，后面 B 树删除的六种情况同样画得出来。

* **实际使用的测试用例**

    * 根节点的 key 是 `5`，`keyNumber` 是 1，它有两个孩子。

    * 0 号孩子装着 `1、2、3`，`keyNumber` 是 3；1 号孩子装着 `6`，`keyNumber` 是 1。

    * 调用时三个形参完全对得上：要分裂的节点是那个装 `1、2、3` 的节点，父节点是 `root`，它是 `root` 的 0 号孩子。

    ```text
    分裂前
                [ 5 ]
               /     \
         [ 1 | 2 | 3 ]   [ 6 ]
            ↑ 要分裂的节点
              它是 root 的 0 号孩子
    ```

## debug 单步走查的验证与盲区

* **根节点分裂未被本用例覆盖**

    * 本次被分裂的节点是 `root` 下面的节点，不是根节点，所以「分裂的是根节点」这个场景的第一个条件不成立，直接跳过去。

    * 这个测试用例覆盖不到根节点分裂，那个场景另有测试用例负责。

* **重写 toString 造成的空节点假象**

    * > **定义**：节点类重写 `toString` 之后，调试时只打印受 `keyNumber` 限制的有效 key。

    * 执行完「复制较大的一半」之后，debug 面板里 `right` 显示是空的，但不是没复制成功。

    * 原因在于此时 `right` 的 `keyNumber` 还是初始值，盯着面板怎么看都是空；把面板展开看数组本身，其实较大的那个 key `3` 已经复制过去了。

    * 紧接着才改 `right` 的 `keyNumber`，一改完 `toString` 立刻变了，面板上清楚显示新节点里已经有了 `3`。

    * 然后回头把 `left` 的 `keyNumber` 也改成 1，它将来只保留较小的那一半，也就是 `1`。

* **中间 key 的上提位置**

    * 中间那个 key 在这里是 `2`，要把它插到父节点里去。

    * 父节点原来那个 key 是 `5`，插到索引 0。

    * > **提示**：分裂的这个节点本来就是 0 号孩子，将来它里面的东西一定比父节点这个 `5` 要小，往上移只能加到父节点的下标 0 上去。

    * 插进去之后父节点变成了 `2、5`，索引位置也查到了。

* **新节点的挂载位置**

    * 新建的 `right` 节点要挂回父节点的孩子数组里，父节点原来只有 `1` 和 `6` 这两个孩子。

    * 新的 `right` 插到 `index + 1` 的位置，也就是原来 0 号孩子的右侧。

    ```text
    分裂后
                [ 2 | 5 ]
               /   |     \
            [ 1 ] [ 3 ]   [ 6 ]
    ```

    * 分裂后四个节点的 key 是 `1、3、6`，验证正确。

* **本次走查的盲区**

    * 这一遍 debug 走下来大部分逻辑被验证过，但有一处没有被覆盖到：这次被分裂的节点是个叶子节点，它没有孩子，所以「复制孩子」那段代码根本没执行。

    * > **易错点**：只看 debug 面板会被重写过的 `toString` 误导，务必先确认 `keyNumber` 是否已经改过，再判断复制是否成功。

    * 测试用例写得越全，代码出错的概率就越低；B 树这种结构边界多、指针多，光靠「我觉得它是对的」是不作数的。

## 只看结果的断言写法

* **为什么改用断言**

    * debug 观察每一步是最细致的，但也最繁琐——每改一行代码都要重新走一遍、逐行比对。

    * 第二种办法只看结果对不对：分裂之后每个节点里面的 key，跟心里想的是不是一致；既然重写了 `toString`，就可以直接拿字符串比。

    * 一个节点检查完，剩下的节点挨个检查就是了。

* **四条断言覆盖全树**

    * > **定义**：四条断言全过，说明分裂结果跟预期完全一致，这个测试用例就过了。

    ```java
    assertEquals("2, 5", root.toString());
    assertEquals("1", root.children[0].toString());
    assertEquals("3", root.children[1].toString());
    assertEquals("6", root.children[2].toString());
    ```

    * > **易错点**：`toString` 用的是 Java 的 `Arrays.toString`，它会在多个元素中间加一个空格，所以期望的字符串得写成 `"2, 5"`，中间那个空格千万别漏，不然断言死活不通过，你会以为是 `split` 写错了。

* **要自己补齐的用例**

    * 根节点分裂的用例。

    * 分裂的节点是非叶子的用例。

    * `t` 等于 3 的用例等等；演示时只测了 `t` 等于 2 时的部分场景。

## split 在 put 中的调用位置

* **第一个调用位置：叶子节点新插入 key 之后**

    * 新插的这个 key 有可能让这个节点的 key 数目达到上限。

    ```text
    t = 2，往叶子节点再插一个 7

    插入前                 插入后（满了）
          [ 2 ]               [ 2 | 4 ]
         /   |   \           /   |   |   \
       [1] [3] [5]   →     [1] [3] [5 | 7]
                                      ↑ keyNumber 到达上限
    ```

    * 满了之后一分为三：大的那部分放进一个新节点，中间的 key 上提到父节点，较小的部分留给自己，新节点也作为父节点的一个孩子挂上去。

* **不止叶子节点要分裂**

    * 叶子节点分裂完把中间的 key 上提到父节点，父节点这时候也有可能超过它的上限。

    * 非叶子节点同样要分裂；不管是叶子还是非叶子，也不管是插完 key 之后还是递归从孩子返回之后，统一都要检查一次当前节点的 key 数目有没有到达上限。

    * > **注意**：这个检查放在 `if...else` 的外面，不用分别写在两个分支里。

    ```java
    // 前面是叶子节点插 key / 非叶子节点递归的 if...else

    // 统一检查：当前节点的 key 是不是满了
    if (node.keyNumber >= MAX_KEY_NUMBER) {
        split(node, parent, index);
    }
    ```

    * `MAX_KEY_NUMBER` 就是之前写过的那个常量，到了就是满了，直接调 `split`。

## put 补上 parent 与 index

* **split 需要的三个参数**

    * 要分裂的节点是谁，这个好说，就是当前这个 `node`。

    * 它还需要 `parent`（分裂节点的父节点）和 `index`（分裂节点是父节点的第几个孩子），而现在的 `put` 方法里根本没有这两个参数。

    * > **提示**：`split` 是被 `put` 调用的，那缺的这两个参数最自然的来源不就是 `put` 自己吗？谁调我，我自然从调用方那里拿。

* **补形参引发的两处报错**

    * 给 `put` 补上 `parent` 和 `index` 两个形参，补完之后一改，调用它的地方立刻报错，一共两个地方：递归调用那处，和最开始调用的那处。

    * 递归调用处：要去处理第 `i` 个孩子节点，这个孩子的父亲就是当前节点自己，`parent` 传 `node`；它是自己处理的孩子里第几个，`index` 传 `i`。

    ```java
    this.put(node.children[i], key, value, node, i);
    ```

    * 最开始调用处：从 `root` 开始，`root` 的 `parent` 是 `null`，`root` 是第 0 个孩子。

    ```java
    this.put(root, key, value, null, 0);
    ```

    * 这两个地方分别把参数正确传进去后，`split` 缺的参数就补齐了，`doPut` 和 `split` 这两个方法正式结合起来。

## 插入 1 到 11 的完整闭环

* **测试条件与最终结果**

    * > **定义**：往这棵 B 树里依次添加 1 到 11、`t` 等于 2 时的预期形态。

    * 最终结果：根节点是 `4、8`，第二层是 `2`、`6`、`10`，最底下一层分别是 `1 3`、`5 7`、`9 11`。

* **几个关键步骤**

    ```text
    插完 1 2 3   → 1 2 3 满了，2 上提
                            [ 2 ]
                           /     \
                        [ 1 ]   [ 3 ]

    插完 4 5     → 3 4 5 满了，4 上提
                         [ 2 | 4 ]
                        /   |   \
                     [ 1 ] [ 3 ] [ 5 ]

    插完 6 7     → 5 6 7 满了，6 上提
                     [ 2 | 4 | 6 ]
                    /   |   |   \
                 [ 1 ] [ 3 ] [ 5 ] [ 7 ]

                  此时非叶子节点 2 4 6 也满了 → 4 再上提
                               [ 4 ]
                              /     \
                      [ 2 | 6 ]   [ 1 | 3 | 5 | 7 ]

    插完 8 9     → 1 3 5 7 9 满了，8 上提
                         [ 6 | 8 ]
                        /   |   |   \
                     [ 5 ] [ 7 ] [ 9 ]

    插完 10 11   → 非叶子节点 6 8 10 满了，8 上提
                              [ 4 | 8 ]
                            /    |    |    \
                        [ 2 ] [ 6 ] [ 10 ]
                         / \    / \     /  \
                       [1][3] [5][7]  [9][11]
    ```

* **验证方式**

    * 验证的时候跟前面验 `split` 一个套路，挨个节点比 `toString` 就行。

    ```java
    assertEquals("4, 8", root.toString());
    assertEquals("2",   root.children[0].toString());
    assertEquals("6",   root.children[1].toString());
    assertEquals("10",  root.children[2].toString());
    assertEquals("1, 3", root.children[0].children[0].toString());
    assertEquals("5, 7", root.children[1].children[0].toString());
    assertEquals("9, 11", root.children[2].children[0].toString());
    ```

    * > **提示**：为了测试方便，把 `children` 属性都设成了非 `private`，测试的时候直接就访问了，省得写一大堆 getter、setter。

    * 能把 1 到 11 这个添加流程从头到尾自己梳理清楚，说明对 B 树的添加算是真理解了；看懂和能完整推出来是两回事。

## Node 的九个工具方法

* **为什么先加工具方法**

    * 一提到树的删除大家应该都有感觉——复杂，AVL 树的删除复杂，红黑树的删除复杂，B 树的删除也复杂。

    * 为了让实现删除方法的时候更顺畅、代码更容易读懂，先给 `Node` 节点类加一些工具方法。

    * 这些方法都见名知意，就是为了让写代码的过程顺畅一点、易懂一点；一共九个方法，从 `removeKey` 开始，每一个实现起来都非常简单。

| 方法 | 干什么 | 返回 |
| :--- | :--- | :--- |
| `removeKey(int index)` | 删掉 `index` 处的 key，它后面的 key 整体左移一位 | 被移除的 key |
| `removeLeftmostKey()` | 移除最左边的 key，即 `removeKey(0)` | 被移除的 key |
| `removeRightmostKey()` | 移除最右边的 key，即 `removeKey(keyNumber - 1)` | 被移除的 key |
| `removeChild(int index)` | 移除 `index` 处的孩子 | 被移除的子节点 |
| `removeLeftmostChild()` | 移除最左边的孩子 | 被移除的子节点 |
| `removeRightmostChild()` | 移除最右边的孩子 | 被移除的子节点 |
| `childLeftSibling(int index)` | `index` 处孩子左边的兄弟，即 `children[index - 1]`；`index == 0` 时左边没人，返回 `null` | 兄弟节点或 `null` |
| `childRightSibling(int index)` | `index` 处孩子右边的兄弟，即 `children[index + 1]`；已是最右则返回 `null` | 兄弟节点或 `null` |
| `moveToTarget(target)` | 把当前节点所有的 key 和 child 追加到 `target` 上（不覆盖 `target` 原有的） | 无 |

* **移除 key 的三个方法**

    * 前三个是一组，都是移除 key 的。

    * `removeKey` 的代码最简单：先找到 `index` 处的 key，把它记到一个临时变量里，最后返回它；然后把 `index + 1` 处的 key 移到原本 `index` 处，也就是整体向左移动一位。

    * `removeLeftmostKey` 和 `removeRightmostKey` 其实就是间接调用它，一个传 `0`，一个传 `keyNumber - 1`。

* **移除孩子的三个方法**

    * 中间三个是一组，都是移除孩子的，跟移除 key 一一对应，也是移除指定位置、最左边、最右边。

    * `removeChild` 返回的是被移除的那个节点对象。

* **找兄弟的两个方法**

    * 再往下面两个是找兄弟的，以 `childLeftSibling` 为例：给一个 `index`，先找到 `index` 处的孩子，但真正要的是它的兄弟。

    * 如果 `index > 0`，说明它左边有人，返回 `children[index - 1]` 就是它左侧的兄弟；如果 `index == 0`，说明它左边没有了、自己就是最左边的，这时候只能返回 `null`。

    * 右兄弟完全对称。

* **moveToTarget**

    * > **定义**：把当前节点的所有 key 和 child 都追加到 `target` 节点去。

    * 里面也很简单：先检查一下当前节点是不是叶子节点，不是的话说明它有孩子，那就把它的孩子追加到 `target` 的孩子数组后面；然后 key 也追加过去。

    * > **易错点**：这里是「追加」不是「覆盖」，`target` 原来已有的孩子不能覆盖掉，是接在它后面的。

    * 这九个方法不难，加它们纯粹是为了让 `remove` 的实现更顺畅。

## B 树删除的对象与六种情况

* **删除的对象**

    * > **定义**：这里说的删除是删除 B 树中某个节点的 key，不是把节点删了，是在节点里找一个 key 来删掉。

    * 整个删除分成六种情况，逐个来看。

### 叶子节点的两种情况

* **case 1：叶子节点没找到 —— 直接返回**

    * 例如要在叶子节点里删一个 key 为 5 的，这个节点里没有这个 5。

    * 不需要继续查找，直接返回就行。

    * > **定义**：因为我是叶子节点，我没有孩子了，不可能在别的地方再找到这个 5 了。

* **case 2：叶子节点找到了 —— 直接删**

    * 例如要删的 3 在这个叶子节点里能找到，找到了；叶子节点的删除也很简单，直接删。

    * 把这个 3 删掉，剩下 `1、2、4`，完事了。

    ```text
    删 3 之前        删 3 之后
    [ 1 | 2 | 3 | 4 ]   [ 1 | 2 | 4 ]
    ```

### 非叶子节点的两种情况

* **case 3：非叶子节点没找到 —— 到孩子继续找**

    * 例如想删除 6，从根节点开始找，根节点里有 6 这个 key 吗？没有，此时不能在这儿就停下直接返回。

    * 因为现在这个根节点是非叶子节点，在非叶子节点里当前节点没有找到这个 key，并不意味着这个 key 一定不存在，还得继续看它的孩子里有没有。

    * 小于 3 的去左边这个孩子，大于 3 的去右边这个孩子，继续查找。

    ```text
            [ 3 ]
           /     \
    [ 1 | 2 ]   [ 5 | 6 ]
    ```

* **case 4：非叶子节点找到了 —— 用后继 key 顶替**

    * 例如想删的是 3，3 在根节点里已经找到了，可它又是非叶子节点，这时候不能直接删。

    * > **提示**：讲红黑树的时候提过这个取巧的办法——找它的后继 key；3 的后继 key 是 4，那就用这个后继的 key 4 把刚才待删除的 key 3 替换掉。

    * 替换完之后删除动作就变了，变成要删除后继的这个 4；接下来找到那个后继 key 4 把它删掉就可以了，整个效果看起来就相当于把 3 删了。

    ```text
            [ 3 ]           [ 4 ]
           /     \         /     \
    [ 1 | 2 ]   [ 5 | 6 ]  [ 1 | 2 ]  [ 5 | 6 ]
                           待删的 key 顺延成 4
    ```

### key 数目低于下限与根节点例外

* **case 5：删除后数目太少要做平衡调整**

    * > **定义**：删除以后 key 的数目小于一个下限了，这时候意味着这棵 B 树不平衡了，就要对树重新进行平衡性的调整。

    * 讲插入的时候提过一个上限，等于上限了就分裂；现在删除的时候 key 的数目不能太少，如果太少了、小于这个下限，同样要做一次平衡调整。

    * 下限的值是 $t - 1$；现在这棵树 `t` 是 3，$3 - 1 = 2$，也就是说如果某个节点的 key 数目小于 2，就意味着不平衡了。

    ```text
            [ 3 ]
           /     \
    [ 1 | 2 ]   [ 5 | 6 ]
       2 个 key    2 个 key
       不小于 2    不小于 2
                  → 平衡
    ```

    * 在这个基础上如果再删一个 5：叶子节点直接删掉，但删除后它的 key 数目变成 1 了，1 小于 2，就匹配到 `case 5`，这时候要对它做平衡处理。

    ```text
            [ 3 ]              [ 3 ]
           /     \            /     \
    [ 1 | 2 ]   [ 5 | 6 ]  [ 1 | 2 ]   [ 6 ]
                            只剩 1 个 key < t - 1 = 2
                            → 不平衡，需要调整
    ```

    * 平衡处理具体讲起来相对比较复杂，又分成三种情况：左旋、右旋，还有一个合并。

    * 目前只需要知道：如果删除后 key 的数目小于下限值，就要重新对它做平衡调整。

* **case 6：针对根节点的特殊处理**

    * > **注意**：`case 5` 那个「删除后 key 数目小于下限」的检查只针对非根节点；除根节点以外，其他节点的 key 数目如果小于 2，才意味着这棵 `t = 3` 的树不平衡了，根节点不用做 `case 5` 的检查。

    * 根节点有它自己特殊的地方，在平衡调整时单独处理。

* **六句话总结**

    * `case 1`、`case 2` 是叶子节点，没找到直接返回，找到直接删。

    * `case 3` 是非叶子节点没找到，到孩子继续找。

    * `case 4` 是非叶子节点找到了，先用后继 key 替换掉，再转去删除那个后继 key。

    * `case 5` 是删除后数目太少，不平衡，做平衡调整。

    * `case 6` 是平衡调整时针对根节点的特殊处理。

## doRemove 的索引查找

* **remove 与 doRemove 的分工**

    * > **定义**：跟插入一样，一个公开的、带一个参数的 `remove`，再提供一个私有的、带两个参数的 `doRemove` 用来做递归。

    * 公开的 `remove` 间接调 `doRemove`，刚开始也是从根节点开始找待删除的 key。

* **定位索引的循环**

    * > **定义**：从 0 开始找，只要第 `i` 个 key 还在有效范围内、并且比待删除的 key 小，就 `i++` 继续往下找；一旦遇到一个大于等于待删除 key 的值，就停下来。

    ```java
    private void doRemove(Node<K, V> node, K key) {
        int i = 0;
        while (i < node.keyNumber && node.keys[i] < key) {
            i++;
        }
    ```

* **i 退出循环时的两层含义**

    * > **易错点**：`i` 退出循环后有两层含义，用之前一定要判断清楚是哪一层，否则后面找错孩子，B 树结构就乱了。

    * 含义一是找到了，`i` 就是待删除 key 的索引位置。

    * 含义二是没找到，`i` 就是要去查找的那个孩子的索引位置。

    ```text
    当前节点 key：  [ 1 | 2 | 3 | 5 ]        待删除：3

    i = 0 → keys[0]=1 < 3 → i = 1
    i = 1 → keys[1]=2 < 3 → i = 2
    i = 2 → keys[2]=3 >= 3 → 停

    i = 2，两层含义分别是：
      含义一：我找到了，i 就是待删除 key 的索引位置
      含义二：我没找到，i 就是要去查找的那个孩子的索引位置
    ```

* **例子一：待删 key 在当前节点里**

    * 节点里有 `1 2 3 5`，要删 3，`i` 循环到 2 的时候停下，`keys[2]` 就是 3。

    * 含义一成立——找到了，`i` 是待删除 key 的索引位置。

* **例子二：待删 key 不在当前节点里**

    * 同一个节点里有 `1 2 3 5`，要删 4，4 不在这个节点里，但有可能在它的孩子里。

    * `i` 循环到 3：`keys[3]` 是 5，5 大于 4，停下。

    * 手动把这五个孩子都排查一遍：0 号孩子全是小于 1 的 key，排除；1 号孩子是 1 ~ 2 之间的 key，排除；2 号孩子是 2 ~ 3 之间的 key，排除；3 号孩子是 3 ~ 5 之间的 key，命中；4 号孩子全是大于 5 的 key，排除。

    ```text
    当前节点 key：  [ 1 | 2 | 3 | 5 ]
    孩子：          [  ] [  ] [  ] [  ] [  ]
                  0     1     2     3     4

    0 号孩子：全 < 1 的 key          → 排除
    1 号孩子：1 ~ 2 之间的 key      → 排除
    2 号孩子：2 ~ 3 之间的 key      → 排除
    3 号孩子：3 ~ 5 之间的 key      → 命中
    4 号孩子：全 > 5 的 key          → 排除
    ```

    * 所以应该到 3 号孩子里继续查找；这个 3 是循环停下来时遇到的那个比待删除 key 大的值 5 的索引。

    * 循环退出时停下位置的下标 `i`，就是接下来要查找的孩子的索引，含义二成立。

* **把「找到没找到」抽成一个方法**

    * 循环退出后又可能有「找到」和「没找到」两种情况，想在循环外再把这两种情况区分开，就还得再做一次条件判断。

    * 判断 `i` 是否仍在有效范围内（`i < node.keyNumber`），并且再比较一遍第 `i` 个 key 是否等于待删除的 key。

    ```java
        // i 仍在有效范围内，且 keys[i] == key，说明在当前节点找到了
        if (i < node.keyNumber && node.keys[i] == key) {
    ```

    * 为了这段代码可读性更好一点，把刚才这个判断条件抽成一个方法；IDEA 里是 `Ctrl + Alt + M`，然后给方法起一个更有意义的名字，就叫 `found`。

## doRemove 的六分支骨架

* **叶子节点的两分支**

    * 先判断当前节点是不是叶子。

    * 如果是叶子，又分成找到和没找到：把条件取反，`!found(...)` 就是「没找到」，对应 `case 1`。

    * 能执行到 `else`，那就是「叶子并且找到了」，对应 `case 2`。

* **非叶子节点的两分支**

    * 如果不是叶子，在外面再写个 `else`，把刚才那两个条件再拿过来用。

    * `!found(...)` 是「不是叶子、没找到」，对应 `case 3`；「不是叶子、找到了」对应 `case 4`。

* **统一的平衡检查**

    * 不管是叶子还是非叶子，整个代码操作完了之后，都要判断一下它的 key 数目是不是小于下限了。

    * 判断条件是 `node.keyNumber < MIN_KEY_NUMBER`；这个下限常量以前写过，在构造方法里 `t - 1` 就是 key 数目的下限。

    * 「调整平衡」具体怎么调另外再写一个方法，在这个方法里面再去区分 `case 5` 和 `case 6`，因为根节点的调整方式跟普通节点稍有不同，它们两个也可以写在同一个方法里。

    ```java

        int i = 0;
        while (i < node.keyNumber && node.keys[i] < key) {
            i++;
        }

        if (node.leaf) {
    ```
