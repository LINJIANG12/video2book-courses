# 进阶数据结构和算法-257-零钱兑换-递归

## 力扣 518 与 322 的孪生关系

* **518 零钱兑换 II**

    * > **定义**：给定若干种硬币与一个总金额，求凑成该总金额**一共有几种凑法**。

* **322 零钱兑换**

    * > **定义**：题干与 518 几乎孪生，仍是那几种硬币、仍凑同一个总金额；变的只是要的结果——不在若干种凑法里问「有几种」，而是挑出其中硬币个数**最少**的一种，返回这个硬币个数。

* **遍历框架完全一致**

    * 都是拿硬币数组去递归，每一枚硬币都试「用」与「不用」，直到剩余金额归零就记一种解。

    * 唯一变的是「记一种解」这个动作之后怎么办，所以整套代码不必重写，只需在 518 的框架上改动。

* **对照例子**

    * 5 分、2 分、1 分凑 5 共有四种凑法，其中只用一个 5 分硬币，硬币个数是 1，这就是 322 要的数。

    * 例子中四种凑法都已列出，最少硬币数无需额外推导即可从「只有一个 5 分」读出。

## 暴力递归版的两个新增量

* **静态变量 min**

    * > **定义**：代表最终要求的最少硬币个数，声明为 `static int min = -1;`。

    * 初始值取 `-1`，因为题目规定 `-1` 代表没找到解。

    * 边界情形：手里只有 2 分硬币而总金额要求 3，根本凑不成，返回 `-1`。

    * 找不到解时它全程不被更新，最终仍是 `-1`；一旦找到解就写回这个值。

* **递归方法新增的参数 count**

    * > **定义**：代表某一种硬币组合中钱币的总数，用 `AtomicInteger` 承载。

    * 5、2、1 凑 5 的四种解里，第一种组合钱币数是 1 就把这个 1 记进 `count`，第二种组合钱币数是 3 就记 3。

    * 后面再加的两个参数纯粹为了把每种组合都打印出来、方便理解整个过程，属于辅助作用，去掉不影响这道题本身。

    * > ⚠️ **易错点**：`min` 全程只读只写、最后拿结果，而 `count` 每一层递归都要改，所以它不能用 `int` 也不能用 `Integer` 包装类型，只能用可变的 `AtomicInteger`。

### count 计的是当前这条路径

* **进自增，出去自减**

    * 进入方法时执行一次 `incrementAndGet()`，把内部维护的硬币数加一；退出这个方法时执行一次 `decrementAndGet()`，把它自减回去。

    * 首次调用时初始值是 -1，进入时 -1 加一，正好被初始化成零，从零开始数。

    * 继续往下递归再次进入时这个值被加一，含义是「我又用掉了一枚硬币」，这样它就知道自己有一种组合、需要几枚。

    * 一条路径试完、方法调用结束后要减一，减回零是为了接下来执行下面的组合时**再从零开始计数**。

    * > **定义**：`count` 记录的是**当前这条递归路径上已经用掉的硬币个数**，而不是「总共找到了几种解」，这是理解自增自减的关键。

    * 进来自增是为了**正确计数**，出去自减是为了**正确归零**，两个动作缺一不可。

* **实例：2+2+1 这一种组合**

    * 第一次用到 2 分，硬币数从零加到一；第二次又用到 2 分，加到二；第三次用到 1 分，加到三，于是知道这第二种组合总共用了三个硬币。

    * 这轮递归走完后方法逐层退出就逐层减回去，最后回到零，下次再尝试下一种组合。

### 方法内部的三种剩余金额

* **剩余金额大于零**

    * 说明还能凑，继续递归，这是方法里的第一种情况。

* **剩余金额等于零**

    * 说明找到解了，把这时候的 `stack`（当前这条路径上的组合）打印出来。

* **剩余金额小于零**

    * 表示这条路走不通、凑过头了，属于无解；322 题里无解不需要额外处理，所以干脆没把这个 `else` 写进来，`min` 始终没被更新。

### 最少硬币数的更新规则

* **第一个解直接赋值**

    * 找到的是第一个解时，无所谓有没有更小的，直接把当前 `count.get()` 记到 `min`——因为它前面根本没有解，当前这个就是最好的，谈不上「挑一个更小的」。

* **之后再找到解才挑较小**

    * 说明之前已经有解了，此时要在「之前的解」和「当前的解」之间挑一个硬币数更小的去更新。

    * 所有递归执行完后返回这个静态变量，就是最终要的最少硬币数。

```java
if (min == -1) {                          // 找到的是第一个解
    min = count.get();                     // 无所谓有没有更小的，直接记下
} else {                                   // 说明之前已经有解了
    min = Math.min(min, count.get());      // 之前的解和当前的解，挑硬币数更小的
}
```

## 贪心思路与它的两条原则

* **从大面值的硬币开始凑**

    * 总金额 18、硬币种类是 5 分、2 分、1 分时，最自然的想法是从大面值开始。

    * 五分硬币看起来「好像快凑够了」，比从 1 分开始凑经济；虽然 18 个 1 分也能凑足 18，但硬币数一下子就上去了。

    * 具体走法：准备三个 5 分共 15 分，还差 3 分用一个 2 分，剩 1 分再准备一个 1 分，剩余金额归零，总共用 3+1+1 = 5 个硬币。

    * 这个从大往小凑的思路能得到正确结果，而且**只用了一次就完成**，后续不用再试其他组合——它就是贪心思路。

### 贪心的两条原则

* **原则一：每次都选取当前的一个最优解**

    * 对照上面的算法，第一步为什么选 5 分而不选 2 分、1 分？因为在第一步这个位置上选 5 分硬币数肯定最少，属于当前的一个最优解。

    * 第三次循环之后第四次为什么不再选 5 分？因为再选就是 15+5=20，超过总金额 18，肯定不行；于是退而求其次选 2 分，而不选 1 分——在第四步这个情况下选 2 分硬币数肯定比选 1 分更少。

* **原则二：向前看，别回头**

    * 前面已经选中了三个 5 分，接下来只跟剩下的 2 分、1 分做组合；不会为了找出所有可能再退回去，比如选两个 5 分再跟 2 分、1 分组合。

    * 这三个 5 分一旦选定就不会再动、不会倒回去。

    * > **定义**：贪心只顾眼前，之前选中的结果就算定下来了不会再变；你要是能倒回去，那就不叫贪心了。

    * ⚠️ **易错点**：「向前看别回头」这条原则会让贪心解法**有可能得到错误的解**。

### 原则二翻车的两组数据

* **15、10、1 凑 21：凑出七个硬币**

    * 按贪心先拿最大的 15 分，剩余 6；6-10 显然是负数，10 分用不上，于是去凑 1 分，六个 1 分凑成 6，剩余归零，共 6+1 = **七个**硬币。

    * 但最优解是两个 10 分加一个 1 分，20+1=21，只需要**三个**硬币；没倒回去，结果比最优解差很多。

* **15、10 凑 20：直接无解**

    * 按贪心先准备一个 15 分，剩余 20-15 是 5；因为不能回头，这个 15 分就定下来了，在此基础上 10 分凑不足剩下的 5。

    * 于是贪心把它判成**无解**，但实际有解：如果能把这个 15 倒回去、不用它，两个 10 分就直接凑出 20。

    * 上一组是没倒回去得到更差的解，这一组是没倒回去直接变成无解；若能倒回去从 10 开始凑，就能得到更少的硬币数。

* **现实中的货币系统**

    * 不必太过担心：正常的货币系统不会设计出 15、10、1 这种面值，肯定是更合理的 5、2、1 这类面值，各国实际货币系统中应该不存在，这是贪心算法本身的问题。

## 贪心解法的代码结构

* **两个准备变量**

    * `reminder` 代表剩余金额，初始值是 `amount`。

    * `count` 代表最后的硬币数目，初始值是 0。

* **降序 for 循环**

    * 对 `coins` 数组做循环，**由大到小**按面值依次处理；假定传入的数组已经按由大到小排好序，代码里不自己降序排序，因为 Java 里基本类型 int 数组做降序排序比较麻烦。

    * 最优解实际上就是找到面值最大的那枚硬币，用剩余金额减掉它，这一轮凑出的硬币数肯定最少。

    * 循环内只要剩余金额大于这个硬币，就减掉它、硬币计数加一。

* **把 if 改成 while**

    * 如果每次只处理一枚硬币，第二次循环 `coin` 就变成 2 了；希望先把所有 5 尽可能处理完再处理面值 2，所以把那个 `if` 改成一个 `while` 循环。

```java
static int coinChange(int amount, int[] coins) {
    int reminder = amount;   // 剩余金额
    int count = 0;           // 硬币总数
    for (int coin : coins) { // 假定 coins 已按面值由大到小排好序
        while (reminder > coin) {
            reminder -= coin;
            count++;
        }
        if (reminder == coin) {  // 查漏补缺：正好被当前硬币凑足
            reminder = 0;
            count++;
            break;                // 找到解，直接退出外层 for
        }
    }
    return reminder > 0 ? -1 : count;
}
```

### 查漏补缺的 if

* **为什么必须有它**

    * 比较条件故意写成大于号，所以总金额 15 时：15 大于 5 进 while 减成 10、`count` 变 1；10 仍大于 5 再进 while 减成 5、`count` 变 2；第三次剩余金额是 5，5 大于硬币 5 不成立，不再进 while。

    * 没进 while 就走外层循环，下一次处理的是 2 分，这就不对了——因为再循环一次到第三个 5 分硬币时 15 正好凑足。

* **if 的判定与动作**

    * 在 while 结束后判断剩余金额是不是正好能被当前硬币凑足，两者相等就表示正好凑足。

    * 凑足后把剩余金额更新成零，`count` 也加一；找到解就不需要再处理面值更小的 2 分，所以直接 `break` 退出外层 for。

* **为什么不写在 while 里面**

    * 在 while 里发现 `reminder` 被减成零同样算找到解，找到解希望退出循环，但此时写 `break` 退出的是 while 循环，并不能退出最外层的 for 循环。

    * 要跳出外层就得写一个比较难看的跳出语句，所以采用折中办法：把代码分成 while 循环和收底的这个 `if` 判断两部分。

### 退出外层循环后的两种情形

* **reminder 大于零**

    * 无论是从 `if` 里 break 退出还是从 `for` 自然退出，只要 `reminder` 大于零就说明没凑够，返回 `-1`。

* **reminder 等于零**

    * 说明凑够了，返回 `count`，因为 `count` 就是硬币数。

### 18 的完整执行流程

* 第一次处理最大面值 5：18 大于 5，进 while 做减法更新成 13，`count` 加一变 1。

* 第二次：13 再减 5 变成 8，`count` 更新成二。

* 第三次：8 再减 5 变成 3，`count` 更新成三，找到了三个 5 分硬币。

* 第四次：3 小于 5，条件不成立，while 不执行；再看 `if`，3 并不等于 5，所以继续尝试面值更小的硬币，再进外层循环处理面值 2。

* `reminder` 是 3，3 大于 2 成立，进 while 减成剩余 1，`count` 更新成四；1 不大于 2，while 不再执行，且 1 也不等于 2，没找到解，再进外层循环去尝试面值 1。

* 最后一次：1 不大于 1，没进 while，但收尾的 `if` 里剩余金额 1 == 1 成立，说明找到解，把 `reminder` 更新成零，`count` 加加变成五。

* 然后 `break` 退出外层 for，执行最后判断：`reminder` 等于零说明找到解，返回 `count`，最终最少硬币数是五个。

## 编码与编码表

### 编码的本质

* **编码（Encoding）**

    * > **定义**：建立**字符和数字的一个对应关系**；计算机里并不能直接存储字符，往计算机里存字符其实都是存一个数字。

* **ASCII 编码表**

    * 它建立了常见英文字符（包括一些英文符号）跟数字的对应关系。

    * 大写字符 A 对应的 16 进制数字是 41（横轴是 4，纵轴是 1，加起来就是 41）；大写字符 B 对应 42。

    * 存储时实际存的就是 42；读取时读到一个 42 就再查这张表，42 原来对应大写 B，就把它显示出来。

### 十个字符二十字节

* **每个字符固定两个字节**

    * Java 中用 `char` 类型代表一个字符，每个字符固定占两个字节。

    * 按前表查：这里大写 A 对应的 16 进制数字是 61（横轴 6，纵轴 1），但 Java 中这个 61 前面还得带一个 00，即 `0061`——00 占一个字节、61 占一个字节。

    * 类似的，两个 B 用两个 `0062`，七个 C 用七个 `0063`。

* **传输体积与效率**

    * 传输一个 A、两个 B、七个 C 这十个字符，每个字符两个字节，共 **20 个字节**。

    * 这显然不经济，占用字节数太多，接下来要想想有没有办法采用别的编码表让传输字节数更少、更节省流量。

## 编码冲突与解码

### 手工二进制编码表省了字节却解不出来

* **手工设计一张表**

    * 假设传输的字符种类只有 A、B、C 三种，重新设计一张二进制编码表：A 用一个比特位 0 表示，B 用 1，C 用二进制的 10。

    * 一个比特就能表示一个字符，C 也只用了两个比特。

* **省下来的体积**

    * 传一个 A、两个 B、七个 C 共十个字符：一个 A 是 0、两个 B 是两个 1，前面一共 3 个比特；后面七个 C 是七个 `10`，即 14 个比特，14 + 3 = **17 个比特**。

    * 17 个比特就是两个字节多一点，相比原来的 20 个字节缩小了约十倍。

* **为什么解不出来**

    * 不光要考虑编码，还得考虑**解码**——要把数字序列还原成原来的字符。

    * 前三个字符没问题：第一个 0 还原成 A，接着一个 1 还原成 B，再一个 1 还原成 B。

    * 接下来它遇到 1 不会聪明地把 `10` 连在一起看，遇到 1 就翻译成 B，再遇到 0 又翻译成 A，本该译成 C 的 `10` 被错译成 `ba`，全部译完得到七个 `ba`，而要的是七个 C。

    * > **结论**：问题的本质在于要让计算机翻译时能把编码后的数字区分开，让它们互不冲突、互不干扰。

### 用二叉树编码保证前缀不重复

* **满二叉树（Full Binary Tree）**

    * > **定义**：每个节点的左右孩子都存在，不存在「只有一个孩子」这种情况；叶子节点可以没有孩子。

```text
          o
        /   \
       o     o
      / \   / \
     o   o o   o     <-- 叶子节点可以没有孩子
```

* **编解码规则**

    * 用二叉树结构来编码可以保证前缀不重复，也就是编码后的数字不冲突。

    * 规则是：**向左走取一个数字 0，向右走取一个数字 1**；走到叶子节点时，路径上累计起来的 0 和 1 加在一起就是这个字符的二进制编码，每个叶子节点存储着一个字符。

* **三个字符的编码**

    * 找 A 的编码：只向左走一步就走到 A，这一步取到的数字是 0，所以 A 的编码是 0。

    * 找 B 的编码：向右走一步、再向左走一步找到 B，路径中数字累计起来是 `10`，所以 B 的编码是 `10`。

    * C 的编码则是 `11`，对应到树上就是这个结构，最终不会冲突、将来能正确解码。

```text
            o
          /   \
         o     o
        / \     \
       a   b     c

    a = 0
    b = 10
    c = 11
```

* **按这棵树重新编码**

    * 一个 A 编成一个 0，两个 B 编成两个 `10`，七个 C 编成七个 `11`，共 1 + 4 + 14 = **19 个比特**，也是两个字节多一点。

    * 解码过程：先遇到的 0 没有歧义，只能译成 A；再遇到一个 1，编码表中没有单独的 `1`（只走一个 1 没走到叶子），得接着往后走，找到 0 时 `10` 走到头，译成 B；接下来又一个 `10` 译成 B；后续的 `11` 都走到头，译成 C——这回解码确实没有问题了。

## 哈夫曼树

### 19 比特能解码但仍不够短

* **频次最高的字符不该编得最长**

    * C 的出现频次最高，出现七次，而 A 只出现一次；把 C 编成 0 只需七个比特，编成 `11` 却要占十四个比特。

    * 所以把那些出现频次高的字符编码成更短的数字才划算。

### 频次高的走左边

* **调整后的树**

    * 这棵树里频次高的字符数字更少、频次低的数字更多：A、B 都需要两个数字，而频次最高的 C 只需一个数字。

```text
            o
          /   \
         o     c
        / \
       a   b

    a = 00
    b = 01
    c = 1
```

* **重新编码后的体积**

    * 用 `00` 表示 A、`01` 表示 B、最后一个 `1` 表示 C：那十个字符编码成 A 的 `00`、两个 B 的 `0101`（共 6 个比特）、七个 C 的七个 `1`（共 7 个比特）。

    * 总共只有 **13 个比特**，比之前的 19 个比特少多了，就是一个字节多一点、不到两个字节。

### 哈夫曼树与哈夫曼编解码

* **哈夫曼树（Huffman Tree）**

    * 上面这种最好的解法所对应的树称为哈夫曼树（也叫霍夫曼树）；用它对字符和数字进行编解码，就称之为哈夫曼编解码，这就是哈夫曼的由来。

    * > **定义**：整条思路就是让出现频次越高的字符在树上的位置越靠近根、编码就越短；所有字符的编码总长度就是所有叶子的深度之和，让重的叶子浅一点、轻的叶子深一点，总长度才会最小。

    * 演进路径：20 字节 → 17 比特（手工表，解不出来）→ 19 比特（树，解得对但不是最优）→ 13 比特（哈夫曼树），就是不断往这个方向逼近的过程。
