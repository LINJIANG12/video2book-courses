# 基础算法-186-哈希算法-Object.has

哈希码不是调用方给的，而是由哈希算法从 key 自己算出来的；key 怎么生成哈希码，决定了它在哈希表里落在哪个下标上。

## 哈希码的生成方

### Object 的哈希码

* **Object.hashCode()**

    * > **定义**：`Object` 是所有对象的共同父类，它提供的 `hashCode()` 方法产生一个随机数，这个随机数就作为该对象的哈希码。

    * 返回值类型是 `int`。
    * 循环创建 10 个 `Object` 并打印 `hashCode()`，得到 10 个互不相同的整数，说明它本质上就是个随机数。
    * 同一个对象多次调用 `hashCode()`，打印结果完全一样。
    * 随机数在一定程度上避免哈希码冲突，使每个对象拥有一个自己的、能代表这个对象的数字。
    * > **结论**：不同对象的哈希值不一样，同一个对象的哈希值一样，所以哈希值确实能代表这个对象，具备这个对象的一些特征。
    * > **提示**：随机数只保证"不同对象大概率不同"，它并不关心对象的内容。

### 哈希方法（hash）

* **哈希方法（hash）**

    * > **定义**：把"由 key 算出哈希码"这一行重复代码从 `get`、`put`、`remove` 中抽出来的私有方法，方法体只做一件事——返回 `k.hashCode()`。

    * 改造前的 `get`、`put`、`remove` 都要额外传一个哈希码参数，调用方凭什么要自己算，这个设计太丑。
    * 改造后：`get` 只要一个 `k`；`put` 去掉哈希码，只留 `k` 和 `value`；`remove` 只留一个 `key`。
    * `get`、`put`、`remove` 内部出现的是完全相同的一行，所以可以抽成一个哈希方法。
    * 抽出来之后，将来要换别的取哈希值办法，只改这一处即可。

```java
public V get(K k) {
    return get(k, hash(k));
}

public void put(K k, V value) {
    put(k, value, hash(k));
}

public void remove(K k) {
    remove(k, hash(k));
}

private int hash(K k) {
    return k.hashCode();
}
```

## 为什么不直接用 Object 的哈希码

* **取值相同的字符串应当哈希码相同**

    * 两个字符串对象取值都是 `abc`，只是各自用 `new` 造出来，属于两个不同的对象。
    * 若用 `Object` 父类的 `hashCode()`，对象不同哈希码就必然不同，放进哈希表大概率落在不同索引。
    * 实测打印两个对象的 `hashCode()`，结果一样，都是 `96354`，说明它并没有走 `Object` 父类的随机数实现。
    * 这样才能做到：只要值相同，就能用其中一个字符串找到另一个相同取值的字符串。
    * 结论是 `String` 这个类型已经重写了 `hashCode()`，覆盖了 `Object` 父类的实现。

## 字符串哈希码的设计原则

* **原则一：取值相同，哈希码必须一样**

    * 两个取值都是 `abc` 的字符串对象，生成的哈希码也必须相同。

* **原则二：值不同，尽量生成不同哈希码**

    * 例如一个 `abc`、一个 `df`，生成的哈希码应该不一样。
    * > **注意**：不能百分之百保证哈希码不冲突，所以只能说尽量满足这一点。

* **字符的数值表示**

    * 字符串由一个个字符组成，每个字符在计算机里又能表示成一个数字，可以利用这些数字组合出哈希码。
    * `a`、`b`、`c` 对应的数字分别是 `97`、`98`、`99`。

## 字符串哈希算法

### 直接累加会冲突

* **字符值直接累加**

    * 做法：哈希码初始值为 0，循环中把每个字符累加进去。
    * `abc` 累加得 $97 + 98 + 99 = 294$，就拿 294 当哈希码。
    * > **易错点** ⚠️：直接累加会把字符顺序的信息丢掉，`bac` 的 `98 + 97 + 99` 同样是 294，与 `abc` 撞在一起，两个值不同的字符串算出了同一个哈希码。

### 不同位乘不同权重

* **逐位加权累加（hash = hash * 10 + c）**

    * 思想：让不同位置上的字符乘以不同权重——最高位乘 100、中间位乘 10、最低位乘 1，再累加，位置就被区分开了。
    * 代码实现就是把累加改成"上一次的哈希值乘以十，再加上本次循环的字符"。
    * 展开后等价于最高位乘 $10^2$、次高位乘 $10^1$、最低位乘 $10^0$。

```java
int hash = 0;
for (int i = 0; i < s1.length(); i++) {
    hash = hash * 10 + s1.charAt(i);
}
```

```text
第 1 次循环：hash = 0 * 10 + 'a'      = 97
第 2 次循环：hash = 97 * 10 + 'b'     = 1068
第 3 次循环：hash = 1068 * 10 + 'c'   = 10779

把第 3 次的整个式子展开：

    hash = ((0 * 10 + 'a') * 10 + 'b') * 10 + 'c'
         = 'a' * 10²  +  'b' * 10  +  'c'
         = 97 * 100  +  98 * 10   +  99
         = 10779
```

    * 实测 `abc` 得到 `10779`，`bac` 得到 `10869`，两个字符串被区分开。
    * 结论：把不同位的字符乘以不同权重再累加，比直接累加的哈希分布性更好。

### 把 10 换成 31

* **质数权重 31**

    * 为了错开每一位，需要乘一个数；经验表明乘一个比较大的质数效果更好，可以让哈希冲突的机会更低。
    * 把乘数从 10 换成质数 31，即 $hash = hash \times 31 + c$，其中 $c$ 是当前字符转成的数字。

```java
int hash = 0;
for (int i = 0; i < s1.length(); i++) {
    hash = hash * 31 + s1.charAt(i);
}
```

    * 用 31 算出的 `abc` 哈希值是 `96354`，与直接调用字符串 `hashCode()` 返回的 `96354` 完全一致。
    * 再验证 `bac`：`hashCode()` 是 `97284`，按该算法算出来也是 `97284`。
    * > **结论**：`String.hashCode()` 的核心公式就是 $hash = hash \times 31 + c$。

### 位运算优化

* **把乘 31 拆成左移与减法**

    * 乘 31 等价于乘 32 再减去自身：`hash * 31` 就是 `hash * 32 - hash`。
    * 32 是 2 的 5 次方，乘以 32 可以优化成左移 5 位。
    * > **易错点**：必须先加括号让左移与减法整体生效，否则运算优先级一变，结果就不再等于乘 31。

```java
int hash = 0;
for (int i = 0; i < s1.length(); i++) {
    hash = (hash << 5) - hash;   // 相当于 hash * 31
    hash += s1.charAt(i);
}
```

    * 改写后 `bac` 仍算得 `97284`，与改之前完全一致，但位运算比乘法效率更高。

## 冲突分布的实测

### 统计链表长度

* **print 方法**

    * > **定义**：遍历哈希表的 `table` 数组，取出每个下标上的链表头，沿 `p = p.next` 走到 `null`，走过几格就把计数器 `sum` 加几，得到该下标处链表的长度。
    * `sum` 写在循环内，每循环一次只统计一条链表的长度。
    * 用一个长度为 `table.length` 的 `int` 数组 `sums` 保存结果，每个下标记录该处链表的长度。

```java
public void print() {
    int[] sums = new int[table.length];
    for (int i = 0; i < table.length; i++) {
        TableNode<K, V> p = table[i];
        int sum = 0;
        while (p != null) {
            sum++;
            p = p.next;
        }
        sums[i] = sum;
    }
    System.out.println(Arrays.toString(sums));
}
```

### 分组后数个数

* **链表长度的分布统计**

    * 判定标准：链表长度普遍较短说明冲突少、算法好；链表太长说明哈希值集中冲突、算法不好。
    * 数组太长时逐个打印太吵，改为分组：先 `stream()` 转成流，再 `boxed()` 把基本类型转成包装类型的流。
    * 分组用 `Collectors.groupingBy(e -> e, ...)` 按元素取值分组，同一个 0 一组、同一个 1 一组。
    * 统计组内个数用 `Collectors.counting()`，结果是 `map`，key 是被分组的值（0、1、2…），value 是每组的个数。

```java
Arrays.stream(sums)
      .boxed()
      .collect(Collectors.groupingBy(e -> e, Collectors.counting()))
      .forEach((len, cnt) -> System.out.println(len + " -> " + cnt));
```

    * 扩到 20 万个后按下表分组统计。

* **234937 个单词入表**

    * 用 `Files.readAllLines(Paths.get("words"))` 读进内存，返回一个 `List<String>`，逐个 `put(word, word)` 入表。
    * `value` 不重要，主要看 `key`，因为哈希码都来自 `key` 的 `hashCode`。

## MurmurHash

### 三个特点与代际

* **MurmurHash**

    * 相对其他哈希函数的三个特点：计算速度快、碰撞率低、随机性好。
    * 碰撞率低到什么程度：处理一个数据只有两个冲突。
    * 属于第二代哈希算法，第一代是 MD5 这一类。

### 在 Guava 中的用法

* **Hashing.murmur3_32()**

    * 依赖谷歌的 Guava 开发包，由它提供 `Hashing` 工具类，支持多种哈希算法。
    * 方法名要拆开看：`murmur3` 是哈希算法的版本，后面的 `32` 指输出值占 32 位，也就是 4 个字节；它还支持 128 位输出。
    * 生成的是 32 位哈希码，正好可以用一个 `int` 整数表示。

```xml
<dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
    <version>${guava.version}</version>
</dependency>
```

```java
int hash = Hashing.murmur3_32()
        .hashString("abc", StandardCharsets.UTF_8)
        .asInt();
```

* **hash 相关方法**

    * `hashInt`、`hashString` 等一系列方法接受不同输入：可对整数做哈希、对 `CharSequence` 字符串做哈希、对 `byte` 数组做哈希等。
    * 对字符串做哈希时还要告诉它字符编码，这里用 `StandardCharsets` 的 UTF_8。

* **替换 hash 方法**

    * > **定义**：在哈希方法里先判断 key 的类型，是 `String` 就改用 Murmur 算法生成哈希码，其他类型仍走 JDK 自带的 `hashCode`。

```java
private int hash(K k) {
    int hash;
    if (k instanceof String) {
        hash = Hashing.murmur3_32()
                .hashString((String) k, StandardCharsets.UTF_8)
                .asInt();
    } else {
        hash = k.hashCode();
    }
    return hash;
}
```

### 与 String.hashCode 的实测对比

* **同一份 20 多万单词的数据**

    * 改成 Murmur 之后只改 `hash` 方法一处，其他地方不动，仍读那 20 多万个单词看分布。
    * 两种算法结果非常接近，说明 Murmur 哈希的分散性与 JDK 字符串哈希处在同一水平。

| :--- | ---: | ---: |

## 哈希表设计的追问

### 冲突后头插还是尾插

* **尾插法（本文实现）**

    * 发现插入位置没有空位就沿链表查找，走到 `next` 等于 `null` 的尾部，把新节点挂上去。

    ```text
    尾插： 沿链表一路走到 next == null，再把新节点挂上去
           while (p.next != null) p = p.next;
           p.next = newNode;

    头插：  新节点直接抢在链表头的位置
           newNode.next = table[index];
           table[index] = newNode;
    ```

* **头插法（JDK 的用法）**

    * JDK 的 `Hashtable` 内部加入新元素时用的就是头插法。
    * JDK 的 `HashMap` 最早版本以及 1.7 之前也都是头插法，1.8 以后改成了尾插法。
    * 头插尾插本身并无区别。
    * > **易错点** ⚠️：头插法在多线程下会带来死循环问题，这正是 `HashMap` 从 1.8 起改为尾插法的原因。

### 为什么高位与低位要异或

* **直接用 hashCode 求索引的冲突**

    * 自己实现的哈希表直接用 `key.hashCode()`，没做高低位异或。
    * 往表里放 `2` 和 `524290`，16 个格子有 15 个是空的，只有 1 个不空，且该链表长度为 2，说明二者冲突了。
    * 原因是初始数组长度只有 16，索引 = hash % 16 等价于取二进制低 4 位，而这两个数的低 4 位都是 `0010`。

    ```text
      hashCode = 2                     hashCode = 524290
      二进制:  0b...0010                二进制:  0b1000_0000_0000_0000_0010
                        ↓ 索引 = hash % 16，等价于取低 4 位
      低 4 位: 0010                      低 4 位: 0010
      索引:    2                         索引:    2        ← 撞了！
    ```

* **异或把高位折回低位**

    * 按位异或的规则：`0 ^ 0 = 0`、`1 ^ 1 = 0`，相同得 0、不同得 1。
    * `524290 >>> 16 = 0b1000 = 8`，与自身异或得 `524298`，再 `& 15` 得索引 `10`；`2 >>> 16 = 0`，异或后仍为 2，索引仍是 2，两者就此分开。
    * 做法是拿到原始哈希值后不急着返回，先跟它的高 16 位异或再返回。
    * 改完之后长度为 2 的链表没有了，变成两条长度为 1 的链表。

    ```text
      2        >>> 16 = 0
          2      ^  0                   =  2        →  & 15 =  2   （索引 2）

      524290   >>> 16 = 0b1000 = 8
          524290  ^  8                   =  524298   →  & 15 = 10   （索引 10）
    ```

```java
private int hash(K k) {
    int hash = k.hashCode();
    return hash ^ (hash >>> 16);
}
```

    * `524290` 中被丢掉的第 19 位，通过异或被"折"到低位，第 0 位与第 4 位综合起来，最终结果不再是索引 2。
    * > **注意**：高低位异或有前提——表格容量是 2 的 n 次方时才做这个运算；如果不用"容量是 2 的 n 次方"策略，这个操作可以不做。

### 容量一定要是 2 的 n 次方吗

* **容量为 2 的 n 次方的三项优化**

    * 自己实现的哈希表和 JDK 的 `HashMap` 都有这个前提，数组长度必须是 2 的 n 次方；即使初始化容量不是 2 的 n 次方，也会取最接近的那个数作为容量。
    * 按位与运算：用它算索引正是基于 2 的 n 次方，脱离这个前提就不能这么算。
    * 扩容时拆分链表：把一条链表一分为二的算法也以容量是 2 的 n 次方为前提。
    * 高低位异或：因为有了容量是 2 的 n 次方这个前提，才需要把对象哈希码的高低位做异或来减少冲突。

* **质数容量是另一个选项**

    * 先例是 JDK 的 `Hashtable`，初始容量是 11，一个质数，没有用 2 的 n 次方。
    * 质数算余数时数据分布性、哈希分布性比较好；2 的 n 次方求余数分布性不好，从二进制角度看高位都用不上，所以才要靠高低位异或减少冲突。
    * JDK 在哈希分散性与运算效率之间求平衡：2 的 n 次方能用按位与让求余数效率高，但分散性差；质数必须用求模求余数，效率不高，但分散性好。
    * 结论：非要用 2 的 n 次方作为表格容量并不是规定，这是一个选择题。

### 链表超过 8 转红黑树

* **红黑树化**

    * JDK 的 `HashMap` 从 1.8 开始，链表长度超过 8 时转换成红黑树。
    * 正常分散的数据不会出现这么长的链表：20 多万个单词放进去，最长的只有 6，且长度 6 的就一两个。
    * 这个操作主要是防患于未然：有人专门造相互冲突的哈希数据来攻击，一旦冲突就会形成非常长的链表，使整个服务器性能下降。
    * > **结论**：正常数据一般到 6 就头了，**长度超过 8 的基本都是恶意的**；红黑树是给极端情况兜底的，不是日常性能优化。
