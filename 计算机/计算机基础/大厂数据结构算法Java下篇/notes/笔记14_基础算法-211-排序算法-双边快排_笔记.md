# 基础算法-211-排序算法-双边快排

## 双边循环分区

* **双边循环**

    * > **定义**：`i` 从左向右寻找比基准点大的元素，`j` 从右向左寻找比基准点小的元素，两个指针一头一尾往中间收缩。

    * 与单边循环的差别只在于把 `j` 的扫描方向拧了过来，`i` 的方向保持不变。

    * 方向变了，基准点的位置也跟着换：单边循环取**最右侧**元素，双边循环取**最左侧**元素。

    * 判断条件与最后的交换动作跟单边循环基本相同，所以只需重写 `partition`。

    ```text
    单边循环：i 和 j 同向             双边循环：i 和 j 相向
      i -> -> ->                       i -> -> ->
      j -> -> ->                      <- <- <- j
    ```

* **指针分工对照**

    | 对照项 | 单边循环 | 双边循环 |
    | :--- | :--- | :--- |
    | `i` 方向 | 从左向右 | 从左向右 |
    | `i` 寻找目标 | 比基准点大的 | 比基准点大的 |
    | `j` 方向 | 从左向右 | 从右向左 |
    | `j` 寻找目标 | 比基准点小的 | 比基准点小的 |
    | 基准点取哪端 | 最右侧元素 | 最左侧元素 |

## 一轮分区的推进顺序

* **分区走查**（示例数组 `4 3 7 2 1 5 6`，`pv = a[left] = 4`）

    ```text
       下标     0    1    2    3    4    5    6
       元素     4    3    7    2    1    5    6
       指针     i                             j
                ^                             ^
    ```

    * 第一步先看 `j`：从最右端往左走，遇到 6、5 都不比 4 小，继续减；走到 1，`1 < 4`，停。

    * 第二步再看 `i`：往右加加，遇到 3 不比 4 大，继续加；遇到 7，`7 > 4`，停。

    * 第三步交换：把找到的大元素与小元素对调，7 与 1 换位。

    ```text
       下标     0    1    2    3    4    5    6
       元素     4    3    1    2    7    5    6
       指针             i           j
                          ^           ^
    ```

    * 第四步各退回一格：`i` 停在 1 上方、`j` 停在 7 上方，两个指针继续相向而行。

    * 第五步 `j` 继续往左一步遇到 2（`2 < 4`）停下，`i` 往右一步撞上 `j`，此时 `i == j`，说明两边都搜过一遍，外层循环结束。

    * 第六步收尾：把基准点元素与 `i` 索引的位置交换；与 `j` 交换也行，反正此刻它俩相等。

    ```text
       下标     0    1    2    3    4    5    6
       元素     2    3    1    4    7    5    6
                           ^
    ```

    * 分区完成后基准点 4 落在正中间，左边 3 个数全比它小、右边 3 个数全比它大，这一轮分区分得干干净净。

    * 剩下的工作是对左边 `[2, 3, 1]` 和右边 `[7, 5, 6]` 各重复一遍同样的分区。

## partition 实现骨架

* **双边循环分区方法**

    ```java
    public static int partition(int[] a, int left, int right) {
        // 基准点：取最左侧元素的值
        int pv = a[left];

        // i 从左往右找比 pv 大的，j 从右往左找比 pv 小的
        int i = left;
        int j = right;

        while (i < j) {
            // ① j 停在「比 pv 小」的位置上
            while (i < j && a[j] > pv) {
                j--;
            }

            // ② i 停在「比 pv 大」的位置上
            while (i < j && a[i] <= pv) {
                i++;
            }

            // ③ 你找到小的了、我找到大的了，交换
            if (i < j) {
                swap(a, i, j);
            }
        }

        // ④ 写在循环外：基准点跟 a[i] 交换归位
        swap(a, left, i);
        return i;
    }
    ```

    * ① 号内层循环：`a[j] > pv` 说明还没找到小的，`j` 继续减；一旦 `a[j] <= pv` 就退出来停在小元素位置上。

    * ① 号循环没有等于号，所以**等于**基准点的元素也会让 `j` 停下，这个细节在处理重复元素时还要再用一次。

    * ② 号内层循环与它对称：`a[i] <= pv` 说明还没找到大的，`i` 继续加，遇到真正比基准点大的才停。

    * ③ 号在两个内层循环都退出后执行，此时 `j` 停在小元素、`i` 停在大元素，`swap` 一换本轮就完成了。

    * ④ 号必须写在循环外：外层退出时 `i` 和 `j` 已经碰头，这一行把基准点送到最终位置。

    * 返回值 `i` 就是基准点排好序之后的索引，外层递归直接拿它去切分左右两段。

## 内层边界与执行顺序

* **内层循环必须附带 `i < j`**

    * 光写元素大小判断是不够的，两个内层循环都要跟外层的 `i < j` 同时成立。

    * 不加的后果：`j` 已经停在小元素上时，`i` 若继续加加，会越过 `j` 跑到错误的范围外面去。

    * > **易错点**：内外三层的边界条件是一套的，任何一层漏写 `i < j`，指针就会跑飞；这类 bug 在测试数据“刚好有序”或“刚好有序的逆序”时才暴露。

* **两个 while 的先后顺序不可调**

    * 故意改成先写 `i` 再写 `j`，第一轮的结果与正确顺序一模一样，表面上看起来好像没问题。

    * 第二轮 `i` 继续往右找大的、跨过 `j` 停在一个大的元素上，`j` 往左找小的停在小元素上，两个指针错开退出。

    * 问题出在收尾：正确写法换的是 `i`，可这一轮 `i` 已跑到 `j` 右边，指向的可是**一个比基准点大的元素**。

    ```text
       下标     0    1    2    3    4    5    6
       元素     7    3    1    2    4    5    6
    ```

    * 结果是一个 7 被换到基准点 4 的左边、基准点右边反而空了，分区直接作废。

    * 真要调整顺序，基准点的选择以及大于小于的判断都得跟着重新变一遍。

    * > **注意**：这段代码的每一步顺序都是配套的，写排序代码时调整顺序等于重写算法，不要轻易去“优化”它。

## 基准点随机化

* **固定基准点在降序数据上的失效**

    * 反例数组 `8 7 6 5 4 3 2 1`，基准点取最左侧的 8。

    * `j` 从右往左找比 8 小的，第一个 1 就符合并停下；`i` 从左往右找比 8 大的，7、6、5、4、3、2、1 全都比 8 小，找不到，一路走到头遇到 `j` 才停。

    * 把 `a[i]` 与基准点交换后，一轮分区完成——分区结果**没有错**，基准点 8 确实被送到了它该在的位置。

    * 但分区效果极其糟糕：理想情况是把它一分为二，现在左边是 n-1 个数据、右边一个没有，两个分区极端不平衡。

    * 后果立竿见影：接下来两次递归，一次没数据要处理，另一次处理的数据只比上次少了 1 个，效率被拖垮。

    * > **注意**：平均情况下快速排序是 $O(n \ln n)$；一旦分区极端不平衡，它就会退化成 $O(n^2)$。

    * 这种最糟情况总共得花 **36 帧**才能把序排好。

* **理想切分的表现**

    * 理想情况是基准点选的值**恰好能把数据一分为二**。

    * 最初那个数组最左侧的 4，比它大的有三个、比它小的也有三个，一轮分区之后正好落在中间，左一半、右一半。

    * 接下来的递归同样顺：左边分区里最左侧的 2 恰好又是这堆数据的中间值，右边分区里最左侧的 7 同样一分为二。

    * 整个过程只花 **23 帧**，而且只确定了 4、2、7 这三个基准点，剩下的自然就分好了。

    * 图里标成黑色的值（曾经的基准点）在最糟那组明显经过了更多步骤才逐个确定下来。

* **随机挑一个基准点**

    * 理想情况要求基准点恰好落在中间值上，这在真实数据里挺难保证；但也不能让它变得更糟，万一挑中最大值或最小值就彻底崩了。

    * 妥协做法是**随机选一个元素当基准点**，在这么多数据里挑到最大值或最小值的概率相对小多了。

    * 改动共三步：在当前 `[left, right]` 范围内随机找一个元素；把它跟最左侧元素交换；剩下的代码**一行都不用改**，仍按“最左侧元素是基准点”往下走。

    * 效果不是每次都能最优，而是不会被一条特定数据稳定 KO。

## 区间内随机下标的取法

* **ThreadLocalRandom**

    * 先取实例：`ThreadLocalRandom random = ThreadLocalRandom.current();`

    * `nextInt(n)` 传一个数 `n`、返回 `[0, n)` 里的随机整数，比如传 `10` 拿到的就是 0 到 9。

    * > **提示**：`nextInt(bound)` 是**左闭右开**的，`bound` 本身取不到，所以不能直接 `nextInt(right)`，那样随机数会跑出当前分区的范围。

    * 正确做法是两步：先按“当前区间内的元素个数”取，再加上左边界。

    ```java
    int count = right - left + 1;              // 当前区间内的元素个数
    int index = random.nextInt(count) + left;  // [left, right] 内的随机下标
    swap(a, index, left);                      // 随机元素换到最左侧
    int pv = a[left];                          // 后面照旧当基准点用
    ```

    * 验证：右半段 `[7, 5, 6]` 的 `left = 4`、`right = 6`，元素个数是 `6 - 4 + 1 = 3`。

    * `nextInt(3)` 返回的是 `[0, 3)`，也就是 0 到 2；再加上左边界 4，范围就变成了 4 到 6，正好是想要的区间。

## 重复元素导致的分区失衡

* **全相等数组下的失衡**

    * 前面的代码里藏着一个不对称细节：`j` 的判断是 `a[j] > pv` 才继续走，所以 `j` **遇到等于基准点的元素会停下来**。

    * `i` 的判断是 `a[i] <= pv` 才继续走，所以 `i` **遇到等于基准点的元素不会停**，会一直往右走。

    * 跑全相等数组 `4 4 4 4 4 4`：基准点是最左侧的 4，`j` 一上来就找到一个等于的停下，`i` 继续往右找大的，一直找到与 `j` 相遇，本轮分区结束。

    * 把 `a[i]` 与基准点交换后，分区又是**极度不平衡**：基准点左边一大堆，右边是空的。

    * 重复元素一样会把分区搞崩，性能肯定受影响。

* **随机化救不了这一类**

    * 随机抽到的元素彼此一样，抽到一个“一样的”仍然解决不了问题。

    * 因此得单独针对重复元素再改一版算法。

## 重复元素优化版 partition

* **三处改动**

    ```java
    public static int partition(int[] a, int left, int right) {
        int pv = a[left];

        int i = left + 1;   // i 从 left + 1 出发，left 上放的是基准点
        int j = right;      // j 仍然从 right 出发，两边向中间收拢

        while (i <= j) {                       // 注意：是 <=
            // i 找「大于等于 pv」的，遇到相等的也停
            while (i <= j && a[i] < pv) {
                i++;
            }
            // j 找「小于等于 pv」的，遇到相等的也停
            while (i <= j && a[j] > pv) {
                j--;
            }

            // 交换前先判一下
            if (i <= j) {
                swap(a, i, j);
                i++;
                j--;
            }
        }

        swap(a, left, j);                      // 收尾只能跟 j 换
        return j;
    }
    ```

    * 起点变了：`i` 从 `left + 1` 开始，因为 `left` 上放的是基准点、不能让它乱跑；`j` 还是从 `right` 开始，依旧从两边往中间收拢，基准点仍取最左侧。

    * 遇到相等也停：以前 `j` 遇相等会停、`i` 遇相等不停，这回两边遇到相等**都停**，停下来照旧交换，然后 `i++`、`j--` 往下走。

    * 交换包一层判断：`if (i <= j)` 为真才换。

* **走查示例**（数组 `4 3 7 2 1 5 6`）

    ```text
       下标     0    1    2    3    4    5    6
       元素     4    3    7    2    1    5    6
       指针             i           j
                          ^           ^
    ```

    * `i` 从下标 1 出发找大于等于 4 的，遇到 3 不满足继续右移，停在 7 上方。

    * `j` 从下标 6 出发找小于等于 4 的，1 满足，停在 1 上方。

    * 两者交换，然后各自进一格，继续下一轮比较。

* **相等元素也交换的意义**

    * 意义在于最终分区的结果：基准点恰好落在**正中间**，相等的那些数据被**左右各分了一半**，分区就不再不平衡。

    * 全相等数组 `4 4 4 4 4 4` 的基准点 4 落位在正中间，左右各 3 个，一刀切得干干净净。

    ```text
       下标     0    1    2    3    4    5
       元素     4    4    4    4    4    4
                        ^
    ```

    * 数组里**根本没有重复元素**时改完也能正常工作：`i` 找大于等于基准点的、`j` 找小于等于基准点的，找到了就交换、交换完各自进一格，等 `i` 越过 `j` 退出循环，最后收尾。

* **收尾只能跟 `j` 交换**

    * 这一版与前一版不同的地方是：退出循环时 `i` 和 `j` **可能不相等**。

    * `i` 找的是比基准点大的，它停下的位置很可能是**一个大的元素**。

    * `j` 找的是比基准点小的（或者相等的），它停下的位置是**一个小的或者相等的元素**。

    * 把大的跟基准点交换，就把大的换到左边来了、顺序立刻错乱，所以只能用 `j`。

## 三处等号的约束

* **最外层循环的 `i <= j`**

    * 换成 `i < j` 会排错，跑一遍得到的结果是 `1 2 3 2 4 4`，明显错了。

    * 第一轮没问题、第二轮看着也没问题，**问题出在最后一轮**。

    * 从第二轮结束处往前看：接下来要对 `[left, right]` 排序，`i` 从 `left + 1` 开始、`j` 在 `right`，这时 `i` 和 `j` **相等**。

    * 等号被去掉后不进入 `while` 循环，直接跳到循环外那句“把 `a[j]` 和基准点 `left` 交换”，而 `j` 根本还没定位好，这次交换是错的。

    * 等号加回去就对了：`i == j` 时也会进去走一次 `while`，循环体里就能把 `j` 定位到正确的位置。

    * 定位完成后虽然再交换一次，但那时 `j` 停在一个小于等于基准点的位置上，`a[j]` 和自己交换，不破坏顺序。

* **内层循环与交换前的比较**

    * 内层循环里 `i` 和 `j` 的比较必须是“小于等于”，不能是“小于”，也必须包含等号。

    * 不加等于，用测试用例跑，排序结果同样不正确。

    * 交换前那个 `if (i <= j)` 判断也不能去掉，不加它同样会错。

    * > **易错点**：这一版代码里一共有三处等号，缺一不可；它们的作用是把“两个指针恰好相等、`j` 尚未定位好”的那一轮也纳入循环体处理。

## 力扣上的实测对照

* **刁钻测试用例的设计**

    * 快速排序已经是**基于比较的排序算法里的天花板**，但直接扔到力扣上跑性能很不理想，一般都是超出时间限制。

    * 一类测试用例准备一大堆**全是重复元素的数组**：没做重复元素优化时，分区效果就是一个分区 n-1 个、另一个 0 个，性能急剧下降、最后达到 $O(n^2)$ 直接超时。

    * 另一类专门针对**没做随机化**的实现：故意在最左侧放一个最大的、最右侧也放一个最大的（或者最小的），同样导致分区极度不平衡。

* **优化组合的耗时**

    | 版本 | 力扣上的表现 |
    | :--- | :--- |
    | 单边快排 + 随机基准点 | 1872ms |
    | 双边快排 + 随机基准点 | 1648ms |
    | 双边快排 + 随机基准点 + 重复元素优化 | 29ms |
    | 再叠加“小数量走插入排序” | 19ms |
    | 归并排序 + 插入排序优化（对照） | 15ms |

    * 单边和双边快排就算加了随机化，性能也是惨不忍睹的一千多毫秒，因为它们都处理不了重复元素，一遇到重复分区照样崩。

    * “小数量直接切换成插入排序”的做法是在递归的边界条件那里判断 `right - left + 1` 是否少于某个阈值，元素个数很少就不再往下分区，直接拿插入排序一把排完。

    * 该改动对随机数据和重复元素都有效，性能能做到 19ms，接近归并加插入优化的 15ms。

## 计数排序

* **计数排序（Counting Sort）**

    * > **定义**：不比较元素、靠“数数”完成排序的算法，一次比较都不做。

    * 归并、堆排、快速排序都需要做元素之间的比较，计数排序与它们都不一样。

* **三步走**（示例数组 `a = {5, 1, 1, 3, 0}`）

    * 第一步找到最大值建 count 数组：最大值一眼看出是 5，最大值加一等于 6，所以创建长度为 6 的数组。

    * 新数组的索引**直接对应旧数组的元素值**：下标 0 对应元素 0、下标 1 对应元素 1、下标 2 没对应上没关系、下标 3 对应元素 3，直到下标 5。

    * count 数组用来记录每个元素分别出现了几次。

    ```text
    元素      0    1    2    3    4    5
    出现次数  1    2    0    1    0    1
    ```

    * 第二步遍历 count 把内容依次吐回新数组：出现 1 次的 0 放一个，出现 2 次的 1 放两个，出现 0 次的 2 跳过，出现 1 次的 3 放一个，4 跳过，5 放一个。

    * 可以另建一个新数组，也可以直接复用原来那个 `a`——原数组的元素留着没用了，直接覆盖。

    * 第三步的结果是 `0 1 1 3 5`，排好序了。

* **为什么天生有序**

    * 关键在于 count 数组的索引本身已经是排好序的：它的索引不就是 0、1、2、3、4、5 吗，顺序天然就是对的。

    * 所以按索引从小到大一个一个把元素取出来，输出顺序自然能得到保障。

    * 不需要比较、不需要冒泡、不需要归并——**顺序是索引自己带的**。

* **代码实现**

    ```java
    public static void countSort(int[] a) {
        // 第一步：找到最大值
        int max = a[0];                       // 先假定下标 0 处是最大值
        for (int i = 1; i < a.length; i++) {
            if (a[i] > max) {                 // 遇到更大的就更新
                max = a[i];
            }
        }

        // 第二步：建 count 数组，长度 = max + 1
        int[] count = new int[max + 1];
        for (int v : a) {                     // v 是原始数组的元素值
            count[v]++;                       // 它同时也是 count 的索引
        }

        // 第三步：遍历 count，按索引顺序吐回去
        int k = 0;                            // k 是配合 a 使用的写入下标
        for (int i = 0; i < count.length; i++) {
            while (count[i] > 0) {            // 出现几次就放几个
                a[k++] = i;
                count[i]--;                   // 放一个减一，减到 0 再看下一个索引
            }
        }
    }
    ```

    * 统计时 `for (int v : a)` 遍历出来的 `v` 是原始数组的元素值；因为元素值直接就是 count 的索引，所以直接 `count[v]++`。

    * 生成时 `for` 循环里的 `i` 有**两层含义**：一层是 count 的索引值，另一层同时也是原始数组的元素值，而 `count[i]` 代表这个元素出现的次数。

    * 写入时只要发现出现次数大于零，就把当前索引 `i` 写进 `a` 并 `k++`；某个元素出现 2 次就放 2 个，过程中 `count[i]` 一直减一，减到 0 才说明这个元素放完了。

* **两个前提**

    * > **前提**：数组中的元素应该是**大于等于 0 的正整数**；如果有负数，count 数组的索引就建不出来，算法得重新改。

    * > **前提**：**最大值不能太大**；count 数组长度是最大值加一，若最大值取整数的最大值，内存会直接撑爆，甚至干脆超过数组的最大上限。
