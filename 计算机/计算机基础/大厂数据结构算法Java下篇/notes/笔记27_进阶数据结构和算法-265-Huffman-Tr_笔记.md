# 进阶数据结构和算法-265-Huffman-Tr

## 哈夫曼编码的实现前提

* **编码（encode）**

    * > **定义**：把原始字符串按已建好的哈夫曼树逐字符翻译成编码串的过程，哈夫曼树写完构造后只差编码和解码两个功能。

    * 建树时原始字符串已经被存进成员变量，因为构造过程本身就得先拿到原始字符串才能统计频率，所以编码时不需要重新分析频率，只要把整个字符串再遍历一遍。

    * 建树过程中每个字符的编码都已全部算出来并塞进 `map` 集合，`a`、`b`、`c` 的编码都能查到。

    * 查法是拿当前字符作 key 去 `map` 里找，拿到的 value 是一个节点对象，该对象专门留了一个属性存这个字符的编码，直接调它的 `code` 就拿到编码。

    * 每个字符的编码都有了，最终把这些编码拼到一块儿就完事：准备一个 `StringBuilder` 做拼接，循环走完 `return sb.toString()`。

    ```java
    public String encode() {
        StringBuilder sb = new StringBuilder();
        char[] chars = source.toCharArray();
        for (char ch : chars) {
            Node node = map.get(ch);
            sb.append(node.code);
        }
        return sb.toString();
    }
    ```

    * 原始字符串先得到哈夫曼树再调 `encode`，结果是 `a`、`b`、`b`、`c`、`c` 依次编码成 `00`、`01`、`01`、`111`、`111`，拼接结果为 `000101111111`。

    * `a` 编码成 `00`，接下来两个 `01` 对应两个 `b`，最后六个 `1`（两个 `111`）对应两个 `c`。

    * > **易错点**：这组编码里 `a` 拿 `00`、`b` 拿 `01`、`c` 拿 `111`，全长 13 位，这个长度在解码踩坑时要直接用到。

    * > **提示**：编码函数返回的是字符串，但严谨地讲编码应该返回一个二进制数字、数字里存的是 `0101` 这些位，这里为了简单才退化成「字符串里存着 0101」。

## 哈夫曼解码的状态转移

* **解码（decode）**

    * > **定义**：把编码得到的比特串沿哈夫曼树逐位下走、还原成原始字符的过程。

    * 工具还是那棵哈夫曼树，从根节点出发，拿比特当路标往下走。

    * 走位规则只有一条：遇到 `0` 就向左走，遇到 `1` 就向右走。

    * 准备阶段先把解码字符串也当成字符处理拿到 `char[] chars`，再准备索引 `i`（循环条件 `i < chars.length`，`i` 等于数组长度说明处理到头就退出），最外层准备 `StringBuilder` 把结果拼回字符串。

    * `node` 变量表示「当前节点」，一开始等于根节点；向左走就是把 `node.left` 赋给 `node`，向右走就是把 `node.right` 赋给 `node`，走完一步别忘了 `i++`。

    * 循环内分两种情况：遇到的都是非叶子节点，和遇到了叶子节点。

    * 碰到叶子就说明找到了解码后的字符，把这个字符 `append` 到 `StringBuilder` 里；又因为下一个位要从头开始处理，同时把当前节点重置为根节点。

    * > **提示**：解码入参按理也该是一个二进制数字、把数字的每一位逐一处理，现在同样为了简化还是当作字符的 `0101` 来处理，别在真实项目里这么写。

    * 比特流沿树下走的状态转移：

    ```text
      node = root
          │
          │   i < chars.length 就继续转
          ▼
      node 非叶子 ──── 是 ────► append(node.ch)，node = root ──┐
          │                                                    │
          否                                                   │
          ▼                                                    │
      '0' → node.left    '1' → node.right                      │
          │                                                    │
          ▼                                                    │
      i++ ────────────────────────────────────────────────────►┘
    ```

    * 走实际比特串：第一个 `0` 从根节点向左走一步、索引 `i` 自增，没走到头还不是叶子，继续处理下一个数字；第二个 `0` 再向左走一步、`i` 又自增，这回走到头了，当前节点是叶子，这两个 `0` 找到的字符就是该叶子上的 `a`。

    * 找到一个字符后把 `node` 重置为根节点再从根处理后面的数字：接下来又一个 `0` 向左走一步、`i` 自增没走到头；接着遇到 `1` 同样先 `i` 自增，加完发现走到头，又找到字符 `b`，所以这两个位 `01` 对应 `b`；以此类推剩下的位全部转换成对应字符。

    * 原代码还少做了一件事：应该把整棵哈夫曼树的根节点记录成成员变量。此前在构造方法里只找到了数组的分界点，并没有把它存成当前这棵哈夫曼树的成员变量，现在补一个 `root`，构造时直接记录根节点，解码时先把它取出来存到 `node` 变量里。

## 互斥分支造成的丢字符

* **根因**

    * 把编码出来的 `000101111111` 再解回去，目标是恢复成原始的 `a`、`b`、`b`、两个 `c`，但结果少了一个字符，原始串里最后一个 `c` 没被解出来。

    * 比特串长度是 13，最后一个 `1` 时 `i` 是 12，而当前节点已经被重置成 `root`，逐步摊开状态如下。

    | 时刻 | `node` 指向 | `i` | 发生了什么 |
    | :--- | :--- | :--- | :--- |
    | 进入本轮循环 | `root` | 12 | `root` 不是叶子，进入 `if` 分支 |
    | 右移之后 | `c` 的叶子节点 | 12 | `chars[12] == '1'`，走 `else if` 的右移分支，这没问题 |
    | 自增之后 | `c` 的叶子节点 | 13 | `i++` 把 `i` 推到了数组长度 |
    | 叶子分支 | `c` 的叶子节点 | 13 | 本轮走的是 `if`，不会再进下面的 `else` |
    | 回到 `while` | `c` 的叶子节点 | 13 | `i == chars.length`，循环直接退出 |
    | 结果 | — | — | 最后一个 `c` 没被 `append` 进去 |

    * 症结在第 4 行：`if` 和 `else` 是互斥的，一次只能走一个分支；把叶子判断写成 `else`，可最后这一位偏偏是先走 `if`（右移）再走 `else if`（`i++`），根本没机会掉进 `else` 那个叶子分支。

    * 下一次循环开始时 `i` 已经是 13，循环直接退出，那个叶子就永远没被读出来。

* **改法**

    * 没有特别优雅的解决方式，做法是把最后那个 `else` 去掉，改成「走完之后重新判断」。

    * 既然当前节点在走完这一步之后已经变了，那就在这一次循环里把它是不是叶子重新判一遍；如果已经是叶子了，就不用等下一轮再走一遍 `if-else` 的叶子逻辑，直接把这段处理逻辑原样拷贝过来。

    ```java
    public String decode(String encoded) {
        StringBuilder sb = new StringBuilder();
        char[] chars = encoded.toCharArray();
        int i = 0;
        Node node = root;

        while (i < chars.length) {
            if (!node.isLeaf()) {
                if (chars[i] == '0') {
                    node = node.left;
                } else {
                    node = node.right;
                }
                i++;

                // 走完之后重新判断当前节点是不是叶子
                if (node.isLeaf()) {
                    sb.append(node.ch);
                    node = root;
                }
            }
        }
        return sb.toString();
    }
    ```

    * 跑一遍，最后两个 `c` 都回来了，数量正确。

    * > **注意**：循环里如果一次迭代可能完成「移动 + 产出」两件事，就别把产出挂在互斥的 `else` 上——`while` 的条件一变，这部分逻辑会被整段跳过；在这次迭代里重新判断一次，比赌下一轮还能进来稳得多。

## 活动选择的冲突定义

* **活动选择问题（activity selection）**

    * > **定义**：在一个会议室举办 `n` 个活动，每个活动有各自的起始和结束时间，找出时间上互不冲突的活动组合，最充分地利用会议室——办的活动次数越多越好。

    * 这个问题最好的解法是贪心解法，但下结论前要先想清楚：贪心要求每一步都找局部最优解，而这里局部最优有好几种选择方式，只有一种能堆叠成最终最优解。

    * > **注意**：持续时间最短、冲突最少、开始最早，这三种局部最优都没办法堆叠成最终的最优解。

* **示例的最优解**

    * 三个活动的数据下，最优解是活动 1 和活动 3：活动 1 结束了，活动 3 正好能开始，选它俩能办 2 个活动。

    | 活动 | 开始 | 结束 |
    | :--- | :--- | :--- |
    | 活动 1 | 1 | 3 |
    | 活动 2 | 2 | 4 |
    | 活动 3 | 3 | 5 |

    * 若选中间的活动 2，它跟其他两个都冲突，就只能办 1 个。

    * 六个活动的例子中最优解是 `1~2`、`3~4`、`5~7`、`8~9` 这四个，它们在时间上不冲突，活动次数能达到 4。

    * 若选中间这个比较长的 `1~6` 活动，`1~2`、`3~4`、`5~7` 以及最后一个就全选不成，只能跟 `8~9` 组合，一共 2 个活动。

    * 若选最后那个，它跟 `5~7`、`8~9` 以及最长的都冲突，只能跟 `1~2`、`3~4` 组合，活动次数是 3 次，所以最优解还是那 4 次。

## 被否掉的局部最优策略

### 优先选持续时间最短

    * 直觉是活动持续时间越短，跟其他活动冲突就越少。

    * 反例数据里活动 2 持续时间只有 2，按策略第一轮应该选中它。

    | 活动 | 开始 | 结束 | 持续时间 |
    | :--- | :--- | :--- | :--- |
    | 活动 1 | 1 | 5 | 4 |
    | 活动 2 | 4 | 6 | 2 |
    | 活动 3 | 5 | 9 | 4 |

    * 选活动 2 不行，第一个和第三个都跟它冲突，最终活动总数只有 1 个。

    * 而如果先选活动 1 再选活动 3，`1~5` 和 `5~9` 在时间上不冲突，活动总数能达到 2。

    * > **结论**：优先选择持续时间最短的活动达不到最终解的效果，否掉。

### 优先选冲突最少的

    * 思路是每次选一个跟其他活动冲突最少的，当作局部最优。

    * 做法是先把每个活动各自冲突了几次都数出来，比如活动 1 在没结束之前活动 2、3、4 就都已经开始，所以它的总冲突次数是 3；然后每轮选冲突次数最少的那个。

    * 冲突次数最少的是 6 号活动，它只冲突了两次，第一轮选中；第二轮选冲突次数为 3 的那个，它跟已选中的 6 号不冲突，选中。

    * 剩下里面冲突次数最少的是 3 号活动，它跟前面的 2 号以及上面那个 3 号都不冲突，选中。

    * 最后冲突次数为 4 的那一批一个都选不了：2 号不行，3、4 号不行，5 号不行（跟 6 号冲突），7 号跟 6 号冲突，8、9、10 号跟 3 号活动冲突。

    * 结果选中了 3 个：1 号、2 号、11 号。

    * > **结论**：真正的最优解是 1 号、5 号、7 号、11 号一共 4 个活动——1 号结束 5 号开始，5 号结束 7 号开始，7 号结束 11 号开始。3 个 vs 4 个，第二个贪心策略也否掉。

### 优先选开始最早的

    * 实在没招了又想的办法，仍然不成立。

    * 例子里有四个活动，第一个活动确实是最先开始的，但显然它也是最后结束的，跟下面三个都会冲突，选了它活动总数就只能有一个。

    * 而选择下面这三个，活动数可以达到三个。

    * > **结论**：第三种办法也被否掉。

## 优先选最早结束的活动

### 机理与首个例子

    * > **定义**：把「优先选择最先结束的活动」作为每轮的局部最优解。

    * 道理是最先结束意味着能最快把会议室腾出来给别的活动用；就这么一点，但恰好能让局部最优解最后堆叠成一个最终的最优解。

    * 按这个策略重走第一个例子（`1~3`、`2~4`、`3~5`），这三个活动本身已经按结束时间排好序：`1~3` 最先结束排最前，`2~4` 第二，`3~5` 最后。

    * 活动 1 直接选中；活动 2 跟选中的活动 1 冲突，排除；活动 3 跟活动 1 没有时间冲突——活动 1 已经结束、活动 3 才开始，选中。

    * 最优解就是选中 1 和 3，共 2 个活动。

### 第二个例子

    * 那 11 个活动同样按结束时间排好序，逐轮判定如下。

    | 轮次 | 活动 | 判定 |
    | :--- | :--- | :--- |
    | 1 | 活动 1 | 结束时间最早，直接选中 |
    | 2 | 活动 2、3、4 | 都与活动 1 冲突，排除 |
    | 3 | 活动 5 | 与活动 1 不冲突，选中 |
    | 4 | 活动 6 | 与活动 5 冲突，排除 |
    | 5 | 活动 7 | 与活动 5 不冲突，选中 |
    | 6 | 活动 8、9、10 | 都与活动 7 冲突，排除 |
    | 7 | 活动 11 | 与活动 7 不冲突，选中 |

    * 得出最优解，4 个活动。

### 反直觉的例子

    * 活动 1 的结束时间最晚，按结束时间排序它应该排在最后，所以排序之后第一个被选中的是活动 2。

    * 接着活动 3 跟活动 2 并没有冲突，也被选中；活动 4 跟上面的活动 3 也没有冲突，也被选中；剩下的最后那个活动跟活动 4 冲突，被排除。

    * 最优解是 3 个。

    * > **结论**：优先选最早结束的活动作为局部最优解，就能达到最终的最优解。

## 活动选择的代码实现

### 数据与排序

    * 活动类里包含活动编号，以及活动的起始和结束时间 `start`、`finish`，配一个构造方法和一个 `toString` 方法。

    * 测试数据是一个活动数组里三个活动，编号分别是 0、1、2，起始结束时间分别是 `1~3`、`2~4`、`3~5`。

    * 必须按结束时间由小到大依次处理，结束时间早的先处理、最后处理的排在后面；排序是一种选择，也可以把它们塞进优先级队列，但顺序必须按 `finish` 排，这里选排序。

    * 比较的是对象中的某一个属性，所以用 `Comparator.comparingInt` 的方法引用，指定一个 `getFinish` 方法，告诉它按 activity 对象中的 `finish` 属性排序。

    ```java
    // 第一个参数传要排序的数组，第二个参数给比较器
    Arrays.sort(activities, Comparator.comparingInt(Activity::getFinish));
    ```

    * 测试时先把顺序打乱再看排序结果：结束时间最早的排在最前面，然后是结束时间 4 的 1 号活动，最后是结束时间 5 的 2 号活动，输入数据就处理好了。

### select 方法

    * 接受两个参数：活动数组和数组长度。

    * 三句话思路：`activities[0]` 肯定被选中，处理它时不用考虑它跟其他活动冲不冲突；后面的每个活动都拿它的开始时间跟上一次被选中的活动的结束时间比；选中了它，它就成为「上一个被选中的活动」。

    * 判定条件是 `current.getStart() >= previous.getFinish()`：`>=` 说明没有冲突则选中并把 `previous` 换成它，小于说明有冲突就跳过继续处理下一个。

    ```java
    public static List<Activity> select(Activity[] activities, int n) {
        // 保存被选中的活动
        List<Activity> result = new ArrayList<>();

        // 结束时间最早的那个一定被选中，不用去比较它跟谁冲突
        result.add(activities[0]);

        // 上一次被选中的活动，最开始就是 activities[0]
        Activity previous = activities[0];

        for (int i = 1; i < n; i++) {
            Activity current = activities[i];  // 当前正在处理的活动
            if (current.getStart() >= previous.getFinish()) {
                // 没有冲突，选中
                result.add(current);
                previous = current;
            }
            // 有冲突就跳过，继续处理下一个
        }

        return result;
    }
    ```

    * > **易错点**：判断冲突时只能拿当前活动的开始时间跟上一次被选中的活动的结束时间做对比，不要拿它去跟 `activities[0]` 的结束时间比——那是不准的，活动多了之后会漏掉中间被选中的那个。

    * 对 `1~3`、`2~4`、`3~5` 这组数据跑一遍，选中的是 0 号和 2 号活动，因为 `1~3` 和 `3~5` 确实不冲突。

## 分数背包的贪心规则

* **问题设定**

    * > **定义**：有 `n` 个液体物品（每种都有各自的重量和价值），取走总量固定（示例中是 10L），每种液体都可以不拿、全拿或只拿其中一部分，求能拿到的最高价值。

    * 示例数据里水总共 4L 价值 24 块，牛奶 8L 价值 160 块，此外还有五粮液和可乐等。

    * 几种拿法都是凑够 10L：4L 的水加 6L 的可乐是 `24 + 108`；8L 的牛奶加 2L 的五粮液是 `160 + 4000`；也可以对某些液体只拿一部分，比如 6L 的可乐加 2L 的五粮液再加 2L 的水。

    * 这个问题最好的解法还是贪心，局部最优的规则就是一句：每轮只拿单位价值最高的那个液体——肯定先拿最贵的茅台，然后次贵的五粮液，等它们拿完了再挑第三贵的，直到拿够 10L。

    * > **注意**：只有缺心眼的才会说最先去拿水，这个想都不用想，我们肯定不拿水。

* **样例推演**

    * 第一轮茅台，1L，4000 块；第二轮五粮液，2L，4000 块，看起来它肯定是第二贵的。

    * 第三轮牛奶和可乐不知道哪个更好，要算单位价格：牛奶 `160 ÷ 8`，1L 是 20 块；可乐 `108 ÷ 6`，是 18；18 比 20 便宜，所以第三轮应该选牛奶。

    * 茅台和五粮液已经拿了 3L，所以牛奶只能拿 7L，也就是它 8L 中的 7/8。

    * 总价值 `4000 + 4000 + 140 = 8140`。

    * > **提示**：举例时简化起见给出的数据都是能整除的、不会出现小数，真实数据里单位价值几乎一定会出现小数。

## 分数背包的单位价值排序

### 数据准备

    * `select` 方法要选出总共拿 10L 的物品及其最大价值，做的第一件事就是根据物品的单位价值做好排序（排序是一种选择，用优先级队列也行）。

    | 编号 | 液体 | 重量（L） | 总价值（元） | 单位价值（元/L） |
    | :--- | :--- | :--- | :--- | :--- |
    | 0 | 水 | 4 | 24 | 6 |
    | 1 | 牛奶 | 8 | 160 | 20 |
    | 2 | 五粮液 | 2 | 4000 | 2000 |
    | 3 | 可乐 | 6 | 108 | 18 |
    | 4 | 茅台 | 1 | 4000 | 4000 |

    * 为了排序得先给 `Item` 加一个计算单位价值的方法 `unitValue`，就是总价值除以重量。

    ```java
    // 单位价值：总价值 / 重量
    public int unitValue() {
        return value / weight;
    }
    ```

    * > **提示**：这里全选了 `int`，换成 `double` 也是可以的。

### 降序排列

    * 排序写成在 `comparingInt` 之后再调一个 `.reversed()`，把默认的升序降下来。

    ```java
    Arrays.sort(items, Comparator.comparingInt(Item::unitValue).reversed());
    ```

    * > **易错点**：`comparingInt` 默认是升序，直接这么写会把水排在最前面、茅台反而排在最后，方向正好反了。

    * 遍历打印验证顺序：最前面是 4 号物品茅台，第二是 2 号物品五粮液，第三是 1 号物品牛奶，第四是 3 号物品可乐，最后 0 号物品水排在最后，顺序确定了。

## 分数背包的主循环

* **定变量与分支**

    * 定一个变量 `max` 代表最大价值，最开始设置为 0。

    * 循环内处理每件物品分成两种情况：这件物品能全部拿完，或者一次拿不完。

    * 情况一的判断条件是剩余重量 `total` 大于等于当前物品的 `weight`，此时把剩余重量减掉当前物品的重量，并把这件物品所有的总价值直接累加到 `max` 上（因为是全拿完了）。

    * 情况二里 `total` 已经小于当前物品的重量，比如剩余重量剩 7L，处理到重量是 8L 的牛奶，只能拿一部分。

* **拿不完的折算**

    * 拿不完时不能把它的总价值直接累加到 `max` 上，而应该是单位价值乘以真正拿的那个数量——剩多少就拿多少，也就是 `total` 乘以当前物品的单位价值。

    * 前面剩 7L、牛奶单位价值 20，`7 × 20 = 140`，这就是这一次拿到的价值，累加到 `max` 上。

    * 处理到这儿就可以结束了——牛奶都没拿完，接下来就不用再循环到可乐和水了，所以直接 `break` 退出循环。

    ```java
    public static int select(Item[] items, int n, int total) {
        // 按单位价值降序：最贵的先处理
        Arrays.sort(items, Comparator.comparingInt(Item::unitValue).reversed());

        int max = 0;   // 最大价值

        for (int i = 0; i < n; i++) {
            Item current = items[i];
            if (total >= current.weight) {
                // 拿得完：整件拿走，总价值直接累加
                total -= current.weight;
                max += current.value;
            } else {
                // 拿不完：只拿剩下的 total 升，按单位价值折算
                max += total * current.unitValue();
                break;
            }
        }

        return max;
    }
    ```

    * 把 `max` 打印出来验证，跟手算一致，都是 8140。
