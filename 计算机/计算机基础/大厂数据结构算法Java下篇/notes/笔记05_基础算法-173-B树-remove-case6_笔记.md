# 基础算法-173-B树-remove-case6

## 根节点失衡：唯一的情形

* **根节点（root）**

    * > **定义**：B 树最顶层的节点，其 key 数目是允许小于下限的。

    * 查数据时它站在树顶，根本不需要靠兄弟借 key，所以「左旋 / 右旋 / 合并」那套调整对它统统不适用。

    * 根节点失衡的唯一情形是 key 数目等于 0，换个说法就是孩子数等于 1。

    * 因为孩子数永远比 key 数目多一，只剩一个孩子就意味着它只剩一条腿，站不住。

* **case 6**

    * 调整方法：拿它唯一那个孩子顶替掉旧根，让这个孩子成为新根。

    * 触发前提是 `root.children[0] != null`，整棵树被删光时不能把 `null` 顶上去。

```java
if (root.keyNumber == 0) {          // 唯一会失衡的根节点情形
    if (root.children[0] != null) { // 整棵树被删光时，别把 null 顶上去当新根
        root = root.children[0];
    }
}
```

一个把根节点摘空的例子：根节点只有一个 k4 挂着四个孩子，删掉同层的 k2 后，该节点 key 数目低于下限，左右都借不到，只能向自己合并——右兄弟整个摘掉、父节点的 key 4 合并下来、右兄弟的 key 也并过来，1、4、5、7 并到一起；麻烦出在合并完成后根节点把仅有的那根 key 4 送了下去。

```text
   合并完成后，根节点把仅有的那根 key 4 送了下去

        [ 4 ]  四个孩子        ⇒        [   ]  一个孩子
                                               ↑
                                    key 数目归零，只剩一条腿
```

* **判据拆分**

    * `keyNumber == 0` 只回答了「会不会失衡」。

    * `root.children[0] != null` 才回答「该不该动」，这两件事必须分开写。

    * 设想把 1、4、5、7 一根一根全删光，`keyNumber == 0` 仍然成立，但此时连孩子都没了，把 `null` 替换上去根节点就不对了，根节点必须留着。

    * > **易错点**：漏掉外层 `root.children[0] != null`，删空一棵树的时候会亲手把树删没了。

## balance 接进 doRemove

* **balance 的三个参数**

| 参数 | 含义 |
| :--- | :--- |
| `parent` | 父节点 |
| `node` | 被调整的节点 |
| `index` | 被调整节点在父节点里的下标，即第几个孩子 |

* **doRemove 补参数**

    * 发现某个节点的 key 数目小于下限时，就调用 `balance` 去重新调整平衡。

    * 麻烦在于 `doRemove` 当时只接收一个参数，就是当前被删除的这个节点，前两个参数根本没有。

    * 所以 `doRemove` 要补两个参数：父节点 `parent`，以及当前节点 `node` 的索引位置。

* **三处调用，三种补法**

    * 判断标准只有一条：下一个要被处理（被删除）的节点是谁，`parent` 就是谁，`index` 就是它在 `parent` 里的下标；递归往下走一层，就换一次爹。

    * > **易错点**：这三处最容易写混，`parent` 与 `index` 必须成对按同一条标准推导，不能凭感觉填。

| 调用点 | 代码 | parent | index |
| :--- | :--- | :--- | :--- |
| 首次调用，从外部进 `doRemove` | `doRemove(null, root, 0)` | `null`，根节点没有父亲 | 0 |
| 非叶子节点上没找到目标，转到孩子里继续查找删除 | `doRemove(node, node.children[1], 1)` | 当前 `node` | 1，到第 2 个孩子 |
| 用后继节点的 key 替换待删除节点的 key，再删除后继 | `doRemove(node, node.children[i + 1], i + 1)` | 当前 `node` | `i + 1` |

## 左旋笔误与测试兜底

* **先把预期结果推出来**

    * 测试用例的原始树：根是 3，两个孩子分别是 `[1, 2]` 和 `[4, 5, 6]`，要删除 2。

    * 删掉 2 以后这个节点 `e` 不平衡了，但右边孩子 `[4, 5, 6]` 的 key 数目是富裕的，可以左旋一次向右借一个。

    * 左旋的效果是把 3 旋转下来、把 4 旋转上去，所以预期结果是根节点 4、左孩子 `[1, 3]`、右孩子 `[5, 6]`。

    * 实际报的是根节点不对：期望 4，返回的是 1。

* **断点停在左旋里**

    * 因为报错信息已经指出问题出在左旋，就直接在左旋处加断点，先确认条件确实进去了，再逐步走。

    * 第一步，把父节点的 key 旋转下来：父节点本来是 3，被调整节点是 1，旋转下来后这边应该变成 `[1, 3]`，看起来是对的。

    * 第二步，把右兄弟最小的孩子换个爹：`[4, 5, 6]` 这个节点没有孩子，条件不成立，跳过，也是对的。

    * 第三步，把右兄弟最小的 key 旋转上去：旋转上去以后变成 1 了。

    * 根因是右兄弟的最左 key 旋转上去这一步写成了 `x`，也就是把被调整节点自己的 key 顶了上去。

```java
// 写错了：把被调整节点自己的 x 顶了上去
parent.keys[index] = x;
// 应该是右兄弟最左边的 key
parent.keys[index] = right.leftMostKey();
```

* **测试的作用**

    * 改完之后重跑，通过；再把 case 1 到 case 5 的各种情况连同几个综合情况全部跑一遍，所有测试用例都通过。

    * > **结论**：写代码没办法保证百分之百正确，必须先设计好各种各样的测试用例，用测试用例检查出代码中可能的疏漏；这不是可选项，是唯一靠谱的兜底手段。

## 顺着删的完整轨迹

* **参数设定**

    * 这几个综合例子选取的 `t` 都等于 2，不是 3，下限就是 $t - 1 = 1$。

    * 树有 11 个 key，从 1、2、3 一直到 11，从右边倒着删：先删 11，再删 10，再删 9，一直删到 1。

* **逐步对照**

| 删除 | 是否失衡 | 做了什么 |
| :--- | :--- | :--- |
| 11 | 失衡 | 左兄弟不够键、右兄弟也不够 → 向左兄弟合并；父节点挪一个 key 下来 |
| ↑ 向上递归 | 父节点也失衡 | 继续向左合并；这一回被合并的节点**还带着孩子**，孩子也得一起挂到左兄弟下面 |
| 10 | 不失衡 | 删完还剩 9，key 数目没有小于下限，直接删 |
| 9 | 失衡 | 向左兄弟合并，父节点的 8 合并下来 |
| 8 | 不失衡 | 直接删 |
| 7 | 失衡 | 向左兄弟 5 合并，父节点的 6 合并下来；父节点再次失衡，继续向左兄弟 2 合并，父节点的 4 合并下来；被调整节点自己没有 key 可合并，但它有个孩子（存 5、6 的节点）要挂过去，得到 k = [2, 4]、孩子 = [1]、[3]、[5, 6]；随后根节点触发 case 6 |
| 6 | 不失衡 | 直接删 |
| 5 | 失衡 | 向左兄弟 3 合并，父节点的 4 合并下来；它没有 key 可合并，合完即可 |
| 4 | 不失衡 | 直接删 |
| 3 | 失衡 | 向左兄弟 1 合并，父节点的 2 合并下来；根节点再次触发 case 6，用 0 号孩子（1、2）替换旧根 |
| 2 | 不失衡 | 直接删 |
| 1 | 不失衡 | 会进入 case 6 的判断，但这次条件不成立，已经没有 0 号孩子了，所以不做任何处理 |

* **有孩子的合并**

    * 合并这件事此前演示删除的时候并没有演示这种场景：被调整的节点自己是有孩子的。

    * 合并时除了 key 要并过去，它的孩子也得跟着并过去；左兄弟接过来以后自己少了一个孩子，把这个补上，正好没问题。

* **父节点也会跟着失衡**

    * 代码里是有体现的：沿着 `doRemove` 一路往下删，删完叶子上的 11 之后，最后还是会走到检查下限那段代码，发现原来存 10 的那个节点 key 数目也小于下限了。

    * > **结论**：平衡调整是递归的、由底向上的，它从叶子一路上来，递归要走一遍，每一层都要重新检查一次；哪怕底层的一次合并看起来很干净，也可能连着触发上面好几层的合并，不能只盯着出问题的那一层看。

## 从中间删：后继替换与修复切换

* **非叶子节点上的 key 怎么删**

    * 4 所在的节点是非叶子节点，不能直接删，要先找到它的后继 5，用 5 替换掉 4，把删除操作变成删除 5。

    * 接下来从 6 开始往下找，去删除 5。

    * 5 删掉后不平衡，左边没得借右边也没得借，又是合并；它没有左边兄弟了，向自己合并——父节点的 6 先合并下来，右边兄弟 7 整个不要了并过来。

    * 合并完成后它原来的父节点再次触发不平衡，父节点左兄弟也有、右兄弟也有但都不够借，于是向左合并：6、7 的分支不要了，向左边兄弟 2 合并，把父节点的 5 挪下来一个；2、5 这边有两个 key 缺一个孩子，第三个孩子就是刚才剩下的 6、7，给它挪过来就恢复平衡。

    * 删一个 4，做了两次合并操作，还有一个找后继的操作，一点都不简单。

* **后续几轮的逐步对照**

    * 后面几轮更能说明问题，因为修复方式是在合并和旋转之间来回切换的。

| 删除 | 用后继替换 | 删掉以后怎么修 |
| :--- | :--- | :--- |
| 8 | 后继 9 替换 8，转成删 9 | 9 删掉后两边都借不到 → 向自己合并（父节点的 10 下来、11 并过来）；父节点这次**左兄弟的 key 富裕** → 改用右旋 |
| 5 | 后继 6 替换 5，转成删 6 | 6 删完仍然满足平衡，直接删 |
| 6 | 后继 7 替换 6，转成删 7 | 左边没有，但右边够借 → 左旋（父节点的 9 下来、右边兄弟的 10 上去） |
| 7 | 后继 9 替换 7，转成删 9 | 不够借 → 向自己合并；父节点再次不够借 → 向左、向 2 合并，随后触发 case 6，用根节点 0 号孩子替换旧根 |
| 2 | 后继 3 替换 2，转成删 3 | 左边不够借，右边够借 → 左旋（父节点的 9 下来、右边兄弟的 10 上去） |
| 3 | 后继 9 替换 3，转成删 9 | 左右都不够 → 向左、向 1 合并，父节点的 9 合并下来 |
| 10 | 后继 11 替换 10，转成删 11 | 兄弟（1、9）的 key 富裕 → 右旋（父节点的 11 下来、9 上去） |
| 9 | 后继 11 替换 9，转成删 11 | 向左合并，得到 1、11；随后触发 case 6，用 1、11 替换旧根 |
| 1、11 | 直接删 | 都不会导致失衡 |

* **三种修复动作**

```text
【右旋】左边兄弟有余，就向左借一个

    ① 本 吞下父的 key，本 变胖
    ② 本 最右边的那个孩子，改挂到新的父 底下
    ③ 兄 最左边的 key 上浮，接替父 原来的位置

    结果：  [ 兄' ]  [ 父' ]  [ 本' ]
            兄' 少一根 key       本' 多一根 key，右孩子被移走


【左旋】右边兄弟有余，就向右借一个

    ① 本 吞下父的 key，本 变胖
    ② 本 最左边的那个孩子，改挂到新的父 底下
    ③ 兄 最左边的 key 上浮，接替父 原来的位置

    结果：  [ 本' ]  [ 父' ]  [ 兄' ]
            本' 多一根 key，左孩子被移走


【向左合并】两边都借不到，把本整个并进左兄弟

    ① 父 少一根 key，并下沉进 兄
    ② 本 的 key 与孩子，全部并进 兄
    ③ 本 整个摘掉，退化为新的 [ 兄' ]

    结果：  [ 兄' ]  [ 父' ]
            兄' 多一根 key、多一批孩子
```

* **先旋还是先合**

    * 取决于兄弟手里有没有余量，而不是取决于你在树的哪一层。

    * 同样是非叶子节点引起的失衡，兄弟富裕就是旋转，兄弟不富裕就是合并，判据始终是同一个。

## 实现的等价变体

* **用前驱替换非叶子节点的 key**

    * 这套实现的做法是：待删除的 key 在非叶子节点上不能直接删，找到后继的 key 先替换掉待删除的 key，再把删除操作变成删除后继 key。

    * 别的办法是：用**前驱的 key** 来替换，思路一样，只是最后实现出来的效果可能稍有差异；所以有些实现是用前驱 key 替换掉非叶子节点中被删除的 key，再把删除转成删除前驱 key。

* **合并方向也可以反过来**

    * 这里统一是向左合并，但完全可以统一以右边为准向右合并，同样能让树恢复平衡，只是最终合并出来的效果可能不同。

* **不要拘泥于某一种实现**

    * 网上一些 B 树实现代码和这套实现不太一样，差别主要就落在上面这两处。

    * > **结论**：写代码时不要拘泥于单一实现，熟练以后可以尝试用新思路改写它，能改写说明是真的懂它了。

## 哈希表的需求起点

* **朴素需求**

    * 红黑树、B 树的查找速度已经很快，是对数时间，但还想要更快。

* **编号加表格的思路**

    * 先给所有数据分配一个编号，比如「肖」编号 0，「牛」编号 1，以此类推。

    * 再准备一张表格，程序里表格就是一个一维数组，并把编号与表格索引建立一一对应：编号 0 放索引 0，编号 1 放索引 1。

    * 已知「编号 = 1 的数据」就直接跳到索引 1，一步到位。

    * 通过数组索引定位数据，跟数据的规模没有关系，所以查找的时间复杂度是 $O(1)$。

    * 不仅仅是查询，找到数据以后做修改或删除，**增删改查的时间复杂度都是 $O(1)$**。

```text
   编号                      表格（一维数组）

   [0] ─── 肖 ──────────→    索引 0 | 肖 |
   [1] ─── 牛 ──────────→    索引 1 | 牛 |
   [2] ─── 李 ──────────→    索引 2 | 李 |

   已知「编号 = 1 的数据」 →  直接跳到索引 1  →  一步到位
```

* **理想与现实的两处矛盾**

    * 理想情况：编号唯一，数组越大越好，最好能容纳所有数据。

    * 现实之一：数组要求存储连续，也就是要一块连续的内存；数据量若是 100 万，所需连续内存长度非常大，对内存分配很苛刻，这一点不现实。

    * 现实之二：编号也不能绝对保证不重复，编号还是有可能重复的。

## 拉链法与编号重复

* **拉链法（chaining）**

    * > **定义**：让即将放入数组的新数据也映射到某个索引，但不覆盖已有数据，而是与已有数据串成一条链表。

    * 数组长度固定为 8 且八个索引都填满，放第 9 个数据时，让它也映射到索引 0。

    * 编号为 0 的「盐」与后放入的编号为 8 的「盐」串成一条链表，谁也不覆盖谁。

```text
   索引 0  ──→  [ 编号 0 的「盐」 ] ──→  [ 编号 8 的「盐」 ] ──→  nil
   索引 1  ──→  [ 编号 0 的「令」 ] ──→  nil
   索引 2  ──→  …

   第 9 个数据照样映射到索引 0，
   只是接在同一条链的尾巴上，谁也不覆盖谁。
```

    * 引入链表之前，靠编号定位索引就能直接拿到数据，无需比较，复杂度是 $O(1)$。

    * 引入链表之后，定位到这个索引并不能唯一确定它，要顺着链表逐一比较才能找到目标数据，复杂度与链表长度有关，链越长比较次数越多。

    * 所以拉链法虽然解决了有限数组存不下更多数据的问题，但带来了性能上的降低，具体实现时要在**节省数组占用空间**与**增删改查的效率**之间求一个平衡。

* **编号重复也不慌**

    * 通过算法生成一个绝对唯一的编号，实现难度比较大，所以允许编号适当重复。

    * 编号重复时通过数据本身来区分：编号都是 0，但一个是「盐」一个是「令」，照样能确定。

* **名字的由来**

    * > **定义**：哈希表（hash table）中「哈希」指的就是前面那个编号，它被称为**哈希码（hash code）**。

    * 哈希码连同它的数据一起放入表格，整个这个整体就叫哈希表，这就是名字的由来。

    * 它的特点是：只要把编号跟表格索引的关系建立好，就可以通过编号快速查找到想要的数据，有多快？$O(1)$。

    * 前面理想与现实的矛盾仍然要解决：结合链表让有限长度的数组存更多数据；编号允许适当重复，将来不行就通过数据自身区分。

## 正着删的练习规则

* **题面**

    * 还是综合一那棵 11 个 key 的 B 树，key 从 1 到 11，`t = 2`。

    * 这回正着删：先删 1，再删 2，再删 3……一直删到 1，把它删完。

* **自查清单**

    * 非叶子节点上的 key 不能直接删，要先用**后继 key** 替换（用前驱 key 也行，思路一样），把删除操作转成删除那个后继 key。

    * 真正落到叶子上的删除之后，如果该节点的 key 数目掉到 $t - 1 = 1$ 以下，就去判断兄弟：左边有余就右旋、右边有余就左旋。

    * 两边都不够借就合并（这套实现统一向左合并，统一向右合并也对）。

    * 合并时被摘掉的那个节点如果有孩子，孩子要一起并进合并后的兄弟。

    * 合并会让父节点少一根 key，所以调整是自底向上递归的，每一层都要重新检查一次。

    * 最后根节点被摘空了走 case 6，拿它的 0 号孩子顶上；整棵树都删空了，什么都不做。
