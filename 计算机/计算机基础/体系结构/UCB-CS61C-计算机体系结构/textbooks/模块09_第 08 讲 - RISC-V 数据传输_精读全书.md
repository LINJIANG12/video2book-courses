## RISC-V 数据传输：架起寄存器与内存的高速通道
> 对应块：BLK09 | 覆盖分集：P09 | 块标题（分集名）：《第 08 讲 - RISC-V 数据传输》

### 走出只有三十二个寄存器的象牙塔

在探讨如何把数据从外部搬运进处理器之前，我们不妨先回顾一下此前掌握的算术工具箱。我们已经见过最基础的加法 `add`、减法 `sub`，以及带立即数的加法 `addi`。

不知你是否曾经好奇过：为什么 RISC-V 提供了 `addi`，却偏偏没有设计一条专门的 `subi`（减立即数）指令？

答案其实非常纯粹：我们拥有极为优雅的二进制补码系统。既然想要减去一个常数，只需要把这个常数取负，然后再用 `addi` 加上去即可。既然两条指令的效果完全等价，在硅片上多造一个硬件减法立即数逻辑就是多余的浪费。这就是精简指令集（RISC）崇尚的设计美学——能省则省，绝不冗余。

在这些运算中，数据的流动形式极其规范。在寄存器传输语言（Register Transfer Language, 简称 RTL）中，我们可以把由 32 个寄存器组成的寄存器堆（Register File）直观地想象成一个容量为 32 的数组 `R[0..31]`。无论是加法还是减法，其标准语义都可以抽象为：

```text
R[rd] = R[rs1] + R[rs2]
```

等号左边的 `rd`（目标寄存器）指定了一个 5 位的编号（取值范围 0 到 31）。每当左侧出现等号，就意味着我们要把计算得到的总和送回寄存器堆，强行覆盖掉 `rd` 中原本保存的旧值。这个过程中唯一的铁律在于零号寄存器 `x0`：它的硬件位永远被硬编码接地为 0。即便你的指令把 `rd` 指定为 `x0`，写入操作也不会报错，但芯片内部什么改变都不会发生，它永远坚固如初地保持为 0。

但请大家从这个只有 32 个寄存器的象牙塔里抽出身来，看一看真实世界的软件：你在 C 语言里写下的 `int a[100]`、成千上万个字符拼接成的长文本、从操作系统命令行传入的 `argv` 参数列表、图像像素矩阵……这林林总总的复杂数据，难道能够塞进区区 32 个寄存器里吗？

显然不可能。现实世界的绝大多数数据，都驻留在外面的内存（DRAM）之中。今天我们的核心使命，就是要搞清楚作为 CPU，我们究竟该如何跨越物理鸿沟，把数据从正确的内存位置准确地拉进寄存器，算完之后再安全地放回去。

### 现实世界的物理鸿沟：萨克拉门托与延迟法则

要理解数据传输的重量，首先得看清现代计算机体系结构中那道残酷的物理鸿沟。

```text
+-----------------------+                    +-----------------------+
|       CPU 芯片        |                    |       主内存 DRAM      |
|  +-----------------+  |                    |                       |
|  | 寄存器堆 (32个)  |  |    系统总线交互    |   数以亿计的字节空间   |
|  +--------+--------+  | <================> |                       |
|           |           |   (极其昂贵的延迟)  |                       |
|  +--------v--------+  |                    |                       |
|  | 算术逻辑单元 ALU|  |                    |                       |
|  +-----------------+  |                    |                       |
+-----------------------+                    +-----------------------+
```

上面这幅简图揭示了计算机系统的运作真相：左边是主频高达 1 GHz 到 4 GHz 的 CPU 核心，算术逻辑单元（ALU）和 32 个通用寄存器全挤在同一块微小的芯片上。在这里，一个时钟周期只有 1 纳秒甚至四分之一纳秒，一切都在电光石火间完成；而数据所在的内存，却孤悬在芯片之外。

在整个物理存储层次结构（Memory Hierarchy）中，越靠上的部件体积越小、速度越快、每比特制造成本也越昂贵，就像大自然中动作飞快的小老鼠与蚊子；而越靠下的部件容量越大、速度越慢、每比特成本越低廉，就像笨重庞大的大象。32 个寄存器加在一起一共才只有区区 128 字节，而底部的 DRAM 动辄是数个吉字节（GiB）。

加州大学伯克利分校的传奇校友、图灵奖得主吉姆·格雷（Jim Gray）曾经提出过一个极为优美且震撼的延迟类比：

> **提示**：如果说 CPU 访问自己内部的寄存器，相当于你在脑子里回想一个密码，只需要耗费 1 分钟；那么 CPU 跨越总线去访问一次主内存，其延迟相当于要慢上 100 到 500 倍。放在北加州的现实地理尺度下，这相当于你必须亲自开上车，从伯克利校园一路开到加州州府萨克拉门托（Sacramento），单程耗费 100 到 500 分钟去把写在纸上的密码取回来！

这意味着，当你在 C 语言中轻巧地写下一行 `g = h + a[3]` 时，CPU 就必须在原地无所事事地空转，苦苦干等几百个时钟周期，直到数据艰难地从萨克拉门托送抵 CPU。在后续的课程中，我们会专门学习硬件架构师如何通过引入“高速缓存（Cache）”这道神奇的屏障来削减这趟痛苦的旅程；但就目前而言，我们必须清醒地认识到：访存是非常昂贵的操作，我们总希望尽量把数据保留在寄存器中计算。

### 内存的几何形态与端序之争

在进入数据传输指令之前，我们必须对内存本身的寻址与组织方式建立精确的几何直觉。

在 32 位系统环境下，内存的逻辑地址空间从第 0 个字节一路延伸到第 $2^{32}-1$ 个字节（共 4 GiB 大小）。在纸上绘制这个庞大的空间时，通常有两种等价却视角不同的画法：

```text
       单字节宽视角                        4 字节字宽视角 (推荐)
       
     地址       内存字节               行地址        字内容 (4 Bytes)
   +------+    +--------+            +------+    +----+----+----+----+
   | 0x0  |    | 1 Byte |            | 0x0  |    | B3 | B2 | B1 | B0 |
   +------+    +--------+            +------+    +----+----+----+----+
   | 0x1  |    | 1 Byte |            | 0x4  |    | B7 | B6 | B5 | B4 |
   +------+    +--------+            +------+    +----+----+----+----+
   | 0x2  |    | 1 Byte |            | 0x8  |    | BB | BA | B9 | B8 |
   +------+    +--------+            +------+    +----+----+----+----+
   | ...  |    |  ...   |            | ...  |    |    ...    ...     |
   +------+    +--------+            +------+    +----+----+----+----+
   高耸入云的曼哈顿细长大楼             宽 4 字节、高约 10 亿行的规整表格
```

第一种画法是画一个只有 1 字节宽、却高达 $2^{32}$ 行的长条。这就像曼哈顿岛上那些超细超高的新式摩天大楼，虽然直观反映了“按字节编址”，但并不利于我们观察 32 位整型数据的结构。

第二种画法则是我们最常用的标准模型：画一个 4 字节（即 1 个字，Word）宽、高为 $2^{30}$ 行（约 10 亿行）的矩阵。两者的乘积面积完全一致，但第二种模型清晰地展现了每 4 个字节如何捆绑为一个字单元。

当一个 32 位的数据（4 个字节）要从寄存器塞进这片内存网格时，一个绕不开的关键问题随之而来：这 4 个字节究竟应该按照什么次序排列？这就是经典的**大端序（Big-Endian）**与**小端序（Little-Endian）**之争。

> **定义**：
> - **最高有效字节（MSB, Most Significant Byte）**：代表数值权重最大的高位字节（在书写十六进制数的最左端）。
> - **最低有效字节（LSB, Least Significant Byte）**：代表数值权重最小的低位字节（在书写十六进制数的最右端）。
> - **小端序（Little-Endian）**：将最低有效字节存放在最低的内存地址处（即 "Little End" 在前）。
> - **大端序（Big-Endian）**：将最高有效字节存放在最低的内存地址处（即 "Big End" 在前）。

RISC-V 架构坚定地采用了**小端序**。

为了彻底摆脱抽象概念的混淆，我们可以看看现实生活中的绝妙类比：

```text
端序概念的生活映射对照：

1. 国际标准日期 (ISO 8601)：
   2026-09-29  ==> 年(最大权重) 在最前，日(最小权重) 在最后【大端序】
   这是最理智的文件命名格式，电脑按字典序排序一万年都不会乱。
   
2. 某些国家的日常日期：
   29/09/2026  ==> 日(最小权重) 在最前，年(最大权重) 在最后【小端序】
   (至于美国习惯的 09/29/2026 月/日/年，则是把次要权重塞在最前面的混乱产物)。

3. Java 包名规范：
   org.my.package.HelloWorld ==> 最顶层域在左，类名在右【大端序】。

4. 东方人名习惯：
   姓氏在先，名字在后 ==> 家族大类别在前，个体区分在后【大端序】。

5. 吃披萨的习惯：
   从薄薄的切尖小头开始吃【小端序】 vs 从厚实的饼边大头开始吃【大端序】。
```

在 RISC-V 的小端世界里，当一个 32 位寄存器的数据平铺进内存时，最右边的低位字节直接对应起始的低地址字节单元。这种直观的对称性为我们在寄存器与内存之间搬运数据提供了极大的便利。

### 字级数据传输：加载、存储与语法的唯一特例

现在我们正式来解决 C 语言中的经典数组操作：

```c
int a[100];
g = h + a[3];
```

> **注意**：局部变量数组 `a[100]` 在函数执行时是分配在操作系统的**栈区（Stack）**之上的。栈负责管理局部的动态空间；只有通过显式调用 `malloc` 分配的内存，才会被安置在堆区（Heap）。

为了完成 `g = h + a[3]`，CPU 必须做两件事：
1. 跑一趟萨克拉门托，把 `a[3]` 从内存里抓出来，暂存到某个临时寄存器中；
2. 在 CPU 内部用加法器把它与 `h` 所在的寄存器相加，把结果写入代表 `g` 的寄存器。

这就引出了我们今天的第一对核心操作——**加载（Load）**与**存储（Store）**。请务必牢牢记住这句口诀：

> **核心口诀**：**Load From, Store To**（从内存加载到寄存器；从寄存器存储到内存）。

#### 加载字指令：lw

负责把一个字从内存读取到寄存器的指令是 `lw`（Load Word）：

```text
lw rd, offset(rs1)
```

这里的语法呈现出一种全新的格式：`offset(rs1)` 称为**基址加偏移寻址（Base + Offset Addressing）**。
- `rs1` 是基址寄存器，存放着目标数据结构的基准指针（比如数组 `a` 的起始内存地址，假设存放在 `x15`）。
- `offset` 是一个硬编码在指令中的常数偏移量（以字节为单位）。
- CPU 访问的真实内存物理地址为：$\text{Address} = R[rs1] + \text{offset}$。

在 `g = h + a[3]` 中，为什么偏移量是 12 而不是 3？
因为在 C 语言中，`int` 占据 4 个字节。数组的索引计算必须乘上元素大小：
- `a[0]` 的地址是：$\text{Base} + 0$
- `a[1]` 的地址是：$\text{Base} + 4$
- `a[2]` 的地址是：$\text{Base} + 8$
- `a[3]` 的地址是：$\text{Base} + 12$

因此，对应的完整汇编指令序列为（假设 `h` 在 `x21`，`g` 在 `x20`，临时存放使用 `x10`）：

```assembly
lw  x10, 12(x15)    # 从 (x15 + 12) 处的内存加载 a[3] 到临时寄存器 x10
add x20, x21, x10   # g = h + a[3]，结果覆盖 x20
```

```text
数据流向 (lw)：
内存地址 [R[x15] + 12] -------------(拉取数据)-------------> 目标寄存器 R[x10]
        (右侧)                                                    (左侧)
```

在 `lw` 中，数据的流动完全符合人们对数学方程的认知：从右侧参数计算出内存位置，拉取数据，覆盖左侧的目标寄存器。

#### 存储字指令：sw 与语法的唯一特例

如果接下来的 C 代码要求我们把计算结果存回数组：

```c
a[10] = g;
```

因为索引是 10，对应的字节偏移量就是 $10 \times 4 = 40$。我们需要使用存储字指令 `sw`（Store Word）：

```assembly
sw x20, 40(x15)     # 把寄存器 x20 中的值存入内存地址 (x15 + 40)
```

> **易错点**：**`sw` 是几乎所有常见 RISC-V 指令中唯一的语法特例！**
> 在通常的指令（包括 `add`, `addi`, `lw`）中，数据流向永远是从右侧的参数流向左侧的目标寄存器（覆盖左边）。
> 然而在 `sw rs2, offset(rs1)` 中，虽然书写格式同样是把寄存器写在左边、括号地址写在右边，但它的数据流动方向却是**反转的**——它将左侧源寄存器 `rs2` 的内容，向右推送到内存地址中！

```text
数据流向 (sw)：
源寄存器 R[x20] -----------------(推送数据)-----------------> 内存地址 [R[x15] + 40]
    (左侧)                                                        (右侧)
```

千万不要因为格式的一致性而误以为 `sw` 是在向寄存器写入数据。请时刻在脑海里复诵：**Store To Memory**，存储指令是在把寄存器推向右边的内存深处。

### 内存对齐规则与总线错误的十六进制判据

当我们讨论加载或存储一个 4 字节的字时，有一个苛刻的前提条件始终悬在头顶——**内存对齐（Word Alignment）**。

> **定义**：**字对齐（Word Alignment）**要求任何 32 位整型数据的起始内存地址，必须能够被 4 整除（即地址是 4 的整数倍）。

回到我们把内存画成 4 字节宽表格的场景：一个整齐的 32 位字，必须严丝合缝地填满矩阵中的单独某一行。

```text
对齐与非对齐对比：

      合法的字对齐读取                     非对齐读取 (引发总线错误)
   字节3  字节2  字节1  字节0            字节3  字节2  字节1  字节0
 +------+------+------+------+         +------+------+------+------+
 | [====== 完整一个字 ======] |  0x00   |      |      | [====  0x00
 +------+------+------+------+         +------+------+------+------+
 |                            |  0x04   | ====] |      |      |  0x04
 +------+------+------+------+         +------+------+------+------+
 (数据在一行内完整取走)                 (数据横跨两行，宛如把披萨切成碎块)
```

这就好比切披萨：披萨必须完整地装在一个打包盒（一行）里，绝对不能一半露在盒外、另一半塞在下一个盒子里。如果硬件设计强制要求对齐，而你的程序试图从一个不是 4 的倍数的地址去执行 `lw` 或 `sw`，底层的硬件控制器就会立即拒绝响应，向系统抛出致命异常——**总线错误（Bus Error）**。

在实际代码调试中，如何一眼看穿某个地址是否会引发总线错误？这里有一条必须牢记的**十六进制末位判据（黄金法则）**：

> **结论**：在十六进制表示下，任何能被 4 整除的字对齐地址，其最右侧的最后一位十六进制数只能是：
> `0`、`4`、`8` 或 `C`（对应二进制末两位必为 `00`）。

如果底层程序报出 Bus Error，不要慌张，直接去检查报错的访存地址。只要最右一位是 1、2、3、5、6、7、9、A、B、D、E、F 中的任意一个，就可以 100% 断定是指针与偏移量相加后破坏了字边界对齐。

### 字节级数据传输与黄油涂抹法则

现实中不仅有 4 字节的整数，还有处理文本字符（ASCII 占 1 字节）或多媒体数据的单字节整型（C 语言中的 `int8_t` / `uint8_t`）。如果我们想按单字节读取内存，该怎么办？

就像童年动画片《芝麻街》里的“字母人（Letterman）”喜欢把胸口的字母揭下来换成另一个字母一样，RISC-V 体系的设计同样极为规整：我们只需把指令末尾代表字长（Word）的字母 `w`，直接替换为代表字节（Byte）的 `b`！

这就派生出了字节级数据传输指令：`lb`、`lbu` 与 `sb`。

由于内存本质上就是按字节线性编址的，任意相邻的单元地址都是合法的字节地址。因此，**字节级传输完全不受字对齐的限制**，任何整数地址都可以自由读写单字节，绝不会引发总线错误。

然而，这也随之暴露出了一个新的矛盾：**我们的寄存器整整有 32 位（4 字节宽），但从内存只拉进来了 8 位（1 字节），该如何安放？剩下的 24 位（3 个字节）又该如何填补？**

```text
32 位寄存器的字节填充难题：

  31                   15          7          0
+---------------------+-----------+-----------+
| ? ? ? ? ? ? ? ? ? ? | ? ? ? ? ? | 读入的字节|
+---------------------+-----------+-----------+
         高 24 位究竟该怎么填？        放最右端(LSB)
```

首先，读入的单字节始终被安置在寄存器最右端的最低有效字节（位 7 到 0）。
至于高 24 位应该放 0、放 1，还是随意丢弃？这取决于我们读入的数据究竟是有符号数还是无符号数。

#### 有符号加载与黄油涂抹法则：lb

假设我们从内存读取的是一个 8 位有符号整数（`int8_t`），其取值范围在补码下是 $-128$ 到 $+127$。

如果读入的值恰好是 $-128$，其 8 位补码二进制表示为：`1000 0000`（十六进制 `0x80`）。
如果我们图省事，直接在高 24 位全部填入 `0`，这个 32 位寄存器的值就会变成：
`0x00000080`，这在 32 位整数下代表的是正 $+128$！一个负数被硬生生读成了正数，这无疑是灾难性的逻辑崩溃。

再比如读入 $-1$，其 8 位二进制为 `1111 1111`（十六进制 `0xFF`）。若高位补零，就会变成正 255。

为了在位宽扩充后严格保全数值原本的正负号与大小，硬件必须执行**符号扩展（Sign Extension）**：

> **比喻**：**英式松饼与黄油涂抹法则（Butter Spreading）**
> 就像早上烤英式松饼，你在松饼的一侧放上一大团黄油，然后拿黄油刀用力一抹，把这团黄油顺畅地刮平铺满整张松饼。
> 当 `lb` 从内存拿到 8 位数据时，它会一把揪住这个字节的最高位（第 7 位符号位），把它像黄油一样，一路向左“涂抹”复制到高 24 位的每一个比特上：
> - 如果符号位是 `1`，高 24 位全部抹成 `1`；
> - 如果符号位是 `0`，高 24 位全部抹成 `0`。

```text
符号扩展的“涂黄油”过程 (以 -128 为例)：

内存读出 (8位):                        [ 1 0 0 0 0 0 0 0 ]
                                         ^ 最高位为 1

向左刮刀涂抹:  <========================= 复制符号位
最终寄存器 (32位): [ 11111111 11111111 11111111 10000000 ] (0xFFFFFF80 == -128)
```

如此一来，`-128` 变成了 `0xFFFFFF80`，在 32 位补码体系下依然精准地表示 $-128$；`-1` 变成了 `0xFFFFFFFF`，依然是坚挺的 $-1$。指令 `lb`（Load Byte）默认执行的就是符号扩展。

#### 无符号加载与零扩展：lbu

如果程序读取的是无符号数值（如 ASCII 字符或图像灰度像素），数值本身不存在负号，255 就是 255。此时如果继续涂抹符号位，就会误把原本的大正数涂成负数。

为此，RISC-V 专门提供了 `lbu`（Load Byte Unsigned）指令。它的机制极其纯粹——无论读入字节的最高位是什么，高 24 位一律执行**零扩展（Zero Extension）**，无条件全部清零。

#### 为什么硬件里没有 sbu 指令？

在学完 `lb` 与 `lbu` 后，很多敏锐的同学都会顺理成章地提问：既然加载有无符号的 `lbu`，那存储指令里为什么只有 `sb`，却找不到任何一条 `sbu`（Store Byte Unsigned）？

这并非设计者的疏忽，而是体系结构上的一记妙笔。请看存储字节指令 `sb` 的实际物理动作：

```text
寄存器 R[rs2] (32 位):  [  高 24 位 (完全忽略)  |  低 8 位 (有效数据)  ]
                                                     |
                                                     | (只搬运这 8 位)
                                                     v
内存目标单元 (1 字节):                      [ 8 位物理存储单元 ]
```

当执行 `sb rs2, offset(rs1)` 时，CPU 只做一件事：精准提取源寄存器最右边的低 8 位，跨越总线塞入指定的内存字节单元中。它根本不去触碰相邻的任何字节，在内存端也完全不存在“空缺的高 24 位需要填充”这回事。

无论这个字节在寄存器里原本代表的是有符号数还是无符号数，写入物理内存的都只是那相同的 8 个比特（bit 7:0）。既然根本不需要做任何高位扩展，`sbu` 自然就毫无存在的物理基础。

### 本讲提到的题目

在课程的尾声，为了检验大家对端序、数据流向以及扩展法则的掌握程度，课堂上组织了两次经典的交互练习。这两道题目极为典型地揭示了初学者容易踩坑的盲区。

#### 题目一：加载、端序与符号扩展综合追踪

**【代码片段】**
假设基址寄存器 `x5` 中已经保存了一个合法的、按字对齐的内存地址。请单步追踪执行以下三条汇编指令：

```assembly
addi x11, x0, 0x39C    # 指令 1
sw   x11, 0(x5)        # 指令 2
lb   x12, 0(x5)        # 指令 3
```

**【问题】**
当执行完第 3 行指令后，目标寄存器 `x12` 中的最终十六进制数值是多少？

**【解析与逐步推演】**
1. **分析指令 1：`addi x11, x0, 0x39C`**
   将立即数 `0x39C` 写入 `x11`。在 32 位寄存器中，完整的十六进制表示为：
   `R[x11] = 0x0000039C`。
   此时最右端的最低有效字节是 `0x9C`，次低字节是 `0x03`，其余高位字节均为 `0x00`。

2. **分析指令 2：`sw x11, 0(x5)`**
   根据存储指令语义，这是将 `x11` 的内容推送写入到小端序内存中。
   由于 RISC-V 采用小端序，**最低有效字节优先写入最低内存地址**：
   - 内存地址 `0(x5)` 写入低字节：`0x9C`；
   - 内存地址 `1(x5)` 写入次低字节：`0x03`；
   - 内存地址 `2(x5)` 与 `3(x5)` 写入高字节：`0x00`。

3. **分析指令 3：`lb x12, 0(x5)`**
   这里有两个极其关键的考点，也是全班同学最容易失分的地方：
   - **考点 A（端序读取）**：访问的地址是 `0(x5)`，抓取出来的单字节正是上一步写入的 `0x9C`。
   - **考点 B（符号扩展）**：调用的指令是 `lb` 而**不是** `lbu`！这意味着必须启动黄油涂抹法则。
     我们把十六进制 `0x9C` 拆开观察其 8 位二进制形态：
     `9` 对应 `1001`，`C` 对应 `1100`，组合起来即为 `1001 1100`。
     注意观察它的最高位（bit 7）：它是 `1`！这表明它代表一个负数。
     既然最高位是 1，`lb` 就会挥动刮刀，将高 24 位全部涂抹置为 `1`。在十六进制下，每 4 个二进制位 `1111` 对应一个字符 `F`。因此，高 24 位被全部填补为 6 个连续的十六进制 `F`。

**【最终答案】**
`x12` 的最终数值为：**`0xFFFFFF9C`**。

> **提示**：很多同学在课堂答题时误选了 `0x0000009C`，这就是遗忘了 `lb` 与 `lbu` 之间符号扩展的致命区别；还有同学混淆了大小端，把高地址的 `0x00` 读了出来。牢记：**小端寻址看最低字节，有符号加载看最高比特**。

#### 题目二：C 语言指针解引用赋值的汇编转换

**【背景与题目】**
在 C 语言中，有一行极具代表性的指针赋值操作：

```c
*x = *y;
```

已知指针变量 `x`（存放目标地址）保存在寄存器 `x3` 中，指针变量 `y`（存放源数据地址）保存在寄存器 `x5` 中，二者所指向的数据均为标准的 32 位整型数据。

**【问题】**
能否只用一条 RISC-V 指令完成这个操作？如果不能，应该如何翻译？

**【解析与推演】**
1. **架构原则审视**：
   RISC-V 属于纯粹的**加载-存储架构（Load-Store Architecture）**。在 RISC 哲学中，算术与数据处理逻辑只能在寄存器之间展开，**硬件绝对不支持从内存单元直接搬移到另一块内存单元**。
2. **两步走战略**：
   要实现 `*x = *y`，必须分为两个独立阶段，并引入一个临时寄存器（例如选择 `x8`，并假设其可以被安全覆盖）：
   - **第一阶段（读取源端）**：按照指针 `y` 的指示，从内存把数据加载进 CPU。口诀为 **Load From**，对应指令：
     ```assembly
     lw x8, 0(x5)    # 将指针 y 指向的内存字加载到临时寄存器 x8
     ```
   - **第二阶段（写入宿端）**：把刚才拿到寄存器的数据推送到指针 `x` 指向的内存位置。口诀为 **Store To**，对应指令：
     ```assembly
     sw x8, 0(x3)    # 将临时寄存器 x8 中的数据存入指针 x 指向的内存
     ```

**【最终结论】**
不能用一条指令完成，必须使用中间寄存器中转，按先后顺序执行两条指令：先 `lw x8, 0(x5)`，后 `sw x8, 0(x3)`。
这也正是精简指令集与 x86 等复杂指令集（CISC）在底层实现上的核心分水岭。
