## RISC-V 条件判断与逻辑运算
> 对应块：BLK10 | 覆盖分集：P10 | 块标题（分集名）：《第 09 讲 - RISC-V 条件判断》

在进入今天的主题前，我们先快速把视野拉回上一讲。上节课我们讨论了如何与内存打交道——怎样把数据写入内存（store to RAM），又怎样把数据读出到寄存器（load from RAM）。在 32 位的寻址空间中，我们拥有整整 4 GiB 的内存可以使用。为此，我们引入了五条核心指令：字级存取的 `lw` 和 `sw` 每次搬运 4 个字节；字节级加载的 `lb` 和 `lbu` 每次只搬运 1 个字节。

这里有个细节大家务必刻在脑子里：寄存器是 32 位（4 字节）宽的，而 `lb` 或 `lbu` 只从内存抓取 1 个字节。这个字节自然是塞进目标寄存器的最低有效字节（least significant byte）里，但高位的其余 3 个字节怎么办？对于有符号加载 `lb`，我们抓取该字节的最高位（符号位），像拿一大块黄油抹在英式玛芬面包上一样，把这个符号位一路向高位抹平（sign-extend）；而对于无符号加载 `lbu`，我们则纯粹用零填满那些高位空缺（zero-extend）。

但退一步看，到目前为止，我们手里搭建起来的其实是一个“极快但极蠢的计算器”。它只能做算术运算，能做加法、减法，能在内存和寄存器之间搬运数据，甚至连乘法都还没学。更致命的是，它没有任何自主决策能力。遇到交叉路口，是该走左边还是右边？面对两段逻辑，是执行这一段还是那一段？如果你连高级语言里最基础的 `if` 语句都翻译不出来，这台机器就谈不上任何智能。今天这一讲，我们的核心使命就是给系统注入灵魂——通过条件分支与逻辑操作，让处理器具备做决定的能力。

### 控制流的本质与汇编线性化

高级语言赋予了我们极其优雅的语法结构：嵌套的花括号、`if-else`、多重嵌套的 `for` 循环与 `while` 循环。但在底层硬件和汇编的世界里，这些树状层级结构统统不复存在。

汇编语言是彻底线性化的（linearized）。所有的指令一行接一行地紧密排列，物理上平铺在内存空间之中。

```text
       低地址 (0x00000000)
    +------------------------+
    |   Instruction 0        |  <-- PC
    +------------------------+
    |   Instruction 1        |  <-- PC + 4
    +------------------------+
    |   Instruction 2        |
    +------------------------+
    |         ...            |
    +------------------------+
    |   Target Instruction   |  <-- 分支跳转目标 (Branch Target)
    +------------------------+
       高地址 (0xFFFFFFFF)
```
*读图说明：程序计数器 PC 默认沿低地址向高地址顺序步进（PC + 4），遇到分支跳转时被直接赋予目标地址，改变控制流方向。*

在 CPU 内部，有一个非常关键的寄存器叫做程序计数器（Program Counter，简称 PC）。PC 内部存储的地址，精确指向当前时钟周期正在被读取和执行的那条指令。

在没有控制流跳转的正常情况下，CPU 按照物理顺序自顶向下依次执行指令。因为 RISC-V 的每条基础指令都严格占据 4 个字节，所以每执行完一条指令，PC 的指针就自动加上 4：

$$PC \leftarrow PC + 4$$

所谓的“执行分支”（Take a branch），在硬件层面其实只有一层含义：强行将 PC 寄存器的值修改为一个全新的地址，使得下一个时钟周期 CPU 转而从新的地址行拉取指令，从而开启一段全新的执行序列。

为了在汇编代码中指定跳转的目的地，我们引入了标签（Label）。

> **定义**：标签（Label）是汇编语言中为特定内存指令地址赋予的符号名称。它由英文字符构成，结尾紧跟一个英文冒号（例如 `Exit:` 或 `Loop:`），在汇编阶段会被汇编器解析为一个具体的物理地址偏移量。

你可以把标签想象成 BASIC 语言里的行号，或者是 HTML 网页里的锚点链接。它在代码里并不占据任何可执行的机器码空间，仅仅是告诉汇编器：“记住这个位置，以后如果有人要跳到这里，就把这个位置的地址填进去。”

> **提示**：在 C 语言中虽然也保留了 `goto` 和标签的语法，但除非你是有着极高架构把控力的专家，否则日常高级语言开发中绝对不要手写标签。而在汇编语言中，标签则是我们构建循环、分支等控制结构的唯一基石。

### 条件分支指令与 RISC 极简主义

我们来看 RISC-V 中最基础的两条决策指令：`beq` 与 `bne`。

```assembly
beq rs1, rs2, Label    # Branch if Equal: 若 (rs1 == rs2) 则跳转到 Label
bne rs1, rs2, Label    # Branch if Not Equal: 若 (rs1 != rs2) 则跳转到 Label
```

这两条指令的执行语义非常清晰：
- 对于 `beq`：硬件取出寄存器 `rs1` 和 `rs2` 中的 32 位数值进行比较。如果两者的数值完全相等，控制流发生跳转，PC 被更新为 `Label` 指向的地址；如果不相等，则条件不满足，CPU 顺序落入下一行执行，即 $PC \leftarrow PC + 4$。
- 对于 `bne`：如果两寄存器中的数值不相等，则发生跳转更新 PC；若相等，则顺序落入下一行。

这里必须强调：指令里指定的 `rs1` 和 `rs2` 是各占 5 位的寄存器索引号（范围在 0 到 31 之间）。比较的不是“寄存器编号是否相同”，而是比较“这两个寄存器内部存放的 32 位数值是否相同”。当然，如果你写 `beq x2, x2, Label`，因为同一个寄存器里的值必然等于自身，该分支就会百分之百无条件发生跳转。

除了相等性判定，程序中极大量的逻辑依赖于大小比较。RISC-V 提供了小于分支 `blt`（Branch if Less Than）以及大于等于分支 `bge`（Branch if Greater than or Equal to）：

```assembly
blt  rs1, rs2, Label   # 若 rs1 < rs2，则跳转到 Label
bge  rs1, rs2, Label   # 若 rs1 >= rs2，则跳转到 Label
bltu rs1, rs2, Label   # 无符号比较：若 rs1 < rs2，则跳转到 Label
bgeu rs1, rs2, Label   # 无符号比较：若 rs1 >= rs2，则跳转到 Label
```

看到这里，敏锐的同学一定会提出两个非常深刻的架构设计问题。

#### 为什么大小比较必须区分有符号与无符号，而相等比较却不需要？

我们来做一次极端的数值推演。假设我们让寄存器 $A$ 存放全 1 比特串（`0xFFFFFFFF`），让寄存器 $B$ 存放全 0 比特串（`0x00000000`）。

如果把这两个数作为有符号补码来解读：
- 全 1 表示数值 $-1$；
- 全 0 表示数值 $0$；
- 显然有 $-1 < 0$，即 $A < B$。

但如果把这两个数作为无符号整数来解读：
- 全 1 表示无符号最大正整数 $2^{32} - 1$（4,294,967,295）；
- 全 0 依然是数值 $0$；
- 此时有 $2^{32} - 1 > 0$，即 $A > B$。

> **结论**：同一个物理比特序列，在有符号和无符号的数学诠释下，大小关系完全倒转！因此硬件在做比较时，必须明确知道程序员意图执行的是有符号比较还是无符号比较。这就是为什么架构必须同时提供 `blt` 和 `bltu`。

那为什么相等判断不需要无符号版本 `bequ` 呢？

因为相等的本质是“比特位完全一致”（bits == bits）。寄存器里哪怕存的是 $-1$、浮点数的非数（NaN），还是一个纯字符串，只要这 32 个位置上的电平高低一模一样，它们就是相等的。数据本身在底层是没有类型的，类型仅仅存在于解读它们的操作符视角中。因此，根本不需要专门设计一条多余的 `bequ` 指令。

#### 为什么没有大于分支 bgt 与小于等于分支 ble？

翻开 RISC-V 指令手册，你会发现根本找不到 `bgt`（branch if greater than）和 `ble`（branch if less than or equal to）。这是设计者的疏忽吗？

绝对不是。请时刻牢记 RISC 的核心哲学：Reduced Instruction Set Computer（精简指令集计算机）。它的最高信条是——**如无绝对必要，绝不增设一条新指令**。只要能用现有指令轻松组合出来的功能，硬件就坚决不造专用的解码电路。

在数学逻辑上：
- $A > B$ 完全等价于 $B < A$；
- $A \le B$ 完全等价于 $B \ge A$。

如果你手写汇编时需要表达 `if (s1 > s2)`，你不需要祈求一条 `bgt` 指令，只需在调用 `blt` 时把两个操作数的位置轻轻对调一下即可：

```assembly
blt s2, s1, Label      # 等价于如果 s1 > s2，则跳转到 Label
```

同样地，要实现 `s1 <= s2`，直接调换寄存器顺序并调用 `bge` 即可：

```assembly
bge s2, s1, Label      # 等价于如果 s1 <= s2，则跳转到 Label
```

仅仅颠倒一下操作数的位置，就能在硬件中省去整套 `bgt` 和 `ble` 的指令解码逻辑，这就是 RISC 的美感与克制。

#### 无条件跳转 j 与指令编码空间的权衡

我们在代码中经常需要无条件直接跳到某个地方，RISC-V 提供了无条件跳转指令：

```assembly
j Label                # 无条件跳转：直接将控制流引向 Label
```

有人会问：“既然 RISC 崇尚极致精简，既然前面说过 `beq x0, x0, Label` 永远为真，那我们为什么不直接用 `beq` 实现无条件跳转，反而要新增一条 `j` 指令呢？”

这背后隐藏着硬件编码空间的深刻博弈：

```text
B-Format: [ imm[12|10:5] | rs2(5) | rs1(5) | funct3(3) | imm[4:1|11] | opcode(7) ]
           ^^^^^^^^^^^^^   ------   ------               ^^^^^^^^^^^^
           分支指令：为了存放 rs1 和 rs2 消耗了 10 位，立即数偏移量受限

J-Format: [ imm[20|10:1|11|19:12] | rd(5) | opcode(7) ]
           ^^^^^^^^^^^^^^^^^^^^^^
           跳转指令：没有两个源寄存器开销，留给目标地址偏移量的位宽极大
```
*读图说明：32 位定长指令中，操作数字段越少，留给跳转偏移量立即数的比特位就越多，寻址范围呈指数级扩展。*

在 32 位的固定指令长度限制下，`beq` 必须分配 $5 + 5 = 10$ 个比特位来指定 `rs1` 和 `rs2`，这导致剩下的立即数字段（保存跳转距离）位宽非常狭窄，使得分支跳转只能在当前 PC 的较小范围内发生短程跳转；而无条件跳转 `j` 根本不需要读取两个寄存器，它可以把宝贵的比特位全部让给立即数字段，从而实现跨越超大内存范围的长程跳转。

### 经典控制结构的汇编翻译套路

理解了分支指令后，我们来看如何将高级语言中的典型分支结构“手工编译”为汇编代码。这里需要建立起一种独特的“逆向思考模式”。

#### 单分支 if 语句的逆向跳过策略

来看一段最基础的 C 语言条件分支：

```c
if (i == j)
    f = g + h;
```

假设变量与寄存器的分配关系为：`f -> x10`, `g -> x11`, `h -> x12`, `i -> x13`, `j -> x14`。

初学者往往下意识地寻找 `beq`，但直觉会在这里撞墙。因为在汇编的线性执行流中，如果不发生跳转，CPU 会顺理成章地执行下一行。我们希望“当 $i == j$ 时执行加法”，这意味着“当 $i 
e j$ 时，绝不能执行加法，必须跳过它”。

因此，我们在看到双等号 `==` 时，汇编中应该第一时间条件反射地写出不等分支 `bne`：

```assembly
    bne  x13, x14, Exit    # 如果 i != j，跳过加法块直奔 Exit
    add  x10, x11, x12     # then 分支：仅在 i == j 时自然落入执行 (f = g + h)
Exit:
```

> **结论**：汇编实现 `if` 结构的黄金法则是“逆向检查”——条件不成立时，分支跳走（branch around）；条件成立时，顺序穿透（fall through）执行目标代码块。

#### 双分支 if-else 的跳过与穿透保护

如果带有 `else` 分支，情况又会怎样？

```c
if (i == j)
    f = g + h;
else
    f = g - h;
```

我们按照逆向逻辑翻译：如果 $i 
e j$，我们跳转到 `Else` 标签；如果 $i == j$，我们顺流而下执行加法。

但注意！加法执行完之后，千万不能直接往下走，否则紧接着就会顺理成章地执行减法，把 `f` 的值错误地覆盖掉！`if-else` 的语义是互斥的二选一，绝不可能两者都执行。因此，在 `then` 块的末尾，必须插入一条无条件跳转 `j Exit`，跳过 `else` 块：

```assembly
    bne  x13, x14, Else    # 若 i != j，跳到 Else 处执行减法
    add  x10, x11, x12     # then 块：f = g + h
    j    Exit              # 关键！加法执行完毕，必须强制跳过 Else 块
Else:
    sub  x10, x11, x12     # else 块：f = g - h
Exit:
```

```text
                 +-------------------+
                 | bne x13, x14, Else|
                 +---------+---------+
                           |
                 [相等]    |    [不相等]
                   +-------+-------+
                   |               |
                   v               v
          +-----------------+    +-----------------+
          | add x10,x11,x12 |    | Else:           |
          +--------+--------+    | sub x10,x11,x12 |
                   |             +--------+--------+
                   v                      |
          +-----------------+             |
          | j Exit          |             |
          +--------+--------+             |
                   |                      |
                   +-------+       +------+
                           |       |
                           v       v
                         +-----------+
                         | Exit: ... |
                         +-----------+
```
*读图说明：执行 then 分支后必须通过无条件跳转绕过 else 分支代码，确保互斥执行。*

> **易错点**：千万不能遗漏 `then` 块末尾的 `j Exit`。如果没有这条跳转，一旦命中 $i == j$，CPU 就会先执行加法，随后顺序穿透执行减法，导致运算结果彻底被减法覆盖破坏。

#### 指令行数与性能直觉

有同学问：“我能不能反过来写？用 `beq` 跳到 `Then` 标签，当前位置直接放减法？”

当然可以，逻辑完全等价。但在底层汇编编写中，我们极度关注**指令的物理条数**。

在高级语言中，代码行数可能只是视觉差异；但在处理器执行时，每一条汇编指令都需要消耗时钟周期。如果你在一个极其高频的循环体内，一段实现是 4 条指令，另一段等价实现是 8 条指令，那么 8 条指令的代码就会实打实地慢上一整倍！

更重要的是，能用寄存器解决的运算，绝不要轻易去碰内存。访问寄存器只需不到 1 个纳秒，而访问一次内存就如同从伯克利驱车去萨克拉门托（Sacramento），需要经历漫长的数百个周期等待。精简指令行数、杜绝多余的内存存取，是底层性能优化的生命线。

### 综合实战：数组累加器与循环翻译

掌握了分支与跳转，我们就可以把更复杂的 C 语言循环结构搬上舞台。来看一个经典的累加器（Accumulator Pattern）程序：

```c
int A[20];
int sum = 0;
for (int i = 0; i < 20; i++)
    sum += A[i];
```

这段代码的核心功能非常纯粹：遍历拥有 20 个整型元素的数组 `A`，将所有元素依次累加到变量 `sum` 中。

在动笔写汇编前，我们先规划好寄存器分配：
- `x8`：存放数组 `A` 的基地址（Base Address）；
- `x9`：指针变量（Pointer $p$），初始化为数组首地址，循环中不断后移；
- `x10`：累加和 `sum`，初始化为 0；
- `x11`：循环计数器 `i`，初始化为 0；
- `x12`：临时寄存器，用来暂存从内存读出的当前元素 `A[i]`；
- `x13`：常量 20，用于循环终止条件判断。

```assembly
    # 1. 初始化阶段
    addi x9,  x8, 0        # 将数组基地址拷贝给活动指针 p (x9 = &A[0])
    addi x10, x0, 0        # sum = 0
    addi x11, x0, 0        # i = 0
    addi x13, x0, 20       # x13 = 20 (循环边界常量)

Loop:
    # 2. 边界检查 (进入循环前先检查，保证符合 for 循环语义)
    bge  x11, x13, Done    # 如果 i >= 20，跳出循环到 Done

    # 3. 循环体：加载数组元素并累加
    lw   x12, 0(x9)        # 从指针当前指向的地址加载一个字：x12 = *p
    add  x10, x10, x12     # sum += x12

    # 4. 指针步进与索引自增
    addi x9,  x9,  4       # 指针向后移动 4 个字节 (指向下一个 int)
    addi x11, x11, 1       # i++

    # 5. 回路闭环
    j    Loop              # 跳回循环开头进行下一轮判断

Done:
```

这段代码蕴含了四个极其关键的体系结构与汇编细节：

#### 为什么不能直接写 lw x12, x11(x9)？
高级语言中我们可以写 `A[i]`，初学者自然会想：“既然 `x9` 是基地址，`x11` 是偏移量 `i`，我能不能直接写 `lw x12, x11(x9)` 呢？”

绝对不行！RISC-V 的 `lw`（I-type）格式非常严格：括号外面的偏移量**只能是一个编译期确定的立即数常数**，绝不允许放置寄存器。硬件层面根本没有支持两个寄存器相加寻址的 `lw` 指令格式。因此，我们必须手动维护一个指针寄存器 `x9`，每次在寄存器内部给它加上 4 个字节的偏移，然后在 `lw` 里使用固定的 `0(x9)` 进行基址寻址。

#### 为什么要把立即数 20 提前存入寄存器？
我们为什么不能直接写一条 `bge x11, 20, Done`？

原因依然是 RISC 架构原则：RISC-V 没有设计“寄存器与立即数比较并分支”的指令格式。因为要在一条 32 位指令内同时塞下分支判断操作码、比较寄存器、立即数数值以及目标跳转地址偏移量，编码位宽是无论如何放不下的。为了保护硬件解码的精简高效，必须先把 20 加载到通用寄存器 `x13` 中，再执行纯粹的寄存器间比较。

#### for 循环的先验条件语义
请务必观察 `Loop:` 标签之后的第一行代码：`bge x11, x13, Done`。

C 语言中 `for` 循环的严格语义是：**在每一次迭代进入之前，必须首先对条件进行判定**。如果初始条件不满足（比如传入数组长度为 0），循环体一次也不能执行。因此进入循环体之前，先拿 `i` 和 20 比较，一旦 `i >= 20`，立刻跳出到 `Done`。

#### 为什么必须使用临时寄存器 x12？
为什么我们要把数据先读入 `x12`，再通过 `add x10, x10, x12` 累加，而不是一步到位直接写 `lw x10, 0(x9)` 呢？

因为 `x10` 保存着前几轮迭代辛苦累加出来的 `sum`！如果直接把数据载入 `x10`，前面积累的加和瞬间被冲刷抹杀。必须先用一个临时寄存器接收内存数据，再合入累加和。

> **提示**：掌握了正向把 C 语言翻译为汇编的过程，你就同时掌握了反编译（Decompilation）的核心技能。在未来的工程排查或安全逆向中，给你一段无源码的二进制汇编指令，你同样能够根据指针步进、边界条件和寄存器流向，精准还原出底层的 C 语言业务逻辑。

### 纯比特视角与并行位逻辑运算

从现在开始，请大家在思维模式上做一个彻底的跳跃：**把寄存器里的 32 个比特，看作 32 个彼此完全独立的信号开关**。

它们不再是整数，不再是浮点数，也不再是 ASCII 字符。它们就是 32 盏并排悬挂的灯泡——高电平为 1（亮），低电平为 0（灭）。你可以用它们记录 32 个外设的状态，也可以用它们来精细操纵浮点数的指数位与尾数位。

RISC-V 提供了五条基础的位逻辑运算指令，涵盖寄存器-寄存器（R-type）和寄存器-立即数（I-type）两种形态：

| 指令助记符 | 运算类型 | 语法格式 | 硬件语义 |
| :--- | :--- | :--- | :--- |
| `and` / `andi` | 按位与 (Bitwise AND) | `and rd, rs1, rs2` | $rd \leftarrow rs1 \ \& \ rs2$ |
| `or` / `ori` | 按位或 (Bitwise OR) | `or rd, rs1, rs2` | $rd \leftarrow rs1 \mid rs2$ |
| `xor` / `xori` | 按位异或 (Bitwise XOR) | `xor rd, rs1, rs2` | $rd \leftarrow rs1 \oplus rs2$ |
| `sll` / `slli` | 逻辑左移 (Shift Left Logical) | `sll rd, rs1, rs2` | 将 $rs1$ 左移，低位补 0，写入 $rd$ |
| `srl` / `srli` | 逻辑右移 (Shift Right Logical) | `srl rd, rs1, rs2` | 将 $rs1$ 逻辑右移，高位补 0，写入 $rd$ |

这里必须强调硬件的并发威力：当你执行一条 `and` 指令时，底层硬件**并非**在运行一个处理 32 个位的软件循环！底层的算术逻辑单元（ALU）是由整整 32 个完全独立的物理 AND 逻辑门并行排开的。在短短一个时钟周期内，32 个比特位的与运算瞬间并发完成。

#### 掩码技术与宇宙的阴阳对偶

位逻辑运算最经典的工程应用就是构造掩码（Mask），用来精准提取、保留、置位或抹掉某些特定位。

`AND` 和 `OR` 在布尔世界中构成了完美的阴阳对偶（Duality）：
- **AND 的特性**：
  - 任何位与 `1` 相与，结果保持原值不变（$x \ \& \ 1 = x$）；
  - 任何位与 `0` 相与，结果被强制清零（$x \ \& \ 0 = 0$）。
  - 因此，`AND` 是用于**提取与保留**特定位、将不需要的位彻底屏蔽清零的绝佳工具。例如我们要保留寄存器的最低字节，抹去高 3 字节，只需施加掩码 `0x000000FF`：
    ```assembly
    andi x11, x10, 0xFF    # 保留最低 8 位，高 24 位全部清零
    ```
- **OR 的特性**：
  - 任何位与 `0` 相或，结果保持原值不变（$x \mid 0 = x$）；
  - 任何位与 `1` 相或，结果被强制置为 1（$x \mid 1 = 1$）。
  - 因此，`OR` 是用于**强制点亮、强制开启**某些标志位的最佳工具。

#### XOR 的绝技：条件反相器与 NOT 的缺席

细心的同学可能会纳闷：“既然有按位与、按位或，为什么 RISC-V 没有专门的按位取反指令 `not` 呢？”

答案全在异或（XOR）的奇妙数学性质之中。让我们推导一下异或的真值表：

$$x \oplus 0 = x$$

$$x \oplus 1 = \sim x$$

```text
       输入信号 y ------+
                       |
                       +-----\
                              )--- 输出 (x=0 时为 y; x=1 时为 NOT y)
                       +-----/
                       |
    控制信号 x --------+
```
*读图说明：XOR 门本质是一个受控条件反相器；控制端为 0 时原样输出，控制端为 1 时反转输出。*

这意味着什么？XOR 在物理上就是一个天然的**条件反相器**（Conditional Inverter）！
- 如果控制端送入 0，信号原封不动穿透出去；
- 如果控制端送入 1，信号被完全取反后输出！

既然如此，我们根本不需要增加任何专用取反硬件。如果我们需要对寄存器 `rs` 中的所有比特取反，只需要让它与全 1 进行异或即可！而在 32 位补码体系中，全 1 正好对应数值 $-1$（`0xFFFFFFFF`）：

```assembly
xori rd, rs, -1        # 等价于 rd = ~rs (按位取反)
```

一条简单的 `xori` 搭配立即数 $-1$，就优雅地完成了单目取反操作。RISC 极简主义在此展现得淋漓尽致。

#### 移位操作与算术右移的符号保护

移位操作常用于快速的位提取以及低成本的乘除法模拟：

- **逻辑左移（`sll` / `slli`）**：将寄存器里的比特整体向左平移，左边溢出的位被丢弃，右侧留出的空位一律无条件用 `0` 填补。左移 $k$ 位在数学上严格等价于乘以 $2^k$。比如将数值 2（二进制 `0010`）左移两位，变成 8（二进制 `1000`），就完成了一次极速的乘以 4 运算。
- **逻辑右移（`srl` / `srli`）**：将比特整体向右平移，右侧溢出位丢弃，左侧高位空出来的空缺一律补 `0`。

对于无符号数，逻辑右移能够完美模拟除以 $2^k$。但如果寄存器里存的是一个**负数**呢？

负数的最高位（符号位）是 1。如果使用逻辑右移在高位无脑填入 0，原本的负数瞬间变成了一个极其巨大的正数！数学意义被彻底摧毁。

为了解决这个问题，硬件引入了**算术右移（`sra` / `srai`，Shift Right Arithmetic）**。

> **定义**：算术右移（`sra` / `srai`）在向右平移比特时，左侧空出的高位由原始数据的**符号位（最高位）**进行填充（Sign Filling）。若原数为负（最高位为 1），则高位全补 1；若原数为正（最高位为 0），则高位全补 0。

例如对数值 $-1$（全 1 比特串）进行算术右移，由于高位源源不断地补充 1，移位后的结果依然是全 1，数值保持为 $-1$。

> **提示**：算术右移并不完全等于向零取整的整数除法。对于奇数负数（例如 $-3$），二进制补码表示为 `...11101`，算术右移 1 位后变成 `...11110`，数值为 $-2$。而 C 语言标准整除 $(-3) / 2$ 的结果是向零截断的 $-1$。算术右移实现的是向下取整（向负无穷取整），两者在奇数负数除法上存在微小的尾数差异。

### 计算机底层全貌：编译链、存储程序与伪指令

在结束控制结构与逻辑运算的讨论之前，我们把视线稍微拉远，观察程序在整个计算机系统中的生存图景。

#### 编译执行三步曲（CAL）

我们手写的 C 源码，最终是如何变成 CPU 上飞速运转的高低电平信号的？请记住这个标准工业流程 CAL：

```text
  [ C 源文件 (.c) ]
         |
         |  1. Compiler (编译器)
         v
  [ 汇编源码 (.s) ]
         |
         |  2. Assembler (汇编器)
         v
  [ 目标机器码 (.o) ]  +  [ 系统静态库 (.a) ]
         \                     /
          \                   /   3. Linker (链接器)
           v                 v
        [ 可执行文件 (a.out / elf) ]
```
*读图说明：C 代码经编译器转为汇编源码，经汇编器转为二进制目标机器码，最终经链接器拼装外部库生成独立可执行程序。*

1. **Compile（编译）**：编译器将高级语言转换为纯文本形态的汇编代码文件（`.s` 文件）；
2. **Assemble（汇编）**：汇编器将汇编助记符逐一翻译成 CPU 硬件唯一听得懂的 0 和 1 机器码（`.o` 目标文件）；
3. **Link（链接）**：链接器将多个目标文件以及系统库（比如数学库、标准 I/O 库）缝合在一起，最终打包生成能够被操作系统载入内存执行的单一可执行文件（在 Unix 传统中常默认命名为 `a.out`）。

#### 存储程序模型（Stored-Program Model）

这涉及计算机历史上最伟大的发明——冯·诺依曼存储程序模型。

在远古时代，像早期的专用电子玩具（比如 Mattel 玩具橄榄球游戏机），其硬件内部的逻辑是固化的，一台机器一生只能玩固定的规则。而现代计算机的本质颠覆在于：**程序代码和运行数据一视同仁，完全存放在同一片连续物理内存空间之中**！

内存就像一个由若干 4 字节宽构成的巨型储物柜，每一格既可以存放一个浮点数，也可以存放一个有符号整数，或者存放一条等待执行的 32 位机器指令。计算机只要从内存中加载不同的指令序列，就能在瞬间从一台音频播放器切换成一门三维图形渲染引擎。

但这种灵活性伴随着巨大的代价：**每一个时钟周期，CPU 都必须经由 PC 访问一次内存来抓取下一条指令**！哪怕你的算术指令在寄存器里跑得再快，CPU 取指依然必须去内存拉取。这再一次警示我们：尽量减少内存操作，后续课程我们会详细讨论高速缓存（Cache）是如何拯救这个瓶颈的。

#### 符号寄存器名称与伪指令语法糖

在实际开发中，天天记 `x0` 到 `x31` 会让人精神崩溃。因此，RISC-V 规范制定了一套官方的寄存器别名（ABI Names）。其中最常用的一组是：

> **定义**：`x10` 到 `x17` 这 8 个寄存器被赋予了符号别名 `a0` 到 `a7`（`a` 代表 Arguments）。它们是高级语言与汇编约定的标准传参契约。在调用函数时，调用者把入参塞进 `a0`~`a7` 中，函数执行完毕后，通常也把返回值通过 `a0`、`a1` 传回。

此外，汇编器为了方便开发者书写，还提供了一系列贴心的**伪指令（Pseudo-instructions）**：

- **数据复制 `mv rd, rs`**：
  硬件底层没有名为 `mv` 的指令。汇编器遇到 `mv rd, rs` 时，会自动将其翻译为：
  ```assembly
  addi rd, rs, 0
  ```
  讲师在这里特别吐槽了一句：这应该叫 `copy` 而不是 `move`！在 Unix 终端里 `mv` 会把源文件挪走，而这里的 `rs` 里的数据依然完好无损，它纯粹是一次值的复制。
- **加载立即数 `li rd, immediate`**：
  想要往寄存器里塞一个常数，无需纠结该用哪条加法指令，直接写 `li rd, 42`，汇编器会自动展开为等价的基址加载指令（如 `addi rd, x0, 42`）。
- **空操作 `nop`**：
  什么都不做，空耗一个周期。底层直接展开为 `addi x0, x0, 0`。因为目标是恒等于零的只读寄存器 `x0`，任何写入都会被硬件静默忽略，完美达成“空操作”的效果。

### 本讲提到的题目

在课堂尾声，讲师留了一道极具启发性的位逻辑综合思考题。

#### 题目描述

假设寄存器 `x10` 内部初始存放的 32 位十六进制数值为 `0x000034FF`，现依次执行以下三条 RISC-V 汇编指令：

```assembly
slli x12, x10, 0x10    # 逻辑左移十六进制 0x10 位 (十进制 16 位)
srli x12, x12, 0x8     # 逻辑右移十六进制 0x8 位 (十进制 8 位)
andi x12, x12, x10     # 将 x12 的当前值与原始 x10 的值进行按位与，存入 x12
```

请问：三条指令执行完毕后，寄存器 `x12` 中的最终十六进制数值是多少？

#### 逐步推导与位演算

我们以标准的 32 位十六进制格式，对每一步执行过程进行精确演算：

- **初始状态**：
  $$x10 = \mathtt{0x000034FF}$$

- **第一步：`slli x12, x10, 0x10`**
  - 注意立即数 `0x10` 是十六进制，转换为十进制是 $1 \times 16^1 + 0 = 16$；
  - 该操作将 `x10` 逻辑左移 16 位，即整整左移 4 个十六进制位（2 个字节），低位全部补零；
  - 移位结果写入 `x12`：
    $$x12 \leftarrow \mathtt{0x34FF0000}$$

- **第二步：`srli x12, x12, 0x8`**
  - 立即数 `0x8` 为十进制的 8；
  - 该操作将 `x12` 逻辑右移 8 位，即整整右移 2 个十六进制位（1 个字节），高位空出的位置全部补零；
  - 移位结果覆盖写入 `x12`：
    $$x12 \leftarrow \mathtt{0x0034FF00}$$

- **第三步：`andi x12, x12, x10`**
  - 将当前 `x12`（`0x0034FF00`）与原本的 `x10`（`0x000034FF`）进行按位与运算；
  - 我们把 32 位拆成 4 个字节，逐字节对照做按位与：
    - **最高字节（31~24位）**：`0x00 & 0x00 = 0x00`
    - **次高字节（23~16位）**：`0x34 & 0x00 = 0x00`
    - **次低字节（15~8位）**：`0xFF & 0x34 = 0x34`（任何字节与全 1 的 `0xFF` 相与保持原值）
    - **最低字节（7~0位）**：`0x00 & 0xFF = 0x00`（任何字节与全 0 的 `0x00` 相与强制清零）
  - 拼装 4 个字节的最终结果：
    $$x12 \leftarrow \mathtt{0x00003400}$$

#### 最终答案
寄存器 `x12` 中的最终数值为 `0x00003400`（在书写中简写为 `0x3400`）。
