## RISC-V 过程与调用约定精读讲义

### 拆开黑盒：程序运行机制的魔法信封

到目前为止，我们已经一步步搭建起了一个计算机的核心逻辑骨架。回顾前面的内容，我们先是做出了一个非常简陋的“傻瓜计算器”——只能做线性的顺序算术运算；接着，我们为它添加了分支决策能力，通过条件分支与无条件跳转，让程序能够根据输入判断“走高路还是走低路”。

但请停下来仔细想一想：直到上一讲为止，我们写的所有汇编代码，其实全部都挤在单一的 `main` 主逻辑中。我们根本无法在汇编层面调用任何独立的子过程（Procedure / Function）。

在你们此前接触过的每一种高级编程语言里——无论是在 C、Java 还是 Python 中——你们一定早就写过类似这样的代码：

```c
int i = mult(j, k);
/* 下一行继续执行其他业务 */
```

每当写下这行代码时，你或许都曾产生过疑惑：我在调用处把变量 `j` 和 `k` 传了进去。在 C 语言里这叫值传递（Pass by Value），也有的语言有引用传递（Pass by Reference），或者我开玩笑常说的“按咒语传递”（Pass by Spell）。不管怎么叫，请在脑子里牢牢记下：值传递的本质就是把参数的值复制一份，塞给被调用的过程。随后，代码跳入下方定义的乘法器子程序 `mult`，它把参数拿过去，利用累加或其他逻辑完成计算。最神奇的是，当 `mult` 计算完毕后，返回值仿佛被施了魔法一般精准地回传给了变量 `i`，而且 CPU 竟然能够分毫不差地知道应当跳回刚才调用点的下一行代码继续执行！

在今天之前，这一切对你们而言都是不折不扣的黑盒、抽象与魔法。从高级语言到底层硬件，到底是谁在操纵这封信封？在 RISC-V 汇编中，内存里的每一条指令都老老实实地占据着一个 32 位的物理地址（连续的行）。既然每条指令都在各自不同的地址行上，那么：

1. 调用者究竟如何把控制权转移到另一段代码的入口？
2. 参数到底被安放在了哪里，子程序又是怎么抓取到它们的？
3. 函数执行完后，返回值究竟藏在何处交还给调用者？
4. 最关键的——CPU 怎么可能知道在执行完之后，应该跳转回调用发生处的哪一行？

今天，正是我们彻底撕开这封抽象信封的日子。今天之后，函数调用的底层机制将不再有任何魔法。

### 过程调用的六步生命周期

为了让一个子程序能够被顺畅地调用、执行并安全返回，无论是在 RISC-V 还是在现代任何指令集体系结构中，整个硬件与软件系统都必须严格协同完成以下六个标准化步骤：

```text
+--------------------------------------------------------------+
|                   过程调用（Procedure Call）六步生命周期        |
+--------------------------------------------------------------+
| 1. 安放参数     | 调用者把参数放置到被调用过程能够访问到的明确位置     |
| 2. 移交控制权   | 修改程序计数器（PC），把执行流程跳转到子程序起始地址   |
| 3. 分配存储空间 | 子程序根据需要，在栈（Stack）上为其局部变量申请空间   |
| 4. 执行计算任务 | 子程序执行其内部的具体指令与业务逻辑               |
| 5. 安放返回值   | 子程序把产出的返回值安放到调用者能够取到的明确位置   |
| 6. 归还控制权   | 恢复 PC 为调用点之后紧随的那条指令地址，返回调用者   |
+--------------------------------------------------------------+
```

这六件事缺一不可：
- **第一步：安放参数**。你准备把控制权交给另一个独立的子程序，那个子程序如何获取输入？你必须先把参数推送到约定好的共享位置。
- **第二步：移交控制权**。我们需要读取当前的程序计数器（PC，指向当前正在执行指令的指针），并让 PC 跳转到目标子程序所在的第一条指令。
- **第三步：分配存储空间**。进入子程序后，它往往需要自己的临时局部变量，这需要在内存栈中迅速腾出局部存储空间。
- **第四步：执行计算任务**。执行该函数真正要做的工作，这正是我们前面一直在练习的算术与逻辑运算。
- **第五步：安放返回值**。计算结束后，数据如何交还？必须把计算结果存放到双方预定好的位置。
- **第六步：归还控制权**。被调用的过程执行完毕后，必须重新找回当初调用它时的上下文，把程序计数器 PC 准确重置为被调用点之后的下一行指令，从而让主程序平滑继续。

今天我们要讨论的全部技术机制，都是为了让这六个步骤以极高的效率、极低的代价在硅片上跑通。

### 为什么需要调用约定

既然需要传递参数和返回值，数据到底该放在哪？

计算机体系结构里有一个颠扑不破的物理定律：**寄存器比内存快得多**。

在前面讲存储层次时我曾打过比方：访问寄存器，速度快得就像从你自己的头顶上抓取帽子；而访问内存（RAM），其延迟之漫长，犹如你要专门驱车去一趟加利福尼亚的首府萨克拉门托（Sacramento）！

如果你在调用函数时，把每一个参数、每一个局部变量都死板地写进内存栈中，调用完后再一条条从内存加载回来看，这就意味着每调用一次函数，你的程序就得来回跑上几十次萨克拉门托。那种频繁的 `sw`（Store Word）和 `lw`（Load Word）开销会彻底拖垮 CPU 的性能。

因此，我们的首选策略是：**尽量通过寄存器直接传递数据**。调用者把数据写入特定寄存器，子程序直接从这些寄存器读取；子程序算完把结果写回特定寄存器，调用者直接拿走。

然而，全局可用的通用寄存器总共只有 32 个。如果毫无规矩，你在你的模块（比如 `foo.c`）里把某个变量存进了 `x5`，然后调用了我的模块（`bar.c`）；而我的代码里不管三七二十一，也用 `x5` 做加法循环，那么当你从我的函数返回时，你的数据早就被我踩得粉碎！

为了让全世界所有开发者写的代码、编译器编译出的不同目标文件、以及预先打包好的系统库能够严丝合缝地协同工作，硬件与操作系统设计者制定了一套神圣不可侵犯的契约——**调用约定（Calling Convention）**。

> **定义**：调用约定是调用者（Caller）与被调用过程（Callee）之间达成的一组强制性软件协议。它严格规定了哪些寄存器用于传参、哪些用于存放返回值、哪些寄存器由被调用者保护、哪些由调用者自负盈亏，以及控制权如何流转。

如果你问我：“丹，如果整个项目的汇编代码全是我一个人闭门造车写的，我可不可以不理会调用约定，爱用哪个寄存器就用哪个？”答案是：从纯裸机硬件的角度看，CPU 确实不会报错；但你的代码将永远无法链接标准 C 库，无法与任何他人编写的代码协同，一旦引入第三方模块系统就会立即崩溃。更现实的是——在期中考试或平时的汇编作业中，只要你不遵循调用约定，就算输出结果碰巧对了，也依然会被直接扣光分！

### 寄存器世界的角色分工与命名哲学

在 RISC-V 中，除了物理代号 `x0` 到 `x31` 之外，应用程序二进制接口（ABI）为每一个寄存器都赋予了具有明确语义的官方名字。从今天起，我们必须彻底告别冷冰冰的数字 `x`，在代码中全面使用 ABI 名称。

```text
+-------------------------------------------------------------------------+
|                        RISC-V 核心寄存器分工与 ABI 别名                   |
+------------+------------+-----------------------------------------------+
| ABI 寄存器名| 物理编号   | 约定用途与角色划分                              |
+------------+------------+-----------------------------------------------+
| zero       | x0         | 恒为常数 0（硬件绑定，写入被忽略）              |
| ra         | x1         | 返回地址（Return Address）                     |
| sp         | x2         | 栈指针（Stack Pointer），指向当前栈顶           |
| gp / tp    | x3 / x4    | 全局指针（Global Pointer）与线程指针（Thread Pointer）|
| t0 - t2    | x5 - x7    | 临时寄存器（Temporary），调用者保存            |
| s0 / fp    | x8         | 保存寄存器 0 / 帧指针（Frame Pointer）         |
| s1         | x9         | 保存寄存器 1（Saved Register）                 |
| a0 - a1    | x10 - x11  | 函数参数寄存器 0-1 / 函数返回值寄存器 0-1      |
| a2 - a7    | x12 - x17  | 函数参数寄存器 2-7                             |
| s2 - s11   | x18 - x27  | 保存寄存器 2-11（Saved Register），被调用者保存|
| t3 - t6    | x28 - x31  | 临时寄存器 3-6（Temporary），调用者保存        |
+------------+------------+-----------------------------------------------+
```

#### 参数与返回值寄存器：a0 到 a7

RISC-V 提供了 8 个专门用于参数传递的寄存器：`a0` 到 `a7`（对应物理寄存器 `x10` 到 `x17`）。

- **传参**：当调用一个函数时，第一个参数放入 `a0`，第二个放入 `a1`，以此类推，最多支持 8 个直接传参。如果一个函数只需要两个参数，子程序只管读取 `a0` 和 `a1` 即可，完全不需要花时间把剩余的 `a2~a7` 清零，多余的寄存器随它去，不必理睬。
- **溢出到栈（Spill to the Stack）**：如果一个 C 函数丧心病狂地声明了 9 个甚至更多的参数怎么办？8 个寄存器被填满后，多出来的参数就会“溢出”到内存中。
  - 为什么多出的参数放入栈中，而不是去堆区调用 `malloc`？
  - 因为调整栈指针只需要**一条简单的算术指令**（比如 `addi sp, sp, -16`），纳秒级完成；而 `malloc` 自身是一个庞大且极其沉重的动态内存管理子程序，内部包含复杂的链表搜索与系统调用，用它来传参纯属舍本逐末。
- **返回值重用（a0 与 a1）**：函数执行结束后，返回值直接写回 `a0` 和 `a1`。
  - 为什么需要两个返回值寄存器？如果只返回一个整型，存入 `a0` 即可；但高级语言中常有超过 32 位的数据类型，例如 64 位的长整型（`long long`）或双精度浮点数（`double`），这时就需要同时使用 `a0`（低 32 位）和 `a1`（高 32 位）来拼装传回；如果只返回单字节（`char`），则将其放在 `a0` 的最低 8 位即可。
  - > **易错点**：如果函数要返回一个数组，绝不能指望用寄存器搬运整个数组。在 C 语言中，返回数组本质上是返回该数组首地址的指针（一个 32 位地址，存入 `a0`）。切记：绝对不能返回指向局部自动变量（栈内存）的指针，因为子程序一返回该栈帧就失效了；要跨作用域返回数据，指针必须指向堆内存（Heap）或静态数据区。
  - > **提示**：正因为 `a0` 和 `a1` 既用来传参又用来装返回值，这就意味着一旦函数返回，原先传入 `a0`、`a1` 的入参就会被返回值直接覆盖！如果调用者后续还要使用原来的入参，调用者必须提前为数据做好备份。

#### 返回地址寄存器：ra

`ra` 即 Return Address，物理寄存器为 `x1`。它专门用于保存被调用函数执行完毕后，应该跳转返回的内存地址。

无论子程序在全工程的哪一个角落、被 20 个不同的上游模块调用，只要被调用者在退出时读取 `ra`，就能准确找到本次调用的返程路口。

#### 保存寄存器：s0 到 s11

`s0` 到 `s11`（共 12 个，物理对应 `x8~x9` 与 `x18~x27`）被称为保存寄存器（Saved Registers）。

关于保存寄存器，调用约定给出的铁律是：**被调用的子程序绝不允许破坏它们**！

请注意我的措辞——这并不意味着子程序在物理上“绝对不能碰它们”。为了向大家讲透这一点，我在课堂上常举“借住房子”的比喻：

> 假设我把房子钥匙交给了室友（被调用者），客厅里有一个属于我私人专用的储物柜（保存寄存器 `s`）。室友在住进来的期间，如果实在腾不出桌子，他可不可以把我的柜子搬到走廊，借用柜子所在的地方放点东西用上五秒钟？
> 答案是：**完全可以**！但前提是，等我推门回家的那一瞬间，柜子必须已经完好无损地放回了原来的位置，柜里的东西一件也不能少。对我（调用者）而言，整件事情就像从未发生过一样。

因此，被调用子程序若想使用 `s0~s11` 来协助完成自身复杂的运算，它必须在动手前把旧值保存到栈中；在函数返回前，再从栈中把旧值完好地加载恢复回去。

#### 临时寄存器：t0 到 t6

`t0` 到 `t6`（共 7 个，对应 `x5~x7` 与 `x28~x31`）是临时寄存器（Temporary Registers）。

临时寄存器是随便使用的“公用草稿纸”。任何过程都可以自由向里面写数据，且无需在退出时进行恢复。

同样用借房子的比喻：临时寄存器就像是你随手扔在洗手间台面上的私人牙刷。当房客借住几天后你再回来，你还敢直接信任并使用那把牙刷吗？电影里各种糟糕的事情就是这么发生的！你绝对不能跨函数调用去信任任何留在临时寄存器里的数据。如果你在调用别的函数之前在 `t0` 里算出了一个半成品，一旦你调用了别的函数，对方随时可能把 `t0` 覆盖得干干净净。调用归来后，你的临时数据早就灰飞烟灭了。

### 控制权转移：从无条件跳转到 JAL 与 JALR

搞清了寄存器的分工，我们来看控制权到底如何从调用者跳转到子程序，又如何从子程序返回。

#### 存储程序概念与硬编码跳转的局限

在深入指令之前，必须重温计算机科学史上最伟大的里程碑之一——由冯·诺依曼等人确立的**存储程序概念（Stored-Program Concept）**：

> **核心原理**：程序指令和运算数据在物理上共存于同一套内存空间中。指令本身也是二进制数据，在 32 位 RISC-V 体系中，每条指令严格占用 4 个连续的字节。

假定在内存中，代码从上往下线性排布，有一个最简单的加法子程序 `sum(x, y)`：

```text
地址 (十进制)      指令汇编代码                   逻辑含义
-----------------------------------------------------------------
1000             mv a0, s0                    ; 将第一个参数传给 a0
1004             mv a1, s1                    ; 将第二个参数传给 a1
1008             ???                          ; 跳转调用 sum，下一条指令在 1012！
1012             add s2, a0, zero             ; 拿回返回值继续执行
...
2000     sum:    add a0, a0, a1               ; 计算 a0 = a0 + a1
2004             ???                          ; 返回到调用处下一行（1012）
```

在讨论成熟指令前，我们先思考：能不能只用普通的无条件跳转指令 `j`（Jump）来实现返回？

假设我们在 `sum` 结尾硬编码写上一句 `j 1012`（或者给 1012 处打个标签 `j back`），这能行吗？

**绝对不行！**

因为 `sum` 是一个通用的公共库函数，它不仅会在 1008 处被调用，还可能在主程序的 1040 处、甚至在另一个源文件的 5000 处被反复调用。如果你把返回地址硬编码为 1012，那么无论别人从哪里调用它，它都永远只跳回 1012，整个系统瞬间陷入逻辑错乱！

退一步讲，就算调用者在 1008 处强行用 `li ra, 1012` 硬把返回地址写入 `ra`，然后再 `j sum`，这也是极度糟糕的设计。因为这强行要求编译器在写代码时就知道这段程序将来被放置在内存的具体绝对地址。一旦操作系统做代码重定位，或者代码位置发生变动，硬编码的地址全部作废。

#### 诞生新指令：JAL（跳转并链接）

为了以优雅、与位置无关（Position-Independent）的方式解决这个问题，RISC-V 专门引入了核心指令：`jal`（Jump and Link，跳转并链接）。

```text
语法格式： jal rd, Label
通用范式： jal ra, Label
```

`jal` 的硬件操作语义包含两个不可分割的动作：
1. **链接（Link）**：将当前指令的下一条指令地址（即 `$PC + 4$`）存入目标寄存器 `rd`（绝大多数情况下，`rd` 直接指定为 `ra`）。
2. **跳转（Jump）**：让程序计数器 PC 无条件跳转到目标 `Label`（基于当前 PC 的偏移量进行跳转）。

```text
执行流程图解：

  当前 PC 处于 [ 1008 ] -> 执行 jal ra, sum
                             |
                             +--> 1. 链接：计算 PC + 4 = 1012，存入 ra 寄存器
                             |
                             +--> 2. 跳转：将 PC 设置为 sum 的地址（2000）
```

> **讲师辨析：为什么叫 JAL 而不是 LAJ？**
> 从逻辑执行的因果上来说，CPU 显然是必须先“形成链接（将当前 PC+4 存入 ra）”，然后再“执行跳转（修改 PC）”。如果你先跳跑了，原来的位置就丢失了。那为什么指令名字不叫 `laj`（Link and Jump）呢？
> 这纯粹是为了照顾人类的语言与认知直觉：在汇编语言中，所有无条件跳转家族的指令都统一以字母 `j` 开头（如 `j`、`jr`、`jal`、`jalr`），便于汇编器识别和程序员记忆。

> **结论：无条件跳转 `j` 的底层真相**
> 在 RISC-V 的精简哲学中，原生的基础指令集甚至没有专门的独立 `j` 指令！
> 你在代码里写的 `j Label`，在硬件底层实际上是一条伪指令：
> `jal zero, Label`
> 因为 `zero`（`x0`）寄存器对任何写入都硬件丢弃，因此把它作为链接目标，就等价于只跳转、不记录返回地址。RISC-V 凭借这一极度精妙的设计，直接省去了一条底层专用跳转指令！

#### 间接跳转：JALR（跳转并链接寄存器）与 RET

当子程序在 `sum`（地址 2000）处算完之后，它怎么利用保存在 `ra` 里的地址跳回来？

此时目标地址已经不是一个固定的代码标签，而是动态保存在寄存器 `ra` 中的数值。为此，RISC-V 提供了寄存器跳转指令：`jalr`（Jump and Link Register）。

```text
语法格式： jalr rd, offset(rs1)
语义：
  1. 将 PC + 4 存入 rd；
  2. 将 PC 设置为 (rs1 + offset)（同时将最低位置 0 以确保对齐）。
```

当从函数返回时，我们不再需要记录新的返回地址，所以 `rd` 填 `zero`；目标地址在 `ra` 中，偏移量为 `0`：

```assembly
jalr zero, 0(ra)    # 底层原生返回指令
```

由于每写一个函数返回都要敲出 `jalr zero, 0(ra)` 实在太过繁琐，RISC-V 汇编器贴心地提供了两条等价的伪指令简写：
- `jr ra`：Jump Register，等价于 `jalr zero, 0(ra)`；
- `ret`：Return from procedure，更高级的终极伪指令简写，底层同样展开为 `jalr zero, 0(ra)`。

现在，我们可以把前述 `sum` 函数的完整汇编代码端出来了：

```assembly
# 调用方代码 (Caller)
main:
    mv   a0, s0         # 参数 1: a0 = s0
    mv   a1, s1         # 参数 2: a1 = s1
    jal  ra, sum        # 核心调用：ra = PC + 4，PC = sum
    mv   s2, a0         # 接收返回值：s2 = a0 (计算结果)
    ...

# 被调用过程 (Callee)
sum:
    add  a0, a0, a1     # a0 = a0 + a1
    ret                 # 优雅返回！等价于 jr ra，也就是 jalr zero, 0(ra)
```

看到没有？没有多余的废话，没有昂贵的内存读写，控制权顺畅移交，计算飞速完成，再凭借 `ra` 精确命中返程路标！

### 内存栈机制与叶函数实战

上述 `sum` 例子非常简单，它不需要使用保存寄存器，也不调用其他人。但在真实工程中，子程序自身往往需要使用额外的寄存器做复杂运算。这就必须引入**栈（Stack）**。

#### 栈的生长特性与内存布局

在 RISC-V 体系中，内存栈具有以下核心特性：
1. **自顶向下增长（从高地址向低地址扩展）**：
   - 压栈（Push）：由于栈向低地址生长，为栈帧开辟空间必须执行**减法**（例如 `addi sp, sp, -8`）；
   - 出栈（Pop）：释放栈帧空间时，执行**加法**（例如 `addi sp, sp, 8`）。
2. **栈指针寄存器 `sp`（即 `x2`）**：时刻指向当前活动栈帧的最新栈顶（物理上的最低有效地址）。
3. **保持平衡的铁律**：如果一个函数把 `sp` 向下移动了 12 个字节，那么在该函数执行 `ret` 之前的最后一刹那，`sp` 必须不多不少、精确地向上回调 12 个字节！如果 `sp` 错位了一丁点，调用者后续去栈里读变量时就会全盘错位，程序必将崩溃。

```text
高地址方向
  +--------------------------+
  |    调用者的上层栈帧      |
  +--------------------------+  <- 调用进入前的旧 sp 位置
  |  保存的旧 s1 (sp + 4)    |
  +--------------------------+
  |  保存的旧 s0 (sp + 0)    |
  +--------------------------+  <- addi sp, sp, -8 后的新 sp 栈顶位置
低地址方向 (栈向下生长 ↓)
```

#### 叶函数案例精析：f = (g + h) - (i + j)

我们称那些内部不再调用任何其他函数的子程序为**叶函数（Leaf Procedure）**——就像树枝末梢的树叶一样，不再分叉。

假设我们要实现如下 C 语言叶函数：

```c
int leaf_example(int g, int h, int i, int j) {
    int f;
    f = (g + h) - (i + j);
    return f;
}
```

约定参数分配如下：
- 参数 `g, h, i, j` 依次传入 `a0, a1, a2, a3`；
- 内部计算希望使用 `s0` 保存 `(g + h)`，使用 `s1` 保存 `(i + j)`；
- 最终结果 `f` 放入 `a0` 作为返回值返回。

因为我们在函数内部要借用 `s0` 和 `s1` 这两个保存寄存器，根据调用约定，我们是“借住的房客”，必须履行“被调用者保存（Callee-saved）”的法定义务：进入时把原来的 `s0` 和 `s1` 压栈，算完退出前原样放回。

完整标准汇编实现如下：

```assembly
leaf_example:
    # ------------------ 1. 函数前言 (Prologue) ------------------
    addi sp, sp, -8         # 在栈上开辟 8 个字节（2 个字）的空间
    sw   s1, 4(sp)          # 将旧的 s1 保存到栈偏移 4 的位置
    sw   s0, 0(sp)          # 将旧的 s0 保存到栈偏移 0 的位置

    # ------------------ 2. 函数主体 (Body) ----------------------
    add  s0, a0, a1         # s0 = g + h
    add  s1, a2, a3         # s1 = i + j
    sub  a0, s0, s1         # a0 = s0 - s1 (即最终结果 f，写入返回值寄存器)

    # ------------------ 3. 函数后记 (Epilogue) ------------------
    lw   s0, 0(sp)          # 从栈中恢复旧 s0 的原值
    lw   s1, 4(sp)          # 从栈中恢复旧 s1 的原值
    addi sp, sp, 8          # 释放 8 字节的栈帧空间，恢复 sp
    ret                     # 返回调用方 (jr ra)
```

> **读图与时序说明**：
> 请注意前言与后记那令人惊叹的**完全镜像对称美学**！
> 在前言里是减 8 字节分配空间，紧接着用 `sw` 存入数据；在后记里完全反转，用 `lw` 取回旧值，再用加 8 字节平栈。代码翻转过来，对调用者来说，`s0` 和 `s1` 就像是从未被触碰过一样。

#### 讲师现场的反思与极致优化告诫

讲完这段代码后，台下同学一定会产生一个极其敏锐的疑问：
“丹，你刚才还告诫我们访存‘去萨克拉门托’非常慢，为什么在这里算个加减法，非要多花 4 次内存读写（两次 `sw`、两次 `lw`）去折腾 `s0` 和 `s1`？难道不能直接全用参数和临时寄存器算完吗？”

**你们完全正确！**

在课堂上我当场指出，如果纯粹为了追求最高性能和最短指令数，我们根本不需要碰任何一个 `s` 寄存器。利用加减法的代数分配律，直接复用传入的 `a` 寄存器：

```assembly
# 极致性能版本：零访存，仅需 4 条指令！
leaf_optimized:
    add a0, a0, a1         # a0 = g + h
    sub a0, a0, a2         # a0 = (g + h) - i
    sub a0, a0, a3         # a0 = (g + h) - i - j = (g + h) - (i + j)
    ret                    # 计算完成，直接返回！
```

看，不需要调整栈指针，没有两次去萨克拉门托存储，没有两次去萨克拉门托加载，4 条指令干净利落！

我之所以在前一段代码里不厌其烦地演示使用 `s` 寄存器的完整流程，是为了向大家传授当一个叶函数逻辑极其复杂、寄存器不够用而**必须动用 `s` 寄存器时**的规范动作。在考试与作业中，只要你严格遵循调用约定完成压栈与恢复，即使代码并非理论最简，也能稳稳拿满分！

> **易错点：出栈时需要把内存清零吗？**
> 很多初学者有强迫症，总觉得弹栈时是不是应该顺便往内存里写个 0 把数据擦掉？
> **千万不要这么做！** 栈上的旧数据留在那里根本无人关心，因为 `sp` 已经回退，那片空间在逻辑上已经失效。为了“把数据抹平”而特意跑去萨克拉门托执行一次写零操作，是对 CPU 时钟周期的纯粹浪费。

### 嵌套调用危机：非叶函数与返回地址的挽歌

如果说叶函数是简单的单层调用，那么现实程序中充斥着复杂的链式调用：函数 A 调用函数 B，函数 B 又调用函数 C。我们称内部还要调用其他函数的子程序为**非叶函数（Non-leaf Procedure）**。

正是在非叶函数中，隐藏着整个体系结构中最容易导致程序暴毙的致命陷阱！

#### “回不了家”的灾难场景

假设我们有三个函数：`main` 调用 `sumSquare`（平方和），而 `sumSquare` 内部又调用了乘法器 `mult`：

```c
int sumSquare(int x, int y) {
    return mult(x, x) + y;
}
```

我们来推演一下执行流中程序计数器与 `ra` 寄存器的惨烈碰撞：

```text
1. main 在地址 1000 处执行：
   jal ra, sumSquare
   此时：ra 寄存器被硬件写入了 main 的返回地址 [ 1004 ]。

2. CPU 跳转到 sumSquare 内部开始执行。

3. sumSquare 为了算平方，在内部地址 2008 处执行：
   jal ra, mult
   ！！！灾难发生！！！
   jal 指令会无情地将当前指令的下一行地址 [ 2012 ] 强行写入 ra 寄存器！

4. 原先保存在 ra 中通往 main 的唯一回程车票 [ 1004 ]，被彻底覆盖粉碎！
```

此时会发生什么？
当 `mult` 执行完 `ret` 时，它读取 `ra`（里面是 2012），顺利返回到了 `sumSquare` 中。但当 `sumSquare` 算完加法，执行自己的 `ret` 时，它再次读取 `ra`——此时 `ra` 里依然残留着 2012！

于是，`sumSquare` 竟然自己跳回了自己的第 2012 行，陷入了万劫不复的死循环或逻辑崩溃。主程序 `main` 望穿秋水，永远也等不到控制权归来！

```text
嵌套调用 ra 覆盖灾难示意：

main (1000) ------- jal ra, sumSquare ------> sumSquare (2000)
       ^                                            |
       |  原 ra = 1004                              | 执行 jal ra, mult
       |                                            v
       |                                       mult (3000)
       |                                            |
       X  ra 惨遭覆盖为 2012!                         | ret (jr ra)
       |  无法回到 1004 <-------------------------- 顺利返回 2012
```

#### 破局之道：在栈中妥善保管返程路标

解决这个危机的唯一法门是：**非叶函数在调用任何下游函数之前，必须先将自己的 `ra` 寄存器存入栈中！**

如果除了 `ra` 之外，非叶函数后续计算还要用到之前传进来的入参（比如 `y` 原本在 `a1` 中，但调用 `mult` 时 `a0`、`a1` 必须被占用作为乘法入参），那么这些跨调用仍需使用的数据，也必须一并压栈保存，或者在进入前换存到 `s` 寄存器中。

```text
非叶函数标准防护流程：

进入非叶函数时：
  1. 压栈开辟空间 (addi sp, sp, -16)
  2. 把关键的 ra 存入栈顶 (sw ra, 12(sp))
  3. 把后续还要用的参数或中间值存入栈中

中途放心调用下游：
  4. 配置下游参数，执行 jal ra, sub_routine
  5. 下游把 ra 踩成碎片也无所谓，因为真身安全地躺在我们的栈里！

准备返回上层调用者前：
  6. 从栈中捞出原初的 ra (lw ra, 12(sp))
  7. 释放栈帧 (addi sp, sp, 16)
  8. 执行 ret 平安回到 main！
```

### 责任天平：调用者保存与被调用者保存

现在，我们把整个调用约定中最重要的核心设计哲学做一次高屋建瓴的提炼。

整个寄存器体系被严谨地划分为两大阵营：谁负责在函数调用发生时保存并恢复这些寄存器？

```text
+---------------------------------------------------------------------------------------+
|                      调用约定权责划分总览表（The Contract）                              |
+---------------------+-------------------+------------------+--------------------------+
| 寄存器类别          | 寄存器名称        | 保存责任人       | 跨函数调用生存状态       |
+---------------------+-------------------+------------------+--------------------------+
| 保存寄存器 (Saved)  | s0 - s11          | 被调用者保存     | 跨调用安全保留           |
|                     | (Callee-saved)    | (Callee 负责)    | 调用者可坚信返回后值不变 |
+---------------------+-------------------+------------------+--------------------------+
| 栈指针 (Stack Ptr)  | sp                | 被调用者保存     | 跨调用必须绝对恢复原位   |
|                     |                   | (Callee 负责)    | 稍有偏移后续访存彻底崩溃 |
+---------------------+-------------------+------------------+--------------------------+
| 临时寄存器 (Temp)   | t0 - t6           | 调用者保存       | 跨调用随时被覆盖摧毁     |
|                     |                   | (Caller 负责)    | 调用者跨调用若需使用需自保|
+---------------------+-------------------+------------------+--------------------------+
| 参数 / 返回值       | a0 - a7           | 调用者保存       | 跨调用随时被覆盖摧毁     |
|                     |                   | (Caller 负责)    | 调用者跨调用若需使用需自保|
+---------------------+-------------------+------------------+--------------------------+
| 返回地址            | ra                | 调用者保存       | 执行 jal 时立即被覆写    |
|                     |                   | (Caller 负责)    | 非叶函数必须压栈保护     |
+---------------------+-------------------+------------------+--------------------------+
| 特殊全局指针        | gp, tp            | 保持不变         | 整个程序运行期间基本不碰 |
+---------------------+-------------------+------------------+--------------------------+
```

#### 被调用者保存（Callee-saved）的内涵

- **阵营成员**：`s0 ~ s11` 以及 `sp`。
- **责任承诺**：如果被调用的函数想要使用 `s` 系列寄存器，被调用者必须在前言中压栈保存它们，并在后记中原样弹栈恢复。
- **对于调用者的意义**：调用者可以高枕无忧。如果在调用前你把重要账目存在了 `s0` 里，不论你调用的子函数内部多么翻江倒海，一旦控制权返回给你，`s0` 里的数值绝对完好无损。
- **对于栈指针 `sp` 的极高警惕**：`sp` 是调用者赖以寻址的生命线。被调用者用完栈后，必须一字节不差地把 `sp` 还原回入场时的位置。如果 `sp` 偏移了 4 个字节，调用者后续的所有局部变量读取都将沦为灾难性的“数据错位”。

#### 调用者保存（Caller-saved）的内涵

- **阵营成员**：`t0 ~ t6`、`a0 ~ a7` 以及 `ra`。
- **责任承诺**：被调用者拥有对这些寄存器的“绝对自由处置权”。被调用者可以任意涂抹、覆盖，完全不需要为调用者擦屁股。
- **对于调用者的意义**：如果调用者在执行 `jal` 之前，在某个临时寄存器（如 `t0`）或入参寄存器（如 `a2`）中存放了调用归来后还要用到的数据，调用者必须在调用发生**前**，自己亲自动手把它们压入栈中；等子程序返回后，再由调用者自己从栈中弹回复原。

### 本讲提到的题目

在本讲的授课过程中，现场共展开了两道核心互动的经典题目：一道是开篇的逻辑移位与掩码运算复习题，另一道是课末检验全讲理解深度的 Clicker 多选辨析题。现将课堂原题与详尽解析还原如下。

#### 课堂开篇预热题：移位与掩码提取字节

##### 题干描述

我们有两个 32 位寄存器，其中 `x10` 的初始十六进制数值为 `0x000034ff`（中间含有字节 `0x34` 与低位 `0xff`）。现依次执行以下汇编操作序列，目标是观察每一步寄存器数值的演变，并确定最终存储在 `x12` 中的数值：

```assembly
slli x12, x10, 16    # 第一步：逻辑左移立即数 16 位
srli x12, x12, 8     # 第二步：逻辑右移立即数 8 位
and  x12, x12, x10   # 第三步：按位与运算
```

##### 推导解析

- **第一步：`slli x12, x10, 16`**
  - 逻辑移位（Logical Shift）无论左移还是右移，移出的位被丢弃，空出的位**始终用 0 填充**（只有算术右移 `srai` 才会进行符号位扩展）。
  - `x10` 的初始值为 `0x000034ff`。将其左移 16 位（即 2 个完整字节），原先处于低 16 位的 `34 ff` 被整体推到了高半区。
  - 执行后，`x12 = 0x34ff0000`。
- **第二步：`srli x12, x12, 8`**
  - 8 位二进制恰好等于 1 个字节（一个十六进制字符代表 4 位，两个字符为一个字节）。
  - 对 `x12` 执行逻辑右移 8 位，高位用 0 填充，整个数据向右平移 1 个字节。
  - 执行后，`x12 = 0x0034ff00`。
- **第三步：`and x12, x12, x10`**
  - 按位与运算具有交换律与**掩码（Masking）**特性：
    - 任何位与 `0` 相与，结果强制被清零（屏蔽该位）；
    - 任何位与 `1`（或十六进制的 `f`）相与，结果完整保留原值。
  - 我们把参与运算的两个寄存器纵向对齐观察：
    - `x12` 当前值：`0x 00 34 ff 00`
    - `x10` 原始值：`0x 00 00 34 ff`
  - 逐字节执行按位与：
    - 最高字节：`0x00 & 0x00 = 0x00`
    - 次高字节：`0x34 & 0x00 = 0x00`（被 `x10` 的零屏蔽）
    - 次低字节：`0xff & 0x34 = 0x34`（因为 `0xff` 全是二进制 1，完整保留了 `0x34`）
    - 最低字节：`0x00 & 0xff = 0x00`（被 `x12` 的零屏蔽）
  - 最终写入 `x12` 的结果为：`0x00003400`。

##### 结论

最终在寄存器 `x12` 中的数值是 `0x00003400`（十六进制 3400）。这一过程生动展示了如何通过逻辑左移、右移配合按位与，从一个字中提取并对齐特定字节的掩码技巧。

#### 课末综合检测题：过程调用机制与调用约定辨析

##### 题干描述

针对 RISC-V 过程调用机制、相关指令及调用约定，下列四项陈述中，**哪一个是错误的（Which one is FALSE）？**

1. RISC-V 使用 `jal` 调用函数，使用 `jr`（或 `ret`）从函数返回。
2. `jal` 指令在跳转时，会将 `PC + 1` 保存到返回地址寄存器 `ra` 中。
3. 调用者可以直接使用临时寄存器（`t` 系列），无需进行压栈保存与恢复；同样地，被调用者也可以直接使用临时寄存器，无需保存与恢复。
4. 调用者可以完全信赖已保存的寄存器组（`s` 系列），无需担心跨函数调用会导致它们的值被篡改。

##### 推导解析

我们对每一个选项结合底层技术事实进行逐一审视：

- **审视选项 1**：陈述正确。
  - RISC-V 通过 `jal ra, Label` 完成控制权移交与返回地址记录；在函数末尾，通过 `jr ra`（也就是 `jalr zero, 0(ra)` 或伪指令 `ret`）读取 `ra` 顺利跳回调用点。
- **审视选项 3**：陈述正确。
  - 临时寄存器（`t0~t6`）在调用约定中本就是公用划痕板。被调用者拿到 CPU 后可以随意修改，不需要为调用者恢复；调用者在调用发生前如果不在乎里面的临时值，也无需保存。双方都不受保存义务约束。
- **审视选项 4**：陈述正确。
  - 保存寄存器（`s0~s11`）属于被调用者保存（Callee-saved）。被调用者如果胆敢触碰，就必须在前言中压栈、后记中出栈恢复原值。因此调用者完全可以信赖 `s` 寄存器在调用前后坚挺不变。
- **审视选项 2**：**陈述严重错误！**
  - 在 RISC-V 体系中，内存寻址是以**字节（Byte）**为基础单元的；
  - 每一条标准 RISC-V 指令严格占据 32 位二进制，即 **4 个字节**；
  - 因此，当前指令位于 `PC`，紧随其后的下一条指令地址必定是 `$PC + 4$`，绝不可能是 `$PC + 1$`！如果硬件存入 `$PC + 1$`，不仅返回地址错落到了指令内部的非对齐字节，引发硬件对齐异常，更彻底丢失了正常的代码逻辑流。`jal` 存入的必然是 `$PC + 4$`。

##### 结论

**错误选项为：第 2 项。**
（`jal` 应当将 `$PC + 4$` 写入 `ra`，而非 `$PC + 1$`）。
