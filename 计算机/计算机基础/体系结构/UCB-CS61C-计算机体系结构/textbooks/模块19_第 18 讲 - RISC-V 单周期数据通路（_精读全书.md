### 处理器解构：数据通路与控制逻辑的双重奏

在系统宏观架构中，计算机主要被划分为两大实体：左边的中央处理器（CPU）和右边的内存（Memory）。今天我们先把内存当作一个外部黑盒，全力攻克 CPU 内部。

整个 CPU 的内部世界，清晰地分工为两个核心子系统：**数据通路（Data Path）** 与 **控制逻辑（Control）**。

```text
+-----------------------------------------------------------+
|                        CPU (处理器)                       |
|                                                           |
|       +-------------------------------------------+       |
|       |           控制逻辑 (Control Logic)        |       |
|       |         "大脑 / 水龙头总指挥 / 状态机"    |       |
|       +-------------------------------------------+       |
|            ^ 控制状态反馈              | 控制信号驱动     |
|            | (如分支比较结果)          | (如 MUX 选通)    |
|            v                           v                  |
|       +-------------------------------------------+       |
|       |             数据通路 (Data Path)          |       |
|       |          "水流管道 / 连线与运算部件"      |       |
|       +-------------------------------------------+       |
+-----------------------------------------------------------+
                             |
                      总线交互 (访存与取指)
                             v
+-----------------------------------------------------------+
|                      内存系统 (Memory)                    |
+-----------------------------------------------------------+
```
数据流与控制流在 CPU 内部形成上下呼应的双层结构。

要彻底想通它们的关系，不妨在脑海中建立两个极具画面感的工程模型。

#### 古希腊引水渠与水龙头把手

设想古希腊的一座宏伟引水渠（Aqueduct）。水源从远山奔流而下，工程师为了让水流精准送达每一座民居，在城邦地下开凿了庞大错综的沟渠网络。水流该在哪里分叉？如何汇入特定街道？某户人家出门度假时，怎么掐断他们家的水管，让水流只涌向邻家？

这一整套用于承载水流物理流向的管道、岔路和物理连线，就是**数据通路**。我们在芯片上铺设的每一根总线、安放的每一个运算器，本质上就是在为数据的奔流开凿渠道。

但在每处关键的三通接头和出水口，都必须安装一个带有旋钮把手的阀门或水龙头（Spigots）。今天早上你想冲澡，就得拧开花洒的水龙头；今天如果不需要浇灌后院，就必须把花园的阀门关死。

这些负责把守各个管道关卡、决定水流走哪条支路的阀门控制器，就是**控制逻辑**。它就像整个系统的中枢大脑，往往由我们上一讲学过的有限状态机（FSM）或真值表纯组合逻辑实现。它根据当前执行的任务下发指令：今天开通寄存器写回的阀门，明天开启内存访问的闸口。

#### 国际空间站与地面控制中心

另一个现代比喻，是翱翔在太空中的国际空间站（ISS）与坐落在休斯顿的地面任务控制中心（Mission Control）。

数据通路就像空间站本体。那是人类精工制造的一具重型物理实体，拥有巨大的太阳能帆板、复杂的对接舱段、密密麻麻的动力电缆和姿态发动机喷管。它具备极其强大的轨道运行能力，但它自身并不知道何时该点火变轨，也不知道哪条数据链路应该接通。

控制逻辑正是休斯顿的地面任务控制中心。地面工程师根据飞行手册查阅操作流程，向空间站遥控发送一串串指令脉冲：“打开 3 号推进器点火两秒”、“关闭 1 号通信天线”。

更关键的是，控制中心并不是蒙着眼睛盲目发令的。控制逻辑与数据通路之间存在着高频的双向信息交互：
- 控制逻辑向数据通路广播控制电平，指挥多路选择器切换选通、命令 ALU 执行加法或减法；
- 数据通路在运转过程中，也会将产生的关键状态回传给控制逻辑。最典型的例子就是条件分支指令 `beq`：数据通路负责将两个寄存器的值拉进比较器，测出它们到底“相等还是不相等”，并把这一位布尔信号飞线送回控制逻辑。控制逻辑拿到这个事实依据后，才能当场拍板，决定命令多路选择器把下一跳 PC 切向 `PC + 4` 还是跳转目标地址。

### 基础构件库：组合逻辑与状态元件的边界

在正式动手走线之前，我们需要先去电子元器件货架上清点我们的工具箱。今天我们要用到的主要器件分为两大流派：纯粹的组合逻辑部件与带有时钟驱动的状态元件。

#### 核心黑盒三大件

我们将以下三个组合逻辑电路打包为可以直接调用的黑盒：

```text
  多路选择器 (MUX)              加法器 (Adder)              算术逻辑单元 (ALU)
    +---------+                  +---------+                  +---------+
A --| 0       |            A ----|         |            A ----| \       |
    |     Out |---- Out          |   ADD   |---- Sum          |  \  ALU |---- Result
B --| 1       |            B ----|         |            B ----|  /      |
    +----+----+                  +---------+                  +----+----+
         |                            ^                            |
         | S (选通信号)               | CI (进位输入)               | ALUop
```
组合逻辑黑盒输入输出示意图：所有部件均不带时钟三角形，输出仅取决于当前输入与内部传播延迟。

- **多路选择器（2-to-1 MUX）**：拥有两个 32 位宽的数据输入端 $A$ 和 $B$，一个 32 位宽的数据输出端，以及一位控制选通信号 $S$。当 $S = 0$ 时选通 $A$，当 $S = 1$ 时选通 $B$。
- **32 位全加器（Adder）**：接收两个 32 位加数输入 $A$ 与 $B$，可选接入进位输入 $C_0$，在输出端吐出 32 位的加法和以及进位输出。
- **算术逻辑单元（ALU）**：计算机的运算核心。不仅能执行加减法等算术运算，还能执行按位与、按位或等逻辑操作。它接收两个 32 位输入端，底部接受来自控制逻辑的 `ALUop` 操作码信号，输出一个 32 位的运算结果。

> **定义**：**硬件的永续并行性**
> 在数字逻辑硬件中，不存在软件概念里的“分支休眠”。当我们将数据送入加法器和与门网络时，所有逻辑门都在耗费电流实时计算。即使下游的多路选择器最终只挑选了加法结果，旁边的与门网络依然在完全并行地吐出逻辑运算值。硬件无法被“关机”，多路选择器的本质只是在一堆并行产生的结果中挑选哪一路接入下一级总线。

#### 触发器、时钟沿与超频惨案

凡是纯组合逻辑器件（CL），在其符号图上绝对找不到任何小三角标记。它们的输出完全由当前输入信号经过固有的物理门延迟后稳定得出。

而状态元件（State Elements）则截然不同。它们的引脚底部必然绘制着一个醒目的小三角形——这代表**边沿触发时钟输入端（Clock Input）**。

```text
               时钟周期 T_cycle
        |<-------------------------->|
        +-------------+              +-------------+
CLK:    |             |              |             |
     ---+             +--------------+             +--------------
        ^                            ^
     时钟上升沿 1                 时钟上升沿 2
        |                            |<--- t_setup --->|
        |                            |  数据必须保持稳定  |
        v                            v                 v
    触发状态更新                     下一次数据锁存采样点
```
时钟上升沿与建立时间约束关系：在下一个有效上升沿到来之前，输入信号必须提前稳定至少 $t_{setup}$ 时间。

状态元件在每个时钟周期的绝大部分时间里，其核心职责就是“咬死”上一周期存入的数据，对外提供持续恒定的电平输出。只有当时钟上升沿（Rising Edge）骤然降临的一瞬间，且写使能信号有效时，它才会以极快的速度把进门处排队等待的新值载入内部。

组合逻辑部件根据工艺规范，有着明确标定的最长物理传播延迟。从状态元件吐出数据，经过复杂的加法器、位移器和多路选择器网络，总线信号逐渐滤除毛刺走向稳定。而这批崭新的电平信号，必须在下一个时钟上升沿撞线前的某一极短窗口期内提前锁定。这个硬性的时间窗口，就是**建立时间（$t_{setup}$）**。

提到 $t_{setup}$，当年我还在读大学时的一段亲身惨痛经历就是最好的注脚。

那时候极客圈子里非常风靡“超频”（Overclocking）。我当时用的是一台速度飞快的老 Macintosh，为了榨干最后一丝性能，我特意给板子改造了晶振插座，还特地给一位专门制作时钟发生器的大神发邮件索取了四个更高频的定制时钟芯片。我挑了一个频率最高的换上去，通电开机，指示灯亮了，系统直接以闪电般的速度飞速运转！我兴奋地打开当时的顶级图像处理软件 Photoshop，给一张大图加了一道炫酷的高斯模糊滤镜，点击保存文件，关机睡觉。

第二天早上，当我志得意满地再次打开电脑准备展示成果时，系统弹出了无情的错误提示：文件损坏，无法读取。

不仅这张图片全毁了，我硬盘上的好几个核心工程文件也接连出现不可逆的数据坍塌。为什么？因为我把时钟周期拧得太短了！物理晶振强行拉高频率，导致时钟上升沿到来的间隔，硬生生小于数据信号穿透组合逻辑所需的物理延迟加上触发器内部的 $t_{setup}$。当上升沿来临时，送达触发器门前的数据根本没有稳定，触发器直接锁存了高低电平未定的亚稳态随机垃圾，进而将整套文件系统写成了一堆乱码。

所以千万记住：**时钟周期绝不能无限缩短，它必须完整包容系统关键路径上组合逻辑的最大延迟，再加上状态元件的 $t_{setup}$**。

### 单周期大构想与状态更新律

明确了时序底线后，我们要提出贯穿本讲乃至整个处理器设计的第一个核心假定：

> **定义**：**单周期处理架构（The Big Idea: One Instruction per Cycle）**
> 处理器每经历一次时钟上升沿的脉动，就必须且只能从头到尾彻底执行完一条完整的计算机指令。

很多敏锐的同学立刻会举手抗议：“老师，你之前明明在讲存储层次结构时反复告诫过我们，从 CPU 跨过总线去内存读取一次数据，通常需要耗费足足数百个时钟周期！你怎么可能在一个周期内搞定访存指令？”

确实如此。现实世界中内存访问极其昂贵，但在我们搭建第一个可用处理器的初始阶段，请大家允许我做出一个善意的工程妥协——**我们故意把时钟频率放得极低极慢**。

慢到什么程度？慢到哪怕把总线拉长，让数据从伯克利校园出发，坐大巴去一趟加州首府萨克拉门托（Sacramento），在那里的内存货架上翻找出数据再慢悠悠运回伯克利，时钟上升沿都还没有到来！在后续章节中，我们会引入分离缓存（Cache）技术在硬件层面兑现单周期命中的承诺，但现在，请在脑海中接受这个超慢时钟，确保每条指令都在单周期内完成全部物理流转。

伴随这一大构想的，是一条近乎铁律的硬件运行准则：

> **结论**：**单指令单状态更新原则**
> 在 RISC-V 架构中，除什么都不做的空操作（`nop`）外，**任意一条指令在一整个执行周期内的终极物理使命，就是精确修改系统中的某一个状态元件**。

我们可以把所有的 RISC-V 指令在脑海中快速过一遍：
- 算术逻辑指令（如 `add`, `sub`）：计算出新值，最终只修改目标寄存器（Register File 中的某一行）；
- 条件分支指令（如 `beq`）：通过比较判断跳转，最终只负责修改程序计数器（PC）；
- 访存写指令（如 `sw`）：运算目标地址，最终只负责修改数据内存（D-Mem 中的某个字）；
- 访存读指令（如 `lw`）：从内存抓取数据，最终也只负责修改目标寄存器。

偶尔有极少数设计极为紧凑的特例（比如跳转并链接指令 `jalr`），会在一个周期内巧妙地同时修改两个状态元件——既把返回地址写入链接寄存器，又把跳转目标灌入 PC。但绝大多数指令，一生都只为更新一个状态元件而运转。

### 状态元件选型与双内存拆分哲学

为了搭建能够闭环运转的处理器，我们需要从电子商店里采购四样不可或缺的核心状态部件：

```text
程序计数器 (PC)        32×32 寄存器堆 (RegFile)            内存模块 (I-Mem & D-Mem)
  +-----------+            +---------------+                     +---------------+
  |        Q  |-- CurrPC   | RS1    Data1  |-- R[rs1]            | Addr   DataR  |-- ReadData
--| D         |          --| RS2    Data2  |-- R[rs2]          --| DataW         |
  |        WE |-- 1      --| RSW           |                   --|          WE   |
  |    CLK ^  |          --| DataW  RegWEn |-- RegWEn          |    CLK ^      |
  +-----------+          |          CLK ^  |                     +---------------+
                         +---------------+
```
单周期 CPU 所需的四类核心状态部件端口分布与时钟属性。

#### 程序计数器 PC

我们可以将其视作系统中的第 33 个寄存器。它是一个独立的 32 位边沿触发寄存器，内部保存着当前正在执行的那条指令在内存中的 32 位绝对地址。

- $D$ 端为数据输入端口，接收计算完毕的下一跳指令地址（Next PC）；
- $Q$ 端为数据稳定输出端口，吐出当前指令的物理地址；
- $WE$ 为写使能端。由于在单周期架构中，时钟每跳一下就必须推进一条指令，因此单周期处理器的 PC 写使能信号被**永远硬连线固定为高电平 $1$**。

#### 寄存器堆 Register File

这是一个深度为 32 行、每行位宽为 32 位的双端口读、单端口写寄存器阵列。硬件规定编号为 0 的寄存器（`x0`）物理恒置为 0。

整个寄存器堆最精彩的设计，在于其读写端口具有完全截然不同的电路属性：

- **读端口（纯组合逻辑机制）**：提供两个 5 位的读寄存器地址输入端口 $RS1$ 与 $RS2$。只要把指令里抽出的 5 位编码加在地址线上，寄存器堆就像一个由多路选择器组成的查表组合逻辑网络，经过短暂的内部解码与寻址延迟后，立刻在数据输出端口 $Data1$ 与 $Data2$ 上吐出对应的 32 位寄存器值（即 $R[rs1]$ 与 $R[rs2]$）。**读操作全程不依赖时钟上升沿，不需要时钟信号参与**。
- **写端口（边沿触发时序机制）**：提供一个 5 位的写寄存器地址端 $RSW$（即指令中的目标寄存器 $Rd$ 字段）和一个 32 位的待写入数据端口 $DataW$。只有当时钟上升沿降临，且寄存器写使能信号 $RegWEn = 1$ 时，这 32 位数据才会被物理打入指定的寄存器行。因此，$RSW$ 和 $DataW$ 必须在上升沿到来前满足 $t_{setup}$ 建立时间要求。

> **提示**：很多初学者会疑惑，一条指令执行时，如果我不打算写寄存器，还能读吗？当然可以！比如条件分支指令 `beq rs1, rs2, label`，它的物理工作就是只读寄存器堆、算出差值、更新 PC，写使能 $RegWEn$ 全程为 0，写操作彻底休眠，读操作畅通无阻。

#### 拆分两套内存：I-Mem 与 D-Mem

在现代计算机体系结构中，程序代码段和全局数据段物理上共存于同一片平坦的主内存空间里。但在我们搭建单周期处理器时，我们必须在此处撒上全篇最重要的一个“工程谎言”：**我们将内存强行拆分为两块完全独立的硬件实体——指令内存（Instruction Memory, I-Mem）与数据内存（Data Memory, D-Mem）**。

为什么必须这么做？请回到“单周期完成一条指令”的核心大前提。

在单周期架构中，任何一条指令（比如 `lw x5, 0(x10)`）要执行完毕，必须先在周期的前半段访问内存去“读取指令机器码”；如果它是一条加载指令，它紧接着又必须在同一个周期内再次访问内存去“读取数据”。如果物理上只有一片单端口内存，同一个时钟周期内这片芯片既要接 PC 地址读指令，又要接 ALU 算出的地址读数据，就会爆发严重的物理硬件结构冲突（Structural Hazard）。

为了从容实现单周期运行，我们把这两块功能割裂：
- **指令内存（I-Mem）**：这是代码区的只读映射。由于处理器绝对不会在单周期执行中动态覆写指令自身，**我们干脆直接将 I-Mem 身上的时钟引脚拔掉！**将它彻底退化为一个纯组合逻辑黑盒：输入一个 32 位 PC 地址，内部逻辑门经过固定延迟后，直接在输出端吐出这 32 位的指令内容。
- **数据内存（D-Mem）**：承载程序的数据区，支持 Load 与 Store。具备 32 位访存地址端口、32 位写数据端口、内存写使能信号 $MemWEn$ 以及时钟同步引脚。若执行读操作（$MemWEn=0$），它表现为纯组合逻辑输出；若执行写操作（$MemWEn=1$），它在时钟上升沿完成物理写入。

当年最令我震撼的硬件事实，是硬件总线的“不可停摆性”：

当我们让单周期处理器执行一条最朴素的 `add x1, x2, x3` 时，由于物理连线是固化在电路板上的，ALU 算出的加法和依然顺着铜线一路灌进了 D-Mem 的地址引脚！D-Mem 根本不知道当前在跑什么指令，它依旧在默默工作，根据这个地址在存储阵列里检索，并在数据读出总线上持续吐出一长串数据。

这会破坏系统吗？完全不会。因为在执行 `add` 指令时，控制逻辑将 D-Mem 的写使能 $MemWEn$ 压制为 0，防止了数据被误写；同时下游的多路选择器也冷酷地屏蔽了 D-Mem 的输出总线。硬件一直在算，但它的输出被我们视作无关紧要的垃圾（Garbage）给丢弃了。

### 指令执行的五大生命周期阶段

无论指令集如何丰富，任何一条 RISC-V 指令在一个时钟周期内的流转旅程，在逻辑上均可以高度抽象为五个标准执行阶段（Five Stages）：

```text
  [IF: 取指]       [ID: 译码/读寄存器]      [EX: 执行]        [MEM: 访存]        [WB: 写回]
+------------+    +---------------+    +------------+    +------------+    +------------+
|  PC 发送   |    | 控制逻辑解析  |    | ALU 算术/  |    | D-Mem 读写 |    | 运算结果或 |
| I-Mem 读码 |===>| 读寄存器堆    |===>| 逻辑运算   |===>| (非访存指令|===>| 访存数据写 |
| PC+4 预备  |    | 立即数生成    |    | 目标地址算 |    | 绕道而行)  |    | 入 RegFile |
+------------+    +---------------+    +------------+    +------------+    +------------+
                                                                                 |
                                                                        包含目标寄存器的
                                                                        建立时间 t_setup
```
指令执行的五阶段逻辑划分流水线模型（单周期内全部依次穿透完成）。

- **阶段一：取指阶段（Instruction Fetch, IF）**
  由程序计数器 PC 提供当前地址，从指令内存 I-Mem 中检索并抓取 32 位机器指令字。取指的同时，专用加法器已在后台静默完成 `PC + 4` 的计算，为无分支场景的下一跳地址做好准备。
- **阶段二：译码与读寄存器阶段（Instruction Decode / Register Read, ID）**
  这颗 32 位机器码兵分两路：一路流入控制逻辑进行指令解析，各路多路选择器的选通信号即刻开始生成；另一路将其中的寄存器字段直接连入寄存器堆的读地址引脚，提取源操作数。
- **阶段三：执行阶段（Execute, EX）**
  算术逻辑单元 ALU 大显身手的舞台。无论是计算两数相加减、执行位运算，还是为访存指令累加基地址与偏移量，都在本阶段完成。我个人不太喜欢“Execute”这个英文词，因为它听起来像古代刑场上的死刑处决（Kill），但它真实表达的意思就是“把该算的账算清楚”。
- **阶段四：访存阶段（Memory Access, MEM）**
  专门为 Load 与 Store 指令设置的关卡。如果当前运行的是一条普通的 `add` 算术指令，数据流根本不进数据内存，就像路上遇到了抛锚的卡车，数据直接从旁边辅道绕开奔赴下一站，处理器在该阶段几乎处于生理休眠状态。
- **阶段五：写回阶段（Write Back, WB）**
  将 ALU 产生的运算和、或是 D-Mem 读出的数据，精准拉回到寄存器堆的写数据端口，在时钟上升沿最终沉淀入目标寄存器 $Rd$。

> **易错点**：**关键路径上的建立时间归属**
> 当我们在期末考试或工程设计中计算处理器的“单周期最小周期时间”（即关键路径延迟求和）时，请务必记住：**阶段五（写回阶段）的时间开销，必须把寄存器堆写端口的建立时间 $t_{setup}$ 完整包容进去**。因为只有在上升沿到来前满足了 $t_{setup}$，写回才算真正合法生效。

### 从零搭建第一条指令：实现加法运算

热身完毕，现在让我们正式打响硬件构建的第一枪：**在空白的电路板上，只用基础元件把 `add` 指令跑起来！**

回顾 RISC-V 基础指令集，R 型加法指令的汇编格式为 `add rd, rs1, rs2`。其寄存器传输级语言（RTL）语义为：

$$R[rd] \leftarrow R[rs1] + R[rs2]$$

$$PC \leftarrow PC + 4$$

整整 32 位的 R 型二进制机器码格式分布如下：

```text
 31       25 24     20 19     15 14  12 11      7 6            0  (位序号)
+-----------+---------+---------+------+---------+--------------+
|  funct7   |   rs2   |   rs1   |funct3|   rd    |    opcode    |
|  0000000  | (5 bits)| (5 bits)| 000  | (5 bits)|   0110011    |
+-----------+---------+---------+------+---------+--------------+
```

#### 纯硬件直连走线

现在，让我们把 PC、I-Mem、寄存器堆、一个独立的 Dedicated 加法器以及算术加法器推上试验台，铺设铜线：

```text
                             +-----------+
                             |    +4     | (常量 4)
                             +-----+-----+
                                   |
                     +-------+     v
                     |       |  +------+
                     |       +->|  +   |-----+ (计算出 PC+4)
                     |          +------+     |
                     v                       |
                  +------+                   |
             +--->|  PC  |                   |
             |    +---+--+                   |
             |        |                      |
             |        | CurrPC               |
             |        v                      |
             |    +-------+                  |
             |    | I-Mem |                  |
             |    +---+---+                  |
             |        |                      |
             |        | Inst[31:0]           |
             |        v                      |
             |   +----+--------------------------------+
             |   | 分解指令字段并物理直连:             |
             |   | Inst[19:15] -> RS1 (5位)            |
             |   | Inst[24:20] -> RS2 (5位)            |
             |   | Inst[11:7]  -> RSW / Rd (5位)       |
             |   +----+-------------+------------------+
             |        |             |
             |        v             v
             |     +-------------------+
             |     |   Register File   |
             |     |                   |
             |     | Data1       Data2 |
             |     +---+-----------+---+
             |         |           |
             |         | R[rs1]    | R[rs2]
             |         v           v
             |       +---------------+
             |       | 运算加法器 +  |
             |       +-------+-------+
             |               |
             |               | 加法运算和
             |               v
             +---------------+ (连回 DataW，同时 PC+4 连回 PC 输入端)
```
纯加法指令的数据通路完整拓扑：利用指令固定字段实现硬件硬连线。

请仔细审视这幅纯粹的拓扑图，体会 RISC-V 架构设计先驱们的绝妙匠心：
- 指令内存 I-Mem 吐出 32 位机器码的一瞬间，我们根本不需要写任何复杂的解码软件，直接用几束物理铜线，把第 15 到 19 位扯出来插进寄存器堆的 $RS1$ 端口；把第 20 到 24 位扯出来插进 $RS2$ 端口；把第 7 到 11 位扯出来插进写目标寄存器 $RSW$ 端口！
- 这就是为什么 RISC-V 无论指令如何变化，源操作数与目标寄存器的比特位置永远固化在相同区间的根本原因——**硬件可以直接把铜线焊死在那些针脚上**。

#### 加法指令的一生（动态时序复盘）

让我们踩慢时钟，全景推演一条加法指令在电路里的激荡过程：

1. **时钟上升沿 1 到来**：PC 内部触发器受激发，立刻向输出引脚吐出当前指令的物理内存地址。
2. **取指与 PC 自增并行推进**：
   - 当前 PC 沿着走线直通只读 I-Mem，I-Mem 组合逻辑开始寻址，稍顷吐出代表 `add` 的 32 位指令机器码。
   - 与此同时，当前 PC 还分流进入一个专属的小加法器，另一侧硬连线固定接入常数 4。这个加法器立刻开始工作，迅速算出了 `PC + 4` 的数值，并将其平稳地输送到 PC 寄存器的 $D$ 输入端门前静静等待。
3. **寄存器读出**：从 I-Mem 喷涌而出的指令码，通过预埋的铜线将 rs1、rs2 字段打入寄存器堆。寄存器堆内部逻辑迅速反应，在 $Data1$ 和 $Data2$ 端吐出两个源寄存器的当前数值。
4. **算术求和**：两路 32 位数据进入核心加法器，加法逻辑门链路震荡后趋于稳定，输出 32 位的加法和。
5. **准备写回并迎接上升沿 2**：
   - 加法和沿着漫长的长途导线，一路回拉至寄存器堆的写数据端口 $DataW$。
   - 此时在寄存器堆这一侧，$RSW$（由 rd 驱动）和 $DataW$（加法和）均已建立完毕并保持稳定，稳稳早于 $t_{setup}$ 窗口。
   - 此时在控制逻辑一侧，控制寄存器写使能的 $RegWEn$ 恒定拉高为 1；PC 的写使能也恒定为 1。
   - **时钟上升沿 2 骤然降临！**
   - 砰！PC 寄存器瞬间把门前等候的 `PC + 4` 锁入内部，指向下一条指令；
   - 砰！寄存器堆内部对应目标寄存器行的触发器瞬间击发，把 $DataW$ 处的加法和安全落盘锁定。

一条真正的硬件加法指令，就这样在电平震荡与时钟脉冲的交织下完美落地！在座的各位完全配得上一阵热烈的掌声——我们真正实现了从无到有，徒手搭建了一台能跑机器指令的物理硬件！

### 演进扩展：一条控制线搞定减法运算

加法已经跑通了，那我们要怎么让机器同时支持减法指令 `sub rd, rs1, rs2`？

难道我们要推倒重来，重新铺设一整套截然不同的电路网络吗？让我们把 `add` 和 `sub` 的 32 位机器码并排摊在桌上做一次对比：

| 指令 | `funct7` (31:25) | `rs2` (24:20) | `rs1` (19:15) | `funct3` (14:12) | `rd` (11:7) | `opcode` (6:0) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| `add` | `0000000` | 源寄存器 2 | 源寄存器 1 | `000` | 目标寄存器 | `0110011` |
| `sub` | `0100000` | 源寄存器 2 | 源寄存器 1 | `000` | 目标寄存器 | `0110011` |

请盯着这张表看三秒钟。这正是体现顶尖指令集架构美学的地方！

一个拙劣的 ISA 设计，可能会让 `add` 和 `sub` 采用不同的寄存器排布，甚至分配风马牛不相及的操作码，把硬件工程师逼疯。但 RISC-V 展现出了惊人的优雅与克制：**两条指令的操作码完全相同、三组寄存器位置完全相同、`funct3` 也完全相同，全身上下 32 个比特位中，有且仅有第 30 位（`funct7` 从左往右数的第二位）差了一个比特！**

- 当第 30 位是 0 时，我们要算加法；
- 当第 30 位是 1 时，我们要算减法。

因此，原本专用的“加法器”黑盒在此刻必须退役，换上功能更为通用的**算术逻辑单元（ALU）**。

```text
                  +----------------------------------+
                  |         控制逻辑 (Control)       |
                  +-----------------+----------------+
                                    |
     Inst[30] (以及 funct3/opcode)  | ALU Select 控制总线
                                    v
                              +-----+-----+
          R[rs1] ------------>| \         |
                              |  \  ALU   |-----> 运算结果 (加法和 / 减法差)
          R[rs2] ------------>|  /        |
                              +-----------+
```
控制逻辑抽取指令特征比特生成 ALU Select 信号，动态切换运算模式。

我们将指令内存出来的第 30 位引脚（乃至整条指令机器码）牵引至上方的**控制逻辑中枢**。控制逻辑内部的解码电路查验后发现：哦，今天来了一位减法客人。于是控制逻辑顺势拉高控制线，向 ALU 下发减法操作指令。

还记得我们上一讲推导过的“利用异或门与求补进位实现的一体化加减法器”吗？ALU 内部接到这个信号，立刻通过异或门将第二操作数按位取反，同时把最低进位 $C_0$ 垫高为 1，一举完成了两补码意义下的加法求减！

数据通路的其他部分（PC 自增、寄存器寻址、写回拓扑）完全无需做任何变更。仅凭多插进控制逻辑的一根线，我们的处理器版图瞬间翻倍，同时支持了加法与减法！

### 接入立即数：多路选择器与符号扩展的协作

课堂还剩下最后几分钟，我们要迎接今天最硬核的一场硬仗：支持立即数加法 `addi rd, rs1, immediate`。

仔细审视 I 型指令 `addi` 的语义：

$$R[rd] \leftarrow R[rs1] + \text{SignExtend}(imm[11:0])$$

它与 R 型指令存在极为关键的两大异同：
1. **相同点**：源操作数 1 依然由 $RS1$ 供给，运算完毕后依然写回目标寄存器 $Rd$；
2. **相异点**：第二操作数不再由寄存器 $RS2$ 提供，而是硬编码在指令自身高 12 位里的立即数常量！

这立刻引爆了一个严重的物理冲突：**ALU 的第二输入端口 $B$，现在面临着两个争抢驱动权的物理源头——一个是来自寄存器堆的 $Data2$，另一个是来自指令字内部的立即数！**

两个不同的输出引脚，绝对不能用导线直接焊死在同一个输入端口上，否则会发生可怕的总线冲突与电路烧毁。当我们面临“二者选其一”的经典窘境时，该召唤谁？

毫无疑问，必须去零件店抱回我们在上一讲学过的利器——**二选一多路选择器（2-to-1 MUX）**！

同时，指令中的立即数字段只有短短的 12 位（占据第 20 到 31 位），而我们的 ALU 运算输入总线足足有 32 位宽。在数字电路里，**严禁让任何输入引脚处于悬空浮接（Floating）状态**，否则外界的电磁干扰会将其随机感应为未知的逻辑电平。我们必须引入一个专门的组合逻辑模块——**立即数生成器（Immediate Generator, 简称 ImmGen）**。

```text
                                        +-------------------+
                                        | 控制逻辑 (Control)|
                                        +----+---------+----+
                                             |         |
                                      ALUop  |         | BSel
                                             |         |
                                             v         v
                                        +----+----+  +---+
                     Inst[19:15] ------>|   RS1   |  | M |
                                        |         |  | U |
                     Inst[24:20] ------>|   RS2   |  | X |
                                        +----+----+  +---+
                                             |         ^
                                             | Data2   |
                                             +---------+ (0 选通端)
                                                       |
        Inst[31:20] (12位) -> [ ImmGen 符号扩展 ] -----+ (1 选通端)
                                  (32位立即数)
```
利用多路选择器 MUX 调解寄存器与立即数对 ALU 第二输入端口的驱动权争夺。

#### 立即数的“符号位涂抹”法

ImmGen 内部究竟在做什么？它接收指令高 12 位（`Inst[31:20]`），将其转换为一个合法的 32 位补码有符号整数。

由于是补码，整个数值的正负极性由第 31 位（即 12 位立即数的最高符号位）一锤定音：
- 如果第 31 位是 0，说明这是一个正数或零，高 20 位必须全部补填 0；
- 如果第 31 位是 1，说明这是一个负数，高 20 位必须全部补填 1。

在物理连线层面，这简直再直白不过了。我们保留低 12 位直通不变，然后把第 31 位这根铜线引出来，像粉笔刷涂抹一样，**直接并联分接、涂抹（Smear / Copy）到输出端的全部高 20 位引脚上**。无需复杂的时序逻辑，瞬间完成完美的算术符号扩展！

#### 旁路逻辑下的硬件冷眼

现在，整条数据通路的拼图完整合拢：
1. 来自 I-Mem 的 12 位立即数进入 ImmGen，扩展为 32 位后，接入 MUX 的第 1 选通端；
2. 寄存器堆的 $Data2$ 输出端，接入 MUX 的第 0 选通端；
3. MUX 的输出直连 ALU 的 $B$ 端口；
4. 控制逻辑吐出一位选通控制信号 $BSel$：
   - 当执行 `add` 或 `sub` 时，$BSel = 0$，放行寄存器数据；
   - 当执行 `addi` 时，$BSel = 1$，放行符号扩展后的立即数。

在这里，请大家再次品味我们刚才提到的硬件哲学。

当一条 `addi` 指令进入处理器时，指令的第 20 到 24 位依然盲目地通向寄存器堆的 $RS2$ 输入端。寄存器堆依旧如实履行自己的组合逻辑职责，根据这 5 位编号在内部读出某个寄存器的数值，并固执地吐在 $Data2$ 总线上。

这会造成系统混乱吗？

**完全不会。因为 MUX 正冷冷地站在前面把守大门。**

MUX 收到来自控制逻辑的 $BSel = 1$ 指令，它轻蔑地对着 $Data2$ 挥了挥手：“对不起这位兄弟，今天走立即数通道，你吐出来的纯粹是垃圾，我彻底忽略你。”数据在 MUX 面前被硬生生阻断，毫无损耗地丢弃在电平的海洋中。这就是基于硬件选择器的优雅调度。

### 迈出第一步：原型的诞生与后续展望

回顾这趟充实的工程探索旅程，我们从德州立法自建电厂的宏观能耗，一路杀到单周期 CPU 内部的铜线走向与逻辑门连接。

我们利用程序计数器、两块解耦的存储抽象、精巧的寄存器堆、一个多功能 ALU 以及一个两选一多路选择器，实打实地组装出了一套完整、闭环、能够独立执行 `add`、`sub` 与 `addi` 三条核心指令的物理单周期计算机原型！
