### 缓存的几何直观与地址切分

在开始推演之前，我们必须先对物理世界建立空间感。

我们面对的主存（Main Memory）本质上是一个巨大的字节数组。在 32 位物理地址空间下，从 `0x00000000` 一直到 `0xFFFFFFFF`，总共拥有 $2^{32}$ 个字节。在我们的体系模型里，主存就像远在萨克拉门托（Sacramento）的大仓库，存着所有你需要的东西，但路途遥远，跑一趟代价极高。

而缓存就在我们手边，容量小得多，但触手可及。在本次推演中，我们设定一个典型的缓存规格：
- 缓存总容量为 16 KiB（$16 \times 1024 = 16384$ 字节）；
- 缓存块大小（Block Size / Cache Line）为 4 个字（Words）。

做个简单的单位换算：在 32 位架构中，每个字是 4 个字节，因此 4 个字等于 16 字节。这意味着我们每次去萨克拉门托出差访问主存，绝不会小家子气地只拿 1 个字节回来，而是一口气抓取连续的 16 字节整块搬回缓存。

#### 矩形模型确定高与宽

每次画缓存时，我脑海中浮现的永远是一个矩形：

```text
+--------------------------------------------------------+ ---
|  行 0    : [ 有效位 ]  [  标签 Tag  ]  [ 数据块 16 字节 ] |  ^
|  行 1    : [ 有效位 ]  [  标签 Tag  ]  [ 数据块 16 字节 ] |  |
|  ...     : [ 有效位 ]  [  标签 Tag  ]  [ 数据块 16 字节 ] | 1024 行 (高)
|  行 1023 : [ 有效位 ]  [  标签 Tag  ]  [ 数据块 16 字节 ] |  |
+--------------------------------------------------------+ v
|<--------------------- 16 字节 (宽) ------------------->|
```
*图解说明：矩形缓存由行数（高度）与行宽（宽度）构成，面积严格守恒于总容量。*

矩形的几何关系极其直观：
- 矩形总面积 = 缓存容量 = 16 KiB；
- 矩形宽度 = 块大小 = 16 字节；
- 矩形高度 = 行数（Lines / Sets）= $\frac{16 \text{ KiB}}{16 \text{ B}} = 1024$ 行（即 $2^{10}$ 行）。

这 1024 行数据进入缓存，编号从 0 到 1023。

#### 物理地址的三字段拆分

当 CPU 发出一个 32 位地址时，硬件线路必须将其精准剥离为三个部分：标签（Tag）、索引（Index）与块内偏移（Offset）。

```text
+-------------------------+--------------------+------------------+
|      Tag (标签位)       |   Index (索引位)   |  Offset (偏移位) |
|         18 位           |       10 位        |       4 位       |
|       [31 : 14]         |      [13 : 4]      |     [3 : 0]      |
+-------------------------+--------------------+------------------+
```
*图解说明：32 位物理地址在直接映射缓存中的标准字段划分。*

我们严格倒推这三部分的位数来源：
1. **块内偏移（Offset）**：
   偏移量的作用是确定在这一行的 16 个字节中，CPU 到底想要读取哪一个具体字节（哪一列）。既然一行有 16 字节，从 16 个位置中唯一定位一个，需要满足 $2^k = 16$，因此 $k = 4$ 位。偏移量范围从 `0000`（0）到 `1111`（15）。
2. **缓存索引（Index）**：
   索引的作用如同行号。缓存共有 1024 行，硬件必须唯一定位这行数据若存在，到底应该落在 1024 行中的哪一行。标识 1024 个互斥状态需要满足 $2^m = 1024$，因此 $m = 10$ 位。索引范围从 0 到 1023。
3. **标签（Tag）**：
   主存空间庞大，可以视作数千个 16 KiB 大小的缓存块在不断重复。无数个主存地址由于低位相同，都会映射到相同的 Index。标签就是用来区分当前驻留在此处的到底是哪一段内存块。标签位即为扣除其余字段后剩下的所有高位：$32 - 10 - 4 = 18$ 位。

> **定义**：直接映射缓存（Direct-Mapped Cache）的查表法则可以凝练为 **IVTO 决策流**：
> 1. **I (Index)**：用地址中的 Index 字段定位到缓存中唯一的候选行（要么在这行，要么全盘落空）；
> 2. **V (Valid)**：检查该候选行的有效位。若为 0 说明是开机未初始化的随机电平垃圾，直接判定未命中；
> 3. **T (Tag)**：若 Valid 为 1，比对行内的 Tag 与地址中的 Tag。完全一致则命中，不一致则未命中；
> 4. **O (Offset)**：命中后，根据 Offset 提取指定字节或字交付 CPU。

### 端到端访存实战：连续四次加载字的硬件追踪

现在我们开启计算机。在开机那一瞬间，缓存处于极寒状态（Cold State），全部 1024 行的有效位（Valid）全为 0。

虽然硬件电线上在物理层面必定呈现某种高低电平（可能是随机的 0 或 1），但那全是无意义的垃圾数据。因为 Valid 为 0，我们确保系统绝不会误读这些脏杂质。

接下来，CPU 顺序发出 4 条 `lw`（Load Word）加载字指令，目标地址依次为：
1. `0x00000014`
2. `0x0000001C`
3. `0x00000034`
4. `0x00008014`

为了具象化，我们设主存初始内容如下：
- 地址 `0x00000010 ~ 0x0000001F` 存放 4 个连续字，代号分别为 `A`（`0x10`）、`B`（`0x14`）、`C`（`0x18`）、`D`（`0x1C`）；
- 地址 `0x00000030 ~ 0x0000003F` 存放 4 个连续字，代号为 `E`（`0x30`）、`F`（`0x34`）、`G`（`0x38`）、`H`（`0x3C`）；
- 地址 `0x00008010 ~ 0x0000801F` 存放 4 个连续字，代号为 `I`（`0x8010`）、`J`（`0x8014`）、`K`（`0x8018`）、`L`（`0x801C`）。

#### 第一次访存：地址 0x00000014

将十六进制地址 `0x00000014` 展开为 32 位二进制：
`0000 0000 0000 0000 0000 0000 0001 0100`

依据 18-10-4 划分：
- **Tag**（高 18 位）：`0000 0000 0000 0000 00` = `0x00000`
- **Index**（中 10 位）：`00 0000 0001` = 1
- **Offset**（低 4 位）：`0100` = 4

执行 IVTO：
- **I**：定位到行 1。如果这个地址的数据存在于缓存中，这是它唯一可能存在的位置。
- **V**：检查行 1 的 Valid 位。当前是 0。
- **结果**：发生未命中（强制缺失 / Compulsory Miss）。

既然未命中，我们必须动身前往萨克拉门托（主存）。既然大老远跑一趟，我们绝不仅取地址 `0x14` 这 4 个字节，而是将 Offset 从 `0000` 到 `1111` 的整行全部带回（即地址 `0x00000010` 到 `0x0000001F`，涵盖 A、B、C、D 四个字）。

回到缓存，执行状态写入：
- 行 1 的数据区填入字 `A, B, C, D`；
- 行 1 的 Tag 记录为 `0x00000`；
- 行 1 的 Valid 改写为 1。

最后根据 Offset = 4，提取出位于字节偏移 4 到 7 的字，成功向 CPU 返回数据 `B`。

#### 第二次访存：地址 0x0000001C

CPU 发出指令 `lw` 读取地址 `0x0000001C`。
转换为 32 位二进制：
`0000 0000 0000 0000 0000 0000 0001 1100`

字段拆分：
- **Tag**：`0x00000`
- **Index**：`00 0000 0001` = 1
- **Offset**：`1100` = 12

执行 IVTO：
- **I**：检查行 1；
- **V**：Valid 此时为 1，数据有效；
- **T**：比较 Tag，缓存行内 Tag 是 `0x00000`，地址 Tag 也是 `0x00000`，完全匹配！
- **O**：命中（Cache Hit）！Offset = 12，直接提取字节偏移 12 到 15 的字，返回数据 `D`。

> **结论**：这就是**空间局部性（Spatial Locality）**的绝佳体现！虽然这是我们第一次向 CPU 交付 `0x1C` 的数据，但由于我们在上次访存 `0x14` 发生未命中时，顺手打包抓取了它周围的邻居，使得 `0x1C` 享受了零惩罚的高速命中。两次访问，只跑了一趟主存。

#### 第三次访存：地址 0x00000034

CPU 发出指令 `lw` 读取地址 `0x00000034`。
转换为 32 位二进制：
`0000 0000 0000 0000 0000 0000 0011 0100`

字段拆分：
- **Tag**：`0x00000`
- **Index**：`00 0000 0011` = 3
- **Offset**：`0100` = 4

执行 IVTO：
- **I**：寻址到行 3；
- **V**：行 3 的 Valid 位依然为 0，全是冷垃圾；
- **结果**：未命中（强制缺失）。

处理流程：
奔赴主存，提取地址 `0x00000030` 至 `0x0000003F`（Offset `0000` 到 `1111`）的完整 16 字节，包含字 `E, F, G, H`。
写入缓存行 3：
- 填入数据 `E, F, G, H`；
- Tag 置为 `0x00000`；
- Valid 置为 1；
- 按 Offset = 4 提取出字 `F` 返回。

#### 第四次访存：地址 0x00008014

CPU 发出指令 `lw` 读取地址 `0x00008014`。
转换为 32 位二进制：
`0000 0000 0000 0000 1000 0000 0001 0100`

仔细观察字段划分：
- **Tag**（高 18 位）：`0000 0000 0000 0000 10` = 2
- **Index**（中 10 位）：`00 0000 0001` = 1
- **Offset**（低 4 位）：`0100` = 4

执行 IVTO：
- **I**：寻址到行 1；
- **V**：Valid 位是 1，数据看似有效；
- **T**：比对 Tag！地址要求的 Tag 是 2，但行 1 当前记录的 Tag 是 0。Tag 不匹配！
- **结果**：未命中（冲突缺失 / Conflict Miss）。

这里发生了一次典型的驱逐替换。虽然行 1 里住着的 `A, B, C, D` 刚刚还过得很舒坦，但因为直接映射缓存的硬性规则，`0x00008014` 这个新租客也必须落脚在行 1。老数据必须被无情踢走。

我们奔赴主存萨克拉门托，抓取 `0x00008010 ~ 0x0000801F` 的 16 字节数据（字 `I, J, K, L`）：
- 覆写行 1 的数据区为 `I, J, K, L`；
- 更新行 1 的 Tag 为 2；
- Valid 保持为 1；
- 按 Offset = 4 取出字节偏移 4 到 7 的字，交付数据 `J`。

#### 核心思辨：抽象屏障与程序员视角

推演到这里，如果你觉得机械、甚至开始觉得“无聊”，那正是我想要的效果——因为这意味着你已经真正穿透了底层的寻址机理。

这里有两个在课堂上被高频问及的精彩问题，值得深思：

第一，**软件程序员能否通过编写代码改善缓存表现？**
答案是绝对可以。当你理解了缓存的运作原理，就会明白：让数据结构紧凑排列、让循环按内存连续地址顺序推进（利用空间局部性与时间局部性），程序就能飞速狂奔；反之，若在堆内存中随机构造指针链表、天女散花般跳跃访问，缓存命中率就会雪崩，你的 CPU 将把绝大部分生命周期耗费在等总线传输上。

第二，**软件代码在运行时如何知道 Tag、Index、Offset 是怎么切分的？**
答案是：**软件根本不需要知道**。这里存在一道森严的抽象屏障（Abstraction Barrier）。
当你用 C 语言或汇编编写程序时，你操作的永远只是纯粹的 32 位地址（比如 `0x0000001C`）。你不需要在软件中做任何位移和掩码提取。
字段的剥离是在抽象屏障之下、由硬件物理连线自动完成的。芯片上布置着一组物理分线器，地址总线上的对应引脚直接焊接到比较器和多路选择器上。这一切对上层软件是完全透明的。

### 硬件数据通路与电路微架构

为了破除大家对“硬件怎么实现”的神秘感，我们把上述逻辑还原为真实的数字逻辑门电路。

```text
               32 位物理地址 [31:0]
                     |
       +-------------+-------------+
       |             |             |
  [31:14] (18位)  [13:4] (10位)   [3:0] (4位)
      Tag           Index        Offset
       |             |             |
       |             v             |
       |       +------------+      |
       |       | 1024行缓存 |      |
       |       +------------+      |
       |       | 行0: V,Tag,Data   |
       |       | 行1: V,Tag,Data   |
       |       | ...        |      |
       |       +------------+      |
       |             | (选中行)    |
       |       +-----+-----+       |
       |       |           |       |
       |      Tag (18位)  Valid(1位) |
       |       |           |       |
       v       v           |       |
     +-----------+         |       |
     | 18位比较器 |         |       |
     +-----------+         |       |
           | (相等=1)      |       |
           +-------+   +---+       |
                   |   |           |
                   v   v           |
                 +-------+         |
                 | 与门  |---------> [ 命中判定 Hit / Miss ]
                 +-------+         |
                                   |
              行内 16 字节数据     |
                     |             |
                     v             |
           +--------------------+  | Offset[3:2]
           | 4选1 多路复用器 MUX |<--+ (高2位选字)
           +--------------------+
                     |
                     v
           [ 32 位数据输出 (Data) ]
```
*图解说明：直接映射缓存硬件数据通路图。分线器剥离字段，比较器与与门判定命中，多路复用器选出目标字。*

硬件数据通路的运作极为精简高效：
1. **行选择**：10 位 Index 信号线接入解码器，从 1024 行中瞬间激活唯一的候选行，并拉出该行的 Valid 位、18 位 Tag 与 16 字节 Data。
2. **命中逻辑**：一个 18 位比较器对比地址中的 Tag 与该行存有的 Tag。若两者相等，比较器输出 1。接着，该信号与行的 Valid 位接入一个与门。只有在“数据有效”且“标签匹配”同时成立时，与门才拉高命中信号（Hit = 1）。
3. **数据截取**：若执行的是 `lw` 加载字，由于字必须 4 字节自然对齐，Offset 的最低两位 `[1:0]` 在硬件上恒为 `00`（可能出现的偏移量只有 0、4、8、12）。因此，多路选择器（MUX）只需接收 Offset 的高两位 `[3:2]`，即可从 4 个候选字中瞬间选出所需的目标字送上 CPU 数据总线。

### 缓存写入策略与状态一致性

到目前为止，我们所有的推演全部集中在“读取”（Read）操作上。在纯读取场景下，缓存就像一份只读镜像，哪怕丢失或被覆盖，也不会引发灾难。

但一旦 CPU 执行 `sw`（Store Word）写入指令，性质就彻底变了。写入操作会修改数据值（例如把地址中的字 `D` 改写为 `E`）。既然修改了手头的缓存，萨克拉门托主存大仓库里的原件要不要同步改？何时去改？

体系结构设计者由此发展出了两种截然不同的策略。

#### 写直达策略（Write-Through）

写直达的核心思想极其朴素：**只要修改，立即同步**。
每当 CPU 执行写操作更新了缓存中的某个块，缓存控制器必须立刻发起一次主存写事务，直接跨越总线去萨克拉门托更新原始数据。

- **优势**：缓存与主存始终保持严格一致，逻辑清晰，断电或发生硬件错误时不易丢失数据。
- **致命缺陷**：**极其缓慢**。主存的写延迟可能高达数百个时钟周期。想象一下你在一段密集的循环中连续写入数组：第一次把 `D` 改为 `E`，第二次改为 `F`，第三次改为 `G`……每一次写指令，CPU 都必须硬生生停下来等待漫长的主存总线交互完成。总线带宽将被瞬间挤爆，系统性能呈断崖式下跌。

#### 写回策略（Write-Back）

写回策略践行了高级开发者的精髓——**极致的懒惰（Lazy）**。

它的逻辑是：既然现代 CPU 的每一次访存（无论是读是写）都**无一例外地必须先查缓存**，而绝不会绕过缓存直接窥探主存，那我为什么非要现在火急火燎地跑去萨克拉门托呢？

在写回策略下：
1. CPU 写入时，仅仅原地修改手头缓存中的数据；
2. 主存里的数据暂时保留不管；
3. 只有当未来某一天，有新的数据块因为冲突不得不挤占这一行、把这个被修改过的块驱逐（Evict）出门时，或者在系统关机刷盘时，我们才将它一次性写回主存。

> **易错点**：写回策略引入了一个严重的技术现实——**数据不一致（Inconsistency）**。
> 在写回机制下，主存中对应位置的数据是过时的，我们称之为**陈旧数据（Stale Data）**，就像放过了期的硬面包一样失去了新鲜度。但在单核场景下，只要所有读取都优先命中缓存中的最新副本，这种不一致就完全无害。

为了支撑写回机制，缓存必须在每行引入一个全新的状态标记——**脏位（Dirty Bit）**。
- `Dirty = 0`（Clean）：说明该缓存行自载入以来从未被 CPU 写过，它与主存的数据完全一致。被替换驱逐时，可以直接覆写抛弃，不需要产生任何主存写回开销。
- `Dirty = 1`（Dirty）：说明该缓存行被 CPU 写入篡改过，内容与主存不一致。当它被驱逐时，必须产生一次写回（Write-Back）操作将整行推入主存更新。

| 评估维度 | 写直达（Write-Through） | 写回（Write-Back） |
| :--- | :--- | :--- |
| **主存一致性** | 始终严格一致，主存时刻保持最新 | 存在暂时的不一致，主存存在陈旧数据 |
| **写操作延迟** | 极高（每次写都受限于主存延迟） | 极低（直接完成于近端高速缓存） |
| **总线流量开销** | 巨大（高频写入时反复冲击总线） | 极小（多次修改合并为单次批量写回） |
| **硬件状态元数据** | 只需 Valid 位 | 必须配备 Valid 位与 Dirty 位 |

### 块大小权衡与乒乓效应

回到最初画的那个矩形：总面积固定为 16 KiB。
我们当时规定每个块是 16 字节，总共 1024 行。那我们能不能剑走偏锋，设计一个形状极端怪异的矩形？

#### 极细高矩形（小块大小）的缺陷

假设我们把块大小压缩到极限：**每个块只有 1 个字节**。
面积仍然是 16 KiB，但行数暴增到 16384 行。

如果采用这种结构，每次发生未命中，你千辛万苦跑一趟萨克拉门托，脚都走酸了，**却只咬了一小口（仅带回 1 个字节）**。
如果你的程序接下来要读取下一个字节，你又得重新长途跋涉跑去主存！小块大小彻底扼杀了**空间局部性**的红利，严重拉高了程序的实际缺失率。

#### 极扁宽矩形（超大块大小）的代价

那反过来，既然带回邻居能利用空间局部性，我们干脆把块大小做成 16 KiB 呢？
整个缓存只有孤零零的 1 行，这一行长达 16384 字节。

这样做的下场同样是灾难性的：
1. **缺失惩罚（Miss Penalty）飙升**：未命中一次，你需要背着大麻袋去萨克拉门托一口气搬运成千上万个比特。总线传输时间拉得极长，未命中的代价变得不可承受。
2. **块数量匮乏引发“乒乓效应”（Ping-Pong Effect / Thrashing）**：
   想象你的程序中有一段极其常见的数组复制循环：
   ```c
   for (int i = 0; i < N; i++) {
       b[i] = a[i];
   }
   ```
   假定数组 `a` 和 `b` 位于内存的不同区域：
   - 迭代 0：读取 `a[0]`。未命中，从主存把包含 `a` 的大块载入缓存那唯一的一行；
   - 接着要写入 `b[0]`。`b` 不在缓存中！未命中，被迫把刚才千辛万苦搬来的 `a` 整个踢出去，载入包含 `b` 的大块；
   - 迭代 1：读取 `a[1]`。缓存里现在住的是 `b`，再次未命中！踢出 `b`，载入 `a`；
   - 接着写入 `b[1]`。缓存里住的是 `a`，再次未命中！踢出 `a`，载入 `b`……

两个变量在唯一的一行里像打乒乓球一样来回互相抽打、死命驱逐对方。每一次内存访问都以未命中告终，系统陷入彻底的颠簸（Thrashing）死循环。

#### AMAT 的黄金平衡点

```text
  未命中率 (Miss Rate)                缺失惩罚 (Miss Penalty)
  ^                                   ^
  |  \                             /  |                /
  |   \                           /   |               /
  |    \                         /    |              /
  |     \_______最佳区间________/      |             /
  +--------------------------> 块大小 +--------------------------> 块大小
```
*图解说明：块大小对未命中率与缺失惩罚的相反作用机制。*

我们借助平均内存访问时间（AMAT，Average Memory Access Time）的经典公式来衡量总性能：
$$\text{AMAT} = \text{Hit Time} + \text{Miss Rate} \times \text{Miss Penalty}$$

- 增大块大小，起初能够充分利用空间局部性，使未命中率（Miss Rate）显著下降；
- 但块若无节制地继续变大，不仅块数量急剧缩水导致乒乓冲突恶化、使 Miss Rate 反弹，而且每一次搬运的数据量剧增使得缺失惩罚（Miss Penalty）单调直线上升；
- 两条曲线相乘，使得最终的 AMAT 呈现出一条 U 型曲线。体系结构工程师的终极任务，就是在极瘦与极胖之间，寻找那个让 AMAT 最优的**最佳甜蜜点（Sweet Spot）**。

### 缺失类型与全相联缓存

当缓存未命中发生时，我们可以从成因上对其进行归类。

#### 缺失类型的分类原则

从体系结构根源上，未命中首先划分为两大阵营：
1. **强制缺失（Compulsory Miss / Cold Miss）**：
   这是物理规律决定的不可抗力。系统刚开机或程序刚启动时，某个内存块在此之前**从未被 CPU 访问过**。无论你的缓存造得有多庞大、结构有多精巧，面对一个未曾谋面的新地址，命中是绝不可能发生的。第一次碰壁必定是强制缺失。
2. **非强制缺失（Non-compulsory Miss）**：
   除强制缺失以外的所有缺失。
   其中最重要的一个子类别就是**冲突缺失（Conflict Miss）**：当多个不同的内存块因为映射规则恰好争夺缓存中的同一行时（比如我们前文追踪示例中的 `0x8014` 撞上 `0x14`，或者循环中的乒乓效应），由于有限的槽位竞争把尚未过时的数据提前挤出，后续再次访问该被挤出的数据时发生的未命中，就叫冲突缺失。

> **提示**：在很多复杂的场景下，非强制缺失还会细分出容量缺失（Capacity Miss）等概念。但在本讲的考察要求中，牢牢把握住**“强制缺失（首次不可避免的冷启动）”**与**“非强制缺失（包含多块抢占冲突）”**的本质差异即可。

#### 全相联缓存与西南航空的比喻

到目前为止，我们分析的全是**直接映射缓存**。
在直接映射中，一个内存地址通过 Index 计算，**只能去一个且唯一的一个行位置**。

这就像乘坐普通航班，机票上印着固定座号（Assigned Seating）。你哪怕觉得那个位置不舒服，或者边上有人，你也只能坐那里；如果两个人分到了同一个座号，就必须有一个人被赶下飞机。

但现实中还有另一种航空运营模式，比如西南航空（Southwest Airlines）——他们实行**自由选座（Open Seating）**。
登机之后，飞机上的任何一个空座位你都可以随便坐，先到先得。

这就是**全相联缓存（Fully Associative Cache）**的本质！

```text
直接映射 (对号入座):
  地址 ──[ Index 计算 ]──> 唯一定位行 K (冲突则强制驱逐)

全相联 (西南航空选座):
  地址 ──[ 无 Index 束缚 ]──> 任意空闲行 (谁有空位坐哪里)
```
*图解说明：直接映射与全相联在行映射自由度上的根本机制对比。*

在全相联缓存中：
- **消灭 Index 字段**：既然数据可以塞进缓存中的任何一行，地址中就不再需要用于行号定位的 Index 字段了！32 位物理地址只剩下两部分：**Offset**（依旧负责行内字节对齐）和极其庞大的 **Tag**（扣除 Offset 后的所有高位全部充当 Tag）。
- **彻底消除冲突缺失**：只要缓存里还有哪怕一个空行，新来的数据就可以直接落座，绝不会因为所谓“哈希散列到同一行”而发生同室操戈。冲突缺失在全相联中直接降为零。

但天下没有免费的午餐。全相联缓存的致命缺点在于**硬件检索成本呈指数级暴涨**：
在直接映射中，硬件顺着 Index 导线只需拉出一行的 Tag，用 1 个比较器即可判定是否命中；
但在全相联缓存中，因为数据可能藏在 1024 行里的任何一个角落，硬件**必须为每一行都配备一个专用的物理比较器**！当 CPU 发出地址时，1024 个比较器必须同时并行对所有行的 Tag 展开全量地毯式扫描。这不仅会消耗极其庞大的芯片硅片面积，更会带来骇人的动态功耗。

因此，在真实的现代处理器中，全相联通常只用在条目极少（如数十条）但对命中率极度敏感的微型结构（如 TLB）中；而在多级大容量缓存中，工程师们则通过组相联（Set-Associative）在直接映射的极简与全相联的灵活之间寻找工程上的优雅折中。
