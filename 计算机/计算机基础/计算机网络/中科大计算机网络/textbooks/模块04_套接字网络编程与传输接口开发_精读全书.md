## TCP 套接字编程：welcoming socket 与 connection socket
> 对应块：BLK21 | 覆盖分集：P20 | 块标题（分集名）：《2.8 TCP 套接字编程》

DNS、FTP、E-mail、Telnet、Web——前面把这一串应用和它们相应的协议、工作原理都过了一遍。应用协议的实质就是两件事：两个应用进程之间交换应用报文（message），一方按协议规范解析收到的报文、弄明白对方要干嘛，再按规范形成响应报文送回去（要不要响应、怎么响应，由应用层协议规定）。但有一个最基本的问题一直悬着没回答：报文究竟是怎么从这一台主机上的应用进程，跑到远端那台主机上的应用进程的？这一章就讲这个比较特殊的东西——套接字（socket）编程，先讲 TCP 的，UDP 的模式另说。

### 应用报文的交接点：层间接口上的 socket

先把结论摆出来：两个应用进程不能直接"隔空"传报文。报文必须借助于下层提供的通信服务才能实现远程传输——从层间接口交下去，由下层一起把它送到对面。下层包括什么？本端的 TCP、IP 及更底下的各层，加上中间网络的所有设备，大家合起来向上提供这一份服务。

```text
   应用进程 A ┄┄┄┄┄┄┄ 应用报文（逻辑通道）┄┄┄┄┄┄▶ 应用进程 B
        │                                              ▲
        ▼                                              │
    [socket] ═══════════ 层间接口上的"门" ══════════ [socket]
        │                                              ▲
        ▼                                              │
   ┌── 传输层 ──┐                                ┌── 传输层 ──┐
   │ 网络层以下  │ ◀═════════ 实通信 ═══════════▶ │ 网络层以下  │
   └───────────┘                                └───────────┘
```

图里两个应用进程之间那条虚线是逻辑通道；报文真正的传递，要经 socket 交到下层，沿实线穿过整条协议栈和中间网络，在对端层层向上交还。

那报文具体从层间接口的哪个位置交下去？socket。以什么形式交？调用 socket API（应用程序接口）。所以说 socket 就像一扇门：进程把报文从这扇门推出去，对方的应用进程就能收到；反过来也一样。门以下的所有东西可以看成一个整体。报文交下去之后，对下层来说它就是服务数据单元（SDU），具体怎么传是下层的事——本课程自顶向下，这一章不讲下层怎么传，只讲应用怎么使用层间接口上的 socket API。

应用进程要做的就三步：传报文之前先建 socket；建出有效 socket 之后用它收、用它发；用完把 socket 关掉。应用进程完全不必考虑报文具体怎么传。顺带说一个有意思的问题：本层协议的实现是为了向上层提供服务，那应用层的上层是什么？是用户（人），或者是其它应用。

### 传输层的两种服务：TCP 与 UDP

TCP/IP 协议栈的传输层有两种类型的协议：TCP 和 UDP。socket 编程的模式因它们而不同。

TCP 提供可靠的字节流（byte stream）服务：这边传过去什么，对方就原原本本收到什么——不错、不重复、不丢失、不失序。但"字节流"三个字要咬文嚼字：它保证按流来看是对的，不保证报文的界限。所以很多应用协议里都能看到同一个痕迹——应用报文之间的界限，应用得自己维护。前面学过的那些例子里去找一找，都有。

| 对比点 | TCP | UDP |
| :--- | :--- | :--- |
| 可靠性 | 可靠：不错、不丢、不重、不失序 | 不可靠 |
| 连接性 | 面向连接：通信前先"打招呼"（握手） | 无连接：上来就是干货 |

所谓连接，指两个应用进程在通信之前先打个招呼："你好吗？""还行啊。"打过招呼之后才开始实质通信——TCP 是这样。UDP 不管这一套，上来就问："那个域名解析，告诉我。"对方直接把解析结果换回来——没有握手的过程，上来就是干货，直接实质性的通信。

### TCP socket 整数的含义：四元组的本地代表

socket 在前面的例子里已经出现过：它就是一个整数，是上下层之间的一个约定。这个整数像什么？像文件句柄。打开一个文件，操作系统返回一个句柄，一个整数；对这个整数的读、写，就是对那个文件的操作。同样，对一个 socket 的读、写，就是对两个应用进程之间那个会话的操作。操作系统里打开句柄返回整数、进程间通信也返回整数（socket 值），是一回事。

那 TCP 的 socket 这个整数具体代表什么？代表四样东西：我的 IP、我的 TCP 端口、对方的 IP、对方的 TCP 端口。它是两个端节点之间连接关系——一次会话——的本地代表。我对这个 socket 发，就是发给对方那个应用进程；我从这个 socket 收，收的就是对方那个应用进程传过来的报文。是哪个应用进程？就是"这个 IP 这个端口、对方那个 IP 那个端口"所对应的那个会话。

```text
  发送方应用报文：  [ 报文1 · 15 KB ]   [ 报文2 · 15 KB ]
                          │
                          │ TCP 可靠字节流：内容不错、不丢、不重、不失序，
                          │ 但报文之间的界限不保证
                          ▼
  接收方实际收到：  [ 30 KB 连成一片的字节 ]
```

发送方发两个 15 KB 的报文，接收方可能一次收到 30 KB 连成一片的字节——传输层不保证报文和报文之间的界限。

> **易错点**：字节流服务的"可靠"是对字节内容而言的，不包括报文边界。报文怎么切、边界在哪，应用层自己定、自己认。

顺带把 UDP 的 socket 也对比一句，后面答疑要用：TCP 的 socket 是四元组的本地代表，而 UDP 的 socket 这个整数只代表本地的 IP 和端口。

### 示例应用：远端大小写转换

接下来整个流程都围绕一个应用场景：客户端进程从标准输入（键盘）读入一串小写字符，通过 socket 发给服务器；服务器把它转换成大写，再通过建立好的 socket 反转回来；客户端从标准输出（显示器）把结果显示出来。

你可能会说：这不是有病吗？小写转大写，本地一行就做了。对，这纯粹是个例子——要演示的是"客户端发出一串信息，服务器做点处理，结果反转回来"这个模式：本地的处理不做，让远端服务器去做。从用户角度看效果：输入一串小写字符、按个回车，远端转换完毕的大写字符串就回来了——用户觉得挺高大上，因为转换不是本地做的，是远端服务器做的。

### 两个关键结构体

后面要反复用到两个结构体，先把它们交待清楚。

#### 端点地址结构 sockaddr_in

```text
  struct sockaddr_in —— 表征一个通信端节点
  ┌──────────────────────────────────────
  │ sin_family   地址族
  │              赋一个常量，指明用在哪一族：TCP/IP、IPX、AppleTalk…
  │ sin_port     端口号
  │ sin_addr     IP 地址（用 IP 通信时取的就是这 32 位）
  │ sin_zero[8]  对齐填充（IPX、AppleTalk 的地址更长，为放得下而留）
  └──────────────────────────────────────
```

family 是地址族。这个数据结构的定义不只用于 IP 通信，也可以用于 IPX 等其它网络——IPX 是 Novell 网的地址，现在基本不用了；还有 AppleTalk 之类，它们的地址都比 IP 地址长。所以用的时候要给 family 赋一个常量，指明用在哪一族：用在 TCP/IP 就赋 Internet 对应的常量。结构体尾部还留了一段填充域，起对齐作用——那些更长的地址要放得下；用 IP 地址时，只取 32 位的那部分。

port 放端口号，sin_addr 放 32 位 IP 地址。一个结构体变量就能表征 TCP（或 UDP）通信时的一个端节点：哪个 IP、哪个端口。比如服务器守候的 1.1.1.1 : 80，用这一个变量就装下了。

#### 域名解析结构 hostent

```text
  struct hostent —— 域名解析的输入与返回载体
  ┌──────────────────────────────────────
  │ h_name       主机域名（字符串指针）
  │ h_aliases    别名列表（指针的指针，二维：主机的一系列别名）
  │ h_addrtype   地址类型
  │ h_length     地址长度（是 32 位还是多少位）
  │ h_addr_list  IP 地址列表：IP0、IP1、…（解析出的地址放在 IP0）
  └──────────────────────────────────────
```

h_name 放主机域名的字符串指针；h_aliases 是指针的指针，二维的——主机的一系列别名，学过 C 语言一看就明白；h_length 是地址长度，是 32 位还是多少位；h_addr_list 是 IP 地址列表，一台主机可能对应多个 IP 地址，解析出来的那个就是 IP0。

这个结构体的作用就是做域名解析：作为解析函数调用的输入（域名）与返回值（IP 列表）。客户端拿到返回的 hostent 指针后，把 IP 地址从列表里 copy 到 sockaddr_in 的地址域里，端口号再用赋值的方法赋上——一个完整的"对方端节点"就填好了。马上就会在代码里用到这一套。

### 连接建立与数据收发的完整流程

光靠语言描述这个流程确实苍白无力，得靠比划——画一张图，再配上具体的地址走一遍。先记口诀：服务器是"创建、捆绑、等待"，客户端是"创建、（隐式）捆绑、连接"。下面出现的 `socket()`、`bind()`、`accept()`、`connect()`、`read()`、`write()`、`close()` 都是 socket API 这一族里的函数——socket API 是一套函数，不是一个函数。

约定：服务器 IP 1.1.1.1，守候 80 号端口；客户端 IP 2.2.2.2，用 777 号端口。

CS 模式里服务器必须先运行——客户端先运行的话，你跟谁打招呼？服务器都没起来呢。

服务器先调 `socket()`：操作系统在 socket 表里建一个表项，返回一个整数，比如 8888——很吉利的一个数。此刻这个整数什么都不是：本地 IP、端口都还没赋。`socket()` 的参数里指明建哪一种 socket：参数给 TCP 的值，建出来的就是 TCP socket；给 UDP 的值，就是 UDP socket；甚至可以建 IP 的 socket。

接着 `bind()`：把 8888 这个整数跟本地哪个 IP、哪个端口捆绑？通过端点地址结构 sad 指定——先把 sad 赋好值（IP 1.1.1.1、端口 80），再调 `bind()`。捆绑完，表项里"本地 IP、本地端口"两个字段就有效了。这个 socket 叫欢迎套接字（welcoming socket），专门迎接新连接。

然后 `accept()`：在 welcoming socket 上等待来自客户端的连接建立请求。调用 `accept()` 时如果没有任何连接请求来，函数就阻塞在那儿，不往下走。

客户端这边：先 `socket()`，返回另一个整数，比如 2222。然后是隐式的捆绑——客户端可以不调 `bind()`，反正它用什么端口号无所谓；你不调，操作系统替你把这个整数跟当前没有被使用的一个端口（比如 777）捆上。

> **易错点**：服务器端必须显式 `bind()`。服务器要在确定的端口上等待客户端的连接建立请求，这个端口一定要是确定的——不绑死在 80 号端口上，客户端来了找谁？

再调 `connect()`，参数里指明对方端节点：sad 填 1.1.1.1 : 80。`connect()` 也是阻塞的：调用之后，底下本端 TCP 实体向服务器发出连接建立请求；服务器 TCP 同意建立连接、应答传回来，`connect()` 才解除阻塞、返回有效值——这时连接才处于真正建立的状态。同时，本端表项里"对方 IP、对方端口"两个字段也被 `connect()` 的参数填上了。

服务器那边，`accept()` 等到了连接建立请求：TCP 一方面同意这个连接（于是客户端的 `connect()` 解除阻塞），另一方面返回一个新的 socket 值，比如 8899。这个新 socket 叫连接套接字（connection socket）：它守候的仍然是服务器自己的 1.1.1.1 : 80，但捆绑关系是完整的四元组——本地 1.1.1.1 : 80，加对方 2.2.2.2 : 777。`accept()` 解除阻塞返回 8899 之后，连接进入有效状态，之后的收发都在 8899 上进行，而 welcoming socket 8888 继续守在原处。

```text
     服务器（1.1.1.1 : 80）                          客户端（2.2.2.2 : 777）
  ──────────────────────────                   ──────────────────────────
  welcomeSocket = socket() → 8888
  bind(8888, sad = 1.1.1.1 : 80)
  accept(8888) ……阻塞等待
                                               clientSocket = socket() → 2222
                                               隐式 bind 到本地 2.2.2.2 : 777
                                               connect(2222, sad = 1.1.1.1 : 80)
                                                        ……阻塞
            ◀──── TCP 连接建立请求 / 应答（底层交互）────▶
  accept 解除阻塞
  connectionSocket = accept() → 8899           connect 返回有效值
  （8899 = 本地 1.1.1.1:80 + 对方 2.2.2.2:777）
                                               write(2222, sentence)
         ◀──────── 应用报文：小写字符串 ──────────
  read(8899) 收到，转成大写
  write(8899, modifiedSentence)
         ────────── 应用报文：大写字符串 ─────────▶
                                               read(2222) 收到，printf 显示
                                               close(2222)
  close(8899)
  （8899 的表项删除；8888 仍守候，回到 accept 等下一个连接请求）
```

图里底层 TCP 的连接建立交互与应用报文的交互是分开的两层：请求、应答那一来一回是 TCP 在底下完成的；字符串的往返才是应用报文。到底是先发再收、还是先收再发？那取决于应用协议怎么定义，不是 socket API 的事。

```text
  socket 表项（操作系统维护，应用层与传输层共用）
  ┌──────────────────────────────────────────────────────────
  │ socket 值 │ 本地 IP  │ 本地端口 │ 对方 IP  │ 对方端口 │ 状态       │ PID
  ├──────────────────────────────────────────────────────────
  │   8888    │ 1.1.1.1  │   80     │   ——    │   ——    │ welcoming │  …
  │   8899    │ 1.1.1.1  │   80     │ 2.2.2.2  │   777   │ 连接有效   │  …
  └──────────────────────────────────────────────────────────
```

welcoming socket 的表项只有本地两格有效，对方两格空着；connection socket 四格齐全，另带状态和 PID。`close()` 之后表项删除。

数据往返的过程：客户端以 2222 为参数调 `write()`，要传的字符串也作为参数喂进去；报文交到下层，封装成 TCP 报文段发给对方。服务器对 8899 调 `read()` 收下小写字符串，在本地转成大写，再 `write()` 回去。客户端 `read()` 2222，拿到转换完的大写字符串，`printf()` 到终端，然后 `close()`。服务器这边先 `read()` 后 `write()`，`close()` 掉 8899——表项删掉——程序反转回 `accept()`，welcoming socket 仍然有效，等待下一个连接建立请求。

要扩展成多进程服务也简单：`accept()` 返回有效值之后 fork 一个新进程，让新进程为这个客户端提供大小写转换服务；老进程仍然守候在 welcoming socket。又来一个连接请求，再返回一个 connection socket，再 fork 一个进程去服务。这样 socket 表里同时有许多条 connection socket 表项，外加一条 welcoming socket 表项。

### 同一端口上的多个 socket 与报文分发

流程走到这里，一个自然的疑问冒出来：服务器正在 8899 上跟客户端收发，用的还是 80 号端口——那 80 号端口还能继续当 welcoming socket 吗？

能。welcoming socket 一直守候在 80 号端口上，等新的连接建立请求。关键还是前面那个概念：TCP 的 socket 值是四元组的本地代表。8899 代表"本地 1.1.1.1 : 80 + 对方 2.2.2.2 : 777"；再来一个客户（对方是另一个 IP 和端口），`accept()` 又返回一个新 socket，本地那一半还是 1.1.1.1 : 80，对方那一半不同。所以两个进程可以同时守候同一个端口，只要它们的 socket 不一样——不一样就不一样在对方的 IP 和端口上。这个概念前面铺垫讲过，回去再翻一翻 TCP socket 那部分。

那再追一层：报文从网上到达 80 号端口，怎么区分该交给哪个 socket、进而交给哪个进程？你看发过来的 TCP 报文段——里面带着本地的 IP 和对方的 IP，也带着本地的端口和对方的端口。拿这四样跟表项一对，不就对上了嘛。这是完备的。表项里还记着这个 socket 对应哪个进程号（PID，process ID）：操作系统维护这张表，数据一到就交给对应的应用进程。

### 客户端代码逐段精读

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <netdb.h>
#include <netinet/in.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <unistd.h>

#define MAX_LINE 4096

int main(int argc, char *argv[])
{
    struct hostent    *ptrh;             /* hostent：域名解析的返回载体 */
    struct sockaddr_in sad;              /* 端点地址结构：服务器端节点 */
    int  clientSocket;                   /* socket 就是一个整数 */
    char host[MAX_LINE];                 /* 服务器域名（argv[1]） */
    int  port;                           /* 服务器守候端口（argv[2] 转整型） */
    char sentence[MAX_LINE];             /* 用户敲入的小写字符串 */
    char modifiedSentence[MAX_LINE];     /* 服务器转换完的大写字符串 */

    strcpy(host, argv[1]);               /* 第一个参数：服务器域名 */
    port = atoi(argv[2]);                /* 第二个参数：端口，字符串转整型 */

    /* 建 socket：参数指明 Internet 族 + 字节流（TCP） */
    clientSocket = socket(PF_INET, SOCK_STREAM, 0);

    memset((char *)&sad, 0, sizeof(sad));   /* 先清零，清掉内存里的残留 */
    sad.sin_family = AF_INET;               /* Internet 地址族 */
    sad.sin_port   = htons((u_short)port);  /* 转无符号短整型，再转网络字节序 */

    ptrh = gethostbyname(host);             /* 调解析器：域名进去，IP 出来 */
    memcpy(&sad.sin_addr, ptrh->h_addr_list[0], ptrh->h_length);

    /* 客户端不显式 bind：操作系统隐式捆绑一个当前未用的端口 */
    connect(clientSocket, (struct sockaddr *)&sad, sizeof(sad));
    /* connect 内部发出 TCP 连接建立请求，收到对方应答后才解除阻塞返回 */

    gets(sentence);                                      /* 标准输入读小写字符串 */
    write(clientSocket, sentence, strlen(sentence) + 1); /* 经 socket 发走 */
    read(clientSocket, modifiedSentence, MAX_LINE);      /* 从 socket 读大写结果 */
    printf("%s\n", modifiedSentence);                    /* 标准输出显示 */
    close(clientSocket);                                 /* 用完关闭 */
    return 0;
}
```

先把骨架记住：建 socket、（隐式）捆绑 socket、连接 socket、写和读、关闭 socket。前面的参数解析和结构体赋值都是铺垫，关键就这一串。

运行客户端必须给两个参数：第一个是服务器的域名，第二个是服务器守候的端口号，都以字符串形式进来，分别放在 `argv[1]` 和 `argv[2]`。`argv[1]` 拷进 host；`argv[2]` 是端口的字符串形式，转成整型赋给 port。顺带一问：那 `argv[0]` 是什么？学过 C 的都知道——程序自己的名字。

sad（server address）就是那个端点地址结构：客户端要用一个结构体描述"服务器守候的 IP 和端口"。用之前先 `memset()` 清零——结构体分到的内存里可能有乱七八糟的残留，先清干净再赋值。然后 `sin_family` 赋 Internet 地址族；端口号先把整型强制转换成无符号短整型，再转成网络字节序（network byte order）。

> **易错点**：为什么要转网络字节序？不同架构的计算机表示整数的方式不同，有大端小端之分——高位低位放在左边还是右边的问题。不做转换，发出去是 0000 1111，到对方那儿可能变成 1111 0000，高低位调了个个儿。统一转成网络字节序，不同架构的设备通过网络传输才不会有歧义。

IP 还缺着——手里只有域名。所以调 `gethostbyname(host)`：这就是调用解析器，输入主机域名，返回 hostent 结构体指针，解析出的 IP 地址已经放在列表第一个位置。把这块 IP copy 进 sad 的地址域。至此 sad 里是完整的服务器端节点：地址族、IP、端口，三样齐了。

`connect()` 之前为什么没有 `bind()`？前面讲过：客户端有隐式 bind——你不调用，操作系统按一定规则默认给你捆一个当前没用的端口号。`connect(clientSocket, sad)` 一调用，底下 TCP 发出连接建立请求并阻塞等待；对方的应答回来，`connect()` 返回有效值，连接建立。

之后就是干活：`gets()` 从标准输入读用户敲的小写字符串；`write()` 以 clientSocket 为参数，把字符串发走；`read()` 再从这个 socket 读回服务器转换完的大写字符串；`printf()` 打到终端；最后 `close()` 关掉，收工。

### 服务器代码逐段精读

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <ctype.h>
#include <netinet/in.h>
#include <sys/types.h>
#include <sys/socket.h>
#include <unistd.h>

#define MAX_LINE 4096
#define QLEN     10                  /* listen 的等待连接队列长度 */

int main(int argc, char *argv[])
{
    struct sockaddr_in sad;          /* 服务器本地端节点 */
    struct sockaddr_in cad;          /* 客户端端节点 */
    int  welcomeSocket, connectionSocket;
    int  port, i, n;
    char clientSentence[MAX_LINE];        /* 收到的小写字符串 */
    char capitalizedSentence[MAX_LINE];   /* 转换完的大写字符串 */
    socklen_t clientlen = sizeof(cad);

    port = atoi(argv[1]);            /* 只有一个参数：本地守候的端口号 */

    welcomeSocket = socket(PF_INET, SOCK_STREAM, 0);   /* welcoming socket */

    memset((char *)&sad, 0, sizeof(sad));
    sad.sin_family      = AF_INET;
    sad.sin_addr.s_addr = INADDR_ANY;      /* 常量：代表本机的 IP 地址 */
    sad.sin_port        = htons((u_short)port);

    /* 捆绑：表项里"本地 IP、本地端口"两格从此有效 */
    bind(welcomeSocket, (struct sockaddr *)&sad, sizeof(sad));

    listen(welcomeSocket, QLEN);           /* 挂一个长度为 10 的等待连接队列 */

    while (1) {
        /* 没有连接请求就阻塞在这里；请求到来返回一个新的 socket 值 */
        connectionSocket = accept(welcomeSocket,
                                  (struct sockaddr *)&cad, &clientlen);

        n = read(connectionSocket, clientSentence, MAX_LINE);
        for (i = 0; i < n; i++)            /* 从小写变成大写 */
            capitalizedSentence[i] = toupper(clientSentence[i]);
        write(connectionSocket, capitalizedSentence, n);
        close(connectionSocket);           /* 表项删除 */
    }   /* 反转回 accept：welcoming socket 继续守候下一个连接请求 */
}
```

TCP 上的服务器应用进程只有一个参数：本地守候的端口号，本例给 80。注意服务器定义了两个地址结构：sad 放服务器本地端节点，cad 放客户端（client address）端节点；还有两个整数——welcomeSocket 和 connectionSocket。打开文件返回句柄、进程间通信返回 socket 值，都是这个套路：对这个整数操作，就是对那个文件或那条网络流、那次进程间通信的操作。

welcomeSocket = `socket()` 建出 welcoming socket。刚建好时表项里只有 socket 值本身；`bind()` 之后"本地 IP、本地端口"两格有效，对方 IP、对方端口还空着；表项里另有状态域，区分它是 welcoming socket 还是 connection socket，还有对应的 PID。sad 赋值：地址族赋 Internet；地址域赋一个常量——这个常量代表本机的 IP 地址；端口号把字符串参数转成整型、强制转成短整型、再转网络字节序。`bind(welcomeSocket, sad)` 一调，刚建的整数跟 sad 里的本地 IP、端口捆在一起，表项里这两格从此有效。

代码里 `bind()` 之后、`while(1)` 之前还有一句 `listen(welcomeSocket, 10)`，刚才特意按下没讲——先把主循环看完。`while(1)` 里：`accept()` 在 welcoming socket 上等连接请求，没有就阻塞，来了就返回一个新的 socket 值——它跟 welcomeSocket 不是同一个值，代表的是本地 IP、本地端口，加对方 IP、对方端口，外加状态和 PID。然后在 connection socket 上 `read()` 对方发来的报文，转成大写，`write()` 回去，`close()` 关掉；程序反转回 `while(1)`，再进 `accept()` 继续守候。

现在回头看 `listen()`：它在系统里挂了一个队列，队列的长度是 10，这是等待连接建立的队列。我正在为一个客户服务的时候，又来了连接建立请求，请求先放进队列排队；等服务完、循环回到 `accept()`，直接从队列里拿一个，就知道又有人要建立连接了。队列里超过 10 个怎么办？拒绝了。

> **提示**：welcoming socket 与 connection socket 的分工——前者永远守在端口上"迎接"，后者才是干活的会话，一个客户一条，用完即关。

单进程版本一次只能伺候一个客户。要变成多进程服务，就用前面说的办法：`accept()` 返回有效值后 fork 一个新进程，让新进程为这个客户端做大小写转换；老进程仍然守候在 welcoming socket。再来一个连接请求，再返回一个 connection socket，再 fork 一个新进程去服务。于是 socket 表里同时有很多条 connection socket，还有一个 welcoming socket。

## UDP 套接字编程与传输层服务概览
> 对应块：BLK22 | 覆盖分集：P21-P23 | 块标题（分集名）：《2.9 UDP 套接字编程》

UDP 套接字跟 TCP 套接字不一样，差别一句话就能问出来：它有没有握手？没有握手。没有握手，套接字里自然也捆不进对方的端点——这一讲就从这个最要紧的不同讲起，把 UDP 套接字的编程模型和两段示例代码走一遍，然后给第二章收尾，再推开第三章传输层的门。

### UDP 套接字的本地捆绑与收发参数

没有握手，UDP 套接字建立之后只跟本地的 IP 和端口相捆绑，它就是"本地 IP + 本地 UDP 端口"的一个本地代表，跟对方的 IP、对方的端口毫无关系。

这个特性直接决定了收发两端该给什么参数：

- **发送**：光有 socket 不够——它只代表我这一端，没有指明对方。所以发送时必须给三个信息：用哪个 socket 发、发的是什么、发给谁。"发给谁"就是对方 IP 地址加对方 UDP 端口组成的一个结构体变量。
- **接收**：任何一个守候在 UDP 端口之上的进程，收报文时要收两件事——对方发过来的是什么，以及对方的端节点是什么。后者通过引用型参数带回来，相当于一个返回值。这个信息有没有用？当然有用：谁发送给我的，我就发送给谁。

UDP 向应用进程提供的服务可能乱序、也可能丢失，因此它是不可靠的，而且是无连接的。

> **定义**：无连接服务的协议数据单元（Protocol Data Unit，PDU）通常称为数据报（datagram）。UDP 的 PDU 叫数据报，IP 的 PDU 也叫数据报——同一个词要结合上下文看，判断它指的是 UDP 的协议数据单元还是 IP 的协议数据单元。

### 一次 UDP 通信的完整时序

设服务器守候在 1.1.1.1 的 80 端口，客户端守候在 2.2.2.2 的 777 端口。

> **易错点**：这里的 80 和 777 都是 UDP 端口，不是 TCP 端口。端口号必须结合协议族来看，UDP 的端口和 TCP 的端口是两回事。

套接字的结构是"socket 值 + 本地 IP + 本地端口"，此外还有状态、PID 之类的附带信息——那些是操作系统设计的事，跟网络没什么关系，不用管。

#### 服务器端流程

1. `socket()` 建立套接字，参数里指明是 UDP socket，函数返回一个整数——假如叫 8888。又是 8888？反正是 UDP socket 跟 TCP socket 两个不同的空间，撞号也不用管它。
2. `bind()`，把这个返回的 socket 值和本地的 SAD 相捆绑。SAD 里放的是本地 IP 地址和端口号：端口号由参数输入转换而来，IP 地址以系统常量的方式给定。绑完，这个套接字就守候在 1.1.1.1 的 80 端口上了。
3. `recvfrom()`：从这个 socket 收。参数包括 socket 值、存放数据的缓冲区，还有一个引用型参数——对方的 IP 和 UDP 端口就通过它带回来。这个函数是阻塞的：对方不发东西，它就一直阻塞在那里，程序不往下走；对方一发过来，函数解除阻塞，缓冲区里有数据，引用参数里也有对方的端点。
4. 解除阻塞后做小写到大写的转换，然后 `sendto()` 把结果发回去——socket 作为其中一个参数；发给谁？谁发送给我的，就发送给谁，也就是引用参数里带回的那个端点。发完再回到 `recvfrom()` 继续守候。

顺带说一句：小写转大写跟协议没关系，那是应用内部处理的事。任何一个应用除了协议之外，还有用户界面、还有一些内部的信息处理；协议只是规范交互双方在通信过程中应当遵守的规矩。

#### 客户端流程

1. `socket()`，参数指明 UDP socket；
2. 本地捆绑，把 socket 与本地 IP 2.2.2.2、本地端口 777 绑在一起；
3. `sendto()`：指明用哪个 socket（它代表本地端点）发、发的是什么、发给谁（对方 IP 加端口的结构体变量）；
4. `recvfrom()`：收服务器转换完发回的大写字符串；
5. 显示出来，`close()` 关闭套接字。

```text
   客户端（2.2.2.2 : 777，UDP）                  服务器（1.1.1.1 : 80，UDP）
   socket() 得 2222                              socket() 得 8888
   本地捆绑 2.2.2.2:777                          bind() 捆绑 1.1.1.1:80
        |                                             |
        | sendto(2222, 小写串, 目的 1.1.1.1:80)       |
        |-------------------------------------------->|
        |                                  recvfrom() 解除阻塞
        |                                  小写转大写（内部处理）
        | sendto(8888, 大写串, 目的 2.2.2.2:777)      |
        |<--------------------------------------------|
   recvfrom() 返回大写串                          回到 recvfrom() 继续守候
   显示，close(socket)
```

读图说明：全程没有握手，客户端建立套接字后直接就发；服务器一个套接字既收又发，收到才醒、回完再守。

在 UDP 之上，两个应用进程通信之前要不要握手？不需要——建立 socket 之后直接就发。服务器端有没有 welcome socket 和 connection socket 之分？没有，就一个 socket，它代表本地 IP 和相应的端口。这跟 TCP 套接字不一样：TCP socket 捆绑的是四元组。为什么要这样？方便嘛。TCP 要先建立连接，建立连接之后这个 socket 才有效；而连接一旦建立，我的 IP、我的端口、对方 IP、对方端口就都已经确定了，用一个参数就能代表这四个信息——往下发、往上收，都只指定这一个参数。

| 对比项 | TCP 套接字 | UDP 套接字 |
| :--- | :--- | :--- |
| 通信前是否握手 | 需要 | 不需要 |
| 捆绑的端点信息 | 本地 IP、本地端口 + 对方 IP、对方端口（四元组） | 仅本地 IP、本地端口 |
| 服务器端套接字 | 分 welcome socket 与 connection socket | 只有一个套接字 |

### 客户端与服务器端代码走读

再看代码，先客户端，后服务器端。

#### 客户端代码

客户端带两个参数：一个放主机的名字，另一个放主机的端口号。前面先安排变量：存放服务器端端节点的地址结构 SAD、整型的 client socket、结构体指针，以及待发送的字符串 sentence。

- `socket()` 建立套接字；
- SAD 先清零，清零完再逐字段附上相应的值：地址族填 Internet 的地址族；端口号是参数输入的字符串，要先转换成无符号短整型、再转换成网络字节序，放进字段；IP 地址则通过域名解析得到，填进结构体指针所指向的空间里；
- 到这里，SAD 这个结构体里就齐了：端口号、IP 地址、地址族；
- 用 gets 从标准输入获得用户输入的一个字符串，放进 sentence，并求出字符串的长度；
- `sendto()` 把 sentence 发走：从哪个 socket 发——这个 socket 代表本地的 IP 和相应的端口；发给谁——SAD 不是已经指明了对方的 IP 和端口号吗；发什么——sentence 及其长度；
- `recvfrom()` 收服务器发回来的内容：收的东西放在缓冲区里，谁发送给我的放在那个结构体变量里；
- 把服务器端发来的东西打印出来，`close()` 关闭。

```text
UDPClient（命令行参数：主机名、端口号）

  socket()                          建立 UDP 套接字
  SAD 清零，逐字段赋值：
      地址族 ← Internet 地址族
      端口号 ← 字符串转无符号短整型，再转网络字节序
      IP     ← 域名解析主机名得到
  gets(sentence)                    从标准输入读入字符串，求长度
  sendto(socket, sentence, SAD)     socket=本地端点，SAD=对方端点
  recvfrom(socket, 收串, 对方端点)  谁发来的放进结构体变量
  打印收到的串
  close(socket)
```

读图说明：发送的三要素——socket、发什么、发给谁——在 sendto 的参数里一一对应；SAD 一旦填好，"发给谁"就不再变动。

#### 服务器端代码

服务器端只有一个参数：守候的端口号，假如是 80，把它从字符串强制转换成一个整数。变量包括：SAD 放服务器端的端节点，CAD 放客户端进程的端节点，server socket 是一个整数值，还有结构体指针、sentence 和转换后的 modified sentence。

- `socket()` 建立 UDP 套接字——注意这里的参数跟前面不一样，指明的是 UDP；
- SAD 赋值：把服务器守候的 IP 地址和端口号填进去；
- `bind()`：把建立好的 UDP socket 与本地的端口号和 IP 地址（SAD）相绑定；
- 进入循环：
  - `recvfrom()` 从这个 socket 收：收到的内容放进 sentence，谁发给我的放进 CAD——引用型参数放在这个结构体里；
  - 在内部对 sentence 做大写转换，得到 modified sentence；
  - `sendto()` 把 modified sentence 发走，发给 CAD——谁发来的就发给谁；
  - 回到循环头继续收。

```text
UDPServer（命令行参数：守候端口号，如 80，转成整数）

  socket()                          建立 UDP 套接字（参数指明 UDP）
  SAD 赋值                          服务器守候的 IP 与端口
  bind(server_socket, SAD)          与本地端点相捆绑
  while (1) {
      recvfrom(server_socket, sentence, CAD)          收串与对方端点
      sentence 大写转换 → modified_sentence
      sendto(server_socket, modified_sentence, CAD)   谁发来的发给谁
  }
```

读图说明：服务器没有 welcome 与 connection 之分，一个套接字在循环里收了就转、转完就回，CAD 记住了来源，回发也就有了目标。

整个过程其实没那么复杂：服务器创建 socket、与本地端点绑定、recvfrom、转换、sendto 回来源、循环；客户端建立 UDP socket、隐式地与本地 IP 和相应的端口绑定、sendto、recvfrom、显示、close。

### 应用层的模式、协议与横向概念

第二章的内容到这里就介绍完了，收个尾。

应用进程之间的体系架构分三种：客户端服务器模式、P2P 模式和混合模式。应用层要借助传输层提供的服务才能实现，而传输层服务的质量可以用这样几个指标来描述：是不是可靠、带宽怎么样、延迟如何、提不提供安全性。互联网 TCP/IP 协议栈的传输层提供两个协议：TCP 提供可靠的、面向连接的字节流服务；UDP 提供无连接的、不可靠的报文服务。应用层这一章介绍过的协议包括 HTTP、FTP、邮件的协议、域名解析系统（DNS），还有 CDN；编程上则覆盖了 TCP socket 和 UDP socket。

这一章还有一组横向的概念，归拢在一起看：

| 概念 | 区分 |
| :--- | :--- |
| 请求报文 / 响应报文 | 应用报文常见的两个方向类别 |
| 报文头 / 报文体 | 报文格式 = 头部 + 数据部分 |
| 数据报文 / 控制报文 | 按用途分：传输数据的是数据报文，传输控制信息的是控制报文 |
| 带内 / 带外信令 | 控制信息在同一个 TCP 连接之上传送是带内；另用单独的连接传送就是带外信令 |
| 目录维护：集中 / 分散 | 客户端服务器模式下目录信息维护的两种方式 |
| 有状态 / 无状态 | 服务器维护 / 不维护客户端的状态 |

总基调一句话：在网络的边缘处理复杂性。

### 传输层的路线图

第三章往下走：我们已经越过了应用层，现在下走到传输层。这一章两条主线：一是介绍一些原理，二是仍然以互联网的传输层为例，介绍它的两个协议——TCP 和 UDP。

原理部分有四个：

- **多路复用与解复用**：传输层不管是 TCP 还是 UDP，上面都同时支撑很多应用进程。源端怎么样把大家的报文收起来做复用，到目标端怎么样把它们分开、还给相应的应用进程，把正确的报文传送到正确的应用进程。
- **可靠数据传输**（Reliable Data Transfer，RDT）：TCP 向上层提供的是可靠的通信服务——下面交上来什么，上面交下来什么，到对方就要原原本本往上交什么；但 TCP 下面依赖的 IP 提供的服务是不可靠的。怎么在不可靠的通信服务之上向上层提供可靠的服务？要增加哪些机制？有哪些原因会造成不可靠、怎么对抗这些因素？怎么安排时空资源、安排协议处理机制？RDT 的工作原理非常重要，可以说是网络核心内容中比较核心的部分，top 10 的问题，甚至可以说是 top 3 的问题，是计算机网络非常经典的内容——所有的计算机网络教材都会在这上面花大量的时间和精力。希望大家打起精神，把这部分内容认真搞懂、搞通。
- **流量控制**：对等的 TCP 实体之间怎么协作，让发送方不至于发送得太快，以至于超过接收方的处理能力。这是一点到另外一点、一个进程到另一个进程的问题。
- **拥塞控制**：就算发送方发送得足够快、接收方接收和处理的速度也足够快，网络路径上的路由器还是可能出现拥塞。需要有拥塞的感知，从拥塞当中恢复出来，等网络不拥塞了再加快发送速度。如果没有拥塞控制这个机制，网络基本上无法使用——网络核心是大家公用的，很多主机之间的通信都要靠它做大范围的数据交换；如果大家无节制地往网络里输入分组，速率太快、太多，某天路径上就会出现拥堵，不加控制的话这网络几乎是无法使用的。这一小节会介绍拥塞的原因、表现、检测和控制动作。

章节安排按这个顺序走：

```text
概述：传输层向上提供的服务与定位
  → 多路复用与解复用
  → UDP 协议
  → 回到理论：RDT 可靠数据传输原理
  → TCP：段结构 / 怎么做 RDT / 怎么做流量控制 / 连接管理（建立、维持、释放）
  → 拥塞控制原理（一般网络：拥塞的表现、原因与常用机制）
  → 互联网怎么做拥塞控制（在端系统 TCP 协议实体上检测并控制，3.7 节详讲）
```

读图说明：先讲服务概述与复用解复用，再讲相对简单的 UDP，然后进入 RDT 原理，带着 RDT 去理解 TCP，最后是拥塞控制的原理与互联网实践。互联网的拥塞控制跟其他网络还有点不一样：它是在端系统的传输层、TCP 的协议实体上检测拥塞、做拥塞控制的，讲到 3.7 节再详细展开。

### 进程间的逻辑通信

传输层向上提供什么服务？为应用进程提供逻辑通信：应用进程能够把报文逻辑地发给对方，再逻辑地把报文回转回来。说"逻辑"，是因为物理上这个报文要通过层间接口交给传输层，由两端的传输实体相互配合——当然也需要网络的相互配合——最终把 message 交给对方的应用进程。看起来是 socket API 一发、对方用 receive 或 read 一收就完成的事，底下靠的是这一整套配合。

> **定义**：传输层向上层提供的服务，是应用进程之间的、以报文（message）为单位的逻辑通信。它不是主机到主机，而是进程到进程。

具体过程：发送端把应用的报文交给 TCP 或 UDP；报文如果比较长，就分解成若干报文段（segment），以段为单位形成本层的协议数据单元——TCP 的 PDU 就是 TCP 的段。段头里包括哪些信息，学到后面会知道，比如源端口、目标端口。这些段借助网络层提供的服务传到对等的 TCP 实体；对端把段头去掉，把段的数据部分按序号排序、整合，还原成原来的 message，再往上交。

TCP 怎么把这些段借助于网络层交给对方对等实体？那是网络层提供的服务，讲网络层时再详细介绍。我们是递归地讲：先假设网络层提供的服务就是这样，看怎么借助网络层的服务、加上传输层自身的努力，向上提供进程间的逻辑通信。

```text
发送端                                             接收端
应用进程                                           应用进程
    | message                                          ^
    | 交传输层                                          | 以字节流形式上交
    v                                                  |
TCP 实体                                           TCP 实体
    | message 分解成若干 segment                        | 去掉段头，把段的数据部分
    | （段头含源端口、目标端口等）                       | 按序号排序、重组回 message
    | segment 交给网络层                                | segment 来自网络层
    v                                                  |
    +---------- 网络层：IP 数据报，best effort，主机到主机 ----------+
```

读图说明：往下是"分解"，往上是"重组"，两端对等传输实体的配合，实现了进程到进程的报文交付。

还有一点要拎清：TCP 向上层提供的是字节流服务，它保证这个流是正常的，但不保证报文的界限。

> **易错点**：TCP 只保证字节流本身可靠有序，不保证"哪里是一个报文的开始、哪里是结束"——报文边界的标识要靠应用层自己的应用协议来完成。

### TCP、UDP 与下层唯一的 IP

在 TCP/IP 协议簇里，传输层向上提供两种协议可选：TCP 和 UDP，两者的服务特性很不一样。但再往下呢？都是 IP——到网络层就没得选了。网络层的基本模式就是以分组为单位、以 IP 数据报为单位的存储转发服务，尽力而为（best effort）。网络通常不会提供好几种服务类型让你挑，特别是在 TCP/IP 网络里，IP 向上层提供的就是 best effort 的分组传输服务。

网络层提供的是主机到主机的服务，传输层在它之上，把主机到主机的服务进一步细分成了进程到进程的服务。所以传输层向上层提供的服务依赖网络层，但同时加强了网络层的服务。

### 可以加强和无法加强的服务品质

网络层的服务有哪些毛病？可能丢失、可能乱序、也可能出错；如果延时变化比较大，先传的还可能后到。传输层就在网络层服务的基础上做加强——但要看清楚，有的品质加强得了，有的加强不了。

加强得了的两样：

- **可靠性**。传输层把网络层在可靠性上的不足加以弥补，向上层提供可靠的服务——怎么弥补，就是后面要讲的 RDT：下层向我提供的服务不可靠，但我要向上层提供可靠的服务。
- **安全性**。TCP 向上层提供的服务是不安全的，TCP 之上可以有 SSL——安全套接字层——来加强安全性；IP 向上层提供的服务同样不安全。借助传输层，可以在端系统里做加密、认证、报文完整性检查，向上提供比较安全的服务。

加强不了的呢？

- **延时**。从交下去到对方交上来，中间有个延时。靠 TCP 的努力，能不能把这个延时降下来？不可以。
- **带宽**。IP 向上层提供的是主机到主机、IP 到 IP 的传输，有吞吐量、有有效带宽。我到你的这条路径要经过的那些路由器、那些链路段里，瓶颈链路限制了我和你之间的最大带宽——第一章分析过，而且这个限制还是动态的。靠传输层的努力，能把管道变得更粗一些、把吞吐量变得更大一些吗？不行。

结论：传输层加强了网络层的服务，可靠性和安全性的品质可以加强；但带宽和延时，加强不了。

### 多路复用与解复用

传输层非常重要的一个功能：复用与解复用。在源端，很多应用进程都复用同一个 TCP 传输实体往外发；到了目标端，TCP 实体会接到来自远端很多应用进程的报文段，要把它们区分出来，谁是谁的，再交还回去。源端做复用，目标端做解复用。

什么叫源端、什么叫目标端？通信是双向的，但双向通信可以分解成两个单向：这个方向上我是源、你是目标；那个方向上你是源、我是目标。所以"源端复用、目标端解复用"没有任何歧义——任何一个应用进程，它既是源端，同时又是目标端。

这也是把 IP 的主机到主机服务细分成果进程到进程服务的一步：复用与解复用，是网络层服务所不具备、经过传输层努力得以加强的品质。

### 封信的邮政比喻

复用解复用没那么抽象，用一个邮政的例子。美国东海岸和西海岸有两家人，Annie 家和 Bill 家，每家 12 个小孩——挺多的——两家是亲戚关系，交往还挺密切。这一家的 12 个小孩，定期地、每礼拜要向对方家的 12 个小孩每人发一封信。一共多少封？$12 \times 12 = 144$ 封。

麻烦的事来了：这 144 封信都要收费；而且这 144 封信的源端和目标端都一样——都是从 Annie 的 house 到 Bill 的 house。

怎么办？在源端，让 Annie 家的老大把发给 Bill 家 12 个小孩的信全部收集过来——老大的、老二的，一直到老 11、老 12 的，像宫廷剧一样——打成一个包。这个包的源地址是 Annie 的 house，目的地址是 Bill 的 house，甩到他门口的邮箱里。邮箱暗示的是邮政公司提供的服务：把邮包从一个 house 搬到另一个 house。到了 Bill 家，Bill 家的老大把邮包拆开：这是老大的 12 封，这是老二的 12 封……老 11、老 12 的 12 封，一一分还。

对应过来：邮政公司提供的是 house 到 house 的服务，这就是网络层的主机到主机；要把 house 里具体某一个人到对方 house 里具体某一个人的通信细分出来，Annie 家的老大做的是聚合——复用，Bill 家的老大做的是拆分——解复用。

### TCP 与 UDP 的服务特性对照

最后把两个协议放在一起看。TCP 提供的服务特性：多路复用解复用是必须的——把 IP 到 IP 的主机到主机服务细分成进程到进程；有流量控制、有拥塞控制，当然还有连接管理——两个应用进程要用 TCP 通信，之前要先建立 TCP 连接，有连接的建立、连接的维持，最后还有连接的拆除。此外非常重要的一点：TCP 提供的是可靠的字节流服务。

UDP 呢？提供的是不可靠的服务，而且是数据报的服务——每一个 datagram 为单位来传，不是字节流。跟 TCP 的差别就两条：一个可靠，一个不可靠；一个是字节流，一个是数据报。UDP 同样提供复用与解复用。

两个协议都是在 IP 提供的服务基础之上向上层服务的。IP 是 best effort，UDP 提供的服务几乎也是 best effort——只不过把服务细化到了进程到进程。除此之外，UDP 没有再做任何额外的工作。还有一条两个协议都一样：不管是 TCP 还是 UDP，都不能提供延时的保证和带宽的保证。

| 服务特性 | TCP | UDP |
| :--- | :--- | :--- |
| 连接 | 面向连接（建立、维持、拆除） | 无连接 |
| 可靠性 | 可靠 | 不可靠（可能乱序、丢失） |
| 交付形式 | 字节流，不保证报文界限 | 数据报，以 datagram 为单位 |
| 流量控制 / 拥塞控制 | 有 | 无 |
| 复用与解复用 | 有 | 有 |
| 延时、带宽保证 | 无 | 无 |

传输层的底子就是这些：把主机到主机的尽力而为服务，加强成进程到进程的、尽量可靠也尽量安全的服务——而带宽和延时，谁也变不出来。接下来就从多路复用与解复用开始，一层一层拆开看。
