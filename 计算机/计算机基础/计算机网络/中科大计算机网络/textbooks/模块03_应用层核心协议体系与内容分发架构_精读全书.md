## 应用层通信原理与网络应用架构
> 对应块：BLK11 | 覆盖分集：P12-P13上 | 块标题（分集名）：《2.0 应用层概述》

### 应用层在协议栈中的定位与学习主线

计算机网络体系结构采用自顶向下（Top-down）的学习路径。在完成了对全书网络基础概念的系统梳理之后，我们正式切入计算机网络体系结构的最高层——应用层。

在协议栈的各个层次中，应用层是直面用户业务需求、直接释放网络价值的关键层次。围绕应用层的技术全貌，我们的学习主线可以清晰地划分为三大支柱：核心原理、协议实例以及网络编程实践。

```text
+-------------------------------------------------------------------------+
|                              应用层学习主线                             |
+-------------------+-----------------------------+-----------------------+
|     核心原理      |          协议实例           |     网络编程实践      |
+-------------------+-----------------------------+-----------------------+
| · 进程标识与寻址  | · Web 应用与 HTTP 协议      | · TCP Socket 编程     |
| · 传输层服务模型  | · 文件传输应用与 FTP 协议   | · UDP Socket 编程     |
| · 层间接口与抽象  | · 电子邮件系统 (Email)      | · 操作系统 API 调用   |
| · 交互架构范式    | · 域名解析系统 (DNS)        | · 客户端/服务器实现   |
|                   | · 对等网络 (P2P) 与 CDN 分发|                       |
+-------------------+-----------------------------+-----------------------+
```

从这张主线图可以看出，本讲的核心目标在于两点：第一，透彻掌握计算机网络分布式应用的工作原理；第二，建立网络应用协议的概念体系，并理解它们在操作系统层面的工程实现机理。

分布式网络应用绝不能脱离下层网络孤立存在。应用进程之间要实现跨越网络的报文交换，必须依托传输层所提供的通信服务。那么，传输层向上层提供的服务能力究竟该如何精确刻画？在计算机网络中，我们使用一个专门的术语来描述它——服务模型（Service Model）。

服务模型是用一组指标体系来刻画传输层服务的。不同的传输层协议（例如 TCP 与 UDP）具有完全不同的服务模型与质量保障特征。应用进程必须基于自身对数据丢失容忍度、吞吐量需求以及时延敏感度等指标的权衡，选用相匹配的服务模型。

在 TCP/IP 体系结构中，应用层与传输层之间存在一个极其特殊的层间界面。传输层向应用层提供服务的形式，正是套接字应用程序接口（Socket API）。Socket API 构成了应用层调用底层网络通信能力的原语。应用层如何借助操作系统内核暴露的 Socket API，构建起稳定可靠的分布式系统，是贯穿应用层理论与实践的关键纽带。

### 端系统驱动的应用创新与低门槛部署

如果考察整个互联网体系结构，哪一个层次的协议种类最多、更新最为活跃？毫无疑问是应用层。

为什么应用层的协议繁荣程度远远超过传输层、网络层和链路层？根本原因在于互联网体系架构所赋予的低门槛创新机制。互联网的核心设计原则之一，是将通信的全部“智能”推向网络边缘的端系统（End System / Host），而网络核心（Network Core）仅专注于数据分组的高速存储转发。

```text
+-------------------+                               +-------------------+
|     端系统 A      |                               |     端系统 B      |
|  [应用层 Application]                             |  [应用层 Application]
|  [传输层 Transport] |      +---------------+      |  [传输层 Transport] |
|  [网络层 Network]   |------| 核心路由器     |------|  [网络层 Network]   |
|  [链路/物理层 Link] |      | (最高到网络层) |      |  [链路/物理层 Link] |
+-------------------+      +---------------+      +-------------------+
```

在网络核心内部的路由器与交换机等中继设备中，协议栈最高只实现到网络层，根本不存在应用层的接入，也不运行任何应用软件。

> **结论**：互联网应用层协议的部署门槛极低。开发者设计、实现并上线一项新型网络应用时，完全不需要对网络核心的基础设施做任何变动，只需要在端系统上编写程序并运行即可。

这种架构设计极大地激发了业务创新。无论是早期的 Email、FTP、Web 浏览，还是后来的 P2P 资源共享、流媒体点播与直播，抑或是移动支付、网约车、共享单车与大规模网络游戏，其落地路径都极其敏捷：开发者编写服务器软件，购买或租用一台联网主机将其启动；编写客户端软件并挂载在分享平台上供用户下载。只要终端用户能够运行该软件并接入互联网，一项全新的网络应用便能迅速运转起来。

只要在上层能够吸引到足够的用户规模，形成正向的商业循环，新型业务便能以极高的速度完成自主演进。这也是互联网发展至今，接入用户与终端设备数量呈现爆炸式增长的根本驱动力。

在应用层创新领域，产业实践呈现出了鲜明的演化特征。早期的互联网应用形态多由国外开创，国内产品多以借鉴为主，例如早期即时通讯产品对 ICQ 的参照。然而伴随国内通信基础设施的大规模建设以及工程技术人才的持续积累，国内在应用层的业务重构与场景创新上已走在世界前列。现代电商交易系统、超大规模移动支付、高并发短视频与直播平台，其交互体验、并发处理深度与工程成熟度均展现出极强的工业竞争力。只要具备工程创新力与架构设计能力，端系统架构赋予开发者的施展空间几乎是无限的。

### 分布式网络应用的通信架构范式

从应用进程之间组织协作与交互的方式来看，主流的网络应用架构可以划分为三种经典范式：客户/服务器模式、对等网络模式以及二者结合的混合模式。

```text
       客户/服务器 (C/S) 模式                      对等网络 (P2P) 模式
          +-------------+                       +--------+        +--------+
          |  服务器     |                       | Peer A |<------>| Peer B |
          | (固定IP/端口)|                       +--------+        +--------+
          +------+------+                            ^                 ^
            /    |    \                              |        / \      |
           /     |     \                             v       /   \     v
          v      v      v                       +--------+  /     \+--------+
     +----+    +----+   +----+                  | Peer C |<------->| Peer D |
     |C 1 |    |C 2 |...|C N |                  +--------+         +--------+
     +----+    +----+   +----+             (每个节点既是客户端，又是服务器)
 (资源集中于服务器，扩展性受限)
```

#### 客户与服务器模式及其性能瓶颈

客户/服务器（Client-Server，C/S）模式是互联网中最基础、应用最广泛的通信范式。在 C/S 模式中，通信双方的地位是高度不对等的：

- **服务器（Server）**：必须先于客户端启动运行，并且通常保持 24 小时常开（Always-on）状态。它在网络中拥有固定的 IP 地址，并在操作系统中守候在预先约定的知名端口（Well-known Port，例如 Web 服务的 80 端口、FTP 服务的 21 端口）上，被动等待连接。全部资源（计算资源、存储硬件、软件逻辑与业务数据）均集中存放于服务器端。
- **客户端（Client）**：后于服务器运行，根据用户需求随时启动，主动向服务器发起资源请求。客户端通常不需要拥有固定的 IP 地址，例如笔记本电脑接入 Wi-Fi 后通过动态主机配置协议（Dynamic Host Configuration Protocol，DHCP）动态获取临时 IP。客户端之间从不进行直接通信。

C/S 架构逻辑清晰、管控便利，但它面临着两个致命的结构性弱点：

> **易错点**：C/S 架构的可扩展性（Scalability）较差。随着并发访问用户规模的扩大，系统性能并不是平滑、线性地温和下降，而是在突破临界负载后呈现断崖式暴跌。

单台服务器的计算能力、内存吞吐、磁盘 I/O 读写以及网卡出口带宽都存在物理上限。当成千上万乃至数十万用户并发涌入时，哪怕逐级升级服务器硬件，系统瓶颈也会迅速转移至网络出口或前端链路上。一旦某一个环节被击穿，服务响应时延将急剧恶化，最终引发请求堆积与全面瘫痪。

此外，C/S 模式存在严重的单点故障（Single Point of Failure，SPOF）隐患。客户端的所有服务均维系于中心服务器，一旦服务器物理宕机或网络中断，依赖该服务器的所有客户端业务将全线停止，系统的整体可靠性严重受限。

#### 对等网络模式与自扩展性优势

为了突破 C/S 模式的容量天花板，对等网络（Peer-to-Peer，P2P）模式应运而生。在 P2P 系统中，网络节点被称为对等体（Peer），任意两个对等体之间可以直接建立通信链路。

P2P 架构的核心特征在于角色的动态性与对等性：
每个 Peer 节点既请求其他节点的服务，同时又利用自身闲置的计算、存储与带宽资源向其他节点提供服务。在某一个具体的会话（Session）中，如果该 Peer 主动向对端请求数据，它就扮演客户端角色；而在另一个并行的会话中，当它响应对端的下载请求、上传本地持有的数据时，它就扮演服务器角色。

> **结论**：P2P 架构具备优异的自扩展性（Self-scalability）。系统每增加一个发起请求的用户，同时也为整个系统贡献了一份全新的服务能力与上行带宽。

这种“人人为我，我为人人”的机制，打破了单点服务器的服务瓶颈。随着用户规模从几千暴增至几十万甚至数百万，系统整体服务供给能力随之同步放大，单个用户感受到的下载性能往往能够维持在相对稳定的水平。诸如迅雷、BitTorrent 等大规模文件传输与分布式多媒体系统，正是依托这一机理实现了低成本的海量扩容。

然而，P2P 架构的优势伴随着沉重的管理代价。P2P 节点高度离散且具备高度动态性（Churn 特性）——用户随时上线，也随时可能下线断网。如何实时追踪海量节点的在线状态、动态索引资源碎片分布，使得 P2P 系统的调度控制与运维管理难度呈指数级攀升。

#### 集中式控制与分布式分发的混合架构

在工程实践中，纯粹的 C/S 模式与纯粹的 P2P 模式往往各有局限，因此融合两者优势的混合架构（Hybrid Architecture）成为了许多知名网络应用的破局之道。

混合架构的典型代表是开创了 P2P 音乐共享浪潮的 Napster 系统。该系统最初由美国西北大学一名大一本科生为了在校园网内共享 MP3 音乐而研发。当时 CD 唱片价格昂贵，学生们将音乐抓轨压缩为 MP3 格式，但在本地计算机之间通过电子邮件或 FTP 共享极其繁琐低效。Napster 巧妙地设计了一套混合通信机制：

```text
                    +--------------------------+
                    |    集中式目录服务器      |
                    | (维护: IP, 在线状态, MP3) |
                    +--------------------------+
                        ^                  ^
       1. 注册上线/列表 |                  | 2. 查询某 MP3
                        v                  v
                 +------------+      3. 建立 P2P 连接      +------------+
                 |  Peer A    |<=========================>|  Peer B    |
                 | (文件拥有方)|    4. 传输 MP3 文件数据   | (文件下载方)|
                 +------------+                           +------------+
```

读懂这张架构图，Napster 的运行机理可以拆解为清晰的四个阶段：
1. **上线注册**：客户端 Peer A 启动后，主动向集中式目录服务器发起注册请求，上报自身的 IP 地址、端口以及本地允许共享的 MP3 文件清单。
2. **目录查询**：当客户端 Peer B 需要获取某首特定歌曲时，它向集中式目录服务器发送检索请求。由于服务器集中维护了所有在线用户的共享元数据，服务器能够瞬间匹配出当前持有该文件的所有在线 Peer 列表（包括 Peer A），并将 Peer A 的地址返回给 Peer B。
3. **点对点传输**：Peer B 拿到地址后，脱离中心服务器，直接按照 Napster 协议与 Peer A 建立底层的 P2P 通信链路，直接发起文件下载。
4. **共享裂变**：Peer B 下载完成后，随即向集中式服务器追加注册，声明自己也持有该音乐并可对外提供上传服务。

Napster 的精髓在于：**目录查询采用集中式的 C/S 模式，保证了检索的确定性与高效性；具体的数据文件分发则采用分布式的 P2P 模式，规避了中心服务器的带宽枯竭风险**。这种网络效应引发了极大的飞轮效应——共享的用户越多，资源总量越丰富，下载速率越快，进而吸引更多用户涌入。在高峰时期，美国许多大学校园网有超过四分之三的带宽被此类 P2P 流量占据。

虽然 Napster 最终因版权诉讼被法院判定侵权，且其集中式目录服务器的“物理电源插头被拔掉”后整个网络便瞬间瘫痪（揭示了控制层单点依赖的脆弱性），但这种集中控制与分布式传输相结合的技术范式却深远地影响了后来的网络工程。早期的即时通信软件（如 QQ、QICQ）同样采用了这种混合思路：用户登录认证、好友在线状态维护采用集中式 C/S 架构，而好友之间发送超大文件或直接音视频通话则尽可能协商走 P2P 通道。

### 分布式应用进程通信的核心支撑机制

无论网络应用采用何种宏观架构，剥开表层业务逻辑，分布式网络应用最本质的技术诉求只有一个：**实现运行在不同端系统之上的应用进程之间的远端通信**。

两台不在同一物理位置的终端设备，唯有彼此能够收发应用报文（Message），才能衍生出五花八门的上层应用。

必须厘清跨网络通信与本地进程通信的本质边界：如果两个通信进程运行在同一台主机内部，它们的通信根本不需要遵循复杂的网络协议标准，直接借助操作系统内核提供的本地进程间通信（Inter-Process Communication，IPC）机制——如管道（Pipe）、消息队列（Message Queue）或共享内存（Shared Memory）——即可高效完成。

一旦通信进程分布在不同的联网端系统上，意念或“隔空传物”在工程上是不存在的。应用进程绝对不能直接把报文凭空扔给对方，必须依赖本地操作系统底层网络协议栈的支持，通过严格的层间接口调用，将报文逐层下沉并交由底层通信网络传输。

在具体通信语境中，进程的角色界定完全取决于会话中的主动性：
- **客户端进程（Client Process）**：在特定通信流程中首先发起通信请求的进程。
- **服务器进程（Server Process）**：在特定通信流程中等待请求并被动做出响应的进程。

在 P2P 系统中，尽管对等体从整体架构上看地位对等，但在微观的每一次具体会话中，主动发起数据索取的一方依然是客户端进程，被动响应提供数据的一方依然是服务器进程。

要让跨越网络的分布式应用进程顺利运转，网络体系结构必须在工程上彻底解决三大核心问题：

```text
+-------------------------------------------------------------------------+
|                  分布式应用进程通信必须解决的三大问题                   |
+-------------------+-----------------------------+-----------------------+
| 核心问题          | 关注焦点                    | 解决机制              |
+-------------------+-----------------------------+-----------------------+
| 问题一：标识与寻址| 如何在全网唯一标记并定位进程 | 主机 IP 地址 + 端口号 |
| 问题二：层间服务调用| 应用层如何使用传输层的能力   | Socket API 与套接字句柄|
| 问题三：应用协议规范| 进程间交换的报文格式与行为   | 报文语法、语义与时序规则|
+-------------------+-----------------------------+-----------------------+
```

### 进程寻址与端口号分配机制

解决跨网络通信的第一个前提，是必须能够唯一标识一个应用进程，并提供有效的寻址路径。

这就像在电商平台寄送包裹：发件人必须提供收件人的确切地址、姓名与手机号。如果两个学生住在同一个寝室，姓名和电话完全相同，快递员送达包裹时将根本无法确认交付对象。进程通信同样如此，标识（Identification）负责提供唯一性以区分彼此，寻址（Addressing）则负责提供路由到达的拓扑位置信息。

在 TCP/IP 体系结构中，要精确寻址一个远端应用进程，必须由三个要素紧密联合界定：

1. **主机 IP 地址**：由网络层（IP 层）提供。IP 地址标识了端系统在互联网中的网络拓扑位置，网络层服务据此将数据分组路由并传送到目标主机。
2. **传输层协议类型**：确定运行在该端系统上的应用进程究竟挂载在 TCP 协议实体还是 UDP 协议实体之下。
3. **传输层端口号（Port Number）**：仅凭主机 IP 地址只能找到设备，但现代操作系统普遍支持多任务并发运行，一台主机上可能同时跑着 Web 浏览器、邮件客户端、音乐播放器与终端远程连接。为了在一台主机中精准区分不同的并发应用进程，传输层引入了端口号这一关键技术机制。

> **定义**：端口号是一个 16 比特（bit）的整型数值，取值范围为 $0 \sim 2^{16}-1$（即 $0 \sim 65535$）。TCP 与 UDP 各自拥有独立的、互不干扰的 65536 个端口号空间。

在端口号的使用约定上，互联网工程界做出了清晰的规划：
某些核心网络应用长期运行在固定的公认端口上，这类端口被称为知名端口（Well-known Port）。例如，Web 服务器默认守候在 TCP 80 端口，FTP 传输默认守候在 TCP 21 端口，Telnet 远程登录默认守候在 TCP 23 端口。当客户端发起访问时，如果不显式指定远程端口，操作系统与协议栈会默认填入该应用约定的知名端口。

通过将主机 IP 地址与传输层端口号进行绑定，就构成了网络通信中的一个端节点（Endpoint）。在实际网络通信中，任何一对应用进程之间的端到端会话关系，本质上就是通过这两个端节点建立起来的。

### 层间接口交互与套接字抽象

应用进程找到彼此之后，必须跨越应用层与传输层之间的层间接口交换数据。

#### 跨越层间接口的最小信息集

应用进程调用传输层提供的服务时，必须通过服务访问点（Service Access Point，SAP）向下传递信息。从物理概念上类比，应用进程好比寄件客户，传输层就像快递承运网络。寄件人委托快递网点寄送货物，必须当面交接清楚三样核心信息：

1. **货物实体**：即应用层产生的原始报文。对于应用层而言这是承载业务逻辑的完整数据，但对于下层传输层而言，这只是上层交付下来的服务数据单元（Service Data Unit，SDU）。
2. **寄件人信息（源端标识）**：本地端系统的 IP 地址以及本地应用进程绑定的传输层端口号。若不携带源端标识，对方收到货物后一旦需要确认或回传应答数据，将因缺乏回邮地址而无法响应。
3. **收件人信息（目的端标识）**：远端目标主机的 IP 地址以及远端目标应用进程守候的传输层端口号。

当传输层协议实体（TCP 或 UDP）在层间接口拿到这三项信息后，便开始进行协议数据单元（Protocol Data Unit，PDU）的封装操作。传输层提取源端口与目的端口等控制字段，按照协议规范压入传输层首部，将应用层报文（SDU）作为数据载荷装入负载区，最终拼装成一个完整的 TCP 报文段（Segment）或 UDP 数据报（Datagram）。

```text
           [ 应用进程 Application Process ]
                          |
             Socket API   |  传递: 数据载荷 (SDU) + Socket 句柄 (整数)
                          v
         +----------------------------------+
         |     传输层接口 (SAP / Socket)     |
         |  TCP Socket: 映射四元组           |
         |  (源IP, 源端口, 目的IP, 目的端口)  |
         |  UDP Socket: 映射二元组           |
         |  (本地IP, 本地端口)               |
         +----------------------------------+
                          |
                          v
         +----------------------------------+
         | 封装为 TCP 报文段 / UDP 数据报   |
         | [ 传输层首部 (Port等) | 数据载荷 ] |
         +----------------------------------+
```

#### 套接字句柄机制与状态映射

如果每一次应用层向下传递数据时，都需要在层间接口上反复完整传递“发给谁（目的 IP、目的端口）”、“谁发的（源 IP、源端口）”以及“货物本身”，不仅会产生巨大的层间参数开销，更会导致操作系统内核的状态维护极其低效。

为了以极低的开销跨越层间接口，操作系统引入了套接字（Socket）抽象。

套接字的设计理念在底层系统编程中有着极具代表性的映射——C 语言中的文件 I/O 操作。在 C 语言程序中，当开发者调用系统调用打开一个磁盘文件时，操作系统内核在内存中建立复杂的文件控制块并初始化读写指针，但返回给应用程序的仅仅是一个微小的整型数值——文件描述符或句柄（File Descriptor / Handle）。在此后的整个生命周期内，程序无论是读取、写入还是关闭该文件，都只需要在 API 中传入这个整数句柄即可。操作系统内核会根据该句柄自动关联到内核中对应的数据结构。

网络通信中的套接字完全继承了这一经典设计：

> **定义**：套接字（Socket）在操作系统与编程接口层面，本质上是一个受操作系统内核管辖的整型数字（句柄）。它作为应用层与传输层交互的门面，将复杂的底层通信上下文封装在一个极小的整型索引之后。

当应用进程通过 Socket API 成功创建通信端点或建立网络连接后，操作系统便会向其返回一个 Socket 整数句柄。不同传输层协议对 Socket 绑定的内核上下文含义存在显著差异：

- **TCP 套接字（面向连接）**：返回的整型 Socket 句柄在操作系统内核中唯一绑定并代表一个**四元组**：
  $$\text{TCP Connection} = (\text{Source IP}, \text{Source Port}, \text{Destination IP}, \text{Destination Port})$$
  此后在整条连接的生命周期内，应用进程向该 Socket 句柄写入或读取数据时，再也无需传递任何 IP 和端口信息。只要指定该整数，操作系统便能瞬间锁定对应的 TCP 连接实体、滑动窗口状态、发送接收缓冲区及重传定时器。
- **UDP 套接字（无连接）**：返回的整型 Socket 句柄在操作系统内核中仅绑定并代表一个**二元组**：
  $$\text{UDP Socket} = (\text{Local IP}, \text{Local Port})$$
  它仅表示本地端点守候在哪个 UDP 端口上。

引入 Socket 句柄机制，最大限度地压缩了穿过层间接口的信息交互量，使跨层调用变得极其轻量，同时也为操作系统内核统一管理网络连接的生命周期与通信状态提供了极其高效的控制支点。

### 应用层协议的设计要素

当应用进程解决了网络寻址、打通了层间接口并依托 Socket 实现了双向数据传输后，分布式通信便进入了最后一个核心阶段：**应用层协议的规范制定**。

传输层所承诺的仅仅是将一连串字节或报文完好地搬运到对端进程，但传输层对字节流内部所代表的业务内涵一无所知。收发双方的应用程序如何准确理解彼此的意图？这必须依赖双方共同遵守的应用层协议（Application Layer Protocol）。

一个严谨的应用层协议，必须在协议设计规范中明确界定三大核心要素：

1. **报文语法（Syntax）**：定义在传输线路上交换的报文格式与结构布局。明确每个字段占用多少空间、何处为首部、何处为正文、字段以 ASCII 文本还是二进制格式编码，以及数据以何种边界进行定界。
2. **报文语义（Semantics）**：阐明报文内各个字段以及字段内特定标志位的确切含义。例如在 HTTP 协议中，请求方法 `GET` 代表向服务器索取指定资源，状态码 `404` 代表目标资源未找到。
3. **报文时序与动作规则（Timing & Action Rules）**：精确规定应用进程在什么时间、满足何种前置条件下方可发送某种报文，以及在接收到特定报文后应当执行怎样的本地状态转移、业务处理并产生何种应答。

唯有在报文的语法、语义和时序规则上达成严格共识，分布在不同异构平台上的应用程序才能够顺畅交互，进而编织出 Web 浏览、文件共享、即时通信等浩瀚而繁荣的现代互联网应用生态。

## 套接字、应用协议与传输层服务
> 对应块：BLK12 | 覆盖分集：P13下 | 块标题（分集名）：《2.1 应用层原理》

传输层交给应用进程的，是一个整数。这个整数到底代表什么？只代表我的 IP 和端口号，还是把对方的信息也包进去了？——它一个数代表的就是四元组：我的 IP 和 TCP 端口号、对方的 IP 和 TCP 端口号。往后我通过这个整数去发数据，操作系统就知道是谁发的、发给谁；对方的数据到达，靠这四个信息反过来一查，就能找到建立起这个套接字（socket）的应用进程，把数据交给它。

### TCP 套接字：四元组的本地标示

先回答一个问题：这个 socket 是一个全局意义的标示，还是本地意义的标示？本地的。对方知不知道你的 socket？不知道。你的 socket 就是本地操作系统管理的一个整数，背后绑着你的 IP、你的 TCP 端口、对方的 IP、对方的 TCP 端口，是为了便于管理而引入的人工机制。对方不知道，网络层以下也不知道，只有本地的应用层和传输层知道——它是应用层和传输层之间的一个约定。

为什么 TCP 要引入这样一个整数？因为 TCP 是面向连接的服务：两个应用进程通信之前要先建立连接，而这条会话通常要持续一段时间，通信关系比较稳定。既然如此，就可以在建立连接的时候，用一个整数把"我的 IP、我的 TCP 端口、对方的 IP、对方的 TCP 端口"这条会话关系整个代表起来。这样一来，应用进程只拿这个 socket 去发，操作系统就知道：从我的这个 IP 的这个 TCP 端口，发给对方的这个 IP 的这个 TCP 端口；收也是类似的。好处有两个：一是穿过层间的信息量最少——不然每发一个报文都得把四元组抄一遍、再附上货物本身，不是很烦吗？二是便于操作系统管理：传输层用这个整数代表了一条稳定的会话关系。

> **易错点**：socket 不是端口号。TCP 的 socket 是一个本地意义的标示，物理上看就是一个整数值，由本地操作系统分配、只有它知道；它代表的是两个应用进程之间的一条会话关系。这个概念重要，也容易和端口号混淆，理解上稍微有一点难度——把"会话关系"这四个字抓住，就都对上了。

它和打开文件是同一个套路。打开一个文件，要指明哪个目录、哪个文件名、什么打开方式，操作系统返回给你一个整数；以后在程序当中就用这个整数操作文件——操作这个整数，就是操作那个文件。TCP socket 完全一样：建立连接时操作系统返回一个整数，代表这条会话关系；以后操作这个 socket 的值，就是操作这条会话关系。对这个 socket 写，就是写给对方；从这个 socket 读，读到的就是对方传过来的。

### 套接字表与收发封装

操作系统要维护一张表，表项包括：socket 值、我的 IP、我的 TCP 端口、对方的 IP、对方的 TCP 端口，还有连接状态。这张表是应用进程借助传输层提供的 socket API 建立 socket 时建立起来的——不过它不是一下子全填满的：TCP 连接的建立分好几个阶段，表项内容和状态都在不断更新，这要留到讲 TCP 连接建立的时候再展开；但只要通过 socket API 建立起 socket，这个表项就有了。这张表应用进程在用，传输层也在用，是两边共同的约定。

发送时，应用进程往下交两样东西：数据本身和 socket 整数值。传输层拿 socket 一查表，得到完整四元组和当前状态，就知道怎么封装了：把要传输的数据——服务数据单元（SDU）——前面加上 TCP 段头，作为 TCP 段的主体，封装成 TCP 段。TCP 封装只用到源端口和目标端口，那源 IP、目标 IP 干什么用？它们作为接口控制信息（ICI）连同 TCP 段一起往下交给 IP，由 IP 去封装 IP 数据报。上节课说过，SDU 穿过层间接口时要附加 ICI：SDU 是要传输的数据，ICI 是穿过层间接口的控制信息——这里就是一个具体例子。

接收方向完全反过来：下层交上来，对方的 IP 和我自己的 IP 从 IP 层得到，配上 TCP 头里的对方端口和我的端口，四元组齐了；拿四元组到套接字表里反查出 socket 值，再找到是哪个应用进程创建了这个 socket——也就是它的进程号（PID）——把数据交给这个进程，应用进程就收到了。

```text
发送方向（本机）：
  应用进程
    |  交下两样：应用数据(SDU) + socket 整数值
    v
  传输层 TCP 实体
    |  拿 socket 查套接字表：
    |    socket值 | 本地IP | 本地TCP端口 | 对端IP | 对端TCP端口 | 连接状态
    |  封装：SDU + TCP段头 ==> TCP 段
    |  连同 ICI(源IP / 目标IP) 下交
    v
  网络层 IP 实体：TCP段 + IP头(源IP/目标IP) ==> IP 数据报
    |
    v
  ~~~~~~ 中间网络（路由器、交换机，网络基础设施提供的服务）~~~~~~

接收方向（对端）：
  IP 数据报到达，IP 层取下源IP / 目标IP 上交
    -> TCP 按四元组(本地IP, 本地TCP端口, 对端IP, 对端TCP端口)反查套接字表
    -> 得到 socket 值，找到创建它的应用进程 PID
    -> 去掉 TCP 段头，把数据交给该应用进程
```

发送方向是"socket 值查四元组"，接收方向是"四元组反查 socket 值"，一正一反，用的是同一张表。

### 同一端点上的多条会话

两个进程通信，它们之间的会话关系由两个端节点（end point）决定。一个端节点是本地 IP 2.2.2.2 上的 80 号端口，另一个端节点是对端 IP 上的 233 号端口。在这台主机上，一个 socket 整数值代表这条会话，另一个不同的整数值代表另一条会话——注意，这两条会话的源 IP 和源端口都是 2.2.2.2 的 80 号端口。也就是说，同一个端口上的同一个应用进程，可以同时维持多条会话，每条会话各有一个 socket，整数值互不相同——具体是多少，完全由操作系统内部分配，两个 socket 的值可能差得很远。

它们区分得开，靠的是四元组整体：会话关系对应的是不同的对方应用进程——对方 IP 可能一样，但目标端口一定不一样；如果四个元素全都一样，那就是同一个 socket 了。所以 TCP socket 代表的是会话关系，而不仅仅是一个主机的标识、一个分布式进程的 ID 号：同一个进程、用同样的 IP 和端口跟不同的对方通信，拿到的是不同的 socket 值，代表的是不同的会话关系。

### UDP 套接字：本地端点的二元组标示

看完 TCP 的 socket 再看 UDP 的。UDP 两个应用进程通信之前要不要握手？不要。有些进程很烦握手：握手去、握手回来，事务性的应用本来一下就能搞定，握手那么麻烦干什么。UDP 的每个报文传输都是独立的：同一个进程通过同样的 IP 和 UDP 端口先后发两个报文，前一个可能给这个进程，后一个可能给那个进程——很可能是这种情况。

所以 UDP 的 socket 用一个整数代表的是一个端节点：只捆绑本地 IP 和本地 UDP 端口这个二元组，不代表会话关系——因为 UDP 无连接。目的同样是让穿过层间的信息量少、便于管理。

发送时必须交三样东西，还是快递的比方：你把货交给顺丰——第一，货物本身总得给吧？交给顺丰一件空气是不行的，必须交数据；第二，socket 要给，它代表你是谁：你的 IP 和你的 UDP 端口；第三，两样够了吗？顺丰说：你是谁我知道，货是什么我也知道，你寄给谁呀？——所以还必须给对方的 IP 和对方的 UDP 端口。对比 TCP：socket 已经代表四元组，每次交两样就够了；UDP 的 socket 只代表自己这一端，所以每次发都要交三样：货物本身、UDP socket、对方的 IP 和端口号。也就是说，不必在每个报文里指明自己的 IP 和 UDP 端口（socket 已经代表了），但必须指明对方的 IP 地址和 UDP 端口。对方的 IP 和端口在 socket API 里用专门的数据结构表示，讲到本章最后两节再介绍。

把这个比方再延伸一步。TCP 相当于你有一个登记号：你经常跟朋友互寄东西，就用一个整数把"我哪栋楼、哪个房间、哪个人，对方哪栋楼、哪个房间、哪个人"这条通信关系登记下来——交给顺丰一个整数、把货甩给它，它就知道怎么寄了。UDP 是偶尔寄一次东西：不常来往，没登记，标示一下你自己，再写上对方的地址就行。

接收时：对方发来的报文带着目标 IP 和目标 UDP 端口，据此查出对应的 socket 值，找到它所对应的应用进程（PID），把数据交给它，对方就收到了。

> **结论**：UDP socket 是一个具有本地意义的二元组映射关系——用一个整数代表本地 IP 和本地 UDP 端口号，它只是两个主机之间会话关系的一个端节点。对方不知道你用的是什么整数值，也不需要关心。

| 对比点 | TCP 套接字 | UDP 套接字 |
| :--- | :--- | :--- |
| 整数代表什么 | 四元组：本地 IP、本地 TCP 端口、对端 IP、对端 TCP 端口 | 二元组：本地 IP、本地 UDP 端口 |
| 标示的含义 | 一条会话关系 | 一个本地端节点 |
| 发送时下交几样 | 两样：数据 + socket | 三样：数据 + socket + 对端 IP 与 UDP 端口 |
| 通信前提 | 先建立连接，会话持续一段时间 | 无连接，每个报文独立 |
| 对端是否知道这个整数 | 不知道，仅本地意义 | 不知道，也不需要关心 |

套接字就像一个门：发送端应用进程把数据从这个门推出去，对方的应用进程就能从它那边的门收到——你可以想象这两个门是连在一起的。中间靠什么连？靠网络基础设施：路由器、交换机这些中间设备提供的服务。应用进程只关心本层的事：借助传输层提供的服务建立 socket，通过 socket 收发——我发对方就收，对方发我就能收，这样就可以了。至于传输层到底怎么实现分布式远程应用进程之间的通信——数据交给它，它能原原本本地送到对端应用进程手里——稍安勿躁，讲到传输层就清楚了，那部分内容还是有一定坡度的。

### 应用协议：只是应用的一部分

到这里解决了两件事：一是标识和寻址各个分布式应用进程；二是传输层通过 socket API 向上提供发送与接收服务。现在轮到第三件事：如何在传输层所提供的服务基础上定义我们自己的协议、编制应用程序，实现业务逻辑和动作次序，最后做出各种各样的应用。

应用协议也是协议的一种，只不过处在 TCP/IP 协议栈的应用层，是协议不断具体化的结果。协议早就复习过：对等层的应用进程在通信过程中应该遵守的规则集合——放在这里，就是对等的分布式应用进程之间遵守的规则集合。它规范三件事：语法（应用报文的格式包含在语法范围之内，即报文长什么样）；语义（每个字段取什么值的时候代表什么含义）；动作和次序（先做什么、后做什么）。

但应用协议是应用的全部吗？不对，仅仅是应用的一部分。一个 Web 应用、一个 FTP 应用，除了协议，还包括用户界面、本地 I/O 操作、业务逻辑——这些是跟网络交互无关的部分。协议只规范双方交互过程中跟网络相关的那部分内容；跟网络交互有关、遵守协议的那部分，我们叫应用实体。跟它无关、但这层功能在实现过程中又需要用到的（界面、I/O、内部处理逻辑），不算在实体范围之内。讲传输层实体、讲 IP 的网络层实体，指的都是"只与网络交互有关、遵守协议"的那部分内容。

Web 是最典型的例子。Web 应用除了 HTTP 协议、用户界面、I/O 操作之外，还包括 HTML 文件的解释。HTML 属于 HTTP 协议的一部分吗？不属于，它是额外的。有人用 HTTP 上载、下载文件，根本不需要 HTML——HTML 只是说把这个文件拿来之后，按 HTML 的格式解释它，在用户的客户区把它画出来，就这么个概念。

应用协议分两类。一类是 open 的开放协议，以 RFC 文档的形式发布，任何厂商和个人都可以遵守它的规范实现自己的应用；另一家厂商按同一个协议实现了应用，双方就能互操作。另一类是不公开的专用协议（私有协议），比如通过互联网打电话的 Skype，它的协议就不公开。

### 传输层服务的衡量指标

传输层向应用层提供的服务，拿哪些指标衡量？四个：数据丢失率（可靠性）、延时、吞吐量、安全性。

可靠性：通过传输层的服务，数据丢不丢？有些应用对可靠性要求比较高，只能跑在 TCP 之上；有些要求不高，就可以跑在 UDP 之上。Web 应用对可靠性要求高不高？高。电子邮件呢？高——错了一个字节，邮件的格式可能就乱了，根本解释不了。文件传输更不用说：传个文件丢两个字节算怎么回事，文件还打得开吗？

延时：这边交上来、对方收到，中间有个延时——不是延时差，延时差是另外一个术语。多媒体应用对延时敏感：通过 Web 跟对方视频，延时一大就很麻烦。我说话的时候数据源源不断传向对方，但因为延时大，对方看到的还是我之前的画面，以为我没在说；为了打破尴尬他开口说话，两个人的声音就撞到一起。

人对多大的延时敏感？这是自然规律：声音的传播速率是每秒 340 米左右，而人在演化过程中只跟周围一二十米、嗓门洪亮顶多一两百米范围内的人说话。所以端到端延时 100 毫秒左右还可以；到了 400、500 毫秒就会被注意到；一两秒一定会被注意到，超过一秒就影响交互——要么两个人同时说，要么两个人都不说话。航天员跟地面家属会话，央视还直播过，就经常这样：要么同时开口，要么基本不说话，这是自然规律造成的。打游戏同样对延时敏感：一个命令、一个动作发出去，好半天才到服务器，服务器的响应再好半天回来，这游戏没法打——电脑被摔、键盘鼠标被砸，通常就发生在这种时候。

吞吐：单位时间内有效送到对方多少数据。发得少的时候，网络吞吐跟得上，发多少对方收多少；不断增大单位时间往外吐的数据量，对方可能就跟不上了——整个网络的吞吐量是有限的。第一章讲过，吞吐量取决于瓶颈链路：瓶颈链路的带宽把你限制在 100 kbps，你想超过 100k 就达不到。文件传输对吞吐要求倒不高：传得快，感受好一点；传得慢，挂着呗，传一天传完也很高兴，不至于影响应用能不能运行起来；对时间也不敏感。实时多媒体就不一样：用一定的编码传输实时音频视频，总需要一定的带宽——视频大致是 100 kbps 到几 Mbps 的量级。网络主播直播带货、才艺表演，传这段实时音视频就需要那么大的带宽；你到主播之间路径上的吞吐量一旦少于这个带宽，这个应用基本就跑不起来。

存储式音视频就是点播。这类多媒体应用可不可以容忍数据的丢失？可以。视频丢一块，看的时候不过多了一个小噪点；音频丢一块，用前后两块数据做插值"骗骗"用户——人基本听不出来，耳朵敏感的人可能听到一点毛刺，但不影响对这段语音语义的理解。不同的应用对这些指标的要求各不相同，自己消化一下。

| 指标 | 谁在乎，谁不在乎 |
| :--- | :--- |
| 可靠性（丢失率） | Web、Email、文件传输要求高；多媒体可容忍丢失 |
| 延时 | 实时多媒体、游戏敏感；文件传输无所谓 |
| 吞吐 | 实时多媒体有最低带宽要求；文件传输慢点也能用 |
| 安全性 | 私密性、可认证性、完整性，后面第八章展开 |

### TCP 提供的服务

从一般的计算机网络，收回到我们现在正在使用的互联网。互联网的传输层就两种协议：TCP 和 UDP。

TCP 向上提供可靠的服务：这边交下来什么，对方收到的就是什么，原原本本。其次是流量控制：两个 TCP 实体能够相互交互、协调——一边发得太快，另一边收不过来，收方就给发送方一个反馈，让它慢下来。再就是拥塞控制：收发双方本身都没问题，但网络可能出了问题，出现堵塞。TCP 实体能感知到路径上的拥塞程度：网络堵的时候把发送速率掐住，网络宽容的时候放开——你有足够的数据要发，我就给你放开——实时地调整、扩大或减少发送速率。

> **定义**：实体指实现网络协议的软件模块或硬件模块，而且是运行当中的模块。

TCP 不能提供什么？时间保证、最小吞吐量保证、安全保证——这三样都没有。另外，TCP 上的应用进程通信之前要握手，所以 TCP 提供的是面向连接的服务。为什么叫"面向连接"？因为这个连接仅仅体现在端系统之上：网络核心当中没有任何设备为这对通信关系维护状态。

### UDP 提供的服务与存在的理由

UDP 提供的是不可靠的服务：没有流量控制，没有拥塞控制，没有时间保证，没有带宽保证，也没有连接建立的过程。这也不行、那也不照，那为什么还要有 UDP？直接在 IP 之上，两个应用进程不也能通信吗？

UDP 存在的理由，一条条看。第一，IP 一般只提供主机到主机的区分，不能提供进程到进程的区分；UDP 增加了端口号这个机制，就能完成一个进程到远端分布式应用进程的通信。

第二，不需要建立连接。两个应用进程通信之前不用握手——有些应用建立连接反倒耽误事，前面说的事务性应用就是。

第三，不做可靠的工作反而好。跑在 TCP 上享受可靠服务，源端和目标端都要做很多复杂的工作：发出去要留副本、要编号，对方要给确认，隔一段合理的时间没等到确认还要重发——这是可靠性必须付出的代价：时空的代价、复杂性的代价，特别是时间的代价。数据封装成 UDP 段、再封装进 IP 分组在网络里飞，路上被噪声干掉了，再重传就要耽误时间；而多媒体应用对时间又敏感，有了可靠机制反倒不好。丢了不管，用前后传输的数据做个插值，反倒更容易让人接受。两个人打网络电话，基本就跑在 UDP 数据报之上：一边不断地说，说的内容不断形成 UDP 数据报、封装成 IP 分组往外打，丢了一个就丢，用前后的语音数据插值补上。

第四，没有流量控制、没有拥塞控制也挺好。实时多媒体应用跑在 UDP 上，这里交给我多快，我往网络中注入分组的速度就有多快——不考虑头部差异的话，下来的速度和注入的速度是一样的——不用考虑对方的感受，也不用考虑网络的感受，对实时多媒体应用来说这是非常好的事情。

| 服务特性 | TCP | UDP |
| :--- | :--- | :--- |
| 可靠传输 | 提供 | 不提供 |
| 流量控制 | 提供 | 无 |
| 拥塞控制 | 提供 | 无 |
| 连接建立（握手） | 有，面向连接 | 无 |
| 时间保证 | 无 | 无 |
| 最小吞吐量（带宽）保证 | 无 | 无 |
| 安全性 | 无 | 无 |

典型应用常跑在什么协议上：Email 跑在 TCP 上，Telnet 跑在 TCP 上，Web 跑在 TCP 上，文件传输跑在 TCP 上；流媒体 TCP 或 UDP 都有——现在的很多网络多媒体应用可以自己选，各有各的好处；互联网电话一般跑在 UDP 之上。那为什么有些实时多媒体应用跑在 TCP 上？因为有些机构接入大网的防火墙、路由器上的防火墙会把 UDP 分组过滤掉，跑 UDP 根本跑不动，只好跑 TCP，忍受 TCP 为实现可靠性而带来的延时增加和带宽波动。没办法，只能这样。

### 安全与 SSL

TCP 和 UDP 都不提供任何安全特性，传输是明文的。用 Telnet 远程登录服务器，用户名、密码全是公开的，没有经过任何加密；电子邮件有两种类型的协议（讲到电子邮件协议的时候再介绍），采用其中一种的话，用户名和口令也是明文传输的。拿抓包工具抓包一剖析，不但知道你用的是什么应用，连用户名和口令都能看到——很可怕。

要增加安全性怎么办？有一个办法：在 TCP 之上加一层 SSL——安全套接字层（SSL）。应用层使用 SSL，SSL 使用 TCP 的服务，SSL 加强 TCP 的安全性，再向应用进程提供安全的通信服务：服务器端的认证、客户端的认证、私密传输、报文的完整性，SSL 都能提供。私密性、完整性字面上容易理解；鉴别或者叫可认证性，就是"谁是谁"——你是不是你。

那 SSL 在哪一层？在传输层吗？不。它以库的形式跟应用进程一起编译、一起运行，严格来说属于应用层。当然也有人说 SSL 还在传输层——毕竟是它向应用层提供服务的——这层的界限就没有那么严格，说它在应用层也可以。SSL 还提供 SSL 级别的 socket API，应用直接跑在 SSL 之上，就不必自己操心安全方面的事了。

平时访问网站，输入的地址不是 HTTP 而是 HTTPS，注意到没有？这就是 Web 应用不直接跑在 TCP 上：浏览器跑在 SSL over TCP 之上，浏览器和服务器之间的通信就是安全的。访问阿里、淘宝、天猫这些网站，基本采用 HTTPS——用户名、口令这些东西如果都明文传就不好玩了，经常出安全漏洞。SSL 到底怎么提供这些安全特性，后面再说。

## Web 与 HTTP：对象、连接方式与报文格式
> 对应块：BLK13 | 覆盖分集：P14上 | 块标题（分集名）：《2.2 Web and HTTP》

Web 是一种应用，HTTP 是支持这种应用的协议。先把一个看起来有点反直觉的事实摆在前面：一个网页里有文字、有图片，可承载这个网页的那个 HTML 文件里，其实一张图片都没有——它存的只是这些图片的链接。理解了这一点，Web 为什么这样工作、HTTP 为什么这样设计，就都顺理成章了。

### 对象与 URL

> **定义**：对象（object）——Web 世界里的基本构件：一个网页是一个对象，网页里引用的一张图片也是对象，互联网中凡是能被访问的东西都可以是对象。

网页本身是一个对象，网页内部又嵌了一些对象——只不过嵌的不是对象本身，而是对象的链接。任何一个对象，都可以用统一资源定位符（URL，Uniform Resource Locator）唯一标示；访问互联网中的任何一个对象，靠的都是 URL。

URL 的格式由几段拼成：

```text
http://user:pass@www.example.edu.cn:80/dir/file.html
  │     │    │           │                │  │
 协议   用户名 口令      主机域名          端口号  目录路径与文件名
```

读法：协议段说明用什么协议去访问——HTTP、FTP、Email 都可以；用户名与口令说明以什么身份去访问这个对象；@后面是对象所在主机的域名；再往后是端口号；最后是对象在主机上的目录路径和文件名。

两个日常疑问在这里一并解答。访问科大、天猫的主页时并没有让你输用户名口令，为什么？因为它们支持匿名访问：匿名时用户名、口令省略不填就行。输入网址时也没写冒号 80，为什么也能访问？因为 HTTP 默认使用 80 号端口，这是它的知名端口；FTP 默认是 21 号端口。不特别指明时，就用协议对应的默认端口号——除非特殊情况，端口号不需要提供。

### 网页的构成与渲染

一个网页通常有一个 base HTML 文件。这个文件按 HTML 格式书写：这里多大的字、居不居中、写什么内容、哪个位置插入一个对象。但它本身不包含图片，只给出图片对象的链接。所以浏览器的渲染分两步走：先把 base HTML 拿到，在客户区把框架画出来——图片的位置暂时用一个空框占着；接着解释这个文件，发现这是图片的链接，就按链接里的 URL 再去访问相应的服务器，把图片对象拉回来，画到空框的位置上。

访问科大的主页就是这么个过程：先拿到 base HTML，把网页框架画出来；网页里包括一堆链接，再把相应的对象逐个拉回来画上去——这里是孺子牛，那里是东校门，当然实际比这更复杂。对象都到位了，一个完整的网页才算画出来。

这样，互联网中的对象通过链接指向对象，被指的对象又指向别的对象，还可能反指回来——整个 Web 就像一个蜘蛛网，把全世界的知识和信息用这种网状结构完成了指向。目前互联网中网页的数量达到数千亿的量级，而且还在不断增长。在这么复杂的网状信息空间里找一个东西很难，怎么办？搜索引擎：给网页建索引，你提供关键字，它把匹配的内容给你，热度高、关联度高的排在前面；点匹配结果里的对象，就能把对象拿到。

### World Wide Web：杀手级应用与 World Wide Wait

这种应用叫 World Wide Web——全世界范围内的网页。Web 是互联网的杀手级应用：正是它吸引了大量用户，企业用户和个人用户把信息挂到网上；任何一个客户端只要装一个浏览器软件，就可以访问世界上任何一个网站。

上个世纪 90 年代，马云去美国访问，一看到这个应用就说："我的天啊，这简直是打开了一扇窗，把整个信息社会又拉入到一个新的时代。"后来他就凭这份眼光创建了自己的公司——看得比较早。

不过当年的 Web 用起来非常慢：终端用户和主干网的链路带宽都不大，终端通常还是拨号上网。马云给企业做网上黄页——把以前电话号码簿里的信息放到网上——画一个页面，过了好几分钟，网页才一行一行地显示出来。所以 World Wide Web 当年有个俗称，叫 World Wide Wait——全世界范围的等待。老网民都熟悉那个画面：网页半天不出来，屏幕上一个咖啡杯的图标在那儿转，提示你下载时间可能有点长，请你去倒杯咖啡，喝完回来再看看网页下载完了没有。当然，现在的技术基础设施已经很强悍，不会出现这种情况了。

### HTTP：超文本传输协议

支持 Web 应用的协议是 HTTP，超文本传输协议（HyperText Transfer Protocol）。超文本前面介绍过：它不是线性文本，指的是文本之间相互的、任意的指向关系。Web 对象不正是这样吗？一个对象带很多链接，链接指向其他对象，其他对象又按需要指向更多对象，还可能反指回来，共同构成一个巨大的网状信息空间——这就是"超文本"这个名字的来历。

HTTP 按客户/服务器方式工作：客户端是浏览器，可以是 IE、谷歌、360，任何一个浏览器，PC 端和移动终端都是这一套；服务器端可以是 Apache，可以是 Linux 上运行的其他服务器，也可以是微软 Windows 上的 IIS。为什么不同厂商生产的浏览器和服务器之间能够相互通信、彼此互操作？因为它们都遵守 HTTP 这个协议。

版本上，HTTP 1.0 在 RFC 1945 中描述，HTTP 1.1 在 RFC 2068 中描述。1.0 和 1.1 有重大差别——差别在哪，后面讲持久与非持久连接时就清楚了。

### 守候套接字与连接套接字

HTTP 跑在 TCP 之上，不是 UDP。服务器运转在某个固定 IP 的 80 号端口上，守候来自客户端的 TCP 连接建立请求：你来请求，我同意，连接就建起来了。具体怎么"同意"，是 TCP 的事，讲到传输层再说。

连接建立之后，服务器进程里就有一个套接字（Socket）指向"和这个浏览器的会话关系"。这时又来了另一个连接建立请求，我也同意——于是再弹出一个 Socket，指向和那个浏览器的会话关系。一个 Web 服务器通常支持大量并发连接，而最初那个守候在 80 端口的原始 Socket 仍然守在那里，继续等待任何一个新客户端的连接请求。

```text
Web 服务器（固定 IP，80 号端口）
 │
 ├─ waiting socket（守候套接字）：守候在 80 端口，等待新浏览器的连接建立请求
 ├─ connection socket 1（连接套接字）：代表与浏览器 A 之间的一套会话关系
 └─ connection socket 2：代表与浏览器 B 之间的一套会话关系

连接建立请求每到来一个，就弹出一个新的 connection socket 指向那次会话；
waiting socket 继续守候，永不下岗。
```

这几个套接字都指向服务器本地的 IP 和 80 号端口，区别只在角色：守候的那个是特殊的 waiting socket，其余每个 connection socket 代表一个固定的会话关系。

再往底层看一眼：浏览器与服务器建立连接，是应用进程借助套接字接口（Socket API）通知下层 TCP"我要跟对方建立连接"，TCP 实体向对方 TCP 实体发连接请求段，对方同意后确认回来——上下两层协议动作联动，一次交互完成连接建立。落到函数调用上：先建立一个 socket，有时还要 bind（捆绑），再发出 connect 调用——实际是好几个函数，客户端最起码两个，服务器端好几个。听着很烦，但这一整套细节讲到 TCP 时再展开。

### 一次完整的网页访问

把流程串起来。服务器在 80 端口守候；客户端发起 TCP 连接建立；连接建好，浏览器在这个连接上发送 HTTP 请求；服务器收到请求，按协议解析，发现你要请求什么对象，就从本地文件系统的相应目录里把对象取出来，封装成 HTTP 响应报文回转给客户端；客户端拿到对象——如果是 HTML 文件，就解释着把它画出来，网页的框架就看到了。拿到被请求的对象、解释完毕，这条连接就可以关掉了。

画 base HTML 的过程中，浏览器发现这里有一个对象的链接、那里有一个图片对象的链接。每个链接就是一个 URL，URL 里带着主机域名——浏览器就跟相应的主机建立 TCP 连接（可能是刚才那台服务器，也可能是别的服务器），把对象按 HTTP 请求的方式拉回来，画到客户区里。一个网页需要的对象都到齐、都画出来，网页就呈现在你眼前；再点网页里的任何一个链接，相应的对象又能这样过来。

顺带说一句：把对象解释出来、画在客户区，是客户端自己的事，跟协议无关。也正因为 HTTP 的"请求—响应"本身就是搬对象的通道，有些文件传输不跑在 FTP 上、跑在 HTTP 上，照样能传文件。

### 无状态协议

HTTP 从一开始的设计就是无状态（stateless）的：服务器不维护客户端的状态。我在这里守着，你来建立连接，同意；你来请求，我把对象取出来、封装成响应报文给你——拉倒，给你断绝关系。你后面还要不要跟我通信？你之前跟我通信过吗？不知道，也不需要知道。这样的服务器称为无状态的服务器，它像一个没有记忆的人——没有记忆，也就没有痛苦：来了什么请求，就给什么响应，完事。

> **定义**：无状态（stateless）——服务器不维护客户端的任何状态信息，每个请求独立处理，处理完就忘。

无状态的好处很实在。一是简单：不必维护一堆状态和历史信息。倘若服务器要维护状态，客户端建立连接之后死机了，服务器还得有一定的机制促使双方重新回到同步状态——很烦。二是同样的网络与服务器软硬件资源，无状态服务器支持的用户数量更多：不用为每个客户端在内存里保存状态，同样的服务器能支撑的用户数可能远超有状态的服务器。

当然，无状态协议也有它的问题——这个问题后面再讲。

### 非持久连接：每个对象两个 RTT

HTTP 1.0 与 1.1 最主要的差别就在持久与否上。HTTP 1.0 是非持久的：取完一个对象，连接就拆掉；取下一个对象，重新建连接。

先定义往返时间（RTT，Round-Trip Time）：一个小分组从客户端到服务器、再从服务器回到客户端所花的时间。这里传输时间忽略不计——小分组字节数很少，相对于带宽，传输它所需的时间可以忽略；但传播时间省不了：过去、再回来，还要算上远端的封装与解封装、中间每个路由器上的转发处理，这些时间都算在内。

非持久连接下取一个对象的全过程是：

```text
客户端                                     服务器
  │ ──────── TCP 连接建立请求 ────────────► │
  │ ◄─────── TCP 连接建立确认 ───────────── │  ← RTT ①：连接建立
  │ ──────── HTTP 请求报文 ──────────────► │
  │ ◄─────── HTTP 响应报文（含对象）───────  │  ← RTT ② + 对象传输时间
  │
  └─ 连接关闭；取下一个对象时，以上四步从头再来
```

所以非持久连接下，一个对象最少需要两个 RTT，外加对象的传输时间：一个 RTT 用于建立连接，另一个 RTT 是请求发过去、响应回来的一次往返，还得加上对象本身的传输时间——传一张大图片，这段时间就不能忽略了。

> **提示**：两个 RTT 里不含对象的传输时间。请求报文字节数少，传输时间可以忽略；对象（比如一张大图片）不行，它的传输时间要单独加上。

之后连接拆除、拆除确认，那是后话。举个具体的例子：客户端请求一个 base HTML 文件——建立连接、连接确认，请求文件、文件回来，连接关闭。浏览器解释这个文件，发现里面包含了十个图片对象的 URL。每个 URL 都带着主机域名，客户端因此知道要跟哪些主机建立连接。于是分别对这十个对象重复那五步：建立连接请求、连接确认、请求对象、对象回来、关闭连接。十个对象都拿到手，在客户机上调用相应的解释器画出来——你打开的 USTC 主页就完整地呈现在眼前了。

非持久的缺点也就看出来了：每个对象都要两个 RTT，很长。

### 持久连接与流水线方式

HTTP 1.1 的默认方式是持久连接：连接请求、连接确认（这仍是下层 TCP 层面的交互，花一个 RTT），之后在这条连接上请求对象、对象回来——连接不关。还有其他对象要取？还在同一条连接上继续发请求，对象继续回来。建连接的那一个 RTT 只付一次，此后每个对象就是一次"请求—响应"的往返加传输时间，不必再为每个对象重新建立、拆除连接。

持久连接又分两种：非流水线（non-pipelined）与流水线（pipelined）。

非流水线方式：请求一个对象，等它回来，再请求下一个，再等它回来——任何时刻只有一个正在处理的请求，前一个对象不回来，绝不发下一个请求。好处只是连接不拆，省掉了反复建连的开销。

流水线方式更进一步。请求 base HTML 之后拿到了十个对象的 URL，假设十个对象都在同一台主机上：第一个对象的请求发出去，对象还没回来，就把第二个、第三个……一直到第十个的请求全部接着发出去，对象依次回来。客户端等待的时间就这样省了下来。这就是流水线方式（pipelining），是持久连接下的默认请求方式；这种情况下，每个对象只花费一个 RTT 是有可能的。

打个比方，就像生产汽车的厂子。非流水线是一个时刻只生产一辆车：前面造底盘，后面装轱辘，轱辘装完套发动机，发动机装完套车壳，车下线，再开始下一辆。流水线则是前一个工序在装轱辘，后一个工序已经开工套发动机，再后面的工序同时在装壳子——当然汽车工业远没这么简单，我们这是在"鄙视"汽车工业了——同一时刻在制的汽车有很多辆，很多道流程同时在跑。把"上一件活没干完就发下一件"用在 HTTP 请求上，就是流水线。

### 请求报文的格式

HTTP 的请求报文与响应报文是两种主要报文，两者都是 ASCII 码可读的（readable）：所有内容都用 ASCII 编码，直接打印出来就能读。这是早期协议留下的历史痕迹，为的是方便程序员调试——抓包抓下来，报文头部直接可读；要是二进制，000011 代表什么还得去查机器码，多烦。

请求报文的结构：一个请求行（也叫命令行），之后是若干首部行，一个回车之后是可能存在的实体部分。GET 请求通常没有实体，为空。

请求行分三段，用空格隔开：命令字、URL、协议版本号。命令字在第一个空格之前：`GET` 是客户端从服务器取东西，头部和 body 都要；`POST` 是往上载；`HEAD` 是只要头——HTML 文件有头有 body，只把头拿过来。要头干嘛？这不是常规用户的用法：头部通常包含网页的描述信息，一些搜索引擎把头拿过来建索引用。请求行里的 URL 只写哪一个目录的哪一个文件；主机名呢？不需要——TCP 连接已经建到那台主机上了，主机名可以省略，它由首部行交代。

首部行的形式是"首部名: 首部值"。几个常见的：

- `Host`：要访问的主机的域名；
- `User-Agent`：用户代理，即发出请求的浏览器程序和它的版本号；
- `Connection: close`：HTTP 1.1 默认持久、传完对象不管连接，但客户端可以用这个首部要求服务器"管一管"——这个对象传完，连接就关掉，服务器不再维护这条连接。

请求报文的通用格式如下，每一行之间都用回车符分隔——回车符是一个特殊的 ASCII 字符：

```text
请求行：  method 空格 URL 空格 HTTP版本 回车
首部行：  首部名: 首部值 回车
          ……（若干首部行）
空行：    单独一个回车
实体：    提交的内容（仅 POST 等才有；GET 通常没有）
```

特别是 `POST`：要向服务器上载东西，这些东西就放在实体部分，跟在空行后面。

### 向服务器提交内容的两种方式

请求报文一般是向服务器要东西，但客户端有时也要向服务器提交内容，有两种方式。

第一种用 `POST`：命令行之后、若干首部行之后，一个回车，后面放的就是提交的表单内容——表单的信息在实体部分。

第二种用 `GET` 也能提交：在 GET 后面的 URL 里以参数的形式带上信息。形式是正常的 URL 后面接一个问号，之后是"参数名=参数值"；有多个参数时，参数之间用与号（`&`）连起来：`正常URL?参数名1=参数值1&参数名2=参数值2`。例如向服务器提交两个参数，参数名是 `wd` 和 `cl`，各自的值跟在等号后面。这样，`GET` 命令配合这种特殊形式的 URL，客户端同样能把信息提交给服务器。

### 方法与版本：GET、POST、HEAD、PUT、DELETE

HTTP 1.0 常用的命令有三个，HTTP 1.1 又加了两个，都是 HTTP 协议支持的方法：

| 方法 | 引入版本 | 方向 | 用途 |
| :--- | :--- | :--- | :--- |
| `GET` | 1.0 | 取 | 请求对象，头部和 body 都要 |
| `POST` | 1.0 | 存 | 向服务器提交内容，表单放在实体部分 |
| `HEAD` | 1.0 | 取 | 只要 HTML 对象的头部，不要 body |
| `PUT` | 1.1 | 存 | 向服务器提交（上传）对象 |
| `DELETE` | 1.1 | 删 | 删除服务器上的对象 |

`HEAD` 的典型用户是搜索引擎。像 Google、百度的索引服务器运行网络爬虫，向大量服务器发出请求，把内容拿过来——但很多时候 body 不要，只要头部：头部里包含网页的元信息，爬虫根据这些元信息建立索引；等用户检索时，搜索引擎就知道这些关键字出现在哪些网页里。这种请求的数量非常大。`HEAD` 的另一个用途是维护。

`PUT` 和 `DELETE` 用于向服务器提交对象、删除对象，通常是网络管理员在维护网页时使用的命令——上传网页、删除网页、更新网页，当然要借助一些网站发布工具来做这些事情。

### 响应报文的格式

响应报文的结构与请求报文对应：一个状态行，之后是若干首部行，一个回车之后是实体部分——被请求的对象本身就在这里。

状态行包含三段：协议和版本号、状态码、状态码的解释短语。比如是 1.0 还是 1.1 版本；`200` 表示 OK；`404` 表示找不到了——404 大家都经历过，都见过。

首部行里几个有讲究的字段：

- `Server`：告诉客户端我是一台什么样的服务器，例如 Apache 1.3.0、运行在 Unix 上；
- `Last-Modified`：你请求我这个对象，我把对象给你，同时告诉你这个对象上次被修改的日期。这基本上相当于一个版本号——它有什么用，后面再说；
- `Content-Length`：内容的长度，例如 `6821`——意思是首部行之后的回车往后，还要读多少个字节才是这份响应报文的内容。这个字段很重要。

为什么重要？HTTP 跑在 TCP 之上，而 TCP 向应用层提供的是字节流（byte stream）服务：它不维护应用报文交下来的边界。应用进程分两次各放下 15K 字节，TCP 可能合成一次 30K 字节交上去——哪里是一个报文的头、哪里是它的结束，TCP 一概不管。所以凡基于 TCP 的应用层协议，都得自己维护报文与报文的界线。HTTP 的办法就是 `Content-Length`：客户端按协议解释响应的头部，解释到这一行时就知道，首部行之后的回车往后有多少个字节属于这份响应报文的内容——报文的边界就这样划出来了。

```text
状态行：  HTTP版本 空格 状态码 空格 状态码短语 回车
首部行：  首部名: 首部值 回车
          ……（若干首部行）
空行：    单独一个回车
实体：    被请求的对象（长度由 Content-Length 标明）
```

### 报文边界问题

先补一个讲响应报文时留下的收尾问题：服务器把响应报文交给 TCP 发出去，接收方怎么知道整个 response 报文到哪里结束？靠报文头部。头部告诉对方的应用实体：后面还要读取多少字节的应用层报文——对方由此才知道这个响应报文的完整边界在哪里。

为什么要这样做？因为 TCP 向上层提供的服务不保留边界。假设发送方应用进程先后往下交了两个 15K 的报文：如果 TCP 保留边界，接收方会分两次收到，每次 15K；但 TCP 不是这样——它可能把两个 15K 合成一个 30K，一次交给应用进程。

```text
发送方应用进程交给 TCP：  [ 报文A: 15K ]   [ 报文B: 15K ]
接收方 TCP 交给应用进程： [         30K（A 和 B 连成一块）        ]
```

两个 15K 下去，上来的是一个 30K：边界信息在 TCP 里丢了，应用进程得自己区分哪一段是前面的 message、哪一段是后面的 message。

> **易错点**：不要指望 TCP 替你划分报文。"一个报文从哪开始、到哪结束"是应用层自己的责任——所有架在 TCP 之上的应用进程，都要自己维护报文与报文之间的 boundary（边界），HTTP 靠头部里声明的长度字段（`Content-Length`）来做到这一点。

### 状态码与 Telnet 手工实验

再看状态行：状态码，加上状态码的解释。注意看，这些是不是全是 ASCII 码字符？早期的应用层协议都有这个特点——命令行、状态码都用 ASCII 码表示。而且不只给你一个代码，还附上代码的解释：200 后面跟着 OK。

为什么这样设计？为的是网络管理员维护网络时排故障方便。把报文直接打印出来、抓包直接打出来，一眼就能看懂、就能排障：200 是什么意思？不用查手册，解释就写在报文里。如果搞成二进制，那就烦了——什么 B、B1、01，B1 代表什么意思，你得翻手册对表。ASCII 方案下，报文打出来就能读。

| 状态码 | 短语 | 服务器想对你说的话 |
|:------:|:-----|:-------------------|
| 200 | OK | 请求成功，对象就在响应的实体里 |
| 301 | Moved Permanently | 对象被永久移走了，原先的位置上它不在了 |
| 400 | Bad Request | 你这个请求我理解不了：报文或首部坏了，服务器解析不了 |
| 404 | Not Found | 最熟悉的一个：请求的对象不存在 |
| 505 | HTTP Version Not Supported | 你报的协议版本我不支持 |

505 的场景：好比客户端报出一个"HTTP 8.0"——还没那么先进——服务器只能回答：这版本我不支持。

我们鼓励大家亲手做一个实验。Linux 上、Unix 上，包括 Windows 上都有命令行界面：用 Telnet 远程登录到 Web 服务器的 80 号端口——那里守候着的正是一个 Web 服务器。连上之后，你就可以模拟一个浏览器，手工敲出一连串请求（不是机器制造的，是手工的），看服务器会给你什么样的响应。

```bash
telnet <Web 服务器域名或 IP> 80
```

服务器回来的是一整段文本：状态行、首部行，然后是实体。实体部分是 HTML 文本，你看得懂；如果请求的是一个图片，回来的就是这张图片的全部内容——那一大片你当然看不懂。但通过这个办法，你可以站在一个纯粹 Web 客户端的位置，亲手看清服务器到底回了什么。

### 无状态协议及其局限

接下来是 HTTP 协议一个非常重要的性质：无状态（stateless）。什么叫无状态？就是服务器不维护客户端的状态。我是一个服务器，在那儿等着；来了请求，你请求什么对象，我解析报文、把对象取出来、封装成 HTTP response 发给你，完事。你下次什么时候再请求这个对象，我如法炮制。你以前有没有请求过，我不管；你以后要不要请求，我更管不了。

> **定义**：无状态——服务器不维护客户端状态，不在请求之间保存任何关于客户端的记忆。

无状态有什么好处？简单。服务器没有任何记忆负担，同样的一台服务器资源，可以支撑的客户端数量更多。服务器活得很轻省、很高兴，但它也因此不那么智能。

越来越多的应用采用无状态的 HTTP 协议可以工作得很好——访问网页这肯定没问题。可如果网页背后是一个电子商务网站、一个文件共享的网站呢？服务器端要不要维护客户端状态？当然要：你是谁？你的用户名是什么？你的购物车里有哪些东西？你以前买了什么——从而我可以向你推荐。这些需不需要服务器维护客户端状态？当然需要。原来的无状态协议在这类应用面前就不适用了。怎么改造它？Cookie，小甜饼。

### Cookie 的四个组成部分

Cookie 机制包括四个部分：

- 响应报文中的 `Set-Cookie` 首部行（服务器发牌）；
- 请求报文中的 `Cookie` 首部行（客户端亮牌）；
- 服务器端数据库里维护的 Cookie 记录；
- 客户端文件系统里保存的 Cookie 文件。

至于客户端具体怎么维护它的 Cookie 文件——放在哪个目录、什么格式——那是客户端自己的事，不属于协议的具体内容；协议只规范报文层面约定的那部分东西。

工作流程是这样：

```text
第一次访问（以亚马逊为例）：

  浏览器 --HTTP 请求报文（不带 Cookie，头一回来）--> 服务器
       <--HTTP 响应报文（首部行 Set-Cookie: 1687）------
  服务器生成 Cookie ID 1687，存入自己的数据库
  浏览器把 1687 存进本地文件系统的 Cookie 文件

此后每次访问（一周后、一个月后、一年后……）：

  浏览器 --HTTP 请求报文（首部行带上 Cookie: 1687）--> 服务器
       <--HTTP 响应报文（按 1687 关联出的用户状态定制）---
  服务器拿 1687 到数据库里一查：这位来过、买过什么、
  购物车里有什么、登录没有，全都能关联出来
```

读图：Cookie 的全部奥妙就是"第一次发牌、以后每次亮牌"——服务器靠发出去的那张牌，把同一个人在不同时刻的访问关联起来。

对照这张图走一遍 Susan 的例子。Susan 第一次访问亚马逊，她的 HTTP 请求报文里没有任何 Cookie 值。服务器一看，来了个新面孔，给她生成一个 Cookie ID——1687，并在响应报文里用 `Set-Cookie: 1687` 这个首部行告诉客户端；同时服务器自己也把这个 Cookie 存进数据库。客户端把 1687 拿下来存好。在 Windows 操作系统的相应目录下，你总能找到好多这样的 Cookie 文件——哪个网站对应什么 Cookie 值，都维护在那里。建议大家打开看一看，它是个文本文件，打开尝一尝。

下次再访问亚马逊，浏览器就可以把这个 Cookie 以首部行的形式带上来；在这次访问后面的一系列动作里，也都可以带着它。服务器拿它和自己数据库里存的记录一关联：这家伙以前来过，三个月之前来过，他以前买了什么——从而可以向他推荐。还要注意一点：第一次的响应之后就不再需要 `Set-Cookie` 了——已经给过你了。一周后、一个月后、一年后再访问，只要那个 Cookie 文件仍然存在，浏览器依然把 1687 以首部行的形式发给服务器，服务器照样能通过这个值关联出他的访问行为。

这样一来，就把原来无状态的 HTTP 协议改造成了一个有状态的协议，从而支撑起更多需要服务器维护客户端状态的应用。

### Cookie 的用途与隐私问题

Cookie 能带来什么特性？

- **验证**：登录一次就够了。ID 值关联的用户已经登录过，不必每次都重新登录；
- **购物车**：这个 ID 对应的用户买了哪些东西，服务器端靠 Cookie 值就能维护；
- **推荐**：根据他以前买过什么，向他推荐；
- **其他用户状态**：你当前处在网站的哪个目录；比如在一个发帖的社区里你正在编辑帖子，服务器要不要维护"你正在编辑"这个状态？两边得同步。很多应用都需要服务器维护客户端状态。

当然，Cookie 和隐私有点相悖：带来便利的同时会带来隐私问题。你访问很多网站，它们都给你发 Cookie，你带着 Cookie 再次访问。单次的行为通常不暴露太多敏感信息，但很长很长时间积累下来，这些 Cookie 值串在一起，是不是就包含了你大量的信息？你是谁，你的习惯、爱好，甚至你的隐私都可能被暴露。服务器端掌握的东西，可能比你的父母了解你还清楚。在互联网当中，隐私是一块很大的问题。

插一句话。手机放在边上，你运行了某些 App（不点名了），隔一段时间之后就给你猛推相关的产品。那天我和我儿子在车上随便说了几句空调的事，好，各种应用就开始向我推空调的各种广告。这是隐私的一个方面；Cookie 给服务器端的线索类似——把你很多网站上的访问行为关联在一起，能挖掘出你更多的东西，甚至你自己都不清楚、但你内心需要的一些东西或产品，他都向你推荐，让你达到有点害怕的程度。所以我们一直在讲：技术是双刃剑。这个话题不做过多的探讨。

### Web 缓存与代理服务器

下面看另一个主题：Web 缓存（web cache）。访问一个 Web 对象有两种方式。第一种，直接访问原始服务器（origin server），把对象从源头取回来。第二种，给浏览器设置一个 Web 代理（proxy）：可以在浏览器里显式设置代理，也可以在网络网段上隐式设置——像科大实际上是隐式设置，所有访问外面 Web 服务器的流量都要首先经过科大的 Web 缓存。

代理的工作方式：如果它自己没有这个对象，就向 origin server 发请求，拿到对象后一方面交给你，一方面缓存到代理服务器自己的文件系统当中。下次再有其他用户访问这个对象，还需不需要向原始服务器请求？不需要——直接从本地文件系统里读出来，封装成 response 报文返回给你。这时我们说，这个对象在 proxy 当中被命中（hit）了——缓存的东西用上了。

这样的好处，大家想一想。是不是快？不需要跑到原始服务器那里去取，对客户端而言响应时间（response time）小了。还有什么好处？站在服务器端看：原来单位时间内有 100 个请求打到原始服务器，现在只有 80 个、20 个——服务器端的负载更轻了。再看网络这一层：网上跑的流量少了，网络的负担也减轻了。所以通常在一次访问行为当中，你要从多个角度来看，不能仅仅从一个角度。我们学自动化出身的人常讲，要多视角：客户端的角度、服务器的角度、网络的角度，好处才看得全。

缓存能有效还有一层原因，就是互联网访问的齐普夫分布（Zipf distribution）——大家听过这个词没有？就是二八分布：80% 的用户访问了 20% 的内容。热点嘛。人和人之间还有趋同性，大家都在看什么？比如青岛的九例检测阳性，比如特朗普神秘地"又又又好了"——大部分人访问的内容一样，这些热点内容在 proxy 里就能被命中。于是一个很小的缓存，就能命中很多用户的访问请求，从而减少服务器的负担、减少网络的负载。前提条件是什么？大家的访问具有一定的趋同性。如果大家的访问没有趋同性，再小的缓存实际起的作用也不大。当然，人和人之间也有差异性，总有一些人访问稀奇古怪的内容，那部分请求缓存就帮不上忙了。

所以缓存这个角色的定位是：对客户端而言，它是服务器；对 origin server 而言，它是客户端。中国科大校园网里就经常安放这样的 Web 缓存，把很多用户的访问请求在本地命中，减少用户的响应时间，减轻 Web 服务器的载荷。

### 缓存收益算例

下面用一个算例，把缓存的作用实打实地算一遍。

场景设定：每个对象是 100 Kbit；局域网内部的一些用户每秒向服务器发出 15 个请求，每个请求会带回来 100 Kbit 的流量，所以单位时间内从外面过来的流量就是 $15 \times 100\ \text{Kbit} = 1.5\ \text{Mbps}$。网络结构是常见的一幕：局域网内部带宽 1 Gbps，经接入路由器通过接入链路连到 ISP，再进入互联网；原始服务器挂在大网那一头。接入链路的带宽是 1.544 Mbps——当时常用的一种接入带宽，1.544 Mbps、2.048 Mbps 这类规格。从路由器到原始服务器再折返回来的往返时间（round-trip time，RTT），假设是 2 秒。局域网内部带宽充裕，一个往返假设是 10 毫秒。

```text
  [Web 客户端们]
        |
     局域网（1 Gbps，往返约 10 ms）
        |
  [接入路由器]
        |
        |  接入链路 1.544 Mbps —— 瓶颈所在
        v
  [ISP 路由器]
        |
      互联网
        |（到原始服务器的往返 RTT 约 2 s）
        v
  [原始服务器 origin server]
```

读图：一次请求的往返要经过三段——局域网内一段、接入链路一段、大网一段。

问：这时候平均而言，每个对象的响应时间是多少？什么叫响应时间？用户的请求发出去开始计时，请求的对象回来了，计时结束。我们不关心对象本身的传输时间，因为在这里其他时间是占主导的。

#### 接入链路的流量强度瓶颈

三段往返，先看两头的。局域网内部是 1 Gbps 的带宽，1.5 Mbps 的流量对它完全没有压力，这个往返假设 10 毫秒。大网那一头，从接入路由器到原始服务器再回来的往返是 2 秒。那中间接入链路这一段的往返是多少？传输时间很少（流量相对带宽很小），关键看排队。

接入链路上的流量强度（traffic intensity）：

$$\rho = \frac{1.5\ \text{Mbps}}{1.544\ \text{Mbps}} \approx 0.97$$

链路带宽 1.544 Mbps，流量 1.5 Mbps——什么情况？流量强度约 0.97，已经非常接近 1 了。接近 1 会怎么样？排队延时非常大，排队延时成了主导（dominant），其他延时都可以忽略不计。这个结论前面分析过：分组的排队延时随流量强度趋近 1 而急剧增大，趋近于无穷大。具体的公式大致是这样：

$$T_{\text{q}} \approx \frac{T_{\text{tx}}}{1-\rho}$$

$T_{\text{tx}}$ 是一个分组的传输时间，$\rho$ 是流量强度。$\rho$ 等于 0.97，分母就只剩百分之几，$T_{\text{q}}$ 非常非常大。大到什么程度？举个量级：假设是两分钟。于是整个的用户访问时间是：10 毫秒（局域网）＋ 两分钟（接入链路排队）＋ 2 秒（大网往返）——两分钟把其他全部淹没。按一下回车、点一个链接，两分钟之后对象才来。这对用户来说不可忍受。

> **提示**：流量强度 $\rho$ 就是到达流量与链路带宽之比；$\rho$ 越接近 1，排队延时越急剧膨胀。这一条是后面两个方案全部计算的钥匙。

这也解释了早年为什么网络访问那么慢：WWW 那时不叫 World Wide Web，被叫成 World Wide Wait——全世界的等待。点个链接之后，先给你一个假的东西：一个动画，一个还冒着香气的咖啡杯，栩栩如生地呈现在你面前，暗示你去喝杯水吧，回来看看运气好不好、对象回来了没有。

#### 接入带宽扩容一百倍

问题的症结很清楚：接入链路带宽 1.544 Mbps，流量 1.5 Mbps，流量强度太大。怎么改善？

有个办法——土豪解决方案。瓶颈就像瓶口，要让水倒得更快，就把瓶颈扩大：把 1.544 Mbps 升级到 154 Mbps，整整 100 倍。这样流量强度立刻陡降到 1% 左右，排队延时还"没起飞"，只占毫秒级。整个响应时间变成：10 毫秒（局域网）＋ 1 毫秒左右（接入链路）＋ 2 秒（大网）≈ 2 秒。问题解决了吗？解决了。点个链接，两秒不到对象就回来，用户很高兴。

代价是什么？钱。带宽升级 100 倍，而且每个月都要花钱。ISP 高兴死了——这肯定是 ISP 给你出的馊主意：你不是堵吗？升级你的带宽啊。原来一块钱一个月，现在收你 90 块——都升级 100 倍了，给你打个九折嘛。运营商很高兴，用户很高兴，那谁不高兴？网络的拥有者不高兴：一次性投入倒也罢了，慢慢钱就赚回来了；每个月都掏 90 倍、100 倍的钱，这个事情就大了。于是把网络主管叫过来一顿狂扁，甩出去两块钱：拿这个解决，一次性搞定，不允许每个月再花钱。

#### 安装本地缓存

网络主管怎么解决？在局域网内部安放一个缓存节点（proxy）。所有对象的访问都要经过它：对象在 proxy 里有，直接返回；没有，就由 proxy 去访问原始服务器，取回来交给用户，同时缓存一份。

```text
  [Web 客户端们]
        |  所有请求都先经过 proxy
        v
  [Web 缓存 proxy] --命中（40%）--> 直接返回，T1 ≈ 10 ms
        |
        | 未命中（60%）：proxy 继续向下请求，延时记为 T2
        v
  [接入路由器]
        |
        |  接入链路 1.544 Mbps
        v
  [ISP 路由器] ---- 互联网（RTT 约 2 s）---- [原始服务器]
```

读图：40% 的请求在缓存处就地解决，其余 60% 才真正穿过那条瓶颈接入链路。

由于用户的趋同性——80% 的用户访问 20% 的内容——大部分请求在本地就被命中、本地满足，只有少部分比较分散的、奇葩的请求，才需要通过 proxy 出外网去取。于是访问分成两种情况：

- **本地命中**（设概率为 0.4）：proxy 直接返回，延时记为 $T_1$。本地是 1 Gbps 的局域网，$T_1$ 就是那 10 毫秒；
- **未命中**（概率为 0.6）：先过一遍本地的 10 毫秒，再由 proxy 经接入链路去外网取，大网的 2 秒少不了，中间接入链路的排队也少不了，延时记为 $T_2$。

平均访问延时就是两者的加权平均：

$$\bar{T} = 0.4\,T_1 + 0.6\,T_2$$

$T_1$ 已经知道是 10 毫秒。$T_2$ 里的三段：局域网的 10 毫秒没有悬念，大网的 2 秒没有悬念，关键是中间接入链路的排队延时，它取决于流量强度。现在过接入链路的流量不再是 15 个请求/秒的全部——四成在本地消化了，只有六成需要出外网：

$$\rho = \frac{15 \times 100\ \text{Kbit} \times 0.6}{1.544\ \text{Mbps}} = \frac{0.9\ \text{Mbps}}{1.544\ \text{Mbps}} \approx 0.58$$

0.58，就像传染病一样还没到陡增的程度——一开始零零散散，不加控制最后才陡增，0.58 远没到那个点。代入公式一算，这一段的排队延时大概是毫秒级到十毫秒级，根本不主导。$T_2$ 里占主导的是大网那 2 秒。

把数代进去：$0.4 \times 10\ \text{ms}$ 只有 4 毫秒；$0.6 \times (2\ \text{s} + \text{毫秒级}) \approx 1.2\ \text{s}$。整个平均时延大约 1.2 秒。

> **结论**：一次性投入安一个缓存，不升级接入带宽，每个月不用额外花钱；平均响应时间约 1.2 秒，比扩容方案的两秒还快——前提是用户访问要有趋同性。

这个问题解决得漂亮不漂亮？漂亮。老板很高兴，一高兴把一个月的接入带宽费作为奖金发给网络管理员：拿去花吧，以后不用再花钱了。用户笑了，老板笑了，网络管理员笑了，谁没笑？ISP 没笑——它的阴谋诡计没得逞。这就是本地缓存的好处：安放一个缓冲服务器，也就是 proxy 代理服务器，按一定比例在本地满足用户的访问要求，满足不了的再通过 proxy 去访问外面的原始服务器。既能够减少投入，也能够减少用户的响应时间，提高访问性能。

### 条件获取（Conditional GET）

采用 proxy 缓存内容来满足用户的访问请求，有一个风险大家想：你把这个对象缓存到本地了，但服务器那端的对象变了，有没有这种可能性？有。那缓存的可能就是一份过期的旧版本，怎么办？

HTTP 协议为此做了一个升级，叫条件式获取（conditional GET）。办法是：在请求报文里加上一个头部，名字叫 `If-Modified-Since`——如果这个对象在那个时刻之后得到了修改，服务器，你把那个东西重新传一遍给我；如果那之后你都没变，我原来的缓存是有用的，你就不用把对象给我了，回我一个响应、告诉我没有改变就完了。这样，服务器就不需要再通过响应报文把整个对象封装传回来，只要传个头部就可以了。

回顾一下前面学响应报文时见过的那个首部字段——对象在什么时间得到了修改（`Last-Modified`）。因此 proxy 的做法是：第一次访问某个对象时，把对象存下来，同时把这个对象上次修改的时间也存下来。用户再请求这个对象时，proxy 明明知道本地有，但不确定服务器那端有没有改过，于是向服务器发出一个条件式获取的请求——在请求的首部行里加上 `If-Modified-Since`。

- 服务器一查：那之后没改过——回一个不含对象实体的响应，只传头部，不传对象；
- 服务器一查：改过了——把改完之后的新对象传回来，proxy 拿它满足用户，同时把新版本的对象和新的修改时间存下来。

这样，代理服务器缓存的对象与服务器上对象之间的版本一致性问题就得以解决——把这个 bug 用一个补丁打掉了。

## FTP 与电子邮件协议
> 对应块：BLK15 | 覆盖分集：P15-P16 | 块标题（分集名）：《2.3 FTP》

讲完 Web 服务器和 HTTP，我们学的其实还只是最基本的 HTTP 协议。在它之上还有大量扩展出来的 Web 技术——那属于 Web 开发的天地，不是网络基础课要铺开的内容，有兴趣可以自己去看。接下来补一个教材正文里没有、但非常经典的应用：FTP（File Transfer Protocol，文件传输协议）。正因为经典，它值得专门讲一讲：文件传输协议到底起什么作用、基本工作原理是什么、协议的主要内容有哪些。而这一讲的下半场，会顺势进入另一个每天都离不开的经典应用——电子邮件（Email）。

### FTP 的由来与用途

先问一个现实问题：现在分享文件，我们常用什么方法？迅雷、百度云盘，或者直接在群里发文件——都对。但早期，大家分享文件通常采用 FTP 的方式。科大和很多机构都维护着一个 FTP 服务器：大家用 FTP 客户端把内容上载上去，再到 BBS 上公布自己有效分享了哪些东西，其他用户再用 FTP 客户端去访问这些内容。这样，一个 FTP 服务器里就维护起大量大家需要共享的文件。如今新的文件分发手段层出不穷，FTP 服务器用得不如以前多，但早期它就是文件共享的主流方式。

FTP 的协议规范是 RFC 959。它是典型的客户端-服务器结构：客户端是发起传输的一方，服务器是远程的主机。FTP 客户端这一套，除了客户端软件本身，还包括用户接口（界面）和本地文件系统；FTP 服务器则守候在 TCP 的 21 号端口——一个知名端口（famous port），本地有自己的硬盘。FTP 协议要干的事情非常直接：客户端可以把本地文件系统里的文件上载（upload）到服务器的相关目录下，也可以把服务器相关目录下的文件下载（download）到本地文件系统——通过网络，一系列文件就这样共享起来。

### 控制连接与数据连接

先把流程走一遍。服务器先运行起来，守候在 TCP 的 21 号端口，等待连接建立请求：你不是 FTP 客户端吗？来跟我 21 号端口建立连接。我同意，TCP 连接就建立了——这条连接叫控制连接。在控制连接上，首先完成用户认证：客户端报上"我是谁"，也就是用户名和口令；服务器端查一查这个用户是不是我开好的、口令对不对。

> **注意**：像 FTP 这种古老的应用，用户名和口令全部是明文传输的。拿抓包工具去抓，你会收获满满——当然，大家不是黑客，看懂就好。

认证完成之后，客户端可以在控制连接上向服务器发出一连串命令：`LIST` 列出当前目录的内容，进入某些目录，上载一些文件，下载一些文件（命令并不是字面上的 download、upload，具体写法后面讲）。下载是怎么下的？我是客户端，向服务器发出命令："把当前目录下的某个文件下载给我。"服务器收到之后，做了一个看起来违反常理的动作——但这就是协议规定的：**服务器主动**向客户端发起建立一条新的 TCP 连接（服务器侧使用 20 号端口），这条连接叫数据连接，文件就在这条连接上传给你。平时的印象都是客户端去连服务器，这里反过来了，服务器主动连客户端——服务器和客户端的身份确实容易让人迷惑，但记住：发起数据连接的一方是服务器。原来的控制连接还在，命令继续在上面发。

```text
FTP 客户端  <====== 控制连接（TCP）======>  FTP 服务器
              客户端主动发起；服务器守候 21 号端口
              上面跑命令与应答：认证、LIST、RETR、STOR……

FTP 客户端  <------ 数据连接（TCP）------>  FTP 服务器
              服务器主动发起（违反常理，但协议就是这样规定的）；
              服务器侧使用 20 号端口；上面只传文件（上载/下载）
```

读图：FTP 的命令和数据分走两条 TCP 连接——控制连接上传用户名口令、列表等命令的发出与应答，数据连接专门承载文件本身的上载与下载。

于是控制信息和数据彻底分家：控制命令的发送和接收不在数据连接上进行，而是单独在控制连接上进行，这叫带外发送控制信息。

> **定义**：带内（in-band）是传数据，带外（out-of-band）是传指令、传控制信息。FTP 的控制信息走带外；对照 HTTP，请求、响应连同响应里的内容都在同一条连接上传输，控制信息和数据不分家，那是带内。

还有一个层次上的说明：两个应用进程通过 TCP 建立连接，具体是怎么建立的？在这一章的最后（讲到 TCP 的时候）会给一个完整的描述。现在掌握到什么程度？两个应用按次序、按规则调用了一系列 socket API，连接就建立起来了。至于调用的次序是什么、TCP 实体里要维护哪些状态——那是 TCP 的事。我们不是一层一层自顶向下地讲吗？对应用来说，传输层提供 socket API 这些原语，按次序按规则调用它，连接就建立起来了。当然，为了前后连贯，上层动作和下层动作如何配合，讲到的时候也会顺带解释。

### FTP 的有状态特性

前面介绍 HTTP 时问过：HTTP 初始设计是有状态还是无状态？无状态，后来靠 Cookie 这个补丁才变成有状态。FTP 正相反：它天然就是一个有状态协议。服务器要不要维护客户端的状态？当然要——你谁呀（登录的是哪个用户）？你当前在什么目录？这些都得记着。有状态，是 FTP 区别于 HTTP 的一个本质特征。

### 控制连接上的命令与应答

控制连接上发出的指令，全部以 ASCII 文本的方式发送。常用的几条：

- `USER username`：提供用户名；
- `PASS password`：提供口令；
- `LIST`：客户端请服务器列出当前目录，看看里面有哪些文件、哪些目录；
- `RETR file`：从服务器下载文件，想拿哪个文件，以参数的形式提供给服务器；
- `STOR file`：上载文件。

> **易错点**：上载和下载一律以客户端为参照。客户端向服务器发东西叫上载（upload），服务器向客户端发东西叫下载（download）。不能换到服务器视角去说——"我是服务器，你才是网络那一侧"，服务器的上传就是客户端的下载，一说就混。这是默认的约定。

应答同样以 ASCII 形式返回，而且状态码和状态码的解释成对出现，非常好用：`331 User name OK, password required`——用户名可以，请继续给口令；`125 Data connection already open`——你不是要我传文件给你吗，数据连接我已经打开了。有码有解释，抓包一看就懂，所以说 FTP 协议比较简单。

> **结论**：FTP 与 HTTP 的差别主要有两点——其一，FTP 是有状态的（HTTP 无状态，靠 Cookie 补救）；其二，FTP 的控制命令与数据传输分别走两条 TCP 连接，控制信息带外传输（HTTP 是带内）。

### 电子邮件系统的三个组成部分

接下来看另一种常见应用：Email，电子邮件。我们是不是每天都通过电子邮件收发信息？可能有些同学不是，用 QQ 多一点——但对很多人来说，电子邮件仍然是非常重大的通信方式，每天都在收或发。

电子邮件这个应用包括几个部分：用户代理（User Agent，UA）、邮件服务器和协议。协议又分发送协议和拉取协议两类：发送协议是 SMTP（Simple Mail Transfer Protocol，简单邮件传输协议）；拉取协议有几种——POP3、IMAP，HTTP 也可以。顺带回答一个可能冒出来的疑问：HTTP 能传文件吗？能。它不但传请求报文、响应报文，也可以作为文件传输的载体——报文就是一个封装嘛，一样的。

用户代理是什么？就是撰写、发送、接收邮件的客户端软件：Foxmail、Outlook 这些。你们经常用什么？Outlook？都不用电子邮件吗——代沟差得有点多。玩笑归玩笑，概念要立住：我们通过用户代理软件来访问电子邮件这个应用，这个软件就是我们使用这个应用的代理，它代理你去执行协议动作——你不是直接跟服务器打交道的。这个概念放到别的应用一样成立：Web 应用的用户代理是浏览器；FTP 应用的用户代理就是 FTP 客户端软件。

### 邮件服务器与邮件的三跳旅程

邮件服务器守候在 25 号端口，一直运转着，它有两个作用。第一是发：用户代理配置好邮件服务器的 IP 地址和端口号，把要发的邮件交给它；邮件先进入服务器的发送队列排着队，排到队头再发走——邮件服务器从队列里挨个取出邮件，向相应的目标邮件服务器送出。第二是收：收到别的邮件服务器送来的邮件后，把它放进相应用户的邮箱（mailbox）里。

一封邮件从 Alice 到 Bob 要走三跳。Alice 通过她的用户代理把邮件发给她自己的邮件服务器，放进发送队列；邮件服务器再把邮件发给 Bob 的邮件服务器（比如谷歌的）；谷歌邮件服务器把邮件放进 Bob 的 mailbox。Bob 隔一段时间打开他的用户代理，按拉取协议从他自己的邮箱里把别人发给他的邮件拉过来。早上把 Foxmail、Outlook 运行起来看看有没有新邮件，干的就是这件事：你的 Foxmail 跟邮件服务器的 110 号端口建立连接，查一下你的邮箱里有没有人给你发的邮件，有的话从邮箱里拉下来，呈现在客户端里，你挨个儿看。

```text
第 1 跳（推，SMTP）           : Alice 的用户代理 ──► Alice 的邮件服务器（邮件进发送队列 Q）
第 2 跳（推，SMTP）           : Alice 的邮件服务器 ──► Bob 的邮件服务器（邮件放进 Bob 的 mailbox）
第 3 跳（拉，POP3/IMAP/HTTP） : Bob 的用户代理  ──► Bob 的邮件服务器（从 mailbox 把邮件拉回本地呈现）
```

读图：邮件从一端的用户代理出发，途经两台邮件服务器，到达另一端的用户代理；发送队列 Q 与 mailbox 分别是发、收两侧的停靠点。

> **结论**：前两跳推，最后一跳拉。用户代理发给邮件服务器、邮件服务器发给目标邮件服务器，用的都是 SMTP；最后一跳是拉取，POP3 这类邮件存取协议负责把邮件从邮箱里取回来。

那为什么邮件要先放进队列排着，而不是来了就直接发？两个原因。其一，队列的本职工作就是干这个的：进来的速度和出去的能力有差距，用队列平滑一下——来得多的先排队，再挨个发。邮件服务器维护的用户很多，一封封立刻发，来不及。其二，服务器往往刻意不"来一封发一封"，而是设置成每隔几分钟（五分钟、十分钟）攒到一起再发，别让服务器那么劳累；在两个发送间隔之间，它可以缓一缓。再说，本来就没什么邮件可发，让服务器每时每刻处于待命状态，是不是也挺耗能？如果告诉你每天都要考试，那就疯掉了——总得有个间隔期。

### SMTP 的工作机制

SMTP 服务器守候在 25 号端口，客户端主动跟它建立连接。那谁是客户端？谁发起推送谁就是客户端：你是科大的邮箱用户，要向谷歌的邮箱用户发邮件，就是科大的邮件服务器主动跟谷歌的邮件服务器建立连接——此时科大是客户端，谷歌是服务器。角色随发起方而定，别被名字绕晕。

连接建立之后，邮件从我传输给你，SMTP 就规范了这些动作。整个传输分三个阶段：握手（handshaking）、传报文（一条一条传邮件，message）、关闭。

命令和响应报文都是 ASCII 码形式；响应报文不仅有状态码，还带状态码的解释。ASCII 形式有什么好处？前面说过：可以直接打出来，抓包之后直接可读。

> **注意**：SMTP 要求报文内容必须是 7 位 ASCII 码。什么叫 7 位 ASCII？一个字节 8 个比特，最高位是 0，剩下 7 位编码出来的都是可打印字符——打印出来是可以读的。命令、响应，连同邮件内容本身，全部必须落在这个范围之内；超出范围的内容，原始的 SMTP 不允许在上面传。这是它保留下来的古老痕迹。超出范围的怎么办？先记下这个问题，讲完原始协议我们看补丁。

### 一次 SMTP 会话的完整过程

把一场会话从头到尾走一遍（S 为服务器，C 为客户端）：

```text
C ──TCP 连接建立──► S
S: 220 + 服务器名称               (问候: 邮件服务器就绪, 顺便告诉你我是谁)
C: HELO                           (客户端报到: 我是谁)
S: 250                            (挺好, 很高兴遇到你)
C: MAIL FROM: 发送方              (发送端是我这个服务器里的某个用户)
S: 250 Sender OK                  (发送方 OK)
C: RCPT TO: 接收方                (接收方是你上面的 Bob 用户)
S: 250 OK                         (接收方也 OK)
C: DATA                           (我真发了)
S: 354                            (你发吧, 以单独一行的点字符作为整个邮件的结束)
C: <邮件正文, 逐行发完>           (最后一行只有一个点字符)
S: 250 Message accepted for delivery    (已收下)
C: QUIT                           (没有别的邮件了, 整个结束, 连接断掉)
```

读图：一场 SMTP 会话就是"命令—应答"的往复，220、250、354 这些状态码都带着解释；邮件正文之后以一个点字符收尾，服务器确认收下。

注意一个安全事实：这一切全是明文，而且命令全是客户端自己写的。所以伪造一个用户发邮件是不是很容易？太容易了。`MAIL FROM` 写谁就是谁——Alice 的情敌伪造一条"分手"消息发给 Bob，这就麻烦了。

另外，客户端发完一封邮件后，如果还有邮件要发，不是断开连接再重新建立连接发下一封，而是在同一条连接上接着发很多很多封：Alice1 发给 Bob1，Alice2 发给 Bob2……直到全部发完，再发出 `QUIT` 结束、断开连接。机会难得啊——我是科大的邮件服务器，你是谷歌的邮件服务器，连接建起来之后不关，我这边一堆 Alice 要向你那边一堆 Bob 发邮件，都发完再关。

> **结论**：SMTP 是持久连接——一条 TCP 连接上传送多封邮件，发完再关。这一点跟 HTTP 不一样。

> **提示**：鼓励大家 Telnet 到科大邮件服务器的 25 号端口，模拟一个客户端向它发出指令，看看效果——顺便看看网络管理员会不会跳起来。

### SMTP 与 HTTP 的对比

两者放在一起比一比。方向上，HTTP 是拉的：客户端发起请求，把内容拉过来；SMTP 是推的：发送方把邮件主动推过去。表示上，两者是共同的：命令、响应状态码和状态码解释都以 ASCII 形式描述。报文封装上有个重要差别：HTTP 的每一个响应报文至多封装一个对象——你传一个 HTML 文件，不会把 HTML 里链接引用的那些对象一并封装进同一个响应报文；而邮件的 message 可以封装多个对象——我传一封邮件给你，里面放了十张图、一个可执行文件、一段录音，这些附件整个算一封邮件发给你。这一点是 SMTP 与 FTP、HTTP 都不一样的地方。

| 对比项 | HTTP | SMTP |
| :--- | :--- | :--- |
| 传输方向 | 拉：客户端请求，把内容拉过来 | 推：发送方主动把邮件推给接收方 |
| 命令与应答的表示 | ASCII 文本（共同点） | ASCII 文本（共同点） |
| 报文封装 | 一个响应报文至多一个对象 | 一个 message 可封装多个对象（图、可执行文件、录音等附件） |

### 邮件报文的格式

前面会话里传的那个 message 其实并不规范——邮件本身是有格式的：头部，一个空行，之后是正文（body）。头部由一项项"名称: 值"组成，最常见的头部名称有这么几个：`To:` 给谁，收件人是谁；`From:` 谁发的；`Subject:` 邮件的标题（title）；`Cc:` 抄送（Carbon Copy）——发邮件给你，同时抄送给另外一个人。抄送经常是什么用处？相关的人不是接收人，但要让他知道这回事。比如领导派了个任务，相关材料我做完之后交给你，同时 Cc 给领导——这实际上告诉领导的是：我做完了，交给他了，你知道了就行。还有一种是暗抄送 `Bcc:`——暗抄比较"黑"：我发送给你，实际上同时抄送给了他，而你还不知道，这叫暗自抄送。

而报文的整个内容，又回到了那条限制：只能在 ASCII 码字符描述的范围之内。

### MIME 与 Base64 编码

这个限制马上带来一个问题。传英文还可以；传中文怎么样？不行了——一个中文字符占两个字节，这两个字节很可能都不在 ASCII 范围之内。传可执行文件当附件呢？也不行。那怎么办？打补丁。互联网络就是这么一个补丁一个补丁过来的。

补丁叫 MIME（Multipurpose Internet Mail Extensions，多媒体邮件扩展）。它定义了一种新的格式：这个格式当中可以包括对象，对象里面还可以再包括对象——一层套一层；里面这些对象采用的编码叫 Base64 编码。

Base64 的思路打个比方：你要传输一个字符，8 个比特一个字节，但它不在 ASCII 码范围之内；又传了另外一些字节，同样不在范围之内。那我们能不能按一定的约定定一个映射关系，把若干个"不在 ASCII 范围之内的字节"转换成"稍微长一点的、但落在 ASCII 范围之内的字符"？定一个映射关系，当然可以。这样的编码方式有很多，最常见的就是 Base64。转换之后，整封邮件都落回 ASCII 范围，SMTP 就能传了；到了对方，再用 Base64 把它转换回来，再用 MIME 解释出这封邮件包含了哪些对象。

> **结论**：有了 MIME 加 Base64，原始的 SMTP 协议经过扩展，就可以传输中文、可执行文件、图片和更大的对象——尽管这些对象的每一个字节都不在 ASCII 范围之内。细节还有很多，但根子就一条：原始 SMTP 只能传 ASCII 范围内的报文内容，MIME 负责把超范围的东西"包"进 ASCII。

### 邮件拉取协议：POP3、IMAP 与 HTTP

三跳旅程的最后一跳是"拉"，拉取（邮件存取）协议有三种。第一种是 POP3（Post Office Protocol version 3），邮局访问协议：用户代理通过 POP3 从自己的邮箱把邮件拉下来。第二种是 IMAP（Internet Message Access Protocol），作用类似，但比 POP3 具备更多特性——远程目录的维护：以 Bob 为例，他的邮箱放在服务器上，POP3 只能让他区分收件箱、发件箱这样简单的划分；IMAP 则允许他在远程的邮箱当中创建目录，把邮件从一个目录搬到另外一个目录，搬来搬去。所以 IMAP 提供的特性更复杂。第三种是 HTTP：这个协议不但用于 Web 访问、用于文件的上传下载（用迅雷客户端上传下载文件时，经常用的就是 HTTP 协议），也可以用来收发邮件——网页邮箱走的就是它。

POP3 的客户端跟邮件服务器之间的会话，分为几个阶段：用户确认阶段（认证阶段）、事务处理阶段，最后是关闭连接。认证阶段，客户端向服务器提供用户名和密码——你可以看到，POP3 的用户名和密码全部是明文，存在安全隐患。这不奇怪：互联网一开始用的时候是一个分组交换的实验网，上面的用户都是科研人员、技术人员，对安全性的考虑并没有那么充分；后来打了一个个补丁，安全性才逐步提升。比如收发邮件可以跑在 TCP 之上，也可以跑在 SSL（Secure Sockets Layer，安全套接字层）之上——传输层提供加密认证方面的措施，应用层即使是明文的用户名和口令，到了传输层也被加密保护，安全性得以增加。

事务处理阶段，客户端可以向服务器发命令。`list`：列出我邮箱当中的邮件——1 号邮件 498 字节，2 号邮件 912 字节……最后以一个只含点字符的行结束。`retr 1`（retrieve）：从我的邮箱当中把 1 号邮件拉下来——服务器随后把 1 号邮件的内容发送过来。`dele 3`：把第 3 封邮件（拉下来之后）在邮箱当中删掉。

由此产生两种使用模式，可以在邮件客户端里设置：

| 模式 | 做法 | 好处 | 代价 |
| :--- | :--- | :--- | :--- |
| 下载并删除 | 邮件拉到本地之后，从服务器邮箱中删除 | 服务器邮箱不会满、不会被占满 | 邮件只存在于拉走它的那台设备上：平板拉下来之后，PC 上就看不到了 |
| 下载并保留 | 邮件拉到本地，但在服务器邮箱中保留 | 从其他客户端、其他终端主机再运行邮件存取协议，依然可以看到这封邮件 | 邮箱迟早会被占满 |

> **结论**：POP3 的会话是无状态的。为什么？因为它不支持远程目录维护，不允许客户端在服务器的邮箱当中建目录、在目录之间跳来跳去；它维护的状态只到"谁上来了、你在哪个邮箱（账户）"这一层，具体邮箱之内的状态是不维护的。IMAP 则由于提供远程目录、文件夹的维护，是一个有状态的协议——服务器端必须维护客户端的状态。

> **承前启后**：上一节讲完「FTP 与电子邮件协议」，下一节接着讲「域名解析系统 DNS：从命名到解析」。

## 域名解析系统 DNS：从命名到解析
> 对应块：BLK16 | 覆盖分集：P17上 | 块标题（分集名）：《2.5 DNS》

应用层是整个协议栈里应用最多、协议也最多的一层——毕竟 everything over IP，什么应用都跑在 IP 之上。我们不可能把所有应用层协议都过一遍，只挑典型的、用得多的、基础性的来讲。这一部分要讲三类非常有特点的应用：**域名解析、P2P、CDN**；讲完它们，再看怎么用传输层提供的 socket API 把各种应用真正实现出来。

先说域名解析系统（Domain Name System，DNS）。它有一个很特殊的地方：它不是一个直接给人用的应用，而是**给其他应用用的应用**。对比一下就明白了：SMTP 是给人发邮件用的；DNS 最终当然也是服务于人，但它直接服务的对象是其他应用——其他应用在为用户提供服务之前，得先来找它。哪些应用会用？Web 最典型：用户输入的是 URL（统一资源定位符），URL 里带着域名，浏览器就得调用 DNS 的解析器，完成从域名到 IP 地址的转换。FTP 也一样：先发出请求，通过域名解析系统拿到域名对应的 IP 地址，然后才开始工作。

顺着这条线，后面还会讲另外两类应用。P2P 的特点是**形式不一样**：前面介绍的所有应用都是客户/服务器（C/S）模式，P2P 是对等（peer-to-peer）模式。CDN 是一种完成内容访问加速的基础设施——内容分发系统（CDN），用来加速 Web 访问、加速内容访问；它的特殊之处在于，它是一种基础设施，却是在端系统、边缘系统的应用层里运转的，层次更靠下。这几类讲完之后是 TCP、UDP 的 socket 编程——这一章跟其他章节不太一样的地方：本层协议的实现要靠下层提供的服务，传输层向应用层提供的就是 socket API 这套接口服务。我们可以建立 socket、使用 socket（用它收和发）、关闭 socket，而且采用 UDP 的 socket 和采用 TCP 的 socket 用法不一样。学会了这套原语，才能亲手实现应用层协议，做出丰富多彩的网络应用。

### 域名解析系统的必要性

DNS 为什么是一个基础性的系统？从网络层看起。网络层的设备用 IP 地址来标识主机、标识路由器，给每台设备分配不同的 IP 地址；发送分组时指明目的 IP 地址，分组就能送到那台具备这个地址的主机。所以 IP 地址的作用有两个：一是**标识**，二是**寻址**。网络里的设备都是按照 IP 地址来工作的。

问题在于，IP 地址是数字。IPv4 是四个字节、32 比特的数；IPv6 更是 128 比特、16 个字节，很难记。IPv4 地址虽然可以用点分十进制简化成 `202.38.64.1` 这种形式，但仍然是数字——人还是倾向于用**有意义的字符串**来标识一台设备、一台主机、一台服务器。

比如邮件服务器的域名 `ustc.edu.cn`：USTC 有意义（科大），edu 有意义（教育网），cn 表示中国互联网——很好记。再比如科大的 Web 服务器 `www.ustc.edu.cn`：www 是 World Wide Web，ustc 是科大——非常容易理解；让你记 `202.38.64.8`，就很烦。

所以合理的分工是：应用的用户在使用应用时提供**域名**（URL 里就包含主机的域名），然后由一套系统自动完成域名到 IP 地址的转换——域名解析系统就这么应运而生。

> **定义**：DNS 最核心的服务，是完成域名到 IP 地址的自动转换。应用进程拿到 IP 地址，就知道该跟哪台主机、哪台 Web 服务器建立连接了。

还有一个细节要咬清楚：应用进程通过传输层接口往下交的是 **IP 地址，而不是域名**。域名是应用层的事；IP 地址才是下层可以理解的地址。除了这个最主要的服务，DNS 还提供其他服务，马上展开。

### 命名、解析与维护：三个子问题

知道了 DNS 要做什么，问题就变成：它的工作原理是什么？怎么实现域名到 IP 地址的转换？这件事可以拆成三个子问题。

**第一个，怎么给设备命名（naming）？** 你说命名很简单，取个名字就完事了：这个叫 Alice，那个叫 Bob，那个叫王健、王刚。但如果用一个平面来命名一台设备，非常容易重名——大路化的名字，全球不知道有多少人叫 Alice。重名问题必须解决，办法是**分层化的命名**。注意：把问题提出来的同时，解决的主要思路也就给出来了——层次化。

**第二个，命名搞定之后，名字到 IP 地址的转换关系怎么做？** 用一台设备集中维护所有域名（当然是层次化的域名）到 IP 地址的对应关系，有人来查、我来回复，行不行？理论上可以，现实上不行。全球有几十亿台设备，上百亿台，到了物联网（IoT）时代可能上千亿台；用一台机器包揽，无论用户端的访问延迟、服务器的负担，还是流量、占用的带宽，都非常可观。集中不可行怎么办？**分布式地做**：一人维护一块、一段。但具体哪些节点维护哪些范围的域名映射，得规划好——这本身就是一个问题。所以 DNS 的骨架是**分层的命名、分布式的维护和解析**。

**第三个，维护问题。** 系统定下来之后不可能一成不变：有时要增加域名、增加域、增加域当中的子域；有时要删除——公司倒闭了，域名没人交钱了，就不再维护。怎么增加、删除这些主机域名和域，是第三个问题。

三个问题都解决了，DNS 向其他应用提供"名字到 IP 地址对应关系的转换"，这件事就解决了。

### 从 ARPANET 到 DNS

这套设计不是凭空来的，看一眼历史就知道它为什么长成这样。互联网是从一个分组交换试验网演化而来的——美国国防部资助的 ARPANET。ARPANET 一开始同样存在命名和解析的问题，它的解法非常朴素：**一台设备维护所有名字到 IP 地址的对应关系，主机的命名全部在一个平面**。

这在当时完全可行，因为节点少：1969 年只有 4 个节点，1972 年也只有 15 个节点。命名在一个平面，重名的可能性不大——总共这么几个节点，哪来那么多 Alice？真重名了，就再给你起一个 Alice 2；可要是名字多到出现 Alice 8898，那还不如直接用数字，这就很烦了。解析也一样：几百个节点，一台设备查表直接应答就完事了。

但随着节点越来越多，这套方案撑不住了：平面命名容易重名；解析的代价越来越大；最要命的是，时时刻刻都要增加名字、增加节点，集中式的名字服务器始终处在增删维护的状态里，而且容易搞错。ARPANET 的方案搞不定了，怎么办？

互联网的开放精神在这里发挥了作用：大家对互联网的进步献言献策，方式就是向 IETF（互联网工程任务组）提交 RFC——请求评述文档。DNS 就这样运行起来了。它的主要思想就两条：**分层的命名**；**分布式的数据库**——不是一台，而是很多台维护域名到 IP 地址对应关系的数据库，而且这些数据库之间还维护着一个树状的关系。

具体到协议层面，DNS 运行在 **UDP 的 53 号端口**——一个知名端口。为什么是 UDP？因为 DNS 事务性很强，正适合 UDP：不用握手，直接问一句"名字服务器，把域名某某某的 IP 地址告诉我"，就完事了；前面先握手再查询，反而很烦。

> **结论**：DNS 是互联网的核心功能，但它不在网络核心实现，而是在边缘系统实现——跑在主机系统的应用层。互联网最核心的功能，很多都是由网络边缘、端系统之上的应用进程实现的；互联网的复杂性体现在边缘、体现在传输层及以上，而不是在核心。

### DNS 的主要服务

最核心的功能已经反复出现：主机域名到 IP 地址的转换。除此之外，DNS 还提供三类服务。

#### 主机别名与规范名字

规范名字是为了**便于管理**而存在的。拿 `www.ibm.com` 来说：只有一台服务器跑 IBM 的 Web 服务可行吗？不可行，它背后是一堆服务器——美国的东海岸、西海岸，可能还有亚太地区，都部署着它的 Web 服务器。这一堆服务器对外的名字统一叫 `www.ibm.com`，这是**别名（alias）**，为了便于用户访问；而每一台真正提供服务的设备，为了便于管理，都有一个规范的名字：西海岸的某台刀片服务器，它的规范名字会带上刀片编号、所在机柜、所在机房，最后才是 `ibm.com`——这就是**规范名字（canonical name）**。

| 名字类型 | 例子 | 为谁服务 |
| :--- | :--- | :--- |
| 别名（alias） | `www.ibm.com` | 对外统一呈现，便于用户访问 |
| 规范名字（canonical name） | 刀片编号·机柜·机房 + `ibm.com` | 对内逐一标识，便于管理 |

别名和规范名字并存，自然产生转换需求。于是 DNS 提供这样一项服务：收到对别名的查询，先返回规范名字，再返回这个规范名字对应的 IP 地址。

#### 邮件服务器的别名

邮件服务有同样的需求。邮件地址 `qzhen@ustc.edu.cn` 里呈现的邮件服务器名字是 `ustc.edu.cn`——注意，这其实是科大**域的域名**，拿它对外呈现是为了便于使用；而为了便于管理，科大的邮件服务器还有正规的管理名，形如 mailserver 某某号，而且可能不止一个——学生和教师用的可能就不是同一台服务器。于是必然存在这样一条链：由邮件服务器的**别名**得到邮件服务器的**正规名字**，再向域名解析系统提交一个查询、由正规名字拿到邮件服务器的 IP 地址，然后邮件服务才开始工作。

#### 负载均衡

还是 IBM 的例子：`www.ibm.com` 背后，东海岸、西海岸很多机柜，每个机柜上很多刀片服务器，都可以向用户提供服务。DNS 收到一个针对这个域名的解析查询时，可以根据各种各样的因素——比如对请求方 IP 地址的判断——决定由东海岸哪个机柜的哪台刀片服务你，还是由西海岸的哪台刀片服务你。来了一个查询，我告诉你：由这个数据中心机房、这个机柜的这台刀片向你服务；又来一个，我根据因素判断，由另一个机柜的另一台刀片去服务；再来，就轮到西海岸某机柜的某台刀片。大家都访问同一个 `www.ibm.com`，DNS 却能把具体的规范名字服务器分配出去——这就相当于在 IBM 这一堆提供 Web 服务的刀片服务器之间，起到了**负载均衡（load balance）**的作用。

这些是 DNS 的主要功能，但最核心的始终是那一条：域名到 IP。

### 域名的层次化命名

#### 名字空间的逐层划分

为了防止重名，命名必须层次化——平面命名容易重名。整个互联网的名字空间，最初缩成一个点，宇宙还没有爆炸；之后"爆炸"式地分解出几百个**顶级域（Top-Level Domain）**。顶级域分两类：**通用的（generic）**和**国家的（country）**。通用顶级域如 `.com`、`.edu`：所有国际化的公司都在 `.com` 之下，比如 `microsoft.com`、`ibm.com`；国家顶级域则每个国家一个，跟国家一一对应，比如美国的 `us`，还有荷兰、日本各自的国家域。注意，`.com` 是通用顶级域，不是哪个国家的顶级域。

> **提示**：区分两类顶级域——`.com`、`.edu` 这类**通用顶级域**按用途划分；`us`、`cn` 这类**国家顶级域**按国家分配，每个国家一个。

每个顶级域下面再分为若干个**二级域**，也可以不分、让公司或机构直接挂在顶级域上。比如 `cn` 下面分出 `com.cn`、`gov.cn`（政府）、`edu.cn`（中国的教育网）。二级域下面再分**三级域**，同样也可以不分。一层层分下去，整个互联网的名字空间就被分解成一棵倒着生长的树。

这里面能看到美国互联网"老大"心态的一点痕迹：美国的一些大学直接挂在 `edu` 下面（比如 MIT 的 `mit.edu`），美国的政府机构直接挂在 `gov` 下面，美国的商业公司直接挂在 `.com` 下面；其他国家在名字解析系统的分配上，看起来反倒都是"我的子集"、归我管。

划分到某个具体的子域——可能是二级域，也可能是三级域——就可以对每台机器命名了。比如科大的 Web 服务器：`www` 是科大的一个 Web 服务器，`ustc` 在科大域名之下，`ustc` 在 `edu` 之下，`edu` 在 `cn` 之下——一层层挂上去，这台设备的名字就定下来了。这样命名，重名的可能性非常小。

#### 主机域名与域的域名

名字空间这棵倒着生长的树，最末端的树叶（leaf）代表一台主机的名字。给一台设备做域名标识：**从树叶往树根走**，每过一个层次用一个点号（.）分隔，一直到顶级域——这就构成了主机的域名。给一个域做标识则不同：**从树枝往树根走**（不是从树叶），每过一级用点号分隔——这构成了域的域名。

```text
.                                    <- 根：逻辑上一个，实际部署 13 个根服务器
├── com                              <- 通用顶级域（generic）
│   ├── microsoft.com                <- 商业公司直接挂在 com 之下
│   └── ibm.com
├── edu                              <- 通用顶级域（generic）
│   └── mit.edu                      <- 美国大学直接挂在 edu 之下
└── cn                               <- 国家顶级域（country）
    ├── com.cn                       <- 二级域：中国的商业机构
    └── edu.cn                       <- 二级域：中国的教育网
        └── ustc.edu.cn              <- 三级域：科大
            └── www.ustc.edu.cn      <- 主机：名字空间的树叶
```

读图：从最末端的树叶往树根走、每过一层用一个点号分隔，就得到主机的域名 `www.ustc.edu.cn`；从中间的某根树枝往树根走，得到域的域名——科大这个域是 `ustc.edu.cn`，中国教育网是 `edu.cn`，中国就是 `cn`。

所以域名分两种：主机的域名从树叶走上去，域的域名从树枝走上去，都能明确无误地区分出来。

> **易错点**：主机域名从树叶往上写，域的域名从树枝往上写——起点不同，写出来的串含义不同；每过一个层次，用点号间隔。

#### 个根服务器

倒着生长的树实际上给了一个查询线索：顺着树从上往下走指针。那这棵树有几个根？逻辑上是一个根。但一个根有问题：大家查找都从树根往下找，如果这个根宕机了，整个互联网的域名查询就出问题了。所以互联网名字空间的根有 **13 个**：大部分在北美，欧洲也有一些，日本也有一些，中国大陆没有。查询的时候，从这 13 个树根中的任何一个往下找都可以。

这种安排的好处是**可靠**。可以选离自己最近的一个树根开始查；这个树根死掉了，就换其他树根再往下查。而且它是树、不是图，顺着树根一层层往下问，总能找到要查的域名：树根知道顶级域在哪里，顶级域知道二级域在哪里，二级域知道三级域在哪里，三级域知道它维护的那些主机域名到 IP 地址的对应关系。

顺带一提，也有人讲：互联网名字空间的 13 个树根没有一个在中国，实际上存在一些安全隐患。这个问题的答案是"是"还是"不是"，先按下不表——为什么可以"不是"，留到后面再看。

#### 子域划分由上级域决定

顶级域分成通用（generic）和国家（country）两类，每个国家分配一个国家顶级域。而**每个域怎么划分它的子域、子域怎么命名，是由这个域的上级决定的，跟其他域没有关系**。最直观的证据是日本：日本国家顶级域底下二级域的划分方式，跟中国就不一样。

| 机构类型 | 中国 | 日本 |
| :--- | :--- | :--- |
| 商业机构 | `com`（如 `com.cn`） | `co` |
| 教育/研究机构 | `edu`（如 `edu.cn`） | `ac`（academic） |

中国用 `edu` 表示教育网、`com` 表示商业机构；日本用 `co` 表示商业机构、用 `ac`（academic）表示教育和研究机构。各划各的，互不相干。

美国的一些大学（如耶鲁、MIT、哈佛）直接挂在 `edu` 下面，而中国的大学基本都挂在 `edu.cn` 这个二级域下面，再一层层往下分。举个完整的例子：耶鲁的计算机和工程这个子域，因为计算机系比较大，又往下分出若干个四级域，比如 `AR`——某个领导课题组或研究课题组；`AR` 课题组下面不再划分，它的机器直接命名、作为树叶。那么这个课题组里一台叫 robot 的机器，域名就是 `robot.ar.cs.yale.edu`；耶鲁计算机系这个子域的域名就是 `cs.yale.edu`。

那层次化命名是不是彻底解决了重名？基本解决了，但不是绝对。真要两个人在同一个子域下面起了同一个名字——都叫王刚，或者都看中 robot 这个名字——那就只能额外区分了：王刚一、王刚二，robot1、robot2。**层次化命名大大降低了重名的概率**，命名问题解决，标识问题也解决：一个域的名字不可能和其他域或主机的域名重复。域名的管理也随之清晰：**一个域管理其下的子域**，日本按日本的方式划分管理，其他国家按各自的方式，跟中国没有关系。

#### 域与物理网络无关

有一点必须强调：**域和物理网络无关**。域是逻辑的名字空间，跟真正用 IP 地址组网互联这件事没有关系。具体体现在两点。

第一点，**同一个域的主机可以在不同的网络上**。科大域名服务器维护的是科大这个子域的域名到 IP 地址的对应关系，而处在科大子域里的这些主机，可能在科大校园内部，可能在北京，可能在苏州、深圳，甚至可能在美国——都有可能。

第二点，**同一个网络上的主机可以属于不同的域**。比如在这间教室里运行一台设备，它完全可以是欧洲某个国家的某所大学的一台服务器——没有任何问题。只要那所大学的服务器维护了这个域名，把"欧洲某大学的域名 ↔ 这台设备在科大子网范围内的 IP 地址"这个对应关系维护起来，就 OK 了。

> **结论**：域的划分是逻辑的，网络的划分是物理的。同一个域可以横跨不同的网络，同一个网络也可以分属不同的域。

### 集中式解析的三条困难

命名这个第一个问题讲完了，接下来看第二个问题：怎么完成域名到 IP 地址的转换。前面其实已经分析过，用一台名字服务器来解决所有的解析和维护问题，存在三条技术上过不去的困难。

第一条是**可靠性**：用一台机器维护所有域名，机器挂了怎么办？域名到 IP 地址的转换没法提供，所有的应用都跑不起来。第二条是**可扩展性**：所有流量都往这一台设备走，域名解析服务器周边的流量会非常大。第三条是**维护麻烦**：远程维护它的数据库非常麻烦——增加一个域、删除一个域，增加或改变一台主机的域名到 IP 地址的对应关系，都很费劲。

所以结论和三个子问题那里的判断一致：集中不可行，要**分布式**地解决名字的维护和解析——一人维护一块、一段。好在名字空间的划分已经给了现成的骨架：整个互联网的名字空间是一棵倒着生长的树，分布式的数据库就沿着这棵树铺开。具体哪些节点维护哪些范围的域名映射、查询又怎么沿着树走，就是接下来要展开的问题。

> **承前启后**：上一节讲完「域名解析系统 DNS：从命名到解析」，下一节接着讲「域名解析系统 DNS：区域、资源记录与查询解析」。

## 域名解析系统 DNS：区域、资源记录与查询解析
> 对应块：BLK17 | 覆盖分集：P17下 | 块标题（分集名）：《2.5 DNS》

整个互联网的名字空间是一棵倒着生长的树，把所有域名的对应关系塞进一台服务器，显然不科学。怎么给这棵树"做手术"？就是把它分解成一个个的区域（zone）。从划区出发，这一讲把资源记录、解析过程、报文格式、域名的增删改和系统可靠性一次讲透。

### 把名字空间划分成一个个区域

做手术的刀法：把互联网的名字空间分解成一个个的区域（zone），区域和区域相互不交织、互不重叠；在每个区域内部安排一台名字服务器，由它维护这个区域内部所有名字到 IP 地址的对应关系。

> **定义**：维护某个区域内名字到 IP 地址对应关系的名字服务器，是这个区域的权威名字服务器（authoritative name server）。"权威"的意思是：关于这个域的名字到 IP 地址的转换，它维护的信息是最权威的。

是不是权威，取决于你是不是维护了这个域权威信息的名字服务器——就像领导，在这个单位是权威，换了个地方就不是权威了。那它维护的信息为什么到了别的域也能发挥作用？这个问题先按下，讲到缓存时就明白了。

划分的粒度看需要。前面那个例子就划了两种：耶鲁的计算机系（CS）说，我是玩计算机的，我上面的计算机非常多，把我所有的域名到 IP 对应关系都放在耶鲁的一台名字服务器上维护，不科学——于是 CS 单独划成一个区域，运行自己的名字服务器；而耶鲁工学院、其他学院连同耶鲁总部，都划在同一个区域里，共用一台权威名字服务器。所以我们看到，CS 下面是一个子域，单独成区；其他学院跟校本部合用一个子域。

划区还隐含了一个关键条件：上层区域得知道下层区域怎么走。倒着生长的这棵树上，如果上面不知道下面在哪儿，解析就无法完成——领导得知道你在哪儿。所以上层要维护一个指针，一个"从上级往下级该怎么走"的指针。

```text
             (根)
               |
              edu                   <- 顶级域
               |
           yale.edu
           /        \
   耶鲁总部、工学院、   cs.yale.edu
   其他学院            （计算机系）
        |                    |
   yale.edu 区域        cs.yale.edu 区域
   一台权威名字服务器    机器多，单独划区，
   维护本区域全部        运行自己的权威
   名字到 IP 映射        名字服务器
```

一棵倒着生长的树被切成互不重叠的区域，每个区域由一台权威名字服务器负责；上层区域手里握着指向下层区域的指针。

### 顶级域与从根往下的指针链

指针链在顶级域这一层同样成立。若干顶级域分别由一些公司维护服务器，这些服务器维护顶级域的域名到 IP 地址的对应关系，还要知道下层有哪些子域：`edu` 这个顶级域的名字服务器得知道 MIT、耶鲁、哈佛等大学的名字服务器在哪里；中国的 `edu.cn` 的名字服务器得知道清华、北大、科大。一句话，上层的域得有一个指针指向下层子域的名字服务器，否则查怎么查？

有了这条链，解析的路径就定下来了：从树根往下走，一直走到权威名字服务器。权威名字服务器肯定知道自己区域内部域名到 IP 地址的对应关系——你不权威还谁权威？

顶级域分两类：generic（通用顶级域）和 countries（国家顶级域）。国家顶级域这里有个有趣的例外：太平洋上有个岛国图瓦卢（Tuvalu），它的国家顶级域是 `.tv`——这名字多酷。他们把这个域卖给了美国的一家传媒机构，卖了几千万。你想，某某电视台用 `.tv` 是不是非常酷？从此 `.tv` 就不再是一个国家的顶级域了，它被收购了。在数字世界、数字空间，这类数字编码都是可以卖钱的。

### 资源记录的字段

每个区域的权威名字服务器要维护一个数据库。数据库里主要有什么？区域内部有哪些子域的情况，区域内部域名到 IP 地址的对应关系，别名到规范名字的对应关系，邮件服务器别名到正规名字的对应关系——所有这些信息，都以资源记录（resource record，RR）的形式维护。

一条资源记录包括这几个字段：域名（name）、生存时间（TTL）、类别（class）、类型（type）和值（value）。我们学过数据库，这就相当于数据库里的字段。

class 字段标明这条记录属于哪一类网络：互联网的取值是 `IN`（Internet）。资源记录能维护非互联网的记录吗？当然可以——域名解析系统在设计时并不是一开始就只针对互联网，很多网络都存在名字到地址转换的问题，那些网络里维护的记录 class 值就不是 `IN`。但在互联网当中，所有资源记录的 class 值都是 `IN`。

TTL（time-to-live，生存时间）指的是：这条资源记录被查到之后，还能存活多长时间。它区分了两种记录：

| 对比维度 | 权威记录 | 缓冲记录 |
| :--- | :--- | :--- |
| TTL 取值 | 无限大 | 有限值，默认两天 |
| 谁维护 | 本区域的权威名字服务器，作为权威信息永久保留 | 其他名字服务器在解析过程中学到的别人的映射 |
| 到期处理 | 不会被删除 | 过了生存时间就删掉 |

TTL 字段为什么要这么设计？因为我是这个区域的权威名字服务器，我维护的权威信息当然要永久存在数据库里。而其他名字服务器在解析时拿到了这个映射——比如交大的名字服务器知道了 `www.ustc.edu.cn` 对应的 IP 地址，中间学到了，就把它缓存下来，TTL 变成有限值，默认两天，到期删除。交大再要查科大的 www 服务器，本地有缓存就直接用，不必再跑一趟科大的权威名字服务器，来得快；而科大的 www 服务器过段时间要维护、要迁移到另一个 IP 上，映射一变，旧缓存就必须删掉。

> **结论**：缓存是为了性能，删除是为了一致性。TTL 无限大的是权威记录，有限值（默认两天）的是缓冲记录，到期即删。

这也回答了开头那个问题：权威名字服务器维护的信息为什么能"到其他域也发挥作用"——因为解析过程中被别的服务器学走、缓存起来了。

再看 name 和 value 两个字段：name 放的是 `www.ustc.edu.cn` 这样的域名，value 放的是这个域名对应的 IP 地址。这个字段非常清晰。

### 资源记录的类型

域名解析系统除了域名到 IP 地址的转换，还提供哪些服务？机器的别名到正规名字的转换，邮件服务器的别名到正规名字的转换，还有上层域下面子域是怎么划分的。这些不同用途的记录，靠 type 字段的不同取值来区分：

| type | name 放什么 | value 放什么 |
| :--- | :--- | :--- |
| `A` | 域名 | 域名对应的 IP 地址 |
| `CNAME` | 别名 | 别名对应的正规名字 |
| `MX` | 邮件服务器的别名 | 邮件服务器别名对应的正规名字 |
| `NS` | 子域的名字 | 该子域的名字服务器的名字 |

`MX` 记录举个例子：科大邮件服务器的别名是 `ustc.edu.cn`，name 放这个别名，value 放这个别名对应的正规名字。

最容易迷惑的是 `NS`。科大下面又分出 CS、苏州高等研究院、各个校区等若干子域，每个子域自己独立维护它的域名到 IP 地址对应关系，有自己的名字服务器。上层域是领导，领导得知道下属在哪儿——所以 type 为 `NS` 的记录，name 放子域的名字，value 放这个子域的名字服务器的名字。

> **易错点**：`NS` 记录的 value 放的是子域名字服务器的"名字"，不是 IP 地址。对照耶鲁的例子：yale.edu 的名字服务器里要有一条 `NS` 记录，name 是 `cs.yale.edu`，value 是 `cs.yale.edu` 这个子域那台名字服务器的名字——一条从上往下走的指路记录。

而且上层要知道下层的两个信息：你叫什么，你在哪儿。第一个信息由 `NS` 记录给出——子域的名字，以及这个子域的名字服务器的名字；第二个信息还得再配一条 type 为 `A` 的记录——这个子域名字服务器的名字到它的 IP 地址。两条合起来，上层域指向下层域的指针才完整。

一条实际维护的记录长什么样？比如某台域名服务器里一条权威的 `A` 记录：class 是 `IN`，type 是 `A`，name 是某个域名，value 是它对应的 IP 地址，TTL 很长——所以它是权威记录；另一类记录 TTL 是个有限值，隔一段时间之后要删掉，那是缓冲记录。

### 本地名字服务器与主机的四项配置

解析过程的第一跳发生在主机上：应用——比如 Web 浏览器——调用本地的名字解析器（resolver），解析器通过域名解析系统的协议（DNS 协议）去问本地名字服务器（local name server），本地名字服务器把 IP 地址返回给应用。

那解析器怎么知道本地名字服务器在哪儿？配置好的。一台设备要上网，必须具备四个信息，要么手工配，要么通过 DHCP 协议自动配：

| 配置项 | 作用 |
| :--- | :--- |
| 主机的 IP 地址 | 自己在网络中的标识 |
| 子网掩码 | 标识自己所在的子网 |
| 默认网关（default gateway） | 出子网往哪儿走 |
| 本地名字服务器 | 遇到名字问题该问谁 |

网关这条多说一句。我在一个子网内部，跟我同子网的机器，分组直接传送，用不着网关，不需要牢记它；但如果要发的分组跟我不在一个子网范围之内，就得把它发给网关，由网关把这个分组"甩"给其他网络。

本地名字服务器可以指定域名解析系统中的任何一台名字服务器来担任——这是个有很多服务器构成的系统，随便指哪台都行。但一般来说，指定的是跟你在一个子网内部的那台，所以才叫 local。为什么？快。它跟你同在一个局域网，如果它已经缓存了某条映射，直接返回给你，一来一回都在局域网内部。因此这个 local 是相对于你来说的 local，它也叫默认的名字服务器。

问题来了：查询交给本地名字服务器，它有缓存就直接返回；要是它没有这条映射呢？

### 递归查询与迭代查询

没有缓存好办。本地名字服务器顺着树根往上走，先问根服务器——全球一共 13 个，指任何一个作为你的根——然后沿着指针链往下捋。比如美国某台公司的设备要解析 `www.ustc.edu.cn`，本地名字服务器没有缓存，那就问：`.cn` 知不知道 `edu.cn` 的权威名字服务器？`edu.cn` 知不知道 `ustc.edu.cn` 的权威名字服务器？顺着树根往下捋，最后捋到科大的名字服务器。关于 `www.ustc.edu.cn` 这个域名到 IP 地址的对应关系，它维护的信息是最权威的，它肯定知道。答案再返回、返回、返回。

这种方式叫递归查询（recursive query）：我不知道问根，根不知道问它，它不知道问它，返回、返回、返回——每一级在这个过程中都挂起了一个未完成的查询。

```text
主机 → 本地名字服务器 → 根 → 顶级域 → 二级域 → …… → 权威名字服务器
（每一级都挂起一个未完成的查询，答案沿原路逐级返回）
```

但递归查询很烦：所有查询最后都压到根服务器身上，根得记住多少事啊？杜甫很忙——人人都来问它，它搞不定。

于是有第二种，迭代查询（iterative query）。主机问本地，本地作为主机的代理去问根；根说，我也不知道，但告诉你一个线索，你去问我下面的顶级域；再去问顶级域，顶级域说，具体的我也不知道，你去问我下面的二级域的名字服务器；就这样作为代理一层层往下捋，最终捋到权威名字服务器，拿到名字到 IP 地址的对应关系，再反转回给查询的主机。就这么简单。

```text
主机 ──查询 www.ustc.edu.cn──> 本地名字服务器

本地名字服务器 ──问──> 根服务器：
    “www.ustc.edu.cn 的 IP 是多少？”
根服务器 ──答──> 本地名字服务器：
    “我不知道，给你一个线索：去问 .cn 顶级域服务器”

本地名字服务器 ──问──> .cn 顶级域服务器：
    “www.ustc.edu.cn 的 IP 是多少？”
.cn 顶级域服务器 ──答──> 本地名字服务器：
    “我也不知道，去问 edu.cn 的名字服务器”

本地名字服务器 ──问──> edu.cn 名字服务器：
    “www.ustc.edu.cn 的 IP 是多少？”
edu.cn 名字服务器 ──答──> 本地名字服务器：
    “去问 ustc.edu.cn 的权威名字服务器”

本地名字服务器 ──问──> 科大权威名字服务器：
    “www.ustc.edu.cn 的 IP 是多少？”
科大权威名字服务器 ──答──> 本地名字服务器：
    “这是它的 IP（权威记录）”

本地名字服务器 ──返回──> 主机：IP 地址到手
```

迭代查询中根不再替你跑腿，只发线索，负担就卸下来了。另外，凡是过手的名字服务器，只要学到了这条 mapping，就把它缓存下来：两天之内有人查，直接应答；两天之外删掉。缓存是为了性能，删除是为了一致性——这一条要反复记住。

### 查询与响应报文的格式

DNS 的查询报文和响应报文格式是一样的，靠标志位判断它到底是查询还是应答（response）。报文里有两个要点。

第一个是 Identification，查询的 ID 号。它为什么非常关键？设想本地名字服务器作为代理不断替别人问询：如果没有 ID 号，发出去一个查询就只能等结果回来才能发下一个——同时只能发起一个查询，这是非流水线的方式。有了 ID 号就不同了：发出去一个查询用不同的 ID，同时再有人问，再发不同的 ID；同时挂起的查询可以非常多；结果回来时，拿响应里的 ID 和原来的查询号一对应，就知道是谁查的，直接给谁。靠"查询的 ID 和响应的 ID 相同"这一个手段，一台名字服务器就能同时维护非常多的并行查询。

> **提示**：这是计算机网络当中经常采用的一条线索——给每个未完成的事务标一个号，让流水线（pipeline）方式具备可行性。

第二个是 Flag，一组标志位：到底采用递归查询还是迭代查询、返回的结果是希望拿到权威信息还是缓冲信息就可以——希望采用哪种方式，就在相应的标志位上打 1，很简单。报文其余字段的一些细节不一定要记，自己看书。

### 新增一个域

查询的问题解决了，域名解析还有第三个问题：如何维护，特别是新增一个域。`.com` 这个顶级域下面挂着微软、搜狐、阿里巴巴等许多公司，这时又来一个新创公司，名字叫乌托邦。`.com` 的域名服务器要在自己的数据库里插入两条资源记录：

- 第一条，type 为 `NS`：乌托邦这个子域的名字 → 这个子域名字服务器的名字——注意，名字服务器自己也有名字；
- 第二条，type 为 `A`：这个名字服务器的名字 → 它的 IP 地址。

两条插完，`.com` 关于这个子域就维护了两个信息，也就有了一个指向乌托邦的指针：知道下面有谁，它的名字服务器叫什么，那台服务器在哪儿。

之后乌托邦公司自己要弄网站、弄 FTP 服务器、弄邮件服务器，这些服务器都有域名，都要对应 IP 地址——这些信息就在乌托邦子域自己的名字服务器里维护，`.com` 不用管。维护当然不止"增"，删好不好删？一样的。修改好不好修改？一样的。增删改查，MIS 系统我们大家都学过。这样，域名解析系统的所有问题——查询、增、删、改——就都解决了。

### 域名解析系统的健壮性与安全性

域名解析系统面对着各种各样的攻击手段，具体的攻击手段和相应的防护措施这里不展开，幻灯片和教材讲得比较清楚。总的结论是：从运行的结果来看，域名解析系统非常可靠。

以攻击根服务器为例。直觉上，所有查询都顺着树根走，把根服务器弄瘫了，查询就解决不了。但实际上几乎所有本地名字服务器都缓存了下一层——顶级域甚至二级域——的域名到 IP 地址的对应关系，根搞瘫了也没关系，直接顺着二级域去查；二级域那么多了，你哪怕攻击得过来吗？

国内也有不少专家、甚至一些行外人士担心：13 个根服务器没有一个在中国，把根一掐，是不是整个系统都运行不起来？实际上不是这样。查询不一定非要从树根开始——所有域名解析系统都缓存了国内这些甚至更高级别的域名到 IP 地址的对应关系，把根掐掉，域名解析服务照常运行。

> **易错点**：有些互联网的"伪专家"说，互联网的流量都要走根。这是错的。流量不走根——学过 IP 就知道，流量是分布式的；查询有可能需要根，但几乎所有本地名字服务器都缓存了顶级域甚至二级域的映射，查询不一定从根。流量和查询是两回事。所以它的安全性，并不像一些外行担心的那样糟糕。

### CS 模式的困境与 P2P 的基本思想

前面我们介绍了一个特殊的应用——域名解析系统（DNS），接下来看另外一类应用：P2P 应用。注意，不是一个，是**一类**。

为什么需要它？CS（Client/Server，客户端/服务器）模式存在的问题我们已经很清楚：可扩展性、可靠性。随着用户数量越来越多，大家都从服务器那里获取服务——文件的下载、视频点播等等，服务器的负担很重，无法支持很多用户；而且服务器一旦瘫掉，整个业务就无法运行。

P2P（peer-to-peer，对等）换了一种思路：任何一个节点，既是客户端又是服务器。在某些会话（session）上，它向其他 peer 请求资源，在这个会话上它是客户端；在另一些会话上，它为其他 peer 提供服务，在这个会话上它就是服务器。

> **定义**：P2P 系统中，任何节点同时扮演客户端与服务器两种角色——在请求资源的会话上是客户端，在提供服务的会话上是服务器，角色按会话切换。

从这一点可以推出 P2P 最关键的性质：随着用户数量增加、peer 节点增加，**请求资源的节点在增加，同时提供服务的节点也在增加**，供需同步上涨。所以 P2P 系统很容易扩展到几百万、甚至上千万的用户级别，CS 模式很难做到这样的用户规模。

可靠性同样受益：P2P 没有集中式服务器，流量是分布式的，业务由成千上万个 peer 节点共同提供，你很难把一个 P2P 系统搞瘫掉；而 CS 模式下，只要把服务器搞瘫，整个业务就停摆。

### P2P 应用的典型形态

> **提示**：这里介绍的 P2P 应用指的是一类应用，不是某种具体的应用；同一套思想可以落到很多场景上。

**文件分发**：BT（BitTorrent），我们有时候把它戏称为"变态"。

**流媒体点播**：看看（PPLive）——据说是首次出现在国外顶级教材上的中国解决方案。运行看看的客户端，你不是从服务器那里获取视频点播的服务，而是从其他节点获取；流量是分布的，每个 peer 节点的负担也轻。因此看看不需要运行专业服务器，就能让成千上万个用户相互提供服务，把多媒体应用流畅地展开。

可以对比一下成本：如果只采用 CS 模式，我是不是要搭一个专用服务器？每个月交给 ISP 的流量费是不是很多？带宽要很大，才能支撑很多很多用户。采用 P2P 方式，很少的服务器搭起来，剩下都是大量的 peer 节点相互服务，很容易就把用户规模扩展到几百万、上千万的级别。

**互联网电话（VoIP，Voice over IP）**：Skype——打电话的语音流量走的是互联网，而不是专用的电信网。微信、QQ、钉钉提供的解决方案实际上效果更优，它们同样采用 P2P 的方式相互服务。

### 下载时间的性能分析

下面从性能上分析 P2P 的优势，性能指标就选**下载时间**。先看 CS 模式，再看 P2P 模式。约定记号：$N$ 个客户端，每个客户端的上载带宽为 $u_i$、下载带宽为 $d_i$；服务器上载带宽为 $u_s$；待分发的文件大小为 $F$ 字节。

> **提示**：上载、下载通常是站在用户（客户端）的角度而言的。服务器的下载能力无关紧要；CS 模式下客户端的上载能力同样无关紧要。

#### CS 模式：两项取最大

CS 模式下，所有客户端都从服务器下载文件，形成以服务器为中心的结构：

```text
        服务器（上载带宽 us）
                  |
                  |   一共要上载 N 份 x F
      +-----------+-----------+
      |           |           |
      v           v           v
   客户端1     客户端2     客户端N
  (u1, d1)    (u2, d2)    (uN, dN)
```

每个客户端要下载一份 $F$ 大小的文件，整个分发最少需要多少时间？我们分析它的**下限**——真实时间一定大于等于这个下限。下限是两个值的最大值。

第一项：每个客户端都要下载一个文件，你下载 2 秒、他下载 8 秒，那 8 秒就是这次分发的下限——**下载带宽最小、下载最慢的那个客户端，决定了整体时间的下限**。所有客户端中最小的下载带宽记为 $d_{min}$，对应时间 $F/d_{min}$。

第二项：所有人都从服务器那里下载，一共 $N$ 份，服务器要上载 $N \times F$ 字节，这些流量全部要通过服务器的上载带宽，对应时间 $NF/u_s$。

$$T_{CS}\ \ge\ \max\left\{\ \frac{F}{d_{min}}\ ,\ \frac{NF}{u_s}\ \right\}$$

> **结论**：CS 模式向 $N$ 个客户端分发一份 $F$ 字节的文件，下载时间下限为 $\max\{F/d_{min},\ NF/u_s\}$。

这个下限的物理意义随 $N$ 变化。$N$ 很小的时候——服务器很强、能服务 100 个人，来的只有 8 个客户端——服务器"一个打十个"没问题，上载能力是富裕的，这时候谁是瓶颈？客户端的**下载能力**是瓶颈，整体下载时间非常快。但随着用户增加到 800 个、8 万个、100 万个，大家都从服务器那里"薅羊毛"，服务器只能"撒胡椒面"——把上载能力摊薄，每个用户分到服务能力的 $1/N$。这时瓶颈换成了**服务器的上载带宽**：它必须上载 $N$ 份、100 万份。反映到曲线上：$N$ 较小时下载时间变化不大，随后基本上随 $N$ 线性增长。8 个客户端需要 1 秒，800 万个客户端就要 100 万秒——受得了吗？大家都从服务器薅羊毛、都要靠服务器撒胡椒面，整体下载时间就非常长，不可忍受。

#### P2P 模式：三项取最大

P2P 模式下，整个下载时间最起码是**三项的最大值**：

- 服务器最起码要上载**一份**，对应 $F/u_s$；
- 所有客户端都要下载一份，其中下载带宽最小的那个客户端决定了整体下载时间的最大值——最慢的那个家伙，对应 $F/d_{min}$，这两项是必须要有的；
- 一共要下载 $N$ 份，总下载量 $NF$，这些字节由**服务器的上载带宽加上每个 peer 节点的上载带宽**共同提供：每个 peer 节点在下载的同时，可以就它拥有的资源为其他 peer 节点提供上载服务。总的服务能力是 $u_s+\sum_{i=1}^{N}u_i$，对应 $NF/(u_s+\sum_{i=1}^{N}u_i)$。

$$T_{P2P}\ \ge\ \max\left\{\ \frac{F}{u_s}\ ,\ \frac{F}{d_{min}}\ ,\ \frac{NF}{u_s+\sum_{i=1}^{N}u_i}\ \right\}$$

当 $N$ 非常大时，前两项几乎是确定值，可以忽略不计。关键看第三项：$N$ 增加，下载量 $NF$ 在增加，但提供服务的节点数量也在增加——除了服务器，还有大量 peer 节点一起上载，总上载能力 $\sum_i u_i$ 随 $N$ 一起涨。所以下载时间仍在增加，但增加得**比较缓**，不再像 CS 模式那样线性。

| 对比项 | CS 模式 | P2P 模式 |
| :--- | :--- | :--- |
| 下载时间下限 | $\max\{F/d_{min},\ NF/u_s\}$ | $\max\{F/u_s,\ F/d_{min},\ NF/(u_s+\sum_i u_i)\}$ |
| 上载能力来源 | 只有服务器 | 服务器 + 所有 peer 节点 |
| $N$ 很大时的瓶颈 | 服务器上载带宽 | 无集中瓶颈 |
| 时间随 $N$ 的走势 | 后段基本线性 | 缓慢增长 |

原因归结为一句话：随着 peer 节点的加入、$N$ 的增加，请求资源的数量在增加，**而这些请求资源的节点同时又是提供服务的节点**。"人人为我、我为人人"的 P2P 精神，在文件下载、文件共享的场景下体现得淋漓尽致：客户端数量越多，下载时间相对 CS 模式越小，而且 $N$ 越大，节约的时间越多——这充分体现了 P2P 模式的优越性。

> **结论**：P2P 的可扩展性来自"供需同步增长"。CS 模式下客户端越多，服务器的服务能力越成为瓶颈——很难想象一个服务器（哪怕一个服务器群）能同时向那么多用户提供上载服务，不可能的；P2P 模式下请求方与提供方一起增加，系统很容易扩充到几百万、上千万用户的数量级别。

这里的分析以文件共享为例；视频分发、视频点播、实时音视频的传播也是同样的道理。

### 节点动态性与可管理性难题

P2P 性能高、可扩展性好，那它有什么问题？**可管理性**。

节点数量非常多，而且节点有时上线、有时下线，整个 P2P 系统经常处于动态之中。上线之后，它所具备的资源才可以为其他节点提供服务；一下线，就不能向其他节点提供服务了。可反过来，别的节点又上线了——它具备的资源可能和刚才下线的那个节点不一样，所在的网络位置不一样，上载、下载的网络带宽也不一样。整个网络具有高度的动态性，所以 P2P 系统中的节点非常难以管理。

这就引出要探讨的问题：P2P 系统到底有哪些管理模式或者运行方式？

### 覆盖网络与两种 P2P 形态

一共分为两种：第一种叫**非结构化的 P2P**；第二种是**结构化的 P2P**，也称为基于分布式散列表（DHT，Distributed Hash Table）的 P2P 系统——这里只介绍它的基本工作原理，DHT 系统的细节放到高级计算机网络课程里去学。

先看非结构化 P2P。所谓非结构化，指的是 peer 节点和另外一些 peer 节点构成**邻居关系**：我是 peer，你是另一个 peer，我们之间有一个会话，正在进行文件的上载和下载，互通有无——你是我的邻居，我是你的邻居。

把视角抬到应用层：我是一个 peer 节点（一个应用进程），你也是一个 peer，我跟你之间建立起 TCP 连接、或者 HTTP 的文件分发关系，这就构成了一条**边**。所有这样的边连起来，构成的网络叫**覆盖网（overlay）**。

> **定义**：覆盖网（overlay）是应用层面上的一个逻辑网络：peer 与 peer 因文件上下载等协作会话而形成的边，把这些节点连接成的整体。

这条边构成的网是逻辑的网还是物理的网？逻辑的——因为它在应用层。覆盖网上，我们两者之间就一条边、只有一跳；但实际上，两个应用进程之间可能要经过很多路由器、很多物理网络的边，才能把两者连在一起。

> **易错点**：覆盖网上的一跳不等于物理网络上的一跳——overlay 的边是应用层的协作关系，底下可以隔着任意多的路由器与物理链路。

非结构化与结构化的分界，就在这张 overlay 的边上：非结构化 P2P 里，节点跟节点之间的边是**任意**建立起来的，overlay 是随意的、随机的；而 DHT 网络里，根据节点 ID 的不同，peer 节点可以构成一个**有序的** overlay——可以构成一个环，可以构成一个树，还可以构成更复杂的、不断嵌入的深层次关系。

### Napster：集中式目录

非结构化 P2P 的第一种工作方式是**集中式目录**，代表是 Napster——第一代 P2P 文件分发系统。它是美国一所大学的低年级本科生创建的，创建这个 P2P 文件分发系统的主要目的，就是在大学校园里分发免费的 MP3。

它怎么工作？看 Alice 下载一首歌的完整流程：

```text
① 上线注册：Alice ──────▶ 目录服务器 （我的 IP 是什么，我有哪些资源）
② 关键字查询：Alice ────▶ 目录服务器 （键入关键字，比如"某某歌"）
③ 返回结果：目录服务器 ─▶ Alice      （给出持有该文件的 peer 节点列表）
④ 建立连接：Alice ──────▶ Bob        （建立 TCP 连接，其上用 HTTP 请求文件）
⑤ 文件传送：Bob ────────▶ Alice      （文件到手，Alice 成为拥有者）
⑥ 上报资源：Alice ──────▶ 目录服务器 （咱也有这个资源了，可对外服务）
```

Alice 拿到文件之后，一方面上报给服务器："咱也有这个资源了，我也可以就这些资源向其他用户提供服务。"另一方面，她在向 Bob 请求服务的同时，还可以就自己拥有的其他资源向别人提供服务，比如向 Trudy 提供文件共享——一方面她是客户端，请求 Bob 的资源；另一方面她是服务器，向 Trudy 提供服务。所以所谓的"客户端"要打个引号，实际上就是一个 peer 节点：从某个会话上看它是服务器，从另一些会话上看它是客户端。

任何一个基于 P2P 的文件分发系统，都要解决两个问题：**第一，资源如何定位**——这是一个目录服务的问题；**第二，节点的加入和退出如何处理**——也就是前面说的动态性怎么管理。Napster 用集中式目录回答第一个问题。

每个节点——Bob、Trudy、所有其他 peer——上线的时候，都要向集中式的目录服务器做一次注册登记："我是 Napster 客户端，上线了，我是哪个 IP，我这个 IP 上有哪些资源。"下线的时候也要打声招呼："拜拜了您呐，我暂时离开一会儿，有什么资源就别再问我要了。"这叫**有序的下线**。这样，目录服务器就维护着两份信息：哪些 IP 当前在线；这些 IP 当中各自具有哪些资源。反过来看，客户端要查询某个资源，服务器按资源做索引，就能回答"A 这首歌在哪里、B 这首歌在哪里"，把 peer 列表返回给查询的客户端；客户端拿到列表后，**直接**向拥有资源的节点发出文件下载请求，对方响应请求，把文件传过来。

所以看清楚：这种方式的**目录服务是集中式的，而文件分发是 P2P 模式的**。

这种 P2P 系统有什么问题？第一，目录服务器挂了怎么办？存在**单点故障（single point of failure）**——这个单点一挂，整个系统全完。第二，Napster 客户端数量非常多的时候，大家都要上线注册、下线报告、随时查询，这些负担全部压到目录服务器上。还有一个更致命的：**版权侵犯的定位问题**。peer 节点之间进行文件的上载下载，很难取证，也很难告——法不责众嘛，那么多大学生都在上面下载、分发 MP3，你去把谁抓起来？你去告谁？很难。但是 Napster 服务器是很容易定位的：就是这个机构运行着目录服务器，正在提供非授权内容的目录查询。版权的拥有者告它——于是 Napster 就这样被干翻了，被判处"拔掉插头"：把服务器从墙上拔下电源插头，宕机。

### Gnutella：完全分布式与泛洪查询

集中式目录有单点故障，另一种方式是**完全分布式**，代表是 Gnutella。所有 peer 节点一律平等，没有任何一个节点维护全局的目录信息。Gnutella 还有两个鲜明的特点：没有中心的目录服务器；代码是开放的（open），所有人都可以下载来剖析，协议也是公开的，实现采用开源方式。于是出现了很多 Gnutella 的变种——基于开源改一改，或者协议公开、自己完全实现一套。只要遵守这个协议，不同版本的 Gnutella 实现都可以相互协作，没有任何问题。

假设 overlay 已经建立起来，每个节点已经跟其他的 8 到 10 个 Gnutella peer 构成了邻居关系。在这种完全分布式的系统里，文件的查询和共享如何进行？答案是**泛洪（flooding）**。Alice 要查某首歌，就把查询发给**所有**邻居；每个邻居收到查询之后，除了进来的这一端，向自己**所有**其他邻居转发；邻居的邻居再照样转发：

```text
（第 1 跳）Alice ──▶ 自己的所有邻居         ← 8~10 个邻居全部收到查询
（第 2 跳）每个邻居 ──▶ 除来路外的所有邻居   ← 收到查询的节点继续转发
（第 3 跳）以此类推，一传十、十传百……
```

采用这种方式，查询很快遍及全网。拥有资源的节点**反向**给出应答，把查询结果送回 Alice；Alice 就知道哪些节点有这个文件——目录问题解决了，接下来她直接向拥有资源的节点发出请求，文件就到手了。查询是 P2P 的方式，文件分发也是 P2P 的方式，全程没有中心。

但泛洪有什么问题？没完没了。你向所有邻居，邻居再向所有其他邻居，有的还绕个圈又转回来——一个查询发出去，十天半个月都还在网络当中回荡，"你有吗？你有吗？"大家感到很困惑。所以泛洪式的查询还要配一些机制，来限制它的泛洪作用：

- **TTL（Time To Live，生存时间）**：设成 5、或者设成 $N$，每过一跳就减一，减到零就不再转发——"五步倒""七步倒"，查五跳、七跳之后自动干掉，这是**有限的泛洪**；
- **中转节点记住已转发的查询**：记住"我已经转发过谁发出的第几号查询"，下次同样的查询绕一圈又回来，就不再泛洪。

方法还有很多，目的一致：既限制泛洪的作用，又能让查询包有效地遍及全网。

Gnutella 的问题也很明显：**维护起来非常困难**。而且刚才一直有一个前提被绕过去了——泛洪所依赖的 overlay 覆盖网到底是怎么建立起来的？办法是：每个 Gnutella 客户端在软件安装的时候都带一个配置文件，里面给出若干个 Gnutella 网络中经常在线的节点的 IP——相当于软件自带一份"死党"名单：十来个节点，它们比较大的概率就在这个网当中。

## P2P 应用：Gnutella、混合体、BT 洪流与 DHT
> 对应块：BLK19 | 覆盖分集：P18下 | 块标题（分集名）：《2.6 P2P 应用》

### Gnutella 的加入与退出

先抛一个尴尬的场景：你装好了 Gnutella 软件，安装包还替你配置好一份十个"死党"节点的列表——结果一查，十个死党全死了，没有一个活的。死党全死了，那就真没办法了，这个节点进不了网络。但只要死党列表里还有一个活的，加入就有戏：这十个死党大概率都存在，向列表里的节点发出加入请求，也就是 Ping。

收到 Ping 的节点做两件事：一方面向源节点回一个 Pong，另一方面把 Ping 转发给自己的所有邻居；邻居收到后又回 Pong、又转发，一路传下去。于是 Ping 泛洪出去，Pong 从四面八方涌回来。新节点从这一大堆响应里随机挑 8 到 10 个，按 Gnutella 协议与它们建立邻居关系——overlay（覆盖网络）就这么构建起来了。

> **结论**：加入 Gnutella 的过程就是"向死党列表泛洪 Ping → 收到者回 Pong 并继续转发 → 从大量 Pong 中随机挑 8~10 个建立邻居"。

退出也讲究有序：离开的节点要向自己那 8 到 10 个邻居逐个打招呼——"哥们儿，暂时离开一会儿"。邻居们得知它离开后，各自再从网络中挑一个新节点补上空缺，维持连接强度，让自己的度始终满足 Gnutella 正常运行的最低要求。加入靠死党列表，退出靠邻居补位，overlay 就这样一直维持着。

overlay 建起来之后，目录、查询和文件分发全都以 P2P 的方式跑在这张网上。理论很漂亮，但 Gnutella 在现实中运行得非常不成功，以至于有人说"在 Gnutella 网里什么也找不到"。原因很多，除了技术原因之外还有很多非技术原因，主要是技术上的。它并不是一开始就开源的：作者做完之后觉得是个宝贝，结果没人用，后来被迫开源、指望扩充用户群——用户群也没扩充多少。

### 混合体：组长与组员

完全分布式之外，还有一种"混合体"架构。每个节点要么是组长，要么是组员：组员归属某个组，组长与组长之间的关系就像 Gnutella，组长与组员之间的关系则像 Napster。

查询这样走：组员把查询发给自己的组长；组长先在本组内匹配，查到就告诉组员"东西在我组内，你去向他们请求"；组内没有，组长再把查询转发给所有其他组长。

```text
        L1 <----------> L2 <----------> L3
        | ^             | ^             |
        v |             v |             v
       组员们           组员们           组员们

  L1/L2/L3 彼此之间：Gnutella 式泛洪（分布式）
  L 与本组组员之间：Napster 式查询（集中式）
```

所以这是一套两层叠加的架构：组内这一层是集中式的，组长与组长这一层是分布式的。集中式查得准、泛洪覆盖面广，两层结合能有效提高查询效率。

### 文件描述与哈希值：分布式命名

每个文件在上传时都要附带两类信息。第一类是描述信息（元信息）：这个文件是干什么的——"某某某在某某演唱会上唱的歌（真唱）"，是现场版还是录音棚版，是高解析度还是低解析度。这些描述都是文本。第二类是哈希值：文件上传时计算出来的、16 字节（或更长）的散列值，作为这个文件的唯一标识。所有资源都这么操作：资源提供方除了提供资源本身，还得提供描述和哈希。

用户检索时匹配的是描述：输入歌手名、歌名，在描述字段里匹配。组长或目录服务器把匹配值最高的结果返回给用户；用户点击某个结果，实际发出的请求是对应那个哈希值的文件请求——以哈希值作为唯一 ID 去把文件取回来。

> **提示**：检索匹配"描述"，下载请求"哈希值"，两者分工不同——描述供人查，哈希供机器精确定位。

为什么要绕这一道？想想"下载某某歌手唱的某某歌"这种命名方式有多糟：同一首歌在各种场合唱的版本多了去了，压码情况不一样、格式不一样，有高解析度有低解析度，还有现场版和录音棚版——用"谁唱了什么歌"根本无法唯一标识一个文件。把文件的哈希值作为唯一 ID，元信息负责描述，索引把描述和哈希对应起来，检索走描述、请求走哈希，文件请求就十有八九不会出问题。这实际上是一种分布式命名的方式；在分布式文件系统的命名当中，用哈希做唯一标识是很常见的做法。

### BitTorrent：洪流与互通有无

最后看一个实际例子，它基本就按我们前面讲的方式来工作：BT（BitTorrent），民间叫"变态"。Peer 要加入一个洪流（torrent）：洪流就是参与同一个文件分发的一组对等节点（Peer），加上它们之间服务和被服务的关系。打个比方：大家都要下同一个文件，Alice 跟其他一些 Peer 就构成了一个互通有无的学习小组——我有的分发给大家，别人有的可以给我，相互协作，最终让小组里每个人都拥有同样的"知识点"。

#### 块与位图：洪流的目录机制

把要分发的文件想成一门课：这门课被切成一个个 256KB 的块，每块相当于一个知识点。目录问题——谁手里有什么——怎么解决？每一块用一个比特来标记：1 表示我拥有这个知识点，0 表示我不具备。一串比特就把"我有什么、缺什么"说完了，这就是位图（bitmap）。

```text
块序号:  0  1  2  3  4  5  ...
bit  :  1  1  0  0  1  0  ...      (1 = 拥有该块, 0 = 不具备)
```

每个 Peer 都维护自己的 bitmap——若干字节而已。但光自己有没用，得互相知道：所有 Peer 定期在洪流中泛洪、交换各自的 bitmap，就像定期传一张小纸条。比方说 8 个人、10 个人构成一个洪流，定期交换纸条之后，每个节点随时都知道洪流中所有其他节点拥有哪些块——这就是 BT 的目录机制。

#### 请求端：先随机四块，再稀缺优先

Alice 新加入，关于这个文件什么都没有，bitmap 全 0——这就是"吸血鬼"：文件里没有任何一块。这时没什么可挑的，饥不择食，随机地向其他节点请求一些块，先弄到 4 块垫底再说。

有了 4 块，就可以挑着请求了：请求洪流中最稀缺的块——稀缺优先（rarest first）。为什么稀缺优先是个好策略？把稀缺块请求过来，整个洪流里这块的副本就得以补齐、增加，它变得不稀缺了。反过来看最坏情形：某一块非常稀缺、全洪流只有一个节点有，这个节点"咣"地一下下线了——所有节点都再也拿不到这一块，这个文件等于缺了一大块。所以说稀缺优先对集体是有利的。

那集体利益怎么跟个人利益捆绑？服务端的策略是优先向"给我服务最好"的节点提供服务——你对我好我对你好，你对我差我对你差，这叫以暴还暴，或者叫针锋相对（Tit-for-Tat）。拿到稀缺块的节点，被其他节点请求的概率就上升；它向别人提供的字节数越多，按 Tit-for-Tat，别人回给它的服务带宽就越大，整个下载时间就越短。稀缺优先对个人同样划算。

> **结论**：稀缺优先同时讨好集体与个人——集体多了副本，个人多了被请求的机会；被请求得越多，按 Tit-for-Tat 换来的下载带宽越大。

那为什么一开始不稀缺优先？稀缺块本来就稀缺，拿到完整一块要花很长时间；在那么长的时间里你无法向别人提供服务，别人也无法很好地向你提供服务。所以起步阶段没有可选，先随机弄 4 块垫底，之后再稀缺优先。

#### 种子与激励

洪流里有扰动：节点上线、下线，不断进出。但只要进出的动态之下，汇聚在系统里的节点数量仍然不少，有很多人上传、有很多人下载，整个洪流依然是一个"供销两旺"的动态平衡系统。别忘了 P2P 的本性：下载的同时，你已具备的内容就在向其他节点提供服务。

拥有文件全部、bitmap 全 1 的节点叫种子（seed）；反过来的就是前面说的吸血鬼。种子可以离开——这是利己主义者；也可以留在洪流里继续上传——这是利他主义、集体主义。留着不走的另一层现实好处是攒人品：以后你下载别的文件时就会来得比较快。BT 就靠这套机制激励各节点勇于奉献、多往系统里贡献自己的上传能力，整个 P2P 系统的性能才上得去。

对照一下现实：很多人跑迅雷或其他 P2P 客户端时，下载并行数恨不得设成 100，上传却设成 0——100 个连接同时下，一个字节不给别人。这其实对自己并不好：你向其他节点提供的带宽越小，其他节点就把你的文件请求优先级排得越靠后。所以在这里，利人就是利己。

#### 服务端：优先疏通与随机试探

再看有内容的一方怎么提供服务。80 个节点同时来请求，我的上传能力就那么大：如果来者不拒，每人只分到我的八十分之一，像撒胡椒面——看似同时在服务 80 个节点，每个节点拿到的带宽都小到没有意义。怎么办？只服务 4 个：同意其中 4 个建立连接，疏通（unchoke）之后在这些 TCP 连接上用 HTTP 传文件，其余 76 个排队；这 4 个服务完毕，再从队列里挑下一批。这叫有限疏通。

排队的 76 个不是先来先到。每个周期（10 秒）评估一遍：上个周期里谁向我提供的字节数多、给我的下载带宽大，就把谁的请求排在前面、优先疏通。比如 C 虽然请求来得靠前，还是往后放——D 上个周期给我的服务带宽不错，把 D 拉进来。每个周期都这么干，这叫优先疏通。

三个周期里前两个都择优，第三个变一变：随机挑一个。为什么？你不知道哪块云彩会下雨。前两个周期服务的都是"对我好的"，剩下的节点里没准有黑马——随机选一个试探一下，万一它资源情况不错、给我的带宽还比较大，下个周期它就能提供很好的服务。选错了也不亏：下个周期评估不合格，照样排回队尾。这种随机化就是通过震荡做试探，让节点之间的协作保持开放，相互之间的并行上载下载带宽才做得更大。

> **结论**：请求端先随机四块、再稀缺优先；服务端每 30 秒一个周期只疏通 4 个名额，三个 10 秒轮次里两轮择优、一轮随机试探。

这些策略的最终目的只有一个：把整个网络看成一个大的整体，很多人上传、很多人下载，让上传的总和 $\sum U_i$ 与下载的总和 $\sum D_i$ 都尽量大——整个网络的吞吐量上去了，每个节点的下载时间自然就短了。

### 加入洪流：torrent 文件与跟踪服务器

BT 的机制讲完了——它本质上也是一种非结构化 P2P，也可以把它归到比较偏混合的一类。不过还遗留一个问题：洪流本身怎么加入？带外（out of band）解决。

我们有一些文件分发的检索网站（各种 BT 网站）：在网站里输入关键字，匹配到资源，返回列表，点击下载——拿到的不是文件本身，而是 torrent 文件。回忆一下分享前的处理：上载方提供文件本身和描述信息，上传时算好的哈希作为唯一标识，这些登记到文件分发网站上；而 torrent 文件是一个元描述信息，记录了关于这个资源有哪些 tracking server（跟踪服务器）在维护它。

客户端向 torrent 文件里记录的 tracking server 发出信令："我是一个 BT 客户端，我要加入这个洪流。"跟踪服务器维护的就是这类信息：关于这个文件，一堆人正在并行上载下载；关于那个文件，一堆人正在上载下载。收到加入请求，它随机地或按某些策略返回一个 peer 列表："欢迎你，Alice，你跟这些节点构成洪流，完成这个文件的上载下载。"Alice 于是以吸血鬼的身份加入，跟列表里的节点互通有无。

```text
文件分发检索网站（带外）
   |  输入关键字 -> 匹配 -> 返回列表 -> 点击下载 torrent 文件
   v
torrent 文件 = 元描述（记录：本资源由哪些 tracking server 维护）
   |
   v
tracking server（跟踪服务器）
   |  客户端信令："我是 BT 客户端，我要加入这个洪流"
   |  返回 peer 列表（随机或按某些策略）
   v
Alice 与列表中的 peer 构成洪流，互通有无
```

### 结构化 P2P 与分布式哈希表

非结构化 P2P 之外还有结构化 P2P，其代表是基于分布式哈希表（Distributed Hash Table，DHT）的方案：节点之间维护的是树状、环状这样有序的拓扑。以环状为例，三个要点是：

**节点 ID。** 每个节点把自己的 IP 地址做哈希，得到 16 字节的 ID 值——节点不用 IP 标识自己，而用 IP 的哈希值。节点按 ID 大小首尾相接排成一个环，overlay 的邻居指向关系就是按节点 ID 构建的有序拓扑。

**内容 ID。** 文件内容也做哈希，同样是 16 字节的哈希值。内容 ID 与节点 ID 处在同一个编号空间里。

**存放约定。** 内容放在哪个节点是约定的。例如内容 ID 从 6 到 88 的全部维护在节点 88 上，从 89 到 199 的全部维护在节点 199 上。

```text
  5 --> 88 --> 199 --> 1011 --> 1012 --> 2560
  ^                                        |
  |________________________________________|

  节点按 ID 大小首尾相接构成环（2560 之后绕回 5）
```

查询就快了：我要查内容 78，按约定它落在 6~88 区间，节点 88 要么存着它、要么肯定知道它在哪儿。沿着有序拓扑很快定位到 88，让它把文件或文件目录给我，再去请求。这样副本数量不需要很多，也能很快找到提供内容服务的节点并完成下载。

对比一下就知道结构化 P2P 解决了什么：集中式目录让一个节点维护所有目录，可扩展性差；完全分布式靠泛洪查询，要查得快副本数量就得很多。结构化 P2P 把这两个问题都摒弃了——节点之间构成有序拓扑，节点与内容共用一套 ID 空间，内容 ID 落在哪些节点 ID 上是一种约定，沿有序拓扑就能快速定位内容所在的节点，快速做内容分发。

| 架构 | 目录与查询方式 | 短板或优点 |
| :--- | :--- | :--- |
| 集中式目录（Napster 式） | 目录集中在一个节点，查询都发给它 | 单点维护所有目录，可扩展性差 |
| 完全分布式（Gnutella 式） | 目录分散在各节点，查询泛洪 | 想查得快，副本数量就得很多 |
| 混合体（组长/组员） | 组内集中、组长之间泛洪 | 两层叠加，查询效率高 |
| 结构化 DHT | 有序拓扑 + 存放约定，按 ID 定位 | 副本少、查找快 |

基于 DHT 的 P2P 系统在现代文件分发系统里用得还比较多；具体细节这里不再展开，了解到这个程度就 OK 了。

## 内容分发网络 CDN 与流媒体内容加速

### 视频业务与两大服务挑战

互联网上的杀手级应用有很多种，视频业务是其中最重要的一种。什么叫杀手级应用？两条标准：占的网络流量大，而且最能吸引用户。据统计，互联网中七八成甚至更高的流量都被视频占据；而且视频流量越多，越能吸引新的用户加入——这两条凑在一起，视频业务就成了要重点伺候的对象。

> **定义**：杀手级应用（killer application）——同时满足「占据大头网络流量」与「最能吸引用户」两个条件的业务；视频业务是当下互联网最重要的杀手级应用。

于是问题来了：如何向成千上万、上百万级的用户**同时**提供质量不错的并行播放服务？放在早年间这不成问题——那时互联网上视频业务占比不大，开几台服务器，撑几十个甚至几百个并发绰绰有余；现在用户规模完全是另一个量级。这个挑战拆开是两条。

一是**规模性**：怎样同时向海量用户提供并行的流化服务。二是**异构的客户端**：每个节点的上下载能力不一样，网络带宽情况不一样，视频处理能力不一样，需求也不一样。手机屏幕就那么大，看视频并不需要很高的清晰度，不必下载高清晰度的视频；可要是家里装了一台 100 寸的网络电视（这东西以后会很便宜），还给你 800×600 甚至 1080 的视频，是不是看着就很模糊？需求不同、能力不同，服务却得同时做好。

解决方式，是采用**分布式的应用层基础设施——CDN**。先把「视频是什么、怎么在网里传」这两件事铺清楚，再看 CDN 怎么解决这个互联网杀手级应用的内容加速问题。

### 视频的构成与压缩基础

视频可以认为是一系列图像（帧）的序列。人眼视网膜有滞留效应：看完一样东西，影像大概要过若干毫秒才会消失。于是前一帧给你、下一帧接上来，你就看到了「动」的效果——这就是电影的原理。现在的视频帧率很高：每秒 24 帧、60 帧，甚至更高，玩游戏的时候帧率尤其高。图像本身，又是像素（pixel）的有序序列。

视频业务最重要的特点是**占带宽特别大**：一路高清晰度视频比一路高清晰度音频占的带宽大得多。完整的、未经压缩的视频直接进网络传输基本不可能——带宽浪费太大。所以音视频（特别是视频）在网络中传输前通常要先压缩，变成小码率的视频再传播。

压缩的基础，是视频在空间与时间上的冗余度。

| 冗余类型 | 存在于哪里 | 压缩的基本思路 |
| :--- | :--- | :--- |
| 空间冗余 | 一帧图像内部 | 相邻大片像素颜色相同或相近，只需描述「这个像素值持续了多少个像素点」 |
| 时间冗余 | 相邻帧之间 | 只把动了的对象编码传输一遍，不必逐帧传完整画面 |

空间冗余看的是一帧之内：大片像素点的颜色一样或类似，描述时直接说「这个像素值持续了多少个像素点」即可——这是最简单的一种空间冗余压缩方法。时间冗余看的是帧与帧之间：相邻两帧画面里大部分内容没动，传输时仅仅把那些动的对象编码一遍就够了，不必传每一帧的完整内容。抓住这两种冗余，就能把待传视频压成小码率。

### 码率类型、编码标准与可伸缩编码

压缩编码按输出码率分两类。**恒定码率（CBR，Constant Bit Rate）**：一路视频压出来的码率基本固定——两兆、一兆或者几百 K，基本不变；有些编码工具还能让你指定压出来大概是多大，它就自动照办。**可变码率（VBR，Variable Bit Rate）**：码率随内容起伏——拍的是静态景色、画面基本不动，传输量就非常少；一旦是打斗场景或者场景切换，当时的瞬时码率就窜得很高，过后又降下来。

标准方面，网络传输中常用 MPEG-1、MPEG-2、MPEG-4，还有我们国家的 AVS（先进音视频编码）。AVS 是中科大的吴枫（学院原副院长、现任校长助理）与他的导师高文院士当年在哈工大期间提交的国际标准。科大在多媒体编码上能力比较强，每年都向国际标准化机构提交不少提案，这是科大的一个传统强项；咱们科大的同学就有不少正在研究音视频编码的标准与技术。

可伸缩编码还要单独说一句：它是科大信息学院李卫平（千人计划学者）多年前提出的，出发点正是终端异构——不同视频终端的需要不一样。手机小，给 400×300 或 800×600 就足够了；家用 PC 的解析度要求又不一样；家里若是 100 寸大电视的网络电视，要求的清晰度还要更高。可伸缩编码按你的要求给编码：要大的给大的，要小的给小的。

### 流化播放与 DASH

#### 流化播放：边下边看

在网络中做视频点播，经常采用流化（streaming）服务。设想一台机顶盒（set-top box，STB）对着流媒体服务器（streaming server）看影片：要把整个视频文件全部下载完才开始看吗？不需要。先下完再看的方式叫 download-then-play，本质上就是一次文件下载，跟视频播放本身没关系——下几个 G 的文件得等上几个小时，之后倒杯水才能开始看，太麻烦。

流化播放是另一回事：一边下载，前面下了一段、缓冲区里存上货了，就可以开始看；下载不停地往缓冲区里灌，播放器从缓冲区里不停地提取着播——**下和看是并行的**。这样用户的点播延迟（playout delay）就非常低：现在点完之后顶多缓冲七八秒钟；掏了钱当会员的更快，连广告都没有，水都没来得及倒就开始播了，搞得你有点措手不及。流化播放就这样把用户的等待时间大幅度压了下来。教材后面的章节会介绍流化播放的具体技术，比如用 RTP 协议封装流化播放的视频内容，那是另外一回事。

#### DASH 的切块、多版本与 manifest 文件

常见的一种流化协议叫 DASH：动态自适应流化 over HTTP（Dynamic Adaptive Streaming over HTTP），内容一块一块地在 HTTP 上传输。

> **提示**：HTTP 仅仅用于 Web 吗？不是。它可以用于文件的上传下载，也可以用于音视频播放——HTTP 就是一个传输协议。

DASH 的做法分三步。第一，把大视频切成一块一块的，每块维持 8 到 10 秒的播放。第二，每一块都处理成多个版本——超高解析度、高解析度、中低解析度、低解析度、超低解析度，还可以配不同的压缩编码标准；每一块都这么处理。第三，用一个 manifest 文件（告示文件）把这一切发布出去：它描述这部视频切成了多少块、每块视频持续的范围、有多少个版本、每个版本的每一块放在哪个 `URL`。本质上就一句话——任何一块，它是什么解析度、什么编码、特别是它的 `URL` 是什么，全在告示文件里。

这些块可以分布在不同的服务器上：源服务器里有，缓存服务器里也可以有——靠预先部署做到。所以一部视频上线时，要先把它做成不同版本、每个版本切成块，再把每一块所在位置的 `URL` 以 manifest 文件的形式发布。

```text
一部影片 ──切成 8~10 秒的块──▶ 块0、块1、块2、……
                                     │
                                     │ 每块压出多个版本
                                     ▼
        超高 / 高 / 中低 / 低 / 超低解析度 × 不同压缩编码标准
                                     │
                                     ▼
   manifest 告示文件：块数、每块持续范围、版本数、每个版本各块的 URL
```

一个视频块在服务器上是一整套版本；manifest 把每块每版本的 `URL` 都登记在案，客户端照着它去取块。

#### 客户端的动态块选择

客户端（那台 STB）点播时，首先下载 manifest 文件并解析；然后一边下载块、播放块，一边决定后续请求哪些块。注意：具体什么时间请求、向哪些服务器请求哪些块，是**客户端自己决定**的。依据什么？到各个服务器的带宽可以实测；再看自己的屏幕尺寸、播放需求、当时的网络能力，还有缓冲区里已经攒了多少货。根据这些，客户端在整部视频的播放过程中不停地切——动态决定向哪些服务器请求哪些解析度的块，目标是流化播放尽可能持续不断，同时解析度尽可能高。

什么时候拿高解析度的块？缓冲区很满、后面 20 秒都能持续播，到那些服务器的带宽又很大——心里有底了，弄个大的，让用户爽一爽。什么时候退而求其次？要么客户端屏幕小，不需要那么大；要么网络带宽受限；要么缓冲区快见底了——都见底了还请求大的，有这个资本吗？有这个资格吗？只能请求小的。

决策做砸了也看得见：缓冲区用完了、后面的块还没到，用户面对的就是那个「努力缓冲中」的转圈界面——一只小鸭子（或者别的什么）飞来飞去，试图从网络里抓取后续的播放块。所以客户端是动态的、智能的，什么时候请求块、选什么编码的块、到哪里请求，都由它定，但智能不智能，取决于决策做得好不好。

> **定义**：DASH（Dynamic Adaptive Streaming over HTTP，动态自适应 HTTP 流化）——视频切成 8~10 秒的块，每块压出多种解析度、多种编码的版本，按预先部署的要求分布在若干服务器上；客户端拿到 manifest 后，根据播放需求、网络带宽和缓冲区水位，动态决定向哪些服务器请求哪些版本的块。

DASH 解决的是不同客户端、不同网络情况带来的需求差异与能力差异问题。但它只回答了「给每个人挑合适的块」，没有回答「块从哪里来」——如果大家都从一个（或为数极少的）服务器上取流，麻烦就来了。

### 集中式流化服务的三个瓶颈

第一，**跳数多**。客户端到服务器隔着长长一串链路。服务器做了再多优化，也只能优化它自身，优化不了中间的网络——服务质量好不好，还取决于中间那些链路和网络的情况，而瓶颈式的链路会卡住端到端的有效吞吐（前面分析吞吐时的结论：整条路径的吞吐被瓶颈链路卡着）。所以指望服务器自身努力没有用：网卡升级、接入带宽升级，统统没用。

> **结论**：集中式流化服务的质量瓶颈不在服务器，而在服务器到用户之间的网络——靠服务器单方面升级解决不了问题。

第二，**重复流量多**。大家都从服务器下载同一个文件流化播放：你也放《纸牌屋》，他也放《纸牌屋》，同一份内容被网络反复搬运。这类流量呈现所谓的二八分布、齐普夫分布（Zipf distribution）——少数热门内容占掉绝大多数访问——对网络资源是实打实的浪费。

第三，把这两条再往下推：单个服务器或超级服务器群存在**单点故障**，有可靠性的问题；有性能瓶颈的问题；还有整个服务器群周边网络拥塞的问题。这三条，就是 CDN 出场要解决的事。

### CDN 的基本思路

> **定义**：CDN（Content Distribution Network，内容分发网络）——在应用层形成的一个内容分发网络，通过在全球部署缓存节点、预先存放内容，向用户提供更好的内容服务。

思路非常简单：提供流媒体服务的运营商（ICP）去买 CDN 运营商的服务；CDN 运营商在全球网络中部署大量缓存节点（cache server），把内容预先部署进去。这样，互联网的角色名单上多了一个新角色——前面学过的角色有终端用户、ISP、ICP，现在加上 CDN 运营商。美国的 Akamai、中国的 ChinaCache（中国蓝汛）都是 CDN 运营商；CCTV、凤凰网、百度这些 ICP 都要买 CDN 运营商的服务，用它加速内容传输、提升对用户的服务质量。

用户上线之后，不必再从源服务器那里获得视频的流化服务：中间经过**域名解析的重定向**，被导向离他最近、服务质量最好的缓存节点，由那个缓存节点提供内容服务。因为跳数少、沿途网络情况好，用户拿到的流化质量自然高。这种服务就叫**内容加速服务**。至于具体在哪些位置部署缓存节点，属于部署策略问题，还要考虑经济层面上的测算指标——后面两节专门说它。

域名解析前面学过，它的主要功能是域名到 IP 的映射、别名到正规名字、邮件别名到邮件服务器名字，以及域的管理。现在给它再加一条用途：**域名解析的重定向**，正是它让 CDN 的运行得以可行。而且如果当前服务的缓存节点网络堵塞了，还可以改从其他缓存节点获得流化服务。

CDN 有自己的口号：**让内容靠近用户**。用户怎么知道该从哪里访问内容？两种方法：一种通过 manifest 文件，另一种就是域名解析的重定向。

### 缓存节点的两种部署策略

把互联网想象成一个松散的层次结构：终端用户最先通过 local ISP 接入，local 接到 regional，regional 再接到 global。CDN 的缓存节点往哪里放，有两条思路相反的主流策略。

```text
                global（全球层）
                    │
            ┌───────┴───────┐
        regional          regional        ◀── Bring Home：少数节点架在
           │                 │               上层 ISP、数据中心机房旁
        ┌──┴──┐          ┌──┴──┐
      local  local      local  local      ◀── Enter-Deep：节点铺进
        │      │          │      │            大量 local ISP 内部
       用户    用户      用户    用户
```

节点铺得越靠下、离用户越近，服务质量越好，但节点数越多；铺得越靠上、越集中，节点越少，但离用户越远。两条策略就卡在这个取舍的两端。

**Enter-Deep（深入群众）**：把缓存节点部署到大量 local ISP 的内部。节点就在用户接入网的屋檐底下，用户点播时跳数最少、带宽大、拥塞少，享受的服务质量最高。代价是要部署的节点非常非常多——Akamai 在大量的 local ISP 里都放了缓存服务器，前几年节点数量就达到数千个服务器群，每一个都要维护，都是要花钱的。

**Bring Home（卡住关键少数）**：不往下铺，而是卡住少数关键位置——上层 ISP 的数据中心机房旁边，选的位置离这些 ISP 的关键节点都非常近，拉光纤直通机房。虽然到终端用户的跳数稍微多一点，但卡住了枢纽位置、迁了光纤，底下 local ISP 用户的体验照样不错。好处是部署的节点非常少，用少数几个位置就能向用户提供很好的流化或内容传输服务；代价就是跳数远一点。

| 对比项 | Enter-Deep | Bring Home |
| :--- | :--- | :--- |
| 部署位置 | 大量 local ISP 内部 | 少数关键位置：上层 ISP、数据中心机房附近 |
| 节点数量 | 非常多（Akamai 达数千个服务器群） | 非常少 |
| 到用户的跳数 | 最少 | 稍多 |
| 服务质量 | 最高 | 仍然很好 |
| 主要代价 | 部署与维护成本高 | 跳数增加 |

### 一次点播的完整流程

以网飞（Netflix）购买 Akamai 内容加速服务为例。Akamai 在全球互联网范围内部署了大量缓存节点，网飞要预先把内容部署进去。之后用户请求流化服务时，首先拿到 manifest 告示文件，从中知道这个内容可以用这个 `URI` 访问、也可以用那个 `URI` 访问——每个 `URI` 对应一台服务器；客户端按策略选离它最近、跳数最少、网络拥塞程度最轻的缓存节点，由它提供服务，而不是去找网飞的源服务器。终端离缓存节点近、跳数少、拥塞程度基本可控，流化质量自然高。

整个流程归纳为三步：

1. ICP 预先把内容部署到 CDN 运营商的缓存节点上；
2. 用户点播时，先从源服务器获得 manifest 告示文件——它告诉终端用户：这部视频分成了哪些版本（高清晰度、低清晰度、各种编码），每一种清晰度、每一种编码都切成 8 到 10 秒的块，每一块在哪些位置；
3. 客户端自行决定什么时间请求、向哪个 `URL` 请求，并挑离它近、服务质量好的缓存节点，由缓存节点提供 DASH 流化服务。

网飞、ICP 们的内容服务就这样得到了加速——「内容加速服务」这个名字里的「加速」，指的就是这一整套机制。

### 央视春晚的 CDN 加速案例

中国质量比较高的 CDN 运营商是 ChinaCache（中国蓝汛）。顺带一提，每年毕业季来科大招聘的互联网企业里就有蓝汛，本科生、研究生都招——它做的就是内容加速：既做流媒体点播的加速，也做实时流媒体的加速。

以央视春晚为例，春晚的点播量是惊人的。如果大家都从央视的源服务器获得流化服务：第一，央视的服务器要部署非常大的规模，才能对抗那么多并发用户的访问请求，很难满足；第二，很多用户离源服务器跳数很长，网络质量根本无法控制，体验也好不了。所以央视的做法是买蓝汛的服务：把流化的内容通过专线（租用的线缆）打到蓝汛分布在全国各地的缓存节点，再由这些缓存节点向终端用户提供服务。终端用户离缓存节点近、跳数少，服务质量就高。各厂家具体细节可能有些差别，但核心思路就一句：让用户靠近缓存节点来访问，让内容靠近用户——这就是 CDN 的口号。

### OTT：应用层边缘的内容加速

CDN 的缓存节点运行在哪一层？应用层。处在网络的什么位置？边上。这是 CDN 运营很有意思的一点——over the top（OTT）：内容加速理论上应该在网络核心去做，但互联网的架构是 everything over IP、IP over everything，网络层提供的是最基本的服务，于是内容加速被放到了应用层来做。而在应用层，服务一定以边缘主机的形式提供——靠一台台 cache 主机之间的相互配合，完成内容加速。这个特点在互联网里非常明显。

> **定义**：OTT（over the top）——内容加速不靠改造网络核心，而是在应用层、网络边缘，以缓存主机之间的协作来完成。

OTT 模式带来三个要解决的问题：其一，那么多缓存节点可能都有这个内容，从哪一个获取服务？其二，正在服务的缓存节点网络堵塞了，怎么切换到离我最近、网络情况最好的另一个缓存节点？其三，哪些节点存这个内容——是这个节点、那个节点，还是所有节点？这就是内容部署问题。

### 节点部署与内容部署

CDN 的运营包括两件大事。第一件是**节点部署**：CDN 运营商在什么地方「撒点」。要考虑的因素非常多：成本——既包括一次性投入的成本，也包括日常维护的成本；用户效果——部署在这里能带来多大改善；还有各种现实条件——有的地方位置再好、离两端都近，可那是沙漠，交通不便又没有电力，照样不行，此外还有很多别的考虑。

第二件是**内容部署策略**：ICP 买了服务之后，CDN 并不是对它的所有内容都加速；哪些内容要加速、具体部署到这些节点还是那些节点、还是所有节点都部署，这是内容部署的策略问题。这属于研究生阶段「高级计算机网络」要学的内容——到时候你们学的数学、优化、运筹就都有用武之地了，这是个非常具体的优化问题。

### 玩具示例：NetCinema 与 KingCDN

用一个玩具版本看 CDN 到底怎么跑起来。ICP 叫 NetCinema，CDN 运营商叫 KingCDN。出场的角色有：NetCinema 的原始服务器（提供原始内容服务）、NetCinema 的权威名字服务器、KingCDN 的权威名字服务器、KingCDN 的缓存节点，以及用户终端 Bob 和他的 local name server。

```text
Bob ── 浏览 NetCinema 网页，点击视频链接（URL）──▶ NetCinema 原始服务器
  │                                                  （网页服务，不做任何修改）
  │ 浏览器把链接里的域名交给 local name server 代为解析
  ▼
local name server ── 问（找到根、顶级域、二级域）──▶ NetCinema 权威名字服务器
  ◀──── 返回的不是 IP 地址，而是另一个域名（重定向）────
  │
  │ 拿着新域名再次解析
  ▼
local name server ── 问 ──▶ KingCDN 权威名字服务器
  ◀──── 返回离该客户最近的 KingCDN 缓存节点 IP 地址 ────
  │
  ▼
Bob ── 请求 DASH 流化服务 ──▶ KingCDN 缓存节点（由它提供流化内容）
```

这条链路里，NetCinema 的权威名字服务器只做一件事：不回答 IP，而是把解析结果重定向到 KingCDN 的域名。具体走一遍：Bob 通过浏览器访问 NetCinema 的网页，网页里有一个视频链接，他点了这个链接。链接是个 `URL`，浏览器要解析其中的域名，把请求交给 local name server——它是名字解析服务的代理。local name server 一路问上去（根、顶级域、二级域），最后问到 netcinema 的权威名字服务器。关键的一步在这里：权威名字服务器返回的**不是**原域名对应的 IP 地址，而是**另一个域名**——一个重定向结果，意思是「你要解析的东西，去再次解析这个」。local name server 拿着新域名再去解析，就问到了 KingCDN 的权威名字服务器；它返回一个 IP 地址——离这个客户最近的一个缓存节点的 IP。如果离 Bob 近的是 KingCDN 的另一个缓存节点，返回的就是那个节点的 IP：每个客户来问，答案按「谁离你近」给。最后 Bob 拿着这个 IP，向 KingCDN 的缓存节点请求 DASH 流化服务，由缓存节点向他提供内容。

这套机制最漂亮的地方是改动极小、对用户完全透明：Web 服务器不需要任何修改；NetCinema 的权威名字服务器只需要知道哪些内容要加速，往里面插入一些域名和重定向的 mapping 表项——你来查询，我就返回重定向；KingCDN 的权威名字服务器要知道哪些缓存节点可以服务这个内容，维护一份到各个 ISP 距离远近的信息，按选择策略返回相应的地址；流媒体服务器照常工作；客户端更是一行都不用改。用户根本感受不到自己是被原始服务器服务，还是被缓存节点服务——整个过程在背后运行，无缝连接。这就是 CDN 的重定向。

### 真实案例：网飞的内容分发架构

网飞是互联网上有名的 ICP，既做视频制作也做视频服务，《纸牌屋》等很多脍炙人口的作品都出自它。它的前身做的是录像带租赁，后来是租碟子——一次可以租几十盘拿回家慢慢看，但毕竟还得跑一趟现场，很烦。有了网络之后，用户完成认证、缴费，就能在线点播，不必再物理地跨越一段距离去租碟、换碟。

它的架构有四个特点。第一，**制作与 Web 都在云上**：视频制作在云中进行，Web 服务也租亚马逊的云，网页直接上载到云里——成本压到最小，尤其一次性投入的成本最小。第二，**认证服务器自己维护**：只保留账户注册、登录、认证这一组服务器——认证这种事放在云里似乎不太合适。第三，**内容发布给多个 CDN**：制作完成后上载到若干 CDN 运营商的缓存节点，包括 Level 3 和 Akamai 等，让它们加速内容访问。第四，**用户侧的流程**：先通过网飞的认证服务器完成认证，然后浏览放在云里的网页（认证之后才能看到相应的视频），点视频链接，经过域名解析的重定向得到离自己最近的缓存节点——可以手选，也可以自动挑一个最近的 CDN 缓存节点——最后由缓存节点提供 DASH 流化服务。

它的制作模式也别具一格：根据大数据分析，一边拍、一边放，同时收集用户反馈，分析什么样的剧情更吸引用户，再接着往下拍。整个周期非常短、反应非常快，抓住人的兴趣取向去引导剧情发展——前面已经播出了，后面的剧情什么样，好多人都不知道，因为还在边播边改、边制作。
