## 散列 II：哈希表为什么会彻底崩盘
> 对应块：BLK25 | 覆盖分集：P68 | 块标题（分集名）：《[61B FA25] 第27讲 - 散列 II》

屏幕上这张看起来有些怪诞的照片，很像二十年前早期 AI 生成的产物。当年有人让它画一个“网络空间里的哈希酒吧”（Hash Bar in Cyberspace），结果就折腾出了这么个奇特的画面。说实话，我觉得这比现在千篇一律的 AI 艺术要有趣得多。

坦白讲，我对今天这节课的内容不像前面红黑树或 AVL 树那样经过了二三十个小时的反复打磨与试讲。以往这门课通常由 Josh Hug 老师亲自讲授，或者由我和 Justin 配合完成。今天是我第一次独立讲这部分内容，咱们一起来看实际效果。

上一讲我们学习了哈希表的基本机制。但哈希表内部的算法、哈希码计算以及碰撞处理往往太引人入胜了，以至于我们非常容易钻进实现细节里，反而忘了它究竟是用来干什么的。

哈希表的终极目标，是用来实现高效的**集合（Set）**与**映射（Map）**。今天我们的讨论主要以集合展开，但请时刻记住，它同样是构建映射的底层基石。我们费尽心思设计哈希码、搞各种数学转换，目标绝不是为了炫技，而是为了得到一个支持元素快速查找（`contains`）与插入（`add`）的高性能无序结构。

为什么一开始要反复强调这一点？因为当我们去观察哈希表在什么情况下会发生严重错误甚至彻底崩溃时，深刻理解“它的初心是集合”是排查所有诡异行为的关键钥匙。

```text
+-------------------+      hashCode()      +--------------------+      % 桶数量 M      +-----------------+
|  任意对象 Object   |  ----------------->  |   整数哈希码 int   |  ----------------->  |  桶索引 (0~M-1)  |
| (String, Walrus)  |  "如果你是个数字...  | (-21亿 ~ +21亿)    |   压缩映射至桶边界   | (定位到具体单链表) |
+-------------------+   你想成为哪一个？"    +--------------------+                     +-----------------+
```

上图概括了哈希集合定位元素的核心两步管道：首先由对象给出其哈希码，再由容器将哈希码压缩映射为数组下标。

回顾上一讲的核心机制：
1. **获取哈希码**：面对任意对象（一个字符串、一个数字，哪怕是一个海象对象 `Walrus`），我们走到它面前问：“喂，如果你是一个数字，你想成为哪一个？”对象返回一个整数，这就是它的哈希码（`hashCode`）。
2. **桶位置压缩**：哈希表拿这个数值输入缩减函数（通常是对桶总数 $M$ 取模），计算出它应该归属的桶编号。如果算出来是 0，只要该元素存在于集合中，它就必然位于 0 号桶。
3. **查找与插入**：带着目标对象直奔该桶，沿链表逐个比对即可完成查找或追加。

如果不进行扩容，最坏情况下的运行时间必然是线性的 $\Theta(N)$。即使散列分布得非常均匀，若只有 5 个桶却有 $N$ 个元素，每个桶平均也挤着 $N/5$ 个元素，遍历链表检查元素依然耗费 $\Theta(N)$。因此哈希表引入了**动态扩容机制**：一旦表内元素增多，就增加桶的数量，把每个桶内的平均元素数量压制在一个常数范围内，从而让查找和插入的平摊运行时间保持在优雅的 $\Theta(1)$。

上一讲 Josh 侧重于哈希表的工作原理与性能优势。今天我们要彻底换个方向：专门来看看**哈希表为什么会出错、会在哪里彻底崩溃**。

### 自定义哈希函数：从彩色数字的分布实验谈起

为了做实验，我们临时定义一种非常简单的对象——**彩色数字（ColoredNumber）**。这种对象包含两个属性：一个整数数值（`number`）和一种颜色（`color`）。

如果我们将一批彩色数字塞进一个固定包含 6 个桶的哈希集合中，它们在桶里的分布会是什么样子？

#### 默认哈希码：基于内存地址的伪随机分布

在 Java 中，如果你没有为自定义类显式重写 `hashCode()` 方法，对象的默认哈希码就是它在 Java 虚拟机中的**内存地址**（或者基于内存地址派生出的整数）。

```text
[桶 0] --> (蓝 18) -> (红 3)
[桶 1] --> (绿 12) -> (黄 7) -> (紫 1)
[桶 2] --> (红 9)  -> (蓝 4)
[桶 3] --> (橙 15)
[桶 4] --> (绿 2)  -> (紫 16) -> (蓝 10)
[桶 5] --> (黄 5)  -> (红 19)
```

上图展示了使用默认哈希码时，数据在 6 个桶中的典型分布：不同颜色的数字被打散混杂在各个桶中，整体分布相当均匀。

当我们在可视化界面中观察默认哈希码的表现时，可以注意到几个非常明显的现象：
- 同一个桶里会容纳不同颜色的数字；
- 元素没有全都挤在某一个桶里，各个桶的负载大致均衡；
- 数据看起来有一种近乎随机散落的分布特征。

这是因为内存地址在底层堆内存分配模型中本身就具备不可预测性。一个对象可能被分配在以 0 结尾的地址，另一个可能在以 5 结尾的地址。因此，Java 默认基于内存地址的散列分布效果其实出奇得好。

#### 极端对比：恒定返回零与按位数哈希

如果我们不喜欢默认行为，决定手动重写 `hashCode()`，会发生什么？

首先尝试一种极端的哈希函数：让它对任何对象都只返回常数 `0`。

```java
@Override
public int hashCode() {
    return 0;
}
```

当我们向每个数字询问它的哈希码时，无论是 15 还是 17，它们全都老老实实回答 `0`。

接下来哈希表对其执行取模：`0 % 6` 永远等于 `0`。结果所有元素争先恐后地涌入 0 号桶，链表长得直接溢出屏幕，而 1 到 5 号桶全部空置。从语法上讲，这是一个完全合法的哈希函数，程序能跑通，但它把哈希表的性能彻底打回了链表的单向遍历。

再换一种尝试：如果按数字的十进制长度（位数）作为哈希码呢？
一位数（如 0 到 9）的长度为 1，全部返回 1，塞进 1 号桶；两位数（如 10 到 99）的长度为 2，全部返回 2，塞进 2 号桶。其他桶依然处于饥饿状态。虽然理论上也能工作，但这种糟糕的散列度同样毫无实用价值。

#### 职责分离：对象与哈希表的明确分工

假设我们希望这批数字在 6 个桶里呈现出绝对规律的自然交替分布：0 号进 0 号桶，1 号进 1 号桶，2 号进 2 号桶……一直到 5 号进 5 号桶，接着 6 号又循环回到 0 号桶。

很多同学第一反应会写出这样的代码：

```java
// 错误的设计思路：在对象内部越权取模
@Override
public int hashCode() {
    return this.number % 6;
}
```

> **易错点**：**对桶数取模绝对不是对象自身的工作！**

彩色数字对象自身根本不应该知道、也无法知道外部的哈希表究竟配置了 6 个桶、10 个桶还是 20 个桶。这个对象可能根本没有存进哈希表，而是被放进了一棵二叉搜索树，或者只是一个独立存在的局部变量。

彩色数字的唯一责任，是如实提供能代表它自身状态的原始数值。

```java
// 正确的设计：对象只返回自身数值，保持职责纯粹
@Override
public int hashCode() {
    return this.number;
}
```

```text
+-----------------------+              +------------------------+
| 彩色数字 ColoredNumber |              |   哈希集合 HashSet     |
+-----------------------+              +------------------------+
| 职责：给出自身数值    |              | 职责：分配与管理容器   |
|   return this.number; |              |   index = hash % M;    |
| (对外部桶结构完全不知情)|              | (根据自身桶数组大小压缩)|
+-----------------------+              +------------------------+
```

上图阐述了职责分离架构：对象提供与容器无关的纯粹状态数值，容器内部依据自身规模负责位置映射。

把自身数值直接作为哈希码，既通用又优雅。当哈希表有 6 个桶时，哈希表自身去执行 `% 6`；当哈希表扩容到 12 个桶时，哈希表自身去执行 `% 12`。两者的权责必须划分得清清楚楚。

### 崩盘灾难之一：equals 与 hashCode 契约脱节

既然 Java 默认基于内存地址的哈希码分布得如此均匀，甚至比很多开发者自己胡乱写的哈希函数还要分散，我们为什么还要费劲巴拉地去重写 `hashCode()` 呢？

要回答这个问题，我们来看看哈希表是怎样由于一个小疏忽而彻底崩盘的。

#### 业务语义重写 equals

在面向对象设计中，我们经常根据业务逻辑重新定义两个对象何时被视为“相等”。

假设我们对 `ColoredNumber` 提出新的业务要求：**只要数值相同，我们就认定这两个数字相等，完全忽略它们的颜色差异**。红色的 12、蓝色的 12、粉色的 12，在逻辑层面上没有任何区别。

我们在类中重写 `equals()` 方法：

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    ColoredNumber that = (ColoredNumber) o;
    return this.number == that.number;
}
```

这段代码精准表达了我们的意图：只要 `this.number == that.number`，就返回 `true`。

但注意：此时我们**没有重写 `hashCode()`**，它依然遵循 Java 的默认规则——返回实例各自的内存地址。

#### 查询灾难：5/6 概率误报不存在

现在我们写一段看似天经地义的测试代码：

```java
HashSet<ColoredNumber> set = new HashSet<>();
// 循环添加 1 到 20 的彩色数字，内部创建的是蓝色数字实例
for (int i = 1; i <= 20; i++) {
    set.add(new ColoredNumber(i, Color.BLUE));
}

// 提问：集合中是否包含 12？
boolean result = set.contains(new ColoredNumber(12, Color.RED));
```

集合里明明刚刚添加了 1 到 20，其中必定包含数值为 12 的对象，而且 `equals()` 已经明确规定所有 12 都相等。按照常理，`set.contains(...)` 理应毫无悬念地返回 `true`。

然而运行这段代码，你会得到一个令人毛骨悚然的结果：**它有五分之六（约 83.3%）的概率返回 `false`，只有六分之一的概率侥幸返回 `true`！**

```text
[桶 0] --> (蓝 18)
[桶 1] --> (蓝 12, 内存地址 A, A%6 = 1) <=== 真正的 12 静静躺在这里！
[桶 2] --> (蓝 4)  <===================== 哈希表拿着红 12 (地址 B, B%6 = 2)
[桶 3] --> (蓝 15)                        直奔 2 号桶搜索，没找到 12，返回 false!
[桶 4] --> (蓝 2)
[桶 5] --> (蓝 5)
```

上图直观展示了查找穿透的根源：查询对象因内存地址不同，被错误分派到了不包含该元素的桶中。

背后的执行轨迹极其滑稽：
1. 循环添加时，程序通过 `new` 在堆中创建了蓝色的 12，它获得了一个内存地址 $A$。哈希表询问它的哈希码，得到 $A$，计算 $A \% 6$ 恰好等于 1，于是把蓝色 12 放进了 **1 号桶**。
2. 调用 `contains` 时，程序又执行了一次 `new`，在堆的另一个角落创建了红色的 12，它拥有完全不同的内存地址 $B$（例如 3002）。
3. 哈希表为了判断集合中是否包含红色的 12，必须先决定去哪个桶里搜寻。哈希表向红色的 12 询问哈希码，红色的 12 爆出了自己的内存地址 $B$。
4. 哈希表拿 $B$ 对 6 取模，假设算出来的结果是 2。
5. 哈希表一头扎进 **2 号桶**，顺着 2 号桶的链表挨个比对：“你是 12 吗？”2 号桶里放着的是 4 和 10，链表很快查到底，哈希表两手一摊：“2 号桶里根本没有 12！”于是毅然决然地返回了 `false`。

那为什么还会有 1/6 的概率返回 `true` 呢？那纯属撞大运——红 12 的随机内存地址 $B$ 对 6 取模，恰巧和蓝 12 的地址 $A$ 对 6 取模余数相同。如果哈希表有 1000 个桶，这种碰巧猜对的概率就会暴跌到 1/1000（99.9% 概率报错）。

系统明明有这个元素，你拿等价的钥匙去开门，它却斩钉截铁地告诉你东西不存在。这已经不是性能好坏的问题，而是程序逻辑发生了毁灭性误判。

#### 插入灾难：集合互异性彻底丧失

如果把 `contains` 换成 `add`，破坏力会进一步升级。

我们知道，集合（Set）最核心的数学特征就是**无序且元素互异（不允许重复）**。如果集合里已经有 0 了，再次添加 0 应该什么都不会发生。

```java
// 假设集合中已存在蓝色的 0
set.add(new ColoredNumber(0, Color.BLUE));

// 试图添加一个红色的 0
set.add(new ColoredNumber(0, Color.RED));
```

在执行 `add` 操作时，哈希集合内部的第一步同样是查重：先算出新对象的桶位置，进桶检查是否已有相等的对象，若有则拒绝加入，若无才挂上链表。

同样因为没有重写 `hashCode()`，红色的 0 拿着自己的新内存地址算出了错误的桶编号（比如 2 号桶）。哈希表跑到 2 号桶巡视一圈，发现里面没有 0，于是高高兴兴地把这个红色的 0 塞进了 2 号桶。

此时此刻，哈希集合内部同时存在了两个被 `equals()` 认定为完全相同的 0！集合的唯一性约束彻底被撕得粉碎。

#### 铁律：哈希契约的双向约束

> **结论**：**Java 哈希契约（Hash Code Contract）**
> 1. **相等必同码**：如果两个对象通过 `equals()` 判断为相等，那么它们调用 `hashCode()` 必须返回完全相同的整数值。
> 2. **重写必成对**：一旦你重写了类的 `equals()` 方法，就**必须**同时重写其 `hashCode()` 方法，确保等价对象的哈希码步调一致。
> 3. **同码未必等**：两个哈希码相同的对象并不一定相等（这属于正常的哈希冲突，哈希表会借助链表和 `equals()` 进一步甄别）。

当你把逻辑相等的对象映射到相同的哈希码后，不管在堆内存的哪个角落重新 `new` 出数值为 12 的实例，它都会稳定返回相同的哈希码，哈希表也因此永远被指引到唯一的正确桶中，上述的所有幽灵 BUG 瞬间烟消云散。

### 崩盘灾难之二：向集合存入可变对象并在外部修改

解决了 `equals` 与 `hashCode` 的成对重写，哈希表就高枕无忧了吗？并没有。

这里存在第二种更为隐蔽、更具摧毁性的崩溃方式：**把可变对象放入哈希结构，并在放入之后修改了它的内部状态**。

为了讲透这个灾难，我们需要先插播一个在面向对象体系中极易被混淆的核心概念——可变性与不可变性。

#### 不可变性的微妙边界与 final 的真面目

> **定义**：**不可变对象（Immutable Object）**
> 指的是该对象一旦在内存中构造完成，在其整个生命周期内，其外部可观察到的状态与数据**绝对无法以任何方式被改变**。

典型的不可变类型包括 Java 中的 `String`、`Integer` 以及各类基本类型的包装类。你手里的字符串哪怕只是拼接一个字符，底层也是在堆中生成一个全新的字符串对象返回，原有字符串稳如磐石。

如何设计一个不可变类？很多人脱口而出：“给字段加上 `final` 关键字！”

但事实是：**`final` 关键字对于实现不可变性，既非充分条件，也非必要条件！**

- **没有 `final` 也可以是不可变类**：如果一个类的字段全都是 `private` 的，而且没有向外暴露任何修改接口（没有 setter），在类内部也绝不在初始化后篡改它，那么即使字段没加 `final`，外部也完全无法修改它，它依然是坚不可摧的不可变对象。
- **加了 `final` 依然可能是可变类**：这是最容易踩坑的深水区。`final` 保证的仅仅是变量自身保存的数值或**内存引用地址不可变**，它根本管不着该引用所指向的对象内部内容！

为了彻底分清这里的微妙差别，我们对比以下四种岩石与盒子模型：

```java
// 模型 1：透明小石子（毫无争议的可变类）
public class Pebble {
    public int weight; // 字段公开，外部可任意修改
}

// 模型 2：实心大岩石（纯粹的不可变类）
public class Rock {
    private final int weight;
    public Rock(int weight) { this.weight = weight; }
    // 字段私有且为 final，无修改途径
}

// 模型 3：公开岩石盒（持有 final 引用的可变类）
public class RocksBox {
    public final Rock[] rocks; // 引用本身不能重定向，但数组元素可随意替换！
    public RocksBox(Rock[] rocks) { this.rocks = rocks; }
}

// 模型 4：秘密岩石盒（看似私有、实则泄漏引用的伪不可变类）
public class SecretRocksBox {
    private final Rock[] rocks;
    public SecretRocksBox(Rock[] rocks) {
        this.rocks = rocks; // 危险！直接接管外部传入的数组引用
    }
}
```

模型 1 和模型 2 显而易见。真正具有欺骗性的是模型 3 与模型 4：

对于模型 3（`RocksBox`），虽然 `rocks` 字段是 `final` 的，你无法执行 `rb.rocks = otherRocks;`，但你完全可以执行 `rb.rocks[0] = null;`。数组槽位里的内容被改变了，对象的状态自然被修改了。

对于模型 4（`SecretRocksBox`），外部虽然无法直接 `rb.rocks` 访问私有数组，但在创建盒子时，原数组引用是外部传进来的：

```text
外部调用者持有的引用 myRocks ──────┐
                                 │
                                 ▼
                         +-------------------+
                         | 堆中的 Rock 数组  |
                         | [0]: 10, [1]: 20  |
                         +-------------------+
                                 ▲
                                 │
SecretRocksBox 内部私有字段 rocks ──┘
```

上图清晰揭示了别名共享（Aliasing）：外部与内部持有指向同一底层数组的物理指针，使得私有封装被轻易绕过。

外部调用者只需要在自己的作用域里轻飘飘地写一行：
`myRocks[0] = new Rock(-999);`
`SecretRocksBox` 内部引以为傲的“秘密阵列”瞬间被暗中篡改，不可变性的承诺彻底告破。

要让它真正不可变，唯一的救赎是采用**防御性复制（Defensive Copy）**：

```java
public class SecureRocksBox {
    private final Rock[] rocks;
    public SecureRocksBox(Rock[] rocks) {
        // 在构造阶段彻底克隆一份全新独立的数组，切断外部任何潜在的操控黑手
        this.rocks = rocks.clone();
    }
}
```

防御性复制虽然耗费了一次内存分配与数据拷贝的开销，但换来了坚如磐石的状态安全性。

#### 现场推演：动态改变对象的哈希灾难

了解了可变性后，我们来看把可变对象放进哈希集合后，究竟会引发怎样震撼的灾难。

这次我们不再用基础数字，而是用大家非常熟悉的动态列表 `ArrayList<Integer>` 作为集合元素。

```java
HashSet<List<Integer>> set = new HashSet<>();

// 创建第一个列表：包含 [0, 1]
List<Integer> list1 = new ArrayList<>(List.of(0, 1));
// 在 Java 中，List 的哈希码根据其包含的每个元素递归计算，算得 hashCode 为 962
set.add(list1);

// 创建第二个列表：包含 [2, 3]
List<Integer> list2 = new ArrayList<>(List.of(2, 3));
// 算得 hashCode 为 1026
set.add(list2);
```

假设哈希表初始化了 4 个桶：
- `list1`：哈希码 $962$。$962 \% 4 = 2$。放入 **2 号桶**。
- `list2`：哈希码 $1026$。$1026 \% 4 = 2$。发生冲突，同样挂在 **2 号桶**。

到目前为止，一切运行平稳。紧接着，致命的代码登场了：

我们在外部拿到 `list1` 的引用，直接往里面追加一个数字 7：

```java
list1.add(7); // list1 的内容瞬间变成了 [0, 1, 7]
```

请注意：这个列表实例在内存中的位置没有动，引用的对象依然是它自身。但它的内部状态被修改了。

这一修改引发了连环雪崩：
1. **哈希码突变**：由于列表的 `hashCode()` 是基于其当前包含的所有元素即时计算的，包含 `[0, 1, 7]` 的列表的新哈希码骤变为了 **29829**。
2. **正确位置迁移**：按照新的哈希码，它应该归属的桶是 $29829 \% 4 = 1$ 号桶。
3. **空间错位停滞**：可是，哈希集合对此浑然不觉！哈希集合根本没有、也不可能长一双眼睛时刻监听堆中各个对象的内部字段变化。因此，`list1` 依然死死地卡在原来的 **2 号桶** 里！

```text
[桶 0] --> 空
[桶 1] --> 空  <==================================== contains([0, 1, 7]) 查此桶！
                                                     (29829 % 4 = 1，桶里为空，误报 false!)
[桶 2] --> (包含 [0, 1, 7] 的 list1) -> (list2: [2, 3]) <=== 实际对象卡在旧桶，沦为幽灵！
[桶 3] --> 空
```

上图展示了状态变更引发的致命空间错位：对象被修改后哈希值改变，但容器并未迁移该对象，导致新桶查不到、旧桶删不掉。

随后的调用将迎来毁灭性的崩溃：
- **查询直接丢失**：我们调用 `set.contains(list1)`，哈希表根据其当前状态算出哈希码 29829，直奔 1 号桶搜寻。1 号桶空空如也，哈希表理直气壮地返回 `false`！明明把这个对象传给了集合，集合却当面否认它的存在。
- **重复注入破坏**：如果我们此时调用 `set.add(list1)`，哈希表跑到 1 号桶查重，自然找不到它，于是顺利地把 `list1` 在 1 号桶又存了一份。同一个对象在同一个哈希表的不同桶里出现了多次。
- **无法正常删除**：调用 `set.remove(list1)` 会试图去 1 号桶定位并删除它，1 号桶没东西可删，返回失败；而卡在 2 号桶里的那个原始条目将永远无法通过正常途径移除，永久沦为内存泄漏的幽灵。

#### 规则：不可变键与设计防线

> **警告**：**哈希集合的元素、以及哈希映射的键（Key），绝对不能在存入后被修改！**

正因这一破坏是毁灭性的，不同的编程语言采取了不同的防范策略：
- **Python 的严苛防御**：在语言层面直接设立铁律。像 `list` 这种可变类型根本没有实现 `__hash__`，只要你试图拿列表作为字典的 key 或放进 set，解释器立刻抛出 `TypeError: unhashable type: 'list'`，直接在编译运行期掐死此类可能。
- **Java 的自由代价**：Java 允许各类集合类重写 `hashCode()` 并允许放进哈希表，它把自律的责任完全交给了开发者。一旦你在 Java 中犯了这类错误，编译器不会报任何警告，你只能在深夜面对各种偶发性丢失数据的幽灵 BUG 抓狂排查。

对于映射（Map）而言，只要**键（Key）保持不可变**，值（Value）是可以自由修改的。因为映射的桶定位、冲突排查全屏 Key 的哈希码驱动，Value 只是挂在节点上的附加数据载荷，它的变更不会对哈希表的内部拓扑产生丝毫扰乱。

### 工业级实现的真相与平均常数时间

在课程的最后，Josh 曾通过调试器打开过标准库的底层实现。实际工业级哈希表的工程复杂度，远超我们课堂上写的简易原型。

#### 工业级与教学原型的差异

以 Java 标准库的 `HashMap` 为例，其源码长度超过 2000 行。工业级实现之所以如此庞大，是因为它在底层做了大量的工程防御与性能榨取：
- **避免直接取模，采用位运算**：在标准库中，桶数组的长度 $M$ 始终严格保持为 2 的整数次幂（如 16, 32, 64...）。在此前提下，复杂的模运算被直接替换为极速的位与运算：`index = (capacity - 1) & hash`。
- **高位扰动混合（Hash Spreading）**：为了防止某些对象的哈希码仅有高位发生变化而低位完全雷同，工业实现会对哈希码进行位移与异或混合（`h ^ (h >>> 16)`），让高位的特征充分渗透到底位，确保在小规模容量下也能均匀铺开。
- **桶内冲突演进**：当单桶链表长度超过阈值（通常为 8）且表容量达到一定规模时，单链表会自动升级为红黑树（TreeNode），将最坏情况下的检索时间强行从 $\Theta(N)$ 压制回 $O(\log N)$。

#### 破解常数时间的迷思：平均恒定而非绝对均匀

很多人对“哈希表具备常数级运行时间 $\Theta(1)$”存在一个普遍的认知误区：以为理想的哈希表能做到每个桶里恰好有且仅有 1 个元素。

这在现实中是绝不可能的。散列本质上是一个概率分布过程。即使是最完美的哈希函数，在抛硬币式的散布下，也会出现泊松分布式的波动——必然有的桶是空的，有的桶有 1 个元素，有的桶则挤了 2 到 3 个元素。

```text
[桶 0] --> 空
[桶 1] --> (条目 A) -> (条目 B) -> (条目 C)
[桶 2] --> (条目 D)
[桶 3] --> 空
[桶 4] --> (条目 E) -> (条目 F)
```

上图展示了真实的哈希表局部状态：各桶元素数量自然起伏，常数级时间保障依赖的是控制平均负载因子。

我们所保证的常数级运行时间，指的是**平均桶负载的恒定**：

$$\text{负载因子 Load Factor } \lambda = \frac{N}{M}$$

在实际工程中，Java `HashMap` 默认将扩容阈值设为 $0.75$。也就是说，当表内元素总量达到总桶数的 75% 时，立即触发整体扩容将桶数翻倍，并把原有元素重新洗牌投影到新桶中。正是通过动态维持这种平均意义上的低负载，哈希表才最终兑现了平摊常数时间 $\Theta(1)$ 的承诺。

在本讲的推导与课堂互动中，提出了两道关于哈希表内部机理的即时推演谜题，其完整题干与技术解析整理如下：

#### equals 忽略颜色但保留默认哈希码时的 contains 行为

**题干**：
已知类 `ColoredNumber` 包含整数 `number` 与枚举 `color` 两个字段。重写其 `equals()` 方法为“只要 `number` 相等即认定两对象相等”，但**未重写** `hashCode()` 方法（保留返回自身内存地址的默认实现）。
现初始化一个拥有 6 个桶的哈希集合，向其中依次加入 1 到 20 的蓝色数字：
`for (int i = 1; i <= 20; i++) set.add(new ColoredNumber(i, Color.BLUE));`
随后执行查询：
`boolean found = set.contains(new ColoredNumber(12, Color.RED));`
请推演并说明：`found` 的运行结果及其概率分布是怎样的？

**答案**：
`found` 的运行结果具有非确定性：有 $5/6$ 的概率返回 `false`，仅有 $1/6$ 的概率返回 `true`。

**解析**：
1. 循环内插入的蓝色 12 在堆中拥有独立的内存地址 $A$。根据默认哈希码，$A \% 6$ 确定了它落入某个确定的桶（不妨设为 1 号桶）。
2. 查询时传入的红色 12 是新创建的独立实例，拥有全新的内存地址 $B$。
3. 哈希集合根据地址 $B$ 计算寻址桶：$B \% 6$ 的结果在 $0, 1, 2, 3, 4, 5$ 六个余数中伪随机分布。
4. 只有当 $B \% 6$ 恰好等于 1 时（概率为 $1/6$），哈希表才会前往 1 号桶，此时通过 `equals()` 能成功比对出匹配项并返回 `true`。
5. 在其余 5 个余数情况下（概率为 $5/6$），哈希表被错误引导至其他空桶或不含 12 的桶中，遍历后判定无该元素，因而错误地返回 `false`。

#### equals 忽略颜色但保留默认哈希码时的重复添加行为

**题干**：
在题目一的相同类定义与 6 桶哈希集合环境下，集合中已经存在数值为 0 的蓝色数字：
`set.add(new ColoredNumber(0, Color.BLUE));`
此时试图再次添加一个数值同样为 0 的红色数字：
`set.add(new ColoredNumber(0, Color.RED));`
请分析集合的实际内部状态变化（理论期望行为与实际发生行为的差异）。

**答案**：
- **理论期望**：集合应拦截重复元素，集合内应始终保持仅有一个数值为 0 的条目。
- **实际行为**：有 $5/6$ 的概率在不同的桶中强行插入重复的 0，破坏集合唯一性；仅有 $1/6$ 的概率成功查重并阻止重复添加。

**解析**：
1. 哈希集合执行 `add` 操作时，必须先在目标桶内执行链表扫描查重。
2. 新创建的红色 0 依据自身内存地址取模寻址。如果落入了已有蓝色 0 所处的同一个桶（概率为 $1/6$），扫描链表时调用 `equals()` 返回 `true`，查重生效，添加操作被正确忽略。
3. 若取模结果落入其余 5 个桶（概率为 $5/6$），由于那些桶里根本没有数值为 0 的条目，查重逻辑判定“该元素尚不存在”，从而在新的桶里追加该红色 0 节点。最终导致同一集合中并存了两个业务语义完全相同的对象。
