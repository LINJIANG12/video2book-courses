### 引入：从画一条水平线到构建整个世界

我们要做的这个大作业（Project 3 / 世界生成器），最终目标是生成一个由若干板块拼接而成的虚拟世界。今天我们要现场搭建的雏形，灵感来自大家熟悉的经典桌游《卡坦岛》（Settlers of Catan）。

在上次课里，我们其实已经做了一点准备工作：定义了一个基础的 `Hexagon` 类，里面包含左上角坐标 `x`、`y`、尺寸 `size` 以及地块类型等成员变量；同时还写好了一个底层辅助函数 `drawHorizontalLine`。为了验证这个基础工具是否管用，我们在一个 $40 \times 40$ 的空画布上画出了一排像锁着的门一样的测试线。

我们为什么要先画那条线？目的非常纯粹：在动手拼装大系统前，必须先验证最底层的基石确实存在、确实能跑通。

那么，怎样在一个由离散瓦片（Tile）构成的二维网格里画出一个正六边形？有人可能会直觉地想：先画出六条边框，再往里面填色。但这在网格世界里很不自然。最平实、最可靠的办法，是**水平扫描线法**——把六边形拆解成若干条并列的水平线段，自上而下一行一行画出来。

> **定义**：水平扫描线法（Horizontal Scanline Rendering）是一种将几何图形沿网格行切片、通过连续绘制单行水平像素线段来拼合出整体图形的光栅化策略。

### 战术决策：方法归属与纯函数之辩

现在我们要写绘制单个六边形的主体函数 `drawHexagon`。在敲下第一行代码前，面临两个很实在的设计抉择。

#### 方法该放哪儿

这个 `drawHexagon` 到底应该定义在 `Hexagon` 类里面，还是直接扔在包含 `main` 函数的主类（比如 `Lec31`）里？

这是个典型的**战术安排**（Tactical Decision）。如果放在主类里，它像是一个过程式的外部渲染脚本；如果放在 `Hexagon` 类里，对象就内聚了自身的渲染逻辑。这里我们先把它放在 `Hexagon` 类中：

```java
public class Hexagon {
    private int x;
    private int y;
    private int size;
    private TETile tile;

    // ... 构造函数与实例变量 ...

    public void drawHexagon(TETile[][] world) {
        // 核心绘制逻辑
    }
}
```

#### 原地修改还是返回全新副本

细看这个方法的签名：它的返回值是 `void`，直接接收一个二维瓦片数组 `world`，并在上面就地修改。

我们为什么不把它设计成返回一个全新副本的纯函数（Pure Function），即 `public TETile[][] drawHexagon(TETile[][] world)`？

- **纯函数的好处**：没有副作用（Side Effects），不修改传入的原对象，返回包含六边形的新世界快照，在并发推理与时态回溯时心智负担更低。
- **原地修改的好处**：内存开销极小。图形系统在本质上就是一个状态机，直接对画布做就地绘制最符合直觉，无需频繁分配和拷贝大型二维数组。

> **结论**：在图形与瓦片网格这种高频修改的场景下，原地修改（In-place Mutation）显著优于频繁克隆大数组。我们选择了非纯函数——用句自嘲的话说，大概因为我们本身也是不纯粹的人吧。

### 单个六边形的几何拆解与实验性编程

一个边长为 $s$（代码中的 `size`）的正六边形，在离散网格中的垂直总高度恰好是 $2s$ 行。我们自然地把它切成两半来处理：先画上半部分（$s$ 行），再画下半部分（$s$ 行）。

```text
        +---------------+      --- 第 0 行: 宽 s, 起点 (x, y)
       /                 \
      +-------------------+    --- 第 1 行: 宽 s + 2, 起点 (x - 1, y - 1)
     /                     \
    +-----------------------+  --- 第 s - 1 行: 宽 3s - 2 (上半部最宽处)
    +-----------------------+  --- 下半部第 0 行: 宽 3s - 2 (镜像衔接)
     \                     /
      +-------------------+    --- 下半部第 1 行: 宽 3s - 4
       \                 /
        +---------------+      --- 下半部第 s - 1 行: 宽 s
```
*读图说明：边长为 $s$ 的六边形拆分为上下各 $s$ 行。上半部每向下移动一行，宽度增加 2，起点 X 向左平移 1；下半部则逐行向内收缩 2，起点 X 逐行向右回缩 1。*

#### 上半部分的几何推导与参数规律

设行号 `rowNum` 从 $0$ 递增到 $s - 1$：
1. **第 0 行**：起点位于左上角顶点 $(x, y)$，线段长度恰好为 $s$；
2. **第 1 行**：向下一行，左右两侧各外扩 1 个格点，因此左边界向左移 1 位，起点变为 $(x - 1, y - 1)$，线段长度变为 $s + 2$；
3. **第 $r$ 行**：依此类推，起点 X 坐标为 $x - r$，Y 坐标为 $y - r$（假设网格 Y 轴向下递增或按世界坐标自顶向下计算），线段长度为 $s + 2r$。

```java
for (int rowNum = 0; rowNum < size; rowNum++) {
    int startX = this.x - rowNum;
    int startY = this.y - rowNum;
    int length = this.size + 2 * rowNum;
    drawHorizontalLine(world, startX, startY, length, this.tile);
}
```

这就是典型的**实验性编程**（Empirical Programming）。遇到几何规律时，不要一开始就陷入复杂的全局数学证明里拔不出来；拿张纸画两笔，把第 0 行、第 1 行的数字列出来，模式（Pattern）自己就会跳到你眼前。

#### 现场调试实录：自赋值 Bug 与参数偏移定位法

写完上半部分一跑，屏幕上一片空白，什么都没渲染出来。

六边形跑哪儿去了？我把调用点放进主类测试，发现控制台没有报错，但在画布极底部隐隐约约有一截残影。这时候别慌，这里分享一个我极其常用的现场调试策略：**参数偏移探测法**。

我故意在绘制调用的 X 和 Y 参数上各加上一个偏移量（比如 `+ 5`），然后重新运行：
- 如果画面上的线往右移了，说明 X 坐标通道是通的；
- 如果画面上的线往上移了，说明 Y 坐标也在响应。

顺着这个线索回头看 `Hexagon` 的构造函数，IDE 实际上已经给出了浅色高亮警告：

```java
// 错误示范：手误自赋值
public Hexagon(int x, int y, int size, TETile tile) {
    x = x;
    y = y; // 警告：Assignment to itself! this.y 依然是默认值 0
    this.size = size;
    this.tile = tile;
}
```

> **易错点**：当参数名与实例变量重名时，遗漏 `this.` 会导致参数被赋值给自己（No-op），导致实例变量停留在默认初始值（`0`）。这种笔误不会引发编译报错，却会导致几何图形直接掉落到世界原点。

修正为 `this.x = x; this.y = y;` 后，上半部分立刻在正确的位置显现了出来。

#### 下半部分的收缩逻辑与叙事性代码

上半部分搞定后，下半部分是向内收缩的镜像过程。行数同样是 $s$ 行，起点宽度为最大宽度，然后逐行向内收缩 2。

这里有两种截然不同的写法：

**风格 A：过度追求紧凑的“聪明代码”**
```java
// 试图用单重循环与条件极性翻转强行拼凑
for (int i = 0; i < size; i++) {
    drawHorizontalLine(world, x - (size - 1) + i, y - size - i, (3 * size - 2) - 2 * i, tile);
}
```
这种写法充斥着多重负号与双重否定，一眼看过去极难核对索引界限，稍微漏写一个 `- 1` 就会导致边界错位。

**风格 B：具叙事性的清晰代码（Narrative Code）**
我更推崇的做法是引入几个具有明确语义的局部变量作为“逻辑钩子”（Hook）：

```java
int firstX = this.x - (this.size - 1);
int firstY = this.y - this.size;
int firstLength = 3 * this.size - 2;

for (int rowNum = 0; rowNum < this.size; rowNum++) {
    int startX = firstX + rowNum;
    int startY = firstY - rowNum;
    int length = firstLength - 2 * rowNum;
    drawHorizontalLine(world, startX, startY, length, this.tile);
}
```

有人会问：“这样多定义了三个变量，内存不会增加吗？”
会，但多占了几个字节的栈帧空间。都 2025 年了，谁在乎这点内存？
代码清晰地表达了起点的基准位置以及每一行的递推规律。这种具备**叙事性**的代码，无论是现场排查还是几个月后回来重构，心智负担都远低于那些看似高深晦涩的单行技巧。

在测试下半部分时，换几个尺寸（如 $s=3, 4, 5$）跑一下，验证最宽处的边界公式是否恒为 $3s - 2$。验证通过后，单个六边形的渲染就彻底稳固了。

### 蜂窝世界的列生成与拓扑咬合

单个六边形画好后，我们要把它们组合成完整的世界。卡坦岛的经典地图由 19 个六边形拼成，呈蜂窝状交错排列，各列包含的六边形数量为固定的 **3-4-5-4-3**。

```text
       列0      列1      列2      列3      列4
      (3个)    (4个)    (5个)    (4个)    (3个)

                         [H]
                [H]               [H]
       [H]               [H]               [H]
                [H]               [H]
       [H]               [H]               [H]
                [H]               [H]
       [H]               [H]               [H]
                [H]               [H]
                         [H]
```
*读图说明：整个世界分为 5 列，六边形数量从左至右依次为 3、4、5、4、3。相邻列之间上下错开半个六边形的高度，形成交错锁定的正六边形蜂窝结构。*

#### 列绘制抽象与同列垂直步长

不要硬编码去一个个算 19 个六边形的绝对坐标。最自然的抽象是提炼出一个绘制单列六边形的辅助函数：

```java
public static void drawHexagonColumn(TETile[][] world, int startX, int startY, 
                                    int size, int numHexagons, TETile tile) {
    for (int i = 0; i < numHexagons; i++) {
        int hexY = startY - i * (2 * size);
        Hexagon hex = new Hexagon(startX, hexY, size, tile);
        hex.drawHexagon(world);
    }
}
```

> **推导**：因为单个边长为 $s$ 的六边形垂直高度为 $2s$，所以同列中紧密相邻的下一个六边形，其 Y 坐标步长恰好递减 $2s$。

#### 3-4-5-4-3 结构的相邻列平移与错位

相邻列之间该如何咬合？我们需要计算两列之间的横向（X 偏移）与纵向（Y 偏移）：

1. **横向偏移（$\Delta X$）**：一个边长为 $s$ 的六边形，顶部平边宽 $s$，斜边在 X 轴的投影宽为 $s - 1$。为了让相邻列的边缘贴合，列与列之间的 X 轴间距为：
   $$\Delta X = 2s - 1$$
2. **纵向偏移（$\Delta Y$）**：为了让蜂窝完美镶嵌，相邻列的垂直起始位置必须错开半个六边形的高度，即向上或向下错位：
   $$\Delta Y = s$$

于是，只要确定最左侧列（列 0）的起始坐标 $(x_0, y_0)$，后续各列的起始锚点便可完全由几何步长推导出来：
- 列 0（3 个）：起点 $(x_0, y_0)$
- 列 1（4 个）：起点 $(x_0 + \Delta X, y_0 + s)$
- 列 2（5 个）：起点 $(x_0 + 2\Delta X, y_0 + 2s)$
- 列 3（4 个）：起点 $(x_0 + 3\Delta X, y_0 + s)$
- 列 4（3 个）：起点 $(x_0 + 4\Delta X, y_0)$

#### 边界溢出与常量提取重构

在现场将六边形列拼接到第 5 列时，程序突然抛出 `ArrayIndexOutOfBoundsException` 崩溃了。原因很简单：六边形群超出了原先设定的窗口边界。

在调整画布大小时，代码里散落着好几个手写的 `40` 或 `45`。如果你发现自己需要去修改多处相同的数字常量，**为了你自己的心理健康，立刻把它们提取为私有静态常量**：

```java
private static final int WIDTH = 50;
private static final int HEIGHT = 50;
```

> **注意**：散弹式修改（Shotgun Surgery）是极易引入低级缺陷的代码坏味道。凡是具有全局约束含义的尺寸、边界参数，必须收拢到单一常量源头，严禁在业务逻辑中散落硬编码魔数。

### 让世界更有生机：随机地形与视觉变体

整张地图全是同一种单调的树木或草地会显得很呆板。我们需要引入**随机生物群系**（Random Biomes）与**视觉细节修饰**。

#### 随机生物群系的分发

我们从项目规范要求的 5 种核心地形中进行等概率抽取：山脉（MOUNTAIN）、森林（TREE）、草地（GRASS）、花朵（FLOWER）和沙地（SAND）。

利用伪随机数生成器产生 $0 \sim 4$ 之间的整数，并通过 `switch` 语句完成地块映射：

```java
Random rand = new Random(seed);
int biomeNum = rand.nextInt(5);
TETile chosenTile;

switch (biomeNum) {
    case 0:  chosenTile = Tileset.MOUNTAIN; break;
    case 1:  chosenTile = Tileset.TREE;     break;
    case 2:  chosenTile = Tileset.GRASS;    break;
    case 3:  chosenTile = Tileset.FLOWER;   break;
    case 4:  chosenTile = Tileset.SAND;     break;
    default: chosenTile = Tileset.NOTHING;  break;
}
```

#### 颜色变体技巧：消除机械重复感

即使铺满了草地，如果每个格子的绿都分毫不差，画面看起来依然充满廉价的塑料感。这里有一个非常酷的小技巧：利用瓦片库提供的 `colorVariant` 方法。

```java
// 为同一种瓦片注入最大偏差为 30 的随机 RGB 扰动
TETile texturedMountain = TETile.colorVariant(Tileset.MOUNTAIN, 30, 30, 30, rand);
```

它允许在给定的基准色上，对 R、G、B 通道施加微小的随机浮动。同样是山脉，有的深青，有的偏灰，蜂窝世界的质感瞬间就跃然纸上。

### 第二阶段预演：键盘交互与自由移动

把世界生成出来只是大作业的前半段；后半段的核心是**交互**——让玩家操控一个角色（Avatar）在世界里自由走动。

#### 游戏主循环与事件驱动渲染

我们用字符 `@`（`Tileset.AVATAR`）代表玩家，设定初始位置为 $(25, 25)$，并建立一个经典的游戏主循环：

```java
int playerX = 25;
int playerY = 25;
world[playerX][playerY] = Tileset.AVATAR;

while (true) {
    if (StdDraw.hasNextKeyTyped()) {
        char c = Character.toLowerCase(StdDraw.nextKeyTyped());
        if (c == 'w') { playerY += 1; }
        else if (c == 's') { playerY -= 1; }
        else if (c == 'a') { playerX -= 1; }
        else if (c == 'd') { playerX += 1; }

        // 仅在状态改变时重新渲染世界，避免无谓空转
        ter.renderFrame(world);
    }
}
```

> **提示**：只在捕获到有效按键输入后才触发重绘。如果无条件每帧全屏刷新，不仅浪费 CPU 算力，还会导致画面出现高频闪烁。

#### 留痕 Bug：当主角把草地踩成自己

跑起这段代码，按 W-A-S-D 移动角色，马上就暴露出一个滑稽的 Bug：角色移动过的地方，留下了一长串 `@` 符号，像贪吃蛇一样无法消除。

为什么会这样？因为我们的移动逻辑直接把新位置强行赋值为了 `AVATAR`，而旧位置根本没有复原！

现场一个最直接的修补方式是引入 `previousTile` 变量，记录主角当前踩在脚下的瓦片：

```java
TETile previousTile = world[playerX][playerY];

while (true) {
    if (StdDraw.hasNextKeyTyped()) {
        char c = Character.toLowerCase(StdDraw.nextKeyTyped());
        
        // 1. 离开旧位置前，将原本的瓦片还原回去
        world[playerX][playerY] = previousTile;
        
        // 2. 更新坐标
        if (c == 'w') { playerY += 1; }
        // ... 其他方向 ...
        
        // 3. 记录新位置原本的瓦片，再把主角画上去
        previousTile = world[playerX][playerY];
        world[playerX][playerY] = Tileset.AVATAR;
        
        ter.renderFrame(world);
    }
}
```

这样一改，主角就能自由穿行于山川花草之间，且身后不再留痕。

### 软件工程反思：数据结构的缺失与复杂度根源

刚才那段能够自由移动的演示，表面上看功能齐全，但在严谨的软件工程视角下，它散发着极其强烈的**代码坏味道**（Code Smells）。

#### 领域模型丢失的代价

我们刚才到底干了什么？
我们在 `drawHexagonColumn` 里创建了一堆 `Hexagon` 对象，把它们画到二维数组里，然后……**立刻把这些对象全扔了！**

这意味着什么？意味着在世界生成完毕的那一瞬间，整个系统里的“六边形”概念彻底灰飞烟灭了。真实的世界状态，仅仅退化成了一个没有任何语义的平面像素矩阵 `TETile[50][50]`。

如果后续策划提出新需求：
- “玩家使用炸弹道具，摧毁当前所在的这片六边形草地”；
- “在特定两个六边形之间打通一条隐藏走廊”；
- “判断玩家当前位于哪个房间”。

这时候你该怎么办？因为你没有保留六边形对象，你必须从主角当前的坐标出发，用极其痛苦的逆向几何算法去重新推算该六边形的中心和外沿边界！

> **核心教训**：**图纸不是建筑本身，瓦片画布不是领域模型。**在生成阶段创建的高阶实体（房间、走廊、六边形板块），必须沉淀到专门的数据结构（如列表、树或图）中长久保存。

#### 单元测试的边界

有同学提到：“老师，咱们写写单元测试吧。”
我的回答很坦诚：对于画六边形这种强依赖 GUI 输出的代码，写单元测试往往性价比极低，甚至是在浪费时间。你很难用 Assert 去断言屏幕上画出的一簇像素看着“舒服不舒服”。

但是，当你的世界生成算法包含复杂的**纯逻辑不变量**（例如六边形最宽行公式必须恒等于 $3s - 2$、走廊必须连通所有房间且无环、迷宫生成算法的图连通性），单元测试就是神兵利器。**把无副作用的纯计算逻辑从 GUI 渲染中剥离出来单独测试**，是大型项目得以平稳重构的底气。

#### Ousterhout 复杂性理论：依赖性与晦涩性

在 John Ousterhout 教授的经典著作《A Philosophy of Software Design》（软件设计哲学）中，他对系统**复杂度**（Complexity）给出了极其精辟的定义：
> **定义**：复杂度是系统任何使得它难以被理解和难以被修改的内部结构特征。

复杂度并非凭空产生，它主要来自两大根源：

```text
                     +---------------------------------------+
                     |           系统复杂度的两大根源          |
                     +---------------------------------------+
                                    /         \
                                   /           \
        +----------------------------+       +----------------------------+
        |   依赖性 (Dependencies)     |       |    晦涩性 (Obscurity)      |
        +----------------------------+       +----------------------------+
        | 某处代码的修改必须牵扯      |       | 关键信息在表面上不可见，   |
        | 另一处代码的同步变更；      |       | 充满魔数与不直观命名，     |
        | 执行顺序产生隐式强耦合。    |       | 意图完全被底层细节掩盖。   |
        +----------------------------+       +----------------------------+
```

看看往届同学在写大作业自由移动与碰撞检测时写出的失控代码：

```java
// 典型反面教材：充斥着依赖性与晦涩性的代码
if (c == 'a') {
    if (world[playerX - 1][playerY] != Tileset.WALL && world[playerX - 1][playerY] != Tileset.LOCKED_DOOR) {
        if (world[playerX - 1][playerY + 1 - 1] != Tileset.MOUNTAIN) {
            oldFloor = world[playerX][playerY];
            playerX = playerX - 1;
            world[playerX][playerY] = Tileset.AVATAR;
            // 一旦漏掉一个减一，或者顺序颠倒，角色就会直接穿墙跌出世界
        }
    }
}
```

这段代码精准踩中了这两个大坑：
1. **晦涩性**：满屏的 `[playerX - 1][playerY + 1 - 1]`，你完全看不出它是在向西移动、在做碰撞检测、还是在做边界试探。魔数与粗糙的坐标算式掩盖了设计意图。
2. **依赖性**：坐标更新、原地面恢复、碰撞判定这三件事被死死捆绑在一个 `if` 梯子里。一旦上下两个操作的顺序搞错，就会发生幽灵穿墙或永久吃掉地块的恶性 Bug。

在这门课的大作业中，你们将要构建的世界比这个六边形复杂得多——包含随机房间、走廊、墙壁与丰富的互动机制。做这个项目时，遇到 Bug 千万别像那只钻进死角出不来的狗一样，在一个坏设计上盲目打补丁、越钻越深。

感到别扭时立刻停下来，审视你的数据结构，把隐式依赖拆解开，消灭晦涩的代码，重构成干净、直观、具叙事性的接口。保持敏捷，享受创造世界的乐趣。
