## 双向链表与基础数组列表
> 对应块：BLK05 | 覆盖分集：P08 | 块标题（分集名）：《[61B FA25] 第5讲 - 双链表与基础数》

我们在前面的课程中探讨了如何将递归定义的裸链表结构（`IntList`）一步步重构为更稳固、更具工业级水准的列表类（`SLList`）。在那个版本中，我们为链表封装了私有变量、引入了哨兵节点（`sentinel`）来消除针对空链表的特殊情况分支，并且维护了 `size` 属性以实现常数时间的长度查询。我们实现了 `addFirst`、`getFirst`、`addLast` 和 `size` 四个核心方法。

但这还远远谈不上完美。只要你动手分析过现有代码的性能，就会发现一个严重的性能痛点：`addFirst` 可以在极短时间内完成，因为它只需找到哨兵节点并在其身后挂上新节点；然而 `addLast` 却慢得多，我们必须从哨兵开始，沿着 `next` 指针一个个节点往后走，直到遍历完整个链表才能完成末尾插入。今天，我们就要直面这一痛点，彻底解决链表两端的操作效率问题，并随后探讨一种截然不同的列表实现思路——基于数组的列表。

### 从单向链表到双向链表

#### 尾部追加与移除的性能困境

既然 `addLast` 需要遍历整个链表，一个极其自然的想法立刻涌现出来：我们为什么不在链表类中额外维护一个名为 `last` 的指针，直接缓存末尾节点的引用？

有了 `last` 之后，在链表末尾追加新元素确实变得轻而易举。我们无需再从头遍历，只要让当前 `last` 所指向节点的 `next` 指向新节点，再把 `last` 指针更新为新节点即可。同时，获取最后一个元素的 `getLast` 也可以直接通过 `last` 指针一步到位。

但问题来了：如果我们还需要支持 `removeLast`（删除末尾元素），这个 `last` 指针还能帮我们维持常数级别的高效吗？

直觉上，很多人会觉得既然握有 `last` 指针，顺着它把末尾节点删掉不就完事了？然而仔细推演一下内存中的指针操作，结果会非常反直觉。要从链表中真正剥离末尾节点，我们必须做到两件事：
第一，找到末尾节点的前驱节点（倒数第二个节点），将其 `next` 指针置为 `null`；
第二，将链表自身的 `last` 指针重新指向这个倒数第二个节点。

```text
单向链表删除末尾节点的困境：

sentinel --> [ 5 ] --> [ 3 ] --> [ 9 ] (倒数第二节点) --> [ 50 ] (末尾节点)
                                  ^                          ^
                                  |                          |
                             如何反向找到？               last 指针
```

读图说明：握有 `last` 只能定位到节点 `[ 50 ]`，但单向链表的指针全部单向朝右，根本无法反向回溯到节点 `[ 9 ]`。

为了把节点 `[ 9 ]` 的 `next` 设为 `null` 并将 `last` 移到 `[ 9 ]`，我们不得不再一次从头节点开始，顺着链表从头一路扫描到倒数第二位。如果链表有一百万个节点，删除末尾节点就得遍历九十九万九千九百九十九次！

有人可能会提议：那为什么不干脆再加一个 `secondToLast` 指针，直接缓存倒数第二个节点？
答案显而易见：一旦删除了末尾节点，你立刻就需要知道倒数第三个节点在哪里，以便更新新的 `secondToLast`；难道我们还要接着维护 `thirdToLast`、`fourthToLast` 指针吗？这显然会陷入无限套娃的死胡同。

> **结论**：单向指针的单向性决定了“向后查找”的廉价与“向前回溯”的昂贵。只在单向链表末尾加指针，无法使末尾删除操作摆脱 $O(N)$ 的遍历宿命。

#### 引入反向指针与双向链表

要让末尾元素的删除同样达到极致的速度，唯一的出路是重构链表节点的拓扑结构：让链表中的每一个节点不仅拥有指向后继者的 `next` 指针，还拥有指向前驱者的 `prev` 指针。

```text
双向链表节点拓扑结构：

             +------+               +------+
  ... <====  | prev |  <=========   | prev |
             +------+               +------+
             | item |               | item |
             +------+               +------+
             | next |  =========>   | next |  ====> ...
             +------+               +------+
```

读图说明：每个节点均具备前驱与后继双向连接，任意节点均可沿 `prev` 在 $O(1)$ 时间内反向访问其前驱。

这就是**双向链表（Doubly Linked List, DLList）**。在这里必须澄清一个初学者容易误解的细节：当我们画指针指向一个节点时，指针引用的是这块完整的节点对象内存，而不是钻进节点内部单独指向里面的某个数据值（比如数字 9）。

有了 `prev` 反向指针之后，链表两端的操作终于实现了完全的对称与飞速执行。当我们要执行 `removeLast` 时，直接通过 `last.prev` 就能瞬时获取倒数第二个节点，两步指针修正即可将末尾节点彻底断开。

### 哨兵节点的演进设计

#### 双哨兵方案的利弊

既然双向链表有了头尾两个操作热点，空的双向链表应该长成什么样？

如果我们依然沿用朴素的设计，链表内部会包含一个 `sentinel` 引用和一个 `last` 引用。但在链表为空时，`last` 应该指向哨兵还是 `null`？当链表只有一个元素时，`last` 又该如何迁移？
这会导致 `last` 指针在运行过程中身份模糊：有时候它指向的是虚构的哨兵节点，有时候指向的却是承载有效数据的真实节点。这种模糊性会逼迫我们在编写 `addLast`、`removeLast` 时充斥大量的 `if-else` 分支去特判各种边界状态，稍有不慎就会抛出空指针异常。

为了避免这种认知负担，我们可以采取方案一：在链表的前后两端各设立一个固定的哨兵节点——头部哨兵（`sentinelHead`）与尾部哨兵（`sentinelTail`）。

```text
双哨兵双向链表结构：

[ sentinelHead ] <=========> [ Node 1 ] <=========> [ Node 2 ] <=========> [ sentinelTail ]
```

读图说明：数据节点被稳稳夹在两个哨兵之间，头指针永远指向头哨兵，尾指针永远指向尾哨兵。

这种方案在逻辑上非常清晰，两端操作完全一致，彻底消除了针对“链表是否为空”的条件判断。但它的代价是需要同时维护两个孤立的哨兵节点对象，在初始化和指针连接时略显冗余。

#### 循环单哨兵的对称之美

是否存在一种在数学上更为纯粹、更为优雅的解法？
答案是：只保留一个哨兵节点，并将其两端首尾相接，构成**循环单哨兵结构（Circular Sentinel）**。

在循环单哨兵模型中，当链表处于完全为空的状态时，哨兵节点的 `next` 指针和 `prev` 指针同时指向它自己。这就像一种万物归一的数学顿悟：空即是闭环。

```text
空链表状态下的循环单哨兵：

         +-------------------------------+
         |                               |
         v                               |
     +-------+                           |
     | prev  | --------------------------+
     +-------+
     | item  |  (哨兵占位值)
     +-------+
     | next  | --------------------------+
     +-------+                           |
         ^                               |
         |                               |
         +-------------------------------+
```

读图说明：在空链表状态下，哨兵的 `prev` 和 `next` 均指回自身，链表天然闭合且没有任何悬空空指针。

当链表被填入真实数据后，这种结构的优美性展现得淋漓尽致：
- 哨兵节点的 `next` 永远精准指向链表的**第一个有效节点（First）**；
- 哨兵节点的 `prev` 永远精准指向链表的**最后一个有效节点（Last）**。

```text
含两个元素的循环单哨兵双向链表：

        +-------------------------------------------------------+
        |                                                       |
        |    +=============================================+    |
        |    |                                             |    |
        v    v                                             |    |
     +----------+           +----------+           +----------+ |
     | sentinel | <=======> |  Node A  | <=======> |  Node B  | |
     +----------+           +----------+           +----------+ |
        |    |                                             ^    ^
        |    +=============================================+    |
        |                                                       |
        +-------------------------------------------------------+
```

读图说明：`sentinel.next` 为首节点 `Node A`，`sentinel.prev` 为末节点 `Node B`；首节点的 `prev` 指回 `sentinel`，末节点的 `next` 同样指回 `sentinel`。

> **结论**：循环单哨兵设计用单个对象实现了完美的环形拓扑。在这一结构下，无论是头部插入、头部删除、尾部插入还是尾部删除，其底层指针链接规则完全统一，无需编写任何一条针对“空链表”或“单元素链表”的特判分支。

### 泛型改造与静态关键字的困惑

#### 类型占位符与包装类限制

此前实现的链表都只能存储整数（`int`）。如果我们想要一个能存字符串（`String`）或者任意自定义对象的通用列表，就必须引入 Java 的**泛型（Generics）**机制。

在定义泛型类时，我们在类名后追加一对尖括号。在尖括号内可以填入任何合法的标识符作为类型占位符。大多数教材和作业习惯使用单字母 `T` 或 `Item`，但为了向大家证明它绝不是什么系统内置的神秘关键字，我们可以随性地把它写成 `Camel`（骆驼）：

```java
public class SLList<Camel> {
    private class Node {
        public Camel item;
        public Node next;

        public Node(Camel i, Node n) {
            item = i;
            next = n;
        }
    }

    private Node sentinel;
    private int size;
    // ...
}
```

在外部使用这个泛型类声明和实例化对象时，语法规则如下：

```java
SLList<String> s1 = new SLList<>();
s1.addFirst("hello");
```

但在处理基础类型时，Java 的类型系统展现出了它的历史包袱：我们不能写 `SLList<int>`，而必须使用对应的包装类 `SLList<Integer>`。
这是由于 Java 在底层实现泛型时采用的类型擦除与对象内存模型决定的。Java 社区为了让泛型能够直接接纳原始基本类型（例如写 `List<int>` 而非包装对象），启动了长达十余年的底层重构探索（著名的 Project Valhalla）。在我们目前的实际编程中，直接记住基本类型必须使用大写包装类即可。

#### 静态内部类与泛型作用域冲突

在将节点类嵌套到外部列表内部时，往往会遭遇一个令人困惑的编译报错。此前我们曾提到过：如果内部类没有使用外部类的成员变量，最好将其声明为 `static`（静态内部类），以避免内部节点隐式持有外部类实例的引用，从而节约内存。

然而，一旦我们将外部类改造为泛型类 `SLList<Camel>`，如果内部节点类依然保留 `static` 修饰：

```java
public class SLList<Camel> {
    private static class Node {
        public Camel item; // 编译报错：无法从静态上下文中引用非静态类型变量 Camel
        public Node next;
    }
}
```

编译器会立刻报错：`cannot be referenced from a static context`。
原因在于：静态成员属于类本身，在概念上独立于任何具体的实例化对象；而泛型类型形参 `Camel` 是在外部类被具体实例化（例如 `new SLList<String>()`）时才确立的。静态内部类脱离了具体的外部类实例上下文，自然无从知晓 `Camel` 到底代表何种具体类型。

> **提示**：在编写课程的第一个大作业（Project 1）时，最稳妥、最直截了当的解法就是直接去掉内部节点类的 `static` 修饰符，将其作为非静态内部类。虽然这会让每个节点在内存中略微多占一点用于链接外部类的空间，但能直接避开复杂的嵌套泛型语法。

#### 静态关键字的多义性过载

初学者在接触 Java 时，常常会对 `static` 这个词产生由衷的紧张与困惑。这种感觉完全正常，因为 Java 语言在设计上让 `static` 这一个词承担了三种截然不同的语义角色：

| 语义场景 | 具体体现 | 核心含义 |
| :--- | :--- | :--- |
| **静态成员** | 静态变量 / 静态方法 | 属于类本身而非具体实例，由所有实例共享 |
| **静态嵌套类** | `static class Node` | 独立嵌套于外部类中，无法直接访问外部类实例的作用域 |
| **静态类型系统** | 静态类型语言（Static Typing） | 变量类型在编译期静态确定，不同于动态语言的运行时推断 |

由于同一个词汇被严重“词义过载（Overloaded）”，大家在阅读报错信息时极易产生混淆。现阶段无需深究语言规范的咬文嚼字，只要在做项目时遵循工程实用原则即可。

### 链表的局限与转向数组

#### 任意位置访问的成本鸿沟

通过双向循环哨兵链表，我们在数据结构的两端构建了极其高效的防线：`addFirst`、`removeFirst`、`addLast`、`removeLast` 全部都在 $O(1)$ 常数时间内完成。

然而，链表结构存在着一个不可调和的原生缺陷：**无法高效实现按索引随机访问的 `get(i)` 操作**。

假设链表中有成千上万个节点，现在我们需要取出中间位置（例如索引值刚好处于正中间）的元素。无论我们是从头部的 `sentinel.next` 出发向后爬行，还是从尾部的 `sentinel.prev` 出发向前倒退，我们都必须沿着指针链条一个节点一个节点地跳转。查找目标离两端越远，跳转的次数就越多，其访问耗时随着位置距离呈线性增长。

虽然学术界和工程界演化出过各种针对链表随机访问的补丁方案——例如在链表正中额外维护指针、增加跳表（Skip List）的远距离跳跃链接等——但这些方案往往伴随着极高的结构复杂度与维护成本。面对任意随机访问的需求，最纯粹的解法不是继续在链表上缝补，而是彻底更换底层的数据组织载体——**数组（Array）**。

#### 数组列表与链表的性能权衡

当我们在 Python 中使用内置的列表（`list`）并调用 `append()` 时，很多初学者会以为底层是链表。事实恰恰相反：Python 的列表底层就是基于数组构建的列表结构（类似于 Java 的 `ArrayList`）。

这带来了一种极其鲜明的性能取舍与权衡：
- **随机读取任意索引 `get(i)`**：基于数组的列表可以在瞬时完成，耗时与索引位置无关；而链表必须步步寻径。
- **列表头部追加 `addFirst(x)`**：双向链表只需修改四个指针引用即可在瞬时完成；而 Python 的基于数组的列表为了在索引 0 处塞入新数据，必须将现有的一整批元素全部往后挪动一格，耗时极其沉重。

> **结论**：没有绝对通吃一切场景的万能数据结构。你在 Project 1 中亲手打造的双向循环链表，在头部连续插入元素的基准测试中，性能可以轻而易举地击败 Python 的原生列表；但在中间索引的任意读取上，基于数组的结构拥有无法撼动的物理优势。

### 数组的底层物理机制

#### 内存盒子与编号索引

在底层思考数据结构，最贴切的模型就是“**内存盒子**”。
在 Java 中，我们声明一个基础类型变量（如 `int x`），系统就会分配一个 32 位的内存盒子；声明一个对象引用变量，系统就分配一个 64 位的盒子用于存放对象在内存中的地址。
当我们通过 `new` 实例化一个类对象时，系统会在堆上开辟一块连续内存，其中包含若干个**有名字的内存单元**（即对象的各个属性，例如海象对象的重量与象牙长度）。

而数组与类对象有着本质区别：数组是一系列**带有数字编号的连续内存单元**。

```text
数组在连续内存中的线性排布：

物理基地址 0x1000
    |
    v
+---------+---------+---------+---------+---------+
| [0] 32b | [1] 32b | [2] 32b | [3] 32b | [4] 32b |  (每个槽位大小完全一致)
+---------+---------+---------+---------+---------+
  0x1000    0x1004    0x1008    0x100C    0x1010
```

读图说明：数组所有元素在内存中物理紧挨排列，每个单元占据的位宽严格相等，编号从 0 到 `length - 1`。

数组具备以下几个硬性物理属性：
1. 数组创建后长度固定不可变更（通过 `.length` 读取）；
2. 数组内所有单元的类型完全相同，所占内存位宽一致；
3. 数组本身没有成员方法，不能像普通对象那样调用自定义逻辑；
4. 无法通过重定向引用直接让底层数组自动“隐形缩放”。

#### 为什么随机访问极快

为什么从一个包含一亿个元素的超大数组中获取第 50,000,000 个元素，和获取第 0 个元素的速度完全一样快？

根本原因在于现代计算机体系结构的内存寻址模式。由于数组在内存中是严格线性连续存储的，且每一个元素的大小都是已知的固定字节数（例如 `int` 为 4 字节），当程序需要访问索引为 `i` 的元素时，硬件甚至无需扫描前面的任何数据，只需执行一次乘法和加法运算：

$$\text{目标物理地址} = \text{数组起始基地址} + i \times \text{单个元素字节大小}$$

计算出绝对地址后，内存控制器直接根据地址将数据提取出来。这种一步直达的寻址机制，使得数组天然具备了 $O(1)$ 复杂度的任意索引随机访问能力。

### 从零构建基础数组列表

#### 核心变量与初始状态

明确了底层原理后，我们忘掉链表指针，从零开始动手构建一个基于数组的列表类，暂且将其命名为 `AList`。为了专注核心逻辑，我们先只处理整数类型。

要支撑一个可动态追加元素的列表，我们的类内部究竟需要维护哪些实例变量？
答案极其精炼，仅需两项：
1. 一个用于承载实际数据的原生整数数组 `items`；
2. 一个用于记录当前列表中实际存储了多少个有效数据的整数 `size`。

```java
public class AList {
    private int[] items;
    private int size;

    /** 初始化空列表，预分配固定容量 100 */
    public AList() {
        items = new int[100];
        size = 0;
    }
}
```

在构造函数运行结束后，`items` 指向堆中一块包含 100 个整数单元的内存空间（默认全被填充为 0），而 `size` 初始化为 0。

```text
AList 初始状态：

items ----> [  0  |  0  |  0  |  0  | ... |  0  ] (容量 100)
               ^
               |
size = 0  (下一个插入位置)
```

读图说明：`items` 引用指向预分配数组，`size` 既代表当前列表包含的元素个数，也精准指明了下一个新元素应当放入的槽位下标。

#### 尾部插入与核心不变式

现在来实现 `addLast(int x)`。新到来的数据 `x` 究竟应该放在底层数组的哪一个下标处？

我们在纸上推演一个具体的小例子：
- 当列表为空时，`size` 为 0，第一个元素显然应当放入 `items[0]`，放入后有效数量变为 1；
- 当列表已有 1 个元素时，`size` 为 1，下一个元素应当放入 `items[1]`，放入后有效数量变为 2；
- 当列表已有 3 个元素（分别占据下标 0、1、2）时，`size` 为 3，下一个元素应当放入 `items[3]`。

规律非常显然：**下一个元素要存入的下标，恰恰就是当前 `size` 的数值！**

```java
public void addLast(int x) {
    items[size] = x;
    size += 1;
}
```

在这里顺便谈一点个人编码习惯：我个人非常不喜欢写 `size++`，而总是习惯写 `size += 1`。因为 `size += 1` 明确带有一个等号，它形象地传达出“计算新值并将其重新放回内存盒子”的赋值感，对于状态变更的直观性更强。

由此，我们确立了 `AList` 内部至关重要的**类不变式（Class Invariants）**：
- `size` 始终精确等于列表中当前包含的有效元素总数；
- 列表中最后一个有效元素，永远存放在 `items[size - 1]` 的位置；
- 下一个通过 `addLast` 插入的新元素，永远存放在 `items[size]` 的位置。

这三条不变式构成了整个类逻辑推演的基石。只要所有方法在退出时都维护好这组不变式，类的运行就不会发生逻辑崩塌。

#### 元素读取与边界越界检查

有了不变式的支撑，提取末尾元素 `getLast` 和按索引随机读取 `get(int i)` 的实现变得水到渠成：

```java
public int getLast() {
    return items[size - 1];
}

public int get(int i) {
    if (i < 0 || i >= size) {
        throw new ArrayIndexOutOfBoundsException("索引超出列表当前有效范围: " + i);
    }
    return items[i];
}
```

在 `get(int i)` 中，必须对索引合法性进行前置保护。如果调用方请求的索引 `i` 大于等于当前的 `size`，即便底层原生数组在 `items[i]` 处确实分配了空间（并且存放着默认的 0），但从列表抽象的角度来看，那里并不属于用户的有效数据范围，必须抛出越界异常进行拦截。

### 移除尾部元素的哲学洞察

#### 洞穴中的影子人与数据结构僧侣

接下来讨论 `removeLast()` 的实现。如果我们要从列表中剔除最后一个元素并返回它的值，底层存储结构究竟需要做出哪些改动？

这里引出了一个极具启发性的哲学思考——类似于柏拉图经典的“洞穴寓言”：
调用我们数据结构的用户，就像生活在漆黑洞穴里的“影子人”。他们无法窥探底层计算机硬件或私有内存单元的真实面貌，他们对世界的全部认知，仅仅建立在数据结构对外暴露的公有 API（`get`、`size`、`getLast`）所投射出的墙上阴影。
而我们这些编写数据结构代码的开发者，则是身处洞穴背后操纵木偶与光源的“僧侣”。我们掌控着底层现实的绝对权力。

```text
数据结构的“洞穴寓言”模型：

+--------------------------------------------------------+
| 洞穴中的影子人（用户）：                                |
| 只能通过 API 观测世界：size() 是多少？get(i) 返回什么？  |
+--------------------------------------------------------+
                           ^
                           | 抽象隔离边界（API / private）
                           v
+--------------------------------------------------------+
| 掌控幕后现实的僧侣（开发者）：                          |
| 知道底层其实是一个固定长度为 100 的数组，存着很多无用数据  |
+--------------------------------------------------------+
```

读图说明：用户只能感知 API 行为契约，开发者只需在满足契约的前提下维护内部状态，无需付出多余的物理操作。

用户期待的效果仅仅是：列表长度减少了 1，之前最后一个元素拿不到了，再次 `getLast` 时拿到的是原本倒数第二个元素。
为了让用户在墙上看到这一预期阴影，底层数组内存框里的那个数值，真的需要被费劲地擦除或置零吗？

#### 为什么不需要清空底层单元

答案是：**完全不需要！**

只要我们将 `size` 变量减 1，由于 `private` 访问权限的保护，外部用户绝对不可能绕过方法直接读取 `items` 数组；而当他们调用 `get(size)` 时，我们的越界检查会直接抛出异常；当他们调用 `getLast()` 时，代码只会读取 `items[size - 1]`；当他们下一次调用 `addLast()` 追加新元素时，新数据会直接把那个旧槽位上的数值无情覆盖掉。

换言之，那个残留的值虽然在物理内存中依然完好无损地存在着，但在整个数据结构的抽象宇宙里，它已经被彻底判了死刑。

> **注意**：这种“逻辑删除而非物理擦除”的机制，正是现代计算机系统的通用设计哲学。就如同你在操作系统中删除一个文件，系统通常根本没有去逐位擦除磁盘磁道上的数据，而仅仅是将该文件所在的数据块标记为“未分配 / 已废弃”。
>
> 讲师在此处分享过一段真实轶事：早在 1993 年，讲师还是个热衷于编写底层系统工具的年轻极客，当时的电脑硬盘容量只有区区 300MB（现在的随意一集网剧体积都远超整块硬盘）。他的好友 Jonathan 误运行了一段磁盘格式化程序，惊恐地以为整块硬盘的数据全被彻底毁灭了。然而讲师随后利用底层恢复工具进行扫描，发现绝大部分文本数据毫发无损地躺在磁道上，最终完整找回了所有文件。所谓的“格式化”，本质上也是一种面向洞穴影子人的标记谎言。

在当前的整数类型 `AList` 中，强行将废弃位置置零没有任何工程收益，只改动 `size` 是消耗资源最少、最为纯粹的高级做法。

#### 极简代码实现与方法复用

基于上述洞察，`removeLast` 的实现极为优雅凝练，我们可以直接复用已经写好的 `getLast()` 方法，避免重复编写取值逻辑：

```java
public int removeLast() {
    int x = getLast();
    size -= 1;
    return x;
}
```

```text
removeLast 操作执行后的状态：

执行前：size = 4, items: [ 5 | 3 | 9 | 50 | 0 | ... ]
                                        ^
                                        | (最后一个元素)

执行后：size = 3, items: [ 5 | 3 | 9 | 50 | 0 | ... ]
                                  ^     ^
                                  |     +-- 物理值 50 仍留在内存中，但对外部已不可见
                              (新末尾)
```

读图说明：将 `size` 从 4 递减为 3 后，原有效范围收缩至下标 2，物理槽位上的数值 50 沦为不可达数据，逻辑删除瞬间完成。

### 基础数组列表的局限与展望

#### 现有实现的未竟之处

我们当前构建的这个极简 `AList`，虽然已经具备了数组列表的核心雏形，但明眼人立刻就能看出几个致命的缺陷与未完工之处：
- **容量死板受限**：初始数组大小被硬编码为 100，一旦用户调用第 101 次 `addLast`，系统将发生硬性数组下标越界崩溃；
- **类型单一**：当前只能容纳 `int`，尚未通过泛型拓展到任意对象类型；
- **操作单一**：尚未实现中间插入、任意位置删除、以及在头部高效添加元素的机制。

在后续课程中，我们将重点解决这些问题：引入真正的动态几何扩容机制（解决容量瓶颈），并将 `AList` 彻底泛型化（届时在 `removeLast` 时，由于 Java 垃圾回收器 GC 的存在，为了避免对象游离与内存泄漏，就必须显式将引用置为 `null`，这与基础基本类型的处理有着细微而关键的差别）。
