## 面向对象进阶与容器世界：类、静态机制、列表与映射
> 对应块：BLK02 | 覆盖分集：P02 | 块标题（分集名）：《[61B FA25] 第2讲 - 列表、集合、映》

每次在投影幕布前打开开发工具，如果冷不丁碰上那个转个不停的“旋转末日轮”等待光标，或者灯光把屏幕照得发白，总会让人感叹现实世界的软硬件环境总是充满意想不到的波折。写代码也是同样的道理：在上一讲里，我们见识到了 Java 世界中最严苛的一面——所有的函数都必须依附于类，而且要让代码跑起来，似乎就必须塞进一个固定的 `main` 方法里。

但如果你以为 Java 只是这套生硬死板的条条框框，那就小看它了。这一讲，我们要把视角从死记硬背的语法规则，转移到 Java 充满工程权衡的真实世界中。我们将系统搞清楚类与启动入口的解耦、静态与非静态在内存与认知层面的深刻鸿沟，并一步步见证列表、数组与映射这些核心容器背后的设计哲学与历史演变。

### 剥离运行入口：类与启动器分离

#### 并非每个类都需要 main 方法

初学 Java 的朋友最容易养成一个肌肉记忆：新建一个文件，声明一个类，然后立刻敲出 `public static void main(String[] args)`。毕竟在集成开发环境（IDE）里，只有类里躺着 `main` 方法，代码编辑器旁边才会亮起那个熟悉的绿色运行（播放）按钮。

但在真实的工业级软件设计中，绝大多数类根本不需要、也不应该包含 `main` 方法。

设想我们正在构建一个反映动物行为的模型，最先定义的可能是一只狗：

```java
public class Dog {
    public static void makeNoise() {
        System.out.println("Bark!");
    }
}
```

在这个类里，只有一个能发出叫声的 `makeNoise` 方法。如果你试图在编辑器里直接右键运行这个文件，系统会无动于衷，因为找不到执行的起点。但这绝不意味着这个类是废弃的残次品——它是一张纯粹的“功能蓝图”，它的使命是供外界调用，而不是自己把自己挂在执行引擎上运转。

#### 从独立的 Launcher 启动程序

既然 `Dog` 类自身不能独立运行，我们该如何使用它的能力？标准的做法是构建一个独立的启动器类（Launcher）。例如新建一个名为 `DogLauncher` 的类：

```java
public class DogLauncher {
    public static void main(String[] args) {
        Dog.makeNoise();
    }
}
```

当我们运行 `DogLauncher` 时，程序从这里的 `main` 方法切入，通过类名 `Dog` 直接指引并调用了 `makeNoise` 方法，控制台成功打印出了狗吠声。

这种将“核心业务模型”（如 `Dog`）与“应用执行入口”（如 `DogLauncher`）彻底分离的结构，是面向对象设计的基本范式。它让职责边界变得异常清爽：核心模型专注于定义现实概念的属性与行为，而启动器则充当测试台或装配线。

> **提示**：Java 是如何在没有显式引用路径的情况下找到 `Dog` 类的？这涉及到 Java 底层的“类路径”（Classpath）机制。在当前阶段，你不需要深究复杂的类加载配置，只要知道 Java 默认会将当前工作目录纳入检索范围，同目录下的类文件彼此天然可见。

### 从抽象蓝图到具体个体：对象与状态

#### 现实的多样性与实例变量

刚才的 `Dog` 类虽然能叫，但非常单薄。在真实世界里，天底下的狗并不都一模一样：一只只有五磅重的吉娃娃，和一只重达一百磅的高加索犬，其外观、力量和叫声有着天壤之别。

优秀的程序设计应当贴合现实世界的规律。为了体现狗与狗之间的个体差异，我们必须让类拥有记录状态的能力。我们在类中引入一个以磅为单位的属性：

```java
public class Dog {
    public int weightInPounds;
    // ...
}
```

这里的 `weightInPounds` 被称为**实例变量（Instance Variable）**。一旦它被写在类体中，就意味着由这张蓝图衍生出的每一个个体，都会拥有属于自己的独立体重数据。

> **定义**：实例变量（Instance Variable）是定义在类体内、方法体外的字段。它不属于类本身，而是属于类的每一个具体对象实例。每当创建一个新对象，系统都会为该对象单独划分一块内存来存放其专属的实例变量。

与 Python 或 MATLAB 等动态语言截然不同，Java 是严格静态类型的。你不能在代码运行到一半时，突然给某只狗随意塞一个此前从未在类蓝图中声明过的属性。类在编写时决定了什么形态，实例就只能拥有什么骨架。

#### 构造函数与隐式对象引用

有了实例变量后，如果我们想创建一只名为 Maya、体重 100 磅的大狗，若采用最笨拙的办法，代码会显得支离破碎：

```java
Dog maya = new Dog();
maya.weightInPounds = 100;
```

这种先凭空造出一个未经初始化的空壳，再在外部通过点号（`.`）访问成员强行赋值的做法，不仅写起来冗长丑陋，而且极易在复杂项目中漏掉必要的初始化赋值。我们更渴望在对象降生的那一刻，就直接把它的初始特征一并确立。

这正是**构造函数（Constructor）**存在的根本意义：

```java
public class Dog {
    public int weightInPounds;

    public Dog(int startingWeight) {
        weightInPounds = startingWeight;
    }
}
```

对于熟悉 Python 的同学来说，这几乎完全等同于 `def __init__(self, startingWeight):`。它们在语义上都是对象的构造器。但请注意 Java 的严谨细节：构造函数的名称**必须与类名完全一致**，并且它**绝不能声明任何返回值类型**（甚至连 `void` 都不能写）。

在 Python 中，方法必须把 `self` 作为第一个形参明晃晃地写出来；但在 Java 中，当前对象的引用是隐式存在的。如果你写成：

```java
public Dog(int weightInPounds) {
    this.weightInPounds = weightInPounds;
}
```

这里的 `this` 关键字就精准扮演了 `self` 的角色，明确指向当前正在被构造的那个具体对象实例。如果参数名与实例变量名没有发生歧义命名，你甚至可以完全省略 `this`，Java 编译器能自动领会上下文指向。

有了构造函数，启动器里的代码瞬间变得优雅自然：

```java
Dog maya = new Dog(100);
```

### 概念上帝与具体实体：静态与非静态的本质分野

#### 编译器阻断：静态上下文无法引用非静态成员

现在我们希望狗根据体重的不同发出不同的叫声。我们给方法增加条件分支：如果体重小于 10 磅，发出尖细的幼犬叫声（如 `"yip yip!"`）；如果介于 15 到 30 磅，发出欢快的狂吠；如果是庞然大物，则发出震撼的轰鸣。

但如果你直接在原有的方法上动手脚：

```java
public class Dog {
    public int weightInPounds;

    public static void makeNoise() {
        if (weightInPounds < 10) { // 编译报错！
            System.out.println("yip yip!");
        }
        // ...
    }
}
```

IDE 的代码检查器会瞬间亮起刺眼的红线，编译器会直接把你拦截在门外：`Non-static field 'weightInPounds' cannot be referenced from a static context`（非静态字段不能从静态上下文引用）。

为什么编译器会发这么大的火？

因为 `static` 关键字代表的是**属于类级别的方法**。如果 `makeNoise` 是静态的，意味着外界可以随时通过 `Dog.makeNoise()` 这样直接指名道姓的方式来呼叫它。但此时你是在命令“狗这个抽象物种”去吠叫！抽象的概念本身悬浮在虚空之中，它没有五脏六腑，更没有站在体重秤上的实体。“狗”这个物种有多重？这个问题毫无意义。既然没有具体的实例，方法里的 `weightInPounds` 就根本不知道该去读哪一块内存。

解决之道唯有一条：**剥离 `static` 关键字**，将其降维为纯正的实例方法（非静态方法）：

```java
public void makeNoise() {
    if (weightInPounds < 10) {
        System.out.println("yip yip!");
    } else if (weightInPounds < 30) {
        System.out.println("bark.");
    } else {
        System.out.println("Aroof!");
    }
}
```

一旦去掉了 `static`，这个方法就不再归“狗这个物种”直接调遣，而是必须由某一只具体的个体来触发。在 `DogLauncher` 里，你必须先 `new` 出具体的 Maya，再让 Maya 去执行叫声：`maya.makeNoise()`。

我们可以用下面的层次关系，将静态与非静态在认知世界中的映射彻底理清：

```text
+-------------------------------------------------------------+
|                     类级别（Static）                         |
|  就像全知全能、永恒不动的“上帝视角”                         |
|  代表宇宙规则、物种共性与宏观定律，超越了具象生命的数据状态 |
+-------------------------------------------------------------+
                              |
                              v 实例化过程（new）
+-------------------------------------------------------------+
|                   实例级别（Non-Static）                     |
|  代表尘世间鲜活存活的具体实体（如 Maya、小白）              |
|  拥有各自独立的体重、名字、生命痕迹与具体动作               |
+-------------------------------------------------------------+
```

> **结论**：静态如同永恒静止的神，超越了具体的数据状态，因此静态方法绝对无法感知任何单个个体的实例变量；非静态扎根于尘世实体的具体状态，必须依附于明确的对象实例才能被唤醒。

#### 静态与非静态方法：仲裁者与当事狗

什么时候该把方法声明为静态？什么时候该声明为非静态？

> **提示**：核心判断准则极其纯粹：**如果该方法需要访问或依赖某个具体实例的内部属性，它就必须是非静态的；如果它完全独立于具体实例的状态，甚至根本不需要实例化任何对象就能完成计算，它就应当设计为静态的。**

最典型的正面范例是 Java 标准库里的数学工具类 `Math`。当你需要对一个浮点数取整时，你直接调用 `Math.round(5.6)`。你绝对不需要在内存里先 `new Math()` 造出一个荒诞的“数学实体”，然后再用这个实体去执行四舍五入。`round` 是一套客观中立的通用法则，它与具体对象毫无瓜葛，天生就属于静态世界。

为了更透彻地对比两种视角的差异，我们来编写一个在两只狗中选出体型更大者的比较方法 `maxDog`。面对同一个需求，面向对象赋予了我们两种截然不同却皆具美感的解法：

##### 视角一：作为客观第三方的静态裁决者

```java
public static Dog maxDog(Dog d1, Dog d2) {
    if (d1.weightInPounds > d2.weightInPounds) {
        return d1;
    }
    return d2;
}
```

在这个静态方法中，方法本身并不依附于任何一只参战的狗。它就像一个居高临下的客观上帝，左手接过 `d1`，右手接过 `d2`，扫一眼双方的磅数，把更重的那只递回给调用者。调用代码非常符合直觉：

```java
Dog bigger = Dog.maxDog(littleDog, maya);
```

##### 视角二：作为当事主体的主动出击者

```java
public Dog maxDog(Dog otherDog) {
    if (this.weightInPounds > otherDog.weightInPounds) {
        return this;
    }
    return otherDog;
}
```

在这个非静态方法中，不再需要传入两个参数。调用它的那只狗就是擂台的主角！它在拿对方（`otherDog`）的体重，和它自己（`this`）的体重较量。如果我更重，我就骄傲地把自己（`return this;`）返回；否则，承认对方更大（`return otherDog;`）。此时的调用语法变成了主体与客体的对话：

```java
Dog bigger = littleDog.maxDog(maya);
// 或者对称地让 Maya 发起对比：
Dog bigger = maya.maxDog(littleDog);
```

更妙的是，因为这两个方法的形参列表不同（一个是接受两个参数的静态方法，一个是只接受一个参数的实例方法），它们甚至可以并驾齐驱地写在同一个 `Dog` 类中而互不冲突——这就是 Java 的**方法重载（Method Overloading）**机制。

#### 静态变量与全局状态的维护噩梦

除了方法，变量同样可以被打上 `static` 标记。设想我们要为所有家犬定义科学分类学上的二名法学名：

```java
public class Dog {
    public static String binomen = "Canis familiaris";
    public int weightInPounds;
    // ...
}
```

既然这是整个物种共享的恒定事实，就不应该在每只狗的内存空间里都重复开辟空间去存一份一模一样的字符串。我们可以直接通过类名访问：`Dog.binomen`。虽然 Java 编译器在语法上也包容你写成 `maya.binomen`，但这是一种极其拙劣的代码坏味道，它会在视觉上误导后来维护代码的人，让人误以为这个学名只是 Maya 特有的属性。

> **注意**：如果一个静态变量是允许被重新赋值修改的，它将成为大型软件工程中最危险的暗礁。

不少初学者在做自动评测作业时，往往图一时省事，把一些中间计算状态随手塞进静态变量里。这种做法相当于在整栋大楼的中央大厅摆了一块没有钥匙的白板，系统里的任何一段代码、任何一个并发任务都可以偷偷走过去擦掉原来的数字，写上自己的值。

自由一旦失去了边界，就会演变成难以追踪的因果混乱。当程序出现 Bug 时，你根本无法理清究竟是哪一个调用者在何时篡改了这块公共黑板。请务必牢记：**尽量让信息在明确的调用管道（参数与返回值）中定向传递，切莫轻易制造可变全局状态。**

### 抽象接口与具体实现：Java 列表体系

#### 为什么不能 new List

掌握了类与静态的规则后，我们把目光投向软件中最常用的基础结构——容器。

所有从 Python 过渡而来的开发者，对列表（List）都有着近乎本能的依赖。在 Python 中，信手拈来一对中括号 `[]` 便能组装起一条序列，配合 `append()` 就能一路追加。

于是在 Java 中，很多初学者的第一反应就是照猫画虎：

```java
List L = new List(); // 编译报错！
```

然而屏幕上会无情地弹出编译错误：`'List' is abstract; cannot be instantiated`（List 是抽象的，无法实例化）。

这是很多工程师在 Java 面向对象世界里撞上的第一堵厚墙：**在 Java 标准库的设计中，`List` 根本不是一个能直接在内存里落地的类，而是一个抽象接口（Interface）。**

列表的概念本质上是一组“有序对象的集合”。作为一纸抽象契约，`List` 接口严密规定了一个合格的列表必须支持的行为：比如按索引获取元素的 `get(i)`、向末尾添加元素的 `add(e)`、判空的 `isEmpty()`、查找下标的 `indexOf(o)` 等等。但这纸契约自己没有提供任何具体的存储载体，它没有声明任何底层数组或链表指针。

#### 接口契约与多种具体实现

既然不能直接实例化契约，我们就必须挑选一个签署并完全兑现了这份契约的具体实现类（Concrete Class）。在 Java 中，最常见的标准实现就是动态数组列表 `ArrayList`：

```java
import java.util.List;
import java.util.ArrayList;

List L = new ArrayList();
L.add("A");
L.add("B");
System.out.println(L);
```

在 Java 里，向序列末尾追加的操作不叫 `append`，而是统称为 `add`。

为什么要大费周章地把接口与实现剥离开来？为什么不干脆像 Python 那样直接给开发者一个唯一的列表类型？

因为在底层的工程世界中，满足“有序序列”这一概念的物理结构有着截然不同的性能表现。Java 的 `List` 接口背后伫立着一整个家族：

- **`ArrayList`（动态数组列表）**：底层依赖一块物理上连续的内存数组。它的长处是通过下标检索极快（常数时间直接寻址），但短板是在序列头部或中间插入元素时，必须搬运挪移后续的所有元素。
- **`LinkedList`（双向链表列表）**：底层由一个个离散分布的节点串联而成。它的长处是在头部和尾部增删元素快如闪电，但如果想要检索第五百个元素，就必须老老实实从头节点一路指针跳转顺藤摸瓜。
- 此外还有面向并发安全的 `CopyOnWriteArrayList`、保留历史遗迹的 `Vector` 等等。

当我们在代码左侧声明抽象的 `List`，而在右侧选用具体的 `ArrayList` 时，我们实际上是在践行面向对象设计的核心法则：“面向接口编程，而非面向实现编程”。整套业务系统只依赖于通用的列表操作，如果未来的某一天，业务场景变成了海量的高频首部插入，你只需要将右侧的 `new ArrayList()` 静默替换为 `new LinkedList()`，后续成千上万行消费列表的业务逻辑完全无需变动分毫！

### 类型的演进与约束：泛型哲学与自我设限

#### 从 Object 强转到菱形运算符的演化

如果你穿越回二十年前，上面写的那段 `List L = new ArrayList();` 确实能跑。但那个年代的 Java（Java 1.4 及之前）隐藏着巨大的隐患与烦恼。

在早期设计中，未加约束的列表为了接纳万物，内部统统退化为最底层的基类 `Object`。这直接导致了取值时的尴尬：

```java
// 2004 年以前的老旧代码风格
List L = new ArrayList();
L.add("A");
String s = L.get(0); // 编译报错！Type mismatch: cannot convert from Object to String
```

因为列表中吐出来的只是一个面目模糊的 `Object`，编译器根本不敢断定它百分之百是个字符串。程序员不得不戴上痛苦面具，手工写下强制类型转换：

```java
String s = (String) L.get(0);
```

更可怕的是，旧式列表根本无法防范程序员的糊涂操作。你可以在往列表塞了一个字符串后，顺手又往里丢了一个数字 `5`。编译器对此保持沉默，直到程序上线运行、某个调用链满心欢喜地试图强转为 `String` 时，才会轰然引发 `ClassCastException` 崩溃。

为了根治这一顽疾，Java 在 2005 年发布的 Java 5 版本中，推出了重磅武器——**泛型（Generics）**：

```java
// 2005 年的泛型语法
List<String> L = new ArrayList<String>();
```

那一对尖括号 `<String>` 就像海关检疫通道：它向编译器立下誓约，这个容器里只准通行字符串。从此，`L.get(0)` 取出来的结果天然就是类型清白的 `String`，再也无需人工强转；而任何试图把整数 `5` 塞进 `L.add(5)` 的代码，都会在按下编译键的毫秒之内被编译器无情击毙。

这一进化在 2011 年的 Java 7 中迎来了最终的优雅收尾。语言设计者意识到，既然等号左边的类型声明已经清清楚楚指明了 `<String>`，右边构造函数里重复书写便纯属冗余。于是**菱形运算符（Diamond Operator `<>`）**应运而生：

```java
// 现代 Java 标准规范写法
List<String> L = new ArrayList<>();
```

编译器能够利用类型推断算法，自动洞察右侧的类型归属。

#### 约束带来的自由：类型安全与生活哲学

很多从动态语言转过来的学习者，初见泛型时往往觉得繁琐：既然 Python 的列表什么都能塞，自由自在无拘无束，Java 为什么非要逼着程序员在声明变量时就自我设限？

这种约束的真正价值，在于**消灭意外，建立确定的心智模型**。

这就像点外卖：当你下单了一份披萨，小哥敲门递给你外卖盒，你满心期待打开，里面规规矩矩躺着热气腾腾的披萨。你不需要先用试纸去化验它是不是一块砖头或者一瓶洗洁精。如果外卖盒每次都有可能随机开出各种意想不到的奇怪物件，你不仅得不到惊喜，反而会陷入随时可能中毒的恐慌之中。

这让我想起我八岁的女儿。每天早晨起床准备上学时，如果把她带到塞满几十种花色款式的衣柜前，让她在无边无际的选项中挑选，刚睡醒的小姑娘就会感到极大的认知压力和不知所措；但如果只给她拿出两套搭配好的合适衣服让她选其一，出门的过程就会变得无比顺畅欢快。

甚至著名的后朋克/新浪潮乐队 DEVO 曾有一首风靡一时的代表作，歌名就叫《选择的自由》（*Freedom of Choice*）。自由固然美好，但过度泛滥且缺乏指引的自由，往往会直接诱发无法承受的复杂性与心智负担。

优秀的程序员懂得主动自我设限。Java 的静态类型与泛型机制，正是通过剥夺程序员在容器里“乱丢垃圾”的短暂自由，换取了大型工程在长年累月的迭代中坚如磐石的稳定与清澈。

### 追求极致性能的底层构件：数组

#### 受限但飞快的固定内存块

既然现代 Java 已经拥有了类型安全且能随心所欲动态扩容的 `List`，为什么语言还要在最底层固执地保留一个古老而僵硬的数据结构——**数组（Array）**？

在 Java 中，原生数组的限制几乎到了严苛的地步：

- 声明创建时必须硬性锁死容量，如 `String[] arr = new String[5];`。
- 一旦在内存中分配落地，其长度大小终生固定，绝无任何伸缩余地。
- 容器内的元素类型必须绝对划一。
- 数组本身几乎没有任何高级的成员方法可供调遣，必须使用最原始的方括号下标访问：`arr[0]`。

我们通过一张直观的对照，剖析数组与现代动态列表的本质分野：

```text
+----------------+-------------------------------+-------------------------------+
|    对比维度    |       原 生 数 组 (Array)     |     动态列表 (ArrayList)      |
+----------------+-------------------------------+-------------------------------+
|    容量边界    | 永久固定，不可动态增减        | 自动扩容，按需平滑增长        |
|    访问语法    | 原生方括号语法 arr[i]         | 成员方法 list.get(i) / add()  |
|    内存布局    | 紧凑物理连续，无多余封装开销  | 依赖对象封装，伴随管理元数据  |
|    运行效能    | 极致的高速寻址与紧凑内存开销  | 相对略有间接层与扩容损耗      |
+----------------+-------------------------------+-------------------------------+
```

读图说明：原生数组是牺牲了使用便利性以榨取极限底层机器性能的物理构件；动态列表则是封装了数组并处理了扩容细节的高层抽象软件工具。

#### 语言设计取向：Java 性能与 Python 简洁

为什么 Java 对待数组如此偏爱，甚至将其作为语言底层的头等公民？

**最根本的原因只有一个字：快。**

数组在操作系统的物理内存中占据的是一段严丝合缝、完全连续的线性地址空间。对于 CPU 而言，访问数组元素只需要拿基地址加上索引乘以元素尺寸，一条汇编指令便能直接命中硬件寻址。它没有对象的额外包装头（Object Header），没有动态扩容时的内存重分配与旧数据拷贝，更没有多层指针间接跳转的缓存失效。

在后续深入的计算机体系结构与硬件接口课程（UCB CS61C）中，你们将从缓存命中率（Cache Hit）、内存对齐与底层机器码的微观世界中，亲眼见证这种物理连续性带来的统治级性能优势。

这也清晰地投射出不同编程语言在诞生之初的哲学取向：

- **Java 的灵魂是为工业级的高性能与大规模吞吐而生。** 它愿意在语法上暴露一定的机械细节，逼迫开发者正视底层的资源消耗与类型契约。
- **Python 的灵魂是为开发者的表达优雅与开发敏捷而生。** 它用优雅的胶水机制把所有底层开销挡在视线之外，哪怕牺牲一定的单机执行效率，也要换取极快的代码迭代速度。

顺便提一句，当今如火如荼的机器学习与深度学习框架（如 TensorFlow、PyTorch、Keras），虽然表面上大家都在用几行简短的 Python 代码构建模型，但其背后支撑海量张量计算的底层核心，毫无例外全是用追求底层极致效率的 C/C++ 乃至于硬件加速指令锻造出来的。理解不同工具在性能与抽象天平上的砝码位置，是每一个计算机科学学子走向成熟的必修课。

### 键值映射与符号表：从抽象字典到树与哈希

#### 键值对映射的概念谱系

本讲要揭晓的最后一块核心拼图，是建立关联关系的强大结构——**映射（Map）**。

映射的本质是**键值对（Key-Value Pairs）的集合**。它建立了一条从“键”精准检索“值”的单向通道，并在结构上严格确保**键的绝对唯一性**。

设想我们在管理大学的课程注册系统：
- **键（Key）**：每一个学生的唯一学号或姓名（例如每位在座的同学）。
- **值（Value）**：该学生当前学期所选修的课程列表（例如 `CS61B` 与 `CS70`）。

由于学号唯一，系统可以通过学号在一瞬间将你的选课清单检索出来。

在不同的计算机科学流派与知识语境中，这种经典的数据组织形式有着截然不同却又殊途同归的称谓：
- 在 Python 中，它被形象地冠以**字典（Dictionary）**的美名，使用花括号 `{}` 声明。
- 在理论计算机科学界以及普林斯顿大学经典的算法教学体系中（例如 Robert Sedgewick 教授的权威讲义），它通常被称为**关联数组（Associative Array）**或**符号表（Symbol Table）**。如同查阅一部实体大英百科全书，词条名作为唯一的符号，对应着背后详尽的释义条目。

#### 抽象 Map 与具体实现：TreeMap 与 HashMap

与 `List` 的架构逻辑如出一辙，Java 中的 `Map` 同样是一个抽象接口，绝对不能被直接 `new` 出来。

我们在声明一个映射时，必须在泛型尖括号中同时声明两件大事：键的类型，以及对应值的类型：

```java
import java.util.Map;
import java.util.TreeMap;
import java.util.HashMap;

Map<String, String> animalSounds = new TreeMap<>();
animalSounds.put("dog", "woof");
animalSounds.put("cat", "meow");

System.out.println(animalSounds.get("cat")); // 准确输出 meow
```

在这个例子中，我们左手抓着抽象的契约 `Map<String, String>`，右手挑选的具体实现引擎是 `TreeMap`。

在 Java 标准库的武器库中，有两大主力实现支撑着映射的运转：
- **`TreeMap`（树映射）**：底层依赖红黑树（平衡二叉搜索树）构建。它的神奇之处在于，放入其中的所有键在任何时刻都会自动保持自然排序状态。
- **`HashMap`（哈希映射）**：底层依赖哈希表与哈希散列算法构建。它放弃了键的有序性，换取了近乎难以置信的常数级存取响应速度。

很多初学 Python 的朋友在写字典时从未思考过这些，那是因为 Python 在底层默默替你做主选定了哈希实现；正如你在 Python 里用中括号列表时，底层默默选了动态数组一样。但在 Java 中，这种底层的控制权与选择权，被堂堂正正地交到了你自己的手中。
