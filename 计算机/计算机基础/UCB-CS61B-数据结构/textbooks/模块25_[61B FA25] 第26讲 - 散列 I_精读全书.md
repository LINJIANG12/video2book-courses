### 告别全序比较：寻找超越对数时间的检索机制

之前学过的所有搜索树集合，都有一个逃不掉的硬性前置要求：**元素必须是可比较的（Comparable）**。向树里插入一个数据时，你必须能够判定 $x < y$ 还是 $x > y$，才能决定往左子树走还是往右子树走。

> **定义**：全序比较（Total Order Comparison）要求数据集合中的任意两个元素都存在明确的先后大小关系。二叉搜索树及其平衡变种均严格依赖该全序关系进行空间二分。

但这套逻辑绝非放之四海而皆准。在真实开发中，我们经常遇到无法自然排序的数据。比如你现在要维护一个音乐库，里面存了一堆音频文件，难道你能说《晴天》排在《加州旅馆》前面吗？文件之间没有绝对的大小先后之分。此时搜索树结构直接瘫痪。

更关键的是效率瓶颈：
- 搜索树集合即便经过了极致的红黑树自平衡优化，增删查的理论时间复杂度依然是**对数级（$\Theta(\log N)$）**；
- 单链表或无序数组则更慢，全都是**线性级（$\Theta(N)$）**。

能否存在一种数据结构，**既不需要元素具备可比较性，查找与插入的速度还能打破对数限制，比 $\Theta(\log N)$ 还要快**？

答案不仅是肯定的，而且其运行效率将逼近计算机科学的物理极限——常数时间 $\Theta(1)$。今天的所有推演，都始于一个极其朴素甚至略显粗暴的想法：**使用多个列表（Multiple Lists）**。

### 多列表与取模规约：从倍速加速到桶索引

#### 拆分策略：从奇偶对半到固定桶数

如果把所有数据都塞进单根链表里，查找和添加操作慢如蜗牛，必须从头到尾挨个遍历。怎么让它变快？在 61B 中我们不展开跳表（Skip List）那种加快速通道的做法，而是换个思路：如果把数据分散到两个独立的列表里呢？

我们把数据拆成两堆：
- 一堆专门放偶数；
- 一堆专门放奇数。

只要输入数据在奇偶上是均匀分布的，每个列表的长度就只有原本的一半。查询某个数字时，先看它是奇是偶，直接去对应的那个列表里找，遍历时间瞬间缩短一半——操作速度直接翻倍！

顺着这个势头往前推：如果不是两个列表，而是准备 10 个列表呢？面对一连串整数（比如 34, 56, 78，或者 12），我们该如何决定它们分别落入哪一个列表？

对于 12，你会把它放进几号列表？大家的直觉非常敏锐：放进 2 号列表。为什么？因为 $12 \bmod 10 = 2$！

```text
数组索引 (桶号)       挂载的链表数据
  [0]        --->  [70] -> null
  [1]        --->  [31] -> [91] -> null
  [2]        --->  [12] -> null
  [3]        --->  null
  [4]        --->  [34] -> null
  [5]        --->  [15] -> [85] -> null
  [6]        --->  [56] -> null
  [7]        --->  null
  [8]        --->  [78] -> null
  [9]        --->  null
```
> 上图展示了固定 10 个桶时整数通过模运算（$\bmod 10$）分散存储在各独立链表中的物理结构。

只要通过末尾数字（对 10 取模）进行分流，查找 15 是否存在时，就完全不需要扫过其他 9 个列表，径直切入 5 号列表，只需比对该列表里的少量数字即可。在数据均匀分布的前提下，速度整整提升了 10 倍。

进一步将列表数量泛化为任意整数 $M$：
在计算机科学中，我们通常把这里的每一个子列表形象地称为**桶（Bucket）**或**箱（Bin）**。在 CS70 里我们总在讨论“箱与球（Bins and Balls）”的经典概率模型，在 61B 中这也是核心载体。

把任意数据分配到各个桶中的规则，我们称之为**规约函数（Reduction Function）**。虽然理论上提取特定数位、截断高位等数学函数都能把数字压进 $0 \sim M-1$ 的区间，但最自然、最均匀且计算最廉价的手段，就是**直接取模（Modulus Operation）**：

$$\text{Bucket Index} = x \bmod M$$

即使我们选 $M = 17$，整个结构依然通过 $\bmod 17$ 完美运转。只要有 $N$ 个均匀分布的元素散落在 $M$ 个桶中，平均每个桶的元素数量就是 $N/M$，检索耗时相应缩小为原来的 $1/M$。

#### 极端状态与时空权衡

此时有同学可能会追问：既然桶越多速度越快，那如果把桶的数量推向极限呢？

假设可能插入集合的每一个整数，都有一个属于它的专属列表——也就是说，桶的数量 $M$ 与可能出现的整数总数完全相等。在 Java 中，32 位有符号整数一共有 $2^{32} \approx 42.9$ 亿种可能，我们直接开辟一个拥有 40 亿个位置的巨型数组：
- **包含检查（contains）**：直接定位到对应编号的桶，检查该列表是否为空即可；
- **添加操作（add）**：直接放进对应专属桶。

操作耗时变成了不可思议的绝对常数时间 $\Theta(1)$！但代价呢？

> **易错点**：为每一个可能的输入预分配专属存储槽，固然能将检索压缩至 $\Theta(1)$，但在实际系统中会导致灾难性的内存崩溃。绝大部分现实应用可能只存几百个数字，却要为 40 亿个空桶买单。

这就是计算机体系中恒久不变的**时空权衡（Space-Time Tradeoff）**。这就像我们在自定义链表里维护一个 `size` 缓存字段：它平白占用了 4 个字节的存储，却让我们省下了每一次调用 `size()` 都要全表遍历的漫长等待。

面对 10 个桶太慢与 40 亿个桶爆内存的极端对立，我们必须在中间找到动态平衡的杠杆。

### 动态扩容与负载因子：锁定常数级平均耗时

#### 负载因子与扩容阈值

解决固定容量瓶颈的武器我们早已掌握——**动态扩容机制（Resizing）**，正如我们在 `AList` 中做过的那样。我们完全不必一上来就开辟天文数字级别的内存，而是从一个极小的桶数 $M$ 起步，随着元素数量 $N$ 的扩张，动态增加桶的配额。

监控整体拥挤程度的物理量，叫做**负载因子（Load Factor）**。

> **定义**：负载因子（Load Factor，记作 $L$ 或 $\lambda$）是集合中当前元素总数 $N$ 与当前桶总数 $M$ 的比值：
> $$L = \frac{N}{M}$$
> 它直观反映了在理想均匀分布状态下，每个桶内链表的**平均长度**。

我们制定一条明确的工程启发式规则：**只要负载因子 $N/M \ge 1.5$，就将桶数量翻倍（$M \leftarrow 2M$）**。

让我们一步步跟踪这个过程：
1. 初始状态：设初始桶数 $M = 4$。刚开始没有元素，$N = 0$，此时负载因子 $L = 0/4 = 0$；
2. 插入元素 `7`：$N = 1$，$L = 1/4 = 0.25$；
3. 插入元素 `16`：$N = 2$，$L = 2/4 = 0.5$；
4. 随着继续插入，当集合内累计达到 4 个元素时：$N = 4, M = 4$，$L = 4/4 = 1.0$，未达阈值，不扩容；
5. 继续插入，当元素数量累计达到 6 个时：$N = 6, M = 4$，此时 $L = 6/4 = 1.5$，精确触碰上限！

平均链表长度已经达到 1.5，警报拉响，立即触发全表扩容。

#### 重新散列与常数时间保证

扩容绝不是简简单单把底层数组的格子拉长。桶的总数从 $M = 4$ 翻倍变成了 $M = 8$，这意味着所有元素的归宿必须全部推倒重算！

因为取模运算的模数变了：
- 原本元素 `13` 存储在 $13 \bmod 4 = 1$ 号桶；
- 扩容后模数变为 8，新的桶索引变为 $13 \bmod 8 = 5$ 号桶，必须将它物理迁移到 5 号桶；
- 元素 `11` 原本在 $11 \bmod 4 = 3$ 号桶，扩容后 $11 \bmod 8 = 3$ 号桶，依然留在 3 号桶。

```text
扩容前 (M = 4, N = 6, L = 1.5):
  [0] ---> [16] -> null
  [1] ---> [13] -> null
  [2] ---> [2]  -> [10] -> null
  [3] ---> [7]  -> [11] -> null

触发扩容 (M 翻倍为 8, 执行 Rehash):
  [0] ---> [16] -> null
  [1] ---> null
  [2] ---> [2]  -> [10] -> null
  [3] ---> [7]  -> [11] -> null
  [4] ---> null
  [5] ---> [13] -> null       <-- 13 从 1 号桶重定位至 5 号桶
  [6] ---> null
  [7] ---> null
扩容后 (M = 8, N = 6, L = 0.75)
```
> 上图展示了桶数量翻倍后所有已有键值执行重新散列（Rehash）并分散至新桶的物理迁移过程。

经过翻倍重构，负载因子骤降为 $6/8 = 0.75$，桶内平均拥挤程度被大幅稀释。

为什么我们可以斩钉截铁地说，它的平均操作耗时必然是常数级 $\Theta(1)$？
论证逻辑非常硬核：
由于扩容策略强制限定了 $N/M < 1.5$，只要元素在各桶间的分布是均匀的，**任何一个桶内的链表平均长度永远被物理压制在 1.5 以内**。在一条长度不超过 1.5 的极短链表里做遍历比对，哪怕加上前期的取模计算，其总耗时都与数据规模 $N$ 毫无关联——这就是严格的渐进常数时间。

> **结论**：虽然单次扩容需要遍历搬迁全部 $N$ 个已有元素，耗费 $\Theta(N)$ 的重新散列成本；但由于采用几何翻倍扩容策略，将该成本分摊（Amortized）到每一次添加操作中，其均摊时间复杂度依然是极其优异的 $\Theta(1)$。

### 字符串整数化：从进制定律到通用哈希码

#### 进制映射与小写字符串编码

纯整数的集合结构已经无懈可击，但在现实世界里，我们要存储海量的文本、图像与复杂对象。如果我想把单词 `"cat"` 存进这个数据结构，该怎么把它放进桶里？

我们首先需要把任意字符串转换成整数，才能进行后续的取模规约。

我们来看几种容易想到的初步尝试：
1. **按首字母在字母表的序号入桶**：例如 `'c'` 是字母表第 3 个字母，就把 `"cat"` 塞进 3 号桶。
   - 缺陷致命：非字母开头的字符串直接无法处理；而且自然语言中字母出现频率极度失衡（字母 `'e'` 的词频远高于 `'z'`）；更要命的是，即便我们把桶扩容到成百上千个，26 号之后的桶永远是空的，扩容加速彻底失效！
2. **按字符串长度入桶**：日常词汇长度高度集中在 3 到 8 之间，桶的利用率依然极度匮乏。
3. **按元音字母数量入桶**：同样取值狭窄，无法散布。

我们必须构思一种能让所有字符充分参与运算、且能将字符串均匀铺散到广阔数值空间的方法。最优雅的解法是：**将字符串视为多进制数字**！

我们把小写字母表映射为 26 个基本数值：$a=1, b=2, c=3, \dots, z=26$。

> **提示**：为什么系统里不从 0 开始（即不采用 $a=0$）？
> 在常规十进制中，数字 $0$ 就是 $0$；但在字符串世界里，`"aaa"` 和 `"a"` 是两个完全独立的单词！如果让 $a=0$，那么在 26 进制展开下：
> $$0 \times 26^2 + 0 \times 26^1 + 0 \times 26^0 = 0$$
> 它和单个字母 `"a"` 算出的数值毫无区别。为了避开前导零导致的信息丢失，我们必须从 1 开始编码，以 26 结束。

让我们以单词 `"cat"` 为例进行 26 进制的数值展开计算：
- `'c'` 对应数值 3；
- `'a'` 对应数值 1；
- `'t'` 对应数值 20。

代入权重公式：
$$\text{val}(\text{"cat"}) = 3 \times 26^2 + 1 \times 26^1 + 20 \times 26^0 = 3 \times 676 + 26 + 20 = 2028 + 26 + 20 = 2074$$

再来算一个单词 `"bee"`：
- `'b'` 对应数值 2；
- 两个 `'e'` 均对应数值 5。

代入公式计算：
$$\text{val}(\text{"bee"}) = 2 \times 26^2 + 5 \times 26^1 + 5 \times 26^0 = 2 \times 676 + 130 + 5 = 1352 + 130 + 5 = 1487$$

进制系统的数学美感在这里展露无遗：只要选定了进位基数，就像十进制中的 317 绝不可能写成其他数值组合一样，每一个由小写字母构成的单词，在数学上都严格映射到一个唯一的十进制整数。

算出唯一整数后，直接挂接我们前面的桶规约函数：假设当前系统有 $M = 7$ 个桶，那么：
$$\text{Index}(\text{"cat"}) = 2074 \bmod 7 = 1$$
`"cat"` 便稳稳落入 1 号桶内。

#### 扩充字符集与 Horner 迭代

但现实中的文本远不止 26 个小写英文字母。我们需要大写字母、数字以及标点符号。

早在 20 世纪 60 年代，计算机先驱们就制定了 ASCII 标准，将常见字符与 $0 \sim 127$ 之间的数值绑定。其中 $33 \sim 126$ 是肉眼可见的可打印字符（例如 33 是感叹号 `!`，35 是井号 `#`，68 是大写字母 `'D'`）。在 Java 底层，写 `char c = 'D'` 和写 `int c = 68` 是毫无二致的。

顺便提一句那些不可打印字符：比如 ASCII 7 对应控制台的蜂鸣符（Bell）。在我十几岁的少年时代，互联网还没普及，我们在拨号局域聊天室里联机打游戏。蜂鸣符无法直接敲进聊天窗口，但你可以先打一句正常话，然后切出十六进制编辑器直接修改内存中的字符串字节，将它强行改成 ASCII 7 再发出去。刹那间，房间里所有人的电脑主板蜂鸣器都会尖叫起来。后来有个网名叫 "sweeper" 的捣蛋少年由于恶作剧过头搞瘫了服务器，激起了公愤——那是我早年探索计算机边界时的有趣回忆。

处理全套可打印 ASCII 字符时，我们只需将进制基数从 26 提升至 126。对于包含 $k$ 个字符的字符串，其多项式值为：
$$\text{val} = \sum_{i=0}^{k-1} c_i \times 126^{k-1-i}$$

在工程实现中，我们绝不能使用效率低下的乘方库函数，而是采用经典的 **Horner 迭代法则**（秦九韶算法）：从数值 0 起步，循环读取每个字符，每一次都把之前的累积值乘以基数 126，再叠加上当前字符的码值：

```java
int hash = 0;
for (int i = 0; i < s.length(); i++) {
    hash = hash * 126 + s.charAt(i);
}
```

再进一步，如果要拥抱 Unicode 全球字符集呢？Unicode 涵盖了雨伞表情 ☂️、大海龟表情 🐢，以及成千上万个中日韩表意汉字。若想容纳所有汉字，进制基数至少要选用 40959 甚至更大。当多位汉字连乘展开时，算出来的数值将瞬间膨胀为不可思议的天文数字。

### 整数溢出与鸽巢原理：不可避免的碰撞现实

#### 有符号整型溢出与底层回绕机制

面对 Unicode 算出的天文数字，我们遭遇了物理硬件与编程语言的底层天花板：**存储空间是有限的**。

在 Python 这种动态语言中，解释器底层虽然提供了高精度大整数支持，但一旦数字位数过长，大数运算就不再是硬件级的常数时间，性能会断崖式下滑。而在 Java 这种强类型工业语言中，基本整数类型 `int` 是固定的 32 位有符号二进制补码表示。

它的值域有着不可逾越的边界：
$$[-2^{31}, 2^{31} - 1] \quad \text{即} \quad [-2147483648, 2147483647]$$

当数值持续累加并突破正整数极限 $2147483647$ 时，硬件底层的高位进位直接截断，在 Java 的语义规范下会发生**回绕（Wrap Around）**：

$$2147483647 + 1 = -2147483648$$

最大正数加一，瞬间跳跃到了最小负数。当我们用 Horner 算法处理长单词或中文文本时，数值在 32 位整数环上像时钟一样飞速旋转回绕，最终可能停在一个看似不可理喻的负数上（例如某个长单词算出了 $-18.67$ 亿）。

#### 鸽巢原理与哈希码的本质

这就引出了一个颠覆初学者直觉的核心命题：**我们之前试图为世界上每一个字符串分配唯一整数的目标，在数学上是注定彻底失败的**。

> **定义**：鸽巢原理（Pigeonhole Principle）表明，若有 $P$ 只鸽子飞入 $H$ 个巢穴，且 $P > H$，则至少存在一个巢穴里栖息着不止一只鸽子。

字符串的可能组合是无限的（哪怕只看长度不超过 20 的字符串，也是个无法想象的超大天文数字），而 Java 的 `int` 只有区区 42.9 亿（$2^{32}$）个取值。把无限的“鸽子”塞进 40 亿个“鸽巢”，无论哈希算法设计得多么精巧，**必然存在两个或多个截然不同的字符串，计算出完全相同的整数值**！

这种不同的输入产生相同数值的现象，就是**哈希冲突（Hash Collision，或称碰撞）**。

由此，我们迎来了现代计算机科学对**哈希码（Hash Code）**的精确定义：

> **定义**：哈希码是一个确定性的函数映射，它将可能具有无限规模的对象集合，压缩映射到固定大小的目标整数集合中。

至此，我们可以为哈希表正名：
**哈希表与我们前面构建的“动态列表数组集合”在骨架上完全一致；二者唯一的区别仅在于——哈希表使用的整数化函数，其值域是有限的。**

### 冲突应对与 Java 落地实现

#### 分离链接法与等价判定

既然冲突在数学物理定律上绝对不可避免，我们的数据结构是否就此失效了？
完全不会！

面对冲突，工业界有若干不同的应对哲学：
- **线性探测法（Linear Probing）**：属于开放寻址策略，桶位如果被占，就按固定步长往后挪找空位，就像停车场抢车位一样。数学系的学生非常迷恋这种理论，因为概率推导极具美感，但在实际工程中处理删除和聚集问题非常繁琐；
- **布谷鸟哈希（Cuckoo Hashing）**：引入多个哈希函数互相踢出旧数据；
- **分离链接法（Separate Chaining）**：每个桶维持一条独立的链表，哈希码相同或取模后落入同号桶的元素，通通串接在同一条链表上。

```text
Hash Code & 模运算             桶数组 (Buckets)            链表节点 (equals 逐个比对)
"cat"    -> 2074 % 4 = 2  ==>   [0] -> null
"hug"    -> 3480 % 4 = 0  ==>   [1] -> null
"potato" -> 7812 % 4 = 0  ==>   [2] -> ["cat"] -> null
                                [3] -> null
                                 ^
                                 |  "potato" 与 "hug" 发生哈希冲突，同入 0 号桶:
                                [0] -> ["hug"] -> ["potato"] -> null
```
> 上图展示了分离链接法解决哈希冲突的机制：不同对象即便映射至相同桶号，仍通过桶内链表串接，依靠 `equals` 逐一精确匹配。

作为一名崇尚极简的工程师，我坚定地选择分离链接法。它极其简单，且在生产环境中坚不可摧。

在分离链接哈希表中，**哈希码与取模运算的唯一职责，只是为你精准指明该去哪一个桶里寻找**。

当你要执行 `contains("hug")` 时：
1. 计算 `"hug"` 的哈希码并取模，找到 0 号桶；
2. 走到 0 号桶跟前，**绝不能只看链表是否为空**，而是必须沿着链表逐个节点比对：
   - 看着第一个节点问：“你是 `"hug"` 吗？”（调用 `equals` 比对，返回 `true`，命中！）；
   - 就算此时有个“土豆清洗机（PotatoCleaner）”对象因为哈希回绕也落在了 0 号桶，比对遍历时问一句：“你是 `"hug"` 吗？”，它回答 `false`，我们继续往下走。

碰撞不仅不是系统故障，反而是哈希表在有限世界中优雅容纳无限可能的核心设计常态。

#### 负哈希码陷阱与取模规范

在 Java 中将这套理论落地时，有一处无数资深开发者都曾栽过跟头的隐蔽暗礁：**负数哈希码的取模运算**。

Java 的基类 `Object` 原生内置了 `hashCode()` 方法（默认实现返回该对象的内存地址，这是天然的优秀整数化函数）。而标准库中 `String` 的实际实现，基数并没有选 126 或 40000，而是挑选了一个轻量小质数 31：

$$s[0] \times 31^{k-1} + s[1] \times 31^{k-2} + \dots + s[k-1]$$

选 31 是因为计算极为迅捷（现代编译器可直接将其优化为位移与减法：`31 * x == (x << 5) - x`）。但正因连续相乘溢出，大量字符串算出的 `hashCode()` 会呈现为**负整数**。

举个实际例子：某个对象的 `hashCode()` 算出来恰好是 `-1`。如果当前哈希表有 $M = 4$ 个桶，直觉上它应该落入几号桶？
从逆向循环来看，0 号桶往前倒数一个，就是 3 号桶（正如 Python 里的负索引支持）。

但在 Java 中，如果你直接写：
```java
int bucketIndex = obj.hashCode() % M; // 危险！致命错误！
```

> **易错点**：Java 中的 `%` 运算符在数学上是**取余（Remainder）**而非严格的**取模（Modulo）**。当被除数为负数时，`-1 % 4` 的运算结果依然是 `-1`！
> 若直接拿 `-1` 作为索引去访问数组，程序将当场抛出 `java.lang.ArrayIndexOutOfBoundsException` 崩溃！

```text
正向索引 (顺时针):   0  -->  1  -->  2  -->  3
逆向循环 (倒数):    -4     -3     -2     -1
对应物理桶号:       [0]    [1]    [2]    [3]
```
> 上图展示了负哈希码映射的环形模数模型：`-1` 在模 4 系统下在数学几何上严格对应 3 号桶。

要在 Java 中获得数学语义完全正确的非负桶索引，标准而优雅的做法是使用 `Math.floorMod`：

```java
int bucketIndex = Math.floorMod(obj.hashCode(), M);
```
`Math.floorMod(-1, 4)` 会精准给出非负结果 `3`，彻底斩断越界隐患。

### 性能边界与退化防线

#### 桶数策略与时间复杂度对比

哈希表的性能神话建立在其架构设计之上。我们通过下表对比不扩容与动态扩容两种策略的根本差异：

| 机制类型 | 桶数量 $M$ | 负载因子 $L = N/M$ | 增删查平均时间复杂度 | 极端最坏时间复杂度 | 空间利用评价 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **固定单列表** | $M = 1$ | $N$ | $\Theta(N)$ | $\Theta(N)$ | 空间零冗余，但检索极慢 |
| **固定固定桶** | $M = \text{常数}$（如 10） | 随 $N$ 增大线性飙升 | $\Theta(N/M) = \Theta(N)$ | $\Theta(N)$ | 元素增多后退化为长链表 |
| **全量预分配** | $M = 40\text{ 亿}$ | 趋近于 0 | $\Theta(1)$ | $\Theta(1)$ | 空间浪费极其惊人，物理不可行 |
| **动态翻倍扩容** | 随 $N$ 动态倍增 | 始终受到物理压制（$< 1.5$） | $\Theta(1)$（均摊） | $\Theta(N)$（哈希全冲突） | 时空极度均衡，工业界标准解法 |

只要桶数量与数据总量保持同比例增长，哈希表就能牢牢锁住 $\Theta(1)$ 的运行速度。

#### 均匀分布假设与树化兜底

然而，天底下没有绝对免费的午餐。哈希表的 $\Theta(1)$ 神话有一个致命的前提假设：**数据必须均匀分布（Uniform Distribution）**。

设想一种极端恶劣的情形：
假设我们有 6 个元素和 6 个桶，理论负载因子 $L = 6/6 = 1.0$。
- **理想状态**：每个桶恰好分配 1 个元素，包含检查只需 1 次操作即可结束；
- **灾难状态**：某个低劣的哈希函数将这 6 个元素全算出了相同的哈希值，或者外部攻击者精心构造了碰撞攻击数据，导致所有元素全塞进了 0 号桶，其余 5 个桶全空！

在灾难状态下，哈希表瞬间坍缩为一根无序单链表，所有操作的时间复杂度直线下坠为耻辱的 $\Theta(N)$。

如何构筑抵御极端退化的防线？
除了精心挑选诸如 31 这类能最大化打散位模式的乘法基数外，现代工程实现给出了极具创意的终极防线：
在 Java 8 的 `HashMap` 源码中，如果某一个桶内的链表长度超过了阈值（默认设定为 8），Java 会自动将该链表重构成**红黑树（平衡二叉搜索树）**！

通过这一层自适应树化防护，哪怕遭遇了恶劣的集中碰撞，该桶内的检索时间也依然能被稳稳卡在 $\Theta(\log N)$ 的上限，彻底堵死了退化为 $\Theta(N)$ 的风险后路。

### 本讲提到的思考与计算练习

在课上我们推导了字符串与桶索引的计算过程，以下整理出本讲讨论的核心推演题目，供大家巩固验证：

#### 字符串进制展开与数值推算

**题目描述**：
假定采用本讲定义的 26 进制小写字母编码方案（即 $a=1, b=2, \dots, z=26$），请分别推算单词 `"cat"` 与 `"bee"` 对应的十进制整数数值。

**解析与答案**：
1. 单词 `"cat"`：
   - 字符映射：$c = 3, a = 1, t = 20$；
   - 展开式：
     $$\text{val} = 3 \times 26^2 + 1 \times 26^1 + 20 \times 26^0 = 3 \times 676 + 26 + 20 = 2028 + 26 + 20 = 2074$$
   - 最终数值为 **2074**。

2. 单词 `"bee"`：
   - 字符映射：$b = 2, e = 5, e = 5$；
   - 展开式：
     $$\text{val} = 2 \times 26^2 + 5 \times 26^1 + 5 \times 26^0 = 2 \times 676 + 130 + 5 = 1352 + 130 + 5 = 1487$$
   - 最终数值为 **1487**。

#### 负哈希码的模数映射

**题目描述**：
假设哈希表底层分配了 $M = 4$ 个桶（索引范围为 $0 \sim 3$）。若某数据对象的 `hashCode()` 计算结果为 `-1`，按照数学循环语义，它应当归属于哪个桶？在 Java 中应当如何编写代码以避免出现负索引越界？

**解析与答案**：
1. **桶归属推算**：
   在模 4 运算系统下，数值形成以 4 为周期的环形。0 号位置的前一位（$-1$）在几何周期上对应最大的合法索引，即：
   $$-1 \equiv 3 \pmod 4$$
   因此该对象在数学语义上应当归属于 **3 号桶**。

2. **Java 正确代码实现**：
   若直接使用 `%` 取余运算符，Java 会输出 `-1 % 4 == -1`，导致数组越界崩溃。
   正确写法是调用底层标准库的向下取模函数：
   ```java
   int bucketIndex = Math.floorMod(hashCode, 4); // 输出 3
   ```
