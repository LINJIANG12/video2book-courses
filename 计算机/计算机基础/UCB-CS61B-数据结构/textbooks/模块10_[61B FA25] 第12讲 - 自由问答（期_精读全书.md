### 泛型参数的定义与引用规则

第一个来自 Ed 的高频问题非常典型：“我们在定义类和实现接口的时候，到底什么时候该写类型参数（例如 `<T>`）？为什么有时候看到类和接口后面都跟着泛型，有时又好像只写了一个？”

甚至有同学怀疑：“是不是存在只在一边写 `<T>` 的特殊写法？”据我所知，在规范的写法里从来不存在只写一半的情况。为了彻底讲明白这一条规则，我们直接对照之前第九讲继承与抽象类时写过的 `ArraySet` 源码来剖析。

#### 类声明中的紧凑表示法

在 Java 中，泛型参数的处理遵循一条核心准则：**首次出现是定义，后续出现是引用**。

```java
public class ArraySet<T> implements Iterable<T> {
    private T[] items;
    private int size;
    // ...
}
```

请仔细观察这行类签名的拆解：
- 类名 `ArraySet<T>` 后面跟着的第一个 `<T>`，是**定义**（Type Parameter Definition）。它在向编译器宣告：“在这个类的上下文中，引入了一个全新的形式类型参数，名字叫 `T`”。
- 在 `implements Iterable<T>` 中出现的 `<T>`，以及后续在声明实例数组 `private T[] items;` 或方法返回值中出现的 `T`，全都是**引用**（Type Parameter Reference）。它们指代的都是在类名后刚刚定义好的那个类型变量 `T`。

在其他某些编程语言里，设计者可能会要求你显式使用特定的关键字来区分“定义”与“引用”。但 Java 采用了一种紧凑表示法：在类名之后第一次出现的尖括号声明即为绑定点；类名之后的所有位置，都只是在复用这个已经生效的类型参数。

如果在类签名里随手把后面的引用写成了未曾定义的字母，例如写成 `implements Iterable<E>`，Java 编译器就会当场报错，质问你：“`E` 到底是从哪冒出来的？”虽然 `Iterable` 接口在源码内部确实使用了 `interface Iterable<E>`，但那只是接口自己的形式参数；你在实现该接口时，必须把自己类作用域内绑定的具体类型（即你定义的 `T`）填入进去。

至于选择用字母 `T` 还是 `E`，本身没有任何技术区别，它们都只是占位符。只要在类声明时确定了字母，后面就一律遵循这个名字。

> **结论**：只要你实现的接口本身是泛型接口（即它被设计用来容纳某种尚未确定的元素类型），你在 `implements` 该接口时就必须为其提供泛型参数；若实现的接口是一个非泛型接口（例如一个单纯的 `Animal` 接口，它不是集合容器，没有未决的元素类型），自然就不需要添加任何 `<T>`。

#### 嵌套类中的类型遮蔽与静态陷阱

这个规则在处理嵌套类（Nested Class，例如集合内部自定义的迭代器类）时，极容易引发隐蔽的 Bug。

很多同学在写 `ArraySet` 内部的迭代器时，习惯性地写成如下形式：

```java
public class ArraySet<T> implements Iterable<T> {
    // 错误示范：在内部类名后重复声明了 <T>
    private class ArraySetIterator<T> implements Iterator<T> {
        // ...
    }
}
```

> **易错点**：千万不要在内部类名后面再加一个 `<T>`！因为当你在 `ArraySetIterator<T>` 处敲下尖括号时，你在语法上声明了一个**全新的、属于该内部类专属的类型参数** `T`。虽然它碰巧也叫 `T`，但在作用域规则下，这个内部的 `T` 会完全遮蔽（Shadow）外部类 `ArraySet<T>` 已经绑定好的外层 `T`。这不仅毫无意义，而且极易导致泛型转换异常。正确的做法是直接写 `private class ArraySetIterator implements Iterator<T>`，内部类作为一个非静态类，天然可以直接引用外层类定义的 `T`。

这里紧接着引出了关于 `static` 关键字的判定：
- **非静态嵌套类（内部类）**：隐式持有外层类实例的引用，可以直接访问外层类的所有实例变量、实例方法以及外层的泛型参数。迭代器正因为需要读取外层集合的 `items` 数组和 `size` 状态，所以绝不能声明为 `static`。
- **静态嵌套类（Static Nested Class）**：它是完全独立的，不绑定在任何外层实例上。静态嵌套类内部**无法访问外层类的任何实例成员（包括实例字段与实例方法）**。如果把内部类写成了 `static`，你在里面访问外层集合的 `items` 时，IDE 会立刻抛出编译错误。

### 递归思维与辅助方法的引入边界

很多同学在完成作业中的栈（Stack）或者准备期中考时，最大的困惑之一就是：“面对一道题目，我到底什么时候需要另外写一个 private 辅助方法（Helper Method）？什么时候能直接在原方法上递归？到底有没有确切的通用原则？”

ChatGPT 对这类宏观设计模式往往给不出直击要害的干脆答案。我来用几个对比极其鲜明的真实例子，把辅助方法的边界彻底划清。

#### 为什么栈结构不能直接自身递归

假设在第 5 次作业的栈实现中，内部结构包含一个用于管理生命周期的哨兵节点 `sentinel` 和一个整型计数 `size`。现在我们想对栈内保存的所有整数求和。如果采用迭代，代码写起来非常平铺直叙：从 `sentinel.next` 开始，一路往后累加，直到指针指向 `null` 为止。

但如果题目强行要求使用**递归**来实现求和，很多初学者就会陷入一种别扭的尝试：

```java
// 错误思路演示：试图直接对栈对象自身进行递归
public class LLStack {
    private Node sentinel;
    private int size;

    public int sum() {
        if (this == null) { // 荒谬的判断！
            return 0;
        }
        // 然后呢？无法继续前进
    }
}
```

为什么这行不通？
首先，在 Java 里写 `this == null` 是一个逻辑悖论。当代码能够执行进 `sum()` 方法时，`this` 对象必然真实存在，编译器甚至会直接给出警告：`this == null` 永远为假（always false）。
其次，栈对象本身**并不是一个递归数据结构**。栈对象持有着 `sentinel` 哨兵，你无法从一个 `LLStack` 对象直接调用 `this.next` 获得“下一个栈”。

> **定义**：当操作的目标对象本身不是自相似的递归结构，或者为了完成遍历必须使用额外变量来跟踪运行状态（例如当前遍历到的节点指针、索引位置或累加器）时，必须引入辅助方法。

我们来为栈求和设计正确的辅助方法：

```java
public class LLStack {
    private Node sentinel;
    private int size;

    // 对外公开的无参 API
    public int sum() {
        return sumStack(sentinel.next);
    }

    // 私有辅助方法：计算从节点 p 开始的剩余链表元素之和
    private int sumStack(Node p) {
        if (p == null) {
            return 0; // 基本情况（Base Case）：已越过链表末尾，相当于空序列
        }
        return p.item + sumStack(p.next); // 递归推进：当前值 + 剩余部分之和
    }
}
```

写这个辅助函数时，最关键的一步是**为辅助方法写下精准的行为定义**。正如我们在 61A 或 88 里强调过的“递归信念（Leap of Faith）”：
1. 不要在大脑里试图展开一层又一层的调用栈去肉眼追踪；
2. 明确定义 `sumStack(Node p)` 的功能就是“返回从 `p` 开始往后所有节点的和”；
3. 直接相信调用 `sumStack(p.next)` 能够正确算出后续所有节点的和；
4. 既然确信它能算出后面的和，那么加上当前的 `p.item`，整个问题便迎刃而解。

对外暴露的 `public int sum()` 不需要任何参数，接口极简；对内利用 `private int sumStack(Node p)` 传入移动的指针状态。客户端使用者根本不需要、也不应该知道这个辅助方法的存在。

#### 什么时候不需要辅助方法

反过来，什么情况下我们完全不需要辅助方法？
**原则是：只要子问题的解完全由原始传入的参数决定，且求解过程不需要任何外部上下文状态时，直接在原函数上递归即可。**

举个纯粹的数值递归例子：编写一个函数，计算从 $1$ 到 $N$ 的所有整数之和，但要求**排除掉所有能被 3 整除或能被 4 整除的倍数**。

函数签名如下：

```java
public static int sumExclude3And4(int n) {
    if (n <= 0) {
        return 0; // 基本情况：超出有效区间
    }
    if (n % 3 == 0 || n % 4 == 0) {
        // 当前数值属于排除对象，不累加，直接递归缩减问题规模
        return sumExclude3And4(n - 1);
    }
    // 当前数值符合要求，累加 n 并递归求解前 n-1 个数的和
    return n + sumExclude3And4(n - 1);
}
```

在这道题里，子问题是什么？计算从 $1$ 到 $N-1$ 且排除 3 和 4 倍数的和。这个子问题依然具有与原问题完全相同的形式，只需要一个参数 `n - 1` 就足以表达完整的计算状态。这里没有任何多余的中间状态需要跨层传递，因此每个问题都是原问题的自然缩小版，根本不需要单独开辟辅助方法。

#### 选择排序中的状态传递与纯静态函数

再看我们在第六讲测试课中演示过的破坏性选择排序（Selection Sort）：

```java
public class SelectionSort {
    // 外部调用入口：仅接收待排序数组
    public static void sort(int[] x) {
        sort(x, 0);
    }

    // 辅助递归方法：对数组 x 从索引 start 开始的子数组进行排序
    private static void sort(int[] x, int start) {
        if (start >= x.length) {
            return;
        }
        int smallestIndex = findSmallest(x, start);
        swap(x, start, smallestIndex);
        sort(x, start + 1); // 状态推进：已排序边界向右移动一位
    }
}
```

在这个例子中，为什么必须有辅助方法？
因为选择排序的运作机理是：找到剩余未排序区间的最小值，与当前未排序区间的首位交换，然后递归地处理“剩余的部分”。在这个过程中，有两个关键的状态要素：
1. 始终需要对原数组 `x` 进行原地的破坏性修改（Destructive Mutation）；
2. 必须依靠一个显式的索引变量 `start` 来精确记录“当前未排序区间的起点”。

原方法 `sort(int[] x)` 没有提供位置参数，如果不引入带 `int start` 的辅助方法，递归就无法向深层传递“我已经排完了前几个元素”这一核心进度状态。

> **提示**：请注意这个辅助方法被声明为了 `static`。纯粹的静态方法就像数学意义上的纯函数（Pure Function）：它们有确定的输入和输出，只要不依赖任何外部静态变量或实例变量，其内部行为就完全封闭且确定。把它写成 `static`，正是因为它根本不需要访问外部类的任何实例成员。

### 双向链表的指针重构与解题脚手架

在双向链表（DLList）中重写指针，是大家在期中考以及 Project 1 中最常感到头皮发麻的操作。很多同学反映：“只要脑子一热直接在代码框里敲指针，哪怕只有三四行，测出来也全是空指针或者循环死锁。”

解这类指针重构问题，必须严格建立一套防错的**解题脚手架（Scaffolding）**。我们在纸面上模拟考场场景，手把手推演带哨兵双向循环链表（Circular DLList with a Sentinel）的 `addFirst` 操作。

#### 模拟考场情境：画图先行

如果把我关在一间屋子里闭卷考试，面对链表插入题，我的第一反应绝对不是去写代码，而是拿出一张草稿纸，强迫自己画图。多花这一分钟画图，能帮你省去后面二十分钟无头苍蝇般的 Debug 时间。

我们先画出操作前的链表拓扑（假设链表当前只有一个哨兵节点和一个存有数字 3 的现有节点）：

```text
操作前初始拓扑：
         +-------------------------------------------------+
         |                                                 |
         v                                                 |
   +------------+         +------------+                   |
   |  sentinel  |=======> |   Node 3   |                   |
   | (哨兵节点)  | <=======|  (旧首节点) |                   |
   +------------+         +------------+                   |
         ^                                                 |
         +-------------------------------------------------+
```
*读图说明：哨兵节点的 next 指向旧首节点（Node 3），旧首节点的 prev 指向哨兵节点；由于是循环链表，首尾双向贯通。*

现在，我们要执行 `addFirst` 插入一个新节点（假设新节点的值为 10，我们称其为 `n`）。做完之后，结构应该变成什么样？

```text
插入新节点 n 后的目标拓扑：
         +---------------------------------------------------------------+
         |                                                               |
         v                                                               |
   +------------+        +------------+        +------------+            |
   |  sentinel  |======> |   Node n   |======> |   Node 3   |            |
   | (哨兵节点)  | <======|  (新首节点) | <======|  (旧首节点) |            |
   +------------+        +------------+        +------------+            |
         ^                                                               |
         +---------------------------------------------------------------+
```
*读图说明：新节点 n 被插入到哨兵与 Node 3 之间。此时哨兵的 next 指向 n，n 的 prev 指向哨兵；n 的 next 指向 Node 3，Node 3 的 prev 指向 n。*

把两幅图往眼前一摆，对比一下：究竟发生了什么变化？
一共有且仅有**4 个指针的指向发生了改变**：
1. 哨兵节点向前的指针（`sentinel.next`）；
2. 新节点向后的指针（`n.prev`）；
3. 新节点向前的指针（`n.next`）；
4. 原先旧首节点向后的指针（旧节点的 `prev`）。

这就意味着，在代码实现中，我们必须且只能执行 4 次指针赋值操作。这就是我们的思维约束底线。

#### 为什么必须命名 oldFront：规避自指向的隐蔽 Bug

明确了需要修改 4 个指针之后，很多同学会写出这样看似“精简”的代码：

```java
// 极易引发死锁的错误写法
Node n = new Node(value);
sentinel.next = n;             // 步骤 1：哨兵指向新节点
n.prev = sentinel;             // 步骤 2：新节点指回哨兵
sentinel.next.prev = n;        // 步骤 3：糟糕！灾难在此发生
n.next = sentinel.next;        // 步骤 4：完全陷入错乱
```

请仔细盯着步骤 3：此时 `sentinel.next` 已经在步骤 1 中被重新赋值成了新节点 `n`！
因此，`sentinel.next.prev = n;` 在实际执行时，等价于 `n.prev = n;`！
你亲手让新节点的 `prev` 指向了它自己，原本的旧首节点彻底脱钩丢失，链表陷入自指向死锁。

为了杜绝这种因为指针被覆盖而导致的致命错误，我的解题秘诀非常简单：**在做任何指针变更之前，先给旧节点起一个语义清晰的局部变量名**。

```java
public void addFirst(T value) {
    // 关键第一步：在修改任何指针前，用一个稳定的局部变量把旧首节点固定住
    Node oldFront = sentinel.next;

    // 创建新节点
    Node n = new Node(value);

    // 严谨执行四步指针缝合：
    sentinel.next = n;      // 1. 哨兵的下一个指向新节点
    n.prev = sentinel;      // 2. 新节点的前一个指回哨兵
    n.next = oldFront;      // 3. 新节点的下一个指向旧首节点
    oldFront.prev = n;      // 4. 旧首节点的前一个指回新节点

    size += 1;
}
```

> **提示**：严格来说，我们只是在栈帧上多声明了一个临时的引用变量 `oldFront`。有些同学可能会纠结：“多声明一个变量会不会浪费内存或者影响性能？”完全不会！在 JVM 运行时，这个临时局部变量的生存周期只在当前方法调用期间，现代 JIT 编译器在优化时甚至会直接将它分配在寄存器中，带来的性能开销完全是零。但是它为你换来了绝对清晰的思维秩序：你不再需要在脑子里把 `sentinel.next`、`sentinel.next.prev` 这一大堆变动不居的链式调用换来算去，从而彻底从根源上消灭了覆盖指针的隐蔽 Bug。

### 关键字 this 的双重必用场景与变量遮蔽

在复习讨论中，有同学问到：什么时候在 Java 代码里必须写 `this`？平时好像很多地方省略 `this.` 代码也跑得好好的。

严格来说，在绝大多数日常访问实例变量或调用本类实例方法时，`this.` 都是隐式包含的。但以下**两种特定场景**必须显式写出 `this`：

#### 变量遮蔽与实例变量区分

第一种最常见的必须用法，发生在构造函数或 setter 方法中：**形参名与类的实例变量重名**。

```java
public class Node {
    public int value; // 实例变量

    public Node(int value) {
        // 错误示范：没有加 this
        value = value; 
    }
}
```

如果像上面这样写，代码能够正常编译通过，但它会导致一个非常低级的逻辑错误：**没有任何实例变量被赋值**。

为什么？因为在作用域解析规则中，作用域更近的局部变量（方法参数 `int value`）把外层的实例变量 `value` 给**遮蔽（Shadowing）**了。
在这段代码的大括号内部，但凡出现 `value`，Java 编译器一律认为你指的就是刚刚传进来的那个函数形参。执行 `value = value;`，仅仅是把调用方传进来的实参值又原封不动地赋给了形参自己，对象内部堆内存中的实例变量根本没有被触碰，仍然停留在默认值 `0`。

这就像现实生活中的一个场景：在教室里，我的名字叫 Josh；结果台下新来了一位同学也自称叫 Josh。如果有人在班上大喊一声“Josh！”，大家默认都会先看向离得最近的那位同学。如果我想强调“指的是我本人——讲台上的这个 Josh”，我就必须站出来说：“不，我说的是 `this.Josh`（当前对象所属的那个 Josh）”。

```java
public Node(int value) {
    this.value = value; // 正确写法：显式指定左侧是当前对象的实例变量
}
```

#### 返回对象自身的引用

第二种必须使用 `this` 的场景，是在方法内部需要将当前对象本身的引用作为返回值或参数进行传递。

最典型的例子是在设计链式调用（Fluent API / Builder 模式），或者在某些数据结构（如二叉树或双向节点）中实现比较与传递：

```java
public class DLList<T> {
    // ...
    public DLList<T> clearAndReset() {
        this.sentinel.next = this.sentinel;
        this.sentinel.prev = this.sentinel;
        this.size = 0;
        return this; // 必须返回当前实例自身，以支持链式连续调用
    }
}
```

在 `Comparable` 接口的实现逻辑中，或者在需要把自身实例注册给监听器、回调系统时，直接返回或传递 `this` 也是唯一正确的途径。

### 封装的底层逻辑与数据结构权衡

在答疑过程中，有同学提到：“为什么我们总是反反复复强调要把链表的节点类 `Node`、哨兵 `sentinel` 和长度 `size` 设为 `private`？如果设成 `public`，代码测起来功能也全对，考试会扣分吗？”

#### 为什么必须 private：喝汽油的比喻

答案非常明确：如果不遵守封装规范，考试中绝对无法拿到满分。如果一个变量在设计上本该是私有的，你却把它公开为 `public`，阅卷标准会非常严格。

为什么必须私有化？我平时常打一个生动的比方：**汽车与汽油**。

你买了一辆汽车，汽车制造厂商会把发动机引擎罩得严严实实，把油箱做成封闭的管道。厂商绝对不可能把发动机齿轮和汽油箱直接敞开在后排座椅上，任由乘客随意把手伸进油箱里舀汽油喝。把机械结构封装在铁皮内部，就是为了防止不懂内部构造的用户乱动核心零件，导致整辆车抛锚甚至爆炸。

在软件设计中，这被称为**类的不变性（Class Invariants）**：
- 我们的 `SLList` 或 `DLList` 对外承诺：这是一个线性的列表，`size()` 方法返回的永远是内部实际节点的真实数量，内部链表首尾永远正确闭环；
- 如果你把 `sentinel` 设为了 `public`，外部的使用者就可以在类的外部写出 `list.sentinel.next = null;` 这样的危险代码；
- 一旦用户这么做了，底层结构被破坏，而 `list.size` 依然显示为原数值，整个类的内部一致性彻底瓦解。

设为 `private`，就是从编译期彻底锁死外部乱伸进来的黑手，守住数据结构的不变性底线。

#### 链表与数组列表的核心权衡

我们在期中考阶段所探讨的数据结构权衡（Tradeoffs），核心聚焦在双向链表（DLList）与动态数组列表（AList）的取舍上。它们之间没有绝对的高下之分，只有适用场景的区别：

| 评估维度 | 双向链表（DLList） | 动态数组列表（AList） |
| :--- | :--- | :--- |
| **首部插入/删除（addFirst/removeFirst）** | **$O(1)$**（极快，仅需调整 4 个指针，无需搬移元素） | **$O(N)$**（较慢，必须将所有现有元素向后或向前平移一位） |
| **尾部插入/删除（addLast/removeLast）** | **$O(1)$**（极快，依靠 sentinel 的 prev 快速定位尾部） | **摊销 $O(1)$**（通常极快，但在容量满时需要触发扩容） |
| **随机索引访问（get(i)）** | **$O(N)$**（较慢，必须从头部或尾部逐节点指针跳跃寻址） | **$O(1)$**（极快，依靠数组连续内存与基地址乘偏移量寻址） |
| **内存与扩容管理** | 元素即时分配节点内存，**永远不需要扩容**；但每个节点多占 2 个指针引用 | 连续内存块紧凑，但存在潜在的**几何扩容与数据复制**成本 |

> **结论**：链表在两端的操作极其高效，尤其是在开头插入元素有着绝对的优势，且完全不需要操心扩容（Resizing）带来的复杂性；但在需要高频根据下标随机读取元素时，数组列表则是唯一的首选。

### 高难迭代器实战：Bookends 迭代器与考试抗压策略

在答疑的后半段，我翻出了一道往年的高难度期中考试原题（Spring 2019 的一道压轴 A 级大题）——“猫住在太空（Cat in Space）”中的 **Bookends 迭代器（首尾迭代器）**。

这道题在当年让很多学生当场愣住，题目形式极其怪异。现实工程中几乎没人会这么写，但它作为一道考题，能极致考察你对迭代器契约的理解、对状态机最小化的掌控，以及在高度受限条件下的破局思维。

#### 猫在太空：Bookends 迭代器的极简破题

**题目需求描述**：
编写一个泛型迭代器类 `BookendsIterator<T>`，它实现了 `Iterator<T>` 接口。构造函数接收一个由别人提供的现有迭代器 `Iterator<T> input`。
要求：这个 `BookendsIterator` **只遍历该输入迭代器的首尾两个元素**（即输入序列的第一个元素，以及输入序列的最后一个元素；若输入序列只有 1 个元素，则遍历这 1 个元素；若为空则不产生元素）。

面对这类看似繁复刁钻的题目，很多同学在考场上试图在 `hasNext()` 和 `next()` 里反复去调用输入迭代器做复杂的跳转，结果写出十几行充满 bug 的死循环代码。

我们来做一次极简破解：**寻找问题的核心洞察（Core Insight）**。
仔细想一想，不管别人给你的 `input` 迭代器里面藏着 2 个、100 个还是 1000 万个元素，作为 `BookendsIterator`，它的 `next()` 方法**最多会被成功调用几次**？
**最多只有 2 次！**
第一次调用必须返回首元素；第二次调用必须返回尾元素；随后迭代立即结束。

既然最多只需要吐出 2 个元素，我们为什么要在 `next()` 里做复杂的指针杂耍呢？我们完全可以在构造函数初始化的那几个有限行数里，把这至多两个元素一次性提取出来，存进我们自己的小型状态容器里！

```java
import java.util.Iterator;
import java.util.NoSuchElementException;

public class BookendsIterator<T> implements Iterator<T> {
    private T[] items;    // 存储捕获到的首尾元素，容量最多为 2
    private int count;    // 实际有效元素的个数（0、1 或 2）
    private int position; // 当前已迭代读取的位置索引

    @SuppressWarnings("unchecked")
    public BookendsIterator(Iterator<T> input) {
        this.items = (T[]) new Object[2];
        this.count = 0;
        this.position = 0;

        // 如果输入为空，直接结束
        if (!input.hasNext()) {
            return;
        }

        // 捕获首元素
        items[0] = input.next();
        count = 1;

        // 持续推进输入迭代器，一路找到最后一个元素
        T recent = null;
        boolean hasMore = false;
        while (input.hasNext()) {
            recent = input.next();
            hasMore = true;
        }

        // 如果存在后续元素，则最后一个元素入库作为尾元素
        if (hasMore) {
            items[1] = recent;
            count = 2;
        }
    }

    @Override
    public boolean hasNext() {
        return position < count;
    }

    @Override
    public T next() {
        if (!hasNext()) {
            throw new NoSuchElementException();
        }
        T toReturn = items[position];
        position += 1;
        return toReturn;
    }
}
```

请仔细体味这个解法的精妙与偷懒之处：
1. **构造期一次性收敛复杂度**：我们在构造函数里，先调用一次 `input.next()` 稳稳抓住第一个元素；然后直接用一个 `while(input.hasNext())` 循环将内部迭代器一路消耗到尽头，变量 `recent` 记住的最后一个值就是尾元素。
2. **极简的状态机**：将捕获到的元素放入大小为 2 的数组中，整个迭代器的运行状态蜕变成了仅仅检查 `position < count`，`next()` 只需要取出当前项并将 `position` 加一。
3. **完美抗击崩溃**：不管原测试用例如何疯狂地调用 `hasNext()`，或者在多线程/边界条件下检查，这套解法的逻辑坚如磐石，行数极其紧凑。

#### 考场防慌心态：思维脚手架与有序撤退

在期中考试这种高压环境下，当你读到一道题完全摸不着头脑、心跳加速、大脑一片空白时，该怎么办？

我有两套非常实用的临场应试招数教给你们：

##### 搭建思维脚手架（Scaffolding）
千万不要逼着自己在第一秒就写出完美可编译的代码。人的大脑在慌乱时是无法同时处理逻辑推理和严格语法的。
先不要在试卷上涂满杂乱的代码，拿出草稿纸：
- 随便画几个最简单的特例图示；
- 写两行不合语法但自己能看懂的伪代码，探索边界；
- 用明确的已知事实（例如“最多只能调用两次”）作为桩子，一步一步帮大脑建立起解题的支撑脚手架。

##### 有序撤退（Orderly Retreat）
每位同学当然都渴望拿到满分，但当你意识到完整实现可能来不及或某个边界条件处理卡壳时，绝不要乱写一通狗屁不通的胡话去赌运气——助教改卷子看到毫无逻辑的胡扯是会非常头疼且绝不会给分的。
此时要执行**有序撤退**：
- 把你能确认的核心洞察清晰地写出来（例如“定义实例变量记录首元素与尾元素”、“明确指出 `hasNext()` 的触发次数上限为 2”）；
- 哪怕内部的循环有一点小瑕疵，但只要阅卷助教看到你的代码框架体现出了对核心问题（抓取首尾、维护状态机）的准确把握，就可以顺理成章地给出大部分的步骤分（Partial Credit）。

#### 题目：双向循环链表的首部插入（DLList.addFirst）

##### 题干说明
在带有一个哨兵节点（`sentinel`）的双向循环链表 `DLList<T>` 中，实现向链表头部插入新元素的方法 `public void addFirst(T value)`。

##### 约束与结构要求
- 链表为空时，`sentinel` 的 `next` 与 `prev` 均指向 `sentinel` 自身；
- 节点结构为 `Node`，包含 `T item`、`Node prev` 和 `Node next`；
- 要求必须正确维护双向循环闭环，且不得发生指针覆盖或自身死锁 Bug；
- 同步维护整型计数 `size`。

##### 标准实现代码

```java
public class DLList<T> {
    private static class Node<T> {
        T item;
        Node<T> prev;
        Node<T> next;

        Node(T item, Node<T> prev, Node<T> next) {
            this.item = item;
            this.prev = prev;
            this.next = next;
        }
    }

    private Node<T> sentinel;
    private int size;

    public DLList() {
        sentinel = new Node<>(null, null, null);
        sentinel.prev = sentinel;
        sentinel.next = sentinel;
        size = 0;
    }

    public void addFirst(T value) {
        // 第一步：用局部变量锚定当前的旧首节点
        Node<T> oldFront = sentinel.next;

        // 第二步：新建节点，前置指针指向 sentinel，后置指针指向 oldFront
        Node<T> n = new Node<>(value, sentinel, oldFront);

        // 第三步：缝合外部进入的指针
        sentinel.next = n;
        oldFront.prev = n;

        // 第四步：更新大小不变性
        size += 1;
    }

    public int size() {
        return size;
    }
}
```

##### 考点与解析依据
1. **防止自引用指针覆盖**：必须在执行任何修改前，将 `sentinel.next` 缓存至临时局部变量 `oldFront`；若直接使用构造函数完成 `n` 的 `prev` 和 `next` 装配，则只需完成 `sentinel.next = n;` 与 `oldFront.prev = n;` 两步，代码最为凝练优雅；
2. **空链表边界普适性**：当链表为空时，`sentinel.next` 指向 `sentinel` 自身，此时 `oldFront` 即为 `sentinel`。执行上述代码后，`sentinel.next` 指向 `n`，`sentinel.prev` 也正确指向 `n`，完美兼容边界条件，无需任何 `if` 特判。

#### 题目：首尾双端迭代器（BookendsIterator）

##### 题干说明
设计并实现一个泛型迭代器类 `BookendsIterator<T>`，它实现 `java.util.Iterator<T>` 接口。该类的构造函数接收一个任意的已有迭代器 `Iterator<T> input`。
该迭代器的行为约束为：按先后顺序，仅遍历输出输入迭代器中的**首个元素**与**末尾元素**。若输入迭代器中仅有 1 个元素，则只遍历该元素一次；若输入迭代器为空，则不遍历任何元素。

##### 标准实现代码

```java
import java.util.Iterator;
import java.util.NoSuchElementException;

public class BookendsIterator<T> implements Iterator<T> {
    private T firstItem;
    private T lastItem;
    private int totalAvailable; // 可迭代的总次数：0, 1 或 2
    private int currentStep;    // 当前已消费的次数

    public BookendsIterator(Iterator<T> input) {
        this.totalAvailable = 0;
        this.currentStep = 0;

        if (input == null || !input.hasNext()) {
            return;
        }

        // 捕获首个元素
        this.firstItem = input.next();
        this.totalAvailable = 1;

        // 扫描至末尾，捕获最后一个元素
        T tempLast = null;
        boolean foundSecondOrMore = false;
        while (input.hasNext()) {
            tempLast = input.next();
            foundSecondOrMore = true;
        }

        if (foundSecondOrMore) {
            this.lastItem = tempLast;
            this.totalAvailable = 2;
        }
    }

    @Override
    public boolean hasNext() {
        return currentStep < totalAvailable;
    }

    @Override
    public T next() {
        if (!hasNext()) {
            throw new NoSuchElementException("迭代器中已无更多首尾元素");
        }
        T result;
        if (currentStep == 0) {
            result = firstItem;
        } else {
            result = lastItem;
        }
        currentStep += 1;
        return result;
    }
}
```

##### 考点与解析依据
1. **调用次数上限的不变性洞察**：意识到无论原序列有多长，本迭代器吐出元素的最大次数严格为 2；
2. **状态前置处理**：在构造函数中通过一次线性遍历耗尽底层迭代器，锁定首尾状态，使后续的 `hasNext()` 与 `next()` 能够以严格 $O(1)$ 的时间复杂度稳定响应，杜绝在迭代消费期间发生状态不一致的风险。
