## 基数排序：突破比较下界与多关键字分治
> 对应块：BLK34 | 覆盖分集：P87 | 块标题（分集名）：《[61B FA25] 第36讲 - 基数排序》

咱们继续讲排序。在正式引入今天的主角之前，咱们先来做个热身，聊一个我们之前一直没怎么展开、但极其实用的性质——稳定性。随后，我们会通过两个看似不起眼的新思路：逐位排序与计数排序，最终将它们拼装组合，推导出一套在特定场景下能够彻底打破比较排序理论瓶颈的全新算法：基数排序。

### 排序算法的暗线特性：稳定性

回顾一下我们之前学过的各种排序算法，每一种都有其核心操作与时间复杂度表现。但在选择排序算法时，除了速度和内存开销，还有一个不关乎对错、却关乎“上下文秩序”的属性，叫做稳定性（Stability）。

#### 什么是稳定性

> **定义**：若待排序序列中存在两个或多个键值相等的等价元素，在排序完成后，如果它们之间的相对前后顺序保持不变、没有发生相互跨越，该排序算法即为**稳定排序**（Stable Sort）；反之，如果等价元素的相对位置被颠倒，则称为**不稳定排序**。

打个比方，假设我们有一群学生，每个人有名有姓，同时各自被分配了 $1 \sim 4$ 的班级编号。现在我们要严格按照“班级编号”对这批学生排序。这意味着所有 1 班的学生要排在最前面，接下来是 2 班、3 班和 4 班。

因为当前的排序基准仅仅是班级编号，所以同在一个班级的学生在比较器看来就是完全等价的。比如 Jia 和 Jonny 都在 3 班，而在排序前的原始花名册中，Jia 排在 Jonny 前面。

```text
【排序前】
... -> [Jia, 3班] -> ... -> [Jonny, 3班] -> ...
             \                    /
              \（保持相对顺序）  /
               v                v
【稳定排序后】
... -> [Jia, 3班] -> [Jonny, 3班] -> ...

【不稳定排序后（发生交叉）】
... -> [Jonny, 3班] -> [Jia, 3班] -> ...
```

在稳定排序下，排序后 Jia 依然排在 Jonny 前面；如果排序算法不稳定，原本在后面的 Jonny 就可能被交换到 Jia 前面。虽然单看班级编号它们都是 3 班、数值上完全正确，但原始序列中的相对位置信息被破坏了。

#### 稳定性的实际应用：多关键字级联排序

为什么我们需要关心稳定性？一个最常见的现实场景就是电子表格（如 Excel 或 Google Sheets）中的多条件排序。

假设你手头有一份员工名单，你希望得到的结果是：先按姓名首字母升序排列；若姓名相同或需要分部门查看，则按部门编号排列。借助稳定排序，你可以非常优雅地分两步达成目的：

1. **第一轮**：先对全局直接按“姓名”排序，此时所有人已经按名字的字母序排好；
2. **第二轮**：在第一轮结果的基础上，再按“部门/组别”进行一次稳定排序。

因为第二轮排序具备稳定性，同属于一个部门的所有员工在被归拢到一起时，绝不会打乱彼此在第一轮中已经建立好的姓名字母先后顺序。最终呈现的报表自然就是“大组有序，组内按姓名严整有序”。

> **易错点**：如果第二步使用的是不稳定排序，那么在调整部门归属的过程中，同组内部原本排好的字母序就会被交叉乱窜的操作彻底破坏，导致多级排序的前置工作前功尽弃。

#### 经典排序算法的稳定性判定

我们之前学过的各个经典排序算法，到底哪些是稳定的，哪些是不稳定的？

```text
+------------------+----------+----------------------------------------------------+
| 排序算法         | 稳定性   | 核心机理与判定理由                                 |
+------------------+----------+----------------------------------------------------+
| 插入排序         | 稳定     | 元素向左比较插入时，遇到相等元素立即停步，绝不交换 |
| 归并排序         | 稳定     | 双路合并时若左右两项相等，强制优先取左半区元素     |
| 堆排序           | 不稳定   | 元素下沉（sink）或上浮时会跨越整层父子节点发生跳跃 |
| 快速排序         | 视实现   | 三路划分原序收集则稳定；原地双指针交换或打乱则破坏 |
+------------------+----------+----------------------------------------------------+
```

我们来逐个剖析背后的物理机制：

- **插入排序（Insertion Sort）**：它是稳定的。以数组中的元素向左寻找插入位置为例，当它往左边探测并遇到一个与自己数值相等的元素时，插入排序的标准规则是“不再继续交换”。相等元素不交换，它们的相对位置就纹丝不动。
- **归并排序（Mergesort）**：它是稳定的。在执行两半有序数组合并（Merge）的循环中，当我们比较 `left[i]` 与 `right[j]` 时，只要我们规定在 `left[i] <= right[j]` 时优先把左侧元素推入合并数组，那么原本在前面的左半区等价项就永远优先于右半区，顺序自然得以保留。
- **堆排序（Heapsort）**：它是不稳定的。在构建堆以及不断把堆顶最大项交换到数组末尾的过程中，长距离的父子节点交换与下沉操作完全忽略了同值节点的原始物理顺序，元素会在二叉树层级之间大幅度跳跃，必然破坏相对顺序。
- **快速排序（Quicksort）**：这取决于具体的实现变体。如果采用三路划分（3-Way Partitioning），且在扫描小于、等于、大于基准的元素时采用按原序复制提取的方式，它是稳定的；但如果采用经典的 Hoare 或 Lomuto 原地双指针头尾对调分区法，等价元素非常容易发生跨越大半个数组的长距离对调；更不用说，许多工程快排为了防止最坏退化情况，在执行前会预先做一次随机打乱（Shuffle），这直接在开局阶段就彻底摧毁了稳定性。

#### 语言工程的抉择：Java 排序的双轨设计

在 Java 标准库的 `Arrays.sort()` 中，存在一个耐人寻味的工业级设计选择：

```text
当排序目标是 Object[] 引用类型数组时  --> 采用归并排序（TimSort）
当排序目标是 int[] 等基本数据类型时   --> 采用快速排序（Dual-Pivot Quicksort）
```

> **思考**：为什么标准库要针对对象与基本类型采取截然不同的排序算法？

其核心根源正是稳定性。对象通常包含多个复合属性（即所谓的“卫星数据”，Satellite Data），比如一个学生对象同时包含姓名、学号和成绩。用户对对象数组排序往往依赖先前的顺序基础，必须保障绝对稳定。而基本数据类型（如原始 `int`）仅仅是一个纯粹的数值，数字 5 和另一个数字 5 之间没有任何附加属性区分，谁在前谁在后在语义上完全等价，根本不存在“破坏上下文”的问题。因此，系统直接选用常数项更小、速度更快的快速排序。

### 逆向观察：逐位排序的思想实验

理解了稳定性之后，我们来看今天的第一块积木：逐位排序（Digit-by-Digit Sorting）。

平常我们比较两个数字的大小，比如比较 22 与 34，或者 34 与 41，都是把它们当成一个完整的整体来比较的。但在程序设计中，我们完全可以换一种思路：**我们每次只比较数字的某一特定位**。如果你熟悉 Java，这相当于传入了一个只对比特定位权字符的自定义 `Comparator`。

#### 从单字段比较器到按位拆解

假设我们有一组两位数，比如 `[34, 41, 53, 23, 31, 32, 34]`。如果我们强制规定：“这一轮比较只准看个位（最右位），其他高位一律视而不见”，会发生什么？

在只看个位的规则下：
- 个位是 1 的排在最前（41, 31）；
- 个位是 2 的紧随其后（32）；
- 个位是 3 的排在下一档（53, 23）；
- 个位是 4 的排在最后（34, 34）。

此时，像 53 和 23 它们的个位都是 3，比较器认为它们“等价”。谁排在前面？完全取决于排序算法的稳定性。如果算法稳定，在原数组中靠前的 53 就依然留在 23 前面。

#### 级联魔术：为什么低位到高位能排好全局

现在，神奇的步骤来了。我们在完成个位排序的基础上，**紧接着按照十位（最高位）再进行一轮排序**。

注意这一轮的执行约束：**我们必须使用稳定排序算法！**

```text
原始输入序列：
  34, 41, 53, 23, 31, 32, 34

第一轮：仅按【个位】进行稳定排序
  41, 31, 32, 53, 23, 34, 34  （按个位 1, 1, 2, 3, 3, 4, 4 排列）
  注意：31 在 41 之后，23 在 53 之后，相对顺序均被稳定保持

第二轮：仅按【十位】进行稳定排序
  以 2 开头：23
  以 3 开头：31, 32, 34, 34
  以 4 开头：41
  以 5 开头：53

最终合并结果：
  23, 31, 32, 34, 34, 41, 53
```

看最终的结果：整个数组竟然已经彻底、精准地完成了全数值升序排序！

> **结论**：为什么从低位到高位的逐位排序能够排好整个数组？
> 核心全在**第二轮的稳定性**上。当第二轮按照最高位把所有数字归入 2 开头、3 开头、4 开头的大桶时，所有同样以 3 开头的数字（31, 32, 34, 34）彼此判定为等价。因为排序是稳定的，它们在桶内的先后顺序完全保留了第一轮根据个位排出来的相对次序！

这和前面提到的“先按姓名排、再按班级排”一模一样。推广到三位数乃至任意多位数：我们先按个位排，再按十位排，最后按百位排。依靠每一轮稳定排序对前一轮相对顺序的完整传承，最终最高位排完时，整个数组自然水到渠成地全局有序。

#### 逐位比较排序的尴尬处境

这个逐位排序的想法虽然精巧，但如果每一轮依然调用快速排序或归并排序，那它就纯属多此一举甚至更慢。因为直接比较两个三位整数的大小只需一次操作，而拆成三轮比较排序却要平白多跑三次，复杂度毫无优势。

逐位排序要想真正发挥出移山倒海的威力，必须搭配一种完全不依赖两两比较的极速排序手段——这就是我们接下来要讨论的计数排序。

### 突破理论天花板：计数排序与非比较排序

在探讨突破瓶颈之前，我们需要直面一座理论高山。

#### 比较排序的理论下界与绕行路径

在算法理论中，我们通过决策树模型（即之前讨论过的猜数字/分支选择推演）严格证明过：

$$T(N) = \Omega(N \log N)$$

任何基于元素之间“两两比较大小”来决定顺序的排序算法，其时间复杂度的下界绝对不可能低于 $N \log N$。无论是快速排序、归并排序还是堆排序，都必须在这道物理铁律面前低头。

要想打破 $N \log N$ 的封锁，关键在于审视“比较”二字。**只要我们根本不让两个元素发生比较——不问‘你比他大还是比他小’——我们就能绕过这个数学下界**。

#### 时间换顺序的脑洞：睡眠排序

如何做到不比较就能排序？先看一个充满极客趣味的极端设想：**睡眠排序（Sleep Sort）**。

算法的逻辑非常直白：假设数组里有一批非负整数，我们针对数组中的每一个数字 $x$，分别启动一个独立的并发线程。该线程执行唯一的指令：沉睡 $x$ 个时间单位（例如秒），睡醒的一瞬间将自身数值打印出来。

```text
输入数据：[3, 1, 4]
线程 1 (数值 3) ---- sleep(3) ----------------> 打印 3
线程 2 (数值 1) ---- sleep(1) --> 打印 1
线程 3 (数值 4) ---- sleep(4) ------------------------> 打印 4

控制台输出时序：1, 3, 4 （天然有序！）
```

在整个执行过程中，程序从未在任何两个数字之间进行过大小比较，仅仅是利用物理时间轴的流逝，把各个数值映射到了未来的时间点上。

> **提示**：睡眠排序在理论上打破了比较下界，但它在真实计算机工程中是不切实际的。因为操作系统的底层调度器本身为了维护睡眠队列的唤醒顺序，在内核态早就对这些唤醒事件进行了排序；此外，当数值过大时，时间开销将取决于最大数值而非数据规模。

#### 空间换时间：连续唯一键的单次散列

既然时间换顺序在工程上行不通，那么真正立得住脚且被工业界广泛采用的路线是：**以空间换时间**。

我们先从最简单的一个特例入手：假设我们有 $N$ 条人员档案，每条记录包含姓名、喜好等数据，且每个人被预先分配了一个互不重复、严格落在区间 $[0, 11]$ 内的整型 ID。

```text
原数组记录：
  [ID 5: Sandra], [ID 0: Lauren], [ID 11: Lisa], [ID 9: Dave] ...
```

如何在线性时间内排好序且一次比较都不做？
办法极其简单：我们直接申请一个长度为 12 的全新结果数组。然后对原数组做一次单向扫描（耗时 $\Theta(N)$）：
- 看到 ID 5 的 Sandra，看都不用看别人，直接放进结果数组下标 5 的位置；
- 看到 ID 0 的 Lauren，直接放进下标 0；
- 看到 ID 11 的 Lisa，直接放进下标 11。

一次扫描结束，所有人各归其位，排序瞬间完成。耗时是严整的 $\Theta(N)$。这里没有问过任何诸如“Sandra 是否比 Lauren 大”的是非题，完全依靠索引地址的直接寻址。

#### 重复键的稳定计数排序算法

现实中的数据往往存在大量重复，不可能每个人恰好占一个独立 ID。比如有一副由扑克牌花色标记的数据：梅花（Clubs）、黑桃（Spades）、红桃（Hearts）、方块（Diamonds），四种花色大量重复，我们要按“梅花 < 黑桃 < 红桃 < 方块”的次序排序。

此时每种花色有多个元素，我们不可能直接把所有黑桃都硬塞进单一槽位。我们需要确定每一种花色在最终排好序的数组中所占据的“区间段”。

这就是标准**计数排序（Counting Sort）**的三步法则：

```text
【步骤 1：频率统计 (Counts)】
扫描原数组，统计每种键出现的频次。
设原数组有：梅花 3 张，黑桃 2 张，红桃 4 张，方块 3 张。
counts = [梅花: 3, 黑桃: 2, 红桃: 4, 方块: 3]

【步骤 2：起始索引累积 (Starts)】
计算前缀和，得到每种花色在结果数组中的首个放置起点：
  梅花起点 = 0
  黑桃起点 = 0 + 3 = 3
  红桃起点 = 3 + 2 = 5
  方块起点 = 5 + 4 = 9
starts = [梅花: 0, 黑桃: 3, 红桃: 5, 方块: 9]

【步骤 3：遍历就位与起点递增】
再次从前往后遍历原数组：
  遇 Lauren (黑桃)  --> 查 starts[黑桃] 为 3，放入 target[3]，starts[黑桃] 递增为 4
  遇 Delbert (红桃) --> 查 starts[红桃] 为 5，放入 target[5]，starts[红桃] 递增为 6
  遇 Alice (梅花)   --> 查 starts[梅花] 为 0，放入 target[0]，starts[梅花] 递增为 1
  遇 Jason (黑桃)   --> 查 starts[黑桃] 为 4，放入 target[4]，starts[黑桃] 递增为 5
```

整个三步流程的数据流动与结构关系如下：

```text
原数组 (N 个元素):
  [黑桃 Lauren] -> [红桃 Delbert] -> [梅花 Alice] -> [黑桃 Jason] ...
       |
       v (步骤 1: 扫描并计数)
  counts 数组: [梅花: 3, 黑桃: 2, 红桃: 4, 方块: 3]
       |
       v (步骤 2: 计算累积偏移量)
  starts 数组: [梅花: 0, 黑桃: 3, 红桃: 5, 方块: 9]
       |
       v (步骤 3: 依序落位，指针后移)
输出目标数组 (N 个槽位):
  [0: 梅花 Alice] ... [3: 黑桃 Lauren] [4: 黑桃 Jason] [5: 红桃 Delbert] ...
```

> **读图说明**：步骤 1 耗时 $\Theta(N)$ 建立频次分布；步骤 2 耗时 $\Theta(R)$（$R$ 为字符集/花色种类数）推导各区间起点；步骤 3 耗时 $\Theta(N)$ 将数据精准派发进目标位置。每放置一个元素，对应花色的指针立即向后移一位，为该花色的下一个元素预留连续位置。

更为关键的是：**这样实现的计数排序天然是稳定的**。因为我们是从前往后遍历原数组，同属于黑桃的 Lauren 比 Jason 先被扫描到，Lauren 就会优先抢占较小的索引 3，而 Jason 随后被派发到索引 4，相对顺序丝毫不差。

#### 计数排序的瓶颈：双变量博弈与快排对照

计数排序的时空复杂度表达式由两个相互独立的变量决定：
- 待排序元素总数 $N$；
- 键可能的取值范围大小（即字母表规模/基数）$R$。

$$T(N, R) = \Theta(N + R)$$
$$S(N, R) = \Theta(N + R)$$

时间上包括两次遍历原数组的 $2N$ 以及遍历频次数组计算前缀和的 $R$；空间上包括大小为 $N$ 的输出暂存数组和大小为 $R$ 的计数/偏移数组。从渐进分析看，它取决于 $\max(N, R)$。

这就引出了一组经典对抗：**计数排序与快速排序，到底谁更强？**

考虑这样一个极具反差的案例：**对全球人口最多的 100 个大城市按照人口数量排序**。
- 城市数量 $N = 100$；
- 人口规模的最大值大约是 3700 万（东京都市圈），因此字母表跨度 $R = 37,000,000$。

如果你头铁使用未经优化的标准计数排序，你必须先在内存中向操作系统申请并初始化一个长度高达 3700 万的整型数组，且必须花费 $3700$ 万次循环把每个槽位清零赋初值！此时，计算耗时被庞大无比的 $R$ 绝对主导。而如果直接调用快速排序，$N \log N \approx 100 \log_2(100) \approx 700$ 次基本操作瞬间搞定。

> **结论**：
> - 当 $R \gg N$ 时（取值范围极其离散庞大，但实际数据量很少），快速排序远胜于计数排序；
> - 当 $N \gg R$ 时（数据量极其庞大，但取值范围非常窄，如 100 万名学生只有 4 种花色或 5 个评级），计数排序呈现纯线性的 $\Theta(N)$，将把快排彻底碾压。

### 珠联璧合：LSD 基数排序

至此，我们手中的两块拼图齐备了：
1. **逐位排序**：能把多位复杂数字拆解为单字符按位排，且必须依赖稳定排序；
2. **计数排序**：在线性时间内完成排序且绝对稳定，但阿喀琉斯之踵是受制于大 $R$。

把二者融为一体，**基数排序（Radix Sort）**应运而生。

#### 拆解字符集：将庞大字母表降维

假设我们要对一批取值范围在 $0 \sim 43,000$ 之间的整数排序。如果直接上计数排序，$R = 43,000$，内存和循环开销依然不菲。

但如果我们运用逐位拆解的思想，把每一个数字看作由个位、十位、百位、千位、万位构成的字符序列：
在每一位上，可能出现的符号只有 $0, 1, 2, \dots, 9$ 共 10 个阿拉伯数字！
这意味着，**原本高达 43,000 的字母表规模 $R$，瞬间被压缩到了恒定的 $R = 10$**！同理，如果处理的是英文单词，拆解到单个字符后，字母表大小也仅仅是 $R = 26$。

#### LSD 的算法执行全流程

这种从**最低有效位**（Least Significant Digit，最右侧）开始一路向左处理到最高有效位的算法，正式命名为 **LSD 基数排序（LSD Radix Sort）**。

其标准执行流程为：
1. 提取所有数字的最低有效位（个位），调用一次稳定的计数排序；
2. 提取所有数字的次低有效位（十位），在上一轮输出的基础上，再做一次稳定的计数排序；
3. 依次向左推进，直到最高有效位（第 $W$ 位）完成稳定计数排序。

每一轮的计数排序都使用固定大小 $R=10$ 的频次数组，既杜绝了巨大空间的浪费，又享受了纯线性的高速分发。

```text
待排序数据：[043, 817, 009, 033]  (预先补齐为 3 位宽)

第 1 轮：按最低位（个位: 3, 7, 9, 3）进行稳定计数排序
  结果：[043, 033, 817, 009]  (个位 3 的两个数保持原序 043 在前)

第 2 轮：按中间位（十位: 4, 3, 1, 0）进行稳定计数排序
  结果：[009, 817, 033, 043]  (十位按 0, 1, 3, 4 排好)

第 3 轮：按最高位（百位: 0, 8, 0, 0）进行稳定计数排序
  结果：[009, 033, 043, 817]  (全局完全有序！)
```

#### 不等长键的处理：高位对齐与补零

在实际数据中，数字的位数常常长短不一。比如序列里混杂着一位数 9、两位数 43、三位数 817。如果不加处理，逐位对齐就会出现歧义。

解决方案非常简明：**以序列中最长的数据宽度 $W$ 为准，短数据一律在高位（左侧）隐式补零（Pad with zeros）**。
例如：9 视同 009，43 视同 043。补零之后的空位在数值上具有等价性，且在字符集中处于最小序号，能够自然而然地排在所有非零高位数字的前面，确保排序结果的数学正确性。

#### 三参数复杂度推导：W、N 与 R

推导 LSD 基数排序的时间复杂度，需要引入三个核心参数：
- $N$：待排序键的总数量；
- $R$：每位符号的基数大小（Radix / Alphabet Size，如十进制为 10，小写字母为 26）；
- $W$：键的最大宽度（Word Length / 最大位数）。

> **结论**：LSD 基数排序的总体时间复杂度为：
> $$T(N, W, R) = \Theta(W \cdot (N + R))$$

针对这个公式，有一个非常深刻的课堂细节问题：
“既然我们知道基数是 $R$，为什么不能只花一次 $R$ 申请一个计数数组复用，把复杂度写成 $W \cdot N + R$ 呢？”

答案是：**必须是 $W \cdot (N + R)$**。因为即便你在内存中复用了同一块物理数组，在进入下一位的计数统计之前，你必须清空上一轮留下的脏数据。重新将长度为 $R$ 的数组全部清零，或者重新计算 $R$ 项的前缀累加和，每一轮都实打实地需要消耗 $\Theta(R)$ 的计算步数。一共处理 $W$ 轮，这笔账就必须实打实地乘上 $W$。

### 顺理成章的逆向探索：MSD 基数排序的萌芽

既然我们可以从右往左按最低有效位（LSD）排序，一个极其自然的发问是：**我们能不能反其道而行之，从最左边的最高有效位（Most Significant Digit，MSD）开始排序？**

#### LSD 的低位浪费与从左向右的直觉

人类查阅字典时的直觉绝不是先看末尾字母，而是先看首字母。LSD 在处理长文本时存在一个显而易见的性能短板：

假设我们要给一批极长的医学专业词汇排序，比如包含 `pseudohypoparathyroidism`（假性甲状旁腺功能减退症，长达 24 个字母）这样庞然大物的词库。如果使用 LSD，算法必须老老实实从第 24 个字母开始，由后向前跑满 24 轮整齐划一的计数排序。

然而在现实中，这批单词可能只要看前两个字母（例如区分以 `p` 开头和以 `a` 开头），其先后关系就已经盖棺定论了。后面的 22 个字母不管怎么倒腾，对最终的大格局根本没有任何决定权。LSD 从右往左的全量推进，在很多长字符串场景下做了海量的无用功。

#### 首位优先引发的跨桶交叉灾难

那么，我们能否直接拿现成的两步套路，机械地反向执行——先排首位，再排第二位？

我们做个推演，立刻就会撞上南墙：

```text
假设输入：[A2, B1, A1, B2]

第一轮：仅对【首字母】进行稳定计数排序
  结果：[A2, A1, B1, B2]  (所有 A 在前，所有 B 在后，完美)

第二轮：若依然对全局仅按【第二位】进行稳定计数排序
  数字 1 组：A1, B1
  数字 2 组：A2, B2
  组合结果：[A1, B1, A2, B2]  <-- 彻底崩溃！A 和 B 发生严重交叉交叉错乱！
```

> **易错点**：从左往右排序时，第二轮对次高位的全局排序，会由于其权重本就低于最高位，强行打乱第一轮已经奠定的最高位分组！原本井水不犯河水的 A 组和 B 组，被第二位的数值直接揉碎并重新洗牌了。

#### 分治子问题的破局思路

如何解决 MSD 的这一致命缺陷？
核心钥匙在于**分治（Divide and Conquer）与划分子问题**。

当我们根据最高有效位（首字符）完成第一轮计数排序后，我们绝不能再把整个数组作为一个整体扔进下一轮；相反，我们必须把数据切分成独立的“子桶”：所有首字母为 A 的归入 A 号子问题，首字母为 B 的归入 B 号子问题。

```text
全局序列
   |
   +--> [A 桶]: 仅在此桶内部递归对第二位排序，绝不越界
   |
   +--> [B 桶]: 仅在此桶内部递归对第二位排序，绝不越界
   |
   +--> [C 桶]: ...
```

由于各个字母的子桶彼此物理隔离、独立递归处理，跨桶交叉的问题被彻底消解。不过，MSD 带来的子问题切分、小数组递归开销与变长字符串边界处理，其精妙结构与完整收尾，我们将留待下一节课继续深入攻坚。

#### 常见排序算法的稳定性判定与机理

> **题目描述**：
> 请判断插入排序、快速排序（包含常见变体）、堆排序与归并排序各自的稳定性，并给出底层操作层面的判定理由。

**解析与答案**：
1. **插入排序（稳定）**：元素向左移动寻找位置时，比较规则通常为 `key < a[j]`。当遇到与自身值相等的项时，扫描终止并不发生交换，因此原序先后的等价元素位置不发生交叉。
2. **快速排序（视实现变体而定）**：
   - 若采用三路划分（3-Way Partitioning），且在遍历数组时按原始顺序将小于基准的元素依次复制追加到新空间，则是稳定的；
   - 若采用原地双指针交换（如 Hoare 分区），两个指针从头尾向中间扫描并对不符合条件的元素长距离互换，等价元素极易跨越彼此，因而不稳定；
   - 若在快排前执行随机打乱（Shuffle）预处理，则人为破坏了所有输入相对顺序，必定不稳定。
3. **堆排序（不稳定）**：在堆化或堆顶元素与堆尾交换下沉调整时，父子节点的跨层级跳跃交换完全不考虑等价元素的初始相对次序，因此不稳定。
4. **归并排序（稳定）**：在左右两路有序子数组合并时，只需在比较条件中严格执行 `left[i] <= right[j]` 时优先选取左侧元素，即可绝对保证原序列中位于左半部分的等价元素始终先于右半部分进入结果数组。

#### 扑克牌花色计数排序的起始偏移量推导

> **题目描述**：
> 给定一个包含 4 种扑克花色（梅花、黑桃、红桃、方块）的无序对象数组，要求按照花色顺序对其执行稳定计数排序。已知扫描统计后各花色的数量分别为：梅花 3 张、黑桃 2 张、红桃 4 张、方块 3 张。若输出数组采用从 0 开始的连续下标：
> 1. 第一张黑桃应当放置在输出数组的哪个索引位置？
> 2. 第一张红桃应当放置在输出数组的哪个索引位置？
> 3. 请写出完整的起始索引数组 `starts`。

**解析与答案**：
计数排序中每个分类的起始下标等于其前面所有较小分类的元素数量总和（前缀累加和）。
1. 梅花是第一个分类，其起始索引为 $0$；
2. 黑桃前面共有梅花 3 张，因此第一张黑桃应当放置在索引：
   $$Starts[\text{黑桃}] = 0 + 3 = 3$$
3. 红桃前面共有梅花 3 张与黑桃 2 张，合计 5 张牌，因此第一张红桃应当放置在索引：
   $$Starts[\text{红桃}] = 3 + 2 = 5$$
4. 方块前面共有梅花 3 张、黑桃 2 张、红桃 4 张，合计 9 张牌，因此方块起始索引为：
   $$Starts[\text{方块}] = 5 + 4 = 9$$
完整的起始偏移数组为：`[梅花: 0, 黑桃: 3, 红桃: 5, 方块: 9]`。

#### 极端分布下的排序算法选型：城市人口排序对比

> **题目描述**：
> 假设你需要对全世界人口最多的前 100 个城市按照人口数量升序排序。现有两种备选方案：未经优化的标准计数排序与经典的快速排序。你会倾向于选择哪一个？为什么？如果将场景换为对 100 万名持有 4 种不同花色卡牌的用户排序，结论又将如何？

**解析与答案**：
1. **100 个最大城市排序场景**：
   - 强推选择**快速排序**。
   - 原因：城市样本数量 $N = 100$ 极小，但人口键值的取值范围跨度 $R$ 极大（最大城市人口约为 37,000,000）。标准计数排序需要申请并初始化长度达 3700 万的计数数组，光是将数组填满零就需要执行 3700 万步操作，性能被 $R$ 严重拖垮。而快速排序只需 $\Theta(N \log N) \approx 100 \times \log_2(100) \approx 700$ 次基本比较，快排远胜计数排序。
2. **100 万名用户与 4 种花色场景**：
   - 强推选择**计数排序**。
   - 原因：此时 $N = 1,000,000$ 极大，而分类基数 $R = 4$ 极小。计数排序只需花费线性时间 $\Theta(N + R) \approx 100$ 万次操作即可完成；而快速排序需要 $\Theta(N \log N) \approx 1000000 \times 20 = 2000$ 万次操作。在 $N \gg R$ 的场景下，计数排序完胜快速排序。

#### LSD 基数排序的三参数复杂度推导

> **题目描述**：
> 设待排序元素数量为 $N$，每个字符/数位的基数取值范围为 $R$（如十进制 $R=10$），键的最大宽度为 $W$。推导 LSD 基数排序的整体运行时间表达式。为什么表达式中 $R$ 项必须乘以 $W$ 而不能简单写为 $\Theta(W \cdot N + R)$？

**解析与答案**：
1. **总体运行时间**：
   $$T(N, W, R) = \Theta(W \cdot (N + R))$$
2. **乘以 $W$ 的根因**：
   LSD 基数排序共需要针对每一位执行一轮稳定的计数排序，总轮数为 $W$。在每一轮计数排序中：
   - 扫描当前有效位并统计频次需要 $\Theta(N)$；
   - 扫描大小为 $R$ 的频次数组并计算前缀和需要 $\Theta(R)$；
   - 依序分发写出数据需要 $\Theta(N)$。
   即便算法在内存中反复复用同一块大小为 $R$ 的计数数组，每一轮在开始统计前，都必须花费 $\Theta(R)$ 的时间将其重新清零，并重新计算累加偏移。因此每一轮实打实的开销均为 $\Theta(N + R)$，累计 $W$ 轮必须完整乘进去，得到 $\Theta(W(N + R))$。

#### Java 标准库排序算法针对类型分歧的设计初衷

> **题目描述**：
> 为什么 Java 的 `Arrays.sort()` 在实现底层，针对引用类型数组（如 `Object[]`）采用归并排序变体（TimSort），而针对基本数据类型数组（如 `int[]`）采用快速排序变体（Dual-Pivot Quicksort）？

**解析与答案**：
1. **针对引用对象需要绝对的稳定性**：
   Java 中的引用对象往往承载着复合属性（如附带各种业务字段）。在实际工程中，用户经常在已有排序结果的基础上追加多级排序（例如在已经按姓名排好的数据上再按部门排）。为了保障多级排序的正确性，算法必须具备稳定性。归并排序（TimSort）天然保证相等对象的相对顺序不被破坏。
2. **针对基本类型追求极限的运行效率**：
   基本类型（如 `int`, `double`）是纯粹的值类型，没有任何附属的卫星数据。两个数值相等的基本类型数据在语义上是完全同质且无法区分的，谁在前谁在后对程序逻辑没有任何影响。因此对于基本类型无需保证稳定性，标准库选用了常数项更小、无需开辟辅助数组且速度更快的双轴快速排序。
