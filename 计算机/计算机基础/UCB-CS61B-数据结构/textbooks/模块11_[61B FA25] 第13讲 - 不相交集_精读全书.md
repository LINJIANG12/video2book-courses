## 不相交集的设计演进与性能跃迁
> 对应块：BLK11 | 覆盖分集：P28 | 块标题（分集名）：《[61B FA25] 第13讲 - 不相交集》

刚刚经历了一场折磨人的期中考试，大家辛苦了。今天我们换个节奏，来看看计算机科学中那些早已被彻底解决、却极其迷人的经典数据结构。

之前我们已经设计过了列表，接下来还要接触集合、映射和优先队列。而今天我们要探讨的这个数据结构，比它们稍微冷门一点，叫做**不相交集**（Disjoint Sets）。在一步步把它构建出来的过程中，我们会从极其直观朴素的原始方案出发，层层推演，最终抵达精妙且处于计算机科学前沿的终极优化方案。

### 洞穴寓言与接口抽象

在正式落笔之前，先看一个我最喜欢的隐喻——柏拉图的洞穴寓言。

想象洞穴里坐着一群穴居人，面对着一面石壁；而在他们身后，僧侣们正围绕着火堆操纵木偶，把影子投射在石壁上供穴居人观看。穴居人看到的只是屏幕上的影子投射；而作为幕后的僧侣，究竟是用悬浮的鸟形木偶，还是用手指在火光前比划出飞鸟的阴影，完全取决于我们自己的工程抉择。

在软件设计中亦是如此：

```text
+-------------------+              +----------------------+
| 外部用户 (穴居人) |              |  底层开发者 (僧侣)   |
|   只关注接口 API  | <=========>  | 关注数据结构内部表示 |
| connect / isConn  |              | 决定执行效率与复杂度 |
+-------------------+              +----------------------+
```

外部调用者只在乎接口的功能表现是否正确；但我们在底层所做的每一个设计抉择，都会对最终系统的性能产生天壤之别的影响——决定了操作究竟是瞬间完成，还是要跑上整整几十年。

#### 核心接口规范

不相交集是一种功能非常纯粹的数据结构，它本质上只提供两个核心操作：

```java
public interface DisjointSets {
    /** 将两个元素 p 和 q 连通 */
    void connect(int p, int q);

    /** 查询元素 p 和 q 是否连通 */
    boolean isConnected(int p, int q);
}
```

- `connect(int p, int q)`：建立两个元素之间的连接关系。
- `isConnected(int p, int q)`：查询两个元素当前是否存在连通关系，连通则返回 `true`，否则返回 `false`。

这个数据结构的关键挑战在于：**连通性具有传递性**（Transitivity）。

不妨以地缘政治打个比方：假设我们调用 `connect("Russia", "China")`，在地图上俄罗斯与中国连通了；接着调用 `connect("Russia", "Mongolia")`，俄罗斯与蒙古也连通了。此时若调用 `isConnected("China", "Mongolia")`，返回值必须是 `true`。虽然中国和蒙古之间没有直接画线，但通过俄罗斯这个中介，它们已经处在同一个连通网络之中。

```text
(Russia) -------- (China)
    |
    |
(Mongolia)

(USA) ------------ (Canada)
```

此时如果询问 `isConnected("USA", "Mongolia")`，结果显然是 `false`。但如果随后我们调用了 `connect("Russia", "USA")`，整个格局便被打破了——此前所有针对美国与蒙古的连通性查询都将从 `false` 翻转为 `true`。

> **定义**：不相交集支持以任意顺序交错调用 `connect` 与 `isConnected`。随着连接的建立，原本为 `false` 的查询结果可能会动态变为 `true`，但连通的状态绝不会撤销或断开。

#### 简化约束与规模挑战

为了抛开语法杂质、聚焦于算法本身，我们先做两个不失通用性的合理简化：

- **元素类型限定为整数**：对象统一采用从 `0` 到 `N - 1` 的非负整数编号。如果实际场景中需要连接字符串或复杂对象，只需在外部维护一个哈希表做一层索引映射即可。
- **元素规模固定**：在初始化时必须显式声明集合包含的元素总数 $N$。初始状态下，所有 $N$ 个元素各自独立，彼此互不连通。

我们要面对的现实工程挑战在于：元素总数 $N$ 可能达到数百万级，而 `connect` 与 `isConnected` 的调用总次数 $M$ 可能会达到数十亿次。在这样庞大的调用量面前，底层的细微差异都会被无限放大。

### 从连线思维跃迁至集合思维

面对这个需求，最直观的下意识冲动是什么？

既然用户要“连线”，我们不妨在内部拿一个列表把每一条连线记录下来。当用户调用 `connect(2, 4)`，我们就记录边 `(2, 4)`；调用 `connect(0, 1)`，就记录边 `(0, 1)`。

然而只要稍加推演就会发现：当用户询问 `isConnected(0, 2)` 时，我们必须在这些连线构成的图结构中跑递归遍历或路径搜索，去验证是否存在一条经过若干中继节点的折返路径。代码不仅极难编写，而且在最坏情况下遍历连线极其缓慢。

这时我们需要停下来，做一个决定性的关键观察：

假设当前集合中包含元素 $0, 1, 2, 4$，它们彼此连通。至于 $0$ 和 $2$ 究竟是通过 $1$ 间接相连，还是通过 $4$ 相连，亦或是彼此之间有一条直连边，**外部调用者根本不在乎**！

```text
连线视角 (冗余关注具体拓扑):
  0 ----- 1 ----- 2
  \              /
   \----- 4 ----/

集合视角 (只关注等价类归属):
  家族 A: { 0, 1, 2, 4 }
  家族 B: { 3, 5 }
  家族 C: { 6 }
```

用户只在乎 $0, 1, 2, 4$ 是否同属一个“家族”。用图论的严谨术语来说，这叫**连通分量**（Connected Component）。

> **结论**：两点是否连通，本质上等价于它们是否属于同一个等价类集合。这一洞察使我们彻底摆脱了复杂的连线拓扑追踪，把问题转化为：**如何高效维护一组动态合并的互不相交集合**。

### 集合列表：直觉方案的性能滑铁卢

既然要维护互不相交的集合，在 Java 中最容易想到的现成容器就是“集合的列表”：`List<Set<Integer>>`。

初始时，我们为 $0$ 到 $N - 1$ 的每个元素分别建立一个单元素 `Set`，并将它们全部存入一个 `List` 中。

```text
List 索引:     0        1        2        3        4        5        6
存储内容:    { 0 }    { 1 }    { 2 }    { 3 }    { 4 }    { 5 }    { 6 }
```

#### 操作逻辑与执行代价

当我们要执行查询与连接时：

- `isConnected(p, q)`：遍历整个列表，逐个检查每个集合是否包含 $p$；找到后，再看该集合是否同时包含 $q$。如果在一个集合中同时找到了两者，说明连通；若遍历完所有集合发现它们分属不同集合，则不连通。
- `connect(p, q)`：遍历列表找到包含 $p$ 的集合 $S_p$，再找到包含 $q$ 的集合 $S_q$；将 $S_q$ 中的所有元素移动并入 $S_p$，随后从列表中移除空集合 $S_q$。

#### 瓶颈剖析

这个方案在直觉上很自然，但在工程实现上非常繁琐，且性能极差。

假设当前所有元素都各自独立（列表中共有 $N$ 个单元素集合）。如果要查询 `isConnected(5, 6)`：
1. 线性遍历列表寻找包含 $5$ 的集合，需要逐个比对，直到扫过大半个甚至整个列表；
2. 再次遍历寻找包含 $6$ 的集合；
3. 最终确认它们不在同一集合中。

因为列表中最多存在 $N$ 个集合，遍历查找定位的最坏时间复杂度为 $O(N)$；而合并两个集合并调整列表同样需要 $O(N)$。

在动辄调用数百万次的场景下，每次操作都要扫描全表，系统必然卡死。这种嵌套数据结构的底层开销注定了它无法承担大规模高频操作。

### 快速查找：极速常数级查询的代价

既然嵌套的 `List<Set<Integer>>` 太重，我们能否用最质朴的固定数组来解决问题？

这就引出了第二代设计：**快速查找**（Quick Find）。

#### 数组建模：以扁平标签代表集合

我们开辟一个长度为 $N$ 的一维整型数组 `int[] id`。数组的索引 $i$ 代表元素本身，而位置 $i$ 存储的值 `id[i]` 则代表该元素所属的“集合标识编号”。

```text
元素索引:   0   1   2   3   4   5   6
数组取值: [ 4 | 4 | 4 | 5 | 4 | 5 | 6 ]
```

读懂上图的对应关系：
- 元素 $0, 1, 2, 4$ 对应的标签值都是 $4$，说明它们同属 $4$ 号家族；
- 元素 $3, 5$ 的标签值都是 $5$，说明它们同属 $5$ 号家族；
- 元素 $6$ 的标签值是 $6$，自成一组。

需要说明的是，标签数值具体是几完全无关紧要，只要同一集合内的元素具有相同数值即可。

#### 核心方法实现

在这种表示法下，两个操作的具体实现方式如下：

```java
public class QuickFindDS implements DisjointSets {
    private int[] id;

    public QuickFindDS(int N) {
        id = new int[N];
        for (int i = 0; i < N; i++) {
            id[i] = i; // 初始时每个元素自成一组，标签为其自身索引
        }
    }

    @Override
    public boolean isConnected(int p, int q) {
        return id[p] == id[q];
    }

    @Override
    public void connect(int p, int q) {
        int pid = id[p];
        int qid = id[q];
        if (pid == qid) {
            return;
        }
        // 遍历整个数组，将所有属于 pid 的元素全部改签为 qid
        for (int i = 0; i < id.length; i++) {
            if (id[i] == pid) {
                id[i] = qid;
            }
        }
    }
}
```

#### 性能特征与评价

来看 Quick Find 的运行时间表现：

- `isConnected(p, q)`：只需访问两次数组槽位并对比数值，执行时间与元素总量 $N$ 毫无关系，是绝对的常数时间 $\Theta(1)$！
- `connect(p, q)`：为了把两个集合合并，必须完整遍历一遍长度为 $N$ 的数组，将所有旧标签替换为新标签，耗时恒定为 $\Theta(N)$。

> **提示**：Quick Find 就像把提线木偶换成了剪纸木偶——穴居人看到的外部行为完全一致，但查询操作被提速到了极致。然而它的弱点也同样致命：每次连接都要全盘扫描数组。如果调用 $N$ 次 `connect`，总耗时将达到 $O(N^2)$。

### 快速合并：引入树状层级体系

我们显然不满意 `connect` 每次都要遍历整个数组去改一堆数值。能不能改动底层的数学模型，让**合并操作在数组里只改动一个数值**？

为了实现这个构想，我们进入第三代设计：**快速合并**（Quick Union）。

#### 等级制建模：从体育队到公司架构

在 Quick Find 中，所有人都是平等的队员，贴着完全一样的队标。

现在我们换个思路，建立一种严格的**层级隶属关系**（类似公司汇报线）：
- 每个节点不再存储扁平的队伍 ID，而是存储它的**直接上级（父节点）**的索引；
- 沿着父节点一路往上汇报，最终到达的顶层最高负责人称为**根节点**（Root）；
- 根节点没有上级，在数组中我们用特殊标记（如 `-1`，或者指向自身）来表示它是根。

```text
树状层级拓扑:
       0           3       6
      / \          |
     1   4         5
     |
     2

底层数组 parent[]:
索引 i:       0    1    2    3    4    5    6
parent[i]: [ -1 |  0 |  1 | -1 |  0 |  3 | -1 ]
```

仔细比对上方的图示与数组：
- 节点 $2$ 的父节点是 $1$（`parent[2] = 1`）；
- 节点 $1$ 的父节点是 $0$（`parent[1] = 0`）；
- 节点 $0$ 的值为 `-1`，说明它是顶层根节点。
- 节点 $5$ 的直接上级是 $3$，而 $3$ 是根节点；
- 节点 $6$ 自身就是根节点。

#### 核心方法实现

在这种结构下，判断连通性与合并集合的操作逻辑发生了根本改变：

```java
public class QuickUnionDS implements DisjointSets {
    private int[] parent;

    public QuickUnionDS(int N) {
        parent = new int[N];
        for (int i = 0; i < N; i++) {
            parent[i] = -1; // 初始时各节点均为独立的根
        }
    }

    /** 顺着父节点指针向上攀爬，寻找元素 i 的根节点 */
    private int find(int i) {
        int curr = i;
        while (parent[curr] >= 0) {
            curr = parent[curr];
        }
        return curr;
    }

    @Override
    public boolean isConnected(int p, int q) {
        return find(p) == find(q);
    }

    @Override
    public void connect(int p, int q) {
        int rootP = find(p);
        int rootQ = find(q);
        if (rootP != rootQ) {
            // 只需修改一个数组值：让 rootP 听命于 rootQ
            parent[rootP] = rootQ;
        }
    }
}
```

#### 为什么合并不能直接连基层员工

在课堂上经常有同学产生这样的直觉：如果要合并 $5$ 和 $2$，为什么不能直接让 `parent[5] = 2`？

> **易错点**：千万不能直接把两个底层节点相连！如果直接让 $5$ 指向 $2$，那么原来归 $5$ 管辖的子节点或 $5$ 上方的根节点 $3$ 就会产生关系错乱甚至断连。两家公司合并，绝不是让两个基层业务员私下拉一条线，而是两家公司的**最高董事长进行并购**——让其中一方的董事长向另一方的董事长汇报，整个组织架构才会自然合并为一体。

通过让 `parent[rootP] = rootQ`，我们仅仅修改了一个数组位置的值，就完成了整个集合的合并，完全避免了循环遍历整个数组！

#### 致命软肋：树高失控与退化

单看单次修改一个值，Quick Union 确实很巧妙；但我们必须审视它的查找代价。

注意：无论是 `isConnected` 还是 `connect`，其内部第一步都是调用 `find` 向上攀爬。攀爬的速度完全取决于树有多高！

假设我们按如下顺序依次调用连接：
`connect(4, 3)`、`connect(3, 2)`、`connect(2, 1)`、`connect(1, 0)`……

每一次连接都漫不经心地把左边的根节点挂在右边的根节点下方：

```text
4
|
3
|
2
|
1
|
0
```

整棵树最终退化成了一条又细又长的单向链表！

在最坏情况下，包含 $N$ 个元素的树高度会达到 $N$。此时要判断最底层的节点是否连通，必须向上爬满整整 $N$ 个台阶：
- `find` 的最坏时间复杂度沦为 $O(N)$；
- 连带着 `connect` 与 `isConnected` 的最坏复杂度也全跌为 $O(N)$！

> **结论**：表面上看，Quick Union 从 Quick Find 的 $O(1)$ 查询退步到了 $O(N)$。但别灰心，这一步极其关键——我们已经把全盘扫描的硬性开销转化为了树高问题。只要能扼制住树的高度的增长，性能爆发就近在咫尺。

### 加权快速合并：小树并入大树的质变

既然树太高是性能恶化的根源，那么在合并两棵树时，我们就不该随心所欲地任意指定从属关系。

这就进入了第四代设计：**加权快速合并**（Weighted Quick Union，简称 WQU）。

#### 核心规则：严禁大树挂在小树下

当我们面对两棵要合并的树时，我们有且仅有两种挂载选择：

```text
选择一 (小树并入大树):                选择二 (大树并入小树):
       0 (大树)                              3 (小树)
      / \                                   / \
     1   3 (小树并入)                      5   0 (大树并入)
         |                                    / \
         5                                   1   2
                                             |
                                             4
(整棵树最大高度保持较低)                   (整棵树高度被强行拔高了一层)
```

显然，选择一是明智之选。把小树接在大树根节点下方，原本大树中所有节点的深度保持不变，只有小树中少量节点的深度增加了 $1$；反之，若把庞大的树挂在小树下方，大树中成百上千个节点的深度都要被迫加深一层。

> **定义**：加权快速合并的核心规则是**小树挂大树**（Union-by-Size）——在合并两个集合时，先检查两棵树的节点总数，始终将节点数较少的树的根节点挂在节点数较多的树的根节点下方。

#### 为什么用大小而非高度

有些同学会问：既然怕树变高，为什么不直接按高度合并（Union-by-Height），把矮树挂在高树下？

答案是：按高度合并在理论上完全可行，而且渐进复杂度与按大小合并完全一致。但从工程实践来看，维护“树的节点总数”（重量）在代码实现上远比动态跟踪和维护“树的高度”简单直接。既然渐进性能相同，作为优秀的开发者，我们当然选择更简单、更不容易出错的方案。

#### 树高以对数级受限的严谨推导

为什么坚持“小树挂大树”，树高就绝不可能野蛮生长？我们通过几何直觉来推导：

树高究竟在什么情况下才会长高一层？

- **高度为 $0$**：单节点自成一棵树，元素数为 $1$；
- **高度为 $1$**：要想让高度达到 $1$，至少要把两个单节点合并，元素数至少为 $1 + 1 = 2$；
- **高度为 $2$**：如果我们拿一个 $3$ 节点树和一个 $1$ 节点树合并，按规则小树挂大树，高度仍然是 $1$；**唯有两棵同样高度为 $1$ 的树（各含 $2$ 个元素）合并时，矮的一方被迫挂下，树高才会增加到 $2$**。此时整棵树至少需要 $2 + 2 = 4$ 个元素；
- **高度为 $3$**：同理，必须由两棵同等规模、高度为 $2$ 的树（各含 $4$ 个元素）合并，高度才会递增到 $3$。此时节点总数至少为 $4 + 4 = 8$。

```text
高度 0: (1 个节点)
  O

高度 1: (至少 2 个节点)
    O
    |
    O

高度 2: (至少 4 个节点，由两棵高度 1 的树合并)
      O
     / \
    O   O
        |
        O

高度 3: (至少 8 个节点，由两棵高度 2 的树合并)
        O
      / | \
     O  O  O
       /|  |
      O O  O
        |
        O
```

看出规律了吗？
树高要想增长 $1$，整棵树的节点数量**必须至少翻倍**！

$$N \ge 2^h \implies h \le \log_2 N$$

> **结论**：在最坏情况下，包含 $N$ 个元素的加权快速合并树，其高度上限严格受制于 $\Theta(\log N)$。在这样的树中，寻找根节点最多只需爬 $\log_2 N$ 步。

因此，加权快速合并的各项操作时间复杂度为：
- `find`：$O(\log N)$
- `isConnected`：$O(\log N)$
- `connect`：$O(\log N)$

从 $O(N)$ 降到 $O(\log N)$ 是什么概念？
如果 $N = 10^9$（十亿级元素）：
- 原本最坏情况下单次查找要跑十亿步，需要耗费约 30 年的时间；
- 现在最坏只需爬约 30 步，几微秒内即可完成！在现实计算环境中，耗时直接从年级骤降至几秒钟。

### 路径压缩：越用越平的终极优化

加权快速合并已经把运行时间压到了对数级，但让我们回到一个哲学问题：**这已经是宇宙中性能极限的最优解了吗？我们还能做得更好吗？**

事实证明，我们还能更进一步。

#### 攀爬过程中的顺手牵羊

请思考这样一个场景：当调用 `isConnected(15, 10)` 时，程序沿着长长的链条一路往上攀爬寻找根节点：

```text
查找前 (路径狭长):
        0 (根节点)
        |
        1
        |
        5
        |
       11
        |
       15
```

从 $15$ 出发，经过 $11$、$5$、$1$，最终找到了真正的老祖宗 $0$。

在完成这次攀爬之后，我们其实已经获知了一个关键事实：$15, 11, 5, 1$ 的根节点全部都是 $0$！

既然我们已经耗费了算力爬完了这条路，为什么还要保留原来那种层层嵌套的深长结构，留给下一次调用再去受罪？我们完全可以在回溯的过程中，**顺手把沿途碰到的所有节点，全部直接挂载到根节点 $0$ 的下方**！

这就是**路径压缩**（Path Compression）。

```text
路径压缩后 (扁平化):
          0
      / / | \ \
     1 5 11 15 ...
```

#### 越用越平的自愈特性

路径压缩赋予了数据结构一种神奇的动态自愈特征：**随着操作的进行，整棵树会被打得越来越扁平；调用越频繁，后续的执行速度就越快**。这在思想上与计算机系统中的缓存和记忆化技术不谋而合。

实现路径压缩极其轻巧，在递归实现 `find` 时只需一行赋值：

```java
private int find(int i) {
    if (parent[i] < 0) {
        return i; // 自身即是根节点
    }
    // 递归寻找根节点，并顺手将当前节点的父指针直接指向根节点
    parent[i] = find(parent[i]);
    return parent[i];
}
```

#### 反阿克曼函数的数学奇迹

当我们在加权快速合并（WQU）的基础上引入路径压缩后，单次操作的均摊时间复杂度不再是 $O(\log N)$，而是惊人的：

$$O(\alpha(N))$$

这里的 $\alpha(N)$ 是数学上著名的**反阿克曼函数**（Inverse Ackermann Function）。

阿克曼函数是增长速度最恐怖的超幂级函数之一，而它的反函数 $\alpha(N)$ 则是增长缓慢到极致的函数：
- 在普通加权快速合并中，要让树高达到 $5$，需要 $2^5 = 32$ 个节点；
- 而在带有路径压缩的加权快速合并中，要想通过精心构造的操作让树高提升到 $5$，所需的节点数量是：

$$2^{2^{2^{2^2}}} = 2^{65536} \approx 10^{19728}$$

这个数字庞大到无法想象——要知道，我们整个可观测宇宙中所有基本粒子的总数，也仅仅在 $10^{80}$ 左右！

> **结论**：在人类已知的物理宇宙中，无论你的算法处理多么庞大的数据集（哪怕超过已知宇宙中所有原子数量），$\alpha(N)$ 的取值都绝不可能超过 $5$。在所有工程实践意义下，$O(\alpha(N))$ 在物理世界里等同于**常数时间** $O(1)$！

### 方案演进与性能全景对比

回顾整堂课，我们为了解决同一个接口需求，经历了五轮底层数据结构的推演与重构：

| 数据结构方案 | 数据结构内部核心表示 | `isConnected` 时间复杂度 | `connect` 时间复杂度 | 核心瓶颈 / 演进契机 |
| :--- | :--- | :--- | :--- | :--- |
| **连线集合列表** | `List<Edge>` | $O(N)$ (图遍历/搜索) | $O(1)$ (直接追加边) | 查询需全图搜索，逻辑极繁且慢 |
| **集合列表** | `List<Set<Integer>>` | $O(N)$ (遍历扫描 Sets) | $O(N)$ (定位并合并 Sets) | 嵌套容器繁重，常数与渐进性能皆差 |
| **快速查找 (QF)** | `int[] id` (存所属集合编号) | $\Theta(1)$ (单次数组取值) | $\Theta(N)$ (全量扫描替换) | 合并需遍历全数组改写，大规模写开销极大 |
| **快速合并 (QU)** | `int[] parent` (树状父节点) | $O(N)$ (沿链寻根) | $O(N)$ (沿链寻根后单点改写) | 树易退化为单链表，树高失控导致攀爬缓慢 |
| **加权快速合并 (WQU)**| `int[] parent` + 节点权重 | $O(\log N)$ (树高对数受限) | $O(\log N)$ (树高对数受限) | 小树并入大树，彻底消除细长链表 |
| **WQU + 路径压缩** | `int[] parent` + 寻根压缩 | $O(\alpha(N))$ (几乎等同常数) | $O(\alpha(N))$ (几乎等同常数) | 树越用越扁平，达到理论与工程的性能巅峰 |

通过改变底层那根不起眼的“木偶线”，我们让同一个接口在大规模调用下的表现发生了云泥之别。这正是数据结构设计的永恒魅力。

### 本讲提到的题目

在课堂推导加权快速合并（WQU）时，主讲人给出了一道经典的课堂实战选择题，用来考察大家对树的合并逻辑与底层数组修改的理解。

#### 课堂实选题还原

**【题目情景】**
现有两棵互不相交的树，其结构与底层数组状态如下：

- 树 $A$：以节点 $0$ 为根节点，统辖节点 $\{0, 1, 2, 3, 4, 5\}$，节点总数为 $6$；
- 树 $B$：以节点 $6$ 为根节点，统辖节点 $\{6, 7, 8, 9\}$，节点总数为 $4$。

```text
合并前的树状结构:
         0 (大小: 6)              6 (大小: 4)
       / | \                     / | \
      1  2  4                   7  8  9
      |
      5
      |
      3

底层 parent[] 数组核心切片:
parent[0] = -1 (或记录大小 -6)
parent[6] = -1 (或记录大小 -4)
parent[3] = 5
parent[8] = 6
```

**【题干问题】**
现在调用 `connect(3, 8)`。按照**加权快速合并（Weighted Quick Union）**的规则，底层数组应该执行哪项修改？

- A. 将 `parent[3]` 的值修改为 `8`
- B. 将 `parent[0]` 的值修改为 `6`
- C. 将 `parent[8]` 的值修改为 `3`
- D. 将 `parent[6]` 的值修改为 `0`

---

#### 试题详细解析

**第一步：排查无效选项（排除 A 和 C）**
$3$ 和 $8$ 只是各自树中的底层普通节点。合并集合的核心原则是**最高负责人之间的并购**，绝不改变底层节点的局部父子指向。如果把 `parent[3]` 改为 `8`，会使 $3$ 与其原来的父节点 $5$ 脱节，破坏原有拓扑。因此选项 A 和 C 毫无意义，直接排除。

**第二步：寻根与权重比较**
- 调用 `find(3)`：沿着 $3 \to 5 \to 1 \to 0$ 找到根节点为 $0$；树 $A$ 共有 $6$ 个元素。
- 调用 `find(8)`：沿着 $8 \to 6$ 找到根节点为 $6$；树 $B$ 共有 $4$ 个元素。

**第三步：按大小执行挂载**
根据加权快速合并规则，**小树必须挂在大树下方**：
- 树 $B$ 只有 $4$ 个元素，是小树；树 $A$ 包含 $6$ 个元素，是大树；
- 因此，小树的根节点 $6$ 必须放弃最高地位，成为大树根节点 $0$ 的子节点；
- 对应到底层数组的操作，就是把节点 $6$ 的父指针指向 $0$，即令 `parent[6] = 0`。

```text
合并后的树拓扑 (选项 D 对应的形态):
             0 (大小: 10)
        /  / | \  \
       1  2  4  5  6
       |           / | \
       3          7  8  9
```

**【正确答案】**
**D**

#### 课后作业提示：数组负数存树大小技巧

在后续的课后编程作业中，大家需要亲自动手实现加权快速合并。主讲人在课上特别点拨了业界一个极其优雅的实现技巧：

我们完全不需要额外开辟一个单独的 `size[]` 数组来记录每棵树的大小！
- 对于普通非根节点 $i$，`parent[i]` 存储非负整数，表示其父节点索引；
- 对于根节点 $r$：我们用**负数**同时充当“根节点标识”与“树的大小记录”！
  - 例如 `parent[r] = -1` 表示它是一个根节点，且当前树只包含 $1$ 个元素；
  - 若 `parent[r] = -6`，负号表明它是根节点，绝对值 $6$ 则直接表明该树包含 $6$ 个节点；
- 当合并两棵树时，只需比较两根节点数值的大小（更负的绝对值更大，代表大树），合并后直接让大树根节点的负数值累加小树的节点数即可。

这个技巧代码极其紧凑，大家在完成作业时请务必加以体会。
