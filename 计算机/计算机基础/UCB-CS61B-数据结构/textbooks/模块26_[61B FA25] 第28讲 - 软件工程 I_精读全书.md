### 认知容量与计算边界：为什么软件不同于传统工程

计算机科学与其他工程学科相比，存在一个极其本质的区别。

如果你去学化学工程，你必须时时刻刻关注反应器的温度、压强、反应速率等物理参数；如果你是生物工程师，研发人造器官时必须面对免疫排斥和生理相容性；土木工程师设计桥梁，必须严密计算钢材与混凝土的抗拉抗压强度；机械工程师设计传动轴，受限于材料力学与热力学定律。这些传统工程领域的核心挑战，始终是由客观的物理定律界定的。

但在软件世界里，除了极端追求算力的底层系统或高密度训练的大模型之外，当我们构建绝大多数应用、网站、工具与业务系统时，物理定律并不构成关键约束。你在这门课写项目时，不需要在计算机的物理内存大小或电压波动之间做精巧平衡，只要算法渐进复杂度合格、内存不泄漏即可。

> **定义**：**软件系统的规模上限，并不取决于物理法则，而取决于人类大脑的认知负荷（Cognitive Load）。**

你能把一个系统造得多大、多强大，唯一限制你的就是你个人或者你的团队，在大脑中究竟能同时理清多少逻辑。当系统真实度越来越高、功能越来越丰富（就像我们课程用的答疑排队系统，起初只有简单的队列功能，后来不断加入各种辅助机制），它的内部逻辑就会呈现指数级膨胀。到最后，团队里的任何一个人都无法把整个系统的运作细节完整装进脑子里。你不敢改，别人也不敢碰，新功能寸步难行，整个软件便走向衰亡。

调试器（Debugger）和测试框架能够辅助我们排查错误，但它们只是工具。要想真正阻止软件走向失控，唯一的解法是从系统设计的源头出发，让软件竭尽全力保持简单。

### 软件复杂性的本质与诊断

到底什么是复杂性？很多同学觉得代码行数多就是复杂，或者算法深奥就是复杂。但奥斯特豪特给出了一个直击工程本质的定义。

> **定义**：**复杂性（Complexity）是任何与软件系统结构相关的、导致系统变得难于理解和难于修改的因素。**

判断一个系统是简单还是复杂，标准极其纯粹：如果别人（或者两周后的你自己）看懂它很吃力、想要做点改动很困难，它就是复杂的；反之，如果看懂它一目了然、改动时心中笃定，它就是简单的。

#### 复杂性的成本视角

在工程实践中，复杂性从来不是一个抽象的学术指标，它直接等同于人力与时间成本。我们可以把系统的总体复杂度抽象成各个部分复杂度的加权和：

$$C = \sum_{p} (c_p \times t_p)$$

其中 $c_p$ 代表系统某一部分 $p$ 的固有复杂度，而 $t_p$ 代表开发者在这部分代码上花费的时间比例。

这个视角带来了一个极其重要的工程洞察：**如果某部分代码虽然内部极其复杂，但一旦写好就封箱稳定运行，几乎永远不需要人工去修改它，那么它对系统总体维护复杂度的贡献其实非常有限。**

举个例子，假设你正在写一个四阶龙格-库塔（Runge-Kutta）常微分方程求解器。为了数值稳定性与极限性能，这段底层数学代码必然极其紧凑晦涩、充满繁复的数学变换。但只要它的输入输出数学定义明确，之后几乎没人会去动它，它安安静静躺在底层充当可靠的齿轮，这种内部高复杂度完全是可以接受的。

类似的情况也发生在许多银行和航空系统的古老遗留代码（COBOL 系统）中——虽然代码陈旧晦涩，但只要它不出错、没人频繁修改，继续运转也是一种务实的平衡。相反，最致命的复杂性往往潜藏在那些与业务逻辑交织在一起、每天都需要添加新特性、每个迭代都被不同人动刀的代码里。那里的任何一点设计缺陷，都会让团队付出成百上千倍的代价。

#### 复杂性的三大临床症状

当你的代码正在走向腐化时，通常会出现以下三种典型的症状：

```text
+-------------------------------------------------------------------------+
|                          复杂性的三大临床症状                            |
+-------------------------------------------------------------------------+
| 1. 变更放大 (Change Amplification)                                       |
|    - 现象: 一个看似微不足道的小需求，迫使你在代码库十几处地方同步修改。    |
|    - 根因: 抽象泄露、硬编码与缺乏统一职责划分。                         |
+-------------------------------------------------------------------------+
| 2. 认知负荷 (Cognitive Load)                                            |
|    - 现象: 阅读并理解一段代码前，脑子里必须硬塞进大量外部上下文与魔术细节。|
|    - 根因: 变量意图模糊、满屏魔术数字、条件嵌套过深与过度简写。          |
+-------------------------------------------------------------------------+
| 3. 未知的未知 (Unknown Unknowns)                                         |
|    - 现象: 最致命的症状。你甚至不知道要完成修改必须改动哪些代码。        |
|    - 根因: 隐式依赖与脆弱的边界，动一处而暗中破坏了遥远模块。            |
+-------------------------------------------------------------------------+
```

上述框图归纳了系统复杂性失控时的三种典型破坏形式，由浅入深地反映了系统结构的脆弱程度。

##### 变更放大

所谓变更放大，是指你想做一个微小的功能变动，却发现必须修改代码库中大量互不相关的部分。

在早期的 CS 61B 里，我们曾把 2048 游戏作为学期初的第一个项目。玩家每次按下方向键，棋盘上的方块就会朝对应方向倾斜滑动并合并相同数字。我曾经看到过一位同学写出的真实核心倾斜逻辑：整个方法没有写任何循环，而是用成百上千行嵌套的 `if-else` 分支，把 $4 \times 4$ 棋盘上所有可能出现的方块排列组合硬生生地全部穷举了一遍！

坦白讲，这在某种程度上令人叹为观止——能靠人力把每种情况手工编织出来，就像不用织袜机纯靠手工一针一线织出一双厚袜子一样，确实需要惊人的毅力。但从软件工程的角度来看，这是一场灾难：

> **易错点**：如果需求发生微调，比如要把 2048 的棋盘从 $4 \times 4$ 扩展到 $5 \times 5$，这套代码将彻底作废，你必须从头手动重写成千上万个条件分支。更可怕的是，如果里面某处不小心漏写了一个 `-1`，编译器不会报任何语法错误，而你将在浩瀚的条件森林里永远找不出这个 Bug。

##### 认知负荷

认知负荷意味着在看懂或修改一小段逻辑之前，你必须在脑子里同时记忆过多的上下文信息。

在伯克利的 CS 10 课程里，曾有学生用图形化语言实现“战舰对决”（Battleship）游戏。代码虽然不算极长，但充斥着多重布尔与（AND）运算、到处重复计算的几何坐标、满屏没有任何命名解释的神秘小数（魔术数字）。哪怕你逻辑再清晰，读到第二行脑子就已经宕机了。

这就解释了为什么我在写代码时，宁可多声明几个看似“冗余”的中间命名变量，把一段复杂的布尔判断拆解成有叙事性的命名：

```java
// 具有良好叙事性、降低认知负荷的写法
boolean isBoardEdge = (x == 0 || x == width - 1);
boolean hasSameAdjacentTile = (currentTile.equals(nextTile));
if (isBoardEdge && hasSameAdjacentTile) {
    // 逻辑一目了然
}
```

顺便聊聊我个人的一个执念：我极其反感在表达式内部使用像 `++x` 这样的前置递增运算符。每当看到有人在嵌套表达式里夹带前置自增，那种感觉就像是有人把我推下深井还往我头上砸烂水果一样难受。我知道它的执行规则，计算机也执行得分毫不差，但它在人类大脑的阅读流里生硬地塞进了一个副反应。直接老老实实分两行写，代码读起来像自然语言一样顺畅，何必为了省一行而折磨读者的脑神经？

##### 未知的未知

这是最严重、最危险的复杂性表现。

如果一个系统存在变更放大，你至少知道自己得改很多地方；如果存在认知负荷，你至少知道需要去查阅哪份手册。但面对一个充斥着“未知的未知”的大型系统，**你甚至根本不知道自己需要了解什么才能完成修改**。你修改了模块 A 里的一个属性，完全无法预料它会以什么离奇的隐式依赖破坏了千里之外的模块 B。在像 `curl` 这样几十年积累的工业级代码库面前，如果缺乏清晰的抽象隔离，新人进去甚至连第一步该往哪放都不知道。

好的软件设计，追求的是**一目了然（Obvious）**。当一个模块设计得足够清晰时，任何人哪怕没有通读整个系统，也能在几分钟内看懂它的契约，胸有成竹地下手修改，并确信底层的抽象层会忠实履行它的职责。

### 掌控复杂性的双重路径：简洁设计与模块封装

面对不可避免的复杂性膨胀，工程师手中最强大的武器主要有两件：第一是把代码本身写得尽可能简单直观；第二是将系统解耦为高质量的模块。

#### 消除特例以实现直观设计

初学者在写代码时，最容易犯的一个毛病就是“打补丁”：发现一个特殊情况，就顺手在外面套一层 `if`；发现空指针，再加一层 `if (x == null)`。随着边缘情况越来越多，代码逐渐退化为千层饼般的特例处理。

真正的极简设计，是寻找能够**天然包容边缘情况的通用抽象**。

回想我们在 61B 前半学期讲解链表时引入的**哨兵节点（Sentinel Node）**。如果不用哨兵节点，双向链表在插入首节点、删除尾节点、处理空链表时，处处都需要特例判断：

```java
// 没有哨兵节点时：充斥特例判断
if (first == null) {
    first = newNode;
    last = newNode;
} else {
    newNode.prev = last;
    last.next = newNode;
    last = newNode;
}
```

而一旦引入了首尾相连的哨兵节点，无论链表是空、只有一个元素，还是有一万个元素，插入与删除的指针操作完全统一，所有原本必须存在的特殊情况分支在一瞬间全部蒸发。初学者可能觉得凭空造一个不存真实数据的节点不够直观，但这恰恰是高级工程思维的体现——用优美的一致性消除了散落各处的认知陷阱。

#### 模块化与深度接口

解决复杂性的第二大支柱是**模块化设计（Modular Design）**。

模块化的理想状态是把系统拆解成若干相对独立的小单元，每个单元各司其职。一个优质的模块必须具备一把锋利的“隔离刀”：向外暴露极其干净、高内聚、易理解的接口，而把所有复杂的实现细节密不透风地锁在内部。

对比一下 Python 生态里的可视化库就能明白这一点。早期许多人在使用 Matplotlib 时感到极度痛苦，因为它的 API 设计得极其琐碎低阶，稍微调个双轴或者图例位置，就要去操控各种底层坐标轴对象与参数；而像 Plotly Express 这样的库，抽象层次极高，开发者直接用一行声明式语句传进数据结构就能绘制出精美的交互图表。当接口能够有效吸收复杂性时，调用者才能真正实现心智自由。

### 战术性编程与战略性编程的抉择

在《软件设计哲学》中，奥斯特豪特将工程师的日常开发模式清晰地划分为两类：**战术性编程（Tactical Programming）**与**战略性编程（Strategic Programming）**。

| 维度 | 战术性编程 (Tactical) | 战略性编程 (Strategic) |
| :--- | :--- | :--- |
| **首要目标** | 尽快让功能跑起来（Just make it work） | 保证系统长期结构的健康与可演进性 |
| **应对 Bug** | 在出错处贴补丁、加特殊分支或复制相似代码 | 追溯根本原因，重构并修复设计缺陷本身 |
| **短期收益** | 极高，今天下午就能提测交差 | 较低，前期需要投入时间思考与对比方案 |
| **长期后果** | 复杂性雪崩，代码变成难以维护的泥潭 | 代码清晰易懂，后续增删功能极为轻松 |
| **典型心态** | “我还有三门作业要交，先写完再说” | “多花十分钟理顺结构，为后续省下一整天” |

#### 短视修补与长远架构

绝大多数初学者和疲于奔命的开发者，日常都在进行战术性编程。比如在写 Project 4 时，为了让界面上的“历史记录”按钮能够工作，你可能会图快直接复制旁边一个类似功能的方法，顺手改掉几个变量名；或者为了应付一个边缘输入，直接在函数开头加一个特殊 `if` 拦截。

从单个任务的角度来看，这么做非常划算，你今天可以早点打卡下班。但软件工程是一场马拉松：你引入的每一个小复制、每一个特殊分支，都在代码库里埋下了一颗微型地雷。等到 Project 5 这种完全开放的大项目时，缺乏前期规划的战术代码最终会变成一场灾难——功能或许勉强跑通了，但内部结构一团糟，每次哪怕想给游戏界面加个倒计时，都会牵动几十处逻辑崩溃。

> **结论**：**战略性编程是成为优秀软件工程师的第一步。你必须深刻意识到，代码仅仅“能跑”是远远不够的。在真实长寿的系统中，系统的长期结构远比当下的几行功能更重要。**

战略性编程要求我们“为变更而设计”（Design for change）。在动手敲下第一行代码前，不要盲目拥抱脑海里跳出的第一个点子，而是强迫自己构思两到三种不同的方案，甚至写几个最小化的核心模块原型来试水。当你发现既有设计无法自然支持新需求时，坚决不要靠打补丁去掩盖设计缺陷，而是回过头去重构设计本身。

从普通工程师向高级系统架构师进阶的核心分野，就在于你是否具备这种前瞻规划的能力。当你在初创公司组建团队搭建系统时，优秀的架构师懂得引入像 Terraform 这样的自动化编排工具，把环境与部署架构化；懂得哪些模块应该抽象、哪些边界应当固化，从而让系统从容应对未来的演进。

#### 硅谷工业界的技术文化反思

在工业界，这两种哲学曾引发过波澜壮阔的碰撞。

最典型的战术代表是早期的 Meta（Facebook）。他们著名的座右铭曾是“快速行动，打破常规”（Move fast and break things）。新人入职第一周就被允许直接修改并上线生产环境代码，这种极端的战术文化让 Facebook 在早期以不可思议的速度试错、抢占社交网络市场。但代价同样极其沉重：整个代码库在很长一段时间里被业界公认是一团乱麻，缺乏完备的测试与注释，修改极其痛苦且动辄崩溃。后来，随着体量增长，他们不得不把口号悄悄修改为“在稳定基建上快速行动”（Move fast with stable infrastructure），为早期的战术债务偿还了高昂利息。

相反，像 Google 和 VMware 则是战略性编程的坚定信徒。VMware 专注于底层的虚拟化引擎，必须在操作系统内核之间做到绝对的严密与高可靠；Google 对工程素养、代码审查（Code Review）和测试覆盖率有着极其严苛的标准。这种注重代码质量的战略文化，使其系统能在数十年中从容支撑全球规模的扩张，并持续吸引着最顶尖的技术人才。

当然，我们不能脱离现实搞教条主义。许多初创公司处于生死边缘，如果不在现金耗尽前把原型（PoC）推上线拿到下一轮融资，公司明天就会倒闭。在那种极限场景下，战术性冲刺是生存所必需的手段。但在一个结构良好的代码库里工作，那种身心舒畅的掌控感，是任何整天在屎山代码里救火的人无法体会的。

#### 大语言模型时代的工程根基

这两年人工智能飞速发展，很多同学难免产生疑问：现在大语言模型（LLM）写代码这么强，我们学这些软件工程哲学还有用吗？

事实恰恰相反。大语言模型最擅长的，恰恰是极其快速地执行**战术性编程**——你给它一个明确的小函数规范，它几秒钟就能吐出一段能跑的代码。

但我曾和 Pensive 团队的创始人深入交流过。他们是一个类似 Gradescope 的作业批改平台，整个团队只有两位创始人，却支撑起了极其庞大的系统。他们的代码库大量依靠大语言模型辅助编写，从前端交互一直写到后端服务。但他们之所以能成功驾驭 AI，是因为两位创始人本身都是极其老练的资深软件工程师。每当 LLM 出现幻觉、生成了看似能跑但结构反常的脆弱代码时，他们能一眼看穿其中的架构隐患，并迅速出手纠偏。

> **提示**：在未来的软件工程职场中，你们亲手敲键盘写出的代码量可能会大幅减少，许多样板代码都会交由模型生成。但如何设计模块边界、如何定义清晰的数据流、如何识别潜在的架构腐化，这些系统层面的宏观判断力不但不会贬值，反而会成为决定你天花板的核心竞争力。如果你自己不懂软件工程，把成千上万行由 AI 生成的战术代码拼在一起，最终只会造出一个连上帝都无法调试的超级泥潭。

### 系统的护城河与依赖的边界

在重构与模块设计的具体落地中，有两个经常被同学问起的关键问题：其一是重构时如何保证不把系统搞垮；其二是到底该什么时候自己写、什么时候外包给第三方依赖。

#### 如何在重构巨型系统时不破坏现有功能

面对一个庞大而古老的代码库，你想要重构它的设计，唯一的护城河就是**立体化的测试体系**。

在 61B 课上，我们写的绝大部分测试属于**单元测试（Unit Tests）**，用 Google Truth 或 JUnit 针对单一方法或单一数据结构进行隔离验证。但在复杂的工业级多层系统中，仅靠单元测试是远远不够的。比如一个系统分为前端、业务层、RPC 传输层和数据库层，如果你要对处于核心位置的中间层进行彻底重构，你就必须引入**模拟数据（Mock Data）与桩对象（Stubs）**，把软件栈的上下游环境严密模拟出来，配合集成测试与端到端测试，才能在不伤筋动骨的前提下完成蜕变。

#### 依赖引入与外包的经济学

在现代软件工程中，直接借用他人的成熟代码（外包依赖）已经成为常态。计算机科学最核心的思想就是把抽象问题拆解并委派出去，这种层级分解与现代经济学中的产业分工有着深刻的同构性。

但依赖的边界到底划在哪里？

一方面，存在一些**必须坚决外包**的铁律。最著名的原则就是：**千万不要自己手写加密库！** 密码学涉及极其深奥的数学原理与侧信道攻击防护，即便是一个资深工程师自己手写的 AES 或 RSA 算法，也必然充满致命的安全漏洞。在学习阶段为了理解原理自己动手写写挺好，但在实际生产中，必须使用经过全世界顶尖专家千锤百炼的标准安全库。

另一方面，我们也必须对滥用微依赖保持高度警惕。如果你关注过前端生态，一定听说过著名的 `left-pad` 事件——这个仅有十几行代码、仅仅用来给字符串左侧填充空格的小模块，有一次因为作者撤包，引发了全网数以万计顶尖项目的构建大雪崩；甚至在 JavaScript 生态里还一度充斥着类似 `is-odd`、`is-even` 这种仅用于判断奇偶数的独立库。过度依赖琐碎的外部轮子，不仅不会带来架构上的优势，反而把自己的系统绑定在了一条脆弱而不可控的外部依赖链上。

### 实战演练：六边形世界的模块化拆解

讲完了这些宏观哲学，我们必须亲自动手写点代码。在接下来的 Project 5 中，大家需要用我们编写的瓦片引擎（Tile Engine）构建一个由房间和走廊组成的随机探索世界。今天我们不妨把这个要求换成一个更有趣的题目：如何编写代码，在屏幕上生成一个类似经典桌游《卡坦岛》（Settlers of Catan）的由六边形拼接而成的奇妙大陆？

```text
                  +-------------+
                 /               \
                /                 \
  +------------+   [山脉六边形]    +------------+
 /              \                 /              \
/                \               /                \
+  [草地六边形]   +-------------+   [森林六边形]   +
\                /               \                /
 \              /                 \              /
  +------------+   [麦田六边形]    +------------+
                \                 /
                 \               /
                  +-------------+
```

上图展示了卡坦岛棋盘的核心构成：由若干不同资源地形（山脉、草地、森林、麦田）的正六边形紧密咬合拼接而成。

面对这个需求，很多同学的第一反应是立刻跳进细节：算每一个像素点的坐标、写一大堆外层 `for` 循环和内层 `for` 循环。但这正是典型的战术式思维。让我们用模块化的解构思维，一步步把这个大问题拆解成优雅的基础单元。

#### 瓦片引擎与世界模型

首先看一下我们为 Project 5 提供的底层基础设施——瓦片引擎。它的核心结构非常简单：

```java
// 创建一个 50x50 的世界画布：本质是一个二维 TETile 数组
int width = 50;
int height = 50;
TERenderer ter = new TERenderer();
ter.initialize(width, height);

TETile[][] world = new TETile[width][height];
```

在这个模型中，整个世界被量化成了一个 $50 \times 50$ 的网格矩阵。我们要做的，无非是将特定的瓦片对象（比如 `Tileset.TREE`、`Tileset.FLOWER`、`Tileset.GRASS`）填入这个二维数组的相应坐标 `world[x][y]` 中，最后由渲染器一次性画在屏幕上。

#### 六边形类的状态设计与责任划分

要画出卡坦岛，最自然的核心抽象单元显然是一个**六边形类（`Hexagon`）**。

那么，一个六边形对象内部到底应该包含哪些状态属性？在课堂讨论中，大家很快达成了共识：

1. **尺寸大小（Size / 边长 $s$）**：决定六边形的几何规格；
2. **地形类型（Tile Type）**：决定该六边形由树木、花朵、草地还是山脉填充；
3. **空间定位（Position）**：记录它在整个二维世界中的坐标。

在存储坐标时，我们应当选择哪个参考点？有人提议存中心点，但对于离散的网格点阵来说，中心点在边长为偶数时容易出现浮点截断；因此，直接存储该六边形包围盒的**左上角坐标（`topLeftX`, `topLeftY`）**会清晰得多。

> **易错点**：千万不要冗余存储。六边形上方的 Y 坐标就是左上角的 Y 坐标，不需要单独再开一个变量存一遍；坐标一处定义即可，重复存储必然带来数据同步的隐患。

紧接着是一个更具深度的软工设计抉择：**六边形内部是否应该维护一个包含所有邻居六边形的列表？**

很多同学在直觉上倾向于在 `Hexagon` 类里加一个 `List<Hexagon> neighbors`。但仔细推敲就会发现：谁该对整个世界的空间拓扑负责？是底层的单个六边形，还是上一层的地图生成器？

如果让每个六边形自己去探测、绑定六个方向的邻居指针，单个六边形类的复杂度将急剧膨胀，它不仅要管自己的绘制，还要管拓扑关系。相反，让上一级的世界管理者统一用一个集合管理所有六边形，而把 `Hexagon` 类保持为一个纯粹负责描述单体几何与填充的“轻量对象”，职责边界会干净得多。

#### 算法拆解为底层原语

明确了类结构后，最核心的问题来了：如何把一个六边形真正“画”进二维数组里？

如果我们直接在一个巨型方法里试图用四重嵌套循环把整个六边形画出来，逻辑会瞬间变成一团乱麻。让我们观察一个正六边形（以边长 $s=3$ 为例）在离散网格中的扫描线规律：

```text
Row 5:       * * *          (y = 5, offset = 2, length = 3)
Row 4:     * * * * *        (y = 4, offset = 1, length = 5)
Row 3:   * * * * * * *      (y = 3, offset = 0, length = 7)
Row 2:   * * * * * * *      (y = 2, offset = 0, length = 7)
Row 1:     * * * * *        (y = 1, offset = 1, length = 5)
Row 0:       * * *          (y = 0, offset = 2, length = 3)
```

上图清晰地展示了六边形在像素网格上的对称结构：它由若干行水平线段逐行堆叠而成，每行线段的起始偏移量与长度呈现严密的几何渐变。

通过这个几何分解，你会发现**最底层的原子操作根本不是画六边形，而是在指定位置画一条水平线！**

这就是战略性分解的力量——我们首先提取出一个极其清晰好用的辅助方法：

```java
/**
 * 在世界网格中的指定坐标处，绘制一条指定长度的水平瓦片线段。
 *
 * @param world  世界瓦片网格
 * @param startX 线段起点的 X 坐标
 * @param y      线段所在的 Y 坐标
 * @param length 线段的长度
 * @param tile   要填充的瓦片类型
 */
public static void drawHorizontalLine(TETile[][] world, int startX, int y, int length, TETile tile) {
    for (int xOffset = 0; xOffset < length; xOffset++) {
        world[startX + xOffset][y] = tile;
    }
}
```

有了这个原子画线工具，绘制一个完整的六边形就变成了非常直观的数学递推：整个六边形由 $2s$ 行水平线构成，上半部分线段长度从 $s$ 开始每行增加 $2$、起始 X 坐标每行递减 $1$；下半部分完全镜像反转。每个复杂的上层逻辑，都被分解为了对极其简单可靠的底层工具的有序调用。在课堂演示中，我们甚至顺手用它把锁着的门（`Tileset.LOCKED_DOOR`）整整齐齐地排成了一道坚固的长廊。

### 课后思考与后续展望

面对一个庞大的软件系统，到底该花多少时间在前期规划上，又该什么时候动手敲代码？

这在软件工程中并没有一条死板的黄金分割线。它更像是一位老工匠打磨器物的直觉手艺：当你经验尚浅时，多做前瞻规划、多在草稿纸上对比推演几种架构方案，能够最大程度避免你在几千行代码的泥潭里溺水；而当你日后手艺日臻纯熟、写过无数系统之后，许多优秀的架构直觉早已融化在你的手指之间，即便直接上手塑造，代码也会天然具备良好的形态。
