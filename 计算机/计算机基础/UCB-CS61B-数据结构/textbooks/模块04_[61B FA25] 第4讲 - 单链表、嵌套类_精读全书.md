## 单链表、封装与哨兵节点：从裸递归走向健壮数据结构
> 对应块：BLK04 | 覆盖分集：P07 | 块标题（分集名）：《[61B FA25] 第4讲 - 单链表、嵌套类》

在上周的课里，Peyman 带大家构建了最初的整数列表。今天上课前，我先向大家透露一个 Peyman 当时没说的秘密：他搞出来的 `IntList`，实际上是一个没有任何封装保护的裸递归列表。这就好比伊甸园里的人还没吃禁果，根本不知道自己其实光着身子。今天这堂课，你们就来尝尝这颗开启认知的苹果。

为什么我们要对裸递归列表大动干戈？它到底有什么隐患？
这种裸列表虽然在 Java 里完全合法、能够运行，但使用起来却极为折磨人。使用者必须精通引用传递、深刻理解递归思维，还得小心翼翼地追踪每一步的指针赋值。只要稍微漏掉一个细节，整个程序就会失控。如果连一个三年级老师想存几个学生的成绩，都必须在代码里被迫处理晦涩的引用和多余的 `null`，这种数据结构显然是不合格的。

今天我们的任务，就是将底层的裸露递归细节彻底隐藏起来，让用户用起来无比轻松自如。我们将通过一步步现场重构，进行连续六项关键改造，最终构建出一个健壮、优雅且安全的单链表数据结构。

### 走出伊甸园：裸递归列表的隐患与痛点

在进入改造之前，我们先直面裸递归列表带来的核心困扰。

在裸递归的 `IntList` 设计中，数据结构本身就是一个个直接串联的节点。当用户持有一个 `IntList` 引用时，这个变量直接指向了数据结构的最深处。这种引用关系就像致命的辐射直接从核心向外喷涌一样，狂野、危险而且极度脆弱。

```text
用户变量 L
    |
    v
+--------+------+      +--------+------+
| item:5 | next | ---> | item:10| next | ---> null
+--------+------+      +--------+------+
```

> **上图说明**：在裸递归结构中，用户的引用变量 `L` 直接指向链表首个节点。用户可以随意通过 `L.next` 篡改底层节点连接。

如果想用 `IntList` 创建一个包含 15、10、5 的列表，你的代码必须写成这样：

```java
IntList L = new IntList(15, null);
L = new IntList(10, L);
L = new IntList(5, L);
```

请仔细观察这段代码：用户只是想存一个数字 15，却不得不显式传入一个奇怪的 `null`；想在最前面添加一个数字，必须手动创建一个新节点并重新赋值给引用变量 `L`。如果要把代码给外行或非计算机专业人员使用，他们很难理解为什么要写这些冗余的样板。

更要命的是，操作裸递归列表要求极高的思维负荷。要理解它的运行机制，你必须在脑海里画出引用环境图，去追踪每一步的内存地址变更。一旦多处变量交叉引用同一个底层节点，任何一处未经深思熟虑的指针修改都会引发全局性的灾难。

因此，我们的第一项改进就是**剥离身份与重命名**：
Peyman 之前定义的类名叫 `IntList`，但这其实名不副实——它本质上只是链表中的一个个“节点”（Node），而不是真正的“列表容器”（List）。我们把这个类重命名为 `IntNode`，将其字段明确声明为 `item` 和 `next`：

```java
public class IntNode {
    public int item;
    public IntNode next;

    public IntNode(int i, IntNode n) {
        item = i;
        next = n;
    }
}
```

改名只是澄清了概念：`IntNode` 只是原材料，接下来我们需要为它披上文明的外衣。

### 引入中间层：面向用户的包装类 SLList

为了让使用者摆脱裸递归的泥潭，我们必须在用户和底层节点之间搭建一道防火墙。这就是我们要创建的新类：`SLList`（Single Linked List，单向链表）。

#### 搭建基础包装类与构造函数

`SLList` 是一个面向最终用户的类，专门用来包装底层的裸递归节点。用户以后交互的对象是 `SLList` 容器本身，而不再直接触碰底层的 `IntNode`。

在 `SLList` 内部，我们用一个名为 `first` 的引用变量来记录底层链表的第一个节点：

```java
public class SLList {
    public IntNode first;

    public SLList(int x) {
        first = new IntNode(x, null);
    }
}
```

通过这层间接封装，我们在用户体验上迈出了巨大的一步。对比一下两者的实例化方式：

```java
// 使用原有的裸递归列表 IntList
IntList L1 = new IntList(10, null);

// 使用带有中间层封装的 SLList
SLList L2 = new SLList(10);
```

两者的差异显而易见：用户想创建一个存有整数 10 的列表，直接写 `new SLList(10)` 即可。那个多余的 `null`、底层的内存分配以及节点的串联逻辑，全部被关在了包装类的黑盒之内。

```text
用户变量 L2
    |
    v
+---------------+
|    SLList     |
|  first: ----+ |
+-------------|-+
              |
              v
        +--------+------+
        | item:10| next | ---> null
        +--------+------+
          (IntNode)
```

> **上图说明**：引入中间层后，用户变量 `L2` 指向的是稳定的 `SLList` 容器对象，容器内部的 `first` 指针负责维系到底层 `IntNode` 的连接。

#### 首部操作的直观实现

有了容器类之后，我们来为它扩展首部添加与读取功能：`addFirst` 与 `getFirst`。

要在列表开头插入一个新元素 $x$，底层指针该如何流转？原来的 `first` 节点不再是表头，新的 `IntNode` 必须装载 $x$，并且它的 `next` 应当精准指向原本的旧 `first` 节点，最后再把容器的 `first` 指针更新为这个新节点：

```java
public void addFirst(int x) {
    first = new IntNode(x, first);
}

public int getFirst() {
    return first.item;
}
```

> **注意**：在 `getFirst()` 中，我们绝不能直接返回 `first`（它的类型是 `IntNode`），而必须解引用返回节点内部的具体数值 `first.item`。

现在让我们以用户的角度来审视整套操作流程：

```java
SLList L = new SLList(15);
L.addFirst(10);
L.addFirst(5);
int x = L.getFirst(); // 获得 5
```

这比之前的裸列表舒服太多了！用户不需要知道什么是递归，不需要手写 Scheme 风格的 `new IntList(5, L)` 重新赋值，更不需要去理会底层的指针变换。所有的操作都是直接向容器发送指令。对于普通开发者来说，心智负担降到了最低。

### 访问控制与信息隐藏：筑牢信任边界

虽然有了 `SLList` 包装，但如果代码保持原样，程序依然潜藏着巨大的安全隐患。

#### 从 public 到 private 的访问修饰符转变

假设某位粗心或恶意的程序员拿到了我们刚才写的 `SLList` 实例，他完全可以绕过我们精心提供的方法，直接写出下面这样的代码：

```java
SLList L = new SLList(15);
L.addFirst(10);
L.first.next.next = L.first; // 致命的指针篡改！
```

这行代码把第二个节点的 `next` 重新赋值指向了表头 `first`。在内存中，原本线性的链表瞬间变成了一个死循环的环形拓扑：

```text
+---------------+
|    SLList     |
|  first: ----+ |
+-------------|-+
              |
              v
        +--------+------+        +--------+------+
        | item:10| next | -----> | item:15| next | --+
        +--------+------+        +--------+------+   |
            ^                                        |
            +----------------------------------------+
```

> **上图说明**：外部代码强行穿透容器直接修改 `first.next.next`，导致链表尾部回绕至表头，产生无限死循环。

一旦形成环形结构，任何试图遍历该链表的操作都将彻底卡死崩溃。允许最终用户直接刺入并破坏对象内部结构是不可接受的。

解决之道在于**信息隐藏**（Information Hiding）。我们只需把 `first` 变量从 `public` 改为 `private`：

```java
public class SLList {
    private IntNode first;
    // ...
}
```

将 `first` 声明为 `private` 之后，外部类（例如业务项目代码）如果试图直接访问 `L.first`，Java 编译器会在编译阶段直接报错并拒绝通过：

```text
Error: first has private access in SLList
```

> **定义**：
> - `public`：公有访问权限，任何外部代码都可以自由调用或修改。
> - `private`：私有访问权限，仅允许当前类内部的方法进行读写，对所有外部类完全封闭。
> - `package-private`（包访问权限，即不写任何修饰符）：仅同包内的类可见。

#### 汽车接口哲学与封装的真正意义

为什么我们要如此强调 `private`？
打个生动的比方：这就像我们日常开的汽车。每一辆汽车都向驾驶员暴露了一套标准、统一的**公共接口**（Public Interface）——方向盘、油门踏板、刹车踏板和换挡杆。我们坐进车里，踩下油门车辆就会加速，踩下刹车车辆就会减速。

但是在汽车底盘和引擎盖下方，存在着庞大而复杂的**私有实现细节**（Private Implementation）：燃油管路、喷油嘴、节气门开度控制器，或者在电动车里的电池逆变器与无刷电机驱动模块。作为司机，我们不需要知道燃油管路具体如何走线，也不需要亲自去调节进气阀门；如果把燃油管路的控制旋钮直接放在仪表盘上让司机手动调节，汽车出事的概率会成倍激增。

在软件设计中亦是同理：
- 隐藏细节，降低认知负担：调用者只需关心“这辆车怎么开”，而不必关心“引擎怎么喷油”。
- 提供自由演进的豁免权：只要公共方法签名保持不变，你可以随意在类内部修改字段名。今天你觉得底层指针叫 `first`，明天你想改名叫 `head` 甚至 `gert`，外部使用者完全无感，他们的业务代码一行都不需要改动。

> **提示**：Java 中的 `private` 访问控制是一种面向程序员的**架构防呆提示**，而不是绝对的计算机安全防线。在技术上，经验丰富的开发者通过 Java 的反射机制（Reflection）依然能够强行读取或修改私有变量，但这绝不属于常规的日常开发实践。`private` 设立的初衷是明确划定系统边界，避免无意识的错误调用。

### 辅助类的归位：嵌套类与静态化优化

现在我们有了两个类文件：`SLList.java` 和 `IntNode.java`。但仔细思考会发现：在这个世界上，除了 `SLList` 之外，还有其他任何地方需要单独使用 `IntNode` 吗？并没有。

`IntNode` 纯粹是为 `SLList` 服务的底层脚手架，它根本没有独立存在的必要。如果一个类明显依附于另一个类存在，最佳实践就是将其收拢，做成**嵌套类**（Nested Class）。

#### 私有嵌套类的设计规范

我们将整个 `IntNode` 的代码直接搬进 `SLList` 类内部：

```java
public class SLList {
    private static class IntNode {
        public int item;
        public IntNode next;

        public IntNode(int i, IntNode n) {
            item = i;
            next = n;
        }
    }

    private IntNode first;

    public SLList(int x) {
        first = new IntNode(x, null);
    }
    // ...
}
```

嵌套类的访问权限同样应当设定为 `private`。既然外部世界根本不需要知道节点的存在，那么让这个嵌套类成为 `SLList` 独享的私有辅助类是最合理的选择。

> **规范提示**：在代码组织结构上，我们通常建议将嵌套类置于类的最顶端，中间放置实例变量与构造函数，最下方放置具体的业务方法。

#### static 关键字背后的内存节约

请密切注意上面代码中嵌套类的修饰符：`private static class IntNode`。
这里为什么加上了 `static` 关键字？

让我们观察 `IntNode` 内部的所有代码：它的构造函数接收 `i` 和 `n`，赋值给自己内部的 `item` 和 `next`。请问：`IntNode` 的任何方法或构造器中，有没有调用过外部 `SLList` 的任何实例变量或方法？
答案是一次都没有。`IntNode` 完全不需要读取外部容器的属性。

在 Java 中，非静态内部类与静态嵌套类有一个极其关键的底层区别：
- **普通内部类（Non-static Inner Class）**：每个内部类实例在创建时，底层都会隐式持有一个指向其外部宿主类实例的引用。
- **静态嵌套类（Static Nested Class）**：彻底切断与宿主实例的隐式联系，它无法直接访问外部类的实例变量，但也不再需要存储指向外部宿主的引用指针。

不要小看这个指针。在 64 位 JVM 中，一个对象引用通常占据 8 字节（64 位）。每个 `IntNode` 内部原本只需要存储一个 32 位的整型 `item` 和一个 64 位的 `next` 指针；如果让它成为非静态内部类，它就必须额外塞入一个 64 位的宿主引用。

使用 `static` 修饰嵌套类，相当于为每个节点直接节约了近三分之一的内存空间！在处理数百万节点的大规模数据结构（例如图搜索、海量拼图求解器等核心场景）中，这种内存开销的优化是至关重要的。

### 从递归推导到常数查询：列表长度的性能跨越

接下来，我们为 `SLList` 扩充两个基本操作：在末尾添加元素的 `addLast(int x)`，以及获取列表当前元素总数的 `size()`。

#### 尾部插入与非递归容器中的递归实现

向链表尾部追加元素，逻辑非常直观：先找到当前链表的末尾节点（即 `next == null` 的节点），然后让它的 `next` 指向新创建的节点：

```java
public void addLast(int x) {
    IntNode p = first;
    while (p.next != null) {
        p = p.next;
    }
    p.next = new IntNode(x, null);
}
```

接着看 `size()` 方法。如果我们要用递归的思路来计算长度，直觉上会写成：
“如果下一个节点为空则返回 1，否则返回 1 加上下一个节点的 `size()`”。

但这在 `SLList` 中遇到了阻碍：`SLList` 容器本身并不是节点，它根本没有 `next` 属性！你不能在 `SLList` 自身上进行递归调用，因为 `SLList` 只有一个，它代表的是整个完整列表。

面对这种“外部容器非递归、内部节点递归”的结构，Java 开发中有一个非常巧妙且经典的实战技巧：**私有递归辅助函数**（Private Recursive Helper Method）。

我们可以在类内部设计一个接收 `IntNode` 作为参数的私有辅助方法，再让公开无参的 `size()` 方法去调用它：

```java
/** 返回以 p 为头节点的裸链表的大小 */
private static int size(IntNode p) {
    if (p == null) {
        return 0;
    }
    return 1 + size(p.next);
}

public int size() {
    return size(first);
}
```

这个设计极其优雅：外部调用者只需使用轻巧的 `L.size()`，而在容器内部，私有辅助函数接过 `first` 指针，沿着底层的裸递归链条顺藤摸瓜完成计数。

#### 空间换时间：长度缓存的设计权衡

虽然上面的递归辅助方法精妙绝伦，但在工程上，我们必须无情地指出它的致命软肋：**性能危机**。

让我们考虑一个实际的运行场景：
假设递归版本的 `size()` 方法在处理一个包含 1000 个元素的链表时需要耗时 2 秒。那么当链表规模扩大到 100 万个元素时，调用一次 `size()` 需要耗费多长时间？

因为该算法必须严格遍历链表中的每一个节点，其执行时间与链表长度呈严格的正比例线性关系（$O(N)$）。链表长度扩大了 1000 倍（从 $10^3$ 增长到 $10^6$），耗时也将同等扩大 1000 倍——整整需要 **2000 秒**！让用户为了查一次列表长度苦等半个多小时，这是绝不可接受的。

如何彻底解决这个问题？
答案是**缓存**（Caching），用微小的空间开销换取极致的时间效率。

我们在 `SLList` 内部增加一个整型实例变量 `private int size`。一旦我们在对象内部开辟了保存元数据的空间，整个设计格局便焕然一新：

```java
public class SLList {
    // ...
    private int size;

    public SLList(int x) {
        first = new IntNode(x, null);
        size = 1;
    }

    public void addFirst(int x) {
        first = new IntNode(x, first);
        size++;
    }

    public void addLast(int x) {
        size++;
        IntNode p = first;
        while (p.next != null) {
            p = p.next;
        }
        p.next = new IntNode(x, null);
    }

    public int size() {
        return size;
    }
}
```

> **提示**：Java 允许成员变量与方法同名，因此字段 `private int size` 与公共查询方法 `public int size()` 完全可以和谐共存。

让我们算一笔账：世上没有免费的午餐。采用这种方案，每次执行 `addFirst` 或 `addLast` 时，我们都必须多执行一次微小的 `size++` 操作；但换来的收益却是无与伦比的——无论链表里有一千个、一百万个还是一亿个元素，调用 `L.size()` 都能在瞬间（常数时间 $O(1)$）直接返回结果，彻底消除了遍历带来的漫长等待。

更重要的是，裸递归的 `IntList` 根本无法使用这种缓存技巧，因为用户直接面对裸节点，根本找不到合适的位置来存储统筹全局的元数据；而我们在用户与节点之间建立的 `SLList` 中间层，天然就是挂载这些全局状态的最佳场所。

### 终结边界特例：哨兵节点的设计艺术

一切看起来都很完美，直到我们决定支持一个自然而然的功能：**空列表**（Empty List）。

#### 空指针崩溃与条件特例的局限

在真实世界中，并不是所有列表一生下来就必须有初始数据。我们需要一个无参构造函数来创建空列表：

```java
public SLList() {
    first = null;
    size = 0;
}
```

看起来很自然：空列表中 `first` 为 `null`，`size` 为 0。
然而，灾难悄然降临。请看下面这段看似平淡无奇的调用顺序：

```java
SLList L = new SLList();
L.addLast(10); // 运行时抛出 NullPointerException！
```

为什么程序直接崩溃了？
回看我们在 `addLast` 里写的逻辑：

```java
IntNode p = first;
while (p.next != null) {
    p = p.next;
}
```

当链表为空时，`first` 是 `null`，变量 `p` 同样变成了 `null`。紧接着代码执行 `p.next`，这无异于对着虚无与永恒的空白发问：“你下一个是谁？”Java 虚拟机会毫不留情地抛出空指针异常（`NullPointerException`）。

常规的修补思路是打补丁——为“空列表”单独开辟一条特殊分支：

```java
public void addLast(int x) {
    size++;
    if (first == null) {
        first = new IntNode(x, null);
        return;
    }
    IntNode p = first;
    while (p.next != null) {
        p = p.next;
    }
    p.next = new IntNode(x, null);
}
```

这种方案确实能跑通，但作为有追求的程序员，我们必须对这种充斥着 `if` 特殊情况修补的代码保持强烈的警惕与反感。

在线性单链表里，特例也许只有一个 `first == null`；但若将来面对更复杂的数据结构（例如二维网格、环形拓扑、平衡二叉树或双向链表），顶部、底部、侧边、拐角每一个边界情况都需要单独写一个 `if` 判断。动辄四五个甚至六七个 `if` 补丁堆叠在一起，代码会变得极其臃肿、丑陋且极其容易漏判。

复杂代码往往是 Bug 滋生的温床。我们的目标是“给生活做减法”——**立下铁律，让特殊情况从根本上不可能发生**。

#### 忠实伙伴哨兵节点

我们要引入一项绝妙的核心设计：**哨兵节点**（Sentinel Node）。

与其让空列表的引用变成悬空的 `null`，不如让链表永远拥有一个特殊节点。这个节点就像你忠实的伙伴，无论列表是满是空，它都永远守候在那里。

我们在哨兵节点里放一个无关紧要的占位数值（例如 47 或 63 这样的“垃圾值”），它只负责占位。链表中真正的数据元素，永远从哨兵节点的下一个节点（`sentinel.next`）开始存储：

```text
1. 空列表状态：
+---------------+
|    SLList     |
| sentinel: --+ |
+-------------|-+
              |
              v
        +--------+------+
        | item:47| next | ---> null
        +--------+------+
         (哨兵节点)

2. 存入 10 和 15 后的状态：
+---------------+
|    SLList     |
| sentinel: --+ |
+-------------|-+
              |
              v
        +--------+------+      +--------+------+      +--------+------+
        | item:47| next | ---> | item:10| next | ---> | item:15| next | ---> null
        +--------+------+      +--------+------+      +--------+------+
         (哨兵节点)               (首个真实节点)          (尾部真实节点)
```

> **上图说明**：
> - 状态 1：空列表绝不为 `null`，它包含一个固定的哨兵节点（内部数值为占位垃圾值 47），其 `next` 为 `null`。
> - 状态 2：真正的首个数据节点始终位于 `sentinel.next`。

我们来看看引入哨兵后，代码是如何实现质的飞跃的：

```java
public class SLList {
    private static class IntNode {
        public int item;
        public IntNode next;

        public IntNode(int i, IntNode n) {
            item = i;
            next = n;
        }
    }

    private IntNode sentinel;
    private int size;

    /** 创建空列表 */
    public SLList() {
        sentinel = new IntNode(47, null);
        size = 0;
    }

    /** 创建含有一个元素的列表 */
    public SLList(int x) {
        sentinel = new IntNode(47, null);
        sentinel.next = new IntNode(x, null);
        size = 1;
    }

    public void addFirst(int x) {
        sentinel.next = new IntNode(x, sentinel.next);
        size++;
    }

    public int getFirst() {
        return sentinel.next.item;
    }

    public void addLast(int x) {
        size++;
        IntNode p = sentinel;
        while (p.next != null) {
            p = p.next;
        }
        p.next = new IntNode(x, null);
    }

    public int size() {
        return size;
    }
}
```

请仔细品味现在的 `addLast` 方法：
当列表为空时，`p` 指向 `sentinel`。因为 `sentinel` 永远真实存在且永不为 `null`，`p.next` 第一次判断就是 `null`，循环直接结束，新节点立刻顺理成章地挂在 `sentinel.next` 上！
当列表非空时，`p` 从 `sentinel` 出发，一路向后推进直到真正的链表尾部，再把新节点追加上去。

**再也不需要任何 `if (first == null)` 的特殊边界判断了！** 空列表与非空列表在结构和行为上达成了完美的统一。哨兵节点用一个极简的占位对象，一举消灭了整套系统中最容易产生空指针异常的死角。

### 保证正确性的基石：程序不变量

在重构出哨兵节点之后，我们必须掌握一个在大型软件系统推演中至关重要的理论工具：**不变量**（Invariants）。

> **定义**：**不变量**（Invariant）是指在程序正常运行期间（排除存在未修复 Bug 的前提下），在任何时刻、对外部观察者而言都始终保持为真的逻辑条件。

对于带有哨兵节点的 `SLList`，我们在架构层面确立了三大核心不变量：

1. **哨兵指针非空不变量**：`sentinel` 引用永远指向一个真实存在的哨兵节点，在对象的整个生命周期中绝对不为 `null`。
2. **首元素定位不变量**：如果列表中存在第一个真实数据元素，它必然且唯一位于 `sentinel.next` 节点中。
3. **规模精准不变量**：实例变量 `size` 的数值始终严格等于当前列表中已加入的真实元素总数。

确立不变量的巨大价值在于**极大降低思维推演的复杂度**。
在实际开发中，你可能会感到疲惫、脑子昏沉，或者像在感冒发烧、整个人晕头转向时被叫去修代码。如果你心中没有确立不变量，你会陷入细节的恐慌：“这里会不会是空？”“我取的是第一个还是第零个？”“尾指针指在哪里？”

但只要心中有不变量，你的代码推理就像拿着一份不可动摇的契约：
当你想拿第一个元素时，你不需要犹豫，直接写 `sentinel.next.item`，因为不变量承诺了真正的第一个元素永远就在那里；在编写任何修改链表的方法时，你的唯一目标就是**确保方法执行结束时，这三条不变量依然成立**。

在学术界的形式化验证（Formal Verification）中，这也是利用数学归纳法证明程序正确性的核心手段：只要前置条件满足不变量，且每个操作步骤都保持不变量不变，整个数据结构在逻辑上就是绝对无懈可击的。

### 六步重构的演进历程

到这里，我们对 Peyman 最初给出的原始裸递归列表完成了脱胎换骨式的六步大重构。让我们用一张对照表来全景复盘这六项演进：

| 演进步骤 | 改造动作 | 核心动因与工程收益 |
| :--- | :--- | :--- |
| **步骤一：重命名节点** | 将 `IntList` 更名为 `IntNode` | 澄清概念，明确其仅为链表底层的离散“节点”，而非面向用户的列表容器 |
| **步骤二：引入中间层** | 新增包装类 `SLList` 管理底层链表 | 封装底层裸递归，为用户提供简洁明了的操作入口，隐藏不必要的 `null` 样板 |
| **步骤三：访问控制私有化** | 将内部成员 `first` 设为 `private` | 筑牢信任边界，阻止外部误操作或恶意构造环形死循环，实现内部实现与公共接口解耦 |
| **步骤四：嵌套静态辅助类** | 将 `IntNode` 声明为 `private static class` 嵌套在 `SLList` 顶部 | 避免污染外部命名空间；`static` 省去对宿主实例的隐式引用，节约近 1/3 的节点内存开销 |
| **步骤五：长度缓存机制** | 维护 `private int size` 实例变量 | 空间换时间，避免每次计算长度遍历整个链表，将查询耗时从线性 $O(N)$ 降至即时常数 $O(1)$ |
| **步骤六：引入哨兵节点** | 废弃可空的 `first`，引入常驻的 `sentinel` 虚拟节点 | 统一空列表与非空列表的拓扑结构，彻底消除 `addLast` 中的空指针边界特例与 `if` 补丁 |

### 本讲提到的题目

#### 列表遍历耗时推导题

- **问题描述**：
  假设采用非缓存的递归遍历方式实现 `size()` 方法，在某台计算机上处理一个包含 1000 个元素的单链表需要耗时 2 秒。如果保持运行环境不变，使用相同的遍历算法处理一个包含 100 万（$1,000,000$）个元素的单链表，大约需要耗费多长时间？

- **解析与依据**：
  在原始递归实现中，`size(IntNode p)` 必须从头到尾无遗漏地访问链表中的每一个节点，其算法的时间复杂度为线性阶 $O(N)$，即算法执行所需的时间与链表中元素的数量成严格正比关系。
  数据规模从 1000 个元素增长至 100 万个元素，元素数量放大了 1000 倍：
  $$\frac{1,000,000}{1,000} = 1000$$
  因此，算法的运行耗时也将同步线性增加 1000 倍：
  $$2 \text{ 秒} \times 1000 = 2000 \text{ 秒}$$
  2000 秒折合约为 33 分 20 秒。这个悬殊的时间反差充分证明了线性遍历在面对规模化数据时的脆弱性，也正是我们在类内部引入 `size` 变量进行常数时间缓存维护的核心动因。

- **答案**：
  **2000 秒**（约 33.3 分钟）。
