## 接口、实现继承与子类型多态
> 对应块：BLK08 | 覆盖分集：P19-P20 | 块标题（分集名）：《[61B FA25] 第8讲 - 接口与实现继承》

我们在之前的讨论课与编程项目中，已经亲手实现过两种结构迥异的列表：一种是基于动态数组的 `AList`，另一种是基于节点指针的单向链表 `SLList`。如果你还记得的话，只要我们为它们补齐通用的操作方法（比如插入、增删与查询），就会面对一个非常尴尬的现实——代码库里出现了两个在外部使用逻辑上几乎一模一样的类，但它们在 Java 的类型体系中却是完全割裂的独立存在。

今天我们深入探讨面向对象设计中最核心的两大支柱：**接口继承（Interface Inheritance）**与**实现继承（Implementation Inheritance）**，并由此延展到编译期类型系统、运行时动态分派，以及利用 `Comparable` 和 `Comparator` 构建优雅而强大的**子类型多态（Subtype Polymorphism）**。

### 从冗余代码到抽象接口

#### 代码复制的维护困境

假设我们在编写一个文本处理工具库 `WordUtils`，其中包含一个非常高频的工具方法 `longest`，用于遍历一个由字符串构成的列表，并返回其中长度最长的那个单词：

```java
public class WordUtils {
    public static String longest(AList<String> list) {
        int maxDex = 0;
        for (int i = 0; i < list.size(); i += 1) {
            String longestString = list.get(maxDex);
            String thisString = list.get(i);
            if (thisString.length() > longestString.length()) {
                maxDex = i;
            }
        }
        return list.get(maxDex);
    }
}
```

这段算法的逻辑没有任何玄机：记录当前最长字符串的索引下标，线性扫过整个列表，一旦发现更长的项就更新下标，最后返回命中项。

但问题接踵而至。如果我们的调用方现在换成了 `SLList<String>`，想用链表来找出最长单词，会发生什么？编译器会毫不留情地报错，指出传入的实参类型与形参声明的 `AList<String>` 不兼容。

为了让程序跑起来，最不动脑子的直接解法是什么？在 Java 中，我们可以利用**方法重载（Method Overloading）**，在同一个类里编写两个同名但参数列表不同的函数副本：

```java
public class WordUtils {
    public static String longest(AList<String> list) {
        // ... 完全相同的遍历比较逻辑 ...
    }

    public static String longest(SLList<String> list) {
        // ... 一模一样的遍历比较逻辑 ...
    }
}
```

在 Java 语法层面，两个方法方法名相同、参数类型不同，完全合法有效。但这绝不是一个优秀的工程方案：

> **易错点**：方法重载带来的代码复制是系统维护恶化的根源。如果后续有开发者写出了新的列表实现（比如基于循环双向链表的 `DLList` 或带有特定队列语义的 `QList`），我们就必须反复复制一份 `longest`；更致命的是，一旦核心查找逻辑发现了缺陷需要修正，只要你改了数组列表版本却遗漏了链表版本，就会引发潜伏极深的逻辑分歧。代码虽然永不生锈老化，但在持续变更中“改一处漏一处”正是软件退化的罪魁祸首。

#### 语言学中的上下位词与抽象契约

这种面临具体特化时无法统一规程的问题，在人类的自然语言中早就有了极其成熟的解决方案。

举个生活中的例子：你在网上搜索给宠物犬洗澡的教程，上面写着“第一步梳理毛发，第二步温水打湿并安抚情绪，第三步涂抹专用香波并彻底冲洗，第四步自然风干，最后给予零食奖励”。如果你家里养的是一只小巧的贵宾犬，你会按这套流程操作；如果你养的是一只体型庞大的阿拉斯加雪橇犬，核心步骤依然完全一致。

自然语言里为什么不需要分别为“贵宾犬洗澡规程”、“阿拉斯加雪橇犬洗澡规程”、“约克夏洗澡规程”各自写一份独立手册？因为语言学中存在**上位词（Hypernym）**与**下位词（Hyponym）**的层级结构：

```text
               +------------------+
               |   实体 (Entity)   |
               +------------------+
                        |
                        v
               +------------------+
               |   动物 (Animal)   |
               +------------------+
                        |
                        v
               +------------------+
               |  食肉目 (Carnivore)|
               +------------------+
                        |
                        v
               +------------------+
               |   犬科 (Canidae)  |
               +------------------+
                        |
                        v
               +------------------+
               |     狗 (Dog)     |  <-- 上位词 (Hypernym)
               +------------------+
                 /        |       \
                /         |        \
               v          v         v
        +--------+  +-----------+  +----------+
        | 贵宾犬  |  | 阿拉斯加犬 |  | 约克夏犬  |  <-- 下位词 (Hyponyms)
        +--------+  +-----------+  +----------+
```

> 上图展示了自然语言概念体系从抽象到具体的树状分层。越往上层越抽象，最顶层汇聚于“实体（Entity/Object）”；下位概念无条件继承上位概念所具备的属性与能力。

在语言学著名的 WordNet 词网项目中，语言学家梳理了成千上万个英文名词的层级树，处于最顶端的名词正是“实体（Entity）”。狗是阿拉斯加犬与贵宾犬的上位词，它确立了一个通用的分类范式。

面向对象编程彻底借鉴了这一自然思维：既然 `AList` 和 `SLList` 本质上都是列表，我们完全可以定义一个上位类型 `List61B`，声明列表应当具备哪些通用能力，让具体的数组列表与链表作为下位词去落实这些能力。

#### 接口契约的语法规范

在 Java 中，定义这一纯粹上位词的武器就是 `interface`（接口）。接口是一个纯粹的契约清单，它规定了某种类型“能做什么（What to do）”，而绝不干预“怎么做（How to do）”。

我们新建一个 `List61B.java` 契约文件：

```java
public interface List61B<Item> {
    void addFirst(Item x);
    void addLast(Item x);
    Item getFirst();
    Item getLast();
    Item get(int i);
    int size();
    Item removeLast();
    void insert(Item x, int position);
}
```

在审视这个接口契约时，有三个核心语法硬性规则必须铭记于心：

> **定义**：接口（Interface）是对操作行为的高阶抽象集合。
> 1. **不可直接实例化**：接口只是行为规约，没有具体的实现逻辑，因此绝对不能执行 `new List61B<>()`，接口内部绝不能包含构造函数；
> 2. **去除底层实现特有的状态与私有机制**：在原先的 `AList` 中，我们有维护内部数组容量的 `resize()` 方法和底层的数组引用，而在 `SLList` 中则是链表哨兵节点。这些纯属底层实现细节，列表这一抽象概念本身不需要关心底层是数组还是指针，因此绝不能将 `resize()` 塞进公共接口契约中；
> 3. **默认均为公共抽象方法**：接口中声明的方法签名默认即为 `public abstract`，无需多余修饰。

### 契约落地与类型体系

#### 接口实现与多态参数

有了上位契约 `List61B`，具体的数据结构必须向 Java 编译器显式“宣誓”自己满足该契约。这一誓约通过关键字 `implements` 来达成：

```java
public class AList<Item> implements List61B<Item> {
    // 落实 List61B 要求的全部具体操作 ...
}

public class SLList<Item> implements List61B<Item> {
    // 落实 List61B 要求的全部具体操作 ...
}
```

这好比向整个类型系统宣告：“`AList` 和 `SLList` 都是合法合格的 `List61B`”。

一旦契约成立，我们开篇那个令人头疼的 `longest` 工具方法便能实现真正的质变。我们无需重载，只需将参数声明为抽象的上位接口：

```java
public class WordUtils {
    public static String longest(List61B<String> list) {
        int maxDex = 0;
        for (int i = 0; i < list.size(); i += 1) {
            String longestString = list.get(maxDex);
            String thisString = list.get(i);
            if (thisString.length() > longestString.length()) {
                maxDex = i;
            }
        }
        return list.get(maxDex);
    }
}
```

无论调用者传入的是 `AList<String>` 还是 `SLList<String>`，甚至未来全新编写的任何实现了 `List61B` 的列表，都能够毫无阻碍地传递进 `longest` 方法中。代码量不仅减少了一半，更获得了面向未来的无尽扩展性。

#### 方法重写与重载的界限

在子类实现接口定义的方法，或者改写父类行为的过程中，我们必须从严区分两个极易混淆的概念：**方法重写（Overriding）**与**方法重载（Overloading）**。

> **定义**：
> - **方法重写（Method Overriding）**：子类重新实现了超类或接口中已声明的方法。重写必须要求**方法签名精确匹配**——方法名、参数类型、参数数量及顺序必须完全一致，且返回类型协变匹配。重写是依托于继承体系（父子、接口实现）而存在的。
> - **方法重载（Method Overloading）**：在同一个类中（或继承体系中）定义了同名的方法，但它们的**参数列表签名不同**（参数类型不同或参数个数不同）。重载纯粹是方法签名的分流，与继承多态无必然因果。

为了让重写的意图得到编译器的强力护航，Java 提供了 `@Override` 注解。

```java
public class AList<Item> implements List61B<Item> {
    // ...
    @Override
    public void addLast(Item x) {
        if (size == items.length) {
            resize(items.length * 2);
        }
        items[size] = x;
        size += 1;
    }
}
```

许多初学者会疑惑：就算我不写 `@Override`，只要签名一致，Java 运行时难道不也会自动执行子类的方法吗？为什么还要多此一举？

> **结论**：`@Override` 的唯一真正使命，是**让原本能通过编译但隐含灾难性拼写缺陷的代码当场报错**。
> 假设你在子类中试图重写 `addLast`，但不小心手滑打成了 `atLast`。如果没有 `@Override`，编译器会天真地认为你只是在子类里新建了一个全新的辅助方法，而接口要求的 `addLast` 却未被实现（或者父类的同名方法未被覆盖），这会导致一个诡异而隐蔽的 Bug；而一旦你标注了 `@Override`，编译器就会逐字核对超类契约，在发现上层根本没有 `atLast` 时当场砸出编译错误，将隐患扑灭在萌芽期。

#### 静态类型与动态类型的双轨机制

要透彻理解面向对象的多态分派，就必须掌握 Java 内存模型与类型检查中的“双轨机制”：**静态类型（Static Type）**与**动态类型（Dynamic Type）**。

请仔细审视下面这行多态声明与赋值语句：

```java
List61B<String> someList = new SLList<>();
```

在 Java 的等式黄金法则中，等号左侧变量的类型是 `List61B<String>`，这就是变量的**静态类型（编译期类型）**；而等号右侧通过 `new` 关键字在内存堆中真实创建出的对象是 `SLList`，这就是对象的**动态类型（运行期实际类型）**。

```text
 编译期视界 (静态类型)                   运行期视界 (动态类型)
+-----------------------+              +-----------------------+
| someList: List61B     |  =======>    | 堆中实体: SLList 实例  |
| 仅暴露 List61B 接口方法 |  (引用指向)  | 具备 SLList 全部字段与方法|
+-----------------------+              +-----------------------+
```

Java 语言在编译与执行两个阶段分工泾渭分明：

1. **编译期看静态类型（Compiler checks Static Type）**：
   编译器在做语法检查与安全审计时，唯一依靠的就是变量声明的静态类型。假设我们在 `SLList` 类中定义了一个链表独有的翻转或特化跳转方法 `public void jump()`，而 `List61B` 接口中并未收录此方法。如果你在代码中写：
   ```java
   someList.jump(); // 编译报错！
   ```
   编译器会立即拦截并拒绝生成字节码。因为在编译器眼中，`someList` 是一个通用的 `List61B`，它只向调用者承诺具有 `List61B` 声明的能力，根本无法预知运行期传入的到底是单链表、数组列表还是某种不支持 `jump` 的列表。

2. **运行期看动态类型（Runtime dispatches to Dynamic Type）**：
   一旦通过了编译阶段，程序真正加载到 JVM 中执行时，调用的则是堆中对象真实所属类的方法实现。这种机制被称为**动态方法分派（Dynamic Method Dispatch）**。

### 默认方法与实现继承的利弊

#### default 关键字与行为复用

在早期的 Java 版本中，接口是纯粹由抽象方法构成的硬壳，子类必须逐字逐句实现每一个接口方法。

但随着系统规模的扩张，开发者们发现不同实现在某些高级操作上具有完全一致的算法模式。例如打印列表的所有元素并用括号括起来，无论是数组列表还是单向链表，宏观步骤都是遍历 `size()` 并通过 `get(i)` 依次取出元素并打印。

从 Java 8 开始，接口引入了 `default` 关键字，允许设计者在接口中提供默认的具体方法体，这就是**实现继承（Implementation Inheritance）**：

```java
public interface List61B<Item> {
    void addFirst(Item x);
    void addLast(Item x);
    Item getFirst();
    Item getLast();
    Item get(int i);
    int size();
    Item removeLast();
    void insert(Item x, int position);

    default void print() {
        for (int i = 0; i < size(); i += 1) {
            System.out.print(get(i) + " ");
        }
        System.out.println();
    }
}
```

有了 `default void print()`，子类在实现 `List61B` 时即使完全不编写 `print` 方法，也能直接拥有打印能力，这极大减轻了基础模板代码的重复率。

#### 通用逻辑的性能陷阱

然而，天下没有免费的午餐。表面上通用优雅的默认实现，往往暗藏极其危险的**算法性能悬崖**。

我们来深入剖析上述 `print` 默认实现在不同底层数据结构上的执行代价：

```java
for (int i = 0; i < size(); i += 1) {
    System.out.print(get(i) + " ");
}
```

1. **在 `AList`（数组列表）上的代价**：
   数组拥有天然的内存连续寻址特性，`get(i)` 是一步到位的 $O(1)$ 常数时间访问。整个循环执行 $n$ 次，总耗时为严格的线性阶 $O(n)$，效率无可挑剔。

2. **在 `SLList`（单向链表）上的灾难**：
   单向链表没有索引下标偏移支持！当执行 `get(i)` 时，链表底层必须从头节点的哨兵指针出发，一步一步沿着 `next` 指针跳跃 $i$ 次：
   - 获取索引 0：跳跃 0 次；
   - 获取索引 1：从头出发跳跃 1 次；
   - 获取索引 2：从头出发跳跃 2 次；
   - ……
   - 获取索引 $n-1$：从头出发跳跃 $n-1$ 次。

总跳跃操作次数为经典等差数列求和：
$$\sum_{i=0}^{n-1} i = \frac{(n-1)n}{2} = O(n^2)$$

> **结论**：原本应当在线性时间 $O(n)$ 内完成的简单打印任务，因为链表对抽象 `get(i)` 的机械套用，时间复杂度暴涨为极其恶劣的二次方阶 $O(n^2)$！当列表规模达到十万级时，程序将瞬间陷入肉眼可见的假死停滞。

#### 子类覆盖与实现继承的危险告诫

实现继承赋予了子类设计者自由决定的权利：如果上层的默认实现效率不理想，子类完全可以通过重写（Override）来提供高度特化的高性能实现。

在 `SLList` 中，我们绕过低效的 `get(i)`，直接使用链表原生的指针向前单向推移：

```java
public class SLList<Item> implements List61B<Item> {
    // ...
    @Override
    public void print() {
        for (Node p = sentinel.next; p != null; p = p.next) {
            System.out.print(p.item + " ");
        }
        System.out.println();
    }
}
```

指针顺着链表从前到后只遍历了一趟，耗时被强行拉回了平滑的 $O(n)$。

在此我们必须严肃告诫所有未来的软件架构师：**实现继承虽然诱人，但极度危险，必须克制使用**。

> **提示**：接口继承（规定做什么）几乎总是利大于弊，是解耦系统的无上利器；但实现继承（规定怎么做）往往是架构恶化的元凶。
> 当父类不仅定义了抽象接口，还强行注入了复杂的具体执行逻辑、私有状态和默认行为时，子类就会不可避免地与父类的内部实现产生强耦合。著名游戏初代《星际争霸：母巢之战（StarCraft: Brood War）》在底层代码中就曾严重滥用庞杂的面向对象实现继承，上层单位基类侵入了太多非通用细节，最终演化为层级深不可测的“脆弱基类”梦魇，改动底层某一逻辑往往导致无数子单位产生不可预知的级联崩溃。

### 抽象数据类型的实现权衡

#### 栈结构的底层选型

在现代计算机科学中，**抽象数据类型（Abstract Data Type, ADT）**关注的是高层的数据行为契约，而非底层的存储骨架。接口是定义 ADT 的天然载体。

我们以基础的**栈（Stack, LIFO 后进先出）**为例，它的核心契约仅仅是两个基本操作：压栈 `push(x)` 与弹栈 `pop()`。

如果让你分别用单向链表和动态数组来实现栈，哪一个在工程实践中效率更高？

```text
 方案 A: 单向链表实现 (SLList Stack)
 [Top 指针] ---> [ 节点 3 ] ---> [ 节点 2 ] ---> [ 节点 1 ] ---> null
 push/pop 仅在头部移动指针，天然 O(1)

 方案 B: 动态数组实现 (AList Stack)
 items: [ 节点 1 | 节点 2 | 节点 3 | 空闲位 | ... ]
                             ^
                           [Top]
 push/pop 仅在尾部操作，均摊 O(1)，但偶尔触发倍增扩容
```

- **单向链表方案**：我们可以将链表的头节点视为栈顶，`push` 即为 `addFirst`，`pop` 即为 `removeFirst`。操作仅仅是修改一两个引用的指向，完全没有任何数组搬运开销，执行时间极其稳定，常数极小且恒定为严格的 $O(1)$；
- **动态数组方案**：我们将数组的末尾下标视为栈顶，`push` 即为末尾写入，`pop` 即为末尾清除并减小下标计数。绝大部分情况下这只是简单的内存赋值，但由于数组空间有限，一旦装满就会触发内存再分配与数据全量拷贝的倍增扩容（Resize）。虽然其均摊时间复杂度依然是 $O(1)$，但在实际运行计时测试中，由于扩容内存搬迁与对象初始化的微观扰动，链表往往表现得更为敏捷平顺。

#### 百宝袋结构的底层选型

我们再审视另一个经典 ADT——**百宝袋（Bag）**。它的行为定义非常特殊：
1. 允许向袋中随机放入元素（`add`）；
2. 允许随时从袋中以均匀分布的概率**随机抽取或移除元素**（`grabRandom`）；
3. 获取当前袋内元素的总数（`size`）。

面对百宝袋的随机抽取需求，动态数组与链表的优劣瞬间反转：

> **结论**：动态数组在百宝袋场景下以绝对优势碾压链表。
> 数组底层是一段连续物理内存，支持极其廉价的 $O(1)$ 随机索引寻址：我们只需调用随机数生成器产生一个 $[0, \text{size}-1]$ 的整数下标，即可一步到位直达目标内存位置；而链表若要获取随机位置上的节点，必须从头指针开始逐个向后步进查找，随机访问代价高达 $O(n)$。因此，针对不同 ADT 的操作特征，选择恰当的具体实现是算法工程师的基本素养。

### 对象的秩序：可比较接口与自然顺序

#### 多态理念的分野：Python 与 Java

在探讨如何给对象排序之前，我们不妨跳出单一语言，对比一下 Python 与 Java 在实现对象通用比较与函数行为传递上的设计哲学差异。

假设我们希望在一组狗（Dog）中找出体型最大的那一只：

1. **Python 的实现机制**：
   - **运算符重载多态**：在 `Dog` 类中定义魔法函数 `__gt__(self, other)`，直接利用大于号 `d1 > d2` 进行比较。Python 的 `max()` 函数内部会直接触发这一运算符调用；
   - **高阶函数直接传递**：Python 允许将函数像普通变量一样作为实参传给高阶函数，例如 `max(dogs, key=lambda d: d.size)`。这里的键提取函数完全独立于 `Dog` 类，极其灵活。

2. **Java 的实现机制（尤其在 Java 8 之前）**：
   Java 在类型哲学上极度推崇形式化的类型安全与契约化，绝不鼓励在核心算法中四处传递孤立无援的“裸函数”，而是完完全全将这种通用能力依托在**基于接口继承的子类型多态**上。

#### Comparable 接口与 compareTo 规范

假设我们定义了一个描述小狗的实体类：

```java
public class Dog {
    private String name;
    private int size;

    public Dog(String n, int s) {
        name = n;
        size = s;
    }
}
```

现在我们在启动类中创建了三只各具特色的小狗：体型为 200 的 GregMax、体型为 5 的 Pauluza，以及体型高达 9000 的大红狗 Clifford（它是一只家喻户晓的巨型红色猎犬）：

```java
List<Dog> dogs = List.of(new Dog("GregMax", 200), new Dog("Pauluza", 5), new Dog("Clifford", 9000));
Dog maxDog = Collections.max(dogs); // 编译直接爆炸！
```

代码刚写完，Java 编译器就会弹出一段极其吓人的泛型类型报错：要求传入的集合元素类型必须满足 `Comparable<? super T>`，指出编译器根本不知道该如何比较两只狗。

为了让任意对象具备官方认可的度量能力，Java 类库的核心维护者之一 Josh Bloch 在标准库中确立了唯一的通用接口——`java.lang.Comparable<T>`：

```java
public interface Comparable<T> {
    /**
     * 比较当前对象与指定对象的相对顺序。
     * 若当前对象小于指定对象，返回负整数；
     * 若当前对象等于指定对象，返回零；
     * 若当前对象大于指定对象，返回正整数。
     */
    int compareTo(T o);
}
```

这套三态返回约定是整个 Java 体系排序算法的基石规则：

```text
 this < o  =====> 返回负整数 (< 0, 如 -1)
 this == o =====> 返回 0
 this > o  =====> 返回正整数 (> 0, 如 1)
```

#### 对象的自我度量与作用域规则

我们让 `Dog` 类实现 `Comparable<Dog>`，明确以体型 `size` 作为其内在的默认度量尺度：

```java
public class Dog implements Comparable<Dog> {
    private String name;
    private int size;

    public Dog(String n, int s) {
        name = n;
        size = s;
    }

    @Override
    public int compareTo(Dog uddaDog) {
        if (this.size < uddaDog.size) {
            return -1;
        } else if (this.size == uddaDog.size) {
            return 0;
        }
        return 1;
    }
}
```

> **提示**：参数命名“uddaDog”来自一段夏威夷大岛凯拉凯夸湾（Kealakekua Bay）划皮划艇的真实经历。当地人带着两只狗在岸边奔跑，一只名字叫 Kai，而向导指着另一只狗脱口而出“dat's udda dog”（那就是另一只狗/the other dog）。在技术语境下，它生动地代表了与当前对象 `this` 进行比对的那个外部传入实例。

在实现 `compareTo` 时，有两个极其关键的技术细节需要特别注意：

1. **同类跨实例的私有访问权限**：
   细心的同学会发现，`uddaDog.size` 中的 `size` 字段明明声明为 `private`，为什么我们在当前方法中可以直接点号访问？
   请牢记：Java 的 `private` 访问修饰符是**类级作用域限制（Class-level scoping）**，而不是**对象级作用域限制（Object-level scoping）**！只要当前代码编写在 `Dog.java` 的类作用域大括号内部，`Dog` 的代码就能自由访问任何一个 `Dog` 实例的所有私有成员变量和私有方法。

2. **简化减法写法的潜在溢出隐患**：
   在很多工业级代码与竞赛解法中，开发者喜欢投机取巧地直接写成：
   ```java
   return this.size - uddaDog.size;
   ```
   如果两个整数均为非负且数值较小（如本例中 200 与 9000），这种减法能够完美产生正、负、零的结果。但如果涉及负数，例如 `(-2000000000) - (2000000000)`，就会触发 32 位整型下溢翻转成巨大的正数，彻底颠倒大小关系！因此，在严肃的工业生产中，更推荐严谨的分支判断，或调用标准库的 `Integer.compare(this.size, uddaDog.size)`。

有了 `compareTo`，再次运行 `Collections.max(dogs)`，程序顺利跑通，精准捕获并输出了体型高达 9000 的最大红狗 Clifford。这种由对象自身声明并落地的默认比较逻辑，被称为该对象的**自然顺序（Natural Order）**。

### 编译期契约的深度辨析

在面对接口、类与外部工具库时，许多学习者容易对“究竟是哪个文件在什么时候报错”产生严重的思维混乱。我们通过一个经典的编译期逻辑推演，把 Java 编译与类型系统的底层机制彻底揭开。

我们有以下三个文件协同工作：

```java
// 文件 1: DogLauncher.java
public class DogLauncher {
    public static void main(String[] args) {
        Dog[] dogs = new Dog[]{new Dog("A", 10), new Dog("B", 20)};
        Dog maxDog = (Dog) Maximizer.max(dogs); // 假设 Maximizer 内部依赖 Comparable
    }
}

// 文件 2: Dog.java
public class Dog implements Comparable<Dog> {
    private int size;
    // ...
    @Override
    public int compareTo(Dog uddaDog) {
        return this.size - uddaDog.size;
    }
}

// 文件 3: Maximizer.java (或 Collections.java 类库)
public class Maximizer {
    public static Comparable max(Comparable[] items) {
        int maxDex = 0;
        for (int i = 0; i < items.length; i += 1) {
            if (items[i].compareTo(items[maxDex]) > 0) {
                maxDex = i;
            }
        }
        return items[maxDex];
    }
}
```

#### 独立编译机制与 ExplosionDetector 类比

在展开推演前，必须明确一个至关重要的计算机体系常识：**Java 源文件是独立解耦编译的，每个类被独立转换成平台无关的 `.class` 字节码文件**。

为了打消“是不是工具类会崩溃”的疑虑，我们做一个思想实验：
假设我今天心血来潮，写了一个极其超前的通用接口 `Explodable`，里面包含一个抽象方法 `void explode(int timer, boolean safe)`；紧接着我又写了一个工具类 `ExplosionDetector`，其中有一个静态方法接受一个 `List<Explodable>` 列表，并遍历让每一个物体引爆。

此时此刻，全世界没有任何一个工程师真正写出过哪怕一个能爆炸的具体类（比如炸药类 `Dynamite`）。
请问：我的 `ExplosionDetector.java` 能否成功编译通过？

**答案是：100% 能够完美编译打包！**
编译器在检查 `ExplosionDetector` 时，只核实语法是否合规、类型依赖是否匹配。只要它知道 `Explodable` 接口承诺拥有 `explode` 方法，就足以生成规整的字节码。它绝不需要等待世界上出现具体的炸药实例。

同理，标准库里的 `Collections.java`（或我们的 `Maximizer`）早在多年前就已经被 Sun/Oracle 官方编译打包成固若金汤的二进制库发往全球了。无论你写的 `Dog` 类怎么折腾，**绝对不可能反向导致 `Collections.java` 编译失败**！

#### 缺失实现的报错归属

现在我们来看**变式一**：
> **题目情境**：在 `Dog.java` 中，我们保留头部的 `public class Dog implements Comparable<Dog>` 声明，但是**删除了类体内的 `compareTo` 方法体**。重新编译整个工程，哪个文件会报错？

```text
 编译检查链条分析：
 [Dog.java] -------------> 宣誓实现 Comparable<Dog>
     |
     +--> 编译器审查: 接口规定了 compareTo(Dog) 抽象契约
     |
     +--> 结果: Dog 类既不是抽象类，又未兑现 compareTo 方法实现！
     |
     +====> 【编译当场崩溃于 Dog.java】
```

> **结论**：**编译报错发生在 `Dog.java` 本身**！
> 既然你白纸黑字写了 `implements Comparable<Dog>`，你就与编译器签下了神圣不可违背的法律合同。你声称具备该能力，却未交出具体实现，编译器会在编译 `Dog.java` 的那一瞬间亮起红灯。而 `DogLauncher.java` 在编译器尚未排查到它时，就已经被底层的 `Dog.java` 编译失败截断了。

#### 缺失接口声明的报错归属

我们再看更有迷惑性的**变式二**：
> **题目情境**：在 `Dog.java` 中，我们**删除了类头上的 `implements Comparable<Dog>`**，但依然在类体内完完整整地保留着 `public int compareTo(Dog uddaDog)` 方法。重新编译，哪个文件会报错？

让我们推演每一个文件的编译反应：

1. **编译 `Dog.java`**：
   编译器进入 `Dog.java`，它看到一个普通的类，里面有一个普通的成员方法叫 `compareTo`。在 Java 中，任何人都有起名叫 `compareTo` 的自由，这不违反任何语法规则。因此，**`Dog.java` 编译完全通过，欢天喜地生成字节码**！
2. **编译 `DogLauncher.java`**：
   编译器进入启动类，审视这行代码：
   ```java
   Dog maxDog = (Dog) Maximizer.max(dogs);
   ```
   `Maximizer.max` 明确要求形参必须是一个 `Comparable[]` 数组。编译器检查传入的实参 `dogs`，发现它的静态类型是 `Dog[]`。编译器翻阅 `Dog` 类的契约清单，震惊地发现 `Dog` 根本没有 `implements Comparable`！
   即使 `Dog` 肚子里有一个一模一样的 `compareTo` 方法，但在缺乏形式契约担保的情况下，Java 的严格静态类型系统绝不认账。

> **结论**：**在变式二中，`Dog.java` 自身完全合法；真正编译崩溃的是调用方 `DogLauncher.java`**。它试图将一个在类型学上“不可比”的类，强行塞给要求可比较契约的泛型方法。

### 外部裁判：比较器与多元排序

#### 为什么自然顺序不够用

我们在 `Dog` 类中用 `Comparable` 确立了以体型 `size` 为基准的自然顺序：体型大者胜出。

但在真实多变的现实需求中，单一的自然顺序往往远远不够：
- 有时候我们希望按照小狗名字的**字母字典序**来排布展台（Clifford < GregMax < Pauluza）；
- 有时候裁判希望按照名字的**字符长度**来排序；
- 还有时候希望先按体型降序，体型相同时再按名字升序。

一个类只能实现一次 `Comparable<Dog>`，`compareTo` 方法的槽位已经被“体型”永久占满了。如果我们想在不破坏原有一切的前提下引入全新、多维的比较尺度，该如何破局？

#### Comparator 接口与外部裁决

Java 给出的第二剂解药是 `java.util.Comparator<T>`。

如果说 `Comparable` 是小狗**自身的度量能力**（内生自然顺序），那么 `Comparator` 就是一个**端坐在场外的独立裁判**（外部仲裁规则）。裁判独立于小狗之外，俯视两只小狗并裁定孰高孰低：

```java
public interface Comparator<T> {
    int compare(T o1, T o2);
}
```

其裁决返回值同样严守三态规范：若 `o1 < o2` 返回负数，`o1 == o2` 返回 0，`o1 > o2` 返回正数。

我们来编写一个专门按照小狗名字字典序进行裁决的名字比较器 `NameComparator`：

```java
import java.util.Comparator;

public class NameComparator implements Comparator<Dog> {
    @Override
    public int compare(Dog a, Dog b) {
        // 直接复用 String 类天生自带的 compareTo 字典序比较方法
        return a.getName().compareTo(b.getName());
    }
}
```

#### 静态嵌套类的设计考量与单例封装

为了让代码组织更加内聚，我们通常不会把 `NameComparator` 孤零零地作为一个独立的 `.java` 文件随意丢在外面，而是将其作为**嵌套类（Nested Class）**安置在 `Dog` 类内部。

在此处，必须回答一个极具深度的架构设计考题：**为什么嵌套的比较器类必须声明为 `static`？**

```java
public class Dog implements Comparable<Dog> {
    private String name;
    private int size;
    // ...
    public static class NameComparator implements Comparator<Dog> {
        @Override
        public int compare(Dog a, Dog b) {
            return a.name.compareTo(b.name);
        }
    }
}
```

> **易错点**：
> - **非静态内部类（Non-static Inner Class）**：其实例天然绑定在外部类的某一个**具体实例对象**身上。如果你不加 `static`，想要 `new NameComparator()`，就必须先凭空捏造出一只具体的小狗实例，然后通过 `myDog.new NameComparator()` 来孵化它。这显然荒谬绝伦——比较器是通用的裁判逻辑，怎么能依赖某一只特定小狗的存在？
> - **静态嵌套类（Static Nested Class）**：直接归属于外部的 `Dog` 类本身，与具体的小狗实例彻底解绑。任何人无需创建任何 `Dog` 实例，都可以直接自由实例化 `new Dog.NameComparator()`。

为了进一步免去调用者每次使用时都要 `new` 一个全新比较器对象的啰嗦与内存开销，最正统优雅的工业实践是在宿主类中直接公开暴露一个单例常量：

```java
public class Dog implements Comparable<Dog> {
    // 公开暴露的全局唯一名字比较器单例
    public static final Comparator<Dog> NAME_COMPARATOR = new NameComparator();

    private String name;
    private int size;

    private static class NameComparator implements Comparator<Dog> {
        @Override
        public int compare(Dog a, Dog b) {
            return a.name.compareTo(b.name);
        }
    }
}
```

外部使用者只需轻描淡写地写下一行：

```java
Dog maxNameDog = Collections.max(dogs, Dog.NAME_COMPARATOR);
```

代码立刻按照名字字母序运转，名字为 "Pauluza" 的小狗脱颖而出！

#### 可比较与比较器的全方位对比

为了让大家在面对设计抉择时不再摇摆，我们将两者的本质区别归纳如下：

| 对比维度 | `Comparable<T>`（可比较接口） | `Comparator<T>`（比较器接口） |
| :--- | :--- | :--- |
| **包路径** | `java.lang.Comparable`（核心语言包） | `java.util.Comparator`（工具实用包） |
| **角色定位** | 对象的内在自我度量（“我能与同类比”） | 独立的场外仲裁者（“我来裁判两者”） |
| **核心方法** | `int compareTo(T o)`（单参数，隐式比对 `this`） | `int compare(T o1, T o2)`（双参数，显式仲裁两者） |
| **规则多寡** | 单一唯一，定义类的**自然顺序（Natural Order）** | 无穷多元，可为同一实体定制无数种比较策略 |
| **侵入性** | 强侵入性，必须修改待比较类的源码以实现接口 | 无侵入性，无需触碰目标实体类即可在外部单独编写 |
| **典型调用** | `Collections.sort(list)` | `Collections.sort(list, comparator)` |

### 本讲提到的题目

#### 题目一：栈与百宝袋的底层结构选型

- **题干**：
  在实现抽象数据类型时：
  1. 对于栈（Stack，仅支持 `push` 与 `pop` 操作），选用单向链表（SLList）还是动态数组（AList）效率更优？为什么？
  2. 对于百宝袋（Bag，支持无序放入、统计大小，以及核心的均匀概率随机抽取元素 `grabRandom` 操作），选用单向链表还是动态数组更优？为什么？

- **解析**：
  1. 栈操作完全集中在一端（栈顶）。链表以头节点作为栈顶，头插与头删仅涉及常数级指针重定向，严格 $O(1)$ 且无任何内存扩容开销；动态数组以末尾作为栈顶，均摊复杂度也是 $O(1)$，但偶尔触发的倍增扩容会引起瞬时性能抖动。在严格的实际运行测试中，链表常数极小，更具轻量优势。两者均优秀，但链表在无抖动性上略胜一筹。
  2. 百宝袋的核心性能瓶颈在随机抽选。数组基于连续内存空间，生成随机下标后可通过内存偏移量在 $O(1)$ 常数时间内瞬时定位读取；而单向链表没有直接寻址能力，定位第 $k$ 个节点必须从头节点开始耗费 $O(k)$ 步线性指针迭代，平均耗时高达 $O(n)$。

- **答案**：
  栈结构两者皆可，单向链表在无扩容停顿上综合表现更优；百宝袋结构动态数组以 $O(1)$ 对 $O(n)$ 的寻址优势取得决定性胜利。

#### 题目二：多态赋值与方法调用判定

- **题干**：
  设有如下代码片段，请分析其编译与执行行为：
  ```java
  List61B<String> lst = new SLList<>();
  lst.addFirst("hello");
  ```
  该代码是：
  A. 编译失败；  
  B. 编译通过，但运行时第一行赋值报错；  
  C. 编译通过，但运行时调用 `addFirst` 时崩溃；  
  D. 编译通过，且完全正常平稳运行。

- **解析**：
  根据面向对象继承规则与等式黄金法则，`SLList` 实现了 `List61B` 接口，因此 `SLList` 是 `List61B` 的合法子类型，将子类对象的引用赋给超类型引用变量完全合法，编译通过且运行期类型转换平滑；在执行第二行时，变量的静态类型 `List61B` 中明确声明了 `addFirst` 方法契约，编译器放行；运行期 JVM 触发动态方法分派，调用堆中实际 `SLList` 对象的 `addFirst` 实现，一切平稳正常。

- **答案**：D。

#### 题目三：可比较契约缺失下的编译报错归属

- **题干**：
  工程中存在三个协同文件：
  - `DogLauncher.java`：在 `main` 方法中创建 `Dog[]` 并调用 `Collections.max(dogs)`；
  - `Dog.java`：小狗实体类；
  - `Collections.java`：标准类库，`max` 方法要求元素满足 `Comparable` 契约。
  
  请分别判定以下两种变式下，编译报错将具体归属于哪一个文件：
  1. **变式 A**：`Dog.java` 头上写有 `implements Comparable<Dog>`，但删除了内部的 `compareTo` 方法实现；
  2. **变式 B**：`Dog.java` 内部保留了完好的 `compareTo` 方法，但类头上删除了 `implements Comparable<Dog>` 接口声明。

- **解析**：
  1. 变式 A 中，`Dog` 宣誓了接口契约却未兑现非抽象方法的实现，违背了 Java 基础语法，编译器在审视 `Dog.java` 时当场拦截报错。
  2. 变式 B 中，`Dog.java` 自身语法无懈可击，能独立编译为有效字节码；但在编译 `DogLauncher.java` 时，编译器检查到 `Collections.max` 的静态参数契约要求传入可比较类型，而 `Dog` 缺乏接口誓约，因此在调用点抛出类型不兼容错误。标准库 `Collections.java` 是预编译的独立存在，绝不受此影响。

- **答案**：
  变式 A 报错在 `Dog.java`；变式 B 报错在 `DogLauncher.java`。

#### 题目四：比较器字母序裁决

- **题干**：
  假设我们在外部调用为小狗定制的名字字典序比较器：
  ```java
  Comparator<Dog> nc = new Dog.NameComparator();
  Dog d1 = new Dog("Frank", 50);
  Dog d2 = new Dog("Zic", 80);
  int result = nc.compare(d1, d2);
  ```
  请问 `result` 的返回值为正数、零还是负数？

- **解析**：
  `NameComparator` 内部依托小狗名字的字符串进行字典序比较，即调用 `"Frank".compareTo("Zic")`。在 ASCII 与 Unicode 编码字符表中，大写字母 `'F'` 的编码值（70）小于大写字母 `'Z'` 的编码值（90），因此字符串 `"Frank"` 在字典序上排在 `"Zic"` 之前，判定为小于关系，故按照比较器契约规范返回负整数。

- **答案**：负数（负整数）。
