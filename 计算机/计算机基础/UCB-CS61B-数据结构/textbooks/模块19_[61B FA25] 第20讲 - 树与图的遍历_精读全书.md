### 重温老朋友：树与有根树的本质

大家对树并不陌生，之前在二叉搜索树（BST）、并查集（Disjoint Sets）以及优先队列与堆（Heap）中，都曾借助树形结构来组织数据。后续我们还会学习前缀树（Trie）。除了作为具体的数据结构，树在现实生活中也无处不在：公司的层级组织架构图、生物学中的物种分类学、医学中的疾病诊断与治疗决策流程，其本质都是一棵树。

#### 树的严格定义与反例辨析

在最纯粹的数学意义上，树其实非常简洁：它由若干个圆圈节点（Nodes / 顶点）以及连接这些节点的连线（Edges / 边）组成。判定一个由节点和边组成的结构究竟是不是树，核心判据只有一条：

> **定义**：一棵树由若干节点和连接它们的边组成，当且仅当**图中任意两个节点之间存在且仅存在一条路径**。

如果任意挑选两个节点，它们之间都能找到一条路径连通，而且这条路径是独一无二的，那它就是一棵合法的树。反之，只要存在某一对节点之间可以通过两条不同的路径相互到达，或者存在不可达的节点，它就绝对不再是树。

为了直观体会这一判定标准，请看下面的结构对比：

```text
      (A)            (1)               (X)
     /   \            |               /   \
   (B)   (C)         (2)            (Y)   (Z)
   / \                |              |
 (D) (E)             (3)            (W)

   [有效树 1]      [有效树 2]       [有效树 3]
  (分支分叉)      (单链退化)       (任意两点路径唯一)
----------------------------------------------------
      (P)                 (M)
     /   \               /   \
   (Q)---(R)           (N)   (O)
     \   /               \   /
      (S)                 (K)

   [非树 1]             [非树 2]
 (存在环路与多条路径) (从顶到底可走左或走右)
```

读图说明：上方三组结构中，任意两节点之间只有一条路径，均属于合法的树（即使像中间那样退化成单链也是树）；下方两组结构中，左侧存在环路 $P-Q-R$，右侧从顶点 $M$ 到最底部的 $K$ 既可以走左路 $M \to N \to K$，也可以绕右路 $M \to O \to K$，因此打破了唯一路径的约束，不再是树。

#### 提根成树：无根树到有根树的蜕变

通常我们在教材或纸面上看到的树，顶部都有一个高高在上的“根节点”。但如果只给出节点和边组成的无向连通且无环的结构，它其实是一棵“无根树”（Unrooted Tree）。

要得到大家习惯的有根树（Rooted Tree），只需要做一个非常生动的物理动作：从树中任选一个节点，指定它为“根”，然后拎着这个根使劲摇晃，让受重力作用的其他所有节点自然垂挂在它的下方。

```text
    (A)---(B)---(C)                 (A)                        (B)
     |     |                       /   \                      / | \
    (D)   (E)                    (D)   (B)                  (A)(C)(E)
                                      /   \                  |
                                    (C)   (E)               (D)

    [原始无根树]              [选 A 为根，拎起摇晃]        [选 B 为根，拎起摇晃]
```

读图说明：对同一张由节点和边构成的拓扑结构，选定不同的节点作为根拎起，会垂挂出形态各异但拓扑等价的有根树。

只要选定了一个根，树上的层级与血缘术语就自然确立了：
- **父节点（Parent）**：沿着当前节点通往根节点的唯一路径上，紧邻的下一个节点就是它的父节点。
- **子节点（Child）**：在远离根节点的方向上，紧邻在当前节点下方的节点为其子节点。
- **叶子节点（Leaf）**：没有任何子节点的终端节点。

> **提示**：挑选哪一个节点当根完全取决于具体问题的视角。你可以挑 $A$ 当根，也可以挑 $B$ 当根。画法虽然大相径庭，但节点之间的连接关系并未改变，它们都是完全合法的有根树。

### 树的遍历：从线性扫描到深度优先

理解了树的结构，接下来的核心问题就是：我们该如何访问一棵树里的所有节点？

在之前的课程（如 61A、CS88）中，大家操作列表（List）时，遍历是极其自然的事情：从头扫到尾；如果想标新立异，也可以从尾扫到头。列表具有严格的一维前后顺序，沿着这一线性方向推进即可。

然而，树是一种非线性结构，根本没有所谓绝对的“前”与“后”。面对一棵拥有分叉的树，到底应该按照什么样的次序去逐一访问节点，才算是一种“有意义的顺序”（Meaningful Order）？这就是树遍历（Tree Traversal / Tree Iteration）所要解决的问题。

访问次序直接取决于我们想达成的业务目标。一种非常直观的策略是像读书一样：从上到下、从左到右，一行一行地扫读。先读顶层的根节点，再读下一层的子节点，最后读更深一层的子节点。这种方式被称为**层序遍历（Level-order Traversal）**，其本质是广度优先，我们会在下一讲详细拆解。

今天我们的重心，放在另外三种极其重要的遍历方式上——**深度优先遍历（Depth-First Traversal，DFS）**。深度优先的核心哲学是：**沿着一条路径先向深层扎下去，优先探访远离根节点的深层节点，回溯之后再去探访相对浅层的分支**。

二叉树的三种深度优先遍历分别是：前序遍历（Pre-order）、中序遍历（In-order）和后序遍历（Post-order）。它们在实现上的核心差异，仅仅在于“访问/处理当前节点自身”这行操作，究竟是放在递归处理子节点之前、中间，还是之后。

接下来，我们统一以这棵经典的二叉树为例进行代码与逻辑推演：

```text
         (D)
       /     \
     (B)     (F)
    /   \   /   \
  (A)   (C)(E)   (G)
```

读图说明：根节点为 $D$，其左孩子为 $B$（拥有左孩子 $A$、右孩子 $C$），右孩子为 $F$（拥有左孩子 $E$、右孩子 $G$）。

#### 前序遍历：访问先于子树

前序遍历（Pre-order Traversal）的直观法则非常果脆：**每到达一个节点，先处理自己，然后再递归处理整棵左子树，最后递归处理整棵右子树**。

其经典递归代码实现如下：

```java
public void preOrder(Node x) {
    if (x == null) {
        return; // 基准情形：节点为空直接返回
    }
    print(x.key);       // 1. 访问当前节点（此处以打印为例）
    preOrder(x.left);   // 2. 递归遍历左子树
    preOrder(x.right);  // 3. 递归遍历右子树
}
```

代码逻辑非常直观，只要信任递归，它就能遍历整棵树。我们来完整跟踪在上述二叉树上的执行流与函数调用栈（Call Stack）：

```text
调用栈推演 (Call Stack Trace):
1. preOrder(D) 进入:
   - D 非空，打印 D
   - 暂停 D，递归调用 preOrder(B)
2. preOrder(B) 进入:
   - B 非空，打印 B
   - 暂停 B，递归调用 preOrder(A)
3. preOrder(A) 进入:
   - A 非空，打印 A
   - 调用 preOrder(A.left -> null)，直接返回
   - 调用 preOrder(A.right -> null)，直接返回
   - A 处理完毕，弹出调用栈，回到 B
4. 回到 B:
   - B 的左子树已全搞定，接下来递归调用 preOrder(C)
5. preOrder(C) 进入:
   - C 非空，打印 C，左右子节点均为空返回
   - B 的右子树搞定，B 完全执行完毕，弹出调用栈，回到 D
6. 回到 D:
   - D 的左子树（包含 B、A、C）全部处理完毕！
   - 接下来递归处理 D 的右子树，调用 preOrder(F)
7. preOrder(F) 进入:
   - F 非空，打印 F
   - 递归左子树 preOrder(E) -> 打印 E 并返回
   - 递归右子树 preOrder(G) -> 打印 G 并返回
   - F 处理完毕，回到 D，整棵树遍历结束！
```

> **结论**：前序遍历的输出序列为：**D, B, A, C, F, E, G**。

调用栈就像一张精密的备忘录：当我们深入到 $A$ 时，调用栈牢牢记着“搞定 $A$ 之后要回去接着处理 $B$；搞定 $B$ 之后还要回去处理 $D$ 的右半边”。正是靠着调用栈，递归程序才能在深扎之后精准回溯。

#### 中序遍历：左子树处理完才轮到自身

中序遍历（In-order Traversal）的思路与前序一脉相承，唯一的区别仅仅在于把打印当前节点的语句移到了两次递归调用之间：**必须先遍历完左侧的所有节点，才能访问当前节点自身，最后再去遍历右侧的所有节点**。

```java
public void inOrder(Node x) {
    if (x == null) {
        return;
    }
    inOrder(x.left);    // 1. 递归遍历左子树
    print(x.key);       // 2. 访问当前节点自身
    inOrder(x.right);   // 3. 递归遍历右子树
}
```

再次跟踪对根节点 $D$ 的调用过程：
- 我们站在 $D$ 节点上，能马上打印 $D$ 吗？不行！必须先去访问 $D$ 左边的整棵子树。
- 于是来到 $B$。能打印 $B$ 吗？依然不行！必须先去处理 $B$ 的左孩子。
- 于是来到 $A$。检查 $A$ 的左孩子为空，直接返回。此时 $A$ 左侧已处理完，终于可以打印 $A$ 了！随后检查 $A$ 的右孩子为空返回。
- 此时 $A$ 处理完毕，控制权回到 $B$。既然 $B$ 的左侧子树已经彻底搞定，现在正式打印 $B$！
- 接着前往 $B$ 的右子树 $C$，处理完毕后打印 $C$。至此，根节点 $D$ 的整棵左子树全部处理结束。
- 控制权回到 $D$。左子树全部就绪，终于可以打印 $D$ 了！
- 随后进入 $D$ 的右子树 $F$。同样先访问 $F$ 的左孩子 $E$，打印 $E$；回到 $F$ 打印 $F$；最后访问右孩子 $G$ 打印 $G$。

> **结论**：中序遍历的输出序列为：**A, B, C, D, E, F, G**。

> **提示**：观察这个输出序列：$A, B, C, D, E, F, G$，刚好是完美的字母升序！这绝非巧合。由于我们选择的示例二叉树恰好满足二叉搜索树（BST）的左小右大性质，而中序遍历“左 $\to$ 根 $\to$ 右”的访问次序，保证了在 BST 上中序遍历的结果必然单调递增。

#### 后序遍历：所有子节点搞定才最终收工

后序遍历（Post-order Traversal）将访问自身的语句放在了最后：**必须把左子树全部搞定，再把右子树全部搞定，最后才能回过头来处理当前节点**。

```java
public void postOrder(Node x) {
    if (x == null) {
        return;
    }
    postOrder(x.left);   // 1. 递归遍历左子树
    postOrder(x.right);  // 2. 递归遍历右子树
    print(x.key);        // 3. 访问当前节点自身
}
```

如果面对一张考试卷或练习题，要求快速写出后序遍历序列，根本不需要在脑子里完整压栈出栈，可以用逻辑排除法迅速锁定答案：
- 从根节点 $D$ 开始：$D$ 必须等左边所有人和右边所有人全部处理完才能打印，因此 **$D$ 必然排在全序列的最后一位**！
- 顺着这一逻辑，对于子树根节点 $F$，$E$ 和 $G$ 必须在 $F$ 之前打印；对于 $B$，$A$ 和 $C$ 必须在 $B$ 之前打印。

逐步推导执行流程：
- 左子树最深处：$A$ 的左右为空，率先打印 $A$；
- 紧接着访问 $B$ 的右孩子 $C$，$C$ 打印；
- $A$ 与 $C$ 都打印完后，回到父节点 $B$，打印 $B$；
- 转向右子树：先处理 $E$ 打印 $E$；再处理 $G$ 打印 $G$；
- $E$ 与 $G$ 搞定后，回到父节点 $F$，打印 $F$；
- 最后，左右两大家族全军收工，根节点 $D$ 最终被打印。

> **结论**：后序遍历的输出序列为：**A, C, B, E, G, F, D**。

#### 人类专属速算技巧：外沿绕圈巡游法

计算机懂得严格执行函数栈调用与回溯，但人类的大脑并不擅长在大脑中维护层层嵌套的递归状态。如果要在草稿纸上几秒钟内写出前序、中序或后序遍历，讲师传授了一个非常精妙的小技巧——**外沿绕圈法（沿树外围逆时针巡游）**。

在树的外围画一圈贴合的轮廓线，手拿激光笔或者铅笔，从根节点的左上方出发，沿着整棵树的外边缘**逆时针**平滑走一圈。在巡游过程中，我们根据经过每个节点的相对方位来触发访问：
- **前序遍历**：巡游线条从**节点的左侧**经过时，立刻记下该节点。
- **中序遍历**：巡游线条从**节点正下方**经过时，立刻记下该节点。
- **后序遍历**：巡游线条从**节点的右侧**经过时，立刻记下该节点。

为了看清这一技巧的威力，我们考察一棵稍复杂的树：

```text
           (1)
         /     \
       (2)     (3)
      /   \       \
    (4)   (5)     (6)
         /   \       \
       (7)   (8)     (9)
```

读图说明：根节点为 1，左孩子为 2，右孩子为 3；2 的左孩子为 4，右孩子为 5（5 下挂 7 和 8）；3 只有右孩子 6，6 只有右孩子 9。

我们手持笔尖，逆时针绕树外沿走一圈：

```text
       ╭───────( 1 )───────╮
      ╱       ╱     ╲       ╲
     │      ( 2 )   ( 3 )    │
     │     ╱    ╲       ╲    │
     │   (4)    ( 5 )   ( 6 )│
     │         ╱    ╲       ╲│
     │       (7)    (8)     (9)
      ╲_______│______│_______╱
```

读图说明：围绕整棵树的轮廓逆时针游走，笔尖会按空间位置依次掠过每个节点的左缘、下缘与右缘。

1. **前序记录（碰左侧即记）**：
   - 从 1 的上方出发，向下擦过 1 的左侧 $\to$ 记下 **1**；
   - 顺势向下擦过 2 的左侧 $\to$ 记下 **2**；
   - 继续向下擦过 4 的左侧 $\to$ 记下 **4**；
   - 绕过 4 的底部折返向上，擦过 5 的左侧 $\to$ 记下 **5**；
   - 向下擦过 7 的左侧 $\to$ 记下 **7**；绕过 7 擦过 8 的左侧 $\to$ 记下 **8**；
   - 回绕越过 2 升至右半区，擦过 3 的左侧 $\to$ 记下 **3**；
   - 向下擦过 6 的左侧 $\to$ 记下 **6**；向下擦过 9 的左侧 $\to$ 记下 **9**。
   - 最终前序序列：`1, 2, 4, 5, 7, 8, 3, 6, 9`。

2. **中序记录（掠过底部即记）**：
   - 笔尖顺着外廓，只有当从节点正下方擦过时才记录。
   - 沿左缘向下，4 最先被经过底部 $\to$ 记下 **4**；
   - 往上掠过 2 的底部 $\to$ 记下 **2**；
   - 拐入 5 的分支，依次掠过 7 的底部 $\to$ **7**，5 的底部 $\to$ **5**，8 的底部 $\to$ **8**；
   - 回到顶层，从 1 的正下方掠过 $\to$ 记下 **1**；
   - 转向右子树，3 没有左孩子，直接掠过 3 的底部 $\to$ **3**；接着是 6 的底部 $\to$ **6**，9 的底部 $\to$ **9**。
   - 最终中序序列：`4, 2, 7, 5, 8, 1, 3, 6, 9`。

3. **后序记录（擦过右侧即记）**：
   - 沿右侧包裹回拉，当笔尖从节点的右侧边缘掠过向上离开时记录。
   - 4 的右侧率先脱离 $\to$ 记下 **4**；
   - 7 的右侧 $\to$ **7**；8 的右侧 $\to$ **8**；5 的右侧脱离 $\to$ **5**；
   - 2 的整棵子树结束，从 2 的右侧升起 $\to$ 记下 **2**；
   - 右半区：9 的右侧 $\to$ **9**；6 的右侧 $\to$ **6**；3 的右侧 $\to$ **3**；
   - 最终回到最顶层 1 的右侧收工 $\to$ 记下 **1**。
   - 最终后序序列：`4, 7, 8, 5, 2, 9, 6, 3, 1`。

这个方法不需要推演任何复杂的递归状态机，只要顺着轮廓走一圈，左、下、右三个位置分别对应三种遍历，简单直观且绝不会出错。

#### 为什么需要不同的遍历顺序？真实场景抉择

为什么前人要定义这么多花哨的遍历顺序？为什么不直接规定一种标准顺序万事大吉？
原因在于：**不同的业务目标天然呼唤不同的访问时序**。

以操作系统中的文件目录系统为例。假设磁盘上存储着如下的层级目录结构（讲师调侃道这就像当年 Josh 玩《星际争霸》（StarCraft）时电脑里杂乱的文件夹）：

```text
                 [SC_Replays]
                 /          \
         [Direct_Overlay]  [Python_Scripts]
          /            \
     [lib1.dll]    [lib2.dll]
```

读图说明：根目录为 `SC_Replays`，其下包含 `Direct_Overlay` 和 `Python_Scripts` 两个子目录，`Direct_Overlay` 内部又存放着若干库文件。

##### 需求一：在终端中打印格式化的目录树（如 `tree` 命令）
如果我们在控制台执行目录打印，希望呈现层级分明、具有缩进美感的目录结构：
```text
SC_Replays
    Direct_Overlay
        lib1.dll
        lib2.dll
    Python_Scripts
```
此时必须采用**前序遍历**！
因为我们要先把父文件夹的名字 `SC_Replays` 打印在第一行，然后才能缩进并逐一打印其下的子文件夹和文件。如果采用后序遍历，先把所有底层文件都打印完了才冒出最顶层的目录名，在阅读逻辑上就彻底颠倒错乱了。前序遍历确保了根节点总是在其所有派生内容之前被优先处理。

##### 需求二：统计每个文件夹的总磁盘占用空间（`du` 命令）
假设现在要计算每个文件夹到底占用了多少字节的磁盘空间：
如果我们采用前序遍历，先访问顶层文件夹 `SC_Replays`，此时程序根本不知道它有多大！因为父文件夹的总体积等于它自身元数据加上所有子文件夹体积的累加总和。在没有处理完子项之前，父节点的统计工作根本无从下手。

因此，计算目录大小必须采用**后序遍历**！
程序必须先深入到最底层，汇总每一个文件的大小，把子文件夹的总容量计算完毕后返回给上层，父文件夹拿到所有子结点的计算结果后求和，才能得到自身的真实大小。

> **结论**：没有任何一种遍历是全能的。要先亮明父辈身份再展示后代，选前序遍历；要先汇总后代成果再结算父辈，选后序遍历。

### 打破唯一路径约束：从树迈向图

树的层级结构非常优美，但在现实世界中，并非所有实体之间的关系都能被规整地塞进上下从属的层级体系中。

不妨观察一下各大都市的地铁运行网，例如巴黎地铁地图（Paris Metro Map）：

```text
  (站 A) ========== (站 B)
    ║               ║   \
    ║               ║    (站 E)
    ║               ║   /
  (站 C) ========== (站 D)
```

读图说明：车站与车站之间纵横交错。从站 A 到站 D，既可以走 $A \to B \to D$，也可以走 $A \to C \to D$，甚至可以绕道 $B \to E \to D$。

这张地铁网显然不再是树。它既没有至高无上的根节点，也没有所谓的上下级子节点，更关键的是——**节点之间存在多条不同的连通路径，甚至形成了闭合环路**。

#### 图的推广：去掉束缚的自由结构

这促使我们对结构进行升维与推广。回顾树的定义：由节点和边组成，且任意两节点间有且仅有一条路径。
那么，如果把“任意两节点间仅有一条路径”这条铁律从规则手册中**彻底撕掉**，会发生什么？

幻灯片上的节点和连线依然存在，但由于删除了唯一路径的束缚，我们便得到了更通用、更强大的数学模型——**图（Graph）**。

> **定义**：图是由一组顶点（Vertices / Nodes）以及连接这组顶点的边（Edges）构成的集合。节点之间可以存在任意多条路径，允许闭合环路的存在。

在这个视角下，**树其实就是图的一个特例**。树是加了“无环且连通（任意两点路径唯一）”严苛约束后的特殊图。

#### 现场测验：BART 捷运系统到底是不是树？

为了考察大家对图与树边界的敏感度，课堂上抛出了一个极接地气的切身案例：我们身处旧金山湾区，每天乘坐的湾区捷运系统（BART）网络图，到底算不算法律意义上的树？

```text
       (Richmond)         (Antioch)
             \               /
              \             /
          (MacArthur)======/
                |
          (Embarcadero)
                |
          (San Bruno) <───────╮
            /       \         │
      (Millbrae)───(SFO 机场)─╯
```

读图说明：BART 线路在北湾和东湾大多呈放射状树枝分支（如 MacArthur 到其他站往往只有单一路线）；但在南部半岛 San Bruno、Millbrae 与旧金山国际机场（SFO）之间，轨道线路构成了一个三角形闭合环路。

从全网整体来看，**BART 绝对不是一棵树**！
虽然北边的大部分分支表现得像树，但只要在局部存在一个环——比如在 2019 年前后的运行图中，乘客可以从 San Bruno 出发，经 Millbrae 坐到 SFO 机场，再从 SFO 机场直接坐回 San Bruno——它就打破了树的判据。

#### 简单图的两大铁律

现实中的网络错综复杂，但在 CS61B 的讨论范畴中，除非有极其特殊的声明，我们通常默认研究的是**简单图（Simple Graph）**。

简单图必须满足两条底线规则：
1. **禁止自环（No Self-loops）**：一个节点不能有一条边直接连接到它自己。
2. **禁止平行边（No Parallel Edges / Multi-edges）**：任意两个节点之间，最多只能存在一条直接相连的边，不得有重边。

```text
    (1)───────(2)            ╭───╮                (1)
       \     /              │   │               // \\
        \   /               └──(A)             (2)   (3)
         (3)
     [简单图]              [含自环: 非简单图]   [含平行边: 非简单图]
 (无自环，无平行边)       (边起点终点同为 A)   (1 与 2 间有双重边)
```

读图说明：左侧为合法的简单图；中间节点 A 自身存在回环（自环），右侧节点 1 与 2 之间存在平行的两条边，均破坏了简单图的定义。

在后续算法讨论中，我们一律默认图为简单图。

#### 图的核心词汇与属性矩阵

图论中包含一套极其严谨的学术词汇体系。讲师反复告诫：**这些概念完全不需要死记硬背**，只要多动手画几张草图，这些词汇就会化作计算机科学家的本能直觉。

为了方便查阅与定位，核心概念整理如下表：

| 术语名称 | 英文对应 | 核心技术定义与内涵 |
| :--- | :--- | :--- |
| **顶点** | Vertex (复数 Vertices) | 图中的基本数据载体节点，与 Node 同义。 |
| **边** | Edge | 连接一对顶点的连线；两顶点连有边则称它们**相邻（Adjacent）**。 |
| **有向图** | Directed Graph (Digraph) | 边带有单向箭头，只能按指定方向单向通行（如网页超链接引用）。 |
| **无向图** | Undirected Graph | 边无箭头，连接是双向对等的（如双向通行的公路或好友关系）。 |
| **有环图 / 无环图** | Cyclic / Acyclic Graph | 图中是否包含可以从某个顶点出发又绕回自身的闭合回路。 |
| **边权重 / 标签** | Edge Weight / Label | 赋予边上的数值或属性，可代表物理距离、过路费、耗时或网络延迟。 |
| **路径** | Path | 顺着边连续相连的一系列顶点序列。 |
| **简单路径** | Simple Path | 序列中**不重复经过任何顶点**的路径。 |
| **环** | Cycle | 起点与终点为同一个顶点的闭合简单路径。 |
| **连通性** | Connected | 若两顶点间存在路径则称两点连通；若图中任意两点均连通，则为**连通图**。 |
| **非连通图** | Disconnected Graph | 图中存在互不相通的孤立子群（称为不同的**连通分量**）。 |
| **顶点的度** | Degree | 依附于该顶点的边的总数目（从该顶点发出的连接数）。 |

再审视之前的巴黎地铁网络：它是一个**无向的、全网连通的、包含多个环路的、顶点带有颜色与站名标签的简单图**。

### 图论的经典问题与难度鸿沟

一旦将现实问题抽象成了图，计算机科学家就能在上面提出无数具有极高应用价值的问题：
- 站点 $S$ 到站点 $T$ 之间的最短路径是什么？（导航地图的核心需求）
- 站点 $S$ 到站点 $T$ 之间不包含环的最长路径是什么？
- 当前拓扑结构中是否存在环？（死锁检测、调度冲突检测）
- 能否找到一条路径，**恰好经过图中的每一条边一次且仅一次**并回到起点？
- 能否找到一条路径，**恰好经过图中的每一个顶点一次且仅一次**并回到起点？

这些问题听起来形式极为相似，但图论展现出了一种令人震撼的奇妙特质——**问题的表象极度相似，背后的算法复杂度却存在天壤之别**。

请特别对比以下两个问题：
1. **欧拉回路（Eulerian Tour）**：在图中寻找一条恰好经过**每条边**一次且仅一次的闭合回路。
2. **哈密顿回路（Hamiltonian Cycle）**：在图中寻找一条恰好经过**每个顶点**一次且仅一次的闭合回路。

> **理论深度解析**：
> - 欧拉回路问题早在近三百年前（1736 年，欧拉解决柯尼斯堡七桥问题）就已经被彻底攻破。判断是否存在欧拉回路极其简单：只需线性扫描检查每个顶点的度数是否全为偶数即可，算法时间复杂度是近乎完美的线性时间 $O(V + E)$。
> - 然而，仅仅把“经过每条边”换成“经过每个顶点”的哈密顿回路问题，几百年来无数顶尖数学家与计算机科学家前赴后继，至今**未能找到任何一个多项式时间（如多项式阶 $O(V^k)$）的高效算法**！
> - 目前已知解决哈密顿回路的最佳算法依然需要指数级时间（Exponential Time，如 $O(2^V)$），在节点规模稍大时计算耗时就会爆炸至天文数字。如果谁能在未来发明出一个高效解决哈密顿回路的多项式算法，将直接证明 $P = NP$，包揽图灵奖、克雷千禧大奖等全球所有顶级荣誉。

图论就是如此迷人而深邃。CS61B 将带大家打好最坚实的基础，后续的高级算法课（如 CS170）还会对这些深刻的理论鸿沟展开更壮阔的推导。

### 实战图问题：$s$-$t$ 连通性与深度优先搜索

现在，我们把目光收回到眼前，亲手攻克一个经典的图论问题：**$s$-$t$ 连通性问题（$s$-$t$ Connectivity）**。

> **问题描述**：给定一张无向图，以及一个指定的起点 $s$（例如节点 0）和一个目标终点 $t$（例如节点 7）。编写一个算法，判断从 $s$ 到 $t$ 是否存在一条通路，返回布尔值 `true` 或 `false`。

人类用肉眼扫一眼图，很容易判断两点是否相通。但计算机没有全局视野，它必须依赖严谨的机械化指令。

我们考察如下这幅包含 9 个顶点的经典图结构：

```text
       (0) ─── (1) ─── (2) ─── (5) ─── (6) ─── (7)
                        |       | \
                        |       |  (8)
                        |      (4)
                        |       |
                        ╰──────(3)
```

读图说明：起点为 0，终点为 7。邻接关系如下：0 连 1；1 连 0, 2；2 连 1, 5；5 连 2, 4, 6, 8；4 连 5, 3；3 连 4；6 连 5, 7；7 连 6；8 连 5。

#### 天真递归的致命缺陷：无休止的“踢皮球”死循环

面对连通性，初学者最容易想到的直觉是递归询问：“如果我自己就是终点 $t$，那显然连通；如果我不是，我就问我身边的所有邻居，只要他们当中有任何一个人能走到 $t$，那我自然也就能到 $t$。”

伪代码设计如下：
```java
// 错误示例：存在致命死循环漏洞的天真算法
boolean connected(int s, int t) {
    if (s == t) {
        return true; // 基准情形：人已在原地
    }
    for (int neighbor : neighbors(s)) {
        if (connected(neighbor, t)) {
            return true; // 只要邻居能到，我就能到
        }
    }
    return false;
}
```

这段逻辑听起来天经地义，但只要在无向图上稍微一跑，就会瞬间崩溃：
1. 我们从 0 出发，要找 7。0 问邻居 1：“你能到 7 吗？”
2. 此时执行流进入 `connected(1, 7)`。1 不是 7，于是 1 环顾四周，寻找自己的邻居。
3. 1 的第一个邻居正是 0！于是 1 严肃地向 0 发起询问：“0 啊，你能到 7 吗？”
4. 0 再次被调用，0 又不是 7，0 又去问 1……

> **易错点**：由于无向图的边是双向互通的，没有状态记忆的递归会在两个相邻节点之间反复来回调用（$0 \to 1 \to 0 \to 1 \dots$），程序陷入无穷递归，最终以栈溢出崩溃（StackOverflowError）惨烈收场。

#### 核心解药：标记机制（Visited / Marked）

解决死循环的手段极其质朴而有力：**引入访问标记（Marking）机制**。

> **核心原则**：一旦我们踏足并访问了一个顶点，就必须立刻在它身上盖一个戳（标记为“已访问”）。在后续探索过程中，**绝对不向任何已经标记过的邻居发起重复询问**！

我们之前已经问过节点 0 能否到 7，它在当前的递归调用路径上已经挂起，绝无必要回头再向它重复请教同一个傻问题。

#### 标记版 DFS 完整执行追踪

引入标记后，我们来严格推演从起点 0 寻找终点 7 的完整执行时序。我们将标记形象地视为“把节点的颜色点亮”：

```text
DFS 追踪步序 (寻找 0 到 7 的通路):
1. 访问 0: 标记 0。检查邻居 1（未标记）。调用 connected(1, 7)。
2. 访问 1: 标记 1。检查邻居：
   - 0 已标记，果断跳过！
   - 发现未标记邻居 2，调用 connected(2, 7)。
3. 访问 2: 标记 2。邻居 1 已标记跳过；向未标记邻居 5 推进，调用 connected(5, 7)。
4. 访问 5: 标记 5。邻居 2 已标记跳过；假设算法先检查未标记邻居 4，调用 connected(4, 7)。
5. 访问 4: 标记 4。邻居 5 已标记跳过；向未标记邻居 3 推进，调用 connected(3, 7)。
6. 访问 3: 标记 3。
   - 检查 3 的邻居：只有 4，但 4 已经被标记！
   - 3 的所有邻居均已考察完毕，全军覆没，3 本身也不是 7。
   - 3 确认“通往 7 的路绝不可能经过我”，向 4 返回 false！
7. 回溯到 4: 4 收到 3 的拒绝；4 环顾四周，所有邻居（3 和 5）都已标记，4 也走投无路，向 5 返回 false！
8. 回溯到 5: 5 得知分支 4 是一条死胡同，并不气馁。5 检查自己其他的未标记邻居，发现了 6！调用 connected(6, 7)。
9. 访问 6: 标记 6。邻居 5 已标记跳过；发现未标记邻居 7，调用 connected(7, 7)。
10. 访问 7: 触发基准情形：7 == 7！宣布成功抵达，返回 true！
```

随后，喜讯沿着调用栈一路向上传递：
- 6 收到 7 的 `true`，向 5 返回 `true`；
- 5 收到 6 的 `true`，任务已完成（甚至无需再去无谓地探索未标记邻居 8！），直接向 2 返回 `true`；
- 2 向上返回 `true` $\to$ 1 向上返回 `true` $\to$ 0 最终返回 `true`！

在解决 $s$-$t$ 连通性问题的过程中，我们实际上创造了一种极为通用的图算法——**图的深度优先搜索（Depth-First Search，DFS）**。

> **结论**：DFS 的本质逻辑在于：**在转向下一个平级邻居之前，必须先把当前邻居所引出的一整片子图完全深入探索到底**。

#### 漫画插曲：约会焦虑与 DFS 思维

讲师在这里引用了一幅非常生动的极客漫画来调侃 DFS 的行事作风：
一个年轻人面临人生重大约会，开始在脑子里预演可能会发生的各种突发状况。他列出了“突发疾病”、“跳舞失误”、“餐厅选错”等多个分支。
接着，他开始用深度优先的方式死磕“突发疾病”：疾病有哪些？遭雷劈、椅子摔坏、被蛇咬……
他盯住“被蛇咬”，继续深入：蛇有哪些种类？束带蛇、玉米蛇……
他进一步聚焦“玉米蛇”：哪种斑纹？某种特定亚种……
结果到了约会当天，他满脑子都在死死纠结一条具体的玉米蛇，完全把约会本身抛到了九霄云外。最后他崩溃自嘲：“我真的不能再用深度优先搜索来思考人生了！”

这幅漫画道出了 DFS 的精髓：**一旦抓住一条线索，就穷追不舍一直钻到最底层的细枝末节（叶子或死胡同），撞了南墙才肯回溯**。

### 路径求解升级：`edgeTo` 数组与回溯还原

刚才的算法虽然解决了连通性问题，但它只回答了一个干瘪的“Yes or No”（布尔值）。在现实世界的导航系统或路径规划中，用户绝不会满足于听到一句“从北京到巴黎确实有路可走”——大家需要的是**具体怎么走**的完整路径指令！

我们能否对 DFS 稍作改造，让它不仅能判断连通性，还能找出从源节点 $s$ 出发、通往图中其他所有可达顶点的完整路径？

答案是肯定的，而且改动出人意料地精巧：**我们不需要推倒重来，只需在 DFS 的递归标记过程中，顺手维护一个记录来源的数组——`edgeTo[]`**。

#### `edgeTo[]` 数组的记录机理

> **定义**：`edgeTo[w] = v` 的技术含义是：在遍历探索过程中，**我们是通过顶点 $v$ 首次发现并踏上顶点 $w$ 的**。也就是说，$v$ 是到达 $w$ 的前驱节点（Edge $v \to w$）。

这就好比我们在穿过幽暗森林时沿途撒下的一串“面包屑导航线”。每当我们通过一条边攻占一个从未访问过的新节点时，就在账本上记下：我是从哪儿过来的。

#### 完整探索与 `edgeTo` 构建追踪

依然从源点 0 出发，执行一次完整的全局深度优先搜索（不仅为了找 7，而是遍历所有连通节点），其记录过程如下：

```text
DFS 轨迹与 edgeTo 写入时序:
1. 在源点 0 处: 标记 0。
2. 0 走向 1: edgeTo[1] = 0; 标记 1; 递归进入 1。
3. 1 走向 2: edgeTo[2] = 1; 标记 2; 递归进入 2。
4. 2 走向 5: edgeTo[5] = 2; 标记 5; 递归进入 5。
5. 5 走向 4: edgeTo[4] = 5; 标记 4; 递归进入 4。
6. 4 走向 3: edgeTo[3] = 4; 标记 3; 递归进入 3。
7. 3 邻居全已标记，回溯到 4; 4 邻居全已标记，回溯到 5。
8. 5 走向 6: edgeTo[6] = 5; 标记 6; 递归进入 6。
9. 6 走向 7: edgeTo[7] = 6; 标记 7; 递归进入 7。
10. 7 邻居全已标记，回溯到 6; 6 回溯到 5。
11. 5 走向 8: edgeTo[8] = 5; 标记 8; 递归进入 8。
12. 8 回溯到 5; 5 回溯到 2; 2 回溯到 1; 1 回溯到 0。DFS 全面结束！
```

遍历结束之后，我们在内存中得到了这样一张极具价值的映射表：

| 目标顶点 $v$ | 前驱来源 `edgeTo[v]` | 物理语义解读 |
| :---: | :---: | :--- |
| `0` | `-` (源点) | 旅程的起点 |
| `1` | `0` | 从 0 跨出一步到达 1 |
| `2` | `1` | 从 1 跨出一步到达 2 |
| `3` | `4` | 从 4 跨出一步到达 3 |
| `4` | `5` | 从 5 跨出一步到达 4 |
| `5` | `2` | 从 2 跨出一步到达 5 |
| `6` | `5` | 从 5 跨出一步到达 6 |
| `7` | `6` | 从 6 跨出一步到达 7 |
| `8` | `5` | 从 5 跨出一步到达 8 |

#### 如何顺藤摸瓜还原完整路径？

有了这张表，无论你想查询从源点 0 到图中哪个顶点的路径，只需做简单的**逆向溯源**即可：

- **查询如何到达顶点 5**：
  1. 查看 `edgeTo[5]`，得知是从 **2** 来的；
  2. 查看 `edgeTo[2]`，得知是从 **1** 来的；
  3. 查看 `edgeTo[1]`，得知是从 **0** 来的；
  4. 遇到源点 0，溯源终止！将链条反转，得到完整前进路径：$0 \to 1 \to 2 \to 5$。

- **查询如何到达终点 7**：
  1. 查看 `edgeTo[7]` $\to$ 来自 **6**；
  2. 查看 `edgeTo[6]` $\to$ 来自 **5**；
  3. 查看 `edgeTo[5]` $\to$ 来自 **2**；
  4. 查看 `edgeTo[2]` $\to$ 来自 **1**；
  5. 查看 `edgeTo[1]` $\to$ 来自 **0**；
  6. 反转链条，得到通往 7 的完整路径：$0 \to 1 \to 2 \to 5 \to 6 \to 7$。

区区一个简单的一维整型数组，不仅帮我们记忆了树状遍历轨迹，还能在常数时间内为任意节点倒推回家谱路径，设计极其轻量而优雅。

#### 课堂关键质询：DFS 找到的一定是最短路径吗？

在展示完这套精巧的路径还原之后，台下有同学提出了一个极具敏锐度的问题：“老师，通过 DFS 和 `edgeTo[]` 数组找出来的这条路径，能保证是步数最少的最短路径吗？”

> **易错点**：**绝对不能保证！**
> DFS 的核心特点是“一条道走到黑”，它在探索时根本没有考虑过距离长短或者边的条数。在上面的例子中，我们从 2 出发，因为碰巧先访问了 5，所以留下的路径是 $0 \to 1 \to 2 \to 5$。如果在另一张图中，从 0 到某个节点有一条直达捷径，但 DFS 偏偏先一头扎进了一条迂回曲折的长廊，那它记录下来的就会是一条冗长绕远的路径。
> 寻找无权图的最短路径，必须依赖下一讲的广度优先搜索（BFS）。

### 图的遍历次序：DFS 前序与后序

正如在二叉树中我们拥有前序与后序一样，图的深度优先搜索同样存在两种极为重要的访问时序：**图的前序（Pre-order）与图的后序（Post-order）**。

理解图的前后序，最简洁精准的判据就是紧盯**递归调用栈**的行为：

> **定义**：
> - **图的 DFS 前序（Pre-order）**：严格等价于**节点初次被调用 `dfs()` 并被打上标记的时刻先后次序**（进入调用栈的次序）。
> - **图的 DFS 后序（Post-order）**：严格等价于**节点的 `dfs()` 方法彻底执行完毕并从调用栈退栈返回的时刻先后次序**（弹出调用栈的次序）。

回到刚才对包含 9 个节点的图的追踪：

```text
进入调用栈 (Push) 的时间线:
dfs(0) -> dfs(1) -> dfs(2) -> dfs(5) -> dfs(4) -> dfs(3) -> [3无处可去] ...
```
在节点首次被标记并进入调用栈的维度上，我们依次标记了：
$0 \to 1 \to 2 \to 5 \to 4 \to 3$，随后是 $6 \to 7$，最后是 $8$。
因此，**图的 DFS 前序序列**为：**0, 1, 2, 5, 4, 3, 6, 7, 8**。

再观察退出调用栈（Pop）的时间线：
- 节点 3 发现所有邻居都已被标记，自己无路可走，第一个完全执行结束并返回！因此，**3 是后序遍历中第一个出现的节点**。
- 随后控制权退回到 4，4 也处理完毕退出栈；
- 紧接着在右下分支中，7 最先处理完毕退栈，接着 6 退栈；
- 分支 8 处理完毕退栈；
- 5 的所有分支均已探明，5 退栈；
- 随后 2 退栈，1 退栈，0 最后一个退栈！

因此，**图的 DFS 后序序列**为：**3, 4, 7, 6, 8, 5, 2, 1, 0**。

> **提示**：牢记一句话：**前序看调用（谁先被踏足），后序看返回（谁先收工结束）**。这个后序序列在后续课程中极其关键，它是解决“拓扑排序”（Topological Sort）和有向无环图强连通分量算法的核心基石。

### 预告与全篇总结

在本讲中，我们完成了一次从特例到一般的认知跃迁：
1. **从树到图**：树是严苛的无环连通特例，任意两节点间路径唯一；撕掉这一限制，我们就拥有了表达任意网络关系的通用模型——图。
2. **术语与规则**：61B 重点关注无自环、无平行边的简单图；熟练掌握有向/无向、连通性、环路等直观概念。
3. **遍历思想**：
   - 树的深度优先包括前序（根左右）、中序（左根右）、后序（左右根），人类速算可使用外沿逆时针绕圈法；
   - 不同的业务场景对应不同的遍历顺序（如目录打印需前序，大小统计需后序）；
   - 图的深度优先遍历（DFS）必须依靠**标记机制（Visited/Marked）**阻断无穷递归环路；
   - 通过巧妙的 `edgeTo[]` 数组，我们可以用极低的开销逆向回溯出从源点到各顶点的完整路径；
   - 图的 DFS 前序代表函数调用与标记的顺序，后序代表函数执行完毕返回的顺序。

DFS 是一种“执着深挖”的探索范式。但正如大家敏锐察觉到的，它并不能解决“寻找最短路径”的问题。下一讲，我们将跳出递归，借助队列构建非递归的**广度优先搜索（BFS）**。BFS 就像水波荡漾一样自近及远一层层向外扩散，它将成为解决无权图最短路径问题的终极利器。

#### 题目一：二叉树的后序遍历序列判定题

**题干**：
给定如下二叉树，要求给出其合法的后序遍历（Post-order Traversal）访问序列：

```text
         (D)
       /     \
     (B)     (F)
    /   \   /   \
  (A)   (C)(E)   (G)
```

**解析**：
根据后序遍历“先左子树、再右子树、最后访问根节点”的技术规则：
1. 对于整棵树的根节点 $D$，$D$ 必须在左子树（包含 $A, B, C$）和右子树（包含 $E, F, G$）全部遍历完毕之后才能被访问，因此 **$D$ 必然位于整个序列的最后一个位置**。据此可以直接排除所有末位不是 $D$ 的选项。
2. 同理，对于子树根节点 $B$，其自身必须在 $A$ 和 $C$ 均被访问之后才能出现；
3. 对于子树根节点 $F$，其自身必须在 $E$ 和 $G$ 均被访问之后才能出现。
4. 综合推导各子树：左子树后序为 $A, C, B$；右子树后序为 $E, G, F$；最后拼接根节点 $D$。

**答案**：
后序遍历序列为：`A, C, B, E, G, F, D`。

#### 题目二：现实交通网络的图属性辨析题

**题干**：
观察旧金山湾区捷运（BART）网络，判断该交通网络图在图论意义上是否为一棵“树”？如果不是，请指出破坏树性质的关键区域。

**解析**：
树的充要条件是：任意两个节点之间存在且仅存在一条路径（连通且无环）。
在 BART 线路中，绝大多数北湾和东湾区间呈现为无环的放射状分支；但在半岛南部区域，存在连接 San Bruno、Millbrae 以及旧金山国际机场（SFO）的闭合轨道环线。
由于乘客可以沿 $San Bruno \to Millbrae \to SFO \to San Bruno$ 形成闭合回环，导致该区域节点之间存在多于一条路径，破坏了“任意两点路径唯一”的铁律。

**答案**：
BART 网络不是树，它是一个包含环路的连通图；成环区域位于 San Bruno — Millbrae — SFO 机场之间的三角形轨道环线。

#### 题目三：递归判断 $s$-$t$ 连通性的天真算法缺陷分析

**题干**：
某同学编写了如下算法来判断无向图中两节点 $s$ 与 $t$ 是否连通：
```java
boolean connected(int s, int t) {
    if (s == t) return true;
    for (int neighbor : neighbors(s)) {
        if (connected(neighbor, t)) return true;
    }
    return false;
}
```
请分析该算法在无向图上运行时会遇到什么严重错误，并给出核心修复方案。

**解析**：
1. **错误根因**：无向图的边是双向对等的。当从节点 $s$ 递归调用其邻居 $w$ 时，$w$ 的邻居列表中必然包含 $s$。由于算法缺乏状态记忆，在 $w$ 处会再次调用 `connected(s, t)`，从而在 $s$ 与 $w$ 之间陷入无限互相调用的死循环，最终引发系统的调用栈溢出（`StackOverflowError`）。
2. **修复方案**：引入一个全局或随递归传递的布尔标记数组 `marked[]`（或 `visited` 集合）。在访问一个节点前将其设为已访问，并在遍历邻居时增加守卫条件 `if (!marked[neighbor])`，严禁重复踏足已经标记过的节点。

**答案**：
缺陷为无向边双向递归导致的无穷递归与栈溢出崩溃；修复手段是引入 `marked[]` 访问标记机制，在遍历时跳过所有已访问的邻居。

#### 题目四：DFS 生成路径的最短性判定题

**题干**：
在无向无权图上运行基于 DFS 的路径记录算法，通过维护 `edgeTo[]` 数组从终点向源点反向回溯得到的前进路径，是否一定是从起点到终点的“最短路径”？为什么？

**解析**：
依据 DFS 的算法机理，DFS 在行进过程中是优先沿着某一条未访问分支盲目深入到底，直至遇到死胡同或目标才终止或回溯。它在挑选邻居时并未综合衡量路径的边数或权重。
如果源点到目标点之间存在一条直达边（长度为 1），但 DFS 碰巧先选择了一条经过若干中继节点的曲折长路径且成功抵达了目标，那么 `edgeTo[]` 记录下来的就会是这条冗长的迂回路线。

**答案**：
不保证是最短路径。DFS 仅保证找到一条可行通路，完全没有考虑路径长度；保证无权图最短路径需采用广度优先搜索（BFS）。
