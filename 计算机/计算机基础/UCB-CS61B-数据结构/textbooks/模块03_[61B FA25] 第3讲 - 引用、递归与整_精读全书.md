## 引用、递归与整数列表
> 对应块：BLK03 | 覆盖分集：P06 | 块标题（分集名）：《[61B FA25] 第3讲 - 引用、递归与整》

接下来的三四讲，我们的核心目标是在 Java 中动手实现一个能够自由生长的列表。大家都知道，Java 内置的数组在初始化时长度就已经写死，无法自动扩容。要想让数据结构能够根据需要无限容纳新的元素，我们就必须自己动手构建一种能够动态伸缩的列表结构。

但在真正动手敲下列表的代码之前，我们必须先直面并解开一个困惑了无数初学者的经典难题——“海象之谜”。这个谜题关乎计算机内存的底层运行机理，搞不懂它，后续构建任何复杂数据结构都像是在流沙上盖楼。

---

### 从海象之谜谈起：两段令人困惑的代码

想象一下，我们定义了一个表示海象的类 `Walrus`，它有两个实例变量：一个是表示体重的整数 `weight`，另一个是表示象牙尺寸的双精度浮点数 `tuskSize`。

现在，我们来看第一段代码：

```java
Walrus a = new Walrus(1000, 8.3);
Walrus b = a;
b.weight = 5;

System.out.println(a.weight);
System.out.println(b.weight);
```

我们创建了一只体重 1000、象牙 8.3 的海象 `a`，接着声明了一个海象变量 `b`，并令 `b = a`。随后，我们把 `b` 的体重改成了 5。

直觉上，你可能会觉得只有 `b` 的体重被改动了，`a` 应该依然是那只 1000 磅的庞然大物。然而实际运行后打印出来的结果令人意外：`a.weight` 是 5，`b.weight` 也是 5！修改 `b` 的属性，竟然悄无声息地同步改变了 `a`。

为了对比，我们再看另一段看似逻辑完全相同的代码，只不过操作对象换成了最普通的整数：

```java
int x = 5;
int y = x;
x = 2;

System.out.println(x);
System.out.println(y);
```

我们令 `x` 等于 5，声明整数 `y` 并令 `y = x`。接着我们把 `x` 的值改成了 2。此时打印出来的结果是什么？`x` 变成了 2，而 `y` 依然稳稳地停留在 5，完全没有受到任何牵连。

> **易错点**：同样是声明两个变量、同样是用等号赋值、同样是修改其中一个变量的值，为什么海象改了一个会影响另一个，而整数改了一个却彼此完全独立？

要彻底解释这个现象，我们不能停留在代码语法表面，必须稍微下潜一步，看看计算机在物理内存中究竟是如何存放数据的。

---

### 计算机内存模型与基本数据类型

计算机的物理内存本质上非常单纯：它就是硬件中一长串由 0 和 1 构成的比特序列（Bits）。至于底层是用带电荷的电容、晶体管还是磁芯线圈实现的，我们写上层代码时无需关心。但在计算机内部，任何数据最终都必须被编码成这一串连续的 0 和 1。

例如，数字 72 在内存中可能被编码为 `01001000`；浮点数 205.75 或字符 `'h'` 也有其各自对应的二进制比特串。

既然所有东西在底层都是 0 和 1，计算机又是怎么区分它们到底是个整数、字符还是浮点数呢？这就依赖于编程语言中的**类型系统**。

在 Java 中，使用任何变量之前都必须先声明它的类型。声明变量的底层实质，就是在告诉 Java 虚拟机：“请在内存中为我预留出足够存放这种类型的比特位空间，并给这块空间贴上一个变量名标签。”

Java 拥有八种内置的**基本数据类型（Primitive Types）**：
- 整数类：`byte`（8 位）、`short`（16 位）、`int`（32 位）、`long`（64 位）；
- 浮点类：`float`（32 位）、`double`（64 位）；
- 逻辑与字符类：`boolean`（通常 1 位或按字长存储）、`char`（16 位）。

当你写下：

```java
int x;
```

Java 就会立刻在内存中圈出一块 32 位的物理空间，并在内部建立一张映射表：以后程序员只要在代码里提到 `x`，指代的就是这特定的 32 个比特位。同理，当你声明 `double y;` 时，Java 会分配 64 位物理空间，日后凡是提到 `y`，指的都是这特定的 64 个比特位。

```text
+-----------------------+          +---------------------------------------+
|  int x (32 bits)      |          |  double y (64 bits)                   |
|  [ 0000...00000101 ]  |          |  [ 0100...00000000 ]                  |
+-----------------------+          +---------------------------------------+
```
读图说明：计算机内存底层为变量分配固定位宽的连续比特盒子，基本类型的值直接编码为二进制比特存放于盒子内部。

在真实的计算机运行中，我们很难直接看懂那漫无边际的 0 和 1。因此在日常设计与调试中，我们通常采用一种高度抽象的人类友好视角——**方框表示法**：我们用一个带名字的方框代表变量所占用的内存，方框里面直接写上人类看得懂的数值，而不是冰冷的二进制比特。

### 变量赋值的等号黄金法则

搞清楚了变量对应的内存盒子，我们就能揭开第一个谜底了。变量赋值遵循一条至关重要的运行公理，我们称之为**等号黄金法则（The Golden Rule of Equals）**。

> **定义**：等号黄金法则（The Golden Rule of Equals）：
> 当你写下赋值语句 `y = x;` 时，赋值运算符永远只做一件事——**把等号右边变量盒子里的全部比特位原封不动地复制一份，写入左边变量的盒子里**。这里没有任何花哨的指针连接，没有隐含的联动绑定，只有纯粹、彻底的位复制（Bit Copy）。

现在我们用这条黄金法则一步一步重新推演整数代码的执行全过程：

```text
第一步：int x = 5;
+-------+
| x: 5  |
+-------+

第二步：int y = x; （把 x 盒子里的 32 位比特直接复制一份写入 y 盒子）
+-------+       +-------+
| x: 5  |  ==>  | y: 5  |
+-------+       +-------+

第三步：x = 2; （根据黄金法则，把数字 2 写入 x 盒子，完全不触碰 y 盒子）
+-------+       +-------+
| x: 2  |       | y: 5  |
+-------+       +-------+
```
读图说明：基本类型变量赋值时，等号运算符直接逐位复制数值，各变量拥有完全独立的内存存储单元。

1. 第一步 `int x = 5;`：内存为 `x` 分配了 32 位盒子，并将数字 5 的二进制编码写入其中；
2. 第二步 `int y = x;`：黄金法则生效。系统把 `x` 盒子里的位直接复制一份放进 `y` 盒子，此时 `y` 也拥有了独立的 5；
3. 第三步 `x = 2;`：黄金法则再次生效。系统将数字 2 的二进制编码写入 `x` 的盒子。黄金法则只规定往叫 `x` 的盒子里写位，根本没有命令去动叫 `y` 的盒子。

因此，`x` 的改变对 `y` 毫无影响。谜题的前半部分彻底解开了。

### 引用类型的底层真相：地址、箭头与共享对象

解开了整数之谜，海象的问题接踵而至。回头看看 Java 的那八种基本类型：`byte`、`short`、`int`、`long`、`float`、`double`、`boolean`、`char`。

这八个名字里根本没有海象！不仅没有海象，我们平时写的大多数类——狗、行星、字符串、各种复杂数据结构，全都不在这八种类型之中。在 Java 中，除了这八种基本类型之外，**所有其他类型统统被称为引用类型（Reference Types）**。

引用类型在内存中的行为方式与基本类型有着本质的区别。

#### 创建对象与 new 关键字

当我们使用 `new` 关键字创建对象时，底层实际执行了两个关键动作：

```java
new Walrus(1000, 8.3);
```

1. **开辟对象存储空间**：Java 虚拟机会前往堆内存（Heap），寻找一块足够宽敞的连续空间来安放海象的实例变量。海象需要 32 位存体重（`int`）、64 位存象牙尺寸（`double`），再加上对象头部元数据，至少需要 96 位以上。找到空间后，构造函数将 1000 和 8.3 等数值填入其中；
2. **返回对象内存地址**：对象在内存中创建好了，但如果不记住它在哪里，它就会立刻在内存的大海中迷失。因此，`new` 关键字在完成对象构建后，会返回该对象在内存中的绝对索引地址（例如第 2384 万号内存单元）。

#### 引用变量的 64 位盒子

接着看变量声明部分：

```java
Walrus someWalrus;
```

当我们声明一个引用类型变量时，Java 同样会在内存（栈空间）中为它预留一个盒子。但请务必记住这个硬性事实：

> **结论**：在 Java 中，**所有引用类型变量的大小固定只有 64 位**。

无论你引用的对象有多大，引用变量本身永远都只有 64 位。为什么？因为真实的海象对象至少占 96 位，如果未来构建一个拥有 10 个甚至 100 个字段的行星对象，它的体积可能高达数千位。如果把对象实体硬塞进变量盒子，变量的尺寸就会变得不可预测，栈内存管理也将彻底崩溃。

因此，Java 设计者规定：**引用类型变量绝不存储对象本体，它只存储对象在内存中的 64 位地址（即引用 Reference）**。如果当前没有任何指向的对象，盒子里就填入全 0，在 Java 中体现为 `null`。

#### 黄金法则在引用类型上的完全生效

现在我们将等号黄金法则套用到海象代码中：

```java
Walrus a = new Walrus(1000, 8.3);
Walrus b = a;
b.weight = 5;
```

1. `Walrus a = new Walrus(1000, 8.3);`：`new` 关键字在堆中造出了一只真正的海象，并返回这只海象的内存地址（假设为 `0x7234`）。等号黄金法则生效，把这个 64 位的地址数字复制放进变量 `a` 的盒子里；
2. `Walrus b = a;`：**等号黄金法则依然在机械地执行位复制！** 它完全不关心盒子里装的是整数还是地址。它只做一件事：把 `a` 盒子里的全部 64 位比特（也就是地址 `0x7234`）完整拷贝一份，填入 `b` 的盒子里；
3. 此时，`a` 盒子里装的是 `0x7234`，`b` 盒子里装的也是 `0x7234`。在物理内存中，**海象对象自始至终只有一只**，而 `a` 和 `b` 保存了完全相同的藏宝图坐标；
4. `b.weight = 5;`：点号运算符（`.`）顺着 `b` 盒子里的地址去访问堆内存中那只唯一的海象，将其体重的 32 位空间修改成了 5。随后我们顺着 `a` 盒子里的地址再去查看这只海象，看到的体重自然也就是 5。

```text
栈内存 (Stack)                           堆内存 (Heap)
+--------------+ 64-bit 地址 (0x7234)    +-----------------------------+
| Walrus a     | ----------------------> | Walrus 实例对象 (96+ bits)   |
+--------------+                         | - weight: 5 (原 1000)       |
                                         | - tuskSize: 8.3             |
+--------------+ 64-bit 地址 (0x7234)    |                             |
| Walrus b     | ----------------------> |                             |
+--------------+                         +-----------------------------+
```
读图说明：引用类型变量仅保存 64 位内存地址指针，执行 `b = a` 复制的是地址位，导致变量 `a` 与 `b` 共同指向堆中同一个海象对象。

在日常推演中，记住冗长的十六进制地址太费力，所以我们用**箭头（Pointer）**来直观代表这个 64 位的地址。每当在图示中看到一个箭头从方框指出去，你的脑海中必须立刻映射出底层事实：**方框里装的是个 64 位地址，顺着这个地址能在内存中找到具体的实体**。

课堂上有同学提出过一个非常敏锐的问题：“如果我建一个行星对象，里面有十个实例变量，引用类型变量还是 64 位吗？”

答案是：**是的，永远是 64 位**。因为无论对象内部有多少字段、体积多么庞大，引用变量始终只负责当一个门牌号，存的永远只是指向那个实体的起始地址。

### 函数参数传递依然遵循黄金法则

很多初学者在初次接触函数调用时，会误以为函数传参有着另一套神秘的传参机制。其实不然，Java 的底层设计极其连贯统一：**方法传参在底层依然完全遵守等号黄金法则**。

看下面这段代码：

```java
public static double average(double a, double b) {
    return (a + b) / 2.0;
}

// 在 main 方法中调用：
double x = 5.5;
double y = 10.5;
double avg = average(x, y);
```

代码里并没有显式写出等号，但在调用 `average(x, y)` 的那一瞬间，Java 虚拟机在栈帧上为形参分配了新的盒子 `a` 和 `b`，并静默执行了赋值操作：`a = x;` 以及 `b = y;`。

根据等号黄金法则，实参 `x` 盒子里的 64 位浮点数位被精准复制给了形参 `a`，实参 `y` 盒子里的位被精准复制给了形参 `b`。在函数内部，`a` 和 `b` 拥有完全属于自己的独立盒子。即使你在函数体内将 `a` 改成 999.0，外部的 `x` 也绝不会发生一丝一毫的变动。

> **结论**：Java 是一门纯粹的**按值传递（Pass-by-value）**语言。传入基本类型时，复制的是具体的数值位；传入引用类型时，复制的是 64 位的地址位。

如果形参是一个对象引用（例如 `Walrus w`），调用时传过去的也是该海象的 64 位内存地址。在函数内通过 `w.weight = 99` 可以修改堆中海象的内部数据；但如果你在函数内执行 `w = null;`，修改的仅仅是局部形参 `w` 这个盒子里的地址位，绝对动摇不了调用方那个原始变量所保存的指向。

### 数组也是引用类型与对象迷失

在引入自定义列表之前，我们再明确一个关键边界：**数组也是对象**。

重新审视那八种基本类型，你会发现 `int[]`、`String[]` 等数组类型并不在其中。这意味着在 Java 中，任何数组都是引用类型：

```java
int[] a = new int[5];
```

变量 `a` 本身只占用 64 位，仅用来保存数组在堆中的首地址；`new int[5]` 才是真正跑到堆内存中开辟 5 个连续整数空间的操作。

由此带来一个非常关键的概念：**对象的迷失与垃圾回收**。

```text
阶段一：变量 a 唯一记录了数组地址
+--------+ 0x9000      +-----------------------------+
| a: •   | ----------> | int[5] 堆数组对象            |
+--------+             +-----------------------------+

阶段二：执行 a = null; （丢弃藏宝图）
+--------+             +-----------------------------+
| a:null |   (断开)    | int[5] 孤儿对象（无法再被访问）|
+--------+             +-----------------------------+
```
读图说明：引用变量重赋值导致原对象失去所有引用路径，成为不可达的内存孤儿，后续会被垃圾回收器自动回收。

如果变量 `a` 是你记录该数组内存地址的唯一途径，一旦你执行了 `a = null;` 或者将 `a` 指向了另一个数组，原本那个数组在内存中虽然还活着，但程序却再也无法顺着地址找到它了。

这就像你把宝藏埋在了海象田里，却亲手把唯一的藏宝图给烧掉了。在程序世界里，没有任何引用指向的对象被称为“不可达对象”。Java 的后台垃圾回收器（Garbage Collector）会自动搜寻并回收这些失去引用的内存垃圾，释放宝贵的硬件资源。

### 构建真正的递归列表：IntList 的设计与进化

搞清了引用类型和内存模型，我们终于拥有了构建无界列表的全部理论武器。

现在我们在 IntelliJ 里新建一个类，起名为 `IntList`。为了聚焦核心机制，我们先只让它存储整数：

```java
public class IntList {
    public int first;
    public IntList rest;
}
```

乍一看，这个类简陋得不可思议：只有两个实例变量，一个是用来存放当前节点数值的整数 `first`；另一个是用来指向下一个 `IntList` 对象的引用 `rest`。

很多同学第一眼看到这里都会犯嘀咕：“一个类内部怎么能包含指向自己同类型的引用？这怎么可能算是一个列表？”

答案是：**这正是链式数据结构与递归的核心魅力所在**。每一个节点只关心两件事：我手里握着的值（`first`），以及我身后剩下的那串列表在哪里（`rest`）。

#### 正向手动拼装的别扭与痛点

如果不加构造函数，我们该如何用这个类搭建一个包含 5、10、15 三个数字的列表？

```java
IntList L = new IntList();
L.first = 5;
L.rest = new IntList();
L.rest.first = 10;
L.rest.rest = new IntList();
L.rest.rest.first = 15;
L.rest.rest.rest = null;
```

这段代码虽然在内存中能跑通，但写起来简直是折磨。试想如果要构建一个包含 20 个元素的列表，我们难道要一路写到 `L.rest.rest...rest.first` 吗？代码冗长混乱，极易让人抓狂。

#### 引入构造函数与反向构建法

为了让列表的创建更加优雅高效，我们为 `IntList` 提供一个能够接收初始参数的构造函数：

```java
public class IntList {
    public int first;
    public IntList rest;

    public IntList(int f, IntList r) {
        this.first = f;
        this.rest = r;
    }
}
```

有了这个构造函数，我们就可以采用一种极其聪明的策略来构建列表——**反向构建（Backward Construction）**：

```java
IntList L = new IntList(15, null);
L = new IntList(10, L);
L = new IntList(5, L);
```

这段代码只有短短三行，却构建出了与刚才完全相同的列表。我们来仔细追踪它的内存步骤：

```text
步骤一：L = new IntList(15, null);
+--------+      +---------------+
| L: •   | ---> | 15 |  null    |
+--------+      +---------------+

步骤二：L = new IntList(10, L);
                +---------------+      +---------------+
新节点:         | 10 |    •     | ---> | 15 |  null    |
                +---------------+      +---------------+
                  ^
                  |
+--------+        | （等号赋值将新节点地址写入 L）
| L: •   | --------
+--------+

步骤三：L = new IntList(5, L);
+--------+      +---------------+      +---------------+      +---------------+
| L: •   | ---> |  5 |    •     | ---> | 10 |    •     | ---> | 15 |  null    |
+--------+      +---------------+      +---------------+      +---------------+
```
读图说明：反向构建通过先求值右侧表达式创建携带前序地址的新节点，再重写头指针 `L`，确保链表引用链在动态增长中永不丢失。

这里有一个极为精妙的提问：“当我们执行 `L = new IntList(10, L);` 时，重新给 `L` 赋值，为什么不会丢失原先 `15` 那个节点的内存引用？”

> **提示**：这全赖于 Java 的运算符执行优先级。等号赋值语句总是**先计算右侧表达式的值**。
> 当虚拟机执行右边的 `new IntList(10, L)` 时，新节点的构造函数已经抢先一步把旧 `L` 所保存的内存地址（即 15 节点的地址）作为参数传入，并牢牢保存在新节点的 `rest` 变量中了。直到新节点完整构建完毕、返回自身的新内存地址后，等号才开始执行赋值，将新地址写给 `L`。因此整个过程中藏宝图从未丢失，指针链完整无损。

### 列表核心操作的递归与迭代实现

虽然现在的 `IntList` 已经能够无限增长，但如果直接把它交付给用户，用户一定会抱怨它太难用了。在 Python 里想看列表有多长，直接调用 `len(L)` 即可；而在我们刚写的列表上，用户甚至不知道该怎么获取它的长度。

接下来，我们为 `IntList` 装备两个核心方法：求长度的 `size` 和按索引取值的 `get`。

#### 计算列表长度：size 方法

为了锻炼大家的算法内功，我们先用**递归**的方式来实现 `size()`。

写递归函数需要牢记两个基本构件：
1. **基准情况（Base Case）**：什么样的列表最小、最单纯，我们一眼就能报出它的大小？
2. **递归调用（Recursive Step）**：如何将大问题拆解为包含自身的更小规模子问题？

对于一个链表节点来说，最简单的情况莫过于它的身后已经没有后续节点了，即 `this.rest == null`。此时这个列表只有孤零零的当前节点，大小显然是 1。

如果身后还有节点呢？那么当前列表的总长度，必然等于当前这 1 个节点，加上身后剩余那串子列表的长度。而身后那串子列表本身也是一个合法的 `IntList`，它天然也拥有 `size()` 方法！

```java
public int size() {
    if (this.rest == null) {
        return 1;
    }
    return 1 + this.rest.size();
}
```

> **定义**：信任递归（Leap of Faith）：写递归时不要在脑海里无休止地展开调用栈。只要基准条件正确，且每一次调用都在向基准条件缩小规模，我们就可以全心信任子节点的递归调用能够正确返回它自身的大小。

我们以包含 `5 -> 10 -> 15` 的列表为例，看看这个递归调用的执行链条：
1. 头节点 5 接收到 `size()` 调用。它的 `rest` 不是 `null`，于是它向身后的节点 10 询问：`rest.size()` 是多少？
2. 节点 10 接收到调用。它的 `rest` 也不是 `null`，于是它继续向身后的节点 15 询问：`rest.size()` 是多少？
3. 节点 15 接收到调用。它的 `rest == null`，触发基准条件，节点 15 立即向上汇报：我的大小是 1；
4. 节点 10 收到回报的 1，加上自己这 1 个单位，算出以自己为首的列表大小为 2，并向上汇报；
5. 节点 5 收到回报的 2，加上自己这 1 个单位，最终得出全局大小为 3。

递归写法行云流水、极为凝练。但为了拓宽思路，我们再来看一种更符合过程式直觉的解法——**迭代（Iteration）版本**。

我们不用递归栈，而是声明一个移动的指针变量 `p`，让它像我们的食指一样，沿着链表从头一路点数到末尾：

```java
public int iterativeSize() {
    IntList p = this;
    int totalSize = 0;
    while (p != null) {
        totalSize++;
        p = p.rest;
    }
    return totalSize;
}
```

在这里，`IntList p = this;` 将指针初始化为当前节点对象（类似于 Python 中的 `self`）。只要 `p` 不为 `null`，说明当前位置确实存在一个真实节点，计数器 `totalSize` 自增 1，然后执行 `p = p.rest;` 将指针向后拨动一位。当循环走到链表末尾的 `null` 时终止，返回累加的总长度。

#### 索引查找：get 方法

今天我们要实现的最后一个功能是 `get(int i)`：传入一个非负整数索引 `i`，返回列表中第 `i` 个节点所存储的数值（索引从 0 开始计数，第 0 项即为头节点的数据）。

这里我们同样用精妙的递归逻辑来实现。我们可以把列表中的每一项拟人化为排成一纵队的人：

1. **基准情况**：如果要找身后的第 0 个人（`i == 0`），那不就是我自己手里拿的牌子吗？直接返回 `this.first`；
2. **递归思考**：如果有人跑来问我：“请把排在你身后第 5 位的那个人手里的数字告诉我”，我该怎么做？
   我不需要亲自往后跑 5 步。我只需要转过身，对紧挨着我身后的伙伴（`this.rest`）说：“请把你身后第 4 位的那个人找出来给我。”
   目标在我身后第 5 位，必然就在我身后伙伴的身后第 4 位！

顺着这个逻辑推演，找我身后的第 $i$ 项，等价于找身后伙伴身后的第 $i - 1$ 项：

```java
public int get(int i) {
    if (i == 0) {
        return this.first;
    }
    return this.rest.get(i - 1);
}
```

我们来做一次具体的边界检验：
假设列表内容为 `5 -> 10 -> 15`，调用 `L.get(2)`：
- 节点 5 收到 `get(2)`，`i != 0`，于是向身后节点 10 发起调用 `rest.get(1)`；
- 节点 10 收到 `get(1)`，`i != 0`，于是向身后节点 15 发起调用 `rest.get(0)`；
- 节点 15 收到 `get(0)`，命中基准条件 `i == 0`，直接返回自身的值 `15`；
- 结果逐层回传，最终返回 `15`，完全符合 0 基索引的定义。

通过解开海象之谜与等号黄金法则，我们洞悉了基本类型与引用类型在内存层面的深层分水岭；以此为地基，我们凭借简单的 `first` 与 `rest` 两个字段，成功构建出了能够自由动态生长、支持递归与迭代操作的完整链式列表。这是我们数据结构进阶之路上的第一座里程碑。
