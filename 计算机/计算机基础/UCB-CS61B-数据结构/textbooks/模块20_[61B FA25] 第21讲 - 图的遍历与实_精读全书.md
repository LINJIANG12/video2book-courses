### 图接口设计：API 契约与客户端视角

在动手写任何底层代码之前，必须先想清楚一件更高级别的事：图的接口（API）应该包含什么。

回忆一下我们在之前课程中接触过的各种抽象数据类型（ADT）。集合（Set）允许调用 `add`、`contains` 和 `remove`；并查集（Disjoint Sets）只暴露出 `connect` 和 `isConnected`；优先队列（Priority Queue）提供了 `add`、`getMin` 和 `removeMin`。接口就像是我们给使用者的一辆新车：这辆车只能前进、后退、左转或右转。接口定义了方法，直接决定了使用者能对这个对象做什么，更决定了程序员思考和解决问题的方式。

对于图这种复杂结构，究竟应该暴露出哪些操作？

#### 顶点表示的极简约束

在自由设计图之前，我们先定下一个极为关键的极简规则：**图的顶点内部只存储整数**。

如果在实际场景中，我们想用图来建模现实世界的地图，顶点代表的是达拉斯（Dallas）、休斯顿（Houston）或奥斯汀（Austin）等城市名称，该怎么办？
做法是各司其职：图的核心结构只负责管理编号为 $0, 1, 2, \dots, V-1$ 的整数节点；至于城市名与数字编号的对应关系，我们在图的外部通过一个数组 `String[] names` 或哈希映射 `Map<String, Integer>` 来额外记录。

> **设计原则**：保持图核心数据结构的精炼与纯粹。顶点统一使用自增的连续非负整数，将业务对象的泛型映射剥离到图外部处理。

```text
[ 业务对象与图顶点的解耦映射 ]

  城市名称 (业务层)         整数索引 (图核心层)          图拓扑关系 (边)
 ┌───────────────┐        ┌─────────────────┐        ┌─────────────┐
 │ 0: "Austin"   │ ──映射──> │  顶点 0         │ ───边───> │  顶点 1     │
 │ 1: "Dallas"   │        │  顶点 1         │          └─────────────┘
 │ 2: "Houston"  │        │  顶点 2         │
 └───────────────┘        └─────────────────┘
```
*外部建立映射表记录业务名称与整数顶点的对应关系，图内部仅操作连续整数索引*

#### 普林斯顿 Graph API 的减法哲学

我们今天实现的图接口，主要参考了普林斯顿大学 Robert Sedgewick 与 Kevin Wayne 的经典算法教材。这套 API 做出了非常坚决的“功能减法”，仅包含以下五个核心方法：

```java
public class Graph {
    public Graph(int V);               // 创建一个包含 V 个顶点、0 条边的空图
    public void addEdge(int v, int w);  // 在顶点 v 和 w 之间添加一条边
    public Iterable<Integer> adj(int v);// 返回与顶点 v 相邻的所有顶点集合
    public int V();                     // 返回图中的顶点总数
    public int E();                     // 返回图中的边总数
}
```

这套 API 定下了几条非常严格的限制：
1. **顶点数量必须预先固定**：在调用构造函数 `Graph(int V)` 时就必须明确指定顶点数 $V$。整套 API 不支持后续动态添加新顶点；
2. **仅支持无权图**：边只是纯粹的连接关系，无法在边上附带距离、费用等权重数值；
3. **极简的方法集合**：它甚至没有提供 `degree(int v)`（查询某个顶点的度数）方法，也没有内置打印图的方法。

#### 客户端适配与“原始人与僧侣”隐喻

这种做减法的 API 会带来什么后果？

这里有一个贴切的比喻：我们作为图 API 的设计者，就像是制定戒律的“僧侣”；而调用图 API 的开发者就像是接受规则的“原始人”。僧侣只给了原始人 `addEdge` 和 `adj` 这几样工具，原始人如果想做别的事，就必须自己在客户端编写代码来实现。

例如，客户端需要知道顶点 $v$ 连接了多少条边（即顶点的度数），但由于 `Graph` 类没有内置 `degree` 方法，使用者只能自己写一个工具方法：通过遍历 `adj(v)` 返回的可迭代列表，逐个累加计数。

```java
public static int degree(Graph G, int v) {
    int degree = 0;
    for (int w : G.adj(v)) {
        degree++;
    }
    return degree;
}
```

再比如，客户端希望将整张图的所有连接关系完整打印出来。因为图本身没有 `print()` 方法，使用者就必须在外部用双重循环自己遍历：

```java
public static void print(Graph G) {
    for (int v = 0; v < G.V(); v++) {
        for (int w : G.adj(v)) {
            System.out.println(v + "-" + w);
        }
    }
}
```

> **提示**：接口设计的本质是权衡。提供更小、更正交的基础操作，可以让数据结构本身的实现与维护极其轻量；而代价是客户端必须承担起组合基础操作以完成特定需求的职责。

#### 算法解耦与智者模式

普林斯顿教材中一个极其精妙的面向对象设计思想，是**将图的数据表示与图的处理算法彻底解耦**。

很多初学者容易把所有图算法（判断连通性、找路径、找环等）全塞进 `Graph` 类中，导致图类变成一个臃肿不堪的上帝类（God Class）。而在这里，`Graph` 类的唯一职责就是表示图的拓扑连接。

针对路径查找问题，我们独立创建一个专门的类——`Paths`。这个类就像是一位精通图论的“智者”：

```text
[ 智者模式 (Paths) 与图结构 (Graph) 的解耦交互 ]

   客户端代码                        智者对象 (Paths)                      图数据结构 (Graph)
  ┌──────────┐                     ┌────────────────┐                  ┌────────────────┐
  │ 调用构造  │ ── new Paths(G, s) ─> │ 构造时盘腿沉思:  │ ── G.adj(v) ────> │ 提供邻接顶点列表 │
  │          │                     │ 执行一次 DFS    │ <── Iterable ─── │                │
  │          │                     │ 填好 marked[]  │                  └────────────────┘
  │          │                     │ 填好 edgeTo[]  │
  │          │                     └────────────────┘
  │ 提问路径  │ ── hasPathTo(v) ───> │ 查 marked[v]   │ 
  │          │ <── 返回 true/false ─ │                │
  │ 获取路径  │ ── pathTo(v) ──────> │ 倒推 edgeTo[]  │
  │          │ <── 返回路径迭代器 ── │ (顺着面包屑回溯) │
  └──────────┘                     └────────────────┘
```
*客户端将图与起点交给智者对象，智者在构造时预计算所有可达路径，随后高效响应各项查询*

当我们调用 `Paths(Graph G, int s)` 实例化智者时，传入图对象 $G$ 和起点 $s$。智者在构造函数执行期间便“盘腿沉思”——完整运行一次深度优先搜索（DFS），计算出从源点 $s$ 到图中所有可达顶点的路径，并将信息沉淀在内部两个核心数组中：
- `boolean[] marked`：记录哪些顶点已被访问过（即可达）；
- `int[] edgeTo`：记录到达每个顶点的最后一个前驱顶点（如同沿途留下的面包屑）。

当智者计算完毕后，客户端就可以直接向他提问：
1. `hasPathTo(int v)`：从 $s$ 到 $v$ 是否有通路？智者无需重新搜索，直接查看 `marked[v]` 即可在 $O(1)$ 时间内回答 `true` 或 `false`；
2. `pathTo(int v)`：从 $s$ 到 $v$ 的完整路径是什么？智者只需从 $v$ 开始，顺着 `edgeTo[v]` 像翻阅面包屑记录一样一路反向倒推回起点 $s$，就能重构出完整路径。

最值得玩味的一点在于：智者完成整套深度优先搜索，与图对象 $G$ 交互的唯一手段，就是调用 `G.adj(v)`。只要图能提供某个顶点的所有相邻节点，图算法就能完整运转。

### 底层数据结构实现：从邻接矩阵到邻接表

明确了接口行为后，进入第二步：在 Java 的内存中，我们究竟使用哪些实例变量来存储图中的顶点和边？

就像树可以用链表节点表示，也可以用扁平数组表示一样，同一张图在内存中也有多种不同的物理表示形态。

#### 邻接矩阵与稀疏图困境

第一种经典思路是**邻接矩阵（Adjacency Matrix）**。它是一个大小为 $V \times V$ 的二维布尔表格（在代码中通常是 `boolean[][] adj` 或 `int[][] adj`），行与列分别代表顶点编号：

```text
[ 邻接矩阵表示法示例 (3个顶点的有向图) ]

   有向拓扑图                         邻接矩阵二维数组 (0/1)
   
     (0) ───> (1)                          列 (终点)
      │        │                       0   1   2
      │        │                   ┌─────────────┐
      ▼        ▼               0   │   0   1   1 │
     (2) <─────┘           行  1   │   0   0   1 │
                         (起点) 2   │   0   0   0 │
                                   └─────────────┘
```
*矩阵的第 x 行第 y 列为 1 表示存在从 x 到 y 的边，为 0 表示无边*

如果图是无向图，矩阵呈现对角线对称：$x$ 与 $y$ 相连意味着 $adj[x][y]$ 和 $adj[y][x]$ 同时被置为 1。

邻接矩阵非常直观，查询任意两点间是否有边只需一次矩阵寻址。但它有一个极其致命的缺陷——**空间浪费**。

现实世界中的绝大多数图都是**稀疏图（Sparse Graph）**。以全班同学的社交关系图为例：假设班级里有 700 名学生，每个人大概只和 5 到 20 个人是朋友。即使是社交达人，也不可能与全班 700 个人都熟识。
如果将每个人作为一个顶点建立邻接矩阵，矩阵的总容量是 $700 \times 700 = 490,000$ 个单元格。然而这近 50 万个格子中，绝大多数都填着数值 0。为了记录稀疏的几千条好友关系，不得不开辟一个充斥着零的巨大内存空间，这是对内存极其低效的挥霍。

#### 邻接表的高效紧凑表达

为了克服邻接矩阵的臃肿，第二种也是工程中最通用的方案是**邻接表（Adjacency Lists）**。

在邻接表中，我们不再维护巨大的二维矩形网格，而是为每个顶点维护一个独立的列表，列表中只存放与该顶点真正相邻的邻居：

```text
[ 邻接表表示法示例 ]

   有向拓扑图                         顶点列表数组 (只存有效连接)
   
     (0) ───> (1)                   索引 (起点)     邻居列表
      │        │                   ┌─────┐        ┌─────────┐
      │        │                   │ [0] │ ────>  │ 1 ──> 2 │
      ▼        ▼                   ├─────┤        ├─────────┤
     (2) <─────┘                   │ [1] │ ────>  │ 2       │
                                   ├─────┤        ├─────────┤
                                   │ [2] │ ────>  │ (空)    │
                                   └─────┘        └─────────┘
```
*每个顶点对应一个只包含其实际出边邻居的紧凑列表，不存储任何无效的零*

在 Java 中，这通常由一个泛型列表数组实现（例如 `List<Integer>[] adj` 或普林斯顿教材中的背包数组 `Bag<Integer>[] adj`）：
- 想查询 10 号顶点的所有朋友？直接访问数组的第 10 项 `adj[10]`，遍历该列表即可；
- 顶点没有朋友（如上图中的顶点 2），其对应列表就是空的，完全不需要耗费多余空间去记录那些不存在的边。

对于稀疏图而言，邻接表既紧凑又直观，是后续绝大部分算法实现的首选结构。

### 双变量渐进分析：为什么是 V 加 E

在确定了邻接表这种数据结构后，我们必须回答一个核心的效率问题：遍历整张图、执行深度优先搜索到底需要耗费多长时间？

在图算法的复杂度分析中，许多人初学时会对类似 $O(V + E)$ 的表达式感到困惑。为什么这里必须同时出现两个变量？为什么中间用加号而不是乘号？

#### 图增长的双重自由度

回忆之前分析二分查找或排序算法时，问题规模只有一个变量——数组长度 $N$。数组变大，就只有“元素个数增加”这一种可能。

但图完全不同，图拥有**两个独立的自由度**，可以通过两种完全不同的方式变大：
1. **顶点数 $V$ 增加，边数 $E$ 保持不变**：想象班级人数从 100 人激增到 10,000 人，但所有新生都互不认识，没有任何人交到朋友。此时图在顶点维度被极度拉伸，而边数 $E$ 是一个恒定常数；
2. **边数 $E$ 增加，顶点数 $V$ 保持不变**：班级人数始终固定为 100 人，但随着学期推进，大家疯狂交朋友，边数从几十条暴增到几千条。此时图在连接密度维度增长，而顶点数 $V$ 是一个恒定常数；
3. **顶点数 $V$ 与边数 $E$ 同时不同步地增长**。

边数 $E$ 的取值范围极广：从完全没有边的 $0$，到人人互相连通的完全图 $V(V - 1) / 2 \approx V^2$。

如果我们图省事，只用单一变量断言算法最坏情况是 $O(V^2)$，那就只描述了图完全连满的那一种极端稠密情况，抹杀了图在稀疏常态下的真实性能。为了准确刻画图在各种拓扑形态下的运行效率，渐进分析必须同时引入 $V$ 和 $E$ 两个变量。

```text
[ 图增长的双重维度与复杂度主导性 ]

    边数 E (连接密度)
      ▲
      │                              稠密极端: E ≈ V²
      │                             (E 占主导，表现为 O(V²))
      │                                   ▲
      │                                  ╱
      │                                 ╱
      │       典型稀疏图: E 与 V 线性相当
      │       (两者同阶，表现为 O(V + E))
      │          ▲
      │         ╱
      │        ╱
      │  稀疏极端: E 极少甚至为 0
      │  (V 占主导，表现为 O(V))
      └────────────────────────────────────────> 顶点数 V (规模)
```
*图具备顶点规模与连接密度两个独立增长维度，复杂度必须由双变量共同描述*

#### 遍历与打印的代价推导

现在，我们通过代码的成本模型来严密推导前面提到的 `print(Graph G)` 方法的运行时间：

```java
public static void print(Graph G) {
    for (int v = 0; v < G.V(); v++) {       // 外层循环：执行 V 次
        for (int w : G.adj(v)) {            // 内层循环：遍历 v 的邻接列表
            System.out.println(v + "-" + w); // 打印语句：每条边打印一次（无向图为两次）
        }
    }
}
```

我们来算一算每一行代码的执行频次：
- 外层 `for` 循环：索引 $v$ 从 $0$ 遍历到 $V-1$，这层循环固定执行 $V$ 次；
- 内层 `for` 循环与打印语句：
  - 某个单独顶点的邻接列表长度我们并不确定——有的节点是“万人迷”，朋友很多；有的节点是“单身狗”，列表为空；
  - 但是，**把图中所有顶点的邻接列表长度全部加起来，其总和必然等于出边的总数**。在有向图中总和恰好是 $E$，在无向图中每条边在两个顶点的列表中各出现一次，总和为 $2E$。

因此，外层循环贡献了 $V$ 的开销，内层的所有迭代与打印操作在全图累计贡献了 $E$（或 $2E$）的开销。将两部分加在一起，总操作次数与 $V + E$ 成正比。

> **结论**：在邻接表表示下，全图遍历与边打印的渐进时间复杂度为 $\Theta(V + E)$。在数量级概念上，它等价于 $\Theta(\max(V, E))$。

为什么绝对不是 $V \times E$？
因为 $V \times E$ 意味着每一个顶点都需要将全图所有的 $E$ 条边都扫描一遍；而邻接表的优势恰恰在于每个顶点只遍历属于自己的那部分邻居边，所有内层遍历的总工作量被分摊在整张图上，累计刚好是 $E$。

#### 遍历算法的复杂度对照

同样的双变量推导逻辑，完全适用于深度优先搜索（DFS）和路径查找算法。

在运行基于邻接表的深度优先搜索时：
- 我们必须对每个顶点进行一次初始化（创建并清空大小为 $V$ 的 `marked` 数组与 `edgeTo` 数组），这需要花费 $V$ 的时间；
- 递归搜索过程中，每个连通节点恰好被标记访问一次；
- 每当访问一个顶点，算法会扫描其所有的出边。全图所有顶点的扫描次数累加起来，每条边最多被考察两次（在无向图中正反各一次）。

因此，DFS 的总时间复杂度同样是 $O(V + E)$。若图是连通的，则为严格的 $\Theta(V + E)$。
空间复杂度方面，算法需要维护 `marked` 数组、`edgeTo` 数组以及递归调用栈。递归栈的深度在最坏情况下（如一条直线的单链图）至多为 $V$，因此空间复杂度为 $O(V)$。

下表直观对比了在不同底层实现下，基础图操作与遍历算法的复杂度差异：

| 算法 / 操作 | 邻接表实现（推荐） | 邻接矩阵实现（低效） | 核心瓶颈根因 |
| :--- | :--- | :--- | :--- |
| **空间开销** | $\Theta(V + E)$ | $\Theta(V^2)$ | 邻接矩阵必须分配固定 $V \times V$ 空间 |
| **添加边 `addEdge`** | $\Theta(1)$ | $\Theta(1)$ | 数组寻址或在链表头部插入 |
| **查询两点是否相邻** | $O(\text{degree}(v))$ | $\Theta(1)$ | 邻接表需遍历列表，矩阵直接寻址 |
| **遍历全图所有边 `print`** | $\Theta(V + E)$ | $\Theta(V^2)$ | 邻接矩阵必须扫完整张二维网格 |
| **深度优先搜索 (DFS)** | $O(V + E)$ | $\Theta(V^2)$ | 邻接矩阵查找一个顶点的邻居需扫一行（$V$ 次） |
| **广度优先搜索 (BFS)** | $O(V + E)$ | $\Theta(V^2)$ | 邻接矩阵同上，每层找邻居均需消耗 $V$ 次扫描 |

由此可见，数据结构的选择并非无关紧要的琐事。对于现实中极为常见的稀疏图，选择邻接矩阵会让原本只需线性时间 $O(V + E)$ 的遍历算法直接劣化为 $O(V^2)$。

### 广度优先搜索：距离层序推进与队列不变量

掌握了图的表示与开销分析后，我们进入今天的第二个重头戏：**广度优先搜索（Breadth-First Search, BFS）**。

在上一讲中，深度优先搜索（DFS）展现出一种“不撞南墙不回头”的探索风格：顺着一条路一直往深处钻，直到无路可走再回溯。
而广度优先搜索完全相反，它的目标是**按照离起点的距离（边数/跳数），由近及远、一圈一圈地向外辐射扩展**。

#### 层序扩展直觉与队列机制

BFS 的直观体验非常类似于树的层序遍历（Level-Order Traversal）。

从源点 $0$ 开始：
1. 第一轮：首先访问所有与源点直接相邻、距离为 1 跳的顶点；
2. 第二轮：接着访问所有与源点距离为 2 跳的顶点；
3. 第三轮：再访问所有与源点距离为 3 跳的顶点；
4. 依此类推，直到图中最深处、距离最远的边缘顶点被访问完毕。

为了在代码中强制实现这种“先近后远”的处理次序，我们必须借助一个至关重要的数据结构——**先进先出队列（Queue，FIFO）**。

```text
[ 广度优先搜索的队列处理机制 ]

      取出当前近距离节点 (队头)                       新发现的较远邻居进入队尾排队
     ┌──────────────────────┐                     ┌────────────────────────┐
<─── │ 出队处理: 标记并记录路径 │                     │ 入队: 距离更远的邻居节点 │ <───
     └──────────────────────┘                     └────────────────────────┘
          ▲                                                    ▲
          │       ┌───────┬───────┬─────────┬─────────┐        │
          └────── │ 队头  │  ...  │   ...   │  队尾   │ ───────┘
                  └───────┴───────┴─────────┴─────────┘
                  距离 = k                 距离 = k + 1
```
*队头始终维持着离起点更近的当前层节点，新扩展出的下一层较远邻居被推入队尾排队*

BFS 的通用执行规程非常简洁：
1. 将起点放入队列，并标记起点；
2. 当队列不为空时，从队头弹出一个顶点 $v$；
3. 检查 $v$ 的所有相邻顶点：如果邻居 $w$ 尚未被标记，则将其标记、记录路径来源 `edgeTo[w] = v`，并将 $w$ 加入队尾；
4. 重复上述过程，直至队列清空。

#### 队尾排队与最近优先证明

为什么这样一个简单的先进先出队列，就能严丝合缝地保证“距离近的节点必然比距离远的节点先被处理”？

这是本节课最精彩的逻辑转折点。我们通过一个具体的追踪过程来观察它的内部机制：

假设起点是 0，处理完 0 后，其距离为 1 的邻居（例如顶点 1）入队。
接着 1 号出队，它发现了与起点距离为 2 的未标记邻居 2 和 4。此时队列中的内容为 `[2, 4]`，它们与起点的距离均为 2。

关键时刻来了：
接下来我们从队头取出顶点 2 进行处理。顶点 2 发现了它的未访问邻居——顶点 5。
请注意，顶点 5 到起点的距离是 3（路径为 $0 \to 1 \to 2 \to 5$）。
根据队列规则，新发现的 5 号顶点**必须排到队列的最末尾**！

此时的队列状态是：
`[4 (距离2)] -> [5 (距离3)]`

5 号顶点虽然已经被发现了，但它不能插队，它必须老老实实在队尾等候。
为什么？因为队头还躺着一个顶点 4，而顶点 4 距离起点的距离只有 2！
队列严格的先进先出性质，强迫算法必须先把所有像 4 号这样距离为 2 的节点全部出队并处理完毕，才有资格轮到排在队尾的、距离为 3 的 5 号节点。

> **核心机制**：如果你离起点较近，你就在队头被优先取出；你在扩展邻居时，你的邻居离起点更远，它们只能被排到队尾等待。这从根本上杜绝了跨层越级访问的可能。

#### 核心不变量与严密推导

为了在理论上彻底确信 BFS 的正确性，我们可以提炼出一个极其优美且强大的**队列核心不变量（Queue Invariant）**：

> **关键不变量**：在广度优先搜索运行的任意时刻，队列中包含的所有顶点到源点的最短距离，要么全部等于某个整数 $k$，要么由连续的距离为 $k$ 的顶点和距离为 $k+1$ 的顶点两部分构成。队列中任意两个元素的距离之差绝对不会超过 1。

我们可以通过状态转移来严密验证这一不变量的成立：

```text
[ 队列距离不变量的状态转移演进 ]

状态 A: 队列中全是同一距离的节点
       队头 ──> [ k,  k,  k,  k ] <── 队尾

状态 B: 队头处理 k，新入队的邻居距离必定为 (k+1)
       队头 ──> [ k,  k,  k | k+1,  k+1 ] <── 队尾
                └─ 正在处理 ─┘  └── 新入队 ──┘

状态 C: 所有距离为 k 的节点全部处理出队，队列全变为 (k+1)
       队头 ──> [ k+1,  k+1,  k+1 ] <── 队尾

状态 D: 队头首次处理 (k+1)，此时新入队的邻居距离首次出现 (k+2)
       队头 ──> [ k+1,  k+1 | k+2 ] <── 队尾
```
*推导图解：只有当所有距离为 k 的顶点出队完毕后，距离为 k+2 的顶点才可能首次入队，极差永远保持在 1 以内*

推导逻辑如下：
1. 初始状态下，队列中只有源点 $s$，距离为 0，不变量显然成立；
2. 假设当前队列处于包含距离 $k$ 和 $k+1$ 的状态。当我们从队头取出一个顶点时，由于取出的一定是当前距离最近的顶点，其距离必然为 $k$；
3. 这个距离为 $k$ 的顶点向外探索未访问的邻居。由于它是从一步之遥跨过去的，这些邻居到源点的距离必然只能是 $k+1$（它们不可能具有比 $k+1$ 更短的路径，否则在更早前就会被访问；也不可能一步跨出 $k+2$）；
4. 这些新发现的距离为 $k+1$ 的邻居被依次添加到队尾。此时队列内部依然只包含 $k$ 和 $k+1$；
5. 随着距离为 $k$ 的顶点被逐个处理完毕，队列中的元素会最终全部变成 $k+1$；
6. 队列何时才会首次迎来距离为 $k+2$ 的节点？**唯一的可能，就是队列中所有距离为 $k$ 的顶点已经全部出队完毕，队头迎来了第一个距离为 $k+1$ 的顶点**。只有在展开这个距离为 $k+1$ 的顶点时，距离为 $k+2$ 的节点才会被首次推入队尾。

这证明了队列内部的距离跨度永远被牢牢锁定在单调的递增窗口中。算法绝不可能在尚未处理完距离为 3 的节点时，就提前跑去处理距离为 4 的节点。

#### 面包屑回溯与算法开销

由于 BFS 是严格按照离源点的距离单调向外推进的，当它首次接触到任意一个未标记的顶点 $w$ 时，所经过的那条路径必然是**从源点到该顶点的边数最少路径（最短路径）**。

我们在遍历过程中记录的 `edgeTo` 数组，完整保留了这一最短路径生成树的拓扑关系：

```java
public class BreadthFirstPaths {
    private boolean[] marked;
    private int[] edgeTo;
    private final int s;

    public BreadthFirstPaths(Graph G, int s) {
        this.s = s;
        marked = new boolean[G.V()];
        edgeTo = new int[G.V()];
        bfs(G, s);
    }

    private void bfs(Graph G, int s) {
        Queue<Integer> q = new LinkedList<>();
        marked[s] = true;
        q.add(s);

        while (!q.isEmpty()) {
            int v = q.remove();
            for (int w : G.adj(v)) {
                if (!marked[w]) {
                    edgeTo[w] = v;    // 留下回到前驱的面包屑
                    marked[w] = true;  // 立即标记，防止后续重复入队
                    q.add(w);
                }
            }
        }
    }

    public boolean hasPathTo(int v) {
        return marked[v];
    }

    public Iterable<Integer> pathTo(int v) {
        if (!hasPathTo(v)) return null;
        List<Integer> path = new ArrayList<>();
        for (int x = v; x != s; x = edgeTo[x]) {
            path.add(x);
        }
        path.add(s);
        Collections.reverse(path);
        return path;
    }
}
```

在邻接表实现下，广度优先搜索的性能表现与 DFS 完全一致：
- **时间复杂度**：每个可达顶点入队并出队各一次，每个顶点的所有出边被检查一次，全图总计耗时 $O(V + E)$；
- **空间复杂度**：队列中容纳的顶点数至多为 $V$，配合大小为 $V$ 的辅助标记数组，总空间消耗为 $O(V)$。

### 本讲提到的题目

在今天的课堂讲授中，穿插提出了两道针对性极强的核心设计与复杂度分析题目：

#### 题目一：仅依赖普林斯顿 Graph API 编写图打印方法

**题干**：
已知普林斯顿 `Graph` 类仅对外公开了五个方法：`Graph(int V)`、`void addEdge(int v, int w)`、`Iterable<Integer> adj(int v)`、`int V()` 和 `int E()`。请在不修改 `Graph` 类源码的前提下，编写一个静态方法 `print(Graph G)`，将图中所有的边按照形如 `v-w` 的格式逐行打印出来。

**解析**：
由于 API 没有提供直接遍历全图所有边的数据结构，客户端必须自行利用顶点的整数索引特性展开迭代：
1. 调用 `G.V()` 获取顶点总数 $V$，外层循环令变量 $v$ 从 $0$ 遍历至 $V-1$；
2. 针对每一个顶点 $v$，调用 `G.adj(v)` 获取与其相邻的顶点集合；
3. 内层循环遍历该邻接集合中的每一个邻居 $w$，输出 `v + "-" + w`。

**完整参考实现**：
```java
public static void print(Graph G) {
    for (int v = 0; v < G.V(); v++) {
        for (int w : G.adj(v)) {
            System.out.println(v + "-" + w);
        }
    }
}
```

> **注意**：在无向图中，每条边会被存储在两个端点的邻接列表中各一次，因此上述打印方法会将每条无向边沿正反两个方向分别打印一次（例如先打印 `1-2`，后续会打印 `2-1`），这在语义上完全符合对所有出边连接的完整枚举。

#### 题目二：邻接表下图遍历的双变量时间复杂度判定

**题干**：
针对题目一中编写的 `print(Graph G)` 方法，假设底层采用邻接表实现，图包含 $V$ 个顶点与 $E$ 条边。请问该方法的渐进时间复杂度应如何表示？
- 选项 A：$\Theta(V)$
- 选项 B：$\Theta(E)$
- 选项 C：$\Theta(V \times E)$
- 选项 D：$\Theta(V + E)$

**答案**：选项 D：$\Theta(V + E)$

**解析依据**：
1. **外层循环成本**：外层 `for` 循环从 $0$ 遍历到 $V-1$，无论图中有多少条边，循环体本身的步进与条件判断固定执行 $V$ 次，贡献了 $\Theta(V)$ 的基础开销；
2. **内层循环累计成本**：内层循环遍历每个顶点的邻接列表。尽管不同顶点的列表长短不一，但全图所有顶点的邻接列表长度之和必然等于图中的总出边数（在无向图中为 $2E$，在有向图中为 $E$）。因此，内层循环体内所有语句的全局累计执行次数恰好为 $\Theta(E)$；
3. **整体合并**：两部分开销是顺序累加关系而非笛卡尔乘积关系。当图处于极度稀疏状态（$E = 0$）时，算法依然需要消耗 $\Theta(V)$ 时间扫描所有空列表；当图处于极度稠密状态时，$E$ 增长并占据主导。综合反映图在不同生长维度下的真实性能，渐进复杂度为 $\Theta(V + E)$（也可写作 $\Theta(\max(V, E))$）。
