#### 旧习惯的幻觉与现实责任

在之前的编程课程里，大家很可能已经养成了一种习惯依赖：写完一段代码，把它提交到 OKPy 或者自动评分系统（Autograder）里，看系统给你打多少分；或者在 IDE 里面点击运行课程官方骨干代码里早就准备好的测试套件，看它报红还是报绿。一旦测试挂了，就对着自动评分器的报错信息盲猜调试，改完再传。

但现实世界的软件工程根本不是这样的。在工业界中，没有人会提前帮你把测试写好端到你面前，更没有现成的自动评分器。

> **结论**：在真实项目中，代码之所以能稳定运行，唯一的原因是**你自己为它编写了周密的自动化测试**。

从理论上讲，我们很难在数学上绝对证明一段通用程序的绝对正确性。学术界虽然有关于“程序形式化验证（Formal Verification）”的研究，通过形式逻辑系统去证明代码无误，但这并不是主流，工业界也几乎没有被广泛采用的全自动形式化证明工具。

因此，现实工程中的基准方案是：通过程序化的结构去驱动代码，构造一组具有代表性的输入，并严格检验输出是否符合预期。测试不能证明代码中绝对没有 bug，但只要测试用例覆盖得足够扎实，它就能提供极强的工程置信度。

### 选择排序与单元测试框架的演进

为了彻底脱离现成测试的温室，今天我们要写一个全新的算法——**选择排序（Selection Sort）**。我们不仅要自己手写排序逻辑，更要从零开始为它编写完备的自动化测试。

#### 选择排序的基本逻辑

选择排序是所有排序算法中最直观的一种。假设我们有一个未排序的数组，我们的目标是把它按升序（例如英文字符串的字典序）排好。

以一组数据为例，选择排序的执行过程非常直接：
1. 遍历当前剩余未排序的部分，找出其中的**最小值（Smallest Item）**；
2. 将这个最小值与未排序部分的第一个元素进行**位置交换（Swap）**；
3. 将已经归位的元素**置灰锁定**，表示它已经处于最终的正确位置上，后续处理完全不需要再去动它；
4. 对剩余未排序的部分重复上述过程，直到所有元素全部有序。

```text
初始状态:   [ 6 , 1 , 7 , 2 , 3 ]
步骤 1:      找出最小值 1，与起始位置元素 6 交换
            [ 1 | 6 , 7 , 2 , 3 ]  (1 已归位置灰)
步骤 2:      在剩余部分中找出最小值 2，与起始位置元素 6 交换
            [ 1 , 2 | 7 , 6 , 3 ]  (1, 2 已归位置灰)
步骤 3:      在剩余部分中找出最小值 3，与起始位置元素 7 交换
            [ 1 , 2 , 3 | 6 , 7 ]  (1, 2, 3 已归位置灰)
步骤 4:      剩余部分依次归位，排序完成。
```
上述字符流向图展示了选择排序如何通过逐轮寻找最小值并交换，将已排序区间从左向右推进。

这里有一个关键的设计思考：为什么我们找到最小值之后，采用的是“**交换（Swap）**”，而不是直接把它拿出来“插入”到开头？

大家可以想象操作一叠物理纸片。如果手里拿着一叠纸，我把最底下一张抽出来插到最顶上，后面的纸顺势一滑，这很容易。但在计算机内存的连续数组中，物理存储结构是固定的：如果你要把第 5 个位置的元素插到第 0 个位置，你就必须把第 0 到第 4 个位置的所有元素在内存里依次向后平移一位！这种数据搬移非常耗时。而交换（Swap）只需要借助一个临时位置，两两对调，一步操作（$O(1)$ 时间）即可完成。

#### 手写对比的繁琐与单元测试的定义

现在，我们要写一个类 `Sort`，里面有一个对外公开的方法：

```java
public class Sort {
    /** 对字符串数组 x 进行原地升序排序 */
    public static void sort(String[] x) {
        // 暂时留空，稍后实现
    }
}
```

我们要如何测试它？最原始的做法是在一个测试类中写个 `main` 方法：

```java
public class TestSort {
    public static void main(String[] args) {
        String[] input = {"velociraptor", "horse", "koshi", "iridium"};
        String[] expected = {"horse", "iridium", "koshi", "velociraptor"};

        Sort.sort(input);

        for (int i = 0; i < input.length; i++) {
            if (!input[i].equals(expected[i])) {
                System.out.println("Mismatch at index " + i + ", expected: " 
                                   + expected[i] + ", but got: " + input[i]);
                break;
            }
        }
    }
}
```

这种手写 `for` 循环遍历对比的做法虽然可行，但太繁琐了。每次写一个方法都要手工写循环、拼打印字符串，如果数组长度不一致还会发生数组越界，代码冗长且极易写错。

这就引出了**单元测试（Unit Testing）**的概念。

> **定义**：软件程序本质上是由一个个功能明确的“小抽象模块”（如找最小值、交换两项、对局部排序等）拼装而成的。每一个这样独立的抽象单元，就称为一个**单元（Unit）**。**单元测试**，就是通过编写自动化代码，专门验证这些独立的源代码单元是否完全符合其设计契约。

#### 从 JUnit 到 Google Truth

为了把程序员从枯燥的手写比对中解放出来，现代软件工程诞生了许多成熟的单元测试框架。

在 2023 年春季学期之前的 CS61B 中，我们一直使用的是 Java 领域最著名的 `JUnit` 框架底层的断言库，比如 `org.junit.Assert.assertArrayEquals(expected, input);`。

后来，我的一位杰出的研究生助教 Ethan Ordentlich（他现在已经在加州理工学院任教）向我推荐了 Google 开源的断言库 **Truth**（`com.google.common.truth.Truth`）。我们尝试后发现，Truth 的使用体验极其流畅：

```java
import static com.google.common.truth.Truth.assertThat;

// 使用 Google Truth 的断言语法
assertThat(input).isEqualTo(expected);
```

> **提示**：Google Truth 的断言读起来就像标准的自然英语句子（Fluent Assertions）：“Assert that input is equal to expected”。与传统 JUnit 经常容易搞反 `expected` 和 `actual` 参数顺序相比，Truth 不仅语义极度直观，而且在断言失败时打印出的差异对比报告非常清晰，精确指出哪一个索引的元素不匹配，极大地提升了调试体验。

#### 注解机制与测试运行器原理

当我们在 IDE 中运行测试时，我们不希望每次都通过 `main` 方法去打印终端红字，而是希望能看到 IDE 侧边栏里那排令人身心愉悦的绿色对勾（Green Checkmark）。

为此，我们把测试代码改写成带注解的形式：

```java
import org.junit.Test;
import static com.google.common.truth.Truth.assertThat;

public class TestSort {
    @Test
    public void testSort() {
        String[] input = {"velociraptor", "horse", "koshi", "iridium"};
        String[] expected = {"horse", "iridium", "koshi", "velociraptor"};

        Sort.sort(input);

        assertThat(input).isEqualTo(expected);
    }
}
```

注意这里的两个重大变化：
1. 方法前面添加了 `@Test` 注解；
2. 方法签名变成了 `public void testSort()`，**去掉了 `static`**，而且根本没有 `main` 方法！

在 Java 的语法规则里，程序没有 `public static void main(String[] args)` 是绝对无法直接启动运行的。那为什么这个测试类能够直接被 IDE 执行？

> **原理剖析**：背后的真正秘密在于，IDE 或者测试构建工具在幕后运行着一个我们看不见的**测试运行器（Test Runner）**。这个测试运行器自身拥有一个标准的 `main` 方法。当它启动时，会通过 Java 反射机制扫描你的测试类，寻找所有标注了 `@Test` 的方法，然后依次动态调用它们，捕获运行中是否有断言异常抛出，并最终将统计结果汇报给图形界面。

`@Test` 注解本身在 Java 语法层面对代码逻辑没有任何实质修改。打个比方：就像我走进教室，在其中几位同学身上贴了一张红色的便利贴。便利贴本身不会改变你这个人，但随后负责拿着彩带喷罐进来的工作人员，会根据这些便利贴准确找到该向谁喷彩带。`@Test` 就是这样一张贴给测试运行器的提示便利贴。

#### 绿色对勾与持续集成的游戏化体验

把测试融入日常开发，还会带来一个意想不到的心理学奖励：**开发过程的游戏化（Gamification）**。

你在写作业或者做工程时会有明确的目标：每当你设计并攻克一个小模块，点击运行，IDE 就会给出一个漂亮的绿色对勾。集齐所有对勾，你就彻底赢下了这局游戏。

几年前我在朋友的公司全职做软件工程，整个团队采用 Python 栈配合 GitHub CI/CD（持续集成与持续交付系统）。我们在本地编写代码前先写好测试，本地测通后提交 Pull Request 到 GitHub，云端自动化集群就会立即启动运行整套测试用例。当你刷新页面，看到 GitHub PR 上代表各项流水线检查的绿色对勾一个接一个全部亮起，那种工程踏实感是无与伦比的。

### 测试驱动开发（TDD）实战

很多初学编程的同学倾向于采用所谓的“**牛仔式编程（Cowboy Coding）**”：没有任何前期构思与接口设计，抓起键盘就直接写核心业务逻辑。写到几百行之后，整个代码一团乱麻，逻辑缠绕在一起，出了 bug 根本无从查起。

今天我们要实践的是现代软件工程极为推崇的方法论——**测试驱动开发（Test-Driven Development, TDD）**。

```text
+-----------------------+     编写失败测试
| Red (红灯/失败)       | <-----------------------------------+
| 针对未实现功能写测试  |                                     |
+-----------------------+                                     |
           | 运行测试（确认报错红叉）                           |
           v                                                  | 迭代进入
+-----------------------+                                     | 下一功能
| Green (绿灯/通过)     |                                     |
| 编写最简实现让测试通过|                                     |
+-----------------------+                                     |
           | 拿到绿色对勾                                     |
           v                                                  |
+-----------------------+                                     |
| Refactor (重构优化)   | ------------------------------------+
| 消除重复、调整内部架构|
+-----------------------+
```
上面的状态流转图展示了 TDD 经典“红灯 - 绿灯 - 重构”的闭环迭代周期。

TDD 要求我们在写具体实现方法之前，**先写测试代码**。这样做有两个核心好处：
1. **强迫你站在调用者的视角理清设计**：在写测试时，你必须先给出一个具体的输入输出用例，强迫自己明确定义出函数的名称、参数类型、返回值以及预期的行为契约；
2. **验证测试本身的有效性**：在业务逻辑尚未编写（或仅返回 dummy 值）时运行测试，你必须亲眼看到红色的测试失败标记。这证明你的测试是真正具备拦截能力的；如果一个空实现居然跑绿了，那就说明你的测试用例写得毫无意义。

我们将选择排序拆解为三个独立的子任务：
1. `findSmallest`：在字符串数组中寻找最小的元素；
2. `swap`：交换数组中指定两个位置的元素；
3. `sort`：组合上述构件，完成整体排序。

#### 构建第一个构件：寻找最小值

我们先在 `TestSort.java` 中写测试：

```java
@Test
public void testFindSmallest() {
    String[] input = {"velociraptor", "horse", "koshi", "iridium"};
    String expected = "horse";

    String actual = Sort.findSmallest(input);

    assertThat(actual).isEqualTo(expected);
}
```

运行测试，由于 `Sort.findSmallest` 还没有实现（直接返回 `null`），测试立即报错抛出断言异常，出现红叉。这证明测试有效。

现在我们着手编写 `findSmallest` 的逻辑。直觉代码可能会写成这样：

```java
public static String findSmallest(String[] x) {
    String smallest = x[0];
    for (int i = 1; i < x.length; i++) {
        if (x[i] < smallest) { // 编译报错！
            smallest = x[i];
        }
    }
    return smallest;
}
```

当我们尝试用 `<` 运算符去比较两个字符串时，Java 编译器直接拒绝编译！

> **易错点**：Java 与 Python 等动态语言不同，**Java 不支持任何形式的运算符重载（Operator Overloading）**。在 Java 中，`<`、`>`、`<=`、`>=` 这些比较运算符只能用于 `int`、`double`、`char` 等基本数据类型（Primitive Types），绝对不能直接用于对象引用类型（Reference Types）。

那么在 Java 中应该如何比对两个字符串的字典先后顺序？我们通过查阅文档可以得知，Java 的 `String` 类实现了 `Comparable` 接口，提供了 `compareTo` 方法：

> **定义**：`s1.compareTo(s2)` 的行为规范：
> - 若 `s1` 在字典序上小于 `s2`，返回一个**负整数**（$< 0$）；
> - 若 `s1` 与 `s2` 内容相等，返回 **0**；
> - 若 `s1` 在字典序上大于 `s2`，返回一个**正整数**（$> 0$）。

因此，正确的比较逻辑是 `x[i].compareTo(smallest) < 0`：

```java
public static String findSmallest(String[] x) {
    String smallest = x[0];
    for (int i = 1; i < x.length; i++) {
        int cmp = x[i].compareTo(smallest);
        if (cmp < 0) {
            smallest = x[i];
        }
    }
    return smallest;
}
```

重新运行 `testFindSmallest`，绿灯亮起，成功通过！

##### 关于使用 AI 辅助编程的警示

在查阅类似 `compareTo` 这种语言语法特性时，大家现在很喜欢求助 ChatGPT 或者大语言模型。使用 AI 探索语言特性和查询语法完全没有问题，但大家一定要注意两点原则：

> **注意**：
> 1. **不要盲目复制代码**：千万不要直接把大半截作业代码丢给 AI 让它帮你补全。这样做不仅会剥夺你理解底层机制的机会，而且 AI 往往不会主动考虑效率和边界条件，常常会埋下极其细微但致命的 bug；
> 2. **切勿泄露敏感凭据**：新手经常在写代码时为了图省事，将个人 API Key（例如 OpenAI API Key）硬编码在代码里，随后连同仓库一起直接 push 到 GitHub 公开仓库！这些密钥绑定着个人信用卡，黑客的扫描爬虫会在数秒内盗取密钥疯狂刷调用量，导致巨额账单。这是必须时刻警惕的安全底线。

#### 构建第二个构件：交换元素

接下来我们通过 TDD 构建第二个构件 `swap`。

先写测试用例：

```java
@Test
public void testSwap() {
    String[] input = {"velociraptor", "horse", "koshi", "iridium"};
    String[] expected = {"koshi", "horse", "velociraptor", "iridium"};

    Sort.swap(input, 0, 2); // 交换下标 0 和下标 2

    assertThat(input).isEqualTo(expected);
}
```

如果在实现 `swap` 时粗心大意，犯了一个低级失误（比如直接赋值导致数据被覆盖）：

```java
// 错误示范：忘记使用临时变量保存数据
input[a] = input[b];
input[b] = input[a];
```

此时运行 `testSwap`，测试会立即拦截并指出数据错乱。正确的实现必须借助临时变量：

```java
public static void swap(String[] x, int a, int b) {
    String temp = x[a];
    x[a] = x[b];
    x[b] = temp;
}
```

再次运行测试，绿灯点亮。单元测试成功为我们兜底了低级手误。

### 接口崩塌、递归设计与科学调试法

两个辅助方法都已通过各自的单元测试。现在我们满怀信心地回到 `Sort.sort`，准备把它们拼装起来。

#### 第一次重大翻车：抽象与接口脱节

在 `Sort.sort` 中，按照选择排序的第一步逻辑，我们需要：
1. 找到输入数组中的最小值；
2. 把它与下标为 0 的元素交换。

我们顺手写下调用：

```java
public static void sort(String[] x) {
    // 找出最小值并交换到第 0 位？
    String smallest = findSmallest(x);
    swap(x, 0, ???); // 糟了！
}
```

写到这里，代码彻底写不下去了。

**问题出在哪里？** `swap` 方法要求传入两个整数索引下标 `a` 和 `b`。但我手里只有 `findSmallest` 返回的字符串内容 `"horse"`，我根本不知道它在数组中的下标到底是几！

这就是不加整体规划、急于上手写代码所必然经历的阵痛：**抽象之间的接口契约对不上**。

我们刚刚编写的 `findSmallest` 应该返回的是**最小项的索引下标（`int`）**，而不是最小项本身的值！

好在由于我们有单元测试的安全网保护，我们完全不用惧怕推倒重来。我们立即重构 `findSmallest`：

```java
public static int findSmallest(String[] x) {
    int smallestIndex = 0;
    for (int i = 1; i < x.length; i++) {
        int cmp = x[i].compareTo(x[smallestIndex]);
        if (cmp < 0) {
            smallestIndex = i;
        }
    }
    return smallestIndex;
}
```

同步修改 `testFindSmallest` 中的断言期望值（期望返回索引数值），重新运行测试，绿勾再次亮起。我们仅用了几秒钟就安全修复了接口契约。

#### 递归实现与私有辅助方法

完成了第一项的归位后，我们需要对数组剩余的部分继续排序。

这里我们可以选择迭代循环，但我更倾向于用**递归**来实现它，因为递归更贴合选择排序数学上的归纳美感：
- 找到全局最小项，归位到开头；
- 剩下的问题，变成了“对除开头以外的剩余子数组进行排序”。

然而，我们在 Java 中遇到了一个语言限制：Python 支持类似 `arr[1:]` 的切片语法，但 Java 不支持直接对数组进行切片切除。

如果直接修改公开的方法签名，变成 `public static void sort(String[] x, int start)`，这是一种极度糟糕的 API 设计。因为作为我们这个类的用户，他只想简单地调用 `Sort.sort(myArray)`，根本不想去操心还要额外传一个 `0` 作为起始参数。

> **结论**：解决这个矛盾的标准设计模式是使用**私有递归辅助方法（Private Helper Method）**。对外暴露简洁干净的公开 API，对内委托给携带额外递归状态参数的私有辅助方法。

```java
public class Sort {
    /** 对外暴露的公共接口：对整个数组进行排序 */
    public static void sort(String[] x) {
        sort(x, 0);
    }

    /** 私有递归辅助方法：对数组 x 从 start 索引开始到末尾的部分进行排序 */
    private static void sort(String[] x, int start) {
        // 基准情形 (Base Case)：当起始位置到达数组末尾时终止
        if (start == x.length - 1) {
            return;
        }

        int smallestIndex = findSmallest(x);
        swap(x, start, smallestIndex);
        sort(x, start + 1);
    }
}
```

#### 科学调试法：在断点处观察宇宙的状态

写完了上述代码，看起来递归骨架齐备、基准情形明确，感觉一切顺利。

我们信心满满地点击运行最初的那个 `testSort`，结果屏幕上弹出了一个巨大的红叉！测试彻底失败了，排出来的结果完全是乱的。

在缺乏经验的时候，很多同学遇到这种情况就会慌乱：是不是递归写错了？是不是基准情形算错了？于是开始在代码里盲目修改数值。

但请记住：**调试是一门严谨的科学实验（The Scientific Method）**。

```text
[ 提出假设 ]  --->  [ 设置断点 ]  --->  [ 运行观测 ]  --->  [ 差异定位 ]
预期每一轮 swap      在 swap 调用处      检查当前变量状态      找到现实行为与
应该把什么放哪里    设置断点暂停程序    (x, start, index)     预期假设的分歧点
```
上面的流程展示了将科学假设检验应用于程序断点排查的标准调试心智模型。

就像物理学家发现异常现象，或者亚历山大·弗莱明发现青霉素一样，面对程序与预期不符的时刻，应该是最令人兴奋的研究契机。

在本次调试中，我们要观察每一次 `swap` 发生时的状态：
1. **提出假设**：对于输入 `{"velociraptor", "horse", "koshi", "iridium"}`，第一次交换应该对调 `"velociraptor"` 和 `"horse"`；第二次交换应该保持已归位的 `"horse"` 不动，在剩余项中找出最小值 `"iridium"` 与第二位的 `"velociraptor"` 交换；
2. **设置断点**：在 `sort` 方法中调用 `swap` 的那一行打上断点；
3. **观察现实**：
   - 第一次击中断点并执行交换：数组变成了 `{"horse", "velociraptor", "koshi", "iridium"}`，符合预期！
   - 点击恢复执行，程序第二次击中断点：此时 `start = 1`。我们检查准备传入 `swap` 的参数，预期 `smallestIndex` 应该是 `"iridium"` 所在的下标 3；然而调试器里赫然显示 `smallestIndex = 0`！

我们顺藤摸瓜立刻抓到了真凶：
程序在第二轮递归中，居然试图把当前项与下标为 `0` 的项进行交换！因为 `findSmallest(x)` 每次都从索引 `0` 开始扫描整个数组，它无论何时返回的全局最小值永远是下标为 `0` 的 `"horse"`！

`findSmallest` 之前单测虽然通过了，但它的行为假设是“扫描整个数组”，并不适用于“只扫描剩余活跃子区间”的真实场景！

#### 最终重构与测试闭环

找到根因后，修复路径一目了然：`findSmallest` 也必须接受一个 `start` 参数，限定寻找最小值的起始范围！

我们再次借助 TDD 迭代：
1. 修改测试 `testFindSmallest`：传入起始下标 `2`，断言它能在后半段子数组中找到局部最小值；
2. 修改 `findSmallest` 的签名与内部逻辑：

```java
public static int findSmallest(String[] x, int start) {
    int smallestIndex = start;
    for (int i = start + 1; i < x.length; i++) {
        int cmp = x[i].compareTo(x[smallestIndex]);
        if (cmp < 0) {
            smallestIndex = i;
        }
    }
    return smallestIndex;
}
```

> **注意**：在修改这类循环边界时，极其容易连续出现低级笔误（例如增加了 `start` 形参但在函数体内依然写成了 `smallestIndex = 0`，或者循环仍然从 `0` 开始计数）。但只要我们每改一行都立即运行测试，这些细小的疏忽就会被测试即时拦截。

在更新完 `findSmallest` 之后，我们将 `Sort.java` 中私有辅助方法的调用修正为：

```java
private static void sort(String[] x, int start) {
    if (start >= x.length - 1) {
        return;
    }

    int smallestIndex = findSmallest(x, start);
    swap(x, start, smallestIndex);
    sort(x, start + 1);
}
```

再次点击运行 `testSort`——
侧边栏所有的测试方法左侧，齐刷刷地亮起了绿色对勾！排序方法全部通过！

### 架构规划与试错的工程张力

在回顾我们刚才经历的整个开发流程时，大家会发现我们经历了多次“翻车”：
- 以为返回字符串就行，结果发现无法调用 `swap`；
- 以为 `findSmallest` 能直接复用，结果递归到第二层发现扫描范围错误；
- 在修改函数签名时，甚至还连续出现了循环起点写错的低级 bug。

在软件工程中，永远存在这样一种张力：
- **前期的严谨架构设计**：理性的声音告诉你，应该在动手写代码之前，先在白板上把所有的抽象层次、类接口、数据流动与交互契约规划得一清二楚，这样后续实现就能一气呵成、极少返工；
- **快速动手的冲动与试错**：我们年轻程序员往往更渴望抓起键盘立刻敲出能运行的代码，在具体的实践中去摸索问题。而且在面对复杂系统时，人类有限的认知很难在第一天就凭空构思出绝对完美的软件抽象。

这两种理念没有绝对的对错之分。但无论你倾向于前期的深度规划，还是倾向于快速的原型试错，**单元测试都是决定你能否走得长远的根本支柱**。

正因为我们为每一个微小的功能模块都构筑了自动化测试，我们在发现接口设计不合理时，敢于立刻大刀阔斧地重构；在面对手误和边界 bug 时，能够被测试瞬间捕获并借助科学调试法迅速修正。

测试并不是减慢你开发节奏的绊脚石，它就是你在代码陡峭崖壁上亲手打下的一枚枚岩钉。有了这套安全绳，你才能真正拥有从容不迫的工程师底气。
