# 双链表与基础数组列表

## 双向链表拓扑与哨兵演进

### 尾部操作与双向链接

* **尾部删除反向回溯困境（Tail Removal Backtracking Dilemma）**
    * > **定义**：单向链表仅维护末尾节点指针时无法在常数时间内完成尾部删除操作的结构性缺陷。
    * 单向指针拓扑结构只支持沿 `next` 向后遍历，无法反向获取目标节点的前驱节点。
    * 仅维护 `last` 指针时，`removeLast` 操作必须从表头重新遍历至倒数第二节点以修正指针，耗时为 $O(N)$。
    * 增设多级指针缓存（如 `secondToLast`）在连续删除场景下会导致前驱回溯链断裂并引发指针维护退化。
    * 单向链表尾部回溯困境如下：
    ```text
    sentinel --> [ 5 ] --> [ 3 ] --> [ 9 ] (倒数第二节点) --> [ 50 ] (末尾节点)
                                      ^                          ^
                                      |                          |
                                 无法反向回溯                   last 指针
    ```
    * > **易错点**：误认为持有 `last` 即可实现 $O(1)$ 的 `removeLast`，忽略了前驱节点的 `next` 指针必须置空且 `last` 需前移的物理要求。

* **双向链表（Doubly Linked List，DLList）**
    * > **定义**：每个节点同时包含指向直接前驱和直接后继引用的线性对称链式存储结构。
    * 节点由数据域 `item`、后继指针 `next` 以及前驱指针 `prev` 三个物理字段构成。
    * 引用指针直接绑定整个节点对象内存，而非节点内部的数据值单元。
    * 任意节点均可在 $O(1)$ 时间内沿 `prev` 访问前驱，两端插入与删除操作完全实现对等常数时间。
    * 双向链表节点拓扑结构如下：
    ```text
                 +------+               +------+
      ... <====  | prev |  <=========   | prev |
                 +------+               +------+
                 | item |               | item |
                 +------+               +------+
                 | next |  =========>   | next |  ====> ...
                 +------+               +------+
    ```
    * > **注意**：每个节点因引入反向指针会多消耗一个引用字段的物理内存空间。

### 哨兵架构演进

* **双哨兵结构（Double Sentinel Scheme）**
    * > **定义**：在双向链表头尾两端分别设置一个固定虚拟节点以消除空指针特判的结构方案。
    * 表头通过 `sentinelHead` 锚定，表尾通过 `sentinelTail` 锚定。
    * 双哨兵双向链表拓扑如下：
    ```text
    [ sentinelHead ] <=========> [ Node 1 ] <=========> [ Node 2 ] <=========> [ sentinelTail ]
    ```
    * 有效数据节点完全约束在两个哨兵之间，彻底消除了空链表及单节点操作中的 `null` 指针分支特判。
    * 结构存在两个孤立的哨兵对象实体，初始化与维护阶段存在对象创建冗余。
    * > **易错点**：在空链表状态下必须严格将 `sentinelHead.next` 指向 `sentinelTail`，同时将 `sentinelTail.prev` 指向 `sentinelHead`。

* **循环单哨兵结构（Circular Sentinel Scheme）**
    * > **定义**：利用单个虚拟哨兵节点首尾自环闭合以管理全表两端操作的环状拓扑结构。
    * 空链表状态下，哨兵节点的 `prev` 与 `next` 均指向自身，形成天然闭环：
    ```text
             +-------------------------------+
             |                               |
             v                               |
         +-------+                           |
         | prev  | --------------------------+
         +-------+
         | item  |
         +-------+
         | next  | --------------------------+
         +-------+                           |
             ^                               |
             |                               |
             +-------------------------------+
    ```
    * 非空链表状态下，`sentinel.next` 恒定指向首个有效节点，`sentinel.prev` 恒定指向末尾有效节点：
    ```text
            +-------------------------------------------------------+
            |                                                       |
            |    +=============================================+    |
            |    |                                             |    |
            v    v                                             |    |
         +----------+           +----------+           +----------+ |
         | sentinel | <=======> |  Node A  | <=======> |  Node B  | |
         +----------+           +----------+           +----------+ |
            |    |                                             ^    ^
            |    +=============================================+    |
            |                                                       |
            +-------------------------------------------------------+
    ```
    * 头部插入、头部删除、尾部插入、尾部删除的指针操作规则完全统一，无需编写任何针对空表或单节点的特判代码。
    * > **提示**：循环拓扑确保全链表在任何状态下均不存在悬空的 `null` 引用。

## 泛型抽象与静态语义边界

### 泛型参数化与包装机制

* **泛型类型形参（Generic Type Parameter）**
    * > **定义**：在类定义中声明用于代指未知具体类型的类型占位符。
    * 占位符置于类名后尖括号内，标识符可自定义声明（如 `Camel`、`Item`、`T`）。
    * 编译期强制执行类型安全检查，运行期通过类型擦除统一转换为基础边界类型。
    * 泛型定义与调用实现示例：
    ```java
    public class SLList<Camel> {
        private class Node {
            public Camel item;
            public Node next;
        }
        private Node sentinel;
        private int size;
    }
    ```
    * > **易错点**：实例化泛型对象时构造函数后尖括号使用菱形操作符 `<>`，不可填入不兼容的具名类型。

* **包装类约束（Primitive Wrapper Restriction）**
    * > **定义**：Java 泛型机制无法直接接纳原生基础数据类型而必须映射到对应引用类型的语言规范限制。
    * 原生基础类型（如 `int`、`double`、`boolean`）不可直接作为泛型实参使用。
    * 基础类型必须使用对应的对象包装类（如 `Integer`、`Double`、`Boolean`）进行类型参数化。
    * 包装类会在堆中产生对象创建开销与寻址间接层，增加内存消耗。
    * > **注意**：泛型类型擦除后无法与不同位宽的原生数据内存模型直接对齐。

### 静态上下文与内部类作用域

* **泛型作用域冲突（Generic Scope Conflict）**
    * > **定义**：静态嵌套类因脱离外部类实例生命周期而无法直接访问外部类泛型类型参数的编译期错误。
    * 带有 `static` 修饰的嵌套类归属于类本身，在未实例化外部类对象前即已独立存在。
    * 外部类的泛型实参仅在其实例化对象时方可具体确定。
    * 静态内部类内部直接引用外部类的泛型变量会导致 `cannot be referenced from a static context` 编译错误。
    * 规避方案包括移除内部类的 `static` 修饰符，或在静态内部类上独立声明泛型形参。
    * > **易错点**：试图通过为泛型节点类盲目添加 `static` 关键字优化内存占用，导致编译拦截失败。

* **静态关键字多义性（Static Keyword Overloading）**
    * > **定义**：语言规范中将 static 单一词汇复用于不同维度的语义重载现象。
    * 静态成员：修饰类变量或类方法，属于类实体并由所有实例共享，脱离单体实例作用域。
    * 静态嵌套类：修饰内部类结构，解除内部类与外部类实例之间的隐式引用关系。
    * 静态类型系统：指代类型判定在编译期静态确定而非运行期动态绑定的类型系统属性。
    * > **提示**：解析静态相关的语法报错时必须优先区分其修饰的是成员作用域还是嵌套类上下文。

## 物理内存模型与数组列表实现

### 连续内存与寻址机理

* **数组内存模型（Array Memory Model）**
    * > **定义**：在物理内存中占据连续字节序列且单元尺寸完全均一的线性存储结构。
    * 数组对象创建后其物理槽位长度 `.length` 恒定不可动态增减。
    * 数组内每个槽位所占用的物理字节大小严格一致。
    * 数组物理存储布局如下：
    ```text
    物理基地址 0x1000
        |
        v
    +---------+---------+---------+---------+---------+
    | [0] 32b | [1] 32b | [2] 32b | [3] 32b | [4] 32b |
    +---------+---------+---------+---------+---------+
      0x1000    0x1004    0x1008    0x100C    0x1010
    ```
    * > **注意**：数组变量本身仅为保存底层连续存储区域首地址的引用指针。

* **常量时间随机寻址（Constant-Time Random Access）**
    * > **定义**：基于数学基地址与偏移量一步直达物理内存单元的直接寻址机制。
    * 绝对物理地址换算方程：$\text{Address}(i) = \text{BaseAddress} + i \times \text{ElementSize}$。
    * 硬件内存控制器仅需执行单次乘法与加法运算即可提取数据，寻址时间复杂度为 $O(1)$。
    * 链表在执行任意位置的 `get(i)` 操作时必须按步跳转指针，寻址时间复杂度为 $O(N)$。
    * 数组列表在头部执行插入时必须全量后移元素，头部操作时间复杂度为 $O(N)$。
    * > **易错点**：试图通过在链表中间维护指针消除访问瓶颈，仍无法消除全局随机访问的线性寻址成本。

### 基础数组列表设计与类不变式

* **基础数组列表（Basic Array List，AList）**
    * > **定义**：基于原生固定数组与长度计数器封装的可按需追加元素的列表雏形。
    * 内部维护原生底层数组 `items` 与记录实际有效数据量的整型变量 `size`。
    * 类初始化实现：
    ```java
    public class AList {
        private int[] items;
        private int size;

        public AList() {
            items = new int[100];
            size = 0;
        }
    }
    ```
    * 初始状态下数组物理空间被预分配，有效元素计数器置零：
    ```text
    items ----> [  0  |  0  |  0  |  0  | ... |  0  ] (容量 100)
                   ^
                   |
    size = 0  (下一个插入位置)
    ```
    * > **提示**：固定容量数组列表在有效元素数量超过初始容量限制后，继续追加会触发越界异常。

* **类不变式（Class Invariants）**
    * > **定义**：在数据结构生命周期中任何公有方法执行完毕后均保持成立的状态恒等式。
    * 规则一：`size` 变量的数值始终严格等于列表中当前有效数据项的总量。
    * 规则二：列表当前最后一个有效元素，物理存储位置必定为 `items[size - 1]`。
    * 规则三：执行 `addLast` 新追加的有效元素，写入目标位置必定为 `items[size]`。
    * 尾部追加与元素读取实现：
    ```java
    public void addLast(int x) {
        items[size] = x;
        size += 1;
    }

    public int getLast() {
        return items[size - 1];
    }

    public int get(int i) {
        if (i < 0 || i >= size) {
            throw new ArrayIndexOutOfBoundsException("索引越界: " + i);
        }
        return items[i];
    }
    ```
    * > **易错点**：`get(i)` 必须严格限制边界为 `i < size` 而非 `i < items.length`，底层预分配但未填充有效值的内存槽位对调用方不可见。

### 状态封装与逻辑删除机制

* **数据结构抽象屏障（Abstraction Barrier）**
    * > **定义**：通过访问权限控制隐藏底层存储细节并仅对外暴露接口行为契约的封装架构。
    * 外部调用方仅能依据 API 返回的状态投影感知数据结构行为，无法接触底层物理内存。
    * 数据结构内部实现只需在公有接口层面满足行为契约，无需执行多余的物理同步擦除。
    * 抽象隔离结构如下：
    ```text
    +--------------------------------------------------------+
    | 外部调用方视角（逻辑状态观测）：                        |
    | API 行为：size()、get(i)、getLast()                    |
    +--------------------------------------------------------+
                               ^
                               | 抽象屏障（private / API）
                               v
    +--------------------------------------------------------+
    | 底层物理现实（内部私有状态）：                          |
    | 原生数组 items[]、预分配空间、废弃数据物理残留          |
    +--------------------------------------------------------+
    ```
    * > **提示**：私有成员修饰与前置边界检查构筑了抽象屏障的防御边界。

* **逻辑删除（Logical Deletion）**
    * > **定义**：仅通过修改状态计数器收缩有效数据边界而不清除对应物理内存数据的剔除策略。
    * `removeLast` 操作无需清零数组槽位，通过递减 `size` 实现元素剔除并复用 `getLast`：
    ```java
    public int removeLast() {
        int x = getLast();
        size -= 1;
        return x;
    }
    ```
    * 执行逻辑删除前后的内存物理状态如下：
    ```text
    执行前：size = 4, items: [ 5 | 3 | 9 | 50 | 0 | ... ]
                                            ^
                                            | (最后一个元素)

    执行后：size = 3, items: [ 5 | 3 | 9 | 50 | 0 | ... ]
                                      ^     ^
                                      |     +-- 物理残留 50 沦为逻辑不可达废弃数据
                                  (新末尾)
    ```
    * 被逻辑排除的槽位在下次调用 `addLast` 时会被新数据直接物理覆盖。
    * > **易错点**：基础类型数组无需显式擦除数据；但泛型对象引用数组必须显式置空 `items[size] = null`，以防止对象游离造成内存泄漏。
