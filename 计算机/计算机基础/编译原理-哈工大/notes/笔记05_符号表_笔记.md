# 符号表

## 符号表的组织

* **符号表（Symbol Table）**

    * > **定义**：编译器在编译全过程中持续收集并保存源程序各个名字属性信息的表，供随时查询。

    * 记录的信息包括：这个名字是变量还是过程、什么类型、占几个字节、放在什么位置、有没有返回值。

    * 组织方式通常不是一张大表，而是为每个作用域、每个程序块各建一张独立的符号表。

* **表项**

    * 变量表项记录名字、类型与相对地址。

    * 过程表项的地址字段不存数据地址，而存指向该过程自身符号表的指针。

    * 一张表里的过程记录因此成为通往下一张表的入口。

* **表头**

    * 表头有一个字段：这个过程一共需要多少个存储单元。

    * 只声明一个整型变量的过程填 4，声明两个整型变量的过程填 8，什么都没声明的过程填 0。

* **表间结构**

    * 各表通过过程表项里的指针连成树：外层表看得到内层表的入口，内层表守着自己的局部数据。

    * 嵌套层次越深，指针链越长；同一层里的变量在同一张表里累计相对地址。

```text
[sort]
  a            int     相对地址 0
  x            int     相对地址 44
  readarray    --> [readarray]
  exchange     --> [exchange]
  quicksort    --> [quicksort]
                     k          int   相对地址 0
                     v          int   相对地址 4
                     partition  --> [partition]
                                      i   int   相对地址 0
                                      j   int   相对地址 4
```

* **实例中的数值**

    * `sort` 表：`a` 为 `int`、相对地址 0；`x` 为 `int`、相对地址 44，前面的 44 个字节被 11 个整型的数组 `a` 占满。

    * `readarray` 表只有 `i`，表头填 4；`quicksort` 表有 `k`（相对地址 0）、`v`（相对地址 4）与指向 `partition` 表的记录，表头填 8。

    * `partition` 表有 `i`（相对地址 0）、`j`（相对地址 4），表头填 8；`exchange` 表没有任何记录，表头填 0。

## 符号表与活动记录的对应

* **活动记录（Activation Record）**

    * > **定义**：过程运行时在栈上占据的数据区，与按过程建立的符号表一一对应。

    * 过程里用到的非局部名字，其信息可以通过扫描外围过程的符号表取得。

* **两条链同步前进**

    * 符号表之间有外围指针链，活动记录之间有访问链，查找非局部名字时两条链并排走、一步对一步。

    * 设栈顶是过程 p 的活动记录，p 中要访问 `a`：先在 p 的符号表里查 `a`，没有。

    * 顺着 p 那张表里的外围指针，来到外围过程 `quicksort` 的符号表；与此同时栈顶的活动记录沿访问链走一步，来到 `quicksort` 的活动记录。

    * `quicksort` 的表里也没有 `a`，再顺着指针到 `sort` 的符号表；活动记录也跟着再走一步，落到 `sort` 的活动记录。

    * 在 `sort` 的表里找到 `a`，取出相对地址，在 `sort` 的活动记录里定位到该单元。

* **同构的结论**

    * 查表走了几步，访问链也走几步，最后正落在名字被找到的那一层。

    * 两条链同构，是它们能对上的根本原因。

```text
符号表链                             活动记录链
[p]              --------->         p 的活动记录        <- 栈顶
 | 外围指针                          | 访问链
 v                                   v
[quicksort]      --------->         quicksort 的活动记录
 | 外围指针                          | 访问链
 v                                   v
[sort]           --------->         sort 的活动记录     <- a 在这里
```

* **访问链的三种建立情形**

    * 外层过程调用内层过程：在调用者 s 的符号表里查 q，查到说明 q 是直接声明在 s 里的，q 的访问链直接指向调用者 s 的活动记录。

    * 递归调用：调用者与被调用者是同一个过程，两者的访问链本来就一样，直接复制过来。

    * 内层过程调用外层过程：在 p 的表里查 e 没有，沿外围指针到 `quicksort` 的表仍没有，再到 `sort` 的表找到，说明 e 声明在 `sort` 中，e 的访问链指向 `sort` 的活动记录。

* **统一规则**

    * 访问链永远指向"名字被找到的那一层"的活动记录。

    * 外层调内层时那一层就是调用者；递归时就是自己；内层调外层时，就是一路向外找到的那一层。

## 标识符的两种出现

* **定义性出现**

    * > **定义**：标识符出现在某一层的声明语句里，身份是被声明的名字。

    * 处理时只查本层的符号表。

    * 查到同名记录就报错，说明这个标识符重复声明了。

    * 查不到就在表里加一条新记录，把标识符及其相关信息填进去。

* **应用性出现**

    * > **定义**：标识符出现在某一层的可执行语句里，身份是被使用的名字。

    * 处理时一层一层往外查：先查本层的表，查不到就到直接外层的表，再查不到就继续往外。

    * 一旦找到，就把记录里的信息取出来做相应处理。

    * 一路查到最外层都没有，报错，说明标识符未经声明就使用了。

* **两条规则的分工**

    * 定义只查本层，内层才能声明一个和外层同名的名字。

    * 使用从内层往外查、先撞上谁就用谁，正好实现"内层优先"的可见性。

    * > **提示**：两条规则看着不对称，其实各有各的道理——前者允许遮蔽，后者让遮蔽生效。

## 用 SDT 建立符号表

### 嵌套过程的声明结构

* **文法形态**

    * 声明序列 $D$ 由若干声明组成，每个声明要么是过程声明，要么是变量声明。

    * 过程声明内部可以继续声明过程与变量。

    * 一个程序由一个声明序列构成。

* **挂起与恢复**

    * 看到嵌套过程 P 时，暂时挂起对外围过程 Q 声明语句的处理，先进入 P 处理 P 自己的声明。

    * P 结束后再回来接着处理 Q 剩下的部分。

    * "挂起一层、进入一层、处理完再回来"用栈实现最自然。

### 两个栈与四个操作

* **tblptr**

    * 存放指向各层符号表的指针。

* **offset**

    * 跟踪各张符号表里已经分配到的相对地址值。

* 栈顶的这一对永远代表现在正在处理哪一层、这一层分到哪儿了。

* **mktable(previous)**

    * 建一张新表并返回指向新表的指针。

    * 参数 `previous` 指向先前创建的、也就是外围过程的符号表。

* **enter(表, 名字, 类型, 相对地址)**

    * 在指定的表里为这个名字建一条记录。

* **addwidth(表, 值)**

    * 把本过程所需的存储单元数填进表的表头。

* **enterproc(表, 名字, 新表)**

    * 在外围过程的表里为新声明的过程建一条记录，地址字段放指向新表的指针。

### 标记非终结符 M 与 N

* **M 的位置与动作**

    * 嵌在程序的开头，对应一段语义动作：调用 `mktable` 建一张新表，再把新表指针与相对地址 0 压进两个栈。

    * 建的是最外层那张表；它没有外围过程，表头里记外围表的那一栏填空。

* **N 的位置与动作**

    * 在识别出一个过程名之后插入，动作同样是 `mktable` 加压栈。

    * 建表时把 previous 传成当前栈顶的符号表，新表以栈顶那张表作为自己的外围过程表。

* **两者的唯一差别**

    * 差别只在 previous 传什么：M 传空，因为程序这一层没有外围；N 传栈顶，因为每个过程的外围就是它被声明时所在的那一层。

    * 两个动作都是"建表 + 压栈"，所以每进一层过程，栈就高一格。

### 变量登记与过程归约

* **变量声明**

    * 每识别出一个变量，先执行 `enter(栈顶表, id, 类型, top(offset))`，相对地址直接取当前栈顶的 offset 值。

    * 然后让 `top(offset)` 加上这个变量的宽度。

    * 宽度从类型来：一个整型 4 个字节，11 个整型的数组就是 44 个字节。

* **offset 栈的作用**

    * 每一层各有各的分配进度，压栈出栈自动切换。

    * 从内层出来回到外层时，offset 也回到外层该在的位置。

* **过程归约的四步**

    * 令 $t$ 指向当前栈顶的符号表。

    * 执行 `addwidth(t, top(offset))`，把这一层总共用掉多少存储单元写进表头。

    * 栈顶的符号表指针和相对地址一起出栈，栈顶于是露出了外围过程的符号表。

    * 执行 `enterproc(栈顶表, 过程名, t)`，在外围过程的表里为刚结束的过程建一条记录，地址字段放指向它那张表的指针。

    * 顺序不能反：必须先出栈露出外围表，才有地方写这条记录。

* **程序收尾**

    * 整个程序识别完归约，执行 `addwidth(栈顶表, top(offset))`，给最外层那张表填上大小。

    * 然后把它的指针和相对地址出栈，栈空，建表结束。

## 建表走查

* **主程序表与 sort 表**

    * 初始时 `tblptr` 与 `offset` 两个栈都为空。

    * 执行 M 的动作建一张新表，它没有外围表，表头那一栏填空；表的指针与相对地址 0 压栈。

    * 读入 `program sort;` 之后执行 N 的动作，以当前栈顶的主程序表为外围，为 `sort` 建一张新表，指针与 0 压栈。

* **变量 a 与 x**

    * `a`：在栈顶的 `sort` 表里建记录，相对地址取 `top(offset)` 的 0；offset 加上 `a` 的宽度 44（11 个整型、每个 4 字节），下一个变量从 44 开始。

    * `x`：相对地址取 44，填完 offset 加 4 变成 48。

* **readarray**

    * 读入 `proc readarray` 执行 N 的动作，为 `readarray` 建表，外围是 `sort` 的表，压栈；offset 也随之从 0 重新开始。

    * `i`：在 `readarray` 表里建记录，相对地址 0，offset 变成 4。

    * 归约：$t$ 指向 `readarray` 的表，`addwidth(t, 4)`，表指针与 offset 出栈露出 `sort` 的表，`enterproc(sort 的表, readarray, t)`。

* **exchange**

    * N 建表，外围 `sort`，压栈；过程里没有变量声明，offset 一直停在 0。

    * 归约时 `addwidth(t, 0)`，表头填 0；出栈后 `enterproc` 在 `sort` 的表里补上 `exchange` 的记录。

    * 没声明任何变量的过程，表就是一张只有表头的空表，大小为 0，这是合法的登记结果。

* **quicksort 与 partition**

    * `k` 相对地址 0、offset 变 4；`v` 相对地址 4、offset 变 8。

    * `partition` 是函数，函数也是过程、只是带返回值，照样走 N 的动作，为它建表，外围是 `quicksort` 的表。

    * `partition` 里 `i` 相对地址 0、offset 变 4；`j` 相对地址 4、offset 变 8。

    * `partition` 归约：`addwidth(t, 8)`；出栈露出 `quicksort` 的表；`enterproc(quicksort 的表, partition, t)`。

    * `quicksort` 归约填 8 而不是 16：`partition` 那 8 个单元记在 `partition` 自己的表头里，不算进 `quicksort` 的局部数据；`quicksort` 的 offset 从头到尾只被 `k`、`v` 推过两次。

* **收尾**

    * `sort` 归约：`addwidth(t, 48)`；出栈露出主程序表；`enterproc(主程序表, sort, t)`。

    * 程序归约：主程序里没有声明全局变量，最外层表头填 0；出栈，栈空，所有符号表建完。

| 符号表 | 表中的记录 | 表头：所需存储单元数 |
| :--- | :--- | :--- |
| 主程序表 | `sort`（指针） | 0 |
| `sort` | `a`、`x`、`readarray`、`exchange`、`quicksort` | 48 |
| `readarray` | `i` | 4 |
| `exchange` | 无 | 0 |
| `quicksort` | `k`、`v`、`partition` | 8 |
| `partition` | `i`、`j` | 8 |

* **三句话总结**

    * 进一层就压栈建表。

    * 声明一个变量就记一笔、把 offset 往前推。

    * 出一层就结账，把大小写回表头，再在外围表里补一条指针记录。

## 基本块

* **代码优化**

    * > **定义**：对代码做等价的程序变换，让它运行得更快、占用的空间更少，或者二者兼顾。

    * 做优化之前通常得先把程序的控制流程分析清楚，用流图描述；流图的每个节点是一个基本块。

* **基本块（Basic Block）**

    * > **定义**：满足两个条件的最大、连续的三地址指令序列。

    * 条件一：控制流只能从基本块的第一条指令进入；任何转移指令的目标都只能是某个基本块的第一条指令，不能是块中间或末尾的指令。

    * 条件二：除了最后一条指令，控制流在离开基本块之前不会跳转或停机。

    * 两条合起来，块内所有指令要么全都执行、要么全都不执行，是作为一个整体行动的。

* **最大性的含义**

    * 两条条件只管入口和出口，不管块有多长。

    * 单拿一条指令出来也满足这两条，可它显然不是所要的块，所以"最大"两个字不能省。

    * 凡是顺着走下来、中间既没有跳转指令、也没有被别的跳转指进来的那一段，都得算在同一块里，不能随手切开。

* **首指令**

    * 首指令是每一块的第一条指令；首指令定下来后，从一条首指令开始、到下一条首指令之前的所有指令构成一个基本块。

    * 来源一：指令序列的第一条指令，一定是第一个基本块的首指令。

    * 来源二：任何条件或无条件转移指令的目标指令，一定是首指令。

    * 来源三：紧跟在一条条件或无条件转移指令后面的那条指令，也一定是首指令。

* **划分算法**

    * 输入一个三地址指令序列，输出它对应的基本块列表，每条指令恰好被分到一个基本块里。

    * 做法是先扫一遍标出所有首指令，再按首指令切段。

* **六条首指令切六块**

    * 首指令为 1、5、9、23、13、14：1 是序列第一条，5、9、23 是某条转移指令的目标，13 紧跟在 12 号转移指令之后，14 紧跟在 13 号转移指令之后。

    * 六个块：$B_1$ 为 1~4，$B_2$ 为 5~8，$B_3$ 为 9~12，$B_4$ 只有 13 号一条，$B_5$ 为 14~22，$B_6$ 从 23 号一直到序列末尾。

    * 12 号是转移指令，所以 13 号成了首指令；13 号本身又是转移指令，所以 14 号也成了首指令——两条跳转挨在一起就切出一个只有一条指令的块，基本块的长度没有下限。

## 流图

* **流图（Flow Graph）**

    * > **定义**：以基本块为节点、以可能的后继关系为有向边的图。

    * 从基本块 $B$ 到基本块 $C$ 有一条边，当且仅当 $C$ 的第一条指令可能紧跟在 $B$ 的最后一条指令之后执行。

    * 这时称 $B$ 是 $C$ 的前驱，$C$ 是 $B$ 的后继。

* **后继的两种来源**

    * 有一条从 $B$ 结尾跳转到 $C$ 开头的转移语句，条件或无条件都算，$C$ 就有可能跟在 $B$ 之后执行。

    * 按原来的三地址指令序列顺序，$C$ 就紧挨在 $B$ 后面，而且 $B$ 的结尾不是无条件跳转，$C$ 也可能跟在 $B$ 之后。

* **六块的边**

    * $B_1 \to B_2$：原序列相邻，$B_1$ 的末条不是无条件跳转。

    * $B_2 \to B_2$：$B_2$ 的末条跳转到 5 号，也就是自己的首条，形成自环。

    * $B_2 \to B_3$：相邻且 $B_2$ 的末条不是无条件跳转。

    * $B_3 \to B_3$：$B_3$ 的末条跳回 9 号，也就是自己的首条，形成自环。

    * $B_3 \to B_4$：相邻且 $B_3$ 的末条不是无条件跳转。

    * $B_4 \to B_5$：相邻且 $B_4$ 的末条不是无条件跳转。

    * $B_4 \to B_6$：$B_4$ 的末条跳转到 23 号，也就是 $B_6$ 的首条。

    * $B_5 \to B_2$：$B_5$ 的末条跳转到 5 号，也就是 $B_2$ 的首条。

    * $B_6$ 没有后继，程序从这里离开。

```text
B1 ──► B2
B2 ──► B2    （末条跳回 5 号，即自身首条）
B2 ──► B3
B3 ──► B3    （末条跳回 9 号，即自身首条）
B3 ──► B4
B4 ──► B5
B4 ──► B6    （末条跳到 23 号，即 B6 首条）
B5 ──► B2    （末条跳回 5 号，即 B2 首条）
B6 ──► 无
```

* **相邻不等于有边**

    * $B_5$ 与 $B_6$ 在指令序列上明明是挨着的，却没有边，因为 $B_5$ 的末条是无条件跳转，执行完它一定走了，落不到下面那条。

    * > **注意**：判断有没有顺序边，看的是"末条会不会跳走"，不是"两块挨不挨着"。

* **图的读法**

    * $B_2$、$B_3$ 各自原地打转，是两个小循环。

    * $B_5$ 的回边把控制送回 $B_2$，串起一个大循环；$B_6$ 没有后继，是程序的出口。

## 代码优化的分类

* **按是否依赖具体机器**

    * 机器无关优化：针对中间代码层做。

    * 机器相关优化：针对目标代码层做。

    * 重点讨论的是机器无关优化，也就是在中间代码层上做优化。

* **按作用范围**

    * 局部代码优化：只做单个基本块范围内的优化。

    * 全局代码优化：面向多个基本块。

| 分法 | 两类 | 差别在哪 |
| :--- | :--- | :--- |
| 按是否依赖机器 | 机器无关优化 / 机器相关优化 | 前者在中间代码层做，后者在目标代码层做 |
| 按作用范围 | 局部代码优化 / 全局代码优化 | 前者限于单个基本块，后者跨多个基本块 |

* **常用优化方法**

    * 共六种：删除公共子表达式、删除无用代码、常量合并、代码移动、强度削弱、删除归纳变量。

    * 删除公共子表达式最能说明"等价变换"四个字的分量。

## 删除公共子表达式

* **公共子表达式（Common Subexpression）**

    * > **定义**：若表达式 $x\ \text{op}\ y$ 先前已被计算过，且从那次计算到现在 $x$、$y$ 的值都没有改变，则这次出现的 $x\ \text{op}\ y$ 称为公共子表达式。

    * $\text{op}$ 是运算符，$x$、$y$ 是两个运算分量。

    * 既然它的值前面已经算出来了，这次就可以删掉，直接拿上次的结果来用，省下一次重复计算。

    * 判定条件其实是两条：同一个表达式；中间它的运算分量没变。

    * 前一条好认，后一条才是真正的麻烦。

* **局部与全局的分界**

    * 上一次计算在同一个基本块内，是局部公共子表达式。

    * 上一次计算在另一个基本块里，是全局公共子表达式。

    * 分界看的是"上一次计算发生在哪儿"，不是"这次出现发生在哪儿"。

### 块内删除

* **$B_5$ 的原始序列**

    ```text
    T6  = 4 * i
    x   = A[T6]
    T7  = 4 * i
    T8  = 4 * j
    T9  = A[T8]
    A[T7] = T9
    T10 = 4 * j
    A[T10] = x
    goto B2
    ```

* **第一处重复**

    * 第一条 `T6 = 4 * i` 与第三条 `T7 = 4 * i` 之间隔着 `x = A[T6]`，只读了数组、没有动过 `i`。

    * `i` 的值没变，所以第三条里的 `4 * i` 是公共子表达式；上一次计算就在本块内，是局部公共子表达式。

    * 删掉后用 `T6` 替换所有对 `T7` 的引用。

* **第二处重复**

    * `T8 = 4 * j` 与 `T10 = 4 * j` 之间隔着 `T9 = A[T8]`，也没有动过 `j`。

    * `T10` 那条同样是局部公共子表达式，删除后用 `T8` 替换。

* **块内删除后的序列**

    ```text
    T6  = 4 * i
    x   = A[T6]
    T8  = 4 * j
    T9  = A[T8]
    A[T6] = T9
    A[T8] = x
    goto B2
    ```

    * 九条指令剩七条。

### 跨块删除

* **沿导入弧往上游找**

    * $B_5$ 的第一条是 `T6 = 4 * i`；沿着 $B_5$ 的导入弧（进入 $B_5$ 的那些边）逆流而上，会发现这个 `4 * i` 在 $B_2$ 里已经算过一次（`T2 = 4 * i`）。

    * 从那次计算到这一次，`i` 的值没有改变，所以这里的 `4 * i` 仍是公共子表达式，只是上一次计算发生在另一个基本块里，是全局公共子表达式。

    * 同理，`4 * j` 在 $B_3$ 里算过（`T4 = 4 * j`），中间也没动过 `j`。

    * 用 `T2`、`T4` 替换后，$B_5$ 剩五条。

* **替换后露出的新机会**

    * `A[T2]` 在 $B_2$ 里计算过（`T3 = A[T2]`），从那次计算到现在 `T2` 没有被重新赋值，中间也没有任何对数组元素的赋值，所以这里的 `A[T2]` 就是 `T3`。

    * `A[T4]` 在 $B_3$ 里计算过（`T5 = A[T4]`），同样是全局公共子表达式。

    * `T9 = A[T4]` 中 `T9` 是临时变量，唯一用处是给下一条指令赋值；值可以直接用 `T5`，于是整条指令删掉，后面用到 `T9` 的地方换成 `T5`。

    * 五条变四条。

* **替换结果**

    ```text
    x   = T3
    A[T2] = T5
    A[T4] = x
    goto B2
    ```

* **连锁性**

    * 新机会是上一轮替换之后才露出来的：删掉算 `4 * i`、`4 * j` 的两条指令，`A[T2]`、`A[T4]` 的重复计算才在眼前显形。

    * 这类优化要一轮一轮往下做，直到再看不出可删的为止。

### 数组元素的下标歧义

* **$B_6$ 里能删的四条**

    * `4 * i` 出现两次（`T11`、`T12`），是局部公共子表达式；`4 * n` 出现两次（`T13`、`T15`），也是局部公共子表达式。

    * `4 * i` 在 $B_2$ 算过（`T2`）、`4 * n` 在 $B_1$ 算过（`T1`），所以这两个还都是全局公共子表达式，四条重复指令全都能删。

    * 删后 `A[T2]` 又能在 $B_2$ 找到出处（`T3`），写成 `x = T3`。

* **$A[T_1]$ 删不得**

    * `A[T1]` 确实在 $B_1$ 里算过；问题在于从那次计算之后、进入 $B_6$ 之前，控制流有可能先拐进 $B_5$。

    * $B_5$ 里有两条对数组元素的赋值 `A[T2] = T5` 与 `A[T4] = x`；`T2` 是 `4 * i`、`T4` 是 `4 * j`、`T1` 是 `4 * n`。

    * 只要 `i` 或 `j` 恰好等于 `n`，这两条赋值写进去的正是 `A[T1]` 这个单元，$B_1$ 里算出的 `A[T1]` 到 $B_6$ 时可能已经过期。

    * 只要有这样一条路存在，就不能赌它不走；`A[T2]` 能删，`A[T1]` 不能删，那趟内存读取必须老老实实留着。

* **最终序列**

    ```text
    x   = T3
    T14 = A[T1]
    A[T2] = T14
    A[T1] = x
    ```

* **易错边界**

    * > **易错点**：判断公共子表达式不能只看"这个式子前面算过"，还得看"从那次计算到现在，它依赖的东西有没有被改过"。

    * 对数组元素尤其要小心：不同的下标表达式可能指向同一个单元；`4 * i`、`4 * j`、`4 * n` 在编译时都不知道具体是多少，谁也不敢保证 `A[T2]`、`A[T4]` 与 `A[T1]` 不是同一块内存。

    * 如何自动识别公共子表达式属于后续专门讲的分析技术。
