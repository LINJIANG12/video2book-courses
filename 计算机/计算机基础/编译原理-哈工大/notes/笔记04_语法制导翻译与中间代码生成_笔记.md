# 语法制导翻译与中间代码生成

## 翻译框架与两种挂法

* **语法制导翻译（syntax-directed translation）**

    * > **定义**：使用上下文无关文法来引导对语言的翻译，是一种面向文法的翻译技术。

    * 语义分析与中间代码生成常合并实现，合称语义翻译；把语义翻译并入语法分析，就是语法制导翻译。

    * 文法因此承担两件事：判定输入串是否合法并给出结构；规定这个结构该翻译成什么。

    * 语义信息用文法符号的语义属性表示：变量有类型、值、存放地址，表达式有类型、值、地址。

* **语义属性与属性记法**

    * 给上下文无关文法中的文法符号设置语义属性，用属性表示语法成分对应的语义信息。

    * 记法 $X.a$：属性 $a$ 在某个标号为 $X$ 的分析树节点上的值。

    * 属性值由与文法符号所在产生式相关联的语义规则算出：先构建输入串的语法分析树，再利用产生式上的规则算出各节点属性值。

* **语法制导定义（Syntax-Directed Definition，SDD）**

    * > **定义**：对上下文无关文法的推广——每个文法符号关联一个语义属性集合，每个产生式关联一组语义规则，规则用来计算该产生式中各文法符号的属性值。

    * 规格说明层面：只说明属性的值怎么互相定义，不显式说明计算顺序。

    * 例：$D \to T\,L$ 配 $L.inh = T.type$；$T \to \text{int}$ 配 $T.type = \text{int}$；$L \to L_1,\text{id}$ 配 $L_1.inh = L.inh$ 与 $addType(\text{id}.lexeme, L.inh)$。

* **语法制导翻译方案（Syntax-Directed Translation Scheme，SDT）**

    * > **定义**：在产生式右部嵌入程序片段的上下文无关文法，这些程序片段称为语义动作，按惯例放在花括号内。

    * 动作位置决定执行时间：动作放在 $T$ 之后，表示分析出 $T$ 后即可用 $T$ 的 type 算 $L$ 的 inh；动作放在右部末尾，表示右部符号全部分析完才算左部属性；动作放在 $L_1$ 之前，表示分析 $L_1$ 前即可用 $L$ 的属性算 $L_1$ 的 inh。

    * 一句话：一个语义动作在产生式中的位置，决定了这个动作的执行时间。

| 对比项 | SDD | SDT |
| :--- | :--- | :--- |
| 形态 | 产生式配一组语义规则 | 产生式右部嵌入语义动作 |
| 抽象层次 | 高层次规格说明 | 具体实施方案 |
| 计算顺序 | 隐含在依赖关系里，不显式说明 | 由动作所在位置显式指明 |
| 回答的问题 | 属性的值怎么互相定义 | 什么时候算、按什么次序算 |

## 属性的两种来源

### 综合属性与继承属性

* **综合属性（synthesized attribute）**

    * > **定义**：节点 $N$ 上非终结符 $A$ 的综合属性，只能通过 $N$ 的子节点或 $N$ 本身的属性值来定义。

    * 例：$E \to E_1 + T$ 配 $E.val = E_1.val + T.val$，规则右边用的是两个儿子 $E_1$ 与 $T$ 的 val，父值由儿子的值攒出来。

    * 终结符也有综合属性，值由词法分析器提供，SDD 里不必为终结符写计算属性值的语义规则。

    * 信息流向自底向上；典型用途是算出本节点的结果。

* **继承属性（inherited attribute）**

    * > **定义**：节点 $N$ 上非终结符 $A$ 的继承属性，只能通过 $N$ 的父节点、$N$ 的兄弟节点或 $N$ 本身的属性值来定义。

    * 例：$D \to T\,L$ 配 $L.inh = T.type$，$T$ 与 $L$ 互为兄弟，$L$ 的 inh 由兄弟 $T$ 的 type 定义。

    * 终结符没有继承属性：它在词法分析器那里拿到的值已经归到综合属性里，不再另开一个继承属性。

    * 信息流向自上而下、从左到右；典型用途是把上下文、环境传下去。

| 对比项 | 综合属性 | 继承属性 |
| :--- | :--- | :--- |
| 值从哪来 | 子节点、自身 | 父节点、兄弟节点、自身 |
| 信息流向 | 自底向上 | 自上而下、从左到右 |
| 终结符 | 有（词法值） | 没有 |
| 典型用途 | 算出本节点的结果 | 把上下文、环境传下去 |

### 注释分析树与属性文法

* **注释分析树（annotated parse tree）**

    * 每个节点都带属性值的分析树；属性值算出来后就贴在分析树上。

    * 综合属性的例子：对以 $n$ 结尾的表达式求值，digit 的 lexval 由词法分析器给出，$E$、$T$、$F$ 各设 val；输入 $3*5+4n$ 时自下而上得到 3、5、15、4，根 $E$ 的 val 为 19。

    * 继承属性的例子：`real a, b, c` 的声明 SDD，$T.type$ 为 real，$L.inh$ 从根沿分析树一路下传，三个标识符都记成 real。

* **属性文法（attribute grammar）**

    * > **定义**：没有副作用的 SDD。属性文法的规则仅通过其他属性值和常量来定义一个属性值。

    * 判定：规则右边除了别的属性和常量，不许有别的东西；一旦出现 `print`、`addType` 这类动作，就不是纯粹在“定义一个值”，那就不算属性文法。

    * 把 $L \to E\,n$ 的 `print(E.val)` 换成 $L.val = E.val$，整张表不再有副作用，这个 SDD 就成为属性文法。

* **虚综合属性**

    * 副作用式规则（打印运算结果、往符号表填记录）不产生新值，但用到了子节点的属性，可以看作对产生式左部符号的虚综合属性做定义的规则。

    * 作用：让没有返回值的动作也能在依赖图里被表示成一个节点。

## 依赖图与求值顺序

### 依赖图

* **依赖图（dependency graph）**

    * > **定义**：描述分析树中节点属性之间依赖关系的有向图。对分析树中每个标号为 $X$ 的节点的每个属性 $a$，依赖图中都有一个节点与之对应；若属性 $X.a$ 依赖属性 $Y.b$，就有一条从 $Y.b$ 指向 $X.a$ 的有向边。

    * 摆法约定：继承属性摆在所对应节点的左边，综合属性摆在右边。

    * 三条构造线索：$D \to T\,L$ 的 $L.inh = T.type$ 给出一条 $T.type \to L.inh$；$L \to L_1,\text{id}$ 的第一条规则给出父 $L.inh \to$ 子 $L_1.inh$；同一条产生式的 `addType` 按虚综合属性设节点，从 $L.inh$ 与 $id.lexeme$ 各引一条边指向它。

    * 每个 $L$ 节点一列：横向箭头是继承属性沿分析树向下传，竖向是该节点的 inh 与对应 id 的 lexeme 共同决定虚综合属性。

* **依赖关系的读法**

    * 要对分析树节点的某个属性求值，必须先求出这个属性值所依赖的所有属性值。

    * 这条约束把“求值顺序”变成了一个纯粹的图论问题。

### 拓扑排序与循环依赖

* **拓扑排序（topological sort）**

    * > **定义**：节点序列 $n_1,n_2,\dots,n_k$，若依赖图中有一条从 $n_i$ 到 $n_j$ 的边，则 $n_i$ 排在 $n_j$ 的前面；这样的排序把有向图变成了一个线性排序。

    * 检查办法：依赖者的序号都大于被依赖者的序号，算到某个属性时，它依赖的值一定都已经算完。

    * 拓扑排序不唯一：互不依赖的节点可以任意调换次序，例如四个叶子上的属性、都依赖同一节点的两个属性、同层互不依赖的两个属性。

* **循环依赖**

    * 例：$A \to B$ 配 $A.s = B.i$ 与 $B.i = A.s$；$s$ 只能是 $A$ 的综合属性，$i$ 只能是 $B$ 的继承属性，两条规则互指，依赖图成环。

    * > **结论**：依赖图无环，至少存在一个拓扑顺序；有环，一个都没有。

    * 给定一个 SDD，很难判定是否存在某棵分析树使属性之间出现循环依赖；有用子类（S 属性、L 属性）不允许产生带环的依赖图。

### 求值性质

* **纯综合属性的顺序**

    * 只具有综合属性的 SDD，可以按任何自底向上的顺序计算属性值。

    * 理由：每个节点的值只依赖子节点，自底向上走到哪儿，儿子总是先算完。

* **继承与综合混合**

    * 同时具有继承属性和综合属性的 SDD，不能保证存在一个顺序把各节点属性都算出来。

    * 能与自顶向下、自底向上分析过程高效配合的两类子类是 S 属性定义与 L 属性定义。

## S 属性定义与 L 属性定义

### S 属性定义

* **S 属性的 SDD（S-SDD）**

    * > **定义**：仅仅使用综合属性的 SDD，也叫 S 属性定义。

    * 每个节点的属性值只依赖子节点，可按分析树节点的任何自底向上顺序求值。

    * 可以在自底向上的语法分析过程中实现。

* **典型例子**

    * $3*5+4n$ 的求值 SDD 所有属性都是综合属性，每个值都靠子节点算出来。

    * 这个性质在讲 SDT 时会变成一条很省事的实施路线：动作一律放产生式末尾。

### L 属性定义的条件

* **L 属性定义（L-SDD）**

    * > **定义**：每个属性要么是综合属性，要么是满足下列条件的继承属性——对产生式 $A \to X_1X_2\dots X_n$，$X_i$ 的继承属性仅依赖：① 父节点 $A$ 的继承属性；② $X_i$ 左边的符号 $X_1,\dots,X_{i-1}$ 的属性，不能依赖 $X_i$ 右边的符号 $X_{i+1},\dots,X_n$ 的属性；③ $X_i$ 本身的属性，但 $X_i$ 的全部属性不能在依赖图中形成环。

    * 直观含义：依赖图的边可以从左指向右，不能从右指向左，所以叫 L 属性；L 取 left 的首字母。

    * 第 ② 条最要紧：只许往左看，不许往右看。左边和上边的信息在分析到 $X_i$ 之前已经拿到，右边的还没分析出来，依赖它就是依赖未来。

    * 包含关系：每个 S 属性定义都是 L 属性定义。S 属性定义只有综合属性，而 L 属性定义对综合属性没有任何限制。

* **限制的用意**

    * > **易错点**：$X_i$ 的继承属性只能依赖父节点 $A$ 的**继承**属性，不能依赖 $A$ 的**综合**属性——$A$ 的综合属性本身可以依赖子节点的属性（当然也包括子节点的继承属性），若子节点的继承属性再回头依赖 $A$ 的综合属性，这一来一回就成环了。

    * 这条限制不是抠字眼，是在防环。

### 判定练习

* **合格的项文法**

    * 产生式与规则：$T \to F\,T'$ 配 $T'.inh = F.val$、$T.val = T'.syn$；$T' \to *\,F\,T_1'$ 配 $T_1'.inh = T'.inh \times F.val$、$T'.syn = T_1'.syn$；$T' \to \varepsilon$ 配 $T'.syn = T'.inh$；$F \to \text{digit}$ 配 $F.val = \text{digit}.lexval$。

    * 判定：$T'.inh$ 依赖左兄弟的 $F.val$；$T_1'.inh$ 依赖父节点的 $T'.inh$ 与左兄弟的 $F.val$，都只往左、往上看，不违反 L 条件。

    * > **结论**：这个 SDD 是 L 属性定义。

* **不合格的例子**

    * 右部 $L$、$M$、$R$、$Q$ 各带一个继承属性：$L.i$ 依赖父亲 $A$ 的继承属性；$M.i$ 依赖左兄弟 $L$ 的综合属性 $L.s$；$R.i$ 依赖父亲 $A$ 的继承属性；$Q.i$ 依赖右兄弟 $R$ 的综合属性 $R.s$。

    * 前三条合规；$Q.i$ 依赖它右边兄弟 $R$ 的综合属性，越界。

    * > **结论**：这一条规则就足以让整个 SDD 不算 L 属性定义；判定 L-SDD 不需要逐条挑毛病，找到一条越界的继承属性就可以收工。

## 从 SDD 到 SDT 的转换

### S 属性定义的动作位置

* **转换规则**

    * 把每个语义规则都放在所在产生式右部的最后。

    * 理由：综合属性要等所有子节点分析完毕才算，右部全部分析完才谈得上计算父节点的综合属性。

    * 适用组合：基本文法可用 LR 分析技术、SDD 是 S 属性的，SDT 可以在语法分析过程中实现。

* **表达式求值的 SDT**

    * 规则内容一个字没改，变的只是位置：原来规则列在产生式旁边的表里，现在嵌进产生式右部，成了文法的一部分。

    * `L → E n { print(E.val) }`、`E → E1 + T { E.val = E1.val + T.val }`、`E → T { E.val = T.val }`、`T → T1 * F { T.val = T1.val * F.val }`、`T → F { T.val = F.val }`、`F → ( E ) { F.val = E.val }`、`F → digit { F.val = digit.lexval }`。

### L 属性定义的动作位置

* **两条转换规则**

    * 计算某个非终结符号 $A$ 的继承属性的动作，插入到产生式右部中紧靠在 $A$ 的本次出现之前的位置。

    * 计算一个产生式左部符号的综合属性的动作，放置在这个产生式右部的最右端。

    * 道理仍是位置决定执行时间：继承属性要在符号被分析之前准备好，动作必须站在它前面；综合属性要等右部全部分析完，动作只能站到最后。

* **项文法的转换结果**

    * `T → F { T'.inh = F.val } T' { T.val = T'.syn }`

    * `T' → * F { T1'.inh = T'.inh * F.val } T1' { T'.syn = T1'.syn }`

    * `T' → ε { T'.syn = T'.inh }`；`F → digit { F.val = digit.lexval }`

    * 第一条产生式：$T'.inh$ 是右部符号 $T'$ 的继承属性，动作插在 $F$ 和 $T'$ 之间；$T.val$ 是左部符号的综合属性，动作追加到末尾。

### 可实现的组合

* **两种落地条件**

    * 基本文法可用 LR 技术且 SDD 为 S 属性：SDT 在 LR 分析过程中实现，归约时执行相应语义动作。

    * 基本文法可用 LL 技术且 SDD 为 L 属性：SDT 在 LL 分析过程中实现，继承属性动作在符号出现前执行，综合属性动作在产生式末尾执行。

    * L 属性定义的基本文法若是 LL 文法，其 SDT 既能在 LL 分析过程中实现，也能在 LR 分析过程中实现。

* **LL(1) 的确认**

    * 判据：具有相同左部的产生式，其候选集（SELECT 集）互不相交。

    * 项文法中左部为 $T'$ 的两条：$T' \to *\,F\,T_1'$ 的 SELECT 集是 `{*}`；$T' \to \varepsilon$ 的 SELECT 集是 $\text{FOLLOW}(T')$，只有输入结束符 `$`。

    * $\text{FOLLOW}(T')$ 的来历：$T$ 是开始符号，$T'$ 出现在 $T \to F\,T'$ 的末尾，所以 $\text{FOLLOW}(T')$ 包含 $\text{FOLLOW}(T)$；第二条产生式以 $T_1'$ 结尾，$\text{FOLLOW}(T_1')$ 也并进来，仍然只有 `$`。

    * 两组 SELECT 集一个是 `{*}`、一个是 `{$}`，互不相交，所以这是 LL(1) 文法。

## 自底向上：S 属性在 LR 分析栈上的执行

### 栈记录的扩展

* **附加属性域**

    * 在 LR 分析栈的记录里加一个附加的域，专门存综合属性值。

    * 属性都很小时，直接把栈记录做大，塞得下所有属性就行；有些字段永远用不上也不会有太大问题。

    * 属性大小没有限制时（比如字符串），把属性值放到栈外一块较大的公共存储区，栈记录里只存指向它的指针。

    * 选择标准是“属性大小有没有上限”：定长小属性直接寻址；变长属性放外面，避免每条记录都被最长的属性撑爆。

* **归约时机**

    * S 属性 SDT 的所有语义动作都在产生式右部末尾，只有右部所有符号都分析出来才执行动作。

    * LR 分析恰好有一个“右部所有符号都分析完了”的时刻——归约；归约时执行相应语义动作，时机天然对得上。

### 归约时的栈改写

* **位置规律**

    * 产生式 $A \to XYZ$ 归约前，栈顶 `stack[top]` 是 $Z$，`stack[top-1]` 是 $Y$，`stack[top-2]` 是 $X$，三个属性值分别落在各自记录的 val 字段。

    * 归约时 $XYZ$ 一起出栈，$A$ 进入 $X$ 原来的位置：`stack[top-2].symbol` 变成 $A$，$A$ 的属性值存进 `stack[top-2].val`，随后 `top-2` 成为新栈顶。

    * $A.val = f(X.val, Y.val, Z.val)$ 改写成可执行形式就是 `stack[top-2].val = f(stack[top-2].val, stack[top-1].val, stack[top].val)`。

* **写回位置**

    * > **注意**：结果写回 `top-2` 而不是别处，因为归约是把右部这一串整体替换成左部符号，新符号占的正是右部最左那个符号的格子。

### 桌面计算器走查

* **设置**

    * 输入串 `3 * 5 + 4`；初始状态栈里是 0 号状态，符号栈里是栈底标记 `$`，输入指针指向 3。

    * 只有 $T \to T*F$ 与 $E \to E+T$ 真正改属性值，其余归约都是“值不动”。

| 步 | 符号栈（属性值） | 剩余输入 | 动作 |
| :---: | :--- | :--- | :--- |
| 0 | `$` | `3 * 5 + 4 $` | 初始格局 |
| 1–3 | `$ T(3)` | `* 5 + 4 $` | 移进 digit(3)，归约 digit → F → T，值不动 |
| 4–6 | `$ T(3) * F(5)` | `+ 4 $` | 移进 `*`、digit(5)，归约 digit → F |
| 7 | `$ T(15)` | `+ 4 $` | 归约 $T \to T*F$，3 × 5 = 15 写回 `top-2` |
| 8–11 | `$ E(15) + T(4)` | `$` | 归约 T → E，移进 `+`、digit(4)，再归约 digit → F → T |
| 12 | `$ E(19)` | `$` | 归约 $E \to E+T$，15 + 4 = 19 写回 `top-2` |
| 13 | `$ E(19)` | `$` | 接受，句子分析完毕 |

* **关键归约**

    * 第 7 步：栈顶三个符号依次是 $T(3)$、`*`、$F(5)$，动作取 `stack[top-2].val` 乘 `stack[top].val`，15 写回 `stack[top-2].val`，三个符号连同状态一起出栈，$T$ 进栈。

    * 第 12 步：栈顶三个符号是 $E(15)$、`+`、$T(4)$，15 与 4 相加，19 写回 `stack[top-2].val`，三个符号出栈，$E$ 进栈；0 号状态遇 $E$ 转 1 号状态，1 号状态遇 `$` 成功接收。

    * > **结论**：分析结束时，文法开始符号 $E$ 的属性值就是整个表达式的值 19；语法分析走完，语义值也顺手算完，没有额外的一遍。

## 非递归预测分析中的翻译

### 三类记录

* **符号记录**

    * 放文法符号本身与它的继承属性。

    * 继承属性只依赖父亲和左兄弟，$A$ 即将出现的那一刻就能算：这时 $A$ 还没展开，子树一个符号都没进栈，但算继承属性要的信息已经齐了。

* **综合记录 $A_{syn}$**

    * 专存 $A$ 的综合属性，位置紧贴在 $A$ 本身记录的下面（更靠栈底）。

    * $A$ 一旦被产生式展开，$A$ 本身记录就要出栈，把位置让给右部的符号；综合属性得一直留到子树分析完，压在下面，$A$ 出栈时它自然留在栈里等结果。

    * > **结论**：$A$ 出栈，$A$ 的综合记录不能出栈。

* **动作记录 `action`**

    * 里面存一个指针，指向将要被执行的语义动作代码。

    * 三类记录凑齐，栈同时装得下符号与继承属性、综合属性、待执行动作。

### 动作符号与栈格局

* **动作符号**

    * 把 SDT 里的语义动作起名 $a_1$ 到 $a_6$，用这些符号把方案里的动作逐块替换掉，得到 `T -> F a1 T' a2`、`T' -> * F a3 T' a4`、`T' -> a5`、`F -> digit a6` 四条产生式。

    * 改写后的 SDT 可看成一类特殊的上下文无关文法，符号只有三类：终结符（`*`、`digit`）、非终结符（$T$、$T'$、$F$）、动作符号。

    * 动作符号在栈上占一条动作记录；终结符和非终结符按前面的规则占一条或两条记录。

* **栈的排布**

    * 自顶向下分析先处理最左符号，所以栈底在右侧、栈顶在左侧。

    * $T$ 没有继承属性，本身记录的属性字段为空；$T$ 有综合属性，后面跟一条 $T_{syn}$，用来存 $T$ 的 value。

    * 展开 $T \to F\,a_1\,T'\,a_2$ 后，栈从顶到底为 `F | F_syn | a1 | T'(in) | T'_syn | a2 | T_syn`。

### 乘法表达式走查

* **前段**

    * $F \to \text{digit}\,a_6$：`digit` 匹配 3，出栈前把词法值备份进 $a_6$；$a_6$ 把栈顶的属性值复制到 `top-1` 的 $F_{syn}$，$F$ 的 value 为 3。

    * $F_{syn}$ 出栈前把值备份给下面的 $a_1$；$a_1$ 执行时把栈顶写进 `top-1`，也就是 $T'$ 记录里的 `in`，得到 $T'$ 的继承属性 3。

* **中段**

    * $T'$ 遇 `*` 选第二条产生式，$T'$ 出栈，`*`、$F$、$a_3$、$T'$、$a_4$ 进栈；$F$ 与 $T_1'$ 各带一条综合记录，一共七条，新栈顶比原 top 高 6。

    * 从原 top 往深处数：$a_4$ 落在 top，$T_1'_{syn}$ 在 top+1，$T_1'$ 在 top+2，$a_3$ 在 top+3；$T'$ 出栈前把 `in` 备份到 `top+3` 的 $a_3$。

    * `*` 匹配、$F$ 算出 5、$a_6$ 复制、$F_{syn}$ 把值交给 $a_3$；$a_3$ 算 $3 \times 5 = 15$，写进 $T_1'$ 的 `in`。

* **后段**

    * $T_1'$ 遇 `$` 选 $T' \to \varepsilon$：$a_5$ 落在 $T_1'$ 原来的位置（top），这次“备份”等于把值留在原地，$a_5$ 把继承属性复制成综合属性，仍写进 `top-1`。

    * 一路往上：$T_1'_{syn}$ 出栈交给 $a_4$，$a_4$ 算 $T'$ 的 syn；$T'_{syn}$ 出栈交给 $a_2$，$a_2$ 算 $T$ 的 value；$T_{syn}$ 出栈，栈空，输入指针停在末尾，开始符号的 value 为 15。

* **偏移的相对性**

    * 每个动作记录要用的值，都来自它左边那些符号的记录；在栈里这些记录压在更靠栈顶的一侧。

    * > **易错点**：把某个绝对位置背下来，换一条产生式就错。所有偏移都是相对当时的栈顶算的，时刻一变就要重数。

### 每个符号的执行代码

* **两种代码**

    * 综合记录出栈时，把值复制给它下面那个特定的动作记录。

    * 变量展开、本身记录出栈时，如果带继承属性，就把继承属性值复制给它下面那个特定的动作记录；属性字段空的记录没有代码。

    * > **结论**：一个 SDT 定下来，其中每个符号对应的执行代码也就定下来了——只需要知道它下面紧挨着谁、偏移是多少。

* **第一条产生式的六条记录**

    | 记录 | 存什么 | 执行代码 |
    | :--- | :--- | :--- |
    | $F$ | 空（$F$ 没有继承属性） | 无 |
    | $F_{syn}$ | $F$ 的 value | 出栈时复制到 `top-1`，即 $a_1$ |
    | $a_1$ | $F$ 的 value 备份 | 把栈顶复制到 `top-1`，即 $T'$ 记录里的 `in` |
    | $T'$ | $T'$ 的 `in` | 展开时按所选产生式备份：选第二条送 `top+3` 的 $a_3$；选第三条原地不动 |
    | $T'_{syn}$ | $T'$ 的 syn | 出栈时复制到 `top-1`，即 $a_2$ |
    | $a_2$ | $T'$ 的 syn 备份 | 把栈顶复制到 `top-1`，即 $T_{syn}$ |

    * 第二条产生式同理：右部七条记录，$F_{syn}$ 出栈时下面紧挨 $a_3$，$T_1'_{syn}$ 出栈时下面紧挨 $a_4$，都按 `top-1` 交给动作记录。

    * 第三条产生式里 $a_5$ 落在 top，真正要执行的一步是把 `in` 复制成 `syn`，写进 `top-1`；第四条产生式里 `digit` 出栈前把词法值备份给 $a_6$，$a_6$ 再把栈顶复制到 `top-1` 的 $F_{syn}$。

## 递归预测分析中的翻译

### 过程升级为函数

* **函数签名**

    * 每个非终结符 $A$ 造一个函数：$A$ 的每个继承属性对应函数的一个形参，函数的返回值就是 $A$ 的综合属性。

    * $T'$ 有一个继承属性 `inh`、一个综合属性 `syn`，函数收一个形参 `T'.inh`，返回 `T'.syn`。

    * 识别逻辑原样保留：按 token 选产生式、匹配终结符、递归调用；扩展的部分全在“怎么把属性接进来、送出去”上。

* **局部变量**

    * 右部出现的每个文法符号的每个属性，都要有一个局部变量接着：$F$ 只有综合属性 `val`，就设 `F.val`；$T_1'$ 继承和综合都有，就设 `T1'.inh` 与 `T1'.syn`。

    * 属性在树上的每一条传递边，在递归下降里就是一次参数传递或一次赋值；原来要靠属性记录保存的中间值，现在落在函数的局部变量里。

### 四条落地规矩

* **四条规矩**

    * 为每个非终结符 $A$ 构造一个函数：$A$ 的每个继承属性对应一个形参，返回值是 $A$ 的综合属性。

    * 对出现在 $A$ 的产生式中的每个文法符号的每个属性，设置一个局部变量。

    * $A$ 的代码根据当前输入决定用哪条产生式。

    * 与每条产生式有关的代码，从左到右考虑右部的词法单元、非终结符和语义动作。

* **右部三类成分的处理**

    * 带综合属性 $x$ 的词法单元 $X$：把 $x$ 的值存进局部变量 `X.x`，然后生成一个匹配 $X$ 的调用，并前移输入。

    * 非终结符 $B$：生成赋值语句 $c = B(b_1,b_2,\dots,b_k)$，$b_1$ 到 $b_k$ 是代表 $B$ 继承属性的变量，$c$ 是代表 $B$ 综合属性的变量。

    * 语义动作：代码复制进分析器，属性引用改成相应的变量引用。

* **主函数**

    * 只做一件事：调用开始符号 $T$ 的函数。

    * $T$ 有综合属性 `val`，声明一个局部变量 `tval` 把返回值接住，整个语义翻译器就完整了。

## L 属性定义的自底向上翻译

### 冲突与标记非终结符

* **时机冲突**

    * 归约要等整个右部都进栈、能认出这条产生式了才发生。

    * 内嵌动作却必须在它右边的符号还没处理之前就把值算出来——右边那些符号的继承属性还等着用它。

    * 一个要求早算，一个只能晚做，硬碰硬；想让 L 属性定义走 LR 分析，第一步不是写代码，是改文法。

* **标记非终结符**

    * 把内嵌动作换成一个新非终结符 $M$，第二个换成 $N$，这类符号叫标记非终结符；每个标记配一条空产生式 $M \to \varepsilon$、$N \to \varepsilon$。

    * 空产生式右部什么都没有，但可以挂一个语义动作，这个动作干的事和被它替换掉的内嵌动作一模一样。

    * 例：$N$ 替换的动作要算 $T'$ 的继承属性，计算时用到 $T'$ 的继承属性和 $F$ 的 val；把这两个属性复制成 $N$ 的两个继承属性 $N.i_1$、$N.i_2$，在空产生式的动作里按老办法算，算出的结果作为 $N$ 的综合属性。

    * > **结论**：如果一个文法是 LL 的，标记非终结符可以插到产生式右部的任何位置，得到的文法仍然是 LR 文法。

* **取值的依据**

    * > **提示**：空产生式的动作不是凭空取属性，它取的是栈上某个固定偏移处的值；整个技巧的命门就在“已知位置”这四个字上，偏移一旦算错，取到的就是别的符号的属性。

### LR 栈走查

* **设置**

    * 输入 `3 * 5`，初始状态栈里只有 0 号状态，符号栈里只有栈底标记 `$`，输入指针指向 3。

    * 状态栈顶在右，符号后面括号里是属性值。

| 状态栈（顶在右） | 符号栈（带属性值） | 剩余输入 | 动作 |
| :--- | :--- | :--- | :--- |
| `0` | `$` | `3 * 5 $` | 移进 `digit`，转 3 |
| `0 3` | `$ d(3)` | `* 5 $` | 按 $F \to \text{digit}$ 归约，转 2 |
| `0 2` | `$ F(3)` | `* 5 $` | 按 $M \to \varepsilon$ 归约，转 4 |
| `0 2 4` | `$ F(3) M(3)` | `* 5 $` | 移进 `*`，转 6 |
| `0 2 4 6` | `$ F(3) M(3) *` | `5 $` | 移进 `digit`，转 3 |
| `0 2 4 6 3` | `$ F(3) M(3) * d(5)` | `$` | 按 $F \to \text{digit}$ 归约，转 7 |
| `0 2 4 6 7` | `$ F(3) M(3) * F(5)` | `$` | 按 $N \to \varepsilon$ 归约，转 8 |
| `0 2 4 6 7 8` | `$ F(3) M(3) * F(5) N(15)` | `$` | 按 $T' \to \varepsilon$ 归约，转 9 |
| `0 2 4 6 7 8 9` | `$ F(3) M(3) * F(5) N(15) T'(15)` | `$` | 按 $T' \to *\,F\,N\,T'$ 归约，转 5 |
| `0 2 4 5` | `$ F(3) M(3) T'(15)` | `$` | 按 $T \to F\,M\,T'$ 归约，转 1 |
| `0 1` | `$ T(15)` | `$` | 接受 |

* **两步精髓**

    * $M$ 的归约：2 号状态遇 `*`，按空产生式归约出 $M$；$M$ 的值等于 $F$ 的值，$F$ 是 $M$ 的左兄弟、此刻在栈顶，把栈顶的值写到 `top+1`，得 $M = 3$；$M$ 在产生式里位于 $T'$ 左边，这个 3 事实上就是 $T'$ 的 `inh`。

    * $N$ 的归约：7 号状态遇 `$`，$N$ 的值等于 $T'$ 的 `inh` 乘 $F$ 的 val；$F$ 在 $N$ 左边、此刻在栈顶，取 `top`；$T'$ 将占据 `*` 的位置，而 $T'$ 的继承属性存在紧贴 $T'$ 之下的标记非终结符记录里，也就是 $M$ 那条，此刻在 `top-2`；乘出 15，写进 `top+1`。

    * > **易错点**：算 $N$ 时最容易被 `top-1` 骗过去。此刻栈顶是 $F$，`top-1` 是 `*`，`top-2` 才是 $M$ 那条记录；$T'$ 还没进栈，它只是“将要”占据 `*` 的位置，继承属性的记录要按这个将来的位置往回数。

* **后续归约**

    * $T' \to \varepsilon$：综合属性等于继承属性，继承属性就存在紧贴 $T'$ 之下的记录里，此刻正在栈顶，把栈顶的值赋给 `top+1` 的 $T'$，得 15。

    * $T' \to *\,F\,N\,T'$：四个符号出栈，$T'$ 进栈落在 `*` 原来的位置（`top-3`），综合属性等于最右儿子的属性，即栈顶的 15。

    * $T \to F\,M\,T'$：$T$ 落在 $F$ 的位置，综合属性等于最右儿子 $T'$ 的值，仍为 15；0 号状态遇 $T$ 转到 1 号接收状态，分析成功。

### 六段执行代码与一般配方

* **六段执行代码**

| 产生式 | 归约后新符号的位置 | 执行代码 |
| :--- | :--- | :--- |
| $T \to F\,M\,T'$ | $T$ 落在 $F$ 的位置，即 `top-2` | 把栈顶（$T'$ 的属性）复制到 `top-2` |
| $M \to \varepsilon$ | $M$ 落在 `top+1` | 把栈顶（$F$ 的属性）复制到 `top+1` |
| $T' \to *\,F\,N\,T'$ | $T'$ 落在 `*` 的位置，即 `top-3` | 把栈顶（最右儿子 $T'$ 的属性）复制到 `top-3` |
| $N \to \varepsilon$ | $N$ 落在 `top+1` | `top-2`（$T'$ 的 inh）乘 `top`（$F$ 的 val），结果送 `top+1` |
| $T' \to \varepsilon$ | $T'$ 落在 `top+1` | 把栈顶（$T'$ 的 inh）复制到 `top+1` |
| $F \to \text{digit}$ | $F$ 落在 `digit` 的位置 | 栈顶属性字段不变 |

* **一般配方**

    * 给定以 LL 文法为基础的 L 属性定义，先构造 SDT：在各非终结符之前放语义动作算继承属性，在产生式后端放语义动作算综合属性；动作位置由属性依赖关系定，不由 LR 分析的方便定。

    * 对每个内嵌语义动作，向文法中引入一个标记非终结符替换它；每个位置配一个不同的标记，任意标记 $M$ 都配一条产生式 $M \to \varepsilon$。

    * 把动作搬进空产生式：若 $M$ 在某个产生式中替换了动作 $a$，就对 $a$ 做改造得到 $a'$；$a'$ 把 $a$ 需要的、来自左部 $A$ 或右部前缀 $\alpha$ 中符号的任何属性，统统作为 $M$ 的继承属性复制进来，再按 $a$ 原来的算法计算，结果作为 $M$ 的综合属性。

    * 这样改造之后，SDT 就能在 LR 分析过程中实现。

* **三条路的统一**

    * 非递归预测分析：属性放在分析栈的记录里，靠“综合记录压在本身记录之下”维持先后。

    * 递归预测分析：属性放在函数的形参、返回值和局部变量里，靠调用链维持方向。

    * LR 分析：属性放在符号栈的记录里，靠归约时的固定偏移取用。

    * 属性值永远跟着“将要成为某个符号的那条记录”走，谁先算谁后算由属性之间的依赖关系决定。

## 类型表达式

### 构造符

* **类型表达式**

    * > **定义**：由基本类型、类型名，以及类型构造符作用于类型表达式构成。

    * 基本类型 `integer`、`real`、`char`、`boolean` 本身就是合法的类型表达式。

    * 给类型表达式命名，类型名也是类型表达式；一个记录类型只需定义一次、起个名字，之后在数组、指针里引用这个名字即可，不必把整个结构一遍遍展开。

* **数组构造符 `array`**

    * 设 $T$ 是类型表达式、$I$ 是整数，$\text{array}(I,T)$ 表示包含 $I$ 个元素、每个元素类型为 $T$ 的数组。

    * 三个整型的数组：$\text{array}(3,\text{int})$。

    * $2 \times 3$ 二维整型数组：$\text{array}(2,\text{array}(3,\text{int}))$，是“数组的数组”，不是“一个装 6 个整型的数组”。

    * 外层 `array` 管第一维，内层 `array` 管第二维；维数从类型表达式的嵌套层数看出，不是从某个“维度属性”看出。

* **指针构造符 `pointer`**

    * $T$ 是类型表达式，$\text{pointer}(T)$ 表示“指向类型 $T$ 的指针”。

* **笛卡尔乘积构造符 $\times$**

    * $T_1$、$T_2$ 是类型表达式，$T_1 \times T_2$ 也是类型表达式。

* **函数构造符 $\rightarrow$**

    * $T_1 \times T_2 \times \dots \times T_n \rightarrow R$ 表示函数类型，$T_1$ 到 $T_n$ 是参数类型，$R$ 是返回值类型。

* **记录构造符 `record`**

    * $\text{record}(N_1 \times T_1 \times N_2 \times T_2 \times \dots \times N_n \times T_n)$ 表示含 $n$ 个字段的记录，字段名为 $N_1$ 到 $N_n$，字段类型为 $T_1$ 到 $T_n$。

### 类型名与实例

* **三个名字的类型表达式**

    * `stype` 是记录名：`record(name × array(8, char) × score × integer)`，两个字段分别是长度为 8 的字符数组与整型。

    * `table` 是数组名：`array(50, stype)`，50 个元素，每个元素的类型是 `stype`。

    * `p` 是指针：`pointer(stype)`，指向 `stype`。

    * 后两个表达式都引用已定义的 `stype`；没有类型名，`table` 的类型表达式就得把整个记录结构再抄一遍。

* **类型宽度（width）**

    * > **定义**：该类型在运行时刻所需要的存储单元的数量。

    * 根据一个名字的类型表达式，可以知道这个类型在运行时刻需要多少个存储单元；编译时刻就用宽度为每个名字分配一个相对地址。

    * 名字的类型和相对地址最终都保存在符号表记录里；声明语句往里写，赋值语句从里读。

## 声明语句的翻译

### 基础文法与属性

* **四个非终结符**

    * $B$：生成基本类型关键字，取 basic 的首字母，定义为 `int` 或 `real`。

    * $C$：生成一个数组下标表达式序列，也就是 `[2][3]` 这种跟在类型后面的尾巴。

    * $T$：表示标识符的类型；$C$ 取空串时 $T$ 生成基本变量，$C$ 不取空时生成数组类型，$T$ 还可定义成指针关键字连接一个 $T$。

    * $D$：生成声明序列，每个声明由 $T$、`id`、分号构成；$D$ 构成程序 $P$。

* **产生式**

```text
B → int | real
C → ε | [ number ] C
T → B C | pointer T
D → T id ; D | ε
P → D
```

* **属性与辅助成分**

    * $B$、$C$、$T$ 各设两个综合属性：`type` 表示对应的类型，`width` 表示这个类型的宽度。

    * 数值假设：整型变量占 4 字节，实型变量占 8 字节，指针占 4 字节；这几个数不是语言规定，换机器、换模型就可能变。

    * `offset`：下一个可用的相对地址，初始时刻为 0。

    * $t$ 与 $w$：把类型和宽度从语法分析树的 $B$ 节点传递到对应产生式 $C \to \varepsilon$ 的节点。

    * `enter(name, type, offset)`：在符号表中为名字 `name` 创建记录，类型设为 `type`，相对地址设为 `offset`。

    * 每识别出一个声明就调 `enter` 建记录，然后把 `offset` 增加 $T.width$；下一个声明的名字从 $\text{offset} + T.\text{width}$ 开始分配。

### 九条产生式

* **产生式与动作**

| 编号 | 产生式 | 语义动作 |
| :---: | :--- | :--- |
| 1 | $P \to A\,D$ | $A$：`offset := 0` |
| 2 | $D \to T\ \text{id}\ ;\ A\ D$ | `enter(id.name, T.type, offset)`；`offset := offset + T.width` |
| 3 | $D \to \varepsilon$ | 无 |
| 4 | $T \to B\ A\ C\ A$ | 第一个 $A$：`t := B.type`、`w := B.width`；第二个 $A$：`T.type := C.type`、`T.width := C.width` |
| 5 | $T \to \text{pointer}\ T_1$ | `T.type := pointer(T1.type)`；`T.width := 4` |
| 6 | $B \to \text{int}\ A$ | `B.type := int`；`B.width := 4` |
| 7 | $B \to \text{real}\ A$ | `B.type := real`；`B.width := 8` |
| 8 | $C \to \varepsilon\ A$ | `C.type := t`；`C.width := w` |
| 9 | $C \to [\ \text{number}\ ]\ C_1\ A$ | `C.type := array(number.lexval, C1.type)`；`C.width := number.lexval * C1.width` |

* **产生式 4 的关节**

    * 表里的 $A$ 是动作符号，不是文法符号；它像文法符号一样进栈，轮到它在栈顶，就执行冒号后面那段语义动作。

    * 第一个 $A$ 在 $B$ 归约完之后立刻执行，把 $B$ 的 `type`、`width` 抄进 $t$、$w$；第二个 $A$ 等 $C$ 归约完才执行，把 $C$ 的属性交给 $T$。

    * 为什么不能让 $C$ 直接读 $B$ 的属性：在分析树里 $B$ 和 $C$ 是兄弟，$C$ 的子树看不到兄弟节点上的属性；$t$、$w$ 就是给这对兄弟搭的通道，$B$ 先把值放进去，$C$ 再取。

    * 产生式 8 的空产生式动作把 $t$、$w$ 取出来当成自己的 `type`、`width`；产生式 9 在已算出的 $C_1$ 外面再套一层数组，宽度是“元素个数 × 元素宽度”。

### LL(1) 验证

* **逐组 SELECT 集**

    * $D$ 的两条：2 号以 $T$ 开头，SELECT 集是 $T$ 的 FIRST 集，即 $\{\text{pointer},\text{int},\text{real}\}$；3 号是空产生式，SELECT 集是 $\text{FOLLOW}(D)$，$D$ 后面跟结束符 `$`，即 `{$}`；不相交。

    * $T$ 的两条：4 号以 $B$ 开头，含 `int`、`real`；5 号以指针关键字开头，`{pointer}`；不相交。

    * $B$ 的两条：6 号 `{int}`，7 号 `{real}`；不相交。

    * $C$ 的两条：8 号空产生式，SELECT 集是 $\text{FOLLOW}(C)$，含 `id`；9 号以 `[` 开头，`{[}`；不相交。

* **结论**

    * > **结论**：基础文法是一个 LL(1) 文法，可以在自顶向下的语法分析过程中实现这套 SDT。

### 走查与数组类型

* **`real x; int i;`**

    * 初始用 1 号产生式把 $P$ 换成 $A\,D$，$A$ 执行 `offset := 0` 后出栈。

    * $B \to \text{real}$：`B.type := real`、`B.width := 8`；4 号第一个 $A$ 执行 `t := real`、`w := 8`。

    * $C \to \varepsilon$ 取走 `t`、`w`，得 `C.type = real`、`C.width = 8`；4 号第二个 $A$ 把它们交给 $T$。

    * 匹配 `id`（`x`）与分号后，2 号动作执行 `enter(x, real, 0)`，`offset := 0 + 8 = 8`。

    * `int i` 同理：`enter(i, int, 8)`，`offset := 8 + 4 = 12`。

    | 名字 | type | 相对地址 |
    | :---: | :---: | :---: |
    | `x` | `real` | 0 |
    | `i` | `int` | 8 |

    * `offset` 最后是 12，下一个声明的名字会从 12 开始分配；两遍声明的动作序列一模一样，变的只有类型和宽度。

* **`int[2][3]`**

    * 从 $T$ 开始推导；$B \to \text{int}$ 给出 `int` 与 4；$C$ 连续套两层 9 号产生式，最内层由 $C \to \varepsilon$ 取走 `t`、`w`。

    * 内层 `[3]`：`C.type = array(3, int)`，`C.width = 3 × 4 = 12`。

    * 外层 `[2]`：`C.type = array(2, array(3, int))`，`C.width = 2 × 12 = 24`。

    * $C$ 的产生式右递归，最里面那一维最先规约，数组类型由内向外一层层套起来；`int[2][3]` 得到 $\text{array}(2,\text{array}(3,\text{int}))$，不是反过来。

    * > **易错点**：数组的宽度不是把各维的数字加起来，而是一层一层乘；每一层的宽度都等于“这一维的元素个数 × 元素的宽度”，而元素本身可能又是一个数组，所以内层的宽度要先算出来，外层才能用。

## 赋值语句与三地址码

### 三地址码

* **形态**

    * 三地址码是形如 `x = y op z` 的中间代码，一条指令最多带一个运算符。

    * `x = (a + b) * c;` 翻成 `t1 = a + b`、`t2 = t1 * c`、`x = t2`；顺序就是表达式求值顺序：先算子表达式，再算外层运算，最后才轮到赋值。

* **基础文法**

    * $S \to \text{id} = E\,;$

    * 一个赋值语句，就是一个标识符、一个等号、一个表达式、一个分号。

### 工具函数与六条产生式

* **三个工具函数**

    * `lookup(name)`：查符号表返回 `name` 对应的记录，查不到返回空。

    * `gen(code)`：生成一条三地址指令 `code`。

    * `newtemp()`：生成一个新的临时变量 $t$，并返回 $t$ 的地址。

    * 约定：例子里面用名字表示地址，`E.address` 等于 `t1` 说的是“这个值放在名为 `t1` 的临时变量里”。

* **六条产生式**

```text
S → id = E ;    { p := lookup(id.name).addr;
                  S.code := E.code || gen(p '=' E.address) }

E → E1 + E2     { E.address := newtemp();
                  E.code := E1.code || E2.code
                            || gen(E.address '=' E1.address '+' E2.address) }

E → E1 * E2     { E.address := newtemp();
                  E.code := E1.code || E2.code
                            || gen(E.address '=' E1.address '*' E2.address) }

E → -E1         { E.address := newtemp();
                  E.code := E1.code || gen(E.address '=' '-' E1.address) }

E → (E1)        { E.address := E1.address;
                  E.code := E1.code }

E → id          { p := lookup(id.name);
                  if p = nil then error;
                  E.address := p.addr;
                  E.code := ε }
```

* **各产生式的要点**

    * $E \to \text{id}$：标识符本身就存放着表达式的值，所以标识符的地址就是值的存放地址；`lookup` 返回空说明标识符未经声明直接使用；不涉及运算，`E.code` 为空串。

    * $E \to (E_1)$：括号不改变值也不产生运算，属性直接照抄。

    * $E \to E_1 + E_2$：先 `newtemp` 造临时变量存结果，再拼三段代码——$E_1$ 的代码、$E_2$ 的代码、最后一条加法指令。

    * $E \to -E_1$：取反的结果同样要有存放位置，先 `newtemp`，再在 $E_1$ 的代码后追加取反指令。

    * $S \to \text{id} = E\,;$：先 `lookup` 取出 `id` 的地址赋给 $p$，再把赋值指令接在 $E$ 的代码后。

    * > **易错点**：$E \to E_1 + E_2$ 的代码顺序是 $E_1$ 的代码、$E_2$ 的代码、最后才是加法指令；加法指令必须排在两个子表达式的代码之后，否则操作数还没算出来，指令就先去取操作数了。

### 增量翻译

* **动机**

    * `code` 属性总要复制子表达式的 `code`，一层套一层，可能是一个很长的字符串，复制、移动都要花时间。

    * 左部符号的 `code` 构造方式永远是“右部各符号的 `code` 按顺序连接起来，再在后面追加一条（或几条）三地址指令”；既然每次都是往后接，就没必要把整串代码在树上来回搬。

* **做法**

    * 不设 `code` 属性，直接在已生成的三地址码后面追加新的三地址指令，把与 `code` 相关的行全部删掉。

    * `gen` 的职责变为：不仅构造一条新的三地址指令，还要把这条指令添加到至今为止已生成的指令序列之后。

    * 属性只剩 `E.address`，语义动作缩成两类：算地址、追加指令。

    * > **提示**：增量翻译不是另换一套语义，它生成的三地址码和属性式翻译完全一样，只是不再把整串代码在语法树上搬来搬去。

| 对比项 | 属性式翻译 | 增量翻译 |
| :--- | :--- | :--- |
| 三地址码放在哪 | 放在 `code` 属性里，随语法树上下传递 | 放在一个全局指令序列里，只往后追加 |
| `gen` 的职责 | 只构造指令 | 构造指令并追加到序列末尾 |
| 主要代价 | 长字符串反复复制、移动 | 只追加，不复制 |

### LR 走查

* **设置**

    * 输入 $x = (a + b) * c$；基础文法可采用 LR 分析技术，所有语义动作都位于产生式右部末尾，可以采用自底向上的方式翻译。

    * 状态栈放状态号，符号栈放已移进或规约出的文法符号，栈底是 `$`。

* **三条读法**

    * 遇到标识符，查符号表，把地址交给 $E$，不发指令。

    * 遇到 `+`、`*`，先 `newtemp` 造临时变量，再发一条运算指令。

    * 遇到括号，属性原样传，不发指令；遇到分号，发最后一条赋值指令。

    * 每条指令发出的时候，操作数的地址都已经就绪——归约到某个产生式时，右部符号的属性早就计算完了。

* **生成结果**

```text
t1 = a + b
t2 = t1 * c
x  = t2
```

    * 先算 $a + b$ 存进 `t1`，再算 `t1 * c` 存进 `t2`，`t2` 就是等号右边的值，最后赋给 `x`。

## 数组引用的翻译

### 寻址公式

* **文法扩展**

    * $S \to L = E$：数组元素出现在赋值号左边，可以被赋值。

    * $E \to L$：数组元素本身也是一个表达式，可以出现在右边。

    * $L \to \text{id}[E]$：标识符带一个下标。

    * $L \to L[E]$：已有的数组元素再接一个下标；这是递归的，`A[i1][i2][i3]` 这种多维引用靠 $L$ 自己套自己就能长出来。

* **寻址公式**

    * 一维：$base + i \times w$，$w$ 是每个数组元素的宽度；$base$ 是基地址，$i \times w$ 是偏移地址。

    * 二维：$base + i_1 \times w_1 + i_2 \times w_2$，$w_1$ 是一行的宽度，$w_2$ 是同一行中每个元素的宽度。

    * $k$ 维：$base + i_1w_1 + i_2w_2 + \dots + i_kw_k$。

    * $w_j$ 指 $A[i_1]\dots[i_j]$ 的宽度：$w_1$ 是 $k-1$ 维子数组的宽度，$w_2$ 是 $k-2$ 维子数组的宽度，$w_k$ 是基本元素的宽度。

    * > **易错点**：$w_1$ 不是“第一维的长度”，而是“第一维每个元素占多少字节”。三维数组第一维有 3 个元素，$w_1$ 不是 3，而是这 3 个元素中每一个（一个完整的二维子数组）的大小；公式里每个下标乘的都是“剥掉这一层之后剩下的那个子数组”的宽度，不是这一维的元素个数。

### 三维数组实例

* **宽度剥离**

    * 设 $A$ 是 $3 \times 5 \times 8$ 的三维整型数组，一个整型占 4 个字节。

    * $A[i_1]$ 是 $5 \times 8$ 的二维整型数组，$5 \times 8 \times 4 = 160$，即 $w_1$。

    * $A[i_1][i_2]$ 是 8 个整型构成的一维数组，$8 \times 4 = 32$，即 $w_2$。

    * $A[i_1][i_2][i_3]$ 是一个整型变量，宽度 4，即 $w_3$。

    * $address = base + i_1 \times 160 + i_2 \times 32 + i_3 \times 4$。

| 这一层的子数组 | 它是什么 | 宽度 |
| :--- | :--- | ---: |
| $A[i_1]$ | $5 \times 8$ 的二维整型数组 | $5 \times 8 \times 4 = 160$ |
| $A[i_1][i_2]$ | 8 个整型构成的一维数组 | $8 \times 4 = 32$ |
| $A[i_1][i_2][i_3]$ | 一个整型变量 | 4 |

* **记法**

    * 第 $j$ 层的宽度，等于第 $j$ 层之后所有维度长度的乘积再乘元素大小；最后一层后面没有维度了，乘积是 1，宽度就是元素自己的大小。

    * 最后一个下标乘的系数最小，最后一维的下标每加 1，地址只移动一个元素，它正是变化最快的那个下标。

### 属性设计与 SDT

* **$L$ 的三个属性**

    * `L.type`：$L$ 所代表的数组元素的类型表达式，提供这一层的宽度 $w_j$。

    * `L.offset`：一个临时变量，累加 $\sum i_j \times w_j$。

    * `L.array`：数组名在符号表中的入口地址，提供基地址。

    * 宽度藏在类型表达式里：`A` 的类型是 `array(3, array(5, array(8, int)))`，取一次 `element` 得 `array(5, array(8, int))`，再取得 `array(8, int)`，最后一次只剩 `int`；类型一层层往里收，宽度从 160 降到 32、再降到 4。

    * `L.array` 沿由若干个 $L$ 组成的链一路向上传：$A$ 只出现在最里层，而最后的取数动作发生在最外层的 $L$ 上。

* **四条产生式**

```text
L → id [ E ]   { L.array  = lookup(id.lexeme);
                 L.type   = L.array.type.element;
                 L.offset = newtemp();
                 emit(L.offset "=" E.addr "*" width(L.type)); }

L → L1 [ E ]  { L.array  = L1.array;
                 L.type   = L1.type.element;
                 t        = newtemp();
                 emit(t "=" E.addr "*" width(L.type));
                 L.offset = newtemp();
                 emit(L.offset "=" L1.offset "+" t); }

E → L          { E.addr = newtemp();
                 emit(E.addr "=" L.array "[" L.offset "]"); }

S → L = E      { emit(L.array "[" L.offset "]" "=" E.addr); }
```

* **要点**

    * 每一层的乘法用**新归约出来的这个 $L$** 的 `type` 的宽度：第一层 $A[i_1]$ 的宽度 160，第二层 32，第三层 4。

    * $t_1$、$t_2$、$t_4$ 是各层的单项偏移，$t_3$、$t_5$ 是前缀和，$t_5$ 就是最终的总偏移。

    * 所有语义动作都放在产生式末尾，可以直接搭在自底向上的语法分析上，不需要在产生式中间留位置，也不用改文法。

    * $S \to L = E$ 只生成一条指令：等号左边是“基址 + 偏移”指出的位置，右边是要存进去的值；给数组元素赋值和从数组元素取值，区别只在最后这条指令的方向。

### 三地址码实例

* **一维 `c = A[i]`**

    * 设 $A$ 是包含 $n$ 个整型变量的数组，$A[i]$ 的地址是 $base + i \times 4$。

```text
t1 = i * 4
t2 = A[t1]
c  = t2
```

    * 第一条算偏移，第二条用数组名 $A$ 表示基地址、基地址加偏移取出元素，第三条把值赋给 $c$。

* **二维 `c = A[i1][i2]`**

    * 设 $A$ 是 $3 \times 5$ 的二维整型数组，行宽 20（一行 5 个整型，$5 \times 4$），元素宽 4。

```text
t1 = i1 * 20
t2 = i2 * 4
t3 = t1 + t2
t4 = A[t3]
c  = t4
```

* **规律**

    * 一维三条、二维五条：每多一维，多一条乘法、多一条加法；$k$ 维数组要算 $k$ 段偏移、做 $k-1$ 次累加。

    * > **提示**：`A[t1]` 不是“下标为 t1 的元素”，`t1` 是字节偏移，不是下标；它只是一种紧凑记法，表示“以 A 为基址、偏移 t1 处的那个字”，把“基址加偏移”和“按地址取数”合在一条里写，真正落到机器指令上是“先算地址、再 load”两条。

## 控制流语句的翻译

### 代码结构图与接口属性

* **控制流文法**

```text
P → S
S → S1 S2
S → id = E
S → if ( B ) S1
S → if ( B ) S1 else S2
S → while ( B ) S1
```

* **三类结构**

    * 顺序结构、分支结构（if、case）、循环结构（while、for、repeat）。

    * 分支和循环语句本身不产生“算术值”，只负责把控制流摆对；翻译产物不是某个临时变量里的数，而是一串排好序的指令加几条跳转。

    * 判断翻得对不对，就看程序执行到某一个点时，是不是该走那条路。

* **接口属性**

    * `S.next`：一个地址，地址里存放紧跟在 $S$ 代码之后那条指令的标号；紧跟其后的指令也叫 $S$ 的后继指令。

    * $S_1$、$S_2$ 执行完都要到 $S$ 后面去，所以 `S1.next`、`S2.next`、`S.next` 指向同一条指令。

    * `B.true`、`B.false`：$B$ 为真、为假时控制流转向的指令标号。

    * > **结论**：控制流语句的翻译本质上是“把代码块按顺序摆好，再用跳转指令把它们的出入口接起来”；`next`、`true`、`false` 记的不是值，而是接口——哪条指令接进来，哪条指令接出去。

### 标号的先占位后回填

* **`newlabel` 与 `label` 的分工**

    * `newlabel()`：生成一个用于存放标号的临时变量，返回这个变量的地址。

    * `label(x)`：把下一条三地址指令的标号赋给变量 $x$。

    * $S$ 之前那个动作只确定“标号存放在哪”，标号的具体值要等 $S$ 分析完之后那个动作才填进去。

    * > **提示**：相当于在旅店先订房间——房间号（存放标号的变量地址）可以预先确定，住的是谁（标号的值）得等代码生成到那里才知道；跳转指令引用这个变量，标号晚一点填也不影响已生成的指令。

* **语句序列**

```text
S → { S1.next = newlabel(); }
    S1
    { label(S1.next); S2.next = S.next; }
    S2
```

    * $S_1$ 执行完，下一条就是 $S_2$ 的第一条指令，可这个标号现在还不知道，先占位；$S_1$ 分析完之后填进去。

    * $S_2$ 执行完要到 $S$ 之后，所以 `S2.next = S.next`。

### if 语句

* **if-then-else**

```text
S → if ( { B.true = newlabel(); B.false = newlabel(); }
         B
     ) then { label(B.true); S1.next = S.next; }
         S1
       { emit("goto " S.next); }
     else { label(B.false); S2.next = S.next; }
         S2
```

    * $B$ 之前调 `newlabel` 生成两个存放标号的临时变量，分别赋给 `B.true` 与 `B.false`。

    * 读入 `then` 后，下一条指令就是 $S_1$ 的第一条，`label(B.true)` 把它填进去；$S_1$ 出现之前令 `S1.next = S.next`。

    * $S_1$ 分析完补一条 `goto S.next`，跳过 $S_2$；读入 `else` 后 `label(B.false)` 填 $S_2$ 的第一条；$S_2.next = S.next$。

    * `B.true` 不能一开始就 label：$B$ 的代码有长有短，$S_1$ 第一条指令的序号要等 $B$ 的跳转代码全部落地才数得出来。

* **if-then**

```text
S → if ( { B.true = newlabel(); B.false = S.next; }
         B
     ) then { label(B.true); S1.next = S.next; }
         S1
```

    * $B$ 为假时直接去 `S.next`，$S_1$ 执行完也去 `S.next`。

    * 和 if-then-else 比，省掉一个标号和一条 `goto`：$B.false$ 直接等于 `S.next`，不用单开变量；$S_1$ 后面也不需要 `goto S.next`，因为 $S_1$ 的代码后面紧跟着的就是 `S.next` 指向的指令，让控制流自然落下去即可。

### while 语句

* **结构与动作**

```text
S → while { S.begin = newlabel(); label(S.begin);
            B.true = newlabel(); B.false = S.next; }
        ( B )
      do { label(B.true); S1.next = S.begin; }
        S1
      { emit("goto " S.begin); }
```

    * 读入 `while` 就立刻记下循环入口：`S.begin = newlabel()`，紧接着 `label(S.begin)` 把下一条指令的标号（while 的第一条）填进去。

    * $B$ 之前算两个出口：`B.true` 新开标号，`B.false` 等于 `S.next`（循环出口）。

    * 读入 `do` 后，下一条是 $S_1$ 的第一条，`label(B.true)` 填进去；$S_1$ 的 next 不是 `S.next` 而是 `S.begin`，循环体执行完要回到入口。

    * $S_1$ 之后再来一条 `goto S.begin`，闭环完成。

* **循环入口的唯一性**

    * > **提示**：三个语句里只有 while 需要 `S.begin`，因为只有它要往回跳。if 的两个分支都是往前走的，`next` 一个属性就够；while 的循环体必须知道“家在哪儿”，这个家就是循环入口的标号。

## 布尔表达式的翻译

### 跳转代码

* **文法**

```text
B → B1 or B2
B → B1 and B2
B → not B1
B → ( B1 )
B → E1 relop E2
B → true
B → false
```

    * `relop` 表示关系运算符：小于、小于等于、大于、大于等于、等于、不等于；作用于两个算术表达式得到关系表达式，关系表达式本身可以构成布尔表达式。

    * 三个逻辑运算符的优先级从高到低：非、与、或。

* **翻译方式**

    * 与、或、非这些运算符被翻译成跳转指令，运算符本身并不出现在代码里。

    * 布尔表达式的值不用一个变量存起来，而是由代码序列中的位置表示：控制流走到真出口就说明它是真，走到假出口就说明是假。

### 各产生式的翻译

* **关系表达式、常量与括号**

```text
B → E1 relop E2  { emit("if " E1.addr relop E2.addr " goto " B.true);
                   emit("goto " B.false); }
B → true         { emit("goto " B.true); }
B → false        { emit("goto " B.false); }
B → ( B1 )       { B1.true = B.true; B1.false = B.false; }
```

    * 关系表达式只能给出一次判断结果，所以生成两条指令：成立跳真出口，不成立跳假出口。

    * 布尔常量 true、false 的值是确定的，只生成一条无条件跳转；括号只是分组，不改变任何出口。

* **not**

```text
B → not B1  { B1.true = B.false; B1.false = B.true; }
```

    * $B_1$ 真等于 $B$ 假，$B_1$ 假等于 $B$ 真，所以把两个出口对调就行，一条指令都不生成。

* **or**

```text
B → B1 or { B1.true = B.true; B1.false = newlabel(); }
       B2 { label(B1.false); B2.true = B.true; B2.false = B.false; }
```

    * $B_1$ 为真，整个式子真，跳 `B.true`；$B_1$ 为假才需要看 $B_2$，先给 `B1.false` 占位，读入 `or` 后 `label(B1.false)` 把位置填实。

    * $B_2$ 的两个出口就是整个 $B$ 的两个出口，原样上传。

* **and**

```text
B → B1 and { B1.false = B.false; B1.true = newlabel(); }
       B2  { label(B1.true); B2.true = B.true; B2.false = B.false; }
```

    * $B_1$ 为假，整个式子假，跳 `B.false`；$B_1$ 为真才需要看 $B_2$。

    * 口诀：`or` 是“左边假了才往下走”，`and` 是“左边真了才往下走”；另一个产生式不用背，把 true 和 false 对调就是它。

| 产生式 | $B_1$ 哪个出口直通 $B$ | 哪个出口要新标号 | $B_2$ 的真出口 | $B_2$ 的假出口 |
| :--- | :--- | :--- | :--- | :--- |
| $B_1$ `or` $B_2$ | true 直通 `B.true` | false 开新标号，指向 $B_2$ | `B.true` | `B.false` |
| $B_1$ `and` $B_2$ | false 直通 `B.false` | true 开新标号，指向 $B_2$ | `B.true` | `B.false` |

### 优先级与短路

* **示例**

    * 输入 `if x < 100 or x > 200 and x != y then x = 0`，按优先级等价于 `x < 100 or ((x > 200) and (x != y))`。

```text
1    if x < 100 goto L2
2    goto L3
3 L3:if x > 200 goto L4
4    goto L1
5 L4:if x != y goto L2
6    goto L1
7 L2:x = 0
8 L1:（if 之后的下一条指令）
```

    * 第 1 条成立，整个布尔表达式为真，直奔 `L2` 执行 `x = 0`；否则跳 `L3` 继续判断。

    * $x > 200$ 成立还要跳到 `L4` 判断 $x \ne y$；成立则整个式子为真，跳 `L2`；不成立则整个式子为假，跳 `L1`；若根本不大于 200，“与”的左边已假，整个式子必假，直接跳 `L1`。

    * 逻辑运算符彻底消失，只剩条件跳转；短路求值也顺带实现——`x < 100` 一旦成立，后面两个关系根本不会被求值。

* **通用实现与适用边界**

    * 任何一个 SDT 都可以先给输入句子建一棵语法分析树，再按从左到右的深度优先顺序执行语义动作。

    * 控制流语句的 SDT 基础文法不是 LL(1) 文法，没法在自顶向下的分析里同时做语义翻译；产生式右部又含内嵌语义动作，想在自底向上的分析里直接执行也得改文法、引入标记非终结符。

    * 这个 SDT 的基础文法本身可以用 LR 技术分析，所以可以先造分析树，再在树上执行动作。

* **while 套 if 的完整例子**

    * 输入：

```text
while a < b do
    if c < d then x = y + z else x = y - z
```

    * 标号：$L_1 = 11$（while 之后的下一条）、$L_2 = 1$（while 第一条，$B$ 的代码起点）、$L_3 = 3$（循环体第一条）、$L_4 = 5$（then 分支第一条）、$L_5 = 8$（else 分支第一条）。

```text
1    if a < b goto 3
2    goto 11
3    if c < d goto 5
4    goto 8
5    t1 = y + z
6    x = t1
7    goto 1
8    t2 = y - z
9    x = t2
10   goto 1
11   （while 之后的下一条指令）
```

    * 检验：$a < b$ 成立跳 3 进循环体，否则执行 2 跳 11 出循环；$c < d$ 成立跳 5 执行 $x = y + z$，执行完 7 跳回 1；不成立跳 8 执行 $x = y - z$，执行完落进 10，同样跳回 1。

    * 两条路径都回到循环入口，循环出口只有一个 11 号；写成四元式就是每条指令拆成运算符、两个操作数、结果四个域，控制流不变。

## 布尔表达式的回填

### 回填机制

* **动机**

    * 跳转指令必须写清楚跳到哪儿，可生成它的那一刻，那个“哪儿”往往还没被翻译出来。

    * 原方案把“存放标号的地址”作为继承属性一路传递，先留地址占位，事后再走一趟把标号和地址绑定起来。

    * 回填不再传地址，而是传列表：把由跳转指令组成的列表作为综合属性向上传递；生成跳转时暂不指定目标标号，先把这条指令放进列表；同一列表里的跳转最终共享同一个目标标号，等标号能确定了再一次性全部填上。

* **两个列表属性**

    * `B.truelist`：指向一个跳转指令列表，这些指令最终获得的目标标号，就是 $B$ 为真时控制流应该转向的那条指令的标号。

    * `B.falselist`：指向一个跳转指令列表，这些指令最终获得的目标标号，就是 $B$ 为假时控制流应该转向的那条指令的标号。

    * > **结论**：回填不是“不填”，而是“先记账、后结算”；列表是账本，生成指令时只管记账，等目标确定了再一次性结算，省掉的正是原来那趟专门用来绑定标号的遍历。

* **三个函数与 `nextcode`**

    * `makelist(i)`：创建只包含标号 `i` 的列表，返回指向新列表的指针。

    * `merge(p1,p2)`：把两个列表合并，返回指向合并后列表的指针。

    * `backpatch(p,i)`：把 `i` 作为目标标号，填入 `p` 所指列表中的每一条指令。

    * `nextcode`：即将生成的下一条指令的标号，决定新指令的编号，也是调用 `makelist` 时的取值依据。

    * > **提示**：$B \to E_1 \text{ relop } E_2$ 要连着生成两条跳转，第一条的标号是 `nextcode`，第二条是 `nextcode + 1`；这两个值必须在生成指令之前取好，因为两条指令一落地，`nextcode` 就往后挪了两位。

### 基本产生式

* **关系表达式**

```text
B.truelist  = makelist(nextcode)
B.falselist = makelist(nextcode + 1)
    if E1 relop E2 goto _        // 标号 nextcode
    goto _                       // 标号 nextcode + 1
```

    * 两条指令的目标标号此刻都定不下来，所以各记一本账：条件跳转的去向是 $B$ 的真出口，挂到 `B.truelist`；无条件跳转的去向是 $B$ 的假出口，挂到 `B.falselist`。

    * 一个关系表达式在代码里只留下两条跳转，加两本待结的账；跳转真正落到哪里，等外层把出口定下来再说。

* **常数、括号与取反**

    * $B \to \text{true}$：值已经确定整个布尔表达式为真，生成一条跳转真出口的指令，进 `B.truelist`。

    * $B \to \text{false}$：值已经确定整个布尔表达式为假，生成一条跳转假出口的指令，进 `B.falselist`。

    * $B \to (B_1)$：对 $B$ 的翻译与对 $B_1$ 完全相同，属性照搬。

    * $B \to \text{not } B_1$：真假整个翻过来，两个属性对调。

    * > **易错点**：`true` 和 `false` 产生的是无条件跳转，不是条件跳转；值已经确定了，没有条件可判，判据都省了，只剩“跳”这一个动作。

### or 与 and

* **or**

```text
B → B1 or M B2

M.code = nextcode
backpatch(B1.falselist, M.code)
B.truelist  = merge(B1.truelist, B2.truelist)
B.falselist = B2.falselist
```

    * $B_1$ 为真，`or` 的结果已真，右边不用算，`B1.truelist` 整个并入 `B.truelist`。

    * $B_1$ 为假，结果还不能定，必须接着判 $B_2$，所以 `B1.falselist` 回填成 $B_2$ 的第一条指令，即 `M.code`。

    * $B_2$ 为真，整个 `or` 为真，`B2.truelist` 并入；$B_2$ 也假，整个表达式才假，`B.falselist` 直接就是 `B2.falselist`。

* **and**

```text
B → B1 and M B2

M.code = nextcode
backpatch(B1.truelist, M.code)
B.truelist  = B2.truelist
B.falselist = merge(B1.falselist, B2.falselist)
```

    * $B_1$ 为假，整个 `and` 就是假，`B1.falselist` 并入 `B.falselist`。

    * $B_1$ 为真，结果还定不下来，得接着判 $B_2$，所以 `B1.truelist` 用 `M.code` 回填。

    * $B_2$ 也真，整个表达式才真，`B.truelist` 直接等于 `B2.truelist`；$B_2$ 为假整个 `and` 就是假，这批和 `B1.falselist` 同一个归宿，`merge` 起来交给 `B.falselist`。

* **`M` 的作用**

    * 自底向上分析里，等 $B_1 \text{ or } B_2$ 可以归约时，$B_2$ 早就翻译完了，“$B_2$ 的第一条指令”这个位置已经被后面一长串指令盖过去，栈上再也找不回来。

    * `M` 的作用就是在那个位置上留一个存档，`M.code = nextcode` 天然就是 $B_2$ 第一条指令的标号，归约时把存档取出来用。

| 比较项 | $B_1$ `or` $B_2$ | $B_1$ `and` $B_2$ |
| :--- | :--- | :--- |
| 左侧能直接定值的一端 | $B_1$ 为真 | $B_1$ 为假 |
| 该端出口的归属 | 并入 `B.truelist` | 并入 `B.falselist` |
| 左侧另一端 | 回填到 $B_2$ 的第一条指令 | 回填到 $B_2$ 的第一条指令 |
| `B.truelist` 的来源 | `merge(B1, B2)` 的 truelist | 只要 `B2.truelist` |
| `B.falselist` 的来源 | 只要 `B2.falselist` | `merge(B1, B2)` 的 falselist |

* > **易错点**：两条规则是镜像，但不是完全对称。`or` 里要 `merge` 的是 truelist，`and` 里要 `merge` 的是 falselist——哪一端能独立定值，哪一端的账就只剩另一本。记混的根源在于只记了“or 合并真、and 合并假”这半句，忘了前面还有一半：左边为真（或假）时右边整段被短路。

### 走查

* **设置**

    * 输入 `a < b or c < d and e < f`，假设下一条指令从 100 号开始编；属性全是综合属性，可自底向上、从左向右扫。

* **过程**

    * `a < b` 归约成 $B$：`truelist = {100}`、`falselist = {101}`，生成 100 号 `if a < b goto _`、101 号 `goto _`。

    * 归约出 `M`：`M.code = 102`。

    * `c < d` 归约成 $B$：`truelist = {102}`、`falselist = {103}`，生成 102、103 两条。

    * 栈顶是 `B or B`、向前看是 `and`；`and` 优先级高于 `or`，不能拿 `or` 产生式归约，得先把 `and` 移进来，否则会算成 `(a < b or c < d) and (e < f)`，语义就变了。

    * 再归约出 `M`：`M.code = 104`；`e < f` 归约成 $B$：`truelist = {104}`、`falselist = {105}`。

    * 归约 `B and B`：用 `M.code = 104` 回填 102，`B.truelist = {104}`，`B.falselist = {103, 105}`。

    * 归约 `B or B`：用 `M.code = 102` 回填 101，`B.truelist = {100, 104}`，`B.falselist = {103, 105}`。

* **结果**

```text
100  if a < b goto _
101  goto 102
102  if c < d goto 104
103  goto _
104  if e < f goto _
105  goto _
```

    * 四条指令还在等回填：`truelist` 里的 100、104 等真出口；`falselist` 里的 103、105 等假出口。

    * 短路语义全写在跳转里：`a < b` 成立，100 直奔真出口，`c < d`、`e < f` 一次都不算；不成立则 101 落 102 去问 `c < d`；`c < d` 成立，102 跳 104 去问 `e < f`，不成立则 103 直奔假出口。

    * “与的优先级高于或”，在代码里就是 102 的目标是 104 而不是 103。

## 控制流语句的回填

### nextlist

* **定义**

    * > **定义**：`S.nextlist` 指向一个跳转指令列表，这些指令最终获得的目标标号，就是按照运行顺序紧跟在 $S$ 的代码之后的那条指令的标号。

* **“下一条”的口径**

    * 它不表示“代码序列里紧挨着的下一条”，而是“运行顺序上的下一条”；两者在 if、while 里恰恰不是一回事，回填的难点都在这儿。

    * 一条语句翻译完之后，对外只留下一个待结的账：我这块代码执行完，还有哪些跳转没找到家。

### if 语句

* **if-then**

```text
S → if B then M S1

M.code = nextcode
backpatch(B.truelist, M.code)
S.nextlist = merge(B.falselist, S1.nextlist)
```

    * `B.truelist` 跳 $S_1$ 的第一条指令——条件成立就进 then 分支。

    * `B.falselist` 跳 $S$ 之后的第一条指令，`B` 为假时整个 if 什么都不做，这批进 `S.nextlist`。

    * $S_1$ 执行完整个 $S$ 也结束，`S1.nextlist` 同样并入 `S.nextlist`；`S_1` 之前插 `M` 记下入口。

* **if-then-else**

```text
S → if B then M1 S1 N else M2 S2

M1.code = nextcode
M2.code = nextcode
N.nextlist = makelist(nextcode)
    goto _
backpatch(B.truelist, M1.code)
backpatch(B.falselist, M2.code)
S.nextlist = merge(merge(S1.nextlist, N.nextlist), S2.nextlist)
```

    * `B.truelist` 跳 $S_1$ 的第一条；`B.falselist` 跳 $S_2$ 的第一条——条件不成立就转去执行 else 分支。

    * $S_1$ 执行完不能顺势落进 $S_2$，必须显式生成一条 `goto` 跳过 else；这条跳转的目标同样要等 $S$ 之后的位置确定，所以它自己进 `S.nextlist`，由 $N$ 的 `makelist` 记账。

    * `S.nextlist` 是三个来源合并：`S1.nextlist`、`N.nextlist`、`S2.nextlist`；`merge` 是二元函数，所以并两次。

    * > **提示**：if-then 不需要那条显式跳转，if-then-else 必须有——差别全在代码的物理排布上。没有 else 时，then 分支的代码后面本来就是 $S$ 之后的指令，落下去正好；一旦有了 else，then 分支的末尾紧贴着 else 分支的第一条指令，不跳就会“穿”进 else 里去。

### while 语句

* **规则**

```text
S → while M1 B do M2 S1

M1.code = nextcode
M2.code = nextcode
backpatch(S1.nextlist, M1.code)
backpatch(B.truelist, M2.code)
S.nextlist = B.falselist
    goto M1.code
```

    * $B$ 之前插 $M_1$，记下循环入口（$B$ 的第一条指令）；$S_1$ 之前插 $M_2$，记下循环体入口，供 `B.truelist` 回填。

    * `B.falselist` 跳假出口，`B` 为假就跳出整个 while，进 `S.nextlist`。

    * 循环体末尾显式生成 `goto M1.code`，这是回边；目标在生成时已经确定（`M1.code` 早记好了），不需要回填。

    * 回填顺序与 if 不同：先用 `M1.code` 回填 `S1.nextlist`，再用 `M2.code` 回填 `B.truelist`，两个 $M$ 一个记头、一个记体，各回填一本账。

* **出口唯一**

    * > **易错点**：`while` 的 `S.nextlist` 只等于 `B.falselist`，不含 `S1.nextlist`。循环体里的跳转全被回填到循环入口去了，它们不会“跳出循环”——跳出循环的唯一出口是条件为假。

### 顺序语句与赋值语句

* **顺序语句**

```text
S → S1 S2

M.code = nextcode
backpatch(S1.nextlist, M.code)
S.nextlist = S2.nextlist
```

    * `S1.nextlist` 里的指令目标就是 $S_2$ 的第一条指令，用 $S_2$ 之前插入的 $M$ 记下入口后回填。

    * `S2.nextlist` 里的指令跳 $S_2$ 之后，$S_2$ 执行完整条 $S$ 也结束，所以直接交给 `S.nextlist`。

* **赋值语句**

    * $S \to \text{id} = E$ 里没有任何跳转指令，所以 `S.nextlist` 等于空。

    * 空列表参与 `merge` 不改变结果，参与 `backpatch` 什么也不做；正是有了这个“空”，while 的循环体是赋值语句时那段回填才能安然无事地跳过。

### 嵌套实例

* **输入**

```text
while (a < b) do
    if (c < 5) then
        while (x > y) do
            z = x + 1
    else
        x = y
```

* **标号与回填**

    * 外层 `M1.code = 100`；`a < b` 的 `truelist = {100}`、`falselist = {101}`；外层 `M2.code = 102`。

    * `c < 5` 的 `truelist = {102}`、`falselist = {103}`；then 之前 `M1.code = 104`。

    * 内层 while：`M1.code = 104`（与上一条相同，因为没有生成新指令），`M2.code = 106`；`x > y` 的 `truelist = {104}`、`falselist = {105}`。

    * 内层归约：用 104 回填 `S1.nextlist`（`S1` 是赋值语句，列表为空，实际什么都没做）；用 106 回填 104；`S.nextlist = {105}`；生成 108 号 `goto 104`。

    * then 之后的 $N$：`N.nextlist = {109}`，生成 109 号 `goto _`；else 之前 `M2.code = 110`。

    * if 归约：用 104 回填 102，用 110 回填 103，`S.nextlist = {105, 109}`。

    * 外层 while 归约：用 100 回填 105、109；用 102 回填 100；`nextlist = {101}`；生成 111 号 `goto 100`。

| 标号 | 指令 | 来龙去脉 |
| :---: | :--- | :--- |
| 100 | `if a < b goto 102` | 外层循环条件，为真进循环体 |
| 101 | `goto _` | 外层循环唯一出口，进 `S.nextlist` 等回填 |
| 102 | `if c < 5 goto 104` | if 条件为真，进 then 分支 |
| 103 | `goto 110` | if 条件为假，转 else 分支 |
| 104 | `if x > y goto 106` | 内层循环条件，为真进循环体 |
| 105 | `goto 100` | 内层循环条件为假，回外层循环开头 |
| 106 | `t1 = x + 1` | 表达式求值 |
| 107 | `z = t1` | 赋值 |
| 108 | `goto 104` | 内层循环的回边 |
| 109 | `goto 100` | then 分支结束，跳过 else |
| 110 | `x = y` | else 分支 |
| 111 | `goto 100` | 外层循环的回边 |

* **三处要点**

    * 101 始终没有填上：它是外层 while 的假出口，“整个 while 之后是哪条指令”取决于这段代码后面接什么，翻译这条语句时根本不可能知道；它只能带着空位交出去，回填的边界不在单条语句内部，而在语句和外层之间。

    * 105 和 109 都跳 100 而不是 111：`nextlist` 的“下一条”按运行顺序算，不是按地址顺序算；两者效果一样，都是回到循环开头重新判断条件，只是 100 比 111 少跳一次。

    * 111 的 `goto 100` 依然必要：105 和 109 已经直接跳到 100，但 else 分支的 110 号指令执行完是自然下落的，必须有一条指令把它送回循环开头。

## switch 语句的翻译

### 第一种方案：测试跟着分支走

* **代码结构**

```text
E 的代码
t = E.address
if t != V1 goto L1
S1 的代码
goto next
if t != V2 goto L2
S2 的代码
goto next
...
if t != V(n-1) goto L(n-1)
S(n-1) 的代码
goto next
Sn 的代码（default）
goto next
```

    * $E$ 只求值一次，结果存进临时变量 `t`，后面所有比较都读 `t`，否则每比一次就要重算一遍表达式。

    * `L1` 指向 `case V2:` 之后的第一条指令，即下一次测试；`L(n-1)` 指向 $S_n$ 的第一条指令，最后一道测试失败正好落进 default。

    * 每段代码末尾一条 `goto next`，否则执行完 $S_1$ 会直接穿进 $S_2$ 的代码里。

* **动作位置**

    * `E` 之后：调用 `newtemp` 生成 `t`，生成 `t = E.address`。

    * `case V1:` 之后：生成新标号 $L_1$，生成 `if t != V1 goto L1`。

    * `S1` 之后：生成新标号 `next`，生成 `goto next`。

    * `case V2:` 之后：调用 `label` 把下一条指令的标号赋给 $L_1$；生成新标号 $L_2$，生成 `if t != V2 goto L2`。

    * `default` 之后：调用 `label` 把下一条指令的标号赋给 $L_{n-1}$；$S_n$ 之后 `label` 把标号赋给 `next`。

* **麻烦**

    * 每个条件跳转指令的四元式里，第四个分量并不是目标标号，而是“存放目标标号的地址”。

    * $L_1$ 要等到读入 `case V2:` 才知道是几，前面那条 `if t != V1 goto L1` 只能先填地址；于是又得额外走一趟把标号和地址绑定起来，绕了一圈回到开头想避开的做法。

### 第二种方案：测试集中到一处

* **代码结构**

```text
E 的代码
t = E.address
goto test
S1 的代码
goto next
S2 的代码
goto next
...
Sn 的代码（default）
goto next
test 指向这里：
if t = V1 goto L1
if t = V2 goto L2
...
if t = V(n-1) goto L(n-1)
goto Ln
```

    * $E$ 求值后先一条 `goto test` 越过所有分支代码，直接去测试区；测试区按 `t` 的取值把控制流分派到各个 $S$ 的第一条指令。

    * $L_n$ 指向 default 段，所有测试都不成立时兜底；`next` 是测试区之后的第一条指令。

* **动作位置**

    * `E` 之后：生成临时变量 `t`、`t = E.address`；生成新标号 `test`，生成 `goto test`。

    * `case Vi:` 之后：建立新标号 $L_i$，把 $S_i$ 第一条指令的标号赋给 $L_i$，在 $V_i$ 与 $L_i$ 之间建立映射放进映射表。

    * `Si` 之后：生成 `goto next`。

    * `default` 之后：建立新标号 $L_n$，把 $S_n$ 第一条指令的标号赋给 $L_n$。

    * 测试区：调用 `label` 把下一条指令标号赋给 `test`；从映射表读出 $n-1$ 个映射，依次生成 `if t = V1 goto L1` 到 `if t = V(n-1) goto L(n-1)`；最后生成 `goto Ln`。

    * 测试区之后：调用 `label` 把下一条指令标号赋给 `next`。

| 比较项 | 第一种方案 | 第二种方案 |
| :--- | :--- | :--- |
| 测试指令的位置 | 紧跟在各段代码之前，与 $S$ 混排 | 全部集中到所有 $S$ 的代码之后 |
| 测试的条件 | `if t != Vi goto Li`，不等就跳过本段 | `if t = Vi goto Li`，相等就进本段 |
| 标号何时绑定 | 生成跳转时还没绑定，需要再走一趟 | 生成测试前已从映射表取到 $L_i$，直接填 |
| 代码生成阶段 | 难以整体优化 | 测试集中，便于合成 $n$ 路分支 |

* **收益**

    * 第二种方案把标号绑定提前解决：进入测试区时，$S_1$ 到 $S_n$ 的代码都已经生成，每条分支入口标号都在手上，`if t = Vi goto Li` 一生成就是完整的，不需要回填。

    * 测试集中后，代码生成阶段才有机会优化：根据分支个数、常量是否落在一个较小的范围内，这一串条件跳转可以翻成最高效的 $n$ 路分支。

### case 指令

* **形态**

    * `case t, V1, L1` 等价于 `if t = V1 goto L1`。

    * 含义完全一样，区别只在形态：它是一族标记统一的指令，代码生成器扫描到连续的 `case` 就能把它们当成一个整体处理，比如合成跳转表。

    * 用普通条件跳转，生成器得先做模式识别；用 `case`，等于在中间代码里就把意图标好了。

* **回填的价值**

    * > **结论**：回填真正有价值的地方，不在于“把标号留空”这个动作，而在于把指向同一个目标的所有跳转组织成一个列表；列表在手上，目标什么时候到都不迟。而一旦顺序安排得好——像 switch 的第二种方案那样，先有各分支的入口、再生成测试——连列表都不必留，标号当场就能填进去。

## 过程调用语句的翻译

### 文法与 param 指令

* **文法**

```text
S     → call id ( elist )
elist → elist , E
elist → E
```

    * `call` 是过程调用的关键字，`id` 是过程名，括号里由 `elist` 生成实参表达式列表。

    * `elist` 写成左递归，参数从左到右一个一个归约进来，写在前面的实参先入队，这直接决定 `param` 指令的先后。

* **代码结构**

    * 一条调用语句的代码，主体是 $n$ 个参数表达式的代码；每个表达式的值存放在对应非终结符 $E_i$ 的 `address` 属性里。

    * 表达式代码生成完之后，为每个实参补一条 `param` 指令，把那个值认领为第几个实参，最后才是 `call` 本身。

    * `param` 有两种排法：与各自的表达式代码混在一起（算完一个立刻发一条）；或把所有 `param` 集中到所有表达式代码之后，让求值和传参分成两段。

    * 集中排法要多一个队列，把每个表达式的 `address` 先存下来；等所有表达式都算完，再一边清空队列、一边把 `param` 序列发出去。

### 队列与走查

* **三条语义动作**

    * `elist → E`：把队列初始化为只含 `E.address` 一个元素。

    * `elist → elist , E`：把新识别出的 `E.address` 追加到左边那个 `elist` 对应队列的末尾。

    * `S → call id ( elist )`：$n \leftarrow 0$；对队列中每个 $t$ 发 `param t`，每发一条 $n \leftarrow n+1$；最后发 `call id.address, n`。

    * 队首始终是最先写的实参，队列顺序天然就是书写顺序；$n$ 不是预先数出来的，而是发一条数一条。

* **走查 `f(b * c - 1, x + y, x, y)`**

    * `b * c - 1` 要两条三地址码，因为一条三地址码只放得下一个运算符。

```text
T1 = b * c
T2 = T1 - 1
T3 = x + y
```

    * 队列变化：$[T_2]$ → $[T_2, T_3]$ → $[T_2, T_3, x]$ → $[T_2, T_3, x, y]$。

    * 清空队列，依次发出 `param T2`、`param T3`、`param x`、`param y`，最后 `call f, 4`。

    * `E.address` 不一定非得是新造的临时变量：`b * c - 1` 的值没有现成名字才要借 $T_2$；`x` 这种标识符表达式的地址属性就是它自己的名字，`param x` 直接把变量当实参传，省掉一次拷贝。

## 运行存储分配

### 静态与动态

* **分界线**

    * 编译时刻就能确定大小的数据对象，编译时刻就把存储空间分好，叫静态存储分配。

    * 定不了大小的走动态存储分配；动态数组最典型，它的上下界可能来自运行时的输入，编译时只产生必要信息，真正的存储空间留到运行时刻分配。

    * 动态存储分配又分栈式存储分配和堆式存储分配。

* **口径**

    * > **定义**：这里所说的静态和动态，分别相对于编译时刻和运行时刻，说的是“什么时候把大小定下来、什么时候把空间划出来”，不是指变量活多久。

### 内存分区与活动记录

* **四个区**

    * 静态代码区：目标代码，编译时刻大小已定，通常位于存储的低端。

    * 静态数据区：编译时刻就能确定大小的数据，紧挨着静态代码区。

    * 堆与栈：放在剩余地址空间相对的两端，都是动态的，大小随程序运行变化，各自从一端向中间伸缩，谁也不必预先给对方留地盘。

    * 栈里存放活动记录，过程调用时生成并进栈，过程返回时出栈；堆管长生命周期对象，如 `malloc` 和 `free` 分配的对象，不受某一次过程调用的约束。

* **活动记录（activation record）**

    * > **定义**：过程体的每次执行称为该过程的一个活动；过程每执行一次，就要为它分配一块连续的存储区，用来管理这一次执行所需要的全部信息，这块区域称为活动记录。

    * 字段：实参字段、返回值字段、控制链、访问链、局部数据字段、临时变量区。

    * 控制链是一个指针，指向调用者的活动记录，是返回时恢复现场的路。

    * 访问链用来访问存放在其他活动记录中的非局部数据，指向“我声明在谁里面”。

    * 两条链长得一模一样，都是指针，可指向的东西完全不同：控制链管“谁调我”，访问链管“我声明在谁里面”。

### 静态存储分配

* **三条要求**

    * 数组的上下界必须是常数，否则编译时刻确定不了数组的大小。

    * 不容许过程的递归调用，否则同一过程可能有若干活动同时处于活跃状态，编译时刻无法确定会有几个，也就不知道该准备多少块活动记录。

    * 不容许动态建立数据实体，因为没有运行时的存储分配机制，运行中临时冒出来的对象没地方安置。

    * 满足这些条件的语言有 BASIC、FORTRAN 等；常用的静态存储分配方法主要有顺序分配法和层次分配法。

* **顺序分配法**

    * 基本思想：按过程出现的先后顺序逐段分配存储空间，各过程的活动记录占用互不相交的存储空间。

    * 六个过程的例子：1 号 22 单元、2 号 15、3 号 18、4 号 17、5 号 23、6 号 10；依次占 0~21、22~36、37~54、55~71、72~94、95~104。

    * 总量 $22+15+18+17+23+10=105$ 个存储单元。

    * 处理简单，但不够经济：105 个单元里，有些单元永远不会在同一次运行中同时派上用场，却各自占了一份。

* **层次分配法**

    * 基本思想：分析过程间的调用关系，凡属无相互调用关系的并列过程，尽量使其局部数据共享存储空间。

    * 前提是不容许递归调用，调用关系图无环，才能采取从下到上的顺序，一层一层为各层中的过程分配存储空间。

    * 底层 4、5、6 互相不调用，共用起点 0：4 占 0~16，6 占 0~9，5 占 0~22。

    * 第二层：2 调用 4 和 6，4 已占到 16，所以 2 从 17 起占 17~31；3 调用 5 和 6，5 已占到 22，所以 3 从 23 起占 23~40。

    * 第一层：1 调用 2 和 3，3 已占到 40，所以 1 从 41 起占 41~62。

    * 总量 63；最长调用链 1 → 3 → 5，$22+18+23=63$，链上三个活动必须同时存在，所以 63 也是下界；链外的 2、4、6 都找到了可共用的空间。

* **调用关系矩阵**

    * 若程序声明了 $n$ 个过程，建立 $n \times n$ 的过程调用关系矩阵 $B$：$B[i,j]=1$ 表示第 $i$ 个过程调用第 $j$ 个过程，0 表示不调用。

    * 还要一个长度为 $n$ 的数组，存放各过程所需的内存单元数量；矩阵管“谁调用谁”，数组管“要多大”。

    * 六过程例子的矩阵：第一行 `0 1 1 0 0 0`，第二行 `0 0 0 1 0 1`，第三行 `0 0 0 0 1 1`，4、5、6 三行全 0。

* **增加一个过程**

    * 7 号过程需 80 个单元，1 号调用 7 号，7 号调用 5 号。

    * 底层不变；7 号只调用 5 号，5 号已占到 22，所以 7 号从 23 起占 23~102。

    * 2 号仍占 17~31，3 号仍占 23~40；3 号与 7 号前 18 个单元重叠，但二者都是 1 号调用的并列过程，不可能同时活跃，合规。

    * 1 号调用 2、3、7，三个被调用者的终点是 31、40、102，取最大的 102，所以 1 号从 103 起占 103~124。

    * 总量 125；最长调用链变成 1 → 7 → 5，$22+80+23=125$，与总量分毫不差，也是下界。

## 栈式存储分配

### 规矩与活动树

* **两条规矩**

    * 过程被调用，活动记录压入栈；过程结束，活动记录弹出。

    * 好处一：活跃时段不交叠的多个过程调用之间可以共享空间——弹出之后腾出来的位置，下一次调用正好接着用。

    * 好处二：允许按这样一种方式为过程编译代码——变量的相对地址总是固定的，和过程调用序列无关。

    * 同一个过程可能在不同位置被调用，代码只编一份；每次活动记录落在栈里的位置不同，代码靠相对偏移找自己的数据，基准由运行时的指针给出。

* **活动树（activation tree）**

    * > **定义**：描述程序运行期间控制进入和离开各个活动情况的树；树中每个节点对应一个活动，根节点是启动程序执行的 `main` 过程的活动。

    * 表示过程 $p$ 某个活动的节点，其子节点对应被 $p$ 这次活动调用的各个过程的活动，按调用顺序自左向右显示。

    * 约束：一个子节点必须在它右兄弟节点的活动开始之前结束。

    * > **结论**：活动树把一次运行的时间顺序摊成了从左到右，而同一时刻活着的那些活动，恰好是树上一条从根往下的路径。

* **快排的活动树**

```text
m
├── r
└── q(1,9)
    ├── p(1,9)
    ├── q(1,3)
    │   ├── p(1,3)
    │   ├── q(1,0)
    │   └── q(2,3)
    └── q(5,9)
```

    * $m$ 是 `main`，$r$ 是 `readArray`，$q$ 是 `quicksort`，$p$ 是 `partition`。

    * $q(1,0)$ 是叶子：第二个参数 0 不比第一个参数 1 大，进去什么也不做就返回，自然没有子节点。

    * $m$ 调 $r$，$r$ 进栈后返回出栈；$m$ 再调 $q(1,9)$，曾经被 $r$ 占用的空间被 $q(1,9)$ 复用。

    * 递归时同一过程常有多个活动记录同时出现在栈中：$q(1,9)$ 与 $q(1,3)$ 并排躺在栈里。

    * 某一刻栈内容自底向顶是 `m`、`q(1,9)`、`q(1,3)`、`q(2,3)`，恰好是活动树上从根到当前控制所在节点的路径。

### 活动记录的内部摆放

* **三段摆放**

    * 调用者与被调用者之间传递的值，包括参数和返回值，放在被调用者活动记录的开始位置，尽量靠近调用者的活动记录。

    * 固定长度的项，包括控制链、访问链和机器状态字等，通常放在中间。

    * 早期不知道大小的项放在活动记录的尾部；大部分局部数据长度固定，但动态数组这类要到运行时刻才知道长度。

* **`top_sp`**

    * 栈顶指针寄存器 `top_sp` 并不指向真正的栈顶，它指向活动记录中局部数据开始的位置，并以这个位置作为基地址。

    * 参数和返回值落在 `top_sp` 的负方向一侧，靠负偏移就能取到；这也解释了为什么返回值的相对位置在返回之后仍然算得出来。

## 调用序列与返回序列

### 分工

* **定义**

    * > **定义**：实现过程调用的代码段称为调用序列，它为一个活动记录在栈中分配空间，并在这个记录的字段里填写信息；实现过程返回的代码段称为返回序列，它恢复机器状态，使得调用过程能够在调用结束之后继续执行。

    * 这两段代码通常不是由一方单独完成的，调用序列里的代码被分割到调用过程和被调用过程两边，返回序列也是如此。

* **调用者的四件事**

    * 计算实际参数的值，并把它放在被调用者活动记录中的指定位置，也就是参数字段。

    * 把返回地址，也就是程序计数器的值，存放到被调用者的机器状态字段中。

    * 把原来的 `top_sp` 值存放到被调用者的控制链中，这样被调用者的控制链就指向调用者的活动记录。

    * 增加 `top_sp` 的值，使它指向被调用者的局部数据开始的位置。

* **被调用者与返回**

    * 被调用者保存寄存器的值和其它状态信息，然后初始化局部数据，开始执行；到这里调用序列结束。

    * 返回时被调用者先计算好返回值，放到与参数相邻的位置；然后用控制链和机器状态字段中的信息恢复 `top_sp` 和其它寄存器的值；最后跳转到调用者放在机器状态字段中的返回地址。

    * `top_sp` 已经退回调用者的记录，调用者仍能拿到返回值：靠相对位置，调用者知道返回值相对于当前 `top_sp` 的偏移，按偏移去取。

    | 项目 | 调用者 | 被调用者 |
    | :--- | :--- | :--- |
    | 参数字段 | 填写 | — |
    | 控制链 | 填写 | — |
    | 返回地址（程序计数器的值） | 填写 | — |
    | 返回值 | — | 填写 |
    | 其它机器状态字 | — | 填写 |
    | `top_sp` | 负责更新（增加） | 负责恢复 |

    * 一句话概括：调用者管“把入口铺好”，被调用者管“把现场收拾干净并交回结果”。

### 变长数据

* **放置原则**

    * 编译时刻不能确定大小的对象通常分配在堆区；但如果它们是过程的局部对象，也可以分配在运行时刻栈中。

    * 尽量放栈区的原因很实际：可以避免对空间进行垃圾回收，减少相应开销。

    * 条件：数据对象局部于某个过程，并且此过程结束时它变得不可访问——过程一走，这块空间就能随活动记录一起被覆盖，栈的规矩才不被破坏。

* **动态数组的策略**

    * 过程 $p$ 里包含三个数组，大小在编译时刻都不能确定；尽管数组存储出现在栈中，它们并不是 $p$ 活动记录的一部分。

    * $p$ 的活动记录里只存放指向三个数组开始位置的三个指针；$p$ 执行时，这些指针相对于栈顶指针的偏移量已知，目标代码通过指针访问数组元素。

    * $q$ 的活动记录分配在 $p$ 的数组之后，记录里只放一个指向自己变长数组的指针；大块数据都挂在记录外面，长度怎么变都不影响记录的固定布局。

## 非局部数据的访问

### 两种语言

* **支持嵌套声明**

    * 可以在一个过程中声明另一个过程，Pascal 就是；按静态作用域原则，过程除自身局部数据和全局数据外，还可以使用外围过程中声明的对象。

    * `sort` 嵌套声明 `readarray`、`exchange`、`quicksort`；`quicksort` 里又嵌套声明函数 `partition`。

    * `readarray`、`exchange`、`quicksort`、`partition` 都能使用 `sort` 中定义的数组 $a$ 和变量 $x$；`partition` 还能用 `quicksort` 中声明的 $v$。

* **不支持嵌套声明**

    * 不可以再在一个过程中声明另一个过程，C 就是；四个过程之间不存在相互嵌套的声明。

    * 过程中使用的数据只有两种来源：自身定义的局部数据，或在所有过程之外定义的全局数据。

    * 非局部数据都是全局变量，分配在静态区，用静态确定的地址访问；其它变量一定是栈顶活动的局部变量，可通过运行时刻栈的 `top_sp` 指针访问。

    * “栈顶活动的局部变量”指当前正在执行的那一次活动的变量，不是“某个过程的变量”；栈顶活动只有一个，地址唯一确定，不需要任何链。

### 嵌套深度与访问链

* **嵌套深度**

    * > **定义**：不内嵌在任何其他过程中的过程，其嵌套深度为 1；如果一个过程 $p$ 在一个嵌套深度为 $i$ 的过程中定义，那么 $p$ 的嵌套深度为 $i+1$；变量的嵌套深度就是它所在过程的嵌套深度。

    * 例：`sort` 深度 1；`readarray`、`exchange`、`quicksort` 在深度 1 的 `sort` 中定义，深度 2；`partition` 在深度 2 的 `quicksort` 中定义，深度 3。

* **访问链（access link）**

    * 在相互嵌套的过程的活动记录之间建立指针，使内嵌的过程可以访问外层过程中声明的对象。

    * 规则：如果过程 $B$ 在源代码中直接嵌套在过程 $A$ 中（$B$ 的嵌套深度比 $A$ 多 1），那么 $B$ 的任何活动中的访问链都指向最近的 $A$ 的活动。

    * “最近的”指当前调用链上离它最近的那一个，也就是真正把它这条调用路径撑起来的那个 $A$ 的活动。

* **快排走链**

    * $R$ 在 $S$ 中直接声明，访问链指向 $S$；$Q(1,9)$ 也在 $S$ 中声明，访问链指向 $S$。

    * $P(1,9)$ 在 $Q$ 中声明，访问链指向 $Q(1,9)$；顺着这条链，$P(1,9)$ 能访问 $Q$ 和 $S$ 两层声明的数据。

    * $E$ 在 $S$ 中声明，虽然被 $P$ 调用，访问链越过 $P$ 直接指向 $S$。

    * > **易错点**：访问链跟着声明走，不跟着调用走。$E$ 是被 $P$ 调用的，可 $E$ 并不声明在 $P$ 里；谁调用谁只决定控制链，谁声明谁才决定访问链。

    * $Q(1,3)$ 与 $Q(1,9)$ 对应同一过程、同一外围过程，访问链同样指向 $S$；$E$ 无论被哪个 $P$ 调用，链永远指回 $S$ 的那份活动记录。

### 访问链的建立

* **三种情况**

    * 设调用者 $X$ 的嵌套深度为 $n_x$，被调用者 $Y$ 的嵌套深度为 $n_y$。

    * $n_x < n_y$：外层过程调用内层过程。$Y$ 一定直接在 $X$ 中定义，深度只能相差 1；把 $X$ 的活动记录地址填进 $Y$ 的访问链字段。

    * $n_x = n_y$：调用者与被调用者深度相等，即递归调用。两者对应同一过程，外围过程也是同一个，访问链指向同一个活动记录；把调用者的访问链复制给被调用者。

    * $n_x > n_y$：内层过程调用外层过程。$X$ 必定嵌套在某个过程 $Z$ 中，而 $Z$ 中直接定义了 $Y$；从 $X$ 的活动记录开始，沿访问链经过 $\Delta + 1$ 步（$\Delta = n_x - n_y$），找到离栈顶最近的过程 $Z$ 的活动记录，$Y$ 的访问链指向它。

* **步数推导**

    * 每条访问链只往上跳一层。从深度 $n_x$ 的调用者出发跳 $\Delta$ 步，落到深度 $n_y$ 的记录上——这一层和被调用者 $Y$ 同层，是 $Y$ 的“邻居”，还不是声明 $Y$ 的地方。

    * 再补一步，才落到深度 $n_y-1$ 的 $Z$ 上，所以步数总是差一层再加一。

    * 判断依据只有一个：比较两个过程的嵌套深度；谁调用谁只影响走几步，不影响访问链指向哪一层。
