## 符号表、流图与公共子表达式
> 对应块：BLK14 | 覆盖分集：P59-P62 | 块标题（分集名）：《7-6符号表》

### 编译器得先给名字建档

编译器干活的时候，有一件事从头到尾没停过：收集和查询源程序里各个名字的属性信息。这个名字是变量还是过程，什么类型，占几个字节，放在什么位置，有没有返回值——这些都得随手查得到。存放这些信息的地方，就是符号表。

而且它通常不是一张大表。常见的做法是：为每个作用域、每个程序块各建一张独立的符号表。

拿一个 Pascal 程序看。主过程叫 `sort`，为它建一张表：

- `sort` 里声明了一个整型数组 `a`，于是 `sort` 的表里多一条记录，记着名字、类型 `int`、还有它的相对地址；
- 又声明了一个整型变量 `x`，再一条记录，类型 `int`，相对地址 44（前面的 44 个字节被数组 `a` 占了）；
- 还声明了三个过程 `readarray`、`exchange`、`quicksort`，于是有三条记录。这三条记录的地址字段有点特殊：里面存的不是数据地址，而是**指向这三个过程各自符号表的指针**。

`readarray` 里声明了整型变量 `i`，所以它的表里有一条 `i` 的记录。`quicksort` 里声明了 `k` 和 `v`，又声明了一个函数 `partition`，所以 `quicksort` 的表里除了 `k`、`v`，还有一条 `partition` 的记录，地址字段指向 `partition` 的表。`partition` 里声明了 `i` 和 `j`，各一条记录。

```text
[sort]
  a            int     相对地址 0
  x            int     相对地址 44
  readarray    --> [readarray]
  exchange     --> [exchange]
  quicksort    --> [quicksort]
                     k          int   相对地址 0
                     v          int   相对地址 4
                     partition  --> [partition]
                                      i   int   相对地址 0
                                      j   int   相对地址 4
```

图里每一行是表里的一条记录，`-->` 表示这条记录的地址字段存的是指针，顺着它能走到下一张表。所以这些表不是平铺的，而是像树一样一层套一层：外层看得到内层的入口，内层守着自己的局部数据。

每张表的表头还有一个字段：这个过程一共需要多少个存储单元。`readarray` 只声明了一个整型变量，填 4；`quicksort` 和 `partition` 各声明两个整型变量，各填 8；`exchange` 什么都没声明，填 0。

### 符号表怎么跟活动记录对上

按过程建表这件事不是巧合：符号表和编译时的活动记录是**对应的**。一个过程里用到的非局部名字，它的信息可以通过扫描外围过程的符号表拿到。

关键在于两条链在同步走。假设当前栈顶的活动记录是过程 p 的，p 里要访问数据 a：

1. 先在 p 的符号表里查 a——没有；
2. 顺着 p 那张表里的外围指针，来到外围过程 quicksort 的符号表；与此同时，栈顶的活动记录也沿着访问链走一步，来到 quicksort 的活动记录；
3. quicksort 的表里也没有 a，再顺着指针到 quicksort 的外围过程 sort 的符号表；活动记录也跟着再走一步，落到 sort 的活动记录；
4. 在 sort 的表里找到了 a，取出它的相对地址，在 sort 的活动记录里定位到 a 那个单元，访问完成。

```text
符号表链                             活动记录链
[p]              --------->         p 的活动记录        <- 栈顶
 | 外围指针                          | 访问链
 v                                   v
[quicksort]      --------->         quicksort 的活动记录
 | 外围指针                          | 访问链
 v                                   v
[sort]           --------->         sort 的活动记录     <- a 在这里
```

左边一列是符号表之间的指针链，右边一列是活动记录之间的访问链，两条链并排往下走，一步对一步。

> **结论**：非局部名字的查找，本质上是"符号表指针链"和"活动记录访问链"并联前进的过程。查表走了几步，访问链也就走了几步——两条链同构，这是它们能对上的根本原因。

访问链本身怎么建，同样要用到符号表。这里分三种情况：

**外层过程调用内层过程。** 比如 s 调用 q，q 进栈。在调用者 s 的符号表里查 q 这个名字——找到了，说明 q 是在 s 里直接声明的。既然被调用者就声明在调用者里面，q 的访问链直接指向调用者 s 的活动记录。

**递归调用。** 比如 q 调用 q。调用者和被调用者是同一个过程，两者的访问链本来就一样，直接复制过来即可。

**内层过程调用外层过程。** 比如 p 调用 e，e 进栈，它的访问链得重新找。先在 p 的表里查 e——没有；顺着外围指针到 quicksort 的表——还是没有；再顺着到 sort 的表——找到了，说明 e 是在 sort 里声明的。所以 e 的访问链要指向 sort 的活动记录。这一路上，查表走了两步（p → quicksort → sort），活动记录那条链也同步走了两步，最后正落在 sort 的活动记录上。

> **结论**：访问链指向的，永远是"名字被找到的那一层"的活动记录。三种情况其实是同一条规则：外层调内层时，那一层就是调用者；递归时就是自己；内层调外层时，就是一路向外找到的那一层。

### 标识符的两种出场

一个标识符在程序里出现，位置只有两类，处理规矩也完全两样。

**定义性出现**，指的是它出现在某一层的声明语句里，身份是"被声明的名字"。处理办法是**只查本层的符号表**：

- 查到同名记录，报错——这个标识符重复声明了；
- 查不到，就在表里加一条新记录，把标识符及其相关信息填进去。

**应用性出现**，指的是它出现在某一层的可执行语句里，身份是"被使用的名字"。处理办法是**一层一层往外查**：先查本层的表，查不到就到直接外层的表，再查不到就继续往外；一旦找到，就把记录里的信息取出来做相应处理；如果一路查到最外层都没有，报错——标识符未经声明就使用了。

> **提示**：这两条规则看着不对称，其实各有各的道理。定义只查本层，内层才能声明一个和外层同名的名字；使用从内层往外查、先撞上谁就用谁，正好实现了"内层优先"的可见性。

### 用 SDT 把符号表建出来

先看嵌套过程声明语句的文法长什么样。这里的 $D$ 是一个声明序列；一个声明要么是过程声明，要么是变量声明；过程声明里又能继续声明过程和变量；一个程序则是由一个声明序列构成的。

在这种允许嵌套过程声明的语言里，每个过程中声明的局部数据，仍然可以用前面讲过的办法分配相对地址。真正的麻烦在别处：**当看到嵌套过程 P 的时候，应该暂时挂起对外围过程 Q 声明语句的处理**。现在得先钻到 P 里面去，把 P 自己的声明处理完；等 P 结束了，再回来接着处理 Q 剩下的部分。

"挂起一层、进入一层、处理完再回来"，用栈做最自然。翻译器里维护两个栈：

- `tblptr`（table pointer）：存放指向各层符号表的指针；
- `offset`：跟踪各张符号表里已经分配到的相对地址值。

栈顶的这一对，永远代表"现在正在处理哪一层、这一层分到哪儿了"。

配套的是四个函数：

- `mktable(previous)`：建一张新表，返回指向新表的指针；参数 `previous` 指向先前创建的、也就是外围过程的符号表；
- `enter(表, 名字, 类型, 相对地址)`：在指定的表里为这个名字建一条记录；
- `addwidth(表, 值)`：把本过程所需的存储单元数填进表的表头；
- `enterproc(表, 名字, 新表)`：在外围过程的表里为新声明的过程建一条记录，地址字段放指向新表的指针。

#### 进一个过程就压一层：M 与 N

在程序的**开头**，嵌入一个标记非终结符 $M$，它对应一段语义动作：调用 `mktable` 建一张新表，再把新表的指针和相对地址 0 压进两个栈。

这张表是最外层的那张。它是全新的，没有外围过程，所以表头里记外围表的那一栏填空。

在识别出一个**过程名之后**，插入标记非终结符 $N$，它的动作也是 `mktable` 加压栈，只不过建表时把 previous 传成当前栈顶的符号表：新表以栈顶那张表作为自己的外围过程表。

M 和 N 的动作几乎一模一样，差别只在 previous 传什么——M 传空，因为程序这一层没有外围；N 传栈顶，因为每个过程的外围就是它被声明时所在的那一层。

#### 声明一个变量就记一笔：enter

$N$ 后面跟着的 $D$ 仍然是一个声明序列，里面的每个声明既可能是嵌套的过程声明，也可能是变量声明。

每识别出一个变量，就执行两件事：先 `enter(栈顶表, id, 类型, top(offset))`，相对地址直接取当前栈顶的 offset 值；然后让 `top(offset)` 加上这个变量的宽度。

宽度从类型来：一个整型 4 个字节，11 个整型的数组就是 44 个字节。offset 栈的作用也在这里——每一层各有各的分配进度，压栈出栈自动切换，从内层出来回到外层时，offset 也回到外层该在的位置。

#### 离开一个过程就结账：addwidth 与 enterproc

当一个过程对应的产生式右部所有符号都识别出来以后，归约，执行四步：

1. 令 $t$ 指向当前栈顶的符号表；
2. `addwidth(t, top(offset))`，把这一层总共用掉多少存储单元写进表头；
3. 栈顶的符号表指针和相对地址一起出栈，栈顶于是露出了外围过程的符号表；
4. `enterproc(栈顶表, 过程名, t)`，在外围过程的表里为这个刚结束的过程建一条记录，地址字段放指向它那张表的指针。

顺序不能反：必须先出栈露出外围表，才有地方写这条记录。

#### 整个程序收尾

整个程序识别完，归约，执行最后一段动作：`addwidth(栈顶表, top(offset))`，给最外层那张表填上大小；然后把它的指针和相对地址出栈。栈空，建表结束。

### 跟着 sort 程序走一遍

拿一个具体程序把整套动作走一遍。程序名叫 `sort`，它本身就是一个过程。里面依次声明：整型数组 `a`；整型变量 `x`；三个过程 `readarray`、`exchange`、`quicksort`。`readarray` 里声明整型变量 `i`；`exchange` 里什么变量也没声明；`quicksort` 里声明 `k`、`v`，又声明了函数 `partition`；`partition` 里声明 `i`、`j`。

#### 主程序表与 sort 表

一开始，`tblptr` 和 `offset` 两个栈都是空的。

先执行 $M$ 的动作：建一张新表。它没有外围表，表头那一栏填空；表的指针和相对地址 0 压栈。

读入 `program sort;` 之后，执行 $N$ 的动作：以当前栈顶的表（主程序表）作为外围，为 `sort` 建一张新表，指针和 0 压栈。

读入 `a`：在栈顶这张表（现在是 `sort` 的表）里为 `a` 建记录，相对地址取 `top(offset)` 的值 0；填完以后 offset 加上 `a` 的宽度——11 个整型、每个 4 字节，一共 44，所以下一个变量从 44 开始。

读入 `x`：相对地址取 44，填完 offset 加 4，变成 48。

读入 `proc readarray`：执行 $N$ 的动作，为 `readarray` 建表，外围是 `sort` 的表，压栈；offset 也随之从 0 重新开始。

#### readarray 与 exchange

`readarray` 里声明 `i`：在它的表里建记录，相对地址 0，offset 变成 4。

`readarray` 的可执行语句全部识别完，归约：$t$ 指向 `readarray` 的表；`addwidth(t, 4)`，表头填 4——这个过程的局部数据只要 4 个存储单元；表指针和 offset 出栈，栈顶露出 `sort` 的表；`enterproc(sort 的表, readarray, t)`，`sort` 的表里多一条 `readarray` 记录，地址字段指向 `readarray` 的表。

读入 `proc exchange`：$N$ 建表，外围是 `sort`，压栈。`exchange` 里没有变量声明，offset 一直停在 0。归约时 `addwidth(t, 0)`，表头填 0；出栈；`enterproc` 在 `sort` 的表里补上 `exchange` 的记录。

> **提示**：一个过程没声明任何变量，它的表就是一张只有表头的空表，大小为 0——这也是合法的登记结果，不是漏了什么。

#### quicksort 与 partition

读入 `proc quicksort`：$N$ 建表，外围 `sort`，压栈。

`k`：相对地址 0，offset 变 4。`v`：相对地址 4，offset 变 8。

读入 `function partition`：函数也是过程，只是带返回值，所以照样走 $N$ 的动作——为 `partition` 建表，外围是 `quicksort` 的表，压栈。

`i`：相对地址 0，offset 变 4；`j`：相对地址 4，offset 变 8。

`partition` 归约：`addwidth(t, 8)`；出栈，露出 `quicksort` 的表；`enterproc(quicksort 的表, partition, t)`。

`quicksort` 归约：`addwidth(t, 8)`——这里填的是 8，不是 16。`partition` 那 8 个单元记在 `partition` 自己的表头里，不算进 `quicksort` 的局部数据；`quicksort` 的 offset 从头到尾只被 `k`、`v` 推过两次。然后出栈，露出 `sort` 的表，`enterproc(sort 的表, quicksort, t)`。

`sort` 归约：`addwidth(t, 48)`；出栈，露出主程序表；`enterproc(主程序表, sort, t)`。

程序归约：主程序里没有声明全局变量，所以最外层表头填 0；出栈，栈空。所有符号表建完。

#### 六张表合起来看

| 符号表 | 表中的记录 | 表头：所需存储单元数 |
| :--- | :--- | :--- |
| 主程序表 | `sort`（指针） | 0 |
| `sort` | `a`、`x`、`readarray`、`exchange`、`quicksort` | 48 |
| `readarray` | `i` | 4 |
| `exchange` | 无 | 0 |
| `quicksort` | `k`、`v`、`partition` | 8 |
| `partition` | `i`、`j` | 8 |

整趟走下来，建表就是三句话：进一层就压栈建表；声明一个变量就记一笔、把 offset 往前推；出一层就结账，把大小写回表头，再在外围表里补一条指针记录。栈保证你回来的时候，看的正是该看的那一层。

### 基本块：要么全做，要么全不做

从这里开始进入代码优化。所谓代码优化，就是对代码做**等价的程序变换**，让它运行得更快、占用的空间更少，或者二者兼顾。

做优化之前，通常得先把程序的控制流程分析清楚。用来描述控制流程的工具就是流图；流图的每个节点是一个基本块，所以先把基本块说清楚。

#### 两个条件与「最大」

基本块是满足下面两个条件的**最大、连续**的三地址指令序列：

1. 控制流只能从基本块的第一条指令进入。也就是说，不能从中间或末尾的指令进来——没有哪条转移指令的目标是块中间或末尾的指令，任何一条转移指令的目标都只能是某个基本块的第一条指令。
2. 除了最后一条指令，控制流在离开基本块之前不会跳转或停机。也就是说，块内除了最后一条，不会再有别的跳转指令。

合起来看，一个基本块里的所有指令，要么全都执行，要么全都不执行——它们是作为一个整体行动的。

> **提示**：定义里"最大"这两个字不能省。上面两条只管入口和出口，不管块有多长：单拿一条指令出来，它也满足这两条，可它显然不是我们要的块。所以凡是顺着走下来、中间既没有跳转指令、也没有被别的跳转指进来的那一段，都得算在同一块里，不能随手切开。

#### 首指令决定边界

把一个三地址指令序列切成基本块，关键是先定**首指令**，也就是每一块的第一条指令。首指令一旦定下来，从一条首指令开始、到下一条首指令之前的所有指令，就构成一个基本块。

首指令从三个地方来：

- 指令序列的第一条指令，一定是第一个基本块的首指令；
- 任何一条条件或无条件转移指令的**目标指令**，一定是首指令——因为按第一个条件，转移指令只能跳到某个块的第一条；
- **紧跟**在一条条件或无条件转移指令后面的那条指令，也一定是首指令——跳转之后落下来的这条，是下一个分支的开始。

于是划分算法就出来了：输入是一个三地址指令序列，输出是它对应的基本块列表，每条指令恰好被分到一个基本块里。做法是先扫一遍标出所有首指令，再按首指令切段。

#### 排序程序被切成六块

拿快速排序的一段源代码，翻成三地址指令序列（编号 1、2、3……顺着往下排），来切一遍。先找首指令：

| 首指令 | 依据 |
| :--- | :--- |
| 1 | 指令序列的第一条指令 |
| 5 | 某条转移指令的目标 |
| 9 | 某条转移指令的目标 |
| 23 | 某条转移指令的目标 |
| 13 | 紧跟在 12 号转移指令之后 |
| 14 | 紧跟在 13 号转移指令之后 |

一共 6 条首指令，于是 6 个基本块：$B_1$ 是 1~4 号，$B_2$ 是 5~8 号，$B_3$ 是 9~12 号，$B_4$ 只有 13 号一条，$B_5$ 是 14~22 号，$B_6$ 从 23 号一直到序列末尾。

留意 $B_4$：12 号是转移指令，所以 13 号成了首指令；13 号本身又是转移指令，所以 14 号也成了首指令。两条跳转挨在一起，就切出一个只有一条指令的块——基本块的长度没有下限，一条也算。

### 流图：把块连起来

有了基本块，就可以说流图了。流图的每个节点是一个基本块。从基本块 $B$ 到基本块 $C$ 有一条边，当且仅当 $C$ 的第一条指令**可能**紧跟在 $B$ 的最后一条指令之后执行。这时称 $B$ 是 $C$ 的前驱，$C$ 是 $B$ 的后继。

后继从哪来？两种方式：

- 有一条从 $B$ 结尾跳转到 $C$ 开头的转移语句（条件或无条件都算），那么 $C$ 有可能跟在 $B$ 之后执行；
- 按原来的三地址指令序列的顺序，$C$ 就紧挨在 $B$ 后面，而且 $B$ 的结尾不是无条件跳转，那么 $C$ 也可能跟在 $B$ 之后。

拿刚才切出来的 6 个块连一遍：

- $B_2$ 在原序列里紧跟 $B_1$，$B_1$ 的末条不是无条件跳转，于是有边 $B_1 \to B_2$。
- $B_2$ 的末条跳转到 5 号指令，也就是 $B_2$ 自己的首条，那 $B_2$ 就是自己的后继，画一条 $B_2$ 到自身的边。
- $B_3$ 紧跟 $B_2$，$B_2$ 的末条不是无条件跳转，于是有边 $B_2 \to B_3$。
- $B_3$ 的末条跳回自己的首条，于是有自环 $B_3 \to B_3$。
- $B_4$ 紧跟 $B_3$，$B_3$ 的末条不是无条件跳转，于是有边 $B_3 \to B_4$。
- $B_4$ 的末条跳转到 23 号指令，也就是 $B_6$ 的首条，于是有边 $B_4 \to B_6$。
- $B_5$ 紧跟 $B_4$，$B_4$ 的末条不是无条件跳转，于是有边 $B_4 \to B_5$。
- $B_5$ 的末条跳转到 5 号指令，也就是 $B_2$ 的首条，于是有边 $B_5 \to B_2$。
- $B_6$ 紧跟 $B_5$，可是 $B_5$ 的末条是**无条件跳转**，这里不能画边：$B_5$ 到 $B_6$ 没有边。

```text
B1 ──► B2
B2 ──► B2    （末条跳回 5 号，即自身首条）
B2 ──► B3
B3 ──► B3    （末条跳回 9 号，即自身首条）
B3 ──► B4
B4 ──► B5
B4 ──► B6    （末条跳到 23 号，即 B6 首条）
B5 ──► B2    （末条跳回 5 号，即 B2 首条）
B6 ──► 无
```

每一行是一条边，从箭头左边走到右边。指向自己的两行是两个小循环，$B_2$、$B_3$ 各自原地打转；$B_5$ 那条回边把控制送回 $B_2$，串起一个大循环；$B_6$ 没有后继，程序从这里离开。把 $B_1$ 到 $B_6$ 各自对应的三地址指令序列填进这 6 个框，就得到这段程序完整的流图。

> **注意**：$B_5$ 和 $B_6$ 在指令序列上明明是挨着的，却没有边——因为 $B_5$ 的末条是无条件跳转，执行完它一定走了，落不到下面那条。判断有没有顺序边，看的是"末条会不会跳走"，不是"两块挨不挨着"。

### 代码优化的两个维度

代码优化可以从两个方向来分。

按**依不依赖具体机器**分：机器无关优化和机器相关优化。机器无关优化针对中间代码层做，机器相关优化针对目标代码层做。这一部分重点讨论的是机器无关优化，也就是在中间代码层上做优化。

按**作用范围**分：局部代码优化和全局代码优化。局部代码优化只做单个基本块范围内的优化，全局代码优化面向多个基本块。

| 分法 | 两类 | 差别在哪 |
| :--- | :--- | :--- |
| 按是否依赖机器 | 机器无关优化 / 机器相关优化 | 前者在中间代码层做，后者在目标代码层做 |
| 按作用范围 | 局部代码优化 / 全局代码优化 | 前者限于单个基本块，后者跨多个基本块 |

常用的优化方法有六种：删除公共子表达式、删除无用代码、常量合并、代码移动、强度削弱、删除归纳变量。先把第一种讲透，它最能说明"等价变换"四个字的分量。

### 删除公共子表达式

#### 什么样的出现算公共子表达式

如果表达式 $x\ \text{op}\ y$ 先前已经被计算过——$\text{op}$ 是运算符，$x$、$y$ 是两个运算分量——并且从先前那次计算到现在，$x$ 和 $y$ 的值都没有改变，那么这次出现的 $x\ \text{op}\ y$ 就称为公共子表达式。

既然它的值前面已经算出来了，这次就可以删掉，直接拿上次的结果来用，省下一次重复计算。

条件其实是两条：**同一个表达式**，以及**中间它的运算分量没变**。前一条好认，后一条才是真正的麻烦——下面 $B_6$ 里那个删不掉的 $A[T_1]$，栽的就是第二条。

> **提示**：局部和全局的分界，看的是"上一次计算发生在哪儿"，不是"这次出现发生在哪儿"。上一次计算就在同一个基本块内，是局部公共子表达式；上一次计算在另一个基本块里，是全局公共子表达式。

#### 第一轮：块内就能删掉的两个

看 $B_5$，它原来的指令序列是：

```text
T6  = 4 * i
x   = A[T6]
T7  = 4 * i
T8  = 4 * j
T9  = A[T8]
A[T7] = T9
T10 = 4 * j
A[T10] = x
goto B2
```

第一条算 $4 \times i$ 存进 $T_6$，第三条又算了一遍 $4 \times i$ 存进 $T_7$。这两条之间隔着的是 $x = A[T_6]$，只读了数组，没有动过 $i$——$i$ 的值没变，所以第三条里的 $4 \times i$ 是公共子表达式。它的上一次计算就在本块内，是个**局部**公共子表达式。

同样，$T_8 = 4 \times j$ 和 $T_{10} = 4 \times j$ 之间隔的是 $T_9 = A[T_8]$，也没有动过 $j$，所以 $T_{10}$ 那条同样是局部公共子表达式。

把这两条删掉，凡是用到 $T_7$、$T_{10}$ 的地方分别换成 $T_6$、$T_8$：

```text
T6  = 4 * i
x   = A[T6]
T8  = 4 * j
T9  = A[T8]
A[T6] = T9
A[T8] = x
goto B2
```

九条剩七条。

#### 第二轮：顺着导入弧往上游找

现在 $B_5$ 的第一条是 $T_6 = 4 \times i$。沿着 $B_5$ 的导入弧（进入 $B_5$ 的那些边）逆流而上，会发现这个 $4 \times i$ 在 $B_2$ 里已经算过一次（$T_2 = 4 \times i$），而且从那次计算到这一次，$i$ 的值没有改变。所以这里的 $4 \times i$ 仍然是公共子表达式，只不过上一次计算发生在另一个基本块里，它是**全局**公共子表达式。

同理，$4 \times j$ 在 $B_3$ 里算过（$T_4 = 4 \times j$），中间也没动过 $j$。

用 $T_2$、$T_4$ 替换掉：

```text
x   = A[T2]
T9  = A[T4]
A[T2] = T9
A[T4] = x
goto B2
```

#### 删干净之后，新的又露出来

替换完再一看，$B_5$ 里又冒出一个全局公共子表达式：$A[T_2]$。它在 $B_2$ 里计算过（$T_3 = A[T_2]$），而从那次计算到现在，$T_2$ 没有被重新赋值，中间也没有任何对数组元素的赋值——所以这里的 $A[T_2]$ 就是 $T_3$。

同样，$A[T_4]$ 在 $B_3$ 里计算过（$T_5 = A[T_4]$），也是全局公共子表达式。

改写：$x = A[T_2]$ 写成 $x = T_3$。$T_9 = A[T_4]$ 这一条，$T_9$ 是临时变量，唯一的用处就是给下一条指令赋值，而现在那个值可以直接用 $T_5$，于是整条指令删掉，后面用到 $T_9$ 的地方换成 $T_5$。

```text
x   = T3
A[T2] = T5
A[T4] = x
goto B2
```

七条变五条，再变四条。注意这一轮的新机会，是上一轮替换之后才露出来的：删掉那两条算 $4 \times i$、$4 \times j$ 的指令，$A[T_2]$、$A[T_4]$ 的重复计算才在眼前显形。所以这类优化要一轮一轮往下做，直到再看不出可删的为止。

#### 为什么 $A[T_1]$ 删不得

再看 $B_6$，它原来的指令是：

```text
T11 = 4 * i
x   = A[T11]
T12 = 4 * i
T13 = 4 * n
T14 = A[T13]
A[T12] = T14
T15 = 4 * n
A[T15] = x
```

和 $B_5$ 一样：$4 \times i$ 出现两次（$T_{11}$、$T_{12}$），是局部公共子表达式；$4 \times n$ 出现两次（$T_{13}$、$T_{15}$），也是局部公共子表达式。而且 $4 \times i$ 在 $B_2$ 里算过（$T_2$）、$4 \times n$ 在 $B_1$ 里算过（$T_1$），所以这两个还都是全局公共子表达式。四条重复指令全都能删：

```text
x   = A[T2]
T14 = A[T1]
A[T2] = T14
A[T1] = x
```

到这里，$B_6$ 的第一条 $A[T_2]$ 又能在 $B_2$ 里找到出处（$T_3$），删掉，写成 $x = T_3$。但另一条 $A[T_1]$ 不行。

$A[T_1]$ 确实在 $B_1$ 里算过。问题在于：从那次计算之后、进入 $B_6$ 之前，控制流**有可能**先拐进 $B_5$，而 $B_5$ 里有两条对数组元素的赋值——$A[T_2] = T_5$ 和 $A[T_4] = x$。$T_2$ 是 $4 \times i$、$T_4$ 是 $4 \times j$，$T_1$ 是 $4 \times n$：只要 $i$ 或 $j$ 恰好等于 $n$，这两个下标就跟 $T_1$ 撞上了，那两条赋值写进去的正是 $A[T_1]$ 这个单元。于是 $B_1$ 里算出来的那个 $A[T_1]$，到 $B_6$ 时可能已经过期。

只要有这样一条路存在，就不能赌它不走。所以这里把 $A[T_1]$ 当公共子表达式是不稳妥的：$A[T_2]$ 能删，$A[T_1]$ 不能删，那一趟内存读取必须老老实实留着。

最终 $B_6$ 是：

```text
x   = T3
T14 = A[T1]
A[T2] = T14
A[T1] = x
```

> **易错点**：判断公共子表达式，不能只看"这个式子前面算过"，还得看"从那次计算到现在，它依赖的东西有没有被改过"。对数组元素尤其要小心：不同的下标表达式可能指向同一个单元——$4 \times i$、$4 \times j$、$4 \times n$ 在编译时都不知道具体是多少，谁也不敢保证 $A[T_2]$、$A[T_4]$ 和 $A[T_1]$ 不是同一块内存。

至于计算机怎么自动把这些公共子表达式识别出来，那是后面要专门讲的分析技术；这里先把"为什么能删、为什么不能删"的道理走通。

### 本讲提到的题目

#### 判断 $A[T_1]$ 能不能在 $B_6$ 里删掉

题干：在基本块 $B_6$ 中，$A[T_1]$ 在基本块 $B_1$ 里已经计算过（$T_1 = 4 \times n$ 也是在 $B_1$ 里算出来的）。既然前面算过，能不能把 $B_6$ 里的这次 $A[T_1]$ 当成公共子表达式删掉，直接沿用 $B_1$ 的结果？

解析：判断依据是"从 $A[T_1]$ 的上一次计算到这次出现，这个单元有没有可能被改过"。控制流从 $B_1$ 出来先到 $B_2$，再到 $B_3$、$B_4$；$B_4$ 有两条出路，一条直接进 $B_6$，另一条进 $B_5$。走 $B_5$ 那条路时会执行 $A[T_2] = T_5$ 和 $A[T_4] = x$。这里 $T_2 = 4 \times i$、$T_4 = 4 \times j$、$T_1 = 4 \times n$，只要 $i$ 或 $j$ 等于 $n$，这两条赋值写的就是 $A[T_1]$。编译器无法排除这种可能，"中间没改过"这个条件不成立。

答案：不能。$B_6$ 里的 $A[T_1]$ 不是公共子表达式，这次读取必须保留；同一个块里能删的只有 $A[T_2]$。
