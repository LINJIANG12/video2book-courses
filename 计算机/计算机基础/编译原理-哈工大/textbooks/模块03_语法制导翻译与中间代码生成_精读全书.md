## 语法制导翻译：把语义挂到文法上
> 对应块：BLK08 | 覆盖分集：P35-P39 | 块标题（分集名）：《5-1语法制导翻译概述》

编译的过程可以分成词法分析、语法分析、语义分析、中间代码生成、代码优化和目标代码生成这么几个阶段。真到实现的时候，这条链子并不是一级一级齐齐切开的：语义分析的结果通常直接表示成中间代码的形式，于是语义分析和中间代码生成经常放在一起实现，合起来叫语义翻译。

既然这两步能合，那么再往前挪一步也很自然——把语义翻译也塞进语法分析里，一边做语法分析一边做翻译。这条路走通了，就叫**语法制导翻译**。

> **定义**：语法制导翻译使用上下文无关文法来引导对语言的翻译，是一种面向文法的翻译技术。

注意"引导"这两个字。文法原来只管一件事：这个串合不合法、它的结构长什么样。现在它还要顺带管另一件事：这个结构该翻译成什么。后面所有的内容，都是在回答"怎么让文法把翻译工作带起来"。

要做语义分析，第一个问题是语义信息怎么表示。语法制导翻译的办法是给上下文无关文法中的文法符号设置**语义属性**，用属性来表示语法成分对应的语义信息。

什么算语义信息？一个变量，它的语义属性包括这个变量是什么类型的、它的值是多少、它的值存放在什么地方；一个表达式也一样，属性包括类型、值、地址。

属性定义好了，第二个问题是这些属性值怎么算出来。答案是用与文法符号所在产生式相关联的**语义规则**来计算：对给定的输入串 $x$，先构建 $x$ 的语法分析树，再利用与产生式相关联的语义规则，算出分析树中各节点对应的语义属性值。

把语义规则和语法规则（也就是产生式）联系起来，会牵出两个概念：**语法制导定义**（Syntax-Directed Definition，SDD）和**语法制导翻译方案**（Syntax-Directed Translation Scheme，SDT）。这两个名字很像，分工却很清楚。

### 两种挂法：规格说明与实施方案

#### SDD：产生式配一组语义规则

SDD 是对上下文无关文法的推广：它把每个文法符号和一个语义属性集合相关联，把每个产生式和一组语义规则相关联，这些语义规则用来计算该产生式中各文法符号的属性值。

> **定义**：如果 $X$ 是一个文法符号，$a$ 是它的一个属性，就用 $X.a$ 表示属性 $a$ 在某个标号为 $X$ 的分析树节点上的值。

光看定义不直观，拿一个描述变量声明语句的文法做例子。基础文法是这样的：

```text
D → T L
T → int
T → real
L → L₁ , id
L → id
```

非终结符 $T$ 表示类型（type），给它设一个属性 type；$L$ 用来生成一个标识符序列，给它设一个属性 inh。配上语义规则，就是一张完整的 SDD：

| 产生式 | 语义规则 |
| :--- | :--- |
| $D \to T\,L$ | $L.inh = T.type$ |
| $T \to \text{int}$ | $T.type = \text{int}$ |
| $T \to \text{real}$ | $T.type = \text{real}$ |
| $L \to L_1\, ,\, \text{id}$ | $L_1.inh = L.inh$；$addType(\text{id}.lexeme,\ L.inh)$ |
| $L \to \text{id}$ | $addType(\text{id}.lexeme,\ L.inh)$ |

表里的 $L$ 和 $L_1$ 是同一个符号，只是为了讨论方便，用下标区分它在产生式不同位置上的出现。

从这张表能读出属性的走向：产生式右部是 `int` 时 $T$ 的 type 值就是 int，右部是 `real` 时就是 real；$L$ 的 inh 由 $T$ 的 type 定义；而 $L_1$ 的 inh 又由 $L$ 的 inh 定义。类型信息就是这样从 $T$ 一路传给整条标识符序列的。

#### SDT：把语义动作嵌进产生式右部

> **定义**：SDT 是在产生式右部嵌入了程序片段的上下文无关文法，这些程序片段称为**语义动作**，按惯例放在花括号内。

同一个变量声明文法，写成 SDT 是这样：

```text
D → T { L.inh = T.type } L
T → int { T.type = int }
T → real { T.type = real }
L → L₁ , id { L₁.inh = L.inh; addType(id.lexeme, L.inh) }
L → id { addType(id.lexeme, L.inh) }
```

三个位置各说明一件事：

- 动作放在 $T$ 后面，意思是**分析出 $T$ 之后**就可以用 $T$ 的 type 值算 $L$ 的 inh；
- 动作放在产生式右部末尾，意思是右部符号**全部**分析出来以后，才算左部（$T$）的属性；
- 动作放在 $L_1$ 前面，意思是在分析 $L_1$ **之前**，就可以根据 $L$ 的属性值算 $L_1$ 的 inh。

把这三句合起来就是一句话：**一个语义动作在产生式中的位置，决定了这个动作的执行时间。**

#### 两者的分工

同一件事的两种写法，区别在抽象层次。

SDD 是关于语言翻译的高层次规格说明，它隐蔽了许多具体实现细节，使用者不必显式说明翻译发生的顺序。SDT 可以看作是对 SDD 的一种补充，是 SDD 的具体实施方案：它显式地指明了语义规则的计算顺序，以便说明某些实现细节。

| 对比项 | SDD | SDT |
| :--- | :--- | :--- |
| 形态 | 产生式配一组语义规则 | 产生式右部嵌入语义动作 |
| 抽象层次 | 高层次规格说明 | 具体实施方案 |
| 计算顺序 | 隐含在依赖关系里，不显式说明 | 由动作所在位置显式指明 |
| 回答的问题 | 属性的值怎么互相定义 | 什么时候算、按什么次序算 |

一句话记住分工：SDD 说"算什么"，SDT 说"什么时候算"。

### 属性分两种：综合与继承

SDD 给每个文法符号关联一个属性集合。属性不是同一类东西，按值从哪来分成两种。

#### 综合属性：由子节点算出来

> **定义**：在分析树节点 $N$ 上的非终结符 $A$，它的**综合属性**（synthesized attribute）只能通过 $N$ 的子节点或 $N$ 本身的属性值来定义。

看产生式 $E \to E_1 + T$ 和它关联的规则：

$$E.val = E_1.val + T.val$$

在分析树里，$E$ 是 $E_1$、加号、$T$ 的父节点。规则右边用的是两个儿子 $E_1$ 和 $T$ 的 val 值，所以 val 是 $E$ 的综合属性——父亲的值由儿子的值攒出来。

终结符也可以有综合属性。终结符的综合属性值由词法分析器提供，所以 SDD 里不需要为终结符写计算属性值的语义规则。

#### 继承属性：由父节点和兄弟传下来

> **定义**：在分析树节点 $N$ 上的非终结符 $A$，它的**继承属性**（inherited attribute）只能通过 $N$ 的父节点、$N$ 的兄弟节点或 $N$ 本身的属性值来定义。

还是变量声明那个文法，看 $D \to T\,L$ 和它的规则：

$$L.inh = T.type$$

在分析树里 $T$ 和 $L$ 互为兄弟。规则让 $L$ 的 inh 由兄弟节点 $T$ 的 type 定义，所以 inh 是 $L$ 的继承属性。名字起成 inh，就是为了强调这一点。

终结符没有继承属性。它在词法分析器那里拿到的值已经被归到综合属性里了，不再另开一个继承属性。

| 对比项 | 综合属性 | 继承属性 |
| :--- | :--- | :--- |
| 值从哪来 | 子节点、自身 | 父节点、兄弟节点、自身 |
| 信息流向 | 自底向上 | 自上而下、从左到右 |
| 终结符 | 有（词法值） | 没有 |
| 典型用途 | 算出本节点的结果 | 把上下文、环境传下去 |

### 把属性算一遍：两棵注释分析树

属性值算出来以后就贴在分析树上，每个节点都带属性值的分析树叫**注释分析树**（annotated parse tree）。

#### 综合属性的例子：表达式求值

这个 SDD 用来对一个以小写 $n$ 作为结尾标记的表达式求值。digit 是终结符，综合属性 lexval 由词法分析器给出；$E$、$T$、$F$ 分别表示表达式（expression）、项（term）、因子（factor），三者各设一个属性 val，表示算术值。

| 产生式 | 语义规则 |
| :--- | :--- |
| $L \to E\,n$ | $print(E.val)$ |
| $E \to E_1 + T$ | $E.val = E_1.val + T.val$ |
| $E \to T$ | $E.val = T.val$ |
| $T \to T_1 * F$ | $T.val = T_1.val * F.val$ |
| $T \to F$ | $T.val = F.val$ |
| $F \to (E)$ | $F.val = E.val$ |
| $F \to \text{digit}$ | $F.val = \text{digit}.lexval$ |

从第二、三条规则就能看出 val 是 $E$ 的综合属性：值来自子节点。$T$ 和 $F$ 的 val 同理，也都是综合属性。

这里插一句语义规则的两种写法。语义规则通常写成表达式的形式，直接算出某个属性值；但有时候规则的目的就是产生一个**副作用**，比如打印一个运算结果、往符号表里填一条记录。这时规则写成过程调用的形式，也可以把它看成"定义产生式左部符号的综合属性"的规则——因为它同样用到了子节点的属性值。

输入串取 $3*5+4n$，分析树长这样：

```text
                            L
                        /       \
                      E           n
                   /  |  \
                 E    +    T
                 |          |
                 T          F
               / | \        |
              T  *  F    digit(4)
              |     |
              F  digit(5)
              |
           digit(3)
```

从下往上看：三个 digit 是叶子，往上依次汇成 $F$、$T$、$E$，最后由根节点 $L$ 收口。每个节点用的产生式和算出的值如下：

| 节点 | 所用产生式 | 属性值 |
| :--- | :--- | :--- |
| 三个 digit 节点 | 词法分析器 | lexval = 3、5、4 |
| 三个 $F$ 节点 | $F \to \text{digit}$ | val = 3、5、4 |
| 两个 $T$ 节点（`*` 的左子、`+` 的右子） | $T \to F$ | val = 3、4 |
| `*` 的父节点 $T$ | $T \to T_1 * F$ | val = 3 × 5 = 15 |
| `+` 的左子 $E$ | $E \to T$ | val = 15 |
| 根 $E$ | $E \to E_1 + T$ | val = 15 + 4 = 19 |
| 根 $L$ | $L \to E\,n$ | 打印 19 |

最后一步值得单独说。第一条产生式的规则是打印 $E$ 的 val，它不产生任何新值，只产生副作用；但因为它用到了子节点 $E$ 的 val，可以把它看作是对产生式左部符号 $L$ 的一个**虚综合属性**做定义的规则。这个"虚"字后面画依赖图时还要用到——它让副作用这种没有返回值的动作，也能在属性的框架里被表示成一个节点。

#### 继承属性的例子：变量声明的类型传递

换成前面那张变量声明的 SDD。这个例子里 $T$ 的属性 type 由它的子节点（`int` 或 `real`）定义，是综合属性；$L$ 的属性 inh 由它的兄弟节点或父节点的属性值定义，是继承属性。

$L.inh$ 的值是一个类型。它表示什么？表示 $L$ 生成的这串标识符的类型。

第四条和第五条产生式里的 $addType$ 是个副作用：在符号表里为 `id.lexeme` 创建一条记录，并把该标识符的类型设成 $L.inh$ 所表示的类型。其中 `id.lexeme` 是终结符 id 的综合属性，由词法分析器提供，就是构成这个标识符的字符序列。这个副作用用到了子节点 id 和 $L$ 自身的属性，所以同样可以看作定义 $L$ 的虚综合属性的一条语义规则。

输入句子取 `real a, b, c`，分析树是：

```text
                D
              /   \
             T     L
             |    /|\
          real   L , id(c)
                /|\
               L , id(b)
               |
             id(a)
```

三个叶节点 a、b、c 的 lexeme 由词法分析器直接给出，重点看继承属性 inh 怎么从根一路往下走。

根节点用 $D \to T\,L$：规则说 $L.inh$ 取兄弟 $T$ 的 type 值，于是 real 传到 $L$ 上。

它下面那个 $L$ 用 $L \to L_1\, ,\, \text{id}$，两条规则各管一件事。第一条把 inh 从父节点传给子节点；第二条在符号表里为 `id.lexeme`（也就是 c）建一条记录，类型写成 $L.inh$ 代表的类型，还是 real。

再往下那个 $L$ 用的还是同一条产生式，动作一模一样：inh 继续下传，为 b 建记录，类型 real。

最底下用 $L \to \text{id}$：为 a 建记录，类型取 $L.inh$，仍然是 real。

> **结论**：第四条产生式的规则把 $L$ 的 inh 沿分析树向下传递，这样由 $L$ 生成的标识符序列里的每一个标识符，都能拿到这个类型信息。

#### 属性文法

> **定义**：一个没有副作用的 SDD 也称为**属性文法**（attribute grammar）。属性文法的规则仅通过其他属性值和常量来定义一个属性值。

拿前面那个算术表达式求值的 SDD 改一下：给 $L$ 设一个属性 val，把第一条产生式的副作用换成对 $L$ 的 val 求值，即 $L.val = E.val$。整张表里不再有副作用，这个 SDD 就成了属性文法。

判断标准很干脆：规则右边除了别的属性和常量，不许有别的东西。一旦出现 `print`、`addType` 这类动作，它就不是纯粹在"定义一个值"，而是"做一件事"，那就不算属性文法。

### 求值顺序：依赖图与拓扑排序

SDD 为文法符号设置了语义属性，对给定的输入串 $x$，应用语义规则就能算分析树中各节点的属性值。剩下的问题是：按什么顺序算？

语义规则建立了属性之间的依赖关系。要对分析树节点的某个属性求值，必须先求出这个属性值所依赖的所有属性值。这句约束听起来像废话，但它把"求值顺序"变成了一个纯粹的图论问题。

#### 依赖图怎么画

> **定义**：依赖图（dependency graph）是一个有向图，描述了分析树中节点属性之间的依赖关系。对分析树中每个标号为 $X$ 的节点的每个属性 $a$，依赖图中都有一个节点与之对应；如果属性 $X.a$ 的值依赖于属性 $Y.b$ 的值，依赖图中就有一条从 $Y.b$ 的节点指向 $X.a$ 的节点的有向边。

画之前先约定摆法：继承属性摆在所对应节点的左边，综合属性摆在右边。type 是 $T$ 的综合属性，摆右侧；inh 是 $L$ 的继承属性，摆左侧。

拿 `real a, b, c` 那个 SDD 画一遍，三条构造线索足够：

- 根节点用 $D \to T\,L$，规则说 $L.inh$ 依赖 $T.type$，于是有一条边 $T.type \to L.inh$；
- 下面每个 $L$ 节点用 $L \to L_1\, ,\, \text{id}$，第一条规则说子节点的 inh 依赖父节点的 inh，于是有一条边从父的 $L.inh$ 指向子的 $L_1.inh$；
- 同一条产生式的第二条规则是副作用 $addType$，按前面的说法，把它看成定义左部符号 $L$ 的虚综合属性的规则。依赖图里就给这个 $L$ 设一个虚节点，从 $L.inh$ 和 $id.lexeme$ 各引一条边指向它。另外两个 $L$ 节点照此办理。

画出来是这样，三列分别对应根 $L$、生成 b 的那个 $L_1$、生成 a 的那个 $L_2$：

```text
  T.type
    │
    ▼
  L.inh ────► L1.inh ────► L2.inh
    │            │             │
    ▼            ▼             ▼
  L.虚         L1.虚         L2.虚
    ▲            ▲             ▲
    │            │             │
 c.lex        b.lex         a.lex
```

横向那排箭头是继承属性沿分析树向下传，竖向每一列是一个 $L$ 节点上"自己的 inh 加上对应 id 的 lexeme，共同决定本节点的虚综合属性"。

#### 拓扑排序给出一个可行顺序

> **定义**：一个可行的求值顺序，是满足下列条件的节点序列 $n_1, n_2, \dots, n_k$——如果依赖图中有一条从 $n_i$ 到 $n_j$ 的边，那么在序列中 $n_i$ 排在 $n_j$ 的前面。这样的排序把一个有向图变成了一个线性排序，称为这个图的**拓扑排序**（topological sort）。

把刚才那个依赖图的十个属性节点编号 1 到 10，编号本身就是它的一个拓扑排序。各节点的依赖关系是：

| 节点 | 依赖的节点 |
| :--- | :--- |
| 1、2、3、4 | 无（叶子上的属性） |
| 5 | 4 |
| 6 | 5、3 |
| 7 | 5 |
| 8 | 7、2 |
| 9 | 7 |
| 10 | 9、1 |

检查的办法很朴素：依赖者的序号都大于被依赖者的序号，所以算到某个属性时，它依赖的值一定都已经算完了。

拓扑排序不唯一。1、2、3、4 这四个节点互不依赖，顺序可以任意调换；6 和 7 都依赖 5，但它俩之间互不依赖，可以对调；8 和 9 都依赖 7，它俩之间也互不依赖，同样可以对调。换一组相对次序，就是另一个合法的求值顺序。

到这里可以总结出一条好用的性质：**只具有综合属性的 SDD，可以按任何自底向上的顺序计算它们的值。** 因为每个节点的值只依赖子节点，自底向上走到哪儿，儿子总是先算完的。

#### 循环依赖：什么时候算不出来

同时具有继承属性和综合属性的 SDD，就没这么幸运了——不能保证存在一个顺序，能把各个节点上的属性都算出来。

看一个只有一条产生式的例子：$A \to B$，配两条语义规则：

- $A.s = B.i$
- $B.i = A.s$

先判断这两个属性各是哪一类。第一条规则算的是 $A$ 的属性 $s$，$A$ 是产生式左部符号，所以 $s$ 只能是 $A$ 的综合属性：假如 $s$ 是继承属性，它的值就可能依赖 $A$ 的兄弟节点或父节点的属性值，而这条产生式里根本不会出现 $A$ 的父节点和兄弟节点，只出现了 $A$ 的子节点，继承属性无从下手。同理，第二条规则算的是 $B$ 的属性 $i$，$B$ 是产生式右部符号，所以 $i$ 只能是 $B$ 的继承属性：假如 $i$ 是综合属性，它就要依赖 $B$ 的子节点，而这条产生式里只出现 $B$ 的父节点和兄弟节点，不出现子节点，综合属性同样无从下手。

于是两条规则互指：$A$ 的 $s$ 要等 $B$ 的 $i$，$B$ 的 $i$ 要等 $A$ 的 $s$。

```text
   A.s ──────► B.i
     ▲           │
     └───────────┘
```

依赖图里出现一个环，先算 $A.s$ 还是先算 $B.i$ 就说不清了。

> **结论**：如果依赖图中没有环，那么至少存在一个拓扑顺序；有环，就一个都没有。

麻烦在于，给定一个 SDD，很难判定是否存在某棵语法分析树，使它的属性之间出现循环依赖。逐个输入去试显然不现实。

幸运的是，存在 SDD 的一些有用子类，能够保证对每棵语法分析树都存在求值顺序，因为它们不允许产生带环的依赖图。再进一步，其中有两类 SDD 可以和自顶向下、自底向上的语法分析过程一起高效实现：一类叫**S 属性定义**（S-SDD），一类叫 **L 属性定义**（L-SDD）。

### 两个好用的子类：S 属性与 L 属性

#### S 属性定义

> **定义**：仅仅使用综合属性的 SDD 称为 **S 属性的 SDD**，也叫 S 属性定义，简称 **S-SDD**。

前面那个 $3*5+4n$ 的求值 SDD 就是典型：所有属性都是综合属性，每个值都是靠子节点算出来的。

S 属性带来的好处很直接。如果一个 SDD 是 S 属性的，每个节点的属性值都只依赖子节点的属性值，那就可以按分析树节点的任何自底向上的顺序，把各节点的属性值算出来。所以 S 属性定义可以在自底向上的语法分析过程中实现——这一点在讲 SDT 的时候会变成一条非常省事的实施路线。

#### L 属性定义的正式条件

L 属性定义（L-SDD）的直观含义是：在一个产生式所关联的各属性之间，依赖图的边可以从左指向右，但不能从右指向左，所以叫 L 属性。这里的 L 是 left 的首字母。

> **定义**：一个 SDD 是 L 属性定义，当且仅当它的每个属性要么是一个综合属性，要么是满足如下条件的继承属性——假设存在产生式 $A \to X_1 X_2 \dots X_n$，其右部符号 $X_i$ 的继承属性仅依赖于下列三类属性：
>
> 1. 父节点 $A$ 的继承属性；
> 2. 产生式中 $X_i$ 左边的符号，也就是 $X_1, X_2, \dots, X_{i-1}$ 的属性，不能依赖 $X_i$ 右边的符号，也就是 $X_{i+1}, \dots, X_n$ 的属性；
> 3. $X_i$ 本身的属性，但 $X_i$ 的全部属性不能在依赖图中形成环。

这三条里，第 2 条最要紧：**只许往左看，不许往右看**。左边和上边的信息都在分析到 $X_i$ 之前就已经拿到了，右边的还没分析出来，依赖它就是依赖未来。

顺便能推出一个包含关系：**每个 S 属性定义都是 L 属性定义。** 因为 S 属性定义里只有综合属性，而 L 属性定义对综合属性没有任何限制；S 属性定义里压根没有继承属性，自然也就不会违反 L 属性定义对继承属性的那三条限制。

> **易错点**：$X_i$ 的继承属性为什么只能依赖父节点 $A$ 的**继承**属性，不能依赖 $A$ 的**综合**属性？因为 $A$ 的综合属性本身可以依赖子节点的属性，当然也包括子节点的继承属性。要是子节点的继承属性再回头依赖 $A$ 的综合属性，这一来一回就成环了——$A$ 的综合属性等子节点，子节点的继承属性等 $A$ 的综合属性。这条限制不是抠字眼，是在防环。

#### 判定练习：一个合格、一个不合格

先看一个合格的。这是一个只处理乘法的项文法，配上语义规则：

| 产生式 | 语义规则 |
| :--- | :--- |
| $T \to F\,T'$ | $T'.inh = F.val$；$T.val = T'.syn$ |
| $T' \to *\,F\,T_1'$ | $T_1'.inh = T'.inh \times F.val$；$T'.syn = T_1'.syn$ |
| $T' \to \varepsilon$ | $T'.syn = T'.inh$ |
| $F \to \text{digit}$ | $F.val = \text{digit}.lexval$ |

判断谁是综合、谁是继承，看规则算的是产生式哪一边的符号。四条规则算的是所在产生式左部符号的属性（$T$、两个 $T'$、$F$），所以这几个都是综合属性；两条规则算的是产生式右部符号 $T'$ 的属性，所以 $T'.inh$、$T_1'.inh$ 是继承属性。

L 属性定义对综合属性没有限制，只限制继承属性，所以这个 SDD 是不是 L-SDD，全看那两个继承属性依赖了什么：

- $T'.inh$ 依赖它左边兄弟的 $F.val$——往左看，不违反限制；
- $T_1'.inh$ 依赖父亲的 $T'.inh$，还依赖左边兄弟的 $F.val$——父节点的继承属性加左兄弟，仍然不违反限制。

> **结论**：这个 SDD 是 L 属性定义。

再看一个不合格的。这个 SDD 左边有两个综合属性，右边有 $L$、$M$、$R$、$Q$ 四个符号，各带一个继承属性，四条规则分别定义它们。把四条继承属性的依赖对象列出来，问题一眼就能看见：

| 继承属性 | 依赖谁 | 是否违反 L 条件 |
| :--- | :--- | :--- |
| $L.i$ | 父亲 $A$ 的继承属性 | 否 |
| $M.i$ | 左兄弟 $L$ 的综合属性 $L.s$ | 否 |
| $R.i$ | 父亲 $A$ 的继承属性 | 否 |
| $Q.i$ | **右兄弟** $R$ 的综合属性 $R.s$ | 是 |

前三条都合规：父节点的继承属性可以依赖，左兄弟的属性可以依赖。第四条越界了——$Q$ 的继承属性依赖它右边兄弟 $R$ 的综合属性。按 L 属性定义，产生式右部符号的继承属性只能依赖左边兄弟的属性值，不能依赖右边兄弟的属性值，而 $R$ 正站在 $Q$ 的右边。

> **结论**：这一条规则就足以让整个 SDD 不算 L 属性定义。判定 L-SDD 不需要逐条挑毛病，找到一条越界的继承属性就可以收工。

### 把 SDD 落成 SDT

SDT 是在产生式右部嵌入程序片段的 CFG，这些程序片段称为语义动作。花括号括起来的部分就是动作所在。

SDT 是 SDD 的具体实施方案，但并不是随便什么 SDD 都能顺手落成 SDT 再塞进分析过程里。真正值得关注的是两类：基本文法可以用 LR 分析技术、并且 SDD 是 S 属性的；基本文法可以用 LL 分析技术、并且 SDD 是 L 属性的。在这两种情况下，SDT 都可以在语法分析过程中实现。

#### S 属性定义：动作一律放末尾

S 属性定义里所有属性都是综合属性，所以只有当所有子节点都分析完毕，才谈得上计算父节点的综合属性。既然要等右部全部分析完，那么计算综合属性的语义动作就只能放在产生式的最右边。

> **结论**：把 SDD 转成 SDT 的方法非常简单——把每个语义规则都放在所在产生式右部的最后。

前面那个表达式求值的 SDD 全是综合属性，直接把语义规则挂到各自产生式右部末尾就行：

```text
L → E n          { print(E.val) }
E → E₁ + T     { E.val = E₁.val + T.val }
E → T          { E.val = T.val }
T → T₁ * F     { T.val = T₁.val * F.val }
T → F          { T.val = F.val }
F → ( E )      { F.val = E.val }
F → digit      { F.val = digit.lexval }
```

跟 SDD 的表比起来，规则的内容一个字没改，变的只是位置：原来规则列在产生式旁边的表里，现在嵌进产生式右部，成了文法的一部分。

#### 在 LR 分析栈上执行：栈记录要带属性域

S 属性定义的文法如果能用 LR 分析技术，它的 SDT 就能在 LR 分析过程里实现。

为什么这么顺？因为 S 属性的 SDT 里所有语义动作都在产生式右部末尾，也就是只有等右部所有符号都分析出来，才执行动作。而 LR 分析恰好有一个"右部所有符号都分析完了"的时刻——**归约**。归约发生时执行相应的语义动作，时机天然对得上。

为了在语法分析的同时做语义分析，LR 分析栈要扩展：在分析栈的记录里加一个附加的域，专门存综合属性值。

一个文法符号可能设了多个综合属性，于是有两种存法：

- 属性都很小的时候，直接把栈记录做大，塞得下所有属性就行。最简单，就算有些字段永远用不上，也不会有太大问题；
- 属性大小没有限制的时候（比如字符串），最好把属性值放到栈外一块较大的公共存储区，栈记录里只存指向它的指针。

> **提示**：选择标准不是"哪个更高级"，而是"属性大小有没有上限"。定长的小属性放大栈记录里，读写都是直接寻址；变长属性放外面，栈记录退回成指针，避免每条记录都被最长的那个属性撑爆。

语义动作里写的都是抽象的定义式，直接扔给机器是执行不了的，得改写成具体的栈操作。

假如有产生式 $A \to XYZ$，$A$ 的综合属性由 $X$、$Y$、$Z$ 的属性定义，动作放在右部末尾，于是在把 $XYZ$ 归约为 $A$ 的时候执行。归约前后的栈格局是这样（栈顶在下）：

```text
    before reduction                        after reduction

    +--------------------------+            +--------------------------+
    |  ...                     |            |  ...                     |
    +--------------------------+            +--------------------------+
    |  X   val: tau(X)         | <- top-2   |  A   val: tau(A)         | <- new top
    +--------------------------+            +--------------------------+
    |  Y   val: tau(Y)         | <- top-1
    +--------------------------+
    |  Z   val: tau(Z)         | <- top
    +--------------------------+
```

归约前，栈顶 `stack[top]` 放的是 $Z$ 的记录，`stack[top-1]` 是 $Y$，`stack[top-2]` 是 $X$，三个属性值分别落在各自记录的 val 字段里。归约时 $XYZ$ 一起出栈，而 $A$ 进入 $X$ 原来所在的位置，所以 `stack[top-2].symbol` 变成 $A$，$A$ 的属性值也存进 `stack[top-2].val`；随后 `top-2` 成为新的栈顶。

于是一句 $A.val = f(X.val, Y.val, Z.val)$，改写成可执行的形式就是：

```text
stack[top-2].val = f(stack[top-2].val, stack[top-1].val, stack[top].val)
```

注意"$A$ 落在 $X$ 的位置"这件事：归约是把右部这一串整体替换成左部符号，替换后新符号占的正是右部最左那个符号的格子，所以结果写回 `top-2`，而不是别处。

#### 桌面计算器：从移进到归约的完整走查

把上面的改写落到一个具体的计算器 SDT 上。这里只列走查用到的几条产生式，语义动作里也只写 val 字段的栈操作；符号栈和状态栈的操作用常规的移进—归约流程处理，不写进动作里。

```text
E → E + T   { stack[top-2].val = stack[top-2].val + stack[top].val }
E → T       { /* 值不动 */ }
T → T * F   { stack[top-2].val = stack[top-2].val * stack[top].val }
T → F       { /* 值不动 */ }
F → digit   { /* 值不动，词法值已在栈中 */ }
```

输入串取 `3 * 5 + 4`。初始时状态栈里是 0 号状态，符号栈里是栈底标记 `$`（`$` 没有属性，属性值为空），输入指针指向第一个符号 3。

| 步 | 状态栈 | 符号栈（属性值） | 剩余输入 | 动作 |
| :--- | :--- | :--- | :--- | :--- |
| 0 | 0 | `$` | `3 * 5 + 4 $` | 初始格局 |
| 1 | 0 5 | `$` digit(3) | `* 5 + 4 $` | 0 号状态遇 digit 移入，进入 5 号状态 |
| 2 | 0 3 | `$` F(3) | `* 5 + 4 $` | 5 号状态归约 digit → F，值不动 |
| 3 | 0 2 | `$` T(3) | `* 5 + 4 $` | 3 号状态归约 F → T，值不动 |
| 4 | 0 2 7 | `$` T(3) `*` | `5 + 4 $` | 2 号状态遇 `*` 移入，进入 7 号状态 |
| 5 | 0 2 7 5 | `$` T(3) `*` digit(5) | `+ 4 $` | 7 号状态遇 digit 移入，词法值 5 |
| 6 | 0 2 7 10 | `$` T(3) `*` F(5) | `+ 4 $` | 5 号状态归约 digit → F，7 号状态遇 F 转 10 号 |
| 7 | 0 2 | `$` T(15) | `+ 4 $` | 10 号状态归约 T * F → T，3 × 5 = 15 写回 `top-2` |
| 8 | 0 1 | `$` E(15) | `+ 4 $` | 2 号状态遇 `+` 归约 T → E，0 号状态遇 E 转 1 号 |
| 9 | 0 1 6 | `$` E(15) `+` | `4 $` | 1 号状态遇 `+` 移入，进入 6 号状态 |
| 10 | 0 1 6 5 | `$` E(15) `+` digit(4) | `$` | 6 号状态遇 digit 移入，词法值 4 |
| 11 | 0 1 6 9 | `$` E(15) `+` T(4) | `$` | 归约 digit → F、F → T，6 号状态遇 T 转 9 号 |
| 12 | 0 1 | `$` E(19) | `$` | 9 号状态遇 `$` 归约 E + T → E，15 + 4 = 19 |
| 13 | 0 1 | `$` E(19) | `$` | 1 号状态遇 `$` 接受，句子分析完毕 |

表里最值得盯的是第 7 步和第 12 步，因为只有这两步真正改了属性值，其余归约都是"值不动"。

第 7 步归约 $T \to T * F$：栈顶三个符号依次是 $T(3)$、`*`、$F(5)$，动作取 `stack[top-2].val`（3）乘 `stack[top].val`（5），结果 15 写回 `stack[top-2].val`，然后三个符号连同它们的状态一起出栈，$T$ 进栈。

第 12 步归约 $E \to E + T$：栈顶三个符号是 $E(15)$、`+`、$T(4)$，动作把 15 与 4 相加，19 写回 `stack[top-2].val`，三个符号出栈，$E$ 进栈。0 号状态遇 $E$ 转 1 号状态，1 号状态遇 `$` 成功接收。

> **结论**：分析结束时，文法开始符号 $E$ 的属性值就是整个表达式的值——19。语法分析走完，语义值也顺手算完了，没有额外的一遍。

#### L 属性定义：动作插在符号出现之前

L 属性定义不能照搬"一律放末尾"的办法。它的继承属性是往下、往右传的，如果全都压到产生式末尾，动作执行时左边的信息早就用不上了。转换规则是两条：

1. 将计算某个非终结符号 $A$ 的继承属性的动作，插入到产生式右部中**紧靠在 $A$ 的本次出现之前**的位置上；
2. 将计算一个产生式左部符号的综合属性的动作，放置在这个产生式右部的**最右端**。

道理和前面一样，还是"位置决定执行时间"：继承属性要在符号被分析之前就准备好，所以动作必须站在它前面；综合属性要等右部全部分析完，所以动作只能站到最后。

拿前面判定为 L-SDD 的那个项文法做转换：

```text
T  → F { T'.inh = F.val } T' { T.val = T'.syn }
T' → * F { T₁'.inh = T'.inh * F.val } T₁' { T'.syn = T₁'.syn }
T' → ε { T'.syn = T'.inh }
F  → digit { F.val = digit.lexval }
```

第一条产生式：$T'.inh$ 是右部符号 $T'$ 的继承属性，动作插在 $T'$ 即将出现的位置，也就是 $F$ 和 $T'$ 之间；$T.val$ 是左部符号的综合属性，动作追加到末尾。

第二条产生式同理：$T_1'.inh$ 是继承属性，动作插在 $T_1'$ 出现之前、紧跟 $F$ 之后；$T'.syn$ 是综合属性，动作放在末尾。

第三、第四条产生式的规则算的都是左部符号的综合属性，直接追加到右部末尾即可。

#### 顺带确认：这个文法是 LL(1)

一个 L 属性定义，如果它的基本文法可以用 LL 分析技术，那么它的 SDT 既能在 LL 分析过程中实现，也能在 LR 分析过程中实现。

判断一个文法是不是 LL 文法，看的是具有相同左部的产生式，它们的候选集（SELECT 集）是否互不相交。

这个文法里左部为 $T'$ 的产生式有两条。第二条产生式 $T' \to *\,F\,T_1'$ 的 SELECT 集里只有一个终结符 `*`；第三条产生式 $T' \to \varepsilon$ 的 SELECT 集就是 $\text{FOLLOW}(T')$。

$\text{FOLLOW}(T')$ 怎么算出来只有一个 `$`？$T$ 是开始符号，$T'$ 出现在 $T \to F\,T'$ 的末尾，所以 $\text{FOLLOW}(T')$ 包含 $\text{FOLLOW}(T)$，而 $\text{FOLLOW}(T)$ 只有输入结束符 `$`；再看第二条产生式以 $T_1'$ 结尾，$\text{FOLLOW}(T_1')$ 也并进 $\text{FOLLOW}(T')$，仍然只有 `$`。

两组 SELECT 集一个是 `{*}`、一个是 `{$}`，互不相交，所以这是一个 LL(1) 文法。

> **结论**：这个 L 属性定义的基本文法是 LL(1) 的，转换出来的 SDT 可以在 LL 或 LR 分析过程中实现。

LL 分析具体又分两条路：一条是在非递归的预测分析过程中做语义翻译，另一条是在递归的预测分析过程中做语义翻译。这两条路各有各的动作摆放讲究，后面分别展开。

## 预测分析中的语义翻译：栈记录、函数与标记非终结符
> 对应块：BLK09 | 覆盖分集：P40-P42 | 块标题（分集名）：《5-6在非递归的预测分析过程中进行翻译》

语法制导翻译方案（SDT）说的是属性怎么在语法树上流动：继承属性从父亲和左兄弟流向自己，综合属性从孩子流回父亲。预测分析走的是另一条路，它不建树，只有一个栈加一个输入指针，一步一步把当前句型最左边的非终结符换掉。

把这两件事接到同一条流水线上，冲突点很具体：属性什么时候算，算出来的值放在哪儿。非递归预测分析里，答案是把分析栈改造成同时装得下属性值和待执行代码的结构；递归预测分析里，答案是把每个非终结符对应的过程升级成函数，形参接继承属性、返回值送综合属性；到了自底向上的 LR 分析，归约时机和内嵌动作的时机正面相撞，得先把文法改写一遍，用标记非终结符把动作搬到产生式末尾。三条路的载体不同，解的是同一个矛盾。

### 非递归预测分析：把分析栈改成三类记录

要在非递归的预测分析过程中做翻译，第一件事是把语法分析栈扩展一下。原来栈里只放文法符号，现在还要放属性值，以及“接下来该执行哪段代码”的线索。

先弄清楚一件事：为什么非终结符的两类属性不能挤在同一条记录里。

#### 两类属性分开存，动作另立一条记录

对一个非终结符 $A$ 来说，继承属性和综合属性的计算时机根本不同。继承属性的值只依赖父亲和左兄弟，$A$ 即将出现的那一刻就能算——这时 $A$ 还没展开，子树一个符号都没进栈，但算继承属性要的信息已经齐了。综合属性必须等 $A$ 的所有子结点都分析完毕才可能算出来。

时机不同，住处就得分开。$A$ 的继承属性存在 $A$ 本身的记录里；另设一种记录类型 $A_{syn}$ 专存 $A$ 的综合属性，位置紧贴在 $A$ 本身记录的下面。

压在下面不是随便挑的。$A$ 一旦被产生式展开，$A$ 本身这条记录就要出栈，把位置让给右部的符号；而综合属性得一直留到子树分析完。把它压在下面，$A$ 出栈时它自然留在栈里等结果。

> **结论**：$A$ 出栈，$A$ 的综合记录不能出栈——这是栈式翻译的第一条纪律，后面每一步都在核对它。

除了属性，SDT 里还有语义动作要执行。为此再加第三种记录类型 `action`，里面存一个指针，指向将要被执行的语义动作代码。三类记录凑齐，栈就同时装得下符号、属性和待办事项：放符号本身与继承属性的、放综合属性的、放待执行动作的。

#### 把语义动作换成动作符号

原 SDT 里有六个语义动作，先给它们起名 $a_1$ 到 $a_6$，再用这些符号把方案里的动作逐块替换掉，得到这样四条产生式：

```text
T   -> F a1 T' a2
T'  -> * F a3 T' a4
T'  -> a5
F   -> digit a6
```

改写后的 SDT 可以看成一类特殊的上下文无关文法，符号只有三类：终结符，比如 `*` 和 `digit`；非终结符，比如 $T$、$T'$、$F$；动作符号 $a_1$ 到 $a_6$。动作符号在栈上占一条动作记录，终结符和非终结符按前面的规则占一条或两条记录。

六个动作各自算什么，光看符号看不出来。拿 `3 * 5` 走一遍就全清楚了，每一步都把栈画出来，左端是栈顶。

#### 走一遍 3 * 5

初始时刻输入指针指向第一个符号 `3`。自顶向下分析必须先处理最左符号，所以栈底在右侧、栈顶在左侧。栈里只有开始符号 $T$：$T$ 没有继承属性，本身记录的属性字段是空的；$T$ 有综合属性，所以后面跟着一条 $T_{syn}$，用来存 $T$ 的 `value`。

```text
栈（左为栈顶）:  T | T_syn
输入          :  3 * 5 $
```

栈顶 $T$ 就是当前句型的最左非终结符。按第一条产生式把 $T$ 换成 $F\ a_1\ T'\ a_2$：$T$ 出栈，$T_{syn}$ 留在原地。$F$、$a_1$、$T'$、$a_2$ 进栈，$F$ 和 $T'$ 都有综合属性，各自的综合记录跟着本身记录一起进；$T'$ 还有继承属性，`in` 就存在 $T'$ 那条记录里。

```text
栈:  F | F_syn | a1 | T'(in) | T'_syn | a2 | T_syn
输入:  3 * 5 $
```

栈顶是 $F$，按第四条产生式换成 `digit a6`。`digit` 是终结符，只有综合属性，值由词法分析器给出，那个 3 就直接存在 `digit` 这条记录里。

栈顶的 `digit` 和当前输入符号匹配，可以出栈。但按第四条产生式，紧跟在 `digit` 后面的 $a_6$ 要用它的值算 $F$ 的综合属性，所以出栈之前先把值备份进 $a_6$ 记录的对应字段。备份完，`digit` 出栈，输入指针移到 `*`。

栈顶露出动作记录 $a_6$，里面存着算 $F$ 综合属性的代码指针。它要写的目标在哪儿？$F$ 进栈之前就占着 $a_6$ 现在这个位置，$F_{syn}$ 一直压在 $F$ 下面没动过；$F$ 被 `digit a6` 取代之后，$a_6$ 顶了 $F$ 的位置，$F_{syn}$ 自然紧贴在 $a_6$ 下面。所以 $a_6$ 的执行代码只有一句：把栈顶的属性值复制到 `top-1` 的属性字段。执行完，$F$ 的 `value` 是 3，$a_6$ 出栈。

$F_{syn}$ 成了栈顶，带着刚算出的 3。按第一条产生式，它下面的 $a_1$ 要用这个值算 $T'$ 的继承属性，所以 $F_{syn}$ 出栈前把值备份进 `top-1` 的 $a_1$。$a_1$ 执行：把栈顶的值写进 `top-1`，也就是 $T'$ 记录里的 `in`，得到 $T'$ 的继承属性 3。$a_1$ 出栈。

```text
栈:  T'(in=3) | T'_syn | a2 | T_syn
输入:  3 * 5 $
```

栈顶 $T'$，当前输入是 `*`，选第二条产生式：$T'$ 出栈，`*`、$F$、$a_3$、$T'$、$a_4$ 进栈。$T'$ 身上带着 `in = 3`，而按产生式，$a_3$ 要用它算内层 $T_1'$ 的继承属性，所以 $T'$ 出栈前必须把 `in` 备份到 $a_3$ 的记录里。$a_3$ 落在哪个位置，数一数就知道。

右部五个符号进栈，其中 $F$ 和 $T_1'$ 各多带一条综合记录，一共七条：`*` 一条，$F$ 两条，$a_3$ 一条，$T_1'$ 两条，$a_4$ 一条。出栈一条、进栈七条，新的栈顶比原来的 top 高 6。

从原 top 往深处数：$a_4$ 落在 $T'$ 原来的位置上，就是 top；$T_1'_{syn}$ 在 top+1；$T_1'$ 本身在 top+2；$a_3$ 在 top+3。

```text
        top      top+1       top+2      top+3
         |         |           |          |
         v         v           v          v
      [ a4 ] [ T1'_syn ]    [ T1' ]    [ a3 ]
                                          ^
                               备份 T'.in 的落点
```

`top+3` 这个偏移是按出栈前那一刻的栈顶算的。等七条记录真的进栈、`*` 匹配出栈、$F$ 又展开并算完，$a_3$ 离新栈顶就很近了——$F_{syn}$ 出栈时，$a_3$ 正好在 `top-1`。同一个物理单元在不同时刻有不同的 top 偏移，唯一不变的是“紧贴在下面”这个相邻关系。

> **易错点**：把某个绝对位置背下来，换一条产生式就错。所有偏移都是相对当时的栈顶算的，时刻一变就要重数。

`*` 与输入匹配，输入指针移到 5。栈顶 $F$ 按第四条产生式换成 `digit a6`；`digit` 匹配 5，出栈前把词法值 5 备份进 $a_6$；$a_6$ 执行，$F$ 的 `value` 变成 5，出栈。$F_{syn}$ 带着 5 出栈，把值备份进 $a_3$；$a_3$ 算出内层 $T_1'$ 的 `in`，$3 \times 5 = 15$，出栈。

栈顶是 $T_1'$，输入已经是 `$`，选第三条产生式：$T_1'$ 出栈，只有 $a_5$ 进栈。$a_5$ 要用 $T_1'$ 的继承属性，而它落的正是 $T_1'$ 刚才的位置（top），所以这次“备份”等于把值留在原地，栈顶属性字段根本没变，还是 15。$a_5$ 干的事是把继承属性变成综合属性：$T_1'$ 的 `syn` 等于它的 `in`，也就是 15。$a_5$ 出栈。

接下来是一路往上的交接：$T_1'_{syn}$ 出栈，把 15 备份给下面的 $a_4$；$a_4$ 算出 $T'$ 的 `syn`，也是 15，出栈；$T'_{syn}$ 出栈，把 15 备份给下面的 $a_2$；$a_2$ 算出 $T$ 的 `value` 等于 15，出栈；$T_{syn}$ 出栈。栈空了，输入指针停在输入串末尾，分析成功，开始符号的 `value` 就是 15。

每个动作记录要用的值，都来自它左边那些符号的记录；在栈里，这些记录就压在更靠栈顶的一侧。右部最后一个动作记录算完，值最终落进左部符号的综合记录。整条链子就是靠这个方向传回去的。

#### 一个 SDT 定下来，每个符号的代码就定下来

走完一遍能看出，栈上的执行代码只有两种：综合记录出栈时，把值复制给它下面那个特定的动作记录；变量展开、本身记录出栈时，如果带继承属性，就把继承属性值复制给它下面那个特定的动作记录。属性字段空的记录没有代码。

> **结论**：一个 SDT 定下来，其中每个符号对应的执行代码也就定下来了——只需要知道它下面紧挨着谁，偏移是多少。

拿第一条产生式核对一遍。右部四个符号 $F$、$a_1$、$T'$、$a_2$，因为 $F$ 和 $T'$ 各带一条综合记录，实际是六条记录：$F$、$F_{syn}$、$a_1$、$T'$、$T'_{syn}$、$a_2$。

| 记录 | 存什么 | 执行代码 |
| :--- | :--- | :--- |
| $F$ | 空（$F$ 没有继承属性） | 无 |
| $F_{syn}$ | $F$ 的 `value` | 出栈时复制到 `top-1`，即 $a_1$ |
| $a_1$ | $F$ 的 `value` 备份 | 把栈顶复制到 `top-1`，即 $T'$ 记录里的 `in` |
| $T'$ | $T'$ 的 `in` | 展开时按所选产生式备份：选第二条送 `top+3` 的 $a_3$；选第三条原地不动 |
| $T'_{syn}$ | $T'$ 的 `syn` | 出栈时复制到 `top-1`，即 $a_2$ |
| $a_2$ | $T'$ 的 `syn` 备份 | 把栈顶复制到 `top-1`，即 $T_{syn}$ |

$F$ 本身没有属性，无代码。$F_{syn}$ 出栈把值交给 `top-1` 的 $a_1$。$a_1$ 执行时把栈顶写进 `top-1`，那是 $T'$ 的记录，正好是 `in` 的住处。$T'$ 是非终结符，得按当前输入选产生式：选第二条，把 `in` 备份到 `top+3` 的 $a_3$；选第三条，$a_5$ 落在原地，值不动。$T'_{syn}$ 出栈交给 `top-1` 的 $a_2$，$a_2$ 再把栈顶写进 `top-1`——那是 $T_{syn}$，因为 $a_2$ 顶的是 $T$ 原来的位置，而 $T_{syn}$ 一直压在 $T$ 下面。

第二条产生式按同样的思路推。右部五个符号、七条记录，出栈一条、进栈七条，新栈顶是 `top+6`。$F_{syn}$ 出栈时下面紧挨着 $a_3$，$T_1'_{syn}$ 出栈时下面紧挨着 $a_4$，都按 `top-1` 交给动作记录。$T_1'$ 的展开和 $T'$ 一样，按所选的产生式决定继承属性备份到哪儿。

第三条产生式里 $a_5$ 落在 top，所以它的“备份”是原地不动，真正要执行的那一步就是把 `in` 复制成 `syn`，还是写进 `top-1`。第四条产生式里 `digit` 出栈前把词法值备份给 $a_6$，$a_6$ 再把栈顶复制到 `top-1` 的 $F_{syn}$。

### 递归预测分析：把过程升级成函数

递归预测分析里，每个非终结符对应一个过程：过程体看着当前输入符号选产生式，遇到终结符就匹配，遇到非终结符就递归调用。要在这套东西上算属性，办法很直接——把过程升级成函数。

#### 过程升级成函数：形参接继承，返回值送综合

为每个非终结符 $A$ 造一个函数：$A$ 的每个继承属性对应函数的一个形参，函数的返回值就是 $A$ 的综合属性。$T'$ 有一个继承属性 `inh`、一个综合属性 `syn`，那么这个函数收一个形参 `T'.inh`，返回 `T'.syn`。

```text
语法分析时的过程 T'()            扩展后的函数 T'(T'.inh) -> T'.syn
        |                                |
        |  只负责识别                     |  识别逻辑原样保留
        |  按 token 选产生式              |  继承属性由形参送进来
        |  匹配终结符、递归调用           |  综合属性由返回值送出去
```

骨架还是原来那套，扩展的部分全在“怎么把属性接进来、送出去”上。

#### 右部每个符号都要有落脚点

函数体里要引用产生式右部各符号的属性，所以右部出现的每个文法符号的每个属性，都要有一个局部变量接着。以 $T'$ 的产生式为例：右部有 $F$，$F$ 只有综合属性 `val`，就设局部变量 `F.val`；右部还有 $T_1'$，继承和综合都有，就设两个局部变量，分别对应 `T1'.inh` 和 `T1'.syn`。

函数体先看当前输入符号 token 决定走哪条产生式，再从左到右处理右部：

- 终结符：和语法分析器一样，执行匹配操作，把输入指针前移；
- 非终结符：调用它对应的函数，实参是它的继承属性变量，返回值赋给它的综合属性变量——$F$ 的返回值落到 `fval`，$T_1'$ 的返回值落到 `t1syn`；
- 语义动作：代码原样抄进函数体，把里面“对属性的引用”逐处改成“对相应局部变量的引用”。

函数最后把算出来的 $T'$ 的综合属性返回。$T$ 和 $F$ 的函数用同样的办法造出来。

> **提示**：这里没有引入任何新机制。属性在树上的每一条传递边，在递归下降里就是一次参数传递或一次赋值；原来要靠属性记录保存的中间值，现在落在函数的局部变量里。

#### 主函数与四条落地规矩

主函数只做一件事：调用开始符号 $T$ 的函数。$T$ 有综合属性 `val`，所以声明一个局部变量 `tval`，把返回值接住，整个语义翻译器就完整了。

把这套做法收成四条规矩：

1. 为每个非终结符 $A$ 构造一个函数：$A$ 的每个继承属性对应一个形参，返回值是 $A$ 的综合属性。
2. 对出现在 $A$ 的产生式中的每个文法符号的每个属性，设置一个局部变量。
3. $A$ 的代码根据当前输入决定用哪条产生式。
4. 与每条产生式有关的代码，从左到右考虑右部的词法单元、非终结符和语义动作。

第 4 条要把三种情况分清楚：

- 带综合属性 $x$ 的词法单元 $X$：把 $x$ 的值存进局部变量 `X.x`，然后生成一个匹配 $X$ 的调用，并前移输入；
- 非终结符 $B$：生成赋值语句 $c = B(b_1, b_2, \dots, b_k)$，$b_1$ 到 $b_k$ 是代表 $B$ 的继承属性的变量，$c$ 是代表 $B$ 的综合属性的变量；
- 语义动作：代码复制进分析器，属性引用改成相应的变量引用。

这四条合起来说明一件事：SDT 里每一次属性传递，在递归下降里都换成了一次参数传递或一次赋值，分析树由函数调用链隐式地撑起来。

### L 属性定义的自底向上翻译

S 属性定义对应的 SDT 能直接在自底向上分析里做翻译，因为它的语义动作全在产生式右部的末尾，归约的时候顺手执行就行。L 属性定义不是这样，它的动作嵌在右部中间。

#### 内嵌动作卡在归约时机上

归约要等整个右部都进栈、能认出这条产生式了才发生。内嵌动作却必须在它右边的符号还没处理之前就把值算出来——右边那些符号的继承属性还等着用它。一个要求早算，一个只能晚做，硬碰硬。

所以想让 L 属性定义走 LR 分析，第一步不是写代码，是改文法：把内嵌动作从右部中间挪走。

#### 标记非终结符与空产生式

拿一个带两个内嵌动作的 SDT 来说。第一个内嵌动作换成一个新非终结符 $M$，第二个换成 $N$，这类符号叫**标记非终结符**。$M$ 和 $N$ 各自只有一条产生式，而且是空产生式：$M \to \varepsilon$、$N \to \varepsilon$。

空产生式的右部什么都没有，但可以挂一个语义动作，这个动作干的事和被它替换掉的那个内嵌动作一模一样。

以 $N$ 为例。它替换的动作要算 $T'$ 的继承属性，计算时用到 $T'$ 的继承属性和 $F$ 的 `val`。那就把这两个属性复制成 $N$ 的两个继承属性 $N.i_1$ 和 $N.i_2$，在空产生式的动作里按老办法算，算出来的结果作为 $N$ 的综合属性。这个结果实质上是 $T'$ 的继承属性值——$N$ 站在 $T'$ 左边，替它把 `inh` 算好带过去。$M$ 那边照同样的方式处理，它替 $T'$ 算的是只由 $F$ 的 `val` 决定的那一份继承属性。

改完之后所有语义动作都落在产生式末尾。这里有一条很好用的结论：

> **结论**：如果一个文法是 LL 的，标记非终结符可以插到产生式右部的任何位置，得到的文法仍然是 LR 文法。

这条结论保证改完的文法建得出 LR 自动机。

乍看这个改写像是非法的：$N \to \varepsilon$ 的动作里要用 $F$ 和 $T'$ 的属性，可这两个符号根本不在 $N$ 的产生式右部。按 LL 分析的眼光确实解释不通，但我们用的是 LR 分析栈——那些属性已经躺在栈上某个**已知位置**了。

> **提示**：空产生式的动作不是凭空取属性，它取的是栈上某个固定偏移处的值。整个技巧的命门就在“已知位置”这四个字上，偏移一旦算错，取到的就是别的符号的属性。

#### 3 × 5 在 LR 栈上的走法

输入 `3 * 5`，初始状态栈里只有 0 号状态，符号栈里只有栈底标记 `$`，输入指针指向 3。分析过程中的移进、归约和状态转移如下，符号后面括号里是它的属性值。

| 状态栈（顶在右） | 符号栈（带属性值） | 剩余输入 | 动作 |
| :--- | :--- | :--- | :--- |
| `0` | `$` | `3 * 5 $` | 移进 `digit`，转 3 |
| `0 3` | `$ d(3)` | `* 5 $` | 按 $F \to \text{digit}$ 归约，转 2 |
| `0 2` | `$ F(3)` | `* 5 $` | 按 $M \to \varepsilon$ 归约，转 4 |
| `0 2 4` | `$ F(3) M(3)` | `* 5 $` | 移进 `*`，转 6 |
| `0 2 4 6` | `$ F(3) M(3) *` | `5 $` | 移进 `digit`，转 3 |
| `0 2 4 6 3` | `$ F(3) M(3) * d(5)` | `$` | 按 $F \to \text{digit}$ 归约，转 7 |
| `0 2 4 6 7` | `$ F(3) M(3) * F(5)` | `$` | 按 $N \to \varepsilon$ 归约，转 8 |
| `0 2 4 6 7 8` | `$ F(3) M(3) * F(5) N(15)` | `$` | 按 $T' \to \varepsilon$ 归约，转 9 |
| `0 2 4 6 7 8 9` | `$ F(3) M(3) * F(5) N(15) T'(15)` | `$` | 按 $T' \to *\,F\,N\,T'$ 归约，转 5 |
| `0 2 4 5` | `$ F(3) M(3) T'(15)` | `$` | 按 $T \to F\,M\,T'$ 归约，转 1 |
| `0 1` | `$ T(15)` | `$` | 接受 |

表里有两步是这套方法的精髓，值得停下来看清楚。

第一步是 $M$ 的归约。2 号状态遇到 `*`，按空产生式归约出 $M$。$M$ 的值等于 $F$ 的值，而 $F$ 是 $M$ 在产生式里的左兄弟，此刻正好在栈顶，所以把栈顶的值写到 `top+1`：$M = 3$。$M$ 在产生式里位于 $T'$ 左边，它的任务就是算 $T'$ 的继承属性，所以这个 3 事实上就是 $T'$ 的 `inh`。

第二步是 $N$ 的归约。7 号状态遇到 `$`，按空产生式归约出 $N$。$N$ 的值等于 $T'$ 的 `inh` 乘上 $F$ 的 `val`。$F$ 在 $N$ 左边，此刻在栈顶，取 `top` 没问题。$T'$ 的继承属性在哪儿？`*`、$F$、$N$、$T'$ 这一串最终要归约成 $T'$，也就是说 $T'$ 将占据 `*` 现在的位置；而 $T'$ 的继承属性存在紧贴 $T'$ 之下的标记非终结符记录里——就是 $M$ 那条，此刻在 `top-2`。

```text
栈（右侧为栈顶）:

   ...   M(3)    *     F(5)      <- 归约 N 之前
          ^              ^
          |              +--------- top：F.val = 5
          +------------------------ top-2：T'.inh = 3
                                    （T' 将占据 * 的位置，
                                      紧贴其下的 M 记录就是它的 inh）

   ...   M(3)    *     F(5)   |  N(15)
                                   ^
                                   +-- top+1：3 * 5 = 15
```

乘出来是 15，写进 `top+1`。$N$ 在产生式里也位于 $T'$ 左边，所以这个 15 就是 $T'$ 的 `inh`。

后面两步顺理成章。8 号状态按 $T' \to \varepsilon$ 归约：$T'$ 的综合属性等于它的继承属性，而继承属性就存在紧贴 $T'$ 之下的记录里，此刻正在栈顶，所以把栈顶的值赋给 `top+1` 的 $T'$，得到 15。9 号状态按 $T' \to *\,F\,N\,T'$ 归约：四个符号出栈、$T'$ 进栈落在 `*` 原来的位置（`top-3`），它的综合属性等于最右儿子的属性，也就是栈顶的 15。最后 5 号状态按 $T \to F\,M\,T'$ 归约，$T$ 落在 $F$ 的位置，综合属性等于最右儿子 $T'$ 的值，还是 15。0 号状态遇到 $T$ 转到 1 号接收状态，分析成功，开始符号的 `value` 是 15。

> **易错点**：算 $N$ 时最容易被 `top-1` 骗过去。此刻栈顶是 $F$，`top-1` 是 `*`，`top-2` 才是 $M$ 那条记录。因为 $T'$ 还没进栈，它只是“将要”占据 `*` 的位置，继承属性的记录要按这个将来的位置往回数。

#### 六段执行代码与一般配方

把每个语义动作翻成栈操作，只要问两件事：归约后新符号落在哪个位置，它要用的值在哪个位置。

归约时出栈 $k$ 个、进栈一个，新符号就落在原来最左边那个符号的位置，也就是归约前栈顶往下数第 $k-1$ 格。$T \to F\,M\,T'$ 出栈三个、进栈一个，$T$ 落在 `top-2`；归约完成后，`top-2` 就是新的栈顶。

| 产生式 | 归约后新符号的位置 | 执行代码 |
| :--- | :--- | :--- |
| $T \to F\,M\,T'$ | $T$ 落在 $F$ 的位置，即 `top-2` | 把栈顶（$T'$ 的属性）复制到 `top-2` |
| $M \to \varepsilon$ | $M$ 落在 `top+1` | 把栈顶（$F$ 的属性）复制到 `top+1` |
| $T' \to *\,F\,N\,T'$ | $T'$ 落在 `*` 的位置，即 `top-3` | 把栈顶（最右儿子 $T'$ 的属性）复制到 `top-3` |
| $N \to \varepsilon$ | $N$ 落在 `top+1` | `top-2`（$T'$ 的 `inh`）乘 `top`（$F$ 的 `val`），结果送 `top+1` |
| $T' \to \varepsilon$ | $T'$ 落在 `top+1` | 把栈顶（$T'$ 的 `inh`）复制到 `top+1` |
| $F \to \text{digit}$ | $F$ 落在 `digit` 的位置 | 栈顶属性字段不变 |

把这套做法抽出来，就是给 L 属性定义做自底向上翻译的标准流程。

给定一个以 LL 文法为基础的 L 属性定义，先构造 SDT：在各个非终结符之前放语义动作算继承属性，在产生式后端放语义动作算综合属性。这一步还是老规矩，动作的位置由属性的依赖关系定，不由 LR 分析的方便定。

接着处理每个内嵌的语义动作：向文法中引入一个标记非终结符替换它。每个位置配一个不同的标记，任意一个标记 $M$ 都配一条产生式 $M \to \varepsilon$。

最后把动作搬进空产生式。如果标记非终结符 $M$ 在某个产生式中替换了语义动作 $a$，就对 $a$ 做改造得到 $a'$，把 $a'$ 关联到 $M \to \varepsilon$ 上。$a'$ 把 $a$ 需要的、来自左部 $A$ 或右部前缀 $\alpha$ 中符号的任何属性，统统作为 $M$ 的继承属性复制进来，再按 $a$ 原来的算法计算，只是把算出来的结果作为 $M$ 的综合属性。

这样改造之后，SDT 就能在 LR 分析过程中实现了。三条路走到这里其实是同一个道理：非递归预测分析把属性放在分析栈的记录里，靠“综合记录压在本身记录之下”维持先后；递归预测分析把属性放在函数的形参、返回值和局部变量里，靠调用链维持方向；LR 分析把属性放在符号栈的记录里，靠归约时的固定偏移取用。属性值永远跟着“将要成为某个符号的那条记录”走，谁先算谁后算，由属性之间的依赖关系决定。

## 从类型表达式到三地址码
> 对应块：BLK10 | 覆盖分集：P43-P45 | 块标题（分集名）：《6-1类型表达式》

从这一章开始，我们进入中间代码生成。这一章要翻译的语句有一串：声明语句、赋值语句、控制语句、过程调用语句……我们一件一件来，先从声明语句开始。

声明语句的翻译要干两件事：把标识符的类型等属性信息收集起来，再为每一个名字分配一个相对地址。要收集类型信息，前提是得有一种办法把类型描述清楚。所以正式动手翻译之前，我们先把类型表达式这个东西交代清楚。

### 类型也有结构

类型不是一串孤零零的名字。类型本身有结构，而类型的结构，我们用类型表达式来表示。

#### 基本类型与类型名

最基本的一层：基本类型是类型表达式。`integer`、`real`、`char`、`boolean`，这些本身就是合法的类型表达式。

再往上一层：我们可以给类型表达式命名，类型名也是类型表达式。这一条看着不起眼，后面却很有用——一个记录类型只需要定义一次、起个名字，之后在数组、指针里引用这个名字就行，不必把整个结构一遍遍展开。

> **定义**：类型表达式由基本类型、类型名，以及类型构造符作用于类型表达式构成。

#### 数组：array(I, T)

第一个构造符是数组构造符 `array`。设 $T$ 是类型表达式，$I$ 是整数，那么 $\text{array}(I, T)$ 就是表示数组类型的表达式：这个数组包含 $I$ 个元素，每个元素的类型都是 $T$。

三个元素的整型数组，类型表达式是 $\text{array}(3, \text{int})$。

二维的例子更能说明问题：一个 $2 \times 3$ 的二维整型数组，类型表达式是 $\text{array}(2, \text{array}(3, \text{int}))$。注意它不是“一个装 6 个整型的数组”，而是“数组的数组”：这个数组里有两个元素，每个元素又是一个一维数组，那个一维数组里装三个整型。

```text
array(2, array(3, int))
│
├── 元素个数：2
└── 元素类型：array(3, int)
    │
    ├── 元素个数：3
    └── 元素类型：int
```

读图：外层 `array` 管第一维，内层 `array` 管第二维。维数是从类型表达式的嵌套层数看出来的，不是从某个“维度属性”上看出来的。

#### 指针、乘积、函数与记录

指针构造符 `pointer`：$T$ 是类型表达式，$\text{pointer}(T)$ 就是表示“指向类型 $T$ 的指针”的表达式。

笛卡尔乘积构造符 $\times$：$T_1$ 和 $T_2$ 是类型表达式，$T_1 \times T_2$ 也是类型表达式。

函数构造符 $\rightarrow$：$T_1, T_2, \dots, T_n$ 和 $R$ 都是类型表达式，那么

$$T_1 \times T_2 \times \dots \times T_n \rightarrow R$$

是一个表示函数的类型表达式。其中 $T_1$ 到 $T_n$ 是函数参数的类型，$R$ 是函数返回值的类型。

记录构造符 `record`：若有标识符 $N_1, N_2, \dots, N_n$ 与类型表达式 $T_1, T_2, \dots, T_n$，则

$$\text{record}(N_1 \times T_1 \times N_2 \times T_2 \times \dots \times N_n \times T_n)$$

是一个表示记录的类型表达式。这个记录有 $n$ 个字段，字段名分别是 $N_1$ 到 $N_n$，字段类型分别是 $T_1$ 到 $T_n$。

#### 三个名字的类型表达式

看一个 C 程序片段，里面声明了三个名字：`stype`、`table`、`p`。我们一个一个看它们绑定的类型表达式。

`stype` 是一个记录的名字。这个记录里有两个字段：第一个叫 `name`，是长度为 8 的字符数组；第二个叫 `score`，是整型变量。按记录构造符的写法：

$$\text{stype} = \text{record}(\text{name} \times \text{array}(8, \text{char}) \times \text{score} \times \text{integer})$$

`table` 是一个数组的名字，50 个元素，每个元素的类型是 `stype`：

$$\text{table} = \text{array}(50, \text{stype})$$

`p` 是一个指针，指向 `stype`：

$$\text{p} = \text{pointer}(\text{stype})$$

| 名字 | 类型表达式 | 读法 |
| :--- | :--- | :--- |
| `stype` | $\text{record}(\text{name} \times \text{array}(8, \text{char}) \times \text{score} \times \text{integer})$ | 含 `name`、`score` 两个字段的记录 |
| `table` | $\text{array}(50, \text{stype})$ | 50 个元素，每个元素的类型是 `stype` |
| `p` | $\text{pointer}(\text{stype})$ | 指向 `stype` 类型的指针 |

后两个表达式里都出现了 `stype`。这里用的正是“类型名也是类型表达式”这一条：`stype` 在前面已经定义过，`table` 和 `p` 里直接引用这个名字就够了。要是没有类型名，`table` 的类型表达式就得把整个记录结构再抄一遍。

### 声明语句：先算宽度，再分地址

回到声明语句。它的语义分析主要任务，开头已经点过：收集标识符的类型等属性信息，并为每一个名字分配一个相对地址。

分配地址要有依据。根据一个名字的类型表达式，可以知道这个类型在运行时刻需要多少个存储单元，这个数量称为类型的宽度（width）。编译时刻，我们就用类型的宽度为每一个名字分配一个相对地址。

> **定义**：类型的宽度，是该类型在运行时刻所需要的存储单元的数量。

名字的类型和相对地址，最终都保存在符号表记录里。符号表是后面所有翻译工作的地基：声明语句往里写，赋值语句从里读。

### 变量声明语句的 SDT

变量声明语句的 SDT 由两部分组成：基础文法，以及挂在产生式上的语义动作。

#### 基础文法怎么分层

基础文法有四个非终结符，各管一段：

- $B$：生成基本类型关键字，取 basic 的首字母，定义为 `int` 或 `real`；
- $C$：生成一个数组下标表达式序列，也就是 `[2][3]` 这种跟在类型后面的尾巴；
- $T$：表示标识符的类型。$C$ 取空串时，$T$ 生成一个基本变量；$C$ 不取空时，$T$ 生成一个数组类型；$T$ 还可以定义成指针关键字连接一个 $T$，这时生成指针类型；
- $D$：生成一个声明序列，每个声明由 $T$、`id`、分号构成。一个声明序列就构成一个程序 $P$。

写成产生式：

$$B \to \text{int} \mid \text{real}$$

$$C \to \varepsilon \mid [\ \text{number}\ ]\ C$$

$$T \to B\ C \mid \text{pointer}\ T$$

$$D \to T\ \text{id}\ ;\ D \mid \varepsilon$$

$$P \to D$$

这里的 `number` 是数字字面量，`[`、`]`、`;` 都是终结符。到了 SDT 里，程序产生式会在 $D$ 前面插一个动作符号，先把 `offset` 清零。

#### 属性、offset 与 enter

变量声明翻译的任务是收集类型信息、按宽度分配相对地址，所以给 $B$、$C$、$T$ 各设两个综合属性：`type` 表示对应的类型，`width` 表示这个类型的宽度。

几个具体数值是假设出来的：一个整型变量占 4 个字节，一个实型变量占 8 个字节，一个指针占 4 个字节。这几个数不是语言规定，换台机器、换个模型就可能变；这里定下来，是为了把宽度怎么算讲清楚。

SDT 里还有几个辅助成分：

- `offset`：下一个可用的相对地址，初始时刻为 0；
- $t$ 和 $w$：把类型和宽度从语法分析树的 $B$ 节点传递到对应产生式 $C \to \varepsilon$ 的节点。为什么要绕这一道，等看完例子就明白了；
- `enter(name, type, offset)`：在符号表中为名字 `name` 创建记录，把类型设为 `type`，相对地址设为 `offset`。

每识别出一个声明，就调用 `enter` 为这个 `id` 建一条记录；建完记录以后，把 `offset` 增加 $T$ 的宽度。也就是说，下一个声明的名字从 $\text{offset} + T.\text{width}$ 开始分配。

#### 九条产生式一览

表里的 $A$ 是动作符号，不是文法符号。它像文法符号一样进栈，轮到它在栈顶，就执行冒号后面那段语义动作。

| 编号 | 产生式 | 语义动作 |
| :---: | :--- | :--- |
| 1 | $P \to A\ D$ | $A$：`offset := 0` |
| 2 | $D \to T\ \text{id}\ ;\ A\ D$ | `enter(id.name, T.type, offset)`；`offset := offset + T.width` |
| 3 | $D \to \varepsilon$ | 无 |
| 4 | $T \to B\ A\ C\ A$ | 第一个 $A$：`t := B.type`，`w := B.width`；第二个 $A$：`T.type := C.type`，`T.width := C.width` |
| 5 | $T \to \text{pointer}\ T_1$ | `T.type := pointer(T1.type)`；`T.width := 4` |
| 6 | $B \to \text{int}\ A$ | `B.type := int`；`B.width := 4` |
| 7 | $B \to \text{real}\ A$ | `B.type := real`；`B.width := 8` |
| 8 | $C \to \varepsilon\ A$ | `C.type := t`；`C.width := w` |
| 9 | $C \to [\ \text{number}\ ]\ C_1\ A$ | `C.type := array(number.lexval, C1.type)`；`C.width := number.lexval * C1.width` |

产生式 4 是整套动作的关节。它在 $B$ 和 $C$ 之间塞了一个动作符号，在 $C$ 后面又塞了一个：第一个 $A$ 在 $B$ 规约完之后立刻执行，把 $B$ 的 `type`、`width` 抄进 $t$、$w$；第二个 $A$ 等 $C$ 规约完才执行，把 $C$ 的属性交给 $T$。中间的 $C$ 负责把数组的维度一层层套上去，它需要知道“元素是什么类型、一个元素多宽”，这个信息就来自 $t$、$w$。

为什么不能让 $C$ 直接读 $B$ 的属性？在语法分析树里，$B$ 和 $C$ 是兄弟，$C$ 的子树看不到兄弟节点上的属性。$t$、$w$ 就是给这对兄弟搭的一条通道：$B$ 先把值放进通道，$C$ 再从通道里取。

产生式 8 是空产生式 $C \to \varepsilon$，它的动作把 $t$、$w$ 里的值取出来，当成自己的 `type`、`width`。产生式 9 则在已经算出的子节点 $C_1$ 外面再套一层数组：元素个数取 `number` 的词法值，元素类型取 $C_1$ 的 `type`，宽度是“元素个数 × 元素宽度”。

产生式 5 单独处理指针：类型是 $\text{pointer}(T_1.\text{type})$，宽度固定为 4。

### 先验证它是 LL(1) 文法

这套 SDT 对应的是一个 L 属性定义：综合属性只看自己的子节点，继承属性只看父节点和左边的兄弟，所以可以一边从左到右分析、一边把属性算出来。如果它的基础文法又是 LL(1) 文法，那么就可以在自顶向下的分析过程中实现这个 SDT。所以动手翻译之前，先验证基础文法是不是 LL(1)。

判定办法：看具有相同左部的产生式，它们的可选集（SELECT 集）是否互不相交。SELECT 集说的是这个产生式右部开头可能出现的终结符集合；空产生式则看它的 FOLLOW 集。逐组看。

**$D$ 的两条产生式。** 2 号和 3 号左部都是 $D$。2 号以 $T$ 开头，所以它的 SELECT 集就是 $T$ 的 FIRST 集。$T$ 的 FIRST 集取决于 $B$ 的 FIRST 集，而 $B$ 的 FIRST 集里有 `int` 和 `real`；另外指针关键字也在 $T$ 的 FIRST 集里。所以 2 号的 SELECT 集是 $\{\text{pointer}, \text{int}, \text{real}\}$。3 号是空产生式，它的 SELECT 集是 $\text{FOLLOW}(D)$。$D$ 出现在程序末尾，后面跟的是结束符 `$`，所以 $\text{FOLLOW}(D)$ 就是 `{$}`。两者不相交。

**$T$ 的两条产生式。** 4 号以 $B$ 开头，SELECT 集含 `int`、`real`；5 号以指针关键字开头，SELECT 集是 $\{\text{pointer}\}$。不相交。

**$B$ 的两条产生式。** 6 号是 `int`，7 号是 `real`，SELECT 集分别是 $\{\text{int}\}$ 和 $\{\text{real}\}$。不相交。

**$C$ 的两条产生式。** 8 号是空产生式，SELECT 集是 $\text{FOLLOW}(C)$。$\text{FOLLOW}(C)$ 取决于 $\text{FOLLOW}(T)$，而 $\text{FOLLOW}(T)$ 里有 `id`（声明里类型后面跟的是标识符），所以 8 号的 SELECT 集里有 `id`。9 号以左方括号开头，SELECT 集是 `{[}`。不相交。

| 相同左部 | 产生式 | SELECT 集 | 结论 |
| :---: | :--- | :--- | :--- |
| $D$ | 2 / 3 | $\{\text{pointer},\text{int},\text{real}\}$ / `{$}` | 不相交 |
| $T$ | 4 / 5 | $\{\text{int},\text{real}\}$ / $\{\text{pointer}\}$ | 不相交 |
| $B$ | 6 / 7 | $\{\text{int}\}$ / $\{\text{real}\}$ | 不相交 |
| $C$ | 8 / 9 | 含 `id` / `{[}` | 不相交 |

> **结论**：基础文法是一个 LL(1) 文法，可以在自顶向下的语法分析过程中实现这套 SDT。

### 走一遍 `real x; int i;`

把输入定为 `real x; int i;`，用栈式自顶向下分析。动作符号和普通文法符号一样进栈，轮到它在栈顶就执行。

1. 初始，输入指针指向 `real`。用 1 号产生式把开始符号 $P$ 换成 $A\ D$。$A$ 到栈顶，执行 `offset := 0`，然后出栈。
2. 栈顶是 $D$，当前输入 `real`，用 2 号：$D \to T\ \text{id}\ ;\ A\ D$。
3. 栈顶是 $T$，输入 `real`，用 4 号：$T \to B\ A\ C\ A$。
4. 栈顶是 $B$，输入 `real`，用 7 号：$B \to \text{real}\ A$。终结符 `real` 与输入匹配，出栈，指针移到 `x`。
5. 栈顶露出 $B$ 的动作：`B.type := real`，`B.width := 8`。
6. 接着是 4 号的第一个 $A$：`t := real`，`w := 8`。
7. 栈顶是 $C$，当前输入是标识符 `x`，落在 8 号的 SELECT 集里，用 8 号：$C \to \varepsilon\ A$。动作执行：`C.type := t`，`C.width := w`，于是 $C$ 拿到 `real` 和 8。
8. 4 号最后一个 $A$：`T.type := C.type`，`T.width := C.width`，$T$ 拿到 `real` 和 8。
9. 匹配 `id`（就是 `x`），再匹配分号，指针移到 `int`。
10. 2 号的动作：`enter(x, real, 0)`，符号表里多一条 `x, real, 0`；然后 `offset := 0 + 8 = 8`。
11. 栈顶又露出 $D$，输入 `int`，再走 2 号；$T$ 走 4 号；$B$ 看 `int` 走 6 号，匹配 `int`，指针移到 `i`。
12. $B$ 的动作算出 `B.type := int`、`B.width := 4`；4 号第一个 $A$ 把 `t`、`w` 更新成 `int` 和 4。
13. $C$ 走 8 号，取走 `int` 和 4；4 号最后一个 $A$ 把它们交给 $T$。
14. 匹配 `id`（`i`）和分号。
15. 2 号的动作：`enter(i, int, 8)`，符号表里多一条 `i, int, 8`；`offset := 8 + 4 = 12`。
16. 栈顶是 $D$，输入是 `$`，用 3 号：$D \to \varepsilon$。分析结束。

| 名字 | type | 相对地址 |
| :---: | :---: | :---: |
| `x` | `real` | 0 |
| `i` | `int` | 8 |

`offset` 最后是 12，下一个声明的名字会从 12 开始分配。

两遍声明走下来，动作序列其实一模一样，变的只有类型和宽度。真正值得注意的是 $t$、$w$ 这条通道：

```text
B
│  B.type / B.width
▼
t , w
│
▼
C → ε  ──▶  C → [n] C  ──▶  …  ──▶  T
            （逐层把数组类型套上去）
```

读图：$B$ 算出的类型和宽度先存进 $t$、$w$，空产生式 $C \to \varepsilon$ 把它们取走，变成 $C$ 自己的综合属性；如果 $C$ 展开成了若干层 `[n] C`，这些属性再沿着 $C$ 链一层层往上交，最后交给 $T$。类型和宽度信息从分析树的 $B$ 节点传到对应空产生式的 $C$ 节点，再作为综合属性返回 $T$——这就是产生式 4 里那两个动作符号存在的理由。

### 数组类型表达式 `int[2][3]`

前面走的是基本变量声明。现在换一个类型表达式：`int[2][3]`。

因为它本身就是一个类型表达式，不是一条完整声明，所以从非终结符 $T$ 开始推导。

1. 输入 `int`，$T$ 用 4 号：$T \to B\ A\ C\ A$。
2. $B$ 用 6 号：$B \to \text{int}\ A$。匹配 `int`，指针移到第一个 `[`。$B$ 的动作算出 `B.type := int`、`B.width := 4`。
3. 4 号第一个 $A$：`t := int`，`w := 4`。
4. 栈顶是 $C$，输入 `[`，用 9 号：$C \to [\ \text{number}\ ]\ C\ A$。匹配 `[`、`2`、`]`，指针移到第二个 `[`。
5. 栈顶还是 $C$，输入还是 `[`，再套一层 9 号。匹配 `[`、`3`、`]`，指针移到一个标识符 `id`。
6. $C$ 看 `id`，用 8 号：$C \to \varepsilon\ A$。动作取走 $t$、$w$：`C.type := int`，`C.width := 4`。
7. 内层 9 号的动作开始算。`number` 的词法值是 3，子节点 $C_1$ 的 `type` 是 `int`，所以 `C.type := array(3, int)`；子节点 $C_1$ 的 `width` 是 4，所以 `C.width := 3 × 4 = 12`。
8. 外层 9 号的动作接着算。`number` 的词法值是 2，子节点 $C_1$ 的 `type` 已经是 `array(3, int)`，所以 `C.type := array(2, array(3, int))`；子节点 $C_1$ 的 `width` 是 12，所以 `C.width := 2 × 12 = 24`。
9. 4 号最后一个 $A$：`T.type := array(2, array(3, int))`，`T.width := 24`。

| 规约顺序 | 处理的维度 | 元素类型从哪来 | 得到的 type | 得到的 width |
| :---: | :---: | :--- | :--- | :---: |
| 先 | `[3]` | 空产生式 $C$ 给出的 `int` | $\text{array}(3,\text{int})$ | $3 \times 4 = 12$ |
| 后 | `[2]` | 内层 $C$ 给出的 $\text{array}(3,\text{int})$ | $\text{array}(2,\text{array}(3,\text{int}))$ | $2 \times 12 = 24$ |

> **易错点**：数组的宽度不是把各维的数字加起来，而是一层一层乘。每一层的宽度都等于“这一维的元素个数 × 元素的宽度”，而元素本身可能又是一个数组，所以内层的宽度要先算出来，外层才能用。

因为 $C$ 的产生式是右递归的（$C \to [\ \text{number}\ ]\ C$），最里面那一维最先规约，数组类型也就由内向外一层层套起来。`int[2][3]` 得到的是 $\text{array}(2, \text{array}(3, \text{int}))$，不是反过来。

类型和宽度信息通过 $t$、$w$ 从 $B$ 节点传到空产生式的 $C$ 节点，再沿着由若干个 $C$ 构成的链返回父节点 $T$。基本变量是这条链上只有一层（$C \to \varepsilon$）的特例，数组是这条链上有多层 `[n] C` 的情形——机制是同一套。

### 赋值语句：生成三地址码

声明语句把名字、类型、地址记进了符号表；接下来看怎么用这些信息给语句生成代码。先看最简单的赋值语句。

它的基础文法很短：

$$S \to \text{id} = E\ ;$$

一个赋值语句，就是一个标识符、一个等号、一个表达式、一个分号。

一个表达式的值不是凭空来的，它要通过一段三地址码算出来。所以赋值语句翻译的主要任务，是生成对表达式求值的三地址码。三地址码就是形如 `x = y op z` 的中间代码，一条指令最多带一个运算符。

看一个例子。输入：

```pascal
x = (a + b) * c;
```

对应的三地址码是：

```text
t1 = a + b
t2 = t1 * c
x  = t2
```

先把 `a` 和 `b` 相加，结果放进临时变量 `t1`；再把 `t1` 和 `c` 相乘，结果放进临时变量 `t2`。`t2` 里装的就是等号右边这个表达式的值。最后把这个值赋给 `x`。

```text
x = (a + b) * c
  ├─ 先算 a + b   ⇒  t1 = a + b
  ├─ 再算 t1 * c  ⇒  t2 = t1 * c
  └─ 最后赋值      ⇒  x  = t2
```

读图：三地址码的顺序就是表达式求值的顺序，先算子表达式，再算外层运算，最后才轮到赋值。

### 赋值语句的 SDT

赋值语句翻译的主要任务是生成三地址码，所以给文法中的两个非终结符 $S$ 和 $E$ 各设一个综合属性 `code`，表示它们对应的三地址码。另外给 $E$ 再加一个综合属性 `address`，表示表达式的值存放在哪里。

#### 三个工具函数

- `lookup(name)`：查符号表，返回 `name` 对应的记录。查不到就返回空。
- `gen(code)`：生成一条三地址指令 `code`。
- `newtemp()`：生成一个新的临时变量 $t$，并返回 $t$ 的地址。

这里有个约定：例子里面我们用名字来表示地址。所以 `E.address` 等于 `t1`、等于 `a`，说的都是“这个值放在名为 `t1` 的临时变量里”“这个值就在变量 `a` 里”。

`gen` 的参数里，引号括起来的符号按字面值传进去，变量部分取它的值。所以 `gen(E.address '=' E1.address '+' E2.address)` 在 `E.address` 是 `t1`、`E1.address` 是 `a`、`E2.address` 是 `b` 的时候，生成的就是 `t1 = a + b`。

#### 六条产生式与动作

```text
S → id = E ;    { p := lookup(id.name).addr;
                  S.code := E.code || gen(p '=' E.address) }

E → E1 + E2     { E.address := newtemp();
                  E.code := E1.code || E2.code
                            || gen(E.address '=' E1.address '+' E2.address) }

E → E1 * E2     { E.address := newtemp();
                  E.code := E1.code || E2.code
                            || gen(E.address '=' E1.address '*' E2.address) }

E → -E1         { E.address := newtemp();
                  E.code := E1.code || gen(E.address '=' '-' E1.address) }

E → (E1)        { E.address := E1.address;
                  E.code := E1.code }

E → id          { p := lookup(id.name);
                  if p = nil then error;
                  E.address := p.addr;
                  E.code := ε }
```

两条竖线 `||` 是连接运算符，把左右两段代码按顺序接起来；$\varepsilon$ 表示空串。

先看 $E \to \text{id}$。这个表达式只是一个标识符，标识符本身就存放着表达式的值，所以标识符的地址就是表达式值的存放地址。语义动作调用 `lookup` 返回标识符在符号表里的记录，从记录里查到存放地址，赋给 `E.address`。如果返回空，说明符号表里没有这个标识符，也就是出现了标识符未经声明直接使用的错误。这个产生式不涉及任何运算，不生成三地址指令，所以 `E.code` 是空串。

再看 $E \to (E_1)$。括号不改变表达式的值，也不产生任何运算，所以 $E$ 的属性直接照抄 $E_1$：`E.address` 等于 $E_1$ 的 `address`，`E.code` 等于 $E_1$ 的 `code`。

$E \to E_1 + E_2$ 要干两件事。第一，调用 `newtemp` 生成一个新的临时变量，用来存放 $E_1 + E_2$ 的值，返回的地址赋给 `E.address`。第二，拼代码：先把 $E_1$ 的代码、$E_2$ 的代码按顺序接起来，再在后面追加一条加法指令，把 $E_1$ 的值和 $E_2$ 的值相加，结果存到 `E.address`。乘法产生式 $E \to E_1 * E_2$ 的动作和它一样，只是把加号换成乘号。

> **易错点**：$E \to E_1 + E_2$ 的代码顺序是 $E_1$ 的代码、$E_2$ 的代码、最后才是加法指令。加法指令必须排在两个子表达式的代码之后，否则操作数还没算出来，指令就先去取操作数了。

$E \to -E_1$ 先调用 `newtemp` 拿一个临时变量，再在 $E_1$ 的代码后面追加一条取反指令：把 $E_1$ 的值取反，存进 `E.address`。取反的结果同样要有一个存放位置。

最后是 $S \to \text{id} = E\ ;$。$S$ 只有一个 `code` 属性，它的代码就是 $E$ 的代码后面接上一条把 $E$ 的值赋给变量 `id` 的指令。为此要先调用 `lookup` 从符号表里取出 `id` 对应的记录，得到 `id` 的地址，把它赋给 `p`，赋值指令的目标就是 `p`。

### 增量翻译

看这几条与 `code` 有关的动作，会发现一个规律：表达式的 `code` 总要复制子表达式 $E_1$、$E_2$ 的 `code`；子表达式的 `code` 又要复制它自己的子表达式的 `code`，一层套一层。这样一个 `code` 属性可能是一个很长的字符串，复制、移动都要花时间。

再仔细看：产生式左部符号的 `code`，构造方式永远是“右部各符号的 `code` 按顺序连接起来，再在后面追加一条（或几条）三地址指令”。既然每次都是往后接，那就没必要把整串代码在树上来回搬——直接在一个全局的指令序列后面追加就行。

这就是增量翻译：不设 `code` 属性，直接在已生成的三地址码后面追加新的三地址指令，把与 `code` 相关的行全部删掉。

`gen` 函数的职责也跟着变了：它不仅要构造一条新的三地址指令，还要把这条指令添加到至今为止已生成的指令序列之后。

删掉 `code` 之后，属性只剩下 `E.address`，语义动作缩成两类：算地址、追加指令。比如 $E \to E_1 + E_2$ 只剩两件事——`E.address := newtemp()`，然后 `gen(E.address '=' E1.address '+' E2.address)`；$S \to \text{id} = E\ ;$ 只剩 `p := lookup(id.name).addr` 和 `gen(p '=' E.address)`。

| 对比项 | 属性式翻译 | 增量翻译 |
| :--- | :--- | :--- |
| 三地址码放在哪 | 放在 `code` 属性里，随语法树上下传递 | 放在一个全局指令序列里，只往后追加 |
| `gen` 的职责 | 只构造指令 | 构造指令并追加到序列末尾 |
| 主要代价 | 长字符串反复复制、移动 | 只追加，不复制 |

> **提示**：增量翻译不是另换一套语义。它生成的三地址码和属性式翻译完全一样，只是不再把整串代码在语法树上搬来搬去。

### 用 LR 分析走一遍

把输入换成 $x = (a + b) * c$。这个 SDT 的基础文法可以采用 LR 分析技术，而所有语义动作又都位于产生式右部的末尾，所以可以采用自底向上的方式来翻译。

先说明栈的记法：状态栈里放状态号，符号栈里放已经移进或规约出的文法符号，栈底是 `$`。初始时状态栈只有 0 号状态，符号栈只有 `$`，输入指针指向第一个符号 `x`。

| 状态栈 | 符号栈 | 剩余输入 | 动作 |
| :--- | :--- | :--- | :--- |
| `[0]` | `$` | `x = ( a + b ) * c ;` | 0 遇 `id`，移进 → 2 |
| `[0 2]` | `$ id` | `= ( a + b ) * c ;` | 2 遇 `=`，移进 → 3 |
| `[0 2 3]` | `$ id =` | `( a + b ) * c ;` | 3 遇 `(`，移进 → 6 |
| `[0 2 3 6]` | `$ id = (` | `a + b ) * c ;` | 6 遇 `id`，移进 → 7 |
| `[0 2 3 6 7]` | `$ id = ( id` | `+ b ) * c ;` | 7 用 6 号规约：`E.address := a`；6 遇 `E` → 12 |
| `[0 2 3 6 12]` | `$ id = ( E` | `+ b ) * c ;` | 12 遇 `+`，移进 → 9 |
| `[0 2 3 6 12 9]` | `$ id = ( E +` | `b ) * c ;` | 9 遇 `id`，移进 → 7 |
| `[0 2 3 6 12 9 7]` | `$ id = ( E + id` | `) * c ;` | 7 用 6 号规约：`E.address := b`；9 遇 `E` → 13 |
| `[0 2 3 6 12 9 13]` | `$ id = ( E + E` | `) * c ;` | 13 用 2 号规约：`t1 := newtemp()`，`gen(t1 = a + b)`；6 遇 `E` → 12 |
| `[0 2 3 6 12]` | `$ id = ( E` | `) * c ;` | 12 遇 `)`，移进 → 15 |
| `[0 2 3 6 12 15]` | `$ id = ( E )` | `* c ;` | 15 用 5 号规约：`E.address := t1`；3 遇 `E` → 4 |
| `[0 2 3 4]` | `$ id = E` | `* c ;` | 4 遇 `*`，移进 → 10 |
| `[0 2 3 4 10]` | `$ id = E *` | `c ;` | 10 遇 `id`，移进 → 7 |
| `[0 2 3 4 10 7]` | `$ id = E * id` | `;` | 7 用 6 号规约：`E.address := c`；10 遇 `E` → 14 |
| `[0 2 3 4 10 14]` | `$ id = E * E` | `;` | 14 用 3 号规约：`t2 := newtemp()`，`gen(t2 = t1 * c)`；3 遇 `E` → 4 |
| `[0 2 3 4]` | `$ id = E` | `;` | 4 遇 `;`，移进 → 8 |
| `[0 2 3 4 8]` | `$ id = E ;` | （空） | 8 用 1 号规约：`p := x`，`gen(x = t2)`；0 遇 `S` → 1 |
| `[0 1]` | `$ S` | （空） | 1 是接受状态，分析成功 |

这张表一行一行读下来，其实就是三句话：

- 遇到标识符，查符号表，把地址交给 $E$，不发指令；
- 遇到 `+`、`*`，先 `newtemp` 造临时变量，再发一条运算指令；
- 遇到括号，属性原样传，不发指令；遇到分号，发最后一条赋值指令。

每条指令发出的时候，操作数的地址都已经就绪——这正是自底向上翻译的好处：规约到某个产生式时，右部符号的属性早就计算完了，语义动作直接拿来用。

最后生成的三地址码是：

```text
t1 = a + b
t2 = t1 * c
x  = t2
```

首先计算 $a + b$ 的值存放在 `t1` 中；接下来计算 `t1 * c` 的值存放在 `t2` 中；`t2` 中存放的就是等号右边的表达式的值；最后把这个值赋给变量 `x`。

到这里，三件事就串起来了：类型表达式把类型结构描述清楚；声明语句用类型的宽度算出相对地址，把名字、类型、地址写进符号表；赋值语句从符号表里取出名字的地址，按表达式的结构生成三地址码。类型表达式为后两件事提供了共同的描述语言，声明和赋值则共用同一张符号表，也共用同一套“属性 + 语义动作”的写法。

## 数组引用与控制流的翻译：地址、标号与跳转
> 对应块：BLK11 | 覆盖分集：P46-P49 | 块标题（分集名）：《6-4数组引用的翻译》

前面我们已经能把赋值语句翻成三地址码：等号右边是常数、简单变量、算术表达式，都能一条条生成指令。可真实程序里，等号两边最常见的不是 `x`、`y` 这种标量，而是 `A[i]`、`A[i][j]` 这样的数组元素。问题马上就来了——`c = A[i]` 这条语句，第一条三地址指令到底该写什么？

标量的地址在符号表里躺着，查一下就有了；数组元素没有现成的地址，它的位置得现场算出来。所以数组引用的翻译，说到底只有一个核心问题：确定数组元素的存放地址，也就是数组元素的寻址。地址一旦算出来，取数和存数都是例行公事。

### 数组元素怎么寻址

为了把数组引用塞进已经熟悉的赋值语句框架，最省事的做法是引入一个新的非终结符 $L$。$L$ 生成的是“一个标识符后面接一串下标表达式”，所以它代表的就是一个数组元素。围绕 $L$ 扩展出来的文法，要回答两个问题：数组元素能不能被赋值，能不能当作表达式用。

```text
S → L = E          数组元素出现在赋值号左边，可以被赋值
E → L              数组元素本身也是一个表达式，可以出现在右边
L → id [ E ]       标识符带一个下标
L → L [ E ]        已有的数组元素再接一个下标
```

两条关于 $L$ 的产生式，一条从标识符起步，一条从已有的 $L$ 再接一个下标——后者是递归的，所以 `A[i1][i2][i3]` 这种多维引用不需要为每一维单独立一条规则，靠 $L$ 自己套自己就能长出来。

接下来是寻址公式。一维最好想：假设每个数组元素的宽度是 $w$，那么元素 $A[i]$ 的相对地址就是

$$base + i \times w$$

其中 $base$ 是数组的基地址，$i \times w$ 是偏移地址。基地址说明这个数组从内存的哪儿开始，偏移地址说明目标元素离起点有多远，两者一加就是元素的位置。

二维数组多了一层。假设一行的宽度是 $w_1$，同一行中每个数组元素的宽度是 $w_2$，那么 $A[i_1][i_2]$ 的地址是

$$base + i_1 \times w_1 + i_2 \times w_2$$

这里的 $i_1 \times w_1 + i_2 \times w_2$ 才是偏移地址。

推到 $k$ 维，形式完全一样：

$$base + i_1 \times w_1 + i_2 \times w_2 + \dots + i_k \times w_k$$

区别只在于每个 $w_j$ 指什么。$w_1$ 是 $A[i_1]$ 的宽度，而 $A[i_1]$ 是一个 $k-1$ 维数组；$w_2$ 是 $A[i_1][i_2]$ 的宽度，$A[i_1][i_2]$ 是一个 $k-2$ 维数组；一路下去，$w_k$ 是 $A[i_1][i_2]\dots[i_k]$ 的宽度，而它已经是数组的基本元素了。

> **易错点**：$w_1$ 不是“第一维的长度”，而是“第一维每个元素占多少字节”。拿三维数组说，第一维有 3 个元素，但 $w_1$ 不是 3，而是这 3 个元素中每一个（也就是一个完整的二维子数组）的大小。公式里每个下标乘的，都是“剥掉这一层之后剩下的那个子数组”的宽度，不是这一维的元素个数。

这个“剥一层、乘一次”的结构，是后面所有工作的骨架。拿一个具体的三维数组把它算一遍。

### 三维数组：宽度是一层层剥出来的

设 $A$ 是 $3 \times 5 \times 8$ 的三维整型数组，一个整型占 4 个字节，求 $A[i_1][i_2][i_3]$ 的地址。

先把三层宽度剥出来。$A[i_1]$ 是 $A$ 的一个元素，它是一个 $5 \times 8$ 的二维整型数组，一共 $5 \times 8 = 40$ 个整型，每个 4 字节，所以宽度是 $40 \times 4 = 160$，这就是 $w_1$。$A[i_1][i_2]$ 是那个二维数组的一行，是由 8 个整型构成的一维数组，宽度 $8 \times 4 = 32$，这是 $w_2$。$A[i_1][i_2][i_3]$ 是最后那个一维数组里的一个整型变量，宽度就是 4，这是 $w_3$。于是

$$address(A[i_1][i_2][i_3]) = base + i_1 \times 160 + i_2 \times 32 + i_3 \times 4$$

| 这一层的子数组 | 它是什么 | 宽度 |
| :--- | :--- | ---: |
| $A[i_1]$ | $5 \times 8$ 的二维整型数组 | $5 \times 8 \times 4 = 160$ |
| $A[i_1][i_2]$ | 8 个整型构成的一维数组 | $8 \times 4 = 32$ |
| $A[i_1][i_2][i_3]$ | 一个整型变量 | 4 |

三个系数 160、32、4 就是把数组从外往里一层层剥开的结果。也可以反过来记：第 $j$ 层的宽度，等于第 $j$ 层之后所有维度长度的乘积再乘元素大小；最后一层后面没有维度了，乘积是 1，宽度就是元素自己的大小。最后一个下标乘的系数最小，这意味着最后一维的下标每加 1，地址只移动一个元素——它正是变化最快的那个下标。

### 把地址公式落成三地址码

先看一维。设 $A$ 是包含 $n$ 个整型变量的数组，要翻译片段 `c = A[i]`。按公式，$A[i]$ 的地址是 $base + i \times 4$，对应的三条三地址码是：

```text
t1 = i * 4
t2 = A[t1]
c  = t2
```

第一条把偏移地址 $i \times 4$ 算出来放进 $t_1$；第二条用数组名 $A$ 表示基地址，基地址加偏移得到这个元素，取出来放进 $t_2$；第三条把 $t_2$ 赋给 $c$。

> **提示**：这里的 `A[t1]` 不是 C 语言里“下标为 t1 的元素”——`t1` 是字节偏移，不是下标。它只是一种紧凑记法，表示“以 A 为基址、偏移 t1 处的那个字”，把“基址加偏移”和“按地址取数”合在一条里写；真正落到机器指令上，它是“先算地址、再 load”两条指令。后面 SDT 生成 `t6 = A[t5]`，用的是同一套记法。

二维的例子长一点。设 $A$ 是 $3 \times 5$ 的二维整型数组，翻译 `c = A[i1][i2]`。地址是 $base + i_1 \times 20 + i_2 \times 4$，其中 20 是行宽（一行 5 个整型，$5 \times 4$），4 是元素宽度。生成的三地址码是：

```text
t1 = i1 * 20
t2 = i2 * 4
t3 = t1 + t2
t4 = A[t3]
c  = t4
```

两条乘法分别算出两段偏移，$t_3$ 把它们加起来得到总偏移，`A[t3]` 取出元素，最后赋给 $c$。

一维三条、二维五条，规律很清楚：每多一维，就多一条乘法、多一条加法；$k$ 维数组要算 $k$ 段偏移、做 $k-1$ 次累加。手写没问题，可编译器不能“看着公式现编”——它得在语法分析的过程中，随着一个个下标读进来，边归约边把这几条指令生成出来。这就是 SDT 要解决的事。

### 数组引用的 SDT：type、offset、array 三件套

设计数组引用的翻译方案，关键是怎么把地址公式同数组引用的文法关联起来。公式里有三样东西：基地址、各个宽度 $w_j$、累加出来的偏移。文法里是一个个下标，归约是一层层进行的，这三样东西也得跟着归约一层层算出来。

沿用简单赋值语句的自底向上翻译：从左向右扫描输入串，读到 `A[i1]` 就把它归约成 $L$，再读到 `[i2]` 就连同前面的 $L$ 归约成一个新的 $L$，如此一层层往下。每归约一次，我们就知道当前这个 $L$ 代表哪一层的子数组，宽度和偏移也就都能算了。为此给 $L$ 配三个属性：

| 属性 | 含义 | 作用 |
| :--- | :--- | :--- |
| `L.type` | $L$ 所代表的数组元素的类型表达式 | 提供这一层的宽度 $w_j$ |
| `L.offset` | 一个临时变量，累加 $\sum i_j \times w_j$ | 存累积偏移 |
| `L.array` | 数组名在符号表中的入口地址 | 提供基地址 |

`type` 是最巧的一个：宽度不用单独存，它藏在类型表达式里。$A$ 的类型表达式是 `array(3, array(5, array(8, int)))`，取它的元素类型 `element`，就得到 $A[i_1]$ 的类型 `array(5, array(8, int))`；再取一次 `element`，得到 `array(8, int)`；最后一次取 `element`，只剩 `int`。类型一层层往里收，宽度也就从 160 降到 32、再降到 4。

`offset` 是个纯粹的累加器，专门用来累加公式里的 $i_j \times w_j$ 这一项。`array` 是数组名在符号表的入口，因为 $A$ 只出现在最里层，而最后的取数动作发生在最外层的 $L$ 上，所以 `array` 得沿着由若干个 $L$ 组成的链一路向上传，传到数组元素所在的节点。

把 `A[i1][i2][i3]` 的归约过程走一遍。第一层，读到 `A[i1]`：

- `L.array = lookup(A)`，用名字表示地址，就是 `A`；
- `L.type = A.type.element`，即 `array(5, array(8, int))`；
- 调 `newtemp` 生成临时变量 $t_1$，`L.offset = t1`；
- `L.type` 的 width 算出来是 $5 \times 8 \times 4 = 160$，于是生成 `t1 = i1 * 160`。

第二层，读到 `i2`，连同前面的 $L$ 归约出新的 $L$：

- `L.array` 由子节点传上来，还是 `A`；
- `L.type = L1.type.element`，即 `array(8, int)`，宽度 $8 \times 4 = 32$；
- 新临时变量 $t_2$，生成 `t2 = i2 * 32`；
- 新临时变量 $t_3$ 作为新的 `L.offset`，生成 `t3 = t1 + t2`，把两段偏移累加。

第三层，读到 `i3`，再归约出一个 $L$：

- `L.array` 继续传上来；
- `L.type = L1.type.element`，即 `int`，宽度 4；
- 新临时变量 $t_4$，生成 `t4 = i3 * 4`；
- 新临时变量 $t_5$，生成 `t5 = t3 + t4`，得到总偏移。

最后把 $L$ 归约为表达式 $E$：新临时变量 $t_6$，生成 `t6 = A[t5]`，取数完成。

| 归约出的 $L$ | `L.type` | 宽度 | 生成的三地址码 | 累积后的 `L.offset` |
| :--- | :--- | ---: | :--- | :--- |
| $A[i_1]$ | `array(5, array(8, int))` | 160 | `t1 = i1 * 160` | $t_1$ |
| $A[i_1][i_2]$ | `array(8, int)` | 32 | `t2 = i2 * 32`；`t3 = t1 + t2` | $t_3$ |
| $A[i_1][i_2][i_3]$ | `int` | 4 | `t4 = i3 * 4`；`t5 = t3 + t4` | $t_5$ |

写成翻译方案，四条产生式对应四段语义动作：

```text
L → id [ E ]   { L.array  = lookup(id.lexeme);
                 L.type   = L.array.type.element;
                 L.offset = newtemp();
                 emit(L.offset "=" E.addr "*" width(L.type)); }

L → L1 [ E ]   { L.array  = L1.array;
                 L.type   = L1.type.element;
                 t        = newtemp();
                 emit(t "=" E.addr "*" width(L.type));
                 L.offset = newtemp();
                 emit(L.offset "=" L1.offset "+" t); }

E → L          { E.addr   = newtemp();
                 emit(E.addr "=" L.array "[" L.offset "]"); }

S → L = E      { emit(L.array "[" L.offset "]" "=" E.addr); }
```

每一层的乘法用哪个宽度，这里要盯准：用的是**新归约出来的这个 $L$** 的 `type` 的宽度。第一层新的 $L$ 是 $A[i_1]$，类型 `array(5, array(8, int))`，宽度 160；第二层新的 $L$ 是 $A[i_1][i_2]$，宽度 32；第三层是 `int`，宽度 4。正好对上公式里三个系数，一个不多一个不少。

> **结论**：数组引用翻译的全部工作量，就是“用类型换宽度、用宽度换偏移、把偏移累加、最后加上基地址”。类型表达式是源头——它每往里收一层，宽度就缩小一次，乘出来的偏移项就高一层，累加器里就多一段。`t1`、`t2`、`t4` 是各层的单项偏移，`t3`、`t5` 是前缀和，`t5` 就是最终的总偏移。

这个方案有个很重要的设计特征：**所有语义动作都放在产生式的末尾**。正因为如此，它可以直接搭在自底向上的语法分析上——归约到哪条产生式，就执行那条产生式末尾的动作，不需要在产生式中间留位置，也不用改文法。最后一句 `S → L = E` 只生成一条指令 `L.array[L.offset] = E.addr`：等号左边是“基址 + 偏移”指出的那个位置，右边是要存进去的值。给数组元素赋值和从数组元素取值，区别只在最后这一条指令的方向上。

### 控制流语句：三种结构与一份文法

程序设计语言的控制流程一般就三种：顺序结构、分支结构、循环结构。分支比如 if 语句、case 语句；循环比如 while 语句、for 语句、repeat 语句。这里以 if 代表分支、以 while 代表循环，同类语句的翻译思路是一样的。

控制流语句的基本文法：

```text
P → S
S → S1 S2                    可执行语句的序列
S → id = E                   赋值语句
S → if ( B ) S1              分支语句
S → if ( B ) S1 else S2
S → while ( B ) S1           循环语句
```

$S$ 生成可执行语句的序列：序列里的每一条语句可以是赋值语句，也可以是分支语句，还可以是循环语句；语句序列再往上构成一个程序 $P$。

分支和循环语句的翻译跟赋值语句有本质不同：它们本身不产生“算术值”，只负责把控制流摆对。翻译的产物不是某个临时变量里的数，而是一串排好序的指令加几条跳转。判断翻得对不对，就看程序执行到某一个点时，是不是该走那条路。

### 代码结构图决定了属性怎么传

以 if-then-else 语句为例。语句 $S$ 的代码由三部分构成：布尔表达式 $B$ 的代码、$S_1$ 的代码、$S_2$ 的代码。$B$ 被翻译成由跳转指令构成的跳转代码，这些跳转指令根据 $B$ 的值选择下一个执行点：$B$ 为真，执行 $S_1$ 的第一条指令；$B$ 为假，执行 $S_2$ 的第一条指令。$S_1$ 执行完以后不能直接往下掉进 $S_2$，必须跳过 $S_2$ 到 $S$ 之后，所以还要生成一条 `goto S.next`。

```text
        [ B 的代码 ]         按 B 的值选出口
          /       \
     B=true     B=false
        |           |
  [ S1 的代码 ] [ S2 的代码 ]
        |           |
  goto S.next       |
         \         /
           S.next
```

`S.next` 是一个地址，这个地址里存放着紧跟在 $S$ 代码之后的那条指令的标号。紧跟其后的指令也叫 $S$ 的后继指令。三地址指令用标号来标识，标号实际上就是一个序号。

既然 $S$ 有 `next` 这个继承属性，$S_1$ 和 $S_2$ 也就都有：它们执行完都要到 $S$ 后面去，所以 `S1.next`、`S2.next`、`S.next` 指向同一条指令。

$B$ 有两个出口：真时跳到哪、假时跳到哪，所以给 $B$ 设两个继承属性 `B.true` 和 `B.false`，都是地址，地址里分别存放 $B$ 为真、为假时控制流转向的指令标号。

> **结论**：控制流语句的翻译，本质上是“把代码块按顺序摆好，再用跳转指令把它们的出入口接起来”。`next`、`true`、`false` 这三个属性记的不是值，而是接口——哪条指令接进来，哪条指令接出去。

### 语句序列的 SDT：先把标号的位置占住

先看最简单的 $P \to S$。$S$ 有继承属性 `next`，所以在 $S$ 出现之前就得把 `S.next` 算出来：调用 `newlabel`，它生成一个用于存放标号的临时变量，返回这个变量的地址，把地址赋给 `S.next`。这个变量将来装的就是 $S$ 执行完之后下一条指令的标号。等 $S$ 分析完、代码全部生成完，下一条指令的标号才能确定，这时候调用 `label`，把下一条三地址指令的标号赋给这个变量，也就是填入 `S.next`。

这里有个关键分工：$S$ 之前那个动作只确定了“标号存放在哪”，标号的具体值要等 $S$ 分析完之后那个动作才填进去。

> **提示**：这相当于在旅店给客人先订一个房间——房间号可以先定下来，客人到了再入住。`S.next` 就是那个房间号：在 $S$ 出现之前，房间号（存放标号的变量地址）可以预先确定，但里面住的是谁（标号的值），得等代码生成到那里才知道。所以属性值本身是一个变量的地址，变量里装的才是标号；跳转指令引用这个变量，标号晚一点填也不影响指令已经生成，填进去的时候所有引用它的跳转自然就指向对了。

再看 $S \to S_1 S_2$。$S_1$ 执行完，下一条就是 $S_2$ 的第一条指令，可这个标号现在还不知道（$S_2$ 的代码还没生成），所以先占位；$S_1$ 分析完之后，下一条指令的标号就是 $S_2$ 的第一条指令的标号，这时填进去。$S_2$ 执行完要到 $S$ 之后，所以 `S2.next = S.next`：

```text
S → { S1.next = newlabel(); }
    S1
    { label(S1.next); S2.next = S.next; }
    S2
```

赋值语句的翻译方案前面已经讲过，直接拿来用。真正要重点处理的是分支语句和循环语句。

### 分支与循环的 SDT

#### if-then-else

照代码结构图写语义动作，位置就有了依据：`B.true`、`B.false` 必须在 $B$ 之前算，因为 $B$ 的代码要引用这两个出口；`B.true` 的标号则要等 $B$ 的代码生成完、下一条指令落在 $S_1$ 的第一条上时才能填。

```text
S → if ( { B.true = newlabel(); B.false = newlabel(); }
         B
     ) then { label(B.true); S1.next = S.next; }
         S1
       { emit("goto " S.next); }
     else { label(B.false); S2.next = S.next; }
         S2
```

在 $B$ 出现之前调 `newlabel` 生成两个用于存放标号的临时变量，分别赋给 `B.true` 和 `B.false`。读入 `then` 以后，下一条指令就是 $S_1$ 的第一条指令，所以调 `label` 把它的标号填进 `B.true`——$B$ 为真时去执行 $S_1$。$S_1$ 出现之前还要把 `S1.next` 设成 `S.next`：$S_1$ 执行完要跳过 $S_2$。等 $S_1$ 分析完毕，补一条 `goto S.next`。读入 `else` 以后，下一条指令是 $S_2$ 的第一条，调 `label` 填 `B.false`。$S_2$ 出现之前再令 `S2.next = S.next`。

注意 `B.true` 为什么不能一开始就 label：$B$ 的代码有长有短，$S_1$ 第一条指令的序号要等 $B$ 的跳转代码全部落地才数得出来。先 `newlabel` 占位、后 `label` 回填，这个套路在整篇里反复出现。

#### if-then

if-then 少一个 else 分支，代码结构随之变简单：$B$ 为假时直接去 `S.next`，$S_1$ 执行完也去 `S.next`。

```text
        [ B 的代码 ]
          /       \
     B=true     B=false
        |           |
  [ S1 的代码 ]     |
        |           |
         \         /
           S.next
```

对应的 SDT 只有一处需要新标号：

```text
S → if ( { B.true = newlabel(); B.false = S.next; }
         B
     ) then { label(B.true); S1.next = S.next; }
         S1
```

和 if-then-else 比，省掉了一个标号和一条 `goto`：`B.false` 直接等于 `S.next`，不用为它单开变量；$S_1$ 后面也不需要 `goto S.next`，因为 $S_1$ 的代码后面紧跟着的就是 `S.next` 指向的指令，让控制流自然落下去即可。

#### while

while 和 if 的根本区别是“要回去”。$B$ 为真时执行 $S_1$，$S_1$ 执行完不能往后走，得跳回 while 的第一条指令重新判断 $B$。所以 while 需要一个属于自己的标号 `S.begin`，记住循环入口在哪。

```text
     S.begin:
        [ B 的代码 ]
          /       \
     B=true     B=false
        |           |
  [ S1 的代码 ]     |
        |           |
   goto S.begin     |
         \         /
           S.next
```

```text
S → while { S.begin = newlabel(); label(S.begin);
            B.true = newlabel(); B.false = S.next; }
        ( B )
      do { label(B.true); S1.next = S.begin; }
        S1
      { emit("goto " S.begin); }
```

读入 `while` 就说明这是一个 while 语句，要立刻记下它的入口：调 `newlabel` 生成存放标号的临时变量赋给 `S.begin`，紧接着 `label(S.begin)` 把下一条指令的标号（也就是 while 的第一条指令）填进去。$B$ 之前算两个出口：`B.true` 新开标号，`B.false` 等于 `S.next`（循环出口）。读入 `do` 以后，下一条是 $S_1$ 的第一条，`label(B.true)` 填进去。$S_1$ 的 `next` 不是 `S.next` 而是 `S.begin`——循环体执行完要回到入口；$S_1$ 之后再来一条 `goto S.begin`，闭环完成。

> **提示**：三个语句里只有 while 需要 `S.begin`，因为只有它要往回跳。if 的两个分支都是往前走的，`next` 一个属性就够；while 的循环体必须知道“家在哪儿”，这个家就是循环入口的标号。

### 布尔表达式：真值藏在代码的位置里

分支语句和循环语句都离不开布尔表达式。它的基本文法：

```text
B → B1 or B2
B → B1 and B2
B → not B1
B → ( B1 )
B → E1 relop E2
B → true
B → false
```

$relop$ 表示关系运算符，包括小于、小于等于、大于、大于等于、等于和不等于；把它作用于两个算术表达式，得到的就是一个关系表达式，关系表达式本身可以构成一个布尔表达式。布尔常量 `true`、`false` 也是布尔表达式。逻辑运算符与、或、非和括号作用于布尔表达式，又得到新的布尔表达式。三个逻辑运算符的优先级从高到低是：非、与、或。

布尔表达式的翻译方式和算术表达式不一样。它被翻译成跳转代码：与、或、非这些运算符被翻译成跳转指令，运算符本身并不出现在代码里；布尔表达式的值不用一个变量存起来，而是由代码序列中的位置来表示——控制流走到真出口，就说明它是真；走到假出口，就说明是假。

看一个输入片段：`if x < 100 or x > 200 and x != y then x = 0`。按优先级，它等价于 `x < 100 or ((x > 200) and (x != y))`。翻译出来的三地址码里一条逻辑运算指令都没有：

```text
1    if x < 100 goto L2      真：整个式子为真，去执行 x = 0
2    goto L3                 假：还得看右边
3 L3:if x > 200 goto L4
4    goto L1                 不大于 200：整个式子为假
5 L4:if x != y goto L2
6    goto L1                 不等于 y 不成立：整个式子为假
7 L2:x = 0
8 L1:（if 之后的下一条指令）
```

第 1 条：$x < 100$ 成立，整个布尔表达式就为真，直接跳到 `L2` 执行 `x = 0`。否则跳 `L3` 继续判断 $x > 200$。$x > 200$ 成立，还要继续跳到 `L4` 判断 $x 
e y$；$x 
e y$ 成立，整个式子为真，跳 `L2`；不成立，整个式子为假，跳 `L1` 去执行 if 之后的下一条语句。如果 $x$ 根本不大于 200，那么“与”的左边已经是假，整个式子必假，直接跳 `L1`。

这段代码里，逻辑运算符已经彻底消失，只剩下条件跳转；短路求值也顺带实现了——$x < 100$ 一旦成立，后面两个关系根本不会被求值，因为控制流已经跳走了。

### 布尔表达式的 SDT

布尔表达式只有两个出口，翻译方案要做的就是给每条产生式安排好这两个出口怎么传下去。

#### 关系表达式、常量与括号

关系表达式是整个布尔表达式的叶子判断，它只能给出一次判断结果，所以生成两条指令：成立跳真出口，不成立跳假出口。布尔常量 true 和 false 的值是确定的，只生成一条无条件跳转。括号只是分组，不改变任何出口。

```text
B → E1 relop E2  { emit("if " E1.addr relop E2.addr " goto " B.true);
                   emit("goto " B.false); }
B → true         { emit("goto " B.true); }
B → false        { emit("goto " B.false); }
B → ( B1 )       { B1.true = B.true; B1.false = B.false; }
```

#### not

`not` 的翻译最省事：$B_1$ 真等于 $B$ 假，$B_1$ 假等于 $B$ 真，所以把两个出口对调就行，一条指令都不生成。

```text
B → not B1  { B1.true = B.false; B1.false = B.true; }
```

#### or

先画代码结构：$B_1$ 为真，整个式子真，跳 `B.true`；$B_1$ 为假，才需要看 $B_2$——跳到 $B_2$ 的第一条指令；$B_2$ 为真跳 `B.true`，为假跳 `B.false`。

```text
        [ B1 的代码 ]
          /       \
     B1=true    B1=false
        |           |
     B.true   [ B2 的代码 ]
                  /      \
             B2=true    B2=false
                |           |
             B.true      B.false
```

```text
B → B1 or { B1.true = B.true; B1.false = newlabel(); }
       B2 { label(B1.false); B2.true = B.true; B2.false = B.false; }
```

$B_1$ 的真出口直接就是整个 $B$ 的真出口，所以 `B1.true = B.true`。$B_1$ 的假出口要落到 $B_2$ 的第一条指令上，但 $B_2$ 还没生成，只好先 `newlabel` 占位；读入 `or` 之后，$B_2$ 的代码紧接着开始，这时 `label(B1.false)` 把位置填实。$B_2$ 的两个出口就是整个 $B$ 的两个出口，原样上传。

#### and

`and` 是 `or` 的镜像：$B_1$ 为假，整个式子假，跳 `B.false`；$B_1$ 为真，才需要看 $B_2$。

```text
B → B1 and { B1.false = B.false; B1.true = newlabel(); }
       B2  { label(B1.true); B2.true = B.true; B2.false = B.false; }
```

对照着看就清楚了：

| 产生式 | $B_1$ 哪个出口直通 $B$ | 哪个出口要新标号 | $B_2$ 的真出口 | $B_2$ 的假出口 |
| :--- | :--- | :--- | :--- | :--- |
| $B_1$ `or` $B_2$ | true 直通 `B.true` | false 开新标号，指向 $B_2$ | `B.true` | `B.false` |
| $B_1$ `and` $B_2$ | false 直通 `B.false` | true 开新标号，指向 $B_2$ | `B.true` | `B.false` |

> **提示**：只记一句话——`or` 是“左边假了才往下走”，`and` 是“左边真了才往下走”。另一个产生式不用背，把 true 和 false 对调就是它。这两个产生式里的 `newlabel`／`label` 也是先占位后回填，和语句里处理 `next` 的手法完全一样。

### 一个完整的例子：while 里套 if

前面这套 SDT，基础文法不是 LL(1) 文法，所以没法在自顶向下的语法分析里同时做语义翻译；而它的产生式右部又含有内嵌的语义动作，想在自底向上的分析里直接执行，也得改文法、引入一些标记非终结符。为了把 SDT 本身讲清楚，这里用 SDT 的通用实现方法：任何一个 SDT 都可以先给输入句子建一棵语法分析树，再按从左到右的深度优先顺序执行语义动作。这个 SDT 的基础文法本身是可以用 LR 技术分析的，所以先用 LR 分析器造出分析树，再在树上执行动作。

要翻译的输入片段是一个 while 里嵌套 if：

```text
while a < b do
    if c < d then x = y + z else x = y - z
```

建出分析树以后，各子树对应得很清楚：$a < b$ 对应 $B$；$c < d$ 对应 $B_1$；$x = y + z$ 对应 $S_1$；$x = y - z$ 对应 $S_2$；整个 if 语句对应 while 的循环体 $S_3$。

从根往下，按深度优先执行动作。根节点是 $P \to S$：$S$ 之前调 `newlabel`，假设生成标号变量 $L_1$，`S.next = L1`；$S$ 分析完之后再回填，这一步先记着。

进入 while 产生式。读入 `while` 之后立刻占住循环入口：`S.begin = newlabel()`，假设是 $L_2$；紧接着 `label(S.begin)`，此时下一条指令就是 1 号，于是 $L_2 = 1$。$B$ 之前设两个出口：`B.true = newlabel()`，假设 $L_3$；`B.false = S.next = L1`。

$B$ 对应关系表达式 $a < b$，生成两条跳转：指令 1 `if a < b goto L3`，指令 2 `goto L1`。

读入 `do`，下一条指令是循环体的第一条，于是 $L_3 = 3$；同时循环体（$S_3$）的 `next` 设为 `S.begin`，执行完要回到 $L_2$。

循环体是那棵 if 子树。读入 `if` 之后，为 $B_1$ 生成两个出口：`B1.true = newlabel()` 得 $L_4$，`B1.false = newlabel()` 得 $L_5$。$B_1$ 对应 $c < d$，生成指令 3 `if c < d goto L4`、指令 4 `goto L5`。

读入 `then`，$B_1$ 的真出口落到下一条指令上，$L_4 = 5$；then 分支的 `next` 继承父节点的值，等于 $L_2$。then 分支是赋值语句 $x = y + z$：先算右边，指令 5 `t1 = y + z`，再赋值，指令 6 `x = t1`。$S_1$ 分析完之后补一条 `goto S.next`，即指令 7 `goto L2`。

读入 `else`，$B_1$ 的假出口落到下一条指令上，$L_5 = 8$；else 分支的 `next` 也等于 $L_2$。else 分支 $x = y - z$ 生成指令 8 `t2 = y - z`、指令 9 `x = t2`。

if 子树的代码到此结束。回到 while 产生式，循环体之后的那条动作生成指令 10 `goto L2`，把控制流送回循环入口。

整个 $S$ 的代码生成完毕，根节点上那条回填动作执行：下一条指令是 11 号，于是 $L_1 = 11$。

五个标号变量最后装的内容如下：

| 标号变量 | 存放的标号 | 指向的指令 |
| :--- | ---: | :--- |
| $L_1$ | 11 | while 之后的下一条指令 |
| $L_2$ | 1 | while 的第一条指令，即 $B$ 的代码起点 |
| $L_3$ | 3 | 循环体的第一条指令 |
| $L_4$ | 5 | then 分支的第一条指令 |
| $L_5$ | 8 | else 分支的第一条指令 |

刚生成时，代码里写的还是标号变量：

```text
1    if a < b goto L3
2    goto L1
3    if c < d goto L4
4    goto L5
5    t1 = y + z
6    x = t1
7    goto L2
8    t2 = y - z
9    x = t2
10   goto L2
11   （while 之后的下一条指令）
```

把标号变量的值代进去，就是最终的三地址码：

```text
1    if a < b goto 3
2    goto 11
3    if c < d goto 5
4    goto 8
5    t1 = y + z
6    x = t1
7    goto 1
8    t2 = y - z
9    x = t2
10   goto 1
11   （while 之后的下一条指令）
```

现在检验一遍。$a < b$ 成立，跳 3 号进入循环体；否则执行 2 号，跳 11 号，直接出循环。进循环体后判断 $c < d$：成立跳 5 号执行 $x = y + z$，执行完 7 号跳回 1 号重新判断 $a < b$；不成立跳 8 号执行 $x = y - z$，执行完落进 10 号，同样跳回 1 号。两条路径都回到循环入口，循环出口只有一个 11 号，和当初画的结构图完全对得上。

把这批指令写成四元式，就是每条指令拆成运算符、两个操作数、结果四个域，控制流和上面一模一样，只是换了一种记录形式。

从数组元素的地址算式，到 while 里套 if 的整段跳转代码，这一路翻译的对象始终是“位置”：数组引用算的是元素在内存中的位置，控制流排的是指令在代码序列中的位置。位置算对了、接口接对了，三地址码自然就出来了。

## 回填：把目标标号的确定推迟到该确定的时候
> 对应块：BLK12 | 覆盖分集：P50-P52 | 块标题（分集名）：《6-8布尔表达式的回填》

布尔表达式和控制流语句的中间代码，说到底是靠跳转指令串起来的。而跳转指令天生带着一个矛盾：它必须写清楚跳到哪儿，可生成它的那一刻，那个"哪儿"往往还没被翻译出来。

`if a < b then ...` 就是现成的例子。条件成立要跳到 then 分支的第一条指令，但这条指令此刻还不在代码序列里。前面介绍过的翻译方案是把这个矛盾往下压：把"存放标号的地址"作为继承属性，一路传递到生成跳转指令的地方，先留个地址占位，事后再走一趟，把标号和地址绑定起来。

这一趟额外的处理是可以省掉的。回填换了个思路——不再传地址，而是传列表：把由跳转指令组成的列表作为综合属性向上传递。生成一条跳转指令时，暂不指定目标标号，先把这条指令放进一个列表；同一个列表里的所有跳转指令，最终共享同一个目标标号；等到这个标号能够确定了，再回头把这个列表里的指令一次性全部填上。

于是非终结符 `B` 拿到两个综合属性：

- `B.truelist`：指向一个跳转指令列表，这些指令最终获得的目标标号，就是 `B` 为真时控制流应该转向的那条指令的标号；
- `B.falselist`：指向一个跳转指令列表，这些指令最终获得的目标标号，就是 `B` 为假时控制流应该转向的那条指令的标号。

> **结论**：回填不是"不填"，而是"先记账、后结算"。列表是账本，生成指令时只管记账，等目标确定了再一次性结算——省掉的正是原来那趟专门用来绑定标号的遍历。

### 三个操作列表的函数

账本要能记、能并、能结，于是配三个函数，全部围绕"跳转指令列表"这一个数据结构。

| 函数 | 参数 | 作用 |
| :--- | :--- | :--- |
| `makelist(i)` | 一条跳转指令的标号 `i` | 创建一个只包含标号 `i` 的列表，返回指向新列表的指针 |
| `merge(p1, p2)` | 两个列表的指针 `p1`、`p2` | 把两个列表合并，返回指向合并后列表的指针 |
| `backpatch(p, i)` | 列表指针 `p`、目标标号 `i` | 把 `i` 作为目标标号，填入 `p` 所指列表中的每一条指令 |

分工很清楚：`makelist` 负责开账，一条新生成、目标待定的跳转指令用它单独成册；`merge` 负责合账，两个子表达式的跳转可能指向同一个出口，就把两本账并成一本；`backpatch` 负责结账，出口标号一旦确定，把账上每一条指令的目标标号统统填上。

贯穿全过程的还有一个 `nextcode`——即将生成的下一条指令的标号。它决定新指令的编号，也是调用 `makelist` 时的取值依据。

> **提示**：`B → E1 relop E2` 要连着生成两条跳转指令，第一条的标号是 `nextcode`，第二条是 `nextcode + 1`。这两个值必须在生成指令之前取好，因为两条指令一落地，`nextcode` 就往后挪了两位。

### 布尔表达式的基本产生式

#### 关系表达式：一次生成两条待回填的跳转

当 `B` 定义为一个关系表达式时，这个布尔表达式被翻译成两条跳转指令：第一条判断关系是否成立，成立就跳到 `B` 的真出口；第二条是无条件跳转，跳到 `B` 的假出口。

```text
B.truelist  = makelist(nextcode)
B.falselist = makelist(nextcode + 1)
    if E1 relop E2 goto _        // 标号 nextcode
    goto _                       // 标号 nextcode + 1
```

两条指令的目标标号此刻都定不下来，所以各记一本账：条件跳转的去向是 `B` 的真出口，把它挂到 `B.truelist` 上；无条件跳转的去向是 `B` 的假出口，把它挂到 `B.falselist` 上。`makelist(nextcode)` 造出一个只含这一条指令标号的列表，指针交给 `B.truelist`；`makelist(nextcode + 1)` 再造一个，指针交给 `B.falselist`。

到这一步，一个关系表达式在代码里就只留下两条跳转，加两本待结的账。至于跳转真正要落到哪里，等外层把出口定下来再说。

#### 常数、括号与取反

`B → true` 和 `B → false` 是两种"值已经确定"的情形。前者可以断定整个布尔表达式为真，于是生成一条跳转到 `B` 真出口的指令，真出口眼下未知，这条指令进 `B.truelist`；后者可以断定整个布尔表达式为假，生成一条跳转到 `B` 假出口的指令，进 `B.falselist`。

`B → (B1)` 不改变任何东西：对 `B` 的翻译与对子表达式 `B1` 的翻译完全相同，属性值直接照搬，`B.truelist = B1.truelist`，`B.falselist = B1.falselist`。

`B → not B1` 把真假整个翻过来，所以两个属性对调：`B.truelist = B1.falselist`，`B.falselist = B1.truelist`。

> **易错点**：`true` 和 `false` 产生的是无条件跳转，不是条件跳转。值已经确定了，没有条件可判——判据都省了，只剩"跳"这一个动作。

### or 与 and：真出口和假出口分别通向哪里

复合的布尔表达式没有新指令，全部工作就是把两个子表达式的四本账重新分配。分配的规矩只有一条：顺着"值什么时候能定下来"去推。

#### or：第一个为假才去问第二个

`B → B1 or B2` 要处理的是两个子表达式的四本账。先把两段代码的骨架摆出来，账记在哪个位置一目了然。

```text
B1 的代码
    if (...) goto _          <- B1.truelist：目标 = B 的真出口
    goto _                   <- B1.falselist：目标 = B2 的第一条指令
B2 的代码
    if (...) goto _          <- B2.truelist：目标 = B 的真出口
    goto _                   <- B2.falselist：目标 = B 的假出口
```

`B1.truelist` 里的指令要跳 `B1` 的真出口。`B1` 为真，`or` 的结果就已经是真的了，右边根本不用算，所以 `B1` 的真出口就是 `B` 的真出口——要跳 `B1` 的真出口，就是要跳 `B` 的真出口，这些指令整个并入 `B.truelist`。

`B1.falselist` 里的指令要跳 `B1` 的假出口。`B1` 为假，结果还不能定，必须接着判 `B2`，所以 `B1` 的假出口就是 `B2` 的第一条指令。这批指令得回填成那个位置，而那个位置在归约的那一刻还没算出来，于是需要提前存下来。

`B2.truelist` 同理：`B2` 为真，整个 `or` 为真，`B2` 的真出口就是 `B` 的真出口，并入 `B.truelist`。

`B2.falselist` 里的指令要跳 `B2` 的假出口。`B2` 也假，整个表达式才是假，所以 `B2` 的假出口就是 `B` 的假出口，`B.falselist` 直接就是 `B2.falselist`。

为了在归约时拿到"`B2` 的第一条指令"这个标号，产生式里在 `B2` 之前插一个标记非终结符 `M`：

$$B \to B_1 \text{ or } M\ B_2$$

`M` 的语义动作只有一件事，把当时的下一条指令标号记下来：`M.code = nextcode`。因为 `M` 就摆在 `B2` 前面，`M.code` 天然就是 `B2` 的第一条指令的标号。

```text
M.code = nextcode
backpatch(B1.falselist, M.code)
B.truelist  = merge(B1.truelist, B2.truelist)
B.falselist = B2.falselist
```

> **提示**：为什么非要插一个 `M`？自底向上分析里，等到 `B1 or B2` 可以归约时，`B2` 早就翻译完了，"`B2` 的第一条指令"这个位置已经被后面一长串指令盖过去，栈上再也找不回来。`M` 的作用就是在那个位置上留一个存档，归约时把存档取出来用。

#### and：第一个为真才去问第二个

`B → B1 and B2` 的结构和 `or` 是镜像的，`B2` 之前同样要有 `M`：

$$B \to B_1 \text{ and } M\ B_2$$

```text
B1 的代码
    if (...) goto _          <- B1.truelist：目标 = B2 的第一条指令
    goto _                   <- B1.falselist：目标 = B 的假出口
B2 的代码
    if (...) goto _          <- B2.truelist：目标 = B 的真出口
    goto _                   <- B2.falselist：目标 = B 的假出口
```

`B1.truelist` 里的指令跳 `B1` 的真出口。`B1` 为真，`and` 的结果还定不下来，得接着判 `B2`，所以 `B1` 的真出口就是 `B2` 的第一条指令——这批指令要用 `M.code` 回填。

`B1.falselist` 里的指令跳 `B1` 的假出口。`B1` 为假，整个 `and` 就是假，`B1` 的假出口就是 `B` 的假出口，并入 `B.falselist`。

`B2.truelist` 里的指令跳 `B2` 的真出口。`B2` 也真，整个表达式才真，所以 `B.truelist` 直接等于 `B2.truelist`。

`B2.falselist` 里的指令跳 `B2` 的假出口，而 `B2` 为假整个 `and` 就是假，所以这批和 `B1.falselist` 是同一个归宿，两者 `merge` 起来交给 `B.falselist`。

```text
M.code = nextcode
backpatch(B1.truelist, M.code)
B.truelist  = B2.truelist
B.falselist = merge(B1.falselist, B2.falselist)
```

把两条规则并排放在一起看，镜像关系就出来了。

| 比较项 | `B1 or B2` | `B1 and B2` |
| :--- | :--- | :--- |
| 左侧能直接定值的一端 | `B1` 为真 | `B1` 为假 |
| 该端出口的归属 | 并入 `B.truelist` | 并入 `B.falselist` |
| 左侧另一端 | 回填到 `B2` 的第一条指令 | 回填到 `B2` 的第一条指令 |
| `B.truelist` 的来源 | `merge(B1, B2)` 的 truelist | 只要 `B2.truelist` |
| `B.falselist` 的来源 | 只要 `B2.falselist` | `merge(B1, B2)` 的 falselist |

> **易错点**：两条规则是镜像，但不是"完全对称"。`or` 里要 `merge` 的是 truelist，`and` 里要 `merge` 的是 falselist——哪一端能独立定值，哪一端的账就只剩另一本的。记混的根源在于只记了"or 合并真、and 合并假"这半句，忘了前面还有一半：左边为真（或假）时右边整段被短路。

### 完整走一遍：`a < b or c < d and e < f`

属性全是综合属性，所以可以自底向上地翻译，从左向右扫输入串。假设下一条指令从 100 号开始编。

读入 `a < b`，把它归约成 `B`。按关系表达式的动作，`makelist(nextcode)` 得到 `{100}` 交给 `B.truelist`，`makelist(nextcode + 1)` 得到 `{101}` 交给 `B.falselist`；`E1.address = a`，`relop` 是小于号，`E2.address = b`，引号里的字符串按字面值传递。于是落下两条指令：

```text
100  if a < b goto _
101  goto _
```

接着读入 `or`。空串归约出一个标记非终结符 `M`，它的动作是 `M.code = nextcode`，此刻 `nextcode` 已经是 102，所以 `M.code = 102`——这就是第二个子表达式的入口。

继续读入 `c < d`，归约成 `B`，同样一套动作：`B.truelist = {102}`，`B.falselist = {103}`，并生成

```text
102  if c < d goto _
103  goto _
```

此时栈顶是 `B or B`，向前看一个符号是 `and`。`and` 的优先级高于 `or`，这里不能拿 `or` 产生式去规约，得先把 `and` 移进来——否则 `c < d and e < f` 会被拆散，算出来的是 `(a < b or c < d) and (e < f)`，语义就变了。

读入 `and` 之后，栈顶再归约出一个 `M`，`M.code = nextcode = 104`。继续读入 `e < f` 归约成 `B`：`B.truelist = {104}`，`B.falselist = {105}`，并生成

```text
104  if e < f goto _
105  goto _
```

到这里，三条关系表达式各自的两本账都记好了。接下来两次归约把账并起来。

先归约栈顶的 `B and B`。用 `M.code`，也就是 104，回填 `B1.truelist` 里的 102 号指令——102 的目标标号定为 104。然后算父节点的两个属性：`B.truelist = B2.truelist = {104}`；`B.falselist` 是两个子节点 falselist 的合并，103 与 105 并成 `{103, 105}`。

再归约 `B or B`。用 `M.code`，也就是 102，回填 `B1.falselist` 里的 101 号指令——101 的目标标号定为 102。然后 `B.truelist` 由两个子节点的 truelist 合并而成，100 与 104 并成 `{100, 104}`；`B.falselist = B2.falselist = {103, 105}`。

整个表达式的三地址码就是这六条：

```text
100  if a < b goto _
101  goto 102
102  if c < d goto 104
103  goto _
104  if e < f goto _
105  goto _
```

其中四条指令还在等回填：`B.truelist` 里的 100 和 104，等 `B` 的真出口确定以后用真出口标号填；`B.falselist` 里的 103 和 105，等 `B` 的假出口确定以后用假出口标号填。

这六条指令值得再读一遍，短路语义全写在跳转里了：`a < b` 成立，100 直奔真出口，`c < d`、`e < f` 一次都不算；`a < b` 不成立，101 落到 102 去问 `c < d`；`c < d` 成立，102 跳到 104 去问 `e < f`，不成立则 103 直奔假出口，`e < f` 也不算。所谓"与的优先级高于或"，在代码里就是 102 的目标是 104 而不是 103。

### 控制流语句的 nextlist

布尔表达式解决的是"条件为真往哪走、为假往哪走"，控制流语句还要多解决一个"整条语句执行完往哪走"。为此给非终结符 `S` 设一个综合属性 `S.nextlist`：它指向一个跳转指令列表，这些指令最终获得的目标标号，就是按照运行顺序紧跟在 `S` 的代码之后的那条指令的标号。

这个属性的定位很关键——它不表示"代码序列里紧挨着的下一条"，而是"运行顺序上的下一条"。两者在 `if`、`while` 里恰恰不是一回事，回填的全部难点都在这儿。

有了 `nextlist`，一条语句在翻译完之后，对外只留下一个待结的账：我这块代码执行完，还有哪些跳转没找到家。

### if 语句：两个标记非终结符各管一个出口

#### 只有 then 分支

$$S \to \text{if } B \text{ then } M\ S_1$$

先把骨架画出来。

```text
B 的代码
    if (...) goto _          <- B.truelist：目标 = S1 的第一条指令（M.code）
    goto _                   <- B.falselist：并入 S.nextlist
S1 的代码
```

`B.truelist` 里的指令跳 `B` 的真出口，也就是 `S1` 的第一条指令——条件成立就进 then 分支。`B.falselist` 里的指令跳 `B` 的假出口，`B` 为假时整个 if 语句什么都不做，直接跳出这条语句，去执行 `S` 之后的第一条指令，所以这批指令要放进 `S.nextlist`。

`S1.nextlist` 里的指令跳 `S1` 之后的第一条指令。`S1` 执行完，整个 `S` 也就执行完了，接下来同样是 `S` 之后的第一条指令，所以这批也要并进 `S.nextlist`。

分析 `S1` 之前，需要用 `S1` 的第一条指令标号回填 `B.truelist`，这个标号得提前记下，于是 `S1` 前面插 `M`。

```text
M.code = nextcode
backpatch(B.truelist, M.code)
S.nextlist = merge(B.falselist, S1.nextlist)
```

一个 if 语句的出口账合起来只有一本：条件为假跳出去的，加上 then 分支内部攒下的。

#### 带 else 分支与那条显式跳转

$$S \to \text{if } B \text{ then } M_1\ S_1\ N\ \text{else } M_2\ S_2$$

```text
B 的代码
    if (...) goto _          <- B.truelist：目标 = S1 的第一条（M1.code）
    goto _                   <- B.falselist：目标 = S2 的第一条（M2.code）
S1 的代码
    goto _                   <- N 生成，目标 = S 之后的第一条
S2 的代码
```

`B.truelist` 跳 `B` 的真出口，也就是 `S1` 的第一条指令；`B.falselist` 跳 `B` 的假出口，这回假出口不再是语句末尾，而是 `S2` 的第一条指令——条件不成立就转去执行 else 分支。

`S1.nextlist` 里的指令跳 `S1` 之后的第一条指令。但 `S1` 执行完不能顺势落进 `S2` 的代码里去，必须跳过 else 分支，去执行 `S` 之后的第一条指令，所以这批进 `S.nextlist`。`S2.nextlist` 同理：`S2` 执行完整条 `S` 就结束，也是去 `S` 之后的第一条指令，同样进 `S.nextlist`。

除此之外还有一条容易漏掉的指令：`S1` 执行完之后，要显式生成一条 `goto`，跳过 `S2` 的代码。这条跳转的目标同样要等 `S` 之后的位置确定，所以它自己也要进 `S.nextlist`。为了在归约时能拿到它，`S1` 之后插一个标记非终结符 `N`，`N` 的动作是造一个只含这条跳转的列表：`N.nextlist = makelist(nextcode)`，随后生成 `goto _`。

```text
M1.code = nextcode                    // 在 S1 之前执行
M2.code = nextcode                    // 在 S2 之前执行
N.nextlist = makelist(nextcode)       // 在 S1 之后执行
    goto _
backpatch(B.truelist, M1.code)
backpatch(B.falselist, M2.code)
S.nextlist = merge(merge(S1.nextlist, N.nextlist), S2.nextlist)
```

`S.nextlist` 是三个来源合并出来的：`S1.nextlist`、`N.nextlist`、`S2.nextlist`。`merge` 是二元函数，所以并两次，先并前两个，再把结果和第三个并。

> **提示**：`if-then` 不需要那条显式跳转，`if-then-else` 必须有——差别全在代码的物理排布上。没有 else 时，then 分支的代码后面本来就是 `S` 之后的指令，落下去正好；一旦有了 else，then 分支的末尾紧贴着 else 分支的第一条指令，不跳就会"穿"进 else 里去。

### while 语句：循环体末尾要跳回开头

$$S \to \text{while } M_1\ B\ \text{do } M_2\ S_1$$

```text
M1.code 指向这里（B 的第一条指令）
B 的代码
    if (...) goto _          <- B.truelist：目标 = S1 的第一条（M2.code）
    goto _                   <- B.falselist：并入 S.nextlist
M2.code 指向这里（S1 的第一条指令）
S1 的代码
    goto M1.code             <- 循环回边，显式生成
```

`B.truelist` 跳 `B` 的真出口，也就是 `S1` 的第一条指令——条件成立就进循环体。`B.falselist` 跳 `B` 的假出口，`B` 为假就跳出整个 while，去执行 `S` 之后的第一条指令，进 `S.nextlist`。

`S1.nextlist` 里的指令，目标是 while 语句的第一条指令——循环体执行完要回去重新判断条件。而"while 语句的第一条指令"就是 `B` 的第一条指令，所以要在 `B` 之前插 `M1` 把这个入口记下来。同时 `S1` 之前插 `M2`，记下循环体的入口，供 `B.truelist` 回填。

循环体末尾还要显式生成一条 `goto M1.code`，这是回边。这条指令的目标在生成时就已经确定（`M1.code` 早就记好了），不需要回填，直接把标号写进去。

```text
M1.code = nextcode                    // 在 B 之前执行
M2.code = nextcode                    // 在 S1 之前执行
backpatch(S1.nextlist, M1.code)
backpatch(B.truelist, M2.code)
S.nextlist = B.falselist
    goto M1.code                      // 循环回边
```

注意这里回填的先后顺序和 if 语句不同：先用 `M1.code` 回填 `S1.nextlist`，再用 `M2.code` 回填 `B.truelist`。两个 `M` 一个记头、一个记体，各回填一本账，正好对上。

> **易错点**：`while` 的 `S.nextlist` 只等于 `B.falselist`，不含 `S1.nextlist`。循环体里的跳转全被回填到循环入口去了，它们不会"跳出循环"——跳出循环的唯一出口是条件为假。

### 顺序语句与赋值语句

`S → S1 S2` 的结构最简单。`S1.nextlist` 里的指令要跳 `S1` 之后的第一条指令，`S1` 执行完就该执行 `S2`，所以这些指令的目标就是 `S2` 的第一条指令，用 `S2` 之前插入的 `M` 记下入口后回填。`S2.nextlist` 里的指令跳 `S2` 之后的第一条指令，`S2` 执行完整条 `S` 也结束，所以直接交给 `S.nextlist`：

```text
M.code = nextcode
backpatch(S1.nextlist, M.code)
S.nextlist = S2.nextlist
```

赋值语句 `S → id = E` 里没有任何跳转指令，所以 `S.nextlist` 等于空。这条看着像废话，实际很要紧：空列表参与 `merge` 不改变结果，参与 `backpatch` 什么也不做——正是有了这个"空"，`while` 的循环体是赋值语句时那段回填才能安然无事地跳过。

### 翻译一棵嵌套的控制流语句

看一个真家伙：while 里套一个 if，if 的 then 分支里又套一个 while。

```text
while (a < b) do
    if (c < 5) then
        while (x > y) do
            z = x + 1
    else
        x = y
```

同样是自底向上、从左向右扫。假设指令从 100 号开始编。

读入 `while`，对应 while 产生式的第一个动作，栈顶归约出一个 `M1`，`M1.code` 记下一条指令的标号，于是 `M1.code = 100`。

读入 `a < b`，归约成 `B`：`B.truelist = {100}`，`B.falselist = {101}`，生成 100 号 `if a < b goto _` 和 101 号 `goto _`。

读入 `do`，栈顶归约出 `M2`，`M2.code = 102`。

读入 `if`，对应 if-then-else 产生式的开头。接着读入 `c < 5` 归约成 `B`：`B.truelist = {102}`，`B.falselist = {103}`，生成 102 号 `if c < 5 goto _` 和 103 号 `goto _`。

读入 `then`，栈顶归约出 `M1`，`M1.code = 104`。

再读入 `while`，进入内层 while。这里又归约出一个 `M1`，它的值还是 104——从上一条指令到此刻没有生成任何新指令，下一条指令的标号没变。接着 `x > y` 归约成 `B`：`B.truelist = {104}`，`B.falselist = {105}`，生成 104 号 `if x > y goto _` 和 105 号 `goto _`。

读入 `do`，内层的 `M2` 归约出来，`M2.code = 106`。

读入 `z = x + 1`。`x + 1` 归约成算术表达式 `E`，给它分配新临时变量 `t1`，`E.address = t1`，生成 `t1 = x + 1`，编号 106。再把 `z = E` 归约成赋值语句 `S`，生成 `z = t1`，编号 107。赋值语句不含跳转，`S.nextlist = ∅`。

到这里，内层 while 可以归约成 `S` 了。它的动作三步走：用 `M1.code = 104` 回填 `S1.nextlist`——`S1` 是那条赋值语句，列表是空的，所以实际上什么都没做；用 `M2.code = 106` 回填 `B.truelist` 里的 104 号指令，104 的目标标号定为 106；`S.nextlist = B.falselist = {105}`，再生成 `goto 104`（编号 108）。

内层 while 归约成 `S1` 之后，栈顶该归约出 `N` 了。`N` 的动作先调用 `makelist` 造一个只含下一条指令标号 109 的列表交给 `N.nextlist`，然后生成 109 号 `goto _`。

读入 `else`，`M2` 归约出来，`M2.code = 110`。

读入 `x = y`，归约成赋值语句，生成 110 号 `x = y`，`S.nextlist = ∅`。

现在可以归约整个 if 语句了。用 `M1.code = 104` 回填 `B.truelist` 里的 102 号指令，102 的目标定为 104；用 `M2.code = 110` 回填 `B.falselist` 里的 103 号指令，103 的目标定为 110；父节点的 `nextlist` 是三本账合并，`S1.nextlist` 的 105、`N.nextlist` 的 109、`S2.nextlist` 的空，合成 `{105, 109}`。

最后归约外层 while。用 `M1.code = 100` 回填 `S1.nextlist` 里的 105 和 109，两条都指向 100，也就是循环开头；用 `M2.code = 102` 回填 `B.truelist` 里的 100 号指令，100 的目标定为 102；父节点 `nextlist = B.falselist = {101}`；再生成 111 号 `goto 100`。

整段代码落成十二行：

| 标号 | 指令 | 来龙去脉 |
| :--- | :--- | :--- |
| 100 | `if a < b goto 102` | 外层循环条件，为真进循环体 |
| 101 | `goto _` | 外层循环的唯一出口，进 `S.nextlist` 等回填 |
| 102 | `if c < 5 goto 104` | if 条件为真，进 then 分支 |
| 103 | `goto 110` | if 条件为假，转 else 分支 |
| 104 | `if x > y goto 106` | 内层循环条件，为真进循环体 |
| 105 | `goto 100` | 内层循环条件为假，回外层循环开头 |
| 106 | `t1 = x + 1` | 表达式求值 |
| 107 | `z = t1` | 赋值 |
| 108 | `goto 104` | 内层循环的回边 |
| 109 | `goto 100` | then 分支结束，跳过 else |
| 110 | `x = y` | else 分支 |
| 111 | `goto 100` | 外层循环的回边 |

这份结果里有几处值得停下来看。

101 号指令始终没有填上，它就是整条语句的 `S.nextlist` 里唯一的成员。这条跳转是外层 while 的假出口，可"整个 while 之后是哪条指令"取决于这段代码后面接什么，翻译这条语句的时候根本不可能知道。它只能带着一个空位交出去，等外层语境确定位置后再回填——回填的边界不在单条语句内部，而在语句和外层之间。

105 和 109 都跳 100，而不是跳 111。105 是内层 while 的假出口，109 是 then 分支结束后的跳过指令，按"运行顺序上的下一条"都应该是外层循环体的末尾，也就是 111 那条回边；但外层 while 的语义动作把 `S1.nextlist` 直接回填成了 `M1.code`。两者效果一样，都是回到循环开头重新判断条件，只是 100 比 111 少跳一次。这说明 `nextlist` 的"下一条"是按运行顺序算的，不是按地址顺序算的。

111 那条 `goto 100` 依然必要。105 和 109 已经直接跳到 100 了，但 else 分支的 110 号指令执行完是自然下落的，必须有一条指令把它送回循环开头。所以"落到 111 再跳 100"和"直接从 105、109 跳 100"并存，各管一条路径。

### switch 语句要生成什么

很多语言里都有 switch 语句，有的语言管它叫 case 语句。它的语法很规整：一个待求值的选择表达式 `E`，配上 $n-1$ 个可能取值——都是常量 $V_1, V_2, \dots, V_{n-1}$；`E` 的值和哪个常量匹配，就执行与它对应的代码段 $S_i$；如果一个都不匹配，执行缺省的代码段 $S_n$。

按这个含义，代码该长成什么样，其实是可以直接想出来的。

`E` 只求值一次，结果存进临时变量 `t`，后面所有比较都读 `t`——否则每比一次就要重算一遍表达式，分支越多越亏。接着拿 `t` 依次和各个常量比：不相等就跳过本段的代码，去比下一个；全都不相等，自然落到 default 那一段。每段代码的末尾还要一条 `goto next`，否则执行完 `S_1` 会直接穿进 `S_2` 的代码里。

### 第一种方案：测试指令跟着分支走

把上面的想法直译成代码，结构是这样：

```text
E 的代码
t = E.address
if t != V1 goto L1              L1 指向 case V2 的测试
S1 的代码
goto next                       next 指向 switch 之后
if t != V2 goto L2              L2 指向 case V3 的测试
S2 的代码
goto next
              ...
if t != V(n-1) goto L(n-1)      L(n-1) 指向 Sn 的第一条指令
S(n-1) 的代码
goto next
Sn 的代码（default）
goto next
```

图中的 `L1` 是 `case V2:` 之后的第一条指令，也就是下一次测试；`L2` 是 `case V3:` 之后的第一条指令；一路推下去，`L(n-1)` 是 `S_n` 的第一条指令——最后一道测试失败，正好落进 default。`next` 是 `S_n` 的代码之后的第一条指令，也就是整个 switch 语句之后的第一条指令。

按位置摆语义动作，就得到这张表：

| 位置 | 语义动作 |
| :--- | :--- |
| `E` 之后 | 调用 `newtemp` 生成临时变量 `t`，生成 `t = E.address` |
| `case V1:` 之后 | 生成新标号 `L1`，生成 `if t != V1 goto L1` |
| `S1` 之后 | 生成新标号 `next`，生成 `goto next` |
| `case V2:` 之后 | 调用 `label` 把下一条指令的标号赋给 `L1`；生成新标号 `L2`，生成 `if t != V2 goto L2` |
| `S2` 之后 | 生成 `goto next` |
| … | 依此类推 |
| `default` 之后 | 调用 `label` 把下一条指令的标号赋给 `L(n-1)` |
| `Sn` 之后 | 调用 `label` 把下一条指令的标号赋给 `next` |

这套动作有个绕不开的麻烦：每个条件跳转指令的四元式里，第四个分量并不是目标标号，而是"存放目标标号的地址"。`L1` 要等到读入 `case V2:` 才知道是几，所以前面那条 `if t != V1 goto L1` 只能先填地址。于是又得额外走一趟，把标号和地址绑定起来——绕了一圈，回到了开头想避开的那个做法。

### 第二种方案：把测试集中到一处

还有一层考虑：第一种方案里，各段的测试指令和 `S` 的代码混在一起。分支一多，测试指令就被大段代码隔开，散得到处都是。把它们集中起来，代码生成阶段才有机会做优化——根据分支的个数、以及这些常量值是不是落在一个较小的范围内，这一串条件跳转可以被翻译成最高效的 $n$ 路分支。

集中之后的代码结构：

```text
E 的代码
t = E.address
goto test                       test 指向下面的测试区
S1 的代码
goto next                       next 指向测试区之后
S2 的代码
goto next
              ...
Sn 的代码（default）
goto next
test 指向这里：
if t = V1 goto L1
if t = V2 goto L2
              ...
if t = V(n-1) goto L(n-1)
goto Ln
```

`E` 求值之后先一条 `goto test` 越过所有分支代码，直接去测试区；测试区按 `t` 的取值把控制流分派到各个 `S` 的第一条指令；`L_n` 指向 default 段，所有测试都不成立时兜底。每个 `S` 的代码后面仍然是 `goto next`，`next` 是测试区之后的第一条指令。

翻译方案随之变成：

| 位置 | 语义动作 |
| :--- | :--- |
| `E` 之后 | 生成临时变量 `t`，生成 `t = E.address`；生成新标号 `test`，生成 `goto test` |
| `case V1:` 之后 | 调用 `newlabel` 建立新标号 `L1`，把 `S1.code` 第一条指令的标号赋给 `L1`；在 `V1` 与 `L1` 之间建立映射，放进映射表 |
| `S1` 之后 | 生成新标号 `next`，生成 `goto next` |
| `case V2:` 之后 | 建立新标号 `L2`，把 `S2.code` 第一条指令的标号赋给 `L2`，建立 `V2` 到 `L2` 的映射放进映射表 |
| `S2` 之后 | 生成 `goto next` |
| … | 依此类推 |
| `default` 之后 | 建立新标号 `Ln`，把 `Sn.code` 第一条指令的标号赋给 `Ln` |
| `Sn` 之后 | 生成 `goto next` |
| 测试区 | 调用 `label` 把下一条指令的标号赋给 `test`；从映射表读出 $n-1$ 个映射，依次生成 `if t = V1 goto L1` … `if t = V(n-1) goto L(n-1)`；最后生成 `goto Ln` |
| 测试区之后 | 调用 `label` 把下一条指令的标号赋给 `next` |

两种方案的差别，落到指令上就是两处对照。

| 比较项 | 第一种方案 | 第二种方案 |
| :--- | :--- | :--- |
| 测试指令的位置 | 紧跟在各段代码之前，与 `S` 混排 | 全部集中到所有 `S` 的代码之后 |
| 测试的条件 | `if t != Vi goto Li`，不等就跳过本段 | `if t = Vi goto Li`，相等就进本段 |
| 标号何时绑定 | 生成跳转时还没绑定，需要再走一趟 | 生成测试前已从映射表取到 `Li`，直接填 |
| 代码生成阶段 | 难以整体优化 | 测试集中，便于合成 $n$ 路分支 |

第二种方案把标号的绑定提前解决了：进入测试区时，`S1` 到 `S_n` 的代码都已经生成，每条分支入口的标号都在手上，`if t = Vi goto Li` 一生成就是完整的，不需要回填，也不需要事后再走一趟。这正是把测试后置换来的好处——顺序一调，延迟消失。

### case 指令：给代码生成器的信号

第二种方案最后生成的是一串 `if t = Vi goto Li`。为了让代码生成器能认出"这是一组分支测试"，可以引入一种新指令：

```text
case t, V1, L1        等价于    if t = V1 goto L1
```

`case` 指令和条件跳转指令的含义完全一样，区别只在于形态：它是一族标记统一的指令，代码生成器扫描到连续的 `case` 就能把它们当成一个整体来处理，比如合成跳转表。用普通条件跳转，生成器得先做模式识别；用 `case`，等于在中间代码里就把意图标好了。

> **结论**：回填真正有价值的地方，不在于"把标号留空"这个动作，而在于把指向同一个目标的所有跳转组织成一个列表。列表在手上，目标什么时候到都不迟；而一旦顺序安排得好——像 switch 的第二种方案那样，先有各分支的入口、再生成测试——连列表都不必留，标号当场就能填进去。

## 从一条 call 语句到一块活动记录
> 对应块：BLK13 | 覆盖分集：P53-P58 | 块标题（分集名）：《6-11过程调用语句的翻译》

一行 `f(b * c - 1, x + y, x, y)` 摆在面前，编译器要做的事其实是两半：先把四个实参各自算出来，再把这四个值交到 `f` 手里。前半件是表达式翻译的活，后半件看着只是补几条指令，可问题一追问就露出来了——这四个值究竟待在内存的哪个位置？`f` 执行的时候又调用 `g`，`g` 的活动记录会不会正好压在 `f` 的实参上？`f` 里要用外层过程声明的变量，它顺着什么线索去找？

把这几问接着往下问，过程调用语句的翻译就和运行存储分配接到了一起：先看调用语句本身怎么变成三地址码，再看一次过程执行在内存里占哪块地方，最后看跨过程的名字怎么被定位。

### 过程调用语句变成什么样

#### 文法与代码结构

过程调用语句的文法不长：

```text
S     → call id ( elist )
elist → elist , E
elist → E
```

`call` 是过程调用的关键字，`id` 是过程名，括号里那一串由 `elist` 负责生成实参表达式列表。`elist` 写成左递归，参数就从左到右一个一个归约进来，写在前面的实参先入队——这一点到下面用队列时会直接决定 `param` 指令的先后。

一条调用语句的代码，主体是这 $n$ 个参数表达式的代码。每个表达式的值存放在对应非终结符 $E_i$ 的 `address` 属性里；表达式代码生成完之后，还要为每个实参补一条 `param` 指令，把那个值认领为第几个实参，最后才是 `call` 本身。

`param` 指令放在哪儿，有两种排法。一种是跟各自的表达式代码混在一起：算完一个实参，立刻发一条 `param`。另一种是把所有 `param` 集中到所有表达式代码之后，让求值和传参分成清清楚楚的两段。后一种排法要多一样东西：一个队列，把每个表达式的 `address` 先存下来；等所有表达式都算完，再一边清空队列、一边把 `param` 指令序列发出去。

#### 用队列攒住每个实参的地址

按这套集中排法写翻译方案，三个语义动作就够了：

| 产生式 | 语义动作 |
| :--- | :--- |
| `elist → E` | 把队列初始化为只含 `E.address` 一个元素 |
| `elist → elist , E` | 把新识别出的 `E.address` 追加到左边那个 `elist` 对应队列的末尾 |
| `S → call id ( elist )` | $n \leftarrow 0$；对队列中每个 $t$ 发 `param t`，每发一条 $n \leftarrow n+1$；最后发 `call id.address, n` |

第一条动作是队列的诞生：整个参数列表里第一个被归约的表达式，独占一个只含它自己的队列。第二条动作是队列的生长：每归约出一个更大的 `elist`，就把新表达式的地址挂到队尾。队首始终是最先写的那个实参，所以队列的顺序天然就是书写的顺序，不用再排一次。

第三条动作发生在整个右部都识别完、归约成 $S$ 的时候。$n$ 从 0 起算，每发一条 `param` 就加一，最后 `call` 指令带上过程入口 `id.address` 和实参个数 $n$。这里 $n$ 不是预先数出来的，而是发一条数一条——队列里有多少个地址，就发多少条 `param`，两者自然对得上。

#### 走一遍 f(b * c - 1, x + y, x, y)

过程名是 $f$，它带四个参数，每个参数都是一个表达式。

第一个实参 `b * c - 1` 要两条三地址码，因为一条三地址码只放得下一个运算符：

```text
T1 = b * c
T2 = T1 - 1
```

$T_2$ 就是这个表达式的值，进队列。第二个实参 `x + y` 一条就够，$T_3 = x + y$，$T_3$ 进队列。第三、第四个实参都是光秃秃的标识符，值本来就在 `x`、`y` 里，不用再造临时变量，直接把 `x`、`y` 挂到队尾。

队列的变化是这样的：

```text
算完 b * c - 1     Q = [ T2 ]
算完 x + y         Q = [ T2, T3 ]
算完 x             Q = [ T2, T3, x ]
算完 y             Q = [ T2, T3, x, y ]
```

四个地址齐了，清空队列，依次发出四条 `param`，最后一条 `call`：

```text
param T2
param T3
param x
param y
call f, 4
```

`param T2` 对应第一个实参，`param T3` 对应第二个，`param x`、`param y` 对应后两个，顺序与书写一致。这里有个容易忽略的地方：`E.address` 不一定非得是新造的临时变量。`b * c - 1` 的值没有现成的名字，才要借 $T_2$；`x` 这种标识符表达式，地址属性就是它自己的名字，所以 `param x` 直接把变量当实参传，省掉一次拷贝。

### 运行存储分配：什么时候把地址定下来

编译器在工作过程中，必须为源程序里出现的数据对象分配运行时的存储空间。这些对象的大小并不是都能在编译时算出来的，于是分配策略先按一条线分开：大小能不能在编译时刻定下来。

对于编译时刻就能确定大小的数据对象，编译时刻就把存储空间分好，这叫静态存储分配。定不了的就走动态存储分配，动态数组是最典型的例子——它的上下界可能来自运行时的输入，编译时根本不知道要开多大——编译的时候只产生各种必要的信息，真正的存储空间留到运行时刻再分配。

动态存储分配又分为两种：栈式存储分配和堆式存储分配。

> **定义**：这里所说的静态和动态，分别相对于编译时刻和运行时刻，说的是"什么时候把大小定下来、什么时候把空间划出来"，不是指变量活多久。

#### 内存里的几个区

生成的目标代码有多大，编译时刻就已经确定，所以它能放在静态确定的区域，也就是静态代码区。静态代码区通常位于存储的低端。编译时刻就能确定大小的数据，放在紧挨着的静态数据区。

为了把运行时刻的空间利用率做到最大，剩下的两个区——堆和栈——被放在剩余地址空间相对的两端。这两个区都是动态的，大小随程序的运行而变化，各自从一端向中间伸缩，谁也不必预先给对方留出地盘。

```text
低地址
+--------------------------+
|         静态代码区       |  目标代码，编译时刻大小已定
+--------------------------+
|         静态数据区       |  编译时刻能定大小的数据
+--------------------------+
|                          |
|             堆           |
|                          |
|           ......         |
|                          |
|             栈           |
|                          |
+--------------------------+
高地址
```

读这张图只要抓住一点：上面两块在编译时刻就固定下来，下面两块是活的，堆和栈分居剩余空间的两端，中间那片空白正是它们还没用掉的部分。

栈里存放的是一种称为活动记录的数据结构：过程调用时生成并进栈，过程返回时出栈。堆管的则是另一类对象——很多程序设计语言允许程序员通过程序控制人工分配和回收，C 语言里的 `malloc` 和 `free` 就是，这些对象具有长生命周期，不受某一次过程调用的约束，所以不能跟着活动记录一起弹掉。

#### 活动记录装了什么

使用过程、函数或者方法作为用户自定义动作单元的语言，其编译器通常以过程为单位分配存储空间，这里把过程、函数和方法统称为过程。

过程体的每次执行，称为该过程的一个活动。过程每执行一次，就要为它分配一块连续的存储区，用来管理这一次执行所需要的全部信息，这块连续的存储区域就称为活动记录。

不同语言的活动记录内容不完全一样，先看一般形式：

| 字段 | 装的是 |
| :--- | :--- |
| 实参字段 | 调用过程传递给被调用过程的参数 |
| 返回值字段 | 被调用过程返回给调用过程的值 |
| 控制链 | 一个指针，指向调用者的活动记录 |
| 访问链 | 用来访问存放在其他活动记录中的非局部数据 |
| 局部数据字段 | 过程本身声明的一些局部数据 |
| 临时变量区 | 过程执行过程中产生的变量，比如表达式求值时生成的临时变量 |

六个字段里，头两个管值的传递，最后两个是过程自己的家当，中间两条链最容易混。控制链和访问链长得一模一样，都是指针，可指向的东西完全不同：控制链指向"谁调我"，是返回时恢复现场的路；访问链指向"我声明在谁里面"，是找外层数据的路。后面讲调用序列和嵌套过程时会反复用到这个区别。

### 静态存储分配

静态存储分配做的事情很干脆：编译器为每个过程确定它的活动记录在目标程序中的位置。位置一定，过程中每个名字的存储位置就定了，这些名字的存储地址可以直接编译到目标代码里；过程每次执行，它的名字都绑定到同样的存储单元。

代价是语言必须收得很紧，三条要求缺一不可：

| 条件 | 原因 |
| :--- | :--- |
| 数组的上下界必须是常数 | 上下界不是常数，编译时刻就确定不了数组的大小 |
| 不容许过程的递归调用 | 递归时同一过程可能有若干个活动同时处于活跃状态，编译时刻无法确定会有几个，也就不知道该准备多少块活动记录 |
| 不容许动态建立数据实体 | 没有运行时的存储分配机制，运行中临时冒出来的对象没地方安置 |

满足这些条件的语言有 BASIC 和 FORTRAN 等。常用的静态存储分配方法主要有两种：顺序分配法和层次分配法。

#### 顺序分配法

先摆一个例子。一个程序声明了六个过程，编号 1 到 6，各自需要的存储单元数是：1 号 22 个，2 号 15 个，3 号 18 个，4 号 17 个，5 号 23 个，6 号 10 个。它们的调用关系是：1 号调用 2 号和 3 号，2 号调用 4 号和 6 号，3 号调用 6 号和 5 号。

```text
              1
            /   \
           2     3
          / \   / \
         4   6 6   5
```

图上箭头方向就是调用方向。4、5、6 落在最底下，它们谁也不调用。

顺序分配法的基本思想是：按过程出现的先后顺序逐段分配存储空间，各过程的活动记录占用互不相交的存储空间。

| 过程 | 所需单元 | 分配区间 |
| :--- | :--- | :--- |
| 1 | 22 | 0 ~ 21 |
| 2 | 15 | 22 ~ 36 |
| 3 | 18 | 37 ~ 54 |
| 4 | 17 | 55 ~ 71 |
| 5 | 23 | 72 ~ 94 |
| 6 | 10 | 95 ~ 104 |

从 0 号单元一直铺到 104 号，这个程序一共需要 105 个存储单元。为什么是 105？把六个数加起来：$22+15+18+17+23+10=105$。

顺序分配法处理上非常简单，一个挨一个往下摆就行。但它对内存空间的使用不够经济合理——105 个单元里，有些单元永远不会在同一次运行中同时派上用场，却各自占了一份。

#### 层次分配法

能不能用更少的存储空间？回到调用关系上看：4、5、6 这三个过程之间互相不存在调用关系，也就是说它们不可能同时处于活跃状态，那么它们完全可以共享一块存储区域。

层次分配法的思路正是这样：通过对过程间的调用关系进行分析，凡属无相互调用关系的并列过程，尽量使其局部数据共享存储空间。

这里有个前提撑着——不容许过程间的递归调用，所以这个调用关系图里不会存在环。无环，才可以采取从下到上的顺序，一层一层为各层中的过程分配存储空间。

最底下这一层是 4、5、6，互相不调用，从所划分区域的同一个起点开始分配，假设就用相对地址 0 号单元：过程 4 拿 0 号到 16 号，17 个单元；过程 6 拿 0 号到 9 号，10 个单元；过程 5 拿 0 号到 22 号，23 个单元。三块重叠着放，因为它们不会同时活着。

第二层有两个过程。过程 2 调用过程 4 和过程 6，而过程 4 已经占用了 0 号到 16 号，所以过程 2 只能从 17 号单元开始，拿 17 号到 31 号，15 个单元。这样就能保证过程 2 分别调用过程 4 和过程 6 的时候，不会相互破坏对方数据区里的内容。同样的道理，过程 3 调用过程 5 和过程 6，过程 5 已经占用了 0 号到 22 号，于是过程 3 从 23 号单元开始，拿 23 号到 40 号，18 个单元。

最后是过程 1，它调用过程 2 和过程 3，而过程 3 已经占到 40 号，所以从 41 号开始为它分配，拿 41 号到 62 号，22 个单元。

| 层次 | 过程 | 分配区间 | 起点是怎么定出来的 |
| :--- | :--- | :--- | :--- |
| 底层 | 4 | 0 ~ 16 | 与同层过程共用起点 0 |
| 底层 | 6 | 0 ~ 9 | 同上 |
| 底层 | 5 | 0 ~ 22 | 同上 |
| 第二层 | 2 | 17 ~ 31 | 被它调用的 4 占到 16 号 |
| 第二层 | 3 | 23 ~ 40 | 被它调用的 5 占到 22 号 |
| 第一层 | 1 | 41 ~ 62 | 被它调用的 3 占到 40 号 |

整个程序一共需要 63 个存储单元，同样的调用关系，顺序分配法要 105 个。

> **提示**：63 不是凑出来的数。最长的一条调用链是 1 → 3 → 5，三个过程所需单元之和正好是 $22+18+23=63$，与总量一模一样。这条链上的三个活动必须同时存在，一块也省不掉，所以 63 同时也是下界；链外的过程（2、4、6）都找到了可以共用的空间，没有一个额外占地方。顺序分配的 105 则是六个过程大小直接求和，差了整整 42 个单元。

#### 用矩阵记住谁调用谁

具体实现层次分配法的时候，如果程序声明了 $n$ 个过程，就建立一个 $n \times n$ 的过程调用关系矩阵 $B$：$B[i,j]=1$ 表示第 $i$ 个过程调用第 $j$ 个过程，$B[i,j]=0$ 表示不调用。

刚才那个例子的矩阵长这样：

```text
        1  2  3  4  5  6
   1 [  0  1  1  0  0  0 ]
   2 [  0  0  0  1  0  1 ]
   3 [  0  0  0  0  1  1 ]
   4 [  0  0  0  0  0  0 ]
   5 [  0  0  0  0  0  0 ]
   6 [  0  0  0  0  0  0 ]
```

过程 1 调用 2 和 3，所以第一行只有第二、第三个元素是 1，其余全 0；过程 2 调用 4 和 6，所以第二行只有第四、第六个元素是 1；过程 3 调用 6 和 5，第三行的第五、第六个元素是 1；4、5、6 不调用任何过程，这三行对应的元素全是 0。

除了矩阵，还要再建一个长度为 $n$ 的数组，用来存放各个过程所需要的内存单元数量。两样东西配齐，从下往上分层、每层找共用起点就有据可依了。

具体算法步骤这里不铺开，把两样东西的分工记住就够了：矩阵管"谁调用谁"，数组管"要多大"，剩下的无非是照着调用关系一层一层往上算。

这里留了一道习题：假如再加一个 7 号过程，它需要 80 个存储单元，1 号过程调用 7 号过程，7 号过程又调用 5 号过程，这时候应该怎么分配存储空间？解在文末。

### 栈式存储分配

有些语言使用过程、函数或方法作为用户自定义动作的单元，几乎所有针对这类语言的编译器，都把它们的至少一部分运行时刻存储以栈的形式进行管理，称为栈式存储分配。

规矩只有两条：当一个过程被调用，该过程的活动记录被压入栈中；当过程结束，该过程的活动记录被弹出。一压一弹，带来两个好处。一是活跃时段不交叠的多个过程调用之间可以共享空间——弹出之后腾出来的位置，下一次调用正好接着用。二是允许按这样一种方式为一个过程编译代码：它的变量的相对地址总是固定的，和过程调用序列无关。

第二条要绕一下才看得清。同一个过程可能在程序的不同位置被调用，调用它的语句各不相同，可它的代码只编一份。既然每次活动记录落在栈里的位置都不一样，代码凭什么找到自己的数据？凭的是相对偏移——活动记录内部各项的排布是固定的，代码里写的都是"相对本记录某个基准偏移多少"，基准由运行时的指针给出。所以调用序列怎么变，过程代码都不用重编。

#### 活动树

要把"栈里到底有什么"说清楚，先引入一个概念：活动树。

活动树是用来描述程序运行期间控制进入和离开各个活动的情况的树。树中每个结点对应一个活动，根结点是启动程序执行的 `main` 过程的活动。在表示过程 $p$ 的某个活动的结点上，它的子结点对应于被 $p$ 这次活动调用的各个过程的活动，按照这些活动被调用的顺序自左向右显示。还有一个必须成立的约束：一个子结点必须在它右兄弟结点的活动开始之前结束。

> **结论**：活动树把一次运行的时间顺序摊成了从左到右，而同一时刻活着的那些活动，恰好是树上一条从根往下的路径。

#### 快排的活动树与栈的进出

看一个快速排序程序的概要。程序首先把 9 个整数读入数组 $a$，然后调用递归的快速排序算法对这 9 个整数排序。主函数 `main` 先调用 `readArray` 读入 9 个整数，再设置上下限的值，接下来在整个数组上调用 `quicksort`。

`quicksort` 里，当第二个参数大于第一个参数时，先调用 `partition`。`partition` 选择一个分割值 $v$ 来划分 $a[m \dots n]$，使得位置 $p$ 之前的元素都小于 $v$，位置 $p$ 的元素等于 $v$，位置 $p$ 之后的元素都大于 $v$，函数返回位置 $p$。接着 `quicksort` 对这两个子数组分别递归调用自己。

某次执行可能得到的活动树如下，为简单起见用过程名的首字母代表过程：$m$ 是 `main`，$r$ 是 `readArray`，$q$ 是 `quicksort`，$p$ 是 `partition`。

```text
m
├── r
└── q(1,9)
    ├── p(1,9)
    ├── q(1,3)
    │   ├── p(1,3)
    │   ├── q(1,0)
    │   └── q(2,3)
    └── q(5,9)
```

过程 $m$ 调用过程 $r$；从 $r$ 返回以后，调用 $q(1,9)$。$q(1,9)$ 里先调用 $p(1,9)$，这次执行返回位置 4，于是 $a[1]$ 到 $a[3]$ 存放的都是小于 $a[4]$ 的元素，$a[5]$ 到 $a[9]$ 存放的都是大于 $a[4]$ 的元素。接下来递归调用 $q(1,3)$ 和 $q(5,9)$。$q(1,3)$ 里调用 $p(1,3)$，这次执行返回位置 1，于是再递归调用 $q(1,0)$ 和 $q(2,3)$，如此执行下去。

$q(1,0)$ 在树上是叶子，这不是省略：它的第二个参数 0 不比第一个参数 1 大，进去什么也不做就返回，自然不会再有子结点。

现在跟着执行看控制栈。程序执行从 $m$ 的一次活动开始，这时控制栈里只有 $m$ 的活动记录。

$m$ 调用 $r$，$r$ 的活动记录进栈；控制从 $r$ 返回时，$r$ 的活动记录出栈。

$m$ 又调用 $q(1,9)$，$q(1,9)$ 的活动记录进栈。注意这里：曾经被 $r$ 占用的那段存储空间，现在被 $q(1,9)$ 复用了。

$q(1,9)$ 调用 $p(1,9)$，$p(1,9)$ 进栈；控制从 $p(1,9)$ 返回，它出栈。

$q(1,9)$ 接着调用 $q(1,3)$，$q(1,3)$ 进栈。这时会发现：一个过程是递归的时候，常常会有该过程的多个活动记录同时出现在栈中——$q(1,9)$ 和 $q(1,3)$ 此刻就并排躺在栈里。

$q(1,3)$ 调用 $p(1,3)$，进栈；返回，出栈。$q(1,3)$ 调用 $q(1,0)$，进栈；返回，出栈。$q(1,3)$ 再调用 $q(2,3)$，$q(2,3)$ 进栈——这一刻栈的样子是：

```text
        +------------------------+
        |  m 的活动记录          |  ← 根的活动记录，位于栈底
        +------------------------+
        |  q(1,9) 的活动记录     |
        +------------------------+
        |  q(1,3) 的活动记录     |
        +------------------------+
        |  q(2,3) 的活动记录     |  ← 程序控制所在，位于栈顶
        +------------------------+
```

（按惯例，栈底画在上方、栈顶画在下方。）

活动树上还会用三种线标状态：蓝线指向已经执行完毕的活动，红线指向处于活跃状态的活动，黑线指向尚未执行的活动。红线串起来的那条路，正好是上面这四块记录。

> **结论**：每个活跃的活动都有一份位于控制栈中的活动记录；栈中全部活动记录的序列，恰好对应于活动树中从根结点到达当前控制所在结点的路径。根的活动记录在栈底，当前控制所在的活动记录在栈顶，栈有多深，就是这条路径有多长。

#### 活动记录内部的摆放

地址在栈里是从上到下逐渐加大的，所以按惯例把栈底画在上方、栈顶画在下方。这一部分是调用者的活动记录，紧接着的那部分是被调用者的活动记录。

摆放顺序有三条讲究。

在调用者和被调用者之间传递的值，包括参数和返回值，一般放在被调用者活动记录的开始位置，这样它们能尽可能地靠近调用者的活动记录。固定长度的项，包括控制链、访问链和机器状态字等，通常放在中间。在早期不知道大小的项放在活动记录的尾部——大部分局部数据的长度是固定的，但有些局部数据要到运行时刻才能知道长度，最常见的例子就是动态数组。

```text
        +------------------------------+
        |  调用者的活动记录            |
        +==============================+
        |  参数 / 返回值               |  ← 紧邻调用者，传递的值放最前
        +------------------------------+
        |  控制链、访问链、机器状态字  |  ← 长度固定的项放中间
        +------------------------------+
        |  局部数据                    |  ← top_sp 指向这里
        +------------------------------+
        |  长度待定的数据（动态数组）  |  ← 运行时刻才知道多大，放尾部
        +------------------------------+
```

还有一处容易想岔：栈顶指针寄存器 `top_sp` 并不指向真正的栈顶，它指向活动记录中局部数据开始的位置，并以这个位置作为基地址。所以参数和返回值其实落在 `top_sp` 的负方向一侧，靠负偏移就能取到——这也解释了为什么"返回值的相对位置"在返回之后仍然算得出来。

### 调用序列和返回序列

过程调用和过程返回都需要执行一些代码，用来管理活动记录栈、保存或恢复机器状态。

> **定义**：实现过程调用的代码段称为调用序列，它为一个活动记录在栈中分配空间，并在这个记录的字段里填写信息。实现过程返回的代码段称为返回序列，它恢复机器状态，使得调用过程能够在调用结束之后继续执行。

这两段代码通常不是由一方单独完成的，调用序列里的代码被分割到调用过程和被调用过程两边，返回序列也是如此。

#### 调用者与被调用者各干哪一半

调用者先动手，做四件事：

1. 计算实际参数的值，并把它放在被调用者活动记录中的指定位置，也就是参数字段；
2. 把返回地址，也就是程序计数器的值，存放到被调用者的机器状态字段中；
3. 把原来的 `top_sp` 值存放到被调用者的控制链中，这样被调用者的控制链就指向调用者的活动记录；
4. 增加 `top_sp` 的值，使它指向被调用者的局部数据开始的位置。

接着换被调用者：保存寄存器的值和其它状态信息，然后初始化局部数据，开始执行。到这里，调用序列结束。

返回的时候倒过来。被调用者先计算好返回值，把它放到与参数相邻的位置；然后用控制链和机器状态字段中的信息，恢复 `top_sp` 和其它寄存器的值；最后跳转到调用者放置在机器状态字段中的返回地址。

这里有一个看似矛盾的地方：`top_sp` 的值已经被减小，退回到调用者的记录上了，调用者还怎么拿到返回值？靠相对位置。调用者知道这个返回值相对于当前 `top_sp` 值的偏移，按偏移去取就行，不需要任何额外的传递。

把两边填的字段对上，分工一目了然：

```text
        +----------------------------+
        |  调用者的活动记录          |
        +============================+
        |  实参                      |  ← 调用者填写
        |  返回值                    |  ← 被调用者填写，紧挨着参数
        |  机器状态字（含返回地址）  |  ← 调用者填返回地址，被调用者填其余状态
        |  控制链（旧的 top_sp）     |  ← 调用者填写，指向调用者的记录
        |  ...                       |
        +----------------------------+
```

| 项目 | 调用者 | 被调用者 |
| :--- | :--- | :--- |
| 参数字段 | 填写 | — |
| 控制链 | 填写 | — |
| 返回地址（程序计数器的值） | 填写 | — |
| 返回值 | — | 填写 |
| 其它机器状态字 | — | 填写 |
| `top_sp` | 负责更新（增加） | 负责恢复 |

一句话概括：调用者管"把入口铺好"，被调用者管"把现场收拾干净并交回结果"。

#### 变长数据为什么也往栈上放

在现代程序设计语言中，编译时刻不能确定大小的对象通常被分配在堆区。但如果它们是过程的局部对象，也可以分配在运行时刻栈中。尽量把对象放在栈区的原因很实际：可以避免对空间进行垃圾回收，也就减少了相应的开销。

当然不是想放就能放。只有当一个数据对象局部于某个过程，并且此过程结束时它变得不可访问，才可以利用栈为这个对象分配空间——过程一走，这块空间就能随着活动记录一起被覆盖，栈的规矩才不被破坏。

变长数据最常见的例子还是动态数组。常用策略是这样：过程 $p$ 里包含了三个数组，它们的大小在编译时刻都不能确定。尽管这些数组的存储出现在栈中，它们并不是 $p$ 的活动记录的一部分——$p$ 的活动记录里只存放了指向这些数组开始位置的三个指针。$p$ 执行的时候，这些指针的位置相对于栈顶指针的偏移量是已知的，因此目标代码可以通过这些指针来访问数组元素。

```text
（自上而下就是这一段栈里的实际顺序）

p 的活动记录
    记录里只放三个指针，分别指向下面三个数组的起始位置
数组 1（长度待定）
数组 2
数组 3
q 的活动记录
    记录里只放一个指针，指向 q 自己的变长数组
q 的变长数组
```

读图时看两层"之外"：数组在 $p$ 的记录之外，$q$ 的活动记录又在 $p$ 的数组之外，而 $q$ 自己的变长数组同样在 $q$ 的记录之外。被过程 $p$ 调用的过程 $q$，它的活动记录就分配在 $p$ 的数组之后——记录里只放指针，真正的大块数据都挂在记录外面，长度怎么变都不影响记录的固定布局。

### 非局部数据的访问

一个过程里，除了可以使用过程自身定义的局部数据，还可以使用过程外定义的非局部数据，比如全局数据。程序运行的时候，这些在过程外定义的非局部数据是怎么找到的？答案分两种情况，而这两种情况的难度差得很远。

分界线是语言允不允许过程嵌套声明。支持过程嵌套声明的语言，可以在一个过程中声明另一个过程，Pascal 就是；不支持过程嵌套声明的语言，不可以再在一个过程中声明另一个过程，C 就是。

#### 两种语言，两种难度

先看支持嵌套声明的 Pascal。一个用 Pascal 写的快速排序程序概要里，`sort` 本身就是一个过程，它嵌套声明了三个过程：`readarray`、`exchange`、`quicksort`；第三个过程 `quicksort` 里，又嵌套声明了函数 `partition`。函数也是过程，只不过它是带返回值的过程。

按静态作用域原则，一个过程除了自身定义的局部数据和全局定义的数据，还可以使用外围过程中声明的对象。`sort` 里声明的这几个过程——`readarray`、`exchange`、`quicksort`，以及再往深一层的 `partition`——都可以使用 `sort` 中定义的数据，比如数组 $a$ 和变量 $x$。而 `partition` 因为在 `quicksort` 中声明，还能用 `quicksort` 中声明的数据 $v$。

再看不支持嵌套声明的 C。用 C 写的快速排序程序概要里声明了四个过程，这四个过程之间不存在相互嵌套的声明。于是过程中使用的数据只有两种来源：要么是自身定义的局部数据，要么是在所有过程之外定义的全局数据。

这种情况下，变量的存储分配和访问都比较简单。过程中使用的非局部数据都是全局变量，它们被分配在静态区，用静态确定的地址来访问；其它变量一定是栈顶活动的局部变量，可以通过运行时刻栈的 `top_sp` 指针来访问。

"栈顶活动的局部变量"这句要理解准：不是"某个过程的变量"，而是"当前正在执行的那一次活动的变量"。栈顶活动只有一个，地址自然唯一确定，不需要任何链。

#### 嵌套深度与访问链

支持嵌套声明的语言就麻烦了：一个过程能看见的数据，取决于它在词法上被写在哪一层，而运行时栈里同名过程可能同时有多份活动。得有两样东西把"词法上的层"和"运行时的记录"对上，一个是嵌套深度，一个是访问链。

> **定义**：不内嵌在任何其他过程中的过程，其嵌套深度为 1。如果一个过程 $p$ 在一个嵌套深度为 $i$ 的过程中定义，那么 $p$ 的嵌套深度为 $i+1$。变量的嵌套深度就是它所在过程的嵌套深度。

拿刚才那个 Pascal 程序对一遍：唯一一个嵌套深度为 1 的过程是最外层的 `sort`；`readarray`、`exchange`、`quicksort` 是在深度为 1 的 `sort` 中直接定义的，深度为 2；`partition` 是在深度为 2 的 `quicksort` 中直接定义的，深度为 3。

深度只是个数，运行时还得有一根实实在在的指针把层连起来。按静态作用域原则，只要过程 $B$ 的声明嵌套在过程 $A$ 的声明中，过程 $B$ 就可以访问过程 $A$ 中声明的对象。于是可以在相互嵌套的过程的活动记录之间建立一种称为访问链的指针，使得内嵌的过程可以访问外层过程中声明的对象。

具体规则一句话：如果过程 $B$ 在源代码中直接嵌套在过程 $A$ 中，也就是说 $B$ 的嵌套深度比 $A$ 的嵌套深度多 1，那么 $B$ 的任何活动中的访问链都指向最近的 $A$ 的活动。

"最近的"这个词是这条规则的分量所在。$A$ 在一次运行中可能有多个活动同时存在（比如递归），$B$ 的这次活动该连哪一个？连当前调用链上离它最近的那一个，也就是真正把它这条调用路径撑起来的那个 $A$ 的活动。

#### 沿访问链走一遍快排

还是这个 Pascal 快排程序。用过程名的首字母代表过程：$S$ 是 `sort`，$R$ 是 `readarray`，$E$ 是 `exchange`，$Q$ 是 `quicksort`，$P$ 是 `partition`。某次执行可能得到的活动树是：

```text
S                   深度 1
├── R               深度 2，访问链 → S
└── Q(1,9)          深度 2，访问链 → S
    ├── P(1,9)      深度 3，访问链 → Q(1,9)
    │   └── E       深度 2，访问链 → S
    ├── Q(1,3)      深度 2，访问链 → S
    │   ├── P(1,3)  深度 3，访问链 → Q(1,3)
    │   │   └── E   深度 2，访问链 → S
    │   └── ...
    └── Q(5,9)
```

程序执行从 $S$ 的一次活动开始，$S$ 的活动记录进栈。$S$ 调用 $R$，$R$ 进栈；$R$ 在原程序中是在 $S$ 中直接声明的，所以 $R$ 的访问链指向 $S$ 的活动记录，$R$ 就能沿着它访问外围过程 $S$ 中声明的数据对象。控制从 $R$ 返回，$R$ 的活动记录出栈。

$S$ 接着调用 $Q(1,9)$，$Q(1,9)$ 进栈。$Q$ 也是在 $S$ 中直接声明的，访问链指向 $S$ 的活动记录。$Q(1,9)$ 调用 $P(1,9)$，$P(1,9)$ 进栈；$P$ 在源程序中直接在 $Q$ 中声明，所以 $P(1,9)$ 的访问链指向它的外围过程 $Q$ 的活动记录——顺着这条链，$P(1,9)$ 能访问 $Q$ 和 $S$ 两层声明的数据。

接下来 $P(1,9)$ 调用 $E$，$E$ 进栈。这里是最值得盯住的一步：$E$ 在源程序中是在 $S$ 中直接声明的，所以 $E$ 的访问链指向 $S$ 的活动记录，而不是指向它的调用者 $P$。

> **易错点**：访问链跟着声明走，不跟着调用走。$E$ 是被 $P$ 调用的，可 $E$ 并不声明在 $P$ 里，它的访问链就越过 $P$ 直接指向 $S$。谁调用谁只决定控制链，谁声明谁才决定访问链。

控制从 $E$ 返回，$E$ 出栈；从 $P(1,9)$ 返回，$P(1,9)$ 出栈。

$Q(1,9)$ 递归调用 $Q(1,3)$，$Q(1,3)$ 进栈。它和 $Q(1,9)$ 对应同一个过程，外围过程也是同一个，所以访问链同样指向 $S$ 的活动记录，两条链指向同一个地方。$Q(1,3)$ 进一步调用 $P(1,3)$，$P(1,3)$ 的访问链指向 $Q(1,3)$。$P(1,3)$ 调用 $E$，$E$ 的访问链依旧指向 $S$。

一路走下来，规律很清楚：访问链只由声明关系决定，和谁调用它无关。同一个过程的不同活动，访问链指向同一个外层记录；$E$ 无论是被 $P(1,9)$ 调用还是被 $P(1,3)$ 调用，链永远指回 $S$ 的那份活动记录。

#### 访问链怎么建：三种情况

建立访问链的代码属于调用序列的一部分，它是在调用发生的那一刻算出来的。设调用者 $X$ 的嵌套深度为 $n_x$，被调用者 $Y$ 的嵌套深度为 $n_y$，分三种情况。

第一种，$n_x < n_y$，外层过程调用内层过程。

这时被调用者 $Y$ 一定是直接在调用者 $X$ 中定义的。$S$ 可以调用 $Q$，$Q$ 可以调用 $P$，但 $S$ 不能直接调用 $P$——$P$ 声明在 $Q$ 里，按静态作用域原则，$P$ 的作用域在 $Q$ 之内，只有 $Q$ 区域范围内的语句才可以调用 $P$。所以外层调内层时，嵌套深度只能相差 1。

既然 $Y$ 直接嵌套在 $X$ 里，$Y$ 的活动记录中的访问链直接指向 $X$ 的活动记录就行：把调用者 $X$ 的活动记录地址填进 $Y$ 的访问链字段。

第二种，$n_x = n_y$，调用者与被调用者深度相等。

这就是递归调用，比如 $Q$ 调用 $Q$。调用者和被调用者对应的是同一个过程，它们的外围过程也是同一个，访问链指向同一个活动记录，直接复制即可——把调用者 $Q$ 的访问链复制给被调用者 $Q$ 的访问链。

第三种，$n_x > n_y$，内层过程调用外层过程。

比如 $P$ 调用 $E$。这时调用过程 $X$ 必定嵌套在某个过程 $Z$ 中，而 $Z$ 中直接定义了被调用过程 $Y$：$P$ 嵌套在 $S$ 中，$S$ 中直接定义了 $E$。

怎么定 $E$ 的访问链？$E$ 和 $P$ 的嵌套深度相差 1，从 $P$ 的记录出发沿着访问链走一步，到达的是与 $E$ 处于同一层的过程 $Q$ 的活动记录；从 $Q$ 再顺着它的访问链走一步，就到了定义了 $Q$、同时也定义了 $E$ 的过程 $S$ 的活动记录。$E$ 的访问链就该指向这里。

一般化：从调用者的活动记录开始，沿着访问链经过 $\Delta + 1$ 步（$\Delta = n_x - n_y$），就找到了离栈顶最近的过程 $Z$ 的活动记录，$Z$ 中声明了被调用者 $Y$，$Y$ 的访问链必须指向 $Z$ 的这个活动记录。

> **提示**：为什么是 $\Delta+1$ 步而不是 $\Delta$ 步？每条访问链只往上跳一层。从深度 $n_x$ 的调用者出发跳 $\Delta$ 步，落到深度 $n_y$ 的记录上——这一层和被调用者 $Y$ 同层，是 $Y$ 的"邻居"，还不是声明 $Y$ 的地方。再补一步，才落到深度 $n_y-1$ 的 $Z$ 上。所以步数总是差一层再加一。

三种情况合起来看，判断依据只有一个：比较两个过程的嵌套深度。深度小的是外层，深度大的是内层，深度相等的是同一个过程的不同活动。谁调用谁只影响走几步，不影响访问链指向哪一层。

### 本讲提到的题目

六个过程的例子里，再加一个 7 号过程，它需要 80 个存储单元；1 号过程调用 7 号过程，7 号过程又调用 5 号过程。按层次分配法，这时候应该怎样分配存储空间？

解这道题不需要重新分层，只要把新的调用关系塞进原来的层次结构里，从下往上重算一遍。

底层的三个过程没有变化。4、5、6 谁也不调用，仍然从相对地址 0 起共用一块区域：过程 4 占 0 ~ 16，过程 6 占 0 ~ 9，过程 5 占 0 ~ 22。

7 号过程只调用 5 号，它的起点由 5 号决定：5 号已经占到 22 号，所以 7 号从 23 号开始，拿 23 ~ 102，正好 80 个单元。

过程 2 仍然调用 4 和 6，4 占到 16 号，所以 2 号还是从 17 号起，占 17 ~ 31。过程 3 仍然调用 6 和 5，5 占到 22 号，所以 3 号还是从 23 号起，占 23 ~ 40。

这里会出现一块重叠：3 号占 23 ~ 40，7 号占 23 ~ 102，两者的前 18 个单元是同一段地址。这不违反规则——3 和 7 都是被 1 号调用的并列过程，1 号调用 3 号时 7 号还没上场，调用 7 号时 3 号早已返回，两者不可能同时活跃，共用一段地址正合层次分配法的本意。

最后是过程 1。它调用 2、3、7，三个被调用者的终点分别是 31、40、102，取最大的 102，所以 1 号从 103 号开始，占 103 ~ 124，22 个单元。

| 过程 | 所需单元 | 分配区间 |
| :--- | :--- | :--- |
| 1 | 22 | 103 ~ 124 |
| 2 | 15 | 17 ~ 31 |
| 3 | 18 | 23 ~ 40 |
| 4 | 17 | 0 ~ 16 |
| 5 | 23 | 0 ~ 22 |
| 6 | 10 | 0 ~ 9 |
| 7 | 80 | 23 ~ 102 |

> **答案**：整个程序需要 125 个存储单元。

验算一下：加入 7 号之后，最长的一条调用链变成了 1 → 7 → 5，$22+80+23=125$，与总量分毫不差。链上的三块记录必须同时存在，所以 125 也是下界；其余过程都挤进了已有区域，没有再额外占地方。这道题真正想让人看的就是这一点：层次分配法的总量，由最长的那条调用链说了算。
