## AVL 平衡的实现：四种旋转、balance 与 put
> 对应块：BLK49 | 覆盖分集：P188-P190 | 块标题（分集名）：《基础算法-143-avl树-旋转》

上一节课我们把 AVL 树失衡的四种情况数清楚了。但真正动手写代码的时候会发现一个很爽的事实：**最基本的旋转其实只有两种,左旋和右旋**。那四种失衡长得千奇百怪,背后无非是这两种旋转的组合。

所以这节课的任务很明确:先把左旋和右旋写出来,再把左右旋、右左旋拼出来,然后写一个 `balance` 把它们接起来,最后把 `put` 补上。整条链路走通,AVL 的核心骨架就齐了。

这里我们先约定好节点高度和平衡因子的写法,后面到处都要用:

$$h(node)=\max(h(node.left),\,h(node.right))+1$$

$$bf= h(node.left)-h(node.right)$$

$bf$ 落在 $-1,0,1$ 这三个值上就是平衡的,大于 1 或者小于 $-1$ 就是失衡了。

### 右旋：把根旋下去,把左孩子旋上来

右旋我给它起名叫 `rightRotate`。参数和返回值的含义先钉死,这是后面四种旋转共用的套路:

> **定义**:`rightRotate(Node node)` 的参数 `node` 是**要旋转的那个节点**(实际调用时传进来的基本就是失衡节点);返回值是**旋转之后产生的新根节点**。

为什么返回值是新根而不是 void?因为旋转的本质就是"在以这个节点为根的指数里把根旋转下去",右旋就是把它的左子树旋转上来。原来的根往下走了,谁成了新根,谁就得被返回给调用方。左旋 `leftRotate` 的参数和返回值完全是同一套说法,一个样。

#### 只有两个节点时,旋转就是一行赋值

先看最简单的情况,先别管平不平衡,纯粹练手。图里 `○` 表示空节点。

```text
        8                         6
       / \                       / \
      6   ○   ==>               ○   8
     /                             / \
    ○                             ○   ○
```

代码就这么写:

```java
public Node rightRotate(Node node) {
    Node yellow = node.left;   // 拿到左孩子

    yellow.right = node;       // 黄色上位:他的右孩子要变成红色

    return yellow;             // 黄色成了新根
}
```

为了跟图对照,我把三个节点分别叫 red、yellow、green。这纯粹是为了讲课时好指着说,你完全可以换成自己顺手的名字——**怎么好理解怎么取变量名**,别为了跟我一样而将就。

#### 黄色节点还带着右孩子,绿色就得换爹

现在把情况变复杂一点:黄色的节点还有右孩子,就是图里绿色的那个 G。

矛盾立刻就来了。黄色旋转上去之后,它的右孩子会被赋值成红色;而它原来那个绿色的右孩子如果不加处理,就被红色**覆盖掉了**。一个节点白白丢了,这肯定不行。

解决办法是**让绿色重新找个爹**,让它依然存活。那么谁当绿色的爹合适?靠二叉搜索树的特性推一下:

```text
        8                         6
       / \                       / \
      6   C   ==>               A   8
     / \                           / \
    A   G                         G   C
```

绿色的 G 在黄色的右侧,所以 **G 比黄色大**;但绿色连同黄色整个都在 8 的左侧,所以 **G 一定比 8 小**。那还有什么好犹豫的,直接让 G 当红色的左孩子:`node.left = green`。原来的爹是黄色 6,现在新爹是红色 8,同时身份还从右孩子变成了左孩子。

所以补上这一行,代码就完整了:

```java
public Node rightRotate(Node node) {
    Node yellow = node.left;   // 先拿黄色
    Node green = yellow.right;  // 再从黄色身上拿绿色

    yellow.right = node;       // 上位
    node.left = green;         // 换爹

    return yellow;
}
```

读图你就知道,剩下的节点都不用管:8 的右孩子旋转之后没变,6 的左孩子旋转之后也没变,还是 6 的左孩子。**特殊的只有带颜色的这三个——黄的、红的、绿的,把三者安排明白,旋转就完成了。**

#### 三个细节:顺序、空指针、能省的变量

有同学会问,那 `yellow` 和 `green` 这两行取节点的代码,顺序能不能换?不能。必须先 `red.left` 拿到黄色,再 `yellow.right` 拿到绿色,这个顺序是定死的。

再看那两句赋值的顺序。`yellow.right = node`(上位)必须在 `node.left = green`(换爹)**之后**,绝对不能往前挪。为什么?你要是先执行上位,黄色的右孩子当场就被红色顶掉了,等下一行再去 `yellow.right` 取绿色,取得到的已经是红色了——绿色早就没了。

但反过来,换爹这行**可以往前挪**。挪到最前面,写成这样:

```java
public Node rightRotate(Node node) {
    Node yellow = node.left;
    node.left = yellow.right;   // 换爹
    yellow.right = node;        // 上位
    return yellow;
}
```

这时候你会发现 `green` 这个变量其实是可以省掉的,三行就搞定了。我的建议是:**一开始你还是老老实实多写几行,没关系**,先把逻辑写得最清晰,后面再做代码的调整和优化。

最后一个细节,关于空指针。有人问:要不要判断 `yellow` 是不是 `null`?万一取到个 null,`yellow.right` 不就空指针了吗?**不需要,完全不用考虑。** 因为我们现在做的是右旋,既然要右旋,那肯定是左边高;左边都能高出这个高度了,它的左孩子怎么可能为空。所以别再画蛇添足加一个 `if (yellow != null)`。而 `green` 为 null 也没关系——你只不过拿到了一个 null,然后把 null 赋值给将来红色的左孩子,完全没事,不用加非空判断。

### 左旋：完全对称的一次操作

左旋跟右旋是一个对称的操作,理解起来就轻多了,还是那三种颜色:红色是传进来要旋转的节点,黄色是将来作为新根的节点,绿色是要换爹的节点。

```text
        8                         6
       / \                       / \
      A   6   ==>               8   B
         / \                   / \
        G   B                 A   G
```

代码就是把左右全部对调:

```java
public Node leftRotate(Node node) {
    Node yellow = node.right;  // 这回是通过右孩子拿到黄色
    Node green = yellow.left;   // 这回绿色是黄色的左孩子

    yellow.left = node;         // 上位:黄色的左孩子变成红色
    node.right = green;         // 换爹:绿色改挂到红色的右边

    return yellow;
}
```

注意这回**是通过右孩子拿到黄色**,黄色这边**是左孩子**,绿色是 `yellow.left`。绿色原来是黄色的左孩子,旋转之后爹变成红色,身份变成红色的右孩子。最后返回新的根——还是黄色。

### 左右旋与右左旋：把两次基本旋转拼起来

四种旋转的前两种我们都会了,现在看组合的两种。它们解决的是 LR 和 RL 这两种"折线型"失衡。

**左右旋**(我命名为 `leftRightRotate`,解决 LR):先对失衡节点的**左子树左旋**,再对**根节点右旋**。

```text
第 1 步 失衡节点 8,左子树 6,6 的右孩子是 5

        8
       / \
      6   C
     / \
    A   5
       / \
      D   E

第 2 步 先对左子树 6 左旋:红色旋下去,黄色旋上来,绿色换爹

        8
       / \
      5   C
     / \
    A   6
       / \
      D   E

第 3 步 再对根节点 8 右旋

        5
       / \
      A   8
         / \
        6   C
       / \
      D   E
```

看着挺复杂对不对?但你想想,整个过程不就是我刚才写好的两次 `leftRotate` 和 `rightRotate` 吗?左边怎么上位、怎么换爹,右旋代码里全都有了,**一个字的重复代码都不用再写**,直接调就行:

```java
public Node leftRightRotate(Node node) {
    node.left = leftRotate(node.left);   // 左子树左旋,旋转上来的黄色要成为根的左孩子
    return rightRotate(node);            // 根节点右旋
}
```

注意第一步里那句赋值:旋转之后黄色的上来了,那它就应该作为根节点的左孩子。原来根节点的左孩子是红色的,现在得改成黄色的,所以要把 `leftRotate` 的返回值重新赋给 `node.left`,父子关系得改对。第二步右旋完直接 `return`,返回的就是旋转上来的黄色。

**右左旋**(命名为 `rightLeftRotate`,解决 RL)完全镜像:先旋转失衡节点的**右子树**,再左旋失衡节点。

```text
第 1 步 失衡节点 8,右子树 6,6 的左孩子是 5

        8
       / \
      A   6
         / \
        5   C
       / \
      D   E

第 2 步 先对右子树 6 右旋

        8
       / \
      A   5
         / \
        6   C
       / \
      D   E

第 3 步 再对根节点 8 左旋

        5
       / \
      8   C
     / \
    A   6
       / \
      D   E
```

```java
public Node rightLeftRotate(Node node) {
    node.right = rightRotate(node.right);  // 右子树右旋
    return leftRotate(node);               // 失衡节点左旋
}
```

第 2 步为什么要写 `node.right = ...`?因为失衡节点的右孩子原来是红色的,右旋之后要变成黄色的,所以得重新赋个值。第 3 步左旋之后,新的根节点直接 `return` 就好了。

到这里,四种旋转就全齐了:**左旋、右旋**这两种基本的,以及**左右旋、右左旋**这两种组合的。

### 旋转完必须补上高度

四种旋转的代码写完,还有个问题绕不过去:**旋转之后,节点的高度需要更新。**

举个最直观的例子。就拿那颗需要右旋的树来说,红色节点旋转下去了,我问你它的高度变没变?肯定会变。

```text
        8                          6
       / \                        / \
      6   ○          ==>        ○   8
     /                                / \
    ○                                ○   ○

旋转前 h(8) = max(3, 1) + 1 = 4
旋转后 h(8) = max(2, 1) + 1 = 2
```

旋转之前它的高度是左右孩子挑一个最大的再加一,等于 4;旋转下去之后,左右孩子挑一个较大的加一,变成 2。高度实打实地变了,所以旋转成功以后**一定要更新它的高度**。

更新高度的代码我们之前写过,就是 `updateHeight`——找到任何一个节点,他的左右孩子里求一个最大值,加一,就是它更新后的高度。这里不用重头再写一遍,在右旋代码里旋转成功之后直接调用它就好。

#### 只有红色和黄色两个节点的高度会变

那其他节点的高度要不要更新呢?可以告诉大家一个很省事的结论:**不带颜色标记的那些普通节点,还有换爹的绿色节点,旋转前后高度都不会变。** 绿色节点旋转之前高度是 1,旋转之后还是 1。

黄色节点呢?有的同学看着图会想"好像没变啊"——这个例子里旋转之前高度 3,旋转之后还是 3。但实际上,**黄色节点的高度是会变的**。我们换左右旋那个例子看:

```text
第 1 步 旋转之前:6 是一棵高度为 2 的树

        8
       / \
      6   C
     / \
    A   5
       / \
      D   E

第 2 步 6 左旋上去之后:6 变成了高度为 3 的树

        8
       / \
      5   C
     / \
    A   6
       / \
      D   E
```

旋转之前黄色的高度是左右孩子最大值加一,等于 2;旋转上去之后,左右孩子最大值 2 加 1,变成 3。所以黄色的高度也得更新。

> **结论**:**只有红色和黄色这两种角色的节点需要更新高度**,剩下的大家下去自己试验一下,旋转后都不会变。

#### 顺序:先更新下面的红色,再更新上面的黄色

那这两行更新高度的代码顺序能不能调?能不能先更新黄色再更新红色?**注意,不行啊,不行。**

因为旋转之后红色的在下面、黄色的在上面,你得先把下面节点的高度算对了,再拿它去算上面的高度才靠谱。你要是先算上面的,下面还没算对呢,它俩取一个最大值,那肯定得不到正确结果。

```text
   旋转之后的位置关系

        6        ← 先更新它(黄)
       / \
      ○   8      ← 后更新它(红)
```

所以正确的顺序是:**先更新旋转后位置较低的红色节点的高度,再更新旋转后位置较高的黄色节点的高度。** 左旋代码里也一样,直接把这两行拷过去就行,依然是先红后黄。

至于左右旋和右左旋,他俩需不需要额外更新高度?**不需要。** 因为他俩更新高度的操作,已经被包含在调用的 `leftRotate` 和 `rightRotate` 里面了,不用再重复一遍。

至此,四种旋转的代码就彻底实现完毕了。

### balance：先认失衡,再选旋转

四种失衡情况有了,四种旋转代码也有了,下面把它们结合起来,写一个叫 `balance` 的方法:传进来一个节点,你检查它是不是失衡了;失衡就做相应的旋转让它重新平衡,然后返回平衡后的根节点;没失衡就原封不动地返回。

这是一个相当重要的方法,后面 `put` 会直接调它。

#### 从平衡因子分出四个分支

架子怎么搭?先来两个基本判断。

第一,节点是 `null` 的话,没必要往下走任何失衡判断,直接返回 `null`,特殊处理掉就行。

第二,判断失衡的工具我们早就有——就是那个平衡因子。它看的是当前节点左右子树的高度差是不是 $-1,0,1$;如果是这三个值就是平衡的,大于 1 或小于 $-1$ 就是失衡的。既然有现成的 `bf` 函数,直接调它求当前节点的平衡因子。

拿到 `bf` 之后,前面对应的那四种情况就派上用场了。四个分支先这么摆着:

```text
                  balance(node)
                       │
                node == ○ ?
                ／         ＼
             是                否
              │                  │
        return ○        bf = balanceFactor(node)
                                 │
            ┌────────────────────┼────────────────────┐
         bf > 1           -1 ≤ bf ≤ 1           bf < -1
            │                   │                   │
       左子树更高                平衡              右子树更高
            │                   │                   │
      LL 或 LR,左旋再右旋    原样 return node   RL 或 RR,右旋再左旋
```

`bf > 1` 表示左边更高,可能就是 LL 也可能是 LR 这前两种;`bf < -1` 表示右边更高,属于后两种;剩下 `-1 ≤ bf ≤ 1` 的就是平衡的,不需要任何旋转,原样返回当前节点。架子到这儿就打好了。

#### 四种失衡,四种旋转

接下来做细分。`bf > 1` 的时候,左边已经确定了更高,那到底走 LL 还是 LR,**就得看它的左子树**。所以再调一次 `balanceFactor`,这次算的是失衡节点的左子树:

- 左子树的平衡因子**大于 0** → 左子树自己左边更高 → **LL**;
- 左子树的平衡因子**小于 0** → 左子树右边更高 → **LR**。

下面两种同理。`bf < -1` 的时候右边更高,再看它的右子树:右子树的 `bf` **大于 0** → 右子树左边高 → **RL**;**小于 0** → **RR**。

这样四种情况就彻底分开了:

| 失衡类型 | 形状描述 | 判定条件 | 对应旋转 |
| --- | --- | --- | --- |
| LL 左左 | 左边更高,左子树也是左边更高 | `bf > 1 && balanceFactor(node.left) > 0` | `rightRotate(node)` |
| LR 左右 | 左边更高,左子树却是右边更高 | `bf > 1 && balanceFactor(node.left) < 0` | `leftRightRotate(node)` |
| RL 右左 | 右边更高,右子树却是左边更高 | `bf < -1 && balanceFactor(node.right) > 0` | `rightLeftRotate(node)` |
| RR 右右 | 右边更高,右子树也是右边更高 | `bf < -1 && balanceFactor(node.right) < 0` | `leftRotate(node)` |

旋转代码就非常好写了。LL 对照着图右旋一下就完事,返回的就是旋转上去的新根——比如例子里黄色的 3 被旋上去之后,返回 3 这个节点。RR 对称,来一次左旋。最后一种都不用想了,肯定就是 `rightLeftRotate`。

> **提示**:这张表是 `balance` 的全部业务逻辑。真正写代码时把这四个条件按"左高两条、右高两条"分成两两一组,每个条件都写成两个 `balanceFactor` 判断的与运算,连 `else if` 都不用写,靠 `return` 直接短路,谁先命中算谁的。

#### 删除特有的两种情况

到这儿,绝大多数添加和删除操作的失衡都能处理了。但还有两个特殊情况我们没考虑到,而且**它们全部发生在删除节点的时候**。

先看一个当前代码能正确处理的情况。删掉节点 8 之后,树变成这样:

```text
        6
       /
      3
     /
    1
```

失衡节点还是 6,它的左子树高度是 2,右子树高度是 0,高度差超过 1 了。它属于四种里的哪一种?就是**左左**:失衡节点左边更高,并且它的左子树也是左边更高。LL 来一次右旋就能恢复平衡。这是当前代码能涵盖的。

再看一个处理不了的。同样是删 8,树变成这样:

```text
        6
       /
      3
     / \
    1   5
```

失衡的还是 6,左子树高度 2、右子树高度 0,高度差超过 1。但它属于四种里的哪一种?**好像没一个能匹配上。** 失衡节点确实是左边更高,可是它的左子树——你注意看——左右高度差**等于零**。我们判断左子树的时候,只判了大于零和小于零,**根本没有一个等于零的情况啊**。

那这个失衡该怎么解决?其实还是来一次右旋就完事了:黄色的旋上去,红色的旋下来,绿色的换个爹,右旋一下就平衡了。

> **易错点**:删除时多出来的两种情况是——**左子树的平衡因子等于 0,也应该按 LL 处理做一次右旋**(左子树等于零,也就是左子树这边是平衡的,我们要把它视为左左)。对称地,**右子树的平衡因子等于 0,也应该按 RR 处理做一次左旋**。这两个"等于"的条件必须加进去。新增的时候不会出现这个问题,**只有删除才会**。

把这两条并进判定条件里,写法变得非常干净:

```java
public Node balance(Node node) {
    if (node == null) {
        return null;
    }
    int bf = balanceFactor(node);

    // bf > 1:左边更高。左子树的 bf >= 0 归 LL(删除时 bf == 0 也算 LL),< 0 归 LR
    if (bf > 1 && balanceFactor(node.left) >= 0) {
        return rightRotate(node);
    }
    if (bf > 1 && balanceFactor(node.left) < 0) {
        return leftRightRotate(node);
    }

    // bf < -1:右边更高。右子树的 bf > 0 归 RL,<= 0 归 RR(删除时 bf == 0 也算 RR)
    if (bf < -1 && balanceFactor(node.right) > 0) {
        return rightLeftRotate(node);
    }
    if (bf < -1 && balanceFactor(node.right) <= 0) {
        return leftRotate(node);
    }

    return node;
}
```

`>= 0` 和 `<= 0` 里的那个等号,就是专门为删除时那两种特殊情形留的口子。至此 `balance` 方法实现完毕。

### put：新增和更新写在一起

到目前位置 AVL 树里几个核心方法都齐了,接下来实现它的**新增**和**删除**。至于**查询**,我们就不重复实现了——查询不会改变树的平衡,跟之前二叉搜索树的查询完全一模一样。

新增方法还是叫 `put`,接受两个参数,一个是 `key`,一个是 `value`。为了简单起见还是用递归实现,另外写一个专门做递归的方法,叫 `doPut`。

`doPut` 的主要思路就一句话:**找空位,找到空位就创建新节点返回。** 递归方法的返回值类型因此就是这个节点类型;参数除了 `key` 和 `value`,还要多一个——**从哪个节点开始去找空位**,同样是个节点类型。方法一共就三种情况。

#### 递归的三种情况

第一种:**找到空位了**。判断有没有空位特别简单,看传进来的节点已经是 `null` 了,就说明这儿有空位,那就创建一个新的节点对象返回。**刚创建出来的节点,高度就是 1。**

第二种:**查找过程中发现 `key` 在树中已经有了**。判断依据是当前的 `key` 等于当前节点的 `key`。有了就没必要做新增,直接走更新的流程,把当前节点的 `value` 更新成传进来的新 `value`,然后 `return` 这个节点就结束了,后面的代码根本不用执行。**而且更新完全不需要考虑改高度、也不需要重新平衡**——因为前面分析过,更新根本不会影响树的高度,树不会失衡。

第三种:**继续查找**。`key` 小于当前节点的 `key`,就沿着左子树递归向左找;`key` 大于当前节点的 `key`,就沿着右子树递归向右找。小于和等于都写了,那剩下的直接 `else` 肯定就是往右走了,不用再写别的 `if`。

```java
private Node doPut(Node node, int key, Object value) {
    // 情况一:找到空位了,创建新节点返回(新节点高度为 1)
    if (node == null) {
        return new Node(key, value);
    }

    // 情况二:key 已经存在,走更新的逻辑。不用改高度,也不用重新平衡
    if (key == node.key) {
        node.value = value;
        return node;
    }

    // 情况三:继续查找
    if (key < node.key) {
        node.left = doPut(node.left, key, value);   // 向左找,并建立父子关系
    } else {
        node.right = doPut(node.right, key, value);  // 向右找,并建立父子关系
    }

    // 下面这两行是 AVL 相对于二叉搜索树新加的
    updateHeight(node);
    return balance(node);
}
```

不管向左还是向右,只要下一层递归找到了空位,就会返回一个新节点,我们就把它接到当前节点上,把父子关系建起来。但**事情没完**——以前的二叉搜索树代码写到这里就结束了,现在加了节点以后,当前节点的高度需不需要变?需要。所以调 `updateHeight` 更新当前节点的高度。

更关键的是下一步:**当前节点高度一更新,这个节点就有可能失衡了。** 失衡了怎么办?调我们刚写好的 `balance` 去重新平衡。没失衡的话,`balance` 最终返回的就是节点本身;失衡了,返回的就是调整平衡之后的新根节点。所以我们只要直接 `return balance(node)` 就行了。

#### 递归调用把它串起来

`doPut` 在 `put` 里被调用,查找的起点应该是根节点,`key` 和 `value` 都传进去:

```java
private Node root;   // 前面的代码里还没定义根节点,这里补上

public void put(int key, Object value) {
    this.root = doPut(this.root, key, value);
}
```

有个细节别漏了:刚开头的根节点是空的,所以第一次调 `put` 的时候,`doPut` 会在第一个 `if` 上直接成立,返回一个新节点。**这个创建好的新节点必须赋值给根节点**,否则这棵树永远长不出来。

#### 回溯路上逐层更新高度

我们结合图把整个新增流程过一遍,插入 9、5、3 三个节点。

```text
   put(9)             put(5)            put(3)
      9                 9                  5
                      /                 / \
                     5                 3   9
```

第一次插 9:树是空的,`doPut` 拿到的根节点是 `null`,第一个 `if` 成立,创建出节点 9 返回,然后赋值给根节点。

第二次插 5:根节点不为空了,第一个条件不成立;5 跟 9 不相等,继续查找;5 小于 9,所以向左找。9 的左孩子是 `null`,说明有空位,创建出 5 返回,作为 9 的左孩子建立父子关系。接着执行 `updateHeight(9)`:9 在左右孩子里挑一个较大的高度,是 1,加 1,新高度是 2。再执行 `balance(9)`:9 没失衡,因为它左右孩子的高度差是 $1-0=1$,没超过 1,于是原样返回 9。最后把这个返回值再赋给 `root`,相当于没变化。

第三次插 3:查找过程不重复说,它找到 5,发现 5 左边有空位,递归创建出 3 返回,跟 5 建立父子关系。然后当前节点 5 继续往下走,`updateHeight(5)` 把 5 的高度更新成 2,`balance(5)` 检查后没失衡。

但代码到这里还没结束——**5 会返回到上一次递归调用的地方,也就是节点 9**,所以 9 那边也要执行后面这两行:`updateHeight(9)` 把 9 更新成高度 3(左右孩子挑较大的 2,加 1);然后 `balance(9)` 这次真的检出失衡了,因为左右孩子高度差 $2-0=2$,已经超过 1。

它属于哪种失衡?左边更高,而且左孩子这边也是左边更高,**LL**。那就对九做一个右旋,右旋的结果返回的不是 9 了,是黄色的节点 5 上位成了新根。所以 `balance` 返回 5,`doPut` 返回 5,再往上返回到最外层,根节点就从 9 替换成了 5。

```text
   插入 3 后的最终形态

        5
       / \
      3   9
```

大家发现没有,**高度是在递归回去的过程中一点一点更新的**——沿着你来时的路,回去的时候逐层把每个节点的高度算对。这也是为什么 `updateHeight` 必须放在递归调用的后面,而不是前面。

到这里新增方法就分析完了。想做更多实验的同学,可以自己再插几个节点,结合网页图观察它的执行流程。

## AVL 树的删除，顺势开讲红黑树
> 对应块：BLK50 | 覆盖分集：P191-P192 | 块标题（分集名）：《基础算法-146-avl树-remove》

### 删除方法的架子

前面我们把 AVL 树的查询、新增，以及那四种失衡对应的四种旋转都过了一遍。最后还剩一个操作没讲——删除。

删除方法我们先看设计。返回值类型我就选 `void` 吧，相当于简化了一下。之前我们实现二叉搜索树的删除，返回的是被删除节点的那个值；这回先简单点，删完就删完，不考虑把那个值再抛回来。

方法名也换一下，主要是跟 Java 中 Map 的删除保持一致，就叫 `remove`。之前我叫的是 `delete`，之前那个名字没起好。

删除的具体实现我还是准备用递归，递归的代码写起来会稍微看着简单一些。所以我们再提供一个方法用来递归——这个递归方法之前我们也实现过一遍了，它的返回值代表**删剩下的**那个节点，所以返回值类型我们也选择这个节点类型。

```java
public void remove(T k) {
    root = doRemove(root, k);
}
```

对外这个 `remove` 简单得很：删除的起点从 `root` 开始，根据 `k` 找；删完之后剩下的节点我们需要用它更新一下根节点。为什么非要更新？因为删除的过程中树会重新平衡，平衡之后根节点可能就变了。总之你把它的返回值重新给根节点赋个值，这个动作省不掉。

递归内部的架子其实就做这么几件事：

```text
private Node<T> doRemove(Node<T> node, T k)

  ① node == null                     → 没必要删了，直接返回
  ② 没找到 k                         → 看是向左走还是向右走，继续递归
  ③ 找到了 k                         → 四种子情况，分派处理
  ④ 更新"删剩下的节点"的高度
  ⑤ 检查它失衡 → 失衡就在 balance 内部旋转，返回平衡后的新根
```

> **易错点**：第 ③ 步只是"找到"，找到之后还不能急着往上返回，因为第 ④、⑤ 两步是对**删剩下的那个节点**做的。找到了就直接 `return`，高度没人更新、失衡也没人修。

下面逐条看。

### 空节点与没找到

第一种情况最简单：`node == null`，那没必要执行后续的任何操作了，直接返回空。

第二种情况是**没找到** `k`。这一种又分向左和向右找两种：

```java
if (node.k.compareTo(k) < 0) {
    // k 比当前节点小，往左
    node.left = doRemove(node.left, k);
} else if (node.k.compareTo(k) > 0) {
    // k 比当前节点大，往右，逻辑跟上面完全类似
    node.right = doRemove(node.right, k);
}
```

大家注意，递归调完 `doRemove` 之后，它返回的是"删剩下的那个节点"，那我们就得拿它来更新一下当前节点的孩子。左孩子那一路就更新 `node.left`，右孩子那一路就更新 `node.right`。

> **提示**：这里的写法是"传参进去 + 接返回值出来"成对的。只传进去不接返回值，等于白递归——子树的根换了，上面还指着旧节点，树就断了。

### 找到了：四种子情况

再写个 `else`，就相当于我们待删除的 `k` 跟当前节点的 `k` 已经相等了，这就是第三种情况，找到了。

找到以后做的事，前面我们说过是比较复杂的，因为它又分成了几种子情况。判断条件是这么排的：

| 子情况 | 判断条件 | 删剩下的是谁 | 能不能立刻 return |
| --- | --- | --- | --- |
| 一 | 左孩子为空 **并且** 右孩子为空 | 空 | 能，直接 `return null` |
| 二 | 左孩子为空（只有右孩子） | 右孩子 | 不能 |
| 三 | 右孩子为空（只有左孩子） | 左孩子 | 不能 |
| 四 | 走到 `else`（左右孩子都有） | 后继节点 | 不能，后面还要接子树 |

情况一没有孩子，当前节点删了它就什么都不剩，返回空就可以了。

### 别急着 return

情况二，之前我们写二叉搜索树的时候是直接 `return node.right` 的，返回它的右孩子。但这里大家**不要立刻返回**。

为什么？因为我们最后拿到这个"删剩下的节点"，是不是也要调整它的高度，包括检查失衡啊。万一它需要重新平衡、要旋转呢？

所以做法是：我们把删剩下的这个 `node.right`，先**暂时赋值给 `node` 这个变量**——反正 `node` 删了没用了，然后让程序继续向下执行。执行到第 ④、⑤ 步，去把删剩下的这个节点的高度更新一下，并且检查失衡。如果失衡了，还要在 `balance` 方法内部对它做旋转。最终返回的呢，也是经过平衡之后产生的那个新的根节点。

```java
} else if (node.left == null) {
    node = node.right;      // 只有右孩子：先暂存进 node，不立刻 return
} else if (node.right == null) {
    node = node.left;       // 只有左孩子：同理，也不立刻 return
}
```

同理，情况三，被删除节点右孩子为空，删剩下的是左孩子，就把这个左孩子暂存在 `node` 这个变量里，让它继续往下执行，最后要更新高度、重新平衡。

> **注意**：唯一可以立刻 `return` 的是情况一，因为删剩下的是空，高度压根不会变。情况二、情况三删剩下的是一棵还活着的子树，它的高度可能已经变了，也可能自己就失衡了。

### 两个孩子：后继节点与它的"后事"

最后这个 `else` 单独讲，因为它代表待删除的节点有两个孩子。这种情况其实非常多，比如说我删这个 5，5 是不是有两个孩子；我删这个 9，9 是不是也有两个孩子——这种情况还是挺多的。

我们拿删 9 举例。删两个孩子的节点，前面讲过还是比较复杂的：先要找到它的**后继节点**。这个例子中 9 的后继节点是不是这个 10？

代码以前也写过：从待删除节点的右子树开始向左找，向左找到头，那就是它的后继节点。

```java
Node<T> s = node.right;        // s 代表后继节点，初始值是待删除节点的右子树
while (s.left != null) {        // 只要 left 不为空，就表示向左还没走到头
    s = s.left;
}
```

退出循环之后，这里的 `s` 就是我们的后继节点。

找到后继节点以后，我们还不能立刻用后继节点代替掉我们的 9。为什么？因为**后继节点它可能还有自己的孩子**。那我们得把它的后事处理好——想起来了吧，把后继节点的后事处理好，然后再用后继节点代替掉我们 9 这个节点。

怎么处理后事？是不是做一个**递归的删除**。所以我们就再递归地调 `doRemove` 方法，这回是从待删除节点的右子树里、从右子树开始找到这个后继节点时进行删除，也就是 `node.right`，对 `s.k` 进行删除。

那这个 `doRemove` 返回的，是不是就是删完这个后继节点之后剩下来的？剩下来的是谁？

```text
递归删除 10 之后，9 的右子树变成这样：

        12
       /  \
      11   13

11 顶上来了，顶到原来 10 的位置上，成为 12 的左孩子；
12 的右孩子 13 不变。
```

那么"删剩下的内容"我们把它作为**后继节点的右子树**——因为后继节点最终要取代掉这个 9，它的右子树就应该是原来这个 12。

```java
node.right = doRemove(node.right, s.k);
s.right = node.right;
```

复制完右子树以后，后继节点的左子树，是不是应该是我们被删除节点的左子树？而这个顺序我们前面讲过，**必须是先给右子树赋值，再给它的左子树赋值**。

```java
s.left = node.left;             // 顺序不能颠倒：先右后左
node = s;                       // 用 s 代替掉之前被删除的 node，删剩下的是后继节点
```

等这些操作都完成了，我们用 `s` 就代替掉了之前被删除的那个节点。最后返回之前，还要调整这个后继节点的高度，以及对后继节点做失衡的检查，包括旋转。

### 删 9 的完整回放

代码写完了，我们通过这张图看一下刚才删除 9 的整个流程。

首先是进入了第一个 `else`，也就是找到了 9，找到了待删除的这个节点。接下来，因为它有两个孩子，所以进入了第二个 `else`，走两个孩子的节点删除的逻辑。

然后从右子树去找它的后继节点，这里沿着右子树向左走到头，循环走完了，后继节点 `s` 就对应到 10 这个节点。

那 10 这个节点有了之后，我们要**先**处理好后事：先从 9 的右子树里把 10 删掉，删的结果是不是就是 11 顶上来，变成 11、12、13 这样的结构，11 顶上来了，12 和 13 不变。也就是说我们执行完这一次 `doRemove`，就把 10 已经删掉了，11 顶上来了，后继节点的后事处理好了。

处理好以后呢，把后继节点的左右孩子都赋上值，值呢都是原来被删除节点的右孩子和左孩子。这里说明一下，我这个网页由于技术原因，实际值其实已经替换上来了，但显示的还是原来那个待删除节点 9——其实已经是 10 的右孩子等于我们原来待删除节点的右孩子，10 的左孩子已经等于原来待删除节点的左孩子了，只不过是显示问题。

那接下来就是要调整后继节点的高度，检查后继节点是否失衡。我们来看后继节点，也就是红色的这个点，失衡了没有？看它的左子树现在比右子树高，高度差已经超过 1 了，所以失衡了。

失衡以后是失衡的哪种情况呢？红色节点是失衡节点，它的左子树比右子树高，而且左子树里面也是左边高右边低，因此属于**左左**的情况。左左的情况我们需要做一次右旋就可以了。

```text
左左型右旋（L-L Rotate）

      x  ← 失衡点，左高右低        y  ← 新根
     / \                          / \
    y   z          右旋          t   x
   / \                                    \
  t   u                                  u   z

对应到删 9 这个例子：
  x = 10（红色，下来）
  y =  5（黄色，上去）
  u =  6（绿色，换个爹）
  z = 12
```

红色的旋转下来，它那个 9 就变成 10 了；黄色的 5 旋转上去了；绿色的呢，它原来的爹是黄色的 5，旋转之后它的爹变成了红色的 10。这样我们这个删除操作涉及到了一个失衡的处理。

删除就先讲到这里。

### 红黑树：换一套判断平衡的依据

接下来我们学习红黑树。红黑树也是一种自平衡的二叉搜索树——我们之前是不是还讲过，AVL 树也是一种自平衡的二叉搜索树。

那么它俩主要的区别在于哪呢？**主要的区别就是判断平衡的依据不一样。**

之前我们学的 AVL 树，是看一个节点它的左右子树高度差是不是超过了一，超过了一表示它不平衡。我们的红黑树判断一棵树是不是平衡，它有自己的一套规则，这个我们待会就会讲到。

那它跟 AVL 树相比有什么优势吗？优势主要就体现在它的**插入和删除**时——红黑树的旋转次数会少一些，也就是性能上稍微比 AVL 要高一些。

#### 五条特性

这节课我们先来看红黑树的特性，一共有五条。

| 特性 | 内容 |
| --- | --- |
| 一 | 节点颜色只有两种：黑色、红色，所以节点对象里要加一个 `color` 属性表示颜色 |
| 二 | 如果出现了 `null`，一律把它看成是黑色 |
| 三 | 红色的节点不能相邻，这条非常重要 |
| 四 | 根节点必须是黑色 |
| 五 | 从根到任意一个叶子节点，所经过路径中的黑色节点数目是一样的 |

第一条很容易理解，从名字上就看出来。红黑树里的节点颜色分成了两种颜色，一种黑色一种红色，就这两种。所以我们待会设计红黑树节点对象的时候，得加一个属性 `color` 表示它节点的颜色。

第二条，如果出现了 `null`，比如说我的孩子节点是 `null`，那这个 `null` 我们把它看成是黑色。举个例子：我这个 6 它的左孩子我没画出来，这是不是是个 `null`？那这个 `null` 我们将来如果对它做颜色判断，就把它当成是黑色。这能理解吧。

第三条，红色节点不能相邻，这条非常重要。大家看我画的这棵树是不是没有相邻的红色节点？也就是红色节点都被黑色隔开了，层与层之间是没有相应的。如果相邻会怎么样呢？如果相邻就意味着**不平衡**了，不平衡我们就需要对它进行调整。这也是判断是否平衡的一个依据。

第四条也简单，红黑树的根节点必须是黑色。同样，将来根节点如果在某个过程中变成红色了，那我们也**得把它重新调整成黑色**，才能认为它是平衡的。

最后一条，从根到任意一个叶子节点，所经过路径中的黑色节点数目是一样的。比如说我这张图里的叶子节点是谁？是不是这里的 2、4、7、9、11 这几个。从根节点到每个叶子节点，它所经过的路径中有相同个数的黑色节点：从根到 2 是两个黑，到 4 也是两个，到 7 也是两个，到 9、到 11 都会出现两个黑色节点。

如果第五条特性也没有满足，那也说明红黑树是不平衡的，我们要对它重新调整。

> **结论**：红黑树只要满足这五条，就表示它是一个平衡的红黑树。而实际判断的时候，最关键的就是**三和五**这两条——出现相邻的红色节点，或者到叶子节点的某条路径中黑色节点个数不一样了，这时候就要重新调整，让它恢复平衡。

#### 拿图判断：黑色叶子必须成对出现

我们来看几张红黑树的图片，大家来判断一下它们是不是属于平衡的红黑树。

第一张，显然不是，违反的是规则三，也就是红色节点不能相邻——图上有两个红色节点相邻了。待会我们去判断的时候，主要就看 3、4、5 这几个条件。

第二个，也不是，违反的是规则五。到任何一个叶子节点，黑色节点数应该一样：到这个、到 3 这两个叶子经过的黑色节点数是两个，到 7、9 这两个叶子经过的黑色节点数目是三个。所以右边重、左边轻，两边不平衡，黑色的必须是平衡的。

第三个，是的，3、4、5 这几个条件都是满足的。你就盯着黑色看，黑色是不是两边都是平衡的呀？这是一棵平衡的红黑树。

第四个就有意思了。有同学说"是吧"，理由是：3 和 4 首先是满足的，5 好像也是满足的，因为你看从 6 到 1 这个叶子和从 6 到 8 这个叶子，是不是都经历了两个黑色节点，好像是对的。但实际上这棵树是**不平衡**的。

红黑树错在哪呢？**是因为我们没有考虑 `null`。**

那什么时候需要考虑 `null` 呢？其实就是当我们发现一个叶子节点，它没有自己的兄弟的时候，那这时候我们就应该把 `null` 这个因素也加进来。

比如刚才这张图，如果我把那些 `null` 都画上，它应该长这个样子：8 左右是不是都是 `null` 了，2 呢也是，然后 1 左右孩子也都是 `null`。大家来看它是不是平衡的？前面我们说过 `null` 是应该把它看成黑色的，你看它到每个叶子节点，到这两个叶子节点路径之中是不是出现了三个黑色；到 1 左右孩子这两个叶子节点，路径中是不是也出现了三个黑色；但是到 2 的右孩子这边，是不是路径中只出现了两个黑色呀？不平衡。

再跟我们前面那个例子做对比的话，为什么它就是平衡的呢？把 `null` 都给它补上，右边：8 左右孩子……是不是出现三个黑色；到 2 这边的右孩子三个黑色；到 1 这边的左右孩子也是三个黑色。

> **提示**：这里有一条经验——以后大家遇到叶子节点，**如果这个叶子节点是红色的，它可以单独一个，它一个没关系**；**但如果遇到的叶子节点就是一个黑色的、它没有兄弟的，这种肯定是不平衡的**。简单地说：黑色叶子肯定得成对出现，红色叶子出现做孩子或者有孩子都可以。

### 红黑树的节点对象

下面我们来看红黑树代码的实现。`RedBlackTree` 这个类我已经提供好了。

红黑树节点有两种颜色，所以我们定义一个枚举类型 `Color` 用来代表两种颜色，分别是 `RED` 和 `BLACK`。根节点 `root` 也提供好了。

节点对象里面的很多属性跟我们前面介绍过的节点对象都是类似的，像什么键 `k`、值 `v`、左孩子 `left`、右孩子 `right`，这跟以前都一样，这个就不再啰嗦了。

新增的属性有两个：

- `parent`：代表这个节点的父节点。因为我们红黑树新增和删除的时候，会经常用到父节点，所以干脆把它作为节点的一个属性了。当然了，这也带来了编码的复杂度——因为我要新增和修改的时候，得维护它的父节点指向正确的对象，所以比以前要复杂一些。
- `color`：颜色。我们希望刚创建出来的节点应该是红色的，所以可以给它赋一个初始值，就是 `RED`。新节点都认为是红色的，这个待会讲新增的时候再说。

#### 三个找人的方法

关于这个节点类，我们要实现三个方法，这三个方法以后都会被频繁用到。

第一个方法判断当前这个节点是不是属于一个**左孩子**，返回布尔值，方法名叫 `isLeftChild`。

```java
private boolean isLeftChild(Node<T> node) {
    return node != null
        && node.parent != null
        && node.parent.left == node;   // 父子指向的是同一个对象
}
```

怎么判断：首先你得有父节点，父节点有了，我们再去判断是不是左孩子——看一下父节点的 `left` 属性跟我当前节点是不是相等的，也就是它俩指向的是同一个对象，说明我当前节点就是父亲的孩子了。第二个条件都不成立，说明它是它父亲的右孩子。

第二个方法去找当前节点的**叔叔**（`uncle`，返回 `Node`）。先来看一下叔叔节点的定义：叔叔就是跟父亲平辈儿的节点。

```java
private Node<T> uncle(Node<T> node) {
    if (node == null || node.parent == null || node.parent.parent == null) {
        return null;                    // 根节点、以及没有爷爷的节点，都没有叔叔
    }
    return isLeftChild(node.parent)
        ? node.parent.parent.right      // 父亲是爷爷的左孩子 → 叔叔是爷爷的右孩子
        : node.parent.parent.left;      // 父亲是爷爷的右孩子 → 叔叔是爷爷的左孩子
}
```

举例说明：图上这个节点 2，它有没有叔叔？有吧——你看它父亲是 3，跟它父亲平辈儿的就是 6，6 就是它的叔叔。再看这边的 7，它父亲是 6，跟 6 平辈的就是 3。所以有些节点是有叔叔的。

是不是所有节点都有叔叔呢？也不一定。比如我们的根节点，它连父节点都没有，那有跟它父亲平辈的吗？没有，所以根节点没有叔叔。包括这里的 5 和 10 这两个节点，这两个节点它是有父亲的，但是有爷爷吗？没有——显然有爷爷才能有叔叔嘛。所以我们先把这两种特殊情况先写出来。

第三种方法是找**兄弟**（`sibling`，兄弟的英文单词是 sibling），返回的也是一个节点类型。

```java
private Node<T> sibling(Node<T> node) {
    if (node == null || node.parent == null) {
        return null;                    // 连父节点都没有，肯定没有兄弟
    }
    return isLeftChild(node) ? node.parent.right : node.parent.left;
}
```

怎么找兄弟：首先你是不是得看看他有没有父节点，如果连父节点都没有，那肯定是没有兄弟。比如说是我们的根节点，根节点就没有兄弟，这时候直接返回就可以了。那如果一个节点有父亲，比如说这里的 2 有父亲，那他是父亲的左孩子的话，那他的兄弟是不是就是父亲的右孩子？反过来，如果我当前节点是父亲的右孩子，那应该返回父亲的左孩子。

#### 判红判黑为什么要放在树里

接下来我们再写两个工具方法，判断这个节点是红色还是黑色。

有同学说，你直接通过节点去点它的 `color` 属性，看颜色不就行了？但大家别忘了，有可能我们会处理到 `null`，你不能直接去点了吧？那样就出空指针了。所以我们单独写两个方法，是为了更友好地处理 `null`。

那这两个方法呢，就**不能定义在 Node 内部了**，我们定义在这个树内部。

```java
private boolean isRed(Node<T> node) {
    return node != null && node.color == Color.RED;
}

private boolean isBlack(Node<T> node) {
    return !isRed(node);    // 不是红色就肯定是黑色，null 也算黑
}
```

为什么 `isRed` 要先判 `node != null`？红黑树里有一条规则，如果你节点已经是 `null` 了，那它肯定是黑色，所以你要成为红色，肯定首先它得不是空。第一个条件就是"当这个节点不是空的时候"，然后继续看它的 `color` 属性，`color` 等于我们前面的 `RED` 这个红色枚举，表示它确实是红色的。

`isBlack` 跟他正好相反：`return !isRed(node)` 是一种写法。当然你如果直接写条件也可以——`node == null` 是第一种黑色的情况；第二种情况是 `node != null`，但是它的 `color` 确实等于 `BLACK`，那这时候它也是黑色。这两种写法都可以。

### 右旋：和 AVL 有两处不一样

接下来我们给出红黑树的右旋和左旋的代码。它跟我们之前介绍的 AVL 树的右旋左旋代码有什么不一样呢？其实**大部分都是一样的**，旋转的核心逻辑是类似的。

但是不一样的地方主要有两点：

1. 现在这个节点对象里多出来一个 `parent` 属性，旋转之后你要让它 `parent` 指向的值是正确的，所以这里处理起来要麻烦一些；
2. 这次给出的旋转代码里**没有返回值**了。原来我们的右旋左旋会返回旋转后的新根对象，这个新根在旋转方法的外一层再去建立父子关系；但这回我们要把旋转后新根的父子关系**直接在旋转方法内部建立好**。

> **结论**：以后写红黑树的旋转，`rotate` 里面自己把 parent 链路修完整，外面就不用再操心重新挂接了。

#### 粉黄绿标记法

接下来我以右旋为例，把右旋代码写出来（左旋跟它是正好对称的，课堂上节省时间就不再演示了）。

我们把右旋代码写出来看。以这张图为右侧，要旋转的节点是这个 8，也就是粉色这个节点；将来作为新根的节点是这里黄色的 5；然后要换爹的节点是这里绿色的 6。

这里教给大家一个小技巧——**对照着图很容易看**，得先把这几个颜色标记出来：

```text
旋转前（三色标记）

        pink（要右旋的节点）
       /
    yellow  = pink.left        ← 将来的新根
        \
        green  = yellow.right   ← 要换爹的节点

旋转后（基本旋转部分，和 AVL 完全一样）

    yellow
        \
        pink
        /
      green
```

黄色节点的右孩子会变成粉色，因为黄色上来了变成了新根，粉色下去了；粉色节点的左孩子变成绿色节点，绿色节点换了个爹。

**我们以前的代码写到这就完了。** 但是现在呢，我们多出了刚才我说的两件事：要把它的 `parent` 关系处理好，并且要把旋转后的新根（也就是黄色）的父子关系直接在这个方法内给它建立好。

#### 第一件事：维护这三个节点的 parent

先做第一件事，把刚才这三个节点的爹先给它处理好。

看旋转之前，绿色的爹是指向黄色的；旋转之后呢，绿色爹指向了粉色，所以它的 `parent` 应该重新赋值。还有黄色的点，黄色在旋转之前是粉色的孩子，但旋转之后呢，它是不是应该变成原来粉色的爹？——当然我这个例子是没有的，粉色的 `parent` 是 `null`，但是你想如果这个粉色它还有上一级、它还有 `parent` 的话，那旋转之后黄色的爹是不是应该变成原来粉色的爹？最后粉色的点，旋转之后它的 `parent` 显然应该变成黄色。

| 节点 | 旋转前的 parent | 旋转后应该指向 |
| --- | --- | --- |
| green | yellow | pink |
| yellow | pink | parent（pink 原来的爹） |
| pink | parent | yellow |

```java
if (green != null) {          // 绿色节点有时候旋转时并不会出现，可能就是 null
    green.parent = pink;
}
yellow.parent = pink.parent;
pink.parent = yellow;
```

> **易错点**：绿色节点一定要加非空判断。我们这个图里是确实有绿色节点，但也有可能它就是 `null`，如果不给它判断就去改 `parent` 属性，就会空指针。

#### 第二件事：新根与上层的父子关系

第二件事呢，我们要把旋转后的新根，也就是这里的黄色节点，跟它**更上层节点**的父子关系，在我们这个旋转方法内给它做好。什么意思呢，我再举个例子。

因为刚才那个是根节点，算是一种特殊情况。那么再来看一个旋转的例子：这里的 5 和 3 要旋转，粉色的是 5，黄色的是 3。旋转之后，这个黄色的 3 是不是作为这个子树的新的根——注意，不是整棵树的新根，它是作为这棵子树的新根。

那大家来看它更上层的节点是谁呀？是不是这里的 8？更上层的节点是这里的 8。那 8 的左孩子原本是粉色的 5，旋转之后呢，8 的左孩子应该变成黄色的 3。我们就是要把黄色跟它更上层的节点的这种父子关系，在这个方法内给它建立好。

这容不容易啊？也容易。旋转之前，是不是可以通过粉色先拿到它更上层的节点呀——通过粉色它的 `parent` 就可以拿到更上层的节点，这个咱们就起个名字叫 `parent`。等旋转之后呢，我们只要把 `parent` 跟新根黄色的父子关系建立好就可以了。

但是这里就带来一个问题了：**你这个黄色是应该作为更上层 `parent` 的左孩子呀，还是右孩子呢？** 我们那个图里只是其中一种情况，它是左孩子。那也有可能黄色的是更上层节点的右孩子，这个怎么判断？

其实我们可以写个条件：如果 `parent` 的左孩子是原来的粉色——因为 `parent` 的左孩子在我们确认之后是不是还没有重新赋值啊，它还是指向原来这个粉色的。那这种情况下，我的黄色节点旋转上去之后，是不是也应该作为 `parent` 的左孩子？如果这个条件不成立，那将来我的黄色旋转上去之后，就应该作为 `parent` 的右孩子。

```java
private void rightRotate(Node<T> pink) {
    Node<T> yellow = pink.left;
    Node<T> green = (yellow != null) ? yellow.right : null;
    // 先把更上层的节点抓在手里，等下 pink.parent 就被改写成 yellow 了
    Node<T> parent = pink.parent;

    yellow.right = pink;
    pink.left = green;

    if (green != null) {
        green.parent = pink;
    }
    yellow.parent = parent;
    pink.parent = yellow;

    if (parent == null) {
        root = yellow;                 // 粉色本身就是根，黄色顶上成为新根
    } else if (parent.left == pink) {
        parent.left = yellow;
    } else {
        parent.right = yellow;
    }
}
```

最后我们再考虑那个特殊情况：旋转的时候粉色节点它本身就是根节点，那你想，它是根节点，根节点的 `parent` 是什么啊？是不是就是 `null`。那 `parent` 等于 `null` 的时候，你再去给他的 `left` 赋值、给他的 `right` 赋值是不是就没有意义了？肯定会抛空指针异常。所以我们应该把"旋转节点是根节点"，也就是 `parent` 等于 `null` 这种情况要处理一下：这种情况就是把我们旋转上去的黄色节点作为新的整个树的根节点，也就是 `root = yellow` 就行了。

**只有 `parent` 不为 `null` 的时候，我们才需要建立 `parent` 跟黄色节点之间的父子关系**，所以这两个应该写到 `if` 和 `else if` 里面。

还有一处等价的修改：这里用到了 `pink.parent`，跟我们上面这个 `parent` 代表的是同一个变量，所以可以直接改成 `parent`。

右旋代码到这里就写完了。看起来整个代码还是比较复杂的，但是你如果按照我刚才的思路来编写，我觉得还是比较清晰的：先把粉黄绿这几个颜色标记出来，把它的旋转代码写好（基本代码）；然后比之前多了一步，把这些节点的 `parent` 属性给它处理好；最后再把旋转后的新根（也就是黄色）跟它更上层的这个 `parent` 节点之间的父子关系建立好就可以了。

至此为止，我们这个右旋代码就实现完毕了。

1. 第一张：**不平衡**，违反规则三（红色节点不能相邻），图上有两个红色节点相邻了。
2. 第二张：**不平衡**，违反规则五（到叶子节点黑色节点数必须相同）——到某些叶子经过两个黑，到另一些叶子经过三个黑，右边重左边轻。
3. 第三张：**平衡**，规则 3、4、5 都满足。判断诀窍就是"盯着黑色看"，黑色在两边是平衡的。
4. 第四张：**不平衡**——最容易被骗的一张。表面上看规则 3、4、5 都满足，实际上是因为没有考虑 `null`。

第 4 张是这道题的陷阱所在：`null` 要当成黑色一起数。什么时候需要数它？**当一个叶子节点没有自己的兄弟的时候**，就要把这个 `null` 加进来算。补上 `null` 之后重新数一遍：到某些叶子是三个黑，到 2 的右孩子那边只有两个黑，不平衡。

**判定经验**：黑色叶子必须成对出现；红色叶子可以单独一个（可以有孩子也可以没有孩子）。这就是为什么第一张图虽然 4、5 都能蒙混过去，但只要出现相邻红节点就直接判不平衡了。

## 红黑树的插入：顺着 k 找空位，再修红红相邻
> 对应块：BLK51 | 覆盖分集：P193-P194 | 块标题（分集名）：《基础算法-148-红黑树-put-case1~3》

一提到红黑树的插入和删除，大家应该都听过一些说法——这俩属于比较难的，比较难。

难在哪儿呢？网上讲红黑树的资料我看大致有两种讲法：一种是就着红黑树本身来讲；另一种是把它跟另外一种叫 2-3 树的东西摆在一起对比着讲。但在我看来，这两种讲法反而会把红黑树的插入和删除搞得更加复杂。所以咱们现在就回归红黑树的本质，就从正儿八经的红黑树讲起它的插入和删除。

其实没有大家想的那么难。

### put 的架子：二叉搜索树的活儿，外加一次修复

我先把两个方法的架子摆出来。一个是 `put`，它负责新增或者更新；另一个是 `remove`，它负责删除。

主要的思路是这样的：

`put` 方法就按我们之前写二叉搜索树的代码正常新增就可以，只是遇到了一种叫**红红不平衡**的情况，我们要把树重新调整平衡。这种红红不平衡，将来细分的话有四种 case，下面我们一个一个演示。

`remove` 呢，也是按正常二叉搜索树的删除去正常删，代码都跟以前差不多，只不过这里会用到一个**李代桃僵**的技巧。如果遇到一种叫**黑黑不平衡**的情况，我们就进行调整，让它重新面对平衡。这种黑黑不平衡细分的话一共有六种 case。

这一讲我们把 `put` 走完，重点是 `fixRedRed`。

### 顺着 k 找空位：新增、更新与双向父子关系

`put` 的思路我们前面已经讲过好几遍了：找空位，新增就是找空位。找到空位以后，根据这里的键值创建出新的节点对象，然后跟一个父节点建立好父子关系，这个新增操作就算是完成了。

如果没有找到空位，我们就根据 k 的大小不断地向左转或者向右找。当然还有一种情况：如果遇到了相同的 k，那我们就不是做新增了，而是做一个更新——把 `p` 它的 value 更新成我们传过来的这个新的 value 值，然后也不用继续查找了，`return` 就完事。

写成代码就是这样：

```java
public void put(int k, int v) {
    Node p = root;          // p 从根节点开始，不断去找空位
    Node parent = null;     // 顺手记下"爹"，循环里每次都更新

    while (p != null) {
        if (k < p.k) {
            parent = p;
            p = p.left;
        } else if (k > p.k) {
            parent = p;
            p = p.right;
        } else {
            p.v = v;        // 找到了，做更新，不用再往下走
            return;
        }
    }

    // 循环结束，这时候 p 肯定是 null 了，说明找到了空位
    Node inserted = new Node(k, v);

    if (parent == null) {
        // 树一开始就是空的（root 是 null），循环压根没走
        // 新增节点直接当根节点
        root = inserted;
    } else if (k < parent.k) {
        parent.left = inserted;
        inserted.parent = parent;   // ← 红黑树特有的这一步
    } else {
        parent.right = inserted;
        inserted.parent = parent;   // ← 红黑树特有的这一步
    }

    fixRedRed(inserted);
}
```

这里有几点要交代清楚。

**关于 `parent`。** 在循环外我们再定一个变量 `parent`，它刚开始是 `null`，代表新插入节点的父节点；每循环一次就把它更新成当前节点。注意 `parent` 也可能是 `null`——如果我一开始树就是空的，`root` 是 `null`，那整个循环就没走。这种情况下 `parent` 也是 `null`，那我们就知道了：新节点直接作为根节点，让根节点等于新增节点就可以了。

如果不是空，就要看看新增节点将来是作为 `parent` 的左孩子还是右孩子。如果 k 小于 `parent.k`，就作为 `parent` 的左孩子；否则肯定是作为 `parent` 的右孩子。以前我们写二叉搜索树的插入代码，写到这儿就结束了。下面来看红黑树里不一样的地方。

**第一个不一样：父子关系从单向变成双向。** 我们的节点对象比原来多出了一个叫 `parent` 的属性。那这个 parent 属性是不是也得给它赋一个正确的值？之前父子关系是个单向的，都是通过父亲 left 或者父亲 right 去找儿子；现在这个关系变成双向的了——不仅通过父亲要找到儿子，儿子这边也应该通过那个 parent 属性找到他的父亲。所以上面那个 `else if` 跟最后这个 `else`，我们都应该做一个赋值的动作，让 `inserted` 它的 parent 等于上面这个父亲。

> **易错点**：如果插入的新节点是根节点，那赋 `parent` 这一步可以省略。因为根节点它的父亲应该是 `null`，这就跟 Node 的 parent 字段初始值 `null` 是一样的，不用单独赋值。所以 `Node` 里要把 `parent` 声明成默认就是 `null`。

**第二个不一样：新节点有个颜色属性，默认是红色。** 那么如果新增节点跟它的父节点两个都是红色，是不是就会触发我们之前说的红黑树的一条不平衡规则——两个相邻的节点不能都是红色。这时候我们就要重新调整平衡。调整平衡的代码我们用单独的一个方法来实现，方法名习惯上把它叫 `fixRedRed`，修复的意思。从方法名大概能猜出来，就是当两个相邻的红色节点这种情况下，我们需要去重新 fix 调整它的平衡。

那调整的是谁呢？就是我们新增的这个节点，比如说我把它叫做 `x`。这个调整方法在我们新增的最后来进行调用就可以了。

### case1：插入的就是根节点

红红不平衡第一种情况是比较简单的：**如果你插入的节点是根节点，那只需要把这个根节点变黑就可以**。

为什么？比如说我加一个 9，它作为根节点，它的初始颜色是不是红色？初始颜色是红色，它又是作为根节点，是不是违反了红黑树的第四条特性——根节点必须是黑色的。那怎么让它恢复平衡、满足这些特性呢？是不是很简单，只要让刚才的这个根节点变成黑色就 OK 了。

```java
if (x == root) {
    x.color = Color.BLACK;   // 根节点必须是黑的
    return;                  // 下面的分支就不用执行了
}
```

### case2：父节点是黑色

第二种情况：**插入节点的父亲如果是黑色的话，红黑树的性质不会发生变化，这时候我们无需任何调整**。

比如现在已经有根节点 8 了，我再加入一个新的节点 5。5 刚加入的时候是不是红色的？加入进去之后，大家看它有没有违反红黑树的这些特性：

- 根节点还是黑色的，这条满足；
- 有没有出现两个红色节点相邻的情况？也没有出现；
- 从根到任意一个叶子，黑色节点的数目是不是一样的？你加入的是一个红色节点，都没有增加什么黑色节点，那数黑色节点的数目肯定没有发生变化。

所以它不会影响到 5，我们不需要做任何的调整，它仍然是平衡的。判断黑色呢，我们前面已经写过一个 `isBlack` 方法了，直接调用一下即可，条件成立就直接 `return`。

```java
if (isBlack(x.parent)) {
    return;   // 不用做任何调整
}
```

这两个 case 属于简单情况，先把它们的代码实现完。它们合起来其实是一句判断：只要插入节点是根，或者它的父亲是黑的，调整就可以直接收工。

### case3：叔叔也是红色，只需要变色

如果插入节点的父亲是红色，插入节点的初始颜色也是红色，红红相邻了，这棵树也因此变得不平衡，因为它违反了红黑树的特性三。这种情况下又可以细分成 case3 和 case4，也就是插入节点"叔叔"是红色的情况和"叔叔"是黑色的情况。这两种情况让它恢复平衡的手段稍有区别。

#### 变色为什么能救回来

先看例子。这棵树是一棵平衡的红黑树，几条特性都是满足的。我插入一个新的节点 1，它比 2 小，所以作为 2 的左孩子加入进来：

```text
                5 (R)              ← 3 的父亲
                │
        ┌───────┴───────┐
      3 (B)            13         ← 13 是 3 的叔叔
     ┌───┴───┐
   2 (R)   4 (R)                    ← 4 就是 2 的叔叔
   │
 1 (R)  ← 本次插入
```

它正是我们 case3：插入节点跟它的父节点两个都是红色，红红相邻了，并且它的叔叔（也就是 4）也是红色。

> **定义**：这里说的"叔叔"，指的是父节点的对称位置上的那个节点——爷爷的另一个孩子。它是红是黑，直接决定我们是"变色"还是"旋转"。

注意红黑树要让一棵树恢复平衡，要结合两种做法：一种叫**变色**，一种叫**旋转**。对于 case3 来讲，我们只需要通过变色就能让这棵树重新恢复平衡。

变色的规则其实很简单。看 2 跟 1 这两个节点，它们不是不能有两个相邻的红色吗？那我能不能把它的父亲 2 从红色变成黑色？这样 2 和 1 来讲，是不是又重新满足了特性三。

但是光这样行吗？这样行是行，**叔叔不干了**。你看对于 3 这个子树来讲，它左边路径中的黑色节点数跟右边路径中的黑色节点数，现在不平衡了：左边路径有两个黑色节点，右边路径呢只有一个黑色节点，所以又违反了规则五。

那怎么办呢？我可以让他的叔叔也一起变成黑色。这样的话，左边路径、右边路径黑色节点的总数是不是就没有变，仍然是平衡的。

事情完了吗？还没有。为什么呢？因为我们局部上——也就是 3 这个子树——它确实满足了那几条特性，但是你从整体上来看，2 这条路径和 4 这条路径是不是多了一个黑色？因为父亲跟叔叔都变成黑色了，多了一个黑色。那其他路径里的黑色有没有增加？没有增加。所以我们得在 2 和 4 这两条路径里，再想办法减少一个黑色——也就是把其中一个节点变成红色。

变谁呢？2 和 4 刚从红色变成黑色，显然变它俩不合适。唯一的选择就是把 3 变成红色。这样来看，每条路径中黑色节点的数目并没有发生改变。

```text
        5 (R)              ← 5 仍是红色，它还是可能和下面红红相邻
        │
  ┌─────┴─────┐
 3 (R)       13 (?)
   │          │
 ┌─┴─┐
2 (B) 4 (B)                 ← 父亲、叔叔双双变黑
 │
1 (R)                        ← 红红相邻被消除
```

有同学要问了：那你 3 又变成红色了，那是不是又触发红红相邻了？没关系，这时候红红相邻，我们只要**递归**来进行操作就可以了，直到它递归到根节点为止就 OK。

我们把这个过程走完。你看 3 和 5 红红相邻了，那把 3 再看成是"刚插入的这个节点"，那他的叔叔是不是这边的 13？又是父亲红、叔叔红，是不是还是刚才的 case3？那做相同的操作就可以了：先把父亲变成黑色，再把叔叔变成黑色，最后把祖父变成红色。

> **结论**：只要遇到了 case3，就把父亲和叔叔变黑、祖父变红就可以了。

最后呢我们发现它到根节点了。那根节点肯定是要把它变成黑色，因为根节点之上没有更多节点了。经过这一轮调整，我们整棵树就恢复了平衡，你可以自行验证一下，看看它是不是又满足了这几条规则。

#### 对应的文字描述与代码

我们把上面的分析用文字描述一遍：当我们插入节点的父亲是红色，并且叔叔也是红色的时候，我们用变色就能解决。具体的做法就是把父亲的颜色变成黑色，同时叔叔的颜色也连带着变成黑色；祖父如果是黑色就保持黑色不变的话，是不是这棵子树的黑色就过多了？所以祖父要变成红色。但是祖父变成红色，它可能会再次触发一个红红相连，所以我们要对祖父做一个递归的调整。

代码也很简单。执行到这个位置，说明这时候它的 parent 肯定是红色了。接下来只要判断他的叔叔是不是红色，就能进入 case3 的处理。因为待会儿既要用到 parent、也要用到叔叔、还用到祖父，所以我们定义三个变量：第一个变量通过它的 parent 属性拿到父亲；然后用我们前面写过的 `uncle` 方法拿到他的叔叔；最后通过它的父亲的 parent 拿到祖父。

```java
private void fixRedRed(Node x) {
    // case1：插入的就是根节点
    if (x == root) {
        x.color = Color.BLACK;
        return;
    }

    // case2：父亲是黑色，红黑树的性质不会变化
    if (isBlack(x.parent)) {
        return;
    }

    Node parent = x.parent;
    Node uncle = uncle(x);
    Node grandParent = parent.parent;   // 祖父

    // case3：叔叔也是红色 —— 只需要变色
    if (isRed(uncle)) {
        parent.color = Color.BLACK;
        uncle.color = Color.BLACK;
        grandParent.color = Color.RED;
        fixRedRed(grandParent);        // 由祖父递归调用后续代码
        return;                        // 后面的分支就不用执行了
    }

    // case4：叔叔是黑色 —— 后面接着讲
    ...
}
```

> **提示**：IDEA 可能会在这里给一个告警，说 `uncle` 这行可能触发空指针异常。会不会呢？不会。因为如果你能满足这个条件，那意味着这个节点肯定不为 `null`——`null` 的话它肯定是黑色节点，是走不到这个 `if` 里来的。既然能进入这个 `if`，这时候我们的叔叔肯定非空，所以不用担心它的空指针。

到此为止，case3 的解决代码就实现完毕了。

### case4：叔叔是黑色，得靠旋转

case4 是：插入节点的父亲是红色，插入节点当然也是红色，它俩触发了红红相连，不过这回叔叔的颜色是黑色。

case4 看起来挺复杂，它又分成了四种小情况。不过这四种小情况大家应该都比较熟悉了——我们在讲 AVL 树的时候其实都见过。

| 不平衡形态 | 判断特征 | 解决办法 |
| --- | --- | --- |
| 左左 LL | 父亲是左孩子，且插入节点是左孩子 | 一次右旋 |
| 右右 RR | 父亲是右孩子，且插入节点是右孩子 | 一次左旋 |
| 左右 LR | 父亲是左孩子，插入节点是右孩子 | 先对父亲左旋，再对祖父右旋 |
| 右左 RL | 父亲是右孩子，插入节点是左孩子 | 先对父亲右旋，再对祖父左旋 |

当然这里也会有少量的变色。下面我们就具体来看 case4 的情况分析。这里主要分析左左和左右这两种情况，至于右右和右左，由于它跟前两种都是对称情况，我们就不做分析了。

#### 左左：变色为什么救不了

这是我们初始的一颗红黑树，我要插入的新节点是 2，它应该作为 3 的左孩子加入进来：

```text
            5 (B)                 ← 祖父
           /       \
       3 (R)        nil → 视作黑  ← 叔叔
       /
   2 (R)  ← 本次插入
```

现在显然触发了一个红红相邻。2 的父亲是 3，它的叔叔是不是黑色？是的——因为咱们说过，如果你遇到了 `null`，那 `null` 是要把它当成黑色来看的。因此父亲是红色、叔叔是黑色，匹配到了我们的 case4。

现在先不看它那四种形态，我们先从变色的角度看：它能不能通过变色重新调整平衡？红红不能让它相邻，所以自然而然想到的，先把父亲 3 变成黑色。但是父亲 3 变成黑色以后，父亲这条路径中的黑色是不是多了一个？原来没变色之前是两个，变色之后这条路径里是不是有三个黑色了。

那怎么办呢？想办法再补偿，让他的祖父变成红色，这样整条路径的黑色总数是不是仍然是两个。但是问题来了：祖父变成了红色，那到它叔叔这条路径里是不是少了个黑色？本来这条路径里是有这个祖父这个黑色的，祖父这个黑色得算一个吧，但现在祖父变成红色了，叔叔这条路径中的黑色是不是少了一个？

这时候我们**就不能用变色来保证黑色的平衡了**。变色做不到，那就得用旋转了。怎么旋转呢？显然叔叔这边少黑色，那我就右旋，想办法把黑色旋转过去一点。我们来次右旋，右旋的轴就是我们的祖父——祖父这个 5 待会旋转下去，父亲这个 3 旋转上来。

```text
            3 (B)                 ← 父亲旋转上来，而且是黑色的
           /       \
       2 (R)        5 (R)          ← 祖父旋转下去，同时染红
                          \
                          nil → 视作黑
```

大家来看，这样黑色平衡了没有？到他父亲这条路径上，和他到原来叔叔这条路径上的黑色，仍然保持还是两个。

所以我们红黑树里面，如果遇到了变色不能让它恢复平衡的时候，这时候我们就要再配合旋转就可以了。当然刚才这种情况你可以简单地这样理解：就是当他的父亲是左孩子的时候，插入节点也是左孩子，其实这就是我们的一种左左不平衡；既然是左左不平衡，显然是不是我们做一次右旋就能解决。当然刚才的变色也不能少。

> **结论**：左左不平衡的三板斧就是——父亲变黑、祖父变红、对祖父做一次右旋。

写成代码。能执行到这个 `if` 下面，说明叔叔肯定是黑色（如果是红色，它就走上面那个分支了）。接下来判断父亲是不是左孩子，并且插入节点也是左孩子——判断"是不是左孩子"我们专门写了个 `isLeftChild` 方法。

```java
if (isLeftChild(parent) && isLeftChild(x)) {
    // 左左不平衡：父亲变黑、祖父变红、对祖父右旋
    parent.color = Color.BLACK;
    grandParent.color = Color.RED;
    rightRotate(grandParent);
}
```

右旋代码我们前面已经写过了，不用再看了，直接调用就可以。右旋之后是不是就平衡了？是的。刚才我们分析过黑色首先平衡了，而且他的父亲是黑色，旋转上去呢肯定也不会再触发什么红红相邻了，所以我们直接放到这里，不用再做额外的递归调用了。

#### 左右：先旋成左左，再走同一条路

再看 case4 的左右不平衡。这回我们插入的节点是 4，它加入进来以后作为红色节点 3 的右孩子，同样也是红红相邻。它的父亲是 3，叔叔是这边的 `null`（视作黑色），所以是符合 case4 的。

现在呢父亲是左孩子，插入节点是他的右孩子，这种情况就是我们的左右不平衡。其实左右不平衡啊，我们可以先通过一次旋转让它变成左左——也就是我们 3 和 4 这两个节点，先围绕 3 做一次旋转，3 旋转下去，4 旋转上来。大家来看，是不是就跟刚才的左左一模一样了？

具体的做法呢：让这个变成黑色的、旋转上来的父亲（其实是我们插入节点 4）变成黑色，然后祖父变成红色，然后来一次右旋，是不是就能让黑色平衡了？同样，旋转上去的是黑色，它不会再次触发红红相邻，因此到此为止就平衡了。

写成代码，就是加一个 `else if`：当我的 `parent` 是左孩子，但是插入节点是右孩子（所以 `isLeftChild(x)` 要取反）。

```java
} else if (isLeftChild(parent) && !isLeftChild(x)) {
    // 左右不平衡：先把父亲左旋，变成左左的情形
    leftRotate(parent);
    // 此时旋转上来的插入节点 x 成了新的父亲，变色也换了人
    x.color = Color.BLACK;
    grandParent.color = Color.RED;
    rightRotate(grandParent);
}
```

注意这里变色的人**换了**：左旋之后变成新的父亲的是插入节点本身，所以是把插入节点 x 它的颜色变成黑色，而不是原来的 parent。这跟左左那种情况不一样，一定要看清楚。祖父还是变成红色，这都是为了让黑色平衡。

#### 右右与右左，以及条件还能再简化

剩余两种情况我们也写一下。

接下来判断：如果我们的 `parent` 是右孩子（也就是 `isLeftChild` 取反），并且我的插入节点也是右孩子，那这时候是我们的右右不平衡。这种情况下变色部分是一样的，也就是父亲变黑、祖父变红，只不过旋转的方向变成左旋，对祖父左旋。

最后还剩一种就不用写 `else if` 了，直接 `else`。能进到 `else`，那就是我们最后的右左不平衡。先让 parent 右旋（那个图上没画），然后还是我们的插入节点颜色变黑、祖父的颜色变红，这跟刚才左右这种情况一样；不过到了祖父这边呢，我们应该让它左旋。

```java
} else if (!isLeftChild(parent) && isLeftChild(x)) {
    // 右左不平衡：先让 parent 右旋，变成右右的情形
    rightRotate(parent);
    x.color = Color.BLACK;
    grandParent.color = Color.RED;
    leftRotate(grandParent);
} else {
    // 右右不平衡：父亲变黑、祖父变红、对祖父左旋
    parent.color = Color.BLACK;
    grandParent.color = Color.RED;
    leftRotate(grandParent);
}
```

刚才 IDEA 里给出了几个提示，我们看能不能把代码再稍微简化一下。你看第一个条件是说当父亲是左孩子、插入节点也是左孩子的时候，那接下来的 `else if` 里，大家想他上一个条件里已经判断了插入节点是左孩子，那能走到下面这个 `else if`，这个条件我们可以不写了——肯定就是插入节点是右孩子，没问题吧？

类似的，走到第三个 `else if` 的时候，因为前两个 `else if` 都已经判断了父亲是左孩子的情况，那能走到这儿，父亲肯定就是右孩子了，所以这个判断我们也可以去掉。

```java
if (isLeftChild(parent) && isLeftChild(x)) {
    // 左左：父亲变黑、祖父变红、祖父右旋
} else if (isLeftChild(parent)) {
    // 左右：parent 左旋，插入节点变黑、祖父变红、祖父右旋
} else if (isLeftChild(x)) {
    // 右左：parent 右旋，插入节点变黑、祖父变红、祖父左旋
} else {
    // 右右：父亲变黑、祖父变红、祖父左旋
}
```

> **提示**：当然了，你把多余的条件留着也没关系，留着效果是等价的。但去掉之后条件能看见更加简单一些，读代码的人不用去反推"走到这里说明什么"。

### 四种情形串起来

我们把整个插入的几种情况再放在一起大概看一下。其实不难吧，就四种情况。

第一种情况，插入节点是根节点的话，我们直接把根节点变黑就行了。那如果插入节点的父亲是黑色的，这时候插入的红节点并不会影响它的平衡性，所以我们不需要任何的调整，直接 `return` 就 OK 了。

那如果是红红相邻了，那就违反了红黑树的特性，那又分成了叔叔为红和叔叔为黑这么两种情况。叔叔为红的 case3，我们只需要做变色就行，父亲跟叔叔变黑、祖父变红，这样一路变色变上去它就能恢复平衡。

那如果是叔叔是黑色，也就是我们 case4 的时候是最复杂的。不过也还好，因为左左、左右、右右、右左我们在以前 AVL 树的时候就接触过，我们只需要做一次变色和相应的一次旋转操作就能满足了。当然左右和右左啊，他俩要做两次旋转。

整个 `fixRedRed` 的判定顺序其实就是这棵树：

```text
                    插入节点 x 是根节点吗？
                     是 ────────► 染黑，return
                     否
                      │
                父亲是黑色吗？
                 是 ────────► 什么都不做，return
                 否
                  │
            叔叔是红色吗？（红红相邻已确定）
          是 ─────┴───── 否
          ▼                ▼
     case3 变色        case4 父亲是左孩子吗？
     父变黑 + 叔变黑       是 ────────┴───── 否
     + 祖变红            ▼               ▼
     递归调 fixRedRed  x 是左孩子吗？   x 是左孩子吗？
     （祖父为红再修）    是 ───┴─── 否   是 ───┴─── 否
                        ▼      ▼        ▼      ▼
                       左左    左右     右左     右右
                     祖右旋  父左旋+  父右旋+  祖左旋
                            祖右旋  祖左旋
```

红黑树的插入代码到此就全部实现完毕了。前面那两种简单情况能收工就收工，只有叔叔是黑色这一支才需要动用旋转；而真正需要递归的，说到底也只有 case3 那一支——因为只有它把祖父染成红色之后，才可能把红红相邻往上"传染"一节。

> **承前启后**：上一节讲完「红黑树的插入：顺着 k 找空位，再修红红相邻」，下一节接着讲「红黑树删除：节点摘掉之后，那少掉的一个黑色怎么办」。

## 红黑树删除：节点摘掉之后，那少掉的一个黑色怎么办
> 对应块：BLK52 | 覆盖分集：P195-P197 | 块标题（分集名）：《基础算法-150-红黑树-remove-case》

插入的红黑树大家应该都写过了，删除才是真正磨人的那一个。

插入你只需要往上走一路，遇到红叔父就换色换叔父，遇到红叔叔就旋转，简单得很。删除不一样——删一个节点本身其实也不难，无非就是让孩子顶上、或者拿后继来顶。真正让人抓狂的是：**你把它摘掉了，摘完那一瞬间整棵树的黑高就不对了**，这时候你得想办法把欠掉的黑色还回去。

所以我们这一讲的主线，其实就是两件事：先把节点"摘下来"，再把"欠掉的黑"还上。摘节点这件事，靠一个叫李代桃僵的技巧能把四种情况砍到两种；还黑这件事，则要看兄弟和侄子的颜色，分出 case 3、4、5。

这一讲我们先把 case 0、case 1、case 2 和 case 3 讲完，4 和 5 就在 `fixDoubleBlack` 这个方法里继续往下写。

> **结论**：删黑色节点要考虑平衡，删红色节点不需要考虑平衡。整个删除调整的全部复杂度，都来自"删的是黑"这一件事。

---

### 先把两个备件准备好

删除要用到两个方法，我们提前写好，待会儿反复调。

#### find：按 key 找到要删的那个节点

这个太熟了，就是 BST 的标准查找。从 `root` 出发，指针 `p` 一路往下走：比当前小就往左，比当前大就往右，相等就返回当前节点。一路走到 `p == null` 还没撞上，说明这棵树里压根没这个 key，返回 null，主流程直接 return，连后面的逻辑都不用进。

```java
private Node find(int k) {
    Node p = root;
    while (p != null) {
        if (k < p.k) {
            p = p.left;
        } else if (k > p.k) {
            p = p.right;
        } else {
            return p;
        }
    }
    return null;
}
```

#### findReplaced：找到"删剩下"的那个节点

第二个方法叫 `findReplaced`，参数就是刚才 `find` 出来的 `deleted`，返回"删剩下"的那个节点——也就是将来要顶到 `deleted` 位置上来的那位。

这个东西我们前面讨论过，就三种情况。我拿这棵树来对照着看：

```text
              5
            /   \
           3     7
          /     /
         2     6
        /
       1
```

- 删 **1**：没有孩子，删剩下的是 `none`。
- 删 **2**：只有一个孩子（1），删剩下的是 **1**。
- 删 **5**：有两个孩子，那删剩下的是谁？这就得找它的**后继节点**了。从 5 的右子树出发一路向左走到头——后继是 **6**。将来就是把 6 搬到 5 的位置上去。

对应到代码，就是三分支加一个后继查找：

```java
private Node findReplaced(Node deleted) {
    // 没有孩子：删剩下的是 null
    if (deleted.left == null && deleted.right == null) {
        return null;
    }
    // 只有一个孩子：左空剩右，右空剩左
    if (deleted.left == null) {
        return deleted.right;
    }
    if (deleted.right == null) {
        return deleted.left;
    }
    // 有两个孩子：去右子树里找后继，也就是右子树中最左边的节点
    Node s = deleted.right;
    while (s.left != null) {
        s = s.left;
    }
    return s;
}
```

> **提示**：为什么上面两个 `if` 不用写"恰好有一个孩子"？因为能执行到那儿，说明前面已经排除了没有孩子的情况，此时至少有一个孩子；两个分支各测一个方向，走不到"都有孩子"那一步。所以第二个 `if` 里直接判 `deleted.right == null` 是安全的。

这两类方法我们都能加上 `private`，我刚才是懒得加了。

### doRemove 的骨架：先搭架子，再逐个填

主入口 `remove(k)` 很简单：先 `find` 拿到 `deleted`，为 null 就直接返回；不为 null 就交给一个递归方法 `doRemove(deleted)` 去做真正的删除。为什么要递归？因为 case 0 那里会把自己转化成更简单的情况再递归一次。

`doRemove` 一上来先 `Node replaced = findReplaced(deleted);`，然后就三个分支：

```text
                  doRemove(deleted)
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
 replaced == null   left==null 或       都不是
 （没有孩子）        right==null
        │            （有一个孩子）          │
        ▼                 │                 ▼
   处理完 return     处理完 return    键值交换后递归
                                          doRemove(replaced)
```

看这张图就明白为什么这套架子撑得起来：**两个孩子的情况自己不会去摘节点，它只负责把自己降级**——交换键值之后递归到 `replaced` 上，而 `replaced` 作为后继，一定是"没有孩子"或者"只有一个孩子"。所以真正干活的永远只有前两个分支。

我们先把架子写出来，注释留好：

```java
private void doRemove(Node deleted) {
    Node replaced = findReplaced(deleted);

    if (replaced == null) {
        // 没有孩子
        // ……
        return;
    } else if (deleted.left == null || deleted.right == null) {
        // 只有一个孩子
        // ……
        return;
    } else {
        // 有两个孩子
        // ……
    }
}
```

先别急着填，待会儿一个一个来。

### case 0：李代桃僵，把"两个孩子的删除"降级

我们先处理看起来最麻烦的那个——**要删的节点有两个孩子**。我拿上面的树举例，比如删 5。

以前我们的做法是：找到后继 6，把 6 的"后事"处理干净，然后让 6 上位去占据 5 的位置——也就是让 6 的 `left` 指向 3、`right` 指向 7，把 5 从树里剥掉。

今天换一种思路，我把它叫做**李代桃僵**。

什么意思呢？删 5 的时候，其实**5 这个对象根本没被删掉**，真正被删掉的是它的后继节点。怎么做？看这张图：

```text
        李代桃僵之前                 交换键值之后

             5                            6
           /   \                        /   \
          3     7                      3     7
         /     /      5 ⇄ 6         /     /
        2     6      ───────▶       2     7
       /                            /
      1                            1
```

第一步用 `find` 找到待删节点 5，再用 `findReplaced` 找到后继 6，然后把这两个节点的**键和值**整个交换过来：5 的键值给到 6，6 的键值给到 5。

请注意交换之后发生了什么、没发生什么：这两个**节点对象的 `left`、`right` 属性一点没变，颜色也一点没变**。变的只是 `k` 和 `value`。所以 6 现在站在 5 的位置上、挂着 3 和 7，而原来那个位置上的对象现在装的是 6 的键值。

接下来才是关键的一句：**我接下来要删的，不是上面那个 6 了，我要删的是下面这个 5。**

于是 `doRemove(replaced)`，把 `replaced` 当成新的删除对象递归下去。

写成代码就是这样，先用临时变量中转一下，`value` 是 Object 类型，也照换不误：

```java
// 交换键
Node t = deleted;
deleted.k = replaced.k;
replaced.k = t.k;

// 交换值
Object v = deleted.value;
deleted.value = replaced.value;
replaced.value = v;

// 现在要删的是 replaced，不是 deleted
doRemove(replaced);
```

> **易错点**：交换的是 `k` 和 `value`，**不是节点引用**。你要是写成 `Node t = deleted; deleted = replaced; replaced = t;` 就全乱了——那等于把两个对象的位置对调，父子指针全断。

这招好处在哪？原来要删的节点有左右两个孩子，一变换，要删的节点就**没有孩子了**（也可能还剩一个，那是另一种情况）。接下来直接走上面那两个 if 分支就完事了，**根本走不到"有两个孩子"那个分支**。复杂问题瞬间被简化掉。

至于 case 0 的几种演示，我们放到后面再看——它们总是伴随着其他几种情况一起出现，拆开看没意思。

---

### case 1：根节点与非根节点，分开看

#### 被删的是根节点

最简单的一种：根节点没有孩子，一个孤零零的根，直接 `root = null`，整棵树清空。

另一种是根节点只有一个孩子。这一种我要先问你一个问题：**根节点有两个孩子的情况，需要考虑吗？**

不需要。为什么？因为它最终会被李代桃僵转换成"有一个孩子"或者"没有孩子"，已经归到前面那一档去了。

那我再问：**根节点有可能只有一个孩子，但这个孩子是黑色的吗？**

也不可能。有一个黑孩子意味着什么？意味着黑高立刻不平衡。而删除之前的树是平衡的，所以根节点如果只有一个孩子，那**只有一种可能：这个孩子是红的**。

想通这一点之后，删除就极其简单了，还是李代桃僵：我不真把根节点删掉，而是让**孩子顶上来**——把孩子的键和值复制到根节点上，再把这个孩子置为 null。实际删的是那个孩子，根节点本身活着，颜色还是黑色，平衡性一点不用调整。

```text
       删除前                 复制键值后              处理完

          5          ──────▶         5        ──────▶      5
         /                          /                      /
        6                          6                      null
```

> **易错点**：置空的时候**不用管它是左孩子还是右孩子**，把根节点的 `left` 和 `right` 都置为 null 就行，反正它就这一个孩子。

#### 被删的不是根节点

接下来两种就好理解了，都是普通操作，我们先不管删除之后的平衡调整，只看节点本身怎么摘。

**没有孩子**（也就是叶子）：找到它的父亲，判断它是父亲的左孩子还是右孩子，把对应那一侧置 null 就行了。删 1 就是它父亲的 `left = null`；删 3 就是它父亲的 `right = null`。

**只有一个孩子**：让这个孩子直接顶上来顶掉父亲的位置——如果 `deleted` 是父亲左孩子，就 `parent.left = replaced`；否则 `parent.right = replaced`。

```text
         删除前                  删除后

           4          ──────▶      4
          / \                    /
         2   5                  1
        /     \
       1       3
```

（图中删的是 2，它不是根节点且只有一个孩子 1，所以 1 直接顶到 4 的左边。）

> **易错点**：孩子顶上去之后，别忘了孩子自己的 `parent` 也要跟着改。图里 1 原来的 `parent` 是 2，现在它成了 4 的左孩子，`parent` 必须改成 4。`replaced.parent = parent;` 这一句不能少。

> **提示**：父子关系是**双向**的，所以这些置空操作其实是"帮 GC 的一行代码"——被删节点的 `left`、`right`、`parent` 全部置为 null，它就不引用任何其他对象了，将来垃圾回收的时候不会有人说"还有人引用着你"，所以回收不掉。

到这里，case 1 的四种情况就写完了。别忘了"被删的不是根节点且有两个孩子"这种——不用考虑，李代桃僵已经把它转走了。

---

### 判断失衡：删黑必失衡，删红不用管

节点摘完了，该看平衡了。先想一个问题：**我怎么知道删掉这个节点之后树就不平衡了？**

看例子。比如删的是 1 这个节点——我一眼就看出来它肯定会导致整棵树失衡。**为什么？因为它是黑色的。**

你想，删掉一个黑色节点，意味着**从根到它这条路径上的黑色数目少了一个**。既然少了一个，规则就被破坏了。当然有补救办法——让它的兄弟变成红色、父亲变成黑色，这样被删掉的黑色就从另一条路径上"补"回来了，各条路径的黑高又相等了。（这只是我先给个直觉，调整的细节我们还没讲到，别着急。）

所以：**只要删的是黑节点，你就必须考虑平衡调整；删红节点，不需要。**

删红色节点为什么没事？因为它压根不参与黑高计数。比如树里那个红色的 3，我删了就删了，不需要变色，不需要旋转，其他节点全部保持原样：

```text
          4(B)                4(B)
         /    \              /    \
      2(R)    5(B)        2(R)    5(B)
      /       /            /       /
   1(B)    3(R)         1(B)    null
```

有同学会问：**那如果我要删的是中间那种有孩子的红节点呢？**

答案是：这种红节点最终**一定**会被转换成 case 0。因为红节点如果有孩子的话，它只能有两个黑孩子（红节点不能有红孩子，否则红红相邻；也不能只有一个黑孩子，那就不平衡了——所以它要么没孩子，要么就是两个黑孩子）。有两个孩子就会走李代桃僵，然后去找后继、把键值交换——注意，这时候真正被删掉的已经不是那个红节点了，而是它的后继，一个黑节点。

所以**中间位置的红节点删除，我们根本不用单独考虑**，我们只需要考虑叶子位置那个红色节点的删除，而它不会影响平衡。

---

### case 2：删黑剩红，一行染色搞定

黑色节点里有一种**特别简单**的情况，我们先把它摘出来，免得待会儿被复杂情况淹没。

情况是这样的：**要删的是黑节点，而删剩下的是个红节点**。

比如我要删 2，它俩是黑色的；那将来谁是删剩下的？是 3。删黑剩红，就进 case 2 了。

怎么处理？很简单。删黑节点，意味着这条路径上少了一个黑；但是剩下的这个红节点，**你把它的颜色改成黑色**，不就正好在原来少黑的那条路径上补上一个黑了吗？

一句话：**把 `replaced` 的 `color` 改成 `BLACK`，完事。**

代码上就是在"没有孩子"和"只有一个孩子"这两个分支里各加一个判断：

```java
// 没有孩子的情况
if (deleted.isBlack()) {
    // 黑色叶子要调用复杂调整
    fixDoubleBlack(deleted);
}
// 否则就是红色叶子，删就删了，什么都不用做

// 有一个孩子的情况
if (deleted.isBlack() && replaced.isBlack()) {
    fixDoubleBlack(replaced);
} else {
    // 否则就是 case 2：删的是黑，剩的是红
    replaced.color = BLACK;
}
```

上面两处"复杂调整"其实都是调同一个方法 `fixDoubleBlack`，我们等下就说它为什么叫这个名字。

> **提示**：如果你的 IDE 在 `deleted.isBlack()` 那里报了个"可能空指针"的警告，不用管，那是误判——能执行到那个分支，说明 `deleted` 一定非空。

---

### 双黑：不是多了个黑，是欠了一个黑，而且补不回来

刚才冒出来一个新名词——**双黑**。先把这个概念掰正，不然名字会把你带沟里去。

有些同学一看见"双黑"就以为：双黑嘛，是不是多了一个黑色？**不是，恰好跟你想的相反——它是少了一个黑色，而且少的这个黑没办法直接补齐。**

对照一下就清楚了。case 2 里删的是黑节点不假，但人家剩下的是个**红**节点，红节点一变色就补上了，所以 case 2 并不算"少一个黑"。

可要是删的和剩下的**都是黑色**呢？删除那个黑色已经没了；剩下的这个，它原来就是黑的，你**不能让它变红**（那不就把问题原样留下、还多欠了一个吗）。所以整条路径上就是实打实少了一个黑——**这个才叫双黑**。

> **定义**：**双黑**不是说有两个黑节点，而是指"删除节点与剩余节点都是黑色"造成的、整条路径上因为少了一个黑色而触发的不平衡。方法名 `fixDoubleBlack` 里的 "double black"，修的正是这个"欠账"。

那要怎么修？接下来引出 case 3、4、5 三种情形。

> **易错点**：双黑跟 case 2 的差别只在一个字上——**case 2 是删黑剩红，剩下的能染色补上；双黑是删黑剩黑，剩下的动不了**。这两个名字挨着，千万别记混。

### 两处调用，顺序正好相反

先把这个坑填了，不然待会儿容易混。`fixDoubleBlack` 一共就两个调用点，但**调用位置和传的参数都不一样**，而且顺序是相反的：

| 场景 | 顺序 | 传给 `fixDoubleBlack` 的参数 |
| --- | --- | --- |
| 没有孩子 | **先调整平衡**，再把节点摘掉 | `deleted` |
| 有一个孩子 | **先真正删除**（`replaced` 顶上），再调整平衡 | `replaced` |

```text
   没有孩子                          有一个孩子

  fixDoubleBlack(deleted)           replaced 顶上来
            ↓                              ↓
     再把 deleted 摘掉            fixDoubleBlack(replaced)
```

> **易错点**：这个顺序**一定要搞清楚**。没有孩子时你还没动结构，所以拿 `deleted` 去调；有一个孩子时结构已经变了，`deleted` 已经不在树里了，这时候能代表"欠了一个黑"的位置是顶上来的 `replaced`，所以传 `replaced`。

---

### case 3：兄弟是红的，先给你过渡成四或五

`fixDoubleBlack(x)` 里的这三种情况，全都是**看兄弟的颜色**。`x` 就是被调整的节点，它可能是删除节点，也可能是删剩下的那个节点，反正触发双黑的时候它是黑的。

- 兄弟是红色 → case 3；
- 兄弟是黑色 → 还得看侄子（兄弟的左、右孩子）的颜色，两个侄子颜色不一样，处理方式也不同 → case 4 和 case 5。

先看 case 3。

#### case 3 是一个"过渡情况"

case 3 不能直接恢复平衡，它得**先把自身转换成 case 4 或 case 5**，然后再继续往下调。所以它是一个过渡性的调整。

来看这个例子，我要删的是 **4**：

```text
          6
         / \
        4   8
           /
          7
```

4 的兄弟是 8，8 是红色的——符合 case 3。而且前面推导过，红兄弟的两个侄子一定是黑孩子，所以 7 必须是黑色，这个条件天然满足。

怎么把 case 3 调成 4 或 5？**一次左旋就够了**。我从 4 的父亲 6 这里来一次左旋：

```text
       旋转前                      左旋 6 之后

          6                             8
         / \                           / \
        4   8                         6   …
           /            ──────▶       / \
          7                           4   7
```

看一下结果：6 旋下去，8 旋上来，它原来的侄子 7 换了个爹（成了 6 的右孩子）。

**旋转完，4 的新兄弟变成了 7**——也就是它原来的侄子。而我们早就知道，红兄弟的侄子一定是黑的。所以新兄弟是黑色，这正是 case 4 和 case 5 所期待的形态。这一步是个挺巧的小技巧。

但事情还没完：**旋完之后这棵树失衡了。** 注意 4 这时候根本还没被删掉呢，所以我们必须先让它恢复平衡，再去进 case 4 或 5。

怎么恢复？回忆旋转之前的状态：**6 是黑的，8 是红的，那时候是平衡的**。那旋转之后，让它们**换个颜色**就行——8 变黑，6 变红：

```text
   旋转后                       父与旧兄弟换色之后

       8                              8(B)
      / \                            /   \
     6   …                         6(R)  …
    / \                            /  \
   4   7        ──────▶         4(B) 7(B)
```

一棵子树做旋转+换色，黑高整体是不变的，所以换完色它又是平衡的了。现在在这个重新平衡的基础上，去匹配 case 4：新兄弟 7 是黑的，两个侄子都没有（也可以看成黑），正好落到 case 4。

那如果本来是 case 5 呢？做法类似，我这里没直接写出来，只要给这个兄弟加个孩子就会落到五去。比如给 7 加个左孩子 **6.5**——6.5 比 6 大、比 7 小，位置合法，而且是红的。再旋转一次、再换一次色：

```text
        6                             8(B)
       / \                           /   \
      4   8          ──────▶       6(R)  …
     / \                            /  \
    7   …                        4(B) 7(B)
   /                                 /
 6.5                               6.5(R)
```

这次 4 的兄弟是黑的 7，而侄子 6.5 是红的——**匹配到 case 5**。

所以结论就是：**case 3 经过"旋转 + 换色"这两步，一定能被调整成 case 4 或 case 5。**

#### 把 case 3 写成代码

我们先把 case 3 的代码写完，不然待会儿 4 和 5 的代码堆上来，就不好写了。

递归方法里的参数我们简化为 `x`，它代表**被调整的节点**——可能是删除节点，也可能是剩余节点。

先写终止条件。这个方法内部还会递归调用自己，所以：**当 `x == root` 时，说明已经调整到整棵树的顶部了**，平衡自然恢复（黑高本来就要求各条路径相等，只要一路补到了根，就没得欠了），直接 return。

没到顶，就准备 3、4、5 的处理。先把用得上的两个变量准备好：`parent` 是 `x.parent`，也就是被调整节点的父亲；兄弟的英文叫 `sibling`，前面我们已经专门写过这个方法，直接调 `x.sibling()` 就能拿到（忘了的同学回去翻一下）。

```java
private void fixDoubleBlack(Node x) {
    // 已经调整到树的顶部，问题自然解决
    if (x == root) {
        return;
    }

    Node parent = x.parent;
    Node sibling = x.sibling();

    if (sibling.isRed()) {
        // case 3：兄弟是红的
        // 被调整节点是左孩子，就对父亲左旋；是右孩子，就对父亲右旋，完全对称
        if (x.isLeftChild()) {
            leftRotate(parent);
        } else {
            rightRotate(parent);
        }

        // 换色：让整棵树暂时重新平衡
        // 父亲的颜色取兄弟的颜色（原来是黑，兄弟是红 → 父亲变红）
        parent.color = sibling.color;
        // 原来的兄弟变黑
        sibling.color = BLACK;

        // 此时 x 的新兄弟已经是黑色了，再递归一次就能进入 case 4 / 5
        fixDoubleBlack(x);
        return;
    }
}
```

> **提示**：`parent.color = sibling.color;` 这一句看着绕，其实就是"父亲和兄弟换色"。因为我们已经判定过兄弟是红色，而红红相邻是不允许的，所以父亲在旋转之前必定是黑色——写它自己的颜色（红）也一样，但取兄弟的颜色在语义上更直白，就是字面意义上的"互换"。

> **易错点**：别忘了最后那行 `fixDoubleBlack(x)`。旋转换色之后只是**过渡**完了，还欠着一个黑没还呢；不递归走一次 case 4 / 5，这个双黑就留在树里了。递归传的参数还是 `x`——此时 `x` 的兄弟已经是黑色，方法会自然落到 4 或 5 上。

到这里 case 3 就写完了。case 4 和 case 5 就写在这个方法的后面，等兄弟是黑的时候再看侄子的颜色。往下走之前，我再把整个删除流程串一遍：入口 `remove(k)` 用 `find` 定位、`findReplaced` 找备件、`doRemove` 按三种情况摘节点，摘的过程中黑叶子走 `fixDoubleBlack`，黑剩红走一行染色，其余交给递归和旋转换色——一条线就这么下来了。

> **承前启后**：上一节讲完「红黑树删除：节点摘掉之后，那少掉的一个黑色怎么办」，下一节接着讲「红黑树删除的最后一段路：case 4、case 5 与六种情况全景」。

## 红黑树删除的最后一段路：case 4、case 5 与六种情况全景
> 对应块：BLK53 | 覆盖分集：P198-P200 | 块标题（分集名）：《基础算法-153-红黑树-remove-case》

删掉一个黑色节点，路径上就少了一个黑，这就是我们前面一直说的"双黑"。补这个洞的办法其实只有两种：**变色**或者**旋转**。前面几种情况基本都能靠变色摆平；从 case 4 开始，变色开始不够用了，旋转要正式登场。

这一段我们就把这两块啃完——case 4 是纯变色，case 5 必须上旋转。规则看着多，但你真去理它，会发现它非常有规律。

先别急着背，我们直接拿几棵树来感觉一下。

### case 4：兄弟和两个侄子全是黑的

> **定义**：case 4（也叫 K4）——被调整节点已经触发了双黑，它的**兄弟是黑色**，并且**兄弟的两个孩子（也就是两个侄子）也都是黑色**。

注意"侄子是黑色"这句话里的坑：`nil`（空节点）我们一直认为它是黑色的。所以哪怕兄弟的两个孩子都是 `nil`，它照样算命中 case 4。

> **提示**：判断"是不是黑色"，一定要把 `nil` 一起算进去。这是红黑树里最容易漏掉的一条。

#### 第一个例子：删 3

```text
          5(黑)
        /      \
     3(黑)    7(黑)
     ↓ 待删
```

删除 3，路径上的黑色少了一个，触发双黑。我们来看 3 的兄弟：7 是黑色的，7 的两个孩子是 `nil`，`nil` 也算黑色——三条全中，命中 case 4。

那怎么调整呢？我先不看文字上的解法，你就自己想一想：**能不能只靠变色把它恢复黑色平衡？**

能。我这边将来要少一个黑色，那我让右边这条路径也少一个黑色，不就扯平了？7 是黑的，我只要让 **7 变成红色**，黑色高度两边就同步减了一。

```text
          5(黑)
             \
            7(红)     ← 3 落地
```

这样 3 被删掉，整棵树仍然是平衡的。就这么简单，一个字都不用旋转。

#### 第二个例子：删 1，父亲是红色

```text
             8(黑)
           /      \
        2(红)     11(黑)
       /    \
    1(黑)   3(黑)
     ↓ 待删
```

还是老规矩：删 1 触发双黑，兄弟 3 是黑的，两个侄子也是黑的（`nil`），命中 case 4。于是把 3 变红。

但这里要停一下：子树 `{1,2,3}` 这一块确实黑色平衡了，可 **1 和 3 这两条路径，比其他路径少了一个黑**。怎么办？

还好它有个爹——2 是红色的。我把红色的 2 变成黑色，不就把 `1→2→3` 这两条路径缺的黑色补齐了吗？

```text
             8(黑)
           /      \
        2(黑)     11(黑)
            \
            3(红)
```

> **结论**：case 4 里只要**父亲是红的**，事情当场就结束——兄弟变红、父亲变黑，两步搞定，绝不能多转一步。

#### 第三个例子：删 1，父亲也是黑的

先说明一下，这种**全黑**的树在红黑树的世界里是可能出现的。正常情况下，一层、两层、三层的全黑红黑树都会出现。像这种四层的全黑红黑树，那是我故意造出来的，正常增删一般不会碰到——但它合法，所以我们照样要能处理。

```text
                    8(黑)
                /          \
            4(黑)          12(黑)      ← 右半边同层同色，图上略
          /      \          …
      2(黑)    6(黑)
      /   \     /   \
     1     3   5     7             ← 第 4 层也全是黑点
     ↑
    待删除
```

还是删 1。老办法：兄弟变红，两边各少一个黑。但这次父亲 **2 已经是黑色**了，你没办法把一个"多余的红色"变黑来让这条路径的黑色总数不变。

怎么办？**把父亲 2 当成新的被调整节点，让它再次触发双黑，向上一层递归处理**。

```text
删 1 → 双黑
   └ 兄弟 3 黑、两个侄黑 ⇒ case 4 ⇒ 3 变红
        └ 1、3 两条路径各少一个黑，父亲 2 已是黑，没法红变黑补齐
             └ 以「2」为被调整节点 ⇒ 再次触发双黑
                  └ 2 的兄弟 6 黑、两个侄黑 ⇒ 又是 case 4 ⇒ 6 变红
                       └ 2、6 两条路径仍各少一个黑，父亲 4 已是黑
                            └ 再以「4」为被调整节点 ⇒ 双黑
                                 └ 4 的兄弟 12 黑、两个侄黑 ⇒ case 4 ⇒ 12 变红
                                      └ 整棵树恢复平衡，1 可以安全落地
```

一路递归上去，到根为止，中间任何一层只要撞上一个红色的父亲，递归就当场收工。

#### case 4 小结

> **结论**：case 4 的调整就两条规则——
> 第一步，**兄弟变红**，目的是让"删除节点那条路径"和"兄弟那条路径"的黑色高度同时减一；
> 然后看父亲：
> - 父亲是红 → **父亲变黑**，缺失的黑色就地补齐，结束；
> - 父亲是黑 → **把父亲当成被调整节点，递归往上处理**。

### case 4 写成代码：先给空指针挖个坑

我们把 case 4 实现一下。

这里有个前提要交代清楚：代码能执行到 case 4，说明 case 3 已经处理完并且 `return` 了。case 3 的作用就是把红色的兄弟消化掉，所以走到这里，**兄弟一定是黑色的**，不用再判兄弟的颜色。

```java
// case 4：兄弟是黑色，并且两个侄子也都是黑色
if (sibling == null) {
    // 兄弟为空，直接访问 sibling.left / sibling.right 会 NPE
    // 没人可调整，就让父节点作为被调整节点，向上递归再次触发双黑
    balance(parent);
} else if (isBlack(sibling.left) && isBlack(sibling.right)) {
    // 命中 case 4
    sibling.color = RED;                // 兄弟变红，兄弟那条路径也少一个黑

    if (isRed(parent)) {
        parent.color = BLACK;           // 父红转黑，缺失的黑色就地补齐，收工
    } else {
        balance(parent);                // 父也是黑的，把债往上还，继续递归
    }
} else {
    // case 5：兄弟是黑色，但是侄子有红色的
    // ...
}
```

这里有两个细节一定要讲。

第一个是 `sibling == null`。判断两个侄子是不是黑色，第一步就是访问 `sibling.left`，可兄弟本身可能是个 `nil`——"兄弟是黑色"是**隐含**了它可能为 `null` 的。所以这一层必须先把空指针堵上，写法就是先判 `sibling` 非空，再去动它的底层孩子；万一真是 `null`，就走"让父节点去递归"那条路。

第二个是那个 `else`。你们想想：case 4 的条件是"两个侄子都黑"。那只要这个条件不成立，无非就是**侄子里有红的**——可能两个都红，也可能只有一个红——这些全都掉进 `else`，那就是 case 5。所以 case 5 的判断根本不用单独再写，`else` 一把兜住就行。

```java
} else {
    // case 5：兄弟是黑色，但是侄子有红色的
    // 左左 / 左右 / 右右 / 右左，四种不平衡
}
```

顺便说一句：我调试的时候虽然把 `sibling == null` 这个分支写出来了，但印象里**在真正触发双黑的删除场景里，好像一直没走到过**。是不是真的走不到，我不敢打包票，所以这段代码我留着——你们自己下去测一测，看能不能把它逼出来。

> **易错点**：不要因为"好像走不到"就删掉空判断。防御性代码的价值就在这里：我没测出来，不等于它不存在。

### case 5：兄弟是黑的，可侄子里有红的

> **定义**：case 5——被调整节点的**兄弟是黑色**，并且**兄弟至少有一个孩子是红色的**。两个侄子都是红也行，那也算 case 5。

case 5 还能再往下拆成四种：兄弟在左边还是右边、红侄子在兄弟的左边还是右边，组合出**左左、左右、右右、右左**四种不平衡。我们只细讲左左和左右，右右和右左是对称的，不啰嗦。

#### 先别急着旋转：拿 case 4 的变色试试

老规矩，先自己想：case 5 能不能也靠变色解决？咱们老老实实按 case 4 的思路走一遍。

删 4，4 这条路径少一个黑，那就让兄弟那边也少一个——把兄弟 2 变红。然后父亲如果是红的，就变黑补齐。

```text
          3(红)
        /      \
     2(黑)    4(黑)  ← 删 4
     /
   1(红)
```

问题来了：**兄弟变红了，而兄弟本来就有个红孩子 1，红红相邻，违反规则 3**。所以 case 4 这套在 case 5 这里是走不通的。

> **结论**：变色解决不了的问题，就用旋转解决。红红相邻是 case 4 和 case 5 的分水岭。

#### 左左：围绕父节点右旋

看图就好判断了：待删除节点 4 的兄弟 2 是**左孩子**，而红侄子 1 也是**左侄子**——兄弟在左、红侄子在左，左左。所以围绕它的父节点 **3** 来一次右旋。

```text
右旋前                  右旋后（暂不染色）
          3(红)              1(红)
        /      \            /      \
     2(黑)    4(黑)      2(黑)    3(红)
     /                             \
   1(红)                            4(黑)
```

旋转完还要染色，目的很明确：**4 这条路径少了一个黑，我要把旋上来的 3 变黑来补**。所以规则是这样的：

- 旋上来的父节点（原 3）**变成黑色**——补齐 4 这条路径缺的黑；
- 原兄弟 2 **变成它原来父节点 3 的颜色**，也就是红色——3 下沉一层去了，位置得有人接，颜色也得跟着走；
- 红色的左侄子 1 **变成黑色**——它的父亲 2 换颜色了，作为 2 的孩子，它有义务把原本属于 2 的那个黑色补上。

```text
最终：3 变黑、1 变黑、2 变成父亲 3 的原色（红）
          1(黑)
        /      \
     2(红)    3(黑)
                \
                4(黑)  ← 现在删它，不影响黑色平衡
```

这样 4 再被删掉，整棵树依然是平衡的。

#### 对照一下：父亲是黑的也照样成立

刚才那个左左，旋转的父节点 3 是**红色**的。我们再做一个对照：结构一模一样，只是父节点 3 是**黑色**的，还是删 4，还是左左，还是围绕 3 右旋。

染色照旧：3 变黑——可它本来就是黑的，无所谓；2 变成父节点的颜色——父节点本来就是黑的，它也不用变；最后红色的侄子 1 旋转上去之后，**我们还是得把它变成黑色**。

```text
          1(黑)
        /      \
     2(黑)    3(黑)
                \
                4(黑)  ← 删掉它，树依然平衡
```

> **结论**：左左这套操作，**不管父亲是什么颜色**，"右旋 + 按规则染色"都能把黑色平衡保住。这就是旋转比变色强的地方——它对颜色的依赖被转嫁到了节点身份上，而不依赖父亲当下的颜色。

### 左左落到代码：变色的顺序不能反

左左的进入条件就两条：兄弟是左孩子，**并且**兄弟的左孩子是红色。

```java
// case 5.1  左左不平衡：兄弟是左孩子，且兄弟的左孩子是红色
if (sibling.isLeft() && isRed(sibling.left)) {
    // 变色：3、2、1 这样去变，实际执行顺序是先变 1，再变 2，最后变 3
    sibling.left.color = BLACK;         // ① 红色左侄子变黑，补齐缺失的黑色
    sibling.color = parent.color;       // ② 兄弟继承父节点原来的颜色
    parent.color = BLACK;               // ③ 父节点变黑
    rightRotate(parent);                // ④ 围绕父节点右旋
}
```

> **易错点**：染色顺序千万不能反，**绝对不能先动父节点**。因为第二步要写 `sibling.color = parent.color`——你要是先把 parent 变黑了，父节点原来是什么颜色就永远不知道了，第二步直接写错。记住这个口诀：**先侄子、再兄弟、最后父亲**。

### 左右：先把自己掰成左左

左右不平衡的情形是：兄弟是左孩子，但这回红色的是兄弟的**右**侄子。

```text
          3(红)
        /      \
     1(黑)    4(黑)  ← 删 4
        \
         2(红)
```

它的解决思路特别巧：**先把它变成左左**。也就是围绕兄弟 1 来一次左旋，1 旋转下去、2 旋转上来——旋转完红侄子就从右侄子变成了左侄子，形状直接归约成左左；接着按左左的办法，围绕父节点 3 再来一次右旋，3 旋转下去、2 旋转上来就行了。

```text
围绕兄弟左旋          再围绕父节点右旋
          3(红)              2(红)
        /      \            /      \
     2(红)    4(黑)      1(黑)    3(红)
     /                             \
   1(黑)                            4(黑)
```

染色的思路要从根上想：**4 这边少一个黑**，所以旋上来的父节点必须变黑；**2 将来要取代父节点 3 的位置**，原来 3 是什么颜色，2 就是什么颜色；而 **1 旋转之前是兄弟，兄弟是黑的，旋转之后颜色不用变**，还是黑的（你要硬写一句 `setColor(BLACK)` 也行，无所谓）。

```java
// case 5.2  左右不平衡：兄弟是左孩子，但红色的是兄弟的右孩子
else if (sibling.isLeft() && isRed(sibling.right)) {
    sibling.right.color = parent.color; // 变色必须写在左旋之前
    leftRotate(sibling);                // 先把自己掰成左左
    rightRotate(parent);                // 再按左左处理
}
```

> **易错点**：这里又有一个顺序坑，但方向和左左正好相反——**变色必须写在左旋之前**。为什么？因为我们写的是 `sibling.right`，它指向的是那个红色的右孩子。可左旋一做完，`sibling`（也就是节点 1）的右孩子**已经变成 `nil` 了**。这时候再去取 `sibling.right.color`，那就是 `None.color` 了，标准的空指针。旋转之前的 `sibling.right` 是能正确找到那个红孩子的，旋转之后就不能了。

最后再收个尾：不管左左、左右，**最后一步都是要把 `parent` 变成黑色**。右左、右右也一样。这行代码完全可以提取出来，放到所有分支的外层统一执行，不用每个分支各写一遍。

### 右左与右右，以及两个红侄子

右左和右右我代码里都已经补齐了，逻辑跟左左、左右完全对称，这部分我就不展开讲了，对应的测试页面你们可以自己去试。

倒是有一个大家特别关心的问题，值得专门说一下：**如果两个侄子都是红的呢？**

```text
          4(黑)
        /      \
     2(黑)    5(黑)  ← 删 5
     /  \
   1(红) 3(红)
```

现在要删 5，兄弟是黑的，两个侄子都是红的。代码里是这么判断的：

- 它自然先走**左左**的逻辑，因为条件进的是第一个 `if`，而左边那个 1 正好就是红孩子；
- 但如果你**强行走左右**的逻辑——不看左边这个红孩子 1，只盯着右边这个红孩子 3 当成左右来处理，**行不行？**

行。而且这两种最终都能得到一棵平衡的树。

我们分别跑一遍。

按左左处理：以父节点 4 为轴右旋，2 旋转上去、4 旋转下来，3 换爹；然后原来的父亲 4 和左边这个红孩子 1 都变黑，兄弟 2 变成父亲 4 的颜色。

```text
旋转 + 染色之后
          2(黑)
        /      \
     1(黑)    4(黑)
              /  \
           3(红) 5(黑)  ← 可以安全删掉
```

按左右处理：先围绕兄弟 2 来一次左旋，再围绕父节点 4 来一次右旋；旋转完之后同样把 2 和 4 变成黑色，3 变成它原来父亲的颜色。

```text
旋转 + 染色之后
          3(黑)
        /      \
     2(黑)    4(黑)
                \
                5(黑)  ← 也可以安全删掉
```

两棵树形状稍有不同，但**都是平衡的**。

> **结论**：两个红侄子的时候你们不用担心。把它当成左左处理行，当成左右处理也行，得到的都是一棵平衡的红黑树。

当然，代码现在是左左优先级高的（`if` 写在 `else if` 前面）。要想让这个例子走左右分支，就得把左右那段 `else if` 提到上面来、左左降级到 `else if` 里——我刚才就是这么改的。改完记得保存，**网页上改了代码要刷新一下才生效**，这一步特别容易让人白等半天。

### 六种情况摊开来看

红黑树的删除我们讲完了。把六种情况放在一块，一次性看个清楚：

| 情形 | 触发条件 | 处理手法 |
| --- | --- | --- |
| 第一种 | 删除节点有两个孩子 | **李代桃僵**：找它的后继节点，把两个的值交换，退化成一个孩子或没有孩子，把问题简化掉 |
| case 1 | 删的是根节点 | 最简单：没有剩余就直接置成 `nil`，`root` 指向 `nil`；有剩余就用剩余的键值替换掉原来根节点的值，再把根节点剩下的那个孩子置成 `nil` |
| case 2 | 删的是黑，剩下的却是红 | 也简单：剩下的这个红正好能补足缺的黑，只要把它变成黑就能恢复平衡 |
| case 3 | 双黑，兄弟是红色 | **过渡情况**：通过一次旋转，把它转化成 case 4 或 case 5 之一 |
| case 4 | 双黑，兄弟是黑、两个侄子也是黑 | **纯变色**：兄弟变红；父亲红则父亲变黑收工，父亲黑则把父亲当被调整节点递归 |
| case 5 | 双黑，兄弟是黑、至少一个侄子红 | **变色 + 旋转**：细分为左左、左右、右右、右左四种不平衡 |

你把这条路捋一遍就会发现，前两种是"简化问题"，case 3 是"搭桥过河"，case 4、case 5 才是真正干活的。而且 case 4 和 case 5 的判断条件是互斥的——**侄子全黑走 case 4，有红侄子走 case 5**，一个 `if / else` 就分完了。旋转也只是在 case 5 里才登场，而且只有四种固定姿势。

所以整个删除过程看着复杂，其实很有规律。

### 上手演练：把几个组合例子跑一遍

光看规则还是虚，我们再跑几个组合例子，把这六种规则串一串。

#### case 3 过后紧接着撞上 case 4

这是一个 case 3 和 case 4 组合的例子。我们删除 4，它匹配到 case 3——删除节点的兄弟是个红色。

case 3 怎么处理来着？通过一次旋转，把它变成 case 4 或者 case 5。删除的 4 是左孩子，那就围绕父亲来一次**左旋**。旋完之后把 **6 和 8 的颜色互换**一下，让它**暂时恢复平衡**——这是 case 3 的全部工作，做完就 `return` 了。

接下来才是重头戏：现在匹配的是 case 4 还是 case 5？显然是 case 4——我们被删除节点的新兄弟已经是黑色的，并且它的两个侄子也都是黑色的（`nil` 也算黑）。

case 4 很简单，只要变色：将来 4 要被删掉，它这条路径少一个黑，那兄弟那条路径也得跟着少一个黑，把兄弟变红。变红之后整个子树里的路径都比别人少一个黑，能不能补齐？能——**因为它的父亲是个红色**，把父亲变成黑色，就把 4 和 7 这两条路径里缺少的那颗黑补齐了。

这时候 4 就可以安全地删掉了。

```text
删除 4 → 双黑
   ├─ 4 的兄弟是红色 ⇒ case 3（过渡）
   │     4 是左孩子 ⇒ 围绕父节点左旋
   │     旋转后把 6、8 的颜色互换 ⇒ 暂时恢复平衡
   └─ 新的兄弟已是黑色、两个侄子也是黑色 ⇒ case 4
         兄弟变红 ⇒ 4、7 两条路径各少一个黑
         父亲是红色 ⇒ 父亲变黑，缺的黑色补齐
         ⇒ 4 可以安全删除
```

#### case 4 递归上去，撞上 case 5

这是一个 case 4 和 case 5 组合的例子。删除 7，兄弟是黑的，两个侄子也看成黑的，匹配到 case 4。

case 4 只需要变色：这边少一个黑，兄弟也变红少一个黑，于是 **7 和 9 这两条路径都少了一个黑**。那还得找个黑色把这个洞补上。很遗憾，**这回它的父亲也是黑色的**，没有空闲的红色可以拿来补。

那就递归对父亲做一次双黑处理——认为父亲这边也少一个黑。那父亲匹配哪种情况呢？8 的兄弟 2 是黑色的，但注意看，8 这一边有一个**红色的侄子 4**，所以匹配到了 case 5。

case 5 的哪一种？8 的兄弟 2 是**左**孩子，这个红侄子 4 是**右**孩子，所以是**左右不平衡**。那就先围绕兄弟 2 来一次左旋，再围绕父亲 6 来一次右旋，中间那点变色就不细看了。

```text
删除 7 → 双黑
   ├─ 兄弟黑、两侄黑 ⇒ case 4 ⇒ 兄弟变红
   │     └─ 7、9 两条路径各少一个黑，父亲却是黑的
   │          ⇒ 把父节点（8）当作被调整节点，递归做双黑处理
   └─ 对 8 做双黑：兄弟 2 是黑的，但有一个红色侄子 4 ⇒ case 5
         └─ 兄弟在左、红侄子在右 ⇒ 左右不平衡
               先围绕兄弟 2 左旋，再围绕父节点 6 右旋
         ⇒ 7 可以被正确删除，根节点最终肯定是黑色的
```

#### 先李代桃僵，再进 case 4

最后三个例子都是"先李代桃僵，再进 case 4"，但结果各不相同。

第一个，删除 7。7 有两个孩子，所以先找它的后继节点 8，把 8 和 7 的值交换一下。原来我要删的那个红节点，现在变成了删这个黑色的叶子 7，简单了。现在匹配到 case 4（兄弟黑、孩子也黑），把兄弟变红，6 和 7 这两条路径都少一个黑——**好在父亲是个红色**，把 8 变成黑色，缺的黑就补上了，7 可以安全删除。

第二个，还是删 7，但这回是那棵全黑的树。同样先找后继交换，交换完重新删除一次。此时匹配到 case 4，兄弟变红之后整棵树少了一个黑，可是父亲已经是黑色的了——父亲这边**再触发一次双黑**。看父亲的兄弟：黑的，两个侄子也黑的，又是 case 4，于是**把父亲的兄弟 3 再变成红色**，整棵树就平衡了，然后把 7 删掉。

第三个，删除 2。2 有两个孩子，找后继找到 3，交换完键值，2 就从"有两个孩子"变成了"没有孩子"，简单了。这是情况四：二的兄弟是黑的、两个侄子也是黑的，所以兄弟变个色；然后父亲恰好也是红色，从红变黑，把缺失的黑色补齐，2 就能被安全删除了。

### 收个尾

红黑树的删除看着复杂，但你把它理清楚，会发现它比想象中容易得多——无非就是"这条路少了一个黑"和"怎么把这个黑补回去"这两件事，补的方式无非变色和旋转，旋转的姿势无非那四种。
