### 第一个算法，从一个查找需求说起

正式开始第一个算法：二分查找。

需求很简单——我想在一个有序数组 a 中去查找一个值 target。如果找到了，就返回这个值的索引位置；如果找不到呢？返回一个 -1。

为什么找不到返回 -1？因为如果成功找到，返回的位置肯定都是大于等于 0 的数；返回一个负数，就表示没有成功。这样成功的情况和失败的情况就被清晰地区分开了。

要解决这个问题，我们有多种做法、多种算法，而二分查找就是其中比较优秀的一种。

### 算法成立的前提：有序，而且允许重复

二分查找有它的前提：**给定一个内含 N 个元素的有序数组 a，以及要查找的值 target。**

注意，这个数组必须是有序的，而且条件写得很具体：数组内的元素保证升序——下标 0 的元素小于等于下标 1 的元素，下标 1 的小于等于下标 2 的，以此类推，直到下标 N-2 的小于等于下标 N-1 的，也就是由小到大排列，这称之为升序排列。

这里有个特别容易忽略的点：条件是“小于等于”，不是“小于”。也就是说，数组内是允许两个元素相等的，允许出现重复元素。重复元素二分查找也能够处理，不过这个我们放到后面再说。

我课上用的例子是一个 8 个元素的升序数组，下标从 0 到 7，其中下标 3 上的元素是 30——它正好是首轮查找会取到的中间值。

> **提示**：target 是每次查找都可以换的。同一个数组，接下来我们要分别找 14、找 38，再找一个根本不在数组里的 25，把三种结果都走一遍。

### 两个指针圈出的搜索范围

算法的第一步，是设置两个指针 i 和 j：i 一开始指向索引 0，j 一开始指向索引 N-1。

```text
      +----+----+----+----+----+----+----+----+
下标  |  0 |  1 |  2 |  3 |  4 |  5 |  6 |  7 |
      +----+----+----+----+----+----+----+----+
      | A0 | A1 | A2 | 30 | A4 | A5 | A6 | A7 |
      +----+----+----+----+----+----+----+----+
         ^                                  ^
         i                              j = N - 1
```

读图：两个指针像两只手一样，从数组的两头往中间夹，把当前还可能有答案的那一段夹在中间。左边是 i，右边是 j。

这两个指针其实就确定了算法的搜索范围：一开始这个范围涵盖了整个数组，从数组开头一直到数组结尾。随着算法逐步推进，i 会向右移动、j 会向左移动，这个范围就越来越小。

缩小范围的过程中，如果找到了元素，算法就结束了；如果没有找到，范围继续缩小。那缩小到什么程度为止呢？当 i 大于 j 的时候。i 都跑到 j 的右边了，就代表这个范围内没东西了，这时候查找也应该结束，这种情况就是没有找到，返回 -1 就可以了。那如果 i 还是小于等于 j，就表示这个范围内还有东西，那有东西的时候我们就得继续往下找。整个流程一共六步，前两步是设置指针和判断范围，第三步是取中间值，后面三步是三种比较结果。

### 中间下标怎么取，三种比较结果怎么走

范围内的元素怎么找？关键点就是找到这个范围内的中间元素，把中间元素和我们的待查找值做一个比较。

中间索引 m 很好求，就是 i 跟 j 它俩加起来除以二。不过我们得考虑一个取整的问题：拿我们的例子来说，0 + 7 除以二是 3.5，3.5 是个小数，它并不能作为索引，所以我们要做一个向下取整，3.5 就变成了 3，中间索引确定为 3，进而就确定了这个中间值 30。

把中间值 30 跟待查找值比较，结果分成三种，这三步可以放在一起看：目标小于中间值（走第 4 步）、目标大于中间值（走第 5 步）、目标等于中间值（走第 6 步）。

```text
                      a[M] = 30
                         |
          +--------------+--------------+
          |                             |
     target = 14                  target = 38
   target < a[M]                 target > a[M]
          |                             |
          v                             v
  i 不变, j = M - 1            i = M + 1, j 不变
          |                             |
          v                             v
  只在左半区继续找                 只在右半区继续找

  第三种情况:  target == a[M]  ->  找到了, 直接 return M
```

读图：中间的竖线就是当前范围的中点，三种比较结果分别把范围往左收、往右收，或者当场收工。

这三个分支为什么成立？根子都在“升序”这两个字上。中间值 30 已经大于 14 了，它右侧的元素只会更大，所以 30 以及它右侧的所有元素，下一次查找时都不用参与比较了——因此 i 不用动，j 缩到 M-1。反过来，38 大于 30，说明要找的 38 肯定在 30 的右侧，30 及其左侧的所有元素下一轮就没必要参与了，因此左边界 i 要推进到 M+1。至于相等，那证明已经找到了，直接返回 m。

### 三个例子，把流程走通

#### 查 14：一次左移就命中

目标值是 14，我们看一下它的执行过程。

| 轮次 | i | j | 中间下标 m | 中间值 | 与 target 比较 | 边界变化 |
| --- | --- | --- | --- | --- | --- | --- |
| 第 1 轮 | 0 | 7 | (0+7)/2 = 3.5 → 3 | 30 | 30 > 14 | 走目标小于中间值：j = M - 1 = 2 |
| 第 2 轮 | 0 | 2 | (0+2)/2 = 1 | 14 | 14 == 14 | 找到了，返回下标 1 |

第一次没有找到，但我们得到了一个结论；带着这个结论把范围缩到左边，第二轮就命中了。

#### 查 38：一次右移就命中

这回目标值换成 38，它位于数组的右侧。刚开始 i 还是 0，j 还是 7，中间下标还是 3，中间值还是 30。

```text
轮 1:  i = 0, j = 7, m = 3 -> a[3] = 30 ;  38 > 30  ->  i = M + 1 = 4
轮 2:  i = 4, j = 7, m = (4 + 7) / 2 = 5.5 -> 5 -> 中间值正好是 38
       38 == 38  ->  找到, 退出循环, 返回 5
```

注意第二轮的取整：4 + 7 是 11，11 除以二是 5.5，同样要向下取整成 5。这轮中间值和目标值相等，循环退出，查找结束。

#### 查 25：范围被压空

最后看一种找不到的情况。目标值是 25，整个数组里并没有这个数。

| 轮次 | i | j | 中间下标 m | 中间值 | 与 target 比较 | 边界变化 |
| --- | --- | --- | --- | --- | --- | --- |
| 第 1 轮 | 0 | 7 | 3 | 30 | 30 > 25 | j = M - 1 = 2 |
| 第 2 轮 | 0 | 2 | 1 | 14 | 14 < 25 | i = M + 1 = 2 |
| 第 3 轮 | 2 | 2 | 2 | 22 | 22 < 25 | i = M + 1 = 3，此时 i > j |
| 结束 | 3 | 2 | — | — | 范围内没东西了 | 返回 -1 |

这里有一个必须记住的细节：当 i 跟 j 相等的时候，仍然会走取中间值和比较这三步，因为这个时候我们还有最后一次查找机会，还不确定当前这个元素是不是我们要找的结果。所以第 3 轮里 m = (2 + 2) / 2 = 2，结果仍停在原位不动，中间值是 22；22 还是比 25 小，于是 i = M + 1 = 3，这一改 i 就跑到了 j 的右边，条件 i > j 终于满足，查找结束，表示没有找到。

> **易错点**：i 和 j 相等时不能提前收工。范围里还剩一个元素没比较过，直接返回 -1 就等于把这个元素漏掉了。

### 落到 Java 上

流程清楚了，代码就是流程的直接翻译。我提前建好了一个 BinarySearch 类，在类里面用一个方法来代表这个算法的实现——其实任何语言里，一个算法都可以对应一个或者多个方法。这里提供的方法叫 `binarySearchBasic`，对应二分查找的基础版实现。

前面提过，一个算法又分成了输入和输出：输入对应方法的参数，我们这个例子已经讨论过有两个输入参数，一个是我们待查找的升序数组 a，另一个是值 target；输出对应方法的返回值，找到就返回值的索引，找不到就返回 -1。

```java
public class BinarySearch {

    /**
     * 二分查找基础版
     */
    public static int binarySearchBasic(int[] a, int target) {
        int i = 0;               // 左边界，初始指向索引 0
        int j = a.length - 1;    // 右边界，初始指向索引 N-1

        while (i <= j) {         // 范围内还有元素，才值得再比较一次
            int m = (i + j) / 2; // Java 中 int 除法自动取整，舍弃小数部分

            if (a[m] > target) {
                j = m - 1;       // 目标在中间值左侧，右边界向左收缩
            } else if (a[m] < target) {
                i = m + 1;       // 目标在中间值右侧，左边界向右收缩
            } else {
                return m;        // 相等，找到，直接返回索引位置
            }
        }

        return -1;               // i > j，范围内没东西了，没有找到
    }
}
```

逐段对照着看：

- `int i = 0;` 和 `int j = a.length - 1;` 就是设指针。N 其实就是数组的元素个数，也就是数组长度 `a.length`，所以右边界等于 `a.length` 减一。
- `while (i <= j)` 就是“看范围内还有没有东西”。i 小于等于 j 表示范围内有东西，就继续执行取中间值和比较的逻辑；什么时候 i 大于 j 了，就表示范围内没东西了，直接返回 -1。
- `int m = (i + j) / 2;` 是取中间下标。Java 这里可以简单一些：两个 int 类型的变量相除会自动取整、自动舍弃小数部分，所以不用再额外调用取整函数了。**但换成别的语言就得把这个取整操作考虑进去**——比如 JavaScript 里两个数字相除是不会自动取整的，它会把 0 和 7 都当成小数，除以 2 之后结果还是小数 3.5，这时就必须再调一个取整函数（一般叫 `Math.floor`），把 3.5 变成 3。Java 里两个整数除法会自动舍弃小数，直接就取整了。
- 三个 `if` 分支正好对应流程里的第 4、5、6 步：目标小于中间值就让 j 等于 M-1，目标在中间值右边就让 i 等于 M+1，相等就直接 `return m`，找到之后不需要再循环下去做比较了。

其实这个算法写到这已经完成了。

### 先跑两组测试用例

写完先别急着信它，跑两个测试用例来看一下实现是否正确。怎么写测试代码？我首先准备一个测试数组，然后运行 `binarySearchBasic` 方法，把它的实际结果跟我预期的结果做一个比较：如果实际运行的跟预期的一致，那这个断言就通过，说明测试没问题；如果它实际返回的结果跟预期不一致，那说明算法实现有问题。

```java
public static void test() {
    int[] arr = {7, 13, 21, 30, 38, 41, 44, 54};

    // 找到的情况：把数组里的每个元素都验证一遍，预期值就是它自己的下标
    for (int k = 0; k < arr.length; k++) {
        assertEquals(k, binarySearchBasic(arr, arr[k]));
    }

    // 找不到的情况，预期值都是 -1
    assertEquals(-1, binarySearchBasic(arr, 0));   // 数组里没有，比所有元素都小
    assertEquals(-1, binarySearchBasic(arr, 15));  // 数组里没有，夹在 13 和 21 中间
    assertEquals(-1, binarySearchBasic(arr, 60));  // 数组里没有，比所有元素都大
}
```

`assertEquals` 就是把预期值跟方法实际返回的结果做一个相等比较（equal）——找 7，索引位置肯定是 0；找 13，索引位置肯定是 1；找 21，索引位置肯定是 2，我就把测试数组里面的所有元素其实都验证了一遍。找不到的情况我就挑了三个测试点：0 是小于数组中任意元素的，15 随便挑了个中间值（在 13 和 21 之间），60 是比数组中任意元素都大的，它们的预期值都是 -1。

跑一下测试用例，可以看到全部测试通过，说明这个算法初步看起来是没有问题的。

### 一听就会一写就废，问题出在那个等号上

这个二分查找算法本身还是属于比较简单的。但不知道大家有没有这样一种感觉：听的时候大家都听懂了，让自己一写呢，算法就写得有毛病——也就是所谓的一听就会、一写就废。

为什么会一写就废？我总结就是：因为对这个算法的细节还没有真正把握。我提一个问题：为什么我们在写这个 while 循环时，这里的条件是 `i <= j`，而不是一个 `i < j`？好像差个等于也没差多少吧？如果你不把这个搞清楚，那么写代码的时候，你下笔时就会不知道这块该怎么写。

那我们就把它改成 `i < j` 看看会不会有问题。怎么验证？很简单，测试用例刚才已经写好了，把测试用例再跑一遍，看看刚才已经通过的那些断言能不能继续通过。

结果一执行第一个断言就报错了：我期望的是 7 这个元素它搜索出来索引是 0，但是实际返回了个 -1，也就是它并没有找到这个元素。显然这个错误就是因为我把 while 条件改成了 `i < j`，导致它并没有搜索到我们真正的元素。

```text
错误版本 while (i < j)，查找数组中下标为 0 的元素 7：

轮 1:  i = 0, j = 7, m = 3 -> a[3] = 30 ;  7 < 30  ->  j = M - 1 = 2
轮 2:  i = 0, j = 2, m = 1 -> a[1] = 13 ;  7 < 13  ->  j = M - 1 = 0
轮 3:  i = 0, j = 0 ;  i < j 不成立  ->  直接退出 while 循环  ->  return -1
                                    ^
                        a[0] = 7 从来没有参与过比较！
```

问题的根源出在哪？其实就是我们少做了一次比较：也就是 i 跟 j 指向的那个元素——它有可能正是我们要查找的目标——我们最后没有那个等于的条件，就相当于把最后 i 跟 j 指向的元素漏掉了。前面几轮参与比较的都是 i 与 j 中间的那个 m 元素，但最后一次我们还得考虑一下，要比较 i 跟 j 指向的这个元素，否则你就会漏掉一次比较。

正确的情况是什么？还是查找下标为 0 的元素：

```text
正确版本 while (i <= j)，查找数组中下标为 0 的元素 7：

轮 1:  i = 0, j = 7, m = 3 -> a[3] = 30 ;  7 < 30  ->  j = M - 1 = 2
轮 2:  i = 0, j = 2, m = 1 -> a[1] = 13 ;  7 < 13  ->  j = M - 1 = 0
轮 3:  i = 0, j = 0 ;  i <= j 成立  ->  继续进入循环
       m = (0 + 0) / 2 = 0 ，和 i、j 指向的是同一个元素
       a[0] = 7 == 7  ->  这回才真正找到目标, 返回 0
```

同样是重新计算了一遍 m，只不过这一回计算出来的 m 其实跟 i 和 j 都是一样的，它们指向的是同一个元素；我们把这个元素再跟目标做一次比较，才不会漏掉。

所以回到算法，我们必须在这个地方把等于条件加上。加上了这个等于条件，就表示 i 跟 j 指向的元素也会参与比较；如果你不加，光写一个 `i < j`，那么相当于只有 i 跟 j 中间的那个 m 会参与比较，就会产生这个疏漏。

> **提示**：这个等号加与不加，跟 j 的取值方式是有关系的。我们现在这个 j 写的是 `a.length - 1`；后面我会给大家看一个二分查找的改进版本，写法跟它有些不一样，j 的取值刚开始取的是不一样的，这个时候我们这个 `i <= j` 的条件就又有变化了。这个等讲到改进版本时再说。

## 中间索引、比较符号与两个版本的边界含义
> 对应块：BLK02 | 覆盖分集：P05-P08 | 块标题（分集名）：《基础数据结构-004-二分查找-问题2-中间索引》

我把网页版的二分查找代码翻出来，跟课堂这份并排放在一起对比的时候，先看到的是一行不一样的东西：求中间索引，网页版写的是 `i + j` 加一个右移运算符移一位，课堂上写的是 `i + j` 除以二。

看着只是写法不同，但这一行是有问题的。而且不只是"风格不统一"这种小问题——它会算出一个**负数**的中间索引来，负数当然找不到元素。这一讲我们就从这行代码开始，把二分查找里几个最容易被背下来、却没真正想明白的地方一个个过掉：中间索引怎么写、为什么全用小于号、改动版的 `j` 到底换了什么身份，以及最后——我们凭什么说一个算法比另一个算法好。

### 中间索引为什么不能写除法

先把这个 bug 现场演一遍。我写了个测试代码，故意把 `i` 设成 0，把 `j` 设成整数的最大值减一，也就是 `Integer.MAX_VALUE - 1`，模拟一个长度大到极致的数组：

```java
int i = 0;
int j = Integer.MAX_VALUE - 1;      // 2147483646

int m = (i + j) / 2;
System.out.println(m);              // 1073741823

// 目标在中间值右侧 → 扩大左边界
i = m + 1;
m = (i + j) / 2;
System.out.println(m);              // 负数！
```

第一次循环没问题，`m` 算出来是 1073741823，确实约等于整数最大值的一半。问题出在第二次循环：目标在中间值右边，按理说要把左边界推到 `m + 1`，`j` 保持不动。于是 `i` 变成了 1073741824，再去和 `j` 相加：

$$
1073741824 + 2147483646 = 3221225470
$$

这个数已经超过了 Java 里最大正整数 2147483647。再除以二，得出来的东西是个负数。

为什么"两个正数相加会得到负数"？这不是玄学，跟二进制数的表现形式有很密切的关系。

> **定义**：一个二进制数其实有两种表现形式。一种把最高位看成符号位，另一种把最高位当成普通数字、不当符号位。同样的比特位，两种看法算出来的数值完全不同。

先用八位的小例子感受一下。八个 1，也就是 `11111111`：如果八个都是普通数字，它是 255；如果把最高位当成符号位，最高位是 1 就代表负，它表示的是 -1。同一个二进制数，结果天差地别。

我们的问题里，Java 总是把最高位当成符号位。我把自己的计算工具切成 32 位，把两个数粘进去相加，得到的比特位是这样的：

```text
i + j 在 32 位下的比特位：
    1011 1111 1111 1111 1111 1111 1111 1110
    ↑最高位

最高位不当符号位：  3221225470    （这就是刚才那个"看起来是正数"的结果）
最高位当符号位：    -1073741826   （Java 看到的是这个）
```

把两个 32 位数并排一搜，比特位一模一样，区别只在于最高位被不被当成符号位。Java 里没有无符号整数，全是带符号的，所以它一定把最高位读成符号位，于是相加的结果就变成了负数。

> **易错点**：这个现象不要笼统地叫"溢出"。`i + j` 的结果 3221225470 其实并没有超出 32 位的表示范围，它超出了 **int 有符号正数的上限**。所以严格讲这不是溢出，而是同一串比特位被按两种规则解读。

这就跟物理学里那个波粒二象性有点像：同样是光子，你一施加观察者，它就表现出粒子的形态；不加观察者，它就表现出波的形态。同一串比特，你从哪个角度看，看到的就是哪个值。

那问题来了：既然除法这条路走不通，用什么来替代？

#### 无符号右移是怎么工作的

答案就是**无符号右移运算符** `>>>`，用它替掉那个除以二。它的工作方式极其朴素：把二进制的所有 0 和 1 一起向右平移，平移几位由我们指定，左边空出来的高位用 0 补齐。

```text
8       = 00001000
8 >>> 1 = 00000100 = 4        高位补 0

16      = 00010000
16 >>> 1 = 00001000 = 8

7       = 00000111
7 >>> 1 = 00000011 = 3        = 7 / 2 = 3.5 向下取整
```

偶数的时候结果就是除以二；奇数的时候是**除以二向下取整**。所以只要右移一位，你都可以直接看成"除以二取整"。

关键的一点在于：除法运算**不会去动那个符号位**。负数除以二还是负数，前面那个已经变负的结果根本救不回来。但右移不一样——符号位本身被一起挪走了。

```text
    1011 1111 1111 1111 1111 1111 1111 1110   3221225470   （i + j，负数）
>>> 1
    0101 1111 1111 1111 1111 1111 1111 1111   1610612735   （约 16 亿，正数）
```

比特位一样，右移的结果就一样。32 亿被移成 16 亿，落回了 Java 能表示的正数区间，结果恢复正常。除法做不到这一点，因为它压根不碰符号位。

> **易错点**：这里必须是 `>>>`，不能写成 `>>`。我们整套道理讲的就是"符号位要被移走"，而 `>>` 是带符号右移，会把符号位一路带下来，负数移完还是负数。

还有一个附带的好处：`>>>` 天然就是向下取整的，不用额外包一层取整函数。如果用除法，`(0 + 7) / 2` 是 3.5，你还得调一个向下取整的函数来收拾；而 `(0 + 7) >>> 1` 直接就是 3。所以在 Java 里、哪怕是在 JavaScript 里，它都可以当成整数运算来用，**这一行代码在多个语言之间是通用的**，不用为每种语言各写一份。

所以回到二分查找：为了避免中间索引算成负数，**一定要把除法改成无符号右移**。

### 为什么我全写小于号

这是问题三，一个编码上的细节。

你看，无论是 `i` 跟 `j` 比较，还是目标跟中间值比较，我用的全是小于号，从来没用过大于符号。为什么？

因为我们这个例子里的数组是**升序排列**的。写成小于号，方向跟数组升序的顺序是一致的。你看到 `i <= j`，第一反应就是 `i` 在左侧、更小；`j` 在右侧、更大；等于意味着两者已经交错了。这跟人脑里的画面是对得上的。

我把代码顺序换一下，写成 `j >= i`，逻辑一模一样，但读起来特别别扭：明明 `i` 更小，它好像跑到右边去了；明明 `j` 更大，它反而在左边。跟数组升序的顺序正好反过来。

下面那处"中间值跟目标值比较"也是同样的道理：一眼就能看出目标更小、在左边，目标更大、在右边。

> **结论**：这是一点编程上的小技巧，让代码跟人类的正常思维保持一致。升序数组就用小于，降序数组自然就该反过来用大于。

### 把二分查找翻译成人话

我们用人类的语言把整段二分查找代码翻译一遍。

先设置两个指针，这两个指针指向数组的两端。当 `i` 还在 `j` 的左侧，或者两者相交的时候，我就循环执行里面的逻辑；当 `i` 跑到 `j` 的右侧了，说明没找到，返回失败的结果。

循环体做的事是：取 `i` 和 `j` 的中间索引，找到中间位置，把中间值跟目标做比较。

- 如果目标在中间值的左侧，那接下来当然还得在左边找，所以让右边界缩小，缩小到中间索引减一的位置，也就是中间索引左侧那一个；
- 如果目标在中间值的右侧，那下次就该在右边找，所以这回改左边界 `i`，让它增大，变成中间索引右边一个位置。

就这样不断循环、不断缩小范围，直到中间值跟目标相等，这时候表示找到了，返回这个中间索引就行。

> **提示**：如果你能不看代码、用自己的话把这段流程完整讲出来，说明你对二分查找已经初步掌握了。

### 改动版：j 换了个身份

大家去读一些文章或者翻别人的代码，会发现二分查找的实现跟我给的这版略有差异。为了加深认识，我再给出另一个版本，我们对比一下它差在哪。

改动一共有三处：

```java
public static int binarySearchAlternative(int[] a, int target) {
    int i = 0;
    int j = a.length;                   // 改动一：去掉 -1
    while (i < j) {                     // 改动二：去掉等号
        int m = (i + j) >>> 1;
        if (a[m] == target) {
            return m;
        }
        if (target < a[m]) {
            j = m;                      // 改动三：去掉 -1
        } else {
            i = m + 1;                  // 这个不变
        }
    }
    return -1;
}
```

- `j` 的初值从 `a.length - 1` 变成了 `a.length`；
- 循环条件从 `i <= j` 变成了 `i < j`；
- 目标在左边时，`j` 从 `m - 1` 变成了 `m`。

改完之后正确性怎么样？还是老办法，用单元测试验。把基础版的测试复制一份，只把调用的方法改成 `binarySearchAlternative`，找到的几种情况和没找到的几种情况都跑一遍——都通过了。所以虽然动了三处，这个算法是正确的。

有了正确性做底，我们再走一遍它的执行流程，看清这三处改动背后的含义。

#### j 只当边界

拿查找 13 举例。第一步还是确定两个指针的初值。`i` 没变，仍然指向下标 0 的元素；但 `j` 不一样了，它指向的是一个**并不存在的元素**。

这里是最关键的地方。对比一下：

```text
基础版（左闭右闭）
  下标    0    1    2    3    4    5    6    7
  元素    4    ?    ?   13   22    ?    ?   25
         ↑                        ↑
         i                        j   ← j 指向的元素可能就是答案 25

改动版（左闭右开）
  下标    0    1    2    3    4    5    6    7    8
  元素    4    ?    ?   13   22    ?    ?   25    ✗
         ↑                        ↑
         i                        j   ← j 一定不是答案，它越界了
```

基础版里，`j` 不光是边界，它指向的元素**也有可能是我们要查找的目标**——比如这里的 4 和 25，都完全可能是答案。

改动版里，`i` 指向的元素还是有可能是查找目标，但 `j` 不一样了：它**只是作为一个边界，它指向的一定不是查找目标**。这句话请记住，后面全靠它。

继续走流程。`m = (0 + 8) / 2` 取整等于 4，中间值是 22。目标 13 比 22 小，应该在左侧查找，所以缩小 `j`，让 `j = m`。

**注意，这里为什么写 `m` 而不是 `m - 1`？** 因为 `j` 指向的一定不是查找目标。如果我写成 `m - 1`，那么下一次 `j` 就指向 `4 - 1 = 3`，也就是 13——它指向的偏偏就是查找目标本身，结果跟目标恰巧错过了，把 13 漏掉了。所以 `j` 的取值只能是 `m`：因为这个 `m` 在第一轮比较的时候已经比较过了，22 跟 13 不等，所以 `j` 指向的并不是查找目标。这跟我们前面强调的那句话并不矛盾。

接着走。这回 `m = (0 + 4) / 2` 取整等于 2，目标比中间值大了，在右侧找，扩大左边界让 `i = m + 1 = 3`，这跟基础版一样。此时 `i < j` 仍然成立，再次进入循环：`m = (4 + 3) / 2` 向下取整还是 3，中间值跟目标相等，找到了。这跟我们之前的推论也一致——`i` 指向的元素仍然有可能是查找目标。

到这里，你问的两个问题其实都回答了：改动版里 `j` 的含义是**只作为一个边界，它指向的元素肯定不会参与比较**，所以缩小边界时才能让它等于 `m` 而不是 `m - 1`。

#### while 里为什么不能加等号

那 `while` 循环里为什么连等号也没有了？

因为 `i` 指向的元素还有可能要去参与比较，但 `j` 指向的元素**本来就不应该让它继续参与比较了**。如果加上等号条件，就意味着最后一步可能让 `i` 等于 `j`，由 `i` 带着 `j`，让它们指向的元素一起参与比较——这跟前面的假设直接矛盾。

有同学会问：我就让 `j` 指向的元素比较一次又能咋呢？问题还挺严重：**它会在某些情况下让我们陷入死循环**。

我先告诉结论：只要加上这个等号条件，在查找一个数组内没有的元素时，就会死循环。比如找一个 30（数组里没有）。

```text
i=0 j=8 → m=4, a[4]=35 > 30  →  j = m = 4
i=0 j=4 → m=2, a[2]=19 < 30  →  i = m + 1 = 3
i=3 j=4 → m=3, a[3]=27 < 30  →  i = m + 1 = 4     （m 恰好等于 i，比较 a[i] 是合法的）
i=4 j=4 → i == j，若允许进循环：m=4, a[4]=35 > 30  →  j = m = 4   ← j 原地不动
i=4 j=4 → …… 状态与上一行完全相同，死循环
```

逐轮看：第一次进循环算出中间值 35，比目标大，所以在左侧找，`j = m`，没问题。第二轮再算中间值，这回是 19，比目标小，所以在右侧找，扩大 `i`，`i = m + 1`，没问题。第三轮 `(3 + 4) / 2` 向下取整还是 3，中间值 27 还是没跟 30 对上，因为中间值比目标小，还得往右找，于是 `i = m + 1 = 4`。

**现在问题来了**：`i` 和 `j` 相等了。如果条件写成 `i <= j`，它就会进入下一轮查询比较。但这一轮其实根本不该进——`j` 指向的元素不应该参与比较。而且 `j` 指向的这个 35，第一次的时候已经比较过了，当时就已经确定不等了。

再往下走：它俩都指向下标 4，算出来中间索引还是 4，`m` 和 `i` 和 `j` 指向的都是那个元素，跟要找的 30 还是不相等；而 30 比中间值小，所以进入"在左边"这个分支，`j = m`，也就是 `j = 4`——**`j` 根本不会动**。于是刚才那段逻辑原封不动地再走一遍，就这样陷入了死循环。

#### 两个版本的边界含义

讲到这里，我希望大家能有这样一种认识：**想更好地掌握一种算法，就必须对算法里的变量、指针背后的含义有更深入的理解**，这样才能从"理解"的层面掌握它。不这样做，那你可能只能靠死记硬背去记住这个算法。

回过头来把两个版本的 `i` 和 `j` 的含义并排说一遍：

| | 基础版 | 改动版 |
| --- | --- | --- |
| `i` 初值 | `0` | `0` |
| `j` 初值 | `a.length - 1` | `a.length` |
| `i` 指向的元素 | 可能是答案 | 可能是答案 |
| `j` 指向的元素 | 可能是答案 | 一定不是答案 |
| 循环条件 | `i <= j` | `i < j` |
| 目标在中间值左侧 | `j = m - 1` | `j = m` |
| 目标在中间值右侧 | `i = m + 1` | `i = m + 1` |
| 边界语义 | 左闭右闭 | 左闭右开 |
| 找不到时返回 | `-1` | `-1` |

基础版的 `i` 和 `j` 不光代表搜索的边界，它们指向的元素最终也有可能参与比较运算，所以可以把它称为**左闭右闭的边界**。

改动版里 `i` 的含义没有改变，但 `j` 的含义变了——我们并不希望它参与比较运算，所以才有了那两处调整。它的边界是**左闭右开的（开）边界**，意味着将来不会参与运算，它只作为一个边界而已。

有同学问我：讲这么多有意义吗？有意义。后面这个改动版还会在二分查找的更多用途里用到它这种写法，包括 left most、right most，写法都是这样的。**所以这两种版本我们都得掌握。**

### 一个更简单的写法

讲到这儿，有同学提出反对意见：老师，你这个算法太复杂了，逻辑难理解，代码行数也多，我有更好的做法。

这位同学提供的办法是这样的，方法接受的参数跟我们之前一样，一个待查找数组，一个目标值：

```java
public static int search(int[] a, int target) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == target) {
            return i;
        }
    }
    return -1;
}
```

算法内部从下标 0 一直循环到数组长度减一，把每个元素拿出来跟目标比较，相等就返回这个索引；都循环完一遍还没找到，就返回 -1。他说了：你看这个代码够简洁吧，代码行数比二分查找少，理解起来也更简单。

这种算法我们叫**线性查找法**。它看起来更简单，而且对数组里的元素也**没有升序的要求**了。但如果我们从执行效率上去对比，你会发现二分查找比它高很多很多很多。那这个怎么去证明？下面就分析。

### 事后统计法：让两个算法各跑一遍

要衡量两个算法的好坏，最为直接的做法就是让两个算法的代码各跑一遍，看看你快还是我慢。这是最直接的做法，被称作**事后统计法**。

它虽然直接，但有两个缺点。

第一个缺点是**比较依赖于测试数据**。比如二分查找跟线性查找，如果你给的测试数据只是一个很小的数字，其实体现不出来谁快谁慢，也许差距并不大；只有在数据量规模比较大的时候，你才能看出好像是二分查找更快。而准备测试数据通常需要花费很多精力。

第二个缺点是**比较依赖于硬件环境**。你写了个算法在自己机器上跑得比较快，那可能只是因为你的机器好、电脑好，并不是因为你的算法好。

所以我们要讲的是另一种方法。

### 事前分析法与它的两条前提

事前分析法这个名字大家可以猜出来：这种做法并不要求实际去执行这个算法，而是通过分析的手段去预估出算法的执行时间。

怎么分析？以线性查找为例，我把整个分析过程走一遍。为了简化，我这里有两个前提。

第一个前提：**只分析算法最差的执行情况**，最好的情况和平均情况先不考虑。当然为了公平起见，待会分析二分查找的时候，也分析它最坏的那种执行情况。

第二个前提实际上是一个简化：**假设每行语句执行的时间是一样的**。比如这里的赋值语句、接下来的比较语句、还有自增运算，我们都假设每行的执行时间一样。不然没法分析——你还得考虑赋值、自增、比较它们之间的差异，那就把事情搞复杂了。

### 线性查找的最坏情况：3n + 3

线性查找的最差执行情况是什么？就是**找不到的时候**。找不到意味着所有循环都循环完了，最后又执行了一个 `return -1`，都执行到最后一行代码了，这种情况下执行的代码行数肯定最多。

确定了最坏情况，我们来数它一共执行了多少行代码。设数组元素个数为 $n$：

| 语句 | 最坏情况下的执行次数 |
| --- | --- |
| `for` 里给临时变量 `i` 赋值 | 1 |
| `for` 里判断是否循环结束 | $n + 1$ |
| `for` 里 `i++` 自增 | $n$ |
| `if (a[i] == target)` 比较 | $n$ |
| `if` 里的 `return i` | 0 |
| 最后的 `return -1` | 1 |

几点要说明：判断条件的次数为什么是 $n + 1$ 呢？因为前面 $n$ 次都是在循环数组内从 0 到 $n - 1$ 的元素，最后当 `i == n` 时发现已经越过数组了，应该退出循环——但最后那一次比较还是得有。而 `i++` 正好执行 $n$ 次，数组里 $n$ 个元素就自增 $n$ 次。

`return i` 为什么是 0 次？因为每次比较都不成立，根本进不了 `if` 里头。最后的 `return -1` 则一定会执行一次。

累加起来：

$$
1 + (n + 1) + n + n + 0 + 1 = 3n + 3
$$

这就是线性查找在最坏情况下的语句执行次数。它跟数组元素个数直接相关：元素越多越吃亏，比如有 1000 个元素，它就要执行 3003 次；有 1 万个，就要执行 30003 次。

### 二分查找的 while 到底循环几次

接下来看二分查找的最坏情况。

有同学说，它的最差执行情况应该跟线性查找类似，都是 while 循环循环完、没找到的时候，这时候语句总数最多。说得没错，**不过一些细节大家考虑得可能不是很周到**：其实"没找到"也要分两种情况。

比如现在有这么一个数组，如果我找一个目标是在左边没找到，和找一个目标是在右边没找到，你实际去试一下会发现，运行的语句总次数是不一样的。而且呢，**右侧没找到更差一些**。所以我们待会儿分析的是以右侧没找到为准。

确定完最坏情况，还是按老规矩逐行数。第一行给 `i` 跟 `j` 赋初值，对应两次赋值操作，可以看成执行了 2 次；最后因为是没找到的情况，`return -1` 执行 1 次。

比较难确定的是中间这个 `while` 循环。它看起来比较复杂，到底会循环几次？它跟数组元素个数有什么关系？让你自己分析可能比较难，我们来推导。

借助我之前做的那个网页工具，看它到底进入了几次循环。怎么数呢？每次进入循环一定会求这个中间索引 `m`，那只要数动画上 `m` 出现了几次，就相当于它进入了几次循环。

比如元素个数给 4，找一个右侧数组中没有的元素，比如 100：

- 第一次循环进来，`m` 被计算出来了，出现 1 次；
- 第二次进入循环，重新计算 `m`，出现 2 次；
- 第三次，`m` 又出现，出现 3 次；
- 再执行的话就没有 `m` 了，直接 `return -1`。

所以元素个数是 4 的时候，循环了 3 次。

再把元素个数设置大一些，改成 8，还是找右侧没有的 100：数 `m` 出现的次数——1 次、2 次、3 次、4 次，没了。循环了 4 次。

中间那几个就不一个一个试了，节省时间。直接给出规律：

| 元素个数 $n$ | while 循环次数 |
| --- | --- |
| 4 ~ 7 | 3 |
| 8 ~ 15 | 4 |
| 16 ~ 31 | 5 |
| 32 ~ 63 | 6 |

找到点规律了吧。从这张表上直接能看出来的是：**区间的长度每翻一倍，循环次数才多一次**——从 4 到 8 翻倍，加 1；从 8 到 16 翻倍，又加 1。这跟咱们公务员考试的行测题类似，给你一组数字，让你推导出数字之间的规律。

那用一句话把这个规律写死究竟是什么，我就留给大家自己找了，下一讲我们把它推出来。

## 怎么衡量一个算法的好坏：时间复杂度、空间复杂度与大 O 表示法
> 对应块：BLK03 | 覆盖分集：P09-P12 | 块标题（分集名）：《基础数据结构-008-如何衡量算法好坏-2》

先把答案摆在纸面上看。我们把元素个数取成 4、8、16、32，每一轮都把待查的范围对半砍掉，循环次数分别落在 2、3、4、5 上——规律几乎是用尺子量出来的：它就是一个以二为底的对数。

### 二分查找的循环次数，藏着一条对数规律

所谓"以二为底的对数"，说白了就一件事：把这个数反复除以二，看除几次能除到 1。

```text
 n = 4      4 -> 2 -> 1                   2 次
 n = 8      8 -> 4 -> 2 -> 1              3 次
 n = 16    16 -> 8 -> 4 -> 2 -> 1         4 次
 n = 32    32 -> 16 -> 8 -> 4 -> 2 -> 1   5 次
```

那有人要问了：5、6、7 这种数怎么办？

它们的以二为底对数算出来不是整数。就拿 7 来说，除一次得 3.5，除两次得 1.75，对数落在 2 和 3 之间——2 点几。

没关系，向下取整就够了。7 取整之后是 2，加一还是 3，跟前面几个完全一致。所以循环次数的表达式是：

$$
L = \lfloor \log_2 n \rfloor + 1
$$

其中 $n$ 是元素个数，$L$ 是循环次数。

> **结论**：二分查找每砍一刀，范围减半；元素个数从 4 涨到 32，循环次数只从 2 涨到 5。$n$ 每翻一倍，$L$ 只多 1。

知道了循环次数，接下来才是关键的一步：循环体里每一行代码，到底各跑了多少次？

### 每一行代码到底跑了多少次

我们把二分查找里跟循环相关的语句拆开看（先不管完整实现，就按结构数）：

```text
 [while 循环内]
   循环条件  i < j                 ->  L + 1 次   (最后一次不成立才退出)
   计算中间索引 mid                ->  L 次
   if:  target 与中间值比较         ->  L 次
   else if:  中间值是否小于目标     ->  L 次
       mid++ 与赋值                 ->  2L 次
   else                            ->  0 次       (只往右边找，永远进不去)
   ----------------------------------------------------
   循环体内小计                     ->  5L 次

 [循环外的零散语句]
   循环初始化、判断、步进等         ->  1 + 1 + 2 = 4 次
```

先看 `i < j` 这个条件。它跑了 $L$ 次？不对，是 $L+1$ 次——因为最后一次比较不成立，循环才退出，这最后一次比较同样要算数。

中间索引那行，每次进循环都得算一次，跑 $L$ 次。

再看 if / else if 这一段。我们要查找的目标在右半边，所以第一个 if 一定不成立；第一个不成立，就会接着去比第二个 else if；else if 条件成立，`mid++` 和赋值这两个动作又各执行一次。至于最后的 else，我们只在右边找，永远不会走到它。

把上面加起来：循环体内是 $L + L + L + L + 2L = 5L$；循环外还有几行零散的语句，$1 + 1 + 2 = 4$。所以二分查找的总执行行数是：

$$
f(n) = 5(\lfloor \log_2 n \rfloor + 1) + 4
$$

### 把两个查找算法放到同一杆秤上

线性查找那边我们早算过：$f(n) = 3n + 3$。

这里沿用前面那个假设——每行语句执行的时间都一样，用单位时间 $t$ 来表示。这样"总执行行数乘以 $t$"就是总时间。

当 $n = 4$ 时：

- 线性查找：$3 \times 4 + 3 = 15$，也就是 $15t$；
- 二分查找：$\lfloor \log_2 4 \rfloor + 1 = 3$，$5 \times 3 + 4 = 19$，也就是 $19t$。

> **易错点**：千万别看到 15 比 19 小，就下结论说线性查找更快。我们刚才只有 4 个元素，数据量太小，优点还没显出来。

把元素个数提到 1024（我算数不好，这回拿计算器算）：

- 线性查找：$3 \times 1024 + 3 = 3075$，也就是 $3075t$；
- 二分查找：$\lfloor \log_2 1024 \rfloor = 10$，$5 \times (10 + 1) + 4 = 59$，也就是 $59t$。

数据量一涨，二分的优势立刻就压过来了。

> **结论**：看一个算法，不能光看它数据量小的情况，要看数据规模持续增大的时候它是不是还能表现得优秀。像这样先推算执行次数、再比大小的办法，我们叫它事前统计法。

#### 画出来比算出来更直观

Java 不擅长画图，我给大家找了一个第三方的画图网站，网址已经记在笔记里了，需要的同学翻笔记拷贝粘贴就行。

横轴 x 代表数据规模，也就是数组内元素的个数；纵轴 y 代表算法执行的代码行数，或者说总时间。用法很简单：把刚才这些算式带进去，把式子里的 $n$ 换成网站的 $x$ 就行。

- 线性查找就是 $3x + 3$，粘进去出来一条红线。$x = 2$ 时 y 对应的是 9，$x = 4$ 时是 15，和我们手算的完全对得上。
- 二分查找的式子也把 $n$ 改成 $x$ 粘进去。一个网页里能画多张图，鼠标点一下就能开第二张，方便两条线摆在一起对比。

验证完正确性，再把图大胆缩小，趋势一下就露出来了：

- 数据量到 120 左右时，二分查找大约 $39t$；而这个规模下，红色那条线性查找线已经看不在哪儿了。
- 数据规模上万、点到 14000 的时候，二分查找的总时间是 $74t$，还是很小的数；这时候红色线都不知道跑哪儿去了。

蓝色（二分查找）几乎不产生多大变化，红色（线性查找）的时间成本却一下子飙升。这就是用画图的方式看到的变化趋势。

### 时间复杂度衡量的到底是什么

前面我们通过事前分析的办法，得知了一个算法在执行时间上的好坏。这个分析的结果，在计算机科学里有一个专门的术语，叫时间复杂度。

> **定义**：时间复杂度是用来衡量一个算法的执行时间随着数据规模的增大而增长的一个时间成本。

这句话怎么理解？翻译成人话就是：如果数据规模不断增大，而算法的执行时间并没有明显地增长，那我们就说这个算法的时间复杂度低，它也是相对比较优秀的算法；反过来，如果数据量越来越大，而算法的执行时间增长得非常快，那时间复杂度就高，相对而言也是不那么好的算法。

> **易错点**：时间复杂度的分析过程是不依赖于环境因素的。这里的环境因素既包括硬件环境（CPU 主频、内存的存取速度等等），也包括软件环境（比如 Java 语言的编译器是不是对你的代码做了优化，优化了之后它跑的速度可能就快了）。分析时间复杂度的过程中，要把硬件、软件环境统统剔除掉，只针对算法本身来考虑它在执行时间上到底好不好。

### 从 f(n) 到 g(n)：不化简就抓不住主矛盾

清楚了定义，接下来一个问题就来了：时间复杂度该怎么表示？

假设算法要处理的数据规模是 $n$，代码总的执行函数我们用一个 $f(n)$ 来表示。前面推导过的式子都能当 $f(n)$ 用：线性查找的 $f(n) = 3n + 3$，二分查找的 $f(n) = 5(\lfloor \log_2 n \rfloor + 1) + 4$。$f(n)$ 代表的，就是数据规模变化时我们代码总执行时间的变化趋势。

不过大家可能也发现问题了：这两个式子相对来讲都挺复杂，我们不容易一眼看过去判断"你这个式子代表的时间复杂度是低还是高"，也就是说——一眼看过去抓不住主要矛盾。

所以我们要对 $f(n)$ 进行化解，用一个更简单的函数来代表数据规模与时间成本之间的变化关系。

> **注意**：更简单的这个函数，它的**变化趋势**要跟 $f(n)$ 相近。注意是相近，不是相等。

"找到一个与原本 $f(n)$ 变化趋势相近的函数，用它来代表我们的时间复杂度"——这种表示法，就是接下来要讲的大 O 表示法。

### 三张图，三个概念

我们用三张图来说明三个概念。先把图里的符号认一下：$c$、$c_1$、$c_2$ 都是常数；$n$ 代表数据规模，对应横轴；$f(n)$ 是实际执行的代码行数与 $n$ 的一个函数，代表执行时间与数据规模之间的变化趋势；$g(n)$ 是我们化简后的函数，它的趋势与 $f(n)$ 一致，也是 $n$ 的函数。

- **第一张图**：$g(n)$ 乘上一个常数 $c$ 之后，从某个点 $n_0$ 开始，所有值都比 $f(n)$ 的值大。于是我们把 $g(n)$ 称为 $f(n)$ 的上界，更严谨地说是**渐近上界**。
- **第二张图**：在某个点以后，$c$ 乘以 $g(n)$ 的值总是小于 $f(n)$，这就是**渐近下界**。
- **第三张图**：$g(n)$ 乘 $c_1$ 在 $f(n)$ 的下面，乘 $c_2$ 在 $f(n)$ 的上面，把 $f(n)$ 包围在中间——一个在它上面，一个在它下面。这种就叫**渐近紧界**。

```text
         c2·g(n)  ────────────────────────  总在上方
        ╱         ╲
      f(n)         ╲                      被夹在中间
    ╱       ╲       ╱
         c1·g(n)  ────────────────────────  总在下方
     └──────────────────────────────────→  n
```

"紧界"这个词起得挺形象：紧，紧的紧，就把它包起来了。

再说一遍：$g(n)$ 总在 $f(n)$ 上面的，叫渐近上界；总在 $f(n)$ 下面的，叫渐近下界；能把 $f(n)$ 包起来的，叫渐近紧界。

| 概念 | 符号 | 几何关系 | 代表的含义 |
| --- | --- | --- | --- |
| 渐近上界 | $O(g(n))$ | $c \cdot g(n)$ 总在 $f(n)$ 上方 | 算法执行的最差情况 |
| 渐近下界 | $\Omega(g(n))$ | $c \cdot g(n)$ 总在 $f(n)$ 下方 | 算法执行的最佳情况 |
| 渐近紧界 | $\Theta(g(n))$ | $c_1 \cdot g(n)$ 在下、$c_2 \cdot g(n)$ 在上 | 最差与最佳都能代表 |

#### 大 O 为什么代表最差情况

用符号怎么写？就是我们今天的主题：大 O。括号里面写上 $g(n)$ 就可以了。

它背后的含义是什么？这种渐近上界，其实就代表我们算法执行的一种最差的情况。

结合图来看：横轴代表数据规模，纵轴代表算法实际执行的代码行数。y 轴的值越大，实际执行的代码行数就越多，相对来讲就更糟糕——因为实际执行的代码越多嘛。

从某个点 $n_0$ 开始，$f(n)$ 总在 $g(n)$ 的下方，那就意味着 $f(n)$ 执行得再糟糕，也不能比 $g(n)$ 更差了，它总在它下面。所以 $g(n)$ 是一种更差的情况。

因此，渐近上界也就是大 O 表示法，说的就是算法的一种最糟糕情况：你再差，不能比这个上界函数表示的更差。

### 怎么把 f(n) 化简成 g(n)

有了前面的铺垫，我们来看两个例子，你就会发现从 $f(n)$ 找 $g(n)$ 一点都不难。

#### 线性查找：O(n)

线性查找的函数式是 $f(n) = 3n + 3$，先把它画出来。画图工具里它只认 $x$ 不认 $n$，一种办法就是把所有的 $n$ 替换成 $x$；另一种办法是让 $n$ 的取值来自于 $x$，把 $x$ 的每一个值赋值给 $n$，将来这里的 $n$ 就等价于 $x$ 了。那条 $n = x$ 的线可以点前面的小图标隐藏掉，剩下的红线就是我们的 $f(n)$。

接下来要找 $g(n)$：它在某一个点以后，取值是不是都要待在 $f(n)$ 的上方？

对于多项式来说，办法很直接——找到它的最高次项，把最高次项作为 $g(n)$。$3n + 3$ 的最高次项就是这里的 $n$，那我们先把 $n$ 当作 $g(n)$。

有同学一看图就发现不对：绿色的 $n$ 在红色的 $3n + 3$ 下面，跟我们介绍的方向反了。

别急——你别忘了，我们的 $g(n)$ 前面还有个系数 $c$ 这个常量系数。所以我们可以给它乘一个值，比如就乘个 4。大家看，是不是现在就变成在某个点之后，所有绿色线的值都比红色线大了，它在红线的上方了。

那个分界点大概是 $n_0 = 3$：从 $n = 3$ 开始，所有绿色线的取值都比红色线大。所以我们这个绿色线的函数，就是原本 $f(n)$ 的一个上界。

那用大 O 表示法写的时候，需不需要考虑那个系数？不需要。大 O 表示法会把那个系数 $c$ 直接去掉，光剩下 $g(n)$：

$$
O(n)
$$

这就是线性查找的答案表示——先找到原始的 $f(n)$，然后只要能找到一个 $g(n)$、保证它是 $f(n)$ 的渐近上界，就可以用大 O 括号把 $g(n)$ 写进去。这个例子里 $g(n)$ 就是 $n$，所以记作 $O(n)$。

#### 二分查找：O(log₂ n)

二分查找的函数式就是那个复杂式子。表达式看起来复杂，但它是不是也可以看成一个多项式？把 5 跟括号里这些乘进去，括号不要了，就变成 $5$ 乘以那一堆，再加上 $5 \times 1$ 和括号里面的 4——相当于整个加了个 9：

$$
f(n) = 5 \log_2 n + 9
$$

这样就能看成多项式了。加号前面是一项，后面那项也是一项。多项式里我们说了要找最高次项，像常数 9 这种肯定是最低项，直接去掉；前面这一项里，系数和 floor 函数都可以去掉。去掉之后剩下的，就是以二为底的 $n$ 的对数。

所以 $g(n) = \log_2 n$。把它画出来，这条紫色的线就是我们的 $g(n)$。

同样的道理，你现在看到的 $g(n)$ 好像又在红色线下面，还不能作为渐近上界。别忘了我们还可以乘一个系数：先乘 3，好像不够，还在下面；那你就多乘点，乘个 10。这回大家可以看到，它跑到所有红色线段的上方了，成为 $f(n)$ 的一个渐近上界。

因此对于二分查找法，用大 O 表示法写就是：

$$
O(\log_2 n)
$$

> **提示**：在 markdown 里写数学公式，先写两个 dollar，然后在两个 dollar 里面写大 O 括号和以二为底的 $n$ 的对数就可以了。

#### 化简的几条口诀

我们总结一下。已知了 $f(n)$，要求 $g(n)$ 函数还是非常容易的。

| 口诀 | 例子 | 为什么可以 |
| --- | --- | --- |
| 相乘的常量可以省略 | $f(n) = 100 n^2 \Rightarrow g(n) = n^2$ | 我们的 $g(n)$ 总是可以再乘一个常数 $c$，只要这个 $c$ 比你原来的 100 大一些，它增长就一定比你原来 $f(n)$ 要快，也就保证了 $g(n)$ 肯定在 $f(n)$ 的上面，所以这个常数是多少并不重要 |
| 多项式的低次项可以省略 | $n^2 + n \Rightarrow n^2$；$n^3 + n^2 \Rightarrow n^3$ | $n$ 再怎么变化，也没有 $n^2$ 变化的快；$n^2$ 也追不上 $n^3$ 增长的快 |
| 对数的底数不重要 | $\log_2 n$ 与 $\log_{10} n$ 等价 | $\log_2 n = \dfrac{\log_{10} n}{\log_{10} 2}$，而 $\log_{10} 2$ 就是一个常数，属于第一条那种情况 |
| 对数的常数次幂可以省略 | $\log^2 n$、$\log^3 n$ 前面的 2 和 3 | 道理一样，那个系数可以直接去掉 |

前两条是要记牢的，后面两条没那么重要，大家心里有数就行。

### 七种常见的大 O，从优秀到糟糕

我按时间复杂度从低到高排了个序。显然时间复杂度低的算法更好，高的更不好。这里一共列举了七种，我们逐一来看。

| 大 O 表示 | 称呼 | 曲线形态 |
| --- | --- | --- |
| $O(1)$ | 常量时间 | 一条黑色横线，跟 $n$ 再也没关系了 |
| $O(\log n)$ | 对数时间 | 绿色，稍微有点弧度，几乎紧贴着 x 轴 |
| $O(n)$ | 线性时间 | 蓝色直线，时间跟数据规模成正比 |
| $O(n \log n)$ | —— | 橙色，跟线性时间是同一档；归并排序就是这一档 |
| $O(n^2)$ | 平方时间 | 红色，幅度变化很大，非常靠上；类似的还有立方时间等等 |
| $O(2^n)$ | 指数时间 | 黑色，会在某一点之后超过前面的平方时间 |
| $O(n!)$ | $n$ 的阶乘 | 图上画不出来——画图软件放上去那条线就不对了，变化太大 |

先看第一种 $O(1)$。它跟数据规模还有关系吗？没关系了。说明这种算法跟数据规模完全无关，数据规模再怎么增长，算法执行的执行时间都是一个常数。这是最优的一种时间复杂度了。

第二种 $O(\log n)$。注意我们前面说过对数的底数没有关系，以二为底还是以十为底都一样。这种时间复杂度有个称呼叫对数时间，可以看到它也是一种非常优秀的时间复杂度。前面举例的二分查找，时间复杂度就是这一档。

第三个 $O(n)$，线性时间，就是前面介绍过的线性查找法这一档，意味着算法时间跟数据规模正好是成正比的。

第四个 $O(n \log n)$ 是橙色的，它跟刚才的线性时间其实是一档的。

第五个 $O(n^2)$ 是红色的，平方时间。

第六个 $O(2^n)$ 是指数时间，注意看，它在之后某一点会超过我们之前的平方时间，所以指数时间比平方时间还要更高一些。

最后第七种是 $O(n!)$，$n$ 的阶乘。这个图上没画出来，因为画图软件真放不上去——变化太大了，画出来那条线就不对。它应该是时间复杂度最高的。

> **结论**：常量时间和对数时间这两档都算非常优秀的算法了；线性和 $O(n \log n)$ 也算一档，属于第二段；至于平方时间、指数时间和 $n$ 的阶乘，就都属于比较差的算法了。

### Ω 与 Θ：另外两个符号

对这个大 O 表示法、也就是渐近上界有了一定认识之后，我们再来看另外两个概念，就非常好理解了——一个是渐近下界，一个是渐近紧界（这几个名字都是按单词的直接翻译来的）。

**渐近下界 $\Omega(g(n))$**：存在一个 $g(n)$ 函数，在某一个点之后它的值总是在 $f(n)$ 的下方。它代表的是算法执行的**最佳情况**、最优情况——它能代表的时间，不能比它再好了。

**渐近紧界 $\Theta(g(n))$**：从某个 $n$ 开始，$g(n)$ 乘 $c_2$ 就在 $f(n)$ 的上面，乘 $c_1$ 就在 $f(n)$ 的下面，把 $f(n)$ 夹在中间。它代表的含义就是既能作为上界也能作为下界，既能代表算法的最差情况，也能代表算法执行的最佳情况——两种情况都能代表，这就叫紧界。

学到现在我们学了三种时间复杂度表示法。大 O、欧米伽，还有 Θ。

> **结论**：实际当中哪种用得更多？大家的认识上可能是大 O——一般考试或者面试，人家问的都是这个大 O。但实际上 $\Theta$ 更好一些，因为它既能代表算法执行的最差情况，也能代表最佳情况。所以以后我在这边写文章的时候出现了 $\Theta$，大家也不要觉得奇怪。当然我还是以大家习惯的大 O 为主，只是有些时候会提到 $\Theta$。

### 空间复杂度：衡量算法的第二个维度

衡量算法好坏的第二个因素叫空间复杂度。之前学的时间复杂度，从字面意思理解就可以了——衡量这个算法在执行时间上的好坏。那空间复杂度同样从字面理解：衡量这个算法在空间占用上的好坏。

> **定义**：空间复杂度衡量一个算法随着数据规模的增大而占用的额外空间成本，它同样用大 O 表示法来表示。

注意是**额外**空间成本——原始数据占用的空间不算在内。就看你的数据量越来越大了，是不是要占用一些额外的空间。

还是以二分查找为例。输入的参数其实都算原始数据，所以我们就在"数组"和"要查找的目标"之外，看还有哪些空间上的占用：

```text
  额外空间  =  i 指针               4 字节
            +  j 指针               4 字节
            +  循环内的 mid 中间索引  4 字节
            ---------------------------------
              合计                  12 字节
```

有同学说了：这个循环不是每次都会产生新的 m 吗？

不会的。在大多数语言里，它这种占内存的方式，会预先估算出你这个方法内这些局部变量会占用多少空间。循环内的这个 mid，实际上是会重用这块空间的，不会说循环一次就多占用一个 mid 的 4 个字节——不会那么傻。

那它会不会随着数据规模增大而增大？也不会。数组内元素变成 1 万、10 万、100 万，i、j、mid 占用的内存都不变。

因此对于二分查找算法，它的空间复杂度是 $O(1)$——额外占用的只是一个常量的空间，就是那么 12 个字节，它不会再多占用，也不会随着 $n$ 的变化而变化。

### 二分查找的性能画像

最后我们把二分查找算法的性能完整总结一遍。

- **时间复杂度 · 最坏情况**：$O(\log n)$。因为我们已经用大 O 表示法来表示了，相当于只考虑了上界，那些常数系数、包括多项式的低阶项，都可以省略掉，所以最终就是 $O(\log n)$。
- **时间复杂度 · 最好情况**：$O(1)$。最好情况就是你要查找的元素正好在数组的中间索引位置，这时候只需要循环一次就能找到。哪怕数组内有一万个元素，恰好要查的就在正中间，它也只需要比较一次。用大 O 表示就是 $O(1)$，因为它跟数据量就没关系了。
- **时间复杂度 · 平均情况**：也是 $O(\log n)$。这个推导过程比较复杂，我就不推导了，都是些数学上的事，大家知道一下就可以。
- **空间复杂度**：额外只占用常数个指针，分别是 i、j、mid，因此额外占用的空间用大 O 表示是 $O(1)$。

> **易错点**：这里我问一下，我们用的是大 O 表示法，也就是渐近上界，那能不能用 Θ 呢？不能。因为紧界要求最坏情况、最好情况有一个共同的函数、同一个 $g(n)$，但大家看，我们的最坏情况是 $\log n$，最好情况是个常数 1，这俩不是同一个函数，所以二分查找不能用紧界表示。

## 二分查找：把比较次数摊平，再把负数返回值用对
> 对应块：BLK04 | 覆盖分集：P13-P15 | 块标题（分集名）：《基础数据结构-012-二分查找-平衡版》

### 向左找只比一次，向右找要比两次

我们先不谈优化，先把一笔旧账算清楚。

现在有一个有序数组，我要用它最基础那版二分查找去找一个元素。`while` 循环跑了几次我已经知道了——假设是 $L$ 次。我的问题是：循环体里那一串 `if / else if` 的比较运算，一共生成了多少次？

分两种情况问。

**目标在最左边。** 那么每一轮都是 `target < a[mid]` 成立，第一个 `if` 条件一定是满足的；既然它满足了，后面那个 `else if` 还会执行吗？不会。一旦 `if` 成立就不会再进 `else if`，所以每一轮只做 1 次比较，$L$ 轮下来一共 $L$ 次。

**目标在最右边。** 情况反过来了，每一轮都是 `target > a[mid]`，第一个 `if` 永远不成立，于是每次都得掉进 `else if`。这样每轮要先把 `if` 比一遍发现不成立，再去比 `else if`，一共 2 次，$L$ 轮就是 $2L$ 次。

```text
目标在最左：target < a[mid] 每轮都成立
    轮 1    if 成立                 → 1 次比较，else if 被短路跳过
    轮 2    if 成立                 → 1 次
     ⋮
    轮 L    命中，退出循环           → 1 次
    ─────────────────────────────────────
    合计    L 次比较

目标在最右：target > a[mid]，if 每轮都不成立
    轮 1    if 不成立 → else if 成立  → 2 次比较
    轮 2    if 不成立 → else if 成立  → 2 次
     ⋮
    轮 L    else if 成立，命中并退出 → 2 次
    ─────────────────────────────────────
    合计    2L 次比较
```

看出问题了吧。基础版二分查找是不平衡的：往左走成本低，每轮只比一次；往右走成本高，每轮要比两次。既然有便宜的一半和贵的一半，那就总有改进空间——下面这一版要做的就是把这两半拉平。

### 左闭右开：让每轮只比一次

#### i 可能是目标，j 一定不是

改法从指针的语义开始。同样是 `i` 和 `j` 两个指针，但这回我们管的是**左闭右开**的区间 $[i, j)$。

```text
index:     0    1    2    3
a:        10   20   22   30
           ^              ^
           i              j   ← j 落在数组右边的空白处，绝不可能是目标

待查找区间 = a[i .. j-1]，也就是 10、20、22、30 一共四个元素
```

记住这条：`a[i]` 有可能就是我们要找的目标，`a[j]` 一定不是——它压根就是一个边界。j 只是"待查区间的右端点之外那一格"。这就是左闭右开的意义，它直接决定了后面 `else` 分支该怎么写。

#### while 条件就是"区间里还剩几个元素"

新的循环条件不再是 `i <= j`，而是 `j - i > 1`。

怎么理解 `j - i`？它就是当前范围内待查找的元素个数。个数大于 1，就说明还不止一个候选者，继续循环、继续缩小区间；一旦只剩一个元素，就退出循环。

拿上面这个四元素的例子看：刚开始 `i=0`、`j=4`，范围内有四个待查找元素，条件成立。跑到最后一步你会发现 `a[j]` 已经不在范围内了——它不是目标——这恰恰说明区间里只剩 `a[i]` 这一个元素了，此时退出循环。

#### 循环只负责收缩，最后一次比较挪到循环外

这是改动后算法最关键的一点，也是它跟前面所有版本最大的不同：**它不在循环内找出那个目标元素**。循环的唯一职责就是把边界缩小；当范围内只剩 `i` 指向的那一个元素时，循环退出，然后才在**循环外面**去比较 `a[i]` 跟目标是否相同。

换句话说，"找到"这个动作被从循环里搬出来了。既然比较被搬到了循环外，循环里就只需要"这一轮往哪边收缩"这一个判断——

#### else 分支为什么必须是 i = m

进循环先算中间索引，这跟前面没什么区别，不多说。接下来看 `if / else`：还有没有那个 `else if`？没有了。就剩一个 `if` 和一个 `else`，所以循环内每轮只可能做一次比较——左边一次、右边也是一次，平衡了。

`if` 分支和从前一样：目标小于中间值，说明目标在左侧，那就把右边界 `j` 收缩到 `m`。这没什么可说的，跟我们以前写的那版完全一致。

真正变了的是 `else`。因为没有 `else if` 了，一旦进了 `else`，意味着目标**要么等于中间值，要么大于中间值**——也就是说，目标有可能就正好在 `m` 上。既然如此，`i` 就不能再写成 `m + 1`，必须写成 `m`。

举个例子。我们要找的目标是 22，而中间索引 `m` 指向的元素恰好就是 22。此时 `target >= a[m]` 成立，程序进了 `else`。进了 `else` 就必须让 `i` 留在 `m` 这个位置上；如果还按老习惯写 `i = m + 1`，那 `i` 一路就跑到 30 去了，把 22 整个错过。

所以 `else` 分支的这一条赋值语句变了：**中间值本身必须被包含在内，而不是跳到中间值加一的位置。** 这是跟之前最不一样的地方。

### 平衡版的代价：最好情况不再是 O(1)

先说优点。这个算法的目的就是减少循环内的比较次数，现在只剩 `if / else` 了，每次循环只比一次——原来目标在左边只要 1 次、在右边却要 2 次，现在左右一律 1 次，循环内的平均比较次数确实降下来了。

不过这个优点有个前提：**必须在数据量非常大的时候才能体现出来**。数量小的话，这点差异并不明显，别指望在小数组上看出什么区别。

再说缺点。我们在分析基础版时间复杂度的时候提过一个最好情况：如果待查找元素恰好在数组正中央，第一轮就比中了，中间元素跟目标相等，直接退出循环，这时候只需要一轮，时间复杂度是 $O(1)$。

改动之后这个最好情况没有了。因为我们刚才说了，循环必须先跑完、退出循环之后才去比较，所以不存在"第一轮就命中直接返回"的情形了。最好情况和最坏情况全都是 $O(\log n)$。

这时候表达式就可以换一种写法了——因为上下界可以用同一个函数来描述，我们把它写成 $\Theta(\log n)$。

> **易错点**：平衡版换来的不是"整体更快"，而是"比较次数更均匀"。它牺牲了 $O(1)$ 的最好情况，换来每轮恒定 1 次比较。这个缺点可以忽略，但别再拿"命中中间值一次就返回"去描述这一版了。

完整的代码形态是这样：

```java
public static int bsearch(int[] a, int target) {
    int i = 0;
    int j = a.length;          // 左闭右开：a[j] 越界，不可能是目标
    while (j - i > 1) {        // j - i 就是范围内待查找的元素个数
        int m = (i + j) / 2;
        if (target < a[m]) {
            j = m;            // 目标在左侧，右边界收缩到 m
        } else {
            i = m;            // 目标 >= a[m]，必须停在 m，不能是 m + 1
        }
    }
    // 循环只负责收缩边界，最后一次比较挪到循环外面做
    return a[i] == target ? i : -1;
}
```

拿前面那个数组 `[10, 20, 22, 30]` 找 22 走一遍：`j - i = 4 > 1`，`mid = 2`，`a[2] = 22`，`22 < 22` 不成立，走 `else`，`i = 2`；`j - i = 2 > 1`，`mid = 3`，`a[3] = 30`，`22 < 30` 成立，`j = 3`；`j - i = 1`，退出循环；在循环外比较 `a[2] = 22` 与目标，相等，返回 2。

### Java 的 Arrays.binarySearch 是怎么写的

Java 里的二分查找不在某个工具类里，而在 `java.util` 包下的 **`Arrays`** 类中。它有一大堆以 `binarySearch` 命名的方法，区别只在于处理的数据类型不一样——`byte[]`、`char[]`、`double[]` 等等。我们挑最熟悉的处理 `int[]` 的那个来讲，因为它们的实现都是类似的。

看参数。第一个参数就是待查找的那个数组，第二个参数是要查找的目标值，只不过命名习惯跟我们不一样：我们管它叫 `target`（目标），它管它叫 `key`。它内部又调了另一个叫 `binarySearch0` 的方法，并且多传了两个参数进去——一个是 0，一个是数组长度。

进入 `binarySearch0`：`low` 就是左边界，含义跟我们写的 `i` 一样；`high` 就是右边界，含义跟我们写的 `j` 一样。它们的取值分别来自刚才那两个多出来的参数——`low` 就是那个 0，`high` 是数组长度减 1。

光看这个出手招式你应该就能猜出来：它用的是二分查找的**基础版**。既然是基础版，`low` 和 `high` 都可能指向要查找的目标，所以 `while` 循环条件必然是 `low <= high`——必须带上等于，保证最后 `low == high` 时指向的那个元素也还能参与一次比较。想起来了吧。

循环里面先算中间索引，用的是**无符号右移运算符**代替除法，这样能避免出现负数的问题。然后取出中间值，接着比较。

#### 判断顺序：先右、再左、后相等

比较的写法和我们的习惯不一样。我们是先看目标是不是在左边，再看是不是在右边；它呢，是**先看目标是不是在中间值的右边**。

```java
public static int binarySearch(int[] a, int key) {
    int low  = 0;                  // 第二个传进来的参数：左边界
    int high = a.length - 1;       // 第三个传进来的参数 - 1：右边界
    while (low <= high) {
        int mid    = (low + high) >>> 1;   // 无符号右移代替除 2，避免负数
        int midVal = a[mid];
        if (key > midVal) {
            low  = mid + 1;        // 目标在中间值右边，左边界右移
        } else if (key < midVal) {
            high = mid - 1;        // 目标在中间值左边，右边界左移
        } else {
            return mid;            // 相等，直接返回中间索引
        }
    }
    return -(low + 1);             // 找不到：-(插入点 + 1)
}
```

到这里为止，它跟我们前面写的代码几乎一模一样，除了比较的次序稍有不同。既然是三分支，那这个算法里哪一种方向成本更高呢？是**向左找**成本更高一些——因为向左走你要比较两次，`if` 比一次不成立、`else if` 再比一次；而向右找的成本低一些，因为它只需要 `if` 那一次比较。顺带挑个小毛病：它这里要是先用小于号就更好了，小于号跟我们的习惯一致，也跟它后面这个"先右"的思路更搭。

#### 找不到时返回的不是 -1

接下来是不一样的地方。我们的代码循环走完没找到，直接 `return -1`；Java 这个实现不这么干，它返回的是**左边界加一，再取个负号**——也就是 `-(low + 1)`。

返回的当然还是个负数，但它不是简单的 -1，那这个负数究竟是什么意思？去读它的文档。文档里有两段标签，`params` 讲参数的含义，`returns` 讲返回值的含义。`returns` 这段话说得很清楚：如果查找的 `key` 已经被包含在数组中，返回的是 `key` 的索引；否则，返回的是一个**负的** "-(insertion point) - 1"。插入点，一个新的词。它返回的是负的插入点，再减掉一个 1。

### 负数返回值的真正含义：插入点

#### 插入点是谁

先问一个更根本的问题：二分查找没找到的时候，究竟谁来代表这个"插入点"？

拿 `[2, 5, 8]` 这个数组举例。找一个比所有元素都小的值，比如 0——将来这个 0 如果要插进这个有序数组，它应该插到哪个位置？索引 0。看程序跑完的结果，是不是 `i` 指向的正是索引 0？就先做一个大胆的假设：这个 `i` 就相当于插入点。

再多试几个。找 20，它该插到索引 4 的位置，跑完看，`i` 指向的正好是 4，假设成立。

再试个更大的：找 40。这时候你会发现图上 `i` 没了，只剩个 `j`。往回倒一步看——因为要找的是 40，`i` 要先做一个 `m + 1` 的动作，也就是 7 + 1 = 8，执行完就退出循环了。我的图上没有把超出数组范围的那个 `i` 画出来，但它确实存在，取值就是 8。而 40 要插进这个数组，索引也应该是 8。没问题。

所以我们证明了——虽然这个证明并不特别严格——对于基础版二分查找算法，插入点的位置用 `i` 这一个变量表示就够了。

回到 Java 的代码：`low` 的含义跟我们代码里 `i` 的含义是一样的，所以 **`low` 就是插入点**。整个返回值就是把 `low` 变成负数：因为这个方法返回 0 和正数表示"找到了"，必须返回负数才表示"没找到"，所以把 `low` 取个负数返回。

#### 文档里的例子

我们用几个例子把"插入点"这个词坐实。数组 `[2, 5, 8]`，调用 `Arrays.binarySearch`，把数组和目标值作为参数传进去：

| 查找的 key | 在数组中 | 返回值 | 真实插入点索引 |
| --- | --- | --- | --- |
| 4 | 否 | `-2` | 1 |
| 1 | 否 | `-1` | 0 |
| 9 | 否 | `-4` | 3 |
| 5 | 是 | `1` | —— |

换算的方法就是文档里那半句 `-(insertion point) - 1`：把 1 移到等式的左边来，就相当于 `返回结果 + 1` 等于负的插入点，再把前面的负号去掉。

- 查 4 得到 -2：`-2 + 1 = -1`，去掉负号得到 **1**。所以 4 将来插进 `[2, 5, 8]` 的索引位置是 1，它应该插到 2 和 5 之间。
- 查 1 得到 -1：`-1 + 1 = 0`，**0**。1 要插进这个升序数组，索引位置是 0——它最小嘛，只能插在最前面。
- 查 9 得到 -4：`-4 + 1 = -3`，去掉负号得到 **3**。9 比所有元素都大，插到索引 3，也就是 8 的后面。

#### 为什么非要减掉那个 1

做到这一步，有个同学一定会问：我把这个 `low` 直接取个负数返回不就行了吗？为啥还要再减一个 1？

因为返回 `-0` 和返回 `0` 是区分不出来的。计算机里的整数，正零和负零其实是同一个值，`0 == -0` 永远为真。

拿刚才那个例子说：找一个比所有元素都小的值，它将来的插入点就是索引 0。假如这时候直接返回 `-0`，它跟 0 一模一样，那你到底是要表达"我命中了索引 0 上的那个元素"，还是"我没找到，插入点是 0"？根本区分不了。

所以必须在插入点的基础上再加一个 `-1`，才能跟"找到了"的情况彻底分开。这就是那个 `-1` 存在的全部理由。

### 顺着插入点把元素插进去

知道返回值的含义之后，就能在二分查找的结果上直接接一个插入操作。

先判断：如果这个返回结果小于 0，说明元素不在数组里，那我们就去做插入。插入之前得先拿到真正的索引值，我们给它起个变量名 `insertIndex`——就是插入点的索引位置。它的取值应该等于返回值加上 1。注意 `-2 + 1` 之后可能还是负数，所以还得求一个绝对值，Java 里可以直接用 `Math.abs`。

```java
int r = Arrays.binarySearch(a, target);
if (r < 0) {                            // 没找到，r 是负数
    int insertIndex = Math.abs(r + 1);  // 真正的插入点索引
    int[] b = new int[a.length + 1];    // Java 的数组不会自动扩容，得新建

    System.arraycopy(a, 0, b, 0, insertIndex);                    // ① 插入点之前
    b[insertIndex] = target;                                      // ② 目标落到插入点
    System.arraycopy(a, insertIndex, b, insertIndex + 1,          // ③ 插入点之后
                     a.length - insertIndex);

    System.out.println(Arrays.toString(b));
}
```

因为 Java 中的数组没有自动扩容，所以第一步得创建一个长度是旧数组加一的新数组，然后分三步搬。

```text
old a:    [ 2   5   8 ]
            ↑
            insertIndex = 1

step 1:   [ 2   0   0 ]        ← System.arraycopy(a, 0, b, 0, insertIndex)
step 2:   [ 2   4   0 ]        ← b[insertIndex] = target
step 3:   [ 2   4   5   8 ]    ← System.arraycopy(a, insertIndex, b, insertIndex + 1, ...)
```

以 `[2, 5, 8]` 插入 4 为例，插入点是索引 1。第一步用 `System.arraycopy` 把插入点之前的元素拷到新数组：第一个参数是旧数组 `src`，第二个参数是从哪个索引开始拷，显然从 0 开始；第三个参数是目标数组 `b`；第四个参数是目标数组的起始索引，也是 0；最后一个参数是拷贝的长度，就是 `insertIndex`（原本写成"索引位置减 0"，减 0 可以直接忽略）。拷完新数组是 `[2, 0, 0]`，其余位置刚开始都是 0。

第二步，把 `target` 放到插入点这个位置，新数组变成 `[2, 4, 0]`。

第三步，把旧数组插入点之后的 5 和 8 拷到新数组的相应索引。注意这回起点变了：源数组的起点是插入点 `insertIndex`，而目标数组的起点应该是**插入点加一**（因为插入点那一格已经被 target 占了），所以第四个参数写 `insertIndex + 1`；拷贝的长度是 `a.length - insertIndex`，正好是 5 和 8 的长度。最终得到 `[2, 4, 5, 8]`——把数组中没有的元素插到了它的正确位置。至于插入到最前面的情况、以及插入点之后右侧那一段的具体情形，留着大家自己试验，代码其实一个字都不用改。

### 重复元素：leftmost 版本

#### 基础版返回的是"第一个碰到的"，不是最左侧的

现在来看二分查找算法对于**重复元素**的处理。基础版的代码碰上数组 `[1, 2, 3, 4, 4, 5, 6, 7]` 这样的数据，里面是有重复元素的。我们查找重复元素 4：第一次求中间索引指向的元素恰好就是目标，所以它直接返回了，不会再继续找别的。也就是说，基础版遇到重复元素时，返回的是**它第一个遇到的那个**，其他的就不管了。

那它返回的是不是最左侧的呢？有同学会说"这不就是返回的最左侧吗"——注意，这不是。那只是碰巧了。中间索引第一次就落在 3 上，而 3 恰好就是最左侧的 4。我们把数据稍微改一改，让数组变成 `[1, 2, 4, 4, 4, 5, 6, 7]`（三个 4），再跑一遍基础版，得到的还是 3，而真正的最左侧是索引 2。它每次找的还是第一个碰到的 4，并不是最左侧的那个 4。

所以需求来了：能不能改进一下，让它在有重复元素的时候，返回**所有重复元素里最左侧的那个**。

#### 候选位置：记下来，还得继续往左走

先不看代码，我们从执行过程理解思路。还是找 4，找最左侧的 4。

第一步肯定先确定中间点。中间点的元素跟目标相等了——它一定是我们最后的结果吗？**不一定**，因为有可能左边还有更靠左的 4。

不过这个中间点位置有用没有用？有用。虽然它不一定就是最终结果，但**它可以作为一个候选的位置**——它毕竟当前这个元素跟我们待查找的目标是相等的。所以我们先把它记录下来。但记录候选位置并不意味着算法结束，**我们还要在它的左侧继续找，看有没有更靠左的 4**，也就是继续缩小 `j`，让 `j = m - 1`。

新的中间点出来了，这回跟目标不等，那就扩大 `i`，让 `i = m + 1`，在这个范围继续找。

又找到一个中间点 `m`，这回它指向的元素又跟目标相等了。应该做什么？把刚才记录的候选位置更新一遍——现在有更靠左的那个 4 了，候选者要换成它。

然后继续向左找，再让 `j` 减一，这时候 `i` 就大于 `j` 了，退出循环。此时候选者记录的位置，就是我们要查找的目标位置。

整个过程在这张表里：

```text
index:   0  1  2  3  4  5  6  7
value:   1  2  4  4  4  5  6  7

轮次   搜索区间          mid   a[mid]   这一轮做什么
  1     i=0 .. j=7        3      4     相等：candidate = 3，j = m - 1 = 2
  2     i=0 .. j=2        1      2     不等：i = m + 1 = 2
  3     i=2 .. j=2        2      4     相等：candidate = 2，j = m - 1 = 1
  4     i=2 > j=1，循环结束 → 返回 candidate = 2
```

再找一个 6，过程是类似的：第一个中间点取到的值是 4，跟 6 不一样，就到它右侧去找；接着某个中间点指向的元素跟目标相等了，先把它作为候选者记录下来，然后 `j = m - 1` 到左侧看有没有更靠左的 6；下一轮求出的中间点是 5，5 跟目标不等，那就扩大 `i`，让 `i = m + 1`，这时 `i` 已经大于 `j`，退出循环。候选者指向的那个 6，就是最左侧的 6。

思路就这么多：**相等时记一个候选者，然后不停止，继续往左走；循环走完，候选者就是答案。**

#### 代码只需要改 else 分支

接下来实现代码。要不要从头写？不用。把最开始那个基础版的代码复制一份，在它基础上改就行，注释去掉先不管。

哪些地方需要改动？确定左右边界的范围、判断要不要退出循环、以及求中间索引——这些逻辑跟以前一样，不用写。甚至接下来判断"目标跟中间值不相等"的那两种情况，跟以前比也一样，也不用动。

**不一样的主要就是这个 `else`**，也就是当中间索引指向的值跟目标相等时的处理逻辑。所以我们只要考虑这一块的改动。

相等的时候，我们是不是立刻返回这个 `m`？不是了。我们要把 `m` 指向的位置先记录下来——前面说过这个思路，先记录下来作为一个候选者，因为你不确定它左边有没有更靠左的元素。所以定义一个变量专门用来记录候选位置，名字就叫 `candidate`（候选者），初始值是 `-1`，表示还没有任何候选者。

当中间索引 `m` 指向的值跟目标相等时，让 `candidate = m`，把这个位置记录下来。记录下来之后，是不是继续还要向左查找？因为我们要找的是最左侧的。向左查找就是缩小 `j` 这个边界，让它等于 `m - 1`。

在缩小边界的过程中，如果又遇到新的 `m`，它指向的值又跟目标相等，那就又走到 `else` 了，这时候更新候选位置就行。

直到什么时候退出呢？直到循环结束，`i > j` 的时候。退出以后直接返回这个候选者的位置，因为它记录的就是我们最靠左的那个重复元素；当然如果一次都没匹配上，就返回它的初始值 `-1`。

```java
int candidate = -1;          // -1 表示还没有任何候选者

while (i <= j) {
    int m = (i + j) / 2;
    if (target < a[m]) {
        j = m - 1;
    } else if (target > a[m]) {
        i = m + 1;
    } else {
        candidate = m;       // 先记下来，不急着返回
        j = m - 1;           // 还要继续往左找
    }
}

return candidate;            // 一次都没相等，就是初始值 -1
```

除了这段 `else`，其余部分——指针初始化、`while` 条件、`mid` 的计算、两个不相等的分支——跟基础版一字不差。

#### 验证

测试用例我已经提前写好了。数组里有这些情况：查 1，返回索引 0；查 2，返回索引 1；查重复元素 4，最靠左的那个位置是 2，所以应该返回 2；查 5，索引 5；查 6，索引 6；查 7，索引 7。没找到的情况也挑了几个：查 0、查 3、查 8，这几个元素都不在数组里，全部返回 -1。

跑一下测试用例，所有断言都通过了，说明 leftmost 这个版本没问题。其实它的改动非常简单，主要就是用一个 `candidate` 变量记录候选位置，以及相等的时候不断继续向左走、缩小 `j` 的边界，把这两点把握住就可以了。

### rightmost：只换一个方向的边界

既然有叫 leftmost 的版本，大家应该能想到它应该有一个对称的 rightmost 版本：leftmost 是在重复元素里找最靠左的，那自然就有一个 rightmost 是在重复元素里找最靠右的。

代码不用从头写，它跟 leftmost 是完全对称的，把两个版本截图对照着看就会发现非常像：同样要用一个 `candidate` 来记录候选位置，同样是每次中间值跟目标相等的时候把它记录下来、更新这个候选位置。**唯一的区别是方向**：leftmost 发现相等了要向左找，把 `j` 缩小；rightmost 发现相等了要向右找，把 `i` 扩大，让 `i = m + 1`，不断地向右找，直到找到最右侧的那个候选者。当然如果都找不到，候选者同样返回 -1。

```java
} else {
    candidate = m;       // 同样先记录
    i = m + 1;           // rightmost：向左找改成向右找，缩小 j 改成扩大 i
}
```

就这一处不一样，其他都一样，所以我不带大家从头写了。测试用例也准备好了，跑一下就能确认。数组里有三个重复的 4，这回要找最右侧的 4，它应该是索引 4——跑出来也通过了。

## 二分查找的 leftMost 与 rightMost：把 -1 换掉，再谈排名、前任和范围查询
> 对应块：BLK05 | 覆盖分集：P16-P18 | 块标题（分集名）：《基础数据结构-015-二分查找-LeftRigh》

### 先把 -1 扔掉

刚才我们把二分查找的 leftMost 和 rightMost 两个版本都讲完了。leftMost 查找的是与目标相等的**最靠左**的索引，rightMost 查找的是与目标相等的**最靠右**的索引，找不到的时候，两个方法都返回 `-1`。

你把这两个方法并排看一眼就会发现：找不到的情况，它们给回来的东西一模一样，都是 `-1`。而这个 `-1` 其实没啥用——往后学你会越来越明显地感觉到，一个只能告诉你"没有"的返回值，能承载的信息量太瘦了。

那能不能返回一个比 `-1` 更有用的值？完全可以。今天这一讲剩下的时间，我们就干这一件事：**把 leftMost 的返回值改成 `i`，把 rightMost 的返回值改成 `i - 1`**，然后看看这两个数字到底代表什么、能撑起哪些应用。

### leftMost：把 -1 换成返回 i

先把 leftMost 原来的代码放在这儿，作为对照：

```java
// leftMost 1：返回与目标相等的最靠左索引，找不到返回 -1
public static int leftMost(int[] a, int target) {
    int i = 0;
    int j = a.length - 1;
    int candidate = -1;          // 候选位置

    while (i <= j) {
        int m = i + ((j - i) >> 1);
        if (a[m] == target) {
            candidate = m;       // 命中就记下这次的位置
        }
        if (target < a[m]) {
            j = m - 1;
        } else if (target == a[m]) {
            j = m - 1;           // 命中也继续往左，才能摸到最左边那个
        } else {
            i = m + 1;
        }
    }
    return candidate;
}
```

理解过这个版本，我们就不重复解释一遍了，直接拷贝一份改成 leftMost 2。

#### 顺手把代码再瘦两圈

拷贝过来之后，我们让它统一返回 `i`，不再返回 `-1`。这个 `i` 的含义待会儿再解释，先改代码。

改完 `return i` 之后，你立刻会发现一个问题：那个 `candidate` 候选位置的变量，还有用吗？根本用不上了——循环结束时它一次都没被赋值机会用上，直接删掉，代码就短了一截。

删掉它之后，条件还能再合并一层。你看这两句：

- `target < a[m]` 的时候，要向左找，`j = m - 1`
- `target == a[m]` 的时候呢？也要向左找，`j = m - 1`

两个条件执行的语句完全一样，那就能合成一个。把等于的条件直接挪上来，写成 `if (target <= a[m])`，原来的 `else` 就省了，`else if` 也直接降级成 `else`。改完之后代码就是下面这样：

```java
// leftMost 2：返回“大于等于 target 的最靠左索引”
public static int leftMost2(int[] a, int target) {
    int i = 0;
    int j = a.length - 1;

    while (i <= j) {
        int m = i + ((j - i) >> 1);
        if (target <= a[m]) {
            j = m - 1;          // 小于等于中间值，都往左
        } else {
            i = m + 1;          // 大于中间值，往右
        }
    }
    return i;
}
```

> **提示**：`i` 是在循环里一路向右累加出来的。如果数组里所有元素都比 target 小，它会一路加到底，最后指向 `a.length`，也就是越界位置。所以 leftMost 2 的返回值不能无脑当索引用，边界得自己判一下。

#### 找到时、找不到时，i 指向哪

改完先别急着下结论，我把这段代码做成了网页，直接跑实际结果，用跑出来的 `i` 来理解它的含义——这比在脑子里空推要靠谱得多。

**第一种，查一个存在的值。** 比如查 `4`，直接跳到最后一步，你看 `i` 指向的位置：它指向的恰恰就是与目标相等的、最靠左的那个索引。找到了的情况下，这个 `i` 的含义和改动前一模一样。

**第二种，查一个不存在的值。** 比如查 `3`，数组里根本没有 3。还是跳到最后一步，`i` 指向的是 **4**。

这个怎么理解？注意我们的目标是 3，所以这个 `i` 找到的是一个**比目标大的**元素，而且是最左侧的那一个。比 3 大的、最靠左的，不就是 4 吗？这就是找不到时 `i` 的含义。

**第三种，有同学问：这个靠不靠谱呢？那我们再试一个。** 这次查 `5`。数组里也没有 5。按照刚才的说法，结果应该是 **7** 这个位置——比 5 大的元素里最靠左的那个就是 7，它没有别的候选了，这个值天然就是最靠左的。跑出来一看，果然指向 7。

> **结论**：把找到和没找到两种情况合到一起，返回的 `i` 代表的就是**大于等于 target 的最靠左的那个索引位置**。

### rightMost：把 -1 换成返回 i - 1

rightMost 版本用同样的思路改，只不过返回的不是 `i`，而是 `i - 1`。代码一样先拷贝过来，`candidate` 一样删掉。

分支合并的方向反过来了：原来是 `target > a[m]` 和 `target == a[m]` 两个分支，执行的都是 `i = m + 1`，那就合成 `if (target < a[m]) { j = m - 1 } else { i = m + 1 }`。意思是：将来 target 大于等于中间值的时候，都走 else 这一支。

```java
// rightMost 2：返回“小于等于 target 的最靠右索引”
public static int rightMost(int[] a, int target) {
    int i = 0;
    int j = a.length - 1;

    while (i <= j) {
        int m = i + ((j - i) >> 1);
        if (target < a[m]) {
            j = m - 1;
        } else {
            i = m + 1;          // 大于等于中间值，都往右
        }
    }
    return i - 1;
}
```

验证的路子跟刚才一模一样。查一个**存在**的 `4`，`i - 1` 落在索引位置 5，那正是最右侧的那个 4——跟改动之前的返回值含义一样。查一个**不存在**的 `5`，`i - 1` 落在索引 5，那个元素是 4：比目标小，并且在所有比目标小的元素里是最靠右的。两种情况一合：

> **结论**：rightMost 2 返回的 `i - 1` 代表的是**小于等于 target 的最靠右的那个索引位置**。

看到这儿你会发现一个漂亮的对照：一个 `>=` 配"最靠左"，一个 `<=` 配"最靠右"。这两个方法合起来，就正好卡住了一个区间左右两端的所有边界。

### 应用：排名、前任、后任、最近邻居

有了上面这两个返回值，能做的事还挺多的：求排名、求前任、求后任、求最近邻居，再做一些范围查询。在讲这些应用之前，我们先把几个名词对齐，不然公式容易记混。这几个名字我都是临时画在图上的，笔记里相应的公式都有，不用死记。

```text
下标: 0   1   2   3   4   5   6  ...
元素: 1   2   4   4   4   7  ...
```

读图：这是一段升序数组，三个 4 挤在中间，靠左的 1、2 和靠右的 7 各自站在自己的位置上；下面所有的例子都拿它当尺子量。

> **定义**：**排名**，指 target 在这个数组里排第几。比 target 小的元素有几个，它自身就是第几。比如图里的 5，比它小的有 1、2、4、4、4 共五个，所以排名第六。

> **定义**：**前任**，指所有比 target 小的元素里，最靠右的那个。图里 5 的前任就是 4。注意得取最靠右的那个 4，取靠左的那个就不叫前任了，那叫前前前任。

> **定义**：**后任**，指所有比 target 大的元素里，最靠左的那个。图里 5 的后任就是它右边第一个 7。

> **定义**：**最近邻居**，就是把前任和后任放在一起，看谁离 target 更近，答案就是谁。

#### 排名：leftMost(target) + 1

求排名该用哪个版本？我先问大家一句：要求 4 的排名，用 leftMost 还是 rightMost？

显然要用 **leftMost**。为什么？因为你得先摸到**最左侧**的那个 4，才能知道它的排名——图里比 4 小的有 1 和 2，所以排名是 1、2、3，4 排第三。既然要最左侧，那就只能是 leftMost。

```java
int idx = leftMost2(a, 4);   // 最左侧 4 的下标 = 2
int rank = idx + 1;          // 排名 = 3
```

这里差了一个 1，原因是：索引从 **0** 开始（0、1、2……），排名从 **1** 开始（1、2、3……）。所以求出最左侧那个 4 的索引之后，最后加个 1 就是它的排名。

那如果 target 是数组里没有的元素，能不能用同一个公式？可以。我们传一个 `5` 进去，leftMost 2 返回的是大于等于 5 的最靠左索引，那就是第一个 7，它的位置数下来是 5，再加上 1 等于 6。把 5 放进这个数组里，它确实排第六。

> **结论**：求排名 = `leftMost(target) + 1`。

#### 前任：leftMost(target) - 1

求前任用 leftMost 还是 rightMost？显然不该用 leftMost 以外的东西——想求 4 的前任，你就得先找到最左侧的那个 4，然后索引减掉 1，正好是它左边贴着的那一个 2。

```java
int idx = leftMost2(a, 4) - 1;   // 2 - 1 = 1，a[1] = 2，就是 4 的前任
```

数组里没有的元素同样成立。想求 5 的前任，就是 `leftMost2(a, 5) - 1`。leftMost(5) 返回大于等于 5 的最靠左索引，也就是第一个 7 的位置 5；再减掉 1，落到位置 4，那个元素是 4。五的前任不就是这个 4 嘛，没问题。

> **结论**：求前任 = `leftMost(target) - 1`。

#### 后任：rightMost(target) + 1

求后任就不能用 leftMost 了，用的是 **rightMost**。求 4 的后任，先找到**最右侧**的那个 4，索引加上 1，就得到它右边那个 7。

数组里没有的也一样。求 5 的后任，`rightMost(a, 5) + 1`：rightMost 找的是小于等于 5 的最靠右索引，小于等于 5 的实际上就是那个 4，取最靠右的，就是最后这个 4；加 1，得到 7。所以五的后任是它右边的 7。

> **结论**：求前任是 `leftMost - 1`，求后任是 `rightMost + 1`。**往前看用 leftMost，往后看用 rightMost**。

#### 最近邻居：把前任后任放一起比

最近邻居我就不演示了，比较简单：它要先把前任求出来，再把后任求出来，然后在这前后任里面挑一个更近的。

图里 5 的前任是 4，它跟 5 中间隔了一个位置；而 7 跟 5 之间隔了两个位置。所以 4 才是 5 的最近邻居，7 离得更远一些，就不是了。

### 范围查询：把不等号翻译成索引区间

所谓**范围查询**，就是给出一个目标值，然后我要找数组内所有小于目标、大于目标、小于等于目标、大于等于目标的元素——按这种"小于啊""大于啊"的条件去查询，我们就称之为范围查询。

它的诀窍是：你根本不用去遍历，只要把条件翻译成一段**索引区间**，那一段里全是答案，区间外一个都不是。

#### 四种基本区间

还是拿那张图，目标都取 `4`。小于 4 的元素，图中就他俩——1 和 2，也就是从下标 0 到最左侧那个 4 的前一位。

大于 4 的，图中也有——四右边的那些；大于等于 4 的不一样了，几个 4 本身也要算进去。四种条件翻译出来是这样：

| 查询条件 | 索引区间 |
| --- | --- |
| `x < target` | `[0, leftMost(target) - 1]` |
| `x <= target` | `[0, rightMost(target)]` |
| `x > target` | `[rightMost(target) + 1, ∞)` |
| `x >= target` | `[leftMost(target), ∞)` |

规律很好记：**"小于"收左端，"小于等于"收右端；"大于"动左端，"大于等于"动右端。** 前两条是从下标 0 一直扫到边界，所以边界只能由 leftMost 或 rightMost 提供；后两条是拿边界当起点往右一扫到无穷，所以起点也只由这两个方法给。

#### 组合区间：四 到 七 之间

这四种基本条件之间是可以组合的。再提一个需求：`x >= 4` 并且 `x <= 7`。

含边界的这种很好办：从 4 的 leftMost 开始，一直到 7 的 rightMost 为止。

```java
int from = leftMost2(a, 4);
int to   = rightMost(a, 7);
// 区间 [from, to]
```

那如果还是刚才那个问题，`x > 4` 并且 `x < 7` 呢？两个等号都摘掉。

- 左边：4 不能包含在内，那就得往右找，所以起点是 `rightMost(4) + 1`；
- 右边：7 不能包含在内，那就得往左找，所以终点是 `leftMost(7) - 1`。

```java
int from = rightMost(a, 4) + 1;
int to   = leftMost2(a, 7) - 1;
```

> **结论**：`target1 <= x <= target2` 用 `[leftMost(target1), rightMost(target2)]`；`target1 < x < target2` 用 `[rightMost(target1) + 1, leftMost(target2) - 1]`。含不含等号，就决定了你用哪一个方法、要不要加减 1。

关于范围查询就讲到这里，具体的公式我都已经给大家推出来了，剩下的实力你们自己去试验好吧。

### 力扣 704：三种写法一次过

接下来我们刷一道力扣的题目，704 题。标题都告诉你了，就是要考二分查找。

题目是：给定一个 n 个元素的**有序**整型数组 `numbers`，并且告诉我们这个数组是升序的，还给了一个目标值 `target`，让你写一个函数在数组中搜索 `target`。目标存在就返回下标，也就是我们说的索引；找不到就返回 `-1`。

这跟二分查找的描述一模一样。题目给了两个例子：一个是搜索一个存在的元素（比如 9），存在就返回下标；另一个搜索的值（比如 2）数组里没有，那就返回 `-1`。下面还有几个提示：数组中元素**不重复**，所以我们不用考虑元素重复的问题，反正找到就算对，不用纠结是找最左边还是最右边；`n` 的取值比较小，只在 1 到 1 万之间，这意味着我们这个数字再加也不会超过 `int` 能表示的最大整数范围，所以不用考虑正数相加变负数的问题——你直接用除法算中点都没问题，不用移位也可以。

#### 基础版：前闭后闭

基础版的特点是：它查找或者说比较的范围，是在 **0 到数组长度减 1** 这个范围内。用 `i` 和 `j` 表示，就是 `i = 0`、`j = a.length - 1`。

这里插一句：大家去力扣提交代码的时候，**方法名、类名最好不要动**，但是参数名可以随便改——比如我觉得 `numbers` 太长了，我给改成 `a` 更短一些。还有同学问：讲的时候对着图写代码，我写的时候没有这张图怎么办？你可以在草稿纸上画个草图，就代替掉我那个动画网页了。其实在草稿纸上画草图，难度比我做那个网页更简单。

范围确定以后就开始循环。先写循环条件，基础版的循环条件应该是 `i <= j`。这个条件成立，表示这个范围内还有没有比较的元素，那就应该继续循环；什么时候 `i > j` 了，表示范围内没元素了，就该退出。

> **易错点**：这里的等号绝对不能去掉。我们每次在循环内比较的，刚开始的全是 `m`——每一轮都只拿中值去比。如果把等号去掉，就意味着 `i == j` 这种情况下不再去找 `m` 了。这时候它俩指向的元素，恰恰可能就是要查找的目标：前面每次比的都是中值，而 `i`、`j` 本身指向的值一直没有机会参与比较。**这就是最后的机会**，我们要在它们相等的时候让它再次进入循环，再次进入循环了，这时候求到的 `m` 才能代表 `a[i]` 跟 `a[j]` 参与比较。等号漏了，就意味着你可能漏掉某一个目标的比较。

进入循环先求中值。中间值这块你用除法也行，用移位也可以——题目给 `n` 的取值范围是 1 到 1 万，并不大，用除法没问题。当然我为了代码稍微通用一些，我还是用移位，右移一位代表除以 2。

找到中值之后跟目标比较。我的习惯是先看这个目标是不是在左侧，然后再看目标是不是在右侧，先左后右。

```java
class Solution {
    public int search(int[] a, int target) {
        int i = 0;
        int j = a.length - 1;

        while (i <= j) {
            int m = i + ((j - i) >> 1);
            if (target < a[m]) {
                j = m - 1;          // 在左侧：m 已经比较过了，下次不用参与比较
            } else if (target > a[m]) {
                i = m + 1;          // 在右侧：m 同样不用再比了
            } else {
                return m;           // 既不在左侧也不在右侧，说明找到了
            }
        }
        return -1;                  // 循环结束还没找到
    }
}
```

就这么几行。提交一下，通过了，执行耗时 0 ms，击败了百分之百的用户。基础版完成。

#### 改动版：前闭后开

这个代码我就不从头写了，直接在刚才提交的基础版上来改。它的特点是：**区间变了，变成了前闭后开的区间**。前面那个 `i` 和以前一样，但后面这个 `j` 是一个开放区间了——**`j` 所指向的元素不参与比较**。这是它的要点。

因此代码上就有了三处改动：

1. **`j` 的初始值改成 `a.length`**，不是 `a.length - 1` 了。
2. **所有给 `j` 重新赋值的地方改成 `m`**，不是 `m - 1`。为什么？因为我们刚才说了，`j` 指向的位置本来就不参与比较。这次算出的 `m`，它既然已经决定了要向左找，那 `m` 指向的元素肯定是已经比较过的，下次就不参与比较了，所以把 `j` 放在 `m` 更合适。你要是放到 `m - 1`，那个位置上的值还没比较过，把它当成 `j`，这个值就被漏掉了。
3. **循环条件改成 `i < j`**，不是 `i <= j`。道理是类似的：`j` 指向的值不参与比较，是上一次（或上上次）的 `m` 值，早就比过了。如果它们相等了，就意味着 `j` 指向的这个比过的值又要再次参与比较，那就可能造成死循环了。所以我们应该在 `i == j` 的时候就退出——那时候说明所有元素都比较过了，只有 `i < j` 才继续循环。

```java
class Solution {
    public int search(int[] a, int target) {
        int i = 0;
        int j = a.length;           // j 指向不参与比较的位置

        while (i < j) {
            int m = i + ((j - i) >> 1);
            if (target < a[m]) {
                j = m;               // 不是 m - 1：m 已经比过了
            } else {
                i = m + 1;
            }
        }
        return (i < a.length && a[i] == target) ? i : -1;
    }
}
```

测一下，也通过了，执行耗时 0 ms，击败百分之百的用户。这是第二种解法。

#### 平衡版：只剩一对 if / else

我们还学过一个二分查找的版本，叫平衡版。前面基础版和改动版有一个共同之处：循环都是三分支的代码——`if / else if / else` 三个分支，名字里的"三分之"就是这个意思，**三个分支最多会比较两次**。平衡版的目标就是把这个三分支改成两分支，最后只剩一对 `if / else`，也就是每次循环只比较一次。

平衡版的关键点在于：**它每次循环只是缩小范围，并不是在循环内就找到结果**。我们不断缩小范围，直到范围内的元素只剩一个，这时候退出循环，然后到循环外面"一锤定音"，把剩的这一个元素跟目标比较一次：相等就返回这时的索引，不等就返回 `-1`。

> **结论**：平衡版循环内只做"缩小范围"这一件事，结果判定统一放在循环外。

再看代码怎么写。平衡版在范围的选取上其实跟改动版一样，也是前闭后开的区间，`j` 指向的是一个不参与比较的位置。所以 `i` 初始值是 0，`j` 初始值是数组的长度 `a.length`。中值还是老样子，`m = i + ((j - i) >> 1)`。

关键的 `if` 条件：由三分支改成两分支，就剩一个 `if` 加一个 `else`。

- `if (target < a[m])` 走左边：向左侧找，缩小 `j`。`j` 等于 `m` 还是 `m - 1`？刚才说过了，`j` 指向的应该是一个不参与比较的位置，所以是 `m`，不能是 `m - 1`。这跟改动版一模一样。
- `else` 走右边：这里跟以前不一样了。`else` 代表目标可能在右侧，但也**有可能 `m` 这个位置就是目标**。这种情况怎么办？显然要扩大 `i`，但扩到哪儿？是 `m` 还是 `m + 1`？应该是 **`m`**。你要扩到 `m + 1`，那如果恰好 `a[m]` 就跟目标相等，岂不是把这个相等的元素给漏掉了。所以 `i` 要扩大到 `m`。

那循环条件呢？前面说过，平衡版的要点是**范围内剩一个元素的时候就退出循环**。`i` 指向的元素是要参与比较的，只是最后一次它不在循环内比了，得等退出循环再比；`j` 指向的只是一个边界，它指向的元素其实已经比较过了。所以退出条件是：**`i + 1 == j` 的时候**退出，此时 `i` 就指向最后一个元素了。

要继续循环，就写成 `i + 1 < j`。当然这个条件你也可以把 `i` 移到右边去，写成 `j - i > 1`，一个意思。

```java
class Solution {
    public int search(int[] a, int target) {
        int i = 0;
        int j = a.length;

        // 循环条件：i + 1 < j，等价写法是 j - i > 1
        while (i + 1 < j) {
            int m = i + ((j - i) >> 1);
            if (target < a[m]) {
                j = m;
            } else {
                i = m;              // 不是 m + 1：a[m] 可能正好就是目标
            }
        }
        // 一锤定音：i 指向的就是最后剩下的那个元素
        return a[i] == target ? i : -1;
    }
}
```

跑一下比较，通过了，也是 0 ms，击败百分之百的用户。平衡版写完了。

**提示（题目给的）**：数组中元素不重复，不用考虑重复元素的问题，也不用管是要找最左边还是最右边的那个，找到就算对；`n` 的取值范围是 1 到 1 万，不大，累加不会超过 `int` 的表示范围，所以用除法算中点也没问题，不用移位也行。

**解析与答案**：这题的答案就是正文里那三种写法，随便挑一种都能过——

- **基础版**：范围是前闭后闭的 `[0, a.length - 1]`，循环条件 `i <= j`（等号不能去，否则 `i == j` 时最后一次比较机会就没了），三分支，`else` 里直接 `return m`。
- **改动版**：范围改成前闭后开的 `[0, a.length)`，`j` 指向不参与比较的位置，三处改动是：`j` 初值改成 `a.length`；给 `j` 赋值改成 `m` 而不是 `m - 1`；循环条件改成 `i < j`，否则可能死循环。
- **平衡版**：同样是前闭后开的区间，但循环内只剩一对 `if / else`，只做缩小范围这件事：`target < a[m]` 就 `j = m`，否则 `i = m`（不是 `m + 1`，否则可能把正好等于目标的那个元素漏掉）；循环条件 `i + 1 < j`，剩一个元素就退出，最后在循环外用三元运算符 `a[i] == target ? i : -1` 一锤定音。

## 二分查找的边界手艺，从静态数组到动态数组
> 对应块：BLK06 | 覆盖分集：P19-P23 | 块标题（分集名）：《基础数据结构-017-二分查找-e02-搜索插入》

这一块我们做两件事：先把二分查找的几个变体彻底钉死——搜索插入位置、搜索开始结束位置；然后掉头回到最底层，去看看数组这个数据结构在内存里到底长什么样，以及我们怎么在它上面手写一个能装能卸的动态数组。

先从力扣第 35 题开始，因为它是二分查找里唯一一个"找不到反而不返回 -1"的题，第一次见很容易懵。

### 搜索插入位置：找不到时该返回什么

题目要求：给定一个**排序的升序数组**和一个目标值，如果能找到目标，就返回它的索引；找不到，就返回它**按顺序插入后仍能保证升序**的那个位置。

> **定义**：插入位置 = 使数组仍升序的第一个空位，也就是第一个满足「左边所有元素 ≤ 目标、右边所有元素 ≥ 目标」的索引。

找到的情况跟我们熟悉的二分查找结论完全一致，一致得让人犯困——真正不一样的是找不到的时候。普通二分查找找不到返回 -1，这道题返回的是插入位置。

看两个例子就明白了。数组是 `[1, 3, 5, 6]`：

```text
index:   0     1     2     3
array:  [1]   [3]   [5]   [6]

target = 2  ->  不在数组内，应插在 index 1，结果 [1][2][3][5][6]
target = 7  ->  不在数组内，应插在 index 4，结果 [1][3][5][6][7]
```

读一下图就知道，target = 2 时插到 1 和 3 之间，target = 7 时它比所有元素都大，只能挂到队尾，索引正好等于数组长度。所以插入位置的取值范围是闭区间 $[0, n]$——它可以是 $n$，这跟查找下标的上界 $n-1$ 不一样，是个很容易写错的点。

#### 题目条件里那条"没有重复元素"

题目注意事项有几条：必须用 $O(\log n)$ 的算法；数组长度在 1 到 $10^4$ 之间，也就是 $n$ 不会太大，所以我们用除法取中点完全可以，不必上移位；最后一条特别强调——**数组是没有重复元素的升序数组**。

这条待会儿就派上用场了。我要用的那种写法，在乎的不是"没有重复"，而是"找最靠左"：**有重复也行，没重复也可以**。所以题目给不给这条约束，我写出来的代码都能过。这就是边界写法比基础写法更值钱的地方。

#### 思路一：从 Java 版二分查找改掉返回值

我们在讲 Java 的二分查找版本时就说过，`Arrays.binarySearch` 找不到时返回的不是 -1，而是一个负的插入点再减一：`-(插入点 + 1)`。那么这道题就简单粗暴了——**别带符号了，也别做那个减一了，直接把插入点还回去**。

```java
int i = Arrays.binarySearch(nums, target);
return i < 0 ? -i : i;
```

它的底层版本长这样：

```java
int i = 0, j = nums.length - 1;
while (i <= j) {
    int m = (i + j) / 2;
    if (target < nums[m]) {
        j = m - 1;
    } else if (target > nums[m]) {
        i = m + 1;
    } else {
        return m;
    }
}
return -(i + 1);
```

循环退出时，`i` 停在的就是插入点——所以最后那行才是 `-(i + 1)` 的由来。解题时我们把 `nums.length - 1` 改成 `a.length - 1`，`k` 改成 `target`，中间的分支一个字不动，只把返回值换成 `return i`。提交，0ms，击败百分之百用户。

顺手就能过，但它毕竟依赖了标准库的约定。自己写一遍才踏实。

#### 思路二：left most，把相等也往左逼

`left most` 版本返回的是：**大于等于 target、并且最靠左的那个索引**。这跟插入位置是同一个东西，所以直接 `return i` 就完事。

```java
int i = 0, j = nums.length - 1;
while (i <= j) {
    int m = (i + j) / 2;
    if (target <= nums[m]) {
        j = m - 1;
    } else {
        i = m + 1;
    }
}
return i;
```

这段代码只有两个分支，但来历值得掰开看。我习惯一开始老老实实写三个分支：

- `target < nums[m]`：目标在中间值左边，`j = m - 1`；
- `target > nums[m]`：目标在中间值右边，`i = m + 1`；
- `target == nums[m]`：中了，但这不一定是最靠左的那个。

> **易错点**：第三种情况最容易写错。如果数组里有重复元素，二分中途撞上相等的那个值，往往是**中间偏右**的那一个，直接返回就错了。比如要找 4，`[1, 2, 4, 4, 4, 7, 8]` 里可能先撞上索引 4，它不是最靠左的 4。所以相等的时候**不能停，还得继续往左走**，`j = m - 1`。

看清楚了吗：`target < nums[m]` 和 `target == nums[m]` 两种情况**动作完全一样**，都让 `j = m - 1`。既然如此，两个条件就合成 `target <= nums[m]`，剩下的 `else if` 顺势改成 `else`。循环跑完，`i` 就是最靠左的那个索引。

验证两下：

```text
index:   0     1     2     3     4     5     6
array:  [1]   [2]   [4]   [4]   [4]   [7]   [8]
                 ^
target = 3  ->  第一个 >= 3 的位置是 index 2  ->  [1][2][3][4][4][7][8]
target = 5  ->  第一个 >= 5 的位置是 index 5  ->  [1][2][4][4][4][5][7][8]
```

两个例子都还是升序，返回的正是插入位置。

> **结论**：这道题推荐用 `left most` 写。它不只能处理无重复数组，有重复元素时同样给出正确的插入位置，适应性比思路一强得多。

### 搜索开始结束位置：left most 与 right most

有了上一题的铺垫，力扣第 34 题几乎是白给的。题目给一个**非递减顺序**排列的整数数组 `nums`（就是升序，只不过允许有重复元素）和一个目标值 `target`，要求找出目标值在数组中的**开始位置和结束位置**。

"非递减"这个说法别被唬住，它就是升序，只是允许相等元素连排。开始位置就是最靠左的那个，结束位置就是最靠右的那个。

```text
index:   0     1     2     3     4      5
array:  [5]   [7]   [7]   [8]   [8]    [10]
                             ^     ^
target = 8  ->  开始位置 3，结束位置 4  ->  返回 [3, 4]
```

找不到就好办了，开始位置和结束位置**都返回 -1**。题目同样要求 $O(\log n)$，我们的 `left most`、`right most` 正好就是 $O(\log n)$。

#### left：候选值写法

这道题里目标值是**存在的**（存在性由 `searchRange` 统一判断），所以 `left` 的返回值语义是"最左侧命中下标，找不到给 -1"。它跟上一题那个"始终返回插入点"的 `left most` 有一处关键差别：上一题里相等时直接丢弃即可，这一题里相等时**得先把下标记下来**，再继续往左逼。

```java
private int left(int[] nums, int target) {
    int i = 0, j = nums.length - 1;
    int candidate = -1;
    while (i <= j) {
        int m = (i + j) / 2;
        if (target < nums[m]) {
            j = m - 1;
        } else if (target > nums[m]) {
            i = m + 1;
        } else {
            candidate = m;
            j = m - 1;
        }
    }
    return candidate;
}
```

三个分支照旧老老实实写。`candidate` 声明在**循环外面**，初值 -1 表示"还没有候选"。一旦 `nums[m] == target`，就 `candidate = m` 记下这个命中——但它只是候选，不能就此收工，接着 `j = m - 1` 继续缩小范围往左找。

循环结束时有两个出口：如果目标存在，最后一次记下的 `candidate` 就是最靠左的索引；如果压根没找到，`candidate` 从头到尾都是 -1。**用一个变量同时表达了"找到"和"没找到"两种状态**，这就是设初值 -1 的妙处。

#### right：跟 left 只差一行

`right` 是把 `left` 拷一遍改个名。它唯一的区别在相等那一支：我不确定当前候选是不是最靠右的，所以要**继续往右找**。

```java
private int right(int[] nums, int target) {
    int i = 0, j = nums.length - 1;
    int candidate = -1;
    while (i <= j) {
        int m = (i + j) / 2;
        if (target < nums[m]) {
            j = m - 1;
        } else if (target > nums[m]) {
            i = m + 1;
        } else {
            candidate = m;
            i = m + 1;
        }
    }
    return candidate;
}
```

看这图，两个方法只差一个赋值：一个是 `j = m - 1`，一个是 `i = m + 1`。就这一行，方向整个反过来。

> **提示**：`left` 和 `right` 其实完全可以合成一个方法，加一个布尔参数表示往左还是往右就行——往左就在相等时压 `j`，往右就多一个判断压 `i`。怎么合，大家下去自己动手做，我这里先留着两份清楚的实现。

#### searchRange：把两次查找拼成一个答案

题目提供的 `searchRange` 方法只负责把两个结果组合起来，所以它最后写。

```java
public int[] searchRange(int[] nums, int target) {
    int start = left(nums, target);
    if (start == -1) {
        return new int[]{-1, -1};
    }
    int end = right(nums, target);
    return new int[]{start, end};
}
```

逻辑很短，但顺序有讲究：**先跑 `left`**。它一旦返回 -1，就说明目标值压根不在数组里，`right` 再跑一遍纯属浪费，直接按题目要求丢回 `{-1, -1}`；只有确认存在了，才有必要去求最右边界。数组下标 0 放开始位置，下标 1 放结束位置。提交，通过，0ms。

到这里，二分查找这一组变体就齐了。下面换个方向，从最基础的容器开始。

### 数组：连续存储带来的直接寻址

数组的定义大家都背得出来：在计算机科学中，数组是由一组元素组成的数据结构——说白了就是把多个元素放一块儿统一管理。这里的元素可以是值，也可以是变量。

> **定义**：我会补充两点。其一，**元素的类型必须一致**，不能一部分是 `int`、另一部分是 `double`，那样就没法用数组管。其二，**每个元素都有一个索引（或者叫键，key）来标识**。index 翻译过来是索引，key 翻译过来是键，这纯粹是翻译问题，本质上就是给每个元素一个唯一标识。

真正值钱的不是定义，是它的**特点**：数组中的元素是**连续存储**的，多个元素紧挨着，一个接一个。

这一个"连续"，直接兑换成一个巨大的好处——**任意元素的地址都能由索引算出来**。

#### 地址公式：连续存储的直接兑现

拿一个 `int` 数组举例，元素是 `1 2 3 4 5`，索引依次是 `0 1 2 3 4`。假设我们已经知道索引 0 那个元素的地址是 $b$，那么：

- 索引 0 的元素占 4 字节（`int` 就是 4 字节），所以索引 1 的元素紧挨在它后面，地址是 $b + 4$；
- 索引 1 再占 4 字节，所以索引 2 的地址是 $b + 8$；
- 依此类推，索引 3 是 $b + 12$，索引 4 是 $b + 16$。

规律出来了。把数组数据的起始地址叫 base address（基地址），元素下标记 $i$，每个元素占用的字节数记 `size`：

$$\text{address}(i) = \text{base address} + i \times \text{size}$$

$i$ 就是索引；`size` 是每个元素占用的字节数。上面用的是 `int` 数组，所以 `size = 4`；哪天换成 `double` 数组，`size` 就变成 8，因为 `double` 占 8 字节。

拿这个公式做个小测试：数组元素还是 `1 2 3 4 5`，但这次数据类型是 `byte` 数组，基地址给的是 `0x...4c8`，问元素 `3` 的地址。

三个数一凑：`3` 的索引是 2（索引从 0 起算，`0 1 2`），`byte` 数组里每个元素**只占 1 字节**，所以 `size = 1`。

$$\text{address}(2) = \texttt{0x4c8} + 2 \times 1 = \texttt{0x4ca}$$

为什么是 `a`？因为十六进制里用字母 `a` 表示十，8 + 2 + 1 = 10，10 就是十六进制的 `a`。答案 `0x...4ca`。

> **易错点**：`size` 是**每个元素**的字节数，不是元素个数；`i` 是**索引**，不是"第几个"。第 3 个元素的索引是 2，这一步错了后面全错。

#### Java 里一个 int 数组的内存账本

不同语言的实现不一样，我以 Java 为准。在 Java 里，数组本质上是一个**对象**，所以它也分**对象头**和**数据**两大部分。

对象头又分三块：`mark word` 8 字节，记录对象的哈希码、GC 分带年龄、加锁时的锁信息；**类指针** 4 字节，顾名思义就是"你这个对象是什么类型"，要找实际类型就得顺着它去查，一个 `int[]` 的类指针可以简单理解成指向 `int[]` 的 `.class`；**数组长度** 4 字节。对象头合起来 $8 + 4 + 4 = 16$ 字节。

数组长度为什么值得占 4 个字节？因为它是 32 位，能表示到 $2^{32}$ 这个量级，这就直接决定了数组的最大容量。

再往下是数据部分。`int` 数组每个元素 4 字节，而且是紧挨着存的。还有最后一块**对齐字节**：Java 里对象大小必须是 8 字节的整数倍，不满的那一截要补齐——你看这个例子好像缺了一条腿，不能让它就这么歪着。

```text
+----------------------------+  offset
|  mark word            8 B  |   0
+----------------------------+   8
|  class pointer        4 B  |   8
|  length               4 B  |  12
+----------------------------+  16   <- 对象头 16 字节
|  a[0] = 1             4 B  |  16
|  a[1] = 2             4 B  |  20
|  a[2] = 3             4 B  |  24
|  a[3] = 4             4 B  |  28
|  a[4] = 5             4 B  |  32
+----------------------------+  36   <- 数据 5 x 4 = 20 字节
|  padding              4 B  |  36   <- 补齐到 8 的整数倍
+----------------------------+  40   总计 40 字节
```

读图：对象头 16 字节 + 数据 20 字节 = 36，最后再补 4 字节对齐，总共 40 字节。（这里说的是指针压缩下的典型情况，真要抠 JVM 实现细节那是另一个话题，先不扯那么多。）

#### 随机访问为什么是常数

所谓**随机访问**，说白了就是"按索引查元素"。为什么叫随机？因为知道了索引，就等于知道了地址——把索引代进上面那个公式，一步算出位置，**跟数组里有多少个元素、数据规模多大，一点关系都没有**。

你甭管它是一万个元素还是一个亿个元素，我知道基地址、知道索引，公式一算就出来了。所以数组随机访问的时间复杂度是常数：$O(1)$。

```text
查找索引 i 的元素：

    base address  +  i  x  size
          |           |      |
       已知         已知    已知
             与 n 无关  ->  O(1)
```

至于是不是要讨论数组的插入和删除性能——这个放到后面去讲。因为我们现在讨论的是**大小固定的数组**，它压根就不能删除元素、也不能添加元素，创建时大小就固定死了。想让数组能加能删？那正好就是接下来要讲的动态数组。

### 动态数组：逻辑大小、容量与扩容

Java 自带的数组不能插入、不能删除，大小在创建时就固定死了，这种数组叫**静态数组**。反过来，如果一个数组能插入或删除元素，而且大小可以按实际需要发生变化，那它就叫**动态数组**。

> **提示**：Java 里当然有现成的动态数组，我们最熟悉的那个 `ArrayList` 就是。不过现在是在学数据结构的课程，所以我们自己动手实现一个。

先看演示动画里的这张图，最显眼的是 `size`。有个东西我没在图上标文字，你们一眼能看出来——容量是 8，也就是说它将来可以放 8 个元素。

#### size：逻辑大小

`size` 我们叫**逻辑大小**，它代表动态数组里**有效的元素个数**。

刚开始它是 0，表示这个动态数组里还没管理任何元素。注意，图上明明已经画着一堆格子，但**它们全是无效的，不能使用**。随着往数组里添加元素，`size` 增大；删除元素，`size` 缩小。

演示一遍：往数组里添加 `1 2 3 4 5`。加入 1，`size` 变 1；加入 2，变 2；依次类推，五个都加进去之后 `size` 变成 5，表示前面这五个元素有效、可以使用，后面几个灰色的无效、访问不得。

删除的例子更能说明问题：想把索引 2 位置的那个元素 `3` 删掉。

```text
size = 5:  [1][2][3][4][5]      想删掉 index 2 的 3

  3 没了，但 1 2 和 4 5 必须连起来
  -> 2 和 4 必须相连，只能把 4、5 整体往前挪一格

删除后:  [1][2][4][5]          size = 4
```

删除要**保证数组元素的连续性**，所以 4 和 5 必须往前移，4 去顶替原来 3 的位置，最后 `size` 减一。

> **结论**：`size` 就是数组内有效元素个数的唯一裁判。有 `size` 在手，那些"物理上存在但逻辑上无效"的格子就永远访问不到——记住这句话，后面实现扩容时会再用一次。

#### 容量与扩容

容量不够了怎么办？这就要说到动态数组的一个重头戏：**扩容**。

演示里容量是 8。加 `6 7 8 9` 都没问题，加到第 10 个元素的时候放不下了。扩容的工作流程是这样的：

```text
[1][2][3][4][5][6][7][8]       容量 8 装满了，第 10 个放不下
        |
        | 1. 创建一个容量更大的新数组
        v
[1][2][3][4][5][6][7][8][ ][ ][ ]...
        |
        | 2. 把旧数组里的元素复制到新数组
        v
[1][2][3][4][5][6][7][8][ ][ ][ ]
        |
        | 3. 用新数组顶替旧数组，再把 10 写进去
        v
[1][2][3][4][5][6][7][8][10]
```

所以"扩容"这个动作，说穿了就是**造一个更大的数组出来，把旧数组的元素复制过去，让新数组顶替旧数组**，最后把刚才放不下的那个元素写进新数组。这个功能我们待会儿也得实现。

顺手总结一下要实现的清单：**插入元素、删除元素、扩容**。前两个操作都要顺带管理逻辑大小 `size`，第三个是在预设容量不够时扩大容量。

### 动态数组的插入：addLast 与 add

类名叫 `DynamicArray`，翻译过来就是动态数组。我们一步步来实现它。

先想清楚这个类该有哪些属性。用面向对象的思想，对着那张图想：

- **底层静态数组**——名字虽然叫动态数组，但底层为了存储元素内容，还是需要一个静态数组。第一个属性先简单点，就搞一个 `int` 数组，**只存数字**；
- **`size`**——逻辑大小，控制数组内有效元素的个数；
- **`capacity`**——容量，英文单词就是 capacity。

三个属性的初始值：刚才是 `size = 0`，表示还没有有效元素；`capacity` 我们跟图上一致，给 8；底层静态数组给一个空数组，容量就是上面的 `capacity`。创建出空数组之后，这些元素都被初始化成了 0，其实值是什么无所谓——**只要 `size` 在控制，我们就访问不到这些无效元素**。

#### addLast：往最后一格写

第一个功能叫 `addLast`，顾名思义，新增的元素作为**最后一个**加进动态数组。前面演示里添加 `1 2 3 4 5`，走的就是这个方法。

最后的位置怎么确定？其实就是 `size`。刚开始 `size = 0`，最后的索引就是 0，把新元素加到索引 0；再加第二个时 `size = 1`，那就加到索引 1。看懂了这个，方法就好写了。

```java
public void addLast(int element) {
    array[size] = element;
    size++;
}
```

就两行：找到底层 `array` 的 `size` 索引位置，把取值赋成 `element`；然后 `size++`。

#### add(index, element)：先把后队整体后移

第二个功能 `add`，是往数组内**某一个索引位置**插入新值，不是加到最后。

比如当前是 `1 2 3 4 5`，我想在索引 2 这个位置插入一个 6。最后效果应该是 `1 2 6 3 4 5`——原来索引 2 之后的所有元素**向后移一位**。

```text
size = 5, array = [1][2][3][4][5], index = 2, element = 6

System.arraycopy(array, index, array, index + 1, size - index);
                    |        |         |              |
                 源数组    源起始位   目标数组      目标起始位  拷贝个数
                              2                   3         5 - 2 = 3

  before:  [1][2][3][4][5]
                    ~~~ 这三个（3 4 5）整体后移一格 ~~~
  after:   [1][2][ ][3][4][5]
                   ^ 索引 2 空出来了
  final:   [1][2][6][3][4][5]      size = 6
```

`System.arraycopy` 能实现数组间或者数组内元素的拷贝复制。四个源参数，逐一对应：

- **参数一**，源数组是谁？就是我们这个 `array`；
- **参数二**，从哪开始拷贝？应该从 `index` 开始；
- **参数三**，拷到哪去？还在同一个数组内，所以还是 `array`；
- **参数四**，目标起始位置在哪？我们希望它**向后移一位**，所以是 `index + 1`；
- **参数五**，拷几个？要把从 `index` 开始的**所有元素**都右移，当前 `size` 是 5、`index` 是 2，$5 - 2 = 3$，所以是 3 个。

拷贝完，索引 2 就空出来了，把 `element` 写进去，最后 `size++`。方法就实现了。

```java
public void add(int index, int element) {
    if (index >= 0 && index < size) {
        System.arraycopy(array, index, array, index + 1, size - index);
        array[index] = element;
        size++;
    }
}
```

> **易错点**：`arraycopy` 的源区间和目标区间**是重叠的**（源从 `index` 起，目标从 `index + 1` 起），但它按元素个数一次性搬运、底层处理得对，不会边搬边覆盖。写成逐个倒序赋值当然也对，只是又慢又啰嗦，用现成的才是正道。

#### 边界：这个 index 到底能取多大

实现完必须回头想边界，不然插进一个天堑里，数组就裂了。插入之前 `index` 的有效取值：

- **小于 0**：压根不在数组里，不行；
- **等于 `size`**：可以，这种情况跟 `addLast` 是一回事，把它作为最后一个元素加进去；
- **大于 `size`**：不行。新加的元素跟前面有效的元素**断开了**，中间不能断，你必须保证新加的元素跟原来的元素都连在一起。

所以 `add` 真正能覆盖的合法区间是 $[0, size-1]$，再加上"等于 `size`"这个尾插特例。

#### 合并：addLast 就是 add(size, …)

既然 `addLast` 和 `add` 有重叠，那就顺手合并掉，让 `add` 的处理能力更大一些。

思路是这样的：给 `add` 多加一个 `else if`，判断 `index == size` 时执行 `addLast` 的逻辑。但把代码搬过来之后你会发现两件事——第一，既然进入了这个分支，`index` 必然等于 `size`，那里面写的 `array[index]` 其实可以直接用 `array[size]`，而这跟 `if` 分支里那两行**一模一样**；既然一模一样，就没有必要把它关在 `if` 里面，干脆抽出来放到 `if` 外面。

```java
public void add(int index, int element) {
    if (index >= 0 && index < size) {
        System.arraycopy(array, index, array, index + 1, size - index);
    }
    array[index] = element;
    size++;
}
```

`else if` 也就跟着没了。现在的 `add` 同时处理两种情况：在 `size` 范围内的插入，以及 `index == size` 时的尾插——反正都要写元素、都要 `size++`，统一放外面执行。

而上面的 `addLast` 就变得非常干净，直接去调用 `add`，只不过 `index` 传 `size`：

```java
public void addLast(int element) {
    add(size, element);
}
```

两个方法的功能就这么合并到一处了。

> **提示**：合并之后，方法进来第一件事最好还是做一次 `index` 的合法性判断——小于 0 或大于 `size` 就直接报错，别让它往下执行。这段判断代码我就不写了，大家可以自己加上。

至此，动态数组的插入部分就完成了。前面章节里那些 `size`、`capacity`、`arraycopy` 后移，把它们串起来就是一个能用的动态数组骨架。

### 本讲提到的题目

**力扣 35 —— 搜索插入位置。** 给定一个升序无重复的整数数组 `nums` 和一个目标值 `target`，若 `target` 存在则返回其索引，若不存在则返回它按顺序插入后仍能保证升序的位置。要求 $O(\log n)$。

答案：用 `left most` 写法，`target <= nums[m]` 时 `j = m - 1`，否则 `i = m + 1`，循环结束返回 `i`。完整的推导、逐段代码和两个验证例子见正文「搜索插入位置：找不到时该返回什么」一节。

**力扣 34 —— 在排序数组中查找元素的第一个和最后一个位置。** 给出一个按非递减顺序排列的整数数组 `nums` 和目标值 `target`，返回 `target` 在数组中的开始位置和结束位置；不存在则返回 `{-1, -1}`。要求 $O(\log n)$。

答案：分别用 `left` 和 `right` 求最左与最右命中下标，二者都用 `candidate = -1` 的候选值写法，唯一差别在相等时一个压 `j`、一个压 `i`；`searchRange` 先跑 `left`，若为 -1 直接返回 `{-1, -1}`。推导与代码见正文「搜索开始结束位置」一节。
