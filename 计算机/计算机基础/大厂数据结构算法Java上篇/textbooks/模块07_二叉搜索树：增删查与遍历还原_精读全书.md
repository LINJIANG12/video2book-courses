## 手写一棵二叉搜索树：节点、get 与最值查找
> 对应块：BLK42 | 覆盖分集：P163-P165 | 块标题（分集名）：《基础算法-118-二叉搜索树-get》

前面我们把二叉搜索树的性质过了一遍，现在就动手把它写出来。写一棵树其实没什么神秘的，和写任何一个普通类一样——先把节点定下来。

节点上要有什么？我先自问自答一遍。一个节点光有一个 k 够不够？不够。我们凭什么只凭一个 key 就能把值捞出来？所以节点上还得再挂一个值，一个 value。value 可以是任意类型，Student 可以，字符串可以，你想存什么就存什么。

大家一看这个"键 + 值"的组合，脑子里应该立刻会跳出一个东西——我们 Java 里已经实现好的 map 集合。二叉搜索树跟 map 做的事情是很像的：根据一个键，去快速找到对应的值。这个类比从这一刻开始就一直成立，后面你会发现我们的代码越写越像 map。

### 节点类：k、value、left、right

节点我把它做成一个静态内部类，类名叫 `BSTNode`，BST 就是 binary search tree，二叉搜索树的缩写。

属性一共四个，非常干净：

| 属性 | 类型 | 作用 |
| :--- | :--- | :--- |
| `k` | `int` | 关键字，决定往左还是往右 |
| `value` | `Object` | 节点携带的值，任意类型 |
| `left` | `BSTNode` | 左孩子 |
| `right` | `BSTNode` | 右孩子 |

`k` 我一开始选的是 int。为什么是 int？因为待会儿我们就要拿这个 key 互相比较大小，而 int 是最容易实现大小比较的类型。先以简单为主，以后想扩展，完全可以让它去实现一个 `Comparable` 之类的接口——这一节我们就先不扩展了。

`value` 为什么定成 Object？因为值可以是任意东西，一个学生对象、一个字符串，都没问题。

`left` 和 `right` 的类型还是 `BSTNode` 自己——左孩子叫 `left`，右孩子叫 `right`，就这么简单。

至于构造方法，我少加几个，方便以后使用：按 k 创建节点的、按 k 和 value 创建节点的、按 k、value 再加左右孩子创建节点的，全给它安排上。

```java
public static class BSTNode {
    int k;
    Object value;
    BSTNode left;
    BSTNode right;

    public BSTNode(int k) {
        this.k = k;
    }

    public BSTNode(int k, Object value) {
        this.k = k;
        this.value = value;
    }

    public BSTNode(int k, Object value, BSTNode left, BSTNode right) {
        this.k = k;
        this.value = value;
        this.left = left;
        this.right = right;
    }
}
```

这样节点类就初步实现了。

### 树类：root 和一串方法

节点有了，接下来看外层的二叉搜索树类 `BSTTree`——既然它作为一棵树，至少得有一个根节点吧。所以树类上加一个属性，类型就是刚才那个 `BSTNode`，属性名叫 `root`。

除了属性以外，还有方法。这些方法我已经提前写好了，我们大概过一遍。

| 方法 | 干什么 |
| :--- | :--- |
| `get` | 根据 key 找到这个节点所关联的值 |
| `min` | 获得树中最小的 k，以及它关联的值 |
| `max` | 获得最大的关键字，以及它关联的值 |
| `put` | 把键值对存到树里面去，也就是添加 |
| 前驱 | 找到比它小的所有值里最大的那个，也就是离它最近的 |
| 后继 | 找到比它大的所有值里离它最近的那个 |
| `delete` | 根据关键字删除节点 |

前面这几行里，最核心的就是 `get`，我们就从它开始。

前驱后继这两个概念我用例子说清楚。比如四的前任是谁？四的前驱是三。七的前驱呢，是六。所谓前驱，就是找到比它小的、但在这些小的里面最大的那个，也就是离它最近的、比它小的那个。有前驱就有后继，后继也叫后继——七的后继就是八。

`delete` 这里要特别注意：它只是删除一个节点，不是说把它后代节点都跟着删掉。比如我要删除六，那就只是把六删了，它不会连着五一起删。五将来会挂到别的位置上去，把这棵树接起来。这些方法我们现在都还没实现，先过一遍，待会儿逐一来实现，后面有需求了再逐步添加。

### get：从根节点出发，只有三种情况

`get` 的逻辑其实我们刚才已经看过一遍了。就是从根节点开始，把根节点的 k 跟我们待查找的 k 做一个比较，然后分成三种情况：

- 如果待查找的 k 小一些——是不是应该从根节点向左找？
- 如果待查找的 k 大一些——就从根节点向右找。
- 如果两个 k 值相等——那就不用找了，就是已经找到了。

为什么"相等"就等于"找到了"？因为我们前面说过的，二叉搜索树里的 k 的值是唯一的。唯一，就不存在"这个 key 藏在别的分支上"的可能。

> **结论**：二叉搜索树的查找永远只有三种走向——小了往左，大了往右，相等就命中。

那接下来的问题来了：不管待会儿向左转还是向右找，下一个节点的判断逻辑跟刚才根节点的判断逻辑一不一样？一样的。一样就说明每个节点的处理逻辑都相同，既然都相同，我们就可以利用递归来进行求解。

#### 递归版：把 doGet 藏到内部

我们再写一个函数专门用来做递归，返回值是 `Object`，表示将来返回的是这个 value。方法名换一个，叫 `doGet`，两个参数：一个是当前的节点，另一个就是待会儿要对比的这个待查找的 key。

三种情况直接翻译成代码：

```java
private Object doGet(BSTNode node, int key) {
    // 向左找
    if (key < node.k) {
        return doGet(node.left, key);
    }
    // 向右找
    else if (key > node.k) {
        return doGet(node.right, key);
    }
    // 找到了
    else {
        return node.value;
    }
}
```

逐段拆开看。`key < node.k` 的时候，"向左找"怎么表示？很简单，只要递归地再去调用 `doGet` 就可以了，只不过这回传给它的 `node` 是 `node.left`——下次我找的时候，是从这个节点的左孩子开始查找。要比较的 key 不变，还是刚才那个 key。

如果 `node.k` 小于待查找的 k，表示待查找的 key 更大，那就在右侧找，也就是调用 `doGet(node.right)`，从它右孩子那边继续查找，重复同样的事。

最后一种情况，既不是小于也不是大于，那就是相等了。找到了。我们最终只想返回它的值，所以直接 `return node.value`。

那这个递归的结束条件在哪里？比方说这个 node 已经到 null 了，它再向左找那就是 null 了。null 就表示没找到，应该结束递归，返回 null。所以最后我们还得补一个判断——如果 `node` 等于 null，就结束递归，返回一个 null 表示没找到。

补上这个条件，完整版是：

```java
private Object doGet(BSTNode node, int key) {
    if (node == null) {
        return null;
    }
    if (key < node.k) {
        return doGet(node.left, key);
    } else if (key > node.k) {
        return doGet(node.right, key);
    } else {
        return node.value;
    }
}
```

外面那个 `get` 怎么用？调用 `doGet` 就完了，只不过起点从 root 开始：

```java
public Object get(int key) {
    return doGet(root, key);
}
```

> **为什么非要分成 `get` 和 `doGet` 两个方法？**
> `get` 是给外界使用的，它对外隐藏了 `BSTNode` 这个内部数据结构——使用者只要知道有这么个 k 就行了，不需要知道他手里拿到的值到底是从哪个节点上翻出来的。`doGet` 是我们这个类内部自己用的，不用暴露给外界。这就是"公开的接口"和"内部的实现"之间那道墙。

#### 先造一棵测试树

代码写完了得测。我提前准备了一棵树，就用我画的那个形状：

```text
            4
          /   \
         2     6
        / \   / \
       1   3 5   7
```

我们对着图捋一遍：一和三是叶子节点，它们的父节点是二，二的左孩子是一，右孩子是三，没问题。另外还有两个叶子节点五和七，它们的父节点是六，六的左孩子是五，右孩子是七。最后还有一个顶层的是我们的根节点，四。它的左孩子是二，而刚才那个二还有一个右孩子……

对，这句是我说顺嘴了，看图就行：二只有左右两个孩子，三；四的左孩子是二，右孩子是六。整棵树就这几个节点。

每个节点都有自己的键和值。键是唯一的，就是这里大家看到的 1 到 7 这七个键；值呢，是一些人名，比如张无忌、宋青书等等。

所以测试代码非常简单，就是到这个树里根据 k 去找值。比如 k 等于 1，对应的值是不是张无忌？如果返回的确实是张无忌，说明我刚才这个 `get` 方法实现的是 OK 的。同理我还测了 k 等于 2，返回的应该是周芷若等等，都测了一遍。

再测一个不存在的：给他一个八。八是一个不存在的 key，你看我这棵树里只有 1 到 7，没有八。八的话他找不到，找不到其实最后就走 `node == null` 这个条件了，会返回一个 null，表示没有找到。

跑一遍，没问题。刚才这几个期望值跟我的实际运行结果都是一致的，那我们的 `get` 方法就初步测试通过了。

#### 非递归版：同样的判断，换成 while

刚才呢我们是使用递归的方式来实现了 `get` 方法。那这道题咱们能不能用非递归的方式来实现呢？答案也是可以的。

我再重写一个方法，还是叫 `get`，刚才那个先注释掉。这回用非递归的方式来实现。刚开始也是准备一个 `BSTNode` 对象，它的初始值是 root——因为我们总是从根节点开始进行比较。

当这个 node 不为空的时候，我们就要不断去看：小了向左找，大的向右找，相等了就找到了。所以我写一个循环 `while (node != null)`，不断执行这个比较的逻辑。

```java
public Object get(int key) {
    BSTNode node = root;
    while (node != null) {
        if (key < node.k) {
            // 向左走：下次循环从当前节点的左孩子开始
            node = node.left;
        } else if (key > node.k) {
            // 向右走：下次循环从当前节点的右孩子开始
            node = node.right;
        } else {
            // 找到了，直接返回，不需要再进循环
            return node.value;
        }
    }
    // 循环结束还没找到，说明整棵树里没有这个 key
    return null;
}
```

逐段看：我的 k 如果小于 node 的 key，就应该到这个 node 的左边这条路去找，所以下一次循环的时候，这个 node 应该变成谁？就应该变成它的左孩子。这是第一种情况。

第二种情况，我的 k 更大一些，比这个 node 的 key 更大，那我就应该到 node 的右边去找，怎么办？把 node 变成当前这个 node 的右孩子。

如果上面这两个条件都不成立，进入 else，就表示相等了，就找到了。找到以后还需要继续 while 循环吗？不需要了，直接 return，返回这个 node 的值。

那等循环结束，如果还没有找到，那说明这个 key 在整棵树里没有，我们就返回 null。

测试用例我都不用改，因为只是方法的实现换了，方法的参数、名字都没换。重新跑一遍，刚才的几个测试用例也都通过了。

#### 伪递归：一条以后要记住的规则

大家记住一条规则：只要是我们以前用递归实现的、属于伪递归的，那它转换成非递归代码非常容易。

啥叫伪递归？当一个函数它的最后一步，也就是 `return` 的时候，调用的是函数自身的，就叫做伪递归。

你看我们这个 `doGet`，是不是最后一句直接 `return doGet(node.left, key)`，连结果都原封不动地往上抛？这种就是典型的伪递归。大家以后遇到这种伪递归的代码，你就想一下：是不是我应该把它转换成非递归的实现？这样性能会更好一些。因为 Java 毕竟不支持尾递归的自动优化，所以我们不妨这件事交给我们自己来做。

### 让 k 不再是 int：泛型与 Comparable

之前实现二叉搜索树的时候，节点里的 k 我们选择了 int。为什么用 int？因为我们节点中的 k 有一个要求：k 与 k 之间必须能够进行大小比较。因此我们选择了 int，因为 int 做大小比较非常简单。

那有同学说了，那我能不能对它这儿进行一个扩展？我希望除了 int 以外，更多的类型也能够作为 k 的类型，行不行？答案是可以的。

第一个能想到的，就是采用泛型来实现。给外层的 tree 这个类加一个泛型声明，给内层的节点类也加一个泛型声明，然后凡是出现 k 的地方，我们都把它的数据类型从 int 改成泛型 T。

```java
public class BSTTree<K extends Comparable<K>> {

    public static class BSTNode<K> {
        K k;
        Object value;
        BSTNode<K> left;
        BSTNode<K> right;
        // 构造方法略
    }
}
```

这里有一个小细节别漏了：因为节点类用了泛型，所以我们在声明左右孩子的时候，也得给它补充上泛型的定义——写成 `BSTNode<K> left`、`BSTNode<K> right`。不然那个黄色的警告就一直在那儿杵着。

都改完了。但改完以后，这个节点类现在能不能正常工作呢？其实还不行。因为你随便给一个泛型 T，它就能够参与大小比较吗？不行。我们的前提是 k 必须能够进行大小比较，你任意给一个 T，并不能保证它就能够进行大小比较。

#### Comparable 上限：给 T 划一条底线

所以接下来我们对泛型再做一点限制，让它能够参与大小比较。Java 中要让任意一个类型具备能比较大小的能力，那你得让它实现一个接口，叫做 `Comparable`。

那我们在声明泛型的时候，能不能让这个泛型也具备这种比较大小的能力呢？答案也是可以的——泛型中它有一个语法叫做泛型上限的语法，用 `extends` 关键字后面跟上一个 `Comparable` 接口：

```java
public class BSTTree<K extends Comparable<K>> {
```

这样就可以了。这个意思是说，将来我的泛型 K 它就有一个上限了，也就是它必须是 `Comparable` 接口的子类型。K 这里就不是任意类型了，而是必须是 `Comparable` 接口的子类型。加上了这个泛型上限语法之后，我们的 k 它才能进行大小比较。

#### 用 compareTo 改写查找判断

有了泛型的 key，我们再来实现一遍 `get` 的查找功能。这回我用非递归的方式来实现，思路跟以前都是类似的：先定一个指针 p，代表当前节点，刚开始这个起点是从 root 开始，然后去不断去循环，看是向左找还是向右找。只要这个 p 这个指针不为空的时候，那么就不断去循环。

那到底是向左转还是向右找？是不是我们就要比较 p 的节点的 key，跟我们传过来这个参数 k，比较他俩的值谁大谁小。

他们俩怎么比较呢？注意我们现在这个泛型 K，它实际上是不是相当于 `Comparable` 接口的此类型？既然是子类型，它能不能用 `Comparable` 这个父类型里定义的方法？可以吧。所以我们点一下 `k.` 你可以看到它是不是有一个 `compareTo` 方法——它就是与另外一个同样实现了 `Comparable` 接口的对象进行一个大小比较。

这个 `compareTo` 我们前面也说过，它的返回值有三种情况：

| 返回值 | 含义 | 查找方向 |
| :--- | :--- | :--- |
| `-1` | 前一个小于后一个，即待查找的 k 小于 `p.k` | 向左走，`p = p.left` |
| `0` | 前一个等于后一个 | 找到了，返回 `p.value` |
| `1` | 前一个大于后一个，即待查找的 k 大于 `p.k` | 向右走，`p = p.right` |

我们把它的返回值先暂存在一个变量里，变量叫 `result`，然后根据这个变量来判断。

```java
public Object get(K k) {
    BSTNode<K> p = root;
    while (p != null) {
        int result = k.compareTo(p.k);
        if (result < 0) {
            // k 小于 p.k，向左走
            p = p.left;
        } else if (result > 0) {
            // k 大于 p.k，向右走
            p = p.right;
        } else {
            // 二者相等，找到了
            return p.value;
        }
    }
    return null;
}
```

测试的时候，节点的类型就包含了一个泛型的声明：将来 k 的类型是字符串类型，k 的取值就是 a、b、c、d 这些字符串。那 String 类它是不是我们 `Comparable` 的子类型呢？是的，我们来看一下 String 的定义里面，它确实已经实现了 `Comparable` 接口，所以字符串是可以比较大小的。测一把：a 对应的还是张无忌，b 对应的还是周芷若，跑一遍，都测试通过。

> **提示**：`compareTo` 的方向千万别搞反——是"待查找的 key 去跟节点上的 key 比"，`k.compareTo(p.k)`。返回负数说明 k 小，该往左走。这一条极容易写反，记住这一条就够了。

#### 还能再往前走两步

写完这个泛型版本之后，这段代码还有没有可以继续改进的地方呢？有这么两点。

第一点，k 现在因为改成了泛型，所以它传过来的有可能是 null，对不对？有可能。那我们最好对这个 key 做一个非空的判断，否则的话去调用任何方法，是不是就会出现空指针啊。这是一个值得注意的地方。当然我这就不改了，只是提醒大家一下。

第二点，我们值这儿也可以做成泛型对吧？它现在是 `Object`，那我们也可以把它做成泛型。你可以声明两个泛型，这个大写的 V 代表值的类型，将来凡是出现值的地方，我们都给它改成 V 这个类型。当然你加了两个泛型声明了，那我们这里也得加上，还有这个 V，这个类型，声明这些变量的时候都得加上两个泛型的类型参数。这都是一样的。

那我们 return 的时候，是不是这个 value 的值我们就可以定义成 V 了？

做到这一步你回头一看——目前这个代码是不是就跟我们 Java 中 map 集合非常的像了？也分成了键值。当然你如果觉得这里的 T 不太符合那个 k 键的第一个字母的缩写，你可以把它改一下，改成 K，这里我们也改成 k，现在是不是就变成 KV、KV 了。

我这里就不改了，测试用例也得跟着改，这就留给大家下去自己调整一下。

> **结论**：后面所有的例子，我还是采用 int 作为 k 的类型，这样我们实现起来简单一些。至于怎么让它的扩展性更好、把它改成泛型，这个任务就留给同学们了。

### min 与 max：一直向左，一直向右

接下来我们再来看 `min` 方法的实现，它是让你去查找最小关键字，然后返回这个最小关键字对应的值。

这个怎么实现呢？其实很容易。你对照着图来看——我们实际上要找最小关键字，就从根节点开始不断向左找，一直走到头，那么它就是最小的关键字。

比方说我们这个四，它向左走是不是走到二了？二呢，继续向左走，是不是就走到一了？一再向左走是不是没有路了？已经走到头了。那这时候一就是我们的最小的关键字。接下来我们只需要返回它的值就可以了。

那我们待会儿怎么用代码去判断是不是向左走到头了呢？其实就看每个节点是不是有左孩子。你看四有左孩子，是不是没走到头？二呢，也有左孩子，没走到头。直到一，没有左孩子了，说明到一这个位置它就到头了。

> **结论**：判断"向左走到头"的唯一标准就是——当前节点还有没有左孩子。有，就是没走到头；没有，就是走到头了。

思路有了，我们同样用递归、非递归两种办法来实现一下。

#### min 的递归版

再写一个独立的、用来递归的函数，叫做 `doMin`，参数是节点对象。把那个用来比较的节点对象作为参数传进来。刚才我们也已经说过，判断是不是走到头的条件，就是看一下你这个节点对象是不是有左孩子。

```java
private Object doMin(BSTNode node) {
    if (node == null) {
        return null;
    }
    // 已经走到头了，当前节点就是最小的那个
    if (node.left == null) {
        return node.value;
    }
    // left 不为空，说明没走到头，继续向左走
    return doMin(node.left);
}
```

他的左孩子已经等于 null 了，啥意思啊？就表示他已经走到头了，向左已经没有路了。那这时候这个节点自己，它是不是就算是最小的了？那我们直接返回节点的 value 值就可以了，这是表示已经找到了最小的那个节点。

如果这个 left 不为空，那是不是要继续向左走？继续向左走是不是就是去递归调用？递归调用谁呢？递归调用我们当前节点的左孩子。比方说他传过来这个 node 是这里的四，四的 left 不为空对吧，所以这个条件不成立，它就得继续递归，再看一下四的左孩子，也就是二，看二是不是满足这个条件。对不对？所以它就继续递归。是不是就 OK 了。

当然我们得考虑一种特殊情况。什么特殊情况呢？就比如说这棵树一开始就是 null，一个节点都没有。那 null 的话，我们需要找它的最左孩子吗？是不是不用找了？它也没有什么进一步的左孩子了，这些判断就都没有必要了。因此有一个特殊条件：如果我的节点等于 null，那这时候相当于根本没有什么最小的节点，直接 return null 表示没有找到。

递归方法写好以后，我们再调用它，从根节点开始找就可以了：

```java
public Object min() {
    return doMin(root);
}
```

测试一下——测试用例我刚才都写好了。我们这个方法里 `max` 还没实现，先不管。这棵树里面最小的关键字是 1，对不对？他将来返回的是不是应该是张无忌？所以调用这个方法，如果返回的是张无忌，就表示正确了。咱们走一遍，没问题，这样查找最小关键字就通过了。

#### min 的非递归版

递归版的 `min` 我先把它注释掉，来一个非递归的实现。

非递归实现里面，刚开始呢我们也是判断一下，看看这棵树如果为空了，那就没必要继续找什么最小关键字了，也就是当 root 都等于 null 的时候，直接 return null 表示没有找到。那如果 root 不等于 null，是不是我们就要不断去向左走？一直向左走到头。

因此我们先设一个指针，一个 node 指针 p，它的起点是 root，从根节点开始，然后写一个 while 循环：

```java
public Object min() {
    if (root == null) {
        return null;
    }
    BSTNode p = root;
    while (p.left != null) {
        // 还有左孩子，说明向左还没走到头
        p = p.left;
    }
    // 走到头了，此时的 p 就是最左边那个节点，也就是最小关键字节点
    return p.value;
}
```

我们刚才强调过，什么时候 node 的 left 等于 null 了，表示已经走到头了。现在这个 left 不等于 null，说明它还没有走到头，那我下次循环的时候，是不是就应该让 p 等于 p.left？这就是下次循环的时候向左来走一步。

这样循环循环循环，什么时候这个 `p.left` 等于 null 了，它就退出循环，表示已经向左走到头了。那走到头时，这时候的 p 是不是就是最左边那个节点啊？也就是我们最小关键字节点，那我们 return `p.value` 就行了。写完以后我们还是跑刚才的测试用例，是不是也通过了，最小值的非递归版实现就做完了。

这里又出现伪递归了。大家看递归实现里面，是不是又是一个伪递归？也就是方法最后又调用了这个函数自己。而且呢这个尾递归算是比较简单的一种情况，它的判断逻辑也没那么多。所以大家可以把它作为一个范例——以后如果你写递归代码，发现写出来是个伪递归，你就可以参考这段代码，看看能不能把你写的伪递归代码转换成上面这种非递归的实现。这个还是有一定意义的，因为尾递归转非递归还是比较容易的。你就以它俩作为参照去尝试转换一下。

#### max：换个方向而已

至于查找最大关键字呢？就跟它差不多了吧。沿着根节点向右找，一直向右走，走到头了，那最右边这个节点就是我们最大关键字所在的节点。

所以这个代码我们就提供一种实现了。如果根节点是空的，树里没东西，那直接 return。那如果根节点里有东西，那么就设置一个指针 p，也是从根节点开始，然后不断向右走：

```java
public Object max() {
    if (root == null) {
        return null;
    }
    BSTNode p = root;
    while (p.right != null) {
        // 还有右孩子，说明向右还没走到头
        p = p.right;
    }
    // 最右端的节点，就是最大关键字节点
    return p.value;
}
```

那怎么判断它向右走到头了呢？那就是当这个节点它的右孩子等于 null 了。走到头，不等于 null 就表示没走到头，它就不断循环，不断循环就向右走，就是 p 等于 p.right。

走到头以后，那 p 就是我们最右端的这个节点，我们直接 return `p.value` 就可以了。这里我就提供了这种非递归的实现，递归的留给大家自己去写。

最后测试一下。我这个树里最右侧的是不是 7 啊？也就是这个阴丽。那么我们把刚才的这个断言打开，将来我调用这个 `max` 去找它最大关键字对应的值，是不是最终应该返回阴丽？好，运行一下，可以看到我们的测试通过了。

至此为止，查找最小关键字，还有查找最大关键字，这两个方法的实现就实现完成了。

## 往二叉搜索树里放东西：put 与前任后任
> 对应块：BLK43 | 覆盖分集：P166-P168 | 块标题（分集名）：《基础算法-121-二叉搜索树-put》

先来看这个 put 方法的实现。

它跟 Java 里大家熟悉的 map 集合中的 put 非常像——注意，是**像**，不是说我们要去实现一个 HashMap。我们要做的事就摆在这儿：一棵二叉搜索树，你往里头丢一个 (k, v)，它得给我把这对键值正确地放到该在的位置上。

整个 put 只分成两种情况，一点都不复杂：

**第一种情况：这个 k 在整棵树里已经有了。**

有了需要新增吗？不需要。有了我们就只做一个更新操作，用你新传进来的这个值，把这个节点里旧的 value 覆盖掉。就这样，不动它的位置。

**第二种情况：这个 k 在整棵树里根本不存在。**

不存在的话，这时候我们才新增——把 key 和 value 封装成一个节点对象，挂到这棵树里。

这两种情况说完，大家心里应该有个数了：不管哪种，**都得先根据这个 k 到树里找一遍**，看对应的节点在不在。因为要对 k 进行查找，所以查找的代码我们不重写了，直接把之前 get 里那段查找逻辑拿过来用。

### 先在纸上走两遍

光说流程没意思，我们把这棵树摆出来。下面这棵树就是接下来一直在用的例子，节点上只标了 key，值对理解算法不重要，所以就不画了。

```text
                4
              /   \
             2     6
            / \   / \
           1   3 5   7
                      \
                       8
```

#### key 已经在了：走一趟查找，然后改值

要 put 的 k 是 1，1 显然已经在树里了。我们看它的过程。

首先跟查找一样，先把 1 跟根节点比较，看 1 跟根节点的 key 谁大谁小。结果 1 比根节点的 key 也就是 4 要小，对吧，所以继续向左找。然后再把 2 跟 1 做比较，发现还是比 2 小，所以继续向左。再找的话，是不是就找到了？两个 k 相等了，找到了。

找到以后做什么事呢？做更新的操作。我们可以用你传过来的这个新的 value 值，更新掉节点中旧的 value 值，做一个更新操作就可以了。这是 key 存在的情况。

```text
  1 与 根 4 比   ->  1 < 4   ->  向左
  1 与   2 比   ->  1 < 2   ->  向左
  1 与   1 比   ->  相等    ->  命中，更新该节点的 value，return
```

#### key 不在：走到尽头，挂在最后那个节点上

现在换一个，put 的 key 是不存在的，比如说是 9。我们看它的过程。

同样也是从根节点开始。先把 9 跟 4 进行比较，发现它比 4 大，所以向右找。然后接下来这个节点 7 再跟 9 比较，发现 9 还是比 7 大，所以继续向右找。找到这个 8 了，那 8 跟 9 比，发现还是 9 大，它要继续向右找吗？前进不了了——因为 8 已经是叶子节点了，它右边没东西了，因此就走到头了。

那走到头我还没有找到 9，怎么办？我新增。就把这个 9 这个节点连同它的值创建出来，作为 8 的右孩子新增进去就可以了。这是 key 不存在的情况。

```text
  9 与 4 比   ->  9 > 4   ->  向右
  9 与 7 比   ->  9 > 7   ->  向右
  9 与 8 比   ->  9 > 8   ->  想向右，但 8 右边已空
                          ->  查找失败，parent 停在 8
                          ->  新节点 9 挂成 8 的右孩子
```

> **结论**：查找成功的出口只有一个（走到 key 相等的节点），查找失败的出口也只有一个（指针被推成 null）。put 只要在这两个出口上分别接上「更新」和「新增」，剩下的活儿就是找对父节点。

### 非递归版 put 的代码骨架

大概的思路咱们清楚了，接下来写代码的实现。我们实现这个 put 方法就使用非递归方式吧，因为非递归方式更加简单一些。

那你看不管是将来要做更新逻辑，还是要做新增的逻辑，是不是你都得先根据这个 k 到树里找，看对应的节点有没有？因为要对 k 进行查找，所以这段查找的代码我们就不重写了，我们直接把之前 get 这段查找逻辑拿过来用，可以直接先复制过来。

#### 查找骨架照搬，两处 return 砍掉

复制过来以后呢，它的那两个 return 的地方我们就不要了，首先去掉。去掉之后，我们先来看看原来这段代码里什么位置应该做什么位置——算是找到了，什么位置算是没找到。

原来这个 `else` 相当于是找到了：为什么？因为它能走到 `else`，说明我们的 k 跟节点的 k 两者是不相等的（非大于即小于），这就表示已经找到了。找到了做什么事？是不是就是我们刚才第一种情况，找到了我们就去做更新，执行完更新之后 return 就可以了。

哪段代码表示没有找到呢？等这个 while 循环都循环完了，执行到这个位置的时候，那表示我们的 k 跟节点里的 k 都对比过一遍了，还是没有找到，那这个情况下我们做新增是不是就可以了。

所以待会呢我们主要改动这两行注释出的代码就可以了，一个做新增，一个做更新。

```java
public Node put(int k, Object v) {
    Node parent = null;          // 新节点要挂的那个父节点
    Node node = this.root;       // 当前考察的节点

    // 查找骨架：从 get 直接搬过来，两处 return 已砍掉
    while (node != null) {
        parent = node;           // 每转一圈，先把上一站记下来
        if (k < node.key) {
            node = node.left;
        } else if (k > node.key) {
            node = node.right;
        } else {
            // 出口一：k 已存在，只更新，不新增，也不必再向下走
            node.value = v;
            return;
        }
    }

    // 出口二：k 不存在，走到这里说明查找失败
    Node newNode = new Node(k, v);      // 键值来自我们这里的 key、value

    if (parent == null) {
        // 新增情况一：整棵树是空的，新节点直接当根
        this.root = newNode;
    } else if (k < parent.key) {
        // 新增情况二：作父节点的左孩子
        parent.left = newNode;
    } else {
        // 新增情况三：作父节点的右孩子（等于的情况已经 return 掉了）
        parent.right = newNode;
    }
}
```

#### parent：比 node 慢一拍的那份引用

更新这儿比较简单，因为能执行到这儿，表示已经找到了这个节点对象了。那我们更新要做的事，不就是把节点对象的 value 更新成一个新的值吗？也就是让节点对象的 value 属性更新成我们传过来这个新的 value 值，就 OK 了。所以更新呢这一行代码就 OK 了。

接下来新增的稍微麻烦一些。新增的话，我得先创建一个节点对象，节点对象它的键值是不是分别来自于我们这里的 key、value？就把这个键值传过去，根据它俩创建出新的节点对象了。

但是光这样还不够啊——我们要把新的节点对象加入到这棵树里面去。就比如说我们刚才要把这个 9 加进去，那加进去意味着什么呢？意味着你得给新的节点 9 找一个父亲。比如说我们这个例子中，就是把 8 这个节点作为新节点 9 的父亲。

但是你看，我们现有的代码里好像并没有一行代码是跟这个父亲相关的是吧？所以我们接下来得想个办法，来找到我们新节点的父节点。

你看我们的最终目的是要找到 9 它的父节点 8。那实际上我们这里 node 这个变量，它就曾经记录过 8 这个节点的引用值啊。一开始 node 变量初始值是根节点对吧，所以他引用的是根节点 root，也就是 4 这个节点。随着他不断向右找，node 的值是不是曾经从 4 被更新成了 7，然后又从 7 被更新成了 8。

当然最后一次循环，他发现 8 的 k 仍然比我们要查找的 9 要小，所以呢他就把 node 又更新成了 8 的右孩子，也就是 null，最后才退出循环。所以呢，我们只要在 node 被更新成 null 之前，能把它的这个引用值记录下来，是不是就相当于找到了我们新增节点的父节点啊？

记录 node 被更新成 null 之前这个值简单吗？简单，我们再加一个变量不就行了吗。这个变量呢我们就把它起个名字叫个 parent。

```text
  查找 9 的过程中，parent 和 node 各自停在哪：

  初始        parent = null      node = 4
  第 1 圈     parent = 4         node = 7     （9>4，向右）
  第 2 圈     parent = 7         node = 8     （9>7，向右）
  第 3 圈     parent = 8         node = null  （9>8，向右；8 没右孩子）
  退出循环    parent = 8   <--  新节点 9 的父亲
              node   = null <--  查找失败信号
```

> **易错点**：`parent = node` 一定写在 `if` 判断**之前**。这样最后一次循环才会先把 8 记进 parent、再把 node 推成 null；如果写在判断之后，parent 就会晚一拍，最后只能记住 7，9 就会被挂错地方。

#### 出了循环：接左孩子、接右孩子，或者干脆当根

有了父节点，有了新节点，那建立它们的父子关系是不是很容易了？

当然这里我们还是得去判断一下，这个新节点是父节点的左孩子还是右孩子啊。因为刚才循环内确实判断过了，但是出了循环以后呢，这个父节点的 k 跟我这个新节点谁大谁小，我们又不知道了，所以我们还得判断一下。

如果父节点的 k 跟新的 key 比较一下，新的 k 小，那它是不是应该作为左孩子？好，它应该作为 parent 的左孩子，那新的节点我们就把刚才那行代码直接复制过来没问题吧，这是一种情况。那如果我们的 key 是大于刚才 parent 的 k，那我就应该作为 parent 的右孩子，这是两种情况。

> **结论**：不可能再相等了，因为相等的那条路径已经 return 走了，走的是更新逻辑。所以最后这个条件可以简化成一个 `else` 就行。

当然呢还有一种可能：树是空的情况。树是空的话，这个 parent 相当于一开始它的值是 null 对吧？那空的话它根本没有走这个 while 循环，所以等循环结束，这个 parent 是不是还是空啊？所以我们应该考虑这个 parent 为空的情况。

parent 为空就表示我这棵树整个也是空的，那这种情况下大家想，那是不是根节点就是我们这个新节点啊？它就没有 parent 了，那我们这个新节点就作为这个根节点就可以了。

所以我们把刚才 put 方法的逻辑稍微串一下：我首先是根据这个 k 去找一找看有没有这个 k；如果找到了这个 k，我们就走更新的逻辑，就是把找到的节点值更新成新值。如果没有找到呢，我们就要走新增的逻辑。那新增逻辑就分成了三种情况：树本身就是空的，我把新节点创建出来，它就作为整个树的根节点；树不是空的，我就要找到新增节点它的父节点是谁，看一下新节点的 k 如果比父节点的 k 小，那是不是把它作为父节点的左孩子呀；如果我的 k 比父节点的 k 大呢，那我的新节点就作为父节点的右孩子。当然这个条件我们还可以稍微简化一下，因为这里只存在小于或者大于这两种情况，不可能再有等于了，所以我们可以把最后这个直接给它改成一个 `else` 就可以。

```text
  新增的三条分支，入口都是同一个：循环走完了，node == null

  parent == null   ->  空树，新节点自己就是根
  k <  parent.key  ->  挂左孩子
  k >  parent.key  ->  挂右孩子     （k == parent.key 这条路早在循环里 return 了）
```

#### 跑一遍：新增和更新各测一次

最后呢我们来测试一下。测试的话我就去往我们这个树里添加了一些键值，有 4 的一个键值、2 的键值、6 的键值……添加出来它最终长的这个树的样子，就是长这个样子。

所以呢我接下来又创建了一个跟他一模一样的树，只不过不是用 put 方法创建的，我就手工创建出来。这个树跟我们刚才用 put 方法创建出来的树，是不是长得一模一样？当然比较的过程只比较了 k 值，没有比较 value。如果一模一样它会返回真、返回正，所以我的断言是 `assertTrue`。这些都是去测试了一些新增的情况。

那修改的情况呢？就是看这个树已经添加好了，我又去 put 一个 1，那 1 是不是已经有了？有了之后它就会把原来这个对象更新成我新的这个新的值。最后呢我去判断一下，如果我再去 get 一下，返回的是不是应该是更新后的这个值。

### 前任后任：先从「先排个序」的直觉说起

好，接下来呢我们来看一下，如何求某个关键字在二叉搜索树中的前任值和后任值。

这道题目啊，其实如果按我们直观的想法，我可以这样做：我先把二叉搜索树中所有的 k 给他排个序，可以吧？比如说我现在这个例子中排好序呢就是 1 2 3 4 5 6 7 8。排好序以后呢，我随便找一个 k，比如说我要找 4 这个 k 的前任后任怎么办？它的前一个肯定是 3 啊，后一个肯定就是 5 啊，没问题吧。排好序了，就很容易知道它的前任是谁、后任是谁了。

那我们这个二叉搜索树怎么排序呢？其实有一个最简单的方式，就是对它做一个中序遍历。二叉搜索树的中序遍历，结果就是升序的结果。

我们用之前这个二叉树遍历的例子来看一遍，看它的中序遍历是不是升序的结果。中序遍历它的规则是不是遵循着「左、根、右」这个规则。

所以从根节点开始，能直接打印根节点值吗？还不能啊，因为根节点的左子树还没有遍历的情况下，那根节点的值你得放一放。所以呢这个顺序就是它得先向左找，找到头。找到头以后，「左根右」：先把 1 这个节点处理好了。1 处理好了，意味着 2 这个节点的左子树处理完成了，所以可以接下来打印 2 的值了。然后处理 2 的右子树，也就是把 3 这边处理好，也就是打印 3。大家看是不是打印的顺序 1 2 3。

等到 3 处理完成了，那大家想，1 2 3 作为 4 的左子树是不是完成了？好，接下来是不是可以打印 4 的值了。四的值打印完了，处理 4 的右子树。那 4 的右子树这边，同样也是先不能处理 7 啊，因为 7 它它的左子树没有处理完成之前，7 这个值不能打印。所以它沿着 7 先找到他的头，向左找找到头，然后所以接下来打印的是 5。5 打印完了，说明 5 6 作为 6 的左子树完成了，所以接下来可以打印 6 的值了。6 完成了，那 5、6 作为 7 的左子树完成了，所以接下来它可以打印 7 的值了。最后呢去打印一个 8，整个这个遍历就完成了。

```text
  1..8 这棵树上的中序（左 -> 根 -> 右）：

  先一路压到最左 1，打印 1
  回 2，打印 2           ->  2 的左子树（1）已完成
  下到 3，打印 3
  回 4，打印 4           ->  4 的左子树（1 2 3）已完成
  下到 5，打印 5
  回 6，打印 6           ->  6 的左子树（5）已完成
  回 7，打印 7           ->  7 的左子树（5 6）已完成
  下到 8，打印 8

  输出：1 2 3 4 5 6 7 8   ——  升序
```

可以看到，你对一棵这样的二叉搜索树做中序遍历，它的结果就是升序的。有了这个升序结果，我们找某个节点的前任后继就很容易了。

#### 中序遍历能解决问题，但性能撑不住

这是我们第一种求前任后任的思路。那我们实际去实现这两个方法的时候，并不会采用中序遍历。很遗憾，并不会用。

为什么呢？因为中序遍历它的性能并不高。比如说我要用中序遍历的办法找某个节点的前任，你想如果让你去实现，你该怎么实现？是不是你得设置两个指针啊：第一个指针指向你要找的那个节点，还有一个指针是在它前面，指向它之前的一个节点。这样我们把这两个指针同步地向前推进。

用中序遍历的方式，以 1 2 3 4 5 6 7 8 来遍历。比如说我要找的这个节点是 8，当后一个指针指向 8 的时候，那前一个指针是不是就指向了它的前任 7 啊？这样我们就把它的前任找到了。

但是你想啊，最坏的情况，你是不是得把整棵树都用中序遍历过一遍，你才能知道它的前任是谁啊？这样性能不太高。

```text
  找 8 的前任，最笨的实现要挂两个指针一起往前走：

  指针 A（要找的节点）  :  1  2  3  4  5  6  7  8
  指针 B（它前面一个）  :  1  2  3  4  5  6  7
                          ^                 ^  ^
                          A                 B  A

  A 走到 8 时 B 才停在 7  ->  8 的前任是 7
  可 8 恰好是最末尾，前面 1..7 全白走了一遍才换来这一个答案
```

那怎么办呢？前人呢给我们总结了一些规律，我们根据这个规律，就能更高效地找到节点的前任和后任。

### 前任的规律一：左子树的最大值

我们先以前任为例，找前任或者说找前驱，有两条规律。

第一条规律：你的节点如果有左子树的时候，这时候你的前任节点就是左子树的最大值。这是一种招法。

我们先理解一下：如果这个节点有左子树，那它的前任节点就是左子树中的最大值。

举个例子大家可能就好明白了。比如说我要找 4 的前任，那 4 的左子树也就是这边的 1、2、3，是不是都比 4 要小呀？那在它小的这个左子树里面，我挑一个最大值，也就是 3，是不是就是 4 的前任？没问题吧。

所以有左子树的情况，左子树中的最大值就是我们当前节点的前任。

在我们这个例子中，这属于这种情况的都有哪些呢？有 2，2 有左子树对吧，那左子树中就一个节点，这个 1 就是 2 的前任。还有谁呢？还有 4，刚才我们说过了，4 呢也是有左子树的，那它左子树里面最大的 3 就是 4 的前任。前面还有谁呢？还有 6，6 也有左子树啊，6 的左子树就一个节点 5，那么这个 5 就是 6 的前任。最后呢还有一个 7，7 的左子树有 5 和 6 啊，那 5、6 里最大的是 6，就是 7 的前任。

### 前任的规律二：从左而来的最近祖先

第二种情况呢，就是这个节点它没有左子树，这时候我们就要从他的祖先节点里去找他的前任了。

那这个祖先我们先理解一下是指什么？是指这个节点它的父节点，或者是爷爷节点，或者是太爷爷节点啊，这些都叫他的祖先啊。并且呢，这个祖先节点必须从这个节点的左边来。

这个从左边而来的祖先，并且也是离这个节点最近的一个祖先，那这个祖先就是我们的前任。

把这个话说起来有点绕啊，我们结合一个例子大家就好理解了。

比如说我们看这张图，这张图里我以 5 这个节点为例。我先问一下，5 这个节点的祖先节点都有哪些？是不是有 6、7、4？6 是他的爹，7 呢是他的爷爷，4 呢是他的太爷爷啊。至于剩下的 8、1、2、3，这跟 5 都没有一个祖先的关系对吧。

那这几个祖先里，谁是他的前任呢？注意第一个条件，就是你这个祖先啊，必须是在我当前这个节点的左侧啊，必须是从左过来的，从右过来的祖先不行。

为啥呢？你看 6 是在 5 的右侧啊，从右过来的。从右过来的祖先它意味着什么呢？它意味着比 5 大啊，因为靠右的一般这个节点都大，靠左的这个节点才是更小一些的。所以从右边过来的 6 这个祖先它比 5 大，比我大，所以他肯定不是我们前任啊，前任是要找比他小的对吧。所以 6 被排除了。那 7 也不行啊，7 也是从右侧过来的，他也不是我们要找的前任。祖先里只有 4 从左过来的吧？4 在 5 的左边过来的，所以 4 是我们要找的前任。

再来看 3。3 呢它也是没有左子树的，那它的祖先里有 2 和 4，那这个 2 和 4 里谁是他的前任？显然是 2，2 是不是从左过来，并且是离 3 最近的，这个 2 就是 3 的前任。

还有一个例子就是 8。8 的祖先里有 7 和 4 啊，他们俩都是从左过来的对吧？但是 4 跟 7 比，7 是不是离 8 更近啊？所以 7 是 8 的前任，那 4 呢由于离得更远就不算了。

那没有左子树的，还有一个就是 1。大家看它的祖先是 2 和 4，2 和 4 都是从右而来对吧？它没有一个从左边而来的祖先，所以呢它没有前任。

所以第二种情况：没有左子树，就找一个从左而来的祖先，这个祖先是我们的前任。

### 把前任写出来

刚才呢我们讨论了找一个节点它的前任的两种情况，那下面呢我们把这个代码来写一遍。

我们要找它的前任，是不是你得先找到这个节点本身啊？如果这个节点在树里都没有，那它也无所谓什么前任了是吧，所以我们先找到这个节点。

那找节点的代码呢我们再写一遍啊，因为有些逻辑跟我们之前的 get 里的逻辑还是有所区别，所以我们得重写一遍。不过还好这个代码呢我们已经写过很多次了，应该比较熟了。

先定一个指针 p 啊，看到初始值是我们的 root 根节点，沿着根节点向下找。写一个循环，当 p 不等于 null 的时候，那就做判断呗：判断一下如果我们要找的 k 它更小一些，在当前节点的左侧，那么就向左找，`p = p.left`；那么如果我们的 k 更大一些，在当前节点 k 的右侧，那我们就应该向右找，p 就等于 `p.right`；当然如果它俩都相等了，两个 k 相等，就表示找到了。

找到以后应该返回整个方法吗？哎不应该，因为我们接下来还有逻辑呢。退出循环以后，那我现在 p 指针所指向的节点是什么？是不是就是我们找到的那个节点？针对这个找到的节点，我们就可以对它套用刚才的规律一和规律二的代码了。这里的 p 就是我们查找到的节点。

当然还有一种可能，就是等循环结束了，这个 p 等于 null 了，它才退出循环，这个时候就表示没有找到对吧。那当前节点都没有找到，那它的前任节点是不是也相当于不存在啊？因此我们先把这种情况处理了：如果这个 p 等于 null 了，表示当前节点没找到，那它的前任是不是也是 null 啊，所以我们 return null，没问题吧。

#### 规律一落地：把 max 从「找全树最大」改成「找任意子树的最大」

那我们先来看第一种情况。第一种情况就是，当我这个节点如果有左子树的话，那这时候我们就找到这个节点左子树中的最大值，这个左子树中最大值就是我们的前任节点。

那写成代码呢就是我们判断一下，如果当前节点 p 它的 left 不为空，这是意思是它是不是有左子树啊，这个时候我们就要去找这个左子树的最大值了。

那怎么找一棵子树中的最大值呢？哎其实我们前面其实写过类似的代码。你看我们之前写过一个 max 方法，那这个 max 方法当时它的作用是什么？就是从根节点开始找整个树中的最大值对吧，他沿着右侧一直向右走，走到头是不是就是最大值？当时我们写过啊。

那我现在不是找整个树中的这个最大值了，我是找一棵子树的最大值，那怎么办呢？其实很简单。比如说我我要找 1、2、3 这棵子树，这个子树的最大值是不是就是以 2 作为起点，然后不断向右走，走到头了，那这个 3 就是它的最大值。所以我们只要把刚才这段逻辑稍微改一下就行。

刚才这段代码它是只针对根节点找一个最大值，现在我们是要针对任意一个节点找它这棵子树的最大值，我们把这个代码给他写得更通用一些。怎么写呢？我们还是来一个 max 方法，只不过它接收的参数是任意一个节点类型，就比如说我们把它叫 node。那我们把刚才的逻辑直接搬过来：刚才逻辑就是以根节点作为起点找这个树中的最大值，现在我把这个根节点换成任意一个节点，是不是显然它就更通用了？它就是找任意一个节点作为起点的这棵子树中的最大值。

这么写完了以后呢，你看我们刚才这个 max 方法其实也可以改一下，我可以改成调用啊，间接调用刚才我们这个重载的 max，只不过参数是 root。这是不是就是找根节点作为起点的这个树的最大值？

```java
// 原版：只能找整棵树的最大值
public Node max() {
    Node node = this.root;
    while (node.right != null) {
        node = node.right;
    }
    return node;
}

// 通用版：换成任意节点作为起点
public Node max(Node node) {
    while (node.right != null) {
        node = node.right;
    }
    return node;
}

// 原版可以直接委托给通用版
public Node max() {
    return max(this.root);
}
```

好，写好以后呢，我们就可以在找前任这儿去用它了。那我要找左子树的最大值怎么办？我们的 `p.left` 是不是就是左子树的这个起点呀？比如说我当前节点是 4 啊，它的左子树的起点是不是就是它的 left，2 啊。那我要找到最大值，简单吧？直接 return 我们刚写的 max，然后把 `p.left` 作为参数传进去就 OK 了。这是我们的情况一就处理完了：如果节点有左子树，那么就找到这个左子树的最大值，这就是它的前任。

#### ancestorFromLeft：祖先不用单独算，查找时顺手就经过

好大家来看代码。如果能执行到这，就表示他肯定是找到节点，并且呢是没有左子树的这种情况。因为没找到节点是不是在前面 return 了，有左子树的情况在前面也 return 啊。走到这呢，说明它是符合我们最后这种情况，就是这个节点已经没有左子树了。

那这种情况下呢，我们就要找他离他最近的、并且是从左而来的这个祖先节点，作为我们的前任节点。

那这句话可能就把同学拦住了：我怎么知道哪些节点是它的祖先节点？又怎么进一步知道这个祖先节点是从左而来呢？

啊，其实很简单啊。我看我以这个 5 这个节点为例，那我要找到 5 这个节点的过程中，是不是它必然已经经历过一些节点了啊？它从根节点开始吧，先是 4 比 5 小要向右找，然后 7 比 5 大要向左找，6 比 5 大是不是继续向左找，最后找到了 5。所以它经历过的 4、7、6 是谁呀？是不是就是 5 的祖先呀。

所以我们刚才这个循环的过程中，其实循环的每一步都是在经历他这些祖先节点，这个没问题吧？知道了怎么去获取祖先，那我们怎么去进一步判断他这个祖先是从左边来还是从右边来呢？哎其实也很容易。

你看如果我们向右走啊，4 到 7 是不是向右走啊？说明 4 是不是在左边啊。所以只要我们看到这种向右走的代码，那就表示祖先是从左而来。那像 7 到 6，7 到 6 是向左走的，这种就不是啊，这种是从右而来的啊，包括 6 到 5，这也不是。

```text
  找 5 的查找路线，以及每一步在"记账"：

   4  --向右-->  7  --向左-->  6  --向左-->  5
   ^              ^
   |              七、6 都是从右边来的，不记账
   四从左边来  ->  ancestorFromLeft = 4

  命中 5 之后不再改动这个变量
  ->  它停在 4  ->  4 就是 5 的前任
```

思路有了，那下面我们把它转换成代码。其实写成代码呢很容易啊：我们设一个指针变量，它代表从左而来的祖先，然后给它起个名字叫做 `ancestorFromLeft`，这是祖先的意思，然后 fromLeft 啊，就是表示是从左而来的祖先啊。

刚开始呢我们给它设置为 null，因为有可能刚开始它没有这个祖先啊。那每次循环的时候，我们刚才说过啊，只要他向右走，就表示这个祖先是从左而来好，那我们就把它它的值改成当前节点的值。那等到循环结束，那如果它不为 null 啊，如果我们这个 `ancestorFromLeft` 它不等于 null，那我们说过这个节点它是不是就是我们的前任节点啊？这个时候我用一个三元运算符，就返回这个节点的值是不是就可以了。那如果它等于 null 呢？他没有这个从左而来的祖先，那也就相当于他没有前任啊，这是我们返回 null 就可以了。

好，这个代码我们就写完了，把它稍微整理一下吧，换个行。

```java
public Object predecessor(int k) {
    Node ancestorFromLeft = null;   // 从左而来的最近祖先，初始为 null
    Node p = this.root;

    while (p != null) {
        if (k < p.key) {
            p = p.left;             // 向左走：当前祖先在右边，不记账
        } else if (k > p.key) {
            ancestorFromLeft = p;   // 向右走：祖先在左边，记一笔
            p = p.right;
        } else {
            break;                  // 找到了，但不能直接返回，后面还有活
        }
    }

    if (p == null) {
        return null;                // 连节点都没找到，前任自然也不存在
    }

    if (p.left != null) {
        return max(p.left).value;   // 规律一：左子树的最大值
    }

    // 规律二：没有左子树，取从左而来的最近祖先；没有就返回 null
    return ancestorFromLeft != null ? ancestorFromLeft.value : null;
}
```

> **结论**：祖先不需要单独去回溯父指针找。查找过程中路径上的每一个节点，天然就是这个目标节点的祖先；而「是从左边来的」这个条件，翻译成代码就是「这一步是向右走的」。这就是 `ancestorFromLeft` 只在 `else if` 分支里赋值、而 `p = p.left` 分支里不赋值的原因。

#### 推演：一没有前任，八有前任

好那我们再看几种情况。

比如说 1 这个节点，1 这个节点我要找它的前任，它的过程是怎样的呢？root 是 4，从根节点开始。那这个从左而来祖先刚开始是不是 null？我们每次循环，因为从 4 找到 1 整个这个过程它都是向左走，都是走的第一个 if，所以它根本没有机会进入我们第二个 else if。因此这个从左而来的祖先是不是始终没被赋上值啊？它的值就一直是 null，将来就表示我这个 1 这个节点没有前任。它就相当于走到这个逻辑了，没问题吧？这是第一种情况。

再看一种情况，比如说我们以这个 8 啊，没有左子树的是 8 对吧？以 8 为例再找一个 8，它是怎么找的呢？刚开始我们这个从左而来祖先也是 null，那我们第一次进入循环的时候，是不是它就进入了我们这个 else if 条件啊？它是向右走的嘛，向右走它就把我们这个变量更新成 4 了。然后继续向右走，因为 7 呢也要向右走，所以呢它就把我们这个祖先这个变量继续更新成 7 这个节点。那等当我们找到了这个 8 以后，那这个祖先变量的值记录的是谁啊？是不是记录的就是我们刚才 7 这个节点。所以我们这个 `ancestorFromLeft` 它不等于 null 了，这是我们的 7，就是我们 8 的前任节点，它就返回这个 7 这个节点的值是不是就可以了。

```text
  找 1：4 --向左--> 2 --向左--> 1
        每一步都走"k < 当前节点"的分支，第二条分支从未进入
        ancestorFromLeft 保持 null  ->  1 没有前任

  找 8：4 --向右--> 7 --向右--> 8
        每一步都走"k > 当前节点"的分支，依次记账 4 -> 7
        命中 8 后不再改动  ->  停在 7  ->  8 的前任是 7
```

所以呢我们这个代码并不难写，但是你要理解这个从左而来的祖先怎么去判断啊，这是关键点。

### 后任就是前任的镜像

好，接下来呢我们再来看这个后继节点啊，或者叫后任节点啊。那他也有两条规则，这两条规则我们可以看到，它跟我们刚才找那个前任时的规则是对称的。

一条规则呢，就是当这个节点有右子树的时候，那这时候后继节点就是右子树中的最小值啊。

你看我们先以 5 为例啊，5 呢是有右子树的，当然它的右子树大家想肯定都比 5 大嘛，但是比 5 大的这些节点里，我们是不是得挑一个最小的，才是离我最近的呀？所以这里面我们挑一个最小的 6，就是 5 的后任节点，没问题吧。

好那这样的例子呢，比如说还有像我们的 2 这个节点，2 它也是有右子树的，右子树里的最小值 3 就是 2 的后任；3 呢它的右子树是 4 啊，里面最小的就它一个，4 是 3 的后继；7 呢，它的后继是 8。

好没问题吧，这都是有右子树的情况。那第二种情况呢，就是这个节点没有右子树，没有右子树还是要到祖先里找。那到祖先里找的话，就是找他从右而来的祖先，从右而来并且离他最近的这个祖先。

那这个我们也看几个例子啊。比如说 1，1 有两个祖先 2 和 4，他们是不是都是从右而来啊？4 是从右而来，2 也是从右而来，那这里离 1 最近的是谁？是 2，那这个 2 就是我们 1 的后任。

还有就是 8，8 呢它也没有右子树，但是它的祖先 7 跟 4 都是从左而来啊，那这时候 8 呢也相当于是没有后继。

这就是我们分析后继如何找的两种情况。

```text
  有右子树：取右子树最小值
      5 -> 6        （5 的右子树里只有 6）
      2 -> 3        （右子树 {3}）
      3 -> 4        （右子树 {4}）
      7 -> 8        （右子树 {8}）

  没有右子树：找从右而来的最近祖先
      1 -> 2        （祖先 2、4 都从右而来，最近的是 2）
      8 -> 无       （祖先 7、4 全是从左而来，一个都没有）
```

好其实有了我们之前写这个求前任代码的基础，我们在写这个求后任的代码就非常容易了。这个代码都是对称的，所以我们就不重头写了，直接拷贝一遍，拿过来粘贴到我们求后任这个方法里。

#### 代码怎么改：变量挪位置，再补一个 min

首先呢咱们把这个变量名改一下对吧。变量名呢我们就不叫 `ancestorFromLeft` 了，起个名字叫 `ancestorFromRight` 啊，就是表示他是从右而来的一个祖先。

那既然是从右而来，是不是我们向左走的这种情况下，它才算从右而来？所以我们把这个赋值语句放在向左走的这个代码这，这是改动。还有哪要改动呢？就是我们如果节点有右子树，那这是我们的后任，就是右子树的最小值，没问题吧？所以我们判断条件呢就改成：当我找到了这个节点以后，就看它有没有右子树啊，如果有右子树，那就是找一个右子树的最小值。

那这个最小值方法我们也是没有写啊，我们把它写一下，就在原来这个最小值的方法基础上咱们改一下，给它加一个重载的求最小值的方法，粘贴过来参数呢就是一个任意一个节点类型，我们就是以这个节点作为起点啊，去找这棵子树里的最小值，这里的 root 都用这个 node 代替掉，没问题吧？啊这个代码我们也简化一下。

```java
public Object successor(int k) {
    Node ancestorFromRight = null;  // 从右而来的最近祖先，初始为 null
    Node p = this.root;

    while (p != null) {
        if (k < p.key) {
            ancestorFromRight = p;  // 向左走：祖先在右边，记一笔
            p = p.left;
        } else if (k > p.key) {
            p = p.right;            // 向右走：当前祖先在左边，不记账
        } else {
            break;
        }
    }

    if (p == null) {
        return null;
    }

    if (p.right != null) {
        return min(p.right).value; // 规律一：右子树的最小值
    }

    // 规律二：没有右子树，取从右而来的最近祖先；没有就返回 null
    return ancestorFromRight != null ? ancestorFromRight.value : null;
}

// 通用版 min：任意节点作为起点，找这棵子树的最小值
public Node min(Node node) {
    while (node.left != null) {
        node = node.left;
    }
    return node;
}
```

这是求从根节点开始求它的最小值的方法，写好了。我们看一下刚才的代码啊，刚才代码里就是当有右子树的情况下，那就找右子树中的最小值，没问题吧？这是第一种情况。那第二种情况呢，就是节点没有右子树，那这时候我们去找离它最近的、并且是从右而来的祖先。

好，那从右而来的祖先是我们的后继啊，那其实从右而来祖先我们是不是前面已经把它记录下来了？哎你向左走的肯定就是从右而来的啊。那判断一下，如果它不为空，那就返回这个祖先的 value 值；如果为空，说明它没有后继了，这时候返回 null 啊。

这是我们的找后继的代码也写完了。

### 本讲提到的题目

**题目**：给定一棵二叉搜索树和一个关键字 k，求 k 在这棵树中的前任值与后任值。

**解析**：

- 直觉做法是先把整棵树的所有 k 排成升序（对二叉搜索树做中序遍历即为升序），再取前后相邻元素。但这样即使只为找一个节点的前任，也要走完整棵树的中序遍历，性能撑不住。
- 正确做法是沿着「目标节点的查找路径」直接推导，规则是**对称**的一对：

| 情况 | 前任 | 后继 |
| --- | --- | --- |
| 有左/右子树 | 左子树的最大值（`max(p.left)`） | 右子树的最小值（`min(p.right)`） |
| 没有左/右子树 | 路径上从左而来的最近祖先（最后一步向右走的那一站） | 路径上从右而来的最近祖先（最后一步向左走的那一站） |
| 找不到该节点 | `null` | `null` |
| 对应祖先也不存在 | `null`（如本树的 1 没有前任、8 没有后继） | `null` |

**答案**：`predecessor(k)` 与 `successor(k)` 的完整实现见上文两节。以本树为例，1 的前任为 `null`、8 的前任为 7、5 的前任为 4；1 的后继为 2、5 的后继为 6、8 的后继为 `null`。

## 二叉搜索树的删除：从托孤讲到递归
> 对应块：BLK44 | 覆盖分集：P169-P172 | 块标题（分集名）：《基础算法-124-二叉搜索树-删除-1》

### 四种情况，前两种最简单

查找和插入我们都已经写完了，唯独删除，相对还是比较复杂——它的情况比较多。一共给大家总结了一共有四种情况。

前两种比较简单，就是说这个被删除的节点只有一个孩子：要么有右孩子没左孩子，要么有左孩子没右孩子。这两种情况待会儿我们可以看到，比较简单，也容易实现。

第三种情况就是被删除的节点左右孩子都没有。当然，第三种情况其实待会儿大家会看到，它会被涵盖到情况一和情况二里面去。

最后一种情况也是最复杂的：被删除的节点左右孩子都有。这种就比较复杂了。

| 情况 | 被删除节点的孩子 | 处理思路 | 难度 |
| :--- | :--- | :--- | :--- |
| 情况一 | 没有左孩子 | 把右孩子托孤给父节点 | 简单 |
| 情况二 | 没有右孩子 | 把左孩子托孤给父节点 | 简单 |
| 情况三 | 左右都没有（叶子节点） | 会被情况一、二涵盖 | 不用写额外代码 |
| 情况四 | 左右孩子都有 | 让后继节点顶替上去 | 最复杂 |

### 没有左孩子：把右孩子托孤给父节点

我们先说明一下，待会儿举例说明的时候，被删除的节点我总是选 4，可以吧？每次咱们都去删除 4。

来看 4 有什么特点。现在这个 4 这个节点是不是只有一个孩子啊？没有左孩子，但是他有一个右孩子 7。不过右孩子 7 啊，它可能还有自己的后代。

```text
          3
         / \
        1   4        <- 4 是 3 的右孩子，没有左孩子，右孩子是 7
         / \
        2   7
             \
              9
```

这种情况我们要删除该怎么做呢？大家也能想到，第一步你得先找到这个被删除的节点，对不对？先从二叉搜索树里找到这个待删除的 4，找到它之后，是不是我就可以把它删掉了？

删除本身很简单，但是他得处理他的后事。啥意思呢？就比如说 4 要死了，那他的儿子是不是总得有人照顾啊？交给谁照顾他呢？

交给 4 的爹，也就是 7 的爷爷 3，由 3 来照顾他。所以这个操作我就把它称之为叫**托孤**——就是把 7 托孤给 3 来抚养。

效果呢，就是把 7 变成了 3 的右孩子。删除前 4 是 3 的右孩子啊，但是 4 被删掉了，那就把 7 作为 3 的右孩子。7 如果有后代的话，这些不用变，它就跟着过来就可以了。

```text
          3
         / \
        1   7        <- 7 托孤给 3，成为 3 的右孩子
         / \
        2   9        <- 7 原有的后代跟着过来，不用动
```

看懂了吧？这是我们第一种情况：**如果删除的节点没有左孩子，那我就将来把他的右孩子托孤给 parent**，parent 就是指被删除节点的父亲。

### 没有右孩子：把左孩子托孤给父节点

那么第二种情况就跟它非常的类似了。来看一个例子，我还是删除 4。

这回 4 是不是有左孩子 2，但是他没有右孩子啊？那大家告诉我怎么处理？是不是类似的呀——我没有右孩子，有左孩子，那将来就把它的左孩子托孤给 4 的父亲。当然这回 4 的父亲是 6。

```text
          6
         / \
        5   4        <- 4 是 6 的右孩子，有左孩子 2，没有右孩子
           /
          2
         / \
        1   3
```

效果呢，也是先找到被删除的节点 4，然后接下来我就知道他左孩子是谁了嘛，然后把他的左孩子托孤给 6。当然注意连带的左孩子后代啊，这些 1、2、3 都会一起带过来。

```text
          6
         / \
        5   2        <- 2 托孤给 6，成为 6 的右孩子
           / \
          1   3        <- 2 原来的后代跟着过来，不用动
```

### delete 方法的架子：先查找，再记 parent

这两种情况我们先分析完了。我们先把前两种情况它的代码实现一下，然后再去分析后面两种情况。

方法呢已经给大家准备好了，就是一个叫 `delete` 这个方法。方法的参数呢，就是我们待删除节点的 `k`，然后它的方法的返回结果呢，是这个被删除节点的 `value` 值。

第一步也是要先找到这个待删除节点，对吧？所以我们那个查找节点的代码还得再来一遍。当然我们就不重头写了，我们随便找一个之前写过的查找代码，咱们复制一份，把它拿过来用就好，稍微改一下。

```java
public Node delete(int k) {
    // 第一步：从根开始找待删除节点，同时记下它的父节点
    Node p = root;
    Node parent = null;
    while (p != null) {
        if (p.value == k) {
            break;
        }
        // 要向左/向右走了，走之前先把当前节点记成 parent
        parent = p;
        if (p.value > k) {
            p = p.left;
        } else {
            p = p.right;
        }
    }

    // 第二步：判断一下这个节点是不是真的找到了
    // 没找到的话，后续的删除也就无所谓了，对不对？
    if (p == null) {
        return null;
    }

    // 第三步：找到了，执行删除操作（下面分四种情况）
    // 第四步：返回被删除节点的 value 值
}
```

`parent` 这个变量怎么记录呢？其实前面也见过类似代码。我们在循环外层定一个变量，就叫 `parent`，用来记录待删除节点的父亲。

你看我们每次在没找到这个待删除节点之前，它是不是要向左走或者向右走啊？在他比如向右走之前，那这个节点我给它存储到 `parent` 变量里。等下次循环的时候，他找到了这个待删除节点，那上次记录的这个节点是不是就是它的 parent？

很简单，就是在比如向右走之前，我们把当前 `p` 指针指向的节点存储到 `parent` 变量里就可以了。下次循环的时候，`p` 呢就变成了右孩子，`parent` 呢是我们的父亲。向左走之前是不是做类似的操作？也是向左走之前记录下 `parent`。

> **易错点**：找到了千万别再记录 `parent`。为什么呢？大家看，你把当前节点的值赋值给了 `parent`，然后就 `break`，`break` 以后，`parent` 跟 `p` 它俩的取值是不是一模一样了？显然就不符合父子关系了。这里咱们不记录。

### 托孤方法 shift

接下来呢，我们来实现一个相对比较重要的方法，叫托孤方法。当然这个名字是我起的。这个方法有一定的通用性，在接下来的好几个地方都会用到，所以我们先把它实现一下。一些资料里啊都把它叫 `shift`，这是它的英文名字。

那这个方法做的事是什么呢？就是我刚才描述的这个托孤动作：比如说 4 被删了，那 4 的孩子将来就托付给 4 的父亲，也就是让这个 7 成为 3 的孩子。

那这个整个动作里需要几个参数呢？你看刚才都有谁参与进来的。首先这个被删除节点的父亲参与进来了，所以第一个参数是父亲；第二个参数就是这个被删除节点；第三个参数呢就是被删除节点的孩子。所以到了我们这个方法，应该有三个参数。

```java
/**
 * 托孤：把 child 顶上去，占据 deleted 原来的位置
 *
 * @param parent  被删除节点的父亲
 * @param deleted 被删除节点
 * @param child   被顶上去的节点
 *                （注意：它可能是被删除节点的孩子，
 *                  也可能是孙子、重孙子，所以用更通用的说法）
 */
private void shift(Node parent, Node deleted, Node child) {
    // 特殊情况：parent == null，说明被删除节点就是根节点，它没有父亲
    // 那 child 将来就成为新的根节点
    if (parent == null) {
        root = child;
    } else if (parent.left == deleted) {
        // 被删除节点原本是父亲的左孩子，child 也作为左孩子顶上去
        parent.left = child;
    } else {
        // 被删除节点是父亲的右孩子，child 也作为右孩子顶上去
        parent.right = child;
    }
}
```

先看这个特殊情况：有可能这个父亲是 null，什么情况下呢？比如说我被删除节点它就是根节点。那大家想这时候有没有父亲？没有吧，因为它已经是根节点了，它就没有父亲，符合 `parent == null` 这种情况。那这种情况下，你说我接下来这个孩子 2 托付给谁？他没有父亲的情况下，2 将来是不是就成为根节点就可以了？所以如果将来 `parent` 等于 null 的情况下，那我们就让将来的 `child` 成为新的根节点。

回到 `parent` 不等于 null 的情况。最开始我还是删除 4，这回 4 有父亲，也就是 `parent` 不等于 null。我们看看这块该怎么做呢？

从结果可以看出来，将来呢我就是要把孩子 7 作为这个父亲 3 的右孩子，对吧？刚才的孩子 7 作为这个父亲 3 的右孩子。那问题来了——我怎么知道这个 7，他将来是这个 `parent` 的左孩子呢，还是右孩子呢？

注意这里被删除节点 4，他是父亲的右孩子，那将来这个 7 呢他也作为这个父亲的右孩子。你就不能把 7 作为这个 3 的左孩子了——你把 7 放到左边，是不是就不符合二叉搜索树的定义了？二叉搜索树要求所有左孩子都要比当前节点小，右孩子要比当前节点大嘛，所以 7 肯定得放在右边。

那怎么判断它要放在右边呢？就看看你被删除节点是右孩子，那我就放右边；被删除节点是左孩子，我就放左边。我再给大家看一个这个左孩子的例子：现在我的被删除节点是不是他父节点的左孩子啊？那将来这个 2 他托付上去之后，是不是也应该是左孩子呀？

所以这个代码呢我们就知道怎么写了。如果我们的 `deleted` 是父亲的左孩子，那我的 `child` 是不是也将来作为父亲的左孩子啊？看懂了吧。当然还有一种情况就是被删除节点是父亲的右孩子了，这已经是最后一种情况了，所以这个 `else if` 里的条件可以省略，我直接写成 `else`。

> **结论**：托孤必须挂在同一侧——被删除节点原本是左孩子，接上去的也只能是左孩子，否则二叉搜索树的定义当场就被破坏了。

### 情况一、情况二的代码与测试

好，那刚才的托孤方法它的注释我补上了。特别注意第三个参数 `child`，我把它注释稍微改了一下，我就不叫它"被删除节点的孩子"了。因为后面我们会看到，也许这个第三个参数啊，它代表的是被删除节点的什么孙子、重孙子呀，也有可能。所以我给它一个更通用的说法，它代表的是那个**被顶上去的节点**。

那么刚才的情况一、情况二的代码就易如反掌了。

```java
    if (p.left == null) {
        // 情况一：删除节点没有左孩子，把右孩子托孤顶上去
        // 第一个参数 parent 代表被删除节点的父节点
        // 第二个参数是被删除节点，就是我们这里的 p

        // 情况二：没有右孩子，但是有左孩子，把左孩子顶上去

    }
```

写完之后呢，我们可以做一个简单的测试啊。我这写了一个针对它的测试用例。我这儿的树长这样，现在呢我要删除其中的 7，就把 7 这个节点删掉了。

大家看它符不符合我们刚才情况一、情况二中的哪一个？符合情况二吧——它是有左孩子、没有右孩子啊，也就是会走到这个 `else if`。它做的操作是什么呢？就把 7 删掉了，但是会把它的左孩子顶上去，把这个 6 顶上去。

顶上去以后，这个 6 作为 parent 4 的左还是右呢？我们刚才看到了，被删除的是右孩子它就作为右孩子顶上去，被删除的是左孩子它就作为左孩子顶上去。那你看我们这个例子中 7 是不是他是右孩子啊？所以将来这个 6 也就是作为右孩子顶上去。最终的效果呢就应该是这个样子。

这个测试用例啊，我们就不带大家再细看了。反正我去验证它，删除之后这棵树如果长这个样子，是不是就代表正确了？去确认一下，删除之后这棵树跟我图上画的这个是一样的，表示我的测试通过。跑一下——可以看到已经测试通过了。

这是其实测试的是情况二啊，那至于情况一呢，跟它比较类似，这里我就没有给出相应的测试代码了。

### 叶子节点：情况一和情况二已经覆盖

接下来呢我们再来看情况三。情况三呢是说删除节点的左右孩子都没有，就比如说我这张图上画的，我要删除 4，它的左右孩子都没有。那这个时候它其实就属于那种叫叶子节点对吧。

```text
      4              <- 待删除：左右孩子都没有，是叶子节点
     / \
    2   3
```

那如果是这种叶子节点，你走情况一的逻辑，或者是走情况二的逻辑，都能得到正确的结果。

举个例子。比如说我现在让他走情况一的逻辑，也就是让这个情况一的代码处理一下——没有左孩子是不是？那就叫右孩子，他的右孩子是谁啊？是 null。把这个 null 托孤给 parent，也就是让 `parent.right` 等于 null，是不是就相当于还是把它删除了？所以呢我们发现，他走第一种情况的处理逻辑，得到的结果是没有错误的。

当然了，我如果让他走第二个处理逻辑：右孩子是 null，左孩子也是 null，走第二个分支的逻辑能不能得到正确结果呢？也是可以的。你看情况二是说没有右孩子，是不是符合条件啊？没有右孩子，那就把他左孩子托孤给 parent，他左孩子也是 null，托孤给 parent，是不是就是让 `parent.right` 等于 null，得到的结果是一样的。

> **结论**：情况三我们不用写额外的代码了。将来他不管是走这里的 `if` 还是走这里的 `else if`，都能得到正确的结果。所以真正写代码，我们只要考虑 1、2、4 就够了。

那情况四呢，我们就把它写在 `else` 里，然后把前面的条件变一下——你看这里的这个"不等于"的判断，还有这里的不等于判断都去掉了。这是什么？这是左孩子没有的情况，这是没有右孩子的情况。那能执行到 `else` 表示什么啊？左右孩子是不是都有了？这就是我们的情况四。

### 两个孩子都有：让后继顶上去

那下面呢我们就来分析一下情况四。情况四呢是说被删除的这个节点，它既有左孩子又有右孩子。

那你看我们之前的那个策略是不是就用不上了？之前是被删除节点只有一个唯一的孩子，那没得选呀，咱就把他唯一的孩子顶上去代替掉，原来被删除节点的位置。现在有两个孩子了，既有 2 也有 5，那选谁呀？

我们先来选择这个被删除节点的**后继节点**，或者叫后任节点。你看 4 的后继是不是 5 啊？先找到它的后继，然后让这个后继顶上去。后继顶上去了，那它就作为它另外一个孩子的爹。你看 5 作为 2 的爹了，那 2 也没啥说的啊，它只能老老实实待在原位不动。

用这种方式呢，我们来实现被删除节点有两个孩子的一个顶替策略：我们是选择他的后继，让他顶上去。

不过呢，我们选择后继的时候，又可以细分成两种情况。一种情况就是大家看到的，我这个被删除节点恰好跟他的后继是相邻的——被删除节点正好是爹，这个后继呢正好是被删除节点的儿子。那这种其实比较简单，我们只要让他直接顶上去就可以了。

```text
相邻：后继恰好就是被删除节点的右孩子

          4
         / \
        2   5        <- 后继节点 = 5，正好在 4 的右边
           \
            6
```

但是还有一种情况，你看我还是要删除那个 4，这是被删除节点嘛。那他的后继是几啊？从这我们可以看出来后继是这里的 5。那大家想，这种情况下我如果把这个后继直接顶上去行不行？你就想 5 取代掉这里的 4，2 跟 8 都成为了 5 的孩子。

但是问题来了——那我原来这个孩子 6 呢？

所以这种不相邻的，我们还得对它再做多一步的处理操作，就是你得先把 5 的后事处理干净了，然后它才能去替代掉刚才被删除的节点。

```text
不相邻：后继藏在右子树更深处

          4
         / \
        2   8        <- 后继不是 8，是 8 的左子树里最左的 5
           / \
          7   9
         /
        5              <- 后继节点 = 5，它的父亲是 7
         \
          6
```

5 的后事怎么处理干净呢？你得把 5 的这个后代 6 交给谁啊？交给 5 的父亲 7。把 5 的后代 6 先交给 7，这样 5 它就没有后顾之忧了，它再取代掉刚才被删除节点的位置。

这是我们两种细分的情况啊：一种就是后继跟被删除节点它俩是相邻的，这时候我们直接顶上去就可以了；还有一种呢就是我们的后继跟这个被删除节点不相邻，这时候我们得把后继先做一个处理啊，把他的后代先处理好了，然后后继再顶替掉刚才的被删除节点。

这是我们第四种情况的一个分析，整个这个过程呢还是比较复杂的。大家可以先用动画看清楚他的这个操作流程，然后呢我们待会儿再来去写它的代码。

### 找后继、判断相邻、清理后事

好，我把刚才的讨论又分成了三个小的步骤。第一个小步骤，是不是我们应该找到被删除节点的后继节点。找到了它以后呢，如果这个后继节点跟我们被删除节点他俩邻着，那就不用做什么事；如果他俩不相邻，那是不是我们得先让后继节点把它的后事处理干净，然后呢再走下面步。所以我们第二步就是要判断一下是不是要处理后继节点的后事。这件事做完了，第三个小步骤呢，就是我们用后继节点取代掉被删除节点，是不是就行了。

#### 找到后继节点：右子树里的最小值

那这个怎么找呢？其实怎么找后继，我们前面都总结过啊。如果这个节点有右子树，那后继节点是不是就是右子树中的最小值啊？这是有右子树的情况。那如果没有右子树，那就要到祖先里找，自左向右的那个祖先就是后继节点。

那我们现在需不需要到祖先里找啊？不需要吧。因为我们如果能进入情况四，那就证明我这个被删除节点是不是既有左子树又有右子树，所以他只需要到右子树里找那个最小值就行了，根本不存在找祖先的情况。所以我们之前虽然写过这个找后继代码，但是并不是所有的代码都能用上，我们只要用上一部分就可以了。

```java
    // 找后继节点：p 的右子树里的最小值
    Node s = p.right;
    Node sParent = p;          // s 的父亲，初始值就是被删除节点 p
    while (s.left != null) {
        sParent = s;
        s = s.left;
    }
    // 循环结束，s 就是我们的后继节点，sParent 是它的父亲
```

那这个找最小值好写吧？我们先定一个节点变量，它代表我们的后继 `s`。那这个后继刚开始的起点应该是它的右子树的起点，也就是我们被删除节点的 `right`。然后开始循环，如果当它的 `left` 不为空的时候——就是它还没有向左走到头，那怎么办呢？`s` 就等于 `s.left`，就不断向左走，直到它的 `left` 属性等于空了，表示走到头了。

比如说我们这个例子中，我起点是 5 对吧，那它向左走能走吗？走不了了啊，它的 `left` 已经是 null 了，所以 5 就是已经表示他向左走到头了，这 5 就是它的后继。那如果是刚才那个不相邻的例子也是差不多，它的右子树起点是 8 对吧，但是 8 呢不是他最左边的这个节点，所以它要向左走。

```text
从 4 的右孩子出发，只要 left 不为空就一直向左走：

        8  --left-->  7  --left-->  5  --left-->  null

   s = 8, sParent = 4
   s = 7, sParent = 8
   s = 5, sParent = 7      <- 5 的 left 已经为空，走到底了
```

5 的左边是 none 了，5 的右边是这个 6 嘛。所以这里的 5 是不是就是我们的后继节点啊？等这个循环结束，那 `s` 就是我们的后继节点。第一个小步骤就写完了。

#### 判断相邻：看后继的父亲

那我们待会儿怎么去判断它俩相不相邻呢？好其实大家来看啊，那我们在查找这个后继节点的过程中，我就问后继节点，也就是这里的这个 `s`，一开始他的父亲是谁啊？一开始他的父亲是不是就是我们这边这个被删除节点啊？因为它是从右子树开始查找嘛。

等这个循环结束，也就是 `s` 查找到了，如果这个后继节点他的父亲仍然是刚才的删除节点，说明什么？说明他俩相邻。

那如果是这种情况，你看一开始我们也是从这个被删除节点的右子树开始去查找这个右子树的最小值嘛，一开始他这个 `s` 是我们这个例子中的 8，没问题吧？那 8 的父亲是不是就是 4 啊？

但是随着我们查找的不断进行，那么等找到这个后继节点的时候，我就问后继节点的父亲是不是就变了啊？变成谁了？变成这个 7 了。那 7 还是他一开始查找时的那个 4 吗？不是了啊。

所以等我们后继节点找到的时候，我们如果对比一下，他的父亲不再是刚才的删除节点了，那说明他俩已经不相邻了。没问题吧？

```java
    // sParent != p，说明后继跟被删除节点不相邻
    if (sParent != p) {
        // 不相邻：先把后继的后事处理干净
        // 把后继从它原来的位置摘掉，让它的右孩子顶上去
        shift(sParent, s, s.right);
    }
```

找父亲这个活儿我们刚才做过一遍了，做过好几遍了啊。我们也是定义一个变量叫 `sParent`，它代表着我们这个后继节点的父亲。它的初始值是谁啊？我们从被删除节点的右子树开始找，那他的父亲一开始是不是就是我们的被删除节点？

每次循环的时候，我们是不是要更新这个父亲的值啊？每次循环我们就把 `sParent` 更新成 `s`。你看一开始他是 8 嘛，他的父亲也是 4；那下次再找的时候，那 `s` 变成了 7，那这个父亲变成了 8；最后找到 5 的时候，`s` 变成了 5，父亲呢是不是变成了 7 啊。

#### 后继不可能有左孩子

接下来呢我们来看一下怎么去处理后继节点的后事。其实是不是就是我们之前写的托孤方法呀？大家这时候你把刚才的后继节点理解为要删除的节点啊，总之它在它原来的位置是不是要被删掉，删掉以后呢，他就会把他的孩子 6 顶上去，顶上去给这个后继节点的父亲 7。所以呢我们调用刚才的托孤方法就行了，不用重写代码，直接调用。

那这个 `shift` 的第一个参数应该传给谁啊？第一个参数是不是后继节点的父亲啊？其实已经找到了，就是这个 `sParent`。将来要托孤给这个 `parent`。但是被删除的是谁呢？被删除的是 `s` 后继节点。那托孤上去的是谁啊？

那这里有同学可能问了——那你这个图是不是没涵盖所有的情况呢？能不能说把这个后继节点它的左孩子将来顶上去了？

> **提示**：注意不可能。为什么呢？你想啊，我们找后继是怎么找的，我是不是找 4 这个被删除节点右子树里的最小值啊？它是右子树里的最小值，那如果 5 它还有左孩子的话，它算最小的吗？它的左孩子肯定比它更小啊。

所以大家注意，如果我们的代码能执行到这儿，那这个后继节点他肯定只有右孩子，不可能有左孩子，这点大家要注意啊。那你就放心大胆把他的右孩子传上去就可以了。

### 顶替之后，后继的指针还得改

好，终于到了我们的最后一步。最后一步呢，我们只要把刚才找到的这个这个后继节点顶上去代替掉这个被删除节点，整个这个删除动作是不是就完成了。

```java
    // 步骤三：后继顶替掉被删除节点
    shift(parent, p, s);

    // 然后把后继节点自己的左右指针接好
    s.left = p.left;
    s.right = p.right;
```

那这个顶上去的方法是不是还是调用托孤方法呀？还是调用这个 `shift` 啊。这回的 `parent` 是谁啊？这回的 `parent` 是我们删除节点的父节点，也就是我们的 `parent`。被删掉的是谁呢？被删掉的是我们的那个 `p`。那第三个参数顶上去的是谁呢？顶上去的是我们的这个后继节点 `s`。

不过这里大家要注意一点啊，你看我们刚才托孤方法里面，我们只是改变了 `parent` 它的两个指针啊，要么改它的 `left`，要么改它的 `right`。那你看我们顶上去的这个后继节点，它的左右指针是不是要变啊？

看我们现在是要变的。它的左指针是不是应该指向原来删除节点 4 的左孩子？它到我们这个 5 的左指针原来没有，但是现在它顶上去了，它的左指针是不是就应该指向删除节点的左孩子啊？

```java
    s.left = p.left;
```

那这个例子中需不需要改它的这个右指针啊？5 的右指针不用动，因为它连着就带上来了，对不对？哎，不用动。

但是什么时候要动那个右指针呢？我们看刚才这种情况，不相邻的情况——你看 5 的孩子是不是托孤给 7 了？脱孤给 7 了。那 5 将来要顶替掉被删除节点，那这时候它的左孩子也要动，右孩子也要动啊。

你看原来 5 在之前啊，左孩子是 none，右孩子是 6 对吧。那他顶上去以后，左孩子要变成被删除节点的左孩子，那右孩子呢？右孩子要变成被删除节点的右孩子啊。左孩子在这儿已经变过了，右孩子的我们在这里变，就是顶上去的这个后继节点，它的右孩子应该等于我们的删除节点的右孩子。

```text
不相邻时的完整流程

  找后继：8 --left--> 7 --left--> 5，得到 s = 5, sParent = 7

  清理后事：shift(7, 5, 6)

          4                  4
         / \                / \
        2   8              2   8
           / \                / \
          7   9              7   9
         /                  /
        5                  6        <- 6 顶上 5 的位置

  顶替：shift(parent, 4, 5)，再接指针 s.left = 2、s.right = 8

          4                  5        <- 后继 5 顶替了 4
         / \                / \
        2   8              2   8
           / \                / \
          7   9              7   9
         /                  /
        5                  6
         \
          6
```

好，代码写到这呢就已经全部完成了。好那关于这个情况四，代码我们就写完了。那这个代码呢其实我们讲的时间长，但是代码量并不大啊，大家下去消化一下，相信都能掌握。而且这是非递归的代码，性能会好一些。

### 为什么必须是后继，不能拿六顶上去

那最后呢，请大家去思考一个问题。就是你看我们在删除这个有左右孩子的节点的时候，我们是说啊，关键点呢在于把这个被删除节点的后继节点让它顶上去对吧，替换掉我们被删除节点。也就是用这里的后继节点 5，替换掉刚才的被删除节点 4。

那这里为什么要替换一个后继节点呢？能不能是其他节点？比如说我让你把这个 6 顶上去替换掉这里的 4，行不行？

不行啊，注意 6 不行。为啥 6 替换上去之后，它就破坏了二叉搜索树的特性了？你看咱们的二叉搜索树是不是要求节点左边的值都要小，节点右边的值都要更大对吧？你把 6 替换上去以后，你就想 6 的右边现在是谁？是不是 5、7、8、9 啊。7、8、9 当然比 6 大还可以，但是 5 呢是不是比 6 小了？它不应该出现在 6 的右边。所以你把 6 放上去，它就会破坏二叉搜索树的特性，不行啊。

因此呢，大家现在要理解为什么要把后继节点替换上去了吧——后继节点替换上去不会破坏它的二叉搜索树特性。

当然能不能把这个被删除节点左子树里边找一个**前任**节点替换掉被删除节点？这是可以的。当然你要替换前任，我们刚才的代码就得再做相应的调整啊，代码量是一样的，但是一些左右指针执行的、找最大值还是最小值这些就要调整了。好，这个就是题外话了，我们这里就不实现了。

好关于我们整个这个二叉搜索树的删除操作，就给大家讲到这里。

### 递归版：返回值就是剩下的孩子

好那我想了下，我们还是提供一个递归版的实现吧。这样两个版本大家结合着来学习，有助于扩展思路。

那递归版的我们需要两个方法：一个方法呢就是提供给外界调用的 `delete` 这个方法；第二个呢是自己内部使用的，专门用来递归的。因为它的递归时的参数跟我们外界这个方法不一样啊，所以单独设计了这么一个递归方法。

那递归方法，我们来解释一下它的第一个参数啊，就是我要删除时从哪个节点开始删啊，它代表删除时的那个起点。比如说一开始是不是 4 传给他呀，随着递归的不断进行呢，比如说这个节点的值会不断变化，下次可能传给他的就是 6 了，我要从 6 开始去查找删除。能理解吧？这是一个代表的是起点啊。起点 `node` 代表递归删除它的一个起点。那个 `key` 呢就不用说了吧？他就是那个关键词。

那这个递归方法它得有一个返回值。那有同学说为什么得有个返回值呢？你看啊，其实递归删除它的关键点在于要把被删除的这个节点从整棵树中给它断开。那怎么断开呢？

比如说我要找的是 6 啊，我要删除 6 啊，那第一步我们也是递归先找到它对吧？那找到它以后，我怎么把它删掉呢？其实很简单，就是我把 6 他的孩子——比如说他只有一个孩子的情况——我就把这个 7 返回，可以吧？递归的过程中返回，返回的时候让 6 的父亲，他的 `right` 指向返回的这个新的 7，是不是就相当于把 6 给从中间断开了？能理解吧？

> **定义**：`delete` 的返回值就是**删除后剩下的那些孩子节点**。找到了，它返回的是删剩下的孩子；没找到，它返回 `null`。

```java
// 对外暴露的删除入口
public Node delete(int key) {
    return delete(root, key);        // 起点就是根节点
}

// 内部递归方法：node 是本次递归的删除起点
private Node delete(Node node, int key) {
    // 传过来的 node 已经是 null，还需不需要继续定位？
    // 不需要了——是 null 就表示找到头了，没找到
    if (node == null) {
        return null;                 // 既然都没找到，那剩下的也是 null
    }

    if (key < node.value) {
        // key 小于当前节点，向左找，还是递归调用 delete
        // 只不过这回的起点变成谁？变成当前节点的 left
        node.left = delete(node.left, key);
    } else if (key > node.value) {
        // key 大于当前节点，向右找，做的事是类似的
        node.right = delete(node.right, key);
    }

    return node;
}
```

那写到这儿呢，我们来思考一下，这个 `delete` 它的返回值该怎么处理？它的返回值啊，我们说过，就是表示删剩下的孩子。假设我就是要找到 2，把 2 删掉，那假设 2 已经被删掉了，它应该返回的是谁？返回的是不是他的孩子 1 啊？

那返回的这个 1 我们拿它该怎么办啊？是不是我们要重新建立 1 跟父亲 4 之间的父子关系？就是把当前节点 4 啊，`node` 代表当前节点，当前节点的左孩子要更新了啊，因为原来他的左孩子已经被删掉了嘛。要更新成什么呢？更新成删除后剩下的孩子啊，也就是 `node.left` 等于 `delete` 的返回值。这个看懂了吧。

那 `key` 大于 `node` 的值呢，就是我们的待删除的节点更大，那就向右找，做的事是类似的，也是把这个代码复制了一下，然后就改成 `right`。啥意思呢？就是我继续向右查找进行这个删除。那如果成功了呢？比如说他删的是 6，那我就把删剩下的 7 返回可以吧？返回了这个剩下的以后，我是不是要重新建立当前节点，也就是 4 的右孩子跟返回结果的父子关系。

至此为止呢，我们已经分析了如果没有找到，那么就进行递归操作。那接下来我们再来看一下，找到了怎么进行删除啊？删除其实就是我们列举的四种情况，跟之前非递归版的情况是一样的啊。那么我们代码如果执行到这儿呢，就表示他已经找到了对吧。

### 递归删除：还是那四种情况

那找到了我们分成这么几种情况。第一种就是他没有左孩子、只有右孩子这种情况。那这种情况我们前面已经说过，它只要把唯一的这个右孩子将来赋值给 parent 父节点是不是就行了？当然我们现在呢只需要把这个右孩子返回就行啊，因为我们只要返回删剩下的这个右孩子就可以了。

那至于建立它的父子关系呢，是不是在上一次递归的时候就帮我们建立了？上一次递归调用的时候，它就可以建立这个 `parent` 跟删剩下的孩子之间的父子关系。

```java
    if (node == null) {
        return null;
    }

    if (key < node.value) {
        node.left = delete(node.left, key);
    } else if (key > node.value) {
        node.right = delete(node.right, key);
    } else {
        // 找到了，按四种情况处理
        if (node.left == null) {
            // 情况一：只有右孩子，把右孩子返回上去
            return node.right;
        } else if (node.right == null) {
            // 情况二：只有左孩子，把左孩子返回上去
            return node.left;
        } else {
            // 情况四：左右孩子都有，找右子树里的最小值作为后继
            Node s = node.right;
            while (s.left != null) {
                s = s.left;
            }
            // 后继顶上来，它的左孩子要接住被删除节点的左子树
            s.left = node.left;
            return s;
        }
    }

    return node;
```

好，代码能走到这，说明他已经进入了第三种情况——被删除节点有两个孩子。那在这种情况下，我们前面其实讲过，是不是要找这个后继节点呀？找后继节点，然后把后继节点顶上去。顶上去以后是不是在建立后继节点跟原来被删除节点父亲之间的父子关系。

那其实对于我们现在这个递归版的例子里，那我是不是只要把后继节点返回就行了啊？因为后继节点在我们这个例子中，就相当于是删剩下的。对不对？

好，所以这个代码呢就变成了我要去查找我们的先查找到后继节点啊。当前节点的右子树开始查，也就是当前节点的右子树是起点，在右子树里要找一个最小的，也就是看它的 `left`，如果它不等于 null 就继续向左走，向左走到头就是右子树中最小的，`s` 等于 `s.left`。好等循环结束，那这个 `s` 就是我们的后继节点。

那大家看啊，后继节点将来顶上去的时候，对于我们现在这种情况，它的左孩子是不是要变一下？你看它的左孩子原来是 none 啊，那是顶上去了，它的左孩子应该变成被删除节点的左孩子啊。所以呢 `s.left` 应该等于被删除节点 `node` 的左孩子。

最后呢我们返回 `s`。`s` 就是我们这种情况下删剩下的啊，删剩下的跟上次递归的就是我们这次 `delete` 删剩下的，就跟上次递归时父节点的 `left` 和 `right` 去建立这种父子关系，是不是就可以了啊。

### 本讲提到的题目

**题目**：我们在删除左右孩子都有的节点时（比如删除 4），要靠"把后继节点 5 顶上去替换掉 4"来完成删除。能不能换成别的节点——比如让 6 顶上去替换掉 4？

**答案**：不行，6 替换上去之后会破坏二叉搜索树的特性。

**解析**：二叉搜索树要求节点左边的值都要小、右边的值都要更大。6 替换上去之后，它的右边现在是谁？是 5、7、8、9。7、8、9 当然比 6 大还可以，但是 5 是不是比 6 小了？它不应该出现在 6 的右边。所以你把 6 放上去，它就破坏了二叉搜索树的特性。

**延伸**：能不能换成左子树里的**前任**来替换？是可以的。但要替换前任，我们刚才的代码就得再做相应的调整——代码量是一样的，不过找最大值还是找最小值、左右指针执行的这些就得改一改。这里就不实现了。

## 二叉搜索树：递归删除的最后一厘米、范围查询与三道力扣题
> 对应块：BLK45 | 覆盖分集：P173-P175 | 块标题（分集名）：《基础算法-128-二叉搜索树-删除-递归-2》

### 上一段代码漏掉的那一类情况

刚才那段递归删除的代码，其实只考虑到了**被删除节点跟后继节点相连**的情况。可我们之前做非递归实现的时候是不是还说过，还有一种情况——**他俩不相邻**？

就拿这张图来说：

```text
              4  ← 待删除节点
            /   \
           2     8
          /     / \
         1     7   9
              /
             5  ← 后继节点
              \
               6
```

四是被删除节点，五是后继节点，它俩现在**不相邻**。不相邻，我们刚才那段代码会不会有问题？

肯定是有问题的。你看不相邻的时候，找到后继五了，把它的 `left` 改成被删除节点的 `left`，也就是让五的左孩子变成二——没问题吧？但五还有人家原来有个右孩子六啊。这时候我如果直接把五返回，最终是不是就只剩下 5、2、6 这几个节点了？四这边原来的右孩子 8、7、9 这几个节点是不是就没了？

所以我们这段代码不行，我们得把这种**不相邻**的情况考虑上。

> **结论**：不相邻的时候，我们要先把后继节点的后事先处理干净了，然后再把后继顶上去。这个顺序是死的。

#### 不相邻怎么办：在右子树里再递归一次

那在递归版里怎么做呢？大家来观察一下四的右子树——被删除节点四的右子树在这棵子树里，如果我把八当成是这个起点，在八的这棵子树里删这个五，删掉五得到的结果是什么？就是**把五的后继顶上来**。这样五的后事就被处理干净了，那我们就能处理这种不相邻的情况。

所以我们应该再做一件什么事儿？再做一个递归。这个递归以八作为起点。我们注意啊，递归时的第一个参数就是起点——这个起点是谁呢？就是当前被删除节点的右子树 `node.right`。

那在八为起点的这棵子树里，要找到谁来删除呢？要找到五来删除。注意这个 `k` 啊，就是我们后继节点的 `k`。删完五之后，**删剩下的**是谁呢？大家想，在这棵子树里，删剩下的最终返回的，应该就是八——以八为起点的这棵子树的根。

那返回的这个八，将来要作为谁的孩子呢？要作为我们刚才这个后继节点的右子树。所以它应该是 `s.right = 删剩下的`。

这样一步看懂了，我们整个这个方法也就实现完成了。变化过程是这么走的：

```text
   初始                错误做法：直接返回 s        正确做法：先在 8 子树里删 5

        4                       5                           5
      /   \                   /   \                       /   \
     2     8                 2     6                     2     8
    /     / \                     ← 8、7、9 没了            / \
   1     7   9                                              7   9
        /                                                      /
       5                                                     6
        \
         6
```

读图：左边是原树，五挂在七底下，所以四和五根本不是父子，属"不相邻"。中间是只做了 `s.left = node.left` 就把五返回的结果——五的右孩子六被保住了，可八、7、9 整条链全丢了。右边是先把五从八子树里"摘干净"（五的后继六顶上七的左孩子），再让五接管四的位置。

#### 先删后接：这两行的顺序反了会把删除搅乱

刚才我的代码里有一处错误，就是这两行代码的顺序颠倒了。

上面这行的意思是要给后继节点五的左孩子赋一个值，赋的是被删除节点的左孩子（二）；下面这行是到被删除节点的右子树里找到后继节点，把它删掉。

但你想啊——如果我**先**给五的左孩子赋值成二，那等八去删五的时候，相当于五**又有两个孩子**了，这种情况就干扰了我们这个删除的动作。

所以我们应该怎么做？**先删**。现在这个后继节点只有一个孩子的情况下，先把它删掉；删掉之后，再把我们后继节点的左孩子变成二。这样才对。

> **易错点**：这两行只有一种合法顺序——先 `delete` 再赋 `left`。反过来写，等于在待删节点上凭空挂出一个新孩子，删除逻辑立刻失真。

#### 顶层还得再接一次：root 必须重新赋值

下面我们把这个递归方法跟上面这个对外暴露的 `public` 方法做个结合。调用这个递归 `delete`，起点是不是应该从根节点开始？k 是我们参数传过来的 k。

注意，调完这个递归方法以后**还要做一个赋值的动作**，就是把 `delete` 方法返回的结果，再重新给根节点赋个值。

为什么要做这一步呢？大家想，拿我们刚才这个例子来讲，我删除的四就是根节点啊。删除完了之后它把后继节点顶上来了，那我问，它返回的是不是就是我们的后继节点？那后继节点是不是得重新给根节点赋一个值啊？

就是在**删除根节点**的情况下，你必须把"删剩下的"这个结果重新给 `root` 这个变量做一次赋值的操作，否则这个根就不正确了。所以这一步大家别忘了。

#### 一个返回值不能代表两种含义

最后我们再来看一下它的返回值。它的返回值要求返回的是**被删除节点的 value 值**。而我们刚才那个递归方法，返回值是**删剩下的**。

一个是要找被删除节点，一个是要找删剩下的，这个返回值是不是两种含义？你不能用一个返回值代表两种含义啊。所以我们待会儿得给他再多加一个参数，这个参数用来保存被删除节点的值。

怎么做呢？也简单——我们创建一个 `ArrayList`，因为值的类型是 `Object`，所以这个 `ArrayList` 的泛型也是 `Object`。这个 `result` 的作用是什么？就是用来保存我们被删除节点的值。我们把它当成参数传给递归方法，将来递归方法里遇到了被删除节点，你就把它那个 `value` 添加到这个集合里。

有了 `result`，执行到"找到了"那一步的时候，就相当于找到了——因为能执行到这儿，说明当前的 `node` 就是被删除节点了嘛——那我们就把这个当前节点的 value 值给它加进去。

所以被删除节点它的值，**并不是通过 return 返回的，而是通过这样一个方法参数来存储它的结果**。当然了，我们这里改了以后，递归的时候要把这个 `result` 都传进去，这里也要传进去，保证整个过程中用的是同一个集合。

不过要注意啊，你看我们去删那个后继节点的时候，是不是也需要一个集合？但这个集合能不能用刚才这个集合？**不能用了**。我们删除后继节点，它的值并不是我们要找的被删除的那个返回值，所以你就创建一个新的 `ArrayList` 就完了，反正咱们用不上。

最终等递归方法执行完成之后，`result` 里就存储了我们被删除节点的 value。当然如果是没找到，它里面存的就是空的——这个集合是空的。所以我们判断一下，如果 `result.isEmpty()` 就表示没有找到，没有找到的情况我们返回 `null`；如果找到了，这个 `result` 里肯定只有一个结果，那么就返回零位置的这个结果就可以了。

```java
// 对外暴露的方法：起点是根，返回被删除节点的 value
public V delete(K k) {
    ArrayList<Object> result = new ArrayList<Object>();
    this.root = delete(this.root, k, result);
    if (result.isEmpty()) {
        return null;                       // 没找到
    }
    return (V) result.get(0);              // 找到了，只有一个
}

// 递归方法：返回的是"删剩下的"，起点 + k + 回传被删值的容器
private BSTNode<K, V> delete(BSTNode<K, V> node, K k, ArrayList<Object> result) {
    if (node == null) {
        return null;
    }
    if (k.compareTo(node.key) < 0) {
        node.left = delete(node.left, k, result);
    } else if (k.compareTo(node.key) > 0) {
        node.right = delete(node.right, k, result);
    } else {
        // 找到了，把被删除节点的 value 记进 result
        result.add(node.value);

        // 情况一：没有左孩子，右孩子直接顶上去
        if (node.left == null) {
            return node.right;
        }
        // 情况二：没有右孩子，左孩子直接顶上去
        if (node.right == null) {
            return node.left;
        }

        // 情况三：左右孩子都在，找后继顶上去
        BSTNode<K, V> s = node.right;                 // 起点 = 当前节点的右子树
        while (s.left != null) {
            s = s.left;                                // 顺着左链找到后继
        }
        // 先删：把后继的后事处理干净，这里用的是全新的集合，用不上就丢
        BSTNode<K, V> rest = delete(node.right, s.key, new ArrayList<Object>());
        // 再接：顺序反了就会给待删节点造出一个新孩子
        s.left = node.left;
        s.right = rest;                                // rest 就是那棵以八为根的子树
        return s;
    }
    return node;
}
```

> **提示**：`delete` 的三个参数各司其职——第一个是遍历起点（所以内层递归才能传 `node.right`），第二个是这一层要找的 key（所以内层传的是 `s.key`），第三个是**唯一**用来往外送被删值的通道。返回值和结果容器，一件事只干一样。

### 范围查询：给中序遍历加个条件

接下来我们再来看这么几个需求，这几个需求就是来做**范围查询**的。

#### 三个需求先摆明白

- `less`：给定一个 `k`，找到所有比 `k` 小的这些节点的值，多个节点值装在一个集合里返回；
- `greater`：给一个 `k`，将来找所有比这个 `k` 大的节点的值，放在一个集合里反馈；
- `between`：给两个 `k`，找的是大于等于 `k1` 并且小于等于 `k2` 的所有节点的值。

这是我们这些范围查询的方法。当然了，大家下去可以自己再扩展一下，比如说你有"小于"，那肯定还有一个"小于等于"吧；有"大于"，你再加一个"大于等于"啊，那个就留给大家去扩展了。

| 方法 | 传参 | 收集哪些节点 | 能否提前结束 |
| --- | --- | --- | --- |
| `less` | `k` | 值 `< k` 的所有节点 | 能，遇到第一个不小于 `k` 的就停 |
| `greater` | `k` | 值 `> k` 的所有节点 | 中序不能，改反向中序才能 |
| `between` | `k1`、`k2` | `k1 ≤ 值 ≤ k2` 的所有节点 | 能，遇到第一个 `> k2` 的就停 |

> **易错点**：`between` 是**含边界**的。找 3 到 5 之间，3、4、5 三个都要，1、2 不要，6、7 不要——期望值是 `[3, 4, 5]`，不是 `[4]`。

#### 思路：中序遍历里加个条件就行

那思路是怎样的呢？其实我们前面说过一个规律：对二叉搜索树来讲，中序遍历是不是就能得到它的一个**升序**的结果呀。我们在中序遍历的过程中加入一些条件——比你小的，我给它加进来；比你大的，我给它加进来。这是核心的思想。

就是在中序遍历的过程中，我自然能判断出来这些个大于小于、或者是大于等于小于等于这些条件，然后有选择地把这些节点值加到我们的结果集合中。

实现上我们用迭代来做。先把代码的架子搭出来：

- 先定一个指针，指针叫个 `p`，起点就从根节点开始；
- 然后我们要向左一直先走到头，对不对？那走的过程中需要记录经过的每个节点，所以需要一个栈。我们用 `LinkedList` 作为这个栈；
- 接下来就开始循环。循环条件呢？就是当 `p` 不等于 `null`，**或者**这个栈不为空，那我们就得表示这个遍历还没有结束，就继续遍历；
- `p` 不等于 `null` 是说我还没向左走到头呢，那就继续前进；当 `p` 等于 `null` 了，就表示它走到头了，该向回走了。向回走的过程中这个栈是不会空的。所以我们一个是向前进，一个是向回走，这两个条件只要有其中之一满足，就表示还没有走完。

先来看向前进的情况：当 `p` 不是 `null` 时，我们就要继续向左走，那怎么走呢？就是 `p = p.left`。当然我们向左前进之前，需要把这个节点先记录起来，记录到栈里，所以我们用 `stack.push` 压一下就可以了。这是先向左走到头。

那走到头以后这个 `p` 它就等于 `null` 了，接下来我们就该向回走了。其实向回走呢，对于前序和中序来讲，就是把刚才栈中记录的变量给它先弹出来，对吧。当然后序稍微复杂一些，后序不能直接弹，你得先判断了右子树遍历完了，然后再弹。我们现在这是中序遍历，所以简单一些，我们就直接 `stack.pop` 就可以了。

那弹出来之后呢？你看我们的左子树已经处理好了，然后这个当前的值是不是该进行处理了？左、值、右嘛。接下来就处理这个值。当然我们现在就不是去打印它了，我们是要去把这个值跟你传过来的 `k` 比较。那如果小于 `k`，那我们就把它记录下来。

处理好了值之后呢，接下来向右走。这样走的话就是又改变这个 `p` 的值，`p = pop.right`，就是我们刚弹出来的那个元素，沿着它向右继续走。这是左、值、右这样一个次序，我们的中序遍历就写好了。

```text
        ┌────────────────────────────────────────────┐
        │  循环条件： p != null  或  栈不为空          │
        └────────────────────────────────────────────┘
                    │              │
         p != null  │              │  p == null
        （向前进）   │              │（向回走）
                    ▼              ▼
          push(p); p = p.left   s = stack.pop()
          记录路径，压栈              │
                                    ▼
                          处理值：跟传入的 k 比较
                                    │
                                    ▼
                              p = s.right
                          （右指针继续向前进）
```

读图：这是标准的中序遍历状态机。`p` 负责"一路向左压栈"，栈负责"一路向右弹栈"，两个条件是"或"的关系，所以任何时刻只要还有一个没走完，就还能继续跑。

这个代码架子写好之后呢，其实接下来的两个方法，包括 `greater`、包括 `between`，它俩都可以重用这段代码，所以咱们就把这个代码给它复制两份，待会儿就不用重头写了。

#### less：条件一不成立就能停

好接下来我们还是回到我们的 `less`，它是要找小于 `k` 的所有的节点值。比如说我这个 `k` 传过来是等于六的，那我就先沿着中序来遍历，1、2、3、4、5、6、7。在这个过程中，只要发现比你这个 `k` 小的这些节点的值，我给它记录下来是不是就行了？所以处理值这非常的简单，判断一下：如果我们 `pop` 的值它是小于你传过来这个 `k`，那是不是应该把它记录下来？记录到 `result` 这个集合中，最终他要的是所有的值，那么就把 `pop` 当前节点这个值给它加进去。

这样不断遍历，经过了 1、2、3、4、5，接下来变成六了。假设这个六弹栈以后，我们发现六它不小于六——这个条件是不成立了。条件不成立了怎么办呢？还需要继续向后遍历七吗？**不需要了**。所以一旦我们检查出来条件不成立，就可以结束了。这是我们的 `less`。

```java
public List<V> less(K k) {
    BSTNode<K, V> p = this.root;
    LinkedList<BSTNode<K, V>> stack = new LinkedList<BSTNode<K, V>>();
    List<V> result = new ArrayList<V>();

    while (p != null || !stack.isEmpty()) {
        if (p != null) {                         // 向前进：压栈 + 左移
            stack.push(p);
            p = p.left;
        } else {                                 // 向回走：弹栈，处理值，右移
            BSTNode<K, V> pop = stack.pop();
            if (pop.value.compareTo(k) < 0) {
                result.add(pop.value);           // 小于 k，记下来
            } else {
                break;                            // 条件不成立，后面只会更大，直接收工
            }
            p = pop.right;
        }
    }
    return result;
}
```

> **注意**：中序是升序，所以 `less` 一旦发现当前值已经不小于 `k`，后面所有值更大，继续走纯属浪费——这个 `break` 是这个方法能"提前结束"的全部秘密。

#### 三个断言先写好

写完之后呢我们来测试一下。这是我画的一棵树，1 到 7，树创建好了，然后我们调用这个 `less` 去遍历。遍历的结果是不是应该是遍历到 1、2、3、4、5，这些都是小于六的啊，应该把它加入到我们刚才这个集合里。当然值呢加的是值啊，那我当然把值故意跟 `k` 写成一样了，这样我们好好看。最终正确的结果，`result` 里应该是 1、2、3、4、5。运行一下，最终打印出来 1、2、3、4、5，这是我们的第一个 `less` 方法，它就实现好了。

这样啊，我先把测试用例改成断言，就不打印了。那我们的期望值是多少？期望值找比六小的，对于我们这棵树来讲，是不是 1、2、3、4、5 啊，所以我们写一个 `assertTrue(...equals(...))`，因为它是比较两个集合是否相等。那我们的期望值呢是一个 `list`，里面放的是 1、2、3、4、5，这是期望值；然后实际值呢就是我们调用这个 `less` 方法它返回的结果。

那如果我接下来实现了那个 `greater`，我要找大于六的，最后应该是七——是不是正确？结果应该是七，比六大的只有七，所以大于六的期望值是七。

最后呢我再找一个，比如说找这个在什么什么中间的，我们用 `between` 这个方法。我要找 3 到 5 之间的，那 3 到 5 之间的是不是应该是 3、4、5 对吧？注意这是有等于条件的，有边界条件的，所以 3、4、5 都满足，那小于它的 1、2 没有，大于它的 6、7 没有，所以最终我们这里面应该是 3、4、5。这是我的测试用例，先给大家写好，那写好之后呢，我们再来实现后两个方法。

#### greater：中序没法提前停，得换个遍历方向

好那我们先来看这个大于的。找大于的，这怎么处理啊？就是判断一下呗——如果我 `pop` 的值比我们传过来这个 `k` 大，是不是我们应该把它加入到结果集合里？`result.add` 给它加进去，加的是 `pop.value`，没问题吧。

那**它能提前结束吗？不行啊**。它得是不是一直遍历到最后啊？找大于的嘛，它肯定是找到比它大的了以后都加，不断加入进去，一直到遍历完成啊。所以呢它就**不要 `break`** 了。

测一下，看一下它的结果是不是是七，没问题。我们的"小于""大于"这两个跟我们的预期值都一样。

那接下来我们再来看这个找在两个 `k` 之间的，这个是不是也很简单呀？判断一下：当我们的 `pop` 的值它**大于等于**我们的 `k1`，这是一个条件；并且 `pop` 的值**小于等于** `k2`，这是第二个条件。当这个条件满足，是不是我们就把它加进去。

那什么时候能退出呢？当你大于 `k2` 的时候，是不是我们就可以退出了。比如说我刚才我们这个测试用例，遍历到六的时候，**我想退出可不可以呢？可以**。接下来你遍历到六了，它已经大于五了，那就没必要继续向后遍历了。因此呢我们再加一个条件：如果我们 `pop` 的值已经大于 `k2` 了，那这时候我们可以退出循环 `break`。

好，最后这个 `between` 也写好了，我们也跑一下。可以看到我们的刚才这个测试用例都通过了，它里面其实有三个断言都通过了。好，我们的测试已经初步完成了。

刚才我们已经实现了 `less` 找比 `k` 小的、`between` 找两个 `k` 之间的、和 `greater` 找比 `k` 大的。那前两个没啥说的，主要是这个 `greater`，我们看一下能不能再优化一下。

你看我们刚才是怎么去找比 `k` 大的——我们是采用了从左向右的中序遍历，是 1、2、3、4、5、6、7 这样一个顺序去遍历它。但是这种缺点呢就在于，你**必须遍历完整棵树**才能找到比他大的。比如说我们要找比六大的，你过了六以后，后续这些是不是都得把它遍历完？这些都是比六大的，都是比六大的，所以不能提前结束。

那我们可以换一个思路：如果我的遍历顺序不是从左向右这样遍历，而是**从右向左**这样遍历呢？我的顺序是 7、6、5、4、3、2、1 这个顺序。那如果是这种遍历方式，我们只要碰到第一个小于等于六的，是不是就可以结束循环了？后面的 5、4、3、2、1 都不用循环了，直接退出循环。这样是不是能效率高些啊？

| 遍历方向 | 二叉搜索树上的输出 | 能不能提前停 | 适合谁 |
| --- | --- | --- | --- |
| 中序（左 → 右） | `1 2 3 4 5 6 7` 升序 | 只有 `less`、`between` 能 | 找小的、找中间的 |
| 反向中序（右 → 左） | `7 6 5 4 3 2 1` 降序 | `greater` 能 | 找大的 |

好那这种遍历方式是否可行呢？答案是可以的。其实我们前面在讲深度优先遍历的时候，咱们接触过的有三种：分别是前序遍历值左右，还有中序遍历左值右，以及后序遍历左右值。那这三种与之对应的还有三种：分别是反向前序遍历、反向中序遍历和反向后序遍历。主要的区别呢就是把左右的顺序颠倒了，原来是先左后右，现在呢变成先右后左。其中跟我们刚才这道题目相关的，就是**反向中序遍历**——右、值、左。

按照这种方式呢，它最后就会出现一个**降序**的这个结果。降序的遍历结果对于我们的二叉搜索树来讲，就是 7、6、5、4、3、2、1 这样一个顺序。

那大概清楚了我们的方向了，接下来我们就用反向中序遍历来写一下这个代码。

```text
   中序（左 → 右）              反向中序（右 → 左）

        4                              4
      /   \                          /   \
     2     8                        2     8
    /     / \                      /     / \
   1     7   9                    1     7   9
        /                                  \
       5                                    5
        \                                    \
         6                                    6

   输出：1 2 4 5 7 8 6         输出：8 9 6 7 4 5 2 1
        （升序）                     （降序）
```

读图：左边的入栈顺序是 `4 → 2 → 1`，右边的入栈顺序是 `4 → 8 → 9`。代码其实是对称的——把左和右对调、值处理前后的子树对调就行。

那这个反向中序遍历好不好实现呢？非常容易实现，我们就把之前的代码给它对称地改一改就行了。好之前代码我们先注释掉，然后处理值这块咱们先把它删掉。删掉以后呢，咱们来实现这个反向的中序遍历——代码原来呢是左值右，其实现在咱们稍微换一下不就行了：**先向右走到头**，没问题吧？向右走到头、向回走的时候呢，这回处理它的左子树啊，处理完值以后处理它的右子树。是不是这样一个顺序？啊，这就写完了，非常简单。

那我们这样吧，我们先把这个值咱们打印出来，看看它是不是那种降序的。打一下 `pop.v`，我来调一下这个 `greater`，先注释掉。现在呢它并没有返回那个结果，我只是看一下它的反向的顺序。没问题吧？7、6、5、4、3、2、1——就是对于反向中序遍历来讲，它去遍历我们的二叉搜索树时，就会实现一个逆序的输出结果呀。

清楚了它的工作方式之后呢，那接下来处理值这块就很简单了。我们就判断一下呗：如果我 `pop` 的值它是大于我们 `k`，这是不是相当于找到了？找到比我这个值大的了，那么我们怎么办呢？我们就把它加入到这个最终的 `result` 集合里去，加入 `pop.value`。那 `else` 呢？它小于等于了，那这时候还需要继续遍历吗？我们已经找到比它小或者等于它的了，是不是就可以退出循环、提前结束？所以就 `break` 就可以了。

```java
public List<V> greater(K k) {
    BSTNode<K, V> p = this.root;
    LinkedList<BSTNode<K, V>> stack = new LinkedList<BSTNode<K, V>>();
    List<V> result = new ArrayList<V>();

    while (p != null || !stack.isEmpty()) {
        if (p != null) {                         // 向前进：压栈 + 右移
            stack.push(p);
            p = p.right;                         // ← 与 less 的唯一区别
        } else {                                 // 向回走：弹栈，处理值，左移
            BSTNode<K, V> pop = stack.pop();
            if (pop.value.compareTo(k) > 0) {
                result.add(pop.value);
            } else {
                break;                            // 降序走到头了，后面只会更小
            }
            p = pop.left;                         // ← 与 less 的唯一区别
        }
    }
    return result;
}
```

好这样我们的代码写完了。写完之后呢，同样把我们之前的测试用例打开，如果这回的这个 `greater` 他仍然是能找到比六大的七啊，就说明它工作正常对吧？没问题吧？这样我们的测试也通过了。

这时候我们对这个 `greater` 做了一些优化啊——用到反向中序遍历取代掉了原来的中序遍历，就是相当于降序遍历。好这样我们这道题目就做完了。

### 力扣三题：删除、插入与查询

这节课开始呢，我们来讲一些跟二叉搜索树相关的题目。那有些题目啊，我们在前面的例题中已经接触过了，这种接触过的我们就快速过一下；那没有见过的题目我们再详细展开来讲。

#### 删除二叉搜索树的节点（力扣 450）

第一道题是删除二叉搜索树的节点。这道题是不是我们做过呀？它对应的是**力扣的 450**。将来你可以用非递归或者递归两种办法去实现。那当然有些注意事项稍微说一下：

力扣中树节点的定义方式，是用了一个叫 `TreeNode` 的类，这个跟我们用的节点类型不一样，它就相当于我们例题中的那个 `BTNode`。那区别在哪呢？

- 这个 `BTNode` 它有三个属性：`val`、`left`、`right`；
- 我们这个 `BSTNode` 呢，它有四个属性：`key`、`value`、`left`、`right`。

可以看到啊，区别就在于，力扣的题目中这个树节点它没有把键和值分开对吧？比较大小也是用 `val`，将来对应的值也是用 `val`；那我们呢是把这个键值分开了，其中键呢是唯一的、不重复的，值呢可以是任意类型。这样当然更为合理。不过我们做题目啊，允许适当的简化，所以力扣里它的设计啊，就是把这个 `val` 啊，它既作为键，又作为值——这一点大家注意一下。

所以你遇到代码里要做大小比较的时候，你就是这个 `val` 属性跟那个待删除的 `key` 做比较就行了。

```java
class TreeNode {
    int val;
    TreeNode left;
    TreeNode right;
    TreeNode() {}
    TreeNode(int val) { this.val = val; }
}

class Solution {
    public TreeNode deleteNode(TreeNode root, int key) {
        if (root == null) {                      // 递归边界：没得找了
            return null;
        }
        if (key < root.val) {                   // 没找到，继续往左递归找
            root.left = deleteNode(root.left, key);
        } else if (key > root.val) {            // 没找到，继续往右递归找
            root.right = deleteNode(root.right, key);
        } else {
            // 到这儿说明 root.val == key，就是被删除节点
            if (root.left == null) {             // 情况一：只有右孩子（或左右都没有）
                return root.right;
            }
            if (root.right == null) {            // 情况二：只有左孩子
                return root.left;
            }
            // 情况三：两个孩子都有
            TreeNode s = root.right;             // 先在后继候选区里找后继
            while (s.left != null) {
                s = s.left;
            }
            s.left = deleteNode(root.left, s.val);   // 后继接走被删节点的左子树
            return s;                                // 后继顶上来，当新的返回
        }
        return root;
    }
}
```

好具体的思路呢我们稍微过一下啊。就是给了你一个树节点 `root`，这是代表要删除它的**一个起点**；然后一个 `k` 是待删除的键。

然后怎么办呢？我们先得根据 `k` 找到待删除节点。那前面这两个 `if` 啊，其实就是**没找到**：当 `k` 小于节点值或者 `k` 大于节点值，就相当于没找到。没找到我们就要继续调用这个方法继续递归查找，直到找到，然后再做删除。

当然了你也要理解我们这个递归方法的**返回值的含义**：它的返回值是不是代表"删剩下的"那些节点？它把删剩下的那些节点跟当前节点——当前这个节点就是我们被删除节点的**父节点**——把父子关系建立好。这是前两个意思。

那从一个"一开始就说找到了"开始——因为能执行到这，说明 `node.value` 跟这个 `k` 是相等的了。那如果相等的话，我们当时讲过一共有主要是三种情况啊，其中那个左右孩子都为 `null` 的情况，可以被涵盖在情况一或者情况二中。

- **情况一**：被删除节点只有右孩子，我们就返回这个右孩子，相当于就把当前这个节点断开了。返回值是"删剩下的"，这个右孩子通过前面这两次递归操作啊，可能跟他的被删除节点的**父亲**建立这种左孩子的关系，或者是建立这种右孩子的关系。
- **情况二**：只有左孩子，那我就把这个"删剩下的"的左孩子返回，然后跟上一个的这个被删除节点的父节点建立这种父子关系。
- **情况三**：是最复杂的一种，就是被删除节点有两个孩子。有两个孩子怎么办呢？我们要先找到他的后继节点；后继节点里面要处理好后继节点的后事啊，也就是对后继节点做一个递归的删除——在我们被删除节点的右子树里面找到这个后继节点，把它删掉。删掉以后呢，后继节点将来它取代我们被删除节点的位置。当然我们要把后继节点的左右孩子给他重新去做一个赋值。最后返回"删剩下的"，就是我们这个后继节点。

#### 插入题：用递归把 put 再写一遍

好接下来呢我们再来看一道题目，这道题目呢是**向二叉搜索树中新增一个节点**。这个我们其实也做过类似例题啊，我们做过一个 `put` 方法，还有印象吧？它接收两个参数，一个是 `k`，一个是 `value` 值。

不过我们当时做的时候分了两种情况：一种情况呢就是这个 `k` 在树里已经找到他了、已经存在了，存在的情况下呢，我们就去做什么更新的操作，就是用我们传过来这个新的 `value` 值去更新掉旧的值。那如果这个 `k` 不存在，我们是不是在做的新增啊？这是我们当时实现 `put` 方法。

当然力扣的这道题啊，它做了一定的简化，它让我们只需要考虑新增这种情况就可以了，不需要考虑更新。为什么呢？因为他题目给了一个前提啊，他说他传过来这个 `value` 值一定与树中的节点是不一样的。既然都不一样啊，它能确保这一点，是不是说我们只需要考虑不存在、也就是新增这种情况了——所以这是这个题目的一个前提，说明一下。

那题目呢具体实现呢，我们这回用递归来求解吧。因为课堂的例题我们用的是非递归去实现了 `put`，这回我们解这道题，用递归的方式来做一下。

好那这个思路我们先分析一下啊。比如说我要插入的是一个新的值 1，树呢就是下面这棵树：

```text
        5
      /   \
     2     6
```

那他就先把这个待插入的新值给我们的根节点做一个比较，发现 1 比 5 小，那是不是 1 应该插不到 5 的左边呀？但是它**能不能插进去，还取决于我有没有孩子**。那 5 这边如果已经有孩子了，那是不是我们应该继续重复这个操作啊？因为他有孩子说明没空位啊，你不能直接作为 5 的左孩子。所以呢我们就把下面这个节点 2 再跟 1 做相同的处理逻辑啊，再把 1 跟 2 比较，发现 1 比 2 小，是不是应该插入到 2 的左边？好继续来看，结果发现 2 这边它的左孩子是 `null` 了，说明有空位对吧？哎有空位，那我们就把 1 加入到这个位置，是不是就可以了。

那类似的，如果我这个 `value` 值是个 7 啊，也是从根节点开始。他发现 7 比 5 大，所以应该插不到 5 的右边。但是 5 的右孩子不为空对吧，所以我们继续做这个比较，看 6 跟 7。这回比较的话发现 6 比 7 还是要小，所以它应该插入到 6 的右边。那 6 的右孩子是个 `null` 了，就是有空位可以插入了。所以呢我们就可以把 7 加入到这个位置，是不是就可以了。

```text
   插入 1                          插入 7

      5                              5
     / \                            / \
    2   6       比 5 小 → 往左       2   6       比 5 大 → 往右
   /                              /
  1                              ...（6 的右边）
                                 6
                                  \
                                   7
```

读图：两条路径的形状完全一样——一路比较、一路左移或右移，直到当前节点为空才落子。变的只有跟谁比、朝哪边拐。

所以呢总结出来，就是我们要**不断地进行查找比较，直到找到一个 `node` 为空**、也就是有空位为止。有空位了，那么就可以把这个节点创建出来。最后呢把新创建出来的节点跟他的父亲建立好父子关系，是不是就可以了？唉这是我们的一个整体思路。

思路有了，我们来写一下这个代码。我还是先写比较的代码。先判断一下，如果 `value` 小于当前节点的值，是不是我们应该向左继续找啊，看有没有空位，所以呢就递归调用，还是我们刚才这个方法啊，只不过下次查找的起点，是不是就应该是我当前节点的左孩子了，当前节点它的左孩子就是 `node.left`。好，继续把左孩子跟我们这个新插入的值做这个比较。

啊当然了，还有一种情况，就是如果我们这个要插的值比当前节点的值要大，那我们应该到右边去查找对吧？那就递归来调用，这回呢传过去的就是当前节点的右孩子啊，从右孩子这边继续查找。

那有没有可能出现相等的情况？**不需要了**，不需要考虑了。因为人家题目前提给了，他要说插的新值肯定是跟树中节点不一样的啊，所以他肯定走不到那个 `else`，我们也不去处理了。这是查找的代码。

那什么时候算找到了呢？找到这个空位子。刚才举的那个例子，我要插入 1，结果当前节点已经是 2 了啊，那下次再递归的时候，是不是他就把 2 的左孩子 `null` 传过去了？传过去以后，我一旦判断出来下次递归时这个 `node` 变成 `null` 了，表示找到空位了对吧？那这时候我们是不是就可以创建一个新的节点对象了，就根据这个 `value` 值把节点创建出来。

那创建出来以后，我们还有一部事儿啊，还有一件工作：就是你把刚创建出来这个 1 这个节点，是不是要跟上次的这个父节点 2 建立父子关系啊？否则的话它俩没有这之间这个联系的。因此我们要利用上这个方法的返回值，就是把刚创建出来这个节点啊，给他 `return` 返回，没问题吧？

```java
public BSTNode<K, V> put(K key, V value) {
    BSTNode<K, V> node = this.root;
    node = put(node, key, value);              // 顶层接一次
    if (node != null) {
        this.root = node;
    }
    return this.root;
}

private BSTNode<K, V> put(BSTNode<K, V> node, K key, V value) {
    if (node == null) {                        // 找到空位了，落子
        return new BSTNode<K, V>(key, value);
    }
    if (key.compareTo(node.key) < 0) {
        // 往左走，并把新节点接到当前节点的左孩子上
        node.left = put(node.left, key, value);
    } else {
        // 往右走，并把新节点接到当前节点的右孩子上
        // 题目前提保证新值跟树中节点一定不同，走不到"相等"那个分支
        node.right = put(node.right, key, value);
    }
    return node;                               // 语法上必须有个返回值
}
```

返回以后返回到哪了呢？你看就是返回到它上次递归调用的地方啊，要么是这个逻辑，要么是这个逻辑。那拿我们刚才的 1 来讲好，我们新插入的这个 `value` 是 1，那是不是他应该返回到这个位置啊？因为这个 1 是小于它的、小于上一次节点这个 2 的。

那怎么建立父子关系啊？很简单。这时候 2 的左孩子肯定是空嘛，那新增的 1 就相当于充当了原来这个空位的一个位置，所以肯定是赋给 `node` 的左孩子，要跟我们刚才这个递归调用返回的新节点建立父子关系。`node` 是父亲，然后我们递归调用返回的是那个新节点，他俩之间建立好父子关系是不是就可以了？

类似的，如果是走右边那条路，那我们就去建立 `node.right` 跟我们返回的新节点之间的父子关系。

啊这样我们的主要代码就写好了。当然我们这个方法呢它还有一些编译的错误啊。你看如果他走的是第一个 `if` 分支，这时候它是有返回值的，因为方法定义上需要有一个返回结果；但如果他走后面两个分支的话，它是不是就缺少一个返回值啊？所以我们这里为了保证它的语法正确性，我们还得 `return node` 啊，就把当前节点返回了。

当然返回当前节点，这里我们稍做一点分析啊，它会多出一些额外的赋值动作。你看啊，我们刚才这个例子中，我创建出来这个新的节点 1 了，把它的结果返回，肯定返回到这次递归的过程中，它会建立我们的父子关系啊，父子关系就在这一步建立好了。下面这个呢也是去建立这个父子关系啊，那这一步这个赋值是**有必要的**，就是把新创建的节点跟他的父亲节点之间建立父子关系是有必要的。

但是你看啊，如果我的当前节点假设是 2 啊，也就是这个 `node` 是 2，然后你看我把 2 跟新创建出来的 1 这个节点父子关系是建立好了。哎那我就把这个 `node` 返回了。返回以后上次的递归调用是谁跟谁之间呢？是不是就是我们的 5 节点跟 5 的 `left` 2 之间，这两个节点之间他们递归调用。那大家看，他把返回的 2 是不是又重新赋值给了这里的 5 的 `left`？唉所以它相当于执行了 `5.left = 2` 这个复制动作，但显然这个赋值是不是就有点多余了啊？因为 2 跟 5 之间**原本它就有这种父子关系**啊。

所以我们用递归的这种实现它的一个缺点，就是多出了一些不必要的赋值动作啊。从你查找、找到这个 `null` 空位的这个过程中来时，这条路上的所有节点都得重新赋值一次。那如果是用非递归实现，就不存在这样的问题。好这一点大家稍微注意一下就可以了。当然我们也没办法啊，因为方法的返回值就决定了，你总得有一个东西得返回上去啊，所以多出来这个复制动作也就只能认了啊，只能认了。

#### 第一题：删除二叉搜索树中的节点（力扣 450）

**题干**：给定一个二叉搜索树的根节点 `root` 和一个整数 `key`，删除二叉搜索树中 `key` 对应的节点。如果存在多个值等于 `key` 的节点，删除任意一个即可。返回删除该节点后的根节点。注意，这里力扣的树节点只有一个数值属性 `val`，键和值没有分开，删除时直接拿 `val` 与 `key` 比较。

**解析**：思路在正文「450：删除二叉搜索树的节点」一节已完整拆开——先按 `key` 在二叉搜索树上做一次标准查找，每一层用返回值把"删剩下的子树"交回给父节点重新接上；找到之后按孩子个数分三种情况处理，其中左右孩子都为空的场景被"只有一个孩子"的两种情况覆盖；最难的两个孩子场景，先在后继候选区找到后继，再用一次递归把后继从它原来的位置上摘掉，最后让后继接管被删节点的左右子树。

**答案**：

```java
class Solution {
    public TreeNode deleteNode(TreeNode root, int key) {
        if (root == null) return null;
        if (key < root.val) {
            root.left = deleteNode(root.left, key);
        } else if (key > root.val) {
            root.right = deleteNode(root.right, key);
        } else {
            if (root.left == null) return root.right;
            if (root.right == null) return root.left;
            TreeNode s = root.right;
            while (s.left != null) s = s.left;
            s.left = deleteNode(root.left, s.val);
            return s;
        }
        return root;
    }
}
```

#### 第二题：向二叉搜索树中新增节点（力扣）

**题干**：给定二叉搜索树的根节点 `root` 和一个整数 `val`，把 `val` 插入到二叉搜索树中，返回插入后的根节点。**题目给定的前提**是：`val` 保证与树中已有的所有节点值都不相同，所以不需要考虑"更新已有节点"的分支，只需要新增。

**解析**：见正文「插入题：用递归把 put 再写一遍」。核心是把课堂上非递归版 `put` 的"一路比较"改成"一路递归"：每一层只用一次大小比较决定往左还是往右往下钻，钻到空节点时构造新节点并返回；上一层拿到这个返回值，赋给当前节点的 `left` 或 `right`，父子关系就在这一步自然建立起来。正文里还分析了这个递归写法的代价：查找路径上的所有节点都会被多赋值一次，而这次赋值其实是冗余的——它们之间原本就是父子关系。

**答案**：

```java
class Solution {
    public TreeNode insertIntoBST(TreeNode root, int val) {
        if (root == null) return new TreeNode(val);
        if (val < root.val) {
            root.left = insertIntoBST(root.left, val);
        } else {
            root.right = insertIntoBST(root.right, val);
        }
        return root;
    }
}
```

#### 第三题：搜索二叉查找树中的目标节点（力扣 700）

**题干**：给定二叉搜索树 `root` 和一个整数 `target`，如果 `target` 存在于二叉搜索树中，返回该节点，否则返回 `null`。

**解析**：见正文「700：搜索二叉查找树中的目标节点」。这一题思路最直白，因为它只做查找、不做任何树形改动：拿 `target` 与当前节点的值比，小了就只可能在左子树里，大了就只可能在右子树里，相等就返回当前节点；走到空节点还不相等，说明树里没有它。这道题课堂上例题已经用 `get` 方法讲过，所以是快速过。

**答案**：

```java
class Solution {
    public TreeNode searchBST(TreeNode root, int target) {
        if (root == null) return null;
        if (root.val == target) return root;
        if (target < root.val) {
            return searchBST(root.left, target);
        } else {
            return searchBST(root.right, target);
        }
    }
}
```

## 用中序遍历判定二叉搜索树，顺手求个范围和
> 对应块：BLK46 | 覆盖分集：P176-P180 | 块标题（分集名）：《基础算法-131-二叉搜索树-e04-判断合法-》

我们接着往下走一道题：**LeetCode 98，验证二叉搜索树**。题目给一棵二叉树，问你这棵树是不是一棵合法的二叉搜索树。

先别急着写代码，我们拿三棵树练练手。

### 三棵树，先练练手

二叉搜索树的定义我们都清楚：任意一个节点，它左边所有的东西都要比它小，右边所有的东西都要比它大。

注意是"左边所有"，不是"左边那个"。这道题的绝大多数坑，都藏在"所有"这两个字里。

第一棵树：

```text
        4
       / \
      2   6
     / \
    1   3
```

合不合法？合法。四的左边是 1、2、3，都比它小；右边只有 6，比它大。二的左边 1 比它小，右边 3 比它大，也是同一套规则。

第二棵树：

```text
        5
       / \
      4   6
     / \
    3   7
```

这个就不对了。六的左边 3 比它小、右边 7 比它大，看着没问题；五的左边 4 也比它小。可是你顺着五的右边往下看——三也在五的右边啊，五的右边跑出来一个比它小的 3，这就破了规矩。

第三棵树更简单，它里面有值相等的两个节点：遍历的时候上一个值是 1，当前值也是 1。所以**两个节点的值相等，同样不算合法的二叉搜索树**，别把判据写成"小于等于"以外的模糊说法。

> **定义**：合法的二叉搜索树 = 任意节点左边的所有值都严格小于它，右边的所有值都严格大于它。严格小于、严格大于，等于也不行。

### 中序遍历：唯一能一把抓住合法性的东西

那怎么判断？靠的是中序遍历的性质：**一棵合法的二叉搜索树，中序遍历出来一定是升序的**。

你看第一棵树，中序遍历的结果是 1、2、3、4、6，肯定是由小到大排下来的。反过来也成立——只要中序遍历不是严格升序，这棵树就一定不合法。

第二棵树中序遍历出来是 4、5、3、6、7。前一个 5 比后一个 3 大了，升序断了，当场就知道它不合法。

所以思路就有了：**在中序遍历的过程中，记住上一个访问到的节点值，每访问一个新节点就跟它比一下。只要出现"上一个值 ≥ 当前值"，立刻判定非法**。注意这个符号是 ≥，等号也算非法。

### 非递归写法，和 previous 的那个边界坑

那先把中序遍历的非递归版本写出来。这里千万不要用递归，用递归会把事情搞复杂——原因我们后面单独讲。

```java
public boolean isValidBST(TreeNode root) {
    Deque<TreeNode> stack = new LinkedList<>();
    TreeNode p = root;
    long previous = Long.MIN_VALUE;   // 记录上一个访问到的节点值
    while (p != null || !stack.isEmpty()) {
        if (p != null) {              // 沿着左边一路向前走
            stack.push(p);
            p = p.left;
        } else {                       // 左边到头了，开始往回走
            p = stack.pop();
            // 向回走：弹出哪个节点，就处理哪个节点的值
            if (previous >= p.val) {
                return false;          // 上一个值 >= 当前值，不合法，没必要继续了
            }
            previous = p.val;
            p = p.right;               // 弹出来的这个节点，右边还有路就向右走
        }
    }
    return true;                       // 整个 while 跑完都没找到非法点，那就是合法
}
```

这段中序遍历的骨架我写过很多遍了，就不多讲了。循环条件两个：`p != null` 表示我还在沿着左边向前走；`stack` 不为空表示我正在向回走。向前走的时候把经过的节点压栈；向回走的时候弹栈，弹出来的这个节点就可以处理它的值了，处理完再看看它右边还有没有路。

关键的判断就加在"处理值"那个位置：

- `previous >= p.val`，直接 `return false`，后面的遍历根本没必要跑；
- 否则把 `previous` 更新成当前节点的值，进入下一轮比较；
- 整个 while 循环跑完一遍还没抓到非法点，说明整棵树是合法的，最后 `return true`。

这里有两个坑要当场处理。

**第一个坑是语法坑。** 我们刚写 `long previous;` 的时候直接编译报错，为什么？因为 Java 里的局部变量在使用前必须赋一个初值。那初值选什么？

有同学说"我给个 0 行不行"——不行。题目根本没限制节点的值范围。假如这棵树最左边那个节点的值是 -1，你这个 0 代表的"上一个值"比人家里最左边的 -1 还要大，一上来第一次比较就错了。

所以 previous 要**尽可能小**。那有人就说，那我选整数的最小值 `Integer.MIN_VALUE`，总行了吧？我们待会儿拿测试用例跑一下，测一测。

果然，一提交就有一个用例挂了：

```text
        -2147483648
```

就这一个节点，期望结果 `true`——一个节点的树肯定合法呀。但我们的代码返回了 `false`。原因清清楚楚：整数的最小值恰好就是这个节点的值，而我们的 `previous` 初始也等于整数的最小值，第一次循环两个最小值一比，**相等**，相等我们也返回了 `false`。

所以我们选的那个值还是不够小。怎么办？换成 `Long.MIN_VALUE`——long 的最小值肯定比 int 的最小值更小，就不存在相等的情况了。整个改动就一行。

> **易错点**：`previous` 的初值不能是 0，不能是 `Integer.MIN_VALUE`，必须是 `Long.MIN_VALUE`。节点值的类型是 `int`，用 int 的边界值当"负无穷"是错的——万一真有节点取到边界值，就成了相等，直接误判。

这就是第一种解法：中序遍历 + 非递归 + previous。

### 递归写法，以及它埋着的两个坑

接下来用递归来实现。倒不是说它有多难，而是里面有不少坑，容易踩。

中序遍历用递归写非常容易，架子三行就搭好了：先递归调用 `node.left`，再处理当前节点的值，最后递归调用 `node.right`。

```java
private long previous = Long.MIN_VALUE;

public boolean isValidBST(TreeNode root) {
    return doValue(root);
}

private boolean doValue(TreeNode node) {
    if (node == null) {
        return true;                 // 空节点没什么可比的，直接合法
    }
    if (previous >= node.val) {
        return false;                // 保证严格升序，>= 都算不合法
    }
    previous = node.val;             // 合法就更新 previous，继续往下递归

    boolean a = doValue(node.left);  // 左子树也要合法
    boolean b = doValue(node.right); // 右子树也要合法
    return a && b;
}
```

三种情况：node 已经空了，没什么可跟上一个值比较的，直接 `return true`；node 不为空，就在处理值的位置跟上一个值比，`previous >= node.val` 就 `return false`；条件不成立就是合法，更新 `previous` 继续递归。

至于左子树的返回值和右子树的返回值——**这个一定要用上**。左子树要合法，右子树也要合法，最终返回 `a && b`，两边同时成立整棵树才算合法。至于当前节点本身，它合不合法在前面那句 `return false` 里已经判掉了。

提交一下，通过了。力扣上显示的执行耗时还比非递归那版更快：非递归 1ms，这个递归 0ms。

#### 坑一：明明已经失败了，还接着往下跑

但这道题是有坑的。要讲清楚这个坑，我们必须对刚才这个递归的过程有一个比较深入的理解。所以我专门做了一个网页来观察这段代码的递归工作流程。

我给出的这棵树是**不合法**的：

```text
            4
          /   \
         2     6
          \   / \
           4 3   7
```

根节点的右子树里，有一个比根节点还小的 3，显然不符合二叉搜索树的特点。所以这段代码跑下来应该返回一个 `false`——结果没错，但它不是最有效率的，中间有些不必要的步骤。

我们把它在中序遍历里过一遍：

从根节点开始，先沿着左边走到头，走到 2。然后按左、值、右的规律处理 2：二的左子树是 null，通过；二自己，通过（一开始 previous 是最小值，最小值小于 2，符合升序），previous 更新成 2；二通过之后，它作为四的左子树，四的左子树也就相当于校验通过了。四自己能不能通过？可以，previous 是 2，2 小于 4，符合升序，previous 更新成 4。

接下来该到四的右子树了。四的右子树是 6，但能直接处理六吗？不行，因为 6 这边还有左子树没处理，所以得先沿着左边走到头，走到的就是 3。

**重点来了。** 这时候 previous 已经被更新成 4 了，而 4 大于 3，已经不符合升序的条件。所以 3 的左子树校验通过，但 3 自己校验失败。

那我们觉得是不是到这就应该结束了？如果传进来的节点就是 3，它 return false 表示整个判断失败，所以接下来 3 的右子树还会处理吗？不会处理了。

**但请注意**——三这一层是结束了，它上面那一层呢？六拿到三的返回值 `false` 之后，大家注意我有没有立刻去检查这个值？**没有**。就因为没有立刻检查，六这个节点的代码还会继续向下运行，去判断 6 的值合不合法，然后再判断 6 的右子树合不合法。

于是程序还会继续递归判断 6：六的左子树没通过，六自身通过了（previous 还停在 4，4 小于 6，升序）；然后去处理 6 的右子树 7，七的左孩子通过、它自己也通过、右孩子也通过。又回到 6，发现 6 的右子树通过了，然后整个这一边作为四的右子树，最终结果不通过，返回一个 `false`。

最终的结果并没有错，但是显然——三既然已经比较失败了，后面 6 和 7 就不应该再处理了。所以我们这个实现并不是最优的。

改正方法非常简单：当前节点是 6，它处理 6 的左孩子也就是 3 的时候，如果已经返回 `false` 了，那我提前做一个判断，还需要继续处理 6、再处理 6 的右子树吗？不需要了。

```java
private boolean doValue(TreeNode node) {
    if (node == null) return true;
    if (previous >= node.val) return false;
    previous = node.val;

    boolean a = doValue(node.left);
    if (!a) return false;             // 剪枝：左边一失败，整棵子树没必要再看
    return doValue(node.right);       // 下面就只需要判断 b 了
}
```

这样处理之后再跑一遍：判断 2，通过；判断 4，左边和自身都通过；判断到 3，判断失败，直接返回，不用再继续比较 6 和 6 的右子树了。步骤比以前少多了。

> **结论**：这种技巧在编程领域里叫**剪枝**。递归本身就是一棵树，这种多路递归构成的那棵调用树，我们把它的一些枝杈减掉，让它提前返回，就结束了一些不必要的递归。

这是第一个坑，效率可以优化一下。优化之后放到力扣上执行，时间还是 0ms，没有明显提高。不过这里其实有一个我想不通的事儿：我们之前的非递归实现，我觉得是应该更有效率、效率更高一些，但反而非递归的执行时长是 1ms，而这种还没优化的递归实现就能达到 0ms。这是一个让人百思不得其解的地方，我觉得可能是力扣底层的一些判断逻辑、一些处理上会有问题吧。

#### 坑二：previous 做成了方法参数

第二个坑，针对的就是 `previous` 这个变量。

刚才实现递归的时候，我把 `previous` 作为所有递归方法的一个**全局变量**。不管你递归的嵌套层数有多深，用的都是同一个 `previous`。

有同学觉得这样写不太对——不符合什么面向对象，也不符合函数式编程——就想把 `previous` 做成方法的参数：

```java
public boolean isValidBST(TreeNode root) {
    return doValue(root, Long.MIN_VALUE);
}

private boolean doValue(TreeNode node, long previous) {
    if (node == null) return true;
    if (previous >= node.val) return false;
    previous = node.val;                        // 改了个寂寞

    boolean a = doValue(node.left, previous);
    boolean b = doValue(node.right, previous);
    return a && b;
}
```

`doValue` 多了一个参数，第二个参数就是代表上一个值，每次递归都把它带上。代码看起来也没什么大问题，跑一些测试用例它也能通过。

比如这两个测试用例，一个合法一个非法，都能查出来：

```text
层次： 4  2  6  1  3     ->  合法
层次： 4  2  6  3  7     ->  非法（3 挂在了 2 的左边，却比 2 大）
```

第一个返回 `true`，第二个返回 `false`，好像也对。

但是呢，**这种错误它难以发现，就在于有的测试用例它能通过，有的测试用例它就通不过**。

我们再来看一个例子，这棵树：

```text
    3
     \
      4
     /
    5
```

它合不合法？非法的。三的右孩子 4、5 确实比它大，但四的左孩子 5 应该是比四小的呀，现在 5 比 4 大，这个就不对。

套用刚才那段代码跑一遍——明明是非法的，它还是给我返回了一个 `true`。这就把人给搞蒙了。

这回我们换一种分析方法，用 debug 来分析。我在 `previous` 跟当前节点值比较的地方加一个断点，但只想让节点等于 5 的时候、和节点等于 4 的时候停下来，其他情况不想停。右键点这个断点就可以加条件，直接写：节点的值等于 5 的时候断点才生效，或者节点的值等于 4 的时候断点才生效，其他情况断点不会停。

中序遍历是左、值、右，我们跟着它跑一遍：先遍历到 3，三的左孩子不用处理；3 的值跟 previous（此时是最小值）比较，肯定符合，通过，previous 更新成 3；接下来处理 3 的右孩子，但它得先沿着右边向左走到头，所以接下来遍历到的节点是 5。

这时候 previous 是几？是 3。这都是正确的，因为 5 的上一个中序值就是 3，3 大于 5 这个条件不成立，目前判断出来还是合法的，所以它就把 previous 更新成了 5。

接下来该向回走了——因为四这条路已经向左走到头了——向回走接下来判断 4。**按我们的想法**，previous 已经被更新成了 5，将来它跟节点 4 比较的时候，5 大于 4 应该就能检查出来它不合法。

但是会怎么样呢？我们继续运行，停在 4 这个节点的断点处，看这时候的 previous 是几——**为什么这时候的 previous 还是三呢？它没有被更新成五。**

其实很简单。我重新跑一遍：执行到 5 这个节点的时候，确实已经把 previous 更新成 5 了。但是这个 previous 它是一个**方法参数**，或者说，它是我这个方法内的一个**局部变量**。它在处理 5 这个节点时确实已经变化了，变成了 5；但是将来回过头来处理 4 这个节点的时候，四中的 previous 变量是 5 吗？不是啊——四中的 previous 是这个四节点被调用的时候传过来的参数值，它始终是那个 3，它并没有被更新成 5。

本质的原因就是因为：**方法参数属于局部变量，每个方法在运行的时候，这个局部变量对外都是私有的。方法内我改了它，不会影响到其他方法的局部变量。** 因此就造成了我们的判断错误。

解决方法有两种。第一种就是我们一开始写的那段代码——一开始为啥没错呢？因为 previous 是一个针对所有方法的一个全局变量，既然是全局变量，你在一个方法内改了，会影响到另一个方法，会的。

第二种方法我们接着来看。刚才这种做法不行，是因为参数是方法内的局部变量。那我们由此想到的是——**能不能把这个参数做成是一个对象？** 让它始终是我们递归调用时传递过来、传递过去的都是同一个对象。如果是同一个对象，我对它里面的值做修改，是不是就能影响到其他方法了？

```java
public boolean isValidBST(TreeNode root) {
    AtomicLong previous = new AtomicLong(Long.MIN_VALUE);
    return doValue(root, previous);
}

private boolean doValue(TreeNode node, AtomicLong previous) {
    if (node == null) return true;
    if (previous.get() >= node.val) return false;      // 调用 get 拿到对象里存的值
    previous.set(node.val);                            // 调用 set 修改，有 get 就有 set

    boolean a = doValue(node.left, previous);
    if (!a) return false;
    return doValue(node.right, previous);
}
```

用 `AtomicLong` 类型的对象当参数。传参的地方也要做相应调整：`new` 一个 `AtomicLong`，值是 long 类型的最小值，这是它的初始值。因为它现在是个对象了，不能直接跟一个 int 整数值比较，所以从对象里调用它的 `get` 方法获得对象中存储的值，拿出来跟节点值比较；要修改值，就调用 `previous` 里的 `set` 方法，把 `node.val` 作为新值传进去。

我只是在一开始创建了一个对象，接下来不管多少次递归调用，传递过来传递过去的都是同一个这个对象。对同一个对象修改它的值，能影响到其他方法，可以的。

再把刚才那个测试用例跑一遍——OK，检查出来了，`false`。

> **提示**：这里大家可能会问，能不能直接用 `Long` 来代替 `AtomicLong`？长整型不也是对象吗？**不行。** `Long` 包括其他一些 Java 包装类型（`Integer`、`Character` 等等）都属于**不可变类型**，它里面的值是不能修改的；`AtomicLong` 属于可变对象，它里面的值可以用 `set` 方法来修改。所以必须用 `AtomicLong`。

到这里，针对 98 题我们前后接触了三种解法。它们的核心思想都是采用了中序遍历的思想——判断中序遍历时前一个值要比后一个值要小，只不过实现方式上有所区别：

| 解法 | 怎么记 previous | 特点 |
|---|---|---|
| 非递归中序 | 循环外一个局部变量 | 骨架简单，但 initial 值必须用 `Long.MIN_VALUE` |
| 递归 + 全局变量 | 类成员变量，所有层共用一个 | 好用，但要记得它是有状态的 |
| 递归 + 对象传参 | `AtomicLong`，全层共用一个对象 | 传参干净，本质等价于全局变量 |

### 只比父子够不够？不够

那有没有可能换一种思路？咱们不用中序遍历这个思想，来判断二叉搜索树是否合法。

有同学就想出了下面这种做法：**判断父亲比左边是大、比右边是小**。

看我们这棵树，父亲 4 比左孩子 2 大、比右孩子 6 小；父亲 2 比左孩子 1 大、比右孩子 3 小。其他的节点好像也可以递归操作。这样对不对呢？

其实这样**并没有涵盖所有的情况**。你看下面这种情况：

```text
        4
       / \
      2   6
         / \
        3   7
```

按他的判断逻辑：父亲 4 比左孩子大、比右孩子小，没问题；父亲 6 比左孩子大、比右孩子小。那按照他的判断，这棵树应该是合法的。但实际并不合法——你看这个父亲的右子树中的 3，是不是比父亲 4 小了？所以这棵树其实并不合法。

所以我们不能只根据父亲跟孩子比。这位同学的思路，局限性在于**他只考虑了父节点和子节点之间的大小关系，并没有考虑祖先节点跟后代节点之间的大小关系**，因此判断上就出现了疏漏。

### 上下限：把祖先的约束一路传下来

那怎么办？我们可以用**上下限**的办法来判断一个值是否在某个范围内，把祖先的约束一路传下去。

还是那棵树，我们一个节点一个节点地算它的合法区间：

- 对根节点 4 来说，如果检查出它在负无穷到正无穷之间，就认为它合法；
- 对 2 来说，它的下限应该是负无穷没错，但它的上限还能是正无穷吗？不行，它一定要比它的父亲小。所以它的下限是负无穷，上限是 4；
- 对 6 来说，它的下限不能是负无穷了，它的下限一定要比 4 大，所以下限是 4；它的上限我们刚开始还不能确定，那就给它一个正无穷；
- 对 3 来说，这回我们就得把祖先的因素考虑进去了。它的下限必须是 4——它得比 4 大，这是从主线传递过来的；它的上限只能是 6，它不能比 6 再大了。这样我们就可以检查出来：3 是不合法的。它这里只能是个比如说 5，5 是合法的，5 比 4 大、比 6 小；
- 最后这个 7，它的下限是 6，上限是正无穷。

整理成一张表：

| 节点 | 下限 min | 上限 max | 结论 |
| --- | --- | --- | --- |
| 4（根） | $-\infty$ | $+\infty$ | 合法 |
| 2 | $-\infty$ | 4 | 合法 |
| 1 | $-\infty$ | 2 | 合法 |
| 6 | 4 | $+\infty$ | 合法 |
| 3 | 4 | 6 | 3 落不进 $(4,6)$，不合法 |
| 5（若存在） | 4 | 6 | 5 比 4 大、比 6 小，合法 |
| 7 | 6 | $+\infty$ | 合法 |

所以我们可以针对每个节点都加上一个上下限，就可以正确地得出判断结论。但这个上下限在我们做递归的过程中要不断地更新：做 6 这个节点的判断时，它的下限就应该更新成 4；做 3 这个节点判断时，它的下限是 4，但上限应该被更新成 6。每次不断递归求解的过程中，上下限会针对每个节点有所变化、有所更新。

思路清楚了，我们用代码来实现。因为待会要用递归来实现，递归过程中需要加一个下限和上限两个参数，所以原来那个只有一个参数的方法就不能用了，我们再提供一个新的方法：

```java
public boolean isValidBST(TreeNode root) {
    return isValid4(root, Long.MIN_VALUE, Long.MAX_VALUE);
}

// min：下限，max：上限，节点值必须大于 min 且小于 max
private boolean isValid4(TreeNode node, long min, long max) {
    if (node == null) {
        return true;                        // 空节点直接认为合法
    }
    if (node.val <= min || node.val >= max) {
        return false;                       // 越界，不合法
    }
    // 左孩子：下限不变，上限收紧为当前节点值
    // 右孩子：下限收紧为当前节点值，上限不变
    return isValid4(node.left, min, node.val) && isValid4(node.right, node.val, max);
}
```

三个参数：第一个是节点对象，第二个是下限 `min`，最小值应该是 long 整型的最小值，第三个是上限 `max`，也就是将来你的节点值必须在这个范围之间，大于 min 小于 max，如果超过这个范围就是不合法。

最开始调用 `isValidBST` 的时候，把当前这个根节点传过去。最小值选什么？因为 Java 的整数没有一个什么负无穷大，我们就选择 long 整型的最小值作为负无穷大；最大值就选 long 整型的最大值作为正无穷大。

方法内：节点为空直接返回 `true`，不用进行有效性检查；如果节点不为空，判断它小于等于最小值、或者大于等于最大值，是不是就超过了这个有效范围，是就返回 `false`。

接下来该递归了。比如 4 已经是合法的，那我得判断它的左孩子是否合法、右孩子是否合法。针对左孩子，从图上我们可以看出，它的下限不用变，保持上次的下限，也就是最小值就可以；上限要变一下，比如我们这个例子中的 2，它的上限应该变成 4，也就是当前节点的值 `node.val`。这是对它左孩子做递归的校验。

右孩子类似，只不过它的最大值这边不需要更新，而下限 `min` 要更新成 `node.val`，上限先不更新，还是保留原来的 `max`。

最后，左右孩子的校验必须也是同时成立的，只有每个节点都合法，整棵树才是合法的。所以最后 return 这两个操作的一个逻辑与关系就可以了。

拿到力扣上跑一下，最佳执行时间也是 0ms，效率还是比较高的。我下面这几个测试用例，第一个是合法的，第二个、第三个、第四个都是非法的，所以第一个打印 `true`，接下来三个都打印 `false`。

### 938 题：二叉搜索树的范围和

我们再来看一道力扣的题目：**938 题，求二叉搜索树的范围和**。

这棵二叉搜索树已经给你了，然后又给你了一个范围。范围的意思就是说，将来我要找的节点必须是大于等于 `low`、小于等于 `high` 的，也就是在这个范围之内的这些节点。

第一个例子，范围是 7 到 15，我们这棵树里符合的只有 7、10、15 这几个节点，把它们的值加起来，最后要求和：7 + 10 + 15 = 32。

第二个例子，范围是 6 到 10，那大于等于 6、小于等于 10 的就是 6、7、10 这几个节点，加起来应该是 23。

需求有了，大家想想怎么去解？其实也很简单——**用一个中序遍历**，从小到大：

```text
中序展开：1  3  5  6  7  10  13  15  18
区间 [7, 15] 命中的节点：7、10、15
7 + 10 + 15 = 32
```

中序遍历的过程中我去检查，只要它在这个范围之内，那我就做一个累加；不在这个范围的，我就跳过。

#### 先用中序遍历求和，再说说它为什么不够快

下面我们采用非递归的方式来实现一下。这个非递归的中序遍历代码我就不从头写了，直接粘过来——反正是左、值、右，这个顺序就是中序遍历的顺序。

```java
public int rangeSumBST(TreeNode root, int low, int high) {
    Deque<TreeNode> stack = new LinkedList<>();
    TreeNode p = root;
    int sum = 0;                     // 求和肯定得定义在循环外
    while (p != null || !stack.isEmpty()) {
        if (p != null) {
            stack.push(p);
            p = p.left;
        } else {
            p = stack.pop();
            if (p.val >= low && p.val <= high) {
                sum += p.val;
            }
            p = p.right;
        }
    }
    return sum;
}
```

判断一下，如果 pop 出来的这个节点的值大于等于下限 `low`，并且小于等于上限 `high`，这就表示它符合我们这个条件、在两个范围之内；这个时候我们累加就行了，`sum += p.val`。最后等循环结束了，`return sum`，`sum` 里保存的就是我们累加的结果。

跑一下：这就是力扣上的例题，查找范围是 7 到 15，7 到 15 加起来是 32，结果正确。

那我们这段代码还有没有必要去优化一下？其实有必要。因为如果仅仅是为了在范围内求和，你不用中序遍历，用前序遍历行不行？可以；用后序遍历行不行？也可以。反正遍历的过程中每个节点都会过一遍，只要它符合在范围内这个条件我就累加。

那我们用中序遍历的目的是啥呢？是当它遍历到 15 这个上限的时候，后续的就不用遍历了，我就可以少循环几次。所以我们再加一个条件判断一下：**如果这个 pop 出来的节点已经是大于我们这个上限了，那还有必要去遍历吗？是不需要了，直接 `break` 就可以了。**

```java
} else {
    p = stack.pop();
    if (p.val > high) break;          // 升序遍历，一旦超过上限，后面全是废的
    sum += p.val;                     // 能走到这行，一定在 [low, high] 内吗？不一定！
    p = p.right;
}
```

> **易错点**：加了 `break` 之后，**`< low` 这个判断千万不能省**。因为中序遍历是从最小值开始的，1、3、5、6 这些小于下限 7 的节点照样会被遍历到，它们只是不参与累加而已。前面的 `>= low && <= high` 两个条件可以简化成一个累加，但"只累加、不中断"的语义必须保留。

很遗憾，中序非递归的这个实现放到力扣上去跑，执行时间大概是 4ms，并不是最优的。

那性能不高的原因在于什么？在于它**并不能进行有效的筛选**。它只能筛选掉比上限 `high` 大的——比 15 大的这些我可以提前结束循环、少循环几次。但是对于这些小于 `low` 的，是不是并不能做有效的处理？因为中序遍历它得从头遍历，3 和 5 都得在一开始过一遍，对不对？

因此我们得找一种更有效的方式。其实这里我们就不用去考虑中序遍历了，我们直接从根节点开始向下直接递归，递归的过程中我们可以做一些**剪枝筛选**的操作。

比如我们先检查当前这个节点 10，它在我这个范围内——下限是 7，上限是 15，在范围内。怎么办？累加。那如果继续向下递归，递归到 5 了，那 5 已经小于这个下限了。那我就问，5 的左子树还需要继续递归吗？不需要了。因为 5 都小于下限了，那它的左子树肯定更小于这个下限，所以 5 的左子树这边就不用递归了——这个枝杈相当于被剪掉了。我们只需要去递归 5 的右子树，因为 5 的右子树比 5 大，有可能还在这个范围内。

#### 上下限递归：该剪掉的枝干剪掉

思路有了，我们再来看一下这个代码怎么写。

```java
public int rangeSumBST(TreeNode root, int low, int high) {
    return rangeSum(root, low, high);
}

private int rangeSum(TreeNode node, int low, int high) {
    if (node == null) return 0;                          // 空节点，累加结果就是 0
    if (node.val < low) {
        return rangeSum(node.right, low, high);          // 自己和整棵左子树都出局
    }
    if (node.val > high) {
        return rangeSum(node.left, low, high);           // 自己和整棵右子树都出局
    }
    // 在范围内：自己 + 左子树结果 + 右子树结果
    return node.val
         + rangeSum(node.left, low, high)
         + rangeSum(node.right, low, high);
}
```

这四种分支画出来就是这样：

```text
                      node
                        │
     ┌──────────────────┼───────────────────┐
     │                  │                   │
 node == null      node.val < low     node.val > high
     │                  │                   │
   返回 0          只递归右子树        只递归左子树
                        │
                        ▼
          low ≤ node.val ≤ high
                        │
                        ▼
        node.val + 左子树累加 + 右子树累加
```

假设我执行到这儿，节点已经在范围内了。在范围内我们是不是应该去做累加？那就把 `node.val` 拿出来，跟谁累加呢？跟它左子树的累加结果、以及它右子树的累加结果，加到一块儿去。所以它应该加上左子树递归调用的结果，`low` 和 `high` 原模原样传过去；然后再加上它右子树的累加结果，这三个加到一块，就是我们最终的结果。

当然，左子树的累加结果不一定就能用得上。比如我们左子树现在是这个 5，那这个 5 它不在范围内，是不是得提前做一个判断？如果这个 `node.value` 都小于 `low` 了，那这种情况下左子树连同它更深层的左孩子，需要再次累加吗？不需要。我们只要考虑这个 5 的右子树，把右子树返回的累加结果返回就可以了。所以这个时候我们应该 `return` 它右子树的累加结果——当我们当前节点小于下限的情况下，它以及它的左子树都不用考虑了，只用考虑右子树。

结果类似的道理：判断一下如果我的 `node.value` 大于了 `high`，那 15 本身以及它右子树的内容是不是都不用考虑了？但是它的左子树有可能是个 13，这个是不是还得考虑？所以我们得返回当前节点左子树的累加结果。

当然还有一种特殊情况，就是这个 `node` 如果是 `null` 了，它的累加结果就是零，`node == null` 那么就认为它是个零。

这样我们这种上下限递归的代码就写完了。放到力扣上跑，它的时间可以达到 0ms。还是拿刚才那个例子跑一遍，结果应该还是 32。这样我们这种上下限递归的代码实现就完成了。

## 从前序遍历结果还原二叉搜索树
> 对应块：BLK47 | 覆盖分集：P181-P183 | 块标题（分集名）：《基础算法-136-二叉搜索树-e06-根据前序遍》

接下来这道是力扣的 1008 题。

题面很短：给你一棵二叉搜索树的**前序遍历结果** `[8, 5, 1, 7, 10, 12]`，让你根据这一串数，把原来那棵树长什么样还原出来。

> **定义**：前序遍历就是"根 → 左 → 右"。所以序列里的第一个元素一定是根，后面接着的先是一整棵左子树的前序，再接着一整棵右子树的前序。

题目还给了一条特别关键的前提：数组里**没有重复值**。这一句等下写代码时会被我们反复用到。

这道题有意思的地方在于——信息其实是足够的，只是你不一定马上看得出来。这一讲我们走三条路，从最直觉的一条一路走到效率最优的那条。

### 顺序插入：把这串数一个个塞进空树

最直觉的想法：既然二叉搜索树的插入规则是固定的，那我干脆从左到右把这串数挨个往一棵空树里插一遍。插完之后，它必然就是那棵原树。

我们手工走一遍。

先插 `8`，它没有父节点，直接当根。

再插 `5`。按二叉搜索树的性质，`5` 比根 `8` 小，应该往左走；发现 `8` 的左边还空着，于是 `5` 成为 `8` 的左孩子。

再插 `1`。从根 `8` 往左走，`1` 比 `8` 小，但 `8` 的左边已经有位置了（那是留给 `5` 的），所以继续往左；`1` 比 `5` 小，`5` 的左边还空着，`1` 落到那儿。

再插 `7`。从根 `8` 往左找到 `5`，`7` 比 `5` 大，`5` 的右边空着，`7` 成为 `5` 的右孩子。

再插 `10`。`10` 比根 `8` 大，直接走右边，`8` 的右边空着，`10` 成为 `8` 的右孩子。

最后插 `12`。`12` 比 `8` 大，走到右边，但右边已经有 `10` 了；`12` 比 `10` 大，`10` 的右边空着，`12` 落到那儿。

走完一遍，长这样：

```text
               8
             /   \
            5     10
           / \      \
          1   7      12
```

再看它的前序遍历是不是回到 `[8, 5, 1, 7, 10, 12]`：先打印根 `8`，然后是左子树的根 `5`，`5` 打完自己的值，先打左孩子 `1` 再打右孩子 `7`；`8` 这一坨完了，才轮到右子树的 `10`、`12`。顺序对得上，说明还原对了。

> **结论**：前序序列 + 二叉搜索树的插入规则 = 原树。

#### 前提就两条，代码也就这么点

写代码前把题目的前提再捋一遍，这两条直接决定了代码长什么样：

- `preorder` 数组长度 $\ge 1$，至少有一个节点，不存在"空数组"的情况。所以索引 0 一定是个真节点，可以放心拿它当根；
- 数组里没有重复值。所以插入时只有"小于往左""大于往右"两种情况，**等于**的情况不用写。

按刚才的思路，主方法就这么几行：索引 0 建根，然后从索引 1 开始循环，每次把数组里的一个值交给插入方法。

```java
public TreeNode bstFromPreorder(int[] preorder) {
    TreeNode root = new TreeNode(preorder[0]);
    for (int i = 1; i < preorder.length; i++) {
        int val = preorder[i];
        insert(root, val);
    }
    return root;
}
```

> **易错点**：循环必须从索引 `1` 开始，不能从 `0`。索引 0 已经拿去建根节点了，再插一遍就把根的值改坏了。

插入方法我们前面写过好几遍了——最早它叫 `put`，后来做别的题时也用过 `insert` 这个名字。这里要留意一处：方法名换了，**返回值类型也得跟着改成 `TreeNode`**，这不是忘了，是有意改的。这个方法最终要把新插入的那个节点作为返回值返回出去。

```java
public TreeNode insert(TreeNode node, int val) {
    if (node == null) {
        // 找到空位了，把新节点建出来返回
        return new TreeNode(val);
    }
    if (val < node.val) {
        // 比当前节点小，往左子树递归去找空位
        node.left = insert(node.left, val);
    } else {
        // 比当前节点大，往右子树递归去找空位
        node.right = insert(node.right, val);
    }
    return node;
}
```

> **提示**：`else` 这一支在这里就够了，不必再单独判"等于"。题目已经声明没有重复值，就这一条前提省掉了我们一个分支。
>
> 还有个地方容易觉得别扭：`node.left = insert(...)` 里，`insert` 返回的新节点被赋给了父节点的左指针或右指针——这个返回值就是用来**建立父子关系**的。至于最外层 `return node` 传回来的那个值，主方法里其实用不上，用不上没关系，它本来就是给递归内部的父子关系用的。

#### 能过，但不是最优

代码写完测试一下：用 `[8, 5, 1, 7, 10, 12]` 建出树，和我们自己手搭的那棵比一下，返回 `true`，没问题。效率也不用怀疑，贴到力扣上跑我记得是 0ms，还击败了 100% 的用户。

但是——**从时间复杂度上它并不是最优的**。

为什么？因为一次二叉搜索树的插入操作，效率是 $O(\log n)$，从根走到空位，最多走树高那么多步。而我们这个程序里，树里有多少个元素就循环多少次，也就是 $n$ 次。$n$ 次、每次 $O(\log n)$，总的复杂度就是：

$$O(n \log n)$$

虽然实测还是 0ms，但复杂度确实摆在那儿。所以我们接着看有没有更高效的方式。

### 给每个节点配一把上限尺

第二种解法我把它叫做**上限法**。

这个解法一样是从左到右遍历每个值，但它做的不是插入，而是**给每个值配上一对上限，用这把尺子判断它该挂到哪儿去**。

#### 一把尺子是怎么量出位置的

先说清楚这上限是干什么的。一个节点被创建出来的时候，我们同时给它记两个数：**左孩子上限**和**右孩子上限**。以后再处理别的值时，想让它当这个节点的左孩子，它必须没超过这个节点的左孩子上限；想当右孩子，就得没超过右孩子上限。

举个具体例子。一开始处理到 `8`，它没有什么限制，直接创建出来。创建完就给它配上：左孩子上限是 `8`，右孩子上限是 $+\infty$。

为什么是 `8`？因为 `8` 的左孩子当然得小于 `8`。为什么右孩子上限是 $+\infty$？因为 `8` 是根，右边没有更大的约束。

这个上限立刻就有用。你要是往后碰到一个 `10`，想把它当 `8` 的左孩子？不行，`10` 已经超过 `8` 的左上限了。正是这道门槛，才让"加左右上限"这件事有意义。

接着处理 `5`。注意：**不是立刻就创建 `5` 这个节点，而是先拿尺子量一下**。`5` 没有超过 `8` 的左孩子上限，可以当 `8` 的左孩子，这才把 `5` 创建出来。`5` 创建出来以后，它也有自己的一对上限：左孩子上限是 `5`，那它的右孩子上限呢？

这里有个容易看懵的地方：`5` 的右孩子上限变成了 `8`，不是 $+\infty$。为什么？因为递归走到 `5` 时，传下来的那个 `max` 已经是 `8` 了（也就是 `8` 的左孩子上限）。`5` 的右孩子既要大于 `5`，又得小于它父亲那一层传下来的 `8`，所以取 `8`。于是 `5` 是左限 `5`、右限 `8`。

继续。处理到 `1`，`1` 没超过 `5` 的左孩子上限，可以创建，创建后左限 `1`、右限 `5`。

```text
                    8   [左限 8, 右限 ∞]
                  /   \
          [左限 5, 右限 8] 的 5    10
                /   \
      [左限 1, 右限 5] 的 1    7
```

（上面只画了已经创建出来的节点。接下来要问的 `7`、`10`、`12`，此刻树里都还没有。）

#### 一次失败的尝试，才看得出这解法的味道

下面不一样了。我们处理到 `7` 这个**值**——注意，此时树里还没有 `7` 这个节点。

先拿 `7` 去试当前的节点 `1`：

- 能不能当 `1` 的左孩子？不行，`7` 已经超过了 `1` 的左限 `1`；
- 能不能当 `1` 的右孩子？也不行，`1` 的右限是 `5`，而 `7` 大于 `5`。

两次都失败，那 `1` 的左右孩子只能都给 `null`。于是 `1` 这个节点就算完整了——它自己被创建出来了，左右指针也都有值了。这时候才回头处理上一层的父子关系：`1` 没有超过 `5` 的左孩子上限，所以 `1` 成为 `5` 的左孩子，`5` 的左孩子才算有着落。

**注意，处理值的时候我们还停留在 `7` 这个值上，没有动。** 这时候回头再看 `7`：它能不能当 `5` 的右孩子？可以啊，`5` 的右限是 `8`，`7` 小于 `8`。满足左右限制的条件之后，`7` 这个节点才被创建出来。

但创建出来也别急着挂上去，还得先往下试。下一个值是 `10`：`10` 能不能当 `7` 的左孩子？不行，`10` 大于 `7` 的左限 `7`。能不能当 `7` 的右孩子？也不行，`10` 大于 `7` 的右限 `8`。两次都失败，`7` 的左右孩子都给 `null`，`7` 完整了，这才回去和 `5` 建立父子关系，`7` 成为 `5` 的右孩子。

然后 `5` 整个完了，再跟父亲 `8` 建立关系，`8` 的左孩子完成。

接着处理值 `10`。它刚才试 `7` 的左右孩子都失败了，那现在该试谁了？试 `8` 的右孩子。`10` 没有超过 `8` 的右上限，可以，创建 `10`。下一个值 `12`：能不能当 `10` 的左孩子？不行，超过了 `10` 的左孩子限制；能不能当 `10` 的右孩子？可以。于是 `10` 的左孩子填 `null`，`12` 被创建出来，将来作为 `10` 的右孩子。`10` 完整了，再跟 `8` 建立父子关系。整棵树完成。

> **提示**：你现在看出来了吗——这种解法里，树的节点刚开始是**散**的，是后来一点一点拼凑起来的。值先在树里一路往下试，等到它能站住脚的那个位置，才把对应的节点创建出来，然后回头补父子关系。这一点和顺序插入"边走边建"的感觉完全不一样；理解了这个差别，后面的代码就好写了。

#### 上限怎么设，代码怎么写

这个过程手工看是有点绕，但代码比想象中简单。

因为要递归，所以专门写一个递归函数。方法名还叫 `insert`，叫什么无所谓。参数两个：`preorder` 数组直接作为方法的参数，因为整个递归过程中要访问数组里的元素，都得靠它；第二个是 `max`，就是我们刚才反复提到的那个上限——它可能是左孩子上限，也可能是右孩子上限，取决于调用的时候传的是谁。

返回值分两种情况：满足上限条件，就把节点创建好返回；超过上限，就不创建新节点，返回 `null`，将来作为上一层节点的孩子。还有一点，即使节点创建出来了，返回之前也得先把这个节点的左右孩子递归处理完整，才能返回它。

```text
insert(preorder, max)
 ├─ i == preorder.length   → return null        （数组取完了）
 ├─ value > max            → return null        （坐不上这个位置）
 └─ 用 value 创建节点
      ├─ i++                                     （先取下一个值）
      ├─ node.left  = insert(preorder, value)     （左限 = 当前值）
      ├─ node.right = insert(preorder, max)       （右限 = 传下来的 max）
      └─ return node
```

递归函数里要依次取到 `8`、`5`、`1`、`7`、`10`、`12` 这些值，怎么取？这里不是一个特别优雅的写法，但我用着方便：我定一个全局变量 `i`，从零开始，每次递归时从 `preorder` 里按 `i` 取到当前要处理的值 `value`。如果节点将来创建好了，就让 `i` 加加——从零加到一，下一个处理的就是 `5`，以此类推。

什么时候结束这个递归？当 `i` 自增到数组长度就该退出了。比如数组是 6 个元素，`i` 等于 6 了，已经到头了，这时候结束递归。

```java
private int i = 0;

public TreeNode bstFromPreorder(int[] preorder) {
    return insert(preorder, Integer.MAX_VALUE);
}

public TreeNode insert(int[] preorder, int max) {
    // 递归的出口：数组已经取完
    if (i == preorder.length) {
        return null;
    }

    int value = preorder[i];

    // 超过上限，坐不上这个位置，返回 null 作为上一层节点的孩子
    if (value > max) {
        return null;
    }

    TreeNode node = new TreeNode(value);
    i++;
    node.left = insert(preorder, value);
    node.right = insert(preorder, max);
    return node;
}
```

**上限怎么定，对着图来看。** 假设我当前处理的节点是 `8`：`8` 的左孩子上限是谁？就应该保持当前的值 `8`，因为左孩子当然要小于 `8`。那 `8` 的右孩子上限呢？保留 `8` 自己的上限 `max` 就行——此时 `8` 是根，它的 `max` 是 $+\infty$，所以右孩子上限也就是这个 `max`。

那处理到 `5` 的时候为什么右限变了？因为递归到 `5` 时传下来的 `max` 已经是当时 `8` 的左孩子上限（也就是 `8`），所以对于 `5` 来讲，只要保持上一次的 `max` 不变就 OK 了。

最外层第一次调用时，`preorder` 原样传过去，最开始这个上限——也就是 `8` 的上限——设成正无穷大。

> **注意**：这道题没有边界条件上的麻烦，它的取值不会超过正整数的最大值，所以放心传一个 `Integer.MAX_VALUE` 就行，不用再考虑溢出。

> **易错点**：代码里这个 `i++` 的**位置**要注意，它必须放在两次递归调用**之前**。能不能挪到后面去？不能。我们处理左右孩子的时候，是希望 `i` 先加加，然后到整个前序遍历数组里找到下一个值，看看它能不能充当当前节点的左孩子或右孩子。要找到下一个值，你得先让 `i` 加加，它才能自增到下一个位置。所以 `i++` 不能放后面。

跑一下测试用例，通过。它相对于我们第一种解法来讲，时间复杂度要更低，能达到 $O(n)$；上一种解法是大 $O(n \log n)$。所以上限法在时间复杂度上更为优秀一些。

### 顺着分界线切下去：分治法

最后用**分治法**再解一遍这道题。

#### 前序结果里到底藏着什么

先观察前序遍历的结果里有什么规律——换个说法，能不能从前序遍历的结构里，区分出来谁是根、哪些节点属于左子树、哪些属于右子树？

可以，而且非常清楚：

- 前序遍历的第一个元素肯定是根节点。我们这里根节点是 `8`，很轻易就找到了。
- 比 `8` 小的那些就是它的左子树：`5`、`1`、`7`。
- 比 `8` 大的那些就是它的右子树：`10`、`12`。
- 而且左右子树在这个序列里肯定是**连续**的。因为前序遍历是"根 → 左 → 右"这个顺序，根值完了之后，肯定先连着一段属于左子树的，再连着一段属于右子树的。

这样我们就用一次划分，把根、左子树、右子树区分开了。但是，光凭这一次区分，还不能确定整棵树最终的样子。所以我们**递归地采用同样的算法**，继续把它的左子树做类似的拆分。

把 `5 1 7` 拿来再拆一次：它的根是 `5`；比 `5` 小的 `1` 是它在 `5 1 7` 里的左子树；比 `5` 大的 `7` 是它的右子树。

`10` 和 `12` 同理：这里的根就是 `10`，它没有比它小的元素，左子树将来就是个 `null`，右子树是 `12`。

整个区域是逐渐缩小的：刚开始区域里有 6 个元素，随着划分进行，它里面可能变成 3 个、变成 2 个、变成 1 个，直到区域内没有元素了。这个划分的过程可以画成这样：

```text
区间 [8,5,1,7,10,12]    根 = 8    index = 3
├─ 左区间 [5,1,7]         根 = 5    index = 2
│  ├─ 左区间 [1]           根 = 1    index = 3（越界 → 左子树为空）
│  └─ 右区间 [7]           根 = 7
└─ 右区间 [10,12]         根 = 10   index = 5
   └─ 右区间 [12]          根 = 12
```

（`index` 是这一次划分找到的分界线位置，也就是右子树的起点，`index - 1` 是左子树的终点。当左区间为空时，`index` 会一路走到越过区域末尾。）

直到区域内没有元素了，就相当于划分完了，这棵树长什么样也就一清二楚了。这就是分而治之的思想。

#### 代码实现

思想有了，看代码。函数名就叫 `partition`，分区的意思。返回值还是 `TreeNode`。它需要几个参数？

- 第一个，还是数组 `preorder`；
- 接下来还得告诉它将来要处理的一个**数据范围**，也就是刚开始处理整个数组，从索引 0 到数组长度减一，整个数组都是它的处理范围。所以需要 `start` 和 `end`。随着算法不断进行，这个范围会逐渐缩小：处理 `8` 的左子树时，范围就是从 `5` 到 `7`；处理 `10` 和 `12` 的右子树时，你也得知道它的索引从几开始、到哪结束。

**结束条件**其实很简单——当我这个范围内没有元素了，说明处理完了。随着处理的进行，范围内元素个数逐渐减小，什么时候 `start` 大于 `end` 了，就表示这个范围内没有元素了，返回 `null`。

**根怎么得到？** 很容易。每个区域它 `start` 起始的那个索引，是不是就对应着根？所以直接通过 `preorder[start]` 就得到了根节点的值，用这个值创建出根节点对象。

**分界线怎么找？** 根创建好之后，接下来要找出剩下的这些里面哪些是左子树的元素、哪些是右子树的元素。其实就找一条分界线就行——因为前序遍历的特点就是左子树这些是连着的、右子树这些也是连着的，所以只要找到第一个比根大的元素，就确定了左右子树的分界线。

怎么做？定一个 `index`，从 `start + 1` 开始找（`start` 已经知道是根了，不用找）。只要 `index` 还没到区域的末尾，就不断循环，每次循环 `index` 加加，把当前 `index` 指向的元素跟根元素比较。什么时候 `index` 指向的元素比根元素大了——比如找到 `10` 了——就退出循环。这时候退出时的 `index`，就是右子树的起点。

```java
public TreeNode bstFromPreorder(int[] preorder) {
    return partition(preorder, 0, preorder.length - 1);
}

public TreeNode partition(int[] preorder, int start, int end) {
    // 区间内没有元素了
    if (start > end) {
        return null;
    }

    // 区间起点的元素就是根
    int rootVal = preorder[start];
    TreeNode root = new TreeNode(rootVal);

    // 从根的下一个位置开始，找第一个大于根的元素作为分界线
    int index = start + 1;
    while (index <= end && preorder[index] < rootVal) {
        index++;
    }

    // 左子树区间：start + 1 到 index - 1
    root.left = partition(preorder, start + 1, index - 1);
    // 右子树区间：index 到 end
    root.right = partition(preorder, index, end);

    return root;
}
```

为什么返回值返回每个区间的根节点就够了？因为左子树 `[5,1,7]` 处理完之后，返回的是这个区间里的根节点 `5`，那么 `5` 就作为当前 `8` 这个节点的左孩子；同理，处理右子树 `10`、`12` 返回的是根节点 `10`，`10` 就作为 `8` 的右孩子。所以每次返回该区间的根节点就可以了。

简单测一下，测试用例没变，还是 `[8,5,1,7,10,12]` 和那棵树，比较结果为 `true`，至少这个测试用例没问题。同样可以把代码贴到力扣上运行，所得结果也是一样。

从时间复杂度上它要比方法二（上限法）稍逊一筹，跟方法一（顺序插入）是一样的，都是大 $O(n \log n)$。

> **提示**：分治法在每个区间里都要**线性扫一遍**找分界线，单次划分的开销跟区间长度成正比，所以它的整体表现跟树的形状有关——树越偏斜、需要反复扫描的区间越多，代价越大。表里这一格的 $O(n \log n)$ 可以理解成"与方法一同档"。上限法之所以能压到 $O(n)$，是因为它在那边每个值只被取用一次。

### 三种解法放在一起看

| 解法 | 核心动作 | 单个值要付出的代价 | 时间复杂度 |
| --- | --- | --- | --- |
| 顺序插入 | 每个值从根一路走到空位插进去 | 一次插入 $O(\log n)$ | $O(n \log n)$ |
| 上限法 | 给每个节点配左右上限，值先试位置、站得住再建节点 | 一次，取用即止 | $O(n)$ |
| 分治法 | 找分界线，把区间切成左右两半再递归 | 随所在区间长度变化 | $O(n \log n)$（与方法一同档） |

同一道题，同一份 `[8, 5, 1, 7, 10, 12]`。顺序插入最好想、最好写；上限法最绕，绕到你必须亲手走一遍"七为什么当不了一的孩子"才真正明白；分治法最贴合 BST 的定义本身——根、左、右，划分，再划分，直到区域为空。

## 从最近公共祖先到 AVL 树
> 对应块：BLK48 | 覆盖分集：P184-P187 | 块标题（分集名）：《基础算法-139-二叉搜索树-e07-最近公共祖》

### 235 题到底在问什么

先来看一道题，力扣 235：给你一棵二叉搜索树，再给你树中的两个节点，让你求出离它俩最近的一个公共祖先是谁。

题意先掰开说清楚，两点必须记住。

第一，这两个节点是确定存在于这棵树里的，你不用考虑找不到的情况。第二，题目里立刻就说明白了——**祖先也算它自己**。这一句很容易被漏掉。

我们拿这棵树来说：

```text
        6
       / \
      2   8
       \
        4
         \
          5
```

问 2 和 8。2 的祖先链是 2、6；8 的祖先链是 8、6。两条链的交集只剩 6，答案就是 6，没有别的选择。

再问 4 和 5。4 的祖先是 4、2、6；5 的祖先是 5、4、2、6。这么一数，2、4、6 全都是它们的公共祖先。可题目问的是**最近**的那个，所以答案是 4。2 和 6 虽也是公共祖先，但离得太远，就不算了。

> **结论**：这道题的难度全部集中在"最近"两个字上。公共祖先往往不止一个，我们要的是深度最大的那一个。

### 一条规律就把问题解决了

规律只有一条，非常干净：

> **当待查找的节点 p 和 q 处在某个节点的两侧时，这个节点就是它俩最近的公共祖先。**

先验证 2 和 8：2 在 6 的左边，8 在 6 的右边，一左一右分居两侧，所以 6 就是答案。

再看 4 和 5 能不能套同一条规律。第一步怀疑 6，但四和五都小于 6，都在 6 的左边，不满足；继续往下。第二步怀疑 2，四和五都大于 2，都在 2 的右边，还是不满足；再往下。第三步怀疑 4——四自己就等于 4，五大于 4。一个正好命中，一个在右侧，这已经算"在两侧"了，所以 4 就是它们的最近公共祖先。

注意这里的"两侧"包含"其中一个正好等于当前节点"这种情形，这正是 4 能命中的原因。

### 把规律写成一个 while 循环

规律想明白了，代码就非常短。先把 `root` 复制给一个临时变量 `a`，让它代表"当前节点"，然后开始循环：**只要 p 和 q 还在 a 的同一侧，就继续往下找**；一旦分居两侧（或者其中一个等于 a），说明找到了，退出循环，此时的 a 就是答案。

怎么判断"同一侧"？两种写法，都写成条件：p 的值小于 a 的值、并且 q 的值也小于 a 的值——这表示它俩都在 a 的左侧；或者 a 的值小于 p、同时 a 的值也小于 q——这表示它俩都在 a 的右侧。

至于往哪边走，循环体内不必把 p 和 q 都跟 a 比较一遍，**只看 p 就够了**：既然能进这个循环，就说明 p 和 q 同时小于 a 或者同时大于 a，那 p 在哪一侧，q 就一定跟着在哪一侧。

```java
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    TreeNode a = root;
    while ((p.val < a.val && q.val < a.val) || (p.val > a.val && q.val > a.val)) {
        if (p.val < a.val) {
            a = a.left;
        } else {
            a = a.right;
        }
    }
    return a;
}
```

最后在构造好的那棵树上跑两组：一组 p、q 分别是 2 和 8，打印出 6；一组是 4 和 5，打印出 4。两个结果都对，这道题就算通过考验了。

> **易错点**：不要一上来就去遍历整棵树、求两条根到节点的路径再找交点。一条比较链就能走下来，没必要把简单题做复杂。

### 不平衡的二叉搜索树，查询会塌成什么

二叉搜索树有个绕不开的问题：它长得不平衡的时候，查询效率会不会受影响？

会。我们来看这张图：

```text
    4
   /
  3
 /
2
/
1
```

想查 1，就得从根节点开始一路向左走、再向左转，四个元素比较了四次才找到——比较次数跟树里的元素个数一样多。正常的二叉搜索树时间复杂度能做到 $O(\log n)$，可一旦出现这种不平衡，最坏情况下就退化成了 $O(n)$。

解决办法叫**旋转**。上面这棵树右旋一下，也就是顺时针转一下：

```text
      3
     / \
    2   4
   /
  1
```

原来的根 4 向右旋下去，原来的 3 向右旋上来当新根。再查 1 就轻松多了：先跟 3 比，发现比 3 小就往左找，比 3 大的那些元素根本不用比较，查询效率就恢复了。

> **结论**：旋转并不会破坏二叉搜索树的性质。旋完之后依然是"左边的都比根小、根右边的都比根大"，因为旋转只改变父子关系，不改变谁比谁大。所以二叉搜索树一旦不平衡，我们就可以通过旋转让它重新平衡。

### 尺子：高度差

问题来了：给你一棵二叉搜索树，我怎么知道它到底平不平衡？刚才那棵树大家一眼就能看出来，一条腿长一条腿没有，可随便给你一棵树，程序怎么判断？

规则很简单：**如果某个节点的左右孩子高度差超过了 1，就认为这棵树不平衡，才需要用旋转去修正它。**

高度按力扣的约定来算：叶子节点高度是 1，往上一层加一，节点 2 的高度就是 2，再往上是 3、4；而空节点（null）的高度约定为 0。

举例说明。上面那棵失衡的树，根节点的左孩子高度是 3，右孩子是 null，高度按 0 算，高度差 $3 - 0 = 3$，明显超过 1，不平衡，该旋。

但也有另一种情况：根节点高度是 3，左右孩子一个高 2、一个高 1，高度差是 1，那就不需要旋转，我们认为它仍然是平衡的。包括它下面那个节点，左孩子高 1、右孩子是 null 高 0，高度差也没超过 1，同样平衡。

那有人要问了，我硬要给它右旋一下会怎样？效率会变高吗？不会。查 1 还是比较一两次，查 4 反而从两次变成三次，一个好的一个坏的，没有本质提升。所以高度差没超过 1 的时候，旋转是没有意义的。

> **结论**：只有当某个节点的左右孩子高度差**超过 1** 时才旋转；不超过 1 一律不动。

### 什么操作会把平衡弄坏

导致二叉树失去平衡的情况只有两种：**新增**和**删除**。

看新增的例子。一棵树现在是平衡的：根的左孩子高度是 1，右孩子是 null 高 0，高度差没超过 1。我再往左边加一个元素，比如加个 3。新节点高度是 1，而原来那个左孩子的高度从 1 变成了 2，根的高度跟着变成 3。这时候从根来看，左子树高 2、右子树高 0，$2 - 0$ 已经超过 1 了，平衡被打破，得靠旋转修回来。

删除的例子同理。删掉右侧的 8 之后，根的高度变成 3，左孩子高度变成 2，右孩子高度归 0，左右高度差又超过 1，于是又得旋转。

那更新操作呢？比如找到某个节点把它的值改掉，会不会导致不平衡？不会。**只有新增和删除会让它失衡，修改不会。**

### AVL 树：把"自己会平衡"写进结构

铺垫做到这儿，就可以给定义了：二叉搜索树在插入和删除时都可能导致节点失衡，而我们如果能在插入和删除时通过旋转，让这棵二叉搜索树**始终保持平衡**，这种二叉搜索树就叫自平衡的二叉搜索树。

自平衡二叉搜索树有很多种实现，其中最著名的一种叫 **AVL 树**。为什么叫 AVL？因为它的发明者有两个人，一个人的名字里有 A 和 V 这两个字母，另一个作者的名字里有 L 这个字母，于是取了这两个作者名字里的这三个字母，拼成 AVL。

#### 节点类：多带一个 height

我们先把 AVL 的节点类定义出来，还是用静态内部类，就叫 `AvlNode`。因为 AVL 树本身也是一种特殊的二叉搜索树，所以二叉搜索树节点里该有的属性它都得有——`key` 用来比较大小、`value`，以及 `left`、`right` 这两个孩子引用。

除此之外还要多存一个东西：将来判断平衡与否要频繁用到每个节点的高度，所以把**高度也做成节点的一个属性**，类型是 int，字段名叫 `height`。一个节点刚创建出来时高度就是 1——这个说法沿用力扣的约定，我们就以它为准。

```java
private static class AvlNode {
    public int key;
    public int value;
    public AvlNode left;
    public AvlNode right;
    public int height;

    public AvlNode(int key) {
        this.key = key;
        this.height = 1;
    }

    public AvlNode(int key, int value) {
        this.key = key;
        this.value = value;
        this.height = 1;
    }

    public AvlNode(int key, int value, AvlNode left, AvlNode right) {
        this.key = key;
        this.value = value;
        this.left = left;
        this.right = right;
        this.height = 1;
    }
}
```

三个构造方法分别对应只传 key、传 key 和 value、四个参数全传。注意不管哪个构造方法，**高度都不需要你传，默认就是 1**。

#### 为什么还要单独写一个求高度的方法

有同学会问：高度不是已经做成节点属性了吗，为什么还要专门写个方法？

因为将来传进来的这个节点对象**有可能是 null**。你不能让一个 null 直接去点 `height` 吧？所以专门封装一个方法，目的是把 null 的情况顺手处理好。它返回节点的高度：先判断，如果这个 node 已经是 null 了，高度就是 0；不是 null，就通过它的 `height` 属性拿高度。

```java
private int height(AvlNode node) {
    return node != null ? node.height : 0;
}
```

> **易错点**：求任何节点的高度都走这个方法，不要图省事直接点属性。空指针就是这么来的。

#### updateHeight：高度到底怎么算

节点高度是"左右子树高度的最大值再加 1"，这个公式之前在求二叉树最大深度的时候其实见过一次，它们是一回事，当时的代码完全可以拿来用。

我们顺着插入的过程走一遍，比死记公式清楚得多。先插入 9，树里就一个节点，它保持创建时的高度 1 不动。接着插入 7，因为比 9 小，所以成为 9 的左孩子。7 自己的初始高度是 1，不用动，但它的父亲 9 就得更新了——更新成 2。再插入一个右孩子 10，这时候 9 的高度**反而不变**，仍然是 2。

为什么不变？因为 9 的左右子树高度都是 1，取最大值 1 再加一，还是 2。

再来一个跨度大一点的。继续插入 5，它应该成为 7 的左孩子。5 的高度是 1；7 的高度更新成 2（它的两个孩子里挑一个高度最大的，再加一）；9 的高度更新成 3（还是在左右孩子里挑最大的 2，加一）。

什么时候需要调用这个更新方法？**新增、删除，还有后面会看到的旋转之后**，这三种情况下高度都可能变，都得重新算一遍。

```java
private void updateHeight(AvlNode node) {
    node.height = Math.max(height(node.left), height(node.right)) + 1;
}
```

公式写成一行就是：

$$h(node) = \max\left(h(node.left),\ h(node.right)\right) + 1$$

方法没有返回值，参数就是一个节点对象，传进来之后先拿 `height` 方法求出左孩子高度、再求右孩子高度，取最大值加一，最后把这个结果更新回节点的 `height` 属性。因为左孩子可能是 null，所以这两处高度必须调 `height` 方法来求。

#### balanceFactor：平衡因子

接下来是判断平衡最核心的一个方法：求某个节点左右子树的高度差。

这里要引入一个新名词，叫**平衡因子**，英文是 balance factor——balance 是平衡，factor 是因子。定义非常简单：**一个节点的左子树高度，减去它的右子树高度，所得结果就是它的平衡因子。**

方法名叫 `balanceFactor`，取前两个字母简称 bf，返回一个整数值，参数还是节点对象。

```java
private int balanceFactor(AvlNode node) {
    return height(node.left) - height(node.right);
}
```

一样地，这里必须调 `height` 方法，因为左右子树都有可能为 null，绕开这个方法就会出 none 的问题。

### 平衡因子的返回值怎么读

这个方法将来返回的取值就那么几种，读懂它的含义比背公式重要。

```text
            6
          /   \
         2     8
          \
           4
            \
             5
```

回到这棵树来看。节点 4 的左子树高度 1、右子树高度 1，$1 - 1 = 0$，零表示左右等高，肯定平衡。节点 2 的左子树高 1、右子树高 2，$1 - 2 = -1$，它同样是平衡的，因为高度差并没有超过 1。如果节点 4 的左子树高 2、右子树高 1，那就是 $2 - 1 = 1$，也还是平衡的。

所以结论是：

| 平衡因子取值 | 含义 | 是否平衡 |
| --- | --- | --- |
| 0 | 左右子树等高 | 平衡 |
| 1 | 左子树比右子树高一层 | 平衡 |
| -1 | 左子树比右子树矮一层 | 平衡 |
| > 1 | 左边太高 | 不平衡，需要旋转 |
| < -1 | 右边太高 | 不平衡，需要旋转 |

不平衡的情况举两个例子：某个根节点左子树高 3、右子树高 1，$3 - 1 = 2$，大于 1，表示**左边高**；镜像过来，左子树高 1、右子树高 3，$1 - 3 = -2$，小于 -1，表示**右边高**。

> **结论**：看到返回值，脑海里就该立刻浮现出这棵树的样子——平衡还是不平衡，不平衡的话是哪边高。这个反应速度后面写旋转代码时会直接用到。

### 四种失衡情况（不止两种）

有同学会问：平衡因子大于 1 就是左边太高，小于 -1 就是右边太高，那不就是两种情况吗？做相应的旋转不就完了？

等我们举完例子你就明白了——**光有这两种，你既定不出旋转的方向，也定不出旋转的次数**。

先看一棵失衡的树。失衡节点是 5，它的左子树高度是 3、右子树高度是 1，$3 - 1 = 2$，特点很明显：**左边高、右边低**。那该往哪边旋？向右旋，把左边的高度降下来。参与旋转的就三个高亮节点：5 向右旋下去，3 代替它原来的位置成为新根。

这里有个细节得先说明白。3 上去、5 下来之后，5 就成了 3 的右孩子。可节点 4 原本已经是 3 的右孩子了，将来 3 不能有两个右孩子，所以 4 必须换个爹——让它变成 5 的左孩子。原来 4 的爹是 3，旋转之后爹变成 5。这个"换爹"操作我们后面还会再说。

可是另一棵同样左边高右边低的树就麻烦了。它的失衡节点是 6，左边高 3、右边高 1，$3 - 1 = 2$。照样做一次右旋：红色节点旋下去，黄色节点上来当新根，绿色节点换个爹。可结果呢——旋完之后左边高度变成 1，右边高度变成 3，失衡不但没解决，反而更极端了。

所以四种情况必须分出来。（顺手说一句，为了省去一个节点一个节点手输的功夫，我准备了一个小网页，上面几个按钮点一下就能直接生成对应的不平衡树，再点后面的按钮就是对应的旋转操作，一会儿我们直接拿它举例。）

四种情况的名字叫**左左、左右、右右、右左**。命名规则是：**第一个字描述失衡节点自己哪边高，第二个字描述它的左孩子或右孩子哪边高。**

#### 左左

名字里两个"左"。第一个左：失衡节点自己左边更高。第二个左：它的左孩子也是左边更高，或者等高。

对应到我们先前那棵失衡的树：失衡节点就是 5，其他节点都是平衡的（叶子节点不用看；节点 2 左高 1 右高 0，没超；节点 3 左高 2 右高 1，也没超）。只有 5 是左边高 3、右边高 1，差了 2。而它的左孩子 3，同样是左边更高。失衡节点和它的左孩子都是左边高、右边更低，这才叫左左。

#### 右右

和左左完全对称。第一个右：失衡节点右边更高。第二个右：它的右子树也是右边更高，左边更低。

也就是失衡节点和它的右孩子，大家都是右边高。

#### 左右

第一个左：失衡节点左边高。第二个右：**它的左孩子是右边高，左边反而更低**。

举例：失衡节点是 6，它的左边高、右边低；它的左孩子（也就是那个红色的节点）却是右边更高。一个是左边高，另一个是右边高，这就是左右。

#### 右左

和左右对称。第一个右：失衡节点右边高；第二个左：它的右孩子左边高。

举例：失衡节点是 2，右子树高 3、左子树高 1，高度差是 2；而它右边那一块是左边高。

四种情况汇总一下：

| 失衡类型 | 失衡节点 | 它的左/右孩子 | 特征 |
| --- | --- | --- | --- |
| 左左 | 左边高 | 左孩子左边高或等高 | 失衡点与左孩子同向偏左 |
| 左右 | 左边高 | 左孩子右边高 | 失衡点与左孩子反向 |
| 右右 | 右边高 | 右孩子右边高或等高 | 失衡点与右孩子同向偏右 |
| 右左 | 右边高 | 右孩子左边高 | 失衡点与右孩子反向 |

这四种后面代码里都会用到，大家先自己在纸上把这四种形状分析清楚。

### 四种情况分别该怎么旋

结论直接给：左左一次右旋就够，右右一次左旋就够，中间的左右和右左都得**两次旋转**。

- **左左**：失衡节点和左孩子都左边高，对整个左左子树做一次右旋就恢复平衡。
- **右右**：与它对称，一次左旋就能恢复平衡。
- **左右**：先让左子树向左旋，再让失衡节点向右旋。看图最直观——先让左子树往左旋，四这个节点换上来，旋完之后它就变成了左左的情况，然后再整体向右旋一次，就恢复平衡了。
- **右左**：先让右子树向右旋，再让整个失衡节点向左旋。那棵树里就是右边这块先向右旋，四上来六下去，然后再让整个失衡节点二向左旋，同样能恢复平衡。

| 失衡类型 | 恢复方式 |
| --- | --- |
| 左左 | 一次右旋 |
| 右右 | 一次左旋 |
| 左右 | 左子树先左旋，失衡节点再右旋 |
| 右左 | 右子树先右旋，失衡节点再左旋 |

### 本讲提到的题目

**题目（力扣 235）**：给定一棵二叉搜索树和其中两个节点 p、q，求它们最近的公共祖先。（注意祖先包含节点自身。）

**解析**：依据是"p、q 分居某个节点两侧时，该节点即为其最近公共祖先"这条规律。设当前节点为 a，只要 p 和 q 同时小于 a，或者同时大于 a，说明它俩还在同一侧，答案不在 a，继续往下走；走到 p、q 一左一右，或者其中一个正好等于 a 的时候，a 就是答案。循环体内只用比较 p 一个节点即可确定往哪边走。

**答案**：对开篇那棵树，`lowestCommonAncestor(root, 2, 8)` 返回 **6**；`lowestCommonAncestor(root, 4, 5)` 返回 **4**。
