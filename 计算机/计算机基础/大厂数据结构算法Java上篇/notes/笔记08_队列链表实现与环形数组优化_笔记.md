# 队列：链表实现与环形数组优化

## 归并的非递归写法

### 三个指针的分工

* **归并非递归版本**

    * 把源数组分成左右两个各自有序的区间，用一个循环把它们并进结果数组；"先并左边、再并右边"的次序不再交给调用栈，而是交给循环自己维护。

    * 指针分工：
        * `i`：区间一当前待比较的位置，只有区间一的元素被取走时才动。
        * `j`：区间二当前待比较的位置，只有区间二的元素被取走时才动。
        * `k`：结果数组下一个空位的下标，每写入一个元素就动。
        * `mid` 与 `right`：分别是区间一的右边界与整个源数组的右边界，全程固定不动，作用是随时告诉我们"走到头了没有"。

    * 循环体只有一句话：比较两个待比较元素，**小的那个写进结果数组**，被写走的那个指针和 `k` 各往后挪一位。

    * > **结论**：每一步只会有一个指针往前挪，因为只会有一个元素被写走——这是归并最核心的不变式。

### 循环退出与对称收尾

* **收尾补偿**

    * > **结论**：循环退出只可能是因为区间一被搬空（`i > mid`）或者区间二被搬空（`j > right`），两个区间至少有一个已被搬空。

    * 区间一被搬空：把源数组从 `j` 开始的剩余部分整段复制进结果数组，长度 `right - j + 1`。
    * 区间二被搬空：把源数组从 `i` 开始的剩余部分整段复制进结果数组，长度 `mid - i + 1`。
    * 两段补偿代码结构一模一样，差别只在起点和长度。

    > **易错点**：循环只处理"两个区间都还有货"的情况，这一步做完至少有一个区间是空的，剩下的元素必须由循环后的补偿逻辑收尾。少了这一步，结果数组会少一截，而且只在"两个区间长度不一样"时才暴露，属于最容易漏测的情况。

### 与递归版的差异

* **签名、边界与复制**

    * 非递归版本比递归版**少一个参数**：递归版把结果数组的写入下标当成方法参数一路往下传，非递归版里它只服务于这一次合并，收成方法内局部变量、初值给 `0`。

    > **易错点**：循环条件必须写 `while (i <= mid && j <= right)`，用 `<=`。`mid` 和 `right` 本身都是**有效元素**，不是"下一个空位"，写成 `<` 会漏掉每个区间的最后一个元素。

    * 两个分支都要做的 `k++` 提到 `if/else` 结构外面，`k++` 就只出现一次；"两个分支都要做的公共动作"往上一层抽是划算的习惯。

    * 批量复制用 `System.arraycopy(src, srcPos, dest, destPos, length)` 而不是手写 `for` 循环：一是意图更清楚，二是数组本来就是连续内存，让底层一次搬完比逐个赋值快。

    * > **提示**：把两个版本摆在一起对，主要思路完全一样——递归版把"取较小值"交给调用栈去循环，非递归版把它交给一个 `while` 去循环，区别只在代码出现的位置。

## 队列的定义与接口

### 定义与操作限制

* **队列（Queue）**

    * > **定义**：以顺序的方式维护一组数据，向队列的一端添加数据（尾部 tail），从队列的另一端移除数据（头部 head）。

    * 现实对应物是排队买商品、排队做核酸——从队尾进来，从队头出去，规矩被固定死了。

    * 链表可以在任意位置插入、删除；队列只能在尾部插入、只能在头部移除。想从中间插队是要被所有人瞪的。

    ```text
    链表                          队列
    +------------------------+    +------------------------+
    | 可以在任意位置插入、删除  |    |  只能在尾部插入          |
    +------------------------+    |  只能在头部移除          |
                                    +------------------------+
    ```

    * > **结论**：队列比链表好实现——链表什么都要考虑，队列被死死限制在头尾两个口上，复杂情况全被挡在外面。

### 精简接口 Queue<E>

* **自定义 `Queue<E>`**

    * 后面会提供多种队列实现（基于链表的、基于数组的），先把接口定义出来，让不同实现都往它上面靠。

    * 不用 JDK 自带的 `java.util.Queue`：它继承的是 `Collection` 这个大接口，方法密密麻麻，全实现一遍太累，违背接口的单一职责原则。

    | 方法 | 动作 | 队列为空时 |
    | :--- | :--- | :--- |
    | `offer` | 提供元素，插到**尾部**，成功返回 `true`、失败（满）返回 `false` | — |
    | `poll` | 拉取头部元素并**移除** | 返回 `null` |
    | `peek` | 只**看一眼**头部元素，不移除 | 返回 `null` |
    | `isEmpty` | 判断队列是否为空 | 返回 `true` |
    | `isFull` | 检查队列是否已满 | — |

    * `offer` 和 `poll` 是一对：一个进一个出，分守两头。
    * `peek` 和 `poll` 的区别只有"移不移除"这一件事：`peek` 相当于队伍里探头看下一个是谁，`poll` 相当于把人叫出来办完事让他走。

## 链表实现队列：单向环形带哨兵

### 三个定语

* **单向、环形、带哨兵**

    * **单向**：节点里只有 `next` 指针，没有 `prev` 指针；省掉一个指针，也省掉一份同步维护的麻烦。
    * **环形**：链表末尾的节点不再指向 `null`，而是回过头来指向头，首尾相连成环。
    * **带哨兵**：有一个专门的头节点**不出现在数据里**，作用就一个——简化空链表时的添加和删除。没有哨兵，"链表为空"和"链表只有一个元素"是两种完全不同的处理分支；有了哨兵，这两种情况被拉平成了同一种。

### 字段与初始化语句块

* **LinkedListQueue 的属性设计**

    * 属性不凭感觉加，**看图倒推**：空队列时 `head` 与 `tail` 指向同一个哨兵节点，所以至少得有两个指针，哨兵的值给 `null`。

    * 环形链表要求 `tail.next` 指回头，可现在 `tail` 和 `head` 是同一个对象，等价于"哨兵的 `next` 指向哨兵自己"，与双向环形链表里的同一场景一致。

    > **易错点**：`tail.next = head` 这一句**没法在字段声明处写**。写它的时候，头节点对象可能根本还没被创建出来，必须放到对象创建完成之后的地方去执行。

    * 把哨兵与环的接线抽到**实例初始化语句块**（一对大括号）里，无参构造和有参构造共用这段公共代码。

    ```java
    public class LinkedListQueue<E> implements Queue<E>, Iterable<E> {

        // 头节点指针，始终指向哨兵
        private final Node<E> head;
        // 尾节点指针，初始与 head 指向同一个哨兵
        private final Node<E> tail;

        private int size;      // 当前节点数
        private int capacity;  // 队列容量上限

        // 哨兵与环的接线：无参构造和有参构造都要用，抽成初始化语句块
        {
            this.head = new Node<>(null);
            this.tail = this.head;
            this.tail.next = this.head;
        }
        ...
    }
    ```

    > **易错点**：用初始化语句块的前提是被赋值的字段**不能在构造方法体里再赋一次值**。Java 的执行顺序是"字段初始化 → 初始化语句块 → 构造方法体"，语句块执行时构造方法体还没跑，所以 `head`、`tail` 必须在这两个阶段完成赋值，构造方法体只留给 `capacity` 这类由参数决定的字段；否则语句块里的 `this.tail` 还是个 `null`。

    * 实现 `Iterable<E>` 不是必须的，加上纯粹是为了将来迭代和测试方便。

### 泛型节点 Node<E>

* **泛型的两个好处**

    * 可以用 `null` 了：节点值之前一直是 `int`，用 `int` 没法表示"没有值"这种特殊情况，而"不存在"是需要被表达出来的——队列为空时 `poll` 和 `peek` 都要返回 `null` 来表示"没东西可拿"，没有泛型这条路走不通。
    * 泛型能代表更多类型：不光是整数，小数类型可以，自定义的 `student` 类型也可以。

    ```java
    private static class Node<E> {
        // 单向链表，所以只要一个 next
        private Node<E> next;
        // 这一回 value 可以是任意类型了
        private E value;

        public Node(E value) {
            this.value = value;
        }
    }
    ```

### offer：只改三个指针

* **尾部插入**

    * 只能从队尾排进来；整个插入过程**一共只改动三个指针**：
        * 旧尾巴的 `next` 指向新节点（空队列时旧尾巴就是哨兵本身，这一步就是"哨兵的 `next` 指向新节点"）。
        * 新节点的 `next` 指向头——新节点成了新尾巴，环形要求尾巴回到头；**如果链表不是环形的，尾巴的 `next` 指向 `null` 就行了**，正因为是环形才必须回头。
        * `tail` 指向新节点，新节点正式成为队尾。

    ```text
      插入前（空队列）              插入后（队列里只有一个 1）

      head ═►[哨兵]◄═ tail          head ═►[哨兵] ──► [1] ◄═ tail
             ⇕ self                        ▲              │
             next 指自己                   └──────────────┘
    ```

    * 加上容量后，`offer` 必须在添加**之前**做一次满员检查：`if (isFull()) return false;`，满了直接失败，后面的建点与接线全部终止。

    * 从尾部插入的队列，元素顺序与插入顺序一致；连调五次 `offer` 塞进 `1 2 3 4 5`，顺序完全符合预期。

### poll：被删节点可能正好是尾巴

* **头部移除**

    * 取出 `head.next` 节点的值并把它删掉，做法就是让哨兵的 `next` 直接指向它的下一个节点，等于把它跳过去。

    ```text
      poll 之前                poll 之后

      [哨兵] ──► [1] ──► [2]   [哨兵] ──────────► [2]
         ▲                                ▲
         └──────── head                   └─ head.next 直接跳到 2
    ```

    * 队列只剩一个节点时，`head.next = first.next` 执行完哨兵的 `next` 又指回哨兵自己，队列确实空了；但 `tail` 仍指着那个已被删掉的节点，指针悬空，`isEmpty()` 也会误判，**必须把 `tail` 重新拉回哨兵**。

    * 多于一个元素时删掉头节点，尾节点根本没动，`tail` 不用管。

    > **易错点**：判断条件是"**被删除的节点 `first` 等于 `tail`**"，而不是"队列里只剩一个元素"。写成后者还得额外维护一个计数，很麻烦；写成前者只多一个判断，而且语义上更准确——**尾节点被删了，尾指针就得重置**。

    * 往队列里加 `1 2 3 4 5`，连续五次 `poll` 依次返回 `1 2 3 4 5`；**第六次再调用时队列里已经没有元素，返回 `null`**。

### peek 与 isEmpty

* **只看不取与判空**

    * `isEmpty` 不用额外记状态，**看两个指针就行**：空时 `head` 与 `tail` 都指向哨兵、两者相等；加入 `1`、`2` 之后两者不相等。所以两者不相等就表示队列非空。

    * `peek` 判空后返回 `head.next.value`；空队列返回 `null`。加一个节点 `1` 后返回 `1`，再加一个节点 `2` 后返回的**还是 `1`**，因为 `2` 在后面、队头没动。

    > **易错点**：`isEmpty()` 判空之后再取 `head.next.value`，顺序不能反。空队列里 `head.next` 是哨兵自己，哨兵的 `value` 恰好也是 `null`，结果"碰巧"对，但那是巧合不是逻辑。**判空这一步是显式的契约，不要指望它自己碰对。**

### 迭代器

* **从 `head.next` 开始走**

    * 迭代指针初值取 `head.next`，因为**哨兵本身不参与迭代，它不是数据**。

    * 环形链表没有 `null` 可判断，终止条件是"当 `p` 又指向哨兵的时候，说明走完一圈了"，即 `hasNext` 返回 `p != head`。

    * `next()` 先把指针所在节点的值记下来返回，再让指针向后走一步（`p = p.next`）；指针同样要声明成泛型。

### 容量上限

* **size 与 capacity**

    * 光靠现有的 `head` 和 `tail` **判断不出满没满**，所以要加两个 `private` 属性：

    | 属性 | 含义 | 变化 |
    | :--- | :--- | :--- |
    | `size` | 当前节点数 | `offer` 时 `++`，`poll` 时 `--` |
    | `capacity` | 队列容量上限 | 固定不变 |

    * 无参构造把 `capacity` 设成 `Integer.MAX_VALUE`，表示容量不受限制、尽可能往里放；有参构造以使用者指定的值为准。

    * `offer` 里不要手写 `size == capacity`，直接换成 `isFull()` 的调用；判定规则是 `size == capacity` 时即已满。

    * 容量为 `3` 的测试：加 `1 2 3` 没问题，再 `offer(4)`、`offer(5)` 被 `isFull()` 拦下返回 `false`，`4`、`5` 根本没被真正加入，最终队列元素期望值仍是 `1 2 3`。

## 环形数组

### 定义与价值

* **环形数组（circular array）**

    * > **定义**：物理上仍然是普通的线性数组，只是让索引在使用时可以循环回绕，从而在逻辑上构成一个环；大小固定、首尾相连。

    * 有效索引范围照旧（`0 1 2 3 4`），走完 `4` 之后下一个不是 `5`，而是绕回 `0`；所谓的"环"完全是程序在控制，内存布局没有变。

    ```text
            索引:   0    1    2    3    4
                  ┌────┬────┬────┬────┬────┐
                  │    │    │    │    │    │
                  └────┴────┴────┴────┴────┘
                    ↑                    │
                    └────────────────────┘
                      走完 4，下一步又回到 0
    ```

    * 索引会自动绕回来，**越界这个问题就不存在了**，根本不用写那句"如果超过长度就归零"的判断。

    * 它毕竟还是数组，能充分利用**局部性原理**、吃到 CPU 缓存的红利，访问速度比链表快得多，这个优点被完整保留下来。

    * > **结论**：环形数组特别适合实现**有界队列**，ring buffer 也是同一个套路。

### 相对普通数组省掉的搬运

* **头尾不必钉死在索引 0**

    * 普通数组实现队列无非两个操作：从尾部入队、从头部出队。入队随便找个空位放进去，时间复杂度 $O(1)$，完全可以接受。

    * 出队就难看了：头必须在索引 0，移走 `a` 后 `b` 要占掉它的位置，`b` 之后所有元素都得跟着往前平移一格，一共 $n$ 个元素全动，时间复杂度直接飙到 $O(n)$。

    * 环形数组里**任意一个索引位置都能当头，也能当尾**，起点和终点不再被钉死在零上；同样移走 `a`，其他元素一个都不用动，只要头指针往前指一格让 `b` 成为新头，元素原地不动，$O(1)$，数据一个字节都不用搬。

    > **易错点**：普通数组出队慢，根子不在"数组"这个结构上，而在"头尾固定"这个约定上——是约定僵住了，不是数组慢。

### 下标绕回公式

* **取模落点**

    * > **结论**：环形数组任意一步的落点，等于"当前位置加步数"再对数组长度取模。

    $$(\text{当前位置} + \text{前进步数}) \bmod \text{数组长度}$$

    * 长度 5、当前位置 3 往前走两步：先按普通方式加得 $3 + 2 = 5$，再拿 5 除以 5 看余数，余数是 **0**，这就是正确的落点。
    * 换成前进三步：$3 + 3 = 6$，$6 \div 5$ 的余数是 **1**，与图对得上。
    * > **提示**：公式本身简单，但得知道它是怎么来的；后面每一处求模都用它。

### 判空与判满

* **判空**

    * 入队是往 `tail` 指向的位置塞一个新元素，然后 `tail` 往前挪一格；出队是把 `head` 指向的元素移除，然后 `head` 往前挪一步。

    * > **结论**：`head == tail` 当且仅当队列为空；反过来只要两者不指向同一格，队列就非空。

* **判满：牺牲最后一个槽位**

    * 连续加入 `a、b、c、d` 后 `tail` 绕回索引 0，此时还能不能再加一个 `e`？加完之后 `tail` 前进到索引 1，**跟 `head` 重合了**——队列里明明装着五个元素一点都不空，却被前面刚定下的判空条件判成空，两个条件撞车。

    * 解法：**最后一个位置空着不存元素，专门留给 `tail` 指针用**。长度为 5 的数组，队列里实际只能装 4 个元素。

    $$(\text{tail} + 1) \bmod \text{数组长度} == \text{head}$$

    * 尾指针再往前走一步，落点与头指针重合就说明满了。

    * 这里有个细节：为求通用，**`tail + 1` 之后还得再对数组长度取模**。例子里长度是 5 就得模 5，不模的话 `tail` 在索引 4 时算出 5，而 5 压根不是合法索引。

    ```text
    长度 5，只装 4 个，索引 1 这一格永远空着给 tail

      [ a ][   ][ b ][ c ][ d ]
        ↑              ↑
        T              H

      tail 停在索引 1 时：(tail + 1) % 5 == 2 ≠ head，还没满
      tail 停在索引 2 时：(tail + 1) % 5 == 3 ≠ head，还没满
      ...
      tail 停在索引 0 时：(tail + 1) % 5 == 1 == head → 满
    ```

    * > **提示**：空指针法只是比较常用的一种判空判满办法，先把它彻底搞明白，后面再介绍更多办法。

## 指针直接存索引的写法

### 字段与构造

* **ArrayQueue1 的结构**

    * 底层数组用泛型 `E[] arr`；头指针和尾指针将来就是数组里的索引位置，用 `int` 存就够了，两个指针初值都是 `0`。

    * 必须有一个带参构造，因为要通过它告诉队列的容量；参数传一个 `capacity`。

    * 实际数组大小是**期望容量加一**：`arr = (E[]) new Object[capacity + 1]`，因为环形数组必须专门留一个位置存 `tail` 指针、它不能存数据；期望存 4 个则实际数组大小为 5。

    * 创建出来的是 `Object` 数组，要做一次类型转换；不想让它报警告就加上 `@SuppressWarnings` 注解。

    ```java
    @SuppressWarnings("unchecked")
    public ArrayQueue1(int capacity) {
        // 环形数组要专门留一个位置给 tail 指针，所以实际大小是期望容量 + 1
        arr = (E[]) new Object[capacity + 1];
    }
    ```

### 各方法的实现

* **offer、poll、peek 与两个判定**

    * `isEmpty`：`return head == tail;`

    * `isFull`：`return (tail + 1) % arr.length == head;`

    * `offer` 先判满、满就 `return false`；没满则 `arr[tail] = e`，然后尾指针前进。

    > **易错点**：直接写 `tail = tail + 1` 不行——万一 `tail` 恰好是 4，加一不能加到 5 去，必须变成零，所以要写 `(tail + 1) % arr.length`，保证索引始终在有效范围内。

    ```java
    public boolean offer(E e) {
        if (isFull()) {
            return false;
        }
        arr[tail] = e;
        tail = (tail + 1) % arr.length;   // 关键：加一之后要模回长度
        return true;
    }
    ```

    * `poll` 先判空、空则返回 `null`；不空则取 `arr[head]` 作为返回值，返回前头指针前进一步，同样要取模。

    ```java
    public E poll() {
        if (isEmpty()) {
            return null;
        }
        E value = arr[head];
        head = (head + 1) % arr.length;
        return value;
    }
    ```

    * `peek` 与 `poll` 非常像，也是先判空、为空返回 `null`，区别只是**不动指针**：直接 `return arr[head];`。

### 迭代器

* **遍历也是一圈一圈的**

    * 迭代指针 `p` 的初值是 `head`；终止条件是 `p != tail`，追上 `tail` 说明没有元素了。

    * `next()` 取出 `arr[p]` 返回，`p = (p + 1) % arr.length`——加一有可能从 4 加到 5 去，所以 `p` 同样要做求模运算。

    * 测试用例基本是把链表实现那套改改，把实现类名换成环形数组版本，其余照旧。

## 指针只增、用时取模的写法

### 核心差异

* **指针不再保存计算结果**

    * 旧写法里 `head` 和 `tail` 代表的就是头和尾，**并且它们存储的就是真正计算后的那个索引值**；每次为了防止越界都跟数组长度做求模运算，求模之后的结果存回 `head`、`tail`。

    * 新写法让它们**不要存储这个计算结果**，只做不断递增的指针值：有新元素入队就让 `tail` 加一，有旧元素出队就让 `head` 加一；最终用到索引值的时候随用随算，什么时候用到什么时候去算。

    > **易错点**：新旧实现的唯一区别就是——旧实现里 `head`、`tail` 本身**存的就是索引**，新实现里它们**只是不断递增的整数**，必须先计算才能得到索引。搞混这一点，后面所有代码都会写歪。

    * 直接好处：**数组的长度就是容量，不需要再给 `tail` 预留一个空位、不需要加一**；而且这个数组以后不可能再被重新赋值，可以看作常量、用 `final` 修饰。

### 容量三走一遍

* **自增到越界就取模**

    * 假设数组容量是 3，最多存三个元素，索引为 `0 1 2`，`head` 与 `tail` 初值都是零。

    ```text
    第 1 次: tail = 0 → 存 a 到索引 0 → tail 自增成 1
    第 2 次: tail = 1 → 存 b 到索引 1 → tail 自增成 2
    第 3 次: tail = 2 → 存 c 到索引 2 → tail 自增成 3
    第 4 次: tail = 3 → 3 不能直接当索引用（有效索引只有 0/1/2）
                      → 3 % 3 = 0 → 存 d 到索引 0
    ```

    * > **结论**：`tail` 就是一个不断自增的整数，每次把它的结果跟数组长度求模，求得的余数作为索引；`head` 的处理完全类似。

### 各方法改写

* **索引现算，指针只做加一**

    * `offer`：满则 `return false`；没满则 `arr[tail % arr.length] = e;` 然后 `tail++`。

    ```java
    public boolean offer(E e) {
        if (isFull()) {
            return false;
        }
        arr[tail % arr.length] = e;   // tail 不是索引，用的时候现算
        tail++;
        return true;
    }
    ```

    * 新旧改动的区别一句话说清：新的实现里 `tail` 本身不是索引，要根据它算出索引再往那个位置赋值，然后 `tail` 加加；旧的实现里 `tail` 本身就是索引，能直接找到位置，但加完元素之后要把它**下一次**的索引（`tail + 1` 再模数组长度）算出来存回 `tail`。

    * `poll`：空则返回 `null`；不空则取出 `arr[head % arr.length]`，返回之后 `head++`，把当前元素跳过去。

    ```java
    public E poll() {
        if (isEmpty()) {
            return null;
        }
        E value = arr[head % arr.length];
        head++;
        return value;
    }
    ```

    * `peek` 与 `poll` 只差 `head++` 那一行，复制过来去掉即可；两行也可以合成一行。

    * `isEmpty` 还是老样子，`head == tail` 就是为空。

    * `isFull` 跟以前**不一样**了：尾巴减掉头就是从头到尾的距离，也就是放进去的元素个数，元素个数等于数组长度即表示满了。

    $$(\text{tail} - \text{head}) == \text{数组长度}$$

    ```java
    public boolean isFull() {
        return tail - head == arr.length;   // 尾巴减头，就是从头到尾的距离
    }
    ```

    * `iterator` 的 `p` 初值是 `head`，每次往前走一步；它**不直接对应索引**，也要根据 `p` 对数组长度取模才能算出索引位置，取到值返回后 `p++`；当 `p == tail` 时结束。

### 整数溢出暗坑

* **普通测试用例测不出来的问题**

    * `head` 和 `tail` 是两个整数值，算法里都是让它俩不断自增——**并没有考虑它自增超过正整数最大值会怎么样**。

    * 复现办法：把 `head` 直接顶到 `2147483640`（`int` 正整数最大值是 `2147483647`），建一个容量为 10 的队列循环十次 `offer`。按理 `0` 到 `9` 都能加进去、容量也是十，实际却报错了——他要访问索引 `-8` 的时候出错，数组里没有 `-8` 这一格。

    ```java
    @Test
    void testOverflow() {
        // 为了让这个测试用例能跑通，先把 head / tail 前面的 private 去掉
        ArrayQueue3<Integer> queue = new ArrayQueue3<>(10);
        queue.head = 2147483640;

        for (int i = 0; i < 10; i++) {
            queue.offer(i);
            System.out.println("tail = " + queue.tail
                    + ", 算出来的索引 = "
                    + Integer.toUnsignedLong(queue.tail) % queue.arr.length);
        }
    }
    ```

    ```text
    第 1~8 次：tail = 2147483640 … 2147483647
                索引 = tail % 10 → 0 … 7            全部合法

    第 9 次：  tail = 2147483647 + 1 = 2147483648
                int 装不下 → 由正变成负，溢出成 -2147483648
                -2147483648 % 10 = -8              ← 数组里根本没有 -8 这一格
    ```

    * 前八次都没问题：`tail` 从 `2147483640` 递增，算出来的索引都是 `0、1、2` 这些合法值；一直到**第九次** `2147483647` 再加一超过正整数最大值变成负数，负数求出来的索引也是负数，于是出错。

    > **易错点**：这是环形数组指针实现的经典暗坑。普通测试用例的 `head`、`tail` 自增不到那么大，暴露不出来，必须把它们的取值设得比较大才能挖出来；**只要指针是"一直自增、用时取模"的写法，就必须配套溢出处理，跑上亿次操作后必然崩，测试用例越普通越测不出来。**

### 无符号整数缺失与迂回解法

* **C 语言的解法与 Java 的绕法**

    * C 语言有 `unsigned int`，无符号整数存储时不含符号位，**只能代表零和正数**，范围从 `0` 一直到 $2^{32} - 1$；自增越过最大值后又从零开始，最终求模算出来的索引总是一个合法的值。所以用 C 语言只要把 `head`、`tail` 改成无符号 `int` 就完了。

    * Java 语言**没有无符号整数**，只能采用迂回的办法：`Integer` 包装类里的 `toUnsignedLong` 把原本超过 `int` 最大正整数之后、溢出变成负数的那个数，重新转换成能表示它的更大的 `long`。

    ```java
    arr[(int) (Integer.toUnsignedLong(tail) % arr.length)] = value;
    ```

    * 这里有两个细节：
        * **求余数之前先转成 `long`**。本来它会变成负数、超过范围，转成这个长整型后又能表示这个超大数字，用长整型再计算余数就不会出现负数的问题。
        * **Java 中数组的索引只能是 `int`、不能是 `long`**，所以最后还得转回 `int`，不转回来照样报错。

    * 所有涉及余数计算的地方都照这个样子改一遍：先转 `long`、求余、最后转 `int`；`head` 那一处用同样的方法包起来，迭代器遍历时也需要转一下。

    * 改完之后回到刚才那个测试用例，不再报错；因为每次把 `i` 加进去、从零加到九，最后打印出来 `0~9` 就对了。

## 位运算优化取模

### 二的幂取模的二进制规律

* **后 n 位即余数**

    * > **结论**：当除数是 $2^n$ 的时候，余数就是被除数二进制形式的**后 n 位**。

    * 前提必须钉死：除数只能是 2、4、8、16……这一串 2 的幂，除数一旦不是这个，规律立刻不成立。

    * 被除数 100、除数 8（$2^3$），商是 12、余数是 4；两侧二进制摆在一起，商的二进制 `1100` 严丝合缝地落在最前面四位，余数的二进制 `100` 落在最后三位。

    ```text
    100 = 1100100b
          ---- ----
          1100  100
           12    4
    ```

    * 再换一组验证：被除数 111、除数 8，商是 13、余数是 7；`111 = 1101111b` 的前四位 `1101` 正好是 13，末三位 `111` 正好是 7。换成除 16，余数变成 15，正是被除数的后四位。

    * 换个视角：除以 2 相当于右移一位，除以 4 相当于右移两位，除以 8 相当于右移三位；111 右移三位后剩下的 `1101` 是商，被移走的三位 `111` 是余数。所以"后 n 位是余数"和"除以 $2^n$ 等于右移 n 位"本来就是同一件事的两面。

### 用掩码抠出后 n 位

* **mask 即 2 的 n 次方减一**

    * 要保留被除数二进制的最后几位，就找一个前若干位全 0、后若干位全 1 的特殊数与它做按位与：零跟任意数做按位与结果为零，相当于把前几位清零；一跟原始数字做按位与则把原数字保留下来。

    ```text
    x    = 110  ->  1 1 0 1 1 1 0
    mask  =   7  ->  0 0 0 0 0 1 1 1
    result      ->  0 0 0 0 0 1 1 0   = 6
    ```

    * 这个特殊数跟除数的关系就是**除数减一**：除 8 用 7，除 16 用 15，除 32 用 31。

    ```text
    divisor   8 = 1000b     mask  8 - 1  = 0111     = 7
    divisor  16 = 10000b    mask 16 - 1  = 01111    = 15
    divisor  32 = 100000b   mask 32 - 1  = 011111   = 31

    x & 7    保留 x 的后 3 位  ->  x % 8
    x & 15   保留 x 的后 4 位  ->  x % 16
    x & 31   保留 x 的后 5 位  ->  x % 32
    ```

    * 所以求余数时不用除法，只要找到被除数的后 $n$ 位；把被除数跟 $2^n - 1$ 做一次按位与就能拿到。

### 替换环形队列里的三处求模

* **前提是数组长度为 2 的幂**

    * 被除数就是 `tail`、`head` 这些指针，除数就是数组的长度；只要能保证数组长度是 $2^n$，就可以把原来的求模运算替换掉。

    ```java
    // 原来的求模
    int index = tail % array.length;

    // 改成按位与
    int index = tail & (array.length - 1);
    ```

    * 不用加括号，因为减法运算优先级高，它是先做完减法再做前面的按位与；不放心的话用括号改一下优先级也行。

    * 改动是一举两得的：
        * **性能上**：按位与运算要比求模运算性能更高，求模运算本质上是除法。
        * **正确性上**：不用再考虑符号位问题了，按位与总是找被除数的后几位，跟最前面那个符号位没有关系，所以也不用考虑 `tail` 自增变成负数时的符号位问题。

    * 三处求模全部换成按位与：`tail` 的写入位置、`head` 的取用位置、迭代器遍历时指针 `p` 的换算。

### 溢出与判满的正确性

* **tail - head 依然算得对**

    * 既然 `size = tail - head` 等于数组长度时判满，那 `tail` 已经自增超过正整数最大值变成负数之后，这个判断还准不准？

    * 实验：`head` 取一个很大的数 1247483640，`tail` 已是最大正整数 `2147483647`，再让它往前走五步，肯定由正变负、打印出来确实是负数。先按正数看：47 亿 + 5 走到 52，再减 40 应该得到 12，也就是当前元素个数是 12，实际算出来的确实是 12。

    * 所以不用担心：**虽然 `tail` 超过了范围，但它跟原来那个数运算的结果没有超过范围就行**；它减过之后的差值没有超过正整数的范围，结果就是正确的。

    * 而 `tail - head` 的差值超不过 `2147483647`：Java 中数组的最大长度就是这个值，从数组尾部的指针减掉头部的指针，不可能超过数组长度。

    > **易错点**：`size = tail - head` 能一直算对，依据是**差值不溢出**，而不是 `tail` 自己不溢出；指针本身溢不溢出、溢成什么值，和这个判断准不准是两码事。

## 容量凑不齐二的幂

### 策略一：校验后抛异常

* **二的幂的判定**

    * > **定义**：一个正整数 $x$ 是二的幂，当且仅当 $x \mathbin{\&} (x - 1) == 0$。

    * 原因很简单：二的幂在二进制里是一个 `1` 后面跟一串 `0`，减一之后正好变成一串 `1`，零和一首尾互补、按位与自然是零。`8` 的二进制 `1000` 减一得 `7`（`0111`），按位与为零；`16` 与 `15` 同理也是零；反例 `14` 与 `13` 的零和一不是正好错开，结果是个非零的数。

    * 检查出来容量不是二的幂就抛一个异常，告诉使用者你传的参数不对，请传一个二的幂作为队列容量；策略一与策略二是**二选一**的。

    ```java
    // 必须加括号：先做按位与，再跟零比较
    if ((capacity & (capacity - 1)) != 0) {
        throw new IllegalArgumentException("capacity 必须是二的幂，也就是二的 n 次方");
    }
    ```

    > **易错点**：写成 `capacity & (capacity - 1) != 0` 是错的。`!=` 的优先级高于 `&`，会先去算 `capacity - 1 != 0`，再拿这个布尔值跟 `capacity` 做按位与，判断的就完全不是想要的东西了；必须用括号把按位与框住，让它先算完。

### 策略二之一：对数换算加左移

* **向上取整到最近且更大的二的幂**

    * 传的数不是二的幂就把它改成一个：传 13 就改用 16，传 22 就找它最接近、比它大的二的幂 32。

    * 找法：把目标数看成 $2^{4.xxx}$ 的形式，小数部分不关心，只要整数部分加一就是我们要的那个指数。问题因此转换成"要求二的几次幂"，即求以二为底的 30 的对数。

    ```text
    30 = 2^4.xxx
         |  |
         |  +-- 小数部分，我不关心
         +----- 整数部分 4，+1 得到 5，再求 2^5 = 32
    ```

    * Java 里要求以二为底的对数比较麻烦，因为它要求的是以十为底或以自然数为底的对数；做个转换即可。

    ```java
    int n = (int) (Math.log(capacity) / Math.log(2)) + 1;
    int newCapacity = 1 << n;
    ```

    * `Math.log(capacity) / Math.log(2)` 算出来是 4 点几，`int` 强制类型转换相当于舍弃小数部分，舍弃之后还得加一得到 $n$；30 代进去打印出来 $n$ 是 5，正是想要的。

    * 用位运算求 $2^n$：把 `1` 左移 $n$ 位即可——`1` 的二进制就是 `1`，左移一位得二（$2^1$）、两位得 `100`（$2^2 = 4$）、五位得 32。

    > **易错点**：这版代码有个小漏洞——传进来的数**本身就是**二的幂（比如 32）时，按这套逻辑会把它变成 64；这种情况下本就该保留原来的 32，不用再去找下一个。

    * 修法：把原始的数先减一，再求对数。减一之后"本来就整除"的情形落到 $n - 1$ 那一档，从而保证正确性。

    ```java
    int n = (int) (Math.log(capacity - 1) / Math.log(2)) + 1;
    int newCapacity = 1 << n;
    ```

### 策略二之二：位运算补位

* **对称的五步右移或运算**

    * 另一种方法完全用位运算达到"最近且更大的二的幂"的效果，可以看成一种二进制的计算技巧：先让 c 在原来的基数上减一，减完以后做右移位运算，右移之后跟原来的 c 做一次逻辑或；接下来把这段"右移加逻辑或"的代码复制四份，移位量变成右移 2 位、4 位、8 位、16 位，最后把 c 加一。

    ```java
    int c = capacity;
    c -= 1;
    c |= c >>> 1;
    c |= c >>> 2;
    c |= c >>> 4;
    c |= c >>> 8;
    c |= c >>> 16;
    c += 1;
    ```

    * 代码写出来很对称、很有规律，最后这个 c 就是要的结果；原始值 30 得到 32，原始值本身就是二的幂时也能保证正确性。

    * 把这段代码放进构造器，策略一的代码注释掉，只留选中的那一套（把传进来的 `capacity` 改名为 `c` 即可）。

    * 这样即使传过来的数不是二的幂，经过这一系列运算也会被改成一个二的幂，据此创建数组，后面计算索引的代码才能保证正确性。

## 二叉树层序遍历

### 二叉树节点与层序的含义

* **TreeNode 与层序**

    * 二叉树顾名思义就是树中每个节点最多有两个分叉；一个分叉、零个分叉都允许，只要孩子数不超过两个都可以称为二叉树。

    * `TreeNode` 用三个属性表示一个节点：节点值、左孩子、右孩子；提供按值创建和按值加左右孩子创建两个构造方法，并重写 `toString` 返回值的字符串，后面直接打印节点就能打出值。

    ```java
    class TreeNode {
        private final int value;
        private TreeNode left;
        private TreeNode right;

        public TreeNode(int value) {
            this.value = value;
        }

        public TreeNode(int value, TreeNode left, TreeNode right) {
            this.value = value;
            this.left = left;
            this.right = right;
        }

        @Override
        public String toString() {
            return String.valueOf(value);
        }
    }
    ```

    * 遍历就是把树中每个节点都过一遍；**层序遍历**就是过的顺序一层一层来。

    ```text
                  1
                /   \
               2     3
              / \   / \
             4   5 6   7

    第一层: 1
    第二层: 2, 3
    第三层: 4, 5, 6, 7
    ```

    * 上面这棵树按层序遍历出来的结果就是 `1 2 3 4 5 6 7`。

### 用队列一层一层地推

* **先入队根节点**

    * 第一层是已知的（把它叫 root、根节点），下面几层都得间接获得：先设一个空队列，把根节点先加入队列；处理完一层的节点后，把它下一层的节点再次加入队列，不断重复这个过程。

    * 每次从队列里取出一个元素并弹出，打印它，再看它有没有左右孩子，有就分别加入队列；队列为空时说明所有节点都处理过了，循环结束。

    ```text
    round   poll & print   offer (next level)     queue left
      1         1              2, 3            [2, 3]
      2         2              4, 5            [3, 4, 5]
      3         3              6, 7            [4, 5, 6, 7]
      4         4                --            [5, 6, 7]
      5         5                --            [6, 7]
      6         6                --            [7]
      7         7                --            []
    ```

    * > **结论**：先进先出的队列正好满足"一层一层"的要求——上一层还没处理完，下一层的节点就已经在队里排好了位置；入队时坚持先左后右，下一层出队时自然就是从左到右的次序，这正是层序的定义。

### 实现要点与队列选型

* **选链表队列的无参构造**

    * 队列元素类型就是树中的 `TreeNode`，用 JDK 自带的队列或自己写的实现都可以，这里用基于链表的实现。

    * 为什么不选基于数组的队列实现：链表队列没有容量限制，调无参构造时 `capacity` 是整数最大值、相当于没有容量限制；树的节点个数事先不确定，设置大了浪费内存、设置小了将来不够用。

    * 循环条件就是队列非空；每轮 `poll` 出队头节点直接打印（依赖重写的 `toString`），左孩子不为空才入队、右孩子同理。

    ```java
    LinkedListQueue<TreeNode> q = new LinkedListQueue<>();   // 无参构造：capacity = 整数最大值
    q.offer(root);                                            // 根节点先入队

    while (!q.isEmpty()) {                                    // 队列非空就还有下层节点没处理
        TreeNode n = q.poll();                                // 从队头取出本轮要处理的节点
        System.out.println(n);                                // 重写了 toString，直接打出值

        if (n.left != null) {                                 // 左孩子不为空才入队
            q.offer(n.left);
        }
        if (n.right != null) {                                // 右孩子同理
            q.offer(n.right);
        }
    }
    ```

    * 用数组队列也能做，只是树的节点个数事先不确定，链表队列没有容量限制更省心。
