# 浮动排版的前世今生：从图文环绕到被放弃的布局陷阱与清除闭合全解

我们在上一讲系统学习了 `display: inline-block`（行内块）模式转换。通过将块级盒子转换为行内块，我们确实能让多个盒子并排显示在一行中，还能给它们设置宽高。然而，上一讲末尾暴露出一个极其恶心的瑕疵——**由于 HTML 源码中的换行与空格会被解析为空白字符折叠，导致相邻的行内块盒子之间永远卡着一条去不掉的神秘缝隙**！为了干掉这个缝隙，我们不得不给父盒子声明 `font-size: 0`，再在子元素里把字号加回来。

这不禁让人追问：在 CSS 的漫长演进史中，难道就没有一种原生支持“同行紧凑排列、中间绝不留任何字符缝隙、还能自由设置尺寸”的技术吗？

有，而且这项技术统治了 Web 前端排版长达十余年之久——它就是**浮动（`float`）**。

但是，请大家务必在翻开这一讲的第一分钟记住我的一句定性：**浮动是一项在现代前端工程中正在被全面放弃、甚至被加速淘汰的过渡性技术！**

既然它已经被放弃了，为什么我们还要花一整节长文的篇幅把它掰开揉碎讲透？原因非常残酷：
1. **看懂祖传代码**：各大一线大厂（如小米、京东等）历经多年迭代的老旧业务线、历史模板中依然遗留着大量浮动代码；
2. **理解布局之痛**：只有亲身体会过浮动带来的“脱标”、“高度塌陷”和“到处擦屁股清除浮动”的痛苦，你才能真正领悟为什么后来的 Flex 弹性盒会被奉为前端救世主。

这一讲，我们就将完整还原浮动的前世今生，从它的设计初衷、野蛮滥用，到它引发的灾难及四大清除浮动方案，彻底解剖清楚！

## 1. 浮动（Float）的技术起源与最初使命

### 1.1 图文环绕排版：浮动诞生的唯一初衷

在 CSS 标准制定的最初岁月里，W3C 设计 `float` 属性压根就**不是为了做复杂的网页大骨架布局**！

它的唯一使命非常纯粹、朴素：**在长篇文字中插入一张图片，让文字能够像现代报纸、杂志排版那样，紧密地围绕在图片四周流淌，即“图文环绕效果”**。

```text
传统的图文环绕排版模型

┌──────────────────────────────────────────────────────────┐
│ ┌───────────────┐ 现代前端技术体系在过去数年间经历了极其 │
│ │               │ 深刻的变革。从最初的静态 HTML 展示，到 │
│ │   浮动图片    │ 如今高度工程化的单页面应用，每一次底层 │
│ │ (float: left) │ 规范的演进都在重塑开发者的工作流与思维 │
│ │               │ 模式。排版布局作为视觉呈现的基石，更是 │
│ └───────────────┘ 承担着将 UI 规范还原为真实渲染像素的关键│
│ 职责。文字顺畅地包围在图片下方继续流淌，形成统一视觉体验。│
└──────────────────────────────────────────────────────────┘
```
*图 1：浮动最初用于报刊杂志式的图文环绕效果*

### 1.2 语法规范与属性取值

浮动的语法极其精简，直接作用于需要浮动的目标元素本身：

```css
选择器 {
    float: 属性值;
}
```

| 取值 (Value) | 含义与排版行为 |
| :--- | :--- |
| `none` | **默认值**。元素不浮动，完全遵循常规标准文档流排版规则 |
| `left` | **左浮动**。元素向左侧浮动，紧靠父容器左边缘或前一个左浮动元素 |
| `right` | **右浮动**。元素向右侧浮动，紧靠父容器右边缘或前一个右浮动元素 |

### 1.3 图文环绕的极简代码验证

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
    <meta charset="UTF-8">
    <title>浮动的最初使命 - 图文环绕</title>
    <style>
        .news-box {
            width: 500px;
            border: 1px solid #e0e0e0;
            padding: 15px;
            font-size: 14px;
            line-height: 1.6;
            color: #333333;
        }

        /* 给图片施加左浮动，文字会自动避开图片并环绕其四周 */
        .news-box img {
            float: left;
            margin-right: 15px;
            margin-bottom: 10px;
            border-radius: 4px;
        }
    </style>
</head>
<body>
    <div class="news-box">
        <img src="https://via.placeholder.com/120x80" alt="新闻配图">
        在 CSS 技术标准确立之初，W3C 设计浮动属性的核心目的就是为了在文本段落中实现图文混排。只要赋予图片浮动属性，原本属于行内替换元素的图片就会向左停靠，右侧与下方的段落文本便会天然地环绕着图片的边缘顺滑展开，这便是浮动最本真的价值所在。
    </div>
</body>
</html>
```

## 2. 历史的选择与浮动布局的野蛮生长

### 2.1 早期开发者的发现：多块同行与零间隙

大约在二十年前的前端蛮荒时代，前端开发者们面对着只能从上往下垂直排布的块级 `<div>`，个个抓耳挠腮。突然有一天，某些“大聪明”开发者发现：
- 如果给普通的块级 `<div>` 加上 `float: left;`，原本独占一行的块级盒子竟然**全部神奇地挤到了同一行**！
- 更加让人惊喜的是：与 `inline-block` 那种带有顽固空白折叠间隙的技术相比，**浮动盒子与浮动盒子之间是严格贴死、零缝隙贴合的**！
- 不仅如此，浮动的盒子依然可以**自由设置确切的 `width` 和 `height`**！
- 甚至还能轻松做左右分栏：左边栏设置 `float: left;`，右边栏设置 `float: right;`，两端顶格对齐一气呵成！

这个在当时近乎完美的“意外特性”，让全球前端开发者欣喜若狂。于是，大家心照不宣地把 `float` 从原本的图文环绕小工具，直接绑上了重工业大布局的战车。在随后的十余年里，互联网上 95% 以上的多列网页骨架全部由浮动强行搭建。

### 2.2 浮动元素的核心表现特征

当一个元素设置了浮动之后，它会表现出以下一系列极具辨识度的特性：
1. **顶对齐同行排列**：浮动的元素会脱离普通流的行限制，多个同向浮动的元素会按照 HTML 中的书写顺序，紧挨着彼此在同一行内水平排列，且默认顶端对齐；
2. **贴靠边缘机制**：第一个浮动元素紧贴父容器的内边距边缘，第二个浮动元素紧贴第一个浮动元素的边缘，依次顺延；
3. **无缝紧贴**：盒子与盒子之间不存在任何代码换行产生的物理空白缝隙；
4. **空间不足自动折行**：如果一行内所有浮动盒子的总宽度超出了父盒子的可用内容宽度，放不下的浮动盒子会自动掉落到下一行，并紧贴最左侧（或右侧）重新排列。

### 2.3 浮动多列布局实战与数学间距推导

在真实项目中，设计师往往要求我们在固定宽度的容器中均匀排布固定列数的卡片。使用浮动排版，开发者必须进行极其严谨的“像素级数学心算”。

**实战场景推导：父盒子宽 600px，内部水平放置 3 个子盒子，盒子之间留有均匀间距**。

```text
浮动三列卡片间距推算模型

┌──────────────────────────── 600px ────────────────────────────┐
│ ┌──────── 190px ────────┐   ┌── 190px ──┐   ┌──────── 190px ────────┐ │
│ │         item 1        │   │   item 2  │   │         item 3        │ │
│ └───────────────────────┘   └───────────┘   └───────────────────────┘ │
│                          ▲               ▲                            │
│                      间距 15px        间距 15px                       │
└───────────────────────────────────────────────────────────────────────┘
  数学公式验算: (190px × 3) + (15px × 2) = 570px + 30px = 600px (严丝合缝!)
```
*图 2：浮动多列卡片的尺寸与外边距数学规划*

#### 间距推导法则：
1. 容器总宽：$W_{\text{total}} = 600\text{px}$；
2. 3 个盒子之间共有 $3 - 1 = 2$ 个空隙；
3. 设定每个盒子宽度为 $190\text{px}$，则 3 个盒子占宽 $190 \times 3 = 570\text{px}$；
4. 剩余可用总间距：$600 - 570 = 30\text{px}$；
5. 平均分配到 2 个间隙上：每个间隙宽度为 $30 \div 2 = 15\text{px}$。

### 2.4 致命细节：最后子元素的清除与伪类约束

根据上述推算，我们给每个小盒子设置 `margin-right: 15px;`。

> **易错点（现场翻车雷区）**：
> 如果你给所有的 `li` 都加上了 `margin-right: 15px;`，那么第 3 个盒子的右侧也会带上 15px 的外边距！
> 此时总占宽将变为：$190 \times 3 + 15 \times 3 = 570 + 45 = 615\text{px}$！
> 因为 $615\text{px} > 600\text{px}$，**超出了父盒子的承载极限，第 3 个盒子会当场掉下悬崖、换行到第二行**！

#### 工业级解决方案：
必须精确移除最后一个子盒子的右边距：
- **方案 1（单行固定场景）**：使用结构伪类 `:last-child`，明确指定最后一个子项的右外边距为 0：
  ```css
  .box li:last-child {
      margin-right: 0;
  }
  ```
- **方案 2（多行多列矩阵场景，如 6 个盒子排成两行三列）**：每一行的第 3 个盒子（即第 3、第 6、第 3n 个）都不能带右外边距！必须使用倍数伪类选择器 `:nth-child(3n)`：
  ```css
  .box li:nth-child(3n) {
      margin-right: 0;
  }
  ```

#### 完整演示代码：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
    <meta charset="UTF-8">
    <title>浮动多列卡片排版与边距清零</title>
    <style>
        * {
            margin: 0;
            padding: 0;
            box-sizing: border-box;
        }

        .box {
            width: 600px;
            margin: 50px auto;
            border: 2px dashed #999;
            list-style: none;
            /* 暂给父盒子写死固定高度，以避免塌陷（后文展开） */
            height: 330px; 
        }

        /* 核心：子盒子统一浮动与尺寸 */
        .box li {
            float: left;            /* 关键：左浮动 */
            width: 190px;
            height: 150px;
            background-color: #e3f2fd;
            border: 1px solid #2196f3;
            margin-right: 15px;     /* 均匀间隙 */
            margin-bottom: 15px;    /* 行间距 */
            text-align: center;
            line-height: 150px;
            font-weight: bold;
            color: #0d47a1;
        }

        /* 关键算法：每行第 3 个盒子（第 3n 个）彻底清空右外边距，防止掉落 */
        .box li:nth-child(3n) {
            margin-right: 0;
        }
    </style>
</head>
<body>

    <ul class="box">
        <li>卡片 1</li>
        <li>卡片 2</li>
        <li>卡片 3</li>
        <li>卡片 4</li>
        <li>卡片 5</li>
        <li>卡片 6</li>
    </ul>

</body>
</html>
```

## 3. 浮动的底层破坏者：脱标（脱离文档流）

上面的排版看似非常工整，但实际上它踩在了一颗巨大的技术地雷上。这颗地雷的根源，就是浮动的本质特征——**脱标（脱离标准文档流）**。

### 3.1 什么是脱标？“漂浮在空中不占地基”的物理模型

> **定义**：脱标（Out of Normal Flow），是指当一个元素被赋予浮动（或后文的绝对定位/固定定位）后，它将**彻底脱离原本在 HTML 标准文档流中所占据的物理空间位置**。

我们可以建立一个非常具象的三维物理空间直觉：
1. **地基平面（Z 轴 = 0）**：这是所有正常的标准流元素生活的地方，大家规规矩矩排队占座，一个萝卜一个坑；
2. **腾空平面（Z 轴 > 0）**：一旦某个元素被写上了 `float: left`，**它就像瞬间拥有了轻功一样，直接从地基上‘漂浮’了起来，向着用户的屏幕迎面扑来，悬浮在空中**！
3. **空间湮灭**：最可怕的是，当它漂浮起来之后，它在地面上原本占据的那个物理位置瞬间化为虚无，**它不再在原来的地基上占有任何尺寸空间**！

```text
浮动元素脱标（脱离标准流）物理空间剖析

【三维俯瞰视角】
   漂浮层 (Z轴升起) ──────> [浮动盒子 1 (float: left)]  (浮在空中，迎面扑来)
                                 │ (不占地基空间!)
                                 ▼
   地面基准层 (Z=0)  ──────> ┌────────────────────────┐
                             │ 标准流盒子 2 (无浮动)   │ <--- 发现前排空了，
                             └────────────────────────┘      直接向前钻到浮动盒子底下！
```
*图 3：浮动元素脱标后悬浮腾空与后续标准流元素钻底模型*

### 3.2 视觉覆盖灾难：标准流兄弟元素的被穿透与钻底

让我们看一段极具代表性的反常代码：
```html
<div class="box1">我是浮动盒子（粉色）</div>
<div class="box2">我是标准流盒子（天蓝色）</div>
```
```css
.box1 {
    float: left;
    width: 200px;
    height: 100px;
    background-color: pink;
}

.box2 {
    width: 300px;
    height: 150px;
    background-color: skyblue;
}
```

**运行结果**：
你根本看不到天蓝色的 `box2` 排在粉色 `box1` 的下面！
因为 `box1` 浮动腾空了，它在地基上的高度变成了 0。`box2` 作为常规流块级元素抬头一看：“咦？上面没人占地啊！”于是 `box2` 毫不客气地直接顶到了容器的最顶部，**整整大半个身躯硬生生钻进了粉色 `box1` 的屁股底下，发生了恶性的层叠重叠**！

## 4. 工业级灾难：父级高度塌陷与结构性崩塌

如果说仅仅是兄弟元素钻底，我们尚且能通过各种手段避开，那么浮动在大型项目中引发的最致命灾难，莫过于——**父容器的高度塌陷（Height Collapse）**。

### 4.1 为什么父级容器“绝不能写死高度”？

在前面的案例中，细心的同学可能注意到了：我们偷偷在 `.box` 父容器上写了 `height: 330px;`。

但在真实的工业级商业网站开发中，**我们几乎不可能、也绝对不能给容纳多项子列表的父盒子写死固定高度**！

以京东商城首页的“猜你喜欢”或者商品瀑布流展示区为例：
- 我们打开京东首页，商品列表到底有多少个商品？是 20 个？50 个？还是随着用户鼠标滚轮“拉呀拉呀拉，我是卖包的小行家，一直拉一直刷新”无穷无尽动态拉取？
- 今天搞大促运营配了 8 件推荐爆款，明天日常运营配了 12 件，后天活动结束只剩 4 件；
- **如果把父盒子的高度写死成 2000px**：当接口只返回 4 件商品时，页面底部会出现大片刺眼的丑陋空白；
- **如果把父盒子的高度写死成 500px**：当接口吐出 100 件商品时，后面的 90 多件商品全部溢出破裂！

> **工业级架构准则**：**最理想的容器设计，永远是‘父盒子不设高度，任由内部的子盒子根据内容自然撑开’！你有多少孩子，就把父亲撑多高！**

### 4.2 高度塌陷的物理过程推导

然而，当“父盒子不设高度（`height: auto`）”遇到“子元素全员浮动”，核灾难发生了：

```text
浮动引发的父级容器高度塌陷灾难

【理想状态：子元素为标准流，自然撑开父容器】
┌────────────────────────────────────────────────────────┐
│ 父盒子 .parent (不设高度，被两个标准流子盒子撑高到 200px) │
│ ┌──────────────────────┐  ┌──────────────────────┐     │
│ │ 子盒子 1 (高 200px)   │  │ 子盒子 2 (高 200px)   │     │
│ └──────────────────────┘  └──────────────────────┘     │
└────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────┐
│ 后续网页底部模块 .footer (安稳排在父盒子下方)           │
└────────────────────────────────────────────────────────┘

【现实灾难：子元素全部 float，父容器瞬时塌陷为 0】
父盒子 .parent 高度变为 0px ──> [------------------------] (地基完全空了!)
                                    │
                                    ▼ .footer 向上穿透顶上来！
┌────────────────────────────────────────────────────────┐
│ 后续网页底部模块 .footer ────┐                          │
│ │ [子盒子1 悬浮在半空]        │ [子盒子2 悬浮在半空]     │ <--- 浮动子项压在了
│ └────────────────────────────┴─────────────────────────┘      页脚的正上方，
                                                               页面彻底错乱变形！
```
*图 4：浮动导致父容器高度归零与后续页脚模块严重错位*

1. 父盒子 `.parent` 没写高度，其高度完全寄希望于子元素把它撑开；
2. 内部的子元素全部被写上了 `float: left;`；
3. 所有子元素全部**腾空脱标**，在父盒子的地基坐标系中，它们的占位空间全部归零；
4. 父盒子低头一看，内部空空如也，没有任何标准流内容来支撑自己，**父盒子的高度瞬间缩水塌陷为 0px**（若有边框则仅剩两条挨在一起的边框线）；
5. 紧随其后的网页下一个标准流大板块（比如重要的 `.footer` 网站底部版权栏）顺理成章地向上平移，**直接钻到了浮动子元素的底下，所有文字、图片彻底穿透重叠，整个页面版式当场爆裂瘫痪**！

## 5. 清除浮动（闭合浮动）的四种解决方案

面对高度塌陷这个巨大的梦魇，历代前端工程师与浏览器引擎展开了旷日持久的博弈，创造出了一系列“清除浮动”的工业方案。

> **核心认知澄清**：**所谓‘清除浮动’，绝不是把子元素的 `float` 属性删掉，而是通过特定技术手段，消除子元素浮动后对父容器高度及后续兄弟元素造成的恶劣影响，让父容器能够重新把浮动的孩子包裹住，在技术术语中它更准确的名字叫作‘闭合浮动（Clearfix）’！**

### 5.1 方案一：额外标签法（隔墙法 / 空 div 法）

这是浮动早期最朴素、最符合直觉的土办法。

**操作手法**：
在父容器内部、**所有浮动子元素的最后面**，强行插入一个空的块级标签（通常是 `<div>`），并给这个空标签赋予 CSS 属性 `clear: both;`：

```html
<div class="parent">
    <div class="float-box">浮动 1</div>
    <div class="float-box">浮动 2</div>
    
    <!-- 额外标签法：在最后一个浮动孩子后面强插一堵墙 -->
    <div class="clear"></div>
</div>
<div class="footer">网页底部</div>
```
```css
.clear {
    clear: both; /* 清除两侧浮动影响 */
}
```

> **机理剖析**：
> `clear: both;` 的底层规范要求该元素自身不能与任何前置浮动元素处于同一水平线，浏览器为了满足这一规则，强制把这堵“墙”推到了所有浮动元素的物理最底端。又因为这堵墙是一个**标准的普通流块级元素**，它成功撑开了父容器的底边，父容器的高度从而被奇迹般地复原了！

- **优点**：通俗易懂，书写直白；
- **致命缺点**：为了纯样式的修补，在 HTML 结构中凭空塞入大量没有任何语义价值的空 `<div>` 代码，严重污染了 DOM 树规范，现代工业开发中早已弃用。

### 5.2 方案二：单伪元素清除法（京东经典写法）

既然“额外标签法”的思路是正确的，唯一的问题是污染了 HTML，那我们能不能**利用 CSS 的伪元素（Pseudo-elements），在不用修改一行 HTML 的前提下，用纯样式动态在父元素最后造出一堵无形的‘墙’呢**？

答案就是——**单伪元素清除法**（京东商城、早期各大门户网站的标准规范）。

```css
/* 京东商城经典单伪元素清除浮动公共类 */
.clearfix::after {
    content: "";              /* 伪元素必须包含 content 属性，哪怕是空字符串 */
    display: block;           /* 核心：伪元素默认是 inline，必须转为块级元素方能撑起高度 */
    clear: both;              /* 核心：清除两侧浮动 */
    height: 0;                /* 防御性样式：确保无形墙高度不产生额外物理占位 */
    visibility: hidden;       /* 防御性样式：隐藏内容 */
}
```

> **使用方法**：
> 遵循“子不教，父之过”的工程哲学，哪个父盒子因为孩子浮动而塌陷了，直接在那个**父盒子**的 class 上挂上 `.clearfix` 类名即可：
> ```html
> <div class="parent clearfix">
>     <div class="float-box">1</div>
>     <div class="float-box">2</div>
> </div>
> ```

### 5.3 方案三：双伪元素清除法（小米经典写法）

小米商城（mi.com）等框架中广泛流行着一种更为完备的进阶版写法——**双伪元素清除法**。

它不仅在元素尾部闭合浮动，还在元素头部插入空桩，顺手解决了一个令前端极为头疼的连带 Bug——**父子盒子的外边距塌陷（Margin Collapsing）**：

```css
/* 小米商城经典双伪元素清除浮动公共类 */
.clearfix::before,
.clearfix::after {
    content: "";
    display: table; /* 关键：转为表格显示模式，天然阻断父子 margin 穿透穿透 */
}

.clearfix::after {
    clear: both;    /* 尾部负责闭合浮动、撑开父级高度 */
}
```

> **机理透视**：
> 1. `::before` 加上 `display: table`，将父元素与第一个子元素的外边距物理隔离开，彻底防范了“给子元素加 `margin-top` 却把父元素整坨向下推”的外边距穿透缺陷；
> 2. `::after` 加上 `clear: both`，稳稳地在底部把浮动孩子造成的高度塌陷闭合撑起。
> 犹如“前面关好大门，后面闭紧窗户”，严丝合缝，极为优雅。

### 5.4 方案四：overflow: hidden 触发 BFC 清除法

还有一种写法极其简练，在某些固定模块中被广泛运用：直接给塌陷的父容器添加一行代码：

```css
.parent {
    overflow: hidden;
}
```

> **深层原理（BFC 机制）**：
> `overflow: hidden` 的表层含义是“超出隐藏”，但更深层的技术事实是：**给块级元素设置 `overflow: hidden` 会促使该元素内部生成一个独立的渲染区域——块级格式化上下文（Block Formatting Context，简称 BFC）**！
> 在 W3C 的 BFC 渲染规则中，有一条神圣不可违背的铁律：**“计算 BFC 容器的高度时，浮动子元素的高度也必须强制计入在内！”**
> 于是，父盒子被强制重新计算内部所有浮动孩子的高度，塌陷瞬间修复。

- **优点**：代码量最少，仅需父级单行配置，极为轻快；
- **致命缺陷（毒副作用）**：既然它是 `overflow: hidden`，**如果你的父容器内部将来有悬浮弹出的二级下拉菜单、气泡提示框（Tooltip）、或者超出边缘的精致小角标，都会被这个属性一刀切断隐藏**，导致内容显示残缺！因此在包含溢出 UI 的组件中绝对禁止使用。

### 5.5 四大清除浮动方案横向全景对比

| 解决方案 | 核心代码原理 | 优点 | 致命缺陷 / 风险 | 工业采纳建议 |
| :--- | :--- | :--- | :--- | :--- |
| **额外标签法** | 尾部插入 `<div class="clear">`，声明 `clear: both;` | 简单直观 | 增加大量无意义标签，污染 DOM | **严禁使用**（已淘汰） |
| **单伪元素清除** | 父级 `.clearfix::after { content:""; display:block; clear:both; }` | 结构纯净，符合规范 | 需在公共 CSS 中维护类名 | **强烈推荐**（工业标准） |
| **双伪元素清除** | `::before, ::after { content:""; display:table; }` + 尾部 `clear:both;` | 兼治浮动塌陷与父子外边距穿透 | 代码行数略多两行 | **强烈推荐**（小米等大厂标准） |
| **BFC 清除法** | 父级添加 `overflow: hidden;` | 极简，单行生效 | 会无情裁切掉任何溢出边界的下拉菜单与角标 | **慎用**（仅用于无溢出组件） |

## 6. 为什么浮动最终被现代前端全面放弃？

剖析到这里，相信聪明的你已经对浮动的本质产生了深刻的怀疑：

> “老师，我只是想老老实实把几个盒子横着摆在同一行，为什么我每写一次浮动，都得提心吊胆地跟在后面写伪元素、算边距、擦屁股清除浮动？我写个网页，怎么跟伺候祖宗一样累？！”

**你的吐槽，正是整个前端工业界十年前的集体呐喊！**

### 6.1 现代前端放弃浮动的根本原因：
1. **脱标本非布局设计**：浮动打破了正常文档流的几何秩序，其脱标特性在宏观排版中百害而无一利；
2. **清除浮动的心智包袱**：无论采用哪种清除浮动手段，本质上都是在为浮动的负面效应“打补丁”，极大增加了代码复杂度与新人维护成本；
3. **缺乏空间自适应能力**：在移动端与响应式设备层出不穷的今天，浮动无法原生处理等比缩放、剩余空间分配、垂直居中对齐等现代排版诉求。

### 6.2 为什么小米等大厂页面里依然能看到浮动？
很多同学去审查小米首页源码，会跳出来反问：“老师，你看小米官网的商品网格明明还在用 `float: left` 和 `.clearfix` 啊，你凭什么说它被放弃了？”

这里必须为大家科普一线大厂的**真实工业工程考量**：
1. **历史技术债务（Legacy Code）**：大型电商网站的核心基础样式库建立于 2012~2015 年甚至更早。一套跑了十来年、每年承载数百亿 GMV 的成熟老系统，底层依赖着海量的复杂业务组件，冒然全量重构替换布局的测试风险与人力成本极高；
2. **SEO 与搜索引擎权重**：头部电商老域名的静态 HTML 骨架深受各大搜索引擎爬虫的深度信任，大范围破坏性结构重构可能会引起搜索权重的短期剧烈波动；
3. **向前兼容老旧设备**：少数下沉业务仍需兼顾极其老旧的内嵌 Webview 或特殊终端环境。

> **结论**：**大厂旧页面保留浮动属于‘历史债务的妥协’，绝非‘技术选型的推崇’！在京东、淘宝、B站以及几乎所有近五年新建的前端工程、中后台系统、移动端应用中，新项目已 100% 杜绝浮动排版，全面倒向了下一讲的核心主角——Flex 弹性盒布局！**

## 7. 本讲核心要点回顾与思考

```text
被放弃的浮动 float 核心知识全景脉络

float 浮动排版
  │
  ├── 1. 前世今生
  │     ├── 诞生初衷 -> 图文环绕 (float: left / right)
  │     └── 历史滥用 -> 被早期开发者篡用于多列水平排版
  │
  ├── 2. 底层机制与缺陷
  │     ├── 脱离标准流 (脱标) -> 腾空升起不占地基，导致标准流兄弟钻底
  │     └── 父级高度塌陷       -> 容器不能写死高度时，浮动子项无法撑起父级
  │
  ├── 3. 清除浮动 (闭合浮动)
  │     ├── 单伪元素法 (京东) -> .clearfix::after { content:""; display:block; clear:both; }
  │     ├── 双伪元素法 (小米) -> .clearfix::before, .clearfix::after { display:table; } 兼防塌陷
  │     └── BFC 清除法        -> overflow: hidden (注意防范菜单裁切)
  │
  └── 4. 时代宿命
        └── 新项目彻底淘汰 -> 全面过渡拥抱 Flexbox 弹性盒
```
*图 6：浮动 float 核心技术全景脉络图*

1. **浮动最本质的物理特征是什么？为什么它会导致兄弟元素钻到其底部？**
   - 浮动元素会脱离常规标准文档流（脱标），在空中悬浮而不再在地基上占据物理空间尺寸。原本排在它后面的标准流兄弟元素在计算排版流时，视前方的空间为空，自然会向前占位并钻到浮动元素的下方。
2. **为什么我们极力推荐单伪元素或双伪元素清除浮动，而不是直接给父盒子写死固定高度或添加空 div？**
   - 商业项目中子元素数量动态可变，写死父级高度极易引发空间溢出或大片留白；添加额外空 div 会增加无意义标签破坏 HTML 语义规范；而伪元素完全由 CSS 纯样式控制，在不改动任何结构的前提下利用浏览器机制撑开父级，是公认最健壮的工业级方案。
