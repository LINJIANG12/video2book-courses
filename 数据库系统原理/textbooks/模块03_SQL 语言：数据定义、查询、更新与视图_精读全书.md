## SQL 数据定义：先把数据库的框架搭起来
> 对应块：BLK09 | 覆盖分集：P07 | 块标题（分集名）：《数据库第3章 SQL （第一部分：数据定义）》

一提到数据库，大家脑海里经常会蹦出“SQL”这三个字母。可真正要动手时，很多同学又觉得它是一堆难记的命令。今天我们先把 SQL 的来龙去脉和基本特点理一理，再进入这一讲真正要解决的问题：数据库的框架究竟怎么搭起来。

学语言其实都差不多。先认单字，再看语法，然后看例子，最后自己动手仿着写。认识几个词，记住几个句式，看着案例把第一张表建出来，后面的内容就有了落脚点。

### SQL 从哪里来，又为什么需要标准

SQL 的全名是 **Structured Query Language**，也就是结构化查询语言。它是通用的、功能极强的关系数据库语言。要理解它为什么重要，先得理解“标准”这个概念。

键盘采用 QWERTY 布局，计算机用 ASCII 码把 0、1 与人类语言对应起来，这些都可以看作技术标准。标准主要有两类：一类由政府通过法律法规制定，电压和插头规格就是典型例子；另一类由行业在长期使用中逐渐形成共识，QWERTY 键盘布局和 ASCII 码属于这一类。SQL 同样是一种行业标准。

为什么标准如此重要？假如 IBM、微软、苹果、华为和小米各用一套自己的技术标准，作为供应商，我们有限的人力、财力与物力就不可能面面俱到。要么 all-in 押在某一家厂商身上 risking 押错；要么把资源平均分给五家，却没有力量把任何一个产品做好。

如果全行业采用统一标准，供应链上的企业就能集中精力围绕同一个技术标准生产键盘、鼠标和计算机设备。供应能力因此上升；当供给超过需求，价格便会下降。技术价格降低，又能让它从少数人的昂贵选择进入普通人的生活，推动大规模普及。被广泛使用之后，需求量继续上升，新的需求反过来又会促进技术创新。

```text
统一技术标准
      ↓
产业链集中生产 → 市场供给增加 → 产品价格下降
      ↑                                  ↓
技术创新 ← 大规模应用 ← 技术进入大众生活
```

> **结论**：标准不是束缚创新，而是在厂商、供应链、市场和技术进步之间建立一条有效的循环路径。

### SQL 把三类功能装进了一种语言

数据库管理系统，也就是 DBMS，要对现实世界中的数据进行定义、操作和控制。这三部分能力在语言层面分别对应 DDL、DML 和 DCL。

所谓数据定义，就是决定数据库的框架：有几张表，每张表长什么样，表与表如何连接。数据操纵则是在框架搭好之后，对其中的数据进行增加、删除、修改和查询。数据控制关注的是数据应当遵守什么规则，例如性别列只允许取“男”或“女”，考试成绩必须位于 0 到 100 之间。

> **定义**：DDL（Data Definition Language，数据定义语言）负责搭建数据框架；DML（Data Manipulation Language，数据操纵语言）负责增、删、改、查；DCL（Data Control Language，数据控制语言）负责访问权限以及完整性、安全性等控制。

这三类功能背后还有关系代数作为理论基础。第 2 章讲关系代数，第 3 章讲如何用 SQL 表达相应任务，数据库的完整性、安全性则会在后续章节中继续展开。基础部分连起来之后，才进入数据库设计。

SQL 有几个重要特点。

#### 综合统一

SQL 把数据定义、数据操纵和数据控制三类能力集于一体。它覆盖数据库生命周期中的各项主要活动：定义框架、修改框架，装入数据，对数据执行增删改查，再处理重构、维护、安全性、完整性与并发访问等事务，还可以嵌入高级语言中作为程序的一部分使用。

> **结论**：对数据库的主要操作，SQL 基本都能用统一的方式完成。

#### 高度非过程化

过程化语言要求写程序的人把执行步骤一行一行写出来，例如 C、Java 等语言。使用 SQL 时，我们只需要说明“想做什么”，不需要说明数据沿什么存取路径被找到。

例如，要查出本班同学在当前课程中的平均成绩，只需用 SQL 表达这个要求，再由系统转换成关系代数并完成查询。至于数据库管理系统内部怎样执行，不由使用者操心。

#### 面向集合

用 C 或 Java 处理一个班 50 名学生的成绩记录时，程序通常要用学号、姓名、课程、成绩等变量逐行接收，再通过循环逐行处理。SQL 的操作对象则是表。表里是一行还是 50 行、5 列还是更多列，对“按条件处理一批记录”这个要求本身没有影响。一条 SQL 语句就可以处理整个集合，而不是只处理一行。

这组特点也让 SQL 与高级语言形成了互补：高级语言擅长定义执行过程，SQL 擅长处理集合式的大规模数据。SQL 可以作为一次函数调用嵌入 C、Java 或 C++ 程序，由程序传入条件，SQL 返回一批结果。

#### 九个核心动词与可作用范围

SQL 完成核心功能主要依靠九个动词：

- DDL：`CREATE`、`DROP`、`ALTER`；
- DML：`INSERT`、`UPDATE`、`DELETE`、`SELECT`；
- DCL：`GRANT`、`REVOKE`。

`GRANT` 把某项权限授予指定用户或用户类别，`REVOKE` 则收回已经授予的权限。例如，把成绩单修改权交给学委，事后发现其操作不合适，就可以收回这项权限。

SQL 能够作用于基本表和视图，并能与上层应用程序连接。存储文件不属于 SQL 直接管理的范围，它由操作系统与数据库管理系统负责。

> **注意**：SQL 的基本概念中，基本表是独立存在的表，也是模式层中的对象；视图则是从一个或几个基本表导出的表。本讲后面会分别介绍它们的定义方式。

### 学习这套语言，先认单字和句式

假设要学一门语言，我们通常先认识其中的动词与名词，再学习主谓宾、定状补、从句等语法结构，然后看别人怎样说话、写文章，最后自己模仿并练习。

学 SQL 也遵循这个过程。这一讲先认识 `CREATE`、`DROP`、`ALTER` 三个核心动词，再认识它们作用的四类对象：

| 对象 | 含义 | 创建 | 删除 | 修改 |
| --- | --- | --- | --- | --- |
| 模式（Schema） | 数据库整体框架或命名空间 | `CREATE SCHEMA` | `DROP SCHEMA` | 通常不提供 |
| 基本表（Table） | 数据库框架中的基本数据表 | `CREATE TABLE` | `DROP TABLE` | `ALTER TABLE` |
| 视图（View） | 从基本表映射出的虚表 | `CREATE VIEW` | `DROP VIEW` | 通常删除后重建，不直接修改 |
| 索引（Index） | 为加快查找建立的辅助结构 | `CREATE INDEX` | `DROP INDEX` | 通常只允许改名 |

> **易错点**：不能把“某个列后面写了 `PRIMARY KEY`”简单理解成“表有两个主码”。单列主码可以跟在列定义后面；联合主码要把多个列放在同一组主码约束中。

模式像一整套房屋框架。基本表像框架中的具体房间，数据定义先要决定的是这些房间的安排；视图是从基本表得到的另一种观察视角，修改视图通常不如直接删掉后重新建立；索引则像图书馆目录，帮助快速找到数据。

在常见示例数据库中，学生表 `Student` 的主码是学号，课程表 `Course` 的主码是课程号，选课表 `SC` 中的学号与课程号共同构成主码。`SC` 中的学号来自 `Student` 表的学号，课程号来自 `Course` 表的课程号，所以两列都承担外码的角色。

学完这些词，再看“动词加名词”的基本句式，DDL 的轮廓就出来了。接下来不必背整段代码。看懂结构、照着案例动手写一遍，遇到实际问题时能够迅速翻回语法，比试图默写全部语句更有用。

> **提示**：课堂上可以把语言规则“抄”一遍来形成手感，工作时没有谁要求不查工具书、不看课件。真正重要的是理解它解决什么问题，并能很快找到需要的语法。

### 模式的定义与删除

模式的定义，就是为某个用户建立数据库的整体命名空间。在常见 SQL 形式中，创建模式使用 `CREATE SCHEMA`：

```sql
CREATE SCHEMA S_T AUTHORIZATION WANG;
```

这条语句为用户 WANG 定义一个名为 `S_T` 的模式。语句执行后，系统中便开出相应的命名空间，用来容纳基本表、视图、索引以及授权定义。

如果不指定模式名，只写用户名：

```sql
CREATE SCHEMA AUTHORIZATION WANG;
```

此时模式名默认采用用户名，也就相当于新空间中直接以用户名作为框架名称。完整形式中，模式名是可选成分；创建模式后，还可以紧接着定义表、视图、索引或给出授权。

> **结论**：定义模式并不是往里面填数据，而是先为数据库开出一块命名空间，为后续对象提供归属。

#### 删除模式时先决定影响范围

删除模式使用 `DROP SCHEMA`：

```sql
DROP SCHEMA S_T RESTRICT;
```

`RESTRICT` 表示限制性删除。系统先检查模式中是否已经定义表、视图、索引等内容，如果存在依赖对象，就拒绝删除并给出提示，要求先清理这些对象。

`CASCADE` 表示级联删除：

```sql
DROP SCHEMA S_T CASCADE;
```

它表示连同模式内部依赖的对象一起清空。模式像已经住人的房子：`RESTRICT` 会先检查里面有没有东西，`CASCADE` 则相当于直接清空整个框架。

> **易错点**：`CASCADE` 与 `RESTRICT` 不只出现在删除模式时，后面删除基本表也会遇到。两种方式表达的是删除时对依赖对象采取什么处理策略。

### 基本表：框架中最需要反复操作的部件

基本表是这一讲的重点。数据库中的大量操作都围绕表展开，而创建一张表时，不能漏掉三个要素：表级框架、主码与外码。

`CREATE TABLE` 的基本结构包括表名、列名及其数据类型、列级完整性约束，以及表级完整性约束：

```sql
CREATE TABLE 表名 (
    列名1 数据类型 [列级完整性约束条件],
    列名2 数据类型 [列级完整性约束条件],
    ...,
    [表级完整性约束条件]
);
```

方括号表示可选项。列级约束针对某一列，例如该列不能为空、取值必须唯一；表级约束则针对完整表，例如谁是主码、哪些列是外码，以及外码引用哪张表的哪一列。

#### 学生表：先明确每一列的类型

先看学生表 `Student`。它有学号、姓名、性别、年龄、所在系五列。学号是主码，因此需要非空且唯一；姓名可以要求不能重复；年龄则可以根据实际需要规定取值范围。示例中的具体写法是：

```sql
CREATE TABLE Student (
    Sno   CHAR(10)   PRIMARY KEY,
    Sname CHAR(20)   UNIQUE,
    Ssex  CHAR(2),
    Sage  INT,
    Sdept CHAR(20)
);
```

这里以 `CHAR(10)`、`CHAR(20)` 这样的长度表示字符串能够容纳的字符范围。学号即使只包含数字，也可以使用字符串类型；具体选什么数据类型需要由实际需求决定，不必机械地把所有数字都写成数值类型。

字符串长度不要一味设得过大。长度设定会影响系统中的存储资源消耗，应当在满足业务需要的前提下选择。

`PRIMARY KEY` 主码从结果上等价于“非空且唯一”。因此，学号后面的 `PRIMARY KEY` 已经同时保证了它不能重复，也不能取空值。

> **易错点**：主码约束不只是一个列名装饰，它在表达“学号是这张表的唯一标识”。在已有数据上建立主码，还必须保证现有数据确实满足该要求。

#### 课程表：主码之外，还要记住外码

课程表 `Course` 有课程号、课程名、先修课、学分四列。课程号是主码。课程表没有设置“先修课”指向外码的约束；示例中让先修课引用本表课程号。

```sql
CREATE TABLE Course (
    Cno     CHAR(4)  PRIMARY KEY,
    Cname   CHAR(20),
    Cpno    CHAR(4),
    Ccredit INT,
    FOREIGN KEY (Cpno) REFERENCES Course(Cno)
);
```

列级约束紧跟相应的列定义，表级约束则写在这张表的定义末尾。外码声明要说明三件事：哪一列是外码、引用哪张表、引用对方哪一列。这里是 `Cpno` 引用同一张 `Course` 表的 `Cno`。

> **提示**：先修课程号不能凭空填写。把 `Cpno` 声明为引用 `Course(Cno)` 的外码，才能使这门课的先修关系与已有课程对应起来。

#### 选课表：联合主码与两个外码

选课表 `SC` 有学号、课程号、成绩三列。学号与课程号的组合才是这张表的主码，因为同一名学生可以选多门课，同一门课程也可以被多名学生选择。但同一名学生不能重复选择同一门课程。

组合主码不能分别写在学号后面和课程号后面，否则会变成两个独立的单列主码；正确做法是把两列放在同一个主码约束中：

```sql
CREATE TABLE SC (
    Sno    CHAR(10),
    Cno    CHAR(4),
    Grade  INT,
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

> **定义**：联合主码是由多个列共同构成的主码，它要求这些列的组合唯一，不能拆成多个单列主码。

这张表特别适合用来检查自己是否真正理解表级约束：表级框架列出三列，组合主码约束两列组合唯一，两个外码分别连接到 `Student` 和 `Course`。先把框架、主码、外码逐一检查一遍，再补数据类型和列级约束，就不容易漏项。

### 模式与表的三种组织方式

模式与表并不是僵化地绑在一起，可以通过三种方式组织。

第一种方式是在创建表时明确写出所属模式。这样即使在编写过程中发现原计划中漏掉了某张表，也可以继续把它归到指定的模式下。这种方式比较灵活。

第二种方式是在创建模式的语句中同时创建基本表。创建框架时顺便把需要的表一起定义，归属关系清楚，但如果一开始就确定好了数据库的完整结构，写起来比较方便；缺点是必须预先想清楚所有表，不适合边写边补充。

第三种方式是设计基本表时通过搜索路径设置所属模式。可以通过类似 `SET search_path TO` 的方式将搜索路径连接到此前的模式，再执行 `CREATE TABLE`，由当前搜索路径确定表的归属。

> **结论**：掌握前两种方式，已经足以应对大多数需要明确表达数据库组织结构的场景。

### 修改基本表

修改基本表使用 `ALTER TABLE`，无论要做什么，都必须先指出被修改的表，再描述修改内容。

可以新增列；可以增加或删除表级完整性约束；可以删除某一列，删除时同样要面对 `CASCADE` 与 `RESTRICT`；也可以修改列名或数据类型。新增列时仍然要明确列名、数据类型和约束条件。

例如，向 `Student` 表增加入学时间列，数据类型为 `DATE`：

```sql
ALTER TABLE Student
ADD Enrolldate DATE;
```

> **易错点**：不管原来的表中是否有数据，新增加的列一开始都是空值。原有数据不会自动补出一个入学时间。

将年龄的数据类型由字符改为整数时，可以写：

```sql
ALTER TABLE Student
ALTER COLUMN Sage INT;
```

这正体现了 SQL 高度非过程化的特点：只要说明“把 `Sage` 改成整数类型”，不需要另写一套过程化的数据搬运逻辑，把原有值如何转换交由数据库管理系统处理。

如果要为课程名增加“必须取唯一值”的约束，可以写：

```sql
ALTER TABLE Course
ADD UNIQUE (Cname);
```

表级约束也可以移除：

```sql
ALTER TABLE Course
DROP CONSTRAINT 约束名;
```

其中，`约束名` 是被移除约束的标识，不是字面量，也不是要求所有数据库系统都能接受的固定写法。要移除某条约束，必须知道它在数据库中实际使用的名称。

### 删除基本表

删除基本表使用 `DROP TABLE`。例如，删除 `Student` 表可以写：

```sql
DROP TABLE Student;
```

如果这个表上已经建立了视图或索引，直接删除会产生依赖问题。比如在 `Student` 基础上建立了一个筛选后的视图，再执行：

```sql
DROP TABLE Student RESTRICT;
```

系统会提示不能删除 `Student`，因为还有其他对象依赖它。应当先删除这些依赖对象，再回来删除基本表。

如果确实希望连同相关对象一起删除，可以使用级联方式：

```sql
DROP TABLE Student CASCADE;
```

执行后，表及相关对象会一起被删除，系统可能同时给出说明信息。

> **注意**：不同数据库管理软件对 `CASCADE` 和 `RESTRICT` 的具体处理可能存在差异。实际使用时，印象中要保留“检查依赖”与“连同依赖一起处理”这两种选择即可，具体行为再查对应软件的手册。

删除表和删除模式都可能出现这两个选项。它们在表达“删除前是否检查依赖对象，以及是否连同依赖对象一起处理”时是一致的。

### 索引：给数据准备一条快速查找的路

索引就是为加快查询建立的辅助结构。拿一本书来比喻：入馆时登记它放在三楼某个书架，以后按出版社、作者和出版年份来查找，就能直接定位到书架位置。这就是索引的作用。

例如，在学生学号列上建立索引后，给定学号 `95001`，系统可以沿索引直接找到对应记录，而不必把整个学生表逐行检查一遍。

常见索引包括顺序文件索引、B+ 树索引、散列或哈希索引以及位图索引等。B+ 树是二叉树的一种特殊形式：同一层节点的左侧值小于当前节点，右侧值大于当前节点。查询时，如果要找的数小于当前节点，就继续向左侧查找。它具有动态平衡的特点。

哈希索引利用哈希函数把数据分散到不同的“堆”中，查询时先定位相应的堆。它通常具有查找速度快的特点。`UNIQUE` 表示建立唯一索引；`CLUSTER` 表示建立聚簇索引。

以手机通讯录为例，查找某个联系人时先按姓名首字母分组，再进入对应字母组寻找，这可以很直观地帮助理解聚簇索引的概念。

通常，数据库管理员和建表的人可以建立索引；数据库管理员与数据库管理系统负责维护索引，数据库管理系统通常自动完成维护；索引建立后，大家都可以使用。

索引可以建在一列或多列上。建立索引的基本形式是：

```sql
CREATE [UNIQUE] [CLUSTER] INDEX 索引名
ON 表名 (列名 [ASC | DESC], ...);
```

`ASC` 是 ascending 的缩写，表示升序；`DESC` 是 descending 的缩写，表示降序。不写排序方向时，默认采用升序。

> **易错点**：`UNIQUE` 和 `CLUSTER` 都是可选成分，平时不写并不代表索引无效，而是使用默认形式。

为学生、课程和选课三张表建立索引时，可以采用有意义的名字，例如包含表名和列名，让阅读代码的同事一眼就能知道索引作用在哪张表、哪一列。名字并不一定要采用固定格式，写成其他不重复的名字也能表达同一个意思；但清楚的命名有助于团队协作。

```sql
CREATE UNIQUE INDEX SC_Sno
    ON SC (Sno ASC, Cno DESC);

CREATE UNIQUE INDEX Student_Sno
    ON Student (Sno ASC);

CREATE UNIQUE INDEX Course_Cno
    ON Course (Cno ASC);
```

这里学生表按学号升序建立唯一索引，课程表按课程号升序建立唯一索引，选课表先按学号升序、再按课程号降序建立唯一索引。选课表的多列索引中间用逗号隔开，排序方向可以逐列指定。

修改索引通常只允许改名：

```sql
ALTER INDEX 索引名 RENAME TO 新索引名;
```

删除索引则直接使用：

```sql
DROP INDEX 索引名;
```

> **注意**：把索引命名为“表名_列名”只是一个便于阅读的命名约定，并非数据库强加的规定。

### 数据字典：让程序和数据能被读懂

数据字典不是这一讲的重点，但它与程序开发文档紧密相关。一个系统可能同时涉及数据库、应用代码、多个数据对象、字段、数据流与业务流程，需要把这些内容系统地整理起来。

程序员完成程序后，通常还要编写开发文档，程序与文档一起交付给用户。接手系统的用户或其他程序员未必参与过开发，当他们看到 `Student(Sno)` 这样的定义时，需要通过文档查清楚它表示学生表的学号列，以及相关字段、数据和约束的含义。

数据字典把这些数据项、数据结构、数据流等有关内容组织成条目，纳入系统开发文档。这样，即使不是原开发者，也能借助字典理解程序中各对象的含义。它是“代码旁边的说明”，不是运行数据本身。

### 本讲提到的题目

#### 用 SQL 建出选课表 `SC`

题干：在学生表 `Student` 和课程表 `Course` 已经建立的基础上，用 SQL 创建选课表 `SC`。表中包含学号、课程号和成绩三列；学号与课程号构成联合主码，学号引用 `Student(Sno)`，课程号引用 `Course(Cno)`。

解析：表格框架由 `CREATE TABLE SC` 和三列定义给出。学号与课程号不是两个独立主码，而要共同放入一个 `PRIMARY KEY` 约束中；两个外码都是表级约束，因此应写在表级定义部分。列级与表级约束混淆，是本题最容易出错的地方。

答案：

```sql
CREATE TABLE SC (
    Sno   CHAR(10),
    Cno   CHAR(4),
    Grade INT,
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

### 数据定义部分的收束

这一讲先认识 SQL 作为关系数据库标准语言的整体面貌，再回到数据库生命周期中最早的一步：先定义框架，再把数据放进去，后续才谈得上查询、更新与控制。

DDL 的核心可以压缩成“**三个动词、四个对象**”：`CREATE`、`DROP`、`ALTER` 作用于模式、基本表、视图、索引。模式与表是建立数据库框架时的主要部件；主码、外码和数据类型决定了表的基本约束；索引让查找更高效；删除时的 `CASCADE` 与 `RESTRICT` 则提醒我们：删除一个对象之前，必须看清它对其他对象的影响。

到这里，SQL 三方面功能中的 DDL 部分才算走完第一步。接下来数据查询、数据更新、空值处理和数据控制等部分，等我们把语言的基础框架真正立住，才好继续往下讲。

## SQL 单表查询：从五个查询语句到分组筛选
> 对应块：BLK10 | 覆盖分集：P08 | 块标题（分集名）：《数据库第3章 SQL (第二部分：数据查询PAR》

先把一条自然语言变成一条 SQL，最重要的不是背语法，而是把它拆成“输入、输出、分析”。第二章讲关系代数时，我们已经用过这个方法；现在把它平移到 SQL，单表查询就再没有多少神秘感了。

一条查询块最常见的基本形式是 `SELECT ... FROM ... WHERE ...`。题目要输出什么，交给 `SELECT`；条件是什么，交给 `WHERE`；数据在哪个表或视图的范围内，交给 `FROM`。这三个位置一对应，查询的基本骨架就搭起来了。

不过，单表查询真正需要掌握的是五个部分：`SELECT`、`FROM`、`WHERE` 配合聚集函数和 `ORDER BY` 完成列、行与结果加工；`GROUP BY` 配合 `HAVING` 完成分组统计。整个数据查询部分的后续内容，则是在这个基础上增加多表连接、嵌套查询、集合查询和派生表。

### 查询语句各管什么

SQL 把数据定义、数据操作和数据控制分成语言功能，其中数据操作语言 DML 负责增加、删除、修改和查询，也就是常说的“增删改查”。四类操作里，查询最有难度，也是这一部分的重点。

> **结论**：一个查询块的基本骨架是 `SELECT-FROM-WHERE`；完整掌握单表查询，还要掌握聚集函数、`ORDER BY`、`GROUP BY` 和 `HAVING`。

| 语句 | 作用 | 用法要点 |
| :--- | :--- | :--- |
| `SELECT` | 指定要显示的属性列 | 可以输出属性、计算表达式、常量或函数结果，也能为输出列指定名称 |
| `FROM` | 指定查询对象 | 可以是表、视图，也可以跟派生表 |
| `WHERE` | 指定查询条件 | 没有条件时可以省略 |
| `GROUP BY` | 按指定列的值分组 | 与聚集函数配合使用 |
| `HAVING` | 筛选分组后的结果 | 有 `GROUP BY` 时，分组后的筛选条件写在这里 |
| `ORDER BY` | 排序 | `ASC` 为升序，`DESC` 为降序；不写方向时默认升序 |

这里有两条要马上分清：

- `WHERE` 筛选的是查询中的行，条件必须针对当前查询范围内的数据。
- `HAVING` 筛选的是 `GROUP BY` 产生的组，条件针对分组后的结果。

两者都表达“筛选”，但作用对象不同。`WHERE` 对整表或当前查询范围起作用；`HAVING` 则是在分组完成之后，对每一个组再判断一次。

> **易错点**：有 `GROUP BY` 时，筛选分组结果的条件要写进 `HAVING`，不能把它当成普通行条件继续写进 `WHERE`。在单表查询的知识范围内，把两者分清楚就够了。

`ORDER BY` 中，`ASC` 是 ascending 的缩写，表示升序；`DESC` 是 descending 的缩写，表示降序。什么都不写时默认升序，因此按系号升序、按年龄降序时，升序方向可以省略。

### 输入、输出和分析

拿到一道题，不要先盯着 SQL 句子背。先问三个问题：输出是什么，输入条件是什么，分析范围在哪里？三个问题分别对应 `SELECT`、`WHERE`、`FROM`。

```text
题目条件
   │
   ▼
WHERE ── 输入：哪些行符合条件
   │
   ▼
FROM  ── 分析：在哪个表或视图范围内查询
   │
   ▼
SELECT ─ 输出：显示哪些列或计算结果
```

这里“输入”不是键盘输入，“输出”也不是屏幕打印，而是数据库查询中的筛选条件、查询范围和显示结果。`WHERE` 把符合条件的数据交给后面的处理，`FROM` 确定处理范围，`SELECT` 决定最后显示什么。

#### 选择若干列

查询全体学生的学号和姓名，要输出的列是 `Sno`、`Sname`，数据范围是 `Student`，没有筛选条件，所以不写 `WHERE`：

```sql
SELECT Sno, Sname
FROM Student;
```

查询全体学生的姓名、学号和所在系，只是把输出列换成 `Sname`、`Sno`、`Sdept`：

```sql
SELECT Sname, Sno, Sdept
FROM Student;
```

查询全体学生的详细记录，就是输出整张表。逐个列出字段当然可以，但表比较长时很费事，可以用 `*` 表示全体属性：

```sql
SELECT *
FROM Student;
```

> **定义**：`SELECT *` 表示输出当前查询范围内的全部属性，并不是忽略查询条件。配合 `WHERE` 使用时，它表示输出所有满足条件的完整记录。

#### 输出表达式、常量与别名

假设当前年份是 2022 年，全体学生的出生年份等于 `2022 - Sage`：

```sql
SELECT Sname, 2022 - Sage
FROM Student;
```

这里没有 `Year` 这个属性，输出的是根据年龄计算出来的值。逐行看时，就像每取出一条学生记录，就取出其中的姓名与年龄；有运算的先运算，没有运算的直接输出，最后形成整张结果表。

还可以直接输出常量，并为输出列改名。例如查询姓名、出生年份和所在系，要求系名使用小写字母，并为各列指定清晰的表头：

```sql
SELECT Sname,
       2014 - Sage AS "Year of Birth",
       LOWER(Sdept) AS NAME
FROM Student;
```

不带引号的 `Sname`、`Sdept` 是属性名，带单引号的 `'Year of Birth'` 是固定常量；`2014 - Sage` 是计算表达式，`LOWER(Sdept)` 是函数调用。`AS` 后面给出的名称会成为结果表头。

`AS` 在 `SELECT` 中还可以直接修饰属性列：

```sql
SELECT Sname AS NAME,
       2014 - Sage AS BIRTH,
       LOWER(Sdept) AS "Dept Name"
FROM Student;
```

所以 `SELECT` 并不只是把原表属性原样抄出来。它可以：

- 输出属性值；
- 输出计算表达式；
- 输出常量；
- 调用函数；
- 用 `AS` 修改输出列名。

这正好解释了为什么表头既可以写成一列属性名，也可以写成 `'Year of Birth'` 这样的固定文字：前者来自数据，后者是每行都要输出的常量。

### 用条件选择行

`WHERE` 负责选择表中的若干行。先看一个可能产生重复的例子：查询选修了课程的学生学号。

```sql
SELECT Sno
FROM SC;
```

`SC` 表记录选课信息，一个学生可能选了多门课，因此同一学号会重复出现。我们只关心“哪些学生选过课”，并不关心一个学生选了几门，所以要去重：

```sql
SELECT DISTINCT Sno
FROM SC;
```

不写 `DISTINCT` 时默认是 `ALL`，保留重复值；`DISTINCT` 表示去掉重复结果。查询挂科学生时也一样：学生挂了两门课，学号会输出两次，而我们只想知道哪些人挂科了，因此仍然使用 `DISTINCT`。

#### 比较、范围与集合条件

查询计算机科学系全体学生的名单：

```sql
SELECT Sname
FROM Student
WHERE Sdept = 'CS';
```

查询所有年龄在 20 岁以下的学生姓名和年龄：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sage < 20;
```

查询考试成绩有不及格的同学学号：

```sql
SELECT DISTINCT Sno
FROM SC
WHERE Grade < 60;
```

常见条件可以归为几类：

- 比较条件，如 `=、<、>、<=、>=`；
- 确定范围，如 `BETWEEN ... AND ...`、`NOT BETWEEN ... AND ...`；
- 确定集合，如 `IN`、`NOT IN`；
- 字符串匹配，如 `LIKE`、`NOT LIKE`；
- 空值判断，如 `IS NULL`、`IS NOT NULL`；
- 多重条件，如 `AND`、`OR`、`NOT`。

范围查询中，`BETWEEN` 的两个端点包含在内。例如查询年龄在 20 到 23 岁之间的学生：

```sql
SELECT Sno, Sname, Sage
FROM Student
WHERE Sage BETWEEN 20 AND 23;
```

不在该范围内则使用 `NOT BETWEEN`：

```sql
SELECT Sno, Sname, Sage
FROM Student
WHERE Sage NOT BETWEEN 20 AND 23;
```

查询 CS、MA、IS 三个专业的学生姓名和性别：

```sql
SELECT Sname, Ssex
FROM Student
WHERE Sdept IN ('CS', 'MA', 'IS');
```

`IN` 表示字段值属于括号中列出的集合，它也可以改写成若干个等号条件用 `OR` 连接。两种写法都能表达同一个意思，但 `IN` 更直接。

#### 字符串匹配与通配符

字符串条件使用 `LIKE`。其中最常见的两个通配符是：

- `%`：代表任意长度的字符串，包括零个字符；
- `_`：代表任意一个字符。

例如：

```text
A%B   → 以 A 开头、以 B 结尾的任意长度字符串
A_B   → 以 A 开头、以 B 结尾、长度为 3 的字符串
```

所以 `A_B` 可以匹配 `ACB`、`ADB`、`AEB`，但不能匹配 `AABB`，因为后者中间不是一个字符。

查询学号为 `201215121` 的学生详细情况，可以使用等号，也可以使用 `LIKE`：

```sql
SELECT *
FROM Student
WHERE Sno LIKE '201215121';
```

但这毕竟是一个完整、确定的字符串，条件虽然能写，真正有价值的还是它对部分字符串的匹配。

查询所有姓刘的学生姓名、学号和性别：

```sql
SELECT Sname, Sno, Ssex
FROM Student
WHERE Sname LIKE '刘%';
```

`'刘%'` 表示字符串以“刘”开头，后面是任意长度的内容。刘姓同学的名字无论两个字、三个字还是更长，都能被匹配。

查询姓欧阳且全名为三个汉字的学生：

```sql
SELECT Sname
FROM Student
WHERE Sname LIKE '欧阳_';
```

前两个汉字固定为“欧阳”，最后一个字符未知，所以用一个下划线占位。如果只要求姓欧阳，不限定名字长度，就改为：

```sql
SELECT Sname
FROM Student
WHERE Sname LIKE '欧阳%';
```

查询名字中第二个字为“阳”的学生姓名和学号：

```sql
SELECT Sname, Sno
FROM Student
WHERE Sname LIKE '_阳%';
```

第一个字未知，用 `_`；第二个字固定为“阳”；第三个字开始长度未知，用 `%`。它真正考的并不是新语法，而是 `%` 和 `_` 的灵活组合。

查询所有不姓刘的同学：

```sql
SELECT Sname, Sno
FROM Student
WHERE Sname NOT LIKE '刘%';
```

#### 转义通配符

当被查询的字符串本身含有 `_` 或 `%` 时，不能再让系统把它们自动当作通配符。可以用 `ESCAPE` 指定转义字符。

查询课程名恰好为 `DB_Design` 的课程号和学分：

```sql
SELECT Cno, Ccredit
FROM Course
WHERE Cname LIKE 'DB\_Design' ESCAPE '\';
```

如果不转义，`_` 只表示一个任意字符，系统可能把 `DBADesign`、`DBCDesign` 等名字也匹配出来。加上 `\` 后，`\_` 就按字面意义表示下划线。

查询以 `DB_` 开头、倒数第三个字符为 `i` 的课程详细情况：

```sql
SELECT *
FROM Course
WHERE Cname LIKE 'DB\_%i__' ESCAPE '\';
```

这里各部分的含义是：

```text
DB\_%i__
│ │  │││
│ │  ││└─ 两个下划线：最后两位长度已知
│ │  │└── 一个 i：倒数第三个字符固定
│ │  └──── 百分号：DB_ 与 i 之间长度未知
│ └─────── 下划线前有转义符，按字面值匹配
└───────── 前缀固定为 DB_
```

如果数据库支持 `ESCAPE`，就可以用它来表达“某个特殊符号按字面意义匹配”。这段判断的关键是理解转义，而不是把 `LIKE` 机械套成一个模板。

#### 空值与多重条件

空值使用 `IS NULL` 或 `IS NOT NULL` 判断：

```sql
SELECT *
FROM Student
WHERE Sage IS NULL;
```

查询非空年龄：

```sql
SELECT *
FROM Student
WHERE Sage IS NOT NULL;
```

多重条件使用 `AND`、`OR` 和 `NOT`。查询计算机系年龄小于 20 岁的学生姓名：

```sql
SELECT Sname
FROM Student
WHERE Sdept = 'CS'
  AND Sage < 20;
```

> **注意**：`AND` 的优先级高于 `OR`。要改变组合关系时，用括号明确表达，不要让系统替你猜。

> **易错点**：字符串和数字的匹配方式不要混用。完整学号可以用等号，字符串的部分匹配才需要 `LIKE`；字符串常量必须放在单引号中。

到这里，`SELECT-FROM-WHERE` 的基本查询已经覆盖了比较、范围、集合、模式匹配、空值判断以及多重条件。它们看起来写法各异，换的只是“输入条件”怎么写，`SELECT`、`FROM` 和 `WHERE` 的职责始终没有变化。

### 排序

`ORDER BY` 决定结果按哪一列排序，以及采用什么方向。

查询选修了 3 号课程的学生学号和成绩，结果按成绩降序排列：

```sql
SELECT Sno, Grade
FROM SC
WHERE Cno = 3
ORDER BY Grade DESC;
```

其中：

- `SELECT Sno, Grade` 决定输出学号和成绩；
- `WHERE Cno = 3` 决定只保留 3 号课程的选课记录；
- `FROM SC` 确定查询范围；
- `ORDER BY Grade DESC` 要求成绩从高到低排列。

查询全体学生，先按所在系的系号升序排列，同系学生再按年龄降序排列：

```sql
SELECT *
FROM Student
ORDER BY Sdept DESC, Sage ASC;
```

这道题要特别注意：题目要求的是“所在系的系号升序”，而表中表示系号的属性是 `Sdept`。如果结果与题意不符，先检查排序字段和方向，不能直接猜 SQL 有问题。

> **易错点**：第一排序关键字决定主要顺序，后续关键字只在前面排序值相同时继续比较。题目要求“同系中按年龄降序”时，第二个排序项不能遗漏。

#### 空值怎样排

空值参与排序时，显示次序由具体系统决定，不能把它当成普通数值比较。日常可以记住一句顺口的话：

> **提示**：空值跟大头。

一个班里有个同学没参加考试，成绩是空值，其他人从 99 分往下排。无论从高到低还是从低到高看，常用的记忆方式都是让空值跟着这一列最大的那头走，也就是“跟大头”。这里是便于记忆的经验性说法，遇到具体系统仍要按其规则处理。

### 聚集函数与统计

聚集函数用来做统计，常见的有：统计行数、统计值的个数、统计列数、求最大值、最小值和平均值。上一节中只列出了五种基本语句，是因为排序、聚集与分组是在这些语句上追加的查询能力。

查询学生总人数：

```sql
SELECT COUNT(*)
FROM Student;
```

`COUNT(*)` 统计所有行，因此得到学生总人数。

查询选修了课程的学生人数：

```sql
SELECT COUNT(DISTINCT Sno)
FROM SC;
```

一个学生可能选多门课，直接 `COUNT(Sno)` 会把多门选课记录重复计算。`DISTINCT` 先把学号去重，再计数，得到的才是选过课的学生人数。

计算 1 号课程的平均成绩：

```sql
SELECT AVG(Grade)
FROM SC
WHERE Cno = 1;
```

`Grade` 在 `SC` 表中，`WHERE Cno = 1` 留下 1 号课程的所有成绩，聚集函数对留下的结果求平均。求最大值和最小值只是换成相应函数：

```sql
SELECT MAX(Grade)
FROM SC
WHERE Cno = 1;

SELECT MIN(Grade)
FROM SC
WHERE Cno = 1;
```

> **结论**：没有 `GROUP BY` 时，聚集函数作用于整个查询结果；使用 `GROUP BY` 后，聚集函数会分别作用于每一个组。

#### 按课程统计选课人数

查询各个课程号和相应的选课人数：

```sql
SELECT Cno, COUNT(*)
FROM SC
GROUP BY Cno;
```

如果 `SC` 表有 1 号到 5 号课程的选课记录，可以把处理过程理解成：先按 `Cno` 把数据分成 5 组，再分别进入每一组，用 `COUNT(*)` 数这一组有多少行，最后把课程号和人数输出。

```text
SC 的查询结果
     │
     ├── Cno = 1 ── COUNT(*) → 选课人数
     ├── Cno = 2 ── COUNT(*) → 选课人数
     ├── Cno = 3 ── COUNT(*) → 选课人数
     ├── Cno = 4 ── COUNT(*) → 选课人数
     └── Cno = 5 ── COUNT(*) → 选课人数
```

读图：从同一条 `GROUP BY Cno` 语句出发，先按课程号分组，再让 `COUNT(*)` 在每一组内分别计数。

#### 按学生统计课程数

查询选修了 3 门以上课程的学生学号：

```sql
SELECT Sno
FROM SC
GROUP BY Sno
HAVING COUNT(*) > 3;
```

过程分三步：

1. `GROUP BY Sno`：把选课记录按学生学号分组；
2. `COUNT(*)`：在每个学生对应的组内统计选课记录数；
3. `HAVING COUNT(*) > 3`：只保留选课记录超过 3 行的组。

学号位于各组的分组键上，统计结果也来自每个组内部，所以满足条件的组可以同时输出学号与课程数。关键不在于记哪一个函数，而在于记住执行次序：先分组，再在组内计算，最后筛选组。

#### 哪些条件放 WHERE，哪些放 HAVING

查询平均成绩大于 90 分的学生学号和平均分，应该按学号分组，再用 `HAVING` 筛选：

```sql
SELECT Sno, AVG(Grade)
FROM SC
GROUP BY Sno
HAVING AVG(Grade) > 90;
```

错误思路是把它写成：

```sql
SELECT Sno, AVG(Grade)
FROM SC
WHERE AVG(Grade) > 90
GROUP BY Sno;
```

第二种写法的问题在于：普通行还没有分组和聚集计算时，条件里就已经要求平均成绩大于 90；而真正的分组、计算与筛选顺序应该是：

```text
原始数据
   │
   ▼
WHERE：先筛选参与统计的行
   │
   ▼
GROUP BY：按 Sno 分组
   │
   ▼
聚集函数：在每个组内计算 AVG(Grade)
   │
   ▼
HAVING：保留平均成绩大于 90 的组
   │
   ▼
输出该组的 Sno 与平均分
```

读图：`WHERE` 位于分组之前，`HAVING` 位于分组和聚集计算之后。二者都叫筛选，作用范围却不同。

从这一讲的范围看，分组查询可以这样记：

```text
先保留需要的记录
        ↓
按指定属性分组
        ↓
在每个组内使用聚集函数
        ↓
保留满足条件的组
        ↓
输出分组属性与统计结果
```

> **结论**：单表查询的基础仍是 `SELECT-FROM-WHERE`，额外能力则是聚集函数、`ORDER BY`，以及 `GROUP BY` 与 `HAVING` 的配合。把这几部分彻底掌握，后面的连接、嵌套、集合和派生表查询才有可靠的落脚点。

## SQL 多表查询的三条路
> 对应块：BLK11 | 覆盖分集：P09 | 块标题（分集名）：《数据库第3章 SQL（第二部分：数据查询PART》

单表查询解决的是一个表里的问题，可现实中的查询往往要同时使用两个甚至三个表。查询“每个学生选了什么课”，就离不开学生表、选课表和课程表。

面对这类多表查询，我们有连接查询、嵌套查询、集合查询三种办法。它们的表达能力大体相当，同一道题常常都能做；区别主要在于哪一种写法更顺手，以及系统实际处理时的效率不同。

> **结论**：不必纠结三种方法谁对谁错。拿到题目后先判断哪种路径最直接，哪个简单就用哪个。

### 连接查询：先连表，再筛选

连接查询用于同时涉及两个以上关系的多表查询。两个表做连接，逻辑上相当于先做笛卡尔积，把所有组合列出来，再按连接条件筛选，把不相等的组合删掉。

因此，SQL 中写下等号进行连接时，实际上暗含了“先笛卡尔积，后按值相等筛选”的过程。

> **注意**：多表查询没有筛选条件，并不代表没有连接条件。只要涉及多个表，就必须先把它们连接起来；至于额外的业务筛选条件，可以在连接条件之后继续用 `AND` 补充。

#### `FROM` 与 `WHERE` 的变化

多表查询和单表查询在输入输出分析上的差别，主要集中在两个位置：

- `SELECT` 负责输出；
- `FROM` 写出涉及的各个表；
- `WHERE` 写出连接条件和筛选条件。

例如，查询每个学生及其选课情况。输出涉及 `Student` 与 `SC` 两个表的全部字段，所以 `FROM` 中写入这两个表，并按学生学号相等建立连接：

```sql
SELECT *
FROM Student, SC
WHERE Student.Sno = SC.Sno;
```

如果还要查询计算机系每一个学生的情况，就追加一个筛选条件：

```sql
SELECT *
FROM Student, SC
WHERE Student.Sno = SC.Sno
  AND Student.Sdept = 'CS';
```

这就是多表查询中唯一需要特别记住的地方：`FROM` 中有几个表就写几个；`WHERE` 中先写连接条件，再写筛选条件。连接条件千万不能漏。

> **提示**：SQL 是高度非过程化语言。我们提出查询需求，数据库管理系统自动选择执行方式。连接可能用循环嵌套、排序合并或索引连接等策略完成，具体执行过程不必逐个记，但连接条件必须由我们写清楚。

#### 自然连接

普通等值连接会把参与连接的两个学号列都输出。如果两个参与连接的属性在值上完全一致，可以手动删掉其中一个重复列，得到自然连接。

关系代数里可以直接用 `NATURAL JOIN` 表示自然连接；SQL 中没有对应的简写，因此就把需要的字段逐个写出来，避免重复输出。

#### 连接与筛选一起出现

查询“选修了 2 号课程，且成绩在 90 分以上的所有学生的学号和姓名”。输出的字段是 `Sno`、`Sname`，输入涉及课程号与成绩，涉及 `Student`、`SC` 两张表，筛选条件则包括课程号、成绩以及两表学号相等。

```sql
SELECT Student.Sno, Student.Sname
FROM Student, SC
WHERE Student.Sno = SC.Sno
  AND SC.Cno = 2
  AND SC.Grade > 90;
```

它与单表查询没有本质区别，只是 `FROM` 多了一张表，`WHERE` 多了连接条件。

#### 自身连接

自身连接用于处理同一张表需要查询两次的问题。查询每门课程的间接先修课，实际需要从“数据库”沿先修关系找到“数据结构”，再从“数据结构”继续找到“Pascal 语言”。如果只查一遍当然找不到这个联系；如果直接写成两表查询，又不是两个真实存在的表。

> **定义**：一个表在查询中被引用两次，就先在思路上把它复制为两个表，再用普通多表查询处理。

复制后的表分别起名，例如 `First` 与 `Second`。按 `First.Cpno = Second.Cno` 建立连接，输出 `First.Cno` 与 `Second.Cpno`，就得到了每门课程的间接先修课：

```sql
SELECT First.Cno, Second.Cpno
FROM Course First, Course Second
WHERE First.Cpno = Second.Cno;
```

一个表空格后加别名，就是一个可引用的表；两个别名表示同一张原始表被使用两次。这里的 `First` 与 `Second` 只表示两个角色，名字换成 `A`、`B` 同样可以。

这个例子体现了输入输出分析法的边界：能直接对应时直接用，不完全符合时先转换结构，再回到输入输出分析法。遇到“同表查两次”，应立刻想到自身连接。

### 外连接：一个也别丢

普通等值连接按学号相等的条件筛选，会自动删除没有匹配值的元组。

假设班里有 5 个同学，只有 4 个人抢到了课，那个没有选课的同学就会从连接结果中消失。这不是他的学号“配错了”，而是他根本没有选课记录，所以没有值能与另一张表相等。他被删得很委屈。

如果作为班主任，我们想了解全班的选课情况，就不能因为某个人没选课，就假装这个人不存在。外连接的作用正是保留这些没有匹配项的元组；无法匹配的位置用空值表示。

> **定义**：保留一侧表的所有数据，另一侧没有对应记录时用空值占位，称为外连接。

| 类型 | 保留规则 |
| --- | --- |
| 左外连接 | 保留左表所有元组，右表无匹配时以空值占位 |
| 右外连接 | 保留右表所有元组，左表无匹配时以空值占位 |
| 整体外连接 | 两侧元组都保留 |

左外连接写作 `LEFT OUTER JOIN`，连接字段写在 `ON` 后：

```sql
SELECT Student.Sno, Student.Sname, SC.Cno, SC.Grade
FROM Student
LEFT OUTER JOIN SC ON Student.Sno = SC.Sno;
```

如果还要附加其他筛选条件，再在 `WHERE` 中继续写。

### 多表连接

多表连接就是两个以上的表共同参与查询。查询“每个学生的学号、姓名、选修的课程名和成绩”，只需分析字段来源：

- `Sno`、`Sname` 来自 `Student`；
- `Cno`、`Grade` 来自 `SC`；
- `Cname` 来自 `Course`。

没有额外筛选条件，但必须先把三个表连接起来：

```sql
SELECT Student.Sno, Student.Sname, Course.Cname, SC.Grade
FROM Student, SC, Course
WHERE Student.Sno = SC.Sno
  AND SC.Cno = Course.Cno;
```

先写连接，再输出需要的字段，多表连接就完成了。

### 嵌套查询：把查询块套起来

一个完整的 `SELECT FROM WHERE` 可以看成黑盒子：有输入，经过处理，产生输出。既然输出可以成为下一个查询块的输入，就可以首尾相接，把查询块一层层嵌套起来。

内层叫子查询，外层叫父查询或外层查询。子查询先执行，将结果交给父查询，父查询再利用这个结果继续处理。

```sql
SELECT Sname
FROM Student
WHERE Sno = 95001;
```

例如，内层先查出选了 2 号课的学生学号，外层再用这个学号查姓名，这就把两个查询块串成了一个整体。

> **定义**：不同查询块套在一起，就是嵌套查询。

嵌套查询可以套两层、三层甚至更多层，没有固定层数。但子查询不能使用 `ORDER BY`：它只是中间过程，最终排序应在最外层完成，在中间层排序不会影响最终输出。

#### 不相关子查询

子查询的查询条件不依赖父查询，就叫不相关子查询。它可以先独立完成，再把结果交给外层。

查询“与刘晨在同一个系学习的学生”时，先固定找出刘晨的专业，再查找该专业的学生：

```sql
SELECT Sno, Sname, Sdept
FROM Student
WHERE Sdept IN (
    SELECT Sdept
    FROM Student
    WHERE Sname = '刘晨'
);
```

内层的 `Sdept = '刘晨'` 这一筛选条件是固定的，不依赖外层传来的任何值，因此是不相关子查询。

这个题也能通过自身连接完成。但两种查询的主要区别是系统效率：连接查询不可避免地涉及笛卡尔积和筛选，中间要占内存；嵌套查询按表逐层处理，没有这个笛卡尔积过程，系统效率相对更高。

#### 先由内向外，再逐层向外

如果一个查询可以拆成几步，就先执行最先做的事，再执行下一步。

查询“选修了课程名为信息系统的学生学号和姓名”。学生表里只有课程编号，没有课程名，而课程名在 `Course` 表中。查询思路自然拆成三步：

1. 在 `Course` 中找出课程名为“信息系统”的课程号；
2. 用这个课程号到 `SC` 中找选课学生学号；
3. 用这些学号到 `Student` 中找学生姓名。

最先做的放最内层，中间做的放第二层，最后做的放最外层：

```sql
SELECT Sno, Sname
FROM Student
WHERE Sno IN (
    SELECT Sno
    FROM SC
    WHERE Cno IN (
        SELECT Cno
        FROM Course
        WHERE Cname = '信息系统'
    )
);
```

代码行数多，不代表查询难。只要按“最先做的写最里层”的顺序展开，逻辑非常简单。

如果内层只产生唯一值，`=` 与 `IN` 在语义效果上可以互相替代；需要 `IN` 的原因不在这道题本身，而在嵌套结构中要先把中间结果传出来。

#### 相关子查询

相关子查询的筛选条件依赖父查询。外层的当前元组要先传给内层，内层处理后返回结果，外层再继续判断。

例如，“找出每个同学超出他选修课程平均成绩的课程号”。对第一个同学，先计算他的平均成绩，再比较每门课的成绩是否超过该平均分；若超过则输出，否则不输出。

```sql
SELECT Sno, Cno
FROM SC x
WHERE Grade > (
    SELECT AVG(Grade)
    FROM SC y
    WHERE y.Sno = x.Sno
);
```

这里，`SC x` 不是把表复制成两个表，而是从表中取出一个元组。`x` 表示外层当前行，内层通过 `y.Sno = x.Sno` 接收这个学号，再计算该学号的平均成绩。

> **易错点**：自身连接中，`Course First, Course Second` 是两个表角色；相关子查询中，`SC x` 只有一个表，单独写一个别名表示当前元组。

`SC x` 这样的写法表示取出一行进行逐行处理。外层从第一条记录开始，把当前元组的 `x.Sno` 传入内层，内层按这个学号求 `AVG(Grade)`；外层拿这个平均分与 `x.Grade` 比较，满足条件才输出。随后再取外层下一条元组，重复这一过程，直到外层所有元组检查完毕。

#### `ANY` 与 `ALL`

`ANY` 表示“任意一个”，`ALL` 表示“全部”。例如“年龄小于 `ANY` 集合中的任意一个值”，写作 `< ANY (...)`；“年龄小于 `ALL` 集合中的全部值”，写作 `< ALL (...)`。这些表达不要死记，能把整句语义读懂即可。

查询“非计算机科学系中，比计算机科学系中任何一个学生年龄小的学生姓名和年龄”，外层还要加 `Sdept != 'CS'`：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sdept != 'CS'
  AND Sage < ANY (
      SELECT Sage
      FROM Student
      WHERE Sdept = 'CS'
  );
```

这里不需要死记“`小于ANY` 对应什么”——从集合角度看，“小于任意一个”就是存在一个计算机系学生年龄比当前学生大。只要找出计算机系的最大年龄，再让外层年龄小于这个值即可。

同理，小于 `ALL` 等价于小于最小值，大于 `ALL` 等价于大于最大值，大于等于 `ALL` 等价于大于等于最大值。

#### `EXISTS`

`EXISTS` 是存在量词，表示“是否存在”。

它与其他谓词有一点不同：子查询不返回具体数据，只返回 `TRUE` 或 `FALSE`。内层结果非空则返回真，空则返回假；返回真时，才能作为筛选条件让最外层输出。

因此，`EXISTS` 子查询的输出字段写什么其实不影响结果。写具体字段没有意义，直接写 `*` 更省事：

```sql
SELECT Sname
FROM Student
WHERE EXISTS (
    SELECT *
    FROM SC
    WHERE SC.Sno = Student.Sno
      AND SC.Cno = 1
);
```

这段查询就是“看看有没有学生选了 1 号课程”，有则输出该学生姓名。`NOT EXISTS` 则是反过来：检查内层是否不存在符合条件的记录。

> **结论**：理解 `EXISTS` 的关键不在于记复杂语法，而在于读懂：内层只给真或假；非空为真，空为假。

### 集合查询：并、交、差

第二章关系代数中，并、交、差与笛卡尔积属于传统集合运算。第三章中，它们对应为 SQL 的集合查询，常用的就是 `UNION`、`INTERSECT`、`EXCEPT` 三种。

集合查询的价值在于化繁为简：把复杂条件拆成几个简单查询，再让结果集之间进行集合运算。

#### `UNION` 与 `UNION ALL`

查询“计算机系的学生和年龄不大于 19 岁的学生”。这可以拆成“计算机系学生”与“年龄不大于 19 岁学生”两个结果，再求并集：

```sql
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sdept = 'CS'
UNION
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sage <= 19;
```

默认情况下，`UNION` 会自动去掉重复元组。如果不想去重，则用 `UNION ALL`。

例如，查询选了 1 号课或选了 2 号课的学生，只需分别查出选 1 号课与选 2 号课的结果，再使用 `UNION` 合并。

#### `INTERSECT`

查询“计算机科学系中，年龄不大于 19 岁的学生”。这相当于两个结果集取交集：

```sql
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sdept = 'CS'
INTERSECT
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sage <= 19;
```

连接查询、嵌套查询、集合查询都能完成这类任务。

#### `EXCEPT`

查询“计算机科学系中，年龄大于 19 岁的学生”。这相当于计算机系学生集合减去年龄不大于 19 岁的学生集合：

```sql
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sdept = 'CS'
EXCEPT
SELECT Sno, Sname, Sdept, Sage
FROM Student
WHERE Sage <= 19;
```

集合查询并不神秘，它只是把题目拆成几个容易写的结果，再让结果集做并、交、差。

### 基于派生表的查询

有时题目并没有现成的表可以直接使用，但查询中会算出一个稳定复用的中间结果。这个中间结果就是派生表。

比如平均成绩并没有天然存在一张表中，它是根据选课记录计算出来的。但我们可以把“每位学生的平均成绩”单独算出来，作为一个新表。以后再次涉及谁与平均分比较，就直接调用这个表。

> **定义**：由基本表经过查询得到的中间结果表，称为派生表。包含派生表的查询，称为基于派生表的查询。

仍然以“找出每个学生超过他选修课程平均成绩的课程号”为例。与逐行执行相关子查询不同，可以把它拆成两步：

1. 在选课表中按学号分组，先算出每位学生的平均成绩；
2. 把平均成绩结果作为派生表，与 `SC` 连接，再筛选超过平均成绩的课程。

第一步按学号分组，用 `AVG(Grade)` 计算各组平均分：

```sql
SELECT Sno AS Avg_Sno, AVG(Grade) AS Avg_Grade
FROM SC
GROUP BY Sno;
```

把这段查询放进括号并起别名，就形成了派生表 `Avg_SC`。它有两列：`Avg_Sno` 保存学号，`Avg_Grade` 保存每位学生的平均成绩。

第二步用普通的 `JOIN` 即可：

```sql
SELECT SC.Sno, SC.Cno
FROM SC
JOIN (
    SELECT Sno AS Avg_Sno, AVG(Grade) AS Avg_Grade
    FROM SC
    GROUP BY Sno
) AS Avg_SC
ON SC.Sno = Avg_SC.Avg_Sno
WHERE SC.Grade > Avg_SC.Avg_Grade;
```

> **结论**：派生表和基本表在查询中都是表，涉及多个表时，同样必须建立连接。

### 把查询写在一起

到这里，数据查询问题可以完整地分成四种：单表查询、连接查询、嵌套查询、集合查询。

单表查询是基础，连接、嵌套、集合查询处理的都是涉及两个或三个表的问题。它们可以互相替代，哪个简单就用哪个。

`SELECT` 语句的一般形式仍然是：

```text
SELECT [DISTINCT] 目标列
FROM 基本表或派生表
WHERE 筛选条件
GROUP BY 分组列
HAVING 分组后的筛选条件
ORDER BY 排序列
```

- `SELECT` 处理输出，可以包含 `DISTINCT`、聚集函数和表达式；
- `FROM` 处理输入，可以来自基本表，也可以来自派生表；
- `WHERE` 处理筛选条件；
- `GROUP BY` 与 `HAVING` 处理分组问题；
- `ORDER BY` 处理最终排序。

> **易错点**：`WHERE` 与 `HAVING` 不能同时用于同一个查询块。存在 `GROUP BY` 时，要对分组后的结果筛选，就使用 `HAVING`。

`ORDER BY` 默认升序（`ASC`）。空值排序的默认规则是“大头在前”，空值排在大值一侧。谓词、聚集函数、表达式以及字符串匹配等具体语法，前面已经逐个讲过；把前面几个例子逐个看懂，查询部分便能串起来。

至此，单表与多表查询就全部讲完了。数据操作中，“增删改查”以查询最复杂。接下来要解决的，是增加、删除、修改数据、空值、视图，以及最后对本章的整体总结。

> **承前启后**：上一节讲完「SQL 多表查询的三条路」，下一节接着讲「SQL的数据更新、空值与视图」。

## SQL的数据更新、空值与视图
> 对应块：BLK12 | 覆盖分集：P10 | 块标题（分集名）：《数据库第3章 SQL（第三部分：数据更新与视图-》

前面花了最多时间讲查询：单表查询、多表查询、嵌套查询、集合运算，再到分组和聚集函数。现在终于轮到“往数据库里放数据、把数据改掉、把数据删掉”，反而会发现它们比查询简单得多。

这里先给大家一个心理准备：SQL是高度非过程化的语言。你告诉数据库“我想干什么”，至于它原来怎么存、中间经过什么步骤，通常不需要你操心。更新语句看起来短，并不是因为它省略了重要原理，而是因为它把“怎么做”交给了数据库。

### 先把SQL的地图摊开

SQL语言服务于数据库管理系统的功能，通常分成三块：

- 数据定义语言，DDL，负责数据的定义。我们已经讲过模式、表、索引，也知道了视图的建立、修改和删除。
- 数据操作语言，DML，负责数据的增加、删除、修改和查询，简称增、删、改、查。
- 数据控制语言，DCL，负责数据的控制，安全性、完整性等问题会放到后面的章节里。

查询是DML里最复杂的一块。查询讲完之后，增删改三件事就接了上来；再把空值的处理补上，DML这一圈才算完整。

视图比较特别：它从形式上属于数据定义，因为它要建立、删除一个对象；但视图里面的值又不是单独存一份，而是通过查询从基本表映射出来。因此必须先理解数据定义，再理解查询和更新，最后才方便把视图接起来。

```text
SQL语言
├─ 数据定义（DDL）
│  └─ 模式、表、索引、视图
├─ 数据操作（DML）
│  └─ 查询、插入、修改、删除
└─ 数据控制（DCL）
   └─ 安全性、完整性

视图：DDL负责定义，DML负责取用和修改
```

> **结论**：增删改查不是四门互不相干的课。查询是后面插入、修改、删除以及视图建立时反复使用的基础。

### 插入数据

插入有两种方式：一种是插入一个元组，也就是放一行；另一种是插入子查询的结果，一次放进去一组元组。先不要把它们混成一个命令，关键在于“待插入的值到底是一行，还是多行”。

#### 一行一行地插入

最常见的写法是 `INSERT INTO ... VALUES ...`。`INSERT` 表示要放数据，`INTO` 指定目标表和属性列，`VALUES` 给出要写入的具体值。

```sql
INSERT INTO <表名> (<列名1>, <列名2>, ...)
VALUES (<值1>, <值2>, ...);
```

这里目标列和值的个数、顺序、类型要对应起来。`VALUES` 后面放的是这一次要写入的常量，不是先从表里查出来的旧值。

比如要记录一个新转来的同学，就把它放到 `Student` 表中。表里有学号、姓名、性别、所在系、年龄这几列，那么插入时把这些列和值一一对应起来即可。写清楚目标列，再把值按同样的顺序写进去，新同学的一行就放进去了。

实际写程序时，我更建议把列名明确写出来。不要为了少写几个字，就把列名省掉。程序通常不会只有这三四行代码，它会嵌在更大的程序里；明确写出列名，既不容易因为表结构理解偏差而出错，将来出错时也更容易知道错在什么地方。这一点花不了多少时间，却能省掉很多麻烦。

#### 缺少成绩时怎么插

选课表 `SC` 有学号、课程号和成绩三列。如果一个同学选了一号课，但还没有考试，成绩暂时没有值，这时有两种写法。

一种是只指定要填的两列，让第三列不参与这次插入：

```sql
INSERT INTO SC (Sno, Cno)
VALUES ('200215128', 1);
```

另一种是明确告诉数据库，第三列没有值，用 `NULL` 占位：

```sql
INSERT INTO SC (Sno, Cno, Grade)
VALUES ('200215128', 1, NULL);
```

两种都能表达“已经选课，但暂时没有成绩”。不过在我这里，第二种主要用于确实需要体现全部列结构的场合；一般开发时还是把要写入的列写出来，代码会更稳。

#### 用子查询一次放一组

真实的数据处理往往不是只增加一行。一个班有很多同学，系里有很多专业，我们更常见的需求是：一次把一批结果放进去。

这时要用子查询。`SELECT ... FROM ... WHERE ...` 是一个查询块，它接收筛选条件，输出一组结果；把这样的结果接到 `INSERT` 后面，就可以一次插入多个元组。

可以把目标表先理解成两列：一个系名，一个平均年龄。表名只是为了叙述方便，关键是它保存“每个系一行，每行是该系的平均年龄”。然后用下面的形式把 `Student` 表里的结果送进去：

```sql
INSERT INTO DeptAge (Sdept, AvgAge)
SELECT Sdept, AVG(Sage)
FROM Student
GROUP BY Sdept;
```

这里没有 `WHERE`，因为要求的是所有系；`GROUP BY Sdept` 把学生按专业分组，`AVG` 分别作用于每一组。比如计算机专业这一组计算出平均年龄是20，数学专业那一组计算出平均年龄是21，就把这两行结果放进新表。

这就是聚集函数遇到分组以后的关键变化：不分组时，它作用于整体；一旦分组，它就分别作用于每个组。不要把“聚集函数分别计算每一组”理解成只计算了一个平均值。

子查询结果的列数和类型也必须和目标表匹配。查询输出几列，目标表就要接收几列；每一列的含义和类型也要对得上，不然数据库放不进去。

> **易错点**：`INSERT ... VALUES` 适合一行；`INSERT ... SELECT` 适合一组。子查询不是把查询结果“看起来像”数据，而是真的可以作为待插入的数据集合。

#### 插入也要过完整性这一关

插入之前，数据库要检查原来表上的完整性约束。实体完整性要求主属性不能取空值；参照完整性要求外码和被参照表的主码之间保持对应；用户定义的完整性则是我们自己规定的取值范围，比如性别只能填男或女，年龄只能在15到55之间。

如果新数据违反了这三方面的约束，插入就不能放进去，数据库会直接报错。不要以为“只是增加一行”就可以绕过规则，插入和修改面对的是同一组约束。

### 修改数据

修改数据同样是三段式：

```text
UPDATE  SET  WHERE
```

`UPDATE` 指定要改哪张表，`SET` 指定哪一列要改成什么值或表达式，`WHERE` 给出筛选条件。只有满足条件的元组，才会真正被修改。

#### 改一行、改多行、改一个范围

最直接的情况是修改一个元组。例如把学号为 `201215121` 的学生年龄改成22：

```sql
UPDATE Student
SET Sage = 22
WHERE Sno = '201215121';
```

这里最值得注意的是：我并不需要先查这个学生原来几岁。原来是多少，我根本不关心；我告诉数据库把这一行的 `Sage` 改成22，它就改。这正是SQL高度非过程化的体现。

如果没有 `WHERE`，就会作用于所有行：

```sql
UPDATE Student
SET Sage = Sage + 1;
```

这不是“增加一个叫 `Sage+1` 的新列”，而是要把每一行原有的年龄都加1。比如过了一年，大家年龄都要加一岁，就可以用这种方式表达。数据库会自己读取每一行的旧值、算出新值，再写回去；写程序的人不用自己逐行处理。

第三种是利用子查询确定修改范围。比如把计算机科学系全体学生的成绩清零。`SC` 表里只有学号、课程号和成绩，想知道哪些学号属于计算机系，就去 `Student` 表里查：

```sql
UPDATE SC
SET Grade = 0
WHERE Sno IN (
    SELECT Sno
    FROM Student
    WHERE Sdept = 'CS'
);
```

`IN` 把子查询返回的学号集合拿来筛选 `SC` 表。子查询负责找范围，外层更新负责改范围内的数据，这就是“一次处理一堆数据”的思路。

修改同样要检查完整性约束。比如把性别误写成99，或者把成绩误写进了别的列，数据库都不能让你把错误值放进去。插入时不能违反的约束，修改时也不能违反。

### 删除数据

删除的格式很短：

```sql
DELETE FROM <表名>
WHERE <筛选条件>;
```

`DELETE FROM` 指定表，`WHERE` 指定要删除哪些行。没有 `WHERE`，就是把这个表里的数据全部清空。

例如，某个同学毕业了，就按他的学号删除 `Student` 表中的那一行；如果要清空选课表中的所有数据，可以写：

```sql
DELETE FROM SC;
```

如果只删除计算机科学系学生的选课记录，仍然用子查询先找出这些学号：

```sql
DELETE FROM SC
WHERE Sno IN (
    SELECT Sno
    FROM Student
    WHERE Sdept = 'CS'
);
```

这里删除的是数据行，不是把表本身删掉。删除操作按照条件移除数据，表的基本框架还在；因此它和把表直接删除的 `DROP TABLE` 不是一回事。

### 空值不是“空”

空值表示不知道、不存在，或者没有意义。比如一个同学已经选课但还没有考试，我们不知道他的成绩；某个属性本来就不应该有值；或者由于某种原因暂时不便填写，都会涉及空值。

#### 空值从哪里来

空值最常见的来源是插入。给 `SC` 插入选课记录时只提供了学号和课程号，成绩没有提供；或者明确把成绩写成 `NULL`，空值就产生了。

更新也会制造空值。比如学号为 `201215210` 的同学转专业，目前还没有专业接收他，那么此刻他的所在系就可以暂时是空值：

```sql
UPDATE Student
SET Sdept = NULL
WHERE Sno = '201215210';
```

这里的空值不是空字符串，也不是0，更不是“还没有来得及输入但数据库知道它应该是多少”。它表示数据库目前不能给出这个属性的值。

#### 用 `IS NULL` 找出漏填的信息

空值判断在管理信息时非常有用。假设老师收到一张有一千行、十几列的信息表，如果要靠眼睛一行行找哪个人漏填了信息，工作量会非常大。更好的办法是直接把含有空值的整行拎出来。

`SELECT *` 表示把匹配行的全部字段都取出来。因为学号是主属性，不能为空，所以只需要检查另外几个字段：

```sql
SELECT *
FROM Student
WHERE Sname IS NULL
   OR Ssex IS NULL
   OR Sage IS NULL
   OR Sdept IS NULL;
```

只要某一行有一个字段是空值，这条 `OR` 条件就成立，整行就会被输出。老师一眼就能看出哪个同学哪一栏没有填。

> **提示**：判断空值要用 `IS NULL`。空值不是一个可以拿来做普通大小比较的普通数。

表定义中的约束也要和空值区分开。`NOT NULL` 明确表示这一列不能为空；主属性受实体完整性约束，同样不能为空。对于唯一属性，空值也无法用来证明“不重复”，所以实际数据中不要把应当唯一的属性留空。

#### 三值逻辑：除了真和假，还有未知

空值参与算术运算时，结果还是空值。比如空值和1相加、相减、相乘、相除，结果都还是一个“不知道”。空值和另一个值作比较时，结果也不是简单的真或假，而是 `UNKNOWN`。

于是，SQL里就不只是传统的二值逻辑了，而是扩展成三值逻辑：真、假、不知道。下面只列出理解这一变化最关键的几格：

| X | Y | `X AND Y` | `X OR Y` | `NOT X` |
|---|---|---|---|---|
| TRUE | TRUE | TRUE | TRUE | FALSE |
| TRUE | UNKNOWN | UNKNOWN | TRUE | FALSE |
| UNKNOWN | TRUE | UNKNOWN | TRUE | UNKNOWN |

真和未知放在一起做“并且”，结果仍然未知，因为不能只靠其中一个真就断定整个条件成立；真和未知做“或者”，只要有一边是真，结果就可以是真。未知取反以后还是未知。这个表不用死记，知道它为什么这样，扫一眼就能推出来。

#### “没及格”不能只写小于60

空值最容易在查询中把人绊住。题目要求“找出一号课没有及格的学生”，如果只写成绩小于60：

```sql
SELECT Sno
FROM SC
WHERE Cno = 1
  AND Grade < 60;
```

这个写法看起来很顺，但它不完整。因为 `NULL` 和60不能比较大小，缺考同学的成绩不会出现在这个结果里。可是“没有参加考试”当然也不能算及格。

所以要把“成绩小于60”和“成绩为空”放在一起：

```sql
SELECT Sno
FROM SC
WHERE Cno = 1
  AND (Grade < 60 OR Grade IS NULL);
```

这仍然是一个单表查询。也可以用集合运算来做：分别查出一号课中小于60分的学号，再查出一号课中成绩为空的学号，最后把两个结果合并起来。两条查询路线都能得到“我想看的学生”，这就是同一道题的多重做法。

到这里，数据的增加、修改、删除、查询，再加上空值的判断与处理，DML的部分就连起来了。查询可以用 `SELECT ... FROM ... WHERE ...`，需要时再配合 `GROUP BY`、`HAVING` 和 `ORDER BY`；插入用 `INSERT ... VALUES` 或 `INSERT ... 子查询`；修改用 `UPDATE ... SET ... WHERE`；删除用 `DELETE FROM ... WHERE`。记住这些语句各自负责的事情，比死记某一个例子更重要。

### 视图：把查询固定成一个表的样子

#### 视图到底是什么

学生表、课程表和选课表是基本表，视图则是在基本表之上形成的一个映射结果。比如学生表里有五列，我只想看姓名和年龄之间的关系，就可以把这两列映射出来，形成一个看起来像表的对象。

这就是视图的特点：它是一个虚表。视图的值来自基本表，视图本身只保存定义，不保存一份独立的数据。基本表的数据发生变化，查询视图得到的结果也会随之变化。

```text
基本表（真正存放数据）
        │
        │ 查询、映射
        ▼
视图（只保存查询定义）
        │
        │ 插入 / 修改 / 删除
        ▼
基本表中的数据发生变化
```

> **定义**：视图是建立在基本表之上的虚表；它保存的是查询定义，而不是查询结果的一份副本。

#### 建立视图

建立视图的格式如下：

```sql
CREATE VIEW <视图名> [(<列名1>, <列名2>, ...)]
AS <子查询>
[WITH CHECK OPTION];
```

视图名和列名可以自己取，但要让别人看代码时知道它代表什么，所以命名最好带上信息。比如 `IS_Student`，就能看出它和信息系学生有关；名字叫 `XYZ` 虽然语法上可以，别人读起来却不直观。

例如，把计算机科学系的学生单独抽成一个视图：

```sql
CREATE VIEW CS_Student AS
SELECT *
FROM Student
WHERE Sdept = 'CS';
```

这个视图的值不是重新抄了一份保存，而是每次都可以沿着这个查询去基本表里取。

如果希望以后通过这个视图插入或修改数据时，修改后的内容仍然满足“必须是计算机科学系学生”這個条件，就加上 `WITH CHECK OPTION`：

```sql
CREATE VIEW CS_Student AS
SELECT *
FROM Student
WHERE Sdept = 'CS'
WITH CHECK OPTION;
```

有了它，对视图进行插入、修改、删除时，数据库会自动检查值是否仍满足建立视图时的条件。没有写这句话，就表示这个视图不替你做这项检查；你更新时不能把条件之外的值通过这个视图带进来。

这里还要分清两件事：视图的“框架”可以建立和删除，但不提供一般意义上的结构修改；如果想改映射关系，最直观的做法通常是删掉旧视图再重新建立。后面会把视图名的修改和视图数据的更新分别说清楚。

#### 列名可以省略，但不要随便偷懒

组成视图的属性列名可以全部省略，也可以全部指定。像前面的 `CS_Student`，查询结果有哪些列，视图就有哪些列；如果要自定义列名或明确展示结构，就把这些列名写在视图名后面。

建立信息系学生视图时，可以只取学号、姓名和年龄：

```sql
CREATE VIEW IS_Student (Sno, Sname, Sage)
AS
SELECT Sno, Sname, Sage
FROM Student
WHERE Sdept = 'IS'
WITH CHECK OPTION;
```

学生表本来有五列，这个视图只取其中三列；专业列没有进入视图，所以这个视图中的每一行都应当仍然是信息系的学生。若不允许通过它改出别的专业，就保留 `WITH CHECK OPTION`。

还要注意：关系数据库管理系统执行 `CREATE VIEW` 时，只是把视图定义放进数据字典，并不会当场执行里面的 `SELECT` 去把结果抄一份出来。等真正查询视图时，系统才按照定义去取数据。

#### 行列子集视图

如果一个视图只来自一个基本表，只是在这个表的基础上去掉某些行、去掉某些列，同时保留主码，就叫行列子集视图。前面把计算机系学生抽出来的视图，以及把学生表五列缩成三列的信息系学生视图，都符合这个特征。

“行子集、列子集”说的是基本表中的行和列被取出了一部分；保留主码，则是为了让视图中的记录仍然能够对应到确定的实体。

#### 多个基本表也能形成视图

视图不一定只来自一个基本表。比如要建立“信息系学生选修一号课程”的视图，就需要同时使用 `Student` 和 `SC`：学号、姓名来自学生表，成绩来自选课表。

```sql
CREATE VIEW IS_S1 (Sno, Sname, Grade)
AS
SELECT Student.Sno, Student.Sname, SC.Grade
FROM Student, SC
WHERE Student.Sdept = 'IS'
  AND SC.Cno = 1
  AND Student.Sno = SC.Sno;
```

这里最不能忘的是连接条件：`Student.Sno = SC.Sno`。两个表放在一起之后，如果不说明怎样对应，学号和成绩就无法正确配起来。这个查询输出三列，视图也就定义三列；其中两列来自学生表，一列来自选课表。

多个基本表组成的视图，不再是前面那种单一基本表上的行列子集视图。

#### 视图上的视图、表达式和分组

既然视图可以像表一样使用，也就可以在视图的基础上再建立视图。例如已经得到“信息系选修一号课程”的 `IS_S1`，还可以从中找成绩大于90的学生：

```sql
CREATE VIEW IS_S2 (Sno, Sname, Grade)
AS
SELECT Sno, Sname, Grade
FROM IS_S1
WHERE Grade > 90;
```

视图的定义里还可以带表达式，查询中做过的运算结果也可以直接成为视图的列。分组、聚集函数同样可以放进视图的定义中。

例如，把学生的学号和平均成绩定义成视图，就要按学号分组，让 `AVG` 分别计算每个学生所选课程的平均成绩：

```sql
CREATE VIEW StudentAvg (Sno, AvgGrade) AS
SELECT Sno, AVG(Grade)
FROM SC
GROUP BY Sno;
```

一号同学的几门课算出一个平均分，二号同学的几门课再算出另一个平均分；视图最后得到的是“每个学生一行”的结果。这里仍然是那条规律：分组以后，聚集函数分别作用于每一个组。

也可以把所有女生定义成视图，查询条件直接写成 `Ssex = '女'`。不过，如果使用 `SELECT *`，就不太推荐。因为基本表以后增加一列时，星号输出的列数会跟着变化，而原来建立的视图可能只按旧的列数定义，结构就接不上了。所以，视图里尽量把需要的列明确列出来。

#### 删除视图时的级联与限制

删除视图的语句是：

```sql
DROP VIEW <视图名>;
```

它还会涉及 `CASCADE` 和 `RESTRICT` 两种选择。`CASCADE` 是级联删除：如果这个视图上又建立了其他对象，删除它时把依赖的对象一起删掉。`RESTRICT` 是限制删除：系统发现还有东西依赖这个视图，就拒绝执行，并提醒你先处理依赖对象。

默认是 `RESTRICT`。例如先建立了 `IS_S1`，又在它的基础上建立了成绩筛选后的 `IS_S2`，此时直接删除 `IS_S1` 就会被拒绝，因为 `IS_S2` 依赖它。确实要一起删除时，才加上：

```sql
DROP VIEW IS_S1 CASCADE;
```

这样，依赖它的视图也会随之删除。删除视图和删除表数据一样，都是在处理对象或数据，不能只看到“删掉”两个字就以为所有情况都一样。

### 在视图上查询和更新

#### 查询视图像查询基本表

因为视图在外表看来就是一个表，所以查询视图的语法和查询基本表基本相同。例如，在信息系学生视图中找年龄小于20岁的同学：

```sql
SELECT Sno, Sname, Sage
FROM IS_Student
WHERE Sage < 20;
```

系统内部可以用“视图消解法”把视图转换成基本表上的运算。它会把 `IS_Student` 还原为 `Student` 上的查询，并补上视图定义中的条件：

```sql
SELECT Sno, Sname, Sage
FROM Student
WHERE Sage < 20
  AND Sdept = 'IS';
```

输出结果不变。视图消解是系统内部实现查询的一种办法，学习时不用钻进它的实现细节；重要的是理解：视图是表，所以对它的查询和对基本表的查询遵循同样的使用方式。

查询平均成绩视图时，如果要筛选平均成绩大于等于90的学生，可以直接查询视图：

```sql
SELECT Sno, AvgGrade
FROM StudentAvg
WHERE AvgGrade >= 90;
```

也可以直接在 `SC` 表上按学号分组，并用 `HAVING` 筛选平均成绩：

```sql
SELECT Sno, AVG(Grade)
FROM SC
GROUP BY Sno
HAVING AVG(Grade) >= 90;
```

这里不要把对平均值的筛选误写成普通行条件。`WHERE` 如果使用，是在分组前筛选原始记录；`HAVING` 是分组以后筛选分组结果的。平均成绩是由一组成绩算出来的，筛选它自然要放在分组之后。

#### 视图结构不能随便改

视图没有一般意义上的结构修改功能，主要原因是它保存的是基本表上的映射关系，而不是一份独立数据。如果想改变这个映射关系，直接把旧视图删掉再按新的定义建立，通常更直观。

这里有一个容易混淆的例外：视图名本身可以修改。真正需要改的是视图所代表的列、来源表和查询条件时，就不要在旧映射关系上打补丁，删掉重建更清楚。

#### 视图中的数据怎么更新

对视图中的数据进行插入、修改、删除时，写法仍然和基本表一样，仍然是：

```text
INSERT ... VALUES
UPDATE ... SET ... WHERE
DELETE FROM ... WHERE
```

系统会把这些操作转换到视图所依据的基本表上。比如在信息系学生视图中把某个学号对应的姓名改成“刘晨”，外层看是在更新视图，实质上是在更新它映射到的学生记录。

但是，不是所有视图都能随便更新。要记住一个结论：行列子集视图可以进行数据的增加、删除和修改；通过多个基本表组合出来的视图，尤其是还经过计算、分组、聚集之后得到的视图，通常不能直接更新。

为什么平均成绩不能随手改？想象一下，教务处手里有一张成绩单，你想把平均分从90改成95。可是这个平均分对应的是几十门课程最后算出来的结果，你到底要改哪几门课，才能让它们重新得到95？这不是改一个显示出来的数字就能完成的事情。同理，多表组合和复杂运算的结果也不一定能被反向拆回原始数据。

> **易错点**：视图“不能修改结构”和视图“不能更新数据”不是一回事。前者通常要删除后重建；后者取决于视图是不是保留了可更新的行列子集。

不同系统对视图更新的限制可能还有细节差异，所以不要把所有视图一概而论。能更新的按基本表方式更新，不能更新的就删掉重建，思路要分清。

### 视图有什么用

视图不是只为了把一条长查询换个名字，它在日常使用里有几个很实际的作用。

第一，可以简化用户操作。教务处老师如果经常查看平均分、最高分、最低分，或者某个班的方差，就可以把常用结果分别定义成视图。数据更新进基本表之后，再查这些视图就能直接得到结果，不必每次都重新写一长串查询。

第二，可以让同一个基本表从不同角度被查看。同一个学生表，可以从姓名和年龄看，也可以从性别和年龄看，还可以从姓名和所在专业看。数据只有一份，观察它的角度可以不止一种。

第三，可以提供一定的逻辑独立性。基本表出了问题，或者原始数据发生了较大变化，原来建立在它上面的视图仍然可以作为理解原来数据结构的参照。视图保存的是一种查询定义和关系，不等于把基本表里的每一个字节都复制一份。

第四，可以保护机密数据。一个表里可能放着学生全部信息，但给教务处老师看的只需要教务相关内容。直接建立一个只包含相关字段的视图，财务、成绩或其他不相关的数据根本不会出现在他看到的范围内。看不到的数据，比只在口头上提醒“不要看”更可靠。

第五，可以让查询表达得更清楚。信息系学生、选修了指定课程的学生、成绩超过某个分数的学生，都可以先定义成清晰的视图，再在这些范围上继续查询。复杂条件被封装在有意义的名称后面，使用者就不必每次都从原始表开始拼条件。

### SQL这一章的闭环

回头看这一章，SQL的主干就很清楚了：数据定义负责搭框架，数据操作负责增删改查，空值处理负责补上数据缺失时不能直接按普通值比较的规则，视图则把数据定义和查询结合起来。

我们也已经把 DML 的主要语句串起来了：查询用 `SELECT`，插入用 `INSERT`，修改用 `UPDATE`，删除用 `DELETE`；再配合 `WHERE`、`GROUP BY`、`HAVING`、`ORDER BY` 和空值判断，就能完成很多实际的数据处理。

视图放在最后，不是它比前面内容更冷，而是它确实需要前面这些内容才能解释清楚。先知道什么是基本表和表结构，再知道查询如何产生结果，最后才能理解为什么一个只保存查询定义的虚表也可以被查询、被更新，以及它在什么情况下不能被更新。

数据控制的有关内容会放到后面的章节；等 SQL 的定义、操作和控制都学完，就可以进入数据库设计。到那时，前面这些对象和操作就不再只是语法，而会成为设计数据库时真正要使用的工具。

### 本讲提到的题目

#### `DELETE FROM SC` 和 `DROP TABLE SC` 有什么区别

题目问的是：删除选课表的数据，和直接把选课表删掉，有什么区别？

| 操作 | 所属语言 | 结果 |
|---|---|---|
| `DELETE FROM SC` | DML | 清空表中的数据，表本身还在 |
| `DROP TABLE SC` | DDL | 删除表本身，连表的基本结构一起删除 |

所以，看到删除数据时，要先问一句：删的是表里的行，还是表这个对象本身。`DELETE` 管数据，`DROP TABLE` 管表结构；这是两个不同层面的操作。

### 这一讲真正要记住的东西

插入既可以放一行，也可以把子查询的一组结果放进去；修改和删除既可以按一个条件处理一行，也可以按条件处理多行，还可以用子查询先划定范围。写这些语句时，列名、条件、值的位置要清楚，尤其是批量处理时不能漏掉连接条件或空值条件。

空值不是0，也不是空字符串；它会进入三值逻辑，查询时要用 `IS NULL` 判断。视图则是建立在基本表上的虚表：定义属于DDL，内容来自查询，查询和更新沿用DML的思路，但复杂计算或多表组合出来的视图通常不能直接更新。

把这几条线连起来，SQL就不再是几串互不相干的命令了。定义一个对象，往里面放数据，改数据，删数据，处理缺失值，再把常用查询固定成视图——这就是SQL数据操作这一部分最完整的工作方式。
