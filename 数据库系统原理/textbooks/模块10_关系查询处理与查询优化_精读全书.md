## 关系查询处理算法与代价计算模型
> 对应块：BLK30 | 覆盖分集：P27 | 块标题（分集名）：《数据库第9章 关系查询的处理与优化（第一部分：处》

### 数据库管理系统内核视角下的查询处理

从数据库课程的知识脉络来看，前八章构成了基础的理论与应用体系：前五章从关系代数、SQL 语言、安全性控制到完整性约束，奠定了关系模型的基本概念；第六章关系数据理论、第七章数据库设计与第八章数据库编程，解决了如何在业务中建立并实现一个规范化数据库的问题。

进入系统内核篇后，我们面对的核心对象从“数据库定义与操作”转向了“数据库管理系统（DBMS）内核机制”。这其中包括关系查询处理与优化、数据库恢复技术、并发控制技术以及系统架构体系。

关系数据库的核心价值之一，在于它为用户屏蔽了底层的物理存取路径。用户在客户端只需要使用声明式的 SQL 语言表达“要什么”，而无需编写过程化指令告知系统“怎么取”。如何将一条声明式的 SQL 查询高效地转换为磁盘 I/O 与内存计算操作，并在多种潜在执行策略中选出系统开销最小的路径，是关系查询处理与优化机制必须解决的根本问题。

### 关系查询执行的四个阶段

当系统接收到一条 SQL 查询语句后，整个查询处理流程通常划分为四个连续的阶段：查询分析、查询检查、查询优化与查询执行。

```text
       SQL 查询语句
            │
            ▼
   ┌─────────────────┐
   │  1. 查询分析    │  词法分析、语法分析
   └────────┬────────┘
            │ 语法分析树
            ▼
   ┌─────────────────┐
   │  2. 查询检查    │  语义分析、权限验证、完整性约束、视图转换
   └────────┬────────┘
            │ 关系代数表达式
            ▼
   ┌─────────────────┐
   │  3. 查询优化    │  代数优化（逻辑优化）+ 物理优化（路径/算法）
   └────────┬────────┘
            │ 执行计划（Execution Plan）
            ▼
   ┌─────────────────┐
   │  4. 查询执行    │  代码生成器（自顶向下/自底向上）、存储引擎调用
   └─────────────────┘
```

> **读图说明**：查询处理流程自顶向下推进，SQL 语句经词法语法分析与合法性检查后转化为内部关系代数表达式，经代数与物理双重优化后生成可执行代码，最终由存储引擎完成物理执行。

#### 查询分析
查询分析的主要任务是对输入的 SQL 查询文本进行词法分析与语法分析。
词法分析器负责扫描输入的字符流，识别出具有独立语义的词法单元（Token），例如关键字 `SELECT`、`FROM`、`WHERE`，以及表名、列名、操作符等。
语法分析器则根据关系数据库的语法规则，对识别出的词法单元进行语法结构分析与判定，验证输入的语句是否符合语法规范，并构建对应的语法分析树。

#### 查询检查
查询检查聚焦于语义层面的合法性验证。即便一条 SQL 语句语法完全正确，其语义也可能违法或缺少访问上下文。该阶段依据系统数据字典（Data Dictionary）完成以下核验与转换：
1. **模式对象有效性**：验证查询中引用的数据表、视图、属性列在数据字典中是否存在。
2. **用户权限审查**：检查当前发起查询的用户是否拥有对应对象的读取权限（即此前通过 `GRANT` 授予或通过 `REVOKE` 收回的权限边界）。
3. **完整性约束校验**：验证查询条件是否符合实体完整性、参照完整性与用户自定义完整性的约束规则。
4. **视图转换与消解**：若查询涉及视图，系统将根据数据字典中记录的视图定义，将视图名替换为底层的基本表查询，实现视图消解。

当查询检查全部通过后，系统将这组包含 `SELECT-FROM-WHERE` 的 SQL 语句转化为系统内部的标准表示形式——关系代数表达式。这正是关系代数核心算子（选择、投影、连接、笛卡尔积、并、交、差）在系统内部的具象化。

#### 查询优化
关系数据库管理系统通常会用“查询树”（Query Tree，亦称语法分析树）来表示扩展的关系代数表达式。
优化的核心任务是从满足查询语义的所有等价执行方案中，基于规则（Rule-based）、代价（Cost-based）或语义（Semantic-based）推导，选出一种系统开销最小的执行方案。在现代通用 DBMS 中，基于代价的优化（CBO）是绝对主流。优化具体细分为两个维度：
- **代数优化**：在关系代数表达式层面，利用等价代数变换定律，调整算子的执行顺序（例如提前执行选择与投影）。
- **物理优化**：针对确定的关系代数操作，挑选底层的具体存取路径（如全表顺序扫描还是利用索引扫描）以及具体的物理算法（如嵌套循环连接还是哈希连接）。

#### 查询执行
查询执行阶段由优化器输出最优执行策略，代码生成器（Code Generator）依据执行计划生成底层的执行代码。执行方式分为自顶向下（Top-down，调用驱动）与自底向上（Bottom-up，数据驱动）两种模式，通过调用存储管理接口从磁盘调入数据块并在内存中完成运算，最终输出查询结果。

### 查询树与内部表示机制

在系统内部，关系代数表达式被组织成层次化的查询树结构：
- 查询树的**叶子节点**对应查询所涉及的基础关系表；
- 查询树的**内部节点（非叶子节点）**对应在关系上施加的关系代数算子（如 $\sigma$ 选择、$\pi$ 投影、$\bowtie$ 等值连接、$\times$ 笛卡尔积）；
- 查询树的**根节点**即为最终输出结果。

执行过程自底向上展开，下层节点的计算结果作为上层节点的输入流。

优化的核心落脚点必然在查询树的拓扑结构与节点属性上。用户书写的 SQL 语句是给定的业务逻辑，但映射为查询树后，树的分支形状、算子高度以及每个算子节点绑定的底层算法拥有巨大的调整空间。改变查询树的形态，直接决定了中间临时结果的规模与系统资源的消耗。

### 选择操作的底层实现算法

在关系代数的基本算子中，选择与连接操作是查询优化器关注的绝对重心。投影操作仅负责裁剪无用字段并最终输出，无法在中间计算中大幅缩减元组数量；而选择与连接算子直接作用于内存中元组的匹配与过滤，直接决定系统 I/O 块数与内存驻留时长。

数据库基本表在物理层以磁盘存储块（Block/Page）为单位组织。执行运算时，必须将磁盘块调入内存缓冲区。系统性能提升的本质，是减少昂贵的磁盘 I/O 交互并提升内存缓冲区的吞吐效率。

#### 全表扫描算法
全表扫描（Table Scan）是指按照物理存储顺序，将目标表所占用的全部磁盘块逐一调入内存，依次检查每个元组是否满足选择条件，将匹配的元组输出。

```text
磁盘（硬盘）                         内存缓冲区（共 M 块）
┌─────────────┐                      ┌─────────────┐
│ 存储块 1     │ ─── 物理顺序读入 ───▶│ 缓冲块 1     │ ── 逐元组判定 ──▶ 输出结果
├─────────────┤                      ├─────────────┤
│ 存储块 2     │ ─── 缓冲区满后 ────▶│ 缓冲块 2     │ ── 逐元组判定 ──▶ 输出结果
├─────────────┤      覆盖或复用      │ ...         │
│ ...         │                      ├─────────────┤
│ 存储块 N     │                      │ 缓冲块 M     │
└─────────────┘                      └─────────────┘
```

> **读图说明**：全表扫描受限于内存容量 $M$，必须分批将磁盘块调入缓冲区，处理完当前批次后再读入后续批次，直至全表所有磁盘块遍历完毕。

假设系统分配给该查询的可用内存为 $M$ 块：
1. 按照物理顺序一次性读入目标表的 $M$ 块数据到内存缓冲区；
2. 遍历缓冲区内的每个元组 $t$，若 $t$ 满足谓词条件则加入结果集；
3. 若磁盘上仍有未读取的数据块，清空或覆盖已处理的缓冲区，重复步骤 1 与 2，直到全表扫描结束。

> **结论**：全表扫描算法实现简单，且无论目标属性上是否存在索引均可执行，适合数据量极小的小表。但对于大表而言，即便只查询满足条件的单条记录，也必须扫描整表所有磁盘块，引发巨大的无谓 I/O 代价。

#### 索引扫描与范围匹配
若选择条件的属性列上预先建立了索引（如 B+ 树索引或哈希索引），系统无需调入整表数据，而是通过索引检索满足条件的元组指针（RID/主码），再按指针定向读取目标磁盘块。

面对不同的条件表达式，索引扫描呈现不同的工作机制：

```text
  条件类型                    典型 SQL 示例                     执行与索引路径
  ─────────────────────────────────────────────────────────────────────────────
  单值唯一匹配      WHERE Sno = '201215121'           走主码/唯一索引直接下探指针
  范围条件过滤      WHERE Sage > 20                   走 B+ 树索引，在叶子链表顺序扫描
  复合条件交集      WHERE Sdept = 'CS' AND Sage > 20  双索引求指针交集，或单索引回表复筛
```

##### 单值精确匹配
如 `WHERE Sno = '201215121'`，通过主键或唯一索引直接定位到该学号对应的元组指针。系统仅需将该指针指向的单个物理数据块读入内存，I/O 复杂度从 $O(N)$ 骤降至 $O(1)$ 或树高深度。

##### 范围条件匹配
如 `WHERE Sage > 20`，由于年龄属性非唯一，若建立的是 B+ 树索引：
1. 从 B+ 树根节点出发下探，定位到键值等于 20 的索引项边界；
2. 利用 B+ 树叶子节点的双向链表结构（顺序集），顺着指针链向右线性遍历，获取所有满足 `Sage > 20` 的元组物理指针集合；
3. 根据提取出的指针集合，回表（Index Lookup）读取磁盘上的真实数据块。

若满足条件的记录数量远少于全表总行数，该方式可避免大量非相关块的读取；但若满足条件的记录占比过大，由于回表操作可能产生大量离散的随机 I/O，其效率可能反而不如顺序全表扫描。

##### 复合条件过滤
如 `WHERE Sdept = 'CS' AND Sage > 20`：
- **双索引求交法**：若 `Sdept` 与 `Sage` 上均有索引，分别通过各自索引检索出满足条件的元组指针集合，在内存中直接对两组指针求交集（Intersection）。最终仅凭借交集中的指针去磁盘调取真实数据，大幅收敛磁盘访问范围。
- **单索引过滤法**：优先使用区分度更高的索引（如 `Sdept`）定位一组元组并调入内存，随后在内存中对 `Sage > 20` 施加二次条件判定。

### 连接操作的实现机制与算法演进

连接操作（Join）是关系代数中计算复杂度最高、对性能影响最剧烈的算子之一。其本质是对两表元组进行配对。以学生表 `Student` 与选课表 `SC` 的等值连接为例：
`SELECT * FROM Student, SC WHERE Student.Sno = SC.Sno`

若不加控制，两表直接进行笛卡尔积运算，中间结果行数将达到两表行数的乘积。在底层存储体系中，实现连接运算有四种典型算法：

#### 嵌套循环连接算法
嵌套循环连接（Nested-loop Join）采用双重循环机制：
- 选取一个表作为外层循环表（外表/驱动表，Outer Table），另一个表作为内层循环表（内表，Inner Table）。
- 对外层表的每一个元组，顺序扫描内层表的全部元组，逐一比对连接属性值。若相等则拼接输出，直至外层表全部元组处理完毕。

若没有缓冲区优化，外层表有 $N$ 条元组，内层表就会被完整扫描 $N$ 次。如果数据量较大，频繁的内表重复读取将导致磁盘 I/O 发生灾难性膨胀。

#### 排序合并连接算法
排序合并连接（Sort-Merge Join / Merge Join）适用于两表均已按照连接属性排序的场景：
1. 若两表在连接属性上尚未有序，则先分别对两表进行物理排序（按连接属性升序或降序）；
2. 维护两个游标分别指向两表的起始元组，由于双方均已有序，只需沿同一方向单向推进比对；
3. 当双方连接属性相等时，拼接输出；若外表值较小，则推进外表游标；若内表值较小，则推进内表游标。

> **结论**：排序合并连接的核心优势在于两表在连接阶段**各只需线性扫描一遍**。相比于嵌套循环连接的重复扫描，在两表已有序或数据量较大时，排序合并连接能够大幅缩减 I/O 次数。

#### 连接索引机制
若内层表（如 `SC`）的连接属性（`Sno`）上已建有索引：
- 遍历外层表（`Student`）中的每一个元组；
- 取出其连接属性值，直接在内层表的索引中进行查找，定位匹配的元组指针并提取数据完成连接。
- 此时外层表仅需扫描一遍，而内层表不需要进行物理全表遍历，每次查找代价仅为索引下探与指针回表的开销。

#### 哈希连接算法
哈希连接（Hash Join）是处理大规模非排序数据等值连接的高性能物理算法。算法分为两个阶段：

```text
阶段一：划分构建（Building Phase）
驱动表（较小表 Student）
       │
       ▼ [Hash 函数 H]
 ┌─────────┬─────────┬─────────┬─────────┐
 │ 桶 0    │ 桶 1    │ 桶 2    │ 桶 3    │ （内存 Hash 表）
 └─────────┴─────────┴─────────┴─────────┘

阶段二：探测匹配（Probing Phase）
被探测表（较大表 SC）
       │
       ▼ [相同 Hash 函数 H]
 定位对应桶并进行元组比对 ── 相等 ──▶ 拼接输出
```

> **读图说明**：哈希连接先用小表在内存中散列建桶，随后大表元组通过相同哈希函数直接落入对应桶中进行精准比对，无需与所有桶比对。

1. **划分与构建阶段（Building Phase）**：
   选择包含较少元组的表（驱动表，如 `Student`），对其进行单遍扫描，使用指定的哈希函数 $H$ 对连接属性计算哈希值，将其散列到内存哈希表的各个桶（Buckets）中。
2. **探测与匹配阶段（Probing Phase）**：
   对另一个较大的表（如 `SC`）进行单遍扫描，采用完全相同的哈希函数 $H$ 计算连接属性的哈希码，精准映射到对应的哈希桶中，仅与该桶内的驱动表元组进行比对，若属性值匹配则立即完成拼接输出。

由于哈希分桶将全局 $O(N \times M)$ 的比对复杂度分摊至各个独立的桶内，极大避免了笛卡尔积级别的无效比对。

### 查询代价模型与开销构成

关系数据库管理系统在评估不同执行方案时，需要依据代价模型计算总执行代价 $Cost$，并选取代价最小者。

在单机集中式数据库系统中，执行开销主要由三部分构成：
$$Cost = Cost_{I/O} + Cost_{CPU} + Cost_{Memory}$$

- **磁盘 I/O 代价（$Cost_{I/O}$）**：存取磁盘数据块的总数量。从磁盘读取到内存以及从内存写出到磁盘临时文件的块数总和。由于机械硬盘或 SSD 的读写速度相较内存慢数个数量级，**磁盘 I/O 代价是单机集中式数据库查询总代价中最主要、最具决定性的因素**。
- **处理机 CPU 代价（$Cost_{CPU}$）**：CPU 执行指令的时间开销，包括元组比对、内存排序、哈希运算、算子逻辑计算等。
- **内存开销（$Cost_{Memory}$）**：执行查询所需的内存缓冲区空间大小与生命周期占用。

对于分布式数据库系统，数据分布在通过网络互连的多个物理节点上。其总代价必须在集中式指标的基础上，额外计入节点间的数据通信网络开销：
$$Cost_{Distributed} = \sum Cost_{Local} + Cost_{Communication}$$

优化器在分布式环境下的首要目标，往往是减少跨节点的网络数据传输量与网络往返次数。

### 典型多表查询的代价定量推导演算

为了建立直观且严谨的代价感知，我们通过一个具体的多表查询实例，对不同执行策略的 I/O 成本进行精确的定量推导。

#### 查询场景与基础参数设定

**查询需求**：求选修了 2 号课程的学生姓名。
对应 SQL 表达：
```sql
SELECT Student.Sname
FROM Student, SC
WHERE Student.Sno = SC.Sno AND SC.Cno = '2';
```

**物理存储与环境参数**：
- `Student` 表总行数：$1000$ 行记录（即 $10^3$）；
- `SC` 选课表总行数：$10000$ 行记录（即 $10^4$）；
- 选修了 2 号课程的记录数：$50$ 行；
- 单个磁盘块容量固定。由于 `Student` 包含 5 个属性列、记录较长，单个块仅能存放 $10$ 行 `Student` 元组；`SC` 仅有 3 列，单个块可存放 $100$ 行 `SC` 元组；
- `Student` 表占用总块数：$1000 \div 10 = 100$ 块；
- `SC` 表占用总块数：$10000 \div 100 = 100$ 块；
- 内存缓冲区限制：可用缓冲区按固定比例配置，假设内存中一次最多可存放 $5$ 块 `Student` 元组与 $1$ 块 `SC` 元组，用于块嵌套连接。

---

#### 策略一：广义笛卡尔积与事后选择（$Q_1$）

该策略严格遵循未优化的初始逻辑表达式：先做两表的广义笛卡尔积，再施加 `Sno` 相等与 `Cno = '2'` 的复合选择，最后投影输出 `Sname`：
$$Q_1 = \pi_{Sname} (\sigma_{Student.Sno = SC.Sno \land SC.Cno = '2'} (Student \times SC))$$

##### 输入连接阶段 I/O
内存采用分块嵌套处理。每次在内存中装入 5 块 `Student` 数据，并留出 1 块装入 `SC` 数据进行全量配对：
- 处理完 5 块 `Student` 需要扫描一次完整的 `SC` 表（100 块）；
- `Student` 表共有 100 块，共需分批 $100 \div 5 = 20$ 轮；
- 因此，`Student` 表累计读取 $100$ 块；
- `SC` 表累计读取 $20 \times 100 = 2000$ 块；
- 输入阶段总 I/O 块数：
  $$100 + 2000 = 2100 \text{ 块}$$

##### 笛卡尔积中间结果产生与落盘
- 笛卡尔积总元组数：$1000 \times 10000 = 10^7$ 行；
- 连接后的组合元组体积膨胀，假设每块仅能容纳 10 行组合元组；
- 写出笛卡尔积中间临时文件所需块数：
  $$10^7 \div 10 = 10^6 \text{ 块}$$
- 这一步需向磁盘**写入** $10^6$ 块。

##### 条件选择阶段 I/O
- 系统必须重新从磁盘将这 $10^6$ 块中间文件逐一**读入**内存，进行 `Student.Sno = SC.Sno` 与 `SC.Cno = '2'` 的谓词过滤；
- 该阶段增加磁盘读 I/O：$10^6$ 块；
- 满足条件的元组最终仅有 50 条，可完全容纳于单块内存中直接投影输出，不再产生落盘写操作。

##### 策略一总 I/O 成本
$$Cost(Q_1) = 2100 \text{（表读取）} + 10^6 \text{（中间文件写入）} + 10^6 \text{（中间文件读回）} = 2{,}002{,}100 \text{ 块}$$

---

#### 策略二：自然连接与中间结果缩减（$Q_2$）

该策略首先对两表执行自然连接（等值连接后消除冗余属性），随后对连接结果做单条件选择与投影：
$$Q_2 = \pi_{Sname} (\sigma_{SC.Cno = '2'} (Student \bowtie SC))$$

##### 输入连接阶段 I/O
两表调入内存进行连接的机制同上，输入阶段读取两表的基本 I/O 仍为：
$$100 + 20 \times 100 = 2100 \text{ 块}$$

##### 中间结果生成与落盘
- 由于在连接阶段直接施加了 `Student.Sno = SC.Sno` 的等值过滤，中间结果不再是笛卡尔积，其元组数上限受限于 `SC` 表的总行数，即最多只有 $10^4$ 行；
- 假设连接后的元组每块可存 100 行，写出中间文件所需块数：
  $$10^4 \div 100 = 100 \text{ 块（即 } 10^2 \text{ 块）}$$
- 写入磁盘中间文件：$100$ 块。

##### 条件选择阶段 I/O
- 重新将该中间文件读入内存进行 `SC.Cno = '2'` 判定，读入 I/O：$100$ 块；
- 过滤出 50 条最终结果，直接在内存中投影输出。

##### 策略二总 I/O 成本
$$Cost(Q_2) = 2100 + 100 + 100 = 2{,}300 \text{ 块}$$

相比策略一，代价缩减为策略一的约：
$$\frac{2300}{2002100} \approx \frac{1}{870}$$
（若中间文件元组较大、分块略多，代价也在策略一的数百倍缩小范围内，性能产生了质的飞跃）。

---

#### 策略三：算子下推与先选后连（$Q_3$）

该策略遵循代数优化的核心公理——**选择算子尽早执行（算子下推）**。先对 `SC` 表进行 `Cno = '2'` 过滤，再将筛选后的中间结果与 `Student` 表进行自然连接：
$$Q_3 = \pi_{Sname} (Student \bowtie \sigma_{SC.Cno = '2'}(SC))$$

```text
策略一（Q1）：笛卡尔积后过滤            策略三（Q3）：算子下推优化
            π(Sname)                                π(Sname)
               │                                       │
      σ(Sno=Sno ∧ Cno='2')                             ⋈ (Sno)
               │                                   ┌───┴───┐
            × (笛卡尔积)                        Student   σ(Cno='2')
         ┌─────┴─────┐                           (100块)     │
      Student        SC                                      SC
      (100块)      (100块)                                (100块)
   中间产生 10^7 行临时数据！                     仅需 50 行常驻内存连接！
```

> **读图说明**：左侧策略一在底层直接进行笛卡尔积，中间结果膨胀至 $10^7$ 行并被迫落盘；右侧策略三将选择算子下推至叶子节点上方，在输入源头直接将数据缩减至 50 行，彻底消除了中间磁盘文件的读写。

##### 预先选择阶段 I/O
- 全表单遍扫描 `SC` 表，读入全部 $100$ 块数据；
- 在内存中实时进行 `Cno = '2'` 过滤，过滤出的元组总计仅有 $50$ 行；
- 单块内存可存放 100 行 `SC` 元组，因此这 50 条记录仅占半个内存块，**可以直接常驻内存缓冲区**，完全无需写入磁盘中间文件。

##### 内存连接与投影阶段 I/O
- 将 50 条筛选后的 `SC` 记录钉在内存中；
- 顺序单遍读取 `Student` 表，共读入 $100$ 块数据；
- 每调入一块 `Student`，直接与常驻内存的 50 条 `SC` 记录按 `Sno` 进行匹配；
- 匹配成功的元组直接提取 `Sname` 输出，无任何中间写盘。

##### 策略三总 I/O 成本
$$Cost(Q_3) = 100 \text{（SC 读入）} + 100 \text{（Student 读入）} = 200 \text{ 块}$$

> **结论**：
> 策略三的总 I/O 消耗仅为 **200 块**。
> - 相比策略一（$2{,}002{,}100$ 块），系统 I/O 降至其**万分之一**；
> - 相比策略二（$2{,}300$ 块），系统 I/O 降至其**二十分之一**。

---

#### 结合物理索引的二次优化

在策略三（200 块 I/O）的基础上，若进一步引入物理索引，代价将进一步呈数量级压缩：
1. **SC 表建立索引**：若在 `SC.Cno` 上存在 B+ 树索引，系统无需对 `SC` 表进行 100 块的全表扫描。检索索引树定位到 `Cno = '2'` 的元组指针后回表，读取满足条件的真实数据块仅需约 **3 到 4 块** I/O；
2. **Student 表建立主键索引**：若在 `Student.Sno` 上建立主键索引，常驻内存的 50 条记录对应 50 个具体的学号。此时不需要对 `Student` 表执行 100 块的全表扫描，而是通过索引检索这 50 个学号，涉及的数据块读取最多仅需 **50 块**。

在此极端优化组合下，整个查询的总 I/O 块数将从 200 块进一步压缩到几十块以内。

### 代数优化与物理优化的分层定位

结合上述定量推导的全过程，我们可以清晰界定关系查询优化中两个层面的分工与本质：

```text
优化层面    核心处理对象                    优化手段与典型策略
─────────────────────────────────────────────────────────────────────────────
代数优化    关系代数表达式（查询树逻辑结构） 算子下推（先选后连）、投影提前、消除笛卡尔积
物理优化    存取路径与底层执行算法          全表扫描 vs 索引扫描、Nested-loop vs Hash Join
```

- **代数优化（逻辑优化）**：
  在关系代数表达式层面，通过语义等价的代数变换公式（如将 $Q_1$ 转换为 $Q_2$，再将 $Q_2$ 转换为 $Q_3$），在逻辑上压降参与计算的中间数据集规模。其核心法则是**尽早执行选择操作（算子下推）**、**尽早执行投影操作**，以及**能做连接绝不做笛卡尔积**。
- **物理优化（物理存取优化）**：
  在确定了逻辑操作顺序后，针对每一个逻辑算子选取最高效的底层存取路径与执行算法。例如对于选择操作，根据属性列上的索引类型决定使用全表扫描、B+ 树范围扫描还是哈希单值检索；对于连接操作，依据两表数据规模与排序状态决定采用嵌套循环、排序合并还是哈希连接。

理解从逻辑代数优化到物理算法选择的演进过程，便掌握了数据库管理系统内核在执行查询时平衡 I/O、内存与 CPU 资源开销的核心脉络。

## 关系查询的代数优化与物理优化
> 对应块：BLK31 | 覆盖分集：P28 | 块标题（分集名）：《数据库第9章 关系查询的处理与优化（第二部分：代》

我们在上一讲系统拆解了关系数据库管理系统（DBMS）处理一个查询的完整生命周期。一个 SQL 查询从客户端发往数据库，内核要依次走完四个核心环节：查询分析（词法与语法分析）、查询检查（语义分析、视图转换、完整性与安全性检查）、查询优化，以及最终的查询执行。

前两个环节主要解决语法与合法性问题，属于静态编译期必须走通的规矩；而系统响应到底快不快、并发吞吐能不能撑住，真正的决胜点全在后两个环节——**查询优化**与**查询执行**。

查询优化绝不是玄学，它的核心任务是在海量可行的执行方案中，为用户提交的声明式 SQL 挑选出一条资源消耗最低、耗时最短的执行路径。这条优化之路分为两大战术支柱：
1. **代数优化（逻辑优化）**：基于关系代数的等价变换原则，在逻辑算子树层面调整操作的执行次序与组合结构，核心是把能够缩减数据规模的算子尽量提前；
2. **物理优化**：脱离抽象的代数符号，深入磁盘数据块、内存缓冲区、存储路径与物理索引结构，为每一个代数算子挑选最高效的底层执行算法（如嵌套循环、排序合并或哈希）与存取路径（如全表扫描或各级索引扫描）。

要吃透这两大优化，必须在脑海里牢牢钉住两条最底层的主线思维：
- **第一条主线：尽可能减少磁盘 I/O**。机械硬盘或固态硬盘到内存的数据吞吐永远是数据库最昂贵的瓶颈，数据从外存读入内存的块数越少越好；
- **第二条主线：尽可能降低内存开销与 CPU 运算量**。中间结果在内存中占用的缓冲页面越小，需要比对的元组配对次数就越少，系统的端到端响应时间自然越快。

无论是逻辑层面的算子下推，还是物理层面的索引探查与内外表选择，全都是在这两条主线思维指引下演化出来的工程解法。

### 关系代数表达式的等价变换规则

SQL 是一门声明式语言，只说明“要什么”，而不规定“怎么取”。当查询优化器将一条 SQL 转换为内部关系代数表达式时，存在无数种形态。我们可以先做笛卡尔积再过滤，也可以先做自然连接，更可以在读取单表时先过滤再向外传递。

优化与不优化，底层的数据传输量可能有成千上万倍的差距。而优化的合法性前提，是变换前后的表达式在语义上必须绝对等价。

> **定义**：对于两个关系代数表达式 $E_1$ 和 $E_2$，如果用相同的任意合法关系实例分别替换它们中相应的关系名，所得到的计算结果完全一致，则称 $E_1$ 和 $E_2$ 是**等价的**，记作：
> $$E_1 \equiv E_2$$

在实际推导中，常用等价变换规则多达十余条。这些规则就像我们在函数依赖章节接触过的 Armstrong 公理系统一样，不需要死记硬背某一条规则在教材上的编号是规则几，更不需要机械抄录。只要我们在脑子里带入两张最经典的基础表——学生表 `Student(Sno, Sname, Sdept, Sage)` 与选课表 `SC(Sno, Cno, Grade)`，顺着逻辑直觉看一遍，就能瞬间想通它们为什么必然成立。

```text
+------------------------------------+       +------------------------------------+
|            Student 关系            |       |              SC 关系               |
+-----+-------+-------+--------------+       +-----+-----+------------------------+
| Sno | Sname | Sdept | Sage         |       | Sno | Cno | Grade                  |
+-----+-------+-------+--------------+       +-----+-----+------------------------+
```

#### 连接与笛卡尔积的交换律与结合律

无论我们是把左边的表与右边的表连接，还是把右边的表与左边的表连接，所产生的元组匹配结果没有任何区别：
$$E_1 \bowtie E_2 \equiv E_2 \bowtie E_1$$
$$E_1 \times E_2 \equiv E_2 \times E_1$$

同理，三个或更多关系做连接或笛卡尔积时，运算次序的先后不会改变最终的元组集合：
$$(E_1 \bowtie E_2) \bowtie E_3 \equiv E_1 \bowtie (E_2 \bowtie E_3)$$
$$(E_1 \times E_2) \times E_3 \equiv E_1 \times (E_2 \times E_3)$$

这条性质赋予了优化器巨大的自由度：面对多表连接时，优化器可以自由重排连接顺序，优先让小表参与连接，而不用拘泥于 SQL 中 `FROM` 子句的书写先后。

#### 投影与选择的串接定律

假设我们有一组属性列集合 $A$ 和 $B$，且 $A$ 是 $B$ 的子集（$A \subseteq B$）。比如 $B$ 包含 `{Sno, Sname, Sdept}`，而 $A$ 只包含 `{Sno, Sname}`。如果我们在一个关系上先投影出 $B$，紧接着又在中间结果上投影出 $A$，其最终效果与直接在该关系上一步投影出 $A$ 没有任何区别：
$$\pi_A(\pi_B(E)) \equiv \pi_A(E)$$

> **结论**：多次连续投影可以被合并为单次投影，只需保留最外层最终所需要的属性集，中间冗余的投影步骤完全可以消除。

对于选择操作，串接定律同样成立。假设筛选条件既要求是“计算机系”（$F_1$），又要求“年龄大于 20 岁”（$F_2$）：
$$\sigma_{F_1 \land F_2}(E) \equiv \sigma_{F_1}(\sigma_{F_2}(E)) \equiv \sigma_{F_2}(\sigma_{F_1}(E))$$

是先筛出计算机系同学再挑出 20 岁以上的，还是先挑出 20 岁以上的再看所在系，抑或是把两项作为合取条件一并筛选，得到的记录完全相同。这意味着选择条件既可以随时合并，也可以按字段来源自由拆解。

#### 选择与投影的交换律

如果在操作一个关系时，选择条件 $F$ 中涉及的所有属性都包含在投影属性集 $A$ 中，那么先做选择后做投影，与先做投影后做选择是等价的：
$$\sigma_F(\pi_A(E)) \equiv \pi_A(\sigma_F(E))$$

带入 `Student` 表即可理解：要在全校学生中找到“计算机系同学的姓名与学号”，我们是先横向筛出计算机系的全部行、再纵向切出学号与姓名两列，还是先切出学号、姓名、系名三列、再筛出计算机系的行，输出结果毫无二致。

在实际执行中，如果选择操作在外层，我们往往希望将其推入内层，因为选择会迅速减少元组数量；但在最终输出端，投影往往置于最外层以精简输出字段。

#### 选择与笛卡尔积及连接的交换与分配

当查询涉及多张表时，选择操作与笛卡尔积/连接的相对位置是性能差异的核心发源地。

1. **单侧选择下推**：若筛选条件 $F$ 涉及的属性全部来自于关系 $E_1$，与 $E_2$ 无关，则：
   $$\sigma_F(E_1 \times E_2) \equiv \sigma_F(E_1) \times E_2$$
   设想 $E_1$ 是学生表，$E_2$ 是选课表，$F$ 是“计算机系的同学”。如果我们先把两个表做成庞大的广义笛卡尔积，再在生成的海量宽行中挑出计算机系学生，代价极其巨大；而先在学生表里把计算机系学生过滤出来，再拿这个小集合去和选课表做笛卡尔积，不仅结果相同，中间数据规模直接缩减几个数量级。

2. **双侧独立选择并行下推**：若复合条件 $F = F_1 \land F_2$，其中 $F_1$ 只涉及 $E_1$ 的属性，$F_2$ 只涉及 $E_2$ 的属性，则选择可同时分配给两端：
   $$\sigma_{F_1 \land F_2}(E_1 \times E_2) \equiv \sigma_{F_1}(E_1) \times \sigma_{F_2}(E_2)$$
   例如筛选“计算机系学生且选了 1 号课程的记录”，我们完全可以在学生端先筛出计算机系学生，在选课端先筛出 1 号课记录，最后只对这两个高度浓缩的小集合做运算。

3. **连接条件与普通选择的协同**：若选择条件既包含两表之间的连接谓词（如 `Student.Sno = SC.Sno`），又包含某张表的单表谓词，优化器利用分配律可以把单表过滤条件直接推到连接运算之前执行，从而实现部分选择在连接前先行完成。

#### 选择与投影对集合操作的分配律

对于并集（$\cup$）、差集（$-$）以及自然连接（$\bowtie$），选择与投影同样满足分配律：
$$\sigma_F(E_1 \cup E_2) \equiv \sigma_F(E_1) \cup \sigma_F(E_2)$$
$$\sigma_F(E_1 - E_2) \equiv \sigma_F(E_1) - \sigma_F(E_2)$$
$$\sigma_F(E_1 \bowtie E_2) \equiv \sigma_F(E_1) \bowtie \sigma_F(E_2)$$

把一个大表按业务切成两半并在一起，我们在并集上整体做筛选，跟在两个子集合上分别筛选之后再并在一起，结果没有区别。投影对于并运算与笛卡尔积同样具备类似的分配性质：
$$\pi_A(E_1 \cup E_2) \equiv \pi_A(E_1) \cup \pi_A(E_2)$$
$$\pi_{A \cup B}(E_1 \times E_2) \equiv \pi_A(E_1) \times \pi_B(E_2)$$

在工程实践中，我们不需要去背诵“规则 3 是投影串接、规则 4 是选择串接、规则 5 是分配”。这种教材编号在实际系统实现与业务排查中没有记忆价值。关键在于建立起强烈的直觉：**只要逻辑语义等价，算子可以在查询执行流上自由挪移，而挪移的方向永远奔向更低的 I/O 与更小的内存占用**。

### 查询树的启发式代数优化算法

了解了上述代数等价规则后，如果面对一个极其复杂的长 SQL，优化器该按照什么样的策略驱动这些规则？这就是**查询树（Query Tree）的启发式优化**。

所谓“启发式（Heuristics）”，就是计算机科学中根据大量工程经验总结出来的、在绝大多数情况下都能带来显著性能提升的确定性策略规则。

#### 启发式优化的核心工程规则

在关系代数树的变换中，有五条被业界公认的基石规则：

1. **选择运算应尽可能先做（选择下推，Predicate Pushdown）**
   这是整个代数优化中最重要、最基础、效果最立竿见影的铁律。
   
   为什么一定要让选择先做？不妨算一笔账：假设 `Student` 表有 100 行记录、5 个属性列。如果我们要查询计算机系前 5 名同学的学号、姓名与所在系：
   - **方案 A（先选择后投影）**：在扫描磁盘时，命中选择条件直接抽取出 5 行记录进入内存缓冲区，然后在这 5 行记录上剔除多余列完成 3 列投影。载入内存并参与后续计算的只有 5 行元组；
   - **方案 B（先投影后选择）**：我们必须把整张表 100 行元组全量读入内存，将原本 5 列 100 行的数据裁剪为 3 列 100 行，然后再在内存中逐行比对找出这 5 行。
   
   两种方案最终输出完全一样，但方案 A 进内存的数据规模缩减了 95%。选择下推的威力就在于它能在数据流动的源头把数据量成倍压缩。

2. **投影运算与选择运算尽可能同时进行**
   如果对同一个关系既有行筛选要求，又有列裁剪要求，最佳的执行姿势是在单次顺序扫描该关系的数据块时，将两项工作合并处理。行不符合条件的当场丢弃，行符合条件的只抽取目标属性列放入内存元组，绝不为了先选后投而把同一个数据块从磁盘反复读取两遍。

3. **把投影与其前后的双目运算紧密结合**
   没有必要为了单纯在关系表达式中剔除某些中间列，而专门增加一次独立的关系扫描与临时关系物化。两表在做连接时，只需保留参与连接的关联键以及后续计算需要的投影列，无用字段在连接扫描阶段即可就地过滤。

4. **把选择与紧随其后的笛卡尔积合并为连接运算**
   在关系代数中，带有等值比较条件的笛卡尔积在本质上就是等值连接或自然连接：
   $$\sigma_{R.A = S.A}(R \times S) \equiv R \bowtie_{R.A = S.A} S$$
   在任何成熟的数据库中，都绝不能先生成庞大的无条件笛卡尔积中间表再去过滤元组。能做单表过滤先做单表过滤；无法单表过滤的，优先收拢为等值连接；万不得已绝不跑全量笛卡尔积。

5. **积极识别并提取公共子表达式**
   如果一个复杂的复合查询中多次出现相同的子查询表达式，且该表达式计算代价较高、生成的结果集规模可控，那么预先将其计算一次并缓存在内存或中间临时文件中是非常划算的。
   典型场景就是基于视图（View）的复杂查询：定义视图的表达式可能被多个外层分支引用，虽然常驻内存或生成临时物化表会占用一部分存储资源，但“两害相权取其轻”——牺牲少量内存空间换取避免多次深层磁盘扫描，系统整体吞吐量会大幅提升。

#### 启发式代数优化的算法执行步骤

当解析器将一条复杂的 SQL 生成初始关系语法树后，优化器按以下标准化流程对其进行重构：

```text
[Step 1: 构造初始查询树]
           ↓
[Step 2: 拆解并彻底展开多表连接为笛卡尔积与选择]
           ↓
[Step 3: 选择算子下推至最底层的叶节点（单表上方）]
           ↓
[Step 4: 投影算子下推与精简，协同双目运算]
           ↓
[Step 5: 将相邻的选择与笛卡尔积重新收拢为高效连接]
```

这套步骤的核心心法极其简明：**选择算子拼命往叶节点（向下）滑，投影算子协同精简，中间连接结构彻底优化**。

#### 典型案例全流程推导

我们以一个在教学与工程中最具代表性的查询为例：
**查询选修了 2 号课程的学生姓名。**

对应的 SQL 语句非常标准：
```sql
SELECT Student.Sname
FROM Student, SC
WHERE Student.Sno = SC.Sno 
  AND SC.Cno = '2';
```

##### 第一阶段：构建初始查询树
如果按照 SQL 语句字面逻辑自底向上机械构建，从两张底表出发，必须先做学号相等的表连接，再过滤课程号等于 2 的元组，最后投影出学生姓名：

```text
               π(Sname)
                  |
             σ(SC.Cno = '2')
                  |
         ⋈(Student.Sno = SC.Sno)
             /        \
         Student       SC
```
*读图说明：初始树直接反映了 SQL 书写结构，中间节点是学号相等的连接操作，其上方叠加了课程筛选与最终姓名投影。*

##### 第二阶段：展开连接与算子重组
为了寻找更大的优化空间，优化器在推导草稿上先把多表连接还原为底层的代数逻辑——广义笛卡尔积与关联键选择条件：

```text
               π(Sname)
                  |
             σ(SC.Cno = '2')
                  |
       σ(Student.Sno = SC.Sno)
                  |
                  ×
             /        \
         Student       SC
```
*读图说明：将连接拆解为无条件的笛卡尔积 $\times$ 以及位于其上的学号等值选择条件。*

这里初学者常常产生困惑：之前不是反复强调笛卡尔积是最糟糕的操作吗？为什么优化器反而要把连接拆成笛卡尔积？
必须明确：**这里的展开绝不是实际执行计划，而是优化器在内部演算树上的中间推演状态**。只有把连接逻辑拆解开，选择条件才能解除捆绑，获得在整棵树上自由滑动的能力。

##### 第三阶段：利用等价规则进行算子下推（Pushdown）
此时树干上有两个选择条件：
- 条件一：`Student.Sno = SC.Sno`（关联双表，无法单表独立执行）；
- 条件二：`SC.Cno = '2'`（纯粹属于 `SC` 选课表的单表属性）。

根据选择与笛卡尔积的交换律，条件二 `SC.Cno = '2'` 完全可以穿透上层的笛卡尔积，直接顺着右侧分支向下滑动，钉死在 `SC` 关系的叶节点正上方！
滑动完成后，笛卡尔积与其上方的 `Student.Sno = SC.Sno` 再次重新收拢为等值连接。优化后的查询树定型如下：

```text
               π(Sname)
                  |
         ⋈(Student.Sno = SC.Sno)
             /        \
         Student    σ(SC.Cno = '2')
                       |
                       SC
```
*读图说明：优化后的查询树中，`SC.Cno = '2'` 已下推到选课表读取源头，只有选修了 2 号课的少量中间记录才会上浮去与 `Student` 表进行等值连接。*

在最终执行时，如果在读取 `Student` 表和过滤 `SC` 表的同时，将不需要的中间字段（如成绩、年龄等）就地裁剪，只向上层连接算子传递 `{Sno, Sname}` 与 `{Sno}`，内存中参与连接的不仅行数极少，而且行宽极窄。这就实现了从 I/O 到内存计算的双重极致优化。

### 物理优化中的存取路径选择与算法决策

代数优化改变的是逻辑算子的次序与结构，它解决的是“先读谁、后读谁、把谁过滤掉”的问题。但代数优化无论多精妙，它完全不了解底层的物理世界：
数据在硬盘上是以什么物理块存储的？有没有溢出块？字段上建的是 B+ 树索引还是哈希索引？内存里分配了几个缓冲区块？

物理优化正是要跨越这层鸿沟。它的核心目标是：**为代数优化产出的逻辑算子树中的每一个算子，挑选具体的物理操作算法与底层存取路径（Access Path），生成最终可执行的执行计划**。

物理优化的实现方法主要分为两大流派：
1. **基于启发式规则的物理优化（Rule-Based Optimization, RBO）**；
2. **基于代价估算的物理优化（Cost-Based Optimization, CBO）**。

在现代数据库引擎中，通常将两者深度融合：先用确定的启发式规则迅速剪除明显劣质的搜索路径，再对剩下的候选方案调用代价模型进行精确量化评估。

#### 基于规则的启发式物理优化（RBO）

在物理层面，内存与磁盘交互最频繁、性能开销最重的算子依旧是**选择（Selection）**与**连接（Join）**。

##### 单表选择操作的存取路径选择规则

面对一个带有 `WHERE` 条件的单表查询，引擎究竟该走全表扫描还是走索引？启发式规则总结为三句话：
- **第一句话：能用索引用索引，不能用索引全表扫描（大前提）**；
- **第二句话：具体情况具体分析（根据查询特征定策略）**；
- **第三句话：最终取决于需要提取的数据规模与占比（数量决定胜负）**。

具体细化为以下工程准则：
- **小表无脑全表顺序扫描**：如果一张表一共才几块磁盘空间，建立索引、载入索引块再回表定位的开销，反而远远超过一口气顺序读取全表的代价。
- **主码等值查询（`PK = value`）**：由于主码具有唯一性，命中结果最多只有一条元组，系统无条件优先选择主码索引进行点查。
- **非主属性等值或范围查询（如 `Sage > 20`）**：列上建有 B+ 树索引时，必须预估满足条件的元组比例。
  > **易错点**：绝不是只要列上有索引就一定要走索引！假设全表有一万行记录，如果查询条件筛选出的结果只有几十行（占比通常在 10% 以内），走索引扫描再回表极其划算；但如果筛选出的记录有 9000 行（占比 90%），如果强行使用索引，系统将产生高达 9000 次离散的随机回表 I/O，其性能将比连续单向读取整张表的全表扫描慢上数十倍！
- **AND 复合条件（合取式）**：如果涉及的列上存在复合索引（联合索引），优先采取复合索引扫描；如果各列分别有单列索引，采取单列索引过滤；若均无可用索引，回退为全表顺序扫描。
- **OR 复合条件（析取式）**：除非 OR 两侧的所有列都有可用索引支持索引合并，否则一般直接采用全表顺序扫描。

##### 表连接操作的算法选择与内外表判定

两个表在物理层面做连接，常见算法有排序合并连接（Sort-Merge Join）、索引连接（Index Join）、哈希连接（Hash Join）以及最通用的嵌套循环连接（Nested Loop Join）。
- 若两表在连接属性上已经物理有序，无条件首选排序合并连接；
- 若其中一个表的连接属性建有高效索引，优先选用索引连接；
- 在无索引且未排序的情况下，若其中一张表能完全装入内存哈希桶，选用哈希连接；
- 若回退到通用的块嵌套循环连接（Block Nested Loop Join），则必须遵循一个根本准则：**选择占用物理块数较小的表作为外表（驱动表）**。

为什么必须让小表当外表？我们先用直观的逻辑来感受：
假设学生表有 5 行记录，选课表有 4 行记录。做嵌套循环时，如果拿 4 行的表做外表，我们只需要从外表取出元组 4 次，每次驱动内表比对；反过来如果拿 5 行的表做外表，就要驱动 5 次。让体量小的关系处于主动驱动位置，系统调用的调度开销与比对波及面最小。

我们可以对这个过程进行严密的数学量化推导。

> **嵌套循环连接的 I/O 代价推导**：
> 设参与连接的两个表分别为 $R$ 和 $S$，它们在磁盘上占用的物理块数分别为 $B_R$ 和 $B_S$。
> 假设系统分配给该连接操作的内存可用缓冲区块总数为 $K$。
> 我们将其中 $K - 1$ 个缓冲区块分配给外表，剩下的 $1$ 个缓冲区块留给内表用于流式轮巡。
> 
> 若选择 $R$ 作为外表，则：
> 1. 外表 $R$ 从磁盘被完整读入内存一次，产生 $B_R$ 次块传输；
> 2. 外表由于占用 $B_R$ 块，一共需要分批 $\lceil \frac{B_R}{K - 1} \rceil$ 次装入内存缓冲区；
> 3. 外表每装入一批，内表 $S$ 就要完整地从头到尾被扫描读取一遍（产生 $B_S$ 次块读取）。
> 
> 因此，整个嵌套循环连接从磁盘传输的总块数（$\text{Cost}$）为：
> $$\text{Cost} = B_R + \frac{B_R \times B_S}{K - 1}$$

观察该公式中的两项：
后半部分的分子项 $B_R \times B_S$ 是对称的乘积项，不管谁当外表，$B_R \times B_S$ 与 $B_S \times B_R$ 数值完全恒定；分母 $K - 1$ 也是固定的可用缓冲区大小。
整道公式唯一的非对称可变量，就在第一项——外表的物理块数 $B_R$！
$B_R$ 越小，公式总和越小。因此在数学推导上无可辩驳地证明了：**外表必须选择物理块数更小的小表**。

#### 基于代价的物理优化（CBO）

启发式规则给出了大方向，但遇到“走索引还是走全表扫描”的临界状态时，唯有依靠基于代价的优化器（CBO）进行精密的数值计算。

CBO 的基本原理是：根据数据字典中记录的底层统计信息，对各种可行的存取路径和物理算法估算其综合代价（主要衡量磁盘 I/O 块数，辅以 CPU 时间与内存空间），最终从中选择代价值最小的方案。

##### 优化器依赖的核心统计信息

为支撑精准估算，DBMS 会在后台持续维护以下三个维度的统计信息：

```text
+-------------------+---------------------------------------------------------+
| 统计维度          | 核心统计指标                                            |
+-------------------+---------------------------------------------------------+
| 基本表级别        | 元组总行数 N、元组平均字节长度 L、占用物理块数 B、      |
|                   | 溢出块数 BO                                             |
+-------------------+---------------------------------------------------------+
| 属性列级别        | 不同值个数（Distinct Values）I、最大值 Max、最小值 Min、|
|                   | 是否有索引及类型、选择率（Selectivity）f                |
+-------------------+---------------------------------------------------------+
| 物理索引级别      | 索引层数 L、不同索引值个数、索引选择基数 S（平均每个    |
|                   | 索引值对应的元组数）、叶节点物理块数 Y                  |
+-------------------+---------------------------------------------------------+
```

关于**选择率（Selectivity）$f$** 的计算，反映了某一查询条件过滤后保留元组的概率：
- **均匀分布假设**：如果该列包含 $I$ 个不同的离散值，且数据分布均匀，则任意一个值的等值查询选择率为：
  $$f = \frac{1}{I}$$
- **频数直方图**：若数据严重倾斜分布（例如全表 100 行，值为 10 的有 10 个，值为 20 的有 20 个），则特定值 $v$ 的选择率为包含该值的元组数除以总行数：
  $$f = \frac{\text{Count}(v)}{N}$$
  此时选择值为 10 的概率为 $10/100 = 1/10$。

##### 常见物理算法的代价估算模型

我们以磁盘 I/O 块传输数为基准，来看几个典型物理算子的代价计算方式：

1. **全表顺序扫描算法**
   - 若无条件全量扫描，必须读穿整张表的物理块，代价为：
     $$\text{Cost} = B$$
     （若表占用 10 块，则 $\text{Cost} = 10$）
   - 若查询条件在唯一码（主码）上做等值查找，命中后立即终止扫描，类似于掷硬币求期望，平均只需扫描一半的块即可命中目标：
     $$\text{Cost}_{\text{avg}} = \frac{B}{2}$$

2. **主码等值查询（B+ 树索引）**
   设 B+ 树索引的层数为 $L$（通常为 3~4 层）：
   - 从根节点沿着分支检索到目标叶子节点，需要读取 $L$ 个索引块；
   - 找到对应的物理元组指针（RID）后，必须访问基本表中该元组所在的物理数据块 1 次（回表）。
   - 总代价公式极其稳定：
     $$\text{Cost} = L + 1$$
     无论底层数据表多么庞大，3 次索引 I/O 加上 1 次数据块 I/O，总共只需 4 次磁盘访问即可命中数据。

3. **非主属性等值查询（B+ 树索引）**
   设选择条件为 `Sdept = 'CS'`，索引层数为 $L$，满足该条件的记录数为 $S$（索引选择基数）：
   - 沿索引树下探至叶节点，耗费 $L$ 次 I/O；
   - 命中的 $S$ 个元组在物理聚簇较差的堆表中可能离散分布在不同的数据块中，最坏情况下每读取一条记录都要做一次随机回表：
     $$\text{Cost} = L + S$$

4. **非主属性范围查询（B+ 树索引）**
   设查询条件为 `Sage > 20`，索引叶节点块数为 $Y$，表数据块数为 $B$。假设根据统计信息判定有一半的元组满足条件：
   - 扫描顺序遍历的一半索引叶子块，开销为 $\frac{Y}{2}$；
   - 通过叶节点指针访问分布在各处的数据块，开销为 $\frac{B}{2}$；
   - 初步代价模型为：
     $$\text{Cost} = \frac{Y}{2} + \frac{B}{2}$$
   优化器会结合更精确的选择基数修正这一代价，若该代价高于全表扫描代价 $B$，优化器便会果断放弃索引，掉头走向全表扫描。

5. **嵌套循环连接的写回代价**
   如果连接操作产生的中间结果集过于庞大，无法留在内存中，而必须落地回写磁盘，还需在传输代价基础上增加写回代价：
   $$\text{Cost}_{\text{write}} = \frac{N_R \times N_S \times f_{RS}}{M_{RS}}$$
   其中 $f_{RS}$ 为连接选择率，$M_{RS}$ 为每个磁盘块可容纳的连接结果元组数。

### 面向执行引擎的 SQL 编写与全章技术闭环

系统梳理至此，我们可以清晰地看到一条连接应用程序与物理硬件的技术脉络：

```text
[ 应用程序 / 客户端 ]
         ↓ (SQL 声明式语句)
[ 查询分析与检查 ] (语法树检查、语义验证、权限与视图消解)
         ↓
[ 代数优化 (逻辑优化) ] (关系代数等价变换、启发式选择/投影下推)
         ↓
[ 物理优化 (RBO / CBO) ] (存取路径选择、索引评估、连接算法与代价建模)
         ↓ (物理执行计划)
[ 查询执行引擎 ] ⟷ [ 内存缓冲区管理 ] ⟷ [ 磁盘存储与索引结构 ]
```

掌握了关系查询处理与优化的底层机理后，我们必须破除一个极大的误区：**不要盲目迷信 DBMS 管理系统的自动化优化能力，更不要把所有查询性能的包袱全甩给优化器**。

现代查询优化器确实极度精巧复杂，但优化器本质上是在一定的搜索空间与启发式假设下运转的程序。如果我们在最上层的 SQL 编写阶段就写出了结构极差的查询（例如滥用大表间毫无必要的多重无序连接、在关联条件中隐式调用禁用索引的函数、或是写出导致中间结果急剧膨胀的恶性笛卡尔积），下层的代数优化器和物理优化器就算拼尽全力进行算子下推与索引匹配，也往往无力回天。

相反，优秀的工程师懂得顺应关系数据库管理系统的优化规律：
- 理解选择下推的原理，在业务逻辑允许的场景下尽早用子查询或特定条件收口数据；
- 清楚连接算法对数据规模的敏感性，合理运用集合操作与精准的连接谓词；
- 了解索引扫描与全表扫描的临界代价，绝不为了“有索引”而强行在全量扫表的场景下逼迫数据库走离散回表。

从最上层的 SQL 书写，到中间层的关系代数表达式等价重组，再到底层的物理索引指针巡检与缓冲区调度，层层贯通，唯有深刻理解从逻辑代数到物理存储的完整链路，才能真正在大型高并发系统的架构实践中写出高效、优雅且坚不可摧的数据库应用。
