## 关系数据库的数据定义与 SQL 规范基石
> 对应块：BLK09 | 覆盖分集：P07 | 块标题（分集名）：《数据库第3章 SQL （第一部分：数据定义）》

即使没有系统学习过数据库系统的人，也一定听说过 SQL。在许多初学者的直观印象中，“一提到数据库，那就是 SQL”。这个几乎成为数据库代名词的语言，在关系数据库中承担着怎样的工作，它又是如何由浅入深构建起整座数据大厦的？

从计算机系统的本质来看，数据库学科核心只做一件事：**将现实世界中的客观对象与联系抽象为数据模型，并以结构化数据库的形式持久化存储**。但现实模型转换成数据之后，必须依赖专门的基础软件进行统一管理与调度，这个软件就是数据库管理系统（Database Management System，DBMS）。

用户与开发者依托 DBMS 开展日常生产工作，核心诉求集中在三类能力上：
1. **数据定义功能（Data Definition）**：搭建数据库的骨架，规约实体空间与数据结构；
2. **数据操纵功能（Data Manipulation）**：对已搭好的框架进行数据的增加、删除、修改与查询；
3. **数据控制功能（Data Control）**：确立数据运转的安全边界与业务规则，涵盖完整性约束与访问权限控制。

能够把这三类职能融于一体的语言，就是**结构化查询语言（Structured Query Language，SQL）**。SQL 底层既完整融合了关系代数的纯粹运算能力，又吸纳了关系演算的谓词表达能力，成为关系数据库中功能极强、通用的标准语言。

整个数据库基础理论的推进链路非常清晰：首先通过数据定义（DDL）把数据库模式与表格框架搭建起来；随后进入最为庞大复杂的数据查询与数据更新（DML）；接着在后续深入数据库的完整性与安全性控制（DCL）。完成这三大块，数据库的底层基础便彻底筑牢，其后才能顺理成章地推进到高阶的数据库工程设计。

### 技术标准化的本质与正向循环

SQL-86 标准自 1986 年由美国国家标准学会（ANSI）首次颁布以来，历经多次重大版本迭代，标准文本的页数成倍激增。但这其中最值得深思的技术命题并非规范的厚度，而是“标准（Standard）”与“标准化（Standardization）”的底层逻辑。

在信息技术领域，标准的成型路径通常可划分为两类：
- **政府主导的法定标准**：由国家行政权力与法律法规强制确立。例如各国的电源接口规范与民用供电电压。我国民用电网统一为 220V 电压，配合两相与三相标准插座；而日本民用电网则为 110V。跨国出差必须携带物理转换插头，这种强制性规范由国家主权背书。
- **市场博弈沉淀的行业标准**：在激烈的商业实践中因使用群体广泛、业界达成事实共识而最终固化。日常键盘采用的 QWERTY 字母排列，计算机领域通用的 ASCII 字符编码表，以及华为、中兴、大唐、中国移动等通信企业在 3G、4G、5G 演进中所贡献的核心专利与传输协议，皆属于典型的行业技术标准。

为什么行业标准值得顶级企业倾尽资源全力争夺？

设想如果关键技术领域缺乏统一规范：IBM 维护一套私有标准，微软推行一套，苹果、华为、小米各自定义一套。此时，身处中下游的零部件供应商与生态开发商将面临不可调和的资源困境。企业的资金、研发人力、物料产能都是有限的：
- 如果孤注一掷 all-in 某一家厂商的私有标准，一旦该厂商在终端竞争中败北淘汰，配套企业的全部研发投入将瞬间归零；
- 如果将有限的技术精力平均分摊至五家体系，则力量彻底分散，根本无法在任何一条技术线上实现规模量产与精细化突破。

统一技术标准的诞生，正是破局这一供应链泥潭的利器，并由此催生出深刻的经济学与工程学正向闭环：

### SQL 语言的核心特质与九大核心动词

作为关系模型的标准化载体，SQL 呈现出四个鲜明的技术特质：

#### 综合统一的语言架构

在早期的非关系数据库（如网状、层次数据库）中，数据定义、数据操作与权限控制往往被割裂为完全独立的子系统与语言规范，开发人员需要穿梭于多套语法规则之间。SQL 将数据定义语言（Data Definition Language，DDL）、数据操纵语言（Data Manipulation Language，DML）与数据控制语言（Data Control Language，DCL）融为一体：
- **DDL** 负责设计建筑蓝图，定义库、表、视图等元数据框架；
- **DML** 负责在房屋建好后，完成住户（数据）的入住、迁移、装修与日常核查；
- **DCL** 负责制定门禁规则与安防条例，确保合规访问。

语言风格自始至终高度统一，能够自主完成关系数据库全生命周期内的所有技术活动。

#### 高度非过程化的操作语义

与 C、Java 等传统高级程序设计语言有着本质分野。面向过程语言解决问题时，开发者必须用严密的逻辑编写控制流语句，一步一行地指定具体算法细节与指令执行次序。

SQL 则走向了高度非过程化。用户只需明确表达**“想要什么结果”**，而完全无需关心**“底层存取路径如何寻找、算法如何实现”**。
例如，要求系统计算某门课程全班学生的平均成绩，用户只需提交一行查询表达式。至于数据库内核底层是走全表扫描还是走索引覆盖，临时哈希表是在内存分配还是落盘到交换区，全部交由 DBMS 查询优化器与操作系统底层自主调度，对上层应用彻底透明。

#### 面向集合的操作范式

在过程化语言中处理 50 名学生的成绩数据，必须在内存中声明诸如学号、姓名、分数的局部变量作为容器，借助 `for` 或 `while` 循环每次只读入一行记录，执行判断与输出后清空容器，再通过步进器拉取下一条。面向过程语言在语法层面一次只能操作单条记录。

SQL 的基本数据结构是“关系”（二维表），其底层运算天然基于关系集合。一条 SQL 指令可以直接作用于整张二维表，输入是一个集合，经过过滤、投影与连接运算后，输出依然是一个集合。即使数据量达到数万甚至数百万行，SQL 也能以集合为单位一次性批处理完毕。

#### 双重运行模式与互补优势

SQL 既可以作为**独立语言**直接在交互式终端敲击执行，也可以作为**嵌入式语言**植入到 C、C++、Java、Python 等高级主语言中协作运行。

这种双模运行能力直接来源于其“高度非过程化”与“面向集合”的特质与过程化主语言形成的天然互补：
- 高级主语言擅长精细控制复杂的业务逻辑流程、分支调度与用户交互，但对大规模关系集合的运算处理极为笨拙；
- SQL 擅长海量数据的快速筛选、投影与关联计算，但缺乏复杂程序分支与循环调度的表达能力。

将 SQL 语句嵌入宿主语言中，SQL 就化身为专职的高效数据访问接口，主语言向其传递参数并接收结果集，实现了系统工程架构层面的各取所长。

#### 九大核心动词

尽管 SQL 支撑着极为庞杂的企业级系统，但其基础词汇体系却精炼到了极致，全语言的核心操作仅由 9 个基础动词驱动：

| 功能范畴 | 英文动词 | 核心语义 | 工程定位 |
| :--- | :--- | :--- | :--- |
| **DDL**（数据定义） | `CREATE` | 创建 | 构建模式、基本表、视图或索引的元数据框架 |
| | `DROP` | 删除 | 彻底抹除指定对象的物理或逻辑定义 |
| | `ALTER` | 修改 | 动态追加字段、调整属性或变更既有约束 |
| **DML**（数据操纵） | `SELECT` | 查询 | 依照指定谓词条件投影、检索与汇总数据集合 |
| | `INSERT` | 插入 | 向二维关系中写入新的元组数据 |
| | `UPDATE` | 更新 | 批量或条件修正既有元组中的属性值 |
| | `DELETE` | 删除 | 依据谓词条件清空或剔除特定元组 |
| **DCL**（数据控制） | `GRANT` | 授权 | 将特定的数据访问或修改权限授予指定用户 |
| | `REVOKE` | 收回 | 剥夺已分配的系统或对象操作权限 |

> **提示**：权限控制的语义非常简明。例如在教学管理系统中，可以将成绩表的更新权限通过 `GRANT UPDATE ON SC TO ...` 授予学习委员；一旦发现违规越权修改，可通过 `REVOKE` 立即将其收回。

#### 三级模式结构与 SQL 的作用域边界

SQL 的具体语法映射到数据库系统的三级模式体系中，有着严格的职能分工：
- **外模式（External Schema）**：在 SQL 中对应**视图（View）**；
- **模式（Schema）**：在 SQL 中对应**基本表（Base Table）**；
- **内模式（Internal Schema）**：在物理层对应底层文件系统中的**存储文件（Storage File）**。

```text
+---------------------------------------------------------------+
|                       外模式 (视图 View)                       |
|           [View 1]                [View 2: 虚表]              |
+----------------------+-----------------------+----------------+
                       | 映射映射               |
+----------------------v-----------------------v----------------+
|                     模式 (基本表 Base Table)                   |
|       [Student 表]           [Course 表]         [SC 表]       |
+----------------------+-----------------------+----------------+
                       | 物理映射               |
+----------------------v-----------------------v----------------+
|                     内模式 (存储文件与索引)                    |
|   [底层数据文件: 0101...]    [B+树索引文件]   [物理磁道/扇区]   |
+---------------------------------------------------------------+
```
> **读图说明**：SQL 能够直接操纵的范围严格止步于基本表与视图层。底层存储文件由操作系统及具体的 DBMS 商业内核全权接管，对数据库用户与应用程序完全隐蔽。

基本表是独立存在的物理实体，一个基本表可以对应一个或多个底层物理数据文件。
视图则是从一个或若干个基本表（或其他视图）导出的虚表。数据库中**只保留视图的元数据定义，绝不重复物理存储其中的元组数据**。实际数据仍牢牢固化在底层的基本表中。例如，若只想以“性别分布”的单一视角观察学生，通过投影学号与性别两列构造出的就是一个轻量级视图。视图上还能继续无限嵌套派生新视图。

### 案例基准环境：学生-课程数据库架构

后续所有 SQL 数据定义的语法推导，全部以经典的**学生-课程数据库（S-T 模式）**为基准展开。该数据库包含三张最经典的关系表：

1. **学生表（`Student`）**：
   - 模式结构：`Student(Sno, Sname, Ssex, Sage, Sdept)`
   - 语义：记录学生的学号、姓名、性别、年龄以及所在院系。
2. **课程表（`Course`）**：
   - 模式结构：`Course(Cno, Cname, Cpno, Ccredit)`
   - 语义：记录课程的课程号、课程名称、先行课程号（`Cpno`）与学分。
3. **学生选课表（`SC`）**：
   - 模式结构：`SC(Sno, Cno, Grade)`
   - 语义：记录学生与课程的多对多选课关联以及考试成绩。

三张表之间的主外码参照依存拓扑如下：

```text
  +------------------+         +------------------+
  |     Student      |         |      Course      |<---+
  |------------------|         |------------------|    |
  | PK: Sno          |         | PK: Cno          |    |
  |     Sname        |         |     Cname        |    |
  |     Ssex         |         |     Cpno (FK) ---+----+ (自引用外码)
  |     Sage         |         |     Ccredit      |
  |     Sdept        |         +--------+---------+
  +--------+---------+                  |
           |                            |
           |                            |
           |    +------------------+    |
           |    |        SC        |    |
           |    |------------------|    |
           +--->| PK, FK: Sno      |    |
                | PK, FK: Cno      |<---+
                |     Grade        |
                +------------------+
```
> **读图说明**：`SC` 表的主码是由 `Sno` 与 `Cno` 构成的复合主码，同时这两个属性分别作为外码引用 `Student` 表与 `Course` 表的主码；`Course` 表中的先行课号 `Cpno` 构成对自身 `Cno` 的自引用外码关系。

### 模式的生命周期与命名空间管理

数据定义语言遵循极简的祈使句语法结构：由 3 个动词（`CREATE`、`DROP`、`ALTER`）搭配 4 个名词宾语（`SCHEMA`、`TABLE`、`VIEW`、`INDEX`）组合而成。

但在具体语法支持上，各对象的行为存在显著差异：

| 操作对象 | `CREATE`（创建） | `DROP`（删除） | `ALTER`（修改） | 工程设计逻辑 |
| :--- | :---: | :---: | :---: | :--- |
| **`SCHEMA`（模式）** | 支持 | 支持 | 尽量不提供 | 模式等同于房屋的地基框架。框架一旦搭好并入住数据，再去撼动地基极易引发灾难性系统错误，必须在一开始就规划清晰。 |
| **`TABLE`（基本表）** | 支持 | 支持 | 深度支持 | 基本表等同于房屋内的房间，新增列、改字段、调约束极为普遍，必须允许动态演进。 |
| **`VIEW`（视图）** | 支持 | 支持 | 不提供 | 视图只是算法映射的虚表。与其维护复杂的映射修改逻辑，不如直接“删除后重建”，既干净彻底又绝无隐式系统故障。 |
| **`INDEX`（索引）** | 支持 | 支持 | 仅支持重命名 | 索引类似于图书索书卡，结构变更通常直接销毁重建，修改仅用于更名。 |

#### 模式的创建与命名空间本质

定义模式的通用语法形式为：
```sql
CREATE SCHEMA <模式名> AUTHORIZATION <用户名>;
```
如果在创建时不显式指定 `<模式名>`，系统将默认以 `<用户名>` 作为该模式的名称。

> **定义**：定义模式的实质，是在数据库内核中**开辟一个独立的命名空间（Namespace）**。

在同一个命名空间下，表名、视图名与索引名不得冲突；但在不同的模式命名空间之间，完全可以存在同名的基本表。
在创建模式的同时，SQL 允许在后方连续嵌套追加子表定义、视图定义与授权语句。

为用户 `ZHANG` 创建一个名为 `TEST` 的模式，并在该模式命名空间内直接开辟一张包含 5 个属性列的测试表 `TAB1`：
```sql
CREATE SCHEMA TEST AUTHORIZATION ZHANG
    CREATE TABLE TAB1 (
        COL1 SMALLINT,
        COL2 INT,
        COL3 CHAR(20),
        COL4 NUMERIC(10, 3),
        COL5 DECIMAL(5, 2)
    );
```
在字段定义中，`NUMERIC(10, 3)` 声明该数值总有效位数最长为 10 位，小数点后保留 3 位精度；`DECIMAL(5, 2)` 则规约总位长 5 位，小数部分占 2 位。

> **提示**：学习编程与系统技术，最忌讳的是死记硬背。没有任何企业会在实际工程中禁止程序员查阅技术手册与工具书，更不会要求纯默写代码。技术能力的真正分水岭，在于彻底理解底层的运行机理、体系框架与边界条件，并能凭借敏锐的技术嗅觉在官方手册中比同行更迅速、更精准地定位到规范解法。

#### 模式删除的工程防御策略

删除已存在的模式语法如下：
```sql
DROP SCHEMA <模式名> <CASCADE | RESTRICT>;
```
面对已容纳了多张基本表、索引与海量数据的模式，删除操作直接触碰到底层资产的安危。为此，SQL 设立了两种严格对立的防御参数：

- **级联删除（`CASCADE`）**：
  执行时无视模式下是否存在关联对象，强行执行“铲地皮”式的彻底抹除。该模式连同其所辖的基本表、视图、存储过程及物理索引统统被一并清空销毁。
- **限制性删除（`RESTRICT`）**：
  默认且具备防误删保护的策略。在删除该模式前，数据库引擎会逐一探查其内部是否残留有下属对象（如表、视图等）。**只要检测到一个下属对象存在，系统将立刻抛出异常并拒绝执行删除**。运维人员必须手动清空该模式下的全部子资产后，方可成功销毁该空模式壳体。

### 基本表定义与完整性约束的工程实现

基本表是整个关系数据库的核心骨架。建立基本表的语法骨架如下：
```sql
CREATE TABLE <表名> (
    <列名> <数据类型> [<列级完整性约束条件>],
    ...
    [, <表级完整性约束条件>]
);
```

#### 单表构建与完整性约束推导

以 `Student` 表为例，包含学号、姓名、性别、年龄、所在系 5 个列：
- 学号作为唯一标识元组的属性，设为主码。在列定义后追加列级完整性约束 `PRIMARY KEY`。
  > **结论**：列级声明 `PRIMARY KEY`，在底层约束语义上完全等价于同时施加了 `UNIQUE`（全局唯一）与 `NOT NULL`（非空）双重限制。
- 姓名要求全校无重名，追加 `UNIQUE` 约束；
- 属性的数据类型与空间占用量必须根据业务边界精确评估。在生产环境中，随意分配过大的字符空间不仅严重消耗硬盘容量，更会迅速蚕食 DBMS 昂贵的物理内存缓冲池（Buffer Pool），劣化整体 I/O 效率。

编写出的 `Student` 建表脚本：
```sql
CREATE TABLE Student (
    Sno   CHAR(9) PRIMARY KEY,
    Sname CHAR(20) UNIQUE,
    Ssex  CHAR(2),
    Sage  SMALLINT,
    Sdept CHAR(20)
);
```

再看 `Course` 表，包含课程号、课程名、先行课号与学分。
此处存在一个关键的自引用关联：先行课号 `Cpno` 本身也是一门课程，其值必须来源于本院开设的 7 门核心课程之一。因此，**`Cpno` 是一条隐含指向本表主码 `Cno` 的外码线**。
```sql
CREATE TABLE Course (
    Cno     CHAR(4) PRIMARY KEY,
    Cname   CHAR(40),
    Cpno    CHAR(4),
    Ccredit SMALLINT,
    FOREIGN KEY (Cpno) REFERENCES Course(Cno)
);
```

#### 复合主码与选课表（SC）构建规范

在三张基本表中，学生选课表 `SC` 要素最为齐备，也是关系模型约束考查的典型基准。

在 `SC` 表中，单纯凭借学号（`Sno`）无法唯一确定一条记录，因为一个学生会选修多门课程；单纯凭借课程号（`Cno`）也无法唯一确定记录，因为一门课程会被多名学生选修。只有将 `(Sno, Cno)` 捆绑为一个整体，才能在全表中唯一锚定一个选课元组。因此，**学号与课程号共同构成复合主码**。

> **易错点**：千万不能将复合主码拆开写在列级定义之后！
> 如果在定义 `Sno` 时在后面跟上 `PRIMARY KEY`，随后在定义 `Cno` 时又跟上 `PRIMARY KEY`，SQL 引擎将直接判定语法报错。因为在关系数据库规范中，**一张表绝对不允许存在两个独立的主码**。写成两个列级约束，表达的不是“共同联合做主码”，而是荒谬的“双主码”。

复合主码必须作为一个**表级完整性约束**，统一收拢在所有属性列定义完毕后的最末尾进行联合声明：`PRIMARY KEY (Sno, Cno)`。

外码同样关乎表与表之间的跨实体引用，同样应当作为表级约束在末尾清晰陈列：
- `Sno` 作为外码，严格参照 `Student` 表的主码 `Sno`；
- `Cno` 作为外码，严格参照 `Course` 表的主码 `Cno`。

标准的 `SC` 建表脚本规范如下：
```sql
CREATE TABLE SC (
    Sno   CHAR(9),
    Cno   CHAR(4),
    Grade SMALLINT,
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```
将主码与外码统一写在末尾不仅规避了复合主码的语法冲突，更能让数据实体的约束拓扑一目了然，是高规格工程代码的标准实践。

#### 常用数据类型概览

SQL 支持丰富的数据类型以适配多样化的数据形态，常用基础类型如下：

| 数据类型分类 | 常用类型名称 | 存储特性与工程适用场景 |
| :--- | :--- | :--- |
| **定长字符** | `CHAR(n)` | 固定分配 $n$ 字节空间，不足时右补空格；适合学号、手机号、身份证等定长字段 |
| **变长字符** | `VARCHAR(n)` | 按实际字符长度动态存储（额外记录长度前缀）；适合姓名、地址等离散文本 |
| **整型数值** | `INT` / `INTEGER` | 标准 4 字节有符号整数，支撑常规数值计算与计数 |
| | `SMALLINT` | 2 字节小整数，适合年龄、学分、成绩等小范围标量 |
| | `BIGINT` | 8 字节大整数，适配超大规模分布式自增主键 |
| **高精度数值** | `NUMERIC(p, s)` / `DECIMAL(p, s)` | 精确小数存储，总长 $p$ 位，小数占 $s$ 位；彻底避免浮点误差，金融核算必备 |
| **布尔逻辑** | `BOOLEAN` | 仅存储 `TRUE` / `FALSE` 逻辑状态 |
| **时空维度** | `DATE` / `TIME` | 分别存储“年-月-日”日期信息与“时:分:秒”时间序列 |

#### 表与模式的归属绑定途径

在分布式或多租户数据库中，如何将创建的表准确绑定至特定的模式命名空间？工业界通常有三类实践路径：

1. **模式显式前缀限定法**：
   在执行建表语句时，显式为表名追加模式前缀：
   ```sql
   CREATE TABLE "S-T".Student (...);
   ```
   **工程优势**：极具灵活性。在漫长的业务迭代期，如果程序员在既有代码中发现遗漏了某张配置表，随时随地写一句带有模式前缀的建表指令即可精准归位，无需侵入全局上下文。
2. **模式定义内嵌嵌套法**：
   在执行 `CREATE SCHEMA` 的主干语句中，直接以嵌套子句的形式紧跟若干个 `CREATE TABLE`。
   **工程优势**：体系严整明晰，建库时所有表结构一气呵成；但缺点是缺乏弹性，要求在工程启动伊始就对全局表结构拥有极其完备的顶层设计。
3. **搜索路径上下文切换法**：
   通过 DBMS 提供的环境指令切换当前客户端的命名空间指针：
   ```sql
   SET search_path TO "S-T", PUBLIC;
   CREATE TABLE Student (...);
   ```
   在掌握方法一与方法二的前提下，已足以应对绝大多数工程场景。

### 基本表的动态演进与安全移除

业务系统的需求迭代是不可逆的技术现实，上线后的基本表必须具备动态演进的能力。

#### 动态调整表结构（ALTER TABLE）

修改基本表结构的通用语法为：
```sql
ALTER TABLE <表名>
    [ ADD [COLUMN] <新列名> <数据类型> [<完整性约束>] ]
    [ ADD <表级完整性约束> ]
    [ DROP [COLUMN] <列名> [RESTRICT | CASCADE] ]
    [ DROP CONSTRAINT <完整性约束名> [RESTRICT | CASCADE] ]
    [ ALTER COLUMN <列名> <新数据类型> ];
```

无论执行何种变更，**首要步骤必须先书写 `ALTER TABLE <表名>` 锁定操作主体**。主体确立后，后续子句才能合法展开。

##### 案例一：向基本表中增添新属性列
为学生表增加入学时间字段：
```sql
ALTER TABLE Student ADD S_entrance DATE;
```
> **注意**：无论原始关系表中已沉淀了多少条历史数据，**通过 `ADD` 动态新扩充的列，一律被系统无条件填赋为 `NULL`（空值）**。

##### 案例二：修改既有属性列的数据类型
将年龄字段的数据类型由字符类型更改为整数类型：
```sql
ALTER TABLE Student ALTER COLUMN Sage INT;
```
这一指令深刻体现了 SQL 的**高度非过程化**：开发者只需向引擎声明目标列的最终期望形态（变为 `INT`），根本无需编写“原本是什么字符编码、底层如何做字节对齐转换”的过程细节。

##### 案例三：后置追加完整性约束
在课程表建立完毕后，追加一条业务规则：要求课程名称（`Cname`）必须全局唯一：
```sql
ALTER TABLE Course ADD UNIQUE(Cname);
```

#### 基本表的安全销毁（DROP TABLE）

当基本表生命周期终结时，可调用 `DROP TABLE` 语句彻底销毁物理存储与元数据：
```sql
DROP TABLE <表名> [RESTRICT | CASCADE];
```

当这张基本表已经被上层视图引用、或者建立了外部索引时，参数的选择将引发截然不同的系统行为：

```text
               +-----------------------------+
               |     信息系学生视图 (View)    |
               +--------------+--------------+
                              | 依赖 (Depend on)
                              v
               +-----------------------------+
               |       Student (基本表)       |
               +-----------------------------+
```

如果基于 `Student` 表以专业为信息系（`IS`）为筛选条件派生出了一个外层视图，此时尝试对底层基本表执行移除：
- **执行限制性删除**：
  ```sql
  DROP TABLE Student RESTRICT;
  ```
  数据库内核检测到存在依附于该表的外部视图，引擎将强行拦截该指令，并在控制台抛出明确的阻断性错误：
  ```text
  ERROR: cannot drop table Student because other objects depend on it.
  ```
  此时必须先行手工通过 `DROP VIEW` 销毁依赖视图，才能成功抹除基本表。
- **执行级联删除**：
  ```sql
  DROP TABLE Student CASCADE;
  ```
  数据库将直接执行清屏操作：物理移除 `Student` 基本表，同时**自动连带销毁一切以此表为源数据建立的视图、触发器与索引对象**，并向控制台返回告警通知（`NOTICE`）。

> **提示**：全球主流商业关系数据库（如 Oracle、SQL Server、MySQL、PostgreSQL）在遵循 SQL 标准的同时，对 `RESTRICT` 与 `CASCADE` 的边界支持与错误回执处理存在一定差异。在工业界实际开发中，无需死记硬背各厂商的边缘细节，只要理解“级联清空”与“依赖受限”的底层哲学，在具体选型落地时调阅厂商的官方 Technical Reference 手册即可。

### 索引机理与多维检索优化

关系数据库中每时每刻都在发生海量检索。如果全表未建立任何定位结构，每次执行查询都将退化为全表物理扫描（Full Table Scan），效率极低。

> **定义**：**索引（INDEX）**是关系数据库中**以额外存储空间和写入开销为代价，用于大幅加速数据检索效率的核心辅助数据结构**。

索引的核心技术机理，正如在图书馆中借阅图书：数以万计的图书分布在多层楼的数百个书架上。读者之所以不必走遍每个书架逐本翻阅，是因为馆方在总服务台建立了一套按照索书号、书名、作者编排的索引卡片系统。只要定位到索引卡片，顺着卡片上记录的物理货架指针，就能一步到位精准提取目标图书。

#### 主流索引数据结构剖析

- **顺序文件索引**：将数据元组按主键物理升序排列，检索时通过折半查找等方式快速锁定扇区。
- **B+ 树索引**：计算机工业界应用最为普遍的平衡多路查找树。树结构中的每一个内部节点仅存储键值和子节点指针，所有实际数据指针全部汇聚于叶子节点，各叶子节点之间通过双向链表相连。
  > **结论**：B+ 树索引具备出色的**动态平衡性**。无论数据如何动态增删，树的高度高度收敛且全局平衡，区间检索与点查的 I/O 次数高度可控。
- **哈希索引（Hash Index）**：基于特定的数学散列函数，将键值直接映射为一个离散的物理桶（Bucket）地址。
  > **结论**：哈希索引具备极其优异的**等值查询极速性**，时间复杂度趋近于常数阶 $O(1)$，但完全无法支持基于 `<`、`>` 的范围查询与有序排序。
- **位图索引（Bitmap Index）**：针对低基数（Cardinality，列值重复率极高，如性别、省份）字段，利用位向量进行按位与、或计算，极其紧凑且速度飞快。

#### 索引的创建与维护规范

在关系数据库的管理规范中，**索引由系统管理员或表的所有者负责创建，由 DBMS 内核负责在数据变更时自动维护，而对所有最终用户与查询进程完全透明开放**。

定义索引的标准语法为：
```sql
CREATE [UNIQUE] [CLUSTER] INDEX <索引名>
ON <表名>(<列名> [ASC | DESC], ...);
```
- `ASC` 与 `DESC`：升序（Ascending）与降序（Descending）。若省略不写，系统默认按照升序（`ASC`）编排。
- `UNIQUE`：声明该索引为**唯一索引**。引擎在加速检索的同时，将强制拦截对该列的重复值写入操作。
- `CLUSTER`：声明该索引为**聚簇索引（Clustered Index）**。

> **提示**：如何具象化理解聚簇索引的机理？
> 手机通讯录是最佳类比。通讯录通常默认按照姓名拼音的首字母划分物理分区（A、B、C、D……）。如果要在通讯录中查找“爸爸”的电话，用户绝不会从头逐个滑动数百个联系人，而是迅速划至字母“B”对应的聚簇区块。由于物理上姓氏首字母为 B 的所有人全都紧凑聚拢在该区块内，一眼扫过几个人即可瞬间定位。**聚簇索引意味着数据表中元组的物理排列顺序直接与该索引的逻辑顺序完全重合，一张表至多只能设立一个聚簇索引**。

#### 工业命名规范与维护实战

为学生-课程数据库建立规范索引：
1. `Student` 表按照学号升序建立唯一索引；
2. `Course` 表按照课程号升序建立唯一索引；
3. `SC` 选课表按照学号升序、课程号降序建立多属性联合唯一索引。

编写的标准 DDL 脚本如下：
```sql
-- 1. 为 Student 表建立学号唯一索引 (默认升序 ASC)
CREATE UNIQUE INDEX Stusno ON Student(Sno ASC);

-- 2. 为 Course 表建立课程号唯一索引 (省略 ASC 仍为升序)
CREATE UNIQUE INDEX Coucno ON Course(Cno);

-- 3. 为 SC 表建立复合联合唯一索引
CREATE UNIQUE INDEX SCno ON SC(Sno ASC, Cno DESC);
```

> **注意**：工业软件工程极其讲究**命名自解释性**。在建立索引时，虽然命名为 `abcd`、`xyz` 语法上完全合法，但绝不能随心所欲。代码不仅是写给编译器运行的，更是交付给整个工程团队长期维护的。采用 `表名_列名` 或标准简写（如 `Stusno`、`Coucno`、`SCno`），能让任何同行在审查执行计划时一目了然其挂载对象，将团队协作与故障排查成本降到最低。

修改索引通常只支持重命名：
```sql
ALTER INDEX <旧索引名> RENAME TO <新索引名>;
```
而删除废弃索引则直接释放其底层物理占用：
```sql
DROP INDEX <索引名>;
```

### 数据字典与系统元数据规范

一个成熟的软件工程项目在历经数月乃至数年研发后，最终连同底层数据库系统交付给甲方客户或后续运维团队。此时，系统内部纵横交错着成百上千张数据表、海量英文缩写字段、外码依赖链以及复杂的业务约束。

没有任何外来接盘的程序员能够单凭代码里的 `Student(Sno)` 脑补出全部背后的商业逻辑。为此，系统交付物中必须包含一本完备的**“技术说明书词典”——数据字典（Data Dictionary）**。

数据字典系统性地登记了整个信息架构的核心元数据，通常完整涵盖六大维度：
1. **数据项**：最小的不可拆分数据单元（属性名称、类型、长度、取值范围与物理单位）；
2. **数据结构**：数据项之间的聚合关系（对应关系实体的属性集合）；
3. **数据流**：数据在各个业务子系统之间的流动路径、频率与峰值通量；
4. **数据存储**：数据固化落盘的逻辑载体（基本表、视图、历史归档库）；
5. **处理过程**：对数据实施业务加工的具体流转逻辑、输入前置条件与输出后置状态；
6. **外部实体**：产生源数据或消费目标数据的外部人、设备与第三方系统接口。

当后续开发者接手系统、面对从未谋面的代码变量时，只需翻阅数据字典的元数据规范，即可实现精准对齐，这是任何企业级系统不可或缺的技术规范基石。

#### 课堂实战练习：选课表 SC 的完整 DDL 定义

**【题干描述】**
要求在关系数据库中通过 DDL 语言建立学生选课表 `SC`。
已知该表包含三个属性：
- 学号 `Sno`：定长 9 字节字符型；
- 课程号 `Cno`：定长 4 字节字符型；
- 成绩 `Grade`：小整型（`SMALLINT`）。

请写出符合标准规范的建表 SQL 语句，要求必须完整体现出该表的主码约束与所有外码引用约束。

**【标准答案】**
```sql
CREATE TABLE SC (
    Sno   CHAR(9),
    Cno   CHAR(4),
    Grade SMALLINT,
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

**【解析与考点依据】**
1. **复合主码的表级约束机制**：`SC` 表的单一属性皆无法独立唯一标识选课事实，必须由 `Sno` 与 `Cno` 联合构成复合主码。在关系模型中一张表只能有一个主码，严禁将两个属性分别声明为列级 `PRIMARY KEY`；必须在表末尾作为表级完整性约束统一声明：`PRIMARY KEY (Sno, Cno)`。
2. **多外码参照完整性**：选课表中的学号必须真实存在于学生表 `Student` 中，课程号必须真实存在于课程表 `Course` 中。必须在末尾分别声明两个表级外码约束：`FOREIGN KEY (Sno) REFERENCES Student(Sno)` 与 `FOREIGN KEY (Cno) REFERENCES Course(Cno)`，以确保参照完整性不受破坏。

## 关系数据库标准语言 SQL 单表数据查询与分组聚合
> 对应块：BLK10 | 覆盖分集：P08 | 块标题（分集名）：《数据库第3章 SQL (第二部分：数据查询PAR》

### 数据查询在 SQL 体系中的定位与核心语句结构

#### SQL 语言功能划分与查询的核心地位

我们在讨论关系数据库标准语言 SQL 时，首先要从整体上把握其功能架构体系。SQL 整体上划分为三大功能模块：

1. **数据定义语言（Data Definition Language，DDL）**：用于定义、修改和删除数据库模式对象（如模式、表、视图、索引）。
2. **数据操作语言（Data Manipulation Language，DML）**：用于对数据库中的数据进行检索与维护，包含数据的增加（INSERT）、删除（DELETE）、修改（UPDATE）与查询（SELECT），也就是工程中常说的“增删改查”。
3. **数据控制语言（Data Control Language，DCL）**：用于数据库的安全性与并发完整性控制，包含用户权限授予、收回以及事务控制。

在数据操作环节中，数据增加、删除与修改统称为数据更新操作，其语义与语法相对直接；而数据查询（SELECT）则是整个 SQL 中表达能力最丰富、组合规则最灵活、技术难度最高的组成部分。掌握数据查询，是深入理解关系数据库检索模型与查询优化机制的基石。

#### 基础查询块的核心子句体系

SQL 查询的核心语法单元称为“查询块”（Query Block），由一组具有严格逻辑执行顺序的子句构成。一个完备的 SELECT 语句骨架如下：

```sql
SELECT [ALL | DISTINCT] <目标列表达式> [, <目标列表达式> ] ...
FROM <表名或视图名> [AS <别名>] [, <表名或视图名> ... ]
[ WHERE <条件表达式> ]
[ GROUP BY <列名1> [ HAVING <条件表达式> ] ]
[ ORDER BY <列名2> [ ASC | DESC ] ];
```

各个核心子句的功能与职责划分如下：

| 子句关键字 | 语法定位 | 技术职责 | 默认行为 / 约束 |
| :--- | :--- | :--- | :--- |
| `SELECT` | 属性投影 | 指定最终结果集中需要显示的属性列、常量、计算表达式或函数 | 默认保留所有行（`ALL`） |
| `FROM` | 查询范围 | 指定数据检索的基表、视图或派生表 | 必需子句，支持为数据源定义别名 |
| `WHERE` | 行级筛选 | 指定元组必须满足的检索条件表达式 | 针对基表元组逐行进行布尔判定 |
| `GROUP BY` | 元组分组 | 按照指定列的属性值对元组进行分类归纳 | 相同属性值的元组聚合为同一个分组 |
| `HAVING` | 组级筛选 | 对 `GROUP BY` 划分后的分组施加统计过滤条件 | 仅与 `GROUP BY` 配合使用，筛选满足条件的组 |
| `ORDER BY` | 结果排序 | 控制输出结果集按照一个或多个属性列的升序或降序排列 | 默认为升序（`ASC`），降序为 `DESC` |

在这六个核心子句中，`SELECT`、`FROM`、`WHERE` 是最基础的三元组，经常组合出现并构成单层查询块的基础骨干。

#### 数据查询的学习脉络与方法规划

在数据库查询的整体知识体系中，学习路径应当由浅入深，按照以下序列逐步演进：

1. **单表查询**：所有检索均严格限定在单一关系表内部完成。单表查询是全部分析机制的立足点，也是彻底厘清上述六个子句语义特性的关键。
2. **多表连接查询（Join）**：涉及两个或两个以上表的笛卡尔积与条件拼接，通过主码与外码关联建立跨表检索。
3. **嵌套查询（Nested Subquery）**：在一个查询块内部嵌入另一个子查询块，实现分步求解与谓词判断。
4. **集合查询（Set Operations）**：通过并（UNION）、交（INTERSECT）、差（EXCEPT）等代数集合操作组合多个查询结果。
5. **基于派生表的查询**：在 FROM 子句中通过子查询临时生成中间结果集（派生表或内联视图），并在此基础上进一步施加筛选。

一个复杂的多表检索任务，往往可以分别采用“多表连接”、“嵌套子查询”或“集合查询”三种不同策略来实现。然而，无论后续方案如何扩展，单表查询都是其底层运算的细胞基元。

为了承接前后讨论，本文的案例统一沿用经典的教学数据库三表模式：
- 学生关系表：`Student(Sno, Sname, Ssex, Sage, Sdept)`，属性分别代表学号、姓名、性别、年龄、所在系。
- 课程关系表：`Course(Cno, Cname, Cpno, Ccredit)`，属性分别代表课程号、课程名、先行课号、学分。
- 选课关系表：`SC(Sno, Cno, Grade)`，属性分别代表学号、课程号、考试成绩，其中 `(Sno, Cno)` 构成复合主码。

### 基于输入输出分析法的单表投影与列选择

#### 关系代数到 SQL 查询块的语义映射

在深入 SQL 具体语法之前，我们需要建立一种结构化的解题思维。在关系代数理论中，我们提出过一套普适的“输入输出分析法”。这种方法将数据检索过程解构为三个维度：输出（需要呈现的属性）、输入（施加的约束条件）与范围（数据运算的定义域）。

在关系代数中，投影算子 $\pi$ 决定了向用户展示的属性列；选择算子 $\sigma$ 提供筛选谓词；而作用的对象关系 $R$ 则划定了检索空间。当我们将这套思维平移到 SQL 语言时，二者存在完全一一对应的映射关系：

```text
  输入输出分析法               关系代数算子                 SQL 查询子句
+------------------+       +-------------------+       +-------------------+
| 输 出 (Output)   | <---> |  投影算子 ( π )   | <---> |   SELECT 子句     |
+------------------+       +-------------------+       +-------------------+
| 范 围 (Scope)    | <---> |  关系/关系积 (R)  | <---> |   FROM 子句       |
+------------------+       +-------------------+       +-------------------+
| 输 入 (Condition)| <---> |  选择算子 ( σ )   | <---> |   WHERE 子句      |
+------------------+       +-------------------+       +-------------------+
```

> **说明**：上述逻辑流向揭示了 SQL 语句声明式表达的本质——用户通过 `SELECT` 声明期望的输出属性（对应投影），通过 `FROM` 限定目标关系（对应操作对象），通过 `WHERE` 声明逻辑约束谓词（对应选择），而底层的遍历与提取则交由关系引擎完成。

面对任何查询需求，我们第一步是识别“输出是什么”（填入 SELECT）、第二步识别“范围在哪个表”（填入 FROM）、第三步判定“是否存在输入约束”（有则填入 WHERE，无则省略）。

#### 选择表中指定列与全体列

当查询仅需要关系表中的特定属性时，直接在 `SELECT` 列表中指明列名，各列名之间以半角逗号分隔。

例如，要求查询全体学生的学号与姓名：
- 输出属性：学号（`Sno`）、姓名（`Sname`）；
- 涉及范围：学生表（`Student`）；
- 筛选条件：全体学生，无条件。

根据规则，`WHERE` 子句缺省不写，SQL 语句为：

```sql
SELECT Sno, Sname
FROM Student;
```

同理，若要求查询全体学生的姓名、学号以及所在系（`Sdept`），只需在目标列表中增加相应属性：

```sql
SELECT Sname, Sno, Sdept
FROM Student;
```

> **提示**：目标列表中属性列的书写顺序不强制受制于物理建表时的顺序，输出结果集的列排布将严格与 `SELECT` 子句指定的顺序保持一致。

若业务场景要求检索关系表中的全体属性列，逐一列出全部字段名虽然语法完全正确，但在属性众多时繁琐低效。SQL 提供了通配符 `*`（星号）来表示关系的全体属性投影：

```sql
SELECT *
FROM Student;
```

此处的 `SELECT *` 与显式罗列 `SELECT Sno, Sname, Ssex, Sage, Sdept` 具有完全等价的关系代数语义。

#### 目标列表达式的高级投影能力

`SELECT` 并不是只能机械地打印物理表中原样存储的静态列名。从程序执行机理来审视，`SELECT` 子句中的各个目标项在内存处理流程中等价于**变量表达式**。关系引擎在扫描每一行元组时，将当前元组对应的属性值代入表达式进行动态求值，并将求值结果作为该行最终的投影数据。

因此，目标列表达式具备极强的计算与格式构造能力：

##### 算术运算表达式

若关系表中未直接存储某个衍生数据，但该数据可通过已有字段推导，可直接在 `SELECT` 中执行算术运算。例如，已知学生的年龄 `Sage`，要求计算其出生年份。我们可用基准年份（如 2022 年）减去其实际年龄：

```sql
SELECT Sname, 2022 - Sage
FROM Student;
```

当关系引擎遍历到第一行元组 `('李勇', 20)` 时，将计算 `2022 - 20 = 2002` 并输出；遍历到第二行时同样执行动态计算，实现了派生属性的运行时求值。

##### 常量列与函数调用

目标列表达式不仅支持数值运算，还支持常量字面量（Literal Constant）与内置标量函数：
- **常量列**：在 SQL 中，未用引号包裹的标识符被解析为属性变量名，而使用单引号包裹的内容则被解析为固定的字符常量。若在 `SELECT` 中声明 `'Year of Birth:'`，该常量将作为固定内容打印在结果集的每一行中。
- **标量函数**：可直接嵌套内置函数对字段值进行转换处理，例如调用 `LOWER(Sdept)` 将系别缩写全部转化为小写字符输出。

```sql
SELECT Sname, 'Year of Birth:', 2014 - Sage, LOWER(Sdept)
FROM Student;
```

该查询输出时，第二列恒为字符串 `'Year of Birth:'`，第三列为动态计算值，第四列为小写转换后的系别标识。

##### 列别名（Alias）机制

直接使用算术表达式或函数调用会导致结果集的表头显示为原始表达式文本（如 `2014-Sage` 或 `LOWER(Sdept)`），严重影响结果的可读性。为此，SQL 允许在目标列表达式后通过空格指定列别名：

```sql
SELECT Sname NAME, 
       'Year of Birth:' BIRTH, 
       2014 - Sage BIRTHDAY, 
       LOWER(Sdept) DEPARTMENT
FROM Student;
```

执行后，查询结果集的表头将直接显示为 `NAME`、`BIRTH`、`BIRTHDAY`、`DEPARTMENT`，实现了展示层与底层物理存储属性名的清晰解耦。

### 行级数据筛选与条件表达式

#### 重复元组剔除机制

关系代数理论上的关系具有纯集合性质，元组具有唯一性；但在实际的 SQL 关系数据库中，基于查询性能与实际应用考量，默认的多重集（Multiset / Bag）模型允许结果集中存在完全重复的行。

`SELECT` 关键字后允许显式指定重复元组的处理方式：
- `ALL`：保留结果集中的所有重复行（系统默认行为）；
- `DISTINCT`：对结果集执行去重操作，相同元组仅保留一份。

考虑如下场景：查询选修了课程的学生学号。
选课表 `SC` 中存储了全校学生的选课记录，其复合主码为 `(Sno, Cno)`。如果一个学生选修了 3 门课程，`SC` 表中就会产生 3 条包含该生学号的记录。

若直接执行：

```sql
SELECT Sno
FROM SC;
```

此时系统采用默认的 `ALL`，结果集中同一个学号会出现多次。如果我们仅关心“有哪些学生选了课”，而不关心具体的选课门数，必须显式引入 `DISTINCT` 消除重复元组：

```sql
SELECT DISTINCT Sno
FROM SC;
```

该语句执行时，关系引擎会对投影后的学号集合执行去重（通常借助排序或哈希去重算法），最终每一个选课学生仅输出一行记录。

#### 比较与范围确定谓词

行级筛选的核心在于 `WHERE` 子句中的布尔条件表达式。只有使该表达式求值结果为 `TRUE` 的元组，才会被筛选进入后续处理环节。

常用的比较运算符包括：`=`（等于）、`>`（大于）、`<`（小于）、`>=`（大于等于）、`<=`（小于等于）、`!=` 或 `<>`（不等于）。

例如，查询所有计算机科学系（`CS`）学生的姓名：

```sql
SELECT Sname
FROM Student
WHERE Sdept = 'CS';
```

查询所有年龄在 20 岁以下的学生姓名及其年龄：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sage < 20;
```

当我们需要判断某个属性值是否落在特定的连续闭区间内时，可使用范围判定谓词 `BETWEEN ... AND ...` 及其反向谓词 `NOT BETWEEN ... AND ...`。

> **定义**：`列名 BETWEEN 下限值 AND 上限值` 严格等价于 `列名 >= 下限值 AND 列名 <= 上限值`，包含两端的边界值。

例如，查询年龄在 20 到 23 岁（含两端）之间的学生姓名、系别与年龄：

```sql
SELECT Sname, Sdept, Sage
FROM Student
WHERE Sage BETWEEN 20 AND 23;
```

反之，若要查询年龄不在 20 到 23 岁之间的学生情况：

```sql
SELECT Sname, Sdept, Sage
FROM Student
WHERE Sage NOT BETWEEN 20 AND 23;
```

#### 集合成员与字符模糊匹配

##### 集合成员判定谓词（`IN` 与 `NOT IN`）

当条件不是连续区间，而是一组离散的枚举常量集合时，可以使用 `IN` 谓词来判断属性值是否属于指定集合：

例如，查询信息系（`IS`）、数学系（`MA`）和计算机科学系（`CS`）学生的姓名与性别：

```sql
SELECT Sname, Ssex
FROM Student
WHERE Sdept IN ('CS', 'MA', 'IS');
```

若需查询既不在 `CS`、也不在 `MA` 和 `IS` 的其他系学生，使用 `NOT IN` 即可：

```sql
SELECT Sname, Ssex
FROM Student
WHERE Sdept NOT IN ('CS', 'MA', 'IS');
```

##### 字符串模糊匹配谓词（`LIKE` 与 `NOT LIKE`）

当针对字符型属性进行查找，且匹配条件包含模糊或部分已知模式时，常规的等号 `=` 无法胜任，必须采用 `LIKE` 谓词。

`LIKE` 语法的一般格式为：
`[NOT] LIKE '<匹配串>' [ESCAPE '<换码字符>']`

SQL 字符串模式匹配定义了两个核心通配符：
- `%`（百分号）：代表**任意长度**的字符串（长度可为 0，亦可为任意正整数）。
- `_`（下划线）：严格代表**任意单个字符**。

不同通配模式的语义对比如下：

| 模式表达式 | 匹配语义说明 | 合法匹配示例 | 非法匹配示例 |
| :--- | :--- | :--- | :--- |
| `'A%B'` | 以 `A` 开头且以 `B` 结尾的任意长度字符串 | `'AB'`, `'ACB'`, `'A123B'` | `'BA'`, `'ACBD'` |
| `'A_B'` | 以 `A` 开头且以 `B` 结尾、中间恰好包含 1 个字符（总长度固定为 3） | `'ACB'`, `'ADB'` | `'AB'`, `'A12B'` |
| `'刘%'` | 所有姓“刘”的人（开头为刘，后接任意个字符） | `'刘勇'`, `'刘德华'`, `'刘'` | `'小刘'`, `'张刘'` |
| `'欧阳_'` | 姓“欧阳”且全名严格为三个汉字的学生 | `'欧阳修'`, `'欧阳锋'` | `'欧阳'`, `'欧阳小明'` |
| `'_阳%'` | 名字中第二个字为“阳”，全名长度至少为 2 的学生 | `'李阳'`, `'欧阳修'`, `'汪阳明'` | `'阳'`, `'李大阳'` |

对于确定值的匹配，如学号为 `'201215121'`，写作 `Sno LIKE '201215121'` 与 `Sno = '201215121'` 效果完全等价。

##### ESCAPE 转义机制

在工程实践中，若属性字段本身就包含 `%` 或 `_` 这类特殊符号（例如课程名 `DB_Design` 中的下划线），如果直接写 `LIKE 'DB_Design'`，系统会将下划线解析为通配符，从而错误地匹配出 `DBADesign`、`DBCDesign` 等非目标记录。

为了匹配字符本身的字面值，必须使用 `ESCAPE` 子句定义换码字符（转义符）：

```sql
SELECT Cno, Ccredit
FROM Course
WHERE Cname LIKE 'DB\_Design' ESCAPE '\';
```

> **原理**：`ESCAPE '\'` 声明反斜杠 `\` 为本次匹配的换码字符。关系引擎在扫描匹配串时，一旦遇到紧跟在 `\` 后面的 `_` 或 `_`，便不再将其作为通配符解析，而是直接作为普通下划线字面量进行精确比对。

再看一个更具代表性的复合匹配案例：查询以 `DB_` 开头，且倒数第三个字符为字母 `i` 的课程详细信息：

```sql
SELECT *
FROM Course
WHERE Cname LIKE 'DB\_%i__' ESCAPE '\';
```

在此模式中：
1. `DB\_`：由换码字符引导，表示课程名必须严格以 `DB_` 四个字符开头；
2. `%`：常规通配符，表示中间可以跨越任意长度的字符序列；
3. `i`：固定字符匹配；
4. `__`：末尾双下划线未被转义，代表倒数第二和倒数第一位各占一个任意字符。

#### 空值判定与逻辑复合条件

##### 空值（NULL）检查

在关系数据库中，空值（NULL）代表“未知”或“不存在”的特殊状态，它既不等于数值 0，也不等于空字符串 `''`。

> **易错点**：绝不能使用关系运算符 `= NULL` 或 `!= NULL` 进行空值判定。根据三值逻辑，任何值与 NULL 进行普通算术比较的结果均为 UNKNOWN（假）。空值的检测必须使用专用的 `IS NULL` 与 `IS NOT NULL` 谓词。

例如，查询尚未录入考试成绩（成绩为空）的选课记录：

```sql
SELECT Sno, Cno
FROM SC
WHERE Grade IS NULL;
```

##### 多重逻辑复合条件与优先级

当存在多个筛选条件时，使用布尔逻辑运算符 `AND`、`OR`、`NOT` 进行联结。
- **运算符优先级**：`NOT` 优先级最高，`AND` 其次，`OR` 优先级最低。
- **括号重载**：当复杂查询同时包含 `AND` 与 `OR` 时，应显式利用小括号 `()` 明确运算顺序，避免因运算符隐式优先级产生非预期的逻辑短路或语义漂移。

例如，查询计算机科学系（`CS`）且年龄在 20 岁以下的学生姓名：

```sql
SELECT Sname
FROM Student
WHERE Sdept = 'CS' AND Sage < 20;
```

前面提到的 `Sdept IN ('CS', 'MA', 'IS')` 集合判断，在底层逻辑展开上与多重 `OR` 完全等价：

```sql
SELECT Sname, Ssex
FROM Student
WHERE Sdept = 'CS' OR Sdept = 'MA' OR Sdept = 'IS';
```

### 查询结果排序控制与空值处理

#### 单列与多列排序规则

关系模型建立在无序集合的基础之上，若未明确指定排序规则，DBMS 返回的元组顺序由物理存储顺序或查询执行计划决定，不具备任何业务确定性。为了获得有序的结果集，必须使用 `ORDER BY` 子句。

`ORDER BY` 紧跟一个或多个属性列名，并支持两种排序列序：
- `ASC`（Ascending）：升序排列，为系统的默认缺省项；
- `DESC`（Descending）：降序排列。

##### 单列排序实战

例如，查询选修了 3 号课程的学生学号与考试成绩，并将结果按成绩由高到低降序排列：

```sql
SELECT Sno, Grade
FROM SC
WHERE Cno = '3'
ORDER BY Grade DESC;
```

##### 多列协同排序

当需要按多个维度进行综合排序时，可以在 `ORDER BY` 中列出多个字段，字段之间以逗号分隔。此时系统将严格按照**左侧字段为主排序列，右侧字段为次排序列**的规则执行级联排序。即：首先按照第一排序列排序；只有当若干元组在第一排序列上的值完全相同时，才依据第二排序列在该子集合内部进行再次排序。

例如，查询全体学生情况，要求结果首先按所在系的系号（`Sdept`）升序排列，而在同一个系内部的学生，再按照年龄（`Sage`）降序排列：

```sql
SELECT *
FROM Student
ORDER BY Sdept, Sage DESC;
```

> **提示**：在该语句中，`Sdept` 后未显式声明排序方向，系统自动应用默认的 `ASC`（升序）；而 `Sage` 后显式标注了 `DESC`，因此同一个系内的学生将按照年龄从大到小排列。

#### 空值在排序中的处理特征

当排序列中存在空值（NULL）时，由于空值缺乏明确的物理大小定义，SQL 标准将空值的排序权交由具体的 DBMS 实现自行决定。

在工程与教学约定中，存在一个广泛流传的实用规律：“**空值跟大头**”（即将 NULL 在逻辑比对中视为最大值）：
- **降序排列（DESC）时**：由于从大到小排，空值被视作“最大头”，因而排在结果集的最前列，紧随其后的是最高分（如 99 分、98 分）；
- **升序排列（ASC）时**：由于从小到大排（如 60 分、70 分、90 分、99 分），空值依然跟随“最大头”，被放置在结果集的最后端。

无论升降序如何流转，空值始终与数据集合中的高值端（大头）聚拢分布。

### 聚集函数统计与分组聚合处理

#### 常用聚集函数的全局统计

为了满足汇总与统筹分析需求，SQL 提供了内置的聚集函数（Aggregate Functions）。聚集函数的输入是一组列值，输出是一个单一的标量汇总值。

SQL 支持的标准聚集函数包括：

| 函数签名 | 功能描述 | 统计语义说明 |
| :--- | :--- | :--- |
| `COUNT(*)` | 统计元组总数 | 统计结果集中的物理行数，不忽略包含 NULL 的行 |
| `COUNT([DISTINCT \| ALL] <列名>)` | 统计某列值的总个数 | 统计指定列中非 NULL 值的行数；若加 `DISTINCT` 则剔除重复值后计数 |
| `SUM([DISTINCT \| ALL] <列名>)` | 计算数值列的总和 | 对该列中所有非 NULL 属性值求和（列类型必须为数值型） |
| `AVG([DISTINCT \| ALL] <列名>)` | 计算数值列的平均值 | 对该列中所有非 NULL 属性值计算均值（总和除以有效非 NULL 计数） |
| `MAX([DISTINCT \| ALL] <列名>)` | 求某列的最大值 | 返回该列非 NULL 值的最大者 |
| `MIN([DISTINCT \| ALL] <列名>)` | 求某列的最小值 | 返回该列非 NULL 值的最小者 |

##### 全局行数与实体统计

查询在校学生的总人数：只需统计学生表 `Student` 一共有多少行元组，使用 `COUNT(*)` 即可：

```sql
SELECT COUNT(*)
FROM Student;
```

##### 去重聚集统计

查询实际选修了课程的学生总人数：
由于一个学生可能选修多门课程，在选课表 `SC` 中多次出现，直接统计 `COUNT(Sno)` 会将同一个学生重复计算。此时必须在函数参数内部引入 `DISTINCT`：

```sql
SELECT COUNT(DISTINCT Sno)
FROM SC;
```

该语句确保系统先对学号做去重集合归纳，再计算独立实体的个数。

##### 数值汇总与极值统计

计算 1 号课程的平均成绩、最高成绩与最低成绩：

```sql
SELECT AVG(Grade), MAX(Grade), MIN(Grade)
FROM SC
WHERE Cno = '1';
```

关系引擎首先应用 `WHERE Cno = '1'` 筛选出所有选修 1 号课程的行，形成一个中间临时工作区；随后在该数据集上，`AVG` 自动过滤成绩为 NULL 的元组，将有效分数累加并除以选考人数，同步计算出极值并输出。

> **延伸思考**：若需要查询学号为 `'201215121'` 的学生选修课程的总学分，由于课程学分 `Ccredit` 存储在 `Course` 表，而该学生的选课记录存储在 `SC` 表，此时查询必须跨越两个表建立连接。我们可以通过两表的主外码等值条件（`SC.Cno = Course.Cno`）建立笛卡尔积上的筛选，进而应用 `SUM(Ccredit)` 实现聚合求和：
> 
> ```sql
> SELECT SUM(Ccredit)
> FROM SC, Course
> WHERE SC.Cno = Course.Cno 
>   AND SC.Sno = '201215121';
> ```
> 
> 这展示了聚集函数由单表向多表连接场景的自然延伸。

#### 分组聚合的运行机理

当查询语句中**没有** `GROUP BY` 子句时，聚集函数的作用域是整个查询结果集，将全体满足条件的行聚合成一个单行标量。

而一旦引入 `GROUP BY` 子句，整个数据处理流水线将发生质的改变：**聚集函数不再作用于全局，而是分别独立地作用于划分出来的每一个分组（Group）**。

`GROUP BY` 的核心作用，是将关系表中的元组按照一个或多个指定列的属性值进行分类归并，具有相同列值的元组被汇入同一个分组。

以“求各个课程号及相应的选课人数”为例：
- 需求目标：输出每一个课程号 `Cno`，以及选修该课程的总人数；
- 逻辑构建：按照课程号 `Cno` 进行元组切分，对切分后的每个组统计学号总数。

```sql
SELECT Cno, COUNT(Sno)
FROM SC
GROUP BY Cno;
```

该操作在底层的运行拓扑如下所示：

```text
  原始选课表 SC 元组集合                 GROUP BY Cno 分组              聚集函数分别作用并输出
+--------+--------+-------+          +-----------------------+          +--------+----------+
| Sno    | Cno    | Grade |          | 组 1 (Cno = 1)        |          | Cno    | COUNT(*) |
+--------+--------+-------+          | - (201215121, 1, 92)  | -------> +--------+----------+
| 201215121 | 1   | 92    |          | - (201215122, 1, 85)  | COUNT=2  | 1      | 2        |
| 201215121 | 2   | 85    |          +-----------------------+          | 2      | 2        |
| 201215121 | 3   | 88    |          | 组 2 (Cno = 2)        |          | 3      | 1        |
| 201215122 | 1   | 85    | -------> | - (201215121, 2, 85)  | -------> +--------+----------+
| 201215122 | 2   | 90    |          | - (201215122, 2, 90)  | COUNT=2
+--------+--------+-------+          +-----------------------+
                                     | 组 3 (Cno = 3)        |
                                     | - (201215121, 3, 88)  | COUNT=1
                                     +-----------------------+
```

> **说明**：关系引擎首先根据 `Cno` 散列或排序，将 5 条原始元组分类放置到 3 个独立的组桶中；随后，`COUNT(Sno)` 分别进入组 1、组 2、组 3 执行行数统计，最终组装输出 3 行聚合记录。

#### 组级筛选子句与行级过滤的本质辨析

当我们需要对分组后的统计结果进一步施加条件筛选时，必须使用 `HAVING` 子句。初学者极其容易将 `HAVING` 与 `WHERE` 混淆，甚至写出在 `GROUP BY` 之后使用 `WHERE` 过滤聚合值的严重语法错误。

##### 案例分析：选课门数筛选

考虑查询：选修了 3 门以上课程的学生学号。
- 分析过程：每一个学生有多条选课记录，必须按照学号 `Sno` 分组；
- 聚合判断：分组后，每组内部的选课记录总数（即 `COUNT(*)`）若大于 3，则该组满足条件。

```sql
SELECT Sno
FROM SC
GROUP BY Sno
HAVING COUNT(*) > 3;
```

执行时，引擎先按 `Sno` 分组，并在每个组内部执行 `COUNT(*)`；凡统计值 $\le 3$ 的分组直接舍弃，仅输出统计值 $> 3$ 的组标识 `Sno`。

##### 经典正误对比：平均成绩门槛筛选

再分析一个典型案例：查询平均成绩大于等于 90 分的学生学号和其平均成绩。

- **错误写法示范**：
  ```sql
  /* 错误写法：试图在 WHERE 中过滤聚集函数，或将 WHERE 置于 GROUP BY 之后 */
  SELECT Sno, AVG(Grade)
  FROM SC
  WHERE AVG(Grade) >= 90
  GROUP BY Sno;
  ```
  上述语句必定报错。因为在执行 `WHERE` 子句时，系统尚未开始分组，甚至尚未完成扫描，在行级维度上根本不存在 `AVG(Grade)` 的值。

- **标准正确写法**：
  ```sql
  SELECT Sno, AVG(Grade)
  FROM SC
  GROUP BY Sno
  HAVING AVG(Grade) >= 90;
  ```

##### WHERE 与 HAVING 的本质区别

为了从根本上杜绝混淆，我们将 `WHERE` 与 `HAVING` 的底层机制对比如下：

```text
  数据流向流水线时序：
  [FROM 基础表] ---> [WHERE 行级过滤] ---> [GROUP BY 划分分组] ---> [聚集函数计算] ---> [HAVING 组级过滤] ---> [SELECT 投影] ---> [ORDER BY 排序]
```

> **说明**：数据首先经由 `WHERE` 在行级完成初筛并剔除无效元组；剩余元组被 `GROUP BY` 打包为分组集合并由聚集函数求值；最后由 `HAVING` 对聚合统计值实施组级筛选，决定哪些组能够最终输出。

两者的核心差异总结如下表所示：

| 维度 | `WHERE` 子句 | `HAVING` 子句 |
| :--- | :--- | :--- |
| **作用对象** | 作用于**基表或视图的原始元组**（行级） | 作用于**划分完成后的各个分组**（组级） |
| **执行时机** | 在**数据分组（GROUP BY）之前**执行过滤 | 在**数据分组与聚集计算完成之后**执行过滤 |
| **聚集函数支持** | **绝对不允许**在谓词中直接包含聚集函数 | **允许且通常必须**在谓词中包含聚集函数表达式 |
| **依赖关系** | 可独立存在于任何查询块中 | 必须依赖于 `GROUP BY` 分组上下文存在 |

理解了这一执行时序，我们便能清晰地构建出单表数据查询与分组聚合的完整认知闭环。掌握了这些单表查询的核心基准，后续的多表连接、嵌套子查询与集合操作，都将建立在这一坚实的基础之上。

## SQL 多表数据查询：连接、嵌套、集合与派生表
> 对应块：BLK11 | 覆盖分集：P09 | 块标题（分集名）：《数据库第3章 SQL（第二部分：数据查询PART》

我们在前一讲探讨的是单表查询。但在实际应用中，绝大多数业务场景都需要跨越多个数据表获取完整信息。单表查询只是一种基础的特例，面对涉及多张表的数据检索，SQL 提供了三套通用的解题路径：连接查询、嵌套查询和集合查询。

几乎所有复杂的多表查询需求，都可以通过这三类方式中的某一种或几种组合来实现。面对同一个业务问题，选用连接、嵌套还是集合，核心考量在于哪种方式编写最直观、逻辑最清晰，以及底层的执行效率更高。

### 多表查询的核心范式与等价性

处理多表查询时，首先需要建立一个宏观视角：连接查询、嵌套查询与集合查询在语义表达能力上具有高度的一致性。

```text
+--------------------------------------------------------------+
|                        多表查询需求                          |
+--------------------------------------------------------------+
           |                       |                      |
           v                       v                      v
     +------------+          +------------+         +------------+
     |  连接查询  |          |  嵌套查询  |         |  集合查询  |
     |   (JOIN)   |          |  (Nested)  |         |   (Set)    |
     +------------+          +------------+         +------------+
           |                       |                      |
           +-----------------------+----------------------+
                                   |
                                   v
                       +-----------------------+
                       |    底层关系代数运算   |
                       | (笛卡尔积/投影/选择等)|
                       +-----------------------+
```

上述图示展示了多表查询的三种核心求解路径。无论从哪一条路径切入，其本质都是对底层关系进行选择、投影、连接或集合操作。理解这种等价性后，我们在面对具体题目或业务需求时，就不会拘泥于某一种固有模式，而是根据表结构特点和运算目标，灵活选取最简练、最高效的方案。

### 连接查询的运行机理与实现

当查询同时涉及到两个或两个以上的关系表时，所进行的查询被称为连接查询（Join Query）。

#### 笛卡尔积与连接条件优先法则

从关系代数的底层机理来看，多表连接操作本质上包含两个核心步骤：首先求得相关表的笛卡尔积（Cartesian Product），穷举所有可能的元组组合；随后依据给定的连接条件对笛卡尔积进行筛选，剔除不满足匹配关系的元组，留下合规的结果行。

```text
表 Student (m 行)               表 SC (n 行)
       \                            /
        \                          /
         v                        v
       +----------------------------+
       |   笛卡尔积 (m × n 行元组)  |
       +----------------------------+
                     |
                     v  [按连接条件 Student.Sno = SC.Sno 筛选]
       +----------------------------+
       |      满足等值条件的行      |
       +----------------------------+
                     |
                     v  [按业务条件继续过滤，如 Cno = '2']
       +----------------------------+
       |        最终查询结果        |
       +----------------------------+
```

该流程清晰地说明了连接的物理演算过程。在 SQL 编写层面，我们可以沿用“输入输出分析法”：
- `SELECT` 对应期望输出的目标列；
- `WHERE` 对应数据筛选条件与匹配约束；
- `FROM` 对应涉及到的基础数据表。

> **结论**：多表连接无论是否有额外的业务筛选条件，只要在 `FROM` 中列出了两个以上的表，就**必须**首先在 `WHERE` 子句中写明连接条件。

若遗漏了连接条件，查询将退化为纯粹的笛卡尔积，不仅结果毫无业务意义，还会迅速耗尽服务器的内存与算力。

例如，需要查询每个学生及其选修课程的全部情况：

```sql
SELECT Student.*, SC.*
FROM Student, SC
WHERE Student.Sno = SC.Sno;
```

如果在此基础上增加筛选条件，例如仅查看计算机科学系（CS）学生的选修情况，只需使用逻辑与运算符 `AND` 进行条件追加：

```sql
SELECT Student.*, SC.*
FROM Student, SC
WHERE Student.Sno = SC.Sno AND Student.Sdept = 'CS';
```

在系统底层，DBMS 优化器可以通过嵌套循环连接（Nested Loop Join）、排序合并连接（Sort-Merge Join）或索引连接（Index Join）等物理算法高效完成匹配。作为声明式语言（Declarative Language），SQL 允许用户只声明“需要什么”，而不必干预底层引擎的算法调度。

#### 自然连接与显式投影

在等值连接的结果中，用于连接的公共属性列（如上述查询中的 `Sno`）会出现两次。关系代数中的自然连接（Natural Join）会自动剔除重复的公共列，保留唯一的属性集合。

但在传统的 SQL 标准查询块中，如果希望实现严格意义上的自然连接，必须在 `SELECT` 列表中显式、逐个列出需要保留的属性字段，手动规避同名列的重复投影：

```sql
SELECT Student.Sno, Sname, Ssex, Sage, Sdept, Cno, Grade
FROM Student, SC
WHERE Student.Sno = SC.Sno;
```

如果查询同时包含了连接条件与多项复合选择谓词，分析思路依然保持不变。例如查询选修了 2 号课程且成绩在 90 分以上的所有学生的学号与姓名：

```sql
SELECT Student.Sno, Sname
FROM Student, SC
WHERE Student.Sno = SC.Sno 
  AND SC.Cno = '2' 
  AND SC.Grade >= 90;
```

这里 `Student.Sno = SC.Sno` 是连接条件，而 `SC.Cno = '2'` 与 `SC.Grade >= 90` 是业务筛选条件，两者在 `WHERE` 子句中通过 `AND` 统一衔接。

#### 自身连接与别名表机制

通常情况下连接操作发生在两张不同的表之间，但如果需要在同一张表内进行多层次的关联检索，就需要运用自身连接（Self-Join）。

典型案例是查询每一门课程的间接先修课（即先修课的先修课）。现有一张课程表 `Course(Cno, Cname, Cpno, Ccredit)`，其中 `Cpno`（先修课号）是外码，参照引用本表的 `Cno`（主码）。

假设 1 号课（数据库）的先修课是 5 号课（数据结构），而 5 号课的先修课是 7 号课（PASCAL 语言）。如果我们只对着这一张表查看，需要先定位到第 1 行的 `Cpno=5`，再回到本表的 `Cno` 列查找 5 号记录，最后取出其 `Cpno=7`。这相当于在同一张表内部串行检索了两次。

单表查询无法在一个查询块内完成这种跨行的两级依赖，而常规的多表连接要求操作不同的表对象。要破解这个矛盾，核心的思维转换在于：**通过复制表对象，将自身单表的二次检索转换为两张虚拟表的跨表连接**。

在 SQL 中，实现表复制的手段是为数据表赋予不同的别名（Alias）：

```sql
SELECT FIRST.Cno, SECOND.Cpno
FROM Course FIRST, Course SECOND
WHERE FIRST.Cpno = SECOND.Cno;
```

```text
虚拟表 FIRST (代表本门课程)          虚拟表 SECOND (代表先修课程)
+-----+--------------+------+        +-----+--------------+------+
| Cno | Cname        | Cpno |        | Cno | Cname        | Cpno |
+-----+--------------+------+        +-----+--------------+------+
|  1  | 数据库       |  5   | --+    |  1  | 数据库       |  5   |
|  3  | 信息系统     |  1   |   |    |  3  | 信息系统     |  1   |
|  5  | 数据结构     |  7   |   +--> |  5  | 数据结构     |  7   |
+-----+--------------+------+        +-----+--------------+------+
                                            连接成功，提取 SECOND.Cpno=7
```

通过将 `Course` 分别命名为 `FIRST` 和 `SECOND`，我们在逻辑上创建了两张独立的表。`FIRST.Cpno = SECOND.Cno` 建立了前驱与后继的连接桥梁。没有先修课的课程（例如先修课号为 NULL 的基础课），由于在 `SECOND` 表中找不到匹配项，会在此连接中被自然剔除。

#### 外连接与悬浮元组保留

在常规的等值连接与自然连接中，匹配失败的元组会被直接丢弃。这些由于缺少对应关联项而被系统舍弃的元组，在关系代数中被称为悬浮元组（Dangling Tuples）。

然而在诸多业务场景中，悬浮元组包含着极具价值的信息。假设我们要统计班级内所有学生的选课状况：
- 班级内一共有 5 名学生；
- 选课表中只有其中 4 名学生的选修记录，第 5 名学生因为未选课或选课失败而在选课表中无任何记录。

如果执行常规等值连接，第 5 名学生因无法匹配而被静默过滤。作为教务人员或班主任查看统计报表时，极易误以为全班所有人都已顺利完成选课，从而忽略了未选课人员的存在。

为了保留这类没有匹配项的主体信息，必须引入外连接（Outer Join）。外连接的基本语义是：当某侧表的元组在另一侧找不到匹配时，不将其删除，而是使用 NULL（空值）填充缺失字段并予以完整呈现。

| 外连接类型 | 关键字 | 语义与行为 |
| :--- | :--- | :--- |
| 左外连接 | `LEFT OUTER JOIN` | 保留左侧表的全部元组；右侧表无匹配项时补 NULL |
| 右外连接 | `RIGHT OUTER JOIN` | 保留右侧表的全部元组；左侧表无匹配项时补 NULL |
| 全外连接 | `FULL OUTER JOIN` | 同时保留两侧表的全部元组；任意一侧无匹配均补 NULL |

以查看全班选课情况为例，采用左外连接可确保所有学生均出现在结果集中：

```sql
SELECT Student.Sno, Sname, Ssex, Sage, Sdept, Cno, Grade
FROM Student 
LEFT OUTER JOIN SC ON Student.Sno = SC.Sno;
```

在此结果表中，未选课的学生（如王敏、张力）依然会列出其学号、姓名与院系，而其 `Cno` 与 `Grade` 栏目均显式标记为 NULL，直观暴露未选课的业务状态。

#### 多表级联连接

当查询涉及的属性分散在三张或三张以上的数据表中时，连接操作可以沿着外码与主码的依赖链条逐级展开。

例如，要求查询每个学生的学号、姓名、选修的课程名以及考试成绩。这些属性分别位于 `Student`、`Course` 和 `SC` 三张表中：

```sql
SELECT Student.Sno, Sname, Course.Cname, SC.Grade
FROM Student, SC, Course
WHERE Student.Sno = SC.Sno 
  AND SC.Cno = Course.Cno;
```

在执行时，系统先基于 `Sno` 将学生基本信息与选课记录相绑定，再基于 `Cno` 关联出具体的课程名称，最终将三个维度的数据聚合在同一行元组中输出。

### 嵌套查询的模块化拆解与分类

在 SQL 语言中，一个形如 `SELECT-FROM-WHERE` 的独立语句被称为一个查询块（Query Block）。将一个查询块嵌入到另一个查询块的 `WHERE` 子句或 `HAVING` 短语中的查询模式，称为嵌套查询（Nested Query）。

#### 查询块黑盒与中间结果传导

理解嵌套查询最清晰的视角，是将每一个 `SELECT-FROM-WHERE` 查询块视作一个“黑盒子”（Black Box）：

```text
                  +---------------------------+
  WHERE 输入条件 ->|   查询块 (Query Block)    |-> SELECT 输出列集
                  | SELECT ... FROM ... WHERE |
                  +---------------------------+
```

既然每个黑盒子都有明确的输入（`WHERE` 过滤判定）与输出（`SELECT` 投影结果），那么内层黑盒子的输出，就可以作为外层黑盒子 `WHERE` 子句的判定输入。这种首尾相连的数据流向，使得查询块可以无限层级地嵌套下去。嵌入在内部的查询块称为子查询（Subquery）或内层查询；包裹在外层的查询块称为父查询（Parent Query）或外层查询。

在系统执行效能层面，嵌套查询与连接查询存在显著的特征差异：
- **连接查询**：需要构建多表之间的笛卡尔积或进行跨表数据对齐，在内存中维护多张表的数据集，数据量极大时系统资源开销显著；
- **嵌套查询**：通常以流水线（Pipeline）形式自底向上逐层处理，中间结果被快速消费或过滤，避免了膨胀性的笛卡尔积。

在编写嵌套查询时，存在一条硬性语法限制：

> **注意**：子查询的内部**严禁使用 `ORDER BY` 子句**。

这是因为子查询的产物仅仅是服务于外层判定的临时中间集，对中间集进行排序毫无业务意义，且白白耗费系统算力。排序操作是最终呈现层面的需求，如果查询结果需要按某种顺序输出，`ORDER BY` 只能写在最外层的父查询末尾。

#### 不相关子查询与相关子查询判定

根据子查询的执行条件是否依赖于外层父查询的当前状态，嵌套查询被划分为两大类别：

```text
不相关子查询 (Uncorrelated):
[内层子查询独立运算, 生成结果集] ---> [传导给外层父查询, 外层单次过滤完成]

相关子查询 (Correlated):
[外层取出一行元组 x] ---> [将 x.属性 传入内层]
         ^                        |
         |                        v
   [推进下一行] <------- [内层带入参数运算，返回真值/标量判定]
```

这两类子查询在计算机制上的边界如下：
- **不相关子查询**：子查询内部的条件完全独立，不引用父查询的任何属性。DBMS 采用自底向上、从里向外的顺序执行：内层子查询只执行一次，计算出确定的常量值或结果集，并将该结果集交付给父查询完成最终筛选；
- **相关子查询**：子查询的过滤条件中包含了父查询正在扫描的元组属性。这意味着内层查询无法脱离外层独立运算。外层查询每扫描一行元组，就必须将该元组的相关属性值传递给内层子查询执行一次运算，根据子查询返回的评估结果决定外层当前元组的去留。

#### 带有 IN 谓词的子查询

`IN` 谓词用于判断某个属性值是否属于子查询返回的结果集合之中，是不相关子查询中最常用的结构之一。

例如，查询与“刘晨”在同一个系学习的学生学号、姓名与所在系：

第一步，先从 `Student` 表中查出“刘晨”所在系的名称；
第二步，利用该院系名称检索所有属于该系的学生。

两步逻辑自然嵌套：

```sql
SELECT Sno, Sname, Sdept
FROM Student
WHERE Sdept IN (
    SELECT Sdept
    FROM Student
    WHERE Sname = '刘晨'
);
```

内层查询首先执行，输出单值 `'CS'`；外层查询随即退化为 `WHERE Sdept IN ('CS')`，单次遍历完成检索。该查询同样可以通过自身连接实现：

```sql
SELECT s1.Sno, s1.Sname, s1.Sdept
FROM Student s1, Student s2
WHERE s1.Sdept = s2.Sdept AND s2.Sname = '刘晨';
```

两者的业务输出完全一致，再次印证了连接与嵌套的等价性。

当查询依赖链条较长时，`IN` 谓词可以呈现三层甚至更多层次的嵌套。例如查询选修了课程名为“信息系统”的学生学号和姓名：
- 最内层（第 1 步）：在 `Course` 表中根据课程名 `'信息系统'` 查询其课程号 `Cno`；
- 中间层（第 2 步）：在 `SC` 选课表中根据求得的 `Cno` 检索选修该课的学生学号 `Sno`；
- 最外层（第 3 步）：在 `Student` 表中根据求得的 `Sno` 提取学生的姓名与基本信息。

```sql
SELECT Sno, Sname
FROM Student
WHERE Sno IN (
    SELECT Sno
    FROM SC
    WHERE Cno IN (
        SELECT Cno
        FROM Course
        WHERE Cname = '信息系统'
    )
);
```

编写这类多层嵌套查询时，严格遵循“最先求解的依赖写在最里层，最后输出的目标写在最外层”的装配逻辑。

#### 带有比较运算符的相关子查询

当子查询返回的结果是单值标量时，我们可以直接使用比较运算符（`=`、`>`、`<`、`>=`、`<=`、`!=` 或 `<>`）。如果返回的是单个值，`= ` 与 `IN` 可以完全互换。

最为关键的应用场景出现在相关子查询中。例如：**找出每个学生超过他自己选修课程平均成绩的课程号**。

这个题目的核心难点在于：每个学生选修的课程门数与科目各不相同，各自的平均分也不相同（例如张三选了 3 门课，平均分是 92 分；李四选了 4 门课，平均分是 78 分）。系统不可能预先求出一个全局的固定平均分，而是必须针对当前正在评估的这位学生，动态计算他自己的专属平均分。

这就构成了一个典型的相关子查询：

```sql
SELECT Sno, Cno
FROM SC x
WHERE Grade > (
    SELECT AVG(Grade)
    FROM SC y
    WHERE y.Sno = x.Sno
);
```

> **易错点**：外层 `FROM SC x` 中的 `x` 并非将表进行全量物理复制，而是一个**元组变量（Tuple Variable）**。它代表外层查询当前正在遍历抽取的某一行具体记录。

其详细执行演进过程如下：
1. 外层查询从表 `SC` 中取出第一行元组赋给 `x`，假定此时 `x.Sno = '201215121'`；
2. 系统将该主码值代入内层子查询中，此时内层查询被特化为：
   ```sql
   SELECT AVG(Grade) FROM SC y WHERE y.Sno = '201215121';
   ```
3. 内层查询计算出该学号对应的平均分（假定为 88 分），将 88 返回给外层表达式；
4. 外层 `WHERE` 评估该元组在当前这门课上的成绩是否满足 `x.Grade > 88`。若满足则将 `(x.Sno, x.Cno)` 写入最终结果集，否则舍弃；
5. 外层推进指针，取出 `SC` 中的下一行元组赋给 `x`，重复执行上述 2 至 4 步，直至外层全表元组处理完毕。

#### 带有 ANY 与 ALL 谓词的语义降维

当子查询返回多行标量时，如果需要与外层属性进行大小比较，需要配合 `ANY`（或 `SOME`）以及 `ALL` 谓词使用：
- `> ANY`：大于子查询结果中的任意一个值（即大于子查询的最小值）；
- `< ANY`：小于子查询结果中的任意一个值（即小于子查询的最大值）；
- `> ALL`：大于子查询结果中的所有值（即大于子查询的最大值）；
- `< ALL`：小于子查询结果中的所有值（即小于子查询的最小值）。

许多教材会列出复杂的等价转换表格，但背诵此类表格极易混淆。真正实用的方法是**顺着自然语言的语义直接推导**。

例如业务需求：查询非计算机科学系中，比计算机科学系任意一个学生年龄都小的学生姓名和年龄。

仔细推敲其语言逻辑：“比计算机系任意一个学生年龄小”，意味着在计算机系的所有学生中，只要有一个人的年龄比该生大即可。换句话说，**只要该生的年龄小于计算机系学生的最大年龄**，就必然满足“比任意一个年龄小”。

使用 `< ANY` 谓词的直观写法为：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sage < ANY (
    SELECT Sage
    FROM Student
    WHERE Sdept = 'CS'
) 
AND Sdept <> 'CS';
```

而将其语义降维后，直接使用聚合函数 `MAX` 的等价写法不仅执行效率更高，而且可读性极好：

```sql
SELECT Sname, Sage
FROM Student
WHERE Sage < (
    SELECT MAX(Sage)
    FROM Student
    WHERE Sdept = 'CS'
) 
AND Sdept <> 'CS';
```

同理，若要求“比计算机科学系所有学生年龄都小”，其物理含义就是该生年龄小于计算机系中的最小年龄（`< ALL` 等同于 `< MIN`）。理解了最值本质，就不需要死记硬背谓词转换规则。

#### 带有 EXISTS 谓词的存在性判定

带有 `EXISTS` 谓词的子查询代表形式逻辑中的存在量词 $\exists$。这类子查询具有两个鲜明的特质：
1. **不返回任何真实的数据列**：子查询只输出布尔真值 `TRUE` 或假值 `FALSE`。当内层子查询的结果集非空时，`EXISTS` 判定为真；当结果集为空集时，判定为假；
2. **目标列表通配化**：由于外层只在乎“是否存在匹配行”，根本不关心内层投影出了哪一列，因此内层 `SELECT` 后面写任何具体字段都没有实际意义。技术规范上**统一采用 `SELECT *`**，简洁明了。

`NOT EXISTS` 则刚好相反：内层为空集时为真，非空时为假。

例如，使用存在量词查询所有选修了 1 号课程的学生姓名：

```sql
SELECT Sname
FROM Student
WHERE EXISTS (
    SELECT *
    FROM SC
    WHERE SC.Sno = Student.Sno 
      AND SC.Cno = '1'
);
```

外层逐行遍历 `Student` 表中的每位同学，将学号传入内层；内层去 `SC` 表中探查该同学是否存在选修 1 号课的记录。一旦探测到记录存在，内层立刻返回 `TRUE`，外层遂将该学生的 `Sname` 输出。

### 集合查询的代数映射与去重控制

SQL 语言直接继承了关系代数中的传统集合运算，允许将两个或多个 `SELECT` 查询块的结果集进行集合运算。集合查询要求参与运算的各个查询结果具有相同的列数，且对应列的数据类型必须相互兼容。

```text
查询块 A 结果集: { 元组1, 元组2, 元组3 }
查询块 B 结果集: { 元组2, 元组3, 元组4 }

并集 (UNION):     { 元组1, 元组2, 元组3, 元组4 }  [自动去重]
交集 (INTERSECT): { 元组2, 元组3 }
差集 (EXCEPT):    { 元组1 }                     [属于 A 但不属于 B]
```

集合查询涵盖三类基础操作符：
- 并操作（`UNION`）；
- 交操作（`INTERSECT`）；
- 差操作（`EXCEPT`，在某些数据库实现中写作 `MINUS`）。

#### 并操作与去重控制

使用 `UNION` 可以将多个查询结果合并为一个结果集。在默认行为下，系统会自动执行去重操作，剔除重复元组：

例如，查询计算机科学系的学生以及年龄不大于 19 岁的学生：

```sql
SELECT *
FROM Student
WHERE Sdept = 'CS'
UNION
SELECT *
FROM Student
WHERE Sage <= 19;
```

如果业务明确需要保留所有重复出现的记录（例如统计两类群体的总体清单而不合并身份），可以使用 `UNION ALL`：

```sql
SELECT *
FROM Student
WHERE Sdept = 'CS'
UNION ALL
SELECT *
FROM Student
WHERE Sage <= 19;
```

#### 交操作与差操作

交操作 `INTERSECT` 返回同时出现在两个结果集中的公共元组。查询计算机科学系中年龄不大于 19 岁的学生：

```sql
SELECT *
FROM Student
WHERE Sdept = 'CS'
INTERSECT
SELECT *
FROM Student
WHERE Sage <= 19;
```

差操作 `EXCEPT` 返回属于第一个集合但排除第二个集合后的剩余元组。查询计算机科学系中年龄大于 19 岁的学生（即从 CS 学生中减去不大于 19 岁的学生）：

```sql
SELECT *
FROM Student
WHERE Sdept = 'CS'
EXCEPT
SELECT *
FROM Student
WHERE Sage <= 19;
```

> **提示**：集合查询是实现“或”（`OR`）、“且”（`AND`）、“非”（`NOT`）逻辑的另一种强有力工具。当过滤条件极其复杂、单表条件嵌套过深时，拆解成几个独立的 `SELECT` 块再利用集合操作拼装，能大幅提升 SQL 的清晰度与可维护性。

### 基于派生表的查询优化与聚合解耦

在前面的相关子查询中，我们处理了“找出每个学生超出其选修课程平均成绩的课程号”这一经典难题。虽然相关子查询能够解出答案，但外层每扫描一行就要调用一次内层聚合运算，在数据规模较大时执行效率较为低下。

派生表（Derived Table）为这一问题提供了极其优秀的工程解法。派生表的核心思维是：**通过子查询在内存中物化出一个具备明确 Schema 的临时结果集，并将其放置在父查询的 `FROM` 子句中，当作一张普通的基础表来进行常规的连接操作**。

我们可以将原先交织在一起的计算流程解耦为两步：
1. **聚合计算**：在 `SC` 表上利用 `GROUP BY Sno`，提前一次性计算出所有学生的平均成绩，并构建一个名为 `Avg_SC` 的派生表，定义其列名为 `(Avg_Sno, Avg_Grade)`；
2. **扁平连接**：将原始基础表 `SC` 与派生表 `Avg_SC` 按照学号进行普通的等值连接，在 `WHERE` 中直接比较各科成绩与计算好的平均分。

```sql
SELECT SC.Sno, SC.Cno
FROM SC, (
    SELECT Sno, AVG(Grade)
    FROM SC
    GROUP BY Sno
) AS Avg_SC(Avg_Sno, Avg_Grade)
WHERE SC.Sno = Avg_SC.Avg_Sno 
  AND SC.Grade > Avg_SC.Avg_Grade;
```

```text
派生表 Avg_SC (预先一次性聚合完成)        基础表 SC (各科原始成绩)
+---------+-----------+                     +-----+-----+-------+
| Avg_Sno | Avg_Grade |                     | Sno | Cno | Grade |
+---------+-----------+                     +-----+-----+-------+
| 95001   |    92     | <------------------ |95001|  1  |  94   | (94 > 92, 输出)
| 95002   |    81     |      等值连接       |95001|  2  |  90   | (90 < 92, 丢弃)
+---------+-----------+   Sno = Avg_Sno     +-----+-----+-------+
```

这种处理方式将低效的相关子查询转换为了两张表之间的普通多表连接，消除了每行元组反复调用子查询的系统开销，充分利用了 DBMS 对连接操作的优化机制。

### 数据查询语句的全景结构与约束

历经单表查询与本讲的多表连接、嵌套、集合及派生表查询，SQL 语言中功能最为庞大、语法最为丰富的 `SELECT` 查询语句已经完整呈现。

#### 语法骨架与子句编排

一个标准的、功能完备的 `SELECT` 语句其通用形式如下：

```sql
SELECT [ALL | DISTINCT] <目标列表达式> [别名] [, <目标列表达式> ...]
FROM <表名或视图名或派生表> [别名] [, ...]
[WHERE <条件表达式>]
[GROUP BY <列名1> [, ...] [HAVING <条件表达式>]]
[ORDER BY <列名2> [ASC | DESC] [, ...]];
```

各核心子句在执行管道中的职能与逻辑次序为：
1. `FROM`：确定数据源，载入基础表、视图或物化派生表；
2. `WHERE`：对数据源元组执行第一道行级过滤，应用连接条件与基本筛选谓词；
3. `GROUP BY`：依据指定的一个或多个属性列对过滤后的行进行分组汇总；
4. `HAVING`：对分组汇总后的组数据应用组级过滤谓词；
5. `SELECT`：投影目标列集，执行表达式运算、去重（`DISTINCT`）与别名赋予；
6. `ORDER BY`：对最终输出的结果集进行升序（`ASC`，默认）或降序（`DESC`）排序。

#### 核心约束与执行禁忌

在应用全景语法时，需重点把握以下几条关键约束：

> **易错点**：`WHERE` 子句与 `HAVING` 短语在作用阶段与功能上有着本质区别，绝不可混用。
> - `WHERE` 作用于基表或视图抽取的元组，过滤发生在数据**分组之前**，且其条件表达式中**严禁包含聚合函数**；
> - `HAVING` 作用于 `GROUP BY` 划分出的各个组，过滤发生在数据**分组之后**，其条件表达式中**通常包含聚合函数**。

在排序控制上，`ORDER BY` 缺省为升序排列（`ASC`）。当排序列存在 NULL 值时，不同的 DBMS 遵循其既定规则（例如某些系统将 NULL 视为极大值排在最后，某些系统视为空值排在最前）。而在所有子查询构造中，除非涉及到分页或顶部截取，否则禁止在外层未敲定前在子查询中使用 `ORDER BY`。

至此，关系数据库“增删改查”核心操作中复杂度最高的“查”（Data Query）已全部梳理完毕。掌握了基于笛卡尔积的连接法则、基于黑盒传导的嵌套机制、基于集合代数的并交差运算，以及基于派生表的性能解耦，我们便具备了应对绝大多数复杂企业级数据检索挑战的完备工具链。

## 数据更新操作、空值处理机制与视图应用
> 对应块：BLK12 | 覆盖分集：P10 | 块标题（分集名）：《数据库第3章 SQL（第三部分：数据更新与视图-》

在学习 SQL 语言时，我们首先要明确它在整个数据库管理系统（DBMS）体系中的功能定位。SQL 主要是为了实现数据库管理系统的三核心能力而设计的：第一是数据定义语言（DDL，Data Definition Language），用于构建模式（Schema）、基本表（Table）、索引（Index）以及视图（View）等数据库的逻辑框架；第二是数据操作语言（DML，Data Manipulation Language），也就是我们常说的增、删、改、查（插入、删除、修改、查询）；第三是数据控制语言（DCL，Data Control Language），用于权限控制与完整性约束管理。

此前我们已经彻底攻克了数据定义的所有 DDL 语句，并详尽剖析了 DML 中语法最灵活、嵌套最复杂的查询问题。查询解决之后，数据操作体系中剩下的就是插入、修改与删除这三项数据更新操作。与查询相比，数据更新的逻辑链条和操作难度要低得多，它直奔目标，充分体现了 SQL 高度非过程化的语言特性。但在实际应用中，数据一旦发生缺漏或未知，便会引入空值（NULL）以及打破传统布尔二值逻辑的三值逻辑系统。更进一步地，当我们把 DDL 的框架定义与 DML 的子查询能力结合起来时，便诞生了数据库体系中极其重要的虚表机制——视图。掌握好更新、空值与视图，我们才算真正掌握了关系数据库完整的数据生命周期操作。

### 数据插入操作

往数据库的基本表中新增数据，通常存在两种截然不同的场景：一种是录入单独一条具体的记录，例如班级里新转来一位同学；另一种则是把批量统计分析或者其他查询的结果一次性灌入表中。在 SQL 中，这分别对应了单行元组插入和基于子查询的多行元组插入。

#### 单元组数据插入

向表中插入单个元组的标准语法遵循清晰的三段式结构：`INSERT INTO ... VALUES ...`。其语法框架如下：

```sql
INSERT INTO <表名> [(<属性列1> [, <属性列2>]...)]
VALUES (<常量1> [, <常量2>]...);
```

在此结构中，`INSERT` 声明插入动作，`INTO` 指定目标表名以及要赋值的具体属性列列表，`VALUES` 后面跟上一组一一对应的具体常量值。

以向学生表 `Student` 中录入一名新同学为例。该表在建表时定义了学号（Sno）、姓名（Sname）、性别（Ssex）、所在系（Sdept）和年龄（Sage）五个字段。当需要插入完整记录时，标准写法是将列名与常量值按位置严格对应：

```sql
INSERT INTO Student (Sno, Sname, Ssex, Sdept, Sage)
VALUES ('201215128', '陈冬', '男', 'IS', 18);
```

在语法规范上，数字类型的常量（如年龄 18）可以直接书写，无需添加单引号；而字符串或字符类型则必须使用单引号闭合。

但在真实的业务场景中，我们经常遇到待插入数据不完整的情况。例如一名学号为 `201215128` 的学生刚选修了 1 号课程，但由于本学期刚开课、尚未组织期末考试，他的选课记录中只有学号和课程号，成绩（Grade）一栏暂时为空。选课表 `SC` 的表头包含 `(Sno, Cno, Grade)` 三列，面对这种情况，通常有两种处理途径：

第一种途径是在 `INTO` 子句中显式指定需要赋值的列名，省略未赋值的属性列：

```sql
INSERT INTO SC (Sno, Cno)
VALUES ('201215128', '1');
```

执行此语句时，DBMS 会自动将常量赋给指定的属性列，未被指定的 `Grade` 列将自动填入空值（NULL）。

第二种途径是在 `INTO` 子句中完全省略属性列列表，但此时 `VALUES` 子句必须提供与目标表定义顺序完全一致的全部属性值，缺少的字段显式使用 `NULL` 关键字占位：

```sql
INSERT INTO SC
VALUES ('201215128', '1', NULL);
```

> **提示**：虽然当为全表所有列提供数据时，SQL 允许完全省略 `INTO` 后的属性列名，但我强烈建议在实际工程中一律不要省略列名。在实际开发中，这一两行 SQL 通常是嵌套在庞大且长期迭代的应用程序中的。一旦未来因业务升级对表结构执行了 `ALTER TABLE`（例如在中间新增了字段或调整了顺序），省略属性列的插入语句就会瞬间因字段数量不匹配或类型错位而直接崩溃。显式声明属性列表，即使未来表结构扩展，原有插入逻辑依然稳健且自解释性极高。

#### 基于子查询的多元组批量插入

当我们需要向表中录入的不是单条手动录入的记录，而是一批可以通过查询获得的数据集合时，`VALUES` 子句就不再适用了。此时的核心解题思路是：利用子查询处理多条数据的输出能力。

嵌套查询中的查询块 `SELECT-FROM-WHERE` 本质是一个数据流发生器。我们给它一组筛选条件，它便能在 `SELECT` 处吐出一个由多行元组构成的结果集。利用这个特性，我们可以把子查询直接嵌套在 `INSERT INTO` 之后，将整个查询结果批量灌入新表中：

```sql
INSERT INTO <表名> [(<属性列1> [, <属性列2>]...)]
<子查询>;
```

例如，学校需要统计各系学生的平均年龄，并将该统计结果持久化存储在数据库中供其他报表使用。原始数据库中只有 `Student`、`Course` 和 `SC` 三张表，并没有存储“系平均年龄”的专用表。此时我们需要分两步完成：先用 DDL 建立承载表，再用带子查询的 `INSERT` 填充数据。

第一步，建立用于存放统计数据的空表 `Dept_Age`：

```sql
CREATE TABLE Dept_Age (
    Sdept CHAR(15),
    Avg_age SMALLINT
);
```

第二步，从学生表中按专业分组计算平均年龄，并将结果集批量插入：

```sql
INSERT INTO Dept_Age (Sdept, Avg_age)
SELECT Sdept, AVG(Sage)
FROM Student
GROUP BY Sdept;
```

这段代码精准展示了多行插入的机理：
1. 子查询从 `Student` 表中读取数据，并按照专业字段 `Sdept` 执行 `GROUP BY` 分组；
2. 在分组后，聚集函数 `AVG(Sage)` 遵从其经典执行特性——分别独立作用于每一个分组（例如单独算出计算机系平均年龄 20 岁、数学系平均年龄 21 岁）；
3. 子查询为每个组输出一行 `(Sdept, 平均年龄)` 的结果元组；
4. 外部的 `INSERT INTO` 接收到这组多行结果集，逐行将其写入目标表 `Dept_Age` 的对应列中。

在此过程中，子查询输出列的个数、顺序和数据类型必须与 `INSERT INTO` 指定的属性列严格兼容，否则系统将拒绝执行。

#### 插入过程中的完整性约束检查

向表中写入新数据绝非简单的字符堆砌，DBMS 在执行 `INSERT` 时必须作为关卡守卫，严格校验关系模型的三类完整性约束：

1. **实体完整性**：主码（Primary Key）对应的属性列绝对不能取空值，且插入的主码值不能与表中已存在的元组重复；
2. **参照完整性**：若插入的数据包含外码（Foreign Key），外码的值要么取空值，要么必须能够在被参照表的主码列中明确找到对应值；
3. **用户定义的完整性**：表定义时通过 `CHECK` 等约束声明的业务规则（例如性别仅限“男”或“女”，学生年龄必须在 15 到 55 岁之间）。

插入的数据一旦违反上述任何一条约束，DBMS 都会立即拦截并报错，绝不允许非法数据落入表中。

### 数据修改操作

数据的修改（Update）同样采用结构规整的三段式语句：`UPDATE ... SET ... WHERE ...`。它的核心功能是根据指定的筛选条件，对满足条件的一个或多个元组的特定字段赋以新的表达式计算值。

#### 数据修改的三种常见模式

修改语句的基本语法模板如下：

```sql
UPDATE <表名>
SET <列名> = <表达式> [, <列名> = <表达式>]...
[WHERE <条件>];
```

其中 `UPDATE` 声明要修改的目标表，`SET` 指定被修改的列名以及赋予的新值或计算表达式，`WHERE` 则是目标行的筛选过滤条件。根据业务场景的不同，数据修改通常分为三种类型：

第一种是**修改单个元组的值**。此时 `WHERE` 条件通常锁定主键，用于对某一条特定记录进行精确修正。例如，将学号为 `201215121` 的学生年龄修改为 22 岁：

```sql
UPDATE Student
SET Sage = 22
WHERE Sno = '201215121';
```

第二种是**修改多个元组的值**。当省略 `WHERE` 子句时，修改操作将无差别地作用于整张表中的每一行。例如，农历新年过后，全校所有学生的年龄统一增长 1 岁：

```sql
UPDATE Student
SET Sage = Sage + 1;
```

第三种是**带子查询的修改操作**。当筛选范围涉及跨表条件时，同样可以引入子查询来圈定目标范围。例如，因业务规则调整，需要将计算机科学系（CS）全体学生的选课成绩清零：

```sql
UPDATE SC
SET Grade = 0
WHERE Sno IN (
    SELECT Sno
    FROM Student
    WHERE Sdept = 'CS'
);
```

选课表 `SC` 本身只包含学号、课程号和成绩，并没有专业字段 `Sdept`。因此，我们在 `WHERE` 条件中使用子查询，先到 `Student` 表中查出所有系别为 `CS` 的学生学号集合，再通过 `Sno IN` 圈定目标记录，最终将符合条件的行中的 `Grade` 全部重置为 0。

#### 高度非过程化特征与完整性校验

很多初学者看到 `UPDATE Student SET Sage = 22 WHERE Sno = '201215121';` 时会觉得不可思议：这就改完了？不需要先查出他原本是几岁吗？

> **结论**：这就是 SQL 作为一种高度非过程化语言（Non-procedural Language）的核心魅力。非过程化语言的特征是“你只要告诉我你想干什么，中间过程你一概不用管”。在过程式编程中，你必须获取游标、定位行、读取旧值、计算新值、回写内存、提交事务。而在 SQL 中，系统根本不关心目标字段原本存储的是 19 岁、20 岁还是空值，你只要声明“把 22 赋给这一列”，DBMS 就会在底层自动调度存储引擎完成覆盖赋值。

与此同时，修改操作同样受到完整性约束的严密监控。如果手误将性别字段更新为数字 `99`，或者将外码字段更新为一个在主表中根本不存在的编号，DBMS 同样会强行报错并中止更新。

### 数据删除操作

数据操作语言中的删除操作使用 `DELETE` 语句，它的功能是把表中满足特定条件的元组整体抹除。

#### 数据删除的常见语法

删除操作的标准语句结构为：

```sql
DELETE FROM <表名>
[WHERE <条件>];
```

与修改类似，删除操作同样可以划分为三种层级：

第一种是**删除单个元组**。例如某位学生毕业离校，需要将其学籍记录从学生表中删除：

```sql
DELETE FROM Student
WHERE Sno = '201215121';
```

第二种是**删除多个元组（清空全表数据）**。如果省略 `WHERE` 筛选条件，系统将把指定表中的所有数据行全数删除：

```sql
DELETE FROM SC;
```

第三种是**带子查询的删除操作**。当删除条件依赖其他表时，使用子查询圈定目标范围。例如删除计算机科学系全体学生的全部选课记录：

```sql
DELETE FROM SC
WHERE Sno IN (
    SELECT Sno
    FROM Student
    WHERE Sdept = 'CS'
);
```

#### 数据清空与模式销毁的本质区别

在讲解 `DELETE FROM SC;` 时，必须深刻辨析它与 `DROP TABLE SC;` 的边界差异。这二者虽然执行后表里都没有了数据，但处于完全不同的维度：

```text
+-------------------------------------------------------------------+
|                     DELETE FROM SC (DML 数据操作)                  |
|  [元组1] ──> 清空                                                 |
|  [元组2] ──> 清空    ====>  表结构 (Table Schema) 与元数据依然完整存在   |
|  [元组3] ──> 清空           随时可以再次 INSERT 新数据             |
+-------------------------------------------------------------------+

+-------------------------------------------------------------------+
|                      DROP TABLE SC (DDL 模式定义)                  |
|  [元组数据] ──> 销毁                                               |
|  [表头字段] ──> 销毁  ====>  该表从数据库数据字典中彻底抹除，后续再次访问   |
|  [约束索引] ──> 销毁         直接报 "Table doesn't exist" 错误     |
+-------------------------------------------------------------------+
```
上图展示了清空数据行与销毁表结构的本质差别。

> **易错点**：`DELETE FROM <表名>` 属于数据操作语言（DML），它的操作对象是表中的**数据元组**。执行完毕后，表内的数据行被清空，但该表的逻辑框架、属性定义、约束以及索引在系统数据字典中依然完好无损，你可以立刻执行 `INSERT` 重新灌入数据。而 `DROP TABLE <表名>` 属于数据定义语言（DDL），它的操作对象是**表对象本身**。它不仅清除数据，还会连同该表在数据字典中的模式定义一并彻底销毁。执行之后再执行任何针对该表的查询或插入，都会直接抛出“表不存在”的致命错误。

### 空值语义与三值逻辑体系

在关系数据库中，空值（NULL）是一个极具特殊性的概念。它不是 0，也不是空字符 `""`，而是代表着“不知道（Unknown）”、“不存在”或“无意义”。

空值在数据库中有几种典型的来源：
1. 该属性本应有值，但当前尚未获知（如学生选修了某门课程，但尚未组织考试，成绩未知）；
2. 该属性客观上就不应该存在值（如未婚员工的配偶姓名）；
3. 录入人员出于某种特殊原因暂未填写。

#### 空值的产生与排查

在 SQL 操作中，空值主要是由两类操作产生的：
- 在 `INSERT` 时显式写入 `NULL`，或未给允许为空的列指定数值；
- 在 `UPDATE` 时将某个字段更新为 `NULL`。例如学号为 `201215210` 的学生办理了转专业手续，已经从原院系转出，但新专业接收手续尚在办理中，此时该学生的院系字段即可更新为空值：
  ```sql
  UPDATE Student
  SET Sdept = NULL
  WHERE Sno = '201215210';
  ```

在日常管理中，空值的判断非常具有实用价值。以学校收集上千名学生的信息表为例：一张上千行、十几列的复杂大表交上来，人工肉眼逐行排查谁漏填了信息几乎是不可能的。如果我们要把所有存在信息缺漏的学生名单一次性筛查出来，空值谓词便派上了用场。

空值的判断必须使用专门的语法：`IS NULL` 或 `IS NOT NULL`，绝对不能写成 `= NULL` 或 `<> NULL`。

对于 `Student` 表中除了不可为空的学号主键之外的四个字段，我们可以使用如下查询将所有存在漏填项的记录抓取出来：

```sql
SELECT *
FROM Student
WHERE Sname IS NULL
   OR Ssex IS NULL
   OR Sage IS NULL
   OR Sdept IS NULL;
```

只要姓名、性别、年龄或所在系中任意一个属性为空，该行元组就会被立即输出，极大提升了数据稽核效率。

在约束层面，并非所有字段都允许接纳空值：
- 显式声明为 `NOT NULL` 的列禁止赋空值；
- 带有 `UNIQUE` 唯一性限制的属性通常禁止为可冲突的空值；
- 实体完整性明确规定：主码中的任何主属性绝对禁止取空值。

#### 空值运算特性与三值逻辑

空值在参与表达式运算时具有极其独特的计算行为：

> **定义**：
> 1. **算术运算黑洞**：空值与任何常量或表达式进行算术加、减、乘、除运算，其结果一律为空值（`NULL + 1 -> NULL`）；
> 2. **比较运算未知**：空值与任何数值进行大小或等值比较运算（如 `=, <>, >, <`），系统均无法给出明确的是与否，其比较结果统一判定为“不知道”（`UNKNOWN`）。

由于比较运算中引入了 `UNKNOWN`，传统的布尔二值逻辑（True、False）在关系数据库中被扩展为**三值逻辑（Three-valued Logic）**。下表给出了三值逻辑下逻辑运算符（AND、OR、NOT）的真值表现：

| 变量 X | 变量 Y | X AND Y | X OR Y | NOT X |
| :--- | :--- | :--- | :--- | :--- |
| True | True | True | True | False |
| True | False | False | True | False |
| True | Unknown | **Unknown** | **True** | False |
| False | False | False | False | True |
| False | Unknown | **False** | **Unknown** | True |
| Unknown | Unknown | **Unknown** | **Unknown** | **Unknown** |

这张真值表无需死记硬背，理解其内在逻辑即可：
- 在 `AND`（且）运算中，必须两边全为真才为真；只要有一方为 False，结果必然是 False；若已知一方为 True，整体真假完全取决于另一方的确定性，因此 `True AND Unknown` 结果仍是 `Unknown`；
- 在 `OR`（或）运算中，只要有一方明确为 True，整个表达式就必定为 True，哪怕另一方是未知的 `Unknown`；若一方为 False，另一方未知，则整体依然是 `Unknown`；
- 对 `Unknown` 取非（`NOT`），得到的结果依然是未知的 `Unknown`。

#### 空值查询的边界陷阱与改写

三值逻辑在实际查询中极易引发逻辑遗漏。看这样一个经典业务需求：**找出选修了 1 号课程且成绩不及格的学生**。

很多人的第一直觉是直接写出如下查询：

```sql
SELECT Sno
FROM SC
WHERE Cno = '1' AND Grade < 60;
```

> **易错点**：这个查询得出的结果是不全面的。如果某个学生缺考，或者刚选课尚未录入成绩，他的 `Grade` 在表中记录为 `NULL`。当系统对该元组执行 `Grade < 60` 判定时，`NULL < 60` 的比较结果并不是 False，而是 `UNKNOWN`。在 SQL 的 `WHERE` 子句中，只有判定结果严格为 `TRUE` 的元组才会被筛选输出，结果为 `FALSE` 或 `UNKNOWN` 的元组都会被直接过滤丢弃。但从业务常理来看，缺考或未考学生同样属于“没有取得及格成绩”的范畴。

为了不遗漏这部分学生，正确的做法是将空值判断显式并入筛选条件中：

```sql
SELECT Sno
FROM SC
WHERE Cno = '1' AND (Grade < 60 OR Grade IS NULL);
```

或者，利用集合并集运算（`UNION`）分别提取两部分数据再行合并：

```sql
SELECT Sno FROM SC WHERE Cno = '1' AND Grade < 60
UNION
SELECT Sno FROM SC WHERE Cno = '1' AND Grade IS NULL;
```

这两种写法都能有效规避空值比较陷阱，确保边界数据的完整性。

### 视图的构建与管理机制

我们为什么把视图放在学完 DDL 和 DML 之后才讲？因为视图本身横跨了这两个领域：建立视图属于数据定义（DDL），搭起了一个虚拟表的框架；而视图内部的数据映射则完全依赖于查询语句（DML）。它是 DDL 与 DML 相互结合的产物。

#### 虚表特性与语法规范

> **定义**：视图（View）是从一个或多个基本表（或其它视图）中导出的表。它与基本表不同，是一张**虚表（Virtual Table）**。数据库系统中只在数据字典（Data Dictionary）中持久化保存视图的定义SQL，并不存放视图对应的物理数据行。基表中的数据一旦发生任何改变，通过视图查询出的映射数据也会实时动态联动。

创建视图的标准语法如下：

```sql
CREATE VIEW <视图名> [(<列名1> [, <列名2>]...)]
AS <子查询>
[WITH CHECK OPTION];
```

当 DBMS 执行 `CREATE VIEW` 语句时，它仅仅是把该视图的元数据定义写入系统字典，**此时并没有执行其中的 SELECT 语句去物理生成数据**。

语句尾部的 `WITH CHECK OPTION` 是一个极其重要的约束防线：
- 如果加了 `WITH CHECK OPTION`，当用户未来通过该视图执行 `INSERT`、`UPDATE`、`DELETE` 操作时，DBMS 会强制校验操作的数据是否满足子查询中指定的 `WHERE` 条件表达式；
- 如果不加该子句，系统在更新时则不予限制。

例如，在 `Student` 表的基础上建立一个信息系（IS）学生的专属视图：

```sql
CREATE VIEW IS_Student
AS
SELECT Sno, Sname, Sage
FROM Student
WHERE Sdept = 'IS'
WITH CHECK OPTION;
```

如果我们在该视图上添加了 `WITH CHECK OPTION`，那么未来有人试图通过 `IS_Student` 视图插入一条数学系（MA）或计算机系（CS）的学生记录时，DBMS 就会立即将该操作拦截并拒绝。因为这个视图本身的定位就是信息系学生，绝不允许非本系数据通过该窗口渗透进来。

关于视图属性列名的定义规则：
- 组成视图的属性列名可以全部指定，也可以全部省略；省略时默认继承子查询目标列表中导出的字段名；
- 但强烈不建议写出 `AS SELECT * FROM Student WHERE ...` 这种依赖通配符的视图。一旦底层基本表后续通过 `ALTER TABLE` 增加了新字段（例如新加了“家庭住址”列），基本表从 5 列变成了 6 列，但原有视图的字典定义并未重新编排，极易导致元数据不匹配而无法读取。

#### 视图构建模式分类

根据导出数据来源的不同，视图通常可以分为以下四种形态：

1. **行列子集视图**：从单个基本表导出，仅仅去掉了某些行和某些列，但保留了原表的主码。前面建立的 `IS_Student` 视图就是一个典型的行列子集视图；
2. **多表导出视图**：基于两个或两个以上的基本表联合导出。在多表导出时，必须在子查询中明确写出表间的连接条件。例如，建立信息系选修了 1 号课程的学生视图：
   ```sql
   CREATE VIEW IS_S1 (Sno, Sname, Grade)
   AS
   SELECT Student.Sno, Student.Sname, SC.Grade
   FROM Student, SC
   WHERE Student.Sno = SC.Sno
     AND Student.Sdept = 'IS'
     AND SC.Cno = '1';
   ```
   这里的 `Student.Sno = SC.Sno` 是连接两张表的必要条件，绝不可遗漏。
3. **基于视图派生的高阶视图**：因为视图对外呈现的形态依然是一张二维表，因此在已有视图的基础上可以继续派生新视图。例如在上述 `IS_S1` 视图的基础上，进一步筛选成绩在 90 分以上的优秀学生：
   ```sql
   CREATE VIEW IS_S2
   AS
   SELECT Sno, Sname, Grade
   FROM IS_S1
   WHERE Grade >= 90;
   ```
4. **带表达式与分组统计的视图**：视图中的字段允许包含计算表达式或分组聚集结果。例如定义一个包含学生学号及其平均成绩的统计视图：
   ```sql
   CREATE VIEW S_G (Sno, Gavg)
   AS
   SELECT Sno, AVG(Grade)
   FROM SC
   GROUP BY Sno;
   ```

#### 视图的销毁与级联控制

在视图的生命周期中，通常**只有 CREATE 和 DROP，不存在复杂的 ALTER 修改机制**（极端情况下仅支持修改视图名称）。

> **结论**：视图本质上只是一段存储在数据字典里的映射规则，自身不存放真实数据。如果你需要变更视图的映射逻辑，与其大费周章地去修改映射规则，不如直接将其删除然后重新创建，这在工程上更直观且不易出错。

删除视图的标准语法为：

```sql
DROP VIEW <视图名> [CASCADE | RESTRICT];
```

系统默认采用 `RESTRICT` 限制性删除策略。当某个视图被其他视图依赖时，删除行为会有明确限制：
- 例如我们先建立了 `IS_S1` 视图，紧接着在其基础上建立了 `IS_S2` 视图；
- 此时若直接执行 `DROP VIEW IS_S1;`，由于默认是 `RESTRICT`，系统检测到下游存在依赖对象 `IS_S2`，便会明确拒绝执行删除；
- 如果确实需要连带删除所有下游派生视图，必须显式附加 `CASCADE` 级联删除参数：
  ```sql
  DROP VIEW IS_S1 CASCADE;
  ```
  执行后，`IS_S1` 以及依赖于它的 `IS_S2` 都会被系统一并从数据字典中清理。

### 视图的查询、更新与工程价值

#### 视图查询与视图消解机制

在用户视角下，查询视图与查询基本表完全没有任何区别，同样使用 `SELECT-FROM-WHERE`。系统在底层究竟是如何实现视图查询的？其核心机制被称为**视图消解法（View Resolution）**。

```text
+─────────────────────────────────────────────────────────────+
|  用户层查询:                                                |
|  SELECT Sno, Sage FROM IS_Student WHERE Sage < 20;          |
+──────────────────────────────┬──────────────────────────────+
                               │
                               ▼ 视图消解引擎 (View Resolution)
+─────────────────────────────────────────────────────────────+
|  数据字典视图定义:                                          |
|  CREATE VIEW IS_Student AS                                  |
|  SELECT Sno, Sname, Sage FROM Student WHERE Sdept = 'IS';   |
+──────────────────────────────┬──────────────────────────────+
                               │
                               ▼ 语义重写与条件合并
+─────────────────────────────────────────────────────────────+
|  最终在物理基本表上执行的真实查询:                         |
|  SELECT Sno, Sage                                           |
|  FROM Student                                               |
|  WHERE Sdept = 'IS' AND Sage < 20;                          |
+─────────────────────────────────────────────────────────────+
```
上图直观展示了用户针对视图发起的查询，被系统内部消解引擎重写合并为对物理基表的直接查询全过程。

例如，当用户在 `IS_Student` 视图上查询年龄小于 20 岁的学生时，执行语句为：

```sql
SELECT Sno, Sage
FROM IS_Student
WHERE Sage < 20;
```

系统接收到指令后，会自动调取该视图在数据字典中的定义，发现其基表是 `Student` 且带有条件 `Sdept = 'IS'`。于是消解引擎自动将二者合并，直接转化为对底层 `Student` 表的执行计划：

```sql
SELECT Sno, Sage
FROM Student
WHERE Sdept = 'IS' AND Sage < 20;
```

用户无需关心这个转换细节，系统全自动完成。但理解视图消解有助于我们理解某些带聚集函数视图的查询限制。例如在前面定义的包含平均成绩的视图 `S_G(Sno, Gavg)` 上查询平均成绩大于等于 90 分的学生，消解后实际上是将条件转化到底层基表 `SC` 上的 `GROUP BY Sno HAVING AVG(Grade) >= 90` 执行。

#### 视图更新准则与不可更新边界

对视图执行 `INSERT`、`UPDATE`、`DELETE` 时，其语法形式与基本表完全一致，系统同样是在底层通过映射转换去修改物理基本表的数据。

但必须特别注意：**并非所有视图都支持更新操作**！

> **结论**：
> - **基本行列子集视图**：可以进行数据的插入、修改与删除。因为它们是从单个基表导出且保留了主码，视图中的每一行与底层物理基表中的每一行存在严格的一对一对应关系；
> - **经过运算、聚集函数或多表连接派生出的视图**：**绝对不要更新，系统也通常会严格禁止更新**。

我们可以用一个形象的现实场景来理解这个限制：这就好比一位同学觉得自己的期末加权平均绩点不够高，他跑到教务处打印出一张成绩单，拿笔在最后的“平均绩点”一栏把 3.0 直接改成了 3.8。这现实吗？当然不可能。因为平均绩点是他选修的几十门具体课程成绩经过加权公式综合运算出来的结果。你只改了一个最终计算值，系统根本无法推断这几十门课程分别应该如何增加分数来倒推凑出这个 3.8。

在数据库中亦是如此。对于包含了 `AVG(Grade)` 的 `S_G` 视图，如果你执行 `UPDATE S_G SET Gavg = 95 WHERE Sno = '1';`，底层涉及该学生多门具体科目的分数分配，数学上无法逆向求解，系统只能拒绝该更新操作。对于这类经过运算汇总出来的视图数据，如果确实需要变动，唯一的解决途径就是修改物理基表的底层源数据，或者销毁重构视图。

#### 视图在系统架构中的五大核心作用

视图在数据库系统设计中被广泛应用，主要承载着以下五项不可替代的核心价值：

1. **极大简化用户操作**：复杂的连接、嵌套和聚集统计可以预先封装在视图中。业务端（如教务处报表）只需简单地 `SELECT * FROM 视图` 即可，底层繁杂的数据关联全部被隐藏；
2. **支持以多维度、多视角审视同一份数据**：同一个 `Student` 基本表，学生处看学籍信息视图，后勤处看住宿信息视图，各业务方拥有最符合自身视角的专属视图；
3. **为重构数据库提供一定程度的逻辑数据独立性**：当底层物理基本表因性能优化被拆分或重构时（例如将一张宽表纵向拆分为两张子表），我们可以通过建立一个原表结构的视图对外部业务保持兼容，使得上层应用程序无需修改任何代码；
4. **对机密敏感数据提供天然的安全隔离防护**：在集成多部门数据的总表中，针对不同权限的角色建立过滤性视图。例如向教务管理人员只暴露包含学号、姓名、成绩的视图，而将底层的家庭收入、身份证号、财务缴费等私密字段屏蔽，防止敏感数据泄露；
5. **清晰表达高阶复杂查询**：面对层层嵌套的复杂业务逻辑，将中间阶段的处理结果抽象为视图，再在视图上进行最终查询，能够让整体 SQL 架构条理分明、极易维护。

至此，SQL 的数据操作（增、删、改、查、空值处理）与视图机制全部闭环。在三、四、五章的知识架构中，第三章解决了数据定义与数据操作，后续的第四章与第五章将接续深入讲解数据控制语言（DCL）中如何用 SQL 代码精准控制数据库的安全性与完整性。

### 本讲提到的题目

#### 题目一：数据清空与模式销毁的本质区别

**题干描述**：  
在关系数据库中，执行 `DELETE FROM SC;` 与执行 `DROP TABLE SC;` 都能让表内的数据消失。这两条语句在执行原理与系统影响上有何本质区别？

**解析依据**：  
从 SQL 语言的模块归属与底层对象来看：
1. `DELETE FROM SC;` 属于数据操作语言（DML）。它的操作目标仅仅是表中的**数据元组**。执行后，表内的所有数据记录被清空，但该表的模式（Schema）定义、列定义、主外码约束、默认值以及索引在系统数据字典中完好无损。表依然存在，后续可以立即继续执行 `INSERT` 录入新记录；
2. `DROP TABLE SC;` 属于数据定义语言（DDL）。它的操作目标是**表对象本身及其元数据**。执行后，不仅表内的全部数据瞬间销毁，该表在系统数据字典中的一切定义与关联索引也被彻底抹除。执行后再发起任何针对 `SC` 表的访问，系统都会报错提示表不存在。

**参考答案**：  
`DELETE FROM SC;` 是 DML 语句，仅清除表中的全部数据行，保留表结构与元数据定义；`DROP TABLE SC;` 是 DDL 语句，不仅清空数据，还将表结构及其在数据字典中的全部定义彻底销毁。

#### 题目二：含空值条件下的不及格学生查询改写

**题干描述**：  
在学生选课表 `SC(Sno, Cno, Grade)` 中，若要查询选修了 1 号课程且成绩不及格的所有学生学号（业务上要求将选课后缺考或未录入成绩、即成绩为 NULL 的学生也一并视作不及格），若直接书写如下语句：
```sql
SELECT Sno FROM SC WHERE Cno = '1' AND Grade < 60;
```
该语句能否满足需求？若不能，请分析原因并给出两种正确的 SQL 书写方案。

**解析依据**：  
不能满足需求。在 SQL 三值逻辑体系中，空值（NULL）与任何具体数值进行比较运算的结果均为 `UNKNOWN`（未知）。当缺考学生的 `Grade` 为 `NULL` 时，`NULL < 60` 返回 `UNKNOWN`，`WHERE` 子句仅筛选判定结果严格为 `TRUE` 的元组，因此包含空值的元组会被自动滤除，导致结果遗漏。

**参考答案**：  
该查询无法完整满足需求，会遗漏缺考或未录入成绩的学生。正确改写方案如下：

方案一（使用复合条件并显式加入空值谓词）：
```sql
SELECT Sno
FROM SC
WHERE Cno = '1' AND (Grade < 60 OR Grade IS NULL);
```

方案二（利用集合并集操作 UNION 合并结果集）：
```sql
SELECT Sno FROM SC WHERE Cno = '1' AND Grade < 60
UNION
SELECT Sno FROM SC WHERE Cno = '1' AND Grade IS NULL;
```
