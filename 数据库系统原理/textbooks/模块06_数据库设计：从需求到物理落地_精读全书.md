## 从需求到图纸：数据库设计与 E-R 图
> 对应块：BLK23 | 覆盖分集：P20 | 块标题（分集名）：《数据库第7章 数据库设计（第一部分：概念结构设计》

前五章讲的是数据库的概念、理论与方法，第六章讲关系数据理论，表头的有表头那一套——第一范式、第二范式、第三范式；没有表头的，也有 Armstrong 公理系统这样一套抽象办法。具体与抽象两条路都走通了以后，我们就获得了一项实实在在的技能：拿到几张表，能判断它们能不能直接拿来用。不能用就规范化，规范化到第三范式，通常可以把冗余压下去、把更新异常压下去，这时才轮到数据库管理系统登场，把这些没有问题的表真正实现为一个数据库。

所以，第七章不是再补一堆理论，而是把前面的一切接起来：从跟人聊需求开始，画出概念结构，拆出二维表，规范到第三范式，选择合适的物理实现，最后实施、维护。后面第八章讲数据库编程——怎样用 SQL，怎样把 SQL 嵌进高级语言里。到那时，从第一章的概述到第八章的编程，整条“数据库怎么做出来”的路才算走通。

这一章既是考试重点，也是毕业设计和工作里真正用得着的东西。只会连数据库还不够，将来自己做数据库，这些步骤都要会。

### 六个阶段，串起一次完整的数据库设计

数据库设计是对给定的应用环境构造优化的数据库逻辑模式和物理模式，并据此建立数据库及其应用系统，使之能有效存储、管理数据，满足应用需求。

跟人聊需求时，最少要弄清楚两类东西：

> **定义**：需求一般分为信息管理需求与对数据的操作要求。

信息管理需求说的是“数据库里存哪些东西”；操作要求说的是“这些数据要进行什么操作”，即增加、删除、修改、查询和统计。给教务处做教学数据库，就得问清楚：要不要存教师、课程、学生、考试？这些东西日常怎么增加、删除、修改、查询、统计？这两方面都清楚了，设计才有依据。

数据库设计还要为用户提供一个信息基础设施（Information Infrastructure），以及一个高效率的运行环境。高效率通常指存取效率高、空间利用率高、运行管理效率高，但这不是本讲的重点。

> **结论**：数据库设计的六个阶段依次是需求分析、概念结构设计、逻辑结构设计、物理结构设计、数据库实施、运行和维护。

#### 设计与实施之间的落差

这六个阶段构成一个标准过程，但每一步都可能发现问题。发现问题就回到前一步改，反复迭代，直到能落实为止。所以它是一张回得了头的路线图，不是一条只能向前走的流水线。

### 规范方法与手工试凑

数据库建设的基本规律是“三分技术、七分管理、十二分基础数据”。这里的管理部分不展开。单说技术与方法，数据库设计有一个很重要的特点：结构设计与行为设计必须紧密结合。

传统的软件工程重行为设计，关心程序怎么编、过程怎么走，尽可能推迟数据结构决策；早期数据库设计则重结构设计，致力于数据模型和建模方法，却忽视了行为对结构的影响。现实中的系统设计往往是结构与行为分离的：

- 功能这一端做功能分析，建立功能模型，解决应用怎么实现、开发怎么实现、调试怎么实现。
- 数据这一端做概念模型、事物设计和应用设计：功能要用到哪些数据、实现功能需要哪些表、表与磁盘之间怎样映射。
- 子模式与数据库的建立则是数据库管理系统的职责。

两者是分开的，又是统一的。

> **易错点**：要把概念结构设计与数据库的“三级模式”对应上。概念结构设计画的是 E-R 图，反映的是逻辑模式；逻辑设计阶段拆二维表、规范到第三范式；物理设计阶段建立索引等，形成内模式。后面概念设计那一节的 E-R 图，与这里说的逻辑模式，不是两回事，要分清。

实现上两类方法：手工试凑法与规范的设计方法。

手工试凑法中，设计质量直接与设计人员经验有关，缺乏科学理论支撑。系统跑一段时间后常常暴露各种问题，维护代价越滚越大。规范方法则有结构化过程，步骤明确、规程明确，数据库按这套方法设计出来。

这个道理在别的课也学过。信息系统开发有结构化生命周期法，也讲按部就班做系统分析、详细设计、系统实现。规范方法适合新手程序员、大公司、大项目；小公司或小型软件若照搬这套流程，像把事办大了，有点浪费时间。手工试凑法适合老程序员——对方提需求，脑子里已经大致知道：大概几张表、哪几个主码、怎样连接、哪里可能出问题，直接上手敲。原型法也可以用来迭代。

所以两类方法对不同的人有不同适配性，但“适合老成手儿”不等于“适合我们考”。

> **易错点**：考试几乎不会考手工试凑法——没有分点可给。命题老师出题要写评分标准，什么地方给几分？真正会考的是规范方法里面的典型方法：基于 E-R 模型的数据库设计方法、基于三范式的数据库设计方法；新奥尔良方法、面向对象的数据库设计方法、UML 方法也要知道。本科阶段重点清楚：会画 E-R 图，会拆表并做关系规范化。

### 各级模式与数据独立性

数据库设计不同阶段会形成数据库的各级模式。E-R 图的概念结构设计对应的是概念模式，这里还有内模式与外模式，以及模式到内模式、模式到外模式的两次映像。

```text
        外模式（应用看到的局部数据视图）
              ↕  外模式／模式映像
        概念模式（全局逻辑结构，E-R 图所在的层）
              ↕  模式／内模式映像
        内模式（磁盘扇区上的物理存储结构）
```

> **结论**：三级模式与两级映像，区分了物理独立性、逻辑独立性与数据独立性。

各层分工明确。外模式由应用程序开发者负责，比如微博、抖音的团队只管自己的应用程序，后端调用 SQL Server 还是 KingbaseDB、DB2，他们不必操心；概念模式由数据库管理系统公司提供接口；内模式关心磁盘扇区上的物理结构，是硬件厂商与操作系统的职责。外模式与概念模式之间、概念模式与内模式之间，只留映射关系；哪一层动了，只改映射，不用牵动别的层。

### 需求分析：把想法落成需求说明

需求分析是数据库设计的起点，任务是给概念结构设计提供素材。能不能准确反映用户的实际需求，直接影响后面所有阶段。

任务有四条：详细调查现实世界要处理的对象；充分了解原有系统；明确用户各种需求；在此基础上确定新系统的功能。

调查重点是数据和处理，也就是我们说的信息要求与对数据的处理要求。除此之外还有一项补充——安全性和完整性要求。学号范围多长、年龄取值在哪个区间、性别可选哪些值，都得在聊天中聊清楚。

方法上，调查清楚用户的实际需求，进行初步分析，达成共识。步骤是：调查情况、了解业务活动、明确用户需求、确定系统边界。需求分析阶段做这些工作的正是数据库分析设计人员。调研方法包括跟班作业、开调查会、专人介绍、询问等；分析方法叫结构化分析（Structured Analysis，SA），从系统最上层的组织机构入手，自顶向下逐层分解系统；实现上则是自底向上。写出来的成果叫需求说明，需要逐字段定义的内容用数据字典说明。需求说明和数据字典一起，就是概念结构设计的素材。

> **提示**：需求分析不是泛泛的“谈需求”。跟教务处老师聊出来的内容，要整理成类似一页 Word 文档的需求说明；它不是最终交付给用户的完整报告，但要把需求写清楚，给下一个阶段用。

### 数据字典：图纸旁边的注释

数据字典（Data Dictionary，DD）是数据的描述。图已经画了，别人看到 `student` 表里的 `Sdept`，总不能每次都来问“这是什么”。你要把注释写出来，这注释就是数据字典。

```text
数据项：Snumber
  含义：学生学号
  类型与长度：字符型，按需求确定
  取值范围：按需求确定
  存储长度：给出所需字节数

数据结构：Student
  含义：学生信息
  组成：Snumber、Sname、Sgender、Sbirth、Sdept、Senrollment
```

数据字典可以包含数据项、数据结构、数据流、存储、处理过程。数据项是数据流中不可再分的数据单位。数据结构的描述包括名字、含义说明、组成的数据项及数据类型。数据流描述来源、去向、平均流量和高峰期流量等。数据存储说明存取频度、存取方法、输入与输出。处理过程也有对应描述。

> **易错点**：数据字典不是随便写两段话，而是一套结构化描述。它要能回答“某字段是什么、什么类型、怎么存、从哪来到哪去”。毕业设计里可以把数据字典尽可能详细地写出来，这既真实反映了工作量，也方便答辩时说明设计细节。

系统开发里也有数据字典，作用相同。数据库课里的数据字典描述表及表之间的结构，数据流相关的部分则更多对应业务流程图和数据流程图里的字段。

### 概念结构设计：把现实世界画成图

概念结构设计，是把需求分析得到的材料抽象为信息结构的过程。说白了：需求分析给你的是一页纸，你拿它来画图纸。盖楼要有楼房的图纸，数据精确到哪儿、用什么线表示什么、什么图形表示什么材质，全行业通用；数据库也有全行业通用的工具，这就是 E-R 图（Entity Relationship Diagram）。

概念结构设计的特点是真实反映现实世界、易于理解、易于更改。它的意义也在于此：没有标准图形，画出来的东西别人看不懂，后面也没法据此拆表。

到这里/database设计也才真正进入核心考点。前面的需求分析、概念结构设计是“为什么画这张图”，逻辑结构设计才是“怎么从图上拆出表”。考核形式也集中在这里：卷面上给一段需求背景，第一个问是“请设计概念结构”，用 E-R 图画出来；第二个问是“请设计数据库的逻辑结构”，把 E-R 图拆成二维表、标注主码与外码，并规范化到第三范式。概念结构与逻辑结构合计 15～20 分。后面“敲进数据库管理软件”属于有手就会的部分。

> **结论**：E-R 图是概念结构设计使用的标准工具。考 E-R 图、考概念结构设计、考逻辑结构设计，是同一个问题的不同深度。

不过，概念结构设计怎么画、怎么合并、怎么练习，要单独开一次课细讲。这里先把概念模型的来历、ER 图的基本形状讲清楚。

到这里，数据库设计包含哪些阶段、哪些阶段重要，已经明确；需求分析怎么做、概念结构设计是什么、ER 图长什么样，到此为止。

### 现实世界的三个东西

现实世界里有什么？E、A、R 三个字母。E 是 Entity，实体；A 是 Attribute，属性；R 不是 relation——relation 是表，是关系；是 Relationship，联系。

```text
现实世界：  实体（方块）  ——  联系（菱形）  ——  实体（方块）
                        │
                        │ 无向边
                        ▼
                  属性（椭圆）
```

ER 图就是把现实世界翻译到纸面上的语言。现实世界有什么，图上就画什么。需求分析文字里找实体、属性、联系，再用相应图形把它们画出来，事情就算完。

在业务流程图和数据流程图里找核心字段，道理一样。设计信息系统时先了解企业业务，画业务流程图表示一个业务的完整流转过程；业务过程会产生数据流动，用 DFD（data flow diagram，数据流程图）表示系统内部数据的流动。业务流程图、DFD、ER 图是本专业学生到目前为止应该掌握的三套图，三者在毕业设计的卷子上都是要的。到这里，行业的手里的图纸就有了三套。

### 实体、属性、联系的标准图形

#### 三个基本图形

实体用矩形表示，矩形里写实体名。属性用椭圆表示，并用无向边把它与实体相连。联系用菱形表示，菱形里写联系名，连接实体与实体。

```text
        (Snumber)             (Sname)
             \                  /
              \                /
              [ Student ]  学生
              [ 学生   ]
                  |
                 / \
            (Sgender) (Sdept)
```

> **易错点**：联系只能连接实体，不能连接属性。联系是实体与实体之间的联系。

实体和实体之间的联系通常有三种：一对一、一对多、多对多。联系是菱形，用“肩膀”上的数字表示：一对一写 1:1，一对多写 1:n，多对多写 m:n。

> **结论**：画联系时，行业习惯用 1、n、m 这套符号，不要自创。你画的东西要交给甲方看、给程序员看、给同行看，不是只给自己看。

#### 联系也可以有属性

这句话很重要。属性有的是跟着实体的，有的是跟着联系的。千万不要把属性默认都挂到实体身上。

学生表 Student 有学号、姓名、性别、出生年份、所在系、入学时间六列。把它当成表看，是学生表有六列；把它画成图看，就是学生实体带六个属性。画实体属性图时，这六列都挂到学生实体上，这很清楚。

但联系属性怎么办？拿工厂物资管理的例子说。仓库、零件、供应商、项目、职工是五个实体，各自有一批属性。仓库和零件的关系要分开看：仓库可以放多个零件，零件也可以存放在多个仓库，两个方向合起来才是完整关系——多对多。联系上还有“库存量”这个属性，它描述的是某个仓库里某个零件的库存，不是仓库自身的属性。供应商、项目、零件三者之间是多对多联系，供应量则是挂在供应联系上的属性。

```text
仓库  ──库存量──  零件        库存量属于“库存”联系
    ╲
     ╲供应量
供应商 ──供应── 项目 ──使用── 零件   供应量属于“供应”联系
```

所以画图时先画实体，再画联系，最后画属性。归实体的椭圆挂到实体上，归联系的椭圆挂到联系上。把属性放最后，是为了分配时心中有数。最容易出的错就是漏掉联系的属性。

> **易错点**：画 E-R 图时，顺序必须是：实体 → 联系 → 属性。先画属性往往会产生偏差，因为还没定联系挂在谁身上。

#### 二元、三元与 n 元联系

三个实体之间的联系叫三元联系，多个实体之间的联系叫 n 元联系。

课程、老师、参考书就是一个三元联系的例子。数据库这门课有四五个老师讲，课程与老师是一对多；不同的老师可能用不同的参考书，课程与参考书也是一对多；多个老师可能使用多个参考书，老师与参考书是多对多。

供应商、项目、零件则是一组经典的三元多对多联系：一个供应商供多个项目的零件，一个项目用多个供应商的零件；一个零件有多个供应商，一个供应商供多个零件；一个项目有多个零件，一个零件被多个项目使用。

还有一种情况是实体自己与自己产生联系。职工里选一个当领导，这个领导也是职工群体里的人。职工与职工领导之间是一对多：一个职工领导负责几个职工。一个班的班长也是班里的人。联系不一定要两个不同实体。

#### 分开画还是一张图画完

教材里工厂物资管理的例子，分两张图：一张是实体属性图，画仓库、职工、零件、供应商、项目及各自的属性；另一张是实体联系图，画它们之间的一对多、多对多、三元多对多关系，以及供应量、库存量两个联系属性。两张图合并起来，才是完整的 E-R 图。

```text
    实体属性图                        实体联系图
┌──────────────────┐            ┌────────────────────┐
│ (仓库属性)─[仓库] │            │ [仓库]─1:n─[零件]  │
│ (职工属性)─[职工] │            │ [供应商]─m:n─[项目] │
│ (零件属性)─[零件] │            │ [职工]─1:n─[职工领导]│
│ (供应商属性)[供应]│            │ [供应商]─供应─[项目]│
│ (项目属性)─[项目] │            │      供应量         │
└──────────────────┘            └────────────────────┘
              └──────── 合并 ────────┘
                         ↓
                  完整 E-R 图
```

分开画图不是强制要求，只是图大时方便：一次从左到右画不完，就先画实体和属性，再画实体和联系，最后合并。像学生、课程、SC 选课这种简单的，直接一张纸画完就行，不必拆成两步。

> **提示**：判断要不要分开画的标准很简单——图大到一张纸难以布置就分开，图简单就直接画。分步画是方法，不是规矩。

### 本讲提到的题目

讲师把上课用的教学数据库给学生、课程、选课三张表，试着把三张表还原成 E-R 图。

表的字段是：

- 学生表 Student：Snumber、Sname、Sage、Sdept、性别。
- 课程表 Course：Cnumber、Cname、CPnumber（先修课）、Ccredit。
- 选课表 SC：Snumber、Cnumber、Grade。

要求画出教学数据库的 E-R 图。

**解析**：

学生、课程是两个实体，SC 是联系表。把 SC 的外码（Snumber、Cnumber）作为联系“选修”的属性，把 Sdept、Sage 作为学生的属性，把 CPnumber、Ccredit 作为课程的属性。

> **提示**：下一节将继续讲具体的画法，这里只指出：SC 在 E-R 图上是“联系”，不是一个独立的实体——这是理解 ER 图与关系模式对应关系的关键铺垫。

> **承前启后**：上一节讲完「从需求到图纸：数据库设计与 E-R 图」，下一节接着讲「ER 图与关系模式的转换」。

## ER 图与关系模式的转换
> 对应块：BLK24 | 覆盖分集：P21 | 块标题（分集名）：《数据库第7章 数据库设计（第二部分：逻辑结构设计》

需求分析做完之后，我们手里有需求说明书；概念结构设计做完之后，需求又被画成了 E-R 图。到了这里，设计人员才算真正有了一张“图纸”。

接下来要做的事很直白：拿着图纸，把 E-R 图拆成一批二维表，再把这些二维表规范好、连接好。这就是数据库设计中的逻辑结构设计。可以把它想成盖房子——E-R 图是图纸，二维表就是按照图纸划分出来的房间，主码、外码和表之间的联系则是让整栋房子能运转起来的结构。

> **结论**：E-R 图与关系模式的转换，是逻辑结构设计中最重要、也最容易出错的一步。考试常见的大题往往分成两问：第一问画 E-R 图，第二问拆表。

---

### 从 E-R 图到二维表，先把三件事想清楚

逻辑结构设计不是只做“拆表”一个动作，而是三个连续步骤。

第一步，把基本 E-R 图转换为二维表，也就是转换为关系模式。

第二步，对拆出来的表进行规范化处理，依据关系数据理论检查 1NF、2NF、3NF 等范式要求，排除不必要的数据冗余与增删改异常。

第三步，设计用户的子模式，把各张表的主码、外码标出来，建立应有的联系，并根据用户需要提供视图、别名等访问方式。

这里的关键难点，不是实体怎么变成表，而是**联系怎么变成表**。每拆出一张表，都必须回答两个问题：

- 这张表长什么样，包含哪些属性列？
- 这张表的主码是谁？

这两个问题分别决定了表的具体结构，以及后续如何连接、如何判断数据是否重复。主码尤其不能忘：它不仅是一列属性，还承担着识别元组、连接其他表的作用。

> **提示**：记不清某个表的主码时，不要死背结论。最稳妥的办法是脑补几行数据，看哪一列单独取值不重复；或者看哪几列合起来才不重复。

---

### 实体拆表：属性直接变成列

E-R 图中的实体是最容易处理的部分，可以直接按“无脑拆表”的思路处理。

例如，E-R 图里有一个 `Student`（学生）实体，旁边连着学号、姓名、年级、年龄、所在系五个属性，那么可以直接转换为同名关系模式：

```text
Student（学号，姓名，年龄，年级，所在系）
```

转换规则很简单：

- 实体变成关系模式，通常以实体名作为关系名；
- 实体的属性变成关系模式中的属性列；
- 实体的码变成相应关系模式的主码。

所以，当 E-R 图中有一个矩形实体、几个椭圆属性时，拆表就是把这个矩形搬成一张表，再把几个椭圆搬成几列。一个实体有几个属性，表里就有几个对应的属性列；哪个属性是这个实体的码，它就成为表的主码。

> **易错点**：拆实体时，不要只搬属性而忘记确定主码。每张表都要同时考虑“表长什么样”和“谁是主码”。

到这里，实体转关系模式几乎没有压力。真正的难点在联系。

---

### 联系拆表：永远看两个问题

联系有三种基数情况：一对一、一对多、多对多。不同联系类型，拆表的列和主码选择不同。

不过，在讨论具体规则之前，先记住联系转换时始终要看的两条线索：

- 如果把联系单独拆成表，联系表应该包含什么属性？
- 如果不单独拆表，而是合并到某一端实体表中，应该往哪张表里加入什么属性？
- 如果真的拆成表，谁是它的主码？

联系是连接实体的桥梁。如果联系单独成为一张表，仅有联系自身的属性往往不够，还必须把两端实体的主码引入联系表。否则，联系表就无法说明“哪一个实体和哪一个实体发生了联系”。

两端主码进来以后，主码的选择与联系的基数直接相关：

- 一对一联系：两端主码都可以作为该关系的主码，任选其一即可。
- 一对多联系：取多端实体的主码作为关系主码。
- 多对多联系：两端主码联合起来，构成复合主码。

> **结论**：一对多取多端，多对多取两端联合主码。记不住时，用“脑补五行数据”的办法判断。

---

### 一对一联系：可拆，也可合并

以“班级—管理—班主任”为例，一个班主任管理一个班级，或者一个班级配一个班主任，这就是一对一联系。

假设班级的主码是班级号，班主任的主码是工号，联系自身的属性有“评价”。

#### 联系单独拆成表

可以把“管理”单独转换为一张关系模式：

```text
管理（班级号，班主任工号，评价）
```

这张表的列包括：

- 左端实体“班级”的主码：班级号；
- 右端实体“班主任”的主码：班主任工号；
- 联系自身的属性：评价。

联系自身没有属性时，就只有两端主码两列。如果有“评价”一类的联系属性，则把它作为一列加入表中。

主码选择方面，一对一的联系表中，两端主码取值都不会重复，任取一端主码作为主码都可以。

```text
┌────────────┬──────────────┬────────────┐
│   班级号   │  班主任工号  │    评价    │
├────────────┼──────────────┼────────────┤
│  1         │  101         │  很负责    │
│  2         │  102         │  很认真    │
│  3         │  103         │  一般      │
└────────────┴──────────────┴────────────┘
```

编号不同的班级与编号不同的班主任一一对应；不管看班级号这一列，还是看班主任工号这一列，都不会重复。因此两端码都可以独立识别表中的一行。

也可以脑补数据来判断主码：

```text
┌────────────┬──────────────┐
│   班级号   │  班主任工号  │
├────────────┼──────────────┤
│  1         │  101         │
│  2         │  102         │
│  3         │  103         │
└────────────┴──────────────┘
```

任意一列都不重复，所以选哪一列作主码都对。

#### 联系不拆表：合并到任意一端

一对一联系也可以不单独拆表，而是把它合并到任意一端对应的关系模式中。

以班级表为例，假设原来班级表已经有班级号、班级名等属性。把管理关系合并到班级表后，在班级表后面加上班主任工号，如果联系自身还有评价，就把评价属性也加进去。

```text
班级（班级号，班级名，班主任工号，评价）
```

此时：

- 班级表的原主码仍然是班级号；
- 班主任工号作为外码，引用班主任表；
- 评价是联系的属性，也并入班级表。

如果把管理关系合并到班主任表，也同样成立：向班主任表加入班级号和评价属性，班主任表原来的主码不变。

因此，一对一联系有两种合法处理方式：

```text
方式一：单独拆表
管理（班级号，班主任工号，评价）
主码：班级号或班主任工号，任选其一

方式二：合并到一端
班级（班级号，班级名，班主任工号，评价）
主码：班级号

或
班主任（班主任工号，姓名，班级号，评价）
主码：班主任工号
```

> **结论**：一对一联系“可拆可不拆”。单独拆出联系表时，两端主码都进入联系表；合并时，联系表消失，只把另一端的主码和联系自身属性加入被合并的实体表。

---

### 一对多联系：也可以拆，也可以合并

假设一个班主任管理多个班级。此时班主任是“1”端，班级是“多”端，构成一对多联系。

#### 单独拆成关系模式

联系仍然可以单独转换为一张表：

```text
管理（班级号，班主任工号，评价）
```

表结构不变，依然包含两端实体的主码和联系自身的属性。

但是主码选择发生了变化。教材规定：在一对多联系转换得到的关系模式中，取“多”端实体的主码作为主码。

本例中，班主任端是“1”端，班级端是“多”端，因此班级号作为联系表的主码。

```text
┌────────────┬──────────────┬────────────┐
│   班级号   │  班主任工号  │    评价    │
├────────────┼──────────────┼────────────┤
│  1         │  101         │  很负责    │
│  2         │  101         │  很认真    │
│  3         │  102         │  一般      │
│  4         │  102         │  很好      │
└────────────┴──────────────┴────────────┘
```

班主任工号这一列会出现重复，因为一个班主任管理多个班级。班级号这一列没有重复，因此班级号才是联系表的主码。

> **定义**：外码指一个关系模式中的属性或属性组，引用另一个关系模式的主码，用于建立两个关系模式之间的联系。在“管理（班级号，班主任工号）”中，班主任工号就是外码，引用班主任表的主码。

这就是为什么一对多联系要取“多”端做主码。一个班主任可以管理多个班级，而“班主任工号”无法单独区分多个班级；“班级号”却能唯一标识一个班级，因此以班级号为主码，班主任工号作为外码指向班主任表。

#### 合并到多端实体表

如果不单独拆表，就把“一”端实体的主码和联系自身的属性加入“多”端实体表中。

向班级表中加入班主任工号和评价后，班级表变成：

```text
班级（班级号，班级名，班主任工号，评价）
```

其中：

- 班级号是主码；
- 班主任工号是外码；
- 评价是联系自身的属性。

这样，班级表中的一行就表达“一个班级由哪个班主任管理，以及这个管理联系的评价是什么”。

所以，一对多联系同样有两种合法方案：

```text
拆表：
管理（班级号，班主任工号，评价）
主码：班级号

合并：
班级（班级号，班级名，班主任工号，评价）
主码：班级号
```

> **结论**：一对多联系“可拆可不拆”。无论拆表还是合并，主码都取多端实体的主码。

---

### 多对多联系：必须拆成独立关系

假设一个班级有多个班主任，这就是多对多联系。多对多联系不能简单地合并到任何一端，必须转换为独立的关系模式。

多对多联系表的结构同样是：

```text
管理（班级号，班主任工号，评价）
```

把两端实体的主码都放进来，再加上联系自身的属性。

关键在主码：多对多联系中，两端主码单独看都会重复，不能任选一端作为主码，必须把两端主码放在一起，构成复合主码。

```text
┌────────────┬──────────────┬────────────┐
│   班级号   │  班主任工号  │    评价    │
├────────────┼──────────────┼────────────┤
│  1         │  101         │  很负责    │
│  1         │  102         │  很认真    │
│  2         │  101         │  一般      │
│  2         │  102         │  很好      │
└────────────┴──────────────┴────────────┘
```

单独看班级号，1 和 2 都有重复；单独看班主任工号，101 和 102 也有重复。只有把两个列结合在一起，表格中每一行才唯一。

所以，多对多联系表的主码是：

```text
主码：（班级号，班主任工号）
```

> **易错点**：多对多联系不是“选一个主码”，而是“两端主码联合做主码”。在关系模式表示法中，这两个主码列下方都要画下划线，表示它们共同构成复合主码。

---

### 多元多对多联系：各方主码联合

三元及以上的多元多对多联系，同样必须拆成独立关系表。

假设“部门—供应—供货商”构成三元多对多联系，那么该联系表包含：

- 部门主码；
- 职工或参与实体的相应主码；
- 产品主码；
- 零件主码；
- 供货商主码；
- 联系自身的属性，如供应量。

按本例来说，供应关系涉及供货商、产品和零件三方，属于三元多对多联系。拆表时，把供货商主码、产品主码、零件主码都取出来，再加上“供应量”这一联系自身属性，得到：

```text
供应（供货商号，产品号，零件号，供应量）
```

此时，这三端的主码必须联合起来构成复合主码：

```text
主码：（供货商号，产品号，零件号）
```

规则与多对多完全相同：**各方主码全部进入联系表，联合构成共同主码；联系自身属性也作为列加入。**

---

### 考试场景下的最稳妥策略

把各种情况合并起来，可以得到一个非常好用的答题策略。

> **结论**：考试时如果拿不准某个联系怎么拆，直接拆成独立关系表，几乎不会错。考试阶段不必优先考虑系统效率，拆表数量多一点只是“墨迹”，不会因此被判错。

具体做法是：

- 实体直接拆表；
- 实体属性直接变成表的列；
- 联系一律拆成独立表；
- 联系表包含两端实体的主码；
- 如果联系自身有属性，再加入联系表；
- 主码按基数确定：一对一任选一端，一对多取多端，多对多取两端联合主码。

如果主码搞不清楚，就脑补数据，最多补五行，通常就能判断出哪一列单独不重复、哪几列合起来才唯一。

> **定义**：复合主码是指由两个或两个以上属性共同构成的主码，单独任何一列都不能唯一标识一行，必须将多列组合起来才能唯一标识一个元组。

例如，一对多中，班主任工号会重复而班级号不重复，所以班级号单独做主码；多对多中，班级号和班主任工号都重复，组合起来才不重复，所以二者共同构成复合主码。

所以，在考试情境下，把 E-R 图拆成二维表时，完全可以遵循一个简单原则：

```text
实体：直接转
联系：一律转
两端主码：全部纳入联系表
联系属性：有就加
主码：看基数确定
```

这个策略的核心是“**宁拆勿合**”：先把逻辑结构拆对，再考虑系统效率。

---

### 实际工作中：能不拆就不拆

考试追求的是答题稳妥，而实际工作追求的是系统效率。这两者的取舍方向不同。

如果面对一个联系，拆成独立表和不拆表都能表达同样的业务关系，那么在系统设计中应尽量合并到已有实体表中，避免无谓地增加表数量和连接操作。

因此，工作中的原则是：

```text
一对一联系：合并到一端
一对多联系：合并到多端
多对多联系：必须拆表
```

具体来说：

- 一对一联系合并到任意一端都可；
- 一对多联系合并到多端；
- 多对多联系必须拆成独立关系模式。

这种选择能减少不必要的表和连接，提升系统效率。反过来，如果一律拆表，虽然逻辑上正确，但可能会产生数据冗余或增加连接操作，影响实际系统性能。

> **提示**：考试时建议“见联系就拆表”，工作时要根据系统效率“能不拆就不拆”。两种场景下的考量不同，但底层规则是一致的。

#### 一个完整 ER 图的拆法

现在看一个包含部门、职工、产品、零件和供货商的 E-R 图。为了突出表结构，先忽略实体自身的属性，只分析实体之间的联系。

这个 E-R 图中有 5 个实体：

```text
部门、职工、产品、零件、供货商
```

它包含 5 个联系：

```text
领导、属于、参加、负责、供应
```

##### 按考试策略拆表：十个表

如果完全按照“考试时无脑拆表”的策略，5 个实体先拆出 5 张表，5 个联系再拆出 5 张表，总共 10 张表。

```text
实体表：
1. 部门
2. 职工
3. 产品
4. 零件
5. 供货商

联系表：
6. 领导（部门主码，职工主码，联系属性）
7. 属于（部门主码，职工主码，联系属性）
8. 参加（职工主码，产品主码，天数）
9. 负责（职工主码，产品主码，联系属性）
10. 供应（供货商主码，产品主码，零件主码，供应量）
```

逐项分析这些联系表：

- “领导”是一对一联系。两端主码取自部门表和职工表，如果联系自身有属性也加入联系表。一对一联系中，任选一端主码作为主码。
- “属于”是部门与职工的一对多联系。两端主码都进入联系表；属于关系如果自身有属性，也一并加入；主码取多端，也就是职工编号。
- “参加”是职工与产品的多对多联系，而且联系自身有“天数”属性。联系表包含职工主码、产品主码和天数；主码是两端主码联合，即（职工编号，产品编号）。
- “负责”是职工与产品的一对一联系。联系表包含职工编号和产品编号；一对一，任选一端作为主码。
- “供应”是供货商、产品、零件之间的三元多对多联系。联系表包含供货商主码、产品主码、零件主码和供应量；主码是三个主码联合。

所以，按考试策略，5 个实体表加 5 个联系表，一共 10 张表，不会错。

> **易错点**：在考试中，多拆几张联系表不会因为“系统效率低”被扣分。多拆不一定最优，但逻辑上合法。不要因为担心表太多而放弃拆联系表。

##### 按工作策略拆表：七个表

实际工作中，实体表肯定要拆，这 5 个实体没有争议：

```text
部门、职工、产品、零件、供货商
```

接下来逐个处理 5 个联系。

“领导”是一对一联系，不必单独拆表。可以在部门表中加入职工编号，也可以在职工表中加入部门编号，以此表示这种领导关系。

“属于”是部门与职工的一对多联系，也不单独拆表，将一端的主码加入多端表中：把部门编号加到职工表中，职工表仍以职工编号为主码。

“负责”是一对一联系，也不拆表。可以把职工编号加到产品表中，表示该产品由哪个职工负责；也可以将这两个联系的信息放到一起处理。

“参加”是一个多对多联系，而且联系自身有“天数”属性，因此必须单独拆表：

```text
参加（职工编号，产品编号，天数）
```

该表的主码为：

```text
（职工编号，产品编号）
```

“供应”是三元多对多联系，而且联系自身有“供应量”属性，也必须单独拆表：

```text
供应（供货商主码，产品主码，零件主码，供应量）
```

该表主码为：

```text
（供货商主码，产品主码，零件主码）
```

最终工作方案得到 **7 张表**：

```text
5 张实体表
+ 1 张“参加”联系表
+ 1 张“供应”联系表
= 7 张表
```

> **结论**：实际系统设计中，一对一、一对多联系尽量合并到已有实体表，只有多对多联系必须拆成独立表。三元多对多同样必须拆。

##### 两种方案对比

考试方案和工作方案的核心差异是：

| 联系类型 | 考试策略：统一拆表 | 工作策略：优先合并 |
| :--- | :--- | :--- |
| 一对一 | 单独建表，两端主码任选其一 | 合并到任意一端实体表 |
| 一对多 | 单独建表，取多端主码 | 合并到多端实体表 |
| 多对多 | 单独建表，两端主码联合 | 必须单独建表 |
| 三元多对多 | 单独建表，各方主码联合 | 必须单独建表 |

这就是本讲最值得记住的结论：

```text
学习和考试：无脑拆表
实际工作：能不拆就不拆
```

考试担心的是把联系表达错；工作更在意系统效率。因此，要掌握两种思路：逻辑上都正确，但选择哪一种，取决于当前场景。

---

### 拆表之后：让表真正规范化

E-R 图拆成二维表，只是逻辑结构设计的第一步。拆出来的表不一定能直接使用，还要经过关系数据理论的检验和处理。

#### 规范化处理的步骤

规范化处理可以这样理解：

1. 拆出 E-R 图中的实体和联系，形成一批关系模式；
2. 检查这些模式是否满足 1NF、2NF、3NF、BCNF 等范式要求；
3. 找出数据冗余以及可能出现的增删改异常；
4. 通过关系模式的分解，使关系模式规范化。

> **定义**：数据冗余是指同样的数据在系统中重复存储，浪费空间，并可能在更新时造成数据不一致。

> **定义**：增删改异常是指由于表结构设计不合理，在插入、删除或修改数据时需要执行额外操作，甚至无法保证数据一致性。

> **定义**：范式是关系模式满足某类数据依赖规则的程度。1NF、2NF、3NF、BCNF 依次是规范化理论中用于衡量关系模式规范程度的级别。

规范化程度越高，冗余和异常通常越少，但并不意味着“越高越好”。实际设计中要根据具体需求，在以下几方面之间取得平衡：

- 系统响应效率；
- 数据冗余程度；
- 增删改异常；
- 实际应用需求。

前面第六章已经介绍过函数依赖、多值依赖以及 1NF、2NF、3NF、BCNF 的理论。逻辑结构设计阶段需要把这些规范再过一遍：把 E-R 图拆出来的一堆表逐张检查，必要时进行分解，以保证数据依赖合理，并尽可能减少冗余与增删改异常。

> **提示**：规范化不是为了追求一个漂亮的范式名称，而是为了解决实际问题。如果进一步规范化会显著降低系统效率，就需要结合实际需求权衡，而不是一味地追求高范式。

---

### 设计用户子模式

当关系模式通过规范化处理后，逻辑结构设计还要进入第三步——设计用户子模式。

子模式可以理解为从整个数据库中为不同用户提供的定制视图。它主要从以下角度考虑：

- 系统的时间效率；
- 系统的空间效率；
- 系统的易维护性；
- 用户的使用习惯；
- 不同用户群体的使用需求。

> **定义**：用户子模式是面向特定用户或用户群建立的数据库局部逻辑结构，主要用于简化用户对数据库的使用。

常见做法包括：

- 为属性或表使用符合用户习惯的别名；
- 针对不同级别的用户定义不同视图，以保证数据安全；
- 简化用户对数据库系统的操作；
- 屏蔽用户不需要看到的复杂表结构。

例如，底层表中有“职工编号”“职工姓名”“部门编号”等列，面向不同业务场景可以定义不同视图，让用户看到更符合业务名称的字段，并隐藏不必要的内部列。

当所有表都规整好、主码外码标清楚、用户需要的视图也设计完成后，就可以把最终逻辑结构录入数据库管理软件中——打开 Access、SQL Server，把表、约束、关系录入系统，逻辑结构设计阶段就算完成了。

> **结论**：逻辑结构设计的完整流程是：按 E-R 图拆表，按关系数据理论进行规范化处理，再设计用户子模式并把各表连接好。

## 从需求描述到可用的概念结构：ER 图的设计、合并与重构
> 对应块：BLK25 | 覆盖分集：P22 | 块标题（分集名）：《数据库第7章 数据库设计（第一部分：概念结构设计》

上节课我们把数据库设计的几个环节排过一遍：从需求分析出发，进入概念结构设计、逻辑结构设计和物理结构设计，最后才是数据库的运行与维护。

需求分析说白了，就是我们跟人聊，把聊出来的东西整理成一页纸。这一页纸里通常装着两类东西：某个人对信息有什么需求，以及对数据有什么需求。比如教务处的老师要了解学生、课程、成绩之间的关系，他提出的就是信息需求；他希望系统里保存哪些数据，就是数据需求。

有了这一页纸，接下来不是马上建表，而是先给数据库画一张“图纸”。这张图纸就是**概念结构设计**，而我们使用的标准画图工具，就是 **E-R 图**，也叫实体联系图、实体关系图。有人说 E-R 图，有人说 E-R 模型，也有人写 ERD，名字不同，指的是同一类东西。

上一节课我们已经看过它的基本样子。这一次要解决的，不是“方框、椭圆、菱形分别是什么”，而是真正画图时最容易犹豫的地方：什么东西该做实体，什么东西只配当属性；不同部门分别画出的局部 E-R 图，怎样合成一张真正可用的总体 E-R 图；合进来以后，哪些冲突必须处理，哪些冗余又没有必要硬删。

```text
需求分析
   │
   │ 得到关于信息与数据的需求描述
   ▼
概念结构设计
   │
   │ 把文字需求转成 E-R 图
   │ 识别实体 → 配置联系 → 分配属性
   ▼
逻辑结构设计
   │
   │ 将基本 E-R 图拆成相互联系的二维表
   ▼
物理结构设计与实现
```

> **定义**：概念结构设计，就是用实体、属性和联系把需求描述画成 E-R 图。E-R 图中的方框表示实体，椭圆表示属性，菱形表示联系；联系旁边标出联系的类型，也就是一对一、一对多或多对多。

所以，从需求分析到概念结构设计，最核心的动作就是一句话：**把文字变成 E-R 图。**

### 实体与属性的边界：能当属性，就别急着当实体

画 E-R 图的顺序很清楚：先把实体找出来，再给实体配联系，最后把属性分配到正确的位置。

有些属性天然跟着实体身上，比如“职工号、姓名、年龄”；有些属性则跟着联系走，比如前面提到的“工作量”。因此，不能一看到名词就立刻画成方框。实体和属性之间，藏着一条非常实用的判断原则。

> **结论**：现实世界中的事物，只要能够作为属性使用，就尽量作为属性，不要轻易升级成实体。

为什么一定要这样克制？因为每多画一个实体，往往就意味着多出一组联系，还可能多出一堆属性。图一复杂，表之间的联系就复杂；表一复杂，数据库维护时消耗的系统资源也会增加。E-R 图追求的是把问题表达清楚，不是让图看起来越“高级”越好。

判断时，下面几条必须同时守住。

> **定义**：属性是不能再具有需要进一步描述的性质的数据项。它应当是不可分的最小数据项，也不能脱离原来的实体，再与其他实体发生联系。

为什么说属性不能再被描述？比如把“职工号”画成一个属性已经可以了，但如果这个“职工号”本身还需要继续挂上一组属性，说明它并不是一个完整的终点，这时就该重新考虑对象边界。属性也不能偷偷承担联系：职工号属于职工，它就不能又跳出来跟另一个对象单独建立关系。

#### 当属性开始有“伙伴”，它就该独立出来

先看职工。职工是一个实体，职工号、姓名、年龄、职称都可以直接作为它的属性，职工跟仓库、部门之间需要什么联系，也直接在图上画联系。

但如果需求继续追问下去：不同职称有不同的工资、住房标准和附加福利，那么“职称”就不只是一个说明职工情况的普通属性了。它还有工资、住房标准、附加福利等一系列属性与它相连，而且这些描述明显比一句职称说明更值得独立管理。这时，我们就把职称从职工身上拿出来，单独做成一个实体，再把跟着它的那些属性一起带走。

这里可以记住一个很形象的判断：

> **提示**：谁跟你有关，谁就“复制自己”出来，把跟着自己的伙伴一起带走，变成独立的实体。

这个对象究竟叫属性还是实体，不能只看它的名字，更不能凭感觉。名字看起来很长，不一定就该是实体；名字很短，也不一定只能是属性。要看它在实际需求里还有没有自己的性质、自己的属性，以及会不会和别人发生独立联系。

#### 病房号为什么可能变成病房

再看病人。病人可以先做成实体，住院号、姓名和病房号作为它的属性，这完全可以。

可是，如果病房号后面还要跟医生发生联系——某个病房有哪些医生、某位医生负责哪些病房——病房就不能只作为一个编号贴在病人身上了。这时要把“病房”单独拿出来做实体，再将与病房有关的内容一起组织进去。

病房和职称看起来属于完全不同的业务，可背后的判断方法是同一个：一个要素自己待着，没有更多描述，就留在原地；一旦它有了自己的伙伴和独立关系，就把它连同相关属性一起带走。

#### 仓库号为什么可能变成仓库

第三个例子是货物。假设一件货物只放在一个仓库，那么“存放仓库号”可以作为货物属性：货物有货号、单价和存放仓库号。这样画已经足够，没必要凭空再增加一个仓库实体。

但如果需求变成“一件货物可以放在多个仓库”，同时仓库本身还有自己的属性，还和管理员发生联系，那么仓库就不能只被压成一个编号了。它应该成为独立实体，货物的存放关系也应当按新的事实重新组织。

> **易错点**：不能因为某个词像是“编号”，就永远把它钉死在属性位置；也不能因为它是一个对象名称，就永远把它画成实体。实体还是属性，最终由真实需求决定。

所以，没有“某个要素一定是实体”或“某个要素一定是属性”的统一答案。我们必须结合具体场景看：如果它不能再被描述、不能拆开、也不会离开原实体独立参与关系，就保留为属性；否则，就该考虑升格为实体。

### 从一段销售需求画出完整 ER 图

理解了实体与属性的边界，我们再看一个能把方法真正用起来的例子：销售管理子系统的 E-R 图。

这个大例子一方面帮助我们练习 E-R 图的画法，另一方面也确实接近大家以后做毕业设计时会碰到的场景。不管是图书馆系统、各类管理系统，还是数据分析类项目，只要涉及完整系统，最后往往都会落到数据库设计上。学校里的教务处、财务处、人事处要做的事情，换成企业里的销售、生产、物资、人事部门，底层做法是相通的。

销售管理子系统的主要功能，是处理顾客和销售员送来的订单；工厂根据订货安排生产，交付货物并开具发票；收到顾客付款以后，再根据存根和现款情况进行应收账款处理。

这些文字看起来很普通，但要把它们变成图，不能一口气把所有东西都画上去。我们还是按“实体—联系—属性”的顺序走。

#### 先确定实体和联系

从功能描述里，我们先识别出订单、订单细节、产品、顾客等对象。随着需求继续展开，又会出现应收账款和折扣规则。订单细节尤其值得注意：它不是订单身上一个孤零零的编号或一句说明，它有自己的相关属性，因此应当上升为实体。

实体先定下来，联系再逐个配：

- 一个顾客可以下多张订单，所以顾客与订单是一对多；
- 一张订单包含若干订单细节，所以订单与订单细节是一对多；
- 订单细节与产品、订单细节与折扣规则，都按需求中的一对多关系组织；
- 一个顾客面对多笔订单时，会对应多笔应收账款处理，所以顾客与应收账款也是一对多。

```text
[顾客] ──1:N── [订单] ──1:N── [订单细节] ──1:N── [产品]
   │                                     │
   │                                     └──1:N── [折扣规则]
   │
   └──1:N── [应收账款]
```

画到这里，有些关系还不能只凭前面的几句话确定。怎么办？先放着。不要为了把图一次画完，凭想象硬补一个关系；继续读需求、读数据字典，等事实多起来，关系自然会明确。

后面的文字正好补上了前面没有确定的内容：原来“订单与产品”的联系，实际上要落到“订单细节与产品”上。每条订货细节对应产品的描述，订单处理时还要从产品那里取得单价等信息。工厂对大宗订货有优惠，每种产品又有不同折扣，于是增加了“折扣规则”这个实体，专门存放折扣信息。

到这里，销售管理子系统的主体结构就基本清楚了。原来订单与产品的直接联系，被订单细节与产品的联系替代；订单、订单细节、产品、顾客、折扣规则和应收账款之间的骨架也已经搭好。

> **提示**：画图时不要追求一笔画到底。某条关系暂时看不出来，就先保留“待确定”的位置，继续从需求和字典中找事实。设计不是猜谜，不能靠想象填空。

#### 最后再分配属性

刚画出的这张图只有方框和联系，还没有椭圆，并不是完整 E-R 图。接下来要回到需求分析，把属性一个一个找出来：属于实体的属性，就抓到对应实体上；属于联系自己的属性，就放到联系上。像前面提到的“工作量”，就属于联系属性，而不是实体属性。

这个顺序能减少混乱。先把实体和联系搭稳，属性才不容易挂错位置。否则，一边猜实体，一边猜联系，一边补属性，很容易把一个本应是实体联系的信息，画成一个含义模糊的椭圆。

最后还要记住：系统通常不只有一个局部 E-R 图。销售管理只是一部分，还有物资、人事等其他子系统。局部图最终要合并，才能形成总体 E-R 图。

### 多个子 ER 图为什么必须集成

一个稍微像样的系统，通常都有若干功能模块。做毕业设计时，大家往往先各自处理图书馆的借阅模块、学校的教务管理模块、工厂的物资管理模块等。每个模块内部都能画出一张局部 E-R 图，但总系统只有一套数据库，最后不能各画各的、互不相干。

因此，E-R 图的集成就是必要的一步：不同部门、不同功能模块画出的局部 E-R 图，怎样合成一张总体 E-R 图？

标准做法分成两步，而且顺序不能乱：

```text
若干子 E-R 图
      │
      │ 第一步：合并，消除冲突
      ▼
初步 E-R 图
      │
      │ 第二步：修改与重构，消除不必要的冗余
      ▼
基本 E-R 图
```

第一阶段解决“怎么放在一起”的冲突，得到初步 E-R 图。第二阶段再检查有没有能够推导、可以合并或应当删除的冗余，得到基本 E-R 图。

> **定义**：初步 E-R 图是局部 E-R 图经过合并、消除冲突后的结果；基本 E-R 图则是在初步 E-R 图基础上继续消除不必要冗余后的结果。

基本 E-R 图才是下一阶段真正能够拿去拆表的基础。

### 先消除冲突，得到初步 E-R 图

第一次听到“E-R 图合并还有冲突”，可能会觉得奇怪：不就是把几张图拼起来吗？

真正麻烦的地方恰恰在这里。不同部门各画各的图时，往往对同一个对象采用了不同的类型、名字和抽象层次。直接拼起来，看起来也许更大了，实际上却可能把含义搅乱。

冲突主要有三大类：属性冲突、命名冲突和结构冲突。

#### 属性冲突：同一个属性，定义并不一致

属性冲突说的是：两个局部图里虽然都有一个同名字段，但它们对字段的要求并不一样。问题可能出现在数据类型、取值范围、表达格式或计量单位上。

比如“生日”，教务处给出的需求可能希望用一个小整数范围来表达；财务处却可能要求写成“年.月.日”的日期格式。合并后到底用哪一种类型、哪一种取值范围，必须根据实际需求统一。

再比如重量，有的局部图用公斤，有的局部图用克。它们都叫“重量”，但数据含义和单位并不相同。直接合并，表面上字段名一样，实际数据却会错得离谱。

> **易错点**：字段名字相同，不等于字段定义相同。类型、格式、取值域和单位任何一项不一致，都可能在合并时变成冲突。

处理属性冲突没有脱离实际、固定套公式的办法。我们要看不同部门为什么采用不同定义，再选出能够覆盖业务要求的统一形式；无法直接统一的，就要进一步澄清需求。

#### 命名冲突：一个名字，一种或多种意思

命名冲突有两种相反的情况：同名异义，以及异名同义。

同名异义，是同一个名字在不同环境中表达的并不是同一件事。比如都说“老师”，放在教学场景里可能指授课教师，放在学校行政语境里又可能指行政人员。两个部门都叫“老师”，但业务含义不同，不能不假思索地合成一个实体。

异名同义，则是一个东西换了不同名字。比如“教科书”“参考书”“教材”，名字看起来不同，说的可能都是同一类对象。这种情况必须统一名称，否则同一个实体会在总体图里裂成好几个。

> **提示**：合并时先问一句，这个名字在各自模块里究竟指什么。名字相同，含义可能不同；名字不同，含义也可能完全相同。

#### 结构冲突：同一对象，一边是实体，一边是属性

结构冲突比命名冲突更深一层。它不是称呼不同，而是抽象层次不同。

还是以“职称”为例。在教务处的局部 E-R 图中，职称只是说明教师情况的一项描述，没有更多独立内容，因此可以放在教师实体下面，作为教师的属性。

可到了财务处，职称要和工资、奖金、绩效等数据发生联系，单独讨论某项职称已经不够用了。于是，职称在财务处的图中可能被提升为实体。

同一个人在两套业务中的不同需求，产生了不同抽象；局部图单独看都可能合理，合并时却不能一边是实体、一边是属性继续并存。我们必须结合实际用途决定：到底是把实体降为属性，还是把属性升为实体。

还有几种结构差异也要处理。同一实体在两个模块中的属性集合、属性个数或排列方式可能不一致；实体之间的联系在一处是一对多，在另一处却可能标成其他类型。这时都不是机械改数字，而是要回到业务事实，统一定义。

> **结论**：冲突必须处理，但处理方法必须来自实际需求。属性与实体之间可以升格，也可以降格；联系类型要按真实关系统一，不能只为了让图“合得上”而迁就某一张图。

#### 合并实例：两个“数量”不能继续同名

我们来看一个具体例子。第一张局部 E-R 图中，产品与零件之间有“构成”联系，是多对多，联系上带一个数量。

另一张局部 E-R 图中，产品、零件、供应商三者之间有“供应”联系，这是一个三元多对多联系，联系上也带一个数量。

```text
第一张局部图
[产品] ──构成 M:N── [零件]
          数量

第二张局部图
[产品]、[零件]、[供应商] ──供应（三元 M:N）── 数量
```

把两张图合并时，产品和零件在两张图中都出现，先将它们对应起来；但“构成”和“供应”是两条不同的联系，不能因为产品、零件相同，就把联系也搅成一条。两条联系都保留，两个数量也先保留。

此时会出现什么冲突？

- 两边的产品如果是相同对象，但数据类型、取值域或单位不一致，要先统一；
- 两边的零件如果定义不一致，同样要处理；
- 两张图各自都有一个“数量”，但一个描述构成关系中的数量，另一个描述供应关系中的数量。同名异义，必须重新区分。

在这个例子中，处理后可以把它们改名为“数量1”和“数量2”。名字一改，含义就不再混在一起。完成这些冲突处理以后，合并结果就是初步 E-R 图。

> **易错点**：合并局部图时，不能因为两个联系里出现同名字段，就把字段直接叠在一起；也不能把“名称相同”误当成“含义相同”。

### 再处理冗余，得到基本 E-R 图

消除冲突之后，为什么还不能直接拿去建库？因为初步 E-R 图里可能还有冗余。

这里的冗余不只包括一眼看上去就重复的属性或联系，还包括能够从其他数据中推导出来的信息。

> **定义**：冗余数据，是指可以从基本数据计算出来的数据；冗余联系，是指可以从其他联系推导出来的联系。

所以，“看起来重复”只是最直观的一类冗余。更隐蔽的情况是：图上两处都记了同一个事实，其中一处的数值可以由另一处聚合或计算得到。

#### 物资管理图里哪些数据可以推导

来看一个物资管理关系。图中包含这些事实：

- 产品与零件之间有“构成”联系，是多对多，零件数记为 $Q_1$；
- 零件与材料之间有“消耗”联系，是一对多，消耗量记为 $Q_2$；
- 产品与材料之间有“使用”联系，是多对多，用量记为 $Q_3$；
- 材料与仓库之间有“存放”联系，是多对多，存放量记为 $Q_5$；
- 材料本身还有一个总存放量 $Q_4$。

```text
[产品] ──构成 M:N── [零件]       零件数 Q1
[零件] ──消耗 1:N─── [材料]       消耗量 Q2

[产品] ──使用 M:N── [材料]       用量 Q3
[材料] ──存放 M:N── [仓库]       存放量 Q5

[材料] 总存放量 Q4
```

$Q_4$ 可以由各个仓库的存放量推导出来。讲师举了一个很直观的例子：一把扳手放在两个仓库，一个仓库存放 5 个，另一个仓库存放 4 个，那么材料总存放量就是 $4+5=9$。既然各个仓库的数量已经能够推出总量，单独再保存一个总量就可能属于冗余。

$Q_3$ 也可能由 $Q_1$ 和 $Q_2$ 推导出来。知道产品包含多少零件，也知道各零件消耗多少材料，就有可能计算出产品对材料的使用量。因此，当 $Q_1$、$Q_2$ 已经存在时，$Q_3$ 也有推导来源。

在这个例子里，$Q_3$ 和 $Q_4$ 可以考虑消除。

但“可以考虑消除”不等于“无论如何都必须消除”。有的时候，我们就是希望查看某个总量时直接得到结果，不希望每次都临时求和；有时保留一个常用结果，是为了让使用更方便。这样的选择未必就是坏设计。

> **易错点**：数据库设计不是范式越高、越严格就一定越好。更高程度的规范化虽然有助于减少冗余，却可能牺牲查询效率。数据库设计没有脱离场景的单一最优解，一切都要因地制宜、实事求是。

#### 规范化理论可以帮忙，但不是非做不可

我们也可以用规范化理论来处理这些冗余。做法是先确定 E-R 图中实体之间的数据依赖，利用实体码和函数依赖把依赖关系表达出来，再尝试求出最小覆盖。发现平凡依赖或部分依赖等可以处理的情况时，再进行相应调整。

不过，在实际应用中，我并不觉得每张 E-R 图都一定要把这套方法完整走一遍。E-R 图如果已经画得清楚，相关数据依赖也能直接看出来，强行套一套复杂方法，未必更有价值；实在看不明白的地方，也未必值得为了“形式上完成规范化”去过度处理。

更重要的是，规范化理论本身受到通用关系假设等条件限制，不存在一个脱离具体业务、要求所有 E-R 图必须处理成某个固定形态的绝对标准。具体问题还是要具体分析。

所以，消除冗余这一步要坚持两个判断：

1. 能从已有数据或联系可靠推导出来的内容，要认真检查是否真的有必要重复保存；
2. 是否删除，要结合查询便利性、维护成本和执行效率决定，而不是看到一个能推导的字段就机械删除。

### 用整套系统例子走一遍集成

理解了“冲突在前、冗余在后”，我们再看一个完整系统怎样把多张局部 E-R 图合成总体图。

某工厂的信息系统里包含多个子模块。我们已经分别画出了物资管理、销售管理，以及项目或人事管理等相关 E-R 图。局部图里可以看到供应商、仓库、职工、零件、项目等对象，也能看到订单、订单细节、顾客，以及项目、职工、部门等关系。

合并时，先找可以连接的地方：

- 两张图中都出现项目；
- 多张图中都有职工；
- 另有局部图使用了不同名称来表达实际上可以对应起来的内容。

比如，项目和产品最后被判断为异名同义。某个项目实际上只生产某个产品，所以在总体图中统一使用“产品”作为实体名。这里不是按字面硬合并，而是回到工厂的业务含义，看清两者究竟是不是同一个对象。

职工也是重要的合并点。不同部门画出的局部图都会描述职工，但侧重点不同。合并时要把共同部分对齐，再处理各模块独有的部分与冲突，不能简单地把一张图叠到另一张图上。

> **提示**：合并前先找“合并点”，再处理冲突。带着完整属性直接叠加，几张图一多就会乱成一团；必要时可以先隐去属性，只看实体和联系的主干结构。

合并过程中至少会遇到两类问题。

第一类就是异名同义。项目和产品统一成“产品”实体，就是一个明确例子。

第二类是重复表达的关系。库存管理图中有关职工的一些关系，在劳动人事管理模块中已经有了相应表达，那么库存图中重复的关系就可以取消。职工之间的领导与被领导关系，如果能够由“职工—经理”的领导关系，以及部门与职工的从属关系推导出来，也不必再额外保留一条直接关系。

于是，整个合并过程可以概括成：

```text
先找合并点
   │
   ├─ 统一实体含义与命名
   ├─ 处理属性、命名和结构冲突
   └─ 对齐联系及其联系类型
   ▼
初步 E-R 图
   │
   └─ 删除或合并能够推导的重复信息
   ▼
基本 E-R 图
```

这里有一个非常实用的轻重之分：**冲突一定要处理，冗余要看情况。** 不同模块对同一对象的定义不一致，会直接破坏总体模型，必须统一。至于某些关系是否应该通过推导得到，我们有时为了直观展示和查询方便，完全可以保留；这不是原则性错误。

经过这些处理，最终得到工厂管理信息系统的基本 E-R 图。它不再只是几张局部图的简单相加，而是整个组织范围内语义相对统一、可以继续向逻辑结构推进的概念模型。

### 基本 ER 图只是走向数据库的前提

到这里，概念结构设计才算真正完成。

我们先从需求分析出发，画出实体、联系和属性；再把不同模块的局部 E-R 图合并起来，先消除冲突得到初步 E-R 图，再根据实际需要消除冗余得到基本 E-R 图。

不要把“基本 E-R 图已经画出来”误解为“数据库已经设计完了”。它只是下一步的前提，就像我们求出了最小函数依赖集，才有可能进一步判断码和范式一样。

下一步是逻辑结构设计。如果 E-R 图是盖楼时用的图纸，那么逻辑结构设计要考虑的就是：怎样把图纸拆成一堆二维表，又怎样把这些表联系起来。之后还要进行规范化处理、连接各表，最终把数据库真正建立起来。

这套过程可以压缩成几条必须记住的话：**先找实体，再配联系，最后分属性；能当属性，就不要随手增加实体；当属性有了自己的伙伴，就把它带着伙伴独立出来；多个局部图先消除冲突，再按实际需要消除冗余；基本 E-R 图出来以后，才进入拆表与规范化。**

概念结构设计看起来只是几类图形，真正难的地方却全在边界判断、语义统一和取舍上。也正因为如此，一张真正可用的 E-R 图，从来不是画得最多，而是表达得最准确。

## 物理结构设计：索引、存储结构与数据库落地
> 对应块：BLK26 | 覆盖分集：P23 | 块标题（分集名）：《数据库第7章 数据库设计（第三部分：物理结构设计》

把需求整理成文档，再用 E-R 图画出概念结构，最后把 E-R 图变成一张张二维表，前面三个环节就接上了。可二维表还只是逻辑上的东西，它究竟怎样落到磁盘上，查询时又该沿着什么路径把数据取出来？这正是物理结构设计要回答的问题。

数据库在物理设备上的存储结构和存取方法，合称数据库的物理结构。为一个已经确定的逻辑模型选择最适合应用要求的物理结构，这个过程就是物理设计。它依赖所选用的数据库管理系统，因为 Access、SQL Server、MySQL、Kingbase、DB2 等系统已经替我们封装了大量底层机制。

所以，这里看似又冒出了一层复杂概念，实际使用中却往往不需要亲手设计。理解它，是为了看懂数据库为什么这样工作，也是为了在采购、验收和系统设计时能够提出真正有分量的问题。

### 从二维表到磁盘中间隔着什么

我们在屏幕上看到的是一张二维表，但计算机最终处理的并不是“学生”“课程”“成绩”这些汉字，而是二进制数据。屏幕上的结果要经过内存运算，数据也要落到硬盘等存储设备上，这个转换链条可以画成下面这样：

```text
用户看到的二维表
        ↓
数据库管理系统与操作系统组织数据
        ↓
0 和 1 的二进制表示
        ↓
存储单元中的不同物理状态
        ↓
磁盘、内存等物理设备
```

最底层可以把存储单元想象成小电容器，通过不同的电压状态区分二进制。例如充满和半满可以分别表示约 1 伏与 0.5 伏的状态。具体硬件怎样把 0 和 1 映射成电压、磁状态或其他物理状态，是硬件平台与设备厂商的工作；在电子计算机上做数据库表设计的人，通常既不决定，也不必操心到这一层。

再往上一层，二维表怎样组织成计算机可以处理的 0 和 1，主要由操作系统和数据库管理系统共同完成。选中一种数据库管理系统，实际上也就接受了它已经设计好的文件组织、数据访问和资源管理机制。

这件事很像买电脑时选择 Windows、macOS 或 Linux：你当然会使用这个系统，但不会因为某块硬盘采用了特定芯片结构，就重新设计一遍二维表。数据库管理系统的选择也是如此。

> **定义**：存储结构说明数据在物理层究竟怎样存放；存取方法说明数据库怎样建立访问路径，以及查询时怎样沿着路径找到数据。索引是存取方法中的核心内容。

这两者不要混在一起。存取方法偏向“怎样找”，存储结构偏向“放在哪里、怎样放”。物理设计先把索引、聚簇等访问方案选出来，再确定关系、索引、日志、备份等数据库文件的具体存储安排。

### 物理设计是一个会回头的过程

物理设计不是选完索引就直接进入实施。设计出来的方案，还要接受时间效率和空间效率的评价。指标满足要求，才能进入物理实施；如果不满足，就要重新修改物理结构，必要时还要退回逻辑模型继续调整。

```text
确定物理结构
      ↓
评价时间效率与空间效率
      ↓
  是否满足要求？
   ↙          ↘
  是            否
进入实施      重新设计物理结构
                 ↓
             必要时返回逻辑模型
```

这个回头过程非常重要。逻辑上看起来完全正确的表结构，换到物理环境中，未必同时拥有理想的访问时间、空间占用和维护成本。

因此，物理设计需要建立在充分的环境调查之上。设计者要知道目标系统与硬件环境，清楚应用提出的详细要求，还要分析主要事务，从而取得查询和更新方面的参数。数据库管理系统内部支持哪些存取方法与存储结构，也必须提前摸清。

查询参数主要包括查询涉及哪些关系、会用到哪些属性、连接条件落在哪些属性上，以及最终需要投影出哪些结果。更新参数则要回答：会修改哪些关系和属性，属性值会发生怎样的变化，每个事务在各个关系上运行的频率如何，以及应用对响应时间有什么性能要求。

这些信息不是拿来写一段泛泛的说明，而是为了回答具体问题：一个属性是否经常出现在查询条件里？哪张表是连接的中心？哪些数据更新频繁？哪条访问路径真正值得建立？

> **结论**：物理设计不是凭感觉给表加索引，而是从应用的事务特征出发选择存取方案，再从存取时间、空间效率和维护代价三个方面检验结果。

### 关系模式需要多条存取路径

数据库是多用户共享的系统。同一个关系常常要服务不同类型的查询，不能只留一条访问路径，更不能指望所有人只能“从一个入口进来，再从一个出口出去”。如果一百个同学同时选课，系统却只有一条狭窄的访问路径，瓶颈自然会立刻出现。

用选课数据库来想就很直观。学生要按学号查，选课记录要按课程查，教师可能按姓名查成绩。每一个入口，都是一条可能需要支持的存取路径。物理设计的任务之一，就是根据数据库管理系统提供的存取方法，确定这些路径。

常讨论的方案主要有 B+ 树索引、哈希存取和聚簇存取。教材上的规则可以记，但更重要的是把它们放回具体案例里理解。学号、成绩和连接条件为什么适合建索引，电话通讯录为什么天然对应聚簇，映射关系为什么怕数据规模频繁变化，这些直觉比背下一串条目更有用。

#### B+ 树索引

B+ 树是一种树状索引结构，节点自上而下排列。给定一个查找值，在每一层都与当前键值比较：比它小的往左走，比它大的往右走。查找不必扫描所有数据，目标越明确，路径就越短。

比如根节点是 25，后来又加入 20、30 和 18，可以形成这样的查找结构：

```text
              25
            /    \
          20      30
         /
       18
```

先比较 25：20 放到左侧下层，30 放到右侧下层。再放入 18，它比 20 小，于是继续向 20 的左下层走。每比较一次，候选范围就缩小一层，这就是 B+ 树适合索引查找的原因。

是否为某个属性建立 B+ 树索引，可以先抓住几个常见信号。

- 属性或一组属性经常出现在查询条件中，应考虑建立索引。比如经常拿学号查学生，查到学号后需要其他信息，就适合以学号为索引入口。
- 属性经常作为最大值、最小值等聚集函数的参数，也可以考虑索引。比如经常查询最高分和最低分，成绩就是合适的候选。
- 属性经常出现在连接条件中，更应该认真评估。student 表和选课表通过学号连接时，学号就很可能成为索引依据。
- 属性涉及单列索引、复合索引还是唯一索引，也要根据应用要求确定。不能看到查询条件里有这个字段，就不加判断地全部建索引。

这几条规则不是让人逢字段必建索引，而是提供一个判断起点：字段是否频繁参与查找、计算和连接，使用它建立索引能否换来更短的访问路径。

索引也不是免费的。把数据放进图书馆，读者输入作者、年份或书名后，前台系统就能告诉他书在几楼、哪一片、哪一层架子上。可新书到了、旧书淘汰了，原来的位置变了，目录也必须跟着维护。数据库索引同样存在这种代价。

索引过多会增加两类开销。

- **维护开销**：数据插入、删除或更新后，索引也要同步维护。书换了位置，目录就得多改一次。
- **查找开销**：索引多并不意味着总能找到最快路径。系统有时反而要先判断该走哪一棵索引树，再从树中找到数据。

> **易错点**：索引不是越多越专业。真正要回答的是：哪一个属性承担了足够多的高频访问，哪一条索引能减少实际 I/O，同时让维护成本保持在可接受范围内。

#### 哈希存取

哈希存取使用哈希函数把记录分组，让属性值与存放位置建立映射。查找时不必从根到叶逐层比较，而是对查找值做同样的映射，直接定位到相应分组。

不过，选用这种方案要满足两个条件之一。

- 关系的大小可以预知，而且保持不变。
- 关系的大小会动态变化，但数据库管理系统提供了动态哈希的存取方法。

为什么不希望规模频繁变化？因为哈希函数建立的对应关系，需要适应数据集合的分布。关系规模变化太大，原来的映射就可能频繁失效，需要重新组织。把数据分组这件事想成“按固定规则摆货架”，一旦进来的数据规模总在大幅变化，原来算好的位置就不再可靠。

哈希的思路并不陌生，它就是把散列分组的思想用于关系数据的定位。真正需要检查的不是“哈希”这个名字，而是两个前提：规模是否稳定，以及选定的数据库管理系统能否处理动态变化。

#### 聚簇存取

为了提高按某个属性查询的效率，把具有相同属性值的元组集中存放在连续的物理块中，这一组织方式称为聚簇。作为依据的属性或属性组称为聚簇码，也叫 cluster key。

手机通讯录就是最容易理解的聚簇结构。拼音首字母为 A 的联系人放在 A 组，首字母为 B 的联系人放在 B 组。找“爸爸”时，可以先定位到 B，再在 B 组里继续找；如果完全没有分组，就只能逐条遍历全部联系人。

聚簇索引的关键，不只是给属性建了一棵查找树，而是让索引项的顺序与表中元组的物理存放顺序保持一致。查找某组值时，系统可以顺着连续物理块一次取回多个元组，不必在磁盘各处来回跳跃。升序还是降序，与通讯录按字母组织的方式是同一个道理。

一个基本表最多只能有一个聚簇索引。既然物理元组已经按照这一套规则组织，就不能再同时换另一套规则从头排列。这个限制可以从通讯录直接理解：联系人已经按 A 到 Z 放好，不能再要求同一个人同时归属到另一套完全不同的主分组。

聚簇索引适合基本表增删操作较少、变长列修改较少的场景。因为它追求的是物理连续，而插入、删除和位置重排都会破坏或重建这种连续性。

来看一个具体对比。假设计算机学院有 500 名学生，查询信息系学生的完整名单。如果 500 名学生分散在 500 个不同物理块中，即使每个人的院系字段都表明自己不是信息系，也可能要逐块读取，至少产生 500 次 I/O。这里可以把一次 I/O 想象成去取一个物理块，像开一次灯的开关。

如果先按院系聚簇，把同一系的学生连续存放，假设学院涉及三个系，那么读取三个物理块就能得到三个系的全部相关学生。I/O 次数从 500 次降到 3 次，效率差异非常直观。聚簇带来的收益，就是让一次取数覆盖更多满足条件的元组。

> **结论**：聚簇不是让查询条件消失，而是让满足同一属性值的记录彼此相邻，使一次物理读取能够带回更多目标数据。

聚簇的代价同样明显。假设通讯录是手写的，A 到 Z 的 26 个组已经排好，B 组中依次放着 BA、BB、BC。现在来了一位拼音首字母仍为 B、但恰好插在 BA 与 BB 之间的人。为了保持顺序，你得给后面的人挪位置，把新纸片插进去，整个 B 组的物理排列都发生了变化。

数据库也是一样。新记录插到聚簇中间，可能迫使已有元组移动；关系原来的物理顺序一旦失效，索引与数据布局都要重新组织。现代机器执行得很快，我们感受不到这种成本，但“已经排好的一摞纸片需要重新插页”已经把机理说得很清楚。

选择候选聚簇时，可以检查这些线索。

- 经常一起进行连接操作的关系，可以考虑建立组合聚簇。
- 一个关系的一组属性经常出现在相等比较条件中，可以围绕这些属性考虑聚簇。
- 一个属性或一组属性的值重复率很高，也适合考虑聚簇，因为大量相同值集中存放后，连续读取的价值更明显。
- 对候选关系逐个检查，取消不必要的聚簇。
- 经常执行全表扫描的关系，局部聚簇未必能带来期望收益。
- 更新操作远多于连接操作的关系，移动元组的维护成本可能超过聚簇收益。
- 重复出现的候选关系也要合并考虑，不能把同一条原则反复建出多套方案。

这些原则不需要脱离场景死记。一个表只有一列候选项时，先看它是不是候选码；多个候选属性中，再看哪个使用得最频繁。所谓具体问题具体分析，并不是拒绝原理，而是别让原理代替判断。

> **提示**：对非计算机专业同学来说，理解多用户需要多条路径、B+ 树逐层定位、哈希按函数映射、聚簇按相同值连续存放，已经足够建立完整直觉。真正从事数据库工程的人，则还要继续面对候选聚簇取舍、参数配置和性能测量。

### 数据库文件怎样摆放

确定了存取方法，还要确定数据库的存放位置与存储结构。这里涉及关系文件、索引、聚簇、日志、备份等对象。数据库管理系统已经提供了实现机制，但具体参数仍要结合应用环境调整。

评价数据存放与存储结构时，主要看三件事：存取时间、空间利用率、维护代价。

| 评价目标 | 核心问题 | 优化方向 |
| --- | --- | --- |
| 存取时间 | 数据与索引能否被快速定位，一次 I/O 能否带回更多所需数据？ | 缩短访问路径，改善连续存放与参数配置 |
| 空间利用率 | 关系、索引、缓冲区等是否占用过多可用空间？ | 减少冗余与过大缓冲，合理设置存储分配 |
| 维护代价 | 插入、删除、更新和恢复是否频繁牵动大量数据？ | 降低数据移动，控制索引与聚簇维护工作 |

这三项通常存在矛盾。

多表连接时，如果先把较大范围的数据组织出来，查找结果近在眼前，读取会更快；但这相当于在内存中撑开一个很大的缓冲，访问时间换来了空间占用。逐表处理、逐层取数时，不必同时容纳整个巨大结果，空间利用率更高，却要付出更多处理时间，维护也更复杂。

所以，不能只问“哪一个最快”。关系只有几百条和有几亿条，答案可能完全不同；数据经常更新和以查询为主，合适的布局也不同。物理设计要做的是结合应用负载，在三个目标之间找到折中。

#### 稳定数据与易变数据分开

一个很实用的摆放原则，是把经常变化的部分与相对稳定的数据分开，也要把高频访问的数据与低频访问的数据分开。

历史性、长期保存而平时很少使用的数据，和频繁增删改查的数据，访问特征完全不同。数据库系统内部也可以按这个思路组织数据：经常更新的活跃部分单独放在一起，访问频率低的数据聚在一起。这样做就像把常用物品放在容易拿到的位置，而不是让全部物品都混在同一层架子上。

这一区分还可以帮助我们理解数据库与数据仓库的差异。数据库往往面对频繁的增删改查，而低频使用的历史数据更适合进入数据仓库长期保存。即便不讨论外部系统，仅看数据库内部的物理组织，也应当识别不同数据的稳定性与访问频率。

#### 参数必须服从应用环境

数据库管理系统会提供一批可分配参数，并为它们设置合理缺省值。物理设计要做的是根据具体应用重新确认这些值，而不是把默认值当成任何场景都适用的真理。

需要关注的参数包括：

- 同时使用数据库的用户数量。
- 同时打开的数据库对象数量。
- 内存分配与缓冲分配。
- 物理块大小。
- 装填因子。
- 时间片设置。
- 数据库大小。
- 锁定数目等。

可以把 Access 的 10 个并发用户与 SQL Server 的 1000 个并发用户放在一起理解。选型时，要判断系统面对的是少量用户的小型应用，还是大量用户同时访问的业务网站；数据库能够同时打开的对象数、内存与缓存是否够用，也必须一起评估。选一个参数能力与实际需求不匹配的系统，再漂亮的物理设计也无处施展。

从数据库选型角度看，问题是现有产品参数能不能满足业务需求；从物理设计角度看，问题则是既然需求已经明确，后端资源有多少，就按需要分配多少，不适用的余量没有必要全部交给应用。

这正是设计与采购之间的对应关系。作为使用方，我们未必亲手调整每个底层参数，但至少要知道应该检查哪些参数，以及它们为什么会影响系统性能。

### 用三个问题验收物理设计

物理结构设计做得好不好，不能只凭“表上加了很多索引”判断。比较实用的验收方式，仍然回到存取时间、空间利用率和维护代价三个方面。

如果参与数据库招投标或技术验收，可以直接围绕这三项提问：存取时间怎么样，空间利用率怎么样，维护代价怎么样？更进一步，还要追问：系统怎样平衡这三个彼此冲突的目标，又怎样满足本企业的实际业务需求？

能回答“做了哪些设置”，只是第一层；能说明“为什么这样设置”“牺牲了什么换来了什么”，才真正理解了物理设计。

对计算机专业同学而言，这些指标对应的是具体的系统设计能力：对非计算机专业同学而言，它们同样不是天书。将来如果参与数据库采购、折旧评估、系统选型或商务谈判，不懂底层实现没有关系，但不能连该验收什么都不知道。知道问什么、听得懂对方如何回答，本身就是一项职业能力。

> **结论**：物理设计的成果不是一个孤立的索引清单，而是一组经过取舍的方案。它必须说明访问路径是否有效、空间是否合理、更新与恢复是否可持续，并用三项指标证明这套取舍符合应用需求。

### 数据库的实施与维护

物理结构确定以后，数据库还不能马上正式投入使用。接下来要装载数据、调试应用程序、试运行，最后进入日常运行与维护。顺序很清楚：先把数据装进去，再让程序跑起来；先在小规模条件下验证，再逐步投入正式使用。

#### 数据装载与程序调试

数据装载可以采用人工方式，也可以使用计算机辅助入库。这里真正困难的不是“把数据敲进去”，而是保证数据库与应用程序使用同一套已经确定的逻辑结构，让程序能够正确访问关系、主码、完整性约束与数据。

应用程序的设计还应当与数据库设计并行，而不是等数据库彻底结束以后再开始。组织数据入库的同时，就可以同步调试应用程序。具体的程序设计、编码和调试方法属于软件工程或信息系统开发的课程范围，但并行开展这个思想必须掌握：数据结构变了，程序接口与处理逻辑就可能随之变化，等一切结束再联调，往往会把问题堆到最后。

#### 试运行与动态调整

试运行主要包括功能测试和性能测试。功能测试检查系统能不能完成预定任务，性能测试则观察真实运行中的时间与空间表现。

物理设计阶段估算时间和空间指标时，为了推进设计，不得不采用许多简化和假设，并忽略次要因素，因此结果通常比较粗糙。真正运行起来以后，需要测量的参数更多。拿到实际数据后，再对物理结构进行动态回溯与迭代。

数据也不适合第一天就毫无节制地全部灌入。通常先输入一小批量数据，供调试和试运行使用；等基本条件满足以后，再放大数据、逐步增加数据量。这样做的价值，是把问题暴露在小规模阶段。若小批量数据已经导致严重性能问题，就不能指望数据规模扩大后问题自行消失。

> **提示**：试运行不是“能跑就算成功”，而是用功能与性能数据检验前面的设计假设。估算再漂亮，也必须接受真实负载的检验。

#### 转储、恢复与日常维护

误操作可能破坏数据库，因此转储和恢复能力必须纳入运行方案。发现问题时，通过已有转储或恢复手段把数据库带回可用状态。

正式运行后，维护工作集中在四类对象上。

- **安全与完整性**：控制谁能访问什么，同时保证数据满足设计好的完整性约束。
- **性能**：持续监督、分析并改进实际运行性能，不把一次试运行的结果当成永久结论。
- **重组织**：处理运行后数据位置与结构变化带来的问题。
- **重构造**：当应用需求本身发生变化时，对数据库结构作进一步调整。

数据库运行不是“建完就撒手”的静态文件。数据会变化，应用会变化，业务重点也会变化，数据库的设计与参数就需要跟着回溯和迭代。

### 数据库设计是一条会回头的主线

说到这里，可以把数据库设计的全过程重新串起来：

```text
需求分析
  整理信息需求与数据需求
        ↓
概念结构设计
  把需求文档画成 E-R 图
        ↓
逻辑结构设计
  拆成关系，确定属性、主码、范式与连接
        ↓
物理结构设计
  选择索引与存储结构，平衡性能代价
        ↓
数据库实施
  装载数据、调试程序、试运行
        ↓
运行与维护
  控制安全与完整性，持续监督和迭代
```

它不是一根只能向下走的直线。只要物理结构不能满足时间与空间要求，就要回头修改；逻辑结构存在缺陷，可能还要继续返回概念结构甚至需求分析。设计由上而下，实施后用真实运行结果检验，再向上回溯定位问题。

> **结论**：数据库设计是一个从上到下推进、再用实际运行结果反复回溯的标准化过程。标准化不代表机械照抄，它要求每一步都用自己的问题把流程走通。

如果从考试角度观察，这套流程的重点非常清楚。需求分析通常作为题干提供，是一整段业务描述；概念结构设计可能要求把描述画成 E-R 图，如果整张图太大，可以先分别画实体属性图和实体联系图，最后再合并；逻辑结构设计则要求把 E-R 图拆成二维表，明确属性列和主码，规范化到三范式，再把多张表连接起来。

物理结构设计与实施维护通常不是大题的主要考点，但如果老师采用选择题或填空题，仍要熟悉课件中的基本流程。把三项评价指标、实施顺序、试运行内容与维护事项记住即可，不必把大量工程细节编成应试故事。

真正理解这套流程后，会发现数据库设计并不神秘。软件开发有结构化生命周期、原型法与敏捷开发等方法，数据分析有跨行业数据挖掘标准流程 CRISP-DM，数据库设计也有自己的标准步骤。每个阶段都提供相应工具、方式和方法，剩下的差别更多是熟练程度，而不是有没有路可走。

这就像盖楼。设计者不必搬砖，但必须知道承重结构、材料和工序为什么这样安排；使用系统的人也未必亲自配置每个参数，但必须能对方案的代价与能力作出判断。

### 学会流程，还要看出它为什么这样设计

学习数据库设计，不能只记住六个环节的名字。至少还要追问两个问题。

第一个问题：这些知识在专业体系里究竟有什么用？物理结构为什么依赖数据库管理系统？索引为什么既能加速查找又会增加维护成本？聚簇为什么只适合特定的更新条件？把数据库放回操作系统、硬件与应用需求共同构成的知识图谱，才能真正理解它，而不是把步骤拆开背诵。

第二个问题：当大家都能完成基本操作时，怎样形成自己的竞争优势？仅仅会做题、照着步骤建表，优势很有限。再向前走一步，思考系统为什么这样设计、某个指标如何权衡、换一种数据库选型会带来什么变化，这种“多走一英里”的习惯，才可能把知识转化为工作能力。

例如，将来参加数据库采购或招投标时，你未必亲自调整底层参数，却能围绕存取时间、空间利用率、维护代价和需求匹配提出问题；参与系统验收时，你能听懂方案为什么这样平衡；参与商务谈判时，你也知道自己真正买到的并不只是软件名称和功能清单，而是一整套文件组织、访问机制与运行保障能力。

这就是跨学科视角的价值。课程内容本身要学会，还要把系统架构、硬件、操作系统、软件工程、项目管理和业务需求连接起来。学会使用只是第一层，理解取舍、处理复杂问题并解释设计理由，才可能形成别人不容易复制的优势。

学完数据库设计，不必把它想象成一堆互不相干的术语。需求、概念、逻辑、物理、实施和维护，本来就是一条从业务想法通向真实系统的主线。索引和存储结构解决的是“数据怎样落下去、怎样找回来”，实施和维护解决的则是“这套数据库怎样真正长期运行”。把这两部分接起来，才算把数据库从图纸变成了可以 dependable 地运行的系统。

> **承前启后**：上一节讲完「物理结构设计：索引、存储结构与数据库落地」，下一节接着讲「数据库设计：从需求、ER图到关系表」。

## 数据库设计：从需求、ER图到关系表
> 对应块：BLK27 | 覆盖分集：P24 | 块标题（分集名）：《数据库设计 核心精简版：核心内容+考试重点+案例》

数据库设计看着像一条很长的流程，真要抓重点，反而没有想象中那么复杂。前面按章节把需求分析、概念结构、逻辑结构、物理结构、实施和运行维护都讲过一遍，信息很多；到了考试和实际开发里，我们更需要抓住两件事：哪些阶段必须亲手做，哪些阶段主要由数据库管理系统和运行环境决定。

我把这套内容重新压成一条主线：**先把需求整理成实体、属性和联系，再画出 ER 图；然后把 ER 图拆成二维表，规范到三范式，连接各表，最后按需要设计视图。**概念结构设计和逻辑结构设计是考试的主战场；再加前面的人为需求分析，就是实际开发中真正需要重点投入的三个阶段。

### 六个步骤只有一条主线

数据库设计仍然遵循六个步骤：

```text
[需求分析]
    ↓
[概念结构设计] ── 把现实需求画成 ER 图
    ↓
[逻辑结构设计] ── 拆成二维表、规范、连接、设计视图
    ↓
[物理结构设计] ── 决定存储结构与存取路径
    ↓
[数据库实施]   ── 创建模式、装载数据、试运行
    ↓
[运行与维护]
```

这六个阶段不是六个互相独立的名词，而是一条因果链。没有需求，就不知道该画什么；没有 ER 图，就不知道该拆什么表；没有拆好表，后面的物理设计、装载和运行都没有可靠基础。

| 阶段 | 核心工作 | 产出或关注点 |
| :--- | :--- | :--- |
| 需求分析 | 弄清要做什么信息处理、数据操作与控制 | 需求说明 |
| 概念结构设计 | 找出实体、属性和联系 | ER 图 |
| 逻辑结构设计 | ER 图转二维表，处理范式、表间联系和视图 | 关系模式 |
| 物理结构设计 | 安排存储结构、索引与存取路径 | 物理存储方案 |
| 实施 | 创建数据库模式、装入数据、试运行 | 可运行的数据库 |
| 运行与维护 | 在实际使用中持续工作 | 运行中的数据库 |

#### 需求分析先抓三类内容

需求分析要弄清楚两件事：有哪些信息处理任务要做，具体有哪些数据需求。考试里常见的要求，可以从数据定义、数据操作和数据控制三个角度梳理，也就是 DDL、DML 和 DCL 这三类事情。

具体说，我们要知道系统里有哪些数据，数据之间是什么含义；有哪些增、删、改、查操作；又有哪些安全性和完整性要求。把这些谈清楚，最后形成需求手册。后面画 ER 图，不是随手画形状，而是把需求说明里已经存在的实体、属性和联系“捞”出来。

> **提示**：拿到一段需求文字时，别急着照句子画图。先问三遍：什么东西需要被管理？它有哪些描述信息？不同东西之间发生了什么关系？这三问本质上就是实体、属性和联系。

#### 概念结构设计就是画 ER 图

概念结构设计用 ER 图描述数据库要管理什么。现实世界里需要识别的东西，在 ER 图里主要就是三类：实体、属性和联系。属性既可能描述实体，也可能描述联系，这正是后面最容易丢分的地方。

ER 图画完以后，还要确定主码。主码必须具有唯一性，图中通常用下划线标出。概念结构设计完成之后，拿到的就是一张能够表达业务结构的“数据库图纸”。

#### 逻辑结构设计要连续做四件事

逻辑结构设计不是简单地把方块抄成表格，它有完整的前后关系：

1. 把 ER 图拆成二维表；
2. 确定属性列、主码、候选码、主属性和非主属性；
3. 检查函数依赖，把不符合要求的关系规范化到三范式；
4. 用外码连接主码，并按实际需要设计视图。

所以，“画 ER 图”和“拆二维表”是两个不同的考试问法。看到“设计概念结构”，就要交 ER 图；看到“设计逻辑结构”，就要交表、范式处理和连接关系。

#### 后三个阶段为什么经常点到为止

物理结构设计讨论两件事：数据怎么存，访问路径怎么安排。索引可以用 B+ 树、哈希，或者采用聚簇方式；表映射到磁盘后，数据又怎样表示成 0 和 1，也是物理设计要面对的问题。

但在真实开发中，这部分通常不需要设计者从头决定。表怎样映射成物理数据，主要由选定的数据库管理系统和操作系统决定；物理磁盘怎样组织，又涉及操作系统和硬件设备厂商。日常使用的 Windows、SQL Server，以及不同厂商提供的存储设备，都不是我们在一次数据库设计作业里从零规定的。

实施阶段则把已经设计好的数据库模式真正创建出来，装入数据并试运行。运行和维护继续使用这个数据库。到了这一步，关键结构已经定型，考题通常更适合用选择或填空检查概念，而不太可能要求我们手工安排每一页数据在磁盘上的位置。

### 考试与工作的重点并不完全相同

从考试角度说，我会重点盯住三个地方：

- 需求分析常以一段需求材料出现，要求整理需求；
- “设计概念结构”通常暗含画 ER 图；
- “设计逻辑结构”通常暗含拆表、规范到三范式和连接表。

这三个知识点要连续完成，不能画完 ER 图就停笔，也不能跳过属性归属直接拆表。物理结构设计、实施、运行与维护更多以选择题、填空题检查概念。

从工作角度说，需求分析、概念结构设计、逻辑结构设计仍然需要人来做。进入物理设计和实施以后，只要选定了数据库产品与开发环境，大量底层工作就由数据库管理系统、操作系统和硬件环境承担了。

> **结论**：考试抓“需求分析、概念结构、逻辑结构”三段；实际开发也重点投入这三段，只是进入后三个阶段后，我们通常不必手工解决所有底层映射问题。

这两个导向后面还会再次出现。尤其是把联系拆成表时，考试与实际系统效率会给出一个看似相反、实则各有用途的答案。

### ER图先认准三个基本元素

ER 图的正式名称是 Entity-Relationship Diagram。整套图并不复杂，方块、椭圆、菱形就是它的基本语言。

#### 实体、属性与联系

实体是现实世界中需要被管理、并且确实存在的事物。它可以看得见、摸得着，比如笔、屋子、桌子、板凳；也可以看不见、摸不着，比如学校、专业、所在系和某个组织。后者虽然不能被手摸到，但在人的观念中确实存在，只要能明确指出某个具体对象，它就可以作为实体。

实体画成方块。

属性用来描述实体，也可以描述联系，画成椭圆。例如某个职工有哪些性质，是实体属性；哪个职工生产了哪个产品、生产绩效如何，描述的就是“生产”这个联系，因此属于联系属性。

联系画成菱形，并标明 1 对 1、1 对多或多对多三种关系。

```text
[职工] ──N──〈生产〉──M── [产品]
                  │
                绩效
```

职工与产品之间是多对多：一个职工可以生产多个产品，一个产品也可以由多个职工生产。因此“生产”不能简单地塞进职工表或产品表，它有自己的属性，也就需要在拆表时认真处理。

#### 固定顺序能帮我们少丢分

画 ER 图时，我建议大家牢牢记住这个顺序：

1. 先找实体；
2. 再找联系；
3. 再分属性；
4. 最后确定主码，形成完整 ER 图。

先实体，是因为实体是核心中的核心。先联系，是为了把对象之间发生的关系固定下来。最后分属性，是为了避免一上头把所有椭圆都插到实体上，却把联系自身的属性忘在一边。

属性不能想当然地归到最近的那个实体。比如“这个学生选了哪门课、得了多少分”，描述的是学生与课程之间的“学习”联系；把它整个塞进学生表或课程表都不合适。再比如“哪个职工生产了哪个产品、绩效如何”，描述的是“生产”联系，也不能硬挂到职工或产品任何一边。

> **易错点**：概念结构设计最常见的坑，不是不会画方块和菱形，而是把联系属性漏掉，或者把本应属于联系的信息全塞给实体。

#### 小系统可以一张图画完，大系统要拆开画

如果系统较小，实体、属性、联系不多，直接画一张完整 ER 图就够了。

系统比较大、涉及很多功能模块时，可以分两步处理。先画一张简化的实体联系图，让所有实体和联系先出现；再把属性和主码补全。较大的系统还可以把整体 ER 图与单独的实体属性图结合起来。

这里不要机械理解成“实体联系图绝对不能有属性”。像主码这种本来就依附于实体的关键信息，可以在第一轮先保留下来。真正的目的，是先让读者看清全局，再补细节，而不是机械地删光所有属性。

主码放在属性都分清以后标出。看到一个属性具有唯一性，就把它确定为主码并加上标记。前面关于主码、候选码的完整规则已经讲过，这里最需要记住的是：主码必须能唯一标识实体。

### ER图怎样拆成二维表

逻辑结构设计的第一个问题是“这张图纸怎么变成表”，第二个问题是“拆出来的表谁当主码”。我把它总结成两个考试挖坑点，后面用几个很小的例子讲明白。

#### 实体直接变成表

实体转换最直接，可以无脑拆：

- 一个实体对应一张表；
- 实体的属性变成表的列；
- 实体的主码变成表的主码。

比如“零件”实体有零件号、零件名，拆表后就得到一张包含这些属性的关系表，其中零件号是主码。材料实体也按同样方式处理。

所以先横着看实体：一个实体一张表，属性就是列，主码就是主码。这一步真正容易出错的地方不在实体，而在联系。

#### 联系先决定表长什么样

把一个联系单独拆成表时，最基本的规则只有一句：

> **联系表由两端实体的主码，加上联系自身的属性组成。**

联系没有属性，就只拿两端主码；联系有“定额”“值勤日”“日期”“数量”等属性，就把这些属性一并放进联系表。如果联系连接三个实体，同样要把三个端点的主码都拿过来，否则就建立不了完整的连接。

联系表长什么样，与它是 1 对 1、1 对多还是多对多无关。基数真正影响的，是这张表由谁当主码。

| 联系类型 | 是否可以单独拆表 | 联系表包含什么 | 联系表主码 | 不拆时怎么合并 |
| :--- | :--- | :--- | :--- | :--- |
| 1 对 1 | 可拆可不拆 | 两端主码 + 联系属性 | 两端主码任选其一 | 合并到任意一端 |
| 1 对多 | 可拆可不拆 | 两端主码 + 联系属性 | 多端，也就是 n 端的主码 | 合并到 n 端 |
| 多对多 | 必须拆 | 两端主码 + 联系属性 | 两端主码共同组成 | 不能直接合并到一端 |

例如，零件和材料之间是 1 对 1 的“消耗”联系，而且联系自身有“定额”属性。拆表时，零件主码、材料主码和定额都要进入联系表。两端主码任选一个作为主码都可以，因为它们本来就是一对一对应。

再比如，一个单位有几辆车，却有很多司机轮班驾驶。汽车和司机是 1 对多关系，“值勤日”属于驾驶联系。若单独拆出联系表，它就包含工号、车号和值勤日，工号是 n 端主码。

多对多必须拆。供应商可以提供多个零件，一个零件也可以由多个供应商提供，“供应”联系即使没有自己的属性，联系表也至少要包含供应商编号和零件号，两端一起组成主码。

#### 主码结论与补数据验算法

联系表的主码可以先记结论：

- 1 对 1：两端主码谁当都行；
- 1 对多：n 端主码当联系表主码；
- 多对多：两端主码共同当主码。

如果一时想不起来，不要死背，补三五行数据就能看出来。

1 对 1 的消耗关系可以补成“1 号零件—1 号材料、2 号零件—2 号材料、3 号零件—3 号材料”。两边都没有重复，所以任选一边都能保证唯一。

1 对多可以补成“1 号车周一由 1 号司机值勤、1 号车周二由 2 号司机值勤、1 号车周三由 3 号司机值勤”。车号重复，工号不重复，所以 n 端的工号当主码。

多对多可以补成“1 号零件—1 号供应商、1 号零件—2 号供应商、2 号零件—1 号供应商、2 号零件—2 号供应商”。两边都出现重复，任何单列都不够，只能让两个端点的主码共同组成主码。

这个方法很笨，却特别稳。不会记规则时，就把三五行数据摆在纸上，找“哪一列单独看没有重复”，主码自然就出现了。

#### 考试可以无脑拆，工作却要衡量效率

如果只追求考试答题正确，实体无脑拆，联系也可以无脑拆，1 对 1、1 对多、多对多统统先拆成表，不会错。

但这个结论只适用于考试。实际系统里，多拆一张表，就多一层表间联系，也会带来更多连接、笛卡尔积和系统缓冲区占用。因此从工作角度出发，能不拆就不拆；多对多关系因为不能直接合并，才必须拆成联系表。

1 对 1 不拆时，可以把另一端的主码和联系属性加到当前表中。零件表与材料表一对一，可以把材料主码加到零件表，也可以反向合并，原来的主码不必因此改变。

1 对多不拆时，应向 n 端合并。汽车与司机是一对多，实际业务关心“哪个司机开哪辆车、哪天值勤”，就可以把车号和值勤日加到司机表，也就是 n 端表中。

多对多不能这样合并。一个零件无法只放在某一个供应商那里，一个供应商也无法只对应一个零件，所以只能老老实实拆出联系表。

> **结论**：考试导向允许“见联系就拆”；工作导向强调“少拆、合并、兼顾效率”，只有多对多必须拆。这个差别不是谁对谁错，而是目标不同。

### 规范化先抓一范式，再看函数依赖

表拆出来以后，不等于逻辑结构就完成了。还要检查候选码、主属性、非主属性以及函数依赖，必要时继续拆分，让关系规范化。

本模块只保留设计时最常用的判断口径，完整范式理论已经在前面讲过。但这几条一定要记住。

#### 一范式不只看表面形状

一范式要求每个单元格都是不可再分的数据项，不能出现表中表、大表套小表。

考试特别爱在这里挖坑，因为表头有时横平竖直，看起来完全规整，语义上却仍然套着表。比如把“所上课程”和“联系电话”拆成“A 课程—联系电话、B 课程—联系电话、C 课程—联系电话”三组列，看起来像三对普通属性，实际上仍然把课程与电话的组合藏在一个单元格里，没有真正做到原子化。

所以判断一范式不能只看列有没有分开，还要问一句：每个单元格表达的到底是不是一个不可再分的数据项？我经常在这一处提醒学生，十个人里九个会凭表头外观下结论。

#### 二范式、三范式与 BCNF

拿到一张表后，先找出候选码。候选码中的属性叫主属性，其他属性叫非主属性。随后检查非主属性对主属性是否存在部分函数依赖、传递函数依赖。

二范式要求消除非主属性对主属性的部分函数依赖。三范式要求继续消除非主属性对主属性的传递函数依赖。BCNF 是三范式中的特殊情况，处理时还要检查主属性内部存在的部分与传递函数依赖问题。

判断时不要凭“列看着挺多”或“主码好像挺大”来猜。真正要做的，是先认清候选码和主属性，再看非主属性究竟依赖哪个属性、依赖的是全部候选码还是其中一部分。

#### 四范式以上先处理多值依赖

1NF、2NF、3NF 和 BCNF 主要处理函数依赖，4NF、5NF 往后更多涉及多值依赖。

一个很实用的原则是：先把多值依赖拆开，让它转化为函数依赖，再按 1NF、2NF、3NF、BCNF 的路线处理。需要升级某个关系时，就沿着“一拆二、二拆三”的方向把不合适的依赖带走。

不过，规范化的具体拆分公式不是这一段要重新展开的内容。这里真正要记住三件事：函数依赖与多值依赖的适用范围、各范式在排除什么、以及拿到表后先找候选码再分析依赖的工作顺序。

### 连接表之后再按需求设计视图

三范式处理完成后，多张表之间还要恢复联系。主码连外码，就是把原本在 ER 图中由联系承担的关系重新落实到表结构中。

例如销售员、产品、仓库被拆成实体表，销售与存储被拆成联系表之后，就要让销售员主码进入销售表的产品主码一侧，让仓库主码、产品主码与存储表对应起来。表没有连接起来，ER 图中的业务关系就不算真正落进数据库。

连接完成后，再根据实际需求设计视图。例如，从学生表、课程表、教师表和选课信息中组合出“哪个学生选了哪门课、哪位教师讲授、得了多少分”；也可以把学生基本情况和考试情况组合成校务处需要的视图。

所以逻辑结构设计可以压缩成一句非常完整的话：

> **拆二维表，规范三范式，连接表，再按需求设计视图。**

### 销售管理信息系统的完整设计

下面用一个销售管理信息系统的例子，把需求分析、ER 图、拆表、规范化与连接连续走一遍。为了把逻辑讲完整，我们不进入“把建表语句敲进数据库软件”的代码阶段，只看数据库结构怎样被一步步设计出来。

#### 从一段业务描述得到 ER 图

这个系统服务于一家公司。原始需求不断提出：能随时查看销售情况，能随时查看产品库存，能随时查看销售员基本信息与产品信息等。

这些自然语言先要整理成数据需求与处理需求。销售情况、产品情况、销售员基本信息和产品信息属于数据需求；汇总分析销售数据、查看库存、更新库存属于处理需求。

分析后，至少可以找出三个实体：

- 销售员；
- 产品；
- 仓库。

实体之间存在两个多对多联系：销售员与产品之间是“销售”联系；产品与仓库之间是“存储”联系。

```text
[销售员：主码为编号] ──N──〈销售〉──M── [产品：主码为产品编号]
                                          │
                                          M
                                        〈存储〉
                                          │
                                          N
                                 [仓库：主码为仓库号]
```

销售员可以销售多个产品，一个产品也可以由多个销售员销售；一个仓库可以存储多个产品，一个产品也可以存放在多个仓库，所以两个联系都是多对多。

完整做法必须继续分配属性。属于销售员、产品、仓库的属性放到三个实体上；属于“销售”和“存储”的属性放到两个菱形联系上。比如后面拆表时会看到的日期、城市、数量属于销售联系，现有库存数量属于存储联系。

考试时，有时题目直接给出整理好的实体、属性和联系，有时只给一段原始描述。无论题目给到哪一步，完整方法都是先从需求中确认实体、属性和联系，再进入 ER 图。

#### 实体表先直接拆出来

按照“实体无脑拆表”的规则，先得到三张实体表：

- 销售员表，以编号为主码；
- 产品表，以产品编号为主码；
- 仓库表，以仓库号为主码。

每个实体的其他属性，按需求材料继续成为相应列。实体转换没有联系表那么复杂，属性、主码与实体一一对应。

#### 销售与存储都必须拆成联系表

“销售”和“存储”都是多对多，所以两张联系表必须拆出来。

销售表取销售员编号、产品编号，再带上销售联系自身的日期、城市和数量。两端都是多的一侧，编号与产品编号共同组成主码。

存储表取仓库号、产品编号，再带上存储联系自身的现有库存数量。仓库号与产品编号共同组成主码。

因此，这个案例的逻辑结构由五张表组成：销售员、产品、仓库、销售、存储。

| 表 | 逐字稿明确给出的结构 | 主码 |
| :--- | :--- | :--- |
| 销售员 | 编号，以及需求给出的销售员属性 | 编号 |
| 产品 | 产品编号，以及需求给出的产品属性 | 产品编号 |
| 仓库 | 仓库号，以及需求给出的仓库属性 | 仓库号 |
| 销售 | 销售员编号、产品编号、日期、城市、数量 | 销售员编号与产品编号共同组成 |
| 存储 | 仓库号、产品编号、现有库存数量 | 仓库号与产品编号共同组成 |

如果记不住多对多的主码，就补数据。例如销售表出现“1 号销售员—1 号产品、1 号销售员—2 号产品、2 号销售员—1 号产品、2 号销售员—2 号产品”，单看哪一列都有重复，只能把两个编号合起来识别一条销售记录。存储表同理。

#### 检查三范式再连接五张表

就本例给出的信息来看，三个实体表不需要继续围绕非主属性拆分。重点要检查的是销售表与存储表。

销售表中的日期、城市和数量不能只由销售员编号单独决定，也不能只由产品编号单独决定，因此不存在这里要检查的部分依赖；同时没有给出传递依赖，所以销售表符合三范式要求。

存储表中的现有库存数量也不能只由仓库号单独决定或只由产品编号单独决定，它描述的是某个仓库中某个产品的库存，因此不存在部分依赖；本例也没有给出传递依赖，所以同样符合三范式要求。

五张表最后通过主码与外码连接起来：销售表连接销售员表和产品表，存储表连接仓库表和产品表。关系恢复以后，数据库的逻辑结构才真正完成。至于如何把五张表创建到具体数据库管理系统里，已经属于实施阶段，不是这组设计题要展开的重点。

### 临场拿到题目时按这条线走

面对一道综合题，不要从某个零散术语开始背，而要顺着设计过程往下走：

1. 从需求里整理数据定义、数据操作和数据控制要求；
2. 圈出实体、联系和属性，先实体、再联系、后属性；
3. 标出主码，完成 ER 图；
4. 实体直接转表，联系按“端点主码 + 联系属性”拆表；
5. 按 1 对 1、1 对多、多对多确定联系表主码；
6. 找候选码、主属性与非主属性，检查部分依赖和传递依赖；
7. 规范到三范式，用外码连接各表；
8. 有实际展示需求时，再设计视图。

整条线里最容易丢分的仍是两处：第一处是概念结构设计时把联系属性漏掉；第二处是逻辑结构设计时不会拆联系表，或者拆完不知道谁当主码。其他环节跟着这条线走，就不容易丢步骤。

### 本讲提到的题目

#### 题目

建设一个图书馆管理数据库。题目给出图书属性、借书人属性和出版社属性，并说明：

- 一个借书人可以借多本书，但一本书只能被一个借书人借；
- 一个出版社可以出版多本书，但一本书仅由一个出版社出版。

要求：

- 画出 ER 图；
- 将 ER 图拆成二维表，规范到三范式，并连接各表。

#### 解析

这道题看着小，却正好同时踩中两个挖坑点。

概念结构设计的坑在属性归属。不能看到题目里列了一堆属性，就全部直接挂到三个实体上，必须先判断每一项究竟描述实体还是描述联系。

逻辑结构设计的坑在联系拆表。“借阅”和“出版”都是 1 对多，可以拆成独立联系表，也可以不拆而向 n 端合并。考试中采用“实体无脑拆、联系无脑拆”的稳妥方案即可；若按工作导向追求少表，则应把联系信息向 n 端合并。

规范化时先找候选码，再区分主属性与非主属性，然后检查非主属性对主属性是否有部分函数依赖或传递函数依赖。

#### 答案

ER 图中先确定三个实体：图书、借书人、出版社。“借阅”连接借书人与图书，比例为 1 对多；“出版”连接出版社与图书，比例也是 1 对多。

```text
[借书人] ──1──〈借阅〉──N── [图书] ──N──〈出版〉──1── [出版社]
```

按照考试中稳妥的拆法，可以得到五张表：

| 表 | 结构 | 主码 |
| :--- | :--- | :--- |
| 借书人 | 借书人主码，以及借书人实体属性 | 借书人主码 |
| 出版社 | 出版社主码，以及出版社实体属性 | 出版社主码 |
| 图书 | 图书主码，以及图书实体属性 | 图书主码 |
| 借阅 | 借书人主码、图书主码、联系自身属性 | 图书主码，即 n 端主码 |
| 出版 | 出版社主码、图书主码、联系自身属性 | 图书主码，即 n 端主码 |

这里的“借书人主码、出版社主码、图书主码”是对原题实体主码的抽象称呼，具体列名与全部属性应按原题给出的字段填写；逐字稿没有念出所有列名，不能凭空补写。

如果采用工作导向的合并方案，则可以不单独保留“借阅”和“出版”表，而把借书人主码、出版社主码及相应联系属性向 n 端“图书”表合并，再检查规范化与连接关系。

这类题在数据库课程以及管理信息系统相关课程里，一般按 15 到 20 分的重要程度考查。题不大，但能把属性归属、ER 图、联系拆表、主码选择、规范化和表间连接串成一条完整链路，恰好就是数据库设计题最有代表性的地方。
