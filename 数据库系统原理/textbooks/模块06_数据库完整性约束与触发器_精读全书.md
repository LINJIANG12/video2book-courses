## 数据库完整性与约束控制体系
> 对应块：BLK14 | 覆盖分集：P12 | 块标题（分集名）：《数据库第5章 数据库完整性（第一部分：实体完整性》

我们在上一章系统讨论了数据库的安全性，这一章进入与之紧密相连的另一个核心维度——数据库的完整性。在数据控制（Data Control Language, DCL）的整体架构中，很多初学者容易将安全性和完整性混为一谈。实际上，这两者在防范目标和语义范畴上有着根本的区别。

安全性防范的是“非法存取”与“不可抗力破坏”，它关注的是主体是否有权进入系统，无论是外部黑客的恶意入侵、未授权用户的数据篡改，还是磁盘损坏等硬件故障，都属于安全性的防护边界。而完整性则专注于数据的“游戏规则”，即数据库中的数据是否合乎现实语义，是否保持正确性与相容性。例如，学生的学号必须全局唯一，性别只能限定在“男”或“女”，年龄必须在合理区间内，选课记录不能关联到一个根本不存在的学生。这些对数据状态与操作逻辑的硬性规范，就是完整性的核心内涵。

为了在工程中有效维持数据完整性，数据库管理系统（DBMS）必须具备三项核心能力：第一，提供定义完整性约束条件的机制（如利用 SQL 规范语言声明规则）；第二，提供高效检查与验证完整性约束的方法；第三，在用户操作触发违约时，提供完备的违约处理机制。

整个完整性体系的构建，本质上源于对现实世界的抽象。现实世界包含三个核心要素：实体、属性以及实体间的联系（Entity-Attribute-Relationship）。映射到关系数据库理论与实践中，恰好构成了三大经典完整性约束：
1. 针对实体的约束——实体完整性（Entity Integrity）；
2. 针对实体间联系的约束——参照完整性（Referential Integrity）；
3. 针对属性本身的业务约束——用户定义完整性（User-defined Integrity）。

在此基础之上，现代数据库还提供了断言（Assertion）与触发器（Trigger）等高级控制手段，用于处理更加复杂、动态的全局规则。

### 实体完整性的语义界定与底层检验机理

#### 核心规则与现实语义

实体完整性所规范的对象是关系模型中的实体。在关系数据库中，现实世界中的一个个具体实体映射为表中的一行行元组，而区分这些实体的唯一标识就是主码（Primary Key）。

> **定义**：实体完整性规则要求关系的主码属性（即主属性）不能取空值（NULL），且主码值必须能够唯一标识一个元组。

这一规则背后的现实意义极为明确。以高校教学管理中最为经典的选课关系 `SC(Sno, Cno, Grade)` 为例，该表记录学生选修课程及考试成绩，其主码由学号 `Sno` 与课程号 `Cno` 联合构成，这两个属性即为主属性。假设系统允许主属性取空值，就会出现以下三种荒谬的数据形态：
1. `(NULL, NULL, 90)`：既不知道是哪位学生，也不知道是哪门课程，凭空记录了一个 90 分，在现实世界中没有任何业务意义；
2. `(NULL, 'C01', 90)`：明确了是 1 号课程考了 90 分，但主考主体缺失，成绩无法落实到具体学生身上；
3. `('S01', NULL, 90)`：明确了 1 号学生考了 90 分，但课程缺失，无法判定该成绩归属哪门学科。

因此，主属性绝不能出现空值，否则关系模型将丧失映射现实实体的基础能力。

#### SQL 语法定义与工程编码规范

在 SQL 中，实体完整性主要通过定义主码来实现。主码的声明有两种语法形式：列级定义与表级定义。

当主码仅由单一属性构成时，既可以在属性定义后直接跟上 `PRIMARY KEY` 关键字（列级约束），也可以在所有属性列定义完毕后，在表末尾通过 `PRIMARY KEY (属性名)` 声明（表级约束）。然而，当主码是由两个或两个以上属性组成的复合主码（如选课表中的学号与课程号）时，语法上**严禁**在每个属性后分别写 `PRIMARY KEY`，而**只能**作为表级约束在最后统一声明：

```sql
CREATE TABLE SC (
    Sno     CHAR(9) NOT NULL,
    Cno     CHAR(4) NOT NULL,
    Grade   SMALLINT,
    PRIMARY KEY (Sno, Cno)  -- 复合主码只能采用表级定义
);
```

> **提示**：在实际工程编码中，强烈建议无论单属性主码还是复合主码，一律采用表级约束写法置于表定义的末尾。单列后仅保留该列专属的数据类型与列级限制，将针对整张表的主码、外码及联合校验统一归拢到底部。这样不仅版面结构层次分明，更能杜绝语法混淆。

此外，一旦某一列或列组合被声明为 `PRIMARY KEY`，DBMS 会自动为其施加非空且唯一（`NOT NULL UNIQUE`）的双重限制，无需也不必再冗余声明。

#### 检查机制：全表扫描与 B+ 树索引比对

实体完整性的违约检查由 DBMS 内核自动触发，虽然在日常业务开发中无需手动编写底层检查逻辑，但理解其内部运行机制对于把握系统性能至关重要。

当应用层向表中插入新记录或更新主码列时，系统需要完成两项检查：非空检查与唯一性检查。非空检查非常直接，仅需判定主属性的输入值是否为 NULL 即可；而唯一性检查则必须确认新输入的主码值是否已在现有数据集中存在。

实现唯一性验证最朴素的算法是全表扫描（Table Scan）。假设当前表中有 100 条记录，当待插入元组到达时，系统必须从第一行开始逐行比对主码：
- 运气最好时，第 1 次比对即发现重复值；
- 运气最差或完全不重复时，必须比对完全部 100 行。

$$E = \frac{1 + 100}{2} = 50.5$$

平均每次插入都需要进行约 50 次的比对操作。随着表规模扩展到百万级或千万级，全表扫描的时间复杂度将导致插入与更新性能断崖式下跌。

为了消除全表扫描的巨大开销，现代关系数据库普遍在主码列上自动构建索引，对于连续型或顺序数值型数据，最常用的便是 B+ 树（B+ Tree）索引。B+ 树是一种多路平衡搜索树，其非叶子节点仅存放检索键值与指针，数据记录或行指针全部挂载在叶子节点上，且子树之间严格保持有序。

```text
               [ 51 ]
              /      \
        [ 12 | 30 ]  [ 60 | 78 ]
        /    |    \
    [3, 7] [15,20,25] [30, 41]
```

以该树形结构为例，假设业务层试图插入一条学号为主码、值为 `25` 的新元组，DBMS 利用 B+ 树执行唯一性校验的查找路径如下：
1. 首先与根节点键值 `51` 比较，判定 $25 < 51$，沿着左侧分支指针向下检索；
2. 进入第二层分支节点，与键值 `12` 和 `30` 比较，判定 $12 < 25 < 30$，选择中间分支指针向下检索；
3. 直接定位到底层叶子节点 `[15, 20, 25]`，在当前节点内找到已有值 `25`，立刻判定违反唯一性约束，拒绝插入。

原本在无序全表扫描中可能需要几十甚至上百次的比对，在 B+ 树中仅仅通过 3 次节点检索便完成了精准判定。这也是工业级数据库在建立主码时必须绑定索引的底层原理。

### 参照完整性的关联约束与违约处置策略

#### 核心语义与跨表映射

现实世界中的各类实体并非孤立存在，实体与实体之间存在着普遍的联系（Relationship）。在关系模型中，这种实体间的关联是通过外码（Foreign Key）来表达的。

> **定义**：若关系 $R$ 中的某一个属性组 $F$ 并非 $R$ 的主码，但它与另一个关系 $S$ 的主码 $K$ 相对应，则称 $F$ 为关系 $R$ 的外码，关系 $R$ 称为参照关系（Referencing Relation），关系 $S$ 称为被参照关系（Referenced Relation）。

参照完整性规则要求：外码属性的取值要么为空值（NULL），要么必须等于被参照关系中某个元组的主码值。

在选课系统架构中，选课表 `SC` 充当了连接学生表 `Student` 与课程表 `Course` 的桥梁。`SC` 中的 `Sno` 参照了 `Student` 表的主码 `Sno`，`SC` 中的 `Cno` 参照了 `Course` 表的主码 `Cno`。两个表一旦建立参照约束，数据就形成联动互锁，任何单方面的孤立变更都可能破坏整体一致性。

#### 四种破坏参照完整性的操作推导

当两张表通过外码建立引用后，存在两种实体角色（参照表与被参照表），而对数据产生结构性变更的操作主要有两类（插入/修改元组、删除/修改元组）。两两组合，构成了 4 种破坏参照完整性的典型场景：

```text
+-------------------+--------------------+-------------------------------------------+
| 操作发起表        | 危险操作类型       | 破坏机理分析                              |
+-------------------+--------------------+-------------------------------------------+
| 参照表 (SC)       | 插入新记录         | 录入了一个不存在的学生学号或课程号        |
| 参照表 (SC)       | 修改外码值         | 将已有选课的学号修改为未注册的学生学号    |
| 被参照表 (Student)| 删除已有记录       | 将某学生注销，但选课表中仍残留其选课记录  |
| 被参照表 (Student)| 修改主码值         | 修改了某学生的学号，导致选课表外码指针断裂|
+-------------------+--------------------+-------------------------------------------+
```

这 4 种情况的本质是：参照表中出现了在被参照表中找不到对应主体的“悬空引用”或孤立元组。

#### 违约处理策略与语法落地

当上述违约操作发生时，DBMS 允许系统架构师预先配置三种违约处理策略：

1. **拒绝执行（NO ACTION / RESTRICT）**：
   系统默认的保守防御策略。一旦检测到操作会导致参照完整性破坏，直接抛出异常并回滚当前操作，拒绝执行。
2. **级联操作（CASCADE）**：
   联动变更策略。当被参照表中的主码元组被删除或修改时，系统自动将参照表中所有引用了该主码的元组同步删除或同步更新，做到“要删一起删，要改一起改”。
3. **设为空值（SET NULL）**：
   软性解绑策略。当被参照表中的主码元组被删除或修改时，将参照表中对应的外码属性值全部置为 NULL。

> **提示**：设为空值必须以该外码列允许为 NULL 为前提。如果外码同时又是参照表主码的组成部分（如 `SC` 表中的 `Sno`），则由于实体完整性的强制约束，该列绝对不能取空值，此时便无法采用 `SET NULL` 策略。

`SET NULL` 在现实业务中具有明确的业务语义。例如，学校院系调整撤销了某个专业（专业编号为 12），在删除该专业元组时，系统不能粗暴地把属于该专业的在校学生元组全部级联删除，更合理的业务动作是将学生表中专业号为 12 的学生记录置为 NULL，表示该批学生的“专业待定，等待重新分配”。

在 SQL 语法中，这些策略直接附着在外码定义之后：

```sql
CREATE TABLE SC (
    Sno     CHAR(9) NOT NULL,
    Cno     CHAR(4) NOT NULL,
    Grade   SMALLINT,
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE      -- 当主表删除学生时，级联删除该生的全部选课记录
        ON UPDATE CASCADE,     -- 当主表修改学号时，级联更新选课记录中的学号
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE NO ACTION    -- 课程若有人选修，严禁直接删除该课程
        ON UPDATE CASCADE      -- 课程号若发生变更，级联同步选课表中的课程号
);
```

通过这一套语法规范，我们在建表时就完成了跨表数据联动逻辑的声明式定义，无需在业务应用层编写繁杂的事务拦截代码。

### 用户定义完整性的多维表达与跨属性校验

#### 属性级业务语义限制

在现实抽象中，实体与联系的问题解决后，剩下的便是属性本身。不同的应用场景对数据字段的取值范围有着高度特化的要求，这就是用户定义完整性。用户定义完整性分为两大层次：针对单一属性列的约束，以及针对元组中多个属性关联关系的约束。

在属性列级别，SQL 提供了三种最基础的约束工具：
1. **非空约束（`NOT NULL`）**：强制该属性在每行元组中必须有真实取值，如人员姓名、登记时间等；
2. **唯一约束（`UNIQUE`）**：保证该属性在整张表中不存在重复值，但允许出现 NULL（除非同时声明了 `NOT NULL`），常用于身份证号、邮箱等替代键（Alternate Key）；
3. **检查约束（`CHECK`）**：通过条件表达式限定属性取值范围。

例如，限定学生性别只能在集合 `{'男', '女'}` 中选取，课程学分必须处于 1 到 4 分之间且不得为 0，考试成绩必须位于 0 至 100 分区间。这些均可在列定义后直接声明：

```sql
CREATE TABLE Course (
    Cno     CHAR(4) PRIMARY KEY,
    Cname   VARCHAR(40) NOT NULL UNIQUE,
    Ccredit SMALLINT CHECK (Ccredit BETWEEN 1 AND 4)
);
```

#### 元组级与跨属性关联校验

当约束条件仅涉及单一列时，将其紧贴属性书写是最直观的做法。然而，在诸多复杂的业务场景中，约束规则往往跨越了两个或两个以上的属性列。

> **易错点**：凡是涉及多个属性列相互制约的完整性规则，在逻辑上不再属于某个单一列的属性，而是属于整行元组乃至整张表的全局约束。此类约束**严禁**写在某个列的后方，**必须**作为表级约束后置书写在表定义的末尾。

考虑一个典型的业务校验需求：在学生档案管理中，为了防止经办人员录入失误，系统要求“如果学生性别为男，则其英文称谓（姓名）绝不能以 `Ms.` 开头”。

这一业务规则同时依赖 `Ssex`（性别）与 `Sname`（姓名）两个属性列，其逻辑真值表如下：
- 当 `Ssex = '女'` 时，姓名无论以何种前缀开头均满足规则；
- 当 `Ssex = '男'` 时，姓名必须满足不以 `Ms.` 开头。

在布尔逻辑中，“$P \rightarrow Q$” 等价于 “$
eg P \lor Q$”。因此该规则在 SQL 的 `CHECK` 子句中表达为：

```sql
CREATE TABLE Student (
    Sno     CHAR(9) NOT NULL,
    Sname   VARCHAR(20) NOT NULL,
    Ssex    CHAR(2) NOT NULL,
    Sage    SMALLINT,
    Sdept   VARCHAR(20),
    PRIMARY KEY (Sno),
    CHECK (Ssex = '女' OR Sname NOT LIKE 'Ms.%')  -- 表级约束：跨两列的逻辑校验
);
```

在此处，`LIKE` 模式匹配中的通配符 `%` 表示匹配任意长度的字符序列。这类试题在考试与技术面试中经常出现，因为其在一个小巧的表结构定义中，同时融合了表级约束语法、跨字段布尔逻辑表达以及字符串模糊匹配与转义等多项关键技能。

### 约束命名规范与动态维护机制

#### 约束命名的工程价值

在前面的基础语法中，大多数约束条件是匿名声明的。然而在大型软件系统的全生命周期中，业务规则是不断迭代与演进的。如果所有约束都没有专属名称，后续若要停用、废除或调整某一规则，DBMS 将无法精确定位。

为了规范工程管理，SQL 提供了完整性约束命名子句：

```sql
CONSTRAINT <约束名> <约束条件>
```

约束条件涵盖 `NOT NULL`、`UNIQUE`、`PRIMARY KEY`、`FOREIGN KEY` 以及 `CHECK`。通过为约束赋予显式名称，数据库模式具备了自解释性与极佳的可维护性。

#### 综合案例：教师薪资表建模

我们通过一个实际案例来展示命名子句的标准工业级写法。建立教师薪资表 `Teacher`，业务规则如下：
1. 教师工号为主码，显式命名为 `TeacherKey`；
2. 教师所属系号为外码，关联部门表 `Department`，显式命名为 `TeacherFK`；
3. 教师的应发工资不得低于 30000 元（应发工资为基础工资 `salary` 与扣除项 `deduct` 之和，扣除项以负数形式存储）。

```sql
CREATE TABLE Teacher (
    Tno     CHAR(7),
    Tname   VARCHAR(20) NOT NULL,
    Ttitle  VARCHAR(10),
    Salary  NUMERIC(10, 2),
    Deduct  NUMERIC(10, 2),
    Dno     CHAR(4),
    CONSTRAINT TeacherKey PRIMARY KEY (Tno),
    CONSTRAINT TeacherFK FOREIGN KEY (Dno) REFERENCES Department(Dno),
    CONSTRAINT CheckSalary CHECK (Salary + Deduct >= 30000)
);
```

在此表定义中，`Salary + Deduct >= 30000` 涉及两个属性的数值运算，作为表级约束放置在末尾，并命名为 `CheckSalary`。当财务人员录入数据时，若基础工资填入 30000，扣除项由于五险一金等扣款填入 -2000，计算总和为 28000，系统将立即拦截该操作并明确提示违反了 `CheckSalary` 约束。

#### 动态维护：修改规则的最佳工程姿势

当业务发生变更，需要调整现有约束条件时，通常使用 `ALTER TABLE` 语句。

例如，由于通货膨胀与薪酬体系改革，原有的薪资底线规则需要进行调整，或者之前对学生年龄上限设置了“小于 30 岁”（约束名为 `C3`），现在需要放宽为“小于 40 岁”。

在 SQL 语法中，修改一个已存在的约束往往不是通过 `ALTER CONSTRAINT` 语法就地覆写，而是遵循工程上的“先删后建”模式：

```sql
-- 第一步：删除旧约束
ALTER TABLE Student 
    DROP CONSTRAINT C3;

-- 第二步：增加放宽后的新约束
ALTER TABLE Student 
    ADD CONSTRAINT C3 CHECK (Sage < 40);
```

> **结论**：修改数据库游戏规则最稳妥、最高效的姿势就是“先删再加”。显式命名的价值在此展露无遗——只要知道了约束名 `C3`，一条简洁的 `DROP CONSTRAINT C3` 即可彻底拔除旧规则，无需将复杂的内部表达式再重抄一遍；随后再通过 `ADD CONSTRAINT` 注入新规则，完成了数据控制逻辑的优雅迭代。

#### 综合表结构设计与约束定义题

**题干**：  
请设计一个学生登记表 `Student`，包含学号 `Sno`、姓名 `Sname`、性别 `Ssex`、年龄 `Sage`、所在院系 `Sdept`。要求：
1. 学号为主码，约束命名为 `PK_Student`；
2. 姓名不能为空，约束命名为 `C_Name`；
3. 性别只允许为“男”或“女”，约束命名为 `C_Sex`；
4. 年龄必须小于 30 岁，约束命名为 `C_Age`；
5. 若学生性别为“男”，则其姓名不能以“Ms.”开头，约束命名为 `C_MaleName`。

**参考代码**：

```sql
CREATE TABLE Student (
    Sno     CHAR(9),
    Sname   VARCHAR(20),
    Ssex    CHAR(2),
    Sage    SMALLINT,
    Sdept   VARCHAR(20),
    CONSTRAINT PK_Student PRIMARY KEY (Sno),
    CONSTRAINT C_Name NOT NULL (Sname),
    CONSTRAINT C_Sex CHECK (Ssex IN ('男', '女')),
    CONSTRAINT C_Age CHECK (Sage < 30),
    CONSTRAINT C_MaleName CHECK (Ssex = '女' OR Sname NOT LIKE 'Ms.%')
);
```

**考点解析**：
1. **主码与非空规范**：主码声明为表级约束 `PK_Student`，姓名列级非空声明为 `C_Name`。
2. **集合约束与单列校验**：`Ssex IN ('男', '女')` 利用 `IN` 谓词高效限定离散取值范围，较多个 `OR` 连结更为紧凑规范；年龄校验使用算术比较运算符 `<`。
3. **跨字段联合校验与通配符逻辑**：`C_MaleName` 考查复合布尔表达式。利用等价命题将条件蕴含转换为析取形式 `Ssex = '女' OR Sname NOT LIKE 'Ms.%'`。通配符 `%` 代表任意长度字符匹配，准确封堵了男性数据误填“Ms.”前缀的录入风险。五个考点融于一表，是考查数据定义与完整性约束的核心综合题型。

## 数据库完整性约束的高级控制机制：断言与触发器
> 对应块：BLK15 | 覆盖分集：P13 | 块标题（分集名）：《数据库第5章 数据库完整性（第二部分：断言和触发》

### 数据控制机制的技术演进与层级梯队

在数据库管理系统（DBMS）的三大核心职能——数据定义（DDL）、数据操作（DML）与数据控制（DCL）中，完整性控制与安全性控制共同构成了 DCL 的核心防线。我们在定义数据库结构时，首先接触的是实体完整性、参照完整性以及用户定义的完整性。这些基础完整性约束通过主码（PRIMARY KEY）、外码（FOREIGN KEY）以及列级或表级的 CHECK 子句来落实。

然而，这类基础约束的控制粒度通常被严格局限在单个表内部的一列或几列之间。例如，我们可以用 CHECK 子句限制学生性别只能填“男”或“女”，也可以在教师表内部通过 CHECK 约束两项津贴与基本工资之间的线性关系。但这本质上依然是一种静态、局部的数据校验。

一旦进入真实的业务场景，数据控制的需求就会迅速超出单个表的静态边界：
- 如果教务系统要求“《数据库》这门课程最多只允许 60 名学生选修”，一旦超出就必须拒绝选课操作；
- 如果系统要求“全校每一门课程在任意学期的选课人数都不能超过 60 人”；
- 如果要求“当录入教授工资时，若数值低于 40000 元，系统必须自动将其补齐修正为 40000 元”；
- 如果教务处规定“任课教师修改学生成绩时，只要单次涨幅超过原成绩的 10%，系统就必须自动生成一条审计记录，将变更前后的成绩与学号归档”。

面对第一类和第二类跨越多个表、依赖全局统计或聚集计算的限制，单纯的表级 CHECK 约束无法直接表达；而面对第三类和第四类不仅要拦截数据、更要求系统主动产生副作用（自动赋值修正、写入审计日志表）的业务规则，静态约束机制更是彻底无能为力。

为了满足不同层次的数据控制需求，数据库系统提供了从基础到复杂的阶梯式约束体系：

```text
+---------------------------------------------------------------+
|  触发器 (Trigger)                                              |
|  - 机制：事件-条件-动作 (ECA)                                   |
|  - 能力：主动执行过程、自动修正数值、跨表审计日志                 |
+-------------------------------+-------------------------------+
                                | 升级
+-------------------------------+-------------------------------+
|  断言 (Assertion)                                             |
|  - 机制：全局声明式谓词检查                                    |
|  - 能力：跨多表关联、聚集操作统计、违规操作即时拦截             |
+-------------------------------+-------------------------------+
                                | 升级
+-------------------------------+-------------------------------+
|  基础完整性约束 (Constraints)                                 |
|  - 机制：PRIMARY KEY / FOREIGN KEY / 列级与表级 CHECK           |
|  - 能力：单表局部字段校验、域完整性与参照一致性                 |
+---------------------------------------------------------------+
```

基础约束、断言与触发器并非互相排斥的替代品，而是一个逐级递进、控制粒度由粗到细、执行能力由被动拦截转向主动接管的完整技术体系。

### 断言机制与复杂多表约束

#### 断言的定义格式与执行原理

当完整性约束需要超越单表上下文，涉及多个关系的连接运算或聚集函数（如 `COUNT`、`SUM`、`AVG`）时，SQL 标准引入了断言（Assertion）机制。

> **定义**：断言是数据库中命名的一般性完整性约束，它独立于任何单一基本表而存在。一旦创建，任何对断言所涉及表的数据修改（INSERT、UPDATE、DELETE）都会自动激活数据库系统对断言条件的核查。任何导致断言判定结果不为真（即结果为 FALSE）的数据操作，都会被系统直接拒绝执行并整体回滚。

断言创建的标准语法格式如下：

```sql
CREATE ASSERTION <断言名> CHECK (<条件表达式>);
```

在工程实践中，断言的命名必须具备清晰的自解释性。断言对象往往独立存放于数据库模式的元数据字典中，如果随意命名为无意义的符号，后续维护、日志排查和脚本管理将极其困难。我们通常采用“对象类型_关联表_业务目标_指标”的组合命名法，例如 `ASSE_SC_DATABASE_NUMBER`：前缀 `ASSE` 标识断言，`SC` 标识关联选课表，`DATABASE` 标识针对的课程，`NUMBER` 明确其约束人数指标。

断言括号内部的 CHECK 子句语法与查询语句中的 WHERE 表达式类似，通常包裹着一个完整的 SQL 子查询。系统要求该逻辑表达式的计算结果恒为真。一旦某个事务的数据操作使得该表达式评估为假，数据库管理系统会立即掐断当前操作的执行链路。

#### 单门课程容量约束的断言设计

考虑最典型的选课容量限制场景：要求限制《数据库》这门课程最多只能有 60 名学生选修。

分析该业务需求涉及的数据结构：课程名称属性 `Cname` 存放于课程表 `Course` 中，而实际的学生选课记录与选修关系则存放于选课表 `SC`（包含学号 `Sno` 与课程号 `Cno`）中。这显然是一个涉及两个表的聚集计算问题。我们需要统计选修了《数据库》课程的学生总数，并确保该统计值始终满足 $\le 60$。

该断言的 SQL 定义如下：

```sql
CREATE ASSERTION ASSE_SC_DATABASE_NUMBER
CHECK (
    60 >= (
        SELECT COUNT(*)
        FROM SC, Course
        WHERE SC.Cno = Course.Cno
          AND Course.Cname = '数据库'
    )
);
```

对该语句的执行机理进行深入拆解：
1. **多表连接与筛选**：子查询的 `FROM` 子句引入了 `SC` 和 `Course` 两个基本表。在处理多表关联时，必须无条件优先建立公共外键连接条件 `SC.Cno = Course.Cno`，防止产生无意义的笛卡尔积；在此基础上追加课程名称匹配条件 `Course.Cname = '数据库'`。
2. **聚集统计计算**：通过 `COUNT(*)` 对连接筛选出的记录条数进行汇总统计。
3. **边界判定与拦截**：只要当前选课记录数在 60 以内，`60 >= COUNT(*)` 计算结果始终为真，正常的选课 INSERT 事务平稳提交；当已有 60 名学生选课成功后，第 61 位学生的选课操作一经发起，子查询计算得出的数值为 61，导致外层不等式求值为假，系统直接阻断该 SQL 语句的执行，前端选课系统随之报错拦截。

#### 全局分组与多维复合断言设计

若业务需求进一步泛化为全局性策略：不再局限于某单一具体课程，而是要求“数据库中每一门课程的选课人数都不得超过 60 人”。

由于课程数量是动态的，我们不能针对每一门课单独写死一个查询常量，必须借助 SQL 的分组机制（GROUP BY）与集合量化比较谓词（ALL）。

在只有 `Sno`、`Cno`、`Grade` 的选课表 `SC` 中，要统计每门课的选课人数，核心在于按课程编号 `Cno` 进行数据归类：

```sql
CREATE ASSERTION ASSE_SC_EACH_COURSE_LIMIT
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno
    )
);
```

在这段定义中，子查询的运行逻辑经历了清晰的阶段转换：
- `GROUP BY Cno` 将选课表划分为若干数据子集：1 号课程的所有选课记录归入第一组，2 号课程记录归入第二组，以此类推；
- 聚集函数 `COUNT(*)` 依据 SQL 标准执行规则，在不分组时作用于整个结果集，而在分组场景下则分别独立作用于每一个分组子集；
- 因此，子查询返回的结果不再是一个标量数值，而是一个单列结果集，其中包含了各个课程当前的人数列表（例如 `[30, 20, 50]`）；
- 外部表达式使用 `>= ALL` 集合谓词，其严格语义为：数值 60 必须大于或等于子查询结果集中的每一个元素（即 $\forall x \in \text{Result}, 60 \ge x$）。只要任意一组计算出的人数达到 61，断言条件即告破裂，操作被拒。

在此基础上，若教务管理引入了学期维度，要求“限制每个学期、每一门课的选课人数均不得超过 60 人”，这就构成了多维复合分组。

如果原有选课表结构中缺少学期属性，首先必须通过模式修改语句为表扩展字段：

```sql
ALTER TABLE SC ADD Term DATE NOT NULL;
```

向 `SC` 表追加 `Term` 列后，断言的判定条件扩展为按课程和学期的二维复合分组：

```sql
CREATE ASSERTION ASSE_SC_TERM_COURSE_LIMIT
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno, Term
    )
);
```

此时系统会将数据切分为形如“1号课-第1学期”、“1号课-第2学期”、“2号课-第1学期”的细分网格，并在每个独立网格内统计行数，确保任意学期中任意单门课程的开课容量都不突破 60 人的硬性上限。

#### 断言的删除与系统维护开销

断言作为数据库模式中的独立对象，其销毁操作遵循标准的 DDL 规范：

```sql
DROP ASSERTION <断言名>;
```

例如删除上述每门课容量的断言：

```sql
DROP ASSERTION ASSE_SC_EACH_COURSE_LIMIT;
```

> **注意**：断言虽然具备强大的全局约束能力，但在企业级生产环境中必须极其审慎地使用。断言的机制决定了：只要底层涉及的关系表发生任何插入、删除或更新，DBMS 内核都必须重新计算并核对该断言。当断言内部嵌套了多表连接、分组和聚集操作时，每一次数据吞吐都会引发高昂的计算与锁开销。如果滥用复杂断言，系统的事务吞吐性能将出现严重下滑。

### 触发器的事件驱动架构与核心模型

#### 事件-条件-动作（ECA）模型与服务端驻留

当业务需求从“被动拦截违规数据”转向“根据数据变动自动接管并执行后续业务逻辑”时，系统必须使用触发器（Trigger）。

> **定义**：触发器是预先定义并存储在数据库服务器中的一类由特定数据库事件所驱动的特殊过程。当任何用户对指定的关系表执行增、删、改等操作时，数据库服务器会自动激活并执行相应的触发器逻辑。

与应用层业务代码不同，触发器直接常驻在数据库引擎内部。在典型的前端-应用服务器-数据库三层架构中，把强一致性约束封装在数据库内部的触发器中，能够保证无论数据是从 Web 界面、移动终端、后台脚本还是管理员运维客户端写入，都能在最底层获得一致且毫秒级响应的保障。

触发器的行为机制遵循经典的 ECA（Event-Condition-Action）规则模型：

```text
+-------------------+      匹配触发事件       +---------------------+
|  数据更新事件发生   | ---------------------> |  检查触发条件 WHEN   |
| (INSERT/UPDATE/   |                       | (可省略，省略即为真)  |
|      DELETE)      |                       +----------+----------+
+-------------------+                                  |
                                                       | 条件成立 (TRUE)
                                                       v
                                            +---------------------+
                                            |   执行触发动作体     |
                                            | (Action: 匿名过程块  |
                                            |   或调用存储过程)    |
                                            +---------------------+
```

1. **事件（Event）**：指明在什么时刻、发生什么操作时激活机制（例如在更新成绩单之后）；
2. **条件（Condition）**：通过 `WHEN` 子句指定规则判断逻辑，只有条件计算为真时才推进至动作阶段；若省略 `WHEN`，则事件一旦激活，动作体立即无条件执行；
3. **动作（Action）**：触发条件满足后真正执行的程序体，可以执行一系列复杂的 SQL 数据操作、调用存储过程或进行逻辑赋值。

#### 触发器定义语法与要素解析

SQL 标准中创建触发器的骨架语法如下：

```sql
CREATE TRIGGER <触发器名>
{BEFORE | AFTER} <触发事件> ON <表名>
[REFERENCING {OLD ROW AS <旧行变量> | NEW ROW AS <新行变量> |
              OLD TABLE AS <旧表名> | NEW TABLE AS <新表名>}]
{FOR EACH ROW | FOR EACH STATEMENT}
[WHEN <触发条件>]
<触发动作体>
```

在编写触发器时，必须严格遵守以下底层规则与参数约束：
- **创建权限与归属**：只有基本表的拥有者（或具备相应 DBA 特权的角色）才能在该表上创建触发器。
- **作用对象限制**：触发器只能定义在基本表（Base Table）上，严禁直接定义在视图（View）上。视图本质上是虚表，内部不持久化数据，因此不能挂载事件监听。
- **命名空间约束**：触发器的名称在同一个数据库模式（Schema）下必须是唯一的，且触发器名与其挂载的目标基本表必须处于同一模式空间内。
- **列级触发精度**：默认情况下，`UPDATE ON <表名>` 会监听整张表的任意字段更新。如果只需要针对表的某一个特定列进行监控（例如只在任课老师修改成绩列时告警，修改学生姓名或选课备注时不激活），必须明确声明为 `UPDATE OF <列名> ON <表名>`。这样可以显著压降不必要的无效触发。

#### 内存执行时机辨析与变量容器机制

理解触发器，最核心的难点在于两处：触发时机 `BEFORE/AFTER` 的真实本质，以及变量引用子句 `REFERENCING` 的运行原理。

**内存执行时机的物理边界**

许多学习者容易对 `BEFORE` 产生误解，误以为“操作者还没在键盘上敲完数据，数据库就能提前预知”。这种理解混淆了物理输入与系统内部执行的概念。

所谓的 `BEFORE` 与 `AFTER`，严格以数据库引擎内部的内存更新与数据落盘为基准界限：

```text
客户端输入数据 (如 Score = 95)
      |
      v
到达 DBMS 服务端缓冲区
      |
      +---> [BEFORE 触发器执行] (在内存数据正式写入目标元组前拦截/修改)
      |
      v
执行底层 SQL 引擎更新 (更新内存中的目标数据块)
      |
      +---> [AFTER 触发器执行] (在目标数据已成功修改后执行联动操作)
      |
      v
事务提交并持久化落盘
```

- `BEFORE` 触发器：数据已经传入数据库服务器内存缓冲区，但在系统底层尚未正式修改目标表的元组之前介入。它拥有就地改写待写入数据的能力（例如将输入的过低数值就地补齐）。
- `AFTER` 触发器：底层的修改操作已经在内存中执行完毕，数据状态已完成更迭，此时触发器启动，通常用于记录审计流水或级联更新其他关联表。

**变量捕获容器与状态快照**

当数据发生变更时，若要在逻辑中对比“修改前是多少分，修改后是多少分”，系统必须提供一种能够同时装载新旧状态的机制。`REFERENCING` 子句正是承担这一角色的“数据容器（广义的变量碗）”：
- `OLD ROW AS <变量名>`：定义一个旧行变量，将受影响元组在事件发生前的历史数据接出来；
- `NEW ROW AS <变量名>`：定义一个新行变量，将受影响元组即将或已经写入的新数据接出来。

这两个变量的生命周期与触发动作体绑定，使得开发者能够通过 `<变量名>.<列名>` 的形式同时读取历史快照与当前快照。

#### 行级触发器与语句级触发器的行为差异

依据触发执行的粒度，触发器被划分为行级触发器与语句级触发器两类：

| 触发器类型 | 声明关键字 | 触发频次与行为特征 | 变量引用能力 |
| :--- | :--- | :--- | :--- |
| **行级触发器** | `FOR EACH ROW` | 事务中**每影响一行元组，动作体就执行一次**。例如单条 UPDATE 批量更新了 1000 行记录，行级触发器就会被循环执行 1000 次。 | 能够使用 `OLD ROW` 和 `NEW ROW` 变量逐行读取旧值与新值。 |
| **语句级触发器** | `FOR EACH STATEMENT` | **无论该语句影响了多少行，整个 SQL 语句执行完毕后只触发一次**。更新 1000 行同样只执行 1 次。 | 不能在动作体中使用行级 `OLD/NEW` 变量，仅可引用宏观的数据表级快照。 |

若执行语句 `UPDATE Teacher SET Deptno = 5;`，假定教师表有 1000 行数据：语句级触发器执行完整个修改后仅仅激活 1 次；而行级触发器则会在每一位教师记录更新时都被调用，累计执行 1000 次。工程实现中需根据是否需要逐行判定状态来准确选择触发类型。

### 触发器业务场景实战设计

#### 成绩变更审计日志的行级触发器

在高校教务管理中，针对成绩篡改的防范是一项刚性需求。设计要求：当任课教师修改选课表 `SC` 中的学生成绩（`Grade`）时，若单次给学生的分数涨幅达到或超过了原成绩的 10%，系统必须自动将该操作归档记录到审计表 `SC_U` 中，记录内容包括学号、课程号、修改前旧成绩和修改后新成绩，以供教务部门后续核查。

此场景必须在成绩修改完成之后记录结果，且需要逐行比对每一位同学修改前后的成绩数值，因此采用 `AFTER` 行级触发器：

```sql
CREATE TRIGGER SC_T
AFTER UPDATE OF Grade ON SC
REFERENCING
    OLD ROW AS OldTuple
    NEW ROW AS NewTuple
FOR EACH ROW
WHEN (NewTuple.Grade >= 1.1 * OldTuple.Grade)
INSERT INTO SC_U(Sno, Cno, OldGrade, NewGrade)
VALUES (
    OldTuple.Sno,
    OldTuple.Cno,
    OldTuple.Grade,
    NewTuple.Grade
);
```

**设计机理与参数拆解**：
1. **精确监听**：`AFTER UPDATE OF Grade ON SC` 明确限定了只监听选课表成绩列的修改事件，避免修改其他列时产生无意义开销。
2. **变量接值**：通过 `REFERENCING` 声明了两个行级变量元组：`OldTuple` 负责把变更前学生的原有记录（学号、课程号、旧成绩）装入容器，`NewTuple` 负责把录入的新记录装入容器。
3. **条件过滤**：`WHEN (NewTuple.Grade >= 1.1 * OldTuple.Grade)` 在动作体执行前就地完成浮动比例计算。只有涨幅大于等于 10% 的异动数据才会进入下游动作体，正常范围的微调直接放行。
4. **动作落地**：动作体通过标准的 `INSERT INTO ... VALUES` 语句，从 `OldTuple` 和 `NewTuple` 容器中精准抽取字段，写入审计日志表。

此业务需求之所以无法用 CHECK 或断言解决，是因为 CHECK 只能做单表内部字段的静态布尔判断，而断言即使判断出成绩异动，也仅仅只能执行“报错并拒绝更新”，无法完成“既允许更新、又自动派生跨表归档数据”的主动任务。

#### 批量数据插入统计的语句级触发器

考虑日志统计场景：当系统向学生表 `Student` 执行批量导入或插入操作时，要求在一条语句执行完毕后，将本次批量操作实际新增加的学生总人数记录到日志表 `insert_log` 中。

由于这里关注的是整条插入语句的总体吞吐结果，不需要针对每一个学生重复记录单行日志，因此采用语句级触发器配合新表容器：

```sql
CREATE TRIGGER Student_Insert_Log
AFTER INSERT ON Student
REFERENCING
    NEW TABLE AS delta
FOR EACH STATEMENT
INSERT INTO insert_log(Insert_Count)
SELECT COUNT(*) FROM delta;
```

**设计机理与参数拆解**：
1. **表级容器**：此时 `REFERENCING` 后方声明的不是单一元组，而是 `NEW TABLE AS delta`。系统将本次 INSERT 语句所成功插入的所有新元组打包汇聚成一张名为 `delta` 的临时过渡表（过渡表内装载了本次新增的数据集）。
2. **单次触发**：`FOR EACH STATEMENT` 确保整条导入 SQL 执行完毕后，动作体仅被调用一次。
3. **批量计数**：动作体通过子查询 `SELECT COUNT(*) FROM delta` 直接从过渡表中统计出本次新增元组的绝对数量，写入日志表。如果第一次批量插入了 20 条，日志记录 20；第二次插入了 10 条，日志记录 10。

#### 业务数值自动修正的内存前置触发器

考虑薪酬底线兜底场景：为教师表 `Teacher` 定义完整性约束，要求全校教授的工资底线不得低于 40000 元；在录入或更新教师数据时，如果发现录入的职称是“教授”且工资低于 40000 元，系统不得直接抛错崩溃，而必须自动将其在内存中静默修正为 40000 元后再行存盘。

该需求要求在数据正式写入数据库之前改写数值，必须使用 `BEFORE` 行级触发器：

```sql
CREATE TRIGGER Insert_Or_Update_Salary
BEFORE INSERT OR UPDATE ON Teacher
FOR EACH ROW
BEGIN
    IF new.job = '教授' AND new.salary < 40000 THEN
        new.salary := 40000;
    END IF;
END;
```

**设计机理与参数拆解**：
1. **前置拦截**：声明为 `BEFORE INSERT OR UPDATE ON Teacher`，确保触发器在内存数据尚未完成最终更新写入之前执行。
2. **无需新旧比对**：本例只需关注即将写入的新数据是否合规，不需要与历史旧工资作差值比较，因此无需声明复杂的 `REFERENCING` 语句，直接使用系统内置的 `new` 变量即可。
3. **过程块就地赋值**：在 `BEGIN ... END` 过程块中，利用 `IF-THEN` 控制语句进行联合判断。一旦满足条件，通过赋值运算符 `:=` 直接修改 `new.salary` 变量的值。由于此时仍处于 `BEFORE` 阶段，内存中修改后的 40000 元会顺理成章地作为最终数据存入数据表中。

如果使用 CHECK 约束（如 `CHECK(salary >= 40000)`）或断言，系统只能在数值违规时中断事务并报错，无法实现“自动干预修正”这一高度智能化的控制逻辑。

### 触发器的执行序列与生命周期维护

#### 复合触发器的执行时序

在大型业务系统中，一张核心业务表上往往同时挂载了多个不同类型、不同阶段的触发器，甚至存在级联触发的情况。当某条数据更新语句命中多重规则时，数据库引擎内部遵循严格的分层处理管道：

```text
[ 用户提交 SQL 更新请求 ]
           |
           v
  1. 执行该表上的 BEFORE 触发器 (依次处理输入过滤、数据清洗与自动修正)
           |
           v
  2. 执行 SQL 语句本身的底层操作与标准完整性检查 (更新内存数据块、核查主外键)
           |
           v
  3. 执行该表上的 AFTER 触发器 (执行业务联动、跨表审计、级联记录写入)
           |
           v
[ 事务完成，正式持久化提交 ]
```

这一标准流水线清晰地表明：`BEFORE` 触发器优先于底层 SQL 操作执行，负责为数据写入扫清障碍或修正数值；而 `AFTER` 触发器必须在数据操作已在当前事务上下文中生效后才执行，确保联动操作所看到的是已经完成修改的最新现实。

> **结论**：如果触发动作体在执行过程中发生严重异常或底层报错，触发事件会立刻被强制终止。当前事务将自动回滚，触发器的目标表以及所有级联影响的关联对象都不会保留任何修改。

#### 触发器的删除与重构原则

触发器属于已持久化的模式对象，删除语法如下：

```sql
DROP TRIGGER <触发器名> ON <表名>;
```

例如删除前文创建的学生表日志触发器：

```sql
DROP TRIGGER Student_Insert_Log ON Student;
```

执行删除必须确保该触发器已真实存在于数据字典中，且当前连接用户拥有对该表的控制权限。

> **提示**：在 SQL 语法体系中，我们常见 `CREATE`、`ALTER`、`DROP` 三件套，但对于触发器，标准语法中通常并不提供 `ALTER TRIGGER`。这是因为触发器的内部结构高度复杂，包含事件定义、触发级别、引用变量、过滤谓词以及内部过程块，局部修改极易引发隐蔽的逻辑冲突。在工程实践中，修改触发器的规范动作是一律先执行 `DROP TRIGGER` 彻底销毁，再重新编写并执行 `CREATE TRIGGER` 进行重建。此外，由于不同商业 DBMS（如 Oracle、SQL Server、MySQL、PostgreSQL、Kingbase）在触发器扩展语法与过程语言（PL/SQL、T-SQL）上存在局部方言差异，实际开发中需结合具体厂商手册进行工程适配。

#### 数据控制语言（DCL）的完整控制体系

至此，由基础约束、断言与触发器构筑的数据库完整性控制拼图完整闭合。结合前面所学的数据定义（DDL）与数据操作（DML），现代数据库管理系统的完整能力骨架可以清晰总结为：

```text
                               数据库系统 (DBMS)
                                      |
         +----------------------------+----------------------------+
         |                                                         |
   数据定义 (DDL)                                             数据控制 (DCL)
   - CREATE / ALTER / DROP                                         |
         |                                  +----------------------+----------------------+
   数据操作 (DML)                           |                                             |
   - INSERT / UPDATE / DELETE / SELECT  数据完整性控制                                数据安全性控制
                                            |                                             |
                   +------------------------+------------------------+             GRANT / REVOKE
                   |                                                 |
             声明式约束与断言                                 事件驱动触发器
             - 基础约束：实体/参照/CHECK (单表局部)            - 行级/语句级 (FOR EACH ROW/STATEMENT)
             - 断言：CREATE ASSERTION (跨表全局聚集)          - 触发时机：BEFORE / AFTER
                                                              - 核心能力：ECA 模型、自动修复、审计归档
```

在工程架构中评估业务约束的落地策略时，应当遵循“能用基础约束绝不用断言，能用断言阻断绝不用触发器”的性能优先原则：
1. 单表内部的空值控制、取值范围、离散枚举，坚定使用 PRIMARY KEY、FOREIGN KEY 与 CHECK；
2. 跨表的数据容量、全局配额、多表联合静态统计约束，使用 CREATE ASSERTION 统一定义；
3. 需要根据输入数据动态改变目标值、需要记录详细变更流水、或需要跨表联动派生业务动作的场景，果断采用 CREATE TRIGGER 接管控制。
