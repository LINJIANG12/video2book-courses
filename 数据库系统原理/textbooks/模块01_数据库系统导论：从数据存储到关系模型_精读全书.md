## IT 基础设施从哪里来，又靠什么往前走
> 对应块：BLK01 | 覆盖分集：P01上 | 块标题（分集名）：《数据库系统课程前导内容一：大IT行业总览》

在钻进数据库的具体技术之前，我们先要把 IT 放回它所处的经济与历史背景中。

看一个组织、一个企业，甚至一个国家过去和现在正在发生什么，最直观的方式之一，就是把数据变成可见的曲线。对照主要经济体的变化，我们能看到中国的发展速度、IT 行业在其中所处的位置，也能更清楚地理解：技术发展不是孤立发生的，它和产业进步、制度变化、工程能力的积累紧紧连在一起。

但这些曲线最终不是为了让我们记住一个预测年份，而是为了帮助我们建立一种判断方式：看见趋势，知道它的来路，也知道趋势背后的机制。

### 先把中国经济发展的位置看清楚

从 1988 年开始看主要经济体的 GDP 变化，中国的增长曲线十分醒目。之所以从 1988 年起画，只是因为那是我的出生年份；更重要的是，1988 年之后，中国真正开始发生明显变化。改革开放在 1978 年已经启动，而图中的变化主要出现在更晚的阶段。

曲线中有两个明显的增长节点。一个是 2001 年前后，中国加入 WTO；另一个是 2008 年前后，北京奥运会开幕。向后做线性外推，曲线给出的交汇时间大约在 2027—2028 年：中国可能在 GDP 总量上追平美国，并在此后超过它。

> **注意**：这只能是依据历史数据作出的线性外推，不是确定预言。新冠疫情这类冲击、地区冲突等极端情况，都不在一条简单直线里。技术发展、经济环境与国际关系的共同作用，是无法靠外推替代的。

如果把时间拉得更长，看到的就不只是最近几十年的增长，而是一条中国与欧美国家国运线的起伏。工业革命之后，中国一度落后并闭关，欧美国家的国运线上升；中国共产党成立以后，中国开始缓慢回升。改革开放又带来了新的增长动力，于是两条曲线的斜率都发生了变化。

线性外推所提示的第二次交集，意味着中国在主要经济体中的上升周期可能与欧美国家的相对下行周期交错。对个人而言，这提供了观察时代的机会；但两条国运线相交时，历史很少平稳过渡。我们既要看到可能的光明阶段，也要为光明之前的阵痛做好心理准备。

GDP 总量之外，平均 GDP、城镇化率、出口水平等指标，也能帮助我们避免只看一条曲线。其中，平均寿命特别值得留意：它能反映一个国家的 GDP 成果是否真正“瓷实”地落到了人民的日常生活中。北京地区的平均寿命已经约为 86 岁，与世界主要经济体的预期平均寿命大致相当。这个例子说明，经济增长最终应当落实为人的真实生活改善。

这些曲线背后，是无数行业、无数工作人员的日常劳动。我们不能说哪个行业更重要、哪个行业贡献更高；不同领域各有其作用。IT 行业在过去二十年的增长中贡献很大，未来也会是继续拉开与其他主要经济体差距的重要一环。但重要的不是抬高某一个行业，而是理解产业之间怎样共同作用。

### 大 IT 不是一个行业，而是一组相互咬合的赛道

大 IT 行业的结构远比“做互联网”复杂。它至少包括硬件设备、操作系统、应用软件、数据库与云服务、网络通信、互联网平台，以及面向组织的 IT 基础设施咨询与集成服务。

| 赛道 | 国内代表 | 国外及其他地区代表 |
| :--- | :--- | :--- |
| 硬件设备 | Acer／华硕、联想、华为、小米 | 戴尔、IBM、惠普、Apple |
| 台式机与笔记本操作系统 | 红旗 Linux、华为鸿蒙 | Windows、Linux、Unix、macOS |
| 移动设备与操作系统 | 安卓生态、鸿蒙等 | iOS；设备中也会使用 Chrome 等浏览器 |
| 应用软件 | 用友、浪潮、华为及国内软件公司 | SAP、Oracle、IBM |
| 数据库与云服务 | 移动、联通、电信，阿里、百度、浪潮等 | SQL Server、MySQL、Hadoop |
| 网络通信 | 华为、中兴、大唐、移动、联通、电信 | 思科、阿尔卡特-朗讯、AT&T |
| 互联网平台 | 腾讯、京东、阿里、美团等 | 微软等平台型企业 |
| IT 基础设施咨询与集成 | 华为、普天、移动、电信等 | IBM、惠普、Accenture（埃森哲） |

日常使用的 Windows 和 macOS 占有较大比例，但操作系统远不止电脑上的那几类。手机、平板、可穿戴设备同样需要操作系统；而数据库、云服务、网络传输和平台业务，则构成数据被生产、存储、处理与传播的其他关键层次。

咨询与集成服务容易被忽略，但它连接着设备、软件和网络。例如，一个组织要设计自己的 IT 基础设施，就需要供应商提供一站式方案，而不只是卖几台设备。学校里的网络基础设施架构与运营商服务，也可以由移动公司整体提供。

把这些赛道放在一起看，可以看到中国在绝大多数方向上已经进入第一梯队：有些领域是明显领先，例如网络通信；还有一些领域是“隐形冠军”——技术能力世界级，但因为没有大规模商业化，公众往往不熟悉。

操作系统就是一个典型例子。外界熟悉的 Windows、macOS、安卓和 iOS 是已经商业化的操作系统，并不意味着我们没有同等级的技术能力。红旗 Linux 从技术角度看具有世界级水平；华为鸿蒙则是面向手表、手机、平板和电脑的全平台操作系统。

> **提示**：判断一个国家、一个企业的技术位置，不能只看它拥有多少面向普通消费者的品牌。操作系统涉及的不只是个人产品，还包括政府、军队、军工等大量关键部门。能否在这些场景中使用，直接关系到技术的自主性与可控性。

### 移动通信：从缺席到并进，再到引领标准

通信标准的变化，最能体现一条技术赛道怎样通过长期投入实现追赶。

在 1G、2G 阶段，中国基本没有参与主流技术标准。3G 阶段，欧洲标准成为中国联通“沃 3G”所采用的技术，美国标准成为中国电信运营 CDMA2000 时使用的标准。与此同时，大唐、中国移动、普天、中兴等共同推动 TD-SCDMA，使 3G 出现了三套主流标准并存的局面。

到了 4G，TD-LTE 与国外主导的 FDD-LTE 成为两套重要技术标准。TD-LTE 至今仍出现在许多人的移动网络使用经历中。再到 5G，两个系统走向融合，TD 技术在其中占据了 65% 以上的技术标准份额。

这条线并不是突然出现的“奇迹”，而是一个技术本土创新的典型过程：从某个年代切入细分市场，持续演化，最终形成世界领先的标准。

### 半导体：六个赛道中的位置与瓶颈

如果说网络通信是中国大 IT 中可以明确说“没有争议地领先”的部分，那么半导体就是一个值得认真面对相对短板的部分。

芯片并不是单一产品。个人设备里有存储芯片，也有负责操作、运行与数据处理的计算芯片。我们平常使用的 Core i5、Core i7 等 Intel 处理器，就是计算芯片的例子。芯片之所以是 IT 行业的绝对基础，是因为从设备运行到数据处理，都绕不开它。

当前需要正视的是，高端芯片领域存在被“卡脖子”的情况：一些设备不能引入，一些芯片造不出来。光刻机等设备为什么受到限制，处在哪些具体环节，又应该如何应对，是后续需要拆解的问题。

芯片行业整体有六个主要细分赛道，其中三个已经出现中国公司的身影。

| 细分赛道 | 国外主要公司 | 中国公司的位置 |
| :--- | :--- | :--- |
| 芯片设计 | 高通、博通、英伟达、联发科、苹果、AMD | 海思半导体、紫光展锐已进入世界前十，但合计营收与头部企业仍有明显差距 |
| 芯片代工制造 | 台积电、格罗方德、联电、三星等 | 中芯国际、华虹半导体已进入第一梯队，但营收与市场占有率仍较低 |
| 封装测试 | 国际主流企业占据前列 | 长电科技、华天科技、富通微电等已参与，中国与主流水平的差距相对较小 |

台积电的突出位置尤其直观：图示数据中，其市场占有率约为 57.8%，超过一半。设计与制造两个核心环节的领先企业，仍主要在高通、英伟达、博通、台积电等公司手中。中国的参与已经不再是空白，但追赶仍然需要具体落到设计和制造能力上。

### 从算盘到计算机：机器怎样开始替人计算

我们今天使用的计算机工具，其开端可以追溯到算盘。

为什么算盘也是计算机？因为人类需要扩展自己的计算能力，而算盘确实完成了“输入—处理—输出”的过程。以“三下五除二”为例，人给出口诀，算盘完成运算，再显示出结果。一个机械的、不必全部依赖心算的过程，本质上就是对计算能力的外延。

接下来，计算机的发展逐步从人力推动，转向借用外部能量。1642 年，帕斯卡计算机尝试借助机械方式推动计算；1679 年，莱布尼茨发明二进制；楚泽的 Z1 计算机又首次尝试以电力推动计算。

1946 年的 ENIAC 是专用计算机，最初服务于战争中的炮弹路径计算。所谓“专用”，意味着它围绕特定任务而设计。1949 年的 EDVAC 则迈向通用计算机：不论输入的是加法、乘法还是别的计算任务，只要给它输入，它就计算并输出结果。

> **易错点**：专用与通用的区别不在于“能不能计算”，而在于计算任务是否被限定在特定用途上。通用计算机出现以后，人们才有了一个可承载多类任务的统一计算平台。再理解量子计算机时，也应当回到“专用还是通用”这个坐标，而不只是看它是不是先进的计算机。

半导体技术推进之后，晶体管和集成电路的发展把通用计算能力推向新的阶段。1957 年，仙童半导体公司成立；许多后来深刻影响硅谷的公司的创始人或早期成员，都曾在仙童体系工作过或创业。它因此成为理解硅谷技术谱系的重要节点。

随后，COBOL 语言、IBM 的大型机与相关操作语言、BASIC、Intel 的芯片、微软的系统以及个人电脑的发展相继展开。1985 年前后的 Windows 1.0 是其中的关键节点。2007 年智能手机出现，2008 年安卓系统与中国 3G 发展又成为新的节点；“九章”量子计算机与 2021 年推出的鸿蒙，则把这条历史线索重新带回中国前沿。

如果用红色标记与中国相关的节点、蓝色标记与中国无关的节点，就会看到：开端有中国，中间大量关键推进来自欧美与日韩，今天的前沿又出现中国。这不是简单的“封闭—开放—追赶”叙事，而是可以看到国运起伏在技术史中留下的痕迹。

### 八卦、二进制与 ASCII：人和计算机如何说话

二进制为什么可以放在这条与中国有关的历史线上？

莱布尼茨发明二进制时，从《伏羲六十四卦次序图》和《伏羲六十四卦方位图》中的八卦得到启发。把长横线看作 1、短横线看作 0，一个卦位就有 0、1 两种状态。三个卦位组合时，状态总数是：

$$2^3=8$$

这正好对应八卦的八种组合。八卦在这里提供了重要的思想启发，二进制则最终成为人与计算机之间的基础语言。

计算机无法直接理解中文或英文，它能感知的是通电与不通电。在课程的底层抽象中，一个晶体管可以对应 1 或 0，一个比特也正是这种二进制状态。八比特组成一个字节，能够表示 $2^8=256$ 种不同的位模式。

```text
人类信息
   │
   ▼
统一的二进制编码
   │
   ▼
晶体管组成的比特与字节
   │
   ▼
计算机可处理的 0 与 1
```

读图方式很简单：人类先把信息编码为统一的 0、1，再交给由晶体管构成的计算机体系处理。英语是人和人沟通时的基础符号体系，二进制则是人和计算机沟通时的基础符号体系。

ASCII 就是把这两端接起来的标准之一。它是 American Standard Code for Information Interchange，即美国标准信息交换代码。大写英文字母 `A` 的编码是：

$$0100\ 0001$$

高四位是 `0100`，低四位是 `0001`；如果把八位从左到右编号，第二位和第八位通电，其余位不通电，就得到这个编码。英文字母、数字和标点符号，都可以按统一的 ASCII 规则转换为八位二进制。

> **易错点**：四个晶体管对应四个二进制位，能够表示的状态数是 $2^4=16$，不是 $2^{16}$。状态数量随位数指数增长，这正是晶体管数量如此重要的原因。

标准为什么重要？假如苹果、华为、IBM 的设备各自采用一套不同的编码规则，那么一台设备写出的文档到了另一台设备上，底层的 0、1 就不再按同样的意义解释，文件呈现出来的东西也就可能完全不同。技术标准就像大家使用同一本教材；只有共同语言稳定，设备之间才能可靠交换信息。

### 把同一段历史拆成三条技术线

把历史重新放到“存储、处理、传输”三条线上，会得到更清楚的 IT 基础设施图景。

| 技术线 | 早期与中间发展 | 走向前沿 |
| :--- | :--- | :--- |
| 存储 | 中国的甲骨文、竹简、造纸；国外发展关系数据库 | 中国在云计算与分布式存储方面处于领先位置 |
| 处理 | 中国的算盘与二进制启发；帕斯卡计算机、Z1、香农、图灵、ENIAC、EDVAC，以及欧美日韩的半导体与计算机企业 | 云计算、分布式处理、全平台鸿蒙与“九章”量子计算机，中国又回到前沿 |
| 传输 | 长城箭楼、烽火台；摩斯密码、互联网、电磁波等主要由国外推动的技术 | 新一代 3G、4G、5G 移动通信，中国重新取得领先 |

这三条线的共同节奏是：

```text
中国起点
    │
    ▼
世界范围的技术发展
    │
    ▼
中国回到前沿竞争位置
```

读图时不要把它误读为“只有中国发明过计算机技术”。它要说明的是：不同技术线在不同历史时期的主导力量会变化，国运的起伏也会在行业中留下痕迹。

其中，烽火台为什么可以算数据传输？因为点烟与不点烟正好对应 1 与 0；无论是烽火、摩斯密码，还是后续的电磁波和移动通信，人与机器之间都在寻找更高效、更远距离的信息传递方式。

### IT 基础设施为什么能持续向前

理解了历史之后，还要继续追问：推动这一切的机制是什么？

对各专业同学来说，这件事不仅关系技术，也关系职业选择。本科专业大多是一种工具：计算机、HR、Finance、Accounting 都在解决特定问题。工具要在什么情境中使用，决定了它的价值。同样做人力资源，在互联网企业与传统企业中的发展空间和收入就可能不同。理解 IT 的目的，不是要求所有人转行做技术，而是要学会把专业放进产业与技术环境中判断。

这也是管理信息系统课程要同时传达的三层内容：具体知识、判断行业的思维范式，以及跨学科的思维体系。内容只是表面，能否形成自己的判断方法更重要。

在这套教材大约第 141 页的部分，摩尔定律是解释 IT 基础设施持续进步的第一个关键动因。

### 摩尔定律：不是自然定律，而是行业观察

1965 年，戈登·摩尔根据芯片产业的发展，对集成元件数量的增长规律作了总结。最初他观察到元件数量大约每年翻一番，后来又表述为每两年翻一番，最终形成了广为流传的“每 18 个月翻一番”的说法。

摩尔定律常见的三种表述是：

- 微处理器的处理能力每 18 个月翻一番。
- 计算机的计算能力每 18 个月翻一番。
- 获得同等计算能力所需的成本每 18 个月下降一半。

这三种说法指向同一个趋势。微处理器的处理能力依赖芯片；假设今天用一万元可以买到某一级别的内存或计算能力，18 个月后用同样的一万元能够买到更高一级的配置，那么换一种表达方式，就可以说获得同等能力的成本下降了一半。

晶体管数量和每秒执行的指令数呈现出指数增长，而单位货币能买到的计算能力持续上升，这正是“翻倍”与“成本下降”在图上的表现。

> **定义**：摩尔定律与万有引力定律、热力学定律不同。它不是对宇宙客观规律的无条件描述，而是戈登·摩尔根据行业长期观察总结出的经验规律。它有适用范围，也应当被当作会受技术路径影响的经验事实，而不是永远不能改变的物理常数。

### 芯片能力从哪里来：晶体管数量

晶体管是芯片最底层的核心。晶体管由硅这样的半导体材料制成。硅既可以在特定条件下导电，也可以阻断电流；在课程的简化表达里，可以把它对应为通电的 1 与不通电的 0。

因此，芯片中最重要的底层指标之一，就是有限空间内能放多少个晶体管。

```text
有限芯片空间
     │
     ├── 晶体管更多 ──► 可表示的二进制状态更多
     │
     └── 晶体管更小 ──► 同一空间可以容纳更多晶体管
```

如果有 $n$ 个晶体管，每个都可以取 0 或 1，那么理论上的状态组合数是 $2^n$。四个晶体管是 16 种状态；图中讲到的一颗现代芯片有接近 20 亿个晶体管，对应的状态组合就是 $2^{20亿}$。这个例子不是说机器会同时处理每一种状态，而是说明可编码的状态空间会随晶体管数量呈指数扩张。

要让有限空间容纳更多晶体管，主要要继续推进两件事：一是改善材料与相关工艺；二是把晶体管做得越来越小。材料进步与尺寸缩小彼此相通，材料特性更合适、制造工艺更精细，晶体管就可能做得更小、集成得更多。

课程中用纳米管作示意：一万根纳米管束在一起的横截面，大约相当于一根人类头发的粗细。芯片通常只有指甲盖大小，却能集成极多的晶体管，背后正是材料学、工程手艺和相关学科长期进步的结果。

摩尔并不是凭空发现了这个趋势。他观察到的是：工程做得越久，工艺越精细；材料学不断进步；集成电路在有限空间里容纳晶体管的能力大约每 18 个月翻一番。最终反映到外界，就是计算芯片能力的增长。

### 芯片能力从哪里来：电路把状态变成计算

晶体管再多，如果只是孤立地排列为一堆 0 和 1，也不能自动形成计算能力。晶体管必须通过电路连接，按照与、或、非等逻辑结构协同工作。

例如：

- 在与逻辑中，1 与 0 的输出为 0。
- 在或逻辑中，0 与 0 的输出为 1。

```text
晶体管：提供 0 / 1 状态
            │
            ▼
逻辑电路：与、或、非等结构组合状态
            │
            ▼
运算能力：加、减、乘、除
            │
            ▼
更高级的运算：线性代数、微积分、概率与数理统计
```

读图方式是从下往上理解计算能力的形成：晶体管提供状态，逻辑结构组织状态，电路把基本运算进一步组合起来。芯片的计算能力因此建立在两个相辅相成的条件上：有限空间内晶体管的数量，以及连接晶体管的电路设计。

摩尔定律解释的是提升速度；晶体管与电路则解释了这个速度最终如何变成真实的计算能力。也正是在这个意义上，IT 基础设施不是几个热门产品堆起来的，而是材料、物理、工程、逻辑与计算不断共同演进的结果。

> **承前启后**：上一节讲完「IT 基础设施从哪里来，又靠什么往前走」，下一节接着讲「算力曲线走到尽头之后：摩尔定律、云与量子计算」。

## 算力曲线走到尽头之后：摩尔定律、云与量子计算
> 对应块：BLK02 | 覆盖分集：P01下 | 块标题（分集名）：《数据库系统课程前导内容一：大IT行业总览》

先把一个容易被忽略的事实摆到桌面上：今天一块很小的芯片里，可以放进去几十亿个晶体管；一根头发丝的尺度，大约可以容纳一万个纳米管。晶体管的数量在增加，线路的排布也在变得越来越精细、越来越科学。把这两件事叠在一起，才有了我们熟悉的摩尔定律。

所以，摩尔定律不是凭空冒出来的一条神秘曲线。它首先是一个结果：芯片工艺和电路设计共同进步之后，计算机大约每 18 个月就能获得一次明显的能力提升。理解摩尔定律，不能只背“18 个月翻倍”，还要问一句：人类究竟靠什么，让这条曲线一直往上走？

### 摩尔定律背后的两股力量

第一条力量是材料与制造工艺的进步。我们从粗糙的电子器件，走到了纳米管级别的精细结构；一块小芯片里容纳的晶体管，从几百万、几千万，逐渐变成几十亿。材料的加工能力变了，能够在极小尺度上制造出可工作的器件了。

第二条力量是电路的设计、排布与连接手艺。晶体管数量变多，还不等于计算能力就一定按同样比例增长。芯片上要摆放几十亿个器件，要给它们安排位置，要让线路连接得尽量合理，还要在有限的面积里控制发热和干扰。电路越密，布局越需要科学，排布和连接也越精细。

这两股力量加在一起，才有了“每 18 个月翻倍”的观察结果。摩尔定律告诉我们结果，却没有凭空替我们完成工程；真正让结果出现的，是材料、制程、电路设计和制造工艺的协同推进。

> **结论**：摩尔定律是技术积累后的结果曲线。晶体管数量增加，是量的扩张；电路排布变得科学，是质的提升。两者缺一不可。

### 点石成金：硅晶圆怎样变成芯片

这个行业有一个很形象的词，叫“点石成金”。今天真正被加工成芯片的，并不是一块完整的石头，而是硅这种材料。硅先被制成晶圆，也就是 wafer，一个很大的圆片；然后再从晶圆上切割出一个个更小的方块。

课程用一个很直观的估算来说明这块圆片的价值：一片 12 英寸的晶圆，大约可以切出 450 片英特尔 i7；按课程给出的价格估算，这些芯片的价值加起来大约是 135 万元人民币。这个例子不是为了让我们记住一个价格，而是让我们感受到，芯片制造已经把普通材料变成了高度精细、价值密集的产品。

切割下来的小方块，还要被封装进相应的盒子里，才成为我们今天使用的芯片。以课程当时介绍的 i7 为例，它采用 14 纳米制程，集成 56 亿个晶体管，而且这一切要挤在指甲盖大小的范围里。56 亿不是一个抽象的数字，它意味着大量器件必须被制造、定位、连接，并共同完成运算。

这个行业的另一面，是持续追赶摩尔定律的成本。摩尔说“18 个月翻倍”，听起来像一个目标，但对一家公司来说，却是非常硬的任务：每过 18 个月，都要把能力提升一倍，而且还要保证产品能够生产出来。这样的追赶要连续维持很多年，研发成本当然会高得惊人。

目前在这条赛道上，课程提到三家领跑者：英特尔、三星和台积电。英特尔曾经长期领先，三星随后追赶，台积电又成为重要力量；课程用它们所处的制程水平说明，大家后来都逼近了相近的水平。真正重要的不是给企业排一个永远不变的座次，而是看见整个行业都在被同一条曲线推着往前走。

### 曲线为什么会走平

摩尔在 1965 年提出这条规律时，也预见到了它的边界：大约到 2000 年前后，单体计算机的计算能力会逐渐摸到上限。这里的“上限”不是说从某一天开始计算能力完全停止变化，而是说，指数级增长不可能无限延续，曲线会逐渐变平。

为什么？先看制造工艺。晶体管越来越小，线路间距也越来越小，电路排布已经精细到非常难以继续压缩的程度。课程用一个很形象的尺度来提醒我们：在 14 纳米这样的制程下，底层间隙小到只有几个原子大小的量级。继续缩小以后，电子通过与不通过之间的差别会越来越难稳定地分辨。

这里牵涉到计算机最基本的逻辑。能通过和不能通过，可以被用来区分 0 与 1；过去我们可以把这种差别做得比较明确，底层逻辑也就建立在这个差别上。但当尺度继续压缩到极限附近，状态之间不再容易分清；如果电子还发生了逃逸，就会带走能量，设备便会持续发热。逻辑区分越来越困难，制程和电路的精细化也就越来越接近极限。

所以，单体计算机遇到的不是一个单纯的工程难题，而是底层物理和制造工艺共同施加的约束。电路还能不能排得更精细？晶体管还能不能继续缩小？电子状态还能不能被可靠地区分？这些问题都在把指数曲线压向天花板。

> **易错点**：这里的“接近上限”不是说某个纳米数一到，芯片就会突然全部失效，而是说尺寸继续缩小以后，工艺控制、状态区分和电子行为的稳定性越来越难以同时满足。

### 单机不够，就把多台机器连起来

可是，社会并不会因为一台计算机接近上限就停止增长。我们仍然需要更高的算力，原因至少有两个。

第一个原因是数据量。我们每天会产生约 2.5 quintillion bytes 的数据，单个计算机很难把这些数据完整地存下来、处理完，再顺畅地传出去。课程用了一个很夸张但有效的比喻：假设某一天的交通数据大得像右手，而一台计算机的存储与处理能力只有左手的拳头那么大，那么这台机器显然不够用。

第二个原因是探索范围。我们还没有走向火星，更不用说太阳系和银河系；如果未来要走向更远的深空，就不可能只依赖一台已经接近能力上限的机器。探索的距离越远，对计算能力的要求就越不可能停留在今天的水平。

这时就自然引出了云计算。云计算不是让一台计算机凭空突破自己的上限，而是把分布式存储、分布式计算和快速传输连接起来，再借助 5G 这样的通信能力，把多个计算节点组织成一个整体。课程用 100 台计算机来帮助想象：把它们连起来，可以在整体上获得类似 800G 内存和 100T 硬盘的资源，用来处理大体量数据。

从曲线图上看，云计算确实能把已经走平的曲线又向上托了一段。但我必须提醒你，这里面有一部分像是“自己骗自己”：单体计算机本身没有突破，我们只是换了一种组织方式，把许多个有限的节点拼成了一个更大的计算系统。

```text
单体计算机能力
     ^
     |                         ______
     |                    ____/
     |               ____/       云计算：多个节点协作
     |          ____/
     |     ____/
     |____/________________________________> 时间
          摩尔定律阶段        新增节点，曲线再次上抬
```

读图：云计算延长了能力曲线，但没有消除节点数量增加所带来的管理问题。

### 云计算为什么也有天花板

既然 100 台机器可以拼起来，那我们为什么不把地球上的计算机全部连成一个网络，让它无限大？这里就碰到了经济学里的边际效益递减。

每增加一台计算机，确实会增加内存、硬盘、计算能力和传输能力；但与此同时，节点内部的数据调度、任务管理、状态同步和通信协调成本也会上升。刚开始增加节点时，新增容量可能很有价值；节点越来越多，管理成本会越来越快地把新增收益吃掉。

最终会出现一个边界：新增节点带来的计算、存储和传输能力的提升，恰好等于新增的调度与管理成本。两者相互抵消，继续加节点也就不再带来净收益。云计算的规模可以很大，但并不是无限大。

这就是云计算的天花板。它解决了单机能力不足的问题，却没有把“多个节点如何高效协同”这个新问题变成不存在。单机有单机的极限，分布式系统有分布式系统的极限；我们沿着算力曲线向上走，换的是解决问题的方式，不是摆脱所有约束。

### 算力停下时：向内卷，还是向外走

当单机接近上限、云计算也接近上限时，接下来仍然需要更高级别的算力。课程在这里提出两种方向，也把它们看成两种不同的技术路线。

一条路线是向内走。既然现实的算力增长变慢，就转而在现有能力内部继续竞争，把已有的空间尽可能卷得更深，于是出现了“元宇宙”这样的想象。这里的“内卷”不是说技术没有价值，而是说技术资源集中到封闭环境里，通过不断叠加内部体验来延续增长。

课程还提醒我们，行业增长即使没有变成负数，只要边际上放缓，也会改变大家的预期。原来每年增长 10%，后来只增长 6%，少掉的 4% 就足以影响判断。技术行业同样会从扩张竞争转向内部竞争，头部企业为了争夺有限的增量，投入的成本可能越来越高。

另一条路线是向外走。像埃隆·马斯克所代表的深空探索方向，核心问题不是把人类一直塞进一个越来越精致的胶囊，而是继续向更远的地方去。课程把扎克伯格所代表的路线与马斯克所代表的路线放在一起对照：一个更强调在有限认知下向内探索能走多深，另一个强调不断向外突破人类能力的边界。

我旗帜鲜明地反对把人类未来全部押在“内卷”上。人类从自然中一路进化到今天，已经把技术发展到了今天这个程度；如果最后只是回到一个胶囊里，脑部接上网线，躺在管子里，只剩下一个大脑在活动，那多少有些浪费大自然给我们的能力。至于最终怎样探索宇宙，当然是严肃的科学问题；但在这个问题上，我个人更支持往外走。

```text
单机能力接近上限
        |
        v
云计算抬高能力曲线
        |
        v
算力继续增长的方向
     /     \\
  向内卷     向外探索
  元宇宙     深空航行
        |
        v
需要新的计算机能力曲线
```

读图：这不是把两条路线说成简单的对错题，而是说明算力需求继续存在时，技术会沿着不同的方向组织自己。

### 先看懂芯片是怎样刻出来的

既然要寻找新的计算机路线，我们先回到最基础的问题：今天的芯片究竟是怎样做出来的？如果连现有芯片的制造过程都不理解，就直接跳到量子计算，听起来会很热闹，却容易把几个名词混在一起。

#### 从光罩到硅片

芯片制造可以先记成一条线：基底、化合物、光刻胶、光罩和光源，最后通过腐蚀与离子注入形成电路。

```text
电路设计
   |
   v
把设计图形缩小并刻到光罩上
   |
   v
光线穿过光罩，照到光刻胶上
   |
   v
光刻胶感光，形成需要加工的图形
   |
   v
用化合物进行腐蚀，形成凹槽
   |
   v
继续腐蚀到硅基底
   |
   v
离子注入，形成 PN 结
   |
   v
导通 / 截止两种状态承载 0 与 1
```

读图：光罩不是最终芯片，而是把设计图形转移出来的“模板”；真正的电路要经过曝光、腐蚀和掺杂等步骤，逐层落到硅片上。

第一步是基底。基底提供了芯片的硅材料基础；然后在上面加入化合物和光刻胶。光刻胶对光敏感，受到特定光照以后，会形成相应的印记。设计好的电路被缩小、缩小、再缩小，刻在光罩上，光穿过光罩照到光刻胶上，感光区域就可以进一步被腐蚀。

腐蚀之后，会出现一个相应的凹槽。这个凹槽告诉后续工艺：这里需要放置电路。再继续腐蚀，就能把结构刻进以硅为基础的晶圆。随后进行离子注入，形成 PN 结。N 和 P 分别对应负、正两类掺杂区域；课程用它们的不同导电状态帮助理解 0 和 1 的逻辑基础。

这里真正需要抓住的不是死记某一个区域名称，而是理解：芯片通过控制不同区域的导电与截止，形成可区分的两种状态，再把大量这样的状态组合起来，承载计算。

> **易错点**：N、P 是材料区域的标记，不能简单理解成“某个区域永远固定代表 0，另一个区域永远固定代表 1”。芯片逻辑依赖的是这些结构在不同条件下的可控状态。

#### 几纳米到底在说什么

我们经常听到 3 纳米、5 纳米、7 纳米、14 纳米、28 纳米、32 纳米这些数字。它们在芯片语境里指向的是制造工艺和关键结构尺度的不断缩小。课程把它们直观地解释为 N 区和 P 区之间的间隙越来越窄。

当尺寸还可以继续缩小时，工艺就必须问：PN 结还能不能做出来？电子通过与不通过还能不能稳定地区分？如果底层状态无法可靠地区分，0 和 1 的基础就会动摇，整套计算机语言也就失去了落脚点。

因此，14 纳米、7 纳米、5 纳米并不是孤立的营销数字，而是一条不断压缩的工艺路线。越往下走，晶体管数量、线路排布和制造精度就越难同时维持。摩尔定律的指数增长，最终会遇到这种底层极限。

### 光刻机：一支比纸还宽的笔

既然芯片需要不断向更小的尺度刻电路，下一件必须面对的事情就是光刻机。

课程的提问很形象：光是有波长范围的，最小的一束光也有宽度。如果这束光的宽度甚至比 PN 结的宽度还大，那么我们怎么用它在更小的结构上雕花？

这就像一张纸，手里拿着的笔尖却比纸还宽，却要求在纸上雕出细密的花纹。你当然不能指望这支笔直接写出比笔尖更窄的线条。芯片制造遇到的就是这种“在有限尺度内雕花”的困难。

光刻机看起来像一台极其复杂的机器。课程提到，ASML 专门生产光刻机，一年只能生产十几台；英特尔、IBM、三星和台积电都是重要股东。也正因为制造难度和产量都有限，光刻机才如此昂贵，课程才会直说中国很难拿到这类设备。

那人类是怎么继续把光变细的？课程借高中物理的光折射来解释：光从一种介质进入另一种介质时，由于介质特性不同，传播方向和有效尺度会发生变化。先让光经过不同的液体介质，逐步缩小它能够刻出的粒度，最后再把这些更细的图形转移到光刻胶和硅片上。

```text
宽波长的光
   |
   v
进入不同液体介质：折射、改变传播条件
   |
   v
有效刻蚀尺度逐步缩小
   |
   v
光刻胶感光
   |
   v
硅片上形成更细的电路结构
```

读图：光刻不是靠一支“无限细的笔”直接刻画，而是借助介质改变光的传播条件，把有限的刻蚀能力逐级压小。

但这套办法也有自己的边界。折射可以把尺度继续压缩，却不能突破底层逻辑的限制。如果再小下去已经无法稳定地区分 0 和 1，那么就不能只沿着传统光刻路线硬走，必须换一种计算机技术路线。

### 量子计算：用两种特性改写曲线

接下来就进入量子计算。这里我先假设大家没有量子力学基础，不去堆一大串术语，只抓住两个对计算机最有影响的特性：量子叠加态和量子纠缠。

量子力学给人的第一印象常常是“测不准”：很多现象看起来无法用日常直觉解释。但课程用普朗克常数这样的精细常量提醒我们，宇宙的规律并不是没有尺度的；越是看起来混沌的现象，越可能对应着非常精确的约束。我们要讨论的不是把“测不准”当成任性，而是理解它怎样改变信息处理的可能性。

#### 量子叠加：把 0 和 1 放进同一个混沌状态

传统晶体管比特的逻辑很确定：通电是一种状态，不通电是另一种状态，我们把它们对应为 0 和 1。量子比特，也就是 qubit，在没有被观察时，可以用一种叠加状态存在：它既可以是 0，也可以是 1，两种可能性同时存在。

可以把两个量子比特想象成两种液体混在同一个锅里。只要还没有把它们分离出来，我们就无法只从整体上判断自己拿到的究竟是哪种液体；一旦去观察，状态就会落到可以辨认的 0 或 1 上。这和薛定谔的猫是一个帮助想象的比喻：盒子没有打开时，不能简单说猫此刻只是死或只是活。

那它对计算有什么用？课程用四个比特做了一个简化模型。四个传统比特的可能组合是：

$$2\times2\times2\times2=2^4=16$$

也就是说，整体状态空间有 16 种可能。但传统计算在某一个时间切片上，只能取其中一种确定状态来运算；可以把 16 个程序想象成排队等待的计算任务，一次处理一个，处理完再处理下一个。

课程再用同样的方式解释量子比特：虽然最终可表示的状态数量仍然是 16 种，但由于量子比特可以处在 0 和 1 的叠加状态，在特定计算过程中可以把 16 种可能性一起纳入计算，再给出结果。于是，讲解中出现了 $2^n$ 的指数关系：4 个量子比特对应 16，位宽增加后，可能性空间会按指数增长。

这里要抓住课程想表达的曲线逻辑，而不是把“同时”理解成任何程序都能无条件免费完成。课程的简化模型是在说明：量子特性有可能把处理能力从传统曲线上再次抬起，位宽带来的量级为什么会从“倍”迅速跳到“亿”的数量级。

把这个模型套到前面提到的 56 亿个晶体管上，按课程的算术直觉，量级会变成 $2^{56\text{亿}}$。新闻里说九章的算力比谷歌悬铃木高出百亿倍，那个“亿”正是用来说明量子位宽与状态空间之间的指数关系，而不是说普通手机之间能随便拉开百亿倍的实际跑分差距。

> **结论**：量子叠加主要改变的是信息处理的组织方式。它不替我们凭空增加晶体管，而是让状态不再只能以传统比特那种确定方式参与计算，因此可能形成新的处理曲线。

#### 量子纠缠：相隔很远也能共振

第二个特性叫量子纠缠，英文是 entanglement。课程先用《三体》里的想象来引入：两个质子即使相隔很远，其中一个感知到环境变化，另一个似乎也能同步知道。

现实中的实验让这种奇怪现象变得具体。课程提到，物理学家在美国实验室里把两个纠缠过的量子拉开大约 500 米，发现它们仍然出现共振；中国的“墨子号”又把量子纠缠带上了卫星，完成纠缠后从同步轨道返回地面，接收端分别放在丽江和贵州，发现两边仍然保持共振。

人类目前还不知道这究竟是怎么做到的。课程把这个未解问题继续往更大的范围推：提到宇宙可能是 11 维的，而人类大脑以及蛋白质能够感知到的是 4 维；又提到“两暗一黑三起源”这样的未解问题。讲师据此猜测，纠缠态之间也许存在某种更高维度的通信 channel。这个说法很重要，但必须说清楚：它是课程对未知机制的探索性设想，不是已经完成的工程解释。

> **注意**：更高维通信通道只是对量子纠缠现象的一种猜想。课程在这里承认“目前不知道”，重点是让我们看到：连通信的基本机制都还没有完全弄清楚，才更需要谨慎地研究它。

纠缠特性对现实通信的启发，则落在加密上。课程把量子被观察后会从叠加状态落到确定的 0 或 1 这件事，转化成一个通信安全模型：发送方发出信息后，如果中间有人观察或窃听，原本的叠加状态就会受到改变；接收方拿到的就不再是原本的干净信息，而可能变成乱码。

我们可以用传纸条来理解。普通情况下，我把折好的纸条交给中间的三位同学，他们可以把纸条打开、看完，再继续往后传；我和接收者通常不知道中间是否有人看过。量子加密的设想则是，让“被观察”本身成为能够被发现、甚至会改变信息的事件。课程把它类比成《哈利·波特》里那种看完就自己烧掉的信件。

课程还提到，二战期间德军密码被破解，而德军并不知道密码已经被破解，这说明传统通信系统很难让发送者及时确认“信息有没有在途中被看过”。量子通信试图补上的，正是这种对窃听可见性的需求：一方面寻找更深的通信通道，另一方面建立更可靠的加密方式。

```text
量子叠加
   |
   +--> 状态空间与计算组织的改变 --> 处理能力曲线再次上抬
   |
量子纠缠
   |
   +--> 远距离共振的未解机制 --> 探索通信 channel
   |
   +--> 观察会改变状态 --> 窃听可被发现，数据可加密
```

读图：叠加主要对应处理，纠缠主要引出远距离通信与加密；两者共同构成课程对量子计算前景的期待。

### 量子计算机走到哪一步

我们不能因为“量子计算”这个名字很前沿，就默认它已经是一台无所不能的通用机器。课程用 ENIAC 和 EDVAC 的历史对照来定位它。

1946 年的 ENIAC 是专用计算机，专门针对某些数学运算，比如计算导弹炮弹的路径。你给它一个数学问题，它就帮你快速算出结果。1949 年的 EDVAC 则是另一条路线：冯·诺依曼为了发明氢弹而参与设计，它代表了通用计算机的思路——你输入什么，它就计算什么，今天的计算机属于这一类。

课程把九章、悬铃木以及日本的富岳等量子计算机放在 ENIAC 这个阶段理解：它们目前更像是针对特定问题的专用探索，还没有走到 EDVAC 那种成熟的通用阶段。这个历史类比的重点不是说量子计算没有潜力，而是提醒我们：专用计算和通用计算之间，还有一段工程与理论都要补齐的路。

接下来的路线可以先按三层来想：先把单一量子计算机在专用任务上做扎实，再尝试把量子计算机连接成云计算；如果还不行，那已经超出我们这几代人眼前最迫切的工程任务，交给下一代人继续解决。课程的态度很明确：先把摩尔定律、云计算和量子的关系想清楚，不必急着替未来所有问题给出答案。

### 三条曲线共同推动大 IT 行业

回到大 IT 行业，我们会发现摩尔定律不是孤立的一条线。课程最后把数据存储、数据处理和数据传输放在一起观察，形成了三条方向相反、彼此配合的曲线。

| 关键维度 | 变化方向 | 对大 IT 行业的作用 |
| --- | --- | --- |
| 数据处理 | 计算能力按指数级上升 | 更多任务可以被机器完成 |
| 数据存储 | 每美元能够存储的数据量按指数级上升 | 存储花销下降，数据应用更容易铺开 |
| 数据传输 | 单位通信成本按指数级下降 | 网络连接更容易普及，互联网使用不再受过高流量费用限制 |

读表：处理能力往上走，存储和通信的单位成本往下走；两个方向共同打开大规模应用的空间。

摩尔定律主要解释了“每 18 个月能力翻倍”的根源。顺着这个根源继续看，每美元信息存储量在上升，互联网通信成本却在下降。数据处理、存储、传输三个方面，一个表现为能力或规模的上升，一个表现为成本的下降，最后共同让大 IT 行业能够进入普通人的工作与生活。

课程还提到“大规模数字存储定律”：计算机设备能力大约每 18 个月翻倍，产生的数字数据也差不多按这个节奏增长。它把摩尔定律从硬件能力推进到了数据规模本身：机器越来越强，产生的数字也越来越多，二者相互推动。

另一条线是梅特卡夫定律和网络经济学。传统经济学讲边际效益递减：一个网络已经很大时，继续增加一个节点，新增价值可能越来越小。但网络价值却会随着节点增加而提高。一个人的电话只有几个联系人，和拥有一万个联系人，价值当然不一样；微信网络里的参与者越多，网络的整体价值就越高。

这就是课程所说的边际效益递增。它和云计算面对的边际效益递减并不矛盾：网络节点本身能增加网络价值，但当节点增加到一定程度后，数据调度和管理成本又会把新增收益吃掉。网络经济学负责解释“连接为什么有价值”，边际效益递减负责解释“连接为什么不能无限扩张”。

### 技术标准：把能造出来变成所有人能用

这些技术曲线要真正形成大 IT 行业，还需要一个经常被低估的环节：技术标准。

技术标准是对产品兼容性和网络通信能力规范的描述。课程把它分成两种来源。一种是国家或政府制定的标准，例如不同地区家里的插头形状、电压和制式可能不同；这些标准背后，也可能包含保护本国工业体系、推动企业规模化扩张的政策考虑。另一种是行业共同形成的标准，参与者发现大家都按同一套规则生产和使用，交流成本就会下降，于是大家愿意接受它。

QWERTY 键盘是一个很典型的故事。早期打字机按照字母顺序排列，但打字员连续快速输入时，打字机经常卡纸。厂商为了缓解这个问题，把键盘顺序故意打乱，用乱序来降低连续击键造成的机械冲突。这个顺序本身并不优美，甚至可以说没有什么漂亮的逻辑；但因为大家认可、接受并长期使用，它就成了事实上的标准。

ASCII 编码表也是同样的道理。人与计算机之间最终要通过 0 和 1 传递信息，但如果每家电脑公司都用自己的编码方式，把同一个字符变成不同的 0 和 1，那么一份 Word 文档在不同电脑上打开时就可能变成另一种样子。统一编码表的价值，就是让不同厂商的设备能够互相理解。

课程把技术标准比作大家都认可的货币：纸本身也许没有特别的价值，但只要所有人相信它值 100 元，它就可以在分工协作中流通。标准有时候来自政府的强制力，有时候来自行业共同认可；来源不同，作用相同，都是让不同主体可以按照同一套规则协作。

技术标准一旦形成，就会推动一个循环：

```text
统一技术标准
      |
      v
不同企业按同一规则生产
      |
      v
形成规模化生产能力
      |
      v
成本下降，终端售价下降
      |
      v
产品大规模推广，用户数量增加
      |
      v
企业营收和行业利润上升
      |
      v
更多资金投入研发
      |
      v
产生更高级的信息技术
      |
      +------ 回到统一标准，继续循环
```

读图：标准不是最后贴上的标签，而是把生产、成本、市场和研发连接起来的循环起点。

这个循环可以用五句话说清楚。第一，有了技术标准，各家供应商才能按照同样的要求生产，而不必为每个客户单独做一套产品。第二，当大家都做同样的事情，生产规模扩大、技术越来越熟练，单位成本就会下降，终端售价也会下降。第三，好技术的价格足够低，就更容易被市场大规模采用。第四，用户规模扩大后，企业获得更高营收和利润水平。第五，企业有更多钱投入研发，推动下一次技术创新；更高级的技术出现后，又回到统一标准、规模生产、市场投放和研发创新的循环。

所以，技术标准并不一定天然合理，但它能够释放出强大的规模经济能量。没有标准，厂商要针对不同设备重复设计和生产；有了标准，产业链才能分工，研发成果才能广泛传播。标准不是创新的对立面，反而是创新能够从实验室走向市场的基础设施。

### 大 IT 行业的七条赛道

课程最后提醒我们，大 IT 行业不是一团模糊的“技术行业”，而是由七个方面构成的基础设施体系。这七个方面是：硬件设备、操作系统、应用软件、数据库、网络通信、服务平台和咨询服务。

这七项可以看成一个行业地图：

```text
硬件设备
操作系统
应用软件
数据库
网络通信
服务平台
咨询服务
```

读图：七条赛道共同支撑大 IT 行业；一个在 IT 行业工作的人，通常是在其中一个或几个方向上提供能力。

这也是一个考试重点：IT 基础设施有哪些构成要素，代表性公司分别对应哪一类。硬件设备是计算的基础，操作系统负责管理计算机资源，应用软件把能力交给使用者，数据库负责数据管理，网络通信连接不同主体，服务平台把能力组织成可使用的服务，咨询服务则把技术能力转化为面向组织和业务问题的方案。

本段口头讲解明确确认了七类构成要素，但代表性公司的具体名单要回到教材对应的那一页去一一核对，不能只凭印象补写。我们真正要掌握的是这张地图的骨架：数据库不是孤立的软件，而是大 IT 基础设施中的一个关键环节；它必须与硬件、操作系统、网络和服务共同存在，才能形成可用的信息系统。

### 把算力曲线连起来看

现在再回头看这一整条线，会发现它并不是“摩尔定律—云计算—量子计算”三个孤立的名词，而是一条连续的判断链。

摩尔定律首先告诉我们，晶体管数量增加、电路排布变得科学，能力就会快速提高；但单台计算机的尺寸、材料和电子状态都有极限，所以第一条曲线会走平。数据持续增长，空间探索又提出更高要求，于是我们把多台计算机连起来，用分布式存储、分布式计算和快速传输组成云计算；但节点调度和管理成本又会上升，边际效益递减让第二条曲线也有天花板。

当两条曲线都逼近边界时，技术路线就出现分叉：一条向内，把现有能力卷到更深；另一条向外，用更强的计算能力支持深空探索。我个人更支持后者。真正要解决的不是把人类永远封装起来，而是继续扩展人类能够到达的边界。

而新的计算路线，课程把目光放到了量子计算。量子叠加改变状态的组织方式，量子纠缠引出远距离共振与量子通信的设想；叠加可能把处理能力重新抬上曲线，纠缠则可能让通信和加密出现新的做法。当然，量子计算机目前仍处在专用探索阶段，通用量子计算机还需要继续发展。

但无论下一条曲线最终由谁来完成，标准、市场和研发都已经给出了它必须落地的路径：统一标准让企业能够规模化生产，生产规模让成本下降，低成本让技术走进大规模市场，市场收入再反哺研发，下一代技术继续沿着同一条循环往前走。

这也是为什么教材可以用一页讲完摩尔定律，而我们值得花一个小时把它背后的芯片、云计算、技术路线、量子特性和产业标准都摊开看。真正学会一个行业，不是记住一张漂亮的曲线图，而是知道曲线为什么会上升、为什么走平，以及走到尽头以后，人类还能怎样继续往上寻找新的可能。

如果还想继续往下追，课程最后推荐了几条延伸方向：从半导体集成电路工业开始理解芯片怎样被制造出来，再去看五分钟的量子计算介绍、量子计算原理解释，以及九章的原理与算力爆炸曲线。它们不是作业题，而是给 interested 的读者留下的继续追踪路线。

## 从数据驱动决策到数据库：信息系统如何把数据存好、用好
> 对应块：BLK03 | 覆盖分集：P02 | 块标题（分集名）：《数据库系统课程前导内容二：信息系统中的数据存储》

先把一组看起来很“管理学”的图放在一起：外部环境在变，组织承受压力、寻找机会，管理层必须作出决策；数据则要及时、可靠地在背后支撑这些决策。这里真正要追问的，不是“商务智能”这个名字有多时髦，而是它为什么会出现、要解决什么问题，以及它的底下究竟靠什么撑起来。

这几个问题不能只靠背一段文字记下来。图上的一条条关系、一个个问题，反而容易留在脑子里。遇到类似问题时，能想起“以前分析过这张图”，也就有了自己的认知和答案。

### 商务智能从环境压力中生长出来

#### 压力与机会逼出决策支持

先看 `Business Environmental Factor`，也就是商业环境。全球化、逆全球化、客户需求、产业链推动、政府规制、市场状况与竞争，都会出现在这里。

这些英文名词硬记并不牢靠，记不住也没关系。以前分析企业环境时，PEST 可以从政治、经济、社会、技术等层面展开；战争时期还可能演化成强调政治、经济与战争环境的 PRIM。再往下，行业层面有波特五力模型、资源基础理论中的核心资源与核心能力，企业内部则可以沿价值链，从上游、下游到内部活动去分析。我们真正需要掌握的，是从不同角度审视企业环境，而不是把这一页英文原封不动背下来。

外部环境变化带来的影响通常有两面：一面是 `Pressure`，也就是压力；另一面是 `Opportunity`，也就是机会。中文里常说“危机”，不要只盯着危的一面。大压力往往也意味着大机会，社会面临的大危难同样可能带来历史性的机会。

一定要有这个思维：不要浪费任何一次大的危机。像疫情带来的政治、经济以及社会文化认同等方面的压力，对所有人都存在；能在这种局面中找到属于自己的机会，其意义甚至可能是历史级别的。与其抱怨，不如主动寻找。

但组织不能只看见环境，它必须作出响应。`Organization Response` 可能是战略调整、供应链重塑、合作伙伴协作，也可能涉及客户关系管理与实时响应。为什么外部一变，组织就得跟着变？

制度经济学，也就是 `Institutional Theory`，给出了一个很重要的解释：任何组织都不可能脱离环境独立存在。每个组织所处的是自己的“组织场域”或“制度场域”，例如 `Organizational Field`、`Institutional Field`。所谓“制度”，就是游戏规则。学校几点上课，是学校的游戏规则；企业要在某个环境里生存，就必须遵守那个环境的规则。

想长久 `Survive`，就得争取 `Legitimate`，也就是让自身在这个组织场域中取得合法性；相应的过程叫 `Legitimation`，即合法化或合理化。外部规则变了，组织若想继续生存，就必须跟着变。

怎么变？战略问题最终要由高层管理人员判断。判断当然离不开管理人员自己的学识、能力和经验，但也离不开数据来源。这里有一个一定要记住的词：`GIGO`，`Garbage in, Garbage out`，垃圾进来，垃圾出去。

拿到的是垃圾信息，基于它作出的判断就会出问题，最后的行为也会出问题。做决策最忌讳信息不对称与信息不完整。以三国故事为例，谁掌握的信息更完整、谁获得的信息更可靠，往往就会影响判断和结果。

因此，高层决策对数据支持提出了几个很实际的要求：数据最好能够实时，质量要足够高，转化为信息后才值得用于判断；除了管理者自己的判断，还需要专家意见与数学模型提供的支持。把这些合起来，就是 `Integrated Computerized Decision Support System`，整合性的计算机决策支持系统——也就是商务智能系统。

这套逻辑可以压缩成下面这条链：

```text
商业环境变化
      |
      +--> Pressure：压力
      |
      +--> Opportunity：机会
                    |
                    v
          Organization Response
                    |
                    v
      高层管理人员的判断与决策
                    |
                    v
  实时数据 + 高质量信息 + 专家意见 + 数学模型
                    |
                    v
     Integrated Computerized Decision Support System
```

记住这条链，就不会把商务智能理解成一个孤立的软件名词。它先是应对环境变化、支撑组织决策的一套机制。

#### 描述、预测与行动

接下来，商务智能到底能做什么？可以把问题拆成三个连续的回答：发生了什么，将会发生什么，以及我应该怎么做。

| 序列 | 要回答的问题 | 主要工具 |
| :--- | :--- | :--- |
| 描述 `descriptive` | `What happened?` 过去发生了什么？`What is happening?` 现在正在发生什么？ | 数据可视化 |
| 预测 `predictive` | `What will happen?` 将会发生什么？`Why will it happen?` 为什么会发生？ | 数据挖掘 |
| 规范 `prescriptive` | `What should I do?` 我应该做什么？`Why should I do it?` 为什么应该这样做？ | 最优化、仿真、决策建模、专家系统 |

描述的答案，我们其实一直在用。问过去的成绩怎么样，可以看成绩单；问一家企业 2021 年的运营情况怎么样，可以看企业年报。仪表盘、平衡计分卡、饼状图、柱状图、条状图、散点图，以及各类报表，都是数据可视化的工具。

它们把一个组织、一个人或一个群体的情况描述出来：过去发生了什么，现在正在发生什么。图表不是装饰，而是在帮助我们回答问题。

预测更进一步，要根据过去和现在，推断未来。在京东或淘宝买过一件东西之后，平台开始推荐别的商品，其实就是在预测你未来可能还会想买什么。使用高德等导航或打车软件时，若经常在早高峰从 A 点去 B 点，软件在该时段自动推荐这条路径，也是在根据已有数据预测接下来的出行。

所以数据挖掘——包括 `Data Mining`、`Text Mining` 和 `Web Mining`——并不是凭空“算出一个未来”，而是从过去和现在的数据中找出可用于预测的规律。

可预测还不够，最终还得行动。`Prescriptive` 要回答的是：事情可能这样发生，那么我应该做什么，为什么这样做；目标是给出更优的行动方案。相应工具包括 `Optimization` 最优化、`Simulation` 计算机仿真模拟、`Decision Modeling` 决策建模，以及 `Expert System` 专家系统。

三者的推进关系必须记住：

```text
描述：发生了什么
   |
   v
预测：将会发生什么
   |
   v
行动：应该做什么
```

数据摆在那里，不等于已经产生了价值。要把数据可视化，进一步从数据中挖掘预测规律，再把预测转化为行动方案，数据才真正进入商务智能的完整链条。

#### 分布式的“千人方阵”

我们平时接触的推荐与导航，已经把“描述—预测—行动”藏在背后了。大型赛事开幕式的实时呈现，则把这件事展示得更加壮观。

一万多人在场地中同时跑动，短短几分钟里，队形不断变化，节目依次展开。张艺谋导演有整体构思以后，怎样把脑海中的场景准确地落实到每个人的每一个动作上？这不是只靠“看一遍效果，觉得很壮观”就能回答的问题。

沿着商务智能的思路来想：先把这个构思用计算机图形表现出来，做数据可视化与仿真模拟；再用数据挖掘中的聚类、分类、关联，把整体图形分配到一个又一个“像素点”或节点上；然后推演，如果一个点对应一个人，那么在整段时间序列的每个时间切片上，这个人应该做出什么动作；最后把结果细化到每个人。

它很像我们拼过乐高时拿到的那本书：书里一步一步告诉每个零件该怎么拼。开幕式里对应的，就是一本告诉每个人每个时刻应做什么动作的手册。大家各自练习，再合练，最终才能形成几万人的整体效果。

这里不是说只靠其中某一种工具就能完成整场表演，而是说这一整套效果背后，正需要信息系统提供数据可视化、数据挖掘与计算机仿真模拟的支持。把大型活动的组织问题想清楚，就能明白商务智能并不是离普通人很远的术语。

#### 让数据成为商务智能的底座

理解商务智能能做什么之后，还要追问：这些能力建立在什么技术架构上？

数据先要有来源。企业内部可能包括前端或后端的 `ERP` 企业资源计划系统、`SCM` 供应链管理系统、`CRM` 客户关系管理系统，还可能有 `Legacy` 遗留系统、`POS` 销售点系统与网页数据；企业外部也可能接入国税总局、社保、公积金等系统提供的数据。

这些来源的数据不能原样堆在一起。先以日期为例：同样是年月日这个事实，教务处可能按“年/月/日”存放，财务处可能按“年.月.日”存放，有些地方还可能使用英文月份。不同系统的数据格式与数据类型都不一样，同一个意思也无法直接放到一起。

所以必须经过 `ETL`：

- `Extract`，提取，把不同来源的数据取出来；
- `Transform`，转换，整理、整合、清洗，使格式和表达能够衔接；
- `Load`，加载，将处理后的数据装入统一的数据存放环境。

完成这一步，得到的是 `Enterprise Data Warehouse`，企业数据仓库。数据像放进图书馆的书，还要建立索引；这里对应的元数据是 `Metadata`，其中保存作者、出版商等描述信息，让使用者能查到它。总馆里有了书，也要有目录，不能把书扔到三层书架后就再也找不到。

还要做 `Replication`，复制。数据真的丢了、数据库真的出问题了，至少还要有备份可用。备份不是额外装饰，而是保证数据还能被找回的一道防线。

不同组织、职能部门关心的主题也不同。以学校为例，财务处、教务处、学工处与各学院不会使用完全相同的数据子集。于是可以从数据仓库中取出与某个主题相关的数据，形成面向该主题的子集镜像，也就是 `Datamart`，数据集市。

财务处关心姓名、学号和财务数据，考试成绩与学生系统中的其他数据对它就没有那么重要；教务处、学工处与学院也各有自己的数据集市。完整数据放在数据仓库中，各职能部门通过数据集市使用自己关心的部分。

数据集市形成以后，再通过 `Middleware` 中间件，或者 `Application Interface` 应用数据接口，把能力交给前端使用。手机 App、网页、小程序与电脑端程序，才可以在这个基础上发出请求并取得所需数据。

整体架构可以这样看：

```text
ERP | SCM | CRM | Legacy/POS | 网页 | 外部政务数据
                          |
                          v
             Extract -> Transform -> Load
                          |
                          v
             Enterprise Data Warehouse
                          |
              +-----------+-----------+
              |                       |
       Metadata 索引          Replication 复制
              |                       |
              +-----------+-----------+
                          |
                          v
    财务 Datamart | 教务 Datamart | 学工 Datamart | 学院 Datamart
                          |
                          v
        Middleware / Application Interface
                          |
                          v
   数据可视化 | 数据挖掘 | 在线实时分析 | App/网页/程序
```

这张图从左到右，恰好把前面“描述、预测、规范”的工作落到了技术实现上：有的数据用于可视化与报表、仪表盘，有的用于数据挖掘，有的用于在线实时分析展示，也有的通过中间件为手机 App、网页和电脑端程序提供数据支持。

商务智能能力不是同时出现的。数据集市、数据库、数据仓库、决策支持系统与计算机数据挖掘等技术在多年间先后出现，最后共同构成今天以计算机技术为基础的商务智能系统。用更抽象的说法，就是先建设 `Data Warehouse Environment` 形成数据基础，再形成包含可视化与数据挖掘的 `Business Analytics Environment`，让数据挖掘结果为 `Business Performance Management`——企业绩效管理——提供决策支持。

一定要把这张图和前面三张图联系起来：业务需求、决策层次、数据技术架构与最终应用，是同一件事情的不同视角。

#### 管理者为什么必须懂它

还有一张图叫“互补性资产”，英文是 `Complementary Assets Perspective`。所谓互补性资产，就是为了保证主营业务投资获得价值而需要的资产。

这解释了为什么商科方向的同学也要理解数据库、数据挖掘与商务智能的底层架构。管理者以后可能会碰到信息系统的采购，招聘信息系统相关人员，亲自主持开发，或者审批开发部门上报的预算。

如果对这些工作完全不懂，那么无论是使用自己购买的系统，还是参与开发系统，都可能出现投入了过多资金、人力与物力，最终却没有达到预期效果的情况，落入图中的第四象限。

所以数据库知识并不是只在技术人员内部才有用的术语。管理者要能看懂系统能力、技术依赖与资源投入，也才能判断一个方案究竟有没有价值。

到这里，本章的第一部分——商务智能是什么、为什么需要它、它的逻辑与能力是什么、底层架构在哪里——就算完成了。接下来，就进入这门课真正的主体：数据库与数据库管理系统。

常规本科课程可能为数据库安排 48 课时，但这里不准备照教材逐页讲完，而是按数据库知识体系拆成若干话题，一个话题一个话题地理解。过去我尝试过用两到三个小时，让零基础的同学建立对数据库的整体认识。

我们仍然用图说话，从最基础的问题开始：什么是数据库？什么是数据库管理系统？它们是怎么来的，又是怎样一步步发展到今天的？

### 数据库不是一堆文件，而是受管理的系统

#### 从 bit 到数据库

计算机底层是 0 和 1。PN 结的通电状态可以反映 0 与 1，一个这样的比特位叫 `bit`。

8 个 bit 放在一起，例如 `01001001`，形成一个 `byte`，也就是字节。人类语言中的英文字母、数字和标点符号，可以通过 ASCII 码表与这些比特位对应起来。

大写字母 `A` 对应 `01000001`，第 2 位与第 8 位为 1，其余位为 0。汉字比英文字母复杂，这里先记住课程里的这条结论：一个汉字用两个字节，也就是 16 个 bit 来表示。

有了字符，就可以把不同字节的表述组合起来，形成一个 `field`，字段。比如 `IS 101`：它是 Information System 的缩写，后面是空格与课程编号，指向《管理信息系统》这门课。

一组字段描述一个具体事实。例如，学号是 `39044`，课程是 `IS 101`，上课时间是 Friday 的第六节课，成绩是 `B+`。把这些值横向放在一起，就构成一条 `record`，记录。

如果班里有一百位同学，就有一百条这样的记录。把它们一行行放在一起，形成一张课程成绩表；这份文件就是 `file`。

再把具有共同主题关系的不同文件放到一起——课程文件、财务文件、学生个人文件等——就能形成面向这个主题的 `database`，数据库。

这条路径非常直接：

```text
bit
  -> byte
  -> field
  -> record
  -> file
  -> database
```

越往上，数据组织的主题性越强。数据库不是凭空出现的，它是从底层编码、字段、记录与文件的逐层组织中长出来的。

这一步本身并没有太大难度。把有共同主题的数据放在一起，就有了数据库。我们真正要学的，不只是“把数据放在一起”。

#### 真正有技术难度的是 DBMS

把一堆数据放到一起，它叫数据库；真正有技术难度、需要由系统负责的，是 `Database Management System`，简称 `DBMS`，数据库管理系统。

DBMS 要负责数据库的搭建，负责对数据库中的数据进行增加、删除、修改、查询，还要控制这些数据，并响应外部程序发来的要求。

它处在应用与物理层数据文件之间。应用是什么？就是我们平常打开的 App、网页与小程序；物理层则涉及底层 0 和 1 怎样映射到磁盘扇区上的具体存储位置。

中间由 DBMS 协调。它的重要作用，是实现数据的逻辑结构与物理结构之间的隔离。我们写 Word 文档，只需要关心内容；文档怎样变成 0 和 1，0 和 1 又如何存到磁盘的物理位置上，应用使用者并不关心。因为这一层的工作由软件来做，具体的物理实现则由微软这样的软件公司操心。

我们研究 DBMS，是希望得到一个运行效率较高、能够合理利用系统资源的数据库管理软件。不同 DBMS 的表现不一样，原因也在这里：底层架构不同，运行逻辑就不同，对数据的存放方式以及增加、删除、修改、查询的处理效率就不同，使用的系统资源也有优劣。

因此，数据库与数据库管理系统的区别必须从一开始就弄清楚：数据库是集中化之后为众多应用同时提供数据的数据集合；DBMS 则是应用访问这些数据时的接口与管理者。真正不断忙碌、真正需要掌握技术的是 DBMS。

#### 把自己的房间想成数据库

用日常生活再把这个区别讲一遍。

此刻大家在房间里上网课。假设这个房间就是你的小书房，房间里的物品几乎都是你的 `personal belongings`。凡是与你个人这个主题相关的物品，放在一起，就构成了你的“数据库”；这个房间本身，就是你的数据库。

那么谁是这个数据库的 DBMS？先别去找机器，就把自己想成数据库管理系统。

你要设计房间怎么布置，这就是数据库的搭建；要把书放到架子上，这就是数据存放；有新物品添进来，是增加；把不用的东西扔出去，是删除；调整物品位置，是修改；想知道《曼昆经济学原理》在哪儿，是查询；还要决定什么东西能放进来、不能放进来、放多少，这就是数据控制。

这三类事情——搭建、增加删除修改查询、控制——正是前面反复强调的 DBMS 职责。

数据库管理系统也有不同特点。不同的人有不同习惯。我们权且拿男同学和女同学作个帮助记忆的类比：有的男同学东西较少，会把书和器具摆得整齐，书架码放有序，杯子等器具也接近直角摆放，这就是比较 `organized` 的方式。有的女同学东西较多，化妆品瓶瓶罐罐集中放，衣服在衣柜里成排放，采用的像是一种批处理方式。

组织方式不同，效率就会不同。批处理方式可能让数据放进去更快，但在查询时未必同样快；整齐归类的方式可能让摆放慢一点，却可能使查询更快。数据库管理系统的差异，道理就在这里：底层安排、运行逻辑与资源利用方式不同，最终表现自然不同。

当 App、网页或小程序提出要求时，它像是在对 DBMS 发出指令。让家人从房间里拿出某件东西，是查询；把新东西放进去，是增加；拿走或替换，是删除与修改。DBMS 接到应用请求后，在自己的数据库里完成这些工作。

所以别再只把数据库看成一堆文件。文件是数据，管理这些数据的系统，才是技术真正要解决的问题。

### 文件系统留下的四道坎

最后，再回头看数据库的历史。现代意义上的第三代数据库是关系数据库，但它不是凭空出现的。前面的路，要走过人工处理阶段与传统的文件系统阶段。

人工处理阶段，是最早的年代。早期计算机存储使用的 3.5 英寸软盘，存储能力峰值只有几个 MB，不可能支撑今天意义上的大规模数据存储。因此，那个阶段主要靠人和简单机器进行数据管理，就像拿计算器做一做加减乘除，把结果显示在屏幕上，数据随即消失。

第一代到这里就先跳过。真正值得停下来讲的，是夹在第一代与今天的第三代之间的第二代：传统文件处理系统，即 `File Processing System`，缩写 `FPS`。

这个系统里，不同部门拥有各自的用户、文件，以及围绕这些文件工作的应用程序：

```text
财务处 --> 工资应用程序 <--> 工资文件
教务处 --> 成绩应用程序 <--> 成绩文件
学工处 --> 学工应用程序 <--> 学工文件
```

它和今天的系统有一个根本差别：今天的系统会把数据统一存放，由前端应用发出请求，再由集中的软件处理数据；而 FPS 中，用户的文件与应用绑定在一起，没有一个统一的软件来帮助大家处理集中数据。

它带来的问题，不是简单地说“文件多了”就能概括。我们来看几个最典型的坎。

#### 应用与文件绑得太紧

在 FPS 中，应用程序与自己的衍生文件高度依赖。

比如，领导的第一个问题是：“我们单位的平均工资是多少？”程序员要先专门编一个程序，打开存放工资的文件，把所有工资加总、除去人数，再把平均工资返回给领导。

第二个问题马上来了：“谁挣钱最多？”这又需要新编一个程序，打开同一个文件，把工资排序，再取第一名。

第三个问题可能还是：“工资最高的女性员工是谁？”再编一个程序，再打开文件，再计算一次。

每换一个问题，就要重新写程序、重新访问文件，这就是应用程序与文件高度依赖带来的复杂性。今天的 DBMS 之所以重要，正是因为它不应该让每一个新问题都变成一次从头开始的专门开发。

#### 冗余与不一致

学校不同职能部门各有一套学生文件，也会造成数据高度冗余。

假设有一位学生 A，在财务处、教务处、学工处与商学院都分别有自己的文件。财务处存学号、姓名、性别、所在系，再存学费缴纳、补贴发放等财务信息；教务处也存学号、姓名、性别、所在系，再存成绩等教务信息。相同的基本信息被重复存放多次，当然不科学。

接着还会出现数据不一致。

假设 A 在自己的本专业学院读劳动经济学，同时到法学院修辅修学位。有一天，他换了电话号码，因为经常与本专业学院联系，第一时间向本专业学院报了新号码，却忘了向法学院更新。

这时，本专业学院文件里的电话号码是新的，法学院文件里的电话号码还是旧的。同一个人、同一项基本信息，在不同文件里已经不一致。

冗余与更新遗漏一起出现，就会破坏数据的可信度。问题不只是重复占了空间，更在于同一事实可能在不同地方变成不同答案。

#### 没有回卷，转账可能丢钱

这一代系统还有一个很有意思的问题：没有 `Rollback` 回卷机制。

回卷是什么意思？一个事件从 A 端到 B 端，要么完整发生，形成确定结果；要么在中途遇到问题时，立刻回到初始状态，当作这件事从未发生。这个机制就叫回卷。

把它放进银行转账中，就很容易看出为什么重要。

假设 A 同学和 B 同学各有 1000 元，A 要向 B 转账 200 元。正常情况下，A 账户先从 1000 减到 800，这 200 元再进入 B 账户，使 B 账户从 1000 变为 1200。最后两边合计仍然是 2000 元，只是钱换了位置。

但如果中间出了故障呢？A 这边已经完成 1000 减 200，剩 800；这 200 元正在转移途中，B 账户还没完成加 200，此时系统崩溃。

有回卷机制，就不会慌：A 账户恢复 1000，B 账户保持 1000，转账没有完成，就当它没发生。没有回卷，A 减掉的 200 元已经离开原账户，B 又没有收到，200 元就可能在途中消失。

所以，没有这种机制的系统可以用于内部文件管理，但用在银行转账上必须非常慎重。不能拿一个“处理过程中崩溃就可能丢钱”的系统，去承担必须保证转账完整性的业务。

#### 同时支钱，会算错

除了转不过去，还可能并发访问出错。

假设班主任手里有 1000 元。班长要支 200 元办活动，学委要支 100 元办读书活动。

如果事情有先后顺序，班主任先给班长 200 元，余额是 800；再给学委 100 元，余额是 700。这没有问题。

问题出在班长、学委和班主任分别被当成不同的应用程序，而且班长与学委在完全相同的时间同时打开了班主任这个文件。

```text
正确顺序：1000 -> 800 -> 700

同时读取：
班长：1000 - 200 = 800
学委：1000 - 100 = 900

正确终值：800 - 100 = 700
```

班长认为终值是 800，学委认为终值是 900；他们都没有得到正确的 700。根因是，两边同时读到初始的 1000，却没有把后续变更正确地依次衔接起来。

像选课这种需要很多同学同时参与的活动，不解决并发访问问题就根本无法支撑。这里的道理，与前面“有回卷就不能让钱消失在途中”一样：数据系统不能只考虑顺利时能不能算出结果，还必须考虑冲突、失败与同时访问时会不会把结果算坏。

至此，数据库并不是从“把文件放在一起”突然出现的。它经历了人工处理阶段，经历过以 FPS 为代表的文件处理阶段，也付出了应用与文件高度依赖、数据冗余与不一致、没有回卷、无法可靠并发访问等代价。

所以我们今天真正要研究的是关系数据库背后的 DBMS：它如何搭建数据库，如何完成增加、删除、修改、查询与控制，如何响应应用请求，又如何把数据的逻辑结构与物理结构隔离开。

到这里，数据库、数据库管理系统、文件、记录、字段、实体、属性，以及它们在系统中的位置，就不再只是一些孤立的名词了。前面从商务智能一路追下来的问题也终于有了答案：信息系统之所以能描述、预测并支持行动，不只是因为“有数据”，而是因为有一整套把数据组织起来、管理起来，并让数据可靠流向应用的技术与系统。

## 从一粒比特到数据库系统
> 对应块：BLK04 | 覆盖分集：P03 | 块标题（分集名）：《数据库系统第一章 绪论 （上）》

这学期我们开始一门新课：数据库系统概论。

先把话说直白一点。我们以前谈 IT 行业时，常见的三件事就是数据的存储、数据的处理和数据的传输。数据库从名字上看，首先就是在解决“数据存起来、以后还能找回来”的问题。但不要一听到“数据库”就急着背定义，更不要以为它就是一堆放在硬盘里的文件。我们先把这门课要学什么、它和整个信息系统是什么关系，以及它为什么值得认真对待，连起来看一遍。

### 先把课程和教材放在一起看

这门课的主教材是《数据库系统概论》第五版，高等教育出版社出版，作者是王珊和萨师煊。国外的核心课程教材是 *Database System Concepts*，课堂展示的是第六版，作者来自耶鲁大学，中文语境里也常看到它的机械工业出版社译文版。我们国内普遍直接使用的中文教材，就是前面那本《数据库系统概论》；它既借鉴了相关内容，也补充了自己的内容。

这三本书都可以在网上找到，但这里要先把边界说清楚：按知识产权 considerations，教材最好还是买一本正版收藏。确实想找电子版的同学，可以自己去正规渠道寻找，别把版权问题当作课程内容的一部分。书本身值得收藏，因为几乎国内学校讲数据库，都会围绕它展开。

课程内容大体分成三块。

| 部分 | 关注的问题 | 教材中的内容 |
| --- | --- | --- |
| 基础 | 数据库的原理、概念，以及最基本的操作语言和约束 | 绪论、关系数据库、SQL、数据库安全、数据库完整性 |
| 设计与应用开发 | 怎样判断一个设计好不好，怎样把数据库设计出来，怎样让程序使用它 | 关系数据理论、数据库设计、数据库编程 |
| 系统 | 数据库怎样处理查询，怎样在并发和故障中保持可靠 | 关系查询处理与查询优化、数据库恢复、并发控制、数据库管理系统相关内容 |

基础部分对应教材前面五章，设计与应用开发对应关系数据理论、数据库设计和数据库编程，系统部分则把视角推到查询处理、查询优化、恢复和并发控制。全书大约十二章左右，每一章的 PPT 都可能有一百多页，第一章就有 150 页，不可能一次讲完。我们会按知识内容拆成几次更新，尽量保持一周两次左右；更新有时会因为日常安排不规律，但目标始终是把每一章讲完。

这里要先把“数据库学什么”和“我们要学什么”分开。数据库是一个对象，数据库管理系统是管理这个对象的软件。后面会看到，课程真正要深入研究的是后者：数据库管理系统怎样组织数据，怎样高效地增加、删除、修改和查询数据，怎样在不同用户、不同系统和不同硬件之间把数据支撑起来。

> **结论**：数据库不是“把文件扔进一个文件夹”就结束了。真正困难、也真正值得学习的地方，是怎样把这些文件变成有组织、可共享、可维护、能被系统可靠使用的数据集合。

### 课程之外，还要建立跨学科的思维框架

除了数据库本身，这门课还会持续训练一种思维方式。我觉得它和数据库知识同样重要。

我们学的课程大致可以分成两类。技术类课程包括计算机基础、计算机网络、数据库、Python、Java、C++ 这样的内容；偏组织、管理和经济方面的课程，则包括社会学、经济学、心理学、组织行为学、战略管理等等。把它们放在一起，就构成了一个更大的跨学科思维框架，也可以叫作 multidisciplinary thinking paradigm，也就是多学科的思维框架。

```text
技术类课程                         组织、管理与经济类课程
计算机基础  数据库  网络            社会学  经济学  心理学
Python     Java   C++               组织行为  战略管理  ……

                 ↓
        跨学科的思维框架
   用多个学科的视角共同理解问题
```

单一学科的思维很容易形成“锤子精神”：手里拿着锤子，看什么都像钉子，什么问题都想拿锤子砸一下。这不是说某个学科没有价值，而是说一个学科的边界往往比真实问题的边界窄。

比如经济学里，稀缺和边际效益递减是重要的支柱。如果一个问题确实完全落在经济学的边界里，从经济学理论出发认识它、解决它，当然没有问题。可是现实中的问题经常不是这样。比如疫情一来，可能同时牵涉大数据管理、生物工程、医药、组织运作，甚至政治问题。你只从经济学或者生物学的角度去看，哪怕专家在自己的专业范围内说得完全正确，也很难形成对整个问题的全面认识。

这就解释了为什么我们会觉得：有些专家说的都很有道理，可最后还是没有解决问题；有些同学每门课都考得很好，却说不清楚这些课程放在一起到底有什么用。课程本身并不是没用，真正出现在培养方案里的内容，往往经过了很多人的推敲。问题可能出在我们还没有把它们挂到同一个框架上。

当各个学科里的经典理论和知识被放到跨学科框架里，时间久了，我们会逐渐拥有多元视角，认知水平也会抬高。这就是为什么在数据库课程里，除了表、SQL 和查询之外，我也会不断引导大家思考：数据从哪里来、怎样被加工、怎样进入社会应用，以及这些环节和哪些其他课程相连。

#### 互补性资产：只押中一件东西还不够

和跨学科框架一起看，还有一张很重要的图，叫“互补性资产的视角”。

保证企业或组织的主营业务投入获得回报的资产，叫做互补性资产。一个企业的核心产品做得好，不代表它一定能把产品卖出去；如果配套能力没有跟上，核心资产也可能发挥不出完整价值。

```text
核心业务投入
    ↓
互补性资产投入
    ↓
生产率提升与企业回报
```

以手机为例。手机的设计和生产是主要投入，但电池、摄像头、屏幕、光学系统、声学系统、精密器件等，并不一定都由同一家公司生产。屏幕、光学、声学、精密器件来自不同的企业，任何一环做得不好，整个手机都可能卖不动。第一代 iPhone 的待机时间很短，即使手机本身设计得很好，用户也未必愿意长期使用；应用生态如果跟不上，手机的价值同样会被削弱。

所以，企业在 IT 领域投入了很多钱，却没有得到相应的生产率提升，一个常见解释就是互补性资产投资不足。我们学习数据库也是一样的：不能只盯着数据库这一门课，还要理解数据存储、处理、挖掘、社会应用以及相关系统之间怎样相互支撑。只把一门课学得很窄，未必能在这个领域走得很深。

我们这十几周想同时完成两件事：把数据库课程内容讲清楚，也帮助大家把跨学科的思维框架搭起来。

### 数据库为什么值得认真对待

数据库产生于 20 世纪 60 年代末，是数据库管理的有效技术，也是计算机科学的重要分支。它是信息系统的核心和基础，推动计算机不断进入各个应用行业；对今天的人来说，它已经是生活中不可或缺的一部分。

为什么数据库的行业地位这么高？先不从抽象定义开始，我们看一部手机。

苹果公司那个被咬了一口的苹果 logo，常见的一种解释是向阿兰·图灵致敬。计算机行业没有诺贝尔奖，阿兰·图灵奖是计算机领域的最高奖之一。图灵和香农的工作，共同奠定了现代计算机的雏形：图灵奠定控制论方向，香农奠定信息论方向。图灵还在曼彻斯特大学学习和工作过，而图灵奖在计算机行业中的分量非常高。

我们还可以继续沿着这个故事往下想。图灵在战争年代曾为破解德军密码作出重要贡献，但他在当时的社会制度下，因为自己的性取向受到歧视和不合理对待，被迫接受当时人们认为能够“治疗”同性恋的激素处理，最终精神崩溃并自杀。课堂上常用“咬过一口、上面有氰化钾的苹果”这个故事来讲他的结局，苹果 logo 的含义也就更容易被记住了。想进一步了解这段历史，可以看《模仿游戏》（*The Imitation Game*）。

数据库领域历史上以数据库为基础的研究成果三次获得阿兰·图灵奖。这个事实至少提醒我们：数据库不是某个产品里的附属功能，而是计算机行业中能够持续产生基础性成果的重要方向。

### 数据在信息系统中的位置

理解了数据库为什么重要，接下来还要回答一个位置问题：一个组织真正搭建信息系统时，数据库究竟站在哪里？

可以把整体链路画成这样。

```text
ERP、Legacy、POS、OLTP、网页、外部数据
                    ↓
        ETL：提取、转换、加载
                    ↓
             数据仓库 Data Warehouse
                    ↓
       面向主题的数据集市 / 部门数据库
        财务       教务       学生工作
                    ↓
       API、中间件、应用数据接口
                    ↓
       应用系统与用户：报表、分析、交互
```

最左边是数据来源。企业资源规划（ERP）是其中一种；Legacy 表示历史系统，POS 是销售点系统，OLTP 是在线事务处理，网页和外部数据也都会不断产生新的信息。数据来到之后，不能想当然地把所有格式原封不动地塞进数据库，中间必须经过 ETL，也就是 Extract、Transform、Load：提取、转换、加载。

为什么一定要转换？以学校为例，财务处、教务处、各个学院可能都在保存同一个学生的生日。有的系统写成月日年，有的系统写成年月日；有的用横杠，有的用斜杠，有的用点。表达的是同一件事，格式却不同。不同系统还可能把同一字段设置成不同的数据类型，有的用小整数，有的用更大的整数，数值范围也可能不同；有些表格为空，究竟是留空、补零，还是保留未知状态，也需要统一处理。数据进入一个共同的数据库之前，必须先把这些差异整理好。

处理后的数据通常先在企业中形成一个中央性的整合结果，这叫数据仓库（data warehouse）。可以把它想成图书馆：数据像一本书，仓库负责大量、历史性数据的存放；一本书放到三楼某个区域、某个书架上之后，还要给它建档，记录书名、作者、出版社、出版年份和存放位置。这个索引就是 metadata，也就是元数据。再配合 replication，也就是复制或备份机制，仓库里的数据就有了一份安全的后盾。

为什么不把所有历史数据都放进每天频繁使用的业务数据库？因为学校数据库每天都在被增加、删除、修改和查询，可能遇到安全问题，也可能崩溃或损坏。历史数据如果一直跟着日常业务使用，还会持续消耗系统资源、占用磁盘空间。于是，大量且不经常使用的历史数据放进数据仓库，日常业务数据则留在更适合频繁操作的数据库中，这个区分就清楚了。

数据仓库还可以按主题形成面向局部用户的数据集市，也就是 data mart。在这个课堂的示意里，面向财务处、教务处或学生处的 data mart，可以理解成对应部门使用的小型数据库。例如，全校数据在仓库中，财务处只取和财务有关的部分，把学号、姓名、专业、学费缴纳情况、补贴等放在一起，就形成财务处自己的数据集市；教务数据和学生工作数据也可以分别形成各自的子集。

这些面向主题的数据再通过 API、中间件或应用数据接口，为前端应用提供数据支撑。后端还可以做报表、数据挖掘、在线实时分析等事情。于是数据库的位置就清楚了：它不是孤零零地待在硬盘上，而是处在数据来源、加工、仓库、部门子集和前端应用之间的关键支撑位置。

### 数据放好之后，能回答哪些问题

数据存下来并不是终点。总体来看，它要帮助我们回答三类问题。

| 类型 | 关心的问题 | 常见工具与方法 | 直观例子 |
| --- | --- | --- | --- |
| 描述性 | 过去发生了什么，正在发生什么 | 数据可视化、报表、表格、饼图、柱状图、散点图 | 看成绩单、年报 |
| 预测性 | 将来可能发生什么，为什么会发生 | 数据挖掘、文本挖掘、Web 挖掘 | 购物车推荐还要买什么 |
| 规范性 | 如果预测发生，我应该怎么做才最优 | 数学建模、最优化、仿真模拟、决策模型、专家系统 | 在约束条件下选择行动方案 |

描述性问题关心的是过去和现在。上学期成绩怎么样，看成绩单；上市公司的经营情况怎么样，看年报；这些都是把已经发生的事情用报表或图表呈现出来。表格、饼状图、条状图、散点图、柱状图等数据可视化方式，本质上都是帮助我们理解过去和现在。

预测性问题把目光放到当下之后：what will happen，why will it happen。你在网上购买一本书，平台根据相关数据推荐购物车里的其他书，这就是数据挖掘的一个直观场景。数据挖掘、文本挖掘、Web 挖掘等工具，都是在已有数据中寻找能够指向未来的规律。

规范性问题再向前一步：过去、现在和未来都比较清楚了，如果预测真的发生，我应该怎么做才是最优的？这时就要用数学建模、optimization、simulation、decision modeling、expert system 等方法。换句话说，数据库提供底层数据，但数据本身还要经过分析、预测和决策，才会真正发挥作用。

### 从 0 和 1 到一个数据库

现在我们再往底层走一点，看看数据库到底是怎么形成的。

```text
0 或 1
  ↓
位 bit
  ↓
8 个 bit = 1 个字节 byte
  ↓
字段 field
  ↓
记录 record
  ↓
文件 file
  ↓
围绕同一主题组织起来的文件集合
  ↓
数据库 database
```

最底层是 0 和 1，一个这样的最小信息单位叫 bit。8 个 bit 放在一起组成一个 byte，也就是字节。比如 01001001 按照 ASCII 码表可以转换成一个英文字母 I。课堂里还用 16 个 bit，也就是两个字节，来说明中文编码所占的字节空间；这里先记住“位组成字节，字节承载更复杂的数据”这个层次关系即可。

有了字节，就可以把一组具有具体含义的内容组织成字段（field）。例如 `学号` 是一个字段，`姓名` 是一个字段，`课程名称`、上课时间、成绩也各自是字段。把一条学生记录中的这些字段按顺序组织起来，就形成一条记录（record），也就是一行数据。

班里有一百位同学，就会有一百条这样的记录。把这些记录放进 Word 文档或 Excel 表格，就形成文件。不同课程的成绩单文件、每个人的财务文件、学生文件等，如果都围绕同一个班级主题组织起来，就很像一个数据库。

到这里有人可能会说：数据库不是很简单吗？把文件放在一起不就行了吗？

确实，数据库的形成过程可以讲得很朴素；我们真正要学的不是“把文件放到一起”这个动作，而是数据库管理系统（DBMS）。数据库管理系统负责把数据库搭建起来，并且在用户提出“增加一条数据、删除一条数据、修改一条数据、查询一条数据”这样的要求时，负责把操作高效地完成。

### 数据、信息、知识与智能

在四个基本概念之外，还有一条理解数据的逻辑线：数据怎样变成信息，信息怎样变成知识，知识又怎样进一步变成智能。

拿数字 24 来说，它本身只是数据。单独放在 Excel 的一个单元格里，我们不知道它是什么意思。只有加上人的语义，比如“今天的气温是 24 摄氏度”“咱们班有 24 个同学”，或者“科比·布莱恩特的号码是 24 号”，数字才和具体对象、具体含义联系起来，成为信息。

```text
数据 Data
  + 人类的语义结构
  ↓
信息 Information
  + 对现象的观察、分析与整理
  ↓
知识 Knowledge
  + 场景、知识库、反馈与行动
  ↓
智能 Intelligence
```

信息变知识的过程，可以拿笔和蔬菜来理解。我们观察到一支笔松手后会掉落，这是一个现象；牛顿用万有引力定律解释它，于是现象被整理成理论。科学家不断观察、比较和整理类似现象，就形成知识、理论和思维框架。知识能够帮助我们解释、描述和预测现象。

比如我们观察蔬菜的保鲜情况：蔬菜放在 24 摄氏度下，保鲜期可能只有半个小时；放十分钟没事，放一个小时就坏了。经过反复观察和研究，人们找到了更合理的保鲜温度范围，比如 2 到 5 摄氏度。这就不再只是一个孤立现象，而是对现象背后规律的知识。

智能则是知识在具体场景中发挥作用。我们人类通过 DNA 传承获得一些 message 和信息，比如没有真的被蛇咬过，却看到蛇就会害怕，这里面就有祖先经验形成的 knowledge base。遇到一个场景时，我们下意识地把场景和知识库进行比较，再给出相对最优的反应。计算机的智能也有类似的逻辑：把人的知识整理成知识库，遇到 circumstance 时进行比对、反馈，最后采取行动。

智能冰箱就是一个小例子：鲜蔬层检测到放入蔬菜，就自动把温度调整到 2 到 5 摄氏度。这里既有数据，也有信息和知识，最后还形成了根据场景采取行动的智能。

所以，数据是一切链条的基础。数据库负责的是数据存储这一环，而它是所有 IT 应用后面很重要的一块基础。

### 数据库：从文件集合到共享数据集合

我们前面用班级的文件集合做了一个直观解释。正式定义上，数据库是长期存储在计算机内的、有组织的、可共享的大量的数据集合。

> **定义**：数据库不是一堆互不相干的文件，而是长期存储在计算机内、经过组织、能够被共享的大量数据集合。

这个定义里有几个关键词。

“长期存储”说明它不是只在程序运行的一瞬间存在；“有组织”说明数据要按照某种模型和结构来组织，而不是随意堆放；“可共享”说明它不是只给某一个人看，而要支持多个用户共同使用；“大量”则说明它面向的是组织性的数据集合，而不是一份孤立的小文件。

课程在绪论阶段还会列出数据库的一些基本特征：可以用一定的数学模型来组织、存储和描述；可以被许多用户共享；冗余度较小；容易扩展；数据独立性较高。现在不用死记这些词。等真正讲到相关地方，我会再提醒大家注意它们。到那时，看到一个设计为什么强调低冗余、为什么强调高独立性，含义会自然清楚。

### 数据库管理系统：真正被学习的对象

数据库管理系统，英文是 Database Management System，也就是 DBMS。它位于用户和操作系统之间，是一层管理软件。

它主要做两件事：

一是科学地组织和存储数据，把数据库的结构搭起来，让数据能够被放进去；二是高效地获取和维护数据，也就是高效地完成增加、删除、修改和查询。

这里可以继续用房间的比喻。数据库像一间屋子，屋里放的是你的 personal belongings，也就是个人物品。不同的人有不同性格：一个人东西码放整齐，知道每件东西放在哪里，找起来就快；另一个人随手乱放，找东西就可能很慢。

两个人不同的整理习惯，可以对应两种数据库管理系统。数据库本身是那间屋子，DBMS 则是管理屋子的方式和性格：它怎样搭建数据架构，怎样存放数据，怎样找到数据，怎样修改数据，都会影响最终效率。数据库管理系统的差异，不只是“有没有一个软件”的问题，也体现在它组织和管理数据的行为方式上。

大家平时听到的许多产品，其实都是数据库管理系统或相关数据管理软件。微软的 Microsoft Access 可以用来设计和管理较小的数据库；SQL Server、MySQL、DB2、Oracle、Kingbase 等产品性能和应用场景不同；Excel 虽然更常被当作个人表格和数据处理工具使用，但也可以承担个人小规模数据库的用途。云计算的发展又带来了 NoSQL，也就是非关系型数据库这一类新的选择。

> **提示**：听到 Excel、Access、SQL Server、MySQL、Oracle、Kingbase、DB2 或 NoSQL 时，不要把它们当成完全不同的“数据世界”。先问一个问题：它是在管理、组织和提供数据，还是只是我们拿来临时记录数据的工具？

数据库管理系统的主要功能，可以先记成三类。

| 功能类别 | 英文 | 它解决的问题 |
| --- | --- | --- |
| 数据定义 | DDL，Data Definition Language | 定义数据库中的数据对象，搭建数据库的框架 |
| 数据操作 | DML，Data Manipulation Language | 增加、删除、修改、查询数据 |
| 数据控制 | DCL，Data Control Language | 控制什么数据可以输入、查询，以及不同用户拥有什么权限 |

用盖房子来理解最省事。DDL 是盖房子、搭框架、安排数据对象放在哪里；DML 是房子盖好以后进行存取和整理；DCL 则是制定规矩，规定什么数据能进来、什么人能查什么。

### 数据库系统：把所有环节接起来

数据库系统（Database System，简称 DBS）不是某一个单独的数据库文件，也不是一个孤零零的 DBMS，而是把数据库、数据库管理系统、前端应用以及负责管理的人一起组织起来的整体。

用户使用 Word、百度云、微博、抖音、哔哩哔哩等应用时，看到的是界面，不会直接接触底层开发工具。应用由开发工具和平台构建，再通过 DBMS 去组织、查询和修改数据。真正的数据仍然存放在硬盘等存储设备上，操作系统负责把语言和逻辑转换成物理存储能够处理的 0 和 1。

```text
用户
  ↓
应用系统：Word、百度云、微博、抖音、B站等
  ↓
应用开发工具与开发平台
  ↓
数据库管理系统 DBMS
  ↓
操作系统
  ↓
存储设备与数据库文件：磁盘上的 0 和 1
```

数据库管理员（DBA，Database Administrator）同时关心数据库的物理层问题和软件问题：数据怎样落盘、怎样备份，数据库系统怎样配置、怎样维护，也都在他的责任范围内。

所以，从本地设备看，数据库系统大致就是用户、应用系统、开发工具、数据库管理系统、操作系统、存储设备和数据库文件之间的连接关系。数据库位于底层硬件之上，却通过 DBMS 和应用系统为用户提供数据支撑。

### 本地之外：三层客户机服务器架构

本地设备上的结构讲清楚以后，再把它放到网络环境里，我们会看到一个三层客户机服务器架构，也叫 three-tier client-server computing architecture。

```text
用户端 Client：手机、电脑、平板、浏览器
                    ↓
             公共互联网 Internet
                    ↓
       Web Server：处理网页导航等请求
                    ↓
 Application Server：处理点击、留言、观看、点赞等交互
                    ↓
 数据库服务器与后端系统：保存和处理视频及相关数据
```

用户在浏览器中输入网站地址后，请求通过公共互联网找到相应的网页服务器。网页服务器主要处理网页导航；当用户进入主页、定位到某一个视频并进行点击、留言、观看、点赞等交互时，主要由应用服务器处理。视频等数据并不是简单地由应用服务器一个人包办，而是继续交给后端的数据库服务器和相关系统去保存与处理。

这就是客户端、网页服务器、应用服务器、数据库服务器之间的分工。个人设备上的数据库系统，可以是本地结构；通过公开互联网访问的服务，则把客户端和服务器分开，各自负责自己的部分。我们今天看一个视频，背后其实正运行着这样一条分层的数据链路。

到这里，数据库的位置、形成过程、能够回答的问题，以及数据库管理系统的职责和系统架构就连起来了。我们学的从来不只是一个“文件夹”或者一种软件，而是一套让数据能够被组织、共享、处理、理解并最终支撑行动的基础系统。数据库是底座，DBMS 是管家，数据库系统则把用户、应用、硬件和管理者一起接到了这条链路上。

## 从文件系统到关系模型：数据库系统的来路与底层语言
> 对应块：BLK05 | 覆盖分集：P04 | 块标题（分集名）：《数据库系统第一章 绪论 （下）》

我们接着上一节，把数据库技术的产生和发展再往下推一层。数据库不是某一天突然从天上掉下来的东西，也不是一开始就长成了今天的样子。把它放到计算机发展的历史里看，今天我们使用的数据库系统，实际上是数据库发展的第三代。

这一代之前，经历过人工管理阶段和文件系统阶段；这一代之后，我们要面对的就不再只是“把数据存下来”这个问题，而是怎样让大量数据能够被不同的人共同使用，能够保持一致，能够被统一控制。这个转变，正是数据库系统真正要解决的问题。

### 数据库为什么会一代一代往前走

先问一个容易被忽略的问题：为什么会有不同代际的数据库？

答案不是某一种技术突然取代另一种技术，而是三种力量一起把数据库往前推。

第一，应用需求在不断推动。我们有了更多事情要做，就希望能够保存更多数据、处理更多数据、让更多人同时使用数据。没有需求，新的技术就没有落脚点。

第二，技术发现和技术创新也在推动。原来做不到的事情，随着人们不断研究新的组织方式、存取方式和处理方法，慢慢可以做了。

第三，计算机硬件和软件一直在发展。早期没有磁盘，后来有了；早期没有操作系统，后来有了；早期只能做科学计算，后来联机处理、分布式处理、批处理都逐渐可以做了。硬件和软件提供了新的条件，数据库技术也就有了新的空间。

所以，下面三代并不是简单的“旧东西被新东西淘汰”，而是每一个阶段都在解决前一阶段解决不了的问题，同时又暴露出新的问题。

### 人工管理阶段：数据能用，却留不住

人工管理阶段大约在 20 世纪 50 年代中期。它的背景很鲜明：应用场景主要是科学计算，硬件上还没有直接的存取设备，软件上没有操作系统，处理方式是批处理。

这几个条件放在一起，大家可能很难脑补出来。我们先用一个不那么精确、但足够形象的比喻：把它理解成一个计算器。

你可以在计算器有限的内存里输入一些数据，让它完成一次运算，也可以在计算器里暂时保留一些内容。但是，能不能进行大规模运算？能不能进行大规模的数据存储？不能。

所以人工管理阶段的特点可以概括为：数据拿来用可以，但不太容易保存。

它面向的是某一个应用程序。一个应用程序需要数据时，就把数据交给这个程序；程序本身又和文件连在一起，程序需要什么，就得把相应数据重新准备进去。于是，数据的共享程度很低，冗余度却很大，而且数据不独立，依赖程序。

把它的结构画出来，大致是这样的：

```text
应用程序 1 ───── 数据集合 1

应用程序 2 ───── 数据集合 2

应用程序 3 ───── 数据集合 3

应用程序 N ───── 数据集合 N
```

每个程序只对应自己的数据集合，彼此没有统一联系。下一次再有新的需求，就可能要重新写一个应用程序、重新准备一份数据。这里的关键问题不是数据不能算，而是数据没有形成一个可以被共同使用的整体。

### 文件系统阶段：数据能留下，却管不好

有了科学计算和数据管理的需求，硬件上开始出现磁盘，软件上开始出现文件系统，数据库技术就进入了文件系统阶段。它的英文缩写是 `FPS`，也就是 `File Processing System`。

这一阶段已经可以把数据长期保存下来，这比人工管理阶段前进了一大步。但是，数据的共享性还是较差，冗余度还是较高。

它的结构可以理解为“应用程序—存取方法—文件”：

```text
应用程序        存取方法        文件

会计部门 ───┐
人力部门 ───┼── 中间协调 ─── A、B、C、D 等文件
销售部门 ───┤
生产部门 ───┘
```

如果把学校系统带进来想象，会更容易理解：财务处、人事处、教务处、各个学院，都可能有自己的应用系统和文件。它们都需要学生、课程、成绩等数据，但每个部门都可能把一份学生信息留在自己的文件里。

我们可以用一个很直观的例子来看这套结构。A 同学是班里的一位学生，他有学号、姓名、班级、年级、所在系等基本信息。财务处可能存一份，教务处可能存一份，人事处也可能存一份。各部门只需要再补充一些和本部门有关的内容，例如财务数据、课程数据，公共信息却重复保存了很多遍。

纵向一看，数据高度冗余，这不是偶然，而是这种组织方式的必然结果。

#### 数据高度冗余

同一个学生的学号、姓名、专业、所在系，本来是同一类信息，却在多个部门的文件里重复出现。不同文件之间只多了一点本部门专属内容，并不代表公共部分可以自动共享。

这里要记住：冗余不是“数据多写了几个字”这么简单，而是同一事实被多处分别保存，保存的份数越多，更新时越容易漏掉一处。

#### 数据可能不一致

假设 A 同学的主要学院是会计学院，同时在工商管理学院修了一个双学位。两个学院都可能为他建立档案，而且档案中的个人信息本来应该一致。

后来 A 同学换了电话号码。他记得向主要学院报备，于是一个档案里的号码更新了；另一个学院因为只是第二学位，他一时忘记报备，号码仍然是旧的。两个文件里明明存着同一个人的同一项信息，对照起来却不一样了。

这就是不一致性。它不是因为两个档案都错，而是因为同一个事实被分开维护，更新没有同时发生。

#### 应用程序和文件高度依赖

用户想使用文件中的数据，通常要通过应用程序来做。假设我是一个小团队的负责人，今天先问：“谁是单位里收入最高的员工？”

那就写一个应用程序：打开工资表，按工资升序排列，把最上面的那个人取出来。过一会儿再问：“平均工资是多少？”还要再写一个应用程序：找到同一个文件，计算平均数。再问“最低工资是谁”，又得再写一个程序。

问题在于，文件没有变，需求却不断变化。每提出一个新问题，就要重新写一个应用程序来处理同一个文件。应用程序和文件之间高度依赖，显然不科学。

#### 不能并发访问

我们用班费来说明。假设班费账本上有 1000 元，班长要支取 200 元，学委要支取 300 元。

如果两个人严格排队，事情很简单：班长先支取 200 元，账本剩下 800 元；学委再支取 300 元，最后剩下 500 元。文件关闭，结果没有问题。

但如果两个程序在同一个瞬间同时打开这个账本，它们看到的初始值都是 1000 元。班长程序支取 200 元，得到 800 元；学委程序也支取 300 元，也得到 800 元——只不过学委的 800 是从它看到的 1000 元算出来的。最后文件关不上，因为 800 和 700 到底哪个应该保存，谁也说不清。

正确结果明明应该是 1000 - 200 - 300 = 500，但两个程序各自都以为自己完成了完整操作，最后却没有一个确定的结果。这就是不能并发访问的麻烦。

#### 没有回滚机制

再看转账的例子。班长账户有 1000 元，学委账户也有 1000 元。班长向学委转 200 元，完整过程应该是：

```text
初始：班长 1000，学委 1000
转账后：班长 800，学委 1200
```

如果中途系统崩溃，数据库应该把这件事回滚到初始状态：班长仍然是 1000，学委仍然是 1000。

可是没有回滚机制时，可能出现班长已经变成 800，而学委仍然是 1000。那 200 元既没有完成转账，也凭空消失了。这里的“要么完整发生并保存，要么中间出了问题就回到初始状态”，就是回滚机制要保证的事情。

所以，文件系统阶段的五个典型问题可以合在一起看：数据高度冗余、可能不一致、应用程序依赖文件、不能并发访问、没有回滚机制。它们并不是五个互不相关的小毛病，而是共同指向一个问题：文件只能被保存，却没有被一个统一的系统管理起来。

### 数据库管理系统：把文件收进一个屋子

为了弥补这些问题，数据库技术发展出了第三代，也就是数据库管理系统，英文叫 `DBMS`，即 `DataBase Management System`。

它出现的背景更成熟：数据可以进行大规模管理，磁盘容量越来越大，甚至出现了大容量磁盘阵列；文件开始由系统来管理；处理方式也不再只有批处理，还可以进行联机实时处理、分布式处理等。

它的基本结构，是把原来分散在各处的文件放到一起，由一个中间的软件统一响应需求：

```text
        应用程序
            │
            ▼
      数据库管理系统
   定义 · 增加 · 删除 · 修改 · 查询 · 控制
            │
            ▼
          数据库
```

这里的“中间的小软件”就是数据库管理系统。它不是把数据放在那里不管，而是负责数据的定义、数据的增加、删除、修改、查询，以及数据的控制。

这三类动作可以对应为三种功能：

- `DDL`，数据定义语言，定义数据的结构；
- `DML`，数据操作语言，完成增加、删除、修改和查询；
- `DCL`，数据控制语言，控制数据，保证数据使用过程符合相应规则。

从这里看，文件系统阶段的问题就不只是“文件不够聪明”，而是没有一个能够统一管理所有数据的系统。第三代数据库的进化，正是把原来分散的存取结构固定下来，形成数据库管理系统，让应用程序不必再为每一个文件、每一个查询重复写程序。

可以把三代的演化压缩成一条主线：

```text
应用程序始终存在
        │
        ▼
人工管理：应用程序 ── 各自的数据集合
        │
        ▼
文件系统：应用程序 ── 存取方法 ── 文件
        │
        ▼
数据库系统：应用程序 ── 数据库管理系统 ── 数据库
```

数据库可以这样定义：它是长期存储在计算机内、有组织的大量共享的数据集合，可以供各种用户共享，具有较小的冗余度和较高的独立性，并且能够统一控制，以保证数据的完整性、安全性、并发访问和可恢复性。

### 数据库系统的特点

理解数据库系统的特点，最好的办法仍然是回头看文件系统阶段的缺点：哪些问题被数据库管理系统的统一管理弥补了，今天的数据库系统就具有相应的特点。

#### 数据是结构化的

数据库中的数据按照统一的数据结构存放，并且用数据模型进行描述。它和具体程序不是一回事，不能说某个程序改一下，数据结构就跟着变成另一个样子。

我们平时说的结构化数据，往往是可以用数学方法处理的数字；图像、音频、视频、网页、流媒体等，则属于非结构化或半结构化的数据。微积分不能直接处理一段视频，也不能直接处理一段音频，这一点很容易理解。

但数据库管理的目标，是让进入数据库的数据能够按照统一的结构化方式存放，方便后续使用。这里并不是说所有数据天生都长得一样，而是说系统要给它一个可管理、可使用的结构。

#### 共享性高，冗余度低

在文件系统阶段，同一个学生的信息可能被财务处、教务处、人事处分别保存。数据库系统把数据和文件统一放在一起，各部门需要什么，就通过数据库管理系统去取，不再由每个部门各自保存一份完整副本。

所以共享性高和冗余度低是同一件事的两面：数据只有一套统一管理，各部门共享使用，就不必为了不同使用者不断复制许多份。

#### 数据独立性高

独立性通常要从三个层次来看：物理层、逻辑层，以及应用或概念层。这里先不深入，后面还会专门讲。我们先抓住两个最容易被忽略的点。

物理独立性关注的是存储细节。二维表在计算机里最终要表现为一串 0 和 1，这些 0 和 1 又要放到磁盘的具体位置上保存。把二维表映射成 0 和 1、把 0 和 1 映射到物理磁盘上，属于物理层的存储问题。

我们使用数据库时，通常只要在屏幕上点击、输入，并不需要关心一张表究竟怎样映射到磁盘扇区，也不需要关心每个物理地址如何安排。这就是物理独立性。

逻辑独立性关注的是逻辑使用。只要把想存放的数据用二维表的形式表达出来，就不必操心它在磁盘上的具体位置；应用程序也不需要随着数据库内部存储方式的变化而全部重写。应用程序和数据库各自保持一定的独立性，需要数据时连接起来即可。

> **易错点**：独立性不是“数据随便放”，而是把用户看到的逻辑结构与内部存储细节隔开。用户不必知道底层怎么实现，系统也不必把所有实现细节暴露给用户。

#### 由统一的系统管理和控制

数据库管理系统能提供数据安全性、完整性、并发访问和数据库恢复等能力。

“完整性”这几个字在数据库领域里，可以先把它理解成“游戏规则”。数据不是想写什么就写什么，必须符合相应规则。比如性别这一列规定只能输入“男”或“女”，如果误输入了 `95001`，系统就应当把这个错误指出来，而不是默默接受。

并发访问就是我们前面班费例子中要解决的问题：多个程序可以同时访问同一个数据库，系统需要让它们按照正确的结果运行。恢复则是我们前面转账例子中提到的回滚思路：事情中途出了问题，要把数据库恢复到正确的状态。

这几种能力合在一起，说明数据库系统的数据不是某个人手里的私有文件，而是由一个统一系统负责管理、约束和保护的公共资源。

### 数据模型：现实世界怎么变成计算机里的数据库

现在我们知道，数据库要统一管理数据，也知道它有结构化、共享、独立和受控制这些特点。但还有一个关键问题：现实世界中的东西，怎样变成计算机硬盘里的数据库？

这就是数据模型要解决的问题。

数据模型是对现实世界数据特征的抽象，通俗地说，就是对现实世界的模拟。它要满足三个要求：能够真实地模拟现实世界，容易被人理解，也便于在计算机上实现。它是数据库系统的核心和基础。

可以把整个转换过程想成三步：

```text
现实世界
   │  认知、抽象、建模
   ▼
概念模型
   │  转成可组织的数据结构
   ▼
逻辑模型
   │  映射成 0 和 1
   ▼
物理模型 / 计算机存储
```

人理解现实世界是一套方式，计算机硬盘保存数据又是另一套方式，中间需要一个转换环节。数据模型就是现实世界与计算机存储之间的这座桥。

我们按三个层次来看它。

#### 概念模型：把现实世界画出来

概念模型做的事情，可以用一个不太复杂的画面来说明：给你一根笔、一张纸，你能不能用一套比较规范的工具，把你理解的现实世界画出来？

思维导图是这种工具，系统流程图、业务流程图、描述数据流动的 `DFD`（data flow diagram，数据流图）也是。它们做的事情不同，但共同点是把脑子里的现实世界变成纸面上的结构。

在数据库这门课里，概念层使用的标准工具是 `E-R` 图，也就是实体联系图。`E` 来自 `entity`，表示实体；`R` 来自 `relationship`，表示联系；`D` 来自 `diagram`，表示图。因此它也写作 `ERD`。

流程图更关注事情发生的流程，思维导图更关注你想做的事情的顺序，实体联系图则从数据库的角度把现实世界中的实体、属性和联系画出来。它们看起来都是“画图”，但观察问题的角度不同。

#### 逻辑模型：把图变成数据结构

概念模型把现实世界画成了一张图，接下来还要把这张图变成计算机可以组织的数据结构。

逻辑模型关注的是设计数据库时采用哪一类数据结构。常见的有层次结构、网状结构、关系结构等。我们今天使用的数据库，逻辑结构最终是二维表；有些模型则会表现为树状结构，或者节点之间互相连接的网络结构。

所以，概念模型像是“把现实世界画出来”，逻辑模型则是“把画出来的东西组织成数据库结构”。

#### 物理模型：把数据结构变成 0 和 1

二维表或树状结构最终都要交给计算机保存，而计算机只认识 0 和 1。数据怎样表示，0 和 1 怎样放到磁盘上，怎样存取，这就是物理模型关心的问题。

可以把三个层次压缩成一句话：概念层把现实世界画图，逻辑层把图变成可组织的数据结构，物理层把数据结构变成 0 和 1 并存到磁盘上。

到这里，为什么后面介绍常用数据模型时主要看逻辑层，也就清楚了：物理层的具体实现由系统处理，我们先把注意力放在数据结构本身。

### 概念模型里的实体、属性和联系

概念模型不是一张随便画的图，它要把现实世界中的重要结构表达出来。通常要抓住三个东西：实体、属性和联系。

把它们放在一起，可以记成 `EAR`：

- `E`，entity，实体；
- `A`，attribute，属性；
- `R`，relationship，联系。

#### 实体：真实存在或被共同认可的存在

实体首先可以是看得见、摸得着的东西。比如手里的一支笔、戴着的眼镜、一个书架，当然人本身也可以是实体。

但“实体”并不等于“必须能摸到”。只要一个东西在人类世界中以共识的形式存在，它也可以是实体。比如一所大学、一家公司、一个组织。清华大学、人民大学、延安大学、西南联大，有的学校现在已经不在了，但我们仍然知道它们存在过，甚至还可以从家人的经历中确认它们曾经存在。

这类东西虽然看不见、摸不着，但它们是人类世界中的存在，因此同样可以进入数据库进行描述。

> **定义**：实体是现实世界中可以被识别、描述和管理的对象，既可以是具体的物品，也可以是人类共同认可其存在的抽象对象。

#### 属性和码：怎样描述一个实体

属性是用来描述实体的特征。比如描述一支笔，可以说它是白色的，可以问它有多重、多长、横截面有多宽、材质是不是塑料。

描述一个学生，则可以用学号、姓名、专业、年级、所在系等属性。理论上，只要描述得足够完整，就可以把这个实体区分出来。但实际使用时，我们更希望能找到一个属性，或者一组属性，给出它们的值以后就直接确定“这是谁”。

这样的属性叫作码。码就是能够唯一标识一个实体的属性；如果需要一个属性组合起来才能唯一标识，那么这个属性组也可以作为码。

比如给学生实体一个学号 `95001`，通常就可以直接确定对应的学生。姓名则不一定可靠，因为可能存在重名；年龄更不能单独确定一个学生，因为很多人可能是同一个年龄。

所以，属性是“描述这个实体是什么”，码则是“把这个实体准确认出来”。

#### 实体型和实体集

实体型可以先理解为框架，实体集则是同类型实体的集合。

这就像先规定一张学生表有哪些列，再把所有学生放进去。框架规定的是学生这一类对象应当怎样描述，集合则是实际有哪些同类对象。

#### 联系：实体之间怎样连接

现实世界中的实体并不是互相孤立的。学生属于某个学院，一个学院又包含多位老师；一个学生可以选多门课，一门课也可以被很多学生选择。

联系通常有三种情况。

- 一对一：一个班级有一个班长。
- 一对多：一位老师给很多位学生上课。
- 多对多：一个学生可以选五门课，一门课又可以被五六十位学生选择。

用实体联系方法，或者用实体联系图，就可以把这些关系表达出来。概念模型要做的，正是把实体、属性和联系放进同一张图中。

### 数据模型的三项组成

概念模型解决“怎样把现实世界画出来”的问题，逻辑模型解决“用什么数据结构承载这张图”的问题。除此之外，一个完整的数据模型还必须回答三个问题：数据是什么、数据怎么操作、数据必须遵守什么规则。

所以，数据模型通常由数据结构、数据操作和完整性约束条件三部分组成。

| 组成要素 | 它要回答的问题 | 课堂上的说法 |
| :--- | :--- | :--- |
| 数据结构 | 数据是什么，数据之间怎样联系 | 把数据组织起来 |
| 数据操作 | 可以对数据做什么 | 增、删、改、查 |
| 完整性约束条件 | 什么数据可以放进去 | 数据的游戏规则 |

#### 数据结构

第一件事是说明数据是什么，以及数据和数据之间的关系。这里正好和我们熟悉的“数据结构”课程接上：数据结构课程讨论数据、数据值以及它们之间的联系，这些联系可以表现为多种不同的数据结构。

所以，数据模型不是只有一张好看的表。它首先要决定数据如何组织、数据之间如何关联。

#### 数据操作

数据操作可以分成查询和更新两大类。把它记成“增删改查”更顺口：增加、删除、修改、查询。

“增删改查”不是四个孤立按钮，而是对同一份数据进行不同方向的处理。数据库管理系统需要明确支持这些操作，应用程序才有可能提出需求并得到结果。

#### 完整性约束条件

完整性约束条件就是数据的“游戏规则”。常见有三类：针对实体的规则叫实体完整性，针对联系的规则叫参照完整性，针对不同属性列的规则叫用户自定义完整性。

比如性别这一列规定只能取“男”或“女”，如果输入 `95001`，系统就应该报错。错误提示可以让窗口弹出来，告诉使用者数据类型或取值要求不满足，而不是让一个明显错误的数据悄悄混进去。

> **结论**：数据结构、数据操作、完整性约束条件三件事合在一起，才构成一个完整的数据模型。

### 常用数据模型：层次、网状和关系

常用的数据模型可以列出六种：层次模型、网状模型、关系模型、面向对象模型、对象关系模型，以及半结构化模型。

我们重点看前三种，是因为它们对应最基础的数据存储问题。后面的模型更多是在分布式存储、区块链等新问题面前，对基础数据结构进行更新或创新。先把最基本的结构弄明白，才不会把不同模型混在一起。

这三种模型并不是谁绝对好、谁绝对坏。它们各有擅长的地方，优缺点平衡之后，有的适合某类工作，有的适合另一类工作。我们观察它们时，主要看三件事：能不能表达实体，能不能表达联系，能不能给出约束条件；同时还要看它是否适合大规模数据存储。

#### 层次模型：树形的清楚，联系的表达受限

层次模型的结构像一棵树。比如下面这样的二叉树：

```text
          根节点 1
         /        \
       2            3
      /  \
     4    5
```

数据可以放在节点里，数据和它们之间的联系通过一层一层的关系来表示。我们可以在上面增加节点或数据，也可以删除、修改、查询，还可以制定相应的规则。因此，从数据模型的三项组成来看，层次模型具备成为数据模型的基本条件。

它的优点是结构清楚，能够比较清楚地反映数据之间的关系，查询起来也很快。

但它的致命缺陷也很明显：层次结构很难自然表达多对多联系。一对一可以表达，一对多也可以表达，但多对多就不行了。比如一个学生选多门课、一门课又被多个学生选择，用这种树形结构去硬套，就会变得很别扭。

层次模型查询快，这是优点；但真实世界中的多对多关系很多，不能灵活表达，这是缺点。两者放在一起，它就不适合作为今天面向大规模、面向所有人共同使用的那种数据库底层结构。

#### 网状模型：联系更自由，但规模一大就乱

网状模型不再要求所有节点都从唯一根节点一层层长下来。它把节点摆出来，节点之间有什么关系，就用什么方式连接。可以把它画成下面的样子：

```text
      A ───── B
       │    ╱  │
       │  C    │
       └── D ─┘
```

这样一来，一对一、一对多、多对多都可以表达，实体、联系和约束条件也都能放进去。和层次模型相比，它更接近现实世界中“多个对象彼此发生联系”的样子。

但“能表达”不等于“适合大规模存储”。我们用一个选课例子来看。假设有 10 个同学，8 门课程，而且要求全选。选课这个关系要记录每个人的每一门课和成绩：

- 1 号同学选 1 号课到 8 号课，共 8 条；
- 2 号同学再选 8 门课；
- 10 个同学一共就是 80 条记录。

如果实体更多，比如有 100 个实体，再让它们两两之间画出联系，纸面上的节点和线就会变得非常混乱。小规模数据库可以勉强使用，但规模一大，网状结构就不适合作为大规模数据库的底层数据模型。

#### 关系模型：把复杂的结构变成二维表

关系模型是这门课的重点，第二章还会具体展开。

1970 年，美国 IBM 公司 San Jose研究室的研究员 E. F. Codd 首次提出了数据库系统的关键模型——关系模型。在经历了数据库三代的发展和数据结构的多次尝试之后，这个模型给出了一个非常简洁的答案：大规模数据存储不一定需要复杂的树或网，一张表就够了。

关系模型的逻辑结构是一张二维表，由行和列组成。比如学生表可以是：

```text
学号 | 姓名 | 年龄 | 性别 | 系名 | 年级
```

数据一行一行地放进去。表本身可以看作学生实体，每一列是描述学生的属性，一行表示一个具体学生；行与行、列与列以及多张表之间的联系，又可以表达实体之间的关系。

它为什么适合做数据库的底层结构？因为实体、属性、联系三件事都能落在里面，而且人看得懂，计算机也能理解。层次结构像树，网状结构像网，关系结构就像一张表。表这种形式足够直观，也足够简单。

### 关系模型的基本语言

关系模型确定了以后，还要给这套结构一套专门的说法。它有点像学英语、日语、医学或数学，每门学科都有自己的术语体系。数据库也有自己的语言：人们平常叫它“行”“列”“单元格”，数据库中则分别对应元组、属性和分量。

先把最基础的一组词放在一起：

| 日常叫法 | 数据库术语 | 含义 |
| :--- | :--- | :--- |
| 表 | 关系（Relation） | 一张二维表 |
| 行 | 元组（Tuple），也叫记录 | 表中的一个记录 |
| 列 | 属性（Attribute） | 描述某一方面的数据 |
| 单元格 | 分量（Component） | 一个具体的取值 |
| 取值范围 | 域（Domain） | 属性可以取值的范围 |

关系等于二维表，这一点一定要说清楚。关系不是抽象的数学名词，在关系模型里，它就直接对应一张二维表。

#### 关系、元组和属性

一行在表中就是一个元组，也叫记录，所以：

```text
行 = 记录 = 元组
```

一列就是一个属性。年龄这一列是学生实体的属性之一，性别这一列也是属性。属性的取值要来自某个域，这里要把“列”和“域”分清楚：列是位置和名称，域是这个属性允许取哪些值。

比如年龄可以限定在一个 0 到 100 的取值池子里，姓名、性别、年级也各有自己的取值范围。不能因为某列叫“年龄”，就把它和“域”当成完全相同的概念。

#### 码、候选码和主码

表中某个属性，或者某几个属性组成的属性组，如果能够唯一确定一个元组，它就是码。英文叫 `key`，中文有时翻译成码，有时翻译成键，这里先统一记作码。

假设表里有学号、姓名、年龄、性别、系名和年级：

- 学号给出一个值，通常就能确定一行；
- 姓名可能重复，不一定能确定；
- 年龄更可能重复，不一定能确定；
- 性别和系名也不能单独保证唯一。

凡是符合“能够唯一确定一个元组”这个条件的，都属于候选码。候选码可能不止一个，我们从中选一个作为主码。

这很像三个人竞选一个位置，最后选出一个当“总统”。主码不是凭空规定的，而是从候选码中选出来的。通常学生表会选择学号，因为学生人数增加以后，学号仍然能够保持不重复；姓名就不敢保证。

所以这几个概念的关系是：满足唯一确定条件的是候选码，从候选码中选出来的是主码。

#### 域和分量

域是一组具有相同取值类型的数据值的集合，可以把它想成一个数据池子。属性的取值范围来自某个域；例如年龄从一个 0 到 100 的池子里取值。

每一个小单元格则叫作分量。它的英文是 `component`。不要把分量和域混淆：域是一组允许值的范围，分量是当前单元格里实际放进去的一个值。

#### 关系模式

关系模式描述的是这张表“长什么样”，也就是表头。前面那张学生表可以写成：

```text
学生（学号，姓名，年龄，性别，系名，年级）
```

这不是在描述某一位学生的实际数据，而是在规定关系的名称和属性组成。

关系模式还有一个非常重要的要求：不允许表中有表。数据库里的表必须横平竖直，不能在一个单元格里再塞进两个小表。

比如工资这一列，如果在一个单元格里同时放了基本工资、岗位工资和业绩工资，向下查看时会发现里面藏着三个更细的类别。这样一来，属性到底指向哪一层就不清楚了。处理方法是把它们上提出来，拆成几列，让整张表保持横平竖直。

> **易错点**：现实中的工资可以由多个部分组成，但关系表不能把多个可区分的部分藏在同一个单元格里；把复合内容拆成属性，才符合关系模型的基本要求。

### 数据操作和数据控制：定义、操作、控制三件事

前面一直在用三个角度组织数据库的知识：数据的定义、数据的操作和数据的控制。这不是三个互不相干的术语，而是一套理解数据库的思维框架。

我们可以用盖房子来记住它们：

- `DDL` 是数据定义，回答“这座房子长什么样”；
- `DML` 是数据操作，回答“往屋子里放什么、拿走什么、修改什么、查询什么”；
- `DCL` 是数据控制，回答“放进去的数据必须符合什么条件”。

因此，数据的增加、删除、修改、查询，是操作；实体完整性、参照完整性和用户自定义完整性，是对数据控制时使用的规则。

还有一个重要特点：存取路径对用户是隐藏的。用户只要说明想做什么，不必详细说明系统打算怎样一步步完成。这个特点使数据库以及 `SQL` 成为高度非过程化的工具。

例如你提出“给我平均分”，把指令交给系统，系统返回平均分即可；它究竟怎样找到数据、怎样计算，你不需要参与安排。和高级程序语言必须把过程逐步定义出来不同，数据库更关注你要达到什么结果，而不是把每一步执行细节都交给你。

### 数据库系统的结构

数据库系统不是只有一个数据库文件。它有几种常见的结构形态：单用户结构、主从式结构、分布式结构、客户机/服务器结构，以及浏览器/应用服务器/数据库服务器的结构。

单用户结构就是一个用户在自己的计算机上使用数据库；主从式结构可以想成一台较大的机器连接着多台小型计算机；分布式结构则像云计算那样，把数据切开放到多个计算节点上，再用网络把它们连接起来。客户机/服务器以及浏览器/应用服务器/数据库服务器的结构，则描述数据库在网络端的位置以及不同软件如何分工。

这一部分最重要的内容，是“三级模式、两层映像”。先把“模式”理解成框架，很多名字就容易记住了。

#### 模式和实例：框架与某个时刻的样子

模式是数据库的框架，描述数据库的结构；值则是对结构填入的具体内容。放到数据库里，就形成了模式和实例这一对概念。

假设一个教学数据库里有学生表、老师表、课程表。先规定每张表有哪些列、表之间怎样联系，这个框架就是模式，也叫 `schema`。即使里面还没有放任何数据，它仍然已经确定了数据库的结构。

当一个班的 100 位同学的数据被装进去时，这一时刻数据库的具体样子就是实例，也叫 `instance`。后来又来了 10 位同学，数据库更新之后，就形成了另一个时刻的实例。

所以可以这样记：

```text
模式：房子的框架
实例：某个时刻房子里实际放好的东西
```

模式相对稳定，实例会随着数据的进入、修改和删除不断变化。实例像是给数据库在不同时间拍下的照片，模式则是照片里那个房子的基本结构。

#### 三级模式与两层映像

数据库系统中的三级模式分别是模式、外模式和内模式。

- 模式位于中间层，可以把整个数据库的基本表看成它的骨架，一个数据库只有一个模式；
- 外模式位于应用程序一侧，是面向不同应用需求形成的视图或映射；
- 内模式位于底层，负责把表和数据的结构映射成计算机中的 0、1，并最终对应到磁盘扇区的存储方式。

把它们之间的关系画出来：

```text
应用程序 A       应用程序 B       应用程序 C
     │               │               │
 外模式 1         外模式 2         外模式 3
（教务视图）       （财务视图）       （人事视图）
     │               │               │
     └──── 外模式 / 模式映像 ────────┘
                      │
                      ▼
              模式：学生表、老师表、课程表
                      │
                      └──── 模式 / 内模式映像 ────┐
                                                   ▼
                                      内模式：0、1 与磁盘映射
                                                   │
                                                   ▼
                                             物理存储
```

外模式/模式映像，把不同应用看到的视图和中间的模式连接起来；模式/内模式映像，把逻辑结构与底层的物理存储连接起来。

读这张图时，可以把它当成“不同角色只看见自己需要的那一层”。教务处通过外模式看到教务相关数据，财务处通过自己的外模式看到财务相关数据，人事处也通过自己的外模式看到人事相关数据。它们并不是把模式中的数据各自复制走，而是通过映射得到面向自己的视图。

这样做至少有两个明显好处。

第一，数据更安全、完整性也更容易保证。应用程序面对的是外模式，底层还有模式和内模式。外部操作通常先发生在映射出来的视图上，未提交的更新不会直接改变底层基本数据；即使应用层出现问题，底层仍有自己的结构和控制。

第二，三层能够各自负责自己的工作。应用程序可能由不同公司开发，数据库管理系统也可能是不同公司的产品，操作系统同样有不同厂商。比如有的应用程序是微博、抖音、小红书；数据库管理系统有 Windows 自带的 Microsoft Access、微软的 SQL Server，也有 MySQL、DB2、Kingbase；操作系统则可能是 Windows、Macintosh 或 Google Chrome。

做应用程序的专注开发应用程序，做数据库的专注做数据库，做操作系统的专注做操作系统。三方不需要过度关心对方的内部实现，只要按照映像和接口连接起来即可。

### 数据库系统由什么组成

最后把数据库系统的组成固定下来。它主要有四部分：数据库、数据库管理系统、应用程序，以及数据库管理员。

- 数据库：把文件和数据统一放在一起；
- 数据库管理系统：负责数据定义、操作和控制；
- 应用程序：调用数据库，比如微博、抖音、快手这类系统；
- 数据库管理员：负责设定密码、维护数据库运行等日常工作。

可以把职责关系理解成下面这样：

```text
用户 ── 客户端 / 应用系统
              │
              ▼
       应用程序：调用数据库
              │
              ▼
     外模式：面向应用的数据视图
              │
              ▼
       数据库管理系统（DBMS）
              │
              ▼
           数据库
              │
              ▼
           操作系统
```

程序员负责处理客户端和外模式这一侧；数据库管理系统负责实现模式、外模式、内模式之间的结构与映射；数据库管理员负责数据库的管理和维护；数据库对应着操作系统这一层，数据库管理员、系统分析员也会参与相关工作。

从纵向看，数据库系统处在操作系统和应用程序之间。它向下连接操作系统和物理存储，向上为不同应用提供数据和访问服务。这个位置不是偶然的，而是我们前面从三代系统演化、特征、模型和结构一路推过来的结果。

### 把整条主线串起来

现在可以把这一讲的内容压成一条完整的路线：

```text
现实世界
   │  实体、属性、联系
   ▼
概念模型（E-R 图）
   │  转成二维表等逻辑结构
   ▼
数据模型：数据结构 + 数据操作 + 完整性约束
   │  采用关系模型
   ▼
二维表：关系、元组、属性、码、域、分量
   │  通过 DDL、DML、DCL 定义、操作、控制
   ▼
数据库管理系统
   │  模式 / 外模式 / 内模式 + 两层映像
   ▼
数据库系统
```

数据库从人工管理、文件系统一路发展过来，核心变化就是从“每个程序各自保存数据”走向“由数据库管理系统统一管理数据”。它通过结构化、共享、低冗余和较高的独立性，让数据能够被更多人共同使用；又通过统一的安全、完整性、并发和恢复控制，让这份共享数据能够稳定地工作。

从数据结构上看，层次模型像树，网状模型像网，关系模型把问题压缩成二维表。关系模型之所以成为重点，不是因为它没有缺点，而是因为它把实体、属性和联系都放进了人能够直观理解、计算机也能够处理的结构里。

下一讲我们会继续往下走，进入关系代数，并进一步讨论二维表是怎样被操作的。现在这条线已经接上了：从现实世界建模，到选择关系模型，再到用数据库管理系统对数据进行定义、操作和控制。前面看似分散的名词，实际上都在回答同一个问题——怎样把现实世界可靠地存进计算机，又让它随时可以被正确地取出来。
