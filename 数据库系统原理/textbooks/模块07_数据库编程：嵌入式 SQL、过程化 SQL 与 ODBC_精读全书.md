## 嵌入式 SQL：让 SQL 走进高级语言
> 对应块：BLK28 | 覆盖分集：P25 | 块标题（分集名）：《数据库第8章 数据库编程（第一部分：嵌入式SQL》

先想一个很朴素的场景：要打印一个班五十名同学某门课的成绩。

如果只用 C 语言来做，就得准备学号、课程编号、成绩这些变量，用 `scanf` 把键盘输入送进变量，再用 `printf` 输出；换下一名同学之前，还要把变量重新赋值、打印、清空，然后靠 `for` 循环把五十个人依次推完。C 语言很擅长控制这样的过程，可它并不擅长一次拿出一大批数据。

SQL 恰好擅长另一件事。给我班级编号和课程编号，我可以直接从学生表或选课表里把符合条件的成绩一次取出来，以表的形式交给你。可你要问它“这一行该不该更新年龄”“下一个人的年龄是多少”，它就很难像 C 那样把键盘输入、条件和循环自然地串起来。

**一门语言擅长控制过程，另一门语言擅长处理集合；把它们接起来，并不是为了凑合，而是为了各取所长。**

这就是嵌入式 SQL 的出发点。

### 这一章要解决的，不止一种编程问题

数据库编程并不是只等于写 SQL。我们这一章先看三条彼此连着的路线。

#### 让 SQL 自己获得一点过程能力

SQL 高度非过程化。普通 SQL 语句直接告诉它“查什么、改什么”，却不必像 C 那样把每一步都写出来。过程化 SQL 试图给它加上一些简单控制：用 `if-then`、`if-then-else`，或者 `loop`、`while loop` 等形式，把 SQL 块像乐高一样拼起来。

它能得到一点过程控制能力，但这种能力是比较粗浅的。嵌入式 SQL 则换一条路：不急着让 SQL 自己包办流程，而是让它与 C、C++、Java 等主语言配合。这两条路，都是为了让程序既会处理过程，又会处理大规模数据。

#### 把常用逻辑封装到数据库服务器上

再往前一步，如果一段过程化 SQL 经常要执行，就可以把它封装成数据库服务器上的组件。

用银行转账来想：给出转出账户、转入账户和金额，转账就完成了。如果这件事经常发生，就没必要每次都重新写代码。可以先写好一个组件，传三个变量进去，让它把事情做完。

不带返回值的封装叫**存储过程**；带返回值的封装叫**函数**。它们本质上都是把过程化 SQL、嵌入式 SQL 组合起来以后，封装成可以在服务器端频繁调用的功能。后面两部分会专门展开它们。

#### 从不同数据库里取数，也需要统一接口

学校里有学生处、教务处、财务处，各部门的信息系统下面可能接的是不同数据库：有的用 SQL Server，有的用 MySQL，有的用 DB2，也有的用 Kingbase。学校再做一个统一的信息系统时，总不能为每一个部门重写一整套程序。

这时需要数据库与应用程序之间的一套接口和调用方法。课程里会提到的有 OLE DB、ODBC 和 JDBC：ODBC 用来提供与不同数据库兼容的访问接口；Java 程序对应的接口路线是 JDBC。前面还摆着 OLE DB 这条较早的路线。

它们和嵌入式 SQL 的关注点不同。嵌入式 SQL 解决的是“SQL 怎么放进高级语言”；ODBC、JDBC 解决的是“应用程序怎么通过统一接口访问不同数据库”。放到整章里看，才知道数据库编程要同时解决 SQL 自身怎么用、语言怎么嵌、服务器组件怎么封装、多个数据库怎么连这几个问题。

> **结论**：嵌入式 SQL、过程化 SQL、存储过程和函数，是本章的重点。ODBC、OLE DB、JDBC 更多是帮助理解数据库应用如何接入实际系统。对这些内容，我们先把原理看懂、代码读懂；不要求现在就能脱离示例独立写出来。

### 两种语言放在一起，关键在“能互相传话”

SQL 有交互式和嵌入式两种使用方式。

交互式使用，就是我们前面学习数据定义、数据查询、数据修改、数据控制时看到的方式：给数据库一条指令，让它独立完成一个要求。嵌入式使用则是把 SQL 放进高级语言中，由高级语言带着它去工作。

为什么要嵌入？因为前面说的互补关系。C、Java、C++ 这些语言擅长控制过程，不擅长处理大规模数据；SQL 擅长处理大规模数据，却不擅长把过程控制写细。把 SQL 放进主语言，让它像被调用的函数一样工作，正好能补上双方的短板。

Python 要另说：处理数据集可以用 NumPy，处理数据可以用 Pandas，做可视化可以用 Matplotlib、Seaborn，Pandas 的 DataFrame 也能帮助处理大规模数据。这里说的主语言，先按 C、Java、C++ 这些传统语言来理解。

#### 主语言与预编译

被嵌入 SQL 的程序语言叫**主语言**。例如，一段 C 程序里包含嵌入式 SQL，那么 C 就是这段程序的主语言。

它的处理方式可以这样理解：把 SQL 转成函数调用。在主语言编译这段程序时，SQL 部分被当作一次函数调用来处理——传入什么值、得到什么结果，都从这个“函数”的接口理解。

```c
EXEC SQL SELECT Sno, Sname, Ssex, Sage
    INTO :Hsno, :Hsname, :Hsex, :Hsage
    FROM 学生表
    WHERE Sdept = :deptname;
```

看到这段代码，先别急着抠里面的查询逻辑，先抓住它的身份：它不是一段孤立的普通 C 代码，而是 C 程序里嵌进去的 SQL。SQL 里的语句前面必须加 `EXEC SQL` 前缀；加了它，编译器才知道后面这部分属于 SQL，不加的话就是主语言语句。

#### 通信区：让主语言知道 SQL 发生了什么

C 里面嵌进 SQL，就像一篇普通话文章中间夹了一段四川话。写的人能写，听的人未必能直接听懂。中间需要翻译，两种语言才能协作。

SQL 负责操作数据库、处理集合；主语言负责流程控制。它们之间同样需要一个“翻译缓冲区”，这就是**通信区**。

通信区不是用来存业务数据的，它是用来传递执行状态信息的。SQL 语句执行结束后，系统通过通信区告诉主语言：这条语句执行成功，还是遇到了错误。主程序取出这些状态信息，再决定接下来怎么走。

通信区叫 **SQLCA**，CA 是 Communication Area 的缩写。它是一个数据结构，可以把其中的 SQL 块当成一个黑盒子：主语言把值送进去，处理完后不直接看盒子内部，而是读取盒子交回来的状态。

```c
long SQLCODE;

EXEC SQL INCLUDE SQLCA;
```

`SQLCODE` 是通信区里用来报告状态的预定义值。你可以把它理解成一个约定的“运行标记”：主程序给过它约定的初始值；每执行一条 SQL，就检查它是不是还保持约定。如果状态发生变化，就说明这条 SQL 的执行过程出了问题，主程序便知道这里需要处理错误或停止当前的处理流程。

> **提示**：`SQLCODE` 报告的是 SQL 执行状态，不是 SQL 查询出来的业务数据。把这两者分开：查询结果交给主变量，执行状态交给通信区。

### 主变量进 SQL 前，得换上冒号

SQL 语句可以使用主语言程序的变量输入数据、接收结果。主语言里的这些变量，进入 SQL 语句工作时就叫**主变量**。

所以要分清两个场景：在 C 里面，它只是 C 的变量；进了 SQL 区域，拿来参与 SQL 的计算或条件，它才以“主变量”的身份工作。

#### 声明主变量，不是直接写 C 的赋值

任何语言使用变量都要先声明，主变量也一样。嵌入式 SQL 专门给它留了一个声明区，由 `EXEC SQL BEGIN DECLARE SECTION` 开始，到 `EXEC SQL END DECLARE SECTION` 结束。主变量和指示变量的说明，都写在这两个语句之间。

在那段交互式更新年龄的程序里，变量区里有四个 `char` 类型的变量，用来容纳字符串；有两个 `int` 类型的变量，用来容纳整数。它们的名字在程序中可以写成 `deptname`、`Hsno`、`Hsname`、`Hsex`、`Hsage`、`newage` 这样的形式。

有些变量前面加了一个 `H`，不用纠结这个字母，它只是为了提醒你别把程序里的变量看混，可以随便起名。但是，变量在 SQL 区域工作时前面的冒号可有可无不了。

#### 冒号是在说：“我现在是外部送来的主变量”

假设从键盘输入一个学号和一个课程编号，把它们传进 SQL，用来查对应成绩。SQL 里就写 `:Hsno`、`:Cno`。

`Hsno`、`Cno` 看起来和数据库里的列名很像。假如不加冒号，SQL 看到它们，怎么知道你是想查列，还是想使用 C 送来的值？主变量前的冒号，就是为了把它和表名、视图名、列名这些数据库对象区分开。

在主语言区域使用主变量时，不用加冒号；它进入 SQL 语句，在可以写表达式的地方出现时，要加冒号。出了 SQL 区域，回到 C 的语句里，又不需要冒号了。

把它当成一套进出场规则，特别好记：

- 变量在 C 里，就是普通变量；
- 进入 SQL 工作，冒号是它的工作服；
- 出了 SQL 区域，冒号脱掉。

#### 输入主变量与输出主变量

主变量分成输入和输出两种。

输入主变量，由主语言赋值，再送入 SQL 使用。刚才的班级编号、学号、课程编号，扮演的就是这个角色。主程序把值放进这些变量，SQL 拿到值后去查数据。

输出主变量，是由 SQL 赋值，把查询或处理后的结果带回主程序。查一行学生信息，SQL 就把结果放进对应的主变量，再交给 C 显示、更新或继续做别的处理。

一条 SQL 里可能同时有输入主变量和输出主变量。向 SQL 传进去的班号是新信息，传出来的是一批处理后的结果；这两头都需要变量的容器。

#### 指示变量：别把“空”与“有值”混成一回事

光有主变量还不够。输入的时候，某个值可能是空的；输出的时候，某个结果也可能是空的。这时再配一个整型变量，叫**指示变量**。

一个主变量可以附带一个指示变量，用法是在主变量前加冒号，紧贴在主变量后面。它主要负责告诉程序：对应的输入是不是空值，以及输出结果是不是空值、是否出现了问题。

比如查学生选修某门课的成绩时：

```sql
EXEC SQL SELECT Grade
    INTO :grade :grade_id
    FROM SC
    WHERE Sno = :snumber AND Cno = :cnumber;
```

`:grade` 接成绩，`:grade_id` 是它的指示变量。如果给 `:grade_id` 一个负值，表示对应的成绩没有值，那么即使 `:grade` 里带着一个数，也要按空值看待。这个例子正好说明了：主变量装值，指示变量说明这个值应该如何理解。

### 游标：给集合结果配一条逐行取数的通道

到这里，SQL 擅长处理大规模数据、高度非过程化的两个特点，正好把游标推了出来。

假设 C 传入一个 `Sdept = 'CS'`，学生表里计算机专业有二十名同学。SQL 会把这个专业符合条件的学生作为一个有二十行的结果表交出来。可 C 一次只拿得住一行：学号、姓名、专业、年龄、所在系，放进一组变量，处理完再装下一组。

这就矛盾了：**SQL 一下子出了二十行，C 一次只能处理一行。**

怎么办？先不要把整个结果表直接扔给 C。让 SQL 把结果放到一个数据缓冲区里，C 再从这个缓冲区逐行取。系统为用户开出的这块结果缓冲区，就叫**游标区**；游标可以理解为指向当前记录的指针。

```text
                SQL 执行查询
                      │
                      ▼
          ┌──────────────────────┐
          │    游标区 / 缓冲区     │
          │  查询得到的整批结果    │
          │  第 1 行  第 2 行  ... │
          └──────────────────────┘
                      │ FETCH 当前一行
                      ▼
            ┌──────────────────┐
            │ 一组主变量         │
            └──────────────────┘
                      │
                      ▼
              C 处理这一行
                      │
           再 FETCH 下一行，直到结束
```

读图的关键是：查询得到的不是一行，而是一整批结果；C 通过 `FETCH` 一次取一行，取出的数据放进主变量，再处理。处理完第一行，就把游标推进第二行，重复这个过程；整批数据处理完成后，关闭游标区。

#### 游标的标准步骤

使用游标不是直接取数据，而是有明确的生命周期：

1. **说明游标**：给它一个名字，并用 `CURSOR FOR` 写出它要装哪条查询语句的结果。
2. **打开游标**：执行这条查询，让结果真正进入游标区。没有打开时，只是把缓冲区说明好了，查询还没有干活。
3. **推进游标**：用 `FETCH` 取出当前一行，放进一组主变量，供主语言处理。
4. **关闭游标**：释放结果集占用的缓冲区和其他资源，结束这次结果处理。

`FETCH` 这个英文很形象，就是“去拿回来”。在 C 里，你要拿到下一行，就要从游标区取下一行；游标方向由程序决定，但每次取出的都必须是一行主变量可以接住的数据。

游标关闭以后，就不再和原来的结果集保持联系。后面还可以再次打开它，但这时会按照它所说明的查询语句重新取得结果，不是继续使用上一次遗留的数据。

### 逐行更新年龄：把概念放进一个真实流程

我们用“依次检查某个系的学生记录，交互式更新某些学生年龄”这件事，把前面几个概念串起来。

先想程序应该怎么走：先让用户选择专业，比如 CS、MA、IS；再从这个专业的学生记录里逐行取数据；每取出一行，就问“要不要更新年龄”；要更新，就输入新年龄；不要更新，就直接看下一行。整个班级处理完，再提交更新，断开数据库。

这个过程里的键盘输入、是否更新、循环推进，得靠 C 这一类主语言；具体从学生表里查记录、按当前那一行改年龄，得靠 SQL。两边必须接上。

#### 从键盘选专业，再把结果接到游标区

主程序先定义 `count` 和 `yn` 等 C 变量，再通过 `printf` 提示：

```text
please choose a department name: CS, MA, IS
```

用户输入一个专业，比如 `CS`，主程序用 `scanf` 接进 `deptname`。接下来，程序建立数据库连接。连接时，主语言提供服务器标识，连接名和用户名也可以指定。`SET CONNECTION` 可以把当前连接切换到另一个连接；全部用完后，用 `DISCONNECT` 断开。

> **提示**：连接和查询是两回事。建立连接，只是让 C 程序和数据库之间有一条可用的通路；真正要查专业学生的数据，还要继续声明游标和查询。

因为一个专业可能有很多学生，所以不能只准备一组变量就直接收结果。先开一个游标区，用 `deptname` 选这个专业的学生：

```sql
EXEC SQL DECLARE sx CURSOR FOR
    SELECT Sno, Sname, Ssex, Sage
    FROM 学生表
    WHERE Sdept = :deptname;
```

注意 `Sdept = :deptname` 里的 `:`。`deptname` 是 C 送来的主变量，工作位置在 SQL 区域，所以要穿冒号。用户刚才输入的 `CS`，在这里就相当于 `Sdept = 'CS'` 的查询条件。这个游标区装下的，就是这个专业符合条件的学号、姓名、性别和年龄。

#### 打开游标，取一行，再交给 C 处理

打开游标之后，查询结果进入缓冲区，游标指向第一行。C 通过 `FETCH` 取出当前行：

```sql
EXEC SQL OPEN sx;

EXEC SQL FETCH sx INTO :Hsno, :Hsname, :Hsex, :Hsage;
```

`FETCH` 只取一行，不是把整个表都塞进 `Hsno`、`Hsname`、`Hsex`、`Hsage` 四个变量。四个变量分别接住这一行的四列；因为它们在 SQL 里工作，前面要加冒号。取出来的值回到 C 里后，冒号就不用了，C 直接用这些变量处理。

如果 `SQLCODE` 还是约定的状态，说明这条 `FETCH` 没出错，程序就可以先打印表头，再打印这一行的数据。`count` 用来记住是不是第一行，第一行就先输出 `Sno`、`Sname`、`Ssex`、`Sage` 这些列名。后面再取一行，就直接输出这一行拿到的值。

然后程序在屏幕上问：

```text
update age? (y/n)
```

这里要敲键盘了，所以仍然是 C 的工作。`yn` 就是一个等着接字符的“碗”：用户敲 `y` 或 `Y`，就表示更新；敲 `n`，就跳过这一行。

#### 更新的是游标当前指向的那一行

用户要更新时，程序再问：

```text
input new age:
```

用户输入的新年龄进入 `newage`。例如原来十九岁，用户输入二十，接着要改的不是“所有二十岁的人”，也不是随便某一行，而是**游标当前所在的那一行**：

```sql
EXEC SQL UPDATE 学生表
    SET Sage = :newage
    WHERE CURRENT OF sx;
```

`WHERE CURRENT OF sx` 是这段语句的关键。游标现在指哪一行，就改哪一行；别的行跟这次更新没有关系。

`newage` 从 C 进入 SQL 参与更新，所以写成 `:newage`；`Sage` 是数据库表里的列名，不需要冒号。这里把“更新哪一条记录”交给游标当前位置来指明，不再需要另外拿学号去写一个复杂的查找条件。

处理完第一行，C 再让循环往下走，`FETCH` 下一行，重复询问、更新或跳过。直到专业下的所有学生都过完，程序才关闭游标、提交更新，再断开连接：

```sql
EXEC SQL CLOSE sx;
EXEC SQL COMMIT WORK;
EXEC SQL DISCONNECT;
```

`CLOSE` 关掉游标区，释放这次结果集用的资源。`COMMIT WORK` 把已经做好的更新正式提交给数据库；不然数据只是在处理过程里，不能算完成。最后 `DISCONNECT` 断开连接，程序才算把这一轮工作做完。

> **易错点**：`FETCH` 取出的是当前一行，`UPDATE ... WHERE CURRENT OF` 改的是游标当前指向的那一行。不要把“取出来供 C 看”和“已经改回数据库”当成同一件事。查询、更新、提交是三个动作。

### 什么时候根本不用游标

如果已经理解了游标的来由，就不用死记一大堆分类。真正要问的只有两个：

- SQL 交给主语言的结果，是一行，还是多行？
- 增删改的目标，是能用条件直接指出来的记录，还是必须先在结果集中找到当前那一行？

#### 单行结果：主变量直接接

按学号查一个学生，SQL 最终返回一条记录。哪怕这一行有五列，也只要准备五个主变量，五只“碗”，让 SQL 分别把五列的值装进去。C 接到之后直接处理，不需要先开一个放多行结果的缓冲区。

所以，**查询结果为单条记录时，不必使用游标。**这是最核心的判断，不要把“有没有 `SELECT`”当成判断标准。关键看 `SELECT` 回来几行。

#### 非 CURRENT 形式的增删改：条件能指明对象，也不用游标

如果已经明确知道要改哪个学生、哪门课的成绩，也不需要游标。比如修改一个学生选修一号课的成绩：

```sql
EXEC SQL UPDATE SC
    SET Grade = :newgrade
    WHERE Sno = :given_snumber AND Cno = :cnumber;
```

主程序把新成绩放进 `:newgrade`，把学号放进 `:given_snumber`，再与课程编号一起放进查询条件。SQL 直接找到对应记录更新，没有“先查出一批结果，再在结果里移动指针寻找当前行”的过程。

这就是非 CURRENT 形式的增删改。它的特点是：目标记录能由条件直接指明，不必依赖一个游标当前停在哪一行。

插入新记录也是同样的道理。学号和课程编号已经由主变量带进来，成绩用指示变量说明是不是空：

```sql
EXEC SQL INSERT INTO SC (Sno, Cno, Grade)
    VALUES (:student_number, :coursenumber, :newgrade);
```

这里不是把“游标当前行”当作修改对象，而是把主变量中的值直接插入 `SC` 表，因此不用游标。

### 多行结果与 CURRENT 形式：游标真正派上用场

当 SQL 的查询结果是多条记录时，就需要游标区先把整批结果接住，再由 C 逐行取。

`SELECT` 使用游标的步骤，仍然是那四步：

```text
DECLARE → OPEN → FETCH → CLOSE
         │             │
         │             └─ 取出当前行到主变量
         └─ 执行查询，让结果进入游标区
```

`OPEN` 时才真正执行 `SELECT`，把结果放进缓冲区；`FETCH` 时取当前一行，`INTO` 后面一定是主变量；`CLOSE` 时释放结果集占用的缓冲区和其他资源。

对于更新和删除，若要处理查询结果中的某一条记录，也有 CURRENT 形式：先用带游标的 `SELECT` 找到满足条件的记录，再用游标推进到目标行，最后通过 `WHERE CURRENT OF` 更新或删除当前行。

CURRENT 和非 CURRENT 的区别，不是“有没有写 `WHERE`，所以那两条语句更高级”的区别。真正区别是目标怎么确定：

- 非 CURRENT 形式：用学号、课程编号等条件直接指出目标；
- CURRENT 形式：先让游标在查询结果中定位，再对当前行做处理。

> **易错点**：如果游标定义中的 `SELECT` 带 `UNION` 或 `ORDER BY`，就不能用 CURRENT 形式的 `UPDATE` 或 `DELETE`。这种游标对应一个不能按当前行随意更新的结果，不能把它当成一个可以随手改动的表。

到这里，游标的使用条件可以收成一张表：

| 情况 | 是否使用游标 | 原因 |
| :--- | :--- | :--- |
| 查询结果为单条记录 | 不使用 | 一行结果可以直接交给一组主变量 |
| 非 CURRENT 形式的增删改 | 不使用 | 学号、课程编号等条件已能指明目标记录 |
| 查询结果为多条记录 | 使用 | 主语言一次处理一行，需要先缓冲整批结果 |
| CURRENT 形式的更新、删除 | 使用 | 需要在结果集中移动指针，确定当前要改的行 |

> **结论**：不要去背“哪些 SQL 语句天然可以不用游标”的长清单。先判断数据行数和目标定位方式，这两个问题一回答，用不用游标就清楚了。

### 动态 SQL：等程序跑起来，再决定要执行什么

前面写好的嵌入式 SQL，是静态嵌入式 SQL。它能满足一般需求：写程序时已经想清楚要查什么、改什么，就一次性把语句写好，后面不再临时变化。

但真实开发不是总能这样。程序已经写起来、跑起来了，突然发现还需要建一张表，或者临时想换一种查询条件。此时再回到程序定义处，把原本的 SQL 重写一遍，不够灵活。

动态 SQL 就是让程序在运行过程中临时组装 SQL 语句。它支持两种变化：**SQL 语句本身可以变化，动态参数也可以变化。**

#### SQL 语句主变量：装的是语句，不是普通数据

我们前面说的主变量，通常装的是一个学号、课程号、年龄这样的普通数据。SQL 语句主变量不一样：它装的是一条 SQL 语句。

例如先让一个字符指针变量 `stmt` 装好一条建表语句，等程序运行到需要使用它的时候，再把这个变量里的内容交给 SQL 执行。这个“装句子的碗”就叫 SQL 语句主变量。

```c
const char *stmt = "CREATE TABLE test (a INT)";
```

`stmt` 是 statement 的缩写。上面这条语句的含义是：创建一张名为 `test` 的表，其中有一列 `a`，数据类型为整数。SQL 语句主变量在程序运行期间可以设置成不同的 SQL 语句，需要时立即执行。

```sql
EXEC SQL EXECUTE IMMEDIATE :stmt;
```

这就是动态 SQL 最直接的执行方式。`EXECUTE IMMEDIATE` 的意思就是“立即执行变量里现在装着的语句”。不用 `stmt` 的时候，它先把语句放在那里；真正要用时，再把语句取出来执行。

#### 动态参数：用问号把值的位置先占住

有时 SQL 的结构已经定了，但某个值不知道什么时候才能确定。比如想往刚建好的 `test` 表中插入数据，但此时还不知道未来究竟要插入多少。

这时不能提前把数值写死在语句里，可以用问号把参数的位置占住。动态参数的绑定，不是在编译主程序时就完成，而是在 `PREPARE` 准备语句、`EXECUTE` 执行语句时完成。

```sql
EXEC SQL PREPARE mystatement FROM :stmt;
EXEC SQL EXECUTE mystatement USING 100;
EXEC SQL EXECUTE mystatement USING 200;
```

第一条 `PREPARE` 准备好带问号的语句，并给它起了名字 `mystatement`，方便后面执行。后两次执行都用同一条语句，只是分别把问号的位置绑定为 `100` 和 `200`。

你看，一开始不需要知道未来的值，先用问号占住；等真正要执行时，再把值填进去。语句与参数分开，程序就能在运行中灵活地改变要执行的 SQL 和要送入的值。

> **易错点**：动态 SQL 不是“把 SQL 当成随便拼的文本就完事”。这里讲的重点是：静态阶段先把语句结构准备好，运行时通过主变量与参数占位，再在真正执行时完成绑定。要区分开“什么时候准备语句”与“什么时候送入参数”。

### 回到起点：把两种长处接起来

嵌入式 SQL 的整体思路，其实不复杂：让 C、C++、Java 这样的主语言负责控制，让 SQL 负责集合式的数据处理。把 SQL 当作编译时转换成函数调用的黑盒子，主程序给它输入，它给主程序返回结果。

但真正要把它写通，必须把三种连接做完整。

第一，**通信区**负责说清运行状态。它让主语言知道 SQL 执行成功还是失败，不至于程序盲目往前走。

第二，**主变量**负责搬运数据。主变量在 SQL 区域要加冒号，用完后回到主语言又要脱掉冒号；输入主变量带值进去，输出主变量带结果出来；指示变量再负责说明空值和状态。

第三，**游标**负责协调处理方式。SQL 一次给出一批结果，主语言一次处理一行，就用游标区缓冲整批结果，再逐行取出。目标记录能直接由条件指明时，不必绕游标；要在多行结果中找到某一行并修改或删除时，CURRENT 形式才需要它。

动态 SQL 则把这套思路再推进一步：不是只有数据可以晚一点才知道，连要执行的 SQL 语句也可以等到运行时再组装、执行。

这就是数据库编程从第三、四、五章走向第八章的意义所在。我们不是只会写几条孤立的 SQL，而是让 SQL 真正进入程序、进入服务器组件、进入信息系统，和过程控制以及大规模数据处理接上。

对这一讲里的代码，先做到逐行看懂：每个变量从哪来，冒号为什么要加，通信区为什么存在，游标为什么在多行结果时必需，`FETCH` 和 `COMMIT` 各做了什么。能读懂这些，下一步再谈独立编码就顺了。

## 过程化 SQL、存储过程与 ODBC：把数据库操作接成可复用的程序
> 对应块：BLK29 | 覆盖分集：P26 | 块标题（分集名）：《数据库第8章 数据库编程（第二部分：过程化SQL》

我们先把几个容易混在一起的词放回它们各自的位置。嵌入式 SQL、过程化 SQL、存储过程和函数，看起来都带着“SQL”，但它们解决的不是同一个问题。

嵌入式 SQL 解决的是：怎样把 SQL 放进一个已有的主程序里，让程序和数据库打交道。过程化 SQL 解决的是：怎样在 SQL 的数据操作之外，加入变量、流程控制和错误处理。存储过程和函数，则把写好的过程化 SQL 封装成一个可以反复调用的模块，存放到数据库服务器中。

可以先用这张关系图把方向看清楚：

```text
嵌入式 SQL
    └── 把 SQL 接入已有的应用程序

过程化 SQL
    ├── 块结构
    ├── 变量、常量与游标
    ├── 条件、循环与错误处理
    └── 像搭积木一样拼出简单的执行过程
            ↓
      预封装并保存到数据库服务器
            ↓
       存储过程 / 函数
            └── 以后通过参数反复调用
```

还有一条相对独立的线，是 ODBC。它要解决的不是“SQL 能不能执行”，而是同一个应用程序能不能用同一套办法访问不同数据库管理系统中的数据。

### 过程化 SQL 为什么值得存在

大家想一想，前面讲 SQL 的时候，我们说它是一个高度非过程化的语言。这和现在要讲的过程化 SQL 听起来不是有点矛盾吗？其实并不矛盾，关键是“高度非过程化”说的是哪一部分。

比如要查一个班某门课的平均成绩。你只要把班级编号、课程编号交给数据库，再给出 `SELECT ... FROM ... WHERE ...` 这样的查询，数据库就会从一堆成绩中算出平均值。中间到底怎样定位数据、怎样扫描、怎样求和，你并不需要一步步指定。

这说的是 SQL 的数据处理能力：你说明想得到什么结果，数据库负责把过程组织起来。非过程化不是说数据库内部没有执行过程，而是说使用者通常不必关心这个执行过程。

但是，作为一个编程语言，SQL 不能只满足“给我一个查询，我给你一个结果”。它还需要具备一些初步的处理过程能力：先做什么，后做什么；满足某个条件时做什么；一组数据要重复处理几次；出现异常时怎么办。

比如在 C 语言里，我们可以一行一行地定义完整过程：读取一个值，把值赋给变量，再把结果显示出来。过程化 SQL 的能力没有这么强。它不能像 C 那样靠一行代码自然地表达一个完整过程，所以它采取的办法有点像搭乐高：每一块只完成一个明确的功能，再用嵌套、循环和 `if ... else` 把这些块拼起来。

从上到下执行这些块，就像按顺序推动一组积木，最后拼出了一个简单的处理过程。这里的“过程化”不是说 SQL 突然变成了 C，而是说 SQL 在原有的数据功能之外，又有了初步的处理功能。

> **结论**：过程化 SQL 和 SQL 的高度非过程化并不冲突。前者强调“处理过程”，后者强调“数据操作”。一个管怎么做，一个管做什么，二者可以同时存在。

### 一个块就是一个黑盒子

过程化 SQL 的基本单位是块。块可以互相嵌套，每个块完成一个操作。一个标准块大体可以写成这样的结构：

```sql
DECLARE
    -- 变量、常量、游标等声明
BEGIN
    -- 可执行语句
EXCEPTION
    -- 异常处理
END;
```

这张结构图很重要：

```text
DECLARE
  ├── 定义变量
  ├── 定义常量
  └── 定义游标
          ↓
BEGIN
  └── 执行具体语句
          ↓
EXCEPTION（需要时）
  └── 处理执行异常
          ↓
END
```

这里有两条一定要记住：第一，先定义，再执行；第二，块有作用域。变量、常量和游标的定义只在这个块里面有效，出了这个块就不能继续使用；基本块执行结束，这些定义也就不存在了。

这很像一个黑盒子。外面把数据送进来，里面用变量接住、带着数据完成处理，处理结束以后，盒子里定义的这些临时东西随着盒子一起结束。我们不能指望块执行完了以后，还能拿里面的局部变量到外面继续用。

#### 变量、常量和游标

变量要说明名称、数据类型，以及是否允许为空，或者给出初始值表达式。常量则要说明它是常量，并给它一个常量表达式。常量在它的作用域内必须保持不变；如果试图修改它，就会得到一个异常。

这里特别容易把两个冒号混在一起。

在嵌入式 SQL 中，主程序里的变量进入 SQL 区域时，要写成带冒号的形式，例如 `:x`。这个冒号是贴在变量前面的，表示“这个值从主程序传进来”。

而在过程化 SQL 中，赋值使用的冒号等号组合，含义完全不同：它是在给变量赋值。冒号等号前面是接受赋值的变量，后面是要赋给它的值。一个是“主程序变量进入 SQL 的标记”，一个是“给变量写值”，千万不要因为都出现了冒号就混为一谈。

游标也在声明区域中定义。它和变量、常量一样，服从块的边界；后面处理结果集时，我们会再次遇到它。

#### 块的执行结构

声明部分结束以后，就进入执行部分：

```sql
BEGIN
    -- 要执行的语句
EXCEPTION
    -- 出错时采取的处理
END;
```

`BEGIN` 和 `END` 把执行部分包起来，`EXCEPTION` 用来放异常处理逻辑。整体上可以记成一句话：先把后面要用的东西定义好，再在块里执行；执行中出了问题，就按照块中安排的异常处理方式处理。

### 流程控制：用块拼出最简单的程序

过程化 SQL 的功能很有限，所以它提供的流程控制也只有三类：条件、循环和错误处理。我们把这三类语句和前面讲的块结构放在一起，就得到了最初步的过程能力。

#### 条件控制

最简单的是 `if-then`：

```sql
IF condition THEN
    statement_sequence
END IF;
```

它表达的就是“条件满足，就按顺序执行这些语句”。

`if-then-else` 则给出两套方案：

```sql
IF condition THEN
    statement_sequence
ELSE
    another_statement_sequence
END IF;
```

条件满足，走第一套；条件不满足，走第二套；两边执行完，整个条件块结束。

而且 `then` 和 `else` 里面还可以继续放 `if`，形成嵌套条件。这里没有什么神秘的语法，仍然是我们熟悉的判断结构，只不过它被放进了 SQL 的块里。要先把一件事做完，再在其中继续判断另一件事，就用嵌套把条件块摞起来。

#### 循环控制

简单循环的基本形态是：

```sql
LOOP
    statement_sequence
    EXIT;
END LOOP;
```

它会不断执行循环体。多数数据库服务器的过程化 SQL 都提供 `exit`、`break` 或 `leave` 一类的结束语句。没有这样的出口，`loop` 就会一直转下去，所以循环必须有一个能够结束的条件。

如果要从一个班级的第一名学生处理到第一百名学生，就可以用简单循环：从当前这一行开始处理，处理完前进到下一行，直到没有下一行。要处理固定的 100 个学生，这段循环的边界就很清楚。

`while-loop` 则是另一种写法：每次执行循环体之前先判断条件，条件为真就执行，为假就退出。

```text
判断条件
   ├── 真 ──> 执行循环体 ──> 回到判断条件
   └── 假 ─────────────────> 结束循环
```

比如教务处要处理若干个班级的成绩，当前处理到一号班，就在条件里控制从一号班开始；一号班处理完，条件不再满足，循环退出。条件负责决定“还要不要继续”，循环体负责做当前这一件事。

`for-loop` 则把计数和绑定值直接放进循环中。它的形式里可以有 `reverse`，也可以没有；有绑定值，循环就按照这个值来安排次数和顺序。这里先把结构记住，真正看到案例时再对照实际用法：

```sql
FOR count IN [REVERSE] bound_value LOOP
    statement_sequence
END LOOP;
```

三种循环的区别可以这样看：简单循环适合按固定流程重复，`while-loop` 适合由条件决定是否继续，`for-loop` 适合计数或按绑定值安排重复。不要因为它们都能重复执行，就以为它们只是换了几个关键字；真正要看的是循环什么时候开始、什么时候结束、每一轮处理什么。

#### 错误处理

执行过程中出现异常时，我们可能希望程序直接停下来，也可能希望记录日志，或者采取其他处理办法。过程化 SQL 为此安排了异常处理位置。

`EXCEPTION` 不是拿来写普通业务判断的。转账时“余额不够”这种业务条件，要用 `if` 明确判断；异常处理则用于执行过程中出现的问题。两者不要混在一起，否则我们连到底是“条件不满足”还是“程序执行失败”都分不清了。

### 存储过程和函数：把程序装进数据库服务器

有了块、变量和流程控制，就可以把一个小功能完整地写出来。可如果每次都要重新写，程序就会变得很啰嗦。预封装的思想正是在这里发挥作用：把一次写好的功能放到数据库服务器中，以后需要时只传入参数，由数据库自动执行。

#### 两者到底差在哪里

从模块的角度看，存储过程和函数可以先理解成同一类东西：都是黑盒子，都是输入数据以后由服务器完成一段处理。

最微小的差别只有一个：函数必须有返回值，存储过程可以没有返回值。

```text
输入数据
   ↓
黑盒子内部处理
   ├── 处理完不需要把结果交回去 ──> 存储过程
   └── 处理后必须返回一个结果值 ──> 函数
```

例如，把两个值相加后把结果保存起来，处理完就结束，不必把结果交回调用者，这就是存储过程。如果调用者还要求得到一个结果，例如一个回执、一个计算值，那么它就是函数。

这里不要急着给它们附加更多神秘区别。就这段内容而言，关键就是把“有没有返回值”这件事说清楚。

#### 命名块和匿名块

过程化 SQL 在实际使用中有两种形式：命名块和匿名块。

命名块在编译以后会保存在数据库中，可以反复调用，运行速度也快。过程、存储过程和函数，都属于命名块。我们把一个小模块写好、封装好，然后把它放到数据库服务器里，之后就可以反复使用、反复调用，这就是命名块的含义。

匿名块则不同：每次执行时都要重新编译，不能保存在数据库中，也不能在别的过程化 SQL 中调用。它适合特殊情况，或者某个功能只实现一次，不需要长期保存。

所以，要不要封装成命名块，取决于功能是不是要重复使用。银行的转账、学校的选课、工资计算这种会反复出现的功能，天然适合命名块；只做一次的临时步骤，匿名块就够了。

#### 存储过程放在哪里

存储过程是用过程化 SQL 语句写成的一个小模块，经过编译和优化以后存放到数据库服务器中。在三层服务器架构里，它属于数据库服务器这一层；Web 服务器、应用程序服务器和数据库服务器各自承担不同的工作，存储过程就在数据库服务器中等着被调用。

使用的时候，应用程序不需要每次把一大段过程重新写出来，只要调用这个黑盒子即可。比如教务处的选课、财务处的算工资，都是频繁使用的功能。如果每次都重复写实现，代码既难维护，也会带来额外的通信和执行开销。

存储过程的优点可以抓住三点：效率高；降低客户机和服务器之间的通信量；方便实施企业规则。第三点尤其重要，因为把经过确定的处理流程放在服务器端，调用者只要遵守调用接口，就不必在每个客户端各写一套不同做法。

#### 创建、执行、修改和删除

存储过程的用户接口有四类基本动作：创建、执行、修改和删除。

创建时使用 `CREATE OR REPLACE PROCEDURE`，后面给出过程名、参数列表，再接 `AS` 和过程化 SQL 块：

```sql
CREATE OR REPLACE PROCEDURE procedure_name(
    parameter_1,
    parameter_2
)
AS
    -- 过程化 SQL 块
;
```

名字本身没有额外魔力，只是为了以后调用时方便。参数负责把外部数据送进黑盒子，过程体负责真正执行功能。参数可以有输入参数、输出参数，或者两者兼有；默认是输入参数。调用时给出的参数值必须明确指定数据类型的值。

执行使用调用语句，例如 `CALL`，也可以使用相应的执行形式；修改过程时，接口可以把它重命名；删除时使用 `DROP PROCEDURE` 加上过程名。

定义阶段比较复杂，是因为我们必须把判断、数据处理和错误处理完整写清楚。执行、删除和重命名则简单得多，因为功能已经被封装好了。这里体现的就是黑盒子的价值：写的时候多花一点功夫，用的时候只管调用。

### 银行转账案例：四个判断拼成一个黑盒子

下面用一个银行转账例子，把过程化 SQL、存储过程、参数、变量和流程控制真正串起来。

要求很具体：从一个账户转出指定金额，转入另一个账户。站在普通用户的角度，这似乎就是“钱从 A 到 B”一步；可站在系统开发人员的角度，至少要想清楚四件事：转出账户是否存在；转出账户的余额是否足够；转入账户是否存在；确认前面都没问题以后，才真正执行转账。

这个例子还有一个很直观的现实来源：银行账户通常是整数性质的标识，不会有小数，也不可能是负数；金额却可能精确到小数点后两位，所以金额要使用浮点类型。

下面这段代码按照讲述的结构整理出来，假定表名是 `account`，其中有 `account_number` 和 `total` 两列：

```sql
CREATE OR REPLACE PROCEDURE transfer(
    in_account INT,
    out_account INT,
    amount FLOAT
)
AS
DECLARE
    total_deposit_out FLOAT;
    total_deposit_in FLOAT;
    in_account_number INT
BEGIN
    SELECT total
      INTO total_deposit_out
      FROM account
     WHERE account_number = out_account;

    IF total_deposit_out IS NULL THEN
        ROLLBACK;
        RETURN;
    END IF;

    IF total_deposit_out < amount THEN
        ROLLBACK;
        RETURN;
    END IF;

    SELECT account_number
      INTO in_account_number
      FROM account
     WHERE account_number = in_account;

    IF in_account_number IS NULL THEN
        ROLLBACK;
        RETURN;
    END IF;

    UPDATE account
       SET total = total - amount
     WHERE account_number = out_account;

    UPDATE account
       SET total = total + amount
     WHERE account_number = in_account;

    COMMIT;
END;
```

这段代码虽然读起来有四页那么长，但逻辑并不神秘。我们不要一上来就被整段代码吓住，应该先看它如何把一个完整转账过程拆成几个块。

#### 参数和变量不是一回事

这里的 `in_account`、`out_account` 和 `amount` 是参数。它们的作用是把外部输入带进存储过程：哪个账户转入、哪个账户转出、要转多少钱，都是调用者传进来的数据。

`total_deposit_out`、`total_deposit_in` 和 `in_account_number` 是变量。变量是在黑盒子内部执行过程时使用的临时容器。可以把变量想成一个碗：先从查询结果中把值接住，再带着这个值去后面做判断或更新。

参数和变量，解决的是两个方向的问题：

```text
外部调用者
    │  参数：把数据送进来
    ▼
存储过程
    │  变量：接住数据、在块内传递
    ├── 查询、判断
    └── 更新、提交
    ▼
数据库中的账户余额
```

这个区分非常重要。用户从键盘输入的账户和金额，是参数；过程内部从表中取出的余额、要操作的账户号，是变量。不要因为它们最后都表现为一个值，就把它们混成一类。

#### 第一步：查转出账户有没有余额

```sql
SELECT total
  INTO total_deposit_out
  FROM account
 WHERE account_number = out_account;
```

这句话的意思是：在 `account` 表中找到要转出的账户，把它的 `total` 取出来，放进 `total_deposit_out` 这个变量。

接着判断：

```sql
IF total_deposit_out IS NULL THEN
```

如果取出来的值是空的，就说明没有从账户中拿到余额。按照这个例子的处理方式，可能是账户不存在，也可能是这个账户没有存款；一个判断同时挡住了这两种情况。发现问题时，执行 `ROLLBACK`，再 `RETURN`，整个过程结束。

`ROLLBACK` 的作用是把事情退回初始状态。转账是一个完整操作，不能只完成了后半段就留下半成品；如果前提不满足，就不要继续改账户数据。

#### 第二步：余额够不够

确认转出账户能够取到余额以后，还要判断它是否足够支付本次转账：

```sql
IF total_deposit_out < amount THEN
```

余额小于要转出的金额，就同样回滚并返回。这个条件不是重复检查账户存不存在，而是在已有的余额基础上继续确认“够不够”。

到这里，转出账户的两个问题就检查完了：账户能不能找到，余额够不够。

#### 第三步：转入账户存不存在

接下来查询转入账户：

```sql
SELECT account_number
  INTO in_account_number
  FROM account
 WHERE account_number = in_account;
```

这次把找到的账户号放进 `in_account_number`，用于判断目标账户是否存在。如果它是空值，就说明要转入的账户没有找到，同样执行 `ROLLBACK` 和 `RETURN`。

这里不需要再判断转入账户有没有钱，因为它是收钱的一方。我们没有理由因为一个账户当前余额不够，就拒绝把资金转入它；只要账户存在并且是合法目标，就可以继续执行。

因此，转账前真正要判断的就是三件事：转出账户存在、余额足够、转入账户存在。三件事都通过，才进入正式更新。

#### 第四步：扣钱、加钱并提交

转账本质上是两次更新：

```sql
UPDATE account
   SET total = total - amount
 WHERE account_number = out_account;

UPDATE account
   SET total = total + amount
 WHERE account_number = in_account;
```

第一条更新从转出账户扣掉 `amount`，第二条更新向转入账户加上同一个 `amount`。做完以后用 `COMMIT` 提交，过程以 `END` 结束。

现在回头看，这段代码并不只是几条 `UPDATE`。它把检查、业务条件和实际更新按顺序摞在一起：

```text
检查转出账户
      ↓
检查余额是否足够
      ↓
检查转入账户
      ↓
扣减转出账户
      ↓
增加转入账户
      ↓
提交
```

这就是过程化 SQL 所说的“像搭积木一样拼出过程”。单个块的能力都很有限，但把它们按照正确的顺序连接起来，就能完成一个完整业务过程。

#### 封装之后，调用非常简单

定义时写得很复杂，使用时却很简单。调用者不需要知道内部的碗、变量和判断顺序，只要把三个接口传进来：转出账户、转入账户、金额。数据库服务器就会自动执行已经封装好的过程。

例如，业务上可以说：从尾号为 `5868` 的账户转出一万元到尾号为 `3828` 的账户。调用时只需给出这三个参数，过程就会先检查，再扣款、加款，最后提交。

这个黑盒子没有必须交回去的结果值。钱已经完成转入转出，过程执行完就结束了，所以它叫存储过程。假如执行后还要给调用者一个回执，例如返回“本次转账已完成”的结果，那么再加上返回值，它就变成函数了。

这个案例最重要的价值，不是让我们背下每一行，而是让我们看懂：过程化 SQL 怎样把判断和数据操作组合成模块，存储过程怎样把这个模块放到数据库服务器中，调用者又怎样只靠参数把它叫起来。

### 函数只多做一件事：把结果交出来

函数和存储过程的共同点非常明确：都是持久性的存储模块，都是命名块，都可以使用过程化 SQL 的块、变量和流程控制。名字不同，但整体结构是一套。

创建函数时使用 `CREATE OR REPLACE FUNCTION`。它仍然有名字、有参数，后面同样接 `AS` 和过程化 SQL 块。唯一的增加是必须指定返回值的类型：

```sql
CREATE OR REPLACE FUNCTION function_name(
    parameter_1,
    parameter_2
)
RETURNS return_type
AS
    -- 过程化 SQL 块
;
```

执行时可以使用 `CALL`，也可以使用 `SELECT` 取得结果。修改函数可以重命名，也可以重新编译。对应的管理动作与存储过程相似，只是对象名称和返回值要求不同。

所以不要因为它叫函数，就把它想象成另一套完全不同的语言。它仍然是前面那套过程化 SQL，只是多了一条明确的出口：必须把结果交回来。这个出口就是它和存储过程最重要的分界。

### ODBC 为什么出现：不同数据库之间需要一个共同接口

接下来这条线和前面的“把一段程序封装起来”不同。我们先问一个很现实的问题：不同数据库管理系统的应用程序，能不能直接拼在一起使用？

现在有很多 DBMS，例如 SQL Server、Kingbase、MySQL，甚至 Access。某个应用程序是在一个 DBMS 的框架下编写的，如果另一个部门使用的是另一种 DBMS，那么原程序能不能直接拿到另一个部门的数据？通常不能直接假定可以。

可以想象一个学校的信息系统：教务处使用 SQL Server，财务处使用 Kingbase。学校主页或综合管理平台需要把两个部门的数据联动起来，例如根据教务处提供的成绩名次和财务处的发放规则计算奖学金。一个应用要同时访问两个不同系统的数据，这就是 ODBC 要面对的需求。

这里不是某一个用户忘了怎么写 SQL，也不是某一个数据库故意为难别人，而是不同 DBMS 各有自己的访问方式。应用程序需要一个共同的办法，屏蔽这些差异，访问不同关系数据库管理系统中的数据资源。

#### ODBC 是谁提出的

ODBC 是微软提出的开放服务体系中关于数据库访问的部分，前面常写作 Windows Open Services Architecture。它提供一组访问数据库的应用程序编程接口，也就是 API。

API 的作用不只是“给一个函数名字”，更重要的是把接口约束下来，规范应用开发，规范关系数据库管理系统的应用接口。以后不同厂商开发自己的 DBMS 或相关程序时，都按这个标准来做，应用程序就有机会互相联系、互相调用。

可以把 ODBC 理解成微软先把游戏规则定出来：不同数据库厂商如果要在同一个应用环境中工作，就要按照共同的接口规范来设计。不按规则做，程序也许只在自己的系统里能用，最后就容易变成一个数据孤岛。

这也是为什么行业标准和龙头企业的影响力不只是“我有一个产品”，还体现在“我能规定大家怎么连接”。ODBC 的价值就在于把不同数据库之间的差异放到一个共同标准后面。

### ODBC 的三层中间层

ODBC 的工作原理可以画成一条很清楚的路径。假设学校综合信息系统要同时取学生处、教务处和财务处的数据，应用程序不直接钻进某一种数据库，而是通过 ODBC 的标准接口逐层访问：

```text
学校综合管理信息系统
          │
          ▼
    ODBC API
  （统一应用程序接口）
          │
          ▼
  ODBC 驱动程序管理器
          │
     ┌────┴────┐
     ▼         ▼
Kingbase      SQL Server
驱动程序      驱动程序
     │         │
     ▼         ▼
Kingbase     SQL Server
数据源        数据源
```

最上面是用户应用程序，中间是 API、驱动程序管理器和数据库驱动程序，最下面才是真正的数据源。应用程序从一个统一入口进去，驱动程序管理器根据目标数据库选择对应驱动，最后把结果送回来。

这就是 ODBC 体系结构真正有用的地方：应用程序不必在代码里直接死记某一个驱动、服务器名和数据库名，只要告诉中间层“我要连接哪个数据源”，中间层就能把请求送到合适的数据库。

#### 应用程序这一层

ODBC 应用程序中包含的内容很多，但可以按工作顺序理解：请求连接数据库；指定数据源；使用存储空间；处理操作结果和数据；处理错误；提交或回滚请求；最后断开数据源。

应用程序不必亲自管理每一种数据库的特殊细节。它把要做的操作交给 ODBC API，再由下面的层负责连接、通信、返回结果和处理错误。

#### 驱动程序管理器这一层

驱动程序管理器管理各种驱动程序，通常包含在系统里，常见名称是 `odbc32.dll`。它负责应用程序和驱动程序之间的通信，因此像一个协调者。

它可以建立、配置和删除数据源，也可以查看当前系统安装了哪些 ODBC 驱动程序。典型功能包括：装载 ODBC 驱动程序；连接并选择正确的驱动程序；管理数据源；检查数据源的合法性；记录 ODBC 函数调用等。

你可以把它类比成 DBMS 在整个数据库框架中的角色：用户负责提出需求，数据库负责保存数据，中间层的衔接、调度和控制工作由驱动程序管理器来做。它虽然不是最终的数据存储者，却把数据访问的中间工作集中起来了。

#### 驱动程序和数据源这一层

应用程序不能直接存取数据库。应用程序发出的各种操作请求，先由驱动程序管理器提交给某个数据库，再通过调用该驱动程序支持的函数完成存取。数据库操作的结果也通过驱动程序返回给应用程序。

如果应用程序要操作不同的数据库，就要动态连接到不同的驱动程序上。也就是说，换数据源并不是让应用程序完全换一套业务逻辑，而是让它通过不同的驱动去访问对应的数据源。

数据源可以是单宿，也可以是多宿。单宿就是数据源和应用程序在同一台机器上；多宿则支持客户机/服务器以及网络环境。三层客户机/服务器架构通常属于后者。数据库访问请求由驱动程序提交，结果也由驱动程序收集，再交给应用程序使用。

数据源对最终用户是透明的。用户真正关心的是从系统中得到数据，而不是底层到底调用了哪一个驱动程序。正因为有这层透明性，应用程序才有机会用统一方式使用不同数据库。

#### 用数据源名称代替底层细节

假设某学校在 SQL Server 和 Kingbase 上分别创建了数据库：一个是人事处数据库，一个是教学科研处数据库。学校信息系统需要同时访问它们，于是为人事数据库建立名为 `Person` 的数据源，为教学数据库建立名为 `Education` 的数据源。

以后访问时，只需要连接 `Person` 或 `Education`，不需要自己记住驱动程序、服务器名和数据库名。这正是中间层带来的便利：名称指向数据源，底层连接由系统安排。

### ODBC 的 API：函数、句柄和数据类型

ODBC API 是一组程序接口。按讲义中的层次，它包含核心级、扩展一级和扩展二级；语法上也可以对应最低限度的 SQL 语法、核心 SQL 语法和扩展 SQL 语法。真正使用时，最先要把三类东西弄清楚：函数、句柄和数据类型。

函数解决“应用程序怎样向数据源发请求、怎样取回结果”；句柄解决“怎样找到下一层的连接和执行环境”；数据类型解决“数据在应用程序和数据库之间怎样保持合适的表示”。

#### 函数接口

ODBC 3.0 标准提供了 76 个函数接口。它们大体覆盖几类工作：分配和释放环境、连接与语句句柄；建立连接；获取信息；事务处理；执行 SQL；读取编目信息。

连接相关的 `DriverConnect`，信息相关的 `GetInformation` 以及 `SQLGetFunction`，事务处理相关的接口，还有立即执行接口，都是这套函数集合中的组成部分。编目函数则可以获取数据字典信息，例如表、列和权限结构等。

这里要记住版本问题。不同版本上的函数和函数使用方式可能不同，某个版本支持的能力不一定在另一个版本里保持同样的调用方式。这和 Python 不同版本之间的函数变化有相似之处：使用接口前不能只看函数名，还要看自己面对的版本和驱动能力。

#### 句柄：把不同层次的资源串起来

句柄可以理解为 ODBC 用来定位下一层资源的连接钥匙。讲义把它描述为一个代表指针的 32 位整数值，分为环境句柄、连接句柄、语句句柄和描述句柄。

它们的关系可以这样看：

```text
一个 ODBC 应用程序
          │
          └── 1 个环境句柄
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
      连接句柄 A           连接句柄 B
          │                   │
      ┌───┴───┐           ┌───┴───┐
      ▼       ▼           ▼       ▼
   语句句柄 语句句柄   语句句柄 语句句柄
```

每个 ODBC 应用程序需要建立一个独立的 ODBC 环境，并分配一个环境句柄，用来保存环境状态、诊断信息等全局背景。一个环境句柄可以连接多个连接句柄；每个连接句柄可以实现与一个数据源的连接。一个连接里又可以建立多个语句句柄，因此它不只对应一条孤零零的 SQL 语句，还可以容纳具体语句、结果集以及相关信息。

描述句柄则是更深一层的结果描述信息。通过这些不同层次的句柄，应用程序才能在不同数据源之间安排连接、语句和结果处理。记住这个层次关系，ODBC 代码就不会只剩下许多没有方向的函数名。

#### SQL 数据类型和 C 数据类型

SQL 数据类型用于数据源，C 数据类型用于应用程序中的变量和代码。应用程序可以通过 `SQLGetTypeInfo` 获取不同驱动程序支持的数据类型情况。

数据在两个方向上传递时，绑定函数的作用也不同：

```text
数据源 ──结果──> 应用程序
      SQLBindCol

应用程序 ──参数──> SQL 语句
      SQLBindParameter
```

从结果集取数据回到应用程序时，要通过 `SQLBindCol`，把结果列绑定到应用程序中的位置；把应用程序变量传进 SQL 语句时，则使用 `SQLBindParameter`，把变量绑定为语句参数。

这件事其实和嵌入式 SQL 里的思想是通的：一边是主程序里的变量和值，另一边是 SQL 的数据。区别只是这里由 ODBC 统一规定函数、句柄和类型，让应用程序不必为每个数据库各写一套处理方式。

### 从配置数据源到释放句柄：ODBC 的工作流程

ODBC 的完整工作流程可以按下面的顺序记住：

```text
配置数据源
    ↓
初始化环境
    ↓
建立连接
    ↓
分配语句句柄
    ↓
执行 SQL
    ├── 没有结果 → 结束
    └── 有结果 → 处理结果集
    ↓
释放句柄并终止
```

#### 配置数据源

数据源可以通过驱动程序管理器提供的配置功能来增加、修改和删除，也可以使用数据源管理工具。配置的本质，是给不同数据库建立可以被应用程序识别的名称和连接信息。

#### 初始化环境并建立连接

环境并不和某一个具体驱动程序直接绑定，而是由驱动程序管理器控制和配置。应用程序调用连接函数以后，驱动程序管理器才会调用所连接驱动程序中的 `SQLAllocHandle`，分配环境句柄所需的数据结构。

建立连接时，应用程序通过 `SQLConnect`、`SQLDriverConnect` 或 `SQLBrowseConnect` 与数据源连接。连接函数的输入包括配置好的数据源名称、用户 ID 和口令。连接失败时会返回相应的错误值；如果成功，就可以继续使用这个连接句柄。

#### 分配语句句柄并执行

在处理任何 SQL 语句之前，应用程序还要先分配语句句柄。语句句柄中会包含具体 SQL 语句、输出结果集以及相关信息。应用程序可以通过 `SQLSetStmtAttr` 设置语句属性，也可以直接使用默认值。

执行 SQL 有两种方式：预处理执行和直接执行。预处理适用于语句需要多次执行的情况；直接执行则是直接运行当前语句。语句中如果含有参数，就先把参数绑定到应用程序变量，再执行。使用了问号这样的占位符以后，真正调用时再把变量值送进去。

可以把它想成先把句柄、语句结构和参数位置准备好，再把具体数据放进去执行。这样同一个过程可以反复运行，而不必每次把整套源代码重新写一遍。

#### 处理结果并释放资源

执行后，如果有结果集，就继续处理结果集。可以获取结果集的列数，也可以获取每一列的名称、类型、长度和范围。结果处理还可以使用游标；游标在这里承担的工作，和前面过程化 SQL 讨论过的游标是同一种思路。

工作结束时，要释放句柄，常见操作就是 `free handle`。不释放，连接和执行环境就一直留着；使用结束后明确释放，才是完整流程的结尾。

### 跨库搬运学生数据：ODBC 的代表性例子

最后看一个具体例子，把前面的层次和工作流程串起来。

假设某个学校的两个部门分别使用 Kingbase 和 SQL Server。Kingbase 中有一个人事处的 `Student` 表，SQL Server 中有一个教学科研处的 `Student` 表。学校信息系统现在要做的事情是：把 Kingbase 中的 `Student` 数据取出来，再通过多次插入放到 SQL Server 的 `Student` 表中。

这就是两个不同关系数据库管理系统之间的数据搬运。它不是简单的“增删改查”问题，因为数据来自 Kingbase，目标是 SQL Server，两个系统的连接环境不同。

如果两个部门本来使用的是同一个 DBMS，例如都用 SQL Server，那么直接从不同数据库取数据即可，ODBC 并不需要介入。ODBC 的代表性场景是：不同部门各自使用不同数据库，而一个应用又需要把它们整合起来。

在这个例子中，操作可以概括为两条 SQL：

```sql
SELECT * FROM Student;
```

它从 Kingbase 的 `Student` 表中取出数据。接着，把取到的值作为参数，反复插入 SQL Server：

```sql
INSERT INTO Student VALUES (?, ?, ?, ?);
```

问号是参数占位符。程序先把从 Kingbase 取出的值绑定到这些参数位置，再执行插入。这里的重点不是把问号当成四个特殊字符，而是理解“取出来的数据如何被绑定成下一条语句的输入”。

#### 两套句柄分别服务于两个数据源

因为需要同时使用两个数据库，程序通常会准备两套相关句柄：

- 以 `king` 开头的一组，对应 Kingbase；
- 以 `server` 开头的一组，对应 SQL Server。

环境、连接和语句的对应关系可以先这样看：

```text
Kingbase
  环境句柄 → Kingbase 连接句柄 → Kingbase 语句句柄
                                      └── 读取数据，产生结果集

SQL Server
  环境句柄 → SQL Server 连接句柄 → SQL Server 语句句柄
                                          └── 接收并写入数据
```

上面这组语句句柄负责从 Kingbase 读取数据，把结果集接出来；下面这组语句句柄负责把取出的值放入 SQL Server。两个方向虽然都在一个应用程序中，但连接对象和执行对象是分开的。

程序先定义环境句柄、连接句柄和语句句柄，再定义后续操作需要的变量和返回状态。讲义中把返回状态记作 `RET`，执行一段操作后用它接收结果或错误状态。这里不要求死记每个变量的拼写，重点是看懂 Kingbase 和 SQL Server 各有一套句柄，不能把两边的连接混成一个。

#### 逐步执行跨库操作

这个例子的操作顺序可以按下面的方式理解：

1. 配置数据源。这里需要同时用到两个数据库系统，因此分别建立 Kingbase 和 SQL Server 两个数据源。
2. 定义并分配环境句柄。通过 `SQLAllocHandle` 为两个环境准备句柄。
3. 建立连接。调用 `SQLConnect`，传入数据源名称、用户 ID 和口令。讲义中示例使用的是 `system` 用户和 `manager` 口令；这里只是说明参数位置，不是在生产系统中照搬凭据。
4. 分配语句句柄。通过 `SQLAllocHandle` 为 Kingbase 和 SQL Server 分别建立语句句柄。
5. 设置语句属性。使用 `SQLSetStmtAttr` 设置需要调整的语句属性。
6. 执行查询和插入。Kingbase 侧执行 `SELECT * FROM Student` 取得数据，SQL Server 侧执行带占位符的 `INSERT`，再把取出的字段绑定进去。
7. 处理结果集。获取结果信息，按需要使用游标，把每一行数据处理成目标表的输入。
8. 释放句柄并结束连接，释放 Kingbase 和 SQL Server 两侧的环境、连接与语句句柄。

如果改变应用程序中的连接函数参数，让它连接到另一种数据源，就可以转而访问另一个关系数据库系统。也就是说，跨库搬运的关键不在于为每个数据库重新设计一套业务步骤，而在于把“连接哪个数据源”和“执行什么 SQL”分开。

### 这一章真正要抓住的东西

数据库编程这一章的内容不少，但重要性并不完全一样。

前面讲过的嵌入式 SQL 是绝对重点，因为它解决的是 C 语言主程序怎样和 SQL 结合起来。今天这一段的重点，则是另外一条线：过程化 SQL 的块怎样组合成一个简单过程；这个过程怎样通过存储过程或函数封装起来；封装以后又怎样放到数据库服务器中，通过参数反复调用。

银行转账例子就是这条线上的完整代表。不要只记住两个 `UPDATE`，要看清楚它为什么先查转出账户、为什么判断余额、为什么还要检查转入账户，以及为什么每个失败分支都先回滚再返回。四个环节串起来，才是一个完整的业务过程。

ODBC 的地位要区分考试要求与现实用途。按这里的要求，ODBC 不再是后面需要重点掌握的内容；重要的是理解它为什么出现：不同 DBMS 的应用程序需要访问不同部门的数据资源时，必须有一套共同的 API、驱动程序管理器、驱动程序和数据源体系。

你可以把它想成微软在中间搭了三层桥：统一 API，交给应用程序；驱动程序管理器，负责协调；具体驱动程序，负责把请求送到对应数据库。今天很多集成开发环境会把连接细节隐藏起来，用户通常只需要在界面上选择数据库、输入连接信息，所以 ODBC 的具体代码不一定经常直接手写。但这不改变它的思想价值：标准化接口和中间层，解决了跨数据库访问的差异问题。

因此，实际工作中真正需要记住的是这条主线：

```text
嵌入式 SQL
    └── 把数据库操作接入应用程序

过程化 SQL
    └── 用块、变量、条件和循环组成处理过程

存储过程 / 函数
    └── 把过程封装到数据库服务器并反复调用

ODBC
    └── 用统一接口访问不同 DBMS
```

到这里，第八章数据库编程的两条主线就接起来了：一条是如何把 SQL 接进程序，另一条是如何把一段处理过程封装成数据库服务器上的可复用模块。ODBC 则补上了跨数据库访问的接口问题。再往后，数据库系统会进入应用环节，继续讨论如何优化、如何恢复，以及如何进行并发访问。

现在回头看过程化 SQL 的那些块、条件和循环，你会发现它们并不神秘：一个块只做一件事，条件决定走哪条路，循环决定重复几次，变量把中间结果接住，异常处理负责在出错时收场。真正困难的不是某个关键字，而是能不能把一个业务过程准确地拆成这些小块，并且按正确顺序把它们拼起来。能把这一点看懂，存储过程就不再是一个需要死记的代码外壳；能把它封装、调用并解释清楚，数据库编程才算真正接上了程序这一端。
