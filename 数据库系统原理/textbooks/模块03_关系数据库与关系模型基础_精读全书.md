## 关系模型结构与数据完整性约束
> 对应块：BLK06 | 覆盖分集：P05 | 块标题（分集名）：《数据库第2章 关系数据库 （上）》

我们在刚接触数据库时，总会听到一句话：“关系就是二维表，二维表就是关系。”但如果退一步审视，在汉语语境里，“关系”描述的是事物之间的关联，“二维表”则是一种直观的行列排布结构，两者字面含义相去甚远。为什么在数据库体系中，关系就能严丝合缝地等价于一张二维表？这张二维表究竟是从什么样的数学机理中推导出来的？

1970年，埃德加·科德（E. F. Codd）在 *Communications of the ACM* 上发表了奠基性论文 *A Relational Model of Data for Large Shared Data Banks*。这篇论文后来入选了20世纪90年代人类计算机科学领域的50篇经典论文之一。科德在论文中开创性地提出了关系模型，随之建立起关系代数与关系演算体系。在此基础上发展出的第一范式（1NF）、第二范式（2NF）、第三范式（3NF）乃至BCNF，本质上就像学生修学分升级一样——从一年级升入二年级、三年级，数据库模式遵循越发严格的标准进行规范化演进。本讲我们将深入剖析关系模型的数学本质、形式化定义、操作体系以及三大完整性约束。

### 关系数据结构与形式化推导

#### 域、笛卡尔积与关系的数学本质

要彻底搞清二维表到底是怎么来的，必须建立一条从集合论通往二维表的逻辑链条。这条链条由三个递进的概念构成：域（Domain）、笛卡尔积（Cartesian Product）和关系（Relation）。

域是一组具有相同数据类型的值的集合。我们可以把它直观地理解为一个“数据池子”，后续所有属性的具体取值都必须从对应的池子中捞取。例如：全体整数、0到100的成绩区间、某高校开设的所有专业、或者取值为“男/女”的性别集合，都是一个域。同一个域中的数据，必然具备统一的数据类型与明确的语义指向。

有了池子之后，我们把多个池子中的元素按照所有可能的方式进行组合，这就得到了笛卡尔积。给定一组域 $D_1, D_2, \dots, D_n$（其中部分域可以相同），这 $n$ 个域的笛卡尔积定义为所有可能有序组的集合：

$$D_1 \times D_2 \times \dots \times D_n = \{(d_1, d_2, \dots, d_n) \mid d_i \in D_i, i = 1, 2, \dots, n\}$$

对于很多初学者来说，教材里的数学符号往往显得晦涩。我们可以通过一个极简的规则来拆解它：每一个大写字母 $D_i$ 代表一个数据池子，小写字母 $d_i$ 代表从池子 $D_i$ 中取出的一个具体数据，下标 $i$ 则是给各个池子排的序号。笛卡尔积的本质，就是把 $n$ 个数据池子中的元素穷举匹配，生成包含所有组合可能性的全集。

在笛卡尔积构成的庞大集合中，存在三个基础度量：
- **元组（Tuple）**：笛卡尔积中的每一个元素 $(d_1, d_2, \dots, d_n)$ 称为一个元组。映射到后续的二维表中，一个元组就是表中的一行。
- **分量（Component）**：元组中的每一个具体值 $d_i$ 称为一个分量。映射到二维表中，分量就是某一行某一列交叉处的一个单元格。
- **基数（Cardinal Number）**：若域 $D_i$ 中包含的元素个数记为 $M_i$，则这 $n$ 个域做笛卡尔积后生成的总元组数即为基数 $M$：

$$M = \prod_{i=1}^{n} M_i$$

```text
+-------------------+      +-------------------+      +-------------------+
| 域 D1: 导师集合   |      | 域 D2: 专业集合   |      | 域 D3: 研究生集合 |
| {王教授, 张教授}  |      | {计算机, 信息}    |      | {李勇, 刘晨, 王敏}|
+---------+---------+      +---------+---------+      +---------+---------+
          |                          |                          |
          +--------------------------+--------------------------+
                                     | 全量穷举组合
                                     v
                  +--------------------------------------+
                  | 笛卡尔积 D1 × D2 × D3 (共 2×2×3=12行)|
                  +--------------------------------------+
                                     | 筛选符合现实语义的子集
                                     v
                  +--------------------------------------+
                  | 关系表 R (仅保留真实的 3 行对应关系) |
                  +--------------------------------------+
```
*图 1：从域到笛卡尔积、再到关系二维表的收敛推导流程*

为了彻底看透这种组合机制，我们设定一个具体的学院场景：
- 第一个域 $D_1$ 为导师集合：$D_1 = \{\text{王教授}, \text{张教授}\}$，基数 $M_1 = 2$；
- 第二个域 $D_2$ 为专业集合：$D_2 = \{\text{计算机}, \text{信息}\}$，基数 $M_2 = 2$；
- 第三个域 $D_3$ 为研究生集合：$D_3 = \{\text{李勇}, \text{刘晨}, \text{王敏}\}$，基数 $M_3 = 3$。

三个域做笛卡尔积 $D_1 \times D_2 \times D_3$，生成的基数为 $2 \times 2 \times 3 = 12$。如果我们将这12组结果排布出来，并横向展开，每一列对应一个域，每一行对应一个组合元组，就天然形成了一张包含12行的二维表。

那么，究竟什么是关系？

> **定义**：在域 $D_1, D_2, \dots, D_n$ 上的笛卡尔积 $D_1 \times D_2 \times \dots \times D_n$ 的任意子集，称为在这些域上的一个关系（Relation），记作 $R(D_1, D_2, \dots, D_n)$。

在这12行穷举出来的笛卡尔积中，绝大部分组合在客观现实中是不成立的。现实中全院只有三位研究生：李勇、刘晨和王敏。每位研究生只能跟随特定的导师，就读特定的专业。假设李勇是王教授带的计算机专业研究生，刘晨是王教授带的信息专业研究生，王敏是张教授带的计算机专业研究生，那么符合客观现实的真实记录只有3行。

我们将这符合现实的3行从庞大的12行笛卡尔积中筛选提取出来，组成一个规模更小的集合。这个集合所表达的，正是导师、专业与研究生三者之间真实的语义对应联系。因为这一子集刻画了客观世界中的实体联系，所以被称为“关系”；而它的组织表现形式，正是一张三列三行的二维表。

关系中的列数称为目（Degree）或度。仅有一列的关系称为一元关系（Unary Relation），有两列的称为二元关系（Binary Relation），有三列的称为三元关系（Ternary Relation），包含 $n$ 列的称为 $n$ 元关系。

在关系模型中，二维表根据生成机制与存储特性的不同，主要表现为三类：
1. **基本表（Base Table）**：在数据库中实际物理存储、独立存在的表，例如全班30名学生的学生信息表。
2. **查询表（Query Table）**：执行查询操作时根据检索条件筛选出的临时结果表，例如从学生表中筛选出10名男生所生成的结果，其数据直接依赖于底层的基本表。
3. **视图表（View）**：由一个或多个基本表导出的虚表。视图并不独立存放具体的物理行数据，而是以定义的形式动态映射基本表中的数据。例如我们只想查看“导师与学生”的对应名单，而不想暴露专业信息，就可以单独抽取这两列构建一张视图。

尽管三种表的工程形态各异，但其底层都遵循完全统一的二维关系结构。

#### 二维表的六大基本性质

关系模型对二维表有着严谨的数学规范，一张合法的关系必须满足以下六大性质：

| 性质序号 | 规范要求 | 核心技术原理 |
| :--- | :--- | :--- |
| 性质一 | 列是同质的（Homogeneous） | 每一列中的各个分量必须取自同一个域，具有相同的数据类型与语义。 |
| 性质二 | 不同的列可出自同一个域 | 允许不同列使用同一数据源。例如将“人名”定义为一个统一域，导师列与学生列均可从中取值。 |
| 性质三 | 列的次序可以任意交换 | 关系的列排列没有前后逻辑依赖，调整列的位置不会改变关系的数学语义。 |
| 性质四 | 行的次序可以任意交换 | 元组的集合是无序的，无论是按成绩降序还是按学号升序，其底层集合等价。 |
| 性质五 | 任意两元组候选码不可重复 | 集合中不允许存在两个完全相同的元组，每一行必须在码的作用下保持唯一标识。 |
| 性质六 | 分量必须取原子值（Atomic） | 表中每一格数据不可再分，绝对严禁“表中套表”，必须维持纯粹的平面结构。 |

在上述性质中，第六条“分量必须取原子值”是关系数据库最为核心的工程红线。在日常办公中，人们经常会在Excel表格的一个大单元格内部嵌套一份细分的小名单（例如在某个专业单元格内，纵向拆出研一、研二两行子列表）。这种非平面的“大表套小表”结构在关系数据库中是绝对无法处理的。因为一旦出现嵌套，从上往下投影时就无法唯一定义属性列的归属。关系数据库处理此类业务时，必须在入库前进行人工或逻辑上的“拉平”处理，将分层信息拆解为平铺的属性列（例如增设一列“年级”），确保整张表横平竖直、每个格点均为原子值。

#### 码体系与属性分类辨析

理解关系模型的关键在于理清“码（Key）”的概念。码在工程中常被称为“键”，其正式的数学定义如下：

> **定义**：若关系中的某一属性或属性组的值能唯一地标识出一个元组，且其任何真子集都无法唯一标识该元组，则称该属性或属性组为**候选码（Candidate Key）**。

将这一术语翻译为直白的工程语言：**表中能够唯一确定某一行数据的单一列，或者多列组合，就是候选码。**

判定一个属性或属性组能否晋升为候选码，必须同时满足两个硬性门槛：
1. **非空性**：该属性绝对不能包含空值（`NULL`）。如果允许为空，一旦传入空值，系统根本无法定位它指向哪一行；
2. **唯一性**：该属性的取值在当前关系中绝对不能重复。一旦存在重复值，就会引发寻址歧义。

以包含“学号、姓名、性别、年龄、所在系”的学生表为例进行推演：
- “学号”唯一分配且不为空，可以唯一标识一行，属于候选码；
- 在学生人数较少的特定样本表中，“姓名”可能刚好没有重名且非空，在当前样本下它也能标识一行，因而也是候选码之一；
- “性别”、“年龄”、“所在系”均存在大量重复值，显然无法作为候选码。

当一张表中存在多个满足条件的候选码时，数据库设计者需要从中挑选一个作为**主码（Primary Key，PK）**。挑选主码并没有绝对的数学限制，但需要遵循工程稳定性原则。在上述学生表中，尽管样本数据里的姓名未发生重复，但随着学校办学规模扩大，重名几乎必然发生，而学号由系统机制保障永远唯一。因此，二选一时应当毫不犹豫地将学号设为主码。

在此基础上，属性被严格划分为两类：
- **主属性（Primary Attribute）**：包含在**任何一个候选码**中的属性，统称为主属性。
- **非主属性（Non-key Attribute）**：不包含在任何候选码中的属性，称为非主属性。

> **易错点**：很多同学在初学时极易产生误解，以为“主属性就是主码那一列”。必须明确：主属性绑定的是“全体候选码”的并集，而不是仅指被选中的“主码”。只要某个属性存在于某一个候选码中，它就是主属性！

除单列主码外，更普遍的场景是多列组合构成的**复合主码**。考虑如下学生选课成绩表：

| 学号 | 课程号 | 成绩 |
| :--- | :--- | :--- |
| 201215121 | 1 | 92 |
| 201215121 | 2 | 85 |
| 201215121 | 3 | 88 |
| 201215122 | 1 | 90 |
| 201215122 | 2 | 80 |

分析这张表的主码定位过程：
1. 单独考察“学号”：同一个学生选修了多门课，学号反复出现，存在重复，无法唯一确定一行；
2. 单独考察“课程号”：同一门课被多名学生选修，课程号也存在重复，无法唯一确定一行；
3. 单独考察“成绩”：考试分数极易相同，绝对不能充当码；
4. 既然单列无法独立寻址，就必须尝试属性组合。考察“（学号，课程号）”二元组：业务逻辑规定一个学生对同一门课程只能有一条选课成绩记录，不会出现同一学号在同一课程下录入两条不同分数的合法情况。因此，由“学号 + 课程号”构成的属性组能够唯一锁定一行，两者联合构成复合主码。

在极端情况下，若关系中任意真子集都存在重复可能，必须将全表所有属性捆绑在一起才能唯一确定一个元组，这种由全体属性组共同构成的候选码被称为**全码（All-key）**。

#### 关系模式的形式化定义

在关系模型中，必须严格区分“型（Type）”与“值（Value）”。
- **型**是对关系的结构描述，称为**关系模式（Relation Schema）**，它是静态的、长久稳定的框架；
- **值**是关系模式在某一时刻的具体状态与数据集合，即实际的二维表数据，它是动态变化的。

打个比方：关系模式好比一套房屋的建筑蓝图（例如“三室一厅、承重墙位置、管道排布”），而关系则是某一时刻搬入具体家具、住进特定住户的房间实体。

为了让任何通用的数据库管理系统（DBMS）都能精准解析一张表的框架，关系模式在形式化上被严谨地定义为一个五元组：

$$R(U, D, DOM, F)$$

这五个分量分别承载着明确的工程语义：
- **$R$（Relation Name）**：关系名，即这张表在系统中的标识（例如 `Student`）。
- **$U$（Attributes Set）**：组成该关系的属性名集合（例如 `U = {学号, 姓名, 性别, 年龄, 所在系}`）。
- **$D$（Domains Set）**：属性组 $U$ 中各个属性所来源的域的集合，定义了数据池的物理与逻辑边界。
- **$DOM$（Domain Mapping）**：属性向域的映射集合，明确表中每一列具体取自哪一个数据池。
- **$F$（Functional Dependencies）**：属性间数据依赖关系的集合。

初学者常常疑惑：表格结构里为什么需要定义依赖关系 $F$？在数学中，函数本质上是自变量向因变量的映射（$y = f(x)$，给定一个确定的 $x$，就能唯一解出对应的 $y$）。在学生表中，若学号是主码，当我们给出确定的学号 $x = \text{95001}$ 时，该学生的姓名、性别、年龄和所在系这组非主属性值便被唯一确定。这种非主属性对主码的强绑定约束，就是属性间的数据依赖。完整描述了 $F$，系统才能在底层实施完整性校验与范式优化。

在日常工程实践中，由于域映射与依赖关系通常已在底层数据字典中固化，关系模式常被精简表示为“关系名 + 属性列表”的简写形式：

$$R(A_1, A_2, \dots, A_n)$$

例如：`Student(学号, 姓名, 性别, 年龄, 所在系)`。

关于关系模型的存储结构，设计者需要建立清晰的抽象隔离认知：我们在逻辑层定义的是横平竖直的二维表，但数据落地到底层磁盘时，最终都被操作系统分解为 `0` 和 `1` 的二进制流，存储在具体的文件块中。这种从逻辑表到物理磁盘分区的映射规则，要么交由操作系统管理，要么由特定的商业 DBMS（如 SQL Server、Oracle）在预先划定的存储空间内自行调度。这种物理实现细节对上层关系模型是完全透明的，应用开发者无需介入底层的物理磁道分配。

### 关系操作体系概述

#### 传统集合运算与专门关系运算

在数值计算中，数字与数字通过加、减、乘、除四则运算产生新的数字；在关系模型中，表与表之间同样通过明确定义的算子进行计算，其运算结果依然是一张二维表。关系操作主要涵盖查询（Query）与更新（Update，包含插入 Insert、修改 Update、删除 Delete）两大范畴。

关系查询操作由两大类共八个基础算子构成：

```text
关系查询操作体系 (8个基础算子)
├── 传统集合运算 (基于集合代数，针对相同结构的元组)
│   ├── 并 (Union, ∪)
│   ├── 交 (Intersection, ∩)
│   ├── 差 (Difference, -)
│   └── 广义笛卡尔积 (Cartesian Product, ×)
└── 专门关系运算 (针对二维表特性的空间投影与筛选)
    ├── 选择 (Selection, σ)      [水平行筛选]
    ├── 投影 (Projection, π)     [垂直列抽取]
    ├── 连接 (Join, ⋈)           [多表条件拼合]
    └── 除 (Division, ÷)         [反向全覆盖检索]
```
*图 2：关系查询操作的两大类八种基础算子分类图*

传统集合运算直接继承自数学中的集合代数：并（$\cup$）、交（$\cap$）、差（$-$）和笛卡尔积（$\times$）。这类运算将二维表视作元组的集合，要求参与运算的关系必须满足并相容性（除笛卡尔积外，参与运算的两张表必须具备相同的目，且对应属性来自相同的域）。

专门关系运算则是专门为关系模型量身定制的核心算子，涵盖选择（Selection，$\sigma$）、投影（Projection，$\pi$）、连接（Join，$\bowtie$）和除（Division，$\div$）。选择算子实现的是水平方向上的行筛选（例如从全表中筛选出 `性别 = '男'` 的记录）；投影算子实现的是垂直方向上的列抽取（例如只提取学生的 `学号` 与 `姓名` 两列）；连接算子通过共有属性将多张表横向拼合；除法算子则用于解决“选修了全部指定课程”这类具备“包含/全覆盖”语义的高级综合查询。这八个算子构成了关系代数的完备基石。

#### 关系数据库语言的分类

关系操作在具体系统实现中演化出不同的语言表现形态：
- **关系代数语言**：以代数算子为核心，通过显式指定表的运算步骤与执行路径来表达查询要求，具备过程化特征。
- **关系演算语言**：以数理逻辑中的谓词为核心，用户仅需声明“需要什么样的数据”，而无需指定“如何一步步运算求出”，具备非过程化特征。
- **结构化查询语言（Structured Query Language，SQL）**：吸纳了关系代数的操作内核，同时融合了关系演算的声明式谓词表达，集数据定义（DDL）、数据操纵（DML）、数据控制（DCL）于一体，成为工业界绝对主导的标准关系数据库语言。

### 关系完整性约束规则

数据模型是现实世界在计算机中的映射。现实世界由三要素构成：**实体（Entity）**、**属性（Attribute）**和**联系（Relationship）**，统称为 EAR 体系。为了保障存储在二维表中的数据不失真、不冲突、不产生语义矛盾，关系模型针对这三要素制定了三类规则，即关系的完整性约束。

```text
现实世界三要素 (EAR)                  关系数据库三大完整性
+-----------------------+              +-----------------------------------+
| 实体 (Entity)         | -----------> | 实体完整性 (主属性不可为空)       |
+-----------------------+              +-----------------------------------+
| 联系 (Relationship)   | -----------> | 参照完整性 (外码要么空，要么对齐) |
+-----------------------+              +-----------------------------------+
| 属性 (Attribute)      | -----------> | 用户定义完整性 (业务规则强约束)   |
+-----------------------+              +-----------------------------------+
```
*图 3：现实世界数据要素与关系数据库完整性约束对应机制*

#### 实体完整性

> **规则**：若属性（一个或一组）$A$ 是基本关系 $R$ 的主属性，则属性 $A$ 绝不能取空值（`NULL`）。

实体完整性直接针对“实体”本身。在关系模型中，一个实体在现实世界中必然是可区分的独立个体，而在数据库中唯一定位该个体的锚点就是主码。如果允许主属性取空值，整个寻址逻辑将彻底坍塌。

以选课表 `SC(学号, 课程号, 成绩)` 为例，该表的主码是复合主码 `(学号, 课程号)`，因此“学号”与“课程号”均属于主属性。如果在录入数据时输入了一条 `(NULL, NULL, 90)`：
- 这条记录表示有人得了90分，但我们既不知道是谁得了90分，也不知道是哪门课得了90分；
- 若输入 `(201215121, NULL, 90)`，我们知道该同学得了90分，但无法确认是哪门课；
- 若输入 `(NULL, 1, 90)`，我们知道1号课程有人得了90分，却查不出得分者。

上述记录在业务上毫无意义，在系统内会导致元组无法唯一定位。因此，实体完整性是不可违背的底线规则。当向数据库中插入或修改数据导致主属性出现空值时，DBMS 会强制拦截并抛出完整性违规异常。

#### 参照完整性与外码机制

参照完整性用于约束实体与实体之间的“联系”。在现实世界中，实体很少孤立存在，表与表之间必须建立关联，而这种关联的实现载体就是**外码（Foreign Key，FK）**。

> **定义**：设 $F$ 是基本关系 $R$ 的一个或一组属性，但不是关系 $R$ 的码。如果 $F$ 与基本关系 $S$ 的主码 $K_s$ 相对应，则称 $F$ 为关系 $R$ 的外码。其中关系 $R$ 称为**参照关系（Referencing Relation）**，关系 $S$ 称为**被参照关系（Referenced Relation）**或**目标关系（Target Relation）**。

在学生表与专业表的关联中，学生表包含 `(学号, 姓名, 性别, 专业号, 年龄)`，专业表包含 `(专业号, 专业名)`。学生表中的“专业号”不是学生表的主码，但它对应了专业表的主码“专业号”。学生表就是参照关系，专业表则是被参照关系，两者通过一条逻辑连线绑定在一起。

必须深入思考一个技术底层问题：**为什么外码关联的必须是被参照表的主码（或候选码），而绝对不能是普通属性列？**

若允许外码关联目标表的非主码列，由于非主码列允许取重复值，一旦目标表中该列出现两条相同数据（例如专业表中存在两个同名的专业记录），参照表中的外码在顺着连线反向寻址时，就会瞬间陷入多歧义的二义性状态，系统无法判定该学生究竟归属于哪一个具体专业。因此，外码必须精准钉死在目标关系的主码上。

外码的拓扑连接形态主要包括以下三种场景：

1. **双表引用**：前述学生表通过“专业号”引用专业表的主码。
2. **多表多对多纽带**：在学生、课程与选修的多对多关系中，选修表 `SC(学号, 课程号, 成绩)` 作为纽带，其属性“学号”引用学生表的主码，“课程号”引用课程表的主码，两条逻辑连线协同维系三表一致性。
3. **自引用（自身参照）**：外码并不一定指向外部其他表，它完全可以指向关系自身。考虑一张班级学生表 `Student(学号, 姓名, 性别, 专业号, 年龄, 班长学号)`。一个班级推选班长，班长必须由本班在册学生担任，不可能从校外凭空抓取。因此，“班长学号”这一列的数据来源，其底层参照的正是该表自身的“学号”列。此时，该表既是参照关系，也是被参照关系。

```text
场景一：双表引用
+-------------------------------+       +---------------------+
| 参照关系 Student              |       | 被参照关系 Major    |
| 学号 | 姓名 | 专业号(FK) | ...| ----> | 专业号(PK) | 专业名 |
+-------------------------------+       +---------------------+

场景二：自引用 (自身参照)
+-------------------------------------------------+
| 学生关系 Student                                |
| 学号(PK) | 姓名 | ... | 班长学号(FK)            |
|    ^                         |                  |
|    +-------------------------+ (自身循环参照)   |
+-------------------------------------------------+
```
*图 4：外码引用的双表拓扑与自引用拓扑示意图*

在外码使用过程中，还需注意以下工程细节：
- 参照关系 $R$ 与被参照关系 $S$ 可以是不同关系，也可以是同一关系（自引用）；
- 外码 $F$ 与目标主码 $K_s$ 必须定义在相同的域上，两者的数据类型、取值范围与语义含义必须严格一致（不能用学号去连人名）；
- 外码与目标主码**不要求同名**。在实际工程中，不同系统对接时可能一张表称“课程编号”，另一张表称“课号”，只要语义和底层域相同即可建立关联，不过同名更有利于工程识别与维护。

在明确了外码定义后，参照完整性规则可以高度概括为以下原则：

> **规则**：若属性（或属性组）$F$ 是基本关系 $R$ 的外码，它与基本关系 $S$ 的主码 $K_s$ 相对应，则对于 $R$ 中每个元组在 $F$ 上的取值只有两种可能：
> 1. 取空值（`NULL`）；
> 2. 等于 $S$ 中某一个元组的主码值。

这两种可能的工程意义极为明确：
- **允许取空值**：用于描述业务尚未建立关联的客观状态。例如刚入学的新生尚未确定专业，学生表中的“专业号”可以暂时为 `NULL`；刚选课尚未结课的学生，选修表中的“成绩”可以为空；
- **非空必须对齐**：只要外码一旦录入了具体数值，它就必须是目标关系中已经存在的有效主码。如果学院一共只有4个专业（编号1至4），学生表中的专业号就绝对不能录入 `5`；同理，班长学号必须在在册学生的学号列表中能够精准命中，绝不允许凭空编造。

#### 用户定义的完整性

实体完整性和参照完整性由关系模型强制约束，由 DBMS 底层自动校验；而用户定义的完整性则是针对特定属性列的具体业务规则。

> **定义**：用户定义的完整性是针对某一具体关系数据库的约束条件，它反映某一具体应用所涉及的数据必须满足的语义要求。

这一完整性完全由应用开发人员根据业务逻辑自主设定：
- **列值唯一性**：例如规定课程表中的“课程号”必须全局唯一；
- **非空限制**：例如规定“课程名”字段无论如何不能为 `NULL`；
- **值域范围校验**：例如学校规定课程学分最高为4学分、最低为1学分，绝无5学分或6学分的课程，则在定义字段时必须设定 `学分 BETWEEN 1 AND 4`，若用户录入 `6`，系统直接报错拒收；
- **枚举限制**：例如“性别”字段仅允许录入“男”或“女”，防止录入人员误将姓名录入至性别列中。

通过实体完整性（实体不丢底线）、参照完整性（联系不错位）、用户定义完整性（属性不越界）三道防线，关系数据库在理论层面为数据的严密性与逻辑一致性提供了完整的保障。

### 本讲思考与推导题

#### 选课成绩表的主码推导与判定

**思考背景**：
在建立关系模式时，精准判定候选码与主码是关系规范化的首要任务。考虑如下所示的学生选课成绩表：

| 学号 | 课程号 | 成绩 |
| :--- | :--- | :--- |
| 201215121 | 1 | 92 |
| 201215121 | 2 | 85 |
| 201215121 | 3 | 88 |
| 201215122 | 1 | 90 |
| 201215122 | 2 | 80 |

请推导该关系的主码构成，并分析为什么不能将单属性选为主码。

**推导解析**：
1. **检验单属性“学号”**：观察样本数据可知，学生 `201215121` 选修了3门课程，对应3行记录。“学号”列存在严重重复，无法依据单一学号唯一定位某一行选课记录，因此“学号”不能单独充当候选码；
2. **检验单属性“课程号”**：课程编号为 `1` 的课程被多名学生（`201215121` 与 `201215122`）选修，“课程号”列同样出现重复，无法唯一定位行，因此“课程号”亦不能单独充当候选码；
3. **检验单属性“成绩”**：成绩代表客观评价，不同学生在不同课程中完全可能考出相同的分数，不仅业务上不能具备标识性，数学上更无法保证唯一，绝无成为码的可能；
4. **两两组合推导**：单属性均失效后，考察二元属性组合。在高校选课规则中，一名学生对某一门特定课程在同一学期内有且仅有一条合法的最终考核记录。因此，“学号 + 课程号”构成的联合属性组在全表中必然非空且唯一，其任何真子集（单学号或单课程号）均无法独立保证唯一性。

**最终结论**：
该选课成绩表的主码为复合主码 `(学号, 课程号)`。其主属性包含“学号”与“课程号”，非主属性为“成绩”。由于“学号”与“课程号”均为主属性，根据实体完整性规则，两者在任何元组中均绝对不可取空值。

## 关系代数的运算体系与核心操作
> 对应块：BLK07 | 覆盖分集：P06上 | 块标题（分集名）：《数据库第2章 关系数据库 （下）》

我们日常使用数据库时，经常会提出各种具体的查询需求，比如“查一下某个班同学的某门课平均分”。当我们把这样一个指令丢给数据库系统时，底层以二维表形式存放的数据究竟该如何响应并给出正确结果？从逻辑层面上看，得出查询结果的过程，本质上就是对表所进行的一系列代数运算。这就是我们所说的关系代数。

> **定义**：关系代数是一种抽象的查询语言，它通过关系的运算来表达查询。

在关系模型中，关系就是二维表。因此所谓关系代数，实质上就是对二维表进行操作的代数系统。我们可以把它完全类比为初等数学：在初等数学里，操作对象是数字，数字与数字之间通过加、减、乘、除等运算符组合，运算结果仍然是数字；而在关系代数中：
1. **运算对象是关系**：参与运算的操作数是二维表；
2. **运算结果也是关系**：运算产生的结果依然是一张完整的二维表；
3. **运算符体系明确**：包含两类共八种核心运算符。

> **结论**：表和表经过运算后，结果依然是一张二维表。无论运算过程多么复杂，最终结果始终只涉及“谁是行、谁是列”。这一核心认知对于理解后续的连接与除法操作至关重要。

关系代数的八个运算符清晰地划分为两大家族：
- **传统的集合运算符**：并（$\cup$）、差（$-$）、交（$\cap$）、笛卡尔积（$\times$）；
- **专门的关系运算符**：选择（$\sigma$）、投影（$\pi$）、连接（$\bowtie$）、除（$\div$）。

```text
               ┌── 传统集合运算符 ── 并(∪)、差(-)、交(∩)、广义笛卡尔积(×)
关系代数运算符 ─┤
               └── 专门关系运算符 ── 选择(σ)、投影(π)、连接(⋈)、除(÷)
```
*上图展示了关系代数的八大运算符分类结构。*

我们先掌握这八种基本运算的计算规则，就如同先学会数学中的加减乘除；随后再将它们组合起来，解决复杂的实际查询“应用题”。

### 传统集合运算与相容性前提

传统的集合运算直接继承自数学中的集合论，概念非常直观。但将集合论引入二维表时，必须特别注意其使用前提。

#### 相容性前提条件

在对两个关系做并、差、交运算时，并不是任意两张表都能直接拿来运算。它们必须严格满足以下两个相容性前提：

1. **具有相同数目的属性列**：参与运算的两个表列数必须一致。如果一个表是三列，另一个表是四列，两者根本无法在集合层面合并或比对；
2. **相应位置的属性取自同一个域**：不仅列数要相同，对应位置上的属性语义和取值范围也必须完全一致。

> **易错点**：如果第一个表的第一列是学生姓名，第二个表对应位置的第一列是学号，即使两张表都是三列，也绝对不能做并、交、差运算。将姓名和学号强行混在一起得到的集合毫无现实逻辑意义。

#### 并运算（Union）

并运算符记为 $\cup$。设关系 $R$ 和关系 $S$ 满足相容性条件，两者的并运算定义为：

$$R \cup S = \{ t \mid t \in R \lor t \in S \}$$

其物理含义是把 $R$ 和 $S$ 中出现过的所有元组合并到一张新表中。如果在两张表中存在完全相同的重复行，则自动去重，只保留一份。

假设关系 $R(A, B, C)$ 包含 3 行元组，关系 $S(A, B, C)$ 也包含 3 行元组。若其中有 2 行元组在两个表中完全一致，则 $R \cup S$ 的结果并不是 $3 + 3 = 6$ 行，而是去重后的 4 行。

#### 差运算（Difference）

差运算符记为 $-$。关系 $R$ 与关系 $S$ 的差运算定义为：

$$R - S = \{ t \mid t \in R \land t 
otin S \}$$

其物理含义是找出所有属于 $R$ 但不属于 $S$ 的元组。实际操作时，从 $R$ 中逐行取出元组与 $S$ 比对：若该元组在 $S$ 中出现过，则剔除；若在 $S$ 中不存在，则保留到结果表中。

若 $R$ 包含 3 行，其中有 2 行与 $S$ 重复，那么 $R - S$ 最终仅保留那一行 $R$ 独有的元组。

#### 交运算（Intersection）

交运算符记为 $\cap$。关系 $R$ 与关系 $S$ 的交运算定义为：

$$R \cap S = \{ t \mid t \in R \land t \in S \}$$

其物理含义是找出既属于 $R$ 又属于 $S$ 的公共元组。在实际计算中，就是提取两张表中完全相同的所有行。在上述示例中，两表相同的 2 行即为交运算的最终结果。

#### 广义笛卡尔积（Extended Cartesian Product）

笛卡尔积用乘号 $\times$ 表示。在关系代数中，两个表的广义笛卡尔积表示将两个表中的元组进行无条件全排列组合，穷举所有的连接可能性。

设关系 $R$ 是 $n$ 目（度）关系，包含 $k_1$ 个元组；关系 $S$ 是 $m$ 目（度）关系，包含 $k_2$ 个元组。则 $R \times S$ 构成的结果表满足两条严格的代数规律：
- **结果表的属性列数（目数）等于各表列数之和**：$n + m$；
- **结果表的元组行数等于各表行数之积**：$k_1 \times k_2$。

$$R \times S = \{ \overset{\frown}{t_r t_s} \mid t_r \in R \land t_s \in S \}$$

这里的符号 $\overset{\frown}{t_r t_s}$ 表示将元组 $t_r$ 与元组 $t_s$ 首尾拼接成一个更长的复合元组。左半部分来自表 $R$，右半部分来自表 $S$。

如果表 $R(A, B, C)$ 拥有 3 列 3 行，表 $S(A, B, C)$ 也拥有 3 列 3 行，那么它们做笛卡尔积的结果表必然是 $3 + 3 = 6$ 列，以及 $3 \times 3 = 9$ 行。表 $R$ 的每一行都会分别与表 $S$ 的每一行进行配对。

### 关系代数表达式记号与像集概念

在进一步学习专门的关系运算符之前，必须先确立一套标准的代数符号体系，以便精确描述表中的行、列及单元格。

#### 常用符号记号

1. **关系与元组**：大写字母 $R$ 表示一个具体的关系（即数据表，如 Student 表）；小写字母 $t$ 代表元组（tuple），即表中的某一行记录，$t \in R$ 表示 $t$ 是关系 $R$ 中的一个元组；
2. **属性与分量**：大写字母 $A$ 表示属性（attribute），$A_i$ 表示第 $i$ 个属性列。记号 $t[A_i]$ 表示元组 $t$ 在属性列 $A_i$ 上的取值。行与列在坐标网格上交叉锁定的单一单元格值，称为分量（component）；
3. **属性组与其补集**：$A$ 也可以表示一组属性列构成的集合，$t[A]$ 表示元组 $t$ 在这一组属性列上的分量集合。记号 $\overline{A}$ 表示全集属性中剔除属性组 $A$ 之后所剩余的其他属性列（即补集）；
4. **元组连接**：记号 $\overset{\frown}{t_r t_s}$ 表示把两个短元组串联成一个更长的新元组。

#### 像集（Image Set）

像集是一个理解除法运算不可或缺的前置概念，英文称为 Image Set，意为“映射的集合”。

> **定义**：给定关系 $R(X, Z)$，其中 $X$ 与 $Z$ 为属性组。当元组 $t$ 在属性组 $X$ 上的分量取特定值 $x$ 时，$x$ 在关系 $R$ 中的像集定义为：
> $$Z_x = \{ t[Z] \mid t \in R \land t[X] = x \}$$

通俗地讲：我们在 $X$ 属性列上锁定某一个固定的取值 $x$，顺着这个条件把表中所有 $X=x$ 的行筛选出来，然后再看这些行在 $Z$ 属性列上都映射出了哪些取值。这些在 $Z$ 上的取值所构成的集合，就是 $x$ 的像集。

以下表关系 $R(X, Z)$ 为例进行推导：

| $X$ | $Z$ |
| :--- | :--- |
| $x_1$ | $z_1$ |
| $x_1$ | $z_2$ |
| $x_1$ | $z_3$ |
| $x_2$ | $z_2$ |
| $x_2$ | $z_3$ |
| $x_3$ | $z_1$ |
| $x_3$ | $z_3$ |

我们来求各元素的像集：
- 当 $X$ 取 $x_1$ 时，观察 $Z$ 列对应的取值有 $z_1, z_2, z_3$，因此 $x_1$ 在 $Z$ 上的像集为 $Z_{x_1} = \{ z_1, z_2, z_3 \}$；
- 当 $X$ 取 $x_2$ 时，对应 $Z$ 的取值为 $z_2, z_3$，因此 $Z_{x_2} = \{ z_2, z_3 \}$；
- 当 $X$ 取 $x_3$ 时，对应 $Z$ 的取值为 $z_1, z_3$，因此 $Z_{x_3} = \{ z_1, z_3 \}$。

我们也可以反向推导：如果要求在 $Z$ 属性列上取固定值 $z_3$ 时，其在 $X$ 属性列上的像集 $X_{z_3}$ 是什么？
在表中检索所有 $Z = z_3$ 的行，可以发现对应的 $X$ 值分别有 $x_1, x_2, x_3$。因此其像集为：

$$X_{z_3} = \{ x_1, x_2, x_3 \}$$

只要抓住“锁定一列的值，收集对应另一列所有可能取值”这一原则，像集的概念就非常清晰。

### 经典教学数据库模型

为了在具体情境下阐明关系代数的操作，我们引入一个贯穿数据库课程全程的经典案例：学生-课程教学数据库（Student-Course）。该模型包含三张核心表。

```text
┌──────────────┐          ┌──────────────┐
│   Student    │          │    Course    │
│  (学生个人)  │          │  (课程信息)  │
└──────┬───────┘          └──────┬───────┘
       │ Sno                     │ Cno
       │ (外码)                  │ (外码)
       ▼                         ▼
┌────────────────────────────────────────┐
│                   SC                   │
│        (选课记录：Sno + Cno 联合主码)    │
└────────────────────────────────────────┘
```
*上图展示了学生表、课程表与选课表之间的主外码参照拓扑关系。*

#### 学生关系（Student）

学生表存储学生的个人基本档案，包含五个属性列：
- 学号（`Sno` / `Snumber`）
- 姓名（`Sname`）
- 性别（`Ssex`）
- 年龄（`Sage`）
- 所在系（`Sdept`）

我们根据候选码必须满足“非空且唯一”的条件来审视各列：
- 性别、年龄、所在系存在大量重复值，无法唯一标识一行记录，绝不能作为候选码；
- 姓名在当前示例中虽然没有重名，但从长远维护和业务拓展的角度来看，重名不可避免；
- 学号具有严格的全局唯一性且非空。

因此，`Sno` 和 `Sname` 都是候选码（对应属性为主属性），但我们必须毫不犹豫地选择**学号（Sno）**作为关系的主码（Primary Key）。

#### 课程关系（Course）

课程表维护学院开设的全部课程及先修依赖关系，包含四个属性列：
- 课程号（`Cno`）
- 课程名（`Cname`）
- 先行课号（`Cpno`）
- 学分（`Ccredit`）

其中先行课反映课程学习的依赖链条。例如数据库课程依赖先修课数据结构，数据结构依赖 Pascal 语言，Pascal 语言依赖数据处理基础，而基础课没有先行课（其 `Cpno` 允许为空值 null）。学分通常由每周课时折算而来（如 4 课时计 4 学分）。

在候选码判定上：`Cpno` 存在重复和空值，`Ccredit` 存在大量重复，均不可行；`Cno` 与 `Cname` 均可作为候选码。但主码同样应当坚决指定为**课程号（Cno）**。因为同一门课（如“数据库”）面对不同专业或教学班开设时，课程名称完全可能重复，教务系统必须依赖独一无二的课程编号来建立全局唯一索引。

#### 选课关系（SC）

选课表（Student Course，SC）在业务上相当于学生成绩单，用于在学生表和课程表之间建立多对多联系，包含三个属性列：
- 学号（`Sno`）
- 课程号（`Cno`）
- 成绩（`Grade`）

在选课表中，单一属性列无法充当主码：一个学生可选修多门课程（`Sno` 重复），一门课程也会被多名学生选修（`Cno` 重复）。因此，必须将 **（Sno, Cno）** 这两个属性组合在一起构成**复合主码（联合主码）**。同时，`Sno` 参照学生表的主码，`Cno` 参照课程表的主码，两者共同充当外码（Foreign Key），将孤立的学生数据与课程数据严密连接。

### 专门关系运算的核心执行机制

专门的关系运算符直击关系数据库的核心业务查询需求。本节深入剖析选择、投影与连接三种核心运算的运行机理。

#### 选择运算（Selection）

选择运算又称为限制（Restriction），用希腊字母 $\sigma$ 表示。

> **定义**：选择运算是在给定的关系 $R$ 中，选取满足逻辑条件的全部元组（行）。
> $$\sigma_F(R) = \{ t \in R \mid F(t) = \text{true} \}$$

其中 $F$ 为逻辑选择条件，它由属性名、比较运算符（$>$, $<$, $=$, $
eq$, $\le$, $\ge$）以及逻辑运算符（与、或、非）组成。

选择运算的核心机理是**水平方向上的行过滤**。它对原始关系的属性列结构不作任何变动，表头完全保留，只提取那些计算结果为真的行记录。运算结果依然是一张完整的二维表。

```text
原始表:  ┌────────┐
        ├────────┤ ─── 不符合条件 (丢弃)
        ├────────┤ ─── 符合条件 F=true (保留) ───┐
        ├────────┤ ─── 不符合条件 (丢弃)         │ 提取出满足条件的行
        ├────────┤ ─── 符合条件 F=true (保留) ───┼──> 结果表 (列结构不变)
        ├────────┤ ─── 符合条件 F=true (保留) ───┘
        └────────┘
```
*上图展示了选择运算针对行记录进行水平筛选的过程。*

##### 示例 1：查询信息系的全体学生

在业务上，这个查询条件需要作用于学生表（Student），筛选所在系等于信息系（IS）的记录。用关系代数表达为：

$$\sigma_{\text{Sdept} = \text{'IS'}}(\text{Student})$$

> **提示**：在选择条件中，常量字符串必须用单引号包裹（如 `'IS'`），以区别于系统变量或属性名。

执行时，数据库遍历 Student 表的每一行，凡是 `Sdept` 属性值为 `'IS'` 的元组全部被提取出来输出。即使最终只有一条记录匹配，其输出形式依然是一张标准的二维表。

##### 示例 2：查询年龄小于 20 岁的学生

该查询在学生表上针对年龄属性施加不等式限制：

$$\sigma_{\text{Sage} < 20}(\text{Student})$$

系统沿行扫描，提取所有满足 `Sage < 20` 的元组，原样输出所有字段。

#### 投影运算（Projection）

投影运算用希腊字母 $\pi$ 表示。它的英文名称是 Projection，可以形象地类比为教室里的投影仪（projector）——将原本庞大的内容中我们真正关注的部分“投射”出来。

> **定义**：投影运算是从关系 $R$ 中选择出指定的若干属性列组成新的关系。
> $$\pi_A(R) = \{ t[A] \mid t \in R \}$$

选择是针对“行”的横向切分，而投影是针对“列”的纵向截取。当一张数据表包含了大量敏感或无关字段时，我们通过投影只暴露需要展示的列。例如，面向财务人员查询时，只需把学生财务相关列投影出去；面向教务人员时，只投影选课与教学相关的列。

> **结论**：投影运算在截取指定属性列之后，**会自动执行去重操作**，消除因丢弃关键区分列而产生的完全重复行。

```text
原始表属性:  [ 列1 | 列2 | 列3 | 列4 | 列5 ]
                    │          │
                    ▼          ▼
投影目标:          [ 列2 | 列4 ] ──> 提取并自动去重 ──> 结果表 (列数减少)
```
*上图展示了投影运算针对属性列进行垂直截取与去重的过程。*

##### 示例 1：查询全体学生的姓名和所在系

我们只需要查阅 `Sname` 与 `Sdept` 两个字段，其余如学号、性别、年龄等均无需呈现：

$$\pi_{\text{Sname, Sdept}}(\text{Student})$$

运算结果仅保留姓名与系别两列，其他三列在视图中被剥离。

##### 示例 2：查询学校目前设立了哪些系

如果直接在 Student 表中查看系别，写成：

$$\pi_{\text{Sdept}}(\text{Student})$$

其运算结果只包含 `Sdept` 这一列。由于原表中会有多个学生属于同一个系，投影操作在抽取出该列后，会自动压缩相同的系名，最终给出一个没有重复项的院系列表。

#### 连接运算（Join）

连接运算是关系数据库中最具威力、也是逻辑上相对复杂的操作，用连接符号 $\bowtie$ 表示。

> **定义**：连接运算是从两个关系的笛卡尔积中，选取在指定属性列上满足特定比较条件的元组，组合成一个新关系。
> $$R \underset{A \theta B}{\bowtie} S = \{ \overset{\frown}{t_r t_s} \mid t_r \in R \land t_s \in S \land t_r[A] \ \theta\  t_s[B] \}$$

其中 $A$ 和 $B$ 分别为 $R$ 和 $S$ 上度数相等且可比的属性组，$\theta$ 为比较运算符。

##### 连接的底层两步执行法

理解连接运算的关键，在于掌握它的逻辑二步推导：
1. **第一步：做广义笛卡尔积**：首先将关系 $R$ 与关系 $S$ 进行完全组合，生成一个行数为两表之积、列数为两表之和的巨大中间表；
2. **第二步：按条件执行筛选**：以连接条件 $A\ \theta\ B$ 为准绳，对这个笛卡尔积大表进行逐行校验，凡不满足条件的组合行全部予以剔除，保留的行构成最终结果。

假设表 $R(A, B, C)$ 包含 3 列 4 行，表 $S(B, E)$ 包含 2 列 5 行。现在要求两表做连接，筛选条件为 $C < E$：
1. 第一步执行笛卡尔积：生成的新表列数为 $3 + 2 = 5$ 列，行数为 $4 \times 5 = 20$ 行；
2. 第二步带入条件 $C < E$ 进行筛选：遍历这 20 行组合，如果某一行中 $C$ 的分量确实小于 $E$ 的分量，则保留；否则从结果集中删除。最终可能仅有少数几行满足要求，其余行全部舍弃。

##### 等值连接（Equi-Join）

当连接条件中的比较符 $\theta$ 专门取为等号（$=$）时，这种运算被称为等值连接。其含义是只保留两表在对应属性列上取值完全相等的那些组合。

例如条件指定为 $R.B = S.B$，则意味着在生成的 20 行笛卡尔积结果中，只筛选出 $R$ 表中的 $B$ 列取值与 $S$ 表中的 $B$ 列取值精确相等的所有元组。

##### 自然连接（Natural Join）

自然连接是一种特殊的等值连接，它省去了人工指定连接条件的繁琐步骤。

> **定义**：两个关系在所有同名公共属性列上执行等值比较，并在最终结果中剔除多余的重复属性列，这种连接称为自然连接，记为 $R \bowtie S$。

自然连接完整的执行流程包含清晰的“三步走”：
1. **第一步：做广义笛卡尔积**；
2. **第二步：同名属性等值筛选**；
3. **第三步：消除重复列**（完全相同的同名属性列只保留一列）。

为什么这种连接方式被称为“自然”？因为它完全契合人类在现实业务中的自然直觉。

以学生表（Student）和选课表（SC）为例：学生表里有学生信息，选课表里有学生的选课成绩。如果只做笛卡尔积，系统会把“1 号学生张三”与“2 号学生李四的选课成绩”强行拼凑在一起，这种拼接在现实世界中没有任何业务意义。人类在心智模型中天然想要看到的结果，必然是“1 号学生张三与其本人的选课成绩”精准配对，并且结果表中没必要保留两列一模一样的学号。

自然连接通过上述三步，自动帮我们完成了业务上的语义对齐并清除了结构冗余。

```text
R 表 ──┐
      ├─> [第 1 步] 广义笛卡尔积 ─> [第 2 步] 同名属性等值筛选 ─> [第 3 步] 去除重复列 ─> 自然连接结果
S 表 ──┘
```
*上图展示了自然连接从笛卡尔积到最终结果的三步核心推导机制。*

在今后的关系代数实际书写中，当需要对存在公共业务键的两个关系进行合理关联时，我们可以直接使用自然连接符号 $\bowtie$。这一个简洁的符号背后，已经内蕴并自动执行了“笛卡尔积 $\to$ 等值筛选 $\to$ 去除重复列”这三层完整的代数逻辑。

在多表关联时，如果我们把两个表的公共属性列横向对比，值相等时留下、不相等时删掉，留下的便全是匹配的记录，这就是等值连接。如果把两列完全一样的重复属性再去掉一列，就变成了自然连接。但在这种常规连接中，隐藏着一个长期被忽视的边界问题：当某些记录在对方表里根本找不到相匹配的值时，它们会在筛选过程中被静默抹杀。这种因“无从匹配”而被舍弃的数据，究竟该如何保留？当查询需求中出现“选修了所有课程”这类全称量词时，我们又该如何用纯代数符号向数据库表达？本讲我们将彻底攻克悬浮元组、外连接、关系除法，并建立一套将人类自然语言精准翻译为关系代数表达式的系统方法论。

### 连接运算的特例与悬浮元组处理

#### 等值连接与自然连接的执行机理

常规的连接运算在本质上分为两步：第一步做笛卡尔积，第二步按照指定的连接条件进行元组筛选。在连接条件中，最典型也是最常见的一种情况就是要求特定属性值相等，这被称为等值连接（Equi-Join）。例如左表与右表通过学号列进行对齐，只有学号完全一致的元组才会被拼接保留，其余毫无对应关系的组合会被全部剔除。

在等值连接的基础上，往往还会产生属性冗余。既然两张表的连接列是基于相等条件匹配出来的，那么最终结果集中必然包含两列数值完全一致的属性。此时多走一步——将其中一列重复的属性列剔除，这种操作就是自然连接（Natural Join）。

因此，从逻辑执行链条来看，自然连接实际上是“三步走”：
1. **第一步**：对两个关系做笛卡尔积，穷举所有元组组合；
2. **第二步**：以两表同名属性值相等为筛选条件，剔除不匹配的行；
3. **第三步**：在投影层面去除重复的同名属性列。

> **定义**：自然连接记作 $R \bowtie S$。它不需要额外书写任何条件表达式，默认基于两表的同名公共属性进行等值比对，并在结果中自动去重同名列。在业务建模中，只要两个实体表之间存在天然的外键或公共编码关联，直接使用自然连接往往就是最符合直觉的关联结果。

#### 悬浮元组的产生与业务信息丢失

当我们在两个关系之间做自然连接时，必须注意一种极为特殊但广泛存在的业务边界：左表中的某些元组，在右表中可能根本找不到公共属性值相等的对应元组；或者反过来，右表中的某些元组在左表中也找不到对应项。

按照自然连接的严格规则，由于它们无法满足等值匹配条件，这部分元组会在筛选阶段被全部丢弃。这些在连接过程中被舍弃的元组，被称为悬浮元组（Dangling Tuple）。

```text
关系 R (学生)               关系 S (选课)
+-------+------+          +------+--------+
| Sno   | Sname|          | Sno  | Cno    |
+-------+------+          +------+--------+
| 1     | 张三 |          | 1    | C1     |
| 2     | 李四 |          | 2    | C2     |
| 3     | 王五 |          | 3    | C3     |
| 4     | 赵六 |          +------+--------+
+-------+------+
    |
    v 4号赵六在右表无选课记录
[ 自然连接 R ⋈ S ]
+-------+------+--------+
| Sno   | Sname| Cno    |
+-------+------+--------+
| 1     | 张三 | C1     |
| 2     | 李四 | C2     |
| 3     | 王五 | C3     |
+-------+------+--------+
（4号学生记录被直接舍弃，成为悬浮元组）
```

上述图示展示了悬浮元组在自然连接中的丢失过程：4号赵六并非因为“信息错误”被剔除，而是因为在右表中根本没有与之匹配的数据项。

这种舍弃机制在很多业务场景下会导致严重的管理信息丢失：
- **班主任视角**：左表是班级学生名单（包含1、2、3、4号），右表是选课系统记录。4号同学可能因为错过了选课时间或者选课系统故障，一门课都没有选上。如果直接做自然连接，4号同学的记录彻底消失。作为班主任查看这张表，根本察觉不到“有同学漏选课程”，新学期开学该同学将面临无课可上的事故。
- **教务处视角**：右表是学校本学期开设的课程（包含开设的5号课），但全校没有一个学生选修这门课。做自然连接时，5号课程记录同样会被全部舍弃。教务处老师因此无法查出“哪些课程开出来却无人问津”，难以及时停开或调整课表。

> **结论**：悬浮元组不是脏数据，它所体现的“无匹配”本身就是一种极具价值的业务事实。为了完整反映实体状态，必须引入能够在连接结果中保留悬浮元组的运算——外连接。

#### 外连接运算及其变体

外连接（Outer Join）的核心逻辑是：将悬浮元组强制保留在连接结果中；对于对方表中缺失的属性列，统一使用空值（NULL）进行占位填充。

根据保留悬浮元组的来源不同，外连接划分为三种形式：
1. **左外连接（Left Outer Join）**：记作 $R \mathbin{⟕} S$。在保留自然连接结果的基础上，完整保留左侧关系 $R$ 中的所有悬浮元组。右侧关系 $S$ 对应的属性位置全部以空值填充。此形式完美对应“班主任视角”：全班每一个学生都必须列出，没选上课的学生其课程属性为空，以便班主任一目了然。
2. **右外连接（Right Outer Join）**：记作 $R \mathbin{⟖} S$。在保留自然连接结果的基础上，完整保留右侧关系 $S$ 中的所有悬浮元组。左侧关系 $R$ 对应的属性位置全部以空值填充。此形式对应“教务处视角”：排出的所有课程全量展示，无人选修的课程其学生属性为空，便于课程资源审计。
3. **全外连接（Full Outer Join / Outer Join）**：记作 $R \mathbin{⟗} S$（或简写为外连接）。两边关系中的悬浮元组全部保留，任何一方没有匹配项的列均以空值填充。

### 关系代数中的除法运算

#### 官方形式化定义的痛点

在八大关系代数运算符中，除法（Division，记作 $\div$）是概念最抽象、最容易引发困惑的一个。经典教材与形式化理论通常将其表述为：元组在某一属性组分量上的象集是否包含除数关系在相应属性上的投影集合。这类高度形式化的数学定义往往阻断了学习者的直观理解。

为了彻底掌握除法，我们必须跳出晦涩的形式化文字，回到表与表运算的基本骨架以及数学除法的本源中去。

#### 除法的双重数学本质：消列与包含

任何关系代数运算的结果依然是一张表。认识一张表只需要抓住两个基本维度：**列（属性）是谁**？**行（元组）是谁**？

我们可以从基础数学的算式 $12 \div 3 = 4$ 中提炼出除法的两层核心物理含义，并完全对应到关系数据库中：
1. **第一层含义：消除相同的因数（确定结果的列）**。
   算式 $12 \div 3 = 4$ 可以写成 $(3 \times 4) \div 3 = 4$，除法在结构上抵消掉了共同的因子 $3$。
   在关系代数中，这一层含义专门用来**确定结果表的属性列**。
   设被除数关系为 $R$，除数关系为 $S$：
   - 找出 $R$ 与 $S$ 共同拥有的公共属性组；
   - 在被除数 $R$ 中直接将这些相同的属性列“除掉”（扣除）；
   - $R$ 中扣除公共列后剩下的属性列，就是 $R \div S$ 的结果属性列。
   - 需要特别注意的是：除数 $S$ 中独有的非公共属性列根本不需要理会，不影响商的列结构。如果颠倒过来做 $S \div R$，则是从 $S$ 中扣除公共列，剩下 $S$ 独有的属性列。
2. **第二层含义：包含关系（确定结果的行）**。
   算式 $12 \div 3 = 4$ 在现实中意味着 12 个苹果分给 3 个小朋友，每人分得 4 个；其抽象数学意义则是“12 里面完整包含了 4 个 3”。
   在关系代数中，这一层含义专门用来**确定结果表的行元组**。
   结果表的每一行，必须在自身的取值下，完全包含除数表所指定的整体集合。

#### 基于象集的除运算求解过程

行数据的具体筛选依赖于关系代数中“象集（Image Set）”的概念。求解 $R \div S$ 的标准操作步骤如下：

```text
步骤 1：分析属性列
被除数 R 属性：(A, B, C)
除数 S 属性：(B, C, D)
公共属性：(B, C)
==> 商的属性列为：A

步骤 2：提取被除数独有列的候选值
扫描 R 表中的 A 列，得到所有候选值：{a1, a2, a3, a4}

步骤 3：求解各候选值在公共属性 (B, C) 上的象集
a1 对应的 (B, C) 组合集合：{(b1, c2), (b2, c1), (b2, c3)}
a2 对应的 (B, C) 组合集合：{(b3, c7), (b2, c3)}
a3 对应的 (B, C) 组合集合：{(b4, c6)}
a4 对应的 (B, C) 组合集合：{(b6, c6)}

步骤 4：比对包含关系
提取除数 S 在 (B, C) 上的元组集合：{(b1, c2), (b2, c1), (b2, c3)}
比对上述各象集，谁能够完全覆盖、包含除数 S：
- a1 的象集完全包含了 S 的要求（甚至相等） ==> 满足条件，入选！
- a2、a3、a4 均无法完全覆盖 S ==> 舍弃！

步骤 5：输出商关系
结果表为单列 A，元组仅有：{a1}
```

上述流程揭示了除法的运行机制：通过公共列将除数与被除数关联，以独有列分组，检查各组在公共列上的映射是否成为除数的全覆盖超集。

#### 除法在业务查询中的“包含”语义

除法在实际业务查询中有何用途？答案只有两个字：**包含**。

在将人类日常业务指令向数据库转译的过程中，只要需求中反映出了全称覆盖或集合包含的特征——例如“至少选修了某几门课”、“购买了某类别的所有商品”、“掌握了清单里的全部技能”——我们在下意识中必须立刻联想到关系除法。

例如业务需求：“查询至少选修了 1 号课和 3 号课的学生学号”。
对这句话进行深层转译：哪一个学生的个人选课记录，**包含**了课程集合 $\{1, 3\}$？
- 如果学生的选课集合是 $\{1, 2, 3\}$，完全包含了 $\{1, 3\}$，合格；
- 如果学生的选课集合是 $\{1, 3, 4\}$，同样合格；
- 但如果学生仅选了 $\{1\}$，或仅选了 $\{3\}$，或两者均未选，则不满足包含条件。

由此，我们可以清晰地构造除法要素：
1. **构造除数**：临时构造一个单列关系，属性为课程号 `Cno`，包含两个元组 $\{1, 3\}$；
2. **构造被除数**：选课表 `SC` 包含 `(Sno, Cno, Grade)` 三列。如果直接用 `SC` 做除法，消去 `Cno` 后将残留 `Grade` 列，且同一个学生不同成绩会破坏象集聚合。因此必须先在 `SC` 上对 `(Sno, Cno)` 两列进行投影，剔除无关的成绩列；
3. **执行除法**：
   $$\pi_{\text{Sno}, \text{Cno}}(\text{SC}) \div \{ (1), (3) \}$$
   被除数属性为 `(Sno, Cno)`，除数属性为 `(Cno)`，相除后消除 `Cno`，剩下的属性列正是我们想要的学号 `Sno`；在行数据层面，只有选课记录同时覆盖了 1 号与 3 号课的学生，才能作为商被输出。

### 关系代数表达式的求解方法论

#### 关系代数作为数据库底层的逻辑基础

在数据库体系中，关系模型包含关系数据结构、关系完整性约束以及关系代数运算。前文总结的八大代数运算符——并（$\cup$）、交（$\cap$）、差（$-$）、笛卡尔积（$\times$）、选择（$\sigma$）、投影（$\pi$）、连接（$\bowtie$）、除（$\div$）——就如同初中数学里的加减乘除运算符。

学完数字与运算规则后，必须进入应用题的综合求解阶段。人类向数据库表达的查询意图使用的是自然语言（中文或英文），但数据库引擎底层完全不理解自然语言，它赖以解析执行的数学根基就是关系代数。把人类意图翻译为关系代数表达式，是数据库执行逻辑优化的前提。

#### 输入输出分析法

为了将复杂的自然语言需求稳定、机械化地转化为关系代数表达式，我们必须建立一套标准化的思维工具——**输入输出分析法**。

这里的“输入”与“输出”是立足于**数据库内核处理引擎**的视角，而非指终端用户的键盘录入或屏幕显示：
- **输入条件（Input Criteria）**：用户给数据库设立的筛选门槛与过滤限制。这一部分在代数运算中由**选择运算符（$\sigma$）**承载；
- **输出字段（Output Attributes）**：用户最终期望在结果集中调阅的属性列。这一部分在代数运算中由**投影运算符（$\pi$）**承载；
- **分析定位（Relation Analysis）**：审查输入条件涉及的属性以及输出期望的属性，分别落在数据库的哪一张表或哪几张表中：
  - 如果所有字段全部存在于单张表内，直接在该表上执行单表操作；
  - 如果字段分散在多张不同的表内，必须找出它们之间的关联纽带，利用自然连接（$\bowtie$）将这些表缝合在一起。

由此可提炼出关系代数表达式的基础构造模板：
$$\pi_{\text{输出属性}}(\sigma_{\text{输入条件}}(\text{涉及表1} \bowtie \text{涉及表2} \bowtie \dots))$$

### 综合查询实战与代数优化

#### 单表查询与操作次序

以具体案例检验输入输出分析法：
**需求**：查询选修了 2 号课程的学生学号。

1. **提取输入**：限定课程为 2 号课，对应条件字段 $Cno = 2$；
2. **提取输出**：需要展示的内容为学号，对应字段 $Sno$；
3. **分析表源**：
   - 查看学生表 `Student`：拥有 $Sno$，但缺乏 $Cno$；
   - 查看课程表 `Course`：拥有 $Cno$，但缺乏 $Sno$；
   - 查看选课表 `SC`：同时完整具备 $Sno$ 和 $Cno$。
4. **构造表达式**：
   字段全部收敛在 `SC` 单表中，完全不需要跨表连接。从内向外构建：先依据输入条件横向筛选行，再依据输出要求纵向投影列。
   $$\pi_{\text{Sno}}(\sigma_{\text{Cno}='2'}(\text{SC}))$$

> **提示**：先做行选择、后做列投影，在逻辑中间环节产出的每一步依然是合法的关系表。先选后投符合从过滤到收缩的自然数据流。

#### 多表连接与跨表路径查找

进一步处理跨表复杂关联：
**需求**：查询至少选修了一门其直接先行课为 5 号课程的学生姓名。

1. **提取输入**：直接先行课编号为 5，对应属性条件为 $Cpno = 5$；
2. **提取输出**：需要最终呈现学生姓名，对应字段为 $Sname$；
3. **分析表源**：
   - 直接先行课属性 $Cpno$ 属于课程表 `Course`；
   - 学生姓名属性 $Sname$ 属于学生表 `Student`；
   - 检查两表公共属性：`Student` 存放学号、姓名、院系等信息；`Course` 存放课程号、课名、学分等信息，两表之间没有任何同名公共属性，彼此无法直接建立自然连接！
   - 必须寻找“桥梁表”：选课表 `SC` 同时包含学号 $Sno$ 与课程号 $Cno$。`SC` 分别与 `Student`（通过 $Sno$）和 `Course`（通过 $Cno$）存在外键关联，由此构成桥梁，完成三表串联。

#### 全局连接与分步投影的性能优化

针对上述跨表查询，存在两种截然不同的代数书写策略与执行逻辑：

**解法一：全局大连接模式**
将涉及的三个表直接用自然连接符号拼合，外层包裹统一的选择与投影：
$$\pi_{\text{Sname}}(\sigma_{\text{Cpno}='5'}(\text{Student} \bowtie \text{SC} \bowtie \text{Course}))$$
这种写法在逻辑上清晰、思维负担低，但在系统底层执行时性能较为低下。三张大表在做笛卡尔积与连接匹配时，会产生规模庞大的中间结果集并占用巨额内存缓存。特别是 `Student` 表中的年龄、性别、系别等属性，以及 `Course` 中的学分等冗余字段，全程参与了连接却与最终解毫无关联。

为了减轻系统开销，我们可以在代数层面做初步的降维优化：在连接之前，先将参与连接的表分别投影，仅保留关联键与目标字段，将无关属性提前过滤掉：
$$\pi_{\text{Sname}}(\sigma_{\text{Cpno}='5'}(\pi_{\text{Sno}, \text{Sname}}(\text{Student}) \bowtie \text{SC} \bowtie \pi_{\text{Cno}, \text{Cpno}}(\text{Course})))$$

**解法二：逐步递推优化模式**
站在精细化执行管线的角度，按数据依赖路径分步推进：
1. 先在 `Course` 表中利用 $Cpno = 5$ 过滤，快速找出直接先行课为 5 的那些课程编号；
2. 拿着这组精简的课程编号与 `SC` 表连接，仅找出选修了这几门特定课程的学生学号；
3. 拿着这组学号与 `Student` 表连接，取出对应的学生姓名。

```text
管线推导流向：
[Course 表 (Cpno=5)] ==> 过滤得到目标 Cno
                             |
                             v
                       [与 SC 表连接] ==> 得到目标 Sno
                                              |
                                              v
                                       [与 Student 连接] ==> 投影输出 Sname
```

> **结论**：逐步递推写法在系统执行效率上显著高于先大连接再过滤的写法，因为它从源头最大限度压缩了参与后续连接的数据量。但在面对考试或快速建模时，全局连接模板具备通用、容错率高的优势。

#### 包含全称量词的除法综合查询

**需求**：查询选修了全部课程的学生学号和姓名。

面对这个题目，如果试图用常规的选择条件（例如令课程数等于某常数），会发现“选修了全部课程”根本无法用单一的代数比较符直接写在 $\sigma$ 的下标里。

此时必须进行语义转换：寻找哪个学生的选课历史，**完全包含**了教务处排出的所有课程。一触发“包含”，代数解法的核心必然落在**除法（$\div$）**上。

1. **构造除数**：
   全校所开设的“全部课程”存放于教务处的 `Course` 表中。我们对该表投影出全部课程号列：
   $$\text{除数} = \pi_{\text{Cno}}(\text{Course})$$
   假设全校共开设 7 门课程，该除数就是包含 1 到 7 号课的单列集合。
2. **构造被除数**：
   在选课记录 `SC` 表中提取学生与课程的关联对，屏蔽与除法无关的成绩列：
   $$\text{被除数} = \pi_{\text{Sno}, \text{Cno}}(\text{SC})$$
3. **除法求商（锁定符合条件的学生学号）**：
   将两者相除：
   $$\text{商} = \pi_{\text{Sno}, \text{Cno}}(\text{SC}) \div \pi_{\text{Cno}}(\text{Course})$$
   公共列 `Cno` 被完全消去，商关系只保留单列 `Sno`。从象集定义可知，只有选课记录完全覆盖了 7 门课程全部元组的学生，其学号才会被保留在商关系中。
4. **回表连接（获取姓名输出）**：
   题目要求输出“学号和姓名”。上述商关系仅得到了学号，因此必须将该商关系作为一个整体，与学生表 `Student` 进行一次自然连接，最终投影出学号与姓名：
   $$\pi_{\text{Sno}, \text{Sname}}((\pi_{\text{Sno}, \text{Cno}}(\text{SC}) \div \pi_{\text{Cno}}(\text{Course})) \bowtie \text{Student})$$

### 本讲提到的题目

#### 题目一：查询选修了 2 号课程的学生学号

**题干**：
已知学生选课数据库包含 `Student(Sno, Sname, Ssex, Sage, Sdept)`、`Course(Cno, Cname, Cpno, Ccredit)`、`SC(Sno, Cno, Grade)` 三个关系。请写出“查询选修了 2 号课程的学生学号”的关系代数表达式。

**解析**：
- 输入条件为选修课程编号 $Cno = 2$；输出要求为学号 $Sno$。
- 检索数据模式可知，`SC` 关系同时具备 $Sno$ 与 $Cno$ 两属性，无需跨表连接。
- 在 `SC` 上对行执行选择条件 $Cno = '2'$，再对列执行投影保留 $Sno$。

**答案**：
$$\pi_{\text{Sno}}(\sigma_{\text{Cno}='2'}(\text{SC}))$$

---

#### 题目二：查询至少选修了一门其直接先行课为 5 号课程的学生姓名

**题干**：
依据上述数据库模式，试编写关系代数表达式，查询至少选修了一门直接先行课（$Cpno$）为 5 号课程的学生姓名（$Sname$）。

**解析**：
- 输入限定条件为 $Cpno = '5'$，位于 `Course` 表；输出字段为学生姓名 $Sname$，位于 `Student` 表。
- `Student` 与 `Course` 无公共属性，必须引入中间关系 `SC` 充当关联桥梁（`Student` 通过 $Sno$ 与 `SC` 关联，`SC` 通过 $Cno$ 与 `Course` 关联）。
- 将三个表做自然连接后实施行选择与列投影；亦可先过滤 `Course` 再做级联连接以优化性能。

**答案**：
常规写法：
$$\pi_{\text{Sname}}(\sigma_{\text{Cpno}='5'}(\text{Student} \bowtie \text{SC} \bowtie \text{Course}))$$
优化写法：
$$\pi_{\text{Sname}}(\pi_{\text{Sno}, \text{Sname}}(\text{Student}) \bowtie \text{SC} \bowtie \sigma_{\text{Cpno}='5'}(\pi_{\text{Cno}, \text{Cpno}}(\text{Course})))$$

---

#### 题目三：查询选修了全部课程的学生学号和姓名

**题干**：
依据上述数据库模式，试编写关系代数表达式，查询选修了当前数据库中开设的全部课程的学生学号与姓名。

**解析**：
- “选修了全部课程”属于全称覆盖语义，普通选择运算符 $\sigma$ 无法表达，必须采用关系除法 $\div$。
- 除数构造为全校所有开设课程的集合：$\pi_{\text{Cno}}(\text{Course})$。
- 被除数构造为各学生的选课清单：$\pi_{\text{Sno}, \text{Cno}}(\text{SC})$。
- 两者相除得到选全所有课程的学生学号集合。为补充输出姓名属性，将该结果与 `Student` 表按 $Sno$ 做自然连接，最终投影输出学号与姓名。

**答案**：
$$\pi_{\text{Sno}, \text{Sname}}((\pi_{\text{Sno}, \text{Cno}}(\text{SC}) \div \pi_{\text{Cno}}(\text{Course})) \bowtie \text{Student})$$
