# 数据库编程：嵌入式 SQL、过程化 SQL 与 ODBC

## 数据库编程路线与职责边界

* **数据库编程能力分工**

    * > **定义**：数据库应用需要同时解决过程控制、集合式数据处理、服务器端逻辑复用和异构数据库访问，而 SQL 单独只擅长其中的数据处理。

    * 主语言 C、C++、Java 擅长输入、判断、循环和逐行处理，却不擅长一次取得并处理大规模数据集；SQL 擅长按条件查、改、增、删整个集合，却不擅长把过程控制写细。

    * 嵌入式 SQL 把 SQL 接入已有应用程序，让主语言负责流程、SQL 负责集合操作。

    * 过程化 SQL 在数据操作之外提供变量、块、条件、循环和错误处理，使 SQL 能拼出简单的处理过程。

    * 存储过程和函数把写好的过程化 SQL 预封装到数据库服务器，供应用程序通过参数反复调用。

    * ODBC 通过共同接口访问不同关系数据库管理系统；OLE DB、JDBC 同属数据库接入路线，但具体层次与调用流程：长文未说明。

## 嵌入式 SQL、主语言与通信区

* **交互式 SQL 与嵌入式 SQL**

    * > **定义**：交互式 SQL 独立接收一条数据库指令并完成要求；嵌入式 SQL 则嵌在 C、C++、Java 等主语言程序中，由主语言带着它工作。

    * SQL 的集合处理能力与主语言的过程控制能力互补，嵌入后二者在同一个程序中分工协作。

* **主语言（host language）**

    * > **定义**：包含嵌入式 SQL 的程序语言称为主语言；一段 C 程序中嵌有 SQL 时，C 就是主语言。

    * SQL 部分在主语言编译时可理解为一次函数调用，传入值并接收结果。

    * 嵌入式 SQL 语句必须带 `EXEC SQL` 前缀，以区分 SQL 语句和主语言语句。

* **通信区（SQL Communication Area，SQLCA）**

    * > **定义**：SQLCA 是 SQL 与主语言之间传递执行状态信息的通信区，不负责存放业务查询结果。

    * SQL 执行结束后，系统通过 SQLCA 向主程序报告成功、错误或其他状态，主程序据此决定是否继续、停止或处理错误。

    * `EXEC SQL INCLUDE SQLCA` 把通信区纳入程序；`SQLCODE` 是其中用于报告 SQL 执行状态的预定义值。

    * > **易错点**：`SQLCODE` 表示执行状态，不表示查询结果；查询数据交给主变量，执行状态交给通信区。

* **连接操作**

    * 建立连接时，主语言提供服务器标识，并可指定连接名和用户名；`SET CONNECTION` 切换当前连接，`DISCONNECT` 结束连接。

    * > **提示**：建立连接只形成主语言与数据库之间的通路，不等于已经完成查询；查询仍需声明游标或执行相应 SQL。

## 主变量与指示变量

* **主变量（host variable）**

    * > **定义**：主语言变量进入 SQL 区域、参与 SQL 计算或条件时称为主变量，用来输入数据或接收处理结果。

    * 主变量集中声明在 `EXEC SQL BEGIN DECLARE SECTION` 与 `EXEC SQL END DECLARE SECTION` 之间。

    * 主变量在 SQL 区域中必须写成 `:变量名`，用于同表名、视图名、列名等数据库对象区分；回到主语言语句后不再写冒号。

* **输入主变量与输出主变量**

    * 输入主变量由主语言赋值后送入 SQL，学号、课程号、部门号等查询条件通常承担这一角色。

    * 输出主变量由 SQL 赋值，把查询或处理结果带回主程序供显示、更新或继续处理。

    * 同一条 SQL 可以同时包含输入主变量和输出主变量，一头传入条件或待写数据，另一头接收结果。

* **指示变量（indicator variable）**

    * > **定义**：指示变量是与主变量配套的整型变量，用于说明对应输入或输出是否为 null，以及输出是否出现问题。

    * 写法是在主变量前加冒号并紧跟其后：`:grade :grade_id` 中，`:grade` 接值，`:grade_id` 说明该值状态。

    * 当指示变量为负值时，对应主变量即使存有数值，也应按空值理解。

    * > **易错点**：主变量负责装值，指示变量负责解释该值；不能把“变量中有数字”等同于“该值有效且非空”。

## 游标与逐行处理

* **游标（cursor）**

    * > **定义**：游标是为多行查询结果建立的结果缓冲区及指向当前记录的通道，用于解决 SQL 一次返回多行、主语言一次处理一行的矛盾。

    * 游标生命周期为“说明游标 → 打开游标 → 推进并取数 → 关闭游标”：先以 `CURSOR FOR` 绑定查询，再由 `OPEN` 执行查询并装入结果区，由 `FETCH` 一次取当前行到主变量，最后由 `CLOSE` 释放缓冲区与其他资源。

    * `FETCH` 每次只取一行，`INTO` 后接一组主变量；处理完当前行后再次 `FETCH`，直到结果取尽并关闭游标。

    * 关闭后游标不再关联原结果集；再次打开时按所声明的查询重新取得结果，不沿用上次遗留的数据。

* **游标使用判定**

    | 情况 | 是否使用游标 | 判定依据 |
    | :--- | :--- | :--- |
    | 查询只返回一条记录 | 不使用 | 一行结果可直接交给一组主变量 |
    | 条件能直接指出增删改目标 | 不使用 | 学号、课程号等条件已能定位记录 |
    | 查询返回多条记录 | 使用 | 需先缓冲整批结果，再由主语言逐行处理 |
    | `UPDATE` 或 `DELETE` 使用 `WHERE CURRENT OF` | 使用 | 目标由游标在结果集中的当前位置确定 |

    * `FETCH` 只是取出当前行供主语言查看，并不代表数据已经改回数据库；更新当前行后仍要提交，查询、更新、提交是三个动作。

    * `WHERE CURRENT OF sx` 使更新只作用于游标当前指向的行，不影响结果集中的其他行。

    * 非 CURRENT 形式用条件直接定位目标；CURRENT 形式先由游标在结果集中定位，再处理当前行，二者的区别在目标确定方式而不是有无 `WHERE`。

    * > **易错点**：游标声明中的 `SELECT` 若带 `UNION` 或 `ORDER BY`，不能使用 CURRENT 形式的 `UPDATE` 或 `DELETE`，因为该结果不能按当前行任意更新。

* **查询、更新与提交的完整收尾**

    ```sql
    EXEC SQL CLOSE sx;
    EXEC SQL COMMIT WORK;
    EXEC SQL DISCONNECT;
    ```

    * `CLOSE` 释放本次结果集占用的资源，`COMMIT WORK` 正式提交更新，`DISCONNECT` 断开数据库连接，三者依次完成结果处理、数据落库和连接收尾。

## 静态嵌入式 SQL 与动态 SQL

* **静态嵌入式 SQL**

    * > **定义**：静态嵌入式 SQL 在编写主程序时已经确定具体语句，程序运行后不再临时改变 SQL 结构或数据。

    * 适合查询目标、修改目标和处理流程在开发阶段已经明确的常规需求。

* **动态 SQL（dynamic SQL）**

    * > **定义**：动态 SQL 允许程序在运行过程中临时组装并执行 SQL，变化既可以发生在 SQL 语句本身，也可以发生在动态参数值上。

    * SQL 语句主变量装的是一条 SQL 语句而非普通业务数据；`EXECUTE IMMEDIATE :stmt` 立即执行变量中当前保存的语句。

    * 动态参数用问号预先占位：先用 `PREPARE mystatement FROM :stmt` 准备语句，再用 `EXECUTE mystatement USING 值` 在执行时绑定参数并传入实际数据。

    * 同一准备语句可反复执行并绑定不同参数，实现语句结构与输入值分离。

    * > **易错点**：动态 SQL 不是运行时任意拼接；应先准备语句结构，再在执行时通过主变量和参数占位完成绑定，区分“准备语句”与“送入参数”的时刻。

## 过程化 SQL 的块与作用域

* **过程化 SQL（procedural SQL）**

    * > **定义**：过程化 SQL 在 SQL 的数据操作之外加入变量、流程控制和错误处理，以多个简单块拼成初步的处理过程。

    * SQL 的“高度非过程化”指用户通常只描述要做什么，不规定数据库内部怎样执行；过程化 SQL 则补充“先做什么、后做什么、何时继续、出错怎么办”的初步过程描述，二者并不矛盾。

* **块结构与作用域**

    * 标准块依次包含声明区、执行区和可选的异常处理区：先用 `DECLARE` 定义变量、常量和游标，再用 `BEGIN` 执行语句，必要时用 `EXCEPTION` 处理异常，最后以 `END` 结束。

    * 先定义、后执行；变量、常量和游标只在所属块内有效，块结束后不能继续访问其局部定义。

* **变量、常量与游标声明**

    * 变量要说明名称、数据类型、可空性或初始值表达式。

    * 常量要通过常量表达式赋值，在其作用域内保持不变；尝试修改常量会产生异常。

    * 游标与变量、常量一样在声明区定义，并受块边界约束。

    * 过程化 SQL 的 `: =` 形式用于给变量赋值，前面是被赋值变量，后面是待赋的值；它不同于嵌入式 SQL 中主变量名前的单独冒号，后者表示值来自主程序。

## 条件、循环与错误处理

* **条件控制**

    * `IF condition THEN statement_sequence END IF` 在条件满足时顺序执行语句。

    * `IF condition THEN ... ELSE ... END IF` 分别提供条件成立与不成立时的两条执行路径。

    * `THEN` 或 `ELSE` 内可以继续嵌套 `IF`，先完成当前处理，再在当前路径中判断下一条件。

* **循环控制**

    * 简单 `LOOP` 反复执行循环体，必须通过 `EXIT`、`break` 或 `LEAVE` 一类出口结束，否则会无限循环。

    * `while-loop` 在每次执行循环体前先判断条件，条件为真时执行，为假时退出，条件负责决定是否继续。

    * `for-loop` 通过计数或绑定值安排重复次数与顺序，形式中可使用 `REVERSE`，也可不使用。

    * 简单循环适合按固定流程重复，条件循环适合由条件决定是否继续，计数循环适合按次数或绑定值安排处理对象。

* **异常处理**

    * `EXCEPTION` 区域处理执行过程中出现的异常，可选择停止执行、记录日志或采取其他补救措施。

    * “余额不够”等正常业务条件应使用 `IF` 判断；`EXCEPTION` 只处理执行问题，不能代替业务条件。

    * > **易错点**：业务条件不满足不等于程序执行失败；把二者写进同一种判断会掩盖真正的执行异常。

## 命名块、存储过程与函数

* **匿名块与命名块**

    * > **定义**：匿名块每次执行时重新编译，不能保存在数据库中，也不能被其他过程化 SQL 调用，适合只执行一次的临时步骤。

    * 命名块编译后保存在数据库中，可反复调用且运行较快；过程、存储过程和函数都属于命名块。

    * 是否封装为命名块取决于功能是否需要重复使用：转账、选课、工资计算等高频逻辑适合命名块，一次性步骤可用匿名块。

* **存储过程（stored procedure）**

    * > **定义**：存储过程是用过程化 SQL 编写、编译优化后存放在数据库服务器中的可调用模块，可以没有返回值。

    * `CREATE OR REPLACE PROCEDURE 过程名(参数列表) AS 过程化 SQL 块;` 负责创建或替换过程；执行可用 `CALL` 或相应执行形式，修改可重命名，删除使用 `DROP PROCEDURE 过程名`。

    * 参数用于把外部数据送入过程，可包含输入参数、输出参数或两者；调用时必须明确提供相应类型的数据。

    * 存储过程属于三层服务器架构中的数据库服务器层，应用程序只需传入参数调用，不必重复传送大段实现。

    * 存储过程的收益是提高执行效率、减少客户机与服务器之间的通信量、便于集中实施企业规则。

* **函数（function）**

    * > **定义**：函数是同样由过程化 SQL 编写并持久保存在服务器中的命名块，但必须指定返回类型并把结果交回调用者。

    * `CREATE OR REPLACE FUNCTION 函数名(参数列表) RETURNS return_type AS 过程化 SQL 块;` 在存储过程结构上增加明确的返回值出口。

    * 函数可用 `CALL` 或 `SELECT` 执行；修改时可以重命名或重新编译，管理动作与存储过程相似。

* **返回值分界**

    * 存储过程处理完成即可结束，不强制返回结果；函数必须在处理后交回一个结果值。

    * 本质差别只有返回要求，不应把两者理解成完全不同的编程体系；二者都能使用过程化 SQL 的块、变量和流程控制。

## 银行转账存储过程

* **参数与局部变量**

    * 参数位于存储过程接口上，负责接收调用者提供的转入账户、转出账户和金额；局部变量位于过程块内部，负责接住查询结果并供后续判断和更新使用。

    * 银行账户按整数标识处理，金额使用浮点类型；案例中转出账户、转入账户和金额的类型分别为 `INT`、`INT`、`FLOAT`。

* **转账前检查顺序**

    * 先查询转出账户余额并存入局部变量；结果为 null 时执行 `ROLLBACK` 并 `RETURN`，表示未能取得余额。

    * 再判断转出余额是否小于转账金额；不足时同样回滚并返回。

    * 然后查询转入账户号并判断是否为空；目标账户不存在时回滚并返回。

    * 转入账户只检查是否存在，不检查余额是否充足，因为它是接收资金的一方；真正更新前只有“转出账户存在、余额足够、转入账户存在”三项必须通过。

    ```text
    检查转出账户
          ↓
    检查余额是否足够
          ↓
    检查转入账户
          ↓
    扣减转出账户
          ↓
    增加转入账户
          ↓
    提交
    ```

* **更新阶段与调用边界**

    * 检查全部通过后，先执行 `total = total - amount` 扣减转出账户，再执行 `total = total + amount` 增加转入账户，最后用 `COMMIT` 提交并以 `END` 结束。

    * 每个失败分支都先 `ROLLBACK` 再 `RETURN`，避免只完成后半段而留下半成品转账。

    * 调用者只需给出转出账户、转入账户和金额，不必知道内部变量、查询顺序与分支判断；转账完成但不交回结果值时属于存储过程，若还要求返回回执或计算结果，则属于函数。

## ODBC 的定位与体系结构

* **开放数据库互连（Open Database Connectivity，ODBC）**

    * > **定义**：ODBC 是微软开放服务体系中面向数据库访问的一组应用程序编程接口，用共同规范屏蔽不同关系数据库管理系统的访问差异。

    * ODBC 解决的是同一应用程序如何用统一办法访问不同 DBMS，而不是 SQL 能否执行或 SQL 如何嵌入主程序。

    * 应用程序不直接依赖某个数据库的专有访问方式，而是通过 ODBC API、驱动程序管理器、具体驱动程序和数据源逐层访问。

* **ODBC 三层中间结构**

    ```text
    应用程序
        ↓
    ODBC API
        ↓
    ODBC 驱动程序管理器
        ↓
    目标 DBMS 驱动程序
        ↓
    数据源
    ```

    * 应用程序通过统一 API 发出请求，由驱动程序管理器选择相应数据库驱动程序，再把存取结果沿原路径返回。

    * 应用程序不必在代码中直接写死某种驱动、服务器名和数据库名，只需指明要连接的数据源。

* **应用程序层**

    * ODBC 应用程序依次承担请求连接、指定数据源、使用存储空间、处理操作结果与数据、处理错误、提交或回滚、断开数据源等工作。

* **驱动程序管理器层**

    * > **定义**：驱动程序管理器负责应用程序与具体数据库驱动程序之间的通信、安装驱动、选择驱动、管理数据源、检查合法性和记录 ODBC 函数调用等协调工作。

    * 常见名称为 `odbc32.dll`，通常由系统提供；它可以建立、配置、删除数据源，并查看系统已安装的 ODBC 驱动程序。

* **驱动程序与数据源层**

    * 应用程序发出的操作先由驱动程序管理器交给目标数据库的驱动程序，再通过该驱动支持的函数完成存取，结果也经驱动程序返回。

    * 更换数据源时，应用程序通过不同驱动访问对应数据库，不必整体改写业务逻辑。

    * 单宿数据源与应用程序在同一台机器；多宿数据源支持客户机/服务器及网络环境，三层客户机/服务器架构属于多宿。

    * 数据源对最终用户透明；用户关心的是取得数据，而不是底层具体调用了哪个驱动程序。

* **数据源名称（Data Source Name，DSN）**

    * 数据源名称代替驱动程序、服务器名和数据库名等底层细节；例如 `Person` 可指向 SQL Server 中的人事数据库，`Education` 可指向 Kingbase 中的教学科研数据库。

## ODBC API 的函数、句柄与类型绑定

* **ODBC 函数接口**

    * ODBC 3.0 标准提供 76 个函数接口，覆盖环境与句柄的分配释放、数据库连接、信息获取、事务处理、SQL 执行和编目信息读取。

    * `DriverConnect` 用于连接驱动，`GetInformation` 与 `SQLGetFunction` 用于获取相关能力信息，事务接口用于处理事务，立即执行接口用于直接执行 SQL，编目函数用于获取表、列、权限结构等数据字典信息。

    * 不同版本的函数及调用方式可能不同，使用接口时既要确认版本，也要确认驱动是否支持相应能力。

* **句柄层级**

    * > **定义**：句柄是 ODBC 中代表指针的 32 位整数值，用来定位环境、连接、语句执行环境及结果描述等资源。

    * 一个 ODBC 应用程序建立一个独立环境并分配一个环境句柄；一个环境句柄可连接多个连接句柄，每个连接句柄连接一个数据源，一个连接句柄又可建立多个语句句柄。

    * 描述句柄承担更深一层的结果描述信息；应用通过不同层级的句柄安排连接、SQL 执行和结果处理。

* **数据类型与绑定函数**

    * SQL 数据类型用于数据源，C 数据类型用于应用程序变量和代码；应用程序可通过 `SQLGetTypeInfo` 获取不同驱动支持的数据类型。

    * 从数据源向应用程序传回结果列时，用 `SQLBindCol` 把结果列绑定到应用程序位置。

    * 从应用程序向 SQL 语句传入参数时，用 `SQLBindParameter` 把应用程序变量绑定为语句参数。

    * > **易错点**：`SQLBindCol` 处理结果列到应用程序的方向，`SQLBindParameter` 处理应用程序参数到 SQL 的方向，不能混用。

## ODBC 执行流程与资源释放

* **ODBC 工作流程**

    ```text
    配置数据源
        ↓
    初始化环境
        ↓
    建立连接
        ↓
    分配语句句柄
        ↓
    执行 SQL
        ├── 无结果 → 结束
        └── 有结果 → 处理结果集
        ↓
    释放句柄并终止
    ```

    * 数据源可由驱动程序管理器的配置功能或数据源管理工具增加、修改和删除，配置内容是应用程序可识别的数据源名称与连接信息。

    * 环境由驱动程序管理器控制和配置；应用程序发出连接调用后，驱动程序管理器才调用目标驱动的 `SQLAllocHandle` 分配所需数据结构。

    * 建立连接可使用 `SQLConnect`、`SQLDriverConnect` 或 `SQLBrowseConnect`，输入包括数据源名称、用户 ID 和口令；连接失败返回相应错误值，成功后使用连接句柄继续。

    * 执行任何 SQL 前都要分配语句句柄；句柄中容纳具体 SQL、输出结果集及相关信息，可用 `SQLSetStmtAttr` 设置属性，也可采用默认值。

    * SQL 有预处理执行和直接执行两种方式；前者适合多次执行，后者直接运行当前语句。含参数时先把应用程序变量绑定到参数位置，再执行并送入实际值。

    * 有结果集时可获取列数以及每列的名称、类型、长度和范围，并可用游标逐行处理；使用结束后必须释放句柄和执行环境。

## 跨数据库学生数据搬运

* **ODBC 的代表性场景**

    * 同一应用需要同时访问 Kingbase 和 SQL Server 等不同 DBMS 时，必须通过 ODBC 分别配置和连接两个数据源。

    * 若两个部门本来就使用同一种 DBMS，例如都在 SQL Server 中，则可直接从不同数据库取数，不需要 ODBC 介入。

* **跨库读写两阶段**

    * Kingbase 侧执行 `SELECT * FROM Student;` 读取源表数据。

    * SQL Server 侧执行 `INSERT INTO Student VALUES (?, ?, ?, ?);`，把源记录字段逐个绑定到四个参数占位符后插入目标表。

    * 问号的本质是参数位置；从 Kingbase 取得一行后，应把该行各字段绑定为 SQL Server 插入语句的输入，再逐行完成搬运。

* **双数据源句柄**

    * 同时使用两个数据库时，程序准备两套相关句柄，例如以 `king` 开头的一组服务 Kingbase，以 `server` 开头的一组服务 SQL Server。

    * Kingbase 的环境、连接和语句句柄负责读取数据并产生结果集；SQL Server 的环境、连接和语句句柄负责接收参数并写入数据，两侧连接与执行对象不能混为一体。

    * 返回状态可由变量 `RET` 接收，用来承接操作结果或错误状态。

* **跨库操作顺序**

    * 分别配置 Kingbase 与 SQL Server 数据源，并为两侧环境调用 `SQLAllocHandle` 分配环境句柄。

    * 调用 `SQLConnect`，传入各自的数据源名称、用户 ID 和口令建立连接；示例中参数位置使用 `system` 用户和 `manager` 口令，只用于说明连接参数，不应作为生产凭据照搬。

    * 为两个数据库分别分配语句句柄，用 `SQLSetStmtAttr` 设置所需语句属性。

    * 在 Kingbase 侧执行查询并处理结果集，在 SQL Server 侧执行带占位符的插入并绑定源字段；最后释放两侧的环境、连接和语句句柄。

    * 改变连接函数所指向的数据源即可访问另一种关系数据库；跨库搬运应把“连接哪个数据源”与“执行什么 SQL”分离，而不是为每个数据库重写整套业务流程。

## 编程机制的选择主线

* **按问题选择机制**

    * SQL 要进入已有 C、C++、Java 等程序并由主语言控制时，使用嵌入式 SQL。

    * SQL 自身需要在数据操作之外表达条件、重复和异常处理时，使用过程化 SQL。

    * 处理逻辑要在数据库服务器上被多个调用者反复使用时，预封装为存储过程或函数；需要返回结果值时用函数，不强制返回值时用存储过程。

    * 同一应用需要屏蔽不同 DBMS 的访问差异时，通过 ODBC API、驱动程序管理器、驱动和数据源完成访问。

* **机制间的连接点**

    * 通信区传执行状态，主变量传输入与结果，指示变量解释空值，游标协调多行集合与逐行主语言处理。

    * 过程化 SQL 用块、条件、循环和异常处理把业务步骤拼成完整过程，服务器端预封装通过参数复用这些逻辑。

    * ODBC 继续解决异构数据源接入：应用层通过统一 API 发请求，驱动管理器选择目标驱动，数据库结果再沿同一链路返回。
