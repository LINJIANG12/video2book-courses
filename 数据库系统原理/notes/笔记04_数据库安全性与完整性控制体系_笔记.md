# 数据库安全性与完整性控制体系

## 计算机系统安全威胁与安全评估标准

### 计算机系统安全威胁与架构边界

* **安全威胁分类（Security Threats）**

    * > **定义**：威胁数据库安全的风险来源在本质上分为主观恶意破坏与客观环境损耗两大类别。

    * 主观恶意破坏包括黑客攻击、非授权越权访问、敏感数据泄露与非法篡改破坏。

    * 客观环境损耗包括硬件介质损毁与系统突发断电宕机等不可抗力导致的数据灾难。

    * 防范机制定位：数据库安全性控制旨在构筑软硬件与网络防御体系，确保数据免受非授权使用与破坏。

* **多层架构安全暴露面（Multi-Tier Architecture Attack Surface）**

    * > **定义**：终端用户请求依次流经客户端、Web 服务器、应用服务器到达数据库服务器的全链路攻击暴露面。

    * 客户端层风险包括个人终端静态口令泄露、木马植入与恶意脚本劫持。

    * 网络通信层基于 TCP/IP 分组交换机制，数据包在公网路由节点转发时存在报文嗅探、抓包截获与中间人窃听风险。

    * 服务端层面临拒绝服务攻击（DoS）与分布式拒绝服务攻击（DDoS），海量伪造并发耗尽计算与网络带宽资源导致系统瘫痪。

* **企业数据管理架构（Enterprise Data Architecture）**

    * > **定义**：企业级数据从多源业务产生经抽取清洗流向分析消费的逐级分化体系。

    * 数据流水线流程：多源数据输入通过抽取、转换、加载（ETL）汇入数据仓库（Data Warehouse）。

    * 元数据（Metadata）充当检索数据仓库中浩瀚数据的系统索引目录。

    * 数据仓库进一步分化出面向具体职能部门的数据集市（Data Mart），作为专用业务数据库通过中间件向终端应用提供分析支持。

### 可信系统评估准则与通用准则体系

* **可信计算机系统评估准则（TCSEC, DoD 85）**

    * > **定义**：美国国防部于 1985 年颁布的评估计算机与数据库系统安全防范能力的权威准则。

    * 等级划分：划分为 4 个大组、7 个等级，安全保障等级严格遵循递进关系：$$D < C1 < C2 < B1 < B2 < B3 < A1$$

    * 级别特征与技术机制：

        | 安全等级 | 级别名称 | 核心安全技术特征与机制 |
        | :--- | :--- | :--- |
        | D 级 | 最小保护（Minimal Protection） | 最低安全级别，几乎无有效安全控制，软硬件缺乏基本的存取隔离措施。 |
        | C1 级 | 自主安全保护（Discretionary Protection） | 提供最基本的分离机制，实现用户与数据隔离，具备基础自主访问控制能力。 |
        | C2 级 | 受控存取保护（Controlled Access） | 具备细粒度自主存取控制（DAC），引入身份认证与审计追踪，防止越权读写。 |
        | B1 级 | 标记安全保护（Labeled Security） | 强制存取控制（MAC）起步标准，引入主体与客体敏感度标记。 |
        | B2 级 | 结构化保护（Structured Protection） | 系统具有清晰的模块化与层次化结构，提供形式化安全模型与隐蔽信道分析。 |
        | B3 级 | 安全域保护（Security Domains） | 具备极强抗渗透能力，设立独立安全监控器（Reference Monitor）与安全域隔离。 |
        | A1 级 | 验证设计（Verified Design） | 最高安全级别，系统体系架构、设计规范与安全机制经过严格形式化数学验证。 |

    * 工业基线标准：主流商业关系型数据库管理系统在未经特殊加固时，默认通常能够达到 C2 级安全标准。

* **信息技术安全评估通用准则（Common Criteria, CC）**

    * > **定义**：国际标准化组织结合多国标准制定的全球通用信息技术安全性评估体系。

    * 分级指标：采用评估保障级（Evaluation Assurance Level, EAL）衡量，划分为从 EAL1 至 EAL7 共 7 个等级。

    * 适用边界：EAL1 至 EAL4 关注功能测试、结构分析与脆弱性评估，适用于常规商业软件；EAL5 至 EAL7 引入半形式化设计、形式化验证与数学模型测试，用以抵御高对抗性攻击。

    * 准则对比规则：TCSEC 采用英文字母从 A 至 D 划分且 A 级最高，CC 采用阿拉伯数字从 1 至 7 划分且 EAL7 最高。

## 数据库安全防范模型与存取控制体系

### 数据库安全防范模型与纵深防御

* **分层过滤安全模型（Multi-Layer Defense Model）**

    * > **定义**：数据库管理系统内核自外向内层层设防以过滤非法访问请求的纵深防御体系。

    * 第一道防线为用户标识与身份鉴别，在系统最外层验证使用者合法身份，防止非法实体伪造身份登录。

    * 第二道防线为操作语义分析与推理控制，防范攻击者利用多次合法查询的返回结果推导核心机密。

    * 第三道防线为自主存取控制（DAC），核验用户是否拥有操作特定模式、表、视图或属性列的显式权限。

    * 第四道防线为强制存取控制（MAC），比对主体许可证级别与客体密级标记，实施硬性隔离。

    * 物理底层防线为存储加密与透明映射，伴随审计模块对关键操作进行全流程记账。

* **推理控制与数据防泄漏（Inference Control and Data Leakage Prevention）**

    * > **定义**：阻止合法用户通过关联分析和数理逻辑推导出被隐藏机密数据的控制机制。

    * 攻击路径：攻击者多次执行系统允许的普通合法查询，通过统计聚集差值推导出个体敏感记录。

    * 防御机理：系统对查询语义与关联约束进行深度检测，阻断推导通道。

### 自主存取控制与授权机制

* **自主存取控制（Discretionary Access Control, DAC）**

    * > **定义**：拥有特定数据对象权限的用户能够自主将该权限转授其他合法用户或随时收回的权限管理机制。

    * 授权语句语法格式：
        ```sql
        GRANT <权限列表> 
        ON <对象类型> <对象名> 
        TO <用户或角色列表> 
        [WITH GRANT OPTION];
        ```

    * 回收语句语法格式：
        ```sql
        REVOKE <权限列表> 
        ON <对象类型> <对象名> 
        FROM <用户或角色列表> 
        [CASCADE | RESTRICT];
        ```

    * 权限对象覆盖范围：数据库模式（SCHEMA）、基本表（TABLE）、视图（VIEW）、索引（INDEX）以及属性列。

    * 权限类型划分：数据操作权限包括 SELECT、INSERT、UPDATE、DELETE、REFERENCES 与 ALL PRIVILEGES。

    * 受权对象指定规则：可指定单个或多个用户，亦可指定保留关键字 PUBLIC 代表系统中的全体合法用户。

    * 列级授权机制：更新操作可通过 `UPDATE(列名)` 限定到具体字段，未指定的敏感列自动保持不可写保护状态。

    * 转授权修饰符：语句包含 `WITH GRANT OPTION` 时允许受权用户向外继续传播权限；缺省时受权用户仅能自用。

    * > **易错点**：⚠️ 权限传播链在逻辑上构成有向无环图（DAG），系统严禁循环授权（如用户 U1 授权给 U2，U2 授权给 U3 后，U3 不得反向将相同权限授予 U1）。

* **权限级联回收机制（Cascade Revocation）**

    * > **定义**：回收拥有转授权资格用户的权限时对其派生下游权限的联动处置策略。

    * CASCADE 选项机理：系统顺着授权树，将由该用户直接或间接转授出的全部下游权限一并连带注销。

    * RESTRICT 选项机理：若系统检测到该权限已转授给他人，则立即中止操作并抛出异常，要求先手动清除下游授权。

### 账户分类与数据库角色机制

* **系统初始用户权限分级（System User Classes）**

    * > **定义**：创建新用户时预设的系统特权级别与行为边界划分。

    * 语法格式：`CREATE USER <用户名> [WITH CONNECT | RESOURCE | DBA];`

    * 权限级别与行为限制：
        * CONNECT：基础默认级别，仅可登录并连接数据库，具备对授权对象的查询与更新能力，严禁创建新用户、创建模式或创建基本表。
        * RESOURCE：中等权限级别，可以自主创建基本表和视图并成为其属主，但不能创建数据库模式，也不能创建其他用户。
        * DBA：超级管理员级别，拥有系统中的最高支配权，可创建用户、定义模式、操作任意数据对象并进行全局授权与审计配置。

* **数据库角色（Database Role）**

    * > **定义**：权限的命名集合，用于对拥有相同职责的用户组进行批量权限映射与维护。

    * 角色生命周期管理语法：
        ```sql
        CREATE ROLE <角色名>;
        GRANT <权限列表> ON <对象> TO <角色名>;
        GRANT <角色名> TO <用户列表> [WITH ADMIN OPTION];
        REVOKE <角色名> FROM <用户名>;
        ```

    * 动态同步机制：向角色扩展权限或剥离权限时，角色的全部隶属用户即刻同步获得新权限或失去旧权限。

    * 成员管理特权：`WITH ADMIN OPTION` 允许受权用户将该角色继续分发授予其他人员。

### 基于敏感度标记的强制存取控制

* **强制存取控制（Mandatory Access Control, MAC）**

    * > **定义**：由系统为所有实体赋予固定安全标记并通过硬性密级规则判定的不可逾越的访问控制机制。

    * 适用场景与标准：属于 TCSEC B1 级以上核心配置，防范合法用户通过转存公开表无意或恶意泄露机密。

    * 实体划分：
        * 主体（Subject）：系统活动实体（用户、应用程序或后台进程），被打上的标记称为许可证级别（Clearance Level）。
        * 客体（Object）：系统被动实体（模式、表、视图、属性列、元组），被打上的标记称为密级（Classification Level）。

    * 敏感度标记层级关系：$$\text{绝密（Top Secret, TS）} > \text{机密（Secret, S）} > \text{秘密（Confidential, C）} > \text{公开（Public, P）}$$

* **访问判定规则与双重校验（Access Rules and Dual Verification）**

    * > **定义**：基于 Bell-LaPadula 安全模型确立的强制存取读写判定准则与系统内核校验顺序。

    * 只下读规则（Read Down）：仅当主体的许可证级别 $\ge$ 客体的密级时允许读取，防范高密级数据流向低资质主体。

    * 只上写规则（Write Up）：仅当主体的许可证级别 $\le$ 客体的密级时允许写入，防范高级特权主体被劫持后将机密转录至低密级文件。

    * 双重校验时序：用户请求必须首先通过 DAC 权限矩阵核验；放行后再触发内核 MAC 密级判定，两道防线皆通过方可发生物理存取。

## 数据库辅助安全控制机制

### 视图机制在安全控制中的运用

* **视图安全隔离机制（View Security Isolation）**

    * > **定义**：通过在基本表上定义行列子集视图并向用户授予视图权限以遮蔽物理基表的隔离技术。

    * 实现机理：通过 `WHERE` 子句过滤特定行，通过 `SELECT` 投影过滤敏感属性列，构建定制化虚拟表。

    * 物理隔离效果：视图在逻辑上提供标准交互接口，物理上不存储真实数据，使用户完全无法感知底层非授权字段与非授权行。

* **细粒度视图授权（Fine-Grained View Authorization）**

    * > **定义**：将增删改查权限绑定到特定视图而非底层物理表的授权模式。

    * 权限范围控制：如对计算机系学生视图 `CS_Student` 授予用户查询权限，用户完全无法窥探非计算机系学生数据。

    * 权限剥离保护：针对特定操作人员开放全权限时，由于视图天然屏蔽了敏感字段，确保基表敏感属性安全隔离。

### 审计日志追踪体系

* **数据库审计机制（Database Auditing）**

    * > **定义**：系统安全模块在底层静默记录用户操作踪迹、SQL 文本与数据快照的记账防线。

    * 定位与价值：当合法特权用户越过 DAC 与 MAC 篡改核心数据时，作为最后一道防线提供事后溯源与取证依据。

    * 记账数据维度：记录登录登出时刻、所执行 SQL 文本、字段变更前镜像（Old Value）与后镜像（New Value）。

    * 配置语法：
        ```sql
        AUDIT <操作列表> ON <对象名>;
        NOAUDIT <操作列表> ON <对象名>;
        ```

* **审计粒度控制体系（Audit Granularity Hierarchy）**

    * > **定义**：为平衡系统 CPU 开销、磁盘 I/O 负担与安全性而设立的层次化监控策略。

    * 服务器级审计：仅监控数据库引擎的建立连接、断开连接及系统启停异常。

    * 语句级审计：仅监控具有全局破坏性后果的特定 SQL 命令（如 `DROP TABLE`）。

    * 对象级审计：精确定位到敏感表的核心属性列变更（如选课表成绩列的修改更新），以最小系统开销保障安全追溯。

### 数据存储加密与端到端传输保护

* **数据存储加密（Data Storage Encryption）**

    * > **定义**：利用加密算法与密钥将磁盘物理数据块由明文转换为不可直读密文的防护技术。

    * 防护边界：防范物理存储介质遭遇盗窃或脱机拷贝后的底层破解分析。

    * 加密时机：数据写入物理介质前由存储引擎透明加密，读取时透明解密。

* **端到端传输加密与数字证书鉴权（Transmission Encryption and CA Authentication）**

    * > **定义**：客户端与服务端基于数字证书建立身份互信并使用会话密钥传输密文的信道安全机制。

    * 交互时序流程：
        1. 客户端发起安全连接请求；
        2. 服务端返回第三方权威认证中心（CA）签发的数字证书；
        3. 客户端验证证书合法性与服务端端点可靠性；
        4. 双方握手协商公私钥算法并生成对称会话密钥；
        5. 在对称加密保护的安全信道中传输业务数据；
        6. 交互结束关闭连接。

    * 安全效能：杜绝明文数据在公网传输过程中遭遇数据包抓包截获与篡改。

## 数据库完整性与三类经典约束

### 数据库完整性与安全性范畴界定

* **完整性与安全性差异（Integrity vs Security）**

    * > **定义**：安全性防范非法存取与客观破坏，完整性保障数据库数据符合现实语义与逻辑相容性。

    * 防范目标对比：安全性关注主体是否具备合法访问权限，完整性关注数据输入与修改是否遵循业务规则。

    * 语义维度：完整性确保数据的正确性、有效性与相容性，防止虚假、自相矛盾或孤立悬空数据入库。

* **数据库管理系统完整性控制能力（DBMS Integrity Capabilities）**

    * > **定义**：DBMS 内核为保障数据完整性所必须具备的三项核心功能支撑。

    * 第一项为提供定义完整性约束条件的机制（通过声明式 SQL 语言描述规则）。

    * 第二项为提供高效检查与验证完整性约束的方法（如底层索引比对）。

    * 第三项为提供完备的违约处理机制（在检测到违约操作时进行阻断或级联联动）。

    * 三类经典约束模型映射：实体约束对应实体完整性，联系约束对应参照完整性，属性约束对应用户定义完整性。

### 实体完整性与底层检验机理

* **实体完整性规则（Entity Integrity Rule）**

    * > **定义**：关系模型中主码属性（主属性）不能取空值（NULL），且主码值必须唯一标识元组。

    * 现实语义逻辑：若主属性允许取空值，将导致实体身份丢失或无法落实业务责任（如产生未知归属的考试成绩）。

    * SQL 定义规范：
        * 单属性主码：既可写在列定义后（列级约束），亦可写在表末尾（表级约束）。
        * 复合主码：必须且只能在所有列声明完毕后在表末尾统一声明（表级约束），严禁在单列分别声明。
        ```sql
        CREATE TABLE SC (
            Sno     CHAR(9) NOT NULL,
            Cno     CHAR(4) NOT NULL,
            Grade   SMALLINT,
            PRIMARY KEY (Sno, Cno)
        );
        ```

    * 自动推导限制：声明 `PRIMARY KEY` 后，DBMS 自动施加非空且唯一（`NOT NULL UNIQUE`）双重约束。

* **唯一性检查机理（Uniqueness Verification Mechanism）**

    * > **定义**：DBMS 在数据插入或主码更新时核验主码唯一性的底层算法实现。

    * 全表扫描（Table Scan）机理：逐行对比主码，平均比对次数为 $E = (1 + n) / 2$，在大数据量下导致性能断崖式下跌。

    * B+ 树索引比对（B+ Tree Indexing）机理：DBMS 默认在主码列构建平衡多路搜索树，键值与指针驻留分支节点，数据与行指针挂载于叶子节点。

    * 索引检验路径：插入新键值时沿根节点与分支节点比较，通常仅需 3 至 4 次节点检索即可定位叶子节点判定重复，显著提升写入性能。

### 参照完整性与违约处置策略

* **参照完整性规则（Referential Integrity Rule）**

    * > **定义**：外码取值必须为空值（NULL）或等于被参照关系中某个元组的主码值。

    * 角色划分：外码所在的关系称为参照关系（Referencing Relation），外码所引用的主码所在关系称为被参照关系（Referenced Relation）。

    * 数据关联机理：通过外码建立跨表实体间的双向数据互锁与引用完整性。

* **参照完整性破坏场景与违约处置（Referential Violations and Handling Policies）**

    * > **定义**：导致外码引用指针断裂的数据变更行为及其对应的引擎防御策略。

    * 四类破坏场景：
        1. 参照表插入新记录，录入不存在的外码值；
        2. 参照表修改外码值，变更为未注册的外码值；
        3. 被参照表删除已有记录，导致参照表残留悬空孤立引用；
        4. 被参照表修改主码值，导致参照表外码指针断裂。

    * 违约处置策略：
        * 拒绝执行（NO ACTION / RESTRICT）：系统默认保守策略，操作破坏完整性时直接抛出异常并整体回滚。
        * 级联操作（CASCADE）：被参照表主码删除或修改时，自动同步删除或更新参照表中对应的引用元组。
        * 设为空值（SET NULL）：被参照表主码删除或修改时，自动将参照表中的对应外码属性重置为 NULL。

    * > **易错点**：⚠️ `SET NULL` 策略必须以外码列允许为 NULL 为前提；若外码同时作为参照表主码的组成部分（如选课表 `SC` 中的 `Sno`），受实体完整性制约绝对禁止取 NULL，此时严禁配置 `SET NULL`。

### 用户定义完整性与跨属性校验

* **属性级约束机制（Attribute Constraints）**

    * > **定义**：针对单一字段根据业务语义设定的取值范围限制。

    * 非空约束（`NOT NULL`）：强制该属性在每行元组中必须具备有效取值。

    * 唯一约束（`UNIQUE`）：保证整张表中属性值无重复，但允许存在 NULL（未同时声明 `NOT NULL` 时）。

    * 检查约束（`CHECK`）：通过布尔表达式限定取值区间或离散枚举（如 `CHECK (Ccredit BETWEEN 1 AND 4)`）。

* **元组级跨属性关联校验（Tuple Cross-Attribute Verification）**

    * > **定义**：约束条件涉及同一元组内两个及以上属性相互制约的表级校验规则。

    * 声明位置规范：涉及跨列制约的规则在逻辑上属于整行元组约束，必须后置书写在表定义的末尾。

    * > **易错点**：⚠️ 跨列业务逻辑需转化为等价布尔表达式。例如业务规则“若学生性别为男，则姓名绝不能以 Ms. 开头”，利用命题等价逻辑 $P \rightarrow Q \equiv \neg P \lor Q$，在 SQL 中必须表达为 `CHECK (Ssex = '女' OR Sname NOT LIKE 'Ms.%')`。

### 完整性约束命名规范与动态维护

* **约束命名子句（Constraint Clause）**

    * > **定义**：使用显式标识符为数据库完整性规则赋予名字的标准语法结构。

    * 语法格式：`CONSTRAINT <约束名> <约束条件>`

    * 适用范围：涵盖 NOT NULL、UNIQUE、PRIMARY KEY、FOREIGN KEY 以及 CHECK。

    * 命名价值：为复杂约束提供专属标识，使系统报错具备自解释性，并为模式的动态重构提供精准引用锚点。

* **约束动态维护机制（Dynamic Constraint Maintenance）**

    * > **定义**：业务规则演进时通过 `ALTER TABLE` 对已有约束进行停用、删除与重建的工程操作。

    * 操作原则：SQL 规范中修改已有约束遵循“先删后建”模式。

    * 实施步骤：
        ```sql
        -- 第一步：按约束名彻底拔除旧规则
        ALTER TABLE Student DROP CONSTRAINT C3;

        -- 第二步：向表中注入调整后的新规则
        ALTER TABLE Student ADD CONSTRAINT C3 CHECK (Sage < 40);
        ```

## 复杂完整性约束高级控制机制

### 断言机制与全局多表约束

* **断言机制（Assertion Mechanism）**

    * > **定义**：数据库中命名的独立一般性完整性约束，用于表达跨多表关联或依赖聚集计算的全局规则。

    * 语法格式：
        ```sql
        CREATE ASSERTION <断言名> CHECK (<条件表达式>);
        DROP ASSERTION <断言名>;
        ```

    * 执行机理：断言独立于单一基本表存储于数据字典中，任何对所涉表的数据更新操作均自动触发条件核验，判定结果为假（FALSE）时立即拒绝并回滚事务。

    * 命名工程规范：推荐采用“对象类型_关联表_业务目标_指标”组合命名法（如 `ASSE_SC_DATABASE_NUMBER`）。

* **断言设计场景与开销控制（Assertion Design Scenarios and Overhead）**

    * > **定义**：断言在跨表关联、单门课程容量限制、全局分组统计中的实现方案与系统性能考量。

    * 单门课程容量约束设计：限制《数据库》课程选课上限为 60 人，通过跨表连接与聚集计数实现：
        ```sql
        CREATE ASSERTION ASSE_SC_DATABASE_NUMBER
        CHECK (
            60 >= (
                SELECT COUNT(*)
                FROM SC, Course
                WHERE SC.Cno = Course.Cno
                  AND Course.Cname = '数据库'
            )
        );
        ```

    * 全局分组与多维复合断言设计：限制全校每门课程各学期选课均不超 60 人，结合 `GROUP BY` 与 `ALL` 谓词：
        ```sql
        CREATE ASSERTION ASSE_SC_TERM_COURSE_LIMIT
        CHECK (
            60 >= ALL (
                SELECT COUNT(*)
                FROM SC
                GROUP BY Cno, Term
            )
        );
        ```

    * 维护开销边界：所涉基础表发生任何插入、删除或更新时均触发全量关联重算，在高吞吐事务系统中需审慎评估性能损耗。

### 触发器事件驱动架构与核心模型

* **触发器（Trigger）**

    * > **定义**：预先定义并存储于数据库服务器内部、由特定数据库事件自动驱动执行的特殊过程。

    * 事件-条件-动作（ECA）模型机理：
        * 事件（Event）：指定激活触发器的数据库操作时刻与类型（INSERT、DELETE、UPDATE）。
        * 条件（Condition）：`WHEN` 子句指定的逻辑表达式，评估为真方推进执行，缺省时无条件执行。
        * 动作（Action）：触发条件满足后执行的过程程序块，可执行 SQL 序列、逻辑改写或存储过程调用。

    * 创建语法格式：
        ```sql
        CREATE TRIGGER <触发器名>
        {BEFORE | AFTER} <触发事件> ON <表名>
        [REFERENCING {OLD ROW AS <旧行变量> | NEW ROW AS <新行变量> |
                      OLD TABLE AS <旧表名> | NEW TABLE AS <新表名>}]
        {FOR EACH ROW | FOR EACH STATEMENT}
        [WHEN <触发条件>]
        <触发动作体>
        ```

    * 约束限制规则：
        * 创建权限：仅基本表属主或 DBA 角色具备在表上创建触发器的权限。
        * 挂载对象限制：触发器只能定义在基本表上，严禁直接定义在视图上。
        * 模式命名空间约束：触发器名在所属模式内必须唯一，且必须与目标表处于同一模式空间。
        * 精确列级监听：通过 `UPDATE OF <列名> ON <表名>` 精准锁定字段变更，避免无关列更新引发无效触发。

* **触发时机与变量容器机制（Trigger Timing and Referencing Containers）**

    * > **定义**：触发器在底层数据引擎中的内存执行物理边界与新旧数据捕获机制。

    * BEFORE 触发器机理：数据到达内存缓冲区但底层尚未正式修改目标表元组之前介入，具备在内存中就地修正待写入数值的能力。

    * AFTER 触发器机理：底层修改已在内存中执行完毕后介入，用于记录审计流水或执行级联联动。

    * REFERENCING 变量容器机制：
        * `OLD ROW AS <变量名>`：定义旧行变量，装载受影响元组在事件发生前的历史数据。
        * `NEW ROW AS <变量名>`：定义新行变量，装载受影响元组即将或已经写入的新数据。
        * `OLD TABLE` 与 `NEW TABLE`：分别装载受批量操作影响的历史元组集合或新增元组临时过渡表。

* **行级与语句级触发粒度（Row and Statement Granularity）**

    * > **定义**：依据单条 SQL 语句执行时动作体调用频度划分的触发级别。

    * 行级触发器（`FOR EACH ROW`）：语句每影响一行元组，动作体执行一次；支持使用行级变量容器。

    * 语句级触发器（`FOR EACH STATEMENT`）：无论影响多少行，整条 SQL 执行完毕后动作体仅执行一次；支持表级快照过渡表。

### 触发器业务场景实战设计

* **成绩变更审计行级触发器（Audit Log Row Trigger）**

    * > **定义**：修改学生成绩且单次涨幅达到或超过原成绩 10% 时自动将异动记录归档至审计表的触发器。

    * 实现代码与要素：
        ```sql
        CREATE TRIGGER SC_T
        AFTER UPDATE OF Grade ON SC
        REFERENCING
            OLD ROW AS OldTuple
            NEW ROW AS NewTuple
        FOR EACH ROW
        WHEN (NewTuple.Grade >= 1.1 * OldTuple.Grade)
        INSERT INTO SC_U(Sno, Cno, OldGrade, NewGrade)
        VALUES (
            OldTuple.Sno,
            OldTuple.Cno,
            OldTuple.Grade,
            NewTuple.Grade
        );
        ```

    * 动作机理：采用 `AFTER UPDATE OF Grade` 精确监听成绩列；通过 `REFERENCING` 装载新旧数据；利用 `WHEN` 在动作体执行前过滤涨幅；动作体插入审计表 `SC_U`。

* **批量导入统计语句级触发器（Batch Insert Log Statement Trigger）**

    * > **定义**：在向学生表执行批量导入后一次性将新增学生总人数记入日志表的触发器。

    * 实现代码与要素：
        ```sql
        CREATE TRIGGER Student_Insert_Log
        AFTER INSERT ON Student
        REFERENCING
            NEW TABLE AS delta
        FOR EACH STATEMENT
        INSERT INTO insert_log(Insert_Count)
        SELECT COUNT(*) FROM delta;
        ```

    * 动作机理：采用 `FOR EACH STATEMENT` 保证单条导入语句仅执行一次动作；利用 `NEW TABLE AS delta` 打包新增数据集；通过 `COUNT(*)` 汇总行数写入日志。

* **业务数值自动修正前置触发器（Data Correction Before Trigger）**

    * > **定义**：录入或修改教授工资若低于 40000 元自动在内存中修正为 40000 元的触发器。

    * 实现代码与要素：
        ```sql
        CREATE TRIGGER Insert_Or_Update_Salary
        BEFORE INSERT OR UPDATE ON Teacher
        FOR EACH ROW
        BEGIN
            IF new.job = '教授' AND new.salary < 40000 THEN
                new.salary := 40000;
            END IF;
        END;
        ```

    * 动作机理：采用 `BEFORE` 在数据正式存盘前拦截；直接使用内置 `new` 变量；通过过程块 `IF-THEN` 将 `new.salary` 改写赋值为 40000。

### 触发器执行时序与生命周期维护

* **多触发器执行流水线（Execution Pipeline）**

    * > **定义**：单表挂载多阶段规则时数据库引擎内部的标准执行管道。

    * 执行时序管道：
        ```text
        [ 用户提交 SQL 更新请求 ]
                   |
                   v
          1. 执行目标表 BEFORE 触发器 (输入过滤、数据清洗与自动修正)
                   |
                   v
          2. 执行 SQL 语句底层操作与完整性检查 (更新内存数据块、核查主外键)
                   |
                   v
          3. 执行目标表 AFTER 触发器 (业务联动、跨表审计、级联写入)
                   |
                   v
        [ 事务完成持久化提交 ]
        ```

    * 异常回滚机制：触发动作体执行报错时，触发事件立即终止，当前事务整体回滚，所有关联修改不予保留。

* **触发器生命周期与重构原则（Trigger Lifecycle and Refactoring）**

    * > **定义**：触发器对象的销毁与重构规范。

    * 删除语法：`DROP TRIGGER <触发器名> ON <表名>;`

    * > **易错点**：⚠️ 标准 SQL 语法不提供 `ALTER TRIGGER`，修改触发器规范操作是一律先执行 `DROP TRIGGER` 彻底销毁，再执行 `CREATE TRIGGER` 重建，防止复杂过程逻辑产生隐蔽冲突。

* **数据控制层级选型原则（DCL Selection Hierarchy）**

    * > **定义**：在工程架构中依据业务场景的控制粒度与性能开销选择数据控制手段的决策准则。

    * 梯队选型原则：基础约束优先于断言，断言阻断优先于触发器。

    * 第一梯队：单表内部空值控制、取值范围与离散枚举，使用 PRIMARY KEY、FOREIGN KEY 与 CHECK。

    * 第二梯队：跨表数据容量、全局配额与多表联合静态统计约束，使用 CREATE ASSERTION 统一定义。

    * 第三梯队：需要根据输入数据动态改变目标值、记录审计流水或跨表主动派生业务动作，采用 CREATE TRIGGER。
