# 数据库的安全性与完整性

## 数据库安全与完整性

* **数据库安全性（Database Security）**

    * > **定义**：通过身份鉴别、存取控制、视图、审计与加密等机制，控制谁可以访问数据以及对数据执行什么操作。

    * 安全问题既包括主动修改、删除、泄露、篡改数据，也包括软硬件故障造成的数据丢失。

    * 风险可出现在客户端、公开网络、Web 服务器、应用服务器、数据库服务器以及数据仓库和数据集市等整个数据链路。

    * 非法使用不只是直接越权，还包括绕过授权、借助应用程序执行未获准的操作，以及通过多次合法查询推导保密信息。

* **数据库完整性（Database Integrity）**

    * > **定义**：数据库在定义、操作和控制过程中必须遵守的规则，目标是保证数据的正确性与相容性。

    * 完整性要求数据库具备约束表达、约束验证和违约处理三种能力：规则能够写入，非法数据能够被识别，违规操作能够被拒绝或按约定处理。

* **安全性与完整性的分工**

    * 安全性主要约束“谁可以对什么数据做什么操作”。

    * 完整性主要约束“数据是否符合既定语义，以及操作是否违反规则”。

    * 安全性防止非法存取与破坏；完整性保证已经纳入控制的数据始终满足业务条件。

## 安全标准与保护链条

### 评估标准

| 标准 | 等级范围 | 保护级别 | 记忆要点 |
| :--- | :--- | :--- | :--- |
| TCSEC（可信计算机系统评估准则） | D、C1、C2、B1、B2、B3、A1 | D 最低，A1 最高 | 较早的数据库安全标准；C2 对应自主安全保护，B1 对应标记性保护 |
| CC（Common Criteria） | 1 至 7 | 1 最低，7 最高 | 评估内容从功能测试逐步发展到形式化的验证、设计和测试 |

* **TCSEC（Trusted Computer System Evaluation Criteria）**

    * > **定义**：1985 年由美国国防部颁布、按照系统达到的等级划分保护水平的安全标准，也称 DoD85。

    * 使用 A、B、C、D 四个大等级，并细分为 A1、B3、B2、B1、C2、C1、D。

    * 保护级别从 D 逐级提高到 A1，A1“验证设计”最高，D“最小保护”最低。

* **CC（Common Criteria）**

    * > **定义**：后来演化形成的安全评估标准，以 1 至 7 表示逐级上升的保护等级。

    * 等级从 1 到 7 逐级提高，7 最高，1 最低。

* **安全控制链**

```text
用户
  ↓
身份鉴别：确认“你是谁”
  ↓
SQL 检查与推理控制：判断操作与结果是否安全
  ↓
自主存取控制（DAC）与强制存取控制（MAC）
  ↓
操作系统与存储保护
  ↓
数据层执行或拒绝
  ↓
审计日志记录操作过程
```

    * 身份鉴别是访问控制的前置条件，审计覆盖访问控制无法阻止的违规或内部行为。

    * 多组合法查询可能推导出保密信息，因此操作合法不等于推理结果安全。

## 用户身份与访问控制

### 用户身份鉴别

* **用户身份鉴别（User Identification and Authentication）**

    * > **定义**：系统先确认访问者身份，再把该身份与已登记的权限对应起来，并据此决定允许或拒绝后续操作。

    * 用户权限先被定义并登记在数据字典中，访问时依据身份和权限进行合法性检查。

    * 可采用静态口令、密码、动态口令、U 盾、短信验证码、生物特征和智能卡等鉴别方式。

* **自主存取控制（Discretionary Access Control，DAC）**

    * > **定义**：由权限拥有者决定用户能够对对象执行哪些操作的存取控制方法。

    * 对应 TCSEC 的 C2 级，控制具有自主性，权限拥有者可以授予或收回权限。

    * 可以把“查询某张表”和“修改某张表中的某一列”分开授权，在需要修改时临时开放写入权限。

    * `GRANT` 和 `REVOKE` 用于灵活管理对象、属性列、操作以及一个或多个用户的权限。

* **强制存取控制（Mandatory Access Control，MAC）**

    * > **定义**：依据制度化的敏感度标记和主客体密级比较，直接决定访问是否允许的存取控制方法。

    * 对应 TCSEC 的 B1 级，保护级别高于 C2 的 DAC。

    * 主体具有许可证级别 `clearance level`，客体具有密级标记 `classification label`。

    * 课程使用的密级由高到低为 `TS`、`S`、`C`、`P`，即绝密、秘密、机密、公开。

    * 读操作要求主体许可证级别大于等于客体密级。

    * 写操作要求主体许可证级别小于等于客体密级，复制数据时敏感度标记不能被拆除。

    * > **易错点**：强制存取控制中，写权限不是“主体级别越高越自由”；本课程的规则要求“主体级别 ≤ 客体密级”。

### 初始身份

| 初始身份 | 权限范围 | 典型场景 |
| :--- | :--- | :--- |
| `CONNECT` | 可以连接数据库，不能创建用户、模式或基本表 | 普通用户 |
| `RESOURCE` | 可以创建基本表和视图，不能创建模式或新用户 | 需要建表的业务人员 |
| `DBA` | 可以创建用户、模式、基本表并执行多种管理操作 | 数据库管理员 |

    * 未明确指定创建新用户的权限时，新用户默认具有 `CONNECT` 身份。

    * 连接数据库只表示可以登录，不表示自动获得创建其他数据库对象的能力。

### 角色授权

* **角色（Role）**

    * > **定义**：可以看作用户集合的虚拟概念；先把权限授予角色，再把角色授予用户。

    * 创建角色的基本写法为 `CREATE ROLE <角色名>`。

    * 角色上的对象权限仍用 `GRANT ... ON ... TO ...` 授予。

    * 将角色授予用户后，集合内的用户同时获得该角色包含的权限。

    * 用 `REVOKE <角色名> FROM <用户>` 收回角色后，用户不再通过该角色取得相应权限。

    * 角色权限增加或删除，分别使用 `GRANT` 和 `REVOKE`，不需要先描述角色的旧状态。

* **角色传播选项**

    * `WITH ADMIN OPTION` 表示接收角色的用户可以继续把该角色授予其他用户。

    * `WITH GRANT OPTION` 表示接收对象权限的用户可以继续把该对象权限授予其他用户。

    * `WITH ADMIN OPTION` 传播角色；`WITH GRANT OPTION` 传播对象权限，二者作用对象不同。

## SQL 权限管理

### 授权

* **`GRANT` 授权语句**

    * > **定义**：把指定对象上的指定操作权限授予一个、多个或全体用户。

```sql
GRANT <权限列表>
ON [对象类型] <对象名>
TO <用户>[, ...] [WITH GRANT OPTION];
```

    * 权限可作用于模式、基本表、视图和索引。

    * 数据操作权限包括增加、删除、修改和查询。

    * 更新权限不指定属性列时作用于整张表；指定属性列时只作用于该列。

    * 授权者可以是管理员、对象创建者或已经拥有该权限并具备继续授权能力的用户。

    * 接收者可以是单个用户、多个用户或 `PUBLIC`；`PUBLIC` 表示全体用户。

* **基础授权形式**

```sql
GRANT SELECT ON TABLE STUDENT TO U1;

GRANT ALL PRIVILEGES ON TABLE STUDENT, COURSE TO U2, U3;

GRANT SELECT ON TABLE SC TO PUBLIC;

GRANT UPDATE(Sno), SELECT ON TABLE STUDENT TO U4;

GRANT INSERT ON TABLE SC TO U5 WITH GRANT OPTION;
```

    * `GRANT SELECT ON TABLE STUDENT TO U1` 只授予 U1 查询学生表的权限。

    * `GRANT ALL PRIVILEGES ON TABLE STUDENT, COURSE TO U2, U3` 将两张表的全部权限授予 U2、U3。

    * `GRANT UPDATE(Sno), SELECT ON TABLE STUDENT TO U4` 只允许 U4 更新学生表的 `Sno` 列，同时允许查询整张表。

    * 多个对象和多个用户均可用逗号分隔。

* **权限传播**

    * 系统后台保存授权信息，至少记录授权者、接收者、对象或列、操作以及接收者能否继续传播。

    * 权限可以沿授权链向下传播，但不能由后授权者再传回前一个授权者形成环。

    * 授权链传播结束的位置取决于接收者是否获得继续传播的能力。

* **权限传播选项**

```sql
GRANT INSERT ON TABLE SC TO U5 WITH GRANT OPTION;

GRANT INSERT ON TABLE SC TO U6 WITH GRANT OPTION;

GRANT INSERT ON TABLE SC TO U7;
```

    * `WITH GRANT OPTION` 传递的是继续授权的能力，而不只是增加一条权限记录。

    * U5 和 U6 收到可传播的 `INSERT` 权限后，可以继续授权；U7 未获得该选项，传播链在此停止。

    * > **易错点**：接收者没有 `WITH GRANT OPTION` 时，只能使用收到的权限，不能把该权限继续授予他人。

### 收回权限

* **`REVOKE` 收回语句**

    * > **定义**：从指定用户收回对象上的操作权限，并按所选方式处理后续传播出去的授权。

```sql
REVOKE <权限列表>
ON [对象类型] <对象名>
FROM <用户>[, ...]
[CASCADE | RESTRICT];
```

    * 收回方向是 `ON ... FROM ...`，与授权方向 `ON ... TO ...` 相对。

    * 权限可以按对象、属性列和操作进行收回，也可以同时面向一个或多个用户。

* **基础收回形式**

```sql
REVOKE UPDATE(Sno) ON TABLE Student FROM U4;

REVOKE SELECT ON TABLE SC FROM PUBLIC;

REVOKE INSERT ON TABLE SC FROM U5 CASCADE;
```

    * 第一条只收回 U4 对 `Student.Sno` 的更新权限。

    * 第二条收回全体用户对 `SC` 的查询权限。

    * 第三条收回 U5 对 `SC` 的 `INSERT` 权限，并处理由 U5 继续传播出去的授权。

* **`CASCADE` 与 `RESTRICT`**

| 选项 | 被收回权限已经继续传播时的行为 |
| :--- | :--- |
| `CASCADE` | 收回原权限，并一并收回该授权链上继续传播的相关权限 |
| `RESTRICT` | 不立即完成收回，先要求处理依赖该权限的下游授权 |

```text
U5 ──INSERT──> U6 ──INSERT──> U7

CASCADE：U5、U6、U7 的相关权限一起收回
RESTRICT：先处理 U6、U7，再收回 U5 的权限
```

    * `RESTRICT` 的关键不是自动连坐，而是存在下游依赖时阻止当前收回操作。

    * 权限在对象、列、操作和用户仍匹配时持续存在，直到被 `REVOKE` 收回。

### 角色修改

* **角色授权与收回**

```sql
CREATE ROLE R1;

GRANT SELECT, UPDATE, INSERT ON TABLE Student TO R1;

GRANT R1 TO U1, U2, U3;

REVOKE R1 FROM U1;
```

    * 先创建角色，再为角色配置对象权限，最后把角色授予用户。

    * 新增符合角色条件的用户时，只需把用户加入角色，不必重复列出每个对象和每项操作。

    * SQL 是高度非过程化语言，角色权限变化直接用 `GRANT` 增加、用 `REVOKE` 删除。

## 视图、审计与加密

### 视图

* **视图（View）**

    * > **定义**：由查询定义、用于投影或筛选基本表数据的受控数据入口。

    * 可以从基本表中选择需要的行和列形成视图，再针对视图授予查询或其他操作权限。

    * 只获得视图权限的用户无需获得底层基本表权限，因此看不到未授权的行或列。

    * 视图上可以执行 `GRANT` 和 `REVOKE`，使用方式与表相似。

    * 视图只能提供部分数据安全性控制，基础表、其他视图、角色和其他访问路径仍需分别控制。

* **行列子集视图**

    * 视图既可以从基本表中筛选满足条件的行，也可以只保留部分列。

    * 对视图单独授权时，授权对象是视图，而不是视图背后的完整基本表。

### 审计

* **审计（Auditing）**

    * > **定义**：把用户对数据库执行的操作按时间顺序写入审计日志，用于事后追查和责任认定。

    * 审计日志可以记录登录、查询、更新以及退出等操作。

    * 对成绩数据的追查可记录操作用户、查看对象、执行操作以及修改前后的值。

    * 身份鉴别和存取控制用于阻止不允许的操作；审计用于在操作无法被阻止时提供证据。

    * 审计范围可按服务器事件、系统权限、语句类别、模式、对象和具体操作设置。

    * 无须审计所有查询；可只审计成绩单 `grade` 列的更新，以减少时间和空间开销。

* **`AUDIT` 与 `NOAUDIT`**

```sql
AUDIT ALTER ON SC;

AUDIT INSERT, UPDATE, DELETE ON SC;

NOAUDIT ALTER ON SC;

NOAUDIT INSERT, UPDATE, DELETE ON SC;
```

    * `AUDIT` 设置审计，`NOAUDIT` 取消相应审计。

    * `ALTER` 关注表结构变化，数据操作审计关注数据内容变化。

    * 审计会产生时间和空间成本，范围应围绕需要保护的对象和操作选择。

* **数据加密（Data Encryption）**

    * > **定义**：用约定算法将数据明文转换为不能直接识别的密文，接收方再用相应算法恢复原文。

    * 存储加密保护数据在存储介质中的形态，传输加密保护数据在网络传播过程中的形态。

    * 课程示例使用 $y=2x-1$ 加密，接收方通过 $x=\frac{y+1}{2}$ 恢复原文。

    * 可信传输包括创建连接、确认端点、协商加密算法和密钥、以密文传递数据、关闭连接。

    * 端点可靠性验证涉及 CA 和数字证书，密钥机制涉及公钥和私钥。

    * 加密保护数据形态和传播过程，访问控制决定谁可以对数据执行什么操作。

## 实体完整性与参照完整性

### 实体完整性

* **实体完整性（Entity Integrity）**

    * > **定义**：数据库保证主属性具有明确、非空的实体标识规则。

    * 主属性不能取空值。

    * SQL 中主要通过 `PRIMARY KEY` 定义实体完整性。

    * 主码已经隐含“唯一且非空”，已声明为主码的列无须重复写 `NOT NULL`。

    * 只针对单个列的要求写在列定义之后；主码、外码和整表约束写在表定义末尾。

* **共同主码**

    * 选课表中的学号 `Sno` 与课程编号 `Cno` 可以共同构成主码 `(Sno, Cno)`。

    * 共同主码必须作为表级约束整体声明，不能拆成两个独立的列级 `PRIMARY KEY`。

    * 成绩允许为空时，选课记录仍能表示“已选课但尚未给出成绩”；学号或课程编号为空则会丢失实体身份或联系对象。

### 参照完整性

* **参照完整性（Referential Integrity）**

    * > **定义**：外码引用的被参照对象存在时，引用方与被参照方必须保持规定的对应关系。

    * 当一个表的外码指向另一个表的主码时，增删改操作必须维护两边的一致关系。

    * SQL 通过 `FOREIGN KEY` 和 `REFERENCES` 声明外码及其被参照关系。

    * 主码与外码并不排斥，同一属性可以既属于本表主码，又引用另一表的主码。

* **参照完整性的破坏情形**

    * 向引用表插入外码，但被参照表中不存在该外码值。

    * 修改引用表的外码，使其指向不存在的被参照对象。

    * 删除被参照表的记录，但引用表仍保留指向它的外码。

    * 修改被参照表的主码值，却没有同步修改引用表中的外码。

* **参照动作**

| 参照动作 | SQL 关键字 | 违约处理 |
| :--- | :--- | :--- |
| 拒绝执行 | `NO ACTION` | 不允许操作破坏参照关系 |
| 级联操作 | `CASCADE` | 随被参照数据一起删除或修改相关引用数据 |
| 设为空值 | `SET NULL` | 将相关外码列置空，表示原联系已消失 |

    * `NO ACTION` 直接阻止造成不一致的操作。

    * `CASCADE` 适用于被参照数据变化时相关数据应一起变化的情形。

    * `SET NULL` 适用于原联系消失、当前暂未建立新联系的语义。

    * 每个外码可以分别指定 `ON DELETE` 与 `ON UPDATE` 的处理动作，不必采用相同策略。

* **外码声明与级联动作**

```text
PRIMARY KEY (Sno, Cno)
FOREIGN KEY (Sno) REFERENCES Student (Sno)
FOREIGN KEY (Cno) REFERENCES Course (Cno)
```

```text
FOREIGN KEY (Sno) REFERENCES Student (Sno)
ON DELETE CASCADE
ON UPDATE CASCADE
```

    * `ON DELETE` 处理删除行为，`ON UPDATE` 处理更新行为。

    * > **易错点**：删除选课记录和更新选课记录的成绩是两种不同操作；`ON DELETE` 不能用于更新成绩值。

## 用户定义的完整性

### 完整性约束

* **用户定义的完整性（User-defined Integrity）**

    * > **定义**：根据具体业务语义，对单个属性或一条元组中多个属性提出的限制。

    * 用户定义完整性负责表达数据类型不能覆盖的业务规则，例如枚举值、数值区间和跨列关系。

    * 单个属性上的要求写在列定义之后；涉及多个属性或整条元组的条件写在表定义末尾。

    * 常见列级要求包括 `NOT NULL`、`UNIQUE` 和 `CHECK`。

* **列级约束**

    * `NOT NULL` 要求属性值非空。

    * `UNIQUE` 要求属性值唯一。

    * `CHECK` 在括号中写入布尔条件，条件为真才允许数据进入。

* **`CHECK` 条件**

```text
CHECK (Ssex IN ('男', '女'))

CHECK (Grade >= 0 AND Grade <= 100)

CHECK (Grade BETWEEN 0 AND 100)
```

    * `IN` 用于把属性值限制在给定常量集合中。

    * `BETWEEN ... AND ...` 用于限制闭区间中的数值。

    * `LIKE` 用于按字符串模式匹配，`%` 代表任意长度内容，`_` 代表一个字符位置。

* **数据类型与业务条件**

    * `SMALLINT` 只能保证成绩是整数，不能保证成绩在 0 至 100 之间。

    * 合法成绩范围仍需通过 `CHECK (Grade >= 0 AND Grade <= 100)` 表达。

    * 数据类型约束与业务约束分别负责取值形态和业务语义，不能互相替代。

* **表级跨列检查**

```text
CHECK (Ssex = '女' OR Sname NOT LIKE 'Ms.%')

CHECK (Salary + Deduct >= 30000)
```

    * 当判断同时依赖 `Ssex` 与 `Sname` 时，条件应作为表级 `CHECK` 写在表定义末尾。

    * 当扣除项以负数记录时，应发工资为 `Salary + Deduct`，检查条件检查的是整条记录而非单个格子。

    * 判断只依赖一个属性时写成列级条件，依赖多个属性组合关系时写成表级条件。

* **约束命名**

    * 标准形式为 `CONSTRAINT <约束名> <完整性约束条件>`。

    * 约束条件可以是 `NOT NULL`、`UNIQUE`、`PRIMARY KEY`、`FOREIGN KEY` 或 `CHECK`。

    * 约束名只是管理标签，真正决定行为的是后面的约束条件。

    * 命名后可以精确删除或重建复杂约束，也便于其他维护人员理解规则用途。

### 约束维护

* **约束修改**

    * 业务规则变化时，使用 DDL 语句 `ALTER TABLE` 维护表结构中的完整性约束。

    * 修改约束的可靠做法是先删除旧约束，再添加新约束，避免旧规则残留。

    * 例如将年龄限制由小于 30 改为小于 40 时，先删除旧约束，再以同一名称或新名称添加新约束。

* **删除与添加约束**

```sql
ALTER TABLE Student
DROP CONSTRAINT C4;
```

    * `DROP CONSTRAINT C4` 只删除名称为 `C4` 的约束。

    * 复杂约束如果未命名，就难以用简短、精确的语句指定删除目标。

## 断言

### 一般性完整性约束

* **断言（Assertion）**

    * > **定义**：使用 `CREATE ASSERTION` 指定、可以涉及多个关系并可包含聚集操作的一般性完整性约束。

    * 断言涉及的关系被操作时，数据库会检查断言条件。

    * 任何使断言条件变为假值的操作都会被拒绝执行。

    * 断言适用于跨表、含聚集运算或比列级 `CHECK` 更一般的完整性条件。

* **断言定义**

```sql
CREATE ASSERTION <断言名>
CHECK (<约束条件>);
```

    * `CREATE ASSERTION` 后给出断言名称，`CHECK` 中给出必须始终为真的条件。

    * 断言名称应清楚体现涉及对象和限制内容，以保持规则可读性并支持后续精确删除。

    * 断言越复杂，检测和维护开销越高。

* **单门课程选课人数限制**

```sql
CREATE ASSERTION ASSE_SC_DATABASE_NUMBER
CHECK (
    60 >= (
        SELECT COUNT(*)
        FROM SC, Course
        WHERE SC.Cno = Course.Cno
          AND Course.Cname = '数据库'
    )
);
```

    * 先通过课程编号连接 `SC` 与 `Course`，再筛选课程名为“数据库”的记录。

    * `COUNT(*)` 统计符合条件的选课记录数，断言要求统计结果不超过 60。

    * 第 61 名学生选课时，`60 >= 61` 为假，数据库拒绝该次选课。

    * 单门课程限制只需统计指定课程，不能用整个 `SC` 表的记录总数代替。

* **所有课程的分组限制**

```sql
CREATE ASSERTION ASSE_SC_CNUMBER_NUMBER
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno
    )
);
```

    * 按课程编号 `Cno` 分组后，`COUNT(*)` 分别统计每门课程的选课人数。

    * `60 >= ALL (...)` 要求每一个课程组的统计结果都不超过 60。

    * 任意一门课程超过 60 人，整个断言条件即为假。

* **按学期和课程分组限制**

```sql
ALTER TABLE SC ADD Term DATE;

CREATE ASSERTION ASSE_SC_CNUMBER_TERM_NUMBER
CHECK (
    60 >= ALL (
        SELECT COUNT(*)
        FROM SC
        GROUP BY Cno, Term
    )
);
```

    * 先给 `SC` 增加学期字段 `Term`，再同时按 `Cno` 与 `Term` 分组。

    * 每个分组表示同一学期、同一门课程的选课记录，数据库分别检查每组人数是否不超过 60。

* **删除断言**

```sql
DROP ASSERTION <断言名>;
```

    * 删除时直接使用创建断言时给出的名称。

    * 断言负责复杂条件下的判断与拒绝，不负责自动修改数据或生成审计记录。

## 触发器

### 事件驱动的完整性控制

* **触发器（Trigger）**

    * > **定义**：定义在关系表上、由特定事件驱动，并在条件满足时执行预先安排动作的特殊过程。

    * 触发器保存在数据库服务器中，由 `INSERT`、`DELETE` 或 `UPDATE` 事件自动激活。

    * 触发器可以用 `event`、`condition`、`action` 三个要素表达：事件发生后检查条件，条件为真才执行过程块或调用存储过程。

    * 断言回答条件还能否成立，触发器还要决定条件成立以后数据库执行什么动作。

    * 基础 `CHECK` 负责简单条件，断言负责复杂条件下的拒绝，触发器负责事件后的自动处理和留痕。

* **触发器定义**

```sql
CREATE TRIGGER <触发器名>
{BEFORE | AFTER} <触发事件> ON <基本表>
[REFERENCING
    [NEW ROW | NEW TABLE] AS <新值变量>
    [OLD ROW | OLD TABLE] AS <旧值变量>]
[FOR EACH {ROW | STATEMENT}]
[WHEN <触发条件>]
<触发动作体>;
```

    * `BEFORE` 与 `AFTER` 指定数据库执行过程中的触发时机。

    * 触发事件可以是 `INSERT`、`DELETE`、`UPDATE`，也可以是这些事件的组合。

    * `UPDATE OF Grade` 把更新事件缩小到 `Grade` 列；`UPDATE ON SC` 关注整张成绩表的更新。

    * `REFERENCING` 引入操作前后的数据，变量既可以表示行、元组或字段，也可以表示整张表。

    * `FOR EACH ROW` 逐行处理，`FOR EACH STATEMENT` 在整条语句执行后处理一次。

    * `WHEN` 是可选条件；条件为真才执行动作，省略时事件一激活就执行动作体。

    * `new` 与 `old` 主要用于行级触发器比较同一行的新旧值。

* **时机、范围与失败处理**

    * `AFTER` 在事件完成之后触发，适合记录修改前后值等后续动作。

    * `BEFORE` 在数据进入计算机后的数据库真正执行更新之前触发，不是键盘输入之前。

    * 对含 1000 行的表执行一次批量更新，语句级触发器动作一次，行级触发器可能动作 1000 次。

    * 触发动作执行失败时，触发事件终止执行，目标对象及触发器影响的其他对象都不发生变化。

* **定义与执行边界**

    * 触发器必须由表的拥有者创建，触发器与所依附的表应处于同一模式。

    * 触发器名称在同一数据库框架下必须唯一。

    * 触发器只能定义在基本表上，不能定义在视图上。

    * 同一张表存在多个触发器时，顺序为先执行 `BEFORE` 类触发器，再执行 SQL 语句，最后执行 `AFTER` 类触发器。

    * 不同数据库产品的触发器语法可能不同，实际使用时应以所用软件的说明书为准。

### 触发器应用

* **成绩大幅变化审计**

```sql
CREATE TRIGGER SC_T
AFTER UPDATE OF Grade ON SC
REFERENCING
    OLD ROW AS OldTuple
    NEW ROW AS NewTuple
FOR EACH ROW
WHEN NewTuple.Grade >= 1.1 * OldTuple.Grade
INSERT INTO <成绩变化记录表>
    (<学号>, <课程编号>, <旧成绩>, <新成绩>)
VALUES
    (OldTuple.Sno, OldTuple.Cno, OldTuple.Grade, NewTuple.Grade);
```

    * 事件是成绩表 `Grade` 列更新，触发时机为更新后，处理范围为每一行。

    * `OldTuple` 保存旧行，`NewTuple` 保存新行，可直接比较新旧成绩。

    * 新成绩达到旧成绩的 1.1 倍时，向记录表插入学号、课程编号、旧成绩和新成绩。

    * 长文未说明记录表及其四个字段的具体名称，因此相关名称只能保留为占位符。

* **插入后统计学生行数**

```sql
CREATE TRIGGER <触发器名>
AFTER INSERT ON Student
REFERENCING NEW TABLE AS delta
FOR EACH STATEMENT
INSERT INTO insert_log
SELECT COUNT(*) FROM delta;
```

    * 语句级触发器把整个插入操作后的 `Student` 新表引入为 `delta`。

    * `COUNT(*) FROM delta` 统计的是操作完成后的学生表总行数，不是本次新增行数。

    * 例如原有 50 名学生，一次插入后变为 70 名时记录 70；下一次变为 80 名时记录 80。

    * > **易错点**：此例记录的是操作后新表的行数，不能把 70、80 改写成本次新增的 20、10。

* **更新前修正教授工资**

```sql
CREATE TRIGGER <触发器名>
BEFORE INSERT OR UPDATE OF Salary ON teacher
FOR EACH ROW
BEGIN
    IF new.job = '教授' AND new.salary < 40000 THEN
        new.salary := 40000;
    END IF;
END;
```

    * 事件为插入或更新工资，触发时机为写入前，触发范围为每一行。

    * 新行职称为教授且工资低于 40000 时，赋值语句把新工资改为 40000。

    * 动作只需检查新记录，因此无须为了形式完整而强行引用旧记录变量。

    * 断言只能拒绝低于 40000 的工资，不能替用户自动把新工资修正为 40000。

* **删除与重建触发器**

```sql
DROP TRIGGER <触发器名> ON Student;
```

    * 删除时使用创建时给出的触发器名称和依附表。

    * 只有已创建的触发器才能删除，且用户必须具备相应权限。

    * 需要改变事件、条件、范围或动作时，删除后重新创建通常比直接修改更清楚。
