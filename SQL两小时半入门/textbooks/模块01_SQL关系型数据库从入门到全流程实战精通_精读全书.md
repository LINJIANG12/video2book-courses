## 关系型数据库基础与 MySQL 入门实操
> 对应块：BLK01 | 覆盖分集：P01上 | 块标题（分集名）：《SQL入门到精通》

无论你们未来是想开发网络游戏、搭建 Web 网站，还是开发手机移动应用，在处理业务持久化需求时，有极大概率都会接触并使用数据库。很多人觉得数据库高深莫测，其实回归本质，它就是一个存放数据的地方。

人类的大脑也是一个数据库，我们可以把知识和经历存进记忆里；一本书、一张草稿纸同样是数据库，文字记录在上面就能被保存。然而，人脑作为数据库致命的短板在于容量有限，能记住的信息极少；纸张与书本虽然能记录大量内容，但当数据规模膨胀到成千上万条时，想要从中找出某一条特定记录，必须逐页翻阅，检索效率极低。

现代应用（例如像视频流媒体平台）需要存储海量的视频元信息、用户凭证与播放记录，同时还必须满足全局搜索栏毫秒级的即时响应。要同时实现“海量存储”与“极致速度”，就必须借助计算机，并且不能把数据杂乱无章地随意丢进磁盘，而是要经过规范化、结构化的组织整理。

### 数据库与数据库管理系统

在开发软件时，我们不需要自己从零手写一套复杂的数据索引与排序算法来整理磁盘数据。工业界早已演化出一系列成熟的基础软件来接管这套工作。

#### 数据持久化介质演进

从人脑的瞬时记忆，到纸张的物理记录，再到现代磁盘存储，持久化介质的演进核心围绕“容量”与“检索效率”两个维度展开：

- **记忆型介质**：容量极低，易受遗忘干扰，但交互延迟最低；
- **平面物理介质**：容量可随纸张堆叠扩展，但缺乏动态索引支持，线性检索复杂度过高；
- **结构化电子存储**：依托高速磁盘与内存缓存，借助多维索引结构，在保障百亿级数据吞吐的同时实现对数级甚至常数级的检索响应。

#### 数据库管理系统与访问交互

这些专门负责对底层数据执行结构化整理、落盘存储并对外提供高效检索调度的软件，统称为“数据库管理系统（Database Management System，DBMS）”。

有了 DBMS 作为中间层调度者，应用程序与底层数据之间的所有读写与检索交互都变得清晰高效。以视频网站检索内容为例：当用户在搜索栏输入目标关键词“小白”时，网站的前端与后端业务系统不会直接去物理磁盘里扫描文件，而是向底层的 DBMS 发送查询请求：“请帮我找出所有标题或标签包含‘小白’的视频信息”。

```text
+-------------------+           +-------------------------------------+           +------------------------+
| 应用程序 / Web 平台 | --------> | 数据库管理系统 (DBMS, 如 MySQL)        | --------> | 物理存储底座 (Database)  |
| (如搜索视频 "小白") | <-------- | (基于索引结构秒级检索目标数据并返回) | <-------- | (持久化存放数十亿条记录) |
+-------------------+           +-------------------------------------+           +------------------------+
```
上图展示了现代应用程序、数据库管理系统（DBMS）与底层物理数据库之间的三层解耦交互链路。

DBMS 接收到请求后，会利用预先构建好的索引体系，在数以亿计的视频记录库中以极高的效率精准定位目标，并将结构化结果装配返回给业务层。用户上传视频（新增数据）、修改简介（更新数据）或者下架视频（删除数据）的流程完全一致——业务平台向 DBMS 派发增、删、改指令，由 DBMS 保证底层数据落盘的准确性与高性能。

> **定义**：数据库管理系统（Database Management System，DBMS）是操纵和管理底层物理数据库的系统级软件，负责数据的组织、存储、高效检索、并发控制以及完整性保护。

### 关系型与非关系型数据库架构分类

目前市面上的 DBMS 软件种类繁多，不同软件底层整理与归纳数据的数据结构大相径庭，对应的存储形态与适用场景也各不相同。根据数据建模方式的核心差异，数据库主要划分为两大阵营。

#### 关系型数据库及其管理系统

关系型数据库（Relational Database）通常也被直接称为 SQL 数据库（SQL 可读作“sequel”）。其核心特征在于：**将所有业务数据规整地存放在一张张二维表格中，并通过公共属性将表格与表格之间关联起来**。

> **定义**：关系型数据库管理系统（Relational Database Management System，RDBMS）是指基于关系模型建立的数据库系统，通过行列构成的表格组织数据，利用键约束维护表间关联。

业界代表性的 RDBMS 软件包括：
- **MySQL**：开源、流行度极高、社区生态庞大；
- **Oracle**：商业级数据库巨头，承载大量金融及电信级企业核心系统；
- **PostgreSQL**：功能极其强大、高度遵循 SQL 标准的开源对象关系型系统；
- **SQL Server**：微软开发的企业级关系型数据库解决方案。

#### 非关系型数据库及其存储形态

非关系型数据库通常被称为 NoSQL，现代含义演化为“Not Only SQL”。它并不是一种单一的架构模式，而是一个统称分类——只要没有采用传统的“二维表格加外键关联”模式来组织数据的数据库系统，均归入此类。

非关系型数据库的数据存储形式多种多样，各软件根据其针对的特定读写场景深度优化：
- **文档型存储**：将整条数据打包为 JSON、BSON 等格式的文件进行存放；
- **图形存储（Graph）**：通过节点与边存储高度复杂的拓扑网络与图谱关系；
- **键值对存储（Key-Value）**：采用简单的键值映射结构实现极致的内存级读写性能。

业界代表性的非关系型数据库管理系统（Non-relational Database Management System，NRDBMS）包括：
- **MongoDB**：主流的文档型数据库，适合存储半结构化数据；
- **Redis**：基于内存的高性能键值存储系统，广泛用于缓存与高并发场景；
- **DynamoDB**：分布式键值与文档型数据库托管服务；
- **Elasticsearch**：面向文本与日志的高性能分布式全文搜索引擎。

| 架构分类 | 组织形态与存储方式 | 通信控制规范 | 核心代表产品 |
| :--- | :--- | :--- | :--- |
| **关系型数据库（RDBMS）** | 二维表格（Table）、主外键关联合约 | 统一遵循标准 SQL 语言交互 | MySQL、Oracle、PostgreSQL、SQL Server |
| **非关系型数据库（NRDBMS）** | 键值（KV）、文档（JSON）、图形拓扑等多态结构 | 各软件自研专用 API 或专用命令集 | MongoDB、Redis、DynamoDB、Elasticsearch |

#### 结构化查询语言的通信定位

我们这门课程的主角是 SQL，全称为结构化查询语言（Structured Query Language）。

请注意其中的“语言”二字——SQL 本质上就是一种专门用于人（或应用程序）与关系型数据库管理系统之间沟通的标准语言。无论业务端采用何种开发语言，当平台需要从底层关系型数据库调取数据时，业务平台必须通过标准 SQL 向 RDBMS 发出指令，RDBMS 解析该 SQL 并执行具体物理操作。

> **注意**：非关系型数据库并没有一个全球统一的交互语言。如果需要操作 MongoDB，就必须编写 MongoDB 专有的查询指令与驱动语法；如果要操作 Redis，则需要使用 Redis 专有的键值操作命令。而在关系型领域，只要熟练掌握了 SQL，就能驱动市面上绝大多数关系型数据库。

通过 SQL 语言，我们能够指示 RDBMS 完成以下核心工作：
- 数据库与数据表的创建、修改与物理销毁（DDL）；
- 业务数据的查询、新增、修改与删除（DML）；
- 数据库访问用户、角色与执行权限的安全控制（DCL）。

### MySQL 与客户端工具安装配置

为了在实践中快速掌握 SQL 语言，我们选用 MySQL 作为教学引擎。

#### 运行环境选型与组件定制

市面上优秀的 RDBMS 很多，之所以选择 MySQL，是因为它拥有完全免费开源的社区版（Community Edition），并且是全球范围内受众最广、各大互联网大厂使用最普遍的关系型数据库系统。

> **提示**：虽然 SQL 存在 ANSI/ISO 行业标准规范，但在不同的数据库管理系统之间，各厂商在标准之上都加入了细微的方言差异（Dialect）。但请不必担心，SQL 最底层的数据定义、增删改查逻辑与关联模型在各大数据库中高度通用，在 MySQL 中练就的核心能力可以无缝平移至其他系统。

在安装 MySQL 时，我们不需要把安装包内所有复杂的辅助组件全部装上，针对常规开发，只需要锁定三项核心组件：
1. **MySQL Server（推荐 8.0 系列最新版）**：真正提供数据库底层持久化与计算服务的后台服务端引擎；
2. **MySQL Workbench**：官方提供的可视化图形界面（GUI）客户端，用于连接 Server、编写并执行 SQL 脚本；
3. **MySQL Shell**：官方命令行高级交互终端工具。

#### 跨平台安装要点与 Workbench 连接

针对 Windows 与 macOS 两类常用操作系统，安装流程与环境适配要点如下：

##### Windows 环境安装要点
1. 访问官方站点检索 `MySQL Community Downloads`，选择进入 `MySQL Installer for Windows`；
2. 在安装包列表中选择体积较大的独立完整安装包（离线版），跳过注册/登录步骤，直接点击底部的 `No thanks, just start my download.`；
3. 启动安装程序后，安装类型**务必选择 Custom（自定义安装）**，避免默认模式安装海量冗余组件；
4. 在组件选择树中展开并添加：
   - `MySQL Servers` -> `MySQL Server 8.0`（选择最新发布版本）；
   - `Applications` -> `MySQL Workbench 8.0`（选择最新版本）；
   - `Applications` -> `MySQL Shell 8.0`（选择最新版本）；
5. 点击 `Execute` 依次下载安装；随后的配置向导中网络端口与服务名均保持默认配置即可；
6. 在账户安全配置阶段，系统会强制要求设置数据库系统管理员（`root`）的访问密码。**该密码务必妥善记录**，后续所有客户端连接均需要凭此鉴权。

##### macOS 环境安装要点
1. 在官网下载页选择 `MySQL Community Server`；
2. **重点确认 CPU 架构体系**：在操作系统的“Select OS Version”下拉框中，如果当前 Mac 搭载的是 Apple Silicon 系列芯片（M1/M2/M3 等），务必下载并安装 **ARM** 架构版本；如果使用的是 Intel 处理器，则选择 **x86** 架构版本。
   若无法确认自身硬件，可点击屏幕左上角的 Apple 标志进入“关于本机（About This Mac）”，查看“处理器”或“芯片”一栏标识；
3. 下载对应的 `.dmg` 镜像文件挂载安装，按向导执行，并在安装结束前设置好数据库 root 管理员密码；
4. 返回官网下载页另行下载并安装独立安装包 `MySQL Workbench`（将应用图标拖入 `Applications` 文件夹）；
5. 若首次启动 Workbench 触发 macOS 系统安全性拦截弹窗提示“无法打开”，可在访达中进入“应用程序”，右键点击该应用图标，在右键菜单中选择“打开”，即可解除门禁限制。

##### Workbench 工作区初始化与连接验证
启动 MySQL Workbench 后，主界面默认会展示一个预置的本地连接卡片（`Local instance MySQL`）。双击该卡片，在密码输入框中填入安装时设置的管理员密码，即可建立与后台 Server 的通信会话。

若初始界面未检测到默认连接，可点击连接栏右侧的加号按钮 `+` 自行新建：
1. 设置 `Connection Name`（例如填入 `local`）；
2. 主机名与端口保持默认的 `127.0.0.1` 与 `3306`；
3. 点击右下角 `Test Connection` 按钮，输入 root 密码，系统提示连接成功后点击 `OK` 保存。

进入 SQL 编辑器工作区后，右上角提供了三个面板折叠控制按钮，分别对应左侧导航区（Schemas / Management）、底部执行控制台（Action Output）和右侧辅助栏。在日常 SQL 编写与学习阶段，**可直接将左侧与右侧栏目折叠收起**，最大限度为中央的 SQL 代码编写区腾出视野。

在执行 SQL 语句时，工具栏提供了两种执行闪电：
- **纯黄色闪电（左侧）**：执行编辑器中被鼠标完整选中的整段脚本，若未选中任何内容则自顶向下执行整个文本区的全部代码；
- **带有光标图标的闪电（右侧）**：仅执行当前文本输入光标所在的那一条单独 SQL 语句。

### 关系模型与键约束机制

理解关系型数据库的核心，在于搞清楚二维表格的几何构造以及如何利用各类“键（Key）”在离散的数据表之间拉起业务纽带。

#### 表格结构与主键唯一性约束

在关系型数据库中，每一个实体集合都会被设计成一张独立的数据表（Table）。表格的形态与我们日常使用的 Excel 表格极其相似：
- **行（Row）**：横向的一整行代表系统中**单独一条完整的数据记录**；
- **列（Column / Attribute）**：纵向的一整列代表某项特定的**属性字段**。

以记录学校在校学生信息的场景为例，我们可以设计一张名为 `student` 的学生表，其属性规划包括学号（`student_id`）、姓名（`name`）与主修专业（`major`）：

```text
+---------------------+-------------------+---------------------+
| student_id (主键 PK) | name              | major               |
+---------------------+-------------------+---------------------+
| 1                   | 小黑              | 生物                |
| 2                   | 小白              | 历史                |
| 3                   | 小白              | 历史                |
| 4                   | 小黄              | 物理                |
| 5                   | 小红              | 化学                |
+---------------------+-------------------+---------------------+
```
上图展示了学生实体表的基本行列划分，其中第 2 行与第 3 行记录在业务属性上完全重名重专业。

观察上述数据，学号为 2 与学号为 3 的两位学生，其姓名均为“小白”，主修专业均为“历史”。现实中重名重专业的情况屡见不鲜，如果仅凭姓名或专业去定位某位同学，系统将陷入逻辑混乱，无法区分到底是哪一位学生。

为了唯一标定表中的每一行数据，我们必须将具备唯一性特性的列指定为**主键（Primary Key，PK）**。在此表中，我们将 `student_id` 设为主键。

> **定义**：主键（Primary Key，PK）是表中用于唯一标识每一条数据记录的一个或一组属性。主键列的值必须在全表范围内绝对唯一，严禁出现重复值，且不允许为 NULL。

只要确立了主键，在执行数据检索或更新操作时，精准指定 `student_id = 2` 就必定只能命中唯一确定的那一位学生。在后续的数据表设计中，无论是系统用户表以 `email`（邮箱天然不重复）作为主键，还是员工表以工号 `emp_id` 作为主键，第一步永远是为表格确立主键约束。

#### 外键参照与跨表关联机制

真实世界中的业务实体往往不是孤立存在的。假设一家企业不仅需要管理员工信息，还需要管理部门信息，系统通常会拆分建立两张实体表：
- **员工表（employee）**：包含员工工号（`emp_id`，PK）、姓名（`name`）、出生日期（`birth_date`）、性别（`sex`）、薪资（`salary`）；
- **部门表（branch）**：包含部门编号（`branch_id`，PK）、部门名称（`branch_name`）。

如果系统想要明确记录“某位员工隶属于哪一个具体的部门”，最直观的做法是在员工表中额外新增一个属性列 `branch_id`，并将其定义为**外键（Foreign Key，FK）**，使其精确指向部门表的主键 `branch_id`。

同理，若要记录“各个部门的部门经理是哪一位员工”，可以在部门表中新增一个名为 `manager_id` 的属性列，同样将其设定为外键，反向指向员工表的主键 `emp_id`。

```text
  员工表 (employee)                                    部门表 (branch)
+--------+------+----------+--------+                +-----------+-------------+------------+
| emp_id | name | ...      | branch_id (FK) |  +-------> | branch_id | branch_name | manager_id |
| (PK)   |      |          |        |        | |  (PK)   |             | (FK)       |
+--------+------+----------+--------+        | |     +-----------+-------------+------------+
| 206    | 小黄 | ...      | 1      | --------+ |     | 1         | 研发部      | 206        | -----+
| 207    | 小绿 | ...      | 2      | --------|-+     | 2         | 行政部      | 207        | ---+ |
+--------+------+----------+--------+         |       +-----------+-------------+------------+    | |
    ^                                         |                                                   | |
    +-----------------------------------------|---------------------------------------------------+ |
    +-----------------------------------------+-----------------------------------------------------+
```
上图展示了员工表与部门表之间通过外键建立的双向参照逻辑：员工表通过外键 `branch_id` 关联部门归属，部门表通过外键 `manager_id` 关联负责人信息。

> **定义**：外键（Foreign Key，FK）是数据表中的一个属性列，其取值必须严格引用并参照另一张表（或自身表）的主键值，用于在多表之间建立严密的逻辑关联并维护参照完整性。

为什么外键必须强制对应目标表的主键？
请设想：如果员工表的 `branch_id` 指向的不是部门表的主键，而是某个允许重复的普通列，那么部门表中一旦同时出现两条 `branch_id = 1` 的记录，当员工小黄标明自己属于 1 号部门时，系统将根本无法判断他究竟属于哪一个具体的研发部门。因此，**外键有且仅能引用具备绝对唯一性保障的主键列**。

#### 自引用外键与层级关系表示

外键并非只能指向外部数据表，在树状层级或上下级汇报体系中，外键完全可以指向**自身表格的主键**，这种设计模式称为自引用外键（Self-referencing Foreign Key）。

以员工的管理汇报链条为例：每位员工都有直属上级主管。我们可以在员工表内扩充一个属性列 `sup_id`（即主管工号 supervisor_id），并将其设为外键，指向员工表自身的 `emp_id` 列：
- 员工小绿的 `sup_id` 为 206，对照本表内 `emp_id = 206` 的记录，可知其主管是小黄；
- 员工小黑的 `sup_id` 同样是 206，其主管也是小黄；
- 员工小蓝的 `sup_id` 为 207，对照可知其主管是小绿；
- 员工小黄的 `sup_id` 为 `NULL`，表明小黄处于公司最高领导地位，没有上级主管。

```text
员工表内部自引用机制 (employee):
+--------+------+---------------+
| emp_id | name | sup_id (FK)   |
| (PK)   |      | (引用本表主键) |
+--------+------+---------------+
| 206    | 小黄 | NULL (无主管) | <-------+
| 207    | 小绿 | 206           | --------+ (上级是小黄)
| 208    | 小黑 | 206           | --------+ (上级是小黄)
| 209    | 小蓝 | 207           | --------+ (上级是小绿，指向 207)
+--------+------+---------------+
```
上图展示了利用自引用外键在同一张数据表内部构建上下级管理树状层级的结构机理。

#### 复合主键与主外键重叠设计

在某些高阶业务关联表中，单一属性往往无法支撑起主键的唯一性要求。

考虑业务明细表 `works_with`，该表用于登记“哪位员工对接了哪位客户，并达成了多少销售金额”，包含三个字段：员工工号（`emp_id`）、客户编号（`client_id`）与销售总金额（`total_sales`）。
分析业务特征会发现：
- 每一位员工可能同时服务多个客户，因此 `emp_id` 会出现重复值；
- 每一个客户也可能由不同员工协同服务，因此 `client_id` 也会出现重复值；
- 销售金额更属于易变指标，极大概率存在重合。

任何单一字段都无法承担主键角色。此时必须将 `emp_id` 与 `client_id` **联合捆绑在一起，共同定义为一个主键**，这被称为复合主键（Composite Primary Key）。

```text
业务对接表 (works_with):
+--------------+----------------+-------------+
| emp_id       | client_id      | total_sales |
| (联合主键 PK / | (联合主键 PK / |             |
|  员工表 FK)   |  客户表 FK)    |             |
+--------------+----------------+-------------+
| 206          | 400            | 55000       |
| 206          | 401            | 267000      |
| 207          | 400            | 12000       |
+--------------+----------------+-------------+
```
上图展示了复合主键的协同约束机制：允许单一属性列分别重复，但两列的二元组组合在全表中必须绝对唯一。

在复合主键约束下，第一条记录为 `(206, 400)`，后续数据可以继续插入 `(206, 401)` 或 `(207, 400)`，但绝对不允许再次插入一条同样是员工 206 服务客户 400 的记录。若双字段组合依然可能重叠，还可根据实际业务进一步扩充为由三个或四个字段构成的复合主键。

更值得关注的是：在这张表里，`emp_id` 既是本表复合主键的组成部分，同时又是引用员工表主键的外键；`client_id` 同样既是复合主键的一部分，又是引用客户表主键的外键。
这表明：**数据表中的某一个列，完全可以同时身兼“主键”与“外键”双重角色**。关系型数据库的数据模型既可以设计得极其简练，也可以通过交错的多表外键与多维复合主键构建起异常精密的业务拓扑网络。

### SQL 基础语法规范与库级管理

完成概念建模后，必须通过具体的 SQL 语句落实为物理数据库对象。

#### 语法编写惯例与反引号规避冲突

在 MySQL 中编写 SQL 指令时，必须恪守以下基础语法规约：

1. **关键字大小写规范**：
   在 SQL 中，诸如 `CREATE`、`DATABASE`、`SHOW`、`DROP`、`USE` 等保留关键字在语法引擎层面并不区分大小写，写成小写 `create` 系统同样可以解析执行。但**工程标准惯例统一使用纯大写英文字母书写关键字**。Workbench 等现代化编辑器会将关键字自动高亮为蓝色；保留字大写能够与业务字段形成极具辨识度的视觉切割，极大提高代码可读性。
2. **自定义命名的反引号转义**：
   由开发者自行命名的对象名称（如数据库名、数据表名、属性列名等）习惯使用纯小写书写，并且**强烈建议统一使用一对反引号（backtick，即键盘 ESC 键正下方的符号 \`）将其包裹起来**。
   使用反引号的核心价值在于：**彻底避免自定义对象名与数据库内置保留关键字发生语法冲突**。
   举一个反面典型：假设你想创建一个名字就叫作 `database` 的数据库，如果直接裸写：
   ```sql
   CREATE DATABASE database;
   ```
   MySQL 解析器在读取第二个单词时会将其识别为语法声明关键字，而读到第三个单词时又遇到了保留字 `database`，解析器无法理解该结构，会当场抛出语法错误中断执行。
   若使用反引号显式界定边界：
   ```sql
   CREATE DATABASE `database`;
   ```
   反引号明确告知引擎：包裹在内的是一个不可分割的标识符实体，而非语法关键字，语句即可顺利编译通过。
3. **指令终结符**：
   每一条独立的 SQL 指令，其末尾**必须以英文半角分号（`;`）闭合**，以此标示该语句语法块的正式终结。

#### 数据库生命周期管理指令

在创建具体的数据表之前，第一步必须在宿主服务中开辟出一个专属的逻辑数据库空间。

##### 创建数据库
使用 `CREATE DATABASE` 指令创建新的逻辑数据库容器：
```sql
CREATE DATABASE `sql_tutorial`;
```
该指令指示 MySQL 服务端开辟一个名为 `sql_tutorial` 的独立数据库命名空间。

##### 检索数据库列表
创建完毕后，可利用 `SHOW DATABASES;` 指令检索当前连接实例下挂载的所有数据库：
```sql
SHOW DATABASES;
```
执行后结果集面板将输出全部数据库清单。除刚创建的 `sql_tutorial` 外，清单中还会包含系统默认初始化的内部审计与性能监控数据库，学习期间无需理会系统自带库。

##### 切换当前工作数据库
在向数据库内建表之前，必须先通过 `USE` 指令选定当前操作的工作上下文：
```sql
USE `sql_tutorial`;
```
由于一个 MySQL 实例内通常托管着多个独立的业务数据库，执行 `USE` 是为了明确告知服务端引擎：后续执行的所有建表、建索引或数据操作，一律生效在该数据库内部。

##### 物理删除数据库
当需要清理丢弃整个数据库及其名下所有数据表与索引时，使用 `DROP DATABASE` 指令：
```sql
DROP DATABASE `database`;
DROP DATABASE `sql_tutorial`;
```
执行物理销毁后再次运行 `SHOW DATABASES;`，目标数据库将彻底从全局列表中消失。

> **易错点**：执行 `DROP DATABASE` 属于高危不可逆操作，被删除库内部所有的结构定义与全部业务数据都将被彻底清除。

### MySQL 核心数据类型

在关系模型中，创建数据表必须为每一个列定义其物理存储属性，即“数据类型（Data Type）”。数据类型决定了字段能承载何种形态的数据，也直接影响底层磁盘空间分配与计算性能。

掌握以下六种最核心、最常见的数据类型，即可应对日常绝大部分业务开发需求：

#### 数值与文本数据类型

1. **整数型 `INT`**：
   专门用于存放标准整数字面量，能够合法存储正整数、0 以及负整数（例如 `0`, `1`, `2`, `-100` 等）。用于主键 ID、年龄、数量等无需小数点的业务指标。
2. **定点小数型 `DECIMAL(M, D)`**：
   用于精确存储带有小数点的数值。该类型必须在括号内传入两个关键精度参数：
   - 第一个参数 `M`（Precision，精度）：代表该数值**允许包含的最大有效数字总位数**；
   - 第二个参数 `D`（Scale，标度）：代表**小数点右侧必须保留的位数**。
   
   示例：若声明列类型为 `DECIMAL(3, 2)`，其含义为：该数值总共占 3 位数字，其中小数位占 2 位，整数位仅剩 1 位（$3 - 2 = 1$）。例如存入数值 `2.33` 即完全符合规范。常用于货币金额、绩点等对精度有严苛要求的场景。
3. **变长字符串型 `VARCHAR(M)`**：
   用于存放可变长度的纯文本字符串。必须传入参数 `M`，用于限制该字段**最多允许容纳的字符上限**。
   
   例如声明 `name VARCHAR(20)`，意味着该字段可以存储 0 到 20 个字符范围内的任意文本。虽然在语法层面设置成 `VARCHAR(10000)` 也不会报错，但工程实践上严禁滥用极端参数——业务上现实中几乎不可能存在长达一万字的人名，字段长度规划应严密贴合业务边界。

#### 二进制与时态数据类型

4. **二进制大对象 `BLOB`**：
   全称为 Binary Large Object，专门用于在数据库底层存储无结构的原始二进制数据块。主要用于直接承载文件流、图像元数据、短音频或可执行文件等非结构化媒介。
5. **纯日期型 `DATE`**：
   专门用于存放标准化日历日期。在 MySQL 中严格遵循标准的 `YYYY-MM-DD` 格式排布（年用 4 位表示，月份和天数必须补足 2 位，彼此用短横线隔开）。例如日期字面量必须书写为 `2021-08-08`。
6. **完整时间戳 `TIMESTAMP`**：
   专门用于记录精准到秒的时间轨迹。相比于 `DATE`，它在年月日的基础上进一步记录了具体的时、分、秒（格式形如 `YYYY-MM-DD HH:MM:SS`）。在工程架构中，该类型通常用于为数据表自动装配审计字段，如精准记录某一行数据是在何年何月何秒被创建、何时被修改或物理注销。

| 数据类型标识符 | 核心物理语义 | 参数要求与参数意义 | 典型数据样例 | 核心适用业务场景 |
| :--- | :--- | :--- | :--- | :--- |
| `INT` | 整数类型 | 无参数 | `1024`, `-50`, `0` | 主键标识符、序列号、计数器 |
| `DECIMAL(M, D)` | 高精度定点小数 | `M`：有效数字总位数；`D`：小数位数 | `DECIMAL(3, 2)` 存 `2.33` | 财务结算、商品金额、学业绩点 |
| `VARCHAR(M)` | 变长文本字符串 | `M`：最大允许字符长度上限 | `VARCHAR(20)` 存 `'小白'` | 用户姓名、登录账号、地址摘要 |
| `BLOB` | 二进制大对象 | 无必需长度参数 | 二进制原始文件流 | 物理图片存储、多媒体二进制流 |
| `DATE` | 离散日历日期 | 无参数（固定 `YYYY-MM-DD`） | `'2021-08-08'` | 出生日期、合同签署日、纪念日 |
| `TIMESTAMP` | 时分秒完整时间戳 | 无参数（含时分秒精度） | `'2021-08-08 14:30:00'` | 数据创建审计、状态流转时间追踪 |

### 数据表结构定义与模式变更

熟练掌握数据类型的规格后，我们即可通过数据定义语言（DDL）在数据库内部完成表的构建、元数据查验、结构热调整与最终销毁。

#### 数据表的创建与模式查看

在创建数据表之前，必须先通过 `USE` 锁定目标库：
```sql
USE `sql_tutorial`;
```

##### 创建数据表（CREATE TABLE）
现在我们正式创建前文规划的学生实体表 `student`，包含学号（整型主键）、姓名（20 字符变长文本）以及主修专业（20 字符变长文本）：

```sql
CREATE TABLE `student` (
    `student_id` INT PRIMARY KEY,
    `name` VARCHAR(20),
    `major` VARCHAR(20)
);
```

代码结构剖析：
- `CREATE TABLE` 为声明新建数据表的保留关键字，后接以反引号包裹的自定义表名 `student`；
- 所有属性字段的定义必须完整包裹在最外层的圆括号 `(...)` 之内；
- 括号内每一个字段的定义格式为：`列名` + `数据类型` + `可选约束属性`；
- 在 `student_id` 之后直接声明 `PRIMARY KEY`，指示底层引擎该列充当此表的主键；
- 字段与字段之间**必须使用英文逗号 `,` 分隔**；
- **注意最后一个字段（`major VARCHAR(20)`）之后绝对不能追加逗号**，否则会引发语法解析错误；
- 整个创建语句以分号 `;` 结尾。

##### 查看数据表元数据结构（DESCRIBE）
表创建成功后，若需检视该表在系统目录中的模式定义与字段规格，可执行 `DESCRIBE` 指令（亦可缩写为 `DESC`）：

```sql
DESCRIBE `student`;
```

执行后，结果集表格将清晰输出该表的元数据结构体系，包括：
- `Field`：属性字段名；
- `Type`：物理分配的数据类型与长度范围；
- `Null`：该列是否允许存入空值（主键列此处将明确显示为 `NO`）；
- `Key`：索引与键约束类型（主键列将标定为 `PRI`）；
- `Default`：未显式传值时的默认填充策略；
- `Extra`：附加扩展属性。

#### 数据表结构的动态变更与删除

软件上线后，业务需求变更是常态，经常需要对已有数据表的字段进行追加或移除。

##### 为数据表追加新字段（ALTER TABLE ... ADD）
假设业务需求变更，我们需要在已存在的 `student` 表中追加一个记录学生学业绩点的属性列 `GPA`，要求数值为三位数且包含两位小数：

```sql
ALTER TABLE `student` ADD `GPA` DECIMAL(3, 2);
```

语法解析：
- `ALTER TABLE` 声明修改指定表；
- 后接关键字 `ADD` 以及需要新增的完整字段声明：字段标识符 `` `GPA` `` 与其对应的数据类型 `DECIMAL(3, 2)`。

执行成功后，再次调用 `DESCRIBE `student`;`，即可在结果集末尾观察到新挂载的 `GPA` 属性。

##### 移除数据表已有字段（ALTER TABLE ... DROP COLUMN）
如果发现某个属性不再需要维护，可以使用 `DROP COLUMN` 语法将其从表结构中剥离：

```sql
ALTER TABLE `student` DROP COLUMN `GPA`;
```

语法解析：
- 将原先的 `ADD` 替换为 `DROP COLUMN`，后接目标列名 `` `GPA` ``。
- 执行该指令后，再次执行 `DESCRIBE `student`;`，可以看到 `GPA` 字段已被彻底抹除。

##### 物理销毁数据表（DROP TABLE）
当整张数据表已完成历史使命、不再需要保存结构与数据时，执行 `DROP TABLE` 将其从所属数据库中彻底移除：

```sql
DROP TABLE `student`;
```

执行删除后再尝试执行 `DESCRIBE `student`;`，MySQL 将直接抛出错误代码并提示表不存在（`Table 'sql_tutorial.student' doesn't exist`），证明物理表结构已被彻底注销。若需要继续后续实验，再次执行全量 `CREATE TABLE` 语句即可将初始表结构重新恢复。

## SQL核心数据操作与多表关系建模
> 对应块：BLK02 | 覆盖分集：P01中1 | 块标题（分集名）：《SQL入门到精通》

在上一次建立数据表结构时，我们已经在字段后方直接定义了主键。不过在真实写 SQL 时，主键还有另一种更为灵活独立的声明写法。建好表格骨架后，空表无法提供任何实际业务价值，我们必须将真实数据一条条存入数据库，并学会在数据出错时修改、废弃时清除，以及在海量记录中按需把想要的数据检索出来。更进一步地，实际业务从来不是一张单表就能搞定的，我们会面对员工、部门、客户、业务订单等错综复杂的多表关联体系，其中还会出现互相参照依赖的“死锁”现象。本篇讲义就从单表的数据存取、更新删除、约束定义起步，最终拆解一套完整的企业级多表关系数据库建模与数据初始化实战。

### 主键独立声明与数据写入基础

#### 主键约束的独立声明写法

在定义表结构时，除了在字段声明行后方直接标记 `PRIMARY KEY` 之外，还可以将主键约束单独提取出来，作为独立的约束声明写在所有属性定义的末尾：

```sql
CREATE TABLE student (
    student_id INT,
    name VARCHAR(20),
    major VARCHAR(20),
    PRIMARY KEY (student_id)
);
```

这种将 `PRIMARY KEY` 后置并用小括号包裹属性名 `(student_id)` 的写法，与直接跟在字段类型后声明是完全等价的。在定义复合主键（由多个属性共同组成主键）时，这种独立写法更是必不可少的标准格式。

#### 基础插入语法与列顺序映射

有了数据表结构之后，向表中灌入数据使用 `INSERT INTO` 语句。其核心语法由表名、`VALUES` 关键字以及紧随其后的小括号数据清单构成：

```sql
INSERT INTO student VALUES (1, '小白', '歷史');
```

执行后，我们通过查询全表来验证数据是否写入成功：

```sql
SELECT * FROM student;
```

这里的星号 `*` 代表获取该表格中的“全部属性”。执行后即可看到数据库回传了包含属性 `student_id` 为 1、`name` 为 `'小白'`、`major` 为 `'歷史'` 的单行记录。

向表中写入数据时，有几个非常关键的技术规范必须严格遵守：

1. **值列表与属性顺序严格对齐**：在不显式指定列名的情况下，`VALUES` 小括号内填入的数据顺序，必须严格按照创建表格时定义的属性先后次序逐一对应。建表时先声明 `student_id`，再声明 `name`，最后声明 `major`，那么插入时就必须是学号、姓名、主修。
2. **数据类型与字符字面量表示**：数值类型（如 `INT`）直接书写字面值，无需包裹；字符串类型（如 `VARCHAR`）必须使用英文成对引物包裹，单引号 `'...'` 或双引号 `"..."` 均可，在 SQL 编码规范中推荐统一使用单引号。
3. **分隔与结束标记**：值与值之间必须用半角英文逗号 `,` 分隔，整条 SQL 语句末尾务必加上分号 `;`。

接着存入第二笔数据：

```sql
INSERT INTO student VALUES (2, '小黑', '生物');
```

再次执行 `SELECT * FROM student;`，便能确认第二笔记录已准确入库。

#### 空值占位与主键冲突拦截

在实际业务录入时，难免会遇到某些属性暂时未知或客观不存在的情况。例如新招录的学生尚未确定主修专业，此时需要使用空值占位符 `NULL`：

```sql
INSERT INTO student VALUES (3, '小綠', NULL);
```

> **定义**：`NULL` 在 SQL 中代表“无数据”或“空值”，它既不是空字符串 `''`，也不是数值 0，而是一个表示数据缺失的特殊占位标识。

写入后全表查询，可以看到该行记录的 `major` 属性显示为空白或 `NULL`。

紧接着需要明确主键的硬性约束机制。主键是表中唯一标识每一笔记录的绝对依据，其属性值绝对不允许重复。如果我们尝试写入另一位同样将 `student_id` 设为 3 的记录：

```sql
INSERT INTO student VALUES (3, '小藍', '英語');
```

执行后系统会立即抛出错误中断执行。原因在于主键属性 3 已经被之前的记录占用，主键机制会自动拦截并阻断任何重复主键的写入请求。

#### 显式指定列名插入与默认值回退

在基础插入写法中，值的顺序完全被表结构的物理列顺序锁死。SQL 允许我们在表名后方添加小括号显式列出待插入的属性名，从而自主控制填入的字段顺序：

```sql
INSERT INTO student (name, major, student_id) VALUES ('小藍', '英語', 4);
```

在表名后显式声明了属性列列表后，`VALUES` 小括号内的值只需与前面声明的列表顺序一一匹配即可，不再受制于数据表创建时的原始字段次序。

这种写法还支持有选择性地插入指定列，忽略其他允许为空的属性：

```sql
INSERT INTO student (major, student_id) VALUES ('生物', 5);
```

在此语句中我们完全没有指定 `name` 属性。执行后查询全表，系统不仅顺利完成了写入，还自动将未指定的 `name` 属性赋予了默认的 `NULL` 值。这与显式在 `name` 处传 `NULL` 的执行效果完全一致。

### 列完整性约束配置

在建立数据表时，若不对属性做进一步的规则限定，使用者就可能灌入大量非法数据（如关键字段缺失、编号重合等）。约束（Constraints）就是我们在创建表格时附加在属性定义后方的检验规则。

为了演示各项约束的效果，先通过 `DROP TABLE student;` 清理旧表，再重新定义建表结构。

#### 非空与唯一约束

针对“字段必须有值”以及“字段值全表不可重复”两类最核心的数据完整性要求，SQL 分别提供了 `NOT NULL` 与 `UNIQUE` 约束：

```sql
CREATE TABLE student (
    student_id INT,
    name VARCHAR(20) NOT NULL,
    major VARCHAR(20) UNIQUE,
    PRIMARY KEY (student_id)
);
```

我们在 `name` 字段后追加了 `NOT NULL`，在 `major` 字段后追加了 `UNIQUE`。通过两组测试用例可直观验证其约束效力：

1. **非空拦截测试**：若试图执行 `INSERT INTO student VALUES (1, NULL, '英語');`，数据库会明确报错，因为 `name` 已声明非空，必须传入有效字串；将其更正为有效名称 `'小白'` 即可写入。
2. **唯一性冲突拦截测试**：在成功写入主修为 `'英語'` 的小白后，若第二名学生小黑同样提交 `'英語'` 作为主修：
   ```sql
   INSERT INTO student VALUES (2, '小黑', '英語');
   ```
   该操作会被数据库拦截报错。因为 `major` 属性被加持了 `UNIQUE` 约束，已有值 `'英語'` 无法再次复用；必须将小黑的主修更正为其他互不重复的值（如 `'歷史'`）方可成功落盘。

#### 默认值设定与主键自增机制

##### 预设默认值 DEFAULT

当某个属性在绝大多数业务场景下都具有确定值，或用户未填写时需要赋予合理兜底时，可以使用 `DEFAULT` 关键字：

```sql
CREATE TABLE student (
    student_id INT,
    name VARCHAR(20),
    major VARCHAR(20) DEFAULT '歷史',
    PRIMARY KEY (student_id)
);
```

在此结构下，如果插入记录时仅指定部分列，刻意忽略 `major` 属性：

```sql
INSERT INTO student (student_id, name) VALUES (1, '小白');
```

执行后查询全表，会发现虽然写入语句没有提及主修专业，但该学生的 `major` 属性已经被数据库自动填入了预设的 `'歷史'`，而不会像之前那样退化为 `NULL`。

##### 主键序列自增 AUTO_INCREMENT

在手工录入主键时，每次新增数据都要人工递增数值（1、2、3、4……），这在海量并发业务下极易产生计算冲突且维护成本极高。使用 `AUTO_INCREMENT` 可以让数据库引擎在每次写入新记录时自动在上一条记录的基础上累加 1：

```sql
CREATE TABLE student (
    student_id INT AUTO_INCREMENT,
    name VARCHAR(20),
    major VARCHAR(20),
    PRIMARY KEY (student_id)
);
```

引入自增约束后，后续执行写入操作时即可彻底免除 `student_id` 的显式传递：

```sql
INSERT INTO student (name, major) VALUES ('小白', '英語');
INSERT INTO student (name, major) VALUES ('小黑', '生物');
INSERT INTO student (name, major) VALUES ('小綠', '歷史');
```

查询全表，系统会自动为第一笔记录分配 ID 值为 1，第二笔自动分配 2，第三笔自动分配 3。数据库在底盘自主维护单调自增的主键序列号，彻底杜绝了人工干预带来的重复与错漏。

### 数据更新与物理删除控制

#### 安全更新模式配置

在对真实业务表进行变更与删除操作前，MySQL 默认开启的安全更新模式（Safe Updates）会阻止未带主键条件的批量更新和删除操作。在学习与测试环境中，需要先执行以下指令将该安全模式关闭：

```sql
SET sql_safe_updates = 0;
```

将 `sql_safe_updates` 设置为 0 意味着关闭限制，这样后续基于非主键条件的更新与删除练习才能够顺利执行。

为了后续演练，我们在 `student` 表中扩充一个用于记录分数的 `score` 整数列，并预置一组测试数据集：

```sql
CREATE TABLE student (
    student_id INT AUTO_INCREMENT,
    name VARCHAR(20),
    major VARCHAR(20),
    score INT,
    PRIMARY KEY (student_id)
);
```

假设表中当前已有 5 笔预置记录（分别包含学号 1 至 5，涵盖小灰、小黑、小绿等学生及对应专业和分数）。

#### 针对性数据更新操作

修改已有记录使用 `UPDATE` 指令。其核心结构是：指定目标表、在 `SET` 后声明要赋的新值，以及在 `WHERE` 后追加筛选范围。

##### 单条件单字段更新

业务场景：英语系决定更名为“英语文学系”，需将表中所有主修为“英語”的记录同步更新。

```sql
UPDATE student SET major = '英語文學' WHERE major = '英語';
```

该语句的执行逻辑是：扫描 `student` 表，定位所有满足 `major = '英語'` 的行，将其 `major` 属性值全部覆盖为 `'英語文學'`。未命中条件的行保持原样。

##### 基于主键更新与 OR 多条件联合更新

根据主键定位修改最为精准：

```sql
UPDATE student SET major = '生物' WHERE student_id = 3;
```

如果高校合并院系，要求将“生物系”与“化学系”合并为统一的“生化系”，则可通过逻辑运算符 `OR` 连接多个条件：

```sql
UPDATE student SET major = '生化' WHERE major = '生物' OR major = '化學';
```

只要记录的 `major` 等于 `'生物'` 或者等于 `'化學'`，就会被纳入更新目标，统一重置为 `'生化'`。

##### 多属性同时更新

如果需要对同一行记录的多列属性同时变更，多个赋值表达式之间使用半角逗号 `,` 分隔即可：

```sql
UPDATE student SET name = '小灰', major = '物理' WHERE student_id = 1;
```

此操作将 `student_id` 为 1 的学生姓名更改为 `'小灰'`，主修专业更改为 `'物理'`。

> **易错点**：千万不能遗漏 `WHERE` 条件！如果不写 `WHERE` 子句，直接执行 `UPDATE student SET major = '物理';`，数据库会无差别地将全表每一行记录的 `major` 全部覆盖为 `'物理'`，导致不可逆的全表数据污染。

#### 物理删除与范围过滤

从表中彻底移除已有记录使用 `DELETE FROM` 指令。删除语句同样极度依赖 `WHERE` 条件来限定影响边界。

##### 精确删除与多条件 AND 过滤

根据特定主键删除单行数据：

```sql
DELETE FROM student WHERE student_id = 4;
```

结合逻辑运算符 `AND`（并且）实现多条件精准匹配过滤：

```sql
DELETE FROM student WHERE name = '小灰' AND major = '物理';
```

只有当一行记录的姓名等于 `'小灰'` 且主修等于 `'物理'` 同时成立时，该行才会被物理抹除。

##### 数值比较运算符删除

除等值判断外，`WHERE` 子句支持常见的数值比较运算符（`<`、`>`、`<=`、`>=`）。例如开除所有不及格的学生：

```sql
DELETE FROM student WHERE score < 60;
```

数据库会计算所有 `score` 小于 60 的记录并将其逐一剔除，其余大于等于 60 分的记录安然保留。

> **警告**：直接执行 `DELETE FROM student;` 而不带任何 `WHERE` 判定，会直接清空目标数据表内的所有数据行，使整张表退化为空表。在生产环境中执行删除操作必须反复核查 `WHERE` 条件。

### 条件检索与结果集控制

查询数据使用 `SELECT` 语句。在复杂应用中，单纯使用 `SELECT *` 无法满足多变的报表与统计需求，我们需要对返回的字段、排序方向、数据条数以及筛选逻辑进行精确控制。

#### 属性投影与结果排序

##### 属性投影

当不需要全部字段时，在 `SELECT` 关键字后方显式书写需要透出的属性名，多个属性之间用逗号隔开：

```sql
SELECT name FROM student;
SELECT name, major FROM student;
```

这能够过滤掉无关列，大幅减少网络传输带宽与内存消耗。

##### 结果排序 ORDER BY

默认情况下查询结果的输出次序是无序或按物理存盘顺序呈现的。使用 `ORDER BY` 子句可实现依据特定字段排序：

```sql
SELECT * FROM student ORDER BY score;
```

> **定义**：`ORDER BY` 缺省的排序行为是升序（从低到高），等价于显式标注 `ORDER BY score ASC`。如果需要按降序（从高到低）输出，必须显式附加 `DESC` 关键字。

```sql
SELECT * FROM student ORDER BY score DESC;
```

若存在分数并列的情况，可以引入次要排序字段，字段间用逗号隔开：

```sql
SELECT * FROM student ORDER BY score, student_id;
```

此时数据库优先根据 `score` 进行升序排序；遇到分数完全相等的行，再根据 `student_id` 进行升序排序。

#### 数量切片与组合截取

##### 条数限制 LIMIT

当满足条件的记录过多时，使用 `LIMIT` 可以强行切断结果集，仅提取指定笔数：

```sql
SELECT * FROM student LIMIT 3;
```

##### ORDER BY 与 LIMIT 组合获取极值

将排序子句与切片子句结合，是业务系统中实现榜单排名的核心范式：

- **提取分数最低的两名学生**（先升序排列，再截取前 2 条）：
  ```sql
  SELECT * FROM student ORDER BY score LIMIT 2;
  ```
- **提取全校排名前三的高分学生**（先降序排列，再截取前 3 条）：
  ```sql
  SELECT * FROM student ORDER BY score DESC LIMIT 3;
  ```

#### 逻辑筛选与集合包含查询

`WHERE` 条件不仅用于更新和删除，更是 `SELECT` 查询的核心过滤引擎。

##### 条件组合与非等值过滤

可以在查询中自由嵌套 `AND`、`OR` 运算符：

```sql
SELECT * FROM student WHERE major = '英語' AND student_id = 1;
SELECT * FROM student WHERE major = '英語' OR score > 20;
```

在 SQL 中，表示“不等于”的比较运算符非常特殊，标准写法为先写小于号再写大于号构成的尖括号对 `<>`：

```sql
SELECT * FROM student WHERE score <> 70;
```

该查询会命中除 70 分以外的所有记录。

##### 集合运算符 IN

如果需要匹配某个字段落在离散的一组可选值之中，写多重 `OR`（如 `WHERE major = '歷史' OR major = '英語' OR major = '生物'`）会显得冗长繁琐。此时使用 `IN` 运算符即可精简逻辑：

```sql
SELECT * FROM student WHERE major IN ('歷史', '英語', '生物');
```

小括号内为离散元素集合，字段只要与集合内任一值匹配即算命中。`IN` 表达式同样可以与 `ORDER BY`、`LIMIT` 无缝串联使用。

### 企业级多表关系建模与参照完整性实战

真实数据库往往包含多张具有业务纽带的表格。下面通过构建一套完整的企业管理数据库，深入探讨多表设计、主外键拓扑、循环参照冲突以及级联操作。

#### 业务实体与表结构拓扑设计

该企业数据库包含四张核心业务表：员工表（`employee`）、部门表（`branch`）、客户表（`client`）以及销售跟进记录表（`works_with`）。

各表之间的拓扑关系与键值依赖如下图所示：

```text
  +------------------+       1:N 部门主管     +------------------+
  |     employee     |<-----------------------|      branch      |
  |  (emp_id [PK])   |----------------------->| (branch_id [PK]) |
  | (branch_id [FK]) |       N:1 所属部门     | (manager_id [FK])|
  |   (sup_id [FK])--+ (自引用直属主管)       +------------------+
  +------------------+
          |
          | 1:N 业务负责
          v
  +-----------------------------------------+       N:1 客户归属     +------------------+
  |               works_with                |----------------------->|      client      |
  | (emp_id [PK, FK], client_id [PK, FK])   |                        | (client_id [PK]) |
  |              total_sales                |                        +------------------+
  +-----------------------------------------+
```

读图说明：`employee` 表与 `branch` 表互为外键关联，同时 `employee` 表内部的 `sup_id` 形成自引用闭环；`works_with` 是一张多对多关联中间表，由 `emp_id` 与 `client_id` 构成复合主键，且双双兼具外键身份。

各表字段规格与业务含义定义如下：

| 表名 | 字段名称 | 数据类型 | 约束属性 | 业务语义 |
| :--- | :--- | :--- | :--- | :--- |
| `employee` | `emp_id` | INT | PRIMARY KEY | 员工工号 |
| | `name` | VARCHAR(20) | - | 员工姓名 |
| | `birth_date`| DATE | - | 出生日期 |
| | `sex` | VARCHAR(1) | - | 性别（'M' / 'F'） |
| | `salary` | INT | - | 薪资 |
| | `branch_id` | INT | FOREIGN KEY | 所属部门代号（参照 branch） |
| | `sup_id` | INT | FOREIGN KEY | 直属主管工号（自引用参照 employee） |
| `branch` | `branch_id` | INT | PRIMARY KEY | 部门编号 |
| | `branch_name`| VARCHAR(20)| - | 部门名称 |
| | `manager_id`| INT | FOREIGN KEY | 部门主管工号（参照 employee） |
| `client` | `client_id` | INT | PRIMARY KEY | 客户编号 |
| | `client_name`| VARCHAR(20)| - | 客户名称 |
| | `phone` | VARCHAR(20)| - | 联系电话 |
| `works_with` | `emp_id` | INT | PRIMARY KEY, FOREIGN KEY | 经办员工工号（参照 employee） |
| | `client_id` | INT | PRIMARY KEY, FOREIGN KEY | 对应客户编号（参照 client） |
| | `total_sales`| INT | - | 销售成交金额 |

#### 循环参照依赖的建表时序与解耦

在这套架构中存在典型的循环参照问题：`employee` 表的 `branch_id` 依赖于 `branch` 表，而 `branch` 表的 `manager_id` 又依赖于 `employee` 表；另外 `employee` 表的 `sup_id` 还依赖自身。

如果直接在建表语句中一次性全部声明外键，会因为被引用的目标表尚不存在而抛错崩溃。解决此类循环依赖的工程化标准流程是**先建无外键基础表，再通过表结构修改指令动态追加外键约束**。

##### 步骤一：创建基础员工表（暂不挂载外键）

```sql
CREATE TABLE employee (
    emp_id INT PRIMARY KEY,
    name VARCHAR(20),
    birth_date DATE,
    sex VARCHAR(1),
    salary INT,
    branch_id INT,
    sup_id INT
);
```

##### 步骤二：创建部门表并挂载经理外键

此时 `employee` 表已存在，因此 `branch` 表中的 `manager_id` 可以安全建立外键参照：

```sql
CREATE TABLE branch (
    branch_id INT PRIMARY KEY,
    branch_name VARCHAR(20),
    manager_id INT,
    FOREIGN KEY (manager_id) REFERENCES employee(emp_id) ON DELETE SET NULL
);
```

> **提示**：`ON DELETE SET NULL` 是一种外键联动删除策略，含义是一旦被引用的主表记录（如某位员工）被删除，从表中对应的外键字段（如该部门的 `manager_id`）会自动被数据库置为 `NULL`，防止出现悬空指针破坏数据一致性。

##### 步骤三：通过 ALTER TABLE 回填员工表的外键约束

由于 `branch` 表已建立完毕，我们可以回过头使用 `ALTER TABLE` 语句将 `employee` 表缺失的两个外键补齐：

```sql
ALTER TABLE employee 
ADD FOREIGN KEY (branch_id) 
REFERENCES branch(branch_id) 
ON DELETE SET NULL;

ALTER TABLE employee 
ADD FOREIGN KEY (sup_id) 
REFERENCES employee(emp_id) 
ON DELETE SET NULL;
```

第二条语句将 `sup_id` 对齐到 `employee(emp_id)`，完成了自引用的闭环绑定。

##### 步骤四：创建客户表

客户表无任何外键依赖，直接独立创建：

```sql
CREATE TABLE client (
    client_id INT PRIMARY KEY,
    client_name VARCHAR(20),
    phone VARCHAR(20)
);
```

##### 步骤五：创建复合主键兼复合外键的跟进记录表

`works_with` 表非常独特，其业务主键由员工号与客户号组合构成，同时这两个字段又各自充当指向对应表的外键：

```sql
CREATE TABLE works_with (
    emp_id INT,
    client_id INT,
    total_sales INT,
    PRIMARY KEY (emp_id, client_id),
    FOREIGN KEY (emp_id) REFERENCES employee(emp_id) ON DELETE CASCADE,
    FOREIGN KEY (client_id) REFERENCES client(client_id) ON DELETE CASCADE
);
```

> **定义**：`ON DELETE CASCADE` 代表“级联删除”。当某个员工或某个客户被系统彻底注销删除时，该员工或客户名下关联的所有销售跟进明细记录都会被数据库自动一并级联清除。

#### 外键参照死锁的写入策略破解

当四张表及其外键关联全部落定后，如果直接向 `employee` 表插入第一条员工记录（工号 206，所属部门 1），数据库会立刻拦截报错。因为此时 `branch` 表中尚未创建 1 号部门，外键约束判定该外键无处安放。

反过来，如果先向 `branch` 表插入 1 号研发部（主管设为 206），数据库同样会拦截报错，因为 206 号员工在员工表中也还不存在。

这种外键双向锁死的局面，必须通过“两阶段写入 + NULL 占位 + 后期回填”的经典策略来破解：

```sql
-- 第一阶段：插入部门，主管字段先设为 NULL 占位跳过外键校验
INSERT INTO branch VALUES (1, '研發', NULL);
INSERT INTO branch VALUES (2, '行政', NULL);
INSERT INTO branch VALUES (3, '資訊', NULL);

-- 第二阶段：此时 1、2、3 号部门已就绪，全量写入员工数据
INSERT INTO employee VALUES (206, '小黃', '1998-10-08', 'F', 50000, 1, NULL);
INSERT INTO employee VALUES (207, '小綠', '1985-09-16', 'M', 29000, 2, 206);
INSERT INTO employee VALUES (208, '小黑', '2000-12-19', 'M', 35000, 3, 206);
INSERT INTO employee VALUES (209, '小白', '1997-01-22', 'F', 39000, 3, 207);
INSERT INTO employee VALUES (210, '小藍', '1995-03-27', 'M', 84000, 1, 207);

-- 第三阶段：员工已入库，通过 UPDATE 补全部门表的主管工号
UPDATE branch SET manager_id = 206 WHERE branch_id = 1;
UPDATE branch SET manager_id = 207 WHERE branch_id = 2;
UPDATE branch SET manager_id = 208 WHERE branch_id = 3;

-- 第四阶段：写入客户表与销售记录表
INSERT INTO client VALUES (400, '阿狗', '254354335');
INSERT INTO client VALUES (401, '阿貓', '256334335');
INSERT INTO client VALUES (402, '旺來', '45354335');
INSERT INTO client VALUES (403, '露西', '2234335');
INSERT INTO client VALUES (404, '艾瑞克', '23454335');

INSERT INTO works_with VALUES (206, 400, 70000);
INSERT INTO works_with VALUES (207, 401, 26700);
INSERT INTO works_with VALUES (208, 402, 22000);
INSERT INTO works_with VALUES (208, 403, 5400);
INSERT INTO works_with VALUES (210, 404, 34000);
```

通过这一套工序严谨的操作，复杂多表及其关联依赖全部平稳初始化完成，数据完整性约束也在整个过程中得到了绝对守护。

### 查询结果排序、截取与去重处理

在执行基础数据检索时，原始结果集通常按照物理存储顺序或主键自增顺序输出。当业务目标需要提取极值区间或清理冗余数据时，需要借助排序子句、数量限制子句以及去重机制。

#### 降序排序与限量截取

当需要查询薪水处于全公司前三高的员工完整档案时，核心逻辑分为两步：首先依据薪水字段由高到低重新排列，随后在结果集的顶部截取前三条记录。

```sql
SELECT * FROM employee
ORDER BY salary DESC
LIMIT 3;
```

在上述语句中，`ORDER BY salary` 声明以薪水为排序基准，末尾追加的关键字 `DESC`（Descending）指定按照降序排列；若省略该关键字，系统默认采用升序 `ASC`（Ascending）。排列完成后，`LIMIT 3` 负责截断后续记录，仅返回排在最前列的三笔完整员工元组。

#### 投影检索与重复项过滤

当查询关注点仅限于员工姓名等单一维度时，应避免使用通配星号 `*`，而应显式指定目标字段：

```sql
SELECT name FROM employee;
```

如果投影的字段包含大量重复取值（例如查询员工的性别或所在部门编号），直接查询会导致控制台输出多条相同的标志。若需要提取该字段具有的所有唯一取值组合，需在字段名前注入 `DISTINCT` 关键字：

```sql
SELECT DISTINCT sex FROM employee;
```

未添加去重修饰时，系统返回包含重复字符的原始列表（如女性 `F` 与男性 `M` 多次交替出现）；添加 `DISTINCT` 之后，重复出现的数值在输出前被引擎自动折叠，仅保留去重后的唯一类别。类似地，针对部门编号 `branch_id` 进行唯一性提取：

```sql
SELECT DISTINCT branch_id FROM employee;
```

> **结论**：`DISTINCT` 作用于其后跟随的所有投影字段组合，在查询引擎执行完数据扫描后，对结果集中完全一致的数据行执行去重过滤。

### 聚合函数与统计计算

聚合函数（Aggregate Functions）是一类对一组数据记录执行汇总运算并返回单个标量值的内置函数，广泛用于规模统计、均值核算与极值挖掘。

#### 记录计数与非空统计

`COUNT` 函数用于统计符合查询条件的数据记录总数。统计企业在册员工总人数的基础语法如下：

```sql
SELECT COUNT(*) FROM employee;
```

此时传入通配符参数 `*`，计算引擎将遍历整张 `employee` 表并计算物理存在的总行数（当前返回值为 5）。

然而，当 `COUNT` 的参数由星号替换为具体的属性列名时，其统计口径将发生关键转变：

```sql
SELECT COUNT(sup_id) FROM employee;
```

> **易错点**：`COUNT(*)` 统计的是整行记录的总条数，包含字段取值为 `NULL` 的行；而 `COUNT(列名)` 仅统计该指定列中取值不为 `NULL` 的有效数据条数。

在当前的员工数据中，最高层级员工小黄本身没有上级主管，其主管编号 `sup_id` 记录为 `NULL`。因此执行 `COUNT(sup_id)` 时，计算引擎会自动忽略该 `NULL` 记录，最终返回值为 4。

`COUNT` 同样可以与 `WHERE` 过滤子句配合，用于受限集合的计数。例如统计出生日期在 1970 年 1 月 1 日之后的女性员工总数：

```sql
SELECT COUNT(*) FROM employee
WHERE birth_date > '1970-01-01' AND sex = 'F';
```

查询引擎首先评估 `WHERE` 子句中的两个布尔表达式：`birth_date > '1970-01-01'` 筛选出年轻员工，`sex = 'F'` 圈定女性群体。由于两条件间使用逻辑运算符 `AND` 连接，仅同时满足二者的两笔记录被送入计数池，最终计算结果返回 2。

#### 数值均值与极值计算

针对数值型字段，SQL 提供了直接计算算术平均值与累加总和的聚合函数。

计算员工薪资均值使用 `AVG` 函数：

```sql
SELECT AVG(salary) FROM employee;
```

该语句自动提取表中全体 5 位员工的薪资金额，累加求和后除以记录总数，计算得出平均薪水 47400。

若需要汇总所有员工薪资的总支出规模，则调用 `SUM` 函数：

```sql
SELECT SUM(salary) FROM employee;
```

系统将所有员工的 `salary` 数值相加，最终返回薪资总和 237000。

当需要提取数值列的极大值与极小值时，分别调用 `MAX` 与 `MIN` 函数：

```sql
-- 查询最高薪资
SELECT MAX(salary) FROM employee;

-- 查询最低薪资
SELECT MIN(salary) FROM employee;
```

执行后分别输出最高薪资 84000 与最低薪资 29000。

### 通配符与文本模式匹配

在执行文本字段匹配时，精确等值匹配无法处理包含部分关键字或特定排版模式的查询。此时需使用 `LIKE` 操作符搭配万用字元（Wildcards）执行模糊模式匹配。

#### 百分比通配符的多字符匹配

百分比符号 `%` 在模式字符串中代表任意数量（包括零个、一个或多个）的任意字符。

查询电话号码尾数为 335 的客户记录：

```sql
SELECT * FROM client
WHERE phone LIKE '%335';
```

在模式串 `'%335'` 中，尾部的 335 是固定匹配项，而前面的 `%` 表示号码前缀无论由多少位数字构成均符合判定。匹配引擎扫描数据后，精准返回电话为 `254-354-335` 的客户阿狗。

同理，若需要检索电话以 254 开头的客户记录，只需将通配符置于末尾：

```sql
SELECT * FROM client
WHERE phone LIKE '254%';
```

若需要匹配电话号码中任意位置包含子串 `354` 的客户，可将通配符同时置于模式串的首尾两侧：

```sql
SELECT * FROM client
WHERE phone LIKE '%354%';
```

此时只要字段内部嵌入了连续的 `354`，不论其前方与后方存在多少字符，均能命中目标。

百分比通配符同样适用于文本姓名的前缀提取。例如寻找所有姓艾的客户：

```sql
SELECT * FROM client
WHERE client_name LIKE '艾%';
```

系统将返回以汉字“艾”作为起始字符的所有客户记录（如艾瑞克）。

#### 下划线通配符的单字符定长匹配

与百分比符号不同，下划线 `_` 具有严格的定长占位特性，每一个下划线仅且必须代表一个任意字符。

在匹配固定日期格式时，该特性尤为有效。关系型数据库中日期字段通常遵循 `YYYY-MM-DD` 的字符串格式（4 位年份数字、1 位连接符、2 位月份数字、1 位连接符、2 位日期数字）。若要检索所有在 12 月份出生的员工：

```sql
SELECT * FROM employee
WHERE birth_date LIKE '_____12%';
```

> **提示**：模式串开头的 5 个连续下划线 `_____` 精准占位了 4 位年份数字加上 1 个短横线分隔符；紧随其后的 `12` 锁定月份位置；末尾的 `%` 吸收后续的短横线与具体日期。

该语句准确过滤出 12 月出生的小黑。同理，若需筛选 9 月出生的员工，需将月份位按两位数补齐书写为 `09`：

```sql
SELECT * FROM employee
WHERE birth_date LIKE '_____09%';
```

### 多查询结果集合并

`UNION` 操作符用于将两个或多个独立 `SELECT` 查询的输出垂直拼接为一个统一的结果集。

#### 联合查询的基本语法与结构要求

若需要将员工表中的姓名与客户表中的姓名汇总到一张名单中，可编写两个独立的查询并通过 `UNION` 串联：

```sql
SELECT name FROM employee
UNION
SELECT client_name FROM client;
```

该操作支持多层级链式合并。若希望将部门名称也一同归并进入姓名清单，继续追加 `UNION` 子句即可：

```sql
SELECT name FROM employee
UNION
SELECT client_name FROM client
UNION
SELECT branch_name FROM branch;
```

执行后，员工姓名、客户姓名与部门名称将被规整在同一列数据中输出。

> **注意**：`UNION` 运算必须满足两条硬性结构约束：
> 1. **列数一致性**：各个 `SELECT` 子句所选取的字段数量必须严格相等。不能在一个查询中投影两个属性，而在另一个查询中仅投影一个属性（例如首个查询包含 `sex`，第二查询未提供对应列，系统将直接报错终止）。
> 2. **类型兼容性**：上下对应的各个属性列，其底层数据类型必须能够相互兼容或隐式转换（例如均为字符类型 `VARCHAR`）。

#### 结果集字段重命名与属性别名

当参与联合的各子查询包含多个字段时，各查询中相同物理位置的列必须在语义上相互对应。例如将员工 ID 及姓名与客户 ID 及姓名联合输出：

```sql
SELECT emp_id, name FROM employee
UNION
SELECT client_id, client_name FROM client;
```

在多表联合输出时，结果集的表头字段名默认继承**第一个 `SELECT` 语句**所采用的属性列名。在上方语句中，输出的表头将显示为 `emp_id` 与 `name`，而非后者的 `client_id` 与 `client_name`。

为了提高结果集的通用性与可读性，可以在首个查询中使用 `AS` 关键字显式定义字段别名：

```sql
SELECT emp_id AS total_id, name AS total_name FROM employee
UNION
SELECT client_id, client_name FROM client;
```

通过赋予中性列名 `total_id` 与 `total_name`，输出报表的语义边界更加清晰。该技巧同样适用于金额流水的跨表汇总展示，例如合并员工薪资支出与客户销售收入：

```sql
SELECT salary AS total_money FROM employee
UNION
SELECT total_sales FROM works_with;
```

### 多表关联连接查询

在关系型数据库规范化设计中，不同业务实体通常切分至各自独立的数据表存储。例如部门表 `branch` 仅存储了部门主管的工号 `manager_id`，若要提取主管的具体姓名，必须通过连接（JOIN）操作建立跨表关联。

为了完整展示不同连接方式的边界行为，我们在测试数据库的 `branch` 表中注入一条主管字段为 `NULL` 的特殊记录：

```sql
INSERT INTO branch VALUES (4, '偷懒', NULL);
```

#### 内连接与表名前缀限定

内连接（`JOIN` 或 `INNER JOIN`）是最基础的连接方式，其核心机制是寻找两表之间满足关联条件的交集记录。

```sql
SELECT * FROM employee
JOIN branch ON employee.emp_id = branch.manager_id;
```

在语法中，`JOIN` 声明与目标表建立连接，`ON` 子句定义匹配条件。此处要求员工表的工号 `emp_id` 与部门表的管理者工号 `manager_id` 保持数值相等。

```text
内连接匹配机制:
[ employee 表记录 (emp_id) ]  <─── ON 关联条件 ───>  [ branch 表记录 (manager_id) ]
     206 (小黄)                    相等                   206 (研發部)  ──> 输出匹配行
     207 (小绿)                    相等                   207 (行政部)  ──> 输出匹配行
     208 (小黑)                    相等                   208 (資訊部)  ──> 输出匹配行
     209 (小白)                   无对应                   未匹配        ──> 丢弃
     210 (小蓝)                   无对应                   未匹配        ──> 丢弃
       无                         未匹配                   NULL (偷懒部) ──> 丢弃
```
上图展示了内连接的双向匹配逻辑，两表中任意一方无法在对方表中找到匹配项的孤立行均被滤除。

由于 `employee` 包含 7 个属性，`branch` 包含 3 个属性，执行 `SELECT *` 会将两表字段横向拼接为包含 10 列的合并元组。因为只有 206、207、208 三位员工在部门表中担任主管，其余未担任主管的员工以及没有主管的“偷懒”部门均未满足条件，最终仅返回 3 条数据。

为了使输出结构清晰，通常需要进行精简投影。当关联的多张表之间存在同名字段时，直接书写列名会触发歧义错误。规范的做法是使用 `表名.字段名` 的前缀限定语法：

```sql
SELECT employee.emp_id, employee.name, branch.branch_name
FROM employee
JOIN branch ON employee.emp_id = branch.manager_id;
```

#### 左外连接与右外连接的数据保留机制

外连接用于在关联条件无法匹配时，强制保留某一侧数据表的全部记录，并在缺失侧补齐 `NULL`。

左外连接（`LEFT JOIN`）以写在 `JOIN` 关键字左侧的数据表为基准主表：

```sql
SELECT employee.emp_id, employee.name, branch.branch_name
FROM employee
LEFT JOIN branch ON employee.emp_id = branch.manager_id;
```

在上述语句中，`employee` 位于左侧。无论 `ON` 条件是否能够命中，左表的全部 5 位员工记录都会被完整保留输出。对于小黄、小绿、小黑，右侧的 `branch_name` 正常填充部门名称；对于未担任经理的小白与小蓝，由于在右表中无对应关联记录，其 `branch_name` 位置由系统填充 `NULL` 返回。

右外连接（`RIGHT JOIN`）则相反，以位于 `JOIN` 关键字右侧的数据表为主表：

```sql
SELECT employee.emp_id, employee.name, branch.branch_name
FROM employee
RIGHT JOIN branch ON employee.emp_id = branch.manager_id;
```

此时 `branch` 表位于右侧，其包含的全部 4 个部门都会在结果集中呈现。由于“偷懒”部门的 `manager_id` 为 `NULL`，在左侧员工表中不存在对应的实体匹配，因此其对应的 `emp_id` 与 `name` 列自动以 `NULL` 补齐返回。

| 连接类型 | 核心驱动方向 | 未匹配记录的处理策略 | 适用业务场景 |
| :--- | :--- | :--- | :--- |
| `INNER JOIN` | 双向对称 | 只要任一侧未满足 `ON` 条件即被完全剔除 | 仅提取关系完全确立的核心业务数据 |
| `LEFT JOIN` | 左表主导 | 左表全量保留；右表无匹配项补填 `NULL` | 保留全量实体主体并附加可选关联属性 |
| `RIGHT JOIN` | 右表主导 | 右表全量保留；左表无匹配项补填 `NULL` | 以从属维度为全量基准反查主体信息 |

### 嵌套子查询

子查询（Subquery）是指将一条完整的 SQL 检索语句嵌套嵌入至另一条外部 SQL 语句内部，利用内层查询的实时执行结果作为外层查询的过滤判别依据。

#### 单值标量子查询

当内层子查询返回的结果为单一标量值（1 行 1 列）时，外层查询可以直接使用等号 `=` 等标准标量比较运算符。

例如，若要查询“研發”部门的主管姓名，但姓名信息与部门名称分属两张表，可以通过两阶段子查询实现解耦：

```sql
SELECT name FROM employee
WHERE emp_id = (
    SELECT manager_id FROM branch
    WHERE branch_name = '研發'
);
```

查询引擎自内向外解析：
1. 内部子查询首先执行 `SELECT manager_id FROM branch WHERE branch_name = '研發'`，在部门表中查得主管工号为单值 `206`。
2. 外部主查询将括号内容替换为该标量结果，等价于执行 `SELECT name FROM employee WHERE emp_id = 206;`，最终输出主管姓名“小黄”。

#### 多值集合子查询

当内部子查询的筛选结果可能输出多行记录（即返回一个数据集合）时，外层条件不能再使用标量等号 `=`，否则当内层返回超过一行数据时会触发运行时错误。此时外层必须借助集合成员运算符 `IN`。

例如，寻找在单笔客户业务中销售金额突破 50000 的员工姓名：

```sql
SELECT name FROM employee
WHERE emp_id IN (
    SELECT emp_id FROM works_with
    WHERE total_sales > 50000
);
```

在该结构中：
1. 内部子查询在 `works_with` 销售关联表中扫描所有单笔金额超过 50000 的记录，提取对应的员工工号集合（返回 `206` 与 `210` 两笔数据）。
2. 外部查询利用 `IN` 运算符判定 `employee` 表中的员工工号是否落入内层计算生成的临时数值集合中。工号为 206 的小黄与工号为 210 的小蓝均命中条件，最终系统返回这两位员工的姓名。

### 外键级联删除约束

在关系模型中，子表通过外键（Foreign Key）建立对父表主键的引用。当父表中的某条主记录被物理删除时，子表中原先指向该主键的外键字段将面临“悬空引用”风险。为了解决数据完整性危机，SQL 在定义外键时提供了 `ON DELETE` 联动约束策略。

#### 置空与级联删除的行为差异

常见的外键删除联动行为主要包括 `ON DELETE SET NULL` 与 `ON DELETE CASCADE` 两种模式。

```text
外键级联联动机制对比:
[ 父表 employee ] (执行 DELETE WHERE emp_id = 207)
       │
       ├───> branch.manager_id (配置: ON DELETE SET NULL)
       │     └─> 原指向 207 的外键字段自动被引擎修改为 NULL (部门记录本身保留)
       │
       └───> works_with.emp_id (配置: ON DELETE CASCADE)
             └─> 原包含 207 的整行销售关联记录被连带彻底删除
```
上图展示了父表主键记录删除后，不同联动策略对子表关联字段及整行数据的生命周期处置方式。

在系统表结构中，`branch.manager_id` 配置了 `ON DELETE SET NULL`，而 `works_with.emp_id` 配置了 `ON DELETE CASCADE`。

现在模拟行政部主管小绿（`emp_id = 207`）离职并从员工主表中物理删除：

```sql
DELETE FROM employee WHERE emp_id = 207;
```

执行后检查部门表：

```sql
SELECT * FROM branch;
```

可以观察到，行政部门原本记录的 `manager_id`（207）被自动刷新为 `NULL`，行政部门本身的元组记录依然安全保留在表中。这正是 `ON DELETE SET NULL` 的运行机理：允许子记录独立存在，仅解除引用关联。

随后检查销售关联表：

```sql
SELECT * FROM works_with;
```

原本属于员工 207 的那笔销售业绩数据已被整行连带抹除，整张表的数据总条数由 5 笔自动缩减为 4 笔。这体现了 `ON DELETE CASCADE` 的级联联动行为：子记录的存在完全依附于父记录，父项一旦消失，从属数据连带清理。

#### 主键非空性对外键置空的约束限制

在配置外键联动规则时，必须严守底层实体完整性原则。

> **易错点**：如果子表中的某个外键列同时参与构成了该子表的主键（Primary Key）或复合主键，该外键**绝对不可**被配置为 `ON DELETE SET NULL`。

在关系型数据库底层定义中，主键的核心约束是必须满足非空（Not Null）且全局唯一。在 `works_with` 表中，为了标识某位员工对特定客户的唯一销售记录，该表的主键是由 `(emp_id, client_id)` 联合构成的复合主键。这意味着 `emp_id` 既是外键，又是主键不可分割的一部分。

一旦将其设定为 `ON DELETE SET NULL`，父表记录被删除时，系统将尝试把该外键列改写为 `NULL`。然而此操作会与主键列禁止为 `NULL` 的底层约束发生不可调和的逻辑冲突，导致建表失败或运行时异常。因此，在此类复合主键场景中，只能选用 `ON DELETE CASCADE` 将整条依赖记录同步销毁。

### Python客户端连接与自动化运维

在实际工程项目中，SQL 通常由宿主编程语言通过专有数据库驱动调用执行。以 Python 为例，通过官方支持的 `mysql-connector-python` 驱动模块，可构建完整的数据库连接、查询与持久化管道。

```text
Python 操作 MySQL 核心拓扑:
[ Python 运行时环境 ]
         │
         │  1. mysql.connector.connect(host, port, user, password, database)
         ▼
[ 物理数据库连接 Connection ]
         │
         │  2. connection.cursor()
         ▼
[ 数据库游标 Cursor ]
         │
         │  3. cursor.execute("SQL 语句")
         │
         ├─── 查询流程 ──> 4. records = cursor.fetchall() (提取并遍历输出)
         │
         └─── 写入流程 ──> 4. connection.commit() (事务持久化落盘)
         │
         ▼
[ 5. 显式释放资源: cursor.close() / connection.close() ]
```
上图总结了 Python 通过连接与游标接口与 MySQL 服务交互的标准生命周期流向。

#### 驱动安装与数据库连接生命周期

首先在终端使用包管理器安装驱动依赖：

```bash
pip install mysql-connector-python
```

在 Python 脚本中引入模块并建立与本地 MySQL 服务的网络连接：

```python
import mysql.connector

# 初始化连接对象
connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password"
)

# 获取执行游标
cursor = connection.cursor()

# 执行数据库创建指令
cursor.execute("CREATE DATABASE qq")

# 释放游标与连接资源
cursor.close()
connection.close()
```

连接参数解析：
- `host`：MySQL 实例所在主机的网络地址。运行在本地时传入 `'localhost'` 或 `'127.0.0.1'`。
- `port`：数据库通信端口。MySQL 默认监听通道为 `3306`。
- `user`：具有操作权限的数据库账户标识（通常为 `'root'`）。
- `password`：对应账户的认证密码。

#### 数据检索与游标结果提取

在执行会产生数据集返回的操作（如 `SHOW DATABASES` 或 `SELECT`）时，需要借助游标提取结果：

```python
import mysql.connector

connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password"
)

cursor = connection.cursor()
cursor.execute("SHOW DATABASES")

# 提取所有结果集元组
databases = cursor.fetchall()
for db in databases:
    print(db)

cursor.close()
connection.close()
```

方法 `cursor.fetchall()` 负责从服务端的网络缓存区中一次性抽取所有匹配的行记录，并将其包装为列表对象。

在实际业务开发中，通常无需在每个脚本中反复执行 `USE 数据库名`。我们可以在调用 `connect()` 初始化连接时直接通过 `database` 参数选定默认数据库上下文：

```python
import mysql.connector

connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password",
    database="sql_tutorial"
)

cursor = connection.cursor()
cursor.execute("SELECT * FROM branch")

records = cursor.fetchall()
for record in records:
    print(record)

cursor.close()
connection.close()
```

#### 数据变更操作与事务提交机制

在关系型数据库管理系统中，执行数据操作语言（DML，包括 `INSERT`、`UPDATE`、`DELETE`）与执行只读查询有着本质差异。

> **注意**：凡是对数据表内容产生修改的写操作，在调用 `cursor.execute()` 之后，变更仅存在于当前会话的事务暂存区中。必须显式调用 `connection.commit()` 提交事务，写入操作才会正式持久化落盘生效。

##### 数据插入示例

```python
import mysql.connector

connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password",
    database="sql_tutorial"
)
cursor = connection.cursor()

# 执行新增语句
cursor.execute("INSERT INTO branch VALUES (5, 'QQ', NULL)")
# 显式提交事务，使物理数据生效
connection.commit()

cursor.close()
connection.close()
```

##### 数据修改示例

若需要将部门表中特定记录的管理人员工号予以更新：

```python
import mysql.connector

connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password",
    database="sql_tutorial"
)
cursor = connection.cursor()

# 将 branch_id 为 4 的部门的主管工号更新为 206
cursor.execute("UPDATE branch SET manager_id = 206 WHERE branch_id = 4")
connection.commit()

cursor.close()
connection.close()
```

##### 数据删除示例

若需要从数据表中移除指定记录：

```python
import mysql.connector

connection = mysql.connector.connect(
    host="localhost",
    port=3306,
    user="root",
    password="password",
    database="sql_tutorial"
)
cursor = connection.cursor()

# 删除 branch_id 为 5 的数据行
cursor.execute("DELETE FROM branch WHERE branch_id = 5")
connection.commit()

cursor.close()
connection.close()
```
