## 汇编程序结构与实验二
> 对应块：BLK08 | 覆盖分集：P14-P15

上次实验我们把 debug 的主要命令过了一遍，实验二就接着往下走：先把 `d` 命令里还没说透的一层补上，再动手做两个实验，最后回到正题——怎么写出第一个真正能编译、能运行的汇编程序。

### 让 d、e、u、a 直接吃段寄存器

上次用 `d` 命令，是拿它查看内存单元的内容，写法是 `d 段地址:偏移地址`。如果不限定范围，一次能看 128 个内存单元。那时候段地址和偏移地址都是我们直接写出来的。

现在要往底层问一层：段地址平时是放在段寄存器里的——`cs`、`ds`、`ss`、`es` 四个。那么 `d` 命令后面如果直接给出段地址，debug 内部是怎么处理它的？

先想 debug 本身靠什么执行。它肯定也是靠一段程序在跑，而这段程序由 CPU 执行。CPU 访问内存单元时，段地址是从哪儿来的？在我们前面的学习里已经知道，是数据段寄存器 `ds` 提供的。

> **结论**：debug 处理 `d` 命令的那段程序里，必须有一段代码，先把段地址送进数据段寄存器 `ds`，再去访问内存。也就是说，debug 在执行 `d 段地址:偏移地址` 时，会先把段地址送入 `ds`，然后再访问。

段寄存器有四个，为什么偏偏是 `ds`？因为 `d` 命令要访问的是内存里的数据，自然借助数据段寄存器 `ds` 来暂存我们要访问的段地址。

顺着这个机理，debug 也提供了一种更贴合 CPU 的格式：`d 段寄存器:偏移地址`——直接拿某个段寄存器里的值当段地址，再和后边的偏移地址拼成最终的物理地址，从那里开始访问内存。

举几个例子就明白了：

- 先用 `r ds` 把 `ds` 里的值改成 `1000`，再用 `d ds:0`，看到的就和 `1000:0` 开始的内存一样。
- 把 `ds` 设成 `1000` 之后，再去看 `1000:10` 到 `1000:18` 这一段的内容。
- 用 `u cs:0`，会从 `cs:0` 对应的物理地址开始，以汇编指令的形式显示当前代码段里的代码——也就是看当前代码段里到底存了什么指令。
- 用 `a` 配合段寄存器，可以从代码段的起点开始向内存里写入指令。

实战一遍就是老套路：先 `mount` 一下（照写即可），打开 debug，`r ds` 改成 `1000`，然后 `d ds:0` 就能直接看到 `1000:0` 开始的内存单元。

`e`、`a`、`u` 这几个命令也一样。回顾一下它们的本职：

- `e` 用来更改内存单元的内容；
- `a` 用来向内存中写入汇编指令；
- `u` 用来把机器码翻译成汇编指令。

凡是这类带内存单元的命令，都可以用「段寄存器:偏移地址」来指定段地址。

> **结论**：这些命令可以直接操作段寄存器——只要在地址里写上段寄存器的名字，debug 就会按 CPU 的机理去取段地址。

### 修改 ss 的指令，会带着下一条一起执行

接着看一个怪现象。用 `a` 往内存里写一段程序：

```asm
mov ax, 2000
mov ss, ax
mov sp, 10
mov ax, 3123
push ax
mov ax, 3366
push ax
```

写完之后逐条 `t` 执行，仔细盯着寄存器的变化：

- 第一步把 `2000` 放进 `ax`，`ax` 变成 `2000`，没问题；
- 下一步 `mov ss, ax` 把 `ax` 的值放进 `ss`，`ss` 变成 `2000`，没问题；
- 再下一步该是 `mov ax, 3123` 了——可这一条执行完之后，debug 并没有把 `mov sp, 10` 显示出来，而是直接跳到了 `mov ax, 3123` 那里。

那 `mov sp, 10` 到底执行了没有？看 `sp` 的值就知道：执行完那一步之后，`sp` 变成了 `0010`。它确实执行了，只是没有被单独显示出来。

为什么会这样？这是一个**中断机制**在起作用，它也是我们后面课程要重点探讨的主题。

> **结论**：在 debug 里用 `t` 命令执行一条修改 `ss` 的指令时，它的下一条指令也会被紧接着执行。现在先知道有这么个机制就够了，往后会深入讲它。

### 写入一段程序，按运行结果填空

实验二的第一个任务是：用 debug 把一段程序写进内存，逐条执行，再根据实际运行情况填空。

动手之前先重新开一次 debug，第一步还是 `mount`——它是给磁盘做一个映射，也就是虚拟磁盘映射，照着写就行。

打开 debug 后，用 `a` 指令加「段地址:偏移地址」指出要写入的第一条指令所在的内存单元。比如从 `1000` 开始写，把下面这段程序敲进去：

```asm
mov ax, ffff
mov ds, ax
mov ax, 2200
mov ss, ax
mov sp, 0100
mov ax, [0]
add ax, [2]
mov bx, [4]
add bx, [6]
push ax
push bx
pop ax
pop bx
```

这里有个细节值得留意：把段寄存器的值设成 `2200`，得先 `mov ax, 2200` 再 `mov ss, ax`，不能直接给段寄存器送立即数。

程序写完还不算完。要让它跑起来，必须让 `cs:ip` 指向程序第一条指令的首地址。所以我们先把代码段寄存器 `cs` 改成 `1000`，再把 `ip` 改成 `0`，这样准备工作才算做完。

逐条执行时，前面讲过的那个现象又出现了：执行到修改段寄存器的指令时，它的下一条指令会被一起执行，所以屏幕上会直接跳到后面那条，中间那条不单独显示。别慌，看寄存器就知道它跑过了。

接着看结果。经过 `mov ax, [0]` 和 `add ax, [2]`，`ax` 里是 `c0fc`；`mov bx, [4]` 和 `add bx, [6]` 之后，`bx` 里是 `6021`。

然后就是 `push ax`、`push bx`、`pop ax`、`pop bx`。按道理，`ax` 的值应该变成原来 `bx` 的值——因为**先入栈的后出栈**，后入先出。

> **结论**：执行完这四条之后，`ax` 变成 `6021`（原来 `bx` 的值），`bx` 变成 `c0fc`（原来 `ax` 的值）。

顺便把入栈改写的内存单元也理清楚。栈段是 `2200`，`sp` 初值是 `0100`：

- 第一次 `push` 后 `sp` 减小 2，数据写进 `2200:00fe` 到 `2200:00ff`；
- 第二次 `push` 后 `sp` 再减小 2，数据写进 `2200:00fc` 到 `2200:00fd`。

### 栈太小：2000:0~f 为什么被改写

实验二的第二个任务，是仔细观察实验过程，然后回答：为什么 `2000:0` 到 `2000:f` 里的内容会发生改变？

同样先写入一段程序：

```asm
mov ax, 2000
mov ss, ax
mov sp, 0010
mov ax, 3123
push ax
mov ax, 3366
push ax
```

把 `ss` 设成 `2000`、`sp` 设成 `0010` 之后，栈就立在这个位置了。先把 `2000:0` 那一片的数据改掉，回头查看确认改动成功；再确认 `cs:ip` 指向的正是第一条指令，然后开跑。

一步一步执行下去，执行到中间某一步时去查看 `2000:0` 到 `2000:f` 的内容，会发现：明明还没有轮到把 `ax` 入栈，那块内存里的东西却已经变了。这是为什么？

答案就在 `sp` 上。我们把 `sp` 设成了 `0010`，也就是栈顶在 `2000:0010`。程序执行过程中，那些 `mov` 之类的指令会伴随一些数据入栈——本来这些入栈的数据不该对程序造成任何影响，可是现在栈空间太小了，压进去的数据就盖住了原本的内容。

> **易错点**：不是指令本身写错了，而是把栈开得太小，指令执行过程中的压栈动作覆盖了不该动到的内存。栈的位置和大小，是这类"莫名其妙被改写"问题的关键。

### 从源程序到可执行文件

前面我们都是通过 debug 写一些零散的小程序。从这一章开始不一样了：写出完整程序后，用编译器把它编译成可执行文件（`.exe`），再放进操作系统里运行——这才是真正能跑起来的文件。

一个源程序从写出到执行，可以简单说成四步：**编写、编译、连接、执行**。

```text
  文本编辑器写出的源程序 a
            │  汇编（编译程序）
            ▼
        目标文件
            │  连接（连接程序）
            ▼
  可执行文件 b
   ┌────────────────────────┬────────────────────────┐
   │  机器码与数据           │  相关描述信息           │
   │ （由汇编指令翻译而来）   │ （程序多大、占多少内存） │
   └────────────────────────┴────────────────────────┘
            │  操作系统按描述信息加载、初始化 cs:ip
            ▼
          内存中运行
```

先看**编写**：用文本编辑器（比如 notepad 记事本）用汇编语言写汇编源程序。由汇编指令组成的程序叫汇编源程序；更准确地说，汇编源程序由**汇编指令、伪指令和标号**组成。

再看**编译和连接**：用汇编语言的编译程序对源程序文件进行编译，产生目标文件；再用连接程序对目标文件进行连接，生成能在操作系统中直接运行的可执行文件。

可执行文件里包含两部分内容：

- 一部分是程序——从源汇编指令翻译过来的机器码和数据；
- 另一部分是相关的描述信息，比如程序有多大、要占多少内存空间等。

为什么非得有描述信息？因为要执行一个程序，得先把它加载到内存里，而加载就得分配对应的内存空间。正是靠这些描述信息，才知道该分配多少内存。

最后是**执行**：在操作系统中执行可执行文件里的程序。操作系统依照可执行文件中的描述信息，把机器码和数据加载进内存，并做相关初始化——比如先把 `cs:ip` 设置成指向第一条要执行的指令。指向了第一条指令之后，这段东西才被 CPU 认作一个程序，然后由 CPU 执行。

把整个过程演示一遍：先用文本编辑器写出源程序文件 a，送进编译器；编译器处理后，变成一段由机器码组成的可执行文件 b，它分成"指令和数据"以及"相关描述信息"两块；再把 b 送进操作系统，操作系统通过描述信息把内容加载到内存，接着开始执行。这就是程序运行的大体过程。

### 源程序由什么构成

有了上面的整体印象，就可以拆开源程序看细节了。先别急着说"这个看不懂那个看不懂"，一条一条来。

一个源程序由两部分组成：**汇编指令**和**伪指令**（再加上标号）。

**汇编指令**是有对应机器码的指令，可以被编译为机器指令，最终由 CPU 执行。

**伪指令**恰恰相反：它没有对应的机器码，最终也不会被 CPU 执行。那问题就来了——伪指令由谁执行？

回想刚才的流程：我们先写源程序，送进编辑器，汇编之后再对它进行编译连接，变成可执行文件，最后送进操作系统执行。最终执行的是 CPU，而伪指令根本进不了 CPU 那一环。

> **结论**：伪指令是由**编译器**来执行的。编译器根据伪指令来做相关的编译工作。

具体到伪指令里，先看 `segment` 和 `ends`。我们之前说过，CPU 里并没有"段"这个东西，段是由程序员主观去定义的。现在就知道段是怎么定义出来的了：靠 `segment` 和 `ends` 这一对成对使用的伪指令，它们是编写可被编译器编译的汇编程序时必须要用到的。

- `segment` 说明一个段的开始；
- `ends` 说明一个段的结束。

一个段必须有一个名称来标识，写法是 `段名 segment` 开头、`段名 ends` 结尾。一个汇编程序由多个段组成，这些段分别用来存放代码、存放数据，或者当作栈空间用——于是就有了代码段、数据段、栈段。

一个有意义的汇编程序至少得有一个段，而且必须有一个代码段：程序总得执行一些指令，连一条指令都不执行，那还叫什么程序。

再看 `end`。它是汇编程序的**结束标志**。编译器在编译汇编程序的过程中，一碰到 `end` 就结束对源程序的编译。程序写完了，一定要在结尾加上 `end`，否则编译器不知道程序在哪里结束，就会一直编下去。

> **易错点**：`end` 和 `ends` 长得像，别搞混。记法很简单——`ends` 看成 `end segment`，是"段结束"的缩写，这样就好区分了。

最后是 `assume`。它的英文意思就是"假设"。它的含义是：假设某一个段寄存器和程序中某个用 `segment`/`ends` 定义的段相关联，通过 `assume` 来说明这种关联。在需要的情况下，编译程序可以把段寄存器和某一个具体的段相联系。

为什么要引入 `assume`？因为如果每次都要专门写 `mov ax, xxx`、`mov ds, xxx` 这样的指令去给段寄存器赋值，那就太麻烦了，每处都得多写那么多。有了 `assume`，就可以直接用它来标志代码段、数据段、栈段各自在哪里。

### 源程序与程序是两回事

这里要专门分清两个词：**源程序**和**程序**。

- 源程序文件里的所有内容，都叫源程序；
- 源程序中最终由计算机执行处理的指令或数据，才叫程序。

> **结论**：源程序和程序不相等。只有最终由计算机处理的指令和数据，才称得上"程序"。

程序最先以汇编指令的形式存在于源程序当中，经过编译连接后转变成机器码，才存进可执行文件里——这时它才是一个真正能被计算机执行的程序。

那源程序里除了伪指令和汇编指令，还有什么？还有**标号**。标号代表一个地址。比如 `codesg` 放在 `segment` 前面，就是给这个段起个名字，标示这个段叫 `codesg`；而这个段名最终会被编译连接程序处理成一个段的段地址。随后再通过 `assume cs:codesg`，把 `cs` 和这个段关联起来。

### 一个完整程序长什么样

把上面这些拼起来，一个完整程序的结构就清楚了。比如要编程计算 2 的三次方：

- 先定义一个段，因为程序至少要有一个代码段；
- 再把这个处理任务写进去——2 的三次方，就是在 `ax` 上不断加 `ax`，相加得到 8；
- 程序结束时写上 `end`；
- 最后用 `assume cs:abc` 把段和段寄存器关联起来（`abc` 就是这个段的标号）。

之所以能这样关联，是因为标号最终会被处理为这个段的首地址，`assume cs:abc` 就相当于把代码段的首地址交给了 `cs`。

### 程序返回：DOS 单任务下的交接

程序编译连接完，它只是一个文件。那它究竟是怎么得到执行的？

先说说我们当时用的虚拟机里的 DOS。它是一个**单任务**操作系统，当前只允许一个任务在执行。这就带来一个交接问题：一个程序 p2 存在可执行文件里，必须由一个正在运行的程序 p1 把 p2 从可执行文件加载到内存，然后把 CPU 的控制权交给 p2，p2 才能运行。p2 一开始运行，p1 就得暂停——毕竟是单任务。

反过来，p2 运行完之后，应该把 CPU 的控制权交还给之前让它得以运行的那个程序 p1，此后 p1 才能继续运行，我们也才能去运行别的文件、别的程序。

> **定义**：一个程序结束后，把 CPU 的控制权交还给使它得以运行的程序，这个过程叫**程序返回**。

那怎么返回？答案是在程序的末尾添加返回的程序段。之前看到的第一个汇编程序，末尾就有两条指令专门干这件事：它们把控制权还给之前把控制权交给我们的那个程序。

> **提示**：这两条指令为什么这么写，现在不用深究，后面会有讲解。这里只要记住它的性质——它是**汇编指令**，由 CPU 执行，因为要靠 CPU 才能把控制权传回给之前的程序。

把三种"结束"放在一起对照，就不会混了：

| 名称 | 写法 | 指令性质 | 谁来执行 |
| :--- | :--- | :--- | :--- |
| 段结束 | `段名 ends` | 伪指令 | 编译器 |
| 程序结束 | `end` | 伪指令 | 编译器 |
| 程序返回 | 程序末尾的两条指令 | 汇编指令 | CPU |

### 语法错误与逻辑错误

程序写出来难免出错，但错误分两类，处理方式完全不同。

**语法错误**是在编译时被编译器发现的错误，它是可见的——编译器会明确告诉我们错在哪里。比如把 `assume` 写错了，编译器立刻就会发现并指出位置，我们改掉就行；像 `end segment` 这类拼写上的问题，也很容易暴露出来。

**逻辑错误**就麻烦得多。它在编译时体现不出来，是运行时才发生的错误，因此不容易被发现。

举个典型的例子：还是那个算 2 的三次方的程序，如果没有写程序返回，把它丢进编译器编译，是不会报错的——因为语法上没毛病，只是少了一段返回。可是少了它就不行：程序执行完，没有把控制权交还给操作系统、也没交还给之前那个持有控制权的程序，结果就是操作系统停在那里，程序到此为止，后面什么都干不了了。

> **结论**：程序返回那一段代码必须补上。缺了它编译能过，运行却会卡住——这正是逻辑错误"不容易发现"的典型样子。

照上一节的做法，先把虚拟磁盘挂载好、进入 DOSBox。挂载出来的盘是 D 盘，所以后面提示符上显示的是 `D`，而不是常见的 `C`，这一点不用理会。进入 DOS 之后，我们就要用 `edit` 打开 DOS 自带的编辑器，把源程序一个字一个字敲进去。

一开始写程序都是照着写的，但照着写也得按我们之前讲过的结构来写。

### 在 DOS 里敲下第一段源程序

程序的第一件事是定义段：先用 `assume` 把段寄存器和我们自己的段名关联起来，再开始 `codesg segment`。接着写一个 `start` 标记，它的意思是标明我们的程序从哪里开始。再往下才是真正干活的指令：把 `0123h` 送进 `ax`，把 `0456h` 送进 `bx`，然后做加法。程序跑到最后必须返回——我们运行完一个程序之后，得把控制权还回去，所以要用 `mov ax,4c00h` 配合 `int 21h` 实现返回。

写完这些，用 `ends` 标志代码段结束，最后再标志整个程序结束。

> **提示**：`start` 这个标号只有在需要用 `end start` 指明程序入口时才有意义。这里程序入口就是第一条指令，不需要额外指定，所以最后没有保留这个标号，`end` 后面也不带操作数。

程序写完之后，得把它和相关的计算机、和我们保存的文件关联起来，整个汇编程序才算写完。保存的方式是用鼠标点 `File` 菜单，选 `Save`，在弹出的对话框里输入文件名。汇编文件的后缀是固定的 `.asm`，我们写的第一程序就取名叫 `1.asm`。填好选 `OK`，文件就存下来了。

```asm
assume cs:codesg

codesg segment

    mov ax,0123h
    mov bx,0456h
    add ax,bx
    add ax,ax

    mov ax,4c00h
    int 21h

codesg ends

end
```

### 编译：从源程序到目标文件

有了 `1.asm`，接下来开始编译，运行 `masm`。如果你用的是打包好的环境，编译器这些东西都已经准备好了，解压出来就能用。

在命令行输入 `masm` 进入程序之后，它会先问你要编译哪个文件。这里有两条规矩：

- 如果文件后缀是 `.asm`，直接输入文件名（这里是 `1`）就行；
- 如果保存时用的不是 `.asm` 后缀，就必须输入它的全名；
- 如果文件不在当前路径下，一定要指明它所在的路径；文件就在当前路径下，只输文件名就够了。

因为刚才保存时没有指定路径，文件就在当前目录，所以这里直接输入 `1`。

> **定义**：目标文件是我们对一个汇编源程序进行编译时得到的最终结果。编译这一步，产出的就是目标文件。

接着它问 `Object file name`，也就是目标文件的名字。默认是 `1.obj`，想改成别的名字就在这里写 `某某某.obj`。这里不用改，直接用默认值。

再往后问的是**列表文件**，它是编译器在编译目标文件时产生的中间文件，可以不生成，按 `n` 就行。接着问**交叉引用文件**，同样是把程序编译成目标文件时产生的中间结果，也不需要，照样按 `n`。

> **提示**：学到汇编，中间难免会碰到一些编译原理方面的知识。这些只要简单了解即可，不必深究，等以后学编译原理课程时再弄清楚。

当屏幕上显示出编译完成的信息时，就说明编译成功了。它输出的最后两行，就是告诉我们编译过程中有没有警告、有没有错误。一般来说，有两类错误会导致我们得不到期望的目标文件：一是程序中有严重错误（severe errors），二是根本找不到我们给出的源程序文件。

### 连接：从目标文件到可执行文件

编译只是把源程序变成目标文件，还得再做一步连接，才能得到可执行文件。接着上一节说过的，我们要把 `1.obj` 连接成最终的可执行文件 `1.exe`。

连接要运行 `link` 程序。执行之后，它先提示我们要连接哪一个目标文件。刚才用的是默认名 `1`，这里就直接输入 `1`。规矩和编译时一样：如果目标文件不是 `.obj` 后缀，就要输全名。输入目标文件之后按回车。

接着它问可执行文件的名字。可执行文件是我们对一个程序进行连接后要得到的最终结果，默认名字是 `1.exe`，要改就在这里改，不改就直接用默认值。

再往后提示的是**映像文件**，它也是我们把程序连接成可执行文件过程中产生的中间结果，不用管，直接跳过。最后它提示要不要连接某个库。

> **定义**：库，就像学 C 语言时一开始就要 `#include` 的 `stdio.h` 那样，里面包含了一些可以调用的子程序。如果我们的程序调用了某个库文件中的子程序，就需要在连接时把这个库文件和目标文件连接在一起，生成可执行文件。用 Java 的话说，这就像导包；用 C 的话说，就是 `include` 那个 `stdio.h`——我们要用 `printf`，就得先把这个头文件引入进来，才能使用那些比较基础的命令。

这里我们的程序没有调用库里的子程序，直接按回车过去就行。

连接过程中屏幕上提示了一个 `warning`：`no stack segment`，意思是没有栈段。`warning` 只是警告，不是 `error`——`error` 才是最致命、会让目标文件彻底得不到的东西，警告可以稍微放一放。这里程序很小，问题不大，不理会它就可以。

就这样，我们用连接器对目标文件做了连接，得到了一个新文件 `1.exe`。当然，如果连接过程中出现错误，那肯定就得不到最终的可执行文件。

那连接的作用到底是什么？这个问题值得想一想。

- **把大程序拆开做**：程序很大时，可以把它分成多个源程序文件分别编译，各自编译成目标文件之后，再用连接程序把它们连在一起生成一个可执行文件。比如开发一个程序，把它分成很多个模块，你做模块一、他做模块二、我做模块三，编写起来就方便多了。
- **把库接进来**：程序中如果调用了某个库中的子程序，就要把这个库文件和该程序生成的目标文件连接在一起，形成一个可执行文件。
- **处理目标文件里那些还不能直接用的内容**：一个源程序编译后得到的是包含所有机器码的目标文件，但目标文件中的有些内容还不能直接用来生成最终的可执行文件，连接程序要把这些内容处理成最终的可执行信息。所以，即使一个源程序文件没有调用任何库的子程序，也仍然必须用连接程序处理一遍目标文件，才能生成可执行文件。

> **结论**：可执行文件才是我们要得到的最终结果，编译和连接都是为了走到这一步。

顺便强调一下我们学汇编的目的：我们是通过汇编语言进行编程，深入理解计算机底层的基本工作原理，达到可以随心所欲控制计算机的目的。我们想直接对硬件编程，却又不想用机器码编程，所以要用汇编语言；用了汇编语言，就离不开编辑器、编译器、连接器、调试工具这一整套工具。而这些工具都运行在操作系统之上，所以学习过程必须在操作系统环境中进行，也就必然会牵扯到一些操作系统、编译原理方面的知识。我们只是借这些环境工具来方便学习，而不是让它们分散注意力，所以简要了解就好，不必在课程里深究，留到后续其他课程再去学习。

### 一条命令完成编译与连接

刚才那一遍步骤太繁琐了，中间文件其实都是可以忽略的——我们编译和连接的最终目的，就是用源程序文件生成可执行文件。所以我们换一个简洁的方式。

先把已经生成的 `1.exe`、`1.obj` 删掉，从头来一遍。编译时，直接在文件名后面加一个分号：

```dos
masm 1;
```

这个分号的作用是：让编译程序对后面所有的提问（目标文件名、列表文件、交叉引用文件）都直接采用默认回答，一路走完。因为 `1.asm` 后缀是 `.asm`，所以文件名写 `1` 就够了。这样一下就编译出了 `1.obj`。

连接同理，也加一个分号：

```dos
link 1;
```

扩展名正是对应的 `.obj`，所以直接写 `1;` 就行。连接完成后，`1.exe` 就生成出来了——这就是我们加工出来的、可以在操作系统下执行的汇编程序。

### 运行之后，屏幕上为什么什么都没有

要执行这个程序，直接打开 DOS，输入 `1` 就行。因为 `.exe` 是可以被操作系统直接执行的，扩展名 `.exe` 不用写，直接敲文件名 `1` 回车。

结果屏幕上什么反应都没有。那它到底运行了没有？

肯定运行了。我们在屏幕上看不到任何运行结果，是因为这个程序只是对一些数据做了操作，并没有把那些数据输出到屏幕上——它没有向屏幕输出任何信息，只是进行了一些数据的传送和加法运算，这些事情从显示屏上当然看不出来。程序执行完返回，屏幕上再次出现操作系统的提示符，这就标志着我们的程序是真正执行过了。

### 程序是怎样被装入内存并运行起来的

在 DOS 中，可执行文件里的程序要运行，必须先有一个正在运行的程序：由它把可执行文件加载进内存——只有进了内存，CPU 才能访问它；然后它再把 CPU 的控制权交给我们的程序，程序才能运行起来；程序运行完毕之后，还应该把控制权交还回去，这样才能保证后续其他程序也能得到运行。

这里可以顺势提出三个问题：

- 第一步操作里，那个正在运行、负责把 `1.exe` 加载入内存的程序，是什么？
- 程序被加载入内存之后，是靠什么让它跑起来的？
- 第三步操作，程序结束后，返回到哪里去了？

先猜一猜：那个正在运行的程序可能是一个操作系统；操作系统是一个软件集，由它把可执行文件加载入内存，再让 `cs:ip` 指向这个程序代码段的第一条指令，执行完之后返回操作系统。

#### 是谁把程序装进去又拿回控制权

答案落在一个概念上：**操作系统的外壳**。

操作系统是由很多功能模块组成的庞大而复杂的软件系统。任何通用的操作系统，都要提供一个称为 shell（外壳）的程序，用户是通过这个程序来操作系统的。DOS 也有这样一个程序——`command.com`，它在 DOS 中称为命令解释器，也就是 DOS 系统的外壳。

有了这层认识，前面的问题就清楚了：在 DOS 中执行 `1.exe` 时，是通过正在运行的 `command.com` 这个外壳把程序加载入内存的；随后 `command.com` 设置 CPU 中的 `cs:ip` 指向程序的第一条指令——必须设置了这一项，CPU 才会把它当成程序、才等于把程序的入口打开了，程序从而得到运行；程序运行结束后返回 `command.com`，CPU 继续运行这个外壳。

把整个流程串起来，从写出到执行是这样的：

```text
1.asm --(masm 编译)--> 1.obj --(link 连接)--> 1.exe
                                                │
                            command.com 加载入内存
                                                │
                       设置 CS:IP 指向程序第一条指令
                                                │
                          程序运行，结束后返回 command.com
```

读图说明：源程序经过编译、连接变成可执行文件，可执行文件由 DOS 的外壳 `command.com` 装入内存并设置好入口，程序跑完后控制权再交回 `command.com`。

#### DOS 加载 .exe 的过程

那么程序究竟被放到了内存的什么地方？在 DOS 中，`.exe` 文件的加载过程是这样的：

1. 先找到一段起始地址为 `SA:0000`（即起始地址的偏移地址为 0）的空闲内存区，容量要足够，才装得下。
2. 在这段内存区的前 256 个字节中，创建一个称为**程序段前缀（PSP）**的数据区。DOS 要利用 PSP 和被加载的程序进行通信。
3. 从这段内存区的第 256 个字节处开始，装入程序。
4. 把这段内存区的段地址存入 `DS` 中，并初始化其他寄存器，最后设置 `cs:ip` 指向程序的入口。

> **提示**：不理解 PSP 也没关系，我们并不研究 DOS 原理，只是借用它，知道内存里有这么个东西就行。程序加载时还有一步称为重定位的工作，它和操作系统关系比较大，这里不展开。

为什么要从第 256 字节处开始？因为 PSP 占了 256 个字节，也就是 $16^2$，写成十六进制就是 `100h`。空闲内存区从 `SA:0000` 开始，`0~255` 这些字节放 PSP，从第 256 个字节起才存放我们的程序。为了让 PSP 和程序区分开，一般把它们划分到不同的段里，于是有了这样的安排：

```text
        SA:0000  ┌───────────────────────────┐
                 │  PSP（256 字节）          │  ← DS 指向这里
   (SA+10H):0000 ├───────────────────────────┤
                 │  程序（1.exe 的机器码）   │  ← CS:IP 指向这里
                 └───────────────────────────┘
```

读图说明：内存区的前 256 字节是 PSP 区，用来存放 DOS 与程序通信的工具；PSP 区之后从第一个内存单元开始，才是程序区。两者在物理上是连续的，却有不同的段地址——PSP 的段地址是 `SA`，程序所在段的段地址是 `SA+10H`。

于是程序所在内存区的地址可以写成 `SA:0`，它的物理地址是 $SA \times 16 + 0$；因为 PSP 占了 256 字节，程序的物理地址是

$$SA \times 16 + 0 + 256 = SA \times 16 + 16 \times 16 = (SA + 10h) \times 16$$

用「段地址:偏移地址」表示，就是 `(SA+10h):0`。这也正是加载过程里把程序地址设为 `SA+10H:0` 的原因。

### 用 debug 看清每条指令到底做了什么

程序运行时到底对不对，光看屏幕看不出来。但我们可以用 `debug` 来观察程序。

用 `debug` 把程序加载入内存，它会设置 `cs:ip` 指向程序的入口，但它**并不放弃对 CPU 的控制**。这样我们就能用 debug 的相关命令一条条地执行程序，查看每条指令执行的结果。这是一种曲线救国的方式：在我们目前所学的知识里，还没有办法在显示器上把输出内容可视化地显示出来，那就通过 debug 查看寄存器里的内容，来判断程序到底对不对。

先执行 `r` 命令看一下寄存器的情况。可以看到，把可执行文件加载入内存之后，`cx` 中存放的是程序的长度——`1.exe` 中程序的机器码共有 15 个字节，所以 `cx` 就是 15（`0Fh`）。到这里我们又弄清楚了一件事：`cx` 的作用之一是存放程序的长度。

接着用 `u` 命令查看程序里的指令。反汇编出来的内容和我们写的源程序一一对应：先是对 `ax`、`bx` 的操作，然后是加法，最后是返回。再往下就是其他程序的内容，不用管，到返回的地方就结束了。

然后用 `t` 命令单步执行每一条指令，观察每条指令执行的结果：

- 第一步，把 `0123h` 放进 `ax`，`ax` 里确实是 `0123h`；
- 第二步，把 `0456h` 放进 `bx`，`bx` 里是 `0456h`；
- 执行 `add ax,bx`，`ax` 变成 `0123h+0456h` 的结果 `0579h`；
- 执行 `add ax,ax`，`ax` 再翻一倍，变成 `0AF2h`；
- 执行 `mov ax,4c00h`，`ax` 被置为 `4c00h`。

到了 `int 21h` 这一步，就不要再用 `t` 了，改用 `p` 命令执行。

> **提示**：`t` 命令会进入中断处理程序内部一条条地跟，`p` 命令则会把 `int 21h` 这类指令直接执行完再停下。这里记住到 `int 21h` 就用 `p` 就行。

用 `p` 执行 `int 21h` 之后，屏幕上显示 `Program terminated normally`，意思是程序正常结束。看到这一行，就说明我们的程序是正当、正常地执行完的。

最后用 `q` 命令退出 debug。

这里还有一层返回关系值得理清。在 DOS 里用 debug 时，是 `command.com` 先加载 debug，debug 再加载 `1.exe`。所以程序结束的时候，`1.exe` 是把控制权交回给 debug；我们再输入 `q`，debug 把控制权交回给 `command.com`。返回的顺序是：

```text
1.exe ──返回──> debug ──q──> command.com
```

如果是直接运行程序，没有经过 debug，那么程序结束后就直接返回到 `command.com` 这个外壳里。理清这一条链，前面讲的外壳加载、控制权交接就全都串起来了。

## 实验三：写出第一个不靠 debug 就能独立运行的汇编程序
> 对应块：BLK10 | 覆盖分集：P17 | 块标题（分集名）：《实验三写一个汇编程序》

好了，正式开始实验三——来写一个**真正的**汇编程序，一个不再依赖 debug、能独立编译链接、独立运行的程序。

不过在动手之前，先把第四章学过的东西回顾一遍。整个第四章的名字就叫「第一个程序」，它从头到尾都在回答一件事：怎么写出并跑起我们的第一个程序。

### 从源程序到可执行程序：编译器和连接器

一个汇编源程序（`.asm`）写完并不等于能跑，中间要经过两道加工：

```text
  源程序 (.asm) --[编译器]--> 目标文件 (.obj) --[连接器]--> 可执行文件 (.exe)
```

读图：源程序先交给**编译器**，编译成以 `.obj` 结尾的**目标文件**；目标文件再交给**连接器**，连接成最终的可执行文件。前者是目标文件，后者是可执行文件，两步缺一不可。

#### 编译：把汇编指令翻译成机器指令

编译器干的活很直接：把 `mov`、`pop` 这类我们自己看得懂的汇编指令，翻译成机器指令，也就是机器看得懂的形式。为什么非得翻译？因为我们写的程序最终要送进计算机里跑，就必须让它从「人能看懂」变成「机器能看懂」。这一步只能靠编译完成。

#### 连接：分模块组装，并告诉机器程序到哪结束

既然编译已经把汇编变成了机器指令，那连接器又有什么用？它有两个作用。

第一个，是方便我们把功能拆开写。当程序里有多个子程序、多个功能时，可以把它分成若干个模块分别编写；每个模块各自编译成 `.obj`，再一起丢进连接器里连接起来。

> **提示**：这就是「分成若干模块来写」的好处——各写各的，最后统一连接。

第二个作用，得从一个问题说起：程序被连接成可执行文件、加载进内存、开始运行的时候，我们知道第一条指令在哪——把 `cs:ip` 指向开头就行了。可我们有没有想过，**最后一条指令在哪**？我们怎么知道程序什么时候结束？

其实是知道的。因为每次程序跑完，它都会自己退出来，返回到外壳，返回到我们的 command、我们的 shell。既然机器知道该在哪结束，那这个「结束」的信息是谁加进去的？编译器的职责只是把汇编指令变成机器指令，管不了这件事，所以只能由连接器来做：**连接器负责给程序加上相关的描述信息**，计算机执行的时候才知道这个程序什么时候结束。

### 可执行程序是怎样被装进内存的

回顾完程序是怎么造出来的，再看它是怎么被**加载**的。

第一步，必须先把可执行文件从磁盘载入内存。这是一条本质：只有程序进了内存，我们才能用 `cs:ip` 指向它的第一条指令，它才跑得起来。

载入内存时，机器会先找一段足够大的空闲内存——内存里已经有别的程序占着地方，得挑一段空白、够装下我们这个汇编程序的区域，把它的起始地址记作 SA。然后：

- 先把这个起始地址设为 `SA:0`，并往里面存入一个 **PSP**；
- 真正的程序，从 `SA+10h:0` 才开始。

为什么是 `SA+10h`？因为 PSP 占 **256 个字节**，而 10h 个段正好是 16 × 16 = 256 字节。也就是说，PSP 和我们的程序是贴着放的，中间不留缝。

```text
   低地址
   SA:0        +----------------------+
               |  PSP（256 字节）      |  <- 机器与程序通信的地方
   SA+10h:0    +----------------------+
               |  真正的程序           |  <- cs:ip 指向这里
               |  （代码段）           |
               +----------------------+
   高地址
```

读图：`SA:0` 到 `SA+10h:0` 之间装的是 PSP，我们的程序从 `SA+10h:0` 开始。所以 `cs:ip` 要指向真正的程序开头，也就是 `SA+10h:0`，绝不能指向 PSP——PSP 是操作系统的东西。

那 PSP 到底干嘛用？它是计算机用来和我们的程序**通信**的地方。程序一旦被加载进来，机器怎么和它打交道？就靠这个 PSP。每一个程序被加载后都会有这么一个东西，机器通过 PSP 里的内容和我们程序进行交互。

> **提示**：PSP 是每个程序加载时都会有的固定区域，占 256 字节，位于真正的程序之前。

### 实验任务：把这段程序写成 t1.asm

回顾到此为止，正式动手。实验要求是：把下面这段程序保存为 `t1.asm`，再把它生成可执行文件 `t1.exe`。

```asm
assume cs:codesg

codesg segment
    mov ax, 2000h
    mov ss, ax
    mov sp, 0
    add sp, 10

    pop ax
    pop bx
    push ax
    push bx
    pop ax
    pop bx

    mov ax, 4c00h
    int 21h
codesg ends

end
```

写的时候，先把**代码段**写出来，最后再在上面补上假定与声明。

逐段看：

- `assume cs:codesg` 与 `codesg segment ... codesg ends`：这是假定与声明。编译、连接、载入内存之后，`codesg` 这个标记会自动变成代码段的首地址，也就是代码段的地址；这条语句的意思，就是把代码段的地址交给 `cs` 寄存器。`codesg ends` 标志代码段结束，最后的 `end` 标志整个程序结束。
- `mov ax, 2000h` 加 `mov ss, ax`：先把 `2000h` 送进 `ax`，再送进 `ss`。这里 `ax` 是当**跳板**用的——`ss` 不能直接塞立即数，得借一个通用寄存器中转。
- `mov sp, 0` 再 `add sp, 10`：设置栈顶指针，让 `ss:sp` 指向要用到的栈顶。

> **提示**：`mov ss, ax` 之后紧接着的那条指令会被立刻执行，设栈时不用担心两条之间被插进别的动作。

- 中间的 `pop ax / pop bx / push ax / push bx / pop ax / pop bx`：这才是这个程序的**真正目的**——演示栈的入栈、出栈机制，效果是让 `ax` 和 `bx` 里的值发生交换（下面细讲）。
- `mov ax, 4c00h` 加 `int 21h`：结束程序。程序跑完，得把主动权交还回去——交还给我们的 command、我们的 shell，所以用这两条作为程序结束的标志。

> **易错点**：`int 21h` 配合 `ax = 4c00h` 才是「结束程序」。用 debug 单步时，这条 `int 21h` 不能用 `t` 进去，否则会钻进中断服务程序里出不来；要用 `p` 把它一次性执行完。

### 编译、连接，生成可执行文件

进入 DOSBox 环境：先挂载磁盘，切到 `d:` 盘，打开实验目录，用 `edit` 编辑工具把上面的内容写进 `t1.asm`。

接着编译、连接。平时那套一步一步确认的流程太麻烦，这里用简化写法：在命令后加一个分号，就能跳过所有中间询问，直接得到结果。

```dos
masm t1;
link t1;
```

分号的作用就是「不需要中间步骤，直接帮你得到最终结果」。两条跑完，目录里就多了 `t1.obj` 和 `t1.exe`，可执行文件确实生成了。

### 用 debug 逐条跟踪执行

现在用 debug 跟踪 `t1.exe` 的执行过程：

```dos
debug t1.exe
```

进来先看一下寄存器状态，确认无误，再逐条往下走：

- 第一条 `mov ax, 2000h`：用 `ax` 当跳板，把 `2000h` 这个数送进 `ss`。
- 接着 `mov ss, ax`：因为讲过中断机制，这条执行完之后，紧随其后、给 `sp` 赋值的那条也会自动执行。
- `mov sp, 0` 把 0 放进 `sp`，`add sp, 10` 让它加上 10，`sp` 变成 `000A`。
- 然后连着一串 `pop` 和 `push`。

> **易错点**：跟踪到最后的 `int 21h` 时，如果习惯性按 `t`，会进入中断服务程序。改用 `p` 执行它，才会看到 `Program terminated normally`（程序正常结束）。我第一次在这里翻了车，只能把程序重新加载一遍再跟踪——那真是大型翻车现场。

### 栈的入栈出栈：两个值为什么交换了

这个程序要我们看的，就是栈的**入栈、出栈机制**：先出栈、再入栈，值的顺序会跟着变。看着挺奇怪——我们执行的 `pop`、`push` 顺序明明一模一样，可最后 `ax` 和 `bx` 的值居然交换了。为什么？

先把栈画出来。假设 `ss = 2000h`，`ss:sp` **始终指向栈顶**，栈顶里放着数据。我们把两个元素记成 `1` 和 `2`：

```text
   初始：ss:sp 指向栈顶
   地址          内容
   2000:0Ah      [ 1 ]   <- sp
   2000:0Ch      [ 2 ]
```

读图：`sp` 指着栈顶那个 `1`，下面一格是 `2`。先出栈：

```text
   pop ax  ->  ax = 1     ; 取走栈顶后，sp 加 2
   pop bx  ->  bx = 2     ; 再取一次，sp 再加 2
```

读图：`pop ax` 先取走 `1` 给 `ax`，`pop bx` 再取走 `2` 给 `bx`，`sp` 一路往上走。

接着把这两个值按顺序压回去：

```text
   压栈：先把 sp 减 2，再把值写到新的栈顶
   2000:0Ah      [ 2 ]   <- sp
   2000:0Ch      [ 1 ]
```

读图：`push ax` 先把 `ax`（值 1）压回，`push bx` 再把 `bx`（值 2）压回——但注意，压回去时 `1` 落在了原来 `2` 的位置、`2` 落在了原来 `1` 的位置，两个值在地盘上已经换了位。

最后再取一次：

```text
   pop ax  ->  ax = 2
   pop bx  ->  bx = 1
```

读图：`ax` 从 `1` 变成了 `2`，`bx` 从 `2` 变成了 `1`——交换完成。

这就是答案：**入栈、出栈本身遵循「后进先出」**。入栈时先把 `sp` 减 2，再把数据放进新的栈顶；出栈时先把栈顶数据取出，再让 `sp` 加 2。正因为数据是经过栈顶一进一出，顺序才被颠倒过来。`ax` 和 `bx` 的值之所以交换，完全是被这个入栈、出栈机制「带」出来的。

> **结论**：栈是后进先出。想让两个寄存器的值互换，用 `pop` 和 `push` 一进一出就能办到。

### 查看 PSP：程序头部的 256 个字节

实验还没完，最后要查 PSP 的头两个字节是不是 `CD 20`。

用 debug 加载 `t1.exe` 查看 PSP 的内容。因为刚才讲过：程序被载入内存时，先找一段空闲内存，起始地址记为 `SA`，设为 `SA:0` 存入 PSP（用于机器与程序通信），PSP 占 256 字节；真正的程序从 `SA+10h:0` 开始。

所以 PSP 就在程序的正前方。用 `d` 命令查看内存内容。假设此时 `cs = 076Ah`，把它减去 10h 得到 `075Ah`，于是 PSP 位于 `075Ah:0`：

```dos
d 075a:0
```

结果开头清清楚楚就是两个字节 `CD 20`。到这儿，实验圆满结束。
