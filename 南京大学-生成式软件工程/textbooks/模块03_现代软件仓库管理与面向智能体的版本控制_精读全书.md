## 从一个目录到 Git：项目级时光回溯
> 对应块：BLK05 | 覆盖分集：P04上 | 块标题（分集名）：《软件仓库管理（上）》

前几次课我一直在讲怎么把 AI 整合到你们的流程里。你们在生活中会遇到无穷多不顺心的事——用很多东西都会感到不顺心——而 AI 作为一个非常强大的 assistant，可以帮你把这些不顺心挡掉：你只需要告诉它你真实的意图就可以了，甚至还可以把过程蒸馏成 skills，让这件事变得更平顺。

在这个过程里，我们不断地看到新模型的进展。GPT-4o 就真的发布了，你们用上了吗？我用了一下，还是有惊喜的。编程上的提升可能有限：我说过，我们现在有经验的软件工程师还有比较好的品位，这个品位可以指导 AI 做出更好的东西；而 AI 现在更多的时候是在完成任务，好像还没有学会这种好品位，我经常还要骂它，所以我觉得我可能还能再苟活几个月。但它在各方面的能力确实都提升了，做更复杂的任务时它变得更快了，省很多 token，我特意 measure 过，真的是这样的。

我们什么时候会觉得它做得不好？还是因为我们面对了一个非常开放的 intent → spec → implementation 的空间。同样的一个任务，比如"给我做一个国民级的应用吧"，每一个人——哪怕是顶级的程序员——脑袋里面想的都不一样，AI 没有办法和人脑直接做这样的对齐，所以它一定会按照它自己的方式去漂移。我还发现 AI 写出来的代码越来越难读了：思维链变得非常非常紧凑，写出来的代码也就非常紧凑，人越来越不想看它，没有办法 review。曾经我们还会用各种各样的 prompt 要求它"写出符合人类工程规范的代码"，但现在我们也不再看 AI 写的代码了，就随它去吧，反正它能把代码弄对。

GPT-4o 给我们最大的惊喜，是它空间感知和理解的能力。我一直认为 OpenAI 对 AGI 的理解是这样的：首先 AI 得学会数学。数学是所有人类世界里最难的那一种语言，因为它有一个世界上所有人都认同的推理系统——一个定理你能证明出来，全球的人都会认为这个证明对或者不对，所以它是一个非常好的能 grounding 的东西。而且数学的逻辑推理可以解释我们人类生活里的各种行为。比如今天中午吃什么、去几食堂，你们可能觉得这是人类世界里的问题、必须是你的灵魂来给出答案的，但其实不完全：你大脑里面不停地在投票。我就会选择在一食堂订饭，因为对我来说这是最快的选项——我下午还要开会，如果时间来得及，我中午可以小睡一会儿。你看，我其实是在各种因素之间投票，而这些因素之间有"如果我做了 A 就会做 B"这样的关系，这其实就是你们在离散数学里学的那种命题逻辑里的东西。所以 OpenAI 应该是这样想的：先把数学学会——数学它好像已经学会了——学会了以后，再去强化学习别的能力。

而空间感知，它不是绝对学不会的。给你一个鲁班锁，那么复杂的结构，我问你按照什么样的方向可以把第一块东西抽出来；给你一个立方体或者奇怪形状的投影，问你哪一块和它是一样的；给你一个六面的骰子，问你哪一个展开图对应你看到的那个骰子——你们从小到大就会做这种智力题，你就在脑袋里做空间想象。而这种空间想象，只要从简单的任务开始强化学习，肯定能做到。

我当时看到那个例子的时候，GPT-4o 还没有发布，我还心疼我的 PhD student，因为我们已经做了大半年的 3D 打印工作了。在模型空间感知能力很差的情况下，我们通过直接对话也已经能生成一个还是很像样、各方面都能符合规范的 3D 打印模型。我们有一些比较 killer 的 application，比如那种光栅玩具、光栅尺——从左边看和右边看是两个不同的图案，你只要说"我要做这个"，背后本来需要一棵很长的搜索树。结果 GPT-4o 昨天 one-shot 直接搞定，我们现在还在想怎么解决这个问题。同样因为它有了空间感知能力，又有数学能力，它在具身赛道上就明显可以做得很好：第二天你就看到很多人在小红书上发用它直接控制机械臂做抓取、叠衣服这样的复杂动作。注意 GPT-4o 是一个语言模型，虽然有视觉能力，它就是一帧一帧地问你下面要干什么，还没有解锁提示词的 engineering，就已经达到了一个 state of the art 的能力范围。所以模型一定会进步，这个例子告诉大家——也许我上课上到某一次，就突然说这个课不用上了，这样也好，大家就可以去做产品了。

那我们为什么还需要学软件工程的知识？AI 解锁的是你的执行力。有人问过我：在 AI 的时代，为什么还要学数据库、学操作系统、学这些东西？我的答案其实也不是特别确定，但我打了这样一个比方：回到 100 多年以前汽车刚发明的时候，汽车开个一两公里就会出故障，所以每一个 driver 都必须对汽车的工作原理了解得非常清楚，因为一旦出故障，你得知道它是怎么工作的。回到那个时代，这是理所应当的：你想要开车，就需要掌握汽车的基本原理；你要学 computer science、要去软件工程的工厂，就要去学操作系统、学数据库，把这些基础知识做好。

但想想今天我们是怎么样开车的：在地下车库直接说"帮我开到什么地方"，自动驾驶汽车就出发了。作为一个普通人，你已经不理解整个系统栈上面是怎么工作的了——虽然它最终的动力还是传递到一个机械装置，和 100 多年前的汽车还有一点相似，但在这个过程中经历的所有东西你都不需要知道，你就可以把汽车开起来。

> **结论**：人工智能也可以想象成类似汽车这样的东西，当然它比汽车更强——它替代的不仅是人腿部向前走的能力，还替代了人的智力。那我们是不是还要学？我今天的答案肯定是要学：学了以后，你可以更好地解锁 AI 的创造力。但以后应该怎么学，我暂时还不知道，你们如果有答案，也欢迎来和我探讨。至少在现在的阶段，学习是有好处的——你理解了正确的概念，可以帮助你从别的地方借鉴一些知识，来创造更好的东西。

### 做项目的第一个动作：建一个目录

今天进入真正的软件工程。如果要开始做软件工程、开始 vibe coding，你干的第一件事情是什么？你不是从网上或者老师要求的地方下载一个东西——如果你今天真的是想做一个项目，你做的第一件事一定是先建一个目录，然后给它起一个名字，可能起个中文名字叫"我的最酷的 GalGame"，然后你就开始 vibe coding。

那什么是一个软件工程的项目？你创建了以后，面对一个空目录的时候，你还记得你们是怎么学会应该做什么的吗？你们可能看到老师上班的时候打开了一个工程项目，里面有一些文件，哪怕是不经意之间，你也记住了一些东西；也可能有人向你推荐"什么东西发布了，你可以去看看"，然后你得到一个 GitHub 或者 Gitee 的链接，打开以后那是一个网页，网页还是非常人类 friendly 的，上面有一些文件，你就知道我的一个目录里面会有一个文件。

> **结论**：当我们说要开始一个软件工程项目的时候，你就会建一个这样的目录，它里面有一堆文件，这堆文件共同构成了一个可以交付的东西，这个东西最后会变成你的产品。

这个目录可能是直接在你本地运行的：你神奇地跟 agent 说"请你帮我运行"，那个窗口就弹出来了，或者网页就弹出来了。这里有一个著名的笑话——GPT-4o 太牛了，我又做了多少个 killer 级的 app，它们是 `http://localhost:5137`，然后发一个 Twitter。所以你还是需要知识的：你在本机可以打开它，但世界上的其他人打不开，因为如果你不知道 `localhost` 是你的本机，你就不知道问题出在哪里。

当然你可以通过把你的 intent 和 specification 说得更清楚一点来解决：如果你在文档里面就说明"我的这样一个东西要被全世界人看到"，它就会去部署；如果你不说，模型可能会把你当成一个开发者，而开发者最正常的一定是在你本地先调试——先起一个本地的 development server，然后你看它的结果，直到你觉得 ready 了，你才会把这个东西送到远端去。但这都是知识：你们是 computer science 的学生，上各种各样的课的时候反复学习这些知识。

你们从最开始学编程，可能是在 Visual Studio 里面一键编译和运行；到后面你们学的时候会知道，`build` 目录里面所有的东西都是由某些命令行的工具创建出来的。你们会开始在大二的时候用一些像 GCC 这样的命令行工具，把一个 `hello.c` 变成一个 `hello` 的 binary。这就构成了一个软件工程的项目。

所以你们会听到这样的一个标准的定义：什么叫软件？这是一个很好的问题，以前老先生很喜欢问我们什么是软件。软件是一个如此基础、无处不在的东西：你想想，没有软件，你们今天看到的是黑的——你不光看不到我，你连这个台子也启动不了。我这个升降桌，如果没有软件，它都是升不起来、降不起来的（这边还有一个高度的显示，现在是 106 厘米）。

> **定义**：有个标准定义说，软件是代码、文档等等一切和软件相关的东西的集合。而我一直在说，软件是人类世界的需求在信息世界的一个投影，这个投影今天看就是一个目录，目录里面有各种各样的东西。

That's all。你知道目录里面应该有什么——比如有一个 `hello.c`，然后你可以编译出一个 `hello`，你就已经在做软件了。这当然可能不符合现在软件工程的最佳实践，但在古老的时期，甚至 10 年以前，大家真的是这样的。

### 从 U 盘、作业 v1 到 Git

给大家讲一个我第一个 PhD student 的故事。他 2012 年入学南大，大一的时候他发现了一个非常好的学习方式：他经常会去机房，因为他自己的笔记本电脑屏幕比较小，也不是很舒服——不像现在，我相信你们都会买一块屏幕，不贵，淘一个二手的只要小几百块钱，你可以在宿舍获得非常好的编程体验——但那个时候标准答案是去机房，来回拷贝代码比较麻烦。所以他想出了一个妙招：大一的时候把代码保存在 U 盘上。你们多多少少也干过这样的事，或者在中学上电脑课的时候，你做的作品就保存在 U 盘上。结果到他大二的时候，这个 U 盘坏了，代码全部都没有了——作业不见了，他珍藏的那些起步时候的作业也不见了。有一点伤心，但好像也没有太大的关系。

我们很长时间都是这样管理代码的。我记得我上学的时候，交作业的方式是打一个压缩包发邮件，现在你们会在一个网页上面上传。还有一种非常直觉的做法：作业 v1、作业 v2、作业最终版，每次复制一个目录。这没问题，这是一个非常直觉的体验，而且这个方式可以找回旧的文件——万一有一天你手滑了，或者不小心改错了（尤其在新手阶段，不小心有一个误操作是非常正常的），你想回去上一个版本看一看，到底我上一版本是怎么写的。

从这样一个需求出发，你自己就能发明一个像 Git 这样的东西。什么是项目？项目就是一堆东西——你的代码、文档、intent、spec、implementation、各种东西、测试用例，全部搅在一起，没问题，一个目录。然后你会想：如果我们能够把目录的版本管理起来——我不再叫作业 1、作业 2、作业 3，我只有一个作业。一个作业的目录，但是我可以提供一个命令行工具，说"我能不能看一看 list、作业的版本是什么""我能不能把当前的版本变成另外一个版本、回到过去的一个版本"——你不就已经发明了一个简化版的 Git 吗？虽然你还没有使用任何分支、合并、冲突这些概念。而当你用着用着，你要跟你的室友同步了，你们俩一起改同一个文件，你就会坐下来想"一起改了同一个文件应该怎么办呢"，于是你又发明了 Git。

> **提示**：从已有的经验出发——你知道什么、你想要什么——就可以推出下一个概念应该是什么样的，这个推演过程本身就是数学式的推理。我上课这样讲下来的时候，每一句话都和之前有逻辑关联，而这些关联多多少少都有一些是数学的联系。所以 OpenAI 认为它要把数学先训好，训好以后所有问题它可能都能解决，然后这件事情可能就真的要成真了。我自己觉得，品位可能也是能解决的。

而软件工程在今天是有的标准答案的：你应该去用 Git。

> **定义**：Git 除了能够保存一个目录（项目是一个目录，目录里面有 `hello.c`、有这个 `hello` 的 binary，还有文档等等），它还能保留、比较和恢复历史的版本。

这是一个很重要的软件工程的特性，我后面会详细展开来讲。

有了 Git 以后，其实很多事情都变得很容易。比如我再也不需要发邮件了。今天在 agent 的时代，我们有了 10 倍、100 倍的生产力提升：我只要让它去帮我写一个投诉 complaint，我就什么也不用管。比如我今天用我的 Codex，我就真的选择信任它，我真的就不管了，这事就过去了，我甚至看都不会看，我让它结束以后把这个浏览器给关掉。但过去的时候，我们真的还在用邮件管理项目。

后来有了 Git 以后，我们发现效率高了很多：我们可以用 `git clone` 去从一个远端获取一个作业；如果作业更新了，我在远端更新，就不需要给每一个同学都发一个压缩包了，我只需要在上课的时候告诉同学们"我的作业更新了，你们用 `git pull` 去下载"；以及我上课的时候有一个 `make submit`，它会自动用一个脚本把包打好，打好以后上传到我的课程网站，非常方便——这有点像一个 CI 流程。CI/CD 我们应该会有专门一次课来讲。

### 学习意识比知识更重要

这引出一个我几乎每节课都要讲的事情：当我们今天学习变容易了以后，这门课上讲的知识都不重要，重要的其实是你们的学习意识。

#### 从别人的项目里读出 best practice

你们肯定都看过很多 Git 的项目，哪怕你打开课程作业，都会看到它有一个 GitHub 的链接。那你有没有留意过不同的项目它们之间细微的区别？比如有的项目有这个文件，有的项目没有那个文件；有的项目里面文档是这样写的，有的项目文档是那样写的。你在这种不停地有信号进入的时候，其实你就能判断出我们应该怎么用 Git。

我不知道大家是不是总有一种感觉——这跟中学的时候有关系吗？中学的时候老师说的事情实在是太多了，你必须要听老师的话，才能把所有的事情做完；如果你不听老师的话，你不可能把事情做完。但到了现在，比如你去 GitHub 学习的时候，如果你还带这个心态——老师说"好，你去把作业拉下来"，那你就只做这件事，绝对不会多碰一点点，因为这是最省时间的。你就有点像 AI：像新开干活的 AI，你被强化学习成了"当老师说让你做这件事的时候，你只做这件事"。AI 也被调成这样了。

但如果你愿意其实我就劝大家，愿意多花一点点时间去点进去看一下里面的各种东西，你可能突然之间就有一个灵光一现：这个文档写得很好嘛。因为你马上觉得，今天你看到那个满世界 GitHub 上面的项目，全部都是巨长无比的 README，README 里面有各种 Unicode 字符组成的目录结构、框图——这种 AI slop 的感觉你马上就有了。你有没有留意过这些细节？然后在你看了这么多 AI slop 的时候，突然你发现了一个什么老项目，十几年、几十年前开始维护的老项目，点进那个文档，清新、舒服，README 很短，但是 README 看完以后，你想看的东西，三个链接你就走过去了，你不需要看那么长的 AI slop。啊，你就学会了文档应该这样写。

我举个自己的例子。你们有没有机会去对比不同的城市的路牌？我觉得这很有意思。很多年以前，我在香港的时候要去找路，我发现每当我有不确定性的时候——比如我前面有三个口——我正前方一定有一个路牌告诉我这三个口是什么。它有一个非常复杂的地下系统，但从来没有让我瞎找。回到南京城，你经常会在地铁站里找"我下一步应该到哪一个口"，你环顾四周去寻找，甚至要移动比较远的距离找到一个地图再去看。这其实是一个学习的过程：如果有一个范例比你做得好，你就学到了。

在这个对比当中我学到的 lesson 是：如果我要做一个 UI 设计，我的 UI 就应该是站在人的角度——人站在这一个页面上的时候，他会想什么？不同的人他要 a、b、c，他会去向不同的方向。我希望用最少的方式把 a、b、c 全部呈现出来。所以你看，一个 README 也是如此：你们都会用 AI 生成 slop README，但当你看过几个好的以后，你就会写 README 了。而且你有了 AI 以后，马上就可以问它：为什么我看到这个项目的 README 没有 AI slop 的感觉？它就会告诉你。

> **结论**：这也是我理解的、为什么很多同学怨气很大、觉得上课耽误学习——因为现在课外的信息量和信息密度，已经远远超过任何一个课堂可以做的事情了。你打开一个成熟的 GitHub 项目，它是这个工程师十几年的心血，甚至在某一个时间点、十年以前，这个项目崩溃过一次，它做了一次大版本的重构，发现以前的那个 practice 不够好，你才看到呈现在你面前的是一个现在好好的东西。但传统的教学方法没有教过大家怎么样把这些海量、信息密度巨大的东西用好，大家也没有准备好去拥抱这样的知识。

我站在这里做老师，大概就是因为我这种惊人的注意力；而大家其实要训练的，也是那种惊人的注意力。

#### 读论文与学课程通用的一招：先自己实现一遍

教大家怎么学习。如果你要读一个 research paper，很早的时候大家就有一个推荐的读法，这个学习方法也适用于大家学任何课程，包括你们的高等数学、你们的计算机系统基础，它叫 virtual implement：你现在有一个具体的问题或者具体的需要，你现在脑袋里面把这个问题自己做一遍，你会得到一个什么样的结果？如果你做出来的方法和作者的方法是一致的，那很好，说明你已经学会了、完全掌握了这个知识。如果不一致，还有两种情况：

一种是成熟的、好的教科书上的方案比你想的那个方案要好、要精巧、要简洁，你就会想"为什么他能想到"，他就变成你知识的一部分；还有一种情况，那就真的是惊喜中的惊喜——你的方法比他还要好。也许你一万次才会遇到一次这样的体验，但这个体验给的正反馈也很大，你会突然想"我能不能去做一个什么什么好玩的东西"。

> **提示**：我自己看任何东西之前，大脑里有一种能力：先把看到的所有东西都忽略掉，想"如果我要自己来解决这个问题，我会怎么做"，然后立即比较我看到的东西和我脑袋里所想的东西谁更好。如果我自己做得更好，我就认为这是一个 slop；如果我发现它做得比我好，我就很惊喜——"它为什么做得比我好？"养成这个习惯以后，这是一个非常恐怖的习惯，因为你在任何时候都在疯狂地从外面接受信息。

所以在 AI 时代，你们更可以对细节保持注意力：去看各种各样的 Git repo，读别人写的、甚至 AI 生成的东西，都要有感知细节的方式。这是我开一个头，然后我们就可以讲关于 Git 的一些具体细节。

### 冲突为什么要把两边都摆在你面前

首先，为什么要有 Git？当然，肯定是因为有了 GitHub 以后，分发代码变得前所未有的方便。这件事情他们创立 GitHub 的时候可能就想到了，但他们没有意识到，它竟然成为了今天 AI 时代的一个底层的技术设施——npm、你所有的各种 Neovim 的配置，全部都在 GitHub 上。

上周末我参加了保研的面试，你们应该也会在一两年以后来到这个场合去面试。我就问大家"什么是 Git"。大家多多少少都能说两句：我可以从 GitHub 那里下载、分发代码，也有的同学可以讲到 Git 管理项目目录的快照。我觉得也没有必要把所有人都挂掉，你能讲一些就可以，取决于你能讲多少来给你一个评估。但 `git rebase` 是 0/10，这个也意料之内。比较意料之外的是，我问大家：如果 Git merge 发生冲突以后，会观察到什么？你们有观察到过吗？

比如你的作业，老师发布了一个更新，而你在本地已经把这个东西改得面目全非了。这个时候你还是会让 agent 说"来吧"，然后 agent 就啪啪啪啪啪给你修好了，反正跟你说"好了"；我现在也是的——"merge 出错了，来帮我修"，最后它说测试都通过了，我看一眼这个东西看着还 OK。这个时候惊人的注意力就有用了：如果你愿意在冲突的时候停下来（大家作为学生总是想"我再学一点嘛，反正就一秒钟，我学一下也没有坏处"），你会看到一个非常神奇的东西——有好多等号，有好多箭头。

```text
<<<<<<< HEAD
int x = 2;          ← 你本地这一支把这一行改成了 2
=======
int x = 3;          ← 要合进来的那一支把它改成了 3
>>>>>>> other-branch
```

冲突以后并不是立即就被 resolved 了，这个责任曾经是到了每一个开发者手上：如果开发者发现了冲突，那开发者有义务要把这个冲突给解决掉；而他要解决掉，他就需要能看到这个冲突。如果你是 Git 的设计者，你要想一想：现在有一个文件原本是 `1 1 1 1`，然后有一个人把第二行改成了 `2`，有一个人把第二行改成了 `3`，那这到底是 `2` 还是 `3` 呢？Git 不能说"对不起，冲突了，我不能合并了"然后就躺在那儿，那对人的负担是非常大的：我到底应该把 `2` 放进来，还是应该把 `3` 放进来呢？

所以它把冲突的两部分代码同时显示在这里。这和我刚才无意中举的那个地铁标示的例子是同一个 first principle：如果你现在发生了一件事，那最好就是在这个地方把它所有要的信息全部都表明了。如果你用像 IDE 这样的工具，上面还会多出一些按钮，比如 accept incoming change，你就可以在 IDE 里面自己 resolve，自己决定谁进谁出。完了以后，你可以再创建一个 commit，把这个 conflict 给 resolve 掉。

> **易错点**：你只需要一点注意力。其实只要有一两次，你就会有一个印象，至少你能说出"两边这个冲突的代码都会显示在一起"。这一题在面试里大家答得不好，原因无非两个：第一个是没有用过、没有开发过——其实就算用 agent 开发，你也很容易遇到这种 conflict，只要你要 agent 在不同分支上开发；第二个还是没有留意。所以比较重要的是，第一个去多用用，第二个试着去拥有更好的注意力。

### Git 是怎么来的

在 U 盘上面放一个目录的方式是不行的，每次打一个包；但"作业 v1、作业 v2、作业最终版，每次复制一个目录"这种方式，可以找回旧的文件。你想回去上一个版本看一看，到底我上一版本是怎么写的——这不就是回到过去某个版本的需求嘛，从这样的一个需求，你自己就能发明一个像 Git 这样的东西。

> **提示**：这体现了人类的局限性。在 Git 之前，我们还用过一个你们可能听都没有听过的东西，叫 SVN，`check-in`、`check-out`。

SVN 和 Git 的设计是不一样的。SVN 是这样的：我们存储的是项目的变化。只要你有一个最初的版本，然后每一次你这个文件改了一行，我就存一个 patch；再改一行，再存一个 patch，存一个 patch，存一个 patch。好像没有问题，这是一个非常高效的实现。但就是这个高效，随着项目的增长，把大家拖回去了，拖入了泥潭。Git 的这个模型要干净得多。

```text
SVN：只存变化（每个版本一个 patch）
  v1 ──patch──▶ v2 ──patch──▶ v3 ──patch──▶ v4
  想回到 v1：只能沿着 patch 一个一个往前推

Git：每一个提交都是一份完整的快照
  c1(快照)      c2(快照)      c3(快照)      c4(快照)
  想回到 c1：直接取那一份快照，一秒就回去
```

> **结论**：这就是所谓的 first principle——我想要回到过去的某一个版本，马上、一秒钟就给我回去。而如果你每一次存的都是一个 delta，你想回到一个早期的版本，你就得一个一个往后推。当然你可以用一些缓存之类的方法来优化它，但我觉得好像确实走错了，走错路了。

Git 基本上就是这样来的，它的作者是 Linux 的作者 Linus。他们在 1991 到 2002 年的时候，如果想要维护 Linux，就是用的"作业 v1、作业 v2"的方式：在邮件列表上面发补丁——相当于我改了一个 `a.c`，我说我有一个 `a.c` 新版，往邮件列表上一发，然后会有一个 maintainer 看到，把它放到他的核心仓库里，然后再去 release 这个版本。后来他们还用了其他一些工具，比如 BitKeeper。直到 Linus 终于受不了了，他觉得我们就应该要一个绝对简单、但又非常好用、概念正确的版本控制工具，所以在 2005 年的时候做了 Git。所以它比我们想象的年轻一点，2005 年。有兴趣的同学可以去看那个 Pro Git——当然，直接让 agent 看就可以了，你不需要再去读了；我读书的时候我们都是看过这些文档的。

| 管理方式 | 存什么 | 回到旧版本 | 协作与分发 |
| :--- | :--- | :--- | :--- |
| U 盘 / 目录副本（作业 v1、作业 v2、作业最终版） | 整个目录的复制品 | 找到那个副本即可 | 拷来拷去，介质坏了就全没了 |
| SVN | 项目的变化，一次改一行就存一个 patch | 要沿着 patch 一个一个往后推 | `check-in` / `check-out` 的工作方式 |
| Git | 每一次提交的一份完整快照 | 直接取快照，一秒回到过去的版本 | `git clone` / `git pull` / `git push`，分发前所未有地方便 |

That's it。我们需要项目级的时光回溯。我们都会犯错误，所以我们只要能去 Git 的历史里面把它捞回来就可以。你们可以试着用这种方式：从已有的经验，你知道什么、你想要什么，然后推出下一个概念应该是什么样的。

### 上手：init、add、status、commit

那什么是 Git？我建一个空的 terminal。大家也都知道，你今天如果要开启一个项目，那就是 `git init`。

```bash
git init
```

它会告诉你一些奇怪的信息。这个时候你有两种选择：第一种是让 agent 来帮你解决、帮你回答你不懂的问题；还有一种就是把它忽略掉。显然是前者更高效——这才是更好的学习方法。你就得到了一个目录，一个 `.git` 目录；当然 `.git` 目录默认是不显示的，所以你看不到它。这就全部了：当你做完 `git init` 以后，你的项目就变成了一个被 Git 版本管理的仓库，然后你可以从远处拉取代码，也可以把代码推到远端去。

最基础的命令，比如说我有一个 `hello.c`：

```bash
git add hello.c
git status
```

用 `git status` 就可以看到，我现在的这个工作区里面有一个 `hello.c`，这里还有一些提示。

> **定义**：Git 很重要的是创建项目的快照，使得你可以在任意时间之间穿梭。

所以我们可以创建一个有消息的快照，这就是 `git commit`。这很重要，它体现了软件工程的智慧。你看，之前我们用复制粘贴的方式，命名为目录 1，不对，是项目版本 v1、项目版本 v2、项目版本 v3，作业 v1、作业 v2、作业 v3；但在 Git 的世界里面不是这样的。

而且我看到很多同学在用 Git 的时候，就是把 Git 当成作业 v1、作业 v2、作业 v3 来用的，但这不是 Git 推荐的 practice。在长期的软件工程实现实践的经验当中形成的 practice 是：你每一次对这个项目做了任何的改动以后——比如说改了一个文件、修了一个 bug、给它增加了一个功能、调整了某一个脚本或者某一个文档——你都应该立即做一次 `git commit`。它会打开一个文本编辑器让你写：

```bash
git commit
```

这个文本写"我这是做了什么"，写好、保存，这个提交就成功了。这些你们都可以在现有的项目里面看到他们是怎么协作的：有些 Git 提交可能比较大，他们放了一个 feature；有些就比较小，就是 fix 非常少的东西。所以当你面对这样一个新鲜的工具的时候，去理解它的 best practice 还是需要花时间的。

> **结论**：你还是不能把所有的事情都交给 AI，你还是多多少少要知道我们为什么要做这件事：什么时候应该做 `git add`？什么时候应该做 `git commit`？`git commit` 的 message 应该怎么写？你真正需要的是在任何时候学习——碰到这个新东西的时候，追问一下"你刚才做的是不是符合 best practice"。

### 水面下的冰山：提交信息与提交力度

比如说我刚才做了一个 `git commit`，这个符合 best practice 吗？这时候你问一下（加上豆包输入法，真的就是一秒钟的时间），它会给你很多解释。它说这个 commit 不太符合 best practice，主要问题在提交信息，其次代码本身也有问题——提交信息的可读性有问题：我故意做了一个 `I did some cool stuffs`，完全看不出做了什么。

> **易错点**：Git 本质上虽然存储的是版本的快照，但我们的项目本质上还是从一个版本 v1 经过一次修改变到 v2。所以 Git 鼓励的是，你需要在 message 里面描述出你改了什么。相当于你如果一直看下去，你就知道这个项目是怎么发展、一直走到现在的：修了多少个 bug、加了什么需求、经历了什么样的重构。你可以在 message 里面看到这个项目历史的轨迹，这是它鼓励的，也是一个好的软件工程的 practice，使得别人能够更容易地理解你的项目。

所以如果你每一个提交都是 `I add some cool stuffs`，你想想如果有一万个提交以后会变成什么？这个 commit message 就变成 slop 了。如果一万个提交都是 `I did some cool stuffs`，那它如果是这样，commit message 这个特性就不应该存在——你不要叫 commit message，你就从这个 v1 到 v2 就行了。

当然你会在各种时候用不同的 commit message。比如你这个版本要收尾了，你可能会有一个提交消息会讲"我要 finalize 这个版本"。甚至 Git 也允许你在不改任何代码的时候——就这个 v1 和 v2 是完全相同的时候——再做一次提交。这件事情可以吗？Git 会拒绝提交你这个空的、没有任何修改的提交。但是 agent 可以：我让它做一个提交，要求它在不做改动的情况下提交。你看，它知道，它有知识，它确实产生了一个 empty commit。从理论上说应该可以吧，比如说我就要说"我要发布一个版本了"——但这个不是 best practice，所以尽量不要做。

> **提示**：什么时候有用？可以在无改动时产生一次提交，触发 CI 或者流水线。比如我要有一个 release——当然其实 release 可以把 tag 打在这儿，比如说 `v0.01`。上一次我修完了最后一个 bug，得到了一个可以 release 的版本，我也可以强行做一个提交说"我要 finalize"，那这就是没有改动的，`v0.01` freeze 所有的东西。那我就把这种 bug fix 的提交和 finalize 的提交给分开了。这件事情在偶尔的情况下还是可以允许的，但你不能显然创建大量这样的空的提交。

再来看一个你们非常常见的事情，这是不是 best practice。我写一个 `hello.c`，编译出 `hello`——这个应该是可以编译的。这时候你有一个 untracked file。然后你们在 tutorial 里面看到，有一个命令很好，叫 `git add .`：这样你如果有好多好多的文件，比如改了 35 个文件，你不需要 `git add a.c b.c c.c` 了，你直接 `git add .`。Git 是不阻止你做这件事情的，这是完全合法的。

```bash
git add .
git commit -m "I did some cool stuffs"
```

然后我再问问它：Git 提交有什么不符合 best practice 的吗？它会看一看，并且按严重程度排序，还是挺聪明的。它说提交信息毫无信息量——刚才还骂了"纯纯废话"——这就比较好，它还会告诉你应该怎么做：用祈使句现在时描述变更动机，例如 `fix off-by-one in strlen_check`（C 里面有这种不好的 practice，现在 fix 了）；然后常用的约定 Conventional Commits 也值得考虑——你可以在更多的项目里面看到这样的 commit 方式。

第二个问题：提交粒度和内容混杂，它开始批评我了。首要的还是提交信息毫无信息量；然后 `hello` 是编译产物，根本不应该进版本库，应该加进 `.gitignore`，用构建系统产出。

> **结论**：Git 的使用方式和你们的"作业 v1、作业 v2"还是不一样的。因为你的作业 v1 里面那个 exe 一定在里面，作业 v2 你的 exe 也在里面；但 Git 它为了防止这个版本库的膨胀，尤其是如果你这个项目里面有 1 万个文件、有 100 个合作者的时候，每一个合作者的环境都是不一样的。

你想，每个环境都不一样，他们 build 出来的东西也是不一样的。你们可能不知道，你们每一次编译出来的那个文件都可能是带一个日期的，它甚至带 hash、带你本机的指纹：你看每一次这个二进制文件可能都是不一样的。如果你把这个东西放进去了，下一次就会产生冲突——因为你这里有一个 `hello`，对方也有一个 `hello`，哪怕是一样的源代码编译出来，它都可能不一样，更何况如果是不一样的源代码编译出来的 `hello`。然后这就会产生一个二进制的冲突，而二进制的冲突是很难合并的。你想，如果我生成的东西不是这种程序编译出来的，如果我生成的是图片呢？图片怎么合并呢？所以这里面有很多很多的 best practice。

然后它花了一些比较长的时间来思考。最后它说：丢弃空提交和编译产物两段历史，新建 main 分支，重写为两个有意义、单一职责的提交。它还贴心地发现历史没有 remote——也就是说我的仓库没有和另外一边同步，不会有别人持有；因为如果别人也持有的话，那这就是一件比较糟糕的事情了。既然没有别人，它就把整个这个项目就给改了。你看，如果你的注意力注意到，你发现它换了一套 commit 的方式：它会有一个 headline 的 message，然后在 headline 的 message 后面还有一些内容。

这里面还有好多好多好玩的。比如说如果你在这个 message 里写一个 `fix #3`，GitHub 会自动把你的这个 issue 给 close 掉。这里面有很多很多好玩的东西，你只有反复地使用、反复地使用、反复地使用，你才能获得。

## 快照、对象模型与 Git 工程实践
> 对应块：BLK06 | 覆盖分集：P04下 | 块标题（分集名）：《软件仓库管理（下）》

### 让 AI 先检查文件变化，再提交

初学者和有一定经验的人，差别在哪里？其实很多时候不在于谁背下了更多命令。现在是 agent 时代，你们都是 agent-native 的人，肯定不会用古法——`git status` 这种东西，已经算是古代手艺了。你们现在一定是用 agent：你不需要知道具体的命令是什么，但你要有概念，知道"我的 git 能干什么"，然后你就可以让它用符合 best practice 的方式去干。

这带来一个问题：你其实根本分不清，是你自己真能干，还是你脱离了 agent 就干不了。也许这也不重要。为了提高学习效率，有一个办法很好用——在做任何 git 操作之前，都让它逐个检查文件的变化。

#### 一次编译不过的提交

我随便试一个，写一段不能编译的代码，然后让它做一次提交。我也猜不到模型会给我什么。结果它很聪明，它比你聪明：你在改作业的时候总会有这种倾向——"改一个字不要紧的，改了就提交吧"，你一定会这样想。但模型见过很多好的工程项目，也读过很多软件工程的书，所以它知道当前不建议直接提交。于是它把代码给你修好了，还给你解释。当然这里面有几个 prompt 在起作用：我有一个 system prompt，大概会说"说中文"，还有"我在上课，所以你可能要讲得更详细一点"。

它给了很好的解释：**git 提交应当是一个完整自洽的快照，提交编译不过的代码相当于让仓库处于坏状态。** 而且它还有更多——它甚至提到，如果真的有人要去 `git bisect`……

这就是"每一次提交的代码都应该能通过构建和测试"这条要求。它其实非常基础，大家也会觉得理所当然，但当你反复被强化、潜移默化以后，它就真的成了你的习惯。

> **结论**：一次提交就是一个快照。让快照始终处于"能构建、能通过测试"的自洽状态，是所有后续操作（回溯、二分、协作）成立的前提。

顺带说一句，`AGENTS.md` 是可以提交进仓库的，这也符合 best practice。

#### 把提交历史当作数组做二分查找

如果真有人要去 `git bisect`——我们可以做二分查找。你们在保研或者找工作面试的时候，可能要手写一个二分查找：你有一个很长的数组，要找出某个位置。

把 git 的提交历史想象成一个很长的数组。你在当前版本上发现一个 bug，但这个 bug 可能不是当前代码引起的，而是过去某一个地方引入的。这时只要有一个测试用例、或者任何一个能检查出这个 bug 的东西，你就可以对整个 git 历史做二分查找。

因为提交历史天然分成两类：有些提交是 OK 的，有些是不 OK 的。在某一个时刻引入了一个 bug 之后，从这个时刻开始，这些提交都不能通过了；而在它之前的每一个提交应该都是 OK 的。这不就是在"所有前缀都是 0、后缀都是 1"的数组里找第一个 1 吗？这正是二分查找擅长的事情。

```text
历史：commit1  commit2  commit3  commit4  commit5  commit6  commit7
检查：   0        0        0        1        1        1        1
                    ▲                          ▲
                  最后一个好提交          第一个坏提交（bug 在这里被引入）
                                   ↑
                        二分查找要定位的就是这个位置
```

二分查找每一次都折半，所以哪怕历史很长，也只需要很少的几次检查，就能把"引入 bug 的那一次提交"钉出来。

#### git blame：每一行是谁改的

还有一个我特别喜欢的功能叫 `git blame`。比如 `git blame hello.c`，它会告诉你每一行代码是在哪一次提交、被谁改的。也就是说，哪怕历史是一条线性的直线，我也能干很多有趣的事情。

知道哪里错了以后，用 `git blame` 就能知道是谁改了这一行、当时发生了什么。你看，AI agent 的一句话，就把整个 git 给打开了。

### 新人进组的高血压时刻

在 LLM 之前，一般来说有新同学进组，都会有一些"高血压时刻"，都跟 git 的 best practice 有关。场景很典型：我们要做一个研究项目，欢迎你加入，你去开一个 git repo 吧，第一周的任务很简单——搭一个架子，把一两个东西跑起来。然后我一打开那个 git 项目，就进入高血压环节。

比如：

- 我看到 `dist`、日志文件被交上来了。日志也是生成的文件，它不应该交。
- 个人配置被交上来，比如你 VS Code 的个人设置，里面甚至有 C 盘下某个路径的硬编码——显然在任何一个其他地方都没办法复现。
- 更高血压的：我可以在审稿的时候看到处于 active 状态的 API key。而当我发现这个 API key 是 DeepSeek 的时候，我就知道这应该是一个中国兄弟。
- 还有没有 Mac 的同学不经意间提交上来的 `.DS_Store`。

`.DS_Store` 这件事值得说清楚。这是 git 的一个特性——如果它没被 ignore，就会出问题。在苹果系统上，如果你用 Finder 打开一个目录，它会自动留下一些索引，大概就是你把哪些子目录展开了，这些信息放在一个叫 `.DS_Store` 的文件里。这个文件因为以点开头，默认是隐藏的，你看不到它（我的 `ls` 还很贴心地给它一个苹果图标）。**你看不到的时候，你就会 `git add .`，然后 `git add .` 就糟糕了——`.DS_Store` 会被 git 追踪。**

当然，默认把带点的文件都收进来也是合理的，因为点开头有可能是一些配置文件，比如 `.github`、`workflows` 这些约定俗成的东西。但临时文件就有点糟糕：你可能会经常地改它，它就不应该被提交进来。

> **易错点**：`.DS_Store` 这类隐藏文件不会在常规列表里显示，但它确实存在于工作区。`git add .` 会把它一并纳入追踪。所以"加一个忽略规则"和"提交前先看一遍变化"这两件事，都不是形式主义。

但反过来说，也不是所有 generated file 都不该提交。比如你可能有 `package-lock.json`；比如你可能会生成一个 header——这个 header 确实是可以生成的，但你把它放进仓库，就可以方便编译：别人在不需要下载很多依赖的情况下依然可以编译这个项目。你可能用另外一套工具链生成了这个 header，然后在一个没有这个工具链的地方去编译它。

所以没有绝对的规则。我自己是做软件工程研究的，一个非常标准的软件工程研究，就是去研究你的 git 项目满不满足这些 best practice，不满足的时候给你一个 warning。像 `.DS_Store` 这种东西就需要一条规则，然后是好多好多规则，最后做一个小工具，在 git 提交之前告诉你 OK 不 OK。

然而今天所有的这些东西都被大模型杀死了。因为大模型可以如此耐心地给你检查，还给你一个 emoji，让你开心一下，缓和你的情绪。

这里还有一层感受。有的时候我作为导师，把学生叫到办公室，第一个反应肯定是高血压了；第二个我还得装作 nice 一点，我会说："你提交的这个项目不太符合软件工程的实践，然后这样这样这样。" 但学生在听的时候，他也觉得我不满意——不管我情绪多么正常，我只是告诉他一个知识，这个时候学生总是有压力的：毕竟是老板批评我了，而我做了一件不该做的事，而且这件事 supposed 是应该知道的。所以 AI 真的解放了同学们，解放了那种你无法控制的力量。

### Hook：在提交前和需要输入时各做一件事

最近我在一个更严肃的项目里，希望把每一个细节都做好，这时我面临一个选择。在 git 提交之前，有一种机制叫 hook，钩子。钩子大家可能用过：你可以 hook 程序的一个函数调用，在函数调用结束时干一件事；你也可以在你的 agent 里加入一个 hook，在某件事发生时干一件事。比如我有一个 hook，会在 agent 完成、需要我输入的时候播放一个声音，叮一声。这件事现在完全可以交给 AI：你直接说"帮我配置一个全局的 hook，在 agent 需要输入的时候叮一声提醒"，你的任何一个 Claude Code、Codex、pi 都支持这样的钩子。

同理，我可以在 git 的 `pre-commit` 这个 hook 上面做检查，因为这个项目的工程标准会更高一些。

然后我就面临一个真正两难的问题：我有几十个这样的 checking rules，我要给每条规则命名，那我应该选全大写，还是全小写？

从使用的角度上来看，两种都没有问题，两个都是好的——只要我这里没有 typo 就 OK。那到底是大写还是小写？这是个两难的问题。而在学习和生活的过程中，你还会面临无穷多个这样的两难问题。如果你每一个问题都多问一句，你就会有很多很多长进和知识。

> **提示**：命名这类"两难"通常没有唯一正确解。真正有收益的动作不是逼自己一次选对，而是遇到时多问一句、把细节做扎实——多问一句，成本极低，回报是长期的。

### Git 是一个持久化数据结构

`AGENTS.md` 有了，接下来就要学一学 git 到底是怎么工作的、它的底层原理。

我可能会推荐大家去看我在操作系统课上讲 git 的那一篇，这里就没有必要再讲一遍。我这里只讲一个头：**git 是一个持久化的数据结构，所以它就是一个数据结构。** 那 git 持久化的是什么呢？是目录树。因为我们说，快照不停地产生版本——版本 1、版本 2、版本 3、版本 4。

从那最基础的想法出发：如果我要存一个目录树，比如根目录 `/` 下面有 `a.txt`、有 `b.txt`，还有一个目录 `d`，`d` 里面有无穷多个文件——这个先不管。现在相当于我有一个非常大的项目树，今天已经快照了，这就是 v1。现在我要创建 v2。我需要把所有的文件都复制一份吗？**不需要。**

比如我现在改的是 `b.txt`。那我肯定需要创建一个 `b.txt` 的新版本。那么，如果我想要以最小的代价记下一整棵树，应该怎么办？

到根的那条路径，反正我要再复制一份——因为根下面的 `a` 不能指向那个旧的 `b.txt` 所在的位置，一指就等于我要用旧的 `b.txt` 了。所以路径上的节点必须新建。而没被动过的部分，我可以用一个指针指过去。

```text
v1 的树
    /
    ├── a.txt
    ├── b.txt
    └── d/

v2 的树（只改了 b.txt）
    /
    ├── a.txt     ← 指针复用 v1 的 a.txt，不复制内容
    ├── b.txt     ← 新建（内容变了）
    └── d/        ← 指针复用 v1 的 d/，不复制内容
```

所以即便你的项目很大，里面有一百万个文件，你只需要创建一个非常小的增量，就得到了一个版本的快照。

为什么可以这么放心地"不深"？因为首先目录本身就不可能很深——没有人会去建一个一千层深的目录，从渐进式披露的角度，你也没有必要建一个巨深无比的目录。它每一级索引都是指数级地增加，所以你很快就能够把所有的（条目）登完。

那么在 git 里面，底层是什么样的？看 `.git` 目录，里面有各种各样的 objects。这些 objects 就是普通的文件，是带 hash 索引的。里面就是各种各样的节点：目录的节点、文件的节点，甚至有 commit 的节点。

三大类对象：

- **commit object**：提交对象；
- **tree object**：目录树对象；
- **blob object**：`blob` 就是 binary，就是字节序列。

它就是这样一个数据结构，然后这个数据结构可以不断地向后生长、向后生长。这就解决问题了，其实就解决问题了。所以如果从 first principle 出发，一个大学生想设计出一个这样的东西，是完全没有问题的。

#### 从字节看清 blob 与 tree

这是 `main` 分支，它就像我画的那样。最早的一次提交，message 是 `I did some cool stuffs`，里面有一个空的 `hello.c`。这个空的 `hello.c`，你可以看到它的文件是来自于 `/tmp` 下的一个 object——这真的是一个 blob object。然后你能看到它的字节序列。看到字节序列以后，它会帮你解压缩，然后你发现：对于很小的文件来说，这个压缩反而是浪费——31 字节解压缩出了一个 23 字节的东西。但这不要紧，这是一个 blob，`blob 15`，文本内容是 `int main`。这是一个 blob object，大小是 15。

除了这样的 blob 以外，还有 `hello` 那个二进制文件。你看 `blob 158`，这是 `7f 45 4c 46`，一个可执行文件的头。它也照样能看到。

它也有 tree object。tree object 同样可以看到它在磁盘上的原始数据：52 字节解压出 43 字节。这个 tree 是这样的：`644`，代表这个文件的访问权限，然后它有 `hello.c`，真的是**以文本的形式存储**——解压完了以后就是文本。它树的结构是：bytes、object、mode `644`、name `hello.c`。

```text
commit object
    ├── tree      → tree object（这次快照的根目录）
    ├── parent    → 父提交（合并提交会有两个 parent）
    └── author / message

tree object（一个目录）
    ├── 100644 blob <hash>  hello.c
    └── 100755 blob <hash>  hello        （755 表示可执行）

blob object：文件的内容本身，就是一段字节序列
```

这个 tree object 指向了这个版本里的 `/`，在这个版本里它就有两个文件：一个 `755` 的 `hello`，一个 `644` 的 `hello.c`——`hello` 是可以执行的。

> **提示**：`100644` / `100755` 是 git tree 里记录的条目模式，后三位就是我们熟悉的文件权限：`644` 不可执行、`755` 可执行。同一次快照里，可执行文件与普通文件在 tree 中是被区别对待的。

#### 分支就是一个文件

在这个工具里你还可以创建分支，直接看到动画效果，左右是实时同步的。创建两个分支以后，你会看到有个东西叫 `refs/heads/a`。

**什么是分支？分支就是一个文件。** `refs/heads/` 下的这些东西就是指针，所谓分支就是指向提交的指针；而 `HEAD` 是指向指针的指针——它指向分支文件，分支文件再指向那个提交。分支文件在磁盘上就是这些字节，里面存的是一个 hash。

我们来看 `a`：它指向的提交对应的那棵树里有 `/`，`/` 里面包含了新的 `hello.c`，内容是 `int main(void)`。同样的，`b` 也是这样，它指向改过的、带 `argc`、`argv` 的那个版本。

```text
HEAD ──► refs/heads/a ──► commit object ──► tree object ──► blob（hello.c 的内容）
                          （分支文件里
                            存的就是这个 hash）
```

视觉效果不是很好，是因为我 one-shot 直出、没有调；我相信跟它对话几轮以后，应该就能得到一个近乎完美的 git 可视化。

#### 冲突现场的三个版本

我也可以让它给我展示 merge conflict 的状态。假设两个开发者在同时开发：你和你的团队成员每个人都对这段代码不爽，你们两个都重构了，那就会进入冲突。

`a` 在这边，`b` 在那边；当你把 `a` 拉到本地的时候，你就会看到冲突状态。冲突现场里，`hello.c` 的内容是带尖括号的：

```text
<<<<<<< HEAD
（当前分支的版本）
=======
（要合进来的那个版本）
>>>>>>> <另一分支>
```

而你看不到的地方是：git 悄悄地在里面留了三个版本，叫 `base`、叫 `ours`、叫 `theirs`。它们就在未提交的区域（index）里。

```text
git 在冲突时保留的三个版本（位于 index 中，工作区里看不到）
    base    —— 双方共同的祖先版本
    ours    —— 当前分支的版本
    theirs  —— 要合进来的那个版本
```

然后我让它 resolve。你看，那些临时文件就没有了。这个 merge 创建了一个这样的 commit object，它的 tree 是这个，并且**它有两个 parent**——它有两个祖先。然后它有 author，指向的关系被正确地保留下来了。你可以看到它的 tree object 选的是这个版本。

最后我想说一段更重要的。在今天，你们真正有价值的品质是你们愿意花一点时间去学习。然后你很快就会发现在求职市场上，"把细节做好"的这个 bar 会不断地提高——因为一旦有人学会了，招人的单位就会用这个标准来衡量你。

你想，我面对一个研究生问他"git merge 以后会发生什么"，他没有任何概念；和另一个同学，在学每一个专业课、每一个算法、每一个细节的时候，都在 AI 的指导下巩固了这个概念、真正消化了这个概念，甚至可以从零开始构建这些概念——这两个人在 job market 上的竞争力是不一样的。

当然我觉得可能还有一件事情会发生：反正 AI 太强了，所有的人都没有竞争力了。那也许这是最好的状态，否则你想一下你们的危机感——这个世界上有很多那样的人，而你们如果不成为那样的人，上了 job market 就死了。

所以我觉着"上课耽误学习"是真实存在的。因为很多老师真正好的东西打开都没有打开过：那些真正好的代码、真正符合工程规范的项目，他对着课本讲一遍就过去了。而刚才那个整个的框架，大概就是我两天的碎片时间，包括视觉效果的调整，就全部完成了——做这些事情已经没有任何成本了。我自己也马上就会被淘汰，我学习的时间非常有限，我很想学很多东西，但不像你们有那么多时间。

我们讲了一个 Git。其实今天虽然我好像在讲 Git，我讲的是 best practice。

### Conventional Commits 与中英文之间的那根空格

best practice 还有好多。比如刚才如果你有注意力，会注意到 AI 给我们的 commit message：前面的提交都是英文，一行加上一个详细解释；然后你看在这 AI 就自由发挥，开始混合英文和中文了。但还好，它还是遵循了这样的格式——有些有 scope，说明我干了什么，然后一个总结，再有 message body。

你看很多就知道这个东西存在，它实际上是有标准的，叫 **Conventional Commits**。它的文档很短。规范里说：commits must be prefixed with a type，这个 type 是一个 noun，包括 feature——如果我要引入一个 feature，我要 fix 一个 bug，要一个冒号，一定要有一个空格。这些都是规范。

```text
<type>(<scope>): <一句话总结>

（空行）
（正文：为什么这么改、改了什么）
```

和同学合作的时候，高血压时间还是比较多的。比如一般来讲，Markdown 文档里英文和中文之间要有一个空格，比如"你好，这是 `hello.c`"。这是肌肉记忆。

我最难受的是：一个文档里面有一些是这样，有一些不是这样。哪怕你通篇都不加空格，我都会认为你是在遵循某一种 convention——你是保持一致的；但你不一致的时候，我就是有点头大。所以 AI 会把这些细节给做好。

这些工程细节其实都是为了：让工程师在面对更大项目的时候，有一种一致性和规范。你的代码要以同样的方式排版，很自然地，你的文档也要以同样的方式排版，这样维护起来会更好。虽然我觉得在 AI 时代这好像也不重要了，AI 都会帮你。所有用 AI 的学生都不会生成那样的 slop。

### 为什么必须小步提交

Git 还有很多很多 best practice。你可以在网上找到各种说法，比如 "commit often, perfect later, publish once"。这些其实都是有工程实践经验的，你们回去读一下这些文档、让 AI 帮你，就会学到更多。

那为什么要及时 commit？因为在复杂的项目里，随着你修改的东西越多，你错的东西就越可能多。

你搞小项目刚开始的时候其实不要紧，你一次提交个两千三千行代码都 OK。但是一旦这个项目里面有错综复杂的关系以后，你的一个大的 commit 可能会 break 这个项目里面多处的东西，引入多个 bug，后面再要引入多个 fix 来 fix 它。这时候你有一个很大的 commit——比如你有一个一万行的 commit，那后面你修了 100 个 bug，你都说这是那次提交产生的，这就很糟糕，甚至修不过来，你也不知道到底修好没有。

而如果你每一次的 commit 都是很小的、都只做一个修改，那就**冤有头债有主**：这个 bug 就是你写的，我修完了也就修完了，这两个 commit 是可以配对的。

| 维度 | 一次巨大的提交 | 一串小步提交 |
| :--- | :--- | :--- |
| 出错后的定位 | 一万行里找问题，修了 100 个 bug 都算在那一次头上 | 每个 bug 都能对上引入它的那次提交 |
| 审计能力 | 基本丧失 | 保留：发生了什么、谁改的，都查得到 |
| 备份粒度 | 电脑坏了就全丢 | 每次 push 都是一份网络上的备份 |

它给了我们**审计**的能力。也给了我们另外一层保障：你改了很多，然后不小心你的电脑真的物理损坏了，而你还没来得及推到远端——如果你之前做了一个小的提交并立即 push，你就得到了一份互联网络上的备份，电脑马上坏了也好。

AI 是很清楚的，它知道你可以 revert、可以 bisect。后面我可能还会讲 hooks 和 CI。

### GitHub 上不属于 Git 的那一半

如果你们还有惊人的注意力，应该观察过：你们的项目可能托管在 GitHub 或者 GitLab 上，那么你会看到你的 AI agent 会试图调用一些 `gh` 或者 `glab` 的命令，然后你会看到一个 `command not found`，然后它就回退到古法编程，又开始写 git 的命令。

因为 GitHub 实在太 popular、太好用了，那么就值得做一个命令行工具。git 管了好多代码的快照，但是 GitHub 上还有 issue：我今天可以发一个文本，我还可以对你的代码做 comments，而这些东西都是不随着 git 的 tree 做 persistence 的。

如果我们想要管理它，就做一个命令行工具：我可以去 fetch 一个 issue，然后可以找 assign 给我的 issue（你要登录）；找到 assign 给我的 issue 以后，我还可以把这个 issue close 掉。这个命令行工具对 agent 来说就很好用。

你装了 `gh` 以后，我就可以在 agent 里面设置一个 goal，说"给我完成一个什么"——可以设置一个很长的任务，我会要求它做小步的提交、做可以审计的提交，还有怎么分支的规则、线性的历史等等。然后你可以看到我的项目里大量的这样的提交，我很多时候都不管它们。

### 一切都是从「原子改动」推出来的

讲了很多 Git，这门课讲的还是软件工程，所以最后这小段总结更重要。

> **结论**：Git 本质上是一个软件，它说我们要把项目组织成**用 atomic change 推进的快照**。这是今天要记住的事情，所有的一切都是从这句话里面推出来的。

组织一个软件项目，你要管理很多的快照，这样就可以随时开启一个新的分支，做一些尝试：如果失败了，你可以把它安全地扔掉；如果成功了，你就可以把它合并进来。然后你甚至可以同时推进多个主线，以合并的方式让它们完成，而不会互相干扰。

你们做大作业、自己古法做大作业，肯定有这个感受：你如果同时改好几个地方，改着改着很可能就改乱了——这个部分和那个部分冲突，这个部分和那个部分又冲突。

项目管理的本质是：人类没有办法处理一团混沌——很多需求、很多代码，一次做一大步。所以很自然地，我们要把需求分解成可以理解、可以审计的小任务，一小步一小步来。

这样出了问题就可以 bisect、可以 blame；协作的时候可以 blame，发生冲突也容易解决。两个小任务发生冲突，可能是因为它们在公共的祖先上面做了好多事；如果每一个都很小，那么发生冲突时，我可能就能知道哪一个小的是冲突的，而剩下的不冲突的部分，它们合并起来可能会比较容易。

关于合并：合并可以是"把这个提交合上来"，这样就像我们看到的一样，我的一个 commit 可以有两个 parent，有两个祖先。然后它可能又继续分开、又分叉、又合并，最后会变成一个很典型的 Git 的结构。

但现在好像大家更流行 linear history。因为反正都是 AI，它 resolve、rebase 都很容易，我就强行要求我的整个 commit history 都是线性的，好像是线性的一样。当然这也不完全是好处，但至少对于现在我们维护项目来说：

- 它会让历史更易于追溯；
- 它对 cherry-pick 和 blame 也更友好。

在无限大能力模型到来之前，这件事情都是好的。你把 Git 记录拆分得非常好，你很容易就能找到这次修改是由谁引入的，那么 AI 维护项目的效率也会高一点，也会省 token 一些——它有些文件就可以不用去读了。

### 先定架构，再开三个 Agent

还有一些经验可以跟大家分享。虽然我们知道是要小步向前进，那我们怎么管理一个项目呢？

**我会在架构设计的阶段，先用单线程、用一个智力比较高的模型跟它讨论。** 这个其实很重要，因为如果你的软件设计得不好，你后面就是无穷的迭代。

我在第一次课的时候就展示过这个例子。我会把组件库的接口定得非常好。比如这个项目里面有很多互相关联的组件：我们的程序会运行产生结果，我拖动这个进度条，它不仅要关联到我的程序编辑器，还要关联到上面那个东西。但我把绝大部分的接口都设置成了 functional 的，就是 pure function。包括我的 trace 是程序的一个 pure function。然后大概有一个标准的这个程序的 derivation 的 graph，我说"你要按照这种方式来展开"；所有全局互相影响的状态，我都要注册到一个全局的地方——比如我光标的位置，光标的位置可能会影响这个可视化，还包括菜单栏。这个状态非常干净、非常小。

所以你看一个这样的 playground，核心的共享状态也就只有十几行，然后一个十几行的组装。剩下所有东西都是黑盒子。我会直接要求 agent 在设计这些 visualization 的时候，**禁止看任何库函数的实现，只看接口**。所以它非常省上下文——几万个 token 就可以做一个这样的 playground。

一旦这样的架构设计完成了以后，我就会开出三个（或者几个）terminal，然后要求它们干活。我的 `AGENTS.md` 里有一个明确的协作规则：比如我让它不需要调用视觉模型去检查——agent 很喜欢做这件事情，会花很多 token；我也不让它调用浏览器任务，而是我在边上的另一块屏幕上放一个浏览器，让它即时刷新，即时发现问题。然后我就开三个 agent，哪里不满意就骂它，然后你就可以肉眼看着右边那个东西不停地变好、变好、变好，最后问题就解决了。

这是一个 agent 能力之内的项目。我非常确信的是，回去以后 agent 的能力会不断地增长，然后越来越多的项目能够被 agent 以这样的方式完成：一个比较轻量的讨论，剩下交给它。

这是一件非常可怕的事情——如果 agent 快了 1000 倍，我们还怎么管理这个版本控制？我们可以下一节课再来讨论。

## 文件系统管不住软件：从 change 到 agent 时代的版本管理
> 对应块：BLK07 | 覆盖分集：P05上 | 块标题（分集名）：《软件仓库管理（二）（上）》

### 会成长的个人助手：开题的由头

上周讲了一点版本管理，这周继续讲版本管理。我发布了一个作业，按照之前的说法，这门课所有作业都是选做、自愿完成；最后当然肯定会验收——因为最终也许学校会让我们提交一个成绩，所以大家会交一些链接，由我的机器人来给大家评分。

我们的第一个 lab 算是一个比较时髦的需求，叫「会成长的个人助手」。对大家的要求都是不限，你们想怎么做就怎么做，最好还是可以 vibe code 一个。我今天课上会留时间，自己就来 vibe code 一个，并且会告诉你：如果你直接让它 vibe code，会遇到什么样的小坑。除了今天以外，这周日要调休周二的课，所以这周日还有课，会讲整个软件的架构，然后把它连起来。

这个例子是你们特别特别每个同学都会需要的，我自己也有的：一个能够持续为你工作的个人助手。下面这些需求是供你参考的，如果你实现它的话会有一点点成就感：

- **你自己的专业数据库**。你们这个学期可能会在学一些专业必修课，比如计算机网络或者概率这类比较难的专业课，你可以把专业课的资料放进你的个人数据库里；或者你参与了研究组的课题，可以把研究组的论文、相关文献、教科书整理成你的个人数据库。这是一种形式的数据库，不限。
- **你自己的个人信息**。我不知道大家是不是已经填表填得很烦了：每次填表都是给你一个 doc 的表格，要填姓名、学号、身份证号，有时候是个人简历这个那个。我现在已经把这些所有的事情都交给 agent 了，就说一句「把这个东西填了」。从以往到今年，这里有一个非常大的效率进步。我记得我大概在疫情的时候招过一个研究生，在我这里做了三年，做的就是自动填表系统——大家都觉得填表很烦。等他要毕业的时候，突然有了 ChatGPT，他很慌，觉得他做的事情马上就要被替代了。我说不要紧，你赶快答辩，就可以毕业了。这世界就是发展得这么快。
- **和你的邮箱关联起来**。在个人数据库的基础上，你可以把数据库和你的 email 邮箱关联起来。如果有机会的话，比如我两周以后会在半夜给大家发邮件，你的 agent 可能会把邮件回给我，实现一个 always on 的后台。你们也许可以买一个很小的嵌入式设备，一两百块钱，就可以在宿舍里面持续地跑你的 agent loop。
- **用你自己的信息去办理事务**，就像我上课时演示的那样；这其实就是一句话的事，直接做一个像 agent 的子进程调用就可以。
- **手机端联动**。有兴趣的话可以做一个网页，也可以是一个别的形式，甚至是一个苹果的 app 或者 Android 的 app。你只要让 agent 去做，它会自己去帮你把需要的东西都下好，然后把你要的东西做出来。

### 为什么要让你亲历一次焦油坑

为什么要布置这样的实验呢？看起来所有的任务都在 AI 的能力范围之内。但如果你直接把实验要求交给 AI——我今天会试的，我还没有试过——它在一开始就会做出很多它认为看起来也合理的决定，而这些决定会让你的项目维护变得越来越困难、越来越困难，最后陷入焦油坑。

> **结论**：每个同学都有必要体验一下软件工程里面的焦油坑——当你的 AI slop 开始不断消耗你的 token，你终于会有一天下定决心：好，我要把这个项目删掉，从头重做，或者回退到某一个很早期的版本从头做。

这大概就是这个实验想告诉大家的事情。当然，我相信这个项目对每个同学来说都是有用的，这也是我设计实验的初衷。

我可以提前预告一下：我的下一个 lab 会和这个 lab 有非常大的关联，而且你们暂时猜不到。你会发现，你先把 lab 1 的那些实验要求都做好了，它成为一个你非常舒适的个人助手；然后我啪给你加一个需求，这个需求和你前面所有的东西都关联，并且有一定的冲突，然后你的 agent 就去改，越改越崩溃，越改越崩溃。所以大家可以期待一下后面的 lab。反过来说，如果你不做，比如你 lab 1 就想着躺倒、或者就不管它，让 AI 直接就做，下一次再把它直接删掉，那可能就没有这个软件工程的体验了。

### README 该写多短

回顾一下上周讲的：项目是各种文件的集合——你的 intent、一些设计文档、你的 README，都在项目里。

> **提示**：我不喜欢那种 AI 写出来非常非常长的 README。对我来说，README 应该写一下你设计这个项目时最初的初衷：你想做一个什么样的产品、这个产品能达到什么样的效果，可能配一两个 screenshots，以及你最重要的那些设计。

为什么是这种感觉呢？有一天你突然想了一个非常好的点子，你真的想用它去挣一个亿；你要挣一个亿的时候，就要组建一个创业团队，要说服一个 computer science 里面的人——比如说你要说服我出来干——你其实只需要一个比较短的 README，这是你的 intent，你想做这个东西。剩下的事情，比如我有架构的能力、我有写代码的能力，我可以把剩下的东西都给你补出来。你不需要知道这个软件系统是怎么样、它的 specification 是什么、它用什么样的数据库、怎么样支持用户从 1 到 10、到 100、到 100 万、到 1 亿；这个架构你可能没有 computer science 的知识，但你不需要有，你只要有那个最原始的设计，那个 intent。

再往后是 spec：我要选什么样的数据库，甚至要选什么样的编程语言，我的项目结构是什么，小到每个模块的接口，都属于 spec。最后是 code implementation。这些现在都放在同一个项目里。

```text
intent  ->  你想做一个什么产品、能达到什么效果        (README 该留下的东西)
   |
   v
spec    ->  选什么数据库 / 什么语言 / 项目结构 / 每个模块的接口
   |
   v
code    ->  implementation
```

从 intent 到 spec 再到实现，是一条自上而下的推进链，而这条链此刻只能平铺在同一个目录里——有了这样的项目以后，很自然你就需要一个容器把这些各种各样的文件给管理起来。

### 文件系统丢了什么：一份文档与一份代码的失联

大家用文件系统来管理项目，其实真的就是图方便。回到 1950、1960 年的时候，操作系统给你的存储功能就只有文件，它没有别的——那个时候关系型数据库还没有发明出来。所以所有的程序员别无他法，只能把你的项目以文件的形式存进来。所以这更多时候是一个历史原因：历史不停往后长、往后长，长成了现在这个样子。

我自己觉得，文件系统可能不是组织项目的正确方式，因为文件系统其实丢失了很多文件不适合表达的信息。有些信息其实是比较容易表达的，比如 intent、spec 这种：我把文档一写好，我就知道这个地方我是怎么想的；或者这个测试用例是什么，输入是什么、输出是什么，我要 assert 在程序的运行过程中什么东西不能被违反。但你马上就会发现，有很多**隐藏的关联**在项目里面是没有的。

举个例子。你们经常会让 AI 写代码，现在的 agent 会稍微好一点，有时候也不会：你让它把某个实现里的方法换掉——比如说你要把 linked list 换成一个更高效的 tree 结构去优化性能。这是很常见的场景，你突然发现这个性能不够了，然后你要 AI 去做，AI 就啪啪啪给你代码改了。但你没有想到的是，你可能在其中的某一个文件里、某一个 Markdown 里写过一个文档：「我这个项目的数据是用 linked list 管理的」。于是在项目当中，你的文档和你的代码、和测试之间就形成了一个关联。你在写文档的时候可能还没有代码，所以你就先写了那个文档，随手一写「这是一个 linked list」；但是一旦你的代码实现了，这个关联又没有强行地联系上。

> **结论**：这就是一个技术债（technical debt）。

因为以后随着文档和代码不断向前推演，它们的不一致只会越来越多，不会越来越少，然后这个软件就陷入一个维护的泥潭：后面你拿出一块代码，甚至 AI 看到一份代码，那到底是文档说得对还是代码说得对？你跟它聊天的那个历史没有了，你那个 chat 已经消失了；你换了一台电脑，git repo 里面可能还有一些 change 的日志，但到最后你真的就不知道到底是代码对还是文档对。

```text
文件系统的表达（树）              软件里真实存在的关联（图）
repo/
  README.md                        docA <----> docB
  hello.c                           |            |
  docs/                             v            v
    design.md                     impl  <---->  test
                                   ^             |
                                   +-------------+
```

左边这种树状结构把文件安排得整整齐齐，右边那些「谁实现了谁、谁覆盖谁、谁和谁必须一起改」的关系却完全没有落脚的地方——而它们一旦断开，就是上面那笔技术债。

### 可追踪性：一个几十年的老问题

其实在软件工程里面，这是一个研究了非常非常长时间的问题，叫 traceability。

> **定义**：可追踪性（traceability）关心的不是文件放在哪儿，而是一个项目里各种各样的测试用例、文档（哪怕只是文档中间的一行）、代码之间的关联是什么，以及我们能不能在软件系统的演进过程中仍然维持它。

有一篇 2014 年的文章 review 了一些更老的文章，标题就叫 software traceability。它发现的就是这件事：文件真的只是图保存在文件系统里方便。这其实是一个非常软件工程的问题，所以很多时候我们觉得蛮有意思的——文件系统将错就错了。

大家最后总有一天会发现，你用文件系统来管理代码，你受不了了：打压缩包发布、打压缩包发布，然后打压缩包发给你的合作者，这件事情已经维护不下去了。所以就有了 SVN，有了 Git。那下一个是什么？大家有没有想过下一个是什么？我今天一会儿会讲 Jujutsu——另外一个可能设计比 Git 还要好一些、更好用的版本控制工具。

### 如果没人再看代码：repo.db 与 view

同时我一直在想另外一件事：如果以后我们再也不要写代码了，那软件它就不应该是一个像现在 Git repo 里面管理的那样——我们有好多文件，什么 README.md，什么 hello.c，还有一些 docs 下的什么文档。如果所有这些我们人都几乎不管了，那我们有没有可能，等这个世界未来到来的时候，把软件或者说部件之间——也许我们还是需要文档，但我们的文档可能是好多个切片——把它们变成好多的对象（object），或者是实体（entity）。

比如说：这个文档和这个实现之间就有一个关系——这个代码实现了这个文档；然后我可能有一个测试用例，这个测试用例也有这个文档，那这个文档和测试用例又关联起来了；然后这个测试用例是和这个代码的这部分实现关联起来的；然后这个文档又和另一个文档是关联起来的。

```text
docA  --implements-->  impl
docA  --covers------>  test
test  --touches----->  impl
docB  <--refers----->  docA
（可以任意互指、形成环：这是一张图 graph，不是一棵树）
```

你看，这是一个完全结构化的东西，你没有办法在文件系统里以一个树状的形式表达——这是一个随便连接的、有 cycle 的图。那这个东西，比如说我可以把它放到一个数据库里，这个就叫 repo.db。

那显然人类就没有办法用现在的 Unix 世界里面的工具去维护这样一个 repository 了。但不要紧，应该怎么解决呢？用魔法打败魔法：人类理解不了的东西，我们只要训练 AI——它只要有强化学习的反馈信号，我们就可以训练 AI，AI 能够理解这个 repo。所以我们要干的是什么呢？这就是一个非常大的项目：Linux 内核、数据库，或者你们想做的一个价值一个亿的产品。

好，那每次你就说：好，AI——因为你也不太可能一下子就说「我要把这个产品直接变成另外一个产品了」，当这个软件系统已经在工作的时候，你一般要做的就是给它增加一个功能、修改一个功能。这就跟 Git 的理念（philosophy）很像：Git 管理了文件、目录、快照和快照之间的关系，它希望我们能够小步前行——我每做一件事情、我 fix 一个 bug、我改一个文档，我都产生一个 commit；这样我就可以在很多人之间协作，每个人可以自己产生自己的 commit，然后我们可以用 rebase、merge、fast-forward 这些，或者普通这种 merge 来创建一个可追踪的整个项目的修改历史。

那在 agent 时代，我们要的就是可以让 AI 自动维护所有软件 artifact 之间的一致性。这个一致性比如说：代码和文档必须要一致——我文档说这是 linked list，我的实现里面就必须是 linked list；我的测试用例——我在文档里面说我要有 a、b、c 三个方面的测试，那我这个 test case 就必须包含 a、b、c。它们都是关联起来的。

你想，从 Git 里面我们知道我们希望小步前行，那同样的，当我们谈要做一小步的时候，其实我们知道这一小步是干什么的，所以你可以 chat：跟 AI 说我现在发现它有个 bug，或者我做了一个产品、比如我今天对这个幻灯片的样式不满意——这就是一个小步。而在一个大型的软件系统里面，绝大部分的内容跟这个小步都是没有关系的。比如我的 repo 顶层的结构：我有一些 assets，甚至还有 `.cache` 这样一个缓存的系统，然后有 p1、p2、p3、p4、p5，还有一些脚本等等。任何一个软件系统，当你只做一小步的时候，你就只需要看到这个软件系统的一小部分，大部分东西应该是不相关的。

既然是不相关的，我们就可以让 AI 根据我们的 chat 把和我相关的东西给摘出来：它可以知道，我现在需要的是这个文件、这个 test case 和这个文档，其它东西都不需要了。然后你想，AI 有什么能力？AI 有动态生成任何内容的能力，Everything is code——Content as code，Code 可以表达任何东西。所以 AI 可以根据我的 chat 生成一个和我要改的这一小步相关的 view，一个视图。

在这里你看，你们学到的各种系统里面的概念还是有用的：不是所有的同学都学过数据库，数据库里面有一个叫 view 的概念——我们的数据就在这了，但我可以创建一个不一样的查询，可以把它以另一个形式展示出来。这就是一个很简单的想法：我希望把这些数据以另外一个形式给展现出来。那比如说当我看到的时候，我就看到的不是这些代码、文档、diff，而是一个可视化的看板。然后这个看板上面大概列出了和我这个小步相关的一些东西，然后问我要改什么。

然后我一改，改完了以后，我同样地还是从一个 v0 到 v1，它还是一个 repo.db。但是这一小步就会把这些相关联的东西一起改掉：比如我要增加一种类型的测试用例，那它就会在这些地方加一些测试用例、那个地方加一些测试用例，有些地方可能要改掉。

```text
v0 repo.db                                 v1 repo.db
文档 - 实现 - 测试                          文档 - 实现 - 测试(+新用例)
  \     |     /       -- 一次小步修改 -->     \     |     /
     一致的状态                              一致的状态（仍然彼此对齐）
```

它就从一个一致的状态——各种错综复杂的关系——经过一次小步的修改，到下一个版本。这样就好像软件工程就又变了，彻底变了。然后我觉得这是一个未来有可能发生的事情：在 AI 内部，它是这样生产软件的，从此以后我们也不用再看代码了。

你们看到现代的这种 IDE，比如 Cursor，我其实还蛮讨厌的：它现在打开默认就是 agent mode，而 agent mode 一来，原来我们熟悉的那个 IDE 就没有了，强迫你用一个像 chat 的方式去跟它沟通。因为我还是相对来说比较精通古法编程的，有时候我还是对代码有一些掌控欲——可能是不好的，这可能是不对的——但未来这可能是一个途径。

那同学们肯定也会焦虑：如果未来这件事情真的有可能发生，而且可能一两年以后就真的有公司把这东西做出来了，那我们学那么多东西还怎么办？其实你发现在创造这些东西的过程当中，我们用的都是你们学习的这些经典、集大成的 computer science 课程里的东西：我刚才说了数据库里的视图，借用了数据库的概念——实体和关系；然后我借用了 Git，Git 这个模型没有变。Git 长期的开发经验说我们要一步一步向前，如果在这个模型底下我们是大步向前的，那就惨了。当然也有可能发生的是：模型变得非常非常强，一个非常大型的项目一步啪就变成下一个了——这个怎么做，我们现在还不知道。但至少在初期，我们可能还是要沿用这个过去的、大家积累的软件工程智慧去小步向前，然后通往那个极乐的世界。我还是相信那个极乐世界确实有可能是能到的。

### CONTRIBUTING.md：新人类与旧人类

这就引发了一个我觉得在大学里面蛮有意思的评论。这个同学应该是已经毕业了——因为我上上节课说，我问同学们 Git rebase，大家都不知道什么是 Git rebase，然后他 raise 了一个 valid point：「学生时代大多数人是不会和他人共同合作的，也就是做作业，所以 rebase、merge 用的场景就很少。」正确，这个 point 是对的，你们做作业的时候确实不会用到。

我的回应大概是这样的：但是如果你真的往外面的世界去走一走的话，这个互联网开发者社区铺天盖地都是文档，所以你一定会有一天留意到别人的项目，会看到一个叫 CONTRIBUTING.md 的东西。

> **提示**：CONTRIBUTING.md 是仓库根目录下的一份贡献者指南，通常回答「我怎么参与这个项目」。它里面会有项目的总体结构，以及分支、提交信息、PR 的规范和流程。

如果你看过很多项目的 CONTRIBUTING.md，随手打开看一眼：如果里面的东西你都知道了，好，那你就知道了；如果你不知道——比如有一天你一定会看到一个项目里面写着「你必须要在你自己的分支上 rebase，我们要保持线性历史，禁止你直接创建那种分叉的 merge」——你就会知道 rebase 是干什么的。

现在我们的社会变得太快了，所以有一种学生思维。这不是批评大家，因为你们上高中的时候就是这样的：在高中的时候，老师不教的就是你不需要会的，考试不考的就是你不用学的。这是为了升学的利益最大化，是正确的，没有错。但你们到了大学以后，如果还带着这个思维，你就会有一个 gap——一种新人类和旧人类之间的 gap。当然我相信每一个同学也还是可以成为新人类的，你只需要去有一些注意力，去注意到这个更多的东西。

因为现在我有一个危机：AI 时代的斩杀线以下的值就全部归零。当然我觉得现在的斩杀线可能还斩不到各位 985 大学 computer science 专业的同学，但可能比如说那些低级的智力劳动——我好像看过一个报道说，中国可能是不是有 1000 万还是有多少的会计从业者——那个行业里面顶尖的人肯定暂时还是没有危险的，但是在底下的大量的人都面临被 agent 替代斩杀的危险。所以你们需要在那些经典的课程上，不管是操作系统、编译器这些，还是软件工程，这里面有一些软件工程的智慧；你们学到一些经典的东西，然后最终形成你们自己的理解。

### 快照与修改：merge 和 rebase 各自欠了什么

我们继续回到软件工程。不管是畅想未来会发生什么，还是就是 Git——Git 它管理的是快照，也就是一个目录，整个一个项目的快照。我可以在快照上面做一个开发，它要求小步。那我现在有两个开发者，一个是 A、一个是 B，我们就可以独立地在这两个上面做开发，做出来的东西就是 commit。如果你想把它们合起来，在 Git 原来的模型里面，rebase 相对来说是不那么提倡使用的；它说的是：你创建一个两路的 merge，它有两个 parent，继承了这两个的修改。

但是这又带来一些问题。比如说这个 merge 是由 A 来干的，那这个 merge 里面的一些内容——由 B 写的那些内容——它的作者就变成 A 了。这其实有一个隐藏的作者修改。比如说 B 在这加了一行，这个可能还能追溯到 B；但如果发生冲突，在 resolve 的时候，冲突完了以后这个 change 是由 A 完成的，那么 B 改的代码最后 ownership 又归到了 A。所以这会带来一些相对来说有一点小的麻烦。

```text
A:  doc --- test -------------- \
                                 >--- M   (M has two parents, a new ID)
B:        feature --- test ---- /
```

两条线上的 commit 在这里都保留了自己的 ID，M 是额外长出来的一个新提交；被合并进来的那些改动的归属，实际上挂在了做 merge 的人（这里是 A）名下。

rebase 解决了这个问题。如果我现在有两个历史：A 同学改了改了两份，做了两次提交，得到两个快照 Δ1、Δ2；然后另一个同学 B 开始改。rebase 做了件什么事呢？比如说 A 先改了文档，然后再加了测试；B 加了一个 feature，然后又加了一个测试。这个时候我不是直接把这两个东西合成一个把两条线路并起来的提交，而是试图先试一试：这个 feature 有没有可能加在 A 的这个后面？如果加上了，OK，那就成功了。

但是这是有一个很大的风险的：我可能在这个里面加入了一个测试用例，而这个测试用例和这个 feature 就是不兼容的——这是有可能的；或者甚至它们就改了同一个地方，我做了两个完全不兼容的东西。那这个时候它就有可能失败。如果成功就比较好，我再把 test 翻过来。也就是说，如果这两条线上面面的修改完全没有任何冲突，我就可以一路把它合并过去，变成一个线性的历史。

但是一旦发生冲突，这就非常危险了。为什么呢？一旦冲突你就需要 resolve，你会进入一个 rebase 的模式。

> **易错点**：进入 rebase 模式之后，很多人会瞬间不知道自己应该怎么办了。这时候正确的做法是打开你的 agent，说清楚「我现在在做什么、发生了什么」，让它细心地解释给你——不要在没搞清状态的时候乱按。

更麻烦的是，你就算是把这个 feature 搬过来了，你可能搬 test 的时候又要失败，然后你还需要再把 test 搬过来，而且每次你都会创建一个新的提交。每个 commit 都有一个 ID。如果你是一个两路的 merge，那么所有原有的这些 ID 都保留了，你会创建一个新的 ID；但是因为你是 rebase 的，rebase 每次都会创建一个新的 commit——这个快照本来 base 在这儿，所谓 rebase，你就知道，它的 base 要改掉，要把这个 base 改到这里来——你会创建一个新的 ID，每次创建一个新的 ID，然后这个历史就变了。

```text
A:  doc --- test
B:              feature --- test
     |
     |  rebase: 把 B 的提交一个一个搬到 A 的后面
     v
A:  doc --- test --- feature' --- test'
                      ^            ^
                 新的 commit ID（base 已经换了）
```

于是你会感觉到这里有一点点轻微的不一致，觉得你好像不是完全想这样去管理软件。因为我们关心的是**修改**：我希望的是把这个修改搬过来、把这个修改搬过来。而在 Git 里面，修改是用 commit 来替代的——我现在有一个 commit，这个 commit 和它 parent 之间的关系就叫一个修改；它没有一个专门叫 change 的对象。

> **结论**：用 commit 来代替修改，绝大部分情况都能满足。但如果我们把 change 也变成 first-class citizen（一等公民），会发生什么呢？你就发明了下一代更好用的版本控制系统。

### Jujutsu：把 change 变成一等公民

这个工具就是 Jujutsu。Jujutsu 和 Git 底层完全兼容，你可以直接把它当 Git 用。但是它增加了一个叫做 change 的概念：每一个这样的东西、每一个 change，它都可以 assign 一个标识。然后它可以把好多的 change——比如 rebase 的时候——把 change 直接搬过来。

冲突本身是躲不掉的：如果 rebase 的时候两条 change 真的撞在同一个地方，这个矛盾没法凭空消掉。但因为它有这个 change 的 object、有这个 change 的概念，它可以把这些 change 一路带下来，直接 rebase 到这里，只不过里面引入了好多冲突。它还是运用了 Git 的那个冲突记录，但你看它在里面有一套自己的记录方式，把所有的这些 change 的冲突也都塞进去，然后你就可以在这里相当于把它们搬过来，然后在这里再 resolve。

它的底层的模型没有变，但是你用起来会舒服很多。

| | merge | rebase | change（Jujutsu） |
| :--- | :--- | :--- | :--- |
| 合起来时产生什么 | 一个新的两路提交 | 把提交逐个搬移，生成新 ID 的提交 | 把 change 搬过去 |
| 原有 commit ID | 全部保留 | 全部被替换 | change 的标识跟着走 |
| 作者归属 | 被合入的改动会挂到做 merge 的人名下 | 不会易主 | 不会易主 |
| 冲突处理 | 在 merge 的时候 resolve 一次 | 搬一个 resolve 一次，可能反复失败 | 冲突随 change 一起带下来，最后集中 resolve |

这张表把三者的差别收成一句话：前两者都在拿 commit 近似地表达「修改」，而 Jujutsu 让修改本身成了一个有身份的 object。

### 没有 staging area 的世界

它还有一个很好的特点：它不需要 staging area。

在 Git 里面最讨厌的是什么呢？我上操作系统的课的时候会讲这个例子：你现在有一个工作区，你有一个 repo，你有一个 hello.c，你把它改改改改、改到一半——这个时候项目还不能编译，也不能运行，测试也通不过。突然导师给你打电话：「哎呀，我现在有一个很高很高优先级的项目，你就有个 bug，马上客户就交不了差了，赶快把这个 bug 给我一分钟修了。」

好，那你怎么办？你不应该 commit。你需要的是把它加到你的 index 里，然后 `git stash`，它会压栈。这其实是一个比较讨厌的操作：你 stash 一个东西，然后你去把原来那个 bug 开始修；你刚修了一半，你导师又给你打电话：「哎呀你这个 bug 别修了，我还有一个优先级更高的 bug，你去把它修了。」你这个时候要再把它 stash。然后 `git stash` 是一个栈，里面会放好多好多个提交，你需要去管理那个 stack。

> **提示**：`git stash` 帮你把没干完的工作挪开，代价是你得自己管理一个栈；栈一深，就要面对 rebase stash 这类额外的操作。

然后你想想，如果任何时候、随时随地你都在编辑这个 repo，这不就是一个 change 嘛：你现在把 hello.c 改一改、加一行、减一行，它都是 change。

所以 Jujutsu 它好像是在干这么一件事：你但凡改了一个字节，它都会立即做一个 git commit；当然这个 commit 不会产生很多线性的历史，而是先把上一次的那个 commit 给抹掉——你改了一个字节，上一次的那个提交就被抹掉，然后你重新用当前的这个修改去替代这个提交。也就是说，你永远有一个 change、一个当前的 snapshot，它永远处于一个提交的状态、一个 change 提交的状态。那你就很舒服了，你连这个 staging area 也不需要了。

```text
工作区改一个字节
      |
      v
[ 当前 change ]           永远处于「已提交」的状态
      |
      | 再改一个字节：抹掉上一个 commit，用当前快照替换它
      v
[ 当前 change' ]          不需要 staging area，也没有栈要管理
```

这就是一个非常好的东西：你从「我要把 change 作为 first-class citizen」开始，再往后推，你就可以发明自己的版本管理系统。当然这不是它的全部，它还有一些别的路线可以推导出来。

所以你们适当的时候可以质疑一下：Git 有没有哪里做得不够好？如果可以做得更好的话，还能做怎么样的设计？我觉得这都是非常有趣的设计。你们可以在 agent 的带领下学，或者说我开了一个头：我给你们一些 motivation，你们可以把这些最重要的 prompt 交给 agent——「我如果要学 Jujutsu，我想从 change 开始理解」。你看它的 tutorial，它其实也是一上来就会告诉你它没有 staging area 等等，用它管理版本是更自然的。它首先对人类更友好，然后实际上它可能会对 agent 也稍微更友好一点。

### 肌肉记忆：为什么你们能够淘汰我们这一代

这就是我觉得为什么你们作为 AI native 的人类能够淘汰掉我们这一代人。因为我已经形成了 Git 的肌肉记忆，而比我更老的一代人，他已经形成了 SVN 的肌肉记忆。一旦人形成一个肌肉记忆以后，要把这个习惯掰过来就很困难。

比如说我现在对 Git 是有肌肉记忆的。我即便能够理解 Jujutsu 的概念——甚至我可能理解得比你们作为初学者还要更好一些，因为我还可以从 first principle 去思考它，相当于 virtually re-implement 这个系统——我即便能够理解，我也没有足够的时间再去训练另外一个肌肉记忆。

所以你们是反过来的，你们跟我正好是反过来的：你们应该在现在还没有形成肌肉记忆的时候，就直接去用那个对的东西。人类历史都是积累的嘛：SVN 实在是用不下去了才用 Git，然后 Git 发现了 Git 的缺点以后有了 Jujutsu。所以你们可以先用肌肉记忆记住一个最正确的设计，然后再去理解这个设计是怎么样。等你再回去想的时候：「哦，原来 Git 这么蠢。」在 Git 出现的时候，大家会想「哦，Git 这么先进，它是一个 persistent data structure」——SVN 从一开始走存 diff 那条线就走错了；然后到现在这个时代你再回去看的时候：「哦，原来 Git 也犯了一些设计上的错误。」当然这是因为它最早的时候没有想过 rebase 会有这么大的 impact：它有 merge 就已经很好了，就能解决它手上的问题了，所以它可能没有把这个概念模型想得更加清楚。

### 使用者是人：版本管理系统的隐藏前提

但门课不是软件工程，这门课是生成式软件工程。所以我们要真正要做的事，是在 agent 时代再次重新设计版本管理系统。也就是说，你当然可以让这个 agent 去用 Git，然后让 agent 去用 Jujutsu——对人类来说 Jujutsu 是一个很大的进步，但对 agent 来说可能进步相对会小一些，因为它好像很会 rebase 这些。

我们一路走过来：SVN 有局限，Git 有局限，那在 agent 时代，我们的局限和我们要破掉的改正是什么？刚才所有的这些 version control system，它都有一个假设。

> **结论**：这个假设就是——version control system 的使用者是人类。

人类有什么特点呢？人类是 single-threaded 的生物。我一直上操作系统的课的时候讲并发程序，并发程序我打什么比方呢？你就把线程想象成是一个人，然后你的线程可以访问共享内存。访问共享内存的时候，两个基本的操作是 load 和 store，或者说 read 和 write：我可以从一个变量里读一个值，把 x 读到我的临时变量里；或者我可以写 x = 1。然后这个操作是不能同时进行的——我不能说既读一个又写一个，你这样就需要一个原子指令了。

绝大部分的 shared memory access，你都想象成是人是什么样呢？我如果想要观察这个世界，对不起，我手要抱在后面，我只能看。等我看完了，比如说我看到这个同学在这，我想要对他施加一个效果，比如说我想用这个粉笔导弹射击他；那当我想要真正 write、写一个变量的时候，我必须要眼睛闭起来。而我把眼睛闭起来扔的时候，注意，我读到的那个值其实已经失效了——那是旧的值，是我上一个时刻读的。在上一个时刻到这个时刻之间，可能经历了很多的事情：可能我被换下 CPU，我被中断打断了，然后换了另外一个线程上来执行，执行了一秒钟以后我才恢复过来；但我恢复过来以后，我看到我的寄存器里面那个 x 值——我上次读的是 x = 1——然后这个时候我就把那个粉笔扔出去了。那很有可能扔的就是错的。

```text
read  （观察世界）：手抱在背后，只能看
      |
      |   中间可能被换下 CPU、被中断打断，过了一秒才恢复
      v
write （施加效果）：必须把眼睛闭起来
      |
      |   此刻寄存器里还是上一次读到的旧值（比如 x = 1）
      v
凭旧值扔出粉笔导弹  ->  很可能扔错了
```

所以 single-threaded，然后当多线程的时候，多线程共享内存又带来了无穷的问题。其实人类也是的：人和人之间是有无法逾越的物理屏障的，你不能理解我的思想，我也不能理解你的思想；我就是一个独立的个体，由分子把「我」很强地连在一起。所以我们只有一份 I/O 设备：只有一双手、一张嘴、一双眼睛。

### 提交节奏：从小时级到秒级

那么我们以这种方式编辑代码库、产生 change，就是以小时为单位的。一个软件公司负责一个模块的开发，可能多也就十几个人——十几个人已经是一个不小的团队了。十几个人每人以小时为单位开发，那最多这个也就是以 10 分钟这样的单位产生一个提交。而 10 分钟为单位产生一个提交，意味着这个速度会比人和人之间沟通的速度要慢很多。

尤其是一个 team，他工位都在一起——你们研究生的工位都在一起。你要写一个东西要一两个小时，你在写之前肯定是跟师兄说一声：「哎，师兄，我要干这个行不行？」20 秒钟、30 秒钟，师兄说：「行，你去改吧，我们现在不再改。」或者你们如果去厂里面打工了，厂里面可能每天早上都要开会：每天早上你的 leader 都会把任务分发出来，今天我们要干什么事情，你做什么、你做什么、你做什么。你就提前在半小时的时间里划分了一个 scope，把这个项目切开了，领了其中一部分走，然后你就去产生 change。当然这是古法——古法编程。

在古法编程的时代，你就看到，比如说 stash 是一个合理的设计：因为像我刚才说的那个情况——导师给你打电话——这件事情是可能发生的；但是在修到一半的时候导师再给你打电话，这件事情是不太可能发生的，概率很低。绝大部分时候你的 stash 也就是 stack 里面就一层；如果有多层，管理其实挺麻烦的，你还需要去 rebase stash。所以你会尽可能地保证这个 stash 不要太深，因为你可以拒绝一个工作：你可以说我手头上有一个更高优先级的工作，我现在对不起我不能干这个事；等你干完了以后，你自己可以排一个队列。所以 Git 是给人用的。

但是在 agent 时代，这件事情变了。如果是一个 agent team，单个 agent 他首先生产这个 AI slop 的速度就远远快于人：他生成 AI slop 就以分钟级为单位，甚至更快——有时候你让他 fix 一个东西，他在上下文是热的时候可能就几十秒钟，像 DeepSeek-V3 唰唰干活的时候就几秒钟就做了。那以秒级，当 agent 工作的时候，以秒级可以产生一个原子提交，并且你可以轻易地得到一个 10 倍、100 倍的 agent team 的时候，Git 或者 Jujutsu 这样的、为人的设计的模型就有点跟不上了。确实是有一点跟不上这个速度。

> **提示**：就算大型项目有一些门控——你改完这个部分以后，它必须要经历一个测试的流程，而这个测试本身可能就要运行几分钟——那可以放缓 agent 提交的速度，但毫无疑问的，agent 加速了这个软件开发的过程。

| 维度 | 古法编程（人类） | agent 团队 |
| :--- | :--- | :--- |
| 并发模型 | single-threaded：同一时刻只能观察或写入 | 多个 agent 各自独立，天然并行 |
| 提交节奏 | 以小时为单位，团队粒度约 10 分钟一次 | 上下文热的时候以秒级产生原子提交 |
| 团队规模 | 一个模块十几个人已经不小 | 轻易就能扩成 10 倍、100 倍 |
| 分工方式 | 工位旁二三十秒对齐，或早会划分 scope | 主 agent 协调、往子 agent 里 inject prompt |
| 中途被打断 | 概率低，stash 栈通常只有一层，栈式设计合理 | 打断频繁，栈式管理不再够用 |

这张表把两边的假设并排放在一起：左边这一列全是「人只有一个脑袋、一双手」推出来的设计，右边那一列的速度与并行度，正是老模型接不住的地方。

### 给每个 agent 一台开发机

那如果 agent 加速了软件开发的过程，我们应该怎么样为 agent 设计这个版本管理的系统？首先，我们可以让 agent 沿用人的模型：每个 agent，你就想象每个 agent 都有一个自己的开发计算机。那就把 single-threaded 的人类和 agent 做一个严格一一对应的类比：你就让他有一个独立的电脑，可能是一个容器，然后你把它放到什么 git.nju.edu.cn 上，然后你就直接 instruct agent 说：「好，我的这个 remote 仓库是在 git 上的，你现在就是一个单人开发者。然后你现在可以从 tmux 里面收到命令，如果你收到命令，你就可以开干。」所以这件事情其实是非常容易实现的。

在 agent 时代有一点特别好：每个人都是领导，你就是这个领导、工头。现在有两个 tmux session，你可以想象，你实际开发的时候，这两个 tmux session 都是位于两台不同的机器或者不同的容器，它物理上隔离开了，他看不到世界上其他的人。用上 master / slave 这个（可能在中国现在还能用的）词：我现在就是 master，我可以给它们每一个都起一个名字，比如 coding agent。然后它们两个就开始工作了，开始写 slop code 了。

```text
master（你 / 主 agent）
  |- 协调、看总监报告、往子 agent 里 inject prompt
  |- tmux session A  ->  容器 / 独立机器（比如 Codex 负责设计）
  |- tmux session B  ->  容器 / 独立机器（比如 Claude 负责 review）
  +- 远端 git 仓库（例如 git.nju.edu.cn）
       两个 session 各自 push / pull，冲突了自己修复
       必要时直接给 master agent 发消息
```

当 AI 开始变快的时候，你想一想：如果你的指挥发生了一点点差错，甚至哪怕不是差错——现在一个流行的 paradigm 就是，你有一个监工的 agent，然后你有好多这个子 agent；有些比如说为了最大化模型的智力、防止 AI 生成你不想要的东西，你会放两个比较强的模型，比如由这个 Codex 来设计，然后让 Claude 来 review，然后让他们互相打架，然后达成一致，你只要开两个 tmux 就行了。你的主 agent 就负责协调，观看他们的输出或者总监报告，然后往里面 inject prompt。这样一个多 agent 系统就转起来了。

然后看一下这个 repo 的 status：如果大家工作在同一个 git 仓库上就会有一些麻烦；但如果他们工作在不同的 repo 上，这是完全可以的——他们可以合到远端去、拉取别人的提交，如果冲突了就会自己修复，必要的时候甚至可以给 master agent 发消息。你们立即就可以构建出一个这样的多 agent 系统。

那么相应的，我们也有一些 workaround，比如说 Git 具有 worktree 这样的功能。所以你看，我可以问它：「**git worktree** 可以改进这样并行的工作方式，那么能不能让这两个 tmux session 都工作在 worktree 上？」

> **提示**：提问其实是关键的。你们甚至可以在今天早上走到教室的时候看微信公众号，上面说类似 git worktree，或者提了一个什么样的 sandbox container，你就可以立即让 agent 来帮你试一试。

git 允许我们创建一个工作树，然后这个工作树你可以想象成就是连接到了那个 remote 的、就是一个 git repo，然后我可以在这里面一个隔离的环境里面做独立的提交。大家都知道 `.git` 是一个目录，对吧？比如我的 `jyy-se`，大家都知道它的 `.git` 是一个目录，然后它里面有比如 logs、还有 objects，三种类型的对象。

```text
一个仓库，多棵工作树：

  <repo>/.git/            <- 共享的仓库本体（logs、objects 等都在这里）
     |- logs
     +- objects
     ^                ^
     |                |
  worktree A       worktree B      <- 各自独立的工作目录
  (tmux session A) (tmux session B)   各自在其中做独立的提交
```

同一个 `.git` 目录被多棵工作树共享，每棵工作树有自己独立的工作目录与提交——这正是「每个 agent 一个隔离环境」在当下就能拿到的现成做法。

## 从 worktree 到悲观锁：agent 时代的版本控制与团队管理
> 对应块：BLK08 | 覆盖分集：P05下 | 块标题（分集名）：《软件仓库管理（二）（下）》

### worktree 里的 `.git` 是什么

上一节我们把 worktree 用起来了，但有一个问题还悬着：worktree 目录里的那个 `.git`，到底是什么？

答案有点反直觉：它就是一个普通的文件，一个文本文件。你可以继续追问 agent，agent 自己也是后来才"知道"这件事的——原来 `.git` 除了可以是一个目录，还可以是这样一种只有特定格式的文件：里面写着 `gitdir`，然后指向别处。

那个"别处"才是关键。它是一个小型的 git 目录，依然带着 `HEAD`、`index`、`logs`，一个微型的 git 的目录；但它依附于原有的那个 git 目录而存在，不是自成一体的仓库。

> **结论**：git 在最大程度上复用了操作系统里的机制。能用一个文件表示的东西，它就不新发明一套目录结构；能借用文件系统的地方，它就不自己造一层抽象。

```text
主仓库                          worktree（第二个工作树）
  .git/                           worktree/
   ├── HEAD                        ├── .git   <- 文本文件，一行 gitdir: ...
   ├── index                       ├── src/
   ├── objects                     └── README.md
   └── worktrees/
       └── wt1/
           ├── HEAD     <- 这个小型 git 目录自己带 HEAD / index / logs
           ├── index
           └── logs
```

读图：worktree 里的 `.git` 只是指向主仓库 `.git/worktrees/<名字>` 的一行文本，那个小型目录自己维护 `HEAD`、`index`、`logs`，但又依附在原有 git 目录上，所以两边共享同一份对象库——这就是"提交在本地互相可见"的物理基础。

这个特性在 AI 时代突然变得好像有点用。因为提交直接在本地互相可见，就不需要互相 `pull` 和 `push` 了。像刚才说的那种做法——我开好几台虚拟机，每台虚拟机里放一个 agent，然后直接往那个 tmux 里面注入——当然也可以，完全能跑通。但 worktree 提供了一个更轻量的合作方式。

当然，它不解决一切：如果有冲突的修改，它仍然需要 `merge` 和 `rebase` 才能真正合并。只是性能会更高一点。

### 为什么需要版本控制：工具是被人的限制塑造的

worktree 这类机制属于今天的 work around。但如果我们手上真的有一个 agent team 或者一个 agent swarm，就不能只顾着找绕路的办法，还要回头来想一个更根本的问题：我们为什么需要版本控制？为什么需要版本管理？

我的答案是：这是人给自己的限制造出来的工具。哪怕是一个很小的 team、一个团队，也要 10 分钟才能产生一个 commit。而人之间是有 communication gap 的，这个 gap 逼出了整套工作习惯——你每天早上都要开一次会议，同步一下各个人的进展，然后再把这个任务给分下去。

这个 gap 有多大？你想想你室友向你请教一个数学问题，明明你会做，你就是怎么都没办法给他讲明白。除非你是个很好的老师，能够共情别人，能站在别人的角度去想问题——沟通的成本就是很高的。

这也解释了大厂和小厂、尤其是初创团队为什么效率可以更高：当软件系统大了、人多了以后，沟通的效率变低了，产出的速度也就降下来了。所以一个 100 人的团队，不可能达到一个 10 人团队效率的 10 倍，能有两倍、三倍就已经挺不错了。所以团队没有办法变大。

正因为人的沟通能力上不去，我们才需要 git 的那些 best practice：快照，小步前进。你改一个 typo 也要做一个 commit，你做点别的什么也要一个 commit，而这些小的 commit 每个都可以追溯。因为一旦出问题，你需要回溯到那个人做 commit 的那个时间点——而人是**有记忆**的，开发者会回想起：哦，那天早上我们开了一个会，我收到要做这个需求，然后做这个需求的时候沟通发生了一个问题。他会去找那个时候的沟通记录文档，然后再说我们这个地方应该怎么修正。

`git bisect`、`git blame` 这些特性，就是专门为人类设计的。

### 谁写错了，还是怎么修好

但换个前提想一想：如果是用 agent team 或者 agent swarm 来实现你的项目，我们还需要 `git blame` 吗？

人可以 blame，因为 blame 是要有人承担的——这个事情我 blame 你多了，你就该被开掉了，实习生你就背锅了。可如果 agent 没有坐牢、被开除的能力，这个模型就变了：我们再也不需要 blame 了，我们的项目只要前进就可以了。

更进一步，我们甚至不需要知道到底是哪一个提交引入了这个错误。我只要知道这个地方错了，我把它修了就行，不必再管它历史上是怎么造成这个错误的。

这背后还有一个更好玩的事实：我们的每个 agent 都是相同的模型。它们是完全相同的克隆体。同一件事让它们来做，虽然模型还是有不确定性，还是会收敛到相同的结果——同样的 prompt 做同一件事，可能有点细微的差别，但最终那个方向性的东西会收敛到相同的答案。

> **结论**：在这个前提下，项目永远是一个向前进的过程。历史的价值从"谁写错了"变成"我怎么把它修好"，我只要能知道从现在开始怎么样往前紧着走，这件事就可以了。

那快照还需要吗？还需要。因为如果这个方向走错了，你又没有保留历史上的某一个 snapshot，一下子往前走了好多以后再想回去，那个代价可能比你一点一点往前修要差。所以我们仍然不断的大步向前，也几乎永远不要看过去。git 的 commit 里面只是留下一些 lessons，记录这个项目到底经历了什么样的演化，然后不停地往前走、往前走、合并、合并、合并。

### 从乐观并发控制到一把锁

想到这里，计算机学科里学过的知识又起作用了。我又回到讲操作系统时讲并发的那一套。

现在的 git 模型，更像是数据库里面的并发控制。比如我们手上有两条 SQL，每一条都是一个 transaction，而且是很大的 transaction，中间可以混任何代码：你先 `select` 一个什么，读一下；我这里也 `select`；读完以后我可以做代码的计算——Python 代码或者 JavaScript 代码，这些代码是图灵完备的，你永远不知道它会根据看到的结果算出什么；我甚至可以从外面，比如根据当前时间去再算一个什么东西；算完以后我再 `update`。而 `update` 的时候就会产生冲突。

```text
事务 T1:  select  ->  ... 任意代码计算（图灵完备，结果不可预知）...  ->  update
                                                                            \
                                                                             >-- 冲突 / 循环依赖 / 死锁
                                                                            /
事务 T2:  select  ->  ... 任意代码计算（图灵完备，结果不可预知）...  ->  update
                              |
                              v
                     transaction abort  ->  rollback
```

读图：两个大事务各自先读、再任意计算、最后才写；真正的麻烦全部堆在最后的 `update` 上——它可能形成循环依赖（我要读你的、你要读我的），也可能互锁对方的对象，于是只能检测到依赖就 abort、回滚重做。

#### git 为什么像乐观并发控制

其实 git 的模型，有一点像这种**乐观的**并发控制（optimistic concurrency control）。

为什么说它乐观？因为它假设这两个 transaction 不会冲突。我在执行的时候就是假设它们不会冲突。

这个假设在数据库系统当中是大概率成立的。想想教务系统：每个同学的读写都是自己那一块数据——我选课选的是我的课，我查看课表查看的是我的课表。全局的冲突是不太可能有的。两个同学哪怕同时开始选课，我也是读我的、写我的，两条事务就都过去了。这叫 optimistic。

git 也是这样：我们事先开过会了，今天早上开过会了，所以我可以顺着这条路先做这个，另一个人做那个，然后合并的时候大概率不会产生冲突。不管是 `merge` 也好还是 `rebase` 也好，都能顺利完成。

#### agent 快了一千倍之后

但这是古法编程时代的比方，就像我们用 SQL 来做个比喻那样。

如果我们的 agent 快了 1000 倍呢？如果主 agent 在协调的时候一下子就分好多任务出去呢？那它们就真的有可能更频繁地触发 transaction 的 abort。

不过触发 abort 在 AI 时代也不是什么大问题——agent 反正出错了或者出了 conflict 它就修，它能修好。真正值得问的是：在 agent 的时代，我们是不是可以换一种并发控制的方式？

想想我们在操作系统里学并发控制，用的是什么？**上锁**。锁和数据库里的 transaction 是有点不一样的。锁是你要 lock 一个对象：我在讲操作系统时反复说要"一把大锁保平安"，你们做过实验就知道了——当我想访问可能冲突的资源的时候，我会先把它锁住，我要先 `acquire` 一把锁。这把锁一旦 acquire 以后，别人想要再 lock 的时候，对不起，上锁的人必须等到这个 acquire 后面的 release 为止。一个 release-acquire 的关系建立起来，就必须是先 E1 后 E2，而不是那种乐观的、大家先往前跑、跑了再说的做法。我必须在使用这个资源之前，先 declare 我对这个资源的使用，用上锁的方式。

你看，只有你在操作系统的课、数据库的课里真的把这些东西学会了，回来再想的时候才会发现：哦，软件工程里面这些概念又要再做一次。

所以想想现在——如果 agent 的动作非常快，我们其实应该用更加偏向**悲观的**并发控制。

也就是说，我今天要做什么事，或者我有一个主 agent 去做规划，规划完了以后就立马把这个项目的某一个部分给锁上。我应该在一个 git repo 或者一个快照上支持一个锁的操作：把 scope 说好，我现在锁住了，我要做一件事、需要这些。先上锁，上锁后做，做完以后 commit。

```text
主 agent 规划
     |
     v
acquire 锁（declare scope：文件级 / 目录级 / 快照的某一块）
     |
     v
动手做 —— 与此同时，别的 agent 在没有被锁住的 scope 上照常推进
     |
     v
commit
     |
     v
release 锁  -->  等在同一个 scope 上的 agent 这时才能 acquire
```

读图：悲观控制把"声明使用范围"提到了动手之前，冲突从"提交时才发现的意外"变成了"上锁时就已排队的事实"，因此几乎不会再有 abort 与回滚，代价是等待。

另外一边当然也可以上锁，但一旦他想要干的事情已经被别人锁上了，他就必须等到前面那个人释放了锁，才能再去 acquire。这样不就几乎避免了所有的冲突吗？比如我可以在**文件级**上锁，就避免了两个 agent 同时去写同一个测试、或者往同一个配置里面做更改。而又因为 agent 数量足够多、速度足够快，我仍然可以保证整体项目的进度往前推——因为也许还有别的 agent 可以继续运行。

这和操作系统里实现并发程序是一回事。我经常说，就算一把大锁保平安，或者哪怕把锁拆小了，互斥锁的本质仍然是**不要并行、不要并发**，它和多处理器的并行是有根本矛盾的，它要把一个能并行的程序退回成一个串行程序。但当系统里面有好多独立的、不冲突的线程在运行时，即便每一个线程都持有了一把锁，它还是可以继续高效地跑——即便悲观的，它依然可以是高效的。

| | 乐观并发控制 | 悲观并发控制（上锁） |
|:---|:---|:---|
| 前提假设 | 假设事务之间不会冲突 | 冲突必须先被排除，才允许动 |
| 典型机制 | 各自读、算、写，提交时检测冲突，失败则 abort | 访问前 `acquire` 锁，别人 release 后才轮到 |
| 冲突的代价 | 回滚、重做 | 等待、阻塞 |
| 适合的场景 | 各人读写各自的数据（教务系统选课） | agent 动作极快、并发极高、冲突频繁 |

把这些知识关联起来，就让你看清楚一件事：在 agent 的时代，我们又可以重新设计一个版本控制的系统。所以我觉得，agent 时代软件工程肯定是要发生很大变化的。从这个 first principle 出发——我们要管理快照，要管理版本，要管理 change，还要管理**飞快的** change——答案是什么？git 可能是一条线；如果我们用一种像上锁这样的方式来管理软件，那可能又是另外一条线。

所以你发现，学操作系统、学数据库这些东西是有用的。虽然痛苦，你还怀疑过：在 AI 时代我学这种东西干嘛，AI 都会写数据库了，这个 SQL 查询我早就不写任何 SQL 查询了。那还有没有可能学数据库是有用的？答案是有用的，你还是得去好好学习。数据库里面也有诸如 2PL 这样的机制。

这也是为什么我喜欢上课：如果我不来上操作系统课、不上这门生成式软件工程课，可能就不会让我在备课的时候把这种事情在脑子里面再过一遍——是不是地球上所有人都错了？因为我讲给你们的时候，我必须共情我的听众，要考虑到你们是一个只能接受比较平实、朴实逻辑的听众，不能直接就说这个系统是怎么设计出来的。我必须要帮你们把那个最顶层的 idea 提炼出来，然后试图让大家共情。当然这可能我做得也不够好，你们可以在 AI 的帮助下再重新理解一下。

### 工具之外，真正难的是团队管理

版本管理到这里，基本上就讲完了：从历史动机，到过去 git，讲到现在，直至再讲到未来可能发生的事情。

但版本控制本质上还是一个工具——哪怕是我刚才说的那种基于乐观锁或者悲观锁的版本控制，它仍然是工具。真正困难的实际上是在进度，也就是**团队的管理**。

我们为什么现在觉得还需要软件工程？就是因为我们还没有办法做到一句话就直出一个高质量的产品。如果这条展开线到了那个程度——老板有一个想法，说我要做一个 agent 用的微信，或者做个 AI 时代的微信，是个社交爆款，以后这些人社交也就不要用微信了，就用我的——而如果这个时候 AI 直接就能出那个微信级的产品，那软件工程就已经死了，我们这就都死了。但现在这条展开线暂时还没有到，至少没有到团队管理这一层面，所以我们可能还要学。

也许有一天我也要被替代。你想想，摩尔定律、scaling law 现在还是成立的，模型肯定会更强、更小、更快，也许算力有一天真的能够换出我们的智能。但今天至少 AI 还不知道怎么做团队的管理，因为每当你多一个人的时候，沟通的关系都是**平方级**上升的。

因此现在软件工程团队里面最难招的其实不是码农，是那个能把任务分解的 team leader。最难招的是那种能接住国民级应用的人：说我要去造一个微信，然后他还真能把它分出去——我就一个 100 人的团队，能分出 10 个小团队，10 个 team leader 各自去干，最后加起来拼接起来还能成为一个东西。这种人最稀缺。接下来那个能够带领小团队的人其实也很稀缺。《人月神话》里面讲的就是这件事：人人之间两两之间是平方级的沟通关系。

而且就算你能把你份内的事情做好，因为这个平方级的沟通关系，别人也在做他的事，你不可能 100% 知道别人在做什么；你对整体团队了解不够好的时候，最后还是各种冲突：你写测试我过不了，这种事经常发生。

那么，如果我们想管一个团队，或者想在毕业的时候具备一定的团队管理能力，你现在就可以当成是那个主 agent——就像我刚才那样。当然刚才我给了一个不好的示范，我说我以前同时接两个 slave。你现在也可以立即拥有这个 DeepSeek-V3 的 slave，然后你可以去想：如果你要尽可能最大化两个、三个或者更多 agent 的产出，你应该怎么把这个任务给分解？你应该怎么样确定一个提交的策略——什么时候你的 agent 应该提交，什么时候它应该合并？然后你就可以把刚才我们讲的所有的版本控制概念，带到你自己的开发流程里。

> **结论**：版本控制是工具，它由蒸馏了人类过去软件工程很多年经验得到；而在这件工具上，你可以开发出属于你自己的软件工程的直觉和经验。

### 一道只能单方向移动的汉诺塔

学东西还是有用，而且常常有意外的用处。最近我看到一个蛮有意思的题目，像是面试题，一般又是小学生考级的题目。

汉诺塔大家都会，低阶的会。现在有个额外的要求：**所有盘子的移动只能往一个方向**。

先拿两个盘子看：我把盘子往这个方向移是可以的，往那个方向移也是可以的，折回来也行——但要只能往一个方向移动。等到了三个盘子，问题就露出来了。正常的汉诺塔，我要移三个盘子，是先把上面两个移到中间，然后把下面那个大盘子从这里移到目标柱上。但在"只能往一个方向"的限制下，你做不到这一步，你只能顺着那一个方向移动。

```text
正常汉诺塔（可双向）：         单向汉诺塔（只许朝一个方向）：
   A ---> C                      旋转环上的唯一前进方向
   小盘可回退，因此先腾出手        不能回退，所以"先移两个到中间"这条路被堵死
   再放大盘                        大盘子的走法被强行固定为"每次一格、同向循环"
```

读图：限制的落点不在小盘子上，而落在最大的那个盘子身上——它失去了"直接挪到目标柱"的自由，只能顺着环一格一格走。

很难想象小学生要做这样的题，而且还要输出方案、输出这个数字。n 也不是很大，但你确实需要真正理解这个问题。这难度放在保研机试里，就相当于是小学生难度——你碰到了这道题，你要输出方案或者输出那个数字，你总得先想明白。

怎么想？还是递归。你要把它移过来，第一步仍然是一样的：你需要先把它移到这里。区别在于后面——你只能让这个最大的盘子向右移一格，然后再把它移到这里，再让向右的盘子移到这，再把它移到这里。

> **结论**：所以看最大的那个盘子就会发现，在最优解里，大盘子总是向右移一个、再向右又移一个。这是不可避免的，因为它没有别的走法；也就是说大盘子移动的次数已经到最少。剩下的部分基于 inductive，用归纳法递归处理，也同样是最优的。

我当时就准备了一个这样的小例子，写了一个程序：如果我的下一个目标不是目标，我就只看最大的盘子，我总是向右移一个、再向右移一个，所以它是最优的。

### 从 playground 到 AI 助教

讲这道题不是为了讲题。真正的问题是：如果我要把这个东西卖给小学生，我怎么才能最好地把它卖出去？当然就是提供**付费的增值服务**。

小学生可以在这里写代码，代码随时可以编辑。可视化的过程是随着代码来运动的——比如说错了，我就能找到那条语句，看到它试图把一个蓝色的（小的）盘子移到一个大的盘子上，然后同学们就能自己找到 bug。

到这一步还只是一个纯粹的 playground：你可以写代码，可以运行它。接下来我就提供一个 **AI 助教**。当小朋友实在做不下去的时候，点一下"我要助教"，这个时候 DeepSeek 的 token 就开始燃烧。然后我就可以收取比 DeepSeek 原价更贵的 token 费，记在你的账户上。

为什么我敢收这个钱？因为我的 prompt 是我独门的。我作为一个有经验的老教师，可以把我自个儿蒸馏成 prompt，然后我能敏锐地知道这个小朋友的问题在哪里，给他一个个性化的指导。

做到这一步，我就涉及要做一个**信息系统**了。这件事我让学生来做，我自己没有时间。我看了学生和 AI 聊完的一版设计，然后让 GPT-4o 大概梳理了一下需求。GPT 的原话是：一个 API 应用、一个关系数据库、一个对象存储；需要异步点评时再加后台任务进程、数据库关系和记录；大课程包与完整轨迹存放对象存储；任务量小时，数据库任务表就够用。

这是一个非常正常的设计。如果你们上软件工程课，那太正常了——你看 GPT 嘛，它是一个语言模型。

**但我并不喜欢这个设计。**

你们有没有用过 Overleaf，跟别人协作过文档？Overleaf 有一个功能：它可以当成一个 git repo 导出来。我最喜欢这个功能，因为我要给学生改论文。我就可以直接把 agent 启动起来——把那个论文 clone 到本地，就不需要忍受那个网页界面了，然后打开我的 Codex，让 Codex 起 sub-agent，给每一个 `.tex` 文件去修复里面的语法错误。我可以给一个很长的 prompt 让它重新指定，然后论文就改好了，再跟学生说已经改好了。

回到 PickCode playground。难道不应该是这样吗：学生每改一次——比如我现在 idle 了，或者我点了运行，或者我切换了——就自动做一个 git 提交？然后我就可以把 AI 的点评挂上去：当我申请 AI 助教、它在那里转圈圈的时候，我就在这个 git 提交上面产生一个分叉，那就是一条 comment。

GPT 没有算到的是：我产生这个东西的成本，远小于把剩下的东西 persist 下来的成本——这个成本是忽略不计的。

而当我用数据库的时候，我确实得到了一些好处，比如总体压缩可能更小、性能更高，但这其实不是我想要的，因为**我的本质需求是版本管理**。

所以我甚至在最早期的时候，可以把我的代码库和这个东西连在一起，把它放在我的代码库里：小朋友的代码就直接存在我的代码库里，然后我可以探索性地在这上面创建 git 的历史记录；直到我认为整个文件目录的格式、commit message 的格式、我怎么使用这些文件都收敛了，再把它迁移到数据库。这完全是可以的。

你学任何东西都是有用的。你学 git 是有用的；你学了 multi-agent 的管理，你就能有一个机会去想到一个和别人不太一样的设计。

### 项目早期：你就是包工头

接下来我们真的可以干一件实事了：怎么开始一个项目。

**项目的早期阶段，你肯定不能用 multi-agent。**项目的早期阶段你就是包工头：你先找一个相对来说能力比较强、你能用到的最强的 agent，然后跟它做多轮对话。所以我要告诉大家，你们现在开始干，就比什么都要好。

我决定现在就直接打开课程作业。我不知道等会儿会发生什么，因为完全没有事先准备过。

#### 让它从零开始做课程作业

有两种办法，第一种是直接回车。我觉得每个同学都可以体验一下，当然我今天来替大家体验。

我们来观察它会做些什么。有时候 AI 的直觉和人的直觉就是有点不太一样。像一些模型，它会先进入一个 plan mode，会跟你再确认一些事实，然后才生成一个 workflow。如果你没看过，其实是挺好玩的。比如 Claude Code，当它需要执行一个比较复杂的任务的时候，它会生成一段 JavaScript 或者 TypeScript，里面有一个函数叫 `agent`，而这个 `agent` 里面是自然语言。它用这种方式来组织 workflow，它甚至可以有循环——我有好多任务，然后可以在循环上面来解决这个 workflow。

然后它就**直接开干**了。用魔法打败魔法。这个 300 token per second 实在太恐怖了。

#### slop 从哪里来

让它跑一会儿之后，你看到的正是我前面说过的、上下文工程或提示词工程里最危险的一点：

> **易错点**：你提示词里面的每一句、每一个词，self-attention 都会看到它。而 AI 现在已经被训练成了 prompt 的舔狗，它有一种没有办法往外拉的倾向，需要遵循你的指令。所以当你把需求——尤其是这可能是一个讨论稿的需求、一个比较开放的需求——丢给它的时候，它就会**过度遵循**这个指令，最终生成一个确实满足了指令、但其实不是你想要的答案。

回头看那个实验的要求，它其实是言外之意。其实最要紧的只有一句话：**实现一个持续为你工作的个人助手**。其他的话相对来说都没有那么重要，它们只是对这一句话的一些解读。

那么，作为一个好的、为你工作的个人助手，要求里列的那些条 1、2、3、4、5，哪些比较重要？这每个人都有自己的观点。对你来说，如果你想实现你自己的个人助手，什么最重要？你实现的第一个 feature 是什么？你在可能一个月以内遇到的最大的痛点问题是什么？

答案是学习，是高效的学习和复习。因为你们要卷成绩，所以这毫无疑问是最重要的一个学习 pipeline。你最好是让这个 agent 能够自动从外网上面收集数据，然后把它以一个层次化的方式归档，最终再给我一个比较好的界面。这才是你最想要的。

我估计它十有八九没有。我们来赌一赌。我问它：我想要的是一个比较好的学习助手，能收集外部信息，不仅是收集，还要综合总结，根据我的进度来学习、看哪部分——能实现我这个功能吗？

你看，它在做 database。

> **结论**：在没有你精心设想过、讨论过的时候，AI 基本上只会生成 slop。你要的东西和你脑子里所想的那个东西——这就是我说的你的 intent、你的 specification——跟它的实现之间有巨大的 gap。

但反过来也要看到：一旦这个模型看到你说要实现这个，他就真的去实现它了。

它肯定也做了一些不好的设计。比如当我提"一号"的时候，我真正需要的是一个 browser use agent，它能帮我在各种网页上面处理；"一号"只是一个作为测试的出口，它能把我的个人信息放到"一号"上面。所以我第一步实现的并不需要在这个教务系统上面做太多的设计——你做了过度设计反而不好。

这和前面那个例子非常相关：看起来它做的所有事情都是对的。从 `README.md` 来看，它做的所有事情都是正确的，没有一个错误。但最终它得到了一个你不想要的东西。

我看现在有没有 git 提交。它甚至都没有创建一个 git repository。这就是你不跟它讲的结果。当然我觉得如果换成 Codex，它可能还是会初始化一个模板，或者会问你这个项目应该怎么管理。如果我是个成熟的产品经理，老板跟我说完这个想法以后，我肯定会跟我的团队去沟通一下：这个项目怎么管？甚至在我写下第一行代码之前，我都要讨论好协作怎么做、项目怎么管、每天什么时候开会。

agent 很好玩，它就直接上手就做，它觉得 OK，这就是一个用一次就丢掉的东西。感觉它烧了我不少 token。也无所谓了，我参与 DeepSeek Janus 内测，它送了我 1000 块的额度，到现在还没有完全用完。

所以你们在刚开始的时候，还是要回到项目、回到管理，脑子里面要有这样一个模型：

> **提示**：你不能直接把任务丢给 agent。第一件事一定是**创建一个空的仓库**，创建完了以后你再去想你的下一步要迈向哪里。而且下一步也不能是它那种一步跨过去的大步，你需要的是**往前再迈一小步**。

你由此会发现：现在的 AI 从零开始做一个东西、做出一个 slop，难度比它到一个成熟的项目里去做一个维护性的任务要**大**很多。

### MVP：以不变应万变

我们对软件工程的真正的要求，或者说如果我要跟一个 team、跟一个学生去谈论我们要设计一个什么软件，我的问题是：**你能不能以不变应万变？**

也就是说，你现在设计一个架构、设计一个流程方法，它能不能抵抗未来需求发生的根本性变化？

在刚才那个例子里，这个问题的落点就是数据库。我说我要生成一个挣钱的产品去挣宝妈们的钱，我真正需要的是一个能扩展的架构。当未来有别的需求来了、AI 模型发生了变化、我的合作模式发生了变化——AI 助教有可能是文字的助教，有可能是图像的助教，有可能有交互，有可能没有交互——在各种各样的需求不断变化的时候，我还有没有可能用最少的变化去应对需求的变化？

而这恰恰是软件工程课也不讲、数据库课也不讲、操作系统课也不讲的。大家都说好：操作系统是长这样的，数据库是长这样的，数据库为什么要这样做并发控制——都是有原因的。但软件工程最不一样的地方，就是对未来需求的变化。

回到现场。它已经实现完了，界面上甚至出现了"提交人民奖学金申请""准备退课"这样的内容。看有没有 git——它倒是做了一个提交，直接一个提交。它说引擎全部是真代码，手机端接的也是真实服务、是集成的，模拟掉的部分里邮箱是没有的。它有一个入口层、一个编排层、一个能力层，还是个非常典型的架构，还有数据层。

```text
入口层
  |
编排层
  |
能力层
  |
数据层（assistant.db：个人资料 / 邮件归档 / 索引 / 草稿）
```

读图：这是一套标准的业务系统分层，看结构没有一处错，问题在于它把这件事整个当成业务逻辑系统来做，于是直接长成了一个教务系统的样子。

我就不试图 review 了。但显然它把它当成一个业务逻辑系统来做，这其实有非常大的风险——它看起来已经像一个教务系统了。我下节课就会讲教务系统。

而现在更符合主流 best practice 的做法是：如果你真的要从零开始构建，你要用一个叫 **MVP** 的 paradigm，也就是 minimum viable product 或 minimal viable product，先有一个最小的验证版本。这里有一句话：the biggest risk in product development is building something nobody wants。

它做的这个东西就是我不要的，其中很大一部分其实不是我要的。在它写代码的时候我就解释过，我其实想要的是什么。

所以如果你要做一个最小的版本，它逼迫的是你要想清楚：什么样的需求才是你**绝对**要的。

如果我要做一个个人助手，我最想要的是它能提升我的学习效率和我的工作效率。总结出这两条以后，你可能在第一个 MVP 里面**没有任何的数据库**。因为你会想到：在任何时候，当你的文件系统膨胀了，你都可以直接跟 agent 说，按照这个数据的组织帮我提炼出一个数据库，这个问题就结束了。

> **结论**：你不需要在刚开始的时候就做数据库。因为一旦你带上一个数据库，你每次数据库重构都需要让 agent 去做 database 的迁移；而文件系统不一样，文件系统你自己就可以在你的文件管理器里去调整它的目录结构，逐渐梳理到你舒服的一个结构上。

你在里面调文件，和你去调 database 的 schema，心智负担是不一样的。人类已经训练过：人类对直观的东西已经训练得非常舒服，文件目录在计算机里面操作，你从小学上电脑课开始就在做这件事，所以你对这个模式非常习惯。但一旦你说你要操作一个 database schema，你们很多同学还没有学过数据库课，你根本不知道它是什么。面对一个未知的东西，你需要强行做一次概念的翻译：我脑袋里面是这样的概念，我要把它翻译到数据库里是这样的。那你不如用一个你已经适应了、熟悉了的 system，用最简单的方式帮你把东西管起来——比如文件形式的学习资料管理、学习资料的进入、通知消息的进入。

甚至到现在，我自己回邮件的那个 agent 都没有用任何的数据库。我的流程大概是这样：

```text
邮箱
  |
  v
[agent 收邮件]  ->  解析出草稿 / 分类 / 是否垃圾邮件
  |
  v
共享云盘同步（只落 email ID 与解析结果）
  |
  v
[下一级流水线] 继续处理
```

读图：这里没有表、没有 schema，只有几级流水线和一份靠云盘同步的中间数据——先想清楚"我的系统里有哪几级流水线、它们之间怎么协作、哪些东西通过云盘流转"，架构的样子自然就出来了。

也就是说，我先要明白的是：我的系统里面有哪几级流水线；然后这几级流水线之间应该怎么协作，哪些东西通过云盘。比如因为我很喜欢我的云盘，那么引入云盘是不是要做一些架构的修改？我希望邮件、资料等都和云盘保持同步——这就叫**需求的更改**。我现在不知道它的架构做得到、做得好不好，我让 agent 来帮我看一下。

所以，什么是好的软件架构？你在当前当然有一个需求，现在这个实现可能是满足这个需求的。但是当你的需求发生变更的时候，你相应做出的那个变化是摧毁性的、是背上一个技术债，还是别的？那就不知道了。

我们来看它的设计。它有一个 `assistant.db`，要把个人资料放到这里，邮件归档也放到这里，索引、草稿仍然在 DB。现在看起来还不会引起很大的问题，因为绝大部分都长这样，确实应该不会引起特别大的问题。但是随着这个项目不断地进展，你会发现有两种开发方式：

一种是，你上来就是一个大的系统，好几大步就把需求都实现完，然后就拖着这个技术债不断地往后迭代，往后加功能、加功能；另一种是，你能以最小的代价得到一个特别精巧的架构。

我为什么要举刚才那个例子——因为当你发现我用 git 管理这个学生的提交以后，很多事情都变得非常容易，我自己控制起来也轻松很多。**直到我遇到性能瓶颈之前，我都不想要把它迁移到任何一种数据库。**

这也意味着，其实你早期的 prompt 对整个项目的走向的影响是最大的：你最早的那个 prompt——我直接把 `README` 给它，还是说我要做一个 MVP——都会对项目造成很大的影响。

### 版本管理做的三件事

如果要给这两节讲版本管理的内容留一句话，那就是：版本管理做三件事——**记住现在，记住历史，记住教训**。这在 agent 时代和古法编程时代都成立。

你需要"现在"，是因为你必须有一个 repository：不管它是哪种形式，现在以 C 或 C++、Python、JavaScript 的项目，你都需要把文件管起来。

你记住历史，是为了有一天你这个东西不要了；或者你删掉了一个东西，最终发现它对你还有用，你还可以把它捞回来。

而在提交的历史过程当中，你能看到自己是怎么演进到一个点的，然后发现这件事情失败了。这个失败你可能就留在那儿，然后你回到另外一个点，再开始另外一条正确的路线。这些东西都在版本控制里。

而 lessons 不停地在警示你：你需要怎么做，你怎么样从第一步开始，迈出向后的一小步。

### 本讲提到的题目

**题目**：单向汉诺塔。把经典的汉诺塔加一条限制——所有盘子的移动**只能往一个方向**（也就是三个柱子构成一个环，只允许沿环的同一个方向前进，不允许反向回退）。给定盘数 $n$，要求输出移动方案，或者输出所需的移动次数。$n$ 不大，但要真正理解这个问题才能做对。

**解析**：正常汉诺塔的解法是"先把上面 $n-1$ 个盘子移到中间柱，再把最大的盘子直接挪到目标柱"。这个思路的关键一步——把最大的盘子直接挪过去——在单向限制下被堵死了，所以必须换一个看法：不看小盘子，只看最大的那个盘子。

在只能单向移动的约束下，最大的盘子没有别的走法，它只能顺着环一次挪一格、同向循环。所以任何合法方案里，大盘子的每一步都是被强制的，它的移动次数自然就已经是最少的，这是不可避免的下界。

**答案**：最优解的结构是——让最大的盘子沿唯一允许的方向一格一格地推进（向右挪一格、再向右挪一格……），在它前进的间隙里，用归纳法（inductive）递归地把上面那 $n-1$ 个盘子挪到合适的位置。因为大盘子这一步是不可约的下界，其余部分按同样的归纳法处理也是最优的，所以整个方案最优。题目要求的是输出这套移动方案（或其次数），而不是只需要一个数字。
