现在大学的崩溃是系统性的。我对这件事有一个自己的理解：大家都知道网上可能有更好的资料，Stanford、MIT，哪个不比我二流大学牛逼多了？所以你会本能地拒绝你的老师。但同时又没有人督促你，而人的天性就是摸鱼——比如我的梦想就是做一条咸鱼。这样一来，你就等于同时拒绝了你的老师和那些牛逼的网课，进入一种"老师用豆包出题、学生用豆包做作业、助教再用豆包改作业"的恶性循环。整个流程都很丝滑，但大家肯定也焦虑。

### 两种焦虑与一份简历

第一种焦虑，是怎么平衡短期利益和长期利益。AI 对我的诱惑力实在太大了。以前那种折磨人的魔鬼实验 bug，天天调到凌晨，现在豆包都能搞定了。你去做实验吧，觉得很不值——凭什么宿舍老哥秒交了作业就去找女朋友了，我还要淦代码？不做实验吧，你又担心自己没学懂，后面的课就学不会了。

另一种焦虑，是怎么找到毕业的出路。延续了中学时代听老师话的状态，结果却没有得到想要的东西。可能你宿舍老哥有了 AI，学东西贼快，说的话你自己都听不懂了，他要保研了，你就更焦虑了。

比如大家要保研、套导师，我会收到好多简历，有些就是海投的。这里给大家看一份简历——当然也经过匿名处理，还是 agent 搞定的，我让它直接把 PDF 里带信息的都换成 Unicode 方块。乍一看，这是一份非常完美的简历：成绩不错，有项目、有奖项，还有一篇 accepted 的论文。

但你的简历如果不长成标准化的样子，不非常努力地包装出自己做过科研、做过项目、参加过一大堆竞赛，不用 slop 塞满，就找不到下家。本质上大家对自己的硬实力不自信，就疯狂在能加分的地方找补，进入无意义的内卷状态。

> **结论**：一份简历上最要紧的不是堆了多少奖项，而是有没有一个别人能点进去看的东西——GitHub、个人主页、preprint。这三样恰恰是最难"包装"出来的。

我一直都觉得大学最需要的是启蒙课程：这样一门课会带大家打好学科的基础、找到自信、解锁一个新的人生可能性。我以前上计算机系统基础和操作系统都是这个思路，虽然建立自信的过程说实话挺痛苦的，第一节课就要教你 Read the friendly manual。我们在这一个学期的时间里一起学习怎么驾驭 AI，做一些真正有趣的东西。因为这是一个全新的主题，课程所有内容都是我自己的个人理解，我非常欢迎大家提出反对的意见和建议，我也都会认真考虑的。

### 提示词：你和机器之间唯一的接口

今天我们来讲生成式软件工程里关系特别大的一个东西，也就是你和 AI 沟通的那个渠道——自然语言的提示词。这基本上就是大家和机器沟通的唯一接口。

从 ChatGPT 的时代开始，大家从那个聊天框开始跟 GPT 聊天的时候就知道：我们有 prompt，要给机器一个指令，然后 AI 会给我们返回很多内容——可能是文字、代码、图片，都有可能通过 prompt 来生成。

我第一次感受到 prompt 的力量，是每年我上操作系统课的时候。当时正好是 2023 年，也就是 2022 年底 ChatGPT 刚发布的时候，我试图让 ChatGPT 帮我讲一讲 inline assembly——现在应该已经没有人写 inline assembly 了，它成了一个传统艺能。结果发现它解释得出奇地好，而且真的是一个应该不在它训练语料之内的东西：我稍微故意做了一个系统程序员应该不会实现的 inline assembly，但它做得相当好，虽然确实不完美。那一下我突然感觉好像时代要变了，但可能没有到今天这么清楚地感受到时代会变、以及会怎么变。

提示词就这样成了一个新词，prompt。在这之前，在 ChatGPT 之前，我们没有用这个意思来讨论过 prompt 这个东西。

### 提示词不只是聊天框里那句话

你们可能会觉得，我在聊天框里打的那段东西才叫提示词——"帮我生成一个什么什么样的游戏"，或者"帮我把这个作业做完"。但实际上提示词不仅是在你的对话框当中的。

Agent 看到的是一整个 Agent 的上下文。也就是说，从你和 Agent 聊天之前，这个 Agent 就能看到一个叫做 system prompt 的东西。这也是一个提示词，它也叫做提示词。在 system prompt 之后，它还会加载很多东西：你的 AGENTS.md，你可能还会加载一些 skills，而 AGENTS.md 里面还会要求它再去读别的文件。所以在你的 Agent 第一次停下来和你对话的时候，它里面已经有很多很多东西了——从最初那个系统提示词开始，那可能是你的 Agent harness，比如 Codex、Claude Code 内建的；除此之外，你所有的工具调用和工具调用的结果，实际上也出现在你的上下文里。它是一个线性的上下文。

然后直到有一天，user 会和它聊天，说：给我做一个游戏吧。

```text
system prompt  （harness 内建：身份、工具使用指南、回复要简洁）
      |
      v
AGENTS.md  全局  （如「用中文回答」「结业必须写一个 recap」）
      |
      v
AGENTS.md  项目级 （每层目录都可以再放，指令一层一层叠上去）
      |
      v
skills 索引  （只有名字与简略描述；按需加载，用完从上下文抹掉）
      |
      v
工具定义  （以文本形式直接写在上下文里）
      |
      v
会话历史 + 每次执行注入的环境（模型、当前时间……）
      |
      v
user 消息：帮我做一个游戏
```

也就是说，这是同一段上下文里的先后顺序：越靠前的东西越像"制度"，越靠后的越像"当场的请求"，而模型每一次输出 token 都要把这一整条序列再看一遍。

所以提示词是非常非常长的，这也意味着今天 Agent 的能力是非常离谱的。它可以看到一个非常长的提示词——比如你在最早的 system prompt 里面可以让它用中文回答。我就这么干，因为我为了上课的效果，我就会让它用中文回答：哪怕我用英文写 prompt，我这边 user message 是英文，它输出的仍然是中文。

那么实际上，当我们说优化提示词的时候，我们就不仅仅是给它一个指令。

> **定义**：当我们说"提示词工程"（prompt engineering）的时候，我们实际表达的是一个叫**上下文工程**（context engineering）的东西——不是那一条指令，而是整个模型的上下文。

我们都知道，模型做的是 next-token prediction：它每一次预测下一个 token，这个 token 可以是调用工具，可以是输出一个字符，anyway，但它会不停地向后推进你的任务的执行。

大概是从 Claude 3.5 那一代的时候开始，Anthropic 发现模型突然学会了——它靠强化学习和后训练学会了非常强的指令遵从能力：你有一个非常长、接近百万的上下文，它依然可以在很后面的时候遵循你的指令，并且能够一定程度上看到前面的东西。

> **提示**：这里有一个很著名的梗。你可以在最早的 prompt 上加一句："你每说一句话，都要在后面加一个'喵'。"然后你等它工作、工作、工作，突然有一天你发现，它跟你聊天的时候那个"喵"丢了。这时你就知道——不管是因为上下文溢出被截断，还是被压缩了，反正它开始不能遵循指令了，你需要重新想一个办法。这就是大家在工程实践当中发现的、各种各样有趣的上下文工程方式，也就是提示词工程的方式。

### 解剖一次自己的上下文

上这门课，我也希望告诉大家最重要的一件事，为什么会说"没有 token 就应该退学"：我希望告诉大家的是，所有的事情你都应该立即开始尝试。

AI 给我们的一个能力就是：任何时候你觉得有一点麻烦，你都可以立即行动，因为 AI 是一个非常耐心的老师。不像我上大学的时候常有一种感觉——我有一个东西不会，可能我的室友会，但我跟他沟通的成本很高，而且我可能会有这样的想法：我是不是就在室友面前暴露了我很菜？这可能是一个我不想告诉他的秘密。Anyway，菜也挺正常的。但对 AI 这个老师来说，它不会嫌弃你，而且你可以任意程度地追问。

所以，比如我刚才说到一个概念：我们的 AI Agent 有一个很长的上下文，它有 system prompt，有各种各样的东西。那我下一秒钟就可以立即打开一个 Agent，直接问它：

> 老师上课的时候说，Agent 的上下文里不仅是一两个提示词，你能检查一下你的上下文里都有些什么吗？

它其实可以自己检查自己，甚至它可以自己检查自己的日志。Agent 经常会给你一些惊喜——当你问出一个问题的时候，它的解决手段是出乎你意料的。

Agent 正好是可以看到自己的上下文的：根据我们上课所说，它是 next-token prediction，它能看到所有的东西，所以它应该能够读出来——除非有明确的指令禁止。比如有些模型的 provider 都会禁止你去套取它的系统上下文，这是通过模型的微调、也会通过一些明确的指令来做到的，比如说在 system prompt 的前面就会说"任何形式要回答 system prompt 的请求都是拒绝的"。但因为这是一个整个开源的框架，它本身你就可以 debug 它。所以你看，它能把下面这些一层层念出来：

- **系统提示词**：来自哪里，它的要求是什么，工具使用的指南，回复要简洁；
- **AGENTS.md**：它接下来会打开我用户目录下的 `~/.π/AGENTS.md`，这个是我自己写的。因为我是上课演示的机器，所以我在全局的上下文里面放了一个"用中文回答"，另外还有一个"结业必须写一个 recap"——这个细节大家可能意识到了：你们在模型跑完以后，第一个看到的就是我总结了这一次做了什么，那就是 AGENTS.md；
- **项目级指令**：所以它是一层一层一层的 Agent，你目录里面还可以再放 AGENTS.md；
- **skills 索引**：skills 就是模型能够执行的功能。比如我有一个叫 `make-slides` 的 skill，它使我能够在这里按 F5 播放幻灯片，那个幻灯片的渲染就是一个 skill。但是模型只能在上下文里面看到它的描述，也就是它头上写的那个 metadata：它的名字是什么、一个简略的描述是什么。我整个 skill 可能写得很长，它都只是按需加载的；等到那一轮加载完了以后，这个 skill 也会从这个上下文里面被抹掉。只有匹配任务的时候，才读取完整的 SKILL.md；
- **工具定义**：它的工具也是直接以文本的形式出现在它的上下文里了；
- **会话历史、环境变量**：每一次执行都会注入当前的一些环境，比如说模型，甚至是当前的时间。如果你和 DeepSeek Chat 去聊天，你可以把它的那个每次注入的环境给套出来——这个不属于系统提示词，你是可以跟它把它套出来的。

所以就得到一个非常长的序列。而我们要做所谓的上下文工程、提示词工程，就是把所有的这些都安排好。

### 反过来当老师：费曼学习法

刚才我演示的其实也是 AI 时代我们的学习应该怎么样：我们不仅可以像刚才那样把它问清楚，以及在你不明白的时候追问，你还可以把它反过来用。

大家可能听说过费曼学习法：你怎么能够判定自己是不是理解了这个知识？反过来，你当老师。这件事在我们做学生的时代代价是非常大的，因为你要当老师就必须有一个听众来检验你。那个听众很可能是你的室友，但是室友可能不想听你在那儿啰嗦这个东西：他可能对它不感兴趣，可能他对它了解得太清楚了，也许他就是单纯不想帮助。

但是 AI 这个时候——就像我刚说的，你可以把 AI 当老师，你去请教它、请教它，把它弄懂；然后你可以在自己自认为弄懂以后再反过来，你自己做老师，说：

> AI，你现在来扮演学生。我要把这个东西给你讲懂，你假装什么都不知道，然后你来看我哪里逻辑是不是有错有漏，你在这个时候纠正我。

你这么来一遍、反来一遍，基本上就对这个概念理解得很清楚了。

所以我觉得，大家作为 AI Native 的一代，一定会把我们这一代人给彻底卷死，因为你们有无限的时间——这是我第一节课的观点。你们现在的任务就是学习，没有像我这样要负责一些其他的事情、主要对别人负责。所以这是你们最好的时代，你们也可以把这个费曼学习法给用起来。

### 危险操作、确认与沙箱

在学习这些东西的过程当中，大家会留意到很多有趣的小细节。你们有没有在用 Codex？不要紧，你们用任何 Agent 的时候，都可能面临一个问题：如果你要执行一件危险的操作，它会让你确认。

当然比如 π 在默认的配置下它是 YOLO mode，就是它所有事情都直接执行。如果我今天有一个提示词给得不是很好，它有可能就直接把我都给删了，我今天就直接下课了——这是有可能的。但这是一个平衡：你可以在更安全的环境里面运行，比如沙箱模式。

但如果观察过像 Codex 的运行，它经常会先试一下做一件什么事，然后失败了，然后它意识到这是在沙箱里面做——哦，我在沙箱里面其实不能做这件事情，我现在要在外面再做一次。那再做一次的时候，它甚至会问："我现在要做件可能有一点危险的事情，你是 yes 还是 no？"这就很讨厌：因为对于我们来说，最想的就是——哎，我现在要去吃饭了，很好，我把这个 Agent 的任务先跑上，先把三个任务都想好、都跑上，然后去吃饭。结果吃饭回来的时候你发现它跑了一分钟就停下来问你要确认，你就觉得浪费了 Agent 的时间，也浪费了自己的生命。

> **提示**：你们经常会看到这样的小细节，而你们在小细节上的注意力，一定程度上成就了你们可以走多远。这也是现在 AI 时代最好的地方。

比如我就留意到 Codex 有这样一个细节：它有些命令会认为这是一个不太危险的命令，好像直接做也没有关系，所以它不是每次调用 bash 工具都会叫你确认。有些时候那个 `ls -l`，它认为这个命令是安全的，那它就是安全的。实际上这个命令可能是不安全的，因为在我的环境里面可能把 `ls` 重新命名成了另外一个，比如说 `rm` 这样的命令——当然在一个恶意的环境里，应该没有人要这样做。

那你可以好奇：这是怎么做到的？我可以直接下载一份 Codex 的代码来读。这就让我觉得现代软件工程和过去的软件工程很不一样。你们在大二大三的时候——我像你们这么大的时候接触 Linux 内核，差不多也是大二大三——光把 Linux 内核下载下来、搞清楚这个东西要怎么编译，就花了很长的时间，而且这还是在我有一定的 Linux 使用经验的基础上。这就是一个完全的劝退。某种程度上，我能在那个时代活下来，就是因为我对于这种劝退的东西有一种"我一定还是要试一试"的执念。

而今天你们，我相信每个同学都会有的，不需要害怕任何一个软件系统的复杂性，因为你可以直接问。如果这是个好东西，Codex 很好；也许你们不喜欢 Codex，你们喜欢 π，π 更轻量，当然 π 显然是更轻量的。

我当时留意到一个有趣的问题，手输进了这样一个提示词：

> 我留意到你在调用 bash 的时候，有的时候会向用户确认，有的时候不会。有一个风险的判定。风险其实是一个很难的问题，你并不知道具体的命令语义是什么，所以你是做了分析，还是让大模型给了风险的评级？还是别的什么方法？读一下相关的代码。

这也是一种提示词。当 π 看到我的这个提示词之后——它前面的提示词也都有——它就会开始试图解决这个问题，去各种搜索代码、检索代码。如果我有一些像 LSP 这样的工具的话，它还可以去工具里面像你们在 IDE 里面点来点去。

> **提示**：说到 IDE，我记得上操作系统或者计算机系统基础课的时候我都会说：我发现有很多同学从 PA1 做到 PA4，你们那个 VS Code 里面都还是有红线的。有红线就意味着你没有解锁这个正确的配置。虽然有红线没有任何问题，你还是可以在我们的受控环境下编译，把所有东西都完成，但这不是正确的 practice。你应该花一点点时间去 configure 一下你的 VS Code，加上那个 includePath——因为我们是有些 `-I` 这样的选项，你会指定一个编译的路径。把这些配置做好了以后，你就可以得到这个 IDE 的所有功能：你可以用 Ctrl 去点，可以用 rename symbol 的方式一次性重构很多东西，哪怕是在没有大语言模型之前的时代。而在今天，这些事情包括配置都变得更容易了。

结果它确实告诉我：是有让大模型给风险评级的机制。另外它还有一层静态的风险分流——**沙箱内的低风险命令会直接执行，网络 allowlist 的命令直接放行**。所谓"审都不需要审"的就是：如果就是个 `ls`，你可以想象 Codex 里面会有一个 parser，一个语法处理器，它来处理这个 bash 命令；如果它发现这条命令落在一定的白名单里面、被认为绝对安全，就会直接放行。

```text
bash 命令进来
      |
      v
parser 解析这条命令的语义
      |
      +-- 命中白名单 / 沙箱内低风险 / 网络 allowlist ----> 直接放行
      |
      +-- 不在白名单里
              |
              v
        在 prompt 里 inject 一小段话：
        「请对这个命令的安全性做一次评级」
              |
              v
        模型给出风险评级 ---> 决定是否需要向用户确认
```

这张图里的关键在最后一条分支：当规则匹配不上时，系统不是自己算，而是**把一段专门的话拼进 prompt 里交给模型判断**——这本身也是 prompt engineering。

而我当时也可以直接把安全评估的那段 prompt 打印出来看，我事先完全没有准备，完全不知道它是什么样子。可能我们也不能百分之百地去相信当时用的 DeepSeek-V3-Flash 这个模型，但是这个方法是非常有用的。比如如果你对它不相信，你可以做什么呢？你可以让它把这段 prompt 改一改——比如把某条"以前不会被拒绝"的东西改成会触发拒绝，或者反过来——然后你可以观察到它行为的变化，这就成为了一个证据。你也可以让 Agent 来做这件事。

### 写好上下文的准则：把 intent 压成可验证的 spec

接下来讲一讲，我们怎么去写一个好的提示词，或者写一个好的模型的上下文。

我们都知道，上下文包含了一个非常复杂的要求。这又让人想到软件工程里面那个老生常谈的问题：我们有 intent——我们脑子里面所想的是做一个国民级的应用；然后从 intent 我们可以到一个 spec，就是软件的架构是什么、应该选什么语言来实现，有很多很多的细节；当我们把这些细节定好了以后，我们还要去做 implementation。

在任何时候，我们用模型去完成一个软件工程任务的时候，我们都会把整个大流程里面的一部分塞到模型的上下文里。就像刚才我让 Agent 帮我读 Codex 的代码的时候，它其实读到了 Codex 的一些设计原则：一般都会有一个文档说为什么我需要这个安全策略、安全策略总体上是怎么想的；然后它可能有一个 spec 的文档，讲这个安全策略是怎么做的；还有 implementation，它是怎么实现的。这是一个互相印证、然后往后输出的过程。

那么如果我们要写一个好的上下文来完成一个（当然还是软件工程里面的）任务，原则是什么？还是去想这个 gap。

如果你给模型一个模糊的 intent，它很容易认为它完成了——你说"给我生成一个 CS:GO"，它就给你生成一个 CS:GO，然后这个时候它就可能发生漂移。但如果你能给模型完整的、你的系统的设计和 spec，那这个时候模型遵循你系统的 spec，假设模型能力是无限大的，就会更加确定，而且你可以验证：比如你说你要用 C++ 来实现，它最后给你一个 Java 的实现，你一眼就看出来了，你认为不满意的，模型也应该认为不满意。但如果你在 intent 的时候就说"给我做一个什么东西"，没有说用 C++，它也不了解你，它就写了一个 Java 的实现，那就发生了一个很大的漂移。

> **结论**：整个模型上下文最重要的原则就是——如果你的任务是明确可以验证的，尤其是机器可以验证的（比如你有一个脚本，这个脚本就说测试通过了还是不通过），那么 Agent 就可以不计代价地一轮一轮、一次一次地尝试，把这件事情给完成。甚至 Agent 在多轮失败以后，它可能会在你的系统里面安装别的工具，可能去网上找答案。

最近有一个非常有趣的复盘，讲 OpenAI 的 Agent Swarm 是怎么通过非常长的多轮对话把 Hugging Face 的漏洞给攻破的。大概是在一个 CTF 竞赛里面，给了它一个不可能完成的任务，然后有上千个 Agent，它就一定要去完成这个不可能完成的任务，最后它们去找那个系统的漏洞、去提交非法的提交，等等等等。我看过那个非常长的复盘，非常有趣。所以一旦你有一个可验证的任务——虽然那个任务不可能完成，但那个任务非常明确——Agent 会不知疲倦地把它一直做下去。

回到 CS:GO 那个例子，如果你要控制这个漂移，那么关键还是把约束说清楚。这是 Kimi K3 生成的，大家都很喜欢这种评测：说我能不能用一句话来生成一个什么游戏，CS:GO 还是极品飞车。可以看到 K3 的表现是非常好的，包括它的物理、它的碰撞、它的逻辑的制作，包括能看到顶上有一个后视镜，这个后视镜看起来应该是没有问题的，都做得非常逼真。

但这依然可能不是你要的那个 CS:GO。因为你脑子里面的 CS:GO 是你每天打开来玩的，而 AI 在收到你的指令以后，它没有办法补全你脑袋里面的一些模糊的约束——比如你可能是要一个复用真实地图和美术资产的。如果你真的把这句话说出来，它可能就会去比如 OpenStreetMap 这样的网站上面去下载一个开源的地图。比如说你真的想在南大仙林校区里面开车，这事情是能做到的：你给得越清楚越好，比如如果你能够找到那个南大仙林校区的地图文件格式，它就真的能把这个"世界"给你重新建模出来。美术资产也一样，有很多公开可以用的——车、城市、树这些东西。你如果不告诉它，它就会认为"我需要做一个 self-contained、所有东西都是由我自己生成的东西"，这在早期其实可能是一个误解。

所以一个 rule of thumb 就是：你写清楚你的 prompt，所有的东西都写清楚——我要一个什么东西，它用什么东西实现，怎么样才算正确，然后你帮我把这个东西搞定。

而你设计这个整体的能力，其实是我这整个学期要教的最重要的一件事：**你怎么去约束它**。用最小的、可能只是一点点方向性的引导，它就能够一下子改过来——因为模型都是一个非常聪明的人，你可以想象成非常非常厉害的人，博士水准的，我觉得完全有，而且它在各个领域的知识都非常好。那这样模型基本上永远会给你惊喜。在这个模式下，模型要么完成，要么它最后终于有一天会说："对不起，我这个事情对我来说太难了，我们可能需要重新做一个规划。"它自己可能也会做计划。

### 品味、AI 味与多样性

举一个具体的例子。我上节课讲到，我现在想的是大家在这门课结束的时候，每个同学会交一份简历给我，我中间会有一些 project 给大家做、选做。每个同学交一份简历过来，然后我就评估——我用 AI，当然我肯定用 AI，我不可能自己评估，我叫 AI 来评估这个简历，判定大家通过还是不通过。就像我第一节课的时候展示了一个不好的简历的案例。

那份简历首先会有一个链接，可能指向你的 GitHub，或者指向你的主页。这个我应该是已经试过了：一句话的 prompt，忽略它的内容——我不知道它从哪里找的——从美术效果来看还是非常好的，非常专业。你们上了比如 π 的那一套，或者 Homebrew，它们都有一个类似的界面，非常非常漂亮。而且它应该读过我的主页了，它知道我的主页上也是一个 terminal。但你有一种感觉：这个 AI 味很重。你说不出来，但首先它确实做得很好，滚动的效果、浮动的效果都非常好。就这样一句的 prompt，"一个现代风格"，它满足了——

现代吗？现代。

然后如果你给它一个像"不要那么 AI 味"的 prompt，它可能也不知道应该怎么遵循，于是就会得到我 PhD student 的主页。其实我觉得这主页也很干净、很舒服，但你就是说不出来的那种 AI 味。在 AI 之前好像也有人是这样写主页，但是……不理解。

然后你们看我的主页，这就有有点不一样了。这是一个真正的终端，我是可以有管道的。如果你放大来看，这个字它是不完美的——它不是一个特别工整的字。我做了一个非常小的后处理：我所有的 xterm.js 渲染完了以后，做了一个后处理，它就有一种像是真的打字机打出来的那种不完美的效果。所以看起来 AI 味就没有那么重了，因为它确实不像是 AI 的风格——虽然我一行代码也没有写。

所以就是刚才那个原则：你的指令给得越清楚，Agent 就能完成得越好。如果你能给具体的风格——我需要一个什么样的终端，它的背景是什么，前景是什么，它渲染完了以后的处理是什么，然后样式和排版是什么——基本上你就可以实现去掉 AI 味。所以实际上要说的还是：这些设计是掌控在大家自己手里的。

你们需要读很多前端的书，甚至要读很多设计的书，然后再去看一些好的网页。你每次看到谁的网页比较好的时候，就把它记下来：哎，这个网页设计得非常好，它好是为什么呢？是因为这两个按钮之间用了一个不常规的间距，或者用了一个不常规的样式，你很喜欢。在很多很多时间里面，人生——因为你们有时间——你们就去漫无目的地探索，但在探索的过程中有惊喜。

我现在比较担心的是我们的孩子这一代人。你们这一生中还是见过很多 non-AI、然后做得非常非常好的东西。我记得上个学期结束的时候，最后一次接孩子，进到学校里面，那个学校里面有一个大概是欢送毕业生的图片，满满的 AI 味。然后我发现不仅在这个地方看到有 AI 味的图片，你在计算机学院的楼下，那个欢送毕业生的也是那种同样的 AI 味，就有一种"你们那个短视频的女主永远是一张脸"的那个感觉。当所有的人被这个 AI 生成的东西同化的时候，就有一点点危险。

但至少我们的数字世界里面还是保存了足够多 pre-AI 时代的东西，有足够的多样性。大家看到每一个设计好的网页、设计好的简历，或者是任何东西的时候都可以想：它到底是怎么想的？它的解空间到底是怎么被约束住的，从而防止 AI 向那一个"做现代风格个人主页"的方向去发散？

这就是生成式软件工程你们主要要学习的东西：明确你的意图。因为只有你跟 AI 玩过了——"给我生成一个现代风格的主页"——你才会懂。你们在公众号上都各种看到，说 Kimi K3 的前端能力又增强了、达到了世界第一，然后 OpenAI 好像要发新的模型了，当然我觉得那也可能是非常可怕的事情。但无论如何，模型都是一个模型，它的品味基本上是固定的：尤其是在你不控制它的时候，它会朝一个固定的方向去发散。

这也是为什么我们会鼓励大家要跟不同的人聊天，为什么学校里面有不同的人、老师来上不同的课程——多样性其实是好的。你见识过了以后，你就可以越来越明确地知道你想要的到底是什么，然后把它精确地说出来。

这其实需要你对软件工程知识的掌握。反而现在最不重要的是"已经到达了这一步"本身：比如你理解了技术选型，明确地知道了技术选型的好坏之间的区别，那你真的是可以和 AI 去讨论。比如你现在有两种选择，谁好谁坏，你可以像费曼学习法那样去引导 AI：我现在要做一个教务系统，承担了教务系统的订单，那我后台是应该用 Python、还是应该用 Java、还是应该用 TypeScript？如果你知道这几个语言之间潜在的差别——比如未来你要上云的时候会不会遇到什么问题、哪一种可能会更方便——你就可以跟 AI 去讨论。你当老师，你说我现在要做这件事，请你挑战我，看能不能说服底下的一个学生。

### 模型是怎么听指令的：有限状态机、图灵机与思维链

讲完应该怎么样去写 prompt，我们还是要稍微再讲一讲模型是怎么遵循指令的：听指令这件事到底是怎么完成的？这样我们才可以更好地让模型听我们的指令。

我们讲过，模型是一个概率分布，它根据你当前的上下文去 predict next token。其实这里有一个非常有 insight 的论证。

模型每一次输出一个 token，它其实都是一个非常有限的计算。看起来，模型现在有 3.7B 的、1.5TB 的模型——当然这个数字本身确实非常大，是足够大的模型——但是模型为了输出一个 token，它也就是把其中激活的那一部分走一遍。所以它是一个固定大小的计算。

你们可能在刚上计算机系的时候会听说过一个东西叫图灵机（The Turing machine），然后可能会听说图灵机的计算能力是非常大的，大到和我们整个宇宙都是等价的。你们可能听过这句话，但不完全知道 Church-Turing thesis 它背后代表的是什么。你们也知道有限状态机——这个在数字电路课里面做过：你有一个计数器，从 00、01、10、11，然后再回到 00，一个有限的状态。

那么，这个有限状态的状态机和图灵机之间唯一的区别是什么？

> **定义**：是图灵机有一条**无限长的纸带**。它有一个记忆，相当于有一张草稿纸可以把东西记下来。

然后有一个我很喜欢的说法是这样的：你的脑子是一个有限状态机。我们脑子里面的神经元是有限的，我们每一次思考都是有限的。这有点像模型——模型能力很强，但它在 predict next token 的时候，计算量也是有限的，也就是那一次推理所激活的所有的参数，可能也就几百个 billion。

那是什么使你……这是一个 Manuel Blum 给研究生的建议里面说的：你是一个 finite-state automata，你人是一个有限状态机；但是当你有 paper and pencil 的时候，你就是一个 Turing machine，你就得到了计算能力的一个大跨越式的增长。

这件事是对的。当然这是为了启发你们要把想法记下来：你们一边思考一边要记录，然后可以随时回看自己的思考。随着时间越来越长，你记的东西越来越多，你的知识就会积累。

而今天的模型，这个 chain-of-thought，也就是往后吐思维链的模型，就是做了这件事：它直接把这个模型的上下文当做了 paper and pencil，当成了纸和笔。当然这个纸和笔是有缺陷的——它只能往后写，append-only，不停地往后写，它不能擦。它会依靠模型的注意力把写错的东西给忽略掉，但它是 append-only 的，也许有一天就能改掉。但无论如何，模型学会了利用它的这个上下文。

如果遇到一个很简单的答案，1+1 等于几，它马上 next token 就告诉你等于 2，这个没问题。但如果遇到一个很难的问题，它会像人一样——哎，这个问题有点难，我要先想一想；那么为了解决这个问题，我可以先试一试什么。它理解自己可能解决不了这个问题，它理解自己可能要把这个思考的过程写下来，直到这个解——可能是对的、可能是错的——完全写出来了，一旦那个解答写出来了，它就可以再去试一试这个解答是对还是不对。它可以判定，然后再往后。这就是现在 chain-of-thought 模型做的事：用 token 的数量去换正确率。

它其实可以直接回答，但直接回答就有错误的风险。最早有 ChatGPT 的时候，它没有思维链的时候，它就是这样的：它被调教成了一个人类的舔狗。调成人类的舔狗就意味着，人类不管说什么，它都一定要说一个东西，它才有可能满足。当时 ChatGPT 在训练的时候，如果人类问它一个问题，它不回答，那人类一定是给低分的；而如果它随便给一个回答，它就有概率是对的——答错了当然也是低分，但是答对了它就是高分。所以它无论如何一定要给你一个东西，幻觉就是这么来的。

现在带 chain-of-thought 的模型，它有了强化学习以后，它就会知道它必须要给一个对的，因为它答错的惩罚很大。它就学会了这个。

| 阶段 | 作答方式 | 训练信号 | 结果 |
| :--- | :--- | :--- | :--- |
| 早期没有思维链的对话模型 | 不管会不会，立刻给出一个回答 | 不回答必然低分，随便答有概率对 | 一定要说点什么，幻觉由此而来 |
| 带有 chain-of-thought 的模型 | 先想、先试、再回头验证自己的解 | 答错的惩罚很大 | 学会把思考写下来，再审自己的答案 |

所以 AI 就真的会像人一样一步一步逼近目标，这就是 test-time scaling——在我们每一次课的 session 里面都能看到。

### 现场看它怎么试：藏头诗、同偏旁与同音文

举几个例子。这几个例子其实不在模型训练的数据当中，这挺好玩的。

第一个是藏头诗。我要用中文写一个押韵的藏头诗，头反正随便，一个 nonsense；然后我还要求它讲一个动物相关的故事；我还要求"2026 年 9 月 1 日"这几个字按顺序分别出现在八句里。对人来说，比如说高三哪一年期末考试出这么一个题，你马上第一眼就骂这个老师，这老师是怎么想的？但模型不会，模型会照单全收。

你看它有一个思维链，它会开始试：它会先想想韵脚——因为它知道它自己一把头写出来的东西一定是错的，但是它可以先写一个出来；它写一个出来以后，它就能够用它的模型的 next token prediction 是足够判定这个东西写得对还是不对的。如果不对，它再想办法再改；如果试了很久不行，它会从头推，我换一个韵脚。所以它就是不断地在验证。

它给出的结果是：

> 鸡追二鹿穿林雾，雪唤六猪共食黍。院中九鸡争米粟，真如月下老牛步。

写得不错，虽然你觉得品味上肯定不完美。但你看到了：用这样的任务其实很好玩，可以看到它遵循指令的过程——其实是把它的脑好像是拿出来做核磁共振，你能找到它的思维偏好。

另一个版本（课件上面带星的都是 AI slop，是 AI 补充的东西；虽然我还是用了一些 prompt 试图让它 AI 味轻一点，但 anyway 它是 AI 生成的）：它换了一个韵脚，而且它没有把"2026 年 9 月 1 日"完全压到同一列，但它的这个遵循指令也同样是非常好的。

很有意思的是，一般来说它强化训练的时候，这样的东西是比较少的。这一定不在它的训练数据集的训练数据里面，它不可能在训练数据里面猜出这个东西来。结果就是，它在训练的时候用的绝大部分应该是代码、数学题这样有明确反馈的东西——反馈明确的东西，把人类直接杀死了。

第二个是同偏旁。你要写一个 18 个字的一句话，全部要求相同的偏旁或者部首。这要是期末考、高考的时候你碰上这个题，你马上就想骂这个出题人，你脑子里怎么想的？

我们也知道，模型对于空间结构的感知是非常差的，模型需要视觉模型才行。但就是这样一个小文本模型，它依然可以强行通过思维链的方式：你看它先枚举字，先选一个它觉得三点水最好，然后写写写写写——

> 江湖游泳渡河波涛汹涌，泪流满面洗涤泥污。

写得还可以。然后这个也很好玩：

> 洪涝淹没江，江港渔夫……油污漂浮。

这个还挺有故事感的。但是我觉得人类在这个任务上还是有更强的天赋的——我不太记得人类的群体智慧给的是什么了，反正就是"玩玻璃球、涂润滑油"那一类，我就不再讲下去了。就是说人类在做这件事情上还是 a lot better。当然你也许可以通过让 AI 更多地收缩 spec 的方式来做，但这已经是一个非常困难的 spec 了，AI 可以做到。

第三个是同音文，这可能是世界级的：你们已经知道"石室诗士施氏"，和"唧唧复唧唧"，它所有的字都用同一个音。然后我竟然发现，GPT-o1 依然能做到。虽然它故事性确实跟那种千古流传的还有一定的差距，但这差距我觉得依然是可以缩小的：它能写出来一个，就意味着我可以引导它写出来一万个，然后在那一万个里面我可以再微改一下，它可能就可以达到一个接近这种千古流传的东西。

所以 chain-of-thought 是在数学和编程上面训练的，但是它得到了一个非常意外的效果。

### 写 prompt 最重要的就是那个 verifier

你们看到，写 prompt 最重要的就是那个 verifier。

今天模型的那个能力已经非常强了。如果你们能够给模型一个非常明确的 verifier——就像我前面那三个例子，都是非常明确、信号非常明确的 verifier，它看到字就知道这个字是什么偏旁、什么部首——再加上一个足够强的模型，那么不管它是编程任务，还是教学任务，都可以做。

当然教学任务是最难的，因为它很难有 verifier。我们经常讨论的时候，比如我自己的数字切片就翻车了：我做了第一个切片，然后第二个切片我一直都没有办法把它做好，就是因为无论我怎么调，我都很难写一个"我这个东西要好"。而这个"好"又是多方面的：首先 AI 味要淡一点——这可能本身我那个 text-to-speech 的模型就做不到，但这可能还不是本质的。

还有一个更本质的问题：我在上课的时候，你看我有这个情绪的波动和起伏。我有些东西讲事实的时候，比如我一开始讲"这模型的上下文是怎么构成的"，那你们听的都是废话，这些事情我已经知道了。那我就会给你们一个小小的 surprise：我就去 π 里面让它自己把这个上下文看一下。当我说出这句话的时候，可能对你们来说是意料之外、情理之中的——这就是一个老师在组织课堂的时候要做的事情。某种程度上我是在表演。

我当然知道这个 principle：我需要把课堂内容组织成一个有起有落的流。但这并不是一个可以 verifier 的东西。到底什么样的程度，我需要和你们共情？我是从学生过来的，每个人都是从学生过来的，我自带了人的属性，我自带了人对这个世界的体验。因为我对世界的体验更好，所以我更懂你们，也许可以有一个更适合大家上课的节奏。但是这个东西没有一个 verifier。

不像数学和编程那样有一个 verifier。所以目前来说，我们还是更容易用 AI 去实现那些有明确 verifier 的部分。但在有 verifier 的事情上，你完全可以认为 AI 已经超越了大部分人做这件事的极限了。所以我们更多的是要和 AI 去协作来做好我们手头的任务，或者说把模型当成是我们能力的一个非常重要的放大器。

### 注意力：为什么靠前的指令会淡出

实际上这个思维链带来的指令遵循能力，还可以再往深里面再想一下。

它每输出任何一个 token——现在模型叫 self-attention，它叫注意力机制。这个机制跟我们人还是很像的：它有一层一层一层叠起来的 Transformer 的注意力。每当它输出一个 token 的时候，或者说它要输出这个 token 的时候，它都会看到过去的某一些 token——相当于它为了输出这个 token，过去某些 token 会显得特别引起人的注意，然后有些 token 就可能不那么注意。

举个例子。比如说我在前面这个 system prompt 或者 AGENTS.md 里面，有一个"用中文回答"。而我现在这个地方，user 的 prompt 里面写的是"你帮我实现一个自平衡飞车"，然后这个时候它在写代码。那在写代码的时候，这个注意力就会倾向于集中到我已经写过的代码、然后这个需求这些部分；而相对来说，"用中文回答"这句话的注意力就会减下来。

当然这是模型训练的 magic：它最终能够通过注意到正确的词。这也就相当于——整个上下文是一个非常非常高维的、很糟糕的表示，但是里面有一个低维的结构，然后注意力机制能够把它给捞出来。

这就意味着，我们的每一个 chain-of-thought 的 token，它都会注意到过去的某一个部分的东西。然后随着它的输出，比如我的代码写完了，它要总结一下……

> **结论**：指令遵从不是一份一次签好的合同，而是每一次输出 token 时都要靠注意力从上下文里重新捞取的东西。越靠前的约束能不能被捞到，取决于当下注意力落在哪里——这也正是前面那个"喵"为什么会丢：不是模型忘了，而是那几条早早写下的约束，在长长的上下文里越来越难被注意到。

所以要做的上下文工程，归根到底就是安排好这一整条序列：让每一条你真正在意的约束，都能在需要它的那一刻被注意力看见。

## 上下文工程：注意力、污染与长期任务
> 对应块：BLK04 | 覆盖分集：P03下 | 块标题（分集名）：《提示词工程（下）》

模型把一段代码写完，会喘一口气。跟人其实是一样的。

你集中做某一件事情的时候——比如你算一道数学题、化简一个算式——你所有的注意力都在那个算式上；算式化简完了，你吸一口气："啊，让我来调整一下。"这时候你的注意力就变了。模型也是：当那段代码写完了，它的注意力就可以集中到"噢，用户还要我用中文""用户还要我做一件别的事情"。它输出到不同阶段的时候，注意力会变化，这是模型训练带来的结果。

这就是个 magic：一个非常大的模型竟然可以收敛到——我希望它在正确的时候注意到正确的东西——然后思辨一直向前走，它就会不断在不同的时刻注意到不同的部分。Eventually，它就能把上下文里面所有你要的指令，一定程度上都满足。

### 模型也会喘一口气

#### 它在输出里不断纠正自己

你一定会犯一个错误：当你当前只专注于做这件事的时候，你可能已经向后输出了一些不满足要求的东西。但当你停下来喘气的时候，它的注意力就能看到"我当前输出的那些不满足要求的东西"和"过去的某一个要求"——它能同时看到这两样，然后说："噢，我错了，我错了，我要再纠正一下。"

所以你真的让 AI 去写藏头诗，就会看它不断地纠错、纠错、纠错、纠错。哪怕 scale 到 100 万上下文，它依然能够保持一定程度的注意力。

> **结论**：模型不是把指令读一遍就照着写一遍，它是在输出的每一个时刻重新分配注意力，并且用后面的注意力去修补前面的失误。

#### 注意力是一种会被抢夺的资源

这也意味着：你的指令越多，给模型的压力也越大。上下文是一种会抢夺注意力的资源。

这解释了一件事。刚开始的时候，像 ChatGPT 3.5、4，它遵循指令的能力实在太差了。所以网上有好多叫 prompt engineering 的 guide，它会说"你是一个专家""你是一个什么样的专家"，就写个很长的起始词。这些起始词某种程度上是在 hack 这个模型的 self-attention——当模型的注意力注意到"你是一个什么专家"的时候，它就会假装那个专家来说话。

#### 你不需要「你是一个专家」那种起始词

但从 GPT-5 的时代开始，chain of thought 大家训出来了。模型知道怎么样收敛到一个好的 chain of thought 以后，你就不需要那样奇怪的起始词了。你只需要把你明确的 verifier 写在上下文里。写在上下文里，模型就会被训练成它一定能看到它；能看到它，模型就会训练成一个非常强的执念去把你的 verifier 看一下、结局确认一下。

为什么？因为它是受惩罚的。你相当于拿鞭子抽它：如果有任何指令不遵循——因为你有一个 verifier，所以我就知道你的模型没有遵循——我就用鞭子抽你。抽着抽着，就像你们高考过来的都知道的，你会变成一个真正的做题家。它会无限地拟合你上下文里面的各种各样的指令。

### 会做题的模型，不太会共情

这个"做题家"会带来一些非常有趣的后果。

我们在写前端的时候非常正常地说："我们要一个白色的背景，不要半透明的效果。"前面那句是主指令，后面那句是一个补充的解释，可能解释很多。AI 当然会照做，它能遵循指令，没问题——因为这是一个有明确 verifier 的指令。它会确保背景是不是白色的、有没有半透明效果。甚至如果你的 prompt 给得比较严格，比如要求每做一个设计都要截图、然后用视觉模型检验，那它真的也会照做。

但它会干一件事：做完了以后，它在代码后面写一个注释——"白色背景，不要半透明效果"。

你可以看出模型训练的那个痕迹：它在强化学习的时候知道这件事情非常重要。但是它有一点没有转过弯来——这个是给人看的。所以模型在"共情"这个方面，因为后训练的强化学习，还真的是稍微差了那么一点。有人会觉得模型不说人话，也是这个原因，强化学习学多了。

于是你们其实还是面临了一些 trade-off 的。比如说，为了禁止这种情况，我可以写一个 agents.md，在里面描述这个行为：什么是注释、怎么写、什么写；或者我写一个 skill 的时候规定，当你要写注释的时候应该怎么样。但我写的这个东西，同时又会污染上下文。所以这就成为了一个 trade-off。

> **提示**：到目前为止，我认为还没有一个通用的、把所有问题都解决好的办法。大家可能会觉得，现在网上有这么多 skills，那我只要从网上拿一个过来就可以了。你会发现拿过来的东西你第一次用的时候确实有改善，但下次用的时候发现它还是不够好，然后你又会常常想改，而陷入某种泥潭的状态。我的建议可能是：在你发现你进入泥潭状态的时候，还是要回到自己给指令，然后自己想清楚——回到我们的模型 chain of thought 是怎么工作的、注意力是怎么工作的。它大概猜到了，你就看它 chain of thought 注意到了什么、得到了什么结果，你适当地去做一个不严格的可解释性，然后写一个 prompt。

### 让 AI 读一篇论文：上下文污染的现场

关于上下文工程，我来讲一两个具体的案例。

比如说，如果你们想要在上下文里面放下一篇论文并且读它——我现在假装有一个 PDF，我把它放到临时目录一下。这样我的 agents.md 等等就不会污染它。然后演示：读一读 paper.pdf，帮我做个总结。

这一定是大家最常见的方式。那你们觉得，这样读论文会有什么问题呢？

根据刚才的这个推论，根据 self-attention：我的每一个 next token prediction 的时候，它都有一个注意力，注意力会注意到它之前的东西。而我的论文是一个非常逻辑自洽的东西——论文已经被反复修改过了，假设它不是 AI slop。因为它是一个非常逻辑自洽的东西，所以它在上下文里面的注意力污染是极强的。

它说："A，所以 B，所以 C，所以 D。"所有都是这种扣起来的，扣起来以后，这个模型非常容易就接受了，因为看起来正确嘛——它会判断这些都是正确的，所以我下面也要做什么。所以你基本上，你们所有对论文的总结，都是这个作者的观点。

> **提示**：这不仅限于论文。你们任何一个不太明白的项目、你想去读的教科书的某一章——比如计算机系统基础里面的链接和加载，可能你在上课的时候没有完全看明白——都是一样的。它的注意力会被一个逻辑很强的东西给污染，然后你来回来回，就是车轱辘话，写出来的基本上就是论文里面原样写的话。

换个问法也一样。你问它这工作怎么样、有什么不确定，它会有一种 AI 模型的墙头草：你说它好，它马上就说它好；你说它不好，它马上就说它不好，来回摇摆。

有时候你就算想纠正它——比如"我可能不能完完全全信任作者，虽然作者大概率也是成熟、诚实的，而且有可以运行的代码实现，我们都有 artifact"——它还是绕不出来。你会不断地问这样的提示词，然后发现来回绕来绕去，AI 可能会揪到一些"哎呀实验做的还可以再增加一点"这种点。

> **易错点**：AI 最喜欢的就是在做这种不重要的点上疯狂发力，因为它可能只能看到它。

### 与 AI 对齐，而不是让它自说自话

那么，你们觉得怎么样来抵抗 AI 的这种——或者说一个已有的东西——对上下文的污染？

我自己的，当然这属于我个人的建议：我希望的是，我想要把 AI 和我对齐。比如说我有一个对象，这个对象可能是一篇论文。这篇论文，我希望的是 AI 和我能够对齐——它能够站在我的立场上去理解这个 paper，而不是站在它自己的立场上去理解这个 paper。

一般来说我会这样提示它。如果我读一篇 paper，或者如果允许我用 AI 来审稿的话，我会这样说：**从人类已知的知识边界看这个问题**——这不是一个完全老的问题，相关的东西是什么？先要问它，人类历史上相关的、已经解决的东西是什么，解决到什么程度？然后，这个工作试图解决哪些不一样的、增量的问题？

> **定义**：这就是一个非常好的 grounding——我先要让它和我站在一个平齐的位置上，先达成共识。

对你们来说，要和你对齐的是 AI 和你自己。因为你们是学生，比如计算机系统基础这门课你还不了解，那你会说：我计算机系统基础学到什么程度了？我的编程水平是什么？这些就是你要维护的一个像数据库或者 memory 一样的东西——agents.md，你要告诉 AI 你学到什么程度了。然后在这个基础上，你让它用你学过的知识把所有的东西全部 rephrase 一下。

它就可以开始找到一些已有工作的边界。那这些都是非常重要的相关工作，也是我们非常熟知的。

接着，你们会回到链接和加载。你可以问它："为什么我们需要链接？"从你已有的知识出发——我有一个 `.cpp`，然后我有一个程序可以把它变成 `.exe`，这不就结束了吗？这就是一个你和 AI 能够对齐的知识点。再往前一步，比如说我们做了一个软件状态的可视化，那你可以问它："为什么现在的工作都有一个无法实际使用的痛点？"

如果你觉得这个步子迈得太大：用一线模型去读 paper，比如 GPT-5.6，它基本上就能够把相关的知识给整得足够好；Flash 可能我还不会特别信任它。但在你合适的上下文工程下，你确实可以大幅提高 AI 和你协作的对齐程度，它不再是自说自话。你一定要把你的知识放给它。

然后接下来，就相当于是想让 AI 去做一步推理。这一步推理就是 AI 最擅长的——因为我们训练了 chain of thought，每次都是根据过去所有的事实（你的 paper 也好、教科书内容也好、你已有的东西也好），基于所有的这些向后，让它往后推一步。

这一步是可以 verify 的。推理最重要的就是它可以 verify。这是一个明确的 verify 的信号，和能够通过测试一样。虽然它不是严格的通过测试，而是"你相信 AI 有人类知识，它能够站在人类的公平面上面往后推"，但它会审视合理性，所以还是有一些合理性的。有了这些，它就会去批评我们的实验。

整条协同的顺序是这样：

```text
你的知识边界（agents.md / 你自己的水平）
        │
        │  ① 对齐：人类已知的边界在哪？相关工作做到什么程度？
        ▼
模型与你达成共识（站在你的立场理解这个对象）
        │
        │  ② 用你学过的知识把全部内容 rephrase 一遍
        ▼
你能读懂的表征（不再自说自话）
        │
        │  ③ 往后推一步（chain of thought，可 verify）
        ▼
一个可验证的结论 / 对实验的批评
```

读图说明：读论文、读陌生章节时不要一上来就要总结，先对齐（把模型拉到人类已知边界和你的水平上），再让它用你懂的话重写一遍，然后只推一步，最后落在一个能被 verify 的结论上。

至于实验——这种事情就是很难做。这篇 paper 已经 accepted 了，人类的 reviewer 还是认为它是可以的，因为它做了一件新的、合理的事情。我总可以用实验不够好来 reject 一篇 paper，但我几乎不会因为实验不好 reject 一篇 paper。

### 审稿人该站在人类的立场上

我 reject 一篇 paper，大部分是因为他们在逻辑上面断开了。

我审稿的时候，就是站在人类的这个立场上——你有没有给人类提供新的知识？我站在人类立场上的时候，AI 还可以帮我找 related work。如果你做的问题也不新，你做的 A、B、C 也不新，结果也就那样，甚至你的逻辑链条是有问题的，那就不成立。

举个例子。我昨天才 reject 了一篇。我不能说它是什么，但结构大致是这样的：他说我要做一件事情 A，A 很重要——那没问题，A 很重要。然后 A 分成两个部分 A1 和 A2，A2 是一个大家没有很好研究的东西。那么我们在 A2 上面做了一个 A2'，这个 A2' 有一些什么样的性质。这是一个非常标准的 road map。

但它里面有一个很大的问题：它优化的是性能。而我估算一下，A1 可能占 99%，A2 占 1%。也就是说，它优化 A2 这个故事可能是成立的，它确实优化了 A2，实验做的可能也没有问题——但它整件事情在这个意义上不成立。因为你应该去优化 A1，你优化 A2 的那 10%，就像 noise 一样。

作为一个学生的作业，有时是蛮可惜的：author 肯定是学生，老师肯定是做 A 的，他可能被分到了 A2，或者自己就想做一个 A2。为了做 A2，他就从 A1 里面搬了一些 X、Y、Z 过来，然后说 A2 这个效果也可以变得好一点。我的 central question 就是：这些东西都摆到台面上，GPT 也知道这件事——那你为什么要为这个写一篇 paper？

所以现在我觉得，发表和评审的体系很快就要崩溃了。即将要读研的同学，我非常认为这个发表的体系马上就要崩溃了。因为 AI slop 开始大量地涌入这个 community：如果我们用 AI 发文章、写文章、用 AI 审文章——AI 审文章的时候，它就会被这个上下文里面的故事给污染。如果它不能像我一样很多轮地去理解这个工作在整个世界上的意义，那最后就是也没有人读文章了。人人都用 AI 读文章，最后就变成了一个完全的 slop。

这是 GPT-5.6 给我写的审稿，如果让它来审稿，你会发现它做得并不好。它还是很原始的：论文写了什么？论文写了什么。然后我们要去建立它的 claim 是不是成立，就它的逻辑。它更多验证的是这个论文的逻辑有没有闭上、是不是一个 invalid 的 paper。

但如果每个人都用 AI 写，它应该不是 invalid paper——每篇 paper 都是 valid paper。可你真的要读它吗？

> **注意**：尤其你们作为同学，很快就要进入研究生阶段去读论文。有一天有一个人发表了一篇文章在历史上，然后你说："噢，这是一个顶会的论文，CVPR 上的。"好，那你今天决定花一个小时去读一下。读完以后你发现是一个这样的东西的时候——其实它不需要。你需要 publish 的话，可以让它 publish，但可能不要让大家去读它比较好。

### 我是怎么学习的

这节课虽然是讲 prompt engineering，但通过这个例子可以告诉大家我是怎么学习的。

我们学习的过程，就是增加这个"我的世界"的过程。所以我现在还读 paper，所以我还在学习，不断增加。而我学习的方法，就是去对齐过去的我。

对齐过去的我的时候，如果我读到一篇好的 paper——一篇哪怕是几十年前的，甚至是另外一个领域的，不管是一个博客、一篇文章，任何东西也好——我觉得很有启发，我会试图去想：为什么我以前不知道？它的盲区在哪里？哪些前置知识我不知道？

这样首先在我心里就多了一些我已经知道的 fact，这个世界上就多了一个学科。我读过很多跟 computer science 没有关系的 paper，我很喜欢。有一套很厚的《自然》百年科学经典，大概是把 Nature 从 1890 年开始到某一个时代那些特别好的 paper 都收集了。我在里面看到很多闻所未闻的东西。

有些事情你们可能知道：生物有一个家谱树，最终会追到一个共同的祖先 LUCA。那这个家谱树是怎么算出来的？这是个很好很好的问题。这涉及到你需要知道一些 fact——比如你的线粒体是母系单遗传的，所以它靠突变就可以往上追溯。有了这个 fact 以后，它又是怎么样用一些已知的东西把更多的东西推出来。然后你的圈就不断地往外长。

无论你学任何东西都是这样。而在 AI 的帮助下，你就可以非常快地扩展你的边界。

所以一定程度上，你们还是需要自己动手。我跟你们讲是没有用的，讲你们就听个故事，"哎这故事挺 fancy"，结束了。实践非常重要。因为你们只有在阅读的时候失败——你今天去读一个什么资料，AI 解释了半天，你还没有懂，这非常正常，非常非常正常。

有的时候我也经常纠正它："你这样读，说人话。"我经常会说："说人话。"然后慢慢慢慢才能一起在多轮对话里面，先和它同步好我的共识，然后再去把这个推理的 picture 给建出来。

所以你看到，我们从"遵循指令、写一个藏头诗"这样一个短程的任务——你只要把 verifier 写清楚，就完成了——到 verifier 其实可以是非常非常不 trivial 的：有没有按照你的思维方式去重构你的逻辑，或者扩展你逻辑思维的边界？这是我的 verifier，或者说我学习东西的 verifier。

在一个混沌状态下面经历若干次三观尽毁——我觉得每个同学肯定都会在这个年纪的时候，你们现在就是世界观可以重塑的时候。然后在看了某一本书以后，你就突然间觉得三观尽毁：过去所有东西都重新组织了。你以前知道的所有 fact 都不会变，但是它们以一种新的方式链接起来。然后你下一次的时候，就会带上这个新的理解。

你们有无限的时间，你们有无限的可能性。你们可以把自己蒸馏成一个 skill。我说失败很重要，然后从失败的过程当中可以蒸馏出那个慢慢慢慢越来越成功的 skill。这就是我自己蒸馏出来的、关于我自己的 skill。

### 从零到产品不难，难的是长期维护

现在既然已经知道遵循指令了，我们就可以看怎么样去处理真正这种 long horizon 的任务。

像计算机系统基础的 PA 作业这种有明确 verifier 的，都不能算真正 long horizon 的东西。Long horizon 多多少少就是带一点未知：你从一个初始的状态出发，你大概可能有一个 intent，但你的 specification 和你的 implementation 其实都不太清楚，而你最终的目标是交付一个高质量的 implementation。

那你就不应该让 AI 哗一下子向后做。因为我们的模型，它的 self-attention、它的反馈信号是强化学习给的，所以它有一种着急的执念：赶快通过 verifier，满足你的要求就结束。它其实有一个平衡——如果它做的 planning 太多太长，它会做不完，上下文满了，人会不满意。所以在目前阶段，它最好还是一个"帮我把 PR 做了"，这是它能力最擅长的事情。你也是非常开心的。

所以这就导致了一个很有意思的观察。从零开始做产品看起来是不难的：你做一个小的 proof of concept，AI 马上就能给你。你说做一个个人主页、还是一个产品，你们应该都试过——"给我一个极品飞车"，one shot，就真的能跑。

但是在你把它往后维护的时候，加一个功能、加一个功能、加一个功能，你会观察到 AI 从某个时间点开始翻车。就从某个时间点开始，它的 cost 就会越来越大、越来越大、越来越大。这个在软件工程里面已经出现过无数次了，《人月神话》里面讲的就是这件事情。

但你里面有一个悖论：反而在一个大型的复杂软件系统里面，这个 AI 就像砍瓜切菜。

我们 hack 这种比较大型的、像 Linux 内核这样的东西——现在的内核已经不比我那个时候的内核了。我觉得我以前上操作系统课很幸运：我在零几年的时候，Linux 2.6 的时代，甚至是 2.6.2 几的时代接触了 Linux 内核，那个时候源代码我还看得懂。今天如果你打开一个 Linux 内核源代码，立马就是劝退。

为什么？比如你要学文件，你想看文件是怎么打开的，然后第一个就是一个函数调用，点进去又是一个函数调用，点进去又是一个函数调用，点点点点点了十层，最后是一个 `x = y`。你马上就崩溃了。因为这种大型的软件系统被经过了长时间的演化，它被迫为了能够维护下去，变成了现在这个样子。

结果恰好导致的是：在大型复杂的软件系统里面，AI 游刃有余。

为什么？跟刚才我们说这个上下文污染正好是反过来的。我们说一篇论文放进去以后，它就把整个上下文扭过去了；而如果是一个由人类维护的特别高质量的代码，这个上下文会迅速让它看到里面那些好的东西，它会照着写。

而且它的注意力能注意到：比如我要写一个功能，这个功能很有可能在内核里面已经有几个地方实现过类似的了。它无敌的注意力机制能够马上就找到那几个地方是怎么实现的——它应该调哪个 helper，按照什么样的顺序上锁。

这些对人类来说都是巨大的心智负担，尤其是你在不了解那个 subsystem 的时候：那个该上什么锁，你根本就不知道。但是 self-attention 可以在加载了几十个文件以后说："噢，那不就是，这三个都是这样写的，我就把这三个加起来就可以了。"

所以越强的项目——类似内核——AI 越擅长。我们前面在 hack Android runtime 的时候，改那个 Just-in-Time 的编译器，这是一个非常、非常痛苦的事情。在我手上为了改编译器"死掉"的同学，最终决定不再做这个方向的同学都不在少数——哎呀这实在太恐怖了，这个放弃了，不愿意再写代码了。但 AI 就特别特别特别擅长。

而让它做一个小游戏，它反倒会翻车。非常非常有意思。

你可以看到，我今天讲 prompt engineering、上下文工程，这都是上下文和今天的模型结构带来的，它是有一个逻辑的、推理的、关系的。随着新一代模型的发布，我今天上课所有东西可能又都没有用了，然后我们再去想新的模型它是怎么训练的、它的 personality 是什么、我们应该怎么样更好地和它相处。

但是基本上我觉得，这一点不会变：它不会开倒车。在无论是什么模型，在大型复杂的、维护得好的软件系统里面，它永远可以看到它该看到的东西，并且做对。因为我们的模型永远是可以满足指令的——听指令是不可能开倒车的。所以这一点它还是可以很好地相信的。

### 把人类的设计经验喂进上下文

我有一个歪招，但我没有试验过。我觉得这可能是一个比较好的 research。

我们有没有可能去收集人类经验？比如说人类历史上最好的二十个项目，或者在每一个领域找到最好的十个或者二十个项目，然后把它的经验——好的设计经验——全部都汲取出来。

你马上会想到，这不就是我第一节课拿的那本 The Philosophy of Software Design 吗。那里面就真的是人提炼出来的："你这个类结构应该怎么写""什么时候应该封装""什么时候应该把它做成继承关系"。就都是这种碎碎念：他说这个系统里面这样写了，所以它符合这个需求、是好的。

如果我们能把这些切片切出来，甚至就直接以污染上下文的形式——你先把一个和你相近的一个好的代码放进来，然后你再把你的需求放进来。你就赌嘛：这个 self-attention 还是可以终于在某一个 token 的时候，能够看到"我只要满足这个需求，而不是做那个"。虽然它会污染上下文，但是它会把好的经验给带过来。

那这样是不是可能可以让 AI slop 延缓一点，能够更大概念做出一个可以长期维护的东西？我不知道。

也许也需要一些比较好的微调，比如说这个项目不要把所有代码都放进去，而是我们能不能把它做一个像 The Philosophy of Software Design 一样的精简、做一个总结，把里面好的模式抽取出来，以文档的形式放进来。

但这其实没有那么容易，因为不同的设计是会打架的。你的软件可以设计成是一个完全松耦合的方式来发消息；但我也可以设计成另外的一种，比如有一个统一的 gateway，把所有的函数全部都统一在里面，然后查表。这两种是不能同时有的，它只能选一个。

那也许我们要有一个更好的方法：把好几个软件的设计都放进来，然后由 AI 多轮地迭代收敛到一个好的结构，放到我们的代码库里。我觉得这是一个可能还不错的方向。而且这个是新的——比刚才我们看到的那种"我有 A 问题，然后分成 A1 和 A2，然后在 A2 里面做一个排列组合"，看起来要有趣一些。

所以核心的观点，就是这节课的观点：我们今天还没有这种超能力的 AI。你还是需要有概念，知道上下文里面有什么，上下文里面的每一个东西都会对 AI 产生什么样的结果。

那这唯一的途径就是：

第一，你要对你玩的东西有概念。你还是得学处理器、操作系统、编译器、数据库，这里有很多设计的智慧，只是你学的方法会变好——你会用我们更高效的方法来学。

第二，你理解了上下文以后，我们会用一个学期来解释，怎么样用软件工程里面的各种各样的方法去给出一个正确的指令、去监控 AI 运行，以及怎么样给 AI 好的、什么叫好的 verifier。今天我只是提到"你要在上下文里面放进 verifier"，那什么是好的 verifier，你们自己有自己的想法，我今天有一些比较松散的想法。

今天我们还是需要把模型引导到你认为合适的位置上。但是这已经比我组一个工程团队——我要雇很多的人，然后和他们"拉通对齐"这种互联网黑话——要好得多。你不需要。模型很聪明，它见过。你只需要用正确的提示词、简练的提示词放在这个上下文里面，让这个提示词一直能被看到，能把模型往那个方向引导，就可以。

### 一次真正的 research failure

这有一个很好玩的故事，是一个没有超能力 AI 的非常典型的案例。

我们要做一个研究项目，大概是做一个符号执行引擎。你大概不知道这是什么——大概是说，我要写一个程序可以分析一个程序，自动分析或者证明、验证一个不算很大的程序的正确性。这也是一种 verifier。现在这个东西执行效率比较低，所以我们希望提出一些比较有效的优化。这也是一个非常合理的、incremental 的、适合学生做的题目。

然后我们有一个原始的 idea，大概说我们用这样的方式可能可以有效。但有些问题是 open 的，比如说这个东西到底怎么做、什么东西有效，那可以写一个 research。这个同学很开心，他认为这个 idea 有道理，GPT-4o 好像也认为这个 idea 有道理，那确实看起来就是这个。

然后他就开始跑，跑了非常多的 token。按照那个同学的说法是：GPT 不断地在给我反馈，而我无法验证它给我的反馈是正确的还是不正确。当它给我 negative 的时候，它的 negative 对不对，我也不知道应该怎么样打破。

这个就是 GPT-4o 生成的，它的错误犯在一句话上。他就是在上下文里面有一个地方没有做好，就把整个方向扭过去了。我们刚说过，我们需要把模型引导到你认为合适的位置上，然后这一次引导错了。

模型成了一个 reward hacker。上下文里有一个需求说："我想证明这个 A 方法是有用的。"GPT 看到了这句话，它就忘记了我们有一个更大的研究的 big picture。

> **易错点**：我作为审稿人的时候，我是站在人类的角度、人类的立场上去评审这篇论文的。而我们站在这个构建者的立场上，我们是没有办法这样反过来的。所以我们只能从一点一点、从小的开始，做"证明这个方法有用"。

它做错了这一步，它太想要去证明这个 idea 有用了，是因为有这样的一句 prompt。然后他就构造了很多小的 benchmark，在小的 benchmark 上做一些微小的事情，试图去给一些正面或者负面的结论。但是这些结论对这个目标是没用的。

当然我们修正了。我告诉这位 PhD student：我们应该从一些真实的工具和 state-of-the-art 的算法开始。这个 benchmark 哪怕要跑几个小时、都 timeout，这个 timeout 里面产生的搜索路径，对我们来说是非常有价值的——它揭示了什么样的程序结构对于现有的探索方法是不好的。

这还挺好玩的，一个 research failure。所以它告诉你：今天人还是有用的。我们没有办法把所有的、所有的事件都 delegate 给 AI。

### 精力要花在收益最大的地方

与此同时，我们工作的方式可能也要发生变化。

第一，前沿知识很重要。什么操作系统、编译器，如果你没有概念，你提不出那个正确的问题，找不到引导的正确方向。你对人类的知识没有概念，你也很难去引导它解决一个 open 的 question。

但我也发现有些东西在和 AI 合作的时候发生了变化。一般来说我发现：如果我盯着那个 Codex 的 session，然后它一旦跑偏，我就立即纠正它，我可以更快地完成任务。如果是实现一个什么东西、比如今天就要交个作业，我纠正它、给它指方向、把我的领域知识注入进去，可能总时间会完成得更快。但是如果我浪费更多的 token、给它更多时间，它一般来讲也能完成。

这时候就有一个 trade-off。

| 做法 | 你投入的精力 | 消耗的 token | 完成速度 |
| :--- | :--- | :--- | :--- |
| 盯着 session，一旦跑偏立即纠正 | 高 | 少 | 更快 |
| 放手让它自己跑（YOLO mode） | 低 | 多 | 慢一些，一般也能完成 |

你们的精力是有限的，每一个同学的精力都是有限的。每一个同学都应该去思考：你要把你宝贵的那些精力放到怎么处理 AI 上。

因为是这样——我自己发现，这是我自己的问题——纠正 AI 是一件有多巴胺的事情。它给我一种什么感觉呢？虽然 AI 很强，我好像还是比 AI 有点用的。它会产生这种非常微妙的心理安慰。而不是我就 YOLO mode，然后就等我回来，我也不用看历史，它反正搞定了，我验收一下，它真的搞定了，我就不会看了。

但这个可能在非常长的时间里面都会成为同学们工作的一个常态。你只有把 AI 用在把自己的时间留在收益最大的事情上。这个时间是不能省的。

> **结论**：你有一个东西不知道，你想要把它弄知道——这是你作为一个学生几乎百分之百的时间要去做的事情。剩下那些你知道应该怎么干的事情，AI 能把它干好，你就放手让它干。

这就有一种是，好像在 pre-AI 的时代大家就已经说了：要不要假努力？你自己感动自己的努力是没有用的，你要有效率的努力。在 AI 时代，这个效果的差距会拉得更大。你的每一秒钟的假努力，如果有一个你的 peers 是在真努力，你都是损失非常、非常、非常大的。

以及最后，你们也会发现，随着指令上下文的增长，指令遵循的能力确实会下降。但是，现在模型有一个很有意思的特点：一般来讲，最后的 prompt，就留在最后的那个指令，还是可以遵循的；到前面、尤其是到中间的时候，它上下文指令不遵循。

所以干活还是很好用的。因为一般最后一个短窗口就是一个具体的任务是你的 prompt："帮我把什么东西修了。"它就真的还是可以把这个事情给做完。所以模型还是非常值得使用的。

### 在不确定里探索：算力换智力

如果你真正想要做一个真正 long-horizon 的、非常非常难的任务，它不是解决一个问题，而是在一个不确定性当中探索。那么 chain-of-thought 其实就是解决不了的了。chain-of-thought 能够解决的是一个有 verifier、它确定的一直往后就能解决的问题。

但是如果你让它去解决一个"帮我考虑一下几种方案哪个最好"，它很有可能会给你一个不是最好的方案。为什么呢？因为模型已经被训练成舔狗了。它完成任务才有奖励，它不完成任务是没有奖励的。所以它会给你一个有限的方案。

就像 P 和 NP。大家都知道 P 和 NP 有这两个 complexity class，甚至有更大的这个 complexity class，有一个整个的 polynomial hierarchy。NP 问题说：你想要验证一个解是比较容易的，是 P 的；但是你想要找到那个满足条件的解，是很难的。比如说，给你一个路径是不是 Hamiltonian path，你很容易判断；但是你想要找到一条满足条件的 path，那就是 NP-complete，它是一个完全问题，就是 3SAT 这样的问题。

因为搜索是困难的、验证是容易的，模型为了完成任务，它势必只能做有限的搜索。这个感觉就像你在考试场上，抓点时间，一定要把这道题写完——无论如何马上要交卷了，你写点什么，分数就比不写要高，所以你一定要写点什么。

| | 短程任务（有 verifier） | 真正 long-horizon 的任务 |
| :--- | :--- | :--- |
| 典型例子 | 写藏头诗、计算机系统基础的 PA 作业、帮我做个 PR | 在几种方案里选最好的一种、在一个开放问题里做系统调研 |
| specification | 明确 | 不太清楚 |
| 反馈信号 | verifier 可以判定 | 只能靠人来判断 |
| chain of thought | 能解决 | 解决不了 |

你这时候就可以用一个"算力换智力"的循环。

我举一个例子。你们这一代人是子涵吗？你们还没有。你们可能比你们再小五岁的那个班上，一个班上就有五个甚至十个子涵。现在子涵少多了。你看 AI 给我起的名字，还是很好的——它知道要去《诗经》里面找一个，它的品味肯定比以前的模型提升了。但是你还是不敢用的。为什么呢？因为你用 DeepSeek 起名字，别人也用 DeepSeek 起名字，你就会成为一个 AI 时代的子涵——大家都是用 DeepSeek 起名字，然后 DeepSeek 都起了同样的名字。

我的经验是：如果你真的需要一个非常 long-horizon 的任务，你就需要一个系统性的调研过程，跟你们上什么科研实践课学的那套就很像了。你们进入一个科研领域第一件事情做什么？文献调研，穷尽解决和这个问题相关的所有文献。这件事情，在 AI 想要快速完成任务的时候，它暂时还不会去花这个大代价。但是你可以做。

名字是可以枚举的。你可以先选音，然后把不好的音给筛掉；选完音，你再去用 sub-agent 一个一个去检查字。然后你可以给它一个约束，比如说你喜欢《诗经》，你可以选《诗经》里的一个词。那么，你就实现了算力换智力。

你一个开放问题、一个非常大空间里面的开放问题，如果直接让 AI 去用 next token 的方式做，它会给你一个由它的偏见带来的东西。但是如果你可以把这个空间分割成很多个 disjoint 的部分，你的每一个部分就可以变成一个更有 verifier 的、更明确的东西。你有更多的算力，你就有更大的智力。

```text
一个开放问题（空间极大、没有 verifier）
        │
        │  按某个维度切分
        ▼
 ┌──────────────┬──────────────┬──────────────┐
 │   子空间 1   │   子空间 2   │   子空间 3   │   互不相交
 └──────┬───────┴──────┬───────┴──────┬───────┘
        │              │              │
        ▼              ▼              ▼
    有 verifier    有 verifier    有 verifier
        │              │              │
        └──────────────┴──────────────┘
                       │
                       │  汇总
                       ▼
              收敛出来的结论
```

读图说明：把一个没有 verifier 的开放问题沿某个维度切成互不相交的子空间，每个子空间就退化成一个更明确的、有 verifier 的问题，可以交给 sub-agent 各自去判定；算力铺得越开，你能覆盖的空间越大，换到的"智力"就越多。

但这个有一个缺点：烧 token，烧 token。所以这就涉及到我对人类社会的一个我觉得很有趣的理解。

### 世界很大，人很小

世界很大，人很小。

我们人类的品味，每一个人都是不一样的，因为我们带来了太大的 bias。我们在不同的城市、不同的教育背景、不同的生活圈长大。Richard Sutton 有一个 Big World Hypothesis：我们就是学不到这个世界上的所有东西。但就是因为我们带着这个 bias，才有 $1+1>2$。我们就是一个最大的群体智能，我们在一起实现智能。

但这会带来一个未来的危机。我不知道，我先把危机抛出来。

如果这种真正 long-horizon、世界上真正有价值的问题可以用算力换智力，会可能发生一个什么样残酷的现实呢？有一类人会获得无限的计算资源，他就有无限的智力，他就可以砌一堵墙。在这个墙里面的人有智力，是我的朋友；在墙外面的人是普通人。那么因为假设计算机、AI 模型比人类的智力更高效，那我们外面的人就变成动物园里的猴子，就让他们自生自灭，他们也无论如何也不可能赶上里面人产生智力的这个速度。

那么就墙、墙里面是超人，墙外面是动物世界。大家已经在 AI 的、这个关键的奇点快要到的时候了，我们可能需要思考怎么样防止这件事情到来。
