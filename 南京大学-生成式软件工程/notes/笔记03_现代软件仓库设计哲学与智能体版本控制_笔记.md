# 现代软件仓库设计哲学与智能体版本控制

## 项目与软件的本质

   * **软件（software）**

       * > **定义**：代码、文档等等一切和软件相关的东西的集合；本质上是人类世界的需求在信息世界的一个投影，投影落到磁盘上就是一个目录。

   * **项目（project）**

       * > **定义**：一个目录，其中的一堆文件共同构成一个可以交付的东西，最终成为你的产品。

       * 开始做软件工程的第一个动作是建一个目录并给它起名，而不是先去下载别人的东西。

       * 目录里放一个源文件、把它编译成一个可执行的二进制，这已经在做软件，只是未必符合当下的最佳实践。

       * 项目里同时混着代码、文档、意图、规格说明、实现与测试用例。

   * **本地可运行与可交付的区别**

       * 只起本机开发服务器时，服务地址是本机回环地址，本机打得开而世界上其他人打不开。

       * 要让别人访问到，必须在意图与规格说明里讲清「要被全世界看到」，模型才会去部署；不讲清，模型会按开发者的习惯先在本地调试。

   * **版本管理工具的产生逻辑**

       * 真实需求是项目级的时光回溯：人会犯错，只要能回到过去的某个版本把它捞回来就够。

       * 从「我知道什么、我想要什么」出发就能推出下一个概念该长什么样，这个推演本身就是一种数学式推理。

## 从副本管理到快照仓库

### 几种历史做法

   * **U 盘保存**

       * 把代码放在 U 盘上，U 盘一坏代码全部丢失；失效点是介质本身。

   * **目录副本（作业 v1 / v2 / 最终版）**

       * 每次改动复制一个目录，非常直觉，也确实能找回旧文件。

       * 代价是目录数量随改动线性膨胀，协作只能靠拷来拷去。

   * **打包分发**

       * 交作业时打成压缩包发邮件或上传到网页，代码一更新就要重新分发一遍。

   * **版本控制软件（SVN，Subversion）**

       * > **定义**：存储项目的变化——保留一个最初版本，之后文件每改一行就存一个补丁（patch）。

       * 工作方式是 `check-in` 与 `check-out`。

       * 想回到早期版本只能沿着补丁一个一个往后推；这套看似高效的实现随项目增长把人拖入泥潭。

### Git 的快照模型

   * **Git**

       * > **定义**：既保存项目目录，又能保留、比较和恢复历史版本；每一次提交都是一份完整的快照。

       * 快照模型让「回到过去的某个版本」变成直接取那一份快照，一秒就能回去；增量模型则被迫逐个推演补丁。

       * 作者是 Linux 的作者 Linus，2005 年诞生。

       * 在此之前维护 Linux 靠邮件列表发补丁，由维护者收进核心仓库再发布版本，期间还用过 BitKeeper。

   * **判据**

       * 出发点始终是：我要回到过去的某一个版本，马上、一秒就给我回去。

       * 增量路线即便用缓存优化，也只是在错误的路径上做补救。

### 管理方式的横向对比

| 管理方式 | 存什么 | 回到旧版本 | 协作与分发 |
| :--- | :--- | :--- | :--- |
| 目录副本（作业 v1 / v2 / 最终版） | 整个目录的复制品 | 找到那个副本即可 | 拷来拷去，介质坏了就全没了 |
| SVN | 项目的变化，一次改一行就存一个补丁 | 要沿着补丁一个一个往后推 | `check-in` / `check-out` |
| Git | 每一次提交的一份完整快照 | 直接取快照，一秒回到过去 | `clone` / `pull` / `push`，分发极为方便 |

   * 三种做法解决的是同一个需求，差别全在「存什么」这一个决定上。

   * 分发的便利性也是需求之一：远端更新后所有人拉取一次即可，不必逐个发送压缩包。

### 基础操作与仓库建立

   * **git init**

       * 执行后项目变成被版本管理的仓库，生成一个默认不显示的 `.git` 目录。

       * 完成后即可从远端拉取代码，也可以把代码推到远端。

   * **git add 与 git status**

       * `git add <文件>` 把改动纳入本次快照的范围，`git status` 查看工作区状态与提示。

       * 遇到看不懂的输出，让工具或智能体解释比直接忽略它更有效率。

   * **git commit**

       * 创建一份带消息的快照，提交时打开编辑器写下这次做了什么。

       * 与「作业 v1、v2、v3」不同，Git 不鼓励按版本号堆目录，而是在每次有意义的改动后立即提交一次。

## Git 的持久化数据结构

### 目录树与结构共享

   * **持久化数据结构（persistent data structure）**

       * > **定义**：Git 本质上是一个持久化的数据结构，它持久化的是项目的目录树。

   * **最小代价地记下一整棵树**

       * 从 v1 改一个文件生成 v2 时，不需要复制所有文件：通往根的那条路径上的节点必须新建，因为根不能再指向旧内容。

       * 没被动过的部分用一个指针指过去，内容不复制。

       ```text
       v1 的树                          v2 的树（只改了 b.txt）
         /                                /
         ├── a.txt                        ├── a.txt   ← 指针复用 v1 的 a.txt
         ├── b.txt                        ├── b.txt   ← 新建（内容变了）
         └── d/                           └── d/      ← 指针复用 v1 的 d/
       ```

       * 项目就算有一百万个文件，每次也只需要创建一个很小的增量，就得到一个版本的快照。

       * 之所以可以放心地「不深复制」：目录本身不可能很深，每一级索引都是指数级增长，很快就能把条目登完。

### 三类对象

   * **提交对象（commit object）**

       * 记录本次快照的根目录、父提交、作者与提交信息。

   * **目录树对象（tree object）**

       * 对应一个目录，登记该目录下的条目：权限模式、对象 hash 与名字。

   * **二进制大对象（blob object）**

       * > **定义**：blob 就是 binary，一段字节序列，即文件的内容本身。

   * **三者的关系**

       * commit 指向 tree，tree 指向 blob 或更深一层的 tree，整个结构可以不断向后生长。

       ```text
       commit object
           ├── tree      → tree object（这次快照的根目录）
           ├── parent    → 父提交（合并提交会有两个 parent）
           └── author / message

       tree object（一个目录）
           ├── 100644 blob <hash>  hello.c
           └── 100755 blob <hash>  hello        （755 表示可执行）

       blob object：文件的内容本身，就是一段字节序列
       ```

### 对象的磁盘形态

   * **存放位置**

       * 对象就是普通的文件，放在 `.git` 目录里，以 hash 为索引。

   * **blob 的字节形态**

       * 对很小的文件来说压缩反而是浪费：31 字节解压出 23 字节的内容。

       * 文本对象在头部记录类型与长度，随后的字节就是文件内容。

       * 二进制文件同样是 blob，可执行文件的头部字节是 `7f 45 4c 46`。

   * **tree 的字节形态**

       * tree 的原始数据同样是压缩过的：52 字节解压出 43 字节。

       * 解压后可以读成文本，条目按「字节、对象、模式、名字」的形式排列。

   * **条目的权限模式**

       * `100644` 是普通文件、不可执行，`100755` 是可执行文件。

       * 同一次快照里，可执行文件与普通文件在 tree 中被区别对待。

### 模拟与真实字节的区别

   * 可视化的教学工具是在模型层面模拟：它自己建了一个 Git 的模型，命令与动画都由这个模型驱动。

   * 更彻底的可视化从真实文件的原始字节出发：展示一个字节一个字节如何被解析、解析成了什么，并且持续监听目录变化后重绘。

   * 前者只能得出「模型应该是这样」，后者才能确认「实现真的是这样」。

## 引用、分支与冲突现场

### 分支与 HEAD

   * **分支（branch）**

       * > **定义**：分支就是一个文件，位于 `refs/heads/` 下，内容是一个指向某个提交的 hash。

   * **HEAD**

       * > **定义**：指向指针的指针——HEAD 指向分支文件，分支文件再指向提交。

   * **引用链**

       ```text
       HEAD ──► refs/heads/<分支名> ──► commit object ──► tree object ──► blob
                  （分支文件里存的就是这个 hash）
       ```

   * 创建分支后即可在两个方向上独立提交，提交历史在这里分叉。

### 提交对象的字段

   * tree 指向本次快照的根目录。

   * parent 指向父提交：普通提交一个，合并提交两个。

   * author 与 message 记录作者，以及这次改动做了什么。

   * 合并提交同样是普通的 commit object，只是它有两个祖先，因此整段历史是一张有向无环图而不是一条直线。

### 冲突现场保留的三个版本

   * **工作区里可见的冲突标记**

       ```text
       <<<<<<< HEAD
       （当前分支的版本）
       =======
       （要合进来的那个版本）
       >>>>>>> <另一分支>
       ```

   * **索引（index）里隐藏的三个版本**

       * base：双方共同的祖先版本。

       * ours：当前分支的版本。

       * theirs：要合进来的那个版本。

       * 三者放在未提交区域，工作区里看不到它们。

   * **为什么把两边都摆出来**

       * 冲突不会被自动解决，解决责任在开发者；要解决就必须看得见两边的差异。

       * 同一个位置被两人分别改成不同的值，Git 无法替人选择，只能把两者同时展示。

       * 一般原则：事情发生时，最好就在当场把所有需要的信息都表明出来。

   * **解决方式**

       * 在文件里保留需要的一边、删掉标记，或用编辑器的接受按钮逐项选择。

       * 解决后另建一个提交，把这次冲突的解决记录下来。

       * > **易错点**：⚠️ 只要动手做过一两次就会记得「冲突的两部分会同时出现在同一个文件里」；答不出来通常是没有实际用过，或没有留意。

## 原子提交与提交信息

### 原子改动推进快照

   * **原子提交（atomic commit）**

       * > **定义**：Git 把项目组织成「用原子改动推进的快照」，整个模型都由这一句话推出。

   * **快照必须自洽**

       * 每一次提交的代码都应该能通过构建和测试；一份完整自洽的快照是回溯、二分、协作全部成立的前提。

       * 提交编译不过的代码等于让仓库处于坏状态，会让后续的二分定位失效。

   * **由原子改动推出的能力**

       * 随时可以开新分支做尝试：失败就安全丢掉，成功就合并进来。

       * 可以同时推进多条主线，靠合并让它们汇合而不互相干扰。

       * 项目管理的本质是人无法一次处理一团混沌，所以要把需求分解成可理解、可审计的小任务。

### 提交信息规范

   * **提交信息（commit message）**

       * > **定义**：提交时写下的一句话或一段文字，用来说明这次改动做了什么、为什么这么改。

   * **项目轨迹靠提交信息串起来**

       * 项目本质是从一个版本经过一次修改变到下一个版本，信息写清楚才能看出修了多少缺陷、加了什么需求、经历了什么重构。

       * > **易错点**：⚠️ 提交信息写成看不出内容的套话，一旦累积成千上万条就退化成噪音；提交粒度过大、把编译产物一并交上来，都是长文点名的反例。

   * **约定式提交（Conventional Commits）**

       * 规范要求提交以类型前缀开头，类型是名词（引入功能、修复缺陷等），冒号后必须有一个空格。

       * 结构为「类型（作用域）加冒号与一句话总结，空行，正文」，正文写为什么这么改、改了什么。

       * 常用祈使句现在时描述变更动机，例如 `fix off-by-one in strlen_check`。

   * **空提交**

       * Git 会拒绝没有任何修改的空提交；有知识的工具可以强行造出一次空提交。

       * 用途有限：在不改代码时触发流水线，例如为发布强行做一次版本冻结的提交，把缺陷修复与版本冻结分成两次。

       * 不能大量创建空提交，这不是最佳实践。

### 提交粒度与收益

   * **为什么必须小步提交**

       * 改动越多，错的地方就越多；一个上万行的提交会同时打断项目里多处，引入多个缺陷，后面还要引入多个修复。

       * 小步提交才能冤有头债有主：每个缺陷都能对上引入它的那次提交，修完即闭环。

| 维度 | 一次巨大的提交 | 一串小步提交 |
| :--- | :--- | :--- |
| 出错后的定位 | 上万行里找问题，修了上百个缺陷都算在那一次头上 | 每个缺陷都能对上引入它的那次提交 |
| 审计能力 | 基本丧失 | 保留，发生了什么、谁改的都能查 |
| 备份粒度 | 电脑坏了就全丢 | 每次推送都是一份网络上的备份 |

   * 收益可以并列记住三条：定位、审计、备份。

   * 实践主张是：频繁提交，之后再来打磨，只在需要时发布。

   * **线性的提交历史**

       * 在智能体能把变基与冲突解决做得很轻松之后，强行要求提交历史保持线性成为可行做法。

       * 好处是历史更易追溯，对摘取单个提交与逐行归属也更友好，智能体维护时还能少读一些文件。

## 版本库的收与不收

### 常见的误提交

   * **构建产物与日志**

       * 构建输出目录与日志都是生成物，不应该被提交。

   * **个人配置**

       * 编辑器的个人设置里可能出现本机磁盘路径的硬编码，换到别处无法复现。

   * **密钥与凭据**

       * 提交进仓库的密钥会随历史长期留存，可能在外部评审时被他人看到。

   * **系统隐藏文件**

       * 文件管理器打开目录时会自动留下索引文件，记录哪些子目录被展开过；它以点开头，默认隐藏。

       * > **易错点**：⚠️ 看不见的隐藏文件确实存在于工作区，`git add .` 会把它一并纳入追踪，所以要加忽略规则，并且提交前先看一遍变化。

   * **后果**

       * 各人环境不同，编译产物各不相同（二进制里可能带日期、hash、本机指纹），一旦入库极易产生难以合并的二进制冲突；图片类产物的冲突同样无从合并。

### 生成物的例外与忽略规则

   * **可以入库的生成物**

       * 依赖锁定文件，用于固定依赖版本。

       * 由另一套工具链生成的头文件：入库后别人在没有该工具链的环境里也能直接编译。

   * **忽略规则**

       * 用忽略清单把生成物与临时文件排除在追踪之外。

       * 把点开头的文件默认收进版本库也是合理的，因为 `.github`、工作流配置这类约定俗成的对象就是以点开头。

   * **没有绝对规则**

       * 软件工程研究里的一个标准题目就是检查仓库是否满足这些实践，不满足就给出警告。

       * 这类检查如今可以由智能体耐心地逐条完成，并给出友好的反馈。

## 历史检索能力

### 二分定位引入点

   * **二分定位（bisect）**

       * > **定义**：把提交历史当成一个很长的数组做二分查找，定位「引入某个缺陷的那一次提交」。

       * 前提是有一个测试用例，或任何能检查出这个缺陷的东西。

   * **为什么可以二分**

       * 提交历史天然分成两类：某次提交引入缺陷之后，往后的提交都通不过；在它之前的每一个提交都是通过的。

       * 这就是在「所有前缀是 0、后缀是 1」的数组里找第一个 1，正是二分查找擅长的问题。

       ```text
       历史：commit1  commit2  commit3  commit4  commit5  commit6  commit7
       检查：   0        0        0        1        1        1        1
                           ▲                          ▲
                         最后一个好提交          第一个坏提交（缺陷在这里被引入）
       ```

   * **收益与前提**

       * 每次检查折半，历史再长也只要很少几次检查就能把引入点钉出来。

       * 前提仍落在自洽性上：历史里存在编译不过的提交，二分给出的结论就不可信。

### 行级归属

   * **逐行归属（blame）**

       * > **定义**：`git blame <文件>` 逐行告诉这一行是在哪一次提交、被谁改的。

   * **用途**

       * 知道哪里错了以后，可以据此定位是谁改的、当时在做什么。

       * 二分找出「哪一次提交出问题」，逐行归属找出「哪一行、谁写的」，两者互补。

   * 这套能力是专为人类设计的：人能回忆当时的情形，也能顺着沟通记录追问当时的决定。

## 合并、变基与 change 一等公民

### 合并与变基的选择

   * **合并（merge）**

       * > **定义**：创建一个有两个父提交的新提交，同时继承两条线上的改动。

       * 原有两条线上的提交 ID 全部保留，这个合并提交是额外长出来的、有自己新 ID 的提交。

   * **变基（rebase）**

       * > **定义**：把一条线上的提交逐个搬到另一条线的后面，试图把历史整理成一条直线。

       * 每次搬移都会创建新的提交 ID，因为基（base）已经换了；原有的 ID 全部被替换。

       * 搬一个就可能冲突一次，冲突后要解决、再继续搬下一个，可能反复失败。

       * > **易错点**：⚠️ 一进入变基模式，很多人瞬间不知道该怎么办；正确做法是把「我现在在做什么、发生了什么」说清楚交给智能体解释，不要在没搞清状态时乱按。

### 归属代价

   * **合并的作者归属问题**

       * 合并由谁执行，冲突解决的结果就记在谁名下：别人写的那几行最后归属到了动手合并的人身上。

       * 这是一次隐藏的作者修改，追溯时会失真。

   * **变基解决了归属问题**

       * 变基不产生由他人代笔的合并提交，被搬移的改动不会易主。

   * **根源在于用提交近似地表达修改**

       * 关心的其实是「修改」：一个提交与它父提交之间的差就是一个修改，但 Git 没有一个专门叫 change 的对象。

       * 用提交来代替修改，绝大部分情况够用；一旦把「修改」也变成一等公民，就得到了下一代版本控制系统。

### change 一等公民

   * **Jujutsu**

       * > **定义**：与 Git 底层完全兼容、可以直接当 Git 用，但把 change 提升为一等公民的版本控制系统。

       * 每个 change 都可以被赋予一个标识，变基时是把 change 搬过去，而不是随手重造提交。

   * **冲突仍然躲不掉，但可以一次带来**

       * 两条 change 真的撞在同一个地方时，矛盾无法凭空消掉。

       * 因为 change 是有身份的 object，冲突会跟着 change 一路带下来，最后集中解决，而不是搬一个解决一次、反复失败。

   * **底层模型未变**

       * 它仍然沿用 Git 的冲突记录方式，只是自己另外维护了一套记录，用起来舒服很多。

| | merge | rebase | change（Jujutsu） |
| :--- | :--- | :--- | :--- |
| 合起来时产生什么 | 一个新的两路提交 | 逐个搬移提交并生成新 ID | 把 change 搬过去 |
| 原有提交 ID | 全部保留 | 全部被替换 | change 的标识跟着走 |
| 作者归属 | 被合入的改动挂到做合并的人名下 | 不会易主 | 不会易主 |
| 冲突处理 | 在合并时解决一次 | 搬一个解决一次，可能反复失败 | 冲突随 change 一起带下来，最后集中解决 |

### 无暂存区的工作方式

   * **暂存与压栈的负担**

       * 改到一半、项目还不能编译也不能运行、又突然要转去做更高优先级的事情时，只能把未完成的改动挪开。

       * 压栈式暂存的代价是要自己管理一个栈，栈一深就要面对额外的操作。

   * **change 视角下不需要暂存区**

       * 只要改了一个字节，就立刻把它记成一次提交，并抹掉上一次的提交，用当前快照替代它。

       * 于是永远有一个「当前 change」，永远处于已提交状态，连暂存区也不需要。

       ```text
       工作区改一个字节
             |
             v
       [ 当前 change ]        永远处于「已提交」的状态
             |
             | 再改一个字节：抹掉上一个提交，用当前快照替换它
             v
       [ 当前 change' ]       不需要暂存区，也没有栈要管理
       ```

## 并发控制视角下的版本管理

### 乐观并发控制

   * **乐观并发控制（optimistic concurrency control）**

       * > **定义**：先假设事务之间不会冲突，各自读、各自算、各自写，只在提交时检测冲突，失败则回滚重做。

   * **Git 为什么算乐观**

       * 它假设两条线上的改动不会冲突，于是一路并行推进，只在合并时才可能遇到冲突。

       * 这个假设在数据库里同样大概率成立：教务系统里每个同学读写的都是自己那块数据，两条事务同时开始也都能过去。

   * **古法编程里它为什么够用**

       * 开工前已经对齐过分工，各人顺着自己的路先做，合并时大概率不冲突，无论合并还是变基都能顺利完成。

   * **智能体提速后的变化**

       * 主智能体一次分出去大量任务时，事务冲突会显著变多；不过出错就修，本身不算大问题。

### 悲观并发控制

   * **悲观并发控制（pessimistic concurrency control）**

       * > **定义**：在访问可能冲突的资源之前先申请锁，别人要动同一块资源必须等到锁被释放。

   * **锁的语义**

       * 先获取锁，再动手，做完提交，最后释放锁；这是一个先建立「先 A 后 B」的顺序、再去执行的关系。

       * 一旦某个范围内的资源被锁住，别的智能体只能等释放之后才能获取，于是几乎不会再出现回滚与重做。

   * **锁的粒度与整体进度**

       * 可以在文件级别加锁，避免两个智能体同时改同一个测试或同一份配置。

       * 加锁的本质是「不要并行」，会把可并行的程序退回成串行；但当系统里存在大量互不冲突的线程时，即便每个都持锁，整体仍能高效推进。

       * 智能体数量多、速度快，某个智能体在等锁时，别的智能体可以继续在新范围上推进。

| | 乐观并发控制 | 悲观并发控制（上锁） |
| :--- | :--- | :--- |
| 前提假设 | 事务之间不会冲突 | 冲突必须先被排除才允许动手 |
| 典型机制 | 各自读、算、写，提交时检测冲突，失败则回滚 | 访问前获取锁，别人释放后才轮到 |
| 冲突的代价 | 回滚、重做 | 等待、阻塞 |
| 适合的场景 | 各人读写各自的数据 | 智能体动作极快、并发极高、冲突频繁 |

   * 管理快照、管理版本、管理修改、还要管理飞快的修改——沿用快照是一条线，用上锁的方式管理软件是另外一条线。

## 智能体时代的版本管理

### 使用者是人的隐藏前提

   * **前提**

       * > **定义**：既有的版本控制系统都有一个共同假设——使用者是人类。

   * **单线程的人**

       * 人是单线程的生物：只有一双手、一张嘴、一双眼睛，只有一份 I/O 设备。

       * 观察世界与施加效果不能同时进行：读完一个值之后，到真正写下去之前，中间可能被中断、被换下处理器，手里还是上一次读到的旧值。

   * **由此长出的设计**

       * 人之间无法直接共享思想，沟通有无法逾越的屏障，所以需要开会、需要对任务边界达成一致。

       * 人与人的改动以小时为单位产生，一个模块十几个人已是不小的团队，团队粒度大约十分钟产生一次提交。

### 提交节奏的变化

   * **古法编程的节奏**

       * 动手前先跟旁边的人确认二三十秒，或每天早上开一次会把任务切分下去，各人领走一块。

       * 修到一半又被更高优先级的任务打断的概率很低，所以压栈式暂存通常只有一层，这个设计是合理的——人也可以拒绝一份工作，把它排进队列。

   * **智能体团队的节奏**

       * 单个智能体在上下文热的时候，几十秒甚至几秒就能完成一次修改，以秒级产生原子提交。

       * 团队规模可以轻易扩成十倍、百倍，主智能体负责协调并往子智能体里注入提示。

       * 即便有测试门控把提交速度压下来，整体开发过程仍被显著加速。

   * **结论**

       * 为人类设计的模型在秒级提交与高并发下开始跟不上。

### 多智能体协作机制

   * **每个智能体一台独立开发机**

       * 把「单线程的人」与智能体做严格一一对应：给每个智能体一个独立的容器或机器。

       * 远端放一个共享仓库，让每个智能体作为单人开发者自行提交与拉取，冲突自己修复。

   * **主从结构**

       * 主智能体担任协调者：分发任务、看汇总报告、必要时注入提示。

       * 子智能体各自在隔离环境里工作，必要时可以直接给主智能体发消息。

       * 常见玩法是让两个较强的模型互相牵制：一个负责设计、一个负责评审，让它们达成一致。

   * **同步依赖的差异**

       * 多个智能体工作在同一个仓库上会有麻烦；工作在不同仓库、合并到远端则完全可行。

### 工作树机制

   * **工作树（worktree）**

       * > **定义**：同一个仓库本体可以挂出多棵工作树，每棵工作树有自己的工作目录与独立提交。

   * **与多虚拟机的对比**

       * 开多台虚拟机各放一个智能体完全能跑通，工作树提供了更轻量的协作方式。

       * 提交在本地互相可见，不需要互相推送与拉取。

   * **它不解决一切**

       * 有冲突的修改仍然需要合并或变基才能真正合起来，只是性能更高一些。

   * **工作树里的点目录是什么**

       * 它是一个普通的文本文件，内容是一行指向别处的路径。

       * 那个「别处」是一个小型的 git 目录，位于主仓库的 `worktrees/` 下，自己带 HEAD、索引与日志，但依附于原有的 git 目录而存在，不是自成一体的仓库。

       ```text
       主仓库                          工作树
         .git/                           worktree/
          ├── HEAD                        ├── .git   ← 文本文件，一行 gitdir: ...
          ├── index                       ├── src/
          ├── objects                     └── README.md
          └── worktrees/
              └── wt1/
                  ├── HEAD   ← 小型 git 目录自带 HEAD / index / logs
                  ├── index
                  └── logs
       ```

   * **设计取向**

       * Git 最大程度复用操作系统已有机制：能用一个文件表示的东西，就不另造一套目录结构。

## 项目组织与可追踪性

### 意图到实现的推进链

   * **意图（intent）**

       * > **定义**：你想做一个什么产品、这个产品能达到什么效果，这是仓库说明文档该留下的东西。

       * 说明文档应写最初的初衷、配一两张截图与最重要的那些设计，越短越好。

   * **规格（spec）**

       * 选什么数据库、什么编程语言、项目结构，小到每个模块的接口，都属于规格。

   * **实现（implementation）**

       * 代码本身；意图、规格与实现现在都平铺在同一个目录里。

       ```text
       intent  →  想做一个什么产品、能达到什么效果
          |
          v
       spec    →  选什么数据库 / 什么语言 / 项目结构 / 每个模块的接口
          |
          v
       code    →  implementation
       ```

### 文件系统的表达局限

   * **历史原因**

       * 早期操作系统只提供文件这一种存储手段，关系型数据库尚未发明，项目只能以文件形式保存。

   * **能表达的东西**

       * 意图、规格、测试用例的输入与输出、要断言什么不被违反，这些写成文档即可表达。

   * **丢失的隐藏关联**

       * 文档里写着「数据用链表管理」，实现后来改成了树，两者的关联却没有被强行联系上。

       * 关联一旦断开就变成技术债：文档与代码只会越来越不一致，最后谁也不知道该信文档还是信代码。

       ```text
       文件系统的表达（树）            软件里真实存在的关联（图）
         README.md                     docA <----> docB
         hello.c                         |            |
         docs/                           v            v
           design.md                   impl  <---->  test
                                       ^             |
                                       +-------------+
       ```

### 可追踪性

   * **可追踪性（traceability）**

       * > **定义**：关心的不是文件放在哪儿，而是一个项目里各种测试用例、文档（哪怕只是文档中间的一行）、代码之间的关联是什么，以及能不能在软件系统演进的过程中仍然维持它。

   * **研究脉络**

       * 这是一个研究了几十年的软件工程问题，早年的综述文章标题就叫软件可追踪性。

       * 核心发现是：文件真的只是图保存起来方便，文件系统这一层的选择将错就错地延续至今。

   * **维持可追踪性的要求**

       * 代码与文档必须一致：文档说是链表，实现就必须是链表。

       * 文档声明要有若干方面的测试，测试用例就必须覆盖这些方面。

### 对象化仓库与视图

   * **把一切变成对象或实体**

       * 文档、实现、测试都变成有身份的实体，实体之间的关系（实现、覆盖、触及、引用）可以任意互指、形成环。

       * 这是一张图而不是一棵树，无法用文件系统的树状结构表达。

   * **仓库即数据库**

       * 这些实体与关系可以放进一个数据库里，成为仓库数据库。

       * 从版本 v0 到 v1，一次小步修改会把相关联的文档、实现与测试一起改掉，从一个一致状态推到下一个一致状态。

   * **视图（view）**

       * > **定义**：数据不变，换一种查询、换一种展示形式呈现出来。

       * 智能体可以根据对话把与本次小步相关的文件、测试与文档摘出来，生成一个只含相关内容的视图，例如一块列出待改项的可视化看板。

       * 绝大部分内容与本次小步无关，只看相关的一小部分正是视图存在的意义。

   * **没有变的地方**

       * 仍然要小步向前：一旦大步向前，这套模型就撑不住。

       * 借用的仍是经典概念——数据库的视图、实体与关系，以及版本控制里一步一步推进的经验。

## 架构选择与最小可行版本

### 最小可行产品

   * **最小可行产品（minimum viable product，MVP）**

       * > **定义**：先做一个最小但可用的验证版本，用它逼自己想清楚哪些需求是绝对要的。

   * **它针对的风险**

       * 产品开发中最大的风险是做出了没人想要的东西。

       * 从零开始时，智能体会迅速做出很多它自认为合理的决定，这些决定让项目越来越难维护，最后陷入焦油坑，往往要痛到删掉重做或回退到很早期的版本。

   * **早期阶段不能用多智能体**

       * 项目早期先找一个能力最强的智能体做多轮对话式的讨论，架构定下来之后再并行开工。

### 数据库的引入时机

   * **不要在第一时间引入数据库**

       * 文件系统膨胀时可以现让智能体按数据的组织提炼出一个数据库，所以第一个最小版本可以完全没有数据库。

       * 文件目录可以在文件管理器里随手调整，逐渐梳理到舒服的结构；数据库结构一变就要做迁移。

   * **心智负担的差别**

       * 人对直观的目录已经训练得非常熟练；面对数据库还要先把脑子里的概念翻译成表与结构。

   * **迁移的门槛**

       * 可以把文件目录格式、提交信息格式、文件用法都收敛之后再迁移到数据库。

       * 在遇到性能瓶颈之前，不急于迁移到任何一种数据库。

   * **不该过度设计的地方**

       * 为一个「把个人信息放到某个测试出口上」的需求去做完整的业务系统设计，属于过度设计。

### 流水线与共享存储

   * **先想流水线，再想架构**

       * 先明确系统里有哪几级流水线、它们之间如何协作、哪些数据通过共享云盘流转，架构的样子自然就出来了。

   * **一个没有数据库的实例**

       ```text
       邮箱
         |
         v
       [agent 收邮件]  →  解析出草稿 / 分类 / 是否垃圾邮件
         |
         v
       共享云盘同步（只落邮件 ID 与解析结果）
         |
         v
       [下一级流水线] 继续处理
       ```

   * **需求的更改**

       * 引入共享云盘同步本身就是一次需求更改，需要评估现有架构能否承受。

   * **分层架构的典型形态**

       * 入口层、编排层、能力层、数据层是常见的业务系统分层；结构挑不出错，问题在于把一切都当成业务逻辑系统来做。

### 提示词对项目走向的影响

   * **过度遵循**

       * > **易错点**：⚠️ 提示词里的每一句、每一个词都会被注意力机制看到，模型被训练成极度遵循指令，所以一个开放的需求会让它过度遵循，生成一个确实满足了指令、却不是你想要的答案。

   * **最要紧的那一句**

       * 需求里最关键的往往只有一句话，其余都只是对它的解读；先想清楚自己最想要什么，再决定第一个功能。

   * **早期提示词的影响最大**

       * 直接丢一个完整需求，与先做一个最小版本，对项目走向的影响完全不同。

   * **人的动作**

       * 任务不能直接丢给智能体：第一件事是创建一个空的仓库，然后只想清楚下一步要迈出的那一小步。

       * 从零做出一个完整东西的难度，比在成熟项目里做一个维护性任务要大得多。

## 团队管理

### 沟通成本与规模上限

   * **沟通缺口逼出了整套习惯**

       * 人与人之间存在沟通缺口，必须靠每天开会同步进展、再分派任务，这直接塑造了版本控制的实践：小步前进、每个小改动都留一次可追溯的提交。

   * **为什么团队不能无限变大**

       * 软件系统变大、人变多以后沟通效率下降，产出一并下降；一百人的团队达不到十人团队效率的十倍，能有两三倍已经不错。

   * **平方级的沟通关系**

       * 每多一个人，沟通关系都是平方级上升。

       * 团队里最稀缺的是能把任务分解下去的负责人：能把一个国民级应用切给十个小团队，最后还能拼成一个东西。

   * **不可回避的盲区**

       * 你无法百分之百知道别人在做什么，对整体了解不足时，最后仍会出现各种冲突，例如你写的测试别人过不了。

### 协作约定文件

   * **贡献者指南（CONTRIBUTING.md）**

       * > **定义**：仓库根目录下的一份贡献者指南，回答「我怎么参与这个项目」，包含项目总体结构与分支、提交信息、变更请求的规范和流程。

       * 随手翻几个项目的这份文档：里面的内容都知道就说明你已经会了；出现要求在自己分支上变基、保持线性历史、禁止直接创建分叉的合并时，就知道变基是干什么的。

   * **仓库说明文档**

       * 写清初衷、效果、几张截图与最重要的设计，不必写成没人看的超长文档。

   * **智能体说明文件**

       * 一份写明协作规则的说明文件可以提交进仓库，这符合最佳实践。

   * **一致性的约定**

       * 同一种约定要在全篇保持一致，例如中文与英文之间统一加一个空格；一致本身就是被接受的理由。

### 钩子

   * **钩子（hook）**

       * > **定义**：在某件事发生的前后自动执行一段逻辑的机制。

   * **提交前钩子**

       * 可以在提交前这个钩子上挂上工程检查规则，用于拦截不符合规范的提交。

   * **智能体侧钩子**

       * 也可以在智能体需要输入或完成任务时触发钩子，例如播放一声提示音。

   * **没有唯一正确解的命名**

       * 几十条规则要逐条命名时，全大写与全小写都没有对错，只要没有拼写错误就行。

       * 这类两难没有唯一解，有收益的动作是遇到时多问一句、把细节做扎实。

### 平台侧命令行工具

   * **为什么需要**

       * 代码快照之外还有议题与代码评论，它们不随目录树的快照持久化，所以值得另做一个命令行工具来管理它们。

   * **能力**

       * 获取某个议题、查询指派给自己的议题、把自己名下的议题关闭，都需要先登录。

   * **与智能体配合**

       * 装好这类工具后，就可以在智能体里设定一个目标，要求它做小步、可审计的提交，并遵守分支规则与线性历史约定。

## 单向汉诺塔的强制步

   * **问题**

       * 在经典汉诺塔上再加一条限制：所有盘子的移动只能沿三个柱子构成的环朝同一个方向前进，不允许反向回退；给定盘数，要求输出移动方案或所需移动次数。

   * **常规解法为何失效**

       * 正常解法的关键一步是把最大的盘子直接挪到目标柱，这一步在单向限制下被堵死。

   * **换一个看法**

       * 不看小盘子，只看最大的那个盘子：它没有别的走法，只能顺着环一次挪一格、同向循环。

   * **最优性论证**

       * 任何合法方案里大盘子的每一步都是被强制的，它的移动次数天然是最少的，构成不可避免的下界。

       * 在大盘子前进的间隙里，用归纳法（inductive）递归地把上面那些盘子挪到合适的位置。

       * 大盘子这一步不可约，其余部分按同样的归纳法处理也是最优的，所以整个方案最优。

## 版本管理做的三件事

   * **记住现在**

       * 必须有一个仓库把文件管起来，无论它是哪种形式。

   * **记住历史**

       * 有一天这个东西不要了，或者删掉的东西又发现还有用，还能把它捞回来。

   * **记住教训**

       * 从提交历史里能看到自己是怎么演进到某一个点的，也能看到哪条路失败了；失败留在那里，回到另一个点再开一条正确的路线。

   * 三件事在智能体时代与古法编程时代都成立。

   * **工具与管理的分工**

       * 版本控制终究是工具，是从人过去许多年软件工程经验里蒸馏出来的。

       * 真正困难的是进度，也就是团队管理。

       * 可以在工具之上开发出属于自己的软件工程直觉：把它当成主智能体，去想怎样分解任务、什么时候提交、什么时候合并。
