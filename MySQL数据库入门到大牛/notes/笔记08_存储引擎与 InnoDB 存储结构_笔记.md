## 1. 存储引擎体系

> **一句话主旨**：存储引擎是表级的底层表处理器，决定落盘文件、锁粒度与事务能力，并区分三大内置引擎与四类专用引擎。

### 1.1 架构定位与表级属性

* **存储引擎（Storage Engine）**
    * > 定义：存储引擎在本质上就是**表的类型**，它定义了一张表在物理介质上的组织方式、索引构建方式、数据锁定粒度以及是否具备事务和崩溃恢复能力。
    * 早期数据库术语中它被称为表处理器（Table Handler）。
    * 它是**表级别**概念而非数据库级别概念：同一个数据库内允许表 A 用 InnoDB、表 B 用 MyISAM、表 C 用 Memory。
    * MySQL 自顶向下分四层：连接层（连接管理、认证授权、SSL/TLS、线程池）→ 服务层（SQL 接口、解析器、预处理器、查询优化器、缓冲管理，5.7 及之前有查询缓存而 8.0 已移除）→ 插件式存储引擎层 → 物理文件系统（redo/undo/binlog 与 `.ibd`/`.MYD`/`.MYI`）。
    * 服务层负责编译、语义检查与优化并产出执行计划；执行器通过统一 API 向引擎下发“读取主键为 10 的行”“插入一行新记录”这类指令，行记录如何以二进制写入磁盘由引擎决定。
    * 引擎可即插即用，也可由第三方或企业自主定制扩展。
    * > 来源: P113

* **索引的引擎层归属**
    * 索引在**存储引擎层**实现，而不是在服务层实现。
    * InnoDB 索引默认且核心采用 B+ 树；Memory 默认采用 Hash；此外还存在 R 树与 Full-Text 全文索引。
    * 单表最大索引数量：主流引擎通常支持至少 16 个（业务设计建议控制在 5~6 个以内）。
    * 最大索引长度：单列或联合索引总字节长度上限至少 256 字节；高版本 InnoDB 可支持 767 乃至 3072 字节的宽前缀索引。
    * > 来源: P115

### 1.2 支持清单与数据库级配置

* **SHOW ENGINES 与六列能力属性**
    * `SHOW ENGINES;` 返回九列属性表，其中 Engine、Support、Comment、Transactions、XA、Savepoints 为核心判据。
    * Support 取值含义：`DEFAULT` 为当前全局默认引擎，`YES` 为已编译加载可随时启用，`NO` 为未编译或被明确禁用。
    * 所有内置引擎中**只有 InnoDB 的 Transactions、XA、Savepoints 三项标为 `YES`**，其余引擎三项均为 `NO`。
    * XA 指 XA 分布式事务规范（两阶段提交 2PC），Savepoints 指事务保存点语法（允许长事务局部回滚），二者都依赖本地事务能力。

    | Engine | Support | Transactions | XA | Savepoints | Comment |
    | :--- | :--- | :--- | :--- | :--- | :--- |
    | InnoDB | DEFAULT | YES | YES | YES | Supports transactions, row-level locking, and foreign keys |
    | MRG_MYISAM | YES | NO | NO | NO | Collection of identical MyISAM tables |
    | MEMORY | YES | NO | NO | NO | Hash based, stored in memory, useful for temporary tables |
    | BLACKHOLE | YES | NO | NO | NO | /dev/null storage engine (anything you write to it disappears) |
    | MyISAM | YES | NO | NO | NO | MyISAM storage engine |
    | CSV | YES | NO | NO | NO | CSV storage engine |
    | ARCHIVE | YES | NO | NO | NO | Archive storage engine |
    | PERFORMANCE_SCHEMA | YES | NO | NO | NO | Memory-engine based tracking of execution metrics |
    | FEDERATED | NO | NO | NO | NO | Federated MySQL storage engine |

    * > 来源: P113

* **默认存储引擎的查看与动态修改**
    * 自 MySQL 5.5.5 起，官方默认存储引擎由 MyISAM 切换为 InnoDB。
    * 查看方式：`SHOW VARIABLES LIKE '%storage_engine%';` 或 `SELECT @@default_storage_engine;`，`default_storage_engine` 代表未写 `ENGINE` 选项时新表采用的引擎。
    * 会话级调整 `SET default_storage_engine = MyISAM;` 只对当前连接生效；全局级调整同样只保存在内存中，服务重启即彻底丢失。
    * 持久化必须改配置文件：Linux 下 `/etc/my.cnf` 或 `/etc/mysql/my.cnf`，Windows 下 `my.ini`，在 `[mysqld]` 节点下写 `default-storage-engine=InnoDB`，保存后重启守护进程生效。
    * 建表可显式声明 `ENGINE = InnoDB`，规范的生产 DDL 应显式声明，避免环境移植时受系统默认值影响。
    * > 来源: P113

* **ALTER TABLE 在线换引擎**
    * 语法：`ALTER TABLE emp4 ENGINE = MyISAM;`，可用 `SHOW CREATE TABLE emp4\G` 查看转换后的建表元数据。
    * 底层流程：创建新引擎格式的临时表 → 逐行复制数据 → 重建所有索引 → 替换老表并重命名。
    * > 易错点：在亿级数据量的生产表上执行换引擎会引发长时间磁盘 I/O 阻塞与高昂锁表开销，绝不可在业务高峰期执行。
    * > 来源: P113

### 1.3 物理文件差异与 InnoDB/MyISAM 对比

* **两种引擎的落盘文件体系**
    * 数据目录位置可用 `SHOW VARIABLES LIKE 'datadir';` 查得，默认 `/var/lib/mysql/`。
    * InnoDB（File-Per-Table 独立表空间）：5.7 下为 `emp2.frm`（服务层维护的表结构定义）加 `emp2.ibd`；8.0 引入统一数据字典后废除 `.frm`，一张表只对应一个 `emp2.ibd`，内部由 16KB 大小的页串联成段和区，并封装全部行记录与索引树。
    * MyISAM：结构定义 5.7 及之前为 `emp3.frm`、8.0 为 `emp3.sdi`（Serialized Dictionary Information，JSON 格式元数据）；数据为 `emp3.MYD`（按插入顺序或定长偏移连续存放每一行）；索引为 `emp3.MYI`（全部 B+ 树索引结构）。
    * MyISAM 索引树叶子节点不包含真实行记录，只记录对应行的物理磁盘地址或文件偏移量。
    * > 来源: P113, P119

* **InnoDB 与 MyISAM 核心机制对比**

    | 核心特性维度 | InnoDB | MyISAM |
    | :--- | :--- | :--- |
    | 事务支持 | 原生支持 ACID，支持提交、回滚与保存点 | 不支持，所有操作即时直接生效 |
    | 崩溃恢复 | 支持安全恢复（依赖 Redo / Undo 日志） | 不支持，异常断电需手动 `myisamchk` 修复 |
    | 并发锁粒度 | 行级锁加间隙锁，高并发友好 | 表级锁，读写互相全表阻塞 |
    | 外键约束 | 支持外键级联检查 | 不支持 |
    | 物理存储结构 | `.ibd` 单文件，数据与索引合一 | `.MYD` 纯数据加 `.MYI` 纯索引分立 |
    | 内存使用特征 | 索引即数据，Buffer Pool 同时缓存索引与数据 | 仅缓存索引（Key Buffer），数据依赖 OS 缓存 |
    | 内存占用开销 | 较高，需大内存支撑数据页与缓冲池 | 极低，硬件资源消耗小 |
    | COUNT(*) 性能 | $O(N)$，须按 MVCC 版本逐行扫描累加 | $O(1)$，内部计数器常驻直接读取 |
    | 主流典型场景 | 高并发、强一致金融业务、核心交易、更新频繁 | 只读归档、小数据量分析、日志流水单向插入 |

    * > 来源: P113

* **崩溃恢复与并发吞吐**
    * InnoDB 重启时自动重放已提交事务、回滚未提交的半截事务，无需人工介入；MyISAM 无事务日志与回滚机制，崩溃后已改数据永久停留，表文件可能损坏，须依赖外部工具做耗时修复。
    * MyISAM 表级锁：即使只更新单条记录也强制锁住整张表，其他线程对该表的任何读写完全排队；InnoDB 行级锁精准锁定受影响目标行，不同行之间的更新与查询互不干扰。
    * COUNT(*) 复杂度差异根源：InnoDB 引入 MVCC，同一物理时刻不同事务按各自 ReadView 看到的有效行版本数不同，无法维护全局固定行数。
    * > 提示：现代高并发微服务架构下主流设计手册明确禁止在数据库层面建立物理外键，完整性校验上移到应用服务层，因此外键是功能差异但不是选 InnoDB 的核心决定因素。
    * > 来源: P113

* **内存模型与场景取舍**
    * InnoDB 遵循“索引即数据，数据即索引”，其聚簇索引 B+ 树叶子节点直接容纳完整行记录，数据页读入 Buffer Pool 时索引结构与整行数据捆绑加载，对内存容量要求极高。
    * MyISAM 的 B+ 树叶子存主键值加指向 `.MYD` 的物理指针；自带 Key Buffer 只缓存索引块，绝不缓存真实行数据，真实数据 I/O 完全依赖操作系统 Page Cache。
    * 强烈推荐 MyISAM：表数据量较小（单表几万到几十万级别）、以纯单向 `INSERT` 与全量高频 `SELECT` 为主、几乎没有 `UPDATE`/`DELETE`、无需事务保障且内存有限的辅助统计类业务。
    * 必须选用 InnoDB：核心交易与金融结算、频繁并发单行更新与物理删除、对数据完整性有绝对要求、需要崩溃安全防护、数据规模巨大的核心业务系统。
    * 工业实践中中小企业 99% 的核心场景直接使用 InnoDB；阿里等超大型企业曾自研基于 LSM-Tree 架构的 X-Engine，在部分交易与归档业务线替代原生 InnoDB。
    * > 结论：InnoDB 与 MyISAM 绝不是单向淘汰与替代关系，而是在各自适配的业务边界内各有不可替代的性能优势。
    * > 来源: P113

### 1.4 Archive 归档引擎

* **Archive**
    * > 定义：Archive 是一种**只支持插入（`INSERT`）和查询（`SELECT`）**的专用存储引擎，底层硬性禁用了修改（`UPDATE`）和删除（`DELETE`）。
    * 在 Archive 表上执行更新或删除语句会被服务层直接拦截并抛出错误；该约束天然适合只读审计日志、操作轨迹流水、电商历史快照、海量物联网监控原始数据。
    * 索引限制：MySQL 5.5 及更高版本中 Archive 开始支持索引，但**只允许在具备 `AUTO_INCREMENT` 属性的自增列上建立索引**（唯一索引或非唯一索引均可）。
    * > 易错点：在 Archive 表的非自增列上建普通索引或组合索引，DDL 会立即报错失败。
    * 压缩：底层集成 zlib 无损压缩算法库，一行数据插入时先在内存缓冲区实时压缩，随后顺序追加写入磁盘；物理文件以表名为前缀，生成 `.ARZ` 文件（ARchive GZip），存放压缩后的纯行记录与自增列元数据。
    * 磁盘占用：同数据量下比 MyISAM 表小约 75%（约四分之一），比 InnoDB 表小约 83%（约六分之一）。
    * 采用行级锁，并发写入归档流水时不同连接之间不会因表锁全盘挂起；支持基于时间点的备份恢复以及数据字典统计信息的实时更新。
    * > 来源: P114

### 1.5 CSV 文本映射引擎

* **CSV**
    * > 定义：CSV 引擎把操作系统底层的普通文本 `.csv` 文件原样映射为 MySQL 内部的一张标准关系表，可直接对其执行 `SELECT` 过滤或 `INSERT` 追加。
    * 建表约束：表中所有字段必须全部显式声明为 `NOT NULL`，否则报错 `ERROR 1178 (42000): The storage engine for the table doesn't support NULL columns`。
    * 不支持任何索引，全表检索必然触发全文件扫描。
    * 物理文件两个：`表名.CSM` 元数据文件（CSV Meta，记录表状态、行计数等运行时元信息）与 `表名.CSV` 纯文本数据文件。
    * 数据文件内容即标准逗号分隔文本，例如两行记录呈现为 `1,"atguigu01"` 与 `2,"atguigu02"`，可被 Excel / WPS 直接双击打开。
    * 底层按标准纯文本 ASCII/UTF-8 字符流切分字段，因文本协议难以统一区分“空字符串”与“物理 NULL 指针”，故要求所有字段杜绝 `NULL` 以保证解析确定性。
    * > 来源: P114

### 1.6 Memory 内存引擎

* **Memory（旧称 HEAP）**
    * 所有行数据完全放置在物理内存中；表结构定义仍固化在磁盘：5.7 下存在 `tablename.frm`，8.0 统一收录至系统数据字典，因此重启后表名、字段名与结构定义依然存在，无需重新 `CREATE TABLE`。
    * 真实行记录完全驻留宿主进程内存堆空间，磁盘上没有任何数据副本；断电、实例宕机或服务正常重启后表还在但查询返回空表。
    * 读写完全摆脱磁盘寻道与 I/O 延迟，速度比 MyISAM 还要快**一个数量级**，响应时间在微秒级别。
    * > 易错点：Memory 要求每行记录具备固定存储长度（Fixed-length Format），严禁使用 `BLOB` 或 `TEXT` 等大对象变长字段；`VARCHAR` 在内存分配时会按最大声明长度转换为定长字符数组，容易引发内存浪费。
    * 默认创建的索引是哈希索引（Hash Index），等值比对为 $O(1)$；哈希索引完全不支持范围查询与排序，`WHERE age > 20` 或 `ORDER BY id` 会使其失效并退化为全表扫描。
    * 改 B+ 树语法：`CREATE TABLE mem_temp (id INT NOT NULL, name VARCHAR(20), INDEX idx_id USING BTREE (id)) ENGINE = MEMORY;`
    * 容量双重边界：单表可用 `MAX_ROWS` 指定最大记录条数；实例全局上限由 `max_heap_table_size` 决定，默认值通常为 **16MB**，可用 `SHOW VARIABLES LIKE 'max_heap_table_size';` 查看。
    * 触达阈值时引擎拒绝写入并抛出 `The table ... is full`；需提前通过 `SET GLOBAL max_heap_table_size = ...` 调大。
    * 适用：复杂计算的临时中间表（多表聚合中途结果集做二次 Hash Join 后立即释放）、数据量极小（几兆以内）极高频读取且磁盘有完整底账的高频只读维度字典（省市区编码、错误码表、行业分类树）、非敏感的用户临时 Session 状态。
    * 严禁：交易记录、充值流水、订单凭证以及任何不能承担丢失风险的核心持久化数据资产。
    * > 来源: P114

### 1.7 其他专用引擎

* **Blackhole 与主从日志中继**
    * 抛弃所有写操作，读操作永远返回空结果集，行为与 Linux 的 `/dev/null` 一致，任何 `INSERT` 都不会落盘，底层没有任何物理存储机制。
    * 价值在复制中继：开启 Binary Log 时，写入 Blackhole 表的 SQL 不会本地落盘但**写操作依然被完整记录到 Binlog 日志流**；在多级分发架构（Master → Relay Slave → Multiple Slaves）中，中继服务器的表可设为 Blackhole，不承担磁盘存储与 I/O 负担，仅作为 Binlog 中转站向下游从库分发，减轻主库网络与 CPU 压力。
    * > 来源: P114

* **Federated 跨库代理**
    * 本地创建 Federated 表时不保存任何真实行数据，只配置指向远程数据库的连接串（IP、端口、账号密码、库表名）。
    * 本地对该表执行 SQL 时，驱动自动转为网络指令向远程节点发起远程过程调用（RPC）。
    * 网络延迟不可控、跨机事务支持脆弱，工业生产中故障率较高，官方默认配置下处于禁用状态（Support 标为 `NO`）。
    * > 来源: P114

* **Merge（MRG_MYISAM）表合并**
    * 将一组结构完全相同（字段名、类型、索引定义完全一致）的物理 MyISAM 表在逻辑上拼接为一张虚拟大表，查询请求自动并行分发到各子表执行。
    * 在缺乏原生表分区的年代常被用来做纯手工冷热数据横向分表；MySQL 5.1 之后原生分区机制成熟，Merge 在现代架构中已逐渐淡出。
    * > 来源: P114

* **NDB（NDBCLUSTER）分布式集群引擎**
    * 专为 MySQL Cluster 高可用集群架构打造，底层将行数据在多个数据节点（Data Nodes）之间自动分片、内存常驻并做多副本同步复制。
    * 可支撑电信级“99.999%”（五个九）的容灾高可用指标，面向需要无中心化高可用与分布式内存级吞吐的金融及通信系统。
    * > 来源: P114

## 2. 索引机制与性能代价

> **一句话主旨**：索引是排好序的快速检索数据结构，其核心使命是压缩磁盘 I/O 次数，代价是磁盘空间与每次 DML 的树维护开销。

### 2.1 必要性、定义与硬约束

* **为什么必须避免全表扫描**
    * 磁盘 I/O 与内存 CPU 计算存在数万倍物理鸿沟，业内比喻为“天上一天，地下一年”：内存级操作耗时几十纳秒到几微秒，一次机械硬盘寻道加旋转或 SSD 闪存块寻址与总线传输耗时几毫秒到几十毫秒（I/O 繁忙时可达数百毫秒）。
    * 三种检索模型的 I/O 代价：物理离散无序存放随机寻道耗时不可控；物理连续顺序扫描查找第 6 条记录需 6 次磁盘 I/O，复杂度 $O(N)$；按二叉搜索树建索引时查 89 只需比对根节点 34 再下潜右孩子，仅 2 次磁盘 I/O，复杂度 $O(\log_2 N)$。
    * > 结论：数据库索引优化的首要底层使命不是减少 CPU 比对指令数，而是**最大限度压缩向操作系统请求物理磁盘 I/O 的调用次数**。
    * 典型劣化：单表从几千行涨到几百万甚至上千万行后，一条 `SELECT * FROM table WHERE ...` 可能从 5 毫秒骤增至 5 秒甚至数十秒，打满连接池导致服务宕机。
    * > 来源: P115

* **索引（Index）**
    * > 定义：索引是帮助 MySQL 高效获取数据的数据结构；工程上可严密定义为**排好序的、用于快速查找的数据结构**。
    * 数据若不经过特定维度的物理或逻辑排序，折半查找与树状搜索都无从谈起。
    * > 易错点：张口就答“索引就是 B+ 树”只能算及格；必须先指明存储引擎上下文——InnoDB 用 B+ 树、Memory 默认用 Hash，另存在 R 树与 Full-Text。
    * > 来源: P115

* **索引规格配额边界**
    * 单表最大索引数量：主流引擎通常支持至少 16 个，业务设计建议控制在 5~6 个以内。
    * 单列或联合索引的总字节长度上限至少 256 字节；现代 InnoDB 高版本配置支持 767 乃至 3072 字节的宽前缀索引。
    * > 来源: P115

### 2.2 性能红利与代价

* **建索引的五项收益**
    * 降低磁盘 I/O 成本：原本需遍历几百个数据页、产生数百次随机 I/O 的全表扫描，通过高阶 B+ 树检索通常只需 **2 到 4 次磁盘 I/O** 即可锁定包含目标行的数据页。
    * 保证物理唯一性：对业务键（身份证号、流水单号）加 `UNIQUE` 约束时底层自动构建唯一索引，插入与修改时利用 B+ 树快速判断冲突重复值，在引擎层捍卫实体完整性。
    * 加速多表关联 `JOIN`：驱动表与被驱动表连接字段（如 `order_id`）有索引时，优化器可对被驱动表采用索引查找，避免 Nested Loop Join 劣化为多次全表扫描。
    * 消除 `ORDER BY` 内存排序：索引底层天然有序（键值如 `1, 1, 2, 2, 3, 4, 4...` 严格单调递增），引擎只需顺着索引树叶子链表顺序拉取，避免在内存开辟 `sort_buffer` 执行单路/双路排序（Filesort）。
    * 优化 `GROUP BY` 分组计算：无索引时须建内部临时表并逐行算哈希散列，有索引时相同值在索引树中物理相邻，引擎顺链表扫一遍并在数值跃迁处划界即可完成分组，规避磁盘临时表生成。
    * > 来源: P115

* **空间与时间代价**
    * 磁盘空间：MyISAM 每个索引实打实写入 `.MYI`；InnoDB 每个二级索引独立开辟一棵由大量 16KB 数据页组成的完整 B+ 树，千万级表若随意建七八个联合索引，索引占用磁盘空间往往远超真实行数据体积。
    * 构建耗时：数千万行大表执行 `CREATE INDEX` 需提取指定列数据、外部排序并逐层构建 B+ 树节点，耗时数分钟乃至数小时，期间易引发大面积系统锁等待。
    * 写入衰减：每次 `INSERT`/`DELETE`/`UPDATE` 都必须同步修改该表上建立的所有索引树，为维持有序性与平衡，底层频繁触发节点移动、页分裂（Page Split）与页合并（Page Merge）。
    * > 提示（生产调优技巧）：海量数据批量灌库前先用 `ALTER TABLE ... DROP INDEX ...` 临时抹掉所有非核心辅助索引，数据以纯顺序 I/O 高速写入后统一 `CREATE INDEX` 批量重建；“先删索引 → 批量导入 → 一次性全量重建”的总耗时远少于挂着索引逐条插入。
    * > 结论：一张表的索引绝非越多越好，索引越多占用的磁盘与 Buffer Pool 空间越多，写入维护链条越长，性能恶化越严重。
    * > 来源: P115, P119

## 3. 索引结构的数据结构选型

> **一句话主旨**：从 Hash 到 BST、AVL、B 树逐层排除，只有非叶子节点不存行数据的 B+ 树才能把树高压到 2~4 层。

### 3.1 Hash 结构与哈希索引

* **哈希结构与散列冲突**
    * 哈希算法通过哈希函数（如 MD5、SHA 或散列映射算法）将任意长度输入映射为固定长度哈希值，具严格确定性：相同输入必得相同输出，输入单个字符变化会导致哈希值剧烈散列。
    * 碰撞处理采用链接法（Chaining）：长度为 16 的桶数组中键 A 哈希值 17 与键 B 哈希值 33 取模后都落在槽位 1，则在该槽位挂一条单向链表依次挂载冲突元素。
    * Java 环境实测对照：10 万条数据线性数组逐一遍历查找累计 823 毫秒，改用基于哈希的 `HashSet` 单值查找累计仅 5 毫秒，差距达两个数量级。
    * > 来源: P120

* **哈希索引的四项致命缺陷**
    * 仅支持等值比对：只擅长 `=`、`!=`、`IN` 这类离散检索；范围查询（`WHERE age BETWEEN 20 AND 30`、`WHERE create_time > '2026-01-01'`）因哈希打散后物理无先后邻近关系，只能退化为全表扫描，复杂度跌落 $O(N)$。
    * 数据散列无序：无法为 `ORDER BY column` 提供有序性保障，数据库必须把满足条件的数据全部捞入内存 Sort Buffer 做外排或快排。
    * 无法支持联合索引最左匹配：哈希索引把 `(c2, c3)` 值拼接后算单一哈希值，查询条件只有 `c2` 时无法用半截输入算出复合哈希值，索引彻底失效。
    * 低基数列严重碰撞：性别列（只有“男”“女”）建哈希索引时数百万行集中于两个桶，桶后链表长达数百万节点，常数级查找退化为 $O(N)$ 线性链表扫描。
    * > 结论：哈希索引是一把极端的手术刀，只适用于单纯的单行精准命中；涉及范围检索、数据排序、联合前缀匹配或高重复列时全线崩溃。
    * > 来源: P120

* **Memory 支持与自适应哈希索引（AHI）**
    * MySQL 中明确支持哈希索引的主要是内存级引擎，如 Memory 引擎与集群版 NDB 引擎；Memory 数据全部常驻内存，默认索引类型即 Hash 索引；Redis 这类 NoSQL 键值数据库底层核心骨架同样是哈希表。
    * **InnoDB 和 MyISAM 不支持用户手动创建独立的 Hash 索引。**
    * 自适应哈希索引（Adaptive Hash Index, AHI）：当 InnoDB 监控到某些数据页、某些二级索引记录被极高频反复访问且满足连续等值命中等条件时，**在内存中自动开辟哈希表空间**，把该数据页的物理内存地址以键值对形式缓存。
    * AHI 命中链路：查询条件 → 内存 Hash 映射（$O(1)$ 一步直达）→ 物理数据页，跳过 B+ 树自根下潜甚至跳过回表流程。
    * 该特性由引擎动态自建与回收、无需人工干预，MySQL 中默认开启，可用 `SHOW VARIABLES LIKE '%innodb_adaptive_hash_index%';` 确认返回 `ON`。
    * > 来源: P120

### 3.2 二叉树类结构的树高瓶颈

* **二叉搜索树（Binary Search Tree, BST）**
    * 节点二分性质：左子树所有节点值均小于根节点值，右子树所有节点值均大于根节点值；在理想树中查找 91 只需与 34、89 比对 3 次，复杂度 $O(\log_2 n)$。
    * 死穴是不具备自我平衡能力：若按 5、12、34、77、89、91 单调递增插入即退化为单向斜树，查 91 需遍历 6 次，树高等于节点总数 $N$，复杂度劣化为 $O(N)$。
    * 若用它充当磁盘索引，每次下潜代表一次物理磁盘 I/O，查一行需数万次 I/O。
    * > 来源: P120

* **平衡二叉树（AVL 树）**
    * 铁律约束：任何节点的两棵子树高度差（平衡因子）的绝对值不能超过 1；插入或删除破坏约束时通过左旋、右旋强制恢复平衡。
    * 31 个节点在严格平衡 AVL 树中的分布为 $1 + 2 + 4 + 8 + 16 = 31$，整树压缩在 5 层以内，检索任一节点最多比对 5 次。
    * 1000 万条记录时 $\log_2(10{,}000{,}000) \approx 24$，即使绝对完美的 AVL 树树高也高达 24 层，对应连续 24 次磁盘物理 I/O，按每次寻道几毫秒计算单次查询需上百毫秒。
    * > 结论：二叉树在内存计算中近乎完美，但扇出过窄导致“太高太瘦”；以磁盘 I/O 为主要矛盾的数据库体系下树结构必须**越矮胖越好**。
    * > 来源: P120

### 3.3 B 树与 B+ 树

* **多路平衡查找树（B 树，B-Tree）**
    * `B-Tree` 中的短横线只是连接符，读作“B 树”，不是“B 减树”。
    * $M$ 阶 B 树特征：一个拥有 $K$ 个子节点的内节点恰好包含 $K-1$ 个排序关键字；插入或删除时通过节点分裂与合并动态维持全树平衡。
    * 数据全树离散分布：非叶子节点和叶子节点都直接存放完整的用户数据行记录（或指向真实数据的物理指针）。
    * 性能波动：查根节点需 1 次 I/O，查中间层需 2 次 I/O，查叶子层需 3 次 I/O。
    * 范围查询须在整棵树上做中序遍历，向下寻址与回溯父节点交替，在多个数据页之间来回跳跃寻道，伴随大量随机磁盘 I/O。
    * 各叶子节点相互独立且无链表串联；出现在非叶节点的关键字，叶节点不再包含（无关键字冗余）。
    * > 来源: P120

* **B+ 树（B+ Tree）与三项优势**
    * 结构改写：$K$ 个子节点的节点包含 $K$ 个关键字；非叶子节点仅存储目录关键字与下层指针，坚决不存放真实数据；所有完整数据集中于最底层叶子节点；叶子节点通过双向链表形成全局有序序列；非叶节点出现的关键字在叶节点中必定冗余存在。
    * 优势一（扇出）：非叶子节点只存“主键 + 页号”，`BIGINT` 主键 8 字节加页号指针 4~8 字节合计约 16 字节，一个 16KB 非叶子页可容纳多达上千个目录项，单节点扇出突破 1000，2~4 层即可托起上千万级数据。反观 B 树非叶子节点若塞入 1KB 的完整行数据，一个 16KB 页顶多容纳十几个关键字与分支指针。
    * 优势二（稳定）：所有实际数据全部在叶子层，任何记录的等值检索都严格经历自顶向下的定长路径下潜到底层叶子页，每次查询 I/O 次数高度稳定恒定。
    * 优势三（范围与全表扫描）：范围查询先自顶向下定位下边界（如 `id=10`）所在叶子节点，再沿底层双向链表顺序遍历到上边界（`id=100`），把昂贵的树形搜索转化为极速的顺序链表遍历。
    * > 来源: P120

* **B+ 树容量与 1~3 次 I/O 测算**
    * 目录项容量：16KB = 16384 字节，`BIGINT` 主键 8 字节加子页地址指针通常取 6 字节（内部按 4~8 字节不等）得 14 字节，含行头元数据约 16 字节，故扇出 $M = 16384 \div 16 \approx 1000$ 个目录项。
    * 树高与容量推导：第一层根节点含 1000 个目录项指向第二层 1000 个目录页；第二层 1000 个页每页再含 1000 个目录项，共指向 $1000 \times 1000 = 1{,}000{,}000$ 个叶子节点数据页；若单页容纳 1000 条记录则 3 层树理论承载 $1000 \times 1000 \times 1000 = 1{,}000{,}000{,}000$ 条（十亿级）。
    * 现实估算：若单行 1KB、单页只能容纳 16 条记录，3 层树仍可容纳 $1000 \times 1000 \times 16 = 16{,}000{,}000$ 条（一千六百万条）。
    * I/O 次数：根页因“根页面位置万年不动”几乎长久常驻 Buffer Pool，第 1 次节点访问（根节点）产生 **0 次**物理磁盘 I/O；第 2 次节点访问（第二层目录页）若未命中缓存触发第 1 次；第 3 次节点访问（底层叶子数据页）触发第 2 次。数据膨胀到数千万至上亿、树高扩展到 4 层时（考虑填充因子不能填满 100%），I/O 次数为 $4 - 1 = 3$ 次。
    * > 结论：千万级表 B+ 树高度通常仅 2~4 层，扣除常驻内存的根节点后，定位任意一行记录最多经历 **1 到 3 次磁盘 I/O**。
    * > 来源: P120

* **数据结构选型矩阵**

    | 数据结构类型 | 时间复杂度 | 范围查询能力 | 排序支持 | 树高控制（海量数据） | 存储引擎支持度 |
    | :--- | :--- | :--- | :--- | :--- | :--- |
    | Hash 结构 | $O(1)$ | 完全不支持 | 不支持 | 无树高概念（纯散列） | Memory、NDB 支持；InnoDB/MyISAM 不支持 |
    | 二叉搜索树（BST） | $O(N)$ ~ $O(\log_2 N)$ | 支持 | 支持 | 极差（易退化为单链表） | 数据库引擎均不采用 |
    | 平衡二叉树（AVL） | $O(\log_2 N)$ | 支持 | 支持 | 较差（二叉太高，深达 20+ 层） | 数据库引擎均不采用 |
    | 多路平衡树（B 树） | $O(\log_M N)$ | 较差（中序遍历跳跃） | 较差 | 适中（节点存数据，扇出偏小） | 早期文件系统采用，主流 DB 不用 |
    | B+ 树 | $O(\log_M N)$ | 极佳（双向有序链表） | 极佳 | 极佳（仅存目录，高度仅 2~4） | InnoDB、MyISAM、Memory 全面支持 |

    * > 来源: P120

* **R 树（R-Tree，空间索引）**
    * 面向“搜索当前经纬度坐标周围 3 公里以内的所有餐馆”这类高维空间检索：B+ 树只能对一维标量数据（数字、字符串）做线性排序，对多维二维空间拓扑矩形束手无策。
    * 基于多维空间边界框（MBR）实现；MySQL 中 MyISAM 和 InnoDB 均支持针对 `GEOMETRY` 空间数据类型建立 R 树空间索引，纯内存的 Memory 引擎不支持 R 树。
    * > 来源: P120

## 4. 索引方案的迭代推导

> **一句话主旨**：从单页内单向链表出发，经页分裂铁律、目录项双元组、目录页与多目录页四步迭代，自然收敛为 B+ 树分层结构。

### 4.1 单页存储与页分裂铁律

* **数据页（Data Page）**
    * > 定义：InnoDB 中无论是从磁盘读取数据到 Buffer Pool，还是把内存脏数据刷回磁盘，其交互的基本物理单位统称为**数据页（Data Page）**，默认配置下单个数据页固定为 **16KB**（16,384 字节）。
    * 表中的每一行数据在页内称为一条记录（Record）；单个 16KB 页除去页头、页尾及系统控制信息后，通常可容纳几十条、几百条甚至上千条普通行记录。
    * 页内单链表规定：所有用户真实记录按主键单调递增被夹在 `Infimum` 与 `Supremum` 两个系统哨兵之间，形成逻辑严格单调递增的单向链表；`Infimum` 的 `record_type = 2`，`Supremum` 的 `record_type = 3`。
    * 页内检索边界：基于主键查找可利用页目录槽位做二分折半查找，复杂度 $O(\log N)$；基于未排序的非索引列查找只能从 `Infimum` 起沿链表逐行比对整页，复杂度恶化为 $O(N)$。
    * > 易错点：页内几十条记录在磁盘物理空间上并非紧挨着连续排列；若强制物理连续，中间发生修改或随机插入就要整页数据全盘搬移。真实机制是记录通过 `next_record` 相对指针以单向链表维系逻辑有序，物理上可放在页内任意空闲碎片位置。
    * > 来源: P116

* **页间双向链表与线性扫页灾难**
    * 每个数据页的 `File Header` 中封装 `FIL_PAGE_PREV` 与 `FIL_PAGE_NEXT` 两个指针，所有数据页相互咬合构成跨全局的双向链表，物理上各页可任意散落，逻辑上保持连续。
    * 若只知页间链表而不知目标页号，查主键 118 只能从表头页开始：发起一次物理 I/O 拉入整页 16KB、内存内翻遍未见目标、再顺 `FIL_PAGE_NEXT` 拉下一页。若目标位于第 8,000 个数据页，将连续触发 8,000 次随机磁盘物理 I/O，按每次 10 毫秒计算单条查询耗时 80 秒。
    * 图书馆模型：仅把几千个书架用绳子首尾相连且无标签，找书须从第 1 个书架第 1 本翻起；真实图书馆按分类编目（书架 01~10 归数理科学类、11~20 归文史哲学类）并贴首末索书号（如 `O13-001` 到 `O13-999`），读者看总目录索引板即可过滤 99% 无关书架。
    * > 来源: P116

* **全局单调铁律与页分裂（Page Split）**
    * 铁律：在全局双向链表拓扑中，**下一个数据页中所有记录的主键值必须严格大于上一个数据页中所有记录的主键值**。
    * 推演设定：测试表为 `CREATE TABLE index_demo (c1 INT, c2 INT, c3 CHAR(1), PRIMARY KEY (c1)) ROW_FORMAT = COMPACT;`，简化假设单个 16KB 数据页最多容纳 3 条用户记录。
    * 插入 `(1,4,'u')`、`(3,9,'d')`、`(5,3,'y')` 至页 10，页内链表为 `Infimum -> 1 -> 3 -> 5 -> Supremum` 完美闭合。
    * 再插入 `(4,4,'a')` 时页 10 已满，系统分配新页 28 并双向挂载；若直接把 `4` 塞进页 28，就会出现前页藏主键 5 大于后页主键 4，粉碎全局单调递增性。
    * 正确分裂流程：找出页 10 中的最大记录 `[5]`；发现新记录 `[4]` 小于 `[5]`；把 `[5]` 强行挪出并搬迁写入新开辟的页 28；把新记录 `[4]` 填补回页 10 的空缺位置并重整页内单链表指针。
    * 分裂终态：页 10 为 `Infimum -> 1 -> 3 -> 4 -> Supremum`，页 28 为 `Infimum -> 5 -> Supremum`，两页由 `FIL_PAGE_NEXT`/`FIL_PAGE_PREV` 互指。
    * 后续梯队：页 10 存 `1,3,4`（最小 1、最大 4），页 28 存 `5,...,11`（最小 5、最大 11），页 20 存 `12,...,20`（最小 12、最大 208），页 9 存 `209,...`（最小 209），每个页内主键绝对严格小于其右侧所有页面的主键。
    * > 来源: P116

### 4.2 目录项、目录页与多目录页困境

* **目录项（Directory Entry）双元组**
    * 目录项只含两个字段：`key` 为该数据页所容纳全部记录中的**最小主键值**，`page_no` 为该数据页在磁盘空间中的真实物理页号。
    * 目录项集合示例：`(1, 页10)`、`(5, 页28)`、`(12, 页20)`、`(209, 页9)`。
    * 跨页剪枝检索主键 `c1 = 20`：比对目录项 1（key=1，下一页 key=5，继续）→ 目录项 2（key=5，下一页 key=12，继续）→ 目录项 3（key=12 且下一项目录项 key=209，因 $20 < 209$ 断定主键 20 绝无可能出现在页 9 及之后），结论为主键 20 必然封印在页 20 内。
    * 定位后引擎只需发起**唯一一次定向磁盘 I/O** 把页 20 读入内存，再在页 20 内部执行二分折半查找命中目标行。
    * 目录项自身天然有序（`1 -> 5 -> 12 -> 209`），因此可直接对目录项集合运用二分查找；假定一个真实数据页能存放 1,000 条记录，仅 4 个目录项就覆盖 4,000 条数据，在目录项上比对一次瞬间剔除 3,000 条数据。
    * > 结论：这套“页内记录按键值单链表递增 → 页间通过分裂保持下界递增 → 抽取各页最小主键与页号构成有序目录项 → 借助目录项剪枝实现定向 I/O 穿透”的方案就是现代数据库索引设计的真正雏形。
    * > 来源: P116

* **物理连续目录项的两大失效场景**
    * 空间申请压力：数据页数量由几个增长到成千上万个后，若目录项仍要求占用物理绝对连续的磁盘块或内存地址空间，内存分配与磁盘碎片整理压力呈几何级数上升；申请超大连续内存块本身高成本且极易失败。
    * 页面废弃导致级联前移：大规模 `DELETE` 清空某数据页后该页被回收、目录项失效，因要求物理连续，其后的所有目录项都必须在内存或磁盘空间中依次向前移动一位。
    * 页分裂与中间插入导致级联后移：相邻目录项前页最大主键为 10、后页最小主键为 22，若写入主键介于 10 与 22 之间的新记录并撑满原页，须开辟新页插在两者之间，该位置之后成千上万个目录项必须全部向后移动一个槽位。
    * > 结论：物理连续的数组结构天然适合高频读、零写入的静态检索，但动态 OLTP 数据库中的频繁增删会引发严重的目录项搬移风暴。
    * > 来源: P117

* **目录页（Directory Page）与两步 I/O 链路**
    * 把目录项打散封装进统一的 16KB 页面：存放目录项记录的页面称目录页，存放真实业务行数据的页面称数据页（User Data Page）。
    * 目录页内每个目录项记录含两个要素：所指向数据页中记录的**最小主键值**与目标数据页的**页号**；目录项记录之间通过记录头指针连成单向链表，始终按主键由小到大排列。
    * 单级目录页查找演算（查找 `C1 = 20`）：第一次磁盘 I/O 把根目录页（页 30）读入 Buffer Pool，在页内用 Page Directory 二分比对目录项主键范围，发现目标 20 处于区间 $[12, 209)$，锁定目录项 2 并取得页号 9；第二次磁盘 I/O 依据页号 9 把数据页载入内存，页内再经页目录槽位二分定位目标组，随后在组内单向链表微调比对命中完整行记录。
    * > 来源: P117

* **目录页与普通用户数据页的辨析**

    | 维度 | 普通用户数据页（User Data Page） | 目录项记录页（Directory Page） |
    | :--- | :--- | :--- |
    | 记录类型 `record_type` | `0`（普通用户记录） | `1`（B+ 树非叶子节点目录项记录） |
    | 承载数据内容 | 业务表的所有列（用户真实字段、事务 ID、回滚指针等） | 仅两列：下层子节点的最小主键值加子节点页号 |
    | 页目录（Page Directory） | 针对行记录划分槽位（Slot），支持二分快速定位 | 同样针对目录项划分槽位（Slot），支持二分快速定位 |
    | 页内组织方式 | 记录间单向链表，物理存储乱序，逻辑有序 | 记录间单向链表，物理存储乱序，逻辑有序 |
    | 页面占用空间 | 固定 16KB | 固定 16KB |

    * 两者在物理结构上没有本质区别，文件格式与头部规范完全一致，共同遵循通用数据页结构。
    * 每条记录头信息中都有占据 3 位的 `record_type`：`0` 为普通用户记录，`1` 为主键与页号组成的目录项记录，`2` 为 Infimum / Supremum 伪记录，`3` 为二级索引的特殊状态等。
    * > 来源: P117

* **多目录页扩展与 $O(M)$ 退化**
    * 极简假设：一个目录页最多存放 4 个目录项、每个数据页最多放 3 条用户记录；插入第 13 条记录时原有 4 个数据页全部存满，须开辟第 5 个数据页，而旧目录页槽位已满，必须申请新目录页（如页 32）容纳新目录项。
    * 多个目录页之间同样通过双向链表连接，逻辑上保证全表目录项从小到大全局有序。
    * 瓶颈：**Page Directory 只在单页内部有效，不能跨越物理页**，进入物理页之前无法预知目标键落在页 30 还是页 32；查 `C1 = 410` 须先加载页 30 比对首尾键值范围未命中，再沿双向链表加载页 32 二分命中子页号，最后第三次 I/O 加载真实数据页。
    * 若数据规模扩充到上百个目录页且目标位于最末尾，须把前面上百个目录页依次读取一遍，磁盘 I/O 复杂度退化为 $O(M)$（$M$ 为目录页总数）。
    * > 来源: P117

### 4.3 B+ 树层次的确立与容量测算

* **层级抽象与 B+ 树拓扑**
    * 只要平级目录页数量大于 1，就为其生成上一级顶层目录页；顶层目录页结构与下层完全相同，记录同样是目录项记录（`record_type = 1`），含所管辖目录页的最小主键值与下层目录页页号。
    * 层级命名约定：最底层存放真实业务数据的叶子节点为**第 0 层（Layer 0）**，紧邻其上的第一级目录项页为第 1 层，依此类推向上直到根节点（Root Page）。
    * 叶子节点（Leaf Nodes）：由所有第 0 层数据页构成，`record_type = 0`，包含完整业务行记录，节点之间通过双向链表互锁相邻关系，范围扫描（如 `BETWEEN ... AND ...`）只需在第 0 层顺链表移动而完全无需回溯上层树结构。
    * 非叶子节点（Non-Leaf Nodes）：由第 1 层及以上所有目录页构成，`record_type = 1`，仅记录路由所需主键分界值与子节点指针，坚决不存放任何真实用户数据；同层非叶子节点之间同样由双向链表连接。
    * 全局唯一根入口：无论下层如何分裂，整棵树始终维护一个固定的根节点页号，任何精确查找均由唯一根节点自顶向下发起，单次路径分支选择的时间复杂度被锁死为树的高度 $H$。
    * > 来源: P117

* **生产环境 B+ 树容量的量化模型**
    * 标准配置基准：数据页与目录页标准尺寸均为 $16\text{ KB} = 16{,}384\text{ Bytes}$；扣除页头（File Header、Page Header）、页尾（File Trailer）、系统记录（Infimum / Supremum）与页目录槽位等开销后，一页内真正可用于存储用户记录或目录项记录的有效空间约为 $15\text{ KB} \approx 15{,}360\text{ Bytes}$。
    * 叶子节点容量：假设平均单条记录长度取较保守的 $160\text{ Bytes}$，则 $N_{\text{leaf}} = 15{,}360 \div 160 \approx 96 \approx 100$ 条。
    * 非叶子节点容量：每个目录项含 `BIGINT` 主键 $8\text{ Bytes}$、页号 $4\text{ Bytes}$、记录头及内部编码开销约 $4\text{ Bytes}$，合计约 $16\text{ Bytes}$，则 $N_{\text{dir}} = 15{,}360 \div 16 \approx 960 \approx 1{,}000$ 个，扇出因子保守取 1,000。

    | 树层数 $H$ | 节点层级分布 | 支持的叶子节点数（数据页） | 理论最大行记录数 | 精确点查磁盘 I/O 上限 |
    | :---: | :--- | :--- | :--- | :---: |
    | 1 层 | 根节点（叶子） | 1 | 约 100 条 | 1 次 |
    | 2 层 | 根目录加叶子层 | 1,000 | 约 10 万条 | 2 次 |
    | 3 层 | 根目录加 1 层目录加叶子层 | 1,000,000 | 约 1 亿条 | 3 次 |
    | 4 层 | 根目录加 2 层目录加叶子层 | 1,000,000,000 | 约 1,000 亿条 | 4 次 |

    * 工程结论：大多数单表业务场景（百万级至千万级）仅需 3 层甚至 2 层 B+ 树；海量超大单表场景（亿级至千亿级）4 层深度足以承载。实际运行中根节点页常驻 Buffer Pool，第二层目录项页因高频访问也有极高内存命中率，因此支撑上亿数据的 3 层树做单条精确主键点查时真正需从物理磁盘发起的寻道 I/O 往往只有最后访问叶子节点的 **1 次**。
    * > 来源: P117

## 5. 聚簇索引、二级索引与联合索引

> **一句话主旨**：聚簇索引是数据本身的物理排布，二级索引以“索引列 + 主键”换取轻量，未覆盖字段查询必须回表重走聚簇树。

### 5.1 聚簇索引与主键约束

* **聚簇索引（Clustered Index）**
    * 它不是一种单独的索引类型，而是一种底层物理数据的存储方式；传统堆表把表数据与索引数据截然分开，InnoDB 中数据本身即按 B+ 树组织形式存放在物理磁盘上。
    * 叶子节点（第 0 层）每个数据页内存放的是完整业务行记录，既含建表定义的所有列（`C1`、`C2`、`C3` 等），也含 InnoDB 必须维护的隐藏列（`DB_ROW_ID`、`DB_TRX_ID` 事务 ID、`DB_ROLL_PTR` 回滚指针等）。
    * 物理文件一体化：每张表默认对应一个 `.ibd` 结尾的独立表空间文件，所有数据行与聚簇索引完全融合存储在其中；MyISAM 把数据拆为 `.MYD` 与 `.MYI`，其索引结构绝不直接挂载真实行数据，因此 MyISAM 根本不存在聚簇索引。
    * > 结论：所谓“聚簇”指表中的数据行与相邻的键值紧密聚簇在一起存放，索引就是数据、数据就是索引，两者高度统一。
    * > 来源: P118

* **自动构建机制与三层键值优先级**
    * 聚簇索引不需要也不能手动 `CREATE INDEX` 创建，InnoDB 在建表及数据写入第一时间自动构建。
    * 第一优先级：建表显式定义了 `PRIMARY KEY` 时，无条件使用主键列值作为键值构建聚簇索引树。
    * 第二优先级：没有定义主键时，InnoDB 由上至下扫描列定义，选取第一个定义为 `NOT NULL UNIQUE`（非空且唯一）的列替代主键构建聚簇索引。
    * 兜底方案：既无主键也无任何非空唯一索引时，底层自动为每一行添加名为 `DB_ROW_ID` 的 6 字节隐藏列，并以此为基准构建隐式聚簇索引。
    * > 易错点：一张物理表只能有且仅有一种物理排布顺序，因此**任何一张 InnoDB 表在底层有且仅能拥有一个聚簇索引**，不可能存在两个物理主键。
    * > 来源: P118

* **聚簇索引的优缺点与主键设计军规**
    * 优势一：点查性能极高，顺聚簇索引树自顶向下到达叶子节点后直接提取整行完整数据，无需发起二次寻址。
    * 优势二：范围查询与排序极快，叶子节点数据页由双向链表串联且页内记录按主键严格升序，执行 `WHERE id BETWEEN 10 AND 100` 或 `ORDER BY id` 时找到起点后沿双向链表向后线性遍历即可。
    * 写入效率依赖键值递增性：主键单调递增（如 `AUTO_INCREMENT`）时每次新增记录只需顺序追加在最后一个数据页末尾，当前页存满只需平滑申请一个新页挂载在末尾。
    * 乱序写入引发分裂风暴：采用无序字符串（UUID、MD5、随机哈希值）作主键时新记录主键随机散落在现有数据页中间，目标页已满时须执行页分裂——开辟新页、把旧页约一半数据物理挪移到新页、修改前后指针以及上层所有目录项页的记录，导致写入性能暴跌并产生严重磁盘空间碎片。
    * 主键更新的毁灭性代价：修改某条记录的主键值时，因聚簇索引严格按主键物理聚簇，引擎必须把该行从原数据页物理删除，再重新路由并插入到新的目标页。
    * > 提示：生产建表规范严禁使用无序 UUID 作主键，必须使用单调自增主键（递增整数或雪花算法 ID），根源正是为贴合 InnoDB 聚簇索引的物理写入特性。
    * > 来源: P118, P119

### 5.2 二级索引与回表

* **二级索引（Secondary Index）与回表（Bookmark Lookup）**
    * 二级索引又称辅助索引、非聚簇索引，同样是一棵标准 B+ 树、节点同样封装在 16KB 数据页中。
    * 叶子节点内容极度精简：**只记录当前索引列的值与该记录对应的主键值**（如 `(C2=2, C1=20)`、`(C2=3, C1=5)`、`(C2=4, C1=1)`），绝不放整行完整用户数据。
    * 排列基准变更：聚簇索引按主键列从小到大排序；`C2` 的二级索引树全流程按 `C2` 列值升序排列，`C2` 值相同时再依据主键 `C1` 大小做页内递增排序。
    * 非叶子节点目录项记录的是该子页中索引列 `C2` 的最小值以及对应的子页号。
    * > 定义：通过二级索引查找到对应的主键值后，再拿着主键值回到聚簇索引中重新进行自顶向下的树形检索以获取完整行记录的过程，称为**回表（Bookmark Lookup）**。
    * 回表全流程（`SELECT * FROM t_user WHERE C2 = 4;`）：第一步在 `C2` 二级索引树中由根节点（页 42）经目录页到叶子节点（页 35），命中记录项 `(C2=4,C1=1)`、`(C2=4,C1=4)`、`(C2=4,C1=10)`，此时仅拿到主键集合 `{1, 4, 10}` 而缺失 `C3` 等其他列；第二步拿主键 1、4、10 分别走聚簇索引树根命中聚簇叶子页提取完整行；最后组装全量数据返回客户端。
    * > 来源: P118

* **二级索引为什么不冗余完整数据**
    * 存储冗余灾难估算：一张 10 个字段、1,000 万条记录、全表数据约 10 GB 的表，若建 4 个二级索引且每个都冗余全量数据，物理净占用会膨胀到 $10\text{ GB} + 4 \times 10\text{ GB} = 50\text{ GB}$。
    * 写放大对比：执行 `UPDATE t_user SET C3 = 'new_value' WHERE C1 = 1;` 时，因 `C3` 未建二级索引，引擎只需在聚簇索引树中找到该行所在数据页直接修改 `C3` 值，`C2` 的二级索引树完全不受影响；若二级索引冗余了全量数据，则每次改 `C3` 都要把 4 个二级索引树的叶子节点全部同步改写一遍。
    * > 结论：二级索引“仅存主键值 + 索引列”的设计，是在存储成本、写入开销与点查效率之间达成的最优雅的工程妥协。
    * > 来源: P118

### 5.3 联合索引与三类索引对比

* **联合索引（Composite Index）**
    * > 结论：从底层存储机制看，**联合索引完全属于二级索引（非聚簇索引）的范畴**；InnoDB 只有聚簇索引与非聚簇索引两大阵营，不存在第三种物理形态。
    * 复合排序法则（如 `ALTER TABLE t_user ADD INDEX idx_c2_c3 (C2, C3);`）：先比较第一列 `C2`，`C2` 较小的记录一定排在前面；只有多条记录的 `C2` 取值完全相同时，才按 `C3` 列值从小到大排序；叶子节点每条记录末尾依然附带聚簇索引主键值 `C1` 用于回表与唯一性标识。
    * 非叶子节点目录项复合抽取：由于上层目录项用于下层路由划分，当两个分界节点 `C2` 值相同时，非叶子节点必须同时记录 `(C2, C3, 下层页号)` 复合键值才能精准引导二分分流。
    * 复合检索过程（`SELECT * FROM t_user WHERE C2 = 4 AND C3 = 'u';`）：顶层二分自根节点下行按首列缩小范围；进入 `C2 = 4` 分支后目录项展示下层页分界记录为 `C3 = 'o'` 与其他更大值，因 `'u' > 'o'` 瞬间排除左侧较小子页精准切入右侧子页；页内用 Page Directory 二分锁定记录 `(C2=4, C3='u', C1=10)`；取出主键 `C1 = 10` 回聚簇索引提取整行全部数据。
    * > 来源: P118

* **三类索引横向对比**

    | 维度 | 聚簇索引 | 单列二级索引 | 联合索引 |
    | :--- | :--- | :--- | :--- |
    | 物理归属 | 数据本身的物理存储方式 | 独立的非聚簇辅助 B+ 树 | 独立的非聚簇辅助 B+ 树 |
    | 单表数量上限 | 必须且仅有 1 个 | 允许创建多个 | 允许创建多个 |
    | 叶子节点承载内容 | 完整的业务行记录加隐藏列 | 索引列的值加主键值 | 所有被索引列的值加主键值 |
    | 创建时机 | 建表时自动创建，禁止手动操作 | 按需手动创建（`CREATE INDEX`） | 按需手动创建（`CREATE INDEX`） |
    | 排序准则 | 严格按主键递增 | 严格按单一索引字段递增 | 按字段从左至右逐级递增 |
    | 查询是否需回表 | 绝不需要，一步到位 | 查未覆盖字段时必须回表 | 查未覆盖字段时必须回表 |
    | DML 维护代价 | 极高（涉及全量数据页重构） | 适中（仅相关列变动时重构） | 稍高（多列联合维护开销） |

    * > 来源: P118

* **普通索引与唯一索引的性能差异**
    * 查找 `c2 = 10` 时，唯一索引因 `UNIQUE` 约束保证唯一，在数据页单向链表中找到 `c2 = 10` 即宣告完成，不需要再往后读指针；普通索引因字段允许重复，定位到第一条 `10` 后还须顺 `next_record` 再读下一条直到遇到大于 `10` 的值。
    * > 结论：磁盘读写最小单位是默认 16KB 的页，查询发生时含目标数据的数据页已完整加载到 Buffer Pool，内存中 CPU 多遍历一条甚至几条记录的开销仅在纳秒级别，相对磁盘 I/O 可忽略不计，两者几乎没有可感知差别。
    * > 来源: P125

### 5.4 InnoDB B+ 树的实现约束

* **根页面位置固定与自上而下的原位升格**
    * > 结论：InnoDB 中数据表的 B+ 树索引一旦建立，该索引的**根页面（Root Page）在磁盘上的物理位置（Page Number）终生固定不变**，此即“根页面位置万年不动”。
    * 初始阶段：创建表时在表空间中预先分配一个数据页作为该索引的根节点页面，整棵树只有这一个页，直接存储插入的真实用户数据，此时根节点同时扮演叶子节点。
    * 首次页满与下层分裂：根页面 16KB 耗尽时（简化场景单页只容 3 条记录，准备写第 4 条），引擎**不是**在旁边新建数据页再在上面建新根页，而是：另申请一个数据页（页 A）把根页面中已有的 3 条真实记录完整**复制**过去；针对即将插入的第 4 条记录再申请新数据页（页 B）并按主键顺序完成页分裂，把第 4 条记录放入页 B（若新记录主键介于老记录之间则在页 A 与页 B 之间做物理行迁移）；原根页面内部数据被清空，职能从“存储用户记录”原位升格为“存储目录项”，把指向页 A 与页 B 的最小主键及页号写入自身，升级为非叶子节点（内节点）。
    * 逐层向上生长：页 A、页 B 继续分裂使根页面目录项增加，根页面作为目录页再次填满时重复上述机制——新建两个内节点页面、把根页面所有目录项复制下去，原根页面再次原位升级为更高层级根目录。
    * 工程价值：数据字典只需记录该索引根页面的一个固定页号，查询引擎遍历该索引时永远直奔这个固定根页号切入，无需在树高裂变时动态修改元数据中的根入口地址。
    * > 来源: P119

* **内节点目录项唯一性与二级索引引入主键列**
    * 失效场景：表有 `c1`（主键）、`c2`、`c3` 三字段，在 `c2` 建单列二级索引，插入 `c1=1,c2=1`（页 4）、`c1=3,c2=1`（页 4）、`c1=5,c2=1`（页 5）、`c1=7,c2=1`（页 5）。若内节点仅由“索引列 + 下层页号”组成，两个目录项即为 `[c2=1, page=4]` 与 `[c2=1, page=5]`。
    * 分流歧义：再插入 `c1=9, c2=1, c3='C'` 时，新记录 `c2` 为 1 而内节点目录项 `c2` 也全为 1，剥掉页号后目录项之间完全无法区分谁大谁小，检索算法无法判断分给页 4 还是页 5。
    * > 易错点：绝不能把“子页页号”作为分流比较的有效依据；B+ 树路由只能依据有序键值做二分判定，不能依赖物理存储分配的页序号，否则数据页合并、移动或裂变时整个索引逻辑会全盘错乱。
    * 解决手段：B+ 树内节点中的目录项记录必须保证唯一性，为此**在二级索引的内节点目录项中强制引入主键列**，真实目录项由三部分复合构成：$\text{二级索引列值} + \text{主键列值} + \text{下层页号}$。
    * 消歧效果：插入 `c1=9, c2=1` 时内节点先比对 `c2`（都是 1，平局），再比对主键 `c1`，因 $9 > 5$ 毫无悬念走向页 5 分支。
    * > 结论：二级索引无论在叶子节点还是内节点，底层物理记录中均包含主键列；叶子节点存主键是为了回表，内节点存主键是为了保证目录项的全局唯一性与路由的确定性。
    * > 来源: P119

* **单数据页最少两条记录**
    * 硬性约束：一个数据页中至少要能够容纳 2 条记录。
    * 若单页容量极限只能存 1 条记录，则每个新记录都需申请新数据页，形成树形目录时每个父目录项也只能指向一个子节点，多路平衡树退化成细长的线性链表。
    * 退化后果：树高等同于数据记录数 $N$，查找复杂度从 $O(\log N)$ 恶化为 $O(N)$，每次查找都要经历 $N$ 次磁盘 I/O，索引机制彻底失去意义。
    * > 来源: P119

### 5.5 MyISAM 的索引方案

* **MyISAM 非聚簇索引与物理地址指针**
    * > 定义：MyISAM 引擎中**根本不存在聚簇索引**的概念；在 MyISAM 中建立的所有索引（无论主键索引还是普通二级索引）在架构分类上全部属于**非聚簇索引**。
    * 文件体系：8.0 下表结构存于 `.sdi`（5.7 为 `.frm`），数据存于 `emp3.MYD`（MYData），索引 B+ 树存于 `emp3.MYI`（MYIndex）。
    * 数据写入方式：新记录写入 MyISAM 表时引擎不关心键值顺序，直接按写入时间先后追加到 `.MYD` 文件末尾（类似堆表组织），即使字段定义了主键或手动指定值，`.MYD` 文件内部也**完全不做基于主键大小的物理排序**。
    * 叶子节点存储内容：按所建索引列的值由小到大严格排序，紧随键值之后的 `data` 域保存的既不是整行完整数据也不是主键 ID，而是该记录在 `.MYD` 数据文件中的**物理存储地址（文件内偏移量指针）**（例如 `[15 | 0x0000]`、`[18 | 0x00A0]`、`[20 | 0x00F0]`、`[30 | 0x0050]`）。
    * 主键索引与辅助索引平权：主键列 `c1` 上建索引时生成一棵 B+ 树、叶子排布 `c1` 值并指向 `.MYD` 物理地址；普通列 `c2` 上建辅助索引时同样生成结构完全相同的 B+ 树、叶子排布 `c2` 值并直接指向 `.MYD` 物理地址。
    * > 注意：官方文档与 `EXPLAIN` 等执行计划输出中常把索引类型统一标为 `BTREE`，**官方语境下的 BTREE 在底层实现上指的就是 B+ 树**，不是数据结构课本里的纯 B 树。MyISAM、InnoDB、Memory 都支持 B+ 树索引（Memory 默认 Hash，但也支持 B+ 树）。
    * > 来源: P119

* **InnoDB 与 MyISAM 索引实现对比**

    | 对比维度 | InnoDB | MyISAM |
    | :--- | :--- | :--- |
    | 聚簇索引 | 强制必须包含一个（索引即数据） | 完全没有，全表所有索引均为非聚簇索引 |
    | 文件组织形式 | 数据与索引合一（统一存于 `.ibd`） | 数据与索引分离（`.MYD` 存数据，`.MYI` 存索引） |
    | 主键依赖程度 | 必须有主键（未指定则自动隐式生成） | 可以完全没有主键 |
    | 主键索引叶子内容 | 包含整行完整的用户数据记录 | 仅包含主键列值与行记录在 `.MYD` 中的物理地址 |
    | 二级索引叶子内容 | 包含索引列值与对应的主键值 | 包含索引列值与行记录在 `.MYD` 中的物理地址 |
    | 回表操作特征 | 携带主键回到聚簇索引重新自顶向下遍历整棵 B+ 树 | 命中物理地址后直接按文件偏移量定位读取，速度极快 |

    * 回表链路对比：InnoDB 为“二级索引查找 → 叶子节点取主键 ID → 切换到聚簇索引 → 从聚簇根节点重新下潜遍历 → 取完整行”；MyISAM 为“任意索引查找 → 叶子节点取物理地址 → 物理偏移量直接读取 `.MYD` → 取完整行”。
    * 单次定位开销上 MyISAM 的指针寻址比 InnoDB 重新遍历一棵 3~4 层聚簇索引树更轻量迅速；但在高并发与复杂事务场景下，InnoDB 凭行级锁、MVCC 与聚簇索引的数据局部性缓存，综合吞吐量远非 MyISAM 可比。
    * > 来源: P119

* **主键设计的长度约束**
    * 因 InnoDB 所有二级索引的叶子节点与内节点目录项都必须存一份主键值，而数据页物理尺寸严格锁死在 16KB：主键占 8 字节（如 `BIGINT`）时一页可塞下数百上千个目录项或记录；主键长度达到 128 字节甚至更长时页内容纳的目录项数量急剧腰斩。
    * 单页扇出（Fan-out）锐减会强行撑高整棵 B+ 树，树高每增加一层查询遍历就多消耗一次随机磁盘 I/O，整体读写性能呈断崖式下跌且磁盘空间消耗成倍放大。
    * > 来源: P119

## 6. InnoDB 存储层次

> **一句话主旨**：页是磁盘与内存交互的基本单位，其上依次是区、段与表空间；页内靠页目录二分，页间靠双向链表串联。

### 6.1 页作为磁盘与内存交互的基本单位

* **页（Page）**
    * > 定义：InnoDB 中数据划分为若干“页”，**页是磁盘与内存交互的基本单位**；默认页大小 16KB，可用 `SHOW VARIABLES LIKE 'innodb_page_size';` 实测检验，返回值为 `16384`。
    * 跨数据库对比：SQL Server 页默认 8KB（恰好是 InnoDB 的一半）；Oracle 用“块（Block）”指代页，大小支持 2KB、4KB、8KB、16KB、32KB 乃至 64KB，均为 2 的整数倍阶梯，允许创建表空间时按业务特征灵活指定。
    * “基本单位”严格内涵：系统在执行特定维度操作时每一次进出的度量颗粒度必须是该单位的整数倍，绝不允许出现半个单位。类比生物体的基本结构单位是细胞（统计有机体必须由整数个细胞组成）、化学性质的基本单位是原子（须按整数颗参与反应）。
    * 双向 I/O 粒度：从磁盘读入内存时哪怕只读一条数据也必须把整整 16KB 的数据页作为完整单位全部装载进 Buffer Pool；内存脏页写回磁盘同样以页为单位成批刷新，刷盘量必须是 16KB 的整数倍。
    * > 来源: P121

* **页级刷盘的必要性**
    * 若仅改动页内一个 4 字节整型字段就只写回这 4 个字节，表面上单次写入量很小，但现实中数据库每秒可能在各数据行发生上万次细碎变动，每次变动都触发一次独立磁盘寻道写操作会把磁头拖垮，吞吐量暴跌几个数量级。
    * 空间局部性收益一（批量平摊）：把一段时间内落在同一页内的所有细碎修改在内存中合并，待时机成熟发起一次 16KB 的顺序或集中写盘，一次性持久化数十甚至上百条改动。
    * 空间局部性收益二（容灾兜底）：针对 16KB 写盘过程中断电导致只刷了 4KB 就中断的“页断裂”/部分写失效，MySQL 用 doublewrite buffer（双写缓冲区）以及 Redo Log、Undo Log 在底层兜底崩溃恢复与事务原子性。
    * > 来源: P121

### 6.2 页内链表、页目录与页间关系

* **页内记录单向链表**
    * 连接方式：记录之间不是紧密无缝的数组结构，而是通过每条记录记录头信息中的 `next_record` 指针串联成单向链表。
    * 排序依据：属于聚簇索引的页，页内记录链表严格按主键值从小到大递增排列；属于二级索引的页，先按索引列值递增排列，索引列值相同时再按包含的主键值递增排列。
    * 虚实边界：页内除真实业务记录外，InnoDB 硬性预装最小记录 `Infimum` 与最大记录 `Supremum` 两个虚拟边界记录，链表起点固定始于 `Infimum`、终点固定指向 `Supremum`。
    * 插入优势与检索劣势：两行之间插入只需修改前驱的 `next_record` 让其指向新节点、再让新节点指向后继，不必像定长数组那样平移后续成百上千条记录；但单向链表不支持下标随机寻址，找特定值只能从头顺指针逐个比对，复杂度为线性阶 $O(n)$。
    * > 来源: P121

* **页目录（Page Directory）**
    * 分组抽取：把页内所有紧密相连的记录划分成若干个组（Group）。
    * 提取槽位：把每组内最大的那条记录的物理地址偏移量提取出来，逆序存放在页尾部的页目录中，每个提取出的地址偏移量称为一个**槽（Slot）**。
    * 二分查找定位：页目录在内存中是连续排列的紧凑数组结构，各槽位代表的主键值严格升序，页内查找目标主键时直接在槽之间执行二分查找（Binary Search），复杂度由 $O(n)$ 降到 $O(\log_2 n)$。
    * 尾段扫描：二分锁定目标记录所在的具体槽位（某小组）后，进入仅含 4~8 条记录的微型单向链表做线性扫描，瞬时精准捕获目标行。
    * 无页目录的后果：若一个 16KB 页塞入 1000 条数据而只能沿单向链表从第 1 条硬比对到第 1000 条，即使 B+ 树在外部找到了页，页内开销也会拖垮整体查询效率。
    * > 来源: P121

* **页间双向链表与物理离散**
    * 数万个 16KB 数据页在物理磁盘文件的存储空间上**不一定**严格紧挨着连续存放，操作系统的文件分配机制很难随叫随到地划拨大片绝对物理连续的空闲空间，频繁增删后页与页之间往往是碎片。
    * InnoDB 在每个数据页头部的 File Header 中记录前驱页指针 `FIL_PAGE_PREV` 与后继页指针 `FIL_PAGE_NEXT`，把所有逻辑相邻的数据页串成双向链表。
    * 页 A 物理位置可能在文件前端、页 B 可能在文件末尾，凭页头指针逻辑扫描能顺畅跨越，这构成 B+ 树叶子节点之间横向遍历的物理基础。
    * > 来源: P121

### 6.3 行、区、段与碎片区

* **五层存储架构与各层职能**
    * 行（Row）：业务真实数据的载体，除自定义业务列（`id`、`name`、`age` 等）外还包含 InnoDB 强行注入的内部系统列（事务 ID 列 `DB_TRX_ID`、回滚指针列 `DB_ROLL_PTR`、隐式主键列 `DB_ROW_ID`）以及行记录头信息（变长字段长度列表、NULL 值列表、删除标记、记录下潜指针等）；行内部具体组织方式即“行格式（Row Format）”。
    * 页（Page）：磁盘与内存进行数据交换的最基础单位，默认尺寸恒定 16KB，一页内可容纳多条甚至数百条行记录。
    * 区（Extent）：**在默认 16KB 页大小的配置下，1 个区在物理磁盘上强行连续占据 64 个页**，即 $64 \times 16\text{ KB} = 1024\text{ KB} = 1\text{ MB}$；表数据量大时 InnoDB 不再零敲碎打申请单页，而是直接以 1MB 整区为单位申请连续空间，64 个页在磁盘物理柱面上连续排列，顺序 I/O 远快于随机寻道。
    * 段（Segment）：数据库对象的空间分配单位，是一个逻辑管理单位而非物理上死板连续切出的空间区域。数据段（叶子节点段）挂载 B+ 树底部的所有叶子节点；索引段（非叶子节点段）挂载非叶子节点的目录项页与区；回滚段（Rollback Segment）管理事务撤销日志（Undo Log）所占存储空间。
    * 表空间（Tablespace）：整个存储结构的最顶层抽象，直接映射到操作系统文件层面的最高级别物理文件容器，内部由若干段、区、页组成。
    * > 提示：若叶子节点与非叶子节点的页混在一起胡乱分配，做大范围扫描（如 `WHERE id BETWEEN 100 AND 100000`）时磁头在读取叶子节点区时会冷不防撞上夹杂中间的目录项页，造成连续物理顺序断裂与震荡；隔离成独立的段可保证叶子节点段内尽可能以连续的区推进，最大化顺序读写优势。
    * > 来源: P121

* **随机 I/O 与顺序 I/O 的代价鸿沟**
    * 范围查询 `SELECT * FROM t WHERE c1 BETWEEN 5 AND 300;` 涉及的数据分散在 3 个不同数据页，页间逻辑上虽由双向链表相连，但在物理扇区上可能相距极远。
    * 随机读取单个页平均约 **10 毫秒**，内部解构为：约 6 毫秒耗费在机械磁头物理寻道时间（Seek Time）与盘片半圈旋转延迟（Rotational Latency）、约 3 毫秒耗费在操作系统与磁盘控制器的队列等待时间、真正把 16KB 传输到缓冲池仅占 **1 毫秒**，即随机 I/O 下 90% 时间空耗在定位物理扇区的机械动作上。
    * 顺序读取：假设普通磁盘顺序吞吐为 $40\text{ MB/s}$，1 秒内可顺序读取 $\frac{40 \times 1024}{16} = 2560$ 个 16KB 页面，读取单个连续页平均耗时约 $\frac{1000}{2560} \approx 0.39 \approx 0.4$ 毫秒。
    * > 结论：随机 I/O 读一页 10ms、顺序 I/O 平均读一页 0.4ms，性能差距高达 **25 倍**；底层核心优化诉求是尽可能让逻辑上相邻的数据页在物理磁盘空间中也连续存储。
    * > 来源: P127

* **段与混杂灾难**
    * 若仅按区为单位向 B+ 树分配空间，一个区内的 64 个页面不可避免混杂存放叶子节点页与目录项页。
    * 混杂后果：真正的数据页被稀释、单个区能容纳的有效数据行急剧减少；扫描数据链表时无法一次性按顺序块流式拉取，必须在物理扇区上不断跳过中间目录页，顺序 I/O 被打断退化为局部随机 I/O；本区数据页过早读完导致引擎频繁跨区寻找下一个数据页，彻底丧失区设计的初衷。
    * > 定义：段并不是一个物理上连续的磁盘空间，而是一个**具有特定存储业务属性的“逻辑集合”**，负责统筹并专有占有一组区，确保不同业务性质的页面绝不混杂在同一个物理区中。
    * > 来源: P127

* **碎片区（Fragment Extent）与阶梯式分配**
    * 引入由头：区的最小分配单位是 1MB，而一棵 B+ 树索引为隔离叶子和非叶子节点必须同时建立数据段与索引段；若空表也按整区分配，数据段 1 个区只用 1 页闲置 63 页、索引段 1 个区只用 1 个根节点页闲置 63 页，建一张空表就平白吞噬 **2MB** 磁盘空间，数百张轻量级字典表时浪费不可接受。
    * 碎片区规格：物理尺寸依然是完整的区（64 个页、1MB），但区内的页面**不再专属于某一个特定的段**，而是充当公共资源池——段 A 可从中申请 1 个页面放数据，段 B 也可从中申请 1 个页面放目录项，实现多个段“拼单”共享。
    * 管理归属：碎片区不属于任何段，它直接隶属于顶层的表空间（Tablespace）统一调度管辖。
    * 阶梯式分配算法第一段（零散拼单阶段）：刚插入数据时段不申请整区，由表空间在碎片区中划拨单个零散页面（Free Page）供该段使用。
    * 阶梯式分配算法第二段（专属独立阶段）：当一个段在碎片区中累计占用的零散页面达到 **32 个页面（即 512KB）** 时，InnoDB 判定该段已具规模化特征，此后不再使用碎片区，而是直接向表空间申请**专属区（Dedicated Extent）**，每次独占申请 1 个或多个完整的 1MB 物理连续区。
    * > 定义修正：在物理本质上，一个段是由“若干零散的碎片页面”加上“若干专属完整的物理区”共同构建而成的。
    * > 来源: P127

* **区的四种物理状态**

    | 区的状态类型 | 状态名称标识 | 归属管理主体 | 物理状态与功能定位 |
    | :--- | :--- | :--- | :--- |
    | 空闲区 | `FREE` | 表空间直接管理 | 该区内的 64 个页面均处于完全未分配状态 |
    | 有空闲页的碎片区 | `FREE_FRAG` | 表空间直接管理 | 碎片区，部分页面已被某些段借用，尚有剩余页面可供分配 |
    | 满载的碎片区 | `FULL_FRAG` | 表空间直接管理 | 碎片区，区内 64 个页面已被各个段瓜分借用完毕，无可用余量 |
    | 附属于段的专属区 | `FSEG` | 专属的段直接管理 | 该区所有 64 个页面全量专属于某一个特定的段（如专属数据段） |

    * 四种状态对应“军管师、师管团”的编制关系：附属于段的专属区 `FSEG` 隶属于段；`FREE`、`FREE_FRAG`、`FULL_FRAG` 三种状态的碎片区不划归任何单一师级编制，直接由表空间统筹调配。
    * > 来源: P127

### 6.4 表空间形态与系统内部表

* **系统表空间与独立表空间**

    | 表空间形态 | 代表物理文件 | 历史默认版本 | 存储管理特征与优缺点 |
    | :--- | :--- | :--- | :--- |
    | 系统表空间（System Tablespace） | `ibdata1`（位于 `/var/lib/mysql` 数据目录） | MySQL 5.5.7 至 5.6.6 之前默认开启 | 全局所有数据库的所有表数据、索引、系统元数据统统混合塞入单一 `ibdata1`；单文件极度膨胀，即便 `DROP TABLE` 删掉几百张表，由于操作系统文件空洞机制，`ibdata1` 磁盘物理体积也无法自动回缩收缩，极易把磁盘撑爆 |
    | 独立表空间（File-Per-Table Tablespace） | 独立的 `表名.ibd`（位于各数据库子目录下） | MySQL 5.6.6 及以上版本（含主流 5.7 与 8.0）默认开启 | 每张独立数据表在其数据库文件夹下拥有以表名命名的专属 `.ibd` 文件；执行 `DROP TABLE` 或 `TRUNCATE TABLE` 时对应 `.ibd` 被操作系统直接删除，瞬时释放物理空间，备份、迁移与排查极为便捷 |

    * 参数验证：`SHOW VARIABLES LIKE 'innodb_file_per_table';` 默认返回 `ON`，只要维持默认值，创建的任何表都会以独立 `.ibd` 文件存在于磁盘。
    * 独立表空间三项优势：便捷的数据迁移（单表数据与索引收敛在一个 `.ibd` 内，可通过冷拷贝或传输表空间实现跨实例迁移）；高效的空间回收（独立表空间下 `DROP TABLE` 直接在操作系统层面删除 `.ibd`，而共享表空间删表后 `ibdata1` 体积并不缩减）；低侵入的碎片重组（执行 `ALTER TABLE t ENGINE = InnoDB;` 通过重建表生成全新的紧凑 `.ibd` 并原子替换旧文件，快速把碎片空间回退给操作系统且对其他业务表毫无干扰）。
    * > 来源: P121, P127

* **初始空表的物理尺寸差异**
    * MySQL 5.7 环境：创建 `CREATE TABLE temp (id INT, name VARCHAR(15));` 后 `temp.ibd` 初始物理大小为 **98304 字节**，即 $\frac{98304}{1024} = 96\text{ KB}$、$\frac{96}{16} = 6$ 个页面。
    * MySQL 8.0 环境：相同建表语句产生的 `temp.ibd` 初始物理大小变为 **114688 字节**，即 $\frac{114688}{1024} = 112\text{ KB}$、$\frac{112}{16} = 7$ 个页面。
    * 5.7 的 6 个页面为 InnoDB 独立表空间初始预留的管理页面：FSP_HDR 表空间头部信息页、IBUF_BITMAP 插入缓冲位图页、INODE 节点管理页等。
    * > 提示：8.0 默认多出的 1 个页面（16KB）用于存储该表自身的字典元数据定义——5.7 及更早版本把表结构元数据单独保存在 `.frm` 文件中，8.0 彻底废弃 `.frm` 并引入统一的数据字典（Data Dictionary），把序列化的表结构字典信息（SDI，Serialized Dictionary Information）直接内嵌到表本身的 `.ibd` 内部。
    * > 来源: P127

* **元数据校验链路与四张内部表**
    * 执行 `INSERT INTO t VALUES (1, 'abc');` 时底层须驱动系统表空间完成校验闭环：检查目标表 `t` 是否真实存在于数据字典中；校验传入字段值（列数、类型、长度、非空约束）是否与元数据定义严格吻合；定位目标根页面（查询目标表聚簇索引以及所有二级索引的根节点页面位于哪个表空间的哪个物理页）；把记录插入聚簇索引 B+ 树对应页面并同步维护各二级索引的树状结构。
    * 支撑数据库运转的核心基础数据（表空间编号、列定义、索引根页面等）统称为元数据（Metadata），由系统表空间内部四张核心系统表持久化维护。

    | 系统内部表名 | 存储的核心元数据信息 |
    | :--- | :--- |
    | `SYS_TABLES` | 记录实例中所有表的元数据：表 ID、表名、所属表空间的 Space ID、列数量等 |
    | `SYS_COLUMNS` | 记录每个表中每一列的元数据：列所属表 ID、列物理排布序号、列名、数据类型等 |
    | `SYS_INDEXES` | 记录每个索引的元数据：索引 ID、所属表 ID、索引名称、索引类型、B+ 树根节点页号 |
    | `SYS_FIELDS` | 记录每个索引所涵盖的字段定义及字段在索引内的前缀长度与排序规则 |

    * > 提示：普通用户与开发人员无法直接通过 SQL 读写上述四张底层 `SYS_*` 内部表；MySQL 在 `information_schema` 库中封装了以 `INNODB_SYS_*`（或 8.0 中的系统视图）为前缀的只读视图（如 `INNODB_SYS_TABLES`、`INNODB_SYS_INDEXES`），作为内部系统表的数据镜像与对外透出接口。
    * > 来源: P127

## 7. 数据页结构与行格式

> **一句话主旨**：16KB 页由七大区域构成，File Header 与 File Trailer 构成首尾校验；行格式则决定额外信息与真实数据在字节层面的排布。

### 7.1 页类型与七大区域

* **页的类型划分**
    * “页”在 InnoDB 中是通用空间规格，并非只有存放数据行的一种。
    * 索引页 / 数据页（`FIL_PAGE_INDEX`）：存放 B+ 树节点；聚簇索引叶子节点存放完整用户数据行、非叶子节点存放目录项；二级索引叶子节点存放索引列和主键。逻辑上常区分的“目录页”与“数据页”在物理类型上统称为索引页。
    * Undo 日志页（`FIL_PAGE_UNDO_LOG`）：存放事务撤销日志，用于支持事务原子性回滚以及 MVCC 的数据版本快照链。
    * 系统页（`FIL_PAGE_TYPE_SYS`）：存放系统管理信息与数据字典元数据。
    * 事务数据页（`FIL_PAGE_TRX_SYS`）：存放事务系统的全局状态与控制信息。
    * 无论承担何种上层业务，只要是 InnoDB 管理的页，底层物理尺寸默认一律为 16KB，基础框架遵循高度标准化的结构布局。
    * > 来源: P122

* **数据页七大功能区域**

    | 序号 | 区域名称 | 英文标识 | 占用空间 | 核心职能说明 |
    | :---: | :--- | :--- | :--- | :--- |
    | 1 | 文件头部 | `File Header` | 38 字节 | 记录该页通用元数据，包括当前页号、双向链表前后指针、校验和、最后修改 LSN 等，所有类型页均包含 |
    | 2 | 页头部 | `Page Header` | 56 字节 | 数据页（索引页）专有的状态信息，记录页内记录数量、槽位数量、空闲链表偏移量等统计属性 |
    | 3 | 虚拟边界记录 | `Infimum + Supremum` | 26 字节 | 系统自动生成的虚拟哨兵记录，Infimum 代表比本页任何主键都小的下界，Supremum 代表比本页任何主键都大的上界 |
    | 4 | 用户记录 | `User Records` | 动态大小 | 存放业务实际插入的数据行记录，记录之间通过单向链表串联 |
    | 5 | 空闲空间 | `Free Space` | 动态大小 | 页内未被使用的连续物理空洞，新插入记录时从该区域切取空间 |
    | 6 | 页目录 | `Page Directory` | 动态大小 | 将页内记录分组后提取各组最大记录偏移量、逆序存放构成的槽数组，支持 $O(\log_2 n)$ 折半查找 |
    | 7 | 文件尾部 | `File Trailer` | 8 字节 | 存放前 4 字节校验和与后 4 字节 LSN 镜像，配合文件头部检测刷盘过程中是否发生部分写断裂 |

    * 三大逻辑模块重组：首尾协同与物理安全（`File Header` + `File Trailer`，头部定义页是谁、属于哪种类型、前后邻居是谁，尾部 8 字节作为头部的影子检测刷盘是否成功）；记录存储与空间流转（`Infimum/Supremum` + `User Records` + `Free Space`，围绕数据如何在页内安置，插入时空闲空间被压缩、用户记录链表被加长、首尾始终卡在两个哨兵之间）；页内状态与高速检索（`Page Header` + `Page Directory`，前者是运行状态仪表盘，后者是基于仪表盘构建的二分检索加速引擎）。
    * > 来源: P122

### 7.2 文件头部与文件尾部

* **File Header 的 38 字节字段**

    | 字段名称 | 字节大小 | 核心用途与职能 |
    | :--- | :--- | :--- |
    | `FIL_PAGE_SPACE_OR_CHKSUM` | 4 字节 | 页的校验和（Checksum） |
    | `FIL_PAGE_OFFSET` | 4 字节 | 当前页的唯一页号（Page Number） |
    | `FIL_PAGE_PREV` | 4 字节 | 上一个数据页的页号（双向链表前驱指针） |
    | `FIL_PAGE_NEXT` | 4 字节 | 下一个数据页的页号（双向链表后继指针） |
    | `FIL_PAGE_LSN` | 8 字节 | 页面最后被修改时对应的日志序列号（LSN） |
    | `FIL_PAGE_TYPE` | 2 字节 | 当前页面的具体功能类型（如索引页、Undo 页等） |
    | `FIL_PAGE_FILE_FLUSH_LSN` | 8 字节 | 仅在系统表空间首页中使用，记录独立刷盘检验点 |
    | `FIL_PAGE_ARCH_LOG_NO_OR_SPACE_ID` | 4 字节 | 当前页所属的表空间 ID（Space ID） |

    * `FIL_PAGE_OFFSET` 记录当前页在整个表空间内的唯一页号，只需将页号乘以 16KB 即可算出该页在物理磁盘文件中的绝对字节偏移量：$\text{Physical File Offset} = \text{FIL\_PAGE\_OFFSET} \times 16384$。
    * `FIL_PAGE_TYPE` 常见取值：`FIL_PAGE_INDEX` 数值通常为 `0x45BF`（B+ 树索引页）；`FIL_PAGE_UNDO_LOG`（Undo 日志页）；`FIL_PAGE_TYPE_SYS`（系统管理页）；`FIL_PAGE_INODE`（管理段分配的索引节点页）。引擎从磁盘读入 16KB 内存块后先读这 2 个字节，立刻判定后续内容按哪种内部协议解析。
    * `FIL_PAGE_PREV` 与 `FIL_PAGE_NEXT` 各占 4 字节，正是依赖这两个页号指针，物理磁盘上零散分布的数据页被串成严密有序的双向链表，这也是 `WHERE id >= 100 AND id <= 500` 这类区间范围查找的底层支撑——定位到主键为 100 的叶子页后，后续扫描只需顺当前页 `FIL_PAGE_NEXT` 向右推进，无需回退根节点重新寻道。
    * > 来源: P122

* **File Trailer 与页断裂捕获**
    * 校验和（Checksum）思想：对数十万字节的庞大字节串设计一套数学算法（如 CRC32、Adler32 或哈希函数）输出一个短小固定的数值（如 4 字节整型）；特性是两个数据块校验和不相等则必然不相同，且块内哪怕仅一个 bit 被篡改或丢包校验和都会显著剧变。
    * 部分写失效（Partial Page Write，俗称“页断裂”）成因：操作系统底层 I/O 调度与物理磁盘驱动器（HDD 扇区通常 512 字节或 4KB、现代 SSD 的 Page 通常 4KB/8KB）并不能保证对整整 16KB 写入的原子性硬件保障；刷盘从页头顺序向后推进，刚写完文件头部、数据部分才刷 4KB 时断电或内核崩溃，写操作在物理中途被腰斩，磁盘上该页前半段是新数据、后半段是旧数据。
    * File Trailer 结构：固定占用 **8 个字节**，前 4 字节存储当前页计算得出的校验和（与 File Header 中的 `FIL_PAGE_SPACE_OR_CHKSUM` 呼应），后 4 字节存储当前页最后修改时 `LSN` 的低 4 位（与 File Header 中的 `FIL_PAGE_LSN` 形成版本映射）。
    * 正常刷盘状态流转：初始稳态时头尾 Checksum 均为 `123`；页读入内存经事务更新后重新计算校验和设为 `256`，InnoDB 把 File Header 与 File Trailer 的 Checksum 同时置换为 `256`；顺序刷盘顺利结束后磁盘上该页头尾均为 `256`，代表此次 16KB 写入是完整成功的原子性落盘。
    * 断裂捕获：刷盘刚覆盖头部（Header 变为 `256`）时断电，页面最底部的 File Trailer 根本来不及被触碰、值仍为历史版本 `123`；实例重启比对 `256 != 123`，立刻断定该数据页最后一次落盘遭遇非正常中断，属于破损页绝不能投入生产运行。
    * 容灾修复两条路径：方案一（Redo Log 重做前滚）——若事务提交时 Redo Log 已完整写入磁盘日志（WAL 机制）且通过 Doublewrite Buffer 找回了该页刷盘前的完整镜像，先还原干净旧页，再按 Redo Log 记录重新执行物理前滚，最终把尾部 Checksum 也刷新为 `256`；方案二（Undo Log 事务回滚）——若断裂页涉及的事务尚未提交或系统判定无法安全重做，利用 Undo Log 记录的逆向逻辑把已部分写入的修改彻底撤销，使页面回滚恢复到首尾均为 `123` 的状态。
    * > 来源: P122

### 7.3 记录头信息与虚拟边界记录

* **记录头信息（Record Header）的 5 字节位域**

    | 字段名称 | 占用空间 | 取值含义与技术规范 |
    | :--- | :---: | :--- |
    | 预留位 1 与 2 | 各 1 bit | 预留标志位，当前版本暂未使用，固定置为 0 |
    | `delete_mask` | 1 bit | 逻辑删除标记，`0` 表示记录有效，`1` 表示已被逻辑删除 |
    | `min_rec_mask` | 1 bit | B+ 树非叶子节点最小目录项标记，为 `1` 表示该记录是某层非叶子节点中主键最小的目录项记录，普通数据行一律为 `0` |
    | `n_owned` | 4 bit | 当前记录拥有的记录数，服务页目录：组长记录在此记录本组记录总数，非组长记录固定为 `0` |
    | `heap_no` | 13 bit | 堆编号，当前记录在页的堆存储空间中的相对物理排布顺序编号 |
    | `record_type` | 3 bit | 记录类型：`0` 普通用户记录，`1` B+ 树非叶子节点目录项记录，`2` Infimum 虚拟最小记录，`3` Supremum 虚拟最大记录 |
    | `next_record` | 16 bit | 下条记录相对偏移量，从当前记录真实数据起始地址到下一条记录真实数据起始地址的字节相对偏移量 |

    * 位域衔接顺序（共 40 bit）：预留 1（1 bit）、预留 2（1 bit）、`delete_mask`（1 bit）、`min_rec_mask`（1 bit）、`n_owned`（4 bit）、`heap_no`（13 bit）、`record_type`（3 bit）、`next_record`（16 bit）。
    * 观测实验表：`CREATE TABLE page_demo(c1 INT, c2 INT, c3 VARCHAR(10000), PRIMARY KEY (c1)) CHARSET=ascii ROW_FORMAT=Compact;` 并插入 `(1,100,'aaaa')`、`(2,200,'bbbb')`、`(3,300,'cccc')`、`(4,400,'dddd')`；字符集指定 `ascii` 使一个英文字符严格对应 1 个字节便于推算物理开销。
    * > 来源: P123

* **`heap_no` 与 `next_record` 的真相**
    * 插入 4 条记录后底层打印的 `heap_no` 依次为：`c1=1` 得 2、`c1=2` 得 3、`c1=3` 得 4、`c1=4` 得 5。
    * > 结论：编号 `0` 和 `1` 并没有丢失，而是被 MySQL 强制分派给了引擎内部维护的两条**虚拟伪记录（Pseudo Records）**——`Infimum` 与 `Supremum`。
    * `next_record` 占 16 bit（2 字节）采用有符号整数表示，存储的绝不是物理内存的绝对指针地址，而是**相对位置偏移量（Relative Offset）**，基准点是当前记录的“真实数据起始位置”（记录头与真实数据列的交界处）；`next_record = 32` 意为从当前记录真实数据第一个字节起向后数 32 个字节即下一条记录的真实数据起始位置。
    * 正负指向规则：下一条逻辑有序记录在物理位置上排在当前记录后面时 `next_record` 为**正数**；经过多次插入与删除后若下一条逻辑有序记录在物理位置上被分配到当前记录前面，`next_record` 就会成为**负数**。
    * 相对偏移量设计的价值：数据记录无论被加载到内存缓冲区的哪一个物理地址段，都不需要逐一重定位和修改指针，极大提升页在内存与磁盘间置换的性能。
    * > 易错点：多条记录的 `next_record` 字段可能显示相同的正数值（例如都为 `32`），这并不代表它们死板指向内存中同一个绝对地址，而是各自相对于自身真实数据起点的字节距离恰好相同。
    * > 来源: P123

* **Infimum 与 Supremum 虚拟边界记录**
    * 数学内涵：`Infimum` 表示集合的**下确界**（小于等于集合中一切元素的最大下界），`Supremum` 表示集合的**上确界**（大于等于集合中一切元素的最紧上界）。
    * 引擎语义：`Infimum` 记录逻辑上比当前数据页中任何用户自定义主键都小的绝对最小值，`Supremum` 记录逻辑上比任何用户自定义主键都大的绝对最大值；无论插入多小（整型极小值或负数）或多大的主键，逻辑大小都必须严格夹在两者之间。
    * 物理位置与总量：位于 `Page Header` 之后、`User Records` 之前，合计固定占用 **26 个字节**，每条虚拟记录各占 **13 个字节**。
    * 单条结构：前 5 个字节为标准记录头信息，后 8 个字节为固定字符常量。`Infimum` 的 `record_type = 2`、`heap_no = 0`，数据部分填充字符串 `"infimum\0"`；`Supremum` 的 `record_type = 3`、`heap_no = 1`，数据部分填充字符串 `"supremum"`。
    * > 来源: P123

* **记录链表的全生命周期流转**
    * 阶段一（初始稳态链路）：逻辑链表始终从 `Infimum` 出发，`Infimum` 的 `next_record` 精准指向页内主键最小的真实记录 `Row 1`；用户记录内部顺次向后指引，呈现严格的物理与逻辑双重递增；最大的用户记录 `Row 4` 的 `next_record` 指向 `Supremum`；`Supremum` 作为终点哨兵其 `next_record` 为 0 终止遍历。
    * 阶段二（删除主键为 2 的记录）：`Row 2` 记录头中 `delete_mask` 由 `0` 翻转为 `1`，物理数据原封不动停留在原处；前驱 `Row 1` 的 `next_record` 被重新计算并改写，直接跳过 `Row 2` 精准指向 `Row 3`；后续正常查询沿 `Infimum` 顺藤摸瓜时不会再访问到 `Row 2`；`Row 2` 的 `next_record` 被重新指向页内垃圾链表表头，占用空间变成可重用空间；负责监控该槽的组长记录（即 `Supremum`）的 `n_owned` 自动由 `5` 调减为 `4`。
    * 阶段三（重新插回主键 2）：InnoDB 在页内垃圾链表中检索到原先释放的空闲槽位且容量完全吻合；直接把新列值写入该物理区域并把 `delete_mask` 由 `1` 恢复为 `0`；修改 `Row 1` 的 `next_record` 指向复活后的 `Row 2`，同时设置 `Row 2` 的 `next_record` 指向 `Row 3`；`Supremum` 的 `n_owned` 由 `4` 递增恢复为 `5`。
    * > 易错点：删除记录时误以为 InnoDB 会立刻清空磁盘字节并把后续记录整体前移填洞，这种做法会触发昂贵的内存块批量搬运、CPU 缓存频繁失效与磁盘碎片重组，完全违背高性能存储引擎的设计准则。
    * > 来源: P123, P124

### 7.4 页目录槽位机制

* **页目录的分组规则**
    * 成员纳管边界：必须纳入分组的包含系统虚拟记录 `Infimum` 与 `Supremum`；已被打上删除标记（`delete_mask = 1`）的失效记录绝对排除在外，绝不允许计入任何分组。
    * 第一组的绝对特殊性：第一组固定且唯一归属于虚拟最小记录 `Infimum`，该组有且仅有 1 条记录，即 `Infimum` 自成一组。
    * 最后一组的动态边界：最后一组必定包含虚拟最大记录 `Supremum`，该组允许容纳的记录条数范围为 **1 到 8 条**。
    * 中间其余各组的标准规格：处于中间的正常数据分组，记录条数严格限定在 **4 到 8 条** 之间。
    * 槽板示例对照：`Slot 0` 对应第一组（固定仅 Infimum，组长为 Infimum 记录，`n_owned = 1`）；`Slot 1` 对应中间组（如含记录 1,2,3,4，组长为记录 4，`n_owned = 4`）；`Slot 2` 对应中间组（如含记录 5,6,7,8，组长为记录 8，`n_owned = 4`）；`Slot 3` 对应最后一组（含记录 9 及 Supremum，组长为 Supremum，`n_owned = 5`）。
    * 槽的物理规格：每个槽（Slot）固定占用 **2 个字节**，存放该组组长记录在页内的相对地址偏移量；槽与槽在物理上逆序从页底向上紧挨着存放，因此在内存中可直接视为一个支持下标随机访问的连续数组。
    * > 定义：在一个分组中主键最大的那条记录被称为“组长”；**只有组长记录的 5 字节记录头中 `n_owned` 字段才会记录当前组内实际拥有的记录总数，该组内其余所有普通成员的 `n_owned` 统统强制置为 0**。
    * > 来源: P124

* **不建全量稠密目录的原因**
    * 稠密索引代价：尤其在二级索引场景下叶子节点页内只存索引列与主键，单条记录物理体积可能只有十几个字节，一个 16KB 页内轻松容纳一两千条记录；若对每条记录都硬性抽取主键建立目录项，目录本身就会吃掉数百甚至数千字节的宝贵空间，相当于在页内近乎完整复制了一份用户记录。
    * 工程解法是分组稀疏索引（Sparse Index）：将页内所有记录切分为若干小组，每组只挑选主键最大的“组长记录”，把组长的相对地址偏移量提取出来按顺序存入页底部数组。
    * 方案对比：顺序扫描顺 `Infimum` 的 `next_record` 沿单向链表逐条比对主键，复杂度线性 $O(n)$，单页记录繁多时 CPU 周期被大量无意义的指针跳转与缓存未命中消耗殆尽；折半二分查找针对有序序列复杂度为对数阶 $O(\log_2 n)$。
    * > 来源: P124

* **分组分裂机制与槽位演进**
    * 初始状态（两极双槽）：全新空数据页中只有 `Infimum` 和 `Supremum` 两条虚拟记录，系统只有 2 个槽——`Slot 0` 指向 `Infimum` 且 `n_owned = 1`，`Slot 1` 指向 `Supremum` 且 `n_owned = 1`。
    * 持续插入（最后一组膨胀）：依次插入主键 1、2、3、4 时，`Infimum` 组规格被锁死为 1 不可扩张；新记录全部顺延划入包含 `Supremum` 的最后一组；`Supremum` 依然是该组主键最大记录；`Supremum` 的 `n_owned` 随每条新记录加入单调递增，插入第 4 条真实记录后 `n_owned = 5`（含 4 条真实记录加 1 条 Supremum）。
    * 触达阈值（分组裂变与新槽诞生）：最后一组总记录数达到 **8 条**时容量达法定上限；再写入第 9 条记录时当前组记录数达到 9 条突破“组内最多 8 条”铁律；InnoDB 强制把 9 条拆成两个独立小组——提取前半段较小的 **4 条记录**独立切为全新中间组并让第 4 条记录担任新组组长、其 `n_owned` 置为 `4`，剩下的 **5 条记录**（后 4 条较大记录加 Supremum）保留在原最后一组且 `Supremum` 的 `n_owned` 调整为 `5`；同时在页目录中开辟一个新槽位写入新中间组组长的相对偏移量。
    * 成熟分布格局：随着数据规模膨胀，页内小组通常呈现规整的 `1（Infimum组）, 4, 4, 4, ..., 5~8（Supremum组）` 分布。
    * > 来源: P124

* **基于页目录的二分查找全流程**
    * 样例页：包含 18 条记录、划分为 5 个槽位（`Slot 0` 至 `Slot 4`）——`Slot 0`（Infimum，`n_owned=1`）、`Slot 1`（组长 PK=4，`n_owned=4`）、`Slot 2`（组长 PK=8，`n_owned=4`）、`Slot 3`（组长 PK=12，`n_owned=4`）、`Slot 4`（Supremum，`n_owned=5`）。
    * 第一阶段（槽位数组二分）：设初始区间 `low = 0`、`high = 4`；计算中点 $\text{mid} = \frac{0+4}{2} = 2$，通过 `Slot 2` 偏移量寻址到该组组长并取出主键 `8`；因目标 `target = 6` 满足 $6 < 8$，收缩高端边界为 `high = mid = 2`；重新计算 $\text{mid} = \frac{0+2}{2} = 1$，读取 `Slot 1` 组长主键 `4`；因 $6 > 4$ 收缩低端边界为 `low = mid = 1`；此时 `high - low = 1`，二分把目标范围锁定在 `Slot 1` 组长与 `Slot 2` 组长之间，目标主键必定归属于 `Slot 2` 所管辖的小组。
    * 第二阶段（逆向单链表切入技巧）：`Slot 2` 存的偏移量指向该组**最大记录（组长）**，而页内记录链表是单向链表只能从小到大向后遍历、无法从组长向前回溯。InnoDB 的核心绝技是**借道上一个槽（`Slot 1`）的组长记录**：直接通过 `Slot 1` 找到上一组组长（主键 4 的记录），顺着它的 `next_record` 向前踏出一步精准切入 `Slot 2` 组内第一条记录（主键 5），再沿单向链表向后比对，因组内最多 4 到 8 条记录，比对到主键 6 时命中返回。
    * 整体开销：整套组合拳下二分查找耗时极短，组内扫描至多不超过 8 次遍历，单页内检索瓶颈被彻底粉碎。
    * > 来源: P124

* **Page Header 的 56 字节状态仪表盘**

    | 字段名称 | 字节大小 | 核心用途与职能说明 |
    | :--- | :--- | :--- |
    | `PAGE_N_DIR_SLOTS` | 2 字节 | 页目录中当前的槽（Slot）总数量 |
    | `PAGE_HEAP_TOP` | 2 字节 | 空闲空间（Free Space）的最小物理地址偏移量 |
    | `PAGE_N_HEAP` | 2 字节 | 当前页内分配的所有记录总数（含虚拟记录与已删除记录） |
    | `PAGE_FREE` | 2 字节 | 垃圾链表（已标记删除记录链表）的头节点物理地址偏移量 |
    | `PAGE_GARBAGE` | 2 字节 | 当前页内所有已标记删除记录累计占用的总字节数 |
    | `PAGE_LAST_INSERT` | 2 字节 | 最后一次插入记录的物理位置偏移量 |
    | `PAGE_DIRECTION` | 2 字节 | 最后一次插入的方向（向左或向右） |
    | `PAGE_N_DIRECTION` | 2 字节 | 连续向同一个方向插入记录的累计次数 |
    | `PAGE_N_RECS` | 2 字节 | 当前页内实际有效的用户记录条数（不含虚拟与删除记录） |
    | `PAGE_MAX_TRX_ID` | 8 字节 | 修改当前页面的最大事务 ID |
    | `PAGE_LEVEL` | 2 字节 | 当前页在 B+ 树中所处的层级（叶子节点恒为 0） |
    | `PAGE_INDEX_ID` | 8 字节 | 当前页面所属的索引唯一 ID |
    | `PAGE_BTR_SEG_LEAF` | 10 字节 | B+ 树叶子节点段的段头信息（仅在根页面有效） |
    | `PAGE_BTR_SEG_TOP` | 10 字节 | B+ 树非叶子节点段的段头信息（仅在根页面有效） |

    * `PAGE_N_DIR_SLOTS`：执行二分查找初始化时，高端指针直接由此字段赋值 `high = PAGE_N_DIR_SLOTS - 1`。
    * `PAGE_HEAP_TOP`：物理未分配空间的起始指针；有全新记录插入且无法从垃圾链表重用时，引擎直接从该处划拨内存并把指针向后推移对应字节数。
    * `PAGE_N_RECS` 与 `PAGE_N_HEAP` 的辨析：前者记录真实有效的用户数据行数（不含 `Infimum`、`Supremum`，也不含被 `delete_mask = 1` 标记删除的行）；后者记录堆内已分配的全部物理记录总数，把两个哨兵以及垃圾链表中所有废弃记录统统算在内。
    * `PAGE_FREE` 与 `PAGE_GARBAGE`：前者是所有被标记删除记录通过自身 `next_record` 链接成的单向链表的入口地址，新记录插入时引擎优先顺其检索是否有大小匹配的废弃槽位可覆写；后者统计垃圾链表累计吞噬的碎片字节数，累积过大且页内空闲空间告急时 InnoDB 触发页内物理重组（Defragmentation），把有效数据集中紧凑重排彻底回收碎片。
    * 插入方向感知与自增优化：`PAGE_DIRECTION` 表示最后一次插入方向（新记录主键比上一条大标记为向右插入，反之标记为向左插入），`PAGE_N_DIRECTION` 记录连续同向插入次数；使用 `AUTO_INCREMENT` 自增主键时几乎所有插入都是单调递增向右插入，`PAGE_N_DIRECTION` 持续飙升，InnoDB 监测到该特征后不再做多余的槽位折半比对，而是直接假定新记录应追加在上一条记录之后，省去大量二分检索开销。
    * > 来源: P124

### 7.5 Compact 行格式与 ibd 字节剖析

* **四种行格式与配置语法**
    * Compact：紧凑行格式，自 MySQL 5.1 引入，核心设计目标是消除物理存储中的冗余字段，使数据页能容纳更多记录，提高内存与缓存利用效率。
    * Dynamic：动态行格式，MySQL 5.7 与 8.0 的默认行格式，针对行溢出（Off-page）机制做了进一步优化。
    * Compressed：压缩行格式，在 Dynamic 基础上对存放在物理页上的数据和行溢出数据进行 zlib 压缩存储。
    * Redundant：冗余行格式，MySQL 5.0 之前的古老格式，不具备 Compact 的紧凑特性，保留了大量冗余元数据。
    * 默认行格式由系统变量 `innodb_default_row_format` 控制，`SHOW VARIABLES LIKE 'innodb_default_row_format';` 在 MySQL 5.7 和 8.0 下均返回 `dynamic`。
    * 设置语法：建表时 `CREATE TABLE emp3 (id INT, name VARCHAR(15)) ROW_FORMAT = COMPACT;`；改已有表 `ALTER TABLE emp2 ROW_FORMAT = COMPACT;`；查看 `SHOW TABLE STATUS LIKE 'emp3'\G`，结果集中的 `Row_format` 字段显示实际行格式。
    * > 来源: P125

* **Compact 的额外信息三部分**
    * 一条完整的 Compact 记录严格划分为两大部分：记录的额外信息（变长字段长度列表 + NULL 值列表 + 记录头信息）与记录的真实数据（系统隐藏列 + 各列值）。
    * 变长字段长度列表三条特征：仅记录变长字段（定长类型如 `INT`、单字节字符集下的 `CHAR(10)` 占用字节固定，不记录在该列表中）；仅记录非 NULL 字段（变长字段值为 `NULL` 时实际长度为 0，长度信息直接省略不占位，NULL 状态完全由 NULL 值列表管理）；逆序排列。
    * 逆序示例：若表中变长字段按定义顺序为 `col1`、`col2`、`col4`，实际占用字节数分别为 1、2、3 字节，则长度列表中记录顺序为 `03 02 01`。
    * > 提示（为什么必须逆序存储）：记录头信息中的 `next_record` 指向的位置不是整行记录最前端，而是记录头信息与真实列数据之间的分界点；读取指针定位在分界点时向右读是用户真实列数据（第 1 列、第 2 列、第 3 列……），向左读是元数据额外信息（第 1 个字节对应第 1 列长度、第 2 个字节对应第 2 列长度……），元数据与实际数据在逻辑上构成“对称展开”，最大化提升 CPU 缓存读取连续内存时的局部性。
    * > 来源: P125

* **NULL 值列表算法**
    * 第一步（统计可为 NULL 的列）：遍历表结构中所有列，排除声明了 `NOT NULL` 的列以及主键列（主键天然不允许为 NULL）；若一张表所有列都定义为 `NOT NULL`，则该记录中的 NULL 值列表完全不生成，节省整段开销。
    * 第二步（用 bit 位映射状态）：每个允许为 NULL 的列对应一个二进制位，位为 `1` 代表该列值为 `NULL`，位为 `0` 代表该列值非 `NULL`。
    * 第三步（逆序排列）：按字段定义的相反顺序依次填充 bit 位，即定义靠前的列存放在二进制的低位、定义靠后的列存放在高位。
    * 第四步（按字节高位补齐）：NULL 值列表存储单位是整字节（Byte，8 bit）；若可为 NULL 的列数为 $N$ 个，则占用 $\lceil N / 8 \rceil$ 个字节，不足 8 位的高位全部用 `0` 补齐。
    * > 来源: P125

* **记录的真实数据与系统隐藏列**
    * `DB_ROW_ID`（row_id，6 字节）：用户建表显式指定主键，或定义非空唯一索引（`UNIQUE NOT NULL`）时，InnoDB 直接复用该列构建聚簇索引，此时记录中**不会**生成 `DB_ROW_ID`；只有表中既无主键也无非空唯一键时，InnoDB 才强制生成一个 6 字节的全局自增隐藏行 ID，以此维系“索引即数据、数据即索引”的聚簇索引骨架。
    * `DB_TRX_ID`（transaction_id，6 字节）：事务 ID，记录最新插入或修改该行记录的事务唯一标识，用于支撑 MVCC 多版本并发控制与事务一致性读。
    * `DB_ROLL_PTR`（roll_pointer，7 字节）：回滚指针，指向该行在 undo log 历史版本链中的最新物理存储地址，用于事务回滚与历史版本快照重构。
    * 顺序说明：一条记录由左至右连续存储，前三个部分为额外信息，紧接着是三个系统保留隐藏列（视建表条件可能省略 `DB_ROW_ID`），随后按字段顺序排列用户实际插入的列数据。
    * > 来源: P125

* **.ibd 十六进制逐字节剖析**
    * 实验表：`CREATE TABLE mytest (col1 VARCHAR(10), col2 VARCHAR(10), col3 CHAR(10), col4 VARCHAR(10)) ENGINE=InnoDB CHARACTER SET=latin1 ROW_FORMAT=COMPACT;`，插入 `('a','bb','bb','ccc')`、`('d','ee','ee','fff')`、`('d',NULL,NULL,'fff')` 三条对照数据。
    * 第一条记录字节流：`03 02 01 00 00 00 10 00 2c` 加 `DB_ROW_ID`（6 字节）、`DB_TRX_ID`（6 字节）、`DB_ROLL_PTR`（7 字节）加 `61 62 62 62 62 20 20 20 20 20 20 20 20 63 63 63`。
    * 变长字段长度列表 `03 02 01`：变长字段为 `col1`、`col2`、`col4`（`col3` 是定长 `CHAR(10)` 不进入该列表）；`col1` 存 `'a'` 占 1 字节、`col2` 存 `'bb'` 占 2 字节、`col4` 存 `'ccc'` 占 3 字节，逆序记录后为 `03 02 01`。
    * NULL 值列表 `00`：第一条记录所有列均有明确赋值不存在任何 `NULL`，所有 bit 位均为 0，高位补齐一个字节后为 `0x00`。
    * 记录头信息（5 字节）：占据接下来的 5 个字节，其中末尾两个字节 `00 2c` 代表 `next_record`，表示从当前记录分界点向后偏移 44 个字节即到达下一条用户记录。
    * 真实列数据：`col1`（`VARCHAR`）存入 `0x61`；`col2`（`VARCHAR`）存入 `0x62 0x62` 占 2 字节；`col3`（`CHAR(10)`）定长字段存入 `'bb'`（`0x62 0x62`）后剩余 8 个字符由空格填充，`latin1` 字符集下 ASCII 空格值为 `0x20`，故底层连续占用整整 10 字节 `62 62 20 20 20 20 20 20 20 20`；`col4`（`VARCHAR`）存入 `0x63 0x63 0x63`。
    * 第三条记录字节流：`03 01 06 00 00 18 00 2c` 加 `DB_ROW_ID`、`DB_TRX_ID`、`DB_ROLL_PTR` 加 `64 66 66 66`。
    * 变长字段长度列表变化为 `03 01`：`col4` 为 `'fff'` 占 3 字节对应 `0x03`；`col2` 虽是 `VARCHAR` 但当前值为 `NULL`，**直接被移出变长字段长度列表**；`col1` 为 `'d'` 占 1 字节对应 `0x01`；逆序存储后该区域仅占用 2 字节。
    * NULL 值列表计算推演为 `06`：表中 4 个列均未显式声明 `NOT NULL` 故全部归入 NULL 值监控范围；按字段定义正序检查得 `col1 = 'd'`（非 NULL，标 `0`）、`col2 = NULL`（标 `1`）、`col3 = NULL`（标 `1`）、`col4 = 'fff'`（非 NULL，标 `0`）；逆序排列为 `col4 col3 col2 col1` 即 `0 1 1 0`；高位补齐为一个完整 8 bit 字节得 `00000110`，即 $0 \times 2^3 + 1 \times 2^2 + 1 \times 2^1 + 0 \times 2^0 = 4 + 2 = 6$，十六进制为 `0x06`。
    * 真实数据区的极致压缩：`col1` 写入 `0x64`；`col2` 和 `col3` 均为 `NULL`，在真实数据区中连 1 个字节的物理空间都没有分配、直接跳过；紧接着直接写入 `col4` 的数据 `0x66 0x66 0x66`。
    * > 结论：值为 `NULL` 的列不仅在变长长度列表中不留痕迹，更在真实数据区实现零空间开销；整个表的所有空值状态仅依靠前置的几个 bit 位以极高密度集中管理。
    * > 来源: P125

### 7.6 行溢出与四种行格式对比

* **行溢出（Row Overflow）机制**
    * 物理矛盾：数据页默认 16KB 即 16384 字节，而 `VARCHAR(M)` 理论上最大可声明 65535 个字节，单个大字段就能申请超过 65000 字节存储空间，即使页内不存任何索引目录与页头元数据也无法塞下这样一行记录。
    * 多字节字符集换算：`VARCHAR(M)` 中 $M$ 代表字符数而非字节数；在默认 `utf8mb3`（每字符最多 3 字节）下执行 `CREATE TABLE varchar_size_demo0 (c VARCHAR(65535));` 会报错 `Column length too big for column 'c' (max = 21845); use BLOB or TEXT instead`，因为 $21845 \times 3 = 65535$。
    * 单字节字符集元数据开销：改用单字节的 `ASCII` 或 `latin1` 后 `VARCHAR(65535)` 仍报错 `Row size too large. The maximum row size for the used table type, not counting BLOBs, is 65535...`；65535 是**包含存储开销（Storage Overhead）在内的一整行记录的最大字节上限**。
    * 两笔额外开销：变长字段最大长度超过 255 字节（$2^8 - 1$）时 1 个字节无法记录真实长度，须分配 **2 个字节**记录实际字节数；该列允许为 `NULL` 时必须至少预留 **1 个字节**（8 个 bit）的 NULL 值列表来记录该列是否为空。
    * 极限容量：字段允许为 `NULL` 时单字段最大有效数据长度为 $65535 - 2 - 1 = 65532$ 字节（`VARCHAR(65532)` 建表成功、`VARCHAR(65533)` 报错超出行尺寸上限）；显式 `NOT NULL` 时整表已无允许 NULL 的列、NULL 值列表的 1 字节开销被直接略去，最大可用容量扩充为 $65535 - 2 = 65533$ 字节（`VARCHAR(65533) NOT NULL` 成功、`VARCHAR(65534) NOT NULL` 失败）。
    * > 结论：MySQL 单行数据的最大物理长度为 65535 字节；单个 `VARCHAR` 字段在单字节字符集下允许为 `NULL` 时最大声明长度 65532，声明为 `NOT NULL` 时最大声明长度 65533。
    * > 来源: P126

* **Compact 与 Dynamic/Compressed 的溢出策略对比**
    * Compact（以及早期 Redundant）采用“部分行溢出”：在本页真实数据区保留该字段的**前 768 个字节**；其余超长数据分散写入一个或多个专门的溢出页（Off-page / Overflow Page），溢出页之间通过双向链表相连；在原数据页的 768 字节数据之后追加一段 **20 个字节**的指针信息，记录存放剩余数据的溢出页所在表空间 ID（Space ID）、页号（Page Number）以及在溢出页中的有效字节长度。
    * Dynamic 与 Compressed 采用“完全行溢出（Fully Off-page）”：在原数据页的真实数据区**完全不存储 768 个字节的前缀数据**；页内仅保留一个 **20 字节**的溢出指针（含表空间 ID、起始溢出页号、实际字节长度）；该超长大字段的所有真实数据全量转移到外部溢出页中存储。
    * Dynamic 性能更优的原因：Compact 保留 768 字节的初衷是让包含前缀索引或极短文本的查询不必产生跨页二次 I/O，但 768 字节在 16KB 数据页中占比过大——一行中有两个超长字段时单行记录在页内就要强行吃掉 $768 \times 2 = 1536$ 字节，数据页能容纳的行记录数断崖式下跌，导致聚簇索引叶子节点急剧膨胀、树高被迫增加，引发更多磁盘随机 I/O 与缓冲池争用。
    * Dynamic 只用 20 字节占位，使单个数据页能容纳更多的行记录，极大提高 B+ 树的扇出能力（Fan-out）与 Buffer Pool 的缓存命中率。
    * Compressed 的独特性在存储编码层面：将物理页刷盘存储时采用 `zlib` 算法对常规数据页与外部溢出页进行整页物理压缩；适用于存储大量文本（`TEXT`）、二进制流（`BLOB`）且存储成本敏感的归档数据库表，但在高并发高写入场景下页面解压与压缩会带来不小的 CPU 计算开销。
    * > 来源: P126

* **Redundant 行格式的冗余机理**
    * 结构变化三点：原“变长字段长度列表”变成“字段长度偏移列表”；原有的“NULL 值列表”彻底消失；记录头信息从 5 字节扩充到 **6 字节**。
    * 冗余原因一（全字段强制记录）：Compact 只对非空变长字段记录长度、定长列由元数据字典硬编码推导；Redundant 的字段长度偏移列表会把记录中所有列（包括系统隐藏列 `DB_ROW_ID`、定长列、变长列、为 NULL 的列）全部无一遗漏地记录一遍，对固定占用 6 字节的隐藏列或确定占用 4 字节的 `INT` 列重复记录物理尺寸。
    * 冗余原因二（累积偏移量计算）：Compact 直接存入各字段占用的真实字节数（如 `06 04 08`）；Redundant 存储累积偏移量——第 1 个隐藏列占 6 字节记录 `0x06`，第 2 个列紧接占 6 字节记录的不是 `0x06` 而是累加后的 `0x0C`（十进制 12），反解析时须用 $0x0C - 0x06 = 6$ 字节才能得出该列物理长度。
    * 冗余原因三（NULL 值内嵌标记）：Redundant 把 NULL 标记偷渡进字段长度偏移列表，偏移列表中每个 1 字节或 2 字节偏移量的最高有效位（第 1 位）被用作 NULL 标志位，最高位为 1 表示该列值为 `NULL`，进一步增加行记录反序列化解析的复杂度。
    * 记录头差异：Redundant 记录头固定占 **6 个字节（48 bit）**，新增 `n_fields`（记录该条记录总共包含多少个列，包括隐藏列）与 `1byte_offs_flag`（标记字段长度偏移列表以 1 字节还是 2 字节为单位寻址）；但**没有 `record_type` 属性**，无法像 Compact 那样直接从头信息区分最小/最大记录（Infimum/Supremum）与 B+ 树目录项记录。
    * > 来源: P126

* **四种行格式综合对比**

    | 行格式 | 默认版本 | 变长/偏移元数据 | NULL 值管理 | 记录头尺寸 | 行溢出处理策略 |
    | :--- | :--- | :--- | :--- | :--- | :--- |
    | Compact | MySQL 5.1 / 5.5 / 5.6 | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 部分溢出：页内保留前 768 字节数据加 20 字节溢出指针 |
    | Dynamic | MySQL 5.7 / 8.0（当前默认） | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 完全溢出：页内仅保留 20 字节溢出指针，数据全外放 |
    | Compressed | 可选指定 | 仅记录变长列实际长度（逆序） | 独立 bit 位列表（逆序，高位补齐） | 5 字节 | 完全溢出：20 字节指针加 zlib 算法整页与溢出页物理压缩 |
    | Redundant | MySQL 5.0 之前（遗留兼容） | 全列累积偏移量列表（逆序，含定长） | 无独立列表（嵌入偏移量最高位标记） | 6 字节 | 部分溢出：页内保留前 768 字节数据加 20 字节溢出指针 |

    * > 结论：从 Redundant 的全列偏移冗余，到 Compact 的变长提纯与独立 NULL 位图，再到 Dynamic 的完全行溢出轻量化，行格式演进始终围绕“提升单页记录密度、降低 B+ 树高度、削减随机 I/O 开销”这一终极目标。
    * > 来源: P126
