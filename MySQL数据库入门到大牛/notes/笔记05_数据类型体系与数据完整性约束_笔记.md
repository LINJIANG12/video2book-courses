# MySQL 数据类型体系与数据完整性约束
## 数据类型的技术定位与全景分类


### 类型精讲的两条工程约束

* **精度约束（业务正确性底线）**
    * 浮点数 `FLOAT`/`DOUBLE` 受底层 IEEE 754 标准限制，存在无法被精确表示的二进制无限循环小数，运算时会发生四舍五入的精度丢失。
    * 涉及电商订单、充值、流水清算的场景，必须使用能够绝对精确存储的定点数 `DECIMAL`，否则累积误差会造成账务事故。
* **性能与微观设计规范**
    * 范式理论（1NF、2NF、3NF、BCNF）决定表与实体关系的宏观骨架，字段类型选型决定微观 I/O 效率与索引吞吐。
    * 字段越窄，B+ 树一个数据页能容纳的索引项越多，系统吞吐量越高；能用 1 字节搞定的绝不用 4 字节。
* **SQL 三大支柱的功能边界**
    * DDL 负责元数据结构与生命周期（`CREATE` / `ALTER` / `DROP TABLE`）。
    * DML 分为 DQL（`SELECT` 单表/多表/子查询/聚合，使用最频繁）与增删改（`INSERT` / `UPDATE` / `DELETE` / `TRUNCATE`）。
    * DCL 分为 TCL 事务控制（`COMMIT` / `ROLLBACK`，保障 ACID）与安全权限体系（`GRANT` / `REVOKE` / 用户与角色）。

### 五大类型族分类矩阵

* **数值类型族（Numeric Types）**
    * 整数系列：`TINYINT`（1 字节）、`SMALLINT`（2 字节）、`MEDIUMINT`（3 字节）、`INT`/`INTEGER`（4 字节）、`BIGINT`（8 字节），空间开销从小到大线性翻倍。
    * 浮点系列：`FLOAT`（单精度，4 字节）、`DOUBLE`（双精度，8 字节），适用于科学计算等对微量截断不敏感的统计场景。
    * 定点系列：`DECIMAL`，通过内部紧凑字符串编码杜绝任何浮点截断，商业开发中涉及金钱和严谨计数一律选用。
    * 位类型 `BIT`：以二进制位形式存储 0 和 1 的开关状态或掩码位，通用业务占用比例较小但属独立标准成员。
* **日期与时间类型族（Date and Time Types）**
    * 成员为 `YEAR`、`DATE`、`TIME`、`DATETIME`、`TIMESTAMP`；仅记录年份用极致紧凑的 `YEAR`（1 字节），追踪完整操作流水则在 `DATETIME` 与支持时区自动换算的 `TIMESTAMP` 之间权衡。
    * 数据库层面细分时间类型的根据：关系型数据库是系统状态流转的最终见证者，业务实体的创建、审核、支付与变更需精确到秒乃至毫秒作为防篡改审计凭据。
* **文本、集合与二进制富媒体类型族**
    * `CHAR` 为固定长度字符串，空间换时间、读取最快；`VARCHAR` 为可变长度字符串，节省物理磁盘、按需分配；海量非格式化大文本交由 `TEXT` 系列。
    * `ENUM` 适用于“固定多选一”（季节、性别），`SET` 适用于“多选多”（用户画像标签、兴趣爱好勾选），底层以紧凑的整型位图映射存储。
    * `BLOB` 与 `BINARY` 专门接纳非纯文本原始字节流；签名私钥、加密证书、小图标必须用 `BLOB`，绝不可用 `TEXT`，否则字符编码解码转换会直接破坏底层二进制序列。
    * 生产环境极少推荐把几十兆的原始图片、MP3、MP4 直接塞进关系型数据库，通常交由外部对象存储 OSS/S3 处理，表内仅存 URL 字符串。
* **JSON 类型与空间数据类型**
    * 原生 `JSON` 内部支持校验 JSON 格式合法性，并具备路径表达式定位与就地更新能力。
    * 空间类型涵盖 `GEOMETRY`、`POINT`、`LINESTRING`、`POLYGON` 等，支撑地图定位、LBS 距离计算与地理信息系统（GIS）。

### 字段修饰属性：无符号与字符集层级

* **无符号修饰符 `UNSIGNED` 的业务语义**
    * 字段修饰符语法结构：`字段名 数据类型 [UNSIGNED] [CHARACTER SET 字符集名] [约束条件]`。
    * 默认整型有符号，最高位作为符号位、正负各半；追加 `UNSIGNED` 后剥离负数表示能力，正数取值上限整整翻倍。
    * 人类年龄、城市常住人口数、商品库存、自增物理主键 ID 等天然非负属性适合追加 `UNSIGNED`，在相同字节开销下获得翻倍的正向容纳上限。
* **字符集的层级继承与列级覆盖机制**
    * 四级作用域自上而下为服务器级（Server Default）→ 数据库级 → 数据表级 → 字段列级，任一级未显式指定即继承上一级。
    * 数据库级：`CREATE DATABASE IF NOT EXISTS dbtest12 CHARACTER SET utf8;`，`SHOW CREATE DATABASE dbtest12;` 返回的元数据中显式包含 `DEFAULT CHARACTER SET utf8`。
    * 数据表级：`CREATE TABLE IF NOT EXISTS temp (id INT);` 未声明编码时继承库编码，`SHOW CREATE TABLE temp;` 尾部标记 `DEFAULT CHARSET=utf8`。
    * 字段列级：`CREATE TABLE temp1 (id INT, \`name\` VARCHAR(15) CHARACTER SET gbk);` 可在 utf8 表内让个别列使用 `gbk` 等其他字符集。
    * > **结论**：下级对象始终以继承上级对象的字符集为默认基准，当前层级显式声明 `CHARACTER SET` 后立即生效并覆盖上级继承值。

## 整数族：物理边界、显示宽度与选型权衡


### 五种整型的存储空间与取值范围

* **二进制位权与上下限推导**
    * 整型严格遵循二进制物理存储规范，每字节 8 个二进制位；根据最高位是否被用作符号位（Sign Bit）分为有符号与无符号两种形态。
    * `TINYINT`（1 字节 = 8 bit）状态总数 $2^8 = 256$ 种，有符号 $[-2^7, 2^7-1]$ 即 $-128 \sim 127$，无符号 $0 \sim 2^8-1$ 即 $0 \sim 255$。
    * `SMALLINT`（2 字节 = 16 bit）状态总数 $2^{16} = 65536$ 种，有符号 $-32768 \sim 32767$，无符号 $0 \sim 65535$。
    * `MEDIUMINT`（3 字节 = 24 bit）状态总数 $2^{24} = 16777216$ 种，有符号 $-8388608 \sim 8388607$，无符号 $0 \sim 16777215$（约 1677 万）。
    * `INT`/`INTEGER`（4 字节 = 32 bit）状态总数 $2^{32} \approx 42.9$ 亿种，有符号 $-2147483648 \sim 2147483647$（约 $\pm 21.47$ 亿），无符号 $0 \sim 4294967295$（约 42.94 亿）。
    * `BIGINT`（8 字节 = 64 bit）状态总数 $2^{64}$ 种，有符号约 $-9.22 \times 10^{18}$，无符号 $0 \sim 2^{64}-1$（约 $1.84 \times 10^{19}$，上限达 1800 亿亿级别）。
* **越界截断与严格模式异常**
    * 测试表：`CREATE TABLE IF NOT EXISTS test_int1 (f1 TINYINT, f2 SMALLINT, f3 MEDIUMINT, f4 INT, f5 BIGINT);`
    * `INSERT INTO test_int1 (f1) VALUES (12), (-12), (-128), (127);` 为有符号 `TINYINT` 的极限合法插入。
    * 写入 `128` 时，在默认严格 SQL 模式（`STRICT_TRANS_TABLES`）下引擎绝不允许静默截断，立即拦截并抛出 `ERROR 1264 (22003): Out of range value for column 'f1'`，强行中断事务。

### 显示宽度 M 与零填充 ZEROFILL

* **`INT(M)` 中 M 的确切含义**
    * > **定义**：括号中的 `M` 严格代表显示宽度（Display Width），合法取值范围为 `0 ~ 255`。
    * 显示宽度绝对不限制底层存储字节（`INT` 永远固定 4 字节），也绝对不限制实际能存入的数值区间；定义为 `INT(5)` 后，6 位数、7 位数乃至 10 位数只要未超出 $\pm 21.47$ 亿边界都能正常存储，绝不报错。
    * 单独声明 `M` 没有任何实际意义，它必须且只能与 `ZEROFILL` 属性配合时才会生效。
* **5.7 默认显示宽度的计算来源**
    * 在 MySQL 5.7 中 `DESC test_int1;` 返回 `tinyint(4)`、`smallint(6)`、`mediumint(9)`、`int(11)`、`bigint(20)`；MySQL 8.0 中括号内数字消失，呈现为 `tinyint`、`smallint`、`int` 等纯净类型名。
    * 默认宽度与最高负数的字符长度直接绑定：`TINYINT` 最小负数 `-128` 为 3 个数字字符 + 1 个负号 = 4；`SMALLINT` 最小负数 `-32768` 为 5 + 1 = 6；`INT` 最小负数 `-2147483648` 为 10 + 1 = 11；`BIGINT` 最小负数 19 个数字字符 + 1 个负号 = 20。
* **ZEROFILL 的联动生效机理**
    * 测试表 `test_int2 (f1 INT, f2 INT(5), f3 INT(5) ZEROFILL)`：插入 `123` 时 `f1`、`f2` 显示 `123`（无前导补齐），`f3` 显示 `00123`；插入 `123456` 时三者均原样完整输出。
    * > **结论**：`ZEROFILL` 在数据位数不足时左侧补零，超出显示宽度时无缝原样输出。
    * 指定 `ZEROFILL` 后 `SHOW CREATE TABLE test_int2;` 显示 `f3` 被系统自动转化为 `int(5) unsigned zerofill`——一旦指定零填充，该字段在逻辑上已被假定为绝对非负数（负数不可能在负号前补零），因此引擎自动隐式附加 `UNSIGNED` 约束。
* **无符号对显示宽度的动态重算**
    * `CREATE TABLE IF NOT EXISTS test_int3 (f1 INT UNSIGNED);` 后 `DESC` 呈现 `int(10) unsigned`：无符号 `INT` 最大值 `4294967295` 共 10 位数字且不再需要负号，最大显示宽度由 11 缩减为 10。
    * 插入 `4294967295` 顺利执行，插入 `4294967296` 立即越界报错。
    * > **提示**：从 MySQL 8.0.17 开始官方已正式废弃对整型指定显示宽度 `M` 的语法（Deprecated），现代工程建议将数据显示格式化（如银行流水补前导 0）下放到上层业务应用完成，建表时直接声明 `INT`。

### 整型的业务适配与容量权衡

* **典型业务场景映射**
    * `TINYINT`：进度百分比（0~100）、逻辑删除标记（0 未删除、1 已删除）、用户性别或审批状态、月份 1~12、星期 1~7。
    * `SMALLINT`：企业固定资产台账、中小学校学生编号、高校各学院学科分类、仓库库位编号（0~65535）。
    * `MEDIUMINT`：大型交通枢纽每日客流量、某地级市机动车保有量、公共交通日刷卡量（约 1600 万量级）。
    * `INT`：通用自增主键、用户 UID、商品 SKU、订单流水，取值区间达 21.47 亿（无符号 42.94 亿）。
    * `BIGINT`：电商全网大促并发交易总额、全网分布式日志 TraceID、社交平台亿级用户的点赞与高频行为流、金融衍生品持仓总额。
* **存储空间与系统可靠性的权衡法则**
    * 从 InnoDB 机制看字段越小越好：数据以 16KB 数据页（Page）为单位驻留内存缓冲区并持久化至磁盘，主键和字段占用字节越少，单个数据页容纳的行记录和 B+ 树索引节点越多，可降低树高、减少磁盘 I/O 寻道次数。
    * > **结论**：在实际工业生产中，系统崩溃停机所造成的业务损失与故障成本，远远高于在磁盘上多增加几个字节所产生的存储开销。
    * 典型教训：核心主键定义为 `MEDIUMINT UNSIGNED`（上限约 1677 万），上线两年后主键值突破 16777215，底层引擎全线抛出 `Out of range` 异常，核心下单接口大面积超时，团队执行线上 `ALTER TABLE` 修改上千万行记录字段类型，停机维护长达数小时。
    * 选型三项法则：评估生命周期需按未来 3 到 5 年的业务翻倍速度测算峰值上限；业务核心实体主键宁可直接使用 `BIGINT`，绝不把空间卡得严丝合缝；只有在取值受数学法则或物理规律严格受限的字段（月份 1~12、星期 1~7、百分比 0~100）才用 `TINYINT` 压榨空间。

## 浮点族、定点数与位类型


### 浮点数的规格与存储格式

* **三种浮点类型规格**
    * `FLOAT`：4 字节，单精度 32 位，约 7 位有效数字，取值范围约 $10^{38}$。
    * `DOUBLE`：8 字节，双精度 64 位，约 15~17 位有效数字，取值范围约 $10^{308}$。
    * `REAL`：默认等价于 `DOUBLE`（8 字节）；`SET sql_mode = 'REAL_AS_FLOAT';` 之后，再声明 `REAL` 会被解析为 4 字节的 `FLOAT`。
    * 若在声明为浮点类型的字段中写入整数 `123`，MySQL 执行隐式类型转换，底层补齐小数位以 `123.00` 形式存储。
* **IEEE 754 存储格式与 UNSIGNED 的反直觉表现**
    * 浮点数物理存储由三部分拼装：符号位（1 bit）、阶码位（`FLOAT` 8 bit / `DOUBLE` 11 bit）、尾数位（`FLOAT` 23 bit / `DOUBLE` 52 bit），数值逻辑为 $V = (-1)^{Sign} \times (1 + Mantissa) \times 2^{Exponent - Bias}$。
    * 在浮点数后加 `UNSIGNED` 并没有扩大正数范围，仅仅是生硬地把负数区间直接切除丢弃，只留下 `0` 到正数最大值的区间。
    * 根本原因：不论是否声明 `UNSIGNED`，底层都必须分配固定的符号位空间，声明无符号不能把符号位挪去给阶码或尾数扩容，只是写入校验层拦截负数；占用字节数（4 或 8 字节）完全不变，可表示的最大正数值丝毫没有增加。
    * > **提示**：MySQL 8.0 已明确将 `FLOAT(M, D)`、`DOUBLE(M, D)` 以及浮点数的 `UNSIGNED` 属性列为废弃特性（Deprecated），未来主版本将被彻底移除，现代开发切忌对浮点数声明 `UNSIGNED`。
* **精度 M 与标度 D**
    * 语法为 `FLOAT(M, D)` 或 `DOUBLE(M, D)`（非标准扩展语法）：`M`（Precision，精度）为总位数即整数位与小数位之和，有效范围 `1 ~ 255`；`D`（Scale，标度）为小数位数，有效范围 `0 ~ 30`，且必须满足 $M \ge D$。
    * 整数位最大容量等于 $M - D$。声明 `FLOAT(5, 2)` 时小数位占 2 位、整数位最多容纳 $5-2=3$ 位，有符号存储范围为 $-999.99 \sim 999.99$，带 `UNSIGNED` 则为 `0 ~ 999.99`。
    * 建表时不指定 `(M, D)`，MySQL 遵循底层硬件与操作系统的标准浮点表示方式，按实际精度存取和显示。

### 浮点数的溢出、四舍五入与误差陷阱

* **小数位超出触发四舍五入**
    * 测试表：`CREATE TABLE test_double1 (f1 FLOAT, f2 DOUBLE, f3 FLOAT(5, 2), f4 DOUBLE(5, 2));`
    * 向 `(5, 2)` 字段写入 `123.456`：不报错，查询结果变为 `123.46`。
    * > **结论**：写入数据的小数位数超过声明的标度 $D$ 时，MySQL 对超出的低位小数执行四舍五入，截断至设定的标度保存。
* **整数位超出直接溢出报错**
    * 向 `(5, 2)` 字段写入 `1234.456`：控制台直接报错 `ERROR 1264 (22003): Out of range value for column 'f4' at row 1`。
    * 四舍五入只能平抑小数位的超长，根本无法压缩整数位；一千多的数值无论如何舍入仍需 4 位整数位，超出 $5-2=3$ 位的硬性限制即判定数据溢出。
* **进位穿越小数点导致的连锁溢出**
    * 向 `(5, 2)` 字段写入 `999.995`：整数部分 `999` 恰为 3 位、小数部分 `.995` 为 3 位，按规则保留 2 位时对末位 `5` 四舍五入向高位进位，`.995` 变为 `1.00`，进位加到整数部分使 `999 + 1 = 1000`，最终结果成为 `1000.00`，整数位从 3 位变成 4 位。
    * 执行该语句同样抛出 `ERROR 1264 (22003): Out of range value for column 'f4' at row 1`。
    * > **易错点**：边界值的四舍五入不是局部的，进位若穿越了小数点，可能导致原本合法的整数位数被撑破，从而触发 `Out of range` 错误。
* **累加误差与相等性比较失效**
    * 创建 `test_double2 (f1 DOUBLE)` 并 `INSERT INTO test_double2 VALUES (0.4), (0.4), (0.3);`，数学直觉上 $0.4+0.4+0.3=1.1$。
    * 实际 `SELECT SUM(f1) FROM test_double2;` 返回 `1.0999999999999999`；`SELECT SUM(f1) = 1.1 FROM test_double2;` 返回 `0`（MySQL 中比较成立返回 `1`，不成立返回 `0`）。
    * 成因：十进制小数（如 `0.1`、`0.2`）转二进制后是无限循环小数，有限尾数位下必须在末位截断舍入；若换成单精度 `FLOAT`（尾数仅 23 位），有效数字更少、相对误差更加夸张。
    * > **易错点**：绝不能在业务 SQL 中用等号 `=` 判断浮点类型字段是否等于某个给定浮点数值，这种条件过滤会因微小的尾数截断导致逻辑判断落空，产生难以排查的幽灵 Bug。

### 定点数 DECIMAL 的精确存储

* **底层存储原理与语法参数**
    * `DECIMAL(M, D)` 的别名包括 `DEC`、`NUMERIC`；$M$ 为精度（总位数），最大值 65；$D$ 为标度（小数位），最大值 30，且 $M \ge D$。
    * 精确性来自存储方式：不再依赖 CPU 二进制浮点寄存器编解码，而是在底层以类似定长字符/压缩十进制字节数组的方式精确存储，整数部分与小数部分分别拆开、按每 9 位十进制数字占用 4 个字节紧凑打包。
    * 占用空间大致可用 $M + 2$ 字节粗略估算；每个十进制数位精准确定，不存在任何进制转换截断误差，与 Java 的 `BigDecimal` 思想异曲同工。
    * 计算性能较低（软件模拟计算），取值范围受 M 限制（最大 65 位）。
* **默认参数缺省行为**
    * `CREATE TABLE test_decimal1 (f1 DECIMAL, f2 DECIMAL(5, 2));` 后 `DESC` 显示 `f2` 为 `decimal(5, 2)`，未指定精度的 `f1` 被赋予默认值 `decimal(10, 0)`。
    * `decimal(10, 0)` 意味着标度 $D = 0$，完全不保留任何小数位；`INSERT INTO test_decimal1 (f1) VALUES (123), (123.45);` 后两条记录的 `f1` 均显示为 `123`，`.45` 按四舍五入规则被直接舍弃。
    * MySQL 8.0 中整型和浮点数后面的显示宽度及 `(M, D)` 已被废弃，但 `DECIMAL(M, D)` 被特许保留并严格要求，因为其占用的实际存储空间和物理编解码规则与 $M$、$D$ 紧密绑定。
    * > **易错点**：定义 `DECIMAL` 字段时遗漏参数，会导致小数位在不知不觉中被全部截断抹平，开发中必须显式指明 `(M, D)`。
* **误差根治实证**
    * `ALTER TABLE test_double2 MODIFY f1 DECIMAL(5, 2);` 改造字段类型后，`SELECT SUM(f1) FROM test_double2;` 干净输出 `1.10`，尾部不再有任何冗余浮点尾巴。
    * 相等性校验 `SELECT SUM(f1) = 1.1 FROM test_double2;` 返回值直接变为 `1`（True）。
* **浮点与定点的横向对比**

| 数据类型 | 存储占用 | 数值取值范围 | 计算性能 | 精度可靠性 |
| :--- | :--- | :--- | :--- | :--- |
| `FLOAT` | 4 字节（固定） | 极大（约 $10^{38}$） | 极高（CPU 硬件直算） | 存在舍入误差 |
| `DOUBLE` | 8 字节（固定） | 极其巨大（约 $10^{308}$） | 极高（CPU 硬件直算） | 存在舍入误差 |
| `DECIMAL(M,D)` | 约 $M+2$ 字节（可变） | 受 M 限制（最大 65 位） | 较低（软件模拟计算） | 绝对精准，无误差 |

### 浮点与定点数的选型原则

* **浮点数的优势领域**
    * 在固定 4 字节或 8 字节空间内，凭借科学计数法（阶码机制）能表达天文数字或微观极小数值，且运算可被现代 CPU 的 FPU（浮点运算单元）硬件加速，吞吐量极高。
    * 计算化学、分子建模、流体力学、天气预报、游戏物理引擎、3D 渲染等科学计算或图形图像领域，微小尾数误差可容忍而对吞吐率与数值跨度要求极高，应坚定选择 `FLOAT` 或 `DOUBLE`。
* **定点数的不可替代性与行业规范**
    * 定点数占用空间大、运算需数据库引擎在内存中逐位模拟算法，但带来 100% 的准确率；硬件存储介质与算力成本逐年下降，而账目差错引发的法律风险、审计阻力与客户投诉损失不可承受。
    * 某大型连锁零售企业核心规范：交易中台与结算中心的所有数据表中，除主键 ID、商品编码、条形码以及状态位等明确无小数的离散标识必须使用整型（`BIGINT` / `INT`）外，凡是涉及金额、单价、折扣、费率、佣金、税率等一切带小数点的字段，一律强制使用 `DECIMAL` 类型，严禁出现 `FLOAT` 或 `DOUBLE`。

### 位类型 BIT 的容量与查询转换

* **语法与容量限制**
    * 语法为 `BIT(M)`：$M$ 为该字段包含的二进制位个数，取值范围 `1 ~ 64`；省略 $M$ 时默认值为 `1` 即 `BIT(1)`，此时只能存储 1 个二进制位（值只能是 `0` 或 `1`）。
    * 物理存储占用 $\lceil M / 8 \rceil$ 个字节（即 $(M+7)/8$ 向下取整）；指定 `BIT(65)` 会直接超出最大边界 64 被拒绝执行。
    * `CREATE TABLE test_bit1 (f1 BIT, f2 BIT(5), f3 BIT(64));` 后 `DESC` 显示 `f1` 为 `bit(1)`、`f2` 为 `bit(5)`。
* **按二进制位数判定容量**
    * `INSERT INTO test_bit1 (f1) VALUES (0), (1);` 成功；写入十进制 `2` 报错 `ERROR 1406 (22001): Data too long for column 'f1' at row 1`，因为十进制 `2` 转二进制为 `10`，需占 2 个二进制位，超出 `BIT(1)` 仅能容纳 1 位的上限。
    * `f2 BIT(5)` 的最大容量为 5 个全 1 的二进制数：$\text{Bin: } 11111_2 = 16+8+4+2+1 = 31$；插入 `31` 顺利存入，插入 `32`（二进制 `100000`，占 6 位）立即触发 `Data too long for column 'f2'`。
    * > **结论**：位类型的容量由其二进制位数而非十进制数值决定。
* **查询呈现与三种转换手段**
    * 直接 `SELECT * FROM test_bit1;` 时客户端会按 ASCII 字符或十六进制字面量渲染，输出形如 `b'0'`、`b'1'`、`0x1F` 的形态，无法直接看清二进制数值。
    * 方式一 `SELECT BIN(f1), BIN(f2) FROM test_bit1;` 用内置函数还原二进制真实面貌，写入的 `31` 显示为文本 `'11111'`。
    * 方式二 `SELECT HEX(f1), HEX(f2) FROM test_bit1;` 显示十六进制，`31` 转为 `'1F'`。
    * 方式三 `SELECT f1 + 0, f2 + 0 FROM test_bit1;` 借助算术运算触发类型推导引擎把底层位串提升为十进制整数输出，`f2` 直接呈现为 `31`。
* **日常开发的实用评价**
    * 仅表示二值状态的字段（是否删除、是否激活、性别）工程习惯上优先用 `TINYINT`（或 `TINYINT(1)`），占 1 个字节、语义明确，MyBatis、Hibernate、JPA 等 ORM 框架适配与反序列化成熟，不易引发乱码或类型映射异常。
    * 需要存储大容量二进制流（加密盐值、哈希校验码、文件流）时，`BINARY`、`VARBINARY` 及 `BLOB` 家族的容量与处理灵活性远胜 `BIT`。
    * `BIT` 适用于设计极度节约存储空间的硬件通信、权限掩码（Permission Mask）等特殊位运算系统。

## 日期时间族：单一维度与复合维度


### 五种日期时间类型的存储规格

| 数据类型 | 存储空间 | 取值范围 | 标准展示格式 |
| :--- | :--- | :--- | :--- |
| `YEAR` | 1 字节 | 1901 ~ 2155（以及 0000） | `YYYY` |
| `DATE` | 3 字节 | 1000-01-01 ~ 9999-12-31 | `YYYY-MM-DD` |
| `TIME` | 3 字节 | -838:59:59 ~ 838:59:59 | `HH:MM:SS`（或 `D HH:MM:SS`） |
| `DATETIME` | 8 字节 | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 | `YYYY-MM-DD HH:MM:SS` |
| `TIMESTAMP` | 4 字节 | 1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC | `YYYY-MM-DD HH:MM:SS` |

* **单一维度与复合维度的划分**
    * 单一维度：`YEAR` 仅存储年份、存储极其紧凑；`DATE` 专门记录年月日（无时刻）；`TIME` 专门记录时分秒（无日期）。
    * 复合维度：`DATETIME` 与 `TIMESTAMP` 均同时记录年月日与时分秒，但字节数、有效时间范围、时区关联性存在本质区别。

### 年份与纯日期类型

* **YEAR 的紧凑性与语法演进**
    * 仅占 1 个字节（8 个 bit），一个字节最多表示 $2^8 = 256$ 种离散状态，因此设计区间为 1901 ~ 2155 年，另加一个特殊的 `0000` 年。
    * 早期允许显式指定显示宽度（`YEAR(4)` 或 `YEAR(2)`）；从 MySQL 5.5.27 起两位格式 `YEAR(2)` 被废弃，从 MySQL 8.0.19 开始显式声明宽度 `YEAR(4)` 同样不再推荐，现代建表直接声明 `YEAR`，默认均为 4 位。
    * `INSERT INTO test_year VALUES ('2021'), (2022), (2155);` 正常写入；写入 `2156` 直接报错 `ERROR 1264 (22003): Out of range value for column 'f1' at row 1`。
* **两位年份的解析黑洞**
    * `'01' ~ '69'` 解析为 2001 ~ 2069 年（假定为 21 世纪早期）；`'70' ~ '99'` 解析为 1970 ~ 1999 年（对应 UNIX 时间戳起点时代）。
    * 数字 `0` 解析为 `0000` 年（视为绝对零值）；字符 `'0'` 或 `'00'` 解析为 `2000` 年（视为千禧年）。
    * 验证：`INSERT INTO test_year VALUES ('69'), ('70'), (0), ('00');` 查询结果依次为 `2069`、`1970`、`0000`、`2000`。
    * > **易错点**：数字 `0` 和带引号的字符串 `'00'` 在 `YEAR` 字段中解析出的年份完全不同，开发中务必始终使用标准的四位数字或字符串（如 `'2024'`），杜绝任何两位简写。
* **DATE 的写入格式与当前日期函数**
    * 标准格式为字符串 `'YYYY-MM-DD'`；`'20210301'` 紧凑字符串格式可被自动识别，`20210301` 纯数字写法依赖内部推导机制，可读性极差，生产环境必须强制统一为带短横线格式；三种写法均能成功存入 `2021-03-01`。
    * 插入当前系统日期可使用 `CURDATE()` 或 `CURRENT_DATE()`；使用 `NOW()` 同样可以写入，`NOW()` 本身返回含“年月日+时分秒”的完整时间戳，但向 `DATE` 字段插入时 MySQL 会自动截除时分秒分量，仅保留年月日入库。

### TIME 的双重语义与解析歧义

* **时刻与时间间隔的双重语义**
    * > **定义**：`TIME` 承载双重语义——表示一天之内具体几点几分几秒的时刻（`00:00:00 ~ 23:59:59`），以及表示两个事件之间流逝的工时、时长差值或倒计时的时间间隔 / 耗时（Elapsed Time / Interval）。
    * 取值跨度为 `-838:59:59 ~ 838:59:59`：它能充当跨天累计耗时（长跑比赛计时、服务器持续运行时间、机器累计工作台时），因此支持带天数的输入格式，最大支持约 34 天（$34 \times 24 \approx 816$ 小时，上限 838 小时 59 分 59 秒）；负数用于表示倒计时或相减产生的负时间差。
* **五种输入格式的解析结果对照**
    * 包含天数的格式 `'D HH:MM:SS'`：`'2 12:30:29'` 转换为 $2 \times 24 + 12 = 60$ 小时，输出 `60:30:29`。
    * 标准时分秒格式 `'12:35:20'` 原样输出 `12:35:20`。
    * 两位带冒号格式 `'HH:MM'`：`'12:10'` 被解析为 12 小时 10 分钟 00 秒，输出 `12:10:00`，绝不是 12 分钟 10 秒。
    * 单个数字格式 `'SS'`：`'45'` 被视为 45 秒，输出 `00:00:45`。
    * 纯数字无冒号格式：数值 `1210` 被解析为 `MMSS` 即 12 分钟 10 秒，输出 `00:12:10`。
    * > **易错点**：字符串 `'12:10'` 带冒号时 MySQL 按“从高位小时开始截取”视为 12 小时 10 分；纯数值 `1210` 不带冒号时按“低位补齐”视为 12 分 10 秒。编写 SQL 必须始终使用完整的 `'HH:MM:SS'` 格式。
    * 获取当前时间可使用 `CURTIME()` 或 `CURRENT_TIME()`。

### DATETIME 与 TIMESTAMP 的核心差异

* **时区机理的本质分歧**
    * `DATETIME` 为“所见即所得”的面值存储：东八区写入 `2024-03-15 14:00:00`，磁盘直接记录 `2024-03-15 14:00:00`，读取时不转时区，无论数据库时区如何切换永不改变。
    * `TIMESTAMP` 为时区自适应存储：东八区写入 `2024-03-15 14:00:00` 时底层减去 8 小时推算出 UTC `06:00:00` 并落盘；会话切到东九区后读出 UTC `06:00:00` 再加 9 小时，动态渲染出 `2024-03-15 15:00:00`。
    * 实证：`SET time_zone = '+09:00';` 后查询同一张 `test_tz_compare` 表，`d1`（`DATETIME`）依然保持 `'2024-03-15 14:00:00'` 丝毫未变，`d2`（`TIMESTAMP`）自动变为 `'2024-03-15 15:00:00'`，整整增加一小时。
* **关键维度对比**

| 比较维度 | `DATETIME` | `TIMESTAMP` |
| :--- | :--- | :--- |
| 存储占用 | 8 字节（MySQL 5.6.4+ 优化为 5 字节） | 4 字节 |
| 时间范围 | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 | 1970-01-01 00:00:01 ~ 2038-01-19 03:14:07 |
| 时区相关性 | 无关（所见即所得，原样存取） | 强相关（内部转为 UTC 存储，按时区渲染） |
| 默认零值 | `'0000-00-00 00:00:00'` | `'0000-00-00 00:00:00'` |
| 排序与比对速度 | 字符串/解包数值比较 | 整数毫秒数比较（性能略优） |

* **2038 年灾难边界**
    * `TIMESTAMP` 仅占 4 字节（32 位有符号整数），存储的是从 UTC `1970-01-01 00:00:00` 开始计算的秒数偏移量；32 位有符号整型最大正整数为 $2^{31}-1 = 2147483647$。
    * 将 2147483647 秒累加到 1970 年元旦，极限时间点为 2038 年 01 月 19 日 03:14:07（UTC）；写入 `'2038-01-20 00:00:00'` 立即触发 `ERROR 1292 (22007): Incorrect datetime value`。
    * > **提示**：如果系统设计生命周期超过 2038 年，或需要存储未来的长期契约（如 30 年房贷合同、百年品牌规划），绝不能使用 `TIMESTAMP`。

### 时间字段的选型决策

* **拆分 DATE 与 TIME 属伪优化**
    * > **结论**：严禁把年月日与时分秒拆成两列：业务查询绝大多数要求跨天、跨周期的精确时间范围检索（如 `WHERE create_time BETWEEN t1 AND t2`），拆为两列后 SQL 必须编写复合比对逻辑，可读性极差且极易在跨天边界出现逻辑 Bug。
    * 索引层面：单一 `DATETIME` 建单列索引时 B+ 树能完美维持全局时间有序；拆成两列只能建 `(date_col, time_col)` 复合索引，树节点更大，范围检索会立即阻断后续列的索引下推与使用。
    * 空间收益层面：MySQL 5.6.4 之后官方对 `DATETIME` 底层存储结构做了优化（不带微秒时仅占 5 个字节），拆分方案在存储上毫无优势。
* **DATETIME 的统治地位**
    * 直观性与确定性：研发、运维和 DBA 排查问题或手动执行 SQL 变更时所见即所得，不会因客户端时区设置混乱产生错觉。
    * 超长生命周期覆盖到 9999 年，彻底免疫 2038 年时间戳溢出漏洞。
    * 现代大型系统通常在应用层统一处理时区转换（服务端统一切为 UTC，前端按用户浏览器地理位置本地化格式化展示），无需依赖数据库引擎在底层频繁转换。
* **整数时间戳 BIGINT 的高并发场景**
    * 在超高并发流水日志、分布式链路追踪、秒级高频排序等极致性能场景中，业界常采用 `BIGINT` 存储 13 位毫秒级 UNIX 时间戳，占用 8 字节。
    * 优势：能直接利用 CPU 原生整数寄存器做瞬时比对与范围排序；与 Java、Go、Python 等后端语言原生的时间戳数据流完美映射，避免字符串解析开销。在不需要直接以 SQL 肉眼看可读日期的核心底层链路中是成熟高效的备选方案。

## 文本字符串类型：从定长到枚举集合


### 字符串类型体系与 CHAR 的空格行为

* **三大分支总览**
    * 短字符串：`CHAR(M)` 固定长度字符、不足右侧补空格、检索时自动截断空格；`VARCHAR(M)` 可变长度字符、按实际内容加长度前缀存储、需显式声明 M。
    * 长文本：`TINYTEXT` 最大 255 字节（约 0.25 KB）；`TEXT` 最大 65535 字节（约 64 KB，最常用）；`MEDIUMTEXT` 最大 16777215 字节（约 16 MB）；`LONGTEXT` 最大 4294967295 字节（约 4 GB）。
    * 预定义选项：`ENUM` 单选枚举，1~2 字节，底层映射为数字索引，最多 65535 项；`SET` 多选集合，1~8 字节，底层以位图存储，最多 64 项。
* **CHAR 的定长特性与空格陷阱**
    * `CHAR(M)` 中的 $M$ 代表字符数（不是字节数），取值范围 `0 ~ 255`；不指定 $M$ 时默认值为 `1` 即 `CHAR(1)`。
    * 写入字符数不足 $M$ 个时，MySQL 在物理存储阶段在字符串右侧用半角空格自动填充补齐至 $M$ 个字符；执行 `SELECT` 检索时，MySQL 会自动将尾部所有填充空格全部截断剔除。
    * 实测：`INSERT INTO test_char1 (c2) VALUES ('ab');` 后用 `SELECT CONCAT(c2, '*') FROM test_char1;` 返回 `'ab*'`，填充空格消失。
    * 主动写入带末尾有效空格的 `'ab  '` 后，`SELECT CHAR_LENGTH(c2) FROM test_char1 WHERE c2 LIKE 'ab%';` 查出的结果是 `2`，业务空格被当作无用填充强行裁掉。
    * > **易错点**：如果业务数据本身在字符串末尾具有严格的空格语义（如特定报文格式、对齐协议），绝对不能选用 `CHAR` 类型，否则末尾空格会在出库时被全量抹去。

### VARCHAR 的变长机制与物理极限

* **版本演进与长度前缀公式**
    * `VARCHAR(M)` 表示字符数，但参数 $M$ 必须显式声明，缺省会直接抛出语法错误。
    * MySQL 4.0 及以前：`VARCHAR(20)` 代表 20 个字节，存放 UTF-8 汉字（一个汉字占 3 字节）最多只能存 6 个；MySQL 5.0 及以后：`VARCHAR(20)` 代表 20 个字符，数字、英文字母还是汉字都能完整存放 20 个。
    * 物理占用公式：$\text{存储空间} = \text{实际字符占用字节数} + L$，其中定义的列最大可能字节数 $\le 255$ 时 $L = 1$ 字节，$> 255$ 时 $L = 2$ 字节。
* **单列长度为何不能声明 65535**
    * 声明 `VARCHAR(65535)` 时 MySQL 立刻抛出 `ERROR 1074 (42000): Column length too big for column 'name' (max = 21845); use BLOB or TEXT instead`，明确提示最大长度只能写 `21845`。
    * 推导：MySQL 规定整张数据表中所有列的物理总长度不能超过 65535 字节（行长度限制，Row Size Limit）；在默认字符集 utf8（准确说是 `utf8mb3`）下每字符最多占 3 字节，$65535 / 3 = 21845$；若字符集为 `utf8mb4`（每字符最多 4 字节）则 $65535 / 4 = 16383$ 字符。
    * 一行数据还需额外扣除：变长列长度列表（`VARCHAR` 自身需 2 个字节记录长度）与 NULL 标志位（允许为 NULL 时需 1 个字节做位图记录），因此真实建表中即便是单个列的极限值往往还要比 21845 再少几个字符。

### CHAR 与 VARCHAR 的选型与存储引擎内幕

* **空间与时间的经典博弈**

| 比较维度 | `CHAR` | `VARCHAR` |
| :--- | :--- | :--- |
| 存储空间 | 固定分配，不足时右补空格，存在尾部空间浪费 | 按需分配，额外占 1~2 字节长度前缀 |
| 修改开销 | 行长度固定，就地原地更新，绝不发生行迁移（Row Migration） | 增大字符时可能超出原位置，引发页分裂与重构 |
| 检索性能 | 内存偏移量计算极快，直接按固定步长寻址 | 需先解析前置长度字节，计算实际数据边界 |
| 数据碎片 | 几乎不产生碎片 | 频繁更新长串易引发页分裂 |

* **适用 CHAR 的三大经典场景**
    * 存储极短文本（门牌号、状态码、性别标识）：存储单字符 `'A'` 时 `CHAR(1)` 占 1 字节，而 `VARCHAR(1)` 既要存字符又要额外拿 1 个字节记录长度，共占 2 字节，空间开销直接翻倍。
    * 天然严格固定长度的业务数据：MD5 哈希校验码（固定 32 位字符）、UUID/GUID（去掉横杠后固定 32 位字符）、居民身份证号（固定 18 位字符）、手机号码（固定 11 位字符），每条记录长度完全相同，用 `CHAR` 免除长度计算。
    * 更新极其频繁且长度变动剧烈的字段：用 `VARCHAR` 时旧空间容纳不下变长后的新字符串，InnoDB 必须在数据页内做碎片整理甚至迁移记录至新页面（引发行溢出与页分裂）；`CHAR` 物理空间从建表起严格锁死，更新永远是就地覆盖（In-place Update）。
* **存储引擎维度的认知反转**
    * MyISAM 的“静态表（Static Format）”下若所有列全是定长（全用 `CHAR`、`INT`），每行记录字节数完全相同，物理指针寻址可直接按 $\text{Offset} = \text{RowID} \times \text{RowLength}$ 计算偏移量，寻址速度极快，因此在 MyISAM 时代空间换时间首选 `CHAR`。
    * Memory 引擎中即使声明为 `VARCHAR`，内部也一律按定长 `CHAR` 进行内存分配。
    * InnoDB 的行格式（`Compact`、`Dynamic`）没有为定长列单独开辟类似 MyISAM 的静态寻址通道；使用变长字符集（如 `utf8mb4`）时 `CHAR(10)` 底层不是固定 10 字节，而是根据具体字符在 10~40 字节之间浮动，InnoDB 同样用变长机制管理它。
    * > **结论**：InnoDB 中决定性能的关键指标是整行数据的总物理字节数——`VARCHAR` 能最大限度剔除空格浪费压低单行体积，单行越小则标准 16KB 数据页容纳的行越多，Buffer Pool 命中率更高、磁盘 I/O 次数大幅减少。除明确固长或极短场景外，首选推荐 `VARCHAR`。

### TEXT 家族与存储空洞防护

* **TEXT 与 CHAR 的读取差异**
    * `INSERT INTO test_text1 VALUES ('尚硅谷   '); SELECT CHAR_LENGTH(tx) FROM test_text1;` 返回 `6`（3 个汉字 + 3 个空格）。
    * 与 `CHAR` 自动抹平尾部空格不同，`TEXT` 完整保留所有输入的尾部空格与格式符，存多少就是多少。
* **生产两项红线**
    * 严禁用 `TEXT` 字段充当主键：主键要求唯一且具备紧凑的高效索引，`TEXT` 长度不固定且体积臃肿，无法直接高效构建 B+ 树主键索引。
    * 频繁更新与删除会引发存储空洞（Holes）：核心业务表存放上万字大文本后，大范围修改或 `DELETE` 删除时操作系统和数据库引擎无法立即无缝回收这块庞大物理磁盘空间，数据页内部撕裂出巨大空洞并产生大量磁盘碎片（Fragmentation），随碎片堆积全表扫描与普通字段查询性能断崖式下跌。
    * > **结论**：严禁在核心事务主表（用户表、订单表）中直接嵌入大容量 `TEXT` 字段，必须实施垂直分表策略——将 `TEXT` 大字段剥离至独立扩展子表（如 `article_content`），通过主键与主表（如 `article_info`）关联；主表只保留标题、作者、发布时间等高频检索轻量字段，仅在需要查看正文详情时通过单条主键点查子表。

### ENUM 与 SET 的位映射机制

* **ENUM 枚举类型：严格单选**
    * `CREATE TABLE test_enum (season ENUM('春', '夏', '秋', '冬', 'UNKNOWN'));` 适用于互斥单选场景（性别、季节、审批状态）。
    * 写入未定义值 `'人'` 报 `ERROR 1265 (01000): Data truncated for column 'season' at row 1`；尝试同时写入两个值 `'春,秋'` 同样被判为非法枚举值报错。
    * 忽略大小写：枚举定义为 `'UNKNOWN'` 时写入小写 `'unknown'` 能正常解析入库。
    * 底层按定义时的先后顺序编为从 `1` 开始的整数索引（`'春'`→1、`'夏'`→2、`'秋'`→3、`'冬'`→4、`'UNKNOWN'`→5），因此 `INSERT INTO test_enum VALUES (1), (3);` 查询结果显示为 `'春'` 和 `'秋'`。
    * NULL 规则：字段未设置 `NOT NULL` 时允许显式存入 `NULL`。
* **SET 集合类型：多选排列**
    * `CREATE TABLE test_set (s SET('A', 'B', 'C'));` 适用于多选场景（用户标签、兴趣爱好、权限位），上限为 64 个成员。
    * 写入 `('A'), ('A,B'), ('A,B,C')` 合法；写入 `'A,B,C,A'` 不报错且系统自动去重，最终入库仍是 `'A,B,C'`；写入集合中不存在的项（如 `'A,B,D'`）直接拦截报错。
    * 复合业务表演练：`CREATE TABLE temp_multi (gender ENUM('男', '女'), hobbies SET('睡觉', '打豆豆', '看书', '写代码'));`，写入 `('男', '睡觉,打豆豆')` 合法；向单选字段塞入 `'男,女'` 报 `ERROR 1265: Data truncated for column 'gender'`。
    * > **结论**：`ENUM` 与 `SET` 能提供数据库级取值校验并节约空间，但现代化微服务架构中过度依赖会导致增删枚举项时需执行昂贵的 `ALTER TABLE` DDL；企业级开发更倾向用 `TINYINT` 配合应用层枚举类做状态管理，小型单体应用或强一致性静态归档表中 `ENUM` 与 `SET` 依然是高效选择。

## 二进制类型、JSON 与空间类型


### 二进制字符串 BINARY 与 VARBINARY

* **与文本类型的本质鸿沟**

| 类型分支 | 核心代表 | 计量单位 | 比较规则 |
| :--- | :--- | :--- | :--- |
| 文本字符串 | `CHAR`, `VARCHAR` | 字符数（Character） | 依赖字符集 Collation（通常忽略大小写） |
| 二进制字符串 | `BINARY`, `VARBINARY` | 字节数（Byte） | 逐字节二进制比对（严格区分大小写） |

* 文本字符串面向字符，存储与检索必须深度绑定字符集（UTF-8、GBK）和校对规则（Collation），比较 `'a'` 与 `'A'` 是否区分大小写取决于 Collation 定义。
* `BINARY` 与 `VARBINARY` 存储未经任何字符集编码转义的原始二进制字节流，排序与比较完全基于字节数值（0~255）逐字节比对，天然区分大小写且不受任何数据库字符集配置影响。
* 常用于存储二进制散列值（MD5、SHA256 生成的原始 16 字节/32 字节 Hash）、AES 加密密文、UUID 二进制压缩、序列化协议数据。
* **定长与变长的机制差异**
    * `BINARY(M)` 为定长二进制，$M$ 表示字节数；不指明 $M$ 时默认值为 `1`（只能存 1 个字节）；写入数据不足 $M$ 个字节时在右侧用十六进制的零值 `\0`（即 `0x00`）填充补齐。
    * `VARBINARY(M)` 为变长二进制，$M$ 表示允许存储的最大字节数且必须显式指明、不可缺省；物理存储空间等于实际字节数加上 1 或 2 个字节的长度前缀。
    * 实测：`f1 BINARY` 写入单字节 `'a'` 成功，写入 `'ab'` 报 `ERROR 1406 (22001): Data too long for column 'f1' at row 1`；向 `f2 BINARY(3)` 与 `f4 VARBINARY(10)` 均写入 `'ab'` 后，`LENGTH(f2)` 输出 `3`（实际内容为 `'ab\0'`，自动补 1 个零字节），`LENGTH(f4)` 输出 `2`。

### BLOB 家族规格与大文件存储禁令

| BLOB 类型 | 最大物理存储容量 | 换算常用容量单位 | 典型应用场景 |
| :--- | :--- | :--- | :--- |
| `TINYBLOB` | 255 字节 | 约 0.25 KB | 极小加密盐值、认证凭证 |
| `BLOB` | 65535 字节 | 约 64 KB | 紧凑证书、小配置二进制包 |
| `MEDIUMBLOB` | 16777215 字节 | 约 16 MB | 标准图片、短语音切片 |
| `LONGBLOB` | 4294967295 字节 | 约 4 GB | 高清长视频、大型可执行文件、ISO 镜像 |

* **存储实操表现**
    * `CREATE TABLE test_blob1 (id INT, image MEDIUMBLOB);` 可通过 GUI 客户端（SQLyog、Navicat）或后端代码（Java 使用 JDBC 的 `PreparedStatement.setBinaryStream()`）把本地 JPG、PNG 以输入流方式灌入字段。
    * 客户端执行 `SELECT * FROM test_blob1;` 只能返回一长串乱码或十六进制符号，数据库无法直接理解该多媒体资源，只能被动充当字节搬运工。
* **大文件入库的四项致命弊端**
    * 磁盘空洞（Holes）与碎片化（Fragmentation）：频繁更新或删除包含大容量 `BLOB`/`TEXT` 的记录时无法在数据页内平滑复用释放出的庞大连续空间，数据页离散度急剧上升，全表扫描和普通索引范围检索 I/O 效率灾难性下跌。
    * 主从同步（Replication）严重延迟：主从复制依赖 Binlog 传输，数兆或数十兆的 `BLOB` 被写入时产生的 Row 格式 Binlog 体积巨大，从库拉取重放会引发漫长延迟甚至读写超时崩溃。
    * 备份与灾难恢复耗时失控：逻辑备份（`mysqldump`）与物理备份（XtraBackup）必须对所有数据页做快照扫描，几百 GB 多媒体二进制流会耗尽磁盘 I/O 导致线上业务卡顿，并将灾难恢复时间（RTO）拉长到无法容忍的数天。
    * 内存缓冲池（Buffer Pool）污染：某条查询意外读取 `BLOB` 字段时，庞大数据块会瞬间把原本缓存的热点索引和高频业务行踢出内存，导致缓存命中率暴跌。
* **动静分离的标准解决方案**
    * 静态资源存入专业存储：图片、音视频、PDF 附件直接上传至分布式文件系统（开源的 FastDFS、MinIO）或公有云对象存储（阿里云 OSS、腾讯云 COS、AWS S3），并结合 CDN 做边缘节点加速。
    * 数据库仅存元数据与访问路径：表中只保留一个普通 `VARCHAR(255)` 类型的 `file_url` 字段存储资源的 CDN 访问链接，数据库回归结构化事务处理的核心职责。
    * > **结论**：字段名可为 `avatar_url`（如 `'https://cdn.site.com/u1001.jpg'`），单行仅数十字节，B+ 树极度紧凑。
* **必须保存大对象时的三项优化规范**
    * 垂直拆表：主表（如 `user_info`）仅存放 ID、账号、状态等轻量高频检索字段；扩展子表（如 `user_profile_detail`）仅存放 `user_id` 与大容量 `BLOB`/`TEXT` 字段。
    * 前缀索引（Prefix Index）：大字段直接建全量索引在物理上不可行（超出单个索引键最大字节数限制），必须用前缀索引，如 `ALTER TABLE article_content ADD INDEX idx_content_prefix (content(20));`。
    * 绝不滥用 `SELECT *`：大字段对网络传输带宽是极大负担，业务 SQL 必须按需声明字段名。

### 原生 JSON 类型与提取语法

* **与存储为普通 TEXT/VARCHAR 的差异**
    * 存为 `VARCHAR` 时数据库视 JSON 字符串为无序死文字，读取必须全量取回应用层，由 Fastjson/Gson 等框架全量解析反序列化才能读取其中一个属性。
    * 原生 `JSON` 内部使用紧凑二进制树状结构存储，键名建立内部索引查找表，引擎可在磁盘/内存中根据键名瞬间跳转到指定字段的物理偏移量直接提取，支持以 $O(1)$ 或二分查找的效率定位特定键值。
    * 写入时 MySQL 在底层严格校验 JSON 语法合法性，格式不符合规范直接拒绝入库。
    * 版本起点：从 MySQL 5.7 开始官方正式引入原生 `JSON` 数据类型，并在 MySQL 8.0 中进行深度优化。
* **表结构定义与箭头操作符提取**
    * `CREATE TABLE test_json (id INT PRIMARY KEY AUTO_INCREMENT, js JSON);` 可写入含嵌套对象的 JSON，尝试存入不闭合括号或非法 JSON 串立即报错拦截。
    * 箭头操作符 `->` 配合以 `$` 开头的 JSON Path 表达式做层级下钻：`$` 代表根节点，`$.key` 定位顶层对象中的键，`$.object.sub_key` 对嵌套子对象深层递归点查。
    * 查询示例：
        ```sql
        SELECT
            js->'$.name' AS full_name,
            js->'$.age' AS user_age,
            js->'$.address.province' AS province,
            js->'$.address.city' AS city
        FROM test_json;
        ```
    * `->` 提取出的字符串值外围默认保留双引号（保留 JSON 原生字面量类型）；需要不带引号的纯文本展示值时使用双箭头操作符 `->>`，等价于 `JSON_UNQUOTE(js->'$.name')`。

### 空间数据类型（GIS）概述

* **单值几何对象**
    * `GEOMETRY`：可以容纳任何类型几何对象的基类。
    * `POINT`：点（坐标，如经度与纬度 `(X, Y)`）。
    * `LINESTRING`：线（由两点或多点连接而成的线段或轨迹）。
    * `POLYGON`：多边形（由多条线闭合构成的区域，如配送范围、行政区划）。
* **复合几何集合对象**
    * `MULTIPOINT` 为多点集合，`MULTILINESTRING` 为多线集合，`MULTIPOLYGON` 为多个多边形集合（如群岛地貌），`GEOMETRYCOLLECTION` 为任意几何对象的混合容器。
    * 空间类型符合开放地理空间联盟（OGC）标准，支撑 LBS、地图导航、打车路线追踪以及“查找附近的商家”等业务场景，通常配合空间分析函数（如 `ST_Distance` 计算经纬度球面距离）与空间 R 树索引协同使用。

## 类型选型基线、规约与高阶方案


### 默认选型基线与底部思维

* **三类默认类型**
    * 整数类型默认 `INT`（或 `BIGINT`），核心考量是兜底容量风险，防止数值溢出导致写入崩溃。
    * 小数与金额默认 `DECIMAL(M, D)`，强精度保证，彻底杜绝浮点数二进制舍入误差。
    * 日期与时间默认 `DATETIME`，跨度大（至 9999 年），无 2038 年溢出风险。
* **整数类型的兜底原则**
    * 只要没有极度明确的节省空间诉求，不出意外一律使用 `INT` 类型；有人看到状态码或类型编码就定义成 `TINYINT`，看到可能几千上万的数据就定义成 `SMALLINT`（最大仅支持 32767 或无符号 65535），业务上线后数据增长超出预期时，严格模式下 `INSERT` 直接报错中断，非严格模式下被截断写入上限值导致业务数据错乱。
    * 选择 `INT`（4 字节，带符号可达 21 亿、无符号可达 42 亿）作为默认值，本质是用微不足道的存储成本买下整个存储系统的可靠性保障。
    * 全局唯一流水号、自增主键、超大流水日志直接一步到位升级为 `BIGINT`（8 字节）。
    * MySQL 8.0 之前常见的 `INT(11)`、`INT(4)` 写法中括号数字并不代表能存储的最大数值大小；MySQL 8.0 已正式不推荐（Deprecated）在整数类型后附加显示宽度括号，现代建表语句直接书写 `INT` 即可。

### 定点数与日期时间的刚性要求

* **DECIMAL 必须显式指定参数**
    * 涉及价格、金额、费率、核算分摊等资金相关场景一律推荐定点数 `DECIMAL`，且必须显式指定精度 `M`（总位数）与标度 `D`（小数位数）。
    * 仅写裸 `DECIMAL` 时 MySQL 底层等价于 `DECIMAL(10, 0)`，默认标度 `D` 为 0 意味着字段彻底失去小数位，任何写入的小数部分都会被四舍五入抹掉；必须按业务明确写成形如 `DECIMAL(10, 2)` 的形式。
* **日期时间稳定性优先**
    * `TIMESTAMP` 占用 4 字节，相比占 5 字节（MySQL 5.6.4 及以后优化版本）或 8 字节（老版本）的 `DATETIME` 略省空间且具备时区自动转换特性，但最大有效时间仅到 `2038-01-19 03:14:07`（受 32 位有符号整型上限限制）。
    * 企业级架构中许多合同到期日、按揭贷款期、会员长期权限早已规划到几十年之后，使用 `TIMESTAMP` 极易引发 2038 年溢出灾难。
    * `DATETIME` 覆盖 `1000-01-01 00:00:00` 到 `9999-12-31 23:59:59`，彻底屏蔽系统运行的时间跨度边界风险；虽需应用层自行统一处理时区，但从底层持久化可靠性角度是最具容错能力的默认选项。

### 阿里巴巴开发手册的四条类型规约

* **非负数值字段强制使用 unsigned**
    * 规则：任何字段如果存储的数值在业务语义上是非负的，必须为其加上 `unsigned` 属性。
    * 底层依据：有符号 `INT`（32 位）为 `[符号位 1 bit][数值位 31 bits]`，范围 $-2147483648$ 到 $2147483647$；无符号 `INT UNSIGNED` 为 32 位全数值位，范围 $0$ 到 $4294967295$。
    * 自增主键 ID、商品库存量、用户年龄、访问 PV、点赞数等绝不可能为负的实体，保留负数区间是无意义资源浪费；附加 `unsigned` 后符号位转化为有效数值位，在不增加任何物理存储字节的前提下正数上限扩大一整倍，相当于把主键用尽的风险向后推迟一倍时间。
    * 浮点类型语法上也支持 `unsigned`，但其底层采用 IEEE 754 编码且在现代数据库规范中被高度边缘化，收益有限，主要战场集中于整型家族。
* **小数类型强制使用 DECIMAL 并严禁浮点**
    * 规则：小数类型必须使用 `DECIMAL`，禁止使用 `FLOAT` 和 `DOUBLE`。
    * 根源：十进制小数部分转二进制通常产生无限循环小数位，例如 $0.1_{10} = 0.00011001100110011..._2$；受限于 `FLOAT`（32 位、23 位尾数）与 `DOUBLE`（64 位、52 位尾数）的存储位宽，超出尾数长度的部分只能被硬件强制截断或舍入。
    * 后果：业务逻辑上完全相等的两个浮点数用 `=` 查询可能永远返回 false；执行 `SUM()` 累加时账目总额会多出一分或少出一分钱。
    * `DECIMAL` 底层不采用 IEEE 754 浮点编码，而是转换为特定的紧凑十进制格式（每 9 个十进制数字打包为 4 字节的整型序列）存储与运算，每一位数字物理上绝对精确。
* **字符串长度分级规约**
    * 长度 $\le 5000$ 用 `VARCHAR`；长度 $> 5000$ 应升级为 `TEXT` 类型，并建议将 `TEXT` 字段从主表中剥离，单独建立一张附加表做一对一关联存储。
    * 理由一：避免主表行记录膨胀引发聚簇索引利用率暴跌——InnoDB 数据以数据页（Page）为单位加载进 Buffer Pool，每页标准大小 16KB；含大量长文本字段导致单行体积急剧膨胀时，一个数据页容纳的行数暴跌，全表扫描、范围查询或非覆盖索引回表必须加载成倍的磁盘数据页。
    * 理由二：规避高频变更产生的存储碎片与空间空洞（Table Holes / Fragmentation）——大文本字段物理底层往往存放在独立于聚簇索引页之外的溢出页（Off-page），高频 `UPDATE`/`DELETE` 时因长度变动剧烈，释放出的溢出页与数据块无法被其他固定长度行记录复用。
    * 隔离收益：即使未来产生严重存储碎片，也可单独针对该子表执行 `OPTIMIZE TABLE` 进行空间回收与表重构，完全不阻塞主核心业务表的正常读写。

### 超出 DECIMAL 上限的拆分存储方案

* **问题边界**
    * `DECIMAL(M, D)` 中 `M` 最大限制 65、`D` 最大限制 30，已足以支撑绝大多数日常业务；但在天体物理模拟、区块链高位加密货币单位（如以太坊最小单位 Wei，$1 \text{ ETH} = 10^{18} \text{ Wei}$）、外汇微秒级高频微点差计算中依然可能面临溢出。
* **拆分存储法的字段设计**
    * 整数部分字段：使用 `BIGINT` 或独立的 `DECIMAL` 存储该数值的整数位。
    * 小数部分字段：使用独立的 `BIGINT` 或 `DECIMAL` 存储该数值的小数部分，记录其放大 $10^N$ 倍后的实际基数与有效精度指数。
    * 应用层（如 Java 服务的底层计算框架）读取这两个字段后组装成 `BigDecimal` 或自研大数运算库进行高精度运算；物理层面两个字段各自承担一部分存储，彼此不会发生精度溢出。
* **字符串选型的决策顺序**
    * 先判断字符串长度是否基本固定：固定则选 `CHAR(N)`，不固定再判断最大长度是否 $\le 5000$。
    * 最大长度 $\le 5000$ 选 `VARCHAR(N)`；$> 5000$ 选 `TEXT` 且独立拆分子表。
    * `CHAR` 典型应用为手机号（11 位）、MD5 密文（32 位）、UUID、身份证号、状态定长代码；`VARCHAR` 典型应用为用户住址、商品标题、个人简介、动态评论。

## 数据完整性与约束的分类体系


### 数据完整性的四大维度

* **数据完整性的定义与目标**
    * > **定义**：数据完整性是指数据库中数据的精确性（Accuracy）与可靠性（Reliability），本质是通过数据库底层机制防止库中存在不符合业务语义规定的垃圾数据，防止因客户端输入错误、并发异常或异常事务导致脏数据入库。
    * 反面例证：把年龄定义为 `INT` 后写入 `-5` 或 `300` 从纯类型角度看完全合法；把部门编号定义为 `INT` 后写入部门表中不存在的 `9999` 底层存储绝不报错；允许两个人用一模一样的用户名注册后，`WHERE` 条件根本无法单独命中某一条记录。
* **实体完整性（Entity Integrity）**
    * 要求表中每一行记录都代表一个唯一的客观实体，同一个表中绝不允许存在两条完全相同、无法区分的记录。
    * 若无区分个体的机制，业务系统给某个特定用户充值 100 元时执行 `UPDATE users SET balance = balance + 100 WHERE name = '张三' AND ...`，无论条件怎么拼都会同时修改这两条记录，没有任何手段把它们物理隔离开。
    * 实现手段：主键约束（`PRIMARY KEY`）或唯一约束（`UNIQUE`）。
* **域完整性（Domain Integrity）**
    * “域”指的是字段或列（Attribute / Column），要求指定列的输入值必须落在合法有效的值域范围之内，例如年龄限定 `0 ~ 120` 岁、性别限定在特定枚举选项内、考试成绩在 `0 ~ 100` 分之间。
    * 实现手段：基础数据类型（如 `TINYINT UNSIGNED` 规避负数）、枚举（`ENUM`）、非空约束（`NOT NULL`）、默认值（`DEFAULT`）、检查约束（`CHECK`）。
* **引用完整性（Referential Integrity）**
    * 解决多表关联时的数据合法性与一致性；员工表 `employees` 的 `department_id` 指向部门表 `departments`，若插入 102 号员工时随手写 `department_id = 100` 而部门表中根本没有 100 号部门，这名员工在物理架构上就失去了立锥之地。
    * 实现手段：外键约束（`FOREIGN KEY`），数据库引擎在写入或更新时自动校验，被引用的主表记录不存在时从表数据坚决不予写入。
* **用户自定义完整性（User-defined Integrity）**
    * 针对特定业务逻辑与规则设立的定制约束，来源于应用层特定的业务契约。
    * 实例：用户注册时用户名必须全平台唯一（前端 `blur` 失焦时发异步请求校验，数据库底层仍须有唯一性约束防止并发绕过）；登录密码、支付密码列必须强制非空；进阶规则如“本部门经理薪资不得高于本部门职工平均工资的 5 倍”“订单总金额必须等于各商品明细金额之和”。
    * 实现手段：数据库约束、触发器或应用层业务校验。

### 约束的技术定位与三维分类

* **约束的定义与技术定位**
    * > **定义**：狭义上的约束（Constraint）是指在数据库表级别设立的、直接作用在字段上的强制性限制规则。
    * 约束是关系型数据库与普通文件存储系统之间最本质的技术分水岭之一：普通文本文件或 NoSQL 文档存储把数据校验完全推给应用层代码，一旦应用层出现 Bug 或有人直接连库执行 SQL，脏数据就会直接渗透。
    * MySQL 约束固化在存储引擎元数据之中，任何试图破坏约束的 DML 操作（`INSERT`、`UPDATE`、`DELETE`）都会被引擎拦截并回滚。
* **按作用列数划分**
    * 单列约束：约束仅独立作用在表中某一个单独字段上，例如单独要求 `id` 为主键或 `email` 唯一，生效与否只取决于这单一列的取值。
    * 多列约束（复合/联合约束）：约束同时作用在两个或两个以上字段的联合组合之上，例如选课系统中不允许“同一个学生重复选同一门课”，需将 `(student_id, course_id)` 绑定为联合唯一约束，只有当两个字段的取值同时重复时才触发拦截。
* **按定义位置划分**
    * 列级约束（Column-level Constraint）：声明在字段类型之后，如 `id INT PRIMARY KEY`、`name VARCHAR(20) NOT NULL UNIQUE`；语法紧凑直观，但涉及多列联合的约束（联合主键、联合唯一键、外键）在 MySQL 中无法通过列级语法声明。
    * 表级约束（Table-level Constraint）：所有字段定义完毕后在建表语句末尾用独立语法子句声明，如 `CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES tb_department(id)`；能灵活给多列组合赋予联合约束并命名。
    * > **易错点**：并非所有功能约束都支持表级声明——在 MySQL 标准语法中 `NOT NULL` 和 `DEFAULT` 只能以列级方式声明在列属性中。
* **按业务功能划分的六大约束**

| 约束关键字 | 约束名称 | 核心作用与完整性维度 |
| :--- | :--- | :--- |
| `NOT NULL` | 非空约束 | 强制字段必须有确定值，不允许存储 `NULL`（域完整性） |
| `UNIQUE` | 唯一性约束 | 保证该列（或列组合）中数据全局唯一、不可重复，但允许 `NULL`（实体/用户自定义完整性） |
| `PRIMARY KEY` | 主键约束 | `NOT NULL` 与 `UNIQUE` 的物理结合体，作为数据行的唯一身份凭据（实体完整性） |
| `FOREIGN KEY` | 外键约束 | 建立两表之间的参照联动，限定从表数据必须对应主表合法数据（引用完整性） |
| `CHECK` | 检查约束 | 通过布尔表达式限制列的取值范围（MySQL 8.0 开始正式生效强制校验）（域完整性） |
| `DEFAULT` | 默认值约束 | 当插入记录未显式传值时，自动赋予预设的默认静态值（域完整性） |


### 约束的生命周期管理

* **建表时声明约束（CREATE TABLE）**
    * 在绝大多数正规软件工程开发中的标准范式与推荐做法。
    * 设计表结构与书写建表 DDL 的初始阶段，架构师与开发人员必须结合业务用例想清楚每个字段的业务边界：哪些字段必填、哪些不可重复、关联关系如何锚定。
    * 在 `CREATE TABLE` 时直接固化约束既能杜绝脏数据趁虚而入，也不会产生后期的结构改造包袱。
* **运行期追加或删除约束（ALTER TABLE）**
    * 追加使用 `ALTER TABLE ... ADD CONSTRAINT ...` 或 `ALTER TABLE ... MODIFY ...`；删除使用 `ALTER TABLE ... DROP ...`。
    * > **易错点**：在已存有大量线上数据的表中通过 `ALTER TABLE` 追加约束风险极高——现存数据中已有重复值或 `NULL` 时，追加 `UNIQUE` 或 `NOT NULL` 会导致整个 DDL 报错中止，必须先人工清洗脏数据；千万级大表上修改列属性或重构索引即使有 Online DDL 支持，也可能消耗巨大 I/O 与元数据锁（MDL）资源。
    * > **结论**：能在一开始建表时规划好的约束，坚决不要留到后期上线后再去改。
* **约束元数据的探查入口**
    * `SELECT * FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_NAME = 'employees';` 可看到约束所属的库表名称、约束对象名称（`CONSTRAINT_NAME`）以及约束类型（`CONSTRAINT_TYPE`，如 `PRIMARY KEY`、`UNIQUE`、`FOREIGN KEY`）。
    * 约束在执行读操作时同样深度参与：主键约束和唯一约束在底层会自动伴生聚簇索引和唯一二级索引，MySQL 优化器解析执行计划时正是依赖这些由约束派生的索引结构实现毫秒级 B+ 树快速寻址。

## 非空约束


### 核心语义与语法边界

* **默认行为与显式开启**
    * 非空约束强制限定表中某个字段（列）的值绝不允许为 `NULL`。
    * MySQL 默认行为下，不加任何特殊修饰的所有基础数据类型（整数、浮点、字符、时间等）都默认允许存储 `NULL`；只有显式声明 `NOT NULL` 关键字，引擎才会对该列开启强校验保护。
* **仅限列级声明且拒绝多列联合**
    * `NOT NULL` 必须且只能声明在对应字段的类型定义之后，MySQL 不支持在表末尾使用独立的 `CONSTRAINT ... NOT NULL` 表级语法。
    * 正因为它只能依附于具体的单个字段声明，数据库不存在所谓的“联合非空约束”；如果一张表中有 5 个字段都要求必填，必须在每一个字段后面独立书写 `NOT NULL`。
* **NULL 与空字符串、数字 0 的本质区别**
    * 空字符串 `''`：长度为 0 的字符常量，占用实际存储空间，具有明确的字符串类型语义。
    * 数字 `0`：数值系统中的具体整数，具有明确的代数意义。
    * `NULL`：代表“未知（Unknown）”“未定义”或“不存在”；物理底层 InnoDB 引擎需通过每行记录头信息中的“NULL 值列表（NULL Value Bitmap）”用位标记专门标识该字段是否为 NULL。
    * > 结论：字段被 `NOT NULL` 修饰时，写入 `0` 或空字符串 `''` 完全合法且能正常通过校验，约束拦截的仅仅是裸的 `NULL` 标识。

### 建表期定义与 DML 拦截验证

* **建表期声明**
    * `CREATE TABLE test1 (id INT NOT NULL, last_name VARCHAR(15) NOT NULL, email VARCHAR(25), salary DECIMAL(10, 2));`：`id` 与 `last_name` 强制非空，`email` 与 `salary` 允许为空。
    * 业务依据：新员工入职时可能尚未分配企业邮箱、薪资定级可能尚在审批流中，允许为空符合业务弹性；但没有 ID 和姓名在业务逻辑上绝对无法成立。
    * `DESC test1;` 中 `Null` 列显示 `id`、`last_name` 为 `NO`，`email`、`salary` 为 `YES`。
* **显式赋值 NULL 的拦截**
    * 正常写入 `INSERT INTO test1(id, last_name, email, salary) VALUES (1, 'Tom', 'tom@126.com', 3400.00);` 成功。
    * 显式置空受保护字段 `INSERT INTO test1(id, last_name, email, salary) VALUES (2, NULL, 'jerry@126.com', 4500.00);` 抛出 `ERROR 1048 (23000): Column 'last_name' cannot be null`；试图将主键标识 `id` 设为 `NULL` 同样阻断。
* **省略列引发的“默认值缺失”报错链条**
    * `INSERT INTO test1(id, email) VALUES (2, 'abc@126.com');` 报出的不是 `Column cannot be null`，而是 `ERROR 1364 (HY000): Field 'last_name' doesn't have a default value`。
    * 底层推导：INSERT 未指定某列时，MySQL 第一动作是检索该列是否配置了 `DEFAULT`；已配置则自动填充默认值，未配置则尝试采用系统标准回退值 `NULL`；该列又被声明 `NOT NULL` 导致回退失效，系统处于“既没有合法值填充、又不允许用 NULL 垫底”的死锁状态，因此最终报出“该字段没有默认值”。
* **UPDATE 场景的防护**
    * `UPDATE test1 SET last_name = NULL WHERE id = 1;` 被拦截并报出 `Column 'last_name' cannot be null`。
    * `UPDATE test1 SET email = NULL WHERE id = 1;` 顺利执行，未受非空约束的列允许回退为 `NULL`。

### 运行期追加与删除

* **`MODIFY` 是唯一维护通道**
    * 非空约束的增加与移除不是通过 `ADD CONSTRAINT` 或 `DROP CONSTRAINT`，而是通过修改列定义（`MODIFY`）实现。
    * 追加语法：`ALTER TABLE 表名 MODIFY 字段名 字段类型 NOT NULL;`
    * 删除语法：`ALTER TABLE test1 MODIFY email VARCHAR(25) NULL;`（重写完整类型定义并显式指定 `NULL` 或直接省略 `NOT NULL`），执行后 `DESC test1;` 中 `Null` 属性重新变回 `YES`。
* **存量脏数据冲突与两步走策略**
    * 若表中 `email` 已被更新为 `NULL`，直接执行 `ALTER TABLE test1 MODIFY email VARCHAR(25) NOT NULL;` 会立即拒绝并抛出 `ERROR 1138 (22004): Invalid use of NULL value`。
    * > **易错点**：向一个已经存在数据的列追加 `NOT NULL` 约束时，只要表中存在哪怕一条记录的该字段值为 `NULL`，整个 DDL 语句就会直接失败。
    * 标准流程：先 `SELECT COUNT(*) FROM table WHERE col IS NULL;` 确认存量空数据规模；再 `UPDATE` 为存量 `NULL` 记录补充业务初值或占位符；确认全量非空后执行 `ALTER TABLE ... MODIFY col TYPE NOT NULL;`；最后用 `DESC table;` 复核元数据。

## 唯一约束


### 业务语义与字段选型

* **核心作用与选型矩阵**
    * 唯一性约束强制限定表中某个字段（或多个字段的组合）的值不得重复。
    * 适合建唯一约束：`id`/工号（全局排他标识）、`email`（通信私密性要求）、身份证号/手机号（自然人真实唯一映射）。
    * 坚决不能建唯一约束：`last_name`（姓名，重名现象极其普遍）、`salary`（工资，密薪制与同岗同酬）、状态码/性别/年龄（天然有限值域）。
* **三类反例与正例的业务根据**
    * 姓名：现实生活中同名同姓普遍，若把姓名列设为 `UNIQUE`，公司录用第二个叫“张超”的员工时人事录入会被数据库报主键重复打回，业务逻辑上极其荒谬。
    * 邮箱：员工企业邮箱必须加 `UNIQUE`，若不设唯一性约束而因录入失误导致两名员工拥有完全相同邮箱，向该邮箱发送年终奖明细、人事变动或商业机密私信会被同时抄送给无关人员。
    * 薪资：密薪制下同职级、同年资员工拿一模一样底薪极其正常，一旦工资要求全员唯一会导致正常的同岗位薪资无法录入，并引发团队内部动荡与离职风险。

### 建表期声明与 DML 校验

* **列级与表级两种声明语法**
    * 列级：`id INT UNIQUE`，直接将 `UNIQUE` 紧跟在字段类型定义之后；书写精炼但无法为约束显式指定业务友好名称，MySQL 默认采用该列的字段名作为约束名。
    * 表级：`CONSTRAINT uk_test2_email UNIQUE(email)`；`CONSTRAINT` 声明约束实体，`uk_test2_email` 为自定义名称（工程规范通常以 `uk_` 代表 Unique Key、后接 `表名_列名`，也可用 `uni_` 前缀），`UNIQUE(email)` 用括号圈定作用字段。
    * 省略 `CONSTRAINT 约束名` 直接书写 `UNIQUE(email)` 建表依然成功，MySQL 同样默认以该字段名作为约束名。
* **约束状态探查与重复拦截**
    * `DESC test2;` 输出中受约束字段的 `Key` 列显示为 `UNI`；`SELECT * FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_NAME = 'test2';` 可检索出两条 `CONSTRAINT_TYPE = 'UNIQUE'` 记录，一条名为默认的 `id`，另一条为自定义的 `uk_test2_email`。
    * 重复 `id` 报 `ERROR 1062 (23000): Duplicate entry '1' for key 'test2.id'`；重复 `email` 报 `ERROR 1062 (23000): Duplicate entry 'tom@126.com' for key 'test2.uk_test2_email'`。
* **NULL 值的多重并存机制**
    * 实测：对声明为 UNIQUE 的 `email` 字段连续两次写入 `NULL` 均执行成功，即不仅可以存入 `NULL`，而且可以写入任意多个 `NULL` 值。
    * 关系代数依据：SQL 三值逻辑（Three-Valued Logic）体系中 `NULL` 代表未知（Unknown），`NULL = NULL` 的比较结果不是 `TRUE` 而是 `UNKNOWN`，既然任何一个 `NULL` 与另一个 `NULL` 都无法判定为相等，唯一性检验算法就认为它们互不冲突，因而可以无限次存入。
    * > **提示**：如果业务上既要求字段唯一又坚决不让存入空值，必须将两个约束组合使用：`email VARCHAR(25) NOT NULL UNIQUE`。

### 复合唯一约束

* **强制表级声明的语法要求**
    * 列级约束只能紧随单列之后、无法将多列同时打包，因此复合唯一约束必须使用表级约束语法声明：
        ```sql
        CREATE TABLE tb_user (
            id INT,
            name VARCHAR(15),
            password VARCHAR(25),
            CONSTRAINT uk_user_name_pwd UNIQUE(name, password)
        );
        ```
    * 判定规则：单列相同允许并存（`(A=1,B=100)` 与 `(A=1,B=200)`、`(A=2,B=100)` 均可写入），组合全同时立即触发 `Duplicate entry` 阻断。
* **多对多选课模型实战**
    * 建表：`student (sid INT PRIMARY KEY, sname VARCHAR(20), tel VARCHAR(11), card_id VARCHAR(18))`；`course (cid INT PRIMARY KEY, cname VARCHAR(20))`；`student_course (id INT PRIMARY KEY, sid INT, cid INT, score DECIMAL(4, 1), UNIQUE KEY (sid, cid))`。
    * 业务模型：一个学生可以选修多门不同的课（`sid` 相同、`cid` 不同）合法；同一门课可被多名不同学生选修（`cid` 相同、`sid` 不同）合法；同一个学生在同一门课程上只能产生一份唯一的最终考试成绩。
    * 已存在 `sid=2, cid=1002` 记录时再次插入 `(2, 1002)` 触发 `ERROR 1062 (23000): Duplicate entry '2-1002' for key 'student_course.sid'`。

### 追加、删除与唯一索引绑定

* **两种等价的追加语法**
    * 表级追加：`ALTER TABLE 表名 ADD [CONSTRAINT 约束名] UNIQUE(字段名);`，例如 `ALTER TABLE test2 ADD CONSTRAINT uk_test2_sal UNIQUE(salary);`，推荐使用并显式命名。
    * 列级追加：`ALTER TABLE 表名 MODIFY 字段名 字段类型 UNIQUE;`，通过重写列定义追加约束。
    * > **易错点**：执行追加唯一约束前，表中现存历史数据若已包含重复值，DDL 语句将直接报错崩溃——例如表中已有两条工资同为 `4500.00` 的记录，执行 `ADD UNIQUE(salary)` 会立刻报 `ERROR 1062: Duplicate entry '4500.00'`，必须先排查并去重存量数据。
* **唯一约束与唯一索引的绑定闭环**
    * 自动伴生：在某个列（或列组合）上声明唯一约束时，底层存储引擎会自动且无条件地在背后为该列创建一个唯一索引（Unique Index），因为快速判断新值是否重复必须依赖 B+ 树索引实现 $O(\log N)$ 级检索，否则每次插入都要全表扫描。
    * 删除路径唯一性：MySQL 官方没有提供独立的物理约束删除指令，删除唯一约束的唯一法定途径就是删除底层伴生的唯一索引，语法为 `ALTER TABLE 表名 DROP INDEX 索引名;`。
    * 索引命名三条规则：显式指定约束名时索引名完全等于该约束名（`uk_test2_email`）；单列唯一约束未命名时索引名默认等于该字段列名；多列复合唯一约束未命名时索引名默认等于括号内排在第一位的字段列名（`UNIQUE KEY (sid, cid)` 的 `CONSTRAINT_NAME` 正是 `sid`）。
    * 删除实操：`ALTER TABLE test2 DROP INDEX last_name;` 与 `ALTER TABLE test2 DROP INDEX uk_test2_sal;`，执行后 `DESC test2;` 中对应字段的 `UNI` 标记彻底消失，再写入完全重复的值数据库将顺利放行。

## 主键约束


### 核心语义与硬性规则

* **实体完整性与行的唯一标识**
    * > **定义**：主键约束（`PRIMARY KEY`）在语义上等价于“唯一约束 + 非空约束”的严格组合，声明为主键的列既不允许多次重复也不允许存放任何 `NULL` 值。
    * 唯一约束虽要求值不能重复，但允许字段多次插入 `NULL`；若业务执行 `WHERE email IS NULL` 可能瞬间弹出十几条甚至上千条记录，只要存在空值该行记录就失去精准定位的基准。
* **一表最多一个主键**
    * 无论声明的是单列主键还是多列组合的复合主键，整张表的主键定义有且仅有一套。
    * 根本原因在于物理存储：InnoDB 中整张表所有行记录的物理排布与存储叶子节点全部依照主键索引构建（聚簇索引），若允许两个互不干涉的主键，引擎无法确定整表数据按哪个字段顺序落盘、树的分裂与节点寻址听谁的。
* **主键名称恒为 PRIMARY**
    * 列级约束语法下 `information_schema.TABLE_CONSTRAINTS` 中 `CONSTRAINT_TYPE` 显示为 `PRIMARY KEY`、`CONSTRAINT_NAME` 固定为 `PRIMARY`，SQL 不允许用户显式指定约束名。
    * 表级约束中写入 `CONSTRAINT pk_test5_id PRIMARY KEY (id)` 执行完全正常、没有任何语法报错，但查询元数据时 `CONSTRAINT_NAME` 依然是 `PRIMARY`。
    * > **结论**：在 MySQL 中主键约束与底层对应的主键索引名称永远是 `PRIMARY`，即使用 `CONSTRAINT 名字` 自定义命名也会被无条件忽略；表级主键定义中写自定义名称没有任何实际意义，直接书写 `PRIMARY KEY (列名)` 即可。

### 聚簇索引与回表代价

* **B+ 树的数据组织方式**
    * 整张表的数据本身就是一颗按主键组织排序的聚集索引（Clustered Index）树，根节点与分支节点只负责维护主键索引键值的路由，底层叶子节点直接存放整行的数据内容。
    * 叶子节点双向链表有序贯通；基于主键检索时查询引擎可直接顺着主键 B+ 树在 $O(\log N)$ 时间复杂度内精确定位到叶子节点并读取整行数据。
* **回表的底层代价**
    * 普通辅助索引（如普通 `UNIQUE` 索引）树的叶子节点存放的仅仅是对应记录的主键值。
    * 引擎查到主键值后，还必须拿着该主键值到主键 B+ 树中再走一次完整的寻址过程，这一过程在工程上称为回表。
    * 这一机理从底层解释了主键在表结构设计中的绝对统治地位。

### 建表、校验与复合主键

* **建表期声明与 DML 拦截**
    * 列级写法：`CREATE TABLE test4 (id INT PRIMARY KEY, last_name VARCHAR(15), salary DECIMAL(10, 2), email VARCHAR(25));`，部门编号、员工编号等天然具备唯一编号性质的列最适合作为主键。
    * 主键值重复：`INSERT INTO test4(id, last_name, salary, email) VALUES (1, 'Jerry', 5500.00, 'jerry@126.com');` 报 `ERROR 1062 (23000): Duplicate entry '1' for key 'test4.PRIMARY'`。
    * 主键值空：显式 `VALUES (NULL, ...)` 或插入时省略 `id` 列且该列未配置默认生成规则，均抛出 `ERROR 1048 (23000): Column 'id' cannot be null`。
* **复合主键的两项硬性指标**
    * 语法要求：涉及多列联合，复合主键绝不能使用列级约束语法定义，必须使用表级约束语法，如 `CREATE TABLE user1 (id INT, name VARCHAR(15), password VARCHAR(25), PRIMARY KEY (name, password));`。
    * 联合唯一：只有参与复合主键的所有列的值全部同时相同才判定为重复，只要其中任何一列不同即视为不同记录——`(1,'Tom','abc')` 与 `(1,'Tom1','abc')` 组合值未重复，允许共存。
    * 绝对非空：组成复合主键的每一个列都必须具备非空属性，绝不允许任何一列出现 `NULL`；`INSERT INTO user1(id, name, password) VALUES (1, NULL, '123');` 立即报 `ERROR 1048 (23000): Column 'name' cannot be null`。
    * > **易错点**：复合主键中的“非空”是对每一个构成列的绝对约束，任何一列传入 `NULL`，无论其余列的值多么唯一，都会直接触发 `Column cannot be null` 异常。
* **选课关联模型的经典应用**
    * 拓扑：学生表 `Student` 的 `student_id (PK)` 与课程表 `Course` 的 `course_id (PK)`，共同汇入选课表 `Student_Course` 的 `student_id (FK)`、`course_id (FK)`，并在该表内以 `PRIMARY KEY(sid, cid)` 联合设为主键。
    * 若业务上不额外设立自增流水号 `id`，一个学生选择一门课程这一业务实体就是由学号与课程编号联合决定的：一名学生对同一门课程只能选一次，同时学号与课程编号都必须实打实存在，二者联合设为主键天然契合实体完整性要求。

### 主键的维护与生产禁令

* **追补与删除的语法及其副作用**
    * 追补：`ALTER TABLE test6 ADD PRIMARY KEY (id);`，执行后 `DESC test6;` 中 `Key` 列出现 `PRI`，`Null` 列自动从 `YES` 翻转为 `NO`。
    * 追补前提：表中已存在存量数据时，目标列必须既没有重复值也没有任何 `NULL`，否则 ALTER 操作直接中断并抛出异常。
    * 删除：`ALTER TABLE test6 DROP PRIMARY KEY;`，因为一张表最多只有一个主键且名字固定为 `PRIMARY`，语法中无需指定约束名。
    * 删除后 `DESC test6;` 显示 `Key` 列 `PRI` 标识消失，但 `id` 字段的 `Null` 属性仍然保留为 `NO`（该细节在工程实践中无需专门记忆）。
* **严禁删除主键**
    * 执行 `ALTER TABLE ... DROP PRIMARY KEY` 后底层会依次发生：聚簇索引树瞬间被判定失效；InnoDB 退而求其次在表中搜索是否存在非空的唯一索引（`UNIQUE NOT NULL`），找到则用那个列重构整张表的 B+ 树；若连非空唯一索引都没有，后台必须为每一行记录自动生成一个隐藏的 6 字节 `DB_ROW_ID`，并依据这个隐藏列强行把整张表重构为一颗新的 B+ 树。
    * 线上运行的千万级核心业务表删除主键意味着底层几千万条数据行必须在磁盘上全部重新挪动、重新物理排序、重新分裂与分配数据页，引发长时间严重锁表与磁盘 I/O 暴涨，直接导致线上服务雪崩，且没有任何业务收益。
* **严禁频繁变更主键字段值**
    * `UPDATE test4 SET salary = ...` 只修改叶子节点中行记录对应列的物理存储数据，属于常见无风险操作。
    * 但执行 `UPDATE test4 SET id = 9999 WHERE id = 1` 时，因主键决定该记录在整个 B+ 树中的物理排序位置，原本位于第一个叶子数据页的行记录必须被物理删除，引擎须在 B+ 树末端叶子页重新开辟空间迁移整行数据，期间高频引发页分裂（Page Split）与页合并（Page Merge），导致严重物理碎片和 I/O 阻塞。
    * > **结论**：主键自被写入的那一刻起就应具备永久不变的唯一标识属性；选定合理的主键策略（自增整数、业务流水号或雪花 ID）并在数据生命周期内保持不可变更性，是关系型数据库物理设计中必须死守的底线规范。

## 自增约束


### 核心概念与三条前置条件

* **自动增长的业务价值**
    * 若完全依赖业务代码在应用层计算下一个 ID 并显式插入，高并发插入场景下极易发生并发主键冲突；若让用户或操作员手工输入编号，遗漏与重复不可避免。
    * `AUTO_INCREMENT` 为特定列提供由数据库内核驱动的自增服务：执行 `INSERT` 时若该列未被显式赋值，存储引擎自动在当前已记录的最大数值基础上累加步长（默认步长为 1），生成一个全新的唯一整数。
    * 自增约束通常与主键约束深度绑定，将主键唯一标识的生成逻辑下沉到数据库引擎内部，借助底层自增锁与并发控制机制保证主键流水号在高并发下的严格单调递增与并发安全。
* **三条必须遵守的物理硬性规则**
    * 唯一性（单表限制）：一个数据表中有且只能拥有一个自增列，不允许同时为两列配置自动增长。
    * 类型限制（必须为整数）：被声明为 `AUTO_INCREMENT` 的列，其数据类型必须是整数族类型（`TINYINT`、`SMALLINT`、`INT`、`BIGINT` 等），浮点型或字符串类型严禁配置自增。
    * 索引限制（必须为键）：自增列必须是键（Key）的一部分，通常为主键（`PRIMARY KEY`）或者唯一键（`UNIQUE`）。
    * 违规报错：在未建立任何键索引的普通列上添加自增属性，如 `CREATE TABLE test_error (id INT AUTO_INCREMENT, name VARCHAR(15));`，执行器直接中断并抛出 `ERROR 1075 (42000): Incorrect table definition; there can be only one auto column and it must be defined as a key`。

### 计数器推进规则

* **缺省值与占位符的递增行为**
    * 建表：`CREATE TABLE test7 (id INT PRIMARY KEY AUTO_INCREMENT, last_name VARCHAR(15));`
    * 省略自增列 `INSERT INTO test7(last_name) VALUES ('Tom');`、显式传 `0` 占位 `VALUES (0, 'Jerry')`、显式传 `NULL` 占位 `VALUES (NULL, 'Bob')` 三种写法均成功，依次得到 `id` 为 1、2、3。
    * 写入 `0` 或 `NULL` 时 MySQL 不报错也不把 `id` 置为 0 或空，而是识别为“请求系统自增”，在上一条最大记录值基础上顺延累加。
* **人工指定数值抬高计数器**
    * `INSERT INTO test7(id, last_name) VALUES (10, 'Rose');` 执行完全成功，表中新增 `id = 10` 的数据。
    * 紧接着使用缺省方式 `INSERT INTO test7(last_name) VALUES ('Jack');`，新记录的 `id` 变成 11。
    * > **规律**：当人工显式指定一个大于当前自增序列的数值时，自增计数器会被强行拔高至该数值；后续缺省插入的数据将从这个人为拔高的新最大值开始继续向上累加。
    * 建表语句末尾显式指定 `AUTO_INCREMENT = 100` 同样会导致序列从 100 起步。
* **负数写入的边界行为**
    * `INSERT INTO test7(id, last_name) VALUES (-10, 'David');` 执行成功，查询时 `-10` 被排在整张表的最前面——作为主键索引，底层 B+ 树按键值真实物理大小升序组织，负数自然排在正数 1 之前。
    * 后续不传自增列继续插入时，引擎依然只依据全表最大的正数值（此时是 11）继续累加生成 12，绝不会在负数基础上向 0 递增。

### 自增属性的追加与剥离

* **`ALTER TABLE ... MODIFY` 追加**
    * 未加自增的 `CREATE TABLE test8 (id INT PRIMARY KEY, last_name VARCHAR(15));`，其 `DESC` 的 `Extra` 列为空、无自增标记。
    * `ALTER TABLE test8 MODIFY id INT AUTO_INCREMENT;` 执行后 `Extra` 列刷新为 `auto_increment`。
    * > **注意**：使用 `MODIFY` 追加自增属性的前提是该列必须已经在表内具备主键约束或唯一性约束；普通无索引字段直接执行同样触发 `Incorrect table definition` 错误。
* **剥离自增**
    * `ALTER TABLE test8 MODIFY id INT;` 用 `MODIFY` 重新定义该列的数据类型与约束且不写 `AUTO_INCREMENT` 关键字即可，执行后 `Extra` 列的 `auto_increment` 标记彻底移除，主键退化为纯手工填值的普通主键。
    * 工程实践中自增主键绝大多数在 `CREATE TABLE` 阶段一次性成型，极少在存量业务表上追加或剥除。
* **生产环境的自增使用规范**
    * > **结论**：一旦数据表的主键列配置了 `AUTO_INCREMENT`，在编写任何应用层业务代码的 `INSERT` 语句时绝不要将该自增列纳入 INSERT 字段列表，所有流水号生成全部交由数据库内核托管，坚决杜绝任何人工干预或跳号传值。
    * 规范目的：避免主键序列产生不可控的碎片空隙与业务歧义。

### 版本差异：重启后的计数器持久化

* **对比实验的四阶段**
    * 建表写入：`CREATE TABLE test9 (id INT PRIMARY KEY AUTO_INCREMENT); INSERT INTO test9 VALUES (0), (0), (0), (0);` 两版本表中均存在 `1, 2, 3, 4`。
    * 产生裂缝：`DELETE FROM test9 WHERE id = 4; INSERT INTO test9 VALUES (0);` 表中数据变为 `1, 2, 3, 5`——曾经插入过 4，即使被删除自增计数器依然推进到了 5，这种中间缺失的序列现象称为自增裂缝。
    * 清空尾部并重启：`DELETE FROM test9 WHERE id = 5;` 后两版本表都只剩 `1, 2, 3`，再分别执行 `net stop mysql57 / net start mysql57` 与 `net stop mysql80 / net start mysql80`。
    * 重启后首次插入：执行 `INSERT INTO test9 VALUES (0);`，MySQL 5.7 中新记录 `id` 显示为 `4`，MySQL 8.0 中新记录 `id` 坚定显示为 `6`。
* **MySQL 5.7 的内存计数器与重启回退缺陷**
    * 5.7 及更早的 InnoDB 实现中，表的自增计数器（Auto-increment Counter）仅仅保存在操作系统内存中，从来不向磁盘文件持久化。
    * 服务重启后内存计数器归零，该表接收到重启后第一次查询或插入请求时，InnoDB 在底层被动触发一次全表扫描寻址 `SELECT MAX(id) FROM test9 FOR UPDATE;`，检索出磁盘上的最大值 3，强行把内存计数器初始化为 $3 + 1 = 4$。
    * > **易错点**：如果外部系统（支付流水、第三方发票系统）已引述并缓存了曾经生成过的 `id = 4` 和 `id = 5`，服务器意外重启后数据库重新复用了这两个旧编号，直接打破主键的业务不可篡改性与全局时序性。
* **MySQL 8.0 的 Redo Log 持久化与崩溃恢复**
    * Redo Log 协同写盘：每一次计数器自增变动都作为重做事件被同步写入 `Redo Log`（重做日志）。
    * 元数据字典持久化：发生系统检查点（Checkpoint）时，最新的计数器数值精确落盘到 InnoDB 内置的元数据字典（Metadata Dictionary）系统表中。
    * 崩溃恢复无缝衔接：服务重启时存储引擎在 Crash Recovery 流程中直接从重做日志与元数据字典还原崩溃前的最大计数器峰值，根本不需要向数据表发起 `MAX(id)` 查询；即使历史 `4` 和 `5` 已被彻底物理删除，8.0 依然清楚记得序列曾走到 5，重启后平滑衔接到 6。

## 外键约束与级联等级


### 核心规范与物理硬性约束

* **引用完整性与主从表拓扑**
    * 主表（父表）如 `dept` 部门表以 `did: 10` 为被引用键，从表（子表）如 `emp` 员工表通过 `dept_id: 10` 外键列建立引用关系。
    * 从表中的外键列相当于从表派驻到主表中的“外交官”，两张表能否建立合法建交必须依凭该列与主表特定凭证之间的精确比对。
* **外键列的三大物理红线**
    * 主表被引用列的索引限制：从表外键列所引用的主表那一列必须是主表的主键（`PRIMARY KEY`）或者唯一键（`UNIQUE`）；若主表被引用的字段仅是没有任何唯一性保障的普通列，建表必抛异常。
    * 数据类型与逻辑意义一致：从表外键列与主表被引用的主键/唯一键列在数据类型上必须完全一致（或严格兼容），业务逻辑语义必须完全对齐。
    * 命名空间与多外键支持：一个数据表中可以声明多个外键约束，例如员工表 `employees` 既可通过 `department_id` 关联部门表，也可通过 `job_id` 关联岗位表，还可通过 `manager_id` 自身外键关联上级管理者。
    * 违规报错：主表 `dept1` 未设主键时创建带外键的 `emp1` 直接抛出 `ERROR 1822 (HY000): Failed to add the foreign key constraint. Missing index for constraint 'fk_emp1_dept_id' in the referenced table 'dept1'`；用 `ALTER TABLE dept1 ADD PRIMARY KEY (dept_id);` 补齐后建表顺利通过。
* **建表与删表的物理时序法则**
    * > **结论**：建表时必须先创建主表（父表）再创建从表（子表），因为从表在解析外键时需要立即校验主表及其被引用字段的存在性；删表时必须先删除从表（子表）再删除主表（父表），若在从表尚存且维持引用时强行删除主表，数据库会直接拒绝执行并报错拦截。

### 自动伴生索引与拦截机制

* **外键自动生成普通 B+ 树索引**
    * 执行 `DESC emp1;` 时外键列 `department_id` 对应的 `Key` 字段显示为 `MUL`（Multiple）。
    * 机制价值：确保向子表写入数据或父表发生更新删除时，引擎不必进行代价极高的子表全表扫描，而是借助该普通索引以 $O(\log N)$ 极速定位子表记录进行引用合法性验证。
* **从表非法引用的拦截**
    * 主表 `dept1` 尚未录入任何部门时向从表写入归属 10 号部门的员工，抛出 `ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails`。
    * 正确顺序：先 `INSERT INTO dept1(dept_id, dept_name) VALUES (10, 'IT');` 向主表添加合法部门，再向从表插入员工即执行成功。
* **主表非法删除与更新的阻断**
    * 主表中已有员工依附于 10 号部门时，`DELETE FROM dept1 WHERE dept_id = 10;` 被内核阻止并报 `ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails`。
    * `UPDATE dept1 SET dept_id = 20 WHERE dept_id = 10;` 同样被直接阻止并抛出完全相同的错误代码 1451。
    * > **易错点**：日常业务中语法完全合规的 `DELETE` 或 `UPDATE` 莫名执行失败，往往就是外键在底层阻止数据孤岛产生的直接体现。

### 运行期维护与外键删除的索引残留

* **`ALTER TABLE` 追加外键**
    * 两张表已独立建好后需要建立物理关联时使用：`ALTER TABLE emp2 ADD CONSTRAINT fk_emp2_dept_id FOREIGN KEY (dept_id) REFERENCES dept2(dept_id);`
    * 前置条件是主表 `dept2` 的被引用列已具备主键或唯一约束。
* **删除外键必须显式清理残留索引**
    * 删除语法需指定外键约束名（因为一张表可能存在多个外键）：`ALTER TABLE emp1 DROP FOREIGN KEY fk_emp1_dept_id;`
    * 运行元数据查询可见外键约束确实消失，但 `SHOW INDEX FROM emp1;` 显示原本由外键附带生成的普通索引 `fk_emp1_dept_id` 依然顽固残留。
    * > **易错点**：删除外键约束（`DROP FOREIGN KEY`）仅仅移除了外键的校验机制，当初自动创建的底层索引不会被联动删除；需要彻底净化表结构必须显式调用 `ALTER TABLE emp1 DROP INDEX fk_emp1_dept_id;`。

### 级联等级与联动行为

* **四类级联等级语义**

| 约束等级关键字 | 核心处理逻辑 | 适用场景与业务效果 |
| :--- | :--- | :--- |
| `CASCADE` | 级联联动：父表记录更新或删除时，子表对应记录自动同步更新或同步物理删除 | 适合强生命周期绑定的主从结构（如订单主表与订单明细表） |
| `SET NULL` | 置空兜底：父表记录更新或删除时，子表对应列自动置为 `NULL` | 适合弱依附关系（如部门撤销，员工暂留公司待转岗） |
| `RESTRICT` / `NO ACTION` | 严格阻止：子表若存在关联记录，绝对拒绝父表的更新或删除操作（默认行为） | 核心资产、关键业务维度，必须人工逐级确认 |
| `SET DEFAULT` | 默认值回退：父表变动时子表回退至列默认值 | 规范定义，但 MySQL InnoDB 引擎暂不支持，实际不可用 |

* **复合级联规则实测**
    * 建表：`CREATE TABLE emp (eid INT PRIMARY KEY, ename VARCHAR(15), did INT, CONSTRAINT fk_emp_did FOREIGN KEY (did) REFERENCES dept(did) ON UPDATE CASCADE ON DELETE SET NULL);`，主表填入 `(1001, '教学部'), (1002, '财务部'), (1003, '咨询部')`，员工填入 `(1, '张三', 1001), (2, '李四', 1001), (3, '王五', 1002)`。
    * 验证级联更新：执行 `UPDATE dept SET did = 1004 WHERE did = 1002;` 后查询王五记录，其 `did` 字段已被数据库内核全自动同步刷新为 1004。
    * 验证级联置空：执行 `DELETE FROM dept WHERE did = 1004;` 语句执行成功、不再报错，王五依然健在但所属 `did` 已全自动被安全重置为 `NULL`。
    * > **提示**：若要在外键上配置 `ON DELETE SET NULL`，从表的外键字段本身绝对不能有 `NOT NULL` 约束，否则引擎在置空时会因列属性冲突而报错。
* **生产推荐的级联组合**
    * 涉及物理外键的传统系统中最成熟的配置组合通常是 `ON UPDATE CASCADE ON DELETE RESTRICT`。
    * 含义：主表编码更新允许自动同步到底层从表，避免主从编码失序；但试图删除父实体必须严防死守拒绝执行，杜绝因一次手抖误删主表而导致下游成千上万条明细数据被连环物理抹杀。

### 物理外键与应用层逻辑外键的取舍

* **高并发下物理外键的锁开销与性能损耗**
    * 每次向子表插入或修改数据，数据库都必须在内部向父表申请行锁或表锁进行跨表校验；写入并发达到数千甚至数万 QPS 时，大量数据库连接被阻塞在跨表行锁等待上，系统吞吐量呈断崖式下跌。
    * 若存在多级外键将引发锁链路连环蔓延，导致主表并发阻塞、锁等待甚至死锁（Deadlock）。
    * 级联风暴：一旦触发生命周期较长的主表级联删除或更新，数据库后台会瞬间裂变出数十万次关联子表修改，产生严重的“更新风暴（Update Storm）”，将整个数据库服务器的 I/O 和 CPU 瞬间打满。
* **阿里巴巴开发手册强制禁用外键与级联**
    * > **【强制】不得使用外键与级联，一切外键概念必须在应用层解决。**
    * 说明原文要点：学生表中的 `student_id` 是主键，成绩表中的 `student_id` 为外键；如果更新学生表中的 `student_id` 同时触发成绩表中的 `student_id` 更新即为级联更新。外键与级联引用的结构适合于单机低并发，不适合分布式、高并发集群；级联更新是强阻塞，存在数据库更新风暴的风险；外键还会极大地影响数据库的插入速度。
    * 规范本质是把原本压在数据库引擎单点上的强计算与校验开销卸载出来，分摊到横向扩展能力极强的应用服务器集群上。
* **分布式与分库分表下的逻辑外键治理**
    * 物理边界隔离：微服务体系下“用户表”归属用户中心服务、存放在物理节点 A，“订单表”归属交易服务、存放在物理节点 B，单机数据库引擎根本无法跨越网络和跨物理实例去建立底层外键。
    * 分库分表断链：单表数据破千万后通过 Sharding-JDBC 或 MyCat 按用户 ID 哈希分片到多个子库，父表与子表往往被拆分到完全不同的物理分片中，物理外键机制彻底报废。
    * > **结论**：现代工程最佳实践是保留“逻辑外键”概念但坚决剥离“物理外键”约束——在从表设计中依然保留 `department_id` 语义字段，但 `CREATE TABLE` 时绝不写 `FOREIGN KEY` 语句。
    * 校验下沉：插入前通过 Spring Boot / Java 代码先从 Redis 缓存中校验部门是否存在；多表之间的数据生命周期同步通过分布式事务（如 Seata）或异步消息队列（MQ）进行最终一致性保障。

## 检查约束与默认值约束


### 检查约束 CHECK 与版本断层

* **语义与建表语法**
    * `CHECK` 的核心职能是验证表中某个字段录入的数据是否满足特定的布尔逻辑表达式或数值范围要求。
    * `CREATE TABLE test10 (id INT, last_name VARCHAR(15), salary DECIMAL(10, 2) CHECK (salary > 2000));`
    * MySQL 8.0 实测：写入 `2500.00` 执行成功；写入 `1500.00` 立即被内核拦截并抛出 `ERROR 3819 (HY000): Check constraint 'test10_chk_1' is violated.`
* **MySQL 5.7 的形同虚设**
    * > **定义**：在 MySQL 5.7 及更早版本中，引擎为兼容 SQL 语法允许用户书写 `CHECK` 关键字建表且不报语法错误，但在底层物理执行时彻底忽略该约束（完全不起作用）；直到 MySQL 8.0.16 开始，MySQL 才真正由内核引擎落地支持 `CHECK` 约束的物理校验。
    * 实测：在 MySQL 5.7 中执行同样的建表语句没有任何语法警告，强行写入 `1500.00` 后被顺顺利利写入了数据表。
    * > **易错点**：目前国内外仍有大量企业在生产环境使用 MySQL 5.7，在 5.7 实例上声明 `CHECK` 约束纯属心理安慰。
* **跨数据库的标准支持差异**
    * Oracle 10g 平行测试：`CREATE TABLE test10 (id INT, last_name VARCHAR2(15), salary NUMBER(10, 2) CHECK (salary > 2000));` 写入 `1500.00` 立即抛出经典约束违规异常 `ORA-02290: check constraint (SCOTT.SYS_C005921) violated`。
    * 商业数据库（Oracle）与开源学院派标杆（PostgreSQL）对 ANSI SQL 标准的贯彻更严谨；MySQL 长期滞后支持，跨数据库迁移与架构设计时必须保持清醒认知。

### 默认值约束 DEFAULT 与生命周期管理

* **建表语法与赋值回退逻辑**
    * `CREATE TABLE test11 (id INT, last_name VARCHAR(15), salary DECIMAL(10, 2) DEFAULT 2000.00);`，`DESC test11;` 中 `Default` 列准确显示为 `2000.00`。
    * 场景 A：`INSERT INTO test11(id, last_name, salary) VALUES (1, 'Tom', 3000.00);` 显式传入值生效。
    * 场景 B：`INSERT INTO test11(id, last_name) VALUES (2, 'Tom1');` INSERT 列列表中完全省略 `salary`，查询结果中第二行数据的 `salary` 自动回退为配置的默认值 `2000.00`。
* **`ALTER TABLE ... MODIFY` 修改与剥离**
    * 追加或修改：对无默认值的 `test12` 执行 `ALTER TABLE test12 MODIFY salary DECIMAL(8, 2) DEFAULT 2500.00;`，`DESC` 显示字段精度成功变更为 `DECIMAL(8,2)` 且 `Default` 刷新为 `2500.00`。
    * 剥除：再次使用 `MODIFY` 重新声明列类型且不追加 `DEFAULT` 关键字，即 `ALTER TABLE test12 MODIFY salary DECIMAL(8, 2);`，`Default` 列恢复为 `NULL`。

### NULL 规避的字段设计规范

* **常见建表写法**
    * 成熟 DDL 中常见形如 `\`user_name\` VARCHAR(32) NOT NULL DEFAULT '',` `\`status\` TINYINT NOT NULL DEFAULT 0,` `\`amount\` DECIMAL(10,2) NOT NULL DEFAULT 0.00` 的组合定义。
* **组合使用 `NOT NULL` 与确定性默认值的四项技术原因**
    * 运算具有传染性毒性：任何数值与 `NULL` 进行算术运算（`NULL + 1`、`NULL * 10`）返回值统统退化为 `NULL`，业务逻辑一旦出现意外的 NULL 渗透会导致财务或积分计算全线清零。
    * 三值逻辑破坏判断意图：`NULL` 参与条件比对时既不是真（TRUE）也不是假（FALSE）而是未知（UNKNOWN），会导致简单的 `WHERE status != 1` 漏掉所有 `status IS NULL` 的记录。
    * 底层索引检索效率低下：InnoDB 的 B+ 树物理存储中 `NULL` 列需要专门的 Null Flag 标记位特殊维护，在复合索引与范围过滤时针对允许为 NULL 的列做寻址和排序，开销显著高于具有明确字面值的非空字段。
    * 防范应用层空指针异常（NPE）：从数据库映射到 Java 等强类型语言的对象实体时，空值极易在下游引发 `NullPointerException`；赋予默认空串或零值可极大保障系统健壮性。

### 约束全景落地共识

* **建表期定型，运行期不动**
    * 关于非空、唯一、主键和默认值的规划必须在详细设计阶段敲定，在 `CREATE TABLE` 时一次性建立到位。
    * 生产环境运行期间严禁通过 `ALTER TABLE` 随意添加或卸载约束。
* **物理约束精简化**
    * 主键不可或缺，非空与默认值强力推行。
    * 对于外键与检查约束，由于跨版本兼容性（如 5.7）与高并发锁竞争瓶颈，主流方案坚决采用业务应用层校验方案替代数据库物理外键与物理检查。
* **外键对存储引擎的限制**
    * 单表独立场景下，用户可以根据业务读写特征在语法上自由指定存储引擎（高并发事务使用 `InnoDB`，纯归档高压缩使用 `Archive`，内存高频读写使用 `Memory` 等）。
    * 一旦两张表之间需要建立物理外键约束，外键绝对不允许跨存储引擎建立；主表与从表必须使用完全相同的存储引擎，且该引擎本身必须具备外键支撑能力；由于 `MyISAM` 等轻量级引擎底层根本不支持事务与外键机制，建立外键关联时主从两表必须同时选用 `InnoDB`。

## 约束综合维护与 DDL 演进实务


### 现有表的主键与外键动态挂载

* **裸表补主键与聚簇索引机理**
    * 初始状态：`CREATE TABLE dept2 (id INT, name VARCHAR(20));` 与 `CREATE TABLE emp2 (id INT, name VARCHAR(20));` 均未声明任何约束。
    * 追加语法：`ALTER TABLE emp2 ADD PRIMARY KEY (id);`（标准语法，不显式起约束名）。
    * 底层理由：以 InnoDB 为例，底层数据以 B+ 树结构组织，整张表的数据本身就是一颗按主键组织排序的聚集索引树，每个叶子节点完整保存整行数据；若建表时未显式声明主键，InnoDB 会寻找表内第一个不允许为 NULL 的唯一索引（Unique Not Null）作为聚簇索引；若连这样的唯一索引都没有，系统底层被迫自动生成一个长度为 6 字节的隐式自增行指针（`ROW_ID`）来搭建 B+ 树——这种隐式机制无法在业务层面直接检索，还会因全局共享并发分配计数器带来隐患。
    * > **结论**：任何一张业务数据表都必须提供主键，绝不要把选择权留给数据库自行猜测。
* **追加主键的前提与命名无效性**
    * > **易错点**：写 `ALTER TABLE emp2 ADD CONSTRAINT pk_emp2_id PRIMARY KEY (id);` 语法不会报错但属于无用功，因为一张表的主键唯一且系统底层统一强制命名为 `PRIMARY`，自定义名字刷新查看系统结构时依然显示为 `PRIMARY`。
    * 前提条件：表中已存有历史数据时，被声明为主键的列中所有现有数据必须已提前满足 `NOT NULL` 与全局唯一性；若已有数据存在重复的 `id = 1` 或包含 `NULL`，该 DDL 语句必定报错回滚。
* **外键列追加的两步操作**
    * 第一步新增字段：`ALTER TABLE emp2 ADD dept_id INT;`
    * > **注意**：从表外键字段的名称（`dept_id`）与主表被引用的主键名称（`id`）可以完全不同、并不要求同名；但两者的字段数据类型必须严格完全一致（此处主从两表均为 `INT`）。
    * 第二步建立外键：`ALTER TABLE emp2 ADD CONSTRAINT fk_emp2_deptid FOREIGN KEY (dept_id) REFERENCES dept2(id);`，执行后刷新表结构会发现在从表索引列表里自动多出一个对应的普通二级索引。
    * 前置条件：被引用的主表字段必须已具备主键约束或唯一性约束。

### 旧表约束重构

* **主键与自增的一步到位合并写法**
    * 传统思路拆成两步：先 `ADD PRIMARY KEY` 追加主键约束，再通过 `MODIFY` 修改字段属性增加 `AUTO_INCREMENT`。
    * 推荐合并写法：`ALTER TABLE books MODIFY id INT PRIMARY KEY AUTO_INCREMENT;` 一条语句同时完成主键约束追加与自增属性挂载；执行后 `DESC books;` 可见 `id` 的 `Key` 列变为 `PRI`、`Extra` 属性标注 `auto_increment`，可读性与执行效率显著优于多次 DDL 分步执行。
* **非空约束的批量修正**
    * 非空约束不同于外键或独立索引，它是直接依附于字段类型的列级修饰属性，给现有字段添加或取消非空约束必须使用 `MODIFY` 语法重新声明该列的完整类型定义。
    * 语句序列：`ALTER TABLE books MODIFY name VARCHAR(50) NOT NULL;`、`MODIFY authors VARCHAR(100) NOT NULL;`、`MODIFY price FLOAT NOT NULL;`、`MODIFY pubdate YEAR NOT NULL;`、`MODIFY num INT NOT NULL;`
    * 校验：执行后 `DESC books;` 中除允许留空的备注字段 `note` 保持 `Null = YES` 外，其余核心字段的 `Null` 标识全部变为 `NO`。
    * > **易错点**：本例历史代码中价格使用了 `FLOAT`，真实商业项目与电商系统中严禁使用 `FLOAT` 或 `DOUBLE` 存储涉及金钱的字段，生产环境应一律采用高精度定点数 `DECIMAL(M, D)`。
    * > **提示**：定义 `num INT` 时不需要习惯性写成 `INT(11)`——未开启零填充时括号内数字仅代表显示宽度，且在 MySQL 8.0 中整数显示宽度属性已明确废弃。

### 新建系统的内嵌约束设计

* **建库字符集差异**
    * MySQL 5.7 环境中默认字符集为 `latin1`，建库时必须显式声明 `CREATE DATABASE IF NOT EXISTS test04_company CHARACTER SET 'utf8';`（或 `utf8mb4`）。
    * MySQL 8.0 之后默认字符集已天然升级为 `utf8mb4`，省去了手工声明字符集的步骤。
* **基准主表的约束内嵌与命名风格**
    * `CREATE TABLE IF NOT EXISTS offices (officeCode INT PRIMARY KEY, city VARCHAR(50) NOT NULL, address VARCHAR(50), country VARCHAR(50) NOT NULL, postalCode VARCHAR(15), CONSTRAINT uk_office_postalcode UNIQUE (postalCode));`
    * `postalCode` 要求全局唯一，虽可直接在字段后紧跟 `UNIQUE` 作为列级约束，但此处采用表级约束写法并显式赋予约束名 `uk_office_postalcode`，好处是后续维护或通过 `ALTER TABLE ... DROP INDEX` 删除时能精准通过命名索引操作。
    * 命名规范：表内字段采用小驼峰（`officeCode`、`postalCode`），而 SQL 传统工程习惯更推荐全小写配合下划线的蛇形命名（Snake Case，如 `office_code`）；Windows 平台下底层不区分字段大小写，但为杜绝 Linux 生产环境大小写敏感策略引发的突发故障，团队必须选定一种规范并保持一致。
* **从表全量约束与类型失配深坑**
    * `CREATE TABLE employees (employeeNumber INT PRIMARY KEY AUTO_INCREMENT, last_name VARCHAR(50) NOT NULL, first_name VARCHAR(50) NOT NULL, mobile VARCHAR(25) UNIQUE, officeCode INT NOT NULL, jobTitle VARCHAR(50) NOT NULL, birth DATETIME NOT NULL, note VARCHAR(255), sex VARCHAR(5), CONSTRAINT fk_emp_officecode FOREIGN KEY (officeCode) REFERENCES offices(officeCode));`
    * 显示宽度与物理存储：若写 `officeCode INT(10)`，括号内的 `10` 仅代表展示宽度，没有对底层存储空间做任何压缩，依然独占 4 个字节的物理磁盘空间。
    * ZEROFILL 导致的类型畸变：单纯写 `INT(10)` 没有实质意义；若加上 `ZEROFILL`（即 `INT(10) ZEROFILL`），MySQL 会在底层自动为该字段追加 `UNSIGNED` 属性；此时若主表 `offices` 中的 `officeCode` 只是普通有符号 `INT`，两者类型冲突，外键创建语句会直接因数据类型定义不匹配而硬性报错退出。
    * > **结论**：外键字段与主表被引用字段的数据类型必须完全匹配；若主表字段未声明 `UNSIGNED`，从表外键字段绝对不可附带 `UNSIGNED` 或带有潜在副作用的 `ZEROFILL`。
    * 外键命名通常遵循 `fk_从表名_字段名` 前缀命名法（如 `fk_emp_officecode`）。

### 表结构的后续演进与生产防线

* **字段物理顺序调整与列重命名**
    * 移动列位置：`ALTER TABLE employees MODIFY mobile VARCHAR(25) AFTER officeCode;`，调整后 `DESC employees;` 显示 `mobile` 成功迁移至 `officeCode` 后方，且原有的 `UNIQUE` 唯一性约束完整保留、不受物理顺序变动影响。
    * 字段更名：`ALTER TABLE employees CHANGE birth employee_birth DATETIME NOT NULL;`，使用 `CHANGE` 语法改名时必须完整补写其原始数据类型。
    * > **提示**：原表字段风格多为驼峰式（如 `jobTitle`），题目要求改成 `employee_birth` 下划线风格时，实际工程项目中严禁在同一个表内混合使用两种命名法则——字段命名混搭不仅造成调用层 ORM 映射困难，还会显得底层表结构设计极不规范。
    * 收紧字段：初始建表将 `sex` 定义为 `VARCHAR(5)` 存在空间浪费与长度冗余，性别通常仅需存储单一字符（`'M'`/`'F'` 或 `'男'`/`'女'`），收紧为 `ALTER TABLE employees MODIFY sex CHAR(1) NOT NULL;`
* **字段废弃与新增的操作规范**
    * 删除字段：`ALTER TABLE employees DROP COLUMN note;`
    * > **易错点**：生产环境中执行 `DROP COLUMN` 必须极其慎重——DDL 操作属于原子级隐式提交，执行后无法通过事务回滚（`ROLLBACK`）撤回；若事前未执行完备的物理冷备或逻辑备份，一旦字段被物理剔除，该列包含的历史生产数据将彻底永久丢失。企业生产规范中废弃字段通常先在应用层停止读写、在数据库保留或软下线，确需清理时必须先执行全量备份。
    * 新增字段：`ALTER TABLE employees ADD favorite_activity VARCHAR(100);`，默认情况下新追加的字段会自动追加至表的末尾列。
* **整表重命名与失效验证**
    * `RENAME TABLE employees TO employees_info;` 执行完毕后原表名 `employees` 即刻失效。
    * 若继续执行 `DESC employees;`，系统明确抛出 `Error 1146 (42S02): Table 'test04_company.employees' doesn't exist` 异常，必须使用全新的表名 `DESC employees_info;` 才能正常访问。
