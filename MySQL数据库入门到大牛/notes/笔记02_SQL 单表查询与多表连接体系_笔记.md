## 1. SQL 语言定位与功能分类

> **一句话主旨**：交代 SQL 的历史与标准演进，划定 DDL、DML、DCL 三条主线的职责边界，并说明 SELECT 独占七个章节的原因。

* **SQL（Structured Query Language，结构化查询语言）**
    * 1974 年由 IBM 圣何塞研究实验室在学术论文中提出，最初名为 SEQUEL（Structured English Query Language，结构化英语查询语言），因商标冲突精简重命名为 SQL。
    * 核心语法规则自诞生沿用至今，骨架没有推倒重来；相比之下 1991 年诞生的 Python 经历 Py2/Py3 破坏性语法断层，1995 年诞生的 Java 已从 Java 8 迭代到 Java 17。
    * 数据持久化层面，只要采用关系型数据库，SQL 就是唯一的通用交互手段；非关系型数据库（NoSQL，即 Not Only SQL）是对关系型数据处理能力的补充而非替代。
    * 在 TIOBE 排行榜中，SQL 早期因被判定缺乏变量声明与流程控制能力而未被收录；纳入排测后长期稳定在前十名（Top 10）以内。
    * > 来源: P12

* **ANSI SQL 标准的演进序列**
    * 标准化工作由美国国家标准局（ANSI，American National Standards Institute）联合各大厂商与 ISO 推进。
    * `SQL-86`：首个正式的 SQL ANSI 标准；`SQL-89`：在 86 标准基础上的增量完善；`SQL-92`（亦称 `SQL2`）：奠定现代关系型数据库语法体系的里程碑标准；`SQL-99`（亦称 `SQL3`）：引入递归查询、触发器及对象关系特性。
    * 现代各类数据库遵循的核心语法规范，绝大多数牢固建立在 SQL-92 与 SQL-99 框架之上。
    * 各厂商在兼容 ANSI 标准的同时保留专属语法扩展：MySQL 用 `LIMIT` 分页与 `AUTO_INCREMENT` 自增，Oracle 早期用 `ROWNUM` 分页与 `SEQUENCE` 序列，SQL Server 用 `TOP` 分页与 T-SQL 扩展。
    * > 来源: P12, P28

* **DDL（Data Definition Language，数据定义语言）**
    * > 定义：负责定义、修改和管理数据库中的所有数据库对象（Database Objects），包括数据库、表、视图、索引、存储过程、触发器等。
    * 核心命令：`CREATE` 从无到有创建对象；`ALTER` 修改已有对象的内部结构（追加列、修改字段长度、增加外键约束）；`DROP` 从物理磁盘抹除对象及其全部结构与数据；`RENAME` 重命名已有对象；`TRUNCATE` 清空表中全部数据行并保留表结构定义。
    * > 来源: P12

* **DML（Data Manipulation Language，数据操作语言）**
    * > 定义：对已存在的数据表中的数据记录（Records / Rows）进行增、删、改、查等细粒度读写操作。
    * 四条指令：`INSERT` 追加一条或多条全新记录；`DELETE` 删除符合条件的数据行；`UPDATE` 原地修改现有记录中某字段的取值；`SELECT` 从一张或多张表检索目标数据。
    * `DELETE` 与 `DROP`、`TRUNCATE` 作用层级不同：前者删除数据行，后两者作用于对象与整表数据。
    * > 来源: P12

* **DCL（Data Control Language，数据控制语言）**
    * > 定义：管理数据库访问的安全权限与底层事务控制，确保多用户并发访问环境下的数据一致性与访问合规性。
    * 事务控制板块：`COMMIT` 把当前事务的增删改固化到物理磁盘使其永久有效；`ROLLBACK` 撤销当前事务内未提交的操作恢复至初始状态；`SAVEPOINT` 在事务链条中打保存点，支持部分回滚到指定标记处。
    * 用户与权限板块：`GRANT` 向指定用户授予数据库、表或列级操作权限；`REVOKE` 回收已赋予用户的特定权限。
    * > 来源: P12

* **DQL 与 TCL 的拆分逻辑**
    * 三类划分（本课程与主流业界采用）为 DDL + DML + DCL；细分为四类或五类时，把 `SELECT` 单独剥离为 DQL（Data Query Language，数据查询语言），把 `COMMIT` 与 `ROLLBACK` 单独剥离为 TCL（Transaction Control Language，事务控制语言）。
    * 剥离依据：查询操作使用频度极高、复杂度极深，且只读特性与写操作存在本质差异；事务控制聚焦 ACID 状态机维护，与账号赋权存在领域差异。
    * 无论归纳为三类、四类还是五类，包含的关键字与语法指令完全一致。
    * > 来源: P12

* **SELECT 的“双重之重”**
    * 使用频度：互联网与企业级系统的读写请求比例通常达到 8:2 甚至 9:1 以上；`DDL` 可能几周执行一次，写操作受严格控制，而 `SELECT` 每分每秒承载高并发冲击。
    * 技术复杂度：`INSERT`、按主键 `UPDATE` 的语法模式高度固化，但查询要面对多表关联、子查询嵌套、动态过滤与执行计划优化。
    * 课程章节权重分配：第 3~9 章全面攻坚 `SELECT`，第 10 章讲 DDL 表与对象，第 11 章讲增删改，第 12 章讲数据类型规范。
    * > 来源: P12

## 2. SQL 使用规范与测试数据导入

> **一句话主旨**：区分强制报错的语法规则与工程约定层面的编写规范，并给出 atguigudb 测试库的两种导入路径与数据基线。

* **规则与规范的边界**
    * 规则是数据库解析引擎强制要求的底线，违反后直接报错中断；规范是业内沉淀的工程约定，违反只影响可读性与跨平台稳定性。
    * > 来源: P13

* **语句换行与结束符**
    * 一条 SQL 可以写在单行，也可拆分成多行；复杂查询建议将不同子句独立成行，嵌套结构使用 Tab 或 2~4 个空格缩进。
    * 每条独立执行的命令通常以分号 `;` 结束，命令行客户端中也可使用 `\g` 或 `\G`；分号的核心作用是作为多语句批处理的指令边界切分符。
    * 图形化工具（如 SQLyog、Navicat）中单独选中并执行单条语句时，末尾省略分号仍可识别；批量执行多条语句时缺少分号，解析器会把下一行的 `INSERT` 误判为前一条语句的后续标记并抛出语法错误。
    * `\g` 在命令行客户端中完全等价于分号，但在部分图形化工具（如早期版本 SQLyog）中可能被当作普通字符或表名解析而引发语法错误。
    * 大写的 `\G` 是 MySQL 命令行特有的排版利器，会把查询结果由横向矩阵转置为纵向键值对，适合列数多或字段文本过长的场景，如 `SHOW CREATE TABLE emp\G`。
    * > 来源: P13

* **关键字与标识符的书写限制**
    * 关键字不能被拆分或缩写，不能把 `INSERT` 写成 `INS`，也不能写成 `IN SERT`；关键字不可跨行断开。
    * 常用关键字：`SELECT`、`FROM`、`WHERE`、`ORDER BY`、`GROUP BY`、`INSERT`、`UPDATE`、`DELETE`。
    * 所有小括号 `()`、单引号 `''`、双引号 `""` 必须成对出现；单引号用于包裹字符串常量与日期时间常量（如 `'Tom'`、`'2026-09-14'`、`'2026-09-14 12:00:00'`）。
    * 标准 SQL 中双引号用于给查询结果的列起别名；MySQL 中反引号（着重号）专门用于包裹可能与保留关键字同名的数据库名、表名或字段名。
    * > 来源: P13, P15

* **MySQL 不同对象的大小写敏感性**（下表为 MySQL 8.0 默认行为对照）

    | 逻辑对象 / 语法元素 | Windows 环境（底层不敏感） | Linux 环境（底层敏感） | 工程防坑建议 |
    | :--- | :--- | :--- | :--- |
    | 数据库名（Schema） | 不区分大小写 | 严格区分大小写 | 统一全部小写 |
    | 数据表名（Table） | 不区分大小写 | 严格区分大小写 | 统一全部小写 |
    | 表的别名（Alias） | 不区分大小写 | 严格区分大小写 | 统一全部小写 |
    | 变量名（Variable） | 不区分大小写 | 严格区分大小写 | 统一全部小写 |
    | 列名 / 字段名（Column） | 不区分大小写 | 不区分大小写 | 统一全部小写 |
    | 列的别名（Alias） | 不区分大小写 | 不区分大小写 | 统一全部小写 |
    | SQL 关键字（Keyword） | 不区分大小写 | 不区分大小写 | 统一全部大写 |
    | 内置函数名（Function） | 不区分大小写 | 不区分大小写 | 统一全部大写 |

    * 底层根源：MySQL 的数据库名对应数据目录下的子文件夹，表名对应子文件夹内的表结构与数据存储文件，因此 Linux 的 ext4 或 xfs 文件系统的区分大小写特性被直接传导至数据库层。
    * 建表时表名为小写 `emp`，迁移到未做特殊配置的 Linux 生产服务器上执行 `SELECT * FROM EMP;` 会报错 `Table 'dbname.EMP' doesn't exist`。
    * > **提示**：Linux 下可通过 `my.cnf` 中的系统变量 `lower_case_table_names=1` 强行令表名不区分大小写，但生产架构中绝不能依赖此类特定配置。
    * > 来源: P13

* **行业通用书写规范**
    * 结构与标识符全小写：数据库名、表名、表的别名、字段名、字段别名一律纯小写，多单词之间用下划线 `_` 连接，即 snake_case 蛇形命名法。
    * 语法保留字全大写：SQL 关键字与系统预定义函数（如 `COUNT()`、`SUM()`、`AVG()`、`NOW()`）以及预编译绑定变量建议一律使用大写。
    * 标准示例：
        ```sql
        SELECT employee_id, last_name, salary, department_id
        FROM employees
        WHERE department_id = 90
        ORDER BY salary DESC;
        ```
    * > 来源: P13

* **SQL 注释的三种书写形式**
    * `#` 单行注释：MySQL 数据库专有的扩展语法，Oracle、SQL Server、PostgreSQL 等其他关系型数据库不支持。
    * `-- ` 单行注释：两个连续连字符后面必须至少紧跟一个空格，才会被解析器视为合法注释；该形式符合 ANSI SQL-92 标准，跨平台移植性最高。
    * `/* */` 多行注释：以 `/*` 开始、`*/` 闭合，可跨任意多行。
    * > 易错点：多行注释绝对不允许嵌套。解析器读到第一个 `/*` 后寻找最近的 `*/` 便认定注释块结束，嵌套内部的闭合符会提前截断外层注释，使后续解释文本暴露在注释块外部引发编译中断。
    * > 来源: P13

* **测试库导出导入与数据基线**
    * 导入脚本为 `atguigudb.sql`，建议拷贝到简短磁盘路径（如 Windows 下 `D:\atguigudb.sql`），避免路径含中文字符或深层多级目录。
    * 命令行导入流程：终端执行 `mysql -u root -P 3306 -p` 登录，然后依次执行 `SHOW DATABASES;` → `SOURCE D:/atguigudb.sql;` → `SHOW DATABASES;` → `USE atguigudb;` → `SHOW TABLES;` → `SELECT * FROM employees;`。
    * `SOURCE` 是 MySQL 客户端自带的内部控制指令，不需要在末尾加分号，Windows 路径中斜杠与反斜杠均可，且必须在已登录的命令行交互提示符（`mysql>`）下执行。
    * 图形化导入路径（以 SQLyog 为例）：顶部菜单「工具 (Tools)」→「执行 SQL 脚本... (Execute SQL Script...)」→ 选择脚本文件 → 点击「执行 (Execute)」并在弹窗确认 → 右键根节点或按 `F5` 刷新对象树 → 双击激活 `atguigudb` 库后新建查询标签页验证。
    * 数据基线：`employees` 表恰好包含 **107 条记录**，`departments` 表 27 条记录，`locations` 表含 `location_id`、`city` 等字段，`job_grades` 表 6 条薪资等级记录。
    * 学习路径主张：先导入现成企业数据表、深度剖析 `SELECT` 查询，再学 `CREATE TABLE` 建表设计与增删改操作；市面上超过 90% 的传统数据库书籍采用「建库→建表→插入→查询」的自底向上顺序。
    * > 来源: P13, P17, P25, P27

## 3. SELECT 查询骨架与字段投影

> **一句话主旨**：拆解 SELECT ... FROM 的对称结构与三处高频书写陷阱，并给出员工表的字段语义与关键业务换算口径。

* **SELECT ... FROM 的逻辑分工**
    * `SELECT` 后接字段列表，决定最终结果集包含哪些列，控制数据表格横向维度的宽度，即投影操作；`FROM` 后接数据表名，指明被检索的数据实体存放于哪一张物理表。
    * > 来源: P14

* **伪表（DUAL）**
    * > 定义：`DUAL` 不是物理磁盘上真实存在的一张包含记录的表，而是供系统维持 `SELECT <目标> FROM <数据源>` 语法对称闭环的特殊虚拟标记。
    * 在 MySQL 中，`SELECT 1 + 1;` 与 `SELECT 1 + 1 FROM DUAL;` 在执行计划和解析结果上完全等价；在 ANSI SQL 标准或 Oracle 中查询语句必须严格符合 `SELECT <目标> FROM <数据源>` 结构。
    * 极度简化的查询可以只保留 `SELECT` 与计算表达式，如 `SELECT 1;`、`SELECT 1 + 1, 3 * 2;`；删掉 `SELECT` 直接键入 `1 + 1;` 会被解析引擎中断报错。
    * 携带 `SELECT` 的同时省略 `FROM` 只适用于常量与表达式求值；一旦涉及真实字段投影，数据源不可省略。
    * > 来源: P14, P18

* **全字段检索与指定列投影**
    * `SELECT *` 中的 `*` 代表目标表中定义的所有字段，MySQL 会扫描全部数据并按建表时定义的物理列顺序依次排开返回。
    * `SELECT employee_id, last_name, salary FROM employees;` 只抽取指定三列，其余列被过滤，该操作称为投影（Projection）。
    * > **提示**：`SELECT *` 适合日常学习、代码调试或控制台临时探查；生产系统的高并发业务开发中普遍严禁滥用，原因是全列扫描无法利用覆盖索引优化、会大幅增加网络传输与内存序列化开销，且表结构增删列时返回的数据契约可能导致上层应用反序列化异常。
    * > 来源: P14

* **员工表 employees 的 11 个字段语义**

    | 序号 | 字段名称 | 数据类型 | 业务语义与取值特征 |
    | :---: | :--- | :--- | :--- |
    | 1 | `employee_id` | `INT` | 员工工号，主键，唯一标识一名员工 |
    | 2 | `first_name` | `VARCHAR` | 员工的名字（名） |
    | 3 | `last_name` | `VARCHAR` | 员工的姓氏（姓） |
    | 4 | `email` | `VARCHAR` | 电子邮箱前缀（系统内唯一） |
    | 5 | `phone_number` | `VARCHAR` | 员工联系电话号码 |
    | 6 | `hire_date` | `DATE` | 员工正式入职（雇佣）的日期时间 |
    | 7 | `job_id` | `VARCHAR` | 职位工种编号（外键关联职位表） |
    | 8 | `salary` | `DOUBLE` | 员工每月的基本固定薪资 |
    | 9 | `commission_pct` | `DOUBLE` | 业绩提成率 / 奖金率（可为 `NULL`） |
    | 10 | `manager_id` | `INT` | 该员工的直属管理者（主管）工号 |
    | 11 | `department_id` | `INT` | 该员工所在的部门编号（外键关联部门表） |

    * 在欧美命名体系中 `last_name` 才对应家族姓氏，业务中要求“查询员工的姓氏”时对应列是 `last_name`。
    * `commission_pct` 是业绩提成比例系数而非固定补贴金额，取值通常介于 `0.10` 到 `0.40` 之间；取值为 `NULL` 表示该员工属于非销售岗、不享有提成结算。
    * 真实月收入换算口径：$实际总薪酬 = salary + salary \times commission\_pct$。以 `salary = 9000`、`commission_pct = 0.25` 为例，提成为 $9000 \times 0.25 = 2250$，实际发放 $9000 + 2250 = 11250$。
    * 其余辅助表结构：`departments` 含 `department_id`(PRI)、`department_name`(varchar(30), NOT NULL)、`manager_id`(int(6), YES)、`location_id`(int(4), YES)，共 4 列 27 行；`locations` 含 6 个字段，主键 `location_id`、外键 `country_id`，另有 `street_address`、`postal_code`、`city`、`state_province`。
    * > 来源: P14, P17, P25

* **投影列表的三类书写陷阱**
    * 尾部逗号：逗号是列与列之间的分隔符而非列定义的结束符，`SELECT employee_id, last_name, salary, FROM employees;` 会让解析器在逗号后强期待下一个列名却迎来 `FROM`，抛出 `1064 - You have an error in your SQL syntax... near 'FROM employees'`。
    * 字段拼写错误：引擎会拿 `SELECT` 列表中的每个标识符去数据字典严格比对，把 `salary` 误写为 `salar` 会报 `1054 - Unknown column 'salar' in 'field list'`。
    * > 易错点：在两个字段之间漏掉逗号（如 `SELECT employee_id last_name FROM employees;`）不会报错，而是输出 107 行、表头显示为 `last_name`、数据内容是 `100`、`101`、`102` 等工号的单列结果。原因是 SQL 中两个紧密相连且仅以空格分隔的标识符会被解析引擎自动判定为「原始列」与「列别名」，上述语句在语义上等价于 `SELECT employee_id AS last_name FROM employees;`。
    * > 来源: P14

## 4. 列别名、去重、空值与表元数据探查

> **一句话主旨**：给出列别名的定义方式与引号规范、DISTINCT 去重的语法位置约束、NULL 的运算污染性，以及 DESC 元数据六列的读法。

* **列别名（Column Alias）**
    * > 定义：为查询结果集的列临时指定的显示名称，默认状态下结果集列名与物理表建表字段名完全一致。
    * 三种定义形式：字段名与别名之间用空格直接连接（`SELECT employee_id emp_id`）；使用 `AS` 关键字显式连接（`SELECT employee_id AS emp_id`）；别名含中文、特殊符号或空格时用双引号圈定（`salary * 12 AS "annual salary"`）。
    * `AS` 全称是 `alias`（别名）的前两个字母简写；显式保留 `AS` 能增强自解释性并避免漏写逗号时把下一字段误解析为别名的隐式 Bug。
    * 去掉双引号直接写 `SELECT salary * 12 AS annual salary FROM employees;`，解析引擎读到 `annual` 时认为别名已完整结束，紧随其后的 `salary` 无法识别，抛出 `1064 - You have an error in your SQL syntax... near 'salary FROM employees'`。
    * > **注意**：MySQL 中用单引号包裹别名（如 `'annual salary'`）同样能运行成功，属于方言层面的宽容度妥协；ANSI SQL 国际标准规定单引号只用于字符串与日期常量，列别名必须严格使用双引号。
    * > 来源: P15, P17, P24

* **DISTINCT 去重**
    * `SELECT department_id FROM employees;` 原封不动返回 107 行，`SELECT DISTINCT department_id FROM employees;` 压缩为 **12 行**（11 个具体数字部门编号 + 1 个 `NULL`）。
    * `SELECT DISTINCT job_id FROM employees;` 由 107 行精简为 **19 行**，即全公司设有 19 种有效工种。
    * 底层机制：提取数据后对指定列的值做哈希或排序归并，过滤掉所有重复出现的取值，仅保留唯一的代表行。
    * 语法错误写法 `SELECT salary, DISTINCT department_id FROM employees;` 会直接报错，物理本质是二维关系表必须保证矩形网格结构，`salary` 的 107 行与去重后的 12 行无法在同一结果集内对齐。
    * `SELECT DISTINCT department_id, salary FROM employees;` 语法合法，返回 **74 行**，作用对象是 `(department_id, salary)` 二元组，只有部门编号且工资金额完全相同时才合并。
    * > 来源: P15, P17

* **NULL 与 0、空字符串、文本字面量的辨析**

    | 取值表现 | 技术语义与物理实质 |
    | :--- | :--- |
    | `0`（数值零） | 确定的、已知的具体数值实体（如银行账户余额为 0 元） |
    | `''`（空字符串） | 长度为 0 的确切字符串对象 |
    | `'null'`（文本字面量） | 包含了 4 个字母的普通字符串常量 |
    | `NULL`（空值） | 未知、未定义、缺失或不存在（尚未分配或无法测量） |

    * `department_id` 为 `NULL` 代表刚入职、系统还未确定归入哪个部门；若武断存为 `0` 则代表被确凿分配到了「0 号部门」。
    * > 来源: P15

* **空值运算黑洞法则与 IFNULL 兜底**
    * 任何数值与 `NULL` 进行算术运算（加、减、乘、除），运算结果一律为 `NULL`。
    * 实例：工号 145 员工月薪 14000、提成率 0.40，`salary * (1 + commission_pct) * 12` 正确算出 $14000 \times 1.4 \times 12 = 235200$；工号 100 的月薪 24000 总裁因 `commission_pct` 为 `NULL`，最终「年总薪资」列显示为 `NULL`。
    * 规避方式：显式调用空值置换函数 `IFNULL(expr1, expr2)`，`expr1` 为 `NULL` 时返回兜底值 `expr2`，否则原样返回其真实值。
    * 健壮写法：
        ```sql
        SELECT employee_id, last_name,
               salary * 12 * (1 + IFNULL(commission_pct, 0)) AS "annual salary"
        FROM employees;
        ```
    * > 来源: P15, P17

* **着重号与保留字命名冲突**
    * `SELECT * FROM order;` 必然报错 `1064 - You have an error in your SQL syntax... near 'order'`，因为 `ORDER` 是 `ORDER BY` 的保留字，解析器误以为开发人员准备发起排序子句。
    * 反引号（着重号，键盘数字 1 键左侧符号）包裹后，词法分析器强制将内部字符视为普通对象标识符，如 ``SELECT * FROM `order`;``。
    * 凡是合法的普通标识符加上着重号执行都不会出错（如 ``SELECT `salary` FROM `employees`;``），但会大幅增加代码凌乱度。
    * > **提示**：工程准则是非必要不加着重号，仅在字段名、表名与关键字冲突时精准包裹冲突字段。
    * > 来源: P15

* **常数查询与行数据广播机制**
    * 常量不来源于物理存储中的具体列，但在 `SELECT` 列表中与数据表字段联合查询时，MySQL 会将该常量以广播方式复制到当前查询命中的每一行记录中。
    * 示例：`SELECT '尚硅谷' AS "所属机构", 1001 AS "批次号", employee_id, last_name FROM employees;` 会在 107 行员工数据左侧统一追加两列固定取值。
    * > 来源: P15

* **DESCRIBE / DESC 与表结构元数据六列**
    * `DESCRIBE employees;` 与 `DESC employees;` 完全等价，执行后返回刻画该表元数据的二维结构报表。
    * 六列含义：`Field` 字段名称；`Type` 物理数据类型与长度（如 `int(11)`、`varchar(25)`、`double(8,2)`，`varchar(25)` 表示最多存 25 个字符）；`Null` 是否允许存放空值（`NO` 表示有非空约束）；`Key` 索引与完整性约束标记（`PRI` 主键约束、`UNI` 唯一键约束、`MUL` 非唯一普通索引、空白为无）；`Default` 字段默认填充值（INSERT 未指定该列时自动灌入的缺省值）；`Extra` 底层附加描述信息（如 `auto_increment`）。
    * `departments` 表的 `DESC` 结果：`department_id` int(4) NO PRI 默认 0；`department_name` varchar(30) NO 默认 NULL；`manager_id` int(6) YES 默认 NULL；`location_id` int(4) YES 默认 NULL。
    * > 来源: P15, P17

## 5. WHERE 行级过滤与基础条件

> **一句话主旨**：确定 WHERE 在查询三维模型中的位置与语法槽位约束，讲清逐行布尔求值与字符串常量的大小写边界。

* **SELECT、FROM、WHERE 的三维控制模型**
    * `SELECT` 决定最终结果集保留哪些列（横向投影宽度）；`FROM` 决定数据从哪一张物理表提取（物理存储源）；`WHERE` 决定哪些行有资格进入最终结果集（纵向数据筛选深度）。
    * 过滤条件在逻辑上是布尔判断表达式，MySQL 底层对每一行记录逐行带入求值：结果为 `TRUE` 则保留，结果为 `FALSE` 或 `NULL`（未知）则直接丢弃。
    * `WHERE` 在英文语境中直译为「在哪里」，在 SQL 语法体系中本质是「过滤条件（Filter Condition）」的代名词。
    * > 来源: P16, P19

* **WHERE 的语法槽位约束**
    * 标准骨架为 `SELECT 字段列表 FROM 数据表名 WHERE 过滤条件;`
    * > 规则：`WHERE` 子句必须且只能声明在 `FROM` 结构的紧后方；`GROUP BY`、`HAVING`、`ORDER BY` 等后续子句一律必须排在 `WHERE` 之后，绝对不允许插入到 `FROM` 和 `WHERE` 之间。
    * > 来源: P16, P22

* **数值字段的等值匹配**
    * `=` 在 SQL 中是比较运算符（等于），用于判断字段实际存储值与右侧目标值是否相等，而非高级编程语言中的赋值符号。
    * `department_id` 为 `INT` 类型时，目标值 `90` 直接以裸数值书写而无需引号：`WHERE department_id = 90` 从 107 条原始数据中命中 **3 条**记录（主管 Steven King、Neena Kochhar、Lex De Haan）。
    * `WHERE employee_id = 176` 精准命中员工 `Taylor`，其所属部门编号为 `80`。
    * > 来源: P16, P17

* **字符串与日期常量的单引号界定**
    * > 规则：凡是非数值类型的字面量——包括所有字符类型（CHAR、VARCHAR、TEXT）以及日期时间类型（DATE、DATETIME）——作为条件常量参与比较时必须强制使用一对单引号包裹。
    * `WHERE last_name = 'King'` 命中 **2 条**记录（公司最高执行总裁 Steven King 与销售代表 Janette King）。
    * > 来源: P16, P17

* **字符数据内容的大小写敏感边界**
    * MySQL 在 Windows 环境下执行 `WHERE last_name = 'king'` 依然返回那两条大写 `'King'` 的记录，因为单引号内包裹的是实打实存储在磁盘记录内部的业务数据内容，与「Windows 文件系统层的库名表名不敏感」是两件事。
    * 跨库对照实证（Oracle 环境）：`WHERE last_name = 'King'` 命中 2 条；`WHERE last_name = 'king'` 返回 0 行；`WHERE last_name = "King"` 直接报 ORA 语法错误、无法识别双引号字符串。
    * MySQL 之所以执行小写也能查出数据，是因为默认字符集（如 `utf8mb4_general_ci` 或 `utf8mb4_0900_ai_ci`）的后缀 `_ci` 代表 Case Insensitive（大小写不敏感）。
    * > 易错点：绝不能因 MySQL 默认放水就认为 SQL 本身不区分数据大小写。一旦把字段校验规则调整为 `_bin`（二进制严格匹配）或 `_cs`（Case Sensitive），或把脚本迁移到 Oracle、PostgreSQL，随性写成小写的查询会导致核心报表瞬间全盘查空。
    * > 来源: P16

* **比较条件的能力边界**
    * 等值比较运算符为 `=`；范围运算符为 `<`、`<=`、`>`、`>=`；不等运算符为 `<>` 或 `!=`。
    * 范围区间与集合匹配由 `BETWEEN ... AND ...`（闭区间连续匹配）与 `IN(...)`（离散集合匹配）承担。
    * 空值精准研判由 `IS NULL` 与 `IS NOT NULL` 承担；模糊文本匹配由 `LIKE` 配合 `%`、`_` 通配符承担。
    * 多条件逻辑连接由 `AND`、`OR`、`NOT` 承担。
    * > 来源: P16

* **基础 SELECT 五题的标准写法**
    * 查询员工 12 个月工资总和并起别名为 `annual salary`：`SELECT employee_id, last_name, salary * 12 AS "annual salary" FROM employees;`；计入提成的增强口径为 `salary * 12 * (1 + IFNULL(commission_pct, 0)) AS "annual salary"`。
    * 查询去除重复 `job_id` 后的数据：`SELECT DISTINCT job_id FROM employees;`，输出去重后的 19 种工种。
    * 查询工资大于 12000 的员工姓名和工资：`SELECT last_name, salary FROM employees WHERE salary > 12000;`。
    * 查询员工工号为 176 的姓名和部门号：`SELECT last_name, department_id FROM employees WHERE employee_id = 176;`。
    * 显示 `departments` 表结构并查询全部数据：`DESC departments;` 加 `SELECT * FROM departments;`，返回 27 行部门数据。
    * > 来源: P17

* **SQL 状语后置与自然语言映射**
    * SQL 由 IBM 研究院在上世纪 70 年代设计，目标是构建高度接近人类自然语言的声明式查询工具。
    * 中文习惯先讲范围与前置条件再说动作；英文语法核心动词主干先行、条件与地点状语后置，因此书写顺序固定为 `SELECT` 声明输出视图、`FROM` 指定数据源、`WHERE` 施加行级过滤器。
    * > 来源: P17

* **表关系与多表连接的铺垫**
    * `departments` 的四个字段构成规范建模：`department_id` 为主键，`department_name` 为文本名称，`manager_id` 本质是指向 `employees` 主键的外键，`location_id` 为部门所在物理位置编码。
    * 级联链路：`employees.department_id = 80` → `departments.department_id = 80`（Sales）→ `departments.location_id = 2500` → `locations.location_id = 2500`（`city = 'Oxford'`）。
    * `departments` 中 50 号部门（Shipping）的 `location_id` 为 `1500`，对应 `locations` 表中坐落于美国加利福尼亚州南旧金山（South San Francisco）的记录。
    * > 来源: P17, P25

## 6. 运算符体系：算术、比较、逻辑与位运算

> **一句话主旨**：给出四类运算符的返回值模型与参数边界，说明三值逻辑对过滤结果的影响，并确定优先级混用时的防御写法。

### 6.1 算术运算符与类型转换

* **算术运算符（Arithmetic Operators）的四类符号**
    * 加法 `+`、减法 `-`、乘法 `*`、除法 `/`（或保留关键字 `DIV`）、取模 `%`（或保留关键字 `MOD`）。
    * 在无表依赖的纯运算测试中，通常使用伪表 `dual` 作为数据源。
    * 运算优先级严格恪守「先乘除后加减」的代数规则。

    | 运算符 | 描述 | 语法示例 | 返回值特征 | 典型边界与坑点 |
    | :---: | :---: | :---: | :---: | :--- |
    | `+` | 加法 | `a + b` | 数值或浮点数 | 无字符串拼接功能；纯字符字符串转为 `0`；遇 `NULL` 得 `NULL` |
    | `-` | 减法 | `a - b` | 数值或浮点数 | 字符串遵循相同隐式转换规则；遇 `NULL` 得 `NULL` |
    | `*` | 乘法 | `a * b` | 数值或浮点数 | 优先级高于加减；参与方有浮点则结果升级为浮点 |
    | `/` 或 `DIV` | 除法 | `a / b` | 浮点数（常规 `/`） | 默认保留多位小数；除数为 `0` 不报错直接返回 `NULL` |
    | `%` 或 `MOD` | 取模（求余） | `a % b` 或 `a MOD b` | 整型余数 | 结果符号恒等同于被模数符号，不受模数符号影响 |

    * > 来源: P18

* **加减运算的类型提升规则**
    * `100 + 0`、`100 - 0`、`100 + 50`、`100 + 50 - 30` 结果为整型；`100` 为整型（Integer），`35.5` 为带小数点的浮点型（Floating-Point）。
    * 加减同级运算遵循从左往右的自然结合律；一旦有浮点数参与，结果自动提升为浮点类型，例如 `100 + 35.5` 得到 `135.5`。
    * 乘法同样遵循类型提升：`100 * 1` 得 `100`，`100 * 1.0` 得 `100.0`，`100 * 2.5` 得 `250.0`。
    * > 来源: P18

* **加号的字符串拼接功能剥离**
    * > **结论**：MySQL 中的 `+` 号只有且仅有算术加法这一种功能，绝对不具备任何字符串连接功能。
    * 对照 Java：`100 + "1"` 会自动把数值转字符串并拼接，产出字符串 `"1001"`；MySQL 执行 `SELECT 100 + '1' FROM dual;` 的结果是数值 `101`。
    * 底层机理为隐式类型转换（Implicit Type Conversion）：引擎确认执行的是算术加法后，会尝试把两侧操作数全部转为数值类型，字符串 `'1'` 可安全解释为数值 `1`，后台静默转换后计算 $100 + 1 = 101$。
    * 需要拼接数字与字符串时，必须使用专用单行函数 `CONCAT()`，例如 `CONCAT(100, '1')` 才会输出 `'1001'`。
    * > 来源: P18

* **非数值字符串的归零机制**
    * > 规则：当 MySQL 尝试把字符串隐式转换为数值时，如果字符串开头不包含有效数字，引擎无法完成数值提取，此时会无条件将该字符串视作数值 `0` 处理。
    * `SELECT 100 + 'a' FROM dual;` 与 `SELECT 100 + 'ab' FROM dual;` 的结果均为 `100`，即 `'a'` 与 `'ab'` 都转成了 `0`。
    * > 易错点：任何基本数值与 `NULL` 进行加减运算，结果恒为 `NULL`；`NULL` 代表未知的空值，非 `0` 也非空字符串，`SELECT 100 + NULL FROM dual;` 返回 `NULL`。
    * > 来源: P18

* **除法默认返回浮点型**
    * 对比 Java 与 C：编译型语言中两个整型相除必然截断小数部分保持整型（如 `5 / 2` 得到 `2`）。
    * MySQL 中 `100 / 1` 输出 `100.0000`，`100 / 2` 输出 `50.0000`，`100 / 3` 输出 `33.3333`。
    * > **结论**：常规除法运算符 `/` 无论操作数是否为纯整数、无论最终能否整除，一律将结果视为浮点数处理，并默认保留若干位小数位数，以防止意外发生数据精度截断丢失。
    * > 来源: P18

* **除零的 NULL 返回策略**
    * > **结论**：在 MySQL 中，当除数为 `0` 时，系统不会抛出致命错误中断查询，而是直接将计算结果判定为 `NULL`。
    * 对照其他语言：Java 执行 `100 / 0` 会抛出 `ArithmeticException: / by zero` 打断程序执行流。
    * 数学背景：初等数学规定分母不能为 0；高等数学极限理论中 $\lim_{x \to 0^+} \frac{n}{x} = +\infty$、$\lim_{x \to 0^-} \frac{n}{x} = -\infty$。
    * > 来源: P18

* **取模运算与符号决定律**
    * `12 % 3` 整除无余数返回 `0`；`12 % 5` 与 `12 MOD 5` 结果均为 `2`（$12 = 5 \times 2 + 2$）。
    * 符号对照：`12 % 5` 得 `2`；`12 % -5` 得 `2`；`12 MOD -5` 得 `2`；`-12 % 5` 得 `-2`；`-12 % -5` 得 `-2`。
    * > **结论**：取模运算结果的正负号只与被模数（左边的数）的符号完全一致，与模数（右边的除数）的正负号没有任何关系。
    * 业务应用：`SELECT employee_id, last_name, salary FROM employees WHERE employee_id % 2 = 0;` 命中 **54 行**偶数工号记录，等价写法为 `WHERE employee_id MOD 2 = 0`。
    * > 来源: P18

### 6.2 比较运算符与三值逻辑

* **三值逻辑（Three-Valued Logic）**
    * > 定义：比较运算符针对左右两个操作数做关系求值，返回值必然属于三者之一——`1` 代表比较结果为真（TRUE）、`0` 代表比较结果为假（FALSE）、`NULL` 代表比较结果未知（UNKNOWN）。
    * `SELECT 1 = 2, 1 != 2, 1 = 1, 1 = NULL FROM dual;` 依次返回 `0`、`1`、`1`、`NULL`。
    * C 语言或 Java 的关系表达式只有 `true` / `false` 两个状态；MySQL 引入第三态是为了表达现实业务中「数据缺失、未定义、未知」的客观事实。
    * > 来源: P19

* **WHERE 对 NULL 判定结果的静默丢弃**
    * 引擎通过行指针逐行扫描数据并把字段代入 `WHERE` 表达式：返回 `1` 的行装入返回缓冲区；返回 `0` 的行被剔除；返回 `NULL` 的行由于无法证明其满足条件同样被静默剔除。
    * 这正是包含 `NULL` 的行在日常排查中「无声无息地消失」在普通查询结果中的底层根源，也是 `WHERE commission_pct = NULL` 返回 0 行的原因。
    * > 来源: P19, P21

* **等号（=）的隐式类型转换法则**
    * `SELECT 1 = 1, 1 = '1', 1 = 'a', 0 = 'a' FROM dual;` 依次返回 `1`、`1`、`0`、`1`。
    * `1 = '1'`：字符串 `'1'` 成功转换为数值 `1`，$1 = 1$ 成立。
    * `1 = 'a'`：字符串 `'a'` 无法解析出合法数值，转换失败时被视作数值 `0`，等式退化为 $1 = 0$ 判定为假。
    * `0 = 'a'`：同理 `'a'` 被视作 `0`，$0 = 0$ 成立，表达式返回 `1`。
    * > 易错点：做字段等值查询时，把整型字段与纯字母字符串做 `=` 比较，数据库会把字符串隐式解析为 0，若表中恰好有某列取值为 0，该记录会被意外匹配出来。
    * > 来源: P19

* **两侧均为字符串时的编码比较**
    * `SELECT 'a' = 'a', 'ab' = 'ab', 'a' = 'b' FROM dual;` 依次返回 `1`、`1`、`0`。
    * > 规则：当比较运算符两侧全部为字符串时，MySQL 绝不会将其隐式转换为数值 `0`，而是按字符编码规范（如 ANSI 码、UTF-8 字符集权重）自左向右逐字符比对字节编码值。
    * 在 ASCII/ANSI 码表中，小写 `'a'` 的码值为 97，小写 `'b'` 的码值为 98，码值不等判定为假。
    * > 来源: P19

* **安全等于（`<=>`，NULL-Safe Equal）**
    * > 定义：为 `NULL` 的等值判定而生，符号写作 `<=>`。
    * `SELECT 1 <=> 1, 1 <=> 2, 1 <=> NULL, NULL <=> NULL FROM dual;` 依次返回 `1`、`0`、`0`、`1`。
    * 三条行为规则：两端均为正常非空数据时行为与 `=` 完全相同；两端同时为 `NULL` 时判定逻辑等价返回 `1`；一端为正常值另一端为 `NULL` 时明确判定不相等返回 `0` 而非 `NULL`。
    * `SELECT employee_id, last_name, commission_pct FROM employees WHERE commission_pct <=> NULL;` 命中 **72 条**提成为空的记录。
    * > 来源: P19, P21

* **不等号与区间比较的 NULL 边界**
    * `<>` 为 SQL 标准写法，`!=` 为程序员熟悉写法，两者语法层面完全等价；`>`、`>=`、`<`、`<=` 遵循标准数学定义。
    * `SELECT 3 <> 2, 3 != 2, 3 != NULL, NULL != NULL FROM dual;` 依次返回 `1`、`1`、`NULL`、`NULL`。
    * 任何常规符号与 `NULL` 进行大小或不等比较，结果恒为 `NULL`。
    * > 来源: P19

* **空值判定的三种正确写法与错误写法**

    | 需求意图 | 最推荐规范写法 | 等价替代写法 | 严禁使用的错误写法 |
    | :--- | :--- | :--- | :--- |
    | 判定为空 | `expr IS NULL` | `expr <=> NULL`、`ISNULL(expr)` | `expr = NULL`（永远查不出结果） |
    | 判定非空 | `expr IS NOT NULL` | `NOT expr <=> NULL`、`NOT ISNULL(expr)` | `expr != NULL`、`expr <> NULL`（同样查不出结果） |

    * `ISNULL(expr)` 是 MySQL 内建单行系统函数：字段值为 `NULL` 时返回 `1`，字段值非空时返回 `0`。
    * > 易错点：表达「不为空」时受中文思维影响写成 `NOT IS NULL` 会引发词法错误；英语结构中 `is` 是系动词、否定词 `not` 必须紧随其后，标准写法是 `IS NOT NULL`，而 `NOT (expr IS NULL)` 这种整体否定形式可以被解析。
    * > 来源: P19, P21

* **极值运算 LEAST / GREATEST**
    * `SELECT LEAST('a', 'b', 'm', 't'), GREATEST('a', 'b', 'm', 't') FROM dual;` 分别输出 `'a'` 与 `'t'`。
    * > 注意：`LEAST()` 处理字符串时绝不是比较字符串的物理长度，而是自左往右逐位比较 ASCII 字符码。名字 `'Abel'`（长度 4）与姓氏 `'Apple'`（长度 5）比对时，第一位均为 `'A'`，第二位 `'b'` 码值 98 小于 `'p'` 码值 112，因此 `LEAST` 判定 `'Abel'` 更小并输出，长度并非决定性因素。
    * > 来源: P19

* **BETWEEN ... AND ... 的闭区间特性**
    * > 定义：`BETWEEN min AND max` 在语义上严格等价于闭区间 $val \ge min \ AND \ val \le max$，必定包含两个端点边界值。
    * `WHERE salary BETWEEN 6000 AND 8000` 返回 **24 条**记录，薪资正好为 6000 和 8000 的员工均在结果中；$24 + 83 = 107$ 与不在区间的 83 条完美闭合。
    * `WHERE salary BETWEEN 5000 AND 12000` 包含 5000 与 12000 两个端点，统计共计 **52 条**记录。
    * 反向写法 `WHERE salary NOT BETWEEN 6000 AND 8000` 等价于 `WHERE salary < 6000 OR salary > 8000`，命中 **83 条**；`NOT BETWEEN 5000 AND 12000` 等价于 `salary < 5000 OR salary > 12000`，返回 **55 条**并严格排除 5000 与 12000 端点。
    * > 易错点：`BETWEEN` 左侧必须是条件区间的下限（较小值）、右侧必须是上限（较大值）。写成 `WHERE salary BETWEEN 8000 AND 6000` 会被展开为 $salary \ge 8000 \ AND \ salary \le 6000$，任何数都不可能同时满足，返回值必定为 0 行。
    * > 来源: P19, P21, P24

* **IN / NOT IN 的离散集合匹配**
    * `WHERE department_id IN (10, 20, 30)` 返回 **9 行**；等价的完整展开写法是 `WHERE department_id = 10 OR department_id = 20 OR department_id = 30`。
    * `WHERE department_id IN (20, 50)` 返回 **47 条**记录；`WHERE salary NOT IN (6000, 7000, 8000)` 用于排除指定离散取值。
    * `WHERE manager_id IN (100, 101, 110)` 返回 **19 行**记录。
    * > 易错点：`WHERE department_id = 10 OR 20 OR 30` 是隐蔽的逻辑灾难写法。该语句被划分为 `(department_id = 10) OR (20) OR (30)`，SQL 逻辑判断中任何非零数值都等同于逻辑真（`1`），表达式变为 `(department_id = 10) OR 1 OR 1`，整行 `WHERE` 裁决恒等于 `1`，导致全表 107 名员工（包括 50、80、90 号部门）全部被查出。
    * > 来源: P19, P21

* **LIKE 模糊匹配的通配符语义与位置组合**
    * `%`（百分号）代表任意长度的不确定字符，包含 0 个、1 个或多个字符；`_`（下划线）代表且仅代表恰好 1 个不确定字符。
    * `last_name LIKE '%a%'` 匹配包含字符 `a`；`LIKE 'a%'` 匹配以 `a` 开头；`LIKE '%a'` 匹配以 `a` 结尾；`LIKE '_a%'` 匹配第二个字符是 `a`；`LIKE '__a%'` 匹配第三个字符是 `a`。
    * > **提示**：连续使用多个下划线占位（如 `__a%`）时，字符之间不要混入多余空格，否则空格会被解释为文本字面量。
    * > 来源: P19, P21

* **多条件包含的两种构造策略**
    * 策略一（推荐）：`WHERE last_name LIKE '%a%' AND last_name LIKE '%e%'`，命中 **20 条**记录，不必关心 `a` 与 `e` 的先后出现顺序。
    * 策略二：`WHERE last_name LIKE '%a%e%' OR last_name LIKE '%e%a%'`，只写 `%a%e%` 会漏掉 `e` 在前 `a` 在后的情况（只剩 16 条），补齐 `OR` 分支后同样达到 20 条。
    * 同一模式在字母 `a` 与 `k` 上的应用：`WHERE last_name LIKE '%a%' AND last_name LIKE '%k%'` 与 `LIKE '%a%k%' OR LIKE '%k%a%'` 均返回 **6 条**记录。
    * > **提示**：需求变为同时包含三个字母时，排列穷举达到 $3! = 6$ 种，而 `AND` 写法只需追加 `AND last_name LIKE '%e%'`。
    * > 来源: P19, P21

* **真实下划线冲突与转义机制**
    * 字段真实数据含下划线（如 `'O_Reilly'`）时，`LIKE '__a%'` 中的两个下划线都会被当作通配符，把所有第 3 位是 `a` 的员工全部带出。
    * MySQL 默认转义字符是反斜杠 `\`，正确写法为 `WHERE last_name LIKE '_\_a%'`：第一个 `_` 匹配任意第 1 个字符，转义序列 `\_` 解除通配符语义严格匹配真实下划线，`a` 要求第 3 个字符为字母 `a`，`%` 匹配后续 0 到任意个字符。
    * 规范允许使用 `ESCAPE` 关键字自定义任意非冲突符号作为当次匹配的转义符：`WHERE last_name LIKE '_$_a%' ESCAPE '$';` 与反斜杠写法执行效果完全一致。
    * > 来源: P19

* **REGEXP / RLIKE 正则匹配**
    * `REGEXP`（Regular Expression）与同义词 `RLIKE` 支持完整的正则表达式匹配引擎，用于邮箱格式验证、连续数字规则、特殊多分支匹配等 `LIKE` 无法覆盖的场景。
    * 锚定元字符：`^`（脱字符）匹配字符串的开始位置；`$`（美元符）匹配字符串的结束位置。
    * `SELECT 'shkstart' REGEXP '^s', 'shkstart' REGEXP 't$', 'shkstart' REGEXP 'hk' FROM dual;` 依次返回 `1`、`1`、`1`。
    * 点号 `.` 代表任意单个字符：`'atguigu' REGEXP 'gu.gu'` 返回 `1`（中间正好间隔一个字母 `i`），`'atguigu' REGEXP 'gu..gu'` 要求中间恰好 2 个字符而返回 `0`。
    * 中括号字符集 `[...]` 匹配集合中的任意一个独立字符（逻辑或）：`'atguigu' REGEXP '[ab]'` 因首字母为 `a` 而返回 `1`。
    * 应用示例：`WHERE first_name REGEXP 'e$'` 与 `WHERE first_name LIKE '%e'` 均检索出 **9 条**以字母 `e` 结尾的记录；`WHERE email REGEXP 'e'` 与 `WHERE email LIKE '%e%'` 均命中 **47 条**记录。
    * > 来源: P19, P21, P24

* **比较运算符全体系速查**

    | 运算符 / 关键字 | 语法模式 | 核心语义 | 返回结果特征 |
    | :--- | :--- | :--- | :--- |
    | `=` | `a = b` | 基础等值比较 | 相等返回 1，不等返回 0；含 NULL 恒返回 NULL；纯字母串隐式转 0 |
    | `<=>` | `a <=> b` | 安全等于 | 为空判定而生；两端皆 NULL 返回 1；一端 NULL 返回 0 |
    | `<>` / `!=` | `a <> b` | 不等比较 | 不相等返回 1，相等返回 0；遇 NULL 恒返回 NULL |
    | `<`、`<=`、`>`、`>=` | `a < b` | 范围大小比较 | 按数值或字符编码大小比较；遇 NULL 恒返回 NULL |
    | `IS NULL` | `expr IS NULL` | 空值判断谓词 | 目标为空返回 1，非空返回 0 |
    | `IS NOT NULL` | `expr IS NOT NULL` | 非空判断谓词 | 目标非空返回 1，为空返回 0 |
    | `ISNULL()` | `ISNULL(expr)` | 空值判断单行函数 | 目标为空返回 1，非空返回 0 |
    | `LEAST()` | `LEAST(v1, v2, ...)` | 求列表最小值 | 逐位比对字符或数值，返回最小者 |
    | `GREATEST()` | `GREATEST(v1, ...)` | 求列表最大值 | 逐位比对字符或数值，返回最大者 |
    | `BETWEEN ... AND` | `v BETWEEN a AND b` | 闭区间连续匹配 | 包含两端端点；左侧必须是下限，右侧必须是上限 |
    | `IN(...)` | `v IN (v1, v2, ...)` | 离散集合包含 | 命中集合中任一值返回 1；等价于多条件 `OR` 链 |
    | `LIKE` | `v LIKE 'pattern'` | 模糊通配查询 | `%` 匹配 0 到多字符；`_` 匹配单字符；支持 `\` 与 `ESCAPE` 转义 |
    | `REGEXP` / `RLIKE` | `v REGEXP 'pattern'` | 正则表达式匹配 | 支持 `^`（开头）、`$`（结尾）、`.`（单字符）、`[]` 等规则 |

    * > 来源: P19

### 6.3 逻辑运算符与位运算符

* **逻辑与（AND / &&）**
    * > 定义：当且仅当左右两端的所有子条件计算结果同时为 `1`（真）时整体结果为 `1`；只要任意一端结果为 `0`（假），整体结果即被判定为 `0`。
    * `WHERE department_id = 50 AND salary > 6000` 从 50 号部门庞大的基数中筛选出 **4 条**资深高薪员工记录。
    * 数据库行业规范强烈建议统一书写为 `AND` 而非 `&&`。
    * > 来源: P20

* **逻辑或（OR / ||）**
    * > 定义：左右两端的子条件中只要有一个成立（为 `1`），整体结果就为 `1`；只有当两端同时为 `0` 时整体结果才为 `0`，在集合论中对应取两组数据的并集（Union）。
    * `WHERE department_id = 10 OR department_id = 20` 同时拉取 10 号与 20 号部门的全部人员。
    * 建议统一使用 `OR` 而非 `||`，因为在某些 SQL 模式下 `||` 会被用作字符串拼接符。
    * > 易错点：企图找出「既是 10 号部门又是 20 号部门」的员工而写出 `WHERE department_id = 10 AND department_id = 20` 必然返回 0 行。关系表的一行实体中外键列 `department_id` 是单一确定值，一个员工不可能物理上同时属于两个部门，$10 = 20$ 恒为假。
    * > 来源: P20

* **逻辑非（NOT / !）**
    * 逻辑非用于对现有布尔结果取反：真变假（$1 \to 0$），假变真（$0 \to 1$），可用关键字 `NOT` 或叹号 `!`。
    * 反向区间匹配：`WHERE salary NOT BETWEEN 6000 AND 8000` 命中 **83 行**。
    * 反向空值判断：`WHERE commission_pct IS NOT NULL` 与 `WHERE NOT commission_pct <=> NULL` 均返回 **35 行**，两条写法完全等价。
    * > 来源: P20, P21

* **逻辑异或（XOR）**
    * > 定义：当且仅当左右两端的条件一真一假（状态不同）时，`XOR` 的结果才为 `1`；两端同为真或同为假时结果均为 `0`。
    * 真值表：`TRUE XOR FALSE` 得 `1`；`FALSE XOR TRUE` 得 `1`；`TRUE XOR TRUE` 得 `0`；`FALSE XOR FALSE` 得 `0`。
    * `WHERE department_id = 50 XOR salary > 6000` 的筛选结果具有互斥特征：50 号部门的员工月薪必定小于等于 6000；月薪大于 6000 的员工绝对不属于 50 号部门。
    * 「既是 50 号部门又拿高薪」的 4 个人与「既不属于 50 号部门月薪又低于 6000」的人会被 `XOR` 全部剔除。
    * > 来源: P20

* **位运算符（Bitwise Operators）与六种符号**
    * 六个标准运算符：按位与 `&`、按位或 `|`、按位异或 `^`、按位取反 `~`、按位左移 `<<`、按位右移 `>>`，直接针对整型数值的二进制比特位操作。
    * `SELECT 12 & 5, 12 | 5, 12 ^ 5 FROM dual;` 依次返回 **`4`**、**`13`**、**`9`**。
    * 二进制推演基础：$12 = 2^3 + 2^2 \to 0000\ 1100$；$5 = 2^2 + 2^0 \to 0000\ 0101$。按位与要求上下全为 1 才得 1（得 `4`）；按位或只要上下有 1 就得 1（得 `13`）；按位异或上下不同得 1、相同得 0（得 `9`）。
    * > 来源: P20

* **按位取反与掩码操作**
    * `SELECT 10 & ~1 FROM dual;` 执行结果仍为 **`10`**。推演过程：`1` 的低 8 位为 `0000 0001`，取反得到掩码 `1111 1110`；`10` 的二进制为 `0000 1010`；两者按位与后最低位被掩码中的 0 强制置零，其余位保持，输出 `0000 1010`。
    * 该模式在系统编程中专门用于在不影响其他状态标记的前提下精准擦除某一特定标志位。
    * > 来源: P20

* **移位运算符与溢出边界**
    * `SELECT 4 << 1, 8 >> 1 FROM dual;` 依次返回 **`8`** 与 **`4`**；左移时高位溢出丢弃、低位补 0。
    * 数学本质：在未发生有效高位溢出的安全数值区间内，每向左移动 1 位等价于乘以 2，向左移动 $n$ 位等价于乘以 $2^n$；每向右移动 1 位等价于整除以 2，向右移动 $n$ 位等价于整除以 $2^n$。
    * 框架底层应用：Java 的 `ArrayList`、`HashMap` 扩容逻辑中，数组扩容一倍写作 `capacity << 1`，扩容 1.5 倍写作 `capacity + (capacity >> 1)`。
    * > **注意**：移位运算的「乘 2」规律存在严格的有效范围约束。持续大幅度左移会把有效二进制高位移出字长边界并被硬件丢弃，一旦有效比特位全部溢出丢失，整个数值就会彻底塌陷为 `0`。
    * 在业务 SQL 中，系统性能瓶颈几乎永远集中在磁盘 I/O 吞吐、B+ 树索引寻道与网络数据交互上，CPU 执行一次算术相加与位移的纳秒差距可以忽略不计。
    * > 来源: P20

* **逻辑与位运算符对照**

    | 运算符 | 类别 | 语法示例 | 逻辑语义 / 数学行为 | 典型应用与注意事项 |
    | :---: | :---: | :---: | :--- | :--- |
    | `NOT` 或 `!` | 逻辑 | `NOT a` | 逻辑非：反转布尔真假 | 常配合 `BETWEEN`、`IN`、`IS NULL` 进行反向过滤 |
    | `AND` 或 `&&` | 逻辑 | `a AND b` | 逻辑与：全真才为真 | 组合多维硬性约束；优先级高于 `OR` |
    | `OR` 或 `\|\|` | 逻辑 | `a OR b` | 逻辑或：一真即为真 | 汇总并集条件；混用时必须用 `()` 防御优先级紊乱 |
    | `XOR` | 逻辑 | `a XOR b` | 逻辑异或：求异，一真一假才为真 | 表达互斥排他业务筛选 |
    | `&` | 位运算 | `a & b` | 按位与：二进制位全 1 得 1 | 状态位检测与掩码提取 |
    | `\|` | 位运算 | `a \| b` | 按位或：二进制位有 1 得 1 | 状态位合并 |
    | `^` | 位运算 | `a ^ b` | 按位异或：二进制位不同得 1 | 校验与对称变换 |
    | `~` | 位运算 | `~a` | 按位取反：逐位翻转 0/1 | 单目掩码生成 |
    | `<<` | 位运算 | `a << n` | 按位左移：低位补 0 | 安全范围内相当于 $a \times 2^n$；溢出会归零 |
    | `>>` | 位运算 | `a >> n` | 按位右移：高位补符号/零 | 相当于 $a \div 2^n$ |

    * 运算符四大类划分：算术运算符负责数值计算与字段衍生；比较运算符负责关系判断与行过滤；逻辑运算符负责多条件布尔裁决并支持三值逻辑；位运算符负责二进制比特位操作，主要用于低层位图标记与掩码匹配。
    * > 来源: P18, P20

* **运算符优先级与防御性编码**
    * > **规则**：`AND` 的运算优先级严格高于 `OR`。形如 `WHERE 条件1 AND 条件2 OR 条件3 AND 条件4` 的子句不会从左到右机械执行，而是先把 `条件1 AND 条件2` 与 `条件3 AND 条件4` 各自作为独立闭包求值，最后把两组结果做一次 `OR` 并集汇总。
    * 阅读他人代码时的结构切分常识：算术运算（先乘除后加减）必定先于关系比较（`>`、`<`、`=`）；关系比较必定先于逻辑裁决；`AND` 的紧密程度天然强于 `OR`。
    * > **结论**：凡遇到混合条件判断、只要存在歧义可能，一律主动给需要优先计算的单元套上英文小括号 `()`。小括号拥有整个 SQL 语法体系中的最高裁决权，显式加上括号不会产生任何性能损耗。
    * > 来源: P20

### 6.4 运算符综合实战题解

* **区间与逻辑合并的边界等价**
    * `WHERE salary NOT BETWEEN 5000 AND 12000` 与 `WHERE salary < 5000 OR salary > 12000` 均返回 **55 行**。
    * > 易错点：`NOT BETWEEN` 的反向展开连接词必须为 `OR` 而非 `AND`，误写为 `salary < 5000 AND salary > 12000` 逻辑恒假返回空集。
    * > 易错点：逻辑运算符前后的表达式必须语法完整，`WHERE salary < 5000 OR > 12000` 缺乏右侧被比较对象会直接抛出语法解析异常；检验方式是把条件顺序颠倒为 `WHERE > 12000 OR salary < 5000`，显然不成立。
    * > 来源: P21

* **离散枚举与连续区间的语义分野**
    * 需求「部门编号在 80 到 100 之间」的三种写法：`WHERE department_id BETWEEN 80 AND 100`（推荐）、`WHERE department_id >= 80 AND department_id <= 100`（等价展开）、`WHERE department_id IN (80, 90, 100)`（存在隐患）。
    * 当前测试库中部门编号恰好以 10 为步长递增（10, 20, 30, …, 80, 90, 100），因此三条语句均返回 **43 条**数据。
    * > **注意**：方式三属于基于当前数据巧合编写的代码。一旦后续业务新增 85 号部门，方式一与方式二能正确纳入统计，方式三会静默漏掉 85，造成极难排查的业务 Bug。SQL 执行报错会被控制台拦截提示，最危险的是执行完全成功但结果集错误。
    * > 来源: P21

* **空值与集合匹配题解**
    * 查询公司中没有管理者的员工姓名和 `job_id`：`WHERE manager_id IS NULL` 或 `WHERE manager_id <=> NULL` 均返回 **1 行**；`WHERE manager_id = NULL` 恒不成立、永远查不出数据。
    * 查询有奖金的员工姓名、工资与奖金率：`WHERE commission_pct IS NOT NULL` 或 `WHERE NOT (commission_pct <=> NULL)` 均返回 **35 行**。
    * 查询在 20 或 50 号部门工作的员工：`WHERE department_id IN (20, 50)` 返回 **47 行**。
    * 查询姓名第三个字母是 `a` 的员工：`WHERE last_name LIKE '__a%'`。
    * 查询姓名同时包含 `a` 和 `k` 的员工：`WHERE last_name LIKE '%a%' AND last_name LIKE '%k%'` 返回 **6 行**。
    * 查询 `first_name` 以字母 `e` 结尾：`WHERE first_name LIKE '%e'` 或 `WHERE first_name REGEXP 'e$'` 均返回 **9 行**。
    * 查询管理者 ID 为 100、101 或 110 的员工：`WHERE manager_id IN (100, 101, 110)` 返回 **19 行**。
    * > 来源: P21

* **查询技能递进阶梯**
    * 单表基础过滤与运算 → 数据排序与物理分页（`ORDER BY` / `LIMIT`，降低网络与内存负载）→ 多表连接查询（内连接、外连接、自连接）→ 单行函数与分组聚合（`GROUP BY` / `HAVING`）→ 子查询嵌套 → DDL / DML 数据操作。
    * > 来源: P21

## 7. ORDER BY 排序机制

> **一句话主旨**：确定升降序的默认行为与 NULL 值位置，厘清列别名在排序与过滤两个子句中的作用域差异及其物理执行时序根源。

### 7.1 单列排序与升降序规则

* **ORDER BY 的语义与位置**
    * `order` 表示「次序、排序」，`by` 表示「通过、依据」，`ORDER BY col` 即表示依据字段 `col` 的取值排序。
    * 未显式指定排序规则时，数据库通常遵循数据在物理磁盘或存储引擎层先后添加的默认插入顺序展示。
    * > 来源: P22

* **升序 ASC 与默认行为**
    * 升序关键字 `ASC` 源自英文 `ascend`（上升、升序）；`SELECT employee_id, last_name, salary FROM employees ORDER BY salary ASC;` 返回的 107 条记录严格按薪水从低到高排列。
    * > **定义**：如果在 `ORDER BY` 后面没有显式指定排序方向，MySQL 默认采用升序规则（`ASC`），因此升序时的 `ASC` 可显式写出也可直接省略。
    * > 来源: P22

* **降序 DESC 与关键字辨析**
    * 降序关键字 `DESC` 源自英文 `descend`（下降、降序），`ORDER BY salary DESC` 使最高薪资 24000 的记录排在第一行。
    * > **提示**：`DESC` 与查看表结构的 `DESCRIBE`（简写 `DESC 表名;`）词形完全相同，但语法槽位不同——放在 `DESC 表名` 开头属于 DDL / 辅助检查命令，追加在 `ORDER BY 字段名` 之后则作为排序方向修饰符专指降序。
    * > 来源: P22, P23

### 7.2 列别名作用域与物理执行时序

* **列别名在 ORDER BY 中合法**
    * `SELECT employee_id, salary, salary * 12 AS annual_sal FROM employees ORDER BY annual_sal;` 执行完全正常，结果集严格按计算后的年薪值递增排列。
    * 在 `ORDER BY` 中直接引用 `SELECT` 列表定义的别名完全合法且受支持。
    * > 来源: P22

* **列别名在 WHERE 中失效**
    * `SELECT employee_id, salary, salary * 12 AS annual_sal FROM employees WHERE annual_sal > 81600 ORDER BY annual_sal;` 直接报错 `Error Code: 1054. Unknown column 'annual_sal' in 'where clause'`。
    * 需要在此处过滤时必须书写原始计算式 `WHERE salary * 12 > 81600`。
    * > 来源: P22

* **SQL 物理执行生命周期**
    * 书写顺序为 `SELECT` → `FROM` → `WHERE` → `ORDER BY`，实际执行顺序为 `FROM` → `WHERE` → `SELECT` → `ORDER BY`。
    * 步骤 1（`FROM`）：从存储引擎加载底层数据表，建立初始数据流。
    * 步骤 2（`WHERE`）：对数据流逐行扫描判定，此时 `SELECT` 子句尚未执行，内存符号表中根本没有 `annual_sal` 别名。
    * 步骤 3（`SELECT`）：筛选指定列，执行 `salary * 12` 运算，并把别名 `annual_sal` 注册进内存上下文。
    * 步骤 4（`ORDER BY`）：排序引擎对步骤 3 产生的投影结果集进行物理排序，此时别名已完全就绪。
    * > 易错点：一条 SQL 同时包含 `WHERE` 与 `ORDER BY` 时，`WHERE` 必须紧跟在 `FROM` 之后，`ORDER BY` 必须位于 `WHERE` 之后，两者的物理书写位置决不能颠倒。
    * > 来源: P22

### 7.3 非投影列排序与多列排序

* **排序字段与投影列表解耦**
    * `SELECT employee_id, last_name FROM employees WHERE department_id IN (50, 60, 70) ORDER BY department_id DESC;` 虽然 `SELECT` 列表未包含 `department_id`，查询依然正确执行。
    * 原理：执行引擎在步骤 1 与步骤 2 中持有的是完整的行记录引用，可以在不输出该列的前提下把它作为排序键参与内存排序。
    * > 来源: P22

* **多列排序的语法与短路原则**
    * 二级排序写法：`ORDER BY department_id DESC, salary ASC;`，由于升序为默认属性可简写为 `ORDER BY department_id DESC, salary;`。
    * 多列排序可沿维度链条扩展至三级、四级，如 `ORDER BY col1 DESC, col2 ASC, col3 DESC`。
    * > **结论**：多列排序严格以左侧第一列作为主排序基准。只有当两个数据行在第一列的取值完全相同时，执行引擎才会调取第二列进行次级排序；若第一列已能分出高下，后续所有列的排序规则被直接忽略。
    * 判定链路：对比两行时先看第一排序列是否相同，不同则直接依其规则判定并终止；相同则看第二排序列；依次下推；全部相同则退化为物理存储层先后顺序。
    * 单列排序中排序列取值完全相同的记录，其内部展示顺序会退化为存储层默认的物理先后顺序，呈无序或伪随机状态。
    * > 来源: P22

* **NULL 值在排序中的确定性位置**
    * > **提示**：MySQL 的排序机制中 `NULL` 值在逻辑上被视作最小值。升序排列（`ASC`）时 `NULL` 值优先排在最前；降序排列（`DESC`）时 `NULL` 值被沉底排在最后。
    * 执行 `SELECT employee_id, last_name, department_id FROM employees ORDER BY department_id ASC;` 时，`department_id` 为 `NULL` 的员工（如刚入职尚未定岗的新员工）被直接放置在结果集最顶部。
    * > 来源: P22

## 8. LIMIT 分页机制

> **一句话主旨**：给出 LIMIT 两参数的 0 索引语义、通用分页公式的推导结果，并说明 8.0 OFFSET 语法与各数据库分页方言的差异。

### 8.1 LIMIT 语法与偏移量机制

* **分页的业务定位**
    * 现代应用普遍采用「按需拉取」的交互机制：客户端先加载第一页（如 10 条）数据，用户上滑触底后前端捕获事件再发异步请求获取第二页。
    * 用户浏览有效注意力通常只覆盖前 10 到 20 家评价较高的结果，返回数据量越大则移动端与数据库保持 Socket 连接的时间越长，射频模块持续工作的电量损耗与蜂窝流量开销成倍放大；服务端超大数据集瞬间加载会引发数据库 I/O 阻塞与内存暴涨。
    * > **结论**：分页的本质是按需计算与分批交付，能显著削减单次请求的数据传输量、降低网络传输延迟，同时大幅减轻数据库服务器的行锁竞争与内存缓存池（Buffer Pool）压力。
    * 标准 SQL 规范中没有针对物理分页的通用关键字，`LIMIT` 是 MySQL 提供的专有子句。
    * > 来源: P23

* **位置偏移量与请求条目数**
    * > **定义**：位置偏移量（Offset）指示从结果集的哪一行之后开始截取，底层遵循 0 索引（0-indexed）规则——偏移量 `0` 代表不发生偏移直接从第 1 条记录提取；偏移量 `1` 代表跳过 1 行从第 2 条记录开始提取；偏移量 $n$ 代表跳过前 $n$ 行从第 $n+1$ 行开始提取。请求条目数（Count / Page Size）指示本次查询最多向客户端返回的行记录数量。
    * 完整格式为 `LIMIT 位置偏移量, 请求条目数;`，且在语法结构中永远处于最底层的垫底位置。
    * 每页 20 条的前三页：`LIMIT 0, 20` 返回员工 ID 100 至 119；`LIMIT 20, 20` 返回 120 至 139；`LIMIT 40, 20` 从 140 开始依次展示。
    * 取第 32 和第 33 条记录（跳过前 31 条取 2 条）：`LIMIT 31, 2`。
    * > 来源: P23

* **单参数缺省简写**
    * `LIMIT 10` 严格等价于 `LIMIT 0, 10`，适用于且仅适用于从首行开始截取头部数据。
    * > 易错点：需要提取中间任意区间的数据（偏移量大于 0）时，绝对不能省略偏移量参数。
    * 无聚合函数条件下求极值：`SELECT employee_id, last_name, salary FROM employees ORDER BY salary DESC LIMIT 0, 1;`（可简写为 `LIMIT 1`）精准输出薪资 24000 的高管记录 Steven King。
    * > 来源: P23

### 8.2 分页公式与子句书写顺序

* **通用分页公式**
    * 业务参数为 $page\_size$（每页固定行记录容量）与 $page\_number$（客户端请求的目标页码，从 1 开始计数的正整数）。

        | 目标页码 | 需跳过的历史记录总数 | 物理位置偏移量 | 提取条数 | 最终拼装子句 |
        | :---: | :---: | :---: | :---: | :--- |
        | 第 1 页 | 0 条 | $0 = (1 - 1) \times 20$ | 20 | `LIMIT 0, 20` |
        | 第 2 页 | 前 20 条 | $20 = (2 - 1) \times 20$ | 20 | `LIMIT 20, 20` |
        | 第 3 页 | 前 40 条 | $40 = (3 - 1) \times 20$ | 20 | `LIMIT 40, 20` |
        | 第 $N$ 页 | 前 $(N-1) \times 20$ 条 | $(N - 1) \times 20$ | 20 | `LIMIT (N - 1) * 20, 20` |

    * 通用公式为：
        $$\text{offset} = (page\_number - 1) \times page\_size$$
    * 动态 SQL 模板为 `LIMIT (page_number - 1) * page_size, page_size;`。
    * 前后端协同流程：前端打包 `{ pageNumber: 4, pageSize: 20 }` 发送至后台；后端控制器或业务逻辑层计算 $\text{offset} = (4 - 1) \times 20 = 60$；数据访问层生成带 `LIMIT 60, 20` 的 SQL 发往数据库；MySQL 引擎位移 60 行并返回随后 20 行。
    * 跨行区间取值的换算：目标范围第 21 条到第 40 条时，条目数为 $40 - 21 + 1 = 20$，偏移量为 $21 - 1 = 20$，最终拼装为 `LIMIT 20, 20`。
    * > 易错点：切勿把「第 21 条到第 40 条」误写为 `LIMIT 20, 40`。`LIMIT` 的第二个参数是提取的行数而非终止行号，写成 `LIMIT 20, 40` 实际截取的是第 21 到第 60 条连续 40 条记录。
    * > 来源: P23, P24

* **SQL 核心子句的书写顺序**
    * > **注意**：书写顺序铁律为 `SELECT` → `FROM` → `WHERE` → `ORDER BY` → `LIMIT`。`WHERE` 必须紧随 `FROM` 完成源数据的物理行过滤，`ORDER BY` 对过滤后的集合完成排序，最后由 `LIMIT` 在有序集合上执行物理切片。
    * 完整示例：`SELECT employee_id, last_name, salary FROM employees WHERE salary > 6000 ORDER BY salary DESC LIMIT 0, 10;`
    * > 来源: P23

* **MySQL 8.0 的 OFFSET 语法糖**
    * 8.0 之前 `LIMIT 偏移量, 行数` 的写法容易让人记忆混淆，8.0 引入显式语法 `LIMIT 请求条目数 OFFSET 位置偏移量;`。
    * > 易错点：参数顺序完全对调。旧版本逗号分隔语法为 `LIMIT offset, count`（偏移量在左、数量在右）；8.0 的 OFFSET 语法为 `LIMIT count OFFSET offset`（数量在左、偏移量在右）。
    * 取第 32 和第 33 条记录的两种写法：全版本兼容 `LIMIT 31, 2`；8.0 写法 `LIMIT 2 OFFSET 31`。若在 8.0 中误写为 `LIMIT 31 OFFSET 2`，含义变成跳过前 2 条连续获取 31 条记录。
    * > 来源: P23

### 8.3 跨数据库分页方言

* **主流关系型数据库分页实现矩阵**

    | 数据库类型 | 分页实现方式与核心关键字 |
    | :--- | :--- |
    | MySQL | `LIMIT [offset,] count` 或 `LIMIT count OFFSET offset` |
    | PostgreSQL / MariaDB | `LIMIT count OFFSET offset` |
    | SQLite（移动端嵌入式） | `LIMIT offset, count` |
    | Microsoft SQL Server | `TOP (n)` 或 `OFFSET ... FETCH NEXT ...` |
    | IBM DB2 | `FETCH FIRST n ROWS ONLY` |
    | Oracle Database | 借助隐藏系统伪列 `ROWNUM`（多层子查询嵌套） |

    * SQL 是操作关系型数据库的国际通用结构化查询语言标准，MySQL、PostgreSQL 等是遵循该标准的具体软件产品，物理分页机制是各产品方言特征最明显的领域。
    * > 来源: P23

* **Oracle 的 ROWNUM 分页限制**
    * Oracle 表结构中默认提供系统级隐式隐藏伪列 `ROWNUM`，执行 `DESC employees;` 可以看到表本身并不包含该物理列；提取前 10 条写作 `SELECT employee_id, last_name FROM employees WHERE ROWNUM <= 10;`。
    * `ROWNUM` 是在数据行被从表中读取、且在 `ORDER BY` 排序执行之前动态分配的递增编号。直接写 `WHERE ROWNUM <= 10 ORDER BY salary DESC` 的实际含义是先盲目抓出前 10 条记录再对这 10 条内部排序。
    * `ROWNUM` 不支持直接大于运算，`WHERE ROWNUM >= 20` 永远返回空集，因为第 1 行未通过条件时其 `ROWNUM` 不会自增。
    * Oracle 中实现分页通常必须嵌套两层甚至三层子查询：内层负责排序并物化 `ROWNUM`，外层负责区间过滤。
    * > 来源: P23

### 8.4 排序与分页综合实战

* **结构化 SQL 的子句映射模型**
    * 「查询/显示员工的姓名、年薪」映射到 `SELECT last_name, salary * 12 AS annual_sal`；「从员工信息中」映射到 `FROM employees`；「要求工资不在特定区间内」映射到 `WHERE salary NOT BETWEEN ...`；「先按年薪降序，再按姓名升序」映射到 `ORDER BY annual_sal DESC, last_name ASC`；「仅展示第 21 到 40 条数据」映射到 `LIMIT 20, 20`。
    * 工程习惯为分步验证逐步追加：先敲定 `SELECT` 目标字段与 `FROM` 数据源确认数据通路；再追加 `WHERE` 并立即执行验证记录数；再追加 `ORDER BY` 检查排序方向；最后追加 `LIMIT` 截取目标窗口。
    * > **提示**：语法错误能通过错误信息迅速定位拼写或槽位问题；最危险的是执行完全成功但因漏掉某个过滤条件或排序列而返回看似合理但实际错误的数据。
    * > 来源: P24

* **计算列别名在二级排序中的复用**
    * `SELECT last_name, department_id, salary * 12 AS annual_salary FROM employees ORDER BY annual_salary DESC, last_name ASC;` 的绝大多数员工年薪各不相同，系统完全依据 `annual_salary` 完成降序输出；只有当多名员工年薪完全相同（如年薪同为 144,000）时才会激活第二排序列 `last_name` 按字母升序裁决。
    * > **注意**：写成 `ORDER BY salary * 12 DESC, last_name ASC` 语法同样通过并得出正确结果，但执行引擎的排序模块不得不对每一行记录重复执行一次乘法算术运算，徒增 CPU 计算开销；优先复用计算别名是业内推崇的规范写法。
    * > 来源: P22, P24

* **过滤、排序与分页的端到端组合**
    * 需求「月薪不在 8000 到 17000 范围内、按月薪降序、截取第 21 到 40 条」的完整实现：
        ```sql
        SELECT last_name, salary
        FROM employees
        WHERE salary NOT BETWEEN 8000 AND 17000
        ORDER BY salary DESC
        LIMIT 20, 20;
        ```
    * `WHERE salary NOT BETWEEN 8000 AND 17000` 由于原区间包含 8000 与 17000 边界，加上 `NOT` 后严格等价于 `salary < 8000 OR salary > 17000`。
    * 查询「工资大于 6000、按工资从高到低、截取前 10 条」：`WHERE salary > 6000 ORDER BY salary DESC LIMIT 0, 10;`（`0` 可省略写为 `LIMIT 10`）。
    * > 来源: P23, P24

* **字符集、比较规则与字节长度函数**
    * 需求「按邮箱长短降序排列」时直接写 `ORDER BY email DESC` 得到的是字典序结果：以 `Z`、`Y`、`X` 开头的邮箱排在前面，以 `A`、`B` 开头的排在后面。
    * > **定义**：字符集（Character Set）决定字符如何转换为二进制字节进行持久化存储；比较规则（Collation / 校验规则）决定执行比较运算符（`=`、`<>`）、范围判定以及 `ORDER BY` 时两个字符之间以何种权重比较大小。
    * 服务端配置文件（`my.ini` 或 `my.cnf`）中 `[mysqld]` 段落分别由 `character-set-server = utf8mb4` 定义字符编码集合、由 `collation-server = utf8mb4_bin` 定义比较规则。
    * 直接对字符串字段做 `ORDER BY` 本质是调用比较规则，从第一个字符开始逐位对比底层二进制权重，例如 ASCII 兼容编码中 `'B'` 的码值大于 `'A'`。
    * 按字节数排序必须引入单行文本处理函数 `LENGTH()`：`SELECT employee_id, last_name, department_id, email FROM employees WHERE email LIKE '%e%' ORDER BY LENGTH(email) DESC, department_id ASC;`，第一维度按邮箱字节数降序，字节数相等时激活次级规则按部门编号升序，极端情况还可追加 `, employee_id ASC` 实现三级排序。
    * > 来源: P24

## 9. 多表查询的必要性与基础规范

> **一句话主旨**：说明实体拆表在存储与并发上的必然性，给出多表连接的基数公式、字段二义性处理与表别名的作用域铁律。

### 9.1 拆表的物理必然性

* **业务场景中的跨表链路**
    * 三张核心表的结构与关联：`employees`（11 个字段，主键 `employee_id`、外键 `department_id`）、`departments`（4 个字段，主键 `department_id`、外键 `location_id`）、`locations`（6 个字段，主键 `location_id`、外键 `country_id`）。
    * 查询「名为 `Abel` 的员工在哪个城市工作」的单表思维解法需要三步：先在 `employees` 中按 `last_name = 'Abel'` 取到 `department_id = 80`（部门编号 `80`，销售部门 Sales）；再用 `department_id = 80` 查 `departments` 得到 `location_id = 2500` 与负责人工号 145；再用 `location_id = 2500` 查 `locations` 得到 `city = 'Oxford'`（牛津，位于英国 UK）。
    * > 来源: P25

* **分步查询的网络往返代价**
    * 企业生产环境中应用服务器与数据库服务器绝大多数部署在不同物理机或独立容器内，依赖局域网甚至跨可用区专线通信。
    * 完成一个「查员工所在城市」功能需要应用与数据库进行三次完整的网络往返（Network Round-Trip Time，RTT），网络抖动或并发压力升高时三次延迟累加会严重拖慢接口响应耗时。
    * 应用层还必须在内存中维持中间状态、编写大量胶水代码解析第一条结果、提取 ID、再拼接第二条 SQL，代码复杂度与出错概率呈倍数增加。
    * > **结论**：单表分步查询把本该由数据库内核高效率执行的关系运算转嫁给了应用层与网络链路，必须借助多表连接查询合成一条 SQL，仅通过一次网络交互由数据库内核直接完成数据匹配并返回最终结果。
    * > 来源: P25

* **大宽表方案的四大隐患**
    * 存储冗余与一致性危机：以 IT 研发部 300 名员工为例，规范化分表下 `departments` 仅需 1 行记录，`employees` 的 300 行各存一个 4 字节整型外键；大宽表设计中每一行员工数据都要重复追加部门名称、管理者编号、办公地点编码乃至街道、邮编、城市与国家 ID，同一套描述信息被物理重复刻写 300 遍。
    * > 易错点：大宽表会直接破坏数据一致性，引发修改异常（部门改名或搬迁需逐行更新，中断后出现新旧部门名混杂的脏数据）、插入异常（新成立部门尚无员工时无法作为独立实体存入，除非在所有个人字段写入 `NULL`）、删除异常（部门全部员工离职后该部门本身的存在信息与管理架构被一并抹除）。
    * 空值泛滥与存储碎片：稀疏关系下大宽表为迎合统一 schema 会填充大量 `NULL`，导致行记录头信息膨胀、变长字段偏移列表拉长，破坏物理数据页连续性并造成巨大存储碎片。
    * 底层磁盘 I/O 开销：MySQL（尤其 InnoDB）数据读取的最小物理调度单位是数据页（Page），默认大小 `16KB`。10 个字段、单行 160 字节的窄表一个数据页可容纳约 100 条记录；100 个字段、单行 1600 字节的宽表一个数据页仅能吞吐约 10 条记录。扫描 10000 名员工时宽表的磁盘 I/O 调用频次激增十倍以上。
    * 宽表模式还会把无用的长文本冗余数据一同读入内存，迅速占满高速缓冲池（Buffer Pool），导致热点数据被过早淘汰出内存。
    * > 易错点：不要以为单表查询少写个 JOIN 性能就一定好。如果单表过宽，付出的磁盘 I/O 代价与内存换入换出开销远远超过在内存中执行高效关联索引匹配的成本。
    * 事务并发度与锁冲突：分表体系下 HR 批量调整员工岗位锁定 `employees` 的数据行、行政部门更新地址信息操作 `locations` 表，两个事务在不同物理表上并发推进互不阻塞；单张宽表中修改某个办公地点名称可能触发整表元数据锁（Metadata Lock，MDL）变更或大范围行级排他锁（X 锁），使员工入职、调薪、考勤打卡操作陷入阻塞排队。
    * > 来源: P25

* **实体关系模型与范式理论**
    * 关系型数据库命名的核心在于解耦实体与建立关系：一实体一表，现实世界中每种独立客观对象在数据库中都应拥有且仅拥有一张专属数据表刻画其原生属性；实体之间的隶属、归属、协同关系（一对一、一对多、多对多）通过在表中存储关联标识键（如外键 ID）实现动态连接。
    * 设计思想在存储层让各实体表保持极窄行宽、无冗余、无异常、锁粒度细、磁盘 I/O 吞吐高；在业务层通过多表连接机制让数据库计算引擎在内存中基于关联键完成快速拼接与重组。
    * > 来源: P25

### 9.2 笛卡尔积与连接条件

* **缺少连接条件的全排列现象**
    * `SELECT employee_id, department_name FROM employees, departments;` 不报语法错误但返回 **2889 行**，每个员工都出现在公司的每一个部门里。
    * 算术验算：`SELECT COUNT(*) FROM employees;` 得 107，`SELECT COUNT(*) FROM departments;` 得 27，`SELECT 2889 / 107 FROM dual;` 恰好除尽等于 27，即 $107 \times 27 = 2889$。
    * > **结论**：数据库在没有得到任何关联过滤指令的情况下，忠实地把 `employees` 表的每一行记录分别与 `departments` 表的所有记录做了一次穷举配对。
    * > 来源: P26

* **笛卡尔积（Cartesian Product）与交叉连接（Cross Join）**
    * > **定义**：设有两个非空集合 $X$ 与 $Y$，由 $X$ 中任意元素 $x$ 与 $Y$ 中任意元素 $y$ 组成的所有有序对 $(x, y)$ 的集合称为笛卡尔乘积，记作 $X \times Y$，形式化表述为 $X \times Y = \{(x, y) \mid x \in X \land y \in Y\}$。
    * 若集合 $X$ 的基数为 $m$、集合 $Y$ 的基数为 $n$，则笛卡尔积集合的基数必为 $m \times n$。示例：$X = \{a, b, c\}$ 与 $Y = \{x, y\}$ 的全部匹配对为 $\{(a, x), (a, y), (b, x), (b, y), (c, x), (c, y)\}$，总数恰为 $3 \times 2 = 6$ 种。
    * > **提示**：笛卡尔积本身是一个中性的数学代数概念，绝不是语法错误。数据库引擎原生支持通过 `CROSS JOIN` 关键字显式计算笛卡尔积：`SELECT employee_id, department_name FROM employees CROSS JOIN departments;` 同样稳定产出 2889 条记录，语法完全等价于逗号连接。
    * 「笛卡尔积错误」的判定依据是真实业务目标为寻找员工与其真实所属部门的对应关系，而代码疏漏使执行引擎退化成了全量排列扫描。
    * > 来源: P26

* **笛卡尔积错误的三类诱因**
    * 完全省略连接条件：在 `FROM` 中书写了多张表但未编写任何 `WHERE` 关联子句。
    * 连接条件无效：`WHERE` 中的条件恒为真（如 `WHERE 1 = 1`），或比较了完全无关的非外键字段。
    * 逻辑孤岛：涉及三张或更多表时遗漏了其中某张表的连接路径，导致该表与其他表产生局部笛卡尔积。
    * > 来源: P26

* **基于 WHERE 的等值连接与 106 行的成因**
    * `SELECT employee_id, department_name FROM employees, departments WHERE employees.department_id = departments.department_id;` 把结果从 2889 行收敛至 **106 行**。
    * 缺失的那 1 人是工号 `178` 的 Kimberely Grant，其 `department_id` 值为 `NULL`（刚入职尚未正式分配归属部门）。
    * 当某一行的 `employees.department_id` 为 `NULL` 时，与部门表中任何整型 `department_id`（10, 20, …, 270）做 `=` 比较的结果既不是 `TRUE` 也不是 `FALSE`，而是三值逻辑中的 `UNKNOWN`；`WHERE` 过滤机制只放行判定结果为 `TRUE` 的行。
    * > **提示**：业务要求「即便员工没有部门也必须列出该员工（部门名称显示 `NULL`）」属于外连接（Outer Join）范畴；基于 `WHERE` 的连接属于内连接（Inner Join），只返回完全匹配条件的交集记录。
    * > 来源: P26, P27

* **至少 n - 1 个连接条件**
    * > **核心定理**：若有 $n$ 张数据表参与多表查询，为了彻底避免笛卡尔积错误，在查询语句中至少需要 $n - 1$ 个有效的连接条件。
    * 三表关联的完整写法：`SELECT e.employee_id, e.last_name, d.department_name, l.city FROM employees e, departments d, locations l WHERE e.department_id = d.department_id AND d.location_id = l.location_id;` 输出稳定为 **106 行**。
    * 连接顺序为：`e` 与 `d` 先通过第一个条件消除员工与部门的笛卡尔积；关联产出的中间结果集再通过 `d.location_id = l.location_id` 与地址表 `l` 建立绑定，彻底消除地址维度的笛卡尔积。
    * 少于 $n - 1$ 个条件必定存在游离表、百分之百产生笛卡尔积错误；多于 $n - 1$ 个条件完全合规且在真实业务中非常普遍。
    * 多于 $n - 1$ 的实例：查询「既在某个部门任职、且恰好是该部门负责人」的记录时，$n = 2$ 张表却拥有 2 个连接条件——`WHERE e.department_id = d.department_id AND e.employee_id = d.manager_id`。
    * > 来源: P26

### 9.3 字段限定与表别名

* **字段二义性（Ambiguous Column）**
    * > **定义**：在多表查询的字段列表或条件子句中，出现了两张或多张参与连接的表中共同存在的同名字段，由于没有显式指明该字段属于哪张表，SQL 解析器无法确定取值来源而抛出运行时异常。
    * `SELECT employee_id, department_id, department_name FROM employees, departments WHERE employees.department_id = departments.department_id;` 报错 `ERROR 1052 (23000): Column 'department_id' in field list is ambiguous`。
    * 修复方案是使用 `表名.字段名` 前缀形式显式限定：`SELECT employees.employee_id, employees.department_id, departments.department_name ...`；投影 `employees.department_id` 或 `departments.department_id` 均可（两值完全一致），但前缀绝不可省略。
    * > 来源: P26

* **全字段显式指明表归属的优化依据**
    * > **结论**：在所有多表查询语句中，`SELECT` 列表与过滤条件中的每一个字段都应当无条件显式指明其归属的表名（或表别名）。
    * 底层机理是 SQL 解析器的元数据寻址成本：写裸字段 `employee_id` 时解析器生成语法树必须先去 `employees` 表元数据字典检索该字段是否存在，再去 `departments` 表检索确认是否重名；写 `employees.employee_id` 时解析引擎直接命中 `employees` 表的结构定义提取列偏移量，省去在其余关联表中的全量试探开销。
    * > 来源: P26, P31

* **表别名与别名作用域铁律**
    * 表别名在 `FROM` 子句中紧跟在表名后以空格加简短别名的方式声明：`FROM employees emp, departments dept`。
    * > 易错点：一旦在 `FROM` 子句中为某张表赋予了表别名，那么在整条 SQL 的其他所有子句（包括 `SELECT`、`WHERE`、`ORDER BY` 等）中必须且只能使用该别名，严禁再使用原表名。
    * 反面示例 `SELECT employees.employee_id, dept.department_name FROM employees emp, departments dept WHERE emp.department_id = dept.department_id;` 报错 `ERROR 1054 (42S22): Unknown column 'employees.employee_id' in 'field list'`。
    * 根源在于执行时序：`FROM` 是整条 SQL 最先被执行的子句，声明 `employees emp` 后执行引擎在当前查询上下文的符号表中已把原表名替换注册为 `emp`；后续阶段解析 `SELECT` 或 `WHERE` 时符号表里根本不存在名为 `employees` 的对象。
    * > 来源: P26

## 10. 多表查询的分类体系与自连接

> **一句话主旨**：建立多表查询的三个独立分类维度，讲清非等值连接的区间映射实现与自连接的逻辑分身机制及其内连接边界。

### 10.1 三维分类框架

* **多表查询的三个独立分类维度**
    * 维度一（按条件运算符）：等值连接 vs 非等值连接，划分依据是连接条件中使用的比较操作符。
    * 维度二（按物理表来源）：自连接 vs 非自连接，划分依据是参与连接的数据源在磁盘中的物理实体是不同物理文件还是同一张物理表在内存中的虚拟映射。
    * 维度三（按结果保留集）：内连接 vs 外连接（左外 / 右外 / 满外），划分依据是未能命中连接条件的行是否强制保留。
    * 三个维度相互独立、交织并存，划分结果完全取决于观察的切入视角。
    * > 来源: P27

### 10.2 等值连接与非等值连接

* **等值连接（Equi Join）**
    * > **定义**：在连接条件中使用等号运算符（`=`）来比对不同表关联字段取值的多表查询。
    * 适用前提是两表之间存在明确的离散键值映射，如员工的部门编号严格匹配部门表的主键：`WHERE employees.department_id = departments.department_id`。
    * > 来源: P27

* **非等值连接（Non-Equi Join）**
    * > **定义**：连接条件中使用除等号之外的操作符（包括但不限于 `BETWEEN ... AND ...`、`>=`、`<=`、`>`、`<`、`!=`）进行跨表数据关联的查询技术。
    * 业务模型：`job_grades`（岗位薪级表）共 6 行，字段为 `grade_level`、`lowest_sal`、`highest_sal`——`A` 档 `[1000, 2999]`、`B` 档 `[3000, 5999]`、`C` 档 `[6000, 9999]`、`D` 档 `[10000, 14999]`、`E` 档 `[15000, 24999]`、`F` 档 `[25000, 40000]`。
    * 实现写法一（`BETWEEN` 闭区间）：`WHERE e.salary BETWEEN g.lowest_sal AND g.highest_sal`。
    * 实现写法二（显式复合比较）：`WHERE e.salary >= g.lowest_sal AND e.salary <= g.highest_sal`。
    * 两种写法均返回 **107 条**记录，员工薪资被精准卡入对应职级：King 的 24000 落入 `E` 档、Kochhar 与 De Haan 的 17000 落入 `E` 档、Hunold 的 9000 落入 `C` 档、Ernst 的 6000 因闭区间而命中 `C` 档。
    * > **提示**：使用 `BETWEEN ... AND ...` 时语法规范强制要求小值写在前面（下界）、大值写在后面（上界），因为底层逻辑恒等解析为 `val >= low AND val <= high`；上下界倒置时条件永远无法满足、结果集必定为空。
    * > 来源: P27

### 10.3 自连接与非自连接

* **自连接（Self Join）与非自连接（Non-Self Join）的概念边界**
    * > **定义**：非自连接指参与连接的多张表在磁盘中属于不同的物理表实体（如 `employees` 与 `departments`）；自连接指参与连接的两端在底层物理磁盘上仅存在唯一的同一张数据表，通过在逻辑层面赋予不同别名虚拟构造成两张独立的数据表进行关联。
    * 自连接的本质映射的是现实世界中普遍存在的自我引用（Self-Reference）或层级树状关系。
    * > 来源: P27

* **组织架构中的自我引用模型**
    * `employees` 表内部实现闭环：`employee_id` 是当前员工本人的唯一主键标识，`manager_id` 是当前员工的直接领导者工号。
    * 真实数据关系：105 号 David Austin 的管理者编号是 103（Alexander Hunold）；103 号自己的管理者编号是 102（Lex De Haan）；顶级管理者 100 号 Steven King 是全公司最高统帅、没有上级，其 `manager_id` 为 `NULL`。
    * 若为「普通员工」与「管理者」分别建表，一旦员工晋升为经理或经理降职为普通员工，数据就必须在两张表之间来回物理迁移，架构极其脆弱。
    * > 来源: P27

* **自连接的别名分身实现**
    * 把 `employees` 在 `FROM` 中书写的两次分别命名为 `emp`（充当员工角色）与 `mgr`（充当管理者角色），连接条件必须严格保持拓扑指向：
        $$\text{emp.manager\_id} = \text{mgr.employee\_id}$$
    * 完整实现：
        ```sql
        SELECT emp.employee_id AS "员工工号",
               emp.last_name   AS "员工姓名",
               mgr.employee_id AS "管理者工号",
               mgr.last_name   AS "管理者姓名"
        FROM employees emp, employees mgr
        WHERE emp.manager_id = mgr.employee_id;
        ```
    * 执行结果为 **106 行**；缺少的 1 人是 100 号 Steven King，因为其 `manager_id` 为 `NULL`，`NULL = mgr.employee_id` 判定为 `UNKNOWN`，在内连接模式下被筛除在外。
    * > **注意**：两张逻辑表结构完全一致时 `employee_id` 与 `last_name` 出现严重的同名冲突，不带 `emp.` 或 `mgr.` 前缀会直接抛出 `Column 'employee_id' in field list is ambiguous`，每个字段的前缀限定在这里是绝对不可逾越的红线。
    * 若希望 King 即使没有管理者也被展示出来（管理者姓名显示 `NULL`），必须依赖外连接。
    * > 来源: P27

* **四种连接形态的业务判定**

    | 连接形态 | 核心语法特征 | 典型业务场景 | 避坑要点 |
    | :--- | :--- | :--- | :--- |
    | 等值连接 | `table1.col = table2.col` | 基于主键-外键关系的精确数据拼装 | 警惕 `NULL` 值在等值匹配中被隐式过滤 |
    | 非等值连接 | `col BETWEEN low AND high` 或 `>=` / `<=` | 业绩提成计算、阶梯水费电费计算、成绩考评等级映射 | `BETWEEN` 必须严格遵循先小后大；区间边界重叠易致重复匹配 |
    | 自连接 | `FROM table a, table b WHERE a.fk = b.pk` | 组织上下级汇报链、电商商品类目多级树 | 必须使用表别名且投影字段必须全量限定前缀，防止 `ambiguous` |
    | 非自连接 | `FROM table_A a, table_B b` | 实体间的跨表关联（如商品表关联商户表） | 至少需要 $n - 1$ 个连接条件防范笛卡尔积 |

    * > 来源: P27

### 10.4 多表查询解题方法论

* **四步破局法**
    * 审题定主从与连接类型：包含「所有」「全部」字眼时锁定主表并必须使用外连接（`LEFT JOIN` / `RIGHT JOIN`）；包含「没有」「未分配」「不存在」字眼时锁定补集过滤，用外连接加 `WHERE 从表.key IS NULL`；仅是条件交集筛选时使用标准等值内连接。
    * 溯源字段与定义别名：遍历每个要查询的字段查明其所在物理表，为参与关联的每一张表定义简短别名，所有 `SELECT` 列必须带上前缀。
    * 分步装配与链式检查：遵循「每 `JOIN` 一张表，紧随一个 `ON` 条件」的规则；链式关联时注意主表外连接的传递性，主表左外连副表后，副表再连第三张表时必须保持 `LEFT JOIN`，否则前功尽弃。
    * 单表基准对比与极值检验：不确定是否丢失数据时，单独用单表 `COUNT(*)` 查询基准数值与多表结果进行对齐核验，并关注主外键为 `NULL` 的极值记录（无部门员工、无上级总裁、无员工部门）。
    * > 来源: P31

## 11. 内连接与外连接及 SQL92 / SQL99 标准

> **一句话主旨**：划清内连接与外连接的集合边界，对比两套标准的连接语法差异，并说明 MySQL 对两种外连接标准语法的兼容现状。

### 11.1 内连接与外连接的本质区别

* **内连接（Inner Join）**
    * > **定义**：合并具有关联关系的两个或多个表，结果集中仅包含完全满足连接条件的行，任何在另一张表中找不到匹配对应项的记录都会被全部丢弃。
    * 逗号左边的 `employees` 称为左表，右边的 `departments` 称为右表。左表中 178 号员工 Kimberely Grant 的 `department_id` 为 `NULL`，右表中部分新建部门（如 Treasury、Shareholder Services）下尚未录入任何员工，两侧孤立行都被双向过滤筛剔除，只保留严丝合缝的 **106** 组交集数据。
    * > 来源: P28

* **外连接（Outer Join）的三种形态**
    * > **定义**：合并两个或多个表，结果集除了包含完全满足连接条件的匹配行之外，还额外包含左表或右表（或两侧）中不满足连接条件的孤立行；对于孤立行中缺失的对侧字段，数据库统一使用 `NULL` 进行占位填充。
    * 左外连接（Left Outer Join）保留交集 + 左表不匹配的孤立行；右外连接（Right Outer Join）保留交集 + 右表不匹配的孤立行；满外连接（Full Outer Join）保留交集 + 左表孤立行 + 右表孤立行。
    * > 来源: P28

* **「查询所有的……」的题型雷达**
    * > **提示**：业务需求或笔试题目中一旦出现「查询所有的……」（如「查询所有员工的姓名和所属部门」、「统计全部考生的考场安排」），而所查询字段又跨越了多张实体表时，该题严禁写内连接，必须使用外连接。
    * 顺手写一个普通的等值关联会让没有部门的员工或没有考生的考场被悄悄漏掉，代码直接被判定为逻辑错误。
    * > 来源: P28, P31

### 11.2 SQL92 与 SQL99 标准演进

* **标准发布序列与规范特征**

    | 标准代号 | 发布年份 | 标准全称与代称 | 核心规范特征与文档体量 |
    | :--- | :--- | :--- | :--- |
    | SQL-86 | 1986 年 | SQL-86 | ANSI 首个 SQL 官方形式化标准，奠定关系查询的基础雏形 |
    | SQL-89 | 1989 年 | SQL-89 | 在 86 标准基础上补充完整性约束规范 |
    | SQL-92 | 1992 年 | SQL2（里程碑） | 规格手册约 500 页，语法紧凑，多表连接完全揉杂在 `WHERE` 子句中，可读性较弱 |
    | SQL-99 | 1999 年 | SQL3（现代基石） | 规格手册膨胀至 1000 余页，引入 `JOIN ... ON` 语法，支持外连接并丰富面向对象特性 |
    | SQL:2003+ | 2003 年至今 | SQL:2003 / 2008 / 2011 / 2016 | 陆续引入 XML 支持、窗口函数（Window Functions）、JSON 原生解析等高级特性 |

    * 工业界落地最广泛的正是 SQL92 与 SQL99 两大标准体系。
    * > 来源: P28

* **SQL92 内连接的实现方式**
    * 多张表在 `FROM` 后面直接用逗号（`,`）隔开，连接条件与业务过滤条件全部堆叠在 `WHERE` 子句中用 `AND` 串联：
        ```sql
        SELECT e.employee_id, e.last_name, d.department_name
        FROM employees e, departments d
        WHERE e.department_id = d.department_id;
        ```
    * > 来源: P28

* **SQL92 外连接的加号「补齐短腿」机理**
    * SQL92 委员会使用括号包裹的加号 `(+)` 运算符表达外连接：左表 107 个元素数据较长，右表匹配时只有 106 组能对应上相对较短，要在短腿底下垫增高鞋垫使其与长腿对齐。
    * 左外连接（期望左表全量展示）时右表是「短腿」，把 `(+)` 加在右表字段后面：$\text{employees.department\_id} = \text{departments.department\_id(+)}$，数据库看到右边的 `(+)` 会自动在右表虚拟出由 `NULL` 构成的填充行。
    * 右外连接（期望右表全部保留）时左表是「短腿」，把 `(+)` 挂在左表字段后面：$\text{employees.department\_id(+)} = \text{departments.department\_id}$。
    * > 注意：`(+)` 的标注位置极易产生极性混淆。核心口诀是想保留哪一侧的全部数据，`(+)` 就必须加在对立的另一侧（想保左，加号放右；想保右，加号放左）。
    * 在 Oracle 中执行 SQL92 左外连接精准返回 **107 行**，Kimberely Grant 的部门名称被赋予 `NULL` 成功打印；右外连接精准返回 **122 行**（106 组在职部门 + 16 个无人入驻的空壳部门）。
    * > 来源: P28

* **MySQL 对 SQL92 外连接的零兼容**
    * 在 MySQL 中执行 `WHERE e.department_id = d.department_id(+)` 报错 `ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ')' at line 4`。
    * > **结论**：MySQL 原生内核彻底不支持 SQL92 标准中的 `(+)` 外连接语法，其查询解析器压根没有接入 `(+)` 的语法解析规则。
    * `(+)` 仍是正统的国际标准，只是不同数据库厂商对标准的吸纳存在取舍与代际差异。
    * > 来源: P28

* **SQL99 的内连接与外连接语法**
    * 内连接：`SELECT e.last_name, d.department_name FROM employees e INNER JOIN departments d ON e.department_id = d.department_id;` 其中 `INNER` 关键字可省略，只写 `JOIN` 时系统默认解析为内连接。
    * 三表链式级联：每拉进一张新表就跟随一个 `ON` 声明其引荐凭证，`FROM employees e JOIN departments d ON e.department_id = d.department_id JOIN locations l ON d.location_id = l.location_id`。
    * 左外连接：`FROM employees e LEFT OUTER JOIN departments d ON e.department_id = d.department_id;` 在 MySQL 中成功返回 **107 行**，178 号无部门员工的姓名右侧稳稳挂着 `NULL`。
    * 右外连接：`FROM employees e RIGHT OUTER JOIN departments d ON e.department_id = d.department_id;` 输出 **122 行**，包含 106 组有员工的部门与 16 个没有任何员工归属的部门（左侧员工信息填 `NULL`）。
    * > **提示**：实际项目开发中 `OUTER` 关键字通常被约定俗成地省略，直接简写为 `LEFT JOIN` 与 `RIGHT JOIN`。
    * > 来源: P28

* **SQL99 相较 SQL92 的三条工程优势**
    * `INNER` 可省略，语法更简洁；连接条件与业务过滤彻底解耦——表与表之间的拓扑桥梁写在 `ON` 子句中，行级数据过滤（如 `salary > 5000`）继续追加在 `WHERE` 子句中。
    * 彻底杜绝笛卡尔积遗漏：SQL92 中写了多个逗号却在 `WHERE` 里少写一个条件会静默退化为笛卡尔积；SQL99 中每次敲下 `JOIN`，语法分析器都强制要求紧随一个 `ON`。
    * > 来源: P28

* **满外连接（Full Outer Join）的幻灭与替代**
    * 按逻辑对称性推导，满外连接的结果集预期为 $106 + 1 + 16 = 123$ 行；标准 SQL99 规范明确定义了 `FULL OUTER JOIN` 关键字。
    * 在 MySQL 中执行 `FULL OUTER JOIN` 报错 `ERROR 1054 (42S22): Unknown column 'FULL' in 'from clause'`。
    * > 易错点：MySQL 原生完全不支持 `FULL JOIN` 或 `FULL OUTER JOIN` 语法。同样的语句在 Oracle 数据库中执行可顺畅返回 123 条数据。
    * 技术选型现状：商业版大型数据库（Oracle、DB2）严格遵循标准、在企业级复杂查询与售后保障上底蕴深厚，但授权昂贵、架构笨重，主要盘踞在银行、证券、电信与大型央国企；开源关系型数据库（MySQL）轻量免费、社区生态繁荣，读写吞吐优异，支撑了全球超过 80%~90% 的互联网应用与中小型企业系统。
    * > 来源: P28

### 11.3 七种 JOIN 的几何模型

## 12. 七种 JOIN 的 SQL99 实现与集合合并

> **一句话主旨**：给出 UNION 与 UNION ALL 的机制差异与选型原则，逐个落地七种 JOIN 的 SQL 构造，并确定 ON 与 WHERE 的职责边界。

### 12.1 集合合并操作

* **UNION 与 UNION ALL 的语法与集合语义**
    * 核心作用是把多条 `SELECT` 查询语句的结果组合成一个单一结果集：`SELECT ... FROM table1 UNION [ALL] SELECT ... FROM table2;`
    * > **定义**：使用 `UNION` 或 `UNION ALL` 合并两个或多个结果集时，各 `SELECT` 子句查询的列数必须相同，且对应位置上的列其数据类型必须兼容或相同。
    * 集合视角的差异：`UNION` 仅保留一份交集数据、完成并集运算；`UNION ALL` 无论记录是否重复都直接把两个数据集上下串联，交集部分被重复计算两次。
    * 以员工表（表 A）与部门表（表 B）为例：交集 106 条、员工表独有 1 条、部门表独有 16 条。合并「左外连接结果集（107 条）」与「右外连接结果集（122 条）」时，`UNION` 结果为 $1 + 106 + 16 = 123$ 条，`UNION ALL` 结果为 $(1 + 106) + (106 + 16) = 229$ 条。
    * > 来源: P29

* **性能对比与工程选型原则**
    * > **结论**：在实际工程开发中，凡是能用 `UNION ALL` 的场景尽量不要使用 `UNION`。
    * `UNION` 的执行代价：引擎先把两个结果集读取并放入内存临时表（或磁盘临时表），随后必须在内存或临时表上执行一次全局排序与去重操作（类似于 `DISTINCT`），消耗大量 CPU 与内存资源，数据量达到数十万或百万级时性能瓶颈尤为突出。
    * `UNION ALL` 的执行代价：引擎仅需分配连续空间把两个结果集直接内存拼接，完全省去排序和哈希去重阶段，资源开销最小、响应速度极快。
    * > 易错点：使用 `UNION ALL` 追求高性能的前提是结果集本身不存在重复，或业务逻辑原本就允许重复。若要用 `UNION ALL` 拼出 123 条的满外连接，必须通过逻辑构造出天然互斥、绝对无交集的两个子数据集，不能简单粗暴地拿左外（107 条）去连右外（122 条）。
    * > 来源: P29

### 12.2 七种 JOIN 的逐个落地

* **七种 JOIN 的空间拓扑与集合定义**

    | 图示方位 | 连接性质 | 对应集合关系 | 核心 SQL 构造特征 | 案例结果条数 |
    | :--- | :--- | :--- | :--- | :--- |
    | 中图 | 内连接 | $A \cap B$ | `A JOIN B ON 条件` | 106 条 |
    | 左上图 | 左外连接 | $A$ | `A LEFT JOIN B ON 条件` | 107 条 |
    | 右上图 | 右外连接 | $B$ | `A RIGHT JOIN B ON 条件` | 122 条 |
    | 左中图 | A 独有（补集） | $A - (A \cap B)$ | `A LEFT JOIN B ON 条件 WHERE B.key IS NULL` | 1 条 |
    | 右中图 | B 独有（补集） | $B - (A \cap B)$ | `A RIGHT JOIN B ON 条件 WHERE A.key IS NULL` | 16 条 |
    | 左下图 | 满外连接 | $A \cup B$ | `左上图 UNION ALL 右中图`（或左中图 `UNION ALL` 右上图） | 123 条 |
    | 右下图 | 对称差集 | $(A \cup B) - (A \cap B)$ | `左中图 UNION ALL 右中图` | 17 条 |

    * 中图是核心交集；左上与右上是单侧全集；左中与右中是单侧补集；左下与右下是跨侧组合集。
    * > 来源: P29

* **左中图与右中图的补集过滤技巧**
    * 左中图查询「没有分配任何部门的员工」：在 `LEFT JOIN` 基础上追加 `WHERE d.department_id IS NULL`，返回 **1 条**记录（`employee_id = 178`）。
    * 过滤机理：执行 `LEFT JOIN` 时交集内的 106 条记录其右表匹配列必然存在真实数值，只有左表存在而右表完全无法匹配的行，引擎才会在右表的所有投影列上强制填充 `NULL`；因此用 `WHERE d.department_id IS NULL`（或右表的任意非空主键列）即可精确剔除所有交集行。
    * 右中图查询「没有任何员工入驻的空壳部门」：在 `RIGHT JOIN` 基础上追加 `WHERE e.department_id IS NULL`，返回 **16 条**记录。
    * > 来源: P29

* **满外连接（左下图）的两种推荐拼装方案**
    * 方案一（推荐）：左上图 `UNION ALL` 右中图。左上图提供 $106 + 1 = 107$ 条，右中图提供 16 条 B 独有，两集合交集为空，可直接使用开销最小的 `UNION ALL`，执行结果 **123 条**（$107 + 16 = 123$），无任何数据重复。
    * 方案二（推荐）：左中图 `UNION ALL` 右上图。左中图提供 1 条 A 独有，右上图提供 $106 + 16 = 122$ 条，两集合同样完全互斥，执行结果 **123 条**（$1 + 122 = 123$）。
    * > **提示**：若采用「左上图 `UNION` 右上图」，语法上可行且结果也是 123 条，但底层执行了 $107 + 122 = 229$ 条记录的合并并对 106 条重复记录执行排序去重，数据量大时会造成严重性能浪费；生产环境中应坚决采用方案一或方案二。
    * 在 Oracle 中，`SELECT e.employee_id, d.department_name FROM employees e FULL OUTER JOIN departments d ON e.department_id = d.department_id;` 一条原生语法即可搞定，同一语句在 MySQL 报错不支持。
    * > 来源: P29

* **对称差集（右下图）的实现**
    * 业务诉求是查询所有异常数据——未分配部门的员工以及没有任何员工的部门，完全排除正常匹配的员工与部门。
    * 实现思路为直接把「左中图（A 独有）」与「右中图（B 独有）」进行拼接，由于二者绝无交集，直接选用 `UNION ALL`。
    * 执行结果 **17 条**记录（$1 + 16 = 17$）；此类查询在数据校验、孤儿数据排查、历史脏数据审计中极为常用。
    * > 来源: P29

### 12.3 生产环境开发建议

* **ON 与 WHERE 的语义区分**
    * `ON` 是连接条件，决定从表（副表）中的记录如何与主表拼接；若副表不匹配，主表记录仍然保留（外连接特性）。
    * `WHERE` 是过滤条件，发生在连接生成结果集之后，会对已经连接的数据进行全局过滤。
    * 在实现「左中图」或「右中图」时，`IS NULL` 条件必须写在 `WHERE` 中才能生效排除交集。
    * > 来源: P29

* **连接字段索引与合并时的字段约束**
    * 做 `JOIN` 操作时，关联字段（如 `e.department_id = d.department_id`）若缺乏索引，数据库将被迫使用嵌套循环（Nested Loop Join）甚至是块嵌套循环（Block Nested Loop）进行全表扫描匹配，导致查询耗时急剧上升；外键列与主键列建立索引是多表查询性能优化的第一道防线。
    * 在进行 `UNION` 或 `UNION ALL` 合并时严禁使用 `SELECT *`：不同表的字段排列顺序和数据类型可能不一致，使用 `SELECT *` 极易引发列对齐错乱或运行时类型转换异常，应始终在每个子查询中显式指定字段列表。
    * > 来源: P29

## 13. 连接语法糖与生产级工程规约

> **一句话主旨**：剖析 NATURAL JOIN 与 USING 两个 SQL99 语法糖的自动匹配机理与适用边界，并给出连接条件写法的唯一推荐与三表 JOIN 的架构替代方案。

### 13.1 NATURAL JOIN 自然连接

* **NATURAL JOIN 的自动匹配机理**
    * > **定义**：自然连接可以视作 SQL92 等值连接的一种自动化变体。使用 `NATURAL JOIN` 关联两张表时，系统会自动探测并检索两张连接表中所有同名、同类型（或兼容类型）的列，并在底层将它们隐式拼接为等值连接条件（`AND` 关系）。
    * `employees` 与 `departments` 恰好存在两个同名字段：`department_id`（部门编号）与 `manager_id`（员工表中指该员工的直属上级编号，部门表中指该部门的负责人编号）。
    * 手工显式书写的等价形式为 `ON e.department_id = d.department_id AND e.manager_id = d.manager_id`，返回结果仅 **32 条**记录，业务含义是只有当员工所属部门编号与部门表编号一致、且员工的直属上级恰好就是该部门负责人时记录才被筛出。
    * 改用 `SELECT employee_id, last_name, department_name FROM employees NATURAL JOIN departments;` 返回记录数同样是精确的 **32 条**，引擎在解析到关键字后自动完成后台等值装配。
    * > 来源: P30

* **自然连接在工程应用中的致命缺陷**
    * > **结论**：NATURAL JOIN 具备高度的死板性与隐蔽性，缺乏业务灵活性。
    * 业务意图被暴力绑架：查询员工与其所属部门信息的核心诉求仅仅是建立归属关系（正常内连接应返回 106 条记录），但引擎会把 `manager_id` 也强行纳为关联键，使结果缩水为 32 条，引发严重的逻辑漏数 Bug。
    * DDL 变更带来的不确定性灾难：表 A 与表 B 未来新增一个同名的辅助列（如 `status` 或 `create_time`）时，原本运行正常的 `NATURAL JOIN` 会瞬间自动把新列追加到关联条件中，导致线上查询结果骤降甚至直接返回空，且这类隐蔽故障极难通过静态代码审查排查。
    * 自然连接了解概念即可，在生产环境的 SQL 编写中应坚决避免使用。
    * > 来源: P30

### 13.2 USING 关键字

* **USING 的语法与替代作用**
    * > **定义**：`USING` 关键字用于在多表连接中显式指定一个或多个同名字段作为等值连接条件，从而替代冗长的 `ON table1.col = table2.col` 写法；圆括号内填入的列名必须在两个关联表中完全一致。
    * `SELECT employee_id, last_name, department_name FROM employees e JOIN departments d USING (department_id);` 精确返回 **106 条**记录，引擎自动在两张表中分别提取同名为 `department_id` 的列并在底层构筑等值判定。
    * 它既避免了 `NATURAL JOIN` 把 `manager_id` 强行捆绑的弊端，又保留了语句的书写简洁度。
    * > 来源: P30

* **USING 的适用边界与局限性**
    * > 易错点：`USING` 只能用于关联两表列名完全相同的等值连接；非同名连接与自连接无法使用 `USING`。
    * 典型反例是自连接：员工表的管理者字段为 `manager_id`、管理者对应的主键字段为 `employee_id`，两列名完全不同，必须回归 `ON emp.manager_id = mgr.employee_id`。
    * 大型老旧系统的命名规范参差不齐时 `USING` 同样无法工作（例如订单表的外键字段叫 `user_code`，而用户表的主键叫 `id`）。
    * > 来源: P30

### 13.3 连接条件的三形态选型

* **三种书写形态的横向对比**

    | 书写形态 | 连接条件位置 | 核心特征 |
    | :--- | :--- | :--- |
    | SQL92 风格 | 在 `WHERE` 子句中直接书写连接条件 | 过滤条件与连接条件高度耦合，不支持外连接 |
    | SQL99 语法糖 | 在 `USING(列名)` 中指定同名列连接 | 书写简洁，但适用场景狭窄，字段名必须一致 |
    | SQL99 标准 | 在 `JOIN` 后紧跟 `ON` 子句显式指定 | 解耦连接与过滤，支持外连接与非等值，推荐标准 |

    * > **结论**：在实际工程开发中强烈推荐唯一统一使用 `JOIN ... ON` 结构。`ON` 不仅通用性最强（支持同名、异名、非等值、自连接以及全系外连接），而且语义最为清晰，把「多表连接机制」与「业务数据过滤（`WHERE`）」进行了绝对的逻辑解耦。
    * > 来源: P30

* **连环 JOIN 后的集中式 ON 写法**
    * SQL99 规范中存在一种极少见但合法的语法变形：多张表连续 `JOIN` 后把所有连接条件统一后置在末尾，如 `FROM employees e JOIN departments d JOIN locations l ON e.department_id = d.department_id AND d.location_id = l.location_id`。
    * 这种集中书写方式语法校验能通过，但严重破坏代码阅读流与排查效率，工程规范中严禁这样组织代码。
    * > 来源: P30

### 13.4 生产级架构规约

* **禁止超过三表 JOIN 的硬性规定**
    * 《阿里巴巴 Java 开发手册》（泰山版）MySQL 规约部分规定：超过三个表禁止使用 JOIN；需要 JOIN 的字段数据类型必须绝对一致；多表关联查询时保证被关联的字段需要有索引。
    * > 来源: P30

* **嵌套循环连接（Nested-Loop Join，NLJ）的开销膨胀**
    * 现代关系型数据库处理多表 JOIN 时最基础、最通用的底层算法模型是嵌套循环连接：两表关联相当于两层 for 循环（外层驱动表、内层被驱动表，逐行比对 key 相等则输出）；三表关联相当于三层 for 循环。
    * 每多引入一张表进行 `JOIN`，底层就相当多套一层循环；当数据量达到百万、千万级时，中间产生的临时笛卡尔积评估开销呈指数级剧增，耗尽数据库连接缓冲（Join Buffer）与内存，导致全表物理 I/O 暴涨。
    * > 来源: P30

* **优化器选择空间失控与索引失效风险**
    * MySQL 基于成本的优化器（Cost-Based Optimizer，CBO）在执行多表关联时需要评估所有可能的连接顺序（如 `A -> B -> C` 还是 `B -> C -> A`）。关联表达到 4 张、5 张甚至更多时，连接顺序的排列组合数以阶乘级（$N!$）暴增，优化器寻找最优执行计划本身消耗的解析时间可能超过查询执行时间，统计信息稍有偏差就会误判并选择性能极差的驱动顺序。
    * 多表关联要求参与关联的列数据类型保持绝对一致。若表 A 的 `order_id` 是 `VARCHAR(32)` 而表 B 的 `order_id` 误设计成 `VARCHAR(64)` 或带不同字符集（`utf8` 与 `utf8mb4`），连接匹配时会触发隐式类型转换函数，导致原本建立在索引上的查找彻底失效、退化为全表扫描。
    * > 来源: P30

* **超三表查询的两种架构替代方案**
    * 应用层拆分查询：把复杂多表关联拆解为若干条简单的单表主键或索引查询，例如先查订单表拿到用户 ID 和商品 ID，再通过 `WHERE id IN (...)` 分别去用户表和商品表做批量点查，最后在后端应用层利用哈希表（Map）在内存中快速完成对象组装。优势是单表点查极高概率命中主键索引与缓存、查询轻量不长时间霸占连接、并发吞吐量极大提高，且应用层加节点成本远低于数据库加节点。
    * 宽表与搜索聚合体系：在需要复杂多表检索、报表聚合的场景下，通过 Canal、Flink 等 CDC（Change Data Capture）中间件监听 MySQL 的 Binlog 日志，把分散在各张业务表的数据实时打平成一张无连接的宽表，投递至 Elasticsearch、ClickHouse 或数仓中专门进行高性能聚合查询。
    * > 来源: P30

## 14. 多表查询综合习题与陷阱复盘

> **一句话主旨**：以九道综合题覆盖外连接判定、连环外连接传递性、补集空值过滤与自连接边界，归纳每类题型的定式与漏数陷阱。

### 14.1 外连接判定与列名歧义

* **显示所有员工的姓名、部门号和部门名称**
    * 「所有员工」是外连接信号：使用内连接会让没有分配部门的员工在关联条件不满足时被直接剔除。MySQL 不支持 SQL92 外连接语法，必须采用 SQL99 的 `LEFT JOIN`。
    * 标准实现：
        ```sql
        SELECT e.last_name, e.department_id, d.department_name
        FROM employees e
        LEFT OUTER JOIN departments d ON e.department_id = d.department_id;
        ```
    * 两表均含 `department_id` 列，`SELECT` 投影列表中必须显式指定表别名，否则抛出 `Column 'department_id' in field list is ambiguous`。
    * 执行结果精确返回 **107 条**记录，包含 106 条正常匹配的员工以及编号 178、部门 ID 显示为 `NULL` 的 Grant。
    * > 来源: P31

* **查询 90 号部门员工的 job_id 和 90 号部门的 location_id**
    * 字段溯源：`job_id` 存在于 `employees` 表，`location_id` 存在于 `departments` 表，字段跨表必须连接；题目明确限定查询「90 号部门」，该部门确定存在且有员工在职，因此属于标准等值内连接。
    * 标准实现：
        ```sql
        SELECT e.job_id, d.location_id
        FROM employees e
        JOIN departments d ON e.department_id = d.department_id
        WHERE d.department_id = 90;
        ```
    * > **结论**：编写带过滤条件的多表连接时，连接逻辑由 `ON` 负责，业务过滤由 `WHERE` 负责，二者职责清晰分离。
    * > 来源: P31

### 14.2 连环外连接的传递性陷阱

* **查询所有有奖金的员工的姓名、部门名、位置编号、城市与奖金率**
    * 初学者写法使用三表内连接后追加 `WHERE e.commission_pct IS NOT NULL`，返回结果为 **34 条**记录。
    * 单表基准校验 `SELECT COUNT(*) FROM employees WHERE commission_pct IS NOT NULL;` 返回真实记录数 **35 条**，缺口来自编号 178 的无部门员工——其奖金率恰好是 `0.15`，在第一步关联 `departments` 时因 `department_id IS NULL` 被抹杀。
    * 仅把第一步改成 `LEFT JOIN departments` 仍不够：该员工在部门表中的 `location_id` 同样补齐为 `NULL`，第二步若写成普通内连接 `JOIN locations l ON d.location_id = l.location_id`，会再次把他过滤掉，结果依然停留在 34 条。
    * 正确实现要求两步都保持 `LEFT JOIN`：
        ```sql
        SELECT e.last_name, d.department_name, d.location_id, l.city, e.commission_pct
        FROM employees e
        LEFT JOIN departments d ON e.department_id = d.department_id
        LEFT JOIN locations l ON d.location_id = l.location_id
        WHERE e.commission_pct IS NOT NULL;
        ```
    * 执行结果精确返回 **35 条**记录，无部门员工的部门名称、位置编号与城市均显示为 `NULL`。
    * > 来源: P31

* **链式关联网的传递性检查**
    * 主表左外连副表后，副表再连第三张表时必须保持 `LEFT JOIN`，否则主表的孤立行会在后续内连接中被再次剔除、前功尽弃。
    * > 来源: P31

### 14.3 内连接类型的综合应用

* **查询在城市 Toronto 工作的员工信息**
    * 过滤条件 `city = 'Toronto'` 位于 `locations` 表，属于强约束（没有部门的员工自然不在多伦多），直接使用标准内连接。
    * SQL99 写法：
        ```sql
        SELECT e.last_name, e.job_id, e.department_id, d.department_name
        FROM employees e
        JOIN departments d ON e.department_id = d.department_id
        JOIN locations l ON d.location_id = l.location_id
        WHERE l.city = 'Toronto';
        ```
    * SQL92 等价写法把三张表用逗号罗列后，把 `e.department_id = d.department_id`、`d.location_id = l.location_id`、`l.city = 'Toronto'` 全部堆在 `WHERE` 中用 `AND` 串联。
    * 两种语法均返回 **2 条**记录；SQL99 的优势在于连接条件与业务筛选在物理子句上完全解耦。
    * > 来源: P31

* **查询部门名称为 "Executive" 的员工所在部门名称、部门地址、姓名、工作与工资**
    * 字段溯源：部门名称取 `d.department_name`；`departments` 表仅有 `location_id`，详细街道地址为 `locations` 表的 `street_address` 字段；员工信息取 `e.last_name`、`e.job_id`、`e.salary`。
    * 标准实现：
        ```sql
        SELECT d.department_name, l.street_address, e.last_name, e.job_id, e.salary
        FROM departments d
        JOIN employees e ON d.department_id = e.department_id
        JOIN locations l ON d.location_id = l.location_id
        WHERE d.department_name = 'Executive';
        ```
    * 执行结果返回 **3 条**记录。
    * > **提示**：真实生产环境建表时数据库规范要求所有列都必须维护完整的注释（Comment）；根据产品需求文档找字段时应严格依托注释或数据字典进行中文匹配，切忌凭英文直译想当然。
    * > 来源: P31

* **查询部门名为 "Sales" 或 "IT" 的员工信息**
    * 员工表本身不存储部门名称、仅存储 `department_id`，因此需要关联 `departments` 表，并用集合操作符 `IN ('Sales', 'IT')` 做多值匹配。
    * 标准实现：
        ```sql
        SELECT e.employee_id, e.last_name, e.salary, d.department_name
        FROM employees e
        JOIN departments d ON e.department_id = d.department_id
        WHERE d.department_name IN ('Sales', 'IT');
        ```
    * 执行结果精确返回 **39 条**记录（Sales 部门与 IT 部门的员工总和）。
    * > 易错点：SQL 标准中字符串字面量必须使用单引号包裹（如 `'Sales'`），切勿混用双引号。在某些数据库或严格 SQL 模式下双引号会被解析为标识符（列名或表名）而引发语法错误。
    * > 来源: P31

### 14.4 自连接与补集空值过滤

* **查询指定员工的姓名、员工号及其管理者的姓名、员工号**
    * 所有信息均保存在同一张 `employees` 表中，必须使用自连接，把 `employees` 逻辑上拆分为 `emp`（员工表）与 `mgr`（管理者表），连接关系为 `emp.manager_id = mgr.employee_id`。
    * 普通内连接写法返回 **106 条**记录，缺的是没有直接上级、`manager_id` 为 `NULL` 的公司最高总裁 King。
    * 题目要求呈现员工的领导情况，大老板本身也是公司员工必须予以展示，因此必须以员工表为主表采用左外自连接：
        ```sql
        SELECT emp.last_name AS "employees", emp.employee_id AS "Emp#",
               mgr.last_name AS "manager", mgr.employee_id AS "Mgr#"
        FROM employees emp
        LEFT JOIN employees mgr ON emp.manager_id = mgr.employee_id;
        ```
    * 执行结果精确返回 **107 条**记录，King 的管理者姓名与管理者编号呈现为 `NULL`。
    * > 来源: P31

* **查询哪些部门没有员工**
    * 这是典型的集合求补运算，输出只存在于部门表（$B$）但在员工表（$A$）中完全没有匹配的记录，即文氏图中的「右中图（$B - A \cap B$）」。
    * 推导步骤为先把部门表置于左侧为主表与员工表执行 `LEFT JOIN`（没有员工的部门其对应的员工表所有字段被系统置为 `NULL`），再在 `WHERE` 中追加 `e.department_id IS NULL`。
    * 实现代码：
        ```sql
        SELECT d.department_id, d.department_name
        FROM departments d
        LEFT JOIN employees e ON d.department_id = e.department_id
        WHERE e.department_id IS NULL;
        ```
    * 执行结果精确返回 **16 条**记录。
    * > **提示**：此类场景在后续章节中亦可通过子查询 `WHERE NOT EXISTS (...)` 实现，但在当前多表连接体系下，`LEFT JOIN ... WHERE ... IS NULL` 是性能最优、兼容性最好的标准实现。
    * > 来源: P31

* **查询哪个城市没有部门**
    * 逻辑与上一题完全同构，仅更换实体表：主表为地理位置表 `locations`（$L$），从表为部门表 `departments`（$D$），核心要求是找出存在于 `locations` 但在 `departments` 中没有任何引用的城市。
    * 实现代码：
        ```sql
        SELECT l.location_id, l.city
        FROM locations l
        LEFT JOIN departments d ON l.location_id = d.location_id
        WHERE d.location_id IS NULL;
        ```
    * 执行结果返回 **16 条**记录；反向求证 `SELECT department_id, department_name FROM departments WHERE location_id IN (1000, 1100, 1200, 1300, 1600);` 结果为空，与事实完全吻合。
    * > 来源: P31
