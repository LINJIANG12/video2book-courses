## 1. 日志体系总览

> **一句话主旨**：梳理 MySQL 六种日志的类型、记录内容与用途，明确文本日志与二进制日志的形态差别以及日志自身的代价。

### 1.1 六大日志的类型与用途

* **通用查询日志（general query log）**
    * > 定义：记录所有连接的起始与终止时间，以及连接发送给服务器的所有指令，是一份不做筛选的全量行为记录。
    * 用于复原真实现场、发现问题以及审计；文件形态是文本日志。
    * 只要服务器启动时它已处于开启状态，服务器的启动与关闭信息、用户的连接与断开起止时间、发送给服务器并被执行的指令都会写进去。
    * > 来源: P187, P188
* **错误日志（error log）**
    * > 定义：记录 MySQL 服务器（实例）从启动运行到宕机整个过程中出现的错误、警告、提示这一类信息。
    * 主要用途是定位宕机与故障原因；文件形态是文本日志。
    * > 来源: P187, P188
* **二进制日志（binary log，binlog）**
    * > 定义：记录所有更改数据的语句，含增、删、改与改表结构等 DDL 操作，不含查询。
    * 两大作用是数据恢复和主从服务器之间的数据同步；文件形态是二进制文件，不能用记事本打开。
    * 以事件（event）为单位记录，一条增删改或 DDL 对应一个事件。
    * > 来源: P187, P189
* **慢查询日志（slow query log）**
    * > 定义：记录执行时间超过 `long_query_time` 阈值的语句。
    * 用于 SQL 优化分析；配合 `EXPLAIN` 等工具分析为什么慢。
    * 文件形态是文本日志；参数设置已在性能分析工具部分讲过。
    * > 来源: P187
* **中继日志（relay log）**
    * > 定义：从服务器通过 I/O 方式从主服务器 `binlog` 读来、并保存在本地文件里的数据。
    * 作用是在主从复制链路中做中转；也称作中转日志；文件形态是文本日志。
    * > 来源: P187, P191
* **数据定义语句日志**
    * > 定义：针对数据定义语句的元操作所做的记录。
    * MySQL 8.0 才引入，与中继日志同属 8.0 新增的两种日志。
    * > 来源: P187

| 日志类型 | 记录内容 | 主要用途 | 文件形态 |
| :--- | :--- | :--- | :--- |
| 通用查询日志 | 所有连接的起始与终止时间，以及连接发送给服务器的所有指令 | 复原真实现场、发现问题、审计 | 文本日志 |
| 错误日志 | 实例从启动运行到宕机整个过程出现的错误与警告信息 | 定位宕机与故障原因 | 文本日志 |
| 二进制日志 `binlog` | 所有更改数据的语句（增、删、改与 DDL），不含查询 | 数据恢复、主从数据同步 | 二进制文件 |
| 慢查询日志 | 执行时间超过 `long_query_time` 阈值的语句 | SQL 优化分析 | 文本日志 |
| 中继日志 `relay log` | 从服务器从主服务器 `binlog` 读来并保存在本地的数据 | 主从复制链路的中转 | 文本日志 |
| 数据定义语句日志 | 数据定义语句的元操作 | 记录 DDL 层面的元操作 | 文本日志 |

### 1.2 日志的文件形态与存放位置

* 除二进制日志外，其余日志都是非二进制、可理解成文本日志，可以直接用记事本，或在 Linux 里用 `vi`、`vim` 打开查看。
* 这些日志默认都存放在 MySQL 的数据目录 `/var/lib/mysql` 下。
* > **易错点**：错误日志的默认位置不在数据目录下，它默认在 `/var/log/mysqld.log`（Linux），这一点与其余日志的默认位置形成差别。
* 二进制日志虽然中文也叫日志，但从形态上它不属于文本范畴，用记事本一类的工具打开不可靠。
* > 来源: P187, P188, P191

### 1.3 日志的两大弊端

* 日志会降低 MySQL 数据库的性能：服务器要分出一部分资源去做记录，性能必然受影响。
* > 易错点：日志会占用大量磁盘空间，尤其通用查询日志什么都记，不做归档与历史文件存储时会越占越多，甚至可能超出数据库文件本身的存储空间。
* 各日志的好处即在于作用各不相同，需要哪一类信息就查哪一类日志。
* > 来源: P187

## 2. 通用查询日志与错误日志

> **一句话主旨**：讲清通用查询日志的开关变量、文件位置、开启归档流程，以及错误日志的路径参数、排查优先级与重新生成的正确顺序。

### 2.1 通用查询日志的开关与文件位置

* **通用查询日志（general query log）的查询语句**
    * 用 `SHOW VARIABLES LIKE 'general_log%';` 一次查出开关与文件路径两项。
    * `general_log`：通用查询日志的开关，默认值是 `OFF`，没有专门设置过就是这个状态。
    * `general_log_file`：日志写入的文件，演示环境中的值是 `/var/lib/mysql/atguigu05.log`，路径就在数据目录下。
    * > 易错点：文件名里的 `atguigu05` 不是序号，而是当前主机的 `hostname`，日志文件默认跟着主机名走。
    * > 来源: P188
* **开关状态与文件存在性的对应关系**
    * `general_log` 为 `OFF` 时，数据目录下不会有这个文件；`cd /var/lib/mysql` 后 `ll` 找不到该文件，正与开关为 `OFF` 对应。
    * 该文件是纯文本文件，可以直接打开查看。
    * 文件大小跟着写入持续变化，增长比较快；`ll` 有时显示的是上一次的旧大小，重新查看才是当前实际大小。
    * > 来源: P188

### 2.2 通用查询日志的开启、关闭与归档

* **开启与关闭的两种方式**
    * 永久方式：写在配置文件的 `[mysqld]` 段，`general_log = ON` 并可用 `general_log_file` 指定记录路径；关闭则改成 `OFF` 或把这一行注释掉；重启之后依然有效。
    * 临时方式：登录 MySQL 后执行 `SET GLOBAL general_log = ON;`，关闭执行 `SET GLOBAL general_log = OFF;`；立即生效，重启后失效。
    * 把日志关掉的这个动作本身仍会被写进通用查询日志，关掉之后再做查询就不再记录了。
    * > 来源: P188
* **归档与重新生成**
    * 归档用改名方式：在日志文件所在目录下执行 `mv atguigu05.log atguigu05.log.old`，旧日志即被留档。
    * 重建用 `mysqladmin -u root -p flush logs`，让服务器重新生成一个新的通用查询日志文件。
    * > 易错点：`flush logs` 不会在日志关闭的状态下凭空生成新的通用查询日志文件；必须保证 `general_log` 是 `ON`，刷新才会生成新文件。
    * > 来源: P188
* **记录形态与时间戳**
    * 连接、断开及各自时间，`select database()`、`show databases`、`show tables` 之类的操作（有些是执行相关语句时服务器后台自己要做的动作）都会一并记录。
    * > 提示：日志里的时间戳不是东八区的本地时间，要往后加 8 小时才是本地时间——日志里显示「下午一点多」，对应的实际时间是晚上九点多。
    * 实际记录中能看到当天列出的表、查询用的语句、删除的条件。
    * > 来源: P188
* **成本与使用建议**
    * 特点同时是「最完整」与「最臃肿」两个：它不做筛选，凡是经过服务器的语句和连接动作都按时间顺序写进去。
    * > 结论：通用查询日志记录最全，代价也最大；日常一般考虑把它关掉，需要排查问题时再临时打开。
    * > 来源: P188

### 2.3 错误日志的路径、查看与优先级

* **记录范围与默认路径**
    * 记录 MySQL 服务器在整个运行过程中出现的错误、警告、提示这一类信息；服务器一旦发生故障，首选就是找错误日志。
    * 查询用 `SHOW VARIABLES LIKE 'log_error%';`。
    * Linux 环境下默认文件名是 `mysqld.log`；Unix 系统（Mac 也属于 Unix）下默认文件名是 `hostname.err`，后缀不同属于平台差异。
    * 默认就是开启状态，不需要特意配置；要改位置就在配置文件里写 `log_error = /var/log/mysqld.log`。
    * > 来源: P188
* **排查时优先于通用查询日志的理由**
    * 记录的信息更直接，不用在一大堆内容里做筛选。
    * 文件更小，翻找起来轻松得多；通用查询日志信息量太大，从里面翻出要找的问题本身就很不容易。
    * 通用查询日志通常并没有开启，而错误日志默认就是开启的，想关还关不掉。
    * > 结论：排查故障的顺序是先看错误日志，再按需借助通用查询日志、慢查询日志这类信息量大但默认关闭的日志。
    * > 来源: P188
* **归档与刷新失败的补救顺序**
    * 归档方式和通用查询日志一样：删掉也行，重命名归档也行；当前不在 `/var/log` 目录下时路径要写全，如 `mv /var/log/mysqld.log /var/log/mysqld.log.old`。
    * 归档后直接执行 `mysqladmin -u root -p flush logs` 会报「无法打开这个文件」；必须在刷新之前先执行 `install` 那一步，把错误日志文件创建出来，之后的 `flush` 只是让服务器把它重新打开、呈现出来。
    * 完成后的新文件里没有任何错误信息，大小是 0。

| 版本 | 刷新日志时对错误日志文件做的事 |
| :--- | :--- |
| MySQL 5.5、5.7 以前 | 既帮我们创建新的日志文件，也把旧文件备份留存成 `old` |
| MySQL 5.5、5.7 及其以后 | 只重新打开这个文件做一次刷新，备份和创建两件事都不做 |

* > 易错点：对错误日志做「重新生成」时，中间一定不能漏掉创建文件的那一步，只发一条刷新指令是会失败的。
* > 来源: P188
* **8.0 的输出改进**
    * 针对以往信息冗余、不容易接受、找起来费劲的问题，8.0 对错误日志的输出做了改变，内容短小精悍，更容易找到需要的信息。
    * > 结论：错误日志默认就开着，平时用不着特意打开；真正出现异常信息时首选查看错误日志。
    * > 来源: P188

## 3. 二进制日志的参数与配置

> **一句话主旨**：给出 binlog 的相关系统变量、三项持久化参数的取值与含义，以及写入缓存的路径和刷盘时机参数 `sync_binlog` 的三个取值。

### 3.1 binlog 的相关系统变量

* **`log_bin`、`sql_log_bin` 与文件路径变量**
    * 查询用 `SHOW VARIABLES LIKE '%log_bin%';`——日志叫 binlog，但参数名叫 `log_bin`，前后各一个百分号匹配。
    * `log_bin`：binlog 是否开启，表示二进制日志当前处于开启状态。
    * `sql_log_bin`：是否把变更语句记入二进制文件，默认 `ON`，改成 `OFF` 就不往里记录了。
    * `log_bin_basename`：二进制日志文件的存放路径，默认在 `/var/lib/mysql` 下，名字叫 `binlog`。
    * `log_bin_index`：日志文件的索引文件，是管理一系列 binlog 文件的清单。
    * > 来源: P189
* **`log_bin_basename` 指向的是一系列文件**
    * 这个路径下看到的不是一个文件：会生成很多个 binlog 文件，后缀依次是 `000001`、`000002`、`000003` 一路递增。
    * 一个文件装不下就新建下一个，所以要为这一系列文件建索引，就是 `log_bin_index` 指向的那份清单。
    * > 来源: P189
* **`log_bin_trust_function_creators` 与主从数据一致性**
    * 创建存储函数时默认报错，提示这个值是 `OFF`，相当于不让你创建，必须改成 `ON` 才能继续。
    * 默认不信任这类函数的原因：`now()` 这类函数写进 binlog 再发到从机执行，同步存在延时，从机上的 `now()` 与主机上的 `now()` 对应的时间会有偏差，会导致主从数据不一致。
    * > 来源: P189

### 3.2 三项持久化参数的设置

* **配置文件位置与参数**
    * Linux 下配置文件是 `/etc/my.cnf`（Windows 下是 `ini`），参数写在 `[mysqld]` 标签下。
    ```ini
      [mysqld]
      log-bin=atguigu-bin
      binlog_expire_logs_seconds=600
      max_binlog_size=300M
    ```
    * `log-bin`：设定文件前缀，写成 `atguigu-bin` 后生成的就是 `atguigu-bin.000001`、`atguigu-bin.000002` 依次往后。
    * `binlog_expire_logs_seconds`：二进制日志文件能够保存的时间，单位是秒；写 `600` 就是 10 分钟；默认是 30 天，另有 4 小时这样的取值场景；作用是用不到的日志到这个时间就做一次清除。
    * `max_binlog_size`：日志文件的上限大小，默认是 1GB，最大值也是 1GB；改成 `300M` 后超过这个大小就自动再生成一个新文件，序号加一。
    * 改完执行 `systemctl restart mysqld` 重启服务器。
    * > 来源: P189
* **单个文件为什么会突破 1GB**
    * > 易错点：`max_binlog_size` 是「写完一个事务再看是否超限」的软边界，不是硬性截断线；一个长事务在同一个 binlog 文件里是完整保留的，实际文件大小可以突破这个上限。
    * 逻辑是：事务执行到一半恰好达到 1GB，剩下的操作仍维护在同一个 binlog 文件里，等这个事务彻底写完，下一个事务才去新建文件。
    * > 来源: P189, P190
* **临时方式与 `sql_log_bin` 的作用域**
    * 临时修改主要用在改路径或改是否支持写入这类场景，例如 `SET sql_log_bin = 0;` 相当于关掉写入。
    * > 提示：`sql_log_bin` 的作用域是会话级的，`SET global sql_log_bin` 会被直接拒绝，只能写 `SET session sql_log_bin = 0;`；做完导入之类不想进 binlog 的操作后，记得把当前会话改回 `1`。
    * > 来源: P189
* **日志文件的生成规律与存放建议**
    * MySQL 服务器每重启一次，都会新创建一个 binlog 文件，所以重启次数多了会出现若干「刚建出来、还没写什么东西」的小文件——刚建出来的文件大小是 156 字节。
    * 默认这些 binlog 文件都放在数据目录下，用 `cd /var/lib/mysql` 加 `ll` 就能看到一系列 `binlog.000001`。
    * 数据库文件最好不要和二进制日志文件放在同一个磁盘上：放一个路径下一旦坏了，想用它来恢复也恢复不了。
    * 要换到别的路径需要创建新的文件目录，这个目录需要用 `mysql` 用户来创建，再在持久化配置里指定新位置；建议直接设成持久化的。
    * > 来源: P189

### 3.3 写入时机与 binlog cache

* **两级缓冲的写入路径**
    * > 定义：`binlog cache` 是每个事务（每个线程）私有的内存缓存，事务执行期间产生的 binlog 事件先写到这里；它和全局的 `redo log buffer` 不是一回事。
    * 事务执行过程中的增删改或 DDL 等更改性语句，先缓存到对应线程的 `binlog cache`。
    * 提交时先 `write` 到操作系统的文件系统缓存（page cache），再由 `sync_binlog` 决定的时机 `fsync` 到磁盘上的 binlog 文件。
    ```text
      事务执行中的增删改 / DDL
              |
              v
      binlog cache（每个事务/线程各自的缓存）
              | write()
              v
      page cache（文件系统缓存）
              | fsync，时机由 sync_binlog 控制
              v
      磁盘上的 binlog 文件
    ```
    * > 来源: P190
* **大事务与文件切换**
    * 事务中写 binlog 写到一半文件满了，这个事务剩下的语句仍然必须继续写进这个文件，即使会超出 `max_binlog_size` 设定的大小。
    * 目的是保证一个事务在 binlog 里的记录是完整的，从机重放时不会读到一个「一半的事务」；这条要求在恢复和主从复制里都是底线。
    * > 来源: P190

### 3.4 刷盘参数 sync_binlog 的三个取值

* 查询用 `SHOW VARIABLES LIKE 'sync_binlog';`，默认值是 `0`。
* 取 `0` 时，每次事务提交只把 cache 里的数据 `write` 到操作系统层面的文件系统缓存，什么时候真正刷新到磁盘由操作系统决定。

| 取值 | 每次提交时的行为 | 安全性 | 性能 |
| :--- | :--- | :--- | :--- |
| `0`（默认） | 只 `write` 到页缓存，刷盘时机交给操作系统 | 操作系统宕机可能丢已提交事务 | 最好 |
| `1` | 每次提交事务都执行刷盘 | 最安全 | 最差，交互频繁 |
| `N`（`N > 1`） | 每次提交都 `write`，攒够 `N` 个事务才刷一次盘 | 一旦宕机，最近这 `N` 个事务可能全丢 | 介于两者之间，减少 IO 次数 |

* 取 `0` 时的风险要分三种挂法看：事务还没提交时 MySQL 服务器挂了不用担心；事务已经提交、MySQL 服务器挂了也不用担心，因为只要事务提交就能保证内存里的 binlog 记录已经放到文件系统缓存中；操作系统挂了就有问题，已提交事务对应的更改语句没有被记录下来，做系统恢复时这部分数据会丢失，文件不全。
* `N > 1` 的折中思路与 redo log 讲过的参数 `2` 一致：攒一批再刷，减少 IO 次数，真有 IO 瓶颈时可以把值改大一点。
* 但这个数越大风险越高：设成 `1000` 就是攒够 1000 个事务才刷一次盘，这 1000 个事务此刻都已提交，操作系统这时候宕机，这些更新操作就全都没有记录下来。
* > 来源: P190

## 4. 二进制日志的查看、恢复与删除

> **一句话主旨**：给出查看 binlog 的工具与参数、事件与 position 的对应关系、按 position 与按时间两条恢复路线的完整命令，以及三种删除方式。

### 4.1 查看工具与伪 SQL

* **`mysqlbinlog` 的基本用法**
    * 命令后面跟双引号包起来的完整文件路径：`mysqlbinlog "/var/lib/mysql/atguigu-bin.000002"`。
    * > 易错点：路径里的斜线一定别丢；文件要选最新的那个，最新的是 `000003` 就得用 `000003`。
    * 直接执行看不到 SQL 的内容，呈现形式里那些变更语句所在的位置看不出来。
    * > 来源: P189
* **加 `-v` 参数看伪 SQL**
    * `mysqlbinlog -v "/var/lib/mysql/atguigu-bin.000002"` 之后能看到 `insert` 往表里添加的记录（id 18、name Jerry、class 四班对应第一、二、三个字段），以及把 id 为 17 的记录从 `Tom` 改成 `Tom1` 的 `update`。
    * 这种呈现可以理解成伪 SQL；不想让它呈现原来那些看不懂的记录信息，可以在 `-v` 后面再加一个指令把它隐掉。
    * > 来源: P189
* **`SHOW BINLOG EVENTS` 的语法**
    ```sql
      SHOW BINLOG EVENTS
          [IN 'log_name']
          [FROM pos]
          [LIMIT [offset,] row_count];
    ```
    * `IN`：要查看的具体 binlog 文件名；中括号表示可以不写，不写查的是最早的那个 binlog 日志。
    * `FROM`：从这个文件的哪个 position 位置开始查。
    * `LIMIT`：分页的两个参数，不写默认是 0。
    * position 是整个文件里一个一个事件各自的起始位置；`SHOW BINLOG EVENTS` 能把它清楚呈现出来，而 `mysqlbinlog` 的呈现方式看不方便。
    * > 来源: P189

### 4.2 三种记录格式的数据表现

* 用 `SHOW VARIABLES LIKE '%binlog_format%'` 查看，演示环境里查出来的默认格式是 `ROW`（行格式）；另外两种是 `STATEMENT` 和 `MIXED`。
* > 易错点：演示环境实测查出的默认值是 `ROW`，而配置参数的讲解里标注的默认格式是 `statement`；两处取值说法不同，以自己环境的实际查询结果为准。

| 格式 | 记录内容 | 举例说明 |
| :--- | :--- | :--- |
| `STATEMENT` | 记录每一个有变更的 SQL | 一条 `update` 只记录这一条语句 |
| `ROW` | 记录行的实际变更结果 | 一条 `update` 改了 10 条记录，就记录这 10 条改成了什么 |
| `MIXED` | 前两者的结合方式 | 由 MySQL 根据语句情况自行选择 |

* 三个格式各有优缺点，正因为各有优缺点才有了把两者结合起来的 `MIXED`。
* > 易错点：查询不会被记录进 binlog，写查询可以顺手做一下方便观察调整，但别指望它出现在日志里。
* > 来源: P189

### 4.3 按 position 恢复

* **恢复前的现场处理**
    * 读这个文件里的内容去执行，执行本身又相当于对表做修改，等于一边用这个文件一边往这个文件里写，所以先执行 `FLUSH LOGS;` 切出一个新文件，让恢复行为产生的增删改记录到新文件里。
    * 前面演示的 `delete`、`update` 没设置过 `autocommit = false`，也没写过 `BEGIN`，相当于各自都是独立提交的行为，想回滚都没有办法。
    * > 来源: P189
* **定位区间的两条规矩**
    * > 易错点：边界不能用 `XID` 这一行的数，要顺着 `XID` 往上找最近的那个 `BEGIN`，用它对应的位置作为起点；结束位置取下一个事件组的 `BEGIN` 那一行。
    * 演示中的定位结果：起点是这一组三个事件里第一个 `BEGIN` 对应的位置 884，终点是下一组事件的 `BEGIN` 所在行 1729。
    * position 是密密麻麻的，可以借 `XID` 挨着这一点往上找：插入的三条操作挨着，生成的 `XID` 也是挨着的（35、36、37），以此对应到目标事件组。
    * > 提示：一次只能圈一组连续事件，所以三件事就分三次执行；区间边界宁可从 `BEGIN` 这一行起算，也不要从 `XID` 起算。
    * > 来源: P189
* **执行恢复的命令与三组区间**
    ```bash
      mysqlbinlog \
        --start-position=884 \
        --stop-position=1729 \
        --database=atguigu_db3 \
        "/var/lib/mysql/atguigu-bin/atguigu-bin.000002" \
        | mysql -u root -p -v atguigu_db3
    ```
    * `--start-position` 是开始的位置，`--stop-position` 是结束的位置，`--database` 是库名，后面是日志文件的完整路径，管道后半段是登录 MySQL 并把语句执行到目标库。
    * 第二组恢复删除：`--start-position=1808`、`--stop-position=2037`；第三组恢复修改：`--start-position=2116`、`--stop-position=2369`。
    * > 来源: P189
* **两种恢复策略的配套工具**

| 恢复策略 | 使用的查看工具 | 定位依据 |
| :--- | :--- | :--- |
| 按 position 恢复 | `SHOW BINLOG EVENTS` | 只有它能把 position 清楚地呈现出来 |
| 按时间恢复 | `mysqlbinlog` | 它里面记录了 `timestamp`，`SHOW BINLOG EVENTS` 里并没有很好地记录时间 |

* > **结论**：以全量备份作为底子，再叠加二进制日志里的增量信息，就能完成数据库的无损失恢复。
* > 来源: P189, P190

### 4.4 按时间恢复

* **时间参数的写法**
    ```bash
      mysqlbinlog \
        --start-datetime="2024-01-01 12:00:00" \
        --stop-datetime="2024-01-01 12:10:00" \
        --database=atguigu_db3 \
        "/var/lib/mysql/atguigu-bin/atguigu-bin.000002" \
        | mysql -u root -p -v atguigu_db3
    ```
    * 时间参数就是 `--start-datetime` 和 `--stop-datetime`，格式是年月日时分秒。
    * > 来源: P189
* **时间的来源与短事件的处理**
    * 时间来自 `mysqlbinlog -v` 的输出：每个事件上面都有一个 `timestamp`，以时间戳方式表示，对应当前这个事件发生的时间，写参数时得把它折算成 datetime 形式。
    * > 易错点：如果一个事件在一秒钟之内就完成了，起止时间很可能被写成同一个值；比如这个事件在 22 秒内写完、下一个事件是 25 秒开始的，那止的时间就可以写 24 秒，只要落在开始之前就行，这样不会把相邻事件误圈进来或者漏掉。
    * > 来源: P189

### 4.5 binlog 的三种删除方式

* **按文件名删除 `PURGE MASTER LOGS TO`**
    * 完整写法是 `PURGE MASTER LOGS`，按文件名删靠的是后缀数字依次递增这一天然性质：报出一个文件名，它前面那些就都不要了。
    * 例如 `PURGE MASTER LOGS TO 'binlog.000003';` 之后，`000003` 之前的文件就被清掉了。
    * > 易错点：这里的 `TO` 是保留边界，不是删除边界；写 `TO 'binlog.000003'` 的意思是 `000003` 之前的都不要、但 `000003` 本身留着，所以这条指令在任何时候都不会把当前正在写的那一个日志文件删掉。
    * > 来源: P190
* **按时间删除 `PURGE MASTER LOGS BEFORE`**
    * 指令是 `PURGE MASTER LOGS BEFORE`，注意不是 `TO` 而是 `before`，后面跟一个时间点，这个时间之前的日志就都干掉了，例如 `PURGE MASTER LOGS BEFORE '2024-05-01 00:00:00';`。
    * 麻烦之处是先要知道各个文件分别对应到什么时间；默认的列表里不显示时间，要先用 `mysqlbinlog --no-defaults binlog.000003` 把文件的时间读出来。
    * 两种方式都行：实际操作里按文件名指定更直观，按时间删适合按保留周期做清理。
    * > 来源: P190
* **全删 `RESET MASTER` 与风险**
    * `RESET MASTER;` 既不用指定文件名也不用指定时间，因为它把日志全清了。
    * > 结论：`RESET MASTER` 不只是删文件，它把整套二进制日志清空、序列重新从 `000001` 开始，恢复数据这条路就此断掉；清完之后新日志文件默认初始大小是 156 字节。
    * > 易错点：删除二进制日志和「删库跑路」是配套的——误删数据库或许还能被原谅，连恢复的日志都清了，性质就完全变了；开发中根本不会这么用。
    * > 来源: P190
* **binlog 恢复的边界**
    * 数据量更大、库和表更多的时候，靠二进制日志恢复是一份细活，得一点一点盯着看，挑战很大。
    * 主从复制在这个位置上更省心：不让自己去读二进制日志，直接让从机去读，从机读到之后生成中继日志，再利用中继日志在从库上完成数据同步。
    * > 来源: P190

## 5. 两阶段提交与两种日志分工

> **一句话主旨**：对比 redo log 与 binlog 的日志类型和主要功能，说明两阶段提交的三个动作如何在崩溃恢复时保证主机与从机的数据一致。

### 5.1 redo log 与 binlog 的两条差别

* **日志类型不同**
    * redo log 是物理日志：记的是物理磁盘上某个数据页的某个偏移量、某个位置、某个字节被做了什么修改。
    * undo log 和 binlog 都属于逻辑日志：记录「给 ID 是几的那条数据、某个字段的值增加多少、减少多少、改成多少」，形式上和具体写的 SQL 语句很像。
    * > 来源: P190
* **主要功能不同**
    * binlog 主要用来恢复数据，以及实现主从复制、在集群当中保证数据一致性——主从之间靠 binlog 做复制和同步。
    * redo log 是为了保证事务提交时具备持久性：事务一旦提交，数据要能持久保存下来，由此获得崩溃恢复的能力。
    * > 易错点：redo 日志服务于事务的持久化，binlog 记录的是所有更改数据的语句，两者都跟「数据变化」有关，但所处的层次和面向的场景不同。
    * > 结论：一个管「重放与同步」，一个管「提交即持久」；两者侧重点不同，但在同一个事务里必须同时成立。
    * > 来源: P187, P190

### 5.2 时机不一致导致的主备数据不一致

* 一个事务里做一次更新，这次更新既会记录到 redo log，也会体现在 binlog 里，但写入时机不一样：redo log 在事务执行过程中可以不断写入，binlog 一般要等到提交的时候才写入。
* 以 `UPDATE t SET c = 1 WHERE id = 2;` 为例：数据已经记录到 redo log 里、还没及时同步到 binlog 文件中，这时候数据库服务器出现异常。
* 主机上既然已经写进 redo log，事务相当于持久化了，做恢复时 `c` 的值就是更新后的 `1`；备机参照的是 binlog，binlog 里没有把 `c` 改成 1 这件事记下来，从机读出来还是 `0`。
```text
  主机：redo log 已写入 ──► c = 1（已提交，恢复后为 1）
  binlog 未写入     ──► 从机重放后仍为 c = 0
                            |
                            v
                   主备数据不一致
    ```
* > 来源: P190

### 5.3 两阶段提交的三个动作

* 解决思路是在写入 binlog 的前和后分别加一次 redo log 的写入，但 redo log 实际只写一次——等价于把 redo log 的写入行为拆成两个阶段。
* 写在 binlog 之前的阶段叫准备阶段（prepare），写在 binlog 之后的阶段叫提交阶段（commit），用它俩把 binlog 的写入夹在中间。
```text
  ① redo log 写入，状态 prepare
            |
            v
  ② 写 binlog（记录本次更改）
            |
            v
  ③ redo log 提交，状态 commit
    ```
* 实操上就是先有一个 prepare 阶段的记录，然后 binlog 这边也做记录，binlog 记录完成之后再执行一次提交。
* > 来源: P190

### 5.4 崩溃恢复时的判断规则

```text
  服务器异常重启
      |
      v
  redo log 是否为 prepare？
      |
      ├── 否 ──► 事务未走到两阶段中的第一阶段，回滚
      |
      └── 是
           |
           v
      binlog 是否写入成功？
           |
           ├── 否 ──► 回滚（主机 c 从 1 回到 0，与从机一致）
           |
           └── 是 ──► 提交事务（主机与从机 c 都为 1）
    ```
* prepare 已执行、binlog 没写成功：虽然 redo log 里已经有了，但为了让备机和从机的数据跟主机一致，要把主机上这条已经执行的 redo log 回滚掉，`c` 又回到 `0`。
* binlog 已经写进去（判断为 YES），那就提交事务。
* WAL 原则的体现：redo 里都没有记录，就违背了预写式日志（write-ahead logging，WAL）的原则——日志都没写下去，整个操作更不会落到磁盘上。
* > 提示：这套机制的全部意义就是让「主机按 redo log 恢复出来的结果」和「从机按 binlog 重放出来的结果」必然相同；两阶段提交牺牲的是一次额外的 redo log 写入，换来的是主备之间不会出现一个 1、一个 0 的裂缝。
* > 来源: P190, P194

## 6. 中继日志与主从复制原理

> **一句话主旨**：界定中继日志的位置与文件组织，给出主从复制的三个作用、三个线程分工、三个步骤与三条约束原则，以及复制延时造成的不一致。

### 6.1 中继日志的定义与文件组织

* **中继日志（relay log）**
    * > 定义：中继日志只存在于主从架构中的从服务器上，是从服务器从主服务器读取 `binlog` 之后写到自己磁盘上的本地日志文件，作用是完成主从服务器的数据同步，达到主从数据的一致性。
    * 从服务器通过网络去读主服务器上的 `binlog`，把数据读过来存在自己磁盘上的一个本地文件里，这个文件就是中继日志；有的地方也叫中转日志。
    * 数据流向：主服务器把增删改与 DDL 记进 `binlog`，从服务器通过网络读走并落到 `relay log`，再从中继日志里把事件应用到本地表上。
    ```text
      主服务器 master                            从服务器 slave
      ───────────────                            ───────────────
      业务表                                       业务表
        │ 增删改 / DDL                              ▲ 应用事件
        ▼                                           │
      binlog（二进制日志） ──── 网络读取 ────▶  relay log（中继日志）
    ```
    * > 来源: P191
* **文件位置、序号与查看方式**
    * 中继日志默认放在从服务器的数据目录下；在从服务器上它也会出现序号 `000001`、`000002`，也会提供一个 `index` 文件作为这些中继日志的索引文件。
    * 格式跟二进制日志一样，查看同样得借助工具，比如 `mysqlbinlog`，能看到是哪个数据库的什么表、哪一行的数据、这一块要干什么事。
    * > 提示：二进制日志建议不要放在数据目录下，原因是数据库表如果挂了、文件又放在同一个目录里，有可能跟着一起损坏，恢复的时候就没东西可用；错误日志的默认位置本来就不在数据目录下。
    * > 来源: P191
* **用中继日志恢复数据时的服务器名问题**
    * 从服务器宕机重启后要从日志里恢复数据；如果这次宕机比较严重、重装了一下系统，再借助中继日志做数据恢复就可能出问题——恢复完发现数据并没有达到一致，或者一读这个文件就冒出一堆异常信息。
    * > 易错点：中继日志里记录了从服务器的名字，新装系统的名字跟原来的不一样，写入的时候就会有问题，表现出来却是恢复失败或者读出大量异常，于是很容易被误判成文件损坏；修改办法就是把现在的服务器名改回原来的名字。
    * > 来源: P191

### 6.2 提升并发能力的思路与调优顺序

* **缓存架构的作用**
    * 请求过来先判断数据是不是已经缓存在 Redis 里，是就直接返回；不是就再查数据库，查完一方面返回给客户，另一方面保存在 Redis 中便于下次直接读内存。
    * 两个好处：数据直接从内存里找到，没有去查数据库，内存访问速度远快于持久化层磁盘；原本所有请求都要并发访问 MySQL，现在一部分请求分给了 Redis，缓和了 MySQL 的访问压力。
    * > 结论：Redis 缓存架构是 MySQL 高并发架构中一个重要的环节。
    * > 来源: P191
* **读写分离与调优维度**
    * 针对数据库的操作通常都是读多写少：增删改比较少，查询比较多。
    * 库级优化的做法是在主从复制的基础上实现读写分离，可以是一主一从的模式；集群比较多的话双主双从，这时候它们其实互为备机；再往下还可以实现分库分表。
    * > 来源: P191
* **调优手段的成本与效果排序**
    * 从成本的角度看，三角最下面那个成本最低，成本最高的是搭建一个服务器集群；从效果的角度看，反而是下面的效果更好。
    * > 结论：做调优的时候，优先考虑成本最低、效果还最好的那一层，然后再按这个顺序往上走。
    * > 提示：搭集群不是不能提，而是不能当成第一选择——先用廉价的手段，再用昂贵的架构；面试官问「用户体验差、延迟长、吞吐量差该怎么办」时，别一上来说搭个集群。
    * > 结论：一方面要知道主从复制的作用是提高并发能力，另一方面要把它放进整个数据库调优的大背景里，当成其中一个环节。
    * > 来源: P191

### 6.3 主从复制的三个作用

* **读写分离**
    * 一台机器充当写库负责写入数据（增删改、DDL），称它为 master；其它服务器充当从库叫 slave，主要负责读；写少读多，所以从机可以多一些。
    * 分散了 master 的压力：读不用 master 管，从库又可以设置多个进一步分散读的压力。
    * 减少了锁表的影响：原来多个事务访问同一台主机可能出现锁的场景，分散开以后相当于并行执行，这时候就没有锁的行为了。
    * 主要场景是写进来的数据一定要同步到从机上，而这个过程当中蕴含的问题正是——同步的时候能不能保证数据的一致性。
    * > 来源: P191
* **数据备份**
    * 主机的数据同步到从机上，从机上就有了一份，可以认为很好地实现了数据备份，而且还是一种热备份的机制。
    * > 来源: P191
* **高可用性与冗余**
    * **高可用（High Availability，HA）**
        * 数据备份实际上是一种冗余的机制，我们是通过这种冗余来换取高可用性。
        * 概念区分：主机宕机以后，剩下的机器里谁能立马顶上、充当写的功能，就称之为备机；从机则可以理解成专门负责读的。
        * 写库宕机之后立马可以切换到从服务器或者备机上，保证服务的正常运行。
        * > 来源: P191
    * 高可用性的衡量指标是全年正常可用的时间除以全年总时间。
        * $$\text{可用性} = \frac{\text{全年正常可用的时间}}{\text{全年总时间}}$$
        * 这个比例达到 99.999% 时，相当于一年里有 5.256 分钟用户访问不到后台；这里边既包含系统崩溃的时间，也包含日常维护导致的停机时间。
        * > 来源: P191

### 6.4 复制的三个线程

* 主从复制的原理一句话概括：从库从主库读取 `binlog` 进行数据的同步；具体剖析会涉及三个线程。

| 线程 | 所在服务器 | 职责 |
| :--- | :--- | :--- |
| 二进制日志转储线程（Binlog Dump Thread） | 主库 | 读取 `binlog`（加锁），把事件通过网络发送给从库，发送完释放锁 |
| I/O 线程（I/O Thread） | 从库 | 接收主库发来的数据，写出到中继日志 |
| SQL 线程（SQL Thread） | 从库 | 从中继日志读出事件并执行，更新本地表数据 |

* **二进制日志转储线程（Binlog Dump Thread）**
    * 主库上负责把数据发出去的这个线程；从机要把二进制日志文件的数据读过来，两端都得各自有一个线程——你请求我，我这块得把数据发给你。
    * > 易错点：去读 `binlog` 数据的时候会有一个加锁的操作，因为这块既要去读、还要再去写入，就会出现并发的问题；发送完之后再把锁释放掉。
    * > 来源: P191
* **I/O 线程（I/O Thread）**
    * 从机上专门来接收数据的线程，接收完紧接着就把数据写出到中继日志当中，一句话就是「读进来，写出去」。
    * > 来源: P191
* **SQL 线程（SQL Thread）**
    * 主要负责从中继日志当中把事件读进来，然后去执行，更新从机上数据库表中的数据，实现主从的同步。
    ```text
      主服务器 master                              从服务器 slave
      ────────────────────────────────────────────────────────────
      业务表                                         业务表
        │ 写入（其它线程，非复制三线程）                ▲ ③ 应用事件
        ▼                                             │
      binlog（二进制日志）                  SQL Thread（SQL 线程）
        │                                             ▲
        │ ① 读取、加锁、发送                           │
        ▼                                             │
      Binlog Dump Thread ────── 网络传输 ──────▶  I/O Thread（I/O 线程）
      （二进制日志转储线程）                          │ ② 写入
                                                     ▼
                                              relay log（中继日志）
    ```
    * 写 `binlog` 的线程跟这三个线程没有关系；要实现主从复制，`binlog` 日志必须处于开启状态。
    * 默认情况下主机上 `binlog` 日志文件里的所有事件都会发给从机；也可以通过特殊的配置让它只执行指定的事件。
    * > 来源: P191

### 6.5 复制的三个步骤与约束原则

* **复制的三个步骤**
    * 主库把数据写入二进制日志文件。
    * 从库从主库把事件拷贝到自己的中继日志。
    * 从库读取中继日志中的事件，把它应用到自己的数据库当中，完成数据同步。
    * 这三个步骤对应的就是那三个线程各自做的事。
    * > 来源: P191
* **复制的三条约束原则**
    * 每个从库只能有一个主库——从库是要从主库这里获取和同步数据的，不能整两个主库。
    * 每个从库只能有一个唯一的服务器 ID（`server-id`）；不光是它，主库也得有一个唯一的服务器 ID。
    * 每个主库可以有多个从库，也就是一主多从。
    * > 来源: P191
* **复制延时造成的主从不一致**
    * 一个 `update` 事件一 `commit` 提交就写入 `binlog`，紧接着走同步这条路同步到从库的表里边；假设从提交到最终在从库当中体现出来需要 500 毫秒（通过网络方式传过去）。
    * 假设用户做了 `update` 操作、一提交马上又做一个 `select` 查询，写是写到主库这一侧，而查询要从从库那一侧查；假设提交完之后他的查询需要 200 毫秒。
    ```text
      T + 0 ms     主库 commit，update 事件写入 binlog
      T + 0 ms     用户立刻发起 select 查询（走从库）
      T + 200 ms   从库返回查询结果 —— 此时事件还没到达从库
      T + 500 ms   事件经网络到达从库，写入 relay log 并被应用
    ```
    * 写到主库的数据 500 毫秒才能到从库，而在 200 毫秒的时候就去读了，读到的数据跟当初写的数据必然不一致。
    * 解决方向：先看看它是怎么出现的，然后尽可能做一些相关设置把时间缩短（比如从机的配置），再从具体的算法层面上去控制它，尽量保证一致性。
    * > 来源: P191

## 7. 一主一从架构的搭建

> **一句话主旨**：给出两台服务器的环境准备与克隆冲突修正、主从两端的参数配置、复制账户创建与起始位置记录，以及启动复制后的状态判定与排错项。

### 7.1 环境准备与克隆冲突

* **版本与环境要求**
    * 一主一从意味着两台 MySQL 数据库服务器：一台 `master`、一台 `slave`，放在两台不同的操作系统里，相当于开两个虚拟机。
    * 版本上尽量一致，至少都要是 `8.0` 以上；`8.0.` 后面那个小版本号不一样没关系，但千万别一个 `8.0`、一个 `5.7`，那样很可能冒出一堆版本不一致的问题。
    * 演示环境里 CentOS 7-5 装的是 `8.0`、CentOS 7-6 装的是 `5.7`，所以再克隆一个与 7-5 同源的虚拟机出来用。
    * > 来源: P192
* **克隆虚拟机与必须修改的四个位置**
    * 克隆流程：先关机 → 右键 → 管理 → 克隆 → 下一步 → 选择「从当前状态」→ 下一步 → 选「完整克隆」→ 下一步 → 起名字 → 选存放路径 → 点完成。
    * 第一处是 MAC 地址：在关机状态下点「网络适配器」双击打开，里面有个「高级」，点一下就能看到 MAC 地址，点一下让它重新生成；两台虚拟机的 MAC 地址必须不一样。
    * 第二处是主机名：先启动新克隆出来的这台，原来那台先别起（两台机器 IP 地址还是一样的，同时开会冲突）；用 `root` 登录，进到主机名那个文件改成 `07`，保存退出后 `reboot`。
    * 第三处是 IP 地址：重启完用 `root` 登录，进到网卡配置文件把 IP 改掉，至少不能跟原来那台一样，演示里设成固定 IP `192.168.1.170`。
    * 第四处是网卡配置里的 UUID：保证跟以前的不一样就行，演示里把里面的 `5` 改成 `12`；保存退出后执行 `systemctl restart network` 重启网络。
    * > 来源: P192
* **克隆带来的隐藏冲突：MySQL Server 的 UUID**
    * 克隆出来的这台虚拟机跟原来那台，MySQL Server 的 UUID 也是一样的；在从机上执行 `SHOW SLAVE STATUS` 时直接报了一个错误，原因就是进行主从复制时这些 UUID 必须是不同的。
    * > 易错点：克隆时改过的 UUID 是网卡配置里的 UUID，报错说的是 MySQL Server 自己的 UUID，两者不是一回事。
    * 改法：在对应的配置文件里把这个值换掉（演示里改成 `1`），保存退出后执行 `systemctl restart mysqld`。
    * 克隆机上的 MySQL 及原有数据可以直接拿来用：`mysql --version` 查看版本，登录后 `SHOW DATABASES;`、`USE db3;`、`SHOW TABLES;`、`SELECT * FROM student;` 都能看到 7-5 里的库表与原有数据。
    * > 来源: P192
* **读写分离的落点**
    * 搭建完成之后实现的是主从复制：在主机上做的增删改操作，在从机上做查询的时候也能看到同样的效果。
    * 请求分开的两条路子：走数据库中间件（如 MySQL 的中间件 `Mycat`，中间件不止 Mycat 一种，通过它不光能做读写分离，还能做分库分表这类功能）；或者从程序的角度自己区分写请求还是读请求。
    ```text
                      ┌──────────────┐
      用户请求 ──────► │ Mycat 等中间件 │
                      └───┬──────┬───┘
               写(增删改) │      │ 读(查询)
                          ▼      ▼
                 ┌────────────┐  ┌────────────┐
                 │   master    │  │   slave    │
                 │ 7-5 / 150   │─►│ 7-7 / 170  │
                 │ atguigu05   │  │ atguigu07  │
                 └────────────┘  └────────────┘
    ```
    * > 来源: P192

### 7.2 主机与从机的参数配置

* **为什么必须用配置文件而不是临时设置**
    * 主机和从机配好信息之后就实现同步了；假如主机宕机，可以让从机（这时候它就叫备机）来充当主机。
    * 不用配置文件的话，原来的主机重启以后里面那些参数就恢复成默认设置，两台机器立刻出现同步问题。
    * 参数配在 `mysqld` 这个标签下面。
    * > 来源: P192

| 参数 | 必选/可选 | 作用与取值 |
| :--- | :--- | :--- |
| `server-id` | 必选 | 给当前主机一个 ID 值，集群内每台服务器都要有唯一 ID，便于区分；从机同样需要 |
| 启动二进制日志（binlog） | 必选 | 生成以指定前缀开头的一系列二进制日志文件，沿用上一章的目录与 `atguigu-bin` 前缀 |
| `read_only` | 可选 | `0` 是默认情况，表示可读可写，能写就表示可以做主库、主机；写成 `1` 就成为只读，只能做从机 |
| 日志文件保留时间 | 可选 | 二进制日志保留多久 |
| 日志文件大小上限 | 可选 | 单个日志文件的大小上限，默认 `1GB` |
| 不复制（不记入 binlog）的数据库 | 可选 | 针对某些库的修改操作不记录到 binlog 文件里，也就是 ignore、忽略的意思 |
| `binlog-do-db` | 可选 | 明确指出需要复制、需要记录到 binlog 的数据库，演示里设成 `atguigu_master_slave` |
| `binlog_format` | 可选 | 二进制日志的格式，配置表里标注的默认格式是 `statement` |

* **主机配置的落地**
    * 在 `/etc/my.cnf` 里改：先删掉上一章为演示 binlog 设置过的那几行，按 `i` 进入插入模式把主机这几个参数粘贴到 `[mysqld]` 下面，`ESC` 后 `:wq` 保存退出，再 `systemctl restart mysqld` 让配置生效。
    * 关于「不复制」的参数，不建议把系统默认的那些库都 ignore 掉：比如 `mysql` 这个库里相当于有很多数据字典（有哪些用户、有什么样的权限等等），最好也记录到 binlog 里去，平时就可以不去设置它。
    * > 来源: P192
* **从机配置与防火墙检查**
    * 从机这边必选的参数就是 ID，可选参数跟主机的 binlog 类似，是指定中继日志（relay log）的文件名前缀。
    * 同样在 `/etc/my.cnf` 里粘贴这两个参数，`ESC` 后 `:wq` 保存退出，再 `systemctl restart mysqld`。
    * 两端配置都改完、都重启生效以后，为了能够实现主从同步数据，一定要把防火墙关闭；用 `systemctl status firewalld` 在两台都查一遍，`firewalld` 是 `dead` 状态就没问题。
    * > 来源: P192

### 7.3 复制账户与起始位置

* **创建复制账户并授权**
    ```sql
      CREATE USER 'slave1'@'%' IDENTIFIED BY '123456';
      GRANT REPLICATION SLAVE ON *.* TO 'slave1'@'%';
      SHOW GRANTS FOR 'slave1'@'%';
      FLUSH PRIVILEGES;
    ```
    * `slave1` 是用户名，`%` 是百分号的方式；`IDENTIFIED BY` 后面是密码 `123456`。
    * `REPLICATION SLAVE` 就是主从复制的权限，这里给的是任何库下的任何表，也就是 `*.*`，这个权限是必须有的；`SHOW GRANTS FOR` 是查看权限用的，不一定非得做；最后 `FLUSH PRIVILEGES` 刷新一下权限。
    * > 注意：如果用的是 MySQL 8.0，这里一定要再多执行一条语句，把 `slave1` 这个账户的加密认证方式换掉；少了这一步，以后在从机上执行 `SHOW SLAVE STATUS` 的时候会报一个错误，错误信息里说的就是加密的那个模块出了问题。这条语句里写的密码必须跟上面创建用户时用的 `123456` 保持一致。5.7 不用执行最后这一句。
    * > 来源: P192
* **记录主机的 binlog 起始位置**
    * 执行 `SHOW MASTER STATUS;`，要用的是里面的 `File` 和 `Position` 两项：`File` 是当前的更改语句写进了哪个 binlog 文件，`Position` 是写在这个文件里的哪个位置。
    * > 结论：把从机的复制配置指向这个 `File` 和 `Position`，从机就会从这个位置开始取主机的二进制日志。
    * > 易错点：到现在为止先不要去创建 `binlog-do-db` 里指定的那个数据库——从机是从刚才记下的这个位置往下才开始跟的，前面已经有这个库了、从机这边还没有，那就麻烦了；等都配置完再去执行 `CREATE DATABASE`，这条 CREATE 语句本身也会被同步到从机上。目前主机就不要动了，一动这个位置就不准了。
    * > 来源: P192
* **从机指向主机的复制参数**
    ```sql
      CHANGE MASTER TO
        MASTER_HOST='192.168.1.150',
        MASTER_USER='slave1',
        MASTER_PASSWORD='123456',
        MASTER_LOG_FILE='atguigu-bin.000005',
        MASTER_LOG_POS=1135;
    ```
    * 参数对照：`MASTER_HOST` 是主机的 IP 地址（`192.168.1.150`）；`MASTER_USER` 是主机上刚创建的复制账户（`slave1`）；`MASTER_PASSWORD` 是该账户的密码（`123456`）；`MASTER_LOG_FILE` 是主机 binlog 的文件名（`atguigu-bin.000005`，前缀要与自己环境一致）；`MASTER_LOG_POS` 是 `SHOW MASTER STATUS` 查到的位置（`1135`）；`MASTER_PORT` 省略，端口号默认 `3306` 所以不写。
    * > 易错点：每一项都要按自己的环境值写——主机 IP、用户名、密码尤其是 binlog 文件名，你当初配置的是不是 `atguigu-bin` 开头？如果不是，千万别写成别的环境里的值。
    * > 易错点：执行时若报 `run STOP SLAVE first`，说明之前做过主从配置而且从机还开着；要重新配就必须先做一次 `STOP SLAVE`，不停掉就没法让它重新生成那些文件。
    * > 来源: P192

### 7.4 启动复制与状态判定

* **启动与重置**
    * 从机的复制参数配好就可以启动复制：`START SLAVE;`。
    * 如果前面开启过、后来又关掉了，关掉之后再 start 会报 slave 初始化中继日志失败这类信息，因为这时已经有中继日志了；办法是先执行 `RESET SLAVE;`——它会把之前的中继日志删掉，然后重新生成一个新的，再去 `START SLAVE` 就没问题；没有报错就不用 reset。
    * > 来源: P192
* **状态判定标准**
    * `SHOW SLAVE STATUS\G`，`\G` 是让结果竖着显示，看起来方便。
    * > 结论：看 `Slave_IO_Running` 是 `Yes`、`Slave_SQL_Running` 也是 `Yes`，两个都是 `Yes` 就成功了，主从现在保持一致的状态。
    * > 来源: P192
* **常见错误类型**
    * 网络不通；IP 地址写错了、密码写错了。
    * binlog 文件名跟自己环境里的不一致；文件找不到那就不行了。
    * MySQL 8.0 里没有执行那条改加密方式的语句，就会在 `Last_IO_Error` 这个位置把信息报出来。
    * 如果下面有一些 error，比如 `Last_Error`，或者 IO 相关的 Error，或者这里写 `Yes`、那里是 `Connecting`（连接中），它通常就会在这些位置把错误信息报出来，按错误信息去排错。
    * > 来源: P192
* **同步效果验证**
    * 主机上 `CREATE DATABASE atguigu_master_slave;` 之后，从机 `SHOW DATABASES` 里已经有这个库（库名就是主机 `binlog-do-db` 里指定的那个），`SHOW TABLES` 则什么也没有。
    * 主机建表并插数据：表里一个 `id`（`INT` 类型）、一个 `name`（`VARCHAR` 类型，长度 `15`）；第二条数据的值写成 `@@hostname` 这个系统变量。
    ```sql
      CREATE TABLE student(
        id INT,
        name VARCHAR(15)
      );
      INSERT INTO student(id, name) VALUES (1, 'Tom');
      INSERT INTO student(id, name) VALUES (2, @@hostname);
    ```
    * 从机 `SHOW TABLES` 里 `student` 表已经有了，两端 `SELECT * FROM student;` 都出现两条数据，主从复制、同步就实现了。
    * > 提示：`@@hostname` 是在语句实际执行的那台机器上求值的——`statement` 格式的 binlog 记录的是语句本身，从机重放同一条语句时 `@@hostname` 取到的是从机自己的主机名，所以从机存下 `atguigu07`，主机自己执行时取到的是 `atguigu05`。
    * > 来源: P192
* **停止、重启与重置**
    * 这些语句都在从机上执行：`STOP SLAVE;` 把复制停掉，`START SLAVE;` 再开启，之后再 `SHOW SLAVE STATUS\G` 看一眼，两个状态标志还是 `Yes`。
    * 如果重置的时候出现问题，可以考虑再加一条 `RESET SLAVE`——它清除的是中继日志；特殊情况下还可以再让它重新做一个重置：`RESET MASTER;`。
    * > 来源: P192

## 8. binlog_format 与数据一致性

> **一句话主旨**：对比三种 binlog 记录格式的记录方式与优缺点，并按一致性从弱到强给出异步复制、半同步复制与组复制的返回时机和取舍。

### 8.1 三种格式的记录方式

* **STATEMENT 格式（SBR）**
    * > 定义：`Statement` 格式在 binlog 中保存的是造成数据更改的 SQL 语句本身，从机拿到这些语句后自己再执行一遍。
    * 也叫 **SBR**（Statement-Based Replication，基于语句的复制）；binlog 里记录的都是更改数据表的 SQL 语句——增删改，也包括 DDL。
    * `Statement` 是一种默认格式，不去设置它默认用的就是它。
    * > 来源: P193
* **ROW 格式（RBR）**
    * > 定义：`Row` 是基于行的格式，简称 **RBR**（Row-Based Replication，基于行的复制），记录的是真正针对哪条记录做了修改，记下来的是一条一条被修改的数据。
    * 例如 `UPDATE t_account SET balance = balance - 100 WHERE status = 1;` 假设影响 100 条记录：`Statement` 格式只记录这一条 SQL 语句，`Row` 模式把这 100 条记录的修改行为一个一个地记录下来，记录的信息量显然更大。
    * 批量添加同理：`INSERT INTO t_target (id, name) SELECT id, name FROM t_source;` 用 SBR 只记录这一条 SQL 语句，用 `Row` 模式从另一张表导过来 100 条记录就会记录这 100 条插入数据的操作。
    * > 来源: P193
* **主从复制中的两条数据通道**
    ```text
              主库（主机 atguigu06）                        从库（从机 atguigu07）
         ┌──────────────────────────┐                ┌──────────────────────────┐
         │ 执行 UPDATE / INSERT ...  │                │      SQL 线程 / 回放线程   │
         └────────────┬─────────────┘                └────────────▲─────────────┘
                      │ 写事务                                     │ 读事件并执行
                      ▼                                            │
         ┌──────────────────────────┐   binlog 传输   ┌────────────┴─────────────┐
         │  binlog：按 binlog_format │ ──────────────► │  relay log（中继日志）     │
         │  记 SQL 语句 或 记行数据   │                 │  内容与 binlog 同构        │
         └──────────────────────────┘                └──────────────────────────┘
    ```
    * binlog 是主机侧唯一的复制出口，它里面到底装 SQL 语句还是装行数据就由 `binlog_format` 决定；从机只管把收到的事件照着执行。
    * > 易错点：这两种格式最本质的分歧在于——语句复制传递的是「怎么算」，行复制传递的是「算出来是什么」；凡是计算结果依赖执行它的那台机器或那个时刻的，语句复制就必然跑偏。
    * > 来源: P193

### 8.2 STATEMENT 格式的优缺点

* **主要优点**
    * 不需要记录每一行的变化：光记录 SQL 语句，减少了 binlog 的日志量，文件较小。
    * 包含了所有数据库更改的信息，可以据此审核数据库的安全等情况。
    * 可以实时还原，而不仅仅是用于复制；用 binlog 做数据恢复时关注的正是一个一个的 SQL，对应的就是 `Statement` 这种格式。
    * 主从版本不一致也没关系：从机执行的都是主机执行过的那些 SQL，从机版本高一些的话向下兼容是可以的。
    * 历史悠久、技术成熟。
    * > 来源: P193
* **主要缺点**
    * 不是所有的 `update` 语句都可以被复制，尤其是包含不确定性操作的语句：比如 `UUID()` 主机和从机取到的肯定是不同的随机值；再比如 `USER()`、`hostname`、`NOW()`、`SYSDATE()` 都是这种情况——这正是创建存储函数时说的「不被信任」的原因。
    * 会产生更多的行级锁：比如 `insert` 之后又 `select` 了另外一张表，那么针对那张表也会做相关数据的锁定；而用 `Row` 模式只管往当前那张表里面插入就完了。
    * `update` 时需要全表扫描、锁也比 RBR 更多：假设表没有使用索引就要全表扫描，要修改第 100 条记录就从第一条往下走，因为没走索引，前边的 99 条也会被锁定——扫描了多少行就要对多少行加锁，而且 `update` 加的还是 X 锁（排他锁）；换成 `Row` 模式就只锁真正修改的这条记录。
    * 针对 `auto_increment` 字段有自增锁问题：这个字段上面有一个对应的表级锁——自增锁，所以这条 `insert` 语句会阻塞其他的 `insert` 语句。
    * 复杂语句在从服务器上消耗的资源比较严重：SQL 语句写得巨长而只做一件特别小的事，`Row` 模式里就是一件事，语句复制这边还记着一堆；语句里再有各种嵌套，复杂度更高、消耗的资源更多。
    * 数据表必须几乎和主服务器保持一致，否则就会出错：这条 SQL 是放到从机上去执行的，只要表结构有些不同，SQL 很容易就报错。
    * > 来源: P193

### 8.3 ROW 格式的优缺点

* **主要优点**
    * 安全可靠：记录的是实际发生的行变更，不依赖从机的执行环境。
    * 多数情况下，从服务器上的表如果有主键，复制会很快——因为有主键，定位就是自增的方式，一路就下去了。
    * 需要更少的锁，这正是 `Statement` 缺点的另一面。
    * 明确知道你做了哪些操作，多线程复制成为可能；而语句复制那边 SQL 本身有先后顺序，就不能多线程，只能按串行方式执行。
    * > 来源: P193
* **主要缺点**
    * 文件太大了：每一条被修改的记录都要落到 binlog 里，日志量比语句复制大得多。
    * 复杂回滚时 binlog 会包含大量数据，这个更麻烦：语句复制要回滚，加一条 `rollback` 记录传过去就行；行复制上面刚记录了做了哪些事，后面要回滚还得把这些事反着再来一遍。
    * 主服务器执行 `update` 时发生的变化要逐条写进去。
    * > 来源: P193
* **两种格式的横向对照**

| 对比项 | STATEMENT（SBR） | ROW（RBR） |
| :--- | :--- | :--- |
| binlog 记录内容 | 造成更改的 SQL 语句 | 每一条被修改的记录及修改后的数据 |
| 日志量与文件大小 | 小，只记语句 | 大，逐行记录 |
| 从机行级锁 | 多 | 少 |
| 无索引 update 的开销 | 全表扫描，扫到多少行锁多少行 | 只定位并锁定真正修改的记录 |
| 函数与不确定性操作 | 可能主从不一致 | 记录实际数据，结果确定 |
| 复制并行度 | 语句有先后顺序，只能串行执行 | 可多线程并行复制 |
| 表结构要求 | 相对宽松，从机版本可略高 | 要求与主表几乎一致 |
| 事后审计 | 能看到执行过哪些 SQL | 看不出用了哪些语句 |

### 8.4 MIXED 格式的自适应规则

* `Mixed` 是 MySQL 5.1 版本引入的，是前面两者的一个结合。
* 规则：一般的修改语句就用 `Statement`，因为它的容量更小；如果语句里带了函数，函数有可能导致主从记录的数据不一致，这种情况下就自动去选择 `Row` 的格式。
```text
      收到一条待写 binlog 的 SQL
                │
                ▼
      语句中是否含有不确定性函数
      （UUID / NOW / SYSDATE / USER ...）
                │
      ┌─────────┴─────────┐
      │ 否                │ 是
      ▼                   ▼
  按 STATEMENT 记录      按 ROW 记录
  （只写一条 SQL，省空间） （写行数据，保证主从一致）
    ```
* > **结论**：`Mixed` 不是第三种记录方式，而是按语句内容在 SBR 与 RBR 之间自动切换的调度策略，判断依据就是语句里有没有会导致结果不确定的函数。
* > 来源: P193

### 8.5 架构扩展：双主与多从

* **双主复制**
    * 两个节点都是 master，其中一个是当前的主库（写库），另一个是备库，它同时也是读库、从库；一个挂了备库立马顶上，顶上的这个节点重启以后原来那个就又充当备库。
    * 两个节点之间是互相做复制操作的。
    ```text
                         应用写入
                            │
                            ▼
                  ┌───────────────────┐  互相复制   ┌───────────────────┐
                  │  主库 / 写库        │ ◄────────► │  备库（备胎）/ 读库 │
                  │  master A          │            │  master B          │
                  └─────────┬─────────┘            └─────────┬─────────┘
                            │  复制                            │  复制
                            ▼                                  ▼
                  ┌───────────────────┐            ┌───────────────────┐
                  │  从库 / 读库 1      │            │  从库 / 读库 2      │
                  └───────────────────┘            └───────────────────┘
    ```
    * 读多写少的场景下从库如果只有一个，读的压力会太大，所以可以挂多个从库；再往下还可以实现分库分表。
    * > 来源: P193
* **中间件与分库分表**
    * 读写分离在实际开发当中通常都是用数据库中间件来做的；一主一从之后还可以设置多主多从。
    * 中间件这一层可以用 Mycat，也可以由程序自己判断读写。
    * > 来源: P192, P193

### 8.6 主从同步一致性的三条硬要求

* 读库和写库的数据必须最终一致。
* 写数据必须落到写库：写库把变更写进二进制日志（binlog），再由 binlog 分发到不同的读库、也就是从库上；不能整多个写库。
* 读数据必须到读库去读，但读库不一定是确定的那台机器——因为会出现角色转换，比如主从切换、主备切换；原来的读库下一刻有可能就充当写库了。
* > 易错点：这里的「读库」说的是角色，不是某台固定的机器；把它当成一个确定的 IP 去理解，主从切换之后一定会踩坑。
* 如果读和写都挤在主库上，那根本不存在一致性问题；问题恰恰出在「要分离」这件事上。
* > 来源: P194

### 8.7 异步复制

* **主库提交与从库回放的时序差**
    * 异步复制（asynchronous replication）就是默认理解的那种场景，也是默认的复制方式。
    * 主库执行完事务就提交，一提交它自己这块就算完事了，紧接着就告诉客户端「我提交完了」——返回客户端这件事由主库的一个线程来做，这个节点叫 $T_1$；从库接过 binlog 一顿执行、把主库上做过的操作原样执行一遍，这个节点叫 $T_3$。
    * 在 $T_1$ 到 $T_3$ 这个区间里，用户要是去读从库，读到的就是旧数据——不一致。
    ```text
      客户端            主库 master              从库 slave
        |                  |                          |
        |-- 提交事务 ----->|                          |
        |                  | 执行事务、写 binlog      |
        |<- 提交成功(T1) --|                          |
        |                  |-- binlog 异步推送 ------>|
        |                  |                          | 回放事务
        |                  |                          | 完成(T3)
        |-- 读请求 ---------------------------------->|
    ```
    * > 结论：异步复制的代价全部压在这段 $T_1 \sim T_3$ 的窗口上——窗口越短越安全，但只要它存在，读从库就可能读到旧数据。
    * > 来源: P194
* **主库故障与备库升级**
    * 主库把事务提交了、从库正在执行这一系列操作，偏偏这个时候主库突然挂掉；挂掉以后其中一台从库（备库）立马升级变成新的 master，可刚才那个事务在从库上并没有写成功——原主库上明明已经提交过的事务，在新的读路径上读不到了。
    * > 易错点：这里丢的不是未提交的数据，而是已经在原主库上提交成功、只是还没同步到从库的数据；站在客户端视角看，就是一件事我明明提交成功过、现在又没了。
    * > 来源: P194
* **提交与 binlog 写入的先后顺序**
    * 顺序不是画错了：一个事务先进入 redo log 的 `prepare` 阶段，`prepare` 执行完再去执行 binlog 的写入阶段，最后还有一个 redo log 的 `commit` 阶段。
    * binlog 已经写进去了，走到 redo 的 `commit` 阶段就相当于把这个事务提交了；反过来 binlog 没有写进去，这个事务就得回滚，redo 里对应的记录也不要保留。
    * > 来源: P194

### 8.8 半同步复制

* **等待至少一个从库确认**
    * 半同步复制（semi-synchronous replication）在异步的基础上加了一个「等一等」：主库写完 binlog 先不着急返回，把 binlog 通过网络传输给从库，从库执行、把变更写进去并提交。
    * 假设从库有 $n$ 个，半同步只要求至少有一个从库写入该事件、事务提交，那个从库就给主库回一个成功信息，主库收到之后才去告诉客户端当前事务结束；这里选的是执行时间最快的那个从库。
    ```text
      客户端            主库 master              从库 slave 1..n
        |                  |                          |
        |-- 提交事务 ----->|                          |
        |                  | 执行事务、写 binlog      |
        |                  |-- binlog 同步推送 ------>|
        |                  |                          | 回放事务并提交
        |                  |<-- 最快的从库返回 ack ---|
        |<- 提交成功(T1) --|                          |
        |                  |   其余从库仍在回放（此刻尚未一致）
        |-- 读请求 ---------------------------------->|
    ```
    * 它只保证到「写入成功的那个从库」为止，那些还没写完的从库事实上的确没保证；所以半同步比异步好一些。
    * > 来源: P194
* **等待从库数量参数**
    * MySQL 5.5 的时候，半同步只能保证至少一个从库写入成功；5.7 又多出一个参数 `rpl_semi_sync_master_wait_for_slave_count`，默认值是 `1`。
    * 如果有 $n$ 个从库，把值改成 $n$，那就相当于所有从库都完成事务提交之后，主库才返回给客户端说「提交成功」；这时一致性是最好的，但相应的性能会受到影响。
    ```text
      参数    rpl_semi_sync_master_wait_for_slave_count
      默认值  1                        -- 只等最快的一个从库确认（与 5.5 的行为一致）
      取值 n  n = 从库数量              -- 等全部 n 个从库确认提交之后，才返回客户端
    ```
    * > 结论：这个值越大越一致、越慢，它是「至少一个」和「全部从库」之间的一个可调刻度。
    * 实际生产里不太可能把这个参数真按从库数量去设，肯定要低于从库的实际数量；而只要你低于它，就会存在不一致的情况，所以对数据一致性要求很高的场景（比如金融领域），半同步还是差了点意思。
    * > 来源: P194

### 8.9 组复制与三种方案的取舍

* **组复制（MySQL Group Replication，MGR）**
    * 组复制推出了一种新的数据复制技术，它基于 Paxos 协议；Paxos 里涉及 Paxos 算法，作为分布式一致性算法被广泛应用，Zookeeper 里面就用到它了；组复制是在 5.7 以后出现的。
    * 纯读事务不需要组内同意，直接 commit 就可以了。
    * 读写事务有一个「组」的概念：组内至少有过半的事务提交了、大家认为可以提交，那就提交。
    * 把读写事务分摊到不同的读写事务当中，通过相应的一致性协议保证它们原子的消息和全局有序消息，也就是先保证组内的数据是一致的，然后只要能达到一半以上的人同意提交就提交。
    * > 来源: P194

| 方案 | 返回客户端的时机 | 一致性 | 并发与性能 |
| :--- | :--- | :--- | :--- |
| 异步复制 | 主库本地提交后立即返回（$T_1$） | 最弱，$T_1 \sim T_3$ 窗口内读从库读到旧数据；主库故障还可能丢已提交的事务 | 最好，主库不被从库拖累 |
| 半同步复制 | 等到至少一个（或指定数量）从库确认提交后返回 | 中等，没被选中的从库此刻仍可能落后 | 中等，多等一个确认的往返 |
| 组复制（MGR） | 组内过半事务提交即提交 | 最强，组内数据先达成一致 | 优于「全体从库同步完再返回」，一致性协议分摊到多个事务上 |

* **落地实现方式**
    * 自己实现的好处是比较自主，完全按业务需求来做，大型互联网公司可以考虑自己去做；它省掉了中间件这一层，也就减少了这一层的性能损耗，但跟业务的耦合度会比较高，相应的要投入开发与维护的成本。
    * 用中间件的好处是功能比较强大、使用比较简单，国内一些厂商也开发了相应的数据库中间件并开源出来供大家使用。
    * > 来源: P194
* **主备切换场景与遗留问题**
    * 切换主要就是把客户端的请求发到备机，由备机来充当写库，同时也就充当了读的角色；如果是一主一备再加多从的场景，那从机也得做相应的切换——它们得改成从新的主机上去读数据。
    * 切换行为分两种场景：主动切换属于主动运维（软件升级，或者主库这台机器本身就要下线了）；被动切换是主库机器掉线了或者主库出现故障，不得不被动地切。
    * > 易错点：切换本身同样会带来数据不一致——写的数据已经到了某一步，一切换又读到了前面那一步，中间那段传输到一半的数据怎么算？转到新主库以后原来的库停下来，中间传输时那些没写完的数据怎么处理、新来的数据又怎么同步过来，这些都是事。
    * > 来源: P194

## 9. 逻辑备份与恢复

> **一句话主旨**：区分物理备份与逻辑备份的速度和空间取舍，列出 mysqldump 的全部备份粒度与选项，并给出逻辑恢复的五种粒度与命令写法。

### 9.1 备份的必要性与恢复的时间缺口

* **数据丢失的两类来源**
    * 人为的：有人故意破坏，或者管理员误操作。
    * 自然情况：天灾人祸、意外的断电，还有计算机系统软硬件的故障。
    * 结果都是数据库当中的数据丢失、服务器瘫痪，而这时候主从服务器之间的同步也会跟着出问题。
    * 需要定期对数据库服务器做备份：每隔一天备份，或者每隔一周备份一次，具体结合公司自己的业务场景去定。
    * > 来源: P195
* **备份频率与恢复的两步流程**
    * 备份不是实时的：频率比较高的每隔一天做一次，比如每天夜里 3:00 做一次备份——这个时间点访问服务器的并发量比较少、业务也比较少。
    * 假设第二天中午 12:00 出现服务器瘫痪、数据丢失或者误删除的问题：先拿到前一天 3:00 的那份备份数据做一次恢复，但不要在我们现在正在运行的主机上去恢复，要先找一台备机（备库）把数据恢复到备机上。
    * 这样恢复完，数据也只是回到了前一天的夜里 3:00；3:00 到 12:00 之间的数据仍然不在备份里，这一段缺口还得再去调用前面讲过的 `binlog` 日志这类日志文件做相对应的追加恢复。
    ```text
                      前一天 03:00                    第二天 12:00
                          |                                |
                          v                                v
                  +----------------+              +----------------------+
                  |  全量备份一份   |              | 故障：瘫痪 / 误删 /  |
                  | (夜里业务空闲)  |              | 数据丢失             |
                  +----------------+              +----------------------+
                          |
                          +-- 步骤 1：在备机 / 备库上恢复 03:00 的备份
                          +-- 步骤 2：用 binlog 等日志补齐 03:00 -> 12:00 的增量
                          +-- 注意：不要在正在运行的主机上直接恢复
    ```
    * > 来源: P195

### 9.2 物理备份与逻辑备份的取舍

* **物理备份（Physical Backup）**
    * 把物理磁盘上的数据库目录备份起来，拷贝到另外的一个目录下就可以了。
    * 特点是恢复速度比较快，但是占用的空间会比较大一些；另外也可以使用第三方的工具去实现备份。
    * > 来源: P195
* **逻辑备份（Logical Backup）**
    * 使用相关工具把整个数据库的信息导出来；特点跟物理备份正好相反：恢复的速度比较慢，占用的空间比较小。
    * 常见使用的工具是 MySQL 官方提供的转储工具 `mysqldump`；实际逻辑就是把 SQL 语句做了一个备份——创建表的语句就是 `create`，表里边的数据就是一些 `insert` 的语句。
    * 恢复到慢的原因：相当于把这些语句重新再执行一遍。
    * > 来源: P195

| 对比项 | 物理备份 | 逻辑备份 |
| :--- | :--- | :--- |
| 备份对象 | 磁盘上的数据库目录 | 建表与插入数据的 SQL 语句 |
| 实现方式 | 直接拷贝目录，也可用第三方工具 | 用 `mysqldump` 这类工具导出 |
| 恢复速度 | 快 | 慢（相当于重新执行一遍 SQL） |
| 占用空间 | 大 | 小 |

* > **结论**：物理备份恢复快、占空间大，逻辑备份占空间小、恢复慢，有利有弊，用到哪一种是看场景决定的。
* > 来源: P195

### 9.3 mysqldump 的备份粒度与命令

* **备份目录与基本语法**
    * 演示用的备份目录是在数据库目录下用 `mkdir /var/lib/mysql/backup` 建的。
    * > 提示：这只是为了演示方便才放在数据库目录下；实际生产环境首先肯定不会放到当前的数据目录下（备份的跟数据库放在一起，数据库出问题可能就都出问题了），其次可能也不会备份在同一台机器上，还可能放到不同的地点、放得远一点，这样有利于容灾备份。
    * 基本语法：`mysqldump -u用户名 -h主机名 -p密码 数据库名 [表名...] > 备份文件.sql`。
    * `-u` 是用户名，`-h` 是主机名称，`-p` 是密码；`-h` 在已连上目标机器时可以省略。
    * > 提示：备份到的这个文件以 `.sql` 结尾，实际上写成 `.txt` 结尾也完全可以，因为它就是一个文本文件。
    * > 来源: P195
* **备份单个数据库**
    * 进入备份目录后执行 `mysqldump -uroot -p atguigudb3 > atguigudb3.sql`；不在这个目录下就要写绝对路径，如 `mysqldump -uroot -p atguigudb3 > /var/lib/mysql/backup/atguigudb3.sql`。
    * 查看用 `cat atguigudb3.sql`，觉得没有高亮就用 `vim atguigudb3.sql`。
    * > 来源: P195
* **备份全部数据库**
    * 用 `--all-databases`，或者用短选项 `-A`：`mysqldump -uroot -p --all-databases > all_databases.sql`。
    * 短选项就写一个大写的 A、前面一个杠；要写全称就用两个杠。相当于把当前这个数据库实例当中的所有数据库都做了一次备份。
    * 执行时会有停顿，因为所有数据库里有一些是百万级的数据；生成的文件非常大。
    * > 来源: P195
* **备份部分数据库**
    * 用 `-B`，或者把 `all` 去掉写成 `--databases`，后面写明想备份的是哪几个数据库：`mysqldump -uroot -p --databases atguigudb2 atguigudb3 > part_databases.sql`。
    * 库名之间用空格隔开；文件名要见名知意，一会儿恢复的时候才好找。
    * > 来源: P195
* **备份指定数据库下的部分表**
    * 写法是直接写数据库名，后面空格写表名：`mysqldump -uroot -p atguigudb3 account student > part_tables.sql`。
    * 中间别用逗号，直接用空格分开表名；前面几种写法都带着 `--databases`、`--all-databases` 这类参数，没有这类参数时后面跟的就是数据库名，再往后空格跟的就是表。
    * > 来源: P195
* **用 `--where` 备份单表中的部分数据**
    * 写法是数据库名、表名，然后 `--where`，过滤条件用双引号引出来：`mysqldump -uroot -p atguigudb3 student --where "id <= 15" > part_data.sql`。
    * 生成的 `part_data.sql` 里注释中带了过滤条件，`insert` 里的数据只到 15。
    * > 来源: P195
* **用 `--ignore-table` 排除指定表**
    * `mysqldump -uroot -p atguigudb3 --ignore-table=atguigudb3.student > no_student.sql`；参数后面要写清楚是哪个库下的哪张表。
    * 验证时表少可以用 `vim` 打开再用 `/student` 查找，表多可以用 `grep`：`grep student no_student.sql` 查不到说明确实不在备份里，`grep account no_student.sql` 能查到说明其他的表是有的。
    * > 来源: P195

### 9.4 结构与数据的分离选项

* **只备份表结构**
    * 用 `--no-data`（短选项 `-d`）：`mysqldump -uroot -p --no-data atguigudb3 > no_data.sql`。
    * 验证时 `grep INSERT no_data.sql` 与 `grep insert no_data.sql` 都查不到，说明确实没有数据；`grep create no_data.sql` 能查到，说明表结构是在的。
    * > 提示：`mysqldump` 生成的关键字统一是大写的，所以校验「这个备份里有没有数据」时直接按大写 `INSERT` 去搜最省事；再顺手用小写验证一次更稳妥。
    * > 来源: P195
* **只备份数据**
    * 用 `--no-create-info`（短选项 `-t`）：`mysqldump -uroot -p atguigudb3 --no-create-info > no_create.sql`。
    * 验证时搜 `insert` 是有的、搜 `create` 就没有了；这一对参数正好和前一对互补。
    * > 来源: P195
* **包含存储过程、存储函数与事件**
    * 默认情况下备份是不包括数据库当中的存储过程（Stored Procedure）、存储函数（Stored Function）和事件（Event）的。
    * `--routines` 或 `-R`：包含存储过程和存储函数；`--events` 或 `-E`：包含事件。
    * `mysqldump -uroot -p -R -E --databases atguigudb3 > func_procedure.sql`；针对单个数据库用 `--databases` 加库名，备份全部数据库就用 `--all-databases`。
    * 验证用 `grep -C 5 random_num func_procedure.sql`（`-C` 加行数会把匹配行的前后 5 行都展示出来），能查到既有函数的创建也有它使用的情况。
    * > 来源: P195

### 9.5 备份文件的结构

* **文件头与 MySQL 版本注释**
    * 最上面显示的是 `mysqldump`，指 MySQL 这个转储工具的版本号——它的版本号跟数据库本身的版本号不一定是匹配的；后面接着是数据库的版本号、所应用的平台，然后是具体的 host、database。
    * 以 `/*!` 开头、以 `*/` 结尾的内容叫 MySQL 注释，做数据恢复的时候会被 MySQL 数据库服务器读取，里面的信息就是给服务器看的；在非 MySQL 的数据库服务器上它就不识别了，这样写可以提高备份文件的可移植性。
    * 注释里的一系列编号代表的其实也是 MySQL 数据库的版本，比如 4.01.01、5.05.03；言外之意是跟在编号后面的这些信息要在该版本及以后的版本当中才可以使用。
    * > 来源: P195
* **表结构与数据的呈现形式**
    * 表在文件里以 `create` 来呈现，表数据以 `insert into` 的方式来呈现，多条数据以逗号的方式隔开在一条语句里。
    * 如果恢复的目标库里已经存在同名表，就把现有数据库下的表先干掉，再重新生成一个备份文件里边的表，之后是添加数据。
    * > 提示：这些关键字都是大写的，这是留的一个伏笔——查文件里到底有没有数据，就是靠按大写 `INSERT` 去搜。
    * 用 `Shift+G` 可以进入文件结尾，结尾还是有很多 MySQL 注释开头，最后有一个这个文件生成的时间记录。
    * > 来源: P195
* **文件头尾的用户变量与系统变量**
    * 文件头把当前系统当中的系统变量赋值给前面的用户变量，相当于做了一个临时的记录；文件尾再把这些用户变量赋回给当前的系统变量，相当于恢复成最初的这样一种状态。
    * 一头一尾这两个动作是成对出现的，目的就是恢复时不破坏服务器原有的变量设置。
    ```text
      +------------------------------------------------------+
      | HEADER : mysqldump ver / server ver / platform        |
      |          host / database                              |
      | COMMENT: /*! ... */   system vars --> user vars       |
      +------------------------------------------------------+
      | TABLE 1: create ...                                   |
      |          insert into ... (多值以逗号分隔)              |
      +------------------------------------------------------+
      | TABLE 2: create ... / insert into ...                 |
      +------------------------------------------------------+
      | TAIL   : /*! ... */   user vars --> system vars       |
      |          dump file create time                        |
      +------------------------------------------------------+
    ```
    * > 来源: P195

### 9.6 逻辑恢复的五种粒度

* **逻辑恢复的本质**
    * > 定义：逻辑备份与逻辑恢复，备份的是「重建数据所需的 SQL 语句」而不是数据文件本身；恢复就是把这份语句脚本重新执行一次，让库、表、数据按语句的描述被重新构建出来。
    * 恢复用的是官方给的那个 `mysql` 指令——它这时候的活是读取 `mysqldump` 生成的那个 SQL 文件，然后把它原样执行一遍。
    * > 来源: P196
* **恢复前的现场准备**
    * 在演示单库备份恢复单库之前，先做一个能观察的现场：`show tables;` 确认表都在，然后 `drop table student;` 把 `student` 表干掉。
    * > 易错点：`drop` 是 DDL 操作，执行即提交；这时候指望 `rollback` 把表找回来是不大靠谱的，只能走备份恢复这条路——能不能回滚不是靠记忆猜的，而是由它属于 DDL 还是 DML 决定的。
    * > 来源: P196
* **单库恢复到原库与新库**
    * 关键判断在于这份 SQL 文件里包不包含创建数据库的操作。

| 备份文件内容 | 恢复命令写法 | 说明 |
| :--- | :--- | :--- |
| 不含 `create database` | `mysql -u root -p 库名 < 文件` | 手动指定要恢复到哪个库 |
| 含 `create database` | `mysql -u root -p < 文件` | 命令里不必再写库名 |

    * 演示中的单库备份文件「一上来就是创建表，没有创建数据库的操作」，所以恢复时得手动把库名写进命令里：`mysql -u root -p{password} atguigudb3 < atguigudb3.sql`。
    * 恢复到新建的库：先 `create database atguigudb4;`，再把刚才那份备份文件里的表和数据全部搬到这个新库来，命令和前面一样、只是把库名从 3 改成 4：`mysql -u root -p{password} atguigudb4 < atguigudb3.sql`。
    * > 结论：同一份单库备份既能覆盖恢复到原库，也能整份导入到一个新库——后一种场景相当于拿一份备份复制出一个新的库环境。
    * > 来源: P196
* **全量备份的整库恢复与代价**
    * `all-databases` 那种一个文件装下所有库的备份对应的恢复行为是：在一台全新的备机上执行 `mysql` 指令，把所有的库一次性全部恢复出来——这就是昨天那一刻所有数据库的快照。
    * 演示里没做这个操作的实因是文件本身已经很大，实际生产环境只会更大，恢复起来肯定很慢。
    * > 结论：粒度越大的恢复，代价越高；判断是否值得走整库恢复，标准不是「能不能恢复」，而是「损坏的范围有多大」。
    * 只是某个库下的某张表损坏，为了这一张表去整库恢复就有点小题大做了。
    * > 来源: P196
* **从全量文件中提取并恢复单个库**
    * 场景：手里只有 `all-databases` 这个全量文件，并没有为这个库单独维护过备份文件，现在其中一个库的数据坏了。
    * 思路是从全量文件里把这个库先找出来，再单独放成一个文件：源是当天的全量备份文件 `all-databases`，目标是 `current database` 为 `atguigudb3` 的那一部分，去处是写入一个新文件 `atguigudb3_1.sql`。
    * > 提示：全量备份文件里包含 `create database` 这样的建库语句——这一点和前面那个单库备份文件正好相反，直接决定了后面恢复命令怎么写。
    * 恢复时不能再在命令里指定库名，否则就写重了：`mysql -u root -p{password} < atguigudb3_1.sql`。
    * > 易错点：恢复已有库之后，当前会话里查不到恢复结果不代表恢复失败——要恢复的库当前已经存在，会话里看到的是旧状态；先 `exit` 重新登录（至少也要切换一次库）再看，这是最容易被误判成「恢复没生效」的一步。
    ```text
        全量备份 all-databases.sql
                 |
                 |  提取 current database = atguigudb3 的部分
                 v
        atguigudb3_1.sql   （含 create database + 建表 + insert）
                 |
                 |  mysql -u root -p < atguigudb3_1.sql
                 v
        服务端重建库表并插入数据
                 |
                 |  旧会话看不到变化
                 v
        exit 退出 -> 重新登录 -> use atguigudb3 -> show tables
                 |
                 v
        account 表与 student 数据均已恢复
    ```
    * > 来源: P196
* **从单库备份中恢复单表**
    * 场景：`atguigudb3` 这个库里表特别多，有的单表就到了百万级的存储量，而现在只是其中某一张表的数据损坏了；前面几种做法本质上都是恢复整个数据库、相当于重新做一次覆盖操作。
    * > 结论：损坏范围是单表时，就用单表粒度的恢复，不要为了几条数据把整个库覆盖一遍。
    * 先 `drop table student;` 把损坏做出来——表没了意味着表结构信息和表内数据信息全部丢失，这两样要分别找回来。
    * 从库脚本 `atguigudb3_1.sql` 上按两个目标分别做一次提取，目录里就多出 `student_structure`（只含 `create` 语句，也就是表结构）和 `student_data`（只含 `insert into student` 这类语句，也就是表数据）。
    * > 提示：真正要记住的是这套拆分的思路——结构和数据分开抽、分开导，参数照着自己环境里的脚本来套。
    * 分步验证用服务端自带的 `source` 指令，在 `mysql>` 提示符下直接执行文件：先 `use atguigudb3;`，再 `source /var/lib/mysql/backup/student_structure;`——`show tables` 看到 `student` 表回来了，但 `select * from student;` 里没有数据；接着 `source /var/lib/mysql/backup/student_data;`，数据就回来了。
    * > 易错点：`source` 后面必须写文件的完整路径，不能只写文件名。
    ```text
         drop table student
                |
                v
         表结构与表数据同时丢失
                |
                +-------------------------------+
                |                               |
         student_structure                student_data
         （create 语句）                   （insert 语句）
                |                               |
                |  source .../student_structure |  source .../student_data
                v                               v
         show tables 能看到 student      select * from student 才有数据
                |                               |
                +---------------+---------------+
                                v
                       表与数据全部恢复
    ```
    * > 来源: P196
* **五种恢复粒度的对照**

| 恢复粒度 | 备份来源 | 恢复动作 | 适用判断 |
| :--- | :--- | :--- | :--- |
| 单库到单库 | 单库备份文件 | `mysql -u root -p 库名 < 单库.sql` | 原库的表被删或数据误删，直接从备份覆盖回来 |
| 单库到新库 | 同一份单库备份文件 | 先 `create database`，再导入到新库名 | 需要一份独立的库环境 |
| 全量到多个库 | `all-databases` 文件 | 在新备机上执行 `mysql -u root -p < all-databases.sql` | 昨天做过全量备份、需要整机恢复；文件大、耗时长 |
| 全量到单个库 | 从全量文件中提取出的脚本 | 提取后执行导入，再重开会话 | 手里没有该库的独立备份，只有全量文件 |
| 单库到单表 | 库脚本中抽出的结构与数据两个文件 | 用 `source` 先结构后数据 | 只有一张表损坏、库里表多且数据量大 |

## 10. 物理备份与表数据的导入导出

> **一句话主旨**：给出物理备份的适用引擎与备份窗口的一致性控制、物理恢复后的属主修复，以及表数据导出导入的三种与两种命令方式。

### 10.1 物理备份的取舍与适用引擎

* **与逻辑备份的差别**
    * 缺点：物理备份生成的文件更大一些，因为拷的就是数据文件本身，表结构、索引这些物理结构都在里面，不像逻辑备份只存 SQL 语句那么精简。
    * 优点：速度比较快、简单粗暴直接——恢复的时候把整个文件直接粘回来就行，不用再把 SQL 一条条执行一遍。
    * 备份的对象就是数据目录下面一个个库目录。

| 对比项 | 物理备份 | 逻辑备份 |
| :--- | :--- | :--- |
| 产出文件体积 | 更大 | 更小 |
| 备份与恢复速度 | 更快 | 更慢 |
| 操作方式 | 直接拷贝数据目录下的库目录 | 用 `mysqldump` 导出 SQL，再用 `mysql` 回放 |

* > 来源: P197
* **存储引擎与工具**
    * 这套「拷目录 + 回拷」的路子主要针对的都是 MyISAM 这种存储引擎（Storage Engine）对应的表，对 InnoDB 来讲是不适用的。
    * 第三方工具比如 `mysqlhotcopy` 也是同样的道理；`mysqlhotcopy` 在 5.5 之前用得比较多，到 5.7 以后就不怎么用了。
    * > 易错点：库里混着 InnoDB 的表，就不能用这种方式整体拷来拷去。
    * > 来源: P197

### 10.2 备份窗口的一致性控制

* 把开始备份的那一刻记作 T1、备份完成的那一刻记作 T2，T1 到 T2 这一段就是备份窗口；这中间要保证数据的一致性——整个备份过程当中，不要对正在备份的这个数据库做增删改。
* 两种做法：第一种是把服务停掉（谁都访问不了），这个思路成立但太暴力；第二种是不停服务，只把「修改」这条路限制住——让表带上一个读锁（Read Lock），这样查询没有问题、增删改就进不来了。
* 另外再顺手刷一下盘：`flush` 一下 `tables`，保证相应的数据该刷新到磁盘的都刷新到磁盘上，数据都落盘了再去作备份。
* 这两件事一条指令就办完了：`FLUSH TABLES WITH READ LOCK;`——`FLUSH TABLES` 是把表相关的数据刷到磁盘，`WITH READ LOCK` 是给它加上读锁；这条要在备份之前执行，执行完再开始拷文件。
```text
         T1 开始备份                          T2 备份完成
            |                                     |
            v                                     v
    --------+=====================================+-------->  时间轴
            |<--------- 备份窗口：拷贝库目录 -------->|
            |
            |  这段窗口内只允许读：
            |    SELECT                正常
            |    INSERT / UPDATE / DELETE   被读锁挡住
            |
            +-- 窗口结束后：UNLOCK TABLES 解锁
    ```
* 备份做完以后一定记得把锁解开：`UNLOCK TABLES;`。
* > 易错点：锁加上了不解，用户那边始终做不了删除、修改这类动作；备份脚本里漏了这一句，影响的不是你自己，是在线业务。
* > 来源: P197

### 10.3 物理备份与恢复的完整流程

* **准备一个 MyISAM 表的演示库**
    ```sql
      CREATE DATABASE atguigudb5;
      USE atguigudb5;
      CREATE TABLE test1 (
          id INT
      ) ENGINE = MyISAM;
      INSERT INTO test1 VALUES (1), (2), (3);
      SELECT * FROM test1;
    ```
    * 之所以不拿现有的数据库去演示：这套东西针对的是 MyISAM 存储引擎的表，而现有的库里多少都会有 InnoDB 的表，掺在一起就不合适了。
    * 建表时用 `ENGINE = MyISAM` 显式指定存储引擎，这一条是整套操作能成立的前提；插的三条数据只是标记，用来验证恢复出来的是不是原来那份。
    * > 来源: P197
* **加锁、刷新与目录拷贝**
    * 先执行 `FLUSH TABLES WITH READ LOCK;`，执行完验证两件事：查询这张表没问题，再去执行 `DELETE FROM test1` 直接被挡下来了。
    * 拷贝：`cd /var/lib/mysql` → `ll` → `cd backup` → `ll` → `cd ..` → `cp -r atguigudb5 backup/`；`-r` 表示把当前这个目录以及它下面所有的子目录一起递归复制。
    * 复制完回到 `backup` 目录 `ll` 一下确认这份目录已经在里面，然后立刻解锁 `UNLOCK TABLES;`。
    * > 来源: P197
* **删数据、删目录与回拷恢复**
    * 造损坏现场：`DELETE FROM test1;` 再 `SELECT * FROM test1;` 查询出来是空的。
    * 恢复：退回数据目录，`rm -rf atguigudb5` 把整个目录干掉，再 `ll` 确认它确实不在了；然后用 `mv` 把备份目录里的那份移回来——`cd backup` → `mv atguigudb5 ../` → `cd ..` → `ll`。
    * 文件回来了还要重启当前这台 MySQL 服务器：`systemctl restart mysqld`。
    * 重启之后回到客户端里查询 `SELECT * FROM test1;`，结果拿到的不是数据，而是一句 `Table 'test1' is read only`——表成了只读的。
    * > 来源: P197
* **重启后的表只读问题与 chown 修复**
    * 退出再登一次（`exit` 后 `mysql -uroot -p`）再查还是 `Table 'test1' is read only`，所以跟重新登录没关系，是当前这张表的权限不够，原因就在 `chown` 上。
    * MySQL 服务器在 Linux 上是拿 `mysql` 这个系统用户去跑、去访问数据文件的，另外还有一个 `root` 用户，是两回事。
    * 把原来的 `atguigudb5` 目录删了、再把备份里那份整体移过来，对系统来说现在这个目录已经不是原来那个了，它算是一个新的目录，属主和权限跟着拷过来的那份走，`mysql` 用户拿不到访问权，于是表就只剩只读了。
    * 修复：`chown -R mysql:mysql atguigudb5`——`-R` 是递归，`mysql:mysql` 是「用户:组」，最后跟的是那个库目录；粘命令时注意把目录名改成自己的库名，名字对不上这一步就白做了。
    ```text
      atguigudb5 目录（从 backup 移回来的那一份）
              |
              |  整体替换掉数据目录下的同名目录
              v
      /var/lib/mysql/atguigudb5    属主不是 mysql
              |
              |  mysqld 以 mysql 用户身份去访问表文件
              v
      Table 'test1' is read only
              |
              |  chown -R mysql:mysql atguigudb5
              v
      属主变成 mysql，表恢复正常读写
    ```
    * 改完再查一次 `SELECT * FROM test1;`，三条数据回来了。
    * > 来源: P197
* **主版本号约束**
    * 备份的那个数据库和要恢复到的这个数据库服务器，主版本号得是一样的——指的就是 `8.0` 对 `8.0`、`5.几` 对 `5.几` 这一层的号。
    * 拿 8.0 的备份去恢复到 5.几的服务器上就叫不一样；因为这个备份包里边的细节在不同大版本之间是有差异的，版本对不上，恢复的时候就会产生一些 bug 问题。
    * > 提示：`chown` 这一步不是可做可不做的，它决定了拷回来的表能不能被正常读写。
    * > 来源: P197

### 10.4 表数据导出的三种方式

* **`SELECT ... INTO OUTFILE`**
    * `SELECT` 决定你查哪些数据，查出来的就写到指定的文件里——导哪一部分数据、导多少，完全由你自己写的那条 `SELECT` 说了算。
    * 用 `SELECT @@secure_file_priv;` 查看路径参数，没提前改过的话默认值是 `/var/lib/mysql-files/` 这个目录。

| `secure_file_priv` 取值 | 含义 |
| :--- | :--- |
| 空（empty） | 可以导出到任意路径 |
| 一个具体路径 | 只能导出到该路径或它的子目录下 |
| `NULL` | 禁止导出 |

    ```sql
      SELECT *
      INTO OUTFILE '/var/lib/mysql-files/account_1.txt'
      FROM account;
    ```
    * 文件里是一条条实实在在的数据，表结构没有——这种方式只搬数据，不搬表结构。
    * > 易错点：`INTO OUTFILE` 是 SQL 语句的一部分，要在 `mysql` 客户端里执行；丢到命令行上去跑是不成立的。
    * > 来源: P197
* **`mysqldump -T` 同时导出表结构与数据**
    * 这条要在命令行里执行，不是在 `mysql` 客户端里：`mysqldump -uroot -p -T /var/lib/mysql-files atguigudb3 account`。
    * `-uroot -p` 是用户名和密码，密码回车后按提示输入；`-T` 后面跟的是导出目录，这个参数别丢了；再往后是数据库名和表名。
    * 执行完同时出来两个文件：`account.sql` 里是这张表的表结构（创建表的语句），没有表数据；`account.txt` 里是表数据。
    * 它还可以有更丰富的用法：`account.txt` 里列与列之间默认用制表符分开、字符串外面什么也不带；希望字符串用双引号引起来、不同的列之间用逗号分隔，就把相应的格式限定写进导出命令里。
    * > 提示：文件名要留意——如果第一次直接写成 `account.txt`，这次 `mysqldump` 生成的文件会把它覆盖掉，前后两个文件的效果就分不出来了。
    * 两种方式的差别说到底就是「导什么由谁决定」：`mysqldump -T` 导的是整张表的全部数据，第一种方式里有 `SELECT`，想导哪部分数据就怎么写。
    * > 来源: P197
* **`mysql` 命令导出与 `--vertical`、`--xml` 两种呈现**
    * `mysql -uroot -p atguigudb3 -e "SELECT * FROM account" > /var/lib/mysql-files/account_2.txt`；数据库名要写清楚，`-e` 后面跟要执行的 SQL，最后把命令的输出重定向到指定的文件里。
    * 这种方式同样不保存表结构，只有一个 `.txt` 文件，里面只有数据。
    * 加上 `--vertical` 后每个字段单独占一行、竖着排下来，跟命令行里敲 `\G` 看到的效果类似。
    * 把 `--vertical` 换成 `--xml` 后文件名后面带 `.xml`，里面的数据就是以 XML 格式呈现的。
    * > 来源: P197

| 方式 | 命令形态 | 是否含表结构 | 数据范围 |
| :--- | :--- | :--- | :--- |
| `SELECT ... INTO OUTFILE` | 在 `mysql` 客户端里执行 SQL | 不含 | 由 `SELECT` 决定 |
| `mysqldump -T` | 命令行工具，指定导出目录 | 含（单独一个 `.sql`） | 整张表 |
| `mysql` 命令加 `-e` | 命令行 + 输出重定向 | 不含 | 由 SQL 语句决定 |

### 10.5 表数据导入的两种方式

* **`LOAD DATA INFILE`**
    * 前提是得先有导出的文件才能导入，这里用的就是 `SELECT ... INTO OUTFILE` 生成的文件。
    * 先导出：`SELECT * INTO OUTFILE '/var/lib/mysql-files/account_0.txt' FROM account;`；再把表里的数据全删掉制造出需要导入的现场（`DELETE FROM account;`）。
    * 然后导入：`LOAD DATA INFILE '/var/lib/mysql-files/account_0.txt' INTO TABLE account;`。
    * > 易错点：这条同样得在 `mysql` 客户端里执行，别丢到命令行上去。
    * 导出的时候如果用了某种分隔符、引号之类的符号，导入的时候要跟它对应上，别一边一种写法。
    * > 来源: P197
* **`mysqlimport`**
    * 同样得先把数据导出到一个具体文件里才能导入；这次换用 `atguigudb3` 下的 `teacher` 表：`SELECT * INTO OUTFILE '/var/lib/mysql-files/teacher.txt' FROM teacher;`。
    * 导出成功后执行 `DELETE FROM teacher;` 把数据都删掉，再用 `mysqlimport -uroot -p atguigudb3 /var/lib/mysql-files/teacher.txt` 恢复。
    * 命令里只写了数据库和文件、没有写表名——`mysqlimport` 是拿文件的主文件名当表名的，所以文件名去掉扩展名之后得正好是那张表的名字。
    * > 来源: P197
* **收尾提醒**
    * 逻辑备份也好、物理备份也好，开发当中都可以根据实际的场景去作这样的操作，但一定要多演示几遍。
    * 别真到了实际生产环境里操作的时候挂掉，更别拿着正在跑业务的这个库直接上去改——那会对数据产生二次污染。
    * > 来源: P197

## 11. 数据库迁移与误删除恢复

> **一句话主旨**：界定数据库迁移与备份恢复的关系及三条注意事项，按 delete、truncate/drop、rm 三类删除给出恢复流程与预防措施，并说明延迟复制备库的价值。

### 11.1 迁移的定义、本质与注意事项

* **定义与触发场景**
    * > 定义：数据库迁移（database migration）是指把数据从一个计算机存储系统永久性地传输到另外一个计算机存储系统的过程。
    * 触发的原因包括服务器或者存储设备的更换、设备的维护和升级、灾难恢复、数据中心的迁移。
    * > 结论：迁移的本质就是备份和恢复，只是侧重点不一样——同一台服务器上把数据备份出去、出了事再恢复回这台服务器叫备份和恢复；把数据备份出去以后恢复到其他主机上就是迁移，两者实现的逻辑完全一样。
    * > 来源: P198
* **收尾的两件事与迁移方案**
    * 迁移之前要验证迁移数据的完整性——这一点备份、恢复、迁移三件事都躲不开。
    * 迁移完成、新环境跑稳之后，要退役原来那台旧的存储设备，不能新旧两套长期并存着跑。
    * 迁移方案没什么新东西：物理备份的迁移、逻辑备份的迁移。
    * > 来源: P198
* **相同主版本号之间的迁移**
    * 相同数据库版本之间的迁移问题会少一些；这里说的「相同版本」指的是主版本号一样，而不是小版本号一个数字都不差。
    * 物理备份这条路只适用于 `MyISAM` 这类存储引擎的表；`InnoDB` 的表不适合做物理备份，也就不适合做物理迁移。
    * > 易错点：别把「字节级复制数据文件」当成通用方案；`InnoDB` 表要走逻辑的方式，推荐使用 `mysqldump` 导出后再导入。
    * > 来源: P198
* **不同版本之间的迁移**
    * 从低版本往高版本迁一般都比较顺：比如从 `5.7` 迁到 `8.0`，数据库本身是向下兼容的，把低版本导出的备份文件拿到高版本的服务器上做一个恢复通常问题不大。
    * 反着来就要小心：高版本通常会修掉低版本的一些缺陷、做过一些修正，高版本导出的数据在低版本里就不一定兼容。
    * 最简单的例子：`5.7` 里默认字符集是拉丁（`latin1`），到 `8.0` 改成了 `utf8mb4`；如果对面那台 `5.7` 从来没改过字符集，而 `8.0` 库里存着中文，往 `5.7` 里一倒就报错了。
    * 跨版本往下迁的时候必须提前把低版本那边需要修正的地方处理好，再去倒数据；能尽量在相同版本之间做迁移会省掉很多事。
    * > 来源: P198
* **不同数据库之间的迁移**
    * 不同数据库之间的差别非常大：关键字不一样、SQL 语句写法也不一样；拿 Oracle 去套 MySQL 的各种优化和策略，有一部分适用，也有一部分根本不适用。
    * MySQL 和 Oracle 之间做迁移相对还算好办一点：MySQL 被 Oracle 收购已经有些年头了，两者对 SQL 的支持比较接近；虽然数据类型上仍有区别——比如 `varchar` 在 Oracle 里叫 `varchar2`——但可以把导出的 SQL 文件手工做一遍调整修改，就能实现在 Oracle 上的恢复。
    * 有些数据库之间的差别是故意造成的技术壁垒；跨数据库迁移也有现成的工具来帮忙，比如 `MyODBC`，以及 MySQL 官方提供的迁移工具。
    * > 注意：不同数据库之间的迁移，一定要有高手专门指导着做，里面的坑比较多。
    * > 来源: P198

### 11.2 传统高可用架构对误删除的失效

* 在主库上执行一个 `drop table`，这条操作很快就会通过二进制日志（binlog）传给所有的从库，连级联的从库在内，结果从库上相应的表也一起被删掉了。
```text
                    DROP TABLE 一条语句
                            |
                            v
                   +------------------+
                   |    主库 Master    |
                   +------------------+
                            |
                 binlog（statement 记录该语句）
              +-------------+-------------+
              v                           v
      +---------------+           +---------------+
      |  从库 Slave-1  |           |  从库 Slave-2  |
      |  表一并被删掉   |           |  表一并被删掉   |
      +---------------+           +---------------+
    ```
* > **结论**：主从高可用只解决「可用」，解决不了「误删」。
* 要解决这件事得先把删除操作分类，不同的问题有不同的方案：按 `delete`、`truncate`/`drop`、`rm` 这三类来谈。
* > 来源: P198

### 11.3 delete 误删的恢复与预防

* **flashback 的恢复原理与前置条件**
    * `delete` 的影响范围比较小、恢复起来也比较容易，常用的措施是拿 `flashback` 这样的工具来做数据恢复。
    * `flashback` 的主要原理其实就是修改 binlog 的内容；前提是 binlog 里记下了一条一条被删除的数据，所以格式上需要的 `binlog_format` 是 `ROW`，同时还要有 `binlog_row_image = FULL` 这个参数配合。
    * 在这个前提下把当初那些删除操作对应的指令取出来做一个反向回放：原来执行的是 `delete`，把它改成 `insert` 再加回去。
    * 如果误删除的数据涉及多个事务，那就反过来操作一遍——恢复的时候按相反的方向把每个事务的动作还原。
    ```text
      binlog 中记录的行事件              恢复时的反向回放
      +--------------------------+      +--------------------------+
      | DELETE FROM ...          | ---> | INSERT INTO ...          |
      +--------------------------+      +--------------------------+
      | UPDATE 新值              | ---> | UPDATE 改回旧值           |
      +--------------------------+      +--------------------------+
    ```
    * > 提示：这个思路和 undo 日志是一脉相承的——记录反向操作，把数据推回原样。
    * > 来源: P198
* **安全更新模式 `sql_safe_updates`**
    * 恢复只是补救，重点还是要预防：代码在上线之前必须做 SQL 审查，确认里面没有你并不想主动执行的删除行为。
    * 打开安全模式：把 `sql_safe_updates` 设置成 `ON`，设置好之后再去执行删除操作时，它就会强制要求你带上 `where` 条件。
    * 这个 `where` 条件不是随便加一个就行：条件里用到的字段必须得有索引，没有索引的话照样报错。
    * 如果确实要删全表、没有 `where` 可用，那就必须使用 `limit`；如果既不想写 `where` 也不想写 `limit`，还有一个办法——写一个一定成立的条件，比如 `where id > 0`，`id` 上有索引而且所有 `id` 都大于 0，这样既满足了安全模式的要求，也等于向自己确认了一遍：你是真的要把数据都删掉。
    ```sql
      -- 打开安全更新模式
      SET sql_safe_updates = ON;

      -- 被拒绝：既没有 WHERE 也没有 LIMIT
      DELETE FROM t;

      -- 被拒绝：WHERE 字段上没有索引
      DELETE FROM t WHERE status = 0;

      -- 通过：id 上有索引，且该条件恒真
      DELETE FROM t WHERE id > 0;
    ```
    * > 来源: P198

### 11.4 truncate 与 drop 的恢复与预防

* **这两类操作与性能提示**
    * 第二类是 `truncate` 和 `drop`，代表操作有 `truncate table`、`drop table`，以及粒度更大的 `drop database`。
    * 顺带一句性能上的区别：`delete` 是比较慢的——如果一张表的数据压根都不想要了，还用 `delete` 一行行删，它还会生成相应的回滚日志、写 redo、写 binlog；这种场景换成 `truncate`，性能会有所提升。
    * > 来源: P198
* **flashback 对这两类操作无效**
    * > 结论：`truncate` 和 `drop` 这三类操作，用 `flashback` 是恢复不回来的。
    * 原因在于这类操作在 binlog 里使用的是 `statement` 格式；`statement` 只记录你执行的语句，并没有把每一条被删掉的数据记下来，所以没有可供反向回放的行数据。
    * > 易错点：表的复制格式本来配的是 `ROW` 也没用——`truncate` 会自动改成 `statement` 模式，最终 binlog 里就只留下一条 `truncate` 语句，数据却全被干掉了。
    * > 来源: P198
* **全量备份加增量日志的恢复流程**
    * 思路是先把数据恢复到某一个时间节点上，再顺着 binlog 往后查、一步步恢复到当前这个场景；前提只有一个——你得有备份。
    * 假设策略是一天一备、备份时间是当天凌晨 2 点，下午 3 点误来了一个 `truncate` 或者 `drop`。
    ```text
      时间轴
        02:00                              15:00
          |                                  |
          |  全量备份（一天一备）              |  误删：truncate / drop
          |                                  |
          |<--------- 需要回放的 binlog ------>|

      恢复步骤
        [1] 取出最近一次全量备份（当天 02:00）
        [2] 先把全量备份恢复到临时库（不要直接动主库，避免二次破坏）
        [3] 取出 02:00 → 15:00 之间这一段的 binlog 日志
        [4] 剔除其中误删除的那条操作语句，用剩下的语句在全量备份的基础上做增量恢复
        [5] 数据确认无误后，再回灌到主库
    ```
    * > 易错点：最要紧的一步是先恢复到临时库，千万不要上来就往主库上恢复——万一接下来哪一步操作失误，等于把主库又二次破坏了一遍。
    * > 来源: P198
* **三条预防措施**
    * 第一，权限分离：避免这件事发生的前提是相关人员根本没有这个权限；轻易不会分配相关的写权限，确实要实施必须走审批。比如业务开发人员给 DML 权限，但不给 `truncate` 和 `drop` 的权限；DBA 成员也类似。不同账号设置不同权限、做权限分离，也就避免了一个账号能把所有的库都删掉。
    * 第二，制定操作规范：既然容易误删，那就先不让你删——先把这张表的名字改一下，改完之后相关 SQL 语句就不再依赖这个改名后的表了；然后观察一段时间，看这张表还有没有价值，确实没价值后面再删掉。改名的时候可以起一个见名知意的名字，比如 `to_be_deleted`。
    * 第三，设置延迟复制备库（delayed replica）。
    * > 来源: P198
* **延迟复制备库的恢复窗口与用途**
    * 通常的想法是主从复制要尽量减少数据不一致、尽快达到一致，但在某些场景下反而要故意去延迟复制这个备库。
    * 比如要求主库上的操作过**一个小时**之后，再同步到备库上；这样一旦出现误删除，只要在一个小时之内发现了，就可以及时地把 `STOP SLAVE` 断掉，先把从库（备库）上的数据拿到手——这时候备库上还没删，主库虽然已经删了，但备库上表还在，接下来做恢复就非常容易了。
    * 延迟多久是可以设置的，参数里的 `N` 代表秒，比如写成 `3600`，代表的就是一个小时。
    * 另外两个用处：做延迟测试（做了读写分离，想看看数据还没及时传到从库上时从库查询出来是什么效果）；查询老数据（让复制延迟一周，想看一周之前的那些数据是什么场景，就可以直接查这个延迟备库）。
    ```sql
      -- 发现误删除后立即断开复制线程，保住备库上还没被删的数据
      STOP SLAVE;
    ```
    * > 来源: P198

### 11.5 rm 删除实例与三类操作的对照

* **`rm` 删除实例的处理**
    * 通过 `rm` 的方式相当于把整个 MySQL 实例给干掉了；看起来影响最大，但这种情况反而比较容易解决。
    * > 结论：对于高可用的 MySQL 集群来说，`rm` 干掉的只是其中一个节点上的实例——把这个节点退下来，让其他节点补上去，然后对这个节点做数据恢复，恢复完再接回去就可以了，影响其实并不大；高可用的系统本身都做过相关的方案处理。
    * 真正麻烦的是恶意把整个集群删掉，这就要求我们确保整个集群的数据最好不要放在同一个地方，要跨机房备份、跨城市备份，尽可能减少这种极端情况下的损失。
    * > 来源: P198
* **三类删除操作的横向对照**

| 删除操作 | 影响粒度 | binlog 记录方式 | `flashback` 能否恢复 | 主要恢复手段 | 主要预防措施 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `delete` | 行级 | `ROW` + `binlog_row_image = FULL`，逐行记录 | 能 | `flashback` 反向回放 binlog | 上线前 SQL 审查，开启 `sql_safe_updates` |
| `truncate` / `drop` | 表级、库级 | `statement`，只记一条语句（`truncate` 会自动切到该模式） | 不能 | 全量备份 + 增量 binlog 回放（先恢复到临时库） | 权限分离、先改名后删除、延迟复制备库 |
| `rm` 删除实例 | 实例级 | 实例已不存在 | 不适用 | 高可用集群其他节点顶上，节点恢复后接回 | 集群数据跨机房、跨城市分散存放 |
