# 索引设计、性能分析与查询优化
## 索引分类体系


### 三维正交分类框架

* **索引的多维分类（Multi-Dimensional Index Taxonomy）**
    * 同一物理索引在三个维度上拥有复合属性，三个维度相互交织、绝非割裂互斥。
    * 例：建立在 `(emp_id, dept_id)` 上的主键，在功能逻辑上是主键索引，在物理实现上是聚簇索引，在作用字段个数上是联合索引。

* **功能逻辑维度（Functional Dimension）**
    * 关注索引对所修饰字段施加的业务约束及特定检索算法，含普通索引、唯一索引、主键索引、全文索引、空间索引五类。

* **物理实现维度（Physical Dimension）**
    * 关注索引树的叶子节点存放了什么实体内容，直接决定查询过程中是否需要产生二次 I/O，分为聚簇索引与非聚簇索引（二级索引）。

* **作用字段个数维度（Column-Count Dimension）**
    * 按索引覆盖的数据列数量划分为单列索引与联合索引（亦称复合索引、多列索引）。

### 功能逻辑维度的五类索引

| 索引类型 | 声明关键字 | 唯一性约束 | NULL 约束 | 关键特性 |
| :--- | :--- | :--- | :--- | :--- |
| 普通索引 | `INDEX` / `KEY` | 允许重复值 | 允许 `NULL` | 无附加约束，纯为加速 `WHERE` 过滤或 `ORDER BY` 排序 |
| 唯一索引 | `UNIQUE INDEX` | 非空值全局唯一 | 允许多个 `NULL` | 一表可建多个；叶子节点点查命中即终止遍历 |
| 主键索引 | `PRIMARY KEY` | 全局唯一 | 禁止 `NULL` | 一表只能有且仅有一个；InnoDB 中等同聚簇索引 |
| 全文索引 | `FULLTEXT INDEX` | 不强加唯一性 | — | 分词 + 倒排索引（Inverted Index），按 TF-IDF 相关度打分 |
| 空间索引 | `SPATIAL INDEX` | 不强加唯一性 | 列必须 `NOT NULL` | 仅建在空间地理类型上，底层为 R-Tree |

* **主键索引与聚簇索引的绑定关系**
    * 主键的排序规则决定整张表数据行在物理磁盘和数据页中的排列顺序；同一批数据行在物理空间中只能按一种顺序组织，不可能分裂存储两份，因此主键索引在物理层面绝不可能存在两个。

* **唯一索引的检索优势**
    * 在 B+ 树叶子节点执行点查（Point Lookup）时，一旦匹配到目标值即可立刻终止页内单向链表遍历，无需向后探测。

* **唯一索引与唯一约束的孪生关系**
    * 在 DDL 中添加唯一约束（`UNIQUE CONSTRAINT`）时，系统底层自动创建同名的唯一索引；删除唯一约束的本质就是通过 `DROP INDEX` 移除底层唯一索引。

* **全文索引的分词与倒排机理**
    * 传统 `LIKE '%keyword%'` 的前导通配符会导致 B+ 树索引彻底失效、引发全表扫描；全文索引改用分词算法（Tokenization）切词并构建倒排索引，记录每个单词出现的数据行及偏移量。
    * 适用边界：适用于海量自然语言文本的关键词检索；小规模数据集上其收益无法对冲底层构建开销。

* **空间索引的算法与约束**
    * 底层不再使用一维 B+ 树，而是基于多维空间组织的 R-Tree 算法；所修饰列必须显式声明为 `NOT NULL`，否则建表直接抛语法错误。
    * 只能建立在 `GEOMETRY`、`POINT`、`LINESTRING`、`POLYGON` 四种空间数据类型之上。

* **`INDEX` 与 `KEY` 的等价性**
    * 两者在语法层面完全等价；工程规范建议统一书写为 `INDEX`，以提升代码语义的纯粹性与可读性。
    * 命名缺省策略：若未显式指定索引名，MySQL 默认采用被索引的第一个字段名称作为该索引的名字；生产开发务必显式命名（如 `idx_字段名`、`uk_字段名`）。

### 物理实现维度：聚簇索引与二级索引

* **聚簇索引（Clustered Index）**
    * > **定义**：索引即数据、数据即索引，叶子节点的数据页中完整保存该数据行的所有列值（含用户自定义业务字段及隐藏列）。
    * 自动构建优先级：① 显式指定主键则取主键；② 未指定主键则取表中第一个被声明为 `UNIQUE NOT NULL` 的列；③ 以上均不存在，InnoDB 自动在行尾隐式生成 6 字节的 `DB_ROW_ID` 隐藏列来构建聚簇索引。

* **非聚簇索引 / 二级索引（Secondary Index）**
    * 叶子节点仅存放索引列本身的值以及该行对应的主键值，不含整行数据全貌。

* **回表（Bookmark Lookup）**
    * > **定义**：通过二级索引查询非索引字段时，先在二级索引 B+ 树中查出主键值，再拿该主键值到聚簇索引 B+ 树中重新进行一次自顶向下的寻址。
    * 代价：直接增加磁盘随机 I/O 与 CPU 页内检索成本。

| 对比项 | 聚簇索引 | 二级索引（非聚簇索引） |
| :--- | :--- | :--- |
| 叶子节点内容 | 整行所有列值（含隐藏列） | 索引列值 + 主键值 |
| 数量限制 | 一表仅一个 | 一表可建多个 |
| 查询是否回表 | 不需要 | 查询非索引列时需要回表 |
| 主键索引特例 | InnoDB 中主键索引即聚簇索引 | 若索引列本身就是主键，则无需回表 |


### 作用字段个数维度：单列索引与联合索引

* **单列索引（Single-Column Index）**
    * 一表可创建多个独立的单列索引。
    * 边界：一条查询的 `WHERE` 中包含多个带单列索引的字段时，MySQL 通常只选择其中代价最低的一个单列索引生效；某些场景会触发 `Index Merge`（索引合并），但性能通常不如针对性优化的联合索引。

* **联合索引（Composite Index）与最左前缀原则（Leftmost Prefix Rule）**
    * 联合索引在底层只生成一棵 B+ 树：先按第一个字段排序；第一个字段值完全相同时才按第二个字段排序；前两个字段均相同时才按第三个字段排序。
    * 最左前缀原则：查询条件必须严格从索引最左列开始匹配。跳过最左列（如仅 `WHERE name = '张三'`）时，整棵树在根部并非按该列全局排序，索引彻底失效、无法用于二分查找定位。
    * `SHOW INDEX FROM` 结果中，联合索引呈现为多行记录，`Key_name` 相同而 `Seq_in_index` 严格为 `1`、`2`、`3`，该物理序号不可调换。

* **联合索引的实测表现（三列联合索引 `(book_id, book_name, info)`）**
    * 情况 A：`WHERE book_id = 1001 AND book_name = 'MySQL'` → `key` 为 `mul_bid_bname_info`，成功利用根节点有序性命中索引。
    * 情况 B：`WHERE book_name = 'MySQL'` → `key` 为 `NULL`，索引彻底失效，退化为全表扫描。

* **联合索引的列序设计原则**
    * 追加多列索引时，必须按工程查询频次精确确定参数顺序：最常作为过滤条件、区分度最高的核心字段置于最左端。

### 全文索引的版本演进与选型边界

* **引擎与中文分词的版本线**
    * MySQL 3.x / 5.5 时代：全文索引仅属 MyISAM 专属，事务型 InnoDB 无法创建 `FULLTEXT` 索引。
    * MySQL 5.5 及以前版本仅 MyISAM 支持；自 MySQL 5.6（P129 记为 5.6.4）起 InnoDB 正式支持基于倒排索引的 `FULLTEXT`。
    * MySQL 原生分词器默认以空格、标点符号为单词边界，对英文表现极佳，对中文、日文、韩文（CJK）完全无法切分词义。
    * 自 MySQL 5.7.6 起官方内置 `ngram` 全文解析器，采用滑动窗口的 $N$-gram 分词技术，默认切分长度为 2 个字符。

* **全文索引的技术约束与工程规范**
    * 字段类型限制：只能构建在 `CHAR`、`VARCHAR`、`TEXT` 及其变体文本列上。
    * 前缀截断参数：`fulltext_content(50)` 仅提取列内容前 50 个字符构建词法索引树，防止单个索引项体积膨胀，增加单个 16KB 数据页容纳的索引条目数。
    * 语法调用要求：必须使用 `MATCH(...) AGAINST(...)`，如 `SELECT * FROM test4 WHERE MATCH(fulltext_content) AGAINST('database');`。
    * 数据写入规范：千万级文本导入应"先批量导入数据，再集中创建全文索引"；先建索引后写数据会让每行插入都伴随分词与倒排列表维护，写入吞吐断崖式下跌。
    * 效果边界：检索速度比传统 `LIKE '%database%'` 快数倍至数十倍，但在分词与停用词策略下结果集注重相关度排序，精度特征与完全模糊包含存在细微差异。

* **现代架构中的全文检索选型**
    * 主流互联网企业极少把大规模全文检索压在 MySQL 上，原因是分词计算与相关度排名属计算密集型任务，高并发全文检索会迅速榨干数据库服务器 CPU 算力、阻塞甚至拖垮核心交易事务；频繁写操作还会导致倒排索引大量碎片化，影响 OLTP 事务吞吐。
    * 常见架构：MySQL 负责核心事务交易（OLTP），专业分布式搜索引擎（如 Elasticsearch、Solr）负责全文检索，通过 Canal、Debezium 等 CDC（Change Data Capture）组件监听 binlog 将文本异步同步至搜索引擎集群。

### 各存储引擎对索引类型的支持边界

| 存储引擎 | B+ 树索引 | Hash 索引 | 全文索引 | 空间索引 |
| :--- | :--- | :--- | :--- | :--- |
| InnoDB | 支持（默认索引结构） | 不支持手动显式创建（内部自带自适应哈希 AHI） | 支持（MySQL 5.6 起） | 支持（MySQL 5.7 起） |
| MyISAM | 支持（默认索引结构） | 不支持 | 支持（历史上最早支持） | 支持 |
| MEMORY | 支持 | 支持（MEMORY 引擎默认索引结构） | 不支持 | 不支持 |

* **索引结构归属的补充说明**
    * InnoDB、MyISAM 默认都用 B+ 树；空间类型用 R 树；Memory 默认支持以哈希算法为主的哈希索引。
    * MyISAM 里数据与索引分离，不存在聚簇索引概念。

## 索引创建与删除的语法体系


### 建表阶段的索引添加（CREATE TABLE）

* **约束驱动的隐式索引创建**
    * 主键约束（`PRIMARY KEY`）→ 自动构建聚簇索引，索引名固定为 `PRIMARY`。
    * 唯一性约束（`UNIQUE`）→ 自动构建唯一索引；未单独命名时系统默认用该字段名作索引名。
    * 外键约束（`FOREIGN KEY`）→ 自动构建普通外键索引，默认使用外键约束名（如 `fk_emp_dept_id`）作为索引标识名。

* **显式定义索引的基础语法**
    ```sql
      CREATE TABLE 表名 (
          字段名 字段类型 [约束条件],
          ...
          [UNIQUE | FULLTEXT | SPATIAL] [INDEX | KEY] [索引名] (字段名[(长度)] [ASC | DESC])
      );
      ```
    * 针对变长字符列可指定前缀截取长度 `(长度)`；尾部可选 `ASC`（升序，默认）或 `DESC`（降序，MySQL 8.0 起支持物理倒序存储）。

* **查看索引的两种方式**
    * `SHOW CREATE TABLE 表名 \G`：查看建表原始语句，可看到系统在表定义中自动补充的 `KEY 索引名 (列名)`。
    * `SHOW INDEX FROM 表名`：查看索引元数据字典。
    * 验证索引是否生效用 `EXPLAIN SELECT ...`：`possible_keys` 为候选索引、`key` 为实际采用索引；若未用索引，`key` 列为 `NULL`，意味着执行全表扫描（`type` 为 `ALL`）。

* **`SHOW INDEX` 结果集核心字段含义**

| 字段名 | 典型返回值 | 判定规则 |
| :--- | :--- | :--- |
| `Table` | `book` | 当前索引所属的数据表名 |
| `Non_unique` | `1` | `0` 表示唯一索引（不可重复）；`1` 表示非唯一索引（允许重复值） |
| `Key_name` | `index_bname` | 索引名称；主键索引固定显示为 `PRIMARY` |
| `Seq_in_index` | `1` | 该列在复合索引中的物理顺序序号（从 1 开始递增） |
| `Column_name` | `book_name` | 构成该索引的具体列名 |
| `Index_type` | `BTREE` | 索引的物理数据结构，InnoDB/MyISAM 默认 B+ 树（写作 BTREE） |
| `Visible` | `YES` | 索引在优化器中是否可见（MySQL 8.0 新增特性） |


* **唯一索引的 NULL 值特性与约束生效表现**
    * > **定义**：声明唯一索引的列在插入或修改数据时必须保证非空值的唯一性；该列可以添加 `NULL`，且允许多次重复添加 `NULL`。
    * 重复值拦截：插入两行完全一致的字符串时报错 `Error Code: 1062. Duplicate entry '...' for key '...'`。
    * `NULL` 宽容性依据：SQL 标准及 MySQL 内部实现中 `NULL` 代表"未知"，任意两个 `NULL` 做相等性比较（`NULL = NULL`）结果均为未知（UNKNOWN），故唯一索引允许多行同时为 `NULL`。
    * `SHOW INDEX` 校验：唯一索引记录的 `Non_unique` 值为 `0`。

* **主键索引的隐式定义与删除陷阱**
    * 语法层面不存在独立的 `CREATE PRIMARY INDEX` 语句；删除主键索引通过移除主键约束实现：`ALTER TABLE book2 DROP PRIMARY KEY;`。
    * > **易错点**：主键字段带自增属性（`AUTO_INCREMENT`）时直接 `DROP PRIMARY KEY` 会报错 `Incorrect table definition; there can be only one auto column and it must be defined as a key`。MySQL 强制规定带 `AUTO_INCREMENT` 的列必须被定义为键（主键或唯一键），必须先 `ALTER TABLE` 去掉 `AUTO_INCREMENT`，再执行 `DROP PRIMARY KEY`。

### 建表后追加索引的三种途径

| 目标索引类型 | `ALTER TABLE ... ADD` 语法 | `CREATE INDEX ... ON` 语法 |
| :--- | :--- | :--- |
| 普通单列索引 | `ALTER TABLE 表名 ADD INDEX idx_名 (列);` | `CREATE INDEX idx_名 ON 表名 (列);` |
| 唯一索引 | `ALTER TABLE 表名 ADD UNIQUE INDEX uk_名 (列);` | `CREATE UNIQUE INDEX uk_名 ON 表名 (列);` |
| 复合多列索引 | `ALTER TABLE 表名 ADD INDEX idx_名 (列1, 列2);` | `CREATE INDEX idx_名 ON 表名 (列1, 列2);` |
| 全文索引 | `ALTER TABLE 表名 ADD FULLTEXT INDEX futxt_名 (列);` | `CREATE FULLTEXT INDEX futxt_名 ON 表名 (列);` |
| 空间索引 | `ALTER TABLE 表名 ADD SPATIAL INDEX sp_名 (列);` | `CREATE SPATIAL INDEX sp_名 ON 表名 (列);` |

* **两条追加语法的等价性**
    * `ALTER TABLE ... ADD INDEX` 与 `CREATE INDEX ... ON` 在 MySQL 内部优化器与数据字典中具有完全等价的物理行为；`CREATE INDEX` 本质上是 `ALTER TABLE` 的高级语法糖封装。
    * 唯一例外是主键索引：`CREATE INDEX` 无法用于创建主键索引（不能写 `CREATE PRIMARY KEY INDEX`），为既有表追加主键只能用 `ALTER TABLE 表名 ADD PRIMARY KEY (主键列);`。

* **追加索引的成本**
    * 为 100 万行表追加索引需消耗一定系统时间（实测约数秒）：存储引擎需分配独立的索引空间（扩展 `.ibd` 物理文件体积），对目标字段执行全局排序并依次构建 B+ 树节点。

* **追加索引的语义侧重差异**
    * `ALTER TABLE ... ADD INDEX`：直接在目标表对象上发起结构变更，指明要新增或丢弃的索引标识。
    * `CREATE INDEX ... ON`：显式强调"将独立索引对象绑定到某张表"的语义，索引名置于前侧，通过 `ON 表名 (字段名)` 确立归属。

### 索引删除的两套指令体系

* **删除语法与添加语法对称**
    ```sql
      -- 方式一
      ALTER TABLE book5 DROP INDEX idx_cmt;
      -- 方式二
      DROP INDEX uk_idx_bname ON book5;
      ```
    * `ALTER TABLE 表名 DROP INDEX 索引名;` 在目标表对象上发起结构变更；`DROP INDEX 索引名 ON 表名;` 显式强调删除某个索引对象，末尾必须携带 `ON 表名` 明确归属范围。

* **批量删除某表全部索引的存储过程思路**
    * 传入数据库名与表名两个参数，若数据库与表都真实存在就把该表上所有索引删掉；主键不删。
    * 用途：反复演示各类索引效果时清理环境，避免残留索引干扰执行计划判读；清理后用 `SHOW INDEX FROM 表名` 确认只剩主键。

* **删除索引的适用场景**
    * 随业务迭代沦为低频访问甚至零命中的冗余索引；海量数据批量导入与清洗（ETL）场景下，临时删除多余索引以避免每条写入都触发多个 B+ 树的实时重平衡与磁盘 I/O 刷盘。

### 删除数据列引发的联合索引级联重构

* **级联演变规则（原三列联合索引 `(book_id, book_name, info)`）**

```text
    联合索引随字段删除的级联演变历程

    初始状态：复合索引包含三列 (1: book_id, 2: book_name, 3: info)

    阶段一：ALTER TABLE book5 DROP COLUMN book_name;
        中间列被删除 -> 索引自动重置为两列 (1: book_id, 2: info)

    阶段二：ALTER TABLE book5 DROP COLUMN book_id;
        最左排序列被删除 -> 索引结构蜕化为单列普通索引 (1: info)

    阶段三：ALTER TABLE book5 DROP COLUMN info;
        组成索引的所有列全部被移除 -> 系统自动从数据字典中彻底注销该索引对象
```

* **级联规则结论**
    * 删除表中某列时，若该列是复合索引的成员，存储引擎自动将该列从索引键中剔除并重排其余列的 `Seq_in_index` 序号。
    * 当索引所覆盖的所有字段均被物理删除时，整个索引对象随之自动消亡。

## 索引新特性与物理特性对比


### 降序索引（Descending Index）

* **演进历史与引擎约束**
    * 列名后追加 `DESC` 的语法早在 MySQL 4.x 就被解析器接受，但直到 MySQL 5.7 为止底层存储引擎始终完全忽略 `DESC` 关键字，一律按 `ASC` 物理存储。
    * MySQL 8.0 才真正落地物理降序存储，且仅限 `InnoDB` 存储引擎支持。
    * 核心价值：消除多字段混合方向排序时的反向扫描瓶颈，避免高消耗的临时表与内存/磁盘文件排序。

* **5.7 与 8.0 的数据字典解析差异**
    * 对 `INDEX idx_a_asc_b_desc (a ASC, b DESC)` 执行 `SHOW CREATE TABLE ts1 \G`：
    * MySQL 5.7 输出 `KEY idx_a_asc_b_desc (a, b)`，`b` 后面的 `DESC` 被静默擦除；
    * MySQL 8.0 输出 `KEY idx_a_asc_b_desc (a, b DESC)`，保留降序物理定义，即相同 `a` 值下的 `b` 键值严格从大到小物理排列。

* **执行计划对比（800 条测试数据、`ORDER BY a ASC, b DESC LIMIT 5`）**

| 评估指标 | MySQL 5.7 | MySQL 8.0 | 技术归因 |
| :--- | :--- | :--- | :--- |
| `possible_keys` | `NULL` | `NULL` | 纯排序列检索，无需候选过滤索引 |
| `key` | `NULL` | `idx_a_asc_b_desc` | 8.0 成功借用索引内部的物理排序 |
| `rows` | `799` | `5` | 5.7 全表扫描 799 行并排序；8.0 仅精准抓取前 5 行 |
| `Extra` | `Using filesort` | `Backward index scan; Using index`（或直接使用索引消除排序） | 8.0 根除了高开销的文件排序操作 |

* **收益前提**
    * > **易错点**：降序索引的收益前提是查询的排序方向与索引声明严格同构（或完全反向对称）。索引声明为 `(a ASC, b DESC)` 而业务 SQL 写成 `ORDER BY a DESC, b DESC` 时，排序向量无法与树内部结构对齐，优化器将再次退化为 `Using filesort`。

### 隐藏索引（Invisible Index）

* **软删除理念**
    * 设计精髓：将索引对查询优化器的"可见性"与"物理存储维护"彻底解耦。
    * 读流量：优化器评估候选集时发现索引被标记为 `INVISIBLE` 即视而不见，效果等同于该索引已被删除。
    * 写流量：存储引擎底层依然对该索引的 B+ 树进行实时双向维护与数据写入，数据字典状态保持最新，不产生数据断层。
    * 生产灰度周期：观察 1~2 周，线上无慢查询报警则执行物理 `DROP INDEX`；突发慢 SQL 则一秒执行 `ALTER ... VISIBLE` 瞬间恢复。
    * 另一用途：在会话中切换其可见状态，用 `EXPLAIN` 前后对比，确切获知该索引带来的执行路径演变。

* **主键索引不可隐藏**
    * > **易错点**：主键索引（`PRIMARY KEY`）绝对不允许被设置为隐藏索引。主键作为聚簇索引的组织基准存储着全部物理数据，若被隐藏系统将无法确定数据行物理定位，MySQL 语法层面强制拦截。

* **隐藏索引的创建与切换语法**
    * 建表时定义：`INDEX idx_cmt (comment) INVISIBLE`，`SHOW INDEX` 中 `Visible` 列显示为 `NO`。
    * 追加时定义：`ALTER TABLE book7 ADD UNIQUE INDEX uk_bname (book_name) INVISIBLE;` 或 `CREATE INDEX idx_year ON book7 (year_publication) INVISIBLE;`。
    * 就地切换：`ALTER TABLE book7 ALTER INDEX idx_year INVISIBLE;` 下线灰度观测，`ALTER TABLE book7 ALTER INDEX idx_year VISIBLE;` 紧急回滚恢复，无需重建数据，恢复后立即 `EXPLAIN` 优化器即可重新选取该索引。
    * 不可见期间执行 `EXPLAIN SELECT * FROM book7 WHERE comment = 'MySQL高级';`，`possible_keys` 与 `key` 均呈现为 `NULL`、`type` 为 `ALL`。

* **写放大隐患与优化器开关**
    * 索引处于不可见状态期间，底层 B+ 树在执行 DML 时依然实时维护与持久化更新；长期隐藏且不予理睬的索引是纯粹的性能负资产，只消耗内存缓存与磁盘写 I/O，无法为任何 SELECT 提供加速，验证完毕必须果断 `DROP INDEX`。
    * 默认 `optimizer_switch` 中的 `use_invisible_indexes` 为 `off`；排错测试时可 `SET SESSION optimizer_switch = 'use_invisible_indexes=on';` 让当前会话优化器识别不可见索引，测试完毕后务必切回 `off` 保持生产基线统一。

### 唯一索引与普通索引的叶子页检索差异

```text
    目标值：检索 student_id = 10025

    普通索引检索流程：
      根节点/目录页二分查找 -> 定位叶子数据页 -> 二分查找到 10025
      -> 无法确定后续是否仍有 10025 -> 沿链表向后顺序线性扫描
      -> 直至遇到首个 10026（若恰处页边界还需触发跨页 I/O 读下一页）

    唯一索引检索流程：
      根节点/目录页二分查找 -> 定位叶子数据页 -> 二分查找到 10025
      -> 机制判定：数据行全局唯一 -> 立即停止扫描，零多余 I/O 消耗
```

* **普通索引的向后试探**
    * 命中第一条匹配记录后必须继续向后试探扫描，直到确认出现不同值为止。

* **唯一索引的短路特性**
    * 一旦在叶子节点比对命中即直接阻断检索流程，具有最严谨的短路特性。

### 长文本字段的前缀索引（Prefix Index）

* **前缀索引的截断机制**
    * 对变长字符列（如 `address VARCHAR(120)`）只截取前 $n$ 个字符构建索引：`ALTER TABLE student_info ADD INDEX idx_addr (address(12));`。
    * 建全长索引的代价：整段长文本被完整复制到 B+ 树的每一个节点中，浪费内存与存储空间，且树节点遍历比较时逐字符比对百字节字符串极度消耗 CPU。

* **前缀索引的二次验证与回表流程**

```text
    查询条件：WHERE address = '北京市海淀区中关村南大街1号院'

    步骤 1：扫描前缀索引树
        依据前 12 字符（'北京市海淀区中关村南'）进行二分查找与精确定位
    步骤 2：提取主键 ID
        前 12 字符完全一致的多行均视为命中候选，分别取对应主键（如 id = 101, 102）
    步骤 3：走聚簇索引回表
        利用主键 ID 回表抓取整行完整物理数据
    步骤 4：内存完整字符精准核验
        在 Server 层内存中将完整的 120 字符逐一比对，剔除前缀相同而后缀不同的记录
```

* **判定结论**：前缀索引仅负责在索引阶段实现高比例的粗筛过滤，最终一致性由回表后的完整列比对兜底保障。

* **区分度计算与最佳截取长度**
    * 区分度公式：$\text{区分度} = \dfrac{\text{COUNT}(\text{DISTINCT } \text{LEFT}(column\_name, n))}{\text{COUNT}(*)}$
    * 逐步增加长度 $n$ 观察收敛：
      ```sql
      SELECT
          COUNT(DISTINCT LEFT(address, 10)) / COUNT(*) AS sel10,
          COUNT(DISTINCT LEFT(address, 15)) / COUNT(*) AS sel15,
          COUNT(DISTINCT LEFT(address, 20)) / COUNT(*) AS sel20,
          COUNT(DISTINCT LEFT(address, 25)) / COUNT(*) AS sel25
      FROM student_info;
      ```
    * 规范与经验值：阿里巴巴《Java 开发手册》强制规定 VARCHAR 字段建索引时必须指定索引长度，根据实际文本区分度决定长度；生产经验上前缀长度取到 **20 左右**时区分度即可达到 **90% 以上**（比值大于 0.9），继续增加长度的边际收益极低。

* **前缀索引对 ORDER BY 的致命制约**
    * > **易错点**：前缀索引无法直接用于 `ORDER BY` 排序。前缀索引树只维护前 $n$ 个字符的相对次序，当多条记录前 $n$ 个字符完全相同时，它们在索引树中的排列是随机或依主键排列的，无法反映第 $n+1$ 个字符及以后的真实顺序，优化器判定该索引对全局排序无效，被迫退化为 `Using filesort`。

## 适合创建索引的场景清单


### 情况 1：字段数值具备唯一性限制

* **规则内涵与工程标准**
    * 业务字段（或由多个业务字段拼装而成的组合字段）在现实物理世界中具备唯一特性（身份证号、员工工号、学籍编号、订单流水号）时，必须建立为唯一索引（`UNIQUE INDEX`）。
    * 规范：阿里巴巴《Java 开发手册》MySQL 规约强制规定——业务上具有唯一特性的字段，即使是多个字段的组合，也必须建成唯一索引。
    * 写入开销边界：非超大规模高频并发瞬时写入场景下，维护唯一索引增加的纳秒级微小开销几乎可忽略；收益是查询性能提升与底层业务数据完整性的防御作用。

* **唯一性校验的认知澄清**
    * > **易错点**：担心加唯一索引后每次 `INSERT` 都要做唯一性校验从而拖垮写入性能，是常见的思维误区；该项开销与它带来的检索短路与数据防御收益完全不成比例。

### 情况 2：频繁作为 WHERE 查询条件的字段

* **百万级实测对照（`student_info` 表 100 万行，`WHERE student_id = 12345`）**

| 状态 | 实测耗时 | 执行过程 |
| :--- | :--- | :--- |
| 无索引 | `276 ms` | 优化器无可用索引，全表扫描顺序逐行解析 100 万行物理记录 |
| `ALTER TABLE student_info ADD INDEX idx_sid (student_id);` 之后 | `43 ms` | 走 B+ 树定位；性能提升 6 倍以上，多次取平均增益更稳定明显 |

* **适用判据**：高频出现在 `WHERE` 过滤子句中的列是设立索引最直观的候选对象。

### 情况 3：经常作为 GROUP BY 和 ORDER BY 的列

* **索引消除排序的底层机理**
    * B+ 树叶子节点内部通过行记录指针串联，各数据页之间由双向链表相连，整个索引在逻辑与物理上天然严格有序。
    * 对 `ORDER BY`：排序字段命中索引时，引擎沿有序链表顺次抓取数据即可，彻底免去全表载入内存或借助磁盘的快速排序（消除 `Using filesort`）。
    * 对 `GROUP BY`：分组本质是把相同值的行聚拢，索引已提前排好序、相同值记录物理紧邻，引擎只需顺序扫描一次链表、在值跳变处分组归集（消除 `Using temporary`）。

* **GROUP BY 单独作用的实测（100 万行按学号分组统计）**
    * 存在 `idx_sid` 索引时耗时 `41 ms`；`DROP INDEX idx_sid` 卸载索引后耗时飙升至 `866 ms`，性能相差逾 20 倍；无索引时 MySQL 必须在内存建立临时表对 100 万行执行聚合哈希计算。

* **同时含 GROUP BY 与 ORDER BY 时的列序博弈**
    * 目标 SQL：`SELECT student_id, COUNT(*) AS cnt, create_time FROM student_info GROUP BY student_id ORDER BY create_time DESC LIMIT 100;`
    * > **易错点**：该语句可能被 `only_full_group_by` 拦截并报 `ERROR 1055 (42000)`；需先调整会话模式：`SET @@sql_mode = REPLACE(@@sql_mode, 'ONLY_FULL_GROUP_BY,', '');`

| 索引方案 | 实测耗时 | 机理 |
| :--- | :--- | :--- |
| 分别建 `idx_sid(student_id)` 与 `idx_ctime(create_time)` | `5.212 秒` | 优化器只能在两者中二选一；按 SQL 逻辑生命周期先 `GROUP BY` 后 `ORDER BY`，被迫选 `idx_sid`，`ORDER BY create_time` 无法利用索引，对海量分组中间结果执行 `Using filesort` |
| 建 `idx_sid_ctime (student_id, create_time)` | `0.257 秒` | `student_id` 分组之后组内天然依赖第二列保持 `create_time` 有序，彻底消除内存二次重排；性能暴增 20 倍以上 |
| 反转列序建 `idx_ctime_sid (create_time, student_id)` | `3.790 秒` | 首先执行的是 `GROUP BY student_id`，优化器无法跳过首列 `create_time` 直接使用次列排序，联合索引彻底无法支撑分组 |

* **结论**
    * 查询中同时存在 `GROUP BY` 与 `ORDER BY` 时，应建联合索引，且必须严格将 `GROUP BY` 的字段置于联合索引最左侧、`ORDER BY` 的字段置于其后。
    * MySQL 8.0 中若 `ORDER BY` 频繁使用降序，建议在定义索引时对对应列直接指明 `DESC`。

### 情况 4：UPDATE、DELETE 语句中的 WHERE 条件列

* **检索与更新的联动成本**
    * 执行 `UPDATE` 或 `DELETE` 时，无论底层要修改多少字段，存储引擎的第一步永远是依据 `WHERE` 子句中的检索条件在物理磁盘上将待操作的数据行检索出来。
    * 实测对象：`UPDATE student_info SET student_id = 10002 WHERE name = '411222199010123456';`

| 状态 | 实测耗时 | 并发隐患 |
| :--- | :--- | :--- |
| `name` 无索引 | `0.633 秒` | InnoDB 为定位满足条件的记录做全表扫描，对扫描过的全部记录行加互斥锁（X 锁），极易导致并发更新完全阻塞甚至死锁雪崩 |
| `ALTER TABLE student_info ADD INDEX idx_name (name);` 之后 | `0.001 秒` | 执行速度飙升逾 600 倍，且 InnoDB 精准加行锁，杜绝大范围锁表隐患 |

* **结论**
    * 对数据依据某列筛选后再 `UPDATE` 或 `DELETE`，必须为 `WHERE` 过滤列建立索引。
    * 被更新的字段是非索引列时性能提升达到极致峰值：既享受毫秒级精确定位收益，又免去多棵 B+ 树的级联维护开销。

### 情况 5：DISTINCT 去重操作字段

* **去重的底层执行差异（100 万行 `SELECT DISTINCT student_id FROM student_info;`）**
    * 无索引：数据物理散乱无序，必须全表扫描把 100 万行逐一加载到内存临时表（或临时哈希表）做唯一性判定，或全量排序后去重，实测耗时 `0.683 秒`。
    * 有索引：相同值键在叶子节点数据页中物理天然连续相邻，引擎顺着叶子节点链表单遍流式扫描，当前键与前一个键不同即输出、相同则指针前移跳过，实测耗时骤降至 `0.010 秒`（10 毫秒），提升近 70 倍。
    * 结论：`DISTINCT`、`ORDER BY` 与 `GROUP BY` 底层完全复用 B+ 树物理有序的红利；对高频 `DISTINCT` 去重的列建索引能直接消除内存临时表与磁盘哈希计算。

### 情况 6：多表 JOIN 连接操作的关键列

* **关联表数量的硬性上限**
    * JOIN 连接的表数量尽量不要超过 3 张。
    * 复杂度机理：MySQL 主要采用嵌套循环连接（Nested-Loop Join, NLJ）及其变体，每增加一张关联表相当于增加一层 `for` 循环——单表为 $O(N)$，双表最坏无索引呈 $O(N^2)$，三表攀升至 $O(N^3)$；关联表达到 4~5 张且数据量庞大时，笛卡尔积中间结果集指数级爆炸，极易耗尽内存与缓冲区。

* **WHERE 过滤列与 ON 连接列的协同索引**
    * 实测 SQL：`SELECT s.student_id, s.name, c.course_name FROM student_info s JOIN course c ON s.course_id = c.course_id WHERE s.name = 'AbcDef';`
    * `WHERE` 过滤列：`student_info.name` 无索引时耗时 `0.227 秒`；追加 `idx_name` 后降至 `0.001 秒`（1 毫秒），提升两百倍以上。
    * `ON` 连接键：被驱动表（此处为 `course`）的连接键 `course_id` 必须建立索引，驱动表匹配出的每一行都能通过被驱动表连接键上的 B+ 树以 $O(\log N)$ 复杂度命中，避免在被驱动表上做全表轮询。

* **关联字段数据类型一致性陷阱**
    * > **易错点**：连接条件两端的字段类型必须保持物理层面的绝对一致——不仅数据类型相同，字符集与校对规则亦须一致。
    * 失效链路：若 `student_info.course_id` 为 `INT` 而 `course.course_id` 误声明为 `VARCHAR`，连接时优化器自动注入隐式类型转换函数（如内部调用 `CAST()` 把字符串转为数字）；在索引字段上应用任何内置函数或进行计算会导致该列索引彻底失效，即便建了索引优化器也无法使用，系统退化为海量磁盘全表嵌套扫描。

### 情况 7：优先选用较小的数据类型构建索引

* **选型优先顺序**
    * 满足业务最大上限的前提下"能小则小"：`TINYINT < SMALLINT < MEDIUMINT < INT < BIGINT`。

* **键值类型大小对 B+ 树页容量与树高的影响**

```text
    InnoDB 物理数据页固定大小：16 KB

    场景 A：采用大类型（BIGINT 或长 VARCHAR，单键值+指针占 100 字节）
      16 KB 目录页容纳项 = 16384 / 100 ≈ 163 项
      数据量 1000 万时 -> 树高膨胀至 4 层 -> 检索单行需 4 次磁盘 I/O

    场景 B：采用紧凑类型（INT，单键值+指针仅占 14 字节）
      16 KB 目录页容纳项 = 16384 / 14 ≈ 1170 项
      数据量 1000 万时 -> 树结构扁平（仅 2~3 层）-> 检索仅需 2~3 次 I/O
```

* **二级索引的主键冗余放大效应**
    * InnoDB 中所有二级索引的叶子节点均需存储主键值；主键字段被错误定义为超长类型时，这一冗余开销在表上每一个二级索引中被成倍放大，最终引发全表索引物理空间的膨胀。

### 情况 8：长文本字段构建前缀索引

* 判据与选取公式见「3.4 长文本字段的前缀索引」：对 `VARCHAR` 等变长列只截取前 $n$ 个字符建索引，$n$ 依区分度公式取值、通常取 20 左右（区分度 90% 以上）。
* 不可用于 `ORDER BY`；前缀相同造成的回表比对由 Server 层完整列核验兜底。

### 情况 9：区分度（散列性）高的列适合建索引

* **列的基数（Cardinality）**
    * > **定义**：某一列中不重复数值的实际物理个数。某列 9 条数据值为 `(2, 5, 8, 2, 5, 8, 2, 5, 8)`，去重后只有 3 个独立值，该列基数仅为 3。
    * 基数与分散性：总行数恒定时，基数越大该列数据越分散（区分度越高）；基数越小数据分布越集中（区分度越低）。

* **低基数列的索引反噬（100 万行表的 `gender` 字段）**
    * 该列基数只有 2，区分度仅为 $2 / 1000000 = 0.000002$。
    * 执行 `WHERE gender = '女'` 时优化器通过统计信息发现将命中约 50 万行；走二级索引需执行 50 万次二级索引寻址和 50 万次聚簇回表随机 I/O，开销远超直接单遍物理全表顺序扫描，因此优化器直接放弃该索引。
    * 工程判据：通常要求字段区分度超过 **33%** 时才具备建索引的价值；主键与唯一键的区分度为 100%（值为 1），是最理想的索引构建对象。

### 情况 10：高频列与最高区分度列置于联合索引最左端

* **列序规则**
    * 构建复合索引时必须把业务查询中最频繁出现、且字段区分度最高的列置于最左侧。
    * 例：`ALTER TABLE student_info ADD INDEX idx_sid_cid (student_id, course_id);` 可完美支持 `WHERE student_id = ? AND course_id = ?`（完全命中）与 `WHERE student_id = ?`（命中首列）。
    * 反向声明为 `(course_id, student_id)` 时，高频单独查询 `WHERE student_id = ?` 将彻底无法利用该索引。

* **过滤性最优字段的位置规则**
    * 单列索引场景：表上只有单列索引而 `WHERE` 里写了一串条件时，尽量选择针对当前 query 过滤性最好的那个索引；只允许挑一个时，同样两个字段一个过滤完剩 10%、另一个能过滤掉 99%，选后者。
    * 联合索引场景：当前 query 中过滤性最好的字段在索引里位置越靠前越好——过滤性越好、筛完剩下的数据越少，后面那些列的比对压力就越小。
    * 反例：把性别这种字段放在索引第一位，过滤完还剩一半数据，后面还有 50% 等着处理，效果就稍差。

### 情况 11：多字段检索时联合索引优于多个单列索引

* **多单列索引的错误设计**
    * 分别建立 `idx_sid(student_id)`、`idx_ctime(create_time)`、`idx_cid(course_id)` 三个独立索引：执行多条件查询时优化器绝大多数情况下只能在多个候选索引中择优选取一个，其余两个索引在查询中完全闲置失效；每次数据写入更新时存储引擎还要同时为这 3 棵独立的 B+ 树做维护与磁盘刷盘。

* **归并为一个联合索引的收益**
    * 归并为 `idx_sid_ctime_cid (student_id, create_time, course_id)` 后：仅需维护一棵物理 B+ 树，写入与磁盘开销骤减；单条复杂 SQL 能一举利用多列联合过滤，大幅削减回表数据量；特定查询下还能达成覆盖索引（Covering Index），彻底免除回表。
    * 联合索引覆盖更多 `WHERE` 字段：优化器选择时也倾向选择包含当前 query 中 `WHERE` 子句更多字段的那一个，字段越多索引被用得越充分。

### 单表索引数量限制（≤ 6 个）与优化器开销

* **数量红线**
    * 单张数据表上的索引数量通常严格控制在 **6 个以内**。

| 约束维度 | 底层物理与运行时机理 |
| :--- | :--- |
| 磁盘与内存空间膨胀 | 每个索引都是一棵独立的物理 B+ 树，海量数据表上索引体积常迅速超越原始数据表本身，急剧挤占 Buffer Pool 缓存内存 |
| DML 写入性能劣化 | 执行 `INSERT`、`UPDATE`、`DELETE` 时所有受影响的二级索引必须同步进行节点寻找、页分裂、页合并与磁盘重写入，写性能断崖式下跌 |
| 优化器成本计算与解析延迟 | 基于成本的优化器（CBO）必须评估 `possible_keys` 中每一个候选索引，单表索引过多会让优化器在路径枚举与代价计算上消耗大量 CPU 算力与执行时间，严重拖慢查询响应起步 |

* **候选索引越多越好的认知纠偏**
    * > **易错点**：`possible_keys` 里的候选索引越多，优化器在编译期计算排列组合、估算读取页面成本的耗时就越长，反而极大拉高 SQL 解析和执行计划生成的代价；表上的索引绝非多多益善，必须克制精简。

## 不适合创建索引的场景清单


### 过滤与排序结构中无引用的冷门字段

* **判据**
    * 在 `WHERE` 条件、`GROUP BY` 分组或 `ORDER BY` 排序等查询子句中完全使用不到的字段不要建索引。
    * 字段仅作为 `SELECT` 投影列表中的普通输出项、从未出现在过滤或分组排序子句中时，建 B+ 树索引纯粹是浪费存储与维护资源。

* **避免超前设计**
    * 索引的添加应当由真实的慢查询日志、业务高频查询路径或明确的技术方案驱动；"万一以后业务要查呢"式的超前设计在数据库领域就是负债。

### 数据量极小的轻量级数据表

* **小表全表扫描与索引检索的成本倒挂**

```text
    【全表扫描路径（小表优势）】
    直接顺序扫描数据页（1~2 个 Page） -> 内存连续匹配 -> 立即输出结果

    【二级索引查找路径（小表劣化）】
    检索二级索引根节点 Page -> 二级索引叶子节点 Page -> 拿到主键回表聚簇索引 Page
```

* 行数只有几百条时数据仅需一两个数据页（16 KB/页）就能全部容纳，全表扫描把这极少数数据页连续读入 Buffer Pool 后内存顺序遍历，耗时通常在毫秒级以内甚至显示 `0.00s`。
* 加二级索引后检索路径反而更冗长：先在二级索引树上页寻址，拿主键后再回聚簇索引树回表，一来一回的页跳转与树查找指令开销和逻辑读次数甚至可能超过直接读两个数据页；含变长字符串场景下加了索引的小表查询耗时甚至可能比纯全表扫描还高。

* **真实测试案例（两个结构相同、各存 900 条记录的小表）**
    * 表 1 `test_small_no_index`：仅主键自增 `id INT` 与 `col_b INT`。
    * 表 2 `test_small_with_index`：增加 `KEY idx_col_b(col_b)`。
    * 分别执行 `SELECT * FROM ... WHERE col_b = 9879;`，两者执行时间均显示 `0.00s`。
    * 结论：数据量小于 1000 行的量级下，B+ 树查找算法优势无法被感知，反而徒增每次插入和更新的索引维护开销；表记录数低于 1000 行时应默认放弃除主键以外的多余索引设计。

### 大量重复取值的低区分度字段

* **区分度过低导致索引退化**
    * 索引是否有效关键在于能否帮优化器以极高比例过滤掉不符合条件的数据；典型代表是性别字段（通常只有"男""女"两种取值，各占约 50%）。
    * 数十万行表上针对性别建索引并执行 `WHERE gender = '男'`，会命中整棵 B+ 树叶子节点中整整一半的数据；优化器发现需遍历一半叶子节点且每条命中记录都要回表，离散随机 I/O 成本极其惊人，通常直接放弃索引转为强制全表扫描。

* **极端倾斜分布下的特例**
    * 100 万行记录的学生表，全校男生总共 10 人、女生 999,990 人；男性比例 $10 / 1,000,000 = 1/100,000$。
    * 业务频繁执行 `SELECT * FROM student WHERE gender = '男'` 时，B+ 树检索能精准定位并锁定这 10 条叶子节点数据，仅 10 次回表，查询耗时从全表扫描的 0.6 秒以上断崖式下降到 `0.00` 秒级别，性能提升达数十倍。
    * 但业务要查那 999,990 个女生时，索引彻底失效。

* **判定基准**
    * 常规业务场景下，当某一列中某个特定取值的重复率超过全部数据的 **10%** 时，该列通常不再具备良好的索引筛选收益，应坚决避免创建单列索引。

### 频繁变更的字段与高频写入的业务表

* **频繁更新的特定字段**
    * 每次执行 `UPDATE`，InnoDB 不仅需修改聚簇索引页中的记录本身，还必须同步在对应的二级索引 B+ 树上删除旧键值、计算新位置并插入新键值；若修改引发键值顺序的跨页变动还会触发索引页的分裂与合并，严重拉低系统写吞吐量。

* **频繁写操作的业务表（单行插入的索引维护清单）**

```text
    事务提交 INSERT INTO trade_order (...)
        ├── 1. 写入 Redo Log / Undo Log
        ├── 2. 插入聚簇索引（Clustered Index B+ Tree）
        ├── 3. 插入二级索引 idx_buyer_id B+ Tree
        ├── 4. 插入二级索引 idx_order_sn B+ Tree
        ├── 5. 插入二级索引 idx_create_time B+ Tree
        └── 6. 插入二级索引 idx_order_status B+ Tree
```

* 电商下单流水、用户行为埋点日志等写多读少的事务表上一张表设置 5~6 个甚至更多二级索引时，每一次单行插入都要并发写入 1 个聚簇索引和 5~6 棵二级索引树。
* 代价：索引维护成本线性累加，加剧磁盘 I/O 竞争与缓冲池脏页刷新负担，极易引发高并发事务之间的行锁和间隙锁冲突。

### 散列无序的非单调自增列作为索引键

* **禁用清单与适用范围**
    * 坚决不建议使用散列、无序的值作为索引列，尤其严禁作为表的主键聚簇索引；常见无序值包括通用唯一识别码（UUID）、MD5 散列值、随机字符串以及身份证号码。
    * 这些字段通常满足"非空且唯一"，但在数值大小或字符字典序上呈完全离散、随机跳跃的物理分布。

* **页分裂（Page Split）机理**

```text
    【单调自增主键（AUTO_INCREMENT）插入】
    Page 1: [1 -> 2 -> 3 -> 4]（满）
                            |
    Page 2: [5 -> 6 -> 7 -> ...]（顺序追加在末尾，无需移动旧记录，零分裂开销）

    【无序散列键（如 UUID）随机插入】
    Page 1 已满: [10 -> 25 -> 40 -> 80]
    此时插入 UUID 对应的值 32 -> 必须强行插入 25 与 40 之间
                            |
    【触发页分裂】：分配新页 Page 3，将 Page 1 后半部分数据搬迁至 Page 3，重调指针与槽位
```

* > **定义**：页分裂是指插入的记录需要落在已经写满的数据页上时，把该页的一部分记录挪到新分配的页里，再完成这次插入；它带来额外的写入以及页指针维护开销。
* 新写入的主键为随机 UUID 时可能落在已写满的任意中间数据页内，InnoDB 必须申请全新数据页、把原页内约一半数据移到新页、重构页内目录槽位并重新挂接前后指针；频繁页分裂导致磁盘写入放大、页内物理碎片，表空间体积暴增而有效缓存命中率急剧下降。
* 最佳实践：业务表主键始终采用具备单调递增特性的整数类型并配置 `AUTO_INCREMENT`（或采用有序的分布式雪花算法 ID），新数据顺序追加在 B+ 树最右侧叶子节点最后位置，页写满后平滑开启新页，彻底消除中间页分裂。

### 业务废弃或几乎无调用的冷存索引

* 早期查询接口被重构或废弃后遗留在表结构中的索引，因"不敢动"的心理被遗忘，默默占据磁盘空间，并在每次写入数据时持续消耗 CPU 与 I/O 资源维护树结构平衡。
* 生产环境应定期通过性能视图或工具梳理索引使用频率，对零访问的废弃索引果断执行 `DROP INDEX` 清理。

### 逻辑重复与覆盖冗余的索引结构

* **联合索引前缀覆盖引起的冗余**
    * 表 `person_info` 上已建 `INDEX idx_name_birthday_phone(name, birthday, phone_number)`，再单独创建 `CREATE INDEX idx_name ON person_info(name);`。
    * 依据最左前缀原则，联合索引在物理上本身就是优先按 `name` 严格排序构建的；执行 `SELECT * FROM person_info WHERE name = '张三';` 时优化器直接利用 `idx_name_birthday_phone` 完成二分查找，执行路径与利用单列索引 `idx_name` 完全等价。
    * 结论：单列索引 `idx_name` 在功能上完全被联合索引的前缀覆盖，属于纯粹浪费存储与写性能的冗余索引。

* **主键列重复挂载二级索引**
    ```sql
      CREATE TABLE test_duplicate (
          col1 INT PRIMARY KEY,
          UNIQUE KEY uk_col1(col1),
          INDEX idx_col1(col1)
      );
      ```
    * `col1` 已指定为主键，InnoDB 自动构建主键聚簇索引；再显式添加 `UNIQUE KEY` 和常规 `INDEX` 相当于在同一个字段上重复构筑三棵功能完全重叠的 B+ 树，属于应在生产环境坚决杜绝的重复索引。

* **反模式汇总对照**

| 不建索引的场景类型 | 典型场景示例 | 核心技术原因与危害 |
| :--- | :--- | :--- |
| 查询冷门列 | 从未出现在 `WHERE` / `GROUP BY` / `ORDER BY` 的列 | 无法参与定位与排序，白白增加存储与维护成本 |
| 小微数据表 | 表行数低于 1000 行的配置表、字典表 | 全表扫描仅需少量连续 I/O；二级索引需额外页跳转并引发回表，成本倒挂 |
| 低区分度列 | 性别、布尔标识位（重复率 > 10%） | 单个条件命中大量叶子节点，全量回表代价巨大，优化器倾向放弃索引 |
| 高频写字段/表 | 频繁 `UPDATE` 字段、高并发日志/流水表 | 每次写入均需同步维护多棵 B+ 树，引发锁竞争并降低写吞吐量 |
| 散列无序键 | UUID、MD5、随机字符串作为主键 | 无法按序追加，高频触发中间数据页分裂，产生大量存储碎片 |
| 废弃冷索引 | 历史遗留、业务已不再调用的接口对应索引 | 纯粹占用磁盘并损耗写性能，需定期扫描清理 |
| 冗余与重复索引 | 联合索引前缀列再建单列索引；主键列再建唯一/普通索引 | 检索功能完全重叠，B+ 树重复构造，极大浪费存储与计算资源 |

## 主键设计方案


### 主键设计的两个核心诉求

* **非核心业务可用自增 ID**
    * > **定义**：对非核心业务，表主键选择自增 ID 是可以的。告警、日志、监控这类场景放在本地，跟分布式关系不大，表数据量也没那么大，只需做一个不同条目的区分即可。

* **核心业务的两项硬要求**
    * 第一是全局唯一性——主键最基本的特征；第二是单调递增。
    * 单调递增主要为保证插入性能：直接在 B+ 树右边插入，不触发页分裂。全局唯一是为应对分布式场景：涉及多个不同数据源、需要合并时必须保证全局唯一。

### 自增 ID 的固有缺陷

* **可靠性不高：ID 可被回溯**
    * 直到 MySQL 8.0 才被修复——此前重启之后自增计数器可能回退到当前表内已有记录的最大值加一，删掉的记录腾出来的号会被重新分配出去。
    * MySQL 8.0 把自增计数器的最大值持久化了下来，实例重启后不会再把已经分配出去的 ID 重新发一遍；8.0 之前没有这个保证。

* **安全性不高：对外暴露可被猜测**
    * 暴露 `/user/1` 形式的接口时很容易猜出用户 ID 值、推断出系统用户量，从而方便被爬虫工具爬取数据。
    * > **易错点**：ID 一旦出现在 URL、接口参数或对外单号里，就是一个信息泄露面。

* **性能较差：需在数据库服务端生成**
    * 自增 ID 必须在数据库服务端生成，性能上要稍差一点。

* **交互次数多**
    * 想查看当前自增 ID 的值需用专门的函数去查询；海量并发系统里每多一条 SQL 就多一份开销。

* **只有局部唯一性**
    * 分布式场景下的连锁超市案例：单个分店的表里自增 ID 能保证在这家分店中唯一，但总部汇总时 ID 值可能不再具有全局唯一性，主键值相同的数据很难处理。
    * 结论：局部唯一性是不能接受的点，而它恰恰是自增 ID 的固有属性。

* **网络流传说法的纠正**
    * 网上流传"淘宝数据库用 8 个字节的 `bigint` 做主键，为确保空间够用而没选 `int`"——这个说法听着很有道理，但实际情况是错误的，淘宝不会这样做。
    * 原因：用 8 字节 `bigint` 做主键本质上只是站在数据库这一层考虑问题，没有从业务角度思考主键。
    * > **易错点**：以为主键就只是一个自增 ID 吗？站在架构设计上看，这个答案连及格都拿不到。

### 业务字段充当主键的可行性裁决

| 候选主键字段 | 唯一性 | 稳定性 | 可行性 | 否决原因 |
| :--- | :--- | :--- | :--- | :--- |
| 姓名、性别、生日 | 差 | — | 不可行 | 大量重复，无法唯一标识会员 |
| 地址 | 差 | 差 | 不可行 | 取值过于泛泛（如"北京""上海"），不唯一 |
| 会员卡号 | 好 | 差 | 不可行 | 卡号会被回收复用，改卡主会污染历史流水 |
| 会员电话 | 好 | 差 | 不可行 | 手机号会被运营商回收再分配，主体会变 |
| 身份证号 | 好 | 好 | 不可行 | 属个人隐私，用户可能拒填，主键不允许为 `null` |

* **会员卡号复用的具体危害**
    * 张三因工作变动不再到店消费，门店把张三的卡号又给王五使用，会员表里张三的信息被改成王五，而销售流水表里的卡号没有变。
    * 此时做多表连接查询，结果就成了"王五在这一天买了一本书，89 块钱"——从业务场景上讲这就是一个错误，卡号不能用来做主键。

* **身份证号被排除的关键一条**
    * 身份证号一旦确定就不能修改，看似比卡号、手机号稳定；但它属个人隐私，登记时用户可能根本不愿报，不愿报就是 `null`，而主键不能是 `null`。
    * > **提示**：`null` 与主键互斥，这一条就足以把身份证号从主键候选人里排除，不需要再讨论它的唯一性和稳定性有多好。

* **业务字段做主键的总体结论**
    * 谁也无法预测项目整个生命周期当中哪一个业务字段会因业务需求而出现重复或者重用；一旦有重复，把它用成主键就等于不允许人家重复。
    * 更改主键的成本非常高——索引与底层存储数据都要跟着变，表数据量大时改动几近崩溃；初学者最常见的错误就是喜欢用业务字段做主键。

### 淘宝订单号的结构观察

* **观察到的形态**
    * 订单表里的订单号相当于唯一，可理解成它就是主键；抽取若干条数据发现共 19 位，其中后 5 位都是 `08113`，前 14 位是单调递增的。

```text
    订单号（19 位）
    ┌────────────────────────┬──────────────┬────────────────────┐
    │  时间段（前 14 位）      │  去重字段     │  用户 ID（后 5 位）  │
    │  单调递增                │              │  取尾数若干位        │
    └────────────────────────┴──────────────┴────────────────────┘
            ↑                                        ↑
       保证时间上递增                            同一用户的订单后缀相同
```

* **订单号唯一性的构成原理**
    * 一个用户的后几位一样即其用户 ID，所以后缀都相同；时间是可能极其一致的（如双十一场景时间点高度重合、多个用户同时消费），但对同一个用户来讲一个订单跟下一个订单的时间完全一样不太可能，所以首先要把用户这一块考虑在内。
    * 用户 ID 不必取完整值，取尾数这样几位已经能起到很好的区分、去重作用。
    * 在考虑 ID 的情况下把时间字段加上，再考虑一个去重字段——这个设计能做到全局唯一，对分布式系统比较友好。
    * 去重字段的具体取法需要自行斟酌，里边是有讲究的。

### 有序 UUID 的改造方案

* **原生 UUID 的特点**
    * UUID（Universally Unique Identifier，通用唯一识别码）的特点是：全局唯一、占用 36 个字节、数据无序、插入性能比较差。
    * 16 字节的说法来自二进制存储方式；MySQL 当中的 UUID 是用字符串方式存储的。

* **36 个字节的构成**

```text
    xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
       8       4    4    4       12      ->  32 个十六进制字符
       └── 4 个短横线 ──┘                     ->   4 个字符
    ────────────────────────────────────────────────────
    字符总数 32 + 短横线 4 = 36，字符串存储下每个字符占 1 字节 -> 36 字节
```


* **UUID 全局唯一性的构成**
    * UUID 由几部分构成：时间（分成时间低位、时间中位和时间高位）、版本、时钟序列，以及 MAC 地址。
    * 光从时间上考虑它就占用了 60 个位，类似 `timestamp` 这样的时间戳；再加上后面的版本、时钟序列和 MAC 地址这些结构，合在一起就能保证唯一性。

* **随机无序的原因**
    * UUID 设计中把时间低位放在了前边。几点几分几秒里的"秒"老是变：一会儿是 10 秒、一会儿变成 50 秒、一会儿又变成 10 秒，不是严格递增；只要不是递增，就相当于把它理解成一个像随机的过程。

* **改造方式：交换时间低位与高位**
    * 改造目标是让它变成单调递增：把时间的低位和高位互换，也就是先考虑时、分，再考虑秒——某年某月某日、然后某时某分某秒，再接着往下走，数据就始终是递增顺序。
    * 用它做主键就可以避免页分裂；MySQL 8.0 可以更换时间低位和高位的存取方式。

* **MySQL 8.0 的二进制存储与函数支持**
    * MySQL 8.0 不再使用字符串保存，而是用二进制方式保存，存储空间从 36 字节降低为 16 字节。
    * 16 字节的推算：不数短横线共 32 个字符，每个位置是一个十六进制字符、一个十六进制位用 4 个 bit（$2^4 - 1 = 15$，15 对应十六进制 `F`），所以 $32 \times 4 = 128$ 个 bit；一个字节占 8 个 bit，$128 \div 8 = 16$ 个字节，短横线不要了。
    * $$32 \times 4 = 128\ \text{bit},\qquad 128 \div 8 = 16\ \text{字节}$$
    * 函数用法：
      ```sql
      -- 生成一个 UUID 并保存到用户定义变量中
      SET @uuid = UUID();

      -- 原始 UUID（字符串形式，36 字节）
      SELECT @uuid;

      -- 转成二进制：16 字节，但仍按原来的时间位顺序存放
      SELECT UUID_TO_BIN(@uuid);

      -- 转成二进制，并把时间低位与高位互换
      SELECT UUID_TO_BIN(@uuid, true);
      ```
    * `UUID_TO_BIN()` 是 MySQL 8.0 提供的转换函数，第二个参数就是"是否交换时间字段顺序"的开关；写 `true` 时把三段时间的顺序交换位置，改成先高位、后中位、后低位，中间这一段位置不变。
    * > **易错点**：`UUID_TO_BIN()` 只做二进制转换时 UUID 依然是无序的——它省的是空间，不是顺序；单调递增要靠第二个参数打开的时间位交换。

* **有序 UUID 与自增主键的实测对比（1 亿条数据、每条 500 字节、表上 3 个二级索引）**

| 对比项 | 自增主键 | 有序 UUID（16 字节二进制） |
| :--- | :--- | :--- |
| 主键占用空间 | 8 字节 | 16 字节 |
| 写入 1 亿条数据的耗时 | 较长 | 较短 |
| 表空间大小 | 基准 240 GB | 多 3 GB（增幅不到 1.5%） |
| 全局唯一性 | 仅局部唯一 | 全局唯一 |
| 生成位置 | 只能数据库服务端生成 | 可在业务端生成 |

* 结论：有序 UUID 比自增 ID 花的时间要短一些；增加的空间比较有限（240 GB 基数上多 3 GB、不到 1.5%），整体比较不错，也能保证全局唯一性。
* 有序 UUID 还可以在业务端生成，不用像自增 ID 那样必须在服务器端生成，可进一步减少 SQL 的交互次数；当今互联网环境下不推荐用自增 ID 作为主键来设计。

### 非 8.0 场景下的自定义主键方案

* **参考思路与前提**
    * 不是 8.0 时需手动设置主键，可以参考淘宝那样的方式去做设置，但要记得保证全局唯一性。
    * 用户可以自己创建一个字段；涉及多个主体（如连锁超市各分店都有自己的具体 ID）要合在一起时，数据可能不能保证全局唯一性。

* **总部统一发号方案**

```text
                  ┌──────────────────────────────┐
                  │   总部：用户信息表             │
                  │   字段：当前主键 ID 的最大值    │
                  └──────────────────────────────┘
                        ↑            │
            ③ 更新最大值 │            │ ① 取走当前最大值
                        │            ↓
                  ┌──────────────────────────────┐
                  │   分店 / 部门                 │
                  │   ② 在取到的最大值上自增       │
                  └──────────────────────────────┘
                        │
                        └── ④ 用完把最新最大值还回来，再记录、更新
```

* 总部只保存"当前最大值"这一个数：哪个部门、哪个分店要用时把最大值取过来做自增，自增完把当前最大值上传到总部字段更新，其他分店再用时接着增长，用到最后再还回来记录更新最新最大值——这样也能保证全局唯一性。
* 真实业务中主键还可以考虑用业务和系统的属性去设计，比如用户的尾号、机房的信息，没有必要非得用有序 UUID。

## 调优闭环与诊断工具链


### 调优的目标与基本动作

* **核心目标**
    * 数据库调优的核心目标永远是两个：让响应时间（RT，Response Time）更快，以及让系统吞吐量（Throughput / QPS / TPS）更大。

* **两个基本动作**
    * 整个优化周期的核心行为抽象为观察（Observation）与行动（Action）：先通过监控与系统状态观察到瓶颈现象，再针对性实施优化措施。

* **数据库调优的四个维度**

```text
    数据库调优的四个方向
    ├── 索引与 SQL 编写    索引失效、没建索引、没充分利用索引 -> 建索引 + 遵守编写准则
    ├── 关联查询           JOIN 的表一般不超过三张；反范式化设计减少 JOIN
    ├── 服务器与参数       my.cnf / my.ini：缓存大小、线程数
    └── 数据量与高并发     分库分表、主从复制、读写分离，分散服务器压力
```

* 索引一旦失效查询效率一般就会差一些：没利用索引或压根没建索引就去建索引；索引失效多半是 SQL 编写方式有问题，注意相应编写准则即可。

* **物理查询优化与逻辑查询优化**
    * 物理查询优化：实打实的物理磁盘层面，创建一个索引对应的 `.ibd` 文件中就会多出索引占用的空间，主要靠索引和表连接方式做优化，是重点要掌握的部分。
    * 逻辑查询优化：通过 SQL 等价变换提升 SQL 质量，MySQL 查询优化器也会对 SQL 做优化和重写（如把子查询转换成内连接），靠 SQL 开发经验积累。

### 全链路故障定位与调优层次

* **第一层：判断波动周期**
    * 周期性业务波峰（如电商双十一、618 抢购促销）时数据库瞬间面临数百倍流量冲击，仅靠优化单条 SQL 无法从根本上解决吞吐上限，必须引入分布式缓存或优化缓存淘汰/预热机制，将读请求前置拦截。

* **第二层：捕获慢查询**
    * 对非周期性的日常卡顿，开启 MySQL 慢查询日志（Slow Query Log），合理设定 `long_query_time`，精准抓取执行耗时超出预期的慢 SQL。

* **第三层：微观工具剖析**
    * 利用 `EXPLAIN` 查看执行计划，结合 `SHOW PROFILES` 查看 SQL 在生命周期中每个阶段（语法解析、锁等待、发送数据等）的精确时间切片。

* **第四层：区分等待耗时与执行耗时**
    * 耗时长在"等待"（如等待锁释放、等待磁盘 I/O 把数据页换入内存）：重点调整 MySQL 服务端参数，例如增大 `innodb_buffer_pool_size` 减少换页颠簸。
    * 耗时长在"执行"（如正在做千万级扫描、大排序、散列关联）：重点放在 SQL 重构、索引补全与表结构字段选型上。

* **第五层：架构级横向扩容**
    * 单机数据库在硬件与索引层面已被压榨至极限时，考虑主从复制实现读写分离，或推进垂直分库、水平分表架构改造。

* **成本与收益的金字塔倒挂**

```text
                   ▲                   成本维度              收益与见效维度
                  / \             ===================     ===================
                 / 4 \            硬件升级与架构重构（高）   边际收益递减（低）
                /-----\           -------------------     -------------------
               /   3   \          服务器系统参数微调（中高） 局部性能改善（中低）
              /---------\         -------------------     -------------------
             /     2     \        表结构设计与字段重构（中） 中等全局收益（中）
            /-------------\       -------------------     -------------------
           /       1       \      SQL 重写与索引优化（极低） 性能飞跃提升（极高）
          +-----------------+
```

* 越靠近底层的 SQL 重写与索引调优提速效果越立竿见影（往往让查询耗时直接降低数个数量级）；越往上的硬件升级在烂 SQL 面前也只是杯水车薪。调优遵循"由下至上、由轻至重"的原则。

### 五步工具链串联

```text
    [第 1 步: 发现问题]
    开启慢查询日志 (Slow Query Log)，设定 long_query_time 阈值，准确定位慢 SQL 语句。
           |
           v
    [第 2 步: 宏观拆解]
    利用 SHOW PROFILE 剖析该语句在生命周期各个阶段（如 Sending data, Creating tmp table）的毫秒耗时分布。
           |
           v
    [第 3 步: 静态诊断]
    执行 EXPLAIN（结合 JSON 格式与 SHOW WARNINGS），审查访问类型 (type)、索引覆盖度 (key_len) 与底层机理 (Extra)。
           |
           v
    [第 4 步: 深度推演]
    若有多索引决策困惑，开启 optimizer_trace 查看优化器真实代价评估细节，探求选型根因。
           |
           v
    [第 5 步: 全局巡检]
    结合 sys schema 定期体检，清理 schema_redundant_indexes 冗余索引，排查锁阻塞与缓冲池占用。
```

* **五步之间的衔接关系**
    * 每一步的输出就是下一步的输入：慢查询日志给出具体的慢 SQL 文本，`SHOW PROFILE` 判定瓶颈落在执行期还是锁等待，`EXPLAIN` 给出访问类型与索引利用度，`optimizer_trace` 解释多索引下的选型根因，`sys` schema 把单条语句的排查上升为周期性巡检。

* **五阶段方法论对照**

| 排查阶段 | 核心任务 | 依赖工具与指令 | 关键关注指标 |
| :--- | :--- | :--- | :--- |
| 第一步：全局感知 | 发现系统慢查询迹象 | `SHOW STATUS LIKE 'Slow_queries';` | 慢查询计数器是否非零且持续累加 |
| 第二步：动态捕获 | 抓取超时慢 SQL | `SET GLOBAL slow_query_log = 'ON';`<br>`SET long_query_time = 1;` | `*-slow.log` 日志文件写入 |
| 第三步：归集提炼 | 筛选 Top N 瓶颈 SQL | `mysqldumpslow -a -s t -t 10 /path/to/log` | 排序维度（总耗时 `t`、平均耗时 `at`） |
| 第四步：微观切片 | 剖析慢 SQL 阶段开销 | `SHOW PROFILE CPU, BLOCK IO FOR QUERY n;` | `executing` 耗时、高危临时表状态、`locked` |
| 第五步：精准治理 | 分析优化器执行计划 | `EXPLAIN SELECT ...` | 访问类型 `type`、命中键 `key`、扫描行 `rows` |

## 服务器性能参数与查询成本


### 系统运行时状态参数（SHOW STATUS）

* **语法结构与作用域**
    ```sql
      SHOW [GLOBAL | SESSION] STATUS LIKE '参数通配符';
      ```
    * `GLOBAL`：统计自 MySQL 服务器启动以来的全局累计状态值。
    * `SESSION`（默认）：仅统计当前客户端会话连接范围内的状态值。
    * 生产排查想要了解服务器整体负载与运行瓶颈时，务必加上 `GLOBAL` 以获取真实的全局宏观数据。

* **连接与运行时间：Connections 与 Uptime**
    * `SHOW GLOBAL STATUS LIKE 'Connections';` 统计自服务启动以来累计建立的连接总次数，用于评估服务并发峰值、辅助设定最大连接数参数。
    * `SHOW GLOBAL STATUS LIKE 'Uptime';` 统计服务器已连续运行的秒数；`systemctl restart mysqld` 重启后返回值立刻归零，随后从 5 秒、7 秒、8 秒逐步累加——通过监控 `Uptime` 可灵敏捕获数据库是否因内存溢出（OOM）发生过意外崩溃重启。

* **慢查询频次：Slow_queries**
    * `SHOW GLOBAL STATUS LIKE 'Slow_queries';` 记录执行耗时严格大于 `long_query_time` 的 SQL 执行总次数；洁净实例中为 0。
    * 判定方向：计数器是否非零且持续累加，据此评估线上 SQL 健康度、决定是否介入慢 SQL 治理。

* **存储引擎行级吞吐：Innodb_rows_%**
    * `SHOW STATUS LIKE 'Innodb_rows_%';` 输出项包括 `Innodb_rows_read`（实际读取的数据行总数）、`Innodb_rows_inserted`、`Innodb_rows_updated`、`Innodb_rows_deleted`。
    * 实测：对 107 条员工记录的 `employees` 表连做两次全表查询后，`Innodb_rows_read` 的计数值精确增加了 $107 \times 2 = 214$，客观反映某些 SQL 是否在底层产生了惊人的无效数据扫描量。

| 指令 / 状态变量 | 核心作用说明 | 生产实战价值与关注点 |
| :--- | :--- | :--- |
| `SHOW STATUS LIKE 'Connections'` | 统计自服务启动以来的客户端累计连接数 | 评估服务并发峰值，辅助设定最大连接数参数 |
| `SHOW STATUS LIKE 'Uptime'` | 统计 MySQL 服务累计在线运行时长（秒） | 监测服务器是否发生过异常宕机或 OOM 重启 |
| `SHOW STATUS LIKE 'Slow_queries'` | 统计累计慢查询触发总次数 | 评估线上 SQL 健康度，决定是否介入慢 SQL 治理 |
| `SHOW STATUS LIKE 'Innodb_rows_%'` | 统计 InnoDB 引擎增删改查的物理行数 | 评估全表扫描带来的无效数据吞吐与 I/O 压力 |
| `SHOW STATUS LIKE 'last_query_cost'` | 查看最近一次 SQL 优化的物理代价（页数） | 定量度量 SQL 开销，评估是否需要优化范围或引入缓存 |


### 度量 SQL 执行成本：last_query_cost

* **物理内涵**
    * 优化器在解析执行后都会计算出一个量化的代价数值，`last_query_cost` 直接调取刚刚执行完成的那条查询的真实开销。
    * 所有计算成本中，数据页（Data Page）的读取数量与 I/O 方式是决定成本高低的绝对主导因素。
    * > 核心定律：位置决定效率，批量决定效率。

* **位置决定效率**
    * 从 InnoDB 缓冲池（Buffer Pool）读取内存数据页的延迟在纳秒到微秒级；内存未命中时必须从物理磁盘（哪怕 NVMe SSD）加载，延迟成倍上升。

* **批量决定效率**
    * 从传统机械硬盘或固态介质随机读取一个孤立的数据页，寻道与寻址开销通常在 **10 毫秒**左右；采用顺序 I/O（Sequential I/O）批量读取连续数据页（例如以区（Extent）为单位连续读 64 个页）时，平均分摊到每个数据页的读取时间被极度压缩。

* **百万级数据的成本实操对比（`student_info` 表 100 万行）**

| 实验 | 语句 | `last_query_cost` | 结论 |
| :--- | :--- | :--- | :--- |
| 主键单点精确等值查询 | `WHERE id = 900001` | `1.000000` | 主键是聚簇索引，树高只有 3 层左右且非叶子节点通常常驻内存，仅需精确定位并加载 1 个数据页，成本基准记为 1 |
| 主键连续小范围查询 | `WHERE id BETWEEN 900001 AND 900100` | 约 `21.000000` | 为连续提取这 100 条记录及相关行，InnoDB 实际寻址并加载约 21 个物理数据页；耗时仍显示 `0.00s` |
| 非聚集范围查询 A | `WHERE student_id > 199000` | `2000+` | 涉及 2000 多个数据页，实际执行耗时约 `0.05 秒` |
| 非聚集范围查询 B | `WHERE student_id > 199900` | 约为用例 A 的十分之一 | 实际执行耗时约 `0.01 秒` |

* **顺序 I/O 与预读的验证**
    * 用例 A 涉及的数据页数量（2000+ 页）几乎是用例 B 的 10 倍，但执行耗时只慢了 0.04 秒（两者实际耗时差距只有 5 倍），没有出现跨数量级的耗时膨胀。
    * 根本原因：大范围连续数据扫描时 InnoDB 充分利用底层区（Extent）连续存储结构，以批量顺序读代替昂贵的随机读，使平摊到每个数据页上的绝对耗时急剧衰减。

## 慢查询日志与日志归约分析


### 慢查询日志的判定阈值与默认关闭原因

* **两个核心判定变量**

```text
    客户端发起 SQL 请求
            ↓
    服务端执行并统计执行耗时（Query Time）与扫描行数（Examined Rows）
            ↓
    【判定条件】：Query Time > long_query_time  AND  Examined Rows >= min_examined_row_limit
            ↓
        [符合条件]  ------------------------->  写入慢查询日志文件 (*-slow.log)
```

* `long_query_time`（慢查询时间阈值）：默认值 **10 秒**；必须是**严格大于**该阈值（`>`），等于该阈值不计入——执行耗时恰好 10.00 秒的语句不会被捕获，必须大于 10 秒（如 10.01 秒）才被判定为慢查询。生产调优或压测场景下 10 秒过于宽松，通常下调至 1 秒甚至 0.5 秒。
* `min_examined_row_limit`（最小扫描行数阈值）：默认值 **0**，含义为查询扫描过的最少记录数。保留默认值 0 时只要 SQL 执行耗时超过阈值、哪怕实际扫描 0 行也会被强制写入；设为 100 时即使耗时超时、扫描记录数不足 100 行也不会被记入。日常排查通常保持默认值 0。

* **为什么默认处于关闭状态**
    * 慢查询日志的写入本身需要消耗磁盘物理 I/O，每次捕获慢查询都要进行文件句柄操作与落盘刷写；高并发生产环境中常态化全量开启、尤其慢 SQL 密集爆发时，日志写入本身会形成严重的"次生 I/O 灾难"。
    * 推荐运维准则：在需要进行系统体检或性能调优时动态开启，调优排查完毕并归档分析后及时关闭。

### 动态启停与永久配置

* **临时动态开启与作用域陷阱**
    * `SHOW VARIABLES LIKE '%slow_query_log%';` 输出两项配置：`slow_query_log`（`ON`/`OFF`）与 `slow_query_log_file`（日志文件的物理绝对路径，默认位于数据目录下，命名格式为 `主机名-slow.log`）。
    * 开启必须显式附加 `GLOBAL`：直接 `SET slow_query_log = 'ON';` 会抛错，因为该参数属于全局变量；正确写法为 `SET GLOBAL slow_query_log = 'ON';`。
    * `long_query_time` 同时具备 `GLOBAL` 和 `SESSION` 两种作用域：`SET GLOBAL` 仅对执行该命令之后新建立的客户端会话连接生效；对当前已建立的会话必须同步修改会话级别参数才能立刻生效。
    * > **易错点**：仅执行 `SET GLOBAL long_query_time = 1;` 后在当前窗口查询仍显示 10 秒，是经典的作用域陷阱；生产标准写法是会话与全局同步调整：
      ```sql
      SET GLOBAL long_query_time = 1;
      SET SESSION long_query_time = 1;
      ```

* **配置文件永久化（my.cnf / my.ini）**
    * 固化到 Linux 的 `/etc/my.cnf`（Windows 为 `my.ini`）配置文件的 `[mysqld]` 节点下，保存后执行 `systemctl restart mysqld` 重启服务，参数永久保持。
    ```ini
      [mysqld]
      slow_query_log = ON
      slow_query_log_file = /var/lib/mysql/atguigu05-slow.log
      long_query_time = 3
      log_output = FILE
      ```

* **慢 SQL 触发与计数器验证（400 万条记录的 `student` 表、`long_query_time` 已设为 1 秒）**
    * `SELECT * FROM student WHERE stuno = 3453451;` 实际执行耗时 `1.19 秒`（> 1 秒，被判定为慢查询）。
    * `SELECT * FROM student WHERE name = 'aBcDef';` 实际执行耗时 `1.25 秒`（> 1 秒，被判定为慢查询）。
    * 随后 `SHOW STATUS LIKE 'slow_queries';` 结果精准显示 `Value = 2`，表明系统内部的慢查询监听器已准确感知并完整记录这两次超标操作。
    * 附带结论：`SELECT COUNT(*) FROM student;` 在 400 万记录下耗时约 `0.82s`，能明显感知短暂停顿。

### 慢查询日志分析工具 mysqldumpslow

* **工具性质与执行环境**
    * `mysqldumpslow` 是一个独立的 Perl 脚本，必须在 Linux 操作系统的终端命令行执行，严禁在 MySQL 的 SQL 命令行内输入。
    * 用途：生产环境慢查询日志运行数周后动辄数百兆甚至几个 G，直接用 `cat`、`less`、`vim` 打开不仅低效，更容易把服务器内存撑爆；该工具负责聚合、排序与归类。

| 参数选项 | 全称 / 含义 | 详细功能说明 |
| :--- | :--- | :--- |
| `-s ORDER` | 排序维度 | `at`：平均查询时间（Average query Time，**默认**）；`t`：总查询时间（Time）；`al`：平均锁等待时间（Average Lock time）；`l`：总锁定时间（Lock time）；`ar`：平均返回行数（Average Row count）；`r`：总返回行数（Row count）；`c`：执行总次数（Count） |
| `-t NUM` | Top N 截取 | 仅返回排序后的前 `NUM` 条慢查询（例如 `-t 5` 返回前 5 条） |
| `-a` | 不抽象化参数 | 默认会将 SQL 中的具体数字抽象为 `N`、字符抽象为 `'S'`；加上 `-a` 则保留原始具体字面值，方便复现 |
| `-g REGEX` | 正则模式过滤 | 仅匹配包含特定关键词或表名的 SQL（类似于 grep） |

* **归约统计与输出解读**
    * `mysqldumpslow -s t -t 5 /var/lib/mysql/atguigu05-slow.log`：对语法结构相同的慢查询自动归一化聚合，输出 `Count`、`Time`、`Lock`、`Rows` 与 SQL 模板。
    * 输出示例中 `SELECT * FROM student WHERE name = 'S'` 与 `SELECT * FROM student WHERE stuno = N`：默认情况下参数已被抽象化归拢。
    * `mysqldumpslow -a -s t -t 5 ...`：保留真实字面参数，原汁原味还原出 `stuno = 3453451` 与 `name = 'aBcDef'` 的具体 SQL，为下一步使用 `EXPLAIN` 分析执行计划提供精准的目标输入。

### 慢查询日志的清理、轮转与重置

* **物理删除与失效场景**
    * Linux 终端可直接 `rm -f /var/lib/mysql/atguigu05-slow.log`；但删除文件后如果不通知 MySQL 重新初始化句柄，MySQL 进程依然持有已删除文件的失效文件描述符（inode），后续慢查询将无法正常落盘写入。

* **使用 mysqladmin 重置与刷新日志**
    * `mysqladmin -u root -p flush-logs slow` 通知 MySQL 重新生成全新的空日志文件。
    * > **易错点**：执行 `flush-logs slow` 后新 `-slow.log` 没有生成，根本原因是 `slow_query_log` 系统变量已被手动置为 `OFF` 状态，MySQL 认为无需记录日志、自然不会主动创建新文件；只有当 `slow_query_log` 处于 `ON` 开启状态时，执行 `flush-logs slow` 才会立刻在磁盘上生成一个初始化大小约 900 字节的新日志文件。

## SHOW PROFILE 执行阶段剖析


### 功能开启与阶段明细查看

* **功能开启与会话生命周期**
    * `SHOW VARIABLES LIKE 'profiling';` 查看是否开启（默认 `OFF`）；`SET profiling = 'ON';` 开启当前会话的分析功能。
    * `SHOW PROFILE` 能追踪当前客户端会话中最近执行的多条 SQL 在各个执行步骤（Execution Stages）中的微秒级资源开销。

* **查询概要查看**
    ```sql
      SHOW PROFILES;
      ```
    * 获取当前会话最近执行过的全部查询清单及其全局执行时长。

| Query_ID | Duration | Query |
| :---: | :---: | :--- |
| 1 | 0.00018500 | `SHOW VARIABLES LIKE 'profiling'` |
| 2 | 1.19234800 | `SELECT * FROM student WHERE stuno = 3453451` |
| 3 | 1.25140200 | `SELECT * FROM student WHERE name = 'aBcDef'` |


* **阶段明细剖析**
    * `SHOW PROFILE CPU, BLOCK IO FOR QUERY 3;` 逐行打印整条语句历经的全部细分子状态，关键列为 `Status`、`Duration`、`CPU_user`、`CPU_system`、`Block_ops_in`、`Block_ops_out`。
    * 典型子状态序列：`starting`、`checking permissions`、`Opening tables`、`init`、`System lock`、`optimizing`、`statistics`、`preparing`、`executing`、`end`、`query end`、`closing tables`、`freeing items`、`cleaning up`。
    * 判读：本案例中从 `starting` 到 `preparing`，前端鉴权、语法优化和锁检查仅消耗微秒级时间；而 `executing` 阶段直接飙升到 `1.250850` 秒，伴随极高的 `CPU_user`（1.150000）与 `Block_ops_in`（3240，物理块读入）。
    * 诊断结论：该 SQL 的延迟完全不是锁等待或网络握手引起的，而是引擎在底层进行 400 万行的全表数据块逐页扫描；解决方案是在 `name` 字段上建立高效索引。

* **用 profiler 排除"其他原因"**
    * 做 ICP 开关对照实验时，`SHOW PROFILES` 查看两次执行各自耗时，再分别 `SHOW PROFILE FOR QUERY 1`、`SHOW PROFILE FOR QUERY 2` 看具体细节，会发现主要耗时区别就落在执行过程当中，与其他环节无关。

### 必须警惕的四类高危状态

* **四类高危状态的统一特征**
    * 这四类状态都出现在 `SHOW PROFILE` 明细的 `Status` 列上，一旦结果集中出现其中之一，往往意味着底层执行机制已发生严重的性能退化，必须作为重点治理对象；判读时应当与该阶段的 `Duration` 一起看，确认耗时确实落在了这个状态上。

| 状态 | 成因 | 危害与处置 |
| :--- | :--- | :--- |
| `converting HEAP to MyISAM`（或 `converting HEAP to ondisk`） | 查询产生的内存临时表（MEMORY/HEAP 引擎存储）体积超过 `tmp_table_size` 或 `max_heap_table_size` 阈值，MySQL 被迫把内存表结构在磁盘上重建为基于磁盘的临时表 | 引发性能断崖式下跌，必须优化过滤条件或适当调大内存临时表阈值 |
| `Creating tmp table` | 执行 `DISTINCT`、`GROUP BY` 或复杂关联排序时，引擎无法利用现有索引消除分组，被迫在内部显式开辟临时表 | 建立与维护内部临时表涉及大量内存分配，需针对分组字段补充索引 |
| `Copying to tmp table on disk` | 临时表在磁盘上创建完毕后，正将海量行记录不断从内存拷贝写入磁盘 | 伴随大量磁盘写 I/O |
| `locked` | 正处于锁等待状态（表锁排队或行锁死锁争用） | 说明存在并发事务冲突，需排查长事务与未提交事务 |


### 工具演进与替代路线

* **官方弃用标记**
    * 在 MySQL 5.7 后期及 MySQL 8.0 中，官方已将 `SHOW PROFILE` 与 `SHOW PROFILES` 语法标记为废弃（Deprecated）。

* **官方推荐替代**
    * 推荐使用更强大、更细粒度的 `performance_schema` 和 `sys` 视图（如 `sys.x$statement_analysis`）获取线程级性能剖析。
    * 保留价值：`SHOW PROFILE` 具有零学习成本、语法极其简练、开箱即用的特点，在日常应急排查现场依然是多数工程师最顺手的快速诊断手段。

## EXPLAIN 概览与字段清单


### EXPLAIN 的定位与优化器机制

* **优化器与执行计划的逻辑关系**

```text
    客户端发送 SQL 请求
            ↓
    词法与语法解析器（生成语法解析树）
            ↓
    【查询优化器 (Optimizer)】
    依据成本模型（Cost Model），评估全表扫描与各索引分支开销
    最终生成一份预估成本最低的方案 ——【执行计划 (Execution Plan)】
            ↓
    【存储引擎与执行器 (Executor)】
    按照执行计划调用存储引擎 API 物理提取数据并返回
```

* 优化器本身并不真正读取表里的具体数据行，而是根据系统统计信息（Cardinality 区分度、数据页数量、索引深度等）通过内部成本计算公式，在所有可能执行路径中挑出综合成本（Cost）最低的一条，生成执行计划；随后执行器严格按该计划调用存储引擎 API 完成数据检索。
* 使用 `EXPLAIN`（或其完全等价的别名关键字 `DESCRIBE`）就是让优化器提前把它敲定的执行计划以二维表格形式展示出来。

* **EXPLAIN 能回答的四类问题**
    * 评估单表访问到底采用全表扫描（`ALL`）还是精确索引定位（`const` / `ref`）。
    * 评估多表关联时的先后驱动顺序（谁是驱动表、谁是被驱动表）。
    * 预测哪些候选索引可能被使用（`possible_keys`），以及最终敲定了哪个索引（`key`）。
    * 预估需要物理读取与检查的记录行数（`rows`）。

* **优化器方案未必最优**
    * > **易错点**：优化器基于统计成本计算出来的"最优方案"属于自动化的数学估算。生产环境中由于统计信息延迟未刷新、数据分布严重倾斜或复杂关联场景，优化器选出的方案并不一定等同于研发或 DBA 眼中实际运行最快的方案——这正是需要通过 `EXPLAIN` 人工介入审查、甚至利用 `FORCE INDEX` 或 SQL 重写来纠偏的原因。

### 版本演进与只读安全性

```text
    MySQL 5.6.3 之前       MySQL 5.6.3 之后            MySQL 5.7 / 8.0+
    -----------------    -----------------------     -------------------------
    仅支持 SELECT 查询     支持 SELECT / INSERT /     无需额外参数，默认展示
                         UPDATE / DELETE 等 DML      partitions 与 filtered 列
```

* **支持的语句范围拓展**
    * MySQL 5.6.3 之前 `EXPLAIN` 仅支持对 `SELECT` 检索语句进行分析；从 5.6.3 起官方正式扩展到 `INSERT`、`UPDATE`、`DELETE` 等全量 DML 语句。

* **扩展参数的内置集成**
    * 5.7 之前的低版本中查看分区信息必须输入 `EXPLAIN PARTITIONS`、查看过滤度必须输入 `EXPLAIN EXTENDED`；5.7 及 8.0 主流版本中直接运行 `EXPLAIN` 就会默认输出全部扩展字段。

* **只读安全性**
    * 执行 `EXPLAIN DELETE FROM student WHERE id = 2;` 时 MySQL 仅仅是在模拟评估删除该行记录所需的索引查找成本，底层物理数据绝对不会被真正删除——这保证了在生产环境审查高危写语句执行计划时的绝对安全。

### 输出字段一览与认知顺序

| 字段名称 | 核心技术含义 | 调优关注级别 |
| :--- | :--- | :---: |
| `id` | 查询标识符（代表每个 SELECT 语句的执行顺序） | ★★★☆☆ |
| `select_type` | 查询的具体类型（如 SIMPLE / PRIMARY / SUBQUERY / UNION） | ★★★☆☆ |
| `table` | 当前行执行计划所对应的具体物理表名或临时表名 | ★★★☆☆ |
| `partitions` | 命中的物理分区信息（无分区表则为 NULL） | ★☆☆☆☆ |
| **`type`** | **单表的物理访问方法（如 const / ref / range / index / ALL）** | ★★★★★ |
| `possible_keys` | 当前查询中可能被优化器选用的候选索引列表 | ★★★★☆ |
| `key` | 优化器最终决策实际使用的索引名称 | ★★★★☆ |
| **`key_len`** | **实际使用到的索引字节长度（判断联合索引命中列数的关键）** | ★★★★★ |
| `ref` | 与索引列进行等值匹配的具体字段或常量来源 | ★★★☆☆ |
| **`rows`** | **优化器预估完成查询必须扫描检查的物理记录行数** | ★★★★★ |
| `filtered` | 存储引擎返回的数据经过 Server 层条件过滤后剩余的百分比 | ★★★☆☆ |
| **`extra`** | **极为重要的额外辅助诊断信息（如 Using filesort / Using temporary）** | ★★★★★ |

* **四大核心指标**
    * 标有五颗星的 `type`、`key_len`、`rows` 和 `extra` 是衡量一条 SQL 优劣的核心生命线。
    * 认知顺序（不按官方列排列顺序死记）：先搞懂目标表 `table`，再搞懂执行顺序 `id`，接着搞懂查询类型 `select_type`，最后攻坚访问类型 `type` 与 `extra`。

### 基准测试环境与 EXPLAIN 的局限

* **基准表设计（`s1` 与 `s2` 结构完全对称，各 10000 条数据）**
    * `id`：聚簇索引（主键 B+ 树）。
    * `key1` 与 `key3`：常规非唯一二级索引（`idx_key1`、`idx_key3`）。
    * `key2`：唯一二级索引（`uk_key2`）。
    * `(key_part1, key_part2, key_part3)`：三列联合复合索引（`idx_part`）。
    * `common_field`：无任何索引的普通字段。
    * > **易错点**：空表在优化器眼中是没有成本差异的，许多真实的索引下推、全表扫描与临时表行为只有在真实数据量下才会触发；拒绝在空表上做 `EXPLAIN` 测试。

* **EXPLAIN 的四个固有局限**
    * 不感知任何数据缓存状态：完全不考虑数据页是已缓存在 Buffer Pool 中，还是需要从物理固态硬盘冷读。
    * 不展现优化器的决策推导过程：呈现的是优化器最终选定的"既定事实"，内部 I/O 成本与 CPU 成本各算出了多少无从获知（需借助 `Optimizer Trace`）。
    * 无法获知触发器、存储过程与 UDF 的动态影响：这些程序性构件在运行期产生的隐式开销与锁竞争，在静态分析中完全失真。
    * 统计信息均为采样估算，非精确物理数字：`rows` 和 `filtered` 是基于数据字典采样得出的概率分布估算值，不能等同于实际执行返回的记录数。

## EXPLAIN 关键字段逐项判读


### table 字段：目标单表映射与驱动表顺序

* **单表映射法则**
    * 无论 SQL 写得多么复杂、嵌套多少层子查询，`EXPLAIN` 结果集中的每一行记录都严格对应着一个具体的单表（或派生表、内存临时表）。
    * 单表查询结果集必然只有 1 行记录，`table` 显示该表表名。

* **驱动表与被驱动表的判定**
    * > **定义**：在执行计划里排在上面（`EXPLAIN` 输出靠上那一行）的是驱动表（Driving Table），排在下面的是被驱动表（Driven Table）。这个上下看的是连接字段在 `EXPLAIN` 里的输出顺序。
    * 查询引擎先扫描驱动表，每拿到一条记录，再拿着连接键去检索被驱动表。
    * 驱动表、被驱动表本质上是"查询优化器优化完以后"的结果，是 `EXPLAIN` 呈现出来的，不是写在 SQL 里的书写顺序。

* **书写顺序不决定执行顺序**
    * 写 `FROM s1 INNER JOIN s2` 时优化器并不一定机械按照书写先后顺序执行；它会评估两张表的大小与索引情况，自动选择成本更低的表作为驱动表。
    * 在多表连接中先打印出的表为驱动表，后打印出的为被驱动表。

### id 字段：查询标识符与执行顺序

* **id 的分配机理**
    * > 核心黄金法则：在一条大的 SQL 查询语句中，每一个 `SELECT` 关键字原则上都会被分配一个唯一的 `id` 值。
    * 整个 SQL 只有一个 `SELECT` 关键字时，无论关联多少张表，所有行的 `id` 全都是 1；出现子查询、嵌套查询或 `UNION` 时存在多个独立 `SELECT` 关键字，依次分配不同的 `id`（1, 2, 3……）。
    * > **易错点**：`id` 不是无意义的行号，它蕴含整个查询的结构层次与执行时序。

* **规律一：id 相同，从上至下顺序执行**
    * `EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.id = s2.id;` 结果集两行 `id` 全部都是 1：第一行 `table=s1` 优先级相同排在第一行首先被读取（驱动表），第二行 `table=s2` 嵌套循环匹配（被驱动表）。

* **规律二：id 不同，值越大优先级越高**
    * `EXPLAIN SELECT * FROM s1 WHERE key1 = (SELECT key1 FROM s2 WHERE id = 1);` 输出 `s1`（`id = 1`）与 `s2`（`id = 2`）两行；子查询内部包含独立 `SELECT` 关键字被分配 `id = 2`。
    * 执行引擎必须先执行 `id = 2` 的子查询，把 `s2` 表中 `id = 1` 对应的 `key1` 值计算出来，再交给外层 `id = 1` 的主查询去检索 `s1` 表。

* **规律三：临时表与 UNION 的 NULL 值含义**
    * `EXPLAIN SELECT * FROM s1 UNION SELECT * FROM s2;` 输出 3 行：
    * 第 1 行 `id = 1`、`table = s1`，对应第一个 `SELECT`；第 2 行 `id = 2`、`table = s2`，对应第二个 `SELECT`。
    * 第 3 行 `table` 显示为 `<union1,2>`，表示是把 `id = 1` 与 `id = 2` 两趟查询结果合并后的临时数据集；`Extra` 显示为 `Using temporary`，印证 MySQL 在底层显式开辟内存临时表执行去重计算；`id` 值为 `NULL`，因为这行代表对前面两趟查询结果的后置聚合处理，不是由任何独立 `SELECT` 关键字产生的。
    * 换成 `UNION ALL` 时控制台只输出两行（`id` 分别为 1 和 2），`<union1,2>` 临时表与 `id = NULL` 行彻底消失——`UNION ALL` 不需剔除重复记录，无需建立临时表暂存数据。

* **子查询重写导致 id 归一**
    * `EXPLAIN SELECT * FROM s1 WHERE key1 IN (SELECT key2 FROM s2 WHERE common_field = 'abc');` 结果集输出 `s1` 与 `s2` 两行，但两行的 `id` 全部变成了 1。
    * 原因：原生非相关子查询机械执行时逻辑类似双层嵌套循环，外层扫描 $N$ 次、内层每次扫描 $M$ 次，复杂度高达 $O(N \times M)$；优化器发现该 `IN` 子查询在语义上完全等价于多表半连接（Semi-Join）或内连接，直接在内存中重写为类似 `SELECT s1.* FROM s1 INNER JOIN s2 ON s1.key1 = s2.key2 WHERE s2.common_field = 'abc'` 的连接查询，重写之后的实际执行 SQL 只有一个主 `SELECT`，因此 `id` 自动归一为并列的 `1`。

* **id 字段背后的性能公理**
    * > 核心公理：每个不同的 `id` 号码都代表数据库需要发起一趟独立的查询检索；一条 SQL 语句在执行计划中的查询趟数（不同 `id` 的数量）越少越好。
    * 看到一条复杂业务 SQL 经 `EXPLAIN` 后输出了 4~5 个不同的 `id`，甚至出现大量内部派生表（Derived Table）时就应警惕：说明查询引擎陷入极深的多层嵌套依赖，应尽可能通过改写为连接查询或利用临时物化表对其扁平化降维。

### select_type 字段：小查询在大查询中的角色

* **SIMPLE：简单查询**
    * 查询语句既不包含 `UNION` 也不包含子查询时，无论单表查询还是多表连接查询，其每一个小查询的 `select_type` 都被标记为 `SIMPLE`。
    * 结论：只要查询语句中不存在 `UNION` 和子查询，不管是单表还是内连接、左外连接，各表的 `select_type` 均为 `SIMPLE`。

* **PRIMARY、UNION 与 UNION RESULT**

| id | select_type | table |
| :--- | :--- | :--- |
| 1 | `PRIMARY` | `s1` |
| 2 | `UNION` | `s2` |
| NULL | `UNION RESULT` | `<union1,2>` |

* 最左边（最外层）的主查询 `select_type` 是 `PRIMARY`；其后通过 `UNION` 或 `UNION ALL` 连接的所有小查询均为 `UNION`；汇聚并剔除重复记录的内部临时表对应的小查询为 `UNION RESULT`（`id` 为 NULL）。
* 换成 `UNION ALL` 因为不需要去重、直接流式返回两部分数据，结果中只有 `PRIMARY` 和 `UNION` 两行，不会出现 `UNION RESULT`。

* **SUBQUERY 与 DEPENDENT SUBQUERY**
    * `SUBQUERY`：包含子查询的语句不能被优化器改写为多表连接，且该子查询是非相关子查询（内层查询独立运行、不依赖外层表字段）。
    * `DEPENDENT SUBQUERY`：子查询无法转为连接查询，且内层查询的过滤条件中引用了外层查询的字段（相关子查询）。
    * > **易错点**：标记为 `DEPENDENT SUBQUERY` 的子查询可能会被执行多次——外层主查询每扫描出一条记录就把其字段值传给内层子查询执行一次，外层扫出多少条内层就可能重复执行多少次，性能开销极大。
    * 示例：`SELECT * FROM s1 WHERE key1 IN (SELECT key1 FROM s2);` 内层为 `SUBQUERY`；`SELECT * FROM s1 WHERE key1 IN (SELECT key1 FROM s2 WHERE s1.key2 = s2.key2);` 内层为 `DEPENDENT SUBQUERY`。

* **DEPENDENT UNION**
    * 大查询内部包含子查询、子查询内部又由 `UNION` 或 `UNION ALL` 构成，且子查询中各小查询都依赖外层查询时，除最左侧小查询之外其余后续 `UNION` 小查询的 `select_type` 标记为 `DEPENDENT UNION`。
    * 内层未显式引用外层字段却依然出现 `DEPENDENT UNION` 的原因：优化器处理 `IN` 子查询时往往自动将其重构改写为 `EXISTS` 相关子查询，重写后外层参数被渗透进内层每个分支，使内层小查询变成依赖外层的查询。

* **DERIVED 与 MATERIALIZED**
    * `DERIVED`（派生表）：子查询出现在 `FROM` 子句中且无法被优化器折叠合并到外层时，MySQL 把该子查询的执行结果物化为一个派生表；该子查询 `select_type` 为 `DERIVED`，外层查询的 `table` 字段显示为 `<derived2>`（由 `id=2` 的查询派生而来）。
    * `MATERIALIZED`（物化表）：优化器决定不把子查询转为连接、也不采用相关子查询的多次循环迭代方式，而选择把非相关子查询结果直接物化为一个带索引的内部临时表再与外层表连接时，内层子查询 `select_type` 为 `MATERIALIZED`，外层 `table` 可能显示为 `<subquery2>`。

### partitions 字段与 type 字段总览

* **partitions：分区表命中分析**
    * 当前查询涉及的表不是分区表时该字段值始终为 `NULL`。
    * 表在建表时通过 `PARTITION BY RANGE/LIST/HASH` 划分了不同分区，且查询带有分区键过滤时，`partitions` 字段明确列出本次查询命中了哪些具体分区（例如 `p0`、`p1`）。
    * 绝大多数未配置物理分区的单表场景下该字段均为 `NULL`，日常调优了解即可。

* **type 字段的定义与性能排序**
    * > **定义**：`type` 字段刻画的是 MySQL 在执行查询时对某个表采取的具体"访问方法"（Access Method）。
    * 性能排序从最优到最差：
      ```text
      system > const > eq_ref > ref > fulltext > ref_or_null > index_merge
      > unique_subquery > index_subquery > range > index > ALL
      ```
    * 规范：《阿里巴巴 Java 开发手册》明确给出数据库 SQL 调优规范——SQL 性能优化的目标至少要达到 `range` 级别，要求是 `ref` 级别，能达到 `const` 则最理想；绝不能放任核心业务接口长期运行在 `index` 尤其是 `ALL` 级别。

* **system：精确统计引擎的极速单行访问**
    * 必须同时满足两个严苛条件：① 表中只有一条物理记录；② 该表所使用的存储引擎具有精确的统计数据（例如 `MyISAM` 或 `Memory` 引擎）。
    * 机理：MyISAM 这类引擎内部维护了精确记录当前表总行数的元数据变量，执行 `SELECT COUNT(*)` 根本不用翻阅数据页，直接读取变量返回常数，因此面对单行表优化器能直接把整行记录当成固定常数提取。
    * 验证：`CREATE TABLE t (a INT) ENGINE = MyISAM;` 插入 1 条后 `EXPLAIN SELECT * FROM t;` 的 `type` 为 `system`；再插入第 2 条后退化为 `ALL`。
    * > **易错点**：InnoDB 下建一张单行记录表执行同样查询不会得到 `system`，而是 `ALL`——InnoDB 采用 MVCC 多版本并发控制，由于并发事务与版本链的存在，表中到底能看到多少条记录必须结合当前事务的 ReadView 实际扫描判断，没有全局精确记录行数的物理变量，即使物理上只有一条数据也必须老老实实做全表扫描。

* **const：主键或唯一索引的常量等值匹配**
    * 通过主键（`PRIMARY KEY`）或非空的唯一二级索引（`UNIQUE KEY`）与一个常量进行等值比较时，该表访问方法为 `const`（常数级）。
    * 机理：主键与唯一索引的根基就是唯一性，在聚簇索引或唯一二级索引的 B+ 树上二分查找一路下潜到叶子节点，只要找到匹配值就能彻底断定整张表里绝不可能再有第二条相同记录，优化器甚至可以在查询准备阶段直接算出该记录并将其视作常量。

* **eq_ref：连接查询中被驱动表的主键/唯一索引匹配**
    * 多表连接中被驱动表通过主键或非空的唯一二级索引列与驱动表某列进行等值匹配连接时，被驱动表的访问方法为 `eq_ref`。
    * 执行过程：优化器选择驱动表并全表扫描（`type = ALL`），对驱动表检索出的每一条记录把其主键值作为确定输入，去被驱动表的主键索引树上做等值匹配；因为被驱动表该列是主键，对驱动表传来的每一个特定值最多只能找到一条匹配记录。
    * > **提示**：主键或唯一索引是联合索引时，必须对该索引包含的每一个列都进行等值匹配才能达到 `eq_ref`。

* **ref：普通二级索引的常量等值匹配**
    * 通过普通的（非唯一的）单列二级索引与常量进行等值匹配检索时访问方法即为 `ref`。
    * 机理：普通二级索引叶子节点中键值为同一值的记录可能不止一条且在叶子节点单向链表中连续排列，优化器定位到第一条后沿链表向后顺序扫描，直到遇到第一个不是该值的记录为止；返回的可能是连续区间而非唯一一条，性能略低于 `const`，但在业务查询中已属非常理想的级别。
    * > **易错点**：隐式类型转换——`key3` 是 `VARCHAR` 字符类型但 SQL 写成 `WHERE key3 = 123`（没有加单引号）时，MySQL 会自动调用类型转换函数将列值转为数值再比对；一旦在索引列上触发隐式函数运算索引彻底失效，访问方法会直接从预期的 `ref` 骤降为 `ALL`。写 SQL 时必须保证常量类型与字段定义完全一致。

* **ref_or_null：支持 NULL 值的普通索引等值扫描**
    * 在普通二级索引等值匹配基础上，查询条件还允许索引列为 `NULL` 时访问方法为 `ref_or_null`。
    * 示例：`EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key1 IS NULL;`——二级索引树叶子节点把所有 `NULL` 值集中存放在链表最左端，MySQL 既要扫描 `'a'` 对应的连续记录，又要扫描最左侧为 `NULL` 的记录。

* **index_merge：多索引合并扫描**
    * 某些特殊场景下优化器可以同时利用多个单列索引检索出各自匹配的主键集，然后将结果集做并集（Union）或交集（Intersection）合并。
    * 示例：`EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key3 = 'a';` 时 `type` 为 `index_merge`，`key` 字段显示 `idx_key1,idx_key3`；优化器分别利用两个索引定位出主键列表，做内存并集运算后再统一回表取整行数据。
    * > **易错点**：把 `OR` 改成 `AND`（`WHERE key1 = 'a' AND key3 = 'a'`）时优化器绝大多数情况下不会走 `index_merge`，而是在 `key1` 与 `key3` 之间精算成本，挑出一个过滤效果更好、成本更低的单个索引执行，另一个条件则在回表后进行内存过滤。

* **unique_subquery / index_subquery**
    * `unique_subquery`：包含 `IN` 的子查询中，优化器把 `IN` 结构转换为 `EXISTS` 相关子查询、且子查询内部的关联条件可以使用主键进行等值匹配时，该子查询对应表的 `type` 即为 `unique_subquery`，本质上是子查询内部对主键做的类似 `eq_ref` 的查找。
    * `index_subquery`：位于 `unique_subquery` 之后、`range` 之前的访问方法级别。

* **range：索引范围扫描**
    * 利用二级索引或聚簇索引获取某个连续范围或离散点集区间的记录时访问方法为 `range`。
    * 通常对应 SQL 中的 `<`、`>`、`<=`、`>=`、`BETWEEN`、`IN` 等操作符；示例：`WHERE key1 IN ('a', 'b', 'c')`、`WHERE key1 > 'a' AND key1 < 'b'`。
    * 利用 B+ 树索引的有序性，优化器只需确定扫描的起始边界与终止边界，并在叶子节点链表中做一段局部遍历——这是日常业务调优必须坚守的底线级别。

* **index：覆盖索引全扫描**
    * `index` 本质上也是一种全表扫描，只不过扫描的是整棵二级索引树而不是聚簇索引树。
    * 触发条件：查询所需要返回的全部列（包括 `SELECT` 列表、`WHERE` 条件列）恰好被某个二级索引（尤其是联合索引）完全覆盖、不需要任何回表操作时，即使查询条件不符合最左前缀原则、无法利用索引树做二分快速定位，优化器依然会选择把整棵二级索引树的所有叶子节点从头到尾扫一遍。
    * 示例：存在联合索引 `idx_part(key_part1, key_part2, key_part3)` 时执行 `EXPLAIN SELECT key_part2 FROM s1 WHERE key_part3 = 'a';`——条件使用 `key_part3` 违背最左前缀原则无法快速跳跃定位，但查询字段与条件字段全都包含在 `idx_part` 中；二级索引树一个数据页往往能塞下几百上千条紧凑的索引条目，而聚簇索引树包含整行全部列数据、页面非常膨胀，扫描整棵二级索引树的磁盘 I/O 成本远小于扫描整棵聚簇索引树，因此 `type` 显示为 `index`，`Extra` 常伴随 `Using index`。
    * > **易错点**：在上述 `SELECT` 列表中额外加入一个不在联合索引中的普通列 `common_field` 时，二级索引无法覆盖它、必须全表回表，优化器会果断放弃扫描二级索引，`type` 立刻跌入 `ALL` 全表扫描。

* **ALL：全表扫描**
    * 最糟糕的访问方法：没有利用任何索引辅助定位，直接从头到尾遍历聚簇索引的所有数据页和所有数据行，磁盘 I/O 开销与 CPU 比对开销达到峰值；线上大表环境中必须通过建立合理索引将其彻底消灭。

### possible_keys、key 与 key_len

* **possible_keys 与 key 的心智模型**
    * `possible_keys`：展示当前查询 `WHERE` 条件中涉及列上建立的、理论上可能被用到的索引清单。
    * `key`：展示优化器通过精细成本估算后最终决定真正采用的索引名称。
    * 示例：`EXPLAIN SELECT * FROM s1 WHERE key1 > 'z' AND key3 = 'a';` 中 `possible_keys` 同时列出 `idx_key1` 和 `idx_key3`，最终 `key` 选定 `idx_key3`——因为 `key1 > 'z'` 是范围查询，扫描数据量与回表开销不确定且可能较大；`key3 = 'a'` 是单列常量的等值精准匹配（`type = ref`），评估的 I/O 与 CPU 成本明显更低。

* **特殊现象：possible_keys 为 NULL 但 key 有值**
    * 典型场景就是 `type = index` 的覆盖索引扫描：查询条件不符合索引树的查找过滤逻辑，优化器初始阶段认为没有可用于精准定位的 `possible_keys`；但后续评估返回列时发现整个查询可由某个二级索引全覆盖免于回表，于是最终在 `key` 中选用了该联合索引。

* **key_len 的核心意义**
    * `key_len` 记录 MySQL 执行查询时实际使用到的索引部分的字节长度，单位是字节（Byte）。
    * > **易错点**："`key_len` 越大越好"的口诀不能跨表比较——拿表 A 的 `key_len = 20` 去跟表 B 的 `key_len = 303` 比毫无意义，不同表字段类型和字符集本身完全不同。`key_len` 只能跟自己的不同查询语句比。
    * 核心应用场景：检查复合索引（联合索引）是否被充分利用。三列联合索引 `idx_part(key_part1, key_part2, key_part3)` 中，只用 `key_part1` 时 `key_len` 为 303 字节，同时用 `key_part1` 与 `key_part2` 时跃升为 606 字节，三列全部用在过滤条件上时达到 909 字节；`key_len` 越长意味着联合索引中参与过滤的列越多，B+ 树中下潜定位的范围越精准，需要扫描的数据页与回表的数据行就越少。

* **单列 key_len 的计算规则**

```text
    单列 key_len = 基础类型字节数
                 + （字符类型需乘以字符集单字最大字节数）
                 + （若允许为 NULL，额外加 1 字节记录 NULL 标志位）
                 + （若为 VARCHAR 等变长字段，额外加 2 字节记录数据实际长度）
```

* 基础数值类型：`TINYINT` 1 字节；`SMALLINT` 2 字节；`MEDIUMINT` 3 字节；`INT` 4 字节；`BIGINT` 8 字节；`DATETIME`（MySQL 5.6.4+）5 字节；`TIMESTAMP` 4 字节。
* 字符集倍率：`latin1` 每字符 1 字节；`gbk` 每字符最多 2 字节；`utf8`（utf8mb3）每字符最多 3 字节；`utf8mb4` 每字符最多 4 字节。
* NULL 标志位开销：列定义允许为 `NULL`（未显式声明 `NOT NULL`）时额外耗费 1 字节。
* 变长长度列表开销：`VARCHAR` 等变长类型额外耗费 2 字节；定长类型（如 `CHAR(n)`、`INT`）无此 2 字节开销。

* **key_len 计算案例（`s1` 表基于 `utf8` 字符集，单字符最多 3 字节）**

| 字段定义 | 语句 | 推算 | `key_len` |
| :--- | :--- | :--- | :--- |
| 主键 `id INT NOT NULL` | `WHERE id = 10005` | `INT` 固定 4 字节；主键自带 `NOT NULL` 无 NULL 标志位；定长无长度列表 | 4 |
| 唯一索引 `key2 INT NULL` | `WHERE key2 = 100` | `INT` 4 字节 + 允许为 NULL 1 字节 | 5 |
| 普通单列 `key1 VARCHAR(100) NULL` | `WHERE key1 = 'a'` | $100 \times 3 = 300$ + NULL 1 字节 + 变长 2 字节 | 303 |
| `col1 VARCHAR(10)` utf8，允许 NULL | 单列索引自测题 | $10 \times 3 = 30$ + 1 + 2 | 33 |
| `col2 VARCHAR(10)` utf8，`NOT NULL` | 单列索引自测题 | $10 \times 3 = 30$ + 0 + 2 | 32 |
| `col3 CHAR(10)` utf8，允许 NULL | 单列索引自测题 | $10 \times 3 = 30$ + 1 + 0（定长无长度列表） | 31 |

* **联合索引 `idx_part(key_part1, key_part2, key_part3)`（三列均为 `VARCHAR(100)`、utf8、允许 NULL）的 key_len 演变**
    * 仅命中第一列 `WHERE key_part1 = 'a'` → `key_len: 303`。
    * 命中前两列 `WHERE key_part1 = 'a' AND key_part2 = 'b'` → `key_len: 606`（$303 + 303$）。
    * 命中全部三列 → `key_len: 909`（$303 \times 3$）。
    * 违背最左前缀 `WHERE key_part2 = 'b'` → `key: NULL, key_len: NULL`（无法使用索引）。
    * 判读用法：看到预期应全部走索引的语句其 `key_len` 只有 303，就必须立刻排查是不是后续字段在 SQL 中触发了范围查询或隐式类型转换，导致联合索引发生截断失效。

### ref 字段：等值匹配对象识别

* **常量匹配**
    * 索引列直接与 SQL 中写死的常量值等值比较时 `ref` 字段显示为 `const`；示例 `EXPLAIN SELECT * FROM s1 WHERE key1 = 'a';` 中 `type` 为 `ref`、`ref` 字段输出 `const`。

* **多表关联的具体列匹配**
    * 多表连接中被驱动表通过索引列与驱动表某列等值连接时，`ref` 会完整打印驱动表提供数值的具体列全称（格式为 `库名.表名.列名`）。
    * 示例 `EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.id = s2.id;` 中被驱动表 `s2` 的 `type` 为 `eq_ref`，`ref` 字段显示 `atguigu...s1.id`，清晰说明 `s2` 在主键索引树上每次查找的键值输入来自 `s1` 表的 `id` 字段值。

* **函数与动态表达式匹配**
    * 关联条件中驱动表的列被函数或复杂表达式包裹时，传递给被驱动表索引的就不是原始列而是运行期计算结果。
    * 示例 `EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s2.key1 = UPPER(s1.key1);` 中被驱动表 `s2` 虽然使用了 `key1` 上的二级索引，但 `ref` 字段不再输出列名而是输出 `func`，代表其等值匹配依赖某个函数的返回值。

### rows 与 filtered 字段

* **rows 字段：预估扫描记录数**
    * > **定义**：`rows` 表示查询优化器根据统计信息，预估为了获取目标结果集所需要读取的物理记录条数。
    * 核心原则是数值越小越好：预估读取的记录数越少，这些记录被收拢在同一个数据页中的概率就越高；记录越发散、行数越多，所需加载的数据页就越多，引发的磁盘 I/O（甚至随机 I/O）次数急剧膨胀。
    * 示例：`EXPLAIN SELECT * FROM s1 WHERE key1 > 'z';` 中 `rows` 显示为 382，表示优化器根据 B+ 树叶子节点的采样统计，估算出大约需要沿着索引链表扫描 382 条记录。

* **filtered 字段：条件过滤保留率**
    * > **定义**：`filtered` 字段是一个百分比（0.00% ~ 100.00%），表示经过当前表的 `WHERE` 条件搜索过滤后，剩余满足条件的有效记录占预估扫描总行数（`rows`）的比例。
    * 数值越高越好：方案 A 为 `rows = 40`、`filtered = 100%`，扫了 40 行全是目标有效数据，过滤精准度 100%；方案 B 为 `rows = 400`、`filtered = 10%`，最终有效条数同为 $400 \times 10\% = 40$ 条，但为这 40 条白白多扫描了 360 条无价值数据，占用更多缓冲区与内存。

* **filtered 在多表连接中的连锁放大效应**
    * > 核心结论：在连接查询中，驱动表预估扫描行数与过滤比例的乘积（$\text{rows} \times \text{filtered}$），直接决定了被驱动表被驱动循环调用的总次数。
    * 案例：`EXPLAIN SELECT * FROM s1 INNER JOIN s2 ON s1.key1 = s2.key1 WHERE s1.common_field = 'a';` 中 `s1` 作为驱动表全表扫描预估 9895 行，其 `WHERE` 条件 `common_field = 'a'` 无索引、过滤后比例仅 10.00%。
    * 驱动表实际向后传递的记录条数约为 $9895 \times 10.00\% \approx 989$ 条，意味着被驱动表 `s2` 必须被外部循环连续调用 **989 次**；驱动表 `filtered` 更低或 `rows` 更大时，被驱动表的执行频率会以数量级飙升——优化驱动表的过滤精准度是治理慢连接查询的首要突破口。

### Extra 字段：深层执行机制诊断

* **No tables used 与 Impossible WHERE**
    * `No tables used`：查询语句中根本没有 `FROM` 子句，如 `EXPLAIN SELECT 1;`。
    * `Impossible WHERE`：`WHERE` 条件在静态分析期即可判定永远为 `false`，根本不可能命中任何数据，如 `EXPLAIN SELECT * FROM s1 WHERE 1 != 1;`；此时优化器甚至连 `table` 都不需要读取，直接返回空结果集。

* **Using where：条件过滤发生的层面**
    * 真正含义：存储引擎层无法单靠索引树把所有过滤条件处理完毕，必须将数据行读取出来，在 Server 层使用额外的条件进行逐行过滤。
    * > **易错点**：`Using where` 并不意味着"只要写了 `WHERE` 条件就会出现"。
    * 常见场景一：全表扫描时使用过滤条件（没有任何索引可用），如 `EXPLAIN SELECT * FROM s1 WHERE common_field = 'a';`。
    * 常见场景二：虽然使用了索引，但 `WHERE` 中还并列存在无法走索引的其他普通列条件，如 `EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' AND common_field = 'b';`——优化器先利用 `key1` 索引定位到主键并回表取出行数据，随后在 Server 层对 `common_field = 'b'` 进行比对过滤。

* **No matching min/max row 与 Select tables optimized away**
    * `No matching min/max row`：`WHERE` 中的等值条件在索引树中根本找不到任何匹配记录时直接输出，如 `EXPLAIN SELECT MIN(key1) FROM s1 WHERE key1 = '不存在的常量';`。
    * `Select tables optimized away`：针对建立索引的列执行 `MIN()` 或 `MAX()` 时，因为 B+ 树天然有序、极小值必在最左叶子节点、极大值必在最右叶子节点，优化器在执行前读取索引根节点和边界就能直接秒得常数结果，执行阶段直接将该表操作"优化掉"。

* **Using index：覆盖索引（最高优状态）**
    * > **定义**：当查询列表（`SELECT` 列）以及搜索条件中的所有字段全部包含在所使用的二级索引树中（包含隐藏的主键列）、无需进行任何回表操作即可返回数据时，`Extra` 会明确显示 `Using index`。
    * 对比：`EXPLAIN SELECT key1, id FROM s1 WHERE key1 = 'a';` 输出 `Extra: Using index`；`EXPLAIN SELECT key1, common_field FROM s1 WHERE key1 = 'a';` 输出 `Extra` 为空或 `Using where`，必须触发回表。
    * 是高并发系统中最推崇的优化状态，避免了昂贵的聚簇索引随机回表 I/O。

* **Using index condition：索引条件下推（ICP）**
    * 示例：`EXPLAIN SELECT * FROM s1 WHERE key1 > 'z' AND key1 LIKE '%a';` 中 `key1 > 'z'` 可利用 B+ 树做范围检索，但 `key1 LIKE '%a'` 以通配符 `%` 开头无法走索引树层级快速查找，优化器在 `Extra` 中标注 `Using index condition`。

```text
    没有 ICP（传统做法）：
    [二级索引] 找出满足 key1 > 'z' 的 382 个主键
        -> 立即逐一回表（触发 382 次聚簇索引查找）
        -> [Server 层] 过滤 key1 LIKE '%a'
        -> 最终只剩 3 行（白白浪费 379 次回表 I/O）

    开启 ICP（现代做法）：
    [二级索引] 找出满足 key1 > 'z' 的候选条目
        -> [存储引擎内部] 直接利用索引条目里的 key1 过滤 key1 LIKE '%a'
        -> 淘汰 379 条不符合项，只剩下 3 个有效主键
        -> 仅对这 3 个主键进行回表取全列（回表次数骤降到 3 次）
```

* ICP 将原本属于 Server 层负责的过滤条件直接"下推"到存储引擎层：凡是索引中已经包含的列，即使无法利用树形做二分快速定位，也先在引擎层做一遍内存过滤，筛掉绝大多数不合格行后再回表。

* **Using join buffer (Block Nested Loop)**
    * 多表连接时被驱动表的关联条件上没有索引，MySQL 无法走索引等值查找，只能采用基于块的嵌套循环连接算法（Block Nested Loop）。
    * 此时 MySQL 在内存中专门划拨一块名为 `join buffer` 的连接缓冲区暂存驱动表的数据行，然后整块与被驱动表批量比对。
    * 调优手段只有一个：立刻在被驱动表的连接字段上建立合适的索引。

* **Not exists：外连接反连接优化**
    * 使用左外连接（`LEFT JOIN`）且 `WHERE` 子句中包含"要求被驱动表的非空列为 NULL"的条件时（常用于求差集反选），优化器利用该主键不为 NULL 的物理特性进行反向剪枝：一旦在被驱动表中找到第一条匹配记录就立即停止对被驱动表的继续扫描，此时 `Extra` 显示为 `Not exists`。

* **Using union(...)：索引合并并集**
    * 对应 `type = index_merge`：单表查询中使用 `OR` 运算符连接两个独立的单列索引时，如 `EXPLAIN SELECT * FROM s1 WHERE key1 = 'a' OR key3 = 'a';`，`Extra` 显示 `Using union(idx_key1,idx_key3); Using where`。
    * 说明优化器分别通过两个单列索引树查出主键集，在内存中完成主键并集去重后再统一执行回表。

* **Zero limit**
    * SQL 末尾显式写了 `LIMIT 0` 时出现，如 `EXPLAIN SELECT * FROM s1 LIMIT 0;`；优化器识别到业务调用方压根不需要任何数据行，直接做短路跳过处理。

* **Using filesort：内存/磁盘文件排序（危险警报）**
    * SQL 包含 `ORDER BY` 而排序字段无法借由现有索引的既有顺序直接输出时，MySQL 被迫在内存（Sort Buffer）或超出内存限制后借用磁盘临时文件进行额外的排序计算。
    * 对比：`EXPLAIN SELECT * FROM s1 ORDER BY key1 LIMIT 10;` 的 `Extra` 为空（索引本身在叶子节点链表中就是单调递增的，无需额外排序）；`EXPLAIN SELECT * FROM s1 ORDER BY common_field LIMIT 10;` 的 `Extra` 为 `Using filesort`。
    * > **易错点**：`Using filesort` 并不一定意味着"生成了磁盘文件"——待排序数据量小于系统参数 `sort_buffer_size` 时排序完全在内存中进行，只有数据量超过缓冲区上限时才切片落盘到临时文件做归并排序；无论哪种，其 CPU 和内存消耗都远高于直接读取索引。
    * 调优准则：线上核心高频查询一旦出现 `Using filesort`，必须优先考虑通过建立联合索引或单列索引来承接 `ORDER BY` 的排序需求。

* **Using temporary：内部临时表（严重性能杀手）**
    * 查询中包含 `DISTINCT`、`GROUP BY`、`UNION` 等操作且相关列无法利用索引维护好的有序分组状态时，MySQL 必须在底层隐式创建内部临时表来累加、暂存和比对数据。
    * 对比：`EXPLAIN SELECT DISTINCT common_field FROM s1;` 输出 `Extra: Using temporary; Using filesort`；`EXPLAIN SELECT DISTINCT key1 FROM s1;` 输出 `Extra: Using index`（直接从索引树走覆盖去重，开销极小）。
    * 建立与维护内部临时表涉及大量内存分配，数据量膨胀超出限制时还会转为磁盘临时表，I/O 成本极为高昂；生产环境中看到 `Using temporary; Using filesort` 组合出现，通常意味着该接口存在巨大的慢查询风险，应立即针对分组字段补充索引。

## EXPLAIN 输出格式与成本模型


### 四种输出格式

| 输出格式 | 核心特征与调用方式 |
| :--- | :--- |
| 传统格式 | 默认二维表格，字段完整，但不提供执行成本数值 |
| JSON 格式 | `EXPLAIN FORMAT=JSON ...`，包含详尽的 I/O 与 CPU 成本核算 |
| TREE 格式 | `EXPLAIN FORMAT=TREE ...`，树状缩进表达节点层级与流转顺序 |
| 可视化图形输出 | MySQL Workbench 放大镜功能，红绿图框直观标注访问代价 |

* 严格来说 MySQL 官方原生语法支持三种文本输出格式，结合官方图形化客户端 Workbench 一共构成四种观察执行计划的视角。
* 传统表格格式最大的痛点是缺失了衡量执行计划好坏的最核心属性——成本（Cost）。

### JSON 格式与 cost_info 成本核算

* **为什么必须掌握 JSON 格式**
    * MySQL 优化器本质上是基于成本的优化器（Cost-Based Optimizer, CBO）；面对同一条复杂 SQL，优化器内部可能推演很多种执行方案（走索引 A、走索引 B、走多表连接、走物化表），最终挑中某一个是因为经过数学模型计算判定其综合成本值最低。
    * 传统格式只能看到被选中的既定事实，完全看不到成本数字；指定 `FORMAT=JSON` 后 MySQL 会把所有内部估算的 I/O 成本、CPU 评估成本完整倾泻出来。

* **JSON 键名与传统表格字段的映射**

```text
    传统表格字段                JSON 键名 (Key)
    --------------------------------------------------------------
    id                          -->  select_id
    table                       -->  table_name
    type                        -->  access_type
    possible_keys               -->  possible_keys
    key                         -->  key
    key_len                     -->  key_length
    ref                         -->  ref
    rows                        -->  rows_examined_per_scan
    rows * filtered 派生值       -->  rows_produced_per_join
    filtered                    -->  filtered
    Extra 中的 Using where 等   -->  attached_condition
```


* **cost_info 的三个核心指标**
    * `read_cost`（读取成本）：驱动表的 `read_cost` 由扫描聚簇索引数据页产生的物理 I/O 成本，以及扫描出来之后因不满足过滤条件而被剔除的废弃数据行所消耗的 CPU 比较成本累加而成，即 $\text{rows} \times (1 - \text{filtered}) \times \text{单行比较 CPU 权重}$。
    * `eval_cost`（求值评估成本）：经过条件筛选后满足过滤条件的有效数据行在准备输出或向下一阶段传递时所消耗的 CPU 评估成本，$\text{eval_cost} = \text{rows} \times \text{filtered} \times \text{单行评估 CPU 权重}$；案例中 $9895 \times 10\% = 989.5$ 行对应 CPU 成本 98.90。
    * `prefix_cost` 与 `query_cost`（累积前缀成本与总成本）：驱动表 `s1` 自身单表处理总成本 $\text{prefix_cost} = \text{read_cost} + \text{eval_cost} = 914.85 + 98.90 = 1013.75$；被驱动表 `s2` 自身 `read_cost`（247.43）与 `eval_cost`（98.90）总和约 346.33；整个多表连接的全局总成本 $\text{query_cost} = 1013.75 + 346.33 = 1360.08$。
    * `data_read_per_join`：指明在当前关联步骤下单次连接预估读取的原始数据体量（例如 1M），为内存缓冲区配置提供直观参考。

* **成本的构成与单位**
    * 外层查询与内层查询各有 `read_cost` 与 `eval_cost`，总成本 = 外层(read_cost + eval_cost) + 内层(read_cost + eval_cost)。
    * 公式中用到表中的行数以及 `filtered` 百分比；这个数值的单位不是时间，可以理解成 1。

### TREE 格式与可视化输出

* **TREE 格式（MySQL 8.0 及以上）**

```text
    -> Nested loop inner join  (cost=1360.08 rows=989)
        -> Filter: ((s1.common_field = 'a') and (s1.key1 is not null))  (cost=1013.75 rows=989)
            -> Table scan on s1  (cost=1013.75 rows=9895)
        -> Index lookup on s2 using idx_key1 (key1=s1.key1)  (cost=0.25 rows=1)
```

* 树以清晰的缩进表达自底向上的算子调用链条：底层先对 `s1` 全表扫描（成本 1013.75）；上层对全表扫描结果应用过滤条件将 9895 行筛至 989 行；最外层执行嵌套循环连接、内部驱动对 `s2` 的索引查找，最终汇总总成本 1360.08。
* 相比复杂的 JSON 嵌套，TREE 格式在保留算子成本和数据流向的同时大大提升了终端阅读的可读性。

* **Workbench 可视化输出（Visual Explain）**
    * 使用步骤：在 SQL 查询编辑器中输入纯业务 SQL（切记不要在前面手写 `EXPLAIN` 关键字），选定 SQL 后点击工具栏中的"执行计划（放大镜）"图标。
    * 表现：Workbench 自动用红绿两色区分访问代价——危险的 `ALL` 全表扫描标为鲜红色，安全高效的索引匹配标为绿色，并在每个图框上方直接标注单步与累计的 Cost 数值。
    * 示例拓扑：`s1` 标为 `[Full Table Scan]` 红色高亮（成本 1013.75、行数 9895），`s2` 标为 `[Index Lookup]` 绿色健康（成本 346.33、行数 989），两者汇入 `Nested Loop Join`（总成本 1360.08）。

## 优化器重写、optimizer_trace 与 sys schema


### SHOW WARNINGS 探查优化器重写实录

* **使用规则与返回规范**
    * > 操作铁律：`SHOW WARNINGS` 必须紧跟在 `EXPLAIN` 语句之后立刻执行；如果中间执行了任何其他 SQL 语句，上一次执行计划的上下文就会被立即冲刷覆盖。
    ```sql
      -- 步骤 1：执行 EXPLAIN
      EXPLAIN SELECT ...;
      -- 步骤 2：紧跟执行 SHOW WARNINGS（命令行终端建议追加 \G 纵向展示）
      SHOW WARNINGS\G;
      ```
    * 输出三列：`Level`（通常为 `Note`）、`Code`（状态码，最常见的是 `1003`）、`Message`（优化器经过词法解析、规则改写、常量折叠与半连接扁平化后最终实际采用的 SQL 结构）。

* **实战一：外连接消除与驱动表逆转**
    * 语句：`EXPLAIN SELECT * FROM s1 LEFT JOIN s2 ON s1.key1 = s2.key1 WHERE s2.common_field IS NOT NULL;`
    * 现象：书写上 `s1 LEFT JOIN s2` 说明 `s1` 必须作为主表保留全部数据、理应是驱动表，但 `EXPLAIN` 后第一行出现的竟然是 `s2`、第二行才是 `s1`。
    * `SHOW WARNINGS\G` 的 `Message` 显示该查询被改写为 `from s2 join s1 where ((s1.key1 = s2.key1) and (s2.common_field is not null))`。
    * 原因：`WHERE` 条件显式约束 `s2.common_field IS NOT NULL`，导致原本左外连接中"当 `s2` 无法匹配时补 NULL 保留"的语义彻底失效——哪怕补了 NULL 也会被 `WHERE` 条件过滤掉；优化器判定该查询在数学语义上与内连接严格等价，直接把 `LEFT JOIN` 改写成了 `JOIN`；一旦变成内连接优化器就拥有自由调换驱动表顺序的权力，评估发现以数据量更小的 `s2` 作为驱动表综合成本更低，于是果断逆转表的执行顺序。

* **实战二：IN 子查询扁平化为多表连接**
    * 语句：`EXPLAIN SELECT * FROM s1 WHERE key1 IN (SELECT key1 FROM s2 WHERE key2 = 'a');`
    * 现象：直觉上外层一个 `SELECT`、内层一个 `SELECT`，执行计划应分配 `id=1` 和 `id=2`，实际运行后两行记录的 `id` 全部都是 1。
    * `SHOW WARNINGS\G` 的 `Message` 显示改写结果为 `from s2 join s1 where ((s1.key1 = s2.key1) and (s2.key2 = 'a'))`：嵌套在 `IN` 内部的子查询被优化器彻底"压平（Flattening）"，直接重构成等价的由 `s2` 和 `s1` 组成的多表内连接。

* **Message 的使用边界**
    * > **易错点**：`SHOW WARNINGS` 输出的 `Message` 只是优化器内部推演重构的抽象语法逻辑表示，里面夹杂着数据库前缀、内部函数修饰及别名映射，严禁直接复制粘贴到生产代码中执行；它的核心价值在于帮助看清优化器的真实执行意图、验证自己的 SQL 改写假设是否与优化器的实际决策同频。

* **外连接被改写的实测验证**
    * 三组测试：① 外连接 + 关联字段 + 过滤条件 → `EXPLAIN` 里先 `b` 后 `a`，明明写的是 `a LEFT JOIN b`，`b` 成了驱动表；② 同一个外连接换一组过滤条件 → 先 `a` 后 `b`；③ 内连接 `a JOIN b` → 先 `b` 后 `a`，顺序同样被颠倒。
    * 测试 ① 的真实原因是优化器把该外连接改造成了内连接，既然已经变成内连接，谁当驱动谁当被驱动就由优化器自己说了算。
    * > 结论：外连接里写在前面那张表，不一定是驱动表。

### optimizer_trace 追踪优化器决策链路

* **功能定义与默认状态**
    * > **定义**：`optimizer_trace` 是 MySQL 5.6 引入的深度追踪功能，能将优化器在解析、重写、代价估算以及方案比对过程中的完整心智决策全程记录为结构化的 JSON 文档，并暂存在 `information_schema.OPTIMIZER_TRACE` 系统表中。
    * 通过它不仅能看优化器重写 SQL 的每一个中间步骤，更能看清它对不同索引的估算行数、数据页成本以及最终决策的裁决依据。
    * 生成追踪信息会消耗额外内存与 CPU 开销，MySQL 默认将该功能置于关闭状态。

* **开启追踪与参数调优**
    ```sql
      SET optimizer_trace = 'enabled=on,end_markers_in_json=on';
      SET optimizer_trace_max_mem_size = 1048576; -- 1MB（根据查询复杂度可设 10MB）
      ```
    * > **易错点**：即使是一条看似普通的单表范围查询，优化器内部推演产生的 JSON 追踪信息也往往长达数百行；内存上限维持默认偏小的值会让超出部分被底层直接截断丢弃，导致最关键的代价比对信息丢失，因此开启追踪前务必先将该内存参数适当调大。

* **标准四步闭环工作流**
    ```sql
      -- 步骤 1：在当前会话开启 trace 并设置内存
      SET optimizer_trace = 'enabled=on,end_markers_in_json=on';
      SET optimizer_trace_max_mem_size = 1048576;
      -- 步骤 2：执行需要深度分析的目标 SQL
      SELECT * FROM student WHERE id < 10;
      -- 步骤 3：立即从系统表中提取最新一条追踪记录
      SELECT * FROM information_schema.OPTIMIZER_TRACE\G;
      -- 步骤 4：排查完毕后，立即关闭 trace 释放资源
      SET optimizer_trace = 'enabled=off';
      ```

* **追踪结果集的四大组成部分**
    * `QUERY`：记录本次追踪所针对的目标原始 SQL 文本。
    * `TRACE`：全量 JSON 报文，自顶向下严格对应优化器的三大执行生命周期——`join_preparation`（准备阶段，含常量折叠、派生表展开、初步语法树重构）、`join_optimization`（优化核心阶段，含 `condition_processing` 条件规范化、`table_dependencies` 表依赖关系分析、`rows_estimation` 单表各候选索引扫描行数与成本精算并记录 `considered_execution_plans`、`attaching_conditions_to_tables` 确定条件下推）、`join_execution`（执行阶段，记录最终确定的调用算子执行计划）。
    * `MISSING_BYTES_BEYOND_MAX_MEM_SIZE`：因超出内存阈值而被截断丢弃的字节数；为 0 说明整份报文完整无缺，大于 0 说明末尾已被截断，必须进一步调大 `optimizer_trace_max_mem_size` 后重试。
    * `INSUFFICIENT_PRIVILEGES`：权限不足指示位；取值为 0 表示当前用户拥有完整查看权限，取值为 1 表示由于权限不足（例如执行了以 `SQL SECURITY DEFINER` 创建的视图或存储过程）系统自动隐匿了 `TRACE` 内容。

### sys schema 性能诊断视图

* **架构演进与设计定位**
    * `information_schema`：提供数据字典、表结构与静态元数据。
    * `performance_schema`：提供锁等待、事件消耗、I/O 吞吐等底层动态插桩数据；其原始表结构极其生僻，存储的数字往往以微秒甚至皮秒（Picoseconds）为单位，且缺乏多表关联逻辑。
    * MySQL 从 5.7 开始官方内置 `sys schema`：通过封装一组预定义的视图、存储过程与函数，将底层原始遥测指标归纳为直观易懂、自带人类可读单位（如秒、MB）的诊断报表。

* **场景一：索引健康度治理**
    * 排查冗余索引：`SELECT * FROM sys.schema_redundant_indexes;`。
    * 经典案例：表 `student_info` 上已有单列索引 `idx_create_time (create_time)`，后为满足联合查询又定义联合索引 `idx_ct_sid (create_time, student_id)`；该视图会立即报警提示 `idx_create_time` 属于冗余索引——因为联合索引天然遵循最左前缀原则，所有能使用 `idx_create_time` 单列过滤的查询完全可以无缝被 `idx_ct_sid` 承接，保留旧的单列索引只徒增维护开销，应立即 `DROP INDEX` 删除。
    * 排查从未被业务使用过的索引：`SELECT * FROM sys.schema_unused_indexes;`；系统上线稳定运行数周后执行，若非主键、非唯一约束的索引命中使用计数始终为 0，说明业务查询根本没用到，可列入清理清单。

* **场景二：表物理访问与 Buffer Pool 内存排查**
    * `SELECT * FROM sys.schema_table_statistics;` 直观呈现各个业务表的读写行数总和及总耗时排行；排在最前列的高频访问表就是重点需要通过缓存（如 Redis）或建立覆盖索引进行架构减负的目标。
    * `SELECT * FROM sys.innodb_buffer_stats_by_table;` 直接展示缓冲池中各表数据页的占用比例与容量（自带 `MB/GB` 单位），快速定位是否存在突发大表全表扫描将热点业务数据"冲刷"出内存的恶性事件。

* **场景三：低效高危 SQL 模式监控**
    * `SELECT * FROM sys.statement_analysis;` 将参数归一化后列出执行频次最高、平均耗时最长、甚至返回全表扫描行数最大的 SQL 模板，是日常架构巡检的首要看板。
    * 结合 `sys.statements_with_sorting` 和 `sys.statements_with_temp_tables` 可秒级抓出哪些线上接口正在后台频繁引发 `Using filesort` 和 `Using temporary`。

* **场景四：行锁阻塞与死锁定点排查**
    * `SELECT * FROM sys.innodb_lock_waits;` 将"谁持有锁（Blocking 事务及 SQL）"与"谁在苦苦等待锁（Blocked 事务及 SQL）"直接配对列出，DBA 可直接拿到对应线程 ID 执行 `KILL` 终止源头阻塞事务。

* **生产环境调用戒律**
    * > **注意**：严禁在生产环境高并发业务高峰期以高频轮询（如每秒一次）的方式自动化扫描 `sys` 视图。`sys` 视图底层基于复杂的嵌套查询和跨内存表汇聚统计，频繁调用自身就会消耗不可忽视的 CPU 和内存资源，甚至在底层数据字典表上引发锁竞争；正确姿势是把巡检脚本安排在夜间低峰期运行，或在排查突发故障时由工程师手动定点触发。

## 索引失效的 11 种情况


### 情况 1：全值匹配与联合索引的最长命中

* **规则与实测（`student` 表：`id` 主键，其余字段只有 `not null`/`null` 约束，无其他索引）**
    * 目标语句：`select ... from student where age = 30 and class_id = 4 and name = 'abcd';`
    * 无索引时：`type` 是 `all`、`key` 也是 `null`；针对 `age` 的查询同样没有任何索引可用，也没有 `using index` 之类字样。

| 索引情况 | `EXPLAIN` 里的 `key` | `key_len` | 实测查询耗时 |
| :--- | :--- | :--- | :--- |
| 不建索引 | `null`，`type=all` | — | 全表扫描 |
| 只建 `idx_age on student(age)` | `age` 上的索引 | 5（`int` 4 字节 + 允许 NULL 1 字节） | 0.022 秒 |
| 再建 `idx_age_class_id (age, class_id)` | 优化器选中更长的这条 | — | 0.001 秒 |
| 再建 `idx_age_class_id_name (age, class_id, name)` | 优化器选中最长的那条 | — | 0.002 秒 |

* **优化器选更长索引的原因**
    * 联合索引构建的 B+ 树先按 `age` 排序、再按 `class_id` 排序。只用 `age` 索引定位到 `age=30` 之后非叶子节点中没有 `class_id`，剩下的条件只能回表去找主键，耗时更多；用 `(age, class_id)` 索引时在 `age` 相同的情况下直接看非叶子节点里的 `class_id` 是不是 4 即可。
    * 第三步再建更长的联合索引后耗时反而略长（0.002 秒）的原因是：用前两个字段筛选完之后剩余数据量已极小，该查询甚至根本没查到数据，所以区分不出来；数据量达到几百万、几千万并且确实有匹配记录时应能看到更小。
    * > 结论：`WHERE` 条件都是等值比较时，把这几个字段建成一个联合索引，效率要比只建其中部分字段的索引更好；数据量越大越能看出差别。

### 情况 2：违背最佳左前缀法则

* **规则**
    * 联合索引中先写谁后写谁有严格区别；查询里要用上该联合索引必须先把左边字段考虑上，然后才能考虑下一个字段、再下一个字段。
    * 反过来说：最左边字段没有出现而直接出现后面某个字段时，该索引也有可能被考虑使用，但只能用上它最前面的那一部分。
    * > **易错点**：使用索引的过滤条件必须按照建立索引的顺序依次满足；一旦跳过某个字段，它后面的字段就都无法使用了。

* **实测判读**
    * 表上有 `(age, class_id, name)` 联合索引时，`WHERE age = 30 AND name = 'abcd'` 只用上 `age` 那部分索引（`key_len` 只有 5），因为 `name` 上没有单独索引；`WHERE` 里换成 `class_id` 或 `name` 则完全用不上索引（`type` 为 `all`）。
    * 疑问澄清：索引里虽然存了 `class_id` 和 `name` 但实际用不上——数据结构是先考虑 `age`、`age` 相同了才看 `class_id`，上来就 `class_id` 这棵树当然用不了。
    * `WHERE class_id, age, name` 三个条件都给上时用上了索引，与上面那条的区别就在于加上了 `age`：访问方法变成 `ref`，而用不上索引的那条是 `all`，效率差别比较大。
    * 清掉干扰索引后只剩 `(age, class_id, name)`，执行 `WHERE age = 30 AND name = 'abcd'`（无 `class_id`）时 `EXPLAIN` 选的就是这个索引，但 `key_len` 只写了 5——只考虑了 `age`；后面明明写了 `name` 却没考虑进去，因为在这棵树中 `age` 相同的情况下要先看 `class_id` 再去考虑 `name`，略过 `class_id` 直接找 `name` 就不合适。
    * > **提示**：一个索引最多可以有 16 个字段，默认情况下就是 16 个。

* **判定演示的联合索引比较顺序**

```text
    联合索引 (age, class_id, name)：B+ 树里的比较顺序

            先比 age        再比 class_id        最后比 name
           +---------+      +------------+      +------------+
    记录 1 |  age=30 | ---> | class_id=4 | ---> | name=abcd  |
    记录 2 |  age=30 | ---> | class_id=4 | ---> | name=abce  |
    记录 3 |  age=30 | ---> | class_id=7 | ---> | name=aaaa  |
    记录 4 |  age=31 | ---> | class_id=2 | ---> | name=bbbb  |
           +---------+      +------------+      +------------+

    只有先给出 age，才能进入下一层；跳过了 class_id 直接找 name，这一层就对不上了。
```


### 情况 3：主键插入顺序与页分裂

* **规则**
    * InnoDB 中数据存储都要按照聚簇索引的方式添加。主键值从小到大递增时始终在页面右边添加，右边不足时再新开辟数据页继续添加。
    * 主键值中间有空隙（如 8 后面空了个 9 直接到 10）而用户后来把 9 插入进来：索引默认升序排列，9 必须插到 8 和 10 之间；若该页数据也已满，这些数据就要考虑移到下一个页当中去，于是出现页分裂，然后再把 9 添加到那个位置——肯定会影响性能。
    * 实际开发建议：一定要让主键是依次递增的顺序，比较好的选择就是给主键加上 `auto_increment`；而 `auto_increment` 本身要求对应字段得是主键或者唯一约束的字段。

* **页分裂示意图**

```text
    数据页 P1（已满）
    +------+------+------+------+
    |  6   |  7   |  8   |  10  |     <- 主键 9 缺失
    +------+------+------+------+

    用户后插主键 9：索引按升序排列，9 必须落在 8 与 10 之间
                    |
                    v
    +------+------+------+------+
    |  6   |  7   |  8   |  9   |     P1：9 插进来了
    +------+------+------+------+
    +------+------+------+
    |  10  | ...  | ...  |              P2：从 P1 挪过来的记录
    +------+------+------+
                              ↑ 一部分记录被移到新页，页与页之间的指针也要一并维护
```

* > **定义**：页分裂是指插入的记录需要落在已经写满的数据页上时，把该页的一部分记录挪到新分配的页里，再完成这次插入；它带来额外的写入以及页指针维护开销。
* 前瞻：非核心业务的表可以考虑用 `auto_increment`，但核心业务的表（如订单表）针对主键用 `auto_increment` 就不是一个很好的选择。

### 情况 4：字段上的运算与函数

* **模糊查询：LIKE 前缀匹配与 LEFT 函数**
    * 先建索引 `create index idx_name on student(name);`，两条作用相同的语句对比：
    * `explain select ... from student where name like 'abc%';` → `key` 有值，`type` 是 `range`，还算不错的访问方法。
    * `explain select ... from student where left(name, 3) = 'abc';` → 全表访问，`key` 位置没有值。
    * 机理：`name` 上的 B+ 树按 `name` 排好序，`like 'abc%'` 可以从树里先定位到以 a 开头那一波、接着看第二个字符是 b 的、第三个字符是 c 的，然后从这一段里开始找；而 `left(name, 3)` 是在字段上作用函数再把结果跟另一个字符串比，函数作用的是什么优化器并不知道，只能老老实实把字段值一个个取出来、每取一个就作用一次函数取前三个字符再看是否等于 abc，一开始就根本无法锁定 bc 开头的那一段。

```text
    where name like 'abc%'
      -> 在按 name 排好序的 B+ 树里，直接定位到 a->b->c 这一段区间去取   （type=range，key 有值）

    where left(name, 3) = 'abc'
      -> 优化器不知道 left() 到底做了什么
      -> 只能逐行取出 name 的值 -> 作用函数 -> 再和 'abc' 比较
      -> 事先无法锁定 'abc' 开头的区间，只能一行行验              （type=all，key=null）
```


* **字段参与算术运算**
    * 先确保 `student_number` 上有索引：`create index idx_student_number on student(student_number);`。
    * `explain select ... from student where student_number + 1 = 900001;` → `key` 上也没有值，走全表扫描。
    * `explain select ... from student where student_number = 900000;` → 把加 1 挪到等号右边（左边减 1、右边也减 1，表达的是同一个意思），明显用上索引了；`student_number` 是 `NOT NULL` 限制、4 个字节。
    * 实测：后一条 `select` 是 0.042 秒，前一条要更多一些。
    * 机理：在现有字段上加了个值相当于要做一次运算；一做运算优化器就没办法直接拿着后面那个值去 B+ 树里找，只能把字段的值一个个都取出来再做运算。

* **函数条件下的 key_len 计算**
    * 针对 `name` 字段在字段上作用一个函数再等于 `abc`（`name` 上已建索引）→ `type` 是 `all`、`key` 是 `null`；建议写法是把前三个字符是 abc 表达成前缀匹配。
    * `name` 是 20 个字符、可以为 NULL、本身可变需要额外字节记录长度，所以 $20 \times 3 + 1 + 2 = 63$ 字节：每个字符最多 3 字节，加 1 字节 NULL 标志，再加 2 字节记录变长字段的长度。

* **共同根因**
    * `left(name, 3) = 'abc'`、`student_number + 1 = 900001`、`name = 123` 这三件事写法各不相同的失效，根子上是同一件事：字段没有以自己的原始值去参与 B+ 树的定位，而是先被算过一遍再拿去比较，有序结构也就没法用了。

### 情况 5：隐式类型转换

* **规则与实测**
    * `name` 上已有索引：`explain select ... from student where name = 123;`（`name` 是字符串类型、右边却写了数字）→ 还是 `all`，`key` 也是 `null`。
    * 加上单引号：`explain select ... from student where name = '123';` → `name` 本身就是字符串类型、右边也给字符串就不会出现类型转换，执行就用上索引了。
    * 机理：前者相当于先把这个字段上的值做了一个隐式的函数（做了一次转换）再拿去跟 123 做对比；既然一旦用上函数索引就失效，这里也是同一个道理。
    * > **提示**：想让索引持续有效，"字段上不加运算、字段上不加函数、比较时两边类型保持一致"这几条一定要考虑在内。

### 情况 6：范围条件右侧的列

* **规则**
    * 只要出现 `<`、`<=`、`>`、`>=`、`BETWEEN ... AND ...` 这一类范围条件，范围列自己能用上索引，它在索引里右边的列就用不上。
    * > **易错点**：这里的"右边"指的是索引里的右边，不是 `WHERE` 语句里的右边——看索引，不要看 SQL。

* **实测：`idx_age_classid_name (age, class_id, name)`，`age` 走等值、`class_id` 走范围、`name` 走等值**
    * 索引肯定用上了，关键看 `key_len` 是 `10`：`age` 是 `int` 且允许 `NULL`（$4+1=5$ 字节），`class_id` 同为 `int` 也允许 `NULL`（5 字节），两列相加正好 $5+5=10$。
    * `name` 若参与进来 `key_len` 还要再加上 63（字符内容按字符集最大宽度算、变长类型多记 2 字节长度、允许 `NULL` 再加 1 字节），现在这个 63 根本没被加上。
    * 卡住 `name` 的不是最左前缀，而是 `class_id` 上的范围条件：范围一旦出现，它在索引里右边的那些列就都用不上了。
    * 机理：叶子节点分层排序，先按 `age` 排、`age` 相同的再按 `class_id` 排、`class_id` 也相同的才按 `name` 排；给定 `age = 常量` 拿到的是 `age` 那一段连续区间，再要求 `class_id > 常量` 就是从这段区间里取出 `class_id` 更大的一截；这一截内部 `name` 只在同一个 `class_id` 之内有序，跨过 `class_id` 边界就重新从头排起，于是它在整个结果区间里并非全局有序，树上根本没有一段连续区间对应"`name = 常量`"。

* **联合索引叶子节点排序示意**

```text
    联合索引叶子节点排序 (age, class_id, name)
        age=20, class_id=3, name='aaa'
        age=20, class_id=3, name='bbb'
        age=20, class_id=5, name='aaa'   <-- 跨过 class_id 边界，name 重新排起
        age=20, class_id=5, name='ccc'
        age=20, class_id=9, name='bbb'

    age = 20 且 class_id > 3 的命中区间：从第 3 行往下全部
        -> 该区间内 name 并非全局有序，无法据此定位
        -> 索引只负责 age、class_id；name 留到回表之后逐行过滤
```


* **抢救方式：调整索引列序而非 WHERE 顺序**
    * 调整 `WHERE` 里条件的书写顺序没有任何意义：对优化器来说这几个条件谁先写谁后写无所谓，它自己会去颠倒顺序；真正颠倒不了的是索引里的列顺序。
    * 办法在建索引这一步就能解决：把确定的等值字段列在前面、范围字段放到最后——重建 `CREATE INDEX idx_age_name_cid ON student(age, name, class_id);` 后用同样的查询，`key` 换成新索引、`key_len` 从 `10` 变成 `73`（$5 + 63 + 5 = 73$），三列全用上了。
    * 范围条件写在 `WHERE` 中间（夹在等值条件之间）也还能用上新索引、`key_len` 依旧是 `73`，因为条件之间是 `AND`，优化器会自动交换：先考虑等值，最后才考虑范围。所以顺序这件事只管索引里的，不用管 `WHERE` 里的。

| 索引列序 | WHERE 条件形态 | `key_len` | 实际用上的列 |
| :--- | :--- | :--- | :--- |
| `(age, class_id, name)` | `age` 等值、`class_id` 范围、`name` 等值 | `10` | `age`、`class_id` |
| `(age, name, class_id)` | 同上 | `73` | `age`、`name`、`class_id` |

* 这条规则在实际开发里几乎躲不开——查金额、查日期往往都是范围；真正要落到索引上的动作只有一句：创建联合索引时务必把范围字段写在最后。

### 情况 7：不等于运算符

* **规则与实测**
    * `name` 上建好索引后 `SELECT * FROM student WHERE name = 'abc';` 肯定能用上索引；把 `=` 换成 `!=` 就用不上，`type` 退化成 `ALL`；换成另一个写法 `<>` 结果一样。
    * 机理：在 B+ 树里要"等于 `abc`"直接顺着树找到等于 `abc` 的那些项就完了；可"不等于 `abc`"树上并没有哪一个连续区间正好对应它，只能一条条记录去比，既然要一条条比那还不如干脆全表扫描。

| WHERE 写法 | 执行计划 |
| :--- | :--- |
| `name = 'abc'` | 走 `name` 上的索引 |
| `name != 'abc'` | `type = ALL`，全表扫描 |
| `name <> 'abc'` | `type = ALL`，全表扫描 |

### 情况 8：IS NULL 与 IS NOT NULL / NOT LIKE

* **规则与实测**
    * `age` 上没有单独索引，但以 `age` 打头的联合索引正好可用来验证：`SELECT * FROM student WHERE age IS NULL;` 用上了索引，走的就是那个联合索引，而且只用到第一个字段 `age`，`key_len` 是 `5`（`int` 加上允许为 `NULL` 的那 1 个字节）。
    * 换成 `SELECT * FROM student WHERE age IS NOT NULL;` 索引就没了，还是 `ALL` 全表扫描。
    * 机理：`IS NULL` 相当于"等于某个值"，在 B+ 树里直接去找 `NULL` 所在的位置就行；`IS NOT NULL` 相当于"不等于某个值"，树上同样没有对应的连续区间，只能一个个看过去。
    * > **定义**：可以把 `IS NULL` 当成一次等值匹配，把 `IS NOT NULL` 当成一次不等值匹配；`!=` 与 `IS NOT NULL` 失效的根子是同一个——不等值在 B+ 树上没有可下探的连续区间。
    * `NOT LIKE` 也一样：凡是带 `NOT` 的、非的，都只能全表扫描。

* **建表经验与 NULL 替代值**
    * 设计数据表时通常给字段都加上 `NOT NULL` 约束：既然所有数据都满足非空，查询时就不必再写 `IS NOT NULL` 这个条件，直接写其他过滤条件，该建索引建索引，索引就能用上。
    * 确实需要"没有值"这个语义时用等价的替代值：数值类型设成 `0`，字符串类型设成一对单引号里什么都不放的空串；用这种写法替换原来 `NULL` 的场景，索引照样能用。

### 情况 9：以通配符 % 开头的 LIKE

* **规则与实测**
    * `name` 上有索引时：`LIKE 'abc%'` 走索引、`type` 是 `range`（范围扫描）；一旦在最前面加上一个百分号，不管是 `'%abc'` 还是 `'%abc%'`，索引就用不上、退化成全表扫描。后面加不加百分号都无所谓，关键是开头是不是通配符。
    * 机理：树上逐层比较键值——比 A 大、比 A 小、还是等于 A，每一步都要有一个确定的起点；`'abc%'` 的开头是确定的所以能一路下探，`'%abc'` 一上来就不确定，第一个该不该走都判断不了，那还不如把数据一条条取出来过一遍。
    * 规范：阿里巴巴开发手册对此强制要求——页面搜索严禁左模糊或者全模糊；业务上非要用这种匹配就别在 SQL 上硬扛，交给搜索引擎去做。

```text
    LIKE 'abc%'   前缀确定
        根节点 -> 逐层比较 'ab' / 'abc' / 'abd' -> 沿确定路径下探
        结果：命中一段连续的索引区间        -> 走索引 (range)

    LIKE '%abc'   前缀不确定
        起点无法确定 -> 树上没有可下探的分支
        结果：只能逐行取出做字符串匹配      -> 全表扫描 (ALL)
```

* 前后对比参照：`WHERE name LIKE 'abc%'` 能走索引（前缀确定）；`WHERE name LIKE '%abc'` 与 `WHERE name LIKE '%abc%'` 走不了、全表扫描。

### 情况 10：OR 两侧存在非索引列

* **规则与实测**
    * 只针对 `age`、`class_id` 中的一个字段建索引（建哪个都无所谓、效果一样）：`CREATE INDEX idx_age ON student(age);`。
    * `SELECT * FROM student WHERE age = 20 OR class_id = 3;` 用不上索引，`type` 是 `ALL`。
    * 机理：`OR` 取的是并集——两边的数据全都要；一侧有索引一侧没有时，有索引的那侧先把结果捞出来，没索引的那侧照样得全表扫描，两段开销加在一起还不如直接来一遍全表扫描快；既然怎么算都不划算，优化器干脆不碰索引了。
    * 让 `OR` 用上索引的方式是让两侧字段都有索引：再 `CREATE INDEX idx_class_id ON student(class_id);` 后同一条 SQL 的 `type` 变成 `index_merge`（索引合并），`Extra` 里会出现 `using union`；索引真正起作用了，查询效率比全表扫描高。

```text
    WHERE age = 20 OR class_id = 3
                |
                +--> idx_age         --\
                |                      >-- index_merge (using union) --> 结果并集
                +--> idx_class_id    --/
```

* 只有两侧都有索引可取这条路径才成立；只要有一侧没索引，整条 SQL 就退回全表扫描。

### 情况 11：字符集不统一

* **规则**
    * 数据库和表的字符集要统一，统一使用 `utf8mb4`，用 `utf8mb3` 也行，重点是一定要统一。
    * 机理：不同字符集的字段在比较之前一定会先做一次字符集转换；一旦涉及转换就相当于在比较的时候用上了一个转换函数，而字段上套了函数索引就失效了。
    * 这条主要针对 MySQL 8.0（默认字符集就是 `utf8mb4`）。
    * > **提示**：这是隐含在每一条 SQL 里的坑——库与表、表与表、字段与字段的字符集只要不一致，等值比较和连接条件都可能因为这个隐式转换把索引丢掉。

* **11 种失效形态的根因与处置汇总**

| 失效形态 | 根因 | 处置 |
| :--- | :--- | :--- |
| 范围条件右侧的列用不上 | 范围列右边的列在命中区间里失去全局有序性 | 建联合索引时把范围字段放到最后 |
| `!=`、`<>` | 不等值在 B+ 树上没有可连续下探的区间 | 尽量改写成等值匹配 |
| `IS NOT NULL`、`NOT LIKE` | 等价于一次不等值匹配 | 字段加 `NOT NULL`；用 `0` 或空串替代 `NULL` |
| 以 `%` 开头的 `LIKE` | 匹配没有确定前缀，树上无法选择分支 | 改成右模糊 `'abc%'`，或交给搜索引擎 |
| `OR` 两侧存在非索引列 | 无索引那侧仍要全表扫描，总代价反而更高 | 两侧字段都建索引，走 `index_merge` |
| 库表字符集不一致 | 比较前发生字符集转换，相当于在列上套了函数 | 库、表、字段统一用 `utf8mb4` |
| 字段上套函数/运算 | 字段未以原始值参与 B+ 树定位，有序结构无法利用 | 改写为前缀匹配或把运算移到等号右侧 |
| 隐式类型转换 | 比较时在字段上注入了转换函数 | 常量类型与字段定义完全一致 |


### 联合索引可用性的统一判读法

* **两条推理依据**
    * 最左前缀：从索引最左列开始，连续命中等值条件，命中到哪一列就用到哪一列；中间跳掉一列，后面的列就都不参与。
    * 范围截断：某一列上出现范围条件（`>`、`<`、`BETWEEN ... AND ...` 等），这一列自己能用上，它在索引里右边的列全部用不上。

* **前置排除清单**
    * 判断任何一条写法之前，先排除那些会让索引直接失效的形态：字段上套函数或做运算、类型或字符集不一致引起的隐式转换、否定条件（`!=`、`<>`、`IS NOT NULL`、`NOT LIKE`）、以 `%` 开头的 `LIKE`，以及 `OR` 两侧存在没有索引的列。

* **四类经验建议**
    * 单列索引：`WHERE` 里写了一串条件而表上只有单列索引时，选择针对当前 query 过滤性最好的那个（优化器自己也会这么做）。
    * 联合索引列序：当前 query 中过滤性最好的字段位置越靠前越好。
    * 联合索引字段数：尽量选择包含当前 query 中 `WHERE` 子句里更多字段的那一个。
    * 联合索引范围列：组合索引里如果某个字段会出现范围条件，尽量把这个字段放到后面。

* **判读心法**
    * 判断索引失效这件事，脑子里有一棵 B+ 树就够了：能不能在树上找到一条可以连续下探的路径，找得到就走索引，找不到就退化成全表扫描。
    * 最容易错的是这两类：`a`、`b` 同时出现的等值写法是能用上索引的；有一类写法看着把条件都写了，实际上只能用到 `a` 这一段、`b` 那一段就用不上了。

* **索引选择的成本依据**
    * 用不用索引最终还是优化器说了算：SQL 写完了、字段上确实也有索引，但优化器一算发现不用索引的成本可能更低，它还真就可能不用。它基于成本开销（cost）做选择，不是基于规则式，也不是基于语义式。
    * 遇到"明明建了索引，结果还不如不建"的情况，要反过来想一想：是不是索引设置本身有问题，才让优化器把它放弃了。
    * SQL 语句是否使用索引跟数据库版本、数据量、数据的选择度都有关系。

## 连接查询优化


### 多表连接的分类与演示环境

* **分类与本讲收敛**
    * 多表连接从内外角度分为内连接和外连接；外连接再分为左外连接、右外连接和满外连接。
    * MySQL 里没有一条直接的满外连接语法，得用 `UNION` 把两侧结果拼起来，本质上是"组合"，且拼起来的两半各自就是外连接，因此不必单独讨论。
    * 右外连接把两个表的位置交换一下就可以改写成左外连接，两者能力等价，所以外连接这一支只拿左外连接当代表。

* **演示环境（两表各 20 条数据）**

| 表名 | 主键 | 参与连接的字段 | 索引情况 | 初始行数 |
| :--- | :--- | :--- | :--- | :--- |
| `type` | `id` | `card` | 无任何索引 | 20 |
| `book` | `book_id` | `card` | 无任何索引 | 20 |

* 数据量故意做小，因为这里要对比的不是"用索引和不用索引性能差多少"，而是谁做驱动表、谁做被驱动表；行数一大执行计划反而不好读，成本差异也容易被掩盖。
* 两张表的主键在这次连接里帮不上忙：连接条件用的是 `card` 而不是 `type.id` 或 `book.book_id`，所以主键索引对这次连接没有任何贡献，能不能用上索引全看 `card` 上有没有——这也是初始状态下两边访问方法都是 `ALL` 的原因。
* 两张表的主键名字不一样（`id` 与 `book_id`）但连接字段同名都叫 `card`；字段名同不同名其实无关紧要。

### 无索引时的左外连接执行过程

* **嵌套循环的匹配账**
    * 假设 `type` 有 20 行、`book` 有 30 行：先从 `type` 里取一条记录，拿它的 `card` 值到 `book` 里按连接条件找匹配；而 `book.card` 上没有索引，这一趟只能把 `book` 整表遍历一遍（30 行）。接着从 `type` 取第二条，`book` 那边又是一次整表遍历……

```text
    驱动表 type（外层循环，访问方法 ALL）
        |
        |  取第 1 条记录  ->  按 type.card = book.card 去被驱动表匹配
        |  取第 2 条记录  ->  按 type.card = book.card 去被驱动表匹配
        |  ...
        |  取第 20 条记录 ->  按 type.card = book.card 去被驱动表匹配
        v
    被驱动表 book（内层循环，card 上无索引 -> 每次匹配整表扫 30 行）
        |
        v
    被驱动表累计被访问 20 x 30 = 600 行
```

* 600 就是没有索引时这条语句要付出的代价量级：驱动表只扫一遍（20 行），被驱动表却要被扫 20 遍。
* 两张表都没有索引时"谁做驱动表"看不出区别：让 `type` 驱动总访问量是 $20 \times 30$，让 `book` 驱动是 $30 \times 20$——同一个数。真正让驱动表位置变得值钱的是被驱动表上有了索引之后：内层不再整表扫而是一次查找，总代价由外层行数乘上一个 $\log$ 级别的查找成本决定。
* > **易错点**：内层循环的代价会被驱动表的行数放大，所以被驱动表上有没有可用的索引比驱动表本身怎么扫重要得多。

* **join buffer 与哈希连接**
    * 被驱动表要被反复遍历，优化器在这里做了优化处理：用 join buffer 把数据缓存起来，配合哈希连接（Hash Join）的方式，让每次探测不必再从表头扫起。
    * 哈希连接的做法是把参与连接的数据按连接字段整理成一张哈希表，再让另一侧的记录直接拿 `card` 的值去哈希表里探测，平均一次探测就能定位到匹配的记录，不必再逐行比对；join buffer 就是给这类批量匹配留出来的内存缓冲。
    * > **提示**：join buffer 是优化器在内存里划出来的一块缓冲，哈希连接是使用这块缓冲的算法——在被驱动表的等值连接字段上没有可用索引时，用哈希表代替反复扫表。
    * 这个优化不会改变"两张表的访问方法都是 `ALL`"这个观察结果：`EXPLAIN` 里看到的仍然全是 `ALL`；判断一条没有索引的连接语句主要就是看 `ALL` 出现在哪张表上。

### 在被驱动表上添加索引

* **实测变化**
    * `CREATE INDEX Y ON book(card);`（等价写法 `ALTER TABLE book ADD INDEX Y(card);`；索引名取 `Y`、给 `type` 加的取 `X`，只为区分两张表上的索引、方便对号）。

| 位置 | 表 | 访问方法 | key | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| 驱动表 | `type` | `ALL` | 无 | 仍然是全表扫描 |
| 被驱动表 | `book` | `ref` | `Y` | 走索引做等值匹配，性能相当不错 |

* **成本再算细一点**
    * 索引没加之前被驱动表每次探测读 30 行，20 次探测总共 600 行；加索引之后每次探测退化成 B+ 树上的一次查找，$\log_2 30$ 大约是 5 次比较，20 次探测总共 100 次左右——同样的结果集代价掉到原来的六分之一量级；驱动表行数越多、被驱动表越大，差距还会继续拉开。
    * 驱动表那一侧 `card` 上的索引也能被利用，`Extra` 里会出现 `Using index` 这样的提示。
    * > **提示**：能否形成覆盖索引取决于查询到底用到哪些列；只要有一列不在索引里就还得回表取数据，`Using index` 也就不会出现。
    * 驱动表毕竟是走 `ALL` 全表扫描的，但这里有个讲究：左外连接本来就要求左表的数据全部保留（除了两张表都匹配上的记录，左表里没匹配上的记录也要留下来），那驱动表走 `ALL` 把数据一条条过一遍、被驱动表用上索引，其实是一个比较好的选择。

* **索引归属的铁律**
    * > 结论：如果两个连接字段上只能加一个索引，那这个索引一定要加给**被驱动表**。
    * 原因：驱动表只被完整读一遍，在它身上装索引收益仅是把那一次全表扫描换成一次索引扫描；而被驱动表要被探测 N 遍（N 就是驱动表的行数），索引装在它身上收益要乘以 N——同样一个索引，装在会被反复探测的那一侧收益才被放大。

* **连接字段的类型一致性要求**
    * 两张表连接字段的名字可以不一样，但类型一定要相同。
    * > **易错点**：两侧字段类型不一致时连接要做隐式类型转换，相当于给字段套了一层函数，直接掉进索引失效场景。一边是字符串类型、另一边是数值类型时，MySQL 在比较之前必须把字符串转成数值，这个转换落在字段值上，`card` 上的索引自然用不上了。设计多表连接时只要有连接关系就让连接字段类型保持一致；字段名不同没有关系。
    * > **易错点**：`type` 是 MySQL 的关键字，表名不加反引号分隔符会直接报"表不存在"；实际开发要么给表起名时避开关键字，要么老老实实把反引号加上。

### 左外连接中驱动表的固定角色

* **规则**
    * 在左外连接里左边的表就是驱动表、右边的表就是被驱动表——角色是定死的。
    * 定死的原因是语义：左外连接要求左表的数据全部出现在结果集中，左表就必须先被完整地读出来当外层，优化器没有把左表塞进内层的自由。
    * 删掉 `book` 上的索引（`DROP INDEX Y ON book;`）后被驱动表那一位又变回 `ALL`——索引一没，被驱动表只能退回 join buffer 加哈希连接那条路。

```text
    左外连接：两个表的位置由写法决定，不由优化器决定
        type（左表，驱动表，访问方法 ALL）
             |
             |  左表的每一行都必须留在结果集里
             v
        book（右表，被驱动表）
             |
             +-- 有索引   -> ref
             +-- 无索引   -> join buffer + 哈希连接
```

* 左外连接里两边的角色被写法钉住了，能变的只有被驱动表用什么方式访问。

### 内连接中优化器的驱动表决策

* **两张表的对等地位**
    * 左外连接里两张表有角色区别、左表的数据必须全要；内连接只取两张表共同匹配的那部分，左右两边地位一样。
    * 地位一样优化器就有决策权了：让谁做驱动表、让谁做被驱动表，两种方案都列出来算一算成本，选成本较低的那一个。
    * 实测：两张表 `card` 上都没有索引时 `EXPLAIN` 里两张表都是 `ALL`（`type` 在上、`book` 在下），跟左外连接最初的样子几乎一样；把 `book` 的索引加回来被驱动表那一位就出现 `ref`、`key = Y`；再给 `type` 加上索引后两张表的先后顺序可能跟别人那儿不一样，甚至同一份脚本、同一台机器上再跑一次也可能互换——顺序有变化不代表它是随机的，优化器是把两种方案的成本都算过一遍才决定谁上谁下，变的只是成本估算的输入。

```text
    内连接：两张表连接字段上的索引情况
        |
        +-- 只有一个字段有索引 ----> 有索引的那张表做被驱动表
        |
        +-- 两个字段都有索引 ------> 按成本计算，小表做驱动表
        |
        +-- 两个字段都没有索引 ----> 两张表访问方法都是 ALL，
                                    被驱动表靠 join buffer + 哈希连接兜底
```

* 最后一条路径是与外连接共有的，前两条才是内连接独有的决策空间。

* **连接字段上只有一个索引时**
    * 把 `book` 上的索引删掉、`type` 上的留着再执行一次：两张表的位置换了——原本 `book` 在下面，删掉它的索引之后 `type` 跑到了下面，成了被驱动表。
    * 场景 A（只有 `book.card` 上有索引）：`type` 驱动表走 `ALL`，`book` 被驱动表走 `ref`、用上 `key = Y`。
    * 场景 B（只有 `type.card` 上有索引）：`book` 驱动表走 `ALL`，`type` 被驱动表走 `ref`、用上 `key = X`。
    * > 结论：内连接的连接条件里如果只能有一个字段有索引，那么有索引的那个字段所在的表会被当作被驱动表出现。
    * 这不是随机结果而是成本算出来的：驱动表只会被完整读一遍，在它身上装索引收益仅是把那一次全表扫描换成一次索引扫描；而被驱动表要被探测 N 遍，收益要乘以 N。

* **两个连接字段都有索引：小表驱动大表**
    * 往位置在上面那张表（这里 `type` 在上面）再插 20 条数据，插完 `type` 40 行、`book` 20 行；再执行 `EXPLAIN`，`type` 跑到下面去了——数据量变了之后谁做驱动表、谁做被驱动表也跟着变了。
    * > 结论：内连接中两个连接字段上都有索引时，优化器会选择小表作为驱动表——这就是"小表驱动大表"；这里的"小"说的是数据量（行数）小，优化器最终比较的是成本，行数只是其中最直观的一个输入。
    * 成本账：驱动表每取出一条记录被驱动表就要按索引探测一次，探测次数约等于驱动表行数，每次探测代价是 $\log(\text{被驱动表行数})$ 量级。
    * 小表（20 行）在外层：$20 \times \log_2 40 \approx 20 \times 5.32 \approx 106$；大表（40 行）在外层：$40 \times \log_2 20 \approx 40 \times 4.32 \approx 173$——驱动表行数在成本里充当乘数，把行数少的那张放在外层总代价更小。

* **两类连接的驱动表决策对照**

| 对比项 | 左外连接 | 内连接 |
| :--- | :--- | :--- |
| 结果集 | 左表全部记录，加上右表能匹配上的记录 | 两张表都能匹配上的记录 |
| 两张表的地位 | 不同，左表数据必须全部保留 | 相同，只取共同匹配的部分 |
| 驱动表由谁决定 | 固定是左表 | 查询优化器按成本决定 |
| 被驱动表由谁决定 | 固定是右表 | 查询优化器按成本决定 |
| 连接字段只有一个有索引 | 索引要加在被驱动表上 | 有索引的那张表做被驱动表 |
| 连接字段都有索引 | 驱动表仍走 `ALL`，被驱动表走 `ref` | 小表做驱动表（小表驱动大表） |
| 连接字段都没有索引 | 驱动表 `ALL`，被驱动表靠 join buffer 加哈希连接 | 两张表都是 `ALL`，被驱动表同样靠 join buffer 加哈希连接 |


### 判定顺序与改写手段

* **内连接不保证书写顺序**
    * 内连接写 `a JOIN b`，`a` 不一定是驱动表——如果 `b` 才是小表，那 `b` 就成为驱动表。

* **STRAIGHT_JOIN 固定顺序**
    ```sql
      SELECT ... FROM t1 STRAIGHT_JOIN t2 ON t1.b = t2.b ...
      ```
    * 明确要求优化器不要破坏书写的前后顺序：写成 `t1 STRAIGHT_JOIN t2` 就是让 `t1` 充当驱动表、`t2` 充当被驱动表；反过来写就倒过来。
    * > **提示**：`STRAIGHT_JOIN` 的价值不是"提速"，而是固定顺序——怀疑优化器选错了驱动表时用它把顺序钉死，再去看成本差异。
    * 外连接也可被优化器改写（详见「14.1 SHOW WARNINGS 探查优化器重写实录」）。

* **判定对象是 EXPLAIN 而不是 SQL 写法**
    * 外连接要分左右来看：`a LEFT JOIN b` 跟 `b RIGHT JOIN a` 仅从字面上看，如果优化器没有改顺序，可以说 `a` 相当于驱动表的位置、`b` 相当于被驱动表的位置；但优化器同样会改外连接，所以外连接里写在前面那张表不一定是驱动表。

### Simple NLJ 与 Index NLJ

* **Simple NLJ（简单嵌套循环连接）**
    * JOIN 操作本质上就是一次循环匹配：从驱动表里取出一条数据，拿去和被驱动表里每一条记录一条条做连接；`a` 和 `b` 都没有任何索引时就是全表遍历——来一条数据全表遍历一遍，再来一条再遍历一遍。
    * 成本账（过滤完之后 `a` 有 100 条、`b` 有 1000 条）：外表扫描次数 $1$（整体扫一遍表 `a`）；内表扫描次数 $a$ 即 100；读取记录数 $a + a \times b$ 即 $100 + 100 \times 1000$；JOIN 比较次数 $a \times b$ 即 100000 次；回表次数 0（不涉及索引就没有回表这回事）。
    * 这是最简单直接的算法，性能也最差。
    * 从读取记录数 $a + a \times b$ 可看出 `a` 出现在两层里、是影响因子更大的那一个，自然 `a` 越小越好——这就是"小表驱动大表"在数理上的出处。

* **Index NLJ（索引嵌套循环连接）**
    * 目的很直接：减少内层表数据的匹配次数。做法是给要当被驱动表的那张表的连接字段加索引——从 `a` 表取一条记录直接拿 `b.b` 去索引里找，走 B+ 树定位很快就能命中，而不是一条一条做遍历。
    * 成本账：外表扫描次数仍为 $1$；内表扫描次数 $0$（不用再扫全表，直接找索引走 B+ 树）；读取记录数 $a + b_{match}$；JOIN 比较次数 $a \times \text{index\_height}$（B+ 树有几层，来一条记录就往下走几层，三层就乘 3）；回表次数——主键索引为 $0$，二级索引则等于匹配到的条数。
    * > **易错点**：如果 `b` 字段上建的是非主键索引（非聚簇索引、二级索引、辅助索引），最终要 `SELECT` 的信息可能还得回表一次；如果 `b` 字段恰好就是主键，那就完全不用回表，性能更高。
    * 两种把它打回原形的情况：没加索引，直接崩回 Simple；加了索引但索引失效（SQL 写法有误导致），同样退回 Simple。

### Block NLJ 与两类参数

* **Block NLJ（块嵌套循环连接）**

```text
    驱动表 a（100 条）
    +----+----+----+ ... +----+   +----+----+ ... +----+
    | a1 | a2 | a3 |     | a40|   | a41| a42|     | a100|
    +----+----+----+ ... +----+   +----+----+ ... +----+
            |                              |
            v  第 1 块（40 条）             v  第 2 块（40 条）     第 3 块（20 条）
      +---------------------+        +---------------------+   +-------------+
      |     join buffer     |        |     join buffer     |   | join buffer |
      +---------------------+        +---------------------+   +-------------+
            |                              |                        |
            v  整表加载一次                 v  整表加载一次             v  整表加载一次
      +-------------------------------------------------------------+
      |              被驱动表 b（1000 条）—— 共加载 3 次              |
      +-------------------------------------------------------------+
```

* 针对的场景：Simple 里从 `a` 表取一条数据、把 `b` 表的数据加载到内存让这一条 `a` 走一遍比对，比完之后加载进来的这份 `b` 数据就被清掉了，第二条 `a` 来了再加载一遍 `b`，I/O 次数非常高。
* 思路转变：不再控制被加载的次数（它直接关联 `a` 表的条目数，不是能控制的），而是控制一次加载进内存的条目数——原来一条一条加，现在一块一块地加。100 条一次来 60 条则分两次加载；切法是 40、40、20 则三次；极端一点一次把 100 条全加载进来就被完整缓存住，被驱动表 `b` 拿进内存一次就把比较做完，不用销毁再加载。能不能一次装完就看缓冲池大小——也就是 `join buffer`。
* 成本账：外表扫描次数 $1$；内表扫描次数 $\dfrac{a \times \text{used\_column\_size}}{\text{join\_buffer\_size}} + 1$（前半是分了几块，后半那个 $1$ 是被驱动表本身也要扫一次）；读取记录数 $a + b \times \text{分块数}$；JOIN 比较次数 $b \times a$（和 Simple 一样）；回表次数 $0$。
* Block NLJ 比 Simple 好很多，这是没有疑问的。

* **两个相关参数**
    * `SHOW VARIABLES LIKE 'block_nested_loop';` 决定是否使用 Block NLJ，查到它是 `on`（启用状态），启用之后才能用这套算法。
    * `SHOW VARIABLES LIKE 'join_buffer_size';` 查看 join buffer 的大小，默认 **256K**，可以用 `SET` 调大。
    * 上限：join buffer 的上限在 32 位系统上是 4 个 G；64 位系统下可以申请大于 4 个 G，但 Windows 下比较特别——即便是 64 位也还是 4 个 G 的上限，多出来的部分会被截断。
    * > **注意**：join buffer 里放的不只是驱动表的连接字段。除了 `a` 本身，`SELECT` 里涉及驱动表的那些字段也要放进去；所以没用的字段就别多写，上来一个 `SELECT *` 很崩溃——它把 join buffer 占满，一次能装的条目数就变少。
    * > **注意**：如果有 $n$ 个 JOIN（$n$ 张表做连接），就会有 $n - 1$ 个 join buffer。

* **三类算法的成本对照**

| 成本项 | Simple NLJ | Index NLJ | Block NLJ |
| :--- | :--- | :--- | :--- |
| 外表扫描次数 | $1$ | $1$ | $1$ |
| 内表扫描次数 | $a$ | $0$ | $\dfrac{a \times \text{used\_column\_size}}{\text{join\_buffer\_size}} + 1$ |
| 读取记录数 | $a + a \times b$ | $a + b_{match}$ | $a + b \times \text{分块数}$ |
| JOIN 比较次数 | $a \times b$ | $a \times \text{index\_height}$ | $b \times a$ |
| 回表次数 | $0$ | 二级索引为 $b_{match}$，主键为 $0$ | $0$ |

* > 结论：整体效率上 Index NLJ 好于 Block NLJ，Block NLJ 好于 Simple NLJ。

### 小表驱动大表的精确化

* **从表行数到结果集大小**
    * 严格来讲"小表驱动大表"这句话是不精确的；更精确的说法是：小的结果集驱动大的结果集。
    * 示例：`a` 表 100 行、`b` 表 1000 行，`a` 是小表；但连接之后加了 `WHERE` 对 `b` 的某个字段做限制、过滤完 `b` 只查出 50 行，再拿这 50 行去跟 `a` 关联时，谁小谁大就要看过滤之后的数据。
    * > 结论：不该说哪个表大哪个表小，而要说结果集——过滤完得到的小结果集才是那个"小"。

* **行数乘以行大小**
    * 真正意义上的谁小谁大应该是表的行数乘以每行的大小：往 join buffer 里放的时候每一条数据越小越好，行大小决定同样 buffer 里能塞进多少条目，条目越多攒满 buffer 所需的分块数就越少。
    * > **提示**：行的"大小"要按实际用到的字段算——连接字段加上 `SELECT` 里涉及的驱动表字段，这两部分才是真正要放进 join buffer 的内容。

* **STRAIGHT_JOIN 的对照实验（两表条件完全一样，区别在书写顺序与 SELECT 字段）**

| 写法 | 驱动表 | 被驱动表 | `SELECT` 查出来的字段 | 谁当驱动表更合适 |
| :--- | :--- | :--- | :--- | :--- |
| `t1 STRAIGHT_JOIN t2` | `t1` | `t2` | `t1` 只查 `b` 这个字段 | 推荐这一种 |
| `t2 STRAIGHT_JOIN t1` | `t2` | `t1` | `t2` 查了它所有字段（字段很多） | 不推荐 |

* 推荐第一种的原因：把 `t1` 当驱动表，往 join buffer 里放的时候只需要放 `b` 这一个字段（关联条件也正好是 `b`），相同 buffer 大小下能放的条目数就更多；反过来用 `t2` 当驱动表，它涉及字段很多、一行数据占的空间大，能放的条目数就变少。
* > 结论：小表驱动大表的本质，是减少外层循环的数据数量。

* **三条优化原则**
    * 小的结果集驱动大的结果集——减少外层循环的数据量。
    * 给被驱动表的匹配条件加索引——以上结论都是在两个表都没有索引的前提下谈的；一旦给被驱动表的匹配字段加上索引就进入了 Index NLJ 场景，内层循环次数大幅减少。
    * 减少驱动表不必要的字段查询——只查必要的字段每行占的空间就小，一次能装的条目数就多；再配合加大 `join buffer` 的 size，一次缓存的数据更多，分摊下来成本更低。

### MySQL 8.0 的 Hash Join 与版本差异

* **Hash Join 的原理与限制**
    * 优化器把两个表中较小的那个表利用 join key 在内存中建立一个散列表（哈希表），然后扫描较大的那个表并探测这个散列表，找出与哈希表匹配的行。
    * > 结论：数据集比较小的时候 NLJ 那套还可以；一旦数据集比较大，推荐的就是 Hash Join。
    * > **易错点**：Hash Join 只能做等值连接。
    * 数据量大时因为它就是针对大表场景适用的，可能会占用临时空间，比如使用不同的区域、临时段这类机制。

* **版本与默认行为的对应关系**

| MySQL 版本 | 大表连接默认走什么 | 说明 |
| :--- | :--- | :--- |
| 5.7 | Block NLJ | `EXPLAIN` 显示 `using join buffer`，即块嵌套循环 |
| 8.0.18 及以后 | Hash Join | 明确开始使用 Hash Join |
| 8.0.20 及以后 | Hash Join | 废弃了 Block NLJ 这种方式，主要用 Hash Join（8.0.25 / 8.0.26 实测可见） |

* 现象差异：MySQL 8.0.25、8.0.26 这类 8.0 版本的 `EXPLAIN` 里看到的不是 `using join buffer (Block Nested Loop)` 而是 `hash join`；换到 5.7 重建库表数据再跑同样的测试，`EXPLAIN` 里呈现的就是 Block NLJ。

### Hash Join 与连接算法选择

* **Hash Join 与 Nested-Loop 的分界**
    * 版本与规模两条线索共同决定了走哪套算法：5.7 及 8.0.18 之前的大表连接走 Block NLJ，8.0.18 及以后（尤其 8.0.20 及以后）走 Hash Join，且 Hash Join 只支持等值连接。

* **选择顺序**
    * 被驱动表连接字段上有可用索引时进入 Index NLJ 场景（内层扫描次数为 0，比较次数为 $a \times \text{index\_height}$）。
    * 没有索引时按版本兜底：5.7 走 Block NLJ（受 `block_nested_loop` 与 `join_buffer_size` 约束），8.0.18 及以后走 Hash Join。
    * 无论哪种兜底算法，优化手段都回到同一件事：给被驱动表的连接字段建索引、减少驱动表放不必要字段。

## 子查询与排序分组优化


### 子查询的开销与 JOIN 改写

* **子查询的两项主要开销**
    * 执行子查询时针对内层查询通常需要建立一张临时表：建表要开销、用完还得销毁，整个过程中消耗过多的 CPU 与 I/O 资源，往往就是产生慢查询的主要源头；同一时间它还占着内存空间。
    * 针对这张临时表没办法建立索引：没有索引可用，一旦临时表比较大（结果集比较大），对性能的影响非常大。

* **改写方向**
    * 实际开发中可以考虑把子查询再拆解成多个查询，拆解的过程中使用 JOIN 操作，也就是用多表连接的方式替代子查询；一个搞不定就拆成多个。
    * 然后在多表连接里把前面的规则用上：小表驱动大表、被驱动表上有索引等等。
    * 用 JOIN 替代子查询最直接的好处是不用再建临时表，而且速度比子查询要快——因为连接里还能创建索引。

* **IN 子查询的物化过程（8.0 演示）**
    * 先在 `class` 表的 `monitor` 字段（存每个班的班长）上建索引：`create index idx_monitor on class(monitor);`。
    ```sql
      select *
      from student
      where number in (
          select monitor
          from class
          where monitor is not null
      );
      ```
    * `EXPLAIN` 有两处值得看：`select_type` 出现了 `materialized`（执行子查询时对内层查询做一次物化，物化之后的结果再和外层查询做连接）；另一处是 `using where` 和 `using index`，说明相应的索引是用上了。
    * 实测跑了 0.2 秒且没查出结果——因为学生表的 `number` 和 `class` 的 `monitor` 都是随机生成的、两边没匹配上。

```text
    外层查询(student)
          |
          | (1) 先执行内层查询
          v
    内层查询(class: monitor is not null)
          |
          | (2) 结果物化(materialized)成临时表 --- 无法建索引
          v
       临时表  ---- (3) 与外层查询做连接 ---->  结果集
```

* **改造成多表查询**
    ```sql
      select *
      from student s
      join class c on s.number = c.monitor
      where c.monitor is not null;
      ```
    * `EXPLAIN` 结果全是 `simple` 状态，索引也用得上；真跑起来执行时间看着还长了一点，但跟上面那个没差出数量级、还算同一个档次。

* **NOT IN 子查询与左外连接改写**
    * 取所有不是班长的同学的信息，先用子查询：`where number not in (select monitor from class where monitor is not null)`，`EXPLAIN` 显示的是子查询的方式，执行效率还挺高、0.007 秒。
    * 改造成多表连接：

      ```sql
      select *
      from student s
      left join class c on s.number = c.monitor
      where c.monitor is null;
      ```
    * 写法就是在左外连接的基数之上把公共的那部分砍掉不要——让 `c.monitor is null` 就可以了；执行效率也很高，秒数很低，同样没拉出明显的差距。
    * 但从规律和结论上讲还是推荐把子查询改造成多表查询，尤其当子查询比较复杂的时候一定要考虑把它变成多表查询。

* **NOT IN / NOT EXISTS 的替换套路**

```text
    A left join B on <A 与 B 的关联条件>
    where B.<关联字段> is null
```

* 原理：`not in` 表示"不在这里边"；把两张表按关联字段相等连在一起，同时去掉 B 表里非 null 的那些数据、只留下 null 的，相当于把公共数据切掉，剩下的就只有 A 表（左表）里独有的数据。这个套路可以直接拿去用。

### ORDER BY 的两种方式与三条优化方向

* **两种排序方式**
    * `Index`：索引本身就有序，按它排序直接操作就行，效率比较高。
    * `FileSort`：相当于要做一次文件排序，一般得把数据加载到内存当中再排，这时要占用 CPU 资源；要排序的数据量很大、内存（缓冲区）里放不下时，就得排一部分写出去、再排一部分再写出去，产生很多临时的 I/O 场景，效率很低。
    * > 结论：以后要养成一个概念——只要看到 FileSort，潜意识里就认为它是比较耗时的；能用 Index 的方式那是最好的。

* **三条优化方向**
    * `where` 子句中、`order by` 子句中都可以考虑使用索引：`where` 里使用是为了避免出现全表扫描；`order by` 里使用索引主要目的是避免出现 FileSort。
    * 尽量使用 Index 方式完成 `order by`：如果 `where` 和 `order by` 后面是相同的列那太完美了——按它过滤完还用它排序，这就是最好的情况；如果两者不同就可以考虑建一个联合索引，因为一般是先执行 `where`，所以 `where` 用的字段放前面、`order by` 用的字段放后面，比如 `where` 用 A、`order by` 用 B，就建成 `(A, B)`。
    * 如果实在没有办法使用 Index 这种方式，那就只能对文件排序方式尽可能地进行调优了。
    * > **提示**：也有极端情况——出现了 FileSort，性能反而比 Index 还要高；后面的案例实战里就有这样的例子。

### 排序索引的生效与失效案例

* **无索引可用时的 FileSort**
    * 清掉 `student` 和 `class` 表里已经创建的索引（复用"删除表中所有索引"的存储过程），删完 `show index` 确认两张表各自只剩一个主键索引。
    * `select * from student order by age, class_id;` 肯定没有索引可用，`EXPLAIN` 结果是 `using filesort`——把数据加载到内存中排序；在此基础上再加一个 `limit`（分页）也还是没有任何索引可用。

* **覆盖索引与 select 列数对索引选择的影响**
    * 建三字段联合索引并注意字段顺序：`create index idx_age_cid_name on student(age, class_id, name);`。
    * `select * from student order by age, class_id;` 会不会用上索引不好说，实测结果是**没有用上索引，还是 `using filesort`**。
    * 原因：假如用上这个索引那就是一条二级索引，用完之后因为这里是 `select *` 要查所有字段，每一条数据还得回表到主表的聚簇索引里逐条找到叶子节点；而这表里有几百万条数据，优化器一算——还不如干脆把表里所有数据都加载进来，在内存级别重新排个序，花的时间比回表还少。
    * 把 `*` 改掉、只查排序用到的两列：`select age, class_id from student order by age, class_id;` 这时候竟然用上了索引，不再走 filesort，原因是没有回表。
    * > **定义**：覆盖索引（covering index）——查询需要的字段全部包含在二级索引里，不用再回到主表（聚簇索引）去取数据，也就是"没有回表"。

* **limit 对索引选择的影响**
    * `select * from student order by age, class_id limit 10;` 一执行发现用上了索引。
    * 原因同上一件事：这张表数据量挺大，走二级索引之后每一条数据都要回表，再在聚簇索引里一条条找叶子节点，还不如直接针对内存当中的数据排序快；而现在只要 10 条数据，那就干脆排好序以后取前 10 个、只对这 10 条回表，这个成本优化器认为很低——毕竟在内存中把所有数据的这两个字段重新排一遍反而更慢。

* **排序字段顺序错误导致的索引失效**
    * 再建 `create index idx_age_cid_num on student(age, class_id, student_number);`，此时表上有两个大的联合索引 `(age, class_id, name)` 和 `(age, class_id, student_number)`。
    * > **易错点**：联合索引的第 1 个字段都不考虑那就肯定用不上——上来就写 `order by class_id`，或者 `order by class_id, name`，连最左前缀原则这一关都过不去，只能走 filesort。
    * 顺序必须和索引里字段的先后一致：索引是 `age` 在前、`class_id` 在后，`order by` 也得先 `age` 后 `class_id`。
    * > **提示**：`key_len` 显示的字节数可以用来看索引实际用了几个字段。本表里 `age` 允许为 null，整数本身 4 字节再加 1 个 null 标志位占 5 字节；`class_id` 同样允许为 null 占 5 字节；`student_number` 是 not null 的占 4 字节；三个字段全用上就是 $5+5+4=14$ 字节。

* **排序方向与反向索引扫描**

| order by 写法 | 是否用上索引 |
| :--- | :--- |
| `order by age desc, class_id asc` | 用不上，走 filesort |
| 不带 age、直接从后面的字段开始 | 用不上 |
| `order by age asc, class_id desc` | 用不上 |
| `order by age desc, class_id desc` | 用上了，提示 `backward index scan` |

* `order by age desc, class_id asc` 不行的原因是 `age` 是一个降序；`order by age asc, class_id desc` 也不行，因为 `age` 是升序、`class_id` 是降序——假设索引里这两列都是升序的，当 `age` 相等时找 `class_id` 还得逆着来，还不如在内存中重新排序（filesort）来得快，于是干脆不用。
* 而 `order by age desc, class_id desc` 反而能用上索引，且 `EXPLAIN` 里有提示 `backward index scan`——倒着遍历就可以了：索引里 `age` 是升序、`class_id` 也是升序，那就干脆整体倒着来，`age` 也好、`class_id` 也好都相当于从大到小。
* > 结论：顺序错了不行，方向反了也不行；要反就全反，但顺序必须一样——先 `age` 后 `class_id`。

* **过滤后的数据量对排序字段取舍的影响**
    * 第一条查询在 `where` 里给出 `age` 的条件再按 `age` 排序：确实用上了索引，而且是优化器综合判断之后挑的那个以 `student_number` 结尾的联合索引，但它的 `key_len` 只有 5——这时候它只考虑了 `age` 这一段，`order by` 的那个字段根本没管。
    * 成因：所有的排序都是先基于过滤数据的；如果过滤完以后能把大部分数据都干掉、只剩几百条几千条甚至上万条，那优化器有可能就不再让另外一个字段进入索引了。这条查询的 `rows` 是 18000 多行，按我们的标准一万多条并不少，但 CPU 觉得这个数据其实不多，它就直接回表了、没有考虑 `order by`。
    * 把 `order by` 的字段换成 `class_id`、`name`，执行结果还是这样——同样没有考虑 `order by`，同样是一万多条数据；两条查询的过滤条件一样，`rows` 的数值自然也应该一样，只是都只用了 `age` 这一段。
    * 再往下这一条 `where` 里除了 `age` 还加上了 `class_id` 的条件并同时保留 `order by`：优化器并不走那两个联合索引去排序。没有 `limit` 限制意味着符合条件的数据全都要、数据量又很大，它觉得还不如直接做一次全表扫描加 filesort——何况本来也没有以 `class_id` 开头的索引。
    * 在这条查询的基础上只加一个 `limit 10`，一执行发现还真用上了、而且两个字段全用上了：先按 `age` 用这个二级索引做了排序，在这个有序的基础上再去找 `class_id` 是 45 的记录，找到以后只取前 10 个直接从这儿取走，所以性能会更高一些。
    * 把索引补上试试：`create index idx_cid on student(class_id);` 之后再执行刚才那条带 `class_id` 条件的查询，毫无疑问它一定会用上这个 `cid` 索引——一开始如果没有 `class_id` 开头的索引，优化器就认为直接全表 filesort 更好；有了这个索引，它的选择就变了。
    * > 结论：`order by` 与 `where` 一起出现时可以考虑构建联合索引；但能不能用、值不值得用还得经过查询优化器的分析——并不是我们看到"它应该能用"就一定用得上。

* **联合索引 (a, b, c) 与 where/order by 的组合清单**

| 查询形态 | 能否用上 `(a, b, c)` 排序 |
| :--- | :--- |
| `order by a` / `order by a, b` / `order by a, b, c` | 可以 |
| 上述写法整体逆序（方向一致地倒着扫） | 可以，但 a、b、c 之间必须保持有序 |
| `where a` 为常量，`order by b` 或 `order by b, c` | 可以 |
| `where a` 为常量且 `b` 也为常量，`order by c` | 可以 |
| 排序字段乱序 | 不行 |
| `order by` 里出现索引之外的字段 | 不行 |
| `order by` 里不带首个字段 a | 不行 |
| `where a` 为常量，`order by c`（缺 b） | 不行 |
| `where a` 为常量，`order by a, d`（多了 d） | 不行，多了个 d 就不能按它排序了 |
| `where a in (...)` | 不行，`in` 相当于还是一个范围，范围就不行 |

* > **注意**：上面只是泛泛地说一些规则，真正用没用上还得结合具体表里的数据来看——优化器要核算一下成本，至少它会把索引作为一个选项来考虑，但选不选是另一回事。

### FileSort 与 Index 排序的性能对比实战

* **无索引基线**
    * `select * from student where age < ? order by name;` 的 `EXPLAIN` 结果是 `type` 为 `ALL` 并且有 `using filesort`；真跑起来其实速度还挺快，跑两遍也差不多，稳定在这个数值范围。

* **(age, name) 联合索引对 FileSort 的消除**
    * `create index idx_age_name on student(age, name);` 之后 `EXPLAIN` 显示用上索引了、后面也没有 `using filesort`，filesort 被去掉了。
    * 但 `key_len` 写的是 5，相当于只考虑到了 `age` 这一段、还没给 `name` 面子——优化器觉得过滤完以后剩下的数据直接回表性能就挺高；执行一下，效率确实比什么都不用的时候要快一些。

* **(age, student_number, name) 索引下的 FileSort 反而更快**
    * 再建 `create index idx_age_num_name on student(age, student_number, name);`，同样的查询这次又出现 `using filesort`，而且前面的 `key_len` 写的是 9——用到了 `age` 和 `student_number` 这哥俩（$5+4=9$），没有考虑 `order by`，所以排序的时候还得 filesort。
    * 可真执行起来这条反而更快，是 **0.002 秒**，比 `(age, name)` 方案的时间明显要短，都差出一个数量级了。
    * 解释：因为 `where` 经过它过滤以后结果数量本身就已经很少了。前面那个方案只考虑了 `age`、没考虑 `name`；而现在多了一个索引（前一个索引还没删掉，是在多了一个索引的情况下），优化器毫不犹豫就奔向了新索引的怀抱——它认为这两个条件合在一起构成的索引结果数量已经很少，`key_len` 是 9 说明 `name` 在不在索引里都无所谓；过滤完就这么点数据，`order by` 也不用考虑了，直接在内存当中针对这十条数据排序，效率当然高。
    * > 结论：并不是看到 filesort 就要紧张、非得把它改成没有 filesort 不可。两个索引同时存在时 MySQL 会自动选择最优的方案，而且随着数据量的变化它的选择也会跟着改变；如果经过前面这两个字段过滤之后数据量仍然极其庞大，那也不排除它会把 `name` 字段也用上。

* **范围条件与排序字段二选一时的取舍**
    * > 结论：当范围条件和 `group by`、`order by` 的字段出现二选一的时候，优先观察条件字段过滤的数量。如果过滤掉的数据量足够多、而需要排序的数据并不多，那就把索引放在范围字段上。
    * 补充验证：不用 `(age, student_number, name)` 这个三字段索引、只建一个两字段的联合索引也行——drop 掉三字段索引再建两字段的跑一遍同样的语句，效果是一样的。

### FileSort 的两种算法与参数调优

* **双路排序（two-pass，MySQL 4.1 之前）**
    * 步骤：先找到 `order by` 的这个字段 `age`，把这一列所有的值加载到内存当中；在内存中针对 `age` 排一遍序；排好序以后再拿着这些 `age` 回磁盘找到表中对应的那一条完整数据，把完整的那条数据再取到内存里来。
    * 整个过程需要两次磁盘扫描，比较耗时，因为 I/O 的次数比较多。

```text
    双路排序(two-pass, 4.1 之前)
      第 1 次扫描: 只读 order by 列(age) --------> 内存中排序
      第 2 次扫描: 按排好的 age 逐条回表取整行 ----> 内存
      结果: 2 次磁盘扫描, 大量随机 I/O
```


* **单路排序（single-pass，MySQL 4.1 之后）**
    * 4.1 之后用的是单路排序，言外之意就是只扫描一次：不再先把 `order by` 那一列单独拿过来，而是上来就把磁盘中查询需要的所有列一次性读进来，在 `sort_buffer` 里针对 `order by` 的 `age` 字段排序。既然要读所有列，它对内存的要求就更高一些。
    * 好处是速度快了，而且把随机 I/O 变成了顺序 I/O：从磁盘读的时候数据页都放在相应的区里边、一次性全读过来了，这就是顺序 I/O；而双路排序是先排好 `age` 这个字段、再拿着每一个 `age` 回去找表中具体的数据，这一条跟下一条有可能就在不同的页当中，那就是随机 I/O。
    * 单路排序大体上是对双路排序的替换，但不算严格的替换关系——双路排序也有它的好处，就是对内存的占用要小一点。

```text
    单路排序(single-pass, 4.1 之后)
      第 1 次扫描: 一次读入查询所需的所有列 ---------> sort_buffer
      在 sort_buffer 内按 order by 列(age)排序 ------> 结果
      结果: 1 次扫描, 顺序 I/O, 但占用内存更大
```


* **sort_buffer_size**
    * 单路排序占用的空间比较多，这时候就要担心容量够不够，于是提到 `sort_buffer_size` 这个参数。
    * > **易错点**：容量不够的时候很恶心——排一部分就得写出去，然后再排下一部分、再写出去，来来回回反而造成大量的 I/O 操作，得不偿失。
    * `sort_buffer_size` 默认是 **1 MB**；开发中尽量用 Index 方式完成排序，万一避不开只能用 filesort 就要对它调优，第一步就是把这块空间调大，让单路排序尽量别反复往磁盘里写。

* **max_length_for_sort_data**
    * 它影响到底选单路还是双路：拿要查询的字段长度跟这个变量做对比。
    * 字段长度比较短（小于这个变量）：可以用单路排序。
    * 字段长度比较长、已经大于这个变量：就走双路排序，性能相应地要稍微差一些。
    * 所以 `order by` 的时候尽量不要 `select *`——那意味着要查的字段是最多的，就有可能超出这个量，一超就开始用双路了。

### GROUP BY 的执行路径与编写规范

* **使用索引时的排序消除**
    * `GROUP BY` 使用索引的情况跟 `ORDER BY` 几乎一致：不仅可以在有 `WHERE` 的情况下配合索引使用，在没有 `WHERE` 的情况下也可以直接使用索引来做分组。
    * 具体能不能用上仍要交给查询优化器判断和选择：它会把不同方案的执行成本放在一起对比，再决定选哪一条路。
    * > 原理性推断：`GROUP BY` 是先排序、再分组。只要索引已经替我们把数据排好序了，分组这一步就可以直接做，排序被完全省掉；反过来如果索引的顺序帮不上忙，这一次排序就躲不过去。
    * `ORDER BY` 与 `GROUP BY` 在"索引本身是否有序"的判断逻辑上是一套的，因此它们遵守同一条法则——最佳左前缀法则；索引的前缀列顺序对不对得上分组列的顺序，决定了这次分组能不能借上索引的力。

* **无法使用索引列时的参数调整**

| 参数名 | 作用 | 调整方向 |
| :--- | :--- | :--- |
| `sort_buffer_size` | 排序缓冲区大小，决定排序能否在内存中完成 | 适当调大 |
| `max_length_for_sort_data` | 参与排序的单行数据长度阈值，决定走全字段排序还是回表排序 | 适当调大 |

* 当无法使用到索引列的时候情况就跟 `ORDER BY` 里那个 filesort 一样了，底层要解决的问题是同一个：排序数据放不下时排序过程就会往磁盘上溢出，性能明显掉下来。

* **过滤条件写在 WHERE 而不是 HAVING**
    * `WHERE` 的效率高于 `HAVING`，所以能写在 `WHERE` 里的条件就不要写到 `HAVING` 里；标准是：针对非组函数（也就是非聚合函数）的条件，一律建议写在 `WHERE` 中。
    * 原因在执行的先后顺序上：`WHERE` 在分组之前就把不合要求的行筛掉了，参与分组的数据量从源头就变小；而 `HAVING` 是对分组结果做的过滤，它要等分组和聚合都算完才生效，前面那些本该被排除的行已经陪着算过一遍了。
    * > **易错点**：把聚合函数写在 `WHERE` 里，或者把普通列条件写在 `HAVING` 里，是最常见的两种写法错误。前者语法上就会报错，后者语法通过但白白多算了一遍聚合。

* **少用 ORDER BY 并控制结果集行数**
    * `ORDER BY` 要尽量少用：能不排序的就不排序，能在程序端做的排序就放到程序端去执行，不要全压在数据库上。
    * 理由：`ORDER BY`、`GROUP BY` 以及 `DISTINCT` 都是比较耗费 CPU 资源的操作；语句里带着 `WHERE` 又带着 `ORDER BY`，如果没能用上排序字段的索引就直接进入 filesort；即便用上了字段索引也可能一路回表，最后还是在内存里做一次排序。
    * > **提示**：不是让你把所有排序都从 SQL 里删掉——数据库的排序是在数据落地的位置完成、不经过网络传输；程序端排序则要先取回更大的结果集。判断依据是"这份数据最终要用到什么程度"，只为取前十行而在数据库里给整表排序才是不划算的那一种。
    * 具体标准：包含 `ORDER BY`、`GROUP BY`、`DISTINCT` 的查询语句，`WHERE` 条件过滤出来的结果请保持在 **1000 行以内**，否则这条 SQL 会很慢。
    * > **定义**："`WHERE` 过滤出来的结果"指的是过滤之后、排序与分组动手之前的那份行数；这个 1000 行是判断"这条语句该不该换个写法"的一条实操线，而不是允许排序开销无限放大的上限。

### LIMIT 深分页的问题与优化

* **问题案例：从 200 万位置取 10 条**
    * 一般情况下的分页优化手段是创建覆盖索引，它能比较好地提高性能；这里先看一个让人比较头疼的具体案例——从 `student` 表中查询从第 200 万这个位置开始的 10 条记录。
    * 这条语句崩溃的三个原因叠在一起：它没有提供任何可用于过滤的字段，用的是 `SELECT *`，并且 `SELECT *` 决定了它没有办法用上主键索引之类的索引来做覆盖。于是执行的时候只能把数据都往内存里加载，等到数到那个位置了才取出十条数据。

```text
    分页偏移的扫描代价
    ──────────────────────────────────────────────
    offset 2000000, size 10

    读取起点 ──► 逐行扫描 ──────────────────────────► 第 2000000 行 ──► 取 10 行返回
                 └──────── 读出来，然后全部丢弃 ────────┘              └─ 真正需要的部分 ─┘

    扫描量 = 2000000 + 10 行
```

* 真正需要交付的只有末尾 10 行，前面 200 万行被读进内存之后就直接丢弃了，扫描量与实际产出完全不成比例。

* **优化方向：往主键索引（聚簇索引）上靠**
    * 思路是尽量用上主键索引也就是聚簇索引，因为走它就不涉及回表的问题；判断分两个分支——如果查的不是 `SELECT *`、字段都能被某条索引覆盖，就考虑用覆盖索引；如果查的就是 `SELECT *`，就尽量使用主键索引。
    * 关键前提是主键本身是不是自增的：如果主键 `id` 本身就是自增的，那么构建出来的整个索引天然就是升序排列的，这时候不需要"跳过 200 万行"，直接按 `id` 的范围去定位就行——让 `id` 大于 200 万，再 `LIMIT 10`，等于直接定位到索引上的那一段、取十条数据出来即可，也不需要回表。

* **主键非自增时的排序处理**
    * 如果 `id` 在赋值的时候不是自增的（比如先给 1、3、7，再给 2、5、6，最后给 10），按"大于某个值"去取那一段，取出来的数据跟自增情况下取出来的那一截就不一样了。
    * > 结论：分页只要保证不重不漏——第 100 页的数据不要跟第 99 页查重了，也不要漏掉一些数据，让每条数据都能出现一次，就够了。
    * 正因为"绝对连续的行号"不是分页的业务要求，"跳过 N 行"这种性能很差的方式才被替换掉。
    * 主键确实不是自增时：按 `id` 做一个排序，排序之后就可以直接使用聚簇索引了——思路始终是尽量往聚簇索引、主键索引上靠；排完序以后仍然用主键索引取出这十条数据，再通过一个 `WHERE` 条件去定位到目标行的 `id` 值上，把这十条数据取出来。两条路径的性能都比"读 200 万行丢 200 万行"要好得多。

```text
    深分页的两条优化路径
    ──────────────────────────────────────────────
    方案一：主键自增，逻辑顺序与自增顺序一致
        范围条件（id > 起始值） ──► 主键索引定位 ──► LIMIT 10 ──► 返回

    方案二：主键非自增，逻辑顺序与自增顺序不一致
        按 id 排序 ──► 主键索引有序 ──► 取出 10 行 ──► WHERE 定位目标 id ──► 返回

    共同点：都不再逐行扫描并丢弃，起点是"定位"出来的，不是"数"出来的
```

* 两条路径的差别只在起点怎么来——自增主键直接用范围条件定位，非自增主键先按 `id` 排序再用条件定位目标行；共同点是都终止了"把前面所有行读出来再丢掉"这个动作。
* 深分页的起点要靠条件定位，而不是靠逐行数过去。
* > **易错点**：用"前一页最后一条记录的 `id`"作为下一页的起点，前提是排序规则稳定且没有并发写入造成的位置漂移；翻页过程中有数据插入或删除时，相邻页之间仍可能出现重复或遗漏——这也是为什么要把"不重不漏"当作分页的验收标准，而不是"第 N 页恰好是第 N 段行"。

## 覆盖索引


### 覆盖索引的判定条件

* **字段增删与索引可用性的变化（索引 `(age, class_id, name)` + 主键 `id`）**

| 查询列表 | 与索引 `(age, class_id, name)` 及主键 `id` 的对应关系 | 是否覆盖 | `EXPLAIN` 的表现 |
| :--- | :--- | :--- | :--- |
| `age, class_id` | 两个字段都落在索引列之内 | 是 | 用上索引 |
| `age, class_id, name` | 恰好等于索引的三列 | 是 | 用上索引 |
| `age, class_id, name, id` | 索引三列再加主键 | 是 | 用上索引 |
| `age, class_id, name, id, student_number` | 多出一个 `student_number` | 否 | 用不上索引，退回 `ALL` |

* 能不能用上索引与这几个字段写在语句里的位置、顺序都无关，只看它们是否落在"索引列 ＋ 主键"这个集合里；只要有一个字段掉在集合外面，结论就翻转。
* > 结论：字段能不能加、能加到几个，本质上是同一个问题——这条索引还能不能把查询要用的列全部提供出来。

* **二级索引结构与回表**

```text
    表 t(c1, c2, c3)：c1 为主键，在 c2 上建一条普通二级索引

      二级索引（c2）                            聚簇索引（主键 c1）
          非叶子节点                                 非叶子节点
          [c2 | c1 | 页号]                           [c1 | 页号]
               |                                         |
               v                                         v
          叶子节点 [c2 | c1]   ---- 回表 ---->      叶子节点 [c1 | c2 | c3]
          按 c2 有序                                 整行数据
```

* 二级索引的非叶子节点上放的是 `c2` 的值、与它对应的 `c1` 值，以及往下的页号；到了叶子节点除了索引列 `c2` 本身还留着主键 `c1` 的值——留着它就是为了回表。
* `select * from t where c2 = 2`：走 `c2` 的二级索引 B+ 树往下判断，命中 `c2 = 2` 的那一项，从它身上取出对应的主键值（假设 `c1` 就是 3）；再拿着 `c1 = 3` 回到聚簇索引最后一级的叶子节点，把这一行的 `c1`、`c2`、`c3` 三个字段完整取出来。取 `c3` 的这一趟就是回表。
* 把语句改成不查 `c3`、只查 `c1` 和 `c2`：`WHERE` 条件里的 `c2` 是索引列，`SELECT` 里的 `c2` 和 `c1` 在二级索引的叶子节点上本来就有，既然压根没打算查 `c3`，这一趟回表就完全没有必要。
* > **定义**：一条查询所需要的列全部由某条索引直接提供，不必再回表取整行，这种情况就叫覆盖索引。

* **可覆盖字段的范围与超界后果**
    * 边界恰好停在"索引列 ＋ 主键"的原因：二级索引的叶子节点上只放了两类东西——索引列本身以及主键值，除此之外它没有地方容纳查询要用的别的字段。所以一条索引能覆盖多少列不取决于语句怎么写，而取决于它的叶子上到底存了什么。
    * 假设索引由三个字段构成，那么能覆盖的字段集合就是"这三个索引列 ＋ 主键"一共四个：查这四个字段是覆盖，少写几个、只用到其中两三个仍然是覆盖，**只多不得**。
    * 硬标准：一个索引包含了满足查询结果的数据就叫覆盖索引，它包含查询里 `SELECT`、`JOIN` 和 `WHERE` 中用到的所有列。
    * 容易漏的一点：`SELECT`、`JOIN`、`WHERE` 三处出现的列算的是同一个集合，没有谁比谁特殊——`WHERE` 里拿来过滤的列和 `SELECT` 里查出来的列都要从这个额度里扣。
    * > **易错点**：把"主键也算在覆盖范围里"当成可有可无的细节，是判断失误的主要来源。同一条索引，写不写主键，能覆盖的字段数差一个，判定结果可能正好相反。

* **超界字段为什么致命**
    * 多出来的 `student_number` 既不在索引列里也不是主键，二级索引的叶子节点上找不到它，想拿到就只能回表；而一旦确定要回表，优化器的算盘就变了——既然横竖要回表，那还不如直接对完整的一张表做扫描过滤（在排序优化那个场景里就是干脆针对整表做一次排序），成本反倒更低，于是索引被彻底放弃。

### 不等值条件下的覆盖索引

* **失效规则与成本判断的关系**
    * 清掉 `student` 表上的索引，重新建一条 `(age, name)` 的联合索引后执行 `SELECT * FROM student WHERE age != 20;`，`EXPLAIN` 一看 `key` 是空的、索引没用上——这跟"出现不等于索引可能失效"的结论一致。
    * 但"不等于就一定用不上索引"这句话千万别记死：前面列的那些规则是拿来帮我们做分析、做判断的，它们本身就是查询优化器从成本出发总结出来的近似规律，**成本的账一重算，规则立刻就能被打破**。
    * > 结论：写 `age = 20` 这种等值条件索引基本上一定会用上；写 `age != 20` 这种不等值条件只是"有可能"被放弃——是有可能，不是一定。

* **覆盖索引下的成本重算**
    * 把 `SELECT *` 换成具体字段：`SELECT age, name FROM student WHERE age != 20;` 再执行一次，索引用上了。
    * 走索引的成本一共两块：一块是针对二级索引 B+ 树本身的运算，另一块是回表；这两块加起来要跟"不用索引、直接全表扫描再逐行过滤"比一比，谁便宜听谁的。
    * 写 `SELECT *` 时：`age`、`name` 能从索引里拿到，其余字段拿不到、必须回表补齐，两块成本加在一起比全表扫描还高，优化器自然放弃索引。
    * 改成 `SELECT age, name` 之后：要查的两列索引里都有，回表这一整块成本被砍掉、只剩一块成本，比全表扫描便宜，优化器就大胆地用上了这条索引。

| 写法 | 二级索引运算 | 回表 | 与全表扫描相比 | 优化器的选择 |
| :--- | :--- | :--- | :--- | :--- |
| `SELECT *` | 需要 | 需要（补齐索引里没有的列） | 更贵 | 放弃索引，走全表扫描 |
| `SELECT age, name` | 需要 | 不需要，索引已覆盖 | 更便宜 | 用上索引 |

* > **易错点**：不要把这些失效规则当成铁律去背。语句一改、字段一换、回表成本一省，结论就可能翻转——判据始终是成本，不是规则本身。

### 前导通配符条件下的覆盖索引

* **实测**
    * 用同一条 `(age, name)` 索引执行 `SELECT * FROM student WHERE name LIKE '%...';`：`%` 写在最前面而索引是按 `name` 排好序的、前缀不定就没法用它来定位，所以用不上索引——而且这里还有另一半原因：`SELECT *`。
    * 把 `SELECT *` 具化成三个字段：`SELECT id, age, name FROM student WHERE name LIKE '%...';` 索引又用上了，原因跟不等值那一例完全是同一个——要查的 `age`、`name` 是索引列，`id` 是主键，三个字段在二级索引的叶子节点上凑齐了、不用回表，优化器就会考虑用它。甚至连 `name` 都可以从查询列表里删掉，只查 `age` 照样能用上。
    * > 结论：判定标准可以压成一句话——只要这次查询不需要回表，优化器就会考虑把索引用起来。前导通配符本身并不单独判死刑，真正决定结果的是"要不要回表"。

### 覆盖索引的收益与代价

* **收益一：避免索引的二次查询**
    * 避免了 InnoDB 的表做索引的二次查询，说白了就是避免回表；回表省掉成本就降下来，优化器在挑执行方案时会优先考虑它，不用像原来那样直接走全表扫描；手上多了一个更优的选择，整条语句的执行时间更短。

* **收益二：随机 I/O 转为顺序 I/O**

```text
    范围查询 c2 ∈ [2, 20]

      二级索引叶子节点（按 c2 有序）
          [2] [3] [4] [5] ... [20]        <- 数据挨着，顺序 I/O
           |   |   |   |        |
           |   |   |   |        |  回表
           v   v   v   v        v
      聚簇索引叶子节点（按主键定位）
          页A(区1)   页K(区3)   页B(区1)   <- 位置散落，随机 I/O

      一个区 = 64 个连续页 × 16 KB = 1 MB
```

* 在索引这一侧这批准数据是连续的；一旦回表它们会按主键落到聚簇索引的各个位置上，相邻的两条记录可能落在不同的页，不同的页又可能落在不同的区，这一趟读下来就是随机 I/O。
* 不回表时只读索引页本身，数据天然有序、挨着的数据可能就在一个页里；即使不在一个页，那些页也通常落在同一个区里、本身还是连续的，一路顺序读下去即可——这就是顺序 I/O。
* 回表这一侧为什么会散：聚簇索引是按主键排的，同一个 `c2` 区间里的记录主键可能相差很远，命中的行数越多要回表的次数就越多，而每一次落点在哪个页、哪个区事先并不知道。索引这一侧刚好相反：数据在叶子节点上已经按 `c2` 排好序，一页装不下就顺延到下一页，页与页之间本来就是接着的。两边一对比，差别不是"要不要多读一次"，而是"读的时候要不要来回跳"。
* 一个区有 64 个连续的页、每页 16 KB，所以 $64 \times 16\ \text{KB} = 1\ \text{MB}$。
* > 结论：覆盖索引砍掉的看似只是一个回表动作，其实砍掉的是一次随机 I/O，剩下的只要顺序 I/O 就够了，性能提升相当明显；也正因为可以减少树的搜索次数、显著提高性能，它才成为一种常用的性能优化手段。

* **代价：索引变长与空间占用**

```text
    优化前：WHERE 只涉及 (a, b)
        索引 (a, b)          -> 只服务过滤条件，占用小

    优化后：为了覆盖 SELECT 出来的 (a, b, c, d)
        索引 (a, b, c, d)    -> c、d 不进过滤，只为免回表而存在，占用更大
```

* 前提是一条大家都认可的事实：索引字段的维护是要付出代价的，所以不要无缘无故地多建索引。
* 本来 `WHERE` 里只涉及两个字段、针对这两个字段建一条联合索引就够了、占用也小；可 `SELECT` 里列了四个字段、一看用不上覆盖索引，就把索引建长一点、在那两个字段之外再补两个进来，目的只有一个：往覆盖索引上靠。
* `c`、`d` 根本不参与条件过滤，它们进索引的唯一作用是让查询不用回表，代价是索引更长、更占空间、维护成本更高——这部分多少有点冗余。
* 多出来的列是要真金白银养着的：索引更长占用的空间就更多，写数据时要维护的索引项也更多，整体成本随之抬高；这笔账不能只看查询这一侧——查询是快了，代价转移到了存储和写入上。到底加合适还是不加合适，是业务的 DBA 或者数据架构师要衡量、要拍板的问题。

## 索引条件下推（ICP）


### 索引下推的定义与原理

* **定义与实现位置**
    * > **定义**：索引条件下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的新特性，是一种在存储引擎层使用索引过滤数据的优化方式；当 `WHERE` 中的某个条件所在的列包含在所使用的索引中、但这个条件本身用不上索引的有序性时，把这个条件下推到存储引擎层，在索引记录上先做一次过滤，只把过滤后剩下的记录回表取整行。
    * ICP 是查询优化器在优化过程中的一个具体策略，与覆盖索引属于同一类东西；`EXPLAIN` 的 `Extra` 字段里的 `Using index condition` 代表的就是索引条件下推。

* **优化前的过程（"我们以为"的过程）**
    * 前提是 `key1` 这个字段上有索引——这是前提，得有索引；查询的写法是 `key1` 上既有范围条件、又有一个以 `%` 开头的模糊匹配条件。
    * `%` 开头的 `LIKE` 用不上索引，所以这里真正能驱动索引的只有前面的范围条件：通过 `key1` 上的索引去查数据，假设满足范围条件的有 100 条；这是二级索引，那这 100 条每一条都要回表到聚簇索引上逐条找到它对应的整行记录；拿到聚簇索引里的数据之后再判断 `key1` 字段是否满足后面那个模糊条件，满足就留下、不满足就丢掉；假设过滤完只剩 10 条。
    * 也就是：100 次回表 + 100 次条件过滤，最后留下 10 条。

* **真实的过程：条件被下推**
    * 优化器同样先查出那 100 条记录，但并不急着对这 100 条都做回表，而是先做后一个条件的判别——条件下推（pushdown），推到后面那个条件所在的位置。
    * 关键点在于：`key1` 所用的这个索引当中本身也包含后面那个字段，那这 100 条记录在索引里就能直接判断是否满足后面的条件——先在索引层把这 100 条过滤一遍、假设只剩 10 条，再拿着这 10 条去回表。于是回表次数从 100 次降到 10 次。
    * 认识上的分界：回表这件事本身没有被取消，它只是变少了——查询该回表还是要回表，最后那 10 条仍然要去聚簇索引里把整行取出来；ICP 改变的是"拿多少条去回表"，从"满足范围条件的全部候选"变成"在索引层先过滤过一轮的候选"。相应地服务器层拿到的也不再是 100 条待判断的记录，而是 10 条已经过了后置条件的记录。

```text
    【没有 ICP】服务器层驱动，索引层只负责范围扫描
                    索引层（二级索引）        服务器层
      范围条件  ──►  取出 100 条索引记录  ──►  回表 100 次（聚簇索引）
                                                  │
                                                  ▼
                                        逐条判断后置条件 → 留下 10 条
                                        随机 I/O 次数：100 次

    【有 ICP】条件被下推到索引层
                    索引层（二级索引）        服务器层
      范围条件  ──►  取出 100 条索引记录
                          │
                          ▼
                  在索引层用后置条件过滤（该字段就在索引里）
                          │
                          ▼
                      留下 10 条  ──────►  回表 10 次（聚簇索引）
                                        随机 I/O 次数：10 次
```

* 两种走法的范围扫描工作量完全相同，差别全部发生在候选记录产生之后——ICP 把只能靠整行数据判断的条件提前到索引层就能判断的位置，于是回表次数与随机 I/O 次数一起被压下去了。

* **省下的不只是回表次数**
    * 回表次数减少，同时减少的是随机 I/O：原来那 100 条数据每一条在聚簇索引里所在的数据页可能并不连续，要把一条记录加载进内存它所在的那个页就得一并载入，这就是随机 I/O。
    * 放大数字感受一下：假设范围条件查到的是 10000 条，而第二个条件过滤完以后只剩 1 条、甚至一条都没有——不用 ICP 时 10000 条全部回表再做 10000 次随机 I/O 把数据页加载进来；用 ICP 时先在索引里过滤到 1 条、只回表一次、只把那一条记录所在的数据页加载一次。
    * 随机 I/O 这一项必须单独拎出来说的原因：随机 I/O 的次数并不等于"读到的记录条数"，而等于这些记录散落在多少个数据页上；100 条记录如果分散在几十上百个不同的页里，就得把这几十上百个页分别从磁盘随机读进内存，哪怕某一条记录最终不要，它所在的那个页也已经付出了加载成本。ICP 把候选集从 100 条压到 10 条，压下去的不只是 90 次回表，还有这 90 条所牵连的那些数据页的随机加载——越往后过滤性越强省得越多。
    * > 结论：ICP 的收益来源只有一句话——把原本必须回表之后才能判断的条件提前到索引层判断，从而减少回表次数与随机 I/O 次数。数据量越大、后置条件过滤性越强，收益越明显。

### 联合索引场景：更一般的情形

* **表结构与索引（`zip_code`、`last_name`、`first_name` 三字段联合索引）**
    * 查询里用到了 `zip_code`，对上了；`last_name` 也对上了，但它用的是 `%` 开头的 `LIKE`，所以用不上；后面还有一个条件对应的字段不在索引里——这是刻意设计的，为了体现更一般的场景。
    * 结论是：这个索引只被用上了前面一部分，`key_len` 上也能看得出来。
    * > **提示**：`key_len` 是 `EXPLAIN` 里判断"联合索引到底用上几个字段"的现成工具。它显示的是本次实际用到的索引键长度，用上的字段越多、长度越大；一旦某个字段因为条件失效（比如 `%` 开头的 `LIKE`）而没能参与定位，`key_len` 就停在前一个字段上、不会继续往后走。看到 `key_len` 只覆盖 `zip_code` 这一段，就说明索引的有效范围到此为止——注意，有效范围到此为止不等于这个索引里没有 `last_name`，这两件事要分开看，ICP 能利用的正是后者。
    * 反过来说，字段不在索引里条件就下推不了——最后一个条件的字段被刻意选在联合索引之外，它不是用来展示 ICP 的，而是用来划出 ICP 的边界。

* **两种走法的对比**
    * 没有 ICP 时：索引只能有效到 `zip_code` 这一段，从索引里找到一波满足该条件的记录、假设有 1000 条，那这 1000 条每一条都要回表找主键索引（聚簇索引）；而且这 1000 个数据项每一项都要以数据页的方式加载进内存，然后才在里面判断第二个条件、第三个条件，过滤完可能只剩 10 条。
    * 有 ICP 时：索引里除了 `zip_code` 还包含 `last_name`，虽然 `last_name LIKE '%张%'` 用不上索引的有序性，但这个字段就在索引里，所以可以在索引层就判断一下 `last_name` 是不是"有张的"——`zip_code` 过滤完之后再在索引里过滤到只剩"有张的"、假设剩下 100 条；至于再往后那个条件用不了了，因为联合索引里根本没有这个字段。
    * 于是拿这 100 条去回表，加载进来之后再看这 100 条里哪些满足最后那个条件、再过滤一次，只剩 10 条。

```text
    索引：idx(zip_code, last_name, first_name)   PK(id)

    查询条件：  zip_code  范围条件        <- 能用索引定位
                last_name LIKE '%张%'    <- 用不上索引有序性，但字段在索引里
                另一条件                   <- 字段不在索引里

    没有 ICP：
      索引层 ── 按 zip_code 扫描 ──► 1,000 条候选
                                      └─► 1,000 次回表 → 1,000 次随机 I/O
                                            └─► 再判断后两个条件 → 10 条

    有 ICP：
      索引层 ── 按 zip_code 扫描 ──► 1,000 条候选
                └─► 在索引层判断 last_name LIKE '%张%' ──► 100 条
                                                           └─► 100 次回表
                                                                 └─► 判断最后一个条件 → 10 条
```

* 能下推的只有"字段在索引里"的那一个条件；字段不在索引里的条件，无论有没有 ICP 都只能在回表之后由服务器层判断。

* **什么时候体现不出 ICP 的好处**
    * 写法换成 `last_name LIKE '张%'`（张开头，不是 `%` 开头）再加一个 `first_name LIKE '三%'`：虽然也写了 `Using index condition`，但真正意义上还没有起到多大作用。
    * 原因：这两个条件对应的列都在联合索引里，而且它们是确定的（非 `%` 开头），使用索引的时候第一个字段、第二个字段、第三个字段本来就会一起考虑上，然后再回表；既然索引本身就能用上这些字段，那就体现不出索引条件下推的好处到底在哪。
    * > 结论：ICP 真正发挥作用的场景是——字段在索引里，但这个字段对应的条件失效了、用不上索引的这部分能力，此时在回表之前用它在索引层做一次数据过滤。这才是它的价值所在。

### 执行计划里的表现与开关控制

* **Using where 与默认开启状态**
    * 执行联合索引那个查询时除了 `Using index condition` 还会看到 `Using where`，因为后面那个条件的字段不在索引当中；不想看到 `Using where` 时只需把那个不在索引里的条件去掉，再执行一次 `Extra` 里就只剩索引条件下推了。
    * 默认行为下 ICP 就是开启的。

* **optimizer_switch 与 NO_ICP 两种关闭方式**
    * 默认情况下该参数处于开启状态，要关闭它就用 `SET` 把优化器开关里的 `index_condition_pushdown` 改成 `off`：
      ```sql
      -- 关闭索引条件下推
      SET optimizer_switch = 'index_condition_pushdown=off';
      -- 重新打开索引条件下推
      SET optimizer_switch = 'index_condition_pushdown=on';
      ```
    * 关掉之后再 `EXPLAIN` 执行一遍会发现索引条件下推没有了（`Extra` 里不再出现 `Using index condition`）、性能随之下降；改回 `on` 再执行它又回来了。
    * 第二种方式：不改变量，直接在写 SQL 时加上 `NO_ICP` 这个优化器提示，表示这条语句不使用索引条件下推；这种写法不需要"一会儿想用还得再打开"，作用范围只在这一条语句上。
    * > **易错点**：两种关闭方式的作用域不同——改 `optimizer_switch` 是会话级/全局级的开关，会影响之后的语句、用完还得自己改回来；写 `NO_ICP` 只影响当前这一条 SQL。做对照实验时后者更省事。

* **性能对比实验（`people` 表 100 万条数据）**
    * 造数据通过存储过程完成：`CALL insert_people(1000000);` 调用之后执行时间会相对久一些，跑完先 `SELECT COUNT(*) FROM people;` 确认数据到位。
    * 先把 `profiling` 打开——它默认是关闭的：`SET profiling = 1;`。

| 对照组 | 索引下推状态 | 执行耗时 |
| :--- | :--- | :--- |
| 第 1 组 | 开启（`on`） | 明显更短 |
| 第 2 组 | 关闭（`optimizer_switch` 改 `off`，或 SQL 里加 `NO_ICP`） | 明显更长 |

* 第 2 组把 ICP 关掉再执行同一条语句，光是等它跑完就能明显感觉到时间长了不少；两组一对照，用时上的差别非常明显。
* 想确认会不会是其他原因造成的差别，可以继续看 `SHOW PROFILES;`、`SHOW PROFILE FOR QUERY 1;`、`SHOW PROFILE FOR QUERY 2;`——会发现主要的耗时区别就落在这个执行过程当中，跟其他环节没有关系。
* > 结论：数据量大起来之后 ICP 开启与关闭的耗时差距很大；这不是纸面上的优化，是能实测出来的优化。

### 使用条件与限制

* **针对的访问类型与引擎**
    * 针对访问表的类型（`type` 的那套分类），只有 `range`、`ref`、`eq_ref`、`ref_or_null` 才适用于 ICP。
    * ICP 对 InnoDB 和 MyISAM 两种存储引擎都生效。

* **只适用于二级索引：前提是"会发生回表"**
    * ICP 的一个前提是它一定得回表——回表之前多做了一个比较、多做了一个条件的判断，因为那个字段出现在索引当中了。
    * 如果本身没有回表这个行为，那 ICP 就没有意义了：查询用的就是聚簇索引时聚簇索引里直接就有整行数据、不存在回表，所以 ICP 不能用于聚簇索引；二级索引 + 覆盖索引时覆盖索引不需要回表，所以 ICP 也用不上、不支持。
    * > **定义**：覆盖索引指查询所需要的全部字段都能从索引里取到，因此不需要回表。

* **相关子查询的条件不能使用 ICP**
    * 相关子查询的条件不能使用 ICP，因为涉及到内外条件之间的相关性问题。

* **三条要点收束**
    * ICP 是 MySQL 5.6 的新特性，属于查询优化器的一个具体优化策略，`EXPLAIN` 的 `Extra` 里显示为 `Using index condition`。
    * 原理是把"字段在索引里、但条件用不上索引能力"的那个条件下推到存储引擎层，在回表之前先过滤，从而减少回表次数与随机 I/O 次数；更多时候针对的是联合索引。
    * 默认开启，靠 `optimizer_switch` 里的 `index_condition_pushdown` 开关或 SQL 里的 `NO_ICP` 提示关闭；只适用于 `range`、`ref`、`eq_ref`、`ref_or_null`，且必须会发生回表（二级索引、非覆盖索引），相关子查询的条件不适用。
    * 判断一次查询能不能吃到 ICP 的收益的顺序：先看 `Extra` 里有没有 `Using index condition`，再看所用的索引里有没有那个失效字段，最后看这条语句会不会回表。三者都对得上，性能的差别才是实打实的。

## 其他查询优化策略


### EXISTS 与 IN 的性能取舍

* **两种写法的对应关系与子查询类型**
    * `IN` 写法：`SELECT * FROM employee WHERE manager_id IN (SELECT manager_id FROM department);`——先从部门表里把管理者（`manager_id`）找出来，再看员工表里哪些人是这些管理者。
    * `EXISTS` 写法：`SELECT * FROM employee e WHERE EXISTS (SELECT 1 FROM department d WHERE d.manager_id = e.manager_id);`。
    * > **提示**：`EXISTS` 只是判断"存不存在"，并不关心子查询里查出什么值，所以子查询的 `SELECT` 列表写 `1`、写 `*` 都不影响语义，写 `1` 最直观地表达了这一点。
    * 区别藏在执行方式里：`IN` 的子查询和外层表之间没有引用关系、是不相关子查询；`EXISTS` 的子查询里引用了外层的 `e.manager_id`、是相关子查询。

* **相关子查询的执行方式与选择规则**
    * 相关子查询的执行过程就类似于嵌套循环：外面是 `A`、里面是 `B`，外层每送一条数据进去内层查完出来，再送下一条进去；所以外层这个表的大小会影响整个查询的性能，它小一点会更好。

| 表的大小关系 | 建议写法 | 原因 |
| :--- | :--- | :--- |
| `A` 表小、`B` 表大 | `EXISTS` | 相关子查询，外层 `A` 逐行驱动内层 `B`，小表在外层，循环次数少 |
| `A` 表大、`B` 表小 | `IN` | 不相关子查询，先把小表 `B` 的 `cc` 查出来，外层只需按这几个值做匹配 |

* > 结论：`EXISTS` 走的是相关子查询那条路，外层驱动表越小越好；`IN` 走的是不相关子查询那条路，内层被先算出来的那个表越小越好。两种写法各自把"小表"放在了不同的位置上，所以选法的本质是看哪张表小、小表能不能被放到该放的位置上。

* **两条执行链路与 NULL 处理**

```text
    不相关子查询 (IN)                          相关子查询 (EXISTS)
    外层大表 A                                 外层小表 A
       |                                          |
       |  1. 内层 B 先整体算一次                  |  1. 从 A 取一行
       v                                          v
    内层小表 B  -->  得到一个值的集合          送到 B 去查是否存在
       |             (只有几个值)                  |
       |  2. A 按集合做值匹配                      |  2. 结果返回，再取 A 的下一行
       v                                          v
    输出匹配行                                  循环往复，逐行判定
```

* 左侧 `IN` 的小表只被算一次，外层表拿到一个很小的值集合后做匹配；右侧 `EXISTS` 的判定必须由外层逐行触发，外层有多少行就要驱动多少次内层查询。
* NULL 处理不一样：`IN` 是在值集合里比对，碰到 NULL 会污染比较结果；`EXISTS` 只做存在性判断、不产生值集合，因而不受 NULL 影响。写法选择时这一点也要一并考虑。

### COUNT 三种写法的效率

* **讨论的两个前提**
    * 第一，讲的是 MySQL，不是所有数据库的通用情况；Oracle 有它自己存储引擎的机制和特征，别的数据库不去谈。
    * 第二，讨论的前提是查询表中有多少条记录，不是统计某个字段的非空行数——两者意义完全不同，你要找某个字段非空的行数，用 `COUNT(*)` 本身可能都是错的。
    * > **易错点**：把"表有多少行"和"某个字段有多少个非空值"混成一件事，是这一节最常见的误用。前者是三者的共同目标，后者只有 `COUNT(字段)` 才成立的语义，拿它跟 `COUNT(*)` 比性能没有意义。

* **COUNT(*) 与 COUNT(1) 的等价性**
    * 它们是对所有结果进行 `COUNT`，两者没有本质上的区别，可以理解成性能效率是一样的；很多同学习惯上用 `COUNT(*)` 完全没有问题。
    * 筛选的影响：有 `WHERE` 子句就按条件做筛选；没有 `WHERE` 子句就是对表里所有数据行做一次统计。

* **存储引擎决定的复杂度差异**
    * 用 `MyISAM`：统计表行数是 $O(1)$ 的复杂度，相当于常量级别。
    * 用 `InnoDB`：需要做一次全表扫描，相当于 $O(n)$ 级别的复杂度。
    * MyISAM 的数据表有一个 meta 信息，其中记录了这个表的记录数、叫做 `row_count`，查询的时候直接把值取出来就行；它的一致性由表级锁保证、锁的粒度其实比较粗，也正是因为访问这个表走的是表级锁的方式，它才有机会用这种方式去做记录。
    * InnoDB 支持事务、行级锁和 MVCC，所以没有办法像 MyISAM 一样维护这样一个变量——这是出于数据一致性的考虑；它的粒度更小、并发性更好，但代价就是不能用这样一个现成的变量，只能是扫描全表、通过循环累加计数的方式把结果统计出来。
    * > **提示**：MyISAM 的 $O(1)$ 只对"不带 `WHERE` 的全表行数"成立，因为 `row_count` 记的是整表记录数；一旦加了筛选条件，得实际数一遍，这个捷径就用不上了。

* **InnoDB 下 COUNT 具体字段与索引选择**
    * 用 `COUNT(具体字段)` 时尽量采用二级索引，不建议用主键索引（聚簇索引）：用聚簇索引统计要把这棵 B+ 树整体加载到内存里，聚簇索引的叶子节点放的就是一条条真实的记录、字段肯定更多、加载到内存中占用的内存就会更大；二级索引的叶子节点放的是索引列和主键，数据量更小、加载的成本也就更低。
    * `COUNT(*)` 与 `COUNT(1)` 没有写明具体用哪个字段时，会自动去选一个空间比较小的二级索引；表里有多个二级索引时选择占用空间最小的那个二级索引。
    * 二级索引之间怎么比大小：靠 `key_len` 这个字段——优化器会选 `key_len` 比较小的那个二级索引来做扫描，因为成本更低；有的 `key_len` 是 5、有的是 10、有的来个 63，那加载的量显然就不一样，带有字符串列的索引会更大。

| 统计写法（InnoDB） | 走哪个索引 | 开销来源 |
| :--- | :--- | :--- |
| `COUNT(具体字段)` | 用该字段所在索引，尽量选二级索引 | 二级索引叶子节点只有索引列与主键，比聚簇索引整行数据小而轻 |
| `COUNT(*)` / `COUNT(1)` | 优化器自动挑 `key_len` 最小的二级索引 | 不读聚簇索引；在多个二级索引里选占用空间最小的那个 |

* > 结论：在 InnoDB 里统计表行数，无论写 `COUNT(*)`、`COUNT(1)` 还是 `COUNT(字段)`，都尽量落到二级索引上；写具体字段时靠你来选（选二级索引），不写字段时由优化器按 `key_len` 自动挑最小的那个二级索引。

### SELECT * 的两项代价

* **解析阶段查询数据字典**
    * 你写的是一个星号、感觉挺省事，但底层的查询过程首先要把这个星号转换成表中具体的字段；这个转换需要查询数据字典，也就是系统内部的那些表，把星号展开成具体的列名。系统内部的表里储存的就是用户定义的表以及表里那些具体字段的信息；查这个数据字典肯定要花时间，而且花的时间还挺多。

* **覆盖索引无法生效**
    * 很多时候我们写了 `ORDER BY`、对应的索引也在，但它就是不用，原因就在于你用了星号、根本没有办法使用覆盖索引。
    * > **易错点**：覆盖索引的前提是"查询要的列全都在索引里"。`SELECT *` 要的是整行的所有列，索引里几乎不可能全有，所以覆盖索引直接失效——`ORDER BY` 那个例子里索引明明存在却用不上，根子就在这里。
    * 列出具体的字段反而能用上覆盖索引、效果更好一点；用星号就用不上了。

| 写法 | 解析阶段 | 覆盖索引 |
| :--- | :--- | :--- |
| `SELECT *` | 需要查数据字典，把 `*` 展开成具体列名，耗时较多 | 几乎无法命中，需要回表取整行 |
| `SELECT 具体字段` | 列名已经写明，无需展开 | 字段被索引覆盖时可命中，避免回表 |

* 补充：`select *` 会把整行的所有列都要回来，哪怕二级索引帮你定位到了记录也得回表把别的列补齐；如果只 select 索引里已经有的字段，就不用再回表查整张表的数据了——索引会不会被选中，跟这种代价算得清楚与否直接相关。

### LIMIT 1 的生效条件

* **全表扫描场景**
    * 针对全表扫描时加上 `LIMIT 1`，就是你已经确定了结果集当中只有这一条记录；那就意味着找到一条记录之后就不再继续扫描了，速度确实会加快。

* **已有唯一索引场景**
    * 如果这个字段已经建立了唯一索引那就没必要了：有了唯一索引，找到一条记录之后索引本身的查找就不再往后进行了，这时候加 `LIMIT 1` 的意义也就不大了。
    * > 结论：`LIMIT 1` 的价值在于"提前终止扫描"。全表扫描时它能让你在第一条命中处停下、收益明显；已经有唯一索引时，唯一性本身就保证了查到即止，再加 `LIMIT 1` 属于多余。

* **数据量对索引选择的影响（`LIMIT 10` 的对照）**
    * 同样是查一张表：一种选择是把整张表的数据都查出来，另一种是加上 `limit 10` 只查十条。不加 `limit` 时某个字段上虽然建了索引，优化器最后可能并没有选这个索引，而是让 `explain` 的 `type` 字段变成了 `all`——它的判断是：用了你那个索引、前面还写着 `select *`，用了索引还得回表做全表查询，那还不如干脆直接全表查一遍效率更高。
    * 但要是加上 `limit 10`，优化器一核算：全表扫描可能要翻一千条、一万条，而你只要十条，行，那我就用一下你这个索引，成本可能更低。
    * 造表时把数据量造得不小的原因也在这里：数据量的多少对优化器的选择是有影响的；另一方面演示用索引和不用索引时也想看出查询时间的差距，数据量稍微大一点效果能明显一些。

### 事务的尽早提交

* **COMMIT 释放的四类资源**
    * 回滚段上用于恢复数据的信息，它对应在 UNDO 日志当中。
    * 被程序语句获得的锁：提交事务之前相应地会有一些锁的获取，提交之后这些锁资源就释放了。
    * REDO、UNDO 日志空间的释放（UNDO 同时也涉及回滚）。
    * 以及管理上述三种资源的内部花费。

```text
    未提交的事务持有                          COMMIT 之后
      UNDO 日志（回滚段恢复信息）  --------->  释放
      事务期间获得的锁              --------->  释放
      REDO / UNDO 日志空间          --------->  释放
      三类资源的管理开销            --------->  随之减少
```

* 事务提交是这四类资源的统一释放点，事务开得越久、持有得越多，这部分开销就累计得越大。
* > **易错点**：前提是你该提交的时候才提交。提交了跟不提交是有区别的，但有时候你要是不该提交那就别乱提交——一旦提交，这个事务就结束了。

## 索引使用的成本判据


### 成本是规则之上的裁决者

* **规则的性质与推导方式**
    * 那些"索引失效"的规则是拿来帮我们做分析、做判断的，让我们写 SQL 的时候心里有个数；它们本身就是查询优化器从成本出发总结出来的近似规律，成本的账一重算，规则立刻就能被打破。
    * 判据始终是成本，不是规则本身：语句一改、字段一换、回表成本一省，结论就可能翻转。

* **规则被打破的两处实证**
    * `WHERE age != 20` 配 `SELECT *` 时索引被放弃；同一条件改成 `SELECT age, name` 后回表成本被砍掉、索引被启用。
    * `WHERE name LIKE '%...'` 配 `SELECT *` 时索引被放弃；改成 `SELECT id, age, name`（索引列 + 主键）后索引用上了，甚至只查 `age` 照样能用上。

* **优化器只看哪条路更省钱**
    * 用不用索引最终还是优化器说了算：SQL 写完了、字段上确实也有索引，但优化器一算发现不用索引的成本可能更低，它还真就可能不用。
    * > **提示**：遇到"明明建了索引，结果还不如不建"的情况，要反过来想一想：是不是索引设置本身有问题，才让优化器把它放弃了。

* **规则的适用前提是环境不变**
    * 判定结论都依赖当时的表数据量：数据量不一样了，例子的结果也可能不同。
    * SQL 语句是否使用索引，跟数据库的版本、数据量、数据的选择度都有关系。
    * 两个索引同时存在时 MySQL 会自动选择最优的方案，而且随着数据量的变化它的选择也会跟着改变。

### 统计估算与工具的认知边界

* **rows 与 filtered 是估算值**
    * `rows` 和 `filtered` 是基于系统数据字典采样得出的概率分布估算值，并非实际运行时的真实条目数；不能将 `rows` 的数值直接等同于实际执行返回的记录数。

* **EXPLAIN 不感知缓存状态**
    * `EXPLAIN` 评估的是一条 SQL 在理论物理架构下的访问方法与成本估算，完全不考虑当前数据页是已经缓存在 Buffer Pool 中还是需要从物理固态硬盘里冷读。

* **EXPLAIN 不展现推导过程**
    * 它呈现的是优化器最终选定的"既定事实"；优化器在三个索引中挑了索引 A、为什么不选 B 和 C、内部 I/O 成本与 CPU 成本各算出了多少，普通 `EXPLAIN` 无法获知，需要借助 `optimizer_trace`。

* **EXPLAIN 看不到程序性构件的运行期开销**
    * SQL 触发底层存储过程、触发器或用户自定义函数（UDF）时，这些程序性构件在运行期产生的隐式开销与锁竞争，在静态分析中完全失真。

* **成本模型的落脚点**
    * 成本由 `read_cost` 与 `eval_cost` 构成，公式中用到表中的行数以及 `filtered` 百分比；数值单位不是时间，可以理解成 1。
    * 优化器基于成本开销（cost）做选择，不是基于规则式，也不是基于语义式。
