## 1. SQL 三分类与库表存储层级

> **一句话主旨**：划定 DDL、DML、DCL 三条语句边界，给出数据从服务器到字段行的四级包含关系与落地时序。

### 1.1 三大语言类别与关键字归属

* **数据定义语言（Data Definition Language，DDL）**
    * > **定义**：负责数据库内部逻辑对象（数据库、数据表、视图、索引等）的定义与属性变更。
    * 核心关键字为 `CREATE`、`ALTER`、`DROP`、`RENAME`，以及用于高速清空表数据的 `TRUNCATE`。
    * > 来源: P49
* **数据操作语言（Data Manipulation Language，DML）**
    * > **定义**：负责表中数据的读写与流转。
    * 包含增 `INSERT`、删 `DELETE`、改 `UPDATE`、查 `SELECT`；增删改必须以表结构建立完成为前提才能施展。
    * > 来源: P49
* **数据控制语言（Data Control Language，DCL）**
    * > **定义**：负责事务保障与权限安全管控。
    * `COMMIT`（提交）与 `ROLLBACK`（回滚）负责划定事务边界，在事务细分领域也被称为事务控制语言（TCL）。
    * `GRANT`（赋权）与 `REVOKE`（撤权）由 DBA 或运维人员用于限制各系统账号的操作边界。
    * > 来源: P49, P52

### 1.2 数据存储四级包含与落地时序

* **数据库管理系统（DBMS）**
    * > **定义**：如 MySQL 8.0 的服务进程 `mysqld`，运行在数据库服务器之上。
    * 四级包含关系由外向内为：数据库服务器 → DBMS → 数据库（Database / Schema）→ 数据表（由行记录与列字段构成的二维关系矩阵）→ 字段与记录行。
    * > 来源: P49
* **一条业务数据的落地四阶段**
    * 启动并连接数据库服务器：通过命令行、Navicat、DataGrip 等客户端与运行中的 DBMS 进程建立长连接。
    * 创建独立的业务数据库：确定业务边界，为新系统划分独立的 Schema 逻辑隔离区。
    * 确认实体字段并创建数据表：定义列名、数据类型、长度规格与约束机制，固化表结构。
    * 写入持久化数据：通过 `INSERT` 将真实数据行写入底层数据页。
    * 因果时序铁律为先 DDL 建库建表，再 DML 写入业务数据，最后结合业务需求做查询与维护。
    * > 来源: P49

## 2. 建库语法与字符集继承

> **一句话主旨**：给出建库的两种写法与字符集继承规则，锁定生产环境可反复重跑的建库黄金模板。

### 2.1 默认字符集与显式字符集建库

* **默认字符集建库**
    * 极简语法为 `CREATE DATABASE mytest1;`，未显式声明时字符集（Character Set）与校对规则（Collation）自动继承当前服务器层级的默认配置。
    * 建库属实例级管理操作，执行账号必须具备权限；未授予 `CREATE` 权限的普通业务账号会被直接拒绝并抛出 `Access denied` 错误。
    * > 来源: P49
* **显式字符集建库**
    * 语法为 `CREATE DATABASE mytest2 CHARACTER SET 'gbk';`，关键字 `CHARACTER SET` 可缩写为 `CHARSET`。
    * `SHOW VARIABLES LIKE 'character_%';` 查看层级默认配置，重点变量为 `character_set_server`（服务器级默认字符集）与 `character_set_database`（当前默认数据库使用的字符集）。
    * MySQL 8.0 及后续版本官方默认字符集为 `utf8mb4`，校对规则为 `utf8mb4_0900_ai_ci`；企业存量系统大量服役的 MySQL 5.7 官方默认字符集为西欧语言的 `latin1`（ISO-8859-1）。
    * > **易错点**：5.7 环境建库不显式指定字符集且管理员未预先修改 `my.cnf` 时，库会继承 `latin1`，后续插入中文直接引发乱码或报字符集越界错误。
    * > 来源: P49
* **建库结构的元数据检视**
    * 语法为 `SHOW CREATE DATABASE mytest1;`；终端下列宽受限可改用 `SHOW CREATE DATABASE mytest1\G` 做行列转置。
    * 输出可读出底层生效的 `DEFAULT CHARACTER SET`、`COLLATE` 与加密属性（`DEFAULT ENCRYPTION='N'`）。
    * > 来源: P49

### 2.2 幂等建库与版本陷阱

* **重复建库的硬性报错与幂等需求**
    * 在已有同名库的实例上再次执行相同的建库语句会硬性报错 `ERROR 1007 (HY000): Can't create database 'mytest2'; database exists`，使自动化脚本运行、CI/CD 持续集成发布与批量刷库链路整体中断退出。
    * 幂等性的目标为多次执行与一次执行产生相同结果且不引发系统异常，对应的安全判断分支语法为 `CREATE DATABASE IF NOT EXISTS mytest2 CHARACTER SET 'utf8';`。
    * > 来源: P49
* **IF NOT EXISTS 的判定逻辑与黄金模板**
    * > **结论**：当 DBMS 检测到底层已存在名为 `mytest2` 的 Schema 实体时，将完全跳过该数据库的创建逻辑，也不对其现有属性做任何更新，仅仅是抑制住本该抛出的 1007 错误并静默结束，控制台返回 `Query OK, 1 warning`；已显式声明为 `gbk` 的字符集不会被这次执行覆盖改写成 `utf8`。
    * 生产推荐黄金模板为 `CREATE DATABASE IF NOT EXISTS mytest3 CHARACTER SET 'utf8mb4';`，兼顾防重报错与跨版本编码统一。
    * 企业更换底层数据库版本的动力极其缓慢（数据迁移与存储引擎升级成本远高于业务代码重构），核心生产库常仍运行在 MySQL 5.7 上，因此无论开发环境是 8.0 还是 5.7，建库 DDL 都应写全 `IF NOT EXISTS` 与 `CHARACTER SET 'utf8mb4'`。
    * > 来源: P49

### 2.3 库列表、作用域切换与跨库检视

* **库清单与当前会话定位**
    * `SHOW DATABASES;` 输出当前用户具有访问权限的所有数据库；新装系统通常自带 `information_schema`、`performance_schema`、`sys` 与核心系统库 `mysql`。
    * 未选库直接查表报 `ERROR 1046 (3D000): No database selected`；库中无该表报 `ERROR 1146 (42S02): Table 'mytest1.employees' doesn't exist`。
    * `USE mytest2;` 将当前会话上下文切换到指定数据库，后续所有表级 DDL 与 DML 指令均在该库上下文中运行。
    * `SELECT DATABASE();` 或 `SELECT DATABASE() FROM DUAL;` 返回当前活跃库名；尚未执行过 `USE` 时返回 `NULL`。
    * > 来源: P49
* **跨库检视与图形化工具的本质**
    * `SHOW TABLES;` 查看当前已激活库中的全部数据表；`SHOW TABLES FROM mysql;` 在不打断、不改变当前会话上下文的前提下检视其他库的表。
    * > **提示**：Navicat、SQLyog、DataGrip 在对象树中展开节点或刷新列表，底层只是自动向服务端投递 `SHOW DATABASES`、`USE 数据库名`、`SHOW TABLES`、`SHOW CREATE DATABASE` 等标准指令并渲染结果集。
    * > 来源: P49

## 3. 改库、改名与删库红线

> **一句话主旨**：明确库级字符集变更的唯一安全窗口，封死数据库改名这条路，并划出系统库不可触碰的删除红线。

### 3.1 ALTER DATABASE 的字符集变更窗口

* **修改数据库字符集**
    * 语法为 `ALTER DATABASE mytest2 CHARACTER SET 'utf8mb4';`，执行后可用 `SHOW CREATE DATABASE mytest2;` 验证字符集已被更新。
    * 语法中严禁添加 `IF NOT EXISTS` 逻辑，因为 `ALTER` 的对象必须是一个已经存在的实体。
    * > 来源: P49
* **允许修改的唯一安全窗口期**
    * 生产环境中库级修改极为罕见：库一旦投入运行，其下挂载几十上百张表、沉淀千万级甚至过亿数据，贸然改动库级配置往往引发级联风险。
    * 唯一安全窗口是数据库刚通过脚本创建完成、表尚未建立，且突然发现字符集或校对规则声明错误的初期极短时间内。
    * 因此库与表的命名、字符集选型、主从同步规则必须在架构需求分析与数据库设计说明书中敲定并组织评审。
    * > 来源: P49

### 3.2 数据库重命名的底层真相与生产禁区

* **RENAME DATABASE 的历史与废弃**
    * > **易错点**：MySQL 中绝对不要尝试直接修改数据库的名称。
    * 官方仅在 5.1.7 版本尝试引入过 `RENAME DATABASE 旧库名 TO 新库名;`，因库在物理磁盘上对应整个存储目录、内部交织存储引擎文件（`.ibd`）、表定义元数据、外键依赖、触发器与权限表，物理改名在测试阶段频繁导致严重的数据损坏与丢失，仅过几个补丁版本（5.1.23）即被紧急且永久废弃。
    * > 来源: P49
* **第三方工具「重命名」菜单的四步真相**
    * 第 1 步 `CREATE DATABASE` 创建全新目标库；第 2 步逐一提取原库所有表的 DDL 并在新库重建；第 3 步将原库所有表的数据批量导出并导入新库；第 4 步数据迁移校验无误后执行 `DROP DATABASE` 彻底销毁旧库。
    * 该流程在数据量极大的生产环境中耗时漫长、严重锁表，一旦网络中断或发生异常将造成毁灭性灾难。
    * > 来源: P49

### 3.3 DROP DATABASE 与系统库保护红线

* **基础删除与防错语法**
    * 直接删除语法为 `DROP DATABASE mytest1;`，库存在时底层对应目录及内部所有数据表、视图、存储过程被物理销毁。
    * 库不存在时再次执行报 `ERROR 1008 (HY000): Can't drop database 'mytest1'; database doesn't exist`；工程推荐写法为 `DROP DATABASE IF EXISTS mytest1;`，不存在时仅给出静默警告、会话判定为 `Query OK`，批处理链路不会崩塌。
    * > 来源: P49
* **四条核心内置系统库**
    * `mysql` 存储核心元数据、用户账号、权限表、密码与审计；`information_schema` 为 ANSI 标准的数据字典视图，存放表、列、索引定义。
    * `performance_schema` 为实例底层运行时资源监控、锁、内存与性能监控统计；`sys` 是将 `performance_schema` 复杂度封装的高级诊断视图。
    * > **易错点**：销毁核心系统库会使 MySQL 进程丧失身份校验机制与元数据寻址能力，轻则报错拒绝服务，重则无法重启直接瘫痪；一切建库、改库、删库练习与测试只能限制在自己亲手建立的业务测试库范围内。
    * > 来源: P49

## 4. 数据类型与字段规格

> **一句话主旨**：锁定建表必备的四类基石类型，给出金额、电话、性别等典型字段的类型定则与长度对磁盘 I/O 的影响。

### 4.1 四大基石类型与取值范围

* **整数类型 `INT`**
    * 占 4 个字节（32 位二进制），未显式声明 `UNSIGNED`（无符号）属性时默认属于有符号整数，取值范围为 $-2^{31} \sim 2^{31}-1$，即 $-2,147,483,648 \sim 2,147,483,647$。
    * 日常业务主键 ID、计数器、部门编号等无特殊大数值要求的场景直接使用 `INT` 即可满足。
    * > 来源: P50
* **小数与数值类型 `DOUBLE` 与 `DECIMAL`**
    * 带小数点的浮点数值（如员工薪资 `salary`）在建表演练中暂用 `DOUBLE`；定点数 `DECIMAL(M, D)` 拥有绝对精确的十进制计算能力，是资金财务核算场景的唯一工业标准。
    * `DOUBLE(10, 2)` 的 10 代表总显示位数（有效数字长度）、2 代表小数部分保留 2 位，整数部分最多容纳 $10-2=8$ 位数字。
    * > **易错点**：`FLOAT` 与 `DOUBLE` 属遵循 IEEE 754 标准的二进制浮点数，四则运算存在天然的浮点舍入误差；阿里巴巴《Java开发手册》硬性规定涉及金钱、价格、账户余额的字段严禁使用 FLOAT 与 DOUBLE，必须强制使用 DECIMAL。
    * > 来源: P50, P51, P53
* **日期时间类型 `DATE` 与年份类型 `YEAR`**
    * `DATE` 专用于记录纯粹的「年-月-日」（如 `2026-09-14`），不携带时分秒；需要记录完整时刻可拓展为 `DATETIME` 或 `TIMESTAMP`。
    * `YEAR` 用于记录出版年份等纯年份语义，既可传入四位纯数字，也可传入单引号包裹的合规年份字符串。
    * > **易错点**：声明日期类型必须拼写为 `DATE`，切勿笔误写成 `DATA`。
    * > 来源: P50, P54, P57
* **变长字符串类型 `VARCHAR(M)`**
    * 用于存储可变长度的文本字符串。
    * > **易错点**：必须在括号中显式声明最大字符长度 $M$（例如 `VARCHAR(15)`）；15 表示该字段最多容纳 15 个字符，无论中文字符还是英文字母均按 1 个计；不传长度参数时 SQL 解析器直接报语法错误拒绝执行。
    * > 来源: P50

### 4.2 显示宽度与整型括号里的数字

* **整型显示宽度与物理字节数**
    * `INT(7)` 中的 7 不代表该整型占用 7 个字节，`INT` 无论括号内写几，底层物理存储永远固定占用 4 个字节。
    * 括号内数字仅代表配置了 `ZEROFILL`（零填充）属性时的显示宽度，数值 `123` 在 `INT(7) ZEROFILL` 下展示为 `0000123`。
    * > 来源: P54
* **三类括号数字的语义区分**
    * `VARCHAR(15)` 的 15 是该字段最多容纳的字符数，中文字符与英文字母均按 1 个计；不传长度参数会让解析器直接报语法错误。
    * `DOUBLE(10, 2)` 的 10 是总显示位数、2 是小数保留位数，整数部分最多容纳 $10-2=8$ 位数字。
    * `INT(7)` 的 7 只作用于 `ZEROFILL` 的展示效果，既不改变 4 字节的物理占用，也不改变取值范围。
    * > 来源: P50, P51, P54

### 4.3 CHAR 与 VARCHAR 的存储机理与选型

* **定长字符类型 `CHAR(M)`**
    * > **定义**：严格分配定长空间、无需长度前缀，直接通过固定物理偏移定位数据的字符类型。
    * `CHAR(1)` 存储单个汉字在 UTF-8 编码下占 3 字节；值长度完全固定的枚举类字段（如性别、状态码、MD5 哈希）优先选用。
    * 性别通常仅取「男」或「女」，选用 `CHAR(1)` 比动态变长的 `VARCHAR` 更加紧凑高效。
    * > 来源: P54, P58
* **变长字符类型 `VARCHAR(M)`**
    * 必须额外耗费 1~2 字节维护长度列表，读取时需解析与维护长度头信息。
    * 姓名、家庭住址、联系电话等长度不定的文本使用 `VARCHAR`，按实际内容动态分配存储空间。
    * > 来源: P54, P58

| 对比维度 | `CHAR(M)` | `VARCHAR(M)` |
| :--- | :--- | :--- |
| 空间分配 | 定长分配，无需长度前缀 | 变长分配，额外 1~2 字节长度偏置 |
| 寻址方式 | 固定物理偏移直接定位数据 | 需解析与维护长度头信息 |
| 典型字段 | 性别、状态码、MD5 哈希 | 姓名、住址、联系电话 |
| 性别字段取舍 | `CHAR(1)` 更紧凑高效 | 需额外长度偏置，不如定长紧凑 |

### 4.4 字段存储长度对查询 I/O 的深层影响

* **数据页（Page）与磁盘 I/O 次数**
    * 定义：InnoDB 引擎管理磁盘与内存数据交换的基本单位，默认大小为 16KB。
    * 字段类型冗余偏大（如过度使用 `BIGINT`、`VARCHAR(255)`）时，单个 16KB 数据页约容纳 1000 行；查询 10000 条记录需从磁盘执行 10 次 I/O，载入 10 个数据页到 Buffer Pool。
    * 字段类型精准克制（如按业务分配 `TINYINT`、`VARCHAR(20)`）时，单个数据页约容纳 10000 行；查询同样 10000 条记录仅需 1 次磁盘 I/O，载入 1 个数据页即可命中。
    * 计算机系统中最昂贵的性能开销就是磁盘 I/O；压缩字段长度的本质是提高内存命中率、降低磁盘读写频次。
    * > 来源: P53
* **类型选型现实标尺**
    * 人类年龄通常在 0 到 150 岁之间，推荐 `TINYINT UNSIGNED`（取值范围 0~255，仅占 1 字节），没有必要使用占 4 字节的 `INT`。
    * 乌龟寿命数百岁，超过 255 但在数万以内，可使用 `SMALLINT UNSIGNED`（0~65535，占 2 字节）。
    * 恐龙化石与宇宙年龄为数亿年至上百亿年，需上升到 `INT`（约 42 亿）或 `BIGINT`。
    * 业务建模时应评估该字段未来 3~5 年内的最大极限范围，选择满足需求的最小数据类型。
    * > 来源: P53

### 4.5 典型业务字段的类型定则

* **电话号码必须使用 `VARCHAR`**
    * 国内手机号通常为 11 位，早期的 4 字节标准 `INT` 最大只能表示到 21 亿，不仅面临溢出风险，且号码中可能包含前导 0（例如固话区号 `010-`）或国际区号符号（`+86`），属纯字符文本语义。
    * 联系电话字段使用 `VARCHAR(25)`，以容纳连字符、固话或国际区号。
    * > 来源: P51, P58
* **员工信息表的字段选型矩阵**
    * 员工工号用 `INT`（整数标识，满足常规企业自增主键容量）；员工姓名用 `VARCHAR(15)`（变长中文姓名通常不超过 15 个字符）。
    * 性别用 `CHAR(1)`（离散固定单字符，定长最优）；家庭住址用 `VARCHAR(35)`（变长地址按需分配）；薪资用 `DOUBLE(10, 2)`（总长 10 位保留 2 位小数）。
    * 图书信息表的字段选型为 `id INT`、`name VARCHAR(50)`、`authors VARCHAR(100)`、`price FLOAT`、`pubdate YEAR`、`note VARCHAR(100)`、`num INT`。
    * > 来源: P57, P58

## 5. 直接声明建表与结构检视

> **一句话主旨**：给出从零定义字段的原生建表语法、两类结构检视方式，以及元数据里隐式生效的默认属性。

### 5.1 CREATE TABLE 语法与幂等保障

* **基础建表语法**
    * 结构为表名后跟一对小括号，括号内逐行声明字段名与数据类型，多项之间用逗号分隔，最后一项后不加逗号。

```sql
CREATE TABLE [IF NOT EXISTS] 表名 (
    字段名1 数据类型,
    字段名2 数据类型,
    ...
    字段名n 数据类型
);
```

* 执行建表同样需要当前账号具备 DDL 操作权限；重复建同名表会报 `Table 'myemp1' already exists` 的硬性异常，应养成使用 `IF NOT EXISTS` 的防御性编程习惯。
* 新建空表执行 `SELECT * FROM myemp1;` 返回 `Empty set (0.00 sec)`，因为底层仅建立了元数据框架。
* > 来源: P50
* **标识符与保留字的冲突处理**
    * `name`、`authors`、`code`、`owner` 等词汇在部分客户端或高版本解析器中易与内置函数、保留字、关键字高亮冲突，最规范的工程习惯是用一对反引号包裹（如 `` `name` ``、`` `code` ``）。
    * 选用 SQL 保留字作为标识符会极大增加 SQL 维护成本与语法解析出错的概率。
    * > 来源: P53, P54, P57, P58

### 5.2 表结构的两种检视方式

* **二维矩阵视图（DESCRIBE / DESC）**
    * 语法为 `DESC myemp1;`，输出六列信息：列名（`Field`）、已生效的数据类型与长度限制（`Type`）、是否允许为空（`Null`）、是否包含主键或外键索引（`Key`）、默认值（`Default`）与附加属性（`Extra`）。

| Field | Type | Null | Key | Default | Extra |
| :--- | :--- | :--- | :--- | :--- | :--- |
| id | int | YES |  | NULL |  |
| emp_name | varchar(15) | YES |  | NULL |  |
| hire_date | date | YES |  | NULL |  |

* > 来源: P50
* **完整 DDL 源码视图（SHOW CREATE TABLE）**
    * 语法为 `SHOW CREATE TABLE myemp1\G`，输出还原建表源码，是核对字符集、存储引擎与默认值的源码级依据。

```text
*************************** 1. row ***************************
       Table: myemp1
Create Table: CREATE TABLE `myemp1` (
  `id` int DEFAULT NULL,
  `emp_name` varchar(15) DEFAULT NULL,
  `hire_date` date DEFAULT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3
1 row in set (0.00 sec)
```

* > 来源: P50

### 5.3 元数据中隐式生效的默认属性

* **默认值补全与存储引擎指定**
    * 建表时未声明 `NOT NULL` 的列，系统自动为每列追加 `DEFAULT NULL`。
    * 数据表默认搭载 MySQL 核心的事务型存储引擎 `ENGINE=InnoDB`。
    * > 来源: P50
* **表级字符集的强制继承**
    * 若建表时未使用 `CHARACTER SET` 显式声明表级字符集，数据表将强制继承其所在数据库的字符集配置。
    * 示例表末尾标注 `DEFAULT CHARSET=utf8mb3`，原因是其所在库由 MySQL 5.7 环境导出的备份脚本而来；5.7 中通用汉字编码为使用 3 字节表示一个字符的 `utf8`，在 8.0 内部被规范命名为 `utf8mb3`，新表自然继承该配置。
    * > 来源: P50

## 6. CTAS 查询派生建表

> **一句话主旨**：讲清基于 SELECT 结果集固化物理表的语法、列名映射方式，以及提取零数据空表模板的恒假条件写法。

### 6.1 结构与数据的同步固化

* **CTAS 语法与自动类型推导**
    * 官方技术规范称为 CTAS，即 `CREATE TABLE ... AS SELECT`，由一条 `SELECT` 语句的二维结果集直接固化为全新物理数据表。
    * 语法为 `CREATE TABLE myemp2 AS SELECT employee_id, last_name, salary FROM employees;`，列类型随查询投影自动推导：`employee_id` 推为 `int`，`last_name` 继承源表 `varchar(25)`，`salary` 继承为 `double(8,2)`。
    * 执行 `SELECT * FROM myemp2;` 完整输出 107 条记录，说明建表与数据导入一次性原子完成。
    * > **结论**：CTAS 是纯粹的物理副本拷贝，新表生成后与源表在物理存储上彻底解耦，后续对 `myemp2` 的任何增删改都不会波及源表。
    * > 来源: P50
* **跨库引用源表**
    * 在非源库会话下必须显式写明 `库名.表名`，否则报 `ERROR 1146 (42S02): Table 'test01_office.departments' doesn't exist`。
    * 语法为 `CREATE TABLE dept02 AS SELECT * FROM atguigudb.departments;`；跨库建表能够执行的前提是当前账号具备跨库查询授权。
    * > 来源: P54

### 6.2 列别名映射与复杂查询融入

* **列别名即物理字段名**
    * `SELECT` 子句中赋予列的别名（Alias）将直接作为新数据表的持久化物理字段名，新表字段名不强制与源表保持一致。
    * 内连接派生建表示例：抽取 `e.employee_id AS emp_id`、`e.last_name AS emp_name`、`d.department_name`，新表字段名精确呈现为 `emp_id`、`emp_name`、`department_name`。
    * > 来源: P50
* **连接与聚合查询可直接派生成表**
    * CTAS 的查询子句完全支持复杂的连接查询与聚合分析，列别名与连接条件可在同一条建表语句中并用。

```sql
CREATE TABLE myemp3
AS
SELECT 
    e.employee_id AS emp_id,
    e.last_name AS emp_name,
    d.department_name
FROM employees e 
JOIN departments d
  ON e.department_id = d.department_id;
```

    * > 来源: P50

### 6.3 零数据空表模板的恒假条件

* **业务边界值过滤的隐患**
    * 为历史归档、分库分表或压测准备结构一致但内部为空的「白板表」，若用 `WHERE department_id > 10000` 之类的业务边界值过滤，开发人员无法在理论上保证未来业务不会新增大于 10000 的部门编号，一旦源数据偏移脚本就会漏进脏数据。
    * > 来源: P50
* **恒假断言 `WHERE 1 = 2` 的运行机理**
    * 工业标准写法为 `CREATE TABLE employees_blank AS SELECT * FROM employees WHERE 1 = 2;`。
    * 存储引擎扫描时每行计算 `1 = 2` 恒得数值 0（即 FALSE），所有行在第一道过滤网被全部拦截并丢弃，查询引擎向 DDL 管道输送「具备完整二维字段元数据头、数据行为 0」的结果集。
    * 验证结果：`SELECT * FROM employees_blank;` 返回 `Empty set (0.00 sec)`，新表具备源表全部字段定义而数据记录为 0。
    * > 来源: P50

### 6.4 两种建表范式的工程对比

| 比较维度 | 直接声明定义 | CTAS 查询派生 |
| :--- | :--- | :--- |
| 语法核心 | `CREATE TABLE 表名 (列名 类型, ...)` | `CREATE TABLE 表名 AS SELECT ...` |
| 数据源依赖 | 无需依赖任何现成表，从物理底层独立构建 | 必须依赖至少一张已存在的基表或复杂视图 |
| 数据填充 | 仅生成空表结构，后续需配合 DML 灌入数据 | 表结构创建与历史数据导入一次性原子完成 |
| 列名定义 | 显式手工书写，精细可控 | 继承查询结果列名，可用 `AS 别名` 映射 |
| 适用场景 | 全新模块研发、核心业务实体架构首次落地 | 报表中间表落盘、历史数据归档、零数据模板克隆 |

* **核心分水岭**
    * 数据源依赖与数据填充时机是两者的分界线：直接声明定义从物理底层独立构建、只产出空结构，数据须后续配合 DML 灌入；CTAS 必须依赖至少一张已存在的基表或复杂视图，并把建表与历史数据导入合并为一次性原子操作。
    * 列名来源也不同：前者由开发人员显式手工书写、精细可控，后者直接继承查询结果列名并可用 `AS 别名` 重映射。
    * > 来源: P50
* **面试应答的规范表述**
    * 第一种是使用标准 DDL 显式定义列名、数据类型与完整约束的原生建表法。
    * 第二种是利用 CTAS 语法（`CREATE TABLE ... AS SELECT`），基于已有结果集快速派生结构并按需同步数据的查询衍生建表法。
    * > 来源: P50

## 7. ALTER TABLE 列级操作

> **一句话主旨**：把新增、改属性、改列名、删列四类列级操作的条件与边界固化下来，并给出不可回滚与拦截规则。

### 7.1 新增列与位置定位

* **追加新列与默认落位**
    * 语法为 `ALTER TABLE myemp1 ADD salary DOUBLE(10, 2);`，新增列默认排在整张表的最后一行。
    * `ALTER TABLE pet ADD COLUMN owner_birth DATE;` 中关键字 `COLUMN` 可以省略；初始追加的新字段在所有已有历史记录中默认自动赋为 `NULL`。
    * > 来源: P51, P58
* **绝对定位：`FIRST` 与 `AFTER 列名`**
    * `FIRST` 将新字段强制置于整张数据表的第一列，如 `ALTER TABLE myemp1 ADD phone_number VARCHAR(20) FIRST;`。
    * `AFTER 列名` 将新字段紧随插入到指定列之后，如 `ALTER TABLE myemp1 ADD email VARCHAR(45) AFTER emp_name;`；执行后 `DESC myemp1;` 可见列顺序被严格重构。
    * 相对位置调动同样可用于已有列的调整：`ALTER TABLE customers MODIFY c_contact VARCHAR(50) AFTER c_birth;`。
    * > 来源: P51, P54

### 7.2 修改列属性 MODIFY

* **语法与适用场景**
    * 语法为 `ALTER TABLE 表名 MODIFY 字段名 新类型 [新约束];`，用于调整已存在字段的存储规格与默认值；`MODIFY` 只改类型、长度、约束或相对顺序，不改列名。
    * 长度扩容示例 `ALTER TABLE myemp1 MODIFY emp_name VARCHAR(25);`，进一步扩容并追加默认缺省值为 `ALTER TABLE myemp1 MODIFY emp_name VARCHAR(35) DEFAULT 'aaa';`，此后插入未显式指定姓名时系统自动填充该默认值。
    * > 来源: P51, P54
* **生产红线：严禁随意修改核心数据类型**
    * 将显然用于存文本的 `email` 列误定义为 `INT` 属严重设计失误，应在需求与代码评审阶段被彻底拦截。
    * 表中已沉淀真实数据时，数值型强行改为字符型可能尚能兼容，但把含字符的列改为数值或日期、或缩小存储容量时，底层无法转换的数据行会直接触发硬性报错并中断事务，甚至造成静默截断与数据损坏。
    * > 来源: P51

### 7.3 重命名列 CHANGE

* **语法与强制要求**
    * 语法为 `ALTER TABLE 表名 CHANGE 旧列名 新列名 数据类型 [约束条件];`。
    * > **易错点**：使用 CHANGE 重命名列时，必须在给出新列名之后再次完整提供该列的数据类型；即使不打算改动任何类型与长度，也必须把原有类型完整写上，否则解析器因缺少列规格定义而抛出语法错误。
    * > 来源: P51, P54
* **复合操作与实例**
    * 因 `CHANGE` 强制要求输入数据类型，它天然支持重命名列的同时一并调整数据类型或长度。
    * 示例：`ALTER TABLE myemp1 CHANGE salary monthly_salary DOUBLE(10, 2);`、`ALTER TABLE customers CHANGE c_contact c_phone VARCHAR(50);`、`ALTER TABLE employees CHANGE birth birthday DATE;`。
    * > 来源: P51, P54

### 7.4 删除列 DROP COLUMN

* **语法与物理后果**
    * 语法为 `ALTER TABLE 表名 DROP COLUMN 列名;`，关键字 `COLUMN` 可写出以增加语义可读性，也可简写为 `DROP 列名`。
    * 执行后整张表中该列存储的所有历史数据被物理抹除，且 DDL 操作不提供事务回滚保障；若该字段积攒了数年高价值业务元数据，误删且无实时有效的冷热备份镜像，后果等同于全表被毁。
    * > 来源: P51, P53
* **列名核实与报错格式**
    * 待删列名不存在时报 `ERROR 1091 (42000): Can't DROP 'email'; check that column/key exists`。
    * 执行字段级物理删除前必须先通过 `DESC 表名;` 核实列名准确性，例如误写 `dept_id` 而实际列为 `department_id` 时同样触发 1091 报错。
    * > 来源: P51, P54

### 7.5 长度缩窄与结构变更的边界行为

* **缩短长度被数据库拒绝**
    * 若表中已插入真实数据且存在超过目标长度的值（如 22、23 位的手机号要压到 `VARCHAR(20)`），MySQL 会直接拒绝执行并报错终止。
    * 该行为是数据库的自我数据保护机制：系统绝不允许因表结构变更而悄无声息地截断丢失现存合法数据。
    * > 来源: P54
* **结构变更的不可回滚性**
    * `ALTER TABLE` 属典型 DDL 操作，具备不可回滚性，该列一旦增加到数据字典中就无法通过事务 `ROLLBACK` 撤回。
    * 想撤销只能再次发起 DDL 语句反向操作，例如 `ALTER TABLE pet DROP COLUMN owner_birth;`。
    * > 来源: P58

## 8. 重命名、删除与截断

> **一句话主旨**：收拢表级重命名的两种语法、幂等删除的写法与物理销毁范围，以及保留骨架的截断清空语义。

### 8.1 表重命名的两种语法

* **独立动词命名法（推荐）**
    * 语法为 `RENAME TABLE myemp1 TO myemp11;`，动词结构与 `CREATE TABLE`、`DROP TABLE` 高度对称，是标准范式。
    * 执行后原表元数据被更新为新名，访问旧表名报 `ERROR 1146 (42S02): Table 'atguigudb.myemp1' doesn't exist`。
    * > 来源: P51, P54
* **ALTER 衍生语法与收敛准则**
    * 语法为 `ALTER TABLE myemp2 RENAME TO myemp12;`，其中 `TO` 关键字可省略，写成 `ALTER TABLE myemp2 RENAME myemp12` 同样合法。
    * 两种写法底层效果完全等价，但日常代码规范与脚本编写推荐统一收敛到 `RENAME TABLE 旧表名 TO 新表名;`，以降低记忆负荷与维护成本。
    * > 来源: P51

### 8.2 DROP TABLE 与幂等删除

* **防错语法与报错格式**
    * 语法为 `DROP TABLE [IF EXISTS] 表名;`；删除不存在的表报 `ERROR 1051 (42S02): Unknown table 'atguigudb.myemp2'`。
    * 生产推荐写法为 `DROP TABLE IF EXISTS myemp2;`，即使表不存在也输出 `Query OK, 0 rows affected, 1 warning`，清库脚本与自动化部署链路顺畅通过。
    * > 来源: P51
* **物理空间回收的三连锁销毁**
    * 表元数据结构抹除：数据字典中该表的列定义、主外键关系、触发器等全部销毁。
    * 表数据物理销毁：数据页上沉淀的全部记录被标为废弃并抹除。
    * 物理空间回收：该表在磁盘上占用的表空间（例如独立表空间文件 `.ibd`）被操作系统回收并释放。
    * > **易错点**：所有 DDL 语句（包括 `CREATE`、`ALTER`、`DROP`、`TRUNCATE`）执行时强制隐式提交当前事务，完全独立于事务安全体系之外，无法通过 `ROLLBACK` 追回。
    * > 来源: P51

### 8.3 TRUNCATE TABLE 的截断清空语义

* **截断语义与结构留存**
    * 核心指令为 `TRUNCATE TABLE employees_copy;`，单词语义为「拦腰斩断、全部抹除」，与单行数学函数 `TRUNCATE(X, D)` 拼写一致。
    * 执行后客户端返回 `Query OK, 0 rows affected`，初学者极易被其蛊惑误以为没有清空成功；实际 `SELECT * FROM employees_copy;` 返回 `Empty set`，而 `DESC employees_copy;` 显示原有所有列名、类型与属性毫发无损。
    * 适用诉求为把数据全部清空、但字段名、数据类型与索引定义必须原封不动保留，以便后续新业务继续写入。
    * > 来源: P51
* **与 DROP TABLE 的效果对照**

| 操作指令 | 表中数据记录 | 表物理骨架结构 | 磁盘表空间 |
| :--- | :--- | :--- | :--- |
| `DROP TABLE` | 全部彻底销毁 | 物理彻底抹除（表不存在） | 完全释放 |
| `TRUNCATE TABLE` | 全部清空重置 | 完好保留（空表状态） | 重建重置 |

* > 来源: P51

## 9. 事务边界与自动提交

> **一句话主旨**：定义 COMMIT 的持久化语义与 ROLLBACK 的回滚边界，并说明 autocommit 是回滚生效的前置条件。

### 9.1 提交与回滚的语义边界

* **COMMIT 的持久化语义**
    * > **定义**：`COMMIT` 使当前事务内所发生的所有数据增、删、改操作被永久性、物理性地固化写入数据库磁盘。
    * > **结论**：数据一旦执行 COMMIT 提交，就彻底丧失了在事务层面上撤销与回滚的可能性；补救的唯一途径是再发起一条全新的反向 DML 变更操作。
    * > 来源: P52
* **ROLLBACK 的回滚边界**
    * > **定义**：`ROLLBACK` 只能将数据回滚到当前会话中「最近的一次 COMMIT 操作之后」的状态，不是无限穿越的时光机。
    * 多提交点时序模型：执行 DML 操作 A → `COMMIT`（提交点 C1）→ 执行 DML 操作 B → `COMMIT`（提交点 C2）→ 执行 DML 操作 C → `ROLLBACK`，引擎只逆向撤销未提交的操作 C，操作 A 与 B 早已脱离回滚日志的保护区。
    * > 来源: P52

### 9.2 autocommit 与回滚前置条件

* **自动提交机制**
    * MySQL 默认配置下会话级系统变量 `autocommit` 的默认值为 `TRUE`（或表示为 1），`SHOW VARIABLES LIKE 'autocommit';` 输出 `ON`。
    * 自动提交意味着每敲下一条独立 DML 语句（无论 `INSERT` 还是 `DELETE FROM`），MySQL 内部都会在执行完毕的瞬间默认替你在后台执行一次 `COMMIT`；因此随后敲 `ROLLBACK` 面对的是刚刚那次自动提交，结果自然无法挽回。
    * > **结论**：要让 DML 的数据变更支持回滚撤销，必须在执行 DML 操作之前显式将自动提交机制关闭，即执行 `SET autocommit = FALSE;`。
    * > 来源: P52, P56
* **标准回滚验证流程**
    * 步骤为：`COMMIT;` 显式提交一次锁定基准线 → 核验表内记录数 → `SET autocommit = FALSE;` → 执行 `DELETE FROM myemp3;` → 确认查询返回 `Empty set` → `ROLLBACK;` → 再次查询数据完整复原。
    * 机理是该删除动作被写入事务回滚日志（Undo Log），`ROLLBACK` 时引擎依据日志寻址到基准提交点，将整个删除动作完全撤销。
    * > 来源: P52

## 10. TRUNCATE 与 DELETE 差异

> **一句话主旨**：把两条清空语句的相同点、语法粒度与底层机制差异摆在一起，给出取舍底线与对照实验结果。

### 10.1 相同点与删除粒度

* **功能交集与骨架留存**
    * 两者都可以用于将数据表中的记录清空，且在抹去记录的同时完整保留数据表的二维结构元数据（列名、数据类型、主键索引、存储引擎与编码定义），清空后表依然存在，后续业务随时可以重新写入数据。
    * > 来源: P52
* **过滤条件的语法粒度**
    * `TRUNCATE TABLE` 属一刀切截断语法，不支持任何 `WHERE` 过滤条件，只要执行就必须对整张表的数据全量清除，没有任何筛选余地。
    * `DELETE FROM` 天然支持 `WHERE` 条件从句，可精确删除单行（如 `DELETE FROM 表名 WHERE id = 10;`）或一个区间的记录；只有显式省略 `WHERE` 条件时才执行全表删除。
    * > 来源: P52

### 10.2 底层机理与资源开销差异

* **事务与日志机制**
    * `DELETE FROM` 属 DML，默认运行在事务环境中，逐行删除时必须把每一行被删除的记录写入回滚日志（Undo Log），相当于一边删除一边为被删数据做副本备份。
    * `TRUNCATE TABLE` 属 DDL，采用立即隐式提交机制，不需要在事务中为回滚保留数据镜像，执行完毕后也不提供回滚支持。
    * > **结论**：`TRUNCATE TABLE` 比 `DELETE` 运行速度快得多，使用的系统资源和事务日志资源要少得多。
    * > 来源: P53
* **触发器开销与空间释放方式**
    * `DELETE` 逐行清理数据时会逐条触发该表上绑定的 `BEFORE DELETE` 与 `AFTER DELETE` 触发器，触发器内含数据同步或审计逻辑时性能开销成倍放大。
    * `DELETE` 只给数据行打上删除标记，表空间的高水位线（High Water Mark）通常不会立即释放，碎片依然存在。
    * `TRUNCATE TABLE` 属整表物理重置，根本不触发任何删除触发器；它使数据字典中的表结构重新初始化，重置自增列计数器，并直接回收数据页空间。
    * > 来源: P53
* **对照特征矩阵**

| 评估维度 | `TRUNCATE TABLE` | `DELETE FROM` |
| :--- | :--- | :--- |
| 语言归属 | DDL（数据定义语言） | DML（数据操作语言） |
| 过滤条件 | 不支持 `WHERE`，只能清空全表 | 支持 `WHERE`，可删全表亦可删子集 |
| 执行效率 | 极快，直接重置数据页指针与高水位线 | 较慢，逐行扫描、加锁并产生 Undo 日志 |
| 回滚能力 | 绝对不可回滚，触发强制隐式提交 | 支持事务回滚，受 autocommit 与事务控制 |
| 自增主键处理 | 强制将 `AUTO_INCREMENT` 计数器重置回初始值 1 | 保留当前最大自增断点，新插入继续递增 |
| 触发器 | 不激活任何触发器 | 正常逐行激活 |

* > 来源: P52, P58

### 10.3 选型底线与对照实验结果

* **回滚对照实验的分歧点**
    * 两组实验的外部操作完全一致：先 `COMMIT;` 确立物理基准线，再 `SET autocommit = FALSE;` 关闭自动提交；实验组 A 用 `DELETE FROM myemp3;` 后执行 `ROLLBACK;`，106 条数据全部复原；实验组 B 换成 `TRUNCATE TABLE myemp3;` 后执行 `ROLLBACK;`，查询结果依然为 `Empty set (0.00 sec)`，数据彻底消失无法找回。
    * > 来源: P52
* **生产选型底线**
    * > **易错点**：实际项目开发中极度不推荐频繁使用 TRUNCATE TABLE，应尽可能使用带明确条件的或受事务保护的操作。
    * 在未做冷备或异地容灾的前提下执行 `TRUNCATE TABLE`，整张表数据瞬间归零且无法通过事务日志回滚恢复；生产环境多消耗一点 CPU 与磁盘 I/O 完全在承载范围内，一次无法逆转的数据丢失足以击穿业务可用性。
    * 规范做法为严格评估数据备份状态；必须清空大表时优先走合规的变更评审与数据归档流程；生产环境交互式终端中严禁随意敲下 `TRUNCATE TABLE`。
    * > 来源: P53

## 11. 隐式提交与 DDL 原子化

> **一句话主旨**：讲透 DDL 强制隐式提交为何能击穿 ROLLBACK，并给出 MySQL 8.0 原子化 DDL 的机制与对照结果。

### 11.1 隐式提交机制与 autocommit 的作用域穿透

* **DDL 的无条件隐式提交**
    * > **定义**：以 `TRUNCATE TABLE`、`CREATE TABLE`、`ALTER TABLE`、`DROP TABLE` 为代表的所有 DDL 操作，在执行完毕后内部必然且无条件地自动触发一次强制的隐式提交（Implicit Commit）。
    * 该隐式提交彻底免疫 `SET autocommit = FALSE` 的约束，后者仅能约束 `INSERT`、`UPDATE`、`DELETE` 这类 DML 语句的自动提交行为。
    * > 来源: P52
* **为什么回滚不到清空之前**
    * `TRUNCATE TABLE` 执行结束的那一毫秒，系统已在后台悄悄完成一次隐式提交；后续 `ROLLBACK` 寻址到的「最近一次提交点」不是此前的显式提交点，而是这个隐式提交点，数据早已被固化为空表，回滚动作实质变为空操作。
    * MySQL 认为 DDL 属系统结构元数据层面的重大变更，为保障底层数据字典与物理文件的一致性，存储引擎必须强制将元数据与数据页状态即刻落盘。
    * 由此得出：涉及结构销毁与物理截断的 DDL 没有后悔药，缺少冷热备份支撑的粗暴清表只能换来无可挽回的线上灾难。
    * > 来源: P52

### 11.2 MySQL 8.0 的 DDL 原子化与事务原子性

* **原子化定义与实现机制**
    * > **定义**：DDL 原子化是指将数据定义语言操作封装为具有原子性（Atomicity）的操作单元，一条包含多个子步骤的 DDL 语句要么全部成功执行并持久化提交，要么在中间任一步骤发生故障时整体回滚到执行前的状态，绝不留下只执行了一半的残留状态。
    * 8.0 之前元数据信息分散存储在各种 `.frm` 文件、MyISAM 系统表或内存结构中，引擎层与 Server 层元数据脱节，无法统一进行事务化日志追踪。
    * MySQL 8.0 引入由 InnoDB 统一管理的集成数据字典（Data Dictionary），原子 DDL 执行时在后台 `innodb_ddl_log` 表中记录所有相关元数据操作记录；顺利结束则该日志被清除，抛出异常（依赖表不存在、命名冲突或硬件故障）时系统自动读取 DDL 日志执行反向补偿操作进行回滚。
    * > 来源: P53
* **5.7 与 8.0 的复合删除对照实验**
    * 实验场景为在同一条 `DROP TABLE book1, book2;` 中同时指定存在的 `book1` 与不存在的 `book2`；两个版本都报 `ERROR 1051 (42S02): Unknown table 'mytest.book2'`。
    * 5.7 下 `SHOW TABLES;` 返回 `Empty set`，`book1` 已被彻底删除：该语句被顺序解析为先执行 `DROP TABLE book1`、成功后再执行 `DROP TABLE book2`，第二阶段报错中断但第一阶段的物理删除已无法追回，数据字典处于割裂状态。
    * 8.0 下 `SHOW TABLES;` 仍返回 `book1` 一行，`book1` 完好保留：检测到复合操作未完全成功时，系统立即通过 DDL 日志启动内部回滚机制，把已执行的 `DROP TABLE book1` 完整回滚并恢复原状。
    * > 来源: P53
* **事务原子性的语义**
    * 事务中全部成功则调用 `COMMIT`（提交），修改被永久写入磁盘并持久化固定下来；中途报错则调用 `ROLLBACK`（回滚），已改动的数据全部撤销还原，就像什么都没发生过。
    * 数据库借用物理学的「原子」概念表达一个操作单元是不可分割的整体，典型业务逻辑通常由多条 DML 语句组合而成。
    * MySQL 8.0 的突破性革新正是将原本仅属 DML 领域的事务原子性机制，全面下沉并覆盖到包括表结构定义在内的 DDL 层面。
    * > 来源: P53

## 12. 命名规范与权限边界

> **一句话主旨**：落地阿里库表命名与字段设计规则，给出业务表三大基础字段的工程考量与高危 DDL 的权限防线。

### 12.1 命名规则与库表语义映射

* **大小写与数字规则**
    * 表名、字段名必须使用小写字母或数字，严禁出现大写字母；正例 `user_id`、`order_item`、`config_version`，反例 `UserId`、`OrderItem`、`CONFIG_VERSION`。
    * 原因在于 Windows 环境下 MySQL 默认对大小写不敏感，而 Linux 生产环境底层文件系统默认对文件名严格区分大小写，使用大写极易在跨平台部署与迁移时引发找不到表或字段的隐蔽 Bug。
    * 表名与字段名禁止以数字开头；正例 `level3_name`、`type1_status`，反例 `1st_name`、`3_level`。
    * > 来源: P53
* **分隔符与保留字规则**
    * 禁止两个下划线中间仅有数字，反例 `level__1__name`、`status__2__code`，应优化为 `level1_category` 或 `category_l1`。
    * 字段名由多个单词组成时统一下划线（snake_case）连接；Java 代码中推崇的小驼峰 `userId` 在数据库中必须规整为 `user_id`。
    * `officeCode`、`postalCode` 这类小驼峰写法不符合规范，工程实战中遇到历史包袱或特定接口要求驼峰命名时，编写 SQL 需格外注意大小写敏感性问题。
    * 严禁使用 SQL 保留字作为表名或字段名，例如 `desc`、`range`、`match`、`delayed`、`key`；非用不可时必须强制使用反引号转义，这会极大增加维护成本与解析出错概率。
    * > 来源: P53, P54
* **修改代价与谨慎原则**
    * 数据库字段一旦落库并上线，其修改代价极大，无法像 Java 应用那样通过预发布环境平滑热切来完全屏蔽风险。
    * 一个核心字段的重命名不仅涉及底层存储重构，还会直接导致线上几十甚至上百处 SQL 映射、缓存系统、索引定义与离线报表任务全面报废；因此在项目初期的 DDL 阶段就必须把字段名称与业务含义推敲清楚，上线后禁止随意重构。
    * > 来源: P53

### 12.2 业务表三大基础字段

* **建表模板**

```sql
CREATE TABLE table_name (
    id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    gmt_create   DATETIME NOT NULL COMMENT '创建时间',
    gmt_modified DATETIME NOT NULL COMMENT '修改时间',
    ...
    PRIMARY KEY (id)
);
```

* **主键 `id` 的类型与属性取舍**
    * 类型推荐 `BIGINT UNSIGNED`（无符号 64 位大整数），原因是普通 32 位整型最大上限仅为 21 亿左右（有符号）或 42 亿（无符号），在大型分布式分表或海量流水场景下极易发生主键耗尽溢出。
    * 声明为 `UNSIGNED` 是因为自增主键没有取负数的业务意义，无符号可将正数范围扩大一倍。
    * 步长默认为 1 并保持单调递增，对 InnoDB 底层 B+ 树索引的顺序写入非常友好，能最大程度减少聚簇索引分裂。
    * > 来源: P53
* **两个时间字段的分工**
    * `gmt_create` 记录数据行首次写入数据库的时间（精确到年月日时分秒），为业务审计、数据对账、冷热数据分离提供可靠的基准时间戳。
    * `gmt_modified` 记录数据行最近一次发生变更的时间，无论是排查数据一致性问题，还是依靠 Canal、Flink 等工具做增量数据同步（CDC），都是核心筛选依据。
    * > 来源: P53

* **表名与库名的业务语义映射**
    * 表名最好遵循 `业务名称_表的作用` 的组合结构，例如交易模块的订单表 `trade_order`、支付宝支付任务调度表 `alipay_task`，一眼即可看清所属子系统与承载的核心实体。
    * 微服务架构下应用通常被拆分为多个独立工程，推荐将微服务的应用名与对应的物理或逻辑数据库名保持一致，便于运维与开发人员建立微服务与数据资产的对应拓扑。
    * > 来源: P53

### 12.3 高危 DDL 的权限边界

* **权限最小化与 DBA 连带责任**
    * 普通开发人员账号在新员工入职或常规应用连接配置中默认只具备 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 等 DML 权限，严禁直接对生产库赋予 `DROP`、`TRUNCATE`、`ALTER` 等 DDL 级别的结构变更权限。
    * 若业务代码中不需要执行 DDL，但初始授权时 DBA 疏忽授予了 `DROP` 权限，一旦发生手抖误删事故，误操作人员与当初配置权限的 DBA 都要承担严重的连带过失责任。
    * 权限管控黄金法则为权限最小化、能不给的坚决不给、按需临时审批开通。
    * > 来源: P53
* **ALTER TABLE 子操作的高危属性**
    * 不仅是 `DROP TABLE` 具备毁灭性，`ALTER TABLE ... DROP COLUMN` 同样是直接生效、不进入普通 DML 事务回滚队列的 DDL 语句。
    * 该字段中积攒数年高价值业务元数据时，一旦误删且没有实时有效的冷热备份镜像，后果等同于全表被毁。
    * > 来源: P53

## 13. DML 插入与查询导入

> **一句话主旨**：给出 VALUES 的四种插入形态、缺省插入的默认值机制，以及基于查询结果集导入的字段匹配与长度安全规则。

### 13.1 四类 VALUES 插入形态

* **隐式全字段插入（不指明字段列表）**
    * 最精简写法为 `INSERT INTO emp1 VALUES (1, 'Tom', '2000-12-21', 3400);`，浮点型字段 `salary` 传入整数 3400 时引擎自动隐式转换为 `3400.00` 存入。
    * > **易错点**：未指明插入字段时，VALUES 括号中传入值的个数、先后顺序、数据类型必须与数据表中定义字段的物理顺序百分之百严格一致；顺序错位（如把 'Jerry' 传到浮点列）会报 `ERROR 1265 (01000): Data truncated for column 'salary' at row 1` 并整条拦截。
    * 业务表往往拥有数十个字段，单纯依靠记忆物理列顺序组装 SQL 极易错位且可维护性极差，工程开发中强烈不推荐这种写法。
    * > 来源: P55
* **显式指定字段插入（推荐的标准写法）**
    * 语法为 `INSERT INTO emp1 (id, hire_date, salary, `name`) VALUES (2, '1999-09-09', 4000.00, 'Jerry');`，字段顺序可完全自定义。
    * `VALUES` 列表中的数据项只需与前面小括号中定义的列名保持一对一的位置绑定，完全不需要理会底层表中 `name` 与 `hire_date` 谁先谁后；即便后续用 `ALTER TABLE` 调整了字段物理顺序，应用层持久化 SQL 也不受任何干扰。
    * > 来源: P55
* **部分字段缺省插入与默认值约束**
    * 语法为 `INSERT INTO emp1 (id, salary, `name`) VALUES (3, 4500.00, 'shk');`，未被显式指明赋值的字段 `hire_date` 被数据库自动赋予默认值 `NULL`。
    * 该插入能成功的前提是 `hire_date` 未显式声明 `NOT NULL` 约束。
    * 若某字段被声明为 `NOT NULL` 且没有预置 `DEFAULT` 默认值，执行 `INSERT` 时一旦遗漏该字段，MySQL 将直接抛出 `Field 'xxx' doesn't have a default value` 错误中断插入。
    * > 来源: P55
* **单语句批量多行插入（性能最优实践）**
    * 语法为 `INSERT INTO emp1 (id, `name`, salary) VALUES (4, '油胜男', 5000.00), (5, '张俊杰', 5500.00);`，执行后提示 `Query OK, 2 rows affected`。
    * 逐条独立 `INSERT` 会在底层引发多次网络往返传输（Round-Trip）、多次 SQL 解析与权限校验，且每条语句都需单独经历一次事务提交与日志持久化过程。
    * 单语句拼接多个值元组则只需 1 次网络 I/O，一次性批量写入并统一提交，吞吐量成倍提升。
    * > **提示**：标准关键字是 `VALUES`，MySQL 某些版本中写单数形式 `VALUE` 也能执行通过，但属非标准扩展语法，生产环境应坚决统一书写 `VALUES`。
    * > 来源: P55

### 13.2 基于查询结果集导入数据

* **语法结构与字段匹配规则**
    * 语法为 `INSERT INTO emp1 (id, `name`, salary, hire_date) SELECT employee_id, last_name, salary, hire_date FROM employees WHERE department_id IN (60, 70);`，决定性前提是目标表必须在物理上已经存在，且严禁使用 `VALUES` 关键字。
    * > **核心原则**：`INSERT INTO` 后声明的目标字段数量必须与 `SELECT` 子句查询投影出的列数量严格对齐；两者按从左到右的位置顺序进行物理映射，而非根据列名文本匹配；对应位置上的数据类型必须兼容并支持合法的隐式转换。
    * > 来源: P55
* **字段长度不对称时的校验时机与工程准则**
    * 目标表 `name VARCHAR(15)` 而源表 `last_name VARCHAR(25)` 时语句仍能成功插入，原因不是长度限制失效，而是完全取决于源表被选中那 6 行记录的实际内容长度恰好都没超过 15 个字符。
    * 若源表中存在一个长度为 18 字符（介于 15 与 25 之间）的姓名，执行该语句时系统会立刻判定数据超宽并直接报错阻止写入。
    * 小范围向大范围迁移（如薪资从 `(8,2)` 搬到 `(10,2)`）天然包容绝对安全；大范围向小范围压缩则必须依赖「当前数据碰巧未超长」的侥幸，架构上不可接受。
    * 工程准则为目标表中接收字段的定义长度与取值范围严禁低于源表对应查询字段的声明范围，发现偏小必须先通过 `ALTER TABLE ... MODIFY` 扩容，例如 `ALTER TABLE emp1 MODIFY name VARCHAR(25);`。
    * > 来源: P55

### 13.3 派生集合灌库与其他写入要点

* **SELECT 常量配合 UNION ALL 构造虚拟数据集**
    * `INSERT INTO ... SELECT` 的查询部分不限于物理表，可直接用 `SELECT` 常量与 `UNION ALL` 联合生成结果集作为数据源。

```sql
INSERT INTO my_employees
SELECT 1, 'patel', 'Ralph', 'rpatel', 895
UNION ALL
SELECT 2, 'Dancs', 'Betty', 'bdancs', 860
UNION ALL
SELECT 3, 'Biri', 'Ben', 'bbiri', 1100;
```

* `UNION ALL` 在内存中将多行独立常量的投影直接合并为一个流式结果集，由于不执行去重排序（相比 `UNION` 省略了哈希与临时表去重开销），执行速度非常快，适合自动化生成测试桩数据、数据迁移转换与离线脚本构造。
* > 来源: P58
* **含空值记录的录入与写入方式选型**
    * 录入存在大面积信息缺失的实体（如刚被收容、可能没有明确主人的动物档案）时，未确定的字段必须显式书写 `NULL` 占位符，保持元组列数与表结构严格契合。
    * 选型对照：外部客户端实时传输的单点业务录入用显式单行 `VALUES`（如用户注册、下单）；批量数据采集（如批量爬取、日志打点）用批量 `VALUES` 拼接；库内数据迁移与归档（如历史报表聚合）用 `INSERT ... SELECT`，且目标表列宽必须覆盖源表列宽。
    * > 来源: P55, P58

## 14. DML 更新与删除

> **一句话主旨**：固化 UPDATE 与 DELETE 语法与 WHERE 防线，讲清外键双向拦截、多表删除与空值边界。

### 14.1 UPDATE 语法与 WHERE 防线

* **基础语法与多字段更新**
    * 结构为 `UPDATE 表名 SET 字段名1 = 值1, 字段名2 = 值2, ... [WHERE 过滤条件];`。

```sql
UPDATE 表名
SET 字段名1 = 值1, 字段名2 = 值2, ...
[WHERE 过滤条件];
```

    * 针对特定记录补全入职日期：`UPDATE emp1 SET hire_date = CURDATE() WHERE id = 5;`。
    * 多字段赋值的各字段在 `SET` 子句中用逗号连接，如 `UPDATE emp1 SET hire_date = CURDATE(), salary = 6000.00 WHERE id = 4;`。
    * > **易错点**：漏掉 WHERE 子句时 SQL 语法本身并不报错，但会以全表批量修改的方式把整张表中所有记录的对应字段瞬间刷新为同一个值；把它写成全表更新后，全表员工的入职时间会被统一抹平为今天。
    * > 来源: P56
* **基于原字段的表达式更新**
    * 更新的值不仅可以是固定常数，还可以是基于原有字段值的数学运算表达式，并结合模糊匹配实现特定群体的批量调薪：`UPDATE emp1 SET salary = salary * 1.2 WHERE `name` LIKE '%a%';`。
    * 只要 `WHERE` 命中的结果集包含多行，MySQL 就会自动对所有命中行统一执行表达式重算。
    * 分类条件的批量价格上调示例：`UPDATE books SET price = price + 5 WHERE note = 'novel';` 命中 `id` 为 1、3、4、6 的书籍，`id=1` 由 23 元调整为 28 元。
    * > **提示**：执行 `UPDATE` 或 `DELETE` 之前，务必先用相同的筛选条件执行一次 `SELECT * FROM ... WHERE ...` 看清受影响的行，操作完成后再查一次核验变更结果。
    * > 来源: P56, P57, P58

### 14.2 外键约束对更新与删除的双向拦截

* **写入完整性校验拦截 UPDATE**
    * 将子表员工的部门编号改为不存在的 10000 号部门报 `ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (...)`。
    * 机理是外键强制要求子表外键列的值必须在主表主键范围内真实存在，试图引用主表中没有的非法值属破坏参照完整性，数据库直接拒止。
    * > 来源: P56
* **被引用保护机制拦截 DELETE**
    * 删除仍被子表引用的父行（如删除下挂大量在职员工的 50 号部门）报 `ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (...)`。
    * 机理是被依赖的 `departments` 为父表（Parent row）、依赖它的 `employees` 为子表（Child row）；允许删除会导致子表员工的 `department_id` 失去挂靠实体，沦为悬空孤儿数据（Orphan Data）。
    * 强制删除父行前必须预先将子表中所有关联记录的部门置空或迁移，或在建表时显式配置级联删除（`ON DELETE CASCADE`）。
    * > 来源: P56

### 14.3 DELETE 语法与多表联合删除

* **基础语法与逐行删除**
    * 结构为 `DELETE FROM 表名 [WHERE 过滤条件];`，定点删除写法为 `DELETE FROM emp1 WHERE id = 1;`。
    * 遗漏 `WHERE` 条件时 `DELETE FROM 表名;` 会直接清空整张表的所有数据；虽在未提交事务前可通过日志回滚，但其高昂的日志与系统资源消耗依然不可忽视。
    * > 来源: P56
* **单语句多表连接联合删除**
    * 常规分步写法需两条语句与两次网络往返：`DELETE FROM my_employees WHERE userid = 'bbiri';` 与 `DELETE FROM users WHERE userid = 'bbiri';`。

```sql
DELETE m, u
FROM my_employees m
JOIN users u ON m.userid = u.userid
WHERE m.userid = 'bbiri';
```

    * 执行路径是在 `DELETE` 关键字后显式列出待删除的目标表别名 `m, u`，引擎沿内连接匹配到的结果集同时把两张物理表中的目标行精准抹去，既保证操作的原子性，又免除多次网络往返的开销。
    * > 来源: P58

### 14.4 空值判断与模糊匹配边界

* **空值必须用 `IS NULL` / `IS NOT NULL`**
    * 检索无主宠物用 `SELECT `name` FROM pet WHERE `owner` IS NULL;`，筛选活体犬只批量更新用 `UPDATE pet SET `owner` = 'Duck' WHERE death IS NULL AND species = 'dog';`。
    * > **易错点**：判定字段是否为空绝对不能写成 `death = NULL`，SQL 三值逻辑中任何值与 NULL 做等值判断得出的布尔结果都是 UNKNOWN，永远无法返回 TRUE。
    * > 来源: P58
* **前缀匹配与全包含匹配的语义差异**
    * 查询姓「刘」的员工必须写成 `WHERE `name` LIKE '刘%'`，语义为以「刘」开头。
    * > **易错点**：把条件写成 `'%刘%'` 会使语义退化为「姓名中包含字符『刘』」，一旦出现诸如「张刘三」这样的名字就会发生严重的业务误命中。
    * 查询姓名中包含「小」字的员工才使用 `WHERE `name` LIKE '%小%'`。
    * > 来源: P58

## 15. 计算列与综合案例

> **一句话主旨**：给出 MySQL 8.0 计算列的语法与联动机制，并把图书库存库的建表、写入、改删落点与检索要点收拢成案例骨架。

### 15.1 MySQL 8.0 计算列

* **传统动态计算的两条路径与弊端**
    * 查询时动态计算：`SELECT a, b, (a + b) AS c FROM 表名;`，单表数据量达数十万乃至数百万行时每一行都必须载入 CPU 执行一次加法运算，巨大算力开销显著拉长查询响应时间。
    * 应用层预计算并持久化额外字段：每次插入或更新时由应用层算好存入，一旦业务代码遗漏或并发更新不同步，极易引发字段 $A$、$B$ 与字段 $C$ 之间的数据不一致。
    * > 来源: P56
* **计算列的定义与语法要素**
    * > **定义**：计算列是指表中某一列的值无需人工或应用层显式赋值，而是由该表中其他物理列通过预先定义的计算表达式自动推导并维护的特殊列，又称虚拟列（Virtual Column）。

```sql
CREATE TABLE IF NOT EXISTS test1 (
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b) VIRTUAL
);
```

    * `GENERATED ALWAYS AS (...)` 强制声明该列由后续小括号内的表达式生成；`VIRTUAL` 表示该列为虚拟计算列，其值不作为物理数据落盘存储到磁盘数据页，仅将表达式记录在数据字典中，读取该列时由存储引擎在内存中高效解算。
    * > 来源: P56
* **自动化协同联动验证**
    * 插入时严禁直接对计算列赋值，只需为底层列提供数据：`INSERT INTO test1 (a, b) VALUES (10, 20);` 查询得 `c` 自动呈现为 `10 + 20 = 30`。
    * 更新底层物理列后计算列立即同步且原子性地重算：`UPDATE test1 SET a = 100;` 后 `c` 变为 `100 + 20 = 120`，应用层无需任何冗余维护代码。
    * > 来源: P56

### 15.2 图书库存库的表结构设计

* **建库与图书表字段布局**
    * 建库语句为 `CREATE DATABASE IF NOT EXISTS test01_library CHARACTER SET utf8;`，随后 `USE test01_library;` 切换工作上下文；图形化或交互式客户端中编辑器能正常提示库名与内部表名即代表切换成功。
    * `books` 表字段依次为 `id INT`（图书编号）、`name VARCHAR(50)`（图书名称）、`authors VARCHAR(100)`（图书作者）、`price FLOAT`（图书单价）、`pubdate YEAR`（出版年份）、`note VARCHAR(100)`（分类与说明）、`num INT`（当前库存量）。
    * > 来源: P57
* **三种写入策略在案例中的落点**
    * 不指定列名：`INSERT INTO books VALUES (1, 'Tal of two cities', 'Charles Dickens', 23, '1995', 'novel', 11);`，强依赖表结构物理声明顺序，结构微调即破坏脚本兼容性。
    * 指定列名（推荐）：`INSERT INTO books (id, `name`, `authors`, price, pubdate, note, num) VALUES (2, 'Emma', 'Jane Austen', 35, '1993', 'joke', 22);`，字段与值一一显式映射，即便后续 `ALTER TABLE` 增加非空默认值列也不破坏已有插入逻辑。
    * 批量元组：单条 `INSERT` 拼接第 3 至第 7 条记录，减少网络往返与事务提交开销，批量录入效率最高。
    * > 来源: P57

### 15.3 综合案例的条件更新与物理清理

* **批量与定点更新**
    * 分类批量上调：`UPDATE books SET price = price + 5 WHERE note = 'novel';`。
    * 唯一标识的多字段联动修正：`UPDATE books SET price = 40, note = 'drama' WHERE `name` = 'Emma';`。
    * > 来源: P57
* **零库存记录的物理删除**
    * 语法为 `DELETE FROM books WHERE num = 0;`，物理清除库存为 0 的售罄或失效记录。
    * 若后续统计分析题目需要全量图书特征，须把因测试删除的数据补回表内以保持初始基线。
    * > 来源: P57

### 15.4 案例延伸的检索要点

* **模糊匹配、聚合与多列排序**
    * 模糊匹配用 `WHERE `name` LIKE '%a%'`；统计命中数量与库存总量用 `SELECT COUNT(*) AS book_count, SUM(num) AS total_num FROM books WHERE `name` LIKE '%a%';`。
    * 多列排序按优先级书写：`ORDER BY num DESC, note ASC`，第一优先级的 `num` 出现并列相同值时才启用逗号后第二优先级的 `note` 字段比较；降序必须显式指定 `DESC`。
    * > 来源: P57
* **分组聚合与结果集筛选**
    * `SELECT note, COUNT(*) FROM books GROUP BY note;` 中若 `SELECT` 列表同时出现非聚合字段与聚合函数，该非聚合字段必须显式声明在 `GROUP BY` 中，否则破坏逻辑分组语义，甚至在启用 `ONLY_FULL_GROUP_BY` 模式下直接报错中断。
    * `WHERE` 用于在物理扫描与分组发生前过滤底层记录行且严禁出现聚合函数；`HAVING` 是在数据完成 `GROUP BY` 分组归约之后对聚合结果集做二次筛选，如 `GROUP BY note HAVING SUM(num) > 30`。
    * > 来源: P57
* **分页、函数计算与流程控制**
    * 标准分页公式为 `LIMIT (page_no - 1) * page_size, page_size`，第 2 页每页 5 条即起始偏移量 `offset = (2 - 1) * 5 = 5`，写作 `LIMIT 5, 5`。
    * 字符数统计用 `CHAR_LENGTH(REPLACE(`name`, ' ', '')) >= 10`；`TRIM()` 只能剥离文本首尾空白，清除单词中间夹杂的空格需借助 `REPLACE()` 置换为空字符；`CHAR_LENGTH()` 统计物理字符个数（汉字与英文均记 1 个单位），不同于按底层物理字节计算的 `LENGTH()`。
    * 简单 `CASE` 表达式针对单一变量做离散等值多路分支比对，末尾补充 `ELSE` 兜底未显式枚举的分类以避免输出 `NULL`；搜索型 `CASE` 后不带变量名，每个 `WHEN` 承接布尔条件表达式，适合范围区间的连续值研判。
    * > 来源: P57
* **汇总增强与极值定位**
    * `GROUP BY note WITH ROLLUP` 会在常规分组统计的基表上方自动增加一条汇总所有分组指标的超级聚合行；该行原分组列默认填充为 `NULL`，用 `IFNULL(note, '合计库存总量')` 动态置换即可产出可读报表。
    * 极值定位组合为聚合排序加 `LIMIT` 切片：`ORDER BY num DESC LIMIT 0, 3` 取库存前三，`WHERE note = 'novel' ORDER BY price DESC LIMIT 0, 1` 取小说类单价最高；复杂函数逻辑也可直接写入 `ORDER BY` 实现自定义动态排序，如 `ORDER BY CHAR_LENGTH(REPLACE(`name`, ' ', '')) DESC LIMIT 0, 1`。
    * > 来源: P57
