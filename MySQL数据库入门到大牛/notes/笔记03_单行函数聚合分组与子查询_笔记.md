## 函数体系与分类


### 函数的本质与引入价值

* **函数（Function）的数学原型**
    * > **定义**：函数是把输入参数按预定义对应法则映射为单一返回值的黑盒计算管道，模型为 $y = f(x)$。
    * 自变量 $x$ 对应函数的输入参数（Argument / Parameter），因变量 $y$ 对应返回值（Return Value），$f$ 对应法则，即 Function 的首字母。
    * 多变量场景下自变量可扩展为向量 $y = f(x_1, x_2, \dots, x_n)$；SQL 中入参可以是字段列名、格式模板、截取长度等。
    * 计算机语言称其为函数或方法（Method），底层本质与数学模型完全一致。
* **数据库内置函数的三项价值**
    * 代码复用：高频复杂算法（字符串截取、MD5 哈希、时间戳转换、四舍五入）固化在内核中，直接调用而无需重复造轮子。
    * 就地清洗与网络 I/O 减负：清洗与类型转换在数据库引擎内部完成，避免把海量原始字段拉到应用层内存再循环处理。
    * 模块化与可维护性：转换逻辑收敛在函数内部，上层业务 SQL 更紧凑、语义更直观。

### 跨数据库的函数方言壁垒

* **方言（Dialect）差异的事实**
    * 通用编程语言（Java、Python、Go）的核心 API 在版本演进中保持高度向下兼容，从 Java 8 升级到 Java 17 极少发生颠覆性突变。
    * 各数据库厂商（MySQL、Oracle、PostgreSQL、SQL Server、IBM DB2）实现内置函数时夹带大量私有语法，**不同数据库之间函数的实现差异远大于同一门语言不同版本之间的差异**。
    * 本笔记的全部函数语法与行为严格锚定 MySQL 规范，不可默认为跨数据库通用；跨库迁移时函数改写往往是工作量最大、隐蔽 Bug 最多的雷区。
* **字符串拼接符 `||` 的方言冲突**
    * Oracle 中 `SELECT 'hello' || 'world' FROM dual;` 输出 `'helloworld'`，双竖线是原生拼接操作符。
    * MySQL 默认配置下双竖线不是拼接符，而是**逻辑或（OR）运算符**；执行 `SELECT 'hello' || 'world';` 输出 `0`。
    * 原因是 `'hello'` 与 `'world'` 无法解析为有效数字，被强制截断隐式转换为数值 `0`（False），$0 \text{ OR } 0$ 的结果即 `0`。
    * MySQL 的标准拼接写法是内置函数 `SELECT CONCAT('hello', 'world');`，输出 `'helloworld'`。
    * > **易错点**：把 Oracle 的 `||` 写法原样复制到 MySQL，不报错但会输出逻辑事故结果 `0`，属于静默错误。

### 三维分类体系

* **维度一：按定义者划分**
    * 内置函数（Built-in Functions）：官方在源码中原生提供，安装启动实例后即可在 `SELECT`、`WHERE`、`ORDER BY` 中直接调用。
    * 自定义函数（User-Defined Functions, UDF）：用 `CREATE FUNCTION` 编写专属业务逻辑并持久化到数据字典，属于后续存储对象章节的进阶内容。
* **维度二：按输入输出行数划分（核心分界线）**
    * 单行函数（Single-Row Functions）：操作表中单一行数据，输入 $N$ 行必然输出 $N$ 行；例 `ROUND(123.45)` 输出 `123`、`UPPER('smith')` 输出 `'SMITH'`、`IFNULL(commission_pct, 0)` 输出数值或 `0`。
    * 多行函数（Multi-Row Functions / 聚合函数 / 分组函数）：接收一组记录，压缩合并返回单一汇总值（$N \to 1$）；例 `SUM(salary)`、`MAX(salary)`、`COUNT(*)`。
    * 该维度是单行函数章节与聚合函数章节划分的本质依据。
* **维度三：单行函数按业务功能领域划分**

    | 函数类别 | 核心覆盖场景 | 代表性函数 |
    | :--- | :--- | :--- |
    | 数值函数 | 数学运算、三角函数、指数对数、精度修剪 | `ABS()`、`ROUND()`、`CEIL()`、`TRUNCATE()` |
    | 字符串函数 | 文本拼接、大小写转换、子串截取、文本替换、对齐补齐 | `CONCAT()`、`LENGTH()`、`REPLACE()`、`SUBSTRING()` |
    | 日期与时间函数 | 获取当前时间戳、日期增减、间隔计算、格式化提取 | `NOW()`、`DATE_ADD()`、`DATE_FORMAT()` |
    | 流程控制函数 | 条件分支判断、多分支匹配、空值回退 | `IF()`、`IFNULL()`、`CASE WHEN ... THEN` |
    | 加密与解密函数 | 敏感密码单向散列、双向数据加解密 | `MD5()`、`SHA()`、加解密函数 |
    | 信息与系统函数 | 数据库引擎环境元数据、当前连接上下文 | `VERSION()`、`USER()`、`DATABASE()` |

* **单行函数的三项行为特征**
    * 参数形式灵活：可以是常量字面量（`ROUND(12.3)`）、动态字段列（`LOWER(last_name)`），也可以是复合表达式。
    * 执行频率逐行：`SELECT UPPER(last_name) FROM employees;` 会对检索出的每一行依次调用，原表多少行结果集就是多少行。
    * 支持多层嵌套（Nested Functions）：内层函数返回值自动作为外层函数入参，求值顺序严格由内向外。
    * 嵌套示例求值链：`round(123.456, 2)` 求得 `123.46` → `mod(123.46, 10)` 求得 `3.46` → `truncate(3.46, 0)` 最终返回 `3`。

## 数值函数


### 基础数学与方向性取整

* **绝对值、符号与圆周率**
    * `ABS(x)`（Absolute Value）：求绝对值，正数返回本身，负数取相反数，`0` 依然是 `0`。
    * `SIGN(x)`：符号函数，正数统一返回 `1`，负数统一返回 `-1`，`0` 返回 `0`；适合盈亏统计等按正负打状态标记的场景。
    * `PI()`：返回圆周率常量近似值 `3.141593`，是纯常量生成器，不需要也不允许传任何参数。
* **`CEIL` / `CEILING` 与 `FLOOR` 的取整方向**
    * `CEIL(x)` / `CEILING(x)`：天花板函数，返回**大于或等于**参数的最小整数，即强制向上靠拢。
    * `FLOOR(x)`：地板函数，返回**小于或等于**参数的最大整数，即强制向下靠拢。
    * `CEIL` 与 `CEILING` 完全等价，是同一个函数的两个名字。
    * 两者都不是四舍五入：`32.0001` 取天花板必定得 `33`，`32.9999` 取地板必定得 `32`。
    * 负数结果：`CEIL(-43.3)` 得 `-43`（数轴上比它大的相邻整数），`FLOOR(-43.3)` 得 `-44`（比它小的相邻整数）。
    * > **易错点**：凭数字绝对值的直觉判断负数取整方向会把极性搞反。
* **极值、取模与开方**
    * `LEAST(v1, v2, ...)` 与 `GREATEST(v1, v2, ...)`：从参数列表中挑出最小值或最大值，支持多个入参。
    * `MOD(x, y)`：求模求余；`MOD(12, 5)`、`12 MOD 5`、`12 % 5` 三种写法效果完全一样，底层遵循 $x - y \times \lfloor x / y \rfloor$。
    * `SQRT(x)`（Square Root）：开平方根，传入正数返回浮点平方根；传入负数在实数范围内无法开方，MySQL 直接返回 `NULL`。

### 随机数与伪随机机理

* **`RAND()` 与区间缩放**
    * 无参 `RAND()` 在 `[0.0, 1.0)` 区间内返回均匀分布浮点数，每次执行结果都不相同。
    * 生成 0 到 100 范围内随机整数的公式：`SELECT ROUND(RAND() * 100)`，即先乘以基数再包一层 `ROUND()` 或 `FLOOR()`。
* **`RAND(seed)` 的确定性**
    * `RAND()` 可接收整型参数作为**种子（Seed）**或因子；两个不同列传入相同种子（如 `RAND(10)`）时，无论执行多少次输出都**永远完全一致**。
    * 计算机底层生成的都是伪随机数（Pseudo-random Number），依赖线性同余法等确定性数学递推算法；给定初始种子 $x_0$ 后随机数序列即被公式锁定。
    * 只要生成序列在 `[0, 1]` 内各点出现概率一致、满足均匀分布，就符合统计学随机要求；带种子随机在数据重现、科学实验与单元测试中不可替代。

### 精度控制

* **`ROUND(x, y)` 的位权控制**
    * $y > 0$：保留小数点后 $y$ 位；$y = 0$：抹去小数部分仅保留整数位；$y < 0$：四舍五入到小数点左侧的整数位。
    * 样本：`ROUND(123.456)` = `123`，`ROUND(123.456, 0)` = `123`，`ROUND(123.456, 1)` = `123.5`，`ROUND(123.456, 2)` = `123.46`。
    * 负数位样本：`ROUND(123.456, -1)` = `120`（看个位 `3` 不足 5 舍去归零）；`ROUND(153.456, -2)` = `200`（看十位 `5` 满足进位，进位后百位变 `2`，后面的位全填 `0`）。
    * > **易错点**：`y < 0` 不是把百位四舍五入成十几，`ROUND(123.456, -1)` 绝不等价于 `12`。
* **`TRUNCATE(x, y)` 的强制截断**
    * 定位是截断，目标位后面的数字不管是 `0` 还是 `9` 全盘扔掉，绝不进位。
    * 样本：`TRUNCATE(123.456, 0)` = `123`；`TRUNCATE(123.456, 1)` = `123.4`（后一位是 5 也不进位）；`TRUNCATE(129.456, -1)` = `120`（个位是 9 也直接抹成 0）。
    * `ROUND(x)` 可以省略第二个参数默认当作 `ROUND(x, 0)`，但 **`TRUNCATE(x, y)` 必须严格提供两个参数**，少写会直接报语法错误。
    * 业务取向：厚道口径用 `ROUND(salary, 2)` 四舍五入，抠门口径用 `TRUNCATE(salary, 0)` 直接抹零。
    * > **易错点**：`TRUNCATE(123.456)` 不会被补默认的 `0` 位，MySQL 直接报语法错误。
* **洋葱式嵌套**
    * `SELECT TRUNCATE(ROUND(123.456, 2), 0)` 的执行流程：内层 `ROUND(123.456, 2)` 千分位 6 进位得 `123.46`；外层 `TRUNCATE(123.46, 0)` 抹掉全部小数，输出 `123`。

### 角度弧度与三角函数

* **角度弧度互换**
    * MySQL 所有三角函数（`SIN`、`COS`、`TAN`）接收的参数**必须是弧度值（Radian）**，而非几何角度值（Degree）。
    * 换算基准：$360°$ 周角 $= 2\pi$ 弧度；1 弧度 $\approx 57.2958°$。
    * `RADIANS(x)`：角度转弧度，传入 `30` 返回约 `0.5236`，传入 `90` 返回约 `1.5708`（即 $\pi / 2$）。
    * `DEGREES(x)`：弧度转角度，传入 `2 * PI()` 得到 `360`，把 `RADIANS(60)` 再转回来完美复原为 `60`。
* **三角函数与反三角函数**
    * 直角坐标系中设对边 $X$、邻边 $Y$、斜边 $Z$：$\sin(\theta) = X/Z$，$\cos(\theta) = Y/Z$，$\tan(\theta) = X/Y$。
    * 样本：`SIN(RADIANS(30))` = `0.5`；`TAN(RADIANS(45))` = `1`；`DEGREES(ASIN(1))` = `90`；`DEGREES(ATAN(1))` = `45`。
    * 反三角函数 `ASIN`、`ACOS`、`ATAN` 算出来的是弧度，通常要外嵌 `DEGREES()` 转回度数才便于人眼理解。
    * 定义域边界：正弦值域严格落在 `[-1.0, 1.0]`，因此 `ASIN(x)` 的入参 $x$ 必须在 $-1$ 到 $1$ 的闭区间内，超出范围（如 `ASIN(1.5)`）数学上无解，MySQL 静默返回 `NULL`。
    * `ATAN(y, x)` / `ATAN2(y, x)` 扩展形式支持传入坐标分量差值 $(y_2 - y_1, x_2 - x_1)$，可直接求得两点连线与横轴的方位角。

### 指数、对数与进制转换

* **幂运算与自然底数指数**
    * `POW(x, y)` / `POWER(x, y)`：求 $x$ 的 $y$ 次方，两写法完全等价，`POW(2, 5)` = `32`。
    * `EXP(x)`：以自然常数 $e$（欧拉数，$e \approx 2.71828$）为底数的指数函数，即 $e^x$；`EXP(1)` 输出 `2.71828...`，`EXP(2)` 输出 `7.389...`。
* **对数函数体系**
    * `LN(x)` 与单参数 `LOG(x)` 等价，统一默认以常数 $e$ 为底；`LN(EXP(2))` 与 `LOG(EXP(2))` 均返回 `2`。
    * `LOG10(x)` 显式以 10 为底（`LOG10(100)` = `2`）；`LOG2(x)` 显式以 2 为底（`LOG2(8)` = `3`）。
    * 双参数 `LOG(base, x)` 可自由指定任意底数，`LOG(2, 16)` = `4`。
    * 指数与自然对数互为反函数，两曲线以 $y = x$ 互为镜像，因此把 `EXP(2)` 的结果塞给 `LN()` 会原样还原出 `2`。
* **进制转换函数**
    * `BIN(10)` = `'1010'`、`OCT(10)` = `'12'`、`HEX(10)` = `'A'`，把十进制数转换为其他标准进制的字符串表现。
    * 八进制满八进位，因此十进制 `8` 对应八进制 `10`、十进制 `9` 对应 `11`、十进制 `10` 对应 `12`；十六进制 `10` 对应 `A`、`15` 对应 `F`。
    * `CONV(x, from_base, to_base)`：万能跨进制转换。`CONV('1010', 2, 10)` = `10`；`CONV(10, 10, 8)` = `12`；`CONV('10', 2, 8)` = `2`。
    * 三个参数依次是待转换值、原始进制、目标进制，底层自动完成进制位权解码与重编码。
* **数值函数核心开发重点**
    * `ROUND` 与 `TRUNCATE`：处理金额、比例、薪酬核算的绝对主力。
    * `RAND`：抽奖、随机洗牌、生成模拟数据。
    * `CEIL` 与 `FLOOR`：分页总页数计算（如 `CEIL(total_count / page_size)`）、抹零向下对齐。
    * `MOD`：分表路由（Hash 取模）、偶数奇数交替染色。
    * 三角函数、指数对数与进制转换的业务场景较为垂直狭窄，日常不需要默写，用到时回查对照即可。

## 字符串函数


### 字符编码与长度度量

* **`ASCII(s)` 首字符编码**
    * 获取字符串首个字符的 ASCII 码值：`ASCII('abc')` 与 `ASCII('a')` 都返回 `97`，`ASCII('A')` 返回 `65`。
    * 该函数只取字符串的第一个字符计算码值，后面跟着多少字符、内容是什么完全不影响结果。
* **`CHAR_LENGTH(s)` 与 `LENGTH(s)` 的本质分野**
    * `CHAR_LENGTH(s)` 统计**字符个数（Characters）**，属于应用逻辑层面长度，中文与英文均计为 1。
    * `LENGTH(s)` 统计**底层物理存储占用的字节数（Bytes）**。
    * 在默认 UTF-8（或 `utf8mb4`）编码下，标准 ASCII 字符（英文字母、数字）占 1 字节，常用中文汉字占 3 字节，特定生僻字或 Emoji 占 4 字节。
    * 样本对照：`CHAR_LENGTH('hello')` = `5`、`CHAR_LENGTH('我们')` = `2`；`LENGTH('hello')` = `5`、`LENGTH('我们')` = `6`。
    * 表设计定义 `VARCHAR(N)` 时必须警惕字符集编码带来的物理存储与网络传输空间差异。
    * > **易错点**：混淆字符数与字节数是线上字段超长截断类 Bug 的常见来源。

### 拼接与格式化

* **`CONCAT(s1, s2, ...)` 无缝聚合**
    * 接收任意多个字符串参数，按传入顺序无缝连接成一个完整字符串。
    * 自连接实战：`SELECT CONCAT(emp.last_name, ' worked for ', mgr.last_name) AS details FROM employees emp JOIN employees mgr ON emp.manager_id = mgr.employee_id;`，单次 SQL 即可输出结构完整的报表文案，避免客户端二次循环拼接。
    * 只要任意一个参数为 `NULL`，整个拼接结果直接坍缩为 `NULL`。
* **`CONCAT_WS(separator, s1, s2, ...)` 带分隔符拼接**
    * `CONCAT With Separator` 的缩写，第一个参数为分隔符，后续参数为待拼接项。
    * 样本：`CONCAT_WS('-', 'hello', 'world', 'beijing')` = `'hello-world-beijing'`；`CONCAT_WS('/', '2026', '09', '14')` = `'2026/09/14'`。
    * 分隔符传空串 `''` 时行为与 `CONCAT` 完全等价。
    * 会自动忽略中间的 `NULL` 参数（分隔符本身为 `NULL` 除外），这是与 `CONCAT` 的关键区别。

### 索引偏移与内容替换

* **SQL 字符串索引从 1 开始**
    * 字符串 `hello world` 对应的 SQL 索引依次为 `1` 到 `11`，而 Java 索引为 `0` 到 `10`。
    * SQL 中第 1 位就是字符 `'h'`，第 2 位就是字符 `'e'`。
    * > **易错点**：按 0 偏移推算会导致全部截取与替换位置产生一个字符的偏差。
* **`INSERT(str, pos, len, newstr)` 位置切除替换**
    * 并非向数据库插入记录，而是字符串的“位置抹除与插入”。
    * 执行 `SELECT INSERT('hello world', 2, 3, 'aaaaa')` 的分步逻辑：定位第 `pos = 2` 位字符 `'e'` → 从 `'e'` 起向后取长度 `len = 3` 的 `'ell'` → 切除这 3 个字符 → 在缺口填入 `'aaaaa'` → 最终得 `'h' + 'aaaaa' + 'o world'` = `'haaaaao world'`。
* **`REPLACE(str, from_str, to_str)` 全文内容替换**
    * 基于字符串内容的语义匹配，与按物理坐标动刀的 `INSERT` 定位方式不同。
    * 样本：`REPLACE('hello', 'll', 'mmm')` = `'hemmmo'`；`REPLACE('hello', 'lol', 'mmm')` 匹配不到 `'lol'`，原样输出 `'hello'`。
    * 原文包含多个目标子串时全局替换所有匹配项；目标子串不存在时不报错，静默返回原始文本。

### 大小写转换与数据库敏感性

* **`UPPER` / `UCASE` 与 `LOWER` / `LCASE`**
    * `UPPER(s)` / `UCASE(s)`：全部字符转为大写，`UPPER('HelLo')` = `'HELLO'`。
    * `LOWER(s)` / `LCASE(s)`：全部字符转为小写，`LOWER('HelLo')` = `'hello'`。
* **大小写过滤的跨库事故**
    * 在 MySQL 中执行 `WHERE last_name = 'king'` 依然能查出 `King` 的记录；同样结构与数据在 Oracle 中执行结果行数直接归零。
    * SQL 标准规范：语法关键字（`SELECT`、`FROM`）不区分大小写，但单引号包裹的字符串字面量严格区分大小写，Oracle 遵循严格规范。
    * MySQL 的宽泛机制：建表或列定义时默认字符集排序规则通常带 `_ci` 后缀（如 `utf8mb4_general_ci`、`utf8mb4_0900_ai_ci`），`ci` 即 **Case Insensitive（大小写不敏感）**，比较时自动忽略大小写差异。
    * 通用健壮写法：需要兼容多数据库或在 `_bin` / `_cs` 敏感列上精确过滤时，必须主动归一化 —— `WHERE LOWER(last_name) = 'king';`。

### 截取与视觉对齐填充

* **`LEFT(s, n)` 与 `RIGHT(s, n)`**
    * 从最左或最右截取 `n` 个字符：`LEFT('hello', 2)` = `'he'`，`RIGHT('hello', 3)` = `'llo'`。
    * 截取长度超过总长度时原样返回整个字符串，`LEFT('hello', 13)` = `'hello'`。
* **`LPAD` 与 `RPAD` 的反直觉对齐效果**
    * `LPAD(str, len, padstr)`：用 `padstr` 在 `str` **左侧填充**直至总长度达到 `len`。
    * `RPAD(str, len, padstr)`：用 `padstr` 在 `str` **右侧填充**直至总长度达到 `len`。
    * **左侧填充实现的是右对齐，右侧填充实现的是左对齐**。
    * `LPAD(salary, 10, '*')` 的对齐效果：`24000.00`（8 位）补 2 个星号成 `**24000.00`；`4800.00`（7 位）补 3 个星号成 `***4800.00`；`600.00`（6 位）补 4 个星号成 `****600.00`，三者个位与小数点完全垂直对齐。
    * 业务选型：金额、数量、计数一律用 `LPAD` 做右对齐；姓名、家庭住址、长文本描述用 `RPAD` 做左对齐。
    * `salary` 本身是数值类型，传入 `LPAD` 时 MySQL 会自动隐式类型转换，将其包裹为字符串后再填充。

### 空白处理与边界字符剔除

* **`TRIM` / `LTRIM` / `RTRIM` 空格去除**
    * `TRIM(s)` 首尾空格全清，`LTRIM(s)` 只清左侧空格，`RTRIM(s)` 只清右侧空格。
    * `'  hello  world  '` 经 `TRIM` 处理后输出 `'hello  world'`，中间的双空格完整保留。
    * 要抹去内部空格必须使用 `REPLACE('hello  world', ' ', '')`。
    * > **易错点**：`TRIM` 只能去除首尾空格，绝对去除不了字符串中间的内部空格。
* **`TRIM(s1 FROM s)` 定制剔除**
    * `TRIM('o' FROM 'oohello worldoooo')` = `'hello world'`，去除首尾全部指定字符。
    * `TRIM(LEADING 'o' FROM 'oohello worldoooo')` 仅去除首部（Leading）的 `'o'`。
    * `TRIM(TRAILING 'o' FROM 'oohello worldoooo')` 仅去除尾部（Trailing）的 `'o'`。
    * 该语法与标准 SQL 一致，无需正则即可剥离前后缀标志位（如多余的引号、斜杠）。

### 重复、比对、定位与离散取值

* **`REPEAT` 与 `SPACE`**
    * `REPEAT('hello', 4)` 把 `'hello'` 重复 4 次拼接；`SPACE(5)` 生成由 5 个纯空格组成的字符串，`LENGTH(SPACE(5))` = `5`。
* **`STRCMP(s1, s2)` 字典序比对**
    * 对应 C 语言的 `strcmp`，按底层字符编码顺序依次比对。
    * 返回规则：左小右大返回 `-1`，完全相等返回 `0`，左大右小返回 `1`；`STRCMP('abc', 'abd')` = `-1`，`STRCMP('abd', 'abc')` = `1`，`STRCMP('abc', 'abc')` = `0`。
    * 比对原则：从左往右逐个比对 ASCII 码，分出胜负立刻返回；前面字符全部相同时长度更长的字符串更大。
* **`SUBSTR` / `SUBSTRING` 子串截取**
    * `SUBSTR('hello', 2, 2)` = `'el'`，从第 2 位开始截取 2 个字符。
    * `SUBSTRING('hello', 3)` = `'llo'`，省略长度参数时从第 3 位一直截取到末尾。
    * 位置参数同样从 1 开始。
* **`LOCATE` 与未命中返回 0 的设计哲学**
    * `LOCATE('l', 'hello')` = `3`，`LOCATE('ll', 'hello')` = `3`（首次出现位置），`LOCATE('lll', 'hello')` = `0`（没找到）。
    * 等价写法还有 `POSITION(substr IN str)` 与 `INSTR(str, substr)`。
    * 返回 0 而非 -1 的原因：Java / C 索引从 0 开始，找到且位于第一个位置时返回 `0`，“没找到”只能往 0 左边借一位返回 `-1`；SQL 索引从 1 开始，位于开头时返回 `1`，1 的左边恰好空着一个非法的自然数位 `0`，返回 `0` 即可表达未命中而无需使用负数。
* **`ELT` 与 `FIELD` 离散列表操作**
    * `ELT(m, s1, s2, ...)`：数字驱动字符，传 `2` 就取第二个参数，`ELT(2, 'a', 'b', 'c', 'd')` = `'b'`；`m` 超界返回 `NULL`。
    * `FIELD(s, s1, s2, ...)`：字符驱动位置，`FIELD('妹妹', '哥哥', '姐姐', '妹妹', '弟弟', '妹妹')` 首次命中在第 3 个位置返回 `3`；未命中返回 `0`。
* **`FIND_IN_SET` 集合子串搜索**
    * 专为逗号分隔存储的关联 ID 字段（如 `'1001,1002,1005'`）设计的查询利器。
    * `FIND_IN_SET('妹妹', '哥哥,妹妹,姐姐,弟弟,妹妹')` 返回 `2`：自动把第二个参数以逗号解构成集合列表，返回匹配项所在的集合下标。
* **`REVERSE` 与 `NULLIF`**
    * `REVERSE('abc')` = `'cba'`，常用于回文数校验或倒序编码的文件扩展名前缀匹配优化。
    * `NULLIF(expr1, expr2)`：`expr1 = expr2` 成立时返回 `NULL`，不相等时返回 `expr1`。
    * 报表实战：`NULLIF(LENGTH(first_name), LENGTH(last_name)) AS compare_result`，姓与名长度恰好相同时输出 `NULL`，不同时输出 `LENGTH(first_name)` 的实际数值，可极醒目地定位“两项属性完全一致”的特殊记录。

### 字符串函数经典辨析样例

| 对比项 | 左 | 右 | 差异要点 |
| :--- | :--- | :--- | :--- |
| 长度度量 | `CHAR_LENGTH('我们')` = 2 | `LENGTH('我们')` = 6 | 字符个数 vs UTF-8 下每汉字 3 字节 |
| 拼接容错 | `CONCAT('a', NULL)` = NULL | `CONCAT_WS('-', 'a', NULL)` 跳过 NULL 项 | 普通拼接遇 NULL 整体坍缩 |
| 补齐视觉 | `LPAD` 左补 → 右对齐 | `RPAD` 右补 → 左对齐 | 金额用 LPAD，文本用 RPAD |
| 清洗范围 | `TRIM('  a  b  ')` = `'a  b'` | `REPLACE('a  b', ' ', '')` = `'ab'` | TRIM 不触内部空格 |
| 未命中返回 | `LOCATE('x', 'hello')` = 0 | Java `indexOf` = -1 | SQL 索引 1-based 的必然推论 |
| 替换机制 | `INSERT` 按 pos/len 物理坐标切除 | `REPLACE` 按内容语义匹配 | INSERT 受 1-based 索引约束 |

## 日期与时间函数


### 系统当前时钟与时区

* **年月日与时分秒独立获取**
    * `CURDATE()` / `CURRENT_DATE()`：获取当前年月日，格式 `YYYY-MM-DD`，两函数完全等价。
    * `CURTIME()` / `CURRENT_TIME()`：获取当前时分秒，格式 `HH:MM:SS`。
* **全时间戳获取与选型**
    * `NOW()`、`SYSDATE()`、`CURRENT_TIMESTAMP()`、`LOCALTIME()`、`LOCALTIMESTAMP()` 都返回 `YYYY-MM-DD HH:MM:SS` 格式的标准时间。
    * 日常认准并使用 `NOW()` 即可：字符最短、语义最明确，各大 ORM 框架默认生成的也是它。
    * `NOW()` 在 SQL 语句开始执行时便锁定时间常量，`SYSDATE()` 是在函数实际执行到该行时动态取系统时钟；批量插入或耗时较长的复杂事务中，`NOW()` 能保证同一批次记录的时间戳严格一致。
* **UTC 与东八区时区差**
    * `UTC_DATE()` 与 `UTC_TIME()` 获取世界协调时间（UTC，英国格林威治所在时区）。
    * 北京时间属东八区（UTC+8）：把 `UTC_TIME()` 的小时数加 8 即得到当下服务器的 `CURTIME()`。
    * 跨国跨时区业务中数据库底层往往统一按 UTC 存储，展示层再做时区换算。

### UNIX 时间戳双向转换

* **`UNIX_TIMESTAMP()` 与 `FROM_UNIXTIME()`**
    * UNIX 时间戳是从 1970 年 01 月 01 日 00:00:00 UTC 开始流逝的整型秒数。
    * `SELECT UNIX_TIMESTAMP()` 获取当前系统时刻的秒级时间戳；`SELECT UNIX_TIMESTAMP('2021-10-01 12:12:32')` 把指定日期转成时间戳；`SELECT FROM_UNIXTIME(1633061552)` 把时间戳还原为标准日期时间。
    * 应用一（分布式订单流水号）：订单号由 `UNIX_TIMESTAMP()` 生成的整数片段拼上机器节点号再加几位随机字符组合而成，保证单调递增且全局唯一。
    * 应用二（存储与索引优化）：整型占固定 4 或 8 字节，比字符串节省磁盘空间，在 B+ 树索引中的比较与排序效率也大幅领先。

### 属性剥离与度量统计

* **独立字段剥离**
    * `YEAR(NOW())`、`MONTH(NOW())`、`DAY(NOW())`、`HOUR(NOW())`、`MINUTE(NOW())`、`SECOND(NOW())` 分别提取对应数值。
    * 也可以传入符合格式的纯字符串（如 `'2021-10-25 23:01:51'`），MySQL 会自动发生隐式类型转换。
* **名称型与季度函数**
    * `MONTHNAME(NOW())` 返回英文月份名称如 `'October'`；`DAYNAME(NOW())` 返回英文星期名称如 `'Monday'`。
    * `QUARTER(NOW())` 返回所在季度 `1~4`，10、11、12 月返回 `4`。
* **星期与周次计数的文化基准差异**
    * `WEEKDAY(date)`（国际标准 / 工作流习惯）：以周一为一周起点，**周一返回 `0`**，周二返回 `1`，…，周日返回 `6`；`WEEKDAY('2021-10-26')` 返回 `1`（周二是 1）。
    * `DAYOFWEEK(date)`（西方宗教日历传统）：以周日为起点，**周日返回 `1`**，周一返回 `2`，…，周六返回 `7`；`DAYOFWEEK('2021-10-25')` 返回 `2`（周一是 2）。
    * `WEEK(NOW())` 返回一年中的第几周（如第 43 周）；`DAYOFYEAR(NOW())` 返回一年中的第几天（如第 298 天）；`DAYOFMONTH(NOW())` 返回本月的第几天（25 号返回 25）。
    * > **易错点**：统计“周末加班”或“周一晨会”时用错函数，基数差 1 会导致逻辑完全颠倒。
* **`EXTRACT(type FROM date)` 复合维度提取**
    * 符合 ANSI SQL 规范的万能提取器，第一个参数 `type` 是预定义语法关键字（不需加引号）。
    * 支持单一维度 `YEAR`、`MONTH`、`DAY`、`HOUR`、`SECOND`，也支持 `HOUR_MINUTE`、`YEAR_MONTH`、`HOUR_SECOND` 等复合跨度提取。
    * 样本：`EXTRACT(HOUR_MINUTE FROM NOW())` 提取小时与分钟合成的整数如 `2307`；`EXTRACT(QUARTER FROM '2021-05-12')` 返回 `2`。
* **`TIME_TO_SEC` 与 `SEC_TO_TIME` 秒数折算**
    * `TIME_TO_SEC('23:09:15')` 的换算公式：$23 \times 3600 + 9 \times 60 + 15 = 83355$ 秒。
    * `SEC_TO_TIME(83355)` 把纯秒数还原为时分秒格式。
    * 这一对函数仅处理 `TIME` 维度换算，完全不牵扯年、月、日等跨日历周期的复杂计算。

### 日期推移与间隔计算

* **`DATE_ADD` 与 `DATE_SUB`**
    * `DATE_ADD(NOW(), INTERVAL 1 YEAR)` 加 1 年；`DATE_ADD(NOW(), INTERVAL -1 YEAR)` 传负数等于减 1 年；`DATE_SUB(NOW(), INTERVAL 1 YEAR)` 减 1 年。
    * 单位可以是 `YEAR`、`DAY`、`SECOND` 等；复合单位示例 `DATE_ADD(NOW(), INTERVAL '1_1' MINUTE_SECOND)` 加 1 分 1 秒，`DATE_ADD(NOW(), INTERVAL '1_1' YEAR_MONTH)` 加 1 年 1 个月。
    * `ADDDATE()` 与 `DATE_ADD()` 完全等价，`SUBDATE()` 与 `DATE_SUB()` 完全等价；只需记住 `DATE_ADD` 一个，需要减时直接传负数即可覆盖。
    * > **易错点**：使用 `MINUTE_SECOND` 或 `YEAR_MONTH` 这类跨单位操作时，入参必须加单引号并用下划线隔开，否则不被识别。
* **`ADDTIME` 与 `SUBTIME` 时分秒微调**
    * `ADDTIME(NOW(), 20)` 中纯数值默认为加 20 秒；`SUBTIME(NOW(), 30)` 减 30 秒。
    * `SUBTIME(NOW(), '1:1:3')` 减 1 小时 1 分钟 3 秒。
* **`DATEDIFF` 与 `TIMEDIFF` 间隔计算**
    * `DATEDIFF(d1, d2)` 计算两个日期的天数差值，规则是 $d1 - d2$；必须把较晚的时间作为第一个参数才能得到正整数天数。
    * `TIMEDIFF(NOW(), '2021-10-25 22:00:00')` 计算两个时间的时分秒差值。
    * 业务实战一（司龄破万天）：`WHERE DATEDIFF(NOW(), hire_date) >= 10000`。
    * 业务实战二（近 7 天统计）：`WHERE DATEDIFF(NOW(), register_time) <= 7`。
* **`TO_DAYS` / `FROM_DAYS` 绝对坐标模型**
    * `TO_DAYS(NOW())` 计算今天距离公元 0000 年 1 月 1 日的总天数；`FROM_DAYS(366)` 返回 `0001-01-01`。
    * 计算两个时间差值有两条等价途径：相对求差 `DATEDIFF(NOW(), hire_date)`，与绝对投影求差 `TO_DAYS(NOW()) - TO_DAYS(hire_date)`，两者数学结果完全恒等。
    * 绝对投影在区间判断与比较时更直观：把所有日期统一投影成纯整型的天数序号再运算。
* **月末截止与构造函数**
    * `LAST_DAY(NOW())` 返回当前月份的最后一天（如 `2021-10-31`），用于月度账单日、月底绩效归档等月末边界。
    * `MAKEDATE(2021, 32)` = `2021-02-01`（1 月有 31 天）；`MAKETIME(10, 21, 23)` 组装出 `10:21:23`。
    * 日期转数值小技法：`SELECT CURDATE() + 0, NOW() + 0` 让 `CURDATE()` 自动转成整数 `20211025`，`NOW()` 自动转成 `20211025232409`。

### 格式化与解析

* **格式化与解析的互逆定义**
    * 格式化（Format）：日期/时间 → 格式化字符串，如把时间对象变成 `'2021年10月25日'`。
    * 解析（Parse）：格式化字符串 → 日期/时间，如把 `'10/25/2021'` 还原成标准 `DATE`。
* **占位符体系**

    | 占位符 | 语义说明 | 取值范围或典型示例 |
    | :--- | :--- | :--- |
    | `%Y` | 4 位完整年份 | `2021`, `2026` |
    | `%y` | 2 位年份后两位 | `21`, `26` |
    | `%m` | 2 位月份（带前导零） | `01` ~ `12` |
    | `%c` | 月份（不带前导零） | `1` ~ `12` |
    | `%M` | 英文月份完整拼写 | `January`, `October` |
    | `%b` | 英文月份缩写 | `Jan`, `Oct` |
    | `%d` | 2 位日（带前导零） | `01` ~ `31` |
    | `%e` | 日（不带前导零） | `1` ~ `31` |
    | `%D` | 英文序数日后缀 | `1st`, `2nd`, `25th` |
    | `%H` | 24 小时制（带前导零） | `00` ~ `23` |
    | `%h` / `%I` | 12 小时制（带前导零） | `01` ~ `12` |
    | `%i` | 2 位分钟（带前导零） | `00` ~ `59` |
    | `%s` / `%S` | 2 位秒数（带前导零） | `00` ~ `59` |
    | `%T` | 24 小时制标准时间 | 相当于 `%H:%i:%s` |
    | `%r` | 12 小时制带 AM/PM | 如 `11:32:05 PM` |
    | `%W` | 英文星期完整拼写 | `Monday`, `Tuesday` |
    | `%w` | 周中的天数编号 | `0`（周日）~ `6`（周六） |

* **`DATE_FORMAT` 与 `TIME_FORMAT`**
    * `DATE_FORMAT(CURDATE(), '%Y-%M-%D')` 输出英文排版 `2021-October-25th`。
    * `DATE_FORMAT(NOW(), '%Y-%m-%d')` 输出中文标准报表格式 `2021-10-25`。
    * `TIME_FORMAT(CURTIME(), '%H:%i:%s')` 输出 `23:32:05`。
    * `DATE_FORMAT(NOW(), '%Y-%m-%d %H:%i:%s %W %w %r')` 一次输出复合全信息，如 `2021-10-25 23:32:05 Monday 1 11:32:05 PM`。
* **`STR_TO_DATE(str, format)` 严密对齐原则**
    * `STR_TO_DATE('2021-10-25 23:32:05', '%Y-%m-%d %H:%i:%s')` 把非标时间字符串解析为日期。
    * 第二个格式参数必须与第一个字符串的内容在字符结构、分隔符、空格位置上完全绝对对齐。
    * 若字符串是 `'2021/10/25'` 而格式串写成 `'%Y-%m-%d'`，或者少了一个空格、时分秒缺少前导零，MySQL 无法识别时**直接返回 `NULL`**。
    * > **易错点**：生产环境排查日志导入失败，绝大多数是格式串中的符号与源数据没有精确对齐。
* **`GET_FORMAT(type, region)` 标准模板**
    * `SELECT GET_FORMAT(DATE, 'USA')` 返回 `'%m.%d.%Y'`，可直接喂给 `DATE_FORMAT`：`SELECT DATE_FORMAT(CURDATE(), GET_FORMAT(DATE, 'USA'))`。
    * 类型可取 `DATE`、`TIME` 或 `DATETIME`，地域代码可取 `'USA'`、`'JIS'`、`'ISO'`、`'EUR'` 等，自动产出合规格式化字符串。

## 流程控制函数


### 双分支与空值特化

* **`IF(expr, v1, v2)` 三元判断**
    * 逻辑上完全等价于高级语言的三元运算符 `(condition ? expr1 : expr2)`，严格接收三个参数。
    * 求值逻辑：`expr` 判定为 TRUE（非零）返回 `v1`；判定为 FALSE 或 `NULL` 返回 `v2`。
    * 薪资档次实战：`IF(salary >= 6000, '高工资', '低工资') AS details`，以 6000 为界，达到返回 `'高工资'`，低于返回 `'低工资'`。
    * 空值安全防范：`IF(commission_pct IS NOT NULL, commission_pct, 0) AS safe_commission`，再代入 `salary * 12 * (1 + IF(...)) AS annual_sal`，彻底杜绝年度总薪酬坍缩为 `NULL` 的线上事故。
* **`IFNULL(v1, v2)` 空值降级**
    * `v1` 不为 `NULL` 时直接输出其本身值；`v1` 为 `NULL` 时由备选值 `v2` 替代输出。
    * 底层完全等价于 `IF(v1 IS NOT NULL, v1, v2)`。
    * 适用场景差异：`IF` 是全功能通用的（可比对数值范围、正则匹配、多条件与或非），`IFNULL` 专门对付 `NULL`，代码更短、语义更聚焦；报表默认值填充优先选 `IFNULL`。

### 搜索型 CASE

* **语法结构**
    * 形态：`CASE WHEN condition1 THEN result1 WHEN condition2 THEN result2 ... [ELSE default_result] END`。
    * 功能上对应 Java 等语言的 `if ... else if ... else`，适合数值区间阶梯划分与复合多逻辑判定。
* **阶梯打标实战**
    * `CASE WHEN salary >= 15000 THEN '白骨精' WHEN salary >= 10000 THEN '潜力股' WHEN salary >= 8000 THEN '小屌丝' ELSE '草根' END AS details`，配合 `department_id` 输出。
* **语法禁忌与省略 ELSE 的后果**
    * `WHEN`、`THEN` 以及下一个 `WHEN` 之间**绝对不要加逗号**，每个 `WHEN` 和 `THEN` 自身就是独立的语法分界词。
    * 整个多分支结构以 `CASE` 开头、以 `END` 结尾；后面还需要查询其他字段时，必须在 `END`（或起的别名）之后再补逗号。
    * 省略 `ELSE` 时，未命中任何 `WHEN` 的记录 MySQL 默认输出为 `NULL`，业务要求非空时必须强制补齐 `ELSE`。
    * > **易错点**：从 C/Java 转过来的开发者最容易在 `WHEN ... THEN` 之间误加逗号。

### 等值型 CASE

* **语法结构**
    * 形态：`CASE expr WHEN val1 THEN result1 WHEN val2 THEN result2 ... [ELSE default_result] END`。
    * 架构上完全等价于高级语言的 `switch-case`；表达式 `expr` 只需在 `CASE` 后写一次，后续 `WHEN` 直接填期望匹配的常量值。
    * 典型适用：状态码翻译（如 0/1/2 翻汉字）、指定部门调薪。
* **部门阶梯调薪实战**
    * 需求：10 号部门发 1.1 倍、20 号部门发 1.2 倍、30 号部门发 1.3 倍，其他部门统一发 1.4 倍。
    * `CASE department_id WHEN 10 THEN salary * 1.1 WHEN 20 THEN salary * 1.2 WHEN 30 THEN salary * 1.3 ELSE salary * 1.4 END AS details`。
    * 这是在 `SELECT` 中的只读动态投影展示，底层物理表数据没有发生任何改动；后续 `UPDATE` 章节该结构同样可嵌入 `SET` 子句做批量阶梯调价。
    * 收窄业务范围时配合 `WHERE department_id IN (10, 20, 30)`，数据源已被精确锁死，内部 `CASE` 即使省略 `ELSE` 也绝不会产生意外的 `NULL` 脏数据。

### 缺失循环结构的原因

* **SQL 自带隐式循环**
    * 执行 `SELECT ... FROM employees` 的瞬间，数据库引擎底层就已启动全表或索引范围的迭代循环游标，107 行数据一行一行顺次过流处理。
    * 单行函数直接作用在流水线的每一行微粒上，因此**不需要也不应该在查询级别显式提供循环语法**。
    * SQL 属于声明式语言（Declarative Language），只需告诉数据库“要什么”，不需要告诉它“怎么遍历”。
* **显式循环的所在位置**
    * MySQL 确实有 `WHILE`、`LOOP`、`REPEAT` 等显式循环结构，但不在单行函数里。
    * 它们存在于高级篇的存储过程（Stored Procedure）与存储函数（Stored Function）中，用于批量插入、数据迁移或跑批事务。

### 四种流程控制形态对照

| 函数 / 语法形态 | 抽象语义模型 | 高级语言类比 | 最佳适用场景 |
| :--- | :--- | :--- | :--- |
| `IF(expr, v1, v2)` | 条件二选一 | `expr ? v1 : v2` | 简单双状态打标、非空防御判断 |
| `IFNULL(v1, v2)` | 空值默认兜底 | `v1 ?? v2`（空值合并） | 报表数据清洗、统计项默认补 0 |
| `CASE WHEN cond THEN ...` | 范围多分支搜索 | `if ... else if ... else` | 数值区间阶梯划分、复合多逻辑判定 |
| `CASE expr WHEN val THEN ...` | 离散等值匹配 | `switch (expr) { case ... }` | 状态码翻译、指定部门调薪 |

## 加密解密、信息与杂项函数


### 加密函数的工程定位

* **数据库内加密通常只作补充**
    * 若客户端把明文密码发给后端、再由后端写库时调用 MySQL 的 `MD5()`，网络传输这一段链路上密码依然是明文，中间人攻击（MITM）或抓包工具可直接截获原始密码。
    * 加解密属于密集 CPU 计算，而数据库核心瓶颈通常在 I/O 与并发连接；把大量散列计算交给应用服务器乃至客户端终端分布式承担远比堆在单点数据库上合理。
    * 工程推荐方案是把加密前置到客户端或服务端应用层完成，配合安全传输通道（HTTPS + Hash）。
* **明文存储的历史教训**
    * 2009 年前后知名技术社区 CSDN 发生严重数据泄露，黑客拖库后发现用户表中密码全部以纯明文保存，导致大量用户在其他平台遭遇撞库危机。
    * 结论：无论是业务层还是数据层，敏感凭证绝不能明文落盘。

### 内置加密与解密函数

* **`PASSWORD()` 的版本弃用**
    * `SELECT PASSWORD('mysql')` 在 MySQL 8.0 中直接报错 `FUNCTION PASSWORD does not exist`。
    * 该函数在 MySQL 5.7 中用于为服务器认证系统生成密码散列，5.7 上尚可运行并返回一段以 `*` 开头的 41 位十六进制散列串。
    * 在 MySQL 8.0 中已被彻底废弃并移除，新项目中严禁在业务 SQL 里继续编写 `PASSWORD()`。
* **`MD5()` 与 `SHA()` 不可逆散列**
    * 单向散列（Hash）算法具有不可逆性：只能把明文映射成固定长度暗文摘要，无法从暗文逆推明文。
    * 样本输出：`MD5('mysql')` = `81c3b080dad537de7e10e0987a4bf52e`；`SHA('mysql')` = `88e7b399d45a9be46a3a4198c8c2025688b5606d`。
    * 散列函数是完全确定性的数学运算，输入明文相同则无论执行多少次哈希值都严格一致；若存在随机性，登录验证将永远无法通过。
    * 验证机理不是把密文还原成明文比对，而是把用户本次输入的明文按相同规则散列后再比对两次暗文是否相等。
    * 把密文直接填入登录框会触发二次哈希 `MD5('81c3b08...52e')`，得到完全不同的值仍不匹配，因此凭证安全。
    * `SHA()` 等价于 `SHA1()`，生成 40 字符散列，比 `MD5()` 的 32 位散列具有更高安全强度与抗碰撞性；MySQL 8.0 默认用户密码认证插件底层采用 SHA-256 族系算法。
* **`ENCODE()` 与 `DECODE()` 对称加密**
    * 语法：`ENCODE(str, seed_hash)` 使用给定种子密钥加密明文字符串；`DECODE(crypt_str, seed_hash)` 用相同种子密钥解密密文。
    * 5.7 环境范例：`SELECT ENCODE('atguigu', 'mysql')` 加密；`SELECT DECODE(ENCODE('atguigu', 'mysql'), 'mysql')` 还原出 `'atguigu'`。
    * 仅适用于需要由授权管理员还原敏感字段（脱敏手机号、临时 Token）的场景。
    * > **易错点**：`ENCODE()` 与 `DECODE()` 已在 MySQL 8.0 中被正式移除，执行会抛 `FUNCTION ENCODE does not exist`；现代生产环境应使用 `AES_ENCRYPT()` 与 `AES_DECRYPT()`，或直接在业务应用代码层加解密。

### 系统信息函数

* **实例与连接元数据**

    | 函数名称 | 典型返回值 | 功能说明 |
    | :--- | :--- | :--- |
    | `VERSION()` | `8.0.26` | 返回当前 MySQL 服务器的完整软件版本号 |
    | `CONNECTION_ID()` | `8` | 返回当前客户端与服务端连接的唯一内部线程 ID |
    | `DATABASE()` | `atguigudb` | 返回当前会话默认连接的数据库名，未切换数据库时为 `NULL` |
    | `SCHEMA()` | `atguigudb` | 与 `DATABASE()` 功能完全等价，二者可互换 |
    | `USER()` | `root@localhost` | 返回发起当前客户端连接时声明的用户名与主机名 |
    | `CURRENT_USER()` | `root@localhost` | 返回服务端实际用于权限认证验证的用户名与主机名规则 |
    | `CHARSET(str)` | `utf8mb3` | 返回给定字符串当前采用的字符编码集 |
    | `COLLATION(str)` | `utf8mb3_general_ci` | 返回给定字符串当前采用的字符排序与比对规则 |

    * `SYSTEM_USER()` 与 `SESSION_USER()` 在绝大多数场景下与 `USER()` 返回完全一致的登录客户端标识。
* **字符集与排序规则细节**
    * `CHARSET('尚硅谷')` 返回 `utf8mb3`，`mb3` 即 Most Bytes 3，意为系统使用最多 3 个字节表示一个字符。
    * 结合长度函数：`'尚硅谷'` 是 3 个汉字字符，`utf8mb3` 下每汉字 3 字节，总字节长度为 $3 \times 3 = 9$ 字节。
    * 排序规则中的 `_ci` 后缀代表 Case-Insensitive（大小写不敏感），字符串比对与排序时忽略英文字母大小写差异。
    * 图形化工具新建连接界面弹出的“测试连接成功：MySQL 8.0.26”，底层就是驱动在握手建立后立即执行 `SELECT VERSION(), DATABASE(), USER();` 等信息函数获取服务器基础画像。

### 杂项工具函数

* **`FORMAT(value, n)` 数值格式化**
    * 把数字 `value` 格式化为带千分位逗号分隔的字符串，并对小数部分四舍五入保留 `n` 位小数。
    * 样本：`FORMAT(123.123, 2)` = `'123.12'`（第 3 位小数 3 舍去）；`FORMAT(123.125, 2)` = `'123.13'`（第 3 位小数 5 进位）；`FORMAT(123.125, 0)` = `'123'`；`FORMAT(123.125, -2)` = `'123'`。
    * 与 `ROUND` 的两点关键差异：返回值类型上 `ROUND` 返回数值类型（DECIMAL 或 FLOAT），`FORMAT` 返回含千分位逗号的字符串类型（VARCHAR）；负数保留位上当 $n \le 0$ 时 `FORMAT` 统一只保留整数位、完全不识别负数四舍五入级别，而 `ROUND(123.125, -2)` 会对十位四舍五入得到数值 `100`。
* **`CONV(value, from_base, to_base)` 进制转换**
    * 支持 2 到 36 进制之间的任意互转。
    * 样本：`CONV(16, 10, 2)` = `'10000'`（即 $2^4$）；`CONV(8888, 10, 16)` = `'22B8'`；`CONV(NULL, 10, 2)` 参数为 `NULL` 时直接返回 `NULL`。
    * 适用于低层网络协议解析、设备位掩码交互或十六进制哈希值的按位排查。
* **`INET_ATON` 与 `INET_NTOA` IP 地址转换**
    * `INET_ATON('192.168.1.100')` 返回 `3232235876`（Address to Number）；`INET_NTOA(3232235876)` 返回 `'192.168.1.100'`（Number to Address）。
    * 数学原理：把 IPv4 的 4 个段分别映射到 4 个字节（32 位二进制位）的高低位上，公式为 $192 \times 256^3 + 168 \times 256^2 + 1 \times 256^1 + 100$，即 $3221225472 + 11010048 + 256 + 100 = 3232235876$。
    * 存储设计结论：把 IPv4 设计为 `INT UNSIGNED` 字段仅占 4 字节，配合 `INET_ATON()` 写入与 `INET_NTOA()` 读出，既节约磁盘空间又大幅提升按 IP 范围查询的索引性能（直接用 `VARCHAR(15)` 存点分十进制至少占用 11 到 15 字节且网段范围检索效率极低）。
* **`BENCHMARK(count, expr)` 表达式基准测试**
    * 把表达式 `expr` 重复执行 `count` 次并测量累积耗时。
    * `BENCHMARK(1, MD5('mysql'))` 耗时极短无法直观观测；`BENCHMARK(100000, MD5('mysql'))` 会显示明显耗时（如 `0.03 sec` 或 `0.05 sec`）。
    * 只返回整数 `0` 代表成功执行完毕，重点不是返回值而是观察控制台输出的 Execution Time，用于对比两种标量函数实现的效率。
* **`CONVERT(expr USING char_code)` 字符集显式转换**
    * `SELECT CHARSET('atguigu')` 返回 `utf8mb3`；`SELECT CHARSET(CONVERT('atguigu' USING utf8mb4))` 返回 `utf8mb4`；`SELECT CHARSET(CONVERT('atguigu' USING gbk))` 返回 `gbk`。
    * 工程原则是恪守“三端编码统一”：Web 浏览器 / App 客户端字符集（UTF-8）、应用后端服务 JVM / Python 字符集（UTF-8）、MySQL 连接与库表字段字符集（UTF-8 / utf8mb4）保持一致。
    * 只有在必须对接外部遗留系统、三端编码出现物理不兼容时，才建议在数据库层用 `CONVERT(... USING ...)` 显式兜底转码。

## 单行函数实战与踩坑清单


### 常用实战写法

* **时间获取与选型**
    * `SELECT NOW(), SYSDATE(), CURRENT_TIMESTAMP(), LOCALTIME(), LOCALTIMESTAMP() FROM DUAL;` 都能输出含年月日时分秒的当前时间。
    * 重点掌握 `NOW()` 与 `SYSDATE()` 即可，其中首推 `NOW()`：仅需三个字母、执行行为确定（语句开始执行时锁定时间常量）。
* **计算列别名与排序**
    * `SELECT last_name, LENGTH(last_name) AS name_length FROM employees ORDER BY name_length ASC;`。
    * `SELECT` 子句中的列别名之所以能在 `ORDER BY` 中直接生效，是因为 `ORDER BY` 的执行阶段位于 `SELECT` 数据抽取之后。
    * 给复杂函数表达式赋予语义明确的别名可提升可读性，并避免在排序列重复书写一遍 `LENGTH(last_name)`。
* **单列融合输出**
    * `SELECT CONCAT(employee_id, ', ', last_name, ', ', salary) AS out_put FROM employees;`，输出形如 `100, King, 24000.00` 的压缩结果集列。
    * 不加分隔符直接拼接体验较差，加入英文逗号与空格可提升可读性。
* **工龄折算**
    * 相对差值解法：`SELECT last_name, DATEDIFF(CURDATE(), hire_date) AS worked_days, ROUND(DATEDIFF(CURDATE(), hire_date) / 365, 1) AS worked_years FROM employees ORDER BY worked_years DESC;`。
    * 绝对投影解法：`TO_DAYS(CURDATE()) - TO_DAYS(hire_date) AS worked_days` 与 `(TO_DAYS(CURDATE()) - TO_DAYS(hire_date)) / 365 AS worked_years`。
    * 两种方式的数值计算结果完全等价，日常开发中 `DATEDIFF()` 更加直观常用。
* **报表文案组装**
    * `SELECT CONCAT(last_name, ' earns ', TRUNCATE(salary, 0), ' monthly but wants ', TRUNCATE(salary * 3, 0)) AS "dream salary" FROM employees;`。
    * 去除小数部分有两种处理方式：`ROUND(salary, 0)` 四舍五入抹平，或 `TRUNCATE(salary, 0)` 直接物理截断小数位。
* **岗位分级映射**
    * `CASE job_id WHEN 'AD_PRES' THEN 'A' WHEN 'ST_MAN' THEN 'B' WHEN 'IT_PROG' THEN 'C' WHEN 'SA_REP' THEN 'D' WHEN 'ST_CLERK' THEN 'E' END AS grade`。
    * 依据具体 `job_id` 离散值做一对一等值映射时，选用简单 CASE 表达式最地道简洁；未在规则中声明的岗位（如 `PU_CLERK`）其 `grade` 返回 `NULL`。
    * 若业务不允许空值，可在 `END` 前显式追加 `ELSE 'undefined'` 或 `ELSE '其他'`。
* **超长工龄检索**
    * `SELECT last_name, hire_date FROM employees WHERE DATEDIFF(CURDATE(), hire_date) >= 10000;`。
    * 10000 天折合约 27.4 年，测试库中该条件筛出 10 位资深员工。
* **日期范围过滤的三条路径**
    * 隐式转换：`AND hire_date >= '1997-01-01'`；图省事写成 `AND hire_date >= '1997'` 虽然能靠容错推断匹配年份，但依赖底层模糊推断风险极高。
    * 格式化路径：`AND DATE_FORMAT(hire_date, '%Y-%m-%d') >= '1997-01-01'`，可进一步精简为 `AND DATE_FORMAT(hire_date, '%Y') >= '1997'`。
    * 解析路径：`AND hire_date >= STR_TO_DATE('1997-01-01', '%Y-%m-%d')`，最大优势是打破默认输入格式束缚 —— 前端传入欧美日月年格式（`'01-01-1997'` 或 `'01/01/1997'`）时隐式转换会彻底失效，只需在第二个参数声明 `'%d-%m-%Y'` 即可平滑转换。

### 高频踩坑清单

* **百分比符号陷阱**
    * MySQL 中 `%` 在算术运算上下文里是**取模运算符**，不是数学意义上的“百分之一”。
    * 写 `salary * 120% AS "new salary"` 会导致解析器认为缺少右操作数或语法紊乱，最终返回 `NULL` 或直接抛语法错误。
    * 正确写法：凡是百分比加成计算必须统一转化为小数形式，提升 20% 即 `salary * 1.2`。
* **含空格的别名**
    * 别名含空格（如 `new salary`）在 SQL 语法中属于非法标识符，必须用双引号 `""` 或反引号包裹。
    * 不加包裹时系统会把空格后的单词误认为是下一条子句的关键字。
* **表名大小写的跨平台差异**
    * Windows 环境写成大写的 `FROM EMPLOYEES` 不报错，因为 Windows 文件系统（NTFS）默认对文件名大小写不敏感，MySQL 在 Windows 默认安装时把系统变量 `lower_case_table_names` 设为不敏感。
    * Linux 生产服务器文件系统严格区分大小写：建表时定义为小写 `employees` 而业务代码用大写 `EMPLOYEES`，会直接抛 `Table 'xxx.EMPLOYEES' doesn't exist`。
    * 学习阶段就要统一规范，库表名称严格与数据字典保持完全一致。
* **空值参与运算的坍缩**
    * 任何数值与 `NULL` 做算术运算结果都会直接变成 `NULL`，年度总薪酬这类指标必须先用 `IF` 或 `IFNULL` 做空值防御。

## 五大聚合函数与 NULL 陷阱


### 聚合函数的数学本质

* **从单行到多行的范式转变**
    * 单行函数每输入一行必输出一行（$1 \to 1$）；多行函数（聚合函数／聚集函数／分组函数）输入一组数据集合，统计汇总后输出单个汇总值（$N \to 1$）。
    * 处理模型对比：单行下 `1000`、`2000`、`3000` 三行各自乘 `1.2` 得到三行输出；聚合下集合 `{1000, 2000, 3000}` 经 `AVG(salary)` 输出唯一标量 `2000`。
    * 数学映射 $y = f(\mathbf{X})$ 中自变量可以是多维向量，但因变量必是确定单标量；聚合函数的底层契约正是**只要未指定分组，最终输出的必定只有单行单列的单一值**。
* **统计指标的取舍背景**
    * 方差（Variance）衡量稳定性：两位运动员平均成绩相同，方差接近 0 者成绩稳定，大起大落者方差极大；淘汰制大赛中稳定性优先。
    * 中位数（Median）抗奇异点：5 人社区中 4 人月薪 1000、1 人月薪 100000，平均数被拉高到 $104000 / 5 = 20800$，而升序排列后正中间（50% 分位）的数值依然是 1000。
    * 面对贫富差距悬殊的分布，中位数往往比平均数更能客观反映普罗大众的生活基准。
    * MySQL 官方把使用频次最高的 5 个函数固化为核心聚合函数：`AVG()`、`SUM()`、`MAX()`、`MIN()`、`COUNT()`。

### AVG 与 SUM

* **基础语法与算术关联**
    * `SELECT AVG(salary), SUM(salary) FROM employees;` 在测试员工表中返回 `AVG(salary)` = `6461.682243`（107 名员工人均月薪）、`SUM(salary)` = `691400.00`（每月薪资总支出）。
    * 数值全非空时均值与总和存在天然数学关系：$\text{AVG}(salary) \times \text{记录总数} = \text{SUM}(salary)$。
* **数据类型约束与跨库行为差异**
    * `SUM` 与 `AVG` 在数学上**只适用于数值类型（整数、浮点数、定点数）**字段；对姓氏或入职日期求和没有任何物理意义。
    * MySQL 表现：对 `last_name`、`hire_date` 执行 `SUM` 或 `AVG` 不抛任何异常，静默进行隐式类型转换，把无法解析为数字的字符串全部转为 `0`，输出结果集为 `0`。
    * Oracle 表现：执行 `SELECT SUM(last_name) FROM employees;` 会立即中断并硬性抛错 `ORA-01722: invalid number`。
    * > **易错点**：在 MySQL 中“SQL 成功执行并输出了结果，绝不等于你的 SQL 写对了”，隐式转换容错会掩盖逻辑设计错误。

### MAX 与 MIN

* **极值函数在全数据类型上的普适性**
    * `SELECT MAX(salary), MIN(salary) FROM employees;` 得到薪资天花板 `24000.00` 与地板价 `2100.00`。
    * 字符串与日期同样合法且具备明确业务意义：`MAX(last_name)` 是字典序最大的姓氏（依据字符集与校对规则逐字节比对编码大小），`MIN(last_name)` 对应 `ORDER BY last_name ASC` 的第一条记录。
    * `MAX(hire_date)` 是最晚入职日期（最新员工），`MIN(hire_date)` 是最早入职日期（元老级员工）。
    * 判定准则：字符串虽然不能做代数加减，但存在严格的大小比较规则；只要数据类型支持全序比对（满足可传递的排序规则），就必然存在极大值与极小值。因此 **`MAX` 和 `MIN` 适用于数值类型、字符串类型以及日期时间类型**。

### COUNT 的运行机理

* **核心定义与三种范式**
    * > **定义**：`COUNT(expr)` 计算在查询结果集中，参数表达式 `expr` 计算结果为非 `NULL` 的行数总和。
    * 三种写法：`SELECT COUNT(*) FROM employees;`、`SELECT COUNT(1) FROM employees;`（或 `COUNT(2)` 等任意常量）、`SELECT COUNT(employee_id) FROM employees;`（指定某物理列）。
    * 在没有空值干扰的主键列上三者都返回 107，但底层运行机理截然不同。
* **`COUNT(1)` 与 `COUNT(*)` 的贴标签机理**
    * 指定物理列 `COUNT(employee_id)` 时，引擎从该行提取 `employee_id` 字段值并检查是否为 `NULL`，不是则累加 1 次计数。
    * 指定常量 `COUNT(1)` 时，引擎不需要从磁盘读取具体物理列，直接在内存中为当前行贴上虚拟常量标识 `1`，下一行同样赋 `1`，最终统计这 107 个 `1` 出现的频次总数。
    * 写成 `COUNT(2)` 只是为每行贴上常量标识 `2`，统计的是常量 `2` 出现的个数，`SELECT COUNT(2) FROM employees;` 返回的依然是 `107` 而非 $107 \times 2 = 214$。
    * 清点的是标签的“张数（频次）”，而不是票面数字的数值和。
* **`COUNT(列名)` 的空值排斥陷阱**
    * 实测：`COUNT(*)` = 107、`COUNT(1)` = 107、`COUNT(salary)` = 107、`COUNT(commission_pct)` = **35**。
    * `COUNT(列名)` 会在底层自动过滤掉该字段为 `NULL` 的行：107 名员工中只有 35 名销售人员享有提成比例，其余 72 名非销售岗位员工的 `commission_pct` 全部为 `NULL`。
    * 只有当字段在表结构定义中带有 `NOT NULL` 约束（例如主键列），`COUNT(列名)` 的结果才与 `COUNT(*)` 保持一致。
    * > **易错点**：误用含空值的字段统计业务总用户数或总订单数，会直接造成严重的数据漏计；统计总记录数首选 `COUNT(*)` 或 `COUNT(1)`。

### NULL 过滤的共性与 AVG 口径

* **聚合函数一律忽略 NULL**
    * `SUM`、`AVG`、`MAX`、`MIN`、`COUNT` 在遇到 `NULL` 时都会自动予以忽略。
    * 与单行函数的差别：单行场景下 `1 + NULL = NULL`，但 `SUM(commission_pct)` 在底层遇到 `NULL` 时直接跳过不累加，最终算出的是那 35 位销售人员提成比例的纯净累加和而非 `NULL`。
* **聚合等式判定**
    * 表达式 1 `AVG(commission_pct)` 与表达式 2 `SUM(commission_pct) / COUNT(commission_pct)` **完全相等**：`AVG()` 计算均值时分母不是整表行数 107，而是参与求和的非空记录数。
    * 恒等式：$\text{AVG}(expr) \equiv \dfrac{\text{SUM}(expr)}{\text{COUNT}(expr)}$。
    * 表达式 3 `SUM(commission_pct) / 107` 分母强行除以全公司总人数而分子只是 35 人的奖金和，因此数值显著偏小。
* **全员平均奖金率的口径修正**
    * 需求是统计公司所有员工的平均奖金率，直接写 `SELECT AVG(commission_pct) FROM employees;` 返回 `0.222857`（约 22.3%），这统计出的不是全员平均，而是“**拥有提成资格的员工的人均奖金率**”，属于幸存者偏差。
    * 正确解法一：`AVG(IFNULL(commission_pct, 0)) AS avg_comm`，在 `AVG` 内部把空值填补为 0。
    * 正确解法二：`SUM(commission_pct) / COUNT(IFNULL(commission_pct, 0)) AS avg_comm`。
    * 正确解法三：`SUM(commission_pct) / COUNT(*) AS avg_comm`。
    * 三种解法得到的真实全员平均奖金率约为 `0.072804`（即 7.28%）。
* **聚合函数性能相关结论**
    * `COUNT(*)`、`COUNT(1)` 与 `COUNT(列名)` 在不同存储引擎（如 InnoDB 与 MyISAM）中的底层执行效率与优化选型，需结合索引结构展开。

## 分组查询与组级过滤


### COUNT 效率的引擎视角

* **MyISAM 的 $O(1)$ 与 InnoDB 的 $O(N)$**
    * MyISAM 每张表的元数据（Meta Information）中显式维护着高精度行计数器 `row_count`；没有 `WHERE` 过滤的全表统计无论写 `COUNT(*)`、`COUNT(1)` 还是 `COUNT(主键)`，都直接从表元数据读取该字段值秒级返回，时间复杂度为 $O(1)$，三者效率完全一致。
    * InnoDB 因引入多版本并发控制（MVCC，Multi-Version Concurrency Control），同一时刻不同并发事务因隔离级别限制能看见的有效行数动态且各不相同，无法在表头写死全局固定的 `row_count` 计数器。
    * InnoDB 必须在被调用时遍历 B+ 树索引树统计符合当前事务可见性快照的记录行数，时间复杂度退化为 $O(N)$。
* **InnoDB 下的性能排序与索引树选择**
    * 列没有 `NULL` 空值时性能排序为 $\text{COUNT}(*) \approx \text{COUNT}(1) > \text{COUNT}(\text{具体列名})$。
    * `COUNT(*)` 与 `COUNT(1)` 语义等价，引擎无需取出任何具体列值，优化器会**遍历全表中体积最小的二级索引树（Secondary Index）**。
    * 执行计划 `EXPLAIN` 中优化器对比各二级索引的 `key_len`：二级索引叶子节点只存索引键值和主键值，占用磁盘页远比含整行所有字段的聚簇索引（Clustered Index）轻量，扫描更窄的索引树极大削减磁盘物理 I/O 与缓冲池加载开销。
    * `COUNT(具体列名)` 必须把该字段从数据行读出并在内存做非 `NULL` 校验后才累加计数器；指定的列不是索引列或是含较多字节的冗余字段时，扫描与内存解析开销必然高于前两者。

### 单列与多列分组

* **分组切块逻辑与 NULL 归宿**
    * `SELECT AVG(salary) FROM employees;` 没有声明分组时全表 107 名员工被视作一个单一的大组，输出一条标量 `6461.68`。
    * `SELECT department_id, AVG(salary) FROM employees GROUP BY department_id;` 展示 12 个独立部门的分组汇总行：10 号 `4400.000000`、20 号 `9500.000000`、50 号 `3475.555556`、80 号 `8955.882353`、90 号 `19333.333333`、`NULL` 组 `7000.000000`。
    * `SELECT job_id, AVG(salary) FROM employees GROUP BY job_id;` 得到 19 行岗位维度汇总。
    * `GROUP BY` 遇到分组字段存在 `NULL` 空值时**不丢弃这些记录，而是把所有为 `NULL` 的行视作一个独立的分组归拢在一起**，对其内部成员统一计算组函数。
* **多列复合分组与声明顺序等价性**
    * `GROUP BY department_id, job_id` 返回 20 行，把同一部门内的不同工种清晰剥离（单看部门总体均值会把经理高薪与基层低薪强行中和）。
    * `GROUP BY department_id, job_id` 与 `GROUP BY job_id, department_id` 在业务逻辑和最终统计结果上完全等价，组数（20 行）与每组平均薪资一致，仅结果集输出时视觉排布的优先顺序有微调。
    * 等价性依据：无论先按哪个维度切分，最终聚拢在最小颗粒度分组里的成员必须同时满足“同一部门”且“同一工种”双重条件。

### 投影列与分组列的语义契约

* **典型反例的逻辑荒谬性**
    * `SELECT department_id, job_id, AVG(salary) FROM employees GROUP BY department_id;` 中，整个 50 号部门的几十名员工被物理压缩合并为结果集中的单一数据行，`AVG(salary)` 能输出唯一数字，但 50 号部门内部同时并存 `ST_MAN` 与 `ST_CLERK`，这一行展示的 `job_id` 填谁都无法代表整个部门。
* **跨数据库对比：MySQL 宽容陷阱与 Oracle 严格报错**
    * Oracle 执行上述语句直接拒绝并报错 `ORA-00979: not a GROUP BY expression`，精准指出 `job_id` 既不是组函数也未声明在 `GROUP BY` 中。
    * MySQL 在早期版本或未启用严格 SQL 模式（`ONLY_FULL_GROUP_BY`）的环境下，错误 SQL 不仅能执行成功还会展示带 `job_id` 的结果 —— 它在 50 号部门中随手抓取物理存储靠前的第一条记录的 `job_id` 显示出来。
    * MySQL 5.7.5 及 8.0 默认配置已默认开启 `ONLY_FULL_GROUP_BY` 严格校验，违反时抛错 `Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column...`。
    * > **易错点**：看到查询成功出图便草率交工，最终交付给业务方一份严重失真的伪造报表。
* **两条黄金准则**
    * 正向约束：`SELECT` 列表中出现的任何非聚合字段（没有被 `AVG`、`SUM`、`MAX`、`MIN`、`COUNT` 包裹的独立物理列），**必须全部显式声明在 `GROUP BY` 子句中**。
    * 反向自由：声明在 `GROUP BY` 子句中的字段**可以不出现在 `SELECT` 列表中**，语法依然合法，只是客户端无法直观看出该汇总数字属于哪个组，可读性较差。
    * 例：只写 `SELECT MAX(salary) ... GROUP BY job_id` 语法完全合法并返回 19 行，但结果集缺失工种标识，外部系统无法知晓每行属于哪个工种。

### HAVING 的必要性与规范

* **WHERE 中使用聚合函数直接报错**
    * 需求“查询各个部门中最高工资比 10000 高的部门信息”若写成 `WHERE MAX(salary) > 10000 GROUP BY department_id`，MySQL 抛错 `Error Code: 1111. Invalid use of group function`。
    * 原因：`WHERE` 的设计初衷是对数据表中的单行记录过滤，而不是对分组统计后的汇总结果过滤。
    * 结论：过滤条件中包含聚合函数（组函数）时，该条件**必须**声明在 `HAVING` 子句中。
    * 正确写法：`SELECT department_id, MAX(salary) FROM employees GROUP BY department_id HAVING MAX(salary) > 10000;`。
* **声明位置与搭配要求**
    * 书写位置：包含 `GROUP BY` 的标准语句中，`HAVING` 必须声明在 `GROUP BY` 之后。
    * 搭配关系：实际项目中 `HAVING` 通常与 `GROUP BY` 配合使用；没有显式 `GROUP BY` 时直接对全表聚合使用 `HAVING`（全表被隐式视为一个单一分组）虽能通过解析，但业务开发中几乎没有实际意义。
* **非聚合条件的归宿抉择**
    * 混合条件场景“部门最高工资比 10000 高，且部门 ID 为 10、20、30、40”存在两种语法上都合法的写法。
    * 方式一（推荐规范）：非聚合条件写 `WHERE department_id IN (10, 20, 30, 40)`，聚合条件写 `HAVING MAX(salary) > 10000`。
    * 方式二（不推荐）：把 `MAX(salary) > 10000 AND department_id IN (10, 20, 30, 40)` 一并塞进 `HAVING`。
    * 效率差异推演：10 万条记录中符合 4 个部门的只有 1000 条时，方式一让进入分组阶段的数据量立刻从 10 万骤降至 1000，只需为 4 个组计算 `MAX(salary)`；方式二必须把 10 万条记录全量载入内存做哈希或排序分组，为全公司 100 个部门都算出最高工资后才发现 96 个部门不需要，前期 CPU 与内存消耗全成无用功。
    * 工程规范：过滤条件不含聚合函数时，可以声明在 `WHERE` 也可以声明在 `HAVING`，但**强烈建议声明在 `WHERE` 中**；把普通字段过滤随意写在 `HAVING` 中，在代码评审或面试中往往被判定为缺乏 SQL 性能与调优意识。
* **WHERE 与 HAVING 全维度对比**

    | 比较维度 | WHERE 子句 | HAVING 子句 |
    | :--- | :--- | :--- |
    | 过滤对象 | 基表或视图中的原始单行记录 | 分组后的汇总组记录 |
    | 聚合函数支持 | 严禁包含（出现即报语法错误） | 完全支持（专用于聚合过滤） |
    | 普通字段过滤 | 支持，通过索引过滤效率极高 | 支持，但必须在分组聚合后执行，效率低 |
    | 适用范围 | 相对受限，无法处理组级指标筛选 | 更广，既可处理组函数也可处理普通字段 |
    | 执行时机 | 在 `GROUP BY` 分组与聚合计算之前执行 | 在 `GROUP BY` 分组与聚合计算之后执行 |
    | 多表连接表现 | 先过滤无效行再参与连接，大幅减少笛卡尔积开销 | 连接与分组全部完成后才过滤，计算开销巨大 |
    | 与 GROUP BY 关系 | 独立存在，先于分组生效 | 依赖分组，通常与 `GROUP BY` 配合使用 |


### 书写顺序与 `WITH ROLLUP`

* **SQL 子句书写顺序**
    * `SELECT [DISTINCT] 字段列表 / 聚合函数 FROM 数据表名 [WHERE 行级过滤条件] [GROUP BY 分组字段1, 分组字段2] [ORDER BY 排序字段 ASC/DESC] [LIMIT 分页偏移量, 每页条数];`。
    * `FROM` 负责锁定物理表数据源；`WHERE` 紧随 `FROM` 之后在分组之前对原始记录逐行初筛；`GROUP BY` 在初筛通过的干净数据集上重新切块聚合。
    * `WHERE department_id > 80` 先过滤员工再按部门分组：`SELECT department_id, AVG(salary) FROM employees WHERE department_id > 80 GROUP BY department_id;`。
    * > **易错点**：`GROUP BY` 必须位于 `FROM`（及 `WHERE`）之后、`ORDER BY` 和 `LIMIT` 之前，颠倒子句顺序直接引发语法解析异常。
* **SQL92 与 SQL99 的完整书写结构**
    * SQL92：`SELECT [DISTINCT] <字段列表, 聚合函数> FROM <表1>, <表2>, <表3> WHERE <多表连接条件> AND <非聚合函数的行级过滤条件> GROUP BY <分组字段1>, <分组字段2> HAVING <包含聚合函数的组级过滤条件> ORDER BY <排序字段> [ASC | DESC] LIMIT <offset>, <size>;`
    * SQL92 下 `WHERE` 同时承担两项重任：指定表连接条件（$N$ 张表关联至少需要 $N-1$ 个连接条件以防笛卡尔积）与过滤单行记录。
    * SQL99：把连接机制从 `WHERE` 中剥离，用 `FROM <表1> [LEFT | RIGHT] JOIN <表2> ON <多表连接条件1> [LEFT | RIGHT] JOIN <表3> ON <多表连接条件2> WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...;`。
    * SQL99 中 `WHERE` 回归纯粹的行级条件过滤，外连接直接在 `JOIN` 前指定；工程上通常推荐把数据量较大的核心驱动表写在左侧并统一使用 `LEFT JOIN`。
* **`WITH ROLLUP` 的功能与互斥法则**
    * `SELECT department_id, AVG(salary) FROM employees GROUP BY department_id WITH ROLLUP;` 把普通 `GROUP BY` 的 12 条记录扩展为 13 条。
    * 新增第 13 行的 `department_id` 被置为 `NULL`，对应平均工资恰为 `6461.682243`，即全表超级汇总行（Grand Total）。
    * 本质是在各小组分别聚合完毕后，在最底层额外追加一次针对全部数据的超级聚合运算。
    * `WITH ROLLUP` 与 `ORDER BY` 完全互斥，混用会报错 `ERROR 1221 (HY000): Incorrect usage of CUBE/ROLLUP and ORDER BY`。
    * 冲突原因：汇总行的业务定位是统领全表的总计行，必须稳定置于表格最顶部或最底部；若允许 `ORDER BY avg_sal ASC` 介入，排序算法会把总计行当普通部门记录参与比对，全公司总均值 `6461.68` 会被随机插入 10 号部门与 20 号部门正中间，彻底摧毁汇总行的业务标识意义。

### SQL 底层执行顺序

* **三大阶段与算子链路**
    * 阶段一（数据源准备、连接过滤与分组聚合）：`FROM -> ON -> [LEFT/RIGHT] JOIN -> WHERE -> GROUP BY -> HAVING`。
    * 阶段二（列投影与行去重）：`SELECT -> DISTINCT`。
    * 阶段三（排序与分页输出）：`ORDER BY -> LIMIT`。
* **虚拟表流水线**
    * `1. FROM (Cross Join)` 生成 vt1-1 笛卡尔积大宽表；`2. ON 连接条件过滤` 生成 vt1-2 保留满足连接条件的匹配行；`3. LEFT/RIGHT JOIN 补充` 生成 vt1-3 补充外部行并填补 `NULL`，锁定数据源 vt1。
    * `4. WHERE 行级过滤` 生成 vt2 剔除不满足行级条件的记录；`5. GROUP BY 分组` 生成 vt3 形成聚合单元；`6. HAVING 分组过滤` 生成 vt4 剔除不满足条件的组。
    * `7. SELECT 列投影` 生成 vt5-1 挑选列并计算表达式与别名；`8. DISTINCT 行去重` 生成 vt5-2；`9. ORDER BY 排序` 生成 vt6；`10. LIMIT 分页截取` 生成 vt7。
* **前向引用（Forward Reference）法则**
    * `WHERE`（步骤 4）发生在 `GROUP BY`（步骤 5）之前，执行 `WHERE` 过滤时数据尚未分组，组内的最大值、平均值、求和值完全处于未计算状态，因此 `WHERE` 中绝对不能使用聚合函数。
    * 任何操作只能引用此前已经生成就绪的数据或状态，绝不可能引用后续步骤才会产生的成果。
    * 别名可用性：`WHERE` 处于步骤 4、`SELECT`（别名定义发生处）处于步骤 7、`ORDER BY` 处于步骤 9。
    * 执行到步骤 4 时 `SELECT` 子句尚未被解析执行，引擎不知道用户给字段起了什么别名，在 `WHERE` 中引用必然报 `Unknown column` 错误。
    * 执行流到达步骤 9 时 `SELECT` 早已执行完毕，别名信息已注册进虚拟表 `vt5` 的元数据中，排序引擎能精准识别并按其排序。
* **调优意识的来源**
    * 数据在 `WHERE` 处被过滤掉意味着它在内存中存活的生命周期极短；把过滤推迟到 `HAVING` 则这部分无用数据不仅耗费 I/O 参与多表连接，还会强制霸占内存构建哈希表参与排序分组。
    * 本篇剖析的是 SQL 语言层面的**逻辑执行过程**；进阶体系还将深入 MySQL 服务器的**物理体系架构**（客户端连接池、SQL 接口、查询缓存、解析器、基于成本的查询优化器 CBO、执行器与 InnoDB / MyISAM 存储引擎的协同）。

## 聚合与分组实战


### 全表聚合与字段别名

* **全表聚合（不写 GROUP BY）**
    * `SELECT MAX(salary) AS max_sal, MIN(salary) AS min_sal, AVG(salary) AS avg_sal, SUM(salary) AS sum_sal FROM employees;` 返回单行四列聚合结果。
    * 全公司所有员工作为一个统一的统计大组，引擎无需在内存中维护多组桶结构，性能极高。
* **别名命名规范**
    * 数据库默认返回的列名通常是原始函数表达式（如 `MAX(salary)`），报表展现不美观，作为子查询或通过 ORM 映射时也不便。
    * 业界通行规范是采用下划线命名法（Snake Case，如 `max_salary` 或 `max_sal`）；避免使用含空格或特殊字符的别名，减少引入双引号转义的复杂度。
* **极值差计算与知识联动**
    * `SELECT MAX(salary) - MIN(salary) AS "DIFFERENCE" FROM employees;`，聚合函数可以直接参与四则算术运算，执行得差值两万多元。
    * 别名 `DIFFERENCE` 可与单行函数联动：计算日期间隔天数的 `DATEDIFF(date1, date2)` 中 `DIFF` 正是 `DIFFERENCE` 的简写。

### 单列分组与 COUNT 参数

* **分组统计与字段对应规则**
    * `SELECT job_id, MAX(salary), MIN(salary), AVG(salary), SUM(salary) FROM employees GROUP BY job_id;` 返回 19 行工种统计数据。
    * 规则一：`SELECT` 中所有未被聚合函数包裹的普通列（如 `job_id`）必须显式声明在 `GROUP BY` 中，不写则在 `ONLY_FULL_GROUP_BY` 下直接报错。
    * 规则二：声明在 `GROUP BY` 中的字段允许不在 `SELECT` 中出现，语法合法但失去业务可读性，因此维度字段应如实映射到 `SELECT` 列表。
* **分组内行数统计的参数语义**
    * `SELECT job_id, COUNT(*) AS employee_count FROM employees GROUP BY job_id;`。
    * `COUNT(*)` 与 `COUNT(1)` 语义完全等价，统计该分组内**所有物理存在的记录行数**，即便某些列的值全为 `NULL`，整行记录只要存在就会计入。
    * `COUNT(employee_id)` 统计该列的**非空（NOT NULL）值个数**，某行 `employee_id` 为 `NULL` 则该行不计入；主键不可能为 `NULL` 因此结果与 `COUNT(*)` 一致。
    * 单表无外连接场景下 `COUNT(*)`、`COUNT(1)` 与 `COUNT(employee_id)` 效果一致。

### 复合条件过滤三件套

* **需求拆解与管理者的最小工资**
    * 需求“查询各个管理者手下员工的最低工资，其中最低工资不能低于 6000，没有管理者的员工不计算在内”可解构为三阶段。
    * 统计维度与指标：管理者对应 `manager_id` 列，指标为手下员工的最低工资 `MIN(salary)`。
    * 行级过滤条件：“没有管理者的员工不计算在内”对应 `WHERE manager_id IS NOT NULL`（公司高层的 `manager_id` 为 `NULL`，不含聚合函数）。
    * 组级过滤条件：“最低工资不能低于 6000”是对聚合结果设的门槛，属于 `HAVING MIN(salary) >= 6000`。
    * 完整语句：`SELECT manager_id, MIN(salary) FROM employees WHERE manager_id IS NOT NULL GROUP BY manager_id HAVING MIN(salary) >= 6000;`
    * 分组前不加 `WHERE manager_id IS NOT NULL` 时，引擎会把 `manager_id` 为 `NULL` 的所有员工单独聚合成一个独立的管理者组，违背“查询各个管理者”的业务定义，同时提前剔除 `NULL` 可防止其占用内存桶。

### 外连接与聚合的协同陷阱

* **“所有”字眼触发的外连接警觉**
    * 题干出现“**所有**”“**每一个**”“**全量**”等字眼（所有部门、所有客户、所有学生）时必须在思维中拉响外连接警报。
    * 标准 HR 库中 `employees` 有 107 条记录其中 1 人没有部门，`departments` 有 27 个部门但只有 11 个配置了员工，另外 16 个部门没有任何员工入驻。
    * 若使用内连接（`JOIN`），空置的 16 个部门会因在员工表中找不到匹配行而全部被物理舍弃；要展现“所有部门”必须以部门表为主表做左外连接（`LEFT OUTER JOIN`）。
* **`COUNT(*)` 让空部门人数凭空变 1**
    * 初版写法 `SELECT d.department_name, d.location_id, COUNT(*) AS emp_count, AVG(e.salary) AS avg_sal FROM departments d LEFT JOIN employees e ON d.department_id = e.department_id GROUP BY d.department_name, d.location_id;`
    * 对那 16 个没有任何员工的空部门，`AVG(e.salary)` 显示正常的 `NULL`，但 `emp_count` 列全部显示为 **`1`**。
    * 原因：左连接为保留主表 `Payroll` 部门，在中间虚拟表中保留了这一行（`Payroll, 260, NULL, NULL`）并把右表 `employees` 所有列填为 `NULL`；`COUNT(*)` 只认物理行数，因此忠实返回了 `1`。
    * 业务要统计的不是虚拟表的记录行数，而是**真实的员工人数**；员工是否存在的唯一凭据是其主键 `e.employee_id` 是否非空。
    * 修正：改成 `COUNT(e.employee_id)`，引擎扫描到该组时发现 `e.employee_id` 为 `NULL`，依据聚合函数自动忽略 `NULL` 的特性不计入，返回 `0`。
    * > **易错点**：外连接与分组聚合联用统计从表实体数量时，绝不能使用 `COUNT(*)`，必须使用 `COUNT(从表主键)` 或 `COUNT(从表非空列)`。
* **修正后的完整实现与字段归属规范**
    * `SELECT d.department_name, d.location_id, COUNT(e.employee_id) AS emp_count, AVG(e.salary) AS avg_sal FROM departments d LEFT JOIN employees e ON d.department_id = e.department_id GROUP BY d.department_name, d.location_id ORDER BY avg_sal DESC;`
    * 多表联合分组中 `department_name` 与 `location_id` 均必须声明表别名前缀 `d.`。
    * 明确字段血统能提高可维护性，并避免多表同名字段引发的列名歧义（`Column ambiguously defined`）报错。
* **多列复合分组下的数据膨胀**
    * 需求“查询每一个工种、每一个部门的部门名、工种名及其最低工资”：`GROUP BY d.department_name, e.job_id`，统计指标 `MIN(e.salary)`，同样因为要求覆盖“每一个部门”必须用左外连接。
    * 内连接返回 19 行（全公司实际有员工上班的部门与工种组合共 19 种）；左外连接返回 **35 行**。
    * 多出的 16 行（$35 - 19 = 16$）恰好对应 16 个没有员工入驻的空部门，其 `job_id` 为 `NULL`、`MIN(e.salary)` 也为 `NULL`。
* **复杂聚合 SQL 的需求分析决策树**
    * 步骤一：是否涉及“所有/全量”？是则锁定 `LEFT/RIGHT JOIN`，谨防内连接数据丢失。
    * 步骤二：存在外连接且需统计从表数量？是则坚决使用 `COUNT(从表非空字段)`，禁用 `COUNT(*)`。
    * 步骤三：混合过滤条件？非聚合条件前置到 `WHERE`，聚合条件后置到 `HAVING`。

## 子查询的分类与契约


### 引入背景与三条技术路线

* **认知模型与版本背景**
    * 数据操作语言（DML）中数据查询（`SELECT`）在业务占比与逻辑复杂度上都是重中之重，子查询作为查询模块的最后一章复杂度达到顶峰。
    * 子查询的本质与通用编程语言中的**嵌套循环（Nested Loops）**完全同构：语法层面没有引入全新控制关键字，只是把一个既有的 `SELECT` 语句塞进另一个 `SELECT` 语句中。
    * 子查询机制早在 MySQL 4.1 版本就已被正式引入标准引擎，并在 MySQL 5.7 与 8.0 中持续优化。
    * 应用层代码无状态或弱状态、可替代性高（Java 微服务可改用 Go 重写，出缺陷可金丝雀发布或回滚止损）；数据库系统持久化存储企业核心命脉，跨大版本升级、数据字典重构或存储格式迁移若遭遇不兼容故障导致数据损坏或不可逆丢失，商业灾难无法挽回。因此企业数据库大版本跃迁的演进动力远低于应用框架。
* **动态未知值问题**
    * 静态常量过滤（`WHERE salary > 10000`、`WHERE department_id = 50`）无法表达“查询谁的工资比 Abel 高？”“哪些员工的工资超过了公司的平均工资？”这类需求。
    * 共同特征：过滤条件依赖于一个尚不确定的值，而这个未知值必须通过另一道查询才能得出。
* **三条技术路线的取舍**
    * 方式一（多轮 SQL 交互）：先查出 Abel 的工资 `11000`，再硬编码进 `WHERE salary > 11000`。应用服务器与数据库之间进行两次网络往返（Round-Trip Time，RTT），在分布式架构或云数据库跨机房调用下网络延迟往往远高于数据库内部内存检索时间，还在应用层引入暂存中间变量的逻辑。
    * 方式二（自连接与不等值连接）：`SELECT e2.last_name, e2.salary FROM employees e1, employees e2 WHERE e1.last_name = 'Abel' AND e2.salary > e1.salary;` 把两次网络通信压缩为一次，同样返回 10 条正确记录；但逻辑抽象度高、可读性晦涩，且在涉及聚合指标计算（如“大于平均工资”）的场景下单纯依靠连接难以直接表达。
    * 方式三（子查询嵌套）：把步骤一的整条查询原封不动搬到比较操作符后方并用小括号封闭为计算单元，一次性完成全部运算，语义贴近自然语言，架构通用性极高。

### 术语定义与编码规范

* **内外查询称谓与相对性**
    * 内查询（Inner Query）亦称子查询（Subquery）：嵌套在圆括号内部、负责提供中间计算结果的查询语句。
    * 外查询（Outer Query）亦称主查询（Main Query）：包含子查询、利用其返回值进行最终数据筛选或投影的外部查询语句。
    * 称谓具有相对性：三层甚至多层嵌套时，“外”与“内”是相对的，中间层查询相对于最内层是外查询、相对于最外层则是内查询。
* **逻辑执行契约**
    * 优先执行：内查询在主查询解析到比较条件之前先行执行完毕。
    * 结果注入：内查询计算出的临时结果（单值标量或值列表）被回传给外查询。
    * 主词生效：外查询消费该结果，完成最终记录的扫描与输出。
* **两条编码守则**
    * 规范一：所有子查询语句都必须严格封闭在一对半角圆括号 `()` 内，括号明确运算符优先级并向解析器宣告这是独立的内部子表达式。
    * 规范二：推荐写成 `<列名> <比较符> (<子查询>)`，例如 `salary > (SELECT ...)`。
    * 把子查询写在比较符左侧（`(SELECT salary ...) < salary`）在部分数据库也能通过编译，但属于严重破坏可读性的反模式：长篇子查询放左侧会让 `WHERE` 语句“头重脚轻”，阅读者必须先读懂内部长 SQL 才能在末尾看到被比对的目标字段。

### 维度一：按返回结果条目数

* **单行子查询（Single-Row Subquery）**
    * > **定义**：内查询执行完毕后仅返回一行记录（通常是单个字段标量值）的子查询。
    * 主查询中必须使用单行比较操作符配合：等于 `=`、大于 `>`、大于等于 `>=`、小于 `<`、小于等于 `<=`、不等于 `<>` 或 `!=`。
* **多行子查询（Multiple-Row Subquery）**
    * > **定义**：内查询执行完毕后返回多行记录（一个结果值列表集合）的子查询，数据库理论中也称集合比较子查询。
    * 内查询返回一组工资集合（如 `{4400, 8000}`）时若仍用单行比较符，引擎在比对时无法决定该与集合中哪一个值相等，直接抛运行时错误 `Error Code: 1242. Subquery returns more than 1 row`。
    * 必须使用多行比较操作符：`IN` 等于集合中任意一个值；`ANY` / `SOME` 与集合中每一个值比较、只要有任意一个满足即为真；`ALL` 与集合中所有值比较、必须每一个都满足才为真。

### 维度二：按内外执行相关性

* **不相关子查询（Non-Correlated Subquery）**
    * > **定义**：内查询的执行完全独立于外查询，内查询中不包含任何外查询表的字段；内查询仅在启动时执行一次，其结果作为静态常量供外查询比对。
    * 案例“查询工资大于本公司平均工资的员工信息”：无论外查询扫描到张三、李四还是王五，比对的基准都是同一个全公司平均薪资（如 `6461.83`）；内查询只运行一次算出该值，随后外查询遍历全表逐行比对即可。
* **相关子查询（Correlated Subquery）**
    * > **定义**：内查询的执行依赖于外查询当前正在处理的数据行；内查询内部引用了外查询表的字段，导致外查询每扫描一行数据，内查询就必须被重新驱动执行一次。
    * 案例“查询工资大于本部门平均工资的员工信息”：处理部门 10 的员工时内层算部门 10 均薪（如 `7000`）并比对，扫描到部门 20 的员工时内层必须被重新唤醒算部门 20 均薪（如 `9500`）并比对。
    * 外层每流动一行内层的计算上下文就随之改变，内外查询之间存在动态的数据血缘依赖。
* **相关性带来的开销量级**
    * 不相关子查询时间复杂度通常为 $O(M + N)$：内查询计算一次耗时 $O(M)$，外查询单次扫描耗时 $O(N)$。
    * 相关子查询在未被优化器展开改写为连接的情况下，朴素执行复杂度退化为 $O(N \times M)$；外表有 10 万条记录时内查询将被重复触发 10 万次，带来巨大 CPU 与磁盘 I/O 压力。
* **渐进式学习路径与优化预告**
    * 阶段一（基础奠基）：单行子查询，聚焦不相关场景，掌握 `=`、`>`、`<` 与异常处理。
    * 阶段二（集合拓展）：多行子查询，聚焦不相关场景，掌握 `IN`、`ANY`、`ALL` 集合运算。
    * 阶段三（高阶突破）：相关子查询，打破单向独立，攻克内外数据联动与 `EXISTS` 运算符。
    * 进阶性能篇将涉及基于成本优化器（CBO）对子查询的改写策略，例如子查询反嵌套（Unnesting）、子查询展开为半连接（Semi-Join）或物化（Materialization）。

## 单行子查询


### 操作符与契约

* **六大单行比较操作符**
    * `=` 等于：外层字段与内层单值严格相等。
    * `<>` 或 `!=` 不等于：外层字段与内层单值不相等。
    * `>` 大于、`>=` 大于等于、`<` 小于、`<=` 小于等于。
* **操作符与返回维度的强契约**
    * 单行操作符是一元对一元的比较算子（Scalar vs Scalar），无法直接处理一个集合或多行数据。
    * 内查询违反单行契约输出多行时，原本看似合法的 SQL 将在运行时直接崩溃。
    * 确保内查询在任何数据分布下都严格产出单行，是使用单行操作符的首要前提。
* **单行属性的判定依据**
    * 判定子查询是单行还是多行，依据是**内查询返回的行数，而非外查询最终返回的行数**。
    * `SELECT MIN(salary) FROM employees` 是没有 `GROUP BY` 的全表聚合，必然且仅会返回单一数值（`2100`），因此是不折不扣的单行子查询；外查询最终查出几名并列 `2100` 的员工属于外层数据分布结果，完全不影响内层的单行属性。

### 双向思维模型

* **由里往外写（Inside-Out）推导验证法**
    * 适用场景：业务逻辑明确、未知量相对单一、直觉推导顺畅。
    * 步骤一：定位未知值，明确哪个参数当前未知（如“149 号员工的工资是多少”）。
    * 步骤二：单独实现并验证，在 SQL 客户端中单独执行子查询，观察返回的单行数据是否符合预期。
    * 步骤三：主干组装，把题目翻译为“查询工资大于 [该数值] 的员工”，编写外查询，最后用括号包裹验证通过的内层 SQL 替换硬编码数值。
* **由外往里写（Outside-In）主干拆解法**
    * 适用场景：题干修饰定语极长、包含多个复合嵌套条件。
    * 步骤一：语法断句提取主谓宾，砍掉“与某某部门某某人薪资相同的……”等冗长定语，只抓核心主干。
    * 步骤二：搭建外层骨架，先写最外层 `SELECT ... FROM ... WHERE ...`，在比较运算符后放空括号 `()` 占位。
    * 步骤三：各个击破，回到被剔除的定语成分中，在括号内针对性地编写子查询逻辑。
* **双向能力的对称性**
    * 汉译英能力：把产品经理或业务方提出的自然语言需求精准翻译为高效 SQL。
    * 英译汉能力：接手遗留系统、排查慢查询日志（Slow Query Log）或代码评审时，面对多层嵌套 SQL 迅速逆向还原其真实业务意图。

### 典型实战形态

* **基于指定员工薪资的过滤**
    * 需求：查询工资大于 149 号员工工资的员工信息。
    * 内层探路 `SELECT salary FROM employees WHERE employee_id = 149;` 返回单值 `10500`，外层组装 `WHERE salary > (SELECT salary FROM employees WHERE employee_id = 149)`。
* **复合子查询多条件联合判定**
    * 需求：返回 `job_id` 与 141 号员工相同，且 `salary` 比 143 号员工多的员工姓名、`job_id` 和工资。
    * 两个独立未知条件用逻辑与串联：`WHERE job_id = (SELECT job_id FROM employees WHERE employee_id = 141) AND salary > (SELECT salary FROM employees WHERE employee_id = 143);`
    * 内查询 1 返回 `'ST_CLERK'`，内查询 2 返回 `2600`。
* **成对列比较（Row Constructor）**
    * 需求：查询与 141 号员工的 `manager_id` 和 `department_id` 相同的其他员工。
    * 方式一：分别对两个字段写独立单行子查询再 `AND` 连接，附带 `AND employee_id <> 141`。
    * 方式二：`WHERE (manager_id, department_id) = (SELECT manager_id, department_id FROM employees WHERE employee_id = 141) AND employee_id <> 141;` 把两个字段打包一起比对，两次内层查询压缩为一次。
    * 选型评价：现代数据库对基于索引的主键点查优化极其极致，两次单列点查与一次双列点查的耗时差异微乎其微；方式二使用场景极其苛刻，必须要求比对的多个列来自同一个子查询实体，一旦变成“管理者与 A 相同、部门与 B 相同”便立刻失效。实际工业界方式一仍是兼容性最好、表达力最通用的主流写法。

### 高阶子句中的嵌入

* **`HAVING` 中嵌套单行子查询**
    * 需求：查询最低工资大于 50 号部门最低工资的部门 id 和其最低工资。
    * 需要 `GROUP BY department_id` 配合 `HAVING`，过滤门槛通过子查询计算。
    * `SELECT department_id, MIN(salary) FROM employees WHERE department_id IS NOT NULL GROUP BY department_id HAVING MIN(salary) > (SELECT MIN(salary) FROM employees WHERE department_id = 50);`
    * 引擎先执行子查询算出 50 号部门最低工资（`2100`），外查询完成分组聚合后由 `HAVING` 把各组最低工资与 `2100` 比对，筛选出达标分组。
* **`CASE` 流程控制中嵌入单行子查询**
    * 需求：显示员工的 `employee_id`、`last_name` 和 `location`，若员工 `department_id` 与 `location_id` 为 1800 的 `department_id` 相同则 `location` 为 `'Canada'`，其余为 `'USA'`。
    * `SELECT employee_id, last_name, CASE department_id WHEN (SELECT department_id FROM departments WHERE location_id = 1800) THEN 'Canada' ELSE 'USA' END AS "location" FROM employees;`
    * 子查询先行在 `departments` 表中解析出目标部门 ID 为 `20`；`CASE` 把当前员工 `department_id` 与 `20` 做分支判断；`department_id` 为 `NULL` 的员工因不等于 20 也会安全落入 `ELSE` 分支输出 `'USA'`。
* **“未知即子查询”的架构化原则**
    * 在 SQL 查询的任何局部（投影列、`WHERE` 行过滤、`HAVING` 组过滤、`CASE` 分支），只要出现无法静态确定的标量值，都可以无缝嵌入一条单行子查询来动态补位。

### 两类高频陷阱

* **子查询空值引发的结果集静默落空**
    * 案例：`SELECT last_name, job_id FROM employees WHERE job_id = (SELECT job_id FROM employees WHERE last_name = 'Haas');` 控制台不抛任何错误，但返回结果集行数为 `0`（Empty set）。
    * 失效链路：底层无 `'Haas'` 此人 → 内查询返回 0 行（结果为 `NULL` / 空结果）→ 外查询变成 `WHERE job_id = NULL` → SQL 三值逻辑（TRUE、FALSE、UNKNOWN）中任何值与 `NULL` 做 `=` 比较结果恒为 UNKNOWN（假）→ 外查询所有记录被静默剔除。
    * > **易错点**：子查询未匹配到任何数据行时不会引发语法异常，而是向外层传递等价于 `NULL` 的空值，导致外层查询结果静默清空；编写代码前必须明确内层数据源的非空预期。
* **维度不匹配引发 1242 运行时崩溃**
    * 错误示范：`SELECT employee_id, last_name, salary FROM employees WHERE salary = (SELECT MIN(salary) FROM employees GROUP BY department_id);` 执行后抛 `Error Code: 1242. Subquery returns more than 1 row`。
    * 崩溃原理：外查询使用单行等于操作符 `=`；内查询因含 `GROUP BY department_id` 输出了全公司十几个部门各自的最低工资集合（如 `{2100, 4200, 4400, 6000, 7000, ...}`）；等号无法回答“当一条记录的工资等于集合中某一个值时是否算成立”，解析引擎检测到左侧是标量、右侧是集合，产生维度冲突直接报错拒绝执行。
    * 结论：内查询在业务上有可能产出多行数据时，绝不能使用 `=`、`>`、`<` 等单行操作符，必须切换为 `IN`、`ANY`、`ALL` 等多行集合比较操作符。

## 多行子查询


### 四大集合比较操作符

* **语义与判定规则**

    | 操作符 | 语法形式 | 核心数学语义 | 判定规则 |
    | :--- | :--- | :--- | :--- |
    | `IN` | `列 IN (子查询)` | 等于集合中的任意一个值 | 列表中存在一个等于当前列的值即返回 `TRUE` |
    | `ANY` | `列 比较符 ANY (子查询)` | 与集合中的某一个（任一）值比较 | 集合中**存在至少一个元素**与当前列满足单行比较符关系即返回 `TRUE` |
    | `ALL` | `列 比较符 ALL (子查询)` | 与集合中的所有值比较 | 集合中的**每一个元素**都必须与当前列满足单行比较符关系才返回 `TRUE` |
    | `SOME` | `列 比较符 SOME (子查询)` | 同 `ANY` | `SOME` 是 `ANY` 的同义词/别名，功能完全一致 |

    * 实际项目与日常开发中习惯统一使用 `ANY`；`SOME` 的存在主要是为符合 ANSI SQL 的不同语法偏好，遗留系统里遇到 `SOME` 直接视同 `ANY` 处理。
* **ANY 与 ALL 的直观分野**
    * `ANY` 模式：只要能从候选集合中成功牵手**任何一位**即可完成匹配，满足任一条件即可。
    * `ALL` 模式：必须同时兼具并征服**所有人**的所有优点，候选集合里的每一个对象都必须完全符合条件才算匹配成功。

### 与极值聚合函数的代数等价

* **四条等价关系**
    * $x < \text{ANY}(S) \iff x < \max(S)$：只要 `x` 小于集合中的最大值就必然满足。
    * $x > \text{ANY}(S) \iff x > \min(S)$：只要 `x` 大于集合中的最小值就必然满足。
    * $x < \text{ALL}(S) \iff x < \min(S)$：必须小于集合中的最小值。
    * $x > \text{ALL}(S) \iff x > \max(S)$：必须大于集合中的最大值。
    * $x = \text{ANY}(S)$ 等价于 $x \text{ IN } (S)$。

### 实战推导

* **`IN` 修复 1242 报错**
    * 把 `WHERE salary = (SELECT MIN(salary) FROM employees GROUP BY department_id)` 中的 `=` 改为 `IN` 即可执行。
    * 执行机理：先按 `department_id` 分组算出各部门最低薪水集合 `{4400, 6000, 6500, 9000, 4200, 2500, ...}`；再遍历 `employees` 每行判断 `salary` 是否在集合中，匹配任意一个即保留该行。
    * `IN` 能够兼容单行结果集：内查询确实只返回单行单列时外层用 `IN` 不会报错，只是已知内部必定为标量时使用 `=` 在语义表达与优化器执行计划上更清晰。
* **`< ANY` 与 `< ALL` 的对比实战**
    * 内查询 `SELECT salary FROM employees WHERE job_id = 'IT_PROG';` 返回集合 `{9000, 6000, 4800, 4800, 4200}`。
    * 题目 A（比任一工资低）：`WHERE job_id <> 'IT_PROG' AND salary < ANY (SELECT salary FROM employees WHERE job_id = 'IT_PROG');`。工资 `8000` 的员工会被查出，因为 `8000 < 9000` 已满足“比集合中某一个值低”；归纳即只要小于集合最高工资 `9000`（`< MAX(salary)`）就会被检索出来。
    * 题目 B（比所有工资都低）：把 `ANY` 换成 `ALL`，`salary < ALL ({9000, 6000, 4800, 4200})` 意味着必须同时小于 9000、6000、4800、4200，数学本质是严格小于整个集合的最低值 `4200`（`< MIN(salary)`）；结果集所有员工薪资均分布在 `4200` 以下（如 2500、3000）。
* **平均工资最低的部门（两种解法）**
    * 步骤一：`SELECT department_id, AVG(salary) FROM employees GROUP BY department_id;` 返回每部门均薪列表，最低项约 `3475.55`（对应 50 号部门）。
    * 报错陷阱：`SELECT MIN(AVG(salary)) FROM employees GROUP BY department_id;` 执行报 `ERROR 1111 (HY000): Invalid use of group function`。
    * 结论：**MySQL 中组函数（聚合函数）严格禁止多层嵌套使用**；单行函数可以无限嵌套（如 `TRUNCATE(ROUND(123.456, 1), 0)`），但聚合函数场景下 MySQL 优化器无法在同一查询作用域内同时解析两层分组聚合。
    * 跨库差异：Oracle 原生支持两层聚合函数嵌套，`SELECT MIN(AVG(salary)) FROM employees GROUP BY department_id;` 在 Oracle 中合法并能成功执行。
    * 方式一（派生表三层嵌套）：把内层查询结果视作一张内存数据表（Derived Table，派生表），`SELECT MIN(avg_sal) FROM (SELECT AVG(salary) avg_sal FROM employees GROUP BY department_id) t_dept_avg_sal;` 其中 `avg_sal` 已成为虚拟表的普通字段而不再是聚合函数。
    * 方式一硬性规则：MySQL 语法规定**放在 `FROM` 子句后面的任何子查询（派生表）都必须显式赋予表别名**，否则抛语法错误 `Every derived table must have its own alias`。
    * 方式一完整三层结构：`SELECT department_id FROM employees GROUP BY department_id HAVING AVG(salary) = (SELECT MIN(avg_sal) FROM (SELECT AVG(salary) avg_sal FROM employees GROUP BY department_id) t_dept_avg_sal);` 精准返回 `50` 号部门。
    * 方式二（`<= ALL` 极值代换两层结构）：`SELECT department_id FROM employees GROUP BY department_id HAVING AVG(salary) <= ALL (SELECT AVG(salary) FROM employees GROUP BY department_id);`
    * 极值代换原理：内查询返回所有部门均薪集合 $S$，外查询的 `AVG(salary)` 本身就是 $S$ 中的一个具体成员；要求它 `<= ALL(S)` 即必须小于等于集合中每一个元素；在有限实数集合中，小于等于所有元素的那个数在数学上有且仅有集合的最小值本身 $\min(S)$。
    * > **易错点**：多层嵌套既深又长，容易漏写派生表别名或写错括号层级。

### NOT IN 与 NULL 空值黑洞

* **业务场景与灾难现场**
    * 需求：查询公司中不是管理者的所有员工姓名。
    * 步骤一 `SELECT DISTINCT manager_id FROM employees;` 返回 18 行非空员工编号，外加 1 行 `NULL`（公司大总裁 Steven King 是最高级别管理者，没有主管，`manager_id` 为 `NULL`）。
    * 步骤二按 107 减去 18 应剩 89 位普通员工，写成 `SELECT last_name FROM employees WHERE employee_id NOT IN (SELECT manager_id FROM employees);` 后结果集为 `Empty set (0.00 sec)`，89 名普通员工瞬间全体“蒸发”。
* **三值逻辑解密**
    * 语法展开：`a IN (v1, v2)` 等价于 $(a = v_1) \lor (a = v_2)$；因此 `a NOT IN (v1, v2, ..., vn)` 被内核严格展开为 $(a \ne v_1) \land (a \ne v_2) \land \dots \land (a \ne v_n)$。
    * `NULL` 比较语义：集合中包含 `NULL` 时最后一项比较是 $a \ne \text{NULL}$，任何数值与 `NULL` 做等值或不等值比较的结果既不是 `TRUE` 也不是 `FALSE`，而是 **`UNKNOWN`**。
    * 短路与失效：普通员工（如 `employee_id = 107`）前面所有判断都为 `TRUE`，最终得到 $\text{TRUE} \land \text{TRUE} \dots \land \text{TRUE} \land \text{UNKNOWN}$；只要有逻辑与序列中存在一个 `UNKNOWN`，整个表达式结果就是 `UNKNOWN`。
    * WHERE 过滤准则：`WHERE` 子句有且仅有在条件求值结果为明确 `TRUE` 时才放行记录，`UNKNOWN` 一律视同不满足条件予以过滤；由于集合包含 `NULL`，无论外层传入什么 `employee_id` 整个条件永远是 `UNKNOWN`，没有任何一条记录能通过筛选。
    * > **易错点**：使用 `NOT IN` 进行多行子查询时，必须确保内层子查询结果集绝对不包含 `NULL` 值。
* **规避写法**
    * 在内查询中显式增加 `IS NOT NULL` 过滤条件：`SELECT last_name FROM employees WHERE employee_id NOT IN (SELECT manager_id FROM employees WHERE manager_id IS NOT NULL);` 执行后预期的 89 条员工记录完整准确返回。

## 相关子查询与 EXISTS 谓词


### 分类正交性与执行机制

* **两个维度交叉而非互斥**
    * 单行 × 不相关：内查询执行一次，返回单行标量。
    * 单行 × 相关：外部每行驱动一次，内层返回单行。
    * 多行 × 不相关：内查询执行一次，返回多行集合。
    * 多行 × 相关：外部每行驱动一次，内层返回集合。
    * 教学递进中选例多为不相关，切不可误以为单行/多行子查询天然就是不相关的。
* **不相关子查询的两步常量模型**
    * 第一步执行内查询独立算出结果（如 Abel 的工资 `11000`）。
    * 第二步遍历外表 107 条记录逐一取出 `salary` 判断是否满足 `salary > 11000`，满足保留、不满足丢弃；内查询从始至终只被计算了**一次**。
* **相关子查询的三步循环机制**
    * > **定义**：如果子查询的执行条件依赖于外部查询的候选行（表现为子查询中引用了外部查询的表字段并构成过滤关联），该子查询被称为相关子查询（关联子查询）；外部查询每处理一条候选记录，子查询都必须带着该行的数据重新计算一次。
    * 第一步：主查询提取第 i 行候选记录（如部门为 90 号的员工）。
    * 第二步：传递关联列（`e1.department_id = 90`）进入子查询，带入 `e1` 字段算出 90 号部门均薪 `19333.33`。
    * 第三步：返回该部门专属均薪，外层求值判断该员工薪资是否大于该值，TRUE 收集至最终结果集、FALSE 剔除；随后继续提取第 i+1 行循环驱动。
    * 逻辑概念上类似高级语言中的嵌套 `for` 循环：外部每迭代一步就把外层的上下文参数“注射”到内层，内层按需计算后向外层回调结果。

### 典型案例

* **高于本部门平均薪资的员工（相关子查询）**
    * 演进推导：全局常量场景（大于全公司平均薪资，内层 `SELECT AVG(salary) FROM employees` 算出 `6461.68`）属不相关；局部常量场景（固定求大于 60 号部门平均薪资，内层加 `WHERE department_id = 60` 算出 `5760.00`）仍属不相关；真实业务场景中内查询过滤条件无法写死，必须绑定外查询当前行的部门。
    * 标准写法：`SELECT e1.last_name, e1.salary, e1.department_id FROM employees e1 WHERE e1.salary > (SELECT AVG(e2.salary) FROM employees e2 WHERE e2.department_id = e1.department_id);` 必须为两层查询分别赋予别名 `e1` 与 `e2`。
    * 逐行执行细节：外部指针指向 Steven King（`department_id = 90`，`salary = 24000`）→ 传入 `e1.department_id = 90` 算出 90 号部门均薪约 `19333.33` → `24000 > 19333.33` 为 TRUE 被选中 → 外部指针指向 60 号部门某员工时子查询动态重算该部门均薪 → 最终全表筛出符合条件记录。
    * 派生表连接替代写法：`FROM employees e JOIN (SELECT department_id, AVG(salary) AS avg_sal FROM employees GROUP BY department_id) t_dept_avg_sal ON e.department_id = t_dept_avg_sal.department_id WHERE e.salary > t_dept_avg_sal.avg_sal;`，派生表必须起别名，`AVG(salary)` 必须显式赋列别名 `avg_sal` 才能作为虚拟实体的具体列参与外层连接与比对，执行结果与相关子查询一致。
* **在 `ORDER BY` 中使用相关子查询**
    * 需求：查询员工的 `employee_id` 和 `salary`，并按照其所属部门的 `department_name` 升序排序。
    * 痛点：`employees` 表只有 `department_id` 没有 `department_name`，该字段存储在独立的 `departments` 维度表中。
    * 写法：`SELECT e.employee_id, e.salary FROM employees e ORDER BY (SELECT d.department_name FROM departments d WHERE d.department_id = e.department_id) ASC;`
    * 运行逻辑：外部表逐行扫描每个员工获取其 `department_id`，内层相关子查询按该 ID 去 `departments` 表检索对应名称字符串，`ORDER BY` 接收该字符串作为该行的排序权重键完成整表字典序排定。
    * 边界情况：某员工 `department_id` 为 `NULL` 时子查询返回 `NULL`，升序排列时该员工被置于结果集最前列。
* **基于 `COUNT(*)` 的跨表阈值统计**
    * 需求：若员工表中的 `employee_id` 在岗位变动历史表 `job_history` 中出现的相同次数不少于 2 次，输出这些员工的 `employee_id`、`last_name` 和当前工种 `job_id`。
    * 写法：`SELECT e.employee_id, e.last_name, e.job_id FROM employees e WHERE 2 <= (SELECT COUNT(*) FROM job_history j WHERE j.employee_id = e.employee_id);`
    * 推导：外部员工输入 `employee_id = 101` → 内查询在 `job_history` 表中执行 `WHERE j.employee_id = 101` 得出匹配记录数为 `2` → 外层求值 `2 <= 2` 为 TRUE 保留；输入 `employee_id = 102` 时匹配记录数为 `1`、`2 <= 1` 为 FALSE 被剔除；最终全公司共有 3 名资深员工经历过 2 次及以上内部调岗记录。

### 声明位置全景与禁区

* **可放置位置**
    * `SELECT ...`：可放子查询，常见于高级投影。
    * `FROM ...`：可放子查询作为派生表（Derived Table），必须带别名。
    * `WHERE ...`：最常见的子查询位置，标量或集合过滤。
    * `HAVING ...`：可放子查询，对分组聚合结果过滤。
    * `ORDER BY ...`：可放子查询，用于跨表字段权重排序。
* **两个禁区**
    * `GROUP BY ...`：**绝对禁止声明子查询**，后面必须是具体的物理列名或表达式，不能放入动态子查询。
    * `LIMIT ...`：**绝对禁止声明子查询**，后面接收的是纯粹的常量数值（预编译语句中可为占位符 `?`）。
    * 核心结论：标准的 SQL 查询语法体系中，除了 `GROUP BY` 和 `LIMIT` 之外，子查询几乎可以嵌入到查询语句的任何子句中。

### EXISTS 与 NOT EXISTS

* **短路求值特性**
    * > **定义**：`EXISTS` 谓词用于测试子查询是否能检索到至少一行满足条件的数据，只关心“存在与否（Existence）”而不关心具体检索出的数据内容。
    * 当外查询将一条候选记录传入 `EXISTS` 子查询后，内层引擎开始检索内部表，**一旦扫描到第一条满足条件的行，子查询立即终止向后的物理扫描并直接返回 `TRUE`**。
    * 只有当内层表全量扫描完毕仍未发现任何匹配项时才返回 `FALSE`。
    * `NOT EXISTS` 相反：整表扫描完未发现匹配时返回 `TRUE`；一旦遇到第一条匹配立即短路终止并返回 `FALSE`。
    * 短路示例：外部传入 `employee_id = 100`，内表 `manager_id` 列扫描中 Row 1 为 `102` 不匹配继续，Row 2 为 `100` 命中后立刻返回 `TRUE` 并中断扫描，Row 3 起无需继续物理读页。
* **投影列无差别**
    * `EXISTS` 子查询投影列表中通常书写 `SELECT *`、`SELECT 1` 或 `SELECT 'X'`，这三者在底层执行效率上**完全没有任何区别**。
    * 优化器解析到 `EXISTS` 语义时会自动忽略 `SELECT` 后的投影列，不会真正去读取和传输字段数据，只做存在性布尔探测。
* **案例：检索所有管理者的三条路径**
    * 路径 1（自连接配合 `DISTINCT`）：`SELECT DISTINCT mgr.employee_id, mgr.last_name, mgr.job_id, mgr.department_id FROM employees e JOIN employees mgr ON e.manager_id = mgr.employee_id;` 因一个管理者可能下辖多名员工，连接后出现大量重复行必须显式 `DISTINCT` 去重，最终输出 18 条。
    * 路径 2（多行子查询 `IN`）：`SELECT employee_id, last_name, job_id, department_id FROM employees WHERE employee_id IN (SELECT DISTINCT manager_id FROM employees WHERE manager_id IS NOT NULL);`
    * 路径 3（`EXISTS` 关联子查询，最推荐之一）：`SELECT e1.employee_id, e1.last_name, e1.job_id, e1.department_id FROM employees e1 WHERE EXISTS (SELECT * FROM employees e2 WHERE e2.manager_id = e1.employee_id);`
    * 路径 3 逻辑：外部指针指向员工 100（Steven King）送入子查询，子查询在 `e2` 表中查找是否存在 `manager_id = 100` 的员工，扫描到第 2 行员工 101 时条件满足，`EXISTS` 瞬间短路返回 `TRUE` 不再继续遍历后面的百余条记录；全表无需额外进行昂贵的排序去重（`DISTINCT`），执行效率极佳，同样精准返回 18 条记录。
* **案例：检索没有员工的空部门**
    * 方式一（右外连接过滤差集）：`SELECT d.department_id, d.department_name FROM employees e RIGHT JOIN departments d ON e.department_id = d.department_id WHERE e.department_id IS NULL;` 通过保留右表全部记录并筛选左表连接键为 `NULL` 的行，获取 16 条空部门记录。
    * 方式二（`NOT EXISTS` 相关子查询）：`SELECT d.department_id, d.department_name FROM departments d WHERE NOT EXISTS (SELECT * FROM employees e WHERE e.department_id = d.department_id);`
    * 方式二机理：外表遍历 27 个部门；测试 10 号、20 号等有员工的部门时内层一旦找到归属员工就立刻短路判定失败；测试到没有分配员工的部门时内层穷尽扫描未发现匹配，`NOT EXISTS` 判定为 `TRUE` 输出该部门；最终输出与外连接完全一致的 16 条记录。

### DML 中的相关子查询

* **相关更新（UPDATE）多表冗余字段同步**
    * 场景：`employees` 表新增 `department_name` 字段后全量 107 行历史数据均为 `NULL`，需用部门表批量回填。
    * `UPDATE employees e SET department_name = (SELECT d.department_name FROM departments d WHERE d.department_id = e.department_id);`
    * 外部 `UPDATE` 遍历 `employees` 每一行，每次更新时动态执行内层相关子查询，根据当前行 `department_id` 从 `departments` 维度表提取唯一部门名称并赋值给当前行 `department_name` 列。
* **相关删除（DELETE）跨表一致性清理**
    * 场景：删除员工表中所有在历史调岗表 `job_history` 中存在对应履历的员工记录。
    * `DELETE FROM employees e WHERE e.employee_id IN (SELECT j.employee_id FROM job_history j WHERE j.employee_id = e.employee_id);`
    * 外部待删除候选行逐一传入内层校验，只有跨表存在交集的实体才会被精准命中并清除。

### JOIN 与子查询的选型

* **核心结论与三条理由**
    * 核心结论：在多表连接（如自连接）与子查询均可实现某一业务需求的场景下，**通常应当无条件优先选择多表连接（JOIN）**。
    * 理由一（优化器成熟度）：关系型数据库（特别是 MySQL）经过数十年演进，优化器针对多表连接的代价估算模型（CBO，Cost-Based Optimizer）、驱动表选择、索引嵌套循环连接（Index Nested-Loop Join）以及 Block Nested-Loop / Hash Join 算法做到了极高水平优化。
    * 理由二（临时表与内存开销）：未经良好优化的子查询执行时往往需要隐式物化临时表（Materialization），产生额外磁盘或内存 I/O，并伴随多轮不必要的重复扫描。
    * 理由三（优化器自动重写）：现代 MySQL（尤其 5.7 与 8.0）内部若分析出某个子查询可等价转换为连接查询，甚至会在执行计划生成前**强行在内部将子查询解构并自动重写为 JOIN 操作**（子查询展开/消除）；既然优化器都在底层竭尽全力改写，编写 SQL 之初直接采用连接查询能减轻优化器解析负担并保证执行计划的可预期性。

## 子查询二十道实战


### 编写心法与适用边界

* **两种思维流派的适用边界**
    * 从外往里写（自顶向下）：优先立起主查询外层框架，遇到未知条件用括号占位，逐步向下嵌套补齐；适合题意直白、嵌套层级在 1 到 2 层的简单场景。
    * 从里往外写（自底向上）：先识别最核心的底层未知变量，编写最内层查询并单独执行校验，确认结果集形态后再套上一层；适合涉及跨表关联、分组聚合、极值筛选的多层复杂场景。
    * 嵌套达到 3 到 4 层时若执意从外往里写，每写一层内心就增加一份不确定性；写完整段数十行的复杂 SQL 后一旦执行报错，很难迅速定位是外层条件冲突还是内层派生表逻辑有误。
    * 自底向上时每写完一层内查询都在客户端独立运行确认其返回的数据形态（是单行还是多行？是否包含 `NULL`？列名是什么？）。
* **等价与兜底技巧**
    * `>` `ALL(集合)` 在数学上严格等价于大于该集合的最大值（`> MAX()`）；对应地 `<= ALL` 等价于小于等于最小值。
    * 无法由唯一索引保证内查询结果唯一性时，用 `IN` 代替 `=` 进行安全兜底；即使内查询仅返回单行 `IN` 亦能完美兼容。
    * 生产库中员工姓名不是唯一主键，极易出现同名同姓；一旦存在两名同姓名的员工且分属不同部门，内查询返回多行，`=` 必然触发 `Subquery returns more than 1 row`。
    * 凡能够使用 `IN` 实现的多行子查询，通常都可以对偶改写为 `EXISTS` 关联子查询；凡能够使用 `NOT IN` 实现的排除型子查询，通常都可以对偶改写为 `NOT EXISTS`。
    * 改写为 `EXISTS` 后能天然规避 `NOT IN` 遇到 `NULL` 导致结果集全空的恶性隐患，同时利用短路求值（Short-circuiting）机制大幅降低扫描成本。

### 单行与集合比较类题目

* **同部门员工检索（等号风险与 IN 兜底）**
    * `SELECT last_name, salary FROM employees WHERE department_id IN (SELECT department_id FROM employees WHERE last_name = 'Zlotkey');`
* **高于全公司均薪（标量子查询标准范式）**
    * `SELECT employee_id, last_name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees);` 内查询返回唯一平均工资 `6461.68`，属于标准的不相关单行子查询。
* **大于指定工种全体员工薪资（`> ALL` 与 `> MAX` 等价）**
    * 内查询取出 `'SA_MAN'` 工种薪水集合 `{14000, 13500, 12000, 11000, 10500}`，`WHERE salary > ALL (SELECT salary FROM employees WHERE job_id = 'SA_MAN');` 等价于 `WHERE salary > (SELECT MAX(salary) FROM employees WHERE job_id = 'SA_MAN');`，筛选出工资严格高于 `14000` 的高薪员工。
* **含特定字母员工的同部门检索**
    * 内查询 `SELECT DISTINCT department_id FROM employees WHERE last_name LIKE '%u%';` 返回 5 个独立部门；外查询用 `IN` 匹配这 5 个部门的全体员工。
* **指定位置 ID 部门的归属员工**
    * 内查询 `SELECT department_id FROM departments WHERE location_id = 1700;` 返回 21 条部门记录；外查询 `WHERE department_id IN (...)` 在 `employees` 表中匹配员工。
    * 21 个部门中部分尚未入驻员工，但 `IN` 只对员工表中实际存在的匹配项放行，不会因空部门产生逻辑异常。
* **指定管理者下属员工（题干语义歧义辨析）**
    * “管理者是 King” 有两种理解：找名为 King 的管理者本人（只需 `WHERE last_name = 'King'`，不需要子查询）；找直属领导为 King 的下属员工（真实意图）。
    * 内查询 `SELECT employee_id FROM employees WHERE last_name = 'King';` 发现公司中有两名员工姓 King，工号分别为 `100`（大总裁 Steven King）与 `156`（销售代表 Janette King）。
    * 外层 `SELECT last_name, salary, manager_id FROM employees WHERE manager_id IN (SELECT employee_id FROM employees WHERE last_name = 'King');` 结果中所有下属员工的 `manager_id` 全部为 `100`，说明工号 `156` 的 King 是普通一线员工、下属数量为 0。
* **全公司薪水最低员工**
    * `SELECT last_name, salary FROM employees WHERE salary = (SELECT MIN(salary) FROM employees);` 内查询输出最低标量薪资 `2100`。
* **平均工资高于全公司平均工资的部门**
    * `SELECT department_id FROM employees WHERE department_id IS NOT NULL GROUP BY department_id HAVING AVG(salary) > (SELECT AVG(salary) FROM employees);`
    * 不加 `WHERE department_id IS NOT NULL` 时结果集中会出现一行 `department_id` 为 `NULL` 的记录：一名尚未明确分配部门的员工薪资为 7000，高过 `6461.68`，被独立归为一个 `NULL` 分组。
    * 过滤位置铁律：凡是不涉及组函数（聚合函数）的普通字段过滤条件，必须且只能优先声明在 `WHERE` 子句中。
    * 效率对比：写在 `HAVING` 中引擎必须把全表 107 行全部加载进内存、为 `NULL` 专门开辟哈希桶进行分组与聚合求均值，最后才通过 `HAVING` 过滤丢弃，产生完全不必要的聚合 CPU 开销；写在 `WHERE` 中则在 `GROUP BY` 分组前直接阻断 `NULL` 行，进入后续分组的数据量被提前压缩。
    * 经 `WHERE` 提前过滤后结果集从 8 行修正为 7 个实际业务部门。

### “极值之极值”类题目

* **平均工资最低的部门信息（四种架构）**
    * 方式一（四层嵌套）：最内层按部门求平均工资 → 第二层派生表求 `MIN` 得 `3475.56` → 第三层在 `employees` 中找出均薪等于该值的部门 ID（输出 50）→ 第四层到 `departments` 提取完整属性。
    * 方式二（三层，`<= ALL` 降维）：省去派生表求 `MIN` 的过程，`HAVING AVG(salary) <= ALL (SELECT AVG(salary) FROM employees GROUP BY department_id)`。
    * 方式三（三层，`ORDER BY` + `LIMIT 1`）：`HAVING AVG(salary) = (SELECT AVG(salary) AS avg_sal FROM employees GROUP BY department_id ORDER BY avg_sal ASC LIMIT 0, 1)`。
    * 方式三关键辨析：若有两个部门平均工资并列全公司最低，最内层 `LIMIT 0, 1` 只切出一条记录会不会丢数据？**不会** —— 因为最内层提取的并不是“部门 ID”而是“**最低平均工资的标量数值**”（如 `3475.56`），外层 `HAVING AVG(salary) = 3475.56` 在做分组比对时，所有平均工资等于该数值的部门都会被一网打尽。
    * 方式四（两层架构最优解）：`SELECT d.* FROM departments d JOIN (SELECT department_id, AVG(salary) AS avg_sal FROM employees GROUP BY department_id ORDER BY avg_sal ASC LIMIT 0, 1) t_dept_avg_sal ON d.department_id = t_dept_avg_sal.department_id;`
    * 方式四优势：层级从四层降至两层；内部构建出唯一的极值部门维度、外部通过 `JOIN` 提取属性；前三种方式均多次对 `employees` 表全表扫描与分组，方式四仅对员工表执行一次分组排序切片。
* **平均工资最低部门信息及该部门均薪（投影列嵌入相关子查询）**
    * 错误思路：`SELECT d.*, (SELECT AVG(salary) FROM employees WHERE department_id = 50) AS avg_sal FROM departments d ...` 硬编码常数 `50`。
    * 正确做法：`SELECT d.*, (SELECT AVG(salary) FROM employees e WHERE e.department_id = d.department_id) AS avg_sal FROM departments d JOIN (...) t_dept_avg_sal ON d.department_id = t_dept_avg_sal.department_id;`
    * 为什么 `SELECT` 投影列能引用 `FROM` 中定义的表别名 `d`：执行引擎内部 `FROM` 最先被解析并加载到内存上下文，执行到 `SELECT` 投影阶段时表别名 `d` 已完全确立并对当前作用域全局可见。
    * > **易错点**：严禁在代码中硬编码已知结果 —— 我们之所以在写查询正是因为不知道哪个部门均薪最低，把 `50` 写死则一旦数据变动最低部门迁移，该 SQL 将输出荒谬的错误数据。
* **平均工资最高的工种信息（对称四解法）**
    * 方式一（四层）：最内层算出各工种最高均薪 `24000.00`，外层定位到 `'AD_PRES'`（公司总裁），从 `jobs` 表查出岗位全量属性。
    * 方式二（三层 `>= ALL`）：`HAVING AVG(salary) >= ALL (SELECT AVG(salary) FROM employees GROUP BY job_id)`。
    * 方式三（三层 `ORDER BY` + `LIMIT 1`）：`HAVING AVG(salary) = (SELECT AVG(salary) AS avg_sal FROM employees GROUP BY job_id ORDER BY avg_sal DESC LIMIT 0, 1)`。
    * 方式四（两层 JOIN）：`SELECT j.* FROM jobs j JOIN (SELECT job_id, AVG(salary) AS avg_sal FROM employees GROUP BY job_id ORDER BY avg_sal DESC LIMIT 0, 1) t_job_avg_sal ON j.job_id = t_job_avg_sal.job_id;`
* **各部门最高工资中最低部门的最低工资**
    * 数值模拟建立直觉：部门 A 最高 `8000` 最低 `3000`、部门 B 最高 `9000` 最低 `4000`、部门 C 最高 `10000` 最低 `5000`；各部最高工资集合 `{8000, 9000, 10000}` → 其中最低为 `8000` → 对应部门 A → 该部门最低工资为 `3000`。
    * 方式一（四层）：`SELECT MIN(salary) FROM employees WHERE department_id = (SELECT department_id FROM employees GROUP BY department_id HAVING MAX(salary) = (SELECT MIN(max_sal) FROM (SELECT MAX(salary) AS max_sal FROM employees GROUP BY department_id) t_dept_max_sal));`
    * 运行结果探秘：最终输出的最低工资依然是 `4400.00`，与算出的最高工资相同；执行 `SELECT * FROM employees WHERE department_id = 10;` 发现属于 10 号部门的员工有且仅有 1 人（Jennifer Whalen，工号 200，工资 4400），她的工资既是该部门最高也是最低，数据完全真实可信。
    * 方式二（`<= ALL` 降维）：`SELECT MIN(salary) FROM employees WHERE department_id = (SELECT department_id FROM employees GROUP BY department_id HAVING MAX(salary) <= ALL (SELECT MAX(salary) FROM employees GROUP BY department_id));`
    * 方式三（`ORDER BY` + `LIMIT 1`）：把 `MIN(max_sal)` 换成 `(SELECT MAX(salary) AS max_sal FROM employees GROUP BY department_id ORDER BY max_sal ASC LIMIT 0, 1)`。
    * 方式四（两层 JOIN）：`SELECT MIN(e.salary) FROM employees e JOIN (SELECT department_id, MAX(salary) AS max_sal FROM employees GROUP BY department_id ORDER BY max_sal ASC LIMIT 0, 1) t_dept_max_sal ON e.department_id = t_dept_max_sal.department_id;`
    * > **易错点**：代码写得越多、嵌套层级越深绝不代表技术段位越高；相反它往往意味着执行计划极其复杂、中间临时表物化繁重、系统吞吐能力低下。
* **平均工资最高部门的管理者信息（五层到三层）**
    * 原始五层嵌套（直觉流）：最外层 `FROM employees WHERE employee_id = (...)`，内层依次为查询该最高均薪部门的 `manager_id` → 根据最高均薪数值反查部门 ID → 从派生表中取出均薪的 `MAX` 标量 → 按部门求均薪。
    * 五层书写风险：现场书写时哪怕少匹配一个右括号、或在中间层遗漏一个别名都会引发一系列报错，带来极大心理认知负荷。
    * 优化写法（扁平化等值 JOIN）：`SELECT mgr.* FROM employees mgr JOIN departments d ON mgr.employee_id = d.manager_id JOIN (SELECT department_id, AVG(salary) AS avg_sal FROM employees GROUP BY department_id ORDER BY avg_sal DESC LIMIT 0, 1) t_max_dept ON d.department_id = t_max_dept.department_id;`
    * 执行引擎仅需一次索引查找即可定位大总裁 Steven King。

### 存在性排除类题目

* **不包含特定工种的部门号**
    * 方式一（`NOT IN` 集合排除）：`SELECT department_id FROM departments WHERE department_id NOT IN (SELECT DISTINCT department_id FROM employees WHERE job_id = 'ST_CLERK' AND department_id IS NOT NULL);` `'ST_CLERK'` 工种集中在 50 号部门，全公司 27 个部门排除 50 号后返回 26 条记录。
    * 方式二（`NOT EXISTS` 相关子查询，推荐）：`SELECT d.department_id FROM departments d WHERE NOT EXISTS (SELECT * FROM employees e WHERE e.department_id = d.department_id AND e.job_id = 'ST_CLERK');` 外层部门表逐行驱动，内层探测到该部门存在任何一名 `'ST_CLERK'` 立即短路抛弃该部门，反之全部扫描未发现则予以保留。
* **没有管理者的大老板**
    * `SELECT emp.last_name FROM employees emp WHERE NOT EXISTS (SELECT * FROM employees mgr WHERE mgr.employee_id = emp.manager_id);`
    * 普通员工的 `manager_id` 能在内部表中找到对应管理者记录，`NOT EXISTS` 判定为假；唯独 Steven King 的 `manager_id` 为 `NULL`、内层匹配永为假、`NOT EXISTS` 判定为真，精准输出 `'King'`。
* **指定管理者的直属下属**
    * 方式一（`IN`）：`SELECT employee_id, last_name, hire_date, salary FROM employees WHERE manager_id IN (SELECT employee_id FROM employees WHERE last_name = 'De Haan');`
    * 方式二（`EXISTS`）：`SELECT e.employee_id, e.last_name, e.hire_date, e.salary FROM employees e WHERE EXISTS (SELECT * FROM employees mgr WHERE mgr.employee_id = e.manager_id AND mgr.last_name = 'De Haan');`
* **所有管理者的详细信息（IN 与 EXISTS 互换）**
    * 方式一（`IN`）：`SELECT * FROM employees WHERE employee_id IN (SELECT DISTINCT manager_id FROM employees WHERE manager_id IS NOT NULL);`
    * 方式二（`EXISTS`）：`SELECT * FROM employees e1 WHERE EXISTS (SELECT * FROM employees e2 WHERE e2.manager_id = e1.employee_id);`

### 跨表阈值统计类题目

* **部门人数超过 5 人的部门名称**
    * 外层主表应扫描 `departments` 维度表（查询的是部门名称），内层把外部部门的 `d.department_id` 送入员工表计算员工总数。
    * `SELECT d.department_name FROM departments d WHERE 5 < (SELECT COUNT(*) FROM employees e WHERE e.department_id = d.department_id);`
* **下属部门数超过 2 的国家编号**
    * 表结构关联：国家信息存储在 `locations`（地址位置表）中，字段为 `country_id` 与 `location_id`；部门信息存储在 `departments` 表中，通过 `location_id` 与地理位置建立关联。
    * `SELECT l.country_id FROM locations l WHERE 2 < (SELECT COUNT(*) FROM departments d WHERE d.location_id = l.location_id);`
    * 执行后仅有编号为 `'US'`（美国）的国家在数据库中配置了 2 个以上的业务部门。
* **高于本部门均薪的员工**
    * `SELECT e1.employee_id, e1.last_name, e1.salary FROM employees e1 WHERE e1.salary > (SELECT AVG(e2.salary) FROM employees e2 WHERE e2.department_id = e1.department_id);` 外部每行将 `e1.department_id` 注入内层，计算该部门的动态均薪。

### 三条黄金准则

* **准则一：按复杂度定编写方向**
    * 低复杂度（1~2 层标量或集合匹配）直接**从外往里写（自顶向下）**，先铺设主查询骨架，在 `WHERE` 中用子查询作为参数输入，开发心流顺畅。
    * 高复杂度（3 层以上多级聚合与极值运算）坚决**从里往外写（自底向上）**，先把最核心的未知变量（如最低均薪、最高均薪）在最底层独立查出并在客户端执行验证，确认结果集无误后再逐层包裹上层逻辑。
* **准则二：按相关性定生命周期**
    * 对于不相关子查询，内层逻辑完全独立，既可自底向上也可自顶向下。
    * 对于相关子查询，内查询的 `WHERE` 条件中直接使用了外层表的别名（如 `e2.department_id = e1.department_id`）；语法解析上**必须先在外层声明主表及其别名（`FROM employees e1`），内层才有资格引用该别名**，因此相关子查询天然必须采用“从外往里”的构建方式。
* **准则三：工程选型与性能谱系**
    * 多表连接（JOIN） > 子查询：能用多表等值连接或派生表 Join 解决的优先使用 Join，便于优化器利用索引和生成最优执行路径。
    * `EXISTS` > `IN`：多表存在性探测中优先使用 `EXISTS`，充分发挥短路求值优势，避免大集合排序去重开销。
    * 规避聚合函数嵌套：牢记 MySQL 组函数不可嵌套的底层红线，善用 `FROM` 派生表别名或 `<= ALL` / `LIMIT 1` 技巧实现降维。
    * 性能度量工具链预告：慢查询日志（Slow Query Log）与日志分析工具 `mysqldumpslow`；执行耗时剖析工具 `SHOW PROFILE`（监控一条 SQL 在 CPU、内存、临时表创建等各生命周期阶段的微秒级开销）；执行计划解构指令 `EXPLAIN`（查看查询类型 `select_type`、关联类型 `type` 从 `ALL` 到 `ref`/`eq_ref`、命中索引与实际扫描行数 `rows`）。
