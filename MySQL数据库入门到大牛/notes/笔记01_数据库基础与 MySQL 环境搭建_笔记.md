## 1. 数据持久化动因与普通文件存储的边界

> **一句话主旨**：从内存易失性与普通磁盘文件的三大局限出发，说明引入数据库是数据规模、检索性能与关系表达能力共同决定的工程必然。

* **持久化（Persistence）**
    * > 定义：将内存中的即时数据保存到可掉电式的存储设备（如磁盘、固态硬盘）中，以供系统在未来随时读取和使用的技术过程。
    * 计算机冯·诺依曼架构中 CPU 直接交互的介质是随机存取存储器（RAM，即内存），内存依靠电路高低电平表征二进制 `0` 与 `1`。
    * 内存读写速度达纳秒级响应，但属于易失性介质（Volatile Memory）：断电、操作系统崩溃或应用进程被终止时电压归零，其中保存的二进制状态瞬间全部丢失。
    * 持久化的落点是可掉电式存储设备，即磁盘与固态硬盘等非易失性物理介质。
    * 客户端应用把认证凭证与会话数据写入手机本地存储芯片后，杀进程重开可自动登录，切断 Wi-Fi 与蜂窝网络仍可查阅本地历史聊天记录与好友列表。
    * > 来源: P02
* **普通磁盘文件存储的三大工程局限**
    * 检索时序断崖式衰减：一亿条结构化记录顺序写入文本文件后，按某一字段查找只能从文件头部逐字节全量顺序扫描（Sequential Scan），属 $O(n)$ 时间复杂度的物理 I/O 操作，高并发下瞬间造成 I/O 队列阻塞与线程雪崩。
    * 专业数据库通过引入 B+Tree 等树状索引结构，可将上亿条记录的检索收敛至 3~4 次磁盘 I/O 即可完成。
    * 数据规模超出通用组件处理极限：数千万条轨迹记录导出为 Excel 文件后，桌面办公软件无法直接双击打开，进程因内存溢出与解析器崩溃直接闪退，只能改用底层 I/O 流程序按块切片读取。
    * 数据类型与复杂关系表达能力匮乏：业务实体属性涵盖定长整型、浮点型、短字符串、高精度日期时间戳、大文本（CLOB）与二进制字节流（BLOB），且实体之间存在参照引用；普通文件系统只能存储非结构化的连续字符流。
    * 普通文件系统无法原生提供字段约束校验、外键引用保护、多表关联计算与脏数据自检能力。
    * 单张数据表承载几千万条甚至上亿条记录在关系型数据库中是常见的工程场景。
    * > **结论**：数据库在横向数据容量的并发承载与快速检索上具有数量级优势，在纵向多维数据类型的精细化表达与关联约束管理上也全面优于普通文件系统。
    * > 来源: P02
* **数据库的横向承载与纵向表达能力**
    * 横向：面向海量结构化记录的并发挂载与高通量读取，索引结构把检索成本从全表扫描降为有限次磁盘 I/O。
    * 纵向：以列定义约束数据类型与取值规范，以内键/外键维系实体间的参照引用，并提供脏数据自检能力。
    * > 来源: P02

## 2. DB、DBMS 与 SQL 的概念边界

> **一句话主旨**：厘清物理数据集合、管理软件与通信语言三者的定义边界与依赖关系，并给出表/行/列结构与 ORM 映射。

* **数据库（Database，DB）**
    * > 定义：长期保存在计算机存储设备上的、有组织的、可共享的大量数据的集合。
    * 从操作系统物理视角看，DB 的本质是一个特定的文件系统子集。
    * Windows 环境下 MySQL 8.0 默认安装路径 `C:\ProgramData\MySQL\MySQL Server 8.0\Data\` 中，每一个子文件夹物理上对应一个独立的逻辑数据库（如系统自动生成的目录或用户创建的 `atguigudb` 文件夹）。
    * 文件夹内部以 `.ibd` 为后缀的文件是特定数据表在磁盘上真实存储索引与行记录的表空间文件（Tablespace File）。
    * 日常沟通中所说的"删库"，物理本质就是通过操作系统指令或数据库服务把这些底层物理数据文件从磁盘介质上彻底抹除。
    * > 来源: P02, P05
* **数据库管理系统（Database Management System，DBMS）**
    * > 定义：位于用户操作系统与数据库底层文件之间的一套大型系统管理软件，用于科学地组织、存储、检索和维护数据库中的数据，并提供安全控制与并发调度。
    * 日常所说的"安装 MySQL 数据库"在严格技术定义上是概念借代：实际下载、安装并运行的是作为系统软件的 MySQL 数据库管理系统。
    * `C:\ProgramData\MySQL\MySQL Server 8.0\Data\` 下每一个子文件夹物理上对应一个独立的逻辑数据库，其中 `.ibd` 文件是特定数据表的表空间文件。
    * 用户或应用程序永远无法绕过 DBMS 直接通过底层二进制指针安全地并发修改 `.ibd` 数据文件。
    * 并发控制、事务保障、权限校验与缓存分配全部由 DBMS 统一调度。
    * > 来源: P02, P11
* **结构化查询语言（Structured Query Language，SQL）**
    * > 定义：一种专门用于与关系型数据库管理系统（RDBMS）进行标准化通信的特定领域编程语言（DSL）。
    * 行业发音习惯作为完整专有名词整体发音，通常读作 `/ˈsiːkwəl/`（类似英文单词 "sequel"），亦可读作 `/ɛs-kjuː-ɛl/`；技术评审中应避免逐字机械拼读 "S-Q-L"。
    * 属高级声明式（Declarative）语言：开发者只用关键字表达"需要获取什么样的数据结果"（What to do），不需要用算法控制指针描述"如何一步一步查找数据"（How to do）。
    * 具体查找路径、是否使用索引、如何执行多表连接等逻辑，均由 DBMS 内部的优化器（Optimizer）与执行器（Executor）自主计算并落实。
    * > 来源: P02
* **DB、DBMS 与 SQL 的层次依赖**
    * 依赖方向单向：用户与开发者代码经 SQL 指令作用于 DBMS，DBMS 通过磁盘文件 I/O 读写落在 DB 上；三者不可逆序。
    * 磁盘文件是静态数据资产，DBMS 是解析与调度工具，SQL 是通信语言，三者分别对应载体、软件与协议三个层级。
    * > 来源: P02, P11
* **数据表、记录与字段**
    * 横向的一行数据称为一条**记录**（Record）或一个**行**（Row），代表某个具体物理实体在系统中的一次完整实例快照。
    * 纵向的一列称为一个**字段**（Field）或**列**（Column），规定该维度下的数据特征、取值类型与存储规范。
    * 列代表实体所拥有的某种特定属性（如工号、姓名、性别、入职日期），行代表一个真实存在的实体对象实例（如工号为 `T001` 的女教师，隶属于计算机系）。
    * 多条行记录在逻辑上组装成一张完整的数据表（Table），相关业务数据表在逻辑与物理上汇聚为数据库（Database）。
    * 物理落盘示例：`C:\ProgramData\MySQL\MySQL Server 8.0\Data\atguigudb\` 下的 `employees.ibd`、`departments.ibd`、`countries.ibd`，各自对应一张数据表的独立表空间文件。
    * 同一个数据库内部每张数据表都必须拥有全局唯一的表名；同名表会导致 SQL 解析引擎无法判定 `SELECT ... FROM table_name` 的目标对象。
    * 中大型系统一个工程涉及数百张表是极为常见的常态；微服务架构下按业务限界上下文拆分为用户、订单、库存、物流等独立模块，每个模块对应独立业务数据库，但每个库内部仍遵循"库含多张互不重名的表"这一原则。
    * > 易错点：不能通过文本编辑器或十六进制工具强行双击打开或非法修改 `.ibd` 文件，否则将直接破坏数据页校验和并引发数据库崩溃；这些文件依赖 DBMS 服务内部的页驱动引擎进行解析与并发加锁控制。
    * > 来源: P04, P05
* **对象关系映射（Object-Relational Mapping，ORM）**
    * > 定义：架起面向对象编程（OOP）与关系型数据库（RDBMS）之间语意鸿沟的映射机制。
    * 表（Table）与类（Class）映射：数据库中的 `student` 表对应代码中定义的 `Student` 类。
    * 行（Row/Record）与对象（Object/Entity）映射：表中一行代表某位具体学生（学号为 1001 的张三），内存中对应 `new Student(1001, "张三")` 对象实例。
    * 列（Column）与字段（Field）映射：表中每一个列定义映射为类中声明的一个成员变量，严格术语为**字段**（Field）。
    * > 易错点：类中成员变量口语常被称作"属性"，但英文中变量声明称 `field`，而 `attribute` 在语言规范中有专门所指（如 Java 字节码 `.class` 文件结构中的 Code 属性、Exceptions 属性等元数据规范），与存放业务数据的 `Field` 完全不是同一层级的概念；专业语境下应对齐为**字段**（Field）。
    * > 来源: P05
* **端到端数据流转的四层链路（电商加购与结算场景）**
    * 客户端层（Client Tier）：终端用户在手机 App 或 PC 浏览器点击"查看我的购物车"，前端把点击事件封装为标准 HTTP/HTTPS 网络请求报文，附用户会话 Token、接口路径与参数，跨公网发往后端。
    * 业务应用服务层（Application / Web Tier）：服务端反解 Token 并鉴权提取真实用户 ID，业务逻辑层判断需提取该用户全部未结算加购明细。
    * 数据访问组件（持久层框架）把业务诉求组装为标准 SQL：`SELECT item_id, item_name, price, quantity FROM shopping_cart WHERE user_id = 10086 AND is_deleted = 0;`。
    * 应用服务器通过数据库连接池（Connection Pool），基于 TCP/IP 与预设端口（MySQL 默认 `3306`）把 SQL 文本推到数据库服务器。
    * 数据库管理系统层（DBMS Tier）四步流水线：连接与鉴权（验证账号、密码、主机访问权限）→ 语法与语义解析（检查拼写、校验表与字段存在）→ 优化与执行（评估执行路径代价，决策命中 `idx_userid` 索引）→ 数据返回（封装结果报文沿 TCP 连接逆向回传）。
    * 视图组装与呈现：应用服务器反序列化结果集为内存业务对象（DTO/VO），经优惠券计算、价格分摊等业务计算后打包为 JSON 响应体，移动端解析并渲染商品清单。
    * > 来源: P02

## 3. 主流 DBMS 格局与选型

> **一句话主旨**：依托 DB-Engines 流行度体系梳理头部产品梯队与技术特长，并给出 Oracle 与 MySQL 之间的企业级选型判据。

* **DB-Engines 流行度评估体系**
    * 全球被持续追踪的 DBMS 产品常年保持在 300 至 400 款之间。
    * 榜单并非单纯统计商业销售额，而是综合搜索引擎查询频次（Google Trends）、专业问答社区活跃度（Stack Overflow、DBA Stack Exchange）、职位招聘需求数量、专业社交网络提及频次与学术文献引用等多维度数据。
    * 头部结构：Oracle 与 MySQL 构成断层式第一梯队且得分常年紧咬；Microsoft SQL Server 长期稳居第三但与第二名存在明显积分鸿沟；开源的 PostgreSQL 稳居第四且近年来增长势头强劲。
    * 排名前十的数据库中，带有 `Relational`（关系型）标识的占据半壁江山以上；承载核心业务数据的基石依然是关系型数据库。
    * > 来源: P03
* **Oracle Database**
    * 全球第一款成功实现商业化的关系型数据库管理系统。
    * 技术优势集中在极端复杂事务处理、高可用集群架构（如 Oracle RAC）、超大规模数据吞吐与军工金融级安全防护机制。
    * 面向大型与超大型企业核心业务，广泛垄断于跨国巨头、国有大型银行、电信运营商、电网电力、证券结算与航空航天等对可用性要求严苛的领域。
    * 工程代价：高昂的软件 License 授权费用、专属硬件绑定成本与昂贵的专业维保服务开销。
    * > 来源: P03
* **Microsoft SQL Server**
    * 与微软自有 Windows Server 操作系统、.NET / C# 开发框架、Visual Studio 工具链及 Azure 云平台形成极高原生协同效应。
    * 内置 SQL Server Management Studio（SSMS）提供可视化管理、监控与分析体验。
    * 选型边界：在以微软技术体系为主导的企业架构中性价比高、运维摩擦低；若底层基础设施以 Linux 发行版与开源 Java/Go 技术栈为主，通常不是首选。
    * > 来源: P03
* **PostgreSQL（pgSQL）**
    * 最初由美国加州大学伯克利分校计算机系主导开发。
    * 在所有开源数据库中被公认为对 ANSI SQL 标准支持最为完整与严苛。
    * 原生支持数组、JSON、空间几何地理数据（PostGIS 插件）等高级数据类型，属对象-关系型支持。
    * 拥有媲美商业级数据库的高并发控制与复杂查询优化器表现，在地理信息系统（GIS）、复杂报表分析与科研场景中被广泛采纳。
    * > 来源: P03
* **SQLite**
    * 无服务器（Serverless）轻量级嵌入式关系型数据库，无需独立安装与网络配置，完整数据库实体仅是宿主磁盘上的一个扁平二进制文件。
    * 通过轻量级 C 语言库直接嵌入宿主应用程序的进程内存空间运行，读写操作直接转换为本地文件 I/O，随程序启动而加载、随程序退出而销毁。
    * 核心场景：Android 与 iOS 设备上的微信、QQ 等客户端 App 本地数据存储、浏览器内置存储引擎、物联网微控制器与开发测试环境。
    * > 来源: P03
* **边缘与历史系统**
    * MariaDB：MySQL 被 Oracle 收购后，其创始人担忧闭源风险而创建的代码完全开源分支；保持在榜单前 20 位，与 MySQL 保持高度语法与驱动兼容，部分 Linux 发行版将其作为默认包。
    * Sybase：早期主流商业 RDBMS 之一，后被 SAP 公司收购，技术遗产包括数据库建模工具 PowerDesigner；生产数据库市场已基本淡出主流。
    * Informix：取名自 Information 与 Unix 的结合，早期专注 Unix/Linux 平台高性能数据处理；市场份额高度边缘化，仅存在于部分传统老旧系统维保中。
    * IBM DB2：历史上广泛运行于大型机（Mainframe）与 Unix 小型机（如 IBM AIX），在 2005 年之前的全球与国内金融核心账务系统中占比极高；随分布式架构发展与"去 IOE"浪潮推进，国内依赖度逐年降低，新增研发项目已极为罕见。
    * > 来源: P03
* **MySQL 关键历史里程碑**
    * 1995 年：瑞典 MySQL AB 公司成立并开源发布，采用 ISAM / MyISAM 存储引擎（早期读性能高，但缺乏事务支持）。
    * 2007 年：Oracle 斥资 85 亿美元收购 BEA Systems，其旗下 JRockit JVM 强化了 Oracle 在企业级中间件与 Java 底层运行时的技术控制权。
    * 2008 年：Sun Microsystems 以 11 亿美元收购 MySQL AB 公司。
    * 2009 年：Oracle 以 74 亿美元整体收购 Sun Microsystems，将 Java 官方版权与规范制定权以及 MySQL 同时纳入产品线。
    * 2013 年：甲骨文公司正式超越 IBM，成为仅次于微软的全球第二大独立软件公司。
    * 5.5 版本：InnoDB 正式取代 MyISAM 成为官方默认存储引擎，带来原生事务与行级锁。
    * 5.7 版本：2015 年发布，工业级经典稳定版，完善 JSON 与优化器。
    * 8.0 版本：2016 年跳跃式发布，全面内核重构，引入窗口函数、原子 DDL、倒序索引。
    * > **易错点**：MySQL 早期默认采用 ISAM 引擎，后升级为 MyISAM，其设计重点在于快速的静态读操作，但存在两大硬伤——不支持事务（Transaction）与仅支持表级锁定（Table-level Locking），写并发激增时整张表被全局锁死，并发性能断崖式下跌。
    * > 来源: P03, P11
* **MySQL 的存储引擎变革与 5.7/8.0 技术断层**
    * 支持 ACID 事务与行级锁（Row-level Locking）的 InnoDB 由第三方芬兰软件公司开发，Oracle 先行收购 InnoDB，进而间接促成了对 MySQL 的全面整合。
    * 历史分水岭：自 MySQL 5.5 版本起，官方正式将默认存储引擎由 MyISAM 切换为 InnoDB，MySQL 由此具备与顶级商用数据库竞争企业级核心交易系统的底层基石。
    * MySQL 5.7 于 2015 年推出，因出色的稳定性与成熟性能表现，成为企业生产环境中生命周期最长、部署基数最庞大的版本之一。
    * MySQL 8.0 于 2016 年首度亮相并跳过 6.x 与 7.x：不仅引入窗口函数、公用表表达式（CTE）、降序索引等应用层新特性，更在底层彻底废除基于 `.frm` 文件的旧元数据体系。
    * 8.0 全面引入基于 InnoDB 存储的事务型数据字典（Data Dictionary），并实现全链路原子 DDL（Atomic DDL）操作。
    * > 来源: P03, P11
* **版本形态分轨：社区版、商业版、集群版与衍生组件**
    * 社区版（MySQL Community Server）：遵循开源通用公共许可证（GNU General Public License，GPL），完全免费供个人与企业下载使用，社区支持活跃。
    * 商业版（MySQL Commercial Edition）：商业闭源授权，按年收取服务与支持费，额外提供商业级监控套件（MySQL Enterprise Monitor）、数据脱敏、高级审计与专业官方技术支持。
    * 集群版（MySQL Cluster / Cluster CGE）：分为开源集群与高级商业集群版（Carrier Grade Edition），采用 NDB 存储引擎，支持多节点内存级分布式架构，保障 99.999% 高可用。
    * 衍生生态组件：MySQL Workbench（跨平台图形化建模与管理工具）、MySQL Router（轻量级透明路由中间件，负责高可用故障转移与读写负载）、MySQL Shell（支持 SQL/JS/Py 的集成式脚本运维工具）、Connectors（面向 JDBC、ODBC、.NET 等语言的官方驱动库）。
    * MySQL 自 6.0 版本起在商业运营模式上确立双轨制；对绝大多数互联网企业，社区版提供的核心引擎能力已足以应对生产环境严苛要求。
    * > 来源: P03, P07

## 4. 关系型与非关系型数据库的模型定位

> **一句话主旨**：以数据组织模型为分界，给出 RDBMS 的架构优势与性能天花板，并逐一梳理五类 NoSQL 的物理机理与混合持久化协同。

* **关系型数据库管理系统（Relational Database Management System，RDBMS）**
    * > 定义：建立在关系模型基础之上，借助于集合代数等数学概念和方法来处理数据库中数据的系统软件；将现实世界中复杂的业务对象及其联系，统一抽象并归结为简单的二维表格（Table）。
    * 数据模型层次：列（Column / 字段 Field）代表实体的某种特定属性并具有预设强数据类型；行（Row / 记录 Record）代表一个真实存在的实体对象实例；数据表（Table）是同类实体记录的二维集合；数据库（Database）是相关业务数据的逻辑与物理集合。
    * 核心工程优势一，复杂关联查询能力（DQL）：不同实体按规范化设计拆分到独立表（如教师信息入 `teachers` 表、部门组织架构入 `departments` 表），通过外键与公共字段可用 `INNER JOIN`、`LEFT JOIN`、`RIGHT JOIN`、自连接以及多层子查询完成复杂统计与筛选。
    * 核心工程优势二，严密的数据完整性约束机制：原生提供主键约束（Primary Key）、唯一约束（Unique）、外键约束（Foreign Key）、非空约束（Not Null）与检查约束（Check），从存储引擎级别严把数据入口关，杜绝无父记录的孤儿数据、重复记录与非法空值。
    * 核心工程优势三，强一致性的 ACID 事务（Transaction）保障：通过行级锁、表级锁、MVCC 以及 Undo/Redo 日志，确保操作系统突发掉电或硬件故障时核心交易数据依然能够无损崩溃恢复。
    * > 来源: P04
* **传统 RDBMS 的四大性能天花板**
    * 磁盘 I/O 成为绝对吞吐瓶颈：B+Tree 索引与数据页均以物理磁盘为最终持久化载体，面对秒杀大促、突发热点等数十万 QPS 的高并发读写冲击，磁盘寻道与 I/O 调度队列迅速达到物理极限，导致连接池枯竭与服务雪崩。
    * 强行多表 Join 的性能衰减：数据量膨胀到千万级乃至上亿级别后，跨越数张大表的笛卡尔积运算与哈希连接，内存占用与 CPU 代价呈指数级攀升。
    * 固定模式（Schema）制约敏捷迭代：表结构要求严格固定的字段定义，生产环境执行 `ALTER TABLE` 添加字段的操作极其沉重，高并发运行期间极易引发全局锁表（Table Lock）。
    * 水平扩展（Scale-out）极其复杂：传统 RDBMS 天生更适合垂直硬件升级（Scale-up，增加 CPU、内存与磁盘阵列），推行跨节点分布式分库分表时，原生跨表 Join 与跨库分布式事务异常繁琐且开销巨大。
    * > 来源: P04
* **非关系型数据库（NoSQL）的定位与语义演进**
    * > 结论：非关系型数据库并非要全盘否定关系型数据库，而是特定场景下的"有所舍，才能有所得"；主动舍弃复杂多表关联查询、严格预定义表结构（Schema）与全局 ACID 事务开销，换取轻装上阵后的极致读写吞吐、低延迟响应与极低成本的水平弹性扩展能力。
    * 早期反叛阶段（We Have No SQL）：面对传统 RDBMS 庞大沉重的单机锁竞争与性能瓶颈，部分开发者试图探索完全远离、彻底不用 SQL 的极简存储机制。
    * 重构反思阶段（No, SQL!）：随着业务复杂度上升，纯粹的键值查找无法支撑复杂业务统计与多维条件过滤，业界重新认识到声明式 SQL 在数据表达上的威力。
    * 现代工业共识（Not Only SQL）：不再是关系型数据库的敌对替代品，而是作为强力补充与延伸，二者在现代大型系统架构中共同构成"混合持久化"基础设施。
    * > 来源: P04
* **键值存储（Key-Value Store）**
    * 代表系统 Redis、Memcached；设计哲学高度类比编程语言中的 `Map<Key, Value>` 结构。
    * Value 支持 String、Hash、List、Set、ZSet 等结构，例如 `user:10086:token` 映射 JWT 字符串、`rank:top_sales` 映射有序集合。
    * 底层原理：对唯一 Key 执行高效哈希算法直接定位物理内存槽位，查找时间复杂度达到近乎理想的 $O(1)$ 常量级。
    * 技术优势：数据主要常驻高速内存（RAM），单机读写吞吐可轻松突破十万级 QPS，网络与处理延迟控制在微秒级。
    * 典型场景：高频热点数据缓存、高并发秒杀库存计数器、用户 Token 状态维护、分布式全局锁以及排行榜（ZSet）。
    * > 来源: P04, P11
* **文档型存储（Document Store）**
    * 代表系统 MongoDB、CouchDB；可看作键值存储的进阶形态，Value 是内部层次丰富、自描述的半结构化文档（通常以 JSON 或二进制 BSON 格式组织）。
    * 无模式（Schema-Free）特性：同一集合（Collection，相当于 RDBMS 的表）内部各文档无需保持完全一致的字段结构，文档 A 可拥有 5 个字段、文档 B 可拥有 8 个字段且包含内嵌数组或嵌套子对象。
    * 技术优势：面向对象编程中的复杂领域对象（Domain Object）无需拆解即可直接落盘存储，省去拆分多表与设计中间关联表的映射开销（消除对象-关系阻抗失配）。
    * 典型场景：内容管理系统（CMS）、富文本博客系统、电商商品多变属性存储、移动 App 设备日志收集及敏捷原型开发。
    * > 来源: P04, P11
* **搜索引擎型（Search Engine）**
    * 代表系统 Elasticsearch、Solr；关系型数据库单列索引在关键字模糊搜索与多条件复杂筛选下捉襟见肘，执行 `LIKE '%keyword%'` 更会直接导致全表扫描崩溃。
    * 底层核心基石为倒排索引（Inverted Index）：传统关系型表采用"正向索引"（根据文档 ID 寻找其内部包含的词汇），倒排索引在数据写入时通过分词器把文本切分为独立词项（Term），构建从"词项"直接映射到"包含该词项的所有文档 ID 列表"的全局倒排表。
    * 技术优势：在海量百亿级非结构化文本中毫秒级完成关键词布尔检索、相关度评分排序与多维度动态聚合统计。
    * 典型场景：大型互联网平台顶部搜索框（京东、淘宝商品检索）、百度全网搜索、海量日志聚合分析平台（ELK 架构）。
    * > 来源: P04, P11
* **列式存储（Columnar / Wide-Column Store）**
    * 代表系统 Apache HBase、Cassandra、ClickHouse。
    * 行式存储物理排布（Row-Oriented，如传统 MySQL）：整行字段连续存放，`[1, 845, 2, 3, 1]`、`[2, 851, 5, 2, 2]` 顺序排列，读取某条记录的任意字段必须把包含所有字段的完整行数据页读入内存。
    * 列式存储物理排布（Column-Oriented）：同一列的全部行数据紧凑连续存放在专属存储块中，字段 A 的全部值与字段 B 的全部值各自成块。
    * 行式存储在局部字段查询下产生 I/O 浪费：假设一张表设计了 20 个业务字段而统计 SQL 仅需其中 2 个，存储引擎仍被迫把包含整行其余 18 个冗余字段的数据块全量读入内存缓冲池。
    * 列式存储的低 I/O 破局：统计查询只需读取目标两列对应的物理块，完全绕过其余无关列的物理扇区，大幅压缩磁盘 I/O 读写总量。
    * 同一列数据具有完全相同的类型与极高的数据重复度，列式存储能够获得极高的压缩算法压缩比，极适配海量冷热数据存储。
    * 短板：单行记录即时事务读写效率较低；典型场景为大数据分布式存储（Hadoop HDFS + HBase）、实时数仓 OLAP 分析、物联网传感器海量时序监控指标汇总。
    * > 来源: P04, P11
* **图形数据库（Graph Database）**
    * 代表系统 Neo4j、Nebula Graph、InfoGrid。
    * 关系型在网状图中的困境：表示多级关系必须通过多层中间关系表执行多级递归自连接（Self-Join），查询链路达 4 层或 5 层以上时多表笛卡尔积膨胀会直接导致查询耗时从毫秒级恶化至数分钟乃至内存崩溃。
    * 图论原生建模：以节点（Node）代表实体、以边（Edge / Relationship）代表实体间双向或单向关联，并在节点与边上绑定丰富的属性键值。
    * 技术优势：通过图遍历指针算法，以指数级高于关系型数据库的效率完成深度好友推荐、反欺诈风控拓扑识别与知识图谱（Knowledge Graph）路径推演。
    * 典型场景：社交人脉推荐、金融反洗钱风控穿透、企业知识图谱推理。
    * > 来源: P04, P11
* **六类数据库的选型权衡矩阵**

| 数据库类别 | 典型工业级代表 | 核心物理模型 | 最大核心优势 | 核心妥协点 / 短板 | 最适工程场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 关系型 (RDBMS) | MySQL, Oracle, PostgreSQL | 强 Schema 二维表格（行式存储为主） | 严苛的数据约束、复杂 Join 表达、强一致性 ACID 事务 | 海量高并发 I/O 承载瓶颈、水平分片扩展代价高 | 核心交易系统、资金账户账本、主干业务状态流转 |
| 键值型 (Key-Value) | Redis, Memcached | 内存 Hash 映射 | 纳秒/微秒级极速响应、十万级 QPS、数据结构丰富 | 内存硬件成本高昂、不支持复杂范围与关联查询 | 高速热点缓存、分布式锁、会话共享、秒杀限流 |
| 文档型 (Document) | MongoDB, CouchDB | BSON / JSON 半结构化文档 | 动态 Schema 无约束自由扩展、面向对象原生映射 | 跨文档事务代价高、弱外键关联保护 | 动态内容发布（CMS）、日志收集、异构字段配置 |
| 搜索引擎 (Search) | Elasticsearch, Solr | 倒排索引表 | 高通量模糊搜索、多维过滤打分、海量文本聚合 | 写入存在近实时（NRT）延迟、硬件内存占用大 | 全文检索框、商品复合筛选、集群全链路日志分析 |
| 列族/列式 (Columnar) | Apache HBase, Cassandra | 按列聚合物理存储 | 极大降低批量扫描磁盘 I/O、极高压缩比、水平弹性强 | 单行记录即时事务读写效率较低 | 海量离线日志、大数据数仓分析、时序监控轨迹 |
| 图形型 (Graph) | Neo4j, Nebula Graph | 节点-边网状拓扑图 | 秒级深度路径遍历、图论复杂拓扑关联计算 | 不适合高通量常规单表点查与大规模批量计算 | 社交人脉推荐、金融反洗钱风控、企业知识图谱 |

* **高并发电商系统的多引擎协同分工**
    * MySQL 担当核心真相源（Source of Truth）：承担订单生成、账户扣款、支付结算等业务操作，依赖严谨事务机制与行级锁确保高并发扣减库存绝不超卖。
    * Redis 构筑最外层防护前哨：拦截 90% 以上针对热点商品详情、用户登录鉴权的只读流量，把海量并发拦截在内存层，保护 MySQL 主库免受穿透式流量冲击。
    * Elasticsearch 承接复杂检索诉求：通过 Canal / Kafka 异步消息队列解析 Binlog 增量变更并同步更新索引，提供按品牌、价格区间、发货地、好评率的多维度条件筛选与毫秒级复合排序。
    * Apache HBase / HDFS 负责海量历史归档与数据挖掘：把产生超过半年的历史订单明细与设备埋点数据异步迁移归档至列式分布式存储，支撑运营报表离线分析与机器学习推荐。
    * > 来源: P04

## 5. ER 模型与表记录的四种关联形态

> **一句话主旨**：从 ER 三要素落到记录基数，逐条给出 1:1、1:N、M:N、自引用四种关联的定义、实现规则、性能机理与边界。

* **实体关系模型（Entity-Relationship Model，ER 模型）三要素**
    * 实体（Entity）与实体集（Entity Set）：实体是现实世界中可以相互区别的客观事物或抽象概念（"张三"是一个具体实体，"李四"也是一个具体实体）；具有相同特征的同类实体构成实体集，在关系数据库中落地为一张数据表。
    * 属性（Attribute）：实体所具有的某种特性，如学生实体具备"学号""姓名""性别""入学年龄"；在数据表设计中落地为表结构的列（字段）。
    * 联系（Relationship）与联系集（Relationship Set）：实体与实体之间的内在关联，如学生与课程之间的"选课"联系、员工与部门之间的"隶属"联系；在物理表结构中通过主外键、关联字段或中间关系表落地。
    * 物理映射链：实体集 → 数据表，属性 → 列字段，联系 → 键关联。
    * 关联设计的核心焦点是**表与表之间的记录对应基数**：表 A 中的一行记录究竟可对应表 B 中的多少条记录，反之亦然。
    * > 来源: P05, P11
* **一对一关联（1:1，One-to-One）与垂直分表**
    * > 定义：表 A 中的一条记录只能且必须对应表 B 中的至多一条记录；反之表 B 中的一条记录也只能对应表 A 中的至多一条记录。
    * 实现规则：从表主键兼任外键直接绑定主表主键，或外键列加 `UNIQUE` 唯一约束；不需要中间表。
    * 核心驱动物理链条：实体全部 30 甚至 50 个字段塞在同一张表会使单条记录体积极其庞大 → InnoDB 以"页"（默认单页 16KB）为最小物理 I/O 单位换入内存而非按需单字节读取 → 90% 以上日常查询只需学号、姓名、手机号等少数常用字段，未拆分时每次全行检索都被迫把超长冗余字段一并加载进缓冲池（Buffer Pool）→ 有限内存被冷数据占据，内存可容纳的有效记录行数急剧减少，产生大量内存换页与直接磁盘 I/O。
    * > **结论**：一对一拆表的核心驱动力是冷热数据分离与 I/O 吞吐优化；高频访问字段归集在基础表（热表），低频长字段独立剥离在扩展表/档案表（冷表）。
    * 典型场景：学生基础信息表与档案信息表、用户账号表与实名认证资料表。
    * > 提示：拆表不是多此一举，而是数据库性能调优中极为关键的高级手段；代价只是多一次 JOIN 联表查询。
    * > 来源: P05, P11
* **一对多关联（1:N，One-to-Many）与主从表机制**
    * > 定义：表 A 中的一条记录可以对应表 B 中的多条记录；反过来表 B 中的一条记录只能对应表 A 中的一条记录。
    * 层级机制：独立存在的一方作为**主表（Parent Table）**持有实体主键，容纳多条依赖记录的一方作为**从表（Child Table）**，在从表中开设外键列指向主表主键。
    * 以部门表与员工表为例：部门表每行以 `department_id` 作为唯一主键；员工表除自身主键 `employee_id` 外必须冗余开设外键字段 `department_id`，部门 10 对应多名员工时这些员工记录的 `department_id` 列填写的都是 10。
    * > 提示：一对多关联中**外键永远设立在"多"的一端（即从表一侧）**；严禁在"一"的一端用逗号拼接字符串去记录多个子实体的 ID，这种做法严重违背关系数据库的第一范式，会导致索引失效、更新异常及查询性能彻底崩溃。
    * 典型场景：客户表与订单表、商品分类表与商品详情表、部门表与员工表、行政省份表与城市表、学生表与课程成绩表。
    * > 来源: P05
* **多对多关联（M:N，Many-to-Many）与中间连接表**
    * > 定义：表 A 中的一条记录可以对应表 B 中的多条记录；同时表 B 中的一条记录也可以反向对应表 A 中的多条记录。
    * 铁律：两张独立的业务表之间绝对无法直接通过在各自表内增设单一外键字段来表达多对多关系。
    * 死局推演：在学生表里加一个课程 ID，一个学生选多门课时填多行会导致学生基础信息被迫重复多次、主键瞬间失效；逗号拼接则结构被彻底破坏；反之在课程表里加学生 ID 同样陷入死局。
    * 破局手段：必须引入第三张表——连接表（Junction Table / Join Table，亦常称为中间表）。
    * 结构解构：中间表通过 `student_id` 引用学生表建立 1:N 关系，通过 `course_id` 引用课程表建立 1:N 关系，两条 1:N 链路在中间表交汇对齐，宏观上完整实现 M:N 关联；两端独立实体表充当主表，中间连接表充当两者的共同从表。
    * 中间表结构：自身主键 `id`、外键 `student_id`、外键 `course_id`，以及选课关联附属属性 `score`；主表向中间表分别引出 1:N 外键，中间表以联合主键防重。
    * 电商落地形态为"订单主表"与"商品表"之间的"订单明细表（Order Detail Table）"：每一行既记录属于哪个订单号，也记录属于哪件商品 ID，并同时沉淀特定于该次交易的购买数量与实时快照单价。
    * 典型场景：学生与课程、电商商品与销售订单、RBAC 权限控制系统中的系统用户与安全角色（一位在校人员既是"在读研究生"也是某门课程的"助教"，"助教"角色模板底下可分配多名研究生）。
    * > 来源: P05
* **自我引用关联（Self-Referencing）与单表自关联**
    * > 定义：表中的某个外键字段，引用的目标并不是外部的其他表，而是直接指向该表自身的主键。
    * 适用对象：在单张物理表内表达具有层级嵌套、树状分支或图状网络特征的同类数据；不需要中间表。
    * 经典案例为企业组织架构的员工与上级主管模型：员工表含 `employee_id`（主键）、`employee_name`、`manager_id`（主管编号，外键，引用自身主键 `employee_id`）。
    * 记录示例：董事长 `employee_id=101`、`manager_id=NULL`（最高领导，无主管）；技术总监 102 的主管为 101；架构组长 103 的主管为 102；研发工程师 A（104）与研发工程师 B（105）的主管均为 103。
    * 主管本质也是公司雇员，拿着 `manager_id = 103` 回溯其详细身份信息时，检索目标依然是在这张员工表内部寻找 `employee_id = 103` 的那条记录。
    * 其他落地：电商系统的多级无限递归分类树（"服装 → 男装 → 运动外套"，每一级的 `parent_id` 均指向上一级类目的分类 ID）、城市行政区划编码树。
    * > 来源: P05, P11
* **四种表关联关系的选型对照**

| 关联关系形态 | 简写形式 | 依赖主键/外键设计规则 | 是否需要中间表 | 核心业务考量与典型应用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 一对一 | 1:1 | 从表主键兼任外键，直接绑定主表主键；或外键列加 `UNIQUE` 唯一约束 | 否 | 冷热分离与性能调优：把低频长字段从高频核心表中垂直剥离（学生基础表与档案表、用户账号表与实名认证资料表） |
| 一对多 | 1:N | 外键强制设立在"多"的一端（从表），指向"一"的一端（主表）主键 | 否 | 从属与层级归属：实体间存在明确从属关系（部门与员工、客户与订单、分类与商品、省份与城市） |
| 多对多 | M:N | 必须由两张主表分别向中间连接表引出 1:N 外键，中间表联合主键防重 | 是 | 交叉聚合与多对多交互（学生选课、订单商品采购、RBAC 用户角色权限模型） |
| 自我引用 | 1:N (自引) | 本表中的特定外键列直接指向本表自身的主键列 | 否 | 树状层级与递归关系（员工与直属主管、无限极商品类目树、行政区划层级） |

* **关联模型与数据结构映射**
    * 一对一对应数据结构中的单元素映射；一对多对应树形层级结构；多对多对应网状图模型；自引用对应单表内的层级递归。
    * 现实世界中的所有商业逻辑，在底层最终都会被降维收敛为上述四种关系之一。
    * > 来源: P05, P11

## 6. MySQL 的物理存在维度与彻底卸载

> **一句话主旨**：定位 MySQL 在 Windows 上的四个物理维度，讲清程序与数据解耦的设计必然性，并给出标准卸载五步法与残留治理规程。

* **MySQL 在 Windows 上的四大物理存在维度**
    * 软件安装目录（DBMS 二进制程序本体）：如 `D:\develop_tools\MySQL\MySQL Server 8.0\`，其下 `bin\` 包含 `mysql.exe`、`mysqld.exe` 等核心可执行命令，`lib\`、`include\`、`share\` 存放依赖库与元数据文件。
    * 数据与配置目录（物理表空间与引擎配置，默认隐藏）：如 `C:\ProgramData\MySQL\MySQL Server 8.0\`，其下 `data\` 存放各数据库物理文件夹（如 `atguigudb/*.ibd`），`my.ini` 是定义端口、字符集、缓冲池等参数的核心配置文件。
    * 操作系统服务进程（Windows Services）：服务名常见为 `MySQL80`（5.7 版本通常为 `MySQL` 或 `MySQL57`），后台守护进程 `mysqld.exe` 对外监听 3306 端口提供网络通信服务。
    * 系统环境变量（System Environment Variables）：`Path` 中追加 `D:\develop_tools\MySQL\MySQL Server 8.0\bin`，实现全局任意终端路径下直接调用 `mysql` 等指令。
    * **综合运维视角下为五处位置**：安装主程序目录、物理数据存储目录、配置文件路径、系统服务注册项、系统环境变量。
    * > **结论**：MySQL 由程序文件、数据与配置文件、系统服务项及全局环境变量四大模块协同构成，单纯删除任何单一模块都属于不完整卸载。
    * > **易错点**：`ProgramData` 在 Windows 下默认属于"隐藏项目"，若在 C 盘根目录下未看到该文件夹，需在文件资源管理器的"查看"菜单栏勾选"隐藏的项目"复选框方可显形。
    * > 来源: P06, P11
* **配置文件 `my.ini` 的关键参数**
    * 位于 `C:\ProgramData\MySQL\MySQL Server 8.0\my.ini`，实例启动时强依赖该核心参数配置文件。
    * 定义内容包括监听端口（默认 3306）、默认存储引擎、默认字符集（8.0 默认 `utf8mb4`）、最大并发连接数、InnoDB 缓冲池尺寸（`innodb_buffer_pool_size`）等系统级参数。
    * 该文件不在软件安装主目录下，而在具有隐藏属性的系统数据目录中；Linux 系统下对应为 `my.cnf`。
    * > 易错点：安装路径或数据路径全路径中绝对严禁包含任何中文字符、特殊符号以及全角/半角空格；底层 `mysqld` 进程加载动态链接库与表空间元数据时，部分底层 C++ 库对 UTF-8 与 Windows 本地 ANSI 路径转码存在缺陷，一旦路径出现中文或空格，会导致服务初始化直接崩溃或后续数据读写异常中断。
    * > 易错点：安装路径含中文时往往初次安装配置看似成功，但第二天电脑重启、服务重新拉起时会莫名其妙死锁或报错退出。
    * > 来源: P06, P07, P10
* **程序与数据物理解耦原理**
    * 通过 Windows 控制面板卸载 MySQL 后，`C:\ProgramData\MySQL` 下的 `data` 文件夹与 `my.ini` 依旧完好留在磁盘上，这不是卸载程序的 Bug，而是专业级企业软件刻意实施的"程序与数据物理解耦"设计。
    * > **结论**：数据库系统严格遵循"程序可卸载，数据不可轻弃"的原则；安装包提供的卸载工具只负责清理 DBMS 程序本体，绝对不会主动销毁用户的数据文件。
    * 设计动因：原地升级场景下若卸载程序默认把包含数十 TB 业务数据的 `data` 目录一并格式化抹除，企业生产数据将在几秒钟内化为乌有。
    * 若目标是彻底重置、重新安装一套干净的全新环境，必须由人工在确认备份或确认无用后**手动删除**该数据目录。
    * > 来源: P06
* **标准卸载五步法操作规程**
    * 第 1 步，停止 Windows 系统后台服务：`Win + R` 输入 `services.msc` 打开服务管理控制台，找到 `MySQL80`（或相应服务名）右键【停止】；或在管理员终端执行 `net stop MySQL80`，确认服务状态由"正在运行"切换为停止状态。
    * 第 2 步，卸载程序本体：打开控制面板进入【程序和功能】，找到发布者为 `Oracle Corporation` 的相关项（通常包括 `MySQL Server 8.0` 与 `MySQL Installer - Community`），右键依次【卸载】；或再次运行 `mysql-installer-community.msi` 进入维护模式点击【Remove】勾选所有组件执行卸载；第三方管家软件的软件管理模块底层实质依然是调用系统的 `msiexec` 卸载引擎。
    * 第 3 步，手动清理数据与配置残留：开启隐藏文件可见模式，定位 `C:\ProgramData\MySQL`，彻底删除整个 `MySQL` 文件夹（或其中 `MySQL Server 8.0` 子目录），抹除遗留物理表数据（`data/`）与旧配置文件（`my.ini`）。
    * 第 4 步，清理环境变量与注册表项：在【此电脑】->【属性】->【高级系统设置】->【环境变量】->【系统变量】中双击 `Path`，删除指向 MySQL `bin` 目录的条目并连续点击【确定】保存；随后用 `regedit` 删除残留注册表项，或在管理员终端执行 `sc delete MySQL80` 强制删除残留服务条目。
    * 第 5 步，重启操作系统：Windows 内核句柄管理机制下，某些被卸载的动态链接库、未完全注销的驱动服务项及注册表变更往往需要系统重新加载内核时才能真正释放句柄占用。
    * > **易错点**：移除程序本体必须通过受控的卸载渠道，严禁直接在文件资源管理器中选中安装目录执行右键"删除"；直接删文件夹会导致操作系统的安装数据库、COM 组件注册信息以及控制面板索引陷入死链状态。
    * > **易错点**：暴力删除文件夹仅删除了上层磁盘文件，Windows 安装数据库中的 MSI 组件 GUID、COM 注册项依然留存在操作系统底层，新安装包试图在相同 GUID 位置注册时将直接抛出严重逻辑冲突。
    * > **易错点**：卸载程序中 `ControlSet001`、`ControlSet002` 是 Windows 硬件与驱动配置的历史备份集，具体机器上的命名编号可能略有差异，凡存在 `Services\MySQL` 或相关事件日志注册的项均应排查清理。
    * 需排查的注册表路径：`HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\Services\Eventlog\Application\MySQL`、`HKEY_LOCAL_MACHINE\SYSTEM\ControlSet002\Services\Eventlog\Application\MySQL`（若存在）、`HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Eventlog\Application\MySQL`、`HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\MySQL`（或对应具体服务名如 `MySQL57`）。
    * > **注意**：任何生产、测试或已有重要业务数据的环境中执行数据目录删除前，必须确认已对核心数据库完成全量逻辑导出备份（如使用 `mysqldump` 导出的 SQL 脚本）；一旦物理删除该目录，无冷备份情况下数据将永久丢失。
    * > 来源: P06, P11
* **私自移动服务目录的灾难性后果**
    * MySQL 服务在安装注册阶段，其守护进程的物理路径、`my.ini` 的绝对指向、数据目录挂载点都已硬编码写入 Windows 注册表和系统服务清单。
    * 私自用 `Ctrl + X` 剪切粘贴整个 MySQL 服务端根目录到另一个盘符后，底层注册表键值并不会跟随动态更新，会导致 `net start` 找不到可执行映像、数据文件脱机损坏，最终只能彻底重装。
    * 规范：软件安装在哪个路径就让它固定在哪个路径，严禁暴力挪动。
    * > 来源: P10

## 7. 8.0 与 5.7 双版本安装与配置

> **一句话主旨**：给出官方版本谱系与安装包格式选型依据，逐步还原 8.0 定制安装的关键参数，并落实双实例四维隔离与精准路由。

* **官方安装包的获取途径与格式选型**
    * 官网导航链路：`https://www.mysql.com` -> 顶部导航栏【Downloads】-> 页面中部展示商业付费的 Enterprise Edition 与 Cluster CGE，滑动至底部进入【MySQL Community (GPL) Downloads】-> 选择核心引擎【MySQL Community Server】-> 操作系统选择【Microsoft Windows】。
    * 企业级研发规范：获取基础软件基础设施严禁通过第三方下载站或未知网盘拉取，以杜绝恶意脚本篡改与捆绑后门，官方途径是第一且唯一首选。
    * ZIP 压缩版（免安装版 / Archive）：下载后仅包含解压后的二进制文件包，不含自动化配置向导，需开发者手动编写 `my.ini`、手动执行 `mysqld --initialize` 初始化数据目录、手动执行 `mysqld --install` 注册系统服务。
    * MSI 安装包版（MySQL Installer）：具备 Windows Installer 图形化引导机制，把软件文件拷贝、目录结构权限分配、多实例服务注册、初始化向导与密码安全策略集成为一条流水线。
    * 采用 MSI 格式（Windows x86, 32-bit, MSI Installer）时，安装器本身会自动根据宿主操作系统位数下载与装配 64 位的 MySQL Server 引擎。
    * 在线安装包（Web Community）体积仅十几兆至二十几兆，仅含轻量级引导壳，安装过程中必须联网动态回源拉取组件，网络波动极易导致超时中断。
    * 完整离线安装包（`mysql-installer-community-*.msi`）体积 400MB 左右，内嵌所有常用组件完整二进制文件，断网环境下亦可独立流畅完成安装。
    * 下载非最新版本历史镜像（如 `8.0.26` 或 `5.7.34`）需在 Community Server 页面点击【Archives】（档案库）标签页；官方页面弹出 Oracle 账号登录界面时，直接点击 `No thanks, just start my download.` 链接可免登录触发本地下载。
    * 8.0 系列内部存在 `8.0.25`、`8.0.26`、`8.0.27` 等按季度迭代的维护小版本，彼此主要包含稳定性补丁与底层微调，核心特性与 SQL 语法完全向下兼容，选择任意主流子版本均可保证教学与开发体验的一致性。
    * > 来源: P07
* **8.0 定制安装的安装模式与组件选择**
    * 向导首页安装模式包含 Developer Default（开发者默认）、Server only（仅服务端）、Client only（仅客户端）、Full（全量组件）与 Custom（自定义）。
    * 必须选择【Custom】自定义模式：默认模式会自动强行捆绑 Visual Studio 插件、ODBC 驱动、Python 适配库等大量无关周边，耗费磁盘且增加系统复杂度；自定义模式可精准挑选核心数据库服务并解锁对物理磁盘安装路径的精细化控制。
    * 组件挑选路径：依次展开 `MySQL Servers` -> `MySQL Server` -> `MySQL Server 8.0`，选中对应的 64 位版本，点击向右箭头迁移至右侧"待安装产品列表"。
    * 物理路径规划通过右下方【Advanced Options】（高级选项）超链接进入：Install Directory（软件安装目录）推荐规划在独立开发工具分区如 `D:\develop_tools\MySQL\MySQL Server 8.0`；Data Directory（数据存储目录）推荐保持系统规划如 `C:\ProgramData\MySQL\MySQL Server 8.0`。
    * > 来源: P07
* **服务器类型与内存拓扑配置**
    * Configuration Type 下拉框含三类预设模式。
    * Development Computer（开发机模式，默认推荐）：专为本地个人开发设计，MySQL 仅分配最低限度的系统物理内存（如 InnoDB 缓冲池等参数设定较小），确保其他 IDE 与本地应用流畅运行。
    * Server Computer（通用服务器模式）：适用于宿主机同时部署 Web 应用服务与数据库服务的场景，占用中等物理内存。
    * Dedicated Computer（专属数据库服务器模式）：系统假定该机器专门用于运行 MySQL，服务进程将竭尽全力榨取操作系统的全部内存与 CPU 资源。
    * Networking 环节需勾选 Open Firewall port for network access 并启用 TCP/IP 协议；默认端口（Port）为 `3306`，X Protocol 端口为 `33060`。
    * > 来源: P07
* **认证算法选型与密码安全策略**
    * Use Strong Password Encryption for Authentication (RECOMMENDED)：基于 `caching_sha2_password` 插件（SHA-256 双重哈希散列与服务端高速缓存），具备极高抗碰撞能力与通信安全性能，是 8.0 官方强力推荐的现代安全机制。
    * Use Legacy Authentication Method (Retain MySQL 5.x Compatibility)：基于早期 `mysql_native_password` 插件（SHA-1 阶段散列逻辑的弱散列算法），向下兼容 5.x。
    * MySQL 官方为彻底阻断基于网络抓包的彩虹表碰撞攻击，在 8.0 中淘汰了历时十多年的旧插件 `mysql_native_password`。
    * > **易错点**：选中强加密算法后，较老版本的第三方客户端（如旧版 SQLyog 或 Navicat 11）连接 MySQL 8.0 时可能因未集成 `caching_sha2_password` 动态握手模块而弹出 `Client does not support authentication protocol requested by server` 或 `2058 Plugin caching_sha2_password could not be loaded`；可通过升级客户端驱动或在数据库中临时修改用户插件解决。
    * 5.7 版本没有 8.0 的双重加密选择界面，其默认原生采用传统的 `mysql_native_password`。
    * > 来源: P07, P10
* **账户凭据与 Windows 服务注册**
    * 在 Accounts and Roles 界面输入 `MySQL Root Password` 与确认密码；密码长度较短时系统可能提示密码强度为 `Weak`，本地学习环境可直接忽略该告警；此界面暂不额外添加普通开发者账号。
    * 在 Windows Service 界面勾选 `Configure MySQL Server as a Windows Service`，Windows Service Name 默认设定为 `MySQL80`，并勾选 `Start the MySQL Server at System Startup`（随系统开机自动启动）。
    * 应用配置（Apply Configuration）点击【Execute】后，向导按序执行：依据所选参数生成 `my.ini` 配置文件 → 调用 `mysqld.exe --initialize` 创建底层系统库（`mysql`、`sys` 等）的表空间 → 把 `MySQL80` 注册至 Windows 系统服务并触发首次启动 → 应用密码安全规则与 root 权限表。
    * 安装完成后 `D:\develop_tools\MySQL\MySQL Server 8.0\` 下被二进制程序填满，`C:\ProgramData\MySQL\MySQL Server 8.0\` 下自动生成 `data/` 目录与 `my.ini`。
    * > 来源: P07
* **全局环境变量 Path 的配置与验证**
    * 未配置 Path 时在新开启的 cmd 窗口中输入 `mysql --version` 会抛出 `'mysql' 不是内部或外部命令，也不是可运行的程序或批处理文件。`，因为操作系统的执行寻址机制不知道 `mysql.exe` 存放位置。
    * 配置链路：【打开系统高级属性】->【环境变量】->【系统变量中的 Path】->【新建条目】，追加 `D:\develop_tools\MySQL\MySQL Server 8.0\bin`，连续点击三次【确定】关闭所有属性对话框。
    * 验证命令：`mysql --version`（注意 version 选项不要末尾误加分号）与 `mysql -u root -pabc123`。
    * > **易错点**：环境变量修改保存后，原先已经开启的终端窗口不会自动加载新的系统环境；必须彻底关闭旧的 cmd 或 PowerShell 窗口，重新开启一个全新的命令行终端。
    * > 来源: P07
* **单机多实例共存的四维资源隔离**

| 资源竞争维度 | MySQL 8.0 实例分配 | MySQL 5.7 实例分配 | 核心防冲突原则 |
| :--- | :--- | :--- | :--- |
| 网络监听端口 (Port) | `3306` | `13306` | 端口范围 0~65535，两个进程严禁监听同一个网络端口 |
| Windows 服务标识 (Service Name) | `MySQL80` | `MySQL57` | 系统注册表服务项严禁同名 |
| 软件安装目录 (Binary Dir) | `D:\...\MySQL Server 8.0` | `D:\...\MySQL Server 5.7` | 避免不同版本的可执行程序与 DLL 互相覆盖 |
| 数据持久化目录 (Data Dir) | `C:\...\MySQL Server 8.0` | `C:\...\MySQL Server 5.7` | 表空间物理文件格式不同，严禁共用同一个 data 目录 |

* **5.7 实例的追加部署流程**
    * 运行 `mysql-installer-community-5.7.34.msi`，向导提示 `Welcome Back!`（欢迎回来）并可能检测到 8.0 的次级升级包；在 Upgrade 提示窗口直接点击【Cancel】取消升级，随后在产品列表界面点击右侧【Add...】进入组件追加模式。
    * 展开 `MySQL Servers` -> `MySQL Server` -> `MySQL Server 5.7`，勾选 64 位版本添加至右侧，点击【Advanced Options】把路径重新指定为专属隔离目录：安装目录 `D:\develop_tools\MySQL\MySQL Server 5.7\`，数据目录 `C:\ProgramData\MySQL\MySQL Server 5.7\`。
    * Networking 页向导会立即检测到端口 3306 已被 `MySQL80` 占用并在界面标红告警（`Port 3306 is already in use`），必须手动把端口改为未被占用的号码，例如前置加 1 修改为 `13306`。
    * 在服务注册页把默认服务名改为 `MySQL57`，同样保持随开机自启动勾选，并为 5.7 的 root 账户设定密码。
    * 配置完成后在 `services.msc` 中可同时观察到两个并驾齐驱的运行中服务：`MySQL80`（对应 8.0 内核，监听 3306）与 `MySQL57`（对应 5.7 内核，监听 13306），启动类型均为自动。
    * > **易错点**：系统 Path 变量中只能保留一个主版本的 bin 目录路径（保持指向 8.0）；操作系统扫描 Path 是从上至下单向匹配，一旦排在前面的路径命中了 `mysql.exe`，后续路径就会被彻底短路截断，盲目配置两个只会导致难以捉摸的版本错乱。
    * > 来源: P07
* **精准会话路由与版本核验**
    * 8.0 的客户端命令工具完全向下兼容 5.7 协议，可直接使用 8.0 的 `mysql` 客户端通过显式传递主机名与端口参数切换连接到不同数据库实例。
    * 登录 8.0 实例：`mysql -h localhost -P 3306 -u root -pabc123`，进入后执行 `SELECT VERSION();` 输出确认指向 `8.0.26`，执行 `QUIT;` 退出会话。
    * 登录 5.7 实例：`mysql -h localhost -P 13306 -u root -pabc123`，执行 `SELECT VERSION();` 返回 `5.7.34`。
    * > 来源: P07, P08
* **安装故障的两大阵营与根因诊断**
    * 初次安装故障（底层依赖缺失）：缺少 .NET Framework 或版本过低需补丁升级至 4.5+；缺少 Visual C++ Redistributable 需补齐 MSVCR/VCRUNTIME；缺少特定系统 DLL 文件需启用 Windows Update 修复补丁。
    * 二次重装故障（历史脏残留污染）：暴力删除目录导致注册表损坏需依赖控制面板规范卸载；`ProgramData/MySQL` 数据未清空导致密码冲突死锁需手动拔除；Windows 服务名或端口冲突需注册表强力注销并重启释放句柄。
    * 缺少 .NET Framework 平台支持的现象与机理：双击 MSI 安装包后向导界面尚未渲染便直接崩溃退出，或弹出系统弹窗提示需要安装更高版本的 `.NET Framework`；MySQL Installer 客户端向导采用 .NET 技术栈构建，强依赖宿主环境的 CLR 运行时环境（通常要求 .NET Framework 4.5.2 及以上版本）。
    * 缺少 Visual C++ Redistributable 的现象与机理：安装进度推进至服务端二进制解包或执行服务初始化阶段时，系统抛出缺少 `MSVCR120.dll`、`VCRUNTIME140.dll` 或提示 `Visual Studio Redistributable is required`；MySQL Server 底层核心引擎全部基于 C/C++ 语言编写，编译时依赖特定版本的 Visual C++ 动态链接库。
    * 离线内网环境可预先下载并安装 `Visual C++ Redistributable 2015-2022`（包含 x86 与 x64 运行时）。
    * 使用二次封装精简系统（如某些深度优化的 Ghost 系统）时常遭遇各种未知动态库链接缺失，需打开 Windows【设置】->【更新和安全】执行系统全量累积更新，或利用系统维护工具的"系统运行库/丢失 DLL 一键修复"功能补全缺失的底层 API 组件。
    * > **结论**：系统性排查必须先区分机器是否具备 MySQL"前科"，针对性实施运行库补齐或残留剥除；曾安装过 MySQL、卸载后重新部署遭遇报错的场景，99% 的问题均由"卸载不干净"引发。
    * > 来源: P08
* **数据目录未清空引发的密码冲突死锁**
    * 控制面板卸载为保护用户数据安全默认绝对不删除 `C:\ProgramData\MySQL` 目录；直接重新安装时向导检测到 `data/` 目录中已存在旧系统表，会假定用户是在执行实例恢复。
    * 配置向导最后一步校验 root 权限时，安装程序要求输入的 root 密码必须与当初创建该 `data` 目录时的旧密码完全吻合。
    * 若开发者已遗忘旧密码并在此处输入新密码，执行配置时会在"Starting Service"或"Applying Security Settings"环节直接标红报错（`Configuration failed`），陷入彻底死锁。
    * > **结论**：若意图重新部署全新环境，在运行新安装包前必须手动打开 `C:\ProgramData\MySQL` 并将其彻底清空。
    * 若提示服务名已被占用，通过 `regedit` 清除 `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\` 下对应的服务项键值，并在清理完毕后重启计算机，使操作系统内核彻底注销无主的驱动句柄与端口绑定。
    * > 来源: P08

## 8. 字符集与比较规则

> **一句话主旨**：从 5.7 中文写入报错切入字符集继承链与变量探测，给出 `my.ini` 持久化改造、历史库表升级与 8.0 默认行为对比。

* **字符集（Character Set）与 `latin1` 的历史渊源**
    * > 定义：`latin1` 字符集（即 ISO-8859-1）是单字节编码，最多只能表示 256 个字符，主要涵盖西欧语言中使用的拉丁字母。
    * `latin1` 在底层根本没有收录中文字符的编码位，任何汉字在映射为 `latin1` 字节流时都会因无法解析而直接报错。
    * 历史根源：MySQL 最初由瑞典的 MySQL AB 公司自主研发，瑞典地处欧洲，本地语言环境使用西欧拉丁字符集，因此早期版本开发者自然把单字节的 `latin1` 设为系统缺省字符集。
    * 中文要被正确识别与存储必须使用多字节通用字符集编码，最典型的是 `utf8`；`utf8` 是一套变长编码标准，完整收录中文字符并囊括日文、韩文、欧洲各国文字以及美式英语对应的二进制编码映射。
    * 在 5.7 实例中插入 `insert into employees values(1003, '杰瑞');` 会立即报错：`ERROR 1366 (HY000): Incorrect string value: '\xBD\xDC\xC8\xF0' for column 'name' at row 1`，且第 3 条数据根本没有写进表中。
    * 纯英文字符数据（`Tom`、`shk-start`）在 5.7 与 8.0 中的插入与查询行为完全一致，只有写入中文汉字时两个版本的行为立即产生分歧。
    * > 来源: P09
* **字符集的继承链**
    * 建表时没有显式指定字符集，表就会默认继承库的字符集；建库时没有显式指定字符集，库就会默认继承更上一层——数据库服务端的默认字符集。
    * 以 `show create table employees;` 验证，5.7 环境下建表定义末尾显示 `ENGINE=InnoDB DEFAULT CHARSET=latin1`。
    * 以 `show create database dbtest1;` 验证，返回 `CREATE DATABASE \`dbtest1\` /*!40100 DEFAULT CHARACTER SET latin1 */`。
    * 在 8.0 实例中执行 `show create table emp;` 可验证表的字符集默认就是 `utf8mb4`。
    * > 来源: P09
* **字符集与比较规则的系统变量探测**
    * `show variables like 'character%';` 用于查看服务器当前生效的字符集环境变量，`like 'character%'` 中的 `%` 是 SQL 通配符，表示匹配以 `character` 开头的任意一个到多个字符。
    * 5.7 默认安装环境回显：`character_set_client` 为 `utf8`、`character_set_connection` 为 `utf8`、`character_set_database` 为 `latin1`、`character_set_filesystem` 为 `binary`、`character_set_results` 为 `utf8`、`character_set_server` 为 `latin1`、`character_set_system` 为 `utf8`。
    * `character_set_client`（客户端输入编码）、`character_set_connection`（连接层转换编码）、`character_set_results`（服务端返回结果编码）构成一条完整的客户端与服务端字符流转换链条。
    * 核心矛盾：5.7 默认安装环境下 `character_set_server` 缺省就是 `latin1`，`character_set_database` 随之继承为 `latin1`。
    * 8.0 默认安装环境回显：`character_set_client`、`character_set_connection`、`character_set_database`、`character_set_results`、`character_set_server` 全部为 `utf8mb4`，仅 `character_set_system` 为 `utf8mb3`，且此环境完全未对 `my.ini` 做过任何字符集手工修改。
    * > 来源: P09
* **比较规则（Collation）**
    * > 定义：字符集解决的是"字符如何编码成二进制存储"的问题；比较规则（Collation）解决的是"两个字符谁大谁小、如何排序、是否区分大小写"的问题。
    * 每一种字符集都有若干套与之严格配套的比较规则。
    * `latin1` 对应的默认规则是瑞典语比较规则 `latin1_swedish_ci`，其中的 `ci` 代表 Case Insensitive（大小写不敏感）；`utf8` 对应的常用比较规则是 `utf8_general_ci`。
    * `show variables like 'collation%';` 在 5.7 默认环境回显：`collation_connection` 为 `utf8_general_ci`、`collation_database` 为 `latin1_swedish_ci`、`collation_server` 为 `latin1_swedish_ci`。
    * MySQL 8.0 默认比较规则为 `utf8mb4_0900_ai_ci`。
    * > 来源: P01, P09
* **`my.ini` 的关键参数持久化改造**
    * 在 `[mysql]` 标签（负责命令行客户端交互参数）正下方顶格添加 `default-character-set=utf8`。
    * 在 `[mysqld]` 标签（负责 mysqld 核心守护进程参数）正下方顶格添加 `character-set-server=utf8` 与 `collation-server=utf8_general_ci`。
    * 配置文件路径为 `C:\ProgramData\MySQL\MySQL Server 5.7\my.ini`，`C:\ProgramData` 是 Windows 系统隐藏文件夹，需勾选"隐藏的项目"才能看见。
    * > **易错点**：`[mysql]` 组下使用的是 `default-character-set`，而 `[mysqld]` 组下使用的是 `character-set-server`，两者键名写法不同，切勿混淆。
    * > **易错点**：参数必须顶格书写，等号两边不要留出多余空格。
    * 修改后参数并不会立即对正在运行的进程生效，必须重启 MySQL 服务，可通过服务管理面板对 `MySQL57` 右键"重新启动"。
    * 重启后 `character_set_database` 与 `character_set_server` 成功变更为 `utf8`，`collation_database` 与 `collation_server` 同步变为 `utf8_general_ci`。
    * 规范操作时序为：先停止服务 -> 修改并保存配置文件 -> 再启动服务；"先改文件后重启"在并发写入或刷盘场景下可能引发参数不同步。
    * > 来源: P09, P11
* **历史库表的字符集继承陷阱**
    * 全局字符集修正后继续向 `dbtest1` 的 `employees` 表补插中文依然再次弹出 `ERROR 1366 (HY000)`，`show create table employees;` 输出的建表语句末尾依旧印着 `DEFAULT CHARSET=latin1`。
    * > **结论**：`my.ini` 配置文件的修改只对服务重启之后"新创建"的数据库和表生效；对于在修改前就已经落盘的历史库和历史表，其物理结构上的字符集元数据已经被固化，绝不会因为底层配置文件的改动而自动升级。
    * 入门演练的干净解法是删除旧库并重建：`drop database dbtest1;` 与 `create database dbtest1;`；此后 `show create database dbtest1;` 回显 `DEFAULT CHARACTER SET utf8`，重新建表并写入中英文数据不再报错。
    * > 来源: P09
* **生产环境下历史库表的字符集在线平滑升级**
    * 修改现有数据库的默认字符集：`ALTER DATABASE dbtest1 CHARACTER SET utf8;`；该语句仅修正数据库元数据中的默认字符集属性，使未来在该库下新建表时默认继承 `utf8`，但不会自动刷写库中已存在的历史旧表。
    * 修改现有历史数据表的字符集与已有列编码：`ALTER TABLE employees CONVERT TO CHARACTER SET utf8;`。
    * > **易错点**：千万不要写成 `ALTER TABLE employees DEFAULT CHARACTER SET utf8;`；`DEFAULT CHARACTER SET` 仅仅改变表的默认属性，表内既有的 `varchar` 列依然停留在 `latin1`，中文写入依然报错。
    * > **结论**：必须使用 `CONVERT TO CHARACTER SET utf8`，它会连同底层所有已存在的字符类型字段及其历史存储数据一次性完成物理编码转换。
    * 生产环境中也可通过 `alter table ... convert to character set utf8;` 批量刷表；转换完成后向历史表 `employees` 写入汉字即可顺畅通过。
    * > 来源: P09, P11
* **5.7 与 8.0 的字符集默认行为对比**

| 核心指标项 | MySQL 5.7（及更早版本） | MySQL 8.0（现代化标准） |
| :--- | :--- | :--- |
| 默认底层字符集 | `latin1`（单字节编码） | `utf8mb4`（4 字节完整版） |
| 默认比较规则 | `latin1_swedish_ci` | `utf8mb4_0900_ai_ci` |
| 中文原生支持能力 | 报错（必须人工干预） | 原生天然支持 |
| 表情符号 (Emoji) | 不支持 | 完美原生存储 |
| 人工运维成本 | 必须手工修改 `my.ini` | 开箱即用，零配置 |

* **`utf8mb4` 与 `utf8mb3` 的字节宽度差异**
    * MySQL 早期所称的 `utf8` 在 8.0 内部被严格重命名为 `utf8mb3`，是一个"残血版"UTF-8 实现，最多只分配 3 个字节来存储一个字符。
    * `utf8mb3` 虽涵盖绝大多数日常中文汉字，但遇到 Emoji 表情符号、复杂罕见汉字或历史古籍符号（这些符号需要完整的 4 字节 UTF-8 编码）时会再次抛出插入异常。
    * MySQL 8.0 起官方把默认字符集统一升级为完全体的 `utf8mb4`（Most Bytes 4，即单个字符最多占用 4 个字节）。
    * 所有使用 5.7 版本的环境必须在初始化阶段完成 `my.ini` 字符集配置改造与服务重启；直接从 8.0 起步则无需再为字符集设置耗费精力。
    * > 来源: P09

## 9. 客户端连接参数、服务治理与图形化工具

> **一句话主旨**：给出命令行连接参数矩阵与密码安全红线，梳理服务启停的权限机理，并解决图形化工具连接 8.0 时的认证插件故障。

* **`mysql` 客户端连接参数矩阵**

| 参数缩写 | 参数全称 | 参数作用与数据规范 | 缺省默认值 |
| :--- | :--- | :--- | :--- |
| `-h` | `--host` | 目标数据库服务器的 IP 地址或网络主机域名（如 `127.0.0.1`、`192.168.1.100`） | `localhost` |
| `-P`（大写） | `--port` | 目标数据库实例所监听的 TCP 网络通信端口号（有效范围 0~65535） | `3306` |
| `-u` | `--user` | 用于通过身份认证的数据库账户名（如 `root`） | 操作系统当前登录用户名 |
| `-p`（小写） | `--password` | 用于身份鉴权的访问口令 | 空密码（无密码尝试） |

* **连接参数的使用规则与缺省补全机制**
    * 完整语法结构为 `mysql -h <主机IP> -P <端口号> -u <用户名> -p[密码]`。
    * 参数先后顺序在命令行解析器中并无硬性限制；习惯上按主机、端口、用户、密码的顺序编排，把密码选项固定放置于命令行末尾。
    * 极简命令 `mysql -u root -p` 能准确登录 8.0 实例，源于底层缺省补全机制：未声明 `-h` 时系统自动回退补齐为 `-h localhost`；未声明 `-P` 时自动回退补齐为 `-P 3306`；执行调用的 `mysql.exe` 二进制文件来自环境变量 Path 中最优先匹配的 8.0 bin 目录。
    * 需明确登入 5.7 兼容实例时必须通过打破缺省值进行精准路由：`mysql -h localhost -P 13306 -u root -p`。
    * 在 `-u` 与用户名之间、`-h` 与主机之间允许包含空格（如 `-u root` 与 `-uroot` 等价）。
    * 退出交互环境使用 `QUIT;` 或 `EXIT;`，终端打印 `Bye` 并退回操作系统标准命令行提示符。
    * > 来源: P08
* **密码录入的安全红线与格式陷阱**
    * 明文拼装密码（如 `mysql -u root -pabc123`）时终端必然抛出安全告警：`mysql: [Warning] Using a password on the command line interface can be insecure.`。
    * 明文风险：任何路过屏幕的人都能肉眼直视密码内容；操作系统的历史命令记录器（如 Bash 历史、PowerShell 日志）会把包含明文密码的完整命令持久化存入磁盘日志，极易引发安全合规事故。
    * > **易错点**：在 `-p` 选项上若试图写明文密码，中间绝对严禁包含任何空格；误敲为 `-p abc123` 时命令行解析器会把空格之后的 `abc123` 误解析为"目标连接的数据库名称"，同时认为当前未提供密码，导致认证彻底失败。
    * > **易错点**：受 SQL 语句以分号结尾的固有习惯影响，在命令行参数末尾随手敲分号（如 `-pabc123;`）会被当作密码的最后一个物理字符一并传递给认证引擎，直接导致密码错误拒绝登录。
    * 最佳安全实践为换行暗文交互录入：仅提供 `-p` 标记并直接敲击回车，在系统唤起的独立提示行中以无回显的暗文模式输入口令，密码不会被屏幕窥视或命令历史审计记录，且避免一切空格与特殊字符的转义干扰。
    * 成功连接后终端输出 `Welcome to the MySQL monitor. Commands end with ; or \g.`、`Your MySQL connection id is 12`、`Server version: 8.0.26 MySQL Community Server - GPL` 等信息。
    * > 来源: P08
* **客户端生态划分**
    * 操作系统原生命令行工具：在任何配妥环境变量的终端（cmd、PowerShell、Git Bash）中直接使用 `mysql.exe`，轻量高效，是开发排障的第一线武器。
    * MySQL 自带命令行客户端（MySQL Command Line Client）：安装时自动注册在开始菜单中，本质是预置了特定参数的快捷批处理方式，默认直接以本机 root 身份运行，启动后跳过参数录入环节直接等待输入密码。
    * 第三方专业图形化协同软件：Navicat、SQLyog、DataGrip、DBeaver 或 MySQL Workbench，提供结构树导航、代码高亮提示与数据网格编辑能力，底层依然严格封装网络连接参数。
    * > 来源: P08
* **服务启停的图形化与命令行控制**
    * 客户端与数据库服务端的连接本质是基于网络协议（如本地回环的 TCP/IP）进行的跨进程通信；客户端发起 TCP 3306 端口连接握手时，若目标服务处于"已停止"状态，操作系统直接 RST 拒绝并报错 `ERROR 2003 (HY000): Can't connect to MySQL server on 'localhost:3306' (10061)`。
    * 服务停止时客户端还可能抛出 `ERROR 2003 (HY000): Can't connect to MySQL server` 或 `Lost connection to MySQL server` 异常。
    * 图形化路径：`Win + R` 输入 `services.msc` 打开服务管理控制台，按键盘字母 `M` 快速索引至 `MySQL80` 或 `MySQL57`，右键可执行【启动】、【停止】、【重新启动】。
    * 启动类型（属性对话框）可定制为：自动（默认推荐，随系统引导开机自启，保障开发时开箱即用）；手动（开机不启动，仅在需要数据库开发时由人工主动唤醒，适合对开机速度有严苛要求的场景）。
    * 命令行语法为 `net start <服务名称>` 与 `net stop <服务名称>`。
    * > **易错点**：在普通用户权限的命令提示符中执行 `net stop MySQL80` 会立即返回 `发生系统错误 5。拒绝访问。`；Windows 后台系统服务属于操作系统底层的全局特权资源，普通用户级权限只具备用户级操作权限，操作系统安全机制（UAC）直接截断对内核级服务的操控请求。
    * 正确流程为在开始菜单或搜索栏键入 `cmd`，在【命令提示符】上点击右键选择【以管理员身份运行】，再执行 `net stop MySQL80` 与 `net start MySQL80`。
    * 服务重新拉起后底层 3306 网络端口恢复监听，客户端方可重新建立会话连接；无论本地客户端网络性能多么优异，服务端停止时都必然遭遇连接超时或拒绝连接。
    * > 来源: P06, P08, P11
* **图形化工具的定位与团队规范**
    * > **结论**：在应用代码开发中团队通常要求强行统一集成开发环境（如 Java 团队硬性规定全员使用 IntelliJ IDEA，禁止私自使用 Eclipse，因为不同 IDE 生成的工程描述文件、编码格式与构建配置极易产生协同冲突）；但在数据库客户端的使用上团队通常不做任何强制统一限制。
    * 原因：数据库服务器遵循通用的网络交互协议，只要网络可通、认证通过，团队内有人用 Navicat、有人用 SQLyog、有人用 DBeaver 彼此互不影响，可完全根据个人操作习惯、界面审美以及操作系统环境自由选择。
    * 生产运维场景（尤其是远程 Linux 服务器环境）出于安全、资源消耗以及无图形桌面的客观限制，必须熟练通过终端命令行操作数据库，包括服务启停、配置排查、权限分配以及紧急运维脚本的编写。
    * > 来源: P10

* **工具选用的分工建议**
    * SQL 语言基础与多表查询采用小巧高效的 SQLyog 展开演示；复杂的数据库逆向工程与表结构建模切换至 Navicat；Mac 用户或大数据混合计算开发采用 DBeaver。
    * MySQL Workbench 虽是官方工具，但在国内企业的实际开发渗透率并不算最高；这几款工具底层执行的都是标准 SQL，核心功能完全相通。
    * > 来源: P10
* **图形化客户端连接四要素与命令行参数的映射**
    * `-h localhost / 127.0.0.1` 对应 GUI 字段"主机名 / IP 地址（Host / Server）"。
    * `-P 13306 / 3306` 对应 GUI 字段"端口号（Port）"，务必与后台运行的目标实例保持严格一致，双版本环境中 5.7 绑定 `13306`、8.0 绑定 `3306`。
    * `-u root` 对应 GUI 字段"用户名（User / Username）"。
    * `-p abc123` 对应 GUI 字段"密码（Password）"。
    * 连接名称（Connection Name）是给客户端本地看的标识标签，不影响网络连接；建议以目标服务器 IP 地址与环境命名（如 `127.0.0.1_MySQL5.7` 或 `127.0.0.1_MySQL8.0`），切忌随手输入无意义的默认字符。
    * 连接本机时主机名填写 `localhost` 或 `127.0.0.1`；连接远程服务器时填写局域网或公网 IP。
    * > **易错点**：点击"测试连接"时若客户端弹出 `Access denied for user 'root'@'localhost' (using password: YES)`，核心排查依据在最后那句 `using password: YES`——表示客户端已尝试携带密码校验但服务端验证未通过，99% 的原因是密码输入错误；应立即检查大写锁定键（Caps Lock）是否意外开启，或是否有前后空格残留。
    * > 来源: P10
* **Navicat、SQLyog 与 DBeaver 的操作要点**
    * Navicat 建立连接：点击主界面左上角【连接】按钮选择【MySQL】，输入连接名 `127.0.0.1_5.7`、主机 `localhost`、端口 `13306`、密码后点击左下角【测试连接】，回显"连接成功"后点击确定保存。
    * Navicat 对象浏览：在左侧连接树上双击激活连接（图标变绿），展开数据库 `dbtest1` 再展开【表】对象即可看到 `employees` 表；双击该表，右侧网格工作区直接以可视化 Excel 形式展现表内所有行与列数据。
    * Navicat SQL 执行：点击顶部工具栏【新建查询】，在查询编辑器录入 `select * from employees;`，选中目标代码片段后点击绿色【运行】按钮或按快捷键 `Ctrl + R`，下方控制台即刻返回结果集。
    * SQLyog 字体实时缩放技巧：鼠标光标停留在查询编辑窗口内，按住键盘 `Ctrl` 键不放同时前后滚动鼠标中间滚轮，即可毫秒级无级放大或缩小编辑区代码字号。
    * SQLyog 语句快速执行技巧：用鼠标高亮选中需要运行的 SQL 片段，点击顶部绿色三角图标或直接按下键盘快捷键 `F9`，即可单步执行选中的 SQL 代码段。
    * DBeaver 底层依赖：纯 Java 语言开发的开源项目，未配置 Java 运行时的系统上启动独立安装包可能提示无法找到 JRE/JDK，开发机必须先配置好标准 JDK 环境。
    * DBeaver 系统预置库自动折叠：默认设置下会智能折叠 `information_schema` 等只读系统元数据库，只把用户自定义的业务数据库（如 `dbtest1`）优先呈现在树形目录前端；这属于客户端的用户体验优化设计，并非底层元数据缺失。
    * > 来源: P10
* **`caching_sha2_password` 认证插件引发的连接故障**
    * 在 Navicat 或 SQLyog 中按 5.7 相同步骤新建指向 8.0 实例（主机 `localhost`、端口 `3306`、用户名 `root`）的连接，点击"测试连接"瞬间弹出 `Authentication plugin 'caching_sha2_password' cannot be loaded: ...`。
    * 根因：许多开发者本机安装的 Navicat 或 SQLyog 是多年前发布的旧版本，其内部捆绑的数据库通信驱动库根本没有编写过解析 `caching_sha2_password` 握手报文的逻辑，客户端识别不了服务器发回的认证加密请求，握手环节当场中断崩塌。
    * > **提示**：官方命令行客户端（`mysql.exe`）本身就是 8.0 原生发布的，具备解析新算法的能力，因此命令行登录完全不受影响。
    * 解决路径一：把本地安装的 Navicat、SQLyog 或 DBeaver 升级更新至支持 MySQL 8.0 通信协议的现代化新版本，新版客户端内部天然自带 `caching_sha2_password` 握手驱动。
    * 解决路径二（推荐实操）：把 8.0 服务端的认证规则降级还原为 5.x 兼容模式，适用于老项目的连接池框架、中间件或既定工具版本不可随意变更的场景。
    * 路径二步骤一：通过命令行登录 8.0 实例 `mysql -u root -P 3306 -p`。
    * 路径二步骤二：切换至系统核心库 `use mysql;`，用户权限与加密凭证属于 MySQL 核心元数据，统一托管在预置的 `mysql` 系统数据库中。
    * 路径二步骤三：`ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY 'abc123';`，显式声明认证插件使用传统的 `mysql_native_password` 并重新设置密码。
    * 路径二步骤四：`FLUSH PRIVILEGES;` 刷新系统权限字典缓存，让修改后的安全插件与密码散列即刻生效。
    * 路径二步骤五：退出命令行，回到图形化工具连接配置面板，无需改动任何端口与密码，再次点击"测试连接"即回显"连接成功"。
    * > **注意**：语句末尾单引号内的 `'abc123'` 是登录密码，务必根据自己的实际密码进行替换，不要生搬硬套。
    * > 来源: P07, P10

## 10. 物理目录结构、基础交互与运维避坑

> **一句话主旨**：拆解安装主目录与数据目录的分层职能、C/S 架构的文件隔离与源码模块，并归纳初始化阶段的高频报错与修复方案。

* **软件安装主目录（Program Directory）的分层职能**
    * 位于用户安装时指定的路径（例如 `D:\develop\mysql-8.0.25`）。
    * `bin/` 目录：存放 MySQL 所有核心二进制可执行文件，包括启动服务端的 `mysqld.exe`、客户端连接工具 `mysql.exe`、数据备份工具 `mysqldump.exe`。
    * `include/` 与 `lib/` 目录：存放供第三方 C/C++ 语言调用数据库引擎的开发头文件与静态、动态链接库。
    * `share/` 目录：存放错误信息字典与多语言字符集定义文件。
    * 把 `bin` 路径追加到操作系统 `Path` 环境变量的目的，是让操作系统的命令解释器能够全局检索到这些执行程序，使任何工作目录下都能直接调起 `mysql` 命令。
    * > 来源: P11
* **运行时数据与配置目录（Data Directory）的物理对象**
    * 位于系统隐藏目录 `C:\ProgramData\MySQL\MySQL Server X.X\` 下，与软件安装主目录处于完全解耦状态。
    * `Data/` 目录是真正存放物理数据文件的地方；执行 `create database dbtest1;` 后底层会在 `Data` 目录下生成一个同名的 `dbtest1` 物理文件夹，文件夹内部存放该库下所有表的结构与数据文件。
    * `#ib_16384_0.dblwr`：共享表空间与双写缓冲文件。
    * `ibdata1`：系统表空间数据文件。
    * `mysql/`：系统核心权限元数据目录。
    * `sys/`：性能诊断视图定义目录。
    * `dbtest1/`：用户自定义创建的业务数据库目录。
    * `my.ini`：Windows 服务端与客户端全局配置文件，控制服务端口、默认字符集、最大连接数与缓冲区大小等核心运行参数。
    * > 来源: P11
* **客户端/服务端（Client/Server，C/S）架构与物理文件隔离**
    * > **结论**：数据库绝不是普通的桌面单机软件；MySQL 是高度解耦的标准 C/S 架构体系，尽管学习阶段把数据库服务端与 Navicat/命令行客户端安装在同一台物理电脑上，但在逻辑通信链路上客户端与服务端完全是两套独立的实体，彼此通过 TCP/IP 网络协议（或本地套接字）建立网络通信。
    * 服务端的守护进程 `mysqld` 独占式地接管底层物理文件的读写与锁控制；客户端只负责向服务端发送符合 SQL 规范的网络请求报文，服务端解析执行后再把结构化结果集通过网络通道回传。
    * 用户绝不能、也无法绕过服务端的管控进程去直接篡改底层的物理数据文件。
    * 从架构层面看，MySQL 在逻辑上由客户端应用与连接接入、MySQL Server 服务层（连接管理 / 语法解析 / 优化器 / 缓存）、可插拔存储引擎层（InnoDB / MyISAM / Memory 等）、底层物理存储系统（数据文件 / 日志文件 / 磁盘 / 操作系统）自顶向下分层构成。
    * > 来源: P01, P11
* **C++ 源码工程核心模块**
    * 官方源码包（以 `mysql-8.0.25.zip` 为例）解压后可见底层工程主要采用 C++ 与 C 语言编写，核心文件以 `.cc` 和 `.h` 结尾。
    * `sql/` 目录：MySQL 最核心的调度中心与 SQL 解析引擎，包含客户端连接握手处理、SQL 词法与语法分析器、查询优化器、执行计划生成器以及表定义缓存（如 `bootstrap.cc`）。
    * `libmysql/` 目录：实现客户端连接与底层通信网络协议的客户端 API 库。
    * `mysql-test/` 目录：官方配套的大规模自动化测试套件与回归测试脚本。
    * `mysys/` 目录：跨平台的底层操作系统抽象库，封装跨 Windows、Linux、Unix 平台的文件 I/O、内存分配、线程锁调度等基础辅助函数。
    * > 来源: P11
* **基础交互流程与系统预置数据库**
    * 连接 5.7 实例：`mysql -u root -P 13306 -p`（`-h localhost` 可省略，但大写 `-P` 参数不能漏）。
    * `show databases;` 回显 4 个默认存在的系统数据库：`information_schema`、`mysql`、`performance_schema`、`sys`。
    * > **易错点**：`show databases;` 中的 `databases` 必须是复数形式且末尾带有 `s`，SQL 语句必须以半角分号 `;` 结尾。
    * 建库：`create database dbtest1;`，再次执行 `show databases;` 可见结果集中已包含新库。
    * 建表：`create table employees (id int, name varchar(15));`。
    * > **易错点**：直接执行 `create table` 会返回 `ERROR 1046 (3D000): No database selected`；MySQL 实例内部可托管成百上千个独立数据库，客户端并未告知服务器当前要在哪一个数据库作用域下建表。
    * 上下文切换：`use dbtest1;`，终端回显 `Database changed`；之后 `show tables;` 显示 `Empty set`。
    * 写入与查询：`insert into employees values(1001, 'Tom');`、`insert into employees values(1002, 'shk-start');`、`select * from employees;` 正常输出两行记录。
    * 在 8.0 实例中做同样的纯英文操作，步骤与现象完全一致。
    * > 来源: P09

| 系统数据库名称 | 核心职责与存储内容说明 | 开发运维关注阶段 |
| :--- | :--- | :--- |
| `information_schema` | 存储数据库服务器的元数据（元信息），包括所有数据库名、表名、列信息、数据类型及访问权限等，属只读视图 | 进阶查询、元数据逆向分析 |
| `mysql` | 存储 MySQL 核心系统运行时所需的信息，如用户账户权限表、系统变量设置、时区信息等 | 权限管理、底层安全审计 |
| `performance_schema` | 收集并存储 MySQL 服务运行时的底层性能指标、锁事件、内存消耗及线程状态 | 高级篇性能调优、锁分析 |
| `sys` | 把 `performance_schema` 和 `information_schema` 的底层复杂度打包封装成易读视图，便于管理员直接诊断 | 慢查询排查、运维监控告警 |

* **系统库的保护边界**
    * 基础实操阶段严禁随意删除或手动修改这 4 个库里的结构与数据。
    * 高级篇和性能优化篇会频繁调取里面的视图来诊断锁争用和性能瓶颈。
    * > 来源: P09
* **无数据库上下文报错的两种修复方案**
    * 故障根源：客户端与服务端建立连接后当前会话处于全局未绑定状态，直接发起针对某张表的 DDL 或 DQL 指令时解析器无法判定目标对象归属于哪一个具体数据库。
    * 方案 A（标准做法）：在操作前先执行上下文切换指令 `use dbtest1;`。
    * 方案 B（全限定名调用）：在表名前显式带上所属数据库前缀，如 `select * from dbtest1.employees;`。
    * > 来源: P11
* **环境变量类报错的修复**
    * 现象：命令行回显"不是内部或外部命令，也不是可运行的程序"。
    * 故障根源：操作系统执行命令时优先在当前目录查找，若找不到则遍历 `Path` 环境变量中配置的所有目录；该报错说明系统在 `Path` 路径清单中未能检索到 `mysql.exe`。
    * 修复方案：检查系统环境变量 `Path`，确保追加了 MySQL 安装根目录下的 `bin` 绝对路径，并确认路径末尾无多余中文字符或截断；配置完成后务必重新打开一个新的命令行窗口以加载最新环境变量。
    * > 来源: P11
* **环境搭建阶段高频避坑清单**
    * 安装路径严禁包含中文字符：从操作系统底层 API 到各类开源数据库服务，底层 C/C++ 动态链接库与系统服务在解析非 ASCII 编码路径时极易出现乱码或路径找不到的情况。
    * 严禁私自对已安装的服务目录执行"剪切"（`Ctrl + X`）移动，底层注册表键值不会跟随动态更新。
    * 修改 `my.ini` 后必须重启后台 Windows 服务才能重新加载参数；规范时序为先停服务、再改文件、后启服务。
    * 二次安装失败的主要原因就是旧版本残留数据未清理干净，必须掌握 MySQL 在 Windows 系统中的全部物理分布及卸载规范。
    * > 来源: P10, P11

## 11. 综合考点收敛与达标验收

> **一句话主旨**：把数据库分类、发展时间线、概念辨析、表关联模型与环境搭建考核点收敛为可复述的答题要点与硬性达标项。

* **数据库分类与发展史的考点要点**
    * 常见数据库清单——关系型 Oracle、MySQL、SQL Server、DB2、PostgreSQL；非关系型 Redis、MongoDB、Elasticsearch、HBase、Neo4j；后端开发通常需要掌握关系型与缓存型（如 Redis）的组合。
    * MySQL 历史与特点——1995 年瑞典 MySQL AB 创立；2008 年 Sun 收购；2009 年 Oracle 收购 Sun 获得 MySQL；2016 年推出里程碑版本 8.0.0；核心特点是开源、关系型、支持千万级数据量存储、成熟稳定。
    * 五类 NoSQL 类型——键值型（Redis）、文档型（MongoDB）、搜索引擎型（Elasticsearch/Solr）、列式存储（HBase）、图形数据库（Neo4j）。
    * > 来源: P11
* **Windows 下 MySQL 踪迹与卸载范围的考点要点**
    * 系统中能看到 MySQL 的位置——软件安装路径、`C:\ProgramData\MySQL` 数据目录及 `my.ini`、系统服务（Services）、`Path` 环境变量。
    * 需要卸载清理的位置——控制面板卸载主程序、手动删除 `ProgramData` 物理数据目录、清理 `Path` 环境变量、清理注册表（`regedit`）服务残留、重启电脑。
    * 二次安装失败的主要原因就是旧版本残留数据未清理干净，必须掌握 MySQL 在 Windows 系统中的全部物理分布及卸载规范。
    * > 来源: P11
* **环境搭建硬性达标项**
    * 下载与安装：至少掌握 MySQL 8.0 的安装，或同时搭建 5.7（`13306`）与 8.0（`3306`）双实例并完成多端口配置。
    * 字符集改造：5.7 环境必须在 `my.ini` 的 `[mysql]` 下加 `default-character-set=utf8`、在 `[mysqld]` 下加 `character-set-server=utf8` 与 `collation-server=utf8_general_ci`，修改后重启服务并验证中文写入，同时对比 8.0 开箱即用支持中文与 `utf8mb4` 的差异表现。
    * 客户端连接：在本机自选至少一款图形化管理工具（Navicat / SQLyog / DBeaver），完整建立 5.7（`13306`）与 8.0（`3306`）的双实例连接。
    * 认证兼容修复：连接 8.0 若出现身份验证插件报错，必须独立在命令行中通过 `ALTER USER ... IDENTIFIED WITH mysql_native_password` 语句完成修复并测试通过。
    * 常用工具清单——Windows cmd 命令行、MySQL 自带 Command Line Client、GUI 工具（Navicat、SQLyog、DBeaver、Workbench）。
    * > 来源: P09, P10, P11
