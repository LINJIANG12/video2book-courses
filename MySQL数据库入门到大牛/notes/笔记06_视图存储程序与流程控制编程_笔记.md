# MySQL 视图、存储程序与流程控制编程
## 数据库对象体系与视图的本质


* **数据库对象（Database Objects）**
    * 存储在数据库中、具有特定技术功能和独立元数据定义的命名实体。
    * 体系包含：表（Table，二维行列持久化业务数据）、数据字典（Dictionary，系统元数据表，如 `mysql` 系统库记录用户账号与权限）、约束（Constraint，含 `pk_`、`fk_`、`uk_` 独立命名机制）、视图（View）、索引（Index）、存储过程（Procedure）、存储函数（Function）、触发器（Trigger）。
    * 数据字典只供查询与探查，严禁通过底层 SQL 直接手动修改；执行 DDL 建用户、DCL 赋权限时由引擎自动维护同步。
    * 存储函数必须且只能返回单个确定结果；存储过程可无返回值，也可用多个 `OUT` 参数批量返回结果。
* **视图（View）的本质**
    * > **定义**：视图是被赋予独立名称并持久化保存在数据字典中的 `SELECT` 查询语句。
    * 创建语法 `CREATE VIEW 视图名称 AS 查询语句;` 相当于给一段 `SELECT` 逻辑加命名外壳，并把该逻辑作为元数据持久化。
    * 视图本身不存储任何实体业务数据，行数据完全由底层物理表动态映射计算生成。
    * 视图依赖的一个或多个物理数据表统称**基表（Base Table）**；对视图增删改查最终都穿透作用于基表，系统中自始至终只有基表里那一份真实数据。
* **视图对物理子表方案的替代**
    * `CREATE TABLE emp_public AS SELECT ...` 是对原表数据的**物理深拷贝**，新表与原表在磁盘上完全独立，在子表上改数据不会改变原表，造成主从数据失步。
    * 改用视图后：敏感字段（如 `salary`、`evaluation`）不在视图投影范围内，调用方无法窥探；对视图 `UPDATE` 会实时改动基表对应记录，直接改基表也会立刻反映到视图查询结果。
    * MySQL 支持针对单个视图独立授予 `SELECT`、`UPDATE`、`DELETE` 权限，可只开放视图读写而彻底关闭物理大表权限。
* **视图的生命周期解耦**
    * 视图的创建与删除只影响视图自身元数据，不会破坏或删除底层基表数据：`DROP VIEW` 只是抹除数据字典里存储的那段 `SELECT` 定义，既不清空基表磁盘数据页，也不改动基表元数据。
    * > **易错点**：基表若发生 DDL 删列或改名，会导致依赖该列的视图在**被查询时**才暴露异常，而不是在基表变更的瞬间报错。
* **视图的价值与代价**
    * 五大赋能：简化复杂查询（跨 5~8 张大表的多层嵌套子查询降维为单表查询）、零数据冗余（不占物理磁盘空间，仅存查询元数据定义）、安全隔离（列级脱敏与行级过滤）、适应多变业务（基表字段拆分或命名重构时加盖兼容视图，外部系统无需改代码）、拆解复杂逻辑（多层报表分段封装为中间视图）。
    * 潜在制约：封装超长 SQL 会使调用方忽视底层多表关联开销；无法替代应用层业务安全风控；每次查询都需穿透执行或动态合并，有计算开销；含聚合函数、分组、`DISTINCT` 等复杂逻辑的视图往往不可更新；隐性耦合使三四层以上嵌套视图的排查维护成本指数级恶化。
    * 工程选型准则：小型项目与轻量应用（几十张表、关系扁平）坚决不推荐滥用视图，直接在持久层写原生 SQL；大型企业系统与数据中台在跨部门权限隔离、核心敏感数据脱敏、跨系统报表共享的关键节点，适度引入单层或浅层视图。

## 视图的创建、派生与元数据查看


### 创建语法与字段命名范式

* **视图创建完整语法骨架**
    * `CREATE [OR REPLACE] [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}] VIEW 视图名称 [(字段别名列表)] AS SELECT 查询语句 [WITH [CASCADED | LOCAL] CHECK OPTION];`
    * `OR REPLACE`：同名视图已存在则直接覆盖替换现有定义，用于平滑变更升级。
    * `ALGORITHM` 三取值：`UNDEFINED`（默认，由优化器自动选择最合适的执行算法）、`MERGE`（把外部查询视图的语句与视图内部 `SELECT` 合并为一条复合 SQL 后再优化检索）、`TEMPTABLE`（每次调用先把视图查询结果物理物化生成内部临时表，外部查询再对该临时表过滤检索）。
    * 常规开发使用最精炼范式 `CREATE VIEW 视图名称 AS SELECT 查询语句;` 即可。
* **字段别名的三种命名范式**
    * 范式 A：默认沿用基表列名，`SELECT employee_id, last_name, salary FROM emps`，视图列名与物理基表完全一致。
    * 范式 B：在 `SELECT` 子句用 `AS` 起别名（如 `last_name AS l_name`），视图内部 `SELECT` 声明的字段别名直接升格为该视图对外暴露的正式列名称。
    * 范式 C：在视图名称后用小括号集中声明列别名，`CREATE VIEW vu_emp3 (emp_id, name, monthly_salary) AS SELECT ...`。
    * 两种定义别名的方式在 MySQL 底层解析出的数据字典元数据完全等价，团队内部保持统一即可。
    * > **易错点**：范式 C 括号内别名数量必须与下方 `SELECT` 投影出的列数量严格相等且位置一一对应，写 3 个别名而查 4 列会立即解析报错。
* **`CREATE TABLE ... AS SELECT` 克隆表的约束丢失**
    * 用 `CREATE TABLE emps AS SELECT * FROM atguigudb.employees;` 克隆表时，只有列的非空属性（`NOT NULL`）被继承，**原表的主键、唯一键、外键约束全部丢失**。
    * 原因：该语法只依据查询结果集的元数据（字段名与数据类型）搭表并插入行记录，不同步复制基表的索引树与键约束关系。
    * 快速克隆空表结构而不带数据的经典写法是加恒假条件：`CREATE TABLE emps_back AS SELECT * FROM emps WHERE 1 = 2;`，解析器仍能推导出列名、列类型与基本约束。

### 单表、多表与嵌套视图

* **单表视图的两种字段来源形态**
    * 实体字段直接映射：视图列与基表物理列一一对应（如 `employee_id`、`last_name`），数据真实保存在基表磁盘行中，具备更新的可映射性。
    * 虚拟计算 / 聚合字段：视图列由函数、算术表达式或聚合统计动态生成（如 `AVG(salary) avg_sal`），**基表中根本不存在对应的物理列**，数据在调用视图时由优化器实时计算。
    * > **易错点**：含虚拟计算或聚合列的视图无法支持反向 `UPDATE` 或 `INSERT`，因为系统找不到物理落盘的目标列。
* **多表关联视图与格式化封装**
    * 跨表连接视图：`CREATE VIEW vu_emp_dept AS SELECT e.employee_id, e.department_id, d.department_name FROM emps e JOIN depts d ON e.department_id = d.department_id;`，创建成功后取员工及部门信息无需再手写 `JOIN ... ON ...`。
    * > **易错点**：两表同名字段（如都叫 `department_id`）必须在查询语句中用表别名限定，否则触发字段二义性错误。
    * 数据展示格式化封装：用字符串函数在视图层面完成拼接，如 `SELECT CONCAT(e.last_name, '(', d.department_name, ')') AS emp_info FROM emps e JOIN depts d ON ...`，直接输出 `King(Executive)` 格式，把排版逻辑固化在数据层。
* **嵌套视图（Nested View）与嵌套深度**
    * 视图在外部查询视角与普通二维表无异，可基于已有视图再次创建新视图：`CREATE VIEW vu_emp4 AS SELECT employee_id, last_name FROM vu_emp1;`。
    * 级联链路为「底层基表 ← 视图 A ← 视图 B」，B 保存的是 `SELECT ... FROM view_A`；视图 A 被 `DROP` 抹除后，B 的依赖对象凭空蒸发，查询 B 会报 `View 'view_B' references invalid table(s) or column(s) or function(s)`，成为必须人工 `ALTER VIEW` 或一并删除的「僵尸视图」。
    * 企业架构中不建议过深嵌套，通常不超过 2 到 3 层，多层包装会使底层执行计划难以预测、排查调优链路冗长。
* **实验基准环境的关键数据**
    * `CREATE DATABASE dbtest14;` 后用 `CREATE TABLE emps AS SELECT * FROM atguigudb.employees;` 与 `CREATE TABLE depts AS SELECT * FROM atguigudb.departments;` 克隆基表，得到 107 条员工记录与 27 条部门记录。
    * `SELECT * FROM vu_emp1;` 返回 107 条；按 `department_id` 分组的平均工资视图 `vu_emp_sal` 输出 11 个部门的数据。
    * 后续 DML 练习删除 101 号员工后，视图 `employee_view` 记录数变为 106 条，印证视图查询动态转换为对基表的查询。

### 元数据查看的四维机制

* **机制一：`SHOW TABLES` 全量对象概览**
    * `SHOW TABLES;` 返回的结果集列表中，物理基表（`emps`、`depts`）与当前库所有视图对象（`vu_emp1`、`vu_emp_dept` 等）平级混排展示，用于快速探查当前库包含哪些可用表与视图。
    * > **易错点**：MySQL 中根本不存在 `SHOW VIEWS` 这条命令，查视图不能照搬「查表是 SHOW TABLES」的直觉。
* **机制二：`DESC` 查看字段结构**
    * `DESC 视图名;`（或完整拼写 `DESCRIBE 视图名;`）输出 `Field`、`Type`、`Null`、`Key`、`Default`、`Extra` 等属性列，用法与普通数据表完全一致，外观上看不出与物理表的差别。
    * 重命名字段后 `DESC employee_view;` 显示的是 `r_name`、`emp_id`、`dept_id` 等逻辑列名，类型与长度继承自基表字段定义，基表真实列名被隐藏。
* **机制三：`SHOW TABLE STATUS` 探查物理状态**
    * `SHOW TABLE STATUS LIKE 'vu_emp1'\G`：`Engine`、`Version`、`Row_format`、`Rows`、`Data_length`、`Max_data_length`、`Index_length`、`Data_free`、`Auto_increment`、`Update_time`、`Collation`、`Checksum`、`Create_options` 全部为 `NULL`，`Comment` 被标记为 `VIEW`，仅 `Create_time` 有值。
    * 该现象从元数据层面证明视图在物理磁盘上不存在真实数据文件，不独占行存储与索引空间，唯一存储痕迹是该定义本身的创建时间戳与元数据条目。
    * 命令行中单行展示字段极多容易折行错乱，建议用 `\G` 替代分号实现行列转置的垂直输出。
* **机制四：`SHOW CREATE VIEW` 逆向 DDL**
    * `SHOW CREATE VIEW vu_emp1\G` 返回创建视图时的全量原生 DDL：`Create View: CREATE ALGORITHM=UNDEFINED DEFINER=\`root\`@\`localhost\` SQL SECURITY DEFINER VIEW \`vu_emp1\` AS select \`emps\`.\`employee_id\` AS \`employee_id\`, ... from \`emps\``。
    * 可据此审计优化器幕后补充的默认参数：自动补充默认算法 `ALGORITHM = UNDEFINED`；绑定安全执行上下文与定义者账号（`DEFINER` 与 `SQL SECURITY`）；把简写 `SELECT` 规范化为带反引号与完全限定列名的标准化查询语法。

| 查看机制 | 命令示例 | 核心输出内容 | 典型应用场景 |
| :--- | :--- | :--- | :--- |
| 全量对象概览 | `SHOW TABLES;` | 库下所有物理基表与视图名称混排列表 | 快速探查当前库包含哪些可用表与视图 |
| 字段结构检视 | `DESC 视图名;` | 字段名、类型、Null 约束、默认值等列定义 | 编写 SQL 前确认视图暴露的字段与类型 |
| 物理状态探查 | `SHOW TABLE STATUS LIKE '视图名'\G` | `Comment: VIEW`，且存储指标均为 `NULL` | 鉴别对象是物理表还是视图，证明无物理数据 |
| DDL 原型逆向 | `SHOW CREATE VIEW 视图名\G` | 完整的 `CREATE VIEW ... AS SELECT ...` 源码 | 审计视图底层引用的基表、字段及过滤算法 |

## 视图的 DML 更新边界与生命周期管理


### 可更新视图的穿透联动

* **UPDATE 的双向穿透**
    * 对简单单表视图执行 `UPDATE` 会导致底层物理基表对应记录实质性修改；反过来直接在基表改数据，视图查询结果也实时同步。
    * 实验数据：`vu_emp1` 与基表 `emps` 中 101 号员工薪资同为 `17000.00`，通过视图 `UPDATE ... SET salary = 20000 WHERE employee_id = 101;` 后基表变为 `20000.00`；绕过视图在基表改为 `10000` 后，视图查询立刻变为 `10000.00`。
    * 联动根本原因：系统内自始至终只有物理基表这一份真实数据，修改视图就是借助视图定义穿透到底层基表进行物理落盘。
* **DELETE 的物理删除与外键拦截**
    * `DELETE FROM vu_emp1 WHERE employee_id = 101;` 后视图与基表 `emps` 的记录数同时从 107 降为 106，基表中该行彻底不复存在。
    * > **易错点**：从视图执行 `DELETE` 能够成功的先决条件是该操作在底层基表上同样被允许；若基表存在外键级联限制（如其他表外键引用该 `employee_id` 且策略为 `RESTRICT` 或 `NO ACTION`），删除会因引用完整性冲突被引擎拒绝。

### 不可更新的判定准则

* **不可更新的判定本质**
    * 当视图的一行数据无法在逻辑上可逆、唯一地映射回基表的具体物理行与物理列时，该视图必定不可更新。
    * 反例推演：`vu_emp_sal` 中 30 号部门的 `avg_sal` 是 6 名员工薪资聚合成的单一数值，把它改成 5000 时引擎无法决定 6 人各自增减多少才能让平均值恰好等于 5000；年薪计算列 `salary * 12 * (1 + IFNULL(commission_pct, 0))` 混合两个物理变量，改年薪也无法决定该动 `salary` 还是 `commission_pct`。
    * 报错表现：对聚合视图执行 `UPDATE` 或 `DELETE` 抛出 `Error Code: 1288. The target table xxx of the UPDATE is not updatable`；对聚合视图执行 `INSERT` 抛出 `Error Code: 1471. The target table xxx of the INSERT is not insertable-into`。
* **可插入性的额外前提**
    * 除视图本身必须满足简单视图规范外，**基表中所有未出现在视图中的字段必须允许为 `NULL`，或者具备明确的 `DEFAULT` 默认值**，否则该视图在业务上天然只读不可插入。
    * 反例：向 `emp_v1(last_name, email, phone_number)` 插入 `('Tom','Tom@126.com','010-12345')` 报 `Error Code: 1364. Field 'hire_date' doesn't have a default value`——基表 `emps` 的 `hire_date`（`date`）、`job_id`（`varchar(10)`）均为 `NOT NULL` 且无默认值，未投影列无法填充合法值，写入违反非空完整性约束后整个事务立即回滚。
* **工程实战根本准则**
    * 视图从诞生之初的核心使命是服务高效查询与安全隔离；虽然在满足严苛条件时语法上支持增删改，但实际工程架构中强烈不建议通过视图进行任何 DML 写入操作，所有业务实体的增删改都应直接、显式地针对底层物理基表进行，确保事务与约束链条清晰透明。
    * 视图字段缺失时无法更新：`UPDATE emp_v1 SET salary = salary + 1000;` 报 `Unknown column 'salary' in 'field list'`，因为 `salary` 已被移出投影；外部只能操作视图元数据中已暴露的字段，必须先用 `CREATE OR REPLACE VIEW` 把该列重新加入投影再执行更新。

| 不可更新的语法特征 | 典型关键字 / 构造 | 拦截原因 |
| :--- | :--- | :--- |
| 聚合与分组函数 | `SUM()`、`AVG()`、`COUNT()`、`MAX()`、`MIN()` | 多行折叠为一行标量，反向拆解无确定解 |
| 去重操作 | `DISTINCT` | 重复记录被合并展现，无法确定修改定位到哪一行 |
| 分组与过滤条件 | `GROUP BY`、`HAVING` | 数据已经过聚合桶分类，无法穿透至原始行记录 |
| 结果集合并 | `UNION`、`UNION ALL` | 结果来自多段独立数据流的叠加，映射归属模糊 |
| 关联连接复杂性 | 复杂的跨表 `JOIN`，尤其含非键保留表 | 容易破坏跨表引用的完整性与唯一性 |
| 计算衍生列 | 数学表达式、`CONCAT` 等字符串函数 | 物理基表中无对应实体字段落盘 |
| 常量与不可更新视图派生 | `SELECT '常量' AS col` 或上层依赖不可更新视图 | 根源上缺乏物理可写的数据靶点 |


### 视图定义的修改与删除

* **定义修改的两种范式**
    * `CREATE OR REPLACE VIEW`（原子覆盖）：视图不存在则创建，已存在则用新的 `SELECT` 定义原子性覆盖，部署脚本幂等性更好，无论对象先前是否存在都能执行成功。
    * `ALTER VIEW`（直接变更）：与 `ALTER TABLE` 风格一致，直接针对已存在的视图结构重定义，如 `ALTER VIEW vu_emp1 AS SELECT employee_id, last_name, salary, email, hire_date FROM emps;`。
    * 变更效果可用 `DESC vu_emp1;` 验证，字段列表与数据过滤范围均会平滑更新。
* **删除语法与防错机制**
    * 基础删除 `DROP VIEW vu_emp4;`；批量删除用逗号分隔 `DROP VIEW vu_emp2, vu_emp3;`；规范写法携带 `IF EXISTS`：`DROP VIEW IF EXISTS emp_v1, emp_v2;`。
    * > **易错点**：未加 `IF EXISTS` 而删除不存在的视图会抛出 `Error 1051: Unknown table ...`，在自动化部署或批处理脚本中会中断整个脚本链条；加 `IF EXISTS` 后目标不存在则降级为一条警告而主流程继续。
    * 批量删除后可再用 `SHOW TABLES;` 检验清理结果（视图同样出现在该输出清单中），重复执行 `DROP VIEW IF EXISTS` 不会产生报错，适合自动化运维脚本与流水线初始化。
* **视图练习的命名与结构规范**
    * 视图命名两种风格：前缀 `vu_` / `view_` 开头（如 `vu_emp`），或后缀 `_view` / `_vu` 结尾（如 `employee_view`），与完整性约束命名习惯类似，团队内部统一即可。
    * 过滤范围变更示例：将 `employee_view` 的暴露范围限定为 `WHERE department_id = 80`，非 80 号部门数据对持有该视图权限的用户完全不可见，实现行级权限隔离与数据脱敏。
    * 为含聚合函数或表达式的查询创建视图时，**必须为该表达式指定合法的列别名**——视图是命名的关系模式，每一列都必须有明确字段名，不能直接把 `MAX(salary)` 当列标识符。

## 存储过程与存储函数总论


### 存储程序定位与返回值契约

* **存储程序（Stored Routine）的本质**
    * > **定义**：存储过程与存储函数本质上是用户自定义的、封装了一组复杂 SQL 逻辑并持久化保存在 MySQL 服务端的程序单元。
    * 它们与系统内置的单行函数（`ROUND(123.45)` 输出 `123`、`LOWER('ABC')` 输出 `abc`、`DATEDIFF(date1, date2)` 计算日期差）与聚合函数（`SUM()`、`AVG()`、`MAX()`、`MIN()`、`COUNT()`）的区别在于由用户自主封装，用于内置函数无法直接满足的业务规则。
* **存储过程与存储函数的划分依据**
    * 核心判定准则：**是否存在强制的单一返回值（因变量）**。
    * 存储函数完全遵循数学函数契约 $y = f(x)$，自变量输入经内部封闭运算后必须通过 `RETURN` 返回一个且仅一个确定类型的值，因此可直接嵌入 `SELECT` 查询列表、`WHERE` 过滤条件或 `HAVING` 子句当作表达式使用。
    * 存储过程更偏向子程序或过程化事务脚本，**没有 `RETURN` 语句、不强制要求返回值**，可执行跨表批量插入、数据清洗、DDL 表重构等整套业务流，结果通过 `OUT` 形参带回或直接在过程体内 `SELECT` 把结果集抛给客户端，必须通过专用 `CALL` 命令显式触发。

| 对比维度 | 存储过程（Stored Procedure） | 存储函数（Stored Function） |
| :--- | :--- | :--- |
| 定义关键字 | `CREATE PROCEDURE` | `CREATE FUNCTION` |
| 返回值声明 | 头部无返回值类型声明 | 头部强制使用 `RETURNS type` |
| 退出返回机制 | 内部无 `RETURN` 语句，靠 `OUT` / `INOUT` 参数带出 | 内部强制执行 `RETURN expression;` |
| 参数模式支持 | 支持 `IN`、`OUT`、`INOUT` 复合与双向模式 | 仅支持隐式 `IN` 模式，不支持出参模式 |
| 调用语法 | 必须使用专用的 `CALL 过程名(...)` 独立执行 | 直接使用 `SELECT 函数名(...)` 内联调用 |
| SQL 嵌入能力 | 不可作为表达式嵌入普通 SQL 语句 | 可以无缝嵌入 `SELECT`、`WHERE`、`ORDER BY` 中 |
| 输出数据形态 | 可输出 0 个、1 个或多个变量值，或直接输出多行结果集 | 严格只能输出且必须输出 1 个单一标量值 |
| 核心业务倾向 | 侧重数据维护与批量更新（含大量 DML / DDL） | 侧重数据转换与计算查询（加工清洗返回标量） |
| 功能灵活性 | 功能更强大、对事务控制更深入、适应复杂程序流 | 结构相对轻量、专精于单一计算职责 |


### 与视图的分野及工程选型

* **存储过程与视图的底层逻辑分野**
    * 视图的灵魂在于「表」，仅封装单一 `SELECT` 查询语句，不支持局部变量、循环、分支与游标，调用者像查普通表一样查它，极不推荐做 DML。
    * 存储过程的灵魂在于「程序」，封装任意复杂的复合 SQL 逻辑，全面支持变量声明、条件分支、循环、异常处理与游标，天然支持大量增删改建表等物理写入，调用者把它当服务端后台任务来触发。
* **预编译驻留与四项技术红利**
    * 网络开销极小化：业务涉及 10 条长 SQL 的顺序执行与中间判定时，传统方式需多次网络往返传输大量文本报文，存储过程只需传输一句 `CALL proc(...)`。
    * 预先编译与执行加速：常规 SQL 文本每次都要经历词法解析、语法解析、预处理、生成逻辑执行计划、优化并编译为机器码；存储过程在 `CREATE` 定义时就在服务端完成编译解析，以预编译形式常驻数据库高速缓存，后续调用直接执行已生成的二进制代码。
    * 安全性与逻辑封装：底层表结构与敏感列名封装在过程体内，可只给业务用户分配特定存储过程的 `EXECUTE` 权限而完全收回对底层物理明细表的 `SELECT` / `UPDATE` 权限，防范内部数据泄露与恶意 SQL 注入。
    * 统一业务逻辑防漂移：多端应用（Web 端、移动 App、第三方合作网关）若用各自语言实现计算极易产生规则不一致，把核心账务逻辑固化在存储过程内可确保所有接入端统一口径。
* **工程抵制的五项硬伤**
    * 移植性极差：Oracle 的 PL/SQL、SQL Server 的 T-SQL、MySQL 的 Procedural 语法、PostgreSQL 的 PL/pgSQL 在语法关键字、变量声明、游标使用、异常捕获机制上差异巨大，重度依赖存储过程基本无法平滑迁移数据库。
    * 调试与版本化痛苦：MySQL 官方没有原生可用的可视化调试器，不支持行级断点、条件断点与内存变量堆栈追踪；排错只能把过程体手工拆碎逐句外提单测，或在内部频繁 `INSERT INTO debug_log` 打桩记录状态；变更需执行 DDL 刷新，多名开发在线变更极易引发版本覆盖冲突。
    * 缺失工程级版本控制：存储过程直接保存在远程数据库实例中，数据库不原生提供 Git 式的 Diff 历史追溯与原子回滚，多人协同易发生后提交覆盖前人成果的「代码踩踏」，线上热修复与灰度发布时版本切换混乱。
    * 违背分布式水平扩展原则：应用服务器无状态、可通过加容器加虚机横向弹性伸缩；数据库服务器有状态且受磁盘 I/O、锁机制与连接数限制，是最昂贵最容易饱和的单点瓶颈。在数据库层跑大量循环、逻辑判断与复杂运算会迅速打满 CPU，直接降低并发承载上限。
    * 黑盒化与人员断层：核心逻辑深埋数据库且缺乏文档，老员工离职后后人既不敢修改也不敢废除，演变成不可维护的技术债务。
    * 阿里巴巴《Java 开发手册》明文规定：「【强制】禁止使用存储过程，存储过程难以调试和扩展，更没有移植性。」
* **技术选型的行业分野与决策指南**
    * 传统企业 / 银行 / 证券 / 电信：业务规则高度稳定、数据安全隔离要求极高、倾向集中式高端数据库硬件、偏好由 DBA 统一收拢权限，因而强制或重度依赖存储过程；典型应用场景包括金融核心、传统 ERP、中小型企业内部系统、数据仓库 ETL 离线批处理与特定数据清洗任务。
    * 互联网行业 / 分布式微服务：业务快速迭代高频发版、海量并发与水平伸缩诉求、架构推崇应用做有状态计算而 DB 瘦身、依赖 CI/CD 与自动化版本治理，因而强制禁止使用存储过程。
    * 「不使用存储过程」分两种境界：第一种是**根本不会**（知识盲区导致无法使用）；第二种是**精通底层原理与语法细节、清楚每一项优缺点与资源消耗**后，基于架构理性主动做出的弃用选择。基本工作法则是「技术全面掌握，工程就地取材」，进入企业后严格遵循所在团队与项目架构师的技术选型规范。

## 存储过程的创建、参数模式与调用


### 参数模式与调用传参规则

* **五种形参组合模式**
    * 无参数过程：小括号内完全为空，调用时不传实参，通常用于执行固定任务的批处理（如每日定时清空临时表、重构统计数据）。
    * 纯 `IN` 参数：仅作纯输入，外部必须提供常量或变量值，过程体内可读；即便在过程体内修改该形参，外部调用方的原始变量也绝不受影响（值传递机制）。
    * 纯 `OUT` 参数：调用时传入的实参必须是能接收结果的变量；过程体执行前该参数在内部初始值为 `NULL`（外部传入时变量已有初始值也会被丢弃），过程体内部必须有 `INTO` 赋值之类逻辑向它写入，执行完毕后外部变量即可读到新数据。
    * 复合参数（`IN` 与 `OUT` 混用）：外部传入若干查询或过滤条件，过程体内计算后把若干汇总结果分别写入对应 `OUT` 参数供外部取出，是业务开发中最标准的交互模式。
    * 双向 `INOUT` 参数：外部调用前必须为变量赋好初值并传给形参，过程先读取该初值参与运算，结束后把新计算值重新写入形参，退出时外部变量的值已被彻底覆写。
    * > **易错点**：定义形参时省略 `IN`、`OUT` 或 `INOUT` 关键字，MySQL 默认将其视为 `IN` 参数。
* **调用端的传参硬约束**
    * `IN` 参数灵活性最高，既可传字面量常量（`CALL show_someone_salary('Abel');` 输出 `11000.00`），也可先 `SET @emp_name := 'Abel';` 再传会话变量。
    * `OUT` 参数与 `INOUT` 参数**绝对禁止传递字面量常量**：`CALL show_min_salary(100);` 或 `CALL double_value(3, 5);` 会被语法分析器直接拒绝（报 `OUT or INOUT argument 1 for routine ... is not a variable`），因为常量是只读的不可变字面量，内存地址无法被写入，无法承担退出时的数据回写。
* **`SET` 赋值符与变量前缀**
    * `SET` 赋值语句既可用常规等号 `=`，也可用赋值符 `:=`；但在非 `SET` 语句中（如 `SELECT @var := col`）必须强制使用 `:=`，避免与等于比较运算符混淆。
    * 用户会话变量以单 `@` 开头（如 `@ms`），作用域为当前客户端会话；系统变量用双 `@@`。

| 参数模式 | 内部初值 | 调用实参要求 | 外部变量最终值 | 典型用法 |
| :--- | :--- | :--- | :--- | :--- |
| 无参 | 不适用 | 不传参 | 不涉及 | 固定批处理、全表统计输出 |
| `IN` | 传入值 | 常量或变量皆可 | 原值不变（值传递） | 动态条件过滤、插入入参 |
| `OUT` | `NULL`（丢弃外部初值） | 必须是变量 | 被过程体写入的新值 | 单指标或复合指标回传 |
| `IN` + `OUT` 混用 | `IN` 为传入值、`OUT` 为 `NULL` | `OUT` 位置必须是变量 | `IN` 不变、`OUT` 被覆写 | 条件入参 + 多结果回传 |
| `INOUT` | 外部初值 | 必须是已初始化变量 | 被彻底覆写为新值 | 单参数先入后出（如查主管姓名） |


### 过程体内部赋值语法与类型匹配

* **`SELECT ... INTO` 赋值机制**
    * 将查询结果写入变量的核心语法是 `SELECT ... INTO 变量名`，如 `SELECT MIN(salary) INTO ms FROM employees;`，要求投影结果必须是**单行单列的标量值**，返回多行多列则赋值直接报错。
    * 多字段回写写作 `SELECT b.name, b.phone INTO name, phone FROM beauty b WHERE b.id = id;`。
    * 不依赖任何物理表的纯内存计算可省略 `FROM`，如 `SELECT DATEDIFF(birth1, birth2) INTO sum_date;`。
    * > **易错点**：`INTO` 之后直接跟以逗号分隔的变量列表，**绝不能加圆括号**；写成 `INTO (name, phone)` 会被解析器识别为子查询语法并抛出 `1064 Syntax Error`。
* **形参与列同名的二义性消除**
    * 定义形参名时强烈建议不要与数据表物理字段名完全同名，通常采用 `emp_name`、`in_name` 等具名方式规避歧义。
    * > **易错点**：若形参名为 `id` 且表主键列也叫 `id`，裸写 `WHERE id = id` 会让 MySQL 把左右两侧都解析为过程的局部形参，条件恒为真（相当于 `WHERE 1 = 1`），不仅无法匹配目标行，还会因查出多条记录试图填充单行标量变量而抛出 `Result consisted of more than one row`。最佳工程规范是为数据表指定别名并在条件中使用 `b.id = id`。
* **形参数据类型的精度匹配**
    * 底层 `employees` 表的 `salary` 字段定义为 `DOUBLE(8,2)`，把输出参数声明为 `DECIMAL(10,2)` 能顺利创建并调用成功，因为 MySQL 内部支持从 `DOUBLE` 到 `DECIMAL` 的兼容隐式转换。
    * 潜在隐患：源字段精度范围较大（如 `DECIMAL(15,2)`）而形参范围较小（如 `DECIMAL(8,2)`）时，实际数值超过 8 位会在 `INTO` 写入时发生数值溢出截断异常；遇到不支持隐式转换的复杂类型会直接崩溃。
    * 形参长度也应与底层表目标列保持一致或略小：若把形参定义为 `VARCHAR(35)` 而表列是 `VARCHAR(25)`，调用方传入 30 字符密码时入口校验能通过，但内部 `INSERT` 会因超出列最大容量抛出数据截断错误（`Data truncation / String data, right truncated`）。
    * 结论：定义入参与出参类型时必须先用 `DESC 表名;` 严谨核验物理表的原始字段类型与长度，参数规格应与物理列严格一致或适当放宽，绝不可随意收窄。
* **过程的五种参数模式实现骨架**
    * 无参：`CREATE PROCEDURE select_all_data() BEGIN SELECT * FROM employees; END $`，调用 `CALL select_all_data();` 返回 107 条完整记录。
    * 无参聚合：`avg_employee_salary()` 内部 `SELECT AVG(salary) AS avg_sal FROM employees;`，调用后服务端直接返回 `6461.68`。
    * 纯 `OUT`：`show_min_salary(OUT ms DOUBLE(8,2))` 内部 `SELECT MIN(salary) INTO ms FROM employees;`，调用 `CALL show_min_salary(@ms);` 后 `SELECT @ms;` 输出 `2100.00`。
    * 纯 `IN`：`show_someone_salary(IN emp_name VARCHAR(20))` 内部 `WHERE last_name = emp_name`。
    * `IN` + `OUT` 复合：`show_someone_salary2(IN emp_name VARCHAR(20), OUT emp_salary DECIMAL(10,2))`，调用 `CALL show_someone_salary2(@emp_name, @emp_salary);`。
    * `INOUT` 双向：`show_mgr_name(INOUT emp_name VARCHAR(25))` 内部先用子查询按 `last_name = emp_name` 查出 `manager_id`，再按该编号查主管 `last_name` 并 `INTO emp_name` 覆写；`SET @emp_name := 'Abel'; CALL show_mgr_name(@emp_name);` 后变量由 `'Abel'` 变为 `'King'`。
    * 等价自连接写法：`SELECT mgr.last_name INTO emp_name FROM employees emp JOIN employees mgr ON emp.manager_id = mgr.employee_id WHERE emp.last_name = emp_name;`。
* **练习环境与关键实测值**
    * 测试库 `dbtest15`（`CHARACTER SET 'utf8mb4'`）中克隆得到 107 条员工记录与 27 条部门记录。
    * 练习库 `test15_pro_func` 建 `admin(id, user_name, pwd)` 与 `beauty(id, name, phone, birth)`；`beauty` 初始灌入朱茵、孙燕姿、田馥甄、邓紫棋、刘涛、杨超越 6 条数据。
    * 单行函数联动：`date_diff('1992-10-30','1992-09-08', @diff_days)` 得到 52 天（`DATEDIFF` 用第一表达式减第二表达式，前者早于后者则为负数）。
    * 日期格式化 `DATE_FORMAT(mydate, '%Y年%m月%d日')`：`%Y` 四位年份、`%y` 两位年份缩写、`%m` 两位数字月份、`%d` 两位日期；逆向解析用 `STR_TO_DATE(str, format)`。
    * 分页封装 `beauty_limit(IN startIndex INT, IN size INT)` 内部 `SELECT * FROM beauty LIMIT startIndex, size;`，`CALL beauty_limit(1, 3);` 直接返回孙燕姿、田馥甄、邓紫棋三条记录。
    * 存储过程并非必须通过 `OUT` 回传数据，过程体内未加 `INTO` 的 `SELECT` 会把结果集直接推送到客户端。
    * > **易错点**：设计用户数据表时密码字段 `pwd` 绝不能设置 `UNIQUE` 唯一性约束，现实中不同用户密码完全可能相同，盲目加唯一约束会导致相同密码时抛冲突异常。

## 存储过程与存储函数的定义语法


### DDL 语法骨架与特征选项

* **存储过程语法骨架**
    * `CREATE PROCEDURE 存储过程名([IN|OUT|INOUT 参数名 参数类型, ...]) [characteristics ...] BEGIN 存储过程体 END`。
    * 四大部分：声明头（`CREATE PROCEDURE` 与过程名）、形参列表（逗号分隔，含参数模式、参数名与合法数据类型）、特征选项集合、由 `BEGIN ... END` 围合的过程体。
* **特征选项（characteristics）逐项语义**
    * `LANGUAGE SQL`：指明过程体由标准 SQL 编写，是当前默认选项，也是目前唯一受支持的语言选项。
    * `DETERMINISTIC` / `NOT DETERMINISTIC`：确定性指示符，前者表示相同实参下多次执行结果必然完全一致，后者表示相同输入可能产生不同结果（如内部调用 `UUID()`、`RAND()` 或读取频繁变更的物理表）。
    * `CONTAINS SQL`：子程序含 SQL 语句，但既不读取也不修改物理表（如纯数值或字符串运算），这是系统**默认值**。
    * `NO SQL`：子程序内部完全不包含任何 SQL 语句。
    * `READS SQL DATA`：子程序内部只包含数据读取操作。
    * `MODIFIES SQL DATA`：子程序内部包含数据写操作（`INSERT`、`UPDATE`、`DELETE`）。
    * `SQL SECURITY { DEFINER | INVOKER }`：前者为**默认模式**，过程始终以创建者身份和权限运行，只要定义者具备权限且授予调用者 `EXECUTE`，调用者即可安全执行；后者以当前发起调用的用户权限运行，调用者若没有底层物理表权限，即便有过程执行权限，过程内访问物理表时仍会抛「权限不足（Access Denied）」。
    * `COMMENT '描述说明字符串'`：业务功能描述，元数据会持久化在系统字典表 `information_schema.ROUTINES` 中。
    * 若未显式指定确定性特征，系统默认按 `NOT DETERMINISTIC` 处理；在开启二进制日志主从复制的高可用环境中，某些函数或过程必须显式声明确定性特征，否则会被引擎拒绝创建。
* **存储函数语法骨架与两项语法铁律**
    * `CREATE FUNCTION 函数名([参数名 参数类型, ...]) RETURNS 返回值类型 [characteristics ...] BEGIN 函数体（必须包含有效的 RETURN 语句） END`。
    * 铁律一：函数头部（小括号之后、`BEGIN` 之前）用复数形式的 `RETURNS` 后跟返回值数据类型（如 `RETURNS VARCHAR(25)`、`RETURNS INT`）；函数体内部（`BEGIN ... END` 之间）用动词单数形式的 `RETURN` 后跟表达式、变量或查询结果（如 `RETURN (SELECT email ...)`），二者混淆直接触发语法分析错误。
    * 铁律二：形参定义格式为 `(param_name type, ...)`，**不能也不允许书写 `IN`、`OUT` 或 `INOUT` 关键字**，系统默认且唯一支持入参模式。
* **存储函数实战案例与实测值**
    * `email_by_name()`：`RETURNS VARCHAR(25)` 内 `RETURN (SELECT email FROM employees WHERE last_name = 'Abel');`，调用 `SELECT email_by_name();` 输出 `"HABEL"`。
    * `email_by_id(emp_id INT)`：按 `WHERE employee_id = emp_id` 返回邮箱，支持 `SELECT email_by_id(100);` 传常量与 `SET @emp_id := 102; SELECT email_by_id(@emp_id);` 传变量两种范式。
    * `count_by_id(dept_id INT)`：`RETURNS INT`，返回 `SELECT COUNT(*) FROM employees WHERE department_id = dept_id`，`@dept_id = 30` 时输出 6，`@dept_id = 50` 时输出 45。
    * 课后函数练习实测：`get_count()` 返回 107；`ename_salary('Abel')` 返回 `11000.0`；`dept_sal('Marketing')` 返回 `9500.000000`；`add_float(12.2, 2.3)` 返回 `14.5`（纯逻辑计算只需声明 `NO SQL`）。
    * 存储函数内部同样可以使用以 `@` 引导的会话用户变量：`SET @sal = 0.0; SELECT salary INTO @sal FROM employees WHERE last_name = emp_name; RETURN @sal;`，函数执行结束后外部 `SELECT @sal;` 依然能读到 `11000`。

### DELIMITER 重定义与 1418 报错

* **默认分号与复合语句块的截断冲突**
    * 标准 MySQL 交互客户端（原生终端、SQLyog、Navicat）默认把分号 `;` 硬编码为单条 SQL 的结束终止符，扫描到分号便立刻把前面的文本打包推送服务端执行。
    * 过程体是由 `BEGIN ... END` 围合的复合语句块，内部每条独立语句按规范必须以分号结尾；客户端读到内部第一个分号就强行截断并提交，服务端收到残缺结构直接抛 `1064` 语法错误（缺少匹配的 `END`）。
* **`DELIMITER` 的工作时序与工程规约**
    * 时序：客户端默认结束符为 `;` → `DELIMITER //` 把结束符重定义为 `//` → 过程体内遇分号客户端忽略并继续吞吐 → `END //` 时客户端判定复合 DDL 结束整体打包发送编译 → `DELIMITER ;` 立即恢复标准分号。
    * 推荐结束符为 `$`、`$$` 或 `//`；**绝不能使用反斜杠 `\`**，因为它在 MySQL 语法与多数宿主语言中具有转义字符语义，会导致后续解析器发生严重转义混淆与不可预测的崩溃。
    * 随借随还规范：只要使用了 `DELIMITER` 改变符号，创建完存储对象后的第一行必须无条件写上 `DELIMITER ;`，否则后续执行普通 `SELECT`、`UPDATE` 脚本时客户端会因迟迟找不到自定义符号而持续挂起等待。
    * 触发器内部同样包含多条以分号结尾的 SQL，创建触发器前后也必须用 `DELIMITER` 修改结束标记。
* **1418 报错的物理根源**
    * 未声明任何特征选项直接创建存储函数，抛错：`Error Code: 1418. This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)`。
    * 根源在二进制日志（Binary Log，binlog）与主从复制一致性校验：默认开启 binlog 的环境中，主库上执行的变更与函数调用都会记录并同步到从库重放；若函数内部含写操作或属于非确定性逻辑（含 `NOW()`、`UUID()`、`RAND()` 或读取动态变更的表），主库执行与从库重放的结果可能完全不同，导致主从数据分裂。
    * MySQL 因此默认开启严格防护：除非在函数定义中明确声明行为特征，或全局明确允许信任函数创建者，否则严禁创建存储函数；创建存储过程时省略 `characteristics` 则能平稳执行。
* **两种合规解决方案**
    * 方案一（精准控制）：在 `RETURNS` 之后、`BEGIN` 之前显式书写特征声明，常用组合为 `DETERMINISTIC`（相同输入始终对应相同输出）+ `CONTAINS SQL`（函数体包含标准 SQL 语句）+ `READS SQL DATA`（只读取 SQL 数据不执行写操作），追加后脚本顺利创建，1418 报错完全消除。
    * 方案二（快速开发）：修改系统变量 `log_bin_trust_function_creators`，其默认值为 `0`（`OFF`）表示严格校验函数创建者，置为 `1`（`ON`）表示放宽校验、信任所有具备创建权限的用户，允许不声明特征直接创建。命令为 `SHOW VARIABLES LIKE 'log_bin_trust_function_creators';` 与 `SET GLOBAL log_bin_trust_function_creators = 1;`（需管理员权限）。
    * > **易错点**：该系统变量若未写入 `my.cnf` 配置文件，MySQL 服务重启后会重置为 `0`，必须重新执行开启。

## 存储程序与触发器的运维管理


### 例程元数据的三种查看途径

* **方式一：`SHOW CREATE` 查看创建源码**
    * 语法 `SHOW CREATE { PROCEDURE | FUNCTION } 存储过程名或函数名;`，与 `SHOW CREATE TABLE`、`SHOW CREATE VIEW` 一脉相承，直接提取创建该例程时的完整 DDL 代码。
    * 返回字段：`Procedure` / `Function`（对象名与类别）、`sql_mode`（创建时绑定的 SQL 运行模式，如是否遵循 `STRICT_TRANS_TABLES` 等严格模式）、`Create Procedure` / `Create Function`（完整可执行代码体，含参数列表、定义者说明与 `BEGIN ... END` 块）、`character_set_client` 与 `collation_connection`（创建时客户端连接的字符集与比对校对规则，用于跨环境迁移保持一致）。
    * 图形化工具会把创建语句塞进一个单元格平铺在一行，阅读体验差；建议在命令行走 `\G` 把每列按行折叠展示。
* **方式二：`SHOW STATUS` 查看状态信息**
    * 语法 `SHOW { PROCEDURE | FUNCTION } STATUS [LIKE '匹配模式'];`；不加 `LIKE` 会把当前实例中所有数据库（含系统自带库）下的全部过程或函数尽数罗列。
    * `LIKE` 天然支持通配符：`%` 匹配任意多个字符，`_` 匹配单个字符，如 `SHOW PROCEDURE STATUS LIKE '%salary%';`。
    * 状态字段语义：`Db` / `Name` / `Type`（库名、对象名与类型）、`Definer`（对象定义者，默认是创建该对象的账户如 `root@localhost`）、`Created` / `Modified`（创建时间与最后一次修改特性的时间，创建后从未执行 `ALTER` 则两时间戳相同）、`Security_type`（默认 `DEFINER`）、`Comment`（未显式声明则为空）。
* **方式三：检索 `information_schema.ROUTINES`**
    * MySQL 把所有元数据以关系表形式暴露在 `information_schema` 字典库中，例程元数据集中存储在 `ROUTINES` 表中，支持标准 `SELECT ... WHERE` 自由过滤与组合检索，字段比前两种方式更丰富。
    * 过程与函数同名时单靠 `ROUTINE_NAME` 会把两者同时查出，需借助 `ROUTINE_TYPE` 字段过滤：`WHERE ROUTINE_NAME = 'email_by_id' AND ROUTINE_TYPE = 'FUNCTION';`。
    * > **易错点**：常规字符串比对通常默认不区分大小写，但 `ROUTINE_TYPE` 字段对大小写有强约束；写成小写 `'function'` 将无法命中记录、返回空结果集，必须严格使用大写 `'FUNCTION'` 或 `'PROCEDURE'`。
* **三种查看方式的选型对照**

    | 查看方式 | 语法形式 | 核心优势 | 局限性 / 适用场景 |
    | :--- | :--- | :--- | :--- |
    | `SHOW CREATE` | `SHOW CREATE {PROCEDURE\|FUNCTION} name` | 直接获取底层完整的可执行 DDL 源码 | 无法查看修改历史与执行上下文概览，适合排查与复制源码 |
    | `SHOW STATUS` | `SHOW {PROCEDURE\|FUNCTION} STATUS [LIKE '...']` | 清晰展示生命周期元数据（时间戳、权限属性、注释） | 不显示例程内部代码体，适合服务巡检与状态比对 |
    | `ROUTINES` 系统表 | `SELECT * FROM information_schema.ROUTINES` | 字段最全面，支持灵活的组合条件筛选与关联查询 | 字段项极多、全表查询开销较大，类型匹配严格区分大小写 |

* **触发器的三种查看方式**
    * `SHOW TRIGGERS;` 列出当前上下文数据库中定义的所有触发器，输出字段含 `Trigger`、`Event`（`INSERT` / `UPDATE` / `DELETE`）、`Table`（绑定的数据表）、`Statement`（`BEGIN ... END` 之间的程序体）、`Timing`（`BEFORE` 或 `AFTER`）、`Created`、`sql_mode`、`Definer`、`character_set_client`、`collation_connection`。
    * > **易错点**：`SHOW TRIGGERS` 列出触发器的顺序并不严格等于创建先后顺序，核实确切创建时序应以 `Created` 时间戳字段为准。
    * `SHOW CREATE TRIGGER 触发器名称;` 返回 `Trigger`、`sql_mode`、`SQL Original Statement`（当初创建的原始 DDL，含 `CREATE DEFINER=... TRIGGER ...`、时机、`FOR EACH ROW` 与完整 `BEGIN ... END` 体）以及客户端字符集元数据。
    * `SELECT * FROM information_schema.TRIGGERS;` 支持条件筛选与跨库检索，常用投影字段为 `TRIGGER_SCHEMA`、`TRIGGER_NAME`、`EVENT_MANIPULATION`、`EVENT_OBJECT_TABLE`、`ACTION_TIMING`、`CREATED`。
    * > **易错点**：命令行使用 `\G` 时末尾严禁再加分号，否则引发语法错误；图形化工具（如 SQLyog）往往无法解析 `\G`，在 GUI 中直接用分号结尾即可。

### 例程与触发器的修改与删除

* **`ALTER` 的修改边界**
    * 语法 `ALTER { PROCEDURE | FUNCTION } 存储过程或函数名 [characteristic ...];`，可修改项为 `CONTAINS SQL`、`NO SQL`、`READS SQL DATA`、`MODIFIES SQL DATA`、`SQL SECURITY { DEFINER | INVOKER }`、`COMMENT 'string'`。
    * > **易错点**：`ALTER PROCEDURE` 与 `ALTER FUNCTION` **绝不能用于修改过程体或函数体内部的业务 SQL 逻辑**，参数列表（`IN` / `OUT` / `INOUT` 变量定义）与 `BEGIN ... END` 内部的控制流也绝对禁止修改。
    * 业务代码变更的唯一路径是先 `DROP` 删除再重新 `CREATE`。
    * 修改效果验证：执行 `ALTER PROCEDURE show_max_salary SQL SECURITY INVOKER COMMENT '查询员工表中的最高工资信息';` 后，`SHOW PROCEDURE STATUS LIKE 'show_max_salary';` 显示 `Security_type` 由 `DEFINER` 变为 `INVOKER`、`Comment` 由空值更新为指定文本、`Modified` 时间戳刷新为最新执行时间而 `Created` 保持不变。
* **`DROP` 语法与 `IF EXISTS` 防护**
    * 例程删除：`DROP { PROCEDURE | FUNCTION } [IF EXISTS] 存储过程或函数名;`，必须明确声明被删除对象是 `PROCEDURE` 还是 `FUNCTION`。
    * 触发器删除：`DROP TRIGGER [IF EXISTS] [schema_name.]trigger_name;`，与删表、删视图、删存储过程遵循完全相同的 DDL 风格。
    * 未加 `IF EXISTS` 且目标不存在时，MySQL 立即中断并抛 `Error Code: 1305. FUNCTION/PROCEDURE ... does not exist`（触发器删除报类似的类型拼写错误），在自动化部署或批处理脚本中会中断整个脚本链条；加 `IF EXISTS` 后目标不存在则降级为一条警告而主流程继续。
* **触发器废弃必须显式删除**
    * 存储过程与函数只要应用层不显式 `CALL` 或 `SELECT`，就仅以静态元数据形式留在数据字典中，除占用极微量磁盘空间外不产生运行副作用。
    * 触发器隐匿性强（无需显式调用，只要目标表发生对应 DML 就会被引擎强制拦截并自动触发），破坏性强（业务逻辑变动后废弃触发器仍在暗中被动激活，极易导致数据被旧逻辑篡改或在主业务流程中抛出不明异常）。
    * 结论：触发器一旦确定废弃，必须第一时间 `DROP TRIGGER` 彻底移出数据库，绝不能采取「留着不调它」的侥幸心理。
* **触发器遗留引发的间接故障**
    * 应用层发起 `INSERT INTO t_note VALUES (...)` 却报 `ERROR 1406 (22001): Data too long for column 'remark' at row 1`——传入字符串仅 20 字符而 `t_note` 字段允许 50 字符，真正原因是该表挂载的触发器往日志表 `t_log` 写入，而 `t_log` 的 `remark` 字段长度仅为 10。
    * 另一类故障：用户只更新会员余额字段却报「不存在字段 A」，开发者误以为原表缺字段而盲目添加，实际是触发器内部 SQL 写错了关联目标表的字段名。
    * 触发器把多个表紧耦合：被触发表或关联表的字段名修改、字段删除、类型变更时触发器不会在表结构变更瞬间报错，而是在后续任意一笔正常业务写入抵达该表时骤然崩溃，进而导致主业务事务全盘回滚。

## 变量体系与错误处理机制


### 系统变量的作用域与生命周期

* **系统变量的来源与实例绑定**
    * 系统变量由 MySQL 官方系统预先定义，在体系结构上归属于**服务器层面**，不是用户写 SQL 时随意命名的。
    * 启动 `mysqld` 服务进程生成运行实例时，加载顺序为：先加载源码编译内置的硬编码默认参数（Hardcoded Defaults），再读取并覆盖配置文件参数（Windows 为 `my.ini`，Linux 为 `my.cnf`），最后初始化全局系统变量池。
    * 版本规模：MySQL 5.7 全局系统变量约 500 多个；MySQL 8.0 全局系统变量 617 个、会话系统变量 640 个，无需逐一死记，掌握作用域规则与高频核心变量即可。
    * 启动命令示例：Windows 下 `net start mysql80`，Linux 下 `systemctl start mysqld`。
* **GLOBAL 与 SESSION 的集合模型**
    * 全局系统变量在整个数据库实例级别生效，对连接当前实例的所有客户端会话起作用；会话系统变量（SESSION / LOCAL）仅在当前客户端连接会话中生效，每个客户端拥有自身独立的局部副本。
    * 纯全局变量（仅属集合 A）：如 `max_connections`（实例允许承载的最大客户端并发连接数），单独在某个会话中讨论「本会话的最大连接数」毫无语义。
    * 纯会话变量（仅属集合 B）：如 `pseudo_thread_id`（当前会话在 MySQL 内部被分配的线程连接 ID），每个客户端线程编号唯一，全局不存在通用的统一连接 ID。
    * 双重变量（属交集 A ∩ B）：如 `character_set_client`（客户端发送 SQL 的字符集编码）、`autocommit`（是否开启事务隐式自动提交）。实例启动时全局池中该变量被赋初值；任一客户端建立会话时，MySQL 以全局变量当前值作为模板为新会话复制一份独立副本；此后某会话把它改成 `gbk` 只作用于自身副本，既不污染全局池也不影响并行会话。
* **系统变量的三层查看方案**
    * 全量查看：`SHOW GLOBAL VARIABLES;`（MySQL 8.0 约 617 条）、`SHOW SESSION VARIABLES;`（约 640 条）；省略作用域关键字的 `SHOW VARIABLES;` 默认且永远匹配**当前会话（SESSION）**级别。
    * 模糊筛选：`SHOW GLOBAL VARIABLES LIKE 'admin_%';`、`SHOW VARIABLES LIKE 'character_%';`（`%` 匹配任意多个字符，`_` 匹配单个字符）。
    * 精准单值检索：`SELECT @@global.max_connections;`、`SELECT @@session.character_set_client;`（`session` 亦可写为 `local`）。
    * 词法隔离设计：双 `@` 符（`@@`）严格且唯一用于标识系统变量，单 `@` 符（`@`）严格用于标识用户自定义会话变量。
    * 缺省匹配规则：执行 `SELECT @@变量名;` 不指定作用域前缀时，优先检索会话级变量池，若该变量不存在会话级别（属纯全局变量）则自动退化为读取全局值。
    * > **易错点**：作用域越界会被引擎阻断——`SELECT @@session.max_connections;` 报 `Variable 'max_connections' is a GLOBAL variable`；`SELECT @@global.pseudo_thread_id;` 报 `Variable 'pseudo_thread_id' is a SESSION variable`。
* **修改的两条路径与生命周期**
    * 途径一（静态配置文件）：在 `my.ini` / `my.cnf` 的 `[mysqld]` 段直接编辑键值对（如 `max_connections = 200`、`character-set-server = utf8mb4`），保存后必须重启 MySQL 服务进程，实例重新引导时挂载配置文件作为全局基准长久生效；软肋是生产环境不允许随意停机重启，破坏高可用 SLA。
    * 途径二（运行时 `SET`）：全局变量可用 `SET @@global.max_connections = 161;` 或 `SET GLOBAL max_connections = 171;`（两种语法功能完全等价）；会话变量可用 `SET @@session.character_set_client = 'gbk';`、`SET SESSION character_set_client = 'gbk';` 或缺省前缀的 `SET character_set_client = 'gbk';`。
    * 实测：修改后 `SELECT @@global.max_connections;` 立即从 `151` 刷新为 `171`，此后新建连接受新上限约束；执行 `net stop mysql80` 与 `net start mysql80` 重启后再次查询，变量重新变回配置文件或系统默认的 `151`。
    * 会话级验证：会话 A 执行 `SET SESSION character_set_client = 'gbk';` 后自身查出 `gbk`；同工具新建会话 B 查出的仍是默认的 `utf8mb3` 或 `utf8mb4`，不受影响；会话 A 查全局值依然岿然不动；关闭会话 A 重连后会话级变量重新继承全局池默认配置，临时修改彻底失效。
    * 结论：`SET GLOBAL` 修改的值仅在当前运行的内存实例中存活，实例重启后内存池重构，未落盘到配置文件的修改彻底蒸发。

| 比较维度 | 全局系统变量（GLOBAL） | 会话系统变量（SESSION） |
| :--- | :--- | :--- |
| 所属层级 | 归属于整个 MySQL 服务器实例 | 归属于单个客户端连接 |
| 初始化时机 | 服务启动、实例初始化时加载 | 客户端与服务端建立 TCP 连接并初始化会话时生成 |
| 默认初始值来源 | 源码编译默认值或 `my.cnf` / `my.ini` 配置文件 | 从当前全局系统变量池中完整克隆继承 |
| 查看全量语法 | `SHOW GLOBAL VARIABLES;` | `SHOW SESSION VARIABLES;` 或 `SHOW VARIABLES;` |
| 单值检索语法 | `SELECT @@global.var_name;` | `SELECT @@session.var_name;` 或 `SELECT @@var_name;` |
| 动态修改语法 | `SET GLOBAL var = val;` / `SET @@global.var = val;` | `SET SESSION var = val;` / `SET var = val;` |
| 修改作用半径 | 影响当前实例及后续所有新建会话 | 仅影响当前会话自身，对其他会话完全隔离 |
| 修改生命周期 | 持续至服务进程关闭，重启后立即失效 | 持续至连接中断退出，断开后立即失效 |
| 典型配置场景 | `max_connections`、缓冲区与连接池大小调优 | `character_set_client`、事务隔离级别与自动提交微调 |


### 用户自定义变量的两大阵营

* **词法前缀与作用域拓扑**
    * 系统变量：`@@global.var_name` 或 `@@session.var_name`，作用域为服务器全局实例 / 客户端连接会话。
    * 会话用户变量：`@var_name`（单 `@`），作用域为当前客户端连接全局有效，特征为弱类型、无需声明、随连接存活、断开连接即销毁。
    * 局部变量：`var_name`（完全不带 `@` 的裸标识符），仅在 `BEGIN ... END` 复合语句块内部有效，特征为强类型、必须在块首行 `DECLARE` 声明、退出块立即消亡。
    * 局部变量不需要 `@` 的原因：它是严格封闭在存储过程或函数 `BEGIN ... END` 内部的私有变量，离开代码块后外部世界感知不到它的存在，可见性被限制在块作用域内，不会与外层全局变量或会话变量产生命名冲突。
* **会话用户变量的声明与赋值**
    * `SET @用户变量名 = 表达式 [, @用户变量名2 = 表达式2 ...];` 或过程化推荐的 `SET @用户变量名 := 表达式;`。
    * 支持复合表达式与连续赋值：`SET @sum := @m1 + @m2;`，随后 `SELECT @sum;` 输出 `3`。
    * 结合 `SELECT` 注入查询结果：投影列表赋值 `SELECT @count := COUNT(*) FROM employees;` 得到 107；标准 `INTO` 语法 `SELECT AVG(salary) INTO @avg_sal FROM employees;` 得到 `6461.682243`（工程推荐）。
    * > **提示**：等号 `=` 既可作为比较运算符又可作为赋值运算符，为消除二义性，进行变量赋值时强烈建议养成使用 `:=` 赋值符的习惯。
* **会话用户变量的内存存活机制**
    * 跨语句持久性：一旦被赋值，即便执行完后续成百上千行其他 SQL，该变量依然常驻在客户端连接对应的服务器内存中，随时可通过 `SELECT @sum;` 调取。
    * 连接断开即销毁：关闭客户端工具、重启连接窗口或会话超时断开后，分配给该连接的内存池被完全回收，之前定义的所有会话用户变量随之灰飞烟灭。
    * > **易错点**：在新会话中读取未初始化的变量（如 `SELECT @sum;`）MySQL 直接返回 `NULL` 而不会报错。
* **局部变量的四大语法铁律**
    * 铁律一：必须使用 `DECLARE` 关键字显式声明，语法为 `DECLARE 变量名 [, 变量名2 ...] 数据类型 [DEFAULT 默认值];`。
    * 铁律二：必须声明在 `BEGIN ... END` 复合语句块内部。
    * 铁律三：必须置于 `BEGIN` 块的最顶部（首行位置），严禁出现在业务代码之后。
    * 铁律四：必须显式指定数据类型（强类型校验，如 `INT`、`VARCHAR(25)`、`DOUBLE(10,2)`、`DATE`），向其写入不兼容类型会触发类型转换失败或截断报错。
    * 默认值机制：未显式书写 `DEFAULT` 子句时，局部变量声明后的初始默认值一律为 `NULL`。
    * 合并声明：类型与默认值完全一致的多个变量可在同一行用逗号分隔声明，`DECLARE a, b INT DEFAULT 0;` 等价于分别声明两行。
    * > **易错点**：`DECLARE` 必须紧跟在 `BEGIN` 之后、写在所有业务逻辑（如 `SELECT`、`UPDATE`、`IF`）最前列；在一条业务 SQL 之后再写 `DECLARE`，解析器直接报 `1064 Syntax Error`。
* **局部变量的赋值与实战流转**
    * 赋值方式一 `SET 变量名 = 表达式;` 或 `SET 变量名 := 表达式;`；方式二 `SELECT 列名 INTO 局部变量名 FROM 表名 WHERE 过滤条件;`。
    * 综合演示 `test_var()`：块首声明 `DECLARE a INT DEFAULT 0;`、`DECLARE b INT;`、`DECLARE emp_name VARCHAR(25);`，赋值后 `CALL test_var();` 输出 `a = 1`、`b = 2`、`emp_name = 'Kochhar'`。
    * 变量规划示例 `different_salary(IN emp_id INT, OUT dif_salary DOUBLE)`：声明 `emp_sal DOUBLE DEFAULT 0.0`、`mgr_sal DOUBLE DEFAULT 0.0`、`mgr_id INT DEFAULT 0`，先 `SELECT salary, manager_id INTO emp_sal, mgr_id`，再按 `mgr_id` 查 `mgr_sal`，最后 `SET dif_salary = mgr_sal - emp_sal;`。
    * 数据溯源验证：102 号员工自身 `salary = 17000`、`manager_id = 100`，100 号员工（King）`salary = 24000`，`CALL different_salary(102, @res_diff);` 得 `7000.0`；103 号员工 `salary = 9000`、主管为 102 号（17000），调用得 `8000.0`。
    * 数值求和的两种实现：会话用户变量方案 `SET @v1 = 10; SET @v2 = 20; SET @result := @v1 + @v2;` 输出 30；局部变量方案把 `DECLARE value1, value2, sum_var INT DEFAULT 0;` 封进存储过程 `add_value()`，调用输出 110。

| 比较维度 | 会话用户变量（Session User Variable） | 局部变量（Local Variable） |
| :--- | :--- | :--- |
| 词法命名规则 | 必须以单个 `@` 符号开头（如 `@my_var`） | 绝对不带 `@` 符号，直接写变量名 |
| 作用域范围 | 当前客户端连接（会话）内的任何地方 | 仅在定义它的 `BEGIN ... END` 复合语句块内部有效 |
| 声明关键字 | 无需显式声明，随用随赋 | 必须使用 `DECLARE` 显式声明 |
| 定义位置约束 | 会话中任意 SQL 语句位置均可直接定义 | 必须强制位于 `BEGIN ... END` 块的最顶部（首行） |
| 数据类型系统 | 弱类型，由运行时根据赋值动态推导 | 强类型，声明时必须显式指定底层数据类型 |
| 默认初始值 | 未定义直接引用时为 `NULL` | 未指定 `DEFAULT` 子句时为 `NULL` |
| 内存生命周期 | 伴随整个会话连接，连接断开时才被销毁 | 伴随过程/函数执行，退出 `BEGIN ... END` 块立即销毁 |
| 典型适用场景 | 接收存储过程的 `OUT` 参数、跨语句传递状态 | 过程/函数内部中间计算、循环计数、游标暂存 |


### 错误处理的双环节设计

* **默认未捕获异常的中断行为**
    * > 结论：默认情况下，存储过程或存储函数执行过程中一旦遭遇任何未捕获的错误（Error），执行引擎会**立刻强行终止整个程序的运行**，直接向调用方抛出错误代码，后续所有业务逻辑被全部截断。
    * 探针验证：`UpdateDataNoCondition()` 中 `SET @x = 1;` 后执行 `UPDATE employees SET email = NULL WHERE last_name = 'Albert';` 触发 `ERROR 1048 (23000): Column 'email' cannot be null`，随后 `SET @x = 2;`、第二条 `UPDATE`、`SET @x = 3;` 全部未执行，`SELECT @x;` 结果为 `1`。
    * 另一例：`departments` 追加 `UNIQUE(department_id)` 后连续两次插入 `'测试部'`，第二条触发 `ERROR 1062 (23000): Duplicate entry ...`，无保护时变量 `@x` 定格在 `2`，探针 3 未能执行。
* **错误处理机制的双环节架构**
    * 环节一「定义条件（Declare Condition）」：事先为可能遭遇的具体错误或警告设定具有语义化的标识符（起别名），把抽象晦涩的代码转换为见名知意的符号；属可选修饰型特性。
    * 环节二「定义处理程序（Declare Handler）」：为特定条件（或底层原始错误码）预先指定应对策略并绑定补救动作（如重置状态标志、记入审计日志或触发级联回退）。
    * 该机制在存储过程与存储函数中均得到原生支持，开发者也可跳过定义条件直接用原始 `mysql_error_code` 或 `SQLSTATE` 绑定处理程序。
* **错误标识的双轨制**
    * 一条错误信息的构成：`ERROR 1048 (23000): Column 'email' cannot be null`——错误等级（`Error Level`）、MySQL 专有错误码（`mysql_error_code`）、ANSI SQL 标准状态码（`sqlstate_value`）、错误描述文本（`Error Message`）。
    * `mysql_error_code`：MySQL 内部专属定义的错误代号，数值型（Integer），典型如 `1048`、`1062`、`1148`、`1364`，仅适用于 MySQL 自身体系。
    * `sqlstate_value`：符合 ANSI SQL 与 ODBC 标准的国际规范状态码，定长 5 位字符串型（`CHAR(5)`），典型如 `'23000'`、`'42000'`、`'HY000'`，具备通用标准语义便于跨数据库栈识别。
* **六类错误类型匹配规则**

    | 分组 | 匹配源 | 写法示例 | 语义 |
    | :--- | :--- | :--- | :--- |
    | 通用精准匹配 | 数值型 `mysql_error_code` | `DECLARE CONTINUE HANDLER FOR 1048 SET @flag = -1;` | 直接指定具体错误编号 |
    | 通用精准匹配 | 字符型 `SQLSTATE [VALUE] sqlstate_value` | `DECLARE EXIT HANDLER FOR SQLSTATE '23000' SET @flag = -1;` | 指定标准 5 位状态码 |
    | 通用精准匹配 | 自定义 `condition_name` | `DECLARE EXIT HANDLER FOR duplicate_entry SET @flag = -1;` | 引用前置 `DECLARE ... CONDITION` 定义的条件名 |
    | 前缀通配 | `SQLWARNING` | `DECLARE EXIT HANDLER FOR SQLWARNING SET @flag = -1;` | 通配所有以 `'01'` 开头的 SQLSTATE（警告） |
    | 前缀通配 | `NOT FOUND` | `DECLARE EXIT HANDLER FOR NOT FOUND SET @flag = -1;` | 通配所有以 `'02'` 开头的 SQLSTATE（查找不到） |
    | 前缀通配 | `SQLEXCEPTION` | `DECLARE EXIT HANDLER FOR SQLEXCEPTION SET @flag = -1;` | 通配除 `SQLWARNING` 与 `NOT FOUND` 外的所有错误 |


### 定义条件与处理程序的语法规范

* **定义条件语法与参数规范**
    * 语法：`DECLARE condition_name CONDITION FOR condition_value;`。
    * `condition_value` 两种合法形式：数值型 `mysql_error_code`（直接填写整数值，不需要加引号）；字符串型 `SQLSTATE [VALUE] sqlstate_value`（必须显式声明 `SQLSTATE` 关键字，`VALUE` 可省略，其后跟 5 位定长字符串且必须携带单引号）。
    * 条件名命名必须见名知意（如 `Field_Not_Be_NULL`、`duplicate_entry`），避免含糊代号。
    * > **易错点**：使用字符串型状态码时必须显式书写 `SQLSTATE` 引导词；省略该关键字直接书写字符串或数字，解析器无法辨识类型归属，会引发隐式转换报错或语义分歧。
    * 课堂范例：非空约束异常（`1048` / `'23000'`）命名为 `Field_Not_Be_NULL`，可写 `DECLARE Field_Not_Be_NULL CONDITION FOR 1048;` 或 `DECLARE Field_Not_Be_NULL CONDITION FOR SQLSTATE '23000';`；当前版本不支持指令的异常（`1148` / `'42000'`）命名为 `command_not_allowed`，可写 `DECLARE command_not_allowed CONDITION FOR 1148;` 或 `DECLARE command_not_allowed CONDITION FOR SQLSTATE '42000';`。
* **定义处理程序语法与三种行为**
    * 语法：`DECLARE handler_action HANDLER FOR condition_value [, ...] statement;`。
    * `CONTINUE`：遇到错误后不终止程序，执行完处理程序绑定的语句后跳过引发异常的那一行代码，继续向下执行后面的 SQL 语句。
    * `EXIT`：执行完处理程序绑定的语句后立刻终止并跳出包含该处理程序的 `BEGIN ... END` 复合语句块。
    * `UNDO`：语义为执行回退操作；SQL 标准包含此机制，但**截至当前 MySQL 版本尚未原生支持 `UNDO` 处理动作**，指定 `UNDO` 会抛出不支持的异常，生产实战只能在 `CONTINUE` 与 `EXIT` 之间权衡。
    * `statement` 的组织形态：单一表达式或赋值操作（如 `SET @proc_value = -1;`），或用完整 `BEGIN ... END` 结构包裹多行 SQL（记录异常堆栈、插入日志表、重设多维状态）。
* **DECLARE 的声明顺序刚性约束**
    * 程序体头部声明区的固定顺序为：局部变量声明（`DECLARE var_name ...`）→ 条件声明（`DECLARE cond_name CONDITION ...`）→ 游标声明（`DECLARE cur_name CURSOR ...`）→ 处理程序声明（`DECLARE ... HANDLER FOR ...`）→ 业务可执行 SQL 逻辑。
    * > **易错点**：处理程序声明必须置于程序体的头部声明区，绝不能写在业务执行语句之后；在第一条业务 SQL（如 `SET @x = 1;`）之后再写 `DECLARE HANDLER`，MySQL 语法解析器直接抛语法错误。
* **CONTINUE 与 EXIT 的状态迁移验证**
    * `CONTINUE` 案例：`DECLARE CONTINUE HANDLER FOR 1048 SET @proc_value = -1;`（等价写法 `DECLARE CONTINUE HANDLER FOR SQLSTATE '23000' SET @proc_value = -1;`）配置后调用同一过程，探针 `@x` 依次推进到 `3`，`@proc_value` 为 `-1`，证明异常被拦截、补偿语句被调用、程序跨过错误指令持续推进至最后一行。
    * `EXIT` 案例：`InsertDepartmentDuplicate()` 用 `DECLARE duplicate_entry CONDITION FOR 1062;`（亦可写 `FOR SQLSTATE '23000'`）配合 `DECLARE EXIT HANDLER FOR duplicate_entry SET @error_value = -1;`，第二次插入冲突时立即退出，查询结果为 `@x = 2`、`@error_value = -1`，`SET @x = 3;` 永久未执行。
    * > **提示**：若二次执行该过程时表中已残留上一轮插入的记录，则第一条 `INSERT` 就会触发唯一性冲突，`EXIT` 在第一条插入处即退出，`@x` 停留在 `1`、`@error_value` 依然为 `-1`；结果与执行前后的表内已有数据状态紧密关联。
    * `EXIT` 的三种等价绑定方式：直接绑定数值型 `mysql_error_code`（`FOR 1062`）、直接绑定字符串型 `SQLSTATE '23000'`、先 `DECLARE ... CONDITION` 再由处理程序承接条件名。
* **MySQL 8.0 全局系统变量持久化**
    * 传统痛点：`SET GLOBAL max_connections = 1000;` 只在内存中生效，服务器维护、断电重启或 `mysqld` 崩溃拉起后瞬间丢失并跌回默认的 151；只改配置文件不重启不立刻生效、必须再配合 `SET GLOBAL` 改内存，若只改内存忘记改文件则下次重启依然失效，极易诱发配置飘移（Configuration Drift）。
    * 8.0 引入 `PERSIST` 关键字：`SET PERSIST max_connections = 1000;`。
    * 底层双写机制：先在当前运行实例的内存中应用该配置立即可用；同时在数据存储目录（Data Directory）下创建或更新 `mysqld-auto.cnf`，以 JSON 格式记录该变量与新值；实例未来重启时在读取完常规 `my.cnf` 之后自动追加加载 `mysqld-auto.cnf` 覆盖先前设置，实现一次配置、跨重启永久生效。

## 流程控制：分支结构


### 分支结构 IF

* **过程化 IF 与查询 IF 的辨析**
    * 内置**控制流单行函数** `IF(expr1, expr2, expr3)` 类似三元运算符 `expr1 ? expr2 : expr3`，是带返回值的表达式，常用于 `SELECT` 字段列表。
    * **过程化流程控制语句** `IF ... THEN ... END IF;` 是包含完整控制结构的语句块，用来组织命令执行路径。
    * > **注意**：所有流程控制语句（`IF`、`CASE`、`LOOP`、`WHILE`、`REPEAT`、`LEAVE`、`ITERATE`）只能编写在存储过程、存储函数或触发器的 `BEGIN ... END` 复合代码块内部，绝不能直接书写在交互式的普通 `SELECT` 顶层查询中。
* **IF 语句语法模板与四条语法规则**
    * 模板：`IF search_condition_1 THEN statement_list_1; [ELSEIF search_condition_2 THEN statement_list_2;] ... [ELSE statement_list_n;] END IF;`。
    * 规则一：条件表达式返回 `TRUE`、`FALSE` 或 `NULL`，只有严格求值为 `TRUE` 时才命中对应 `THEN` 语句体。
    * 规则二（短路跳出）：从上至下顺序计算条件，一旦命中首个 `TRUE` 分支并执行完毕，立即跳出整个 `IF` 结构，后续 `ELSEIF` 与 `ELSE` 全部被短路跳过。
    * 规则三（`ELSEIF` 拼写）：中间的多分支关键字必须严密拼写为 **`ELSEIF`（中间无空格）**，拆成 `ELSE IF` 会被解析器理解为一个嵌套内层 `IF` 的起始，导致在最后的 `END IF;` 处抛出类似 `Unterminated statement` 的语法报错。
    * 规则四：整个结构最外层必须用 `END IF;` 作为结束标识符，分号不可遗漏。
* **三大分支形态与执行推导**
    * 单分支 `IF ... THEN ... END IF;`：仅满足条件才做特殊操作，未命中则维持现状。示例 `test_if_01()` 声明未赋初值的 `DECLARE stu_name VARCHAR(15);`（默认 `NULL`），`IF stu_name IS NULL THEN SELECT 'stu_name is null'; END IF;` 输出对应字符串。
    * 双分支 `IF ... THEN ... ELSE ... END IF;`：`test_if_02()` 中 `email` 未初始化时值为 `NULL`，命中主分支输出 `'email is null'`；若用 `DEFAULT` 初始化则流向反转，执行流必将且只能落入 `ELSE` 分支输出 `'email is not null'`。
    * 多路级联 `IF ... ELSEIF ... ELSE ... END IF;`：`test_if_03()` 中 `age` 为 20，`age > 40` 为 `FALSE` 继续推进，`age > 18` 为 `TRUE` 命中并执行 `SELECT '青壮年'`，随后立即短路跳出，`age > 8` 与 `ELSE` 不再被扫描。
* **IF 的应用要点与避坑**
    * 入职年限换算：`DATEDIFF(expr1, expr2)` 的运算逻辑是 `expr1 - expr2`，把 `CURDATE()` 置于首位、`hire_date` 置于次位得到总天数，再除以 365 换算工龄年数，即 $\text{工龄（年）} = \dfrac{\text{DATEDIFF}(\text{CURDATE}(), \text{hire\_date})}{365}$。
    * 组合条件判定：`update_salary_by_eid1(IN emp_id INT)` 中 `IF emp_sal < 8000 AND hire_year > 5 THEN` 命中才 `SET salary = salary + 500`，不满足则不操作直接结束。
    * 分支阶梯的逻辑剪枝：`update_salary_by_eid3` 进入 `ELSEIF` 时第一道门槛 `salary < 9000` 已被排除，天然满足 `salary >= 9000`，因此只需写 `salary < 10000`。
    * 空值判定必须用 `IS NULL`，切禁写成 `= NULL`（`commission_pct` 允许为 `NULL`）。
    * > **易错点**：在存储过程中书写 `UPDATE` 时必须把局部输入参数严格绑定在 `WHERE employee_id = emp_id` 限制条件中；若不慎漏掉过滤子句，将引发全表数据误改的生产事故。
    * 覆盖性实测：`update_salary_by_eid3` 中 104 号（`salary = 7000 < 9000`）命中档位 1 重置为 `9000.00`；103 号（`salary = 9100` 且 `commission_pct IS NULL`）命中档位 2 使 `commission_pct` 变为 `0.01` 而薪资不变；102 号（`salary = 17000`）命中兜底 `ELSE` 递增 100 变为 `17100.00`。
* **IF 语法常见错误对照**

    | 错误类型 | 错误书写习惯 | 正确规范写法 |
    | :--- | :--- | :--- |
    | 关键字连写错误 | `ELSE IF`（拆分写法） | `ELSEIF`（紧凑连写） |
    | 结束标记缺失 | 遗漏 `END IF;` 直接写 `END` | 必须显式书写 `END IF;` |
    | 空值判定错误 | `commission_pct = NULL` | `commission_pct IS NULL` |
    | 作用域混淆 | 在顶级 `SELECT` 中写 `IF` | 仅能在 `BEGIN ... END` 块内 |


### 分支结构 CASE

* **过程化 CASE 语句与查询级 CASE 表达式的分野**
    * 查询级 `CASE` 表达式本质是标量计算表达式（返回单一值），用于交互式 `SELECT` 列表、`WHERE`、`ORDER BY` 等；`THEN` 后跟单一表达式或字面量（如 `'及格'`、`salary * 1.1`）；**`THEN` 后面严禁加分号、整体不以分号结尾**；以 **`END`** 闭合。
    * 过程化 `CASE` 语句本质是流程控制语句（调度多条可执行 SQL），用于存储过程、存储函数、触发器的 `BEGIN ... END` 块内部；`THEN` 后跟完整可执行 SQL（如 `UPDATE`、`SET`、`INSERT`）；每个分支内的语句**必须显式加分号**结尾；必须以 **`END CASE;`** 显式闭合。
    * > **易错点**：在存储过程内部编写过程化 `CASE` 控制流时，若只写 `END` 而漏写 `END CASE;`，解析器会视作未闭合的语法错误。
* **过程化 CASE 的两种语法模式与执行机理**
    * 模式一（简单等值匹配，类似 switch-case）：`CASE case_value WHEN when_value1 THEN statement_list1; [WHEN when_value2 THEN statement_list2;] ... [ELSE statement_list;] END CASE;`。计算主干 `case_value` 的值后依次与各 `WHEN` 后的 `when_value` 做等值比较（`=`），发现相等即执行对应 `THEN` 语句列表并跳出整个 `END CASE;`；全部匹配失败且声明了 `ELSE` 则执行兜底语句。
    * 模式二（条件搜索匹配，类似多重 IF-ELSEIF）：`CASE WHEN search_condition1 THEN statement_list1; [WHEN search_condition2 THEN statement_list2;] ... [ELSE statement_list;] END CASE;`，`CASE` 关键字后不挂接任何变量或表达式，自上而下计算每个 `WHEN` 的布尔表达式，命中 `TRUE` 即执行并跳出。
    * > **易错点**：两种模式下若省略 `ELSE` 且传入值在所有 `WHEN` 中均未命中，MySQL 抛出运行时异常 `ERROR 1339 (20000): Case not found for CASE statement`，导致整个存储程序意外崩溃；工程规范中强烈建议无论何时都显式书写 `ELSE` 兜底分支。
* **CASE 两模式的适用边界与探针验证**
    * 模式二完全无缝替代复杂的 `IF ... ELSEIF ... ELSE`，且在排版上更紧凑清爽；`update_salary_by_eid4` 与其 `IF` 版本 `update_salary_by_eid3` 逻辑等价。
    * 模式二实测：103 号（`salary = 9100` 且有奖金提成非 `NULL`）命中 `ELSE`，薪资 `9100.00 → 9200.00` 而奖金率不变；104 号（`salary = 9000` 且 `commission_pct IS NULL`）薪资维持 `9000.00` 不变而提成率由 `NULL` 变为 `0.01`；105 号（原薪资低于 9000）薪资直接修正保底为 `9000.00`。
    * 模式一要求输入值属于离散有限枚举，适用于根据部门编号、订单状态码分流等场景。
    * 模式一的数据预处理：`DATEDIFF(CURDATE(), hire_date)/365` 计算出的工龄带较长小数位（如 8.2345 年），直接放进 `CASE hire_year WHEN 1` 因浮点精度与等值比较机制永远无法命中离散整数；必须先离散化取整——方案 A 用 `ROUND(DATEDIFF(...) / 365)`（可不带参数，默认四舍五入取整），方案 B 用 `TRUNCATE(DATEDIFF(...) / 365, 0)`（显式保留 0 位小数）；变量类型建议直接声明为 `INT`，使等值匹配更严密。
* **分支选型的决策准则与事故教训**
    * 等值枚举匹配：判定对象为具体整型、枚举或字符且匹配项不多时，用 `CASE expr WHEN ...` 模式一最直观、代码整齐。
    * 区间判断与组合条件：条件涉及 `>`、`<`、`BETWEEN` 或复杂 `AND` / `OR` 组合时模式一完全无法胜任（它强制要求等值匹配）；此时既可用 `IF ... ELSEIF ... ELSE`，也可用模式二 `CASE WHEN 条件 THEN`，两者底层执行效率完全一致，更多取决于团队代码风格偏好。
    * > 易错点（血泪教训）：`update_salary_by_eid5_bug` 的每个 `CASE` 分支里的 `UPDATE employees SET salary = salary + 500;` 漏写 `WHERE employee_id = emp_id`，调用 `CALL update_salary_by_eid5_bug(101);` 时控制台反馈 `Query OK, 107 rows affected`——整张表一共只有 107 名员工，全公司薪资被无差别上调 500 元。**存储过程语法通过编译、无报错成功创建绝不代表业务逻辑没有致命缺陷**；书写任何 `UPDATE` 或 `DELETE` 时必须警惕作用域并严格绑定限定主键。
    * 修正后验证：`CALL update_salary_by_eid5(101);` 后 101 号员工薪资从 `17000.00` 精准变为 `17500.00`，受影响行数严格为 1，其余 106 名员工薪水安然无恙。
* **入口年限梯级调薪的完整规则**
    * 入职满 0 年加 50 元、满 1 年加 100 元、满 2 年加 200 元、满 3 年加 300 元、满 4 年加 400 元、其余（工龄 5 年及以上）统一加 500 元，用 `CASE hire_year WHEN 0..4 THEN ... ELSE ... END CASE;` 实现，每条 `UPDATE` 均须绑定 `WHERE employee_id = emp_id`。

## 流程控制：循环结构与跳转控制


### 循环结构与三种实现

* **循环结构四要素与死循环陷阱**
    * 四要素：初始化条件（循环启动前给控制变量赋初值，或先查出当前基准值）、循环条件（决定是否继续执行或立即终止的布尔表达式）、循环体（反复执行的一组可执行 SQL）、迭代条件（每轮循环体执行后驱动控制变量向终止状态靠近，如 `SET i = i + 1;` 或重新检索最新表状态）。
    * > **易错点**：最容易遗漏的就是**迭代条件**。高级语言的 `for` 循环在头部强制要求步进表达式，而 SQL 的 `WHILE` 或 `LOOP` 中迭代变量的修改必须由开发者手工显式编写；一旦遗漏，状态变量永远定格在初始值、循环条件永远为真，存储过程陷入致命的死循环（Infinite Loop），导致数据库连接被占满、CPU 飙升至 100%。
* **LOOP 结构与 `LEAVE` 跳出**
    * 语法：`[loop_label:] LOOP statement_list; END LOOP [loop_label];`，`loop_label` 起始处的 `label:` 与结尾处的 `END LOOP label` 必须严格一致。
    * `LOOP` 本身**没有任何先验或后验的退出条件判断**，从一进入起就是无限循环，必须与标签名和跳转关键字 `LEAVE` 配合，通过在循环体内部嵌套 `IF` 判定主动中断。
    * 基础计数案例 `test_loop()`：`DECLARE num INT DEFAULT 1;` 后进入 `loop_label: LOOP`，`SET num = num + 1;` 并判 `IF num >= 10 THEN LEAVE loop_label; END IF;`，最终输出 `num = 10`。
* **`OUT` 形参不得充当循环计数器**
    * > **注意**：直接把 `OUT num` 形参当计数器累加存在严重隐患。其一，`OUT` 模式参数本质是只出不进，过程被调用时无论外部赋了什么初值，进入过程体内该形参的值都是未定义的（初始值为 `NULL`），而对 `NULL` 执行加法运算（`NULL + 1`）结果永远是 `NULL`，计数器彻底失效；其二，若把参数模式改为 `INOUT`，外部传入变量若本身含脏数据（如初值为 10），直接累加会严重污染基准，返回的不是本次实际循环次数。
    * 规范做法：始终在内部独立声明一个确定性初值的局部变量（`DECLARE loop_count INT DEFAULT 0;`），所有自增操作仅作用于该局部变量；循环安全结束、完成所有业务操作后再把局部变量的值单向赋值给输出形参（`SET num = loop_count;`）。
* **WHILE 结构与先验判定**
    * 语法：`[while_label:] WHILE search_condition DO statement_list; END WHILE [while_label];`。
    * 只要 `search_condition` 求值为 `TRUE` 就执行 `DO` 之后的语句体，一旦求值为 `FALSE` 或 `NULL` 循环立即终止；标签名属可选属性，只有在循环体内部需要通过 `LEAVE` 或 `ITERATE` 跨层跳转时才需显式声明。
    * > 结论：`WHILE` 的核心特征是「先审后批」，如果初始进入时 `search_condition` 本身就不成立，其循环体一次都不会执行（执行次数为 0）。
    * 计数机理 `test_while()`：`number` 从 1 开始，`WHILE number <= 10 DO SET number = number + 1; END WHILE;`，自增到 10 时回到头部判定 `10 <= 10` 依然为真再次加 1 变 11，第三次判定 `11 <= 10` 为假终止，最终输出 `number = 11`。
* **REPEAT 结构与后验判定**
    * 语法：`[repeat_label:] REPEAT statement_list; UNTIL search_condition END REPEAT [repeat_label];`。
    * 先执行后检查：程序执行到 `REPEAT` 结构时不管当前条件是否满足，直接无条件先执行一遍循环体内的语句，执行至底部再对 `UNTIL search_condition` 求值。
    * 退出极性完全相反：`WHILE` 中条件为 `TRUE` 表示继续留在循环内，而 `REPEAT ... UNTIL` 中 `search_condition` 代表的是**终止/退出条件**，表达式为 `TRUE` 时立即退出循环、为 `FALSE` 时折返继续。
    * > **易错点**：`UNTIL search_condition` 语句尾部**切禁添加分号**，误加分号会抛出 `You have an error in your SQL syntax near '; END REPEAT'` 编译报错。
* **REPEAT 最小执行次数的边界验证**
    * `update_salary_repeat(OUT num INT)` 在平均薪资 `4829.41` 时首次调用，`@up_count` 返回 8，平均薪资跃升至 `14773.12`。
    * 在平均薪资已为 `14773.12`（明显高于 13000 门槛）时立即二次调用，`@repeat_again` 返回 **1**（而非 0）且薪资被强行再涨 15% 至 `16989.09`。
    * > 结论：若改用 `WHILE avg_sal < 13000 DO`，初始进入时 `14773 < 13000` 直接为假，循环体一次都不会执行、计数器输出必定为 0、薪资分文不改；而 `REPEAT` 秉持先斩后奏哲学，无论当前客观数据是否已越界，只要进入该结构必定先强行跑完一次循环体再去判定末尾的 `UNTIL`，因此 `REPEAT` 的最小执行次数必然是 **1 次**。
* **三种循环的横向对比**

    | 评估维度 | `LOOP` 循环 | `WHILE` 循环 | `REPEAT` 循环 |
    | :--- | :--- | :--- | :--- |
    | 基础语法结构 | `[label:] LOOP ... END LOOP` | `WHILE cond DO ... END WHILE` | `REPEAT ... UNTIL cond END REPEAT` |
    | 判定逻辑时机 | 无原生判定（需内嵌 `IF`） | 先验判定（先检查，后执行） | 后验判定（先执行，后检查） |
    | 条件求值极性 | 不适用 | 条件为 `TRUE` 则继续执行 | 条件为 `TRUE` 则立即退出 |
    | 最小执行次数 | 0 次（若一进循环立即被 `LEAVE`） | 0 次（首轮判定失败直接跳过） | 1 次（首轮无条件强制执行） |
    | 退出依赖手段 | 强依赖 `label` 与 `LEAVE` | 依赖自身条件，标签可选 | 依赖自身条件，标签可选 |
    | 典型适用场景 | 复杂无界迭代、游标提取异常捕获 | 最通用的常规计数与业务循环 | 无论如何都必须至少执行一次的事务批处理 |

* **循环业务实战的关键数值**
    * `update_salary_loop(OUT num INT)`：平均薪资未达 12000 时循环全员上浮 10%（`SET salary = salary * 1.1;`），直至达到或超过 12000；迭代条件除计数器递增外，还必须重新执行 `SELECT AVG(salary) INTO avg_sal FROM employees;` 驱动 `avg_sal` 向阈值逼近；实测 `@count` 返回 `6`，全表平均薪资更新为 `12465.34`。
    * `update_salary_while(OUT num INT)`：`WHILE avg_sal > 5000 DO` 循环全员降薪为原薪资的 90%（`salary * 0.9`），实测降薪轮次 9 次后平均薪资定格在 `4829.41`。
    * `leave_while(OUT num INT)`：用 `while_label: WHILE TRUE DO` 构建常真循环，循环体首部用 `IF avg_sal <= 10000 THEN LEAVE while_label; END IF;` 作为退出断点，实测初始平均薪资约 16000 多元时执行 6 轮全员打九折后平均薪资约 `9028.xx`；紧接着再次调用时首次进入循环体即命中断点跳出，`@count` 准确返回 0。
    * `insert_data(IN insert_count INT)` 批量造数：`WHILE init_count <= insert_count DO` 循环内 `INSERT INTO admin(user_name, password) VALUES (CONCAT('@atguigu-', init_count), ROUND(RAND() * 1000000));` 最后 `SET init_count = init_count + 1;`，`CALL insert_data(100);` 后 `SELECT COUNT(*) FROM admin;` 返回 100。
    * `test_if_pro(IN sal DOUBLE)` 动态 DML 分派：`sal < 3000` 执行 `DELETE FROM employees WHERE salary = sal;`（`CALL test_if_pro(2900);` 后原 116 号员工被物理删除）；`ELSEIF sal <= 5000` 执行 `UPDATE employees SET salary = salary + 1000 WHERE salary = sal;`（`CALL test_if_pro(3100);` 后原 115 号员工薪资变为 4100）；`ELSE` 执行 `salary = salary + 500`（`CALL test_if_pro(24000);` 后变为 24500）。

### 跳转控制 LEAVE 与 ITERATE

* **LEAVE 的语义与作用域**
    * 语法 `LEAVE 标签名;`。
    * > **定义**：`LEAVE` 语句用于退出指定的构造块，不仅可应用于循环语句（`LOOP`、`WHILE`、`REPEAT`），而且可以直接应用于 `BEGIN ... END` 复合语句块。
    * 为存储过程的 `BEGIN ... END` 主体赋予标签后，在过程体内部任何深层分支执行 `LEAVE 标签名;` 就相当于直接提前终结该存储过程的执行，效果类似高级语言中的函数提前 `return`；控制效果等同于 `break`。
    * 两项语法约束：被 `LEAVE` 控制的代码块（循环或 `BEGIN`）前必须附带标签名并以英文冒号结尾（如 `label_name: BEGIN` 或 `label_name: WHILE ... DO`）；代码块结束处的标签是可选的，但只要该结构需要被内部 `LEAVE` 引用，起始处的前置标签就是强制必选。
* **ITERATE 的语义与作用域限制**
    * 语法 `ITERATE 标签名;`。
    * > **定义**：`ITERATE` 语句表示「重新开始循环」，只能在循环语句（`LOOP`、`WHILE`、`REPEAT`）的循环体中使用，控制行为是立即忽略该循环体内后续尚未执行的代码行，直接把程序指针拉回循环头部开始下一轮条件的评估与迭代；控制效果等同于 `continue`。
    * > **易错点**：`LEAVE` 既能用于循环也能用于 `BEGIN ... END` 块，而 **`ITERATE` 只能且必须使用在循环结构中**；在非循环的 `BEGIN ... END` 结构中调用 `ITERATE`，MySQL 语法分析器直接拒绝并报语法错误。
* **跳转语句的标签书写与多层嵌套**
    * 起始位置给语句块挂载标签时必须以英文冒号结尾（如 `outer_loop: LOOP`）；在 `LEAVE` 或 `ITERATE` 后面引用标签时**严禁加冒号**，直接写标签名并以分号结尾（如 `LEAVE outer_loop;`）。
    * 命名语义化：避免 `label1`、`l2` 等无意义命名，推荐采用 `外层对象_循环类型_label` 的规范，如 `dept_while_label`、`emp_loop_label`。
    * 多层嵌套跳出能力：在深层嵌套循环中，内层的 `LEAVE` 可以直接指定最外层循环的标签名，一旦触发控制流直接穿透所有内部循环跳离整个最外层循环体，在处理多级关联数据的短路退出时极为高效。

| 特性维度 | `LEAVE` | `ITERATE` |
| :--- | :--- | :--- |
| 字面语义 | 离开、退出、终结 | 迭代、重试、开启下一轮 |
| 高级语言等价物 | `break` / 复合块提前 `return` | `continue` |
| 合法作用域 | 循环结构（`LOOP` / `WHILE` / `REPEAT`）以及 `BEGIN ... END` 复合语句块 | 仅限循环结构（`LOOP` / `WHILE` / `REPEAT`） |
| 标签依赖度 | 必须显式指定目标标签 | 必须显式指定目标循环标签 |
| 执行后果 | 结构立即解体，跳到结构末尾之后向下执行 | 跳过当前循环体内剩余语句，回到循环首部重新评估 |
| 典型应用场景 | 异常中断、搜索命中提前退出、死循环主动熔断 | 数据无效过滤、黑名单跳过、特定区间穿透处理 |


* **`LEAVE` 跳出复合语句块的实测**
    * `leave_begin(IN num INT)` 用 `begin_label: BEGIN` 绑定复合块，`IF num <= 0 THEN LEAVE begin_label; ELSEIF num = 1 THEN SELECT AVG(salary) ...; ELSEIF num = 2 THEN SELECT MIN(salary) ...; ELSE SELECT MAX(salary) ...; END IF;`，`IF` 结构之后另有一条独立 `SELECT COUNT(*) AS total_count FROM employees;`。
    * 传 `num = 0` 时命中第一分支执行 `LEAVE begin_label;`，控制流瞬间跳出存储过程最外层，后续分支判断与末尾 `SELECT COUNT(*)` 统统被掠过，客户端不会收到任何结果集返回。
    * 传 `num = 1` 时先返回平均工资结果集，`IF` 结构自然闭合后控制流继续向下执行末尾 `SELECT COUNT(*)` 并返回总人数结果集。
    * > **提示**：部分图形化客户端（如某些版本的 SQLyog）在存储过程连续抛出多个 `SELECT` 结果集时界面网格可能只渲染第一个，若要直观验证多个结果集是否全部执行，可在 MySQL 原生命令行客户端调用 `CALL leave_begin(1);` 观察先后输出的两个完整数据表格。
* **`ITERATE` 与 `LEAVE` 协同的逐轮推演**
    * `test_iterate()` 用 `DECLARE num INT DEFAULT 0;` 配合 `loop_label: LOOP`，循环体先 `SET num = num + 1;`，再 `IF num < 10 THEN ITERATE loop_label; ELSEIF num > 15 THEN LEAVE loop_label; END IF;`，分支之后写 `SELECT '让天下没有难学的技术' AS msg;`。
    * 该 `IF ... ELSEIF ... END IF;` 完全**没有书写最后的 `ELSE` 分支**，这是完全合规且高效的写法：`num` 落在 `[10, 15]` 时既不满足 `< 10` 也不满足 `> 15`，程序自然穿透整个 `IF` 判定安全下行至后续 `SELECT`。
    * 执行轨迹：阶段一 `num` 从 1 到 9 每次被 `ITERATE` 拉回循环起始点，下方 `SELECT` 被完全跳过；阶段二 `num = 10` 时两个判断均为假，首次成功输出；阶段三 `num` 从 11 到 15 连续输出；阶段四 `num = 16` 时命中 `ELSEIF` 触发 `LEAVE`，循环被彻底斩断。命令行调用 `CALL test_iterate();` 依次准确弹出 6 次结果集（对应 `num = 10, 11, 12, 13, 14, 15`）。

### 游标的四步生命周期

* **游标（Cursor）的定位**
    * > **定义**：游标的本质是结果集上的一个指针，充当 SQL 与过程化代码之间的桥梁，允许在存储过程或函数中以单行记录为粒度获取字段，将字段存入局部变量中进行独立的算术、逻辑与条件控制。
    * 面向集合处理模式一次性打包结果集，无法在单次批量中针对某一行做特殊逻辑，遇到动态累计计算时必须查回前端再循环；游标模式通过 `DECLARE → OPEN → FETCH → CLOSE` 让指针逐行步进。
    * > 结论：游标让原本只能进行集合运算的 SQL 语言拥有完整的面向过程开发能力。
* **四步操作与声明位置**
    * 第一步声明：`DECLARE 游标名 CURSOR FOR SELECT查询语句;`。MySQL、SQL Server、DB2 与 MariaDB 使用 `CURSOR FOR`，Oracle 与 PostgreSQL 的语法为 `CURSOR IS`。
    * 第二步打开：`OPEN 游标名;`，引擎执行其绑定的 `SELECT` 并把结果集加载到游标专属工作区内存中，此时内部指针指向第一条记录的前方。
    * 第三步读取：`FETCH 游标名 INTO 局部变量1 [, 局部变量2, ...];`，每执行一次指针自动向后步进一行，因此 `FETCH` 几乎必然置身于循环结构（`LOOP`、`WHILE` 或 `REPEAT`）中。
    * 第四步关闭：`CLOSE 游标名;`。
    * > 易错点（一个萝卜一个坑的严格对应法则）：`SELECT` 查询投影了多少个字段，`INTO` 后面就必须严格按序提供相同数量的局部变量，且对应变量的数据类型必须与查询字段兼容；查 3 个字段却给 2 个或 4 个变量会直接报错中断执行。
* **游标资源释放的必要性**
    * 游标会持续占用 MySQL 服务器的内存工作区句柄。
    * 在事务执行期间，游标遍历扫描数据集时会对底层数据行持有行锁或间隙锁；若游标不及时显式关闭，相关锁资源将一直被霸占，直到整个外层存储过程彻底结束甚至事务提交。生产高并发场景下其他并发会话对这些数据的查询或修改将被长时间挂起排队，极易诱发锁等待超时甚至系统雪崩。
    * > **提示**：坚持在不再需要使用游标数据的第一时间显式调用 `CLOSE` 释放资源，不要依赖存储过程执行完系统自然清理。
* **游标的优势、代价与选型**
    * 显著优势：逐行颗粒度提供细致的数据提取；支持状态累计与中断；突破集合思维限制表达复杂算法。适用场景为计算某一行严重依赖上一行累计运行状态、无法用单一 SQL 表达式或窗口函数化解的极度复杂逐行计算，以及离线批处理、历史数据清洗、管理员定制化运维等小批量与管理型任务。
    * 潜在代价：缓冲整个结果集带来内存占用；扫描行级长期持锁加剧加锁竞争；难以享受批量处理优化导致性能瓶颈。
    * 避坑准则：严禁在超大并发 OLTP 核心接口中滥用游标（每次 `FETCH` 都有额外 CPU 开销，长时间不提交会拉长事务链路）；能用集合操作替代时优先使用集合，若需求可通过一条带 `GROUP BY`、`CASE` 或单行函数的 `UPDATE` / `SELECT` 完成，绝不强行用游标重构。
* **游标实战的关键设计点**
    * `get_count_by_limit_total_salary(IN limit_total_salary DOUBLE, OUT total_count INT)`：游标 `DECLARE emp_cursor CURSOR FOR SELECT salary FROM employees ORDER BY salary DESC;`，用 `REPEAT ... FETCH ... UNTIL sum_sal >= limit_total_salary END REPEAT;` 驱动。
    * 变量规划：`sum_sal DOUBLE DEFAULT 0.0` **必须赋初始默认值**，因为循环体中执行 `sum_sal = sum_sal + 当前工资`，若不指定默认值则初始为 `NULL`，任何数值与 `NULL` 相加结果永远是 `NULL`，逻辑全盘失效；`emp_sal DOUBLE` 每轮被 `INTO` 直接覆盖赋值故无需默认值；`emp_count INT DEFAULT 0` 充当计步器必须显式设初值 0。
    * 实测：`CALL get_count_by_limit_total_salary(200000, @count);` 返回 `11`（前 10 名累加尚不足 20 万元，第 11 名加入后首次突破）。
* **游标与分支嵌套的阶梯调薪**
    * `update_salary(IN dept_id INT, IN change_sal_count INT)`：游标 `DECLARE emp_cursor CURSOR FOR SELECT employee_id, hire_date FROM employees WHERE department_id = dept_id ORDER BY salary ASC;`，用 `WHILE init_count <= change_sal_count DO` 严格控制只迭代指定员工数量。
    * 阶梯倍率：`YEAR(emp_hire_date) < 1995` 时 `add_rate = 1.20`；`ELSEIF YEAR(...) <= 1998` 时 `1.15`；`ELSEIF YEAR(...) <= 2001` 时 `1.10`；`ELSE` 时 `1.05`；随后针对当前游标锁定的单名员工执行 `UPDATE employees SET salary = salary * add_rate WHERE employee_id = emp_id;`。
    * 必须使用游标而非普通 `UPDATE` 的原因：直接写 `UPDATE ... WHERE department_id = dept_id` 会更新全部门所有员工，且普通 `UPDATE` 虽支持 `LIMIT` 但无法针对每一行不同的入职年份计算不同涨薪系数。
    * 实测（50 号部门共 43 名员工，按薪资升序最低三位为 132 号 2100、128 号 2200、136 号 2200，第四位起为 2400 及以上）：`CALL update_salary(50, 3);` 后仅前三位按各自入职年份乘以对应系数，127、135 号薪资仍为 2400。

## 触发器


### 事件驱动模型与创建维度

* **触发器的本质定位**
    * > **定义**：触发器是由 MySQL 事件驱动的特殊存储过程，与特定数据表紧密绑定，当表发生特定的插入、修改或删除操作时由数据库引擎自动触发执行，主要用于强制实施复杂的数据完整性规则与审计追踪。
    * 触发器自 MySQL 5.0 版本引入，是与表、视图、存储过程、存储函数平级的独立数据库对象。
    * 存储过程是主动调用模型，必须主动键入 `CALL 存储过程名()` 才会触发；触发器则**严禁且无法被显式调用**，像潜伏在业务表背后的监听器静默监视数据流，只有当用户对该表执行特定 DML 操作时引擎才会自动、强制地调起它。
    * 类比：事件（Event）就是用户对某张表发起的 `INSERT`、`UPDATE` 或 `DELETE` 操作，触发器（Trigger）就是绑定在该表上的监听器。
* **创建语法与四大核心维度**
    * 语法：`CREATE TRIGGER 触发器名称 {BEFORE | AFTER} {INSERT | UPDATE | DELETE} ON 表名 FOR EACH ROW BEGIN 触发器执行逻辑代码 END;`。
    * 监视地点（`ON 表名`）：触发器必须深度寄生于某一张具体物理表，不能脱离具体的表空泛存在。
    * 监视事件（`INSERT | UPDATE | DELETE`）：只对指定的一种 DML 动作产生响应，绑定 `DELETE` 事件的触发器在向该表插入新数据时绝不执行。
    * 触发时机（`BEFORE | AFTER`）：`BEFORE` 在目标表物理写入操作发生**之前**执行，用于数据前置校验、非法值拦截或默认值自动修正；`AFTER` 在物理变更顺利落盘**之后**执行，用于联动更新关联表、写入系统操作审计日志或统计汇总。
    * 触发频率（`FOR EACH ROW`）：行级触发器声明，一条批量更新或删除语句同时影响 10 行时该触发器会被严格触发执行 10 次。
    * 命名规范推荐 `{时机}_{事件}_{表名}_tri` 格式，如 `before_insert_test_tri`、`after_delete_order_tri`。
* **BEFORE 与 AFTER 的时序验证**
    * 环境：`dbtest17` 中建业务主表 `test_trigger(id INT PRIMARY KEY AUTO_INCREMENT, t_note VARCHAR(30))` 与日志从表 `test_trigger_log(id INT PRIMARY KEY AUTO_INCREMENT, t_log VARCHAR(30))`。
    * 先建 `before_insert_test_tri`（`BEFORE INSERT ON test_trigger`，体内 `INSERT INTO test_trigger_log(t_log) VALUES('before_insert');`），插入 `('Tom')` 后日志表出现 `id=1, t_log='before_insert'`。
    * 再建 `after_insert_test_tri`（`AFTER INSERT ON test_trigger`，体内写入 `'after_insert'`），此时该表同时挂载两个针对 `INSERT` 的触发器；插入 `('Jerry')` 后日志表输出为：id 1 = `before_insert`（插入 Tom 时生成）、id 2 = `before_insert`（插入 Jerry 发生前生成）、id 3 = `after_insert`（插入 Jerry 顺利完成后生成）。
    * 执行时序结论：先走 `BEFORE` 触发器，再落盘主表记录，最后走 `AFTER` 触发器。
* **行级触发与批量删除验证**
    * `emps_del_trigger`（`BEFORE DELETE ON emps FOR EACH ROW`）体内用 `OLD` 提取即将被删除的行写入存档表 `emps_back1`：`INSERT INTO emps_back1(employee_id, last_name, salary) VALUES (OLD.employee_id, OLD.last_name, OLD.salary);`。
    * 单行删除 `DELETE FROM emps WHERE employee_id = 101;` 后 `emps` 从 109 条变 108 条，`emps_back1` 中出现该行完整原始记录。
    * 批量删除 `DELETE FROM emps;`（影响 108 行）后 `emps_back1` 总行数准确变为 109 条，证明行级契约：引擎在物理存储层每删除一行就同步调用一次该触发器，无论上层 DML 以批处理还是一次一行形式下发，触发器都按受影响的实际物理行数逐行执行。
    * 该基于 `OLD` 变量的归档触发器可直接形成「操作回收站」：误删后从备份表执行 `INSERT INTO emps SELECT * FROM emps_back1;` 即可实现快速原地自愈。
* **新增数据同步备份的完整流程**
    * 用 `CREATE TABLE emps_back AS SELECT * FROM emps WHERE 1 = 2;` 克隆空表结构（`1 = 2` 永远返回 `FALSE`，无法筛选出任何物理记录，MySQL 仅按查询结果集的列定义生成新表字段架构）。
    * `emps_insert_trigger`（`AFTER INSERT ON emps FOR EACH ROW`）体内 `INSERT INTO emps_back(employee_id, last_name, salary) VALUES (NEW.employee_id, NEW.last_name, NEW.salary);`。
    * 插入 `(300, 'Tom', 3400)` 与 `(301, 'Tom1', 3600)` 后，`emps_back` 中整齐出现这两行，应用层无需关注双写事务。
    * 另一存档练习：`trg_inventory_recycle`（`BEFORE DELETE ON tb_inventory FOR EACH ROW`）体内 `INSERT INTO tb_inventory_recycle(goods_id, stock_count, deleted_at) VALUES (OLD.goods_id, OLD.stock_count, NOW());`，在执行物理删除前 `OLD` 命名空间下的旧字段值仍可稳定读取，配合 `NOW()` 实现删除审计溯源。

### NEW / OLD 伪行与异常拦截

* **NEW 与 OLD 的适用矩阵**
    * `INSERT`：`OLD` 无效（不存在旧记录）；`NEW` 指代即将插入或已插入的新数据行，如 `NEW.salary`。
    * `UPDATE`：`OLD` 指代被修改前的原始旧数据行（如 `OLD.salary`）；`NEW` 指代修改后的全新数据行（如 `NEW.salary`）。
    * `DELETE`：`OLD` 指代即将被删除或已删除的原数据行（如 `OLD.id`）；`NEW` 无效（删除后无新记录）。
    * 数据流动示例：执行 `INSERT INTO employees(salary, manager_id) VALUES(10000, 103);` 时，触发器内部可借 `NEW.manager_id` 查询领导薪资（`SELECT salary INTO mgr_sal FROM employees WHERE employee_id = NEW.manager_id;`），再与 `NEW.salary` 比较。
* **SIGNAL 异常主动抛出机制**
    * 语法：`SIGNAL SQLSTATE '错误状态码' SET MESSAGE_TEXT = '自定义错误提示文案';`，为 MySQL 5.5+ 官方提供的标准异常抛出语法（早期只能用「除以零」或插入非法字段等旁门左道强行中断）。
    * > 结论：在 `BEFORE` 触发器中执行 `SIGNAL` 时，MySQL 引擎会捕获该未处理的严重错误，**立即强制终结当前代码向下执行的权利**；由于前置校验未通过，原始引发触发器的 `INSERT` 动作被整体阻断回滚，从而实现企业级强数据校验拦截。
* **薪资风控拦截的实测对照**
    * 触发器 `salary_check_trigger`（`BEFORE INSERT ON employees FOR EACH ROW`）：先 `DECLARE mgr_salary DOUBLE;`，再 `SELECT salary INTO mgr_salary FROM employees WHERE employee_id = NEW.manager_id;`，最后 `IF NEW.salary > mgr_salary THEN SIGNAL SQLSTATE 'HY000' SET MESSAGE_TEXT = '薪资高于领导薪资错误'; END IF;`。
    * 场景 A（合规）：103 号领导薪资 9000，插入 `(300, 'Tom', 'tom@126.com', CURDATE(), 'AD_VP', 8000, 103)` 时命令瞬间成功执行、受影响行数为 1，Tom 顺利入职。
    * 场景 B（违规）：插入 `(301, 'Tom1', 'tom1@126.com', CURDATE(), 'AD_VP', 10000, 103)` 时客户端立即中断并报 `Error Code: 1644. 薪资高于领导薪资错误`，随后 `SELECT * FROM employees WHERE employee_id = 301;` 返回空结果集，证明物理写入动作在 `SIGNAL` 瞬间已被彻底扼杀。

### 触发器的优缺点与级联边界

* **三项核心优点**
    * 强力保证数据完整性与一致性：以进货单头表（单据编号、供货商、总进货件数、总金额）与进货单明细表（商品进货数量、采购单价、明细金额）为例，明细表发生任何新增、修改或删除时由 `AFTER` 触发器自动重新计算 `SUM(数量)` 与 `SUM(金额)` 并同步回写头表，规避应用层因网络波动或代码分支疏漏导致的主从表数据不一致。
    * 自动化审计与操作日志留痕：为会员表 `member` 绑定 `AFTER UPDATE` 触发器，检测到 `balance` 变更时自动把 `OLD.balance`、`NEW.balance`、`NOW()` 与操作用户写入 `member_recharge_log` 审计日志表；即使应用层忘记写记日志代码、或多个独立微服务都在修改会员表，数据库底层仍能一视同仁实现 100% 审计留痕。
    * 持久化前的强制合法性校验（防呆防错）：超市库管误把 13 位商品条形码扫入数量字段、或把进货价 100 元输成 1000 元等事故，可通过 `BEFORE` 触发器设置刚性防线（如校验 `NEW.quantity <= 10000` 且 `NEW.purchase_price <= NEW.retail_price`），数值异常时直接阻断并抛出异常。
* **两项核心缺点**
    * 逻辑极度隐蔽、代码可读性与可调试性极差：触发器完全脱离应用程序代码库（Java / Go / Python 源码），应用层发起一条简单 `INSERT` 却突然报出与自身无关的错误，排查需反向挖掘数据库底层的触发器与关联表。
    * 级联依赖脆弱、表结构变更极易触发大面积雪崩：触发器把多个表紧紧耦合，一旦被触发表或关联表的字段名被修改、字段被删除或类型变更，原有触发器不会在表结构变更的瞬间报错，而是等后续任意一笔正常业务写入抵达该表时骤然崩溃，导致主业务事务全盘回滚。
    * 阿里《Java 开发手册》等行业规范普遍明文禁止或严格限制使用触发器。
* **外键级联与触发器激活的关键边界**
    * 场景：父表 `departments`（主键 `department_id`）与子表 `employees`（外键 `department_id`）建立 `ALTER TABLE employees ADD CONSTRAINT fk_emp_dept FOREIGN KEY (department_id) REFERENCES departments(department_id) ON DELETE SET NULL;`，同时在子表挂载 `CREATE TRIGGER trg_emp_update AFTER UPDATE ON employees FOR EACH ROW ...`。
    * 从父表删除 10 号部门记录时，引擎按级联规则把子表中所有部门编号为 10 的员工的 `department_id` 自动置为 `NULL`。
    * > 结论：**子表上的 `UPDATE` 触发器不会被激活**。由外键约束的级联行为（如 `ON UPDATE CASCADE`、`ON DELETE SET NULL`）引发的底层从表数据更新或删除属于存储引擎内部执行的外键级联操作，绝不会触发挂载在该从表上的任何行级触发器。
    * > **易错点**：选择题中「父表主键物理删除且外键设为 `ON DELETE CASCADE` 级联删除从表行时，从表上定义的 `DELETE` 触发器会自动执行并记录日志」这一描述是错误的。

## MySQL 8.0 窗口函数


### 窗口函数的语义与语法

* **窗口函数的定义与行数守恒**
    * > **定义**：窗口函数是一种特殊的函数计算模型，兼具单行函数与聚合函数的特征。它能像聚合函数一样针对一组相关的数据行（称为窗口或分区）执行聚合、排名与位移计算；但与聚合函数不同的是，**窗口函数绝不折叠压缩数据行**，每一行原始数据都被完整保留，计算得到的值直接挂载在当前行之上。
    * 对比：传统聚合函数 `GROUP BY` 把部门 10 的三行折叠产生 1 条汇总行（原行数减少）；`OVER(PARTITION BY)` 让三行各自保留并各自附带聚合统计值（行数不变）。
* **核心语法规范与要素拆解**
    * 语法：`函数名称([参数列表]) OVER ([PARTITION BY 分区列名] [ORDER BY 排序列名 [ASC|DESC]] [ROWS|RANGE 窗口帧范围])`。
    * 函数名称既可以是专用窗口函数（`ROW_NUMBER()`、`RANK()`、`LAG()`），也可以是传统聚合函数（`SUM()`、`AVG()`、`MAX()`、`MIN()`、`COUNT()`）。
    * `OVER` 关键字声明当前函数作为窗口函数运行，标识窗口定义的开始。
    * `PARTITION BY`：把输入数据集按指定列划分为互不相交的逻辑区块，作用类似 `GROUP BY` 但各行仍然独立存在；**省略该子句表示整个结果集视作一个单独的大分区**。
    * `ORDER BY`：定义各分区内部数据行的排序规则，对序号函数（如 `ROW_NUMBER`）与前后函数（如 `LAG`）而言是确定位次逻辑的绝对前提。
    * `ROWS / RANGE`：在分区内部进一步界定当前行所关联的物理行范围或逻辑数值范围；若省略且存在 `ORDER BY`，默认窗口帧为 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`。
* **相对传统写法的生产力对比**
    * 需求：在同一张结果集中同时展示每个区的销售额、所在城市销售总额、全国总销售额、区占城市比重、区占全国比重。
    * MySQL 5.7 写法需先 `CREATE TEMPORARY TABLE temp_grand_total AS SELECT SUM(sales_val) AS grand_total FROM sales;`、再 `CREATE TEMPORARY TABLE temp_city_total AS SELECT city, SUM(sales_val) AS city_total FROM sales GROUP BY city;`，最后把明细表与两张临时表 `JOIN` 与 `CROSS JOIN` 起来算除法比重；缺陷是开发成本高、需多次全表扫描与临时结构及多表 Hash / Nested-Loop 连接导致性能随数据量断崖式下跌、多会话并发访问临时表存在不可重入与命名及生命周期冲突。
    * 8.0 写法把上述过程压缩为一条 `SELECT`：`SUM(sales_val) OVER(PARTITION BY city) AS city_total`、`ROUND(sales_val / SUM(sales_val) OVER(PARTITION BY city), 4) AS ratio_in_city`、`SUM(sales_val) OVER() AS grand_total`（不分区即全表窗口）、`ROUND(sales_val / SUM(sales_val) OVER(), 4) AS ratio_in_grand`；代码量锐减 70% 以上，执行计划只扫描一次基表。
    * 样本数据实测结果（`sales` 表四条记录）：北京海淀 10（`city_total` 30、`ratio_in_city` 0.3333）、北京朝阳 20（30、0.6667）、上海黄浦 10（40、0.2500）、上海长宁 30（40、0.7500），`grand_total` 均为 70，两行北京的 `ratio_in_grand` 分别为 0.1429 与 0.2857、上海分别为 0.1429 与 0.4286。
* **MySQL 8.0 其他新特性要点**
    * SQL 编程利器：窗口函数与公用表表达式（CTE）；更完善的 JSON 支持（内部存储采用更紧凑的二进制格式）与正则表达式（引入 ICU 国际化组件，支持更多元字符与多字节字符）。
    * 底层引擎与索引：原生支持降序索引（Descending Indexes）与隐藏索引（Invisible Indexes），使联合索引排序优化更灵活并让索引灰度下线测试成为可能；系统数据字典事务化（告别 5.7 及之前分散在磁盘上的 `.frm`、`.par` 等元数据文件，统一归集在 InnoDB 事务型系统表），原生支持原子 DDL（Atomic DDL，建表或删表过程中若发生故障可实现事务级整体回滚）；内部临时表引擎由 Memory 升级为专用的 TempTable 引擎。
    * 废弃与移除：彻底移除查询缓存（Query Cache，旧版本中目标表任何微小数据变动都会导致挂载其上的所有查询缓存瞬间全盘失效，生产命中率极低反而增加锁竞争开销）；移除 `PASSWORD()`、`ENCRYPT()` 等旧式加密解密函数；默认字符集由 `latin1` 改为 `utf8mb4`（`utf8` 实际为 `utf8mb3` 每字符最多 3 字节，无法表达 Emoji 与部分生僻字，`utf8mb4` 完整覆盖 4 字节编码）。

### 各类窗口函数与帧边界

* **序号函数的三套并列策略**
    * `ROW_NUMBER()`：为分区内每一行分配连续、严格自增的自然数序号（1, 2, 3, 4, 5...），即使两行排序列数值完全相同序号也绝不重复，单纯按记录处理顺序强行顺延。
    * `RANK()`：多行排序列数值相同时赋予相同位次，但后续行的序号会**跳过**被占用的名次（1, 2, 2, 4...）。
    * `DENSE_RANK()`：同样支持并列赋值，但对后续序号采用稠密连续（Dense）策略，序号绝不跳空（1, 2, 2, 3...）。
    * 实测（`goods` 表 `category_id = 1` 共 6 件商品，价格降序）：最高价 399.90 三者均为 1；并列 89.00 的卫衣与牛仔裤 `ROW_NUMBER` 为 2 与 3、`RANK` 均为 2、`DENSE_RANK` 均为 2；随后 79.90 的连衣裙 `RANK` 跳跃至 **4**、`DENSE_RANK` 为 **3**。
    * > **提示**：窗口函数生成的动态列无法在同级的 `WHERE` 条件中直接引用，做组内 Top-N 时通常在外层嵌套一层子查询完成过滤，如 `SELECT * FROM (SELECT ..., ROW_NUMBER() OVER(PARTITION BY category_id ORDER BY price DESC) AS row_num FROM goods) t WHERE t.row_num <= 3;`。

| 分区排序依据（价格降序） | 价格相同情况 | `ROW_NUMBER()` 输出 | `RANK()` 输出 | `DENSE_RANK()` 输出 |
| :--- | :--- | :--- | :--- | :--- |
| 商品 A (399.90) | 最高价 | 1 | 1 | 1 |
| 商品 B (89.00) | 并列第 2 | 2 | 2 | 2 |
| 商品 C (89.00) | 并列第 2 | 3 | 2 | 2 |
| 商品 D (79.90) | 次低价 | 4 | 4（跳跃） | 3（连续） |
| 商品 E (39.90) | 次低价 | 5 | 5 | 4 |
| 商品 F (29.90) | 最低价 | 6 | 6 | 5 |


* **分布函数的两个公式**
    * `PERCENT_RANK()` 计算当前行在分区内的相对排位百分比：$\text{PERCENT\_RANK} = \dfrac{\text{RANK} - 1}{\text{Rows} - 1}$，其中 $\text{RANK}$ 为 `RANK()` 计算出的名次、$\text{Rows}$ 为当前分区总记录行数。
    * `category_id = 1`（`Rows = 6`）价格降序推导：399.90（`RANK = 1`）得 $0/5 = 0.0$；两行 89.00（`RANK = 2`）均得 $1/5 = 0.2$；79.90（`RANK = 4`）得 $3/5 = 0.6$；39.90（`RANK = 5`）得 $4/5 = 0.8$；29.90（`RANK = 6`）得 $5/5 = 1.0$。
    * `CUME_DIST()`（Cumulative Distribution）计算小于等于当前行排序列数值的数据行数占分区总行数的比例：$\text{CUME\_DIST} = \dfrac{\text{分区中小于或等于当前排序列值的行数}}{\text{分区总行数}}$；升序排列下价格 29.90 无更低价格时自身占 1 行共 6 行得 $1/6 \approx 0.1667$，到达最高价 399.90 时全部 6 件商品均小于等于它得 $6/6 = 1.0$。
* **前后函数与首尾函数**
    * `LAG(expr, n, default)`：在保留当前行的同时向前调取同一分区内前第 $n$ 行的指定表达式值，默认 $n = 1$；若不存在前第 $n$ 行则默认填充 `NULL`，也可通过第三个参数指定缺省替换值。
    * `LEAD(expr, n, default)`：与 `LAG` 相反，向后调取同一分区内后第 $n$ 行的数据行。
    * 价格升序实测：每品类最便宜的第一件商品前无更便宜数据，其 `pre_price` 为 `NULL`、相减后差值亦为 `NULL`；从第二件商品起均能精准得到与前一档商品的递增差额。价格最高的最后一件商品 `next_price` 为 `NULL`。
    * `FIRST_VALUE(expr)`：返回当前窗口范围内排序排在第一位的表达式数值。实测女装分类下所有行附带的 `lowest_price` 均为 29.90，户外运动分类下统一为 59.00。
    * `LAST_VALUE(expr)`：返回当前窗口范围内的最后一个值。
    * > **易错点**：使用 `LAST_VALUE()` 时返回的往往不是分区最大值而是**当前行本身的值**。根本原因是显式指定了 `ORDER BY` 时系统默认窗口帧为 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（从分区开头到当前行），对当前行而言它所见范围内的最后一个值就是它自己。要取到整个分区的最终末尾值必须显式拓展窗口帧为当前分区全域：`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`。
* **NTH_VALUE 与 NTILE 的取值规则**
    * `NTH_VALUE(expr, n)` 用于直接捕获当前窗口内部排名第 $n$ 个位置的值，取第 2、第 3 个价格时配合 `WINDOW w AS (PARTITION BY category_id ORDER BY price ASC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)`。
    * `NTILE(n)` 将分区内部的数据行尽可能均匀地切分成 $n$ 个桶（编号从 1 到 $n$），用于把客户按消费金额分档或做四分位数分析；6 件商品按价格升序划分到 3 个桶时每桶 2 件。
    * 分桶分配原则：分区总行数不能被 $n$ 整除时 MySQL 优先把多余的数据行均摊给编号靠前的桶。例如 6 行分 4 桶，$6 \div 4 = 1$ 余 2，前 2 个桶各多分 1 行，最终第 1 桶 2 行、第 2 桶 2 行、第 3 桶 1 行、第 4 桶 1 行，桶号分布为 `[1, 1, 2, 2, 3, 4]`。
* **命名窗口（WINDOW 子句）的复用**
    * 语法：在查询主体末尾用 `WINDOW 窗口名 AS (窗口定义)` 对公共窗口命名声明，在 `SELECT` 列表中直接按名引用 `OVER 窗口名`。
    * 示例：`SELECT id, category, name, price, ROW_NUMBER() OVER w AS row_num, RANK() OVER w AS rk_num, DENSE_RANK() OVER w AS dense_rk_num FROM goods WINDOW w AS (PARTITION BY category_id ORDER BY price DESC);`。
    * 学生成绩全量排名（不需按班级或学科拆分时 `OVER()` 内部无需写 `PARTITION BY`）：`WINDOW w AS (ORDER BY points DESC)`，实测 90 分排 1，并列 89 分的李四与王五 `ROW_NUMBER` 为 2 与 3、`RANK` 均为 2、`DENSE_RANK` 均为 2，随后的 88 分赵六 `RANK` 为 4 而 `DENSE_RANK` 为 3。
* **窗口函数三条铁律**
    * 行数守恒律：窗口函数兼具聚合与明细特性，在分区内部完成统计但绝对不减少原表的物理行数。
    * 三类排序辨析：`ROW_NUMBER()` 纯自然序号永不重复；`RANK()` 并列且跳号（1, 2, 2, 4）；`DENSE_RANK()` 并列且紧凑连续（1, 2, 2, 3）。
    * 窗口帧边界陷阱：带 `ORDER BY` 的 `LAST_VALUE()` 等计算必须警惕默认窗口帧只算到当前行的边界陷阱，按需使用 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` 展开全域。
    * 分数 `[100, 95, 95, 90]` 降序排名的标准答案：`ROW_NUMBER()` 为 `1, 2, 3, 4`；`RANK()` 为 `1, 2, 2, 4`；`DENSE_RANK()` 为 `1, 2, 2, 3`。

## 公用表表达式与代码组织


### 普通 CTE 与递归 CTE

* **CTE 的定义与生命周期**
    * > **定义**：公用表表达式（Common Table Expression，CTE）是一个在单个语句（如 `SELECT`、`INSERT`、`UPDATE` 或 `DELETE`）执行范围内有效的临时结果集，使用标准 SQL 的 `WITH` 关键字定义并赋予命名的别名，在随后的主查询中可以像操作普通数据表或视图一样多次引用它。
    * > **易错点**：CTE 的生命周期与作用范围严格限制在**定义它的当前单条 SQL 语句内部**，一旦该语句执行完毕其临时结果集生命周期即告终结，绝不能在后续其他查询中跨语句直接复用；若需跨语句复用应当创建视图或临时表。
* **与子查询、临时表的三方对比**

    | 组织模式 | 作用范围 | 复用性 | 资源开销 | 类比 |
    | :--- | :--- | :--- | :--- | :--- |
    | 内联子查询 | 仅当前嵌套位置可见 | 零复用（需重复写） | 随每次执行重复评估 | 编程语言中的局部字面量 |
    | 公用表表达式 CTE | 当前完整 SQL 语句内可见 | 单语句内支持多次引用 | 内联轻量化临时视图 | 单函数内部局部常量定义 |
    | 物理临时表 | 整个 Session 会话可见 | 全会话跨语句复用 | 占用磁盘或 TempTable 引擎 | 全局持久化实体 |


* **普通 CTE 语法与实战**
    * 语法：`WITH cte_name [(column_name [, ...])] AS (SELECT ...) SELECT ... FROM cte_name;`，以 `WITH` 开头，`AS (...)` 内部包裹产生临时结果集的子查询，主查询中把 `cte_name` 当普通物理表名关联或投影；CTE 名称建议具备明确业务含义（如 `cte_emp`、`cte_dept_sales`）。
    * 实战（查询所有存在在职员工的部门明细）：传统写法用 `WHERE department_id IN (SELECT DISTINCT department_id FROM atguigudb.employees)`；CTE 写法把准备逻辑前置——`WITH cte_emp AS (SELECT DISTINCT department_id FROM atguigudb.employees) SELECT d.*, e.department_id AS active_dept_id FROM departments d JOIN cte_emp e ON d.department_id = e.department_id;`。
    * 优势：逻辑自顶向下（遵循先声明定义、后消费引用的顺序，而传统 SQL 阅读顺序是「由外向内」再「由内向外」反复跳转）；多处重用（主查询中若还需把该集合用于 `EXISTS` 判定或二次合并计算，直接再次 `JOIN cte_emp` 即可）。
    * 与临时表的差异：临时表是物理存在的数据库对象（由内存引擎或磁盘支撑），生命周期贯穿整个连接会话，必须显式 `DROP TEMPORARY TABLE` 释放；CTE 是高度轻量级的逻辑临时结果集，随当前这一条 SQL 语句开始而生成、随语句执行完毕自动在内存中消失，不留任何元数据残留。
* **递归 CTE 的两段结构与运行机理**
    * 标准语法必须加 `RECURSIVE` 修饰符：`WITH RECURSIVE cte_name AS (种子查询 SELECT ... UNION ALL 递归查询 SELECT ... FROM 表名 JOIN cte_name ON 递归条件) SELECT * FROM cte_name;`。
    * 种子查询（Anchor / Initial Member）为非递归查询块，用于定义递归的起始点（如根节点、最顶级部门、初始计数器代次等），在整个执行流程中仅评估一次。
    * 递归查询（Recursive Member）在 `FROM` 或 `JOIN` 中直接引用 CTE 自身，每一轮迭代把上一轮计算出的增量数据代入计算生成下一层级数据，直至返回空集自动终止。
    * 运行环路：先获取初始数据集 R0，检查当前批次 Ri 结果非空则执行递归部分 Ri+1 并回到检查点，结果为空（终止条件满足）则把 R0、R1、R2... 用 `UNION ALL` 汇聚返回完整的树形展开结果集。
* **递归 CTE 的层级穿透实战**
    * 员工表采用自关联（Adjacency List）模型，每条记录含自己的 `employee_id` 与直属领导的 `manager_id`；最顶层 CEO 为 `employee_id = 100`（其 `manager_id` 为 `NULL`，算第 1 代），以初代为直属领导的员工称下属（第 2 代），下属所管辖的员工及再往下的所有层级成员统称「下下属」（第 3 层及更深层级）。
    * 传统手写迭代必须写多轮嵌套自连接，且公司层级不确定（有的部门深达 5 层、有的只有 2 层）时，由于 SQL 没有原生循环控制语句，在单条查询中根本无法穷尽。
    * 递归写法：`WITH RECURSIVE cte_emp_hierarchy AS (SELECT employee_id, last_name, manager_id, 1 AS n FROM atguigudb.employees WHERE employee_id = 100 UNION ALL SELECT a.employee_id, a.last_name, a.manager_id, b.n + 1 AS n FROM atguigudb.employees a JOIN cte_emp_hierarchy b ON a.manager_id = b.employee_id) SELECT employee_id, last_name, manager_id, n AS hierarchy_level FROM cte_emp_hierarchy WHERE n >= 3;`。
    * 实测：`WHERE n >= 3` 瞬间输出 92 条记录；改为 `WHERE n = 4` 准确返回 10 条；改为 `WHERE n = 5` 返回空集（0 条）。
    * 层级分布结论：该公司管理架构树总深度严格为 **4 层**，全公司 107 名员工中初代 1 人（100 号）、第 2 代 14 人（$107 - 92 - 1 = 14$）、第 3 代 82 人（$92 - 10 = 82$）、第 4 代 10 人，完全闭环。
* **变量作用域在函数代码重构中的选型**
    * 规范写法：在 `BEGIN ... END` 内部声明整型局部变量 `emp_count`，通过 `SELECT COUNT(*) INTO emp_count FROM employees;` 写入变量，最终 `RETURN emp_count;` 提交结果（`get_count()` 返回 107），避免直接书写 `RETURN (SELECT COUNT(*) FROM ...)` 这种无法对中间结果做二次业务校验或多步计算的嵌套写法。
    * 多表关联函数：`dept_sal(dept_name VARCHAR(20))` 中 `DECLARE avg_sal DOUBLE;` 后 `SELECT AVG(e.salary) INTO avg_sal FROM employees e JOIN departments d ON e.department_id = d.department_id WHERE d.department_name = dept_name;`，最后 `RETURN avg_sal;`（`SELECT dept_sal('IT');`）。
    * 纯内存计算可直接用 `SET`：`add_float(value1 FLOAT, value2 FLOAT)` 中 `DECLARE sum_value FLOAT; SET sum_value = value1 + value2; RETURN sum_value;`，无需经过 `SELECT` 引擎。
    * 会话用户变量的穿透性：函数内 `SET @sal = 0.0; SELECT salary INTO @sal FROM employees WHERE last_name = emp_name; RETURN @sal;` 执行后外部 `SELECT @sal;` 同样返回 11000——局部变量通过 `DECLARE` 声明仅在 `BEGIN ... END` 内有效、执行完毕即在栈内存中销毁，而 `@sal` 生命周期贯穿当前客户端连接始终；团队协同开发中应严格按需选型，避免会话变量污染全局上下文。
    * 成绩等级判定双解法（同一业务两种分支语法）：`test_if_case_if` 用 `IF score > 90 THEN SET score_level = 'A'; ELSEIF score > 80 THEN 'B'; ELSEIF score > 60 THEN 'C'; ELSE SET score_level = 'D'; END IF;`；`test_if_case_case` 用 `CASE WHEN score > 90 THEN ... WHEN score > 80 THEN ... WHEN score > 60 THEN ... ELSE SET score_level = 'D'; END CASE;`。
    * > **易错点**：`CASE` 分支的两种语法形态中，`CASE 表达式 WHEN 值 THEN ...` 只能用于离散值的等值匹配，区间、大于小于等复杂表达式必须采用 `CASE WHEN 布尔条件 THEN ...` 形态；区间等级判断用错形态会无法命中。
    * 变量体系的内存层级：系统变量由 MySQL 引擎预先定义（GLOBAL 全局系统变量所有连接共享、重启后失效除非 `SET PERSIST`；SESSION 会话系统变量仅当前连接生效、断开后销毁）；用户自定义变量由开发者自主定义（会话用户变量 `@var_name` 作用域为整个连接会话、跨过程/函数持久访问；局部变量 `DECLARE var` 仅在 `BEGIN ... END` 块内有效、随复合块退出而销毁）。
