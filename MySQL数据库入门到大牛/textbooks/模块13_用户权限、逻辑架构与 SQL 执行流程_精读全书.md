## 105-用户的创建_修改_删除
> 对应分集：P105 | 原始标题：《105-用户的创建_修改_删除》

我们在平时的学习、开发或是本地调试阶段，几乎无一例外都是使用 `root` 账户直连 MySQL 数据库服务器。各种建库、建表、增删改查乃至底层参数修改，一行 `mysql -u root -p` 敲到底。然而在真实的生产环境当中，`root` 账户绝对不能、也绝不允许成为日常业务系统或开发运维团队的高频连接入口。

`root` 是 MySQL 体系内的最高超级管理员，拥有全局无限制的特权。业内戏称的“从删库到跑路”，其前提恰恰是操作者持有能够直接 Drop 数据库的超规格权限；一旦在缺乏热备或多机异地容灾的生产库上执行了误操作，系统面临的就是灾难性打击。企业内部必然存在前端服务连接、后端定时批处理、只读数据报表、不同业务线研发人员以及初级 DBA 等多种角色，如果每个人、每个微服务都拿着 `root` 账号跑，权限隔离与审计溯源就会彻底形同虚设。

因此，数据库安全的核心防线正是**账户与权限管理**。在生产环境中，必须贯彻**最小分配原则（Principle of Least Privilege）**：每一个具体的用户账户或服务进程，被授予的权限范围应当严格限制在它完成业务所必须的最小边界内，能给单表 `SELECT` 的绝不给整库只读，能给 DML 操作的绝不给 DDL 操作。本篇便从最基石的用户生命周期出发，系统梳理客户端完整连接参数、用户表的物理结构、用户的创建、重命名、安全销毁，以及底层权限刷新机制的真实运行机理。

### MySQL 客户端连接参数与执行模式

在终端使用命令行客户端连接 MySQL 服务端时，绝大多数场景习惯于缩写，例如 `mysql -u root -p`。但这实际上省略了连接链路中的一系列关键配置，全面理解客户端的各项启动参数，是理解后续用户“Host（主机列）”概念与自动化运维脚本编写的前提。

#### 完整连接参数剖析

客户端连接 MySQL 数据库的标准完整命令格式如下：

```bash
mysql -h [主机地址/IP] -P [端口号] -u [用户名] -p[密码] [目标数据库名] -e "[SQL语句]"
```

各参数的技术含义及默认值定义如下：

| 参数选项 | 全称 / 含义 | 默认行为与注意事项 |
| :--- | :--- | :--- |
| `-h` | `--host`（连接的目标主机） | 缺省时默认为 `localhost` 或 `127.0.0.1`。若连接远程服务器，需填入对应 IP 地址或域名 |
| `-P` | `--port`（服务端监听端口） | 大写字母 `P`。缺省时默认为 `3306`；若目标实例调整过通信端口，必须显式声明 |
| `-u` | `--user`（连接用户名） | 缺省时可能默认匹配操作系统当前登录的用户名 |
| `-p` | `--password`（连接密码） | 小写字母 `p`。可以直接在 `-p` 后无空格紧跟明文密码，或仅敲 `-p` 回车在安全提示下隐式输入 |
| `[数据库名]` | Target Database | 可选项。连接成功后直接自动切换到该数据库（相当于登录后立即执行 `USE dbname;`） |
| `-e` | `--execute`（执行 SQL 语句） | 执行双引号内的一条或多条 SQL 语句，查询完毕后立即将结果打印并退出客户端 |

针对密码参数 `-p`，存在一个典型的安全警告。若在命令行中直接追加明文密码（例如 `mysql -uroot -pabc123`），MySQL 终端会立即抛出警示信息：

```text
mysql: [Warning] Using a password on the command line interface can be insecure.
```

这是因为在多用户 Linux 操作系统中，其他具有查看进程权限的用户可以通过 `ps -ef` 等指令直接从命令行参数中捕获明文密码，同时该指令也会被原样写入 Shell 的历史记录文件（如 `~/.bash_history`）。因此，除非在安全的批处理脚本或测试场景，生产规范要求一律单独输入 `-p`，并在随后换行出现的 `Enter password:` 遮罩提示中完成密文录入。

#### 免交互直接执行模式（`-e` 机制）

在 shell 运维巡检、定时监控或 CI/CD 自动化流水线中，通常不需要进入 MySQL 交互式终端，而是期望获取查询结果后直接回到操作系统。此时可以使用 `-e` 参数配合特定数据库：

```bash
mysql -h localhost -P 3306 -u root -p dbtest1 -e "SELECT * FROM emp1;"
```

```text
+----+---------+--------+
| id | name    | salary |
+----+---------+--------+
|  1 | Tom     |   8000 |
|  2 | Jerry   |   9500 |
+----+---------+--------+
```

系统在完成密码认证后，建立网络套接字连接，将 `SELECT * FROM emp1;` 提交给服务端语法解析与执行引擎，格式化输出结果集到标准输出（stdout），随后即刻发起连接关闭序列并返回 Linux Shell。

```text
+-------------------+      TCP Handshake & Auth      +-------------------+
|   Linux Shell     | -----------------------------> |   MySQL Server    |
| (mysql -e "SQL")  | <----------------------------- |  (Port: 3306)     |
|                   |        Auth OK                 |                   |
|                   | -----------------------------> | Execute SQL Query |
| Formats stdout    | <----------------------------- | Return Resultset  |
| Process Exits     |      TCP FIN (Connection Closed)                   |
+-------------------+                                +-------------------+
```
*图 1：`-e` 命令行参数单次免交互查询时序流向*

### 系统元数据库 mysql 与 user 表物理架构

MySQL 的账户认证信息与底层全局权限并非孤立存在，而是完全依托系统内置的字典表进行持久化管理。

#### 系统字典库 mysql

安装初始化 MySQL 服务实例后，数据目录会自动建立名为 `mysql` 的内部核心数据库。可以通过以下指令切换并查看：

```sql
USE mysql;
```

该数据库是 MySQL 自身运转的神经中枢，包含了存储账户配置、全局权限、库表列级权限细则、插件配置、时区数据、帮助文档等核心元数据。在本章用户与权限管理中，绝大多数底层配置与审计查询都聚焦于该库。

#### user 表中的联合主键机理

在 `mysql` 数据库中，最为关键的账户元数据表即为 `user` 表：

```sql
SELECT host, user FROM mysql.user;
```

在 MySQL 8.0 初始安装状态下，查询结果通常呈现 4 个默认系统账户：

```text
+-----------+------------------+
| host      | user             |
+-----------+------------------+
| localhost | mysql.infoschema |
| localhost | mysql.session    |
| localhost | mysql.sys        |
| localhost | root             |
+-----------+------------------+
4 rows in set (0.00 sec)
```

其中前三项（`mysql.infoschema`、`mysql.session`、`mysql.sys`）为系统内置的保留运维账户，专供数据字典锁机制、内置性能视图（sys schema）或内部会话提取数据使用，严禁手动删除或更改；第四项即为管理员 `root`。

> **定义**：在 MySQL 的账户模型中，判定一个用户的唯一标识从来不是单纯的用户名 `user`，而是由主机列与用户名构成的二元组：`'user'@'host'`。

如果在 `mysql.user` 表结构上执行 `DESC mysql.user;`，会发现主键定义由两个字段复合而成：

```sql
PRIMARY KEY (`Host`, `User`)
```

联合主键的特性决定了：
1. `Host` 与 `User` 联合起来必须保持全局唯一，且二者皆不允许为 `NULL`；
2. 允许存在多个同名的 `User`，只要它们绑定的 `Host` 不同。例如 `'zhangsan'@'localhost'` 与 `'zhangsan'@'%'` 在底层物理表中属于两条完全独立的记录，各自持有完全独立的密码哈希值、生命周期策略与权限位。

### 账户创建：CREATE USER 规范与细节

在 MySQL 8.0 中，创建新用户必须使用标准的 DDL 语句 `CREATE USER`。

#### 语法规范与密码指定

标准创建语法如下：

```sql
CREATE USER '用户名'@'主机名' IDENTIFIED BY '认证密码';
```

例如，在 `root` 账户登录的会话中执行：

```sql
CREATE USER 'zhangsan'@'localhost' IDENTIFIED BY 'abc123';
```

执行后查询 `mysql.user` 表：

```sql
SELECT host, user FROM mysql.user;
```

输出如下：

```text
+-----------+------------------+
| host      | user             |
+-----------+------------------+
| localhost | mysql.infoschema |
| localhost | mysql.session    |
| localhost | mysql.sys        |
| localhost | root             |
| localhost | zhangsan         |
+-----------+------------------+
```

#### 缺省 Host 的默认行为与隐患

如果在执行创建命令时省略了 `'@主机名'` 部分，直接执行：

```sql
CREATE USER 'zhangsan' IDENTIFIED BY 'abc123';
```

MySQL 服务端会自动将其补全为 `'zhangsan'@'%'`。其中通配符 `%` 表示允许该账户从**任何远程主机/任意 IP 地址**发起连接认证。

此时再次查看 `mysql.user`：

```text
+-----------+------------------+
| host      | user             |
+-----------+------------------+
| %         | zhangsan         |
| localhost | mysql.infoschema |
| localhost | mysql.session    |
| localhost | mysql.sys        |
| localhost | root             |
| localhost | zhangsan         |
+-----------+------------------+
```

由于 `(Host, User)` 联合主键的互异性，`'zhangsan'@'%'` 与 `'zhangsan'@'localhost'` 可以和谐共存。但如果再次尝试执行一遍完全相同的 `CREATE USER 'zhangsan'@'%' IDENTIFIED BY 'abc123';`，服务端将立即报错：

```text
ERROR 1396 (HY000): Operation CREATE USER failed for 'zhangsan'@'%'
```

这是因为复合主键冲突。为了避免网络权限过宽引发的安全隐患，以及多客户端连接时因匹配优先级导致的混淆：

> **最佳实践**：在生产环境创建账户时，哪怕意图赋予全网访问权，也必须显式写出 `'用户名'@'%'`，严禁省略 Host 部分；若明确仅限特定子网或本地访问，务必指明具体的 IP 段（如 `192.168.1.%`）或 `localhost`。

#### 新创建用户的初始权限边界验证

刚刚创建的普通用户具备怎样的操作权限？可以通过新开终端进行登录测试：

```bash
mysql -u zhangsan -pabc123
```

登录成功后，执行查看数据库操作：

```sql
SHOW DATABASES;
```

此时的返回结果仅有极度受限的内容：

```text
+--------------------+
| Database           |
+--------------------+
| information_schema |
+--------------------+
1 row in set (0.00 sec)
```

用户连业务数据库、`mysql` 系统库甚至 `performance_schema` 均无法感知。进一步查看当前用户的权限位：

```sql
SHOW GRANTS;
```

```text
+-------------------------------------------------------------+
| Grants for zhangsan@%                                       |
+-------------------------------------------------------------+
| GRANT USAGE ON *.* TO `zhangsan`@`%`                        |
+-------------------------------------------------------------+
1 row in set (0.00 sec)
```

> **定义**：`USAGE` 权限项在 MySQL 中等同于“无权限（No privileges）”。它仅赋予用户连接并握手登录到数据库服务器的资格，无法对任何库、表、视图或存储过程执行读写操作。因此，新建用户在分配角色或赋予具体权限之前，处于严格的“零权限沙箱”隔离状态。

### 账户修改与内存权限刷新机理

对已有账户的修改通常分为两类：一是修改密码或认证插件（下一篇深入展开），二是修改账户名称或绑定 Host。在实际业务运维中，账户重命名的需求极少，但其底层的生效机制揭示了 MySQL 权限子系统的运行本质。

#### 直接更新系统表 DML 与条件定位

若需要将已存在的 `'lisi'@'%'` 重命名为 `'wangwu'@'%'`，在底层技术上可以直接对 `mysql.user` 执行标准 `UPDATE` 语句：

```sql
UPDATE mysql.user 
SET user = 'wangwu' 
WHERE user = 'lisi' AND host = '%';
```

> **易错点**：更新 `mysql.user` 表时，`WHERE` 条件千万不能只写 `user = 'lisi'`。一旦历史环境中存在 `'lisi'@'localhost'`、`'lisi'@'192.168.%'` 等多个同名记录，缺少 `host` 条件将直接导致全量同名用户被一并更改，破坏原有主机的拓扑隔离。

#### FLUSH PRIVILEGES 的底层原理与反面案例

当 `UPDATE` 语句执行成功后，通过 `SELECT host, user FROM mysql.user;` 查验，磁盘表中的 `lisi` 确实已经变成了 `wangwu`。

然而，如果此时尝试在另一个终端使用旧用户名 `lisi` 进行连接：

```bash
mysql -u lisi -pabc123
```

现象极其反直觉：**旧用户 `lisi` 竟然依旧能够成功登录系统！而尝试使用新用户名 `wangwu` 登录，系统却报错拒绝访问。**

```text
+---------------------------------------------------------------------------------+
|                                 MySQL Server                                    |
|                                                                                 |
|  +--------------------------------+       +----------------------------------+  |
|  |       In-Memory Cache          |       |     Disk (InnoDB Engine)         |
|  |       (Privilege Hash)         |       |      mysql.user Table            |
|  |                                |       |                                  |
|  |  Active Users:                 |       |  Updated Data:                   |
|  |  - root@localhost              |  VS   |  - root@localhost                |
|  |  - lisi@%  <-- [Stale Cache]   |       |  - wangwu@%  <-- [Committed DML] |
|  +--------------------------------+       +----------------------------------+  |
|                 ^                                                               |
|                 |------------ Handshake reads Cache, ignores Disk --------------|
+---------------------------------------------------------------------------------+
```
*图 2：Direct DML 修改元数据表导致的内存缓存与磁盘数据不一致*

导致该现象的根本机理在于：
- 为了追求极致的高并发认证效率，MySQL 服务端在启动初始化时，会将 `mysql.user`、`mysql.db` 等权限表的全量内容一次性加载并解析到**内存数据结构（Privilege Hash Buffers）**中；
- 客户端每次发起连接握手时，鉴权模块直接在内存缓存中执行哈希比对，根本不会去实时扫描磁盘上的 `mysql.user` 表；
- 直接使用 `UPDATE` 这类 DML 语句修改系统表，只修改了存储引擎层（InnoDB 数据页与重做日志），根本没有通知权限模块去刷新内存结构。

要使手动 DML 的修改立即生效，必须向服务端显式发送权限重载指令：

```sql
FLUSH PRIVILEGES;
```

执行该指令后，服务端会强制从底层字典表中重新读取所有账户与权限记录，清空并重建内存哈希映射。此时再次验证：
1. 使用 `lisi` 登录：立即报错 `ERROR 1045 (28000): Access denied for user 'lisi'@'...'`；
2. 使用 `wangwu` 登录：验证通过，顺利建立会话。

> **结论**：凡是绕过官方管理 DDL、直接通过 DML（`INSERT`/`UPDATE`/`DELETE`）操作 `mysql` 系统库底层表的操作，必须配合 `FLUSH PRIVILEGES;` 才能使内存状态同步。而在标准管理中，应尽量避免直接对系统表执行 DML。

### 账户删除机制与技术选型对比

当员工离职、业务服务下线或测试账号周期结束时，必须对数据库废弃账户执行清理。MySQL 提供了标准 DDL（`DROP USER`）与底层 DML（`DELETE`）两种截然不同的清理方式。

#### 标准 DDL 方式：DROP USER

官方推荐且标准的用户销毁方式是使用 `DROP USER` 语句：

```sql
DROP USER 'wangwu'@'%';
```

该语法支持批量删除，多个账户之间使用逗号分隔：

```sql
DROP USER 'user1'@'localhost', 'user2'@'%', 'user3'@'192.168.1.100';
```

若被删除的目标账户仅声明了用户名，例如 `DROP USER 'zhangsan';`，其默认行为依然是追加 `@'%'`，即尝试销毁 `'zhangsan'@'%'`。若实际需要删除的是本地账号，必须显式指明：

```sql
DROP USER 'zhangsan'@'localhost';
```

`DROP USER` 属于原生数据定义语言（DDL），具备以下关键特性：
1. **内部原子性清理**：服务端在执行该指令时，不仅抹除 `mysql.user` 中的记录，还会级联遍历并清空 `mysql.db`、`mysql.tables_priv`、`mysql.columns_priv`、`mysql.procs_priv` 以及默认角色映射表中的所有关联权限项；
2. **自动刷新内存**：执行完毕自动触发内存权限缓存的清空与重置，**完全不需要、也不应该执行 `FLUSH PRIVILEGES;`**。

#### 底层 DML 方式：DELETE FROM mysql.user 的残留风险

有些使用者习惯于对系统表执行暴力删除：

```sql
DELETE FROM mysql.user WHERE user = 'zhangsan' AND host = 'localhost';
```

这种直接操作系统表的方式在生产环境中被**明令禁止**，原因在于其存在严重的“权限残留与脏数据碎片”风险。

我们可以将其类比为操作系统中软件的卸载过程：
- **`DROP USER` 就好比使用操作系统的“控制面板 / 官方卸载向导”**：它会依次调用软件自身的卸载程序，逐步清理主程序目录、关联动态链接库、环境变量配置以及系统注册表键值，保证系统环境纤尘不染；
- **`DELETE FROM mysql.user` 就好比直接在文件管理器中把软件的安装文件夹强制 Delete**：可执行文件虽然看似没了，但注册表里残留着大量快捷方式关联项、系统服务列表中留着无法启动的空壳服务，后台依赖的配置文件依旧残留在各个系统子目录中。

```text
+-------------------------------------------------------------------------------+
|                             DROP USER vs DELETE FROM                          |
|                                                                               |
|  [DROP USER 'u'@'h'] (官方安全卸载)                                           |
|       |                                                                       |
|       +--> mysql.user (身份注销)                                              |
|       +--> mysql.db (库级授权级联清除)                                        |
|       +--> mysql.tables_priv (表级授权级联清除)                               |
|       +--> mysql.columns_priv / procs_priv (细粒度授权清除)                   |
|       +--> In-Memory Privilege Buffers (自动同步重构)                         |
|                                                                               |
|  [DELETE FROM mysql.user] (文件级暴力删除)                                    |
|       |                                                                       |
|       +--> mysql.user (仅本表行记录被删)                                      |
|       +--x mysql.db (残存孤儿权限记录!)                                       |
|       +--x mysql.tables_priv (残存孤儿权限记录!)                              |
|       +--x In-Memory Privilege Buffers (未刷新，旧连接可能仍能鉴权!)          |
+-------------------------------------------------------------------------------+
```
*图 3：DROP USER 级联清理 vs DELETE 系统表残留对比*

如果在其他权限表中残存了孤儿记录（Orphaned Privilege Records），未来一旦运维人员重新创建了一个同名同 Host 的新账户，这个新账户在没有任何显式授权的情况下，可能会自动继承当年残留的历史库表访问权限，引发极其严重的数据越权漏洞。

#### 账户销毁对存量活跃会话的生命周期影响

一个值得注意的技术边界是：当管理员执行 `DROP USER 'wangwu'@'%';` 成功后，如果该用户在此之前已经建立了一个交互式连接且处于活跃状态，该会话并不会被服务端当场强行 `KILL` 中断。

在当前已建立的会话中，该用户依然能够执行部分会话内的查询或查看指令。然而：
1. 一旦该用户执行 `quit` 或连接超时断开，后续将彻底无法重新通过鉴权认证；
2. 若管理员需要立即阻断其所有在途操作，必须配套执行管理员命令：先通过 `SHOW PROCESSLIST;` 定位其正在运行的线程 ID（`Id`），随后执行 `KILL [Thread_Id];` 强行切断底层 TCP 连接。

## 106-用户密码的设置和管理
> 对应分集：P106 | 原始标题：《106-用户密码的设置和管理》

在数据库系统的日常运维中，人员的流动与岗位的更迭是不可避免的现实。一个研发人员或 DBA 离职或转岗时，企业通常有两种处置路径：一种是将该用户彻底 `DROP` 销毁，等新人接替时重新建号并逐项授权；另一种则是在既有账户的权限体系已经十分稳定、且与微服务或内部系统高度绑定的情况下，直接保留该账户实体，仅需将连接凭证进行安全交接。此时，核心操作就是**用户密码的重置与修改**。

密码修改看似只是一行简单的命令，但背后涉及到了 MySQL 的版本演进、密码哈希存储字段的变迁，以及生产环境下对特权操作与密码强度的管控。在 MySQL 8.0 中，由于认证机制与安全组件的全面升级，以往在 5.7 乃至更早版本中广为人知的修改手段很多已经失效甚至直接报错。本篇将系统梳理当前用户修改自身密码、管理员重置其他用户密码的标准语法，揭示底层 `authentication_string` 密文存储本质，并深入剖析生产级密码过期与重用限制策略。

### 当前会话修改自身密码的规范实现

无论是超级管理员 `root`，还是权限极低的新建业务账户（如上一讲创建的 `zhangsan`），只要能够成功建立连接，都拥有修改自身认证密码的基本权利。修改当前登录用户的密码主要有两种官方标准方式。

#### 方式一：ALTER USER 配合 USER() 函数（官方首选）

在 MySQL 8.0 中，最为规范、官方最为推荐的改密方式是使用 `ALTER USER` 语法：

```sql
ALTER USER USER() IDENTIFIED BY '新密码';
```

这里的核心细节在于 `USER()` 函数。它是一个内置的无参会话信息函数，能够动态解析并返回当前连接发起者的完整身份认证上下文（即 `'当前用户名'@'当前客户端Host'`）。例如，以 `root` 登录并执行：

```sql
ALTER USER USER() IDENTIFIED BY 'abcabc';
```

执行后，当前连接并不会立即断开，但服务端的内部认证信息已实时持久化。我们可以主动退出客户端并进行双向鉴权测试：

```bash
# 尝试使用旧密码登录
mysql -u root -pabc123
```

服务端立即拒绝接入：

```text
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: YES)
```

随后换用新密码测试：

```bash
mysql -u root -pabcabc
```

验证通过，成功建立会话。由于 `ALTER USER` 属于原生 DDL 操作，其修改结果不仅在底层元数据表中完成事务提交，而且会自动同步刷新内存中的权限缓存缓冲区，**完全不需要执行 `FLUSH PRIVILEGES;`**。

#### 方式二：SET PASSWORD 极简语法

第二种常见写法是直接执行 `SET PASSWORD`：

```sql
SET PASSWORD = '新密码';
```

例如以普通用户 `zhangsan` 登录后，直接在交互式环境中修改自身凭据：

```sql
SET PASSWORD = 'abcabc';
```

随后退出终端并重新登录，同样能够验证新密码生效。这种写法由于指令简短，在日常命令行手动维护中极为流行。

### 密码底层存储机理与 8.0 废弃语法避坑

在许多老旧的技术资料或网络博文中，频繁出现使用 `UPDATE` 语句直接修改系统表密码的案例，甚至伴随调用 `PASSWORD()` 单行加密函数。但在 MySQL 8.0 运行环境下，这些做法不仅被严格禁止，而且会直接触发语法错误。

#### authentication_string 密文哈希字段解析

在 `root` 管理员会话中，我们可以深入 `mysql.user` 表的物理结构来观察密码字段的存储形式：

```sql
DESC mysql.user;
```

在早期 MySQL 版本中，存储密码的字段名为 `password`；而在 MySQL 5.7 及以后的 8.0 版本中，该字段已被彻底重构并更名为：

```sql
`authentication_string` text COLLATE utf8_bin
```

我们执行查询，对比提取 `root` 与 `zhangsan` 的底层实际存储值：

```sql
SELECT host, user, authentication_string FROM mysql.user;
```

输出示例（截取部分密文）：

```text
+-----------+------------------+------------------------------------------------------------------------+
| host      | user             | authentication_string                                                  |
+-----------+------------------+------------------------------------------------------------------------+
| %         | zhangsan         | $caching_sha2_password$5$G8.o7z/K8721...eR4X3B8yW6z1                    |
| localhost | root             | $caching_sha2_password$5$hL9.q1/M9982...aW8K2P1xV0u9                    |
+-----------+------------------+------------------------------------------------------------------------+
```

> **定义**：MySQL 内部绝对不会在元数据表中存储明文密码。无论我们通过 `ALTER USER` 还是 `SET PASSWORD` 传入诸如 `'abcabc'` 的原始字串，服务端都会调用当前用户所绑定的**认证插件（Authentication Plugin）**（MySQL 8.0 默认为 `caching_sha2_password`），引入动态盐值后生成不可逆的高强度哈希串，最终持久化至 `authentication_string` 列中。

#### PASSWORD() 函数的移除与 UPDATE 方式失效

在 MySQL 5.7 时代，常见的一种底层直接刷库写法为：

```sql
-- 注意：以下为 MySQL 8.0 中的错误示范，切勿在 8.0 中执行
UPDATE mysql.user 
SET authentication_string = PASSWORD('abcabc') 
WHERE user = 'root' AND host = 'localhost';
```

> **易错点**：在 MySQL 8.0 中，内置加密函数 `PASSWORD()` 已被官方正式**彻底移除**。如果尝试在 8.0 实例中调用该函数，系统会立即抛出错误：`ERROR 1305 (42000): FUNCTION mysql.PASSWORD does not exist`。

直接使用 `UPDATE` 语法修改密码，不仅存在由于插件算法差异导致无法手动生成合规哈希串的问题，更面临上一讲深入分析过的“内存权限缓存不同步”问题。因此，在 8.0 环境中必须彻底抛弃 `UPDATE` 和 `PASSWORD()` 函数，统一采用 `ALTER USER` 或 `SET PASSWORD`。

### 管理员修改其他账户密码的技术实现

超级管理员 `root` 或拥有 `CREATE USER` / 全局特权的子管理员，承担着重置下属开发账号或服务账号密码的职责。针对其他指定用户的修改，语法逻辑与针对自身的修改高度对称。

#### 方式一：ALTER USER 显式指定宿主与标识

管理员必须在 `ALTER USER` 后精准提供目标用户的 `'用户名'@'主机名'` 二元组：

```sql
ALTER USER 'zhangsan'@'%' IDENTIFIED BY 'hello';
```

此时，服务端完成针对 `'zhangsan'@'%'` 账户记录的更新与密文重构。

```text
+---------------------+     ALTER USER 'zhangsan'@'%'     +---------------------+
|    Admin Session    | --------------------------------> |    MySQL Server     |
|   (root@localhost)  |                                   |  (Update user table |
|                     |                                   |  & In-Memory Cache) |
|                     |                                   +---------------------+
|                     |                                              |
|                     |                                              | (Asynchronous)
|                     |                                              v
|  User Active Term   |  Existing TCP socket stays alive   +---------------------+
|   (zhangsan@%)      | ---------------------------------> | Normal Query (OK)   |
|                     |  Session Closed (quit)             +---------------------+
|                     |                                              |
|  User Re-login      |  mysql -uzhangsan -phello (OK!)              v
|   (zhangsan@%)      | ---------------------------------> +---------------------+
|                     |  mysql -uzhangsan -pabcabc (FAIL!) | Fresh Auth Denied   |
+---------------------+                                    +---------------------+
```
*图 1：管理员修改密码后存量活跃连接与新建会话的鉴权差异*

> **提示**：当管理员在后台修改了某个用户的密码时，该用户如果当前正打开着命令行并保持连接，其**现存的 TCP 连接和会话不会被服务端强行阻断**，仍然可以继续执行查询。只有当该用户退出会话、或者发起新的连接握手时，新密码的约束才会强制介入。

#### 方式二：SET PASSWORD FOR 语法

另一种等价的标准语法是追加 `FOR` 关键字指定受体：

```sql
SET PASSWORD FOR 'zhangsan'@'%' = 'hello123';
```

该语法结构具有鲜明的语法要素：
1. 必须包含 `FOR 'user'@'host'`，明确指定操作受体；
2. 赋值符号必须使用等号 `=`，后接单引号包裹的全新明文密码；
3. 执行成功后同样立即自动刷新底层认证缓存。

### 生产级密码安全管理策略

在金融、电信及大型互联网企业的等保合规要求中，静态长久不变的弱密码是最大的安全风险源之一。MySQL 8.0 内核层面提供了完善的**密码生命周期与重用审计策略**，支持从“密码过期”与“历史重用限制”两个核心维度进行全局或针对性防御。

```text
+---------------------------------------------------------------------------------+
|                        MySQL 8.0 密码安全策略防御体系                            |
|                                                                                 |
|  +-------------------------------------+   +---------------------------------+  |
|  |     密码过期策略 (Expiration)        |   |     密码重用策略 (Reuse Limit)   |  |
|  +-------------------------------------+   +---------------------------------+  |
|  | - 全局生命周期:                     |   | - 历史次数限制:                 |  |
|  |   default_password_lifetime         |   |   password_history              |  |
|  | - 个人级覆盖:                       |   | - 历史时间窗限制:               |  |
|  |   PASSWORD EXPIRE INTERVAL N DAY    |   |   password_reuse_interval       |  |
|  | - 手动即时吊销:                     |   |                                 |  |
|  |   PASSWORD EXPIRE (沙箱登录模式)    |   | 杜绝"假性忘记密码后改回旧密码"  |  |
|  +-------------------------------------+   +---------------------------------+  |
+---------------------------------------------------------------------------------+
```
*图 2：MySQL 8.0 企业级密码安全策略体系构成*

#### 密码过期策略（Password Expiration）

密码过期机制用于强制要求用户定期更换凭据，避免因凭据泄露导致系统长期处于潜伏入侵状态。

##### 手动强制即刻过期与沙箱限制现象

管理员可以针对疑似凭据泄露的账户执行即时过期指令：

```sql
ALTER USER 'kangshifu'@'localhost' PASSWORD EXPIRE;
```

该操作会触发一个极其特殊的系统状态——**受限沙箱登录状态**：
- 当用户 `kangshifu` 发起登录时，输入原密码依然能够成功通过 TCP 握手并进入终端；
- 但登录后一旦尝试执行任何业务查询（例如 `SELECT * FROM emp1;` 或 `SHOW DATABASES;`），服务端会当场拦截并拒绝执行，抛出必须先修改密码的错误提示：

```text
ERROR 1820 (HY000): You must reset your password using ALTER USER statement before executing this statement.
```

- 该用户在当前连接下唯一被允许执行的操作，正是 `ALTER USER USER() IDENTIFIED BY '新密码';`。只有自救重置密码完成后，会话才会恢复正常查询能力。

##### 全局自动定期过期配置

通过系统全局变量可以统一设定全服生命周期：

```sql
-- 动态设置全局密码有效期为 180 天
SET PERSIST default_password_lifetime = 180;
```

该变量默认值为 `0`，表示全局禁用自动过期（即密码永久有效）。若设置为 180，则所有用户在创建满 180 天后，登录即被自动标记为过期状态。该参数也可以持久化写入 MySQL 配置文件（Linux 下为 `my.cnf`，Windows 下为 `my.ini`）的 `[mysqld]` 模块中：

```ini
[mysqld]
default_password_lifetime = 180
```

##### 单个用户维度的过期策略覆盖

全局策略可以被账户级专属配置精细化覆盖：

```sql
-- 创建账户时明确指定 90 天后过期
CREATE USER 'user_test'@'%' IDENTIFIED BY 'abc123' 
PASSWORD EXPIRE INTERVAL 90 DAY;

-- 修改既有账户为永不过期（常用于无人值守的后台持久连接服务账户）
ALTER USER 'app_backend'@'%' PASSWORD EXPIRE NEVER;

-- 重置账户策略，重新跟随全局默认规则
ALTER USER 'user_test'@'%' PASSWORD EXPIRE DEFAULT;
```

#### 密码重用限制策略（Password Reuse Policy）

在实际生活中存在一种典型现象：很多用户在使用手机应用或银行卡系统时，自以为“忘记了密码”，点击找回密码流程并一路完成手机短信或身份核验，但在最终输入“新密码”并确认时，界面赫然弹出提示：“**新密码不能与最近一次使用的密码相同**”。此时用户才恍然大悟，原来自己正在输入的新密码就是之前用的旧密码。

在企业安全规范中，如果允许用户在改密时重新填入刚刚废弃的旧密码，整个定期改密的防御机制就会彻底沦为空谈。MySQL 8.0 引入了两种基于历史维度的重用拦截机制。

##### 基于更改次数的重用限制（Password History）

该策略规定新密码不能与最近 `$N$` 次使用过的历史密码发生碰撞。

- **全局参数**：`password_history`，默认为 `0`（不开启历史比对）。
- **用户级语法**：

```sql
-- 要求张三改密时，不能与最近 3 次使用过的密码重复
ALTER USER 'zhangsan'@'%' PASSWORD HISTORY 3;

-- 恢复为跟随系统全局设定
ALTER USER 'zhangsan'@'%' PASSWORD HISTORY DEFAULT;
```

当配置为 3 时，服务端会在内部安全表中记录张三最近 3 次改密的哈希快照。若用户第四次改密尝试改回前 3 次内的任意一个口令，执行时将被直接阻断。

##### 基于时间窗口的重用限制（Password Reuse Interval）

该策略从物理时间跨度实施限制，规定新密码不能与最近 `$M$` 天之内使用过的任何密码相同。

- **全局参数**：`password_reuse_interval`，单位为天，默认为 `0`（不开启时间窗比对）。
- **用户级语法**：

```sql
-- 要求张三在 60 天内不得重新循环使用过往密码
ALTER USER 'zhangsan'@'%' PASSWORD REUSE INTERVAL 60 DAY;

-- 恢复为跟随系统全局设定
ALTER USER 'zhangsan'@'%' PASSWORD REUSE INTERVAL DEFAULT;
```

通过将 `password_history` 与 `password_reuse_interval` 配合使用（二者任意一项被触发均会拦截），并叠加基础篇中介绍的 `validate_password` 强度校验组件（强制大写字母、小写字母、数字及特殊符号组合），即可构建起符合金融级安全审计标准的企业级数据库凭据防护网。

## 107-权限管理与访问控制
> 对应分集：P107 | 原始标题：《107-权限管理与访问控制》

在上一讲中，我们成功创建了全新的普通用户，并验证了其通过账号密码登录数据库实例的能力。然而，刚刚创建并登录的普通用户在执行 `SHOW DATABASES;` 时，只能看到诸如 `information_schema` 等极少数系统默认视图，根本无法感知任何业务数据库，更无法对业务数据表执行增删改查。“只能连入实例，却什么都干不了”，这样的账户在实际生产中毫无业务价值。

数据库安全的核心使命，绝不仅是验证用户的身份是否合法，更在于精确界定该用户**在登录之后能够做什么、不能做什么**。这就是权限管理的范畴。如果说一个国家的行政体系中，北京市市长不能越界插手河北省的政务，那么在数据库中，一个仅被允许对订单表进行 `SELECT` 统计的只读分析账户，就坚决不能拥有执行 `UPDATE` 或 `DELETE` 的操作能力。本篇将系统剖析 MySQL 的权限体系、最小分配原则、`GRANT` 与 `REVOKE` 语法精要，并深入底层系统字典表，彻底揭秘 MySQL 在握手与执行 SQL 时的“双阶段访问控制”流向。

---

### 权限分类与分配的最小化原则

在掌握具体命令之前，首先必须对 MySQL 的权限清单及其在工业级生产环境下的落地红线建立全局认知。

#### 系统支持的 62 项权限概貌

通过在超级管理员终端执行以下指令，可以列出当前 MySQL 实例支持的全部特权清单：

```sql
SHOW PRIVILEGES;
```

该指令会返回一个包含 62 项权限的矩阵，详尽列出了每项权限的名称、上下文生效级别以及功能说明。从系统架构与管理粒度来看，这些权限可以归纳为三大核心层级：

| 权限层级 | 典型特权项 | 生效上下文与作用范围 |
| :--- | :--- | :--- |
| **库 / 表级别** | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `INDEX`, `ALTER` | 控制用户对特定数据库或数据表的结构定义（DDL）与数据读写（DML） |
| **列级别** | `SELECT(col1)`, `INSERT(col1, col2)`, `UPDATE(col1)` | 极细粒度控制。允许用户仅对某张表中的特定字段进行查询或修改，屏蔽敏感列 |
| **过程 / 函数级别** | `EXECUTE`, `ALTER ROUTINE`, `CREATE ROUTINE` | 控制存储过程、存储函数以及触发器的定义与调用执行资格 |

#### 生产环境权限分配的四大黄金准则

1. **最小权限原则（Principle of Least Privilege）**：只赋予能够满足业务功能正常运转的绝对最小权限集。用户对某张表只需要查阅，就严禁下放 `INSERT`、`UPDATE` 与 `DELETE`；能给只读的绝不给写，能给 DML 的绝不给 DDL。防范有意越权的同时，杜绝因程序 Bug 或人为手滑造成的灾难性破坏；
2. **严密限制登录主机（Host 绑定）**：严禁无脑使用通配符 `%`。正如高校内网才能登录知网下载论文、离开校园 IP 范围即被拦截一样，生产库账户必须精准绑定到具体的业务微服务集群 IP（如 `192.168.10.%`）或堡垒机 IP；
3. **强制凭据复杂度策略**：为每一个独立账户配置高强度复合凭据，并启用历史重用限制；
4. **定期审计与动态收缩**：周期性审计长期闲置账户，针对转岗、降职人员及时收回富余权限，废弃账户果断销毁。

### 权限授予：GRANT 语法、权限叠加与 WITH GRANT OPTION

MySQL 提供了标准的 `GRANT` 语句用于向账户赋予单项或多项特权。

#### GRANT 基础语法与权限横向纵向维度

授予权限的标准语法如下：

```sql
GRANT 权限列表 ON 数据库名.数据表名 TO '用户名'@'主机名';
```

在权限控制的抽象模型中，存在两个正交的维度：
- **横向范围**：代表用户可以接触到的物理数据资产边界，即 `ON` 后面指定的对象。可以是全局所有库表（`*.*`）、特定库的所有表（`dbtest1.*`），或者特定库的特定表（`dbtest1.emp1`）；
- **纵向程度**：代表用户在既定数据资产上能够施加的操作深度，即 `GRANT` 紧跟的动作。是只能查看（`SELECT`），还是允许变更（`UPDATE`），抑或是具有结构擦除能力（`DROP`）。

```text
+-------------------------------------------------------------------------+
|                         权限分配的正交维度模型                          |
|                                                                         |
|  纵向程度 (Privilege Levels)                                            |
|     ^                                                                   |
|     |  [DROP / ALTER] (DDL 破坏性变更)                                  |
|     |  [DELETE / UPDATE / INSERT] (DML 数据写操作)                      |
|     |  [SELECT] (只读操作)                                              |
|     +---------------------------------------------------------------->  |
|        dbtest1.emp1           dbtest1.*                *.*              |
|        (单表粒度)             (单库粒度)             (全局实例粒度)     |
|                                                     横向范围 (Data Scope) |
+-------------------------------------------------------------------------+
```
*图 1：权限配置的横向范围与纵向程度正交模型*

例如，要求普通用户 `zhangsan` 能够对 `dbtest1` 数据库下的所有表执行查询与更新操作：

```sql
GRANT SELECT, UPDATE ON dbtest1.* TO 'zhangsan'@'%';
```

#### 权限生效验证与并集叠加（Union）机制

授权完成后，切换至 `zhangsan` 用户的终端进行验证：

```bash
mysql -u zhangsan -pabc123
```

此时执行 `SHOW DATABASES;`，发现结果中已经正常显现出 `dbtest1`；切换至该库并对 `emp1` 进行验证：

```sql
USE dbtest1;

-- 验证 SELECT 权限：查询成功
SELECT * FROM emp1;

-- 验证 UPDATE 权限：更新成功
UPDATE emp1 SET last_name = 'Jerry' WHERE id = 1;

-- 验证未授予的 DELETE 权限：服务端当场拦截
DELETE FROM emp1 WHERE id = 1;
```

针对未授权的 `DELETE` 语句，MySQL 立即抛出拦截报错：

```text
ERROR 1142 (42000): DELETE command denied to user 'zhangsan'@'localhost' for table 'emp1'
```

若业务后续需要补充删除权限，管理员再次执行：

```sql
GRANT DELETE ON dbtest1.* TO 'zhangsan'@'%';
```

> **结论**：多次针对同一用户执行 `GRANT` 语句，其底层的权限计算方式是**自动合并取并集（Union）**，新追加的权限绝不会冲掉或覆盖已有的既有权限。此时 `zhangsan` 同时拥有了 `SELECT`、`UPDATE` 与 `DELETE` 三项特权。

#### ALL PRIVILEGES 与 WITH GRANT OPTION 的深层区别

在很多快速初始化脚本中，经常能看到赋予全量权限的操作：

```sql
CREATE USER 'lisi'@'%' IDENTIFIED BY 'abc123';
GRANT ALL PRIVILEGES ON *.* TO 'lisi'@'%';
```

执行后，`lisi` 账户对整台实例的所有库、所有表拥有了如同皇帝般的支配权，可以任意执行 DDL 与 DML。

此时产生了一个核心问题：**拥有 `ALL PRIVILEGES ON *.*` 的用户 `lisi`，在权限体系上是否等同于超级管理员 `root`？**

答案是**坚决否定**的。二者的根本差异在于**转授权限的能力**：
- `root` 账户不仅拥有所有的库表操作权，还天然持有 `WITH GRANT OPTION` 特权；
- `lisi` 虽然自身能做任何读写，但他**无法将自己所拥有的权限再转授给第三个用户（如王五）**。当 `lisi` 尝试执行 `GRANT SELECT ON ... TO 'wangwu'` 时，系统会当场拒绝；
- 如果确实需要让一个下级管理员拥有代为授权的资格，必须在授权指令的末尾显式追加转授标记：

```sql
GRANT ALL PRIVILEGES ON *.* TO 'lisi'@'%' WITH GRANT OPTION;
```

查看用户权限时（`SHOW GRANTS FOR 'lisi'@'%';`），末尾是否包含 `WITH GRANT OPTION` 字样，是判定其是否具备“管理特权转授能力”的唯一标识。

### 权限回收：REVOKE 语法与生命周期闭环

在软件开发中，有集合的 `add()` 就必然有对应的 `remove()`，有向内存容器放入数据的机制，就必须有向外提取销毁的通路。在真实企业管理中，员工的职责会动态调整，一旦发生转岗或安全降级，必须能够平稳收回权限。

#### REVOKE 语法规范

权限回收的标准语法如下：

```sql
REVOKE 权限列表 ON 数据库名.数据表名 FROM '用户名'@'主机名';
```

> **提示**：对比授权与回收的英文语法结构：授权是把权限交付给用户，因此使用的是目标介词 `TO`；回收是从用户手中将权限剥离抽回，因此使用的是源介词 `FROM`。

#### 实操演示与会话缓存重载

收回 `zhangsan` 针对 `dbtest1` 的全量查询权限：

```sql
REVOKE SELECT ON dbtest1.* FROM 'zhangsan'@'%';
```

执行后再次查看张三的权限列表：

```sql
SHOW GRANTS FOR 'zhangsan'@'%';
```

结果中仅剩下 `UPDATE` 与 `DELETE` 权限，`SELECT` 已被精确剥离。若张三尝试重新执行 `SELECT * FROM emp1;`，系统将抛出 `SELECT command denied`。

若需要将某个用户的特权彻底清空：

```sql
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'lisi'@'%';
```

### 底层元数据权限四表（四级权限架构）

MySQL 的权限数据并不是虚无缥缈的运行时变量，而是分层持久化在 `mysql` 核心系统库中。理解底层的**权限四表**结构，是搞懂 MySQL 鉴权机理的核心。

```text
+------------------------------------------------------------------------------+
|                         MySQL 系统权限分级物理表结构                         |
|                                                                              |
|  +------------------------------------------------------------------------+  |
|  | mysql.user (全局层级)                                                  |  |
|  | PK: (Host, User)                                                       |  |
|  | 包含身份凭据、全局权限位 (Select_priv...)、资源配额 (max_questions...) |  |
|  +------------------------------------------------------------------------+  |
|                                      |                                       |
|                                      v                                       |
|  +------------------------------------------------------------------------+  |
|  | mysql.db (数据库层级)                                                  |  |
|  | PK: (Host, Db, User)                                                  |  |
|  | 声明特定用户对特定 Schema 的全库操作权                                |  |
|  +------------------------------------------------------------------------+  |
|                                      |                                       |
|                                      v                                       |
|  +------------------------------------------------------------------------+  |
|  | mysql.tables_priv (数据表层级)                                         |  |
|  | PK: (Host, Db, User, Table_name)                                       |  |
|  | Table_priv 字段采用 SET 集合类型记录具体支持的表级 DML/DDL 特权         |  |
|  +------------------------------------------------------------------------+  |
|                                      |                                       |
|                                      v                                       |
|  +------------------------------------------------------------------------+  |
|  | mysql.columns_priv (数据列层级)                                        |  |
|  | PK: (Host, Db, User, Table_name, Column_name)                           |  |
|  | Column_priv 记录最细粒度的字段级访问权                                 |  |
|  +------------------------------------------------------------------------+  |
+------------------------------------------------------------------------------+
```
*图 2：MySQL 权限分级元数据表物理结构及主键拓扑*

#### 全局层级：mysql.user 表

`mysql.user` 表是权限层级的总入口，其主键为 `(Host, User)`。该表共包含五十余个字段，划分为四大核心职能区：
1. **身份认证区**：`Host`、`User`、`authentication_string`、`plugin` 等，决定是否允许用户接入；
2. **全局权限区**：如 `Select_priv`、`Insert_priv`、`Update_priv` 等。数据类型均为 `ENUM('N', 'Y')`，默认值为 `'N'`。**一旦这里的某个权限位被置为 `'Y'`，它将作为超级全局权限穿透作用于该实例下的所有数据库、所有表**；
3. **安全通道区**：`ssl_type`、`ssl_cipher` 等 SSL/TLS 加密通信配置；
4. **资源配额区（Resource Limits）**：
   - `max_questions`：每小时允许该用户执行的 SQL 查询（Query）最大次数；
   - `max_updates`：每小时允许执行的数据修改操作（DML/DDL）最大次数；
   - `max_connections`：每小时允许该用户发起的握手连接最大频次；
   - `max_user_connections`：该用户同时允许建立的最大并发活跃连接数。

#### 数据库层级：mysql.db 表

`mysql.db` 记录用户在特定数据库作用域内的权限分配，其主键由三元组复合而成：

```sql
PRIMARY KEY (`Host`, `Db`, `User`)
```

表中包含了针对该数据库作用域的所有常见特权字段。如果某个普通用户仅在 `dbtest1` 上被赋予了 `SELECT`，那么在 `mysql.user` 中其 `Select_priv` 依然为 `'N'`，而在 `mysql.db` 中对应记录的 `Select_priv` 则为 `'Y'`。

#### 数据表层级：mysql.tables_priv 表

当授权细化到单张表时（例如 `ON dbtest1.emp1`），数据记录落入 `mysql.tables_priv`。其主键拓展为四元组：

```sql
PRIMARY KEY (`Host`, `Db`, `User`, `Table_name`)
```

该表的核心特性在于其权限字段定义：`Table_priv` 与 `Column_priv` 字段不再采用枚举，而是采用 `SET` 集合类型（`set('Select','Insert','Update','Delete','Create','Drop',...)`），支持在单列中以位图方式复合记录多个表级特权。

#### 数据列层级：mysql.columns_priv 表

如果业务仅允许用户查看员工表的工号与姓名，严禁触碰薪资列，授权精确到列时记录写入本表。其联合主键由五元组构成：

```sql
PRIMARY KEY (`Host`, `Db`, `User`, `Table_name`, `Column_name`)
```

这是 MySQL 内核支持的最细粒度权限控制机制。此外，针对存储过程和函数的执行权，则独立记录在 `mysql.procs_priv` 表中。

### 访问控制全流程：连接核实与请求核实的双阶段演进

当 MySQL 启动时，服务端进程会一次性将上述权限表中的全量记录加载并解析至内存中的权限散列桶（Privilege Buffers）中。在用户与 MySQL 的整个交互生命周期中，内核的访问控制严格分为两个前后衔接的阶段。

```text
+-------------------+
|  Client Connects  |
+-------------------+
          |
          v
============================= 阶段一：连接核实阶段 =============================
[ Check mysql.user ]
  - Does Host match incoming client IP?
  - Does User exist?
  - Does password hash match authentication_string?
          |
          +---> [NO]  --> Reject Connection (Access Denied: 1045)
          |
          v [YES]
   Connection Accepted
          |
          v
============================= 阶段二：请求核实阶段 =============================
[ Client executes SQL: e.g. SELECT * FROM dbtest1.emp1 ]
          |
          v
[ Level 1: mysql.user (Global) ]
  Is Select_priv == 'Y'?
          |
          +---> [YES] ----------------------------+ (Short-circuit Pass)
          |                                       |
          v [NO]                                  |
[ Level 2: mysql.db (Schema) ]                    |
  Is Select_priv for dbtest1 == 'Y'?              |
          |                                       |
          +---> [YES] ----------------------------+ (Pass)
          |                                       |
          v [NO]                                  |
[ Level 3: mysql.tables_priv (Table) ]            |
  Does Table_priv for emp1 include 'Select'?      |
          |                                       |
          +---> [YES] ----------------------------+ (Pass)
          |                                       |
          v [NO]                                  |
[ Level 4: mysql.columns_priv (Column) ]          |
  Are all queried columns authorized?             |
          |                                       |
          +---> [YES] ----------------------------+ (Pass)
          |                                       |
          v [NO]                                  v
+-----------------------------+         +-----------------------------+
| Reject SQL (Command Denied) |         | Execute SQL & Return Data   |
+-----------------------------+         +-----------------------------+
```
*图 3：MySQL 双阶段访问控制与权限漏斗穿透判定流程图*

#### 阶段一：连接核实阶段（Connection Verification）

当客户端发起 TCP 握手并递交身份凭据时触发。

服务端优先在内存的 `mysql.user` 结构中检索：
1. **网络 Host 匹配**：检查发起连接的物理客户端 IP，是否能够被用户配置的 Host（具体 IP、网段掩码或通配符 `%`）所成功命中；
2. **账号与口令核验**：提取该用户的 `authentication_string` 密文，通过绑定的身份认证插件与客户端传输的握手哈希进行安全比对。

若以上校验任意一项不吻合，连接在握手期即刻被强行终止，返回经典的 `ERROR 1045 (28000): Access denied` 错误；只有全部核验无误，TCP 会话方能正式确立，并转入就绪态。

#### 阶段二：请求核实阶段（Request Verification）

一旦连接确立，用户在交互终端发送的**每一条独立 SQL 语句**，都必须实时经过请求核实阶段。该阶段遵循**“由宽到窄、逐层穿透、短路退出”**的漏斗鉴权模型：

1. **第一层：全局权限核查（`mysql.user`）**
   - 内核首先扫描 `mysql.user`。如果该用户在该表对应的特权列（如 `Select_priv`）已经被赋予了 `'Y'`，则判定该用户对全库全表拥有全局查询权；
   - **短路放行**：一旦在此处命中 `'Y'`，鉴权引擎直接放行并执行该 SQL，**绝不会再多余消耗 CPU 去检索后续的低层级权限表**；
2. **第二层：数据库级权限核查（`mysql.db`）**
   - 若全局表中为 `'N'`，鉴权引擎下潜至第二层 `mysql.db`；
   - 检查目标数据库（如 `dbtest1`）在当前用户下是否被显式赋予了该操作的特权。若为 `'Y'`，同样放行并执行；
3. **第三层：数据表级权限核查（`mysql.tables_priv`）**
   - 若库级特权依然未开放，下潜至数据表层级；
   - 检查目标表（如 `emp1`）的 `Table_priv` 集合是否包含当前操作指令。若命中，放行；
4. **第四层：数据列级权限核查（`mysql.columns_priv`）**
   - 若表级未赋予完整权限，且 SQL 请求触及具体字段，下潜至最底层的 `mysql.columns_priv`，逐一比对该 SQL 语句中所投影或涉及到的每一个具体字段名；
   - 只要有任意一个被访问的字段未在授权清单中，即刻终止执行。

如果请求穿透了全部四层元数据结构仍未获得许可，MySQL 立即拦截该指令，向客户端返回 `ERROR 1142: command denied to user` 越权报错。这种多级漏斗的短路设计，既保障了企业级微粒度访问控制的严密性，又在全局或库级授权场景下将权限判定的性能开销降到了最低。

## 108-角色的使用
> 对应分集：P108 | 原始标题：《108-角色的使用》

在 MySQL 8.0 之前，数据库权限管理模型本质上是二维平面的：系统一端是“用户”，另一端是离散的“62 项具体权限”。当一个企业仅有几位研发人员时，管理员为张三、李四手动敲几行 `GRANT` 尚能勉强应付；但在现代化企业协作与微服务架构中，开发团队、运维团队、测试团队、BI 报表团队可能有数十上百人，同一岗位的员工所需的权限高度重叠。如果每次入职一个测试人员，DBA 都要机械地把这十几个库表权限一条条赋过去，不仅运维成本极高，而且极易遗漏配置，在人员离职或转岗时更会形成难以清查的“权限黑洞”。

为了解决权限离散化带来的管理瓶颈，MySQL 8.0 正式引入了**角色（Role）**这一里程碑特性。事实上，类似的设计早在 Oracle 10g 等成熟商用数据库中就已广泛应用，MySQL 8.0 充分借鉴并标准化了该设计。在引入角色后，权限被有效“组件化”与“模板化”。本篇将从角色的抽象概念切入，系统梳理角色自身生命周期（上篇）与用户绑定应用（下篇），并深度剖析新手极易碰壁的“角色赋予后却无法使用”的未激活状态与底层解决方案。

### 角色抽象概念与权限体系解耦

要透彻理解角色，可以从生活常识、面向对象编程思想以及企业组织架构三个视角建立清晰认知。

#### 什么是角色

在影视剧中，导演在选角时首先定义的是“角色”本身——例如“江湖大侠”或“反派谋士”，角色本身预设了一整套言行举止与特征规范；演员张三进入剧组演了大侠，他就拥有了大侠的身份，李四接替大侠，李四也同样拥有该身份。

> **定义**：在 MySQL 中，**角色本质上就是一组权限的具名集合（A named collection of privileges）**。角色自身并不是一个用来直接登录服务器的实体账户，而是一个权限包容器。

我们可以向角色中批量添加（GRANT）或移除（REVOKE）各项具体的库表级特权；当把这个打包好的角色授予某个具体用户时，该用户便瞬间继承了该角色所囊括的全部权限。

```text
+-------------------------------------------------------------------------+
|                  无角色直连模式 vs 角色解耦抽象模型                      |
|                                                                         |
|  [旧版直连模式：N×M 离散管理]                                            |
|   User A ----+-----> SELECT ON db.*                                     |
|              +-----> UPDATE ON db.tbl1                                  |
|   User B ----+-----> (每次加人必须逐项机械重复授权，极易漏配)            |
|   User C ----+                                                          |
|                                                                         |
|  [8.0 角色解耦模式：模块化封装]                                         |
|   Privileges -------> +---------------------+                           |
|   - SELECT db.*       |     Role: DEV       |                           |
|   - UPDATE db.tbl1    +---------------------+                           |
|   - INSERT db.tbl2               |                                      |
|                                  +--------> User A                      |
|                                  +--------> User B (一键继承，标准统一)  |
|                                  +--------> User C                      |
+-------------------------------------------------------------------------+
```
*图 1：旧版用户直接绑定离散权限 vs 8.0 引入角色解耦的架构演化对比*

#### Java 接口比喻与企业组织架构映射

- **面向对象视角（接口与实现类）**：角色就像 Java 语言中的**接口（Interface）**，它声明了一套行为规范，但不能直接通过 `new Interface()` 去创建运行时会话；用户就如同**具体的实现类（Class）和对象**。接口必须由具体的类去实现，角色也必须授予真实的用户；
- **企业组织架构视角**：在小微作坊中，老板对两三名员工单线布置任务；而像华为这样拥有数十万员工的巨型企业，各事业群必然严谨设立“研发主管”、“销售经理”、“HR 专员”等标准岗位角色。公司招募北京区销售经理王五，只需把“销售经理”的角色权限授予王五即可；当王五调岗，只需剥离该角色并换上新角色，无需逐个数据库查阅收缩。

### 角色生命周期与权限绑定（角色与权限的关系）

角色管理的完整流程分为两大部分：上篇聚焦于角色自身的创建、授权、查验与销毁；下篇聚焦于角色与用户之间的绑定、激活与撤销。

#### 创建角色：CREATE ROLE

创建角色的标准语法与创建用户高度相似：

```sql
CREATE ROLE '角色名'[@'主机名'];
```

如果不指定主机名，默认缺省依然为 `'%'`。在超级管理员 `root` 会话中，支持同时批量创建多个角色：

```sql
CREATE ROLE 'manager'@'%', 'boss'@'%', 'admin'@'%';
```

> **提示**：如果我们此时在 `mysql` 系统库中执行 `SELECT host, user FROM mysql.user;`，会发现刚刚创建的 `manager` 和 `boss` 赫然列在其中！在底层存储上，MySQL 8.0 的角色复用了 `mysql.user` 表的物理结构，但角色记录的 `account_locked` 标志位默认为 `'Y'`，且没有登录密码，因此系统严禁任何人直接拿角色名发起 TCP 登录握手。

#### 为角色赋予权限：GRANT TO ROLE

角色的权限绑定语法与普通用户完全一致：

```sql
GRANT 权限列表 ON 作用域 TO '角色名';
```

例如，我们为部门经理角色 `manager` 分配 `dbtest1` 库的全表查询与修改权限：

```sql
GRANT SELECT, UPDATE ON dbtest1.* TO 'manager';
```

为老板角色 `boss` 分配整台服务器的全局最高控制权：

```sql
GRANT ALL PRIVILEGES ON *.* TO 'boss'@'%';
```

#### 查看角色的权限：SHOW GRANTS FOR ROLE

查验角色内部包裹的具体权限项：

```sql
SHOW GRANTS FOR 'manager';
```

终端返回如下：

```text
+---------------------------------------------------------------------+
| Grants for manager@%                                                |
+---------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `manager`@`%`                                 |
| GRANT SELECT, UPDATE ON `dbtest1`.* TO `manager`@`%`                |
+---------------------------------------------------------------------+
```

#### 回收角色的权限：REVOKE FROM ROLE

当业务规范变动，要求收回经理角色的修改权限、仅保留只读权限时：

```sql
REVOKE UPDATE ON dbtest1.* FROM 'manager';
```

再次执行 `SHOW GRANTS FOR 'manager';`，会发现 `UPDATE` 已被剔除，角色容器中的规则被实时更新。

#### 销毁废弃角色：DROP ROLE

对于废弃不用的角色，使用 `DROP ROLE` 进行物理清除：

```sql
DROP ROLE 'admin';
```

执行后，如果对已删除的实体执行 `SHOW GRANTS FOR 'admin';`，服务端将立即报错提示该角色/授权不存在。

### 角色绑定、激活陷阱与权限生效（角色与用户的关系）

完成了角色模板的定义后，接下来必须将角色赋给具体用户，并完成最终的鉴权落地。

#### 用户创建与角色赋予

我们首先创建一个没有任何多余权限的全新普通用户 `wangwu`：

```sql
CREATE USER 'wangwu'@'%' IDENTIFIED BY 'abc123';
```

随后，将已配置好的 `manager` 角色授予该用户：

```sql
GRANT 'manager' TO 'wangwu'@'%';
```

在超级管理员终端核实王五的权限绑定状态：

```sql
SHOW GRANTS FOR 'wangwu'@'%';
```

```text
+-------------------------------------------------------------+
| Grants for wangwu@%                                         |
+-------------------------------------------------------------+
| GRANT USAGE ON *.* TO `wangwu`@`%`                          |
| GRANT `manager`@`%` TO `wangwu`@`%`                         |
+-------------------------------------------------------------+
```

清单明确显示，`wangwu` 已经成功持有了 `manager@%` 角色。

#### 现场反面案例：赋予角色后依然无法访问的“激活陷阱”

此时打开另一个终端，使用新用户 `wangwu` 登录 MySQL 并查看数据库：

```bash
mysql -u wangwu -pabc123
```

```sql
SHOW DATABASES;
```

终端令人大跌眼镜的输出如下：

```text
+--------------------+
| Database           |
+--------------------+
| information_schema |
+--------------------+
1 row in set (0.00 sec)
```

**王五明明已经被赋予了拥有 `dbtest1` 查询权限的 `manager` 角色，但进入系统后依然看不到 `dbtest1`！即使退出终端重登、或者执行 `FLUSH PRIVILEGES;`，都毫无变化。**

导致该现象的根本原因在于 MySQL 8.0 核心机制设计：
> **易错点**：在 MySQL 8.0 中，**赋予给用户的角色默认处于“未激活状态（Inactive / Disabled）”**！用户虽然持有了角色的头衔，但该角色包含的权限在连接建立后并没有自动注入到当前鉴权上下文中。

我们可以通过会话状态函数直接印证这一事实：

```sql
SELECT CURRENT_ROLE();
```

返回结果：

```text
+----------------+
| CURRENT_ROLE() |
+----------------+
| NONE           |
+----------------+
```

输出 `NONE` 明确告知我们：当前没有任何生效的角色！

```text
+---------------------------------------------------------------------------------+
|                       MySQL 8.0 角色激活状态机转换流向                          |
|                                                                                 |
|   GRANT 'manager' TO 'wangwu'@'%'                                               |
|              |                                                                  |
|              v                                                                  |
|   +----------------------------------------------------+                        |
|   |   State 1: Granted but Inactive (未激活态)         |                        |
|   |   - SHOW GRANTS shows: `manager`@`%`               |                        |
|   |   - SELECT CURRENT_ROLE() returns: NONE            |                        |
|   |   - Privileges inside role are FROZEN (不可用!)    |                        |
|   +----------------------------------------------------+                        |
|              |                                                                  |
|              |  SET DEFAULT ROLE manager TO 'wangwu'@'%'                        |
|              |  OR SET GLOBAL activate_all_roles_on_login = ON                  |
|              v                                                                  |
|   +----------------------------------------------------+                        |
|   |   State 2: Active Role (激活就绪态)                |                        |
|   |   - Re-login triggers session role initialization  |                        |
|   |   - SELECT CURRENT_ROLE() returns: `manager`@`%`   |                        |
|   |   - Privileges (SELECT on dbtest1.*) UNLOCKED!     |                        |
|   +----------------------------------------------------+                        |
+---------------------------------------------------------------------------------+
```
*图 2：角色从“已授予”到“激活就绪”的状态转移时序*

#### 角色激活的双重解决方案

要破除“未激活陷阱”，有两种标准手段。

##### 方案一：显式配置用户的默认角色（SET DEFAULT ROLE）

管理员可以针对特定用户，将其被授予的角色设定为登录时的默认激活角色：

```sql
-- 将 manager 设定为王五登录时的默认角色
SET DEFAULT ROLE manager TO 'wangwu'@'%';

-- 若被授予了多个角色，可直接使用 ALL 关键字全量激活
SET DEFAULT ROLE ALL TO 'wangwu'@'%';
```

配置完毕后，王五在自身终端执行 `quit` 退出并重新登录：

```bash
mysql -u wangwu -pabc123
```

再次执行探针函数验证：

```sql
SELECT CURRENT_ROLE();
```

输出如下：

```text
+----------------+
| CURRENT_ROLE() |
+----------------+
| `manager`@`%`  |
+----------------+
```

此时执行 `SHOW DATABASES;`，`dbtest1` 赫然在列；随后执行业务查询：

```sql
USE dbtest1;
SELECT * FROM emp1;
```

查询成功返回！而如果王五尝试执行角料之外的破坏性操作：

```sql
DELETE FROM emp1 WHERE id = 2;
```

服务端立即阻断：`ERROR 1142: DELETE command denied to user 'wangwu'@'localhost'`。完全符合 `manager` 角色的定义。

##### 方案二：全局开启登录自动激活角色（生产推荐最佳实践）

如果企业内部大量依赖角色体系，要求每次建人赋角色后都手动 `SET DEFAULT ROLE` 显然过于冗余繁琐。MySQL 提供了系统全局变量 `activate_all_roles_on_login`。

查看当前参数状态（默认为 `OFF`）：

```sql
SHOW VARIABLES LIKE 'activate_all_roles_on_login';
```

将其全局动态开启：

```sql
SET GLOBAL activate_all_roles_on_login = ON;
```

同时可以将其持久化至配置文件 `my.cnf` 或 `my.ini` 中：

```ini
[mysqld]
activate_all_roles_on_login = ON
```

开启该参数后，任何用户在登录时，MySQL 鉴权模块会自动将其名下被授予的所有角色无感激活，彻底免除手动激活的步骤。

### 角色撤销与系统强制角色机制

#### 撤销用户的角色：REVOKE FROM USER

当员工转岗不再担任经理职务时，管理员需要剥离其角色：

```sql
REVOKE 'manager' FROM 'wangwu'@'%';
```

> **易错点**：该撤销指令必须由具有足够管理权限的账户（如 `root`）执行。如果普通用户王五试图在自身终端中执行 `REVOKE manager FROM 'wangwu'@'%';`，系统会因权限不足抛出 `Access denied`。

在回收角色时同样存在**存量活跃会话的延迟生效特性**：
- 管理员执行 `REVOKE` 成功后，如果王五当前已连接的会话没有断开，他**在当前会话中仍然能够继续执行 `manager` 赋予的查询操作**；
- 只有当王五退出并重新建立连接后，角色注销才会真正生效。此时重新登录的王五执行 `SHOW DATABASES;`，将再度失去 `dbtest1` 的访问资格。

#### 系统级强制角色（Mandatory Roles）

对于有严格内控合规要求的生产集群，MySQL 8.0 还支持**强制角色（Mandatory Roles）**机制。

通过在配置文件中配置 `mandatory_roles` 参数：

```ini
[mysqld]
mandatory_roles = 'audit_role,common_reader_role'
```

- **全员隐式赋予**：该实例上创建的任何现有用户与未来新用户，在创建瞬间会被系统自动强制附加上这些角色，无需 DBA 执行任何手动的 `GRANT` 关联；
- **防篡改与不可剥离**：被列为 `mandatory_roles` 的角色**无法通过 `REVOKE` 从用户身上剥离，也无法通过 `DROP ROLE` 删除**；
- 典型应用场景包括：全服强制挂载安全审计收集角色、公共字典视图只读角色等，构建起不可绕过的安全基线底座。

## 109-配置文件、系统变量与MySQL逻辑架构
> 对应分集：P109 | 原始标题：《109-配置文件、系统变量与MySQL逻辑架构》

很多读者在学习 MySQL 的过程中经常会遇到这样的困惑：在做环境搭建或者字符集修改时，教程里总会轻描淡写地写上一句“打开 `my.cnf` 或 `my.ini`，在里面加上 `character-set-server=utf8` 即可”。很多教材和技术文章也是如此，默认大家对配置文件了如指掌。如果你此前从事过应用层开发，接触过 `.properties`、`.xml` 或者 `.yaml` 格式的配置文件，或许还能举一反三；但若是一个从零起步学习数据库的新人，往往会觉得十分突兀——这个配置文件究竟应该怎么写？里面那几个带中括号的标签到底代表什么含义？为什么有时把配置写在某个标签下能生效，写在另一个标签下却毫无反应？

要想彻底搞懂 MySQL 的工作机制，我们就必须先扫清配置管理与变量持久化的这处基础死角，进而从全局视角深入剖析 MySQL 服务器内部的逻辑架构体系。

### 配置文件格式规范与启动选项组机制

MySQL 在启动过程中会读取一系列配置文件（在 Linux 环境下通常为 `/etc/my.cnf`、`/etc/mysql/my.cnf`，在 Windows 环境下通常为 `my.ini`）。通过查看 `/etc/my.cnf` 的实际内容，可以发现其中的配置语法主要遵循极其鲜明的两种格式。

#### 配置文件的两种配置格式

在配置文件中，配置项主要呈现为以下两类结构：

1. **键值对类型（Key-Value）**：
   形式为 `key = value`。配置项名称与设定值之间通过等号连接。例如数据目录的存储路径：
   ```ini
   datadir = /var/lib/mysql
   socket = /var/lib/mysql/mysql.sock
   port = 3306
   ```
   这类配置项直接决定了服务器启动时的环境参数和基础路径。

2. **开关状态类型（布尔/开关标记）**：
   这一类选项并不附带具体的值，其存在本身就代表一种开启或关闭的意图。例如：
   ```ini
   disable-log-bin
   ```
   该配置项表示禁用二进制日志功能。如果在配置行前面添加 `#` 井号，则该行变为注释行，MySQL 在启动解析时会自动跳过。

> **定义**：配置文件的语法本质上分为“具名赋值”与“特性开关”两类；凡以 `#` 开头的文本行均视作注释，在服务端引导阶段不参与参数装载。

#### 选项组与启动程序的匹配规则

在配置文件中，我们常常会看到用方括号括起来的标签，这些被称为**选项组（Option Groups）**。例如 `[mysqld]`、`[mysql]`、`[client]` 等。

这些选项组并非随意划分，它们严格对应着系统中的不同可执行程序。在 Linux 系统中，如果我们在 `/usr/bin` 和 `/usr/sbin` 目录下检索 MySQL 的相关二进制指令，会发现它们各自归属于客户端与服务端：

- `/usr/bin/mysql`：最常用的客户端命令行工具，用于用户身份鉴权与交互式登录；
- `/usr/sbin/mysqld`：MySQL 服务器主守护进程，负责底层数据库引擎的常驻监听与核心调度。

不同程序在启动时，只会主动寻找并加载与其自身匹配的选项组：

```text
+-------------------+--------------------------------------------+
| 启动程序 / 二进制命令 | 默认读取的配置文件选项组                     |
+-------------------+--------------------------------------------+
| mysqld (服务端守护进程) | [mysqld]、[server]                         |
| mysql (客户端命令行)   | [mysql]、[client]                          |
| mysqldump (备份工具)   | [mysqldump]、[client]                      |
| mysqladmin (运维工具)  | [mysqladmin]、[client]                     |
+-------------------+--------------------------------------------+
```

在这里有两个特殊的公共选项组需要重点区分：
- `[server]`：通用服务端选项组，作用于所有服务端程序（包括 `mysqld`、`mysqld_safe` 等）；
- `[client]`：通用客户端选项组，作用于所有官方客户端程序（包括 `mysql`、`mysqldump`、`mysqladmin` 等）。

除此之外，MySQL 还支持**特定版本的专用选项组**。例如我们可以声明：
```ini
[mysqld-5.7]
# 仅在 MySQL 5.7 版本的 mysqld 启动时装载生效
default-storage-engine = InnoDB

[mysqld-8.0]
# 仅在 MySQL 8.0 版本的 mysqld 启动时装载生效
default-storage-engine = InnoDB
```
当部署多版本实例或规划版本平滑升级时，这种专用选项组能精确隔离不同主版本间的配置差异。

> **注意**：编写配置文件时切不可将客户端配置项与服务端配置项混为一谈。例如若将 `socket` 指定在 `[client]` 组中，则所有本地客户端均遵循该套接字通信；但若服务端参数被误写在 `[mysql]` 组内，`mysqld` 启动时根本不会予以读取。

#### 选项组与命令行的配置优先级冲突

当同一个参数在不同的选项组中被赋予了不同的取值时，MySQL 采用**后声明覆盖（Last-Wins）**的仲裁规则。

假设配置文件中先后声明了如下内容：
```ini
[server]
default-storage-engine = InnoDB

[mysqld]
default-storage-engine = MyISAM
```
由于 `mysqld` 启动时会同时扫描 `[server]` 与 `[mysqld]`，在读取顺序上 `[mysqld]` 出现在 `[server]` 之后，因此最终生效的默认存储引擎将是 `MyISAM`。如果将二者的物理声明次序颠倒，生效结果便会反转为 `InnoDB`。

与此同时，如果在启动 MySQL 实例的命令行指令中显式追加了参数，例如：
```bash
mysqld --default-storage-engine=MEMORY
```
命令行中显式指定的启动选项拥有**最高优先级**。无论配置文件中最后一个选项组如何配置，均会被命令行的即时参数完全覆盖。

### 系统变量的生命周期与配置方式

系统变量（System Variables）是控制 MySQL 运行时行为的核心载体。我们在日常调优中经常会面对大量变量的查看与变更。

#### 全局变量与会话变量的作用域划分

MySQL 中的系统变量按照生命周期与隔离边界分为两类：
- **全局系统变量（Global Variables）**：作用于整个 MySQL 实例级别。对全局变量的修改会影响所有后续新建立的会话连接，但对已经处于打开状态的既有连接通常不产生实时影响。大部分全局变量需要具备相应的管理权限（如 `SYSTEM_VARIABLES_ADMIN` 或 `SUPER`）才可调整。
- **会话系统变量（Session Variables）**：仅作用于当前特定的客户端连接会话。各个客户端之间的会话变量互不干扰、物理隔离。客户端连接断开后，会话级变量所分配的上下文环境即刻销毁。

部分变量既存在全局副本，又拥有独立的会话副本（例如 `autocommit`、`sql_mode`、`sort_buffer_size`）；而另一些特定变量则天然只具备全局属性（例如 `datadir`、`max_connections`）或只具备会话属性。

#### 内存临时修改与配置文件持久化的结合

对系统变量的配置主要有以下两种实现路径：

1. **内存动态修改（临时性调整）**：
   在已运行的会话中执行：
   ```sql
   -- 设置全局变量（仅在当前内存实例有效，重启失效）
   SET GLOBAL max_connections = 1000;
   
   -- 设置当前会话变量
   SET SESSION sort_buffer_size = 4194304;
   ```
   这种方式适合在线应急排障与动态性能探针，它的优势是立竿见影、无需重启服务；但弊端是一旦 mysqld 进程重启，内存中的改动全部丢失，变量值重置回初始设定。

2. **配置文件固化（持久性配置）**：
   将变量名（去掉前缀）直接写入 `my.cnf` 的对应选项组中：
   ```ini
   [mysqld]
   max_connections = 1000
   sort_buffer_size = 4M
   ```
   写入配置文件属于永久性调整，服务重启后参数会自动加载。

> **结论**：运维实践中若需变更全局配置，常规操作通常是“双管齐下”——先用 `SET GLOBAL` 立即修改内存变量使当前生产集群免于重启，再同步编辑写入 `my.cnf` 确保未来服务重启时不发生参数漂移。

### MySQL 逻辑架构三层体系剖析

当我们把关注点从外部的配置体系转向数据库内部时，整个 MySQL 服务器对外部客户端而言往往就像一个黑盒子：客户端发送一行纯文本 SQL 查询语句，服务端经过内部运转，随后将结构化的数据集响应回客户端。

要彻底打开这个黑盒子，就必须清晰理清 MySQL 服务器内部的**逻辑架构（Logical Architecture）**。

#### 客户端与服务端交互模型

MySQL 是非常典型的 **C/S（Client/Server，客户端/服务端）架构**。
- **客户端**：形态多样，既可以是官方自带的交互式 CLI 程序 `mysql`，也可以是基于各主流开发语言构建的应用程序。
- **服务端**：以单进程多线程模型在后台运行的 `mysqld` 守护进程。

在讨论逻辑分层时，技术界常存在一个容易混淆的认知偏差：很多人习惯性地把架构图上的“客户端连接器（Connectors）”以及“底层文件系统（Filesystem）”也划归为 MySQL 的内部层次，形成所谓的五层架构。但从严格意义上讲，**MySQL 数据库管理系统（DBMS）本体只包含中间的三层**：
- 客户端 Connectors 属于数据库外部的第三方应用依赖；
- 底层物理磁盘上的存储介质与操作系统文件系统，属于宿主主机的存储基础设施；
- 真正的 DBMS 核心逻辑架构，自上而下严格划分为：**连接层**、**服务层（SQL 层）**、**引擎层**。

#### 连接层（Connection Layer）核心组件

连接层位于 MySQL 架构的最顶端，是所有外部客户端与 MySQL 服务端建立通信的第一道关卡。

##### 客户端连接池与线程管理
在实际业务场景中，绝不可能仅有一个客户端或一个系统独占数据库。多个业务模块、多个应用实例甚至微服务集群会高并发地向 MySQL 发起连接。建立一次 TCP 握手开销是昂贵的，频繁为每个请求创建和销毁底层系统线程更是对 CPU 和操作系统资源的巨大浪费。

因此，连接层的核心是**连接池（Connection Pool）**与**线程调度机制**：
- 它维护了客户端网络长连接，限制最大连接数（由 `max_connections` 参数硬性约束）；
- 它负责为每一个接入的客户端连接分派或从线程缓存区（Thread Cache）调取一个专属的**工作线程**，负责承接该连接在其存活期间发送的所有请求；
- 当客户端正常断开连接时，对应的服务器线程不会被暴力杀灭，而是重新归还到线程缓存中，等待服务后续接入的会话。

##### 身份安全认证与权限表预载
在握手阶段，连接层执行严格的认证逻辑：
- 校验客户端提交的主机名（Host）、用户名（User）与加密凭据（Password）；
- 若密码不正确，立即阻断握手并抛出经典异常：`Access denied for user 'xxx'@'xxx' (using password: YES)`；
- 一旦用户鉴权成功，连接层会立即查询系统权限元数据表（`mysql.user`、`mysql.db`、`mysql.tables_priv`、`mysql.columns_priv` 等），获取该用户所拥有的全局及库表级权限，并将其**深拷贝并绑定**到该连接的专属工作线程上下文中。后续所有操作的权限校验直接读取内存中的权限副本，无需每次重复扫描磁盘系统表。

#### 服务层（Server Layer / SQL 层）关键部件

服务层是 MySQL 的中枢大脑。除了可插拔的存储引擎之外，MySQL 绝大多数的核心系统功能、跨引擎通用的 SQL 解析与优化、触发器、视图、内置函数等全部固化在这一层。

##### SQL 接口（SQL Interface）
SQL 接口充当服务层的门面与出入口调度器。它负责直接接收客户端经由连接层传递进来的各类 SQL 文本指令（包括数据定义语言 DDL、数据操作语言 DML、数据查询语言 DQL 等），在各内部组件执行完毕后，再将打包好的状态码或二维结果集回传。

##### 解析器（Parser）与语法树构建
计算机底层无法直接执行人类编写的 SQL 字符串，必须将其解构为机器可识别的抽象语法树（Parse Tree）。解析器所做的工作在形式上宛如“庖丁解牛”：

1. **词法解析（Lexical Analysis）**：
   从左至右逐字扫描 SQL 字符串，将连续字符切分为一个个不可分割的标记（Tokens）。它能识别出哪些是 MySQL 保留关键字（`SELECT`、`FROM`、`WHERE`、`ORDER BY`），哪些是数据库对象名称（表名、列名），哪些是字面常量值或操作符。
2. **语法解析（Syntax Analysis）**：
   依据 MySQL 既定的 SQL 语法规范，检查提取出来的各个 Token 是否拼装组合成合法的语义结构。
   如果在编写语句时将 `FROM` 误拼写成了 `FOM`，或者丢失了必要的逗号，解析器在语法检查阶段便会立即拦截并中断流程，向客户端抛出精准的语法错误报告（`You have an error in your SQL syntax...`）。

经过词法与语法分析后，解析器最终在内存中构建出一棵结构严谨的语法分析树。

##### 优化器（Optimizer）与执行计划生成
语法正确绝不等于执行效率最优。一条结构稍微复杂的 SQL，底层的物理存取路径往往有成百上千种组合：
- 多张表进行关联（Join）时，究竟以哪张表作为外层的驱动表？
- 某张表上同时建有 `idx_age` 与 `idx_dept` 复合索引，当前条件究竟使用哪个索引最优，亦或是全表扫描更具优势？
- `WHERE` 子句中存在的子查询，是否能改写展开为半连接（Semi-Join）？
- 外连接（LEFT JOIN）在特定条件下是否能够无损降级为性能更好的内连接（INNER JOIN）？

优化器就是专职负责裁决这些方案的核心组件。优化器分为**逻辑优化（Logical Optimization）**与**物理优化（Physical Optimization）**：
- **逻辑优化**：利用代数等价变换规则对 SQL 表达式进行重写与化简（如谓词下推、外连接转内连接、投影剔除）；
- **物理优化**：依托底层收集的统计信息，基于**成本代价模型（Cost Model）**评估各种路径的 I/O 代价与 CPU 运算代价。

> **结论**：优化器最终输出的产物是**执行计划（Execution Plan）**。需要明确的是，优化器基于成本计算选定的方案代表其“自认为最优的策略”，但在统计信息过时或存在数据倾斜时，执行计划所选的不一定绝对是实际物理耗时最短的路径。

##### 查询缓存（Query Cache）的运行机制及其在 8.0 彻底被废弃的深层原因
在 MySQL 5.7 及更早版本中，服务层还包含一个备受争议的组件——**查询缓存（Query Cache）**。

- **工作机制**：
  查询缓存采用 Key-Value 字典模型。其 Value 保存的是查询返回的原始完整结果集，而 Key 是客户端发送给服务端的**原始 SQL 文本字节序列**。
  当新的查询进入服务层时，MySQL 在词法语法解析之前会优先计算该 SQL 的哈希值并检索查询缓存。如果能够命中（Cache Hit），系统将直接跳过后续的解析、优化和存储引擎调用，瞬间将缓存结果输出回客户端。
- **严苛的命中前提**：
  缓存的 Key 校验要求字节级别的**完全等价**。两个查询哪怕只多了一个空格、大小写不一致、或者注释略有差异，由于哈希值不同，均被判定为未命中。此外，如果 SQL 中包含了任何动态函数（如 `NOW()`、`UUID()`）或系统函数，该查询直接不可缓存。
- **MySQL 8.0 彻底移除去除查询缓存的技术根因**：
  既然查询缓存能够极大提速读操作，为什么官方在 MySQL 8.0 中毅然将其连根拔除？
  核心症结在于**极低的生产命中率与极高的全局锁失效代价**：
  在 OLTP（联机事务处理）业务中，表的数据是频繁动态变化的。MySQL 规定：**只要某张表发生了任何一次写操作（INSERT、UPDATE、DELETE），该表上绑定的所有历史查询缓存将被强制整体清空失效**。为了保证缓存与物理数据的一致性，频繁的表更新会导致查询缓存反复失效与重建；高并发下，所有工作线程争夺查询缓存的全局互斥锁更会产生严重的性能抖动。付出如此高昂的维护开销，换来的命中率却微乎其微。因此在 MySQL 8.0 中，官方彻底将该功能完全剔除，建议将缓存职责全权移交至应用层（如 Redis）。

#### 引擎层（Storage Engine Layer）与存储层

逻辑架构的第三层是**引擎层**，它下沉直面底层存储。

##### 插件式存储引擎的解耦设计
MySQL 与许多一体化商业数据库（如 Oracle、SQL Server）截然不同，其最显著的架构特征就是**插件式存储引擎（Pluggable Storage Engines）**：
- 服务层与引擎层之间定义了标准的存储引擎 API 抽象规范（包含行读取、索引遍历、事务提交等抽象接口）；
- 存储引擎是**表级别（Per-Table）**的，同一个数据库实例中，A 表可以使用 InnoDB，B 表可以使用 MyISAM，C 表可以使用 MEMORY；
- 存储引擎的加载如同 U 盘插拔一般自由，研发人员甚至可以按照官方 API 规范自行开发专属的私有存储引擎。

可以通过在终端执行管理指令查看当前数据库支持的引擎阵列：
```sql
SHOW ENGINES;
```
输出结果中会明确罗列出 InnoDB（默认事务型引擎）、MyISAM、MEMORY、CSV、ARCHIVE 等引擎支持的事务性（Transactions）、安全保存点（Savepoints）以及 XA 分布式事务等特性矩阵。

##### 存储层（Storage Layer）与物理交互
数据最终的宿命是持久化保存在操作系统的物理磁盘之上。通过执行：
```sql
SHOW VARIABLES LIKE 'datadir';
```
可以精准定位到底层物理文件所在的宿主目录（Linux 下默认路径通常为 `/var/lib/mysql/`）。该目录下不仅存放着各数据表对应的物理数据与索引文件（如 InnoDB 的独立表空间 `.ibd`、系统表空间 `ibdata1`），更存放着一系列保障高可用与 ACID 特性的核心日志文件（Redo Log、Undo Log、Binlog、慢查询日志等）。

> **提示**：CPU 与物理磁盘之间的 I/O 读写速度存在着多个数量级的巨大鸿沟。因此在真实的数据检索过程中，存储引擎绝不会愚蠢到每次按需逐字节翻找磁盘，而是必须依托内存中的**缓冲池（Buffer Pool）**。所有的查找与更新优先在内存页中完成，再通过后台线程异步刷盘，从而保证系统吞吐量。

### SQL 查询在各组件间的完整执行时序

为了让大家将前面学到的各个组件有机串联，我们以一条典型的 `SELECT` 查询语句为例，梳理其在 MySQL 5.7 与 8.0 架构中的生命周期调用链：

```text
[客户端]             [连接层-连接池]       [服务层-接口/缓存]       [服务层-解析器/优化器]     [引擎层-存储引擎]      [存储层-磁盘/缓冲池]
   |                      |                      |                      |                      |                      |
   | 1. 发起网络连接握手    |                      |                      |                      |                      |
   +--------------------->|                      |                      |                      |                      |
   |                      | 2. 鉴权认证/绑定权限  |                      |                      |                      |
   |                      |    分派工作线程       |                      |                      |                      |
   | 3. 发送 SELECT 文本   |                      |                      |                      |                      |
   +-------------------------------------------->|                      |                      |                      |
   |                      |                      | 4. 检查查询缓存      |                      |                      |
   |                      |                      |    (5.7 命中即返)    |                      |                      |
   |                      |                      |                      |                      |                      |
   |                      |                      | 5. 未命中/8.0直通     |                      |                      |
   |                      |                      |--------------------->|                      |                      |
   |                      |                      |                      | 6. 词法/语法解构     |                      |
   |                      |                      |                      |    生成语法树        |                      |
   |                      |                      |                      | 7. 代价评估与优化    |                      |
   |                      |                      |                      |    生成执行计划      |                      |
   |                      |                      |                      |                      |                      |
   |                      |                      |                      | 8. 调度存储引擎 API  |                      |
   |                      |                      |                      |--------------------->|                      |
   |                      |                      |                      |                      | 9. 检索 BufferPool/  |
   |                      |                      |                      |                      |    按需触发磁盘 I/O  |
   |                      |                      |                      |                      |--------------------->|
   |                      |                      |                      |                      |<---------------------|
   |                      |                      |                      |<---------------------| 10. 返回数据页与记录
   |                      |                      |<---------------------| 11. 汇总与结果集封装
   |                      |                      | 12. 写入查询缓存(5.7)|
   | 13. 返回结果集       |                      |                      |
   |<--------------------------------------------|                      |

   |                      |--------------------> |                      |
```

1. **建立网络链路**：客户端向服务器端口发起连接请求；
2. **鉴权与环境绑定**：连接池验证账户密码，校验来源 IP，装载对应用户的权限镜像并分配专属工作线程；
3. **指令投递**：客户端向服务端发送 SQL 字符串，由 SQL Interface 统一截获；
4. **缓存嗅探（仅 5.7）**：若开启了查询缓存，优先对比哈希，完全命中则直接组装结果集退回；
5. **词法与语法解构**：若未命中（或在 8.0 运行），解析器介入进行词法分析与语法规范校验，构造 Parse Tree；若存在拼写或语法错误在此刻中断报错；
6. **执行计划制定**：优化器接收语法树，进行代数重写与代价成本运算，决定索引选型与连接驱动次序，确定最优 Execution Plan；
7. **引擎层接口调用**：执行器根据执行计划，逐级调用存储引擎提供的抽象 API 读写接口；
8. **内存与磁盘交互**：存储引擎首先探查内存 Buffer Pool 中是否已经缓存了目标数据页；若未命中则从底层物理磁盘加载至内存，提取满足过滤条件（选取）与字段要求（投影）的数据行；
9. **缓存写回与结果投递**：数据流原路交回服务层；在 5.7 中同步将该 SQL 文本与数据结果集注册到查询缓存中；SQL Interface 将最终二维数据集格式化输出并回传客户端；
10. **线程资源回源**：操作完成，工作线程挂起并交还给服务端的线程缓存池，以供后续业务复用。

## 110-SQL执行流程
> 对应分集：P110 | 原始标题：《110-SQL执行流程》

在搞清楚 MySQL 的三层逻辑架构之后，很多读者可能会觉得那些概念听起来偏宏观：连接层、服务层、引擎层，各个部件的名字虽然记住了，但当我们在终端中敲下一行回车、发送一条查询语句时，这行 SQL 到底是在哪个环节被拆碎的？为什么有时候换个写法性能差十倍？底层的执行器又是怎么一行行跟存储引擎要数据的？

把 SQL 的执行流程彻底拆开，不仅是因为在各类技术面试中这是一个被问烂了的高频考点，更重要的是，它是我们后续深入理解 B+ 树索引结构、各类性能分析工具（如 `EXPLAIN`、`SHOW PROFILE`）以及高级 SQL 调优技术的基石。所有的优化手段，本质上都是在干预或者顺应这个执行流程中的特定节点。

### SQL 全生命周期执行流程总览

从客户端发起请求，到最终拿到二维数据表格，一条查询语句在 MySQL 服务器内部要经历一条环环相扣的流水线。

```text
+-----------------------------------------------------------------------------------+
| 客户端 (Client)                                                                   |
|   | 1. 发起 SQL 查询请求                                                           |
+---|-------------------------------------------------------------------------------+
    v
+-----------------------------------------------------------------------------------+
| 连接层 (Connection Layer)                                                          |
|   | 2. TCP 握手认证、权限绑定、指派专属工作线程                                    |
+---|-------------------------------------------------------------------------------+
    v
+-----------------------------------------------------------------------------------+
| 服务层 (Server Layer)                                                             |
|   |                                                                               |
|   +---> [第一关] 查询缓存 (Query Cache)  <--- 仅 MySQL 5.7 及更早版本支持           |
|   |       |-- 命中 (Hit) --------------------------------------+                  |
|   |       \-- 未命中 (Miss) / 8.0 直通                          |                  |
|   |             v                                              |                  |
|   +---> [第二关] 解析器 / 分析器 (Parser)                       |                  |
|   |       |-- 词法分析 (识别关键字、表名、列名)                |                  |
|   |       \-- 语法分析 (校验语法合规性，生成抽象语法树)        |                  |
|   |             v                                              |                  |
|   +---> [第三关] 优化器 (Optimizer)                            |                  |
|   |       |-- 逻辑优化 (等价代数重写、外连接转内连接)          |                  |
|   |       \-- 物理优化 (计算成本、驱动表定序、索引选型)        |                  |
|   |       \-- 输出产物: 执行计划 (Execution Plan)              |                  |
|   |             v                                              |                  |
|   +---> [第四关] 执行器 (Executor)                             |                  |
|           |-- 权限终审 (判断对具体表是否具备 SELECT 权限)      |                  |
|           \-- 调度存储引擎 API 执行数据扫描                    |                  |
+-----------------|----------------------------------------------|------------------+
                  v                                              |
+-------------------------------------------------------------+  |
| 引擎层 (Storage Engine Layer)                               |  |
|   | 3. 调用统一标准 API (如 rnd_next / index_read)          |  |
|   | 4. 探查 Buffer Pool 内存缓冲，按需触发磁盘 I/O          |  |
|   | 5. 逐行比对过滤，组装数据集回传至服务层                 |  |
+-----------------|-------------------------------------------+  |
                  v                                              |
+-------------------------------------------------------------+  |
| 结果交付与写回                                              |  |
|   | 6. 若 5.7 开启缓存，将 SQL 与结果集写入 Query Cache     |  |
|   | 7. 经由 SQL 接口将结果集响应给客户端 <------------------+--+
+-----------------------------------------------------------------------------------+
```
*图解说明：SQL 执行流向图直观呈现了查询请求自客户端注入后，在服务端各关键节点之间的流转判断机制。*

### 第一关：查询缓存的运作机理与淘汰根因

在 MySQL 5.7 及其更早的体系中，SQL 穿透连接层后的第一站是探查**查询缓存（Query Cache）**。

#### 字符级哈希匹配与不可缓存陷阱

查询缓存的底层组织形式是一个简单的 Key-Value 哈希结构。其中 Value 存储的是执行完毕的完整结果集，而 Key 则是客户端提交的**原始 SQL 语句文本**。

这种设计导致查询缓存的命中条件苛刻到了极点：
1. **字符级绝对一致**：
   假设客户端首先执行了如下查询：
   ```sql
   SELECT employee_id, last_name FROM employees WHERE employee_id = 101;
   ```
   执行完成后，该语句与查出的单行数据作为键值对存入内存。若下一次客户端发来的语句仅仅在 `WHERE` 后面多敲了一个空格，或者关键字的大小写发生了细微变动：
   ```sql
   -- 字符长度与 ASCII 序列发生改变，无法命中缓存
   SELECT employee_id, last_name FROM employees WHERE  employee_id = 101;
   ```
   因为字符串哈希值直接改变，MySQL 会判定为完全不同的两条语句，从而直接穿透缓存重新走解析和优化，缓存匹配的鲁棒性极差。
2. **动态函数直接失效**：
   如果 SQL 语句中包含任何非确定性函数或系统变量，例如 `NOW()`、`CURRENT_DATE()`、`UUID()`、`RAND()`，MySQL 在预处理阶段便会判定该查询不可缓存。因为哪怕两次发送的字符串一模一样，当前时间戳也是动态跳变的，强行缓存必然导致结果失真。

#### 缓存失效的连锁雪崩

更严重的技术软肋在于**强一致性保障下的失效代价**。

MySQL 规定：**只要某张数据表发生了一次数据变更（包括 `INSERT`、`UPDATE`、`DELETE`、`TRUNCATE` 或 `ALTER TABLE`），该表在查询缓存中所关联的所有历史查询结果集，必须立刻全量清空淘汰**。

在高度并发的在线事务处理（OLTP）场景下，核心业务表每秒都在经历海量的写入与更新。这意味着某条高频查询刚刚花费 CPU 资源写入缓存，不到半毫秒后就因为一条细微的写入操作被整体驱逐。在极端情况下，查询缓存不仅无法提供加速，还会因为全局互斥锁（Mutex）的高频加锁与哈希槽清理，导致工作线程严重排队阻塞。

> **结论**：在绝大多数动态业务场景下，查询缓存是一个弊远大于利的“鸡肋”组件。它唯一的适用场景是几乎没有任何写入操作的**静态字典表**或配置表。基于这个事实，MySQL 8.0 官方彻底从内核代码中彻底移除了查询缓存。

#### 查询缓存的开关配置与监控状态分析

在 MySQL 5.7 环境中，查询缓存的运行受系统变量 `query_cache_type` 控制：
- `0`（OFF）：彻底关闭查询缓存功能；
- `1`（ON）：全局开启查询缓存。所有合规的 `SELECT` 均尝试缓存，除非显式指定 `SQL_NO_CACHE`；
- `2`（DEMAND）：按需缓存模式。默认不走缓存，只有语句中显式追加了 `SQL_CACHE` 关键字时才启用缓存。

例如在 `DEMAND` 模式下的使用方式：
```sql
-- 显式声明要求走查询缓存
SELECT SQL_CACHE * FROM static_config WHERE id = 5;

-- 显式声明绕过查询缓存
SELECT SQL_NO_CACHE * FROM dynamic_orders WHERE user_id = 10086;
```

如果在 5.7 中需要排查查询缓存的健康度，可以通过状态命令检视：
```sql
SHOW STATUS LIKE 'Qcache%';
```
输出的状态参数具有非常关键的排障指导价值：

| 状态参数名 | 技术含义 | 调优与排障诊断结论 |
| :--- | :--- | :--- |
| `Qcache_free_blocks` | 缓存中空闲内存块数量 | 该值若持续偏高，说明缓存碎片化极严重，需定期使用 `FLUSH QUERY CACHE` 整理 |
| `Qcache_total_blocks` | 缓存分配的内存块总数 | 反映缓存系统的物理块规模 |
| `Qcache_free_memory` | 剩余未使用的空闲内存量 | 若该值过大，说明分配给查询缓存的内存存在闲置浪费 |
| `Qcache_lowmem_prunes` | 因内存耗尽被迫淘汰的查询总数 | 若该计数持续暴涨，说明分配给查询缓存的内存空间严重不足，频繁发生驱逐 |
| `Qcache_queries_in_cache` | 当前驻留在缓存中的查询总数 | 实时监控指标 |
| `Qcache_not_cached` | 未被缓存的查询语句计数 | 统计不符合缓存要求或被规则排斥的语句量 |
| `Qcache_hits` | 缓存成功命中的历史累计总次数 | 该值越大说明缓存效益越显著 |
| `Qcache_inserts` | 新写入缓存的查询历史累计总次数 | 若 `inserts` 极高而 `hits` 极低，说明写得多用得少，属于典型负优化 |

而在 MySQL 8.0 环境下执行上述查询，返回结果均为空：
```sql
-- MySQL 8.0 终端中执行
SHOW VARIABLES LIKE 'query_cache_type';
-- 结果集: Empty set (0.00 sec)
```
这从底层参数层面证实了查询缓存模块在 8.0 中已被物理剔除。

### 第二关：解析器（Parser）的词法与语法剖析

如果查询缓存未命中（或在 8.0 运行），SQL 字符串正式进入服务层的核心处理单元——**解析器（Parser，亦称分析器）**。

#### 词法分析与语法分析的分工

计算机无法直接理解连成一片的字符串，解析器必须执行“两步走”战略：

1. **词法分析（Lexical Analysis）**：
   解析器像分词机一样，把长字符串拆分为离散的单词片段（Token）。它能够识别并打标：
   - 哪些是系统关键字（`SELECT`、`FROM`、`WHERE`、`GROUP BY`）；
   - 哪些是用户自定义标识符（库名、表名、字段名、别名）；
   - 哪些是比较运算符与字面常量值。
2. **语法分析（Syntax Analysis）**：
   在词法分析的基础上，语法分析器利用预设的上下文无关文法，判定这些 Token 的排列顺序是否符合 SQL 语言规范。

例如，当我们编写了如下违背语义约束的查询语句：
```sql
SELECT department_id, job_id, AVG(salary)
FROM employees
GROUP BY department_id;
```
从词法上看，每一个单词都是标准词汇；但若当前处于严格 SQL 模式（`ONLY_FULL_GROUP_BY`），语法/语义检查器在遍历分析树时，会立刻捕获到 `job_id` 既非聚合函数目标、又未包含在 `GROUP BY` 分组维度中的逻辑冲突。

若有基础语法残缺，解析器会立即阻断请求，直接抛出经典提示：
```text
ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '...' at line 1
```

#### 抽象语法分析树（Parse Tree）的构建

通过语法分析后，原本平铺的字符串被重构为一棵多叉层次化的**语法分析树（Parse Tree）**。

```text
                        [SELECT 语句节点]
                               |
       +-----------------------+-----------------------+
       |                       |                       |
 [投影字段列表]           [FROM 目标表]            [WHERE 过滤条件]
   /        \                  |                       |
[id]      [name]          [user_info]             [AND 逻辑节点]
                                                   /          \
                                            [> 运算]         [= 运算]
                                            /     \          /     \
                                         [age]   [18]    [status]  [1]
```
*图解说明：语法树将平铺的 SQL 字符串层级化为树状数据结构，使后续优化器能够遍历与处理各个子句节点。*

语法分析树精确界定了语句的骨架结构，使后续程序能够以此为根据进行代数改写与物理优化。

### 第三关：优化器（Optimizer）的代价评估与决策

优化器是 MySQL 最复杂、技术含量最高的核心模块。在拿到语法分析树后，优化器的首要职责是回答一个核心问题：**为了拿到用户想要的结果，底层究竟该采取哪种执行路径？**

一条 SQL 查询往往存在很多种等价的执行方式，它们产生的数据集完全相同，但在消耗的 I/O 读写量与 CPU 运算时间上却有天壤之别。优化器的目标就是挑出其中**成本代价（Cost）最低**的那套方案。

优化过程主要分为逻辑优化与物理优化两个层面：

#### 逻辑查询优化（代数等价变换）
逻辑优化侧重于**规则变换**。它利用离散数学与关系代数的等价定理，在不改变查询结果语义的前提下，把原 SQL 改写为结构更扁平、消除冗余运算的新形式：
- **子查询解嵌套（Subquery Unnesting）**：将性能极差的嵌套子查询，在可能的情况下平铺重写为多表内连接（`JOIN`）或半连接（`Semi-Join`）；
- **外连接消除（Outer Join Elimination）**：如果在 `LEFT JOIN` 的 `WHERE` 条件中存在对右表非空列的强过滤，优化器会自动把性能较重的值补空外连接无损降级为更轻量的内连接（`INNER JOIN`）；
- **常量折叠与谓词下推**：提前对 `1 + 1` 等常量运算进行归并，尽可能把过滤条件（`WHERE`）推向底层，提前剔除无效数据行。

#### 物理查询优化（代价模型与路径裁决）
物理优化侧重于**执行路径估算**。优化器会读取数据表上由后台线程采集的统计信息（包括表的数据页数、行记录数、索引基数 Cardinality 等），结合内部精密的成本代价模型，计算各个候选方案的 I/O 成本与 CPU 成本。

物理优化裁决的关键议题包括：
1. **单表访问路径**：全表物理扫描（Table Scan）与索引扫描（Index Scan）的代价对比。
2. **多索引竞选**：若某个字段上既有单列索引，又命中了一个联合索引的前缀，到底调用哪一个索引代价更小。
3. **多表关联的驱动顺序（Driving Table）**：这是多表联查中最核心的决策。

##### 驱动表选择的经典案例
考虑如下典型的两表关联查询：
```sql
SELECT *
FROM test1, test2
WHERE test1.id = test2.id
  AND test1.name = '张伟'
  AND test2.course_name = 'MySQL高级课程';
```
假定 `test1` 存放全校学生花名册，`test2` 存放选课详情，两表通过 `id` 进行关联匹配。
- 经过初步评估，`test1` 中叫“张伟”的人数非常多，拉出来甚至能组成一个连、一个营（重名率极高，比如有 500 条匹配记录）；
- 而 `test2` 中选修“MySQL高级课程”的记录非常少，全校仅有 3 条。

此时摆在优化器面前的有两种迥异的物理执行方案：
- **方案 A（以 `test1` 为驱动表）**：
  先从 `test1` 中过滤出 500 个叫张伟的记录；然后循环 500 次，拿着每个张伟的 `id` 到 `test2` 中去比对是否选了“MySQL高级课程”。
- **方案 B（以 `test2` 为驱动表）**：
  先从 `test2` 中过滤出选了“MySQL高级课程”的 3 条选课记录；随后仅需循环 3 次，拿着这 3 个 `id` 回到 `test1` 中快速核验学生名字是否叫“张伟”。

很显然，方案 B 产生的嵌套循环比对次数远远低于方案 A。
优化器在物理优化阶段会计算这两种顺序的综合代价，最终做出仲裁：**强制指定小结果集表 `test2` 作为驱动表，大结果集表 `test1` 作为被驱动表**。

> **结论**：优化器输出的最终产物是**执行计划（Execution Plan）**。我们在日常调优中通过执行 `EXPLAIN SELECT ...` 指令所观察到的表格输出，正是优化器在此处生成的执行计划明细。

### 第四关：执行器（Executor）与存储引擎的交互

执行计划敲定后，真正的物理执行工作交由**执行器（Executor）**接管。

#### 权限二次判定
在正式驱动存储引擎检索数据之前，执行器必须对该 SQL 所触碰的目标表进行权限终审：
- 校验当前连接绑定的用户凭据，是否对目标库、目标表及目标字段拥有对应的 `SELECT`（或写操作）权限；
- 如果在会话存活期间管理员通过 `REVOKE` 剥夺了相关权限，执行器在此处会立即中断执行并报错拦截。

#### 存储引擎 API 调度与逐行检索逻辑

确认权限完备后，执行器开始按照执行计划，通过标准的**存储引擎 API 抽象接口**与底层引擎（如 InnoDB）进行深度交互。

存储引擎 API 是一套严谨的虚函数/抽象接口规范。执行器并不感知底层的具体存储格式是 B+ 树、哈希表还是堆表，它只负责依据算法调用预设的驱动原语。

##### 全表扫描模式下的交互流转
假设我们要查询一张没有任何索引的普通表：
```sql
SELECT * FROM test_user WHERE age = 25;
```
执行器与存储引擎的交互步骤如下：
1. **读取首行**：执行器调用底层存储引擎的 `ha_rnd_init()` 初始化读指针，紧接着调用 `ha_rnd_next()` 接口，要求存储引擎读取当前表的“第一行记录”；
2. **条件校验**：存储引擎将读取到的第一行数据载入内存并传递给执行器；执行器调用服务层的过滤组件判定：该行记录的 `age` 是否等于 25？若不等于，直接跳过弃用；若等于，将这行数据推入临时的结果集缓冲区；
3. **循环拉取**：执行器再次调用 `ha_rnd_next()` 接口，要求存储引擎读取“下一行记录”；引擎层依序后移指针并返回数据；
4. **遇尾终止**：不断重复上述拉取与判定过程，直至存储引擎返回读取到表尾的终止状态码；
5. **打包输出**：执行器将最终在内存缓冲区中攒齐的所有满足条件的行记录，统一交由 SQL 接口打包成通信协议包，回传给客户端。

##### 索引扫描模式下的交互流转
如果我们在 `age` 字段上建立了索引：
1. 执行器首先调用存储引擎的 `ha_index_init()` 初始化索引上下文；
2. 调用 `ha_index_read_map()` 接口，要求存储引擎在 `age` 索引的 B+ 树上定位满足 `age = 25` 的“第一条记录”；
3. 引擎层完成 B+ 树遍历后，将命中主键并回表拿到的数据整行提交给执行器；
4. 执行器继续调用 `ha_index_next()` 接口向后按序扫描索引链表，直至引擎返回键值不匹配为止。

通过这种“引擎负责提数、执行器负责调度与裁决”的高内聚、低耦合架构，MySQL 实现了引擎的可插拔特性。所有的物理数据读取，均由执行器通过引擎 API 发出指令，在引擎层借助内存缓冲池（Buffer Pool）完成数据页调度，最终完成了整条 SQL 的闭环执行。

## 111-MySQL8.0和5.7中SQL执行流程的演示
> 对应分集：P111 | 原始标题：《111-MySQL8.0和5.7中SQL执行流程的演示》

前面我们在理论层面详细拆解了 MySQL 的三层架构，以及 SQL 从连接层、解析器、优化器到执行器的全生命周期。但理论讲得再漂亮，如果不亲自到控制台里看一看底层究竟输出了什么，大家心里总归觉得隔着一层窗户纸。

一条完全一模一样的查询语句，执行第一次和执行第二次到底有没有区别？MySQL 5.7 里的查询缓存到底是在哪一步把数据存进去的？又是怎么瞬间命中的？而 MySQL 8.0 既然把查询缓存干掉了，那我们连续执行两次相同的 SQL，它是不是真的一板一眼地把所有解析和优化阶段重新跑了一遍？

本讲我们就通过 MySQL 官方提供的内部性能探针工具 Profiling，在 MySQL 8.0 和 5.7 两个真实环境中进行实操对照演示，用抓取到的底层执行阶段与耗时数据，彻底印证前面的架构理论。

### 实验准备与基准环境搭建

为了使执行的 SQL 具备代表性，并且方便后续章节统一演示，我们需要先在实验服务器中导入标准的测试数据库。

#### 导入测试数据库
实验环境准备了两台 Linux 虚拟机，分别部署了 MySQL 8.0 和 MySQL 5.7。

我们使用图形化管理工具 SQLyog 分别连接这两台服务器，执行附带的 `atguigudb.sql` 脚本：
1. 在 SQLyog 菜单栏选择【工具】->【执行 SQL 脚本】；
2. 选中本地桌面的 `atguigudb.sql` 文件，点击执行；
3. 执行完成后刷新对象列表，在两台实例中均成功构建出 `atguigudb` 数据库，其中包含了后续演示常用的 `employees`（员工表）、`departments`（部门表）等结构。

在 Linux 终端中也可以通过命令行验证库表的就绪状态：
```sql
SHOW DATABASES;
USE atguigudb;
SHOW TABLES;
```

#### Profiling 工具的运行机制与启用方式

在 MySQL 中，默认情况下系统是不会耗费 CPU 和内存资源去精确记录每一条 SQL 的内部执行明细的。要捕获 SQL 在各个生命周期阶段的耗时，我们需要借助系统变量 `profiling`。

##### 查看与开启 Profiling
`profiling` 是一个会话级别的系统变量：
```sql
-- 查看当前会话的 profiling 状态（默认值为 0，即 OFF）
SELECT @@profiling;
-- 或者显式指定会话作用域
SELECT @@session.profiling;
```

为了开启当前会话的执行分析，执行如下指令：
```sql
-- 开启 SQL 性能分析探针
SET profiling = 1;

-- 再次校验，返回 1 即代表开启成功
SELECT @@profiling;
```

> **注意**：`SET profiling = 1;` 仅对当前客户端连接会话生效。一旦断开重连，该参数将恢复为默认值 0。这种轻量级的按需开启方式，非常适合在生产环境中针对特定慢查询进行定向诊断，而不会对全实例造成额外的监控负载。

##### Profiling 命令族与高级监控参数
开启 profiling 之后，当前会话执行的所有 SQL 语句及其耗时，都会被缓存到性能视图中（默认保留最近 15 条）。

核心操作命令包含以下几条：
1. **查看历史查询概览**：
   ```sql
   SHOW PROFILES;
   ```
   该命令会列出近期执行的所有语句的 `Query_ID`、总耗时 `Duration` 以及对应的 SQL 文本。
2. **查看单条 SQL 的细粒度阶段耗时**：
   ```sql
   -- 默认展示最近执行的一条 SQL 的各个阶段
   SHOW PROFILE;
   
   -- 显式查看指定 Query_ID 的各阶段耗时
   SHOW PROFILE FOR QUERY 7;
   ```
3. **查看硬件级资源消耗扩展**：
   除了查看时间开销，我们还可以通过追加参数，同时监控 CPU 时间以及磁盘 I/O 块操作次数：
   ```sql
   SHOW PROFILE CPU, BLOCK IO FOR QUERY 7;
   ```
   该指令不仅能输出各个阶段的耗时，还会额外输出 `CPU_user`（用户态 CPU 耗时）、`CPU_system`（内核态 CPU 耗时）、`Block_ops_in`（物理块输入计数）以及 `Block_ops_out`（物理块输出计数），是深挖慢查询瓶颈的利器。

### MySQL 8.0 环境下的 SQL 执行流程实操验证

我们首先在 MySQL 8.0 终端中验证上一讲得出的结论：在 8.0 中，无论 SQL 是否重复执行，都必须经历完整的解析与优化。

#### 重复执行相同查询的 Profile 阶段分析

在已开启 `profiling = 1` 的 8.0 会话中，我们切换到 `atguigudb` 库，并执行如下操作：

```sql
USE atguigudb;

-- 首次执行全表查询
SELECT * FROM employees;

-- 利用终端方向向上键，再次执行完全一致的查询
SELECT * FROM employees;
```

执行完毕后，调用概览命令：
```sql
SHOW PROFILES;
```
输出列表呈现如下历史记录（示意）：
```text
+----------+------------+---------------------------------+
| Query_ID | Duration   | Query                           |
+----------+------------+---------------------------------+
|        6 | 0.00084200 | SELECT * FROM employees         |
|        7 | 0.00081500 | SELECT * FROM employees         |
+----------+------------+---------------------------------+
```
Query 6 与 Query 7 是连续执行的两条完全一模一样的语句。我们分别调取这两次执行的明细阶段：

```sql
-- 查看首次执行明细
SHOW PROFILE FOR QUERY 6;

-- 查看第二次执行明细
SHOW PROFILE FOR QUERY 7;
```

通过观察对比输出的各个状态节点，两者的执行轨迹高度一致，均经历了如下完整的 17 个内部步骤：

```text
+--------------------------------+----------+
| Status                         | Duration |
+--------------------------------+----------+
| starting                       | 0.000075 |
| Executing hook on transaction  | 0.000004 |
| starting                       | 0.000008 |
| checking permissions           | 0.000006 |
| Opening tables                 | 0.000036 |
| init                           | 0.000006 |
| System lock                    | 0.000009 |
| optimizing                     | 0.000009 |
| statistics                     | 0.000014 |
| preparing                      | 0.000013 |
| executing                      | 0.000047 |
| Sending data                   | 0.000481 |
| end                            | 0.000004 |
| query end                      | 0.000004 |
| waiting for handler commit     | 0.000008 |
| closing tables                 | 0.000009 |
| freeing items                  | 0.000015 |
| cleaning up                    | 0.000010 |
+--------------------------------+----------+
```

> **结论**：在 MySQL 8.0 中，哪怕是前后间隔半秒、字符完全相同的查询，第二次查询依然从 `checking permissions`（权限检查）、`Opening tables`（打开表）、`optimizing`（优化）、`preparing`（准备）、`executing`（执行）一路走到 `Sending data`。整个链路完整走完，没有出现任何跳步，实测印证了 8.0 完全不依赖查询缓存的直通机制。

#### 内核级参数验证与配置异常排查

可能有读者会产生疑问：是不是因为 8.0 默认没有开启查询缓存，只要我们在配置文件里把它打开，就能像 5.7 一样加速了？

我们可以通过实操来检验这一设想。首先在 8.0 终端中检索查询缓存相关的系统变量：
```sql
SHOW VARIABLES LIKE 'query_cache_type';
-- 输出: Empty set (0.00 sec)
```
控制台明确提示返回为空集，说明该系统变量在 8.0 的变量字典中根本不存在。

如果我们不信邪，强行在 Linux 系统下的 `/etc/my.cnf` 中写入如下配置：
```ini
[mysqld]
# 尝试在 8.0 中强行启用查询缓存
query_cache_type = 1
```
保存配置文件并尝试重启服务：
```bash
systemctl restart mysqld
```
终端会立即抛出红色告警：`Job for mysqld.service failed because the control process exited with error code.`
查看系统服务日志，`mysqld` 明确报错拒绝引导，原因就是遭遇了无法识别的未知参数 `query_cache_type`。必须将该行配置彻底删除后，MySQL 8.0 才能正常恢复启动。

这在内核级层面彻底坐实了一个技术事实：**MySQL 8.0 不仅是默认关闭了查询缓存，而是把整个查询缓存模块的底层代码全部铲除了**。

### MySQL 5.7 环境下的查询缓存与执行链路对比

接下来，我们把同样的测试搬到 MySQL 5.7 实例中。

#### 开启 5.7 查询缓存与服务重启

在 5.7 终端中查看初始状态：
```sql
SHOW VARIABLES LIKE 'query_cache_type';
```
输出显示此时 `Value` 为 `OFF`。在 5.7 源码中，虽然保留了查询缓存功能，但官方在默认安装包中同样将其置为关闭状态。

为了开启查询缓存，我们编辑配置文件：
```bash
vim /etc/my.cnf
```
在 `[mysqld]` 选项组下追加一行：
```ini
[mysqld]
query_cache_type = 1
```
保存退出后，重启 5.7 服务：
```bash
systemctl restart mysqld
```
重新登录客户端并检查：
```sql
SHOW VARIABLES LIKE 'query_cache_type';
```
此时回显 `Value` 成功变为 `ON`，说明查询缓存已处于全天候待命状态。

#### 首次查询与二次查询的 Profile 阶段极值对比

在 5.7 中开启性能监控探针：
```sql
SET profiling = 1;
USE atguigudb;

-- 首次执行部门表查询
SELECT * FROM departments;

-- 紧接着执行完全一致的查询
SELECT * FROM departments;
```

执行 `SHOW PROFILES;` 获取查询 ID（假定首次为 Query 7，二次为 Query 8），随后分别执行：
```sql
SHOW PROFILE FOR QUERY 7;
SHOW PROFILE FOR QUERY 8;
```

此时控制台输出的阶段对比呈现出极其震撼的断崖式差异：

| 执行阶段对比项 | 首次执行（Query 7，未命中缓存） | 二次执行（Query 8，成功命中缓存） |
| :--- | :--- | :--- |
| **执行步骤总数** | 约 25 个微状态阶段 | 仅 4 ~ 5 个阶段 |
| **关键核心阶段** | `checking permissions`<br>`Opening tables`<br>`waiting for query cache lock`<br>`optimizing`<br>`executing`<br>`Sending data`<br>`storing results in query cache` | `starting`<br>`waiting for query cache lock`<br>`checking query cache for query`<br>`sending cached result to client`<br>`cleaning up` |
| **底层核心动作** | 经历了完整的优化与文件检索，在**最后一步执行了 `storing results in query cache`**，将结果集序列化写入查询缓存哈希表 | **在 `checking query cache for query` 阶段直接判定命中**，立即调用 `sending cached result to client` 返回，彻底跳过了表打开、优化器评估与存储引擎交互！ |
| **整体执行耗时** | 耗时相对较长（约 0.000350s） | 耗时出现数量级骤降（约 0.000040s） |

通过这组实测数据，我们可以清晰看到：在 5.7 首次执行查询时，执行器在向客户端发送数据的同时，默默在末尾追加了一道工序——`storing results in query cache`（将本次结果存入查询缓存）；而当第二次相同的查询到达时，服务层在 `checking query cache for query` 阶段便直接截胡，执行计划与存储引擎连被唤醒的机会都没有，结果集就被直接回抛给客户端。

#### 字符级差异对缓存命中的破坏性验证

为了验证查询缓存的“脆弱性”，我们在 5.7 中设计如下两组对照实验。

##### 实验一：空格注入测试
我们首先执行一条过滤语句：
```sql
SELECT * FROM departments WHERE department_id = 10;
```
随后，我们在 `WHERE` 后面刻意敲入三个连续空格，语句语义没有任何变化：
```sql
SELECT * FROM departments WHERE   department_id = 10;
```
通过 `SHOW PROFILES;` 取出对应的 Query ID（如 10 和 11）并执行 `SHOW PROFILE` 查看：
- Query 10 走完了 25 个阶段，并在末端执行了 `storing results in query cache`；
- Query 11 并没有像大家预想的那样命中缓存，而是**重新老老实实完整走了一遍 25 个阶段**，又在末端重新执行了一次 `storing results in query cache`！

##### 实验二：等价逻辑变换测试
若我们将查询条件改写为等价形式：
```sql
-- 逻辑等价，但字符完全不同
SELECT * FROM departments WHERE department_id > 9 AND department_id < 11;
```
由于文本哈希完全匹配不上，缓存同样彻底失效，系统依然按全新查询重新解析与优化。

> **结论**：查询缓存是以文本字符串作为硬性 Key 进行精确匹配的。业务代码中只要存在动态拼接 SQL、不同开发者格式化风格不一（多一个缩进、大小写不同），查询缓存的命中率就会急剧劣化。

### 生产环境建议与按需缓存模式

通过上述在 8.0 和 5.7 上的对比实操，我们可以清晰得出如下生产与调优结论：

1. **MySQL 5.7 生产调优建议**：
   如果线上系统必须运行在 5.7 环境，且存在使用查询缓存的诉求，**强烈建议将 `query_cache_type` 设置为 `2`（即 DEMAND 模式）**。
   ```ini
   [mysqld]
   # 开启按需缓存模式
   query_cache_type = 2
   ```
   在 `DEMAND` 模式下，普通查询默认统统不进缓存，从而彻底避免了频繁更新的高频表因为缓存失效引发的全局锁竞争；只有在业务方明确知晓该表是静态字典表（如城市编码表、行业分类表）、且查询量极大时，才由程序员在 SQL 中显式声明：
   ```sql
   -- 仅对静态数据显式要求缓存
   SELECT SQL_CACHE * FROM base_district_code;
   ```
2. **Profiling 工具的定位习惯**：
   在后续深入学习索引调优时，当发现某条查询耗时异常时，第一时间进入测试环境执行：
   ```sql
   SET profiling = 1;
   -- 运行慢 SQL
   SHOW PROFILE CPU, BLOCK IO;
   ```
   重点排查列表中的 `Sending data`（数据在引擎与服务层之间流转）、`Copying to tmp table on disk`（内存临时表被打爆转为磁盘临时表）或 `Sorting result`（外部文件排序）是否占据了 90% 以上的耗时，从而为针对性加索引或重构 SQL 提供精准的物理诊断依据。

## 112-Oracle中SQL执行流程_缓冲池的使用
> 对应分集：P112 | 原始标题：《112-Oracle中SQL执行流程_缓冲池的使用》

在掌握了 MySQL 的三层架构与 SQL 执行全生命周期之后，很多同学往往会形成一种技术定势，认为天下所有的关系型数据库底层大抵都是这么运转的。为了打破这种思维局限，本讲我们首先把视线投向商用数据库霸主 Oracle，看看在 Oracle 的架构设计中，一条 SQL 是如何被解析、编译和执行的。更重要的是，通过横向对比 Oracle 著名的“共享池”与 MySQL 的“查询缓存”，我们将自然引出无论是 Oracle 还是 MySQL 能够支撑海量高并发业务的最核心心脏——**数据库缓冲池（Buffer Pool）**。

---

### 跨数据库对比：Oracle 中 SQL 执行流程与共享池架构

把 SQL 投递给 Oracle 数据库服务器后，其内部处理管线同样井然有序。表面上看，它与 MySQL 同样要经历校验、优化与执行，但在关键设计节点上却展现出了完全不同的架构哲学。

```text
[客户端提交 SQL 文本]
         |
         v
+-----------------------------------------------------------------------------------+
| 1. 语法检查 (Syntax Check) : 校验关键字拼写、括号配对是否合法                      |
+----------------------------------------+------------------------------------------+
                                         |
+----------------------------------------v------------------------------------------+
| 2. 语义检查 (Semantic Check) : 校验表名、字段名、视图是否存在                     |
+----------------------------------------+------------------------------------------+
                                         |
+----------------------------------------v------------------------------------------+
| 3. 权限检查 (Permission Check) : 校验当前会话账户是否对目标对象拥有访问权限        |
+----------------------------------------+------------------------------------------+
                                         |
+----------------------------------------v------------------------------------------+
| 4. 共享池检查 (Shared Pool Check) : 检索 SGA 中的共享池                            |
|    +----------------------------------------------------------------------------+ |
|    | 库缓存 (Library Cache) : 基于 SQL 哈希值检索是否已有缓存的执行计划          | |
|    | 数据字典缓冲区 (Data Dictionary Cache) : 检索系统元数据与数据字典           | |
|    +------------------------------------+---------------------------------------+ |
+-----------------------------------------|-----------------------------------------+
                    |                     |
     [未命中执行计划] |                     | [命中执行计划]
                    v                     v
+-----------------------------------+  +--------------------------------------------+
| 【硬解析 (Hard Parse)】           |  | 【软解析 (Soft Parse)】                    |
| - 调用优化器计算代价              |  | - 直接复用共享池中的执行计划               |
| - 决定存取路径并生成执行计划      |  | - 彻底跳过优化器漫长且昂贵的编译优化运算   |
| - 将 SQL 与执行计划回写共享池     |  |                                            |
+-------------------+---------------+  +--------------------+-----------------------+
                    \                     /
                     \                   /
+---------------------v-----------------v-------------------------------------------+
| 5. 执行器调度与数据读取 (进入数据高速缓冲区 Database Buffer Cache 提数)            |
+-----------------------------------------------------------------------------------+
```
*图解说明：Oracle 中 SQL 执行流程图呈现了由三大前置检查进入共享池，再分流为硬解析与软解析的关键路径。*

#### 共享池的两大核心组成

Oracle 在其系统全局区（SGA, System Global Area）中开辟了一块极其核心的内存区域——**共享池（Shared Pool）**。共享池主要由两大子模块构成：

1. **库缓存（Library Cache）**：
   库缓存是保存 SQL 文本及其对应**已编译执行计划（Execution Plan）**的专属区域。
   > **对比**：MySQL 5.7 的查询缓存存的是“SQL 文本与其返回的最终数据结果集”；而 Oracle 库缓存存的是“SQL 文本与其背后的执行计划”。
2. **数据字典缓冲区（Data Dictionary Cache）**：
   数据库在执行任何一条业务 SQL 时，都必须频繁获知相关的元数据信息（例如 `user_tables`、`user_tab_columns`、账户权限等）。如果每次执行权限校验或字段核对都去物理磁盘扫描数据字典表，系统性能将彻底崩溃。
   因此，Oracle 在实例启动时就会把常用系统表及元数据预热并驻留在数据字典缓冲区中。这与 Java 虚拟机在启动时优先把核心基础类（如 `java.lang.Object`、`java.lang.String`）载入内存方法区的机制如出一辙。

#### 硬解析与软解析的技术边界

在 Oracle 执行流程中，最具代表性的概念莫过于**硬解析（Hard Parse）**与**软解析（Soft Parse）**：

- **硬解析（Hard Parse）**：
  当一条 SQL 传入共享池后，Oracle 计算其哈希值并在库缓存中检索。如果从未见过这条语句，优化器必须介入，经历完整的语义分析、多表驱动次序评估、索引选型、代价估算，最终生成一份二进制的执行计划，并将其连同 SQL 注册进库缓存。这一套重型编译过程开销极大，重度消耗 CPU。
- **软解析（Soft Parse）**：
  若 SQL 传入后，系统在库缓存中精准命中了完全相同的语句，Oracle 将直接调取此前已经编译好的执行计划交付执行器调度，彻底免去了优化器的编译推演开销。

#### 绑定变量（Bind Variables）的提效与代价

为了尽可能规避沉重的硬解析、全力促成软解析，Oracle 极为推崇**绑定变量（Bind Variables）**机制。

如果我们在业务代码中直接硬编码拼接参数：
```sql
-- 第一次执行：硬解析，编译生成执行计划
SELECT * FROM orders WHERE order_id = 10001;

-- 第二次执行：字符不同，哈希值变动，再次触发硬解析！
SELECT * FROM orders WHERE order_id = 10002;
```
由于数值的物理变动，Oracle 判定为两条完全不同的独立 SQL，导致系统频繁进行重复的硬解析。

若改用绑定变量（形如占位符）：
```sql
-- 将动态参数变量化绑定
SELECT * FROM orders WHERE order_id = :v_order_id;
```
无论后续业务端将 `:v_order_id` 赋值为 10001 还是 10002，发送到 Oracle 服务端的 SQL 模板与哈希值恒定不变。Oracle 仅在首次执行时执行一次硬解析，后续成千上万次调用均可享受软解析的零开销提速。

> **提示**：绑定变量固然能极大节省 CPU 解析损耗，但也并非完美无瑕。其主要弊端在于**数据倾斜下的执行计划固化**：若某列数据分布极不均匀（例如某个状态值占全表 99% 数据，另一个状态值仅占 1% 数据），强制复用基于首次参数生成的执行计划，可能会导致本该走全表扫描的查询误走索引，或者本该走索引的查询误走全表扫描。

### 数据库缓冲池（Buffer Pool）的核心定位与设计哲学

在探讨了 SQL 如何被解析与编译之后，执行器终究要面对数据的存取。无论是 MySQL 还是 Oracle，数据最终都要落盘持久化在机械硬盘或固态硬盘上。

但如果在每一次需要数据时，都由操作系统去驱动磁头或主控芯片寻址物理磁盘，任何现代数据库都会瞬间瘫痪。

#### 内存与磁盘的物理鸿沟

计算机硬件的层级访问速度存在着量级悬殊的鸿沟：
- CPU 寄存器与各级高速缓存（L1/L2/L3）的访问耗时在纳秒（$ns$）级别；
- 物理内存（DRAM）的访问耗时在几十到几百纳秒之间；
- 机械磁盘的随机寻址耗时在毫秒（$ms$）级别，即便是顶级的 NVMe 固态硬盘，其随机 I/O 耗时也在数十微秒级别。

内存与磁盘之间的速度差距，正如俗话所说：**“天上一天，地上一年”**。

在高校学习数据结构与算法时，我们常常纠结于一个算法的时间复杂度是 $O(n^2)$ 还是 $O(n \log n)$。但需要认清一个事实：**那些算法复杂度的对比，全部是建立在纯内存计算的基础之上的**。一旦某套运算逻辑跨越了物理边界触发了一次磁盘 I/O，那么哪怕是一个 $O(1)$ 的磁盘随机读取，其物理等待耗时也足以将你在内存中精心优化的算法优势彻底归零。

> **结论**：数据库的核心优化目标，永远是**尽可能减少物理磁盘 I/O 的交互频次**。而数据库缓冲池（Buffer Pool）正是为了抹平 CPU 与磁盘之间的速度鸿沟而生的最核心组件。

#### 缓冲池与查询缓存的本质区别

很多初学者容易将“查询缓存”与“缓冲池”混为一谈，必须在此划清界限：

| 对比维度 | 查询缓存（Query Cache） | 缓冲池（Buffer Pool） |
| :--- | :--- | :--- |
| **所属架构层级** | MySQL 服务层（Server Layer） | 存储引擎层（如 InnoDB 引擎层） |
| **底层缓存对象** | 纯文本 SQL 字符串 $\rightarrow$ 结果集（Key-Value 结构） | 磁盘底层的**物理数据页（Data Pages）**与索引页 |
| **数据动态粒度** | 粗粒度黑盒：表有写操作则整表缓存清空 | 细粒度控制：基于页的加载、修改、LRU 淘汰与刷盘 |
| **版本存废现状** | 表现鸡肋，在 MySQL 8.0 中已被官方彻底废除 | **各大数据库的核心基石，任何版本均重度依赖并持续演进** |

#### 数据页（Data Page）与成批调度机制

在磁盘与操作系统层面，数据并不是像一条条字符串一样散落存放的。InnoDB 存储引擎将底层表空间划分为连续的逻辑块，这个基本物理单元被称为**数据页（Data Page）**，其默认大小为 **16KB**。

假设我们执行如下查询：
```sql
SELECT * FROM employees WHERE employee_id = 101;
```
虽然我们只向数据库索要 101 号员工这一条记录（物理上可能仅占几十个字节），但存储引擎**绝不可能**跑到磁盘上只把这几十个字节扣出来返回。
存储引擎的最小 I/O 交互单位是**页**：它必须将 101 号员工所在的**整个 16KB 数据页**完整读入内存中的缓冲池，随后由服务层在内存中过滤出该单行数据。

### 缓冲池的工作原则、脏页刷盘与崩溃安全前瞻

既然物理内存容量远小于物理磁盘（例如服务器物理磁盘有 500GB 数据，但系统只分给 Buffer Pool 8GB 内存），缓冲池该如何运作？

#### 缓冲原则与预读（Read-Ahead）机制

缓冲池的维护策略遵循：**“位置决定效率，频次决定留存”**。

1. **热点数据淘汰置换**：
   缓冲池使用改进的 LRU（Least Recently Used）链表管理物理页。系统优先将访问频次极高的“热数据页（Hot Pages）”常驻在缓冲池中；当空闲空间不足时，自动淘汰长期未被访问的冷数据页。
2. **局部性原理与预读特性**：
   存储系统具有显著的**空间局部性**——如果当前某数据页被读取，那么与其在物理上相邻或逻辑连续的前后数据页，在极短时间内大概率也会被访问。
   因此，InnoDB 具备**预读（Read-Ahead）**机制：在加载当前 16KB 数据页时，系统若判定其处于连续读取状态，会异步预先将周围的一批相邻页一并提前载入缓冲池。当后续查询真正发生时，直接命中内存，省去了磁盘 I/O 阻塞。

#### 脏页（Dirty Page）的产生与异步刷盘

当应用端向数据库发送写操作（`INSERT`、`UPDATE`、`DELETE`）时，缓冲池的执行逻辑如下：

```text
[客户端发送 UPDATE 指令]
         |
         v
+-----------------------------------------------------------------------------------+
| 1. 检查数据所在页是否在 Buffer Pool 中                                              |
|    - 若在，直接在内存中修改该数据页;                                               |
|    - 若不在，先将磁盘数据页读入 Buffer Pool，再在内存中完成修改。                    |
+----------------------------------------+------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
| 2. 产生【脏页 (Dirty Page)】                                                       |
|    - 此时 Buffer Pool 内存页已被更新，但磁盘文件尚未同步，内存与磁盘数据产生不一致。 |
+----------------------------------------+------------------------------------------+
                                         |
                                         v (严禁立即同步回写磁盘!)
+-----------------------------------------------------------------------------------+
| 3. 异步刷盘机制 (Checkpoint / 后台刷新线程)                                        |
|    - 后台线程依据负载策略，定期将多个脏页批量顺序写回物理磁盘。                   |
+-----------------------------------------------------------------------------------+
```

为什么绝对不能“改完内存立刻同步写磁盘”？
因为一个数据页足足有 16KB，而一个 `UPDATE` 往往只是将某个用户的年龄从 20 改成 21，仅仅动了其中的 1 个字节。如果为了同步这 1 个字节，强迫操作系统发起一次随机 I/O 去覆写整个 16KB 的磁盘物理块，在高并发下磁盘会瞬间被 I/O 队列压垮。

因此，修改动作优先在内存完成，内存中已被篡改但尚未刷盘的数据页被称为**脏页（Dirty Page）**。系统依托后台线程按照预设的 **Checkpoint（检查点）** 机制，平滑、周期性地批量将脏页异步刷新到物理磁盘（这一动作即俗称的“刷盘”）。

#### 宕机与事务安全前瞻：Redo Log 与 Undo Log 的诞生由头

异步刷盘机制虽然大幅提升了写入吞吐，但却在系统架构上撕开了一个致命的安全漏洞：**如果内存中的脏页刚刚被修改，还没来得及刷盘，服务器突发停电或操作系统宕机，已提交的数据不就凭空蒸发了吗？**

与此同时，如果在一次包含多条修改的业务事务处理中，数据只刷盘了一半系统就崩溃了，重启后如何把这半截脏数据彻底撤销（回滚）？

为了解决这一矛盾，MySQL 设计了底层的核心事务日志体系：
- **Redo Log（重做日志）**：解决“刷盘未完成突发宕机”的问题。在修改内存数据页的同时，将物理修改以顺序追加写的方式极速记录到 Redo Log。只要 Redo Log 成功刷盘，即便内存脏页未来得及同步，实例重启时也能依据 Redo Log 进行前滚重放，保障数据的持久性（Crash-safe）。
- **Undo Log（回滚日志）**：解决“事务撤销回滚与原子性”的问题。在修改数据之前，先将数据被修改前的原始镜像记入 Undo Log。若事务需要回滚或崩溃后需要清理未提交的半拉子操作，系统可以依据 Undo Log 逆向还原旧值。

### 缓冲池参数调优与多实例（Instances）并发解耦

缓冲池作为系统资源消耗大户，其内存大小与结构划分直接主导着整个数据库实例的承载上限。

#### 缓冲池容量调优（Size）

不同的存储引擎对缓冲池的调配策略各异：
- **MyISAM 存储引擎**：天然只使用 `key_buffer_size` 缓存索引块，并不在内存中缓存纯数据行，数据读取依赖操作系统自身的文件系统缓存；
- **InnoDB 存储引擎**：索引与数据全部由 InnoDB 自治管理，其核心调优参数为 `innodb_buffer_pool_size`。

在 MySQL 8.0 终端中检视该参数的默认设定：
```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
```
控制台回显：
```text
+-------------------------+-----------+
| Variable_name           | Value     |
+-------------------------+-----------+
| innodb_buffer_pool_size | 134217728 |
+-------------------------+-----------+
```
`134217728` 字节即 **128MB**。在真实的生产服务器（如配置 64GB 内存的独立数据库宿主机）上，128MB 显然过于拮据。行业经典实践通常将物理内存的 **50% ~ 75%** 全权倾斜划拨给 `innodb_buffer_pool_size`。

在支持动态重置的较新版本中，可以通过动态指令进行内存扩容：
```sql
-- 动态将缓冲池提升至 256MB
SET GLOBAL innodb_buffer_pool_size = 268435456;
```
在生产环境中，应同步将其写入 `/etc/my.cnf` 确保持久固化：
```ini
[mysqld]
innodb_buffer_pool_size = 256M
```

#### 缓冲池多实例拆分（Instances）

随着服务器硬件核心数向几十甚至上百核演进，高并发场景下暴露出另一个严重瓶颈：**缓冲池的全局互斥锁竞争**。

如果整个数据库只维护一个庞大的 Buffer Pool 单实例，数以千计的业务线程在并发访问、换入换出数据页时，都必须频繁申请并竞争这同一个缓冲池的全局保护锁（Mutex）。锁争用会导致线程排队自旋，CPU 使用率居高不下而系统吞吐量停滞不前。

为了打破互斥锁天花板，InnoDB 支持将缓冲池逻辑切分为**多个独立的 Buffer Pool 实例（Instances）**。

```text
+-----------------------------------------------------------------------------------+
|                        总缓冲池空间 (例如 2GB)                                     |
| ================================================================================= |
|  +-------------------------------+  +-------------------------------------------+ |
|  | Buffer Pool 实例 1 (1GB)      |  | Buffer Pool 实例 2 (1GB)                  | |
|  | - 独立的物理内存块与 LRU 链表 |  | - 独立的物理内存块与 LRU 链表             | |
|  | - 独立的互斥锁 (Mutex)        |  | - 独立的互斥锁 (Mutex)                    | |
|  +---------------+---------------+  +-------------------+-----------------------+ |
+------------------|--------------------------------------|-------------------------+
                   ^                                      ^
                   |                                      |
              [工作线程 A]                           [工作线程 B]
             (独占访问实例 1)                       (独占访问实例 2)
```
*图解说明：多实例拆分图展示了将全局大缓冲池划分为互相独立的物理子实例，各线程操作独立加锁，消除了并发互斥锁热点。*

通过配置参数 `innodb_buffer_pool_instances`，每个实例独立管理自己的 LRU 链表、Flush 链表和互斥锁：
```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';
```
系统默认值为 `1`。如果需要在多核高并发服务器上拆解为多个实例，可在配置文件中调整：
```ini
[mysqld]
innodb_buffer_pool_size = 2G
innodb_buffer_pool_instances = 2
```

> **注意（1GB 约束硬门槛）**：
> 官方对多实例设计设有严格的约束底线：**只有当 `innodb_buffer_pool_size` 的总大小大于或等于 1GB 时，设置多实例才被系统真正激活生效**。
> 如果总缓冲池容量小于 1GB（例如仅为 256MB），即便在配置中强行指定 `innodb_buffer_pool_instances = 4`，MySQL 在初始化时也会强行将其重置回 `1`。这是因为在微型内存体量下，多实例引发的内存碎片及实例间管理元数据的损耗，远大于锁解耦带来的并发收益。
