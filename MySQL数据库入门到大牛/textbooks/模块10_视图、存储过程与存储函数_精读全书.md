## 74-数据库对象与视图的理解
> 对应分集：P74 | 原始标题：《74-数据库对象与视图的理解》

在前面的章节中，我们从最基础的单表查询、多表关联、单行函数、聚合函数，一路推演到 DDL 表定义、DML 数据变更、事务控制以及第 13 章的完整性约束。回过头来看，之前所有内容的物理承载核心只有一种结构——**数据表（Table）**。

但在现代关系型数据库的完整体系中，数据表仅仅是底层存储基石。从本讲开始，我们将跨过一条重要的技术分水岭，系统性地推开**数据库对象（Database Objects）**的大门。这一体系包含了视图（View）、存储过程（Stored Procedure）、存储函数（Stored Function）、触发器（Trigger）以及索引（Index）。

而作为数据库对象体系的第一站，**视图（View）**绝非只是简单的“快捷查询模板”。很多人在初学时容易把它当作一张普通表来用，结果在生产环境中遇到数据权限失控、多表更新异常等一系列棘手问题。本讲将从数据库对象全貌切入，深入拆解视图的设计初衷、物理本质与核心价值。

---

### 关系型数据库对象体系全景图

在 MySQL 中，所谓“数据库对象”，是指存储在数据库中、具有特定技术功能和独立元数据定义的命名实体。理解这些对象的分工，是建立高阶数据库设计思维的前提。

```text
+--------------------------------------------------------------------+
|                         MySQL 数据库对象体系                        |
+--------------------------------------------------------------------+
| [存储基石]  表 (Table)            : 二维行与列，真实持久化业务数据  |
| [元数据]    数据字典 (Dictionary) : 系统元数据表，记录权限、用户与架构|
| [完整性]    约束 (Constraint)     : 保证实体、引用、域完整性的规则  |
| [逻辑抽象]  视图 (View)           : 虚拟表，本质是持久化的查询逻辑  |
| [性能检索]  索引 (Index)          : B+ 树等高效检索与聚簇排序载体   |
| [逻辑封装]  存储过程 (Procedure)  : 预编译 SQL 代码块，支持复杂逻辑 |
| [函数扩展]  存储函数 (Function)   : 封装计算逻辑，必须且仅有单返回值|
| [事件驱动]  触发器 (Trigger)      : 监听 DML 事件并在操作前后自动执行|
+--------------------------------------------------------------------+
```
> 图 1：MySQL 核心数据库对象分类与协作示意图。

#### 数据字典与约束对象
- **数据字典（Data Dictionary）**：本质上也是表，但属于系统内部元数据表。例如名为 `mysql` 的核心系统库，里面记录着当前实例的所有用户账号、全局与库表级权限配置等。对于普通业务开发与维护人员而言，数据字典通常只供查询与探查，严禁通过底层 SQL 直接手动修改。当我们执行 DDL 创建用户或通过 DCL 赋予权限时，引擎底层会自动维护并同步数据字典的状态。
- **约束（Constraint）**：约束不仅是一条语法规则，同样具备独立的对象命名机制（如 `pk_`、`fk_`、`uk_`）。它的核心使命是构筑数据完整性的防线，拦截非法数据的脏写入。

#### 索引与程序化逻辑对象
- **索引（Index）**：主要目标是提升数据检索效率。很多初学者常把索引比作《新华字典》前面的部首拼音检字目录：有了目录，找某个汉字直接翻到对应页码即可；没有目录，就只能从第一页一页页死翻到底。虽然这个比喻很形象，但索引在底层还承担着 InnoDB 聚簇索引数据存储排布的重任，其机理远比纸质书的静态目录复杂。
- **存储过程（Stored Procedure）与存储函数（Stored Function）**：它们是对一系列复杂业务 SQL 逻辑的高级封装。两者的核心区别在于返回值规范：存储函数（Function）具有严格的返回值约束，必须且只能返回单个确定结果；而存储过程（Procedure）在接口设计上更为灵活，它既可以没有返回值，也可以通过多个 `OUT` 模式的输出参数批量向调用方返回结果。
- **触发器（Trigger）**：触发器本质上是一种内嵌于数据库引擎的“事件监听器（Event Listener）”。如同在手机屏幕上点击一个操作按钮会触发底层绑定的点击事件监听一样，当对业务表执行 `INSERT`、`UPDATE` 或 `DELETE` 时，系统会自动侦测并执行预先挂载的触发器脚本。例如，在核心业务表中物理删除某条重要记录之前，触发器可以在删除落盘的瞬间自动把被删数据拦截并转存至历史审计备份表中，形成无缝的数据审计链路。

### 视图的设计初衷与业务演进痛点

有了承载实体数据的物理表，为什么还要在表之上凭空引入一层视图？我们可以通过一个真实的业务场景来推导它的必然性。

#### 敏感数据泄露与权限失控的工程危机

假设我们有一张包含 30 多个字段的员工全量档案表 `employees`。这张表里不仅保存着员工编号、姓名、联系电话、入职日期等基础信息，还包含着极其敏感的核心字段：员工薪资（`salary`）以及管理层对该员工的私密考评与晋升评语（例如“该员工表现突出，下季度升职加薪”或“该员工技能不达标，试用期延长一个月”）。

```text
+-------------------------------------------------------------------+
|                        employees 全量基表                         |
+-------------+----------+--------------+-----------+---------------+
| employee_id | name     | phone        | salary    | evaluation    |
| (公开标识)  | (公开)   | (普通运维)   | (极度敏感)| (内部机密)    |
+-------------+----------+--------------+-----------+---------------+
       |           |            |             |             |
       \-----------+------------/             \-------------/
            基础普通字段                          机密敏感字段
```
> 图 2：员工档案全量表字段敏感度分级。普通运维与机密数据混杂于同一张物理表中。

在实际运维中，通常需要指派初级运维人员（如初入职的系统管理员或外包维护人员）对员工的普通档案进行日常更新维护（如修改员工变更后的联系电话）。

此时立刻暴露出两个严峻的技术矛盾：
1. **数据隐私泄露风险**：员工薪水和人事考核只允许人力资源主管（CHRO）及高管查阅。如果把整张 `employees` 表的权限开放给普通管理员，全公司的薪酬与评价将对所有人裸奔。
2. **操作失误引发灾难**：如果为了让他能改电话而直接下发整张大表的 `UPDATE` 甚至 `DELETE` 权限，一旦操作失误没有写 `WHERE` 条件，或者误执行了全表清除且事前没有备份，整张生产大表的数据就会瞬间被清空，造成不可逆的生产事故。

#### 实体子表复制方案的缺陷

面对这个矛盾，很多没有架构经验的开发者会本能地想到方案一：**利用查询创建物理子表**。

通过前面学习的 DDL 语法：
```sql
CREATE TABLE emp_public 
AS 
SELECT employee_id, name, phone 
FROM employees;
```
这样确实剥离了敏感字段，然后把新表 `emp_public` 的操作权限赋予管理员，让他全权维护这张新表。

然而，这种设计在工程上是致命的错误：
- **物理数据割裂**：`CREATE TABLE ... AS SELECT` 在执行时是对原表数据做了一次**物理深拷贝**。生成的新表与原表在磁盘上完全独立。
- **数据更新无法联动**：当管理员在 `emp_public` 中把某位员工的电话更新为新号码后，原生产主表 `employees` 中的对应记录根本不会发生任何改变！
- **主从数据严重失步**：生产系统业务仍然依赖 `employees` 派发业务，导致新修改的数据成了死数据，引发严重的业务逻辑混乱。

#### 视图方案的破局：逻辑投影与权限穿透

这就是视图（View）大显身手的标准场景。

我们不再去建物理表，而是创建一个视图：
```sql
CREATE VIEW v_emp_public 
AS 
SELECT employee_id, name, phone 
FROM employees;
```

```text
[ DBA / 普通管理员 ]
        |
        | 1. 查询/修改视图 (脱敏环境)
        v
+-----------------------------+
|    视图: v_emp_public       | ---> 纯逻辑投影 (不占物理行空间)
+-----------------------------+
        |
        | 2. 引擎底层映射穿透
        v
+-------------------------------------------------------------+
|                    底层物理基表: employees                  |
| [employee_id] [name] [phone] | [salary] [evaluation] (隐藏) |
+-------------------------------------------------------------+
```
> 图 3：视图在用户与底层物理基表之间构建的安全隔离层。

将视图交付给管理员后：
1. **敏感字段天然隔离**：在视图的投影范围内，根本不存在 `salary` 和 `evaluation` 字段，管理员无论用任何 SQL 探索，也绝无可能窥探到底层机密。
2. **数据双向实时同步**：当管理员对 `v_emp_public` 执行 `UPDATE` 修改电话号码时，底层基表 `employees` 的对应记录被实时修改；反之，若在底层基表直接变更数据，查视图也会立刻展现最新结果。
3. **精细化权限管控**：MySQL 支持针对单个视图独立授予 `SELECT`、`UPDATE`、`DELETE` 权限。我们可以只开放视图的读写权限，而彻底对物理大表关上权限大门，杜绝误操作毁库的风险。

### 视图的物理本质与核心工作机理

彻底掌握视图，必须将其抽象认知从“神奇的表”还原到真实的底层实现。

#### 核心本质：持久化存储的 SELECT 语句

> **结论**：**视图的本质，就是被赋予了独立名称并持久化保存在数据字典中的 `SELECT` 查询语句。**

普通的一条 `SELECT` 查询语句在终端执行完毕后，结果集仅在网络传输和客户端内存中短暂驻留，查询本身随之结束。而创建视图的操作：
```sql
CREATE VIEW 视图名称 AS 查询语句;
```
实际上相当于给这段复杂的 `SELECT` 逻辑加了一个“命名外壳”，并将其作为数据库元数据持久化保存在系统架构中。

因此必须建立三个深刻的技术认知：
1. **视图本身不存储任何实体业务数据**：它的行数据完全是动态由底层物理表映射计算生成的。
2. **基表的定义**：视图所依赖的一个或多个物理数据表，在数据库术语中统称为**基表（Base Table）**。
3. **数据源的一致性**：对视图进行增删改查，最终都是底层存储引擎穿透转换并作用于基表。系统中自始至终只有一份真实数据，那就是基表里的物理数据。

#### 视图生命周期与基表的解耦特性

很多学习者存在一个顾虑：既然通过视图修改数据会直接改动基表，那么反过来，如果哪天业务迭代我不需要这个视图了，执行 `DROP VIEW` 会不会误删基表数据？

> **结论**：**视图的创建与删除只会影响视图本身的元数据，绝对不会对底层基表的数据造成任何破坏或删除！**

因为删除视图本质上只是把数据字典里存储的那段 `SELECT` 字符串定义抹除掉，它既不会去清空基表的磁盘数据页，也不会改动基表的元数据结构。基表依然完好无损。

### 视图在不同工程规模中的适用边界

在软件工程实践中，视图并非无脑滥用的万能钥匙，必须根据系统的架构规模与复杂度理性决策。

#### 小型系统与移动端轻量级应用的场景考量
在常规的初创型项目、毕业设计、或仅有几十张表的中小型 App/Web 场景中：
- 业务表关联关系通常比较扁平，表内字段少，业务 SQL 逻辑相对可控。
- 过度包装视图反而会在代码与数据库之间多增加一层抽象屏障，增加维护人员排查调试的链路复杂度。
- 在这种场景下，**不推荐大规模堆砌视图**，直接在持久层编写原生 SQL 即可满足诉求。

#### 大型企业级系统与复杂数据流的赋能价值
当业务进入大规模阶段（例如微服务核心共享库、大型 ERP、电商中台或数仓报表系统），数据表往往多达数百张，单张表几十上百个字段：
- **复杂查询的降维简化**：一个报表需求可能需要跨 5 到 8 张大表做三层嵌套子查询和复杂内联外联，手写一段 SQL 动辄上百行。将其封装为视图后，外部调用人员只需像操作单表一样执行 `SELECT * FROM v_report_summary WHERE ...`，大幅降低协作团队的认知负荷。
- **构建统一的数据安全沙箱**：针对风控、财务、外部第三方服务商等不同层级角色，可以基于同一组核心底层表派生出形态各异的视图切片，实现颗粒度极细的列级数据访问控制。

#### 核心优缺点对比

| 维度 | 视图（View）的优势 | 潜在的边界与制约 |
| :--- | :--- | :--- |
| **查询编写** | 封装超长复杂 SQL，多表联查降维为单表查询 | 抽象层级过深可能导致调用方忽视底层多表关联的开销 |
| **数据安全** | 天然实现列级/行级数据脱敏与精细化权限隔离 | 无法替代应用层的业务安全风控 |
| **存储开销** | 不占用物理磁盘空间（仅存查询元数据定义） | 每次查询都需要穿透执行或动态合并，有一定计算开销 |
| **数据联动** | 与底层基表天然双向联动，无需额外开发同步管道 | 包含聚合函数、分组、DISTINCT 等复杂逻辑的视图往往不可更新 |
| **生命周期** | 视图的创建与删除完全解耦，不影响基表安全 | 基表若发生 DDL 删列改名，会导致依赖该列的视图不可用 |

通过本讲的拆解，我们理清了视图作为虚拟表的设计哲学。在接下来的章节中，我们将进一步进入实操，系统掌握视图的创建语法、多源派生、结构查看以及安全更新的边界约束。

## 75-视图的创建与查看
> 对应分集：P75 | 原始标题：《75-视图的创建与查看》

在上一讲中，我们从架构层面把视图的本质剖析得非常透彻：视图就是一段被命名并持久化在数据字典中的 `SELECT` 查询语句，本身并不占用任何物理行存储。那么在具体的数据库开发与系统运维中，如何优雅、规范地构建视图？面对单表、多表关联甚至多层嵌套的业务需求，视图有哪些不同的创建方式？创建完毕后，又该如何借助数据库内置的元数据指令对其结构与状态进行全方位检视？

这一讲我们将进入全实操阶段。不仅要掌握视图创建的标准语法模板，更要搞明白字段别名映射、计算字段虚拟投影、基于现有视图派生新视图的链路机理，并熟练运用四种不同的元数据查看机制，洞悉视图在底层系统字典中的真实表现形态。

### 实验基准环境准备与复制表约束剖析

在演练视图操作之前，我们先在本地创建专用的测试数据库 `dbtest14`，并从示例库中克隆两张经典的基础表——员工表 `emps` 与部门表 `depts`，作为后续构建视图的物理基表。

```sql
CREATE DATABASE dbtest14;
USE dbtest14;

-- 基于现有数据库全量克隆员工表与部门表
CREATE TABLE emps AS SELECT * FROM atguigudb.employees;
CREATE TABLE depts AS SELECT * FROM atguigudb.departments;
```

执行后查询 `SELECT COUNT(*) FROM emps;`，返回 107 条员工记录；查询 `depts` 返回 27 条部门记录，数据已完备导入。

```text
+-------------------------------------------------------------+
|                      基准测试库 dbtest14                    |
+------------------------------+------------------------------+
|       物理基表: emps         |       物理基表: depts        |
|    (包含 107 条员工数据)     |     (包含 27 条部门数据)     |
+------------------------------+------------------------------+
                               |
            +------------------+------------------+
            | 逻辑抽象 (不占物理存储)            |
            v                                     v
+-----------------------+             +-----------------------+
|  单表视图 (如 vu_emp1)|             | 多表视图 (vu_emp_dept)|
+-----------------------+             +-----------------------+
```
> 图 1：基准物理数据表与上层派生视图的逻辑关系示意图。

#### 关键避坑：CREATE TABLE AS SELECT 的约束丢失现象
当我们执行 `DESC emps;` 检查新克隆的表结构时，会发现一个容易被忽视的底层细节：
虽然原库中的 `atguigudb.employees` 明确拥有主键约束（`employee_id` 为 `PRI`）、唯一性约束以及外键约束，但在通过 `CREATE TABLE ... AS SELECT` 生成的 `emps` 表中，除了列的非空属性（`NOT NULL`）被继承下来外，**原表的所有主键、唯一键和外键约束全部丢失了**！

> **注意**：`CREATE TABLE ... AS SELECT` 本质上只是依据查询结果集的元数据（字段名与数据类型）搭建一张新表并插入行记录，它不会把基表的复杂索引树与键约束关系同步复制过来。虽然这一特性并不阻碍我们后续基于该表构建视图，但在生产环境中克隆数据表时必须保持清醒，切勿误以为所有约束均已自动继承。

### 视图创建的核心语法与多维构建场景

在 SQL 体系中，创建对象的命令保持着高度的对称性：建表是 `CREATE TABLE`，建函数是 `CREATE FUNCTION`，建触发器是 `CREATE TRIGGER`，而创建视图就是直观的 `CREATE VIEW`。

#### 视图创建的完整语法骨架

MySQL 官方提供的完整视图创建语法规范如下：

```sql
CREATE [OR REPLACE]
    [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}]
    VIEW 视图名称 [(字段别名列表)]
    AS SELECT 查询语句
    [WITH [CASCADED | LOCAL] CHECK OPTION];
```

##### 语法参数简析：
- `OR REPLACE`：若指定名称的视图已存在，则直接覆盖替换现有定义，常用于视图的平滑变更升级。
- `ALGORITHM`：视图处理算法，包含三种取值：
  - `UNDEFINED`（未定义，默认）：由 MySQL 优化器自动选择最合适的执行算法；
  - `MERGE`（合并）：将外部查询视图的语句与视图内部的 `SELECT` 语句合并为一条复合 SQL 后再执行优化与检索；
  - `TEMPTABLE`（临时表）：每次调用视图时，先将视图的查询结果物理物化生成一张内部临时表，外部查询再针对该临时表执行过滤检索。
- `WITH CHECK OPTION`：更新视图时的完整性检查策略，分为层叠检查（`CASCADED`）与本地检查（`LOCAL`）。

在常规业务开发中，我们通常无需在一开始就显式介入复杂的底层算法，可以采用最精炼的标准核心范式：
```sql
CREATE VIEW 视图名称 AS SELECT 查询语句;
```

#### 场景一：基于单表构建视图与字段命名的两种范式

当业务需要将单张表中的部分字段投影出来，并实施行级数据过滤时，通常构建单表视图。

##### 范式 A：默认沿用基表列名
```sql
CREATE VIEW vu_emp1 
AS 
SELECT employee_id, last_name, salary 
FROM emps;
```
创建完成后执行 `SELECT * FROM vu_emp1;`，返回 107 条记录，每一行仅展示我们指定的 3 个字段。此时视图列名与物理基表完全一致。

##### 范式 B：在 SELECT 子句中使用列别名重命名视图字段
如果希望向调用方隐藏底层物理字段名称，或者对外提供更具业务表意性的字段名，可以在内部查询中指定别名：

```sql
CREATE VIEW vu_emp2 
AS 
SELECT employee_id, last_name AS l_name, salary 
FROM emps 
WHERE salary > 8000;
```
执行后查询该视图，返回结果的列名自动变成了 `employee_id`、`l_name`、`salary`，且仅包含薪水大于 8000 的员工记录。

> **结论**：**视图内部 SELECT 子句中声明的字段别名，将直接升格为该视图对外暴露的正式列名称。**

##### 范式 C：在视图名称后通过小括号显式声明列别名列表
除了在查询语句内零散起别名，MySQL 还支持一种集中化、全局感更强的声明方式——直接在视图名称后加括号指定所有列名：

```sql
CREATE VIEW vu_emp3 (emp_id, name, monthly_salary)
AS 
SELECT employee_id, last_name, salary 
FROM emps 
WHERE salary > 8000;
```

> **易错点**：使用小括号集中定义视图列名时，**括号内的字段别名数量必须与下方 SELECT 查询投影出的列数量严格相等**，且位置一一对应。若上方写了 3 个别名而下方 `SELECT` 查了 4 列，SQL 解析器会立即报错中断。

#### 单表视图的底层投影形态：实体字段与虚拟计算字段

在单表视图中，我们需要清晰辨析两种完全不同的字段来源形态：

| 字段形态分类 | 典型特征 | 示例代码与语法 | 底层物理事实 |
| :--- | :--- | :--- | :--- |
| **情况一：实体字段直接映射** | 视图列与基表中的某个物理列存在一一对应的真实血缘关系 | `SELECT employee_id, last_name FROM emps` | 数据真实保存在基表磁盘行中，具备更新的可映射性 |
| **情况二：虚拟计算/聚合字段** | 视图列由函数、算术表达式或聚合统计动态计算生成 | `SELECT department_id, AVG(salary) avg_sal FROM emps GROUP BY department_id` | **基表中根本不存在对应的物理列**，数据由内存临时运算得出 |

我们来看一个实际的聚合计算视图案例：
```sql
CREATE VIEW vu_emp_sal 
AS 
SELECT department_id, AVG(salary) avg_sal 
FROM emps 
WHERE department_id IS NOT NULL 
GROUP BY department_id;
```
查询 `SELECT * FROM vu_emp_sal;`，系统输出了 11 个部门的平均工资。

必须要深刻理解：虽然在视图里可以像查普通列一样查 `avg_sal`，但基表 `emps` 中绝对没有一个叫做 `avg_sal` 的物理字段。这个数据完全是当你在调用视图时，数据库优化器实时通过 `AVG()` 聚合函数临时计算出来的。**这个本质特征，直接决定了该视图无法支持反向的 `UPDATE` 或 `INSERT` 操作**，因为系统根本找不到物理落盘的目标列。

#### 场景二：基于多表关联构建视图与业务数据格式化

在复杂业务场景中，多表 `JOIN` 往往涉及多层外键匹配与繁复的连接条件。将多表连接封装在视图内，能够极大地减轻业务开发人员的心智负担。

##### 跨表连接视图的封装
```sql
CREATE VIEW vu_emp_dept 
AS 
SELECT e.employee_id, e.department_id, d.department_name 
FROM emps e 
JOIN depts d 
ON e.department_id = d.department_id;
```
在建立视图时，由于两个表均存在 `department_id`，必须在查询语句中显式使用表别名限定（如 `e.department_id`），避免字段二义性错误。

一旦视图创建成功，后续需要获取员工及其归属部门信息时，再也无需手写 `JOIN ... ON ...`，直接将视图当作单表操作即可：
```sql
SELECT * FROM vu_emp_dept;
```

##### 数据展示格式化封装
在很多报表展示或前端需求中，经常需要将多个字段按照特定格式拼接在一起（例如“员工名(部门名)”）。我们可以利用字符串函数直接在视图层面完成格式化组装：

```sql
CREATE VIEW vu_emp_info 
AS 
SELECT CONCAT(e.last_name, '(', d.department_name, ')') AS emp_info 
FROM emps e 
JOIN depts d 
ON e.department_id = d.department_id;
```
查询 `SELECT * FROM vu_emp_info;`，直接输出如 `King(Executive)` 格式的数据行，把复杂的排版逻辑固化在数据层。

#### 场景三：基于现有视图派生新视图（嵌套视图）

既然视图在外部查询视角下表现得与普通二维表完全无异，那么一个很自然的技术延伸是：**能否基于一个已经存在的视图，再次创建新的视图？**

答案是完全可以。这被称为视图的嵌套（Nested View）。

```sql
-- 基于已有的 vu_emp1 视图，进一步过滤投影创建 vu_emp4
CREATE VIEW vu_emp4 
AS 
SELECT employee_id, last_name 
FROM vu_emp1;
```

```text
[ 底层基表 emps ] 
        ^
        | (定义查询)
[ 视图 vu_emp1 ] : 包含 employee_id, last_name, salary
        ^
        | (二次过滤)
[ 视图 vu_emp4 ] : 仅暴露 employee_id, last_name
```
> 图 2：多层视图的级联嵌套依赖链路。

执行 `SELECT * FROM vu_emp4;`，数据顺畅呈现。但需要注意的是，在企业架构设计中，**不建议进行过深层次的视图嵌套**（通常不超过 2 到 3 层）。多层嵌套如同洋葱一样，层层包装会使得底层的性能执行计划变得难以预测，后期的排查与调优链路也会变得极其冗长。

### 视图元数据查看的四维机制

视图创建完毕后，我们如何探查当前库中有哪些视图？如何查看其字段结构与底层 DDL 定义？MySQL 提供了四种从粗粒度到细粒度的查看机制。

#### 机制一：探查库内所有表与视图对象（SHOW TABLES）

在终端或客户端中执行：
```sql
SHOW TABLES;
```

> **易错点**：很多同学直觉上认为，既然查表是 `SHOW TABLES`，那查视图是不是应该有一个 `SHOW VIEWS` 命令？**MySQL 中根本不存在 `SHOW VIEWS` 这条命令！**
> 当我们执行 `SHOW TABLES;` 时，控制台返回的结果集列表中，不仅包含了真实的物理基表（如 `emps`、`depts`），同时**完整罗列了当前数据库下的所有视图对象**（如 `vu_emp1`、`vu_emp_dept` 等）。在系统字典初级概览中，物理表与虚拟视图是平级混排展示的。

#### 机制二：查看视图的表结构字段元数据（DESC）

查看视图所包含的列名、数据类型以及是否允许为 NULL，其用法与普通数据表完全一致：

```sql
DESC vu_emp1;
-- 或者使用完整拼写
DESCRIBE vu_emp1;
```
控制台会以标准的表格形式输出 `Field`、`Type`、`Null`、`Key`、`Default`、`Extra` 等属性列。从结构外观上看，它与一张普通的物理表没有任何差别。

#### 机制三：查看视图的状态属性与存储本质（SHOW TABLE STATUS）

如果想要从底层区分某张表究竟是“物理表”还是“虚拟视图”，可以使用状态探查指令：

```sql
SHOW TABLE STATUS LIKE 'vu_emp1';
```

在命令行（CMD / Terminal）中，单行展示由于字段极多容易导致字符折行错乱，强烈建议使用 `\G` 替代分号结束，实现行列转置的垂直输出：

```sql
SHOW TABLE STATUS LIKE 'vu_emp1'\G
```

执行后的输出细节呈现出非常震撼的技术证据：
```text

         Engine: NULL
        Version: NULL
     Row_format: NULL
           Rows: NULL
 Avg_row_length: NULL
    Data_length: NULL
Max_data_length: NULL

      Data_free: NULL
```

> **结论**：仔细观察上述状态属性：
> 1. `Engine`、`Rows`（行数）、`Data_length`（数据空间占用）、`Index_length`（索引开销）**全部为 NULL**！
> 2. `Comment`（备注）列明确被系统标记为 **`VIEW`**。
>

#### 机制四：查看视图的完整创建 DDL 定义（SHOW CREATE VIEW）

如果需要逆向审计某个视图底层的完整构造 SQL，使用：

```sql
SHOW CREATE VIEW vu_emp1\G
```

系统会完整返回创建该视图时的全量原生 DDL 语句：
```sql

    DEFINER=`root`@`localhost` 
    SQL SECURITY DEFINER 
    VIEW `vu_emp1` AS 
    select `emps`.`employee_id` AS `employee_id`,
           `emps`.`last_name` AS `last_name`,
           `emps`.`salary` AS `salary` 
    from `emps`
```

通过这一命令，我们可以清晰看到 MySQL 优化器在幕后为我们补充的各项默认参数：
- 自动补充了默认算法 `ALGORITHM = UNDEFINED`；
- 明确绑定了安全执行上下文与定义者账号（`DEFINER` 与 `SQL SECURITY`）；
- 将原有的简写 `SELECT` 规范化为带有反引号与完全限定列名的标准化查询语法。

## 76-更新视图数据与视图的删除
> 对应分集：P76 | 原始标题：《76-更新视图数据与视图的删除》

在前面两讲中，我们完成了视图从概念认知到语法实操的跨越。我们知道了视图是“存储起来的 `SELECT` 语句”，并且掌握了单表投影、多表关联以及基于已有视图构建嵌套视图的方法。但在日常开发和数据库维护中，关于视图最容易引发争议和混淆的核心问题才刚刚浮出水面：

**既然视图在外观上表现为一张二维表，那么我们能否像操作普通数据表一样，对视图执行 `INSERT`、`UPDATE` 和 `DELETE` 呢？**
如果可以，它对底层物理基表究竟会产生怎样的连锁反应？如果不行，为什么有些视图可以更新，而有些视图一执行修改就会立即报错？当业务发生变迁时，我们又该如何对视图进行平滑升级与安全删除？

本讲将从视图的 DML 更新联动机制切入，深入拆解视图“可更新（Updatable）”与“不可更新”的底层边界条件，系统讲解视图修改与删除的操作规范，并在全章收官之际，对视图在现代软件架构中的技术价值与潜在代价进行全景审视。

### 视图的 DML 数据更新与基表联动机制

在数据库领域，当我们谈论“更新视图中的数据”时，这里的“更新”是一个广义概念，涵盖了所有的 DML（数据操作语言）行为，即增（`INSERT`）、删（`DELETE`）、改（`UPDATE`）。

我们在前一讲准备的 `dbtest14` 库中，以基于单表构建的员工视图 `vu_emp1` 为例展开验证。

#### 视图 UPDATE 操作与基表数据的穿透同步

首先检视 `vu_emp1` 视图及其物理基表 `emps` 中编号为 101 的员工（Kochhar）当前的数据状态：

```sql
-- 查看视图当前记录
SELECT employee_id, last_name, salary FROM vu_emp1 WHERE employee_id = 101;

-- 查看底层物理基表对应记录
SELECT employee_id, last_name, salary FROM emps WHERE employee_id = 101;
```
此时两处输出的薪资（`salary`）完全一致，均为 17000.00。

现在，我们通过视图将 101 号员工的薪水变更为 20000：

```sql
UPDATE vu_emp1 
SET salary = 20000 
WHERE employee_id = 101;
```

执行完毕后，我们立刻检查物理基表 `emps`：
```sql
SELECT employee_id, last_name, salary FROM emps WHERE employee_id = 101;
```
查询结果显示，基表 `emps` 中 101 号员工的薪水赫然变为了 20000.00！

反过来，如果我们绕过视图，直接在基表 `emps` 上将该员工的薪水调整为 10000：
```sql
UPDATE emps 
SET salary = 10000 
WHERE employee_id = 101;
```
再次查询视图 `SELECT salary FROM vu_emp1 WHERE employee_id = 101;`，视图中的数据同样实时同步变为 10000.00。

```text
[ 客户端修改视图 ] ---> UPDATE vu_emp1 SET salary = 20000
                             |
                             v (底层穿透)
[ 物理基表 emps ]  ---> salary 物理磁盘页实时变更为 20000
                             ^
                             | (反向查询映射)
[ 客户端查询基表 ] <--- 读出最新值 20000
```
> 图 1：视图 DML 变更与物理基表的底层穿透映射逻辑。

> **结论**：**对简单单表视图执行 UPDATE 操作，会导致底层物理基表对应记录的实质性修改；反之，修改基表数据也会实时反映在视图的查询结果中。**
> 这种联动之所以发生，根本原因在于系统内从始至终只有物理基表这一份真实数据。修改视图，本质上就是借助视图的定义穿透到底层基表进行物理落盘。

#### 视图 DELETE 操作的物理影响

同样地，如果针对视图执行物理删除操作：

```sql
DELETE FROM vu_emp1 WHERE employee_id = 101;
```

执行后统计总记录数：
```sql
SELECT COUNT(*) FROM vu_emp1; -- 结果从 107 降为 106
SELECT COUNT(*) FROM emps;    -- 结果同样从 107 降为 106
```
去基表中查询 `WHERE employee_id = 101`，该行记录已彻底不复存在。

> **注意**：从视图中执行 `DELETE` 会导致底层物理基表中的实体行被直接永久删除。如果该基表上挂载了外键约束且存在从表关联，删除操作还会受到外键引用完整性的约束拦截。

### 视图不可更新（Not Updatable）的底层边界与判定法则

很多开发者在此处容易产生一种误解：“既然视图能改能删，那它不就和物理表一模一样吗？”

事实绝非如此。能够顺畅执行增删改的，通常仅仅是字段一一对应的简单单表视图。在绝大多数包含复杂计算与转换的业务视图中，执行 DML 操作会直接被系统硬性拦截。

#### 聚合计算视图更新失败的现场还原

回顾前一讲我们创建的部门平均薪资视图 `vu_emp_sal`：
```sql
CREATE VIEW vu_emp_sal 
AS 
SELECT department_id, AVG(salary) AS avg_sal 
FROM emps 
WHERE department_id IS NOT NULL 
GROUP BY department_id;
```

此时我们尝试通过该视图，将 30 号部门的平均薪资调整为 5000：
```sql
UPDATE vu_emp_sal 
SET avg_sal = 5000 
WHERE department_id = 30;
```

SQL 解析器会立刻无情抛出错误：
```text
Error Code: 1288. The target table vu_emp_sal of the UPDATE is not updatable
```
同样，若尝试执行 `DELETE FROM vu_emp_sal WHERE department_id = 30;`，系统同样报出 `1288 ... is not updatable` 错误。

#### 为什么不可更新？数学与逻辑上的不可逆性

为什么数据库不允许更新这个视图？我们从数据底层逻辑推演一下：
- 视图中的 `avg_sal` 字段在基表 `emps` 中**根本没有对应的物理列**；
- 30 号部门在基表中可能对应着 6 名不同薪资的员工，这 6 个人的薪资经过 `AVG()` 运算后聚合成了一个单一数值；
- 如果允许你将平均薪资直接改成 5000，数据库底层的存储引擎该如何去调整这 6 名员工各自的具体薪资，才能恰好让算出来的平均值等于 5000？是有的人加 200、有的人减 300？还是全员均摊？

> **结论**：数据库引擎不是具有主观意识的业务仲裁者，它无法处理这种“一对多”且存在无穷多解的反向拆解。**当视图的一行数据无法在逻辑上可逆、唯一地映射回基表的具体物理行与物理列时，该视图必定不可更新！**

同理，若我们在视图中定义了一个员工年薪计算字段 `salary * 12 * (1 + IFNULL(commission_pct, 0))`，由于它混合了基本薪水与提成率两个物理变量，直接去 `UPDATE` 视图中的年薪，引擎同样无法得知究竟该修改 `salary` 还是修改 `commission_pct`，因此同样不可更新。

#### 视图不可更新的典型场景归纳

只要视图的查询定义中包含以下任何一种语法特性，该视图就自动失去可更新性：

| 不可更新的语法特征 | 典型关键字 / 构造 | 拦截原因深度剖析 |
| :--- | :--- | :--- |
| **聚合与分组函数** | `SUM()`, `AVG()`, `COUNT()`, `MAX()`, `MIN()` 等 | 多行数据折叠为一行标量，反向拆解无确定解 |
| **去重操作** | `DISTINCT` | 重复记录被合并展现，无法确定修改定位到具体哪一行 |
| **分组与过滤条件** | `GROUP BY`, `HAVING` | 数据已经过聚合桶分类，无法穿透至原始行记录 |
| **结果集合并** | `UNION`, `UNION ALL` | 结果来自于多段独立数据流的叠加，映射归属模糊 |
| **关联连接复杂性** | 复杂的跨表 `JOIN`（尤其是包含非键保留表的更新） | 容易破坏跨表引用的完整性与唯一性 |
| **计算衍生列** | 数学表达式、字符串拼接函数 `CONCAT` 等 | 物理基表中无对应实体字段进行数据落盘 |
| **常量与不可更新视图派生** | `SELECT '常量' AS col` 或上层依赖不可更新视图 | 根源上缺乏物理可写的数据靶点 |

> **提示**：**工程实战的根本准则**
> 视图从诞生之初，其核心使命就是**服务于高效查询与安全隔离**（存储起来的 `SELECT` 语句）。
> 虽然在满足严苛条件时语法上支持增删改，但**在实际工程架构中，强烈不建议通过视图进行任何 DML 写入操作**！所有涉及业务实体的增删改，均应直接、显式地针对底层物理基表进行，确保事务与约束链条的清晰透明。

### 视图的定义修改与生命周期管理

随着系统版本的迭代，基表结构的调整往往要求上层视图同步发生形态重塑。

#### 视图修改的两种标准范式

当我们需要为现有视图增删字段或调整过滤策略时，有两种标准的 DDL 语法。

##### 方式一：CREATE OR REPLACE VIEW（原子覆盖范式）
如果视图不存在则直接创建；如果视图已存在，则用新的 `SELECT` 定义原子性覆盖现有定义：

```sql
CREATE OR REPLACE VIEW vu_emp1 
AS 
SELECT employee_id, last_name, salary, email 
FROM emps 
WHERE salary > 7000;
```
通过 `DESC vu_emp1;` 检视，字段列表中成功扩充了 `email` 列，且原有的数据过滤范围也平滑更新。

##### 方式二：ALTER VIEW（直接变更范式）
与数据表结构的 `ALTER TABLE` 保持风格一致，直接针对已存在的视图结构进行重定义：

```sql
ALTER VIEW vu_emp1 
AS 
SELECT employee_id, last_name, salary, email, hire_date 
FROM emps;
```
执行后通过 `DESC vu_emp1;` 可以确认新增的入职日期 `hire_date` 已经就位。

#### 视图的物理删除与级联失效深坑

##### 删除语法与防错机制
删除视图使用 `DROP VIEW` 语法，支持同时批量删除多个视图：

```sql
-- 基础删除
DROP VIEW vu_emp4;

-- 批量删除
DROP VIEW vu_emp2, vu_emp3;

-- 规范写法：携带 IF EXISTS 防止异常抛出
DROP VIEW IF EXISTS vu_emp4;
```
若未加 `IF EXISTS` 而尝试删除一个不存在的视图，系统会抛出明确的 `Error 1051: Unknown table ...` 错误。

##### 关键陷阱：嵌套视图的上游断裂灾难
在上一讲中我们提到，可以基于已有视图创建新视图（例如基于 `view_A` 创建 `view_B`）：

```text
[ 底层基表 ] <--- [ 视图 A ] <--- [ 视图 B ]
                      |
              执行 DROP VIEW view_A
                      |
                      v
[ 底层基表 ]       (被抹除)       [ 视图 B (彻底报废) ]
```
> 图 2：上游中间视图删除后引发的下游依赖断裂示意图。

如果我们执行 `DROP VIEW view_A;` 成功删除了中间层视图，此时视图 B 会发生什么？
千万不要幻想“中间商没有了，视图 B 会自动绕过视图 A 直接对接底层基表”。

> **易错点**：**视图 B 本质上保存的是 `SELECT ... FROM view_A`。一旦视图 A 被物理抹除，视图 B 的底层依赖对象便凭空蒸发！**
> 此时只要外部尝试查询 `SELECT * FROM view_B;`，数据库会立刻崩溃报错：`View 'view_B' references invalid table(s) or column(s) or function(s)`。
> 此时视图 B 已彻底沦为无法访问的“僵尸视图”，必须人工手动修改（`ALTER VIEW`）其查询源头，或者将其一同删除。

### 视图架构全景总结：核心优势与潜在代价

作为数据抽象层的重要工具，视图在架构设计中具有鲜明的两面性。系统架构师必须在“便利性”与“维护性”之间做出精准权衡。

#### 视图的核心赋能价值

```text
+-------------------------------------------------------------------+
|                        视图的核心架构价值                         |
+-------------------------------------------------------------------+
| 1. 操作降维化 : 封装数十行多表 JOIN，对外暴露如单表般极简查询     |
| 2. 空间零冗余 : 纯逻辑投影，杜绝物理拷贝导致的存储膨胀与数据脱节  |
| 3. 安全沙箱化 : 针对不同角色建立列级脱敏与行级过滤视图，隔离大表  |
| 4. 架构解耦化 : 基表物理微调时，通过调整视图抹平差异，稳定前端接口|
| 5. 逻辑模块化 : 将多阶段的复杂统计逻辑拆分为视图梯队，化繁为简    |
+-------------------------------------------------------------------+
```
> 图 3：视图在企业级数据架构中的五大核心赋能维度。

1. **简化复杂查询**：将涉及 5 张大表、多重嵌套子查询与复杂连接条件的逻辑固化在视图中，业务开发人员只需针对视图执行 `SELECT ... WHERE ...`，开发效率与 SQL 可读性成倍提升。
2. **零数据冗余**：相较于拷贝物理子表，视图不占存储，且天然保证与物理基表的数据强一致性。
3. **构筑安全防线**：在复杂的企业组织架构中，不同部门、不同层级的运维人员只能通过其授权的特定视图读取脱敏数据，绝无权限直接接触核心物理表。
4. **适应多变业务**：当基表字段拆分或命名重构时，可以在物理表之上重新加盖一层与老版本字段兼容的视图，外部业务系统完全无需改动任何代码，平滑渡过重构期。
5. **拆解复杂逻辑**：多层业务报表可以分段封装为中间视图，实现查询逻辑的模块化解耦。

#### 视图的潜在代价与选型准则

- **维护成本的高昂性**：视图与基表之间存在高度的隐式强耦合。如果基表删除了某个字段或变更了字段数据类型，所有依赖该字段的视图在被查询时才会暴露出致命异常。一旦系统内存在三四层以上的嵌套视图网状结构，链路排查与维护成本将呈现指数级恶化。
- **性能评估的盲区**：如果调用方把一个底层封装了多表关联与笛卡尔积的复杂视图误当成轻量级单表来频繁调用，极易产生严重的慢查询风暴。

> **工程选型准则**：
> - **小型项目与轻量应用**：表少、关系简单，**坚决不推荐滥用视图**，直接在应用层编写清晰的原生 SQL 即可；
> - **大型企业系统与数据中台**：在涉及跨部门权限隔离、核心敏感数据脱敏、以及跨多系统报表共享的关键技术节点，适度、规范地引入单层或浅层视图，以最小的维护代价换取极高的安全与开发红利。

### 基础视图构建与结构变更练习

在企业规范中，为了兼顾不同前端应用、对外接口或历史系统的调用习惯，我们经常需要对基表的某些敏感字段进行过滤，并对输出字段重新命名。本节我们基于测试数据库 `dbtest14` 中的员工数据表 `emps`，演练单表基础视图的定义、重命名及条件过滤改造。

#### 创建重命名字段的基础视图

我们需要基于员工表 `emps` 创建一个名为 `employee_view` 的视图，包含员工姓氏（`last_name`）、员工工号（`employee_id`）以及部门编号（`department_id`），同时要求将这三个字段在视图中分别呈现为 `r_name`、`emp_id` 与 `dept_id`。

在命名规范上，行业中常见的视图命名有两种风格：一种是以前缀 `vu_` 或 `view_` 开头（如 `vu_emp`），另一种是以 `_view` 或 `_vu` 结尾（如 `employee_view`），这与数据表完整性约束的命名习惯类似，团队内部保持统一即可。为了防止脚本重复执行时报“对象已存在”的错误，推荐使用 `CREATE OR REPLACE VIEW` 语法。

定义字段别名有两种标准写法：
1. 直接在 `CREATE VIEW 视图名(列名1, 列名2...)` 括号中显式指明；
2. 在 `SELECT` 查询投影列表中使用 `AS` 赋予列别名。

这里我们采用在投影列表中直接赋予别名的方式，SQL 实现如下：

```sql
USE dbtest14;

-- 创建或替换员工基础视图
CREATE OR REPLACE VIEW employee_view
AS
SELECT 
    last_name AS r_name,
    employee_id AS emp_id,
    department_id AS dept_id
FROM emps;
```

> **提示**：若采用第一种方式，语句写作 `CREATE OR REPLACE VIEW employee_view(r_name, emp_id, dept_id) AS SELECT last_name, employee_id, department_id FROM emps;`。两种方式在 MySQL 底层解析出的数据字典元数据完全等价。

#### 查看视图结构与检索视图数据

视图创建成功后，MySQL 会在元数据中记录该视图的列定义。我们可以像操作普通物理表一样，使用 `DESCRIBE` 或其缩写 `DESC` 来查看视图的结构定义：

```sql
-- 查看视图表结构
DESC employee_view;
```

执行后输出的列信息如下：
- `r_name`：对应基表的 `last_name`，字符类型与长度继承自基表字段定义；
- `emp_id`：对应基表的 `employee_id`；
- `dept_id`：对应基表的 `department_id`。

这说明外部调用者在面对该视图时，只能看到重命名后的逻辑列，基表真实列名被有效隐藏。接下来查询视图的全部内容：

```sql
-- 查询视图全部数据
SELECT * FROM employee_view;
```

在执行结果中，总记录数为 106 条（标准 HR 样例库包含 107 条，此处少一条是因为在先前的 DML 练习中删除了工号为 101 的员工）。这直观展示了视图的实时性：**视图本身不存储任何行数据，每次对视图的查询都会动态转换为对底层物理基表的查询**。

#### 视图过滤范围变更

现业务需求发生变动，要求将视图 `employee_view` 暴露的数据范围严格限定在部门号为 80（销售部）的员工之内。

针对已经存在的视图，修改其查询逻辑通常有两种途径：
- 途径一：使用 `ALTER VIEW 视图名 AS SELECT ...`；
- 途径二：使用 `CREATE OR REPLACE VIEW 视图名 AS SELECT ...`。

在实际编写部署脚本时，使用 `CREATE OR REPLACE VIEW` 的兼容性更好，因为无论该对象先前是否存在，语句都能幂等执行成功。修改语句如下：

```sql
-- 将视图数据范围限定为80号部门
CREATE OR REPLACE VIEW employee_view
AS
SELECT 
    last_name AS r_name,
    employee_id AS emp_id,
    department_id AS dept_id
FROM emps
WHERE department_id = 80;
```

再次执行 `SELECT * FROM employee_view;`，返回的记录将严格限制为部门号等于 80 的员工数据集。基表中非 80 号部门的员工数据对于持有该视图权限的用户完全不可见，实现了行级别的权限隔离与数据脱敏。

### 视图 DML 更新边界与约束冲突深度探究

许多初学者容易产生一个认知误区，认为“只要视图是一对一映射的单表视图，就必然可以随意执行 INSERT、UPDATE 和 DELETE”。本节我们通过一系列具有真实代表性的测试用例，揭示物理基表的约束条件是如何反向制约视图操作的。

#### 基于模糊匹配构建初始视图

首先创建视图 `emp_v1`，要求筛选出电话号码以 `011` 开头的员工姓名（`last_name`）、薪资（`salary`）和电子邮箱（`email`）。

对于“以 011 开头”的文本匹配，在 SQL 中最标准且走索引友好的写法是利用 `LIKE` 关键字配合通配符 `%`，即 `phone_number LIKE '011%'`（部分场景也可使用正则表达式 `REGEXP '^011'`，但在标准过滤中 `LIKE` 足够高效）。

```sql
-- 创建电话号码以 011 开头的员工视图
CREATE OR REPLACE VIEW emp_v1
AS
SELECT 
    last_name,
    salary,
    email
FROM emps
WHERE phone_number LIKE '011%';
```

执行后，可通过 `SELECT * FROM emp_v1;` 验证查询逻辑，确认筛选出的记录均符合 `011%` 前缀规则。

随后业务提出变更：要求将 `emp_v1` 修改为“电话号码以 011 开头且邮箱中包含字符 e”的员工，投影列调整为姓名（`last_name`）、邮箱（`email`）和电话号码（`phone_number`），暂时移除了 `salary` 列。

```sql
-- 修改视图定义：调整投影字段并增加邮箱包含 'e' 的过滤条件
CREATE OR REPLACE VIEW emp_v1
AS
SELECT 
    last_name,
    email,
    phone_number
FROM emps
WHERE phone_number LIKE '011%'
  AND email LIKE '%e%';
```

执行变更后，视图 `emp_v1` 此时仅对外暴露 `last_name`、`email` 和 `phone_number` 三个字段。

#### 单表简单视图 INSERT 失败机理剖析

现在我们尝试向刚刚修改后的视图 `emp_v1` 中插入一条全新记录：
- 姓名：`'Tom'`
- 邮箱：`'Tom@126.com'`
- 电话：`'010-12345'`

执行插入语句：

```sql
INSERT INTO emp_v1(last_name, email, phone_number)
VALUES ('Tom', 'Tom@126.com', '010-12345');
```

执行该语句后，MySQL 并没有成功插入数据，而是直接抛出严重错误：
```text
Error Code: 1364. Field 'hire_date' doesn't have a default value
```

为什么一个结构如此简单的单表视图，甚至没有使用任何聚合函数和分组，却无法执行数据插入？

我们来追溯底层的数据写入机理。向视图插入数据，在物理本质上必须由存储引擎将这行数据落盘到基表 `emps` 中。我们通过 `DESC emps;` 仔细审视底层基表的元数据约束：

```text
+--------------+-------------+------+-----+---------+-------+
| Field        | Type        | Null | Key | Default | Extra |
+--------------+-------------+------+-----+---------+-------+
| employee_id  | int         | NO   | PRI | NULL    |       |
| first_name   | varchar(20) | YES  |     | NULL    |       |
| last_name    | varchar(25) | NO   |     | NULL    |       |
| email        | varchar(25) | NO   | UNI | NULL    |       |
| phone_number | varchar(20) | YES  |     | NULL    |       |
| hire_date    | date        | NO   |     | NULL    |       |
| job_id       | varchar(10) | NO   |     | NULL    |       |
| salary       | double(8,2) | YES  |     | NULL    |       |
| ...          | ...         | ...  | ... | ...     | ...   |
+--------------+-------------+------+-----+---------+-------+
```

```text
向视图插入数据时的列映射与约束检验机制：

 [客户端 INSERT 请求] 
       │
       ▼
 [视图 emp_v1 提供的字段] ───► last_name     email     phone_number
                                   │           │            │
                                   ▼           ▼            ▼
 [基表 emps 物理字段]      ───► last_name     email     phone_number   hire_date   job_id ...
                                [有值]       [有值]       [有值]        [未提供]    [未提供]
                                                                          │           │
                                                                          ▼           ▼
                                                                     NOT NULL    NOT NULL
                                                                    (无 DEFAULT)(无 DEFAULT)
                                                                          │           │
                                                                          └─────┬─────┘
                                                                                ▼
                                                                     [抛出 1364 异常，拒绝写入]
```

分析上述映射关系可知：
1. 客户端通过视图只提交了 `last_name`、`email` 和 `phone_number` 三个列的值；
2. 对于基表 `emps` 中的其他未投影列（如 `hire_date`、`job_id`），MySQL 尝试使用其列默认值填充；
3. 但在基表定义中，`hire_date` 与 `job_id` 被显式标记为 `NOT NULL`，且**没有配置任何默认值（Default is NULL）**；
4. 这导致物理行在写入时违反了关系数据库的非空完整性约束，整个事务立即回滚并报错。

> **结论**：要使一个视图具备可插入性（Insertable），除了视图本身必须满足简单视图规范外，**基表中所有未出现在视图中的字段，必须允许为 NULL，或者具备明确的 DEFAULT 默认值**。否则，该视图在业务上天然只读不可插入。

#### 视图字段缺失下的 UPDATE 修复与基表联动

接下来考虑业务要求：将视图 `emp_v1` 中所有员工的薪资上调 1000 元。

若我们直接针对当前视图执行如下更新：
```sql
UPDATE emp_v1 SET salary = salary + 1000;
```
MySQL 会立即报错：`Unknown column 'salary' in 'field list'`。这是因为在 2.1 节最后的修改中，我们将 `salary` 从投影列中剔除了。视图作为虚拟表，外部只能操作其元数据中已暴露的字段。

要实现调薪，必须先扩展视图定义，将 `salary` 字段重新加入投影：

```sql
-- 重新修改视图，纳入 salary 字段
CREATE OR REPLACE VIEW emp_v1
AS
SELECT 
    last_name,
    email,
    phone_number,
    salary
FROM emps
WHERE phone_number LIKE '011%'
  AND email LIKE '%e%';
```

视图更新后，再次执行薪资递增更新：

```sql
-- 执行批量调薪
UPDATE emp_v1 
SET salary = salary + 1000;
```

执行后，语句顺利受影响。此时通过 `SELECT * FROM emp_v1;` 观察，视图中符合条件的员工工资均增加了 1000 元。更关键的是，我们直接查询底层物理表 `SELECT employee_id, last_name, salary FROM emps WHERE phone_number LIKE '011%' AND email LIKE '%e%';`，会发现物理基表中的对应行薪资同样被增加了 1000 元。

> **提示**：通过视图执行的 `UPDATE` 操作会直接穿透并作用于底层物理基表。对视图数据的修改，实质上就是对基表数据的直接修改。

#### 基于视图的 DELETE 操作与外键引用约束

针对视图执行删除操作，考察删除特定员工记录的场景：

```sql
-- 从视图中删除特定员工
DELETE FROM emp_v1 
WHERE last_name = 'Olsen';
```

执行该删除语句后，记录被成功清除。检验视图及底层基表 `emps`，该员工均已不复存在。

> **注意**：从视图中执行 `DELETE` 能够成功的先决条件是：该操作在底层基表上同样被允许。若底层基表存在外键级联限制（如其他业务表的外键正在引用该员工的 `employee_id`，且外键约束策略为 `RESTRICT` 或 `NO ACTION`），则删除操作会由于外键引用完整性冲突而被数据库引擎拒绝。

### 聚合视图的创建与更新不可逆性

在日常数据分析和报表展示中，包含 `GROUP BY`、`HAVING` 和聚合函数的“多对一”视图极其常见。这一类视图具备鲜明的不可更新特征。

#### 聚合过滤视图的创建与别名规范

现要求统计各个部门的最高工资，并过滤出最高工资高于 12000 的部门编号（`department_id`）及其最高工资。基于此需求构建视图 `emp_v2`。

这里涉及分组（`GROUP BY department_id`）与分组后过滤（`HAVING MAX(salary) > 12000`）。在为含有聚合函数或表达式的查询创建视图时，**必须为该表达式指定合法的列别名**。视图是一个命名的关系模式，关系模型中的每一列都必须拥有明确的字段名称，不能直接把 `MAX(salary)` 这种函数表达式作为列标识符。

```sql
-- 创建各部门最高薪资聚合视图
CREATE OR REPLACE VIEW emp_v2
AS
SELECT 
    department_id,
    MAX(salary) AS max_sal
FROM emps
GROUP BY department_id
HAVING MAX(salary) > 12000;
```

创建成功后，查询该视图：

```sql
SELECT * FROM emp_v2;
```

查询结果仅返回满足最高薪资大于 12000 的三条部门汇总记录。

#### 聚合视图执行 INSERT 的逻辑荒谬性剖析

假设我们尝试向视图 `emp_v2` 中插入一条新的“部门最高工资”记录：
- 部门编号：`4000`（虚拟部门编号）
- 最高工资：`20000.00`

```sql
-- 尝试向聚合视图插入数据
INSERT INTO emp_v2(department_id, max_sal)
VALUES (4000, 20000);
```

执行后，MySQL 明确拒绝并抛出异常：
```text
Error Code: 1471. The target table emp_v2 of the INSERT is not insertable-into
```

系统提示该目标表“不可插入”。我们可以从**物理存储机制**与**逻辑反证法**两个维度来理解为什么这一限制是不可逾越的：

```text
聚合视图与基表的数据映射断裂：

 [视图虚拟记录]         department_id: 4000  │  max_sal: 20000 (计算得出的聚合值)
                               ▲                         ▲
                               │                         │
 ────── 试图向下写入物理基表时发生逻辑断裂 ──────────────────────────────────────────
                               │                         │
 [物理基表行 1]        department_id: 4000  │  salary: ? (填 20000 还是其他值？)
 [物理基表行 2]        department_id: 4000  │  salary: ? (该部门应有几个员工？)
 [物理基表行 ...]       ...                  │  谁才是这个“最高”工资的获得者？
```

1. **反证法分析**：假定此 `INSERT` 允许成功执行，那么对应到底层基表 `emps`，引擎必须插入实际的员工数据行。但是，基表中根本不存在名为 `max_sal` 的物理字段，只有每个具体员工的 `salary`。引擎该为这个 4000 号部门创建几个员工？每个员工的名字、邮箱、入职时间填什么？如果只插入一个员工且工资为 20000，那这个 20000 就既是实际工资又是最高工资；若该部门已有其他员工，这个 20000 应该赋给谁才能使得聚合算出的最高工资恰好是 20000？逻辑上根本无法自洽推导。
2. **多对一的单向不可逆性**：`MAX()`、`SUM()`、`AVG()`、`COUNT()` 等聚合操作属于“有损投影”，多条原始明细行被压缩成了一条统计行，该过程在数学和逻辑上均单向不可逆。

> **结论**：凡是包含以下元素的视图，均不可执行 `INSERT`、`UPDATE` 或 `DELETE` 操作：
> - 聚合函数（`SUM`、`MIN`、`MAX`、`COUNT`、`AVG` 等）；
> - `DISTINCT` 关键字；
> - `GROUP BY` 与 `HAVING` 子句；
> - `UNION` 或 `UNION ALL` 联合查询；
> - `JOIN` 操作中的某些非键保留表关联；
> - `FROM` 子句包含不可更新视图或无法直接确定物理行映射的子查询。

### 视图对象的安全清理与状态验证

当某些临时视图或报表视图生命周期结束时，需要将其从数据库字典中清除，避免占用元数据空间或引发维护混淆。

删除视图使用 `DROP VIEW` 语句。为了保证 DDL 脚本的可重复执行性（幂等性），建议附带 `IF EXISTS` 从句。同时，MySQL 允许在一条 `DROP VIEW` 语句中通过逗号分隔指定多个视图名称，实现批量删除：

```sql
-- 批量安全删除视图
DROP VIEW IF EXISTS emp_v1, emp_v2;
```

执行后，我们可以通过 `SHOW TABLES;` 命令检验清理结果（在 MySQL 中，视图作为关系表对象同样会在 `SHOW TABLES` 的输出清单中列出）。确认 `emp_v1` 与 `emp_v2` 已被彻底移除。若再次执行上述 `DROP VIEW IF EXISTS` 语句，系统会平稳响应而不会产生报错，非常适用于自动化运维脚本与流水线初始化。

## 78-存储过程使用说明
> 对应分集：P78 | 原始标题：《78-存储过程使用说明》

在前面数据库对象模块中，我们系统学习了数据表（Table）与视图（View）。从本讲开始，我们进入 MySQL 高级特性的核心领域——存储过程（Stored Procedure）与存储函数（Stored Function）。

对于编程背景不同的开发者，初次接触存储过程时的感受往往截然不同。如果你有 C 语言、Java 或 Python 的开发经历，对函数、方法、入参、出参和代码块封装的概念绝不陌生；但如果你此前仅仅将 SQL 视作单条交互式的“数据查询与操作语言”，那么存储过程将彻底颠覆你的认知：**SQL 不仅可以被动地执行增删改查，还可以具备逻辑判断、流程控制、变量传递与模块化封装的完整编程能力**。

与此同时，存储过程也是技术社区中争议最大的一项数据库特性。阿里巴巴在《Java 开发手册》中白纸黑字明确写道：“【强制】禁止使用存储过程，存储过程难以调试和扩展，更没有移植性。”既然大厂明令禁止，为什么我们还要花大篇幅深入学习它？它在底层究竟是如何编译与驻留的？它与视图、内置函数以及存储函数之间有什么本质区别？本篇将深入剖析存储过程的技术全貌。

### 存储过程与存储函数的核心定位与概念辨析

我们在日常开发中经常统称“存储过程与函数”，严格从 MySQL 官方命名规范来看，二者分别对应**存储过程（Stored Procedure）**与**存储函数（Stored Function）**。它们均属于 MySQL 服务端的高级数据库对象，但在功能设计和返回值规范上有着清晰的界限。

#### 从内置函数到用户自定义存储逻辑

回想我们在前序章节中接触过的函数体系：
1. **单行函数**：如数学函数 `ROUND(123.45)` 输出 `123`，字符串函数 `LOWER('ABC')` 输出 `abc`，日期时间函数 `DATEDIFF(date1, date2)` 计算日期差等。
2. **聚合函数**：如 `SUM()`、`AVG()`、`MAX()`、`MIN()`、`COUNT()` 等，针对多行数据进行统计并返回单一结果。

上述函数都是 MySQL 系统底层预先内置好的（Built-in Functions），我们作为调用者，只关心其输入参数与输出结果，无需探究其 C/C++ 底层源码的实现细节。

但在复杂的业务场景下，系统预设的函数往往无法直接满足业务规则。例如：我们需要根据员工工号计算其年终综合绩效奖金，计算过程涉及税率阶梯计算、考勤系数扣减以及多张表的业务交叉运算。此时，我们可以把这段包含多条 SQL 和计算公式的业务逻辑，自主封装成一个服务端的**存储函数**。

> **定义**：**存储过程与存储函数**，本质上是用户自定义的、封装了一组复杂 SQL 逻辑并持久化保存在 MySQL 服务端的程序单元。

#### 存储过程与存储函数的本质差异

同样是封装一段 SQL 逻辑，存储过程与存储函数的关键分水岭在哪里？

最为核心的判定准则就是：**是否存在强制的单一返回值（因变量）**。

```text
存储过程与存储函数在调用接口上的核心机制对比：

 [存储函数 Stored Function]
       输入参数 (自变量 x) ───► [ 函数内部计算逻辑 ] ───► 必须通过 RETURN 返回单一值 (因变量 y)
       （在 SELECT / WHERE 表达式中直接内联调用，如 SELECT my_func(col) FROM t;）

 [存储过程 Stored Procedure]
       输入参数 (IN)      ───┐
       输出参数 (OUT)     ───┼─► [ 过程体业务逻辑 ] ───► 无 RETURN 返回值
       输入输出参数 (INOUT)──┘   (执行批量 DML/DDL)      (通过 OUT 参数传出或直接返回结果集)
       （通过专用指令独立调用，如 CALL my_proc(param);）
```

- **存储函数（Stored Function）**：完全遵循数学意义上的函数契约。自变量输入，经由内部封闭运算，**必须通过 `RETURN` 关键字返回一个且仅一个确定类型的因变量值**。正因如此，存储函数可以直接嵌入在 `SELECT` 查询列表、`WHERE` 过滤条件或 `HAVING` 子句中当作表达式使用。
- **存储过程（Stored Procedure）**：更偏向于软件工程中的“子程序（Subroutine）”或“过程化事务脚本”。**存储过程没有 `RETURN` 语句，不强制要求返回值**。它可以执行一整套复杂的业务流（如跨表批量插入、数据清洗、DDL 表重构），其结果可以通过 `OUT` 类型的形参带回给调用方，也可以在过程体内部直接发起 `SELECT` 将结果集抛给客户端。它必须通过专用的 `CALL` 命令显式触发。

#### 存储过程与视图（View）的底层逻辑分野

有学习者会产生疑问：“视图也是将一段复杂的 SQL 保存起来供后续调用，存储过程也是封装 SQL，二者难道不是重复的吗？”

二者的设计哲学与底层结构完全不同，不可混为一谈：

| 比较维度 | 视图（View） | 存储过程（Stored Procedure） |
| :--- | :--- | :--- |
| **本质定位** | 虚拟关系表（Virtual Table） | 服务端可执行程序逻辑块（Procedural Logic） |
| **封装核心** | 仅封装单一的 `SELECT` 查询语句 | 封装任意复杂的复合 SQL 逻辑（含多条增删改查） |
| **程序化特性** | 不支持局部变量、循环、分支与游标 | 全面支持变量声明、条件分支（IF/CASE）、循环、异常处理与游标 |
| **主要用途** | 数据展示、字段脱敏、行级/列级权限隔离 | 批量业务处理、定时数据维护、事务级联控制 |
| **写操作倾向** | 极不推荐做 DML，多表或聚合视图严格只读 | 天然支持大量的增、删、改、建表等物理写入操作 |

视图的灵魂在于“表”，调用者像查普通表一样查它；存储过程的灵魂在于“程序”，调用者把它当成服务端的后台任务来触发。

### 存储过程的执行架构与优缺点权衡

为什么数据库厂商要费尽心力在 RDBMS 内部植入一整套面向过程的执行引擎？存储过程在架构上有哪些不可替代的优势？又为什么会在互联网分布式时代遭遇严重的工程抵制？

#### 预编译驻留与网络开销的物理机理

在传统的应用交互模型中，应用程序（如 Java 驱动的 Web 后端）向数据库提交复杂数据处理时，通信与执行链路如下：

```text
传统单条 SQL 交互模式 vs 存储过程调用模式链路对比：

【传统交互链路】：
 应用客户端 ───[ 网络传输多条长 SQL 字符串 ]───► MySQL 接收端
                                                        │
                      ┌─────────────────────────────────┘
                      ▼
            [SQL 词法与语法解析] ───► [优化器生成执行计划] ───► [引擎逐条执行]
                      ▲                                              │
                      └─────────────(多轮往返耗时严重)────────────────┘

【存储过程交互链路】：
 编译阶段（仅一次）：
 存储过程源码 ───► [预编译优化与语法解析] ───► 编译好的二进制/中间代码驻留于服务器内存字典
 
 执行阶段（高频）：
 应用客户端 ───[ 仅发送极短指令：CALL proc_name(arg) ]───► 服务端直接命中预编译对象并执行
```

存储过程的核心技术红利主要体现在以下四个层面：
1. **网络开销极小化**：若一个业务涉及 10 条长 SQL 语句的顺序执行与中间判定，传统方式需要在网络上往返交互多次，传输大量文本报文；而采用存储过程，这 10 条逻辑已固化在服务器端，客户端只需传输一句 `CALL proc(...)`，大幅节约网络带宽与传输延迟。
2. **预先编译与执行加速**：存储过程在首次创建并被载入缓存后，其语法树与解析逻辑已被数据库解析器预先处理。省去了后续重复调用时的词法语法解析与执行树生成开销。
3. **安全性与逻辑封装**：复杂的底层表结构、敏感列名完全被封装在过程体内部，客户端无法窥探底层表结构；运维人员可以只给业务用户分配特定存储过程的 `EXECUTE` 权限，而完全收回对底层物理明细表的 `SELECT` 和 `UPDATE` 权限。
4. **统一业务逻辑防漂移**：多端应用（如 Web 端、移动 App、第三方合作网关）若采用各自的语言编写业务计算，极易产生计算规则的不一致。将核心账务逻辑固化在数据库存储过程内，能确保所有接入端统一口径。

#### 互联网架构下的工程痛点与阿里规范解析

既然存储过程具备上述优势，为什么阿里巴巴在《Java 开发手册》中严禁使用它？现代互联网软件架构为何倾向于“把数据库仅当存储，把计算前置给应用集群”？

我们需要看清存储过程的致命硬伤：
1. **极度缺乏跨数据库移植性**：各个 RDBMS 厂商的存储过程语法存在极大的“方言鸿沟”。Oracle 的 PL/SQL、SQL Server 的 T-SQL、MySQL 的 Procedural 语法、PostgreSQL 的 PL/pgSQL 语法大相径庭。一旦业务重度依赖存储过程，系统几乎不可能在不同数据库之间平滑迁移。
2. **调试与版本化异常痛苦**：现代微服务开发高度依赖强大的 IDE、断点调试与 Git 细粒度版本控制。存储过程的代码调试在各客户端工具中体验糟糕，难以打断点排查高并发下的内存状态；且存储过程的变更通常需要执行 DDL 刷新，一旦多名开发人员在线变更，极易引发版本覆盖冲突。
3. **违背分布式水平扩展原则**：这是互联网高并发架构的核心痛点。在分布式集群中，**应用服务器是无状态的，支持极低成本的水平弹性扩容（加容器、加虚机）**；而**关系型数据库服务器往往是有状态的核心瓶颈**。如果在数据库层跑大量的循环、逻辑判断与复杂运算，会导致数据库 CPU 迅速被打满，无法支撑核心的事务读写。现代互联网倡导“计算下推到 Java/Go 集群，数据库专注于 ACID 存储与高效索引扫描”。

> **结论**：在金融核心、传统 ERP、中小型企业内部系统、数据仓库 ETL 离线批处理以及特定数据清洗任务中，存储过程依然扮演着无可替代的高性能底座角色；但在高并发、高弹性、快速迭代的互联网微服务系统中，应坚决遵循业务计算前置、数据库纯粹化的工程准则。

### 存储过程参数模式分类

在定义存储过程时，其核心接口定义在参数列表（形参列表）之中。根据数据流动的方向性，形参被严格划分为五种组合模式。

```text
存储过程形参流向模型：

  [调用方环境]                           [存储过程内部空间]
       │                                         │
       ├─── IN 入参 (只读注入) ─────────────────►│
       │                                         │
       │◄── OUT 出参 (回写导出) ──────────────────┤
       │                                         │
       ├─── INOUT 双向参 (初始值注入) ────────────►│
       │                                         │ (计算修改)
       │◄── INOUT 双向参 (修改后回写) ────────────┤
```

#### 无参数过程
小括号内部完全为空（形参为空），调用时不传递任何实参。通常用于不需要动态条件、执行固定任务的批处理（如每日定时清空临时表、重构特定维度的统计数据）。

#### 纯 IN 参数过程
形参仅被修饰为 `IN`。表示该参数仅作为**纯输入参数**。
- 外部调用时必须提供具体的常量或变量值；
- 过程体内部可以读取该参数的值，但即便在过程体内对该形参进行了修改，外部调用方的原始变量绝对不会受到任何影响（值传递机制）；
- **参数默认修饰规则**：如果我们在定义形参时省略了 `IN`、`OUT` 或 `INOUT` 关键字，**MySQL 默认将其视为 `IN` 参数**。

#### 纯 OUT 参数过程
形参被修饰为 `OUT`。表示该参数作为**纯输出参数**。
- 调用该存储过程时，传入的实参必须是一个能够接收结果的变量（如用户变量 `@my_var`）；
- 过程体执行前，该参数在内部的初始值为 `NULL`（即使外部传入时变量已有初始值，也会被丢弃）；
- 过程体内部必须有逻辑（如 `INTO` 赋值）向该参数写入数据；过程执行完毕后，外部变量即可读取到这个被赋值的新数据。

#### 复合参数过程（IN 与 OUT 混用）
形参列表中既包含若干个 `IN` 参数，又包含若干个 `OUT` 参数。这是业务开发中最标准的交互模式：外部传入若干查询或过滤条件（如部门编号、日期区间），过程体内部执行计算后，将统计汇总的若干结果分别写入对应的 `OUT` 参数供外部取出。

#### 双向 INOUT 参数过程
形参被修饰为 `INOUT`。表示该参数**既作为输入、又作为输出**。
- 外部调用前必须为一个变量赋好初值并传给该形参；
- 存储过程在执行时，首先读取该变量的初始数据参与运算；
- 运算结束后，过程体内的逻辑将新计算出的值重新写入该形参；
- 过程执行完毕退出时，外部传入的变量值已被彻底覆写为新数据。

### 存储过程基础语法与特征选项剖析

掌握了参数流向后，我们来系统审视存储过程的整体 DDL 定义规范。

#### 语法骨架结构

创建存储过程的标准语法模板如下：

```sql
CREATE PROCEDURE 存储过程名([IN|OUT|INOUT 参数名 参数类型, ...])
[characteristics ...]
BEGIN
    存储过程体（由合法的 SQL 语句构成）
END
```

整个语法骨架由四大部分构成：
1. **声明头**：`CREATE PROCEDURE` 及过程名称；
2. **形参列表**：包裹在小括号内的参数声明，各参数以逗号分隔，包含参数模式、参数名称及 MySQL 合法数据类型；
3. **特征选项集合（characteristics）**：针对该过程执行特性的元数据修饰符；
4. **过程体（Body）**：由 `BEGIN ... END` 围合的复合语句块，内部书写具体的业务 SQL。

#### 特征选项（characteristics）详解

在实际编写脚本时，很多开发者会直接跳过 `characteristics` 项，使用系统默认值。但深入理解这些元数据选项，对于掌握 MySQL 优化器决策与权限沙箱机制至关重要。主要包含以下五组选项：

##### LANGUAGE SQL
指明存储过程体是由标准的 SQL 语言编写而成。
- 这是当前 MySQL 规范中的默认选项，也是目前唯一受支持的语言选项；
- 为后续可能扩展其他外部嵌入式语言保留兼容语法接口。

##### DETERMINISTIC 与 NOT DETERMINISTIC
确定性指示符，用于告知优化器该过程在相同入参下输出结果是否保持恒定。
- `DETERMINISTIC`：表示“具有确定性”。即只要传入的实参完全相同，多次执行该过程所产生的结果必然完全一致。
- `NOT DETERMINISTIC`：表示“不具确定性”。即相同的输入参数，多次调用可能产生不同的结果（例如过程体内部调用了 `UUID()`、`RAND()` 函数，或者读取了会频繁动态变更的物理表）。
- **默认机制**：若未显式指定，系统默认按 `NOT DETERMINISTIC` 策略处理。在开启二进制日志（Binary Log）主从复制的高可用环境中，某些函数或过程必须显式声明确定性特征，否则会被引擎拒绝创建。

##### SQL 行为数据特征修饰符
用于向存储引擎显式说明过程体对底层物理数据的访问行为，共包含四种互斥状态：
- `CONTAINS SQL`：表明子程序包含 SQL 语句，但**既不读取物理表，也不修改物理表**（例如纯粹进行数值数学计算或调用字符串运算）。这是系统的**默认值**；
- `NO SQL`：表明子程序内部完全不包含任何 SQL 语句；
- `READS SQL DATA`：表明子程序内部**只包含数据读取操作**（如包含 `SELECT` 语句，但不执行任何写入）；
- `MODIFIES SQL DATA`：表明子程序内部**包含数据写操作**（如包含 `INSERT`、`UPDATE`、`DELETE` 等数据修改语句）。

##### 安全上下文 SQL SECURITY
定义该存储过程在执行阶段以何种身份权限运行，提供两种安全隔离模式：
- `DEFINER`（定义者模式）：**默认模式**。指明该过程在被调用执行时，始终以**创建该过程的用户身份和权限**来运行。即使当前调用者本身没有操作底层表的权限，只要定义者具备权限且授予了调用者 `EXECUTE` 权限，调用者依然可以安全执行该过程。这是一种非常标准的权限隔离机制。
- `INVOKER`（调用者模式）：指明该过程在被执行时，严格以**当前发起调用命令的用户的权限**来运行。如果当前调用者没有底层相关物理表的直接操作权限，即便拥有过程的执行权限，过程内部在访问物理表时依然会直接抛出“权限不足（Access Denied）”异常。

##### 注释说明 COMMENT
为该存储过程补充业务功能描述文档，格式为 `COMMENT '描述说明字符串'`。该元数据会直接被持久化在系统字典表 `information_schema.ROUTINES` 中，便于团队协作与数据治理。

### DELIMITER 分隔符重定义的核心痛点与机制

在编写存储过程代码块时，几乎所有初学者遇到的第一个语法阻碍，都源自客户端的“分号截断机制”。

#### 默认分号与复合语句块的语法冲突

在标准的 MySQL 交互客户端（无论是原生终端命令行，还是 SQLyog、Navicat 等图形工具）中，**默认情况下分号 `;` 被硬编码为单条 SQL 语句的结束终止符**。当客户端解析器扫描到文本中的分号时，会立刻将分号前面的文本作为一个完整的 SQL 单元打包推送给服务端执行。

然而，存储过程的过程体是一个由 `BEGIN ... END` 围合的复合语句块。在这个复合体内部，可能包含三条、五条甚至几十条独立的 SQL 语句。按照 SQL 语法规范，过程体内部的每一条独立语句本身**必须以分号 `;` 结尾**！

```text
默认分号环境下客户端解析截断冲突：

 客户端脚本输入:
   CREATE PROCEDURE test_proc()
   BEGIN
       SELECT * FROM emps;  <─── [客户端解析器扫描到分号]
       SELECT * FROM depts;      客户端误认为整条 CREATE PROCEDURE 语句在此结束！
   END;                          立即向服务端发送半截代码: "CREATE PROCEDURE test_proc() BEGIN SELECT * FROM emps;"
                                 ▼
                          [服务端报错抛出 1064 语法错误：缺少匹配的 END]
```

由于客户端在读到内部第一个分号时就强行截断并提交，导致服务端接收到的 SQL 结构完全残缺，直接引发 `Syntax Error` 崩溃。

#### 使用 DELIMITER 改变终止判定符

为了彻底解决这一冲突，MySQL 客户端提供了 `DELIMITER` 命令，用于**临时修改客户端判定“语句结束”的标记符号**。

其工作时序与生命周期如下：

```text
DELIMITER 命令执行生命周期控制流：

 [客户端环境初始化: 默认结束符为 ;]
        │
        ▼
   DELIMITER //       ───► [将客户端语句结束符重定义为 //]
        │
        ▼
   CREATE PROCEDURE ...
   BEGIN
       SELECT ... ;   ───► [遇到分号，客户端忽略，继续向下吞吐]
       INSERT ... ;   ───► [遇到分号，客户端忽略，继续向下吞吐]
   END //             ───► [遇到 //，客户端判定复合 DDL 结束，整体打包发送给服务端编译]
        │
        ▼
   DELIMITER ;        ───► [立即恢复客户端结束符为标准分号 ;，防止污染后续常规 SQL]
```

具体代码书写规范如下：

```sql
-- 1. 临时将语句结束符修改为双斜线 //
DELIMITER //

-- 2. 编写完整的存储过程创建语句
CREATE PROCEDURE select_all_data()
BEGIN
    SELECT * FROM emps;
    SELECT * FROM departments;
END //

-- 3. 过程定义完毕，必须立刻将结束符重置回标准分号 ;
DELIMITER ;
```

#### 结束符选型禁忌与工程规范

在定制 `DELIMITER` 时，符号的选择具有严格的工程讲究：
1. **推荐符号**：行业中最通用、辨识度最高的结束符是 `$`、`$$` 或 `//`。
2. **严禁使用转义字符**：**绝不能使用反斜杠 `\` 作为结束符**！因为在 MySQL 语法以及绝大多数宿主编程语言中，反斜杠 `\` 具有转义字符（Escape Character）的特殊语义。一旦将其设定为分隔符，会导致后续解析器发生严重的转义混淆与不可预测的崩溃。
3. **随借随还规范**：在任何脚本或部署文件中，只要使用了 `DELIMITER` 改变了符号，在创建完存储对象后的第一行，**必须无条件写上 `DELIMITER ;` 改回分号**。否则后续执行普通的 `SELECT`、`UPDATE` 脚本时，客户端会因为迟迟找不到自定义符号而陷入持续挂起等待状态。

### 本讲提到的题目

本讲作为存储过程与函数章节的开篇导论，主要涉及架构原理、特性分类与使用规范的推演。讲师在课上着重提出了几个核心思考与判定题目，以下将其整理归纳：

#### 题目 1：存储过程与存储函数最根本的区分点是什么？
- **题干**：在 MySQL 数据库对象中，存储过程与存储函数在能力与设计契约上有何最根本的区别？
- **解析**：
  存储函数必须拥有单一的因变量返回值，其在语法层面上强制要求声明返回值类型并在函数体内使用 `RETURN` 关键字返回数据，支持在 `SELECT` 投影或条件表达式中直接内联调用；而存储过程没有单一返回值约束，语法内部不支持 `RETURN`，主要通过 `OUT`/`INOUT` 参数带回数据或直接输出结果集，必须通过独立专用的 `CALL` 指令显式触发。

#### 题目 2：存储过程形参缺省修饰符的默认行为是什么？
- **题干**：在编写 `CREATE PROCEDURE proc_test(name VARCHAR(20))` 时，参数 `name` 未显式标明 `IN`、`OUT` 或 `INOUT`，此时该参数属于哪种模式？
- **解析**：
  根据 MySQL 语法规范，当定义存储过程形参时未显式指明参数流向模式，系统默认将其作为 `IN`（纯输入参数）处理。

#### 题目 3：阿里巴巴《Java 开发手册》为何明令禁止使用存储过程？
- **题干**：结合现代微服务与分布式数据库架构，分析为什么一线互联网公司规范中严禁业务开发使用存储过程？
- **解析**：
  1. 移植性极差：不同数据库厂商对存储过程的语法支持严重分化，无法实现平滑的数据库技术栈迁移与兼容；
  2. 调试与版本控制困难：难以通过标准 IDE 进行断点调试，排查线上并发故障成本极高；
  3. 算力架构失衡：分布式环境下应用节点容易通过加容器弹性扩容，而数据库是有状态的核心计算瓶颈。将业务逻辑下沉到数据库运行会严重消耗数据库 CPU 资源，阻碍系统的高并发水平扩展能力。

#### 题目 4：创建存储过程时为什么必须临时使用 DELIMITER 重定义结束符？
- **题干**：若在终端工具中不使用 `DELIMITER //` 直接编写并执行包含 `BEGIN SELECT * FROM emps; END;` 的存储过程脚本，会导致什么现象？底层机理是什么？
- **解析**：
  会导致语法解析错误（Syntax Error）。因为客户端默认以分号 `;` 作为单条 SQL 的提交截止点。当解析器扫描到过程体内部 `SELECT * FROM emps;` 处的分号时，会误认为整条 `CREATE PROCEDURE` 语句已经结束并强行向服务端提交半截脚本，导致过程体结构不完整而引发报错。通过使用 `DELIMITER` 可以临时将结束符替换为 `//` 或 `$$`，确保客户端将整个 `BEGIN ... END` 复合语句块完整读取并一次性提交给服务端编译。

## 79-存储过程的创建与调用
> 对应分集：P79 | 原始标题：《79-存储过程的创建与调用》

在上一讲中，我们系统剖析了存储过程的预编译执行架构、生命周期、特征选项（`characteristics`）以及通过 `DELIMITER` 重定义结束符的核心原理。理论铺垫完成后，本讲我们将把理论转化为纯粹的代码实战。

编写存储过程绝不是简单的“把几句 SQL 塞进 `BEGIN ... END`”。根据数据在客户端与数据库服务端之间的流向契约，形参模式被严格划分为**无参、纯 IN 入参、纯 OUT 出参、IN 与 OUT 复合参、双向 INOUT 参**五种形态。不同的参数类型直接决定了过程体内部的赋值语法（如 `SELECT ... INTO`）以及客户端发起 `CALL` 时的传值与变量捕获规则。

本讲我们以 `dbtest15` 数据库为沙箱，完整演练全部 5 种参数模式的标准语法、底层机制、变量联动与生产避坑细节。

### 无参数存储过程的创建与调用

无参数存储过程是最纯粹的批处理程序，过程体在执行时不依赖外部动态输入的条件，主要用于执行固定的数据清洗、全量汇总或状态轮转。

#### 全表扫描与无参过程的标准闭环

我们首先实现一个最简单的需求：创建存储过程 `select_all_data()`，用于直接查看 `employees` 表中的全部员工明细数据。

在上一讲我们强调过，如果直接在常规交互界面书写 `CREATE PROCEDURE`，过程体内部的分号会导致语句被提前截断而崩溃。因此必须采用 `DELIMITER` 将结束符置换为 `$` 或 `//`：

```sql
-- 重定义结束符为 $
DELIMITER $

-- 创建无参存储过程
CREATE PROCEDURE select_all_data()
BEGIN
    SELECT * FROM employees;
END $

-- 恢复标准分号结束符
DELIMITER ;
```

创建成功后，在数据库管理工具中刷新即可看到名为 `select_all_data` 的存储过程对象。

调用无参数存储过程极为直接：在 SQL 中使用 `CALL` 命令，后跟过程名及空括号即可：

```sql
-- 调用无参存储过程
CALL select_all_data();
```

执行后，客户端立即呈现出 107 条员工完整记录。虽然看似只执行了一条 `SELECT *`，但这条语句已经在 MySQL 服务端完成了预编译和元数据驻留。

#### 聚合统计无参过程

我们再来看第二个经典需求：创建存储过程 `avg_employee_salary()`，用于计算并返回全公司所有员工的平均工资。

这里我们将结束符更换为 `//` 进行演练，加深对 `DELIMITER` 符号选择的熟练度：

```sql
DELIMITER //

CREATE PROCEDURE avg_employee_salary()
BEGIN
    SELECT AVG(salary) AS avg_sal FROM employees;
END //

DELIMITER ;
```

调用该过程获取全员平均薪资：

```sql
CALL avg_employee_salary();
```

服务端直接返回结果 `6461.68`。客户端完全无需知晓底层调用了哪张表、应用了哪个聚合函数，只需发出指令即可获取预设的聚合计算结果。

### 带 OUT 参数的存储过程与数据传出机制

很多初学者容易混淆概念：“前面不是说存储过程没有返回值吗？那 OUT 参数传出的值算不算返回值？”

这里必须明确辨析：**存储函数（Function）的返回值是通过语法级别的 `RETURN` 关键字强行约定的单一因变量出口；而存储过程的 `OUT` 参数，本质上是一个‘出参占位符’，过程体在执行过程中将内部计算出的某个单值‘灌入’这个形参，再由客户端传入的变量带出到会话环境中**。

#### 单值查询与 INTO 赋值机制

需求：创建存储过程 `show_min_salary()`，查询员工表中的最低薪资，并通过 `OUT` 参数 `ms` 将该薪资输出给外部。

在存储过程体内部，将查询结果写入变量的核心语法是 **`SELECT ... INTO 变量名`**。该语法要求 `SELECT` 投影的结果必须是**单行单列的标量值**，如果查询结果返回多行多列，赋值操作将直接报错抛出异常。

```sql
DELIMITER $

CREATE PROCEDURE show_min_salary(OUT ms DOUBLE(8,2))
BEGIN
    -- 将聚合函数计算出的单行单列值写入输出参数 ms
    SELECT MIN(salary) INTO ms 
    FROM employees;
END $

DELIMITER ;
```

#### 用户变量接收与查看

当一个存储过程包含 `OUT` 参数时，调用端**绝不能传入字面量常量**（例如传个 `CALL show_min_salary(100);` 会直接报语法错误，因为常量无法被内存写入）。**调用方必须传入一个用户会话变量来接收数据**。

在 MySQL 中，用户会话变量以单 `@` 符号开头（如 `@ms`），作用域为当前客户端会话。调用与查看步骤如下：

```sql
-- 1. 调用存储过程，传入用户变量 @ms 接收出参
CALL show_min_salary(@ms);

-- 2. 查看当前会话中用户变量的值
SELECT @ms;
```

执行后，`@ms` 输出 `2100.00`。数据从过程体内部的 `MIN(salary)` 成功通过 `INTO ms` 绑定并带出到了会话级变量 `@ms` 中。

### 带 IN 参数的存储过程与入参传递

当业务逻辑需要外部根据不同的条件进行动态查询或处理时，就必须引入 `IN` 参数。`IN` 参数是纯粹的输入参数，在过程体内部只能被读取。

#### 动态条件过滤过程构建

需求：创建存储过程 `show_someone_salary()`，查看指定员工的薪资，并通过 `IN` 参数 `emp_name` 接收外部传入的员工姓名。

```sql
DELIMITER $

CREATE PROCEDURE show_someone_salary(IN emp_name VARCHAR(20))
BEGIN
    SELECT salary 
    FROM employees 
    WHERE last_name = emp_name;
END $

DELIMITER ;
```

> **注意**：在定义形参名时，**强烈建议不要与数据表的物理字段名完全同名**（例如不要将形参命名为 `last_name`）。如果形参名与列名同名，在 `WHERE last_name = last_name` 表达式中，解析器可能会将两侧均识别为字段名或均识别为形参，导致全表匹配失控。通常采用 `emp_name`、`in_name` 等具名方式规避歧义。

#### 常量传递与会话变量传递双模式

对于 `IN` 参数，调用方具有更高的灵活性，既可以直接传递常量，也可以传递变量。

##### 方式一：直接传递字面量常量
对于偶发性手动查询，直接传入字符串字面量即可：

```sql
CALL show_someone_salary('Abel');
```

执行后，服务端直接输出 Abel 的工资 `11000.00`。

##### 方式二：通过会话变量赋值传递
在程序化流水线中，输入条件往往来自于上一环节的变量。我们可以先使用 `SET` 指令为用户变量赋值，再将变量传入过程：

```sql
-- 声明并赋值用户变量（支持 = 或 :=）
SET @emp_name := 'Abel';

-- 传入变量调用
CALL show_someone_salary(@emp_name);
```

> **提示**：在 MySQL 中，`SET` 赋值语句既可以使用常规等号 `=`，也可以使用赋值符 `:=`。但在非 `SET` 语句（如 `SELECT @var := col`）中，必须强制使用 `:=` 避免与等于比较运算符发生混淆。

### 带 IN 和 OUT 复合参数的综合实战

在真实业务开发中，最普遍的场景往往是“根据若干入参进行业务处理，并将若干指标汇总为出参带回”。此时需要在形参列表中同时定义 `IN` 与 `OUT`。

#### 数据类型精度匹配与隐式转换风险

需求：创建存储过程 `show_someone_salary2()`，接收员工姓名作为 `IN` 参数 `emp_name`，并将该员工的薪资通过 `OUT` 参数 `emp_salary` 输出给外部。

在编写该过程时，讲师在实战中专门探讨了一个极具工程价值的细节：**形参数据类型的严谨选型**。

底层 `employees` 表中的 `salary` 字段定义为 `DOUBLE(8,2)`。如果我们在定义输出参数 `emp_salary` 时，将其声明为 `DECIMAL(10,2)`，代码能够执行吗？

```sql
DELIMITER $

CREATE PROCEDURE show_someone_salary2(
    IN emp_name VARCHAR(20),
    OUT emp_salary DECIMAL(10,2)
)
BEGIN
    SELECT salary INTO emp_salary 
    FROM employees 
    WHERE last_name = emp_name;
END $

DELIMITER ;
```

实测表明该脚本能顺利创建并调用成功，因为 MySQL 内部支持从 `DOUBLE` 到 `DECIMAL` 的兼容隐式转换。但是，**这种写法存在潜在的生产隐患**：
1. 若源表字段精度范围较大（例如 `DECIMAL(15,2)`），而形参定义的范围较小（如 `DECIMAL(8,2)`），一旦实际数值超过 8 位，`INTO` 写入时就会发生数值溢出截断异常；
2. 若遇到不支持隐式转换的复杂类型，语句将直接崩溃。

> **结论**：在为存储过程定义入参和出参的数据类型时，**绝不能凭主观想象臆造，必须使用 `DESC 表名;` 严谨核验物理表的原始字段类型与长度，参数规格应与物理列严格一致或适当放宽，绝不可随意收窄**。

调用与捕获复合参数过程：

```sql
-- 准备输入变量与接收变量
SET @emp_name := 'Abel';

-- 发起调用（第一个参数传输入，第二个参数传输出变量）
CALL show_someone_salary2(@emp_name, @emp_salary);

-- 查看输出结果
SELECT @emp_salary;
```

### 带 INOUT 双向参数的高级特性与自连接实战

`INOUT` 参数是存储过程特有的一种高效参数模式。它将输入通道与输出通道合并在同一个参数标识符上，实现“携带初值进入，携带运算新值出厂”的闭环。

```text
INOUT 参数内存状态转移时序：

 [调用方会话环境]                 [存储过程内部空间: emp_name]
       │                                     │
  @emp_name := 'Abel'                        │
       │                                     │
       ├─── CALL proc(@emp_name) ───────────►│ (读取初始值 'Abel' 作为过滤条件)
       │                                     │
       │                                     │ (执行自连接/子查询定位 Abel 的主管)
       │                                     │ (查出主管姓名为 'King')
       │                                     │
       │                                     │ (SELECT 'King' INTO emp_name 覆写形参)
       │                                     │
       │◄── 过程执行完毕退出返回 ──────────────┤
       │
  @emp_name 此时的值变为 'King'
```

#### 员工主管层级查询业务构建

需求：创建存储过程 `show_mgr_name()`，查询某个员工领导的姓名；要求**仅使用一个 `INOUT` 参数 `emp_name`**，调用前用它输入员工姓名，调用后用它输出该员工直接主管的姓名。

首先核验底层数据表结构：通过 `DESC employees;` 获知 `last_name` 字段长度为 `VARCHAR(25)`。因此形参规格明确指定为 `INOUT emp_name VARCHAR(25)`。

在过程体内部，根据员工姓名查询其主管姓名，有子查询和自连接两种标准实现范式。这里以清晰的子查询写法为例：

```sql
DELIMITER $

CREATE PROCEDURE show_mgr_name(INOUT emp_name VARCHAR(25))
BEGIN
    -- 1. 子查询根据员工 last_name 查出其直接主管编号 manager_id
    -- 2. 外层查询根据该编号定位主管的 last_name，并覆写写入 emp_name
    SELECT last_name INTO emp_name
    FROM employees
    WHERE employee_id = (
        SELECT manager_id 
        FROM employees 
        WHERE last_name = emp_name
    );
END $

DELIMITER ;
```

> **提示**：若采用自连接（Self-Join）语法，逻辑等价为：
> ```sql
> SELECT mgr.last_name INTO emp_name
> FROM employees emp
> JOIN employees mgr ON emp.manager_id = mgr.employee_id
> WHERE emp.last_name = emp_name;
> ```

#### 双向覆写的调用规则与强制变量约束

对于 `INOUT` 参数，调用规则极其严格：
1. **绝对禁止传递字面量常量**！执行 `CALL show_mgr_name('Abel');` 会被 MySQL 语法分析器直接拒绝，因为常量无法承担 `OUT` 阶段的数据回写；
2. **必须使用已初始化赋值的变量**作为实参进行传递。

完整调用与覆写验证代码如下：

```sql
-- 1. 定义用户变量并赋予员工姓名初值（体现 IN 特性）
SET @emp_name := 'Abel';

-- 2. 调用存储过程（@emp_name 同时充当入参与出参载体）
CALL show_mgr_name(@emp_name);

-- 3. 查看变量值（此时变量已被覆写为主管姓名，体现 OUT 特性）
SELECT @emp_name;
```

执行后，`@emp_name` 的输出结果由原来的 `'Abel'` 变为了其直接领导的姓氏 `'King'`。

### 存储过程的调试困境与维护痛点

在完成上述五种参数模式的编写后，我们必须正视为什么存储过程在现代大型系统架构中备受争议。关键症结就在于**排错与调试（Debug）的极端艰难**。

在本次演练中，我们每个存储过程的过程体仅有 2~3 行 SQL，逻辑一目了然。但在实际复杂的企业级遗留系统或数据处理任务中，一个存储过程的内部可能交织着上百行 SQL，融合了条件判断、嵌套循环、游标遍历与事务回滚点。

一旦一个上百行的存储过程在生产环境中发生运行时挂起或逻辑报错，开发人员将面临极度崩溃的排错处境：
- **无原生单步断点支持**：C、C++、Java 或 Python 拥有成熟且强大的 IDE 支持（如 IntelliJ IDEA、Visual Studio、VS Code），支持堆栈回溯、断点单步步进与局部变量实时监视；而 MySQL 原生客户端完全不具备断点单步调试能力。
- **排错手段原始低效**：为了定位某一行 SQL 的计算偏差，开发人员往往只能采取“人工拆解、逐段外提”的原始手段——把存储过程体手工切碎，一句一句拿到外部单测运行，或者通过在内部频繁 `INSERT INTO debug_log` 打桩记录状态。
- **第三方商业工具门槛高**：虽然市面上存在少数提供调试插件的商业数据库管理软件，但成本高昂且在分布式环境或线上生产库中由于网络与权限限制往往无法启用。

正因如此，虽然存储过程在特定批处理中性能卓越，但在代码可读性、工程可维护性与持续集成（CI/CD）流水线中，其沉重的调试维护代价必须在架构设计初期进行严肃评估。

#### 题目 6：INOUT 双向参数存储过程实战（员工主管级联查询）
- **题干**：创建存储过程 `show_mgr_name()`，仅使用一个 `INOUT` 参数 `emp_name`，调用前输入员工姓名，调用后将该变量覆写为该员工主管的姓名，并说明为何不可直接传入字面量常量。
- **代码解答**：
  ```sql
  DELIMITER $
  CREATE PROCEDURE show_mgr_name(INOUT emp_name VARCHAR(25))
  BEGIN
      SELECT last_name INTO emp_name
      FROM employees
      WHERE employee_id = (
          SELECT manager_id 
          FROM employees 
          WHERE last_name = emp_name
      );
  END $
  DELIMITER ;

  SET @emp_name := 'Abel';
  CALL show_mgr_name(@emp_name);
  SELECT @emp_name;
  ```
  *原因说明*：因为常量是不可变的字面量，内存地址无法被写入；而 `INOUT` 参数在过程退出时需要将新计算的数据回写到实参中，因此必须传递可被赋值的用户会话变量。

## 80-存储函数的创建与调用
> 对应分集：P80 | 原始标题：《80-存储函数的创建与调用》

在前面的课程中，我们系统学习了 MySQL 系统提供的单行函数（如字符串处理、数值四舍五入、日期计算等）以及聚合函数（`SUM`、`COUNT`、`AVG` 等）。使用这些现成的内置函数，极大地提升了日常数据统计与分析的开发效率。

但在面对特定企业的垂直业务规则时，仅靠系统内置函数往往捉襟见肘。此时，我们可以使用**存储函数（Stored Function）**——即用户自定义函数（UDF）。与前两讲介绍的存储过程相比，存储函数在语法形式、调用方式以及底层约束机制上有着鲜明的个性和更为严格的规则限制。很多开发者初次在生产环境或本地终端中尝试创建存储函数时，最常遭遇的就是臭名昭著的 **1418 错误**，导致执行直接中断。

本讲我们将从存储函数的数学契约与语法骨架切入，逐一剖析 1418 报错的深层机理与两种彻底解决方案，并通过三个典型实战案例，全面打通存储函数的创建、变量传参内联调用，以及它与存储过程的深度架构对比。

### 存储函数的数学契约与语法定义规范

理解存储函数，最直接的切入点是回归到中学数学中的函数定义：$y = f(x)$。

```text
存储函数与存储过程在参数流向上的本质模型差异：

 [存储函数 Function: 严格的数学函数映射]
  自变量输入 (形参列表)                 因变量输出 (单一标量值)
  x1 ──┐                                   ▲
  x2 ──┼─► [ 存储函数体: 封闭计算逻辑 ] ─────┘ (必须通过 RETURN 输出单个结果)
  xn ──┘   (所有形参均为隐式 IN 模式)
  
 [存储过程 Procedure: 过程化子程序]
  入参 (IN)    ──► [ 过程体逻辑 ] ──► 出参 (OUT / INOUT 赋值)
  多参混用     ──► [ 执行 DML  ] ──► 直接抛出多行结果集 (无单一 RETURN)
```

在存储函数中，小括号内的形参列表就是**自变量集合**（可以有 0 个、1 个或多个自变量 $x_1, x_2, \dots, x_n$）。这些自变量只能向函数内部传递数据，因此**存储函数的形参只能且必须是输入（IN）模式**，语法上无需且**不允许书写 `IN`、`OUT` 或 `INOUT` 关键字**，直接声明形参名与数据类型即可。

而经过函数内部封闭运算后，**输出端必须且只能有且仅有一个因变量 $y$**。这一契约通过声明阶段的 `RETURNS` 与执行阶段的 `RETURN` 强制约束。

#### 语法骨架剖析

创建存储函数的标准语法模板如下：

```sql
CREATE FUNCTION 函数名([参数名 参数类型, ...])
RETURNS 返回值类型
[characteristics ...]
BEGIN
    函数体（必须包含有效的 RETURN 语句）
END
```

整个语法体系有三个核心语法点必须格外注意：
1. **`RETURNS` 与 `RETURN` 的单复数严格区分**：
   - 在函数头部（小括号之后、`BEGIN` 之前），使用的是复数形式的 **`RETURNS`**，后跟返回值的数据类型（如 `RETURNS VARCHAR(25)`、`RETURNS INT`），用于声明函数出厂的数据规格；
   - 在函数体内部（`BEGIN ... END` 之间），使用的是动词单数形式的 **`RETURN`**，后跟具体的表达式、变量或查询结果（如 `RETURN (SELECT email ...)`），用于向外部提交最终计算结果。二者不可混淆，否则直接触发语法分析错误。
2. **形参的纯输入属性**：小括号内的参数定义格式为 `(param_name type, ...)`，不能加上 `IN` 修饰符，系统默认且唯一支持入参模式。
3. **调用方式的自然内联性**：由于存储函数具有明确单一的返回值，它的调用完全不需要使用 `CALL` 命令，而是与系统内置函数一样，**直接在 `SELECT` 投影列、`WHERE` 条件子句甚至 `HAVING` 表达式中以函数名加实参的形式调用**。

### 报错根源与两种工程解决方案

掌握了基本语法结构后，很多同学按照直觉编写存储函数并执行时，往往会遭遇 MySQL 引擎的当头一棒。

#### 报错现象重现与二进制日志风险

我们尝试编写一个极简函数：查询员工 `'Abel'` 的电子邮箱并返回。如果完全不声明任何特征选项（`characteristics`），直接执行如下脚本：

```sql
DELIMITER $

CREATE FUNCTION email_by_name()
RETURNS VARCHAR(25)
BEGIN
    RETURN (SELECT email FROM employees WHERE last_name = 'Abel');
END $

DELIMITER ;
```

执行该 DDL 语句时，MySQL 客户端立即抛出严重异常：
```text
Error Code: 1418. This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)
```

为什么在上一讲创建存储过程时，省略 `characteristics` 能够平稳执行，而在创建存储函数时却被系统强行拦截？

其物理根源在于 **二进制日志（Binary Log，简称 binlog）与主从复制一致性** 的安全校验机制：
- 在默认开启了 binlog 的生产或开发环境中，所有在主库（Master）上执行的数据变更与函数调用，都会被记录进日志并同步发送给从库（Slave）重放。
- 如果一个自定义函数内部包含写操作（如修改表），或者属于非确定性逻辑（例如包含了 `NOW()`、`UUID()`、`RAND()` 或读取了动态变更的表），那么相同的函数在主库执行与在从库重放时，产生的数据结果可能完全不同，导致**主从数据严重不一致（数据分裂）**。
- 因此，MySQL 默认开启了严格防护：除非开发者在函数定义中明确声明了其行为特征（如 `DETERMINISTIC` 或 `READS SQL DATA`），或者全局明确允许“信任函数创建者”，否则严禁创建存储函数。

针对这一问题，官方提供了两种完全合规的工程解决方案。

#### 解决方案一：显式声明特征参数（精准控制）

第一种方案是在 `RETURNS` 之后、`BEGIN` 之前，显式书写该函数的行为特征（`characteristics`），明确告知优化器该函数的运行属性。

最常用的特征声明组合如下：
- `DETERMINISTIC`：表明该函数是确定性的（相同输入始终对应相同输出）；
- `CONTAINS SQL`：表明该函数体包含标准的 SQL 语句；
- `READS SQL DATA`：表明该函数只读取 SQL 数据，不执行任何写操作。

```sql
DELIMITER $

CREATE FUNCTION email_by_name()
RETURNS VARCHAR(25)
    DETERMINISTIC
    CONTAINS SQL
    READS SQL DATA
BEGIN
    RETURN (SELECT email FROM employees WHERE last_name = 'Abel');
END $

DELIMITER ;
```

追加特征声明后再次执行，脚本顺利创建成功，完全消除了 1418 报错。

#### 解决方案二：配置全局信任变量（快速开发）

如果项目中需要编写大量的业务函数，每个函数都要手工书写冗长的三行特征声明，无疑会降低开发体验。

报错信息中其实已经给出了第二种途径：修改系统变量 `log_bin_trust_function_creators`。
- 该变量默认值为 `0`（`OFF`），表示严格校验函数创建者；
- 若将其置为 `1`（`ON`），则表示放宽校验，信任所有具备创建权限的用户，允许在不声明特征的情况下直接创建存储函数。

在创建函数前，执行如下管理指令：

```sql
-- 查看当前变量状态
SHOW VARIABLES LIKE 'log_bin_trust_function_creators';

-- 设置全局变量放宽函数创建校验（需要管理员权限）
SET GLOBAL log_bin_trust_function_creators = 1;
```

> **提示**：在当前测试会话或开发环境中执行 `SET GLOBAL log_bin_trust_function_creators = 1;` 后，后续创建所有存储函数均可直接省略 `characteristics` 声明，直接由 `RETURNS 类型` 过渡到 `BEGIN ... END`。

### 存储函数实战案例演练

接下来我们在测试库 `dbtest15` 的员工表 `employees` 基础之上，通过三道由浅入深的典型案例，演练存储函数的全流程生命周期。

#### 案例一：无参存储函数与特征声明

需求：创建存储函数 `email_by_name()`，查询并返回指定员工（姓氏为 `'Abel'`）的电子邮箱地址。

本案例采用【方案一】，完整书写特征选项，熟悉标准的规范化定义：

```sql
USE dbtest15;

-- 1. 定义结束符为 $
DELIMITER $

-- 2. 创建无参函数
CREATE FUNCTION email_by_name()
RETURNS VARCHAR(25)
    DETERMINISTIC
    CONTAINS SQL
    READS SQL DATA
BEGIN
    -- 使用 RETURN 将子查询标量结果直接返回
    RETURN (SELECT email FROM employees WHERE last_name = 'Abel');
END $

-- 3. 还原结束符为分号
DELIMITER ;
```

调用该函数非常简单，直接在 `SELECT` 之后引用即可：

```sql
-- 内联调用无参存储函数
SELECT email_by_name();
```

执行后，查询面板输出单个单元格结果：`"HABEL"`。我们可以通过直接查询物理表 `SELECT email FROM employees WHERE last_name = 'Abel';` 验证比对，两者数据完全吻合。

#### 案例二：单参存储函数与全局变量信任机制

需求：创建存储函数 `email_by_id(emp_id INT)`，根据外部传入的员工工号，动态查询并返回该员工的电子邮箱。

在本案例中，我们采用【方案二】，先开启全局信任参数，进而精简函数声明：

```sql
-- 确保全局信任变量生效
SET GLOBAL log_bin_trust_function_creators = 1;

DELIMITER //

CREATE FUNCTION email_by_id(emp_id INT)
RETURNS VARCHAR(25)
BEGIN
    -- 依据入参 emp_id 执行过滤查询并返回结果
    RETURN (SELECT email FROM employees WHERE employee_id = emp_id);
END //

DELIMITER ;
```

对于带参存储函数，在调用时支持两种标准的传参范式：

##### 方式一：直接传递字面量实参
```sql
-- 查询工号为 100 的员工邮箱
SELECT email_by_id(100);

-- 查询工号为 101 的员工邮箱
SELECT email_by_id(101);
```

##### 方式二：通过用户会话变量传参
在外部批处理或应用驱动中，工号往往存储在变量中。我们通过 `SET` 赋值变量后传递给函数：

```sql
-- 声明并赋值用户变量（:= 或 = 均可）
SET @emp_id := 102;

-- 传入会话变量调用存储函数
SELECT email_by_id(@emp_id);
```

执行后，精准带出 102 号员工对应的电子邮箱。

#### 案例三：聚合统计存储函数与部门人数汇总

需求：创建存储函数 `count_by_id(dept_id INT)`，输入部门编号，统计并返回该部门内部的实际员工总人数。

在该案例中，函数内部需要调用聚合统计函数 `COUNT(*)`，返回值类型为整数 `INT`：

```sql
DELIMITER $

CREATE FUNCTION count_by_id(dept_id INT)
RETURNS INT
BEGIN
    -- 聚合统计指定部门的员工行数并返回标量
    RETURN (
        SELECT COUNT(*) 
        FROM employees 
        WHERE department_id = dept_id
    );
END $

DELIMITER ;
```

创建成功后，我们通过会话变量切换不同部门进行动态压测验证：

```sql
-- 统计 30 号部门人数
SET @dept_id := 30;
SELECT count_by_id(@dept_id); -- 输出结果为 6

-- 统计 50 号部门人数
SET @dept_id := 50;
SELECT count_by_id(@dept_id); -- 输出结果为 45
```

### 存储过程与存储函数多维深度对比

通过对存储过程（P78-P79）与存储函数（P80）的系统实战，我们可以站在系统架构的高度，全面审视二者的技术特性与工程选型边界。

| 对比维度 | 存储过程（Stored Procedure） | 存储函数（Stored Function） |
| :--- | :--- | :--- |
| **定义关键字** | `CREATE PROCEDURE` | `CREATE FUNCTION` |
| **返回值声明** | 头部**无**返回值类型声明 | 头部强制使用 **`RETURNS type`** |
| **退出返回机制** | 内部**无** `RETURN` 语句；靠 `OUT`/`INOUT` 参数带出 | 内部强制执行 **`RETURN expression;`** |
| **参数模式支持** | 支持 `IN`、`OUT`、`INOUT` 复合与双向模式 | 仅支持隐式 `IN` 模式，不支持出参模式 |
| **调用语法** | 必须使用专用的 **`CALL 过程名(...)`** 独立执行 | 直接使用 **`SELECT 函数名(...)`** 内联调用 |
| **SQL 嵌入能力** | **不可**作为表达式嵌入在普通 SQL 语句中 | **可以**无缝嵌入在 `SELECT`、`WHERE`、`ORDER BY` 中 |
| **输出数据形态** | 可输出 0 个、1 个或多个变量值，或直接输出多行结果集 | **严格只能输出且必须输出 1 个单一标量值** |
| **核心业务倾向** | 侧重于**数据维护与批量更新**（含大量 DML/DDL） | 侧重于**数据转换与计算查询**（加工清洗返回标量） |
| **功能灵活性** | 功能更强大、对事务控制更深入、适应复杂程序流 | 结构相对轻量、专精于单一计算职责 |

#### 为什么存储过程无法内联在 SELECT 中？
存储过程调用后，可能在内部执行了多次 `UPDATE`、生成了多张临时表，甚至抛出了包含多行多列的结果集，其行为不具备确定的数学因变量语义。普通 SQL 的投影列需要的是一个可以逐行渲染的单元格标量，因此只有具备强类型单一返回值的存储函数，才能内嵌于 `SELECT col, my_func(col) FROM t` 的表达式链路中。

#### 为什么复杂业务更倾向于存储过程？
当一段业务逻辑需要向调用方同时回传多个指标（例如既要返回总销售额，又要返回达成率，还要返回异常订单数）时，存储函数只能返回一个值，强制拆解为多个函数会导致对底层物理表的重复扫描；而存储过程只需一次运行，通过多个 `OUT` 参数将全部指标一次性回写，不仅性能卓越，而且更容易与数据库事务（`COMMIT` / `ROLLBACK`）进行一体化绑定。

## 81-存储过程与函数的查看修改和删除
> 对应分集：P81 | 原始标题：《81-存储过程与函数的查看修改和删除》

在前面的学习中，我们已经分别掌握了存储过程（Stored Procedure）与存储函数（Stored Function）的定义语法和调用方式。由于在业务调用时，存储过程通过 `CALL` 语句显式触发，而存储函数直接嵌入在表达式中并返回值，两者的调用机制截然不同，因此在语法定义上我们采取了分开讲解的策略。然而，当这些例程（Routine）在数据库中创建完毕后，进入到日常的运维与生命周期管理阶段时，它们在元数据查看、特性修改以及对象删除等操作上的语法和底层体系是高度统一的。

很多初入职场的开发者经常会遇到这样的困惑：去银行、证券或金融外企面试，或者接手老牌大型企业级项目时，主管要求核心业务必须写成存储过程；但如果转头看互联网大厂的规约，比如《阿里巴巴 Java 开发手册》，里面却用极其严厉的字眼明确规定：**【强制】禁止使用存储过程**。这两种截然相反的技术要求并非非黑即白，而是取决于系统在性能、安全、可移植性与高并发扩展性之间的权衡取舍。本讲将系统梳理存储过程与函数的查看、修改、删除三类核心运维操作，并深入剖析其底层的优劣势与工程争议。

### 存储过程与存储函数的元数据查看

当数据库中创建了大量的存储过程和函数之后，我们需要了解系统内到底注册了哪些例程、它们的内部逻辑是如何编写的、是由谁创建的、具备怎样的安全权限与字符集设置。在 MySQL 中，查看这些元数据通常有三种标准方式，分别适用于代码复现、状态巡检与系统级精准检索。

```text
+-------------------------------------------------------------------------+
|                  MySQL 存储过程与函数查看的三种途径                     |
+-------------------------------------------------------------------------+
|  [方式一] SHOW CREATE PROCEDURE / FUNCTION                             |
|          -> 查看创建例程的完整 DDL 源码、SQL 模式与字符集               |
|                                                                         |
|  [方式二] SHOW PROCEDURE / FUNCTION STATUS [LIKE '...']                 |
|          -> 查看数据库归属、类型、创建者、修改时间、执行权限与注释       |
|                                                                         |
|  [方式三] SELECT * FROM information_schema.ROUTINES                     |
|          -> 系统元数据字典表查询，支持复杂过滤，精准区分同名对象        |
+-------------------------------------------------------------------------+
```

#### 方式一：使用 SHOW CREATE 语句查看创建源码

`SHOW CREATE` 语句是开发过程中最常用的指令之一，与查看建表语句（`SHOW CREATE TABLE`）和查看视图定义（`SHOW CREATE VIEW`）一脉相承。它的核心价值在于直接提取出创建该例程时所使用的完整 DDL 代码。

其基本语法结构如下：

```sql
SHOW CREATE { PROCEDURE | FUNCTION } 存储过程名或函数名;
```

##### 实操案例：查看存储过程与函数的创建语句

在客户端管理工具（如 SQLyog、Navicat）或命令行终端中，我们可以针对已经创建好的对象发起查询：

```sql
-- 1. 查看存储过程 show_mgr_name 的创建信息
SHOW CREATE PROCEDURE show_mgr_name;

-- 2. 查看存储函数 count_by_id 的创建信息
SHOW CREATE FUNCTION count_by_id;
```

在图形化界面工具中执行该语句时，查询结果通常会以网格形式将字段平铺在一行展示，其中的创建语句被塞进一个单元格，阅读体验较差。在排查问题时，更推荐在原生命令行（CLI）中使用 `\G` 替代末尾分号，将每列按行折叠展示：

```sql
mysql> USE dbtest15;
Database changed

mysql> SHOW CREATE PROCEDURE show_mgr_name \G
*************************** 1. row ***************************
           Procedure: show_mgr_name
            sql_mode: ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
    Create Procedure: CREATE DEFINER=`root`@`localhost` PROCEDURE `show_mgr_name`(IN emp_id INT, OUT mgr_name VARCHAR(20))
BEGIN
    SELECT last_name INTO mgr_name
    FROM employees
    WHERE employee_id = (
        SELECT manager_id
        FROM employees
        WHERE employee_id = emp_id
    );
END
character_set_client: utf8mb4
collation_connection: utf8mb4_0900_ai_ci
  Database Collation: utf8mb4_0900_ai_ci
1 row in set (0.00 sec)
```

##### 返回字段的核心技术细节

- **Procedure / Function**：表明当前对象的名称及其类别。
- **sql_mode**：展示该例程在创建时所绑定的 SQL 运行模式（例如是宽松模式还是遵循 `STRICT_TRANS_TABLES` 等严格模式）。该模式决定了例程在执行过程中的语法兼容性与校验规则。
- **Create Procedure / Create Function**：例程完整的可执行代码体，包含了参数列表、定义者说明、`BEGIN ... END` 块以及业务逻辑。
- **character_set_client** 与 **collation_connection**：记录了创建时客户端连接所采用的字符集及比对校对规则，用于确保跨环境迁移时字符编码行为一致。

> **提示**：如果仅想快速把例程的完整 DDL 导出并导入到测试库中重现，使用 `SHOW CREATE` 是最高效的选择。

#### 方式二：使用 SHOW STATUS 语句查看例程状态信息

如果我们关心的不是内部的 SQL 实现细节，而是该对象的生命周期元数据（如归属数据库、创建者账户、创建时间、最后修改时间、调用权限级别等），应该使用 `SHOW STATUS` 系列语句。

其基本语法结构为：

```sql
SHOW { PROCEDURE | FUNCTION } STATUS [LIKE '匹配模式'];
```

##### 实操案例：全量与模糊匹配检索

如果不加 `LIKE` 子句，系统将会把当前 MySQL 实例中所有数据库（包括系统自带库）下的全部存储过程或函数尽数罗列出来，输出结果通常极其庞大：

```sql
-- 展示当前服务器中所有数据库定义的存储过程状态
SHOW PROCEDURE STATUS;
```

为了快速定位目标对象，必须结合 `LIKE` 进行过滤匹配。`LIKE` 子句天然支持通配符（`%` 匹配任意多个字符，`_` 匹配单个字符）：

```sql
-- 精确查找指定的存储过程 show_max_salary
SHOW PROCEDURE STATUS LIKE 'show_max_salary';

-- 模糊查找包含 salary 的所有存储过程
SHOW PROCEDURE STATUS LIKE '%salary%';

-- 精确查找指定的存储函数 email_by_id
SHOW FUNCTION STATUS LIKE 'email_by_id';
```

在命令行下通过 `\G` 格式化后，输出结果如下：

```sql
mysql> SHOW PROCEDURE STATUS LIKE 'show_max_salary' \G
*************************** 1. row ***************************
                  Db: dbtest15
                Name: show_max_salary
                Type: PROCEDURE
             Definer: root@localhost
            Modified: 2026-09-14 10:20:30
             Created: 2026-09-14 10:20:30
       Security_type: DEFINER
             Comment: 
character_set_client: utf8mb4
collation_connection: utf8mb4_0900_ai_ci
  Database Collation: utf8mb4_0900_ai_ci
1 row in set (0.00 sec)
```

##### 状态字段的技术含义

- **Db / Name / Type**：指明所在数据库库名、对象名及具体类型（`PROCEDURE` 或 `FUNCTION`）。
- **Definer**：对象定义者。默认情况下为创建该对象的账户（如 `root@localhost`）。
- **Created / Modified**：创建时间与最后一次修改特性的时间。如果创建后从未执行过 `ALTER` 修改特性，则两个时间戳完全相同。
- **Security_type**：安全执行上下文级别。其默认值为 `DEFINER`，表示只有具备定义者对应权限时方可执行；若改为 `INVOKER`，则表示任何拥有当前例程执行权限的调用者，均可以自身权限上下文执行该例程。
- **Comment**：定义例程时附带的业务注释说明。如果在创建时未显式声明，则该项显示为空。

#### 方式三：从 information_schema.ROUTINES 系统表中检索

MySQL 将所有的元数据以关系表的形式暴露在 `information_schema` 字典库中。对于存储过程与函数，其元数据集中存储在 `ROUTINES` 数据表中。直接通过 `SELECT` 语句查询该系统表，不仅能够获得比前两种方式更丰富的信息，还支持与开发中标准 SQL 语法一致的自由过滤和组合检索。

##### 实操案例：基于系统表的条件检索

查询 `ROUTINES` 表的基础 SQL 结构如下：

```sql
SELECT * 
FROM information_schema.ROUTINES
WHERE ROUTINE_NAME = 'email_by_id';
```

在实际工程中，当存储过程与存储函数存在同名情况时，单靠 `ROUTINE_NAME` 会将两者同时查出。此时需要借助 `ROUTINE_TYPE` 字段进行类型过滤：

```sql
-- 过滤只查看名为 email_by_id 的存储函数
SELECT * 
FROM information_schema.ROUTINES
WHERE ROUTINE_NAME = 'email_by_id' 
  AND ROUTINE_TYPE = 'FUNCTION';

-- 过滤只查看名为 show_min_salary 的存储过程
SELECT * 
FROM information_schema.ROUTINES
WHERE ROUTINE_NAME = 'show_min_salary' 
  AND ROUTINE_TYPE = 'PROCEDURE';
```

> **易错点**：虽然在常规的 MySQL 查询中字符串比对通常默认不区分大小写，但在检索 `ROUTINE_TYPE` 字段时，该字段对大小写具有强约束。若写成小写的 `AND ROUTINE_TYPE = 'function'`，查询引擎将无法命中记录，返回空结果集。必须严格使用大写的 `'FUNCTION'` 或 `'PROCEDURE'`。

##### 三种查看方式的比对与选型

| 查看方式 | 语法形式 | 核心优势 | 局限性 / 适用场景 |
| :--- | :--- | :--- | :--- |
| **SHOW CREATE** | `SHOW CREATE {PROCEDURE\|FUNCTION} name` | 直接获取底层完整的可执行 DDL 源码与建表逻辑 | 无法查看修改历史与执行上下文概览，适合排查与复制源码 |
| **SHOW STATUS** | `SHOW {PROCEDURE\|FUNCTION} STATUS [LIKE '...']` | 清晰展示生命周期元数据（时间戳、权限属性、注释） | 不显示例程内部代码体，适合服务巡检与状态比对 |
| **ROUTINES 系统表** | `SELECT * FROM information_schema.ROUTINES` | 字段最为全面，支持灵活的 SQL 组合条件筛选与关联查询 | 字段项极多，全表查询时开销较大，且类型匹配时严格区分大小写 |

### 存储过程与存储函数的特性修改

关于存储过程与函数的修改，很多初学者常有一个严重的思维误区：以为 `ALTER PROCEDURE` 或 `ALTER FUNCTION` 可以用来修改过程体或函数体内部的业务 SQL 逻辑。

> **结论**：在 MySQL 中，**`ALTER PROCEDURE` 和 `ALTER FUNCTION` 绝不能用于修改存储过程体或函数体（SQL 业务代码）**。它们只能且仅能修改例程相关的**特性参数（Characteristics）**。

如果编写完存储过程后发现查询的表名写错了、算法逻辑有纰漏，唯一的解决办法是先将其通过 `DROP` 删除，然后重新编写 `CREATE` 语句建一次。

```text
+-------------------------------------------------------------------------+
|                  存储过程与函数的修改边界判定                           |
+-------------------------------------------------------------------------+
|  [允许修改的内容 - Characteristics 特性]                                |
|  - SQL SECURITY : 切换调用权限上下文 (DEFINER / INVOKER)                 |
|  - COMMENT      : 修改或补充例程的业务注释说明                          |
|  - SQL 数据特性 : CONTAINS SQL / NO SQL / READS SQL DATA 等              |
|                                                                         |
|  [绝对禁止修改的内容 - Routine Body 逻辑体]                             |
|  - 参数列表 (IN / OUT / INOUT 变量定义)                                 |
|  - BEGIN ... END 内部的 SQL 业务逻辑与控制流                            |
|                                                                         |
|  * 业务代码变更唯一路径：DROP IF EXISTS -> 重新 CREATE                  |
+-------------------------------------------------------------------------+
```

#### ALTER 语法结构与支持的特性范围

修改存储过程与函数特性的标准语法如下：

```sql
ALTER { PROCEDURE | FUNCTION } 存储过程或函数名
[characteristic ...];
```

其中可修改的 `characteristic` 包含：

1. **`CONTAINS SQL`**：表明子程序包含 SQL 语句，但不包含读写数据的语句。
2. **`NO SQL`**：表明子程序中完全不包含 SQL 语句。
3. **`READS SQL DATA`**：表明子程序中包含从表中读取数据的语句（如 `SELECT`）。
4. **`MODIFIES SQL DATA`**：表明子程序中包含向表中写入数据的语句（如 `INSERT`、`UPDATE`、`DELETE`）。
5. **`SQL SECURITY { DEFINER | INVOKER }`**：指明谁有权限来执行。
   - `DEFINER`（默认值）：只有定义者账户才能执行，或者以定义者的权限上下文来执行。
   - `INVOKER`：只要拥有执行权限的调用者账户，就能以该调用者自身的权限执行。
6. **`COMMENT 'string'`**：为该例程补充或覆盖说明注释。

#### 实操案例：修改存储过程的权限上下文与注释

以存储过程 `show_max_salary` 为例，我们希望将其执行权限放宽为调用者角色（`INVOKER`），并为其添加规范的业务注释说明：

```sql
-- 修改存储过程的特性：设置安全上下文为 INVOKER，并添加注释
ALTER PROCEDURE show_max_salary
SQL SECURITY INVOKER
COMMENT '查询员工表中的最高工资信息';
```

执行后，我们利用前文介绍的 `SHOW PROCEDURE STATUS` 语句进行状态验证：

```sql
SHOW PROCEDURE STATUS LIKE 'show_max_salary';
```

可以看到返回结果中：
- `Security_type` 字段的值由原先的 `DEFINER` 成功变更为了 `INVOKER`；
- `Comment` 字段由原本的空值更新为了 `'查询员工表中的最高工资信息'`；
- `Modified` 字段的时间戳被自动刷新为当前执行 `ALTER` 的最新时间，而 `Created` 时间保持不变。

对于存储函数的特性修改，语法完全对称，只需将关键字替换为 `ALTER FUNCTION 函数名 [characteristic ...]` 即可。

### 存储过程与存储函数的删除操作

当例程的业务逻辑需要重构，或者废弃不用时，需要从数据库中将其彻底清除。由于 `ALTER` 无法变更代码体，删除重建也是修复例程业务 Bug 的标准操作。

#### DROP 语法规范与 IF EXISTS 的防护机制

删除存储过程与函数的语法非常简单：

```sql
DROP { PROCEDURE | FUNCTION } [IF EXISTS] 存储过程或函数名;
```

##### 语法要点解析

- 必须明确声明被删除对象是 `PROCEDURE` 还是 `FUNCTION`。
- **强烈建议加上 `[IF EXISTS]` 子句**：如果在执行删除时指定的例程在数据库中并不存在，且未添加 `IF EXISTS`，MySQL 会立即中断执行并抛出错误（`Error Code: 1305. FUNCTION/PROCEDURE ... does not exist`）。如果在自动化部署脚本或批处理 SQL 脚本中发生此类报错，会导致整个脚本链条中断执行。添加 `IF EXISTS` 后，若目标对象不存在，MySQL 会自动降级为发出一条警告（Warning），而让主流程继续执行。

#### 实操案例：安全删除存储函数与存储过程

##### 案例一：删除存储函数

尝试删除一个名称拼写错误的函数：

```sql
-- 若未加 IF EXISTS 且名字写错（如多写了一个 d），将直接报错
-- 错误：FUNCTION dbtest15.count_by_idd does not exist
DROP FUNCTION count_by_idd;

-- 推荐的标准写法：带 IF EXISTS 容错
DROP FUNCTION IF EXISTS count_by_idd;

-- 执行真实存在的函数删除
DROP FUNCTION IF EXISTS count_by_id;
```

执行成功后，在客户端管理工具的函数对象列表中按 `F5` 刷新，可以看到 `count_by_id` 函数已被完全销毁。

##### 案例二：删除存储过程

```sql
-- 删除指定的存储过程 show_min_salary
DROP PROCEDURE IF EXISTS show_min_salary;
```

执行并刷新数据库对象列表，`show_min_salary` 过程即被彻底移除。

### 架构辩证：存储过程与函数的行业争议与利弊权衡

在现代软件工程中，关于是否应该在生产系统中使用存储过程和存储函数，一直存在着激烈的讨论与分歧。有的系统将其奉为圭臬，有的技术团队则明令禁止。掌握技术本身只是初级阶段，理解该技术在不同系统架构中的利弊权衡，才是软件工程师进阶的核心素养。

```text
+-------------------------------------------------------------------------+
|                  存储过程的两极分化：传统行业 vs 互联网大厂             |
+-------------------------------------------------------------------------+
|  [传统企业 / 银行 / 证券 / 电信]      [互联网行业 / 分布式微服务]        |
|  - 业务规则高度稳定                   - 业务快速迭代与高频发版           |
|  - 数据安全隔离要求极高               - 海量并发与水平伸缩诉求           |
|  - 倾向于集中式高端数据库硬件         - 架构推崇“应用有状态计算，DB瘦身” |
|  - 偏好由 DBA 统一收拢数据权限        - 依赖 CI/CD 与自动化版本治理      |
|  ==> 【强制或重度依赖存储过程】       ==> 【强制禁止使用存储过程】       |
+-------------------------------------------------------------------------+
```

#### 核心优势（为什么传统系统青睐存储过程）

在银行、证券、政务以及传统外企等对于安全性、数据一致性和内部封锁性要求极高的场景下，存储过程具有不可替代的价值：

1. **一次编译，多次使用，提升执行效率**  
   客户端发送给 MySQL 的常规 SQL 文本，每次都需要经过词法解析、语法解析、预处理、生成逻辑执行计划、优化并编译为机器码的过程。而存储过程是在最初通过 `CREATE` 定义时，就在 DBMS 服务端完成了编译解析，并以预编译的形式常驻在数据库的高速缓存中。后续任何客户端调用时，只需发送简短的调用指令，服务端直接执行已生成的二进制代码，避免了重复编译的算力浪费。

2. **极大地降低网络传输开销（Network Overhead）**  
   如果一段业务涉及复杂的多次查询、中间比对和连续修改，若在应用层通过程序控制，需要在客户端与数据库服务器之间进行数次 TCP 网络往返（RTT），每次传输的内容都是冗长的 SQL 文本和庞大的中间结果集。如果将这段逻辑封装为服务端的存储过程，客户端只需向服务器发送一条极短的指令（例如 `CALL process_settlement(202609);`），所有的密集计算与多表交互均在数据库内部以内存总线速度完成，最后仅回传最终状态或少量结果，显著减轻了网络带宽压力。

3. **良好的业务逻辑封装性与代码复用**  
   存储过程相当于把数据访问层（DAL）的公共业务沉淀到了数据库层面。多个异构客户端（例如一个用 Java 编写的后台管理系统、一个用 Python 编写的报表脚本、一个用 C++ 编写的高频交易网关）可以同时调用同一个存储过程，确保底层数据清洗与核心结算算法完全统一，无需在各个客户端语言中重复编码。

4. **严密的安全与权限隔离机制**  
   在安全审查极为严格的组织中，系统管理员（DBA）往往不会向业务开发人员或应用账号开放底层数据表（如 `employees`、`accounts`）的 `SELECT`、`UPDATE` 等原始权限。而是通过编写存储过程，仅向应用账户授予该过程的 `EXECUTE` 执行权限。应用程序只能通过规定的接口输入参数并获取输出，无法脱离接口肆意探测或批量 dump 底层数据表，防范了内部数据泄露和恶意 SQL 注入攻击。

---

#### 核心劣势与弊端（为什么互联网大厂明令禁止）

与传统企业不同，互联网企业（以阿里、腾讯、美团等为代表）面临的是极度苛刻的用户并发规模（如双十一秒杀、海量请求）和极快的业务敏捷迭代节奏。在此类架构下，存储过程暴露出了致命的缺陷：

1. **调试极其困难，缺乏成熟的现代 IDE 支撑**  
   在 Java、Go、Python 等现代开发语言中，开发者拥有极为成熟的集成开发环境（如 IntelliJ IDEA、VS Code、Goland），可以方便地进行行级断点打点、条件断点、内存变量堆栈追踪与步进调试。而在数据库存储过程中，代码一旦写成几十行、上百行，内部嵌套多层循环与分支判断时，MySQL 官方并没有提供原生好用的可视化调试器。一旦逻辑计算出现偏差，开发人员往往只能被迫将过程体拆碎，在命令行中逐行手敲 SQL 排查，或者在代码中人工插入临时日志表来打印状态。排错排障成本极为高昂。

2. **可移植性（Portability）极差**  
   虽然关系型数据库都遵循通用 SQL 标准，但在**过程化 SQL 语法规范（Procedural SQL）**上，各大主流数据库厂商之间存在极大的私有实现壁垒。MySQL 的语法、Oracle 的 PL/SQL、微软 SQL Server 的 T-SQL、PostgreSQL 的 PL/pgSQL 之间在语法关键字、变量声明、游标使用、异常捕获机制上存在天壤之别。系统一旦大量使用存储过程与函数，就彻底与特定数据库产品深度绑定。日后若想进行数据库平替或国产化数据库迁移，几乎需要将整个业务代码全盘推翻重构。

3. **缺失工程级的版本控制与代码协同机制**  
   在现代软件工程中，团队协作高度依赖 Git 等分布式版本控制系统进行分支管理（Branching）、代码走查（Code Review）、自动化集成与原子回滚。而存储过程是直接保存在远程数据库实例中的，数据库本身并不原生提供 Git 式的代码 Diff 历史追溯功能。多人协同开发时，极易发生后提交的代码覆盖前人成果的“代码踩踏”现象；在线上热修复或灰度发布时，版本切换与故障回滚极为混乱。

4. **违背分布式水平扩展原则，加剧单点数据库瓶颈**  
   在高并发互联网架构设计中，核心黄金法则是：**“应用层做无状态计算，算力易扩容；数据库层做纯粹持久化存储，算力难扩容”**。应用服务器可以通过增加节点、挂载到负载均衡器后面轻松实现数十倍、上百倍的横向弹性伸缩（Scale Out）；而数据库往往处于分库分表的受限状态，且受制于磁盘 I/O、锁机制与网络连接，是整个系统最昂贵、最容易饱和的“单点瓶颈”。如果在数据库中运行包含大量逻辑判断与密集运算的存储过程，相当于把宝贵的数据库 CPU 资源消耗在业务计算上，直接降低了数据库的并发承载上限，阻碍了系统架构向分布式与读写分离的演进。

5. **黑盒化与人员断层导致的维护灾难**  
   由于存储过程与应用代码仓库脱节，久而久之，老员工离职后，大量核心逻辑深埋于数据库中且缺乏详尽文档，后人既不敢随意修改过程内部逻辑，又不敢轻易废除，最终演变成不可维护的技术债务。

### 存储过程 8 大核心实战题解

存储过程的实战主要围绕 `IN`（输入参数）、`OUT`（输出参数）、`INOUT`（输入输出双向参数）的协同工作机制，以及过程内部的 DML 写入、单行函数处理、数据分页和生命周期运维。

```text
+-------------------------------------------------------------------------+
|                        存储过程参数与调用数据流图                        |
+-------------------------------------------------------------------------+
|  [IN 参数]   : 外部字面量/变量 ---> 传入存储过程内部 (内部修改不影响外部) |
|  [OUT 参数]  : 外部用户变量   <--- 过程内部计算赋值回写 (外部必须传变量) |
|  [INOUT 参数]: 外部变量值     ---> 传入并计算回写自身 ---> 外部变量值刷新 |
+-------------------------------------------------------------------------+
```

#### 题 1：IN 参数实战——向 admin 表批量插入用户记录

- **业务需求**：创建存储过程 `insert_user`，接收用户名和密码，将其写入 `admin` 表中。
- **参数考点**：形参长度定义对底层表字段容量的匹配防护。

```sql
DELIMITER //

CREATE PROCEDURE insert_user(
    IN user_name VARCHAR(15),
    IN pwd VARCHAR(25)
)
BEGIN
    INSERT INTO admin(user_name, pwd)
    VALUES (user_name, pwd);
END //

DELIMITER ;
```

##### 关键技术点与避坑分析

在定义 `insert_user` 的参数时，`user_name` 声明为 `VARCHAR(15)`，`pwd` 声明为 `VARCHAR(25)`。**在存储过程参数设计中，形参的数据类型与长度应当严格与底层表的目标列保持一致或略小**。如果形参长度定义为 `VARCHAR(35)`，调用方传入一个长度为 30 的密码字符串，在存储过程入口处校验可以通过，但在执行内部的 `INSERT` 语句时，由于超出 `admin` 表 `pwd` 字段的最大容量限制，MySQL 会直接拦截并抛出数据截断错误（Data truncation / String data, right truncated）。

##### 验证与调用

```sql
-- 调用存储过程写入数据
CALL insert_user('Tom', 'abc123456');

-- 检查数据表验证持久化结果
SELECT * FROM admin;
```

#### 题 2：OUT 参数与语法陷阱——根据编号提取信息

- **业务需求**：创建存储过程 `get_phone`，传入女神的编号，返回对应的姓名和电话号码。
- **参数考点**：`SELECT ... INTO` 多字段提取时的语法规范与字段二义性避坑。

```sql
DELIMITER //

CREATE PROCEDURE get_phone(
    IN id INT,
    OUT name VARCHAR(15),
    OUT phone VARCHAR(15)
)
BEGIN
    -- 核心规约：INTO 之后接收的变量名列表绝对不能加圆括号
    SELECT b.name, b.phone INTO name, phone
    FROM beauty b
    WHERE b.id = id;
END //

DELIMITER ;
```

##### 易错点 1：INTO 变量列表误加括号

很多开发者习惯性地将多个回写变量用括号包起来，写成：
```sql
-- 错误写法：语法错误！
SELECT b.name, b.phone INTO (name, phone) FROM beauty b ...
```
在 MySQL 的过程化 SQL 语法中，`INTO` 后面直接跟以逗号分隔的变量列表，加括号会导致解析器将其识别为子查询语法，直接抛出 `1064 Syntax Error`。

##### 易错点 2：形参名与表列名冲突导致的二义性（Ambiguity）

本题中，形参名叫做 `id`，表中的主键列也叫 `id`。如果在 `WHERE` 子句中直接裸写 `WHERE id = id`，MySQL 会将左右两边都解析为过程的局部形参，导致该条件恒为真（相当于 `WHERE 1 = 1`），不仅无法精准匹配目标行，还会因查询出多条记录试图填充单行标量变量而抛出 `Result consisted of more than one row` 异常。**最佳工程规范是为数据表指定别名（如 `beauty b`），并在条件中使用 `b.id = id` 明确消除二义性**。

##### 验证与调用

```sql
-- 传入编号 1 查询朱茵的信息
CALL get_phone(1, @name, @phone);

-- 投影查看用户变量
SELECT @name, @phone;

-- 传入编号 3 查询田馥甄的信息
CALL get_phone(3, @name, @phone);
SELECT @name, @phone;
```

#### 题 3：单行函数联动——计算两个出生日期的天数间隔

- **业务需求**：创建存储过程 `date_diff`，传入两个出生日期，计算二者相差的天数并返回。
- **参数考点**：过程内部调用内置数学与日期单行函数，以及无表查询的标量赋值。

```sql
DELIMITER //

CREATE PROCEDURE date_diff(
    IN birth1 DATE,
    IN birth2 DATE,
    OUT sum_date INT
)
BEGIN
    SELECT DATEDIFF(birth1, birth2) INTO sum_date;
END //

DELIMITER ;
```

##### 函数机理深度剖析

内置日期函数 `DATEDIFF(expr1, expr2)` 的计算规则是**用第一个表达式减去第二个表达式**（即 $expr1 - expr2$）。如果传入的 `birth1` 早于 `birth2`，计算结果将为负数。此外，因为该运算仅针对内存中的传入形参进行计算，不需要关联任何底层物理数据表，因此内部的 `SELECT` 语句后完全可以省略 `FROM` 子句。

##### 验证与调用

```sql
-- 定义测试日期变量
SET @b1 = '1992-10-30';
SET @b2 = '1992-09-08';

-- 调用过程并将差值存入 @diff_days
CALL date_diff(@b1, @b2, @diff_days);

-- 验证结果：相差 52 天
SELECT @diff_days;
```

#### 题 4：日期格式化封装——格式化日期并返回指定字符串

- **业务需求**：创建存储过程 `format_date`，传入一个 `DATE` 类型日期，将其格式化为类似“xx年xx月xx日”的文本格式并回传。
- **核心概念**：格式化（Formatting）与解析（Parsing）的对称性理解。

```sql
DELIMITER //

CREATE PROCEDURE format_date(
    IN mydate DATE,
    OUT str VARCHAR(25)
)
BEGIN
    SELECT DATE_FORMAT(mydate, '%Y年%m月%d日') INTO str;
END //

DELIMITER ;
```

##### 知识沉淀：日期与字符串的双向转换

- **格式化（Formatting）**：将底层的二进制 `DATE / DATETIME` 类型转换为人类可读的字符串，采用 `DATE_FORMAT(date, format)`；
- **解析（Parsing）**：将输入的非结构化字符文本逆向还原为系统合法的日期对象，采用 `STR_TO_DATE(str, format)`。
- **占位符规范**：`%Y` 代表完整的四位年份（如 2026），`%y` 代表两位年份缩写（如 26）；`%m` 代表两位数字月份（01~12）；`%d` 代表两位日期（01~31）。

##### 验证与调用

```sql
-- 结合内置函数 CURDATE() 获取当前系统日期作为实参传入
CALL format_date(CURDATE(), @formatted_str);

SELECT @formatted_str;
```

#### 题 5：分页查询业务封装——基于 LIMIT 的结果集直接返回

- **业务需求**：创建存储过程 `beauty_limit`，根据传入的起始索引和每页条目数，输出对应记录。
- **核心机制**：存储过程并非必须通过 `OUT` 参数回传数据。当过程体执行未加 `INTO` 的 `SELECT` 语句时，MySQL 会将查询生成的结果集直接推送到客户端。

```sql
DELIMITER //

CREATE PROCEDURE beauty_limit(
    IN startIndex INT,
    IN size INT
)
BEGIN
    SELECT * 
    FROM beauty 
    LIMIT startIndex, size;
END //

DELIMITER ;
```

##### 验证与调用

```sql
-- 从索引 1 开始（即第 2 条记录），连续提取 3 条数据
CALL beauty_limit(1, 3);
```
执行后客户端直接接收到包含孙燕姿、田馥甄、邓紫棋三条完整记录的二维数据表格。

#### 题 6：INOUT 双向参数与变量赋值机制——实现数值翻倍

- **业务需求**：创建存储过程 `double_value`，接收变量 $a$ 和 $b$，将两者分别翻倍并写回原变量。
- **参数考点**：`INOUT` 的本质要求，以及过程内部的 `SET` 赋值语句。

```sql
DELIMITER //

CREATE PROCEDURE double_value(
    INOUT a INT,
    INOUT b INT
)
BEGIN
    SET a = a * 2;
    SET b = b * 2;
END //

DELIMITER ;
```

##### 致命避坑点：禁止直接给 INOUT 参数传递字面常量

`INOUT` 参数兼具输入与输出双重属性。很多开发者常犯如下错误：
```sql
-- 致命错误！
CALL double_value(3, 5);
```
该语句在执行时会立即报错（`OUT or INOUT argument 1 for routine ... is not a variable`）。其根本原因在于：字面量 `3` 和 `5` 是只读的不可变常量，无法在内存中承载被翻倍后的写回结果。**调用带有 OUT 或 INOUT 属性的例程时，实参位置必须显式传入已初始化的用户变量（User Variable）**。

##### 验证与调用

```sql
-- 1. 显式声明并初始化会话用户变量
SET @num1 = 3;
SET @num2 = 5;

-- 2. 将变量以引用语义传入
CALL double_value(@num1, @num2);

-- 3. 检查变量变化：原本的 3 和 5 分别翻倍变成了 6 和 10
SELECT @num1, @num2;
```

- **业务需求**：从系统中删除题目 5 中创建的存储过程 `beauty_limit`。

#### 题 8：存储过程的多维度信息审查

- **业务需求**：多角度审查题目 6 中所编写的 `double_value` 存储过程。


### 存储函数 4 大核心实战题解

存储函数的最大特征是**必须且只能有一个返回值**，并且其参数默认强制为输入语义（绝不允许显式声明 `IN`、`OUT` 或 `INOUT`）。在函数体内部必须显式通过 `RETURN` 关键字返回计算结果。

```text
+-------------------------------------------------------------------------+
|                        存储函数调用与执行机制                           |
+-------------------------------------------------------------------------+
|  调用方式: SELECT function_name(arg1, arg2...)                         |
|  内嵌规则: 存储函数是一个标量或聚合表达式，可直接嵌入 SELECT、WHERE 子句  |
|  语法铁律: 参数列表只写 (变量名 类型)，严禁写 IN/OUT 关键字             |
+-------------------------------------------------------------------------+
```

#### 前置准备：1418 报错机理与全局信任开关

在创建存储函数之前，我们从经典样例库 `atguigudb` 中快速同步两张员工与部门表：

```sql
-- 快速复制表结构与数据
CREATE TABLE employees AS SELECT * FROM atguigudb.employees;
CREATE TABLE departments AS SELECT * FROM atguigudb.departments;
```

> **易错点**：如果在创建自定义函数时遇到 `Error Code: 1418. This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled`，说明开启了二进制日志（Binary Log）的安全校验。
> 解决办法有两种：
> 1. 在函数头部声明其特性，如 `READS SQL DATA` 或 `DETERMINISTIC`；
> 2. 临时开启全局信任开关：`SET GLOBAL log_bin_trust_function_creators = 1;`。需要特别注意：**该系统变量若未写入 `my.cnf` 配置文件，在 MySQL 服务重启后会重置为 0，必须重新执行开启**。

#### 题 1：无参聚合统计——返回公司员工总人数

- **业务需求**：创建函数 `get_count`，无需输入参数，返回 `employees` 表中所有员工的总人数。

```sql
DELIMITER //

CREATE FUNCTION get_count()
RETURNS INT
DETERMINISTIC
READS SQL DATA
BEGIN
    RETURN (SELECT COUNT(*) FROM employees);
END //

DELIMITER ;
```

##### 调用与验证

存储函数的调用方式与存储过程完全不同，不能使用 `CALL`，而是像调用 MySQL 原生内置函数一样直接使用 `SELECT`：

```sql
SELECT get_count();
```
控制台立即返回标量数值 `107`。

#### 题 2：单行单列条件查询——按员工姓名返回工资

- **业务需求**：创建函数 `ename_salary`，传入员工的姓氏（`last_name`），返回其对应的工资金额。
- **语法规范**：函数参数列表严禁添加 `IN` 关键字。

```sql
DELIMITER //

CREATE FUNCTION ename_salary(emp_name VARCHAR(15))
RETURNS DOUBLE
DETERMINISTIC
READS SQL DATA
BEGIN
    RETURN (
        SELECT salary 
        FROM employees 
        WHERE last_name = emp_name
    );
END //

DELIMITER ;
```

##### 核心认知：SQL 查询依然是核心竞争力

无论在函数外部包裹多么复杂的过程化框架，其核心业务落脚点依然是那条高效的 `SELECT ... WHERE` 语句。掌握基础 SQL 的投影、筛选与聚合，是写好所有高级存储程序的底层基石。

##### 调用与验证

```sql
-- 查询知名员工 Abel 的工资
SELECT ename_salary('Abel');
```
查询返回 `11000.0`。

#### 题 3：多表连接与聚合统计——按部门名称计算平均薪资

- **业务需求**：创建函数 `dept_sal`，传入部门名称（`department_name`），返回该部门所有员工的平均工资。
- **多表关联**：通过 `departments` 匹配部门并与 `employees` 进行内连接求均值。

```sql
DELIMITER //

CREATE FUNCTION dept_sal(dept_name VARCHAR(20))
RETURNS DOUBLE
DETERMINISTIC
READS SQL DATA
BEGIN
    RETURN (
        SELECT AVG(e.salary)
        FROM employees e
        JOIN departments d ON e.department_id = d.department_id
        WHERE d.department_name = dept_name
    );
END //

DELIMITER ;
```

##### 调用与验证

在调用前，我们可以先从部门表中预览可用的部门名称：

```sql
SELECT department_name FROM departments;
```

以 `'Marketing'`（市场部）为例进行测试：

```sql
SELECT dept_sal('Marketing');
```
函数经过多表关联并做分组平均后，准确返回 `9500.000000`。

#### 题 4：纯算术运算函数——计算两数相加

- **业务需求**：创建函数 `add_float`，传入两个 `FLOAT` 类型的浮点数，返回两数之和。
- **场景特征**：完全不访问物理表，属于纯粹的逻辑计算，特性可声明为 `NO SQL`。

```sql
DELIMITER //

CREATE FUNCTION add_float(value1 FLOAT, value2 FLOAT)
RETURNS FLOAT
DETERMINISTIC
NO SQL
BEGIN
    RETURN (SELECT value1 + value2);
END //

DELIMITER ;
```

##### 调用与会话变量结合演练

我们可以直接传入字面常量，也可以将定义好的会话用户变量注入函数中：

```sql
-- 定义测试变量
SET @v1 = 12.2;
SET @v2 = 2.3;

-- 作为参数传入函数求和
SELECT add_float(@v1, @v2);
```
执行后得到准确结果 `14.5`。

### 存储过程与函数实战易错点全景对照

在 12 道课后题的编码过程中，涌现出了许多高频犯错点。将其汇总对比，有助于形成条件反射式的避坑意识：

| 场景 / 维度 | 存储过程（Stored Procedure） | 存储函数（Stored Function） |
| :--- | :--- | :--- |
| **参数模式关键字** | 必须显式注明 `IN`、`OUT` 或 `INOUT` | **严禁书写** `IN / OUT / INOUT`，默认全为输入 |
| **返回值机制** | 没有返回值；通过 `OUT / INOUT` 变量参数写回 | 必须在头部声明 `RETURNS <type>`，体部有 `RETURN <val>` |
| **调用执行指令** | 使用独立的指令：`CALL proc_name(...)` | 嵌入表达式中：`SELECT func_name(...)` |
| **INTO 赋值语法** | `SELECT col1, col2 INTO var1, var2`（**绝无括号**） | 通常直接用 `RETURN (SELECT ...)` 包裹或内部 `INTO` |
| **同名词法遮蔽** | 形参与字段名相同时，必须用表别名（`b.id = id`）消歧 | 形参与字段名相同时，同样必须使用表别名明确归属 |
| **实参类型约束** | `OUT / INOUT` 实参必须是变量，不能传字面常量 | 纯输入参数，可以直接传递字面常量或用户变量 |
| **服务重启影响** | 无特殊全局开关依赖 | `log_bin_trust_function_creators` 重启后若失效需重新配置 |
