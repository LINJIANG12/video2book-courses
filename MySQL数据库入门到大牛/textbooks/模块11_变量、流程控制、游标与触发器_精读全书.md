## 83-GLOBAL与SESSION系统变量的使用
> 对应分集：P83 | 原始标题：《83-GLOBAL与SESSION系统变量的使用》

在前面的章节中，我们系统学习了存储过程与存储函数的创建、调用与元数据管理。紧接着的知识模块是“变量、流程控制与游标”。很多开发者会有疑问：为什么在深入探讨存储过程和函数体内部的复杂控制逻辑之前，必须先将“变量”单独拎出来进行系统讲解？

回想一下在第 15 章编写存储过程实战时，当我们使用 `OUT` 参数接收返回结果时，在调用环节实际上已经写过了类似 `SET @name = ...; CALL get_phone(1, @name, @phone); SELECT @name;` 这样的语句。当时我们为了完成调用，提前预支了“用户变量”的用法。然而在 MySQL 中，变量绝对不仅仅局限于用户随手定义的临时变量，它是一个庞大而严密的层次体系。在服务端的底层支撑着整套数据库高效稳定运行的，是数量更为庞大、对系统行为起决定性作用的**系统变量（System Variables）**。

无论是日常排查字符集乱码、优化最大连接数限制，还是在生产环境中动态调整缓冲区大小，理解系统变量的作用域与其生命周期，是每一位后端工程师与 DBA 迈向高阶调优的必经之路。本讲将从宏观体系切入，全面拆解全局系统变量（GLOBAL）与会话系统变量（SESSION）的底层模型、查看方式、动态修改技巧以及持久化机制。

---

### 系统变量的体系架构与集合论模型

#### 系统变量的来源与实例绑定

系统变量不是由外部用户在写 SQL 时随意命名的，它是由 MySQL 官方系统预先定义好的，在体系结构上归属于**服务器层面**。

```text
+-------------------------------------------------------------------------+
|                  MySQL 实例启动与系统变量装载过程                       |
+-------------------------------------------------------------------------+
|  [硬件/操作系统]                                                        |
|         │                                                               |
|         ▼ 启动 mysqld 服务进程 (生成数据库运行实例)                     |
|  +───────────────────────────────────────────────────────────────────+  |
|  | MySQL 运行时实例 (内存空间)                                       |  |
|  |   ┌─────────────────────────────────────────────────────────────┐ |  |
|  |   │ 1. 加载源码编译内置的默认参数 (Hardcoded Defaults)          │ |  |
|  |   │ 2. 读取并覆盖 my.cnf / my.ini 配置文件参数                  │ |  |
|  |   │ 3. 初始化全局系统变量池 (GLOBAL Variables Pool)             │ |  |
|  |   └─────────────────────────────────────────────────────────────┘ |  |
|  +───────────────────────────────────────────────────────────────────+  |
+-------------------------------------------------------------------------+
```

当操作系统启动 MySQL 服务进程（如 Windows 下的 `net start mysql80`，或 Linux 下的 `systemctl start mysqld`）时，就会在内存中创建并运行一个独立的 MySQL 数据库实例。伴随该实例的生成，系统会立即执行系统变量的初始化加载：
1. **编译期硬编码默认值**：MySQL 源码在编译构建时预设的初始基准值；
2. **配置文件重载覆盖**：启动脚本读取指定路径下的配置文件（Windows 为 `my.ini`，Linux 为 `my.cnf`）。比如在初装 MySQL 5.7 时，默认字符集是 `latin1`，我们通过修改配置文件将其调整为 `utf8mb4`，服务启动时便会读取该配置文件并重写对应系统变量的值。

> **提示**：MySQL 8.0 官方文档列出了全部系统变量的规范字典。随着版本迭代，系统变量的总量在不断增加。例如在 MySQL 5.7 中全局系统变量大约为 500 多个，而到了 MySQL 8.0 实例中，全局系统变量已扩充至 617 个，会话系统变量达到 640 个。在日常开发中完全不需要逐一死记硬背，只需掌握其作用域规则和高频核心变量即可。

---

#### 全局系统变量（GLOBAL）与会话系统变量（SESSION）的集合模型

系统变量根据其影响范围与隔离级别，划分为两大核心类别：
- **全局系统变量（GLOBAL Variables）**：在整个数据库实例级别全局生效，对连接到当前实例的所有客户端会话起作用；
- **会话系统变量（SESSION / LOCAL Variables）**：仅在当前客户端连接会话（Connection Session）中生效，每个客户端拥有自身独立的局部副本。

这两个层级并不是彼此孤立的平行世界，而是一种典型的数学**文氏图（Venn Diagram）**包含与交集关系：

```text
+─────────────────────────────────────────────────────────────────────────+
|                     系统变量的作用域分类模型                             |
+─────────────────────────────────────────────────────────────────────────+
|                                                                         |
|         集合 A (GLOBAL 变量)               集合 B (SESSION 变量)        |
|     ┌────────────────────────┐         ┌────────────────────────┐       |
|     │                        │         │                        │       |
|     │      纯全局变量        │  A ∩ B  │       纯会话变量       │       |
|     │                        │         │                        │       |
|     │  max_connections       │ 既是全局│  pseudo_thread_id      │       |
|     │  innodb_buffer_pool_   │ 又是会话│                        │       |
|     │    size                │         │                        │       |
|     │                        │ 字符集类│                        │       |
|     │                        │ 事务控制│                        │       |
|     └────────────────────────┘         └────────────────────────┘       |
|                                                                         |
+─────────────────────────────────────────────────────────────────────────+
```

我们将系统变量划分为三类典型存在形式：

1. **纯全局系统变量（仅属于集合 A）**  
   这些变量决定着整个 MySQL 实例的全局运行骨架，无法在单个连接内进行差异化设置。
   - 典型代表：`max_connections`（实例允许承载的最大客户端并发连接数）。每个客户端连接消耗的是整个数据库的资源池，单独在某个会话中讨论“我这个会话的最大连接数”是毫无语义的，因此它只能是全局变量。

2. **纯会话系统变量（仅属于集合 B）**  
   这些变量仅针对某个具体连接的特定上下文状态存在，上升到实例全局层面没有任何意义。
   - 典型代表：`pseudo_thread_id`（当前会话在 MySQL 内部被分配的线程连接 ID）。每个客户端连接的线程编号都是唯一的，全局不存在一个通用的“系统统一连接 ID”。

3. **双重变量（属于交集 A ∩ B）**  
   这类变量兼具全局与会话双重身份。
   - 典型代表：`character_set_client`（客户端发送 SQL 的字符集编码）、`autocommit`（是否开启事务隐式自动提交）。
   - **继承与独立性机理**：当 MySQL 实例启动时，全局池中的该变量被赋初值；当任意一个客户端（如客户端 1、客户端 2）发起 TCP 连接建立会话时，MySQL 会**以全局变量的当前值作为模板，为该新会话复制一份独立的会话变量副本**。此后，若客户端 1 在其会话中将自己的字符集修改为 `gbk`，该修改仅作用于其自身的会话副本，既不会污染全局变量池，也不会对并行的客户端 2 产生任何干扰。

### 系统变量的多层次查看方案

在 MySQL 中，查看系统变量可以划分为：全量检索、模式匹配过滤，以及精准定位特定单值变量三种层级。

#### 全量查看系统变量

我们可以通过 `SHOW` 语法分别拉取全局与会话层面的所有变量：

```sql
-- 1. 查看当前 MySQL 实例的所有全局系统变量（MySQL 8.0 约 617 条）
SHOW GLOBAL VARIABLES;

-- 2. 查看当前会话的所有会话系统变量（MySQL 8.0 约 640 条）
SHOW SESSION VARIABLES;

-- 3. 若省略作用域关键字，MySQL 默认等价于 SHOW SESSION VARIABLES
SHOW VARIABLES;
```

> **结论**：在没有明确指出 `GLOBAL` 还是 `SESSION` 的情况下，`SHOW VARIABLES` 默认且永远匹配的是**当前会话（SESSION）**级别。

---

#### 结合 LIKE 通配符进行部分模糊筛选

全量查询输出的几百行数据往往难以直接阅读，在日常工程中几乎总是配合 `LIKE` 子句进行定向过滤：

```sql
-- 检索所有以 admin 开头的全局系统变量
SHOW GLOBAL VARIABLES LIKE 'admin_%';

-- 检索所有以 character 开头的会话系统变量（排查字符集配置的核心命令）
SHOW VARIABLES LIKE 'character_%';
```

当初我们在学习 MySQL 字符集配置时，验证终端编码使用的 `SHOW VARIABLES LIKE 'character_%';`，其本质正是检索会话系统变量列表。

---

#### 精准定位查看单个指定的系统变量

如果已知目标系统变量的确切名称，使用 `SELECT` 语句是最高效、最精准的读取方式。

##### 词法规范：双 `@` 符（`@@`）的隔离设计

在 MySQL 的语法规范中，对变量的前缀符号有着严密的设计隔离：
- **两个 `@` 符号（`@@`）**：严格且唯一用于标识**系统变量（System Variable）**；
- **单个 `@` 符号（`@`）**：严格用于标识**用户自定义会话变量（User Variable）**。

##### 精准查询语法

```sql
-- 1. 查看指定的全局系统变量
SELECT @@global.max_connections;

-- 2. 查看指定的会话系统变量
SELECT @@session.character_set_client;

-- 等价写法：session 亦可写为 local
SELECT @@local.character_set_client;

-- 3. 省略作用域的缺省写法
SELECT @@character_set_client;
```

##### 缺省匹配规则（关键机理）

当执行形如 `SELECT @@变量名;` 而不指定 `global.` 或 `session.` 前缀时，MySQL 会遵循自底向上的寻址策略：
1. **优先检索会话级变量池**：如果该变量存在会话级别，直接返回当前会话变量的值；
2. **后备检索全局级变量池**：若该变量不存在会话级别（即属于纯全局变量），则自动退化为读取全局变量的值。

##### 作用域越界报错剖析

如果试图在错误的作用域层级查询变量，MySQL 会严加防范并阻断执行：

```sql
-- 错误案例 1：max_connections 属于纯全局变量，强行以 session 查询将报错
-- 报错：Variable 'max_connections' is a GLOBAL variable
SELECT @@session.max_connections;

-- 错误案例 2：pseudo_thread_id 属于纯会话变量，强行以 global 查询将报错
-- 报错：Variable 'pseudo_thread_id' is a SESSION variable
SELECT @@global.pseudo_thread_id;
```

### 系统变量的动态修改与生命周期效应

修改系统变量有两种完全不同的技术路径：一种是物理持久化的修改配置文件，另一种是运行时利用 `SET` 语法动态变更。两者的适用场景、执行成本以及生命周期有着本质区别。

```text
+─────────────────────────────────────────────────────────────────────────+
|                  系统变量修改的两大路径与生命周期对比                   |
+─────────────────────────────────────────────────────────────────────────+
|  [途径一: 静态文件修改] (my.cnf / my.ini)                              |
|   修改磁盘配置文件 ---> 重启 MySQL 服务进程 ---> 全量永久生效           |
|   * 优点: 实例重启不丢失 (一劳永逸)                                     |
|   * 缺点: 生产环境停机重启成本巨大，破坏高可用 SLA                      |
|                                                                         |
|  [途径二: 动态运行时修改] (SET 语句)                                    |
|   通过 SQL 命令在线修改内存变量池 ---> 无需停机立即生效                 |
|   * 优点: 零停机平滑调优                                                |
|   * 缺点: 驻留在内存，一旦服务重启全部还原为默认配置                     |
+─────────────────────────────────────────────────────────────────────────+
```

#### 途径一：静态配置文件修改（持久化机制）

在宿主机的配置文件（如 Windows 下的 `C:\ProgramData\MySQL\MySQL Server 8.0\my.ini`）中直接编辑键值对：

```ini
[mysqld]
max_connections = 200
character-set-server = utf8mb4
```

保存文件后，必须重启 MySQL 服务进程。实例在重新引导时会重新挂载配置文件，修改后的变量将作为全局基准长久生效。这种方式的致命软肋在于：**生产环境下运行的数据库不允许随意停机重启**。

---

#### 途径二：运行时动态修改全局系统变量（GLOBAL）

为了在系统不关机的前提下进行动态调优，DBA 可以在运行期使用 `SET` 语句在线调整全局变量。

##### 修改全局变量的两种标准语法

以调整实例最大连接数 `max_connections` 为例：

```sql
-- 语法 1：使用双 @ 符点语法
SET @@global.max_connections = 161;

-- 语法 2：使用 GLOBAL 关键字标准语法
SET GLOBAL max_connections = 171;
```

这两种语法在功能上完全等价。

##### 验证与生命周期实测

1. **在线即时生效**：执行修改后，立即执行 `SELECT @@global.max_connections;`，返回值从原本的 `151` 瞬间刷新为 `171`。此后任何新建的连接都会受到该新上限的约束。
2. **重启后失效归位**：
   - 打开管理员权限命令行窗口，执行服务重启：
     ```cmd
     net stop mysql80
     net start mysql80
     ```
   - 重新连接并再次查询全局变量：
     ```sql
     SELECT @@global.max_connections;
     ```
   - 查询结果显示：`max_connections` 重新变回了配置文件或系统默认的 `151`。

> **结论**：通过 `SET GLOBAL` 修改的变量值，**仅在当前运行的 MySQL 内存实例中存活**。一旦实例重启，内存池被重构，未落盘到配置文件的修改将彻底蒸发。

---

#### 运行时动态修改会话系统变量（SESSION）

如果业务只需临时调整某个会话自身的行为（如导入大批数据时临时改变客户端字符集），应当精准修改会话级变量。

##### 修改会话变量的标准语法

以将客户端输入字符集临时调整为 `gbk` 为例：

```sql
-- 语法 1：使用双 @ 符 session 点语法
SET @@session.character_set_client = 'gbk';

-- 语法 2：使用 SESSION 关键字语法
SET SESSION character_set_client = 'gbk';

-- 语法 3：缺省前缀（默认即为会话级）
SET character_set_client = 'gbk';
```

##### 会话隔离性与生命周期验证

1. **会话隔离性验证**：
   - 在连接会话 A 中执行 `SET SESSION character_set_client = 'gbk';`；
   - 在会话 A 中执行 `SELECT @@session.character_set_client;`，结果显示为 `gbk`；
   - 此时在同一客户端工具中新建一个连接窗口（会话 B），在会话 B 中执行 `SELECT @@session.character_set_client;`，输出依然是默认的 `utf8mb3`（或 `utf8mb4`），不受会话 A 的任何影响。
2. **全局独立性验证**：
   - 在会话 A 中查询全局变量 `SELECT @@global.character_set_client;`，发现全局值依然岿然不动。
3. **断开重连生命周期**：
   - 关闭会话 A 并重新建立连接，此时再次查询会话级变量，发现值已重新继承自全局池的默认配置，之前所做的会话临时修改彻底失效。

### 全局变量与会话变量核心属性全景对比

为了在实战中杜绝混淆，下表系统总结了 GLOBAL 与 SESSION 变量的各项技术指标：

| 比较维度 | 全局系统变量（GLOBAL Variables） | 会话系统变量（SESSION Variables） |
| :--- | :--- | :--- |
| **所属层级** | 归属于整个 MySQL 服务器实例（Instance） | 归属于单个客户端连接（Connection） |
| **初始化时机** | MySQL 服务启动、实例初始化时加载 | 客户端与服务端建立 TCP 连接并初始化会话时生成 |
| **默认初始值来源** | 源码编译默认值或 `my.cnf / my.ini` 配置文件 | 从当前全局系统变量池中完整克隆继承 |
| **查看全量语法** | `SHOW GLOBAL VARIABLES;` | `SHOW SESSION VARIABLES;` 或 `SHOW VARIABLES;` |
| **单值检索语法** | `SELECT @@global.var_name;` | `SELECT @@session.var_name;` 或 `SELECT @@var_name;` |
| **动态修改语法** | `SET GLOBAL var = val;` / `SET @@global.var = val;` | `SET SESSION var = val;` / `SET var = val;` |
| **修改作用半径** | 影响当前实例以及后续所有新建会话 | **仅影响当前会话自身**，对其他会话完全透明隔离 |
| **修改生命周期** | 持续至服务进程关闭；**重启服务后立即失效** | 持续至连接中断退出；**断开会话后立即失效** |
| **典型配置场景** | `max_connections`、缓冲区与连接池大小调优 | `character_set_client`、事务隔离级别与自动提交微调 |

## 84-会话用户变量与局部变量的使用
> 对应分集：P84 | 原始标题：《84-会话用户变量与局部变量的使用》

在上一讲中，我们系统剖析了 MySQL 服务器底层的系统变量（包括 GLOBAL 全局变量与 SESSION 会话变量）。系统变量是由数据库软件预先定义好的，主要用于控制数据库实例的运行行为与资源配额。然而，当我们在日常业务中编写复杂的存储过程、存储函数，或者编写批处理脚本需要暂存中间计算结果时，仅仅依靠系统变量是远远不够的。此时，必须借助开发者自主创建的**用户变量（User-Defined Variables）**。

在 MySQL 中，用户自定义变量并不是铁板一块，而是严格根据其**作用域边界（Scope）**和**内存生命周期（Lifecycle）**细分为两大阵营：**会话用户变量（Session User Variables）**与**局部变量（Local Variables）**。很多开发者在初学过程化编程时，常常搞不清为什么有的变量前面必须加 `@` 符，有的变量加了 `@` 就会报错；为什么有的变量直接 `SET` 就能用，而有的变量必须在第一行用 `DECLARE` 显式声明类型。本讲将从底层机制出发，逐一解开这些设计原理，并通过实际业务案例彻底掌握两类变量的实操技法。

### 用户变量的体系划分与前缀规约

在进入代码实操之前，首先需要理清 MySQL 变量全景中的词法前缀与作用域规约：

```text
+-------------------------------------------------------------------------+
|                  MySQL 变量全景词法标识与作用域拓扑                     |
+-------------------------------------------------------------------------+
|  1. 系统变量 (System Variables)                                         |
|     - 词法标识: @@global.var_name 或 @@session.var_name (双 @ 符号)     |
|     - 作用域  : 服务器全局实例 / 客户端连接会话                         |
|                                                                         |
|  2. 会话用户变量 (Session User Variables)                               |
|     - 词法标识: @var_name (单 @ 符号)                                   |
|     - 作用域  : 当前客户端连接 (Connection Session) 全局有效            |
|     - 特征    : 弱类型、无需声明、随连接存活、断开连接即销毁            |
|                                                                         |
|  3. 局部变量 (Local Variables)                                          |
|     - 词法标识: var_name (完全不带 @ 符号，裸写标识符)                  |
|     - 作用域  : 仅在 BEGIN ... END 复合语句块内部有效                   |
|     - 特征    : 强类型、必须在块首行 DECLARE 声明、退出块立即消亡       |
+-------------------------------------------------------------------------+
```

#### 为什么局部变量不需要加 `@` 符？

在 MySQL 的词法解析设计中：
- 系统变量采用双 `@` 符（`@@`），会话用户变量采用单 `@` 符（`@`），这两者都存在于当前连接的会话上下文中，通过 `@` 数量的差异实现词法隔离；
- 而**局部变量**是严格封闭在存储过程或函数的 `BEGIN ... END` 代码块内部的私有变量，其作用范围极其受限。离开代码块后，外部世界根本感知不到它的存在。正因为它的可见性被严格限制在块作用域内，完全不会与外层的全局变量或会话变量产生命名冲突，因此语法设计上直接使用纯净的标识符名（无需任何 `@` 前缀）。

### 会话用户变量的定义、赋值与生命周期

会话用户变量属于当前客户端连接。其核心特征是**弱类型**（无需提前声明类型，直接根据赋予的值自动推断）且**即插即用**。

#### 变量的声明与赋值语法

会话用户变量的声明与赋值通常合二为一，主要有两种操作途径：

##### 途径一：使用 SET 语句直接赋值

```sql
SET @用户变量名 = 表达式 [, @用户变量名2 = 表达式2 ...];
-- 或者使用过程化推荐的赋值符 :=
SET @用户变量名 := 表达式;
```

> **提示**：在 SQL 语句中，等号 `=` 既可以作为比较运算符，也可以作为赋值运算符。为了消除二义性，在进行变量赋值时，**强烈建议养成使用 `:=` 赋值符的习惯**。

```sql
-- 1. 定义标量变量并赋初值
SET @m1 = 1;
SET @m2 := 2;

-- 2. 变量之间支持复合表达式计算与连续赋值
SET @sum := @m1 + @m2;

-- 3. 查看变量结果
SELECT @sum;  -- 输出：3
```

##### 途径二：结合 SELECT 语句将查询结果注入变量

当变量的值不是硬编码常量，而是来自数据表的统计、聚合或单行字段查询时，可以使用 `SELECT` 语句赋值：

```sql
-- 方式 2.1：在投影列表中使用 := 赋值
SELECT @count := COUNT(*) FROM employees;
SELECT @count;  -- 输出：107

-- 方式 2.2：使用标准的 INTO 语法（工程推荐）
SELECT AVG(salary) INTO @avg_sal FROM employees;
SELECT @avg_sal;  -- 输出：6461.682243
```

#### 会话用户变量的内存存活机制

会话用户变量的生命周期与当前客户端的**物理连接（Connection）**强绑定：
1. **跨语句持久性**：在一个会话连接内，一旦某个会话用户变量被赋值（如上面的 `@sum`、`@avg_sal`），即便执行完后续成百上千行其他 SQL 语句，该变量依然常驻在客户端连接对应的服务器内存中，随时可以通过 `SELECT @sum;` 重新调取。
2. **连接断开即销毁**：一旦关闭客户端工具、重启连接窗口，或者会话超时断开，分配给该连接的内存池将被完全回收，之前定义的所有会话用户变量全部随之灰飞烟灭。若在新会话中尝试读取未初始化的变量（如 `SELECT @sum;`），MySQL 会直接返回 `NULL` 而不会报错。

### 局部变量的声明铁律与作用域控制

局部变量（Local Variables）是构建企业级复杂存储过程与存储函数的核心构件。不同于随性的会话用户变量，局部变量具有极其严密的语法规范与静态类型约束。

```text
+-------------------------------------------------------------------------+
|                       局部变量的四大语法铁律                            |
+-------------------------------------------------------------------------+
|  [铁律 1] 必须使用 DECLARE 关键字进行显式声明                           |
|  [铁律 2] 必须声明在 BEGIN ... END 复合语句块内部                      |
|  [铁律 3] 必须置于 BEGIN 块的最顶部（首行位置），严禁出现在业务代码之后  |
|  [铁律 4] 必须显式指定数据类型 (强类型校验)，可选赋予 DEFAULT 默认值     |
+-------------------------------------------------------------------------+
```

#### DECLARE 声明语法与默认值规则

局部变量声明的标准语法如下：

```sql
DECLARE 变量名 [, 变量名2 ...] 数据类型 [DEFAULT 默认值];
```

##### 语法细节与规范

1. **强类型约束**：必须明确指定变量的存储类型（如 `INT`、`VARCHAR(25)`、`DOUBLE(10,2)`、`DATE` 等）。向其写入不兼容的数据类型时会触发类型转换失败或截断报错。
2. **默认值机制**：若未显式书写 `DEFAULT` 子句，局部变量在被声明后的**初始默认值一律为 `NULL`**。
3. **合并声明**：如果多个局部变量的数据类型与默认值完全一致，可以将其合并在同一行用逗号分隔声明：
   ```sql
   -- 独立声明
   DECLARE a INT DEFAULT 0;
   DECLARE b INT DEFAULT 0;
   
   -- 等价的合并简写
   DECLARE a, b INT DEFAULT 0;
   ```

> **易错点**：局部变量的 `DECLARE` 语句**必须紧跟在 `BEGIN` 之后、写在所有业务逻辑（如 `SELECT`、`UPDATE`、`IF`）的最前列**。如果试图在执行了一条业务 SQL 之后再写 `DECLARE`，MySQL 解析器会直接报 `1064 Syntax Error`。

---

#### 局部变量的赋值与使用

局部变量一旦在块首声明完毕，其赋值与使用方式与常规过程化语言完全相同：

```sql
-- 方式 1：使用 SET 直接赋值
SET 变量名 = 表达式;
SET 变量名 := 表达式;

-- 方式 2：使用 SELECT ... INTO 回写
SELECT 列名 INTO 局部变量名 FROM 表名 WHERE 过滤条件;
```

##### 综合演示案例：局部变量的基础流转

我们编写一个简单的存储过程 `test_var`，观察局部变量从声明、初始化、赋值到终端输出的完整闭环：

```sql
DELIMITER //

CREATE PROCEDURE test_var()
BEGIN
    -- 1. 块首声明局部变量 (包含带默认值与不带默认值)
    DECLARE a INT DEFAULT 0;
    DECLARE b INT;
    DECLARE emp_name VARCHAR(25);
    
    -- 2. 赋值操作
    SET a = 1;
    SET b := 2;
    
    SELECT last_name INTO emp_name
    FROM employees
    WHERE employee_id = 101;
    
    -- 3. 在过程内部输出局部变量的值
    SELECT a, b, emp_name;
END //

DELIMITER ;
```

调用该存储过程进行验证：

```sql
CALL test_var();
```
控制台精准输出：`a = 1`, `b = 2`, `emp_name = 'Kochhar'`。

### 会话用户变量与局部变量全维度技术对比

为了在实战编码时能够清晰选型，下表将两类变量的技术指标进行了全方位对照：

| 比较维度 | 会话用户变量（Session User Variable） | 局部变量（Local Variable） |
| :--- | :--- | :--- |
| **词法命名规则** | 必须以单个 `@` 符号开头（如 `@my_var`） | **绝对不带 `@` 符号**，直接写变量名（如 `my_var`） |
| **作用域范围** | 当前客户端连接（会话）内的任何地方 | 仅在定义它的 `BEGIN ... END` 复合语句块内部有效 |
| **声明关键字** | 无需显式声明，随用随赋 | 必须使用 `DECLARE` 显式声明 |
| **定义位置约束** | 会话中的任意 SQL 语句位置均可直接定义 | **必须强制位于 `BEGIN ... END` 块的最顶部（首行）** |
| **数据类型系统** | 弱类型，由 MySQL 运行时根据赋值动态推导 | **强类型**，声明时必须显式指定底层数据类型 |
| **默认初始值** | 未定义直接引用时，默认值为 `NULL` | 未指定 `DEFAULT` 子句时，默认值为 `NULL` |
| **内存生命周期** | 伴随整个会话连接；连接断开时才被销毁 | 伴随过程/函数执行；退出 `BEGIN ... END` 块立即销毁 |
| **典型适用场景** | 接收存储过程的 `OUT` 参数、跨语句传递状态 | 存储过程/函数内部的中间计算、循环计数、游标暂存 |

#### 练习 3：高阶综合——计算员工与其直属主管的薪资差额

- **需求描述**：创建存储过程 `different_salary`。
  - 输入参数：`IN emp_id INT`（员工工号）；
  - 输出参数：`OUT dif_salary DOUBLE`（薪资差额）；
  - 核心逻辑：查询该员工自身的工资，以及其直属领导（Manager）的工资，计算二者的绝对差距并回传给输出参数。

##### 解题推导链条与局部变量规划

在编写该复杂存储过程时，我们无法一步到位直接输出结果，需要分步拆解并规划内存中间变量：
1. 我们需要记录该员工的工资，因此需要一个局部变量 `emp_sal`；
2. 我们需要知道该员工的直属管理者是谁，因此需要从该员工记录中提取 `manager_id`，需要一个局部变量 `mgr_id`；
3. 我们需要记录管理者的工资，因此以 `mgr_id` 为主键查询管理者的工资，需要一个局部变量 `mgr_sal`；
4. 最后计算差额 $mgr\_sal - emp\_sal$，将最终结果赋予输出参数 `dif_salary`。

```text
+-------------------------------------------------------------------------+
|                  不同薪资计算存储过程内部数据流动                       |
+-------------------------------------------------------------------------+
|  入参: emp_id (如 102)                                                  |
|     │                                                                   |
|     ├─> 查询 employees 表 ──> 获取当前员工 salary     ──> INTO emp_sal  |
|     │                                                          (17000)  |
|     └─> 查询 employees 表 ──> 获取 manager_id (如 100) ──> INTO mgr_id  |
|                                                                 │       |
|  ┌──────────────────────────────────────────────────────────────┘       |
|  ▼                                                                      |
|  以 employee_id = mgr_id 查询 employees ──> 获取领导 salary ──> INTO mgr_sal  |
|                                                                (24000)  |
|                                                                   │     |
|  差值计算: SET dif_salary = mgr_sal - emp_sal  <──────────────────┘     |
|            (24000 - 17000 = 7000)                                       |
|     │                                                                   |
|     ▼                                                                   |
|  写回出参: OUT dif_salary (供外部会话用户变量承接)                      |
+-------------------------------------------------------------------------+
```

##### 完整代码实现

```sql
DELIMITER //

CREATE PROCEDURE different_salary(
    IN emp_id INT,
    OUT dif_salary DOUBLE
)
BEGIN
    -- 1. 首行声明 3 个核心局部变量
    DECLARE emp_sal DOUBLE DEFAULT 0.0;
    DECLARE mgr_sal DOUBLE DEFAULT 0.0;
    DECLARE mgr_id INT DEFAULT 0;
    
    -- 2. 获取目标员工的工资与直属主管 ID
    SELECT salary, manager_id INTO emp_sal, mgr_id
    FROM employees
    WHERE employee_id = emp_id;
    
    -- 3. 根据主管 ID 获取主管的工资
    SELECT salary INTO mgr_sal
    FROM employees
    WHERE employee_id = mgr_id;
    
    -- 4. 计算薪资差额并赋值给 OUT 参数
    SET dif_salary = mgr_sal - emp_sal;
END //

DELIMITER ;
```

##### 生产级验证与数据溯源比对

我们选取两条具备代表性的员工数据进行全流程调用测试：

## 85-程序出错的处理机制
> 对应分集：P85 | 原始标题：《85-程序出错的处理机制》

### 存储过程执行异常与错误处理的引入

#### 默认未捕获异常的中断现象

在前面讨论完变量的体系与应用之后，我们进入存储过程与存储函数开发中的核心保障环节——**定义条件与处理程序**。

在实际业务开发中，数据库中的数据表通常都配置了各类完整性约束。以测试数据库 `dbtest16` 中的员工表 `employees` 为例，我们先观察数据表的字段定义：

```sql
DESC employees;
```

在查看表结构时会发现，`email` 等核心字段的 `Null` 属性被显式限定为 `NO`，即配置了非空约束（`NOT NULL`）。倘若在没有任何保护机制的场景下，执行如下单列插入语句：

```sql
INSERT INTO employees(last_name) 
VALUES('Tom');
```

执行引擎会立即拦截该操作并抛出错误提示：

```text
ERROR 1048 (23000): Column 'email' cannot be null
```

如果在普通的交互式客户端（如 SQLyog 或终端）中执行单条 SQL，出现报错仅仅是该条 SQL 执行失败；但在存储过程或存储函数中，情况会完全不同。如果一个包含数十行核心业务逻辑的存储过程在运行到中途时触发了类似的数据异常，MySQL 的默认处理机制是什么？

> **结论**：在默认情况下，存储过程或存储函数执行过程中一旦遭遇任何未捕获的错误（Error），执行引擎会**立刻强行终止整个程序的运行**，并直接向调用方抛出错误代码，后续的所有业务逻辑将被全部截断。

为了直观量化这种中断，我们可以编写一个带有探针变量的无防护存储过程：

```sql
DELIMITER //

CREATE PROCEDURE UpdateDataNoCondition()
BEGIN
    -- 探针 1：进入程序起始段
    SET @x = 1;
    
    -- 触发 1048 非空异常：尝试将 Albert 的 email 篡改为 NULL
    UPDATE employees 
    SET email = NULL 
    WHERE last_name = 'Albert';
    
    -- 探针 2：理论上的第二阶段
    SET @x = 2;
    
    UPDATE employees 
    SET email = 'aaa' 
    WHERE last_name = 'Albert';
    
    -- 探针 3：理论上的终点阶段
    SET @x = 3;
END //

DELIMITER ;
```

调用该存储过程后观察其行为：

```sql
CALL UpdateDataNoCondition();
-- 执行报错：ERROR 1048 (23000): Column 'email' cannot be null

SELECT @x;
```

查询结果显示会话变量 `@x` 的数值为 `1`。这表明由于在执行第一条 `UPDATE` 时触发了非空约束冲突，程序在探针 1 之后便被硬性中断，探针 2、第二条更新语句以及探针 3 均未获得执行机会。

```text
+-------------------------------------------------------------------+
| 默认无保护执行流状态转移图                                          |
+-------------------------------------------------------------------+
|  [CALL]                                                           |
|    ↓                                                              |
|  SET @x = 1; (执行成功，@x = 1)                                    |
|    ↓                                                              |
|  UPDATE employees SET email = NULL ...                            |
|    ↓ (违反 NOT NULL 约束)                                          |
|  [抛出 ERROR 1048 (23000)] ───> 发生致命中断，退出程序             |
|    × (以下逻辑被永久截断)                                          |
|  SET @x = 2;                                                      |
|  UPDATE employees SET email = 'aaa' ...                           |
|  SET @x = 3;                                                      |
+-------------------------------------------------------------------+
```

#### 引入异常处理机制的工程价值与双环节设计

如果大家接触过 Java 等现代高级面向对象编程语言，一定对异常处理体系印象深刻。在 Java 中，语言层面封装了健全的异常类型层次树（如 `Exception`、`Error`、`RuntimeException`），并配备了诸如 `try-catch-finally`、`throws`、`throw` 等严密的控制机制，允许程序在发生意外故障时具备降级、容灾与状态恢复的能力。

一个真正具备工程可用性的数据库后端逻辑，绝不能任由底层异常无序穿透。为了保障存储过程与函数在生产环境下的高健壮性（Robustness），MySQL 提供了原生的错误处理机制。该机制解耦为两个核心步骤：

1. **定义条件（Declare Condition）**：事先为程序执行过程中可能遭遇的具体错误或警告设定具有语义化的标识符（起别名），将抽象晦涩的代码转换为“见名知意”的符号。
2. **定义处理程序（Declare Handler）**：为特定条件（或底层原始错误码）预先指定应对策略（是带病坚持继续推进，还是优雅记录后退场），并绑定相应的补救动作（例如重置状态标志、记入审计日志或触发级联回退）。

```text
+-------------------------------------------------------------------+
| MySQL 错误处理体系架构                                             |
+-------------------------------------------------------------------+
|                                                                   |
|  1. 定义条件 (可选，增加可读性)                                    |
|     DECLARE condition_name CONDITION FOR error_code/sqlstate;     |
|                            │                                      |
|                            ▼                                      |
|  2. 定义处理程序 (核心，决定流向与操作)                            |
|     DECLARE {CONTINUE | EXIT} HANDLER FOR condition_name          |
|     SET @state_var = -1;                                          |
|                                                                   |
+-------------------------------------------------------------------+
```

> **提示**：定义条件与定义处理程序在 MySQL 的**存储过程（Stored Procedure）**与**存储函数（Stored Function）**中均得到原生支持。

#### MySQL 错误代码的双轨制：错误码与状态码

在配置错误处理之前，必须首先理解 MySQL 错误信息的本质构成。无论在客户端还是在命令行控制台，MySQL 输出的每一条错误信息都包含两套并行的错误标识符：

```text
ERROR 1048 (23000): Column 'email' cannot be null
──┬── ─┬──  ─┬───   ───────────────┬─────────────
  │    │     │                     │
  │    │     │                     └─> 错误描述文本 (Error Message)
  │    │     └───────────────────────> ANSI SQL 标准状态码 (sqlstate_value)
  │    └─────────────────────────────> MySQL 专有错误码 (mysql_error_code)
  └──────────────────────────────────> 错误等级 (Error Level)
```

这两套错误标识代码的特性与对比如下：

| 标识维度 | `mysql_error_code` | `sqlstate_value` |
| :--- | :--- | :--- |
| **代码本质** | MySQL 内部专属定义的错误代号 | 符合 ANSI SQL 与 ODBC 标准的国际规范状态码 |
| **数据类型** | 数值型（Integer） | 定长 5 位的字符串型（CHAR(5)） |
| **典型示例** | `1048`、`1062`、`1148`、`1364` | `'23000'`、`'42000'`、`'HY000'` |
| **跨系统兼容** | 仅适用于 MySQL 自身体系 | 具备通用标准语义，便于跨数据库栈识别 |

在捕获错误时，无论使用专有的数值型 `mysql_error_code`，还是标准字符串型 `sqlstate_value`，均能够准确指向该异常事件。

### 第一环节：定义条件（DECLARE CONDITION）

#### 定义条件的语法规则与参数规范

定义条件的核心意图是将一个抽象的数字或代码关联到一个人类可读的名称上，从而提升后续存储代码的可读性与可维护性。

##### 语法格式

```sql
DECLARE condition_name CONDITION FOR condition_value;

-- condition_value 的合法形式：
-- 形式 1 (数值型): mysql_error_code
-- 形式 2 (字符串型): SQLSTATE [VALUE] sqlstate_value
```

##### 参数规范与关键约束
- **`condition_name`**：自定义的条件名称，命名必须见名知意（例如 `Field_Not_Be_NULL`、`duplicate_entry`），避免使用含糊不清的代号。
- **`mysql_error_code`**：直接填写对应错误的整数值，不需要加引号。
- **`SQLSTATE [VALUE] sqlstate_value`**：必须显式声明 `SQLSTATE` 关键字（`VALUE` 可选省略），其后跟 5 位定长字符串。必须携带单引号包裹。

> **注意**：如果使用字符串型的状态码，必须显式书写 `SQLSTATE` 引导词。若省略该关键字直接书写字符串或数字，解析器将无法正确辨识其类型归属，甚至引发隐式转换报错或语义分歧。

#### 课堂例题解析：非空约束与非法指令的条件命名

##### 【例题 1】为违反非空约束错误定义条件名
针对 MySQL 中字段赋值为 `NULL` 触发的 `ERROR 1048 (23000)` 异常，定义名为 `Field_Not_Be_NULL` 的错误条件。

- **写法一（基于 `mysql_error_code` 数值码）**：
  ```sql
  DECLARE Field_Not_Be_NULL CONDITION FOR 1048;
  ```
- **写法二（基于 `sqlstate_value` 字符串状态码）**：
  ```sql
  DECLARE Field_Not_Be_NULL CONDITION FOR SQLSTATE '23000';
  ```

##### 【例题 2】为客户端非法命令错误定义条件名
针对执行当前 MySQL 版本不支持的指令所触发的 `ERROR 1148 (42000)` 异常，定义名为 `command_not_allowed` 的错误条件。

- **写法一（基于 `mysql_error_code` 数值码）**：
  ```sql
  DECLARE command_not_allowed CONDITION FOR 1148;
  ```
- **写法二（基于 `sqlstate_value` 字符串状态码）**：
  ```sql
  DECLARE command_not_allowed CONDITION FOR SQLSTATE '42000';
  ```

### 第二环节：定义处理程序（DECLARE HANDLER）

#### 处理程序的完整声明语法与位置约定

定义处理程序是错误应对机制的落脚点。它指定了当程序在执行中捕捉到指定类型的问题时，应该以何种流向策略继续运转，以及执行何种具体的补救操作。

##### 语法格式

```sql
DECLARE handler_action HANDLER FOR condition_value [, ...] statement;
```

##### 声明位置的刚性约束
在存储过程或函数体内，`DECLARE` 语句有着严密的书写顺序规范：
1. 局部变量声明（`DECLARE var_name ...`）
2. 条件声明（`DECLARE cond_name CONDITION ...`）
3. 游标声明（`DECLARE cur_name CURSOR ...`）
4. 处理程序声明（`DECLARE ... HANDLER FOR ...`）
5. 业务可执行 SQL 逻辑

> **易错点**：处理程序的声明必须置于程序体的头部声明区，**绝不能写在业务执行语句之后**。如果在第一条业务 SQL（如 `SET @x = 1;`）之后再去编写 `DECLARE HANDLER`，MySQL 语法解析器将直接抛出语法错误。必须“兵马未动，粮草先行”，在程序遭遇故障之前就完成应急预案的铺设。

#### 三种错误处理行为（CONTINUE、EXIT、UNDO）

`handler_action` 支持以下三种策略，分别对应不同的生命周期流向：

```text
+--------------------------------------------------------------------+
| 处理行为动作 (handler_action) 语义比喻与状态迁移                     |
+--------------------------------------------------------------------+
| 1. CONTINUE ("带病坚持工作")                                       |
|    捕获异常 ──> 执行 handler 预设 statement ──> 紧接着原出错行向下推进  |
|                                                                    |
| 2. EXIT ("请假回家休息")                                           |
|    捕获异常 ──> 执行 handler 预设 statement ──> 强行跳出当前复合语句块  |
|                                                                    |
| 3. UNDO ("撤回全部既有工作")                                        |
|    捕获异常 ──> 执行 handler 预设 statement ──> 回滚先前操作并退出      |
|    * 注：MySQL 语法层面保留了 UNDO 关键字，但底层引擎当前暂不支持该动作 |
+--------------------------------------------------------------------+
```

1. **`CONTINUE`**：表示遇到错误后不终止程序，执行完处理程序绑定的语句后，**跳过引发异常的那一行代码，继续向下执行后面的 SQL 语句**。
2. **`EXIT`**：表示遇到错误后，执行完处理程序绑定的语句，**立刻终止并跳出包含该处理程序的 `BEGIN ... END` 复合语句块**。
3. **`UNDO`**：表示遇到错误后执行回退操作。需要特别指明：虽然 SQL 标准包含此机制，但**截至当前的 MySQL 版本，尚未原生支持 `UNDO` 处理动作**。如果在代码中指定 `UNDO`，解析器会抛出不支持的异常。因此在生产实战中，我们只能在 `CONTINUE` 与 `EXIT` 之间权衡决策。

#### 六类错误类型匹配规则

`condition_value` 用于匹配具体发生的错误。它可以分为两组：三类通用匹配源与三类范围通配符。

```text
+-------------------------------------------------------------------+
| condition_value 错误匹配源分类                                    |
+-------------------------------------------------------------------+
|  [通用精准匹配]                                                   |
|    ├─ 1. mysql_error_code  (整数代码，如 1048、1062)              |
|    ├─ 2. SQLSTATE 'value'  (5位字符代码，如 '23000')              |
|    └─ 3. condition_name    (前置自定义的条件标识名)                |
|                                                                   |
|  [特定前缀与全集通配]                                              |
|    ├─ 4. SQLWARNING        (所有以 01 开头的 SQLSTATE 警告)       |
|    ├─ 5. NOT FOUND         (所有以 02 开头的 SQLSTATE 未找到状态) |
|    └─ 6. SQLEXCEPTION      (其余所有非 01、非 02 开头的致命错误)  |
+-------------------------------------------------------------------+
```

##### 通用匹配源
- **数值型 `mysql_error_code`**：直接指定具体错误编号。
  ```sql
  DECLARE CONTINUE HANDLER FOR 1048 SET @flag = -1;
  ```
- **字符型 `SQLSTATE [VALUE] sqlstate_value`**：指定标准状态码。
  ```sql
  DECLARE EXIT HANDLER FOR SQLSTATE '23000' SET @flag = -1;
  ```
- **自定义 `condition_name`**：使用通过 `DECLARE ... CONDITION` 预定义的条件名。
  ```sql
  DECLARE EXIT HANDLER FOR duplicate_entry SET @flag = -1;
  ```

> **提示**：前置的“定义条件”步骤并非必选项，它属于修饰型特性。开发者完全可以直接使用原始的 `mysql_error_code` 或 `SQLSTATE` 绑定处理程序；只有在需要对核心故障进行语义命名时，才先声明条件再挂接处理程序。

##### 宏观通配分类
- **`SQLWARNING`**：通配捕获所有以 `'01'` 开头的 `SQLSTATE` 代码（通常对应各类警告信息）。
- **`NOT FOUND`**：通配捕获所有以 `'02'` 开头的 `SQLSTATE` 代码（专用于数据查找不到的场景，尤其在游标遍历提取结束时使用）。
- **`SQLEXCEPTION`**：通配捕获除 `SQLWARNING` 和 `NOT FOUND` 之外的所有错误代码（即真正的致命异常事件）。

#### 处理语句的组织形态

`statement` 是错误捕获后所执行的动作代码：
1. **单一表达式或赋值操作**：最常见的方式是重置会话用户变量（如 `SET @proc_value = -1;`）或修改局部标记变量。
2. **复合语句块（`BEGIN ... END`）**：当需要执行多项联动动作（如记录异常堆栈、插入日志表、重设多维状态）时，可以使用完整的 `BEGIN ... END` 结构包裹多行 SQL。

### 实战案例全流程推演与机制验证

#### 案例一：非空约束冲突与 CONTINUE 容错恢复

回归第 1.1 节展示的 `UpdateDataNoCondition` 存储过程。我们在保持探针与原更新逻辑不变的前提下，为其植入错误处理程序，目标是验证 `CONTINUE` 在捕获非空约束冲突（1048）后的执行连续性。

##### 改造后的存储过程定义

```sql
-- 先行清理已存在的存储过程
DROP PROCEDURE IF EXISTS UpdateDataNoCondition;

DELIMITER //

CREATE PROCEDURE UpdateDataNoCondition()
BEGIN
    -- 核心处理程序配置：捕获 1048 错误，策略设为 CONTINUE，并将指示变量赋为 -1
    -- 方式一：直接使用数值型 mysql_error_code
    DECLARE CONTINUE HANDLER FOR 1048 SET @proc_value = -1;
    
    -- 方式二（等价写法）：基于 SQLSTATE 声明
    -- DECLARE CONTINUE HANDLER FOR SQLSTATE '23000' SET @proc_value = -1;

    -- 探针 1
    SET @x = 1;
    
    -- 此处尝试将 email 置空，必将触发 1048 异常
    UPDATE employees 
    SET email = NULL 
    WHERE last_name = 'Albert';
    
    -- 探针 2：验证 CONTINUE 是否成功跨越异常行
    SET @x = 2;
    
    UPDATE employees 
    SET email = 'aaa' 
    WHERE last_name = 'Albert';
    
    -- 探针 3：验证程序是否完整执行至末尾
    SET @x = 3;
END //

DELIMITER ;
```

##### 调用与变量探针断言

```sql
CALL UpdateDataNoCondition();

-- 检查运行结果
SELECT @x, @proc_value;
```

##### 运行结果与状态机分析
查询返回的行数据如下：

```text
+----+-------------+
| @x | @proc_value |
+----+-------------+
|  3 |          -1 |
+----+-------------+
```

```text
+-------------------------------------------------------------------+
| CONTINUE 处理机制状态迁移时序                                      |
+-------------------------------------------------------------------+
|  [CALL UpdateDataNoCondition()]                                   |
|    ↓                                                              |
|  SET @x = 1;                           --> @x 变为 1              |
|    ↓                                                              |
|  UPDATE ... SET email = NULL           --> 触发 ERROR 1048        |
|    ↓                                                              |
|  [捕获成功] 触发 CONTINUE HANDLER       --> 执行 SET @proc_value = -1|
|    ↓                                                              |
|  (跳过出错的 UPDATE，带病继续执行)                                 |
|    ↓                                                              |
|  SET @x = 2;                           --> @x 变为 2              |
|    ↓                                                              |
|  UPDATE ... SET email = 'aaa'          --> 正常执行成功           |
|    ↓                                                              |
|  SET @x = 3;                           --> @x 最终锁定为 3        |
|    ↓                                                              |
|  [正常退出存储过程]                                               |
+-------------------------------------------------------------------+
```

探针 `@x` 最终为 `3`，且 `@proc_value` 成功被赋予 `-1`。这充分证明了 `CONTINUE` 机制的特点：异常被拦截，自定义补偿语句被调用，程序没有中途崩塌，而是跨过错误指令持续推进至最后一行。

#### 案例二：唯一键冲突与 EXIT 安全终止的多种实现

在金融或核心配置场景下，一旦发生数据冲突，绝不能允许程序继续往后乱写，必须立即“安全退出（EXIT）”。我们以部门表 `departments` 的唯一性冲突场景进行全链路演示。

##### 测试环境与唯一键准备

```sql
-- 检查 departments 表结构
DESC departments;

-- 为 department_id 字段追加 UNIQUE 唯一性约束
ALTER TABLE departments 
ADD UNIQUE(department_id);
```

##### 构造无保护的插入测试存储过程

```sql
DELIMITER //

CREATE PROCEDURE InsertDepartmentDuplicate()
BEGIN
    SET @x = 1;
    
    -- 假定此处添加一条新部门记录，若主键/唯一索引发生重叠
    INSERT INTO departments(department_name) VALUES('测试部');
    
    SET @x = 2;
    
    -- 第二次插入相同数据，故意制造主键/唯一键冲突
    INSERT INTO departments(department_name) VALUES('测试部');
    
    SET @x = 3;
END //

DELIMITER ;
```

在未引入错误处理时调用该存储过程，由于第二次插入违反了唯一性约束，MySQL 抛出：

```text
ERROR 1062 (23000): Duplicate entry ... for key '...'
```

检查变量 `@x`，数值定格在 `2`，探针 3 未能执行。

##### 引入 EXIT 处理程序的三种等价实现

为了实现故障发生时“立即终止当前程序段并给调用方返回警示状态”，我们需要将处理动作设定为 `EXIT`。针对 `ERROR 1062 (23000)`，存在三种标准的实现路径：

```sql
DROP PROCEDURE IF EXISTS InsertDepartmentDuplicate;

DELIMITER //

CREATE PROCEDURE InsertDepartmentDuplicate()
BEGIN
    -- 【方式 1】：直接绑定数值型 mysql_error_code
    -- DECLARE EXIT HANDLER FOR 1062 SET @error_value = -1;

    -- 【方式 2】：直接绑定字符串型 SQLSTATE
    -- DECLARE EXIT HANDLER FOR SQLSTATE '23000' SET @error_value = -1;

    -- 【方式 3】：先显式声明条件，再由处理程序承接条件名
    DECLARE duplicate_entry CONDITION FOR 1062;
    -- 亦可写为: DECLARE duplicate_entry CONDITION FOR SQLSTATE '23000';
    DECLARE EXIT HANDLER FOR duplicate_entry SET @error_value = -1;

    SET @x = 1;
    
    INSERT INTO departments(department_name) VALUES('测试部');
    
    SET @x = 2;
    
    -- 此处插入触发 Duplicate entry 冲突
    INSERT INTO departments(department_name) VALUES('测试部');
    
    -- 因策略为 EXIT，此行绝对不会被执行
    SET @x = 3;
END //

DELIMITER ;
```

##### 运行验证与 EXIT 退出截断机理

调用改写后的存储过程：

```sql
CALL InsertDepartmentDuplicate();
-- 执行顺利完成，控制台未暴露红字异常

SELECT @x, @error_value;
```

查询结果展现为：

```text
+----+--------------+
| @x | @error_value |
+----+--------------+
|  2 |           -1 |
+----+--------------+
```

```text
+-------------------------------------------------------------------+
| EXIT 处理机制状态迁移时序                                         |
+-------------------------------------------------------------------+
|  [CALL InsertDepartmentDuplicate()]                               |
|    ↓                                                              |
|  SET @x = 1;                           --> @x = 1                 |
|    ↓                                                              |
|  INSERT INTO departments ... (第1次)   --> 执行成功               |
|    ↓                                                              |
|  SET @x = 2;                           --> @x = 2                 |
|    ↓                                                              |
|  INSERT INTO departments ... (第2次)   --> 触发 ERROR 1062 冲突   |
|    ↓                                                              |
|  [捕获成功] 触发 EXIT HANDLER           --> 执行 SET @error_value = -1|
|    ↓                                                              |
|  [立刻终止退出当前复合代码块]                                      |
|    × (后续代码全部终止)                                            |
|  SET @x = 3; (永久未执行)                                         |
+-------------------------------------------------------------------+
```

> **提示**：如果在二次执行该存储过程时，表中原本就已经残留了上一轮插入的记录，则第一条 `INSERT` 语句就会立刻触发唯一性冲突。届时捕获程序在第一条插入处就会触发 `EXIT` 并退出，导致 `@x` 停留在 `1`，而 `@error_value` 依然为 `-1`。这与业务执行前后的表内已有数据状态紧密关联。

### 本讲提到的题目与代码练习

在课堂实战中，围绕“定义条件与处理程序”的语法细节，梳理出以下核心题目与练习：

#### 题目一：定义字段非空异常条件（两种方式）
- **题干描述**：请为 MySQL 抛出的“字段不允许为 NULL”异常（错误码 `1048`，SQLSTATE 代码 `'23000'`）声明一个名为 `Field_Not_Be_NULL` 的错误条件。
- **解题依据**：依据 `DECLARE condition_name CONDITION FOR condition_value;` 语法规范，分别使用整型与字符型填入。
- **参考答案**：
  ```sql
  -- 方式 1：使用数值型 mysql_error_code
  DECLARE Field_Not_Be_NULL CONDITION FOR 1048;

  -- 方式 2：使用字符串型 sqlstate_value
  DECLARE Field_Not_Be_NULL CONDITION FOR SQLSTATE '23000';
  ```

#### 题目二：定义版本非法指令异常条件（两种方式）
- **题干描述**：请为 MySQL 抛出的“当前版本不允许使用该命令”异常（错误码 `1148`，SQLSTATE 代码 `'42000'`）声明一个名为 `command_not_allowed` 的错误条件。
- **解题依据**：同题目一，重点掌握 `SQLSTATE` 关键字对字符型代码的引导作用。
- **参考答案**：
  ```sql
  -- 方式 1：使用数值型 mysql_error_code
  DECLARE command_not_allowed CONDITION FOR 1148;

  -- 方式 2：使用字符串型 sqlstate_value
  DECLARE command_not_allowed CONDITION FOR SQLSTATE '42000';
  ```

#### 题目三：六类错误处理程序的声明语法匹配
- **题干描述**：请列举出 `DECLARE ... HANDLER FOR ...` 在处理语句统一设定为用户变量赋值（`SET @flag = -1;`）的前提下，能够使用的六种错误类型匹配形态。
- **解题依据**：通用三类（SQLSTATE、mysql_error_code、自定义条件名）与特殊三类（SQLWARNING、NOT FOUND、SQLEXCEPTION）。
- **参考答案**：
  ```sql
  -- 1. 匹配特定 SQLSTATE
  DECLARE CONTINUE HANDLER FOR SQLSTATE '42000' SET @flag = -1;

  -- 2. 匹配特定 mysql_error_code
  DECLARE CONTINUE HANDLER FOR 1148 SET @flag = -1;

  -- 3. 匹配自定义条件名 (假设前置已定义 command_not_allowed)
  DECLARE CONTINUE HANDLER FOR command_not_allowed SET @flag = -1;

  -- 4. 匹配以 01 开头的所有 SQLSTATE (警告)
  DECLARE EXIT HANDLER FOR SQLWARNING SET @flag = -1;

  -- 5. 匹配以 02 开头的所有 SQLSTATE (未检索到)
  DECLARE EXIT HANDLER FOR NOT FOUND SET @flag = -1;

  -- 6. 匹配既非 01 也非 02 开头的所有错误 (异常)
  DECLARE EXIT HANDLER FOR SQLEXCEPTION SET @flag = -1;
  ```

## 86-分支结构IF的使用
> 对应分集：P86 | 原始标题：《86-分支结构IF的使用》

### 流程控制结构的总览与分支结构的定位

#### 程序的顺序、分支与循环三大结构

在探讨完存储过程中的异常处理之后，我们正式进入存储程序（存储过程与存储函数）的核心逻辑构建部分——**流程控制（Control Flow）**。

任何现代编程语言都离不开对程序执行流向的调度与组织。从计算机程序的本质来看，所有复杂的业务算法均由三种基础逻辑结构复合而成：

```text
+--------------------------------------------------------------------+
| 程序控制流三大基本逻辑结构                                          |
+--------------------------------------------------------------------+
| 1. 顺序结构 (Sequential)                                           |
|    [语句 1] ──> [语句 2] ──> [语句 3] (自上而下逐行执行)             |
|                                                                    |
| 2. 分支结构 (Selection / Branch)                                   |
|               ┌─ 条件真 ─> [操作 A] ──┐                            |
|    [条件判断] ┤                       ├─> [后续汇合节点]            |
|               └─ 条件假 ─> [操作 B] ──┘                            |
|                                                                    |
| 3. 循环结构 (Iteration / Loop)                                     |
|    ┌──> [条件判断] ── 满足 ──> [循环操作体] ──┐                    |
|    │          │                               │                    |
|    │          └────── 不满足 ─────────────────┴──> [退出循环]       |
|    └──────────────────────────────────────────┘                    |
+--------------------------------------------------------------------+
```

1. **顺序结构**：这是最普遍的执行流，程序默认严格按照编写的先后顺序，自上而下、逐行执行。在此前编写的大多数基础存储过程内部，语句均依照顺序推进。
2. **分支结构**：在程序执行链路中引入逻辑判断点，根据输入参数或上下文状态计算得出的真假结果，动态决定执行路径。这包括二选一的抉择场景（例如工业质检流水线中，零件抽检尺寸合格则流入装配线，不合格则流入返修线），以及更为复杂的多选一分级场景。
3. **循环结构**：当某些计算逻辑需要被重复执行多次时，将其置入循环控制体。例如工件在特定工艺环节需要经历多次清洗与检验，每次达到特定计数或状态门槛后再跳出循环。

#### MySQL 流程控制体系与语句分类

针对分支与循环这两大非顺序控制流，MySQL 的过程化 SQL（Procedural SQL）提供了完备的关键字支持：

| 控制类别 | 实现机制 | 关键字与结构 | 适用场景说明 |
| :--- | :--- | :--- | :--- |
| **分支结构** | 条件分支判断 | `IF ... THEN ... ELSEIF ... ELSE ... END IF;` | 基于连续区间或布尔表达式的分流判断 |
| | 多路选择匹配 | `CASE ... WHEN ... THEN ... ELSE ... END CASE;` | 类似 Switch 语法的离散值匹配或条件匹配 |
| **循环结构** | 无条件死循环 | `[loop_label:] LOOP ... END LOOP [loop_label];` | 最底层的死循环，必须配合跳出语句使用 |
| | 先验条件循环 | `[while_label:] WHILE ... DO ... END WHILE;` | 相当于 C/Java 中的 `while`，先判断再执行 |
| | 后验条件循环 | `[repeat_label:] REPEAT ... UNTIL ... END REPEAT;` | 相当于 `do-while`，先执行一次，满足条件则退出 |
| **跳转控制** | 跳出循环体 | `LEAVE label;` | 等价于高级语言中的 `break`，彻底退出指定循环块 |
| | 迭代下一轮 | `ITERATE label;` | 等价于高级语言中的 `continue`，跳过本轮直接进入下一次循环 |

> **注意**：此处讨论的所有流程控制语句（`IF`、`CASE`、`LOOP`、`WHILE`、`REPEAT`、`LEAVE`、`ITERATE`），**只能编写在存储过程、存储函数或触发器的 `BEGIN ... END` 复合代码块内部**。绝不能像单行函数那样直接书写在交互式的普通 `SELECT` 顶层查询中。

### 分支结构 IF 的语法规则与逻辑分型

#### 复合语句中 IF 的基础语法框架

需要首先澄清一个初学者极易混淆的概念：MySQL 中存在两种截然不同的 `IF`。
- 一种是内置的**控制流单行函数**：`IF(expr1, expr2, expr3)`，类似于三元运算符 `expr1 ? expr2 : expr3`，它是一个带返回值的表达式，常用于 `SELECT` 字段列表中；
- 另一种则是本讲深入讲解的**过程化流程控制语句**：`IF ... THEN ... END IF;`，它是一个包含完整控制结构的语句块，用来组织命令执行路径。

过程化 `IF` 语句的完整语法模板如下：

```sql
IF search_condition_1 THEN
    statement_list_1;
[ELSEIF search_condition_2 THEN
    statement_list_2;] ...
[ELSE
    statement_list_n;]
END IF;
```

##### 语法规则与解析细节
1. **`search_condition` 判定机制**：每个条件表达式返回布尔值 `TRUE`、`FALSE` 或 `NULL`。只有当表达式严格求值为 `TRUE` 时，才会命中对应的 `THEN` 语句体。
2. **短路跳出特性**：从上至下按顺序计算条件，**一旦命中首个为 `TRUE` 的分支并执行完毕后，程序将立即跳出整个 `IF` 结构**，后续的所有 `ELSEIF` 和 `ELSE` 将被全部短路跳过。
3. **`ELSEIF` 拼写硬性约束**：在 MySQL 过程化语法中，中间的多分支关键字必须严密拼写为 **`ELSEIF`（中间无空格）**。在 Java 或 Python 等高级语言中常习惯写作 `else if` 或 `elif`，但在 MySQL 中若将 `ELSE` 与 `IF` 拆分为两个单词，解析器会将其错误理解为一个嵌套的内层 `IF` 起始，直接导致语法报错（Syntax Error）。
4. **语句块闭合标记**：整个结构的最外层必须使用 `END IF;` 作为结束标识符，分号不可遗漏。

```text
+-------------------------------------------------------------------+
| IF 分支结构多路执行流向图                                          |
+-------------------------------------------------------------------+
|  [进入 IF 结构]                                                   |
|    │                                                              |
|    ▼                                                              |
|  <条件 1 为真？> ─── 是 ───> [执行 语句 1] ──┐                     |
|    │ 否                                      │                    |
|    ▼                                         │                    |
|  <条件 2 为真？> ─── 是 ───> [执行 语句 2] ──┤                    |
|    │ 否                                      │                    |
|    ▼                                         │                    |
|  <条件 3 为真？> ─── 是 ───> [执行 语句 3] ──┤                    |
|    │ 否                                      │                    |
|    ▼                                         │                    |
|  [执行 ELSE 默认语句] ────────────────────────┤                    |
|                                              ▼                    |
|                                      [跳出 END IF 结构]           |
+-------------------------------------------------------------------+
```

#### 三大典型分支形态的代码演进

为了彻底理清该语句的组织形式，我们从无到有构建三个渐进式测试场景。

##### 形态一：单分支条件判断（命中则行，未命中即过）
仅包含 `IF ... THEN ... END IF;`。适用于“只有满足某条件才需要做特殊操作，否则维持现状”的场景：

```sql
DELIMITER //

CREATE PROCEDURE test_if_01()
BEGIN
    -- 声明局部变量，未赋初值，默认值为 NULL
    DECLARE stu_name VARCHAR(15);
    
    IF stu_name IS NULL THEN
        SELECT 'stu_name is null';
    END IF;
END //

DELIMITER ;

CALL test_if_01();
```
*执行结果*：控制台输出字符串 `'stu_name is null'`。

##### 形态二：双分支二选一（IF ... ELSE）
包含 `IF ... THEN ... ELSE ... END IF;`。适用于二元对立的互斥场景：

```sql
DELIMITER //

CREATE PROCEDURE test_if_02()
BEGIN
    DECLARE email VARCHAR(25);
    -- 若指定 DEFAULT 'abc@163.com'，则流向会反转
    
    IF email IS NULL THEN
        SELECT 'email is null';
    ELSE
        SELECT 'email is not null';
    END IF;
END //

DELIMITER ;

CALL test_if_02();
```
*执行机制*：由于 `email` 未初始化，其值为 `NULL`，命中主分支输出 `'email is null'`；若通过 `DEFAULT` 初始化变量，则该分支为假，执行流必将且只能落入 `ELSE` 分支输出 `'email is not null'`。

##### 形态三：多路级联分支（IF ... ELSEIF ... ELSE）
包含多个连续判断区间，适用于多档位评级：

```sql
DELIMITER //

CREATE PROCEDURE test_if_03()
BEGIN
    DECLARE age INT DEFAULT 20;
    
    IF age > 40 THEN
        SELECT '中老年';
    ELSEIF age > 18 THEN
        SELECT '青壮年';
    ELSEIF age > 8 THEN
        SELECT '青少年';
    ELSE
        SELECT '婴幼儿';
    END IF;
END //

DELIMITER ;

CALL test_if_03();
```
*执行推导*：
- 探针变量 `age` 为 20；
- 第一个条件 `age > 40` 评估为 `FALSE`，继续推进；
- 第二个条件 `age > 18` 评估为 `TRUE`，命中分支，立即执行 `SELECT '青壮年'`；
- 命中后直接短路跳出，后续的 `age > 8` 及 `ELSE` 不会再被扫描。

### 生产级实战案例：结合数据表的动态薪资与职级调整

在实际业务中，我们很少在存储过程内部仅仅 `SELECT` 打印常量，而是需要结合数据表中的现有字段，进行动态计算、逻辑判定，并最终把决策结果反写回数据库表（执行 `UPDATE`）。

以下三个案例均围绕员工信息表 `employees` 展开。

#### 案例一：单分支考核与低收入资深员工调薪

##### 业务需求描述
创建存储过程 `update_salary_by_eid1`，接收一个输入参数 `emp_id`（员工工号）。
- 逻辑要求：判断该员工的当前薪资水平与工龄。若该员工的**薪资低于 8000 元，且在公司的入职时间已超过 5 年**，则为其基本薪资增加 500 元；
- 若不满足该组合条件，则**薪资保持原样不变**。

##### 关键技术点突破
1. **如何计算入职年限**：
   MySQL 提供了天数差函数 `DATEDIFF(expr1, expr2)`，其运算逻辑为 `expr1 - expr2`。我们将当前日期函数 `CURDATE()` 置于首位，员工入职日期 `hire_date` 置于次位，计算得出相隔的总天数，再除以 `365`，即可换算出工龄年数：
   $$\text{工龄（年）} = \frac{\text{DATEDIFF}(\text{CURDATE}(), \text{hire\_date})}{365}$$
2. **数据的提取与绑定**：
   使用 `SELECT ... INTO ... FROM employees WHERE ...` 将目标单行字段值直接注入到预先声明的局部变量中。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_by_eid1(IN emp_id INT)
BEGIN
    -- 1. 声明承接业务指标的局部变量
    DECLARE emp_sal DOUBLE;    -- 记录员工当前的薪资
    DECLARE hire_year DOUBLE;  -- 记录员工在职的实际年限
    
    -- 2. 查询并给局部变量动态赋值
    SELECT salary INTO emp_sal 
    FROM employees 
    WHERE employee_id = emp_id;
    
    SELECT DATEDIFF(CURDATE(), hire_date) / 365 INTO hire_year 
    FROM employees 
    WHERE employee_id = emp_id;
    
    -- 3. 逻辑分支判定
    IF emp_sal < 8000 AND hire_year > 5 THEN
        UPDATE employees 
        SET salary = salary + 500 
        WHERE employee_id = emp_id;
    END IF;
    -- 若不满足条件，不作任何操作，直接平稳结束
END //

DELIMITER ;
```

##### 调用与数据断言验证
我们选取数据库中一名薪资低于 8000 且入职早于 5 年前的员工进行实测：

```sql
-- 检索目标员工执行前的基准数据
SELECT employee_id, salary, hire_date, DATEDIFF(CURDATE(), hire_date)/365 AS years
FROM employees 
WHERE employee_id = 104;
-- 假设 104 号员工执行前：salary 为 6000.00，years 约为 8.2 年

-- 调用存储过程触发调薪
CALL update_salary_by_eid1(104);

-- 验证更新结果
SELECT employee_id, salary 
FROM employees 
WHERE employee_id = 104;
-- 断言输出：salary 变为 6500.00，涨薪 500 元逻辑执行成功。
```

#### 案例二：双分支调薪考核与普惠兜底

##### 业务需求描述
创建存储过程 `update_salary_by_eid2`，输入参数仍为 `emp_id`。
- 逻辑要求：
  - 若该员工**薪资低于 9000 元，且工龄超过 5 年**，则薪资上调 500 元；
  - 否则（其余所有未达标人员），实行普惠性微调，**薪资一律上调 100 元**。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_by_eid2(IN emp_id INT)
BEGIN
    DECLARE emp_sal DOUBLE;
    DECLARE hire_year DOUBLE;
    
    SELECT salary INTO emp_sal 
    FROM employees 
    WHERE employee_id = emp_id;
    
    SELECT DATEDIFF(CURDATE(), hire_date) / 365 INTO hire_year 
    FROM employees 
    WHERE employee_id = emp_id;
    
    -- 二选一分支逻辑
    IF emp_sal < 9000 AND hire_year > 5 THEN
        UPDATE employees 
        SET salary = salary + 500 
        WHERE employee_id = emp_id;
    ELSE
        UPDATE employees 
        SET salary = salary + 100 
        WHERE employee_id = emp_id;
    END IF;
END //

DELIMITER ;
```

##### 多元样本比对验证
我们选取两位具有对比特性的员工执行测试：
1. **员工 103**：基准薪资为 9000 元（不满足 `< 9000` 门槛），预期走 `ELSE` 分支，调增 100 元；
2. **员工 104**：基准薪资为 6500 元且工龄 > 5 年，满足主分支，预期调增 500 元。

```sql
-- 1. 查看基准数据
SELECT employee_id, salary FROM employees WHERE employee_id IN (103, 104);

-- 2. 依次调用
CALL update_salary_by_eid2(103);
CALL update_salary_by_eid2(104);

-- 3. 查看最终结果
SELECT employee_id, salary FROM employees WHERE employee_id IN (103, 104);
```
*结果输出*：
- 103 员工薪资从 9000.00 变更为 9100.00（+100）；
- 104 员工薪资从 6500.00 变更为 7000.00（+500）。两个分支各司其职，验证通过。

#### 案例三：多分支综合调级与空值约束处理

##### 业务需求描述
创建存储过程 `update_salary_by_eid3`，输入参数为 `emp_id`。引入更为复杂的薪资与奖金提成率组合评级规则：
1. **第一档**：若薪资严格**低于 9000 元**，则直接将该员工的薪资重置调高为 9000 元；
2. **第二档**：若薪资处于 **[9000, 10000)** 之间，且其原先的**奖金率（`commission_pct`）为 NULL**，则将其奖金率更新为 `0.01`（补齐基础提成资格）；
3. **兜底档（ELSE）**：其余情况，将员工薪资在原有基础上增加 100 元。

##### 关键约束与设计考量
- 字段识别：`commission_pct` 在表结构中允许为 `NULL`，在 SQL 逻辑判断时必须严密使用 `IS NULL`，切禁写成 `= NULL`；
- 阶梯设计：进入 `ELSEIF` 分支时，由于第一道门槛 `salary < 9000` 已经被排除，因此进入第二档时系统天然满足 `salary >= 9000`，在代码中只需聚焦编写 `salary < 10000` 即可，体现了逻辑剪枝的严密性。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_by_eid3(IN emp_id INT)
BEGIN
    -- 1. 声明局部变量
    DECLARE emp_sal DOUBLE;
    DECLARE bonus DOUBLE;
    
    -- 2. 获取目标员工的当前指标
    SELECT salary INTO emp_sal 
    FROM employees 
    WHERE employee_id = emp_id;
    
    SELECT commission_pct INTO bonus 
    FROM employees 
    WHERE employee_id = emp_id;
    
    -- 3. 多分支阶梯裁决
    IF emp_sal < 9000 THEN
        -- 档位 1：直接保底设定为 9000
        UPDATE employees 
        SET salary = 9000 
        WHERE employee_id = emp_id;
        
    ELSEIF emp_sal < 10000 AND bonus IS NULL THEN
        -- 档位 2：薪资在 [9000, 10000) 且无提成，给予基础提成率
        UPDATE employees 
        SET commission_pct = 0.01 
        WHERE employee_id = emp_id;
        
    ELSE
        -- 档位 3：其余所有员工普调 100 元
        UPDATE employees 
        SET salary = salary + 100 
        WHERE employee_id = emp_id;
        
    END IF;
END //

DELIMITER ;
```

##### 覆盖性测试用例与状态验证
为了检验每一个逻辑分支的正确性，我们针对三个分支分别构造对应的样本：

| 员工工号 | 执行前状态 | 命中的分支逻辑 | 执行后预期状态 |
| :--- | :--- | :--- | :--- |
| **104 号** | `salary = 7000`（`< 9000`） | 档位 1（主 IF） | `salary` 跃升重置为 `9000.00` |
| **103 号** | `salary = 9100`，`commission_pct IS NULL` | 档位 2（ELSEIF） | `salary` 保持不变，`commission_pct` 变为 `0.01` |
| **102 号** | `salary = 17000`（高薪资阶层） | 档位 3（兜底 ELSE）| `salary` 递增 100 变为 `17100.00` |

```sql
-- 查看基准数据状态
SELECT employee_id, salary, commission_pct 
FROM employees 
WHERE employee_id IN (102, 103, 104);

-- 依次发起调用
CALL update_salary_by_eid3(104);
CALL update_salary_by_eid3(103);
CALL update_salary_by_eid3(102);

-- 查验执行后的数据快照
SELECT employee_id, salary, commission_pct 
FROM employees 
WHERE employee_id IN (102, 103, 104);
```
实测输出与推演预期完全一致，验证了复合 `IF ... ELSEIF ... ELSE` 在真实复杂业务流中的可靠性。

### 常见误区与避坑指南

在编写 MySQL 过程化 `IF` 语句时，开发者最常踩的坑主要集中在语法规则和运行边界上：

```text
+-------------------------------------------------------------------+
| IF 分支语法常见错误对照表                                          |
+-------------------------------------------------------------------+
| 错误类型       | 错误书写习惯            | 正确规范写法             |
+----------------+-------------------------+--------------------------+
| 关键字连写错误 | ELSE IF (拆分写法)       | ELSEIF (紧凑连写)        |
| 结束标记缺失   | 遗漏 END IF; 直接写 END  | 必须显式书写 END IF;     |
| 空值判定错误   | commission_pct = NULL   | commission_pct IS NULL   |
| 作用域混淆     | 在顶级 SELECT 中写 IF   | 仅能在 BEGIN...END 块内  |
+-------------------------------------------------------------------+
```

> **易错点**：
> 1. **切勿把 `ELSEIF` 拆成两个单词**。在很多高级语言编译习惯下，拆开是合法的，但在 MySQL 语法解析器中，`ELSE IF` 会被判定为在 `ELSE` 分支内部强行启动了一个尚未闭合的子 `IF` 语句，导致在最后的 `END IF;` 处抛出 `Unterminated statement` 类似语法报错。
> 2. **`UPDATE` 一定要带 `WHERE` 条件**。在存储过程中书写数据修改语句时，务必将局部输入参数 `emp_id` 严格绑定在 `WHERE employee_id = emp_id` 限制条件中。若不慎漏掉过滤子句，将引发严重的“全表数据误改”生产事故。

## 87-分支结构CASE的使用
> 对应分集：P87 | 原始标题：《87-分支结构CASE的使用》

### 过程化 CASE 语句与查询 CASE 表达式的辨析

在上一讲中，我们详细剖析了分支结构中的 `IF` 语句。而在实际开发中，当面临多个等值条件判断或者多档位分级评估时，除了使用级联的 `ELSEIF`，MySQL 还提供了另一种非常经典且语义清晰的分支语法——**`CASE` 语句**。

很多同学在初次接触过程化 SQL（Procedural SQL）中的 `CASE` 时，容易把它与之前在 `SELECT` 基础查询中学过的 `CASE` 表达式混为一谈。这两者虽然关键字相同，但在底层语义、作用域以及语法闭合上存在本质区别：

```text
+--------------------------------------------------------------------+
| 查询级 CASE 表达式 vs 过程化 CASE 语句对比                          |
+--------------------------------------------------------------------+
| 1. 查询级 CASE 表达式 (Expression)                                  |
|    SELECT col,                                                     |
|           CASE col WHEN 1 THEN '一' ELSE '其他' END AS alias       |
|    FROM table;                                                     |
|    * 作用：纯计算表达式，返回一个标量计算值; 结束标志为 END; 没有分号 |
|                                                                    |
| 2. 过程化 CASE 流程控制语句 (Statement)                             |
|    BEGIN                                                           |
|        CASE expr                                                   |
|            WHEN 1 THEN UPDATE ...;                                 |
|            ELSE INSERT ...;                                        |
|        END CASE;                                                   |
|    END;                                                            |
|    * 作用：组织命令执行路径，THEN 后跟可执行 SQL 语句块;              |
|           结束标志必须为 END CASE;; 每条分支语句必须带分号            |
+--------------------------------------------------------------------+
```

| 比较维度 | 查询级 `CASE` 表达式 | 过程化 `CASE` 语句 |
| :--- | :--- | :--- |
| **本质定位** | 标量计算表达式（返回一个单一值） | 流程控制语句（调度多条可执行 SQL） |
| **使用环境** | 交互式 `SELECT` 列表、`WHERE`、`ORDER BY` 等 | 存储过程、存储函数、触发器的 `BEGIN ... END` 块内部 |
| **`THEN` 后续内容** | 单一表达式或字面量（如 `'及格'`、`salary * 1.1`） | 完整可执行的 SQL 语句（如 `UPDATE`、`SET`、`INSERT`） |
| **分号要求** | `THEN` 后面严禁加分号，整体不以分号结尾 | 每个分支内的语句**必须显式加分号**结尾 |
| **结束关键字** | 以 **`END`** 闭合 | 必须以 **`END CASE;`** 显式闭合 |

> **注意**：如果在存储过程内部编写过程化 `CASE` 控制流，最末尾必须书写 `END CASE;`。若只写了 `END`，解析器会将其视作未闭合的语法错误，这是初学者非常容易踩中的第一个坑。

### 过程化 CASE 语句的两种语法模式

过程化 `CASE` 语句完全沿袭了高级编程语言中“多路选择”的设计哲学，并同时兼顾了“简单等值选择”与“复杂条件裁决”两种模式。

```text
+-------------------------------------------------------------------+
| 过程化 CASE 语句的两种形态分类                                    |
+-------------------------------------------------------------------+
| 模式一：等值匹配模式 (类似 Java / C 的 switch-case)                 |
|   CASE 变量或表达式                                                |
|       WHEN 常量值 1 THEN 语句 1;                                  |
|       WHEN 常量值 2 THEN 语句 2;                                  |
|       ELSE 兜底语句;                                              |
|   END CASE;                                                       |
|                                                                   |
| 模式二：条件搜索模式 (类似多重 IF-ELSEIF-ELSE)                     |
|   CASE                                                            |
|       WHEN 布尔条件表达式 1 THEN 语句 1;                           |
|       WHEN 布尔条件表达式 2 THEN 语句 2;                           |
|       ELSE 兜底语句;                                              |
|   END CASE;                                                       |
+-------------------------------------------------------------------+
```

#### 模式一：简单等值匹配（类似 switch-case）

##### 语法结构

```sql
CASE case_value
    WHEN when_value1 THEN statement_list1;
    [WHEN when_value2 THEN statement_list2;] ...
    [ELSE statement_list;]
END CASE;
```

##### 执行机理
1. 计算主干上的 `case_value` 表达式的值；
2. 依次与各个 `WHEN` 后面的 `when_value` 进行等值比较（`=`）；
3. 一旦发现相等的分支，立即执行对应 `THEN` 后面的语句列表，并在执行完毕后跳出整个 `END CASE;`；
4. 若全部匹配失败，且声明了 `ELSE`，则执行 `ELSE` 下的兜底语句。

> **易错点**：如果在模式一中**省略了 `ELSE` 分支**，并且传入的 `case_value` 在所有 `WHEN` 选项中均没有命中，MySQL 将抛出运行时异常：`ERROR 1339 (20000): Case not found for CASE statement`，导致整个存储程序意外崩溃！因此在工程规范中，**强烈建议无论何时都显式书写 `ELSE` 兜底分支**。

#### 模式二：条件搜索匹配（类似多重 IF-ELSEIF）

##### 语法结构

```sql
CASE
    WHEN search_condition1 THEN statement_list1;
    [WHEN search_condition2 THEN statement_list2;] ...
    [ELSE statement_list;]
END CASE;
```

##### 执行机理
1. `CASE` 关键字后不挂接任何变量或表达式；
2. 自上而下计算每个 `WHEN` 后面的布尔表达式 `search_condition`；
3. 只要某一个表达式计算结果为 `TRUE`，立刻执行其对应的 `statement_list` 并跳出整个结构；
4. 同样，若无任何条件满足且未编写 `ELSE`，系统亦会抛出 `ERROR 1339` 异常。

### 业务实战与案例深度演练

为了在真实数据表场景下对比这两种模式的优劣与应用边界，我们基于员工表 `employees` 进行业务案例的推演。

#### 案例一：基于条件搜索模式的多档位调薪与奖金更新

在很多业务规则中，划分标准属于连续的数值区间（如薪资区间）以及复合条件（如结合空值判断）。这种场景天然契合模式二（条件搜索匹配）。

##### 业务需求描述
创建存储过程 `update_salary_by_eid4(IN emp_id INT)`，输入参数为员工工号。
- 逻辑要求：
  1. 若该员工薪资低于 9000 元，则将其薪资直接更新为 9000 元；
  2. 若该员工薪资在 `[9000, 10000)` 之间，且其奖金提成率（`commission_pct`）为 `NULL`，则将其提成率修改为 `0.01`；
  3. 其余所有员工，薪资在原有基础上增加 100 元。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_by_eid4(IN emp_id INT)
BEGIN
    -- 1. 声明承接业务指标的局部变量
    DECLARE emp_sal DOUBLE;
    DECLARE bonus DOUBLE;
    
    -- 2. 检索当前员工的数据并赋值
    SELECT salary INTO emp_sal 
    FROM employees 
    WHERE employee_id = emp_id;
    
    SELECT commission_pct INTO bonus 
    FROM employees 
    WHERE employee_id = emp_id;
    
    -- 3. 使用条件搜索模式的 CASE 语句
    CASE
        WHEN emp_sal < 9000 THEN
            UPDATE employees 
            SET salary = 9000 
            WHERE employee_id = emp_id;
            
        WHEN emp_sal < 10000 AND bonus IS NULL THEN
            UPDATE employees 
            SET commission_pct = 0.01 
            WHERE employee_id = emp_id;
            
        ELSE
            UPDATE employees 
            SET salary = salary + 100 
            WHERE employee_id = emp_id;
    END CASE;
END //

DELIMITER ;
```

##### 测试用例筛选与数据断言验证
我们从员工表中找出分别命中这三种流向的代表性记录：
- 员工 105：原薪资低于 9000 元；
- 员工 104：原薪资为 9000 元（命中 `< 10000`），且 `commission_pct` 字段为 `NULL`；
- 员工 103：原薪资为 9100 元，且其已有奖金提成（非 NULL），将命中 `ELSE` 兜底。

```sql
-- 1. 基准测试数据预查
SELECT employee_id, salary, commission_pct 
FROM employees 
WHERE employee_id IN (103, 104, 105);

-- 2. 分别调用存储过程
CALL update_salary_by_eid4(103);
CALL update_salary_by_eid4(104);
CALL update_salary_by_eid4(105);

-- 3. 查验执行结果
SELECT employee_id, salary, commission_pct 
FROM employees 
WHERE employee_id IN (103, 104, 105);
```

##### 运行结果断言
- **103 号员工**：薪资从 9100.00 递增 100 元变为 `9200.00`，奖金率不变；
- **104 号员工**：薪资维持 9000.00 不变，奖金提成率由 `NULL` 变更为 `0.01`；
- **105 号员工**：薪资直接修正保底为 `9000.00`。
测试证明，模式二的 `CASE WHEN 条件 THEN 语句` 能够完全无缝替代复杂的 `IF ... ELSEIF ... ELSE` 结构，且在排版上更加紧凑清爽。

#### 案例二：基于等值匹配模式的工龄评级调薪与反面教材剖析

模式一（`CASE 变量 WHEN 常量 THEN 语句`）适用于输入值属于离散有限枚举的情况。

##### 业务需求描述
创建存储过程 `update_salary_by_eid5(IN emp_id INT)`，输入参数为员工工号。根据员工入职公司的年数计算调薪幅度：
- 入职满 0 年（刚入职不足一年）：薪资上涨 50 元；
- 入职满 1 年：薪资上涨 100 元；
- 入职满 2 年：薪资上涨 200 元；
- 入职满 3 年：薪资上涨 300 元；
- 入职满 4 年：薪资上涨 400 元；
- 其余情况（工龄 5 年及以上）：统一上涨 500 元。

##### 核心技术点与数据预处理
如果直接使用 `DATEDIFF(CURDATE(), hire_date)/365`，计算出来的工龄通常带有较长的小数位（例如 8.2345 年）。如果直接放入 `CASE hire_year WHEN 1`，由于浮点精度与等值比较机制，将永远无法命中离散的整数 `1`、`2`。

因此，在向局部变量写入之前，必须进行离散化取整：
1. **方案 A（四舍五入）**：使用 `ROUND(DATEDIFF(...) / 365)`，可不带参数，默认四舍五入取整；
2. **方案 B（直接向下截断）**：使用 `TRUNCATE(DATEDIFF(...) / 365, 0)`，显式保留 0 位小数。
变量类型建议直接声明为整数类型 `INT`，使得等值匹配更为严密。

##### 现场反面教材：漏写 WHERE 条件导致全表误改的事故推演
在编写多分支 `UPDATE` 语句时，极易因重复复制粘贴而遗漏核心限制。我们在构建此存储过程时，还原一次真实的“现场翻车”事故：

```sql
-- 【错误示范】：千万注意以下分支中的 UPDATE 没有加 WHERE 限制！
DELIMITER //

CREATE PROCEDURE update_salary_by_eid5_bug(IN emp_id INT)
BEGIN
    DECLARE hire_year INT;
    
    SELECT ROUND(DATEDIFF(CURDATE(), hire_date) / 365) INTO hire_year 
    FROM employees 
    WHERE employee_id = emp_id;
    
    CASE hire_year
        WHEN 0 THEN UPDATE employees SET salary = salary + 50;  -- 致命漏写 WHERE！
        WHEN 1 THEN UPDATE employees SET salary = salary + 100; -- 致命漏写 WHERE！
        WHEN 2 THEN UPDATE employees SET salary = salary + 200;
        WHEN 3 THEN UPDATE employees SET salary = salary + 300;
        WHEN 4 THEN UPDATE employees SET salary = salary + 400;
        ELSE UPDATE employees SET salary = salary + 500;        -- 致命漏写 WHERE！
    END CASE;
END //

DELIMITER ;
```

当我们调用 `CALL update_salary_by_eid5_bug(101);` 时，MySQL 控制台显示：

```text
Query OK, 107 rows affected
```

> **易错点（血泪教训）**：
> 控制台反馈“影响了 107 条记录”！这是因为整个 `employees` 表一共只有 107 名员工。由于 `UPDATE` 语句后缺失了 `WHERE employee_id = emp_id` 过滤条件，导致系统不仅没有对目标员工 101 进行单独调薪，反而把**全公司所有员工的薪资全都无差别地上调了 500 元**！
> 
> 这是一个极度危险且具备代表性的反面教材。必须切记：**存储过程语法通过编译（无报错成功创建），绝不代表业务逻辑没有致命缺陷**。在存储过程中书写任何 `UPDATE` 或 `DELETE` 语句时，务必警惕其作用域，严格绑定限定主键。

##### 纠正后的正确版本实现

```sql
DROP PROCEDURE IF EXISTS update_salary_by_eid5;

DELIMITER //

CREATE PROCEDURE update_salary_by_eid5(IN emp_id INT)
BEGIN
    -- 1. 声明整型工龄变量
    DECLARE hire_year INT;
    
    -- 2. 计算并四舍五入取整
    SELECT ROUND(DATEDIFF(CURDATE(), hire_date) / 365) INTO hire_year 
    FROM employees 
    WHERE employee_id = emp_id;
    
    -- 3. 等值 CASE 分支，每条 UPDATE 均严密绑定 WHERE employee_id = emp_id
    CASE hire_year
        WHEN 0 THEN 
            UPDATE employees SET salary = salary + 50 WHERE employee_id = emp_id;
        WHEN 1 THEN 
            UPDATE employees SET salary = salary + 100 WHERE employee_id = emp_id;
        WHEN 2 THEN 
            UPDATE employees SET salary = salary + 200 WHERE employee_id = emp_id;
        WHEN 3 THEN 
            UPDATE employees SET salary = salary + 300 WHERE employee_id = emp_id;
        WHEN 4 THEN 
            UPDATE employees SET salary = salary + 400 WHERE employee_id = emp_id;
        ELSE 
            UPDATE employees SET salary = salary + 500 WHERE employee_id = emp_id;
    END CASE;
END //

DELIMITER ;
```

##### 正确调用的数据验证

```sql
-- 查询目标员工 101 当前薪资

-- 假设当前 salary = 17000.00

-- 执行修正后的存储过程

-- 验证更新结果

```

### 两种分支结构（IF 与 CASE）的技术选型

在实际编写存储过程或函数时，面对多分支逻辑，应当如何选择？

```text
+--------------------------------------------------------------------+
| 分支结构选型决策树                                                  |
+--------------------------------------------------------------------+
|  遇到多分支业务判断？                                              |
|    │                                                               |
|    ├─ 是否针对单一离散整数/字符做等值列举？                         |
|    │    └─ 是 ──> 优先选用 CASE 模式一 (CASE var WHEN val THEN ...) |
|    │                                                               |
|    └─ 是否涉及不等式区间、复合布尔运算 (AND/OR) 或复杂规则？        |
|         │                                                          |
|         ├─ 倾向经典结构、多步退出 ──> 选用 IF ... ELSEIF ... ELSE  |
|         └─ 倾向代码扁平对齐、模式统一 ──> 选用 CASE 模式二 (CASE WHEN ...)|
+--------------------------------------------------------------------+
```

1. **等值枚举匹配**：当判定对象为一个具体的整型、枚举或字符，且匹配项不多时（如根据部门编号、订单状态码分流），使用 `CASE expr WHEN ...` 模式一最为直观，代码整齐；
2. **区间判断与组合条件**：当条件涉及 `>`、`<`、`BETWEEN` 或复杂的 `AND`/`OR` 组合时，模式一完全无法胜任（因为模式一强制要求做等值匹配）；此时既可以使用 `IF ... ELSEIF ... ELSE`，也可以使用模式二 `CASE WHEN 条件 THEN`。两者底层执行效率完全一致，更多取决于团队的代码风格偏好。

#### 题目一：过程化 CASE 语句与查询 CASE 表达式的语法辨析
- **题干描述**：请对比在存储过程中编写的 `CASE` 分支语句与在 `SELECT` 查询列表中编写的 `CASE` 表达式在语法结束符和分号使用上的区别。

## 88-LOOP_WHILE_REPEAT三种循环结构
> 对应分集：P88 | 原始标题：《88-LOOP_WHILE_REPEAT三种循环结构》

### 循环结构的本质认知与四要素模型

在学习完分支结构（`IF` 与 `CASE`）之后，我们进入流程控制模块中最具威力和灵活性的部分——**循环结构（Iteration / Loop）**。

在日常数据处理与后台任务调度中，很多计算并非一次性能够得出结果，而是需要根据业务状态反复重试或分批迭代。例如在月度薪酬核算、数据批量归档、分步调级等场景下，我们常常需要某段特定的 SQL 逻辑在满足特定阈值之前反复执行。这种执行流在程序设计中被称为循环。

无论是高级编程语言（如 C、Java、Python），还是 MySQL 中的过程化 SQL，**任何合法的循环结构在底层都必须严密具备四个核心要素**。如果大家在编写循环语句时经常遭遇死循环或逻辑混乱，十有八九是这四个要素中的某一个出现了缺失或错位：

```text
+--------------------------------------------------------------------+
| 循环结构核心四要素状态流转模型                                      |
+--------------------------------------------------------------------+
|                                                                    |
|   1. 初始化条件 (Initialization)                                    |
|      [声明计数器或读取当前数据基准值]                                 |
|               │                                                    |
|               ▼                                                    |
|   2. 循环条件 (Loop Condition) ◄─────────────────────────┐         |
|      <是否满足继续执行的阈值？>                            │         |
|         │                        │                         │         |
|        是 (满足)               否 (不满足)                 │         |
|         │                        │                         │         |
|         ▼                        ▼                         │         |
|   3. 循环体 (Body)          [跳出循环体]                   │         |
|      [执行核心业务操作]                                    │         |
|         │                                                  │         |
|         ▼                                                  │         |
|   4. 迭代条件 (Iteration)                                  │         |
|      [驱动变量向前推进，如自增或刷新数据基准] ─────────────┘         |
|                                                                    |
+--------------------------------------------------------------------+
```

1. **初始化条件（Initialization）**：在循环正式启动前，给参与循环控制的变量赋予初始状态（例如定义计数变量初值为 1，或在循环开始前先查询出当前部门的平均薪资）。
2. **循环条件（Loop Condition）**：决定循环是否应当继续执行或立即终止的布尔表达式。
3. **循环体（Loop Body）**：循环内真正反复执行的一组可执行 SQL 业务逻辑。
4. **迭代条件（Iteration）**：每轮循环体执行后，**驱动循环控制变量向终止状态靠近的操作**（例如计数器自增 `SET i = i + 1;`，或者重新检索最新更新后的表状态）。

> **易错点（死循环的罪魁祸首）**：
> 在实战编码中，开发者最容易遗漏的就是**迭代条件**。如果循环体内修改了数据库数据，却忘记在循环体内重新查询刷新基准变量，或者忘记对计数器累加，控制变量将永远定格在初始值。此时循环条件永远保持为真，存储过程就会陷入致命的**死循环（Infinite Loop）**，导致数据库连接被占满、CPU 飙升至 100%。

MySQL 原生提供了三种循环结构：
- **`LOOP` 循环**：天然死循环，必须显式结合标签与 `LEAVE` 关键字跳出；
- **`WHILE` 循环**：先验条件循环（先判断，后执行），类似于 `while(...)`；
- **`REPEAT` 循环**：后验条件循环（先执行，后判断），类似于 `do-while(...)`。

### 第一种循环：LOOP 结构的语法与应用

#### LOOP 的语法形式与跳出机制

`LOOP` 是 MySQL 中最底层的循环结构。与其他语言中的循环不同，**`LOOP` 语句本身没有任何先验或后验的退出条件判断**。它从一进入起就是无限循环。因此，它必须与**标签名（Label）**以及跳转关键字 **`LEAVE`**（类似于高级语言中的 `break`）配合使用，通过在循环体内部嵌套 `IF` 判定来主动中断。

##### 语法模板

```sql
[loop_label:] LOOP
    statement_list;
    -- 通常必须在此处嵌套条件判断：
    -- IF 退出条件 THEN
    --     LEAVE loop_label;
    -- END IF;
END LOOP [loop_label];
```

- **`loop_label`**：为当前循环块赋予的唯一标签标识符。起始处的 `label:` 与结尾处的 `END LOOP label` 必须严格一致。
- **`LEAVE loop_label;`**：用于立刻强行跳出并销毁指定标签对应的循环。

```text
+-------------------------------------------------------------------+
| LOOP 循环执行状态迁移图                                           |
+-------------------------------------------------------------------+
|  [进入 loop_label: LOOP]                                          |
|    │                                                              |
|    ▼                                                              |
|  [执行循环体业务语句]                                              |
|    │                                                              |
|    ▼                                                              |
|  <IF 满足退出条件？>                                              |
|    ├─ 是 ──> [LEAVE loop_label;] ───> [跳出 END LOOP 并终止循环]   |
|    │                                                              |
|    └─ 否 ──> [继续推进循环体剩余语句] ──> [回绕至 LOOP 顶部]       |
+-------------------------------------------------------------------+
```

#### 入门案例：基于 LOOP 的基础计数器

我们编写一个最简洁的测试存储过程，体会 `LOOP` 标签与 `LEAVE` 的配合：

```sql
DELIMITER //

CREATE PROCEDURE test_loop()
BEGIN
    -- 1. 初始化条件
    DECLARE num INT DEFAULT 1;
    
    -- 2. 带有标签的 LOOP 循环
    loop_label: LOOP
        -- 迭代与循环体
        SET num = num + 1;
        
        -- 循环退出判定
        IF num >= 10 THEN
            LEAVE loop_label;
        END IF;
    END LOOP loop_label;
    
    -- 3. 查看输出
    SELECT num;
END //

DELIMITER ;

CALL test_loop();
```
*执行结果*：控制台输出 `num = 10`。
*机理分析*：当 `num` 自增到 10 时，触发 `IF num >= 10`，命中 `LEAVE loop_label` 指令，执行引擎立刻跳出该循环体，继续向后执行 `SELECT num;`。

#### 业务实战：员工调薪至平均薪资达标与 OUT 参数避坑

##### 业务需求描述
创建存储过程 `update_salary_loop(OUT num INT)`。
- 业务规则：公司进行激励性调薪，若全公司员工的平均薪资尚未达到 12000 元，则全员薪资上浮 10%（即薪资变为原来的 1.1 倍）；
- 循环递增执行该操作，直至员工平均薪资**达到或超过 12000 元为止**；
- 存储过程结束时，需通过输出参数 `num` 返回总共调薪的循环次数。

##### 深度辨析：为什么严禁直接拿 OUT 形参当循环计数器？
在设计形参时，很多同学会产生一个疑问：“既然外面传入了一个 `OUT num INT` 参数用来记录次数，那我为什么还要在里面额外声明一个局部变量？我直接在循环体里 `SET num = num + 1;` 不更省事吗？”

> **注意（形参污染与类型陷阱）**：
> 这种做法在工程上存在严重的安全漏洞与逻辑隐患：
> 1. `OUT` 模式参数的本质是**只出不进**。当存储过程被调用时，无论调用者在外部给该变量赋了什么初值，进入存储过程体内时该形参的值都是未定义的（初始值为 `NULL`）。在 SQL 中，对 `NULL` 执行加法运算（`NULL + 1`），其结果永远是 `NULL`！这会导致计数器彻底失效。
> 2. 如果将参数模式改为 `INOUT`，调用方在外部传入该变量时若原本包含脏数据（例如初始变量值为 10），直接累加会导致基准被严重污染（最终返回的不是本次实际循环的次数，而是带有外部基数的污染值）。
> 
> **规范做法**：始终在内部独立声明一个确定性初值的局部变量（`DECLARE loop_count INT DEFAULT 0;`），所有自增操作仅作用于该局部变量；在循环安全结束、完成所有业务操作后，再将该局部变量的值单向赋值给输出形参（`SET num = loop_count;`）。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_loop(OUT num INT)
BEGIN
    -- 1. 声明局部变量：初始化条件
    DECLARE avg_sal DOUBLE;          -- 记录动态变化的平均薪资
    DECLARE loop_count INT DEFAULT 0; -- 内部严密计数的循环次数，初值设为 0
    
    -- 获取初始基准平均薪资
    SELECT AVG(salary) INTO avg_sal FROM employees;
    
    -- 2. 启动 LOOP 循环
    loop_label: LOOP
        -- 循环条件：达到 12000 元立即跳出
        IF avg_sal >= 12000 THEN
            LEAVE loop_label;
        END IF;
        
        -- 循环体：全员薪资上浮 10%
        UPDATE employees SET salary = salary * 1.1;
        
        -- 迭代条件 1：计数器递增
        SET loop_count = loop_count + 1;
        
        -- 迭代条件 2：极为关键！重新计算最新平均薪资，驱动 avg_sal 向阈值逼近
        SELECT AVG(salary) INTO avg_sal FROM employees;
        
    END LOOP loop_label;
    
    -- 3. 循环安全退出后，将内部计数结果交由 OUT 参数输出
    SET num = loop_count;
END //

DELIMITER ;
```

##### 调用与结果验证

```sql
-- 调用前先查看基准平均薪资
SELECT AVG(salary) FROM employees;
-- 假设基准平均薪资约为 7400 多元

-- 调用带 OUT 参数的存储过程
SET @count = 0;
CALL update_salary_loop(@count);

-- 验证结果
SELECT @count AS loop_times;
SELECT AVG(salary) AS new_avg_salary FROM employees;
```
*执行反馈*：`@count` 返回为 `6`，全表平均薪资更新为 `12465.34` 元，平稳突破 12000 元红线并安全终止。

### 第二种循环：WHILE 结构的语法与应用

#### WHILE 的语法形式与先验判定机理

`WHILE` 循环是使用最为广泛的标准循环结构。它属于**先验条件循环（Pre-test Loop）**。

##### 语法模板

```sql
[while_label:] WHILE search_condition DO
    statement_list;
END WHILE [while_label];
```

- **`search_condition`**：进入循环的判定表达式。**只要该条件求值为 `TRUE`，执行引擎就会执行 `DO` 之后的语句体**；一旦求值为 `FALSE` 或 `NULL`，循环立即终止。
- 标签名 `[while_label:]` 属于可选属性。只有在循环体内部需要通过 `LEAVE` 或 `ITERATE` 进行跨层跳转时，才需要显式声明标签。

```text
+-------------------------------------------------------------------+
| WHILE 循环执行状态迁移图 (先判断，后执行)                          |
+-------------------------------------------------------------------+
|  [进入 WHILE 循环]                                                |
|    │                                                              |
|    ▼                                                              |
|  <search_condition 是否为 TRUE？>                                 |
|    ├─ 是 (满足) ──> [执行循环体语句 statement_list]                |
|    │                       │                                      |
|    │                       ▼                                      |
|    │               [执行迭代条件更新状态] ──> 回到顶部再次判定      |
|    │                                                              |
|    └─ 否 (不满足) ─────────────────────────> [跳出 END WHILE]     |
+-------------------------------------------------------------------+
```

> **结论**：`WHILE` 循环的核心特征是“**先审后批**”。如果初始进入时 `search_condition` 本身就不成立，则其循环体**一次都不会执行（执行次数为 0）**。

#### 入门案例：WHILE 循环计数机理

```sql
DELIMITER //

CREATE PROCEDURE test_while()
BEGIN
    DECLARE number INT DEFAULT 1;
    
    WHILE number <= 10 DO
        SET number = number + 1;
    END WHILE;
    
    SELECT number;
END //

DELIMITER ;

CALL test_while();
```
*执行结果*：输出 `number = 11`。
*过程剖析*：当 `number` 在循环体内自增到 10 时，回到头部判定 `10 <= 10` 依然为真，再次进入加 1 变成 11；再次回到头部判定时，`11 <= 10` 为假，循环终止退出，输出最终值 11。

#### 业务实战：行业调整期企业临时降薪度过难关

##### 业务需求描述
经济环境与行业政策存在周期性波动。当市场处于调整下行期时，企业为规避断流风险往往需要暂时下调支出。创建存储过程 `update_salary_while(OUT num INT)`：
- 逻辑要求：若当前公司员工的平均薪资**高于 5000 元**，则对全员薪资进行阶梯下调，每次下调为原薪资的 90%（即打 9 折）；
- 重复该过程，直至公司平均薪资**降至 5000 元及以下**为止；
- 输出实际执行降薪的轮次 `num`。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_while(OUT num INT)
BEGIN
    -- 1. 初始化局部变量
    DECLARE avg_sal DOUBLE;
    DECLARE while_count INT DEFAULT 0;
    
    -- 获取基准数据
    SELECT AVG(salary) INTO avg_sal FROM employees;
    
    -- 2. WHILE 先验循环：只要平均薪资依然高于 5000，就执行降薪
    WHILE avg_sal > 5000 DO
        -- 循环体：全员降薪 10%
        UPDATE employees SET salary = salary * 0.9;
        
        -- 迭代计数
        SET while_count = while_count + 1;
        
        -- 迭代条件：重新拉取最新平均薪资，避免死循环
        SELECT AVG(salary) INTO avg_sal FROM employees;
    END WHILE;
    
    -- 3. 将结果输出给形参
    SET num = while_count;
END //

DELIMITER ;
```

##### 调用与结果验证

```sql
-- 调用前平均薪资为之前测试上升后的 12465.34 元
CALL update_salary_while(@drop_count);

SELECT @drop_count;
SELECT AVG(salary) FROM employees;
```
*执行反馈*：`@drop_count` 返回循环降薪次数（例如 9 次），平均薪资最终回落定格在 `4829.41` 元，低于 5000 元阈值，循环顺利终结。

### 第三种循环：REPEAT 结构的语法与应用

#### REPEAT 的语法形式与后验判定机理

`REPEAT` 属于**后验条件循环（Post-test Loop）**，它的逻辑架构类似于其他语言中的 `do ... while`。

##### 语法模板

```sql
[repeat_label:] REPEAT
    statement_list;
UNTIL search_condition
END REPEAT [repeat_label];
```

##### 语法规则与致命易错点
1. **先执行，后检查**：程序执行到 `REPEAT` 结构时，**不管当前条件是否满足，直接无条件先执行一遍循环体内的语句**，执行至底部时再对 `UNTIL search_condition` 进行求值。
2. **退出极性完全相反**：
   - 在 `WHILE` 中，条件为 `TRUE` 表示**继续留在循环内**；
   - 而在 `REPEAT ... UNTIL` 中，`search_condition` 代表的是**终止/退出条件**！即**当表达式为 `TRUE` 时立即退出循环**；为 `FALSE` 时则折返继续循环。
3. **`UNTIL` 后面绝对不能加分号**：这是初学者最高频的语法报错点。在 `UNTIL search_condition` 语句尾部，**切禁添加分号（`;`）**！若误加分号，MySQL 语法分析器会抛出 `You have an error in your SQL syntax near '; END REPEAT'` 的编译报错。

```text
+-------------------------------------------------------------------+
| REPEAT 循环执行状态迁移图 (先执行，后判断退出)                     |
+-------------------------------------------------------------------+
|  [进入 REPEAT 循环]                                               |
|    │                                                              |
|    ▼                                                              |
|  [无条件先执行一次循环体 statement_list]                           |
|    │                                                              |
|    ▼                                                              |
|  [执行迭代条件推进状态]                                            |
|    │                                                              |
|    ▼                                                              |
|  <UNTIL 退出条件是否为 TRUE？>                                     |
|    ├─ 是 (满足退出) ─────────────────────────> [跳出 END REPEAT]   |
|    │                                                              |
|    └─ 否 (未达退出标准) ─────────────────────> 回绕至 REPEAT 起始  |
+-------------------------------------------------------------------+
```

#### 入门案例：UNTIL 分号禁忌验证

```sql
DELIMITER //

CREATE PROCEDURE test_repeat()
BEGIN
    DECLARE number INT DEFAULT 1;
    
    REPEAT
        SET number = number + 1;
    UNTIL number >= 10   -- 注意：末尾绝不能加分号！
    END REPEAT;
    
    SELECT number;
END //

DELIMITER ;

CALL test_repeat();
```
*执行结果*：输出 `number = 10`。
*逻辑推导*：当 `number` 递增到 10 时，遇到 `UNTIL number >= 10`，判定为真，触发退出动作，平稳跳出。

#### 业务实战：市场复苏奖励调薪与 REPEAT 至少执行一次的深度检验

##### 业务需求描述
当外部环境逐步转暖，企业业绩回升，公司对坚持留任的员工进行激励性加薪。创建存储过程 `update_salary_repeat(OUT num INT)`：
- 逻辑要求：每次加薪为原有薪资的 1.15 倍（增幅 15%）；
- 循环递增，直至全员平均薪资**达到或超过 13000 元**时终止；
- 统计并输出加薪轮次 `num`。

##### 完整存储过程实现

```sql
DELIMITER //

CREATE PROCEDURE update_salary_repeat(OUT num INT)
BEGIN
    DECLARE avg_sal DOUBLE;
    DECLARE repeat_count INT DEFAULT 0;
    
    -- 初始化基准平均薪资
    SELECT AVG(salary) INTO avg_sal FROM employees;
    
    -- REPEAT 后验循环
    REPEAT
        -- 循环体：全员薪资上浮 15%
        UPDATE employees SET salary = salary * 1.15;
        
        -- 迭代计数递增
        SET repeat_count = repeat_count + 1;
        
        -- 迭代条件：重新查询刷新平均薪资
        SELECT AVG(salary) INTO avg_sal FROM employees;
        
    UNTIL avg_sal >= 13000  -- 终止条件：达到 13000 元即退出，注意无分号！
    END REPEAT;
    
    SET num = repeat_count;
END //

DELIMITER ;
```

##### 初次调用与数据验证

```sql
-- 调用前平均薪资为上一步降薪后的 4829.41 元
CALL update_salary_repeat(@up_count);

SELECT @up_count;
SELECT AVG(salary) FROM employees;
```
*执行反馈*：`@up_count` 返回为 `8`，全员平均薪资经过 8 轮上浮后跃升至 `14773.12` 元，达到且超越 13000 元红线，循环正常退出。

##### 趣味探究实验：二次调用揭示 REPEAT 的运行本质
在当前全员平均薪资已经处于 `14773.12` 元（明显早已高于 13000 元门槛）的前提下，我们立即**对该存储过程发起第二次调用**：

```sql
-- 在平均薪资已经为 14773.12 元时，强行再次调用
CALL update_salary_repeat(@repeat_again);

SELECT @repeat_again;
SELECT AVG(salary) FROM employees;
```

控制台返回的结果非常耐人寻味：
- `@repeat_again` 返回的值为 **`1`**（而非 0）；
- 平均薪资进一步暴涨为 **`16989.09` 元**！

```text
+-------------------------------------------------------------------+
| REPEAT 边界特性：即便条件一开始就满足，仍会“先斩后奏”执行一次         |
+-------------------------------------------------------------------+
|  [CALL update_salary_repeat] (当前平均薪资已达 14773 元)           |
|    ↓                                                              |
|  [直接冲入 REPEAT 内部]                                            |
|    ↓                                                              |
|  UPDATE employees SET salary = salary * 1.15; (强行再涨薪 15%！)    |
|    ↓                                                              |
|  SET repeat_count = 0 + 1 = 1;                                    |
|    ↓                                                              |
|  SELECT AVG(salary) INTO avg_sal; (变为 16989 元)                 |
|    ↓                                                              |
|  UNTIL avg_sal >= 13000 (求值为 TRUE，退出循环)                   |
|    ↓                                                              |
|  [赋值 OUT num = 1，程序结束]                                     |
+-------------------------------------------------------------------+
```

> **结论（核心对比）**：
> 这个测试现象彻底揭示了 `REPEAT` 与 `WHILE` 的本质区别：
> - 若使用 `WHILE` 结构（`WHILE avg_sal < 13000 DO`），由于初始进入时 `14773 < 13000` 直接为假，循环体一次都不会执行，计数器输出必定为 `0`，薪资分文不改；
> - 但 `REPEAT` 秉持“**先斩后奏**”哲学——无论当前的客观数据是否已经越界，只要进入该结构，**必定先强行跑完一次循环体**，再去判定末尾的 `UNTIL`。因此，`REPEAT` 结构的最小执行次数必然是 **1 次**！

### 三种循环结构的横向综合对比

通过上述真实环境下的案例推演与边界测试，我们将 MySQL 中的三大循环结构提炼总结如下：

| 评估维度 | `LOOP` 循环 | `WHILE` 循环 | `REPEAT` 循环 |
| :--- | :--- | :--- | :--- |
| **基础语法结构** | `[label:] LOOP ... END LOOP` | `WHILE cond DO ... END WHILE` | `REPEAT ... UNTIL cond END REPEAT` |
| **判定逻辑时机** | 无原生判定（需内嵌 `IF`） | **先验判定**（先检查，后执行） | **后验判定**（先执行，后检查） |
| **条件求值极性** | 不适用 | 条件为 **`TRUE` 则继续执行** | 条件为 **`TRUE` 则立即退出** |
| **最小执行次数** | 0 次（若一进循环立即被 `LEAVE`） | **0 次**（首轮判定失败直接跳过） | **1 次**（首轮无条件强制执行） |
| **退出依赖手段** | **强依赖** `label` 与 `LEAVE` | 依赖自身条件，标签可选 | 依赖自身条件，标签可选 |
| **典型适用场景** | 复杂无界迭代、游标提取异常捕获 | 最通用的常规计数与业务循环 | 无论如何都必须至少执行一次的事务批处理 |

## 89-LEAVE和ITERATE的使用
> 对应分集：P89 | 原始标题：《89-LEAVE和ITERATE的使用》

在 MySQL 存储过程与存储函数中，我们已经系统掌握了 `LOOP`、`WHILE` 和 `REPEAT` 三种基础循环结构。无论是在 C 语言、Java、Python 还是在 SQL 的存储过程中，所有完备的循环逻辑在本质上都由四个核心要素构成：初始化条件、循环条件、循环体以及迭代条件。

然而在实际生产开发中，纯粹依赖条件表达式来驱动循环往往缺乏灵活性。有时我们需要在满足特定业务条件时提前从深层嵌套的循环中跳出，或者在满足某些过滤规则时直接掠过本次循环的后续操作、直接开始下一轮迭代；甚至在某些复杂的业务校验分支中，我们需要直接从当前的 `BEGIN ... END` 复合语句块中全身而退，不再执行后续任何逻辑。

为此，MySQL 提供了两个专门用于流程跳转与控制的核心关键字：`LEAVE` 与 `ITERATE`。我们可以将它们自然地类比为通用编程语言中的 `break` 与 `continue`。本讲我们将彻底剖析这两个跳转语句的语法规范、标签（Label）绑定机制、适用作用域差异，并通过三个典型的生产级实战案例，掌握其在过程化编程中的精准应用。

---

### 循环要素与流程跳转控制机理

在深入学习跳转语句之前，我们有必要再次审视循环结构的底层运行模型。

#### 循环结构的四大核心要素与死循环陷阱

任何一个健康的循环结构，都必须严格具备以下四个逻辑部分：

```text
标准循环控制逻辑的时序与数据流向：

  [1. 初始化条件] (声明并赋予初始值，如 count = 0)
        │
        ▼
  [2. 循环条件] ◄────────────────────────────────┐
        │                                        │
    (满足: True)                             (进入下一次)
        │                                        │
        ▼                                        │
  [3. 循环体] (执行核心业务 SQL，如 UPDATE / SELECT) │
        │                                        │
        ▼                                        │
  [4. 迭代条件] (修改状态变量，如 count = count + 1)─┘
        │
    (不满足: False)
        │
        ▼
   [退出循环结构]
```

在这四个要素中，初学者最常犯的错误就是**漏写迭代条件**。在高级语言中，`for` 循环往往会在头部强制要求书写步进表达式；但在 SQL 的 `WHILE` 或 `LOOP` 中，迭代变量的修改必须由开发者在循环体内手工显式编写（例如 `SET i = i + 1;`）。一旦遗漏了这个迭代语句，状态变量将永远保持初始状态，布尔类型的循环条件永远为真，程序就会瞬间陷入死循环。

#### 跳转控制语句的引入与语言类比

当循环体内部逻辑极其复杂、涉及多分支条件判断时，仅靠顶部的布尔循环条件来控制退出会使代码极其臃肿。此时引入流程跳转语句，可以实现控制流的解耦：

- **`LEAVE`**：英文原意为“离开”。它的作用是强行跳出并终止当前指定的代码块，其控制效果类似于高级语言（Java/C/C++）中的 `break`。
- **`ITERATE`**：英文原意为“迭代”或“再次循环”。它的作用是立即结束当前这次循环中尚未执行的代码，直接重新回到循环头部开启下一次迭代，其控制效果等同于高级语言中的 `continue`。

在 MySQL 中，为了精确指明我们要跳出或继续的是哪一个具体的代码块或循环体，`LEAVE` 和 `ITERATE` 必须与**标签（Label）**协同工作。

---

### LEAVE 语句：中断并跳出指定代码块

`LEAVE` 语句的语法格式非常简洁，但它的适用作用域却比许多人想象的更为宽广。

#### 语法定义与标签绑定规则

`LEAVE` 语句的基本语法如下：

```sql
LEAVE 标签名;
```

> **定义**：`LEAVE` 语句用于退出指定的构造块。它不仅可以应用于循环语句（`LOOP`、`WHILE`、`REPEAT`），而且可以直接应用于 `BEGIN ... END` 复合语句块。

这意味着，如果我们为一个存储过程的 `BEGIN ... END` 主体赋予了一个标签名，那么在过程体内部任何一个深层分支中执行 `LEAVE 标签名;`，就相当于直接提前终结了该存储过程的执行，效果类似于高级语言中的函数提前 `return`。

使用 `LEAVE` 时有两项严格的语法约束：
1. **目标结构必须显式定义前置标签**：被 `LEAVE` 控制的代码块（循环或 `BEGIN`）前必须附带标签名并以英文冒号结尾，例如 `label_name: BEGIN` 或 `label_name: WHILE ... DO`。
2. **闭合处的可选标签**：代码块结束处的标签是可选的（例如 `END label_name;` 或仅写 `END;`），但只要该结构需要被内部的 `LEAVE` 引用，其起始处的前置标签就是强制必选的。

#### 案例一：跳出 BEGIN ... END 复合语句块

我们通过一个实际案例来观察 `LEAVE` 如何作用于普通的复合语句块。

**需求描述**：
创建存储过程 `leave_begin(IN num INT)`。为 `BEGIN ... END` 添加标签 `begin_label:`。在内部使用 `IF` 语句判断传入参数 `num` 的值：
- 若 `num <= 0`，则使用 `LEAVE` 直接退出整个 `BEGIN ... END` 结构；
- 若 `num = 1`，查询 `employees` 表中员工的平均薪资；
- 若 `num = 2`，查询 `employees` 表中员工的最低薪资；
- 若 `num > 2`，查询 `employees` 表中员工的最高薪资；
- 在 `IF` 结构执行完毕后，执行一条查询员工总人数的独立 `SELECT` 语句。

**实现代码**：

```sql
DELIMITER $

CREATE PROCEDURE leave_begin(IN num INT)
begin_label: BEGIN
    -- 1. 使用 IF 多分支结构进行条件判断
    IF num <= 0 THEN
        -- 当参数小于等于0时，直接退出整个存储过程体
        LEAVE begin_label;
    ELSEIF num = 1 THEN
        SELECT AVG(salary) AS avg_sal FROM employees;
    ELSEIF num = 2 THEN
        SELECT MIN(salary) AS min_sal FROM employees;
    ELSE
        SELECT MAX(salary) AS max_sal FROM employees;
    END IF;

    -- 2. 位于 IF 结构外部的独立语句
    SELECT COUNT(*) AS total_count FROM employees;

END begin_label $

DELIMITER ;
```

**逻辑解析与执行跟踪**：
- 当我们传入 `num = 0` 时，程序命中第一个分支 `num <= 0`，执行 `LEAVE begin_label;`。由于 `begin_label` 标记的是整个 `BEGIN ... END` 块，控制流瞬间跳出存储过程最外层，后续的分支判断以及末尾的 `SELECT COUNT(*)` 统统被掠过，客户端不会收到任何结果集返回。
- 当我们传入 `num = 1` 时，程序命中第二个分支，先执行并返回平均工资结果集；`IF` 结构自然闭合后，控制流继续向下推进，执行末尾的 `SELECT COUNT(*)` 并返回总人数结果集。

> **提示**：在很多图形化客户端（如部分版本的 SQLyog）中，当一个存储过程连续抛出多个 `SELECT` 结果集时，界面网格可能默认只渲染呈现第一个结果集。若要在视觉上直观验证多个结果集是否全部正常执行，可直接在 MySQL 原生命令行客户端终端中调用 `CALL leave_begin(1);`，即可清晰观察到先后输出的两个完整数据表格。

#### 案例二：跳出 WHILE 循环（死循环模拟与条件跳出）

在编写复杂的批处理存储过程时，有时我们无法在循环进入前预判明确的终止边界，此时可以采用“常真循环 + 内部条件断点”的工程设计范式。

**需求描述**：
市场大环境不景气，公司决定实行降薪策略：使用 `WHILE` 循环将全体员工的薪资统一下调为原薪资的 90%（即降低 10%），循环往复，直到全公司员工的平均薪资下调至 10,000 元及以下（`<= 10000`）时立即停止，并记录降薪循环的实际执行轮数。
创建存储过程 `leave_while(OUT num INT)`，将统计的轮数输出。

**实现代码**：

```sql
DELIMITER $

CREATE PROCEDURE leave_while(OUT num INT)
BEGIN
    -- 1. 声明局部变量：记录平均工资与循环计数器
    DECLARE avg_sal DOUBLE;
    DECLARE while_count INT DEFAULT 0;

    -- 2. 循环前初始化：获取员工当前的平均薪资
    SELECT AVG(salary) INTO avg_sal FROM employees;

    -- 3. 构建死循环，依赖内部 LEAVE 实现条件跳出
    while_label: WHILE TRUE DO
        -- 循环退出断点判断
        IF avg_sal <= 10000 THEN
            LEAVE while_label;
        END IF;

        -- 循环体：执行全员薪资下调 10%
        UPDATE employees SET salary = salary * 0.9;

        -- 迭代状态更新：重新计算平均薪资并递增计数器
        SELECT AVG(salary) INTO avg_sal FROM employees;
        SET while_count = while_count + 1;
    END WHILE while_label;

    -- 4. 将最终循环轮数赋给 OUT 参数
    SET num = while_count;

END $

DELIMITER ;
```

**执行测试与机制验证**：
假设当前 `employees` 表中所有员工的初始平均薪资约为 16,000 多元。
我们在客户端进行调用与验证：

```sql
-- 调用存储过程，传入用户会话变量 @count 接收结果
CALL leave_while(@count);

-- 查看循环次数
SELECT @count;
-- 返回结果为 6，说明系统共执行了 6 轮全员打九折的操作

-- 验证当前员工平均工资
SELECT AVG(salary) FROM employees;
-- 返回结果约为 9028.xx 元，确实已压降至 10,000 元以下
```

如果我们在此状态下紧接着再次执行一次 `CALL leave_while(@count);`：
- 程序在进入 `WHILE` 循环前查出当前平均工资已经是 9028 元；
- 首次进入循环体，立刻命中 `avg_sal <= 10000`，随即触发 `LEAVE while_label;`；
- 控制流立即跳出循环，最终将初始值 `0` 赋予 `@count`，返回结果准确无误为 `0`。

该案例生动地印证了：通过将循环条件恒定设为 `TRUE`，并将业务终止逻辑交由 `IF ... THEN LEAVE` 负责，可以构建出控制粒度极为精细的动态循环结构。

### ITERATE 语句：提前终结单次迭代进入下一轮

与 `LEAVE` 的“彻底决裂”不同，`ITERATE` 是“暂时略过、下不为例”。

#### 语法契约与应用范围限制

`ITERATE` 语句的语法格式如下：

```sql
ITERATE 标签名;
```

> **定义**：`ITERATE` 语句表示“重新开始循环”。它只能在循环语句（`LOOP`、`WHILE`、`REPEAT`）的循环体中使用，其控制行为是立即忽略该循环体内后续尚未执行的代码行，直接将程序指针拉回循环头部，开始下一轮条件的评估与迭代。

```text
ITERATE 与 LEAVE 在循环控制流中的流向差异：

       ┌─────────────────── [循环开始] ◄────────────────────┐
       │                          │                         │
       │                          ▼                         │
       │                    [条件判断/开始]                  │
       │                          │                         │
       │                          ▼                         │
       │                  [循环前半部操作]                   │
       │                          │                         │
       │                  ┌───────┴───────┐                 │
       │      (满足退出条件)│               │(满足跳过条件)    │
       │          [触发 LEAVE]         [触发 ITERATE]───────┘
       │                │              (放弃后半部，立即开启下一轮)
       │                │
       │                ▼
       │         [循环后半部操作]
       │                │
       │                ▼
       │         [迭代条件推进]
       │                │
       │                └───────────────────────────────────┘
       ▼
   [跳出循环体]
```

> **易错点**：`ITERATE` 与 `LEAVE` 在应用范围上存在本质区别——`LEAVE` 既能用于循环也能用于 `BEGIN ... END` 块，而 **`ITERATE` 只能且必须使用在循环结构中**。若在非循环的 `BEGIN ... END` 结构中调用 `ITERATE`，MySQL 语法分析器将直接拒绝并报出语法错误。

#### 案例三：LOOP 循环中 ITERATE 与 LEAVE 的协同控制

为了深刻理解 `ITERATE` 对代码执行路径的截断效果，我们通过一个结合了计步器与控制台信息打印的综合案例进行实操。

**需求描述**：
创建存储过程 `test_iterate()`。定义局部变量 `num INT DEFAULT 0`。
使用 `loop_label: LOOP` 结构执行如下逻辑：
1. 每次循环将 `num` 自增 1；
2. 若 `num < 10`，则继续循环（使用 `ITERATE`）；
3. 若 `num > 15`，则退出当前循环（使用 `LEAVE`）；
4. 在上述条件分支之外，书写一条信息打印语句：`SELECT '让天下没有难学的技术';`。

**实现代码**：

```sql
DELIMITER $

CREATE PROCEDURE test_iterate()
BEGIN
    -- 1. 声明局部变量并赋默认值 0
    DECLARE num INT DEFAULT 0;

    -- 2. 标签化 LOOP 循环
    loop_label: LOOP
        -- 步进自增
        SET num = num + 1;

        -- 分支跳转控制
        IF num < 10 THEN
            ITERATE loop_label;
        ELSEIF num > 15 THEN
            LEAVE loop_label;
        END IF;

        -- 仅在 num 处于 [10, 15] 区间时才会执行到的代码
        SELECT '让天下没有难学的技术' AS msg;

    END LOOP loop_label;

END $

DELIMITER ;
```

**语法细节剖析**：
注意上述代码中的 `IF ... ELSEIF ... END IF;` 结构：这里完全**没有书写最后的 `ELSE` 分支**。这在 SQL 流程控制中是完全合规且极其高效的写法。当 `num` 的取值落在 `[10, 15]` 之间时，既不满足 `< 10`，也不满足 `> 15`，程序便自然顺畅地穿透整个 `IF` 判定，安全下行至后续的 `SELECT` 语句。

**执行轨迹逐轮推演**：
1. **阶段一（`num` 从 1 到 9）**：
   - 每次循环开始，`num` 递增（1、2、...、9）；
   - 执行 `IF num < 10` 判断，结果均为 `TRUE`；
   - 触发 `ITERATE loop_label;`，控制流立即被重置并拉回到 `LOOP` 起始点；
   - 下方的 `SELECT` 语句被完全跳过，一次都没有执行。
2. **阶段二（`num` 变为 10）**：
   - `num` 递增为 10；
   - 判断 `num < 10` 为假，判断 `num > 15` 亦为假，`IF` 块正常结束；
   - 控制流抵达 `SELECT`，首次成功输出消息。
3. **阶段三（`num` 从 11 到 15）**：
   - `num` 逐次递增为 11、12、13、14、15，均穿透 `IF` 判定；
   - `SELECT` 语句被稳定触发执行，连续输出 5 次消息。
4. **阶段四（`num` 变为 16）**：
   - `num` 递增为 16；
   - 命中 `ELSEIF num > 15` 分支，触发 `LEAVE loop_label;`；
   - 循环被彻底斩断，控制流跳离整个 `LOOP` 体系，存储过程平稳终止。

通过原生命令行客户端调用 `CALL test_iterate();`，终端将依次、准确地弹出 6 次包含 `'让天下没有难学的技术'` 的结果集表格（分别对应 `num = 10, 11, 12, 13, 14, 15`），彻底验证了 `ITERATE` 跳过局部代码块的精准特性。

### 跳转语句技术对比与工程规约

为了在生产环境的复杂存储过程开发中准确选型，我们将 `LEAVE` 与 `ITERATE` 的关键属性梳理对比如下：

| 特性维度 | `LEAVE` | `ITERATE` |
| :--- | :--- | :--- |
| **字面语义** | 离开、退出、终结 | 迭代、重试、开启下一轮 |
| **高级语言等价物** | `break` / 复合块提前 `return` | `continue` |
| **合法作用域** | 循环结构（`LOOP`/`WHILE`/`REPEAT`）以及 `BEGIN ... END` 复合语句块 | **仅限**循环结构（`LOOP`/`WHILE`/`REPEAT`） |
| **标签依赖度** | 必须显式指定目标标签 | 必须显式指定目标循环标签 |
| **执行后果** | 结构立即解体，跳到结构末尾之后向下执行 | 跳过当前循环体内剩余语句，回到循环首部重新评估 |
| **典型应用场景** | 异常中断、搜索命中提前退出、死循环主动熔断 | 数据无效过滤、黑名单跳过、特定区间穿透处理 |

#### 标签命名与书写规范

在涉及多层循环嵌套（例如外层遍历部门、内层遍历员工）的场景中，标签的合理命名与绑定至关重要：
- **命名语义化**：避免使用 `label1`、`l2` 等毫无意义的命名。推荐采用 `外层对象_循环类型_label` 的规范，如 `dept_while_label`、`emp_loop_label`。
- **冒号约束**：起始位置给语句块挂载标签时，**必须以英文冒号结尾**（如 `outer_loop: LOOP`）；而在 `LEAVE` 或 `ITERATE` 后面引用标签时，**严禁加冒号**，直接写标签名并以分号结尾（如 `LEAVE outer_loop;`）。
- **多层嵌套跳出能力**：在深层嵌套循环中，内层的 `LEAVE` 可以直接指定最外层循环的标签名。一旦触发，控制流将直接穿透所有内部循环，直接跳离整个最外层循环体，这在处理多级关联数据的短路退出时极为高效。

- 若 `num <= 0`，退出整个复合语句块；
- 若 `num = 1`，查询全员平均工资；
- 若 `num = 2`，查询全员最低工资；
- 若 `num > 2`，查询全员最高工资；
- 在 `IF` 块外部，查询全员总人数。

**标准解析与答案**：
利用 `LEAVE` 针对 `BEGIN ... END` 的解体能力，在首个分支直接退出。

```sql
DELIMITER $
CREATE PROCEDURE leave_begin(IN num INT)
begin_label: BEGIN
    IF num <= 0 THEN
        LEAVE begin_label;
    ELSEIF num = 1 THEN
        SELECT AVG(salary) FROM employees;
    ELSEIF num = 2 THEN
        SELECT MIN(salary) FROM employees;
    ELSE
        SELECT MAX(salary) FROM employees;
    END IF;

    SELECT COUNT(*) FROM employees;
END begin_label $
DELIMITER ;
```

#### 题目二：降薪模拟与动态循环退出

**题干要求**：
创建存储过程 `leave_while(OUT num INT)`。使用 `WHILE` 循环将全体员工薪资逐次降为原薪资的 90%，直到全公司平均薪资小于等于 10,000 元为止，最终通过输出参数 `num` 返回降薪所经历的循环次数。

**标准解析与答案**：
声明双变量分别维护平均薪资与计数器。将 `WHILE` 条件设为 `TRUE` 构建死循环，在循环体首部使用 `IF avg_sal <= 10000 THEN LEAVE while_label; END IF;` 作为退出断点，并在其后执行 `UPDATE`、重新计算平均薪资及计数器累加。

```sql
DELIMITER $
CREATE PROCEDURE leave_while(OUT num INT)
BEGIN
    DECLARE avg_sal DOUBLE;
    DECLARE while_count INT DEFAULT 0;

    SELECT AVG(salary) INTO avg_sal FROM employees;

    while_label: WHILE TRUE DO
        IF avg_sal <= 10000 THEN
            LEAVE while_label;
        END IF;

        UPDATE employees SET salary = salary * 0.9;
        SELECT AVG(salary) INTO avg_sal FROM employees;
        SET while_count = while_count + 1;
    END WHILE while_label;

    SET num = while_count;
END $
DELIMITER ;
```

#### 题目三：LOOP 循环中 ITERATE 与 LEAVE 协同控制

**题干要求**：
创建存储过程 `test_iterate()`。定义局部变量 `num` 初始值为 0。在带标签的 `LOOP` 循环中每次递增 `num`：
- 若 `num < 10`，使用 `ITERATE` 继续循环；
- 若 `num > 15`，使用 `LEAVE` 跳出循环；
- 在分支之后打印 `'让天下没有难学的技术'`。
分析并验证该语句在循环过程中的实际触发次数。

**标准解析与答案**：
利用不带 `ELSE` 的 `IF ... ELSEIF ... END IF;` 结构实现特定区间的代码穿透。`num` 在 1 到 9 时被 `ITERATE` 拦截，在 10 到 15 时顺利穿透执行 `SELECT`，在 16 时触发 `LEAVE` 彻底终止。因此信息语句将被精准触发执行 6 次。

```sql
DELIMITER $
CREATE PROCEDURE test_iterate()
BEGIN
    DECLARE num INT DEFAULT 0;

    loop_label: LOOP
        SET num = num + 1;

        IF num < 10 THEN
            ITERATE loop_label;
        ELSEIF num > 15 THEN
            LEAVE loop_label;
        END IF;

        SELECT '让天下没有难学的技术' AS msg;
    END LOOP loop_label;
END $
DELIMITER ;
```

## 90-游标的使用
> 对应分集：P90 | 原始标题：《90-游标的使用》

在 SQL 的世界中，绝大多数查询与更新操作都是针对数据“集合（Set）”展开的。当我们执行 `SELECT * FROM employees WHERE department_id = 50;` 时，数据库引擎返回的是一个由多行记录构成的完整结果集；当我们执行 `UPDATE employees SET salary = salary * 1.05;` 时，也是一条 SQL 命令瞬间更新整张表或符合条件的一大批数据。

这种“面向集合”的操作模式正是关系型数据库高效处理海量数据的核心优势。然而在实际业务研发中，我们经常会遇到一种尴尬的困境：业务规则极其复杂，不仅需要对查询结果集做排序，还需要深入到数据的内部，**一条一条记录逐行读取、逐行研判、并在特定状态累计达到阈值时提前终止**。例如：从全公司最高薪资的员工开始逐个累加薪资，当累计发放金额首次突破 20 万元预算时立即停下，并精准返回这笔预算究竟覆盖了多少名员工。

对于这种强依赖“前一行运算结果作为后一行判定依据”的面向过程需求，纯粹面向集合的 SQL 语句就捉襟见肘了。为了打破这一局限，MySQL 提供了**游标（Cursor，部分文献也称光标）**机制。游标就像一个可在结果集上逐行移动的精确指针，让面向集合的 SQL 具备了细腻的面向过程处理能力。

本讲我们将系统解析游标的内部工作机理、完整的声明生命周期四大步，并通过高阶工资累计实战案例彻底掌握游标与流程控制的配合；同时，结合全章知识脉络，补充学习 MySQL 8.0 中针对全局系统变量持久化（`SET PERSIST`）的关键工程特性。

### 游标的核心定位与面向过程能力重构

要理解游标，我们可以先观察日常文本编辑器中光标的行为：当你在编辑器中移动光标时，光标所停驻的位置，就是当前被选中的具体字符或具体某一行行首。

#### 面向集合与面向过程的鸿沟

在没有游标之前，SQL 查询产生的结果集在概念上是“铁板一块”：

```text
面向集合处理 vs 游标逐行指针处理模型对比：

  [ 面向集合处理模式: 整体吞吐 ]
   SQL 查询 ──► [ 查询结果集 Result Set ] ──► 一次性打包抛给客户端或执行批量变更
                ┌─────────────────────┐       (无法在单次批量中针对第 3 行做特殊逻辑，
                │ Row 1: King    24000│        遇到动态累计计算时必须查回前端再循环)
                │ Row 2: Kochhar 17000│
                │ Row 3: De Haan 17000│
                └─────────────────────┘

  [ 游标 Cursor 处理模式: 指针逐行步进 ]
   DECLARE CURSOR ──► 绑定结果集
         │
   OPEN CURSOR    ──► 结果集送入游标工作区，指针就位
         │
   FETCH CURSOR   ──► [ 指针指向 Row 1 ] ──► 取出值赋给变量 ──► 业务逻辑运算 1
         │
   FETCH CURSOR   ──► [ 指针指向 Row 2 ] ──► 取出值赋给变量 ──► 业务逻辑运算 2 (累加/判断)
         │
   FETCH CURSOR   ──► [ 指针指向 Row 3 ] ──► 取出值赋给变量 ──► 业务逻辑运算 3 (阈值拦截)
         │
   CLOSE CURSOR   ──► 释放指针与数据锁
```

通过上面的架构图可以清晰看出：
- 当我们使用 `WHERE` 或 `HAVING` 进行条件过滤后，数据库输出的仍然是一个多行集合。如果不在后端应用层（如 Java、Python）写循环去解析，单凭一条 SQL 无法对这个集合内部做逐行微调；
- **游标的本质就是结果集上的一个指针**。它充当了 SQL 与过程化代码之间的桥梁，允许开发者在存储过程或函数中，以单行记录为粒度获取字段，将字段存入局部变量中进行独立的算术、逻辑与条件控制。

> **结论**：游标让原本只能进行集合运算的 SQL 语言，拥有了完整的“面向过程”开发能力。

### 游标生命周期的四大规范步骤

在 MySQL 中使用游标，有着极其严密的步骤与声明次序要求。任何一步缺失或颠倒，都会导致编译失败或运行期资源泄露。

标准游标操作分为以下四个核心步骤：
1. **声明游标（DECLARE）**
2. **打开游标（OPEN）**
3. **使用游标逐行读取数据（FETCH）**
4. **关闭游标（CLOSE）**

```text
游标完整生命周期的状态机迁移过程：

    [ 未初始化状态 ]
           │
           ▼ DECLARE cursor_name CURSOR FOR SELECT ...
    [ 游标声明就绪 ] (仅定义数据契约，未执行查询，不耗费缓存)
           │
           ▼ OPEN cursor_name
    [ 游标激活工作态 ] (查询执行，结果集载入工作区，产生行级锁定)
           │
           ├────────────┐
           ▼ FETCH ...  │
     (逐行读取数据)      │ 循环调用 FETCH
           │            │
           └────────────┘
           │
           ▼ CLOSE cursor_name
    [ 游标销毁释放态 ] (清空工作区内存，释放行级数据锁)
```

#### 第一步：声明游标（DECLARE CURSOR）

声明游标的语法如下：

```sql
DECLARE 游标名 CURSOR FOR SELECT查询语句;
```

在语法编写上需要注意两点：
1. **跨数据库语法差异**：在 MySQL、SQL Server、DB2 以及 MariaDB 中，使用的是 `CURSOR FOR`；而在 Oracle 与 PostgreSQL 中，语法为 `CURSOR IS`。
2. **声明位置严格有序**：在存储过程的 `BEGIN ... END` 体内，声明语句是有严格优先级顺序的：
   - 最先书写的必须是**普通局部变量的声明**（`DECLARE var_name type ...`）；
   - 其次书写的是**游标的声明**（`DECLARE cursor_name CURSOR FOR ...`）；
   - 最后书写的才是**错误处理程序的声明**（`DECLARE ... HANDLER FOR ...`）。
   如果把变量声明写在游标声明的下方，MySQL 将直接抛出语法解析错误。

#### 第二步：打开游标（OPEN CURSOR）

声明游标只是定义了一条查询契约，并未真正触发底层执行。只有执行打开语句后，游标才真正就绪：

```sql
OPEN 游标名;
```

执行 `OPEN` 时，数据库引擎会执行其绑定的 `SELECT` 语句，并将返回的结果集加载到游标专属的工作区内存中。此时游标内部指针指向第一条记录的前方，为接下来的读取做好全部底层准备。

#### 第三步：使用游标读取数据（FETCH CURSOR）

使用游标的本质就是通过 `FETCH` 命令将指针当前所指记录的各列数据，提取并写入预先声明好的局部变量中：

```sql
FETCH 游标名 INTO 局部变量1 [, 局部变量2, ...];
```

> **易错点**：**“一个萝卜一个坑”的严格对应法则**。
> `SELECT` 查询投影了多少个字段，`INTO` 后面就必须严格按序提供相同数量的局部变量，且对应变量的数据类型必须与查询字段兼容。如果 `SELECT` 查了 3 个字段，而 `INTO` 只给了 2 个变量，或者给了 4 个变量，MySQL 会直接报错中断执行。

每执行一次 `FETCH`，游标指针便会自动向后步进一行。因此，`FETCH` 几乎必然置身于循环结构（如 `LOOP`、`WHILE` 或 `REPEAT`）中，循环往复地取数并执行计算。

#### 第四步：关闭游标（CLOSE CURSOR）

当数据读取完毕或已满足业务退出条件时，必须显式调用关闭命令：

```sql
CLOSE 游标名;
```

很多初学者容易遗漏 `CLOSE`，认为存储过程执行完了系统自然会清理。这是一个极其危险的坏习惯：
- **资源占用**：游标会持续占用 MySQL 服务器的内存工作区句柄；
- **锁并发阻塞**：在事务执行期间，游标遍历扫描数据集时会对底层数据行持有行锁或间隙锁。若游标不及时显式关闭，相关锁资源将一直被霸占，直到整个外层存储过程彻底结束甚至事务提交。在生产高并发场景下，其他并发会话对这些数据的查询或修改将被迫长时间挂起排队，极易诱发锁等待超时甚至系统雪崩。

> **提示**：坚持在不再需要使用游标数据的第一时间，显式调用 `CLOSE` 进行资源释放。

### 生产级实战案例：高薪累计人数统计

我们通过讲师在课上详细带练的经典业务场景，把局部变量、游标定义、循环控制、条件中断与资源释放完整地串联起来。

#### 业务需求建模

**场景需求**：
创建存储过程 `get_count_by_limit_total_salary(IN limit_total_salary DOUBLE, OUT total_count INT)`。
业务逻辑如下：
1. 查询 `employees` 表中所有员工的薪资，并按照**从高到低（DESC）**降序排列；
2. 定义一个累加薪资总额的变量，从最高薪资员工开始，逐个取出其薪资并累加；
3. 直到累加的薪资总额**首次达到或超过**传入的薪资上限 `limit_total_salary` 时立即停止累加；
4. 统计并输出此时一共累加了多少名员工的人数，将该数值通过输出参数 `total_count` 返回。

#### 变量规划与结构推导

在动手编写之前，我们先梳理存储过程内部所需的局部变量：
1. `sum_sal DOUBLE DEFAULT 0.0`：用于记录累加的工资总额。由于在循环体中需要执行 `sum_sal = sum_sal + 当前工资`，因此**必须赋初始默认值 0.0**。若不指定默认值，其初始值为 `NULL`，任何数值与 `NULL` 进行算术加法其结果永远是 `NULL`，直接导致逻辑全盘失效。
2. `emp_sal DOUBLE`：用于记录每次被 `FETCH` 取出的一行员工工资。由于每轮循环都会直接被 `INTO` 覆盖赋值，无需设置默认值。
3. `emp_count INT DEFAULT 0`：用于充当计步器，每取出一行工资并累加后自增 1，必须显式设置默认值为 0。

#### 完整代码实现

本次实现我们采用后置判断的 `REPEAT ... UNTIL ... END REPEAT` 循环结构来驱动游标：

```sql
DELIMITER $

CREATE PROCEDURE get_count_by_limit_total_salary(
    IN limit_total_salary DOUBLE,
    OUT total_count INT
)
BEGIN
    -- 1. 声明局部变量（必须置于最顶端）
    DECLARE sum_sal DOUBLE DEFAULT 0.0;     -- 累加的总薪资
    DECLARE emp_sal DOUBLE;                 -- 单个员工薪资
    DECLARE emp_count INT DEFAULT 0;        -- 累加的员工人数

    -- 2. 声明游标（紧随变量声明之后）
    DECLARE emp_cursor CURSOR FOR 
        SELECT salary 
        FROM employees 
        ORDER BY salary DESC;

    -- 3. 打开游标
    OPEN emp_cursor;

    -- 4. 循环使用游标读取数据
    REPEAT
        -- 取出一行数据写入变量
        FETCH emp_cursor INTO emp_sal;

        -- 业务计算：总额累加与人数递增
        SET sum_sal = sum_sal + emp_sal;
        SET emp_count = emp_count + 1;

    -- 退出条件：累计总薪资达到或超过设定的上限阈值
    -- 注意：UNTIL 之后的表达式末尾绝对不能加分号！
    UNTIL sum_sal >= limit_total_salary
    END REPEAT;

    -- 5. 将内部统计的人数赋予 OUT 参数
    SET total_count = emp_count;

    -- 6. 显式关闭游标，释放资源
    CLOSE emp_cursor;

END $

DELIMITER ;
```

#### 执行调用与结果验证

我们通过传入参数测试存储过程：

```sql
-- 调用存储过程，设定薪资累计上限为 20 万元，并用用户变量 @count 接收人数
CALL get_count_by_limit_total_salary(200000, @count);

-- 查询输出结果
SELECT @count;
-- 返回结果为：11
```

**业务逻辑推演验证**：
在标准的演示数据集中，`employees` 表中最高薪资分别为 24000、17000、17000、14000 等。游标逐行扫描累加，当累加到第 10 名员工时，总薪资尚不足 20 万元；当读到第 11 名员工并加入总和后，`sum_sal` 首次突破 20 万元大关。此时命中 `UNTIL sum_sal >= limit_total_salary`，循环平稳跳出，返回人数 11，完全契合业务预期。

### 游标的优劣权衡与架构决策

在实际工程选型中，游标是一把双刃剑：

```text
游标（Cursor）的技术全景权衡：

        ┌───────────────────────────────┐
        │       游标的核心技术价值       │
        └───────────────┬───────────────┘
                        │
       ┌────────────────┴────────────────┐
       ▼                                 ▼
   [ 显著优势 ]                      [ 潜在代价 ]
   - 逐行颗粒度：提供细致的数据提取  - 内存占用：缓冲整个结果集
   - 过程控制：支持状态累计与中断    - 加锁竞争：扫描行级长期持锁
   - 算法表达：突破集合思维限制      - 性能瓶颈：难以享受批量批处理优化
```

#### 适用场景与优势
- **极度复杂的逐行计算**：当计算某一行的逻辑严重依赖上一行的累计运行状态，且无法通过单一 SQL 表达式或窗口函数直接化解时，游标是最直接的解法；
- **小批量与管理型任务**：在非核心高频路径的离线批处理、历史数据清洗、管理员定制化运维存储过程中，游标开发直观可靠。

#### 性能陷阱与避坑指南
- **严禁在超大并发 OLTP 核心接口中滥用**：游标每次 `FETCH` 都会带来额外的 CPU 执行开销；长时间不提交还会拉长事务链路，加剧锁竞争。
- **能用集合操作替代时，优先使用集合**：如果某个需求可以通过一条带有 `GROUP BY`、`CASE` 或单行函数的 `UPDATE`/`SELECT` 完成，永远不要为了“显得懂面向过程”而强行使用游标重构。

### 补充拓展：MySQL 8.0 全局系统变量持久化（SET PERSIST）

在本章讨论存储过程变量的过程中，我们学习了系统变量（分为 `GLOBAL` 全局级与 `SESSION` 会话级）和用户自定义变量。结合全局系统变量的运维特性，本节拓展一个 MySQL 8.0 的重要生产新特性：**全局变量持久化**。

#### 传统运行时配置丢失的运维痛点

在早期的 MySQL 5.7 及更早版本中，运维人员若想调整某个全局系统变量（例如最大连接数 `max_connections`），通常有两种途径：
1. **纯内存动态修改**：执行 `SET GLOBAL max_connections = 1000;`。
   - **后果**：该设置即刻在内存中生效，但**不具备跨重启持久性**。一旦由于服务器维护、断电重启或 mysqld 进程崩溃崩溃拉起，该配置将瞬间丢失，重新跌回默认的 151。
2. **配置文件手工修改**：登录服务器后台，用编辑器修改 `my.cnf` 或 `my.ini`。
   - **后果**：修改配置文件不需要重启不会立刻生效，必须配合 `SET GLOBAL` 再次修改内存；若只改内存忘记改文件，下次重启依然失效，极易诱发配置飘移（Configuration Drift）故障。

#### SET PERSIST 的语法与底层机理

针对这一痛点，MySQL 8.0 正式引入了 `PERSIST` 关键字：

```sql
-- 将全局系统变量 max_connections 设为 1000 并持久化
SET PERSIST max_connections = 1000;
```

```text
SET PERSIST 的底层双写持久化机制：

  管理员执行: SET PERSIST max_connections = 1000
                         │
                         ├──► 1. 动态生效：立即修改当前运行实例的内存全局变量
                         │
                         └──► 2. 持久化落盘：在数据目录下自动写入/更新 mysqld-auto.cnf
                                 (JSON 格式记录键值对)
                                         │
  [ 后续服务器重启 mysqld 重启 ] ─────────┘
         │
         ▼
  优先读取 my.cnf 基础配置，随后读取 mysqld-auto.cnf 覆盖配置
  无需人工手动干预，修改后的 1000 依然稳固生效！
```

通过执行 `SET PERSIST`：
1. MySQL 会先在当前正在运行的内存实例中应用该配置，立即可用；
2. 同时，MySQL 会自动在数据存储目录（Data Directory）下创建或更新名为 `mysqld-auto.cnf` 的文件，以标准的 JSON 格式记录该变量与新值；
3. 当 MySQL 实例在未来重新启动时，在读取完常规的 `my.cnf` 之后，会自动追加加载 `mysqld-auto.cnf`，覆盖先前的设置，实现真正的“一次配置，跨重启永久生效”。这极大减轻了云原生环境下数据库集群参数调优的运维心智负担。

在本讲的授课过程中，讲师通过一个完整的案例推导了游标在薪资累计统计中的核心应用。

#### 题目：降序薪资累计上限与人数统计

**题干要求**：
创建存储过程 `get_count_by_limit_total_salary(IN limit_total_salary DOUBLE, OUT total_count INT)`。
要求使用游标读取 `employees` 表中按降序排列的员工工资，逐行累加薪资总和，直到累计总额达到或超过 `limit_total_salary` 时停止，通过输出参数 `total_count` 返回累计的员工总人数。编写完整的定义脚本与调用验证命令。

**标准解析与答案**：
1. 局部变量中，累加和 `sum_sal` 与计数器 `emp_count` 必须赋予初始值 0；
2. 游标 `emp_cursor` 查询语句必须附加 `ORDER BY salary DESC`；
3. 游标开启后通过 `REPEAT ... UNTIL sum_sal >= limit_total_salary END REPEAT;` 推进；
4. 退出循环后将计数器赋值给 `total_count`，并务必调用 `CLOSE emp_cursor;` 释放锁资源。

```sql
DELIMITER $

CREATE PROCEDURE get_count_by_limit_total_salary(
    IN limit_total_salary DOUBLE,
    OUT total_count INT
)
BEGIN
    DECLARE sum_sal DOUBLE DEFAULT 0.0;
    DECLARE emp_sal DOUBLE;
    DECLARE emp_count INT DEFAULT 0;

    DECLARE emp_cursor CURSOR FOR 
        SELECT salary 
        FROM employees 
        ORDER BY salary DESC;

    OPEN emp_cursor;

    REPEAT
        FETCH emp_cursor INTO emp_sal;
        SET sum_sal = sum_sal + emp_sal;
        SET emp_count = emp_count + 1;
    UNTIL sum_sal >= limit_total_salary
    END REPEAT;

    SET total_count = emp_count;

    CLOSE emp_cursor;
END $

DELIMITER ;

-- 调用验证
CALL get_count_by_limit_total_salary(200000, @count);
SELECT @count;
```

#### 题目一：员工总人数统计函数的变量规范化

**需求描述**：

```sql
    RETURN emp_count;
END $

-- 返回结果：107
```

#### 题目二：基于姓名查薪资与会话用户变量的穿透性验证

**需求描述**：
创建存储函数 `ename_salary(emp_name VARCHAR(20))`，根据传入的员工姓氏（`last_name`），返回其薪资。

**核心机制辨析：局部变量 vs 会话用户变量**：
通常在函数内部我们使用 `DECLARE` 定义局部变量。但本题我们特意演示在函数内部使用以 `@` 引导的**会话用户变量**（例如 `@sal`），借此观察变量在函数退出后的外部表现。

**标准代码**：

```sql
DELIMITER $

CREATE FUNCTION ename_salary(emp_name VARCHAR(20))
RETURNS DOUBLE
BEGIN
    -- 使用会话用户变量接收查询结果
    SET @sal = 0.0;

    SELECT salary INTO @sal 
    FROM employees 
    WHERE last_name = emp_name;

    RETURN @sal;
END $

DELIMITER ;

-- 调用函数
SELECT ename_salary('Abel');
-- 返回结果：11000

-- 在函数外部直接验证会话用户变量
SELECT @sal;
-- 返回结果同样为：11000
```

> **深度辨析**：局部变量通过 `DECLARE` 声明，仅在 `BEGIN ... END` 内部有效，执行完毕即在栈内存中销毁；而 `@sal` 是会话级变量，其生命周期贯穿当前客户端连接的始终。即使函数执行结束，外部查询依然能够捕获到该变量的最新值。在团队协同工程开发中，应严格按需选型，避免会话变量污染全局上下文。

#### 题目三：多表关联与部门平均工资计算函数

**需求描述**：
创建存储函数 `dept_sal(dept_name VARCHAR(20))`，根据传入的部门名称，计算并返回该部门员工的平均工资。

**实现思路**：
需要通过 `employees` 与 `departments` 两张表的内连接，匹配 `department_name`，并将 `AVG(salary)` 赋给局部变量 `avg_sal`。

**标准代码**：

```sql
DELIMITER $

CREATE FUNCTION dept_sal(dept_name VARCHAR(20))
RETURNS DOUBLE

    DECLARE avg_sal DOUBLE;

    SELECT AVG(e.salary) INTO avg_sal
    FROM employees e
    JOIN departments d ON e.department_id = d.department_id
    WHERE d.department_name = dept_name;

    RETURN avg_sal;
END $

DELIMITER ;

-- 调用验证（查询 IT 部门平均薪资）

```

#### 题目五：成绩等级判定的 IF 分支与 CASE 分支双解法

**需求描述**：
创建存储函数 `test_if_case(score DOUBLE)`，根据传入的分数评定等级：
- 分数 $> 90$：返回 `'A'`；
- 分数 $> 80$：返回 `'B'`；
- 分数 $> 60$：返回 `'C'`；
- 否则：返回 `'D'`。
分别使用 `IF ... ELSEIF` 与 `CASE WHEN` 两种方式实现。

##### 方式一：IF ... ELSEIF 多分支实现

```sql
DELIMITER $

CREATE FUNCTION test_if_case_if(score DOUBLE)
RETURNS CHAR(1)
BEGIN
    DECLARE score_level CHAR(1);

    IF score > 90 THEN
        SET score_level = 'A';
    ELSEIF score > 80 THEN
        SET score_level = 'B';
    ELSEIF score > 60 THEN
        SET score_level = 'C';
    ELSE
        SET score_level = 'D';
    END IF;

    RETURN score_level;
END $

DELIMITER ;
```

##### 方式二：CASE WHEN 条件表达式实现

```sql
DELIMITER $

CREATE FUNCTION test_if_case_case(score DOUBLE)
RETURNS CHAR(1)
BEGIN
    DECLARE score_level CHAR(1);

    CASE 
        WHEN score > 90 THEN SET score_level = 'A';
        WHEN score > 80 THEN SET score_level = 'B';
        WHEN score > 60 THEN SET score_level = 'C';
        ELSE SET score_level = 'D';
    END CASE;

    RETURN score_level;
END $

DELIMITER ;
```

> **易错点**：`CASE` 分支有两种语法形态：一种是 `CASE 表达式 WHEN 值 THEN ...`，只能用于离散值的等值匹配；另一种是 `CASE WHEN 布尔条件 THEN ...`，可以用于区间、大于小于等复杂表达式。区间等级判断必须采用第二种形态。

#### 题目六：基于薪资区间的动态 DML 批量操作

**需求描述**：
创建存储过程 `test_if_pro(IN sal DOUBLE)`，根据传入的特定工资数值 `sal`，对全表中所有等于该工资的员工执行差异化的 DML 变更：
1. 若 `sal < 3000`：直接删除工资为该数值的所有员工记录；
2. 若 `3000 <= sal <= 5000`：将工资为该数值的员工薪资统一上调 1000 元；
3. 若 `sal > 5000`：将工资为该数值的员工薪资统一上调 500 元。

**业务建模与实现代码**：

```sql
DELIMITER $

CREATE PROCEDURE test_if_pro(IN sal DOUBLE)
BEGIN
    IF sal < 3000 THEN
        -- 条件 1：低薪触发清理
        DELETE FROM employees WHERE salary = sal;
    ELSEIF sal <= 5000 THEN
        -- 条件 2：中低薪调薪 1000
        UPDATE employees SET salary = salary + 1000 WHERE salary = sal;
    ELSE
        -- 条件 3：其余薪资统一调薪 500
        UPDATE employees SET salary = salary + 500 WHERE salary = sal;
    END IF;
END $

DELIMITER ;
```

**测试跟踪与验证**：
1. **测试删除分支（`sal = 2900`）**：
   原始表中员工编号 116 的薪资恰好为 2900。执行 `CALL test_if_pro(2900);` 后，重新查询 `employees`，116 号员工已被彻底物理删除。
2. **测试涨薪 1000 分支（`sal = 3100`）**：
   原员工编号 115 的薪资为 3100。执行 `CALL test_if_pro(3100);` 后，再次查询其薪资，准确跃升为 4100 元。
3. **测试涨薪 500 分支（`sal = 24000`）**：
   原高管薪资为 24000。执行 `CALL test_if_pro(24000);` 后，薪资准确调整为 24500 元。

#### 题目七：性能压测利器——海量随机测试数据批量生成

在后续进阶篇讲解索引底层原理、B+ 树扫描以及慢查询日志时，数据库中几十条小数据根本无法体现全表扫描与索引扫描的性能差异。为了模拟百万级真实压测场景，掌握在存储过程中通过循环批量生成模拟数据是每一位后端工程师的看家本领。

**需求描述**：
向 `admin` 表（包含自增主键 `id`、用户名 `user_name` 与密码 `password`）中批量插入指定条数的模拟测试数据。
创建存储过程 `insert_data(IN insert_count INT)`，参数表示需要生成的记录行数。

```text
批量随机造数逻辑流程图：

  [ 循环初始化: init_count = 1 ]
             │
             ▼
  [ 循环判定: init_count <= insert_count ] ────(超出)──► [ 循环结束 ]
             │ (满足条件)
             ▼
  [ 随机值生成: ]
  - user_name ──► CONCAT('@atguigu-', init_count)
  - password  ──► ROUND(RAND() * 1000000) (生成 6 位随机密文)
             │
             ▼
  [ 执行 INSERT INTO admin VALUES(...) ]
             │
             ▼
  [ 迭代步进: init_count = init_count + 1 ] ───► 回到循环判定
```

**标准代码**：

```sql
-- 1. 创建目标测试表
CREATE TABLE IF NOT EXISTS admin (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_name VARCHAR(20) NOT NULL,
    password VARCHAR(20) NOT NULL
);

-- 2. 创建批量插入存储过程
DELIMITER $

CREATE PROCEDURE insert_data(IN insert_count INT)
BEGIN
    -- 1. 声明循环计数器（初始化条件）
    DECLARE init_count INT DEFAULT 1;

    -- 2. WHILE 循环结构（循环条件）
    WHILE init_count <= insert_count DO
        -- 3. 循环体：利用单行函数构建具备区分度的随机数据
        INSERT INTO admin(user_name, password) 
        VALUES (
            CONCAT('@atguigu-', init_count),
            ROUND(RAND() * 1000000)
        );

        -- 4. 迭代条件：绝对不能遗漏，否则必然死循环！
        SET init_count = init_count + 1;
    END WHILE;

END $

DELIMITER ;

-- 调用验证：极速插入 100 条随机数据
CALL insert_data(100);

-- 查看插入结果
SELECT COUNT(*) FROM admin; -- 返回 100
SELECT * FROM admin LIMIT 5;
```

### 游标与复合业务逻辑的工程级整合

在复杂的数据库应用中，最考验功力的往往是将游标与循环、多分支判断严丝合缝地嵌套起来。

#### 题目八：基于薪资排序与入职年份的阶梯调薪存储过程

**业务背景与需求**：
公司希望对特定部门进行薪资结构优化。但由于预算有限，不能对该部门全员涨薪，而是需要精准筛选出该部门内**薪资最低的前 N 名员工**实施保底调薪。
同时，为了体现司龄关怀，不同入职年份的员工享受不同的涨薪幅度：
- 入职年份 $< 1995$ 年：薪资上调 20%（`salary * 1.20`）；
- $1995 \le$ 入职年份 $\le 1998$ 年：薪资上调 15%（`salary * 1.15`）；
- $1998 <$ 入职年份 $\le 2001$ 年：薪资上调 10%（`salary * 1.10`）；
- 其余（入职年份 $> 2001$ 年）：薪资上调 5%（`salary * 1.05`）。

要求创建存储过程 `update_salary(IN dept_id INT, IN change_sal_count INT)`：
- 参数 1 为目标部门编号；
- 参数 2 为需要调薪的最低薪资员工人数。

#### 技术选型与算法剖析

为什么该需求必须使用游标？
1. **行数截断性**：如果直接使用 `UPDATE ... WHERE department_id = dept_id`，会将全部门所有员工更新；虽然普通 `UPDATE` 支持 `LIMIT`，但无法针对每一行不同的入职年份计算不同的涨薪系数。
2. **状态依赖计算**：我们需要游标先按 `salary ASC` 排好序，按序精准抓取前 `change_sal_count` 行，在抓出单行的瞬间提取其 `employee_id` 与 `hire_date`，通过 `YEAR(hire_date)` 算出其对应的调薪倍率，然后针对该具体的 `employee_id` 执行单行精准更新。

#### 完整代码实现

```sql
DELIMITER $

CREATE PROCEDURE update_salary(
    IN dept_id INT, 
    IN change_sal_count INT
)
BEGIN
    -- 1. 声明局部变量（必须置于首部）
    DECLARE emp_id INT;                      -- 承接游标读取的员工 ID
    DECLARE emp_hire_date DATE;              -- 承接游标读取的入职日期
    DECLARE init_count INT DEFAULT 1;        -- 循环计数器（初始化条件）
    DECLARE add_rate DOUBLE;                 -- 动态记录计算出的调薪比例

    -- 2. 声明游标：锁定目标部门，并严格按薪资升序排列
    DECLARE emp_cursor CURSOR FOR 
        SELECT employee_id, hire_date 
        FROM employees 
        WHERE department_id = dept_id 
        ORDER BY salary ASC;

    -- 3. 打开游标
    OPEN emp_cursor;

    -- 4. 循环控制：严格控制只迭代指定的员工数量
    WHILE init_count <= change_sal_count DO
        -- 逐行提取数据（字段数量与类型必须一一对应）
        FETCH emp_cursor INTO emp_id, emp_hire_date;

        -- 多分支业务判断：根据入职年份确定阶梯涨薪倍率
        IF YEAR(emp_hire_date) < 1995 THEN
            SET add_rate = 1.20;
        ELSEIF YEAR(emp_hire_date) <= 1998 THEN
            SET add_rate = 1.15;
        ELSEIF YEAR(emp_hire_date) <= 2001 THEN
            SET add_rate = 1.10;
        ELSE
            SET add_rate = 1.05;
        END IF;

        -- 针对当前游标锁定的单名员工执行精准更新
        UPDATE employees 
        SET salary = salary * add_rate 
        WHERE employee_id = emp_id;

        -- 递增迭代计数器，推进循环
        SET init_count = init_count + 1;
    END WHILE;

    -- 5. 必须显式关闭游标，释放内存与行锁
    CLOSE emp_cursor;

END $

DELIMITER ;
```

#### 执行跟踪与现场数据比对验证

我们以拥有 43 名员工的 50 号部门为例进行实测：

```sql
-- 1. 调薪前观察 50 号部门薪资最低的员工基准情况
SELECT employee_id, hire_date, salary 
FROM employees 
WHERE department_id = 50 
ORDER BY salary ASC;
```

查询结果显示，50 号部门薪资最低的前三位员工为：
- 员工 132：薪资 2100；
- 员工 128：薪资 2200；
- 员工 136：薪资 2200；
- 第四位之后的员工（如 127、135）薪资为 2400 及以上。

现在我们调用存储过程，要求**仅仅给薪资最低的前 3 位员工调薪**：

```sql
CALL update_salary(50, 3);
```

**调薪后结果比对**：
再次执行查询，发现员工 132、128、136 的薪资已经分别根据各自的入职年份顺利乘以了调薪系数；而排在第 4 位及以后的员工 127、135 薪资依然纹丝不动保持 2400。
这完美验证了游标对于“特定边界集合内部精细化逐行运算”的强大控制力。

## 92-创建触发器
> 对应分集：P92 | 原始标题：《92-创建触发器》

在关系型数据库管理中，保证数据的一致性与完整性始终是系统的核心生命线。我们在实际电商项目中经常遇到这样的经典场景：每年“双十一”大促期间，当运营人员录入一条全新的商品档案时，不仅需要向“商品信息表”中插入一条记录，同时必须向“库存信息表”中同步初始化该商品的库存数量。商品档案和库存数据是一对孪生兄弟，如果商品表录入了而库存表漏更，整个交易链路就会直接瘫痪。

为了保证这种强关联操作的原子性，我们通常可以使用**事务（Transaction）**在应用层包裹多条 SQL，确保它们“要么全执行，要么全不执行”；或者依赖后端研发人员编写双写逻辑。但人工维护总有疏漏的风险，代码一旦遗漏，数据完整性就荡然无存。

针对这类“由一个表的数据变更自动牵引关联表联动同步”的诉求，MySQL 提供了**触发器（Trigger）**。触发器不同于需要显式调用的存储过程，它是由数据库底层事件自动唤醒执行的。本讲我们将从触发器的本质机理出发，深入剖析其事件驱动模型与完整的定义语法，并通过基础审计日志记录以及结合 `NEW` 虚拟行和自定义异常抛出的高阶校验拦截，全面打通触发器的构建与实操。

---

### 触发器的本质定位与事件驱动架构

触发器（Trigger）自 MySQL 5.0 版本便已被引入，是与表、视图、存储过程、存储函数平级的独立数据库对象。

#### 触发器与存储过程的根本执行差异

初学者经常将触发器与存储过程混为一谈，因为它们内部都可以书写复杂的 `BEGIN ... END` 复合语句块，都可以使用变量与分支控制。但它们在**调用触发机制**上有着天壤之别：

```text
存储过程主动调用 vs 触发器被动事件监听架构对比：

  [ 存储过程 Procedure: 主动调用模型 ]
   客户端/应用程序 ──► 显式发送 CALL proc_name() ──► 数据库引擎执行逻辑 ──► 抛出结果集

  [ 触发器 Trigger: 事件驱动监听模型 ]
   客户端/应用程序 ──► 向业务表执行 DML 操作 ──────► [ MySQL 内部事件分发器 ]
                      (INSERT / UPDATE / DELETE)           │ (捕获表事件)
                                                           ▼
                                               [ 挂载在表上的触发器 Trigger ]
                                               (自动捕获 NEW/OLD 数据并执行后续逻辑)
```

- **存储过程**：是主动调用的。无论是前端后台还是 DBA，必须在终端或代码中主动键入 `CALL 存储过程名()` 才会触发；
- **触发器**：**严禁且无法被显式调用**。它像一个潜伏在业务表背后的“监听器”，静默监视着表上的数据流。只有当用户对该表执行了特定的增、删、改（DML）操作时，MySQL 引擎才会自动、强制地调起该触发器。

#### 移动端 UI 监听器类比：理解事件驱动模型

我们可以将 MySQL 触发器与移动端手机 App 的 UI 事件机制进行生动类比：
- 在手机界面上，当你点击一个“提交”按钮时，系统会产生一个“点击事件（Click Event）”，挂载在按钮上的事件监听器（OnClickListener）就会被回调，执行数据打包并发送给服务器的代码；
- 当你在屏幕长按一张图片时，系统会触发“长按事件（LongClick Event）”，进而弹出包含“保存图片”、“转发”、“分享”的对话框；
- 在数据库中，**事件（Event）**就是用户对某张表发起的 `INSERT`、`UPDATE` 或 `DELETE` 操作；而**触发器（Trigger）**就是绑定在该表上的监听器。只要指定的 DML 事件发生，触发器内部预埋的业务逻辑就会瞬时激活。

> **定义**：触发器是由 MySQL 事件驱动的特殊存储过程。它与特定的数据表紧密绑定，当表发生特定的插入、修改或删除操作时，由数据库引擎自动触发执行，主要用于强制实施复杂的数据完整性规则与审计追踪。

### 触发器的创建语法体系与四大核心维度

创建触发器有着极其规整的 DDL 语法。

#### 语法骨架剖析

创建触发器的标准语法模板如下：

```sql
CREATE TRIGGER 触发器名称
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON 表名
FOR EACH ROW
BEGIN
    触发器执行逻辑代码（复合语句块）
END;
```

定义一个完备的触发器，必须明确以下四大核心维度：
1. **监视地点（`ON 表名`）**：触发器必须深度寄生于某一张具体的物理表上，不能脱离具体的表而空泛存在。
2. **监视事件（`INSERT | UPDATE | DELETE`）**：指明该触发器只对哪一种 DML 动作产生响应。若绑定的是 `DELETE` 事件，那么向该表插入新数据时，该触发器绝不会执行。
3. **触发时机（`BEFORE | AFTER`）**：
   - `BEFORE`：在目标表的物理写入操作发生**之前**执行触发器代码。通常用于**数据前置校验、非法值拦截或默认值自动修正**；
   - `AFTER`：在目标表的物理变更顺利落盘**之后**执行触发器代码。通常用于**联动更新关联表、写入系统操作审计日志或统计汇总**。
4. **触发频率（`FOR EACH ROW`）**：行级触发器声明。在 MySQL 中，如果一条批量更新或删除语句同时影响了 10 行数据，该触发器就会被**严格触发执行 10 次**。

#### 命名规范与 DELIMITER 结束符重申

在实际生产工程中，一个数据库中可能存在几十上百个触发器。为了避免对象名混淆与冲突，建议遵循清晰的语义化命名规范：
- 推荐格式：`{时机}_{事件}_{表名}_tri`，例如 `before_insert_test_tri` 或 `after_delete_order_tri`。

此外，由于触发器内部包含完整的复合语句块，往往涉及多条以英文分号结尾的 SQL 语句。若不重新定义结束符，MySQL 客户端在读到第一个分号时就会误以为整条 DDL 已经结束，从而抛出语法截断错误。因此，**在创建触发器前后必须使用 `DELIMITER` 修改结束标记**：

```sql
DELIMITER $
-- 创建触发器逻辑...
DELIMITER ;
```

### 基础实战：BEFORE 与 AFTER 审计日志联动

我们首先通过两张关联测试表，直观体验触发器的自动激活与时序差异。

#### 准备环境与测试表构建

我们在数据库 `dbtest17` 中创建业务测试表 `test_trigger` 和操作日志表 `test_trigger_log`：

```sql
CREATE DATABASE IF NOT EXISTS dbtest17;
USE dbtest17;

-- 1. 业务主表：记录员工姓名
CREATE TABLE test_trigger (
    id INT PRIMARY KEY AUTO_INCREMENT,
    t_note VARCHAR(30)
);

-- 2. 日志从表：记录操作轨迹
CREATE TABLE test_trigger_log (
    id INT PRIMARY KEY AUTO_INCREMENT,
    t_log VARCHAR(30)
);
```

#### 案例一：创建 BEFORE INSERT 触发器

**需求**：在向 `test_trigger` 插入数据之前，自动向 `test_trigger_log` 插入一条记录 `'before_insert'`。

```sql
DELIMITER $

CREATE TRIGGER before_insert_test_tri
BEFORE INSERT ON test_trigger
FOR EACH ROW
BEGIN
    INSERT INTO test_trigger_log(t_log) 
    VALUES('before_insert');
END $

DELIMITER ;
```

**测试与验证**：
执行数据插入并观察主从两表的变化：

```sql
-- 向主表插入一条记录
INSERT INTO test_trigger(t_note) VALUES('Tom');

-- 查询主表数据
SELECT * FROM test_trigger;
-- 结果展示：id=1, t_note='Tom'

-- 查询日志表数据
SELECT * FROM test_trigger_log;
-- 结果展示：id=1, t_log='before_insert'
```

我们完全没有对 `test_trigger_log` 表编写过任何 `INSERT` 命令，但日志记录却如影随形地被自动创建，证明触发器已被平稳激活。

#### 案例二：创建 AFTER INSERT 触发器（多触发器共存）

**需求**：在向 `test_trigger` 插入数据之后，自动向 `test_trigger_log` 插入一条记录 `'after_insert'`。

```sql
DELIMITER $

CREATE TRIGGER after_insert_test_tri
AFTER INSERT ON test_trigger
FOR EACH ROW
BEGIN
    INSERT INTO test_trigger_log(t_log) 
    VALUES('after_insert');
END $

DELIMITER ;
```

此时，`test_trigger` 表上同时挂载了两个针对 `INSERT` 事件的触发器。
我们再次向主表插入一条新记录 `'Jerry'`：

```sql
INSERT INTO test_trigger(t_note) VALUES('Jerry');

-- 再次查询日志表
SELECT * FROM test_trigger_log;
```

**日志表最新输出结构**：
```text
+----+---------------+
| id | t_log         |
+----+---------------+
|  1 | before_insert |  <-- 插入 Tom 时生成
|  2 | before_insert |  <-- 插入 Jerry 发生前生成
|  3 | after_insert  |  <-- 插入 Jerry 顺利完成后生成
+----+---------------+
```
数据结果严谨印证了执行时序：先走 `BEFORE` 触发器，再落盘主表记录，最后走 `AFTER` 触发器。

### 高阶实战：NEW 伪行与 SIGNAL 业务约束拦截

仅记录静态字符日志远远无法满足复杂的企业级业务控制。在触发器内部，我们往往需要动态获取“当前正在被插入/更新/删除的那一行具体字段值”，并据此展开逻辑运算。

#### NEW 与 OLD 伪行变量机制

MySQL 触发器内部提供了两个至关重要的虚拟对象（伪行）：`NEW` 与 `OLD`。

| DML 操作类型 | `OLD` 虚拟行的含义 | `NEW` 虚拟行的含义 |
| :--- | :--- | :--- |
| **`INSERT`** | 无效（不存在旧记录） | 指代**即将插入或已插入的新数据行**，如 `NEW.salary` |
| **`UPDATE`** | 指代**被修改前的原始旧数据行**，如 `OLD.salary` | 指代**修改后的全新数据行**，如 `NEW.salary` |
| **`DELETE`** | 指代**即将被删除或已删除的原数据行**，如 `OLD.id` | 无效（删除后无新记录） |

```text
NEW 伪行在 INSERT 过程中的数据流动：

  客户端执行 INSERT INTO employees(salary, manager_id) VALUES(10000, 103);
                               │
                               ▼
               ┌───────────────────────────────┐
               │ NEW 虚拟行内存镜像             │
               │ NEW.salary = 10000            │
               │ NEW.manager_id = 103          │
               └───────────────┬───────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
   在触发器内部查询领导薪资             比较: IF NEW.salary > mgr_salary
   SELECT salary INTO mgr_sal          
   FROM employees WHERE employee_id = NEW.manager_id;
```

#### SIGNAL 异常主动抛出机制

在早期的 SQL 编程中，若想在触发器中强行中断用户操作，往往使用“除以零”或插入非法字段等旁门左道。而在现代 MySQL（5.5+）中，官方提供了标准的异常抛出语法——`SIGNAL`：

```sql
SIGNAL SQLSTATE '错误状态码' SET MESSAGE_TEXT = '自定义错误提示文案';
```

> **结论**：当在 `BEFORE` 触发器中执行 `SIGNAL` 命令时，MySQL 引擎会捕获该未处理的严重错误，**立即强制终结当前代码向下执行的权利**。由于前置校验未通过，原始引发触发器的 `INSERT` 动作将被整体阻断回滚，从而实现企业级强数据校验拦截。

#### 案例三：新员工薪资不得高于直接领导的业务拦截

**需求描述**：
基于员工表 `employees` 创建触发器 `salary_check_trigger`。在向该表插入新员工记录之前（`BEFORE INSERT`），动态查询出该员工所指定的直接领导（`manager_id`）的当前薪资。
- 若新员工薪资（`NEW.salary`）大于直接领导的薪资，则使用 `SIGNAL SQLSTATE` 抛出错误：`'薪资高于领导薪资错误'`，坚决阻断该员工的入职数据落盘；
- 若新员工薪资小于等于领导薪资，则触发器平稳放行，允许正常入职。

**完整代码实现**：

```sql
-- 准备工作：从基准库中复制员工表到当前库
CREATE TABLE employees AS SELECT * FROM atguigudb.employees;

DELIMITER $

CREATE TRIGGER salary_check_trigger
BEFORE INSERT ON employees
FOR EACH ROW
BEGIN
    -- 1. 声明局部变量：记录领导的薪资
    DECLARE mgr_salary DOUBLE;

    -- 2. 借助 NEW 伪行，精准查询出该新员工领导的当前薪资
    SELECT salary INTO mgr_salary 
    FROM employees 
    WHERE employee_id = NEW.manager_id;

    -- 3. 业务校验拦截
    IF NEW.salary > mgr_salary THEN
        SIGNAL SQLSTATE 'HY000' 
        SET MESSAGE_TEXT = '薪资高于领导薪资错误';
    END IF;

END $

DELIMITER ;
```

#### 拦截效果验证

我们预先查询已知编号为 103 的部门领导薪资为 9,000 元。

##### 场景 A：薪资合规测试（薪资 8000 < 领导 9000）

```sql
INSERT INTO employees(
    employee_id, last_name, email, hire_date, job_id, salary, manager_id
) VALUES(
    300, 'Tom', 'tom@126.com', CURDATE(), 'AD_VP', 8000, 103
);
```
执行结果：命令瞬间成功执行，受到影响行数为 1。重新查询 `employees`，员工 Tom 顺利入职。这表明合规数据顺利穿透了触发器的 `BEFORE` 检查。

##### 场景 B：违规薪资拦截测试（薪资 10000 > 领导 9000）

```sql
INSERT INTO employees(
    employee_id, last_name, email, hire_date, job_id, salary, manager_id
) VALUES(
    301, 'Tom1', 'tom1@126.com', CURDATE(), 'AD_VP', 10000, 103
);
```
执行结果：MySQL 客户端立即中断并爆出红色阻断异常：
```text
Error Code: 1644. 薪资高于领导薪资错误
```
我们随后执行 `SELECT * FROM employees WHERE employee_id = 301;`，返回空结果集。证明在触发器执行 `SIGNAL` 的瞬间，后续的物理写入动作已被彻底扼杀，数据完整性得到了坚如磐石的保障。

#### 题目三：利用 NEW 伪行与 SIGNAL 实现薪资风控校验

**题干要求**：

**标准答案**：
```sql
DELIMITER $
CREATE TRIGGER salary_check_trigger
BEFORE INSERT ON employees
FOR EACH ROW
BEGIN
    DECLARE mgr_salary DOUBLE;

    SELECT salary INTO mgr_salary 
    FROM employees 
    WHERE employee_id = NEW.manager_id;

    IF NEW.salary > mgr_salary THEN
        SIGNAL SQLSTATE 'HY000' 
        SET MESSAGE_TEXT = '薪资高于领导薪资错误';
    END IF;
END $
DELIMITER ;
```

## 93-查看删除触发器_触发器课后练习
> 对应分集：P93 | 原始标题：《93-查看删除触发器_触发器课后练习》

我们在前一讲掌握了触发器（Trigger）的基础概念与创建语法。存储过程与函数可以通过显式的 `CALL` 或 `SELECT` 按需调用，但触发器完全不同——它像是一个静默潜伏在底层的“监听器”，由特定表上的 DML 事件（INSERT、UPDATE、DELETE）自动激活。这种“隐式触发”的特性决定了它的运维与管理方式具备独特性。

如果在开发环境中随手创建了触发器，后续业务表结构发生变更，或者逻辑已经废弃却未清理，这些静默执行的代码就会在底层引发各种诡异的报错与隐蔽故障。因此，如何精准查看系统中的触发器定义、在何种时机果断将其删除、触发器在实际业务中的利弊边界何在，以及如何在生产中运用它实现数据的自动化备份与审计，是每一位数据库开发者必须扎实掌握的内容。

---

### 触发器的查看方式

在 MySQL 中查看已经存在的触发器，通常有三种方式：使用 `SHOW TRIGGERS` 查看当前库的所有触发器概览、使用 `SHOW CREATE TRIGGER` 调取特定触发器的完整创建代码，或者直接查询系统的元数据字典表 `information_schema.TRIGGERS`。

#### 使用 SHOW TRIGGERS 查看当前数据库的所有触发器

`SHOW TRIGGERS` 命令用于列出当前上下文数据库中定义的所有触发器信息。

```sql
-- 查看当前数据库中的所有触发器
SHOW TRIGGERS;
```

在图形化管理工具（如 SQLyog、Navicat）中，可以直接执行上述语句输出表格型数据。但在终端命令行（CLI）中，因为触发器的定义字段较多、包含的 SQL 语句较长，表格排版往往会被挤压换行，导致整体可读性极差。此时，可以在命令行末尾使用 `\G` 替代分号 `;`，让 MySQL 将每一行记录按照垂直键值对的形式展开输出。

> **注意**：
> 在命令行使用 `\G` 时，末尾**严禁再加分号**，否则会引发语法错误；而在图形化工具（如 SQLyog）中，`\G` 往往无法被解析识别，在 GUI 环境中直接使用分号 `;` 结尾即可。

在终端中执行的效果如下：

```sql
mysql> USE dbtest17;
mysql> SHOW TRIGGERS\G
```

系统会输出类似如下的详细属性块：

```text
*************************** 1. row ***************************
             Trigger: salary_check_trigger
               Event: INSERT
               Table: employees
           Statement: BEGIN
                      DECLARE mgr_sal DOUBLE;
                      SELECT salary INTO mgr_sal FROM employees WHERE employee_id = NEW.manager_id;
                      IF NEW.salary > mgr_sal THEN
                          SIGNAL SQLSTATE 'HY000' SET MESSAGE_TEXT = '薪资不能超过直属领导薪资！';
                      END IF;
                      END
              Timing: BEFORE
             Created: 2026-09-14 10:20:15.00
            sql_mode: ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE...
             Definer: root@localhost
character_set_client: utf8mb4
collation_connection: utf8mb4_0900_ai_ci
  Database Collation: utf8mb4_0900_ai_ci
```

输出各字段的核心含义说明如下：
- `Trigger`：触发器的名称。
- `Event`：激活触发器的事件类型，为 `INSERT`、`UPDATE` 或 `DELETE` 之一。
- `Table`：该触发器所绑定的数据表名称。
- `Statement`：触发器执行时执行的程序体内容（即 `BEGIN ... END` 之间的逻辑语句）。
- `Timing`：触发时机，为 `BEFORE`（操作前）或 `AFTER`（操作后）。
- `Created`：触发器创建的精确时间戳。
- `sql_mode`：创建该触发器时会话所使用的 SQL 模式（例如严格模式等）。
- `Definer`：创建并拥有该触发器的用户账户（如 `root@localhost`）。
- `character_set_client` / `collation_connection`：客户端字符集以及连接校对规则。

> **提示**：
> `SHOW TRIGGERS` 列出触发器的顺序并不严格等同于创建触发器的先后顺序。如果需要核实确切的创建时序，应当以输出结果中的 `Created` 时间戳字段为准。

#### 使用 SHOW CREATE TRIGGER 查看指定触发器的创建语句

当业务库中积累了大量触发器时，若通过 `SHOW TRIGGERS` 打印全库信息会显得繁杂杂乱。如果需要定位特定触发器的精确建表与定义脚本，可以使用 `SHOW CREATE TRIGGER`：

```sql
SHOW CREATE TRIGGER 触发器名称;
```

例如查看薪资校验触发器的创建语句：

```sql
-- 在 SQLyog 等客户端中查看
SHOW CREATE TRIGGER salary_check_trigger;

-- 在终端命令行中使用 \G 展开格式化查看
SHOW CREATE TRIGGER salary_check_trigger\G
```

输出结果包含三大部分：
1. `Trigger`：触发器名称。
2. `sql_mode`：创建时的环境模式配置。
3. `SQL Original Statement`：当初创建该触发器时所书写的原始 DDL 完整语句（包括 `CREATE DEFINER=... TRIGGER ...`、`BEFORE/AFTER` 时机、`FOR EACH ROW` 以及完整的 `BEGIN ... END` 事务体代码）。
4. 相关的客户端字符集编码元数据。

#### 查询 information_schema.TRIGGERS 系统元数据表

MySQL 将整个实例的所有元数据统一集中存储在系统自带的 `information_schema` 架构库中。触发器对应的元数据表是 `information_schema.TRIGGERS`。

这种方式的灵活性在于支持使用标准的 `SELECT ... WHERE` 语法进行条件筛选、多字段投影或跨库检索：

```sql
-- 查询系统全部触发器（包含 MySQL 系统库和所有业务库）
SELECT * FROM information_schema.TRIGGERS;

-- 精准查询指定数据库下的触发器名称、事件与触发时机
SELECT 
    TRIGGER_SCHEMA AS '所属数据库',
    TRIGGER_NAME AS '触发器名',
    EVENT_MANIPULATION AS '触发事件',
    EVENT_OBJECT_TABLE AS '监听表名',
    ACTION_TIMING AS '触发时机',
    CREATED AS '创建时间'
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = 'dbtest17';
```

当我们需要在自动化脚本、监控工具或运维平台中检查数据库规范时，直接查询 `information_schema.TRIGGERS` 表是最标准、最易集成的途径。

### 触发器的删除操作

删除触发器的语法极为简洁，与删除表、视图、存储过程遵循完全相同的 DDL 设计风格：

```sql
DROP TRIGGER [IF EXISTS] [schema_name.]trigger_name;
```

若要在当前数据库中删除名为 `after_insert_test_trigger` 的触发器，标准写法如下：

```sql
DROP TRIGGER IF EXISTS after_insert_test_trigger;
```

#### 为什么不用的触发器必须及时显式删除？

在日常开发中，我们可能在数据库中遗留了一些不用的存储过程或自定义函数。对于存储过程，只要应用层不显式调用 `CALL my_procedure()`，或者对于函数不调用 `SELECT my_func()`，它们就仅仅以静态元数据的形式保存在数据字典中，除了占用极微量的磁盘空间外，不会对运行时的增删改查产生任何副作用。

但**触发器截然不同**：
1. **隐匿性强**：触发器不需要人为显式调用，只要目标表上发生了对应的 `INSERT`、`UPDATE` 或 `DELETE` 语句，MySQL 引擎就会在底层强制拦截并自动触发它。
2. **破坏性强**：如果业务逻辑发生变动，某个触发器已经不再符合现实需求，但由于它被遗忘在数据库中，只要后续开发人员向该表写入数据，该触发器仍会在暗中被动激活。这极易导致数据被旧逻辑篡改，或者在主业务流程中抛出不明原因的异常阻断执行。

> **结论**：
> 触发器一旦确定废弃，必须第一时间使用 `DROP TRIGGER` 彻底移出数据库，绝不能采取“留着不调它”的侥幸心理。

---

### 触发器的优缺点与工程适用边界

任何技术特性的出现都是一把双刃剑，触发器同样具备鲜明的两面性。

#### 核心优点

触发器运行在数据库底层存储引擎与事务边界之内，具备脱离上层应用程序独立运作的特性，其主要优势体现在以下三方面：

##### 优点一：强力保证数据的完整性与一致性
当系统存在复杂的从属数据或者多表联动计算时，触发器能够实现强一致的闭环计算。

以典型的电商或零售 ERP 场景为例：
- 系统中存在一张**进货单头表**（记录单据编号、供货商、总进货件数、总金额）与一张**进货单明细表**（记录每一笔具体商品的进货数量、采购单价、明细金额）。
- 进货单头表中的“总进货件数”与“总金额”必须严格等于该单据下所有明细条目的代数累加和。

```text
[ 客户端写入/修改/删除 ]
           │
           ▼
    ┌──────────────┐
    │ 进货单明细表 │
    └──────┬───────┘
           │ 自动激活触发器 (AFTER INSERT/UPDATE/DELETE)
           ▼
    ┌──────────────────────────────────────────────┐
    │ 触发器内部重算明细表 SUM(数量) 与 SUM(金额)  │
    └──────────────────────┬───────────────────────┘
                           │ UPDATE 同步写入
                           ▼
                    ┌──────────────┐
                    │ 进货单头表   │
                    └──────────────┘
```
*读图说明：对明细表的任何 DML 都会在底层原子地驱动头表统计值的刷新，确保两张表的数据分秒不差、绝对闭环。*

当进货单明细表发生任何新增、修改或删除记录时，只要配置了触发器，底层就会自动重新计算明细表中对应单据的总数与总金额，并同步回写至进货单头表，彻底规避了应用层由于网络波动、代码分支疏漏导致的主从表数据不一致。

##### 优点二：自动化审计与操作日志留痕
在涉及金融账务、会员储值、资产变动的核心系统中，每一笔操作的发生时机与变更明细都必须具备可追溯性。

例如会员充值业务：
- 应用程序主要对 `member` 会员表的 `balance` 余额字段执行 `UPDATE`。
- 如果在数据库层为 `member` 表绑定一个 `AFTER UPDATE` 触发器，每当检测到余额字段被更改，便自动将变更前金额（`OLD.balance`）、变更后金额（`NEW.balance`）、操作时间戳（`NOW()`）以及操作用户抓取并插入到独立的 `member_recharge_log` 审计日志表中。
- 即使应用层开发人员忘记写记日志的代码，或者存在多个独立微服务都在修改会员表，数据库底层均能一视同仁地实现 100% 审计留痕，防范漏记隐患。

##### 优点三：在持久化前进行强制性合法性校验（防呆防错）
人为录入操作常常会出现严重失误。例如：
- 超市库管在录入商品进货数量时，误将商品条形码（一串极长的 13 位数字）扫入了数量字段，导致进货数量被录成数亿件；
- 在手工录入进货成本单价时，看错行把原本售价 100 元的商品进货价输成了 1000 元，导致系统在后续销售中“卖得越多、亏得越惨”。

类似现实生活中电商平台偶尔发生的“两千元手机标错成两百元瞬间被抢空”等标价事故，若能在数据库层面借助 `BEFORE` 触发器设置一道刚性防线（如校验 `NEW.quantity <= 10000` 且 `NEW.purchase_price <= NEW.retail_price`），当数值异常时直接阻断并抛出异常，便能把严重的人为录入事故扼杀在持久化之前。

---

#### 核心缺点与维护风险

尽管功能强大，但在现代互联网软件架构与大中型系统中，阿里《Java开发手册》等行业规范普遍**明文禁止或严格限制使用触发器**，原因主要在于其不可控的隐蔽性与维护灾难：

##### 缺点一：逻辑极度隐蔽，代码可读性与可调试性极差
触发器完全脱离于应用程序代码库（如 Java / Go / Python 源码）。应用层工程师发起一条简单的 `INSERT INTO t_note VALUES (...)`，控制台却突然莫名其妙报出错误：
```text
ERROR 1406 (22001): Data too long for column 'remark' at row 1
```
开发者反复排查 `t_note` 的表定义与传入参数，发现传入的字符串长度明明只有 20 个字符，而字段允许 50 个字符。最终几经周折才在数据库底层排查出：该表挂载了一个触发器，触发器内部尝试将操作动作记录到另一张叫 `t_log` 的日志表，而 `t_log` 表的 `remark` 字段长度仅为 10，导致了字段溢出报错！

又比如用户进行会员充值，只更新了余额字段，数据库却报错说“不存在字段 A”。开发者甚至会误以为是表缺字段，盲目在原表添加字段 A，其实是触发器内部 SQL 写错了关联目标表的字段名。这种“隔山打牛”式的底层联锁，极大增加了系统定位问题的成本。

##### 缺点二：级联依赖脆弱，表结构变更极易触发大面积雪崩
触发器将多个表紧紧耦合在了一起。一旦被触发表或关联表的字段名被修改、字段被删除，或者类型产生变更，原有的触发器并不会在表结构变更的瞬间报错。然而，当后续任意一笔正常的业务写入抵达该表时，触发器便会骤然崩溃，进而导致主业务事务全盘回滚，引发大面积生产事故。

#### 关键边界认知：外键级联与触发器的激活机制

在数据库中同时使用外键（Foreign Key）与触发器时，存在一个极其容易混淆的核心机制：

设有两个表：
- 父表 `departments`（部门表，主键为 `department_id`）；
- 子表 `employees`（员工表，外键为 `department_id`，关联父表主键）。

为该外键定义了级联规则：
```sql
ALTER TABLE employees ADD CONSTRAINT fk_emp_dept 
FOREIGN KEY (department_id) REFERENCES departments(department_id)
ON DELETE SET NULL;
```
同时，在子表 `employees` 上挂载了一个针对修改行为的触发器：
```sql
CREATE TRIGGER trg_emp_update AFTER UPDATE ON employees FOR EACH ROW ...
```

**问题场景**：
当我们从父表 `departments` 中删除了 10 号部门的一条记录时，按照级联规则，MySQL 会自动在引擎层将子表 `employees` 中所有部门编号为 10 的员工的 `department_id` 自动置为 `NULL`。

此时，**子表上的 UPDATE 触发器是否会被激活？**

> **结论**：
> **不会被激活**！
> 由外键约束的级联行为（如 `ON UPDATE CASCADE`、`ON DELETE SET NULL` 等）所引发的底层从表数据更新或删除，属于存储引擎内部执行的外键级联操作，**绝不会触发**挂载在该从表上的任何行级触发器。这是日常系统架构设计与排错中极易踩坑的关键技术细节。

```sql
-- 创建测试数据库
CREATE DATABASE IF NOT EXISTS test17_trigger CHARACTER SET utf8mb4;
```

此时 `emps` 表包含 `employee_id`、`last_name`、`salary` 三个列，共计 107 条基准记录。

#### 练习 1：新增数据同步备份（AFTER INSERT 场景）

##### 需求描述
1. 创建一张与 `emps` 具备相同结构的空备份表 `emps_back`（仅包含表结构，不包含任何原始数据）；
2. 创建一个名为 `emps_insert_trigger` 的触发器；
3. 要求：每当向 `emps` 表成功添加一条记录后，由触发器自动将新录入的数据同步插入到备份表 `emps_back` 中；
4. 插入测试数据验证同步机制。

##### 实现步骤与代码解析

**第一步：基于原表快速克隆空表结构**
在 SQL 中，快速复制表结构而不携带历史数据，最为经典高效的做法是使用 `WHERE 1 = 2` 这一恒假条件：

```sql
-- 复制空表结构
CREATE TABLE emps_back AS
SELECT * FROM emps WHERE 1 = 2;

-- 确认表中暂无任何数据
SELECT * FROM emps_back;
```
由于 `1 = 2` 永远返回 `FALSE`，查询无法筛选出任何物理记录，MySQL 仅会按查询结果集的列定义来生成新表的字段架构。

**第二步：创建同步触发器**
此处要求添加完成后同步，触发时机选择 `AFTER INSERT`。在触发器内部，代表全新插入数据的关键字是 `NEW`。

```sql
DELIMITER //

CREATE TRIGGER emps_insert_trigger
AFTER INSERT ON emps
FOR EACH ROW
BEGIN
    -- 将刚刚插入 emps 表的各字段通过 NEW 关键字取出，同步插入备份表
    INSERT INTO emps_back(employee_id, last_name, salary)
    VALUES (NEW.employee_id, NEW.last_name, NEW.salary);
END //

DELIMITER ;
```

**第三步：插入数据验证触发器**
我们向 `emps` 表写入两条主键避开现有区间的员工数据：

```sql
-- 插入测试员工 300
INSERT INTO emps(employee_id, last_name, salary)
VALUES (300, 'Tom', 3400);

-- 插入测试员工 301
INSERT INTO emps(employee_id, last_name, salary)
VALUES (301, 'Tom1', 3600);
```

**第四步：验证备份结果**
```sql
SELECT * FROM emps_back;
```
执行后可以看到，`emps_back` 表中已经整齐罗列出了编号 300 的 Tom 与编号 301 的 Tom1。应用层无需关注双写事务，底层触发器已经自动完成了镜像备份。

---

#### 练习 2：删除数据前自动存档（BEFORE DELETE 场景与批量处理机理）

##### 需求描述
1. 创建一张与 `emps` 结构相同的空备份表 `emps_back1`，用于沉淀被删除的废弃员工记录；
2. 创建名为 `emps_del_trigger` 的触发器；
3. 要求：每当从 `emps` 表删除记录之前，自动将即将被删除的数据捕获并转储到备份表 `emps_back1` 中，以实现“逻辑防误删”或“操作回收站”机制；
4. 验证单行删除与批量全表清空场景。

##### 实现步骤与代码解析

**第一步：克隆第二张空备份表**
```sql
CREATE TABLE emps_back1 AS
SELECT * FROM emps WHERE 1 = 2;

-- 验证表为空
SELECT * FROM emps_back1;
```

**第二步：创建删除备份触发器**
在删除数据时，旧数据行即将从物理页中抹除，因此时机选择 `BEFORE DELETE` 尤为安全。此时需要引用的行变量为 `OLD`，表示当前即将在物理上被擦除的原始数据行。

```sql
DELIMITER //

CREATE TRIGGER emps_del_trigger
BEFORE DELETE ON emps
FOR EACH ROW
BEGIN
    -- 使用 OLD 关键字提取即将被删除的旧数据行，写入存档表
    INSERT INTO emps_back1(employee_id, last_name, salary)
    VALUES (OLD.employee_id, OLD.last_name, OLD.salary);
END //

DELIMITER ;
```

**第三步：单行记录删除测试**
我们挑取一条真实员工编号（例如 `employee_id = 101`）执行删除：

```sql
-- 执行前检查原表行数（此前含 107 条初始记录 + 2 条新增，共 109 条）
SELECT COUNT(*) FROM emps;

-- 删除指定员工
DELETE FROM emps WHERE employee_id = 101;

-- 验证原表记录（变更为 108 条）
SELECT * FROM emps WHERE employee_id = 101;

-- 检查备份存档表 emps_back1
SELECT * FROM emps_back1;
```
查询返回包含 `employee_id = 101` 的完整原始行，证明单行拦截存档完全生效。

**第四步：批量删除与 `FOR EACH ROW` 深入验证**
很多初学者会产生疑虑：如果执行一条全表清空语句（批量删除多行），触发器是一次性执行一次，还是对每条记录分别执行？

我们直接在当前会话中执行全表删除：

```sql
-- 彻底清空 emps 表中全部剩余的 108 条数据
DELETE FROM emps;

-- 再次确认 emps 原表已空无一物
SELECT * FROM emps;
```

此时再次查询存档表 `emps_back1`：
```sql
SELECT * FROM emps_back1;
```
结果显示：`emps_back1` 中整整齐齐记录了此前删除的 101 号员工，以及随后被批量删除的全部 108 名员工，总行数准确无误地变成了 109 条！

```text
       SQL 发起：DELETE FROM emps; (影响 108 行)
                     │
    ┌────────────────┴────────────────┐
    │ MySQL 存储引擎逐行迭代删除游标   │
    └────────────────┬────────────────┘
                     ▼
         第 1 行 ──► 触发 emps_del_trigger ──► INSERT INTO emps_back1 (OLD...)
         第 2 行 ──► 触发 emps_del_trigger ──► INSERT INTO emps_back1 (OLD...)
         ...
         第 108 行 ──► 触发 emps_del_trigger ──► INSERT INTO emps_back1 (OLD...)
```
*读图说明：`FOR EACH ROW` 行级契约保证了无论上层 DML 语句是以批处理还是一次一行的形式下发，底层触发器都会按受影响的实际物理行数逐行执行。*

> **深度解析**：
> 在 MySQL 中，触发器一律属于**行级触发器（Row-Level Trigger）**，定义中的 `FOR EACH ROW` 明确规定了：触发器的激活频次严格取决于 DML 语句**实际影响的行数**。
> 上层哪怕只下达了一条 `DELETE FROM emps;` 语句，引擎在物理存储层每删除一行，就会同步调用一次该触发器。
> 在未开启事务回滚保障（或者开启了 `autocommit = 1` 自动提交）的生产环境下，很多初级运维因为一条不加 `WHERE` 条件的 `DELETE` 误删数据而追悔莫及；而若事先部署了这类基于 `OLD` 变量的归档触发器，被删掉的数据便在毫秒之内被无死角地转移到了回收站备份表，直接从备份表执行 `INSERT INTO emps SELECT * FROM emps_back1;` 即可实现快速原地自愈。

#### 题目 1：在 MySQL 中，以下关于触发器的描述哪一项是错误的？
A. 使用 `SHOW TRIGGERS` 可以查看当前数据库中的所有触发器定义  
B. 如果存储过程不用了可以不调它，但触发器只要事件匹配就会执行，废弃时必须显式使用 `DROP TRIGGER` 删除  
C. 当父表主键发生物理删除、且外键设置为 `ON DELETE CASCADE` 级联删除从表行时，从表上定义的 DELETE 触发器会自动执行并记录日志  
D. 触发器中的 `NEW` 代表新插入或修改后的数据，`OLD` 代表被删除或修改前的数据  

**【答案】**：C  
**【解析】**：根据 MySQL 核心存储机制，由外键约束级联操作（`CASCADE` 或 `SET NULL`）所导致的数据行变更，是由存储引擎内部直接处理的底层联动，**不会激活**挂载在目标表上的任何行级触发器。因此 C 项描述错误，符合题意。

#### 题目 2：如何使用 SQL 语句快速克隆一张表 `t_user` 的完整表结构，但要求新表 `t_user_empty` 中不包含任何数据？请写出实现语句并简述原理。

**【答案】**：
```sql
CREATE TABLE t_user_empty AS
SELECT * FROM t_user WHERE 1 = 2;
```
**【解析】**：
`CREATE TABLE ... AS SELECT ...`（CTAS 语法）通过执行子查询并将其架构作为新建表的依据。`WHERE 1 = 2` 是一个永假表达式，查询引擎在评估谓词逻辑时判定条件永远无法成立，因此不会从源表扫描并返回任何物理记录；但解析器能够准确推导出查询结果集的列名、列类型与基本约束，从而快速完成“只克隆空表架构、不携带历史数据”的目标。

#### 题目 3：请编写一个触发器：当向商品库存表 `tb_inventory(goods_id, stock_count)` 执行物理删除时，自动将待删除的 `goods_id`、原库存 `stock_count` 以及删除时刻 `NOW()` 归档至 `tb_inventory_recycle` 回收站表中。

**【答案】**：
```sql
DELIMITER //

CREATE TRIGGER trg_inventory_recycle
BEFORE DELETE ON tb_inventory
FOR EACH ROW
BEGIN
    INSERT INTO tb_inventory_recycle(goods_id, stock_count, deleted_at)
    VALUES (OLD.goods_id, OLD.stock_count, NOW());
END //

DELIMITER ;
```
**【解析】**：
对于删除行为的数据捕获，必须选用 `BEFORE DELETE` 时机并在表体中提取 `OLD` 命名空间下的旧字段值。在执行物理删除操作前，`OLD.goods_id` 与 `OLD.stock_count` 仍然可以被稳定读取，配合内置时间函数 `NOW()` 能够无缝实现删除审计溯源。

## 94-MySQL8.0新特性_窗口函数的使用
> 对应分集：P94 | 原始标题：《94-MySQL8.0新特性_窗口函数的使用》

在学习了存储过程、函数与触发器等数据库高级编程对象之后，我们进入到数据库开发中极具现代感与生产力的一章——MySQL 8.0 的核心新特性。

很多同学会好奇：为什么 MySQL 在 5.7 之后，版本号没有按部就班地命名为 6.0 或 7.0，而是直接大幅跳跃到了 8.0？在软件工程领域，这种跨越式命名本身就是一个明确的技术信号：底层架构与上层语法发生了里程碑式的演化。然而在企业生产实践中，数据库的版本迭代往往比 Java、Go 等应用层编程语言更为审慎。应用层代码用 Java 8 还是 Java 17 重构，影响的往往只是系统运行层；但数据库承载着一家企业沉淀多年的核心数据资产，若非新版本带来了能够颠覆性解决现有业务痛点、大幅提升开发效能与查询性能的杀手级特性，技术团队绝不会轻易冒险进行数据迁移。

在 MySQL 8.0 引入的诸多特性中，最受开发者瞩目、在日常复杂报表统计中能够带来“降维打击”般效能提升的，当属**窗口函数（Window Functions）**。本讲将从底层思维、语法规范到具体分类函数，带大家彻底吃透这一重量级特性。

### MySQL 8.0 新特性全景与架构演进

在深入窗口函数之前，我们先宏观梳理 MySQL 8.0 的技术版图，明确哪些是日常写 SQL 必须掌握的，哪些属于底层运维架构的演进。

```text
               ┌─────────────────────────────────────────────────────────┐
               │                    MySQL 8.0 特性矩阵                   │
               └────────────────────────────┬────────────────────────────┘
                                            │
           ┌────────────────────────────────┼────────────────────────────────┐
           ▼                                ▼                                ▼
    【SQL 编程利器】                  【底层引擎与索引】               【安全、运维与规范】
  ├─ 窗口函数 (Window Functions)   ├─ 降序索引 & 隐藏索引          ├─ 默认 utf8mb4 字符集
  ├─ 公用表表达式 (CTE)             ├─ 原子 DDL 操作 (InnoDB 事务型)├─ sha256 强密码认证插件
  └─ 完善的 JSON 聚合函数          ├─ 优化器直方图与代价模型增强  ├─ 彻底移除查询缓存 (Query Cache)
                                   └─ 临时表引擎切换为 TempTable   └─ 资源组精细化调度
```
*读图说明：MySQL 8.0 在开发者体验端最大的变革是引入了窗口函数与 CTE，在底层则围绕事务型数据字典、降序索引和查询缓存清理进行了全面重构。*

#### 编程与查询能力增强
- **窗口函数与公用表表达式（CTE）**：彻底改变了复杂嵌套子查询与报表分析的书写范式。
- **更完善的 JSON 与正则表达式支持**：不仅提供了更丰富的 JSON 操作函数，内部存储也采用了更为紧凑的二进制格式；正则表达式引入了 ICU（International Components for Unicode）国际化组件，支持更多元字符与多字节字符。

#### 底层存储引擎与优化器演进
- **索引能力升级**：原生支持降序索引（Descending Indexes）与隐藏索引（Invisible Indexes），使得联合索引的排序优化更加灵活，也让索引的灰度下线测试成为可能。
- **系统数据字典事务化**：彻底告别了 5.7 及之前版本分散在磁盘上的 `.frm`、`.par` 等元数据文件，将所有元数据统一归集在 InnoDB 事务型系统表中，从而原生支持了**原子 DDL（Atomic DDL）**——建表或删表过程中若发生故障，操作能够实现事务级整体回滚。
- **内部临时表引擎替换**：由原有的 Memory 存储引擎升级为专用的 TempTable 引擎，提升了内存中临时表分配与变长字段存储的效率。

#### 废弃与移除的特性
- **彻底移除查询缓存（Query Cache）**：在旧版本中，只要目标表发生任何微小的数据变动，挂载在该表上的所有查询缓存就会瞬间全盘失效，实际生产环境中的命中率极低，反而增加了锁竞争开销，因此 8.0 果断将其移出内核。
- **移除旧式加密与解密函数**：如 `PASSWORD()`、`ENCRYPT()` 等已被官方废弃，全面升级为标准安全的散列机制。
- **默认字符集升级**：默认字符集由 `latin1` 更改为 `utf8mb4`。以往在 `utf8`（实际为 `utf8mb3`）中每个字符最多占 3 字节，无法表达 Emoji 表情及部分特殊生僻字；而 `utf8mb4` 完整覆盖了 4 字节编码，避免了开发者反复手工修改数据库编码的困扰。

### 窗口函数的诞生背景与生产力对比

为了直观体会窗口函数的威力，我们通过一个电商零售业务的真实统计需求，对比 MySQL 5.7 传统写法与 MySQL 8.0 窗口函数写法的巨大差异。

#### 业务场景与测试数据准备

#### 传统写法（MySQL 5.7）：多重临时表与复杂多表连接

在没有窗口函数的年代，SQL 的基础逻辑是：明细数据由明细行展现，而总额统计必须通过 `GROUP BY` 聚合。但 `GROUP BY` 会无情地将多行折叠压缩成单行！因此，开发者不得不创建中间临时表分别保存聚合结果，再回过头与原始明细表执行笛卡尔积或等值连接。

```sql
-- 第一步：创建临时表 a，计算全国总销售额（不分组聚合，只有 1 行）
CREATE TEMPORARY TABLE temp_grand_total AS
SELECT SUM(sales_val) AS grand_total FROM sales;

-- 第二步：创建临时表 b，按城市分组计算每个城市的销售总额（2 行数据）
CREATE TEMPORARY TABLE temp_city_total AS
SELECT city, SUM(sales_val) AS city_total 
FROM sales 
GROUP BY city;

-- 第三步：将原始明细表与两张临时表进行多表连接，完成除法比重计算
SELECT 
    s.id,
    s.city,
    s.county,
    s.sales_val,
    c.city_total,
    ROUND(s.sales_val / c.city_total, 4) AS ratio_in_city,
    g.grand_total,
    ROUND(s.sales_val / g.grand_total, 4) AS ratio_in_grand
FROM sales s
JOIN temp_city_total c ON s.city = c.city
CROSS JOIN temp_grand_total g;
```

这种做法存在极其明显的缺陷：
1. **开发成本高**：为了单次查询，需要显式创建和销毁多张临时表，代码篇幅极其冗长；
2. **性能开销大**：数据库底层需要经历多次全表扫描、建立物理临时结构以及多表 Hash/Nested-Loop 连接，随着数据量的增长，性能呈断崖式下跌；
3. **不可重入与并发冲突**：多会话并发访问临时表容易引发命名与生命周期管理难题。

---

#### 现代化写法（MySQL 8.0）：窗口函数一步到位

在引入窗口函数后，上述所有复杂的临时表构建与多表关联被压缩为一条极其清爽的 `SELECT` 语句：

```sql
SELECT 
    id,
    city,
    county,
    sales_val,
    -- 1. 按城市分区计算城市总额
    SUM(sales_val) OVER(PARTITION BY city) AS city_total,
    -- 2. 计算区占所在城市的比例
    ROUND(sales_val / SUM(sales_val) OVER(PARTITION BY city), 4) AS ratio_in_city,
    -- 3. 不分区（全表窗口）计算全国总额
    SUM(sales_val) OVER() AS grand_total,
    -- 4. 计算区占全国总额的比例
    ROUND(sales_val / SUM(sales_val) OVER(), 4) AS ratio_in_grand
FROM sales;
```

对比之下，代码量锐减了 70% 以上，逻辑一气呵成，且执行计划只扫描一次基表，效率极高。这就是窗口函数带来的生产力跃迁。

### 窗口函数的运行机理与标准语法

#### 什么是窗口函数？

> **定义**：
> 窗口函数（Window Function）是一种特殊的函数计算模型，它兼具“单行函数”与“聚合函数”的特征。它能够像聚合函数一样针对一组相关的数据行（称之为“窗口”或“分区”）执行聚合、排名与位移计算；但与聚合函数不同的是，**窗口函数绝不折叠压缩数据行**，每一行原始数据都会被完整保留，计算得到的值会直接挂载在当前行之上。

```text
[ 传统聚合函数 GROUP BY ]
   Row 1 (部门10) ──┐
   Row 2 (部门10) ──┼──► 聚合折叠 ──► 产生 1 条汇总行 (原行数减少)
   Row 3 (部门10) ──┘

[ 窗口函数 OVER(PARTITION BY) ]
   Row 1 (部门10) ───────────────► Row 1 + 聚合统计值 (行数不变)
   Row 2 (部门10) ───────────────► Row 2 + 聚合统计值 (行数不变)
   Row 3 (部门10) ───────────────► Row 3 + 聚合统计值 (行数不变)
```
*读图说明：窗口函数在逻辑分区内部开辟了一扇计算视窗，在保留原始行级明细的同时，将统计结果实时回填至当前行。*

---

#### 核心语法规范

窗口函数的标准调用语法如下：

```sql
函数名称([参数列表]) OVER (
    [PARTITION BY 分区列名]
    [ORDER BY 排序列名 [ASC|DESC]]
    [ROWS|RANGE 窗口帧范围]
)
```

语法要素深度拆解：
1. **函数名称**：既可以是专用的窗口函数（如 `ROW_NUMBER()`、`RANK()`、`LAG()`），也可以是传统的聚合函数（如 `SUM()`、`AVG()`、`MAX()`、`MIN()`、`COUNT()`）。
2. **`OVER` 关键字**：声明当前函数作为窗口函数运行，标识窗口定义的开始。
3. **`PARTITION BY`（分区）**：将输入的数据集按照指定列划分为互不相交的逻辑区块（称为“分区”）。它的作用类似于 `GROUP BY`，但各行仍然独立存在。若省略该子句，则表示整个结果集视作一个单独的大分区。
4. **`ORDER BY`（排序）**：定义各个分区内部数据行的排序规则。对于序号函数（如 `ROW_NUMBER`）以及前后函数（如 `LAG`），`ORDER BY` 是确定位次逻辑的绝对前提。
5. **`ROWS / RANGE`（窗口帧）**：在分区内部进一步界定当前行所关联的物理行范围或逻辑数值范围（例如“从分区起始行到当前行”）。若省略且存在 `ORDER BY`，默认窗口帧为 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`。

#### 序号函数：ROW_NUMBER()、RANK() 与 DENSE_RANK()

序号函数用于在分区内部为每一行生成排序列号，是处理“组内 Top-N”、“热销排行榜”最核心的工具。它们在处理**数值相同（并列名次）**时的策略各有千秋。

##### ROW_NUMBER()：绝对递增行号（无并列）
`ROW_NUMBER()` 为分区内的每一行分配连续、严格自增的自然数序号（1, 2, 3, 4, 5...）。即使两行数据的排序列数值完全相同，它的序号也绝不重复，单纯按记录处理顺序强行顺延。

```sql
-- 查询各类别的商品，按价格降序分配连续序号
SELECT 
    id, category_id, category, name, price, stock,
    ROW_NUMBER() OVER(
        PARTITION BY category_id 
        ORDER BY price DESC
    ) AS row_num
FROM goods;
```

> **经典应用：获取每个商品分类下价格最高的前 3 种产品（组内 Top-N）**：
> 窗口函数生成的动态列无法在同级的 `WHERE` 条件中直接引用，因此通常在外层嵌套一层子查询完成过滤：

```sql
SELECT *
FROM (
    SELECT 
        id, category_id, category, name, price, stock,
        ROW_NUMBER() OVER(PARTITION BY category_id ORDER BY price DESC) AS row_num
    FROM goods
) t
WHERE t.row_num <= 3;
```

##### RANK()：并列跳跃排名
`RANK()` 专门用于处理并列名次。当多行排序列的数值相同时，它们会被赋予相同的位次；但后续行的序号会**跳过**被占用的名次（即：1, 2, 2, 4...）。

这就像高考录取或商业大奖评选：如果有两人并列第 2 名，那么他们共同占用了第 2 和第 3 的名额，下一位考生的名次将直接顺延为第 4 名。

```sql
SELECT 
    id, category_id, category, name, price,
    RANK() OVER(
        PARTITION BY category_id 
        ORDER BY price DESC
    ) AS rank_num
FROM goods;
```
*在 `category_id = 1` 中，卫衣与牛仔裤的价格均为 89.00，它们的 `rank_num` 均为 2；紧随其后的连衣裙价格为 79.90，其 `rank_num` 直接跳跃至 4。*

##### DENSE_RANK()：并列连续排名
`DENSE_RANK()` 同样支持并列赋值，但它对后续序号的处理采用**稠密连续（Dense）**策略，序号绝不跳空（即：1, 2, 2, 3...）。

这恰如奥运会赛场上的名次机制：跳高比赛中两名选手成绩完全相同并列获得金牌（并列第 1 名），但他们并不剥夺后续选手的奖牌资格，接下来的选手仍然正常摘得银牌（第 2 名）与铜牌（第 3 名）。

```sql
SELECT 
    id, category_id, category, name, price,
    DENSE_RANK() OVER(
        PARTITION BY category_id 
        ORDER BY price DESC
    ) AS dense_rank_num
FROM goods;
```
*同样面对 89.00 的并列价格，卫衣与牛仔裤均为 2，而紧随其后的连衣裙获得的排名是 3，绝不跳步。*

##### 三大序号函数差异对照表

| 分区排序依据（价格降序） | 价格相同情况 | ROW_NUMBER() 输出 | RANK() 输出 | DENSE_RANK() 输出 |
| :--- | :--- | :--- | :--- | :--- |
| 商品 A (399.90) | 最高价 | 1 | 1 | 1 |
| 商品 B (89.00) | 并列第 2 | 2 | 2 | 2 |
| 商品 C (89.00) | 并列第 2 | 3 | 2 | 2 |
| 商品 D (79.90) | 次低价 | 4 | **4 (跳跃)** | **3 (连续)** |
| 商品 E (39.90) | 次低价 | 5 | 5 | 4 |
| 商品 F (29.90) | 最低价 | 6 | 6 | 5 |

#### 分布函数：PERCENT_RANK() 与 CUME_DIST()

分布函数用于统计某个数值在整个分区或窗口范围内的相对分布百分比。

##### PERCENT_RANK()：百分比相对排位
`PERCENT_RANK()` 计算的是当前行在分区内的相对排位百分比，其数学计算公式如下：

$$\text{PERCENT\_RANK} = \frac{\text{RANK} - 1}{\text{Rows} - 1}$$

其中，$\text{RANK}$ 为当前行由 `RANK()` 函数计算出的名次，$\text{Rows}$ 为当前分区内部的总记录行数。

我们以 `category_id = 1`（共 6 条记录，即 $\text{Rows} = 6$）为例，按照价格降序推导：
- 第 1 行（价格 399.90，$\text{RANK} = 1$）：$\frac{1 - 1}{6 - 1} = \frac{0}{5} = 0.0$；
- 第 2 行（价格 89.00，$\text{RANK} = 2$）：$\frac{2 - 1}{6 - 1} = \frac{1}{5} = 0.2$；
- 第 3 行（价格 89.00，$\text{RANK} = 2$）：$\frac{2 - 1}{6 - 1} = \frac{1}{5} = 0.2$；
- 第 4 行（价格 79.90，$\text{RANK} = 4$）：$\frac{4 - 1}{6 - 1} = \frac{3}{5} = 0.6$；
- 第 5 行（价格 39.90，$\text{RANK} = 5$）：$\frac{5 - 1}{6 - 1} = \frac{4}{5} = 0.8$；
- 第 6 行（价格 29.90，$\text{RANK} = 6$）：$\frac{6 - 1}{6 - 1} = \frac{5}{5} = 1.0$。

```sql
SELECT 
    id, category_id, name, price,
    RANK() OVER w AS rk,
    PERCENT_RANK() OVER w AS pr
FROM goods
WHERE category_id = 1
WINDOW w AS (PARTITION BY category_id ORDER BY price DESC);
```

##### CUME_DIST()：累积分布占比
`CUME_DIST()`（Cumulative Distribution）用于计算小于等于当前行排序列数值的数据行数占分区总行数的比例：

$$\text{CUME\_DIST} = \frac{\text{分区中小于或等于当前排序列值的行数}}{\text{分区总行数}}$$

```sql
SELECT 
    id, category_id, name, price,
    CUME_DIST() OVER(
        PARTITION BY category_id 
        ORDER BY price ASC
    ) AS cume_val
FROM goods;
```
*在升序排列下，如果某件商品价格为 29.90，且没有比它更低的价格，它自身占 1 行，总计 6 行，则比例为 $1/6 \approx 0.1667$；到达最高价格 399.90 时，所有 6 件商品的价格均小于等于它，计算结果为 $6/6 = 1.0$。*

#### 前后函数：LAG() 与 LEAD()

在时间序列分析、环比与同比计算中，经常需要“在当前行访问前一行的数据”或者“在当前行访问后一行的数据”。在以往，这必须通过自连接或复杂的游标才能达成，而前后函数彻底简化了这一过程。

##### LAG(expr, n, default)：调取前 n 行的字段值
`LAG` 能够在保留当前行的同时，向前“偷看”同一分区内前第 $n$ 行的指定表达式值（默认 $n = 1$；若不存在前第 $n$ 行，则默认填充 `NULL`，亦可通过第三个参数指定缺省替换值）。

> **实战需求：计算每个商品与它前一个相邻商品（按价格升序）的价格差额**

```sql
SELECT 
    id, category, name, price,
    pre_price,
    -- 用当前商品价格减去上一个商品的价格
    ROUND(price - pre_price, 2) AS diff_pre
FROM (
    SELECT 
        id, category, name, price,
        -- 取出同品类下、按价格升序排序的前一个商品的价格
        LAG(price, 1) OVER(
            PARTITION BY category_id 
            ORDER BY price ASC
        ) AS pre_price
    FROM goods
) t;
```
由于每个品类中最便宜的第一件商品前无更便宜的数据，其 `pre_price` 自然为 `NULL`，两者相减后的差值亦为 `NULL`；从第二件商品开始，均能精准得到它与前一档商品的递增差额。

##### LEAD(expr, n, default)：调取后 n 行的字段值
与 `LAG` 恰好相反，`LEAD` 用于向后“预看”同一分区内后第 $n$ 行的数据行。

```sql
SELECT 
    id, category, name, price,
    next_price,
    ROUND(next_price - price, 2) AS diff_next
FROM (
    SELECT 
        id, category, name, price,
        -- 取出同品类下后一个商品的价格
        LEAD(price, 1) OVER(
            PARTITION BY category_id 
            ORDER BY price ASC
        ) AS next_price
    FROM goods
) t;
```
每个品类中价格最高的最后一件商品后无后续记录，其 `next_price` 为 `NULL`。

#### 首尾函数：FIRST_VALUE() 与 LAST_VALUE()

首尾函数用于在分区内部快速锁定首位或末位的值，极便于求取“每位员工薪资与部门最低/最高薪资的差距”。

##### FIRST_VALUE(expr)
返回当前窗口范围内排序排在第一位的表达式数值。

```sql
-- 查询商品信息，并带出所属分类中价格最便宜（第一名）的商品价格
SELECT 
    id, category, name, price,
    FIRST_VALUE(price) OVER(
        PARTITION BY category_id 
        ORDER BY price ASC
    ) AS lowest_price
FROM goods;
```
在执行结果中，女装分类下的所有行附带的 `lowest_price` 均为 29.90，而户外运动分类下则统一为 59.00。

##### LAST_VALUE(expr)
返回当前窗口范围内的最后一个值。

> **易错点**：
> 很多开发者在使用 `LAST_VALUE()` 时，会困惑地发现它返回的并非全部分区中的最大值，而是**当前行本身的值**！
> **根本原因**：当在 `OVER` 子句中显式指定了 `ORDER BY` 时，系统默认的窗口帧范围是 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`（从分区开头到当前行）。对于当前行而言，当前行的值本身就是它所见范围内的“最后一个值”！
> 若要真正取到整个分区的最终末尾值，必须显式拓展窗口帧范围为当前分区全域：`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`。

```sql
-- 正确获取所属品类内最高价格（最后一名）的标准写法
SELECT 
    id, category, name, price,
    LAST_VALUE(price) OVER(
        PARTITION BY category_id 
        ORDER BY price ASC
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS highest_price
FROM goods;
```

#### 其他常用窗口函数：NTH_VALUE() 与 NTILE()

##### NTH_VALUE(expr, n)：抓取窗口内第 n 个值
`NTH_VALUE(expr, n)` 用于直接捕获当前窗口内部排名第 $n$ 个位置的值。

```sql
-- 查询商品类别中，价格排名第 2 和第 3 的商品价格
SELECT 
    id, category, name, price,
    NTH_VALUE(price, 2) OVER w AS second_price,
    NTH_VALUE(price, 3) OVER w AS third_price
FROM goods
WINDOW w AS (
    PARTITION BY category_id 
    ORDER BY price ASC 
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
);
```

##### NTILE(n)：均匀分桶切片
`NTILE(n)` 将分区内部的数据行尽可能均匀地切分成 $n$ 个“桶”（编号从 1 到 $n$），常用于“将客户按消费金额分成高、中、低 3 档客群”或“将数据均分 4 等份（四分位数分析）”。

```sql
-- 将 6 件商品按价格升序平均划分到 3 个桶中（每个桶 2 件商品）
SELECT 
    id, category, name, price,
    NTILE(3) OVER(
        PARTITION BY category_id 
        ORDER BY price ASC
    ) AS bucket_no
FROM goods;
```

> **分桶分配原则**：
> 如果分区总行数不能被 $n$ 整除（例如 6 条记录划分为 4 个桶），MySQL 会优先把多余的数据行**均摊给编号靠前的桶**。
> 例如 6 行记录分 4 桶：$6 \div 4 = 1$ 余 2。前 2 个桶各多分 1 行，因此第 1 桶包含 2 行，第 2 桶包含 2 行，第 3 桶包含 1 行，第 4 桶包含 1 行，最终桶号分布为 `[1, 1, 2, 2, 3, 4]`。

### 命名窗口（WINDOW 子句）的工程化复用

在实际生产写报表时，一条 `SELECT` 语句内部往往需要同时调用多个窗口函数。如果每个函数后面都跟着一长串重复的 `OVER (PARTITION BY category_id ORDER BY price DESC)`，不仅代码篇幅臃肿，后续调整业务分区时也极易发生漏改。

MySQL 8.0 引入了**命名窗口（Named Window）**语法。我们可以使用 `WINDOW` 关键字在查询主体末尾对公共窗口进行命名声明，并在 `SELECT` 列表中直接按名引用：

```sql
-- 使用 WINDOW 关键字提取复用窗口
SELECT 
    id, category, name, price,
    ROW_NUMBER() OVER w AS row_num,
    RANK()       OVER w AS rk_num,
    DENSE_RANK() OVER w AS dense_rk_num
FROM goods
WINDOW w AS (PARTITION BY category_id ORDER BY price DESC);
```
这种写法就像在编程语言中提取公共变量一样，不仅显著提升了代码的简洁度与可读性，而且大幅降低了后续维护修改的遗漏风险。

### 本讲核心要点总结

回顾整讲窗口函数的学习，关键概念可以凝练为以下三条铁律：
1. **行数守恒律**：窗口函数是兼具聚合与明细特性的混种，它在分区内部完成统计，但**绝对不减少原表的物理行数**；
2. **三类排序辨析**：`ROW_NUMBER()` 纯自然序号永不重复；`RANK()` 并列且跳号（1, 2, 2, 4）；`DENSE_RANK()` 并列且紧凑连续（1, 2, 2, 3）；
3. **窗口帧边界陷阱**：在带有 `ORDER BY` 的 `LAST_VALUE()` 等计算中，必须警惕默认窗口帧只计算到当前行的边界陷阱，按需使用 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` 展开全域。

### 本讲提到的题目与实战检验

#### 题目 1：在 MySQL 8.0 中，使用窗口函数对分数 `[100, 95, 95, 90]` 按降序排名，`ROW_NUMBER()`、`RANK()` 与 `DENSE_RANK()` 的排名结果分别是什么？

**【答案】**：
- `ROW_NUMBER()` 的结果是：`1, 2, 3, 4`
- `RANK()` 的结果是：`1, 2, 2, 4`
- `DENSE_RANK()` 的结果是：`1, 2, 2, 3`

**【解析】**：
两个 95 分并列。`ROW_NUMBER()` 强制按行分配连续序号，不考虑数值相同；`RANK()` 在面对并列时名次相同，但会跳过已占名额（第 3 名被占用，下一位为 4）；`DENSE_RANK()` 同样赋予相同名次，但后续序号紧随其后保持紧凑递增。

---

#### 题目 2：现有员工表 `emp(dept_id, emp_name, salary)`，请使用窗口函数编写一条 SQL 语句，查询出每个部门中薪资排名前两位的员工姓名、所属部门及薪水。

**【答案】**：
```sql
SELECT dept_id, emp_name, salary
FROM (
    SELECT 
        dept_id, 
        emp_name, 
        salary,
        DENSE_RANK() OVER(
            PARTITION BY dept_id 
            ORDER BY salary DESC
        ) AS rank_in_dept
    FROM emp
) t
WHERE t.rank_in_dept <= 2;
```
**【解析】**：
首先利用子查询，在 `DENSE_RANK()`（或 `ROW_NUMBER()`）窗口函数中按部门 `PARTITION BY dept_id` 进行逻辑分组，并按薪资降序排列，计算出组内名次 `rank_in_dept`；在外层查询中通过 `WHERE rank_in_dept <= 2` 筛选出排名前两位的员工。窗口函数生成的别名无法在同级 `WHERE` 中使用，因此必须使用派生表子查询结构。

在掌握了窗口函数的强大分析能力后，我们紧接着来看 MySQL 8.0 带来的另一项重磅 SQL 编程新特性——**公用表表达式（Common Table Expression，简称 CTE）**。

在复杂业务查询的编写中，子查询（Subquery）几乎是每个开发者的家常便饭。然而随着业务维度的增加，子查询层层嵌套，往往会把一段 SQL 演变成几百行的“面条代码”，既难以阅读，更无法复用。CTE 的出现，彻底重塑了多层嵌套 SQL 的编写逻辑。

### 公用表表达式（CTE）的核心概念与架构优势

#### 什么是 CTE？

> **定义**：
> 公用表表达式（Common Table Expression，CTE）是一个在单个语句（如 `SELECT`、`INSERT`、`UPDATE` 或 `DELETE`）执行范围内有效的临时结果集。它使用标准 SQL 的 `WITH` 关键字进行定义，并赋予一个命名的别名，在随后的主查询语句中可以像操作普通数据表或视图一样多次引用它。

我们在日常交流中一定要注意术语的严谨性：它的全称是“公用表表达式”或“通用表表达式”，英文缩写为 `CTE`（注意不要口误拼写成大学英语考级 CET）。这里的关键词在于“**表**”——它本质上是一个命名的、结构化的临时结果虚拟表。

---

#### CTE 与子查询、临时表的本质差异

为了彻底理清 CTE 在数据库运行体系中的坐标，我们将它与大家熟知的“子查询”和“临时表”进行对比：

```text
               ┌─────────────────────────────────────────────────────────┐
               │                 临时数据组织模式对比                    │
               └────────────────────────────┬────────────────────────────┘
                                            │
           ┌────────────────────────────────┼────────────────────────────────┐
           ▼                                ▼                                ▼
     【内联子查询】                     【公用表表达式 CTE】                【物理临时表】
  - 范围：仅当前嵌套位置可见         - 范围：当前完整 SQL 语句内可见     - 范围：整个 Session 会话可见
  - 复用性：零复用 (需重复写)        - 复用性：单语句内支持多次引用       - 复用性：全会话跨语句复用
  - 资源开销：随每次执行重复评估     - 资源开销：内联轻量化临时视图       - 资源开销：占用磁盘/TempTable 引擎
  - 类比：编程语言中的局部字面量     - 类比：单函数内部局部常量定义       - 类比：全局持久化实体
```
*读图说明：CTE 位于子查询与临时表之间的“甜点位”，既克服了子查询无法复用的缺陷，又免除了物理临时表繁重的生命周期管理成本。*

1. **对比子查询（类比局部变量 vs 共享命名结构）**：
   在常规 SQL 中，如果你在外层查询的 `JOIN` 条件和 `WHERE` 条件中需要用到同一组去重数据，你必须在每个地方都把 `(SELECT DISTINCT ... FROM ...)` 子查询完整手工敲一遍。这就好比我们在存储过程的代码块内部定义了一个极其狭隘的局部变量，走出这个括号就灰飞烟灭。
   而 CTE 则将这一逻辑抽象为语句顶层的“命名中间件”，定义一次，后续的关联、筛选、计算均可反复直读。
2. **对比临时表（TEMPORARY TABLE）**：
   临时表是物理存在的数据库对象（由内存引擎或磁盘支撑），其生命周期贯穿整个连接会话，必须在会话结束或事务完成后显式执行 `DROP TEMPORARY TABLE` 释放。而 CTE 是高度轻量级的“逻辑临时结果集”，只随着当前这一条 SQL 语句的开始而生成、随着语句执行完毕而自动在内存中灰飞烟灭，丝毫不留任何元数据残留。

---

### 普通公用表表达式（Non-Recursive CTE）的语法与实战

CTE 按照计算模型分为两大类：**普通公用表表达式**与**递归公用表表达式**。我们首先看最为常用的普通 CTE。

#### 基本语法结构

```sql
WITH cte_name [(column_name [, ...])] AS (
    -- 查询定义语句（通常为 SELECT 语句）
    SELECT ...
)
-- 紧随其后消费该 CTE 的主查询
SELECT ... FROM cte_name;
```

核心语法要素：
- 以 `WITH` 关键字开头；
- `cte_name` 为自定义的表达式名称（建议具备明确业务含义，如 `cte_emp`、`cte_dept_sales`）；
- `AS (...)` 内部包裹产生临时结果集的子查询逻辑；
- 在随后的主查询（或 `INSERT/UPDATE/DELETE`）中，直接将 `cte_name` 视作普通物理表名进行关联或投影。

---

#### 案例实战：查询所有存在在职员工的部门明细信息

我们以经典的员工与部门关系为例，对比传统子查询与 CTE 的代码组织方式。

**准备工作**：确保当前数据库拥有测试基准表 `departments`：

```sql
CREATE DATABASE IF NOT EXISTS dbtest18 CHARACTER SET utf8mb4;
USE dbtest18;

-- 从标准样本库中克隆部门表
CREATE TABLE IF NOT EXISTS departments AS
SELECT * FROM atguigudb.departments;

SELECT * FROM departments;
```

业务需求：**从部门表中查询出所有至少有一名员工入职的部门完整信息（排除那些没有任何员工的空置部门）。**

##### 传统子查询写法
过去，我们通常在 `WHERE` 条件中嵌套一个 `IN` 或 `EXISTS` 子查询：

```sql
SELECT * 
FROM departments
WHERE department_id IN (
    -- 内层子查询：提取员工表中有记录的部门编号并去重
    SELECT DISTINCT department_id 
    FROM atguigudb.employees
);
```

##### CTE 现代写法
使用 CTE 时，我们把“提取有效部门编号”的准备逻辑独立抽离到语句前置区：

```sql
WITH cte_emp AS (
    -- 定义公用表表达式，抽取有员工的部门编号
    SELECT DISTINCT department_id 
    FROM atguigudb.employees
)
-- 主查询直接使用 cte_emp 与部门表执行等值连接
SELECT d.*, e.department_id AS active_dept_id
FROM departments d
JOIN cte_emp e ON d.department_id = e.department_id;
```

两相比较，CTE 的优势体现在：
- **逻辑自顶向下**：传统 SQL 的阅读顺序往往是“由外向内”再“由内向外”反复跳转；而 CTE 遵循现代编程语言的“先声明定义、后消费引用”顺序，极具条理性；
- **多处重用**：若主查询中还需要将该集合用于 `EXISTS` 判定或二次合并计算，直接再次 `JOIN cte_emp` 即可，免除复制代码的隐患。

### 递归公用表表达式（Recursive CTE）的运行机理与层级遍历

如果说普通 CTE 只是提升了代码可读性，那么**递归公用表表达式（Recursive CTE）**则是真正具备了解决传统 SQL 无法处理图与树形结构的“硬核算力”。

#### 递归的本质模型与运行机理

什么是递归？递归在计算机科学中就是“自己调用自己”，并将规模逐步缩小直至触碰终止基准。最典型的数学与算法案例是“汉诺塔”问题：将 $n$ 阶圆盘从 A 柱移动到 C 柱，本质上依赖于先将上面 $n-1$ 阶看作整体移到 B 柱，再把最底层大盘移到 C，最后把 $n-1$ 阶从 B 移到 C。多阶问题的求解完全建立在低阶问题的递归推导上。

递归 CTE 的运行架构与此如出一辙。它的标准语法必须加上 `RECURSIVE` 修饰符：

```sql
WITH RECURSIVE cte_name AS (
    -- 1. 种子查询（Anchor / Initial Member）：提供递归迭代的起点（初值）
    SELECT ...
    UNION ALL
    -- 2. 递归查询（Recursive Member）：在 FROM 或 JOIN 中直接调用 cte_name 自身
    SELECT ... FROM 表名 JOIN cte_name ON 递归条件
)
SELECT * FROM cte_name;
```

```text
            ┌──────────────────────────────────────────────┐
            │   种子查询 (Anchor Member)                    │
            │   获取初始数据集 R0 (如根节点 / CEO / n=1)    │
            └──────────────────────┬───────────────────────┘
                                   │
                                   ▼
        ┌──────────────────► [ 检查当前批次 Ri ] ◄─────────────────┐
        │                          │                               │
        │                          ├─ 结果非空                      │
        │                          ▼                               │
        │             ┌─────────────────────────┐                  │
        │             │ 执行递归部分 Ri+1        │                  │
        │             │ 依赖 Ri 计算下一层级节点 │                  │
        │             └────────────┬────────────┘                  │
        │                          │                               │
        │                          └───────────────────────────────┘
        │
        └─ 递归查询结果为空 (终止条件满足)
                   │
                   ▼
       ┌───────────────────────────────┐
       │ 将 R0, R1, R2... UNION ALL 汇聚│
       │ 返回完整的树形展开结果集      │
       └───────────────────────────────┘
```
*读图说明：递归 CTE 内部维护一个迭代计算环路，每一轮生成的增量数据直接作为下一轮递归调用的上下文，直到某次迭代产生空集合，引擎自动安全退出。*

#### 递归 CTE 实战：公司组织架构树与“下下属”层级穿透

在企业人力资源（HR）管理中，员工表通常采用“自关联（Adjacency List）”模型：每条员工记录包含自己的 `employee_id`，以及其直属领导的 `manager_id`。

现提出一项深度组织架构分析需求：
- 公司最顶层的核心领袖（CEO）是 `employee_id = 100` 的员工（其 `manager_id` 为 `NULL`，算作第 1 代）；
- 以初代为直属领导的员工称为“下属”（第 2 代）；
- 下属所管辖的员工，以及再往下的所有层级成员，统称为该初代领导者的“**下下属**”（即组织树中处于第 3 层及更深层级的所有员工）。
- **业务目标：穿透查询出全公司所有具备“下下属”身份的员工信息。**

##### 传统手写迭代的困局
如果不用递归，开发者必须写多轮嵌套自连接：
1. 先建临时表提取 100 号；
2. 再查 `manager_id = 100` 的第 2 层人员存入临时表；
3. 再查以第 2 层人员为领导的第 3 层人员存入临时表……
如果公司层级不确定（有的部门深达 5 层，有的只有 2 层），由于 SQL 没有原生循环控制语句，在单条查询中根本无法穷尽！

##### 递归 CTE 的优雅解法

借助 `WITH RECURSIVE`，我们可以让 SQL 自行向下延伸迭代，并引入计数器 `n` 标识组织层级深度：

```sql
WITH RECURSIVE cte_emp_hierarchy AS (
    -- 1. 种子查询：定位初代根节点（第 1 代 CEO）
    SELECT 
        employee_id, 
        last_name, 
        manager_id, 
        1 AS n  -- 初始代次标记为 1
    FROM atguigudb.employees
    WHERE employee_id = 100

    UNION ALL

    -- 2. 递归查询：员工表与 CTE 自身关联，匹配直属领导并自增代次
    SELECT 
        a.employee_id, 
        a.last_name, 
        a.manager_id, 
        b.n + 1 AS n  -- 每向下延伸一层，层级代次累加 1
    FROM atguigudb.employees a
    JOIN cte_emp_hierarchy b ON a.manager_id = b.employee_id
)
-- 3. 消费端主查询：过滤出代次 n >= 3 的所有员工（即“下下属”）
SELECT employee_id, last_name, manager_id, n AS hierarchy_level
FROM cte_emp_hierarchy
WHERE n >= 3;
```

##### 执行推导与层级验证
执行上述代码，MySQL 会瞬间输出 92 条记录，表明公司有 92 名员工属于“下下属”范畴。

为了探明该企业组织架构的真实深度，我们可以动态调整过滤条件：
- 将条件改为 `WHERE n = 4`（查看第 4 代基层员工）：查询准确返回了 10 条记录；
- 将条件改为 `WHERE n = 5`（探查是否存在第 5 代）：查询结果为空集（0 条数据）。

这清晰地证明：
1. 该公司的管理架构树总深度严格为 **4 层**；
2. 全公司 107 名员工中，初代 1 人（100 号），第 2 代 14 人（$107 - 92 - 1 = 14$），第 3 代 82 人（$92 - 10 = 82$），第 4 代 10 人，层级分布完全闭环！递归 CTE 展现出了处理树状层级遍历无可比拟的高效与优雅。

### 新特性综合实战演练

为了巩固第 18 章所学的窗口函数与代码组织规范，我们通过一个学生成绩综合排名练习进行全真演练。

#### 场景描述与数据准备

在学校考试系统中，我们需要录入一批学生的测试成绩，并按照考分从高到低呈现多维排名。

```sql
-- 创建专用测试库
CREATE DATABASE IF NOT EXISTS test18_mysql8 CHARACTER SET utf8mb4;
USE test18_mysql8;

-- 创建学生测试成绩表
CREATE TABLE students (
    id INT PRIMARY KEY AUTO_INCREMENT,
    student_name VARCHAR(20),
    points INT
);

-- 插入包含并列分数的样本数据
INSERT INTO students(student_name, points) VALUES
('张三', 90),
('李四', 89),
('王五', 89),
('赵六', 88),
('钱七', 77),
('孙八', 77);

SELECT * FROM students;
```

---

#### 需求与窗口函数写法

**需求**：按照分数降序排列，同时输出三列排名：
1. `ROW_NUMBER()` 方式生成的连续唯一位次；
2. `RANK()` 方式生成的并列且跳号位次；
3. `DENSE_RANK()` 方式生成的并列且紧凑连续位次。

##### 写法一：直接在 SELECT 中内联声明
由于本题是对全班所有学生进行全量大排名，不需要按班级或学科拆分，因此 `OVER()` 内部**无需书写 `PARTITION BY`**，直接声明 `ORDER BY points DESC` 即可：

```sql
SELECT 
    id,
    student_name,
    points,
    ROW_NUMBER() OVER(ORDER BY points DESC) AS "排序1(ROW_NUMBER)",
    RANK()       OVER(ORDER BY points DESC) AS "排序2(RANK)",
    DENSE_RANK() OVER(ORDER BY points DESC) AS "排序3(DENSE_RANK)"
FROM students;
```

##### 写法二：利用 WINDOW 命名窗口提升复用性
三个排序函数所依赖的排序规则完全一致，使用 `WINDOW` 子句进行集中声明，能够让 SQL 极富美感与扩展性：

```sql
SELECT 
    id,
    student_name,
    points,
    ROW_NUMBER() OVER w AS "排序1(ROW_NUMBER)",
    RANK()       OVER w AS "排序2(RANK)",
    DENSE_RANK() OVER w AS "排序3(DENSE_RANK)"
FROM students
WINDOW w AS (ORDER BY points DESC);
```

##### 结果数据集对比展现

```text
+----+--------------+--------+------------------+-------------+--------------------+
| id | student_name | points | 排序1(ROW_NUMBER)| 排序2(RANK) | 排序3(DENSE_RANK)  |
+----+--------------+--------+------------------+-------------+--------------------+
|  1 | 张三         |     90 |                1 |           1 |                  1 |
|  2 | 李四         |     89 |                2 |           2 |                  2 |
|  3 | 王五         |     89 |                3 |           2 |                  2 |
|  4 | 赵六         |     88 |                4 |           4 |                  3 |
|  5 | 钱七         |     77 |                5 |           5 |                  4 |
|  6 | 孙八         |     77 |                6 |           5 |                  4 |
+----+--------------+--------+------------------+-------------+--------------------+
```
*验证结论：面对 89 分并列的李四与王五，`ROW_NUMBER` 机械分配 2 和 3；`RANK` 均计为 2，但把随后的赵六推到了第 4 名；`DENSE_RANK` 均计为 2，紧接着把赵六标为第 3 名。完全印证了此前总结的理论推导。*

### 本讲提到的题目与实战检验

#### 题目 1：关于 MySQL 8.0 中的公用表表达式（CTE），以下说法错误的是哪一项？
A. 普通公用表表达式使用 `WITH` 关键字定义，且可以在当前 SQL 语句中多次被引用  
B. 递归公用表表达式必须显式声明 `WITH RECURSIVE`，内部通过 `UNION` 或 `UNION ALL` 关联初始查询与递归查询  
C. CTE 在当前数据库会话（Session）关闭之前一直有效，可以在随后的多个独立 SQL 语句中持续访问  
D. 相比于传统的物理临时表，CTE 是语句级别的临时结果集，执行完毕自动释放，不产生会话级元数据残留  

**【答案】**：C  
**【解析】**：CTE 的生命周期与作用范围严格限制在**定义它的当前单条 SQL 语句内部**。一旦该语句执行完毕，CTE 的临时结果集生命周期即告终结，绝不能在后续的其他查询中跨语句直接复用（若需跨语句复用，应当创建视图或临时表）。因此 C 项陈述错误，符合题意。

---

#### 题目 2：请简述使用递归 CTE 进行组织树或多级分类遍历时的基本编写规范，包含哪两个必不可少的核心查询块？

**【答案】**：
递归 CTE 必须由以下两个核心部分通过 `UNION` 或 `UNION ALL` 连接而成：
1. **种子查询（Anchor / Initial Member）**：非递归查询块，用于定义递归的起始点（如根节点、最顶级部门、初始计数器代次等），在整个执行流程中仅评估一次；
2. **递归查询（Recursive Member）**：在查询体的 `FROM` 或 `JOIN` 中直接引用 CTE 自身的查询块，每一轮迭代将上一轮计算出的增量数据代入计算，生成下一层级数据，直至返回空集自动终止。

#### 题目 3：现有成绩表 `students(id, student_name, points)`，要求使用命名窗口语法（WINDOW 子句），按照分数从高到低排列，输出行号（ROW_NUMBER）和跳跃排名（RANK），请写出符合规范的 SQL 语句。

**【答案】**：
```sql
SELECT 
    id,
    student_name,
    points,
    ROW_NUMBER() OVER w AS row_no,
    RANK()       OVER w AS rank_no
FROM students
WINDOW w AS (ORDER BY points DESC);
```
**【解析】**：
通过在查询末尾使用 `WINDOW w AS (ORDER BY points DESC)`，将公共的排序逻辑抽象并命名为 `w`，在 `SELECT` 投影列表中分别通过 `OVER w` 进行复用调用，使代码结构紧凑、易读且避免了多处冗余编写。
