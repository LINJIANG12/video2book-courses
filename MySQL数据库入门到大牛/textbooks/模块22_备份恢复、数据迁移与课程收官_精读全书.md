## 195-数据备份概述与mysqldump实现逻辑备份数据
> 对应分集：P195 | 原始标题：《195-数据备份概述与mysqldump实现逻辑备份数据》

MySQL 高级篇一共分成四个小篇章，最后一个小篇章叫「日志与备份篇」，这一讲我们就迎来最后这一章了。如果你已经看到最后一章，先恭喜你，前面这么多章节都能坚持下来；如果吸收得还比较好，对你系统性地看待 MySQL 的这些高级内容应该比较有帮助。相较于前面几个篇章，最后一章的难度偏小一些，主要讲的就是数据库的备份与恢复这件事。

### 备份与恢复的必要性

#### 生产环境中数据丢失的来源

实际生产环境里，让数据出问题的原因大致是两类。一类是人为的：有人故意破坏，或者管理员误操作；另一类属于自然情况：天灾人祸、意外的断电，还有计算机系统软硬件的故障。它们的结果都是数据库当中的数据丢失、服务器瘫痪，而这时候主从服务器之间的同步也会跟着出问题。

出了问题当然要把损失降到最低，而「要恢复」的前提是先得有备份。你恢复的前提是不是得先有这个备份才行？没问题的，这是常识。

这件事对个人也是一样的。我这台电脑一万出头买的（当年 13000，现在更便宜了），要是被人偷了、丢了，从物理损失上讲，撑死就是我买它时候花的这点钱；电子设备也不具备什么保值功能，你指望它再卖两万多也不可能。但它对我的影响肯定高于这一万多块钱——所有跟课程相关的内容全在我这一台电脑上，我要是没有备份，丢了以后这个损失对我来讲是非常大的。

企业就更是如此了。比如京东，它这里有用户的个人信用数据，好不容易建立起来的个人信用体系，如果对应的核心数据丢了，那这个损失是不可估量的，还会直接影响甚至是大批量的 C 端用户。所以说，对数据库服务器、对 B 端业务来讲，数据是一定不能够丢失的。我们需要定期对数据库服务器做备份：每隔一天备份，或者每隔一周备份一次，具体结合你公司自己的业务场景去定。等出现错误问题时，就用备份的数据来做恢复。

#### 备份频率与恢复流程中的时间缺口

有人一看会说，这不挺简单吗？这里你就要注意：我们的备份肯定不会说是实时备份的。频率比较高的，咱们每隔一天做一次，比如每天夜里 3:00 做一次备份——这个时间点访问服务器的并发量比较少、业务也比较少，适合做备份。

假设第二天中午 12:00 出现了服务器瘫痪、数据丢失或者误删除的问题，我们要做恢复：首先得拿到前一天 3:00 的那份备份数据做一次恢复。但恢复这里有一个要点，下面还会谈到：不要在我们现在正在运行的主机上去恢复，要先找一台备机（备库），把数据先恢复到备机上。这样恢复完，数据也只是回到了前一天的夜里 3:00。换句话说，3:00 到 12:00 之间的数据仍然不在备份里（通俗地讲，3:00 和 12:00 其实已经是同一天了，只不过一个是天还黑着，一个是天已经亮了）。这一段缺口，还得再去调用前面讲过的 `binlog` 日志这一类日志文件，做相对应的追加恢复。

```text
                前一天 03:00                    第二天 12:00
                    |                                |
                    v                                v
            +----------------+              +----------------------+
            |  全量备份一份   |              | 故障：瘫痪 / 误删 /  |
            | (夜里业务空闲)  |              | 数据丢失             |
            +----------------+              +----------------------+
                    |                                |
                    |                                v
                    |                    恢复目标：把数据补到 12:00
                    |
                    +-- 步骤 1：在备机 / 备库上恢复 03:00 的备份
                    +-- 步骤 2：用 binlog 等日志补齐 03:00 -> 12:00 的增量
                    |
                    +-- 注意：不要在正在运行的主机上直接恢复
```

读图说明：横轴是时间，恢复被拆成两步——先用最近一次全量备份把数据拉回到备份时刻，再用 `binlog` 日志把备份时刻到故障时刻之间的增量补回来，中间这段缺口是备份频率决定的，不是恢复能绕开的。

关于这一章，也要给大家一个预期：不要期望太高。你说是不是这一节的内容就能融合三、五年 DBA 的开发经验？那显然是不现实的。专门针对备份与恢复，其实可以单开一个栏目去讲，而且还会遇到非常多具体的场景、具体的问题，都得具体分析。这一章我们更多讲的是规范性的一些操作和场景，大家注意一下这一点。

### 备份的两种类型

备份分成两种，一种叫物理备份（Physical Backup），一种叫逻辑备份（Logical Backup）。这就跟我们前面提到的 `redo` 日志和 `undo` 日志一样，相对应地理解就能明白这个意思。

#### 物理备份

物理备份顾名思义，就是你把物理磁盘上的数据库目录备份起来，把它拷贝到另外的一个目录下，就可以了。

它的特点是恢复速度比较快，但是占用的空间会比较大一些；另外也可以使用第三方的工具去实现备份。这就是它的特点。

#### 逻辑备份与 mysqldump 的工作方式

逻辑备份，是我们使用相关工具把整个数据库的信息给它导出来。它的特点跟物理备份正好相反：恢复的速度比较慢，占用的空间比较小。有利有弊。

我们常见使用的工具，就是 MySQL 官方提供给我们的转储工具 `mysqldump`。它做的是逻辑备份，实际的逻辑就是把 SQL 语句做了一个备份：比如我们创建表的语句，就是 `create`；然后表里边的数据，就是一些 `insert` 的语句。所以它备份、恢复比较慢——相当于把这些语句是不是重新再执行一遍？恢复起来自然就慢一些。

| 对比项 | 物理备份 | 逻辑备份 |
| --- | --- | --- |
| 备份对象 | 磁盘上的数据库目录 | 建表与插入数据的 SQL 语句 |
| 实现方式 | 直接拷贝目录，也可用第三方工具 | 用 `mysqldump` 这类工具导出 |
| 恢复速度 | 快 | 慢（相当于重新执行一遍 SQL） |
| 占用空间 | 大 | 小 |

> **结论**：物理备份恢复快、占空间大，逻辑备份占空间小、恢复慢，有利有弊，用到哪一种是看场景决定的。

下面就先来讲逻辑备份，用的就是 `mysqldump` 这个工具；备份完以后再做恢复。

### 演示场景清单与环境准备

#### 要覆盖的备份场景

先从宏观上看这一节要演示哪些场景，逻辑备份的操作范围就是这些：

- 备份一个数据库，比如我们之前创建的某一个单独的数据库；
- 备份全部的数据库，也就是当前这个数据库实例下的所有数据库；
- 备份部分数据库，从所有库里挑出比如两个来备份；
- 备份部分表，一个数据库当中的一部分表；
- 备份单表中的部分数据，一张表里我们只要一部分数据；
- 排除某些表的备份；
- 只备份结构，也就是整个数据库下所有表的结构；或者只备份数据；
- 备份的时候，默认是不包括数据库当中的存储过程、存储函数和事件的，要把它们也包含进来该怎么写；
- 以及除了这些之外，还有哪些其他备份的特殊场景和行为。

这些常用选项都会罗列出来，下面我们一个一个实现。

#### 演练环境与备份目录

演示这一块我用 Xshell 来连，其实用 SQLyog 也还行。这里要提前先做一个操作：我们备份以后生成的文件，它其实是一个文本文件，是可以打开去看的，所以这个文本文件最好别让它太大了，不然咱们分析起来也不方便。

所以我们先去备份的这个数据库 `atguigudb3` 里做点处理。当初演示调优的时候，这个库里有一些表特别大，我把特别大的那些表直接删了，就不要了——就用图形化界面的方式删的，超过 1000 行的我都不要了，一个一个看一看，十几行的、0 行的留着，行数多的 `delete` 掉。这样备份出来的文本文件里数据不会太多，看起来不费劲。

接着创建备份目录。我是在数据库目录下用 `mkdir` 建的：

```bash
mkdir /var/lib/mysql/backup
```

> **提示**：这里只是为了演示方便，才把它放在了我们这个数据库目录下。实际的生产环境当中，首先肯定不会放到当前的数据目录下——你备份的跟数据库放在一起，如果数据库出问题了，有可能就都出问题了；其次，我们可能也不会备份在同一台机器上，主机出问题，备份也放在这儿，这也不靠谱。备份也可能放到不同的地点、放得远一点，这样有利于容灾备份。

### 备份单个数据库

#### 基本语法与参数

先针对刚才准备好的 `atguigudb3` 这个数据库做备份。具体如何实现？有一个基本的语法：

```bash
mysqldump -u用户名 -h主机名 -p密码 数据库名 [表名...] > 备份文件.sql
```

`-u` 是用户名，`-h` 是主机名称，`-p` 是密码。我这里已经连上 150 那台机器了，所以 `-h` 就可以省略；后面跟的就是我们要备份的数据库的名称。如果你要具体指定这个数据库下的某些表，就在数据库名后面接着写表名——那属于「备份部分表」，后面单独说，暂时先忽略。

> **提示**：备份到的这个文件是以 `.sql` 结尾的，实际上写成 `.txt` 结尾也完全可以，因为它就是一个文本文件，我们直接打开查看，这都是没问题的。

#### 备份到文件：相对路径与绝对路径

进入备份目录以后执行备份：

```bash
mysqldump -uroot -p atguigudb3 > atguigudb3.sql
```

因为现在已经在这个文件目录下了，所以直接写文件名，就表示把它备份到当前这个目录下。如果你不在这个目录下，就要写绝对路径：

```bash
mysqldump -uroot -p atguigudb3 > /var/lib/mysql/backup/atguigudb3.sql
```

密码按提示输入（演示里输的是 `abc123`）。执行完 `ll` 看一下，这个文件就已经有了。有了这个文件，我们就可以打开做查看：

```bash
cat atguigudb3.sql
```

如果觉得这样查看没有高亮、看着不清楚，就用 `vim` 打开，花花绿绿的看着更清晰一些：

```bash
vim atguigudb3.sql
```

### 备份文件的结构解析

#### 文件头与 MySQL 版本注释

最上面显示的是 `mysqldump`，指的是 MySQL 这个转储工具的版本号。这里要注意：它的版本号跟数据库本身的版本号不一定是匹配的。后面接着是数据库的版本号，以及所应用的平台，然后是具体的 host、database。

往下会看到一些以 `/*!` 开头、以 `*/` 结尾的内容，这叫 MySQL 注释。这些注释在我们做数据恢复的时候，会被 MySQL 数据库服务器读取，里面的信息就是给服务器看的；而在其他的、非 MySQL 的数据库服务器上，它就不识别了。这样写可以提高我们备份文件的可移植性。

注释里还会出现一系列编号，这些编号代表的其实也是 MySQL 数据库的版本，比如 4.01.01 这样的版本、5.05.03 这样的版本。言外之意是：跟在编号后面的这些信息，要在该版本及以后的版本当中才可以使用。这主要还是为了 MySQL 服务器读取用的，大家做个了解就可以了。

#### 表结构与数据的呈现形式

再往下就涉及到具体的表了。比如这个备份要恢复到另外一台数据库上去，而对方那个数据库下有可能已经存在 `account` 表，那怎么办呢？你就把现有数据库下的 `account` 表先干掉，干掉以后再重新生成一个备份文件里边的 `account` 表。再往下就涉及到添加数据了，也就是 `insert` 行为。

所以这个 SQL 文件里边，主体结构就是 `create` 这样的建表语句，还有 `insert` 这样的语句：表在文件里以 `create` 来呈现，表数据以 `insert into` 的方式来呈现，多条数据以逗号的方式隔开在一条语句里。

> **提示**：这些关键字都是大写的。这个「大写」是留的一个伏笔——一会儿我们要查文件里到底有没有数据，就是靠按大写 `INSERT` 去搜。

用 `Shift+G` 可以进入这个文件的结尾，结尾还是有很多这样的 MySQL 注释开头，最后有一个这个文件生成的时间，做了一个记录。

#### 文件头尾的用户变量与系统变量

用 `gg` 回到开头，看这些注释：它把当前系统当中的系统变量赋值给了前面的用户变量，相当于做了一个临时的记录。再用 `Shift+G` 到结尾，最后的时候再把这些用户变量赋回给当前的系统变量，相当于恢复成我们最初的这样一种状态。一头一尾这两个动作是成对出现的，目的就是恢复时不破坏服务器原有的变量设置。

```text
+------------------------------------------------------+
| HEADER : mysqldump ver / server ver / platform        |
|          host / database                              |
| COMMENT: /*! ... */   system vars --> user vars       |
+------------------------------------------------------+
| TABLE 1: create ...                                   |
|          insert into ... (多值以逗号分隔)              |
+------------------------------------------------------+
| TABLE 2: create ... / insert into ...                 |
+------------------------------------------------------+
| TAIL   : /*! ... */   user vars --> system vars       |
|          dump file create time                        |
+------------------------------------------------------+
```

读图说明：文件从上到下依次是文件头版本信息与变量注释、一张张表的建表语句加插入语句、文件尾把用户变量还原回系统变量并记录备份生成时间；后面所有 `mysqldump` 生成的 `.sql` 文件都是这个骨架。

### 备份全部数据库

备份全部的数据库，用 `--all-databases`，或者用短选项 `-A`：

```bash
mysqldump -uroot -p --all-databases > all_databases.sql
```

写法上注意：短选项就写一个大写的 A，前面一个杠（`-A`）；要写全称就用两个杠（`--all-databases`）。这样相当于把当前这个数据库实例当中的所有数据库都做了一次备份。后面写入到哪个文件里——刚才演示用的是绝对路径，后续因为都在 `backup` 这个目录下，就都写成相对路径了。

执行的时候你会发现它会在这儿停顿一下，因为我们所有数据库下，前面授课时演示的内容里边有一些是百万级的数据，所以做备份的时候就会慢一些。再 `ll` 查看，这个文件就生成了，而且你会发现这个文件非常的大。这个咱就别打开看了，有点太恐怖了；它的结构整体跟我们前面看的那个文件是一样的。

### 备份部分数据库

备份部分数据库用 `-B`，或者把 `all` 去掉写成 `--databases`；后面要写明你到底想备份的是哪几个数据库：

```bash
mysqldump -uroot -p --databases atguigudb2 atguigudb3 > part_databases.sql
```

库名之间用空格隔开，看清楚别写错了。文件名叫 `part_databases.sql`，是为了见名知意——一会儿我们还要涉及到恢复的问题，名字起得清楚，恢复的时候才好找，不然就找不到到底是哪一个了。查看一下，里面记录的就是这两个数据库以及各自对应的数据。

### 备份指定数据库下的部分表

针对某一个数据库下的部分表，写法是直接写数据库名，后面空格写表名就行。

有同学会问：这跟上面的写法会不会混？不会混。前面几种写法都带着其他的参数（比如 `--databases`、`--all-databases`），你没有这类参数的时候，后面跟的就是数据库名；再往后空格，跟的就是这个表。

先回到库上看一下有哪些表：

```sql
use atguigudb3;
show tables;
```

比如把 `account` 表和 `student` 表这两张表做一个备份：

```bash
mysqldump -uroot -p atguigudb3 account student > part_tables.sql
```

中间别用逗号，不要用逗号去隔开，直接用空格分开表名。查看一下 `part_tables.sql`：前面是一些注释信息，接着是 `account` 这张表的创建、数据的一个添加，然后是 `student` 表的创建、表数据的添加，然后就结束了——确实就只有这两个表。

### 用 --where 备份单表中的部分数据

只要单表里的部分数据，用 `--where`，相当于对数据做一个过滤。写法是：数据库名、表名，然后 `--where`，过滤条件用双引号引出来。

先看一下表里的数据：

```sql
select * from student;
```

这里我们只想要 `id` 小于等于 15 的那些数据：

```bash
mysqldump -uroot -p atguigudb3 student --where "id <= 15" > part_data.sql
```

查看生成的 `part_data.sql`：前面是注释信息，注释里带了我们的过滤条件；在这一条 `insert` 里边，数据只到 15，然后一个分号就结束了，后面的数据就没有要。确实相当于只保留了这一部分数据。

### 用 --ignore-table 排除指定表

备份某一个数据库，但是其中有些表我们不要了，可以单独地把某一个表给它抠出去，用 `--ignore-table` 这个参数——这个单词你得会写，是 table，没有 s：

```bash
mysqldump -uroot -p atguigudb3 --ignore-table=atguigudb3.student > no_student.sql
```

参数后面要写清楚是 `atguigudb3` 下的哪张表，比如把 `student` 这个表单独抠出去。写入到 `no_student.sql`。

备份完验证一下里面到底有没有这张表。表少的时候可以用 `vim` 打开，用 `/student` 去查找——你会发现找不到，那就说明里面确实没有。表比较多的时候，也可以用 `grep`：

```bash
grep student no_student.sql
grep account no_student.sql
```

第一条查不到，说明 `student` 表确实不在这个备份里；第二条能查到 `account`，说明其他的表是有的。这就相当于把具体的这个表从备份里抠出去了。

### 只备份表结构或只备份数据

#### 只备份表结构

只备份指定数据库下的表结构，相当于只保留 `create` 这样的语句，用 `--no-data`（短选项 `-d`）：

```bash
mysqldump -uroot -p --no-data atguigudb3 > no_data.sql
```

验证的时候就用得上前面说的那个伏笔了：如果里面没有数据，就意味着没有大写的 `INSERT` 语句，直接搜大写关键字就行；为了以防万一，也可以再搜一次小写确认：

```bash
grep INSERT no_data.sql
grep insert no_data.sql
grep create no_data.sql
```

前两条都查不到，说明确实没有数据；第三条能查到 `create`，说明表结构是在的。

> **提示**：`mysqldump` 生成的关键字统一是大写的，所以校验"这个备份里有没有数据"时，直接按大写 `INSERT` 去搜最省事；再顺手用小写验证一次，更稳妥。

#### 只备份数据

不要表结构、只要数据，用 `--no-create-info`（短选项 `-t`）：

```bash
mysqldump -uroot -p atguigudb3 --no-create-info > no_create.sql
```

同样用 `grep` 验证：搜 `insert` 是有的，因为我这里只保存了数据；搜 `create` 就没有了。这一对参数正好和前一对互补。

### 包含存储过程、存储函数与事件

默认情况下，备份是不包括数据库当中的存储过程（Stored Procedure）、存储函数（Stored Function）和事件（Event）的。前面看 `atguigudb3` 的备份文件时也能发现，里面确实没有存储过程和函数，而事实上库里是有的——`atguigudb3` 下有一个存储函数 `random_num`，还有 4 个存储过程。

要把它们包含进来，需要用到这两个参数：

- `--routines` 或 `-R`：包含存储过程和存储函数；
- `--events` 或 `-E`：包含事件。

```bash
mysqldump -uroot -p -R -E --databases atguigudb3 > func_procedure.sql
```

这里针对的是单个数据库，所以用 `--databases` 加库名；如果要备份全部数据库，那就是 `--all-databases` 了。

验证里面到底有没有那个函数，用 `grep` 的 `-C` 参数（大 C）加上行数，把匹配行的前后 5 行信息都展示出来：

```bash
grep -C 5 random_num func_procedure.sql
```

能查到，里面既有对应函数的创建，也有它使用的情况，说明存储函数确实被包含进来了。存储过程我没有单独演示验证，道理是一样的，也是包含的。

其他常用选项我就不一个个过多展示了，大家也可以自己动手操作一下，其实比较简单。

## 196-演示mysql实现逻辑恢复数据
> 对应分集：P196 | 原始标题：《196-演示mysql实现逻辑恢复数据》

前面我们用 `mysqldump` 把库、多个库、部分表都备份出来了。备份是为了什么？就是把当前这些表和库里的数据存成文件，等到人为操作失误、自然灾害影响，或者数据库本身损坏，导致数据缺失的时候，把备份拿出来顶上——这就是数据的恢复行为。

恢复用的是官方给的那个 `mysql` 指令。这个指令大家一点都不陌生：我们最初接触 MySQL、要登录用户，用的就是它。但它在恢复场景里的角色变了——它这时候的活是**读取 `mysqldump` 生成的那个 SQL 文件，然后把它原样执行一遍**。

文件里存的是什么？就是你当初的 `create` 和 `insert` 语句。`create` 里是建库、建表，把这些语句重新跑起来，库和表就建好了；然后 SQL 文件里的 `insert` 语句一条条执行，表中的数据也就一条条回来了。这就是逻辑恢复最底层的原理。

> **定义**：逻辑备份与逻辑恢复，备份的是「重建数据所需的 SQL 语句」而不是数据文件本身；恢复就是把这份语句脚本重新执行一次，让库、表、数据按语句的描述被重新构建出来。

接下来按粒度从小到大，把几种恢复行为都演示一遍。

### 恢复前的准备：先造出数据损坏现场

在演示单库备份恢复单库之前，得先有一个能观察的现场。前面我们做过 `atguigudb3` 这个数据库的单独备份，就从这个库下手。

先确认自己在哪个库，再 `show tables` 看一眼现有的表：

```sql
show tables;
```

表都在。那就直接删一张，把 `student` 表干掉：

```sql
drop table student;
```

`drop table` 一执行，`student` 表就没了。

> **易错点**：`drop` 是 DDL 操作，执行即提交。这时候指望 `rollback` 把表找回来是不大靠谱的——所以只能走备份恢复这条路。

这里就是一个必须记住的边界：`drop` 和后面要演示的表内 `delete`（DML）性质不同，能不能回滚不是靠记忆猜的，而是由它属于 DDL 还是 DML 决定的。表已经被删掉，而备份文件还在，恢复的演练条件就齐了。

### 单库备份中恢复单库

#### 关键判断：备份文件里有没有建库语句

`mysql` 指令有两种写法，区别只在一件事上——**这份 SQL 文件里包不包含创建数据库的操作**：

| 备份文件内容 | 恢复命令写法 | 说明 |
| --- | --- | --- |
| 不含 `create database` | `mysql -u root -p 库名 < 文件` | 手动指定要恢复到哪个库 |
| 含 `create database` | `mysql -u root -p < 文件` | 命令里不必再写库名 |

当年备份的时候文件里到底有没有建库语句？时间一长就记不清了。那就直接看文件，用 `vim` 打开（高亮看着确实舒服一些）：

```bash
vim atguigudb3.sql
```

看头部，**文件一上来就是创建表，没有创建数据库的操作**。既然没有建库语句，恢复时就得手动把库名写进命令里：

```bash
mysql -u root -p{password} atguigudb3 < atguigudb3.sql
```

这条命令的三段分别是：`-u root -p{password}` 是登录凭据（演示里讲师把密码直接跟在 `-p` 后写成 `-pabc123`，下面也都用这个密码）；`atguigudb3` 指定把语句导入到哪个库；`<` 后面的文件就是备份文件本身。

> **提示**：这里的路径是相对路径。因为当前已经在 `backup` 目录下，直接写文件名就行；如果不在这个目录，就得写绝对路径，例如 `/var/lib/mysql/backup/atguigudb3.sql`。

回车，输入密码 `abc123`，执行完毕。恢复完成，`show tables` 一看，刚才被 `drop` 掉的 `student` 表又回来了。

> **结论**：单库备份文件导入已有库，是把语句在目标库里重新跑一遍；`drop` 掉的表和表里的数据会一起回来。

这里必然有人怀疑：「是不是刚才根本没删掉？」讲师自己也没在做完 `drop` 之后立刻 `show` 一下确认——但执行的的确确成功了，而且 `drop table` 这种操作一旦执行就是删了。演示上不再重复一遍，没有这个必要。

#### 恢复到新建的库

同一个备份文件，还可以往一个全新的库里倒。先建库：

```sql
create database atguigudb4;
```

建好之后切过去：

```sql
use atguigudb4;
show tables;
```

新库当然是空的，一张表都没有。那么把刚才那份备份文件里的表和数据全部搬到这个新库来。命令和前面一样，只是把库名从 3 改成 4：

```bash
mysql -u root -p{password} atguigudb4 < atguigudb3.sql
```

执行完再切回来查：

```sql
use atguigudb4;
show tables;
select * from student;
```

表全在，`student` 里也有数据。

> **结论**：同一份单库备份既能覆盖恢复到原库，也能整份导入到一个新库——后一种场景就相当于拿一份备份复制出一个新的库环境。

### 全量备份的整库恢复与它的代价

`all-databases` 那种一个文件装下所有库的备份，是另一条路。它对应的恢复行为是：在一台全新的备机上执行前面的 `mysql` 指令，把所有的库一次性全部恢复出来——这就是昨天那一刻所有数据库的快照。

但这个演示不做。原因很实在：`all-databases` 文件本身已经很大（授课环境里就有好多百万级以上的库），实际生产环境里只会更大，恢复起来肯定很慢。

> **结论**：粒度越大的恢复，代价越高。判断是否值得走整库恢复，标准不是「能不能恢复」，而是「损坏的范围有多大」。

于是这里就出现了一个取舍。考试环境、生产环境都会遇到的典型情形是：只是某个库下的某张表损坏了。为了这一张表去整库恢复，就有点小题大做了。

就像裤子只是脏了，洗一下就行，非要说不穿了、再买一条，多少有点浪费；笔记本边框磕了一下其实不影响什么，非得换台新笔记本，也没必要。**只损坏一张表却整库重来，就是这种浪费。**

### 从全量备份中提取并恢复单个库

真实的备份现场往往没这么讲究。我们不会像授课这样按库、按表、按粒度整得花花绿绿，往往就是对着当时所有数据库做一次全量备份。现在其中一个库的数据坏了，只想把这一个库恢复回来。更麻烦的是：**手里只有 `all-databases` 这个全量文件，并没有为这个库单独维护过备份文件**。

#### 从全量文件中切出目标库

思路是从全量文件里把我们这个库先找出来，再单独放成一个文件。这一步对语料里演示的提取命令做一次剖析——它要表达三件事：

- 源：当天的全量备份文件，名字是 `all-databases`（结尾带 `s`）；
- 目标：`current database` 为 `atguigudb3` 的那一部分；
- 去处：写入一个新文件，命名为 `atguigudb3_1.sql`。

> **提示**：全量备份文件里**包含 `create database` 这样的建库语句**——这一点和前面那个单库备份文件正好相反，直接决定了后面恢复命令怎么写。

执行完 `ll` 一下，新文件生成了。用 `vim` 打开 `atguigudb3_1.sql` 看一眼：里面就是这个库下各种表的建表语句和表数据，而且**开头就带着建库操作**。

> **易错点**：提取出来的文件里既然已经有 `create database`，那么稍后恢复时就**不能再在命令里指定库名**，否则就写重了。

#### 执行恢复与「表没回来」的排查

直接按「文件里含建库语句」的那种写法恢复，路径同样在 `backup` 目录下（不在就写绝对路径）：

```bash
mysql -u root -p{password} < atguigudb3_1.sql
```

回车，输入 `abc123`，执行完成。恢复完成了——可 `show tables` 一看，不对劲：`account` 没回来，`student` 也没回来。

问题不在恢复本身，而在于**要恢复的库当前已经存在，会话里看到的是旧状态**。它不像查看一个新库那样能立刻反映变化。所以要先退出当前这个会话，重新登录一次：

```sql
exit;
```

然后重新登录、切库、再查：

```sql
use atguigudb3;
show tables;
select * from student;
```

这次 `account` 回来了，`student` 里被删掉的数据也全回来了。

```text
   全量备份 all-databases.sql
            |
            |  提取 current database = atguigudb3 的部分
            v
   atguigudb3_1.sql   （含 create database + 建表 + insert）
            |
            |  mysql -u root -p < atguigudb3_1.sql
            v
   服务端重建库表并插入数据
            |
            |  旧会话看不到变化
            v
   exit 退出 -> 重新登录 -> use atguigudb3 -> show tables
            |
            v
   account 表与 student 数据均已恢复
```

读图说明：从全量文件切出单库脚本，脚本本身已含建库语句，所以导入命令不再写库名；导入完成后必须换一个新会话重新登录，才能看到恢复后的库表。

> **易错点**：恢复已有库之后，**当前会话里查不到恢复结果不代表恢复失败**。先 `exit` 重新登录（至少也要切换一次库）再看，这是最容易被误判成「恢复没生效」的一步。

这个库如果被删得更彻底——整个 `atguigudb3` 直接干掉——恢复流程其实完全一样：先把库建出来，再把 SQL 文件倒进去，和前面演示的思路是一致的。

### 从单库备份中恢复单表

粒度再往小收一档：只恢复一张表。

场景是这样的：`atguigudb3` 这个库里表特别多，有的单表就到了百万级的存储量。前面几种做法本质上都是**恢复整个数据库，相当于重新做一次覆盖操作**。而现在库不想动，只是其中某一张表（比如 `student`）的数据损坏了，只有几条数据缺失——有必要把所有表都恢复一遍吗？数据量一大，花的时间就很长。

> **结论**：损坏范围是单表时，就用单表粒度的恢复，不要为了几条数据把整个库覆盖一遍。

#### 用 source 分两步恢复表结构与表数据

先把损坏做出来。这次下手重一点，直接把表干掉：

```sql
drop table student;
show tables;
```

`student` 表不在了。表没了，意味着**表结构信息和表内数据信息全部丢失**——这两样要分别找回来。

思路是先定位到装这个库的那份脚本，再从里面专门把 `student` 表抽出来。抽成两个文件：

- 一个只含 `student` 表的 `create` 语句，也就是**表结构**（structure）；
- 一个只含 `insert into student` 这类语句，也就是**表数据**（data）。

在库脚本 `atguigudb3_1.sql` 上按这两个目标分别做一次提取，回车之后 `ll` 一下，目录里就多出两个文件：`student_structure` 和 `student_data`。表结构在一个文件里，表数据在另一个文件里。

> **提示**：这两份提取命令的具体写法当场是粘贴进来的，屏幕上闪过得太快，抓不住它的参数细节。真正要记住的是这套拆分的思路——**结构和数据分开抽、分开导**，参数照着自己环境里的脚本来套。

#### 分步验证：先结构后数据

接下来进入 MySQL 命令行操作。这里不再用 `mysql < 文件` 那种外部重定向，而是用服务端自带的 `source` 指令，在 `mysql>` 提示符下直接执行文件。

先进到目标库：

```sql
use atguigudb3;
```

> **易错点**：`source` 后面**必须写文件的完整路径**，不能只写文件名。演示里的路径是 `/var/lib/mysql/backup/student_structure`。

先导表结构：

```sql
source /var/lib/mysql/backup/student_structure;
```

执行完 `show tables` 一看，`student` 表回来了。但这时候去查数据：

```sql
select * from student;
```

**表在，里面没有数据**。这正好把「结构」和「数据」两件事分开了：上一步只恢复了结构，数据还在另一个文件里。

再导数据：

```sql
source /var/lib/mysql/backup/student_data;
```

执行完再查一次 `select * from student;`，数据回来了。

```text
   drop table student
          |
          v
   表结构与表数据同时丢失
          |
          +-------------------------------+
          |                               |
   student_structure                student_data
   （create 语句）                   （insert 语句）
          |                               |
          |  source .../student_structure |  source .../student_data
          v                               v
   show tables 能看到 student      select * from student 才有数据
          |                               |
          +---------------+---------------+
                          v
                 表与数据全部恢复
```

读图说明：单表恢复要分两次 `source`，先执行结构文件建出空表，再执行数据文件把 `insert` 语句跑一遍；只做前一步，查表就只能看到空表。

### 五种恢复粒度与选择依据

| 恢复粒度 | 备份来源 | 恢复动作 | 适用判断 |
| --- | --- | --- | --- |
| 单库到单库 | 单库备份文件 | `mysql -u root -p 库名 < 单库.sql` | 原库的表被删或数据误删，直接从备份覆盖回来 |
| 单库到新库 | 同一份单库备份文件 | 先 `create database`，再导入到新库名 | 需要一份独立的库环境 |
| 全量到多个库 | `all-databases` 文件 | 在新备机上执行 `mysql -u root -p < all-databases.sql` | 昨天做过全量备份、需要整机恢复；文件大、耗时长 |
| 全量到单个库 | 从全量文件中提取出的脚本 | 提取后执行导入，再重开会话 | 手里没有该库的独立备份，只有全量文件 |
| 单库到单表 | 库脚本中抽出的结构与数据两个文件 | 用 `source` 先结构后数据 | 只有一张表损坏、库里表多且数据量大 |

粒度是越收越小的。如果发现损坏的只是表中的部分数据，那就选粒度最小的操作，没必要把整个库恢复一遍。

到这里，逻辑备份配逻辑恢复这一套用法就说清楚了。**下来大家自己动手把几种粒度都操作一遍**——恢复这条路，光看不练，真出事的时候手是生的。

## 197-物理备份和物理恢复的演示、表数据的导出与导入
> 对应分集：P197 | 原始标题：《197-物理备份和物理恢复的演示、表数据的导出与导入》

上一节我们把逻辑层面上的备份和恢复做完了：用 `mysqldump` 把数据导成一堆 SQL 语句，再用 `mysql` 把这些语句执行回去——这一部分大家下来可以自己去实现一遍。这一节换到另一个层面：物理备份和物理恢复。

一说起备份，感觉很高大上，其实说白了就是一个拷贝。这事你们最擅长：在 Windows 平台上点一下右键、复制一下，这就是一个拷贝了。

那就要问一句：是不是真像我们想的这么简单？把物理磁盘上的一个数据库目录，甚至整个数据目录，整个拷贝出去；等现在这个库的文件损坏了，再把那份拷贝粘回来覆盖上，是不是就万事大吉了？这里边肯定还有一些细节问题。我们一步一步看该怎么实现。

这一节的后半段还有另一件事：具体某张表里的数据怎么导出到文件里，又怎么再导回表里。

### 物理备份与逻辑备份的取舍

物理备份（Physical Backup）和逻辑备份（Logical Backup）放在一起看，差别就落在两件事上。

先说缺点：物理备份生成的文件更大一些。因为我们拷的就是数据文件本身，表结构、索引这些物理结构都在里面，不像逻辑备份只存 SQL 语句那么精简。

再说优点：这种方式速度比较快。简单粗暴、直接——恢复的时候把整个文件直接粘回来就行，不用再把 SQL 一条条执行一遍。

| 对比项 | 物理备份 | 逻辑备份 |
| --- | --- | --- |
| 产出文件体积 | 更大 | 更小 |
| 备份与恢复速度 | 更快 | 更慢 |
| 操作方式 | 直接拷贝数据目录下的库目录 | 用 `mysqldump` 导出 SQL，再用 `mysql` 回放 |

> **结论**：物理备份就是拷贝数据目录，快，但占地方；逻辑备份走 SQL 语句，省地方，但慢。用哪一种，看你的场景。

备份的对象，就是数据目录下面一个个库目录。默认情况下各个平台的数据目录位置不一样，这个前面已经很熟了，在这儿就不啰嗦。

### 备份窗口内的数据一致性

库目录里的文件比较多，备份是要花时间的。我们把开始备份的那一刻记作 T1，备份完成的那一刻记作 T2，T1 到 T2 这一段就是备份窗口。这中间要保证数据的一致性——说白了就是：整个备份过程当中，不要对我们正在备份的这个数据库做增删改。

```text
       T1 开始备份                          T2 备份完成
          |                                     |
          v                                     v
  --------+=====================================+-------->  时间轴
          |<--------- 备份窗口：拷贝库目录 -------->|
          |
          |  这段窗口内只允许读：
          |    SELECT                正常
          |    INSERT / UPDATE / DELETE   被读锁挡住
          |
          +-- 窗口结束后：UNLOCK TABLES 解锁
```

读图说明：横轴是时间，T1 到 T2 之间是拷贝文件的窗口，窗口内用读锁把增删改挡在外面、只放查询进来，窗口结束立刻解锁，业务恢复可写。

那怎么做到？两种思路。

第一种，把服务停掉。停了谁都访问不了：想增删改不行，查询也不行。这个思路成立，但太暴力了。

第二种，不停服务，只把「修改」这条路限制住——让表带上一个读锁（Read Lock）。这样查询没有问题，增删改就进不来了。另外再顺手刷一下盘：`flush` 一下 `tables`，保证相应的数据该刷新到磁盘的都刷新到磁盘上。数据都落盘了，我们再去作备份。

这两件事，一条指令就办完了：

```sql
FLUSH TABLES WITH READ LOCK;
```

名字里已经把两件事说全了：`FLUSH TABLES` 是把表相关的数据刷到磁盘，`WITH READ LOCK` 是给它加上读锁。这条要在备份之前执行，执行完再开始拷文件。

备份做完以后，一定记得把锁解开：

```sql
UNLOCK TABLES;
```

> **易错点**：锁加上了不解，用户那边始终做不了删除、修改这类动作。备份脚本里漏了这一句，影响的不是你自己，是在线业务，要小心。

### 第三方工具与适用的存储引擎

除了自己拷目录，还可以借助第三方的工具，比如 `mysqlhotcopy`，用它来实现备份。

这里有一个关键限制要说清楚：我们这时候的备份，包括下面要讲的恢复，主要针对的都是 MyISAM 这种存储引擎（Storage Engine）对应的表。对 InnoDB 来讲是不适用的，`mysqlhotcopy` 这个工具也是同样的道理。

> **易错点**：这套「拷目录 + 回拷」的路子只对 MyISAM 表成立。库里混着 InnoDB 的表，就不能用这种方式整体拷来拷去。

版本上也有个情况：`mysqlhotcopy` 在 5.5 之前用得比较多，其实到 5.7 以后就不怎么用了，大家注意一下就行。

### 物理恢复的步骤与主版本号约束

恢复的基本做法是这样：把之前备份出来的那个数据库目录，直接拷贝回当前的数据目录下，然后重启一下 MySQL 服务器，再查询看看数据是不是就有了。

先记住有这么几步，至于为什么拷回来还得再做点别的，等演示的时候说——这里边还有一个辅助操作 `chown`。

> **提示**：`chown` 这一步不是可做可不做的，它决定了拷回来的表能不能被正常读写，后面演示完你就明白它的分量了。

还有一个比较严格的要求：备份的那个数据库，和我们要恢复到的这个数据库服务器，主版本号得是一样的。

主版本号指的就是 `8.0` 对 `8.0`、`5.几` 对 `5.几` 这一层的号。你拿 8.0 的备份去恢复到 5.几的服务器上，这就叫不一样。为什么要卡这么严？因为这个备份包里边的细节在不同大版本之间是有差异的，版本对不上，恢复的时候就会产生一些 bug 问题。

### 物理备份与恢复的完整演示

理论上就这些，下面做一遍实操。

#### 准备一个 MyISAM 表的演示库

先刷新一下，目前的数据目录下有这么几个库。有同学可能会问：怎么不拿现有的数据库去演示？因为这套东西针对的是 MyISAM 存储引擎的表，而现有的库里多少都会有 InnoDB 的表，掺在一起就不合适了。所以重新建一个库、一张表：

```sql
CREATE DATABASE atguigudb5;

USE atguigudb5;

CREATE TABLE test1 (
    id INT
) ENGINE = MyISAM;

INSERT INTO test1 VALUES (1), (2), (3);

SELECT * FROM test1;
```

几处关键的地方：库是新建的，避免跟别的库混在一起；表 `test1` 只写了一个 `id INT` 列，这里是简单演示，就不铺开了；建表时用 `ENGINE = MyISAM` 显式指定存储引擎，这一条是整套操作能成立的前提；后面插的三条数据只是标记，用来验证恢复出来的是不是原来那份。

`SELECT *` 一看，三条数据都在。这时候在数据目录下 `ll` 一下，就能看到这个库对应的目录和文件已经物理地躺在磁盘上了——我们备份的就是它。

#### 加锁、刷新与目录拷贝

备份之前先按前面说的把一致性锁上：

```sql
FLUSH TABLES WITH READ LOCK;
```

执行完马上验证两件事：查询这张表，没问题，能查；再去执行 `DELETE FROM test1`，直接被挡下来了。锁就是这么起作用的——防止备份之前表里的数据出现不一致。

接着做拷贝。我们此刻就在 MySQL 的数据目录下，`backup` 是之前建好的备份目录：

```bash
cd /var/lib/mysql
ll
cd backup
ll
cd ..
cp -r atguigudb5 backup/
```

`cp -r` 里的 `-r` 表示把当前这个目录以及它下面所有的子目录一起递归复制；要备份的库是 `atguigudb5`，目标是 `backup/` 这个目录下。库里数据少，所以复制一下就完了。复制完再回到 `backup` 目录 `ll` 一下，确认这份目录已经在里面。

然后立刻解锁：

```sql
UNLOCK TABLES;
```

到这里，一个物理备份就完成了。

#### 删数据、删目录与回拷恢复

下面演示恢复。为了造出一个「数据损坏」的现场，先在表里做一次删除：

```sql
DELETE FROM test1;
SELECT * FROM test1;
```

查询出来是空的，你就当这个库的数据现在已经损坏了。接下来恢复：先退回数据目录，把整个 `atguigudb5` 目录干掉，再 `ll` 确认它确实不在了：

```bash
cd /var/lib/mysql
rm -rf atguigudb5
ll
```

然后用 `mv` 把备份目录里的那份移回来：

```bash
cd backup
mv atguigudb5 ../
cd ..
ll
```

回来以后再 `ll` 一下，`atguigudb5` 又出现在数据目录里了。文件回来了，还要重启当前这台 MySQL 服务器：

```bash
systemctl restart mysqld
```

重启之后回到客户端里查询：

```sql
SELECT * FROM test1;
```

结果拿到的不是数据，而是一句 `Table 'test1' is read only`——表成了只读的。

#### 重启后的表只读问题与 chown 修复

看到只读，第一反应是不是会话的问题、需要重新登录一下？那就退出再登一次：

```bash
exit
mysql -uroot -p
```

密码按提示输入（演示里是 `abc123`），登录成功后切到库，再查：

```sql
USE atguigudb5;
SELECT * FROM test1;
```

还是 `Table 'test1' is read only`。所以跟重新登录没关系，是当前这张表的权限不够。原因就在前面提过的那个 `chown` 上。

MySQL 服务器在 Linux 上是拿 `mysql` 这个系统用户去跑、去访问数据文件的，另外还有一个 `root` 用户，是两回事。我们刚才做了什么？把原来的 `atguigudb5` 目录删了，再把备份里那份整体移过来——对系统来说，现在这个目录已经不是原来那个了，它算是一个新的目录，属主和权限跟着拷过来的那份走，`mysql` 用户拿不到访问权，于是表就只剩只读了。

修复的办法就是把目录连同它下面所有子目录的属主交给 `mysql` 用户：

```bash
chown -R mysql:mysql atguigudb5
```

`-R` 是递归，`mysql:mysql` 是「用户:组」，最后跟的是那个库目录。粘命令的时候注意把目录名改成 `atguigudb5`，名字对不上这一步就白做了。

```text
atguigudb5 目录（从 backup 移回来的那一份）
        |
        |  整体替换掉数据目录下的同名目录
        v
/var/lib/mysql/atguigudb5    属主不是 mysql
        |
        |  mysqld 以 mysql 用户身份去访问表文件
        v
Table 'test1' is read only
        |
        |  chown -R mysql:mysql atguigudb5
        v
属主变成 mysql，表恢复正常读写
```

读图说明：从备份移回来的目录带着自己的属主信息，MySQL 服务进程以 `mysql` 用户身份打不开它，表现就是表只读；`chown` 把属主与属组改成 `mysql` 之后，读写才恢复。

改完再查一次：

```sql
SELECT * FROM test1;
```

三条数据回来了。到这儿，物理层面上的备份和恢复就演示完了，大家稍微熟悉一下这套流程。

最后再叮嘱一句：逻辑备份也好、物理备份也好，开发当中都可以根据实际的场景去作这样的操作，但一定要多演示几遍。别真到了实际生产环境里操作的时候挂掉，更别拿着正在跑业务的这个库直接上去改——那会对数据产生二次污染，后面就麻烦了。

### 表数据导出的三种方式

下面讲一件小事：具体一张表当中的数据，我们可以导出到具体文件里，也可以再把它导回表里。导出和导入来回就这么几条指令，熟悉一下就可以了。先看导出，导出有这么三种方式。

#### SELECT ... INTO OUTFILE 与 secure_file_priv

第一种是 `SELECT ... INTO OUTFILE`。`SELECT` 决定你查哪些数据，查出来的就写到指定的文件里——所以导哪一部分数据、导多少，完全由你自己写的那条 `SELECT` 说了算。

这种写法对文件路径有要求，先看一下相关的参数：

```sql
SELECT @@secure_file_priv;
```

没提前改过的话，默认值是 `/var/lib/mysql-files/` 这个目录。这个参数取什么值，含义完全不一样：

| `secure_file_priv` 取值 | 含义 |
| --- | --- |
| 空（empty） | 可以导出到任意路径 |
| 一个具体路径 | 只能导出到该路径或它的子目录下 |
| `NULL` | 禁止导出 |

现在的值是一个具体路径，所以就要导到那个目录里边去。先切到演示库，看一眼要导的表：

```sql
USE atguigudb3;
SELECT * FROM account;
```

`account` 表里有三条数据，把它们全导出去：

```sql
SELECT *
INTO OUTFILE '/var/lib/mysql-files/account_1.txt'
FROM account;
```

> **易错点**：`INTO OUTFILE` 是 SQL 语句的一部分，要在 `mysql` 客户端里执行；丢到命令行上去跑是不成立的。

执行成功以后，到那个路径下找一找：

```bash
cd /var/lib/mysql-files
ll
cat account_1.txt
```

文件确实在。`cat` 一下看内容：里面是一条条实实在在的数据，**表结构没有**——这种方式只搬数据，不搬表结构。这一节里导出去的数据，后面还要再导进来。

#### mysqldump -T 同时导出表结构与数据

第二种用 `mysqldump`。前面用它做过逻辑备份，它同样可以针对某一张表中的数据做导出。跟第一种不一样的地方在于：它能把表结构也一起导出。

这一条要在命令行里执行，不是在 `mysql` 客户端里：

```bash
mysqldump -uroot -p -T /var/lib/mysql-files atguigudb3 account
```

参数逐个看：`-uroot -p` 是用户名和密码，密码回车后按提示输入；`-T` 后面跟的是导出目录，这个参数别丢了；再往后是数据库名和表名。

执行完 `ll` 一下，同时出来两个文件：

- `account.sql`：用 `vim` 打开看，里面是这张表的表结构，也就是创建表的语句，**没有表数据**；
- `account.txt`：表数据在这个文件里。

这就是 `mysqldump` 比第一种强的地方——表结构和数据它一块儿给你导出来，两边分开放。

> **提示**：文件名要留意。第一种方式里我特意把导出文件写成了 `account_1.txt`；如果那次直接写成 `account.txt`，这次 `mysqldump` 生成的文件会把它覆盖掉，前后两个文件的效果就分不出来了。

两种方式的差别，说到底就是「导什么由谁决定」：`mysqldump -T` 导的是整张表的全部数据；第一种方式里有 `SELECT`，你想导哪部分数据，就怎么写。

它还可以有更丰富的用法。刚才看那个 `account.txt`，列与列之间是用制表符分开的，字符串外面什么也不带。如果希望字符串用双引号引起来、不同的列之间用逗号分隔，就把这两条格式限定写进导出命令里。

演示的时候把目标表换成 `student`——再拿 `account`，又把这些同名文件覆盖掉了，前后就分不出来了。执行完同样是两个文件：

```bash
vim student.sql
cat student.txt
```

`student.sql` 里就是创建这张表的语句，仍然没有表数据；`student.txt` 里，列与列之间是逗号，字符串外面带着双引号，就是这么个效果。

#### mysql 命令导出与 --vertical、--xml 两种呈现

第三种是用 `mysql` 这个命令去导出文本文件。它比 `mysqldump` 更灵活一点，因为后面可以直接写 SQL 语句，不一定非得导全部数据；导出到哪个文件，也可以具体指定。

```bash
mysql -uroot -p atguigudb3 -e "SELECT * FROM account" > /var/lib/mysql-files/account_2.txt
```

数据库名要写清楚，`-e` 后面跟要执行的 SQL，最后把命令的输出重定向到指定的文件里。执行完 `ll` 一看，只有一个 `account_2.txt`，没有 `.sql` 文件——这种方式同样不保存表结构，`cat` 一下，里面只有数据。

除了这种默认的呈现方式，还有更灵活的。加上 `--vertical`：

```bash
mysql -uroot -p --vertical atguigudb3 -e "SELECT * FROM account" > /var/lib/mysql-files/account_3.txt
```

`cat account_3.txt` 看到的就不是一行一条记录了，而是每个字段单独占一行、竖着排下来，跟我们在命令行里敲 `\G` 看到的效果类似。

把 `--vertical` 换成 `--xml`：

```bash
mysql -uroot -p --xml atguigudb3 -e "SELECT * FROM account" > /var/lib/mysql-files/account_4.xml
```

这次文件名后面带的是 `.xml`。查看的时候我少写了个 `4`，`ll` 一看才发现文件名是 `account_4.xml`：`cat` 出来，里面的数据就是以 XML 格式呈现的。

三种方式对照一下：

| 方式 | 命令形态 | 是否含表结构 | 数据范围 |
| --- | --- | --- | --- |
| `SELECT ... INTO OUTFILE` | 在 `mysql` 客户端里执行 SQL | 不含 | 由 `SELECT` 决定 |
| `mysqldump -T` | 命令行工具，指定导出目录 | 含（单独一个 `.sql`） | 整张表 |
| `mysql` 命令加 `-e` | 命令行 + 输出重定向 | 不含 | 由 SQL 语句决定 |

### 表数据导入的两种方式

导出讲完了，下面是导入。

#### LOAD DATA INFILE

第一种是 `LOAD DATA INFILE`。它有个前提：得先有导出的文件才能导入，这里用的就是上面第一种导出方式 `SELECT ... INTO OUTFILE` 生成的文件。

重新导一遍：

```sql
SELECT *
INTO OUTFILE '/var/lib/mysql-files/account_0.txt'
FROM account;
```

这条是在 `mysql` 客户端里跑的——我第一次把它放到命令行上去执行，跑不通。

命令行下 `ll` 一看，`account_0.txt` 已经生成了。接着把表里的数据全删掉，制造出需要导入的现场：

```sql
SELECT * FROM account;
DELETE FROM account;
```

然后导入：

```sql
LOAD DATA INFILE '/var/lib/mysql-files/account_0.txt'
INTO TABLE account;
```

> **易错点**：这条同样得在 `mysql` 客户端里执行，别丢到命令行上去——我也是换了地方才跑通的。

再查一次，数据就都回来了。

另外提一句：导出的时候如果用了某种分隔符、引号之类的符号，导入的时候要跟它对应上，别一边一种写法。这一条就不单独演示了，没什么特别的。

#### mysqlimport

第二种用 `mysqlimport`。同样得先把数据导出到一个具体文件里，然后才能导入。

这次换个表，用 `atguigudb3` 下的 `teacher`：

```sql
SELECT *
INTO OUTFILE '/var/lib/mysql-files/teacher.txt'
FROM teacher;
```

导出成功，先看看表里有数据，然后执行 `DELETE FROM teacher;` 把数据都删掉。回到命令行 `ll` 一下，`teacher.txt` 已经帮我们生成在那个目录里了。

接着用 `mysqlimport` 恢复，这条在命令行执行：

```bash
mysqlimport -uroot -p atguigudb3 /var/lib/mysql-files/teacher.txt
```

密码回车输入 `abc123`，执行完再查一次 `SELECT * FROM teacher;`，数据就都回来了。

命令里可以看到，我们只写了数据库和文件，没有写表名——`mysqlimport` 是拿文件的主文件名当表名的，所以文件名去掉扩展名之后得正好是那张表的名字。这也是为什么前面既要把数据库调对，还要把文件改成 `teacher`。

`mysqlimport` 还有其他一些相关参数，这里就不一一介绍了。关于表中数据的导出、导入，涉及到的就是这些指令，大家熟悉一下就可以了。

## 198-数据库迁移与如何删库不跑路
> 对应分集：P198 | 原始标题：《198-数据库迁移与如何删库不跑路》

### 数据库迁移的定义、触发场景与本质

一说到数据迁移，你们脑子里可能先跳出来另一个词——迁徙。非洲大草原上那些动物，随着季节变化成群结队地换地方，那叫迁徙。我们要讲的数据库迁移（database migration）跟它有点像，但不是一回事。

> **定义**：数据库迁移，是指把数据从一个计算机存储系统**永久性**地传输到另外一个计算机存储系统的过程。

为什么要做这件事？逼着我们把数据挪一次的原因不少：服务器或者存储设备的更换、设备的维护和升级、灾难恢复、数据中心的迁移，这些情况都会落到迁移上。

那迁移的本质是什么？

> **结论**：迁移的本质就是我们前面讲过的备份和恢复，只是侧重点不一样。同一台服务器上把数据备份出去，出了事再恢复回这台服务器，我们叫备份和恢复；把数据备份出去以后，恢复到**其他主机**上，这就是迁移。两者实现的逻辑完全一样。

这个过程中有两件收尾的事要单独拎出来：迁移之前，要验证迁移数据的完整性——这一点备份、恢复、迁移三件事都躲不开；迁移完成、新环境跑稳之后，要退役原来那台旧的存储设备，不能新旧两套长期并存着跑。

至于迁移方案，没什么新东西可说：物理备份（physical backup）的迁移、逻辑备份（logical backup）的迁移，前面都讲过，这里不重复。

### 迁移注意点之一：相同主版本号之间的迁移

相同数据库版本之间的迁移，问题会少一些。注意这里说的“相同版本”，指的是**主版本号一样**，而不是小版本号一个数字都不差。

这里有一个前面讲物理备份时就强调过的限制：物理备份这条路，只适用于 `MyISAM` 这类存储引擎（storage engine）的表。`InnoDB` 的表不适合做物理备份，也就不适合做物理迁移。

> **易错点**：别把“字节级复制数据文件”当成通用方案。`InnoDB` 表要走逻辑的方式，推荐使用 `mysqldump` 导出后再导入。

### 迁移注意点之二：不同版本之间的迁移

版本不一样的时候，方向决定难度。

从低版本往高版本迁，一般都比较顺。比如从 `5.7` 迁到 `8.0`：数据库本身是向下兼容的，把低版本导出的备份文件拿到高版本的服务器上做一个恢复，通常问题不大。

反着来就要小心了。假设你手上是 `8.0` 的库，把数据备份出来，数据中心迁到另外一个城市，结果那边的数据库版本比较低，比如还是 `5.7`——这中间往往有很多坑。原因在于高版本通常会修掉低版本的一些缺陷，做过一些修正，高版本导出的数据在低版本里就不一定兼容。

举个最简单的例子：`5.7` 里默认字符集是拉丁（`latin1`），到 `8.0` 改成了 `utf8mb4`。如果对面那台 `5.7` 从来没改过字符集，而你的 `8.0` 库里存着中文，往 `5.7` 里一倒就报错了。

所以跨版本往下迁的时候，必须提前把低版本那边需要修正的地方处理好，再去倒数据。当然，能不折腾就不折腾——尽量在相同版本之间做迁移，会省掉很多事。

### 迁移注意点之三：不同数据库之间的迁移

粒度再提高一点，变成不同类型的数据库之间迁移，坑就更多了。不同数据库之间的差别非常大：咱们这门课讲的各种优化和策略都是基于 MySQL 的，你拿 Oracle 去套，有一部分适用，也有一部分根本不适用；关键字不一样、SQL 语句写法也不一样，这些都是坑。

#### MySQL 与 Oracle 之间的迁移

MySQL 和 Oracle 之间做迁移，相对还算好办一点。MySQL 被 Oracle 收购已经有些年头了，两者对 SQL 的支持比较接近。虽然数据类型上仍有区别——比如 `varchar` 在 Oracle 里叫 `varchar2`——但我们可以把导出的 SQL 文件手工做一遍调整修改，就能实现在 Oracle 上的恢复。这类场景的前提是：两个数据库本身差别不算太大。

#### 技术壁垒与迁移工具

有些数据库之间的差别是**故意**造成的技术壁垒，说白了就是对大家都好，你用了就尽量一直用下去。这事跟国内通信运营商的情况一模一样：移动、电信、联通，你想换个手机号，成本高得离谱。你的京东、淘宝、美团，各个银行的账号，全绑在这个号上，你觉得这家信号特别差、收费也不合理，想迁到别的运营商——根本不敢迁，只能忍着。运营商还特别喜欢对新用户优惠，你是老用户，月租高、套餐还不合适。最后是国家出面，要求转号必须顺畅，也就是携号转网。如果没有这种干预，他们当然乐意一直营造这种壁垒。

跨数据库迁移也有现成的工具来帮忙，比如 `MyODBC`，以及 MySQL 官方提供的迁移工具，都可以考虑。

> **注意**：不同数据库之间的迁移，一定要有高手专门指导着做，里面的坑比较多，这一讲没办法把它完全展开。

### 传统高可用架构对误删除的失效

接下来换个问题：删库了不敢跑，能干点啥？不敢跑，或者不想跑，道理是类似的。

网上经常看到一句话叫“从删库到跑路”。这大多数时候是调侃，但实际情况里，我们确实没法保证——恶意操作可能不至于，但**无意**删掉了不该删的数据，这是完全可能发生的。常在河边走，哪能不湿鞋。

真出了这种事，第一件要认清的事是：传统的高可用架构，**不能**预防误删除。

比如你在主库上执行了一个 `drop table`，这条操作很快就会通过二进制日志（binary log，binlog）传给所有的从库，连级联的从库在内，结果从库上相应的表也一起被删掉了。这就非常恶心了。

```text
                  DROP TABLE 一条语句
                          |
                          v
                 +------------------+
                 |    主库 Master    |
                 +------------------+
                          |
               binlog（statement 记录该语句）
            +-------------+-------------+
            v                           v
    +---------------+           +---------------+
    |  从库 Slave-1  |           |  从库 Slave-2  |
    |  表一并被删掉   |           |  表一并被删掉   |
    +---------------+           +---------------+
```

读图说明：一条删除操作在主库上执行完，会顺着复制链路迅速扩散到所有从库，从库上的表跟着一起消失，所以主从高可用只解决“可用”，解决不了“误删”。

要解决这件事，得先把删除操作**分类**，不同的问题有不同的方案。我们按 `delete`、`truncate`/`drop`、`rm` 这三类来谈。

### delete 误删的恢复与预防

`delete` 的影响范围比较小，恢复起来也比较容易。常用的措施是拿 `flashback` 这样的工具来做数据恢复。这个工具我不在这儿演示，你们有这个诉求，直接拿来用就行，比较容易上手。我想主要说的是它的原理。

#### flashback 的恢复原理与前置条件

`flashback` 的主要原理，其实就是**修改 binlog 的内容**。前提是 binlog 里记下了一条一条被删除的数据，所以格式上我们需要的 `binlog_format` 是 `ROW`，同时还要有 `binlog_row_image = FULL` 这个参数配合。

在这种前提下，我们把当初那些删除操作对应的指令取出来，做一个反向回放就行了：原来执行的是 `delete`，我们把它改成 `insert` 再加回去。

> **提示**：这个思路和我们前面讲过的 undo 日志是一脉相承的——记录反向操作，把数据推回原样。

如果误删除的数据涉及多个事务怎么办？这一个事务、那一个事务，里面有 `update`、`delete`、`insert` 各种行为。那就反过来操作一遍：恢复的时候按相反的方向把每个事务的动作还原，就可以了。

```text
binlog 中记录的行事件              恢复时的反向回放
+--------------------------+      +--------------------------+
| DELETE FROM ...          | ---> | INSERT INTO ...          |
+--------------------------+      +--------------------------+
| UPDATE 新值              | ---> | UPDATE 改回旧值           |
+--------------------------+      +--------------------------+
```

读图说明：`flashback` 不去翻原始数据页，而是把 binlog 里的行事件按相反动作重建成新语句再回放一遍，所以它能不能用，完全取决于 binlog 有没有把每一行都记下来。

#### 安全更新模式 sql_safe_updates

恢复只是补救，重点还是要**预防**。

第一，代码在上线之前必须做 SQL 审查，确认里面没有你并不想主动执行的删除行为。

第二，打开安全模式，防止误删大批数据。这里涉及的是 `sql_safe_updates`，把它设置成 `ON`。设置好之后，你再去执行删除操作时，它就会强制要求你带上 `where` 条件。

而且这个 `where` 条件不是随便加一个就行：条件里用到的字段**必须得有索引**。这一点我特意去官网上确认过，实际也用代码测了一遍——没有索引的话，照样报错。

那如果确实要删全表、没有 `where` 可用呢？那就必须使用 `limit`。如果既不想写 `where`，也不想写 `limit`，还有一个办法：写一个一定成立的条件，比如 `where id > 0`——`id` 上有索引，而且所有 `id` 都大于 0，这样既满足了安全模式的要求，也等于向自己确认了一遍：你是真的要把数据都删掉。

```sql
-- 打开安全更新模式
SET sql_safe_updates = ON;

-- 被拒绝：既没有 WHERE 也没有 LIMIT
DELETE FROM t;

-- 被拒绝：WHERE 字段上没有索引
DELETE FROM t WHERE status = 0;

-- 通过：id 上有索引，且该条件恒真
DELETE FROM t WHERE id > 0;
```

上面的表名 `t` 只是占位写法，关键是这三条语句各自为什么会被安全模式拦下或被放行。

### truncate 与 drop 的恢复：全量备份加增量日志

第二类是 `truncate` 和 `drop`，代表操作有 `truncate table`、`drop table`，以及粒度更大的 `drop database`——整个数据库都被删掉了。

顺带说一句性能上的区别：`delete` 是比较慢的。如果一张表的数据你压根都不想要了，还用 `delete` 一行行删，它还会生成相应的回滚日志、写 redo、写 binlog。这种场景换成 `truncate`，性能会有所提升。

#### flashback 为什么对 truncate 与 drop 无效

> **结论**：`truncate` 和 `drop` 这三类操作，用 `flashback` 是恢复不回来的。

原因在于，这类操作在 binlog 里使用的是 `statement` 格式。`statement` 只记录你执行的**语句**，并没有把每一条被删掉的数据记下来，所以没有可供反向回放的行数据——这就没法恢复了。

> **易错点**：表的复制格式本来配的是 `ROW` 也没用。`truncate` 会**自动**改成 `statement` 模式，最终 binlog 里就只留下一条 `truncate` 语句，数据却全被干掉了。

打个比方：某一时刻表里还有 100 条数据，你一条 `truncate` 下去，这 100 条全没了，而 binlog 里只有孤零零一条语句。那你说怎么恢复？肯定不行。

```sql
-- binlog 里只会留下这一条语句，行数据一条都没记
TRUNCATE TABLE t;
```

#### 从全量备份到 binlog 回放的恢复流程

这种场景要恢复，思路是：先把数据恢复到某一个时间节点上，再顺着 binlog 往后查，一步步恢复到当前这个场景。这就是**全量备份（full backup）加增量日志**的方式。道理很容易想到，前提只有一个——**你得有备份**。有备份在手，再配合 binlog，就能搞定。

举个具体的场景。下午 3 点，人比较困，咖啡也没喝，手一抖来了个 `truncate` 或者 `drop`，怎么办？

假设我们的策略是一天一备，备份时间是当天凌晨 2 点。

```text
时间轴
  02:00                              15:00
    |                                  |
    |  全量备份（一天一备）              |  误删：truncate / drop
    |                                  |
    |<--------- 需要回放的 binlog ------>|

恢复步骤
  [1] 取出最近一次全量备份（当天 02:00）
            |
            v
  [2] 先把全量备份恢复到临时库（不要直接动主库，避免二次破坏）
            |
            v
  [3] 取出 02:00 → 15:00 之间这一段的 binlog 日志
            |
            v
  [4] 剔除其中误删除的那条操作语句，用剩下的语句在全量备份的基础上做增量恢复
            |
            v
  [5] 数据确认无误后，再回灌到主库
```

读图说明：恢复的基准是最近一次全量备份，binlog 只负责把备份之后到误删之前这段时间的变化补回来，中间那条误删语句必须剔除。

这里最要紧的一步是**先恢复到临时库**，千万不要上来就往主库上恢复。万一接下来哪一步操作失误，等于把主库又二次破坏了一遍。binlog 具体怎么用来恢复，前面已经讲过了。

具体的操作步骤我在这里也不演示，方案就是这个方案。

### truncate 与 drop 的预防：权限分离与操作规范

针对 `truncate` 和 `drop`，预防措施我写了三条，先说前两条。

**第一，权限分离。** 避免这件事发生的前提，是相关人员**根本没有**这个权限。我们轻易不会分配相关的写权限；确实要实施，必须走审批。比如业务开发人员给 DML 权限，但不给 `truncate` 和 `drop` 的权限；DBA 成员也类似。不同账号设置不同权限、做权限分离，也就避免了一个账号能把所有的库都删掉。始终从权限的角度去做限制。

**第二，制定操作规范。** 既然容易误删，那就先不让你删：先把这张表的名字改一下，改完之后相关 SQL 语句就不再依赖这个改名后的表了。然后观察一段时间，看这张表还有没有价值，确实没价值，后面再删掉。

这跟我们衡量一个员工的价值是一个道理：假设你两天没来公司，结果发现公司运转得特别好，没有你反而更好——那你就是可有可无的，甚至走了以后更好。反过来，没了你整个公司就不转了，那你的价值显然非常大。判断一张表要不要删，用的也是这个思想。

改名的时候可以起一个见名知意的名字，比如 `to_be_deleted`，谁一看都知道这是将来要被删掉的东西。

### 延迟复制备库的恢复窗口与用途

第三条措施是设置**延迟复制备库（delayed replica）**。

我们一开始的想法通常是：主从复制要尽量减少数据不一致，尽快达到一致，把主从延时压到最低。但在某些场景下，我们反而要**故意**去延迟复制这个备库。

比如要求主库上的操作过**一个小时**之后，再同步到备库上。这样一旦出现误删除，只要你在一个小时之内发现了，就可以及时地把 `STOP SLAVE` 断掉，先把从库（备库）上的数据拿到手——这时候备库上还没删；主库虽然已经删了，但备库上表还在，接下来做恢复就非常容易了。

```sql
-- 发现误删除后立即断开复制线程，保住备库上还没被删的数据
STOP SLAVE;
```

延迟多久是可以设置的，这个参数里的 `N` 代表**秒**，比如写成 `3600`，代表的就是一个小时。

延迟复制备库除了防误删、让恢复更方便，还有两个用处。

一个是做**延迟测试**。比如你做了读写分离，写入之后看到的是这样的效果，你想看看数据还没及时传到从库上时，从库查询出来是什么效果，就可以设置一个延迟备库来观察。

另一个是查询**老数据**。夸张一点，我们让复制延迟一周，也就是这一周之后数据才会同步过去，那么你想看一周之前的那些数据是什么场景，就可以直接查这个延迟备库。

### rm 删除实例的处理与集群数据的分散存放

最后一种是通过 `rm` 的方式，相当于把整个 MySQL 实例给干掉了。看起来影响最大，但这种情况反而比较容易解决。

> **结论**：对于高可用的 MySQL 集群来说，`rm` 干掉的只是其中一个节点上的实例。把这个节点退下来，让其他节点补上去，然后对这个节点做数据恢复，恢复完再接回去就可以了，影响其实并不大——高可用的系统本身都做过相关的方案处理。

真正麻烦的是**恶意把整个集群删掉**。这就要求我们确保整个集群的数据最好不要放在同一个地方，要跨机房备份、跨城市备份，尽可能减少这种极端情况下的损失。

### 三类删除操作的对照

| 删除操作 | 影响粒度 | binlog 记录方式 | `flashback` 能否恢复 | 主要恢复手段 | 主要预防措施 |
| --- | --- | --- | --- | --- | --- |
| `delete` | 行级 | `ROW` + `binlog_row_image = FULL`，逐行记录 | 能 | `flashback` 反向回放 binlog | 上线前 SQL 审查，开启 `sql_safe_updates` |
| `truncate` / `drop` | 表级、库级 | `statement`，只记一条语句（`truncate` 会自动切到该模式） | 不能 | 全量备份 + 增量 binlog 回放（先恢复到临时库） | 权限分离、先改名后删除、延迟复制备库 |
| `rm` 删除实例 | 实例级 | 实例已不存在 | 不适用 | 高可用集群其他节点顶上，节点恢复后接回 | 集群数据跨机房、跨城市分散存放 |

### 内卷的含义与现实判断

#### 局部极限投入与总体无收益的竞争

内卷是这一两年非常火的一个词，每个人也经常把内卷这个词应用到自己的行业里，说自己所处的行业非常内卷。一定程度上，这是想缓解一下自己的焦虑，也是面对竞争的一种自我安慰。

那么内卷这个词的含义到底是什么？有一句话我觉得非常精炼地概括了这种情况——这不是我说的，是罗胖（罗振宇）说的：

> **定义**：内卷是指那些即使在局部玩命地投入资源，但在总体上也没有什么实际收益的竞争。

大家去细细体会这里面的几个词：**局部**、**玩命地投入资源**、**总体上没有实际收益**。判断一件事到底算不算内卷，就看它是不是同时满足这三条——在很小的范围里把力气用到极致，却换不来整体上的收益增量。

#### 劳动、技术、资本三个投入角度

那么在我们现在中国这样一个大环境当中，各行各业真的都那么内卷吗？我觉得未必。

一提到经济上大体量的竞争，懂经济学的人可能会更懂一些，我这里稍微卖弄一下——主要其实有三个角度：第一是劳动，第二是技术的投入，第三是资本的投入。

- 对于改革开放三十多年的中国来讲，资本一直都有；现在中美竞争加剧，我们也看到好多资本又要涌入中国。所以从资本这个角度看，投入从来没有缺过。
- 我们传统上是劳动密集型的，很便宜。
- 现在我们在往上走，往第二个层面，也就是技术层面，加大投入。大家也能看到，国家的一系列策略是不是都在针对技术这个角度去做投入。

所以从这层意义上讲，中美竞争其实是必然的——因为中国现在已经在挑战美国的一些技术场景了。至于是不是真的能规避修昔底德陷阱（Thucydides Trap），这个我们只能走着看。

我们现在才开始往技术方面进行大范围的投入，那就意味着从劳动型到技术型之间，这个阶段的"卷"其实还没有那么严重。

#### 技术、设计、餐饮三个行业的回报检验

是不是这样，我们拿几个行业实打实地讲：

| 行业 | 投入方向 | 能感知到的回报 |
| --- | --- | --- |
| 技术岗 | 把自己的技术实打实地提升一些 | 薪资待遇、在老板心中的形象，越来越被重视 |
| 设计、产品经理 | 把设计做得更好一些 | 来自客户的反馈会更好一些 |
| 餐饮 | 服务更贴心、更用心一些 | 顾客来得更多一些 |

三行看下来是同一个道理：投入能被别人明确辨认出来，回报就跟着来。

> **结论**：只要你的提升是别人看得见、用得上的，就还在有收益的区间里——从这个意义上来讲，我们离内卷还早。

### 技术岗位上的两类角色与能力要求

那么如果我们回到技术岗位上来，我觉得可以分两种角色看。

#### 一线员工：业务熟练度与不可替代性

如果你身为一线员工，我觉得你要不断地去提升自己的业务能力。

如果你还比较年轻，有幸被领导指导，他能手把手地带你，这是一件非常非常非常非常幸福的事情——我这里重复了好几遍，大家能懂我想表达的意思。

如果没有这个条件，你自己一定要千方百计地去成长。

如果你能长到比领导对具体业务还要熟悉，那你就是不可替代的，你的价值就会很大。到那个时候，你去卷别人，别人可能连跟你 PK 的机会都没有。

#### 部门领导：管理能力与编码能力

如果你身为一个部门的领导，你可以不去一线写代码。但除非你有极强的管理能力，否则我觉得你也要有不错的编码能力。

不知道大家有没有看过《贞观之治》《汉武大帝》这样的历史剧。我看《贞观之治》的时候有一点感触：李世民是千古一帝，管理能力极强；但他打仗也绝对是一把好手，只不过后来成为帝王之后很少御驾亲征了，可他的打仗水平绝对是一顶一的。

带团队和带兵在这一点上是一样的：可以不必亲自上手，但不能不懂。

### 技术积累的实操路径

第二件事，是关于更好的技术积累该怎么做。我从两个角度上去说，先讲实操的角度。

有的同学会问我："你是如何把 MySQL 的整个知识架构整理出来、录制这套课程的？"这次的下篇，我一共罗列了 19 个章节，是通过四个小的子篇章梳理开的。我是怎么学的，也可以做一个简单的分享。

决定录 MySQL 这样一套课程的时候，我有好几个维度：一个是以前的积累；第二个是尚硅谷毕业了非常多的同学，我可以通过他们输入很多信息和经验；还有一个维度，就是看书。

#### 书籍的选择与交叉阅读

有的同学时不时会问我：想学数据架构，想学一些设计模式，想学某个框架，有没有好的书推荐？其实这是一件很容易的事情。以 MySQL 为例，在京东上搜一下，相关的书就能搜到这样一些。也经常有同学问：我到底应该买哪本书会更好一些？

如果你没有确定的观点，那么大家已经做技术了，也不差这个钱——你多买几本。事实情况也确实如此，这是我的一个经验：比如我买这本书，看这一个章节的时候，感觉它跟我有共鸣，我很好理解；但下一章它可能描述得并不太好，那我就换一本书，那本书可能写得就会更好一些。所以你可以颠倒着这样去看，可以多买几本。

应该说，MySQL 这里边的这些书，就我现在看的话，眼睛都非常熟。为什么？因为我不能保证自己看到哪儿了——我不敢说从上往下翻到这块的书我都看完了，但基本上每本书我都翻过、都看过，家里边关于 MySQL 的书其实很一摞。

当你有这样一个意识的时候，你再投入一点精力，你很难说把这件事弄得特别好，但你一定不会特别差。

#### 知识系统的搭建流程

在你翻了这么多书的情况下，接着要做一个什么事呢？如果你想做一个整体的梳理，大家要形成一个知识系统。

要列一个思维导图，然后把知识细节都展开：先列一级目录，然后通过一些书再去看，查漏补缺，看它是不是完整的；然后再去列二级目录。二级目录一般我们就不说为什么了，就是列出这样几个知识点。

列完之后再往下列的时候，大家不断地去问为什么就可以了。包括我们在实际工作当中，你去提升，怎么提升？你就持续不断地去问为什么，问到一定程度之后，基本上你也到底了，就可以了。

```text
          列出思维导图的一级目录（主干章节）
                       │
                       ▼
       对照手中多本书籍逐条核对 ──► 查漏补缺，确认主干是否完整
                       │
                       ▼
          列出二级目录（只罗列知识点，不追问原因）
                       │
                       ▼
        继续向下展开：对每一个知识点不断追问「为什么」
                       │
                       ▼
                问到底 ──► 知识系统成型
```

读图说明：一级目录靠书籍交叉核对来保证完整，二级目录之后靠连续追问「为什么」把细节推到尽头。

> **提示**：一级目录负责完整性，二级目录负责知识点清单，从更细的层次开始才靠不断追问「为什么」往深处走。

### 技术积累的态度：延迟满足

那么从态度上来讲，我觉得需要做延迟满足。

比如我录制 MySQL 高级这样一套课程，实际上从 12 月的上旬开始，一直到现在的这个时间，这期间我都在录制。中间还经历了 2022 年的元旦，应该说有半个多月时间我都没怎么休息过了，没有所谓的周末。

但是说实话，我一点都不感觉累。大家可能看我录制的时间，大部分都集中在下午和晚上，因为白天还有公司的一些事情需要去忙，一忙起来再去录，中间就耽搁了，所以一般晚上的时间比较安静一些，可以有大块的时间来录制课程。说实话，真的不觉得累。

在这里我想起一句话，是日本的稻盛和夫说的：工作不是不得不做的必要之恶。

大家不要把这个工作非得跟生活分离开。你说今天是周日，我没有出去玩，我工作了，就觉得特别对不起自己——不要这样去想。现在这种场景，基本上大家工作的话，你也会发现很难把工作和生活分离得特别清晰。既然如此，那你何不快乐地去应对这个工作呢？何况你现在的积累对你以后还有极大的帮助。

延迟满足这个概念，以前我给大家分享的时候也提过，这里就不多说了。
