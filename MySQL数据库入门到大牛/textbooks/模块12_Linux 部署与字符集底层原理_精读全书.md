## 96-MySQL高级特性篇章节概览
> 对应分集：P96 | 原始标题：《96-MySQL高级特性篇章节概览》

在《MySQL 基础篇》的 18 个章节中，我们从零起步，系统攻克了 SQL 语法、单行与多行函数、多表查询、子查询、DDL/DML 操作、约束、视图、存储过程与函数、触发器，以及 MySQL 8.0 的窗口函数和公用表表达式。这一套组合拳，帮助我们在“应用与操作”层面打下了坚实的地基。

但如果你问任何一位资深的后端架构师或技术专家：“掌握了这些，在真实的工业级高并发系统面前够用吗？”答案显然是否定的。

写出一句能够跑通逻辑的 SQL 只是第一步。当业务数据从几千条膨胀到几千万条、并发请求从个位数飙升到几万 QPS 时，原本运行良好的系统往往会骤然陷入瘫痪：慢查询拖垮 CPU、锁等待导致线程池耗尽、深分页引发 I/O 阻塞、数据出现幻读与死锁……此时，浮于表面的“增删改查”语法完全失去了排障能力。要破除这些生产瓶颈，我们必须穿透上层语法黑盒，潜入 MySQL 的内核深水区。

这就是我们开启**《MySQL 高级特性篇》**的初衷。我一贯提倡的学习方法是**“大处着眼，小处着手”**：在扎进任何一个微观知识点（小处着手）之前，必须先登高远眺，看清整个知识体系的宏观地貌与底层骨架（大处着眼）。本讲将作为高级篇的总领导引，带大家俯瞰四大核心篇章、19 个章节的完整技术版图。

#### 为什么全面切入 Linux 环境？
我们在基础篇采用 Windows 环境讲解，是为了照顾零基础与初学者的上手成本；但所有从事过实际开发与系统运维的同学都知道：在真实企业生产实践中，**几乎 100% 的 MySQL 生产集群都运行在 Linux 环境下**。

Linux 在多线程调度、虚拟内存映射、文件系统 I/O（如 Direct I/O 与 Async I/O）以及系统资源限制（ulimit）上的表现，与 Windows 存在显著差异。高级篇第一步就从 Linux 环境下的标准化编译与安装起步，直面真实的生产目录与配置文件，彻底告别单机玩具式的运行思维。

### 篇章一：MySQL 架构篇（深入内核机理）

高级特性篇的第一大板块是**架构篇**（涵盖第 01 至 06 章）。要想调优，必须先识其身；如果不了解 MySQL 内部的各个组件如何分工协作、数据在物理磁盘上如何排列，后续的所有优化都只能是无源之水、空中楼阁。

```text
               ┌─────────────────────────────────────────────────────────┐
               │                   MySQL 内部逻辑架构全景                │
               └────────────────────────────┬────────────────────────────┘
                                            │
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
  │ 【第一层：连接层 (Connectors)】                                                   │
  │  客户端连接池 (Connection Pool)、认证授权 (Auth)、安全通信 (SSL)                   │
  └─────────────────────────────────────────┬─────────────────────────────────────────┘
                                            │
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
  │ 【第二层：服务层 (SQL Interface & Core)】                                          │
  │  ├─ SQL 接口 (SQL Interface)     ├─ 解析器 (Parser & AST 语法树生成)             │
  │  ├─ 优化器 (Optimizer 代价评估)  └─ 缓冲池管理 (Buffer Pool)                      │
  └─────────────────────────────────────────┬─────────────────────────────────────────┘
                                            │
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
  │ 【第三层：引擎层 (Pluggable Storage Engines)】                                     │
  │  可插拔存储引擎：InnoDB (默认事务引擎)、MyISAM、Memory、Archive、CSV ...           │
  └─────────────────────────────────────────┬─────────────────────────────────────────┘
                                            │
  ┌─────────────────────────────────────────┴─────────────────────────────────────────┐
  │ 【第四层：存储层 (File System)】                                                   │
  │  物理日志文件 (Redo/Undo/Binlog)、表空间数据文件 (ibd)、系统元数据                 │
  └───────────────────────────────────────────────────────────────────────────────────┘
```
*读图说明：一条 SQL 语句需要自顶向下穿透四层逻辑架构，服务层完成语法解析与执行计划编译，引擎层通过标准的读写接口与物理磁盘交互。*

#### Linux 部署与数据目录深度剖析（第 01-02 章）
- **Linux 环境实战**：系统掌握 RPM、Yum 以及通用二进制包在 Linux 系统上的标准化安装与服务管理；
- **目录拓扑结构**：彻底搞清楚命令安装目录、配置文件（`/etc/my.cnf`）与核心**数据目录（Data Directory，`/var/lib/mysql`）**。深挖系统表空间、独立表空间（`.ibd` 文件）以及 MySQL 5.7（`.frm` 表结构元数据文件）与 MySQL 8.0（去除 `.frm`，全面合流至事务型数据字典）的物理文件差异。

#### 用户管理与权限控制体系（第 03 章）
在实际生产中，直接使用 `root` 账户连接业务应用属于极其危险的高危违规行为。
- **细粒度分权**：从 DDL、DML 到连接资源限制，实战讲解用户的创建、主机段限制（`'user'@'192.168.%'`）、权限授予（`GRANT`）与撤销（`REVOKE`）；
- **角色（Role）机制**：深入剖析 MySQL 8.0 最新引入的“角色管理”（借鉴自 Oracle 体系）。通过“将权限绑定到角色、将角色绑定到用户”的双层抽象，大幅简化百人技术团队的数据库权限运维复杂度。

#### 逻辑架构与执行流转机理（第 04 章）
- **解构四层架构**：系统拆解连接层、服务层、引擎层与文件存储层；
- **SQL 执行全生命周期**：将一条普通的 `SELECT` 查询与一条包含写入的 `UPDATE` 操作，在词法解析（Lexer）、语法分析树（AST）、查询优化器（Optimizer 计算 CBO 代价）、执行器（Executor）到存储引擎的完整交互时序逐段打通；
- **核心内存缓冲机制**：首次引入数据库缓冲池（Buffer Pool）机制，阐明为什么内存命中率能够直接决定系统吞吐量。

#### 存储引擎深度对比（第 05 章）
全面横向评测 MySQL 各类可插拔存储引擎：
- **InnoDB 与 MyISAM 终极对比**：事务保障、行级锁与表级锁、外键支持、崩溃自愈能力（Crash-Safe）；
- **专用场景引擎**：了解内存缓存引擎 Memory、只读高压缩审计日志引擎 Archive、以及通用文本交换引擎 CSV 的适用边界。

#### InnoDB 物理数据存储结构（第 06 章）
这是从 SQL 开发者蜕变为数据库专家的关键一役。MySQL 绝非像文本文件那样粗暴地平铺存储数据，而是构建了一整套严密的物理存储层级：

$$\text{表空间 (Tablespace)} \longrightarrow \text{段 (Segment)} \longrightarrow \text{区 (Extent)} \longrightarrow \text{页 (Page)} \longrightarrow \text{行 (Row)}$$

- **行格式（Row Formats）**：深入剖析 Compact、Dynamic、Compressed 与 Redundant 四种行格式在存储变长字段列表、NULL 值列表、记录头信息以及行溢出（Off-Page）时的位图布局；
- **页（Page）**：InnoDB 磁盘读写的最小基本物理单元（默认 16KB）。掌握页内记录是如何通过单向链表和槽位（Page Directory）实现二分查找的；
- **区（Extent）与段（Segment）**：掌握 64 个连续物理页（共 1MB）构成的区，以及数据段、索引段和回滚段的宏观管理机制。

### 篇章二：索引及调优篇（工业级性能优化与面试核心）

**索引及调优篇**（涵盖第 07 至 11 章）是整个高级篇中耗时最长、工程价值最高、在技术面试中必考的核心内容。

#### 索引底层数据结构（第 07 章）
- **为什么必须是 B+ 树？** 从二叉查找树、平衡二叉树（AVL）、红黑树（Red-Black Tree）、B 树（B-Tree）一路推导到 B+ 树。剖析为什么多路平衡搜索树能够将几千万数据的树高压制在 3 到 4 层，从而将磁盘 I/O 次数降至极限；
- **为什么“书的目录”比喻不够严谨？**
  很多初学者被广泛灌输“索引就是一本书前面的目录”。这个比喻虽然形象，但丢失了极其关键的工程细节。更科学的类比是**大型大学图书馆的图书索书与分类排架体系**：

```text
    ┌──────────────────────────────────────────────┐
    │  大学图书馆检索台 (B+ 树非叶子节点 / 索引目录) │
    └──────────────────────┬───────────────────────┘
                           │ 按分类号二分指引 (如 TP311.13)
                           ▼
    ┌──────────────────────────────────────────────┐
    │  三楼计算机书库 4 架 B 侧 (聚簇索引物理叶子页) │
    ├──────────────────────────────────────────────┤
    │  [书本 1 (物理行)] [书本 2 (物理行)] [书本 3] │
    └──────────────────────────────────────────────┘
```
*读图说明：索引不仅是一张纸面目录，非叶子节点充当索书指南，而叶子节点本身就是排列整齐的物理存储书架（数据与主键紧密交织在一起，构成聚簇索引）。*

- **聚簇索引 vs 二级索引（辅助索引）**：彻底讲透聚簇索引（数据即索引）与二级索引在叶子节点上的存储差异，以及二级索引在检索非排序列时必不可少的**回表（Bookmark Lookup）**开销。

#### 索引创建与设计准则（第 08 章）
- **拒绝死记硬背**：在过去，很多人面对“12 条适合建索引的场景”和“7 条不适合建索引的场景”痛苦地背诵。一旦真正理解了 B+ 树的物理结构与排序逻辑，这些规则就能像坦克平推一样顺理成章地推导出来：
  - 为什么区分度高、唯一性强的字段适合建索引？（区分度低会导致大量无效扫描与回表）；
  - 为什么频繁更新的字段不适合建索引？（频繁触发 B+ 树叶子页分裂与合并开销）；
  - 为什么大文本字段必须建前缀索引？（控制非叶子节点容量，防止树高失控膨胀）。

#### 性能分析工具箱（第 09 章）
调优必须讲究“证据链”，不能靠瞎猜。我们将系统操练全套生产级排查工具：
- **慢查询日志（Slow Query Log）**：捕获线上拖垮性能的长耗时慢 SQL；
- **执行成本评估（Last_Query_Cost）**：量化单次查询评估的数据页数量；
- **EXPLAIN 执行计划精读**：拆解 `id`、`select_type`、`type`（从 system、const 到 ALL 的性能阶梯）、`possible_keys`、`key`、`key_len`（判断联合索引命中字节数）、`ref`、`rows`（预估扫描行数）以及 `Extra`（Using index、Using filesort、Using temporary 等核心指标）；
- **SHOW PROFILE**：毫秒级洞察 SQL 在各个底层系统调用阶段（Starting、Checking permissions、Opening tables、Sending data）的时间开销。

#### 索引优化与实战避坑指南（第 10 章）
- **经典索引失效陷阱**：最佳左前缀法则被破坏、在索引列上进行函数计算或类型隐式转换、范围查询导致右侧索引列失效、`LIKE` 模糊匹配以 `%` 开头引发全表扫描；
- **复杂查询重构**：大表 `JOIN` 优化（Nested-Loop Join 与 Block Nested-Loop 机理）、深分页优化（利用子查询覆盖索引推迟回表）、`ORDER BY` 与 `GROUP BY` 的文件排序（FileSort）消除技巧。

#### 数据库设计规范与范式化取舍（第 11 章）
- **六大范式系统梳理**：第一范式（1NF）、第二范式（2NF）、第三范式（3NF）、巴斯-科德范式（BCNF）、第四范式（4NF）与第五范式（5NF）；
- **反范式化（Denormalization）的艺术**：“巧妇难为无米之炊”，表结构设计缺陷无法仅凭 SQL 优化弥补。但在高并发电商读场景中，为了极致的响应速度，往往需要适度违反 3NF 故意引入冗余字段，用可控的存储冗余换取免 `JOIN` 的极致并发读性能；
- **ER 实体建模与大表治理**：系统掌握一对一、一对多与多对多的建表规范，探讨冷热数据分离、垂直拆分与水平分库分表的宏观策略。

### 篇章三：事务篇（并发控制与数据安全基石）

**事务篇**（涵盖第 12 至 15 章）是衡量一个开发者能否胜任金融、支付、交易等高可靠系统的试金石。

```text
       ┌─────────────────────────────────────────────────────────┐
       │                 ACID 事务特性与底层实现技术映射          │
       └────────────────────────────┬────────────────────────────┘
                                    │
    ┌──────────────────────┬────────┴─────────────┬──────────────────────┐
    ▼                      ▼                      ▼                      ▼
 【原子性 (A)】          【持久性 (D)】         【隔离性 (I)】          【一致性 (C)】
  Undo Log (回滚日志)     Redo Log (重做日志)    锁机制 (Locking)       ACID 协同运作
  操作失败反向撤销        WAL 机制防掉电断电     MVCC (多版本快照读)    保证业务状态自洽
```
*读图说明：事务四大属性并非抽象的概念口号，底层由 Undo Log、Redo Log、锁机制与 MVCC 分别提供物理实现支撑。*

#### 事务基础与隔离级别（第 12 章）
- **ACID 原则**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）的严谨工程内涵；
- **并发异常场景**：脏读（Dirty Read）、不可重复读（Non-Repeatable Read）与幻读（Phantom Read）的时序复现；
- **四大隔离级别**：读未提交（Read Uncommitted）、读已提交（Read Committed）、可重复读（Repeatable Read，MySQL 默认级别）与可串行化（Serializable）。

#### 核心事务日志系统（第 13 章）
- **Redo Log（重做日志）**：剖析 WAL（Write-Ahead Logging）预写日志机制。阐明内存脏页与磁盘顺序写入（Sequential I/O）的协同，彻底揭开“即使服务器突然断电，未刷盘的事务数据依然能 100% 自动恢复（Crash-Safe）”的底层奥秘；
- **Undo Log（回滚日志）**：深入记录行的回滚指针与撤销链，解析事务回滚（Rollback）时如何执行逻辑反向操作保证原子性。

#### 锁机制全景透视（第 14 章）
从多维度系统梳理 MySQL 极其庞杂的锁体系：
- **粒度维度**：全局锁、表级锁（表锁、元数据锁 MDL、意向排他锁 IX、意向共享锁 IS）、行级锁；
- **机制维度**：记录锁（Record Lock）、间隙锁（Gap Lock，用于在 RR 隔离级别下解决幻读问题）、临键锁（Next-Key Lock）；
- **死锁（Deadlock）攻防**：死锁产生的原因、并发死锁检测机制与线上死锁排查方法论。

#### 多版本并发控制（MVCC 原理，第 15 章）
- **Multi-Version Concurrency Control**：解决“读-写并发冲突”的终极法宝；
- **快照读与当前读**：深入剖析 `SELECT` 快照读与 `FOR UPDATE` 当前读的区别；
- **底层双引擎**：彻底揭示每一行隐藏的 `trx_id`（事务 ID）与 `roll_pointer`（回滚指针），结合事务启动时刻生成的 **Read View（一致性读视图）**四大规则，手算推导数据版本链的可见性裁决过程。

### 篇章四：日志与备份篇（企业级高可用与运维实战）

最后一篇为**日志与备份篇**（涵盖第 16 至 19 章），直击生产架构的高可用保障。

#### 通用日志全解析与 Binlog vs Redo Log 核心辨析（第 16 章）
- **MySQL 六大日志**：错误日志（Error Log）、通用查询日志（General Query Log）、慢查询日志、二进制日志（Binlog）、中继日志（Relay Log）与 DDL 日志；
- **必考高频题：Binlog 与 Redo Log 的本质区别**：
  1. **层级不同**：Binlog 属于服务层原生支持的所有引擎通用日志；Redo Log 是 InnoDB 存储引擎层私有的特有物理日志；
  2. **内容不同**：Binlog 是逻辑日志（记录具体的 DML/DDL 变更语句）；Redo Log 是物理日志（记录的是“对某数据页做了什么物理修改”）；
  3. **刷盘与生命周期不同**：Binlog 采用追加写，历史数据永久归档用于备份和主从同步；Redo Log 大小固定，采用环形循环覆盖写；
  4. **两阶段提交（2PC）**：深入探讨两阶段提交（Prepare 与 Commit）如何保证 Binlog 与 Redo Log 在崩溃恢复时的数据强一致。

#### 主从复制原理与高可用架构（第 17-18 章）
- **主从复制底层流转**：从库 I/O 线程读取主库 Binlog 写入本地中继日志（Relay Log），从库 SQL 线程重放中继日志完成数据同步；
- **读写分离与中间件边界**：探讨在高并发读场景下搭建一主多从架构的意义，并说明生产中配合分布式数据库中间件（如 Mycat 等）的工业协作方案。

#### 数据备份、闪回与灾难恢复（第 19 章）
掌握全量逻辑备份（`mysqldump` 工具实战）、物理备份以及基于 Binlog 增量日志的“时间点精确恢复（Point-in-Time Recovery）”方案，构筑生产数据资产的最后一道安全底线。

### 双版本对比环境规划与虚拟机克隆原理

为了在讲解中兼顾当前工业界的存量应用与未来的技术演进，我们采取“以 8.0 为主、兼顾 5.7”的双版本对照教学策略：
- **MySQL 8.0**：官方长期支持与未来发展的主力版本，引入了大量架构级的重构与性能优化；
- **MySQL 5.7**：当前各企业生产环境中存量占比极高的经典稳定版本。

在学习过程中，我们绝不能将 MySQL 8.0 与 MySQL 5.7 安装在同一台虚拟机中。如果强行安装在同一台机器上，不仅会面临 3306 默认端口冲突，还会导致服务管理脚本（mysqld）、全局配置文件（`/etc/my.cnf`）、默认数据目录（`/var/lib/mysql`）以及动态链接库的混杂污染，极大增加环境调试的复杂度。因此，我们规划两台完全干净、相互隔离的 CentOS 7 虚拟服务器节点：
- **CentOS 7-5 节点**：IP 地址规划为 `192.168.1.150`，主机名为 `atguigu05`，专门用于安装部署 MySQL 8.0；
- **CentOS 7-6 节点**：IP 地址规划为 `192.168.1.160`，主机名为 `atguigu06`，专门用于安装部署 MySQL 5.7。

```text
+-----------------------------------------------------------------------------------+
|                           Windows 物理宿主机 (开发与管理终端)                       |
|   管理工具: Xshell (SSH 终端) | Xftp (SFTP 文件传输) | SQLyog (图形化数据库管理客户端)    |
+------------------------------------------+----------------------------------------+
                                           |
             VMware Workstation 虚拟局域网 (NAT 模式虚拟交换机 VMnet8)
                                           |
             +-----------------------------+-----------------------------+
             |                                                           |
             v                                                           v
+-----------------------------+                             +-----------------------------+
|   CentOS 7-5 虚拟节点        |                             |   CentOS 7-6 虚拟节点        |
|   IP 地址: 192.168.1.150    |                             |   IP 地址: 192.168.1.160    |
|   主机名称: atguigu05        |                             |   主机名称: atguigu06        |
|   目标软件: MySQL 8.0       |                             |   目标软件: MySQL 5.7       |
|   部署目录: /opt            |                             |   部署目录: /opt            |
+-----------------------------+                             +-----------------------------+
```
> **架构说明**：物理宿主机通过虚拟交换机分别与两台独立的 CentOS 虚拟机进行网络通信。两台虚拟节点各自拥有独立的物理磁盘文件、MAC 地址、IP 地址与主机名，互不干扰。

#### 完整克隆与链接克隆的底层机制对比

在已有母机 CentOS 7-5 的前提下，最高效的环境搭建方式是借助虚拟化平台的克隆技术复制出一台全新的 CentOS 7-6，而非重新经历漫长的新系统安装过程。在 VMware Workstation 的克隆向导中，提供了两种克隆模式：

| 对比维度 | 创建链接克隆（Linked Clone） | 创建完整克隆（Full Clone） |
| :--- | :--- | :--- |
| **磁盘物理文件** | 仅生成指向母机快照的差异磁盘（Delta VMDK） | 将母机虚拟磁盘（VMDK）进行完整、独立的物理拷贝 |
| **创建耗时与容量** | 耗时极短（秒级完成），占用极小磁盘容量 | 耗时取决于磁盘 I/O 速度，占用一份完整的物理磁盘空间 |
| **与母机的耦合性** | 强依赖母机：母机若被删除、移动路径或受损，子机立刻瘫痪 | 彻底解耦：克隆完成后完全独立运行，母机任何变更均不影响子机 |
| **生产适用性** | 适合快速临时测试，严禁用于高负载、配置修改频繁的系统 | **数据库服务器与集群节点搭建的标准选择** |

> **结论**：用于支撑数据库服务器这类高 I/O 负载、需要独立修改底层内核与网络配置的虚拟机，**必须严格选择“创建完整克隆”**，绝不能为了节省磁盘空间而使用链接克隆。

#### VMware Workstation 完整克隆标准化操作

执行完整克隆的标准操作规程如下：
1. **确认母机处于完全关机状态**：在 VMware 左侧虚拟机清单中，确认母机 `CentOS 7-5` 处于关机（Power Off）状态。如果虚拟机正在运行或处于挂起状态，克隆功能将受限或无法创建冷克隆镜像；
2. **启动克隆向导**：右键点击 `CentOS 7-5` -> 点击【管理（Manage）】-> 点击【克隆（Clone）】；
3. **选择克隆源**：向导第一步提示选择克隆源，保持默认选中的“虚拟机中的当前状态（The current state in the virtual machine）”；
4. **选择克隆类型**：在克隆类型选项中，明确勾选【创建完整克隆（Create a full clone）】，点击下一步；
5. **指定虚拟机标识与物理磁盘路径**：
   - 虚拟机名称命名为 `CentOS 7-6`；
   - 存储位置指定到磁盘空间充裕的独立文件夹（例如 `D:\Virtual Machines\CentOS 7-6`），建议存放在固态硬盘（SSD）分区中，以保证并发读写与快照效率；
6. **执行文件克隆**：点击【完成（Finish）】。VMware 开始全量复制母机的物理文件，待进度条执行至 100% 后关闭向导。此时在库列表中即出现独立的 `CentOS 7-6` 实例。

### 克隆虚拟机的四大网络与系统标识重构

完整克隆实质上是整盘物理数据的字节级复刻。克隆产生的新虚拟机完整继承了母机的网络物理地址（MAC 地址）、主机名（Hostname）、全局唯一标识（UUID）以及静态 IP 地址。

如果未经任何修改就将母机与克隆机同时通电启动，它们将以完全相同的物理和网络特征出现在同一个局域网中，立刻引发 MAC 地址冲突、网络广播风暴以及 IP 抢占断流。为了确保网络拓扑正常，必须在开机前后按严格的流水线顺序重构这四处标识：

```text
克隆虚拟机标识重构流水线：
┌────────────────────────────────────────────────────────┐
│ 步骤 1: 物理层 MAC 地址重构 (关机状态下在 VMware 硬件面板重新生成) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 步骤 2: 开机登录 -> 系统层主机名重构 (修改 /etc/hostname 并 reboot) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 步骤 3 & 4: 网络层 IP 与 UUID 重构 (编辑 ifcfg-ens33 配置文件) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 步骤 5: 服务层生效 (执行 systemctl restart network 重启网络) │
└────────────────────────────────────────────────────────┘
```

#### 物理层 MAC 地址物理重构（开机前必做）

MAC 地址是数据链路层网卡的唯一物理硬件标识。克隆机的 MAC 地址与母机完全重复，必须在开机前强制刷新：
1. 打开 VMware，在左侧选中新克隆出的 `CentOS 7-6`（保持关机）；
2. 点击【编辑虚拟机设置】，选中【网络适配器】；
3. 点击右下角【高级（Advanced）】按钮；
4. 在弹出的高级设置窗口中，找到 MAC 地址配置栏，点击右侧的【生成（Generate）】按钮。系统会在 VMware 分配的组织唯一标识（OUI）网段内随机分配一个全新的 MAC 地址；
5. 点击两次以确认数值已刷新，随后点击【确定】保存。

> **易错点：动态 IP（DHCP）与静态 IP（Static）的开机避坑规则**：
> - **若采用 DHCP 动态分配**：在启动克隆机 7-6 之前，**必须先将母机 7-5 开机并锁定原有 IP 租约**！如果母机处于关机状态，局域网内的 DHCP 服务器在接收到 7-6 的租约请求时，极大概率会将此前分配给 7-5 的 IP 分配给 7-6；等稍后母机 7-5 开机时，发现原有 IP 被占用，只能分配到一个全新的未知 IP，导致之前保存的所有远程终端会话全线失效；
> - **若采用静态绑定（Static）**：由于 IP 地址硬编码在系统配置文件中，不存在租约争抢问题，可以任意顺序开机。我们强烈推荐使用静态 IP。

#### 系统主机名（Hostname）重构与重启生效

完成 MAC 地址生成后，启动虚拟机 `CentOS 7-6`。引导完成后使用系统超级管理员 `root` 账户登录，初始密码为母机原设定的 `abc123`。

此时桌面右键打开终端，命令行提示符依然显示为 `[root@atguigu05 ~]#`。
为什么我们必须立即修改主机名？
在当前的单点教学环境下，主机名似乎只是终端上的一个显示标签；但在后续章节中，我们将深入讲解 MySQL 主从复制（Replication）与读写分离集群（MyCat 中间件部署）。届时多台虚拟机协同工作，各个节点的角色分工极其严密。如果所有节点的主机名混同为 `atguigu05`，排查 binlog 日志流动、查看主从同步心跳与节点状态时极难区分哪台是 Master、哪台是 Slave。

在 CentOS 7 中，修改主机名的标准规范是修改 `/etc/hostname` 配置文件：
```bash
vim /etc/hostname
```
1. 终端执行上述命令进入 Vim 编辑器；
2. 此时处于 Vim 命令模式，按下键盘字母 `i` 键，终端左下角显示 `-- INSERT --`，进入插入编辑模式；
3. 将原有的 `atguigu05` 删除，修改为当前节点专属的主机名 `atguigu06`（或者 `atguigu160`）；
4. 按键盘 `Esc` 键退出插入模式，进入命令模式；
5. 键入 `:wq`（代表写入并退出），敲击回车执行保存。

修改完成后，当前正在运行的 Shell 会话上下文不会自动更新主机名环境变量，必须通过重启系统使其生效：
```bash
reboot
```
虚拟机重启后，重新使用 `root` 登录并打开终端，提示符已正式变更为 `[root@atguigu06 ~]#`。

> **提示**：多台虚拟机会消耗宿主机大量物理内存。若宿主机物理内存有限（如 8G 或 16G），日常实验中建议根据需要只保留当前操作的虚拟机处于运行状态，未使用的虚拟机及时挂起或关机。

#### 网卡静态 IP 与设备 UUID 重构

主机名重构完成后，进入网卡配置重构环节。我们需要修改系统网络脚本，为克隆体分配固定的 `192.168.1.160` 静态地址，并修改设备 UUID，防止网络管理器（NetworkManager）将其与母机网卡识别为同一硬件。

CentOS 7 默认的以太网卡配置文件存放在 `/etc/sysconfig/network-scripts/` 目录下，网卡文件一般命名为 `ifcfg-ens33`。在终端中执行编辑命令：
```bash
vim /etc/sysconfig/network-scripts/ifcfg-ens33
```

打开该文件后，会看到类似如下的核心参数内容：
```bash
TYPE="Ethernet"
PROXY_METHOD="none"
BROWSER_ONLY="no"
BOOTPROTO="static"
DEFROUTE="yes"
IPV4_FAILURE_FATAL="no"
IPV6INIT="yes"
NAME="ens33"
UUID="8f63b015-728b-4a55-89f5-9b24479e51c8"
DEVICE="ens33"
ONBOOT="yes"
IPADDR="192.168.1.160"
NETMASK="255.255.255.0"
GATEWAY="192.168.1.1"
DNS1="114.114.114.114"
DNS2="8.8.8.8"
```

针对克隆节点，按 `i` 进入插入模式，重点修改以下两处：
1. **修改 UUID**：UUID（Universally Unique Identifier）代表网卡设备在系统内的全局唯一识别码。克隆后该值与母机一致，为了防止网络服务异常，将该字符串末尾的几位字符进行随机修改（例如将末尾的 `51c8` 修改为 `51c9`）；
2. **修改 IPADDR**：将继承自母机的 `192.168.1.150` 修改为规划好的目标静态 IP `192.168.1.160`；
3. **核查基础参数**：
   - `BOOTPROTO="static"`：协议必须为静态配置；
   - `ONBOOT="yes"`：开机必须自动加载该网卡；
   - `GATEWAY` 与 `DNS`：必须与宿主机虚拟交换机（VMnet8 NAT 模式）的网关设置保持一致。

修改完毕后，按 `Esc` 键退出插入模式，输入 `:wq` 保存并退出。

#### 重启网络子系统与联通性验证

配置文件保存后，内存中正在运行的网卡驱动并不会立即识别，必须通过 `systemctl` 重启网络系统服务：
```bash
systemctl restart network
```

重启完成后，执行以下指令检查网卡分配的真实 IP 并验证网络通信：
```bash
ip addr show ens33
ping -c 3 www.baidu.com
```
若 `ens33` 端口正确绑定了 `inet 192.168.1.160/24`，且对外网发送的 3 个 ICMP 包实现 0% 丢包率，则证明克隆虚拟机的底层网络与标识重构全面成功。

#### Linux 软件目录规范与安装包远程投递

在推送安装包前，我们必须了解 Linux 系统中标准的文件系统层次结构规范（FHS）：
- `/bin` 与 `/sbin`：存放基本用户命令和系统管理命令的二进制程序；
- `/etc`：存放主机特定的系统级配置文件（如网络配置、MySQL 主配置文件 `/etc/my.cnf`）；
- `/var`：存放动态变化的数据，例如日志文件 `/var/log` 与 MySQL 数据库的实际数据文件 `/var/lib/mysql`；
- `/usr/local`：主要用于存放用户手动源码编译的第三方软件；
- `/opt`：**大型商业软件、第三方可选应用程序与离线安装包的标准存放目录**。

我们严格遵循该规范，将所有待安装的 RPM 离线包统一放置在 `/opt` 目录下。

在 Windows 本地解压好官方压缩包后，我们会获得抽出的关键 RPM 文件（下一讲将专门剖析这些 RPM 文件的来源与角色分工）：

## 98-MySQL的卸载
> 对应分集：P98 | 原始标题：《98-MySQL的卸载》

在学习如何在 Linux 环境下安装 MySQL 之前，我们有必要先掌握如何将一个现存的 MySQL 数据库彻底卸载干净。很多同学可能会产生疑问：为什么不直接讲解安装，反而先演示卸载？

我们在讲解 MySQL 基础篇（上篇）时，在 Windows 环境下也是采取“先讲卸载、后讲安装”的逻辑——“先看它是怎么没的，再看它是怎么来的”。在实际的研发、测试与日常学习中，很多同学在初次安装 MySQL 时，经常因为漏装依赖、安装顺序颠倒、密码初始化错误或者版本选型不当而导致安装中途夭折。此时如果不懂得如何彻底卸载，直接在残破的环境上重复执行安装，残留的底层配置文件、历史数据目录、动态链接库和 RPM 包缓存会引发层出不穷的依赖冲突与服务启动失败。

因此，把卸载掌握清楚，不仅能帮助我们在环境搞崩时拥有“秒级重置、从头再来”的兜底能力，更是深刻理解 MySQL 在 Linux 文件系统中各个组件分布规律的绝佳契机。

```bash
mysqladmin --version
# 或者直接执行
mysql --version
```
如果控制台正确输出了类似 `mysqladmin  Ver 8.0.25 for Linux on x86_64 (MySQL Community Server - GPL)` 的信息，说明当前系统内部确实存在一套正在生效的 MySQL 环境。

#### 检索系统已安装的 RPM 软件包

Linux 下通过包管理器部署的软件都会在系统底层数据库中留下元数据索引。我们通过 `rpm`（Red-Hat Package Manager）命令配合管道符与正则表达式，检索当前机器中所有与 MySQL 相关的安装包：
```bash
rpm -qa | grep -i mysql
```
参数含义解析：
- `-q`（query）：执行软件包查询操作；
- `-a`（all）：查询系统当前已安装的所有软件包；
- `|`（管道符）：将前面命令的查询输出作为后方命令的输入流；
- `grep -i`（ignore-case）：忽略大小写匹配关键字 `mysql`。

在典型的 MySQL 8.0 规范安装环境下，终端通常会输出 5 个核心 RPM 软件包：
```text
mysql-community-server-8.0.25-1.el7.x86_64
mysql-community-client-8.0.25-1.el7.x86_64
mysql-community-libs-8.0.25-1.el7.x86_64
mysql-community-common-8.0.25-1.el7.x86_64
mysql-community-client-plugins-8.0.25-1.el7.x86_64
```
这 5 个包各自代表服务端、客户端命令行、共享库、公共元数据与客户端插件，构成了 MySQL 运行时的软件实体。

#### 检查 MySQL 后台守护进程运行状态

在对软件执行删除动作前，必须明确其后台服务是否处于活动状态。CentOS 7 采用 `systemd` 初始化系统，服务管理的核心指令为 `systemctl`（CentOS 6 及以下版本则使用 `service` 命令）：
```bash
systemctl status mysqld
```

> **易错点：服务命名与守护进程后缀**：
> - 在 Windows 环境下，MySQL 的服务名通常被命名为 `MySQL`、`MySQL80` 或 `MySQL57`；
> - 在 Linux 环境下，系统服务默认命名为 **`mysqld`**。末尾的字母 **`d`** 代表 Daemon（守护进程），即在后台默默监听 3306 端口并处理网络请求的核心后台进程。命令末尾的 `.service` 后缀可以省略；

### 彻底卸载与残留清理四大核心阶段

很多初学者卸载软件往往只做“删除程序”这一步，以为执行了一条 remove 命令就万事大吉。然而，对于数据库这类复杂的基础软件，只卸载二进制程序往往会导致重装时灾难性的失败。一套完备的卸载必须覆盖以下四大阶段：

```text
MySQL 彻底卸载四步闭环模型：
┌────────────────────────────────────────────────────────────┐
│ 第一阶段: 停止后台守护进程 (systemctl stop mysqld)         │
└─────────────────────────────┬──────────────────────────────┘
                              │
                              ▼
┌────────────────────────────────────────────────────────────┐
│ 第二阶段: 卸载 RPM 安装程序包 (yum remove 级联清理)         │
└─────────────────────────────┬──────────────────────────────┘
                              │
                              ▼
┌────────────────────────────────────────────────────────────┐
│ 第三阶段: 递归抹除数据目录与依赖库 (rm -rf /var/lib/mysql ...)│
└─────────────────────────────┬──────────────────────────────┘
                              │
                              ▼
┌────────────────────────────────────────────────────────────┐
│ 第四阶段: 彻底清除主配置文件 (rm -rf /etc/my.cnf)           │
└────────────────────────────────────────────────────────────┘
```

#### 第一阶段：安全关闭 MySQL 后台服务

**严禁在数据库服务正在运行的情况下强行卸载程序包或直接删除数据目录！**
若服务处于活动状态，内存中的脏页（Dirty Pages）尚未刷盘，表空间文件被操作系统内核加锁占用。此时强行删除会导致数据损坏、文件句柄泄漏，甚至使操作系统出现不可杀死的 D 状态（不可中断睡眠）僵尸进程。

执行安全关闭指令：
```bash
systemctl stop mysqld
```
关闭后再次检查服务状态：
```bash
systemctl status mysqld
```
确认控制台输出显示为 `Active: inactive (dead)`，证明后台守护进程已完全退出，所有网络连接与文件句柄均已安全释放。

#### 第二阶段：级联卸载 RPM 程序包

在 Linux 中，卸载 RPM 包可以使用原生的 `rpm -e`，也可以使用上层的包管理器 `yum remove`。
为什么我们强烈推荐使用 `yum remove`？
因为 MySQL 的多个组件之间存在严密的上下游依赖关系（例如服务端 server 强依赖 client，client 依赖 libs，libs 依赖 common）。如果直接使用 `rpm -e`，一旦卸载顺序颠倒，系统会立刻抛出 `error: Failed dependencies` 依赖错误阻断执行。而 `yum remove` 具备自动依赖解析树，能够自动计算出当前组件所牵涉的上下游关联包，并给出级联清理方案。

我们可以从依赖层级最顶端的服务端包开始卸载：
```bash
yum remove mysql-community-server
```
执行后，Yum 会自动检索依赖关系，并在控制台列出计划一并卸载的关联包，终端提示 `Is this ok [y/N]:`，输入字母 `y` 并按回车确认。

卸载完成后，再次调用 `rpm` 检查系统剩余包：
```bash
rpm -qa | grep -i mysql
```
此时会发现先前的 5 个包已经被自动级联移除了 3 个，可能还残留有公共库或底层插件包（如 `mysql-community-common`、`mysql-community-libs`）。继续使用 `yum remove` 对剩余项执行清理：
```bash
yum remove mysql-community-common
# 提示输入 y 确认
```
若仍有剩余包（如单个插件包或独立的 client 包），再次执行：
```bash
yum remove mysql-community-client-plugins
# 提示输入 y 确认
```
在整个卸载过程中，不断反复执行 `rpm -qa | grep -i mysql`，直到该命令执行后控制台**没有任何回显输出**为止。至此，MySQL 的软件包实体才算被完全从系统的 RPM 数据库中剔除。

#### 第三阶段：深度查找并清除数据目录与运行时残留

这是整个卸载过程中最容易被忽视、却最关键的一步！
包管理器的卸载逻辑仅仅是删除了 `/usr/bin` 下的可执行程序和 `/usr/share` 下的手册，**出于数据安全策略考虑，包管理器绝不会自动删除用户的数据库数据文件！**
如果你不手动清理这些文件，重装后 MySQL 会直接挂载历史残留的系统表空间（`ibdata1`）和事务日志，极大概率导致数据字典不一致、root 初始密码失效或服务无法启动。

我们使用 Linux 的全局查找命令 `find` 检索全盘根目录下的残留项：
```bash
find / -name mysql
```
系统会遍历整个文件系统，通常会搜索出以下三类典型路径：
1. `/var/lib/mysql`：MySQL 默认的核心数据存放目录（包含所有用户库、系统元数据表、InnoDB 共享表空间、redo/undo 日志及自增计数器等）；
2. `/var/lib/mysql/mysql`：系统权限元数据内部子目录；
3. `/usr/lib64/mysql`：64 位系统底层动态链接库和扩展支持目录。

使用强制递归删除命令对搜索出的目录进行彻底抹除：
```bash
rm -rf /var/lib/mysql
rm -rf /var/lib/mysql/mysql
rm -rf /usr/lib64/mysql
```
核心参数含义说明：
- `-r`（recursive，递归）：将目录以及该目录下所有的子目录、深层文件呈树状逐级递归删除；
- `-f`（force，强制）：即使文件是只读属性或者不存在，也强制删除，并且跳过所有的确认交互提示。

删除完成后，再次执行检索命令进行复查：
```bash
find / -name mysql
```
确认控制台没有任何相关目录输出，证明数据与依赖库文件已被彻底抹除。

#### 第四阶段：彻底清除全局配置文件 my.cnf

最后一步是清除 MySQL 服务器的全局运行参数配置文件。

> **对比辨析：Windows 与 Linux 下的配置文件**：
> - 在 Windows 环境下，MySQL 的主配置文件名为 **`my.ini`**，通常存放在安装目录根下或 `C:\ProgramData\MySQL\` 隐藏目录中；
> - 在 Linux 环境下，其核心配置文件统一命名为 **`my.cnf`**，存放在全局配置目录 `/etc/` 根下（完整路径为 `/etc/my.cnf`）。

该文件中配置了端口、字符集、默认存储引擎、缓冲区大小等关键参数。若不手动清除，重新安装时的新实例可能会读取老旧的错误参数配置，引发莫名其妙的启动报错。

执行删除指令：
```bash
rm -rf /etc/my.cnf
```
删除后通过精确查找验证：
```bash
find /etc -name my.cnf
```
若系统反馈未找到该文件，则证明整个系统的配置层也已被彻底净化。

### 运维小贴士与卸载自查矩阵

> 1. 在桌面顶部菜单栏点击【应用程序（Applications）】；
> 2. 选择【系统工具（System Tools）】-> 点击【设置（Settings）】；
> 3. 在硬件设置中找到【隐私（Privacy）】选项；

至此，原机器上的 MySQL 8.0.25 已被百分之百彻底清除。经过上述四阶段清理后的操作系统，其底层纯净度与一台从未安装过 MySQL 的崭新机器完全一致。此时**完全无需重启操作系统**，便可以直接平滑进入下一讲的全新版本安装。

最后，我们将整套彻底卸载的标准命令规约归纳为如下速查表：

| 阶段步骤 | 执行命令 | 操作目的与技术机理 |
| :--- | :--- | :--- |
| **步骤 1：停服务** | `systemctl stop mysqld` | 终止后台 Daemon 进程，释放端口、内存与文件句柄 |

### MySQL 官方发行体系与安装介质选型

访问 MySQL 官方网站（`mysql.com`），点击顶部导航栏中的【Downloads】进入下载主页。官方将 MySQL 体系划分为四大主要发行版本：

#### 官网 Linux 离线安装包检索与命名规则

进入【MySQL Community Server】下载页面后，需要针对我们的 Linux 宿主环境进行参数选型：
1. **Operating System（操作系统）**：下拉菜单中并没有直接提供“CentOS”的专属选项。因为 CentOS 是完全基于 Red Hat Enterprise Linux（RHEL）源码二次构建的开源发行版，底层二进制 ABI 完全兼容，因此操作系统必须选择 **Red Hat Enterprise Linux / Oracle Linux**；
2. **OS Version（系统大版本）**：我们使用的是 CentOS 7 操作系统，因此必须选择 **Red Hat Enterprise Linux 7 / Oracle Linux 7 (x86, 64-bit)**；
3. **硬件架构**：根据宿主机与虚拟机配置，选择标准的 **x86_64** 架构（若宿主环境为 ARM 芯片如 Apple Silicon 虚拟化平台，则选择对应的 ARM 架构）。

在版本下载列表中，官方提供了一个形如 `mysql-8.0.27-1.el7.x86_64.rpm-bundle.tar` 的聚合包（Bundle Tar）。该文件的命名结构具有严格的技术规范：

```text
mysql - 8.0.27 - 1 . el7 . x86_64 . rpm-bundle . tar
──┬──   ───┬──   ┬   ─┬─   ───┬──   ────┬─────   ─┬─
  │        │     │    │       │         │         └─ 最终打包格式为 Tar 归档
  │        │     │    │       │         └─ 集合包，内含多个独立 RPM 组件
  │        │     │    │       └─ 适用于 64 位 x86 架构处理器
  │        │     │    └─ 代表 Enterprise Linux 7 (CentOS 7) 系统内核
  │        │     └─ 当前版本发布修订次数 (第 1 次发行发布)
  │        └─ 软件版本号 (主版本 8，次版本 0，小版本 27)
  └─ 软件标识名称
```

#### 核心 RPM 安装包的“抽取”策略与功能划分

下载得到的 `.rpm-bundle.tar` 文件本质上是一个归档压缩包。解压该文件后，内部会释放出十几个不同的 RPM 软件包。在实际生产部署中，**绝无必要将所有解压出的 RPM 包全部上传并安装**！其中包含了嵌入式引擎库、开发测试套件、C++ 头文件等普通服务端运行时完全不需要的冗余文件。

我们需要从中“抽取”出真正驱动数据库服务端与核心客户端运行的 RPM 最小集合：

| 软件版本 | 抽取安装包名称 | 组件功能与技术职责 |
| :--- | :--- | :--- |
| **8.0 / 5.7 共同** | `mysql-community-common` | 数据库服务器与客户端共享的全局公共配置、字典编码与底层错误信息 |
| **8.0 独有** | `mysql-community-client-plugins` | 客户端连接所必需的认证、安全加密与通信插件包（8.0 新增必选） |
| **8.0 / 5.7 共同** | `mysql-community-libs` | MySQL 客户端共享的动态链接库（提供 libmysqlclient 运行时支持） |
| **8.0 / 5.7 共同** | `mysql-community-client` | 核心客户端命令行程序（提供 `mysql`、`mysqladmin`、`mysqldump` 等工具） |
| **8.0 / 5.7 共同** | `mysql-community-server` | 数据库核心服务端二进制守护进程（`mysqld`）及内置核心存储引擎 |

> **提示**：MySQL 8.0 需要抽取并安装上述 **5 个**核心包，而 MySQL 5.7 由于历史架构原因尚未剥离独立的客户端插件包，仅需抽取安装上述对应的 **4 个**核心包。

按照上一讲的标准流程，我们已通过 Xftp 将 8.0 的 5 个包传输至 `CentOS 7-5`（`192.168.1.150`）的 `/opt` 目录下，将 5.7 的 4 个包传输至 `CentOS 7-6`（`192.168.1.160`）的 `/opt` 目录下。

### 系统底层运行依赖与环境赋权

在正式执行 RPM 包安装前，必须确保 CentOS 7 的底层运行时库与临时目录权限达到 MySQL 的最低部署标准。

通过 Xshell 连接至目标服务器（以 150 节点为例），在控制台依次执行以下检查与赋权动作：

```bash
# 1. 为系统临时目录赋予完全控制权限
chmod -R 777 /tmp
```
**为什么必须为 `/tmp` 目录赋权 777？**
在后续执行数据库服务端安装与初始化的过程中，系统会自动创建一个无登录权限的受限系统账户 `mysql`。RPM 安装脚本在构建套件与动态 socket 管道时，会频繁以 `mysql` 账户的身份在 `/tmp` 目录下读写临时文件。如果 `/tmp` 权限过于收紧，安装脚本会抛出静默的 `Permission denied` 错误，导致服务初始化失败或套接字文件无法生成。

```bash
# 2. 检查异步 I/O 引擎库 (libaio)
rpm -qa | grep libaio

# 3. 检查基础网络工具集 (net-tools)
rpm -qa | grep net-tools
```
- **`libaio`（Linux Asynchronous I/O Library）**：MySQL 的核心存储引擎 InnoDB 重度依赖 Linux 内核提供的异步 I/O 接口进行脏页刷盘与日志追加。若缺少该库，`mysqld` 守护进程将无法初始化 AIO 线程池；
- **`net-tools`**：提供 `netstat`、`ifconfig`、`route` 等基础网络诊断命令，是排查 3306 端口监听与网络连接的必备工具。

若以上检索输出非空，则证明系统已具备安装基础。

### 在 CentOS 7-5 节点安装与配置 MySQL 8.0

切换至 `CentOS 7-5`（`192.168.1.150`）的 Xshell 会话，进入安装包所在的绝对路径：
```bash
cd /opt
```
**严禁在其他非安装包所在路径下执行本地安装指令**，否则 `rpm` 命令将无法定位目标文件。

#### 严格依赖安装顺序与 MariaDB 冲突解决

RPM 包之间存在严格的依赖链：服务端依赖客户端，客户端依赖共享库，共享库依赖通用字典。因此，安装命令必须严格按照以下递进顺序执行：

```text
RPM 安装依赖拓扑链:
common ──> client-plugins ──> libs ──> client ──> server
```

使用 `rpm -ivh` 命令（参数含义：`-i` 代表 install 安装；`-v` 代表 verbose 显示详细过程；`-h` 代表 hash 打印进度条哈希符 `#`）逐一执行：

```bash
# 步骤 1: 安装通用元数据组件
rpm -ivh mysql-community-common-8.0.25-1.el7.x86_64.rpm

# 步骤 2: 安装客户端插件集
rpm -ivh mysql-community-client-plugins-8.0.25-1.el7.x86_64.rpm
```

当执行到第 3 个包时：
```bash
# 步骤 3: 安装客户端共享库
rpm -ivh mysql-community-libs-8.0.25-1.el7.x86_64.rpm
```
此时终端极大概率会中断并抛出如下典型的依赖冲突报错：
```text
error: Failed dependencies:
    mariadb-libs is obsoleted by mysql-community-libs-8.0.25-1.el7.x86_64
```

> **技术背景与冲突根因**：
> 当 Sun 公司及后来的 Oracle 收购 MySQL 之后，MySQL 的原创核心团队担忧开源社区受到商业公司的收紧威胁，遂出走另起炉灶创建了完全开源的分支数据库 **MariaDB**。由于其开源属性，Red Hat 在发布 CentOS 7 时，将其默认基础软件源中的底层库替换为了 `mariadb-libs`。系统预装的 `mariadb-libs` 占用了 `libmysqlclient.so` 的软链接命名空间，与官方原厂的 `mysql-community-libs` 产生了互斥冲突。

**标准解决方案**：直接清除系统预置的 MariaDB 库。为了防止因级联依赖阻断删除，使用 `--nodeps` 参数强制解除依赖绑定后卸载：
```bash
rpm -e mariadb-libs --nodeps
```
卸载完成后，重新执行第 3 步的安装命令即可顺利通过。随后依次安装客户端与服务端组件：
```bash
# 重新安装 libs
rpm -ivh mysql-community-libs-8.0.25-1.el7.x86_64.rpm

# 步骤 4: 安装客户端命令行程序
rpm -ivh mysql-community-client-8.0.25-1.el7.x86_64.rpm

# 步骤 5: 安装核心服务端组件 (该文件体积最大，需等待哈希条全部输出)
rpm -ivh mysql-community-server-8.0.25-1.el7.x86_64.rpm
```

安装完成后，执行版本与安装包自检：
```bash
mysqladmin --version
rpm -qa | grep -i mysql
```
控制台回显清晰列出 5 个 RPM 包，代表二进制程序已成功写入系统路径。

#### 服务初始化与安全权限绑定

安装完成仅仅意味着二进制文件落盘，数据库的物理数据目录（`/var/lib/mysql`）目前仍处于未初始化状态。执行以下指令初始化系统库：
```bash
mysqld --initialize --user=mysql
```
**参数细节剖析**：
- `--initialize`：触发数据库物理目录构建。该过程会在 `/var/lib/mysql` 下创建默认的 `mysql`、`information_schema`、`performance_schema`、`sys` 系统数据字典表空间，生成默认 SSL 密钥证书，并生成一个经过高强度加盐哈希的 root 用户初始临时密码；
- `--user=mysql`：**极为关键的权限约束参数！** 它强制要求新生成的所有数据目录、文件及套接字的操作系统宿主用户和宿主用户组均为 `mysql:mysql`。如果以 root 身份执行而未指定 `--user=mysql`，底层文件属主将变为 root，随后的守护进程将因权限不足崩溃。

#### 检索临时密码与服务状态生命周期管控

服务初始化完成后，系统将初始密码写入了 mysqld 运行日志中。通过 `grep` 过滤日志提取初始密码：
```bash
cat /var/log/mysqld.log | grep "temporary password"
```
终端会输出类似如下的信息：
```text
2026-09-14T10:35:12.123456Z 6 [Note] [MY-010454] [Server] A temporary password is generated for root@localhost: h.p(k9wPq?wL
```
末尾那串包含字母、数字和怪异标点符号的字符串（如 `h.p(k9wPq?wL`）即为 root 的初始临时密码。使用鼠标精准选中并复制备用。

接下来启动后台守护进程并配置开机自启：
```bash
# 启动后台守护进程
systemctl start mysqld

# 查看服务运行状态
systemctl status mysqld
```
看到高亮的绿色 `active (running)` 即代表服务端已正常拉起并在 3306 端口监听。

为了避免每次重启虚拟机后都要手动输入命令启动 MySQL，需要将其注册为系统引导自启动服务：
```bash
# 检查当前是否为自启动状态
systemctl is-enabled mysqld

# 若显示 disabled，执行启用开机自启
systemctl enable mysqld
```

#### 首次安全登录与强制密码重置

在 150 节点控制台执行首次本地连接：
```bash
mysql -u root -p
```
按回车后提示 `Enter password:`，此时**在 Xshell 中使用快捷键 `Shift + Insert`** 粘贴刚才复制的 12 位复杂临时密码（出于安全机制，控制台不会回显任何星号或占位符），敲击回车进入 MySQL 交互式 Shell：
```text
Welcome to the MySQL monitor.  Commands end with ; or \g.
Your MySQL connection id is 8
Server version: 8.0.25 MySQL Community Server - GPL
...
mysql>
```

进入终端后，若迫不及待地执行一条查看数据库的指令：
```sql
SHOW DATABASES;
```
MySQL 会立刻返回阻断性错误：
```text
ERROR 1820 (HY000): You must reset your password using ALTER USER statement before executing this statement.
```

> **安全机制说明**：MySQL 在完成安全初始化后，强制要求 root 用户必须先显式修改密码，才能解锁所有的 SQL 查询与管理功能。

使用 `ALTER USER` 语句将本地 root 用户的密码修改为便于实验的 `abc123`：
```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY 'abc123';
```
控制台回显 `Query OK, 0 rows affected (0.01 sec)`。输入 `exit` 退出会话，使用新密码重新登录并验证：
```bash
mysql -u root -pabc123
```
重新登录后再次执行业务指令：
```sql
SHOW DATABASES;
```
终端打印出默认的 4 大系统数据库：
```text
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
4 rows in set (0.00 sec)
```
至此，CentOS 7-5 节点上的 MySQL 8.0 安装配置宣告圆满成功！

进入 160 节点的存放路径：

```
核查基础依赖并赋权：

```

#### 初始化、启动与重置 5.7 密码

安装成功后，执行初始化与启动流水线：
```bash
# 1. 初始化数据库目录
mysqld --initialize --user=mysql

# 2. 提取生成的随机临时密码
cat /var/log/mysqld.log | grep "temporary password"

# 3. 启动 5.7 服务并设置开机自启
systemctl start mysqld
systemctl status mysqld
systemctl enable mysqld
```

复制日志末尾输出的临时密码，发起终端登录：
```bash
mysql -u root -p
# 粘贴临时密码后回车
```
登录后同样执行安全重置：
```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY 'abc123';
```
重置成功后执行 `SHOW DATABASES;`，同样能看到 4 个默认系统库。

至此，我们的两台测试虚拟机已分别就绪：`192.168.1.150` 稳定运行 MySQL 8.0，`192.168.1.160` 稳定运行 MySQL 5.7。环境底座坚实完整，为下一讲实现客户端远程连接铺平了道路。

### 远程连接故障复现与全链路排查拓扑

启动 Windows 本地的 SQLyog 客户端，新建一个会话连接，命名为 `192.168.1.150`。
填写连接参数：
- **MySQL 主机地址**：`192.168.1.150`（CentOS 7-5 虚拟节点）；
- **用户名**：`root`；
- **密码**：`abc123`；
- **端口**：`3306`。

点击【测试连接】按钮。此时界面陷入长时间的无响应卡顿状态，鼠标指针呈现等待状态。稍等片刻后，SQLyog 最终弹出一个经典的阻断性错误对话框：
```text
Error No. 2003: Can't connect to MySQL server on '192.168.1.150' (10060)
```

很多初学者遇到该报错时往往手足无措，甚至盲目去重装系统或数据库。实际上，从宿主机客户端向虚拟机数据库发起 TCP 握手，涉及操作系统、虚拟网络、防火墙规则、数据库进程及访问控制策略等多层结构。我们可以遵循标准网络排查模型进行逐层定位：

```text
远程数据库连接全链路排查模型：
[第一层: 物理与链路层]  Ping 检测 (网络是否通畅、路由是否可达)
        │
        ▼  通畅
[第二层: 传输与防火墙]  Telnet 3306 (宿主机与虚拟机防火墙是否拦截)
        │
        ▼  放行
[第三层: 数据库访问权限] 检查 mysql.user 表 (root 是否仅绑定 localhost)
        │
        ▼  放开 host=%
[第四层: 认证算法兼容性] 解决 8.0 独有的 caching_sha2_password 插件不兼容
```

### 远程连接四层故障排查与深度修复实操

#### 第一层：链路层与网络互通性排查（Ping 诊断）

首先排除物理网络与虚拟交换机链路故障。在 Windows 宿主机上按下 `Win + R` 键，输入 `cmd` 打开命令提示符，执行对目标虚拟机的连通性探测：
```cmd
ping 192.168.1.150
```
控制台正常接收到了 4 次来自 `192.168.1.150` 的 ICMP 应答（Reply），丢包率为 0%。这证明虚拟机处于开机运行状态，且 Windows 宿主机与虚拟机之间的虚拟网络拓扑（VMnet8）是完全通畅的。

#### 第二层：传输层端口与系统防火墙排查（Telnet 诊断）

网络通畅但数据库拒绝握手，大概率是传输层 3306 端口未对外开放，或者数据包被系统的防火墙策略拦截。
在 Windows 命令行中使用 `telnet` 命令探测目标端口：
```cmd
telnet 192.168.1.150 3306
```

> **提示：Windows 下开启 Telnet 客户端工具**：
> 若在 Windows 命令提示符中执行时系统提示 `'telnet' 不是内部或外部命令`，说明当前宿主机尚未激活 Telnet 客户端组件。
> **激活方式**：打开 Windows【控制面板】-> 点击【程序和功能】-> 点击左侧【启用或关闭 Windows 功能】-> 在弹出的功能列表中勾选【Telnet Client（Telnet 客户端）】-> 点击确定并等待系统安装完毕即可。

执行 Telnet 探测后，控制台在等待数秒后直接报错退出：`无法打开到主机的连接。在端口 3306: 连接失败`。这直接证明 3306 端口无法完成三次握手，流量遭到了防火墙拦截。

针对此问题，通常有两种解决思路：
1. **针对性放行端口**：在防火墙中针对 3306/tcp 端口添加允许入站规则；
2. **彻底关闭防火墙**：在本地开发、教学与测试环境中，为了彻底杜绝后续多节点集群通信（如 MyCat、Redis、主从心跳）的端口干扰，**最推荐的方式是直接关闭并彻底禁用系统的防火墙服务**。

通过 Xshell 登录 `192.168.1.150` 节点，执行防火墙生命周期管控：
```bash
# 1. 检查防火墙当前运行状态
systemctl status firewalld
```
控制台显示 `Active: active (running)`，证明系统默认的防火墙守护进程正在强力过滤外部连接。

```bash
# 2. 立即关闭当前运行的防火墙服务
systemctl stop firewalld

# 3. 再次核查确认状态已变为 dead
systemctl status firewalld

# 4. 彻底禁用防火墙开机自启动
systemctl disable firewalld
```

> **注意：Windows 宿主机本地防火墙核查**：
> 除了 Linux 虚拟机的防火墙之外，Windows 操作系统在经历系统补丁更新后，有时也会自动重置并开启本地的高级安全 Windows Defender 防火墙，阻断局域网内的回环流量。如果在关闭 Linux 防火墙后依然无法通信，务必在 Windows 控制面板中同步核查本地防火墙规则。

#### 第三层：应用层账户主机访问权限排查（mysql.user 表修改）

关闭虚拟机防火墙后，再次在 Windows 中执行 `telnet 192.168.1.150 3306`，此时控制台瞬间黑屏并输出 MySQL 握手版本字符串，证明 3306 端口物理通路已彻底打通！

此时满怀期待地回到 SQLyog 重新点击【测试连接】，却依然抛出了新的连接阻断报错：
```text
Host '192.168.1.100' is not allowed to connect to this MySQL server
```

**故障机理剖析**：
MySQL 拥有自身独立的权限验证模型，其核心账户信息存放在系统库 `mysql` 的 `user` 表中。在 MySQL 默认的安全策略中，初次初始化生成的 `root` 超级管理员账户，其绑定的允许登录主机被死死限制为 **`localhost`**！这意味着 root 账户被严格限制仅能从服务器本地（通过 UNIX Domain Socket 或本机回环地址 127.0.0.1）登录，严禁任何来自外部 IP 的网络连接。

通过 Xshell 在 150 节点登录 MySQL 控制台，查看账户底层元数据：
```sql
mysql -u root -pabc123
```
```sql
USE mysql;
SELECT host, user FROM user;
```
终端输出如下：
```text
+-----------+------------------+
| host      | user             |
+-----------+------------------+
| localhost | root             |
| localhost | mysql.infoschema |
| localhost | mysql.session    |
| localhost | mysql.sys        |
+-----------+------------------+
4 rows in set (0.00 sec)
```
可以看到，`root` 账户的 `host` 列确实为 `localhost`。

我们必须通过数据操作语言（DML）将 root 绑定的 host 拓宽：
```sql
UPDATE user SET host = '%' WHERE user = 'root';
```

> **易错点：企业生产环境中的通配符使用禁忌**：
> 在本课程的教学实验环境中，为了使宿主机不同网段的客户端均能便捷访问，我们将 `host` 设置为了百分号 **`%`**（在 SQL 模式匹配中代表任意客户端 IP）。
> **但是在真实的生产环境与商业系统运维中，绝不允许将 root 的 host 设为 `%` 并暴露在公网！** 生产规范要求必须严格指定具体的受信任内网 IP，或者绑定特定的子网掩码（例如限制为应用服务器所在的网段 `192.168.1.%`），将攻击面收敛至最小。

修改完成后，再次查询验证：
```sql
SELECT host, user FROM user WHERE user = 'root';
```
此时 `host` 已变为 `%`。**紧接着必须立即执行权限刷新指令**：
```sql
FLUSH PRIVILEGES;
```
> **技术说明**：MySQL 服务器为了追求极致的访问性能，会在启动时将 `mysql.user` 表的内容全部载入内存的授权缓存区中。直接执行 `UPDATE` 修改底层表结构，并不会自动触发内存字典的重载。必须执行 `FLUSH PRIVILEGES` 强令服务器重新清空并重载授权表缓存，修改才能对正在运行的服务端生效！

#### 第四层：MySQL 8.0 独有的安全认证插件冲突与降级方案

完成权限刷新后，再次切换回 SQLyog 点击【测试连接】。此时并没有像预想中那样直接连接成功，而是弹出了另一个具有时代特征的错误窗口：
```text
Plugin caching_sha2_password could not be loaded: 找不到指定的模块。
```

```text
MySQL 5.7 与 8.0 认证加密算法重大演变：
┌────────────────────────────────────────┐
│ MySQL 5.7: mysql_native_password       │
│ - 算法: 基于 SHA-1 进行双重哈希验证    │
│ - 特点: 历史悠久，全生态客户端与驱动完美适配│
└────────────────────────────────────────┘
                    │
                    ▼ 官方架构安全升级
┌────────────────────────────────────────┐
│ MySQL 8.0: caching_sha2_password       │
│ - 算法: 基于 SHA-256 进行密码哈希运算  │
│ - 特点: 加密强度极大提升，支持内存缓存提升握手效率 │
│ - 代价: 老旧图形客户端 (如旧版 SQLyog) 驱动缺少该解密库 │
└────────────────────────────────────────┘
```

**根因剖析**：
这是由 MySQL 8.0 的架构安全升级引发的客户端兼容性问题。在 MySQL 5.7 及以前版本中，默认采用的是 `mysql_native_password` 插件（基于 SHA-1 哈希算法）。而从 MySQL 8.0 开始，为了防范哈希碰撞与彩虹表攻击，官方将默认的认证插件全面替换为更为安全的 **`caching_sha2_password`**。
许多经典的客户端管理软件（包括老版本 SQLyog、早期 Navicat 以及部分老旧的 JDBC 驱动包）内部尚未内置解析 `caching_sha2_password` 的动态链接库，因此在握手解密密码时直接抛出插件无法加载的异常。

**标准解决方案**：
通过 `ALTER USER` 语法，显式将目标用户的认证加密插件降级回全生态通用的 `mysql_native_password`：
```sql
ALTER USER 'root'@'%' IDENTIFIED WITH mysql_native_password BY 'abc123';
FLUSH PRIVILEGES;
```

执行成功后，回到 SQLyog 中再次点击【测试连接】。控制台瞬间弹出激动人心的提示：
```text
连接成功！
```
点击【确定】并保存会话设置，成功在 SQLyog 左侧对象树中看到了远程 CentOS 7-5 上的 MySQL 8.0 实例，默认的 4 大系统数据库一览无余！

### 扩展认知：MySQL 8.0 密码强度评估机制（了解）

在学习了上述内容后，有的同学会产生一个新的疑问：
我们在刚刚安装完成 MySQL 8.0 时，日志里生成的初始密码极其复杂怪异（包含大小写、数字、特殊符号）；随后我们使用 `ALTER USER` 将其重置为了极其简单的 `abc123`，整个过程顺畅无阻。
为什么有的同学在某些生产或云端 MySQL 8.0 环境中修改密码时，系统会疯狂报错，甚至提示 `Your password does not satisfy the current policy requirements` 拒绝执行？

这涉及到 MySQL 8.0 引入的一项重要的企业级安全加固机制——**密码强度评估组件（`validate_password`）**。

> **提示**：本小节内容定位为“了解”。旨在让大家知晓底层运行机理，在企业生产环境中遇到密码策略报错时不慌张，**日常个人实验无需强制配置**。

#### 密码强度校验组件的启用机制

在纯原生的最小化安装中，`validate_password` 模块默认并未强行启用。要想激活该模块的强制审计，有两种标准途径：
1. **配置文件永久生效**：在 `/etc/my.cnf` 的 `[mysqld]` 标签下追加密码策略配置参数，随后重启服务；
2. **终端动态安装插件**：在 MySQL 命令行会话中直接执行插件安装命令：
   ```sql
   INSTALL PLUGIN validate_password SONAME 'validate_password.so';
   ```

当插件安装成功并激活后，如果再次尝试将密码修改为诸如 `abcd1234` 这样缺乏特殊字符或全小写的简单密码：
```sql
ALTER USER 'root'@'%' IDENTIFIED BY 'abcd1234';
```
MySQL 会立刻阻断该语句，并抛出严格的错误响应：
```text
ERROR 1819 (HY000): Your password does not satisfy the current policy requirements
```

#### 密码校验核心策略与系统变量解析

激活组件后，我们可以通过系统变量查看当前的密码审计规则：
```sql
SHOW VARIABLES LIKE 'validate_password%';
```
控制台会输出一系列核心控制参数，其中最具决定性的是以下两项：

| 系统参数项 | 默认取值 | 技术含义与校验规则 |
| :--- | :--- | :--- |
| **`validate_password.policy`** | `MEDIUM`（1） | 密码安全策略等级（支持 `LOW`/0、`MEDIUM`/1、`STRONG`/2） |
| **`validate_password.length`** | `8` | 允许设定的最小密码长度（字符数必须 $\ge 8$） |
| **`validate_password.mixed_case_count`** | `1` | 密码中必须包含的大写与小写字母的最少数量 |
| **`validate_password.number_count`** | `1` | 密码中必须包含的阿拉伯数字的最少数量 |
| **`validate_password.special_char_count`**| `1` | 密码中必须包含的非字母数字特殊字符（如 `_`、`@`、`#`）的最少数量 |

策略等级矩阵：
- **LOW（0）**：仅校验密码的最小长度（必须满足 `length` 参数规定）；
- **MEDIUM（1，默认）**：在长度满足的前提下，**必须同时混用大写字母、小写字母、数字以及特殊符号**；
- **STRONG（2）**：在 MEDIUM 的严苛基础上，还会加载一个内置字典文件，如果密码包含字典中常见的单词或字典子串，直接判定违规拒绝录入。

#### 密码强度评估函数与策略动态调整

如果我们在设置密码前想提前得知其安全分值，可以使用系统内置的评估函数：
```sql
SELECT VALIDATE_PASSWORD_STRENGTH('Atguigu_2026_Root');
```
该函数会返回一个 `0 ~ 100` 之间的整数。若返回 `100`，说明该密码在长度、多样性及复杂度上均达到最高标准。

在开发、测试或内网实验环境下，若大家觉得高强度的密码录入繁琐，可以通过动态调整全局系统变量的方式，降低校验严苛度：
```sql
-- 将策略等级降至最低 (仅限制长度)
SET GLOBAL validate_password.policy = LOW;

-- 将最小长度限制调低 (例如设为 4 或 6)
SET GLOBAL validate_password.length = 4;
```
完成上述调整后，再次将密码修改为简单的 `abc123` 即可顺利通过校验。若后续彻底不再需要该校验功能，亦可在命令行中将其直接注销：
```sql
UNINSTALL PLUGIN validate_password;
```

通过这一层面的剖析，我们既搞清了 MySQL 8.0 密码安全的底线逻辑，又掌握了生产与研发场景下的灵活应对法则。至此，全套 Linux 双版本环境搭建与网络连接全线贯通！

## 101-字符集的修改与底层原理说明
> 对应分集：P101 | 原始标题：《101-字符集的修改与底层原理说明》

在前面搭建 MySQL 环境时，我们分别安装了 MySQL 5.7 与 MySQL 8.0。如果你在 5.7 的默认环境下直接建库、建表，并且插入包含中文的数据，几乎百分之百会迎头撞上一条报错：`ERROR 1366 (HY000): Incorrect string value`，甚至出现中文乱码；但换到 8.0 环境下执行完全相同的 SQL 语句，中文却能丝滑存入。

出现这种截然不同现象的根源，就在于版本间默认字符集的演进。5.7 默认的字符集是 `latin1`，而 8.0 默认将其升级为了通用的 `utf8mb4`。字符集不是孤立存在的配置项，它在 MySQL 内部有一套自上而下、极其严密的四层继承与覆盖机制。如果搞不清其底层的生效逻辑，在生产环境中盲目修改配置文件或执行转换命令，极易引发旧数据的不可逆损坏或乱码灾难。

---

### MySQL 5.7 与 8.0 默认字符集行为对比

在 Linux 测试环境中，我们准备了两台虚拟机节点：`150` 节点安装了 MySQL 8.0，`160` 节点安装了 MySQL 5.7。通过对比相同建表与插入操作在两个版本下的不同表现，能够直观看到字符集的约束行为。

#### 查看全局字符集系统变量

通过 `SHOW VARIABLES` 指令，我们可以查看当前 MySQL 实例运行时加载的各项字符集参数：

```sql
SHOW VARIABLES LIKE 'character%';
```

在 MySQL 8.0（`150` 节点）中执行该语句，控制台输出的关键变量如下：

| 变量名 (`Variable_name`) | 8.0 默认值 (`Value`) | 5.7 默认值 (`Value`) | 作用简析 |
| :--- | :--- | :--- | :--- |
| `character_set_server` | `utf8mb4` | `latin1` | 服务器默认字符集 |
| `character_set_database` | `utf8mb4` | `latin1` | 默认创建或当前选中数据库的字符集 |
| `character_set_client` | `utf8mb4` | `utf8` | 客户端来源数据的编码字符集 |
| `character_set_connection` | `utf8mb4` | `utf8` | 接收并处理请求时所用的连接字符集 |
| `character_set_results` | `utf8mb4` | `utf8` | 返回给客户端的查询结果字符集 |
| `character_set_system` | `utf8` | `utf8` | 存储元数据（如表名、字段名）的系统字符集 |

在创建具体的数据库和数据表时，起决定性默认值作用的核心变量是 `character_set_server` 与 `character_set_database`。在 8.0 中它们默认是支持 4 字节全量 Unicode 字符（包含 Emoji）的 `utf8mb4`；而在 5.7 中，它们默认是仅支持单字节西欧语言的 `latin1`。

#### 环境下的隐式字符集写入验证

在 8.0 节点下，我们不显式指定任何字符集与比较规则，直接创建数据库并建表插入数据：

```sql
-- 创建数据库（不显式声明字符集）
CREATE DATABASE dbtest1;
USE dbtest1;

-- 创建数据表（不显式声明字符集）
CREATE TABLE emp1 (
    id INT,
    name VARCHAR(15)
);

-- 插入英文字符
INSERT INTO emp1(id, name) VALUES (1, 'Tom');

-- 插入中文字符
INSERT INTO emp1(id, name) VALUES (2, '康师傅');
```

执行后两条记录均成功写入。检查此时数据库与数据表的元数据定义：

```sql
SHOW CREATE DATABASE dbtest1;
SHOW CREATE TABLE emp1;
```

控制台返回信息明确显示：
- `dbtest1` 的字符集为 `DEFAULT CHARACTER SET utf8mb4`；
- `emp1` 表的字符集为 `DEFAULT CHARSET=utf8mb4`。

因为 `utf8mb4` 完整覆盖了 Unicode 编码空间，所以中文数据的插入与检索没有任何障碍。

#### 环境下的字符截断与报错复现

同样的操作，挪到未做任何配置修改的 MySQL 5.7 节点（`160`）上复现：

```sql
CREATE DATABASE dbtest1;
USE dbtest1;

CREATE TABLE emp1 (
    id INT,
    name VARCHAR(15)
);

-- 插入英文数据：成功
INSERT INTO emp1(id, name) VALUES (1, 'Tom');

-- 插入中文数据：失败并报错
INSERT INTO emp1(id, name) VALUES (2, '康师傅');
```

执行插入英文时一切正常，因为几乎所有现代单字节与多字节字符集都向下兼容标准的 7 位 ASCII 码（0~127）；但当尝试插入 `'康师傅'` 时，客户端直接抛出致命错误，数据无法落盘。

检查 5.7 当前表与库的真实定义：

```sql
SHOW CREATE DATABASE dbtest1;
-- 输出: CREATE DATABASE `dbtest1` /*!40100 DEFAULT CHARACTER SET latin1 */

SHOW CREATE TABLE emp1;
-- 输出: ENGINE=InnoDB DEFAULT CHARSET=latin1
```

由于 `latin1` 仅占用单字节（0x00~0xFF），其内部编码表根本不存在汉字的码点映射。当底层引擎尝试将 UTF-8 编码的中文三字节序列塞入 `latin1` 字段时，因无法匹配有效字符而直接阻断写入。

### Linux 环境下 MySQL 5.7 字符集的持久化修改

在企业实际交付与生产运维中，如果依然使用 MySQL 5.7，在安装完成后的第一道必做工序就是纠正全局字符集配置。

#### 修改配置文件 my.cnf

在 Windows 环境下，MySQL 的主配置文件通常是安装目录或数据目录下的 `my.ini`；而在 Linux（如 CentOS / RedHat）环境下，主配置文件为 `/etc/my.cnf`。

通过 vim 打开该配置文件：

```bash
vim /etc/my.cnf
```

在配置文件的 `[mysqld]` 标签段内，追加指定服务器级别的默认字符集参数：

```ini
[mysqld]
# 设置服务端默认字符集为 UTF-8
character_set_server=utf8
```

按 `Esc` 键退出编辑模式，输入 `:wq` 保存并退出。

> **提示**：在 MySQL 5.7 中，`character_set_server=utf8` 实际映射为 `utf8mb3`（最大 3 字节编码）。生产环境中若需支持移动端 Emoji 表情，建议直接显式配置为 `character_set_server=utf8mb4`。

#### 重启服务与参数验证

修改配置文件属于静态变更，不会直接作用于当前正在运行的 mysqld 守护进程。必须通过 systemd 重启服务：

```bash
systemctl restart mysqld
```

重启完成后，重新通过客户端连接登录 MySQL 实例并检查全局字符集变量：

```sql
SHOW VARIABLES LIKE 'character%';
```

此时可以观察到：
- `character_set_server` 已成功变更为 `utf8`；
- `character_set_database` 紧随其后变更为 `utf8`。

### 配置生效边界：新建对象与历史对象的字符集割裂

修改并重启配置后，很多初学者最容易犯的一个严重错误，是误以为“全库的所有表都自动变成 UTF-8 了”。

> **结论**：在 `my.cnf` 中修改 `character_set_server`，其作用域**仅仅影响在此之后全新创建的数据库和表**；对**已经存在**的历史库、历史表，没有任何溯及既往的追溯修改作用！

#### 历史库与表的隔离验证

重新检查我们在修改配置前创建的 `dbtest1` 与 `emp1`：

```sql
USE dbtest1;
SHOW CREATE DATABASE dbtest1; -- 依然显示 DEFAULT CHARACTER SET latin1
SHOW CREATE TABLE emp1;       -- 依然显示 DEFAULT CHARSET=latin1
```

此时若再次在 `dbtest1.emp1` 表中执行中文字符插入：

```sql
INSERT INTO emp1(id, name) VALUES (2, '康师傅');
```

系统依然会毫不留情地抛出字符集错误。

#### 全新对象的继承行为

我们在修改配置生效后，新建数据库 `dbtest2`，并不显式指定字符集：

```sql
CREATE DATABASE dbtest2;
SHOW CREATE DATABASE dbtest2;
-- 输出: DEFAULT CHARACTER SET utf8
```

随后在 `dbtest2` 下新建数据表 `emp1` 并插入中文：

```sql
USE dbtest2;

CREATE TABLE emp1 (
    id INT,
    name VARCHAR(15)
);

SHOW CREATE TABLE emp1;
-- 输出: DEFAULT CHARSET=utf8

INSERT INTO emp1(id, name) VALUES (2, '康师傅');
SELECT * FROM emp1;
```

此时中文字符正常插入并检索成功。

#### 跨库创建新表的继承陷阱

这里存在一个极高频的混淆点：如果我们在旧数据库 `dbtest1`（`latin1`）下，新建一张全新的表 `emp2`，此时全局变量明明已经是 `utf8`，这张新表的字符集究竟是 `utf8` 还是 `latin1`？

```sql
USE dbtest1;

CREATE TABLE emp2 (
    id INT,
    name VARCHAR(15)
);

SHOW CREATE TABLE emp2;
-- 输出: DEFAULT CHARSET=latin1
```

> **易错点**：建表时若未显式指定字符集，它不会越级去找全局的 `character_set_server`，而是严格继承其所属数据库（`dbtest1`）的字符集！因为 `dbtest1` 是历史遗留的 `latin1` 库，所以其下新建的任何表依然默认是 `latin1`。

### 历史库与表的字符集原地变更实践

对于在生产环境中已经以旧字符集建立的数据库与数据表，必须通过 DDL（数据定义语言）语句进行显式修改。

#### 修改已有数据库的默认字符集

针对已有数据库，使用 `ALTER DATABASE` 语句：

```sql
ALTER DATABASE dbtest1 CHARACTER SET utf8;
```

执行后查看数据库状态：

```sql
SHOW CREATE DATABASE dbtest1;
-- 输出: DEFAULT CHARACTER SET utf8
```

此时，`dbtest1` 的元数据定义已被更正为 `utf8`。后续在该库下新创建的表，将自动继承这一新的字符集。

#### 修改已有数据表及其历史数据

仅修改数据库字符集，并不会级联更新库中已经存在的表。必须对具体的表执行 `ALTER TABLE` 操作：

```sql
USE dbtest1;

-- 彻底转换数据表字符集及现有列中所有文本数据的编码
ALTER TABLE emp1 CONVERT TO CHARACTER SET utf8;
```

执行后验证表结构：

```sql
SHOW CREATE TABLE emp1;
-- 输出: DEFAULT CHARSET=utf8
```

转换完成后，再次向 `dbtest1.emp1` 插入中文测试数据：

```sql
INSERT INTO emp1(id, name) VALUES (2, '康师傅');
SELECT * FROM emp1;
```

查询结果显示中英文记录共存且解析无误，验证成功。

```text
+------+-----------+
| id   | name      |
+------+-----------+
|    1 | Tom       |
|    2 | 康师傅    |
+------+-----------+
```
*图 1：成功转换字符集后的数据表查询输出*

#### 语法区别：CONVERT TO 与普通 CHARACTER SET

在修改表字符集时，SQL 提供了两种常见写法，二者的底层执行语义完全不同：

1. `ALTER TABLE t1 CONVERT TO CHARACTER SET utf8;`
   - **全面转换**：不仅修改表级别的默认元数据定义，还会将表中现存所有字符类型字段（`CHAR`、`VARCHAR`、`TEXT` 等）的列字符集批量更新为 `utf8`，同时将底层存储的现有二进制字节流原地做重新编码转储。
2. `ALTER TABLE t1 CHARACTER SET utf8;`
   - **浅层修改**：仅修改表元数据中的“默认字符集”属性。已经存在的物理字段其字符集保持原样不变，已有数据亦不做重新编码，仅对后续 `ALTER TABLE t1 ADD COLUMN` 未指明字符集的新增列生效。

> **注意**：在做字符集转换时，必须确保源字符集能够被目标字符集安全兼容（例如从单字节的 `latin1` 提升到多字节的 `utf8`）。这是“小集合向大集合”的扩容包含，原有 ASCII 字节序列能够无损转换为 UTF-8 序列；若从大字符集盲目强转为小字符集，或在两个不兼容的多字节编码（如从 `GBK` 强行非对称转为某种小语种编码）之间硬转，极易导致底层字节码点无法映射，造成不可恢复的乱码。

### MySQL 字符集四级继承体系与底层原理

在梳理完修改流程后，我们需要站在底层架构视角，彻底拆解 MySQL 字符集的层级模型。在 MySQL 体系中，字符集拥有从粗到细、粒度极其精准的四级控制体系：

```text
+-------------------------------------------------------------+
| 1. 服务器级别 (Server Level: character_set_server)          |
+-------------------------------------------------------------+
                              | (当建库未指明字符集时向下继承)
                              v
+-------------------------------------------------------------+
| 2. 数据库级别 (Database Level: character_set_database)      |
+-------------------------------------------------------------+
                              | (当建表未指明字符集时向下继承)
                              v
+-------------------------------------------------------------+
| 3. 表级别 (Table Level: DEFAULT CHARSET)                    |
+-------------------------------------------------------------+
                              | (当建字段未指明字符集时向下继承)
                              v
+-------------------------------------------------------------+
| 4. 列/字段级别 (Column Level: VARCHAR(...) CHARACTER SET)   |
+-------------------------------------------------------------+
```
*图 2：MySQL 字符集四级自上而下的继承与覆盖关系*

#### 四级粒度的继承与层级推导链

这一继承链条的运作规则可以归纳为四句话：
1. **服务器级别**：由配置文件中的 `character_set_server` 决定，是整个 MySQL 实例的顶层兜底基准。
2. **数据库级别**：如果在执行 `CREATE DATABASE` 时没有显式写出 `CHARACTER SET`，数据库自动继承当前服务端的 `character_set_server`。
3. **表级别**：如果在执行 `CREATE TABLE` 时没有显式写出 `CHARACTER SET`，数据表自动继承其所属数据库的字符集。
4. **列级别**：在定义字符类型的列（如 `VARCHAR(15)`）时，如果没有单独指明 `CHARACTER SET`，该字段自动继承数据表的默认字符集。

这就解释了为什么我们在 5.7 中仅仅在 `my.cnf` 中修改了服务端级别参数，重启后新建数据库、新建表、新建列，中文插入便一路通畅——因为整条继承链路从根部被疏通了。

#### 各层级的显式声明与覆盖语法

MySQL 的灵活性在于：虽然存在层层继承，但在每一个层级，开发者都拥有完全覆盖上一级的权力。

##### 1) 数据库级别的显式声明
```sql
CREATE DATABASE my_custom_db
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_general_ci;
```

##### 2) 表级别的显式声明
即使所属数据库使用的是 `latin1`，我们也可以在建表时将其单独指定为 `utf8mb4`：
```sql
CREATE TABLE my_custom_table (
    id INT,
    name VARCHAR(15)
) DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

##### 3) 列/字段级别的显式声明
粒度可以细化到具体的某一个字符串字段。在同一个表中，允许不同字段拥有不同的字符集：
```sql
CREATE TABLE multilingual_table (
    id INT,
    en_desc VARCHAR(50) CHARACTER SET latin1,
    cn_desc VARCHAR(50) CHARACTER SET utf8mb4
) DEFAULT CHARSET=utf8mb4;
```
在上表中，`en_desc` 字段被严格限定为只能存储 `latin1` 范围内的字符，而 `cn_desc` 字段则使用 `utf8mb4`。

### 生产环境开发规约与统一性准则

虽然 MySQL 允许在数据库、数据表甚至单独列上随心所欲地混用不同字符集，但在工程实践中，绝对不要滥用这种高级灵活性。

> **结论**：生产环境中务必保持**端到端全链路字符集统一**。前端展示层、应用服务端（如 Java Web 服务连接池与代码编译）、数据库服务端（`server`、`database`、`table`、`column`）必须统一采用 UTF-8（8.0 推荐 `utf8mb4`）。

如果在数据库内部出现一张表用 `latin1`、另一张表用 `utf8`，或者列级别存在异构字符集，当应用发起跨表关联查询（`JOIN`）或跨服务数据传输时，MySQL 不得不在查询执行期间频繁进行内部编码转码（Transcoding）。这不仅极度浪费 CPU 计算资源，还可能导致基于索引的等值查询因字符集或排序规则不匹配而导致**索引失效**，引发慢查询与全表扫描；一旦字符映射存在偏差，更会直接产生不可挽回的乱码数据。

在 MySQL 8.0 中，直接依赖其默认的 `utf8mb4` 即可；而在 MySQL 5.7 中，安装后的第一步必须修改 `my.cnf` 将 `character_set_server` 设为 `utf8` 或 `utf8mb4`，在后续的业务建表 DDL 中尽量不要画蛇添足地混用异构字符集。

## 102-比较规则_请求到响应过程中的编码与解码过程
> 对应分集：P102 | 原始标题：《102-比较规则_请求到响应过程中的编码与解码过程》

在上一次梳理中，我们解决了字符集在服务器、数据库、数据表与字段层面的继承与覆盖机制。但在实际排查乱码和检索异常时，经常会遇到两类更深层次的困惑：其一，明明数据库和表的字符集都设成了 UTF-8，为什么有时大小写查询不敏感、有时却敏感？中文汉字是按拼音排还是按笔画排？其二，在很多公司的测试环境中，数据库明明存的是 UTF-8，终端客户端也是 UTF-8，但中间为什么会出现 `character_set_client`、`character_set_connection` 和 `character_set_results` 这三个绕来绕去的系统变量？数据从客户端发出去到最后呈现在屏幕上，底层究竟经历了几次转码？

本篇我们重点拆解字符集背后的比较规则（Collation），以及 SQL 请求从客户端发送、服务端处理到响应返回的全生命周期编解码链条。

---

### 字符集与比较规则的内在关联

字符集负责“怎么存”，即字符与二进制字节之间的映射关系；而比较规则（Collation，也称校对规则）负责“怎么比”，即字符串在排序（`ORDER BY`）、比较大小（`>`、`<`）以及等值匹配（`=`、`LIKE`）时遵循的准则。

#### utf8 与 utf8mb4 的本质区别

在 MySQL 5.7 中，我们经常直接写 `utf8`，而在 8.0 中默认则全面采用 `utf8mb4`。这两个概念在 MySQL 内部有明确的界限：

标准的 Unicode UTF-8 编码是一种变长编码规范，单个字符占用 1 至 4 个字节：
- 单字节（1 Byte）：兼容 ASCII 码，存储英文数字（如 `'a'`、`'1'`）；
- 双字节（2 Bytes）：欧洲部分拉丁语系、希腊文、阿拉伯文等；
- 三字节（3 Bytes）：常用汉字（如 `'我'`）、日文、韩文等基础多语言平面（BMP）字符；
- 四字节（4 Bytes）：辅助平面字符，典型代表如 Emoji 表情符号（`😀`、`🚀`）以及极少数生僻字。

```text
+-------------------+--------------------+------------------------+
| 编码类型          | 最大字节数(Maxlen) | 适用场景与限制         |
+-------------------+--------------------+------------------------+
| utf8 / utf8mb3    | 3 字节 (0~3 Bytes) | 覆盖绝大多数中英文字符 |
|                   |                    | 无法存储 4 字节 Emoji  |
+-------------------+--------------------+------------------------+
| utf8mb4           | 4 字节 (0~4 Bytes) | 完整 Unicode 字符集   |
|                   |                    | 完美支持移动端 Emoji   |
+-------------------+--------------------+------------------------+
```
*图 1：utf8(utf8mb3) 与 utf8mb4 的编码宽度对比*

> **提示**：MySQL 早期实现的 `utf8` 实际上是阉割版的 `utf8mb3`（Max Bytes 3），只支持最多 3 字节编码。当移动互联网普及、移动端大量输入 Emoji 表情时，`utf8mb3` 就会抛出字符截断或非法字符异常。因此，MySQL 8.0 将默认字符集全面替换为真正的 `utf8mb4`。

#### 查看系统支持的字符集清单

在 MySQL 8.0 控制台中，可以通过以下指令查看当前实例支持的所有字符集、默认比较规则以及最大占用字节数：

```sql
SHOW CHARACTER SET;
```

控制台返回 41 行记录，核心字段含义如下：
- `Charset`：字符集名称（如 `utf8mb4`、`gbk`、`latin1`）；
- `Description`：字符集描述信息；
- `Default collation`：该字符集挂载的默认比较规则（每个字符集都有且仅有一个默认规则）；
- `Maxlen`：单个字符在该字符集下可能占用的最大字节数（例如 `gbk` 是 2，`utf8` 是 3，`utf8mb4` 是 4）。

### 比较规则的命名规范与行为差异

当执行如下查询或排序时，底层必然依赖比较规则：

```sql
SELECT * FROM emp WHERE name = 'Tom';
SELECT * FROM emp ORDER BY name ASC;
```

字符串 `'Tom'` 与 `'tom'` 算不算相等？在包含重音符号的西欧语言中，带有音标的字母如何排队？这全部由比较规则决定。

#### 比较规则后缀后缀命名规范

MySQL 中的比较规则命名具有极其严整的工业命名规范，一般格式为：`字符集名_语言或通用规范_比较行为后缀`。常见的后缀定义如下：

| 后缀 | 英文全称 | 核心含义 | 技术特征 |
| :--- | :--- | :--- | :--- |
| `_ai` | Accent Insensitive | 不区分重音 | 忽略重音字符差异（如 `e` 与 `é` 视为相同） |
| `_as` | Accent Sensitive | 区分重音 | 严格区分重音字符 |
| `_ci` | Case Insensitive | 不区分大小写 | 字符串比较与匹配时 `'A'` 与 `'a'` 视为相等 |
| `_cs` | Case Sensitive | 区分大小写 | 严格区分大小写，`'A'` 与 `'a'` 视为不等 |
| `_bin` | Binary | 二进制比对 | 逐字节甚至逐比特比对 ASCII/Unicode 码点，天然区分大小写 |

例如：
- `gbk_chinese_ci`：针对 GBK 字符集的中文不区分大小写比较规则；
- `gbk_bin`：针对 GBK 字符集的二进制精确比对规则；
- `utf8mb4_0900_ai_ci`：MySQL 8.0 默认比较规则，基于 Unicode 9.0 规范，不区分重音、不区分大小写。

#### 检索指定字符集的比较规则

通过 `SHOW COLLATION` 指令可以筛选特定字符集下的可用比较规则：

```sql
-- 查看 GBK 字符集下的比较规则
SHOW COLLATION LIKE 'gbk%';

-- 查看 UTF-8 相关的比较规则
SHOW COLLATION LIKE 'utf8%';
```

在 UTF-8 族系中，除了 MySQL 8.0 新增的 `0900` 系列外，最常用的两套经典规则是 `utf8mb4_general_ci` 与 `utf8mb4_unicode_ci`。

> **结论**：
> - `general_ci`：校对算法相对简单，比对与排序执行速度极快，但在某些特定西欧小语种的复杂排序上准确度稍逊一筹。对绝大多数中英文混合业务而言，几乎感觉不到准确度差异，性能表现优异。
> - `unicode_ci`：完全遵从 Unicode 标准排序算法，能够精准处理各种多语言混合、特殊符号排序，准确度极高，但在复杂字符集比对时计算开销略大。

日常中英文开发通常直接使用 `utf8mb4_general_ci` 或 8.0 默认的 `utf8mb4_0900_ai_ci` 即可。

#### 查看与变更数据库及表的比较规则

比较规则与字符集是一一绑定的。在各层级中，字符集决定上限，比较规则决定比对策略。

##### 1) 查看服务器与数据库当前比较规则
```sql
SHOW VARIABLES LIKE 'collation_server';
SHOW VARIABLES LIKE 'collation_database';
```

##### 2) 修改数据库的默认比较规则
```sql
ALTER DATABASE dbtest1 
    DEFAULT CHARACTER SET utf8mb4 
    COLLATE utf8mb4_general_ci;
```

##### 3) 查看表的比较规则
```sql
USE dbtest1;
-- 方式一：查看建表元数据
SHOW CREATE TABLE emp1;

-- 方式二：查看表状态详情中的 Collation 字段
SHOW TABLE STATUS FROM dbtest1 LIKE 'emp1';
```

##### 4) 显式变更数据表的字符集与比较规则
```sql
ALTER TABLE emp1 
    CONVERT TO CHARACTER SET utf8mb4 
    COLLATE utf8mb4_general_ci;
```

> **注意**：修改数据库的默认比较规则，同样**不影响**已经存在的历史表，只对之后新建的表产生继承影响；如果需要同步调整现有历史表，必须使用 `ALTER TABLE ... CONVERT TO` 语句。

### 请求到响应全链路的编解码全流程

在前面的字符集变量列表中，除了服务端的 `character_set_server` 与 `character_set_database`，还有三个高频变量直接掌管网络通信链路：
- `character_set_client`：服务器假定客户端发送过来的 SQL 语句所采用的字符集；
- `character_set_connection`：服务器在接收到请求后、在执行 SQL 前，将请求文本转换为该连接字符集进行语法解析与处理；
- `character_set_results`：服务器执行完毕后，将数据结果集与错误信息编码为该字符集再回传给客户端。

在 MySQL 5.7 和 8.0 中，这三个参数默认通常均保持与 UTF-8 一致。为了把这三者的协作机理彻底剖析清楚，我们通过一个极具代表性的跨编码处理案例来走一遍底层流转。

#### 编解码流转拓扑架构

假设客户端向 MySQL 发起一条包含汉字 `'我'` 的等值查询请求：

```text
[客户端 (Client)] 
       |
       | 1. 客户端使用自身编码将 SQL 转化为二进制字节流发送 (例如 UTF-8: 0xE6 0x88 0x91)
       v
+-------------------------------------------------------------------+
| MySQL 服务端连接层                                                |
|                                                                   |
| 2. character_set_client 解码:                                     |
|    将接收到的二进制序列按 client 字符集解码还原为逻辑字符 '我'     |
|                                                                   |
| 3. character_set_connection 转码:                                 |
|    将逻辑字符 '我' 转换为 connection 字符集编码 (例如 GBK: 0xCED2) |
+-------------------------------------------------------------------+
       |
       | 4. 执行引擎检索 (与存储层交互)
       v
+-------------------------------------------------------------------+
| 存储引擎与物理表 (Storage Engine / Table / Column)                |
|    匹配列字段 (其自身定义为 GBK: 0xCED2)                           |
|    比对二进制码点匹配成功，提取目标数据行                         |
+-------------------------------------------------------------------+
       |
       | 5. 查询结果集返回给连接层
       v
+-------------------------------------------------------------------+
| MySQL 服务端响应层                                                |
|                                                                   |
| 6. character_set_results 编码:                                    |
|    将结果字符 '我' 按 results 字符集重新编码 (例如 UTF-8: 0xE6 0x88 0x91) |
+-------------------------------------------------------------------+
       |
       | 7. 网络回传二进制结果字节流
       v
[客户端终端 / 展现层]
       8. 客户端使用本地展示字符集解码字节流并在控制台呈现 '我'
```
*图 2：MySQL 请求接收、连接处理、查询匹配与响应回传全链路编解码流转*

#### 全链路八步流转详解与转码推导

我们以汉字 `'我'` 为例，详细对比它在 UTF-8 和 GBK 下的不同二进制表现：
- `'我'` 在 UTF-8 字符集中占用 3 个字节：十六进制序列为 `0xE6 0x88 0x91`；
- `'我'` 在 GBK 字符集中占用 2 个字节：十六进制序列为 `0xCED2`。

假设我们有意将服务端的参数配置为混合状态：
- `character_set_client = utf8`
- `character_set_connection = gbk`
- 表中的目标字段 `col` 字符集为 `gbk`
- `character_set_results = utf8`

##### 第一步：客户端请求生成与发送
客户端运行在基于 UTF-8 的环境（如 Web 页面或 UTF-8 配置的终端），用户输入 SQL：
```sql
SELECT * FROM my_table WHERE col = '我';
```
客户端将此字符串以 UTF-8 编码转化为字节流，其中 `'我'` 对应为 `0xE6 0x88 0x91`，通过 TCP 报文发送给服务端。

##### 第二步：服务端按照 character_set_client 解码
MySQL 连接接收线程截获字节流。此时服务端必须得知这串字节是以什么规则编码的。它依赖 `character_set_client` 的设定。
- 因为 `character_set_client=utf8`，服务端正确识别出 `0xE6 0x88 0x91` 代表中文字符 `'我'`。

> **易错点**：如果客户端实际发出来的是 UTF-8 的 3 字节，但服务端把 `character_set_client` 错误配成了 `gbk`，服务端就会以双字节为单位强行拼装（把前两个字节拼成一个乱码字符，第三个字节截断溢出）。请求在进入解析阶段就已经损坏，后续必然查不到数据或报语法错误！

##### 第三步：转换为 character_set_connection 编码
解码为逻辑字符 `'我'` 后，服务端并不急于直接去查表，而是将其转换为当前连接上下文的字符集——`character_set_connection`。
- 本例中 `character_set_connection=gbk`，服务端在内存中把 `'我'` 重新转换为 GBK 格式的字节流 `0xCED2`。

##### 第四步：存储引擎检索比对
服务端生成执行计划，与底层 InnoDB/MyISAM 存储引擎交互。表中的 `col` 字段定义正好也是 GBK。此时内部比对的是 GBK 编码序列 `0xCED2` 与物理行中存储的二进制字节。两者完全吻合，成功锁定目标行。

##### 第五步：将字段值提取为逻辑字符
引擎将检索到的字段原始字节（GBK 的 `0xCED2`）返回给 SQL 解析层，解析层根据该列的字符集定义（GBK）将其还原为通用字符 `'我'`。

##### 第六步：按照 character_set_results 编码
服务端准备向客户端回传响应包。回传之前，必须将数据转换为 `character_set_results` 指定的编码。
- 本例中 `character_set_results=utf8`，服务端将字符 `'我'` 再次编码为 UTF-8 格式的 `0xE6 0x88 0x91`。

##### 第七步与第八步：回传并在客户端展现
字节流 `0xE6 0x88 0x91` 通过网络返回给客户端。客户端以本地设置的 UTF-8 规则进行解码，屏幕上最终准确渲染出汉字 `'我'`。

### 全链路字符集匹配法则与运维实践

通过上述推导，我们可以清晰提炼出保证数据传输零乱码的“两对铁律”：

```text
+------------------------+      必须一致      +-------------------------+
|  客户端发送编码规范    | <================> |  character_set_client   |
+------------------------+                    +-------------------------+

+------------------------+      必须一致      +-------------------------+
| character_set_results  | <================> |  客户端接收展示编码规范 |
+------------------------+                    +-------------------------+
```
*图 3：防止网络传输出现乱码的核心匹配准则*

1. **请求入站一致性**：客户端发送实际采用的编码，必须与服务端 `character_set_client` 保持严格一致；
2. **响应出站一致性**：服务端 `character_set_results` 的编码，必须与客户端终端或展现层所使用的解码字符集保持严格一致；
3. **中间连接层容忍度**：`character_set_connection` 理论上可以与前后两者不同，只要其编码空间能够完整容纳待转换的字符集即可。但中途转码会消耗 CPU，且容易因为字符集包含范围不对称（如从 UTF-8 转为 Latin1）导致无法逆转的字符丢失。

#### 会话级快捷配置：SET NAMES 指令

如果每个连接都要逐个敲命令去修改 `client`、`connection` 和 `results`，运维与开发成本极高。MySQL 提供了简写宏命令 `SET NAMES`：

```sql
SET NAMES utf8mb4;
```

这一行 SQL 等效于并发执行以下三条赋值语句：

```sql
SET character_set_client = utf8mb4;
SET character_set_connection = utf8mb4;
SET character_set_results = utf8mb4;
```

在执行 `SET NAMES utf8mb4` 后，从请求进入、连接解析到结果响应，整条链路在服务端一气呵成、全部对齐为 `utf8mb4`。

#### 配置文件持久化：[client] 标签设置

为了避免每个新会话都要手工设置一次，可以在 Linux 系统的 `/etc/my.cnf`（或 Windows 下的 `my.ini`）中直接配置客户端通用段：

```ini
[client]
# 设置所有直连客户端工具的默认字符集
default-character-set=utf8mb4

[mysql]
# 针对 mysql 命令行工具的默认字符集
default-character-set=utf8mb4

[mysqld]
# 服务端默认字符集
character-set-server=utf8mb4
collation-server=utf8mb4_0900_ai_ci
```

在 `[client]` 标签下增加 `default-character-set=utf8mb4` 后，任何使用 MySQL 官方库（如命令行客户端、原生驱动）建立连接的程序，在握手阶段都会自动通知服务端将 `client`、`connection`、`results` 统一步齐为 `utf8mb4`，从源头彻底杜绝由终端字符集不匹配引发的传输乱码问题。

## 103-SQL大小写规范与sql_mode的设置
> 对应分集：P103 | 原始标题：《103-SQL大小写规范与sql_mode的设置》

在日常开发与跨平台部署中，许多开发者常遇到两类棘手问题：其一，本地在 Windows 环境下开发运行正常的 SQL 语句，部署到 Linux 生产环境后，忽然频繁报出 `Table doesn't exist` 错误；其二，测试环境中执行某些字段类型不符的插入或非严格的 `GROUP BY` 分组聚合查询能够顺利跑通，一到线上数据库却瞬间阻断并抛出异常。

这两类现象分别受控于 MySQL 的两个底层机制：**大小写敏感参数 `lower_case_table_names`** 与 **SQL 执行模式变量 `sql_mode`**。掌握这两个核心配置的底层原理、平台差异及生产规范，是保障数据库稳健运行的必备功底。

---

### 跨平台大小写敏感机制与底层参数

在编写 SQL 时，很多初学者常误以为“SQL 语言天然不区分大小写”。事实上，MySQL 是否区分大小写，与底层宿主操作系统的文件系统行为高度绑定，并且有着精细的对象边界。

#### 系统变量 lower_case_table_names 的取值含义

通过以下指令可以查询当前 MySQL 实例的大小写控制参数：

```sql
SHOW VARIABLES LIKE 'lower_case_table_names';
```

在 Windows 系统的 MySQL 8.0 实例中执行，该变量的默认返回值为 `1`；而在 Linux（CentOS/Ubuntu）系统下执行，默认返回值则是 `0`。

| 参数值 | 存储形式 | 比对查找规则 | 默认适用系统 | 核心特征 |
| :---: | :--- | :--- | :--- | :--- |
| `0` | 按 SQL 声明的原样大小写存储 | 大小写严格敏感（比对二进制字符） | Linux / Unix | 区分大小写，`Emp` 与 `emp` 视为两张不同的表 |
| `1` | 全部自动转换为小写存储到磁盘 | 大小写不敏感（统一转小写比对） | Windows | 不区分大小写，输入大写也会转为小写处理 |
| `2` | 按 SQL 声明的原样大小写存储 | 实际比对时转为小写比较 | macOS / 不区分大小写的文件系统 | 原样保存展示，但比对时不区分大小写 |

在 Windows 下，底层 NTFS/FAT 文件系统本身对文件名大小写不敏感；而在 Linux 下，底层 ext4/xfs 文件系统严格区分文件名大小写。MySQL 中的数据库在磁盘上对应一个目录，表在磁盘上对应数据文件与元数据文件，因此 Linux 默认继承了文件系统的严格区分规则。

#### Linux 环境下大小写敏感与不敏感的对象边界

许多人容易走入极端，误以为在 Linux 下所有 SQL 内容都区分大小写。必须明确划清边界：

```text
+-------------------------------------------------------------+
|               Linux 下的大小写敏感边界划分                  |
+-------------------------------------------------------------+
| [严格区分大小写]                                            |
|   1. 数据库名 (Database Name)                                |
|   2. 数据表名 (Table Name)                                  |
|   3. 表的别名 (Table Alias)                                 |
|   4. 用户自定义变量名 (User-defined Variables)              |
+-------------------------------------------------------------+
| [完全不区分大小写]                                          |
|   1. SQL 关键字 (SELECT, FROM, WHERE, GROUP BY, INSERT 等)  |
|   2. 内置函数名 (COUNT, MAX, MIN, NOW, CONCAT 等)           |
|   3. 列名 / 字段名 (Column Name)                            |
|   4. 列的别名 (Column Alias)                                |
+-------------------------------------------------------------+
```
*图 1：Linux 平台下 SQL 各类对象的大小写敏感性判定*

##### 1) 严格区分大小写对象验证
在 Linux 环境下，我们此前创建过名为 `dbtest1` 的数据库及表 `emp1`。进行如下测试：

```sql
-- 数据库名大小写测试
USE dbtest1;  -- 成功切换
USE dBtest1;  -- 报错: ERROR 1049 (42000): Unknown database 'dBtest1'

-- 数据表名大小写测试
SELECT * FROM emp1;  -- 成功查出数据
SELECT * FROM Emp1;  -- 报错: ERROR 1146 (42S02): Table 'dbtest1.Emp1' doesn't exist
```

##### 2) 完全不区分大小写对象验证
无论是关键字、内置函数，还是字段名，大小写混用均能正常执行：

```sql
-- 关键字与函数名大小写混用测试
sElEcT COUNT(*) FrOm emp1;  -- 正常执行

-- 列名大小写混用测试
SELECT id, ID, name, NAME FROM emp1;  -- 正常执行，无报错
```

### 生产环境中 lower_case_table_names 的修改限制与工业规范

既然 Linux 区分大小写容易在多平台联调时引发找不到表的报错，我们能否直接在 Linux 下将其改为 `1`？

#### MySQL 5.7 与 8.0 的修改限制差异

在 MySQL 5.7 中，可以通过修改配置文件变更该参数：
1. 打开 `/etc/my.cnf`，在 `[mysqld]` 标签段追加 `lower_case_table_names=1`；
2. 重启 MySQL 服务：`systemctl restart mysqld`。

> **易错点**：在 MySQL 5.7 中修改该参数前，**必须先将库中所有现存的历史数据库名、表名、视图名全部手动转换为小写**！若磁盘上已存在大写文件名（如 `EMP.frm` / `EMP.ibd`），一旦修改为 `1`，MySQL 查询时会将 SQL 统一转为小写 `emp` 去磁盘检索，导致已有的历史表彻底无法被定位。

而在 MySQL 8.0 中，情况发生了根本性变化：
- MySQL 8.0 引入了全新的数据字典架构，元数据统一托管在数据字典表空间中。
- `lower_case_table_names` 参数被强制规定为**只能在数据库初始化阶段（`mysqld --initialize`）指定**！
- 如果在 8.0 实例初始化完成后，强行在 `/etc/my.cnf` 中修改该参数并尝试重启服务，mysqld 会直接启动崩溃并拒绝服务。如果非要修改，必须备份全库数据、彻底清空 `/var/lib/mysql` 数据目录，并在初始化命令中附带该参数重新初始化整个实例。

> **结论**：官方在 8.0 上的这一强限制，实质上传递了明确的设计导向：**强烈建议保留系统默认设置，不要在 Linux 上强行将 `lower_case_table_names` 修改为 1**。

#### 生产级 SQL 书写规范与规约

为了避免因跨环境迁移（从 Windows 线下开发到 Linux 线上部署）引发大小写异常，阿里巴巴开发手册及主流工业标准达成了如下统一规约：

1. **关键字与函数名全部大写**：例如 `SELECT`、`FROM`、`WHERE`、`LEFT JOIN`、`COUNT()`、`MAX()`；
2. **库名、表名、表别名全部小写**：统一使用全小写字母，多个单词间使用下划线分割（如 `order_detail`、`emp_record`）；
3. **字段名、字段别名全部小写**：统一小写（如 `user_id`、`create_time`）；
4. **SQL 语句显式以分号结尾**：严格规范语法边界。

大小写区分的初衷，是为了让开发人员通过视觉扫视一眼就能清晰剥离 SQL 骨架与业务结构：看到全大写即为语言机制与算子，看到全小写即为自定义业务库表实体。

### sql_mode 的作用机制与模式演进

很多开发者习惯了传统数据库宽松的容错特性，但随着数据质量要求的提高，MySQL 对非法输入与非标准语法的拦截越来越严格。这一核心校验阀门即为 `sql_mode`。

> **定义**：`sql_mode`（SQL 模式）是 MySQL 的核心系统变量，用于定义系统支持的 SQL 语法规范，以及执行数据插入、更新和聚合计算时的数据有效性校验严格程度。

#### 宽容模式与严格模式的演进

在 MySQL 5.6 及更早版本中，`sql_mode` 默认值通常为空字符串，系统处于**宽容模式**；而在 MySQL 5.7 及 8.0 中，默认启用了 `STRICT_TRANS_TABLES` 等一系列强校验参数，全面切换为**严格模式**。

```text
+-----------------------------------------------------------------+
|                        sql_mode 演进对比                        |
+-----------------------------------------------------------------+
| MySQL 5.6: 宽容模式 (默认值为空)                                |
|   - 字符串超长: 自动静默截断，保留前 N 位，给出 Warning, 不报错 |
|   - 类型不匹配: 尝试强制类型转换或填充零值 (0 / 0000-00-00)     |
|   - 语法不严谨: 允许隐式聚合，产生不可预期的数据输出            |
+-----------------------------------------------------------------+
                               |
                               v
+-----------------------------------------------------------------+
| MySQL 5.7 / 8.0: 严格模式 (STRICT_TRANS_TABLES / 默认多项组合)  |
|   - 字符串超长: 直接抛出 Error，事务中断，拒绝非法数据落盘      |
|   - 类型不匹配: 拒绝强制转换，直接抛出 Error                    |
|   - 语法不严谨: 强制 ONLY_FULL_GROUP_BY，阻断歧义聚合           |
+-----------------------------------------------------------------+
```
*图 2：MySQL 宽容模式与严格模式的核心行为对比*

#### 宽容模式的适用场景与潜在隐患

在数据表 `name CHAR(10)` 的场景下，若向该字段插入长度为 13 的字符串 `'1234567890ABC'`：
- **宽容模式下**：执行 `INSERT` 不报错，仅仅抛出一个警告（Warning），底层自动截取前 10 个字符 `'1234567890'` 存入磁盘，后缀 `'ABC'` 被静默丢弃；
- **严格模式下**：直接抛出 `Data too long for column 'name'` 错误，彻底终止执行。

宽容模式唯一的合理使用场景是**异构数据库的历史数据迁移**。在跨引擎搬迁大批量旧数据时，为了避免个别脏数据阻断整体迁移进度，可以临时调为宽容模式完成灌库。但在正常生产与线上业务中，宽容模式会将业务 BUG 和非法输入全部“粉饰太平”存入数据库，导致不可逆的数据腐败。

### 常见 sql_mode 约束行为与实测分析

查看当前实例的 `sql_mode` 取值：

```sql
-- 查看当前会话级别的 sql_mode
SELECT @@session.sql_mode;

-- 查看全局级别的 sql_mode
SELECT @@global.sql_mode;
```

控制台返回的复合模式通常包含以下核心参数项：

| 模式名称 | 核心限制与校验规则 |
| :--- | :--- |
| `ONLY_FULL_GROUP_BY` | 强制标准 SQL 分组规范：`SELECT` 列表中除聚合函数外的所有列，必须出现在 `GROUP BY` 之后 |
| `STRICT_TRANS_TABLES` | 对事务型存储引擎（如 InnoDB）开启严格数据校验，非法数据直接报错阻断事务 |
| `NO_ZERO_IN_DATE` | 禁止日期中出现月份为 0 或日为 0 的半合法日期（如 `'2026-00-01'`） |
| `NO_ZERO_DATE` | 禁止插入全零非法日期（如 `'0000-00-00'`） |
| `ERROR_FOR_DIVISION_BY_ZERO` | 在进行除法运算遇到除数为 0 时，抛出错误而非静默返回 `NULL` |
| `NO_ENGINE_SUBSTITUTION` | 当建表指定的存储引擎不可用时，直接报错而非自动降级使用默认引擎 |

#### 案例实测一：ONLY_FULL_GROUP_BY 的分组歧义拦截

在 `dbtest1` 中创建员工部门测试表并填充数据：

```sql
CREATE TABLE my_emp (
    id INT,
    name VARCHAR(15),
    age INT,
    dept VARCHAR(10)
);

INSERT INTO my_emp VALUES 
(1, '张三', 25, '研发部'),
(2, '李四', 30, '研发部'),
(3, '王五', 28, '市场部');
```

执行如下需求查询：“查询各个部门中年龄最大的人”：

```sql
SELECT name, dept, MAX(age) 
FROM my_emp 
GROUP BY dept;
```

在默认的严格模式下，执行该语句会立即阻断并抛出异常：
`ERROR 1055 (42000): Expression #1 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'dbtest1.my_emp.name' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by`

> **提示**：在标准 SQL 中，按 `dept` 分组后，研发部对应了多条不同的 `name`（张三、李四）。若未对 `name` 使用聚合函数且未将其作为分组依据，系统根本无法确定该返回哪一个名字。严格模式精准拦截了这种逻辑漏洞。

若临时将当前会话的 `sql_mode` 清空置为宽松：

```sql
SET SESSION sql_mode = '';

-- 再次执行查询
SELECT name, dept, MAX(age) 
FROM my_emp 
GROUP BY dept;
```

此时语句顺利跑通，但 `name` 字段显示的值纯属物理行上的随机首条记录，无法保证名字与最大年龄形成精确映射。

#### 案例实测二：非法类型赋值拦截

依然在宽松模式（`sql_mode=''`）下，向整型字段写入非法字符串：

```sql
-- age 字段定义为 INT 类型，故意赋入纯英文字符串 'aaa'
INSERT INTO my_emp (id, name, age) VALUES (6, 'Tom', 'aaa');
```

执行后语句未报错，仅给出警告。查询表记录：

```sql
SELECT * FROM my_emp WHERE id = 6;
-- 输出: id=6, name='Tom', age=0
```

系统在宽松模式下擅自将无法解析的字符隐式转换填充为整型默认值 `0`。而在恢复严格模式后，该语句会直接被系统拒之门外：
`ERROR 1366 (HY000): Incorrect integer value: 'aaa' for column 'age' at row 1`

### 生产环境持久化配置方案：双管齐下法

在实际生产运维场景中，修改 `sql_mode` 面临着一对经典的工程矛盾：
- **纯临时修改（SET GLOBAL）**：立即对新建连接生效，无需重启数据库，业务无感知；但一旦服务器宿主机发生维护重启，所有配置瞬间丢失，直接回退到旧配置；
- **纯静态文件修改（my.cnf）**：持久化保存在磁盘上，不怕实例重启；但必须重启 mysqld 服务才能加载，而在高并发生产环境下，随意重启数据库会导致大量线上交易中断。

针对这一困境，最佳的运维工程实践为**临时修改与静态持久化双管齐下**：

```text
[运维变更流程]
       |
       +---> 步骤 1: 执行 SET GLOBAL sql_mode = '...' 
       |            (线上实时生效，所有新接入会话即刻应用，零停机无感知)
       |
       +---> 步骤 2: 编辑 /etc/my.cnf 追加相同 sql_mode 配置
                    (落盘固化，保障未来例行维护或故障重启后配置不丢)
```
*图 3：生产环境 sql_mode 变更的双管齐下策略*

#### 第一步：执行全局动态生效

登录 MySQL 客户端，执行全局动态设置：

```sql
SET GLOBAL sql_mode = 'ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
```

执行后，当前已建立的长连接保持原样，之后新建立的业务数据库连接将无缝应用最新的严格模式，保障线上服务零中断。

#### 第二步：同步修改配置文件持久化

编辑 Linux 系统的 `/etc/my.cnf` 文件：

```bash
vim /etc/my.cnf
```

在 `[mysqld]` 标签下方追加配置行：

```ini
[mysqld]
sql_mode=ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

保存并退出。通过双管齐下的方式，既兼顾了当前生产系统的连续性可用，又锁定了未来系统重启后的长期一致性。

## 104-MySQL目录结构与表在文件系统中的表示
> 对应分集：P104 | 原始标题：《104-MySQL目录结构与表在文件系统中的表示》

在学习 SQL 的初步阶段，我们习惯了通过客户端连接实例，执行 `CREATE DATABASE`、`CREATE TABLE` 或 `INSERT`，把数据视为抽象的“行与列”。但作为一名后端开发者或 DBA，如果仅仅停留在逻辑抽象层，一旦遇到性能调优、空间爆满、数据迁移或深入剖析 B+ 树索引底层时，就会陷入“盲人摸象”的困境。

MySQL 究竟把我们的库、表结构、索引和每一条数据塞在宿主操作系统的哪个角落？为什么在 5.7 时代每张表至少有两个文件，到了 8.0 却只剩一个 `.ibd`？MyISAM 引擎生成的一堆 `.MYD`、`.MYI` 又和 InnoDB 有什么本质差异？本篇我们将深入 Linux 真实文件系统，彻底掀开 MySQL 底层物理存储的面纱。

---

### 跨平台目录布局对比：Windows 与 Linux

在回顾 Windows 环境安装时，MySQL 主要依托两个核心目录：
- **程序目录**（如 `D:\Program Files\MySQL\MySQL Server 8.0\`）：存放服务二进制可执行文件，核心是 `bin` 目录（内置 `mysql`、`mysqld`、`mysqldump` 等工具指令，通常配入系统的 Path 环境变量）；
- **数据与配置目录**（如 `C:\ProgramData\MySQL\MySQL Server 8.0\`）：核心包含主配置文件 `my.ini`，以及存放物理库表文件的 `Data` 目录。

将视野切换到生产环境主流的 Linux（CentOS / RedHat / Ubuntu）平台下，这一布局被标准规范化地分散到了 Linux 的 FHS（文件系统层次结构标准）目录中。在 `150`（MySQL 8.0）节点上，执行查找命令即可检索出核心挂载点：

```bash
find / -name mysql
```

排查后提炼出 Linux 环境下承载 MySQL 生命周期的三大支柱路径：

| 目录路径 | 对应角色 | 承载内容与功能 |
| :--- | :--- | :--- |
| `/var/lib/mysql/` | **数据目录 (Data Directory)** | 存储所有系统库、用户数据库、表空间、持久化数据与重做日志 |
| `/usr/bin/` 与 `/usr/sbin/` | **命令目录 (Binary Directory)** | `/usr/bin/` 存放客户端管理指令；`/usr/sbin/` 存放服务端守护进程 `mysqld` |
| `/etc/my.cnf` | **主配置文件 (Config File)** | 服务端全局配置文件（等同于 Windows 下的 `my.ini`） |
| `/usr/share/mysql-8.0/` | **共享支持目录 (Share Directory)** | 存放默认配置模板、多语言错误提示信息文件及字符集说明包 |

#### 数据目录系统变量 datadir 验证

数据目录是 MySQL 实例启动时加载数据、运行时读写落盘的核心大本营。在 MySQL 客户端中执行如下查询：

```sql
SHOW VARIABLES LIKE 'datadir';
```

控制台准确返回：
```text
+---------------+-----------------+
| Variable_name | Value           |
+---------------+-----------------+
| datadir       | /var/lib/mysql/ |
+---------------+-----------------+
```
这印证了 `/var/lib/mysql/` 正是数据库的官方物理落盘点。

#### 命令工具与配置文件路径实测

进入 `/usr/bin` 目录通过 `ls` 筛选，可以看到 MySQL 提供的丰富客户端工具集：
- `mysql`：交互式客户端命令行入口；
- `mysqladmin`：服务运维管理程序（检查状态、关机、刷新日志）；
- `mysqlbinlog`：专门用于解析与提取二进制日志（Binary Log）的专用工具；
- `mysqldump`：逻辑全量与分库分表备份工具；
- `mysqlimport`：文本数据高速导入工具；
- `mysqlcheck`：表完整性检查、修复与优化工具。

而守护进程 `mysqld` 则独立安置在超级用户权限的 `/usr/sbin/mysqld` 下。系统全局配置则收归在 `/etc/my.cnf`，任何服务端参数（如端口、缓冲池大小、字符集）的持久化修改均在此处落地。

### 默认系统数据库的功能职责划分

进入 `/var/lib/mysql/` 目录执行 `ll` 列出内容，除了我们自定义的业务库外，映入眼帘的是 4 个至关重要的默认系统数据库。它们各司其职，支撑着整套 MySQL 引擎的运转：

```text
/var/lib/mysql/
├── mysql/                  # 核心系统库 (用户、权限、元数据)
├── information_schema/     # ANSI 标准信息架构视图库 (不落磁盘)
├── performance_schema/     # 性能剖析与运行时监控数据
└── sys/                    # DBA 综合监控视图库 (结合前两者)
```
*图 1：MySQL 核心默认系统数据库在物理目录中的呈现*

#### mysql 核心权限库
这是 MySQL 最关键的系统库。它直接记录了连接实例所需的用户账号、主机授权与权限映射。例如执行如下查询：
```sql
USE mysql;
SELECT host, user FROM user;
```
该库下的 `user` 表是整个实例访问控制体系的基石，此外还存放了插件定义、时区数据、系统帮助文档等元数据。

#### information_schema 信息架构库
该库完整遵从 ANSI SQL 标准，维护着当前实例中所有其他数据库、数据表、列字段、索引、视图、触发器及存储过程的元数据。
- 在日常开发中，我们查询存储过程、自定义函数定义，或排查触发器状态时，访问的正是 `information_schema.routines` 或 `information_schema.triggers`；
- 它在物理磁盘上并没有实体数据文件，而是一套纯内存中的虚拟视图。

#### performance_schema 性能监控库
专门用于在底层微秒级收集 MySQL 服务的运行时内部事件。它记录了内存消耗、锁等待、线程执行生命周期、IO 读写频率等性能指标，且设计为极低计算开销，是性能调优和排查慢查询与锁冲突的根本数据来源。

#### sys 性能诊断简化库
`performance_schema` 内部表结构极为繁琐、信息维度过于底层。MySQL 官方专门开发了 `sys` 库，通过一系列高级封装视图，将 `information_schema` 与 `performance_schema` 结合起来。开发人员和 DBA 可以直接调用 `sys` 视图，一键定位“当前最消耗内存的查询”、“哪个索引从未被使用”等生产级瓶颈。

### 存储引擎表在文件系统中的物理映射演进

当我们执行 `CREATE TABLE` 后，操作系统磁盘上到底发生了什么？这取决于你选择的**存储引擎**（InnoDB 还是 MyISAM）以及你所处的**软件版本**（MySQL 5.7 还是 MySQL 8.0）。

为了条理清晰，我们以两张表为例：
- `emp1`：采用 **InnoDB** 引擎；
- `student`：采用 **MyISAM** 引擎。

#### InnoDB 引擎在 MySQL 5.7 下的物理文件形态

登录 5.7 节点（`160`），进入数据目录 `/var/lib/mysql/dbtest1/`，执行 `ll` 查看文件列表：

```text
-rw-r----- 1 mysql mysql    65 db.opt
-rw-r----- 1 mysql mysql  8556 emp1.frm
-rw-r----- 1 mysql mysql 98304 emp1.ibd
```
*图 2：MySQL 5.7 下单个 InnoDB 表在数据库目录中的文件形态*

在 5.7 中，一个数据库对应一个子目录。在 `dbtest1` 目录下，呈现出三个独立文件：

##### 1) db.opt
数据库属性元文件。使用纯文本记事本即可打开，里面仅存储了两行元数据：当前数据库默认的字符集与比较规则（如 `default-character-set=utf8` 与 `default-collation=utf8_general_ci`）。

##### 2) 表名.frm
表结构定义文件（Format File）。存放该表的 DDL 定义信息，包括字段名称、数据类型、主外键约束与默认值等，所有引擎在 5.7 中通通都有 `.frm`。

##### 3) 表名.ibd 与系统表空间 ibdata1
数据究竟放在哪？这涉及 InnoDB 的表空间架构演进：
- **系统表空间 (System Tablespace)**：在 `/var/lib/mysql/` 根目录下存在一个公共的 `ibdata1` 文件，默认初始大小为 12MB，支持按需自动扩展。在 MySQL 5.5.7 至 5.6.6 早期版本中，全实例所有库、所有表的数据与索引被默认混杂地堆放在这一个全局 `ibdata1` 文件中！
- **独立表空间 (File-Per-Table Tablespace)**：将各表的数据独立剥离为 `表名.ibd`。通过参数 `innodb_file_per_table` 控制（在 5.6.6 及后续版本中默认开启为 `ON`）：

```sql
SHOW VARIABLES LIKE 'innodb_file_per_table';
```

在开启独立表空间的情况下，`emp1` 表的行记录数据以及聚簇索引，全部被封装在独立的 `emp1.ibd` 文件中。

#### InnoDB 引擎在 MySQL 8.0 下的重大重构：结构数据合一

切换到 8.0 节点（`150`），进入 `/var/lib/mysql/dbtest1/` 执行 `ll`，会惊奇地发现目录极其清爽：

```text
-rw-r----- 1 mysql mysql 114688 emp1.ibd
```

##### 消失的 db.opt
8.0 彻底废弃了 `db.opt`，数据库层级的字符集与排序规则统一迁移到了全局的数据字典表空间中维护。

##### 消失的 .frm 与结构数据合一
在 8.0 中，`.frm` 文件完全不复存在！
很多初学者会疑惑：“没有了 `.frm`，表的结构定义去哪了？难道不存了吗？”

> **结论**：在 MySQL 8.0 中，官方实现了**表结构与表数据的彻底合一**。表的列定义、索引元数据（SDI，序列化字典信息）被直接作为一段 JSON 序列化数据，内嵌灌装在了 `emp1.ibd` 独立表空间文件内部！

##### 工业级实测：使用 ibd2sdi 工具提取表结构
Oracle 官方在 MySQL 8.0 的命令集中内置了一个底层的独立解析工具——`ibd2sdi`（IBD to Serialized Dictionary Information）。利用该工具，我们可以从二进制的 `.ibd` 文件中逆向解构出完整的表定义 JSON：

```bash
# 进入数据库目录
cd /var/lib/mysql/dbtest1

# 解析 emp1.ibd 并导出为文本
ibd2sdi --dump-file=emp1.txt emp1.ibd

# 查看解析出来的文本文件
vim emp1.txt
```

打开 `emp1.txt`，在长达数百行的结构化 JSON 数据中搜索 `id` 和 `name`：
- 可以清晰看到表的元数据定义：`"name": "emp1"`；
- 字段 `id` 的底层信息：`"type": 4`（代表整型），包含 `is_nullable`、`is_zerofill`、`is_unsigned` 等修饰符；
- 字段 `name` 的底层信息：`"type": 16`（代表变长字符串 `VARCHAR`）。

这从底层无可辩驳地证明了：8.0 的 `.ibd` 已经进化为兼具“元数据定义”与“行级物理数据”的复合存储单元。

### MyISAM 引擎的物理拆分与索引机制伏笔

我们在 5.7 与 8.0 节点上，分别创建一张显式声明为 MyISAM 引擎的测试表：

```sql
CREATE TABLE student (
    id INT,
    name VARCHAR(20)
) ENGINE = MyISAM;
```

#### MySQL 5.7 下 MyISAM 的三剑客文件

在 5.7 节点的 `/var/lib/mysql/dbtest1/` 目录下，查看 `student` 表生成的物理文件：

```text
-rw-r----- 1 mysql mysql  8556 student.frm
-rw-r----- 1 mysql mysql     0 student.MYD
-rw-r----- 1 mysql mysql  1024 student.MYI
```

MyISAM 展现了与 InnoDB 完全不同的三文件分离架构：
- `student.frm`：表结构定义文件；
- `student.MYD`：**数据文件 (MYData)**，存放实际的数据行；
- `student.MYI`：**索引文件 (MYIndex)**，单独存放为该表构建的 B+ 树索引结构。

#### 下 MyISAM 的演变：sdi 文件登场

在 8.0 节点下查看 MyISAM 表文件，同样发生了变革：
- `student.MYD`：保持不变，依旧存储纯数据；
- `student.MYI`：保持不变，依旧存储纯索引；
- `student_xxx.sdi`：`.frm` 退出历史舞台，由独立的 `.sdi`（Serialized Dictionary Information）文本文件接替，里面以 JSON 格式完整记录了该表的字段与约束定义。

#### 为什么 MyISAM 拆分存储而 InnoDB 合并存储？

这正是理解后续高级篇“聚簇索引（Clustered Index）”与“非聚簇索引（Secondary Index）”的最关键物理依据：

> **核心原理**：
> - **MyISAM 引擎**采用的是非聚簇索引架构。索引和数据在物理上完全解耦，索引文件（`.MYI`）的叶子节点仅仅记录数据的“物理磁盘地址”（指针）；数据文件（`.MYD`）则单纯按写入顺序平铺追加数据行。两者必须拆分为两个独立文件。
> - **InnoDB 引擎**采用的是聚簇索引架构，崇尚“**索引即数据，数据即索引**”。InnoDB 的主键 B+ 树叶子节点本身直接包裹并容纳了整行完整的数据。数据行就是挂在树根底部的叶子，索引与数据血肉相连，因此物理上直接整合进唯一的 `.ibd` 表空间文件中！

### 视图与日志文件的物理本质

除了基表外，数据目录下还存在其他特殊对象的物理痕迹：

#### 视图在文件系统中的呈现
视图（View）是逻辑上的“虚表”，其本身不产生、不拥有任何真实的物理行数据。
- 在 MySQL 5.7 中，若创建视图 `v_emp`，在数据库目录下只会生成一个轻量级的 `v_emp.frm` 文件，用于记录创建该视图的 `SELECT` 语句骨架，绝不会派生出 `.ibd` 或 `.MYD`；
- 这从物理视角彻底验证了“视图纯属虚拟查询逻辑，不占实际数据空间”的底层事实。

#### 核心服务日志文件简述
在 `/var/lib/mysql/` 目录下，随着实例的持续写入，还会陆续产生一系列重量级日志：
- **重做日志 (Redo Log)**：如 `ib_logfile0`、`ib_logfile1`，保障事务持久性（Crash Recovery）；
- **回滚日志 (Undo Log)**：在独立的 undo 表空间中维护，用于支撑事务回滚与 MVCC 多版本并发控制；
- **错误日志 (Error Log)**：记录实例启停、严重故障与崩溃追踪堆栈；
- **二进制日志 (Binary Log)**：如 `binlog.000001`，按顺序记录所有 DDL 与 DML 变更事件，是主从复制与灾难恢复的心脏。

深入理解数据目录中每一个文件的来龙去脉，不仅能帮我们在排查生产磁盘故障时胸有成竹，更是在后续剖析 InnoDB 页结构、行格式与索引检索时最坚实的技术立足点。
