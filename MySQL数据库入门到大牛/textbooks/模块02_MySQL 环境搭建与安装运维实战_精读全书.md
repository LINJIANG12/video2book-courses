## 第 1 章：06-MySQL8.0的卸载
> 对应分集：P06 | 原始标题：《06-MySQL8.0的卸载》

进入 MySQL 学习体系的实操阶段，首要任务无疑是搭建一套稳定、可用的数据库运行环境。然而，在正式展开安装流程之前，摆在许多初学者面前的第一道难关往往不是“如何装上”，而是“如何卸干净”。

在大量学习与工程实践中，许多人在初次安装 MySQL 时由于选项配置失误、网络中断或权限不足，导致安装流程走到一半异常终止。此时如果直接再次运行安装包，往往会遭遇端口被占用、服务名冲突、数据目录已存在等连环报错，最终导致安装陷入死锁。不仅如此，对于机器上原本安装过 MySQL 5.7 或其他旧版本的同学，若未能彻底清除系统深处的底层残留，直接部署 8.0 版本几乎必然遭遇冲突。所谓“未学其来，先知其去”，掌握如何将 MySQL 从操作系统中彻底、干净地剥离，是保证后续所有实操顺利推进的先决技术能力。

### 1. 宿主系统中 MySQL 的四大物理存在维度

要想将 MySQL 彻底从操作系统中连根拔起，首先必须在全局视角下审视：当一套完整的 MySQL 部署在 Windows 操作系统中时，它究竟在系统的哪些关键位置留下了足迹？

在系统正常运行状态下，我们可以通过命令行验证 MySQL 的健康状态。在 Windows 终端中执行版本检测与登录命令：

```bash
# 验证 MySQL 客户端及服务端版本信息
mysql --version

# 以超级管理员 root 身份登录本地数据库实例
mysql -u root -p
```

终端提示输入密码后，输入预设的凭证（如 `abc123`），便可成功进入 `mysql>` 交互提示符。通过执行基础元数据查询命令：

```sql
-- 查看当前实例所管理的所有逻辑数据库
SHOW DATABASES;

-- 切换至具体业务数据库并查看其包含的数据表
USE atguigudb;
SHOW TABLES;
```

能够清晰观察到当前数据库引擎管理的各个逻辑库与表。此时，MySQL 在操作系统底层实际上分布于以下四个物理维度。

```text
+-------------------------------------------------------------------------+
|                      MySQL 在 Windows 系统的四大物理维度                |
+-------------------------------------------------------------------------+
| 1. 软件安装目录 (DBMS 二进制程序本体)                                   |
|    D:\develop_tools\MySQL\MySQL Server 8.0\                             |
|    |-- bin\ (包含 mysql.exe, mysqld.exe 等核心可执行命令)                |
|    \-- lib\, include\, share\ (依赖库与元数据文件)                      |
|                                                                         |
| 2. 数据与配置目录 (物理表空间与引擎配置，默认隐藏)                       |
|    C:\ProgramData\MySQL\MySQL Server 8.0\                               |
|    |-- data\ (存放各数据库物理文件夹，如 atguigudb/*.ibd)               |
|    \-- my.ini (核心配置文件，定义端口、字符集、缓冲池等)                |
|                                                                         |
| 3. 操作系统服务进程 (Windows Services)                                   |
|    服务名: MySQL80 (后台守护进程 mysqld.exe)                             |
|    控制运行状态，对外监听 3306 端口提供网络通信服务                     |
|                                                                         |
| 4. 系统环境变量 (System Environment Variables)                          |
|    Path = ...;D:\develop_tools\MySQL\MySQL Server 8.0\bin;...           |
|    实现全局任意终端路径下直接调用 mysql 等指令                          |
+-------------------------------------------------------------------------+
```

> **图 1-1 说明**：MySQL 在 Windows 下由程序文件、数据与配置文件、系统服务项及全局环境变量四大模块协同构成。单纯删除任何单一模块都属于不完整卸载。

#### 1.1 软件安装目录（DBMS 程序本体）

这是数据库管理系统（DBMS）的二进制程序集合，相当于电脑上安装的常规应用软件本体。通常位于用户指定的安装分区，例如 `D:\develop_tools\MySQL\MySQL Server 8.0`。

该目录下最核心的子目录是 `bin/`（Binary），其中存放了服务端启动守护进程 `mysqld.exe`、客户端连接工具 `mysql.exe`、数据备份工具 `mysqldump.exe` 等核心可执行文件。此外，还包含了系统运行时所需的动态链接库（`lib/`）与资源定义文件。

#### 1.2 数据与配置文件目录（Data 与 my.ini）

这是关系型数据库最核心的“物理载荷”存放地，与软件安装目录处于完全解耦的状态。在 Windows 平台默认设置下，它隐藏在系统驱动器的全局应用数据目录下：`C:\ProgramData\MySQL\MySQL Server 8.0\`。

> **提示**：`ProgramData` 在 Windows 下默认属于“隐藏项目”。如果在 C 盘根目录下未看到该文件夹，需要在文件资源管理器的“查看”菜单栏中勾选“隐藏的项目”复选框，方可使其显形。

该目录下包含两个极其关键的对象：
1. **`data` 文件夹**：内部按逻辑数据库名称划分为一个个具体的子文件夹（如 `mysql/`、`sys/`、`atguigudb/`）。每一个文件夹内包含了 `.ibd`（InnoDB 表空间文件）等具体的物理表存储文件，直接承载了系统中的全部业务数据；
2. **`my.ini` 配置文件**：MySQL 实例启动时强依赖的核心参数配置文件，定义了监听端口（默认 3306）、默认存储引擎、默认字符集（8.0 默认 `utf8mb4`）、最大并发连接数、InnoDB 缓冲池尺寸（`innodb_buffer_pool_size`）等核心系统级参数。

#### 1.3 操作系统后台服务（Windows Services）

MySQL 作为一个服务端守护软件，必须在后台作为独立的操作系统进程长驻运行。它以 Windows 服务的形式向系统注册，常见服务名称为 `MySQL80`（5.7 版本通常为 `MySQL` 或 `MySQL57`）。

当客户端尝试发起连接时，其前提是 `MySQL80` 服务处于“正在运行”状态。如果通过 Windows 服务管理控制台（`services.msc`）手动将该服务“停止”，再次在终端执行数据查询或建立新连接时，客户端将立即抛出 `ERROR 2003 (HY000): Can't connect to MySQL server` 或 `Lost connection to MySQL server` 异常。

#### 1.4 系统全局环境变量 Path

为了能够在任意工作目录下直接呼叫 `mysql`、`mysqladmin` 等命令，而无需每次都切换到庞长复杂的 `D:\develop_tools\MySQL\MySQL Server 8.0\bin` 物理路径下，操作系统的 `Path` 环境变量中必须追加该 `bin` 目录的绝对路径。

操作系统在接收到未知命令时，会依次检索当前目录与 `Path` 变量中所列出的所有路径条目。若配置了该路径，便能在全局实现无缝命令行调用。

### 2. 软件卸载与数据解耦原理

在明确了四大物理维度之后，彻底卸载的本质就是将这四个维度逐一进行清理。但在开始动手之前，必须先理清一个让无数初学者倍感困惑的技术现象。

很多同学通过 Windows 控制面板成功卸载了 MySQL，但当进入 `C:\ProgramData\MySQL` 时，却惊奇地发现 `data` 文件夹和 `my.ini` 依旧完好无损地留在磁盘上，进而怀疑卸载程序存在缺陷。事实上，**这绝不是卸载程序的 Bug，而是专业级企业软件在系统架构层面上刻意实施的“程序与数据物理解耦”设计**。

我们可以通过生活与办公中的常见软件来理解这种设计：
- 在电脑上使用 Office 或 WPS 撰写文档，保存为 `report.docx`。当我们从控制面板中卸载 Office 时，写好的 Word 文档会被系统同步删掉吗？显然不会；
- 在手机上下载一款美颜修图软件拍摄了大量生活照片。当某一天卸载该相机 App 时，手机相册中保存的照片会被清空吗？同样不会。

映射到工业级数据库领域，这种解耦机制体现得更为严苛：
考虑生产环境中的真实运维场景：某系统最初运行在 MySQL 5.7 上，随着业务演进计划原地升级至 MySQL 8.0。在升级替换二进制程序的过程中，如果不幸遭遇依赖库损坏或升级中断，运维人员需要卸载当前的 8.0 安装包并回退。如果卸载程序默认将包含数十 TB 业务数据的 `data` 目录一并格式化抹除，那么整个企业的生产数据将在几秒钟内化为乌有，没有任何企业敢于使用这种软件。

> **结论**：数据库系统严格遵循“程序可卸载，数据不可轻弃”的原则。安装包提供的卸载工具只负责清理 DBMS 程序本体，绝对不会主动销毁用户的数据文件。
> 在日常学习中，若目标是**彻底重置、重新安装一套干净的全新环境**，则必须由人工在确认备份或确认无用后，**手动删除**该数据目录。

### 3. 标准卸载五步法操作规程

为了确保系统环境恢复至绝对干净的未安装状态，必须严格遵循以下标准五步规程依次执行。

```text
[第 1 步: 停止系统服务] 
        |
        v
[第 2 步: 卸载程序本体 (控制面板)]
        |
        v
[第 3 步: 手动清理数据与配置残留 (ProgramData)]
        |
        v
[第 4 步: 清理环境变量与注册表项 (5.7 残留治理)]
        |
        v
[第 5 步: 重启计算机 (释放系统句柄)]
```

#### 3.1 步骤一：停止 Windows 系统后台服务

在移除任何磁盘文件与注册表项之前，必须确保 MySQL 守护进程已停止运行，否则运行中的进程会锁死文件句柄，导致卸载程序报错或文件残留。

- **图形化操作**：按下 `Win + R` 键，输入 `services.msc` 打开 Windows 服务管理控制台。在服务列表中找到 `MySQL80`（或相应的服务名称），右键选择【停止】；
- **命令行操作**：以管理员身份打开命令提示符或 PowerShell，执行服务终止命令：

```powershell
# 停止运行中的 MySQL 服务实例
net stop MySQL80
```

确认服务状态由“正在运行”切换为停止状态。

#### 3.2 步骤二：通过官方通道卸载 DBMS 软件本体

移除程序本体必须通过受控的卸载渠道，严禁直接在文件资源管理器中选中安装目录执行右键“删除”。直接删文件夹会导致操作系统安装数据库、COM 组件注册信息以及控制面板索引陷入死链状态。

推荐采用以下三种途径之一（以官方控制面板为首选）：

1. **控制面板卸载（通用首选）**：
   打开 Windows 控制面板，进入【程序和功能】（或“卸载程序”）。在已安装程序列表中，找到发布者为 `Oracle Corporation` 的相关项，通常包括：
   - `MySQL Server 8.0`（核心数据库引擎）
   - `MySQL Installer - Community`（如果使用了集中安装器）
   右键依次点击【卸载】，跟随系统向导完成二进制程序的移除。
2. **MySQL Installer 维护向导**：
   如果原本是通过官方提供的 `mysql-installer-community.msi` 进行集约化安装，可以直接再次运行该安装包。向导识别到本机已存在安装实例后，会进入维护模式界面。在界面中点击【Remove】，勾选所有组件后执行卸载；
3. **第三方管理软件辅助卸载**：
   如系统深度安装了相关电脑管家类软件，亦可调用其软件管理模块进行卸载，其底层实质上依然是调用系统的 `msiexec` 卸载引擎。

卸载完成后，进入原安装路径（如 `D:\develop_tools\MySQL`），会发现其下的子文件与依赖库已被清空。仅留下最初用户自定义创建的顶层空目录，此时可直接将该空目录清理干净。

#### 3.3 步骤三：深度清理数据文件与残留目录

在教学与重装演练场景下，必须将数据目录连根拔除。

1. 确认已开启隐藏文件可见模式，定位至物理路径：
   `C:\ProgramData\MySQL`
2. 彻底删除整个 `MySQL` 文件夹（或其中的 `MySQL Server 8.0` 子目录）。
   该操作将抹除旧数据库遗留的物理表数据（`data/`）以及旧的配置文件（`my.ini`），切断后续新安装流程与历史损坏配置的任何关联。

> **警告**：在任何生产、测试或已有重要业务数据的环境中执行此步骤前，必须确认已对核心数据库完成了全量逻辑导出备份（如使用 `mysqldump` 导出的 SQL 脚本）。一旦物理删除该目录，无冷备份情况下数据将永久丢失。

#### 3.4 步骤四：清理系统环境变量与残留服务注册表项

##### 1. 清理 Path 环境变量
1. 右键点击【此电脑】->【属性】->【高级系统设置】；
2. 在弹出窗口中点击【环境变量】；
3. 在下方的【系统变量】列表中定位并双击 `Path` 变量；
4. 找到之前配置的指向 MySQL `bin` 目录的条目（例如 `D:\develop_tools\MySQL\MySQL Server 8.0\bin`），选中并点击【删除】；
5. 连续点击【确定】以保存环境配置。

##### 2. 深度清理服务项与注册表残留（MySQL 5.7 与异常残留治理）
在安装与卸载较新的 MySQL 8.0 时，官方卸载向导通常会自动反注册 Windows 服务项。然而在早期的 **MySQL 5.7** 版本中，或者因安装中途崩溃导致异常退出的场景下，Windows 服务项往往无法被自动注销。当重新安装时，安装向导会直接提示“服务名 `MySQL` 已被占用”，导致流程彻底阻断。

若在服务管理控制台（`services.msc`）中发现旧服务项依然残留，必须通过注册表进行强力清扫：

1. 按下 `Win + R` 键，输入 `regedit`，按回车打开 Windows 注册表编辑器；
2. 依次导航并定位至以下注册表路径，若存在对应的 `MySQL` 项，直接右键将其删除：

```text
HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\Services\Eventlog\Application\MySQL
HKEY_LOCAL_MACHINE\SYSTEM\ControlSet002\Services\Eventlog\Application\MySQL (若存在)
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Eventlog\Application\MySQL
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\MySQL (或对应具体的服务名如 MySQL57)
```

> **易错点**：`ControlSet001`、`ControlSet002` 是 Windows 硬件与驱动配置的历史备份集，具体机器上的命名编号可能略有差异，凡是存在 `Services\MySQL` 或相关事件日志注册的项，均应排查并清理干净。

3. 若注册表清理后控制台显示仍未同步，也可以在管理员终端中直接执行服务注销命令：

```powershell
# 通过 Windows 内置工具强制删除残留的服务条目
sc delete MySQL80
```

#### 3.5 步骤五：重启操作系统

在完成上述全部文件与注册表项的剔除之后，务必重新启动操作系统（Reboot）。

Windows 操作系统由于其内核句柄管理机制，某些被卸载的动态链接库、未完全注销的驱动服务项及注册表变更，往往需要在系统重新加载内核时才能真正释放句柄占用。重启完成后，宿主机的系统环境将彻底恢复至无任何 MySQL 痕迹的纯净状态，为下一步干净、零冲突地安装全新 MySQL 8.0 或 5.7 实例铺平道路。

## 第 2 章：07-MySQL8.0与5.7版本的下载、安装与配置
> 对应分集：P07 | 原始标题：《07-MySQL8.0与5.7版本的下载、安装与配置》

在完成操作系统的彻底清理并重启后，宿主机已处于绝对纯净的未安装状态。接下来将正式展开 MySQL 运行环境的构建。

许多刚接触数据库的同学常常会产生一系列疑问：“MySQL 不是开源免费的吗？为什么官网下载列表里有那么多五花八门的产品线？”“日常开发究竟该选哪一个版本？”以及“在实际学习与架构演进中，如何让最新的 MySQL 8.0 与行业长期广泛应用的 5.7 版本在同一台操作系统中和平共处、互不干扰？”

本篇将从 MySQL 官方的产品版本谱系出发，详解社区版的选型逻辑，并以离线 MSI 安装包为主线，完整还原 MySQL 8.0 的自定义定制安装、核心路径规划、安全认证算法选择、系统服务配置，以及 5.7 版本在同一台机器上的端口隔离与双实例共存方案。

### 1. MySQL 官方版本分类与选型策略

访问 MySQL 官方网站（`mysql.com`）的下载频道，系统通常会呈现若干不同的产品分支。总体而言，MySQL 官方主要维护以下四大版本形态：

```text
+-------------------------------------------------------------------------+
|                        MySQL 官方软件版本形态体系                       |
+-------------------------------------------------------------------------+
| 1. 社区版 (MySQL Community Server)                                     |
|    - 遵循 GPL 开源协议，代码完全开放，全球免费下载使用                  |
|    - 适用于个人学习、中小型互联网公司、初创团队及通用业务系统           |
|                                                                         |
| 2. 商业/企业版 (MySQL Enterprise Edition)                              |
|    - 商业闭源授权，需向 Oracle 支付服务年费或商业许可                  |
|    - 提供企业级线程池、高级监控、数据脱敏、热备份与官方专属技术支持     |
|                                                                         |
```

#### 2.2 安装包格式深度选型（MSI vs ZIP）

在 Windows 下载界面中，通常会提供两种物理封装格式供用户下载：

1. **ZIP 压缩版（免安装版 / Archive）**：
   下载后仅包含解压后的二进制文件包。该版本不包含自动化配置向导，需要开发者手动编写 `my.ini` 文本文件、手动在命令行执行 `mysqld --initialize` 进行数据目录初始化、手动执行 `mysqld --install` 注册系统服务。对于初学者，极易在文本编码、服务注册权限与密码生成等环节出现重大障碍；
2. **MSI 安装包版（MySQL Installer）**：
   具备成熟的 Windows Installer 图形化引导机制，将软件文件的拷贝、目录结构权限分配、多实例服务注册、初始化向导与密码安全策略集成为一条流水线，大幅提升了环境搭建的鲁棒性。

> **结论**：本流程全面采用 **MSI 格式（Windows x86, 32-bit, MSI Installer）**。虽然其标注为 32-bit，但安装器本身会自动根据宿主操作系统位数下载与装配 64 位的 MySQL Server 引擎。

在 MSI 列表中，官方通常提供两个下载项：
- 体积仅十几兆至二十几兆的在线安装包（Web Community）：仅包含轻量级引导壳，安装过程中必须通过网络动态回源拉取组件，网络波动极易导致超时中断；
- 体积 400MB 左右的**完整离线安装包（mysql-installer-community-*.msi）**：内嵌所有常用组件的完整二进制文件，断网环境下亦可独立流畅完成安装。

> **提示**：若需要下载非最新版本的历史镜像（如 `8.0.26` 或 `5.7.34`），在 Community Server 页面点击 **【Archives】（档案库）** 标签页，在下拉列表中即可精准定位历史小版本。
> 点击下载时，官方页面会弹出 Oracle 账号登录界面，直接点击下方的 **`No thanks, just start my download.`** 链接，即可免登录直接触发本地下载。

#### 3.2 物理路径规划与中文路径避坑红线

将目标组件移入右侧后，必须点击右下方出现的 **【Advanced Options】（高级选项）** 超链接，弹出路径规划对话框：

1. **Install Directory（软件安装目录）**：
   指定 DBMS 程序二进制文件的存放位置。推荐规划在独立的开发工具分区，例如：
   `D:\develop_tools\MySQL\MySQL Server 8.0`
2. **Data Directory（数据存储目录）**：
   指定业务数据表空间（`data/`）与配置文件（`my.ini`）的存放位置。推荐保持其系统规划，例如：
   `C:\ProgramData\MySQL\MySQL Server 8.0`

> **易错点（绝不可踩的红线）**：
> 无论是程序安装路径还是数据存储路径，**全路径中绝对严禁包含任何中文字符、特殊符号以及全角/半角空格**！
> 底层 `mysqld` 进程在加载动态链接库与表空间元数据时，部分底层 C++ 库对 UTF-8 与 Windows 本地 ANSI 路径转码存在缺陷，一旦路径出现中文或空格，会导致服务初始化直接崩溃或后续数据读写异常中断。

确认路径后点击 Next，在弹出的路径已存在确认对话框中选择确认。随后进入 Execute 界面，点击【Execute】执行文件的本地写入。

#### 3.3 服务器类型与内存拓扑配置

安装文件解包完成后，向导自动推进至 **Type and Networking（类型与网络）** 配置环节。

##### 1. Server Configuration Type（配置类型）
下拉框包含三类预设模式：
- **Development Computer（开发机模式，默认推荐）**：专为本地个人开发设计，MySQL 仅分配最低限度的系统物理内存（如 InnoDB 缓冲池等参数设定较小），确保其他 IDE 与本地应用流畅运行；
- **Server Computer（通用服务器模式）**：适用于宿主机同时部署了 Web 应用服务与数据库服务的场景，占用中等物理内存；
- **Dedicated Computer（专属数据库服务器模式）**：系统假定该机器专门用于运行 MySQL，服务进程将竭尽全力榨取操作系统的全部内存与 CPU 资源。

在个人电脑上搭建学习环境，必须保持默认的 **【Development Computer】**。

##### 2. Connectivity（网络通信）
勾选 **Open Firewall port for network access** 并启用 **TCP/IP** 协议。
默认端口（Port）设定为 **`3306`**，X Protocol 端口设定为 `33060`，保持默认即可。

#### 3.4 认证算法选型与密码安全策略

在 **Authentication Method（认证机制）** 界面中，MySQL 8.0 引入了划时代的安全变更，提供两个单选项：

```text
(o) Use Strong Password Encryption for Authentication (RECOMMENDED)
    -> 基于 caching_sha2_password 插件 (SHA-256 散列，8.0 原生推荐)
( ) Use Legacy Authentication Method (Retain MySQL 5.x Compatibility)
    -> 基于 mysql_native_password 插件 (早期弱散列算法，向下兼容 5.x)
```

- **Strong Password Encryption（推荐采用）**：采用基于 SHA-256 的散列加密体系，具备极高抗碰撞能力与通信安全性能，是 8.0 官方强力推荐的现代安全机制；
- **Legacy Authentication**：沿用旧有的 SHA-1 阶段散列逻辑。

> **提示**：选中推荐的强加密算法后，如果未来使用较老版本的第三方客户端管理软件（如旧版 SQLyog 或 Navicat 11）连接 MySQL 8.0，可能会由于客户端尚未集成 `caching_sha2_password` 动态握手模块而弹出 `Client does not support authentication protocol requested by server` 或 `2058 Plugin caching_sha2_password could not be loaded` 报错。该问题可通过升级客户端驱动或在数据库中临时修改用户插件解决，但在安装阶段，我们遵循 8.0 的最佳安全实践，直接选定第一项。

#### 3.5 根用户账户配置与服务项自启动

1. **Accounts and Roles（账户凭据）**：
   界面要求输入 `MySQL Root Password`（Root 管理员密码）与确认密码。
   输入预设的管理口令（例如 `abc123`）。由于设置的密码长度较短，系统可能会提示密码强度为 `Weak`，本地学习环境可直接忽略该告警。
   *在此界面暂不额外添加普通开发者账号，保持系统初始纯净状态*；
2. **Windows Service（Windows 系统服务注册）**：
   - 勾选 `Configure MySQL Server as a Windows Service`；
   - **Windows Service Name（服务名）**：默认设定为 **`MySQL80`**；
   - 勾选 `Start the MySQL Server at System Startup`（随系统开机自动启动）。
     开启自启保证了每次开启电脑后无需手动寻找后台进程，即可随时在命令行发起数据库连接。

#### 3.6 执行配置与安装成果检验

点击 Next 推进至 **Apply Configuration（应用配置）** 步骤，点击【Execute】。
向导将按序执行以下底层操作：
- 依据所选参数生成 `C:\ProgramData\MySQL\MySQL Server 8.0\my.ini` 配置文件；
- 调用 `mysqld.exe --initialize` 创建底层系统库（`mysql`、`sys` 等）的表空间；
- 将 `MySQL80` 注册至 Windows 系统服务，并触发服务首次启动；
- 应用密码安全规则与 root 权限表。

所有条目显示绿色勾选后，点击【Finish】完成安装。

此时检查物理磁盘：
- `D:\develop_tools\MySQL\MySQL Server 8.0\` 下已被二进制程序填满；
- `C:\ProgramData\MySQL\MySQL Server 8.0\` 下已自动生成 `data/` 目录与 `my.ini`。

### 4. 全局环境变量 Path 的配置与命令行验证

虽然此时 MySQL 8.0 已在后台成功运行，但在新开启的 cmd 窗口中输入 `mysql --version`，系统依然会抛出错误：`'mysql' 不是内部或外部命令，也不是可运行的程序或批处理文件。`

这是因为操作系统的执行寻址机制并不知道 `mysql.exe` 存放在哪个分区目录中。

```text
[打开系统高级属性] -> [环境变量] -> [系统变量中的 Path] -> [新建条目]
追加: D:\develop_tools\MySQL\MySQL Server 8.0\bin
```

3. 点击【新建】，将上述路径完整粘贴进去。可将其上移至开发工具集中的合适层级；
4. 连续点击三次【确定】关闭所有属性对话框。

> **易错点**：环境变量修改保存后，**原先已经开启的终端窗口不会自动加载新的系统环境**。必须彻底关闭旧的 cmd 或 PowerShell 窗口，**重新开启一个全新的命令行终端**。

在新终端中执行验证：

```bash

# 本地无缝登录
```

终端成功输出 `mysql>` 交互提示符，代表 MySQL 8.0 的安装、配置与环境变量注入已达成闭环。

### 5. MySQL 5.7 与 8.0 多实例共存实操规程

在单台计算机上部署两个完全不同代际的 MySQL 数据库，在架构上被称为**单机多实例共存**。

#### 5.1 多实例共存的底层技术约束

要让两个独立的 MySQL 守护进程在同一台 Windows 机器上同时平稳运行，必须打破四个维度的资源竞争：

| 资源竞争维度 | MySQL 8.0 实例分配 | MySQL 5.7 实例分配 | 核心防冲突原则 |
| :--- | :--- | :--- | :--- |
| **网络监听端口 (Port)** | `3306` | **`13306`** | 端口范围 0~65535，两个进程严禁监听同一个网络端口。 |
| **Windows 服务标识 (Service Name)** | `MySQL80` | **`MySQL57`** | 系统注册表服务项严禁同名。 |
| **软件安装目录 (Binary Dir)** | `D:\...\MySQL Server 8.0` | **`D:\...\MySQL Server 5.7`** | 避免不同版本的可执行程序与 DLL 互相覆盖。 |
| **数据持久化目录 (Data Dir)** | `C:\...\MySQL Server 8.0` | **`C:\...\MySQL Server 5.7`** | 表空间物理文件格式不同，严禁共用同一个 data 目录。 |

#### 5.2 启动 5.7 离线安装向导

运行 `mysql-installer-community-5.7.34.msi` 安装包。
由于本机已安装了 MySQL Installer 运行时环境，向导打开后会提示 `Welcome Back!`（欢迎回来），并可能检测到 8.0 的次级升级包。
在弹出的 Upgrade 提示窗口中，直接点击 **【Cancel】取消升级**，随后在产品列表界面点击右侧的 **【Add...】** 按钮进入组件追加模式。

#### 5.3 5.7 组件选择与隔离路径指定

1. 展开产品树：`MySQL Servers` -> `MySQL Server` -> `MySQL Server 5.7` -> 勾选 64 位版本并添加至右侧；
2. 选中该组件，点击右下方的 **【Advanced Options】**；
3. 将路径重新指定为专属于 5.7 的隔离目录：
   - 安装目录：`D:\develop_tools\MySQL\MySQL Server 5.7\`
   - 数据目录：`C:\ProgramData\MySQL\MySQL Server 5.7\`
4. 确认后推进至 Execute 阶段，完成 5.7 二进制文件的解压落盘。

#### 5.4 规避端口与服务名冲突的关键配置

进入 5.7 的配置向导后，有两处决定成败的核心修改：

1. **Networking 端口修改（破除端口冲突）**：
   在网络配置页中，向导会立即检测到端口 3306 已被 `MySQL80` 占用并在界面标红告警（`Port 3306 is already in use`）。
   必须手动将端口修改为一个未被占用的端口号，例如前置加 1 修改为 **`13306`**；
2. **Windows Service Name 修改（破除服务项冲突）**：
   在服务注册页中，将默认的服务名改为 **`MySQL57`**，同样保持随开机自启动勾选；
3. **账户密码设定**：
   5.7 版本没有 8.0 的双重加密选择界面（其默认原生采用传统的 `mysql_native_password`）。直接为 5.7 的 root 账户设定密码为 `abc123`；
4. 点击【Execute】完成配置生成与服务挂载。

此时打开 Windows 服务管理列表（`services.msc`），可以同时观察到两个并驾齐驱的运行中服务：
- `MySQL80`（对应 8.0 内核，监听 3306）
- `MySQL57`（对应 5.7 内核，监听 13306）

```text
+-------------------------------------------------------------------------+
|                    Windows 计算机管理: 服务列表快照                     |
+-------------------------------------------------------------------------+
|  服务名称     | 描述                      | 状态     | 启动类型  | 端口  |
+--------------+---------------------------+----------+-----------+-------+
|  MySQL57     | MySQL Server 5.7 Instance | 正在运行 | 自动      | 13306 |
|  MySQL80     | MySQL Server 8.0 Instance | 正在运行 | 自动      | 3306  |
+-------------------------------------------------------------------------+
```

#### 5.5 环境变量共存原则与精准会话连接

面对双版本的共存，初学者极易产生一个认知误区：“我能不能把 5.7 的 bin 路径也加进 Path 环境变量？”

> **易错点**：**系统 Path 变量中只能保留一个主版本的 bin 目录路径（保持指向 8.0）**。
> 操作系统扫描 Path 是从上至下单向匹配的，一旦排在前面的路径命中了 `mysql.exe`，后续路径就会被彻底短路截断。若盲目配置两个，只会导致难以捉摸的版本错乱。

由于 8.0 的客户端命令工具是完全向下兼容 5.7 协议的，我们完全可以直接使用 8.0 的 `mysql` 客户端，通过**显式传递主机名与端口参数**来任意切换并精准连接到不同的数据库实例！

##### 1. 登录连接 8.0 实例
在终端中执行（指定端口 3306）：

```bash
# 显式指定连接本机的 3306 端口实例
mysql -h localhost -P 3306 -u root -pabc123
```

进入后通过内建元数据函数查询当前会话的物理版本：

```sql
SELECT VERSION();
```
输出结果确认指向 `8.0.26`。执行 `QUIT;` 退出会话。

##### 2. 登录连接 5.7 实例
在同一个终端中执行（指定端口 13306）：

```bash
# 显式指定连接本机的 13306 端口实例
mysql -h localhost -P 13306 -u root -pabc123
```

执行版本核验：

```sql
SELECT VERSION();
```
终端清晰返回 `5.7.34`。至此，一台机器内部同时承载最新 8.0 与经典 5.7 的数据库矩阵已全面架设完毕，为后续全方位的深度特性比对与 SQL 编程打下了坚实无虞的基础。

## 第 3 章：08-MySQL安装常见问题_服务启动与用户登录
> 对应分集：P08 | 原始标题：《08-MySQL安装常见问题_服务启动与用户登录》

在完成了 MySQL 8.0 与 5.7 双版本的标准安装之后，绝不意味着每位开发者的实际落地过程都能一帆风顺。现实中，因 Windows 操作系统版本各异、运行库补丁缺失、Ghost 精简版系统破坏底层组件，或者历史版本残留未净，初学者在安装阶段极易遭遇各种意料之外的报错。

面对层出不穷的环境故障，不能靠盲目重启或胡乱点击来碰运气。本篇将系统梳理两类高频安装故障的诱因与排查路径，提炼出排查安装死锁的通用法则，并深入剖析 Windows 服务控制的权限机理，最后全景解构 MySQL 客户端连接的完整参数矩阵与安全实践。

### 1. 常见安装故障分类与根治排查体系

根据故障发生的前置条件，MySQL 安装过程中的异常可精准划分为两大阵营：**全新裸机初次安装的系统环境缺陷**，以及**旧版本卸载重装残留导致的配置污染**。

```text
+-------------------------------------------------------------------------+
|                        MySQL 安装故障根因诊断树                         |
+-------------------------------------------------------------------------+
| [初次安装故障: 底层依赖缺失]                                            |
|   |-- 现象 1: 缺少 .NET Framework 或版本过低 -> 补丁升级至 4.5+         |
|   |-- 现象 2: 缺少 Visual C++ Redistributable -> 补齐 MSVCR/VCRUNTIME   |
|   \-- 现象 3: 缺少特定系统 DLL 文件 -> 启用 Windows Update 修复补丁     |
|                                                                         |
| [二次重装故障: 历史脏残留污染]                                          |
|   |-- 残留 1: 暴力删除目录导致注册表损坏 -> 依赖控制面板规范卸载        |
|   |-- 残留 2: ProgramData/MySQL 数据未清空 -> 密码冲突死锁，需手动拔除  |
|   \-- 残留 3: Windows 服务名或端口冲突 -> 注册表强力注销并重启释放句柄  |
+-------------------------------------------------------------------------+
```

> **图 1-1 说明**：系统性排查必须先区分机器是否具备 MySQL“前科”，针对性实施运行库补齐或残留剥除。

#### 1.1 初次安装故障：操作系统底层运行库缺失

在一台从未安装过 MySQL 的机器上运行安装程序却遭遇报错，根本原因在于宿主操作系统缺乏支撑安装器运行的底层运行库。

##### 1. 缺少 .NET Framework 平台支持
- **故障现象**：双击 MSI 安装包后，向导界面尚未渲染便直接崩溃退出，或弹出系统弹窗提示需要安装更高版本的 `.NET Framework` 框架；
- **排查机理**：MySQL Installer 客户端向导采用 .NET 技术栈构建，强依赖宿主环境的 CLR 运行时环境（通常要求 .NET Framework 4.5.2 及以上版本）；
- **根治方案**：访问微软官方网站或通过可信镜像，下载安装最新版的 `.NET Framework` 独立安装程序。安装完毕后重新引导 MySQL 安装向导即可顺利进入界面。

##### 2. 缺少 Visual C++ Redistributable（VC++ 运行库）
- **故障现象**：安装进度推进至服务端二进制解包或执行服务初始化阶段时，系统抛出缺少 `MSVCR120.dll`、`VCRUNTIME140.dll` 或提示 `Visual Studio Redistributable is required`；
- **排查机理**：MySQL Server 底层核心引擎全部基于 C/C++ 语言编写，编译时依赖特定版本的 Visual C++ 动态链接库；
- **根治方案**：保持网络畅通，官方在线安装器通常会尝试自动回源拉取 VC++ 依赖；若处于离线内网环境，可预先下载并安装 `Visual C++ Redistributable 2015-2022`（包含 x86 与 x64 运行时）。

##### 3. 操作系统底层特定 DLL 缺失与精简版系统缺陷
- **故障现象**：部分使用二次封装精简系统（如某些深度优化的 Ghost 系统）的用户，安装时常遭遇各种未知动态库链接缺失；
- **根治方案**：打开 Windows【设置】->【更新和安全】，执行系统的全量累积更新；或利用主流系统维护工具的“系统运行库/丢失 DLL 一键修复”功能，将缺失的系统级底层 API 组件补全。

#### 1.2 二次重装故障：历史状态残留与配置死锁

对于曾经安装过 MySQL、卸载后重新部署遭遇报错的场景，99% 的问题均由“卸载不干净”引发。

##### 1. 暴力删除文件夹导致的控制面板与 MSI 索引损坏
严禁在文件资源管理器中直接右键删除 `C:\Program Files\MySQL` 或自定义安装路径。这种操作仅删除了上层磁盘文件，而 Windows 安装数据库中的 MSI 组件 GUID、COM 注册项依然留存在操作系统底层。当新安装包试图在相同 GUID 位置注册时，将直接抛出严重逻辑冲突。必须通过操作系统【控制面板】执行合规卸载。

##### 2. ProgramData 数据目录未清空引发的密码冲突死锁
这是重装阶段最高频的致命陷阱。如前所述，控制面板卸载为了保护用户数据安全，默认绝对不删除 `C:\ProgramData\MySQL` 目录。
- 若初学者直接重新安装，向导检测到 `data/` 目录中已存在旧系统表，会假定用户是在执行实例恢复；
- 在配置向导最后一步校验 root 权限时，安装程序要求输入的 root 密码**必须与当初创建该 data 目录时的旧密码完全吻合**；
- 若开发者早已遗忘旧密码，且在此处输入了新的密码，执行配置时在“Starting Service”或“Applying Security Settings”环节将直接标红报错（`Configuration failed`），陷入彻底死锁。

> **结论**：若意图重新部署全新环境，**在运行新安装包前，必须手动打开 `C:\ProgramData\MySQL` 并将其彻底清空**。

##### 3. 服务项与注册表残留
若提示服务名已被占用，通过 `regedit` 清除 `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\` 下对应的服务项键值，并在清理完毕后**重启计算机**。重启能够使操作系统内核彻底注销无主的驱动句柄与端口绑定，确保重装流程顺畅推进。

### 2. Windows 操作系统下 MySQL 服务的启停控制

在客户端发起任何 SQL 交互之前，必须确保作为服务器后台守护进程的 `mysqld.exe` 处于健康运行状态。

客户端与数据库服务端的连接，本质是基于网络协议（如本地回环的 TCP/IP）进行的跨进程通信。类比于日常生活中的在线服务：若用户在深夜尝试访问某电商网站，恰逢机房服务器在执行硬件割接或维护性断电，无论用户本地的客户端网络性能多么优异，都必然遭遇连接超时或拒绝连接。

```text
[本地客户端 mysql.exe] 
       |
       | 发起 TCP 3306 端口连接握手
       v
[目标操作系统后台守护进程 mysqld.exe (MySQL80 服务)]
  - 状态: [正在运行]  ===> 握手成功，进入验证环节
  - 状态: [已停止]    ===> 操作系统直接 RST 拒绝，报错 ERROR 2003
```

在 Windows 操作系统中，服务进程的运维管理主要涵盖图形化管理与命令行控制两种手段。

#### 2.1 图形化服务控制台

1. 按下快捷键 `Win + R`，输入 `services.msc` 打开 Windows 服务管理控制台；
2. 按键盘字母 `M` 快速索引至目标服务项（如 `MySQL80` 或 `MySQL57`）；
3. 右键点击目标服务，可自由执行【启动】、【停止】或【重新启动】；
4. 右键进入【属性】对话框，可对【启动类型】进行定制：
   - **自动（默认推荐）**：随系统引导开机自启，保障开发时开箱即用；
   - **手动**：开机不启动，仅在用户需要进行数据库开发时，由人工主动唤醒，适合对开机速度有严苛要求的场景。

#### 2.2 命令行指令与系统权限陷阱

在企业级运维中，必须熟练掌握基于命令行的启停控制（为后续 Linux 环境下的服务运维打下基石）。

Windows 下控制系统服务的标准命令语法为：

```powershell
# 启动指定名称的服务
net start <服务名称>

# 停止指定名称的服务
net stop <服务名称>
```

##### 1. 权限不足故障场景复现
许多初学者直接按下 `Win + R` 输入 `cmd` 打开普通用户终端，并执行：

```powershell
net stop MySQL80
```

系统将立即无情地中断执行并返回错误：
`发生系统错误 5。拒绝访问。`

> **易错点**：Windows 的后台系统服务属于操作系统底层的全局特权资源。普通用户权限开启的命令提示符只具备用户级操作权限，操作系统安全机制（UAC）直接截断了对内核级服务的操控请求。

##### 2. 管理员模式特权执行
正确操作流程：
1. 点击 Windows 开始菜单或搜索栏，键入 `cmd`；
2. 在匹配出的【命令提示符】上点击右键，选择 **【以管理员身份运行】**；
3. 在弹出的管理员终端中执行启停指令：

```powershell
# 管理员权限下停止 8.0 服务
C:\Windows\system32> net stop MySQL80
MySQL80 服务正在停止.
MySQL80 服务已成功停止。

# 验证服务停止时的连接表现
C:\Windows\system32> mysql -u root -pabc123
ERROR 2003 (HY000): Can't connect to MySQL server on 'localhost:3306' (10061)

# 管理员权限下重新启动服务
C:\Windows\system32> net start MySQL80
MySQL80 服务正在启动 .
MySQL80 服务已经启动成功。
```

当服务重新拉起后，底层的 3306 网络端口恢复监听，客户端方可重新建立会话连接。

### 3. MySQL 客户端连接工具与参数矩阵规范

MySQL 服务就绪后，可以通过多种客户端接入渠道访问数据。

#### 3.1 客户端生态划分

1. **操作系统原生命令行工具**：
   在任何配妥环境变量的终端（cmd、PowerShell、Git Bash）中直接使用 `mysql.exe` 命令，轻量高效，是开发排障的第一线武器；
2. **MySQL 自带命令行客户端（MySQL Command Line Client）**：
   安装时自动注册在开始菜单中。其本质是一个预置了特定参数的快捷批处理方式，默认直接以本机 root 身份运行，启动后跳过参数录入环节，直接等待输入密码；
3. **第三方专业图形化协同软件**：
   在后续深入 SQL 开发时，将采用 Navicat、SQLyog、DataGrip、DBeaver 或 MySQL Workbench 等可视化 IDE。图形化工具提供了结构树导航、代码高亮提示与数据网格编辑能力，但其底层依然严格封装了本节所述的网络连接参数。

#### 3.2 客户端连接核心参数矩阵

在命令行环境中执行 `mysql` 命令时，其完整连接语法结构遵循标准的参数矩阵体系：

```bash
mysql [选项参数]
```

各核心选项参数的定义与工程规范如下表所示：

| 参数缩写 | 参数全称 | 参数作用与数据规范 | 缺省默认值 |
| :--- | :--- | :--- | :--- |
| **`-h`** | `--host` | 目标数据库服务器的 IP 地址或网络主机域名（如 `127.0.0.1`、`192.168.1.100`） | `localhost` |
| **`-P`** (大写) | `--port` | 目标数据库实例所监听的 TCP 网络通信端口号（有效范围 0~65535） | `3306` |
| **`-u`** | `--user` | 用于通过身份认证的数据库账户名（如 `root`） | 操作系统当前登录用户名 |
| **`-p`** (小写) | `--password` | 用于身份鉴权的访问口令（安全规范详见下文） | 空密码（无密码尝试） |

```text
mysql -h <主机IP> -P <端口号> -u <用户名> -p[密码]
       |          |          |          |
       | 默认本机 | 默认3306 | 必填身份 | 严禁明文
```

> **提示**：参数先后顺序在命令行解析器中并无硬性限制。习惯上，通常按照主机、端口、用户、密码的顺序编排，将密码选项固定放置于命令行末尾。

#### 3.3 密码录入的安全红线与排坑

在配置 `-p` 选项时，存在极其关键的安全规范与格式细节。

##### 1. 明文录入引发的安全告警与审计风险
若直接将密码明文拼装在命令行中执行：

```bash
mysql -u root -pabc123
```

终端在建立连接的同时，必然会抛出一行严重的安全性告警：
`mysql: [Warning] Using a password on the command line interface can be insecure.`

其核心危害体现在：
- 任何路过屏幕的人都能肉眼直视密码内容；
- 操作系统的历史命令记录器（如 Bash 历史、PowerShell 日志）会将包含明文密码的完整命令持久化存入磁盘日志，极易引发安全合规事故。

##### 2. 空格与分号引发的密码畸变陷阱
- **空格陷阱**：在 `-u` 与用户名之间、`-h` 与主机之间允许包含空格（如 `-u root` 与 `-uroot` 等价）。但在 `-p` 选项上，**若试图在 `-p` 后面写明文密码，中间绝对严禁包含任何空格**！若误敲为 `-p abc123`，命令行解析器会将空格之后的 `abc123` 误解析为“目标连接的数据库名称”，同时认为当前未提供密码，导致认证彻底失败；
- **分号陷阱**：受 SQL 语句以分号结尾的固有习惯影响，初学者极易在输入命令行参数的末尾随手敲上一个分号（如 `-pabc123;`）。此时，分号会被当作密码的最后一个物理字符一并传递给认证引擎，直接导致密码错误拒绝登录。

##### 3. 最佳安全实践：换行暗文交互录入
最严谨、安全的登录方式是仅提供 `-p` 标记并直接敲击回车，在系统唤起的独立提示行中以无回显的暗文模式输入口令：

```bash
C:\Users\Admin> mysql -h localhost -P 3306 -u root -p
Enter password: ******
Welcome to the MySQL monitor.  Commands end with ; or \g.
Your MySQL connection id is 12
Server version: 8.0.26 MySQL Community Server - GPL
...
mysql>
```

此种模式下，密码不会被任何屏幕窥视或命令历史审计记录，且避免了一切空格与特殊字符的转义干扰。

#### 3.4 参数缺省机制与双版本实例切换机制

在日常开发中，我们频繁使用极简的快捷命令：

```bash
mysql -u root -p
```

该命令之所以能准确登录 MySQL 8.0 实例，是因为系统的底层缺省补全机制：
1. 未声明 `-h` 时，系统自动回退补齐为 `-h localhost`；
2. 未声明 `-P` 时，系统自动回退补齐为 `-P 3306`；
3. 执行调用的 `mysql.exe` 二进制文件来自环境变量 Path 中最优先匹配的 8.0 bin 目录。

而当需要明确登入上一讲共同部署的 **MySQL 5.7 兼容实例** 时，必须通过打破缺省值的方式进行精准路由：

```bash
# 显式重写端口参数，将通信管道对准 5.7 实例监听的 13306 端口
mysql -h localhost -P 13306 -u root -p
```

回车并在提示符后键入密码，连接成功后执行会话信息核实：

```sql
-- 查询当前物理引擎的版本号
SELECT VERSION();
```

返回输出为 `5.7.34`，证明流量已精准接入 5.7 守护进程。

最后，当完成数据库交互需要断开网络链路时，在 `mysql>` 提示符下执行退出指令：

```sql
-- 优雅断开连接并退出客户端交互 (以下任意指令皆可)
QUIT;
EXIT;
```

终端屏幕打印 `Bye` 并退回操作系统标准命令行提示符。至此，从底层环境排障、后台系统服务治理，到终端客户端多参数全场景连接的完整工程闭环全部构建完成。

## 第 4 章：09-MySQL的使用演示_MySQL5.7字符集的设置
> 对应分集：P09 | 原始标题：《09-MySQL的使用演示_MySQL5.7字符集的设置》

前面几讲我们把 MySQL 5.7 和 8.0 的双版本安装、环境配置与多端口服务启动都讲完了。许多同学在这个阶段最容易犯怵——前面光顾着装环境、敲各种配置命令，生怕哪个步骤不对报错。既然两个版本的服务都已经成功跑起来了，我们先抛开抽象的理论，打开命令行窗口连上去，亲手敲几行命令，真刀真枪地感受一下：当我们连接上 MySQL 数据库服务器之后，究竟能做哪些事。

在这一讲的演示中，我们先登录 5.7 版本（端口 13306），接着在里面建库、建表、插入数据。在这个极其普通的操作流程中，你会当场撞见一个困扰无数初学者的经典痛点——中文数据写入报错。随后我们将层层排查其底层的字符集体系，修改 `my.ini` 配置文件，理清历史旧表的继承陷阱，并在最后切换到 8.0 版本（端口 3306）做比对，看清楚高版本到底为我们省去了哪些运维成本。

### 1. 数据库基础操作与系统预置数据库

#### 1.1 连接验证与系统自带的四个数据库

我们先在终端中调出命令行窗口，登录此前配置在 13306 端口上的 MySQL 5.7 实例。因为本机测试默认就是连接本机的服务，参数 `-h localhost` 可以省略，但由于我们本机跑了两个不同端口的实例，大写的 `-P`（Port）参数绝不能漏：

```bash
mysql -u root -P 13306 -p
```

输入密码回车后，终端显示 `mysql>` 提示符，说明客户端已经与数据库服务器建立了连接。此时我们输入最基础的查看命令：

```sql
show databases;
```

> **易错点**：这里的 `databases` 必须是复数形式，末尾带有 `s`，且 SQL 语句必须以半角分号 `;` 结尾。

执行之后，终端会回显 4 个默认存在的系统数据库：

```text
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
4 rows in set (0.00 sec)
```

这 4 个数据库是 MySQL 服务安装初始化后系统自带的内部资产。很多同学一看到这么多生僻英文库名就慌，其实现阶段不需要去深究里面的每一张表，我们先清楚它们各自承担的分工职责：

| 系统数据库名称 | 核心职责与存储内容说明 | 开发运维关注阶段 |
| :--- | :--- | :--- |
| `information_schema` | 存储数据库服务器的元数据（元信息），包括所有数据库名、表名、列信息、数据类型及访问权限等。只读视图。 | 进阶查询、元数据逆向分析 |
| `mysql` | 存储 MySQL 核心系统运行时所需的信息，如用户账户权限表、系统变量设置、时区信息等。 | 权限管理、底层安全审计 |
| `performance_schema` | 收集并存储 MySQL 服务运行时的底层性能指标、锁事件、内存消耗及线程状态。 | 高级篇性能调优、锁分析 |
| `sys` | 将 `performance_schema` 和 `information_schema` 的底层复杂度打包封装成易读的视图，便于管理员直接诊断。 | 慢查询排查、运维监控告警 |

在现阶段的基础实操中，我们严禁随意删除或手动修改这 4 个库里的结构与数据。到了课程的高级篇和性能优化篇，我们会频繁调取里面的视图来诊断锁争用和性能瓶颈。

#### 1.2 库表创建与基础增删查操作流程

熟悉了预置数据库之后，我们在 5.7 实例中自己创建一个全新的测试数据库：

```sql
create database dbtest1;
```

创建完毕后，通过方向键向上翻出历史命令，再次执行 `show databases;`，可以看到结果集中已经包含了新创建的 `dbtest1`。

有了数据库，接下来自然是要建表。数据库最主要的核心存储单元就是表（Table）。我们尝试创建一张员工信息表 `employees`，里面包含两个字段：整数类型的员工工号 `id`，以及字符串类型的员工姓名 `name`：

```sql
create table employees (
    id int,
    name varchar(15)
);
```

敲下回车，命令行立即返回了错误：

```text
ERROR 1046 (3D000): No database selected
```

> **易错点**：MySQL 实例内部可以托管成百上千个独立的数据库。直接执行 `create table` 时，客户端并没有告知服务器当前到底要在哪一个数据库的作用域下建表，因此系统会抛出 `No database selected`。

在进行建表或后续的增删改查之前，必须使用 `use` 命令显式切换当前会话的工作数据库上下文：

```sql
use dbtest1;
```

终端回显 `Database changed`，表示当前连接上下文已切换至 `dbtest1`。此时执行 `show tables;`，结果显示 `Empty set`，表明库内尚无表对象。我们重新调出刚才的建表语句执行：

```sql
create table employees (
    id int,
    name varchar(15)
);
```

执行成功后再次输入 `show tables;`，终端便清晰展示出刚创建的 `employees` 表。为了确认表内是否有数据，我们使用全表查询命令：

```sql
select * from employees;
```

查询结果显示 `Empty set`。接下来向其中写入测试记录：

```sql
insert into employees values(1001, 'Tom');
insert into employees values(1002, 'shk-start');
```

执行后再次查询全表：

```sql
select * from employees;
```

控制台正确输出了包含两行记录的表格：

```text
+------+-----------+
| id   | name      |
+------+-----------+
| 1001 | Tom       |
| 1002 | shk-start |
+------+-----------+
2 rows in set (0.00 sec)
```

至此，纯英文字符数据的增查流程一切正常。如果我们在 8.0 实例中做同样的操作，步骤与现象也是完全一致的。然而，只要我们往表里写入一个中文汉字，两个版本的行为就会立即产生分歧。

### 2. MySQL 5.7 中文乱码根源与字符集机制

#### 2.1 中文插入报错现象与 latin1 历史渊源

我们在刚才的 5.7 实例中继续插入第 3 条员工数据，工号为 1003，姓名改为中文汉字 `'杰瑞'`：

```sql
insert into employees values(1003, '杰瑞');
```

按下回车，终端瞬间跳出报错：

```text
ERROR 1366 (HY000): Incorrect string value: '\xBD\xDC\xC8\xF0' for column 'name' at row 1
```

执行 `select * from employees;` 进行检查，发现第 3 条数据根本没有写进表中。为什么英文的 `Tom` 和 `shk-start` 能正常插入，而换成汉字 `'杰瑞'` 就会报字符值不正确（Incorrect string value）？

为了找到根源，我们执行表结构元数据查看命令：

```sql
show create table employees;
```

终端打印出的建表定义中，末尾赫然显示着默认字符集定义：

```sql
CREATE TABLE `employees` (
  `id` int(11) DEFAULT NULL,
  `name` varchar(15) DEFAULT NULL
) ENGINE=InnoDB DEFAULT CHARSET=latin1;
```

这张表的字符集竟然被默认设置成了 `latin1`。

> **定义**：`latin1` 字符集（即 ISO-8859-1）是单字节编码，最多只能表示 256 个字符，主要涵盖西欧语言中使用的拉丁字母。它在底层根本没有收录中文字符的编码位，因此任何汉字在映射为 `latin1` 字节流时都会因无法解析而直接报错。

为什么 MySQL 会默认采用这么冷门的一个字符集，而不是我们习惯的 ASCII 或通用多语言编码？回顾 MySQL 的发展史，MySQL 最初是由瑞典的 MySQL AB 公司自主研发的。瑞典地处欧洲，其本地语言环境使用的就是西欧拉丁字符集，因此在早期版本中，开发者很自然地将单字节的 `latin1` 设为了系统的缺省字符集。

中文字符要被计算机正确识别与存储，必须使用多字节的通用字符集编码，最典型的就是 `utf8`。`utf8` 是一套变长编码标准，它不仅完整收录了中文字符，还囊括了日文、韩文、欧洲各国文字以及美式英语对应的二进制编码映射。正因为当前表所继承的字符集是 `latin1`，才直接导致了中文写入被系统拒之门外。

我们进一步查看数据库自身的创建语句：

```sql
show create database dbtest1;
```

返回信息同样显示：

```sql
CREATE DATABASE `dbtest1` /*!40100 DEFAULT CHARACTER SET latin1 */
```

这证明我们在建表时没有显式指定字符集，表就会默认继承库的字符集；而建库时没有显式指定字符集，库就会默认继承更上一层——数据库服务端的默认字符集。

#### 2.2 系统字符集与比较规则变量探测

为了摸清整套系统的默认编码链条，我们在 5.7 实例中查询当前所有与字符集相关的系统环境变量：

```sql
show variables like 'character%';
```

> **语法说明**：`show variables` 用于查看服务器当前生效的环境变量；`like 'character%'` 中的 `%` 是 SQL 中的通配符，表示匹配以 `character` 开头的任意一个到多个字符。

执行后，终端回显出一组核心系统变量：

```text
+--------------------------+-----------------------------------+
| Variable_name            | Value                             |
+--------------------------+-----------------------------------+
| character_set_client     | utf8                              |
| character_set_connection | utf8                              |
| character_set_database   | latin1                            |
| character_set_filesystem | binary                            |
| character_set_results    | utf8                              |
| character_set_server     | latin1                            |
| character_set_system     | utf8                              |
+--------------------------+-----------------------------------+
```

从打印出的清单可以清晰地看到：
- `character_set_server`（服务器级字符集）的值为 `latin1`；
- `character_set_database`（当前数据库级字符集）的值同样为 `latin1`。

至于清单中的 `character_set_client`（客户端输入编码）、`character_set_connection`（连接层转换编码）以及 `character_set_results`（服务端返回结果编码），构成了一条完整的客户端与服务端字符流转换链条。这部分深层原理我们放到高级篇去推导，在上篇实战中，我们抓住核心矛盾：**在 5.7 默认安装环境下，`character_set_server` 缺省就是 `latin1`**。

除了字符集本身，还有一个紧密挂钩的概念叫做“比较规则”（Collation）。我们执行如下命令查询：

```sql
show variables like 'collation%';
```

终端回显结果如下：

```text
+----------------------+-------------------+
| Variable_name        | Value             |
+----------------------+-------------------+
| collation_connection | utf8_general_ci   |
| collation_database   | latin1_swedish_ci |
| collation_server     | latin1_swedish_ci |
+----------------------+-------------------+
```

> **概念解析**：字符集解决的是“字符如何编码成二进制存储”的问题；而比较规则（Collation）解决的是“两个字符谁大谁小、如何排序、是否区分大小写”的问题。
> 每一种字符集都有若干套与之严格配套的比较规则。例如 `latin1` 对应的默认规则就是瑞典语比较规则 `latin1_swedish_ci`（其中的 `ci` 代表 Case Insensitive，即大小写不敏感）；而 `utf8` 对应的常用比较规则是 `utf8_general_ci`。

### 3. MySQL 5.7 字符集的持久化改造方案

#### 3.1 配置文件 my.ini 的关键参数修改

要想彻底根治 5.7 上的乱码和字符报错，必须从源头上修改 MySQL 服务启动时读取的配置文件，将服务端与客户端的默认编码一次性固化为 `utf8`。

在 Windows 环境下，MySQL 的配置文件名为 `my.ini`。这个文件并不在安装主目录下，而是存放在具有隐藏属性的系统数据目录中：

```text
C:\ProgramData\MySQL\MySQL Server 5.7\my.ini
```

> **注意**：`C:\ProgramData` 是 Windows 系统的隐藏文件夹，在文件资源管理器中需要勾选“隐藏的项目”才能看见。

使用纯文本编辑器打开 `my.ini` 后，文件内部包含了大量英文字段和参数。不要被冗长的配置吓退，我们需要精准定位并修改以下两个区块：

```text
======================= my.ini 修改位置拓扑 =======================

  [mysql]                      <--- 客户端配置组
  default-character-set=utf8   <--- 在此组下新增客户端通信字符集

  ......

  [mysqld]                     <--- 服务端引擎配置组
  character-set-server=utf8    <--- 在此组下新增服务端核心字符集
  collation-server=utf8_general_ci <--- 新增配套比较规则
==================================================================
```

具体的配置段落如下：

1. 定位到 `[mysql]` 标签（负责命令行客户端交互参数）：
   在该配置组正下方，顶格添加：
   ```ini
   default-character-set=utf8
   ```

2. 定位到 `[mysqld]` 标签（负责 mysqld 核心守护进程参数）：
   在该配置组正下方，顶格添加：
   ```ini
   character-set-server=utf8
   collation-server=utf8_general_ci
   ```

> **易错点**：
> 1. `[mysql]` 组下使用的是 `default-character-set`，而 `[mysqld]` 组下使用的是 `character-set-server`，两者的键名写法不同，切勿混淆；
> 2. 参数必须顶格书写，等号两边不要画蛇添足地留出多余空格。

保存文件（Ctrl + S）后关闭编辑器。

#### 3.2 服务重启与历史库表的字符集继承陷阱

修改完配置文件后，参数并不会立即对正在运行的进程生效，必须**重启 MySQL 服务**。
我们可以打开 Windows“服务”管理面板，找到名为 `MySQL57` 的服务项，右键点击“重新启动”；或者以管理员身份打开终端，通过系统命令关闭并重新拉起服务。

重启完成后，我们重新打开命令行，登录 5.7 实例进行验证：

```bash
mysql -u root -P 13306 -p
```

登录后再次执行字符集探测语句：

```sql
show variables like 'character%';
```

此时回显中关键的 `character_set_database` 和 `character_set_server` 已经成功变更为 `utf8`：

```text
+--------------------------+-----------------------------------+
| Variable_name            | Value                             |
+--------------------------+-----------------------------------+
| character_set_database   | utf8                              |
| character_set_server     | utf8                              |
+--------------------------+-----------------------------------+
```

接着检查比较规则：

```sql
show variables like 'collation%';
```

对应的 `collation_database` 与 `collation_server` 也同步变为了 `utf8_general_ci`。

到这里，很多同学会想当然地认为：既然服务端的全局字符集已经修正为 UTF-8 了，那我现在切回刚才的数据库，继续往 `employees` 表里补插中文，总该能成功了吧？

我们切入 `dbtest1` 并尝试写入 `'杰瑞'`：

```sql
use dbtest1;
insert into employees values(1003, '杰瑞');
```

执行后，控制台再次弹出刺眼的错误：

```text
ERROR 1366 (HY000): Incorrect string value: '\xBD\xDC\xC8\xF0' for column 'name' at row 1
```

为什么全局配置明明已经改了，依然写不进中文？

我们再次调出元数据定义：

```sql
show create table employees;
```

你会发现，输出的建表语句末尾依旧印着 `DEFAULT CHARSET=latin1`！

> **结论**：**`my.ini` 配置文件的修改只对服务重启之后「新创建」的数据库和表生效；对于在修改前就已经落盘的历史库和历史表，其物理结构上的字符集元数据已经被固化，绝不会因为底层配置文件的改动而自动升级。**

虽然在生产环境中可以通过 `alter table ... convert to character set utf8;` 来批量刷表，但对于初学者刚刚搭建的测试环境，最干净、最彻底的处理方式就是直接删除旧库并重建：

```sql
drop database dbtest1;
create database dbtest1;
```

我们重新查看新建库的属性：

```sql
show create database dbtest1;
```

回显信息显示该库已自动继承了服务端的编码：`DEFAULT CHARACTER SET utf8`。
接着切入新库，重新创建 `employees` 表并写入包含中英文的数据：

```sql
use dbtest1;

create table employees (
    id int,
    name varchar(15)
);

insert into employees values(1001, 'Tom');
insert into employees values(1003, '杰瑞');
```

这一次没有任何报错，顺利写入。执行全表查询：

```sql
select * from employees;
```

终端回显结果如下：

```text
+------+--------+
| id   | name   |
+------+--------+
| 1001 | Tom    |
| 1003 | 杰瑞   |
+------+--------+
2 rows in set (0.00 sec)
```

中文汉字被端端正正地打印在终端控制台上，至此 5.7 版本的字符集改造彻底闭环。

### 4. MySQL 8.0 字符集新特性对比

#### 4.1 默认 utf8mb4 规范与 4 字节编码优势

解决完 5.7 的问题，我们把视角转向 MySQL 8.0。我们先退出 5.7，通过默认的 3306 端口直接登录 8.0 实例：

```bash
mysql -u root -P 3306 -p
```

注意：我们在之前的安装中，**完全没有对 8.0 的 `my.ini` 做过任何关于字符集的手工篡改**。此时我们直接在 8.0 中执行字符集查看命令：

```sql
show variables like 'character%';
```

终端展现出的变量值如下：

```text
+--------------------------+-----------------------------------+
| Variable_name            | Value                             |
+--------------------------+-----------------------------------+
| character_set_client     | utf8mb4                           |
| character_set_connection | utf8mb4                           |
| character_set_database   | utf8mb4                           |
| character_set_filesystem | binary                            |
| character_set_results    | utf8mb4                           |
| character_set_server     | utf8mb4                           |
| character_set_system     | utf8mb3                           |
+--------------------------+-----------------------------------+
```

可以看到，在 8.0 中，`character_set_database` 和 `character_set_server` 默认就是 `utf8mb4`。

> **提示**：
> MySQL 早期所称的 `utf8`（在 8.0 内部被严格重命名为 `utf8mb3`）其实是一个“残血版”UTF-8 实现，它最多只分配 3 个字节来存储一个字符。虽然涵盖了绝大多数日常中文汉字，但在遇到诸如 Emoji 表情符号、复杂罕见汉字或历史古籍符号时（这些符号需要完整的 4 字节 UTF-8 编码），`utf8mb3` 就会再次抛出插入异常。
> 从 MySQL 8.0 开始，官方彻底顺应了互联网多媒体时代的需求，将默认字符集统一升级为完全体的 **`utf8mb4`（Most Bytes 4，即单个字符最多占用 4 个字节）**。

#### 4.2 两个版本的运维规范总结

我们在 8.0 实例中无需任何额外配置，直接执行建库建表与中文写入流程：

```sql
create database dbtest2;
use dbtest2;

create table emp (
    id int,
    name varchar(15)
);

insert into emp values(1001, 'Tom');
insert into emp values(1002, '杰瑞');
```

执行 `show create table emp;` 可以验证，表的字符集默认就是 `utf8mb4`，数据插入与查询行云流水，没有任何字符阻碍。

我们将 5.7 与 8.0 在字符集层面的核心差异归纳如下：

```text
+-------------------------------------------------------------------+
|                     MySQL 字符集默认行为对比                      |
+-------------------+-----------------------+-----------------------+
| 核心指标项        | MySQL 5.7 (及更早版本)| MySQL 8.0 (现代化标准)|
+-------------------+-----------------------+-----------------------+
| 默认底层字符集    | latin1 (单字节编码)   | utf8mb4 (4 字节完整版)|
| 默认比较规则      | latin1_swedish_ci     | utf8mb4_0900_ai_ci    |
| 中文原生支持能力  | 报错 (必须人工干预)   | 原生天然支持          |
| 表情符号 (Emoji)  | 不支持                | 完美原生存储          |
| 人工运维成本      | 必须手工修改 my.ini   | 开箱即用，零配置      |
+-------------------+-----------------------+-----------------------+
```

所有使用 5.7 版本的同学，必须在初始化阶段完成 `my.ini` 字符集的配置改造与服务重启；而直接从 8.0 起步的同学，则无需再为字符集设置耗费精力。搞清楚底层的继承机理与版本演进，我们在后续面对数据库中文乱码与字符截断等生产问题时，就能做到心中有数、手中有招。

### 2. 图形化工具的核心连接配置与交互操作

#### 2.1 连接四要素与底层命令行参数的映射关系

初学者在使用图形化工具连接数据库时，经常把它的配置弹窗视作一个全新的黑盒。实际上，任何图形化客户端在建立底层 Socket 连接时，所需录入的参数与我们在命令行中输入的参数是一一对应的。

```text
===================== 客户端连接四要素映射拓扑 =====================

  命令行参数体系                 图形化客户端配置字段 (GUI Field)
  --------------------------------------------------------------
  -h localhost / 127.0.0.1  ---> 主机名 / IP 地址 (Host / Server)
  -P 13306 / 3306           ---> 端口号 (Port)
  -u root                   ---> 用户名 (User / Username)
  -p abc123                 ---> 密码 (Password)

==================================================================
```

在配置图形化工具时，界面通常会包含如下字段：
1. **连接名称（Connection Name）**：这是给客户端本地看的标识标签，不影响网络连接。在实际开发中，由于经常需要在“本地开发库”、“局域网测试库”以及“线上预发库”之间频繁切换，强烈建议以目标服务器的 IP 地址与环境来命名（例如 `127.0.0.1_MySQL5.7` 或 `127.0.0.1_MySQL8.0`），切忌随手输入无意义的默认字符。
2. **主机名/IP 地址（Host Name / IP Address）**：连接本机时填写 `localhost` 或 `127.0.0.1`；连接远程服务器时填写局域网或公网 IP。
3. **端口号（Port）**：务必与后台运行的目标实例保持严格一致。在我们的双版本环境中，MySQL 5.7 绑定的是 `13306`，而 MySQL 8.0 绑定的是 `3306`。
4. **用户名与密码（User & Password）**：管理员账户填入 `root`，密码输入此前安装时设定的凭据（如 `abc123`）。

> **易错点**：
> 在点击“测试连接”时，若客户端弹出类似 `Access denied for user 'root'@'localhost' (using password: YES)` 的错误，核心排查依据就在最后那句 `using password: YES`。
> 该提示表示客户端已经尝试携带密码进行校验，但服务端验证未通过。此时 99% 的原因都是**密码输入错误**。请立即检查键盘上的大写锁定键（Caps Lock）是否意外开启，或者是否有前后空格残留。

#### 2.3 数据库环境破坏的经典避坑告诫

在带领成千上万名学员搭建开发环境的过程中，讲师遇到过各种匪夷所思的“误操作”。在此特别告诫大家两件绝对不能做的事情：

1. **绝对禁止安装路径中包含中文字符**：从操作系统底层 API 到各类开源数据库服务，底层 C/C++ 动态链接库与系统服务在解析非 ASCII 编码路径时极易出现乱码或路径找不到的情况。如果安装目录包含中文，往往在初次安装配置时看似成功，但第二天电脑重启、服务重新拉起时就会莫名其妙死锁或报错退出。
2. **绝对禁止私自对已安装的服务目录执行“剪切”（Ctrl + X）移动**：
   > **重点告诫**：有学员在装完 MySQL 服务几天后，觉得原本配置在 `D:\Program Files` 下的文件夹“看着不顺眼”，随手按个 `Ctrl + X`，直接将整个 MySQL 服务端根目录剪切粘贴到了另一个盘符下。
   > 这是灾难性的破坏操作！MySQL 服务在安装注册阶段，其守护进程的物理路径、`my.ini` 的绝对指向、数据目录挂载点都已经硬编码写入了 Windows 注册表和系统服务清单。你私自剪切移动目录，底层的注册表键值并不会跟着动态更新，会导致 `net start` 找不到可执行映像、数据文件脱机损坏，最终只能彻底重装。软件安装在哪个路径，就让它固定在哪个路径，严禁暴力挪动。

### 3. MySQL 8.0 加密认证插件引发的连接故障与根治方案

#### 3.1 caching_sha2_password 机制与连接报错溯源

在通过图形化工具轻松搞定 5.7 实例后，我们按照完全相同的步骤，在 Navicat 或 SQLyog 中新建一个连接，目标指向本地的 MySQL 8.0 实例：
- 主机：`localhost`
- 端口：`3306`
- 用户名：`root`
- 密码：`abc123`

满怀信心地点击「测试连接」，界面并没有弹出绿色对勾，而是瞬间弹出一个刺眼的错误弹窗：

```text
Authentication plugin 'caching_sha2_password' cannot be loaded: ...
```

在 SQLyog 中点击测试连接，同样抛出包含 `caching_sha2_password` 无法加载的相同报错！

为什么完全相同的凭据在命令行登录一切正常，5.7 实例连接行云流水，而 8.0 实例一连就挂？

我们必须回溯到安装 MySQL 8.0 时的关键步骤。在 8.0 的安装向导中，有一个在 5.7 中从未出现过的独有配置界面——「Authentication Method」（身份验证方式配置）：

```text
======================= 8.0 身份验证选项机理 =======================

  选项 A: Use Strong Password Encryption for Authentication (RECOMMENDED)
          -> 采用 caching_sha2_password 认证插件
          -> 基于 SHA-256 双重哈希散列与服务端高速缓存
          -> 安全性极高，防止中间人窃听与暴力破解

  选项 B: Use Legacy Authentication Method (Retain MySQL 5.x Compatibility)
          -> 采用 mysql_native_password 认证插件
          -> 基于老旧的 SHA-1 原生单向哈希
          -> 安全性一般，但对旧版第三方开发工具兼容性极佳

==================================================================
```

当时安装向导默认勾选了推荐的选项 A（`caching_sha2_password`）。
MySQL 官方为了彻底阻断基于网络抓包的彩虹表碰撞攻击，在 8.0 中淘汰了历时十多年的旧插件 `mysql_native_password`，改用安全等级极高的 `caching_sha2_password` 算法。

但问题在于：许多开发者本机安装的 Navicat 或 SQLyog 是多年前发布的旧版本。这些老版本客户端内部捆绑的数据库通信驱动库，根本没有编写过解析 `caching_sha2_password` 握手报文的逻辑。客户端识别不了服务器发回的认证加密请求，握手环节便当场中断崩塌。

#### 3.2 两种解决方案与降级为 mysql_native_password 实操

遇到这个典型故障，业界有两种标准的应对路径：

- **路径一：升级客户端管理工具**
  将本地安装的 Navicat、SQLyog 或 DBeaver 直接升级更新至支持 MySQL 8.0 通信协议的现代化新版本。新版客户端内部天然自带 `caching_sha2_password` 的握手驱动，连接即可恢复正常。
- **路径二：将 8.0 服务端的认证规则降级还原为 5.x 兼容模式（推荐实操）**
  在企业开发场景中，许多老项目的连接池框架、中间件或既定工具版本不可随意变更。我们完全可以直接在 MySQL 8.0 实例内部，将 `root` 账户的加密规则手工修正为向后兼容的 `mysql_native_password`。

我们按照路径二，在当前运行的 MySQL 8.0 服务上进行平滑修复：

##### 步骤 1：打开终端，通过命令行登录 8.0 实例
由于官方的命令行客户端（`mysql.exe`）本身就是 8.0 原生发布的，它具备解析新算法的能力，因此命令行登录完全不受影响：
```bash
mysql -u root -P 3306 -p
```
输入密码回车，进入 `mysql>` 交互环境。

##### 步骤 2：切换至系统核心库 `mysql`
用户权限与加密凭证属于 MySQL 的核心元数据，统一托管在预置的 `mysql` 系统数据库中：
```sql
use mysql;
```

##### 步骤 3：重置账户的身份认证插件与密码
执行针对用户账户体系的 DDL 变更指令，显式声明认证插件使用传统的 `mysql_native_password`，并重新设置密码：
```sql
ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY 'abc123';
```

> **注意**：末尾单引号内的 `'abc123'` 是你的登录密码，请务必根据自己的实际密码进行替换，不要生搬硬套。

##### 步骤 4：刷新系统权限字典缓存
为了让修改后的安全插件与密码散列即刻生效，执行系统权限刷新指令：
```sql
FLUSH PRIVILEGES;
```

##### 步骤 5：回到图形化工具重新测试
完成上述四行命令后退出命令行。我们重新切回 Navicat 和 SQLyog 的连接配置面板，无需改动任何端口与密码，再次点击「测试连接」：

弹窗即刻回显绿色的「连接成功」！

点击连接进入 8.0 实例，左侧目录树完整展现出系统库与我们在上一讲创建的业务库 `dbtest2`，双击打开其内部的 `emp` 表，之前插入的中英文数据整整齐齐地呈现在可视网格中。

### 1. MySQL 物理目录结构与源码架构剖析

#### 1.1 安装根目录与数据配置目录分层

在 Windows 环境下，MySQL 的物理存在形式主要划分为两大核心阵营：**程序执行目录**与**数据/配置资产目录**。许多新手之所以在配置环境变量或修改字符集时频频迷路，就是因为混淆了这两套路径。

```text
===================== MySQL Windows 物理目录拓扑 =====================

  1. 软件安装主目录 (例如 D:\develop\mysql-8.0.25\)
     ├── bin/                  <--- 核心可执行程序 (.exe 集中营，需配入 Path)
     │    ├── mysql.exe        (命令行交互客户端)
     │    ├── mysqld.exe       (MySQL 后台守护主进程服务)
     │    └── mysqldump.exe    (逻辑备份导出工具)
     ├── include/              <--- C/C++ 开发头文件
     ├── lib/                  <--- 静态与动态链接库
     └── share/                <--- 错误信息字典与多语言字符集定义

  2. 运行时数据与配置目录 (默认 C:\ProgramData\MySQL\MySQL Server 8.0\)
     ├── Data/                 <--- 物理数据总库
     │    ├── #ib_16384_0.dblwr (共享表空间与双写缓冲)
     │    ├── ibdata1           (系统表空间数据文件)
     │    ├── mysql/            (系统核心权限元数据目录)
     │    ├── sys/              (性能诊断视图定义目录)
     │    └── dbtest1/          (用户自定义创建的业务数据库目录)
     └── my.ini                <--- Windows 服务端与客户端全局配置文件

====================================================================
```

##### 1. 软件安装主目录（Program Directory）
- 位于用户安装时指定的路径（例如 `D:\develop\mysql-8.0.25`）。
- **`bin` 目录（Binary）**：存放了 MySQL 所有的核心二进制可执行文件。包括启动服务端的 `mysqld.exe`、客户端连接工具 `mysql.exe`、数据备份工具 `mysqldump.exe` 等。我们之所以在安装阶段要求必须将该 `bin` 路径追加到操作系统的 `Path` 环境变量中，目的就是让操作系统的命令解释器能够全局检索到这些执行程序，使我们在任何工作目录下都能直接调起 `mysql` 命令。
- **`include` 与 `lib` 目录**：存放供第三方 C/C++ 语言调用数据库引擎的开发头文件与链接库。

##### 2. 数据与全局配置目录（Data Directory）
- 位于系统隐藏目录 `C:\ProgramData\MySQL\MySQL Server X.X\` 下。
- **`Data` 目录**：真正存放物理数据文件的地方。我们在上一讲中通过 `create database dbtest1;` 创建的数据库，底层就会在 `Data` 目录下生成一个同名的 `dbtest1` 物理文件夹；文件夹内部则存放了该库下所有表的结构与数据文件。
- **`my.ini` 配置文件**：服务启动时加载的系统配置文件。控制着服务端口、默认字符集、最大连接数与缓冲区大小等核心运行参数（在 Linux 系统下该文件对应为 `my.cnf`）。

#### 1.2 C/S 网络架构意识与物理文件隔离

很多初学者在发现 `Data` 目录下的业务库文件夹后，往往下意识地想要通过文件资源管理器双击打开这些文件来查看表中的数据。这种做法是完全错误的。

> **结论**：
> 数据库绝不是普通的桌面单机软件。从架构层面看，MySQL 是高度解耦的标准 **客户端/服务端（Client/Server，C/S）架构体系**。
> 尽管在学习阶段，我们将数据库服务端与 Navicat/命令行客户端安装在同一台物理电脑上，但在逻辑通信链路上，客户端与服务端完全是两套独立的实体，彼此通过 **TCP/IP 网络协议（或本地套接字）** 建立网络通信。

服务端的守护进程 `mysqld` 独占式地接管了底层物理文件的读写与锁控制。客户端只负责向服务端发送符合 SQL 规范的网络请求报文，服务端解析执行后，再将结构化的结果集通过网络通道回传给客户端。用户绝不能、也无法绕过服务端的管控进程去直接篡改底层的物理数据文件。

#### 1.3 C++ 源码工程核心模块概览

MySQL 社区版是完全开放源代码的。从官网下载官方源码包（以 `mysql-8.0.25.zip` 为例），解压后可以看到其底层工程主要采用 C++ 与 C 语言编写（核心文件以 `.cc` 和 `.h` 结尾）。源码工程的骨干目录结构反映了整个数据库系统的功能分工：

- **`sql/` 目录**：MySQL 最核心的调度中心与 SQL 解析引擎。包含了客户端连接握手处理、SQL 词法与语法分析器、查询优化器、执行计划生成器以及表定义缓存（如 `bootstrap.cc`）。
- **`libmysql/` 目录**：实现客户端连接与底层通信网络协议的客户端 API 库。
- **`mysql-test/` 目录**：官方配套的大规模自动化测试套件与回归测试脚本。
- **`mysys/` 目录**：跨平台的底层操作系统抽象库。封装了跨 Windows、Linux、Unix 平台的文件 I/O、内存分配、线程锁调度等基础辅助函数。

阅读底层源码并非初学阶段的必经之路，但了解这些模块有助于我们建立敬畏心与工程感知：数据库底层并不神秘，它是由高度工业化的工程结构与注重执行效率的 C++ 算法严密构建而成的。

### 2. 数据库初始化与环境配置避坑指南

结合前两章的实操过程，我们将开发与测试环境中最高频的几类故障场景及其标准解法做系统归纳：

#### 2.1 环境变量与无数据库上下文报错应对

##### 1. 命令行回显“不是内部或外部命令，也不是可运行的程序”
- **故障根源**：操作系统在执行命令时，会优先在当前目录查找，若找不到则遍历 `Path` 环境变量中配置的所有目录。该报错说明系统在 `Path` 路径清单中未能检索到 `mysql.exe`。
- **修复方案**：检查系统环境变量 `Path`，确保追加了 MySQL 安装根目录下的 `bin` 绝对路径，并确认路径末尾无多余中文字符或截断；配置完成后务必**重新打开一个新的命令行窗口**以加载最新的环境变量。

##### 2. 命令行执行建表或查询报 `ERROR 1046 (3D000): No database selected`
- **故障根源**：客户端与服务端建立连接后，当前会话处于全局未绑定状态。直接发起针对某张表的 DDL 或 DQL 指令，解析器无法判定目标对象归属于哪一个具体数据库。
- **修复方案**：
  - 方案 A（标准做法）：在操作前先执行上下文切换指令：
    ```sql
    use dbtest1;
    ```
  - 方案 B（全限定名调用）：在表名前显式带上所属数据库前缀：
    ```sql
    select * from dbtest1.employees;
    ```

#### 2.2 历史库表字符集平滑升级（alter 语法）

在第 9 讲中，我们通过修改 `my.ini` 成功将 5.7 实例的默认字符集固化为 `utf8`。当时我们强调：配置文件只对重启服务后**新创建**的数据库生效，而修改前创建的历史数据库 `dbtest1` 和 `employees` 表依旧停留在 `latin1` 编码，向其中插入中文依然会报错。

在入门演练中，我们推荐直接 `drop database` 删库重建。但如果是在生产环境或已有业务数据的场景下，删库显然不可接受。我们必须掌握在线平滑升级字符集的 SQL 指令：

##### 1. 修改现有数据库的默认字符集
```sql
ALTER DATABASE dbtest1 CHARACTER SET utf8;
```
> **提示**：该语句仅修正数据库元数据中的默认字符集属性，使得未来在该库下新建表时默认继承 `utf8`，但不会自动刷写库中已存在的历史旧表。

##### 2. 修改现有历史数据表的字符集与已有列编码
```sql
ALTER TABLE employees CONVERT TO CHARACTER SET utf8;
```
> **核心区别**：千万不要写成 `ALTER TABLE employees DEFAULT CHARACTER SET utf8;`。
> - `DEFAULT CHARACTER SET` 仅仅改变表的默认属性，表内既有的 `varchar` 列依然停留在 `latin1`，中文写入依然报错；
> - 必须使用 `CONVERT TO CHARACTER SET utf8`，它会连同底层所有已存在的字符类型字段及其历史存储数据，一次性完成物理编码转换。

完成上述转换后，再次向历史表 `employees` 中写入汉字即可顺畅通过：

```sql
insert into employees values(1003, '杰瑞');
```

#### 2.3 服务的规范启停与修改流程

修改 `my.ini` 配置文件后，必须重启后台 Windows 服务才能重新加载参数。

##### 1. 规范的操作时序
最严谨的操作时序应为：**先停止服务 -> 修改并保存配置文件 -> 再启动服务**。虽然在实际开发中许多人习惯“先改文件后重启”，但在某些并发写入或刷盘场景下，热改配置文件可能引发参数不同步。

##### 2. 命令行服务启停指令
在以管理员身份运行的终端中执行：
```cmd
net stop MySQL57
net start MySQL57
```
若需要操作 8.0 服务，将服务名替换为对应的实例名即可（如 `net stop MySQL80`）。

### 3. 前两章课后综合习题深度解析

#### 3.1 数据库分类、MySQL 发展史与 DB/DBMS/SQL 辨析

##### 1. 关系型数据库与非关系型数据库的典型代表
在现代软件架构中，企业往往采用“多数据引擎协同”的混合持久化方案：
- **关系型数据库（RDBMS）**：依据关系模型构建，支持严密的 ACID 事务，支持复杂 SQL 多表联查。
  - **Oracle**：商业数据库霸主，功能极其强大，高并发与高可用方案成熟，广泛应用于金融、电信及大型政企核心交易系统。
  - **MySQL**：全球最受欢迎的开源关系型数据库，生态极其繁荣，互联网与中小型企业的主流首选。
  - **SQL Server**：微软出品，与 Windows 平台及 .NET 技术栈深度整合，在中大型企业内部系统中有广泛应用。
  - **DB2**：IBM 商业巨型数据库，主要应用于银行、大型机与关键业务支撑。
  - **PostgreSQL（简称 PG）**：被称为“功能最强大的开源关系型数据库”，对复杂数据类型、地理信息（GIS）与高阶 SQL 标准支持极佳。

##### 2. MySQL 关键发展时间线
- **1995 年**：由瑞典公司 **MySQL AB** 正式发布，这也是其早期默认字符集采用西欧 `latin1` 的历史根源。
- **2008 年**：Sun 公司以 10 亿美元收购 MySQL AB。
- **2009 年**：Oracle（甲骨文）公司收购 Sun 公司，MySQL 正式收归 Oracle 旗下。至此，全球排名前两位的两大关系型数据库（Oracle 与 MySQL）同归一家商业巨头所有。
- **2016 年**：MySQL 官方跳过 6.x 与 7.x，正式推出里程碑式的 **MySQL 8.0.0** 版本。版本号的跨越代表着底层架构的巨变，引入了真正的系统数据字典、支持现代化的通用表表达式（CTE）、窗口函数以及默认全方位的 `utf8mb4` 字符集。

##### 3. DB、DBMS 与 SQL 的内在逻辑辨析
这三者是数据库领域最基础却最容易被混为一谈的概念：

```text
===================== DB / DBMS / SQL 协同运作图 =====================

  [ 开发者 / 用户 ]
         │
         │  1. 编写结构化指令 (SQL)
         ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 数据库管理系统 (DBMS, 如 MySQL Server 进程)                  │
  │  - 负责权限鉴权、语法解析、查询优化、缓存管理与事务控制       │
  │  - 充当物理磁盘数据与业务指令之间的核心翻译调度器           │
  └──────────────────────────────┬──────────────────────────────┘
                                 │
                                 │  2. 执行低级文件 I/O 读写
                                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 数据库 (DB, 物理磁盘文件集合)                               │
  │  - 真实落盘的二进制文件 (ibdata1, .ibd, 表结构字典)         │
  └─────────────────────────────────────────────────────────────┘

====================================================================
```

- **DB（Database，数据库）**：本质上是指**存放在物理介质上的、有组织的结构化数据文件集合**。类似于硬盘上的 `.txt` 文本、`.doc` 文档或 `.mp3` 音乐文件，它本身是静态的数据资产。
- **DBMS（Database Management System，数据库管理系统）**：是专门用来**科学组织、操作和维护底层 DB 文件的核心系统软件**。类似于编辑 `.doc` 文件必须安装 Microsoft Word 或 WPS，播放 `.mp3` 必须借助音频播放器。MySQL 软件本身就是一个典型的 DBMS。
- **SQL（Structured Query Language，结构化查询语言）**：是用户与 DBMS 之间进行**沟通交互的标准编程语言**。用户通过编写 SQL 语句，指挥 DBMS 对物理 DB 进行增删改查。

#### 3.2 非关系型数据库类型与表关联模型

##### 1. 非关系型数据库（NoSQL）的核心类型

| 分类模型 | 核心数据结构与存储特点 | 典型代表系统 | 适用业务场景 |
| :--- | :--- | :--- | :--- |
| **键值型 (Key-Value)** | 类似哈希表（Map），通过唯一的 Key 索引 Value，主要基于内存操作，读写延迟极低（微秒级）。 | **Redis**、Memcached | 热点数据高速缓存、分布式 Session、计数器、秒杀库存锁 |
| **文档型 (Document)** | 以类似 JSON 或 BSON 的半结构化格式组织数据，无需固定 Schema，支持字段动态增删。 | **MongoDB** | 内容管理系统、日志采集、社交动态、非规范化业务数据归档 |
| **搜索引擎型 (Search Engine)**| 底层采用倒排索引（Inverted Index）结构，针对海量文本的模糊匹配与分词搜索性能卓越。 | **Elasticsearch**、Solr | 电商全文商品检索、日志分析聚合（ELK 技术栈） |
| **列式存储 (Column-Oriented)**| 按列而非按行切分存储数据，极大提升单一字段的大规模聚合与统计效率，具备极高的数据压缩比。 | **HBase**、ClickHouse | 大数据数仓分析（OLAP）、时序指标汇总、离线报表计算 |
| **图形数据库 (Graph)** | 专门存储实体节点（Node）以及节点间的拓扑边关系（Edge），擅长深度关系图遍历。 | **Neo4j**、InfoGrid | 社交好友关系网络、风控反洗钱穿透、金融知识图谱推理 |

##### 2. 表与表之间的关联关系（E-R 模型精要）
在关系型数据库中，现实世界中实体与实体之间的业务逻辑，通过主外键映射为 4 种经典的结构化关联，这与基础数据结构有着清晰的映射对应：

- **一对一关联（One-to-One）**：例如“员工表”与“员工详细档案卡表”，或者“用户表”与“身份证信息表”。（类比数据结构中的单元素映射）。
- **一对多关联（One-to-Many）**：例如“部门表”与“员工表”（一个部门包含多名员工，每名员工归属一个部门）。（类比数据结构中的树形层级结构）。
- **多对多关联（Many-to-Many）**：例如“学生表”与“课程表”（一个学生可选多门课，一门课包含多名学生）。在物理落地时，必须借助一张“中间关联表”拆解为两个一对多。（类比数据结构中的网状图模型）。
- **自引用/自关联（Self-Referencing）**：同一张表内部的行记录之间产生关联。最典型的就是“员工表中的管理者”，每个员工的 `manager_id` 实际上指向本表中另一条记录的 `id`。

#### 3.3 Windows 环境下 MySQL 物理踪迹与彻底卸载规范

许多学员在二次安装 MySQL 失败时，主要原因就是旧版本的残留数据未清理干净。必须掌握 MySQL 在 Windows 系统中的所有物理分布及卸载规范：

##### 1. MySQL 存在的 5 个关键物理与系统位置
1. **安装主程序目录**：存放核心可执行文件的路径（如 `D:\develop\mysql-8.0.25\`）；
2. **物理数据存储目录**：存放实际表与数据的路径（`C:\ProgramData\MySQL\MySQL Server X.X\Data\`）；
3. **配置文件路径**：全局运行参数文件（`C:\ProgramData\MySQL\MySQL Server X.X\my.ini`）；
4. **系统服务注册项**：系统后台守护服务（Windows 服务列表中的 `MySQL`、`MySQL57` 或 `MySQL80`）；
5. **系统环境变量**：`Path` 中配置的二进制路径映射。

##### 2. 彻底干净卸载的 5 步标准流线
- **第 1 步：关闭服务并卸载主程序**
  打开 Windows 控制面板 -> 程序和功能，选中所有与 MySQL 相关的安装包（如 MySQL Server、MySQL Installer 等），执行标准卸载。
- **第 2 步：手动粉碎残留的数据文件目录**
  控制面板卸载仅会移除程序本身，**绝不会自动删除用户的业务数据**。必须手动进入隐藏的 `C:\ProgramData\MySQL` 文件夹，将整个 `MySQL` 目录彻底清空删除。
- **第 3 步：清理 Path 环境变量**
  右键“此电脑”-> 属性 -> 高级系统设置 -> 环境变量，在系统变量 `Path` 中找到之前追加的 MySQL `bin` 路径，将其剔除。
- **第 4 步：清理系统注册表与服务残留（针对 5.7 等顽固服务）**
  在运行窗口（Win + R）输入 `regedit` 进入注册表编辑器，排查并删除以下路径下的 MySQL 节点：
  - `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\`
  - `HKEY_LOCAL_MACHINE\SYSTEM\ControlSet001\Services\`
  若服务项已不存在可跳过此步。
- **第 5 步：必须重启计算机**
  这是最关键的一步。只有在重启操作系统后，被占用的底层 DLL 句柄与注册表资源才会被 Windows 内核彻底释放，为下一次全新安装扫清障碍。

### 本讲提到的题目

讲师在课上将第一章《数据库概述》与第二章《环境搭建》的课后练习题进行了逐题提问与全面串讲。各题的标准题干与解答依据如下：

#### 第一章：数据库概述练习题
1. **说一说常见的数据库都有哪些？**
   - **解答依据**：关系型包含 Oracle、MySQL、SQL Server、DB2、PostgreSQL；非关系型包含 Redis、MongoDB、Elasticsearch、HBase、Neo4j。后端开发通常需要掌握关系型与缓存型（如 Redis）组合。
2. **谈谈对 MySQL 历史和特点的理解。**
   - **解答依据**：1995 年瑞典 MySQL AB 创立；2008 年 Sun 收购；2009 年 Oracle 收购 Sun 获得 MySQL；2016 年推出里程碑版本 8.0.0。核心特点是开源、关系型、支持千万级数据量存储、成熟稳定。
3. **谈谈对 DB、DBMS 和 SQL 的理解。**
   - **解答依据**：DB 是物理磁盘上的数据库文件资产（如 `.doc`）；DBMS 是操作管理 DB 的软件系统（如 Word）；SQL 是人与 DBMS 交互的标准查询语言。
4. **你知道哪些非关系型数据库类型？**
   - **解答依据**：键值型（Redis）、文档型（MongoDB）、搜索引擎型（Elasticsearch/Solr）、列式存储（HBase）、图形数据库（Neo4j）。
5. **表与表记录之间存在哪些关联关系？**
   - **解答依据**：一对一、一对多、多对多、自关联。对应数据结构中的线性映射、树模型与图模型。

#### 第二章：环境搭建练习题
1. **安装好 MySQL 之后，Windows 系统中的哪些位置能够看到 MySQL？**
   - **解答依据**：软件安装路径、`C:\ProgramData\MySQL` 数据目录及 `my.ini`、系统服务（Services）、`Path` 环境变量。
2. **MySQL 主要卸载哪几个位置？**
   - **解答依据**：控制面板卸载主程序、手动删除 ProgramData 物理数据目录、清理 Path 环境变量、清理注册表（regedit）服务残留、重启电脑。
3. **能否独立完成 MySQL 8.0 或 5.7 的下载、安装和多端口配置？**
   - **解答依据**：本章实操硬性考核，要求至少掌握 8.0 的安装，或同时搭建 5.7（13306）与 8.0（3306）双实例。
4. **5.7 配置完后为什么要修改 my.ini 配置文件？修改哪些信息？**
   - **解答依据**：默认字符集为 `latin1` 不支持中文；需在 `[mysql]` 下加 `default-character-set=utf8`，在 `[mysqld]` 下加 `character-set-server=utf8` 和 `collation-server=utf8_general_ci`。修改后重启服务。
5. **熟悉常用的数据库管理与操作工具有哪些？**
   - **解答依据**：Windows cmd 命令行、MySQL 自带 Command Line Client、GUI 工具（Navicat、SQLyog、DBeaver、Workbench）。
