### 事务与文件系统的分野：存储引擎层面的事务支持

事务是数据库区别于文件系统的重要特征之一。文件系统就是我们平时存文件的地方，它和数据库都是一种持久化的媒介，都能把数据留下来。那数据库凭什么跟文件系统拉开显著的区别？事务在这里起了非常重要的作用，而事务之所以能成为分界线，靠的就是它的 ACID 四个特性。

不过在讲这四个特性之前，得先确认一件事：MySQL 里是不是所有的表都能用事务？我们在存储引擎那一章讲过不同存储引擎的特点，其中有一条就是：有的存储引擎支持事务，有的不支持。

登录进 MySQL 看一眼：

```bash
mysql -u root -p
```

```sql
SHOW ENGINES;
```

`SHOW ENGINES` 会列出 MySQL 支持的所有存储引擎，重点看 `Transactions` 这一列——它就表示这个引擎支不支持事务。列出来的结果里，标成 `YES` 的只有 InnoDB 一个，MyISAM 是不支持的。

| 存储引擎 | `Transactions` 列 | 事务支持 |
| :--- | :--- | :--- |
| InnoDB | YES | 支持事务；MySQL 5.5 之后默认使用的就是它 |
| MyISAM | NO | 不支持事务 |

> **结论**：本章讲的事务，全部是在 InnoDB 这个存储引擎下讲的。5.5 以后默认使用的 InnoDB 默认就支持事务，事务相关的所有内容都落在 InnoDB 里。

### 事务的定义与处理原则

先用最简单的一句话把事务刻画出来：事务是一组逻辑操作单元，使数据从一种状态变换到另一种状态。

> **定义**：事务（Transaction）是一组逻辑操作单元，使数据从一种状态变换到另一种状态。

这句话的关键词是「一组操作单元」。所谓操作单元，就是我们写的那类 DML 操作——增、删、改。一组增删改操作凑在一起，作用在表里的数据上，把数据从一种状态改到另一种状态，整体就构成一个事务。

不过光看这句定义，是理解不了事务的，还得看事务的处理原则。

事务必须作为一个工作单元来执行，即使出现了故障，也不能改变这种执行方式——它就是一个整体，不能拆开来处理。而一个事务里往往包含多个 DML 操作，它的结局只有两种：要么事务中所有操作都被提交（`COMMIT`），这些操作带来的修改就永久保存下来；要么数据库管理系统放弃所做的全部修改。假设一个事务里有 5 个 DML 操作，你做了 3 个、剩下 2 个没做，这不行——已经做掉的那 3 个也得回滚回去，让数据回到最初的状态。

### 转账案例：一组 DML 的整体性

#### 两条 UPDATE 构成一个事务

拿一个真实的例子来说就清楚了：用户 AA 给用户 BB 转账 100 块钱（前提是两个人账户里的钱够）。这件事对应的是两个 DML 操作，准确讲是两个 `UPDATE`：

```sql
UPDATE account SET money = money - 100 WHERE name = 'AA';
UPDATE account SET money = money + 100 WHERE name = 'BB';
```

第一条让 AA 这个用户的余额减 100，第二条让 BB 这个用户的余额加 100。这两个操作整体上就构成了一个事务，因为它们必须作为一个整体出现：要么 AA 减掉了 100、同时 BB 也加上了 100，两个操作都执行完，事务就算执行完了，这时候我们把数据提交、永久保存下来，转账成功；要么中间出了状况——服务器宕机、停电之类——AA 那 100 块钱已经减掉了，BB 这 100 块钱还没加上，那就必须把 AA 的 100 块钱退回去，也就是回滚到 AA 还有这 100 块钱的那个最初状态。

```text
        ┌────────────────────────────────────────────────┐
        │          AA 向 BB 转账 100 元的两种结局          │
        └───────────────────────┬────────────────────────┘
                                │
        ┌───────────────────────┴────────────────────────┐
        ▼                                                ▼
  【都执行】                                       【都不执行】
  AA 减 100，BB 加 100                            中途宕机 / 停电
  两条 UPDATE 全部成功                            AA 已减 100，BB 未加 100
        │                                                │
        ▼                                                ▼
  COMMIT 提交                                      回滚：AA 的 100 元退回
  数据永久保存，转账成功                            数据回到最初状态，转账失败
```

*读图说明：两条 `UPDATE` 只能作为整体一起生效或一起失效，不存在「只做了第一条就算数」的中间状态。*

> **结论**：这两条语句要么都执行，要么都不执行，它们作为一个整体出现，这才叫一个事务。

#### 两组互不相干的转账是两个事务

换一组条件再看：AA 给 BB 转 100 块钱，同时 CC 给 DD 转 100 块钱，而这四个人互相都不认识。这四个操作会构成一个事务吗？

准确地说，不是——这是两个事务。AA 和 BB 这一组自成一个事务，它要求要么都执行完、要么都回滚到最初状态，也就是要么转账成功、要么转账失败；而 CC 给 DD 转账是 CC 和 DD 两个人的事，这两组之间并没有「必须都做或者必须都不做」的要求，也就没有「一个工作单元」这层含义。所以要把它从中间切开：这一组是一个事务，那一组是另一个事务。

把定义、处理原则和这两个例子放在一起看，其实事务的特性已经蕴含在里面了。我们按 A、C、I、D 的顺序逐个说：A 是原子性（Atomicity），C 是一致性（Consistency），I 是隔离性（Isolation），D 是持久性（Durability）。

---

### 原子性（Atomicity）：不可分割的工作单位

原子性指事务是一个不可分割的工作单位，要么全部提交，要么全部失败回滚，没有第三种结果。就像转账那个例子，要么转账成功，要么转账失败，中间状态是不存在的——成王败寇，成了就是王，败了就是寇；你说咱们先停战一会儿、组成一个联合政府吧，没有这一说，没有中间状态。

这一点应该很好理解：它就是一个整体。原子性这个说法借用了物理世界里的含义——我们曾经认为物理世界中最小的单位就是原子，原子不能再分，所以用它来表达整体性这样一种概念。

---

### 一致性（Consistency）：语义层面的合法性状态

一致性这一块值得多花点力气。如果你以后要当面试官，我建议在事务这块重点问一致性和隔离性：这两个最不好答。隔离性牵扯到后面要讲的隔离级别，而一致性往往是理解上出问题最多的一个——国内很多网站、一些帖子对一致性的阐述是有问题的，或者说是不全面的。

一致性指事务在执行前后，数据从一个合法性状态变换到另外一个合法性状态。

关键词是「合法」。我们平时写代码说符合规定叫合法、不符合规定叫不合法，那个合法指的是语法上的：少一个括号、关键字没写全、`SELECT` 少写一个字母，这就叫不合法，语句是语法层面有毛病。事务这里说的「从一个合法性状态到另一个合法性状态」，指的是语义上的。

> **提示**：语法上的合法由 SQL 本身把关，语句写错了根本执行不了；语义上的合法只能由现实业务里的约束把关，SQL 语法完全正确、语句也能跑通，但结果在现实中不成立。一致性始终说的是后者。说得直白一点，语义上合法就是满足现实当中的那些约束，在你的具体场景里是合规的。

合法，我们就认为是一致的；不合法、不满足这种合法状态，我们就认为是不一致的。不一致怎么办？回滚到最初的状态就行——这体现的正是原子性的特征。

下面三个例子可以把这个「合法性」的意思彻底钉住。

**例一：余额被转成负数。** A 账户有 200 块钱，却要转 300 块钱给 B 账户。账户最起码的规矩是余额得大于等于 0：你可以把 200 块钱全取出来，但不能多取——你又不是信用卡。所以这笔转账不能让成功。失败的原因就归结为没有遵循一致性：一开始的 200 块钱是合法状态，而转完之后的 -100 不是合法状态，它不满足现实中的约束。

**例二：两个账户的总额变了。** A 账户有 200 块钱，转 50 块钱给 B 账户，A 这边扣了钱，B 那边因为各种意外没有加上。这时候不行，得把 A 这 50 块钱给人家退回来。为什么？因为规定是 A 账户和 B 账户的金额总数应该是一定的：你转了 50 给 B，两个账户加在一起还应该是原来那个数，可现在加在一起不是了，总额变了。这也不算现实中合规的状态，同样不满足一致性。

**例三：唯一性被破坏。** 数据表里把姓名设置成了唯一性约束，言外之意就是姓名不能相同。事务提交或者事务发生回滚的时候，发现表里的姓名不唯一了——只要你的操作导致姓名不唯一，就不合法，就破坏了一致性的要求。

> **结论**：一致性关心的不是你写了几条 SQL，而是事务结束时数据是否仍然站在一个现实允许的状态上；站不住就回滚。

### 隔离性（Isolation）：并发事务之间的互不干扰

#### 定义与线程安全类比

隔离性指一个事务的执行不能被其他事务干扰，即一个事务内部的操作及使用的数据，对并发的其他事务是隔离的；并发执行的各个事务之间不能相互干扰。这两句话最好多念一遍、熟悉熟悉，如果之前没接触过隔离性，要能做到用自己的语言把它表达出来。后面讲的事务隔离级别（transaction isolation），讲的就是这件事的落地方式。

如果你接触过 Java 里的多线程，那对理解隔离性很有帮助。我们可以先把这里的事务理解成一个用户客户端发来的请求（当然也可能几个请求共同构成一个事务），为了好理解，先干脆把事务替换成「一个线程」。多线程操作共享数据（shared data）的时候，就可能出现线程安全问题。

一个很生活的场景：你这个账户里有 2000 块钱，你是一个线程，你媳妇儿是另一个线程。你先判断一下银行卡里够不够 2000——一看够，接着就想把这 2000 取出来；可这时候还只是判断完了，钱还没取。就在这一刻，你媳妇儿也来了：你手里拿的是银行卡，她拿的是淘宝关联你这个账户，她进来想买个东西，1999，判断一下余额够不够——一判断也够。现在你俩都能去减账户里的钱了：你把 2000 取出来，账户其实已经变成 0 了；她又花掉 1999，账户就成了负的 1999。这就是所谓的线程安全问题。

线程安全问题怎么处理？用 `synchronized` 把它包一层：A 用户在操作共享数据的过程当中，其他线程不允许进行操作，线程就是安全的。

搬到数据库的表上，只是把「线程」换成了「事务」。一个事务在操作表里的数据，做着增删改：原来人家是 100，现在你把它改成 200，而此时还没有提交。这时候另一个事务过来查询——它该查出来 100，还是查出 200？这就牵扯到隔离级别了。这就是隔离性：对并发执行的其他事务是隔离的，相互之间不能干扰。

#### 并发转账导致丢失更新的过程推演

再举一个具体例子看清隔离性是怎么被破坏的。假设 A 账户有 200 块钱，B 账户没有钱，是 0；现在 A 要给 B 转两次钱，每次转 50，也就是「A 减 50、B 加 50」这样执行两轮。用两个事务来体现，每个事务负责转 50 一轮。

事务一开始执行：先从磁盘上把 A 账户的余额读到内存的变量 A 当中，是 200；然后执行减 50 的操作，变量 A 变成 150；接着把 A 的值写回磁盘，磁盘上的 A 就成了 150。这一步没问题。

接下来从磁盘上把 B 的余额读到变量 B 当中，这时候 B 是 0；然后给它加 50。注意这一步：加完的 50 还只在内存里，也就是变量 B 被设成了 50，还没有把这个值写回磁盘，磁盘上的 B 仍然是 0。如果这里先把 B 写回磁盘、再去执行事务二，那什么麻烦都不会有。关键就在于磁盘上的 B 还是 0、还没往回写的这个时刻，另一个事务进来了。

事务二先读取，也是从磁盘上把 A 的余额读到变量 A——因为事务一之前已经写出过 150，所以这会儿读进来的就是 150；接着执行减 50，再写回去，A 就变成 100 了。然后事务二把磁盘上 B 的值读到变量 B 当中：事务一还没有回写到磁盘，所以这里读到的仍然是 0；给 B 加 50，变量 B 变成 50。

剩下就是往回写。这时候谁先回写已经不重要了：事务二先回写，就是把磁盘上的 B 从 0 改成 50，事务一再回写，又把 50 改成 50；反过来事务一先回写，是从 0 改成 50，事务二再回写，是从 50 改成 50。总之最终磁盘上的结果是 A 剩 100 块钱，B 还是 50 块钱，两个账户加在一起是 150。

```text
磁盘（持久层）          内存（变量）                        事务
──────────────────────────────────────────────────────────────────────────────
A = 200    ──读出──▶   变量A = 200
                         变量A = 150      ◀── 减 50
A = 150    ◀──写回──    变量A
B = 0      ──读出──▶   变量B = 0
                         变量B = 50       ◀── 加 50（尚未写回磁盘）
─────────────── 磁盘里的 B 仍是 0，此刻事务二进入 ─────────────────────────────
A = 150    ──读出──▶   变量A = 150
                         变量A = 100      ◀── 减 50
A = 100    ◀──写回──    变量A
B = 0      ──读出──▶   变量B = 0         ◀── 读到的还是旧值 0
                         变量B = 50       ◀── 加 50
B = 50     ◀──写回──    变量B（事务二先写 0→50，事务一后写 50→50）
──────────────────────────────────────────────────────────────────────────────
最终：磁盘上 A = 100，B = 50，两账户合计 150（最初是 200）
```

*读图说明：A 的两次自减都及时写回了磁盘，B 的两次自增却读到了同一个旧值 0，第二次自增的结果把第一次覆盖掉了。*

| 观察项 | 正确的结局 | 上面推演出的结局 |
| :--- | :--- | :--- |
| A 账户余额 | 100（转出两次共 100） | 100 |
| B 账户余额 | 100（收到两次共 100） | 50 |
| 两账户合计 | 200 | 150 |

A 一共转出了 100，B 一共只收到 50，整整少了 50 块钱。这就是并发处理事务时出现的问题，原因就归结为隔离性没有被很好地遵守——两个事务相互之间产生了干扰。

> **易错点**：两个事务各自都「算对了」，读、减、加一步不差，最终结果却错了。问题不在某一条语句写错，而在于两次转账的「读—改—写」区间交错重叠，后一次写回把前一次的结果盖掉了。

针对隔离性的问题——并发会引发哪些麻烦、用哪几种隔离级别去解决——下一节重点谈的就是这些，这部分非常重要。这里先把隔离性理解到这一步。

---

### 持久性（Durability）：提交结果的永久保存

ACID 四个特性里，最容易解释的就是 A 原子性和 D 持久性。所谓持久性，就是一旦数据要提交，那么对数据库中的改变就是永久性的。

还是拿转账说：A 给 B 转了 100 块钱，转成了，最后 `COMMIT` 提交，数据就持久地改下来了。这时候 A 反悔了，说这 100 块钱不该转、想把这 100 块钱要回来——从事务的角度讲，已经解决不了了。因为在开启事务之后、执行完一条语句的时候你还可以反悔；可你把这条也执行了、`COMMIT` 提交了，就不能再反悔了。你只能去跟 BB 说：大哥，我最近生活有点困难，你再给我转回来吧——注意，这时候转回来相当于又开启了一个事务，那是另外一个事务的事了。对当前这个事务来讲，修改已经生效，数据被永久保存在磁盘上，不能再改，这就是持久性的意思，它不会随着数据库的故障等产生任何影响。

持久性靠什么保障？靠事务的日志来保障，下一章就专门讲事务日志。日志主要讲两种：一种叫 `redo` 日志，也就是重做日志；一种叫 `undo` 日志，也就是回滚日志。这里先强调重做日志：我们把内存中的数据修改之后，首先会把这个修改记录到重做日志当中，然后再以相应的策略去处理——相关的服务器参数在讲参数设置那一部分提到过，至于什么时候刷盘到磁盘这件事，下篇再重点谈。这样做的好处是：即使数据库系统崩溃了，数据库重启以后也能从重做日志当中把你做过的那些操作再读取出来、再执行一遍，相当于就具备了持久性的效果。

---

### ACID 四个特性之间的关系

ACID 是事务的四大特征，这四个特征并不是平铺的四条并列规则，它们各自承担的角色不一样。

| 特性 | 在事务中承担的角色 |
| :--- | :--- |
| 原子性（Atomicity） | 基础：事务是一个不可分割的整体，要么都成、要么都退 |
| 一致性（Consistency） | 约束条件：事务前后都必须落在语义合法的状态上 |
| 隔离性（Isolation） | 手段：保证事务在操作过程中对其他事务是隔离的 |
| 持久性（Durability） | 目标：最终让磁盘上的数据发生真实的、永久的修改 |

原子性是基础，它体现的就是事务是一个整体；隔离性是手段，它保证整个事务在操作过程当中对其他事务是隔离的；一致性是我们的约束条件，要求从一种合法性状态到另一种合法性状态；而最终的目的是保证持久性——因为我们的操作说到底，是希望它对磁盘中的数据做出真实的修改，这就是持久化这件事。

顺着这个关系，可以说：事务是什么？其实我们就是在解释 ACID。我们针对数据库中的数据做那些操作，就是想让它们体现出这四个特性，只不过这四个特性被一个词概括起来了，这个词就叫「事务」。所以一提到事务，必然会提到这四个特性。

---

### 事务的状态与状态转移

在往下讲隔离性的具体内容之前，还有一个基本概念要先谈清楚：事务的状态。仍然拿刚才转账那个行为来体会，一个事务从开始到结束，会依次经过几种不同的状态。

#### 活动、部分提交与提交

**活动的（active）**：事务对应的数据库操作正在执行的过程当中，就说该事务处于活动的状态。比如现在正在操作第一条语句，以及第一条语句操作完、正要执行第二条语句，这个「正在执行」的过程都说明它是活动状态。

**部分提交的（partially committed）**：当事务中的最后一个操作执行完成了，但由于操作都是在内存中执行的，并没有对磁盘中的数据产生影响——也就是在把数据刷新到磁盘之前，我们称它处于部分提交的状态。这里要注意，事务里不一定只有两条语句，复杂一点可能有好几个 DML 操作：假设有四条，在这四条的执行过程中都是活动状态；一旦第四条执行完，也只是把内存里的数据改了——表数据都是以数据页的方式加载到内存里的——此时还没有把数据刷盘到磁盘上，所以叫部分提交的。

**提交的（committed）**：把处于部分提交状态的事务中的数据修改同步到磁盘上，其实就是做了一次持久化，这时候就称为提交的状态。它很好理解，就是部分提交的下一个阶段——刷盘这个操作；一旦刷新到磁盘上，就叫提交的状态。这是事务的最终状态之一：相当于数据执行完了，磁盘上的数据最终被改掉了。

#### 失败与中止

**失败的（failed）**：当事务处在活动的、或者部分提交的状态时，有可能遇到一些错误，比如数据库自身的错误、操作系统的错误，或者直接断电等等，导致它无法继续执行下去——下面不该刷盘了吗？没刷成；又或者是人为地让当前事务不能继续执行，我们就说这个事务处在失败的状态。它有可能从活动状态直接奔到失败，也有可能从部分提交的状态、还没刷盘就直接奔到失败。

**中止的（aborted）**：如果事务执行了一部分之后变成失败状态，说白了就是没能走到提交那一步。到了失败以后怎么办？要保住前面说的一致性：数据得从一个合法性状态到另一个合法性状态，你就得保证原子性。这意味着需要把已经在这个事务中做过的修改，还原到事务执行前的状态；这个整体还原的过程、或者叫撤销的过程，就叫做回滚。所以中止的状态其实就是遇到失败情况之后采取的一种处理方案：终止，把数据回滚回去。

#### 两个最终归宿

事务的最终状态只有两种：要么是提交的状态，要么是中止的状态。

```text
   ┌──────────────┐   最后一条 DML 执行完   ┌──────────────────┐   刷盘成功   ┌──────────────┐
   │ 活动的        │ ─────────────────────▶ │ 部分提交的        │ ──────────▶ │ 提交的        │
   │ active       │   （只改了内存数据）     │ partially comm.  │             │ committed    │
   └──────┬───────┘                        └────────┬─────────┘             └──────┬───────┘
          │                                         │                              │
          │  出错 / 断电 / 人为终止                   │                              ▼
          └────────────────┬────────────────────────┘                      最终归宿 ①
                           ▼
                   ┌──────────────┐   回滚（撤销已做的修改）  ┌──────────────┐
                   │ 失败的        │ ─────────────────────▶ │ 中止的        │
                   │ failed       │                        │ aborted      │
                   └──────────────┘                        └──────┬───────┘
                                                                  ▼
                                                           最终归宿 ②
```

*读图说明：活动状态和部分提交状态都可能直接走向失败；失败之后必须回滚，回滚完成才落到中止状态。能作为事务终点的只有「提交」与「中止」两者之一。*

这两种归宿跟前面讲的处理原则完全对得上：要么所有操作都执行成了，数据被更新、被持久化，这对应的就是提交的状态；要么执行了一半出现服务器宕机——宕机就相当于把事务推入了失败状态——那就得把已经做过的操作回滚回去，回滚之后的状态就称为中止的状态（也叫终止的状态）。二选一，没有第三种可能。

事务的 ACID 特性和事务的状态，到这里就讲完了。

## 162-显式事务与隐式事务
> 对应分集：P162 | 原始标题：《162-显式事务与隐式事务》

前面把事务的 ACID 特性、事务的状态都讲完了，但那些都是概念层面的东西。真到了写代码的时候，一个完整的事务到底该怎么落到语句上？我们平时敲的那些增删改，什么时候算一个事务、什么时候不算？

这里有两个词要分清楚：**显式事务**（explicit transaction）和**隐式事务**（implicit transaction）。我先说一句容易被忽略的话——前面讲 `truncate table`、讲 `delete from` 的时候，我们用的其实一直是隐式事务，只不过当时没有把这个名字点出来。

---

### 事务的完整过程

先把一个事务从头到尾的样子定下来，后面所有讨论都挂在这三步上。

第一步，**开启事务**。这是主动的动作，得由我们自己发一条语句把事务打开。

第二步，**一系列 DML 操作**。注意“一系列”三个字：有的事务里少，两条就够了；有的事务里多，可能几十条。我们反复举的 AA 给 BB 转账的例子，最少就是两条 `update`，一条减、一条加。

> **提示**：一条 DML 语句本身能不能构成一个事务？可以的。单独一条语句独立地构成一个事务，完全没问题。所以“一系列”是上限描述，不是下限要求。

第三步，**结束事务**。这一系列 DML 都执行完了，我们就要决定是把它持久化下来，还是放弃掉。这一步用的关键字是 `commit`——执行 `commit` 之后，事务进入**提交状态**。

#### 事务的两种结束状态

说到“结束”，我原本想叫它“事务的结束”，但严格讲，事务的结束状态有两种，不能只提一个：

- **提交状态**：用 `commit` 体现，数据持久化落库；
- **中止状态**：用 `rollback` 体现，这一串操作全部撤销。

两者都是结束状态，但只有这两者。也就是说，一个事务要收尾，只可能二选一：要么提交，要么回滚，没有第三条路。

```text
        START TRANSACTION / BEGIN
                  |
                  v
        +-------------------+
        |  一系列 DML 操作   |   （update / insert / delete ...）
        +-------------------+
                  |
        +---------+---------+
        |                   |
     COMMIT             ROLLBACK
        |                   |
        v                   v
   [ 提交状态 ]        [ 中止状态 ]
   数据持久化           操作全部撤销
```

图里只有两个收尾分支：`COMMIT` 走向提交状态，`ROLLBACK` 走向中止状态，中间没有别的出口。

---

### 显式事务的开启方式与三种模式

有显式事务，自然就对应着隐式事务，这一对概念是绑在一起的。我们先看显式事务的第一个问题：怎么开启。

#### 开启事务的两条语句 START TRANSACTION 与 BEGIN

开启事务可以用关键字 `start transaction`，也可以简单一点，直接写 `begin`。

```sql
-- 写法一：完整形式，功能更全
START TRANSACTION;

-- 写法二：简写形式
BEGIN;
```

有同学会想：既然两个都行，那我就选 `begin` 了，它比较短。选 `begin` 没问题，日常写事务用 `begin` 完全够。

但在功能上，两者不等价。`start transaction` 后面可以跟修饰内容，`begin` 不能跟——这是它们之间真正的区别。

#### 三种事务模式 READ ONLY、READ WRITE 与一致性读

`start transaction` 后面可以跟的东西有三样：

| 修饰项 | 作用 | 能否与另一模式共存 |
| --- | --- | --- |
| `READ ONLY` | 开启只读事务，只能查询 | 与 `READ WRITE` 互斥 |
| `READ WRITE` | 开启可读可写事务，默认值 | 与 `READ ONLY` 互斥 |
| `WITH CONSISTENT SNAPSHOT` | 开启一致性读（快照） | 与前两者均可搭配 |

`WITH CONSISTENT SNAPSHOT` 里的 `snapshot` 就是“快照”的意思，它开启的是一致性读。这条修饰与前两个不是互斥关系：`READ ONLY` 能搭配它，`READ WRITE` 也能搭配它。

但第一个和第二个绝对不能搭配。它们只能二选一——要么只读，要么可读可写，写成“既只读又可读可写”是没有意义的。

```sql
-- 只读事务：只能查询
START TRANSACTION READ ONLY;

-- 可读可写事务：可以增删改
START TRANSACTION READ WRITE;

-- 只读 + 一致性读快照
START TRANSACTION READ ONLY WITH CONSISTENT SNAPSHOT;

-- 可读可写 + 一致性读快照
START TRANSACTION READ WRITE WITH CONSISTENT SNAPSHOT;
```

那如果我写了 `start transaction`，后面什么都不跟呢？什么都不写时，默认就是 `READ WRITE`。

> **结论**：`START TRANSACTION` 后面不写修饰项时等价于 `START TRANSACTION READ WRITE`，这才是我们平时最常用的那种事务。

#### READ ONLY 对临时表的例外

`READ ONLY` 意味着只能读、不能增删改。但这里有个特例值得说清楚：严格来讲，只读事务不是对任何表都禁止增删改。

原因在于**为什么**要禁止。我们之所以不让你在只读事务里改表，是因为这张表可能被别的事务同时操作，你去改它会带来并发上的麻烦。但如果这张表只归当前事务使用、别的事务根本碰不到它，那就没有这个顾虑了，你是可以增删改的。

符合条件的表就是**临时表**（temporary table）。临时表只在当前会话当中起作用，别的会话看不到它。而我们说的“当前会话”，在事务语义下就是你当前这一个事务。

> **提示**：所以针对临时表，即使处在 `READ ONLY` 事务下也依然可以增删改。这种场景出现得比较少，理解它是特殊情况即可，不要由此推导出“只读事务其实能写”。

---

### 保存点 SAVEPOINT 与事务内部的部分回滚

`SAVEPOINT` 这个关键字，针对的是事务**中止**那一步。注意，事务的中止状态只有 `rollback` 一种体现方式，并不存在“`rollback to savepoint` 中止状态”这种说法。保存点是另一回事。

#### 保存点要解决的问题

`SAVEPOINT` 是“保存点”的意思。它解决的是一个很实际的麻烦：一个事务里操作特别多，你做到一半发现写错了，如果只能整体回滚，前面白做的全废，得从头再来一遍。

我们拿 AA 账户减钱来演示。开启事务之后：

1. 第一条操作，AA 减 100；
2. 第二条操作，AA 再减 100；
3. 第三条操作，AA 再减 100。

到这里如果执行 `commit`，AA 一共减掉 300，持久化保存下来了。如果走到最后执行 `rollback`，就回滚到最初的状态，这 300 块钱一分都没减。

问题出在中间：假设你要做的是减 100，结果不小心写成了加 100。这时候你一回滚，回滚到的是事务最初的状态——你可能已经做了好多正确的操作，全都被一并抹掉，中间这块都白做了。

#### 保存点的设置与回滚

解决办法就是在正确的位置先打一个点。在减完 100 块钱之后，设置一个保存点：

```sql
-- 在正确的中间位置设置保存点
SAVEPOINT s1;

-- 后面某一步写错了（本该减 100，写成了加 100），回滚到这个保存点
ROLLBACK TO SAVEPOINT s1;
```

执行 `rollback to s1` 之后，刚才那个写错的操作就失效了，相当于把事务回滚到了保存点所在的位置。

```text
START TRANSACTION
      |
      |-- update  AA 减 100        （正确）
      |
      |-- SAVEPOINT s1             <-- 正确位置，打点
      |
      |-- update  AA 加 100        （写错了）
      |
      |-- ROLLBACK TO SAVEPOINT s1  --> 撤销上一步，回到 s1
      |
      |-- update  AA 减 100        （重写正确）
      |
      +-- COMMIT  /  ROLLBACK      <-- 事务真正的收尾
```

注意图里的层次：`ROLLBACK TO SAVEPOINT` 只是回到打点位置，事务本身还在继续，所以最后仍然必须再走一次 `COMMIT` 或 `ROLLBACK`。

#### 回滚到保存点不等于中止状态

这一点我特别强调：执行 `rollback to s1` 之后，事务**没有**进入中止状态。它还在事务里面，还没结束。

所以在回滚到保存点之后，你还得接着考虑后面怎么办：

- 如果这时直接 `commit`，那么从 `start transaction` 到这里的所有操作一起生效，独立构成一个事务；
- 如果后面还要接着减，那就回滚到保存点之后继续往下做，做完再决定 `commit` 还是 `rollback`。

> **易错点**：`ROLLBACK TO SAVEPOINT` 不是事务的最终状态，它只是中间过程当中的一个便利手段。事务要结束，只有最后的 `COMMIT` 或 `ROLLBACK` 说了算。

保存点的价值就在这里：一个事务里可能有很多步骤绑在一起才是一个事务，你没法把它们拆开提交，但你可以用保存点把“到这里为止都做对了”这件事记下来。后半段写错了就回滚到点上重写，不用把前面全部重做一遍。

#### 保存点的释放

保存点用完、不再需要的时候，可以直接释放掉：

```sql
-- 设置保存点
SAVEPOINT s1;

-- 回滚到保存点
ROLLBACK TO SAVEPOINT s1;

-- 保存点不再需要时释放
RELEASE SAVEPOINT s1;
```

### 隐式事务与自动提交变量 autocommit

显式事务是“我自己主动开启”，隐式事务则相反：事务的边界不用你写 `start transaction` 或 `begin` 来划，系统按规则替你划好了。前面讲 `truncate table`、讲 `delete from` 的时候，我们虽然没有主动开启过事务，但事务照样存在、照样结束——那就是隐式事务。

隐式事务这块要先认识一个关键字：`autocommit`。

#### autocommit 变量的查看与修改

`autocommit` 是 MySQL 的一个系统变量。查看它：

```sql
SHOW VARIABLES LIKE 'autocommit';
```

默认情况下，这个变量的值是 `ON`。含义很直接：我们现在做的相关 DML 操作，都是**自动提交**的。

```sql
-- 关闭自动提交
SET autocommit = false;

-- 或者
SET autocommit = 0;

-- 再查看，值变成 OFF
SHOW VARIABLES LIKE 'autocommit';
```

> **提示**：`false` 与 `0`、`true` 与 `1` 在这里是等价的写法，`SHOW VARIABLES` 显示出来的则是 `ON` / `OFF`。别看到显示的 `OFF` 就以为设置没生效。

#### autocommit 为 ON 时每条 DML 独立成事务

默认 `autocommit = ON` 的情况下，**每一条 DML 操作都是一个独立的事务**。

我们写两条 DML 放在一起，它们不是“一个事务里的两条语句”，而是两个事务：

```text
autocommit = ON

  语句 1  --执行完立即 COMMIT-->  事务 1 结束
  语句 2  --执行完立即 COMMIT-->  事务 2 结束
```

也就是说，一条语句执行完之后，系统会默认替我们做一次 `commit`。`autocommit` 嘛，自动就提交了。一提交，这个事务就结束了。这就是“自动提交”这四个字的准确含义。

#### autocommit 为 OFF 时多条 DML 合并为一个事务

把自动提交关掉，情况立刻不同：DML 执行完之后不会自动 `commit`。此时把前面那两条语句放在一起，它们就不再各自成事务，而是**合在一起构成一个独立的事务**，直到你显式执行 `commit` 或 `rollback` 才算收尾。

```sql
-- 方式一：关闭自动提交，让多条 DML 归入同一个事务
SET autocommit = false;
UPDATE ...;      -- 语句 1
UPDATE ...;      -- 语句 2
COMMIT;          -- 上面两条一起生效；换成 ROLLBACK 则一起撤销
```

```text
autocommit = OFF

  语句 1  \
           >--- 同一个事务 ---> COMMIT / ROLLBACK
  语句 2  /
```

> **易错点**：`SET autocommit` 只对 **DML** 语句有效，对 **DDL** 操作是无效的。哪些操作即使关掉 `autocommit` 也照样会提交，下一节专门讲。

#### 第二种方式 autocommit 为 ON 时用 BEGIN 开启

除了上面这种“先把 `autocommit` 改成 `false`”的做法，还有第二种做法，它要和显式事务的开启语句结合起来用：**在 `autocommit` 仍然为 `true` 的情况下**，用 `start transaction` 或 `begin` 开启事务。

这里要特别明确一个前提：`autocommit` 是 `true`，没有改成 `false`。

在这种前提下，只要你在前面加了 `start transaction` 或 `begin` 这样的语句，后面的 DML 操作就不会自动提交了。系统看到你主动开启了事务，就默认不提交，把这几条 DML 归入你刚开启的这个事务里。最后再用 `commit` 或 `rollback` 结束它。

```sql
-- 方式二：autocommit 保持 ON，用 BEGIN 主动开启事务
-- 此时 autocommit 依然是 ON
START TRANSACTION;
UPDATE ...;      -- 语句 1，不会自动提交
UPDATE ...;      -- 语句 2，不会自动提交
COMMIT;          -- 或者 ROLLBACK
```

```text
autocommit = ON  但  BEGIN / START TRANSACTION 在前

  BEGIN
    |
  语句 1  \
           >--- 同一个事务（不自动提交）---> COMMIT / ROLLBACK
  语句 2  /
```

> **结论**：两种方式合起来看，更规范、更主动的写法是——自己主动开启事务，同时把 `autocommit` 改成 `false`，结束时按需要选择提交或回滚。这样事务的边界完全掌握在自己手里。

### 会触发隐式提交的操作类型

最后回到一个很关键的问题：哪些行为会**隐式地**把数据提交掉？注意这里说的隐式提交，意味着它**不受 `autocommit` 变量控制**——你把 `autocommit` 关成 `false` 也没用。

#### DDL 数据定义语言

第一类是**数据定义语言**（Data Definition Language，DDL）。这一类大家比较熟悉，不用多说。前面讲创建表、管理表的时候提到过的 `truncate table` 就属于 DDL，它会自动提交数据。

#### 用户、权限与账户相关语句

第二类是隐式地使用或修改 MySQL 数据库中的表。典型的是针对用户、权限、账户的这一系列操作：

```sql
ALTER USER ...;
CREATE USER ...;
DROP USER ...;
GRANT ...;
RENAME USER ...;
REVOKE ...;
SET PASSWORD ...;
```

这些语句也是会自动提交数据的。哪怕你前面正开着事务，碰到这种操作也白扯。

#### 未结束的事务后再次开启新事务

第三类是一个以后很可能会遇到的场景：你写了一个 `begin`，然后执行了增删改操作，事务正执行着呢——既没有写 `commit`，也没有写 `rollback`——紧接着你又写了一个 `begin`。

这时候上边那个还没结束的事务怎么办？答案是：**上边这个事务会自动提交**。这也叫隐式提交。

```text
BEGIN
  |
  DML 操作            （事务 1 进行中，未提交）
  |
BEGIN                 <-- 又开启一个新事务
  |                       ==> 事务 1 被隐式提交
  DML 操作            （事务 2）
  |
COMMIT / ROLLBACK
```

> **易错点**：第二次 `BEGIN` 不会“嵌套”进第一个事务，也不会报错等你先结束前一个——它直接把前一个事务提交掉。

#### autocommit 由 false 手动改为 on

第四类：当前 `autocommit` 系统变量值为 `false`，当我们手动把它调成 `on` 的时候，也会隐式提交前面所属的那个事务。

```sql
SET autocommit = false;
UPDATE ...;      -- 语句 1
UPDATE ...;      -- 语句 2；此时这两条还没提交

SET autocommit = true;   -- 一旦改成 true，前面这两条语句就被提交了

UPDATE ...;      -- 这一条开始按自动提交走
```

一旦写成 `true`，前面那两条语句就提交了——这就是它的作用。

#### 锁表、批量导入、复制与表维护语句

剩下的几类一并列出：

- **`LOCK TABLES` / `UNLOCK TABLES`**：锁定表或解锁表时，会隐式提交前面的事务；
- **`LOAD DATA`**：用 `LOAD DATA` 批量往数据库导入数据时，会隐式提交之前的操作；
- **MySQL 复制的相关语句**：`START SLAVE`、`STOP SLAVE`、`RESET SLAVE`、`CHANGE MASTER TO`，这些在主从复制里会遇到的操作，同样会导致隐式提交前面做过的事务；
- **表维护语句**：上一章讲过的分析表、检查表、优化表，这些行为也会隐式提交前面的事务。

```text
        会不会被隐式提交？
                |
      +---------+---------------------------+
      |                                     |
   DML 操作                           非 DML 操作
  （update/insert/delete）        （DDL、用户权限、锁表、
      |                            LOAD DATA、复制语句、表维护）
      |                                     |
  受 autocommit 控制                 不受 autocommit 控制
  ON  -> 每条独立自动提交            一律隐式提交
  OFF -> 合并为一个事务
```

简单来讲：**`autocommit` 这个变量主要约束的是 DML 操作**。不在这张控制网里的那些语句，该提交的时候一定会提交，跟你把 `autocommit` 设成什么无关。这一点要记牢。

### 显式事务与隐式事务对照

| 对比项 | 显式事务 | 隐式事务 |
| --- | --- | --- |
| 边界由谁划定 | 自己用 `START TRANSACTION` / `BEGIN` 主动开启 | 系统规则自动划定 |
| 受 `autocommit` 控制 | 开启后 DML 不再自动提交 | DML 受 `autocommit` 的 `ON` / `OFF` 控制 |
| 结束方式 | 显式 `COMMIT` 或 `ROLLBACK` | 自动提交，或由特定语句触发隐式提交 |
| 典型场景 | 多条 DML 需要同时成功或同时失败（如转账） | 单条 DML；DDL、用户权限、锁表、`LOAD DATA`、复制语句、表维护 |
| 部分回滚 | 可用 `SAVEPOINT` + `ROLLBACK TO SAVEPOINT` | 不适用 |

到这里，显式事务与隐式事务就说完了。要带走的是三件事：事务的收尾只有提交和中止两种状态；`START TRANSACTION` 比 `BEGIN` 多了模式和一致性读修饰，但两者开启的事务在结束方式上没有区别；以及 `autocommit` 只管得住 DML，管不住那些会隐式提交的语句。

## 163-事务的使用举例
> 对应分集：P163 | 原始标题：《163-事务的使用举例》

显式事务、隐式事务这两件事说清楚了，接下来就不必再停在概念上——我们回到代码层面，把开启事务、提交事务、回滚事务这一整套行为亲手走一遍，从代码里去体会它们各自的效果。

我会举三个例子，分别体会三件事：`COMMIT` 与 `ROLLBACK` 是怎么用的、InnoDB 和 MyISAM 在事务上差在哪里、"保存点"到底在什么场景下能救你一命。

不过在动手之前，得先小心一件事。

### 演示前的准备：把 autocommit 恢复成默认值

刚才讲显式事务和隐式事务的时候，我们把 `set autocommit` 改成过 `false`。这个改动还留在当前会话里，会直接影响下面的操作，所以第一步先查一下它现在是什么值：

```sql
SHOW VARIABLES LIKE 'autocommit';
```

查出来是 `OFF`。把它改回默认行为：

```sql
SET autocommit = true;
```

> **提示**：`autocommit` 的默认值本来就是 `true`。也就是说，接下来这组演示是在"默认情况"下做的——这个前提在后面第二种情况里是决定性的，先记住它。

然后把表结构刷新一下，看一眼当前库里有哪些表，避开它们，新建一张自己的表来用：

```sql
USE atguigudb2;
```

### 举例一：显式事务中的提交与回滚

先建表。这里刻意做得简单，只留一个字段：

```sql
CREATE TABLE user3 (
    name VARCHAR(15) PRIMARY KEY
);
```

`name` 是 `VARCHAR(15)`，并且直接声明成主键。

> **提示**：主键意味着这个字段的取值唯一；同时，InnoDB 会按照主键构建聚簇索引，也就是数据行本身就挂在这棵索引树上。

建好之后先查一眼：

```sql
SELECT * FROM user3;
```

不用怀疑，这张表里一条数据都没有。

接下来是三种情况。之所以叫「情况1、情况2、情况3」而不是「举例二、举例三」，是因为这三段的场景非常相似，都属于同一个案例——它们之间的差别只有一两行语句，而结果却完全不同。

#### 情况1：BEGIN 内的插入冲突与 ROLLBACK 落点

用 `BEGIN` 显式开启一个事务，然后插一条数据：

```sql
BEGIN;
INSERT INTO user3 VALUES ('张三');
SELECT * FROM user3;
```

以前讲 `TRUNCATE TABLE`、`DELETE FROM` 的时候，我们靠的是 `autocommit` 这个变量；现在换成显式开启事务的方式来体会。

这里先问一句：加了 `BEGIN` 之后，这条 `INSERT` 还会自动提交数据吗？不会了。而且要看清原因——**不是因为 `autocommit` 的事，是因为我们在前面加了一个 `BEGIN`**。

> **结论**：`BEGIN`（或 `START TRANSACTION`）一旦显式开启事务，事务内部的 DML 就不再自动提交，`autocommit` 在这个事务里不起提交作用，提交时机由我们自己决定。

此时查一下，张三就在表里。接着提交：

```sql
COMMIT;
```

提交之后，张三就持久化了——你可以理解为它刷盘到磁盘上，这件事确定下来了。

再开一个新事务：

```sql
BEGIN;                              -- 注意，这是一个全新的事务
INSERT INTO user3 VALUES ('李四');
```

`BEGIN` 意味着我们开启了一个新事务。这条 `INSERT` 执行成功，查一下肯定有李四。接着再插一条：

```sql
INSERT INTO user3 VALUES ('李四');  -- 报错：主键冲突
```

报错了。原因就是主键约束——主键要求字段的值唯一，重复的值加不进去。

> **易错点**：这里是「语句执行失败」，不是「事务自动回滚」。语句报错之后，事务只是进入**失败状态**；失败状态是个临时状态，事务本身并没有结束，接下来怎么处理由我们决定。

```text
失败状态的终止（衔接上一讲讲过的几种事务状态）

  活动状态 ── 某条语句执行出错 ──> 失败状态（临时状态）
                                        │
                                     ROLLBACK
                                        │
                                        v
                              终止：回到最近一次提交之后
```

图里要看清的是：出错之后事务停在失败状态，这个状态是临时的，需要我们显式执行 `ROLLBACK` 把它终止，才能回到最近一次提交之后的位置。

那现在来处理它：

```sql
ROLLBACK;
SELECT * FROM user3;
```

先别急着执行，想一想：回滚之后表里还剩几条记录？

`ROLLBACK` 的含义是**回滚到最后一次 `COMMIT` 之后**。这里最近的一次提交，就是上面那条 `COMMIT`，而它落在"插入张三"之后、"插入李四"之前——所以李四这条数据被撤销，查出来只剩张三。

还要注意一点：这次 `ROLLBACK` 并不会顺手替你提交什么，因为我们一直待在事务里，跟前面"加了 `BEGIN` 就不自动提交"是同一个原因。

```text
情况1 的时间线（全程被 BEGIN 框住，没有自动提交）

  BEGIN ── INSERT 张三 ── COMMIT ── BEGIN ── INSERT 李四 ── INSERT 李四(冲突) ── ROLLBACK
                           ▲                                                    │
                           └─────────── 回滚落点：只剩张三，李四被撤销 ─────────┘
```

图里那条竖线标出的是回滚落点：`ROLLBACK` 只撤销最后一次提交之后的修改，也就是李四那一段。

#### 情况2：没有 BEGIN 时回滚落点的前移

先把表清干净，把上一步残留的数据影响剥掉：

```sql
TRUNCATE TABLE user3;
SELECT * FROM user3;
```

> **提示**：`TRUNCATE TABLE` 属于 DDL，DDL 操作会**自动提交**数据，不受 `autocommit` 变量影响。也就是说，不管前面 `autocommit` 是 `true` 还是 `false`，它执行完一定会提交一次。

清空之后，把刚才那套操作原封不动地再来一遍：

```sql
BEGIN;
INSERT INTO user3 VALUES ('张三');
COMMIT;                             -- 张三持久化到磁盘
SELECT * FROM user3;                -- 张三
```

到这里跟情况1完全一样。**区别在下一步**——这次我上来就直接插入，不再用 `BEGIN`：

```sql
INSERT INTO user3 VALUES ('李四');  -- 执行成功
SELECT * FROM user3;                -- 张三、李四都在
INSERT INTO user3 VALUES ('李四');  -- 又报错，事务再次进入失败状态
ROLLBACK;
SELECT * FROM user3;
```

最后这次 `SELECT` 的结果是：**张三和李四都在**。

跟情况1不一样吧？为什么？差别就在那个 `BEGIN`。

情况1有 `BEGIN`，所以事务里的 DML 不自动提交；情况2这次没有 `BEGIN`，于是"默认情况"生效了——所谓默认情况，就是 `autocommit = true`，此时 DML 操作**会自动提交数据**。那条成功的 `INSERT 李四` 执行完就已经自动提交，李四被持久化了；后面那条语句虽然失败了，但它本来也没写进去。

> **定义**：所谓"默认情况"，指的就是 `autocommit = true`。此时每一条 DML 语句执行完都会被自动提交，效果上相当于每条语句自己就构成一个事务。

那 `ROLLBACK` 呢？它依然回滚到最后一次 `COMMIT` 之后，而**自动提交也算一次提交**，最近的那次提交就在 `INSERT 李四` 之后。所以结果就是张三、李四都在。

前面说的失败状态在这里同样只是临时的：我们用 `ROLLBACK` 把这个事务终止掉，回到最初的状态——只不过这个"最初的状态"里，已经包含了自动提交过的李四。

```text
情况2 的时间线（最后那段 INSERT 没有 BEGIN，落回默认的自动提交）

  BEGIN ── INSERT 张三 ── COMMIT ── INSERT 李四(自动提交) ── INSERT 李四(冲突) ── ROLLBACK
                                       ▲                                          │
                                       └──── 回滚落点在这里：张三 + 李四 ──────────┘
```

对比两张图就能看清：同样一次 `ROLLBACK`，落点却往前挪了一段，因为中间多了一次看不见的自动提交。

两种情况放在一起对照：

| 环节 | 情况1：有 `BEGIN` | 情况2：没有 `BEGIN` |
| :--- | :--- | :--- |
| 提交时机 | 只有显式 `COMMIT` 才提交 | `autocommit = true`，DML 执行完即自动提交 |
| `INSERT 李四` 之后 | 数据留在事务里，未提交 | 数据已经落盘 |
| 冲突语句的效果 | 事务进入失败状态（临时状态） | 同样进入失败状态，但该语句本身没写入 |
| `ROLLBACK` 的落点 | 显式 `COMMIT` 之后 | 自动提交的那条 `INSERT` 之后 |
| 回滚后的结果 | 只剩张三 | 张三、李四都在 |

#### 情况3：completion_type = 1 时的提交行为

还是先清表：

```sql
TRUNCATE TABLE user3;
SELECT * FROM user3;
```

这一次在第一个 `BEGIN` 之前，多加一行变量设置。两个 `@` 前缀表示这是系统变量：

```sql
SELECT @@completion_type;      -- NO_CHAIN，对应数值 0
SET @@completion_type = 1;
```

查出来是 `NO_CHAIN`，它对应的数值是 0，也就是"没有链式"的意思。设成 1 之后，就开启了一种链式的行为。

设好之后，流程和情况2几乎一样：

```sql
BEGIN;
INSERT INTO user3 VALUES ('张三');
COMMIT;                             -- 张三持久化
SELECT * FROM user3;                -- 张三
INSERT INTO user3 VALUES ('李四');  -- 成功
INSERT INTO user3 VALUES ('李四');  -- 失败
ROLLBACK;
SELECT * FROM user3;                -- 结果：只有张三！
```

和情况2相比，只多了那一行 `SET @@completion_type = 1`，结果却从"张三李四都有"变成了"只有张三"。为什么？

因为设成 1 之后，`COMMIT` 就不再是单纯地结束事务了，它相当于执行 `COMMIT AND CHAIN`——**提交事务的同时，自动帮我们开启一个相同隔离级别的新事务**，这就是链式事务。所以后面那条成功的 `INSERT 李四`，并不是在"没有事务、默认自动提交"的状态下执行的，它落在这个自动开启的新事务里；既然在事务里，它就不会被自动提交，随后被 `ROLLBACK` 一并撤销。

```text
completion_type = 1 时，COMMIT 的实际动作

  COMMIT ──┬── 提交当前事务（张三落盘）
           │
           └── 自动开启一个新事务（隔离级别与刚才相同）
                          │
                          v
              INSERT 李四 落在这个新事务里，未提交
                          │
                          v
                 ROLLBACK 把它一起撤销，只剩张三
```

也就是说，那个变量改变的不是某条语句的写法，而是 `COMMIT` 这个动作本身的含义。

### completion_type 的三个取值

顺着这个变量，把它的三个取值一次说清。

| 取值 | 提交时的行为 | 说明 |
| :--- | :--- | :--- |
| `0` | 正常提交事务，下一个事务需要重新用 `START TRANSACTION` 或 `BEGIN` 开启 | 默认值，显示为 `NO_CHAIN` |
| `1` | 相当于 `COMMIT AND CHAIN`：提交后自动开启一个相同隔离级别的新事务 | 链式事务 |
| `2` | 相当于 `COMMIT AND RELEASE`：提交后自动与服务器断开连接 | `RELEASE` 是释放、断开连接的意思 |

取值 0 就是我们平时最熟悉的行为；取值 2 的场景里，提交事务之后连接会自动断开，这一点稍微留意一下。

### 事务的五种常见分类

这个分类我一开始是放在第一章里的，但那时候大家还没怎么接触过事务，一讲就蒙了。既然现在提到了链式事务，就借着这个变量梳理一遍——看着挺复杂，其实比较简单。

1. **扁平事务**：就是举例一里演示的那些。用 `BEGIN` 开启，用 `COMMIT` 或 `ROLLBACK` 结束。
2. **带保存点的扁平事务**：扁平事务里用上了 `SAVEPOINT`，也就是下面举例三要演示的写法。
3. **链式事务**：一个事务由多个子事务构成。执行完一个事务并 `COMMIT` 之后，通过一个触发器触发下一个事务的执行。
4. **嵌套事务**：一个大事务里涉及几个子事务，子事务还可以再往下嵌套，彼此之间是有嵌套关系的。
5. **分布式事务**：数据分布在网络中不同的节点上，需要对不同节点的资源做调用和读写操作时，就要用到分布式事务。真做分布式系统，这个是必须要讲的。

> **提示**：这五类在这里先做个了解即可，重点是把它跟前面那几个变量的行为对上号。

### 举例二：InnoDB 与 MyISAM 在回滚上的差异

举例一体会的是 `COMMIT` 和 `ROLLBACK` 的用法，举例二换一个角度：看看 InnoDB 和 MyISAM 的区别。

前面已经说过，MyISAM 本身**不支持事务**。但"不支持"到底是个什么表现？建两张表来对比：

```sql
CREATE TABLE test1 (i INT) ENGINE = InnoDB;
CREATE TABLE test2 (i INT) ENGINE = MyISAM;
```

先看我们比较熟悉的 InnoDB 表 `test1`：

```sql
BEGIN;
INSERT INTO test1 VALUES (1);
SELECT * FROM test1;    -- 有 1
ROLLBACK;
SELECT * FROM test1;    -- 没有数据了
```

回滚正常生效，数据被撤销。

同样一套操作换成 MyISAM 表 `test2`：

```sql
BEGIN;                  -- 对它没什么影响
INSERT INTO test2 VALUES (1);
SELECT * FROM test2;    -- 有 1
ROLLBACK;
SELECT * FROM test2;    -- 1 还在！
```

| 存储引擎 | 回滚后的结果 | 原因 |
| :--- | :--- | :--- |
| InnoDB（`test1`） | 数据被撤销 | 支持事务，回滚生效 |
| MyISAM（`test2`） | 数据依然在 | 无视事务的存在，添加成功就是成功 |

> **结论**：MyISAM 表会无视事务的存在——添加成功就是成功了，回滚不起任何作用。这就是"MyISAM 不支持事务"最直观的体现。

> **易错点**：在 MyISAM 表上执行 `BEGIN`、`ROLLBACK` 都不会报错，但也都不会生效。这种失效是静默的：语句照跑、日志照过，数据却已经落盘，等到发现回滚没管用的时候，数据已经回不去了。

### 举例三：SAVEPOINT 与 ROLLBACK TO

最后一个例子体会保存点。先建一张带金额字段的表：

```sql
CREATE TABLE user3 (
    name    VARCHAR(15),
    balance DECIMAL(10, 2)
);
```

这里没写引擎，默认就是 InnoDB。

先造一条基础数据，并且让它单独构成一个已经提交的事务：

```sql
BEGIN;
INSERT INTO user3 (name, balance) VALUES ('张三', 1000);
COMMIT;
SELECT * FROM user3;    -- 张三 1000.00
```

现在开一个新事务，做两次扣款：

```sql
BEGIN;
UPDATE user3 SET balance = balance - 100 WHERE name = '张三';   -- 900
UPDATE user3 SET balance = balance - 100 WHERE name = '张三';   -- 800
SAVEPOINT s1;
```

保存点的意思，是**给当前位置临时做一个记号**：前面执行过的操作都没问题，就在这儿记一笔。

> **提示**：这有点像在虚拟机里打快照——前面整台虚拟机都是好的，先拍一个快照；万一之后出了问题，还能回滚到快照这一层。

保存点设好之后继续改。本来还想再减 100，结果手一哆嗦，写成了加 1：

```sql
UPDATE user3 SET balance = balance + 1 WHERE name = '张三';     -- 801，写错了
SELECT * FROM user3;    -- 801
```

一看整错了，只想把这条错误的操作丢掉。这时候就回滚到保存点，`SAVEPOINT` 关键字不用再写，直接写保存点名：

```sql
ROLLBACK TO s1;
SELECT * FROM user3;    -- 回到 800
```

余额从 801 回到 800，那条加 1 的操作失效了。

```text
举例三的余额变化轨迹

  1000 ── update -100 ──> 900 ── update -100 ──> 800
                                                  │
                                          SAVEPOINT s1
                                                  │
                                   update +1（写错了）──> 801
                                                  │
                                     ROLLBACK TO s1 ──> 800
                                                  │
                                        ROLLBACK ──> 1000
                                     （回到最初那次 COMMIT 之后）
```

沿着这条轨迹看，保存点把事务切成了两段：保存点之前的修改被保留，保存点之后的错误被丢弃。

这里有个关键区别，一定要注意：**回滚到保存点不是事务的终止状态**。事务的结束状态只有两个——提交，或者整体回滚。`ROLLBACK TO` 只是把事务拉回保存点，事务本身还在进行中。

既然还在事务里，就可以继续收尾。有同学可能会想：都已经回滚到保存点了，还能再回滚吗？试一下：

```sql
ROLLBACK;
SELECT * FROM user3;
```

结果是 1000——整个事务被回滚，回到最初那次 `COMMIT` 之后。也就是说，保存点只是事务内部的一个临时落脚点，它挡不住事务最终的两种结局。

```text
保存点之后的两种收尾方式

  事务开始 ── 若干正确操作 ── SAVEPOINT s1 ──┬── 出错 ──> ROLLBACK TO s1 ──> 继续做完 ──> COMMIT
                                             │
                                             └── 整个不做了 ──> ROLLBACK ──> 回到上次 COMMIT 之后
```

这张图给出的是保存点的定位：它只是一次中途的纠错机会——改对之后接着往下做，最后由 `COMMIT` 收尾；如果整件事都不想做了，那就整体 `ROLLBACK`，保存点也跟着一起被撤销。

> **结论**：保存点解决的是"事务做到一半写错了"的问题。假设一个事务要做五件事，现在做成了三件，这三件都没写错，你怕后面写错，就在这儿设一个保存点；后面真的写错了，回滚到保存点，这一条操作失效，接着再写一条正确的。整个事务要么整体回滚，要么把剩下的执行完，最后 `COMMIT`。

这几个例子本身都不复杂，针对的都是**单个事务内部**的行为。下来自己动手写一写、感受感受。再往下，就该看事务的并发问题了——那涉及多个事务之间相互交互的行为。

## 164-数据并发问题与4种隔离级别
> 对应分集：P164 | 原始标题：《164-数据并发问题与4种隔离级别》

事务这一块，前面我们已经过了两个问题，现在到第三个：隔离级别。

怎么突然冒出来一个隔离级别？它有它的来处。第一处，我们讲事务的 ACID 特性时，里面那个 `I` 就是 Isolation，隔离性——当时我没有展开去说，留了个点在今天。第二处，讲"如何使用事务"的时候，不管是显式事务还是隐式事务，我们谈的都是**一个**事务：它怎么开启、怎么接着做多条 DML、最后怎么 `commit`、怎么 `rollback`。这算是把一个事务的完整生命周期讲完了，但那始终是它一个人在动数据。

真实情况没这么清静。表里有这么一条记录，我们的事务要去增删改它；同时另外的事务也想去增删改这条记录，而且改的还是同一个字段。这个时候该怎么办？这就落到数据的一致性上了——也就是我们现在要谈的隔离性、隔离级别的问题。

我们这一讲的推进顺序也是顺着这个疑问走的：先把并发可能引发的问题在理论上说清楚，再看 MySQL 针对这些问题是怎么设置隔离级别，来权衡并发性与隔离性的。

### 客户端/服务器架构下的并发访问

MySQL 是客户端/服务器（Client/Server）架构的软件，这一层结构是并发问题的物理来源。服务器端就是我们说的 DBMS；客户端可以有很多个，每一个客户端拿到针对服务器端的一个连接之后，就可以发送请求了。发一个，接着还能发第二个、第三个，这几个请求有可能就构成一个事务，记作 T1。另外的客户端也来访问，那就是 T2、T3……它们访问的可能是 DBMS 里某张表，具体讲，就是某一条数据。

```text
   客户端 A            客户端 B            客户端 C
      |                   |                   |
      | 连接              | 连接              | 连接
      v                   v                   v
  ------------------------------------------------------
   DBMS（服务器端）：同一张表、同一条记录
  ------------------------------------------------------
      ^                   ^
      |                   |
   请求1 -> 请求2 -> 请求3        请求……
   ===== 事务 T1 =====          ===== 事务 T2 =====
```

读图说明：并发在数据库里并不是抽象概念，它就是多个连接各自把若干请求打包成事务，然后一起去碰同一张表、同一条记录。

所以"多个事务并发"具体体现出来就是多个请求，只不过这些请求分布在不同的（也就是并发开启的）事务当中来体现。那么如果我们放任这种并发，数据就有可能出现不一致，准确性也难以保证。这就体现为隔离性的问题：隔离性与并发性，我们该如何权衡？这就是接下来要面对的场景。

> **提示**：本讲先只谈并发会产生哪些问题，以及 SQL 标准给了哪几种隔离级别；具体怎么查看、怎么设置隔离级别，以及各个级别下的实机演示，放到后面几讲去做。

### 示例表与"不串行"这个前提

先用一张很小的表把后面的例子都挂上去。表里三个字段：学号 `number`、姓名 `name`、班级 `class`，`number` 是主键，这没毛病。往里加一条记录：`number = 1`、叫小谷、一班。查询出来就是这样一条记录。

| number（学号） | name（姓名） | class（班级） |
| --- | --- | --- |
| 1 | 小谷 | 一班 |

后面凡是说"这条记录"，指的都是这一行。

在动手分析之前，必须先约定一个前提：我们要讨论的并发问题，是**在不保证串行执行**的前提下才存在的。

串行执行是什么意思？就是一个事务针对表中的数据执行完了，下一个事务再进来。这种情况下肯定不会导致数据一致性问题——可是它的性能太低了。我们真正要考虑的，是事务之间有交叉访问的情况，说白了就是要有并行的效果。四种并发问题全都长在这种交叉里。

> **提示**：这些场景我暂时不逐个演示，原因是它们必须在具体的隔离级别下去演示才有意义。先把理论说清楚，一会儿再演示。

### 并发访问可能引发的四类问题

在交叉访问的前提下，都可能产生哪些问题？一共四个：脏写、脏读、不可重复读、幻读。名字都带点情绪，其实每一个对应的都是"A 看到了本不该看到的东西"的一种具体情形。先把它们横向摆在一起看：

| 问题 | 事务 B 的动作（相对事务 A 的读） | 事务 A 的观察结果 |
| --- | --- | --- |
| 脏写（Dirty Write） | A 改写之前，B 已经改过但未提交 | A 提交成功之后，值被 B 的回滚带回了改动前 |
| 脏读（Dirty Read） | A 读之前，B 已经改过但未提交 | A 读到了 B 那份未提交、随后被回滚掉的值 |
| 不可重复读（Non-Repeatable Read） | A 第一次读之后，B 改并提交 | A 第二次读同一个字段，值不一样了 |
| 幻读（Phantom Read） | A 第一次读之后，B 插入新行并提交 | A 第二次读同一个范围，行数变多了 |

下面一个一个把过程走完。

#### 脏写（Dirty Write）

> **定义**：事务 A 修改了另一个**未提交**事务 B 修改过的数据，就发生了脏写。

未提交意味着什么？意味着它有可能回滚。这就是脏写危险的根子。

一个事务其实是在一个会话、一次连接里体现的，所以下面把两个事务写成 Session A 和 Session B。过程按时间排开是这样：

| 时刻 | 事务 A（Session A） | 事务 B（Session B） |
| --- | --- | --- |
| T1 | `begin` 开启事务 | `begin` 开启事务 |
| T2 | | 把姓名字段由小谷改成李四（未提交） |
| T3 | 把姓名由李四改成张三，然后 `commit` 提交 | |
| T4 | | `rollback` 回滚，值回到小谷 |
| T5 | `select` 一查，读出来的是小谷 | |

改动链条是小谷 → 李四 → 张三，最后又回到小谷。事务 A 那边做了 `commit`，言外之意就是我们非常确定这个数据应该已经写成功、甚至刷盘落定了；结果事务 B 一 `rollback`，回滚到它自己操作之前的状态，李四那次修改等于白做。

于是事务 A 一去查询就懵圈了：我明明改成张三，也 `commit` 成功了，`select` 一下，小谷出来了。

> **结论**：脏写是四个问题里最严重的——我们自己提交的数据，竟然被别人给回滚掉了。这很不靠谱，接受不了。

#### 脏读（Dirty Read）

> **定义**：事务 A 读取了已经被事务 B 更新、但是还未提交的字段。因为 B 没有提交，之后如果 B 回滚，事务 A 读取的内容就是临时且无效的。

第一次接触这类内容看着会有点生疏，还是用同一条记录走一遍：

| 时刻 | 事务 A（Session A） | 事务 B（Session B） |
| --- | --- | --- |
| T1 | `begin` 开启事务 | `begin` 开启事务 |
| T2 | | 把姓名由小谷改成张三，**没有提交** |
| T3 | 去读这条记录，读出来的竟然是张三 | |
| T4 | `commit`（它没改数据，这个提交只是把事务 A 结束掉） | |
| T5 | | `rollback` 回滚，值回到小谷 |

注意 T3 这一下：正常来讲，磁盘当中写入的还是小谷；但事务 A 没有读出小谷，它读的是张三。事务 B 从头到尾没有提交，所以它有权回滚，一回滚小谷就回来了——那份张三从来没算数过。

> **易错点**：脏读的定义里有两个条件必须同时满足——"被别的**事务**更新"且"**未提交**"。数据被读过之后对方回滚了，读它的人拿到的就是一份无效数据，这就是脏读。

#### 不可重复读（Non-Repeatable Read）

> **定义**：事务 A 读取了一个字段，随后事务 B 更新了这个字段；事务 A 再去读这个字段，发现值不一样了。

`Non-Repeatable` 这个词反过来念就懂了：你要是能重复读，那就没问题；一旦重复读出来不一样，问题就来了。

| 时刻 | 事务 A（Session A） | 事务 B（Session B） |
| --- | --- | --- |
| T1 | `begin` 开启事务 | |
| T2 | 读 `number = 1` 这条记录，此时存的是王五，读出来就是王五 | |
| T3 | | `update` 把王五改成张三，并且 `commit` 提交 |
| T4 | 再去读同一条记录，读出来的是张三 | |
| T5 | | 后面若再有人把它改成李四并提交 |
| T6 | 再读，就成了李四 | |

T3 这一次提交相当于默认场景：`autocommit` 就是 `true`，改完即提交。所以事务 A 第二次读到的是别的用户已经提交的数据。刚开始读的是王五，一会儿再读变成张三，李四再改一次就成李四——每次重复去读，值都不一样，这就是不可重复读。

有同学会说：这不很正常吗？从这个并发问题上讲，它也算个问题。你之所以觉得正常，是因为我们平时开发里根本没考虑并发问题，觉得这个可以接受——可以接受，不等于它不是个问题。

#### 幻读（Phantom Read）

> **定义**：事务 A 从一张表中读取了一个字段（一个范围），随后事务 B 在该表中**插入**了一些新的行；事务 A 再去读取同一张表时，发现多了几行。

幻读，跟出现幻觉一样。这里的关键词是"插入"，注意它是插入行为，跟上面不可重复读的更新行为不是一回事。

| 时刻 | 事务 A（Session A） | 事务 B（Session B） |
| --- | --- | --- |
| T1 | `begin` 开启事务 | |
| T2 | 读 `number > 0` 的记录，此时只找到张三 | |
| T3 | | 插入一条赵六，并自动 `commit` 提交 |
| T4 | 再读 `number > 0`，张三和赵六都出来了 | |

一开始只有一条记录，再去查询变成两条，多出来一条赵六。感觉就像发生了幻觉一样。多出来的这条记录，我们自然就称之为**幻影记录**。

同样地，你可能觉得这很正常：人家事务往表里加入了行，你再读可不就多出几个。还是那句话——我们平时处理隔离性问题时没考虑它，或者认为它可以接受，但得先认可它是一种问题。

#### 与幻读相邻的两种情形

这里有两个点需要特别关注，考试和面试都容易在这里设陷阱。

第一，如果 Session B 做的是**删除**记录，Session A 再去查发现记录变少了，这**不算**幻读。因为幻读强调的是插入了一些新的行、是再读的时候"多了一些东西"；多出来的那条才叫幻影记录，删掉的不算。

第二，对于先前能查到的数据，之后又读不到了（少了一些数据），非要追究的话，可以理解成**不可重复读**的场景：刚读的时候有这几条，再读的时候少了，相当于重复读的时候发生了变更，归到不可重复读里。

> **结论**：幻读强调的是"多了东西"，是一个插入行为；变少的情形不是幻读，最多归入不可重复读。这一点一定要小心。

### SQL 标准给出的四种隔离级别

四个并发问题到这里就讲完了：脏写、脏读、不可重复读、幻读。接下来要看的是 SQL 标准——注意，是 SQL 标准，还没具体到 MySQL——针对这四个问题给我们提供了几种隔离级别。

隔离级别是什么意思？即：这四个问题，到底是全部解决，还是只解决其中一部分，还是怎么样？

这里之所以会有"只解决一部分"这个选项，是因为全都解决意味着隔离性、数据一致性非常好，但整个并发性会变得特别差；反过来，全都不解决，并发性很好，但隔离性、数据一致性很差，脏读之类的问题我们接受不了。所以这里要**达到一个平衡**：对并发性要求高一点，就怎么选；对并发性要求没那么高，就怎么选。于是按"解决这四个问题的不同程度"，分出了几种隔离级别。

#### 四个问题的严重程度排序

先给问题本身排个序，隔离级别的取舍才有依据。我们认为严重程度从高到低是：脏写、脏读、不可重复读、幻读。

| 严重程度（高 → 低） | 问题 | 为什么排在这里 |
| --- | --- | --- |
| 1 | 脏写（Dirty Write） | 自己已经提交的数据居然没写进去，绝对接受不了 |
| 2 | 脏读（Dirty Read） | 读到了别人未提交、随后被回滚的数据，同样接受不了 |
| 3 | 不可重复读（Non-Repeatable Read） | 同一事务内两次读同一个字段值不同，一致性被破坏 |
| 4 | 幻读（Phantom Read） | 同一事务内两次读同一个范围行数不同，影响相对最小 |

#### 四种隔离级别的名称

SQL 官方标准设置了四种隔离级别：

- `READ UNCOMMITTED`，读未提交；
- `READ COMMITTED`，读已提交；
- `REPEATABLE READ`，可重复读；
- `SERIALIZABLE`，可串行化。

#### 隔离级别对四个问题的解决情况

把这四种级别和上面的排序对起来看，就是一张四列的表格。有一个细节值得注意：表格里**没有脏写**这一列。为什么呢？因为这四种隔离级别**都**解决了脏写的问题——脏写是我们绝绝对接受不了的，所以它被排除在外，不用再逐个比较。表格里另外还多了一列关于锁、关于加锁读的情况，那是后面专门讲锁的时候再说的事。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED`（读未提交） | 可能发生 | 可能发生 | 可能发生 |
| `READ COMMITTED`（读已提交） | 已解决 | 可能发生 | 可能发生 |
| `REPEATABLE READ`（可重复读） | 已解决 | 已解决 | 可能发生 |
| `SERIALIZABLE`（可串行化） | 已解决 | 已解决 | 已解决 |

读表说明：四种级别对脏写都是"已解决"，所以脏写不占一列；剩下的三个问题严重程度依次降低，所以解决的时候优先考虑严重的那个——级别越往下，解决的问题越多。

---

### 四种隔离级别的逐个说明

#### READ UNCOMMITTED（读未提交）

读未提交能够解决脏写问题，但脏读、不可重复读、幻读这三个问题一个也解决不了，也就是说这三个都可能发生。

为什么脏读会发生？因为在这个级别下，事务 A 有可能读取到另外一个事务 B 更新过的、但没有提交的数据——它读到了人家那份未提交的东西，这就是脏读，它解决不了。

> **结论**：读未提交这个级别我们其实是接受不了的。所以平时给数据库设置隔离级别的时候，这种情况我们都没有选。

#### READ COMMITTED（读已提交）

读已提交解决了脏读的问题。也就是说，一个事务针对表中这个字段，只能读到别人**已经提交**的值。

还是用同一条记录体会：B 先把这个字段由小谷改成张三。A 去读的时候先看张三提交没提交——没提交，A 读到的还是小谷；提交了，A 读到的就是张三。也就是说，A 不会在 B 没有提交张三的时候把张三读出来。脏读问题就这样被解决了。

对于 Oracle 来讲，默认使用的就是这个隔离级别。相当于 Oracle 就没有在乎不可重复读和幻读问题。

#### REPEATABLE READ（可重复读）

`repeatable` 就是可重复的读，这个级别是 MySQL 默认使用的隔离级别，相当于比 Oracle 的级别要高一些。越往下，隔离级别越高，解决的问题越多，也就意味着并发性越差——到最后就都成串行化了。

可重复读解决了脏读，也解决了不可重复读。这意味着：事务 A 读取了一条记录之后，事务 B 对相应数据做了修改、并且还提交了；事务 A 再去读，读到的其实还是 B 修改之前的那份数据。这样重复读的时候，数据都是一样的。

> **提示**：可重复读和读已提交的差别要体会一下。读已提交是"人家先改了、也提交了，你再去读"，你读到新值；可重复读是"你先读了一次，人家改了、也提交了，你再读"，你读到的还是原来那份提交之前的数据。同样是"别人改了并提交"，先后顺序不同，读到的结果就不同。

#### SERIALIZABLE（可串行化）

可串行化把这几个问题相当于全都解决了，幻读也不会出现。

它的行为是：事务 A 去读表里的记录，比如一开始读到了三条；其他事务想对它进行修改等操作，但事务 A 再去读的时候，还是这三条记录，不会多出来。换句话说，事务 A 占用着这张表、或者占用着这一行记录，其他事务这时候都得等待。这已经不是并发问题了，已经走到了串行化的场景。所以在这种场景下，它的性能是十分低下的，并发性能十分低下。

---

### 隔离级别与并发性能的权衡

把四种级别按解决问题的多少排成一列，并发性能的变化方向就一目了然了：

```text
隔离级别                          解决的问题                        并发性能
-------------------------------------------------------------------------
SERIALIZABLE     脏写 + 脏读 + 不可重复读 + 幻读                    最差
REPEATABLE READ  脏写 + 脏读 + 不可重复读                           较差
READ COMMITTED   脏写 + 脏读                                        较好
READ UNCOMMITTED 脏写                                               最好
-------------------------------------------------------------------------
        隔离级别越高  -->  解决的问题越多  -->  并发性能越差
```

读图说明：隔离级别越高，解决的问题越多，并发的性能就会越差——有利有弊，这就是前面说的"要达到一个平衡"的那杆秤。

并发的问题和这四种隔离级别，大家需要能够理解，并且能用自己的语言表达出来。面试当中其实也常来问这样的问题。

## 165-MySQL隔离级别的查看和设置
> 对应分集：P165 | 原始标题：《165-MySQL隔离级别的查看和设置》

上一页板书上我把一个单词写错了：`read committed` 被我写成了 `red committed`，少了一个 `a`。重录的时候发现了，这一页重新写、图也重新截了一遍，顺便把两个最容易串的级别名钉牢——**read uncommitted 是读未提交，read committed 是读已提交**，就差一个字母，级别完全不同。

四种隔离级别到这里算是说明白了。但说明白的是 SQL 标准里的**规定**，规定不等于产品实现。所以我们紧接着要落到具体数据库上，看清楚三件事：它支持哪几种、默认是哪一种、我们怎么去查和改。

### 各数据库对四种隔离级别的支持

有同学可能会问：四种隔离级别是标准里定好的，这还有什么可讲的？

关键在于，**标准里规定的东西，不一定在每个数据库里都被完美支持**。举一个最有代表性的例子：Oracle 只支持其中的两种——`read committed` 和 `serializable`。

你顺着往下想一步：一个数据库只支持这两种，那它的默认隔离级别还能是谁？不可能是 `serializable`，并发性实在太差了。所以 Oracle 的默认级别只能是**读已提交**。

我们这门课的重点 MySQL 就不一样了：**四种它全都支持**，默认的隔离级别是 `repeatable read`，也就是**可重复读**。

默认可重复读意味着什么？意味着 MySQL 在默认情况下，**脏读的问题能解决，不可重复读的问题也能解决**。而且 MySQL 的可重复读比标准还多做了一点：它**在一定程度上连幻读也能解决**。这跟官方标准里的规定是有区别的，怎么做到的？后面讲 MVCC 的时候再展开，这里先把结论记住。

| 数据库 | 支持的隔离级别 | 默认隔离级别 |
| :--- | :--- | :--- |
| Oracle | `read committed`、`serializable` | `read committed`（读已提交） |
| MySQL | `read uncommitted`、`read committed`、`repeatable read`、`serializable` | `repeatable read`（可重复读） |

读表说明：Oracle 只实现了标准四种里的两种，默认落在两者中较松的那一档；MySQL 四种全部实现，默认落在中间一档的可重复读上。

接下来的任务清单也就清楚了：先会**查**（默认级别到底是什么），再会**改**（能不能把级别换掉），然后才谈得上用代码去演示不同级别下"什么叫脏读""什么叫不可重复读"。要演示就必须先有改级别的能力，顺序不能颠倒，所以我们一个一个来。

> **提示**：这一讲以及后面几讲的级别演示都在**命令行**里做。原因很实际——命令行可以随手开好几个连接、好几个事务，比图形化工具方便得多。

### 查看隔离级别

#### 版本分界：tx_isolation 改为 transaction_isolation

查默认隔离级别，第一件要注意的事是**版本**。

- 在 **5.7.20 之前**的版本里，这个系统变量的名字叫 `tx_isolation`；
- 从 **5.7.20** 开始，不再用 `tx_` 这个缩写，改用全称 `transaction_isolation`。

一个很小的版本区别，大家务必记一下。如果你当年把 5.7.20 之前的版本用得很溜，顺手敲的就是 `tx_isolation`，那套习惯换到新版本上就会落空。

我的环境是 5.7.3x，已经不属于 5.7.20 之前的版本了，所以旧名字在我这儿本来就不存在，"旧名还能查到"这个状态我没法演示给你看，你只要知道有这么一个分界点就行。

> **提示**：变量名写旧了、拼错了，MySQL **不会报错**，只是查不到这个变量，返回结果为空。所以一旦查不出东西，先别怀疑权限，先想想是不是名字和版本对不上——`tx_isolation` 和 `transaction_isolation` 其实就是同一个变量的新旧两个名字。

#### 两种查看写法：SHOW VARIABLES 与 SELECT @@

查看这件事只有两种写法，用哪一种都行。

```sql
-- 写法一：SHOW VARIABLES LIKE
SHOW VARIABLES LIKE 'transaction_isolation';

-- 写法二：直接读系统变量（两个 @ 表示系统变量）
SELECT @@transaction_isolation;

-- 旧版本的变量名：在 5.7.20 及之后的版本（含 8.0）里查不到，但不会报错
SHOW VARIABLES LIKE 'tx_isolation';
```

逐段说明：

- `SHOW VARIABLES` 是查看系统变量的通用语句，`LIKE` 后面跟变量名。写成全名时属于精确匹配，只会返回这一条记录。
- 变量名要写**全称** `transaction_isolation`。有同学说这个单词写起来好麻烦——但它就是这么写的，麻烦也得写全。
- `@@transaction_isolation` 里的两个 `@` 表示取系统变量，变量名同样用全称。它和第一种写法读的是同一个变量，结果自然一致。
- 第三条在较新的版本上不会抛错，只是查不到东西。这不是语法错误，是变量在 5.7.20 之后改了名字。

我实际执行下来，查到的默认级别就是 `repeatable read`——跟前面说的对上：MySQL 默认的就是可重复读。

### 设置隔离级别

改级别之前先声明一件事：**先把 `GLOBAL` 和 `SESSION` 的区别放一放**，这一节只看语法本身，作用范围下一节单独讲。

大方向上有两种写法。

#### 写法一：SET TRANSACTION ISOLATION LEVEL

```sql
SET [GLOBAL | SESSION] TRANSACTION ISOLATION LEVEL <隔离级别>;
```

隔离级别从四个里挑一个，单词之间用**空格**分隔：

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

- 关键字建议大写，写小写也能识别，MySQL 对关键字大小写不敏感。
- 级别名本身可能是两个单词的（`read uncommitted`、`read committed`、`repeatable read`），中间必须是**空格**。
- 这条语句同样可以带 `GLOBAL` / `SESSION` 作用范围关键字，位置就在 `SET` 后面。作用范围的行为我不在这里演示，下面统一用另一种写法来演。

#### 写法二：给 transaction_isolation 变量赋值

```sql
SET [GLOBAL | SESSION] transaction_isolation = '<隔离级别>';
```

关键差别只有一处：**级别要当成一个整体来写，用中划线连接**，不能用空格：

```sql
SET transaction_isolation = 'read-uncommitted';
SET transaction_isolation = 'read-committed';
SET transaction_isolation = 'repeatable-read';
SET transaction_isolation = 'serializable';
```

为什么这边要换成中划线？因为这里放的是一个**值**。一个值就得是一个整体，两个单词必须用中划线连起来，凑成一个值。

四种级别在两种写法里分别长什么样，对照着记最省事：

| 隔离级别 | 写法一里的写法 | 写法二里的取值 |
| :--- | :--- | :--- |
| 读未提交 | `READ UNCOMMITTED` | `'read-uncommitted'` |
| 读已提交 | `READ COMMITTED` | `'read-committed'` |
| 可重复读 | `REPEATABLE READ` | `'repeatable-read'` |
| 串行化 | `SERIALIZABLE` | `'serializable'` |

读表说明：同一件事，左边是空格分隔的多个单词，右边是带中划线的一个字符串；`serializable` 本来就是一个词，所以两种写法里它都一样。

拿一条完整的语句拆开看，`SET GLOBAL transaction_isolation = 'read-committed';` 一共只有三段：

- `SET` 是赋值动作，后面跟的就是"要改谁"和"改成什么"；
- `GLOBAL` 是作用范围，可以换成 `SESSION`，换了以后影响的会话范围完全不同（下一节详细说）；
- `transaction_isolation = 'read-committed'` 是变量名加值。变量名跟查看时用的名字**一模一样**，这也是我偏爱这种写法的原因：查什么就设什么，不用在两套单词之间来回换算。

> **提示**：查看的时候我们写成 `@@transaction_isolation`，多出来的两个 `@` 是"取系统变量"的标记；赋值的时候不加 `@`，直接写变量名。看到 `@@` 就知道是在**读**，看到 `SET ... =` 就知道是在**写**。

两种写法的差异摊开看，就是这张表：

| 对比项 | 写法一 | 写法二 |
| :--- | :--- | :--- |
| 语句主干 | `SET TRANSACTION ISOLATION LEVEL` | `SET transaction_isolation =` |
| 级别怎么写 | 一个及以上单词，空格分隔，如 `READ COMMITTED` | 一个字符串，中划线连接，如 `'read-committed'` |
| 是否加引号 | 不加 | 要加 |
| 作用范围关键字 | `SET` 之后可写 `GLOBAL` / `SESSION` | 同样可写 |
| 我的建议 | 也能用 | 习惯上用这个 |

用哪个？看你自己心情，两个都行。我习惯用第二种，理由很朴素：这个系统变量本来就叫 `transaction_isolation`，那我直接去设置它的值不就完了吗。

> **易错点**：两种写法里的分隔符千万别串。写法一用空格，写法二用中划线；写法二的中划线是"值的组成部分"，所以引号也不能省。

### GLOBAL 与 SESSION 的作用范围

现在把刚才放下的事捡回来。

#### GLOBAL：只对之后新建的会话生效

先记住一个前提：**我们做设置的时候，自己也是通过一条连接在做事的**，也就是说你本身也是一个会话。假设这个会话叫会话 A，我在会话 A 里执行了一条 `GLOBAL` 级的设置。

结果会有点反直觉：

> **结论**：`GLOBAL` 设置**对当前已经存在的会话无效**。在会话 A 里设置完，回到会话 A 再查，原来是什么还是什么。

那它对谁有效？对**后起的会话**有效。语句执行完之后新开的那些会话——后面陆续连进来的每一个会话——用的都是你设置好的值。

（本来想按顺序把它们叫成"会话 B""会话 C"，可 S 和 B 连在一起读着不太雅观，那我干脆换个说法，后面统一叫它**新开的会话**。）

还有一种更省事的验证方式：不新开会话，直接把会话 A 退出去（`quit`），再重新登录进来。重新登录就等于开了一个**新的会话**，这时候新设置自然就生效了。

> **易错点**：`GLOBAL` 只对**新建的会话**生效，不是"执行完就全局立刻生效"。设置它的那个会话自己不受影响，得退出重连才会用上新值。

还有一条比作用范围更根本的规矩：

> **提示**：这两种设置都只是**内存级别**的。把 MySQL 服务重启一下（`systemctl restart mysqld`），前面设置得再狠也不作数——一切**回归最初的默认值**。

```text
  SET GLOBAL 的作用范围

  会话 A ──[ SET GLOBAL transaction_isolation = 'read-committed' ]──▶ 本会话仍用旧值
                                                                     （退出重连后才变新值）
  此后新开的会话 ──────────────────────────────────────────────────▶ 直接就是新值

  systemctl restart mysqld
        │
        └──▶ 所有会话回归默认值（内存级设置全部丢失）
```

读图说明：`GLOBAL` 的生效对象是"设置之后才出现的会话"，包括退出重连的老会话；而它的寿命只到服务重启为止。

#### SESSION：只作用于当前会话的后续事务

`SESSION` 是会话级的：你在当前会话里把隔离级别改了，之后这个会话里的**后续事务**就都用你设的这个值。

这里要分两种场景，区别只在于**这条 `SET` 语句落在什么位置**。

第一种，落在**两个事务之间**——上一个事务已经结束，下一个事务还没 `BEGIN`。这种情况最干脆，后续事务全部用新的隔离级别。

第二种，落在**一个已经 `BEGIN` 的事务中间**。这时候问题就来了：这个事务剩下的语句，到底听谁的？

> **结论**：`SET SESSION` 语句**可以在已经开启的事务中间执行**，但**不会影响当前正在执行的事务**。当前这个事务继续用之前的级别；等它执行完，你**再起一个新事务**的时候，才用你设置好的值。

```text
  在已开启的事务中间执行 SET SESSION

  事务 1：BEGIN ─────────────────────────────────────────── COMMIT
                    │
                    │  SET SESSION transaction_isolation = 'read-uncommitted'
                    ▼
              事务 1 剩下的语句：仍然用旧隔离级别

                                                        事务 2：BEGIN ────▶ 用新隔离级别
```

读图说明：这条语句本身能执行成功，但它的生效时点是**下一个事务**，不是当前事务——"能执行"和"已生效"是两件事。

### 命令行演示

规则讲完了，对不对还得跑一遍。这一节把 `GLOBAL` 和 `SESSION` 两种情况分别演一次。

两场演示的套路是一样的，先记下这条路线，看的时候就不容易乱：

```text
  验证一条隔离级别设置，固定要走这几步

  ① 查默认值 ──▶ ② 执行设置 ──▶ ③ 在当前会话再查 ──▶ ④ 换一个会话查
                                                              │
                                        （只有 GLOBAL 才需要） │
                                                              ▼
                                              ⑤ 重启服务，再查一遍

  每一步都在回答同一个问题：这一次，是"谁"的级别变了？
```

读图说明：前两步是在改，后三步是在验——第三步验"生效了没有"，第四步验"对谁生效"，第五步验"能撑多久"。

先确认起点：现在什么都没改过，还是默认级别。

登录：

```bash
mysql -u root -p
```

输入密码，登录成功。下面这些 `SELECT @@transaction_isolation;` 就在两个会话之间交替执行。用 root 用户登录都是没问题的。

#### GLOBAL 级设置的验证过程

```sql
-- 会话 A：改动之前，先看一眼默认级别
SELECT @@transaction_isolation;          -- 可重复读（repeatable read）

-- 会话 A：改成 GLOBAL 级的读已提交
-- 这里用变量赋值那种写法，值用中划线连接
SET GLOBAL transaction_isolation = 'read-committed';
```

设置完成了。先别急着开新窗口，就在当前这个会话 A 里再查一次：

```sql
SELECT @@transaction_isolation;          -- 还是可重复读
```

这一步特别值得停一下：明明设置成功了，会话 A 里查出来却还是老值——原因就是前面那条规则，`GLOBAL` 对当前已经存在的会话是失效的。

接下来新开一个会话，再敲一次登录命令，这就得到一个全新的会话：

```sql
-- 新开的会话：这里的查询结果应该变了
SELECT @@transaction_isolation;          -- 读已提交（read committed）
```

后起的会话确实用上了新值。

再看另一条路：回到会话 A，`quit` 退出，然后重新登录：

```sql
-- 会话 A 退出重连之后，等同于一个新会话
SELECT @@transaction_isolation;          -- 读已提交
```

跟新开窗口是一个道理——退出去再进来就是一个新会话，设置对它生效。

最后验证"内存级别"这一条。重启服务：

```bash
systemctl restart mysqld
```

重启完，回到任意一个会话里再查：

```sql
SELECT @@transaction_isolation;          -- 又变回可重复读
```

这个会话如此，换另一个会话也一样，全都回到默认值了。`GLOBAL` 改得再牛，也只是内存里的事，服务一重启就全没了。

把这几步的观察结果收在一张表里：

| 观察点 | 查到的隔离级别 | 原因 |
| :--- | :--- | :--- |
| 会话 A 设置后立刻查 | 可重复读 | `GLOBAL` 对已存在的会话无效 |
| 新开的会话 | 读已提交 | 新会话读到的是设置之后的值 |
| 会话 A 退出重连后 | 读已提交 | 重连等同于一个新会话 |
| 重启服务后的任意会话 | 可重复读 | 设置只在内存，重启回归默认 |

#### SESSION 级设置的验证过程

`GLOBAL` 演完，换成 `SESSION`：

```sql
-- 会话 A：改成 SESSION 级的读未提交
SET SESSION transaction_isolation = 'read-uncommitted';
```

> **易错点**：`uncommitted` 这个词要拼准——两个 `m`、两个 `t`（`u-n-c-o-m-m-i-t-t-e-d`）。前面 `read committed` 我就在拼写上栽过一次，少一个 `a` 就变成了 `red`。这类长单词写错，后面排查起来特别费时间，不如敲的时候就慢一点。

设置完，还在这个会话里查：

```sql
-- 会话 A：本会话立刻生效
SELECT @@transaction_isolation;          -- 读未提交（read uncommitted）
```

当前会话马上就用上新级别了。换个会话再查：

```sql
-- 另一个会话：跟我没关系
SELECT @@transaction_isolation;          -- 还是可重复读
```

还是可重复读——因为这个改动是在人家那个会话里做的，跟当前这个会话一点关系都没有。

| 观察点 | 查到的隔离级别 | 原因 |
| :--- | :--- | :--- |
| 会话 A 执行 `SET SESSION` 后 | 读未提交 | 会话级设置对本会话直接生效 |
| 另一个会话 | 可重复读 | 修改只属于它自己的会话，与其他会话无关 |

到此，怎么查、怎么改就都说清楚了。动手之前，脑子里先过一遍那个问题：你是想改**当前会话**的，还是想改 `GLOBAL` 的？这两者的生效时机完全不同——一个立刻对自己生效，一个只对后来出现的会话生效。级别改明白了，接下来才好用不同的事务去演示"脏读""不可重复读"到底长什么样子。

## 166-读未提交隔离性下的演示
> 对应分集：P166 | 原始标题：《166-读未提交隔离性下的演示》

MySQL 怎么查看隔离级别、怎么改隔离级别，前面已经落定。接下来就该把并发问题挨个拉出来看一遍：脏写、脏读、不可重复读、幻读，这些现象在真实的库里到底长什么样。

先把一句实话放在最前面：**脏写（Dirty Write）在我们讲的这四种隔离级别里都已经解决了**，所以你们想再现一次脏写，是再现不出来的。演示只能从脏读（Dirty Read）起——它恰好是读未提交（READ UNCOMMITTED）没有解决的那个问题，因此在这个级别下能稳稳地把它演出来。前面讲的全是理论，这一讲我们就拿代码把这些现象落实一遍，加深巩固。

为什么挑脏读当第一个演示对象，一对比就清楚了：

| 并发问题 | 在四种隔离级别下的处境 | 能否演示 |
| :--- | :--- | :--- |
| 脏写（Dirty Write） | 所有级别都已解决，写与写之间互斥 | 不能，无法再现 |
| 脏读（Dirty Read） | 读未提交没有解决这个问题 | 能，本讲就演它 |

读表说明：演示的起点不是随便选的，得挑一个在当前隔离级别下还存在、又能被稳定复现的问题，读未提交下的脏读正好符合这两个条件。

### 演示准备与账户表结构

#### 账户表的创建与初始数据

要演示并发行为，先得有表。为了一看就懂，我们还是拿转账来说事，用 `account` 表——就是讲保存点（SAVEPOINT）时用过的那张表。表里三个字段：`id` 是主键，`name` 是账户名，`balance` 是余额。选转账这个场景是有讲究的：一笔转账天然对应两条 `UPDATE`、牵动两行数据，后面讲并发问题时最容易看出两边的分歧。

动手之前我先做了一件事：把之前演示留下的会话全都关掉。原因不难理解——刚刚演示隔离级别设置时，那些会话的级别已经被改成 READ UNCOMMITTED 了，留着它们，你们很容易分不清后面看到的现象到底是新会话造成的，还是旧会话的遗留。所以干脆全关掉，重新登录一个干净的会话，root 用户。

进入 MySQL 之后先选库、看一眼现有表：

```sql
USE atguigudb3;
SHOW TABLES;
```

当前库里没有 `account`，那就建：

```sql
CREATE TABLE account (
    id      INT PRIMARY KEY,    -- 账户编号，主键
    name    VARCHAR(20),        -- 账户名
    balance DECIMAL(10, 2)      -- 余额
);
```

表建好，往里加两条数据。注意主键值是显式写上的，一个 `1`、一个 `2`，张三 100 块钱，李四没钱：

```sql
INSERT INTO account (id, name, balance)
VALUES (1, '张三', 100), (2, '李四', 0);
```

这两条 `INSERT` 前面既没有 `BEGIN`，也没有 `START TRANSACTION`，为什么直接就算数了？因为默认的 `autocommit` 是 `true`：**没有显式开启事务时，一条 DML 语句自成一个事务，语句执行完就提交了**。所以这两行数据此刻已经落到磁盘上。

这一点后面每写一条 DML 都要在心里过一遍，两种写法的差别就在这里：

| 写法 | 语句执行完之后 | 数据是否已提交 |
| :--- | :--- | :--- |
| 不写 `BEGIN`，直接执行 DML（`autocommit` 为 `true`） | 该 DML 自成一个事务，事务随即结束 | 已提交 |
| 写了 `BEGIN` 之后再执行 DML | 事务仍在进行中 | 未提交，可回滚 |

读表说明：同样一条 `UPDATE`，放不放在显式事务里，决定了它的结果是不是已经落定；本讲后面所有的"看到未提交数据"，前提都是写的一方处在 `BEGIN` 之后、还没提交的状态。

查一下确认：

```sql
SELECT * FROM account;
```

张三 100、李四 0，没问题。此刻表里的内容就是后面所有演示的基准状态：

```text
account 表（初始状态，已提交）
+----+--------+---------+
| id | name   | balance |
+----+--------+---------+
|  1 | 张三   |     100 |
|  2 | 李四   |       0 |
+----+--------+---------+
```

再看当前隔离级别：

```sql
SELECT @@transaction_isolation;
```

结果是 REPEATABLE READ，也就是可重复读——这是 MySQL 的默认隔离级别。

#### 两个会话的隔离级别设置

再启一个会话（新开一个命令行窗口），用 `mysql -u root -pabc123` 登录进去。

> **提示**：两个会话都用 root 登录没有任何问题。会话是不是同一个，跟用什么用户名登录无关；两个独立的连接就是两个独立的事务边界，各自执行 DML 就是两个不同的事务。

新会话先查一遍隔离级别，还是 REPEATABLE READ，然后把它改掉：

```sql
SET SESSION transaction_isolation = 'READ-UNCOMMITTED';
```

这里的值要连成一个单词来写，两个字之间是中划线：`READ-UNCOMMITTED`。写成 `SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` 那种形式时，两个词之间才是空格，并且不需要引号——两种写法等价，看你们顺手。

改完必须回查，别改完就当它生效了：

```sql
SELECT @@transaction_isolation;    -- READ-UNCOMMITTED
```

接着把这条 `SET` 语句复制回第一个会话，粘过去同样执行一遍，回查也变成 READ-UNCOMMITTED。为了后面不迷路，我把两个窗口重命名成「事务 1」和「事务 2」——**两个会话此刻都是读未提交，每个窗口各代表一个事务**。

```text
  会话 A（事务 1）                  会话 B（事务 2）
  transaction_isolation             transaction_isolation
    READ-UNCOMMITTED                  READ-UNCOMMITTED
          |                                  |
          +----------------+-----------------+
                           |
                  account 表（磁盘）
                  (1, 张三, 100)   (2, 李四, 0)
```

读图说明：两个会话的隔离级别各自独立设置，设完之后都处于读未提交；它们共用同一张 `account` 表——脏读要观察的，就是同一个数据被两个事务分别看待时出现的分歧。

在两个会话里都查一下 `account`，都是张三 100、李四 0。这一次查询本身就是一条隐式事务，查完即结束，不会一直挂着不放。

### 单条更新下的脏读与回滚

事务 1 里正式开启一个事务：

```sql
BEGIN;      -- 等价于 START TRANSACTION
UPDATE account SET balance = balance + 100 WHERE id = 1;
```

给 1 号张三加了 100。注意这次和前面的 `INSERT` 不一样了：前面没有 `BEGIN`，语句执行完就提交；现在我们在事务里，事务没有结束，这个修改就只是临时的——没提交，也没落盘。

那么问题就来了：这个还没提交的数据，另一个事务能不能读到？切到事务 2，直接查：

```sql
SELECT * FROM account;
```

出来的张三已经是 200。

你看，读出来了。事务 2 读到的是事务 1 修改过、但尚未提交的数据——这就是脏读。事务 1 写下的这个 200 是临时数据，随时可能被撤回，事务 2 却把它当成真实数据读进来了，读到的就是一个**脏数据**。

紧接着事务 1 反悔了，回滚：

```sql
ROLLBACK;
```

再查，张三又回到 100。事务 1 写的东西一笔勾销，磁盘上从头到尾都是 100 和 0。

```text
事务 1                              事务 2
  BEGIN
  UPDATE id=1  +100
  （未提交：balance = 200）
                                     SELECT * → 张三 200   ← 脏读
  ROLLBACK
  （balance 复原为 100）              （读到的 200 从未真实存在）
```

读图说明：事务 1 的 `UPDATE` 只是把值改成了 200，并没有提交；事务 2 在事务 1 回滚之前就把 200 读走了，于是读到了一份注定被撤销的值。

> **结论**：事务 2 读到的那个 200，是一个临时且最终无效的值——它从来没有真实存在过。

这个场景本身就叫脏读。但你们可能会觉得差点意思：不过就是读错一个数字，人家一回头滚，两边也就都没事了。那我们再看一个在实际开发里更难接受的版本。

### 转账场景下的脏读、锁等待与余额错位

先确认两个会话都还是 READ UNCOMMITTED，同时确认表里现在是张三 100、李四 0——上一轮的事务 1 已经回滚，写的那些都不算数。

事务 1 开始转账，张三给李四转 100 块钱。转账对应两条 `UPDATE`：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
```

在自己这个会话里 `SELECT *` 一看，是 0 和 100，钱确实转过去了。但我再强调一次：**没有 `COMMIT`，也没有 `ROLLBACK`，这个事务还没结束**。

切到事务 2，也 `BEGIN` 开启一个事务，然后查询：

```sql
SELECT * FROM account;
```

查到的是 0 和 100。跟刚才一样，这已经是脏读了：人家既没提交也没回滚，你把人家的临时数据读了过来。

接下来事务 2 做了一件"好心"的事——李四觉得这钱我不想要，给你转回去吧：

```sql
UPDATE account SET balance = balance - 100 WHERE id = 2;
```

执行下去，卡住了。

它撞的正是事务 1 刚改过的那一行：事务 1 的转账动了两行，`id = 2` 这一行还攥在它手里，事务 2 上来就要改这一行，自然只能等。换句话说，卡住的这一条语句本身没错，错的是它出现的位置——它建立在一份不该看见的读结果之上。

> **易错点**：这里卡住不是连接断了，也不是 MySQL 服务忙不过来——这台机器上就我们自己开的这么两个会话，没什么可忙的。真正的原因是事务 1 还占着这一行的锁：写操作要持有被修改行的排他锁（Exclusive Lock，X 锁），事务 2 要改同一行，就只能排队等待。

这一行的锁要等到事务 1 结束才会释放，不管它是提交还是回滚。所以事务 2 只能老老实实等着——它等的不是"事务 1 别改"，而是"事务 1 给出一个最终结论"。等事务 1 那边一结束，锁一放开，事务 2 的 `UPDATE` 立刻按最新可见的值继续执行。

> **提示**：注意区分这两件事——脏读是"读"这一侧没有任何阻拦，锁等待是"写"这一侧必须排队。前者让我们看见了不该看见的中间状态，后者保证了写与写之间不会互相踩踏。

这一幕其实正好呼应了开头那句话。**两方要写同一行，只能一个先来、另一个等着，写与写之间天然互斥**——所以脏写在任何隔离级别下都造不出来，能造的只有"读"这一侧的问题。

那事务 1 这边打算结束这个事务了。注意我用的是 `ROLLBACK` 而不是 `COMMIT`——张三转完 100 块钱后悔了：

```sql
ROLLBACK;
```

回滚一执行，张三转出去的钱全部撤回，表里又变回张三 100、李四 0。而事务 2 那边被卡的 `UPDATE` 立刻执行下去：李四 0 减 100，变成 -100。

事务 2 并不知道自己脚下踩的是脏数据，继续把"还回去"这半边做完：

```sql
UPDATE account SET balance = balance + 100 WHERE id = 1;
COMMIT;
```

这里要留意 `UPDATE` 是怎么算的：事务 2 是在**拿到锁之后**、按它当时能读到的最新值来计算的——李四那一行此刻已经是 0，所以算出来是 -100；张三那一行是 100，加完就是 200。它的每一步都对得上它自己的账，问题是它的账本从第一眼起就是脏的。

提交之后，两个会话再查一遍，结果一模一样：**张三 200，李四 -100**。乱套了。两个数加起来倒还是 100——本来它俩的和就是 100——可张三凭空多出 100，李四反倒欠了 100，跟一开始的理解完全不同。更要紧的是，事务 2 这一 `COMMIT`，就把基于脏数据做出的决定永久留在磁盘上了。

```text
事务 1（张三 → 李四 转 100）          事务 2（李四 → 张三 转回 100）
  BEGIN                                BEGIN
  UPDATE id=1  -100
  UPDATE id=2  +100
  （未提交，仅在事务 1 内看到 0、100）
                                       SELECT *  → 0、100      ← 脏读
                                       UPDATE id=2  -100  ──┐
                                                            │ 等锁
  ROLLBACK                          <───────────────────────┘
  （磁盘恢复 100、0）                  UPDATE id=2 落定 → 李四 -100
                                       UPDATE id=1  +100 → 张三 200
                                       COMMIT
最终：张三 200、李四 -100（合计仍为 100）
```

读图说明：左侧事务 1 始终没有提交，右侧事务 2 在它未提交时就把 0、100 当成了事实；随后事务 2 的写操作被事务 1 的行锁挡住，直到事务 1 回滚才继续执行——它是在一个已经作废的状态之上，把自己的决定做完了。

把整场演示的数据状态按时间轴排开，错在哪一步就很清楚了：

| 时点 | 张三 balance | 李四 balance | 合计 |
| :--- | ---: | ---: | ---: |
| 演示开始（磁盘上的值） | 100 | 0 | 100 |
| 事务 1 未提交（只在事务 1 内可见） | 0 | 100 | 100 |
| 事务 2 脏读读到的值 | 0 | 100 | 100 |
| 事务 1 回滚之后 | 100 | 0 | 100 |
| 事务 2 提交之后 | 200 | -100 | 100 |

读表说明：全程总额都是 100，一分没多、一分没少，但钱的分布彻底错了。问题不在算术上，在于事务 2 是拿着一个最终不成立的状态做出的决定。

> **结论**：合计数正确，不代表结果正确。脏读破坏的是判断依据——被读到的那个版本可能永远不会成立，而后续所有操作都建立在它之上。

### 脏读的判定标准与危害

本讲一共演了两个场景，把它们的差别摆在一起看，脏读的轮廓就完整了：

| 对照项 | 场景一：单条更新 | 场景二：转账一对更新 |
| :--- | :--- | :--- |
| 事务 1 的写操作 | 张三 +100 | 张三 -100、李四 +100 |
| 事务 2 的读时机 | 事务 1 未提交时 | 事务 1 未提交时 |
| 事务 2 读到的脏值 | 张三 200 | 张三 0、李四 100 |
| 事务 1 的收场 | 回滚 | 回滚 |
| 事务 2 之后做了什么 | 只是读，没有动作 | 基于脏值继续更新并提交 |
| 最终结果 | 数据复原，无害 | 张三 200、李四 -100，账目错位 |

读表说明：两个场景里被读到的都是"未提交且最终不成立"的数据；区别在于场景二的读取结果被拿去驱动了后续写操作，于是错误被固化进了磁盘。

怎么感性地理解脏读？一个事务正在改数据，改完还没提交，只是临时写了一份；另一个事务就把这份临时数据读走了。这在数据库开发里是一定要避免的。

我说得夸张一点：这是人家的房间，人家进去的时候衣冠整齐，进去以后换衣服、干些不可描述的事情，出来的时候依旧是衣冠整齐的。**他在房间里的那个过程，你本来是不该看见的**——可在读未提交下，你看见了。这就叫脏读。

为什么这个级别会这样？因为它读的时候既不要求共享锁，也不去读一个一致性快照，而是直接取该行的最新版本，其中就包括别的事务尚未提交的版本。换句话说，读取方对写入方的中间状态毫无防备，写入方改到哪一步，它就可能读到哪一步。而读已提交（READ COMMITTED）及以上的级别里，读操作看到的是已经提交的版本，别人事务内部的中间状态根本不会进入它的视野，读写之间也就有了隔离。所以脏读不是"偶尔读错"，而是读未提交这个级别在语义上允许的结果。

> **定义**：一个事务读到了另一个尚未结束的事务未提交的数据，而这份数据随时可能被对方回滚掉，这种情况就叫脏读（Dirty Read）。

要判定一次读取是不是脏读，看三点就够了：读发生在**两个不同的事务**之间、被读的那个事务**还没有结束**（既没提交也没回滚）、读到的值**来自对方的未提交修改**。三条都满足，就是脏读；只要对方已经提交，读到的就是正常数据，只是在不同隔离级别下"何时能看到它提交"另有讲究。

回到 §3 那个结果上，脏读的可怕之处就落地了：事务 2 以为张三只要 0 块、李四有 100 块，它做出"转回去"的决定完全合理；可这个前提从来就是假的。等两边事务都结束，账目变成了张三 200、李四 -100——没有任何一条语句写错，错误全部来自那份被提前看见的脏数据。

所以要根治脏读，办法只有一个方向：把隔离级别提上去。读已提交（READ COMMITTED）及以上就不会再出现脏读，因为一个事务只能读到别人提交之后的版本。

而这也正是脏读必须守住的理由：读未提交这个级别能让我们把现象看清楚，但在生产环境里，它带来的恰恰就是这种"看起来一切正常的错账"。

## 167-读已提交和可重复读的隔离性下的演示
> 对应分集：P167 | 原始标题：《167-读已提交和可重复读的隔离性下的演示》

上一讲我们把脏读演示清楚了，这一讲顺着往下走：把隔离级别切到 `read committed`（读已提交），看看脏读是怎么被解决的；再看它没解决掉的那个问题——不可重复读，是怎么在同一组会话里冒出来的；最后切到 `repeatable read`（可重复读），把不可重复读也堵上。整讲是一场真实的双会话实验，我们照着敲、照着看结果。

### 实验环境与数据复位

两台会话（两个客户端连接）都连在同一个库上，操作对象是转账用的 `account` 表，字段就一个账户主键 `ID` 和一个余额 `balance`。

这一讲要反复从同一个起点出发，所以先做数据复位。复位在事务一里操作：

```sql
-- 事务一
TRUNCATE TABLE account;
```

清空之后，把最初的数据恢复成：`ID = 1` 的张三余额 `100`，`ID = 2` 的李四余额 `0`。用的就是前面讲开启事务时提到的那段添加数据的语句，直接粘回来执行。

> **提示**：复位语句没有写 `begin`，也没有写 `start transaction`。单条语句默认自身就相当于一个已经提交的事务，所以这次复位对其他会话是即时可见的。

复位完在事务一里查一次：

```sql
SELECT * FROM account;
```

结果是张三 `100`、李四 `0`，回到了最初状态。后面两场演示都从这个状态起步。

### 会话隔离级别的设置方式

复位完，把两个会话的隔离级别改成 `read committed`：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

这条语句里有个必须守住的细节：

> **易错点**：`SESSION` 这个词千万不要省。省掉之后会出现一些莫名其妙的问题。到底是 `global` 还是 `session`，你想指定哪一级，就把对应那个单词明确写上。

这条设置要在两个会话里各执行一次。两个会话的隔离级别都变成 `read committed` 之后，才进入现象演示。

要确认当前会话的级别，用系统变量查：

```sql
SELECT @@transaction_isolation;
```

### 读已提交（READ COMMITTED）下的脏读防护

第一组实验分两段：先证明未提交的修改看不见，再证明提交之后立刻看得见。

这里只有事务二在写，两边不会撞在一起。原因和上一讲看到的一样：两个事务要改同一行，写操作之间天然互斥，只能一个先来、另一个等着，所以写这一侧没问题；要看的全在读这一侧。

#### 事务二的修改与事务内的查询

事务一开启一个事务并查一次：

```sql
-- 事务一
BEGIN;
SELECT * FROM account;
```

此时张三 `100`、李四 `0`。

接着事务二也开启一个事务，做一次扣款：

```sql
-- 事务二
BEGIN;
UPDATE account SET balance = balance - 50 WHERE ID = 1;
SELECT * FROM account;
```

事务二自己查，结果是张三 `50`、李四 `0`——事务内部自己改的，看得见。

```text
会话A（事务一）                       会话B（事务二）
    |                                     |
  BEGIN                                 BEGIN
    |                                     |
  SELECT * -> 张三100 李四0         UPDATE balance = balance - 50
    |                                WHERE ID = 1
    |                                     |
    |                                SELECT * -> 张三50 李四0
    |                                     |   （本事务内可见，未提交）
    |                                     |
  SELECT * -> 张三100 李四0 ←──────  修改未提交，读不到
    |                                     |
                                    COMMIT
    |                                     |
  SELECT * -> 张三50 李四0 ←──────  提交后立即可见
    |                                     |
  COMMIT
```

读图说明：事务二的 `BEGIN` 与 `UPDATE`、`SELECT` 全在同一个事务里，修改既没有提交也没有回滚；事务一两次读到的一直是磁盘上那个 `100`，直到事务二提交才变成 `50`。

#### 两个会话各自的读结果

关键在事务一这边。事务二改完还没提交的时候，事务一去查：

```sql
-- 事务一
SELECT * FROM account;
```

张三还是 `100`。

> **结论**：事务二写出来的那笔改动，在它自己提交之前只是临时的；事务一读到的是磁盘上还存着的 `100`，没有读到这份临时数据。脏读就此被避免。

对照上一讲的场景就清楚了：如果隔离级别还是 `read uncommitted`（读未提交），这里会直接看到 `50`。

#### 提交之后的可见性与不可重复读

事务一把自己改完了，执行提交：

```sql
-- 事务一
COMMIT;
```

提交之后再查，必然是 `50`、`0`——提交相当于把数据真正刷盘。

> **定义**：提交（`commit`）在这里可以理解为把本事务的改动落到真正的磁盘上；提交之前，改动还只在内存级别。

现在回头看事务二。事务二的 `begin` 还开着，事务从头到尾没有结束。此时它再查一次：

```sql
-- 事务二（事务未结束）
SELECT * FROM account;
```

结果变成了张三 `50`。

同一条 `SELECT`，在同一个还没结束的事务里执行了两次，拿到的值不一样——这就是不可重复读。

```text
事务二：BEGIN ──SELECT→ 100 ──SELECT→ 50 ──COMMIT
                 ↑              ↑
              第 1 次读      第 2 次读（事务未结束，值已被别的事务改掉）
```

读图说明：事务二自己没做任何修改，但它在事务期间被另一个事务的提交“插了一刀”，两次读结果不一致，这正是不可重复读的定义场景。

顺着这个场景把原因说清：事务二还在查看的过程中，事务没有结束；另一个事务把这条数据改了，而且提交了；于是事务二再查的时候，拿到的就是修改之后的值。

那事务一自己这两次读为什么一致？因为它正是在写这条数据的那一方，改动是它自己做的，在它自己的事务里当然从头到尾都看得见。这一点别和事务二的遭遇混在一起看。

把这一场的数据摆出来，转折点落在哪一步一目了然：

| 时点 | 事务一读到的张三 | 事务二读到的张三 | 磁盘上的张三 | 事务状态 |
| :--- | ---: | ---: | ---: | :--- |
| 复位之后 | — | — | 100 | 两个会话都没有事务 |
| 事务一 `BEGIN` 后查询 | 100 | — | 100 | 事务一未结束 |
| 事务二 `BEGIN` 后扣款 50（未提交） | — | 50 | 100 | 两个事务都在进行中 |
| 事务一再次查询 | 100 | — | 100 | 未提交的 50 读不到，脏读被避免 |
| 事务二 `COMMIT` 之后 | 50 | 50 | 50 | 事务二已结束，事务一仍未结束 |

读表说明：前三行的 `100` 与 `50` 是两个会话各自的视图——事务二看得到自己未提交的改动，事务一看到的是磁盘上的 `100`；最后一行事务二一提交，事务一这条还没结束的事务立刻就跟上了新值。

> **结论**：`read committed` 只保证你读到的是**已提交**的数据，不保证你在一个事务里读到的值一直不变。同一事务内相同语句返回不同结果，就是不可重复读。

要特别留心的是，事务一那两次查询之间，它自己一条写语句都没发，结果还是变了——不可重复读的“肇事者”从来不是读的那个人，而是别的事务的提交。

### 可重复读（REPEATABLE READ）下的两种现象

事务二提交，把表定格在张三 `50`、李四 `0`：

```sql
-- 事务二
COMMIT;
SELECT * FROM account;   -- 张三50 李四0
```

提交之后无需再看，真实表里存的就是 `50`、`0`。下面在这个数据上演示下一场。

这一场要验两件事：可重复读把脏读和不可重复读两个问题是不是都解决掉了。注意两个问题的验证方式不一样——脏读看的是“别人未提交的值能不能读到”，不可重复读看的是“本事务内两次读同一语句结果是否一致”。

#### 隔离级别切换与确认

两个会话都切成可重复读：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

注意级别名里那个中划线要写上，是 `repeatable-read`。设置语句复制一份到第二个事务里执行，两个会话保持一致。同样地，要查一下就查：

```sql
SELECT @@transaction_isolation;
```

确认结果是 `repeatable read`，事务一那边也瞅一眼，没问题。

#### 脏读仍然被避免

这一次先从事务二开始：

```sql
-- 事务二
BEGIN;
SELECT * FROM account;   -- 张三50 李四0
```

张三是 `50`、李四 `0`。

然后事务一也开一个事务，顺手查一次，看到的一样是 `50`、`0`：

```sql
-- 事务一
BEGIN;
SELECT * FROM account;   -- 张三50 李四0
```

接着事务一改数据，这次减 `10`：

```sql
-- 事务一
UPDATE account SET balance = balance - 10 WHERE ID = 1;
```

张三的余额从 `50` 变成 `40`。

回过来看事务二，再查一次：

```sql
-- 事务二
SELECT * FROM account;
```

还是 `50`。事务一那边实际已经变成 `40` 了，但事务二没查出来 `40`——脏读被避免了。

#### 事务内重复读的一致性

事务一提交：

```sql
-- 事务一
COMMIT;
```

提交以后在事务一里查，看到的是 `40`。之前和之后的区别就在这里：提交之前属于内存级别，提交之后相当于刷新到磁盘的行为。

> **提示**：两个隔离级别对提交的处理是一样的——提交前改动不外泄，提交后立刻被其他已提交的读看见。差别不在这里。

现在回到事务二。事务一已经结束了，事务二的 `begin` 还没有结束。此时再查：

```sql
-- 事务二（事务未结束）
SELECT * FROM account;
```

还是 `50`。

这就说明不可重复读被解决了。如果这里变成 `40`，那就和上一个隔离级别表现一样了。为什么会不一样？差别就在事务二第一次查询的那一刻——`repeatable read` 下事务二在事务内第一次读到的是 `50`，此后它的读就一直沿着这个起点走，别的事务提交了 `40` 它也不改口。

把这场的数据也排一遍，和上一场的表对着看，差别只在事务二那两列：

| 时点 | 事务一读到的张三 | 事务二读到的张三 | 磁盘上的张三 | 事务二的事务状态 |
| :--- | ---: | ---: | ---: | :--- |
| 切换级别之后 | — | — | 50 | 会话空闲，没有事务 |
| 事务二 `BEGIN` 后查询 | — | 50 | 50 | 已开启，快照建立在这一刻 |
| 事务一 `BEGIN` 后查询 | 50 | — | 50 | 事务二未结束 |
| 事务一扣款 10（未提交） | — | 50 | 50 | 未提交的 40 读不到，脏读被避免 |
| 事务一 `COMMIT` 之后 | 40 | 50 | 40 | 磁盘已是 40，事务二仍读 50 |
| 事务二再次查询 | — | 50 | 40 | 同一条 SQL，结果不变，可重复读 |
| 事务二 `COMMIT` 之后再查 | 40 | 40 | 40 | 事务结束，才读到 40 |

读表说明：`repeatable read` 下事务二那一列全程钉在 `50`，无论磁盘上的值在它的事务期间怎么变；只有它自己提交、事务终结之后，才跟上磁盘变成 `40`。对照上一场，同一个位置在 `read committed` 下是从 `100` 跳成了 `50`。

最后提交事务二：

```sql
-- 事务二
COMMIT;
```

事务结束之后，不管你是重新 `begin`，还是直接写一条 `select`，都能看到 `40`——不写 `begin` 的 `select` 默认自己就是一个独立的事务。

> **结论**：事务二的 `begin` 到 `commit` 期间，两次执行相同的 SQL 语句，查询结果完全一致，这才叫可重复读。`repeatable read` 把不可重复读这个问题也解决了。

把这一场的关键判断再收一句：事务二在事务内两次读到的都是 `50`，而磁盘上早就变成 `40` 了。**它读的是自己事务开始时的那一份**，不是磁盘上最新的那一份。隔离级别越高，事务看到的世界越稳定，代价也是明摆着的——它看到的可能已经不是当前的真实值了。

### 两个隔离级别的现象对照

把这一讲亲眼看到的四组结果对齐起来：

| 隔离级别 | 事务二改完未提交，事务一读 | 事务一提交后，事务二在自身事务内再读 | 事务二提交后（事务结束）再读 |
| :--- | :--- | :--- | :--- |
| `read committed` | 张三 `100`（脏读被避免） | 张三 `50`（值变了，不可重复读） | 张三 `50` |
| `repeatable read` | 张三 `50`（脏读被避免） | 张三 `50`（值不变，可重复读） | 张三 `40`（快照结束，读到最新） |

同一张表里记录的是这条规律：

```text
read uncommitted : 读到别人未提交的改动        → 脏读
read committed   : 只读已提交的最新版本        → 避免脏读，仍有不可重复读
repeatable read  : 事务期间读同一快照          → 避免脏读与不可重复读
```

读图说明：随着隔离级别提高，被排除的并发现象逐步增加，代价是读到的数据越来越“旧”——`repeatable read` 在事务内根本不会看到别的事务新提交的值，直到本事务结束。

> **易错点**：可重复读的“不变”是有边界的。它保证的是同一个事务内重复读一致，事务一结束、快照失效，新事务照样读到最新值。所以事务二提交后再查是 `40`，而不是停在 `50`。

到这里，`read committed` 下脏读被解决但不可重复读仍在、`repeatable read` 下两个问题都被解决，都已经在真实终端里跑出来、看到了。

## 168-幻读的演示与解决方案
> 对应分集：P168 | 原始标题：《168-幻读的演示与解决方案》

前面在 `repeatable read`（可重复读）这个隔离级别下，我们已经演示过两件事：脏读被解决掉了，不可重复读也被解决掉了。那么顺着往下，`repeatable read` 底下是不是还留了一个幻读问题没解决？既然把两种并发问题都演示过了，幻读当然也得当场做一遍给大家看。

不过在动手之前，先把幻读是什么复习一下，不然演示到一半容易不知道自己在看什么。

### 可重复读隔离级别下的幻读

#### 幻读的复习：先查后插的那个场景

假设有两张事务的席位，一个叫事务 1，一个叫事务 2，中间是我们那张具体的表。

我们先开事务 2，让它去查表里符合某个条件的记录数。假设查的是 `id` 为 3 的记录个数，那显然结果是 0。这里有个顺序上的讲究：是**先开启事务，再做这条 `select` 查询**，不是查完了才 `begin`。

事务 2 到这里先停住，事务没有结束。这时候事务 1 上场：它也开启一个事务，然后执行 `insert`，把 `id` 为 3 的这条记录添加进表里。添加完以后它做了一个 `commit`，提交了，事务 1 收工。

现在回到事务 2——它的事务还开着呢。它刚才明明查出 `id` 等于 3 的记录数是 0，那按这个结论，它自己是不是就可以放心地插一条 `id` 为 3 的数据了？结果一执行，报错了：这个表里现在已经有 `id` 是 3 的那条记录，而 `id` 是主键，不允许存放相同的 `id` 值。

> **定义**：在一个事务里，刚开始查询时符合条件的记录是 0 条；等另一个事务插入了一些数据之后，这个事务再去查，发现记录变多了——这种"凭空多出记录"的行为就叫幻读。

下面就来把这个过程完整演示一遍。

#### 隔离级别确认与持久化设置的区别

演示之前先确认当前在哪个隔离级别。执行：

```sql
select @@transaction_isolation;
```

查出来是 `repeatable read`，没问题。

这里要强调一件事：**两个事务必须在相同的隔离级别下**。更准确地说，是会话里的事务都在相同的隔离级别下——反正我们用的是同一个，一定是相同的。

顺便插一句关于隔离级别怎么设。前面讲查看和设置的时候，我们用的是 `set` 的方式：

```sql
set session transaction isolation level repeatable read;
```

这种方式属于内存级别的，服务器一重启就没了。如果你想改成比如 `read committed`，还想让它持久生效——服务器重启之后也照样生效——那就得去改配置文件了。在配置文件里加一个参数 `transaction_isolation`，值可以写成 `serializable`，也可以写成 `read-committed`，然后重启服务器，它就起作用了。

有同学会问：那我重启服务器，当前这个服务不就没了吗？

> **提示**：这两件事可以分开做，不必二选一。配置文件里加上参数，是为了让**以后每次启动**都按这个值来；当前这台服务器不想重启，就再用 `set global` 把它改掉，当前这次 `global` 立刻生效。等你哪天真重启了，配置文件会被加载，隔离级别仍然是你要的那个值。这样才达到持久化的目的。

#### 事务 2 的查询与事务 1 的插入提交

确认隔离级别是 `repeatable read` 之后，进入演示。

事务 2 里第一步，`begin` 开启事务：

```sql
begin;
```

接着查 `id` 为 3 的账户条数：

```sql
select count(*) from account where id = 3;
```

结果是 0，符合预期。

现在切到事务 1。同样先 `begin`，然后插入一条记录：

```sql
begin;

insert into account(id, name, balance) values (3, '王五', 100);

select * from account;
```

`values` 里三个值对应的三个字段是 `id`、`name`、`balance`，所以这条记录是 `id` 为 3、`name` 叫王五、`balance` 是 100。执行完 `insert`，再用 `select *` 看一眼，王五这条数据已经有了，这很正常。

随后事务 1 执行 `commit`：

```sql
commit;
```

事务 1 到此完全结束，这条数据也写到了磁盘上。

#### select 看不到、insert 却报错：幻读的隐式证明

回到事务 2。再查一次同样的语句：

```sql
select count(*) from account where id = 3;
```

哎，不对吧？刚才另一个事务明明增加了一条记录，而且已经提交了，在当前这个事务里应该能查出来才对——可它还是 0，并没有查出来。

那怎么证明这里确实出现了幻读？换个方式：刚才事务 1 里做的那句 `insert` 语句，把它复制过来，粘到事务 2 里：

```sql
insert into account(id, name, balance) values (3, '王五', 1000);
```

`id` 仍然写 3，`balance` 改成 1000，好跟事务 1 插的那条做个区分。执行——出问题了，报的是 `duplicate`，唯一性约束错误。

这里就出现了一个很别扭的组合：

- 在当前事务开启之后，我们查出来 `id` 为 3 的记录数是 0；
- 可我们往表里 `insert` 同样的 `id` 时，MySQL 告诉我们重名了。

以前讲过，对主键来说，只要 3 已经存在，就不能再添加。既然报了唯一性约束错误，那就意味着**这个表里已经有一条 `id` 是 3 的记录了**。

> **提示**：MySQL 在 `repeatable read` 下有个特别之处——你直接用 `select` 去看，看不出所谓的"多出几条记录"；但通过这次 `insert` 报的主键冲突，能隐式地证明记录确实多了。这就是幻读。

演示到这里，事务 2 已经没法按原计划往下走了，所以给它做一个 `rollback`：

```sql
rollback;
```

事务终止，这次演示结束。

#### 幻读为什么让人不踏实：事务并未结束

回过头看，出现幻读这件事本身就感觉差点意思。

我们在当前事务开启的时候查看，确实**没有**记录，这一点要特别注意。然后另外一个事务往里加了一条记录。按理说，那条插入不该落在这个事务的判断里——可它偏偏就影响了我们的插入：我开启事务的时候查你确实没有，我往里边插的时候你告诉我报错，而**我这个事务可没关**。

要说是我把事务关了再 `insert`，那当然是另外一说了。可我没关，所以这不太理想。幻读这个问题，还得考虑去解决一下。

### 幻读的解决方案

#### 串行化隔离级别如何避免幻读

按前面讲过的思路，要解决幻读，是不是得用 `serializable` 这个隔离级别？可你看它这名字——`serial` 就是串行的意思。读操作都串行化了，那还想实现一定的并发性就无从谈起了，性能会很差，这个方案不理想。

不过既然要理解它，就得先说明白：串行化到底是怎么解决幻读的。

在 `serializable` 隔离级别下，它会**隐式地添加一个行的独占锁**，或者叫**间隙锁**。（锁的具体内容放到下下章再讲。）它的场景可以直接描述出来，前提是两个事务都用 `serializable`：

事务 2 先 `begin`，然后查询 `id` 为 3 的记录，结果还是 0。关键在下一条：这个"没查到"的查询，已经让它把 `id` 为 3 这条数据给锁定了。

接着事务 1 打开，`begin`，然后想插入 `id` 为 3 的那条数据。一执行，**它不会让你执行**。因为事务 2 已经锁定了 `id` 为 3，其他任何想改这条记录的操作都不行，它就在那里停住、不往下走了——这个阻塞的场景，我们在前面那个演示里见过。

等事务 2 自己再查一次，发现的还是 0。如果事务 2 要去 `insert`，就让它添加成功。添加成功了，事务 2 就 `commit`。

事务 2 一 `commit`，事务 1 这边立刻就不阻塞了：那边释放了锁，这边紧接着去执行。但这一执行就发现，事务 2 已经把 `id` 为 3 的数据写进去了，于是 `duplicate` 这条错误信息会报到事务 1 这里——事务 1 添加不成功。

道理很清楚：是谁先开启事务、先去查、先去操作这个 3，谁就拿到了锁；锁在事务 2 手里，事务 1 就不让你再 `insert`。这样一来，幻读就被避免了。

```text
      事务 2 (serializable)                事务 1 (serializable)
      ---------------------                ---------------------
      begin
      select ... where id = 3  -->  0
        |  查询虽为 0 条，仍对 id = 3 加锁
        |                                          begin
        |                                          insert id = 3
        |                                             |
        |                                             |  被阻塞，停住
        |                                             |  不往下走
      insert id = 3  -->  成功                        |
      commit  ------------------ 释放锁 ------------->|
                                                     |
                                        发现该行已存在，报 duplicate
                                        事务 1 添加不成功
```

读图说明：串行化下"查不到也加锁"，事务 1 的插入被挡在锁上，等事务 2 提交放锁后再执行时，唯一性约束把它拦了下来——幻读没有机会出现，代价是插入操作全程被阻塞。

#### MySQL 默认隔离级别下的行锁与间隙锁方案

既然 `serializable` 性能比较差，换个思路：在 `repeatable read`——也就是 MySQL 默认的隔离级别下——它也是可以避免幻读的。

这件事在这里先泛泛地讲一遍，等后面讲到锁和多版本并发控制（Multi-Version Concurrency Control，MVCC）的时候再具体展开。

解决方式其实也是加锁，加的是**行的 X 锁**，X 锁就是独占锁。它的逻辑和串行化那套有点像：

```text
      事务 2 (repeatable read)              事务 1 (repeatable read)
      -----------------------              -----------------------
      begin
      select ... where id = 3  -->  未找到 id = 3 的记录
        |  按索引加锁：索引上 id = 3 这个位置被锁住
        |                                          begin
        |                                          insert id = 3
        |                                             |
        |                                             |  不让访问
      insert id = 3  -->  成功                        |
      commit                                          |
                                                      |
                                          此时才轮到它执行，报 duplicate
```

读图说明：可重复读下即便没查到 `id` 为 3 的记录，也会沿着索引把那个位置锁住，所以后发起插入的事务被挡在外面；先查到 0 的那个事务自己插得进去，另一个只能等到报唯一性约束错误。

在 `repeatable read` 下，我们这样理解这件事：事务 2 `begin` 之后做一次 `select`，确实没找到 `id` 是 3 的那条记录。但这个时候**也会去锁定**。

这里立刻会冒出一个问题：我们都没有这条记录，你锁什么？

> **结论**：锁的不是那条不存在的记录，而是**按索引来锁**——虽然没有 `id` 是 3 的记录，但它会把索引上 `id` 为 3 的这个位置锁住。这样一来，事务 1 再去 `insert` 的时候，就还是不让它访问。而事务 2 自己可以添加成功；事务 1 想添加，就报错了。

#### 三类方案的取舍

把三条路摆在一起看，差别就很直观了：

| 方案 | 幻读是否避免 | 并发性能 | 关键手段 |
| --- | --- | --- | --- |
| `serializable` | 避免 | 差，读操作也被串行化 | 隐式加行的独占锁或间隙锁 |
| `repeatable read` | 可以避免 | 较好 | 行的 X 锁（独占锁），按索引加锁 |
| `read committed` | 不能避免 | 好 | 无相应加锁 |

读表说明：串行化能挡住幻读，但把并发性一起牺牲了；MySQL 默认的 `repeatable read` 是折中的那一档——用 X 锁按索引锁住位置，既拦住幻读，又不至于让读操作全部串起来。

## 169-Redo日志和Undo日志的理解、为什么需要Redo日志
> 对应分集：P169 | 原始标题：《169-Redo日志和Undo日志的理解、为什么需要Redo日志》

事务的四个特性我们上一章已经讲完了：原子性、一致性、隔离性、持久性——ACID。这四个特性跟事务基本是等价的关系，一提事务，必然提到这四个特性。但这里有一个问题得往下追问一句：**这四个特性到底是怎么保证的？** 这一讲就来回答这个问题，答案落在「日志」上。

### ACID 四特性的保证手段与两类事务日志

先做分工。

**隔离性**是由锁机制来实现的。锁机制的内容量还不少，也有一定的难度，我们放到下一章专门详讲，这里先不碰它。

**剩下这三个特性——原子性、一致性、持久性——靠日志来保证。** 因为是跟事务相关的日志，所以放在这里讲；其他一些日志，放到后面的章节里去说。

跟事务相关的日志就两种：重做日志（`redo log`）和回滚日志（`undo log`）。

| 日志 | 中文名 | 作用 | 保证的特性 |
| :--- | :--- | :--- | :--- |
| `redo log` | 重做日志 | 提供再写入操作，恢复提交事务修改的页的操作 | 持久性 |
| `undo log` | 回滚日志 | 把行记录回滚到某个特定的版本 | 原子性、一致性 |

> **结论**：ACID 的实现手段一句话概括——隔离性靠锁，其余三个靠日志。

### redo 日志的作用：从内存修改到持久性

`redo` 是音译，直译过来就叫重做日志。它的作用里写着一句容易读不懂的话——提供再写入的操作，恢复提交事务修改的页的操作。它怎么就"恢复提交事务修改的页"了？这里的关键在一个点上：一个事务当中是不是会涉及多个操作，比如多个 DML？

这些操作的过程当中，我们修改的内容首先是在**内存层面**——改的是已经加载到内存里的那个数据页当中的数据。改完以后注意：这时候我们**还没有**把数据及时地更新到磁盘中去。

> **定义**：只有真正把数据更新到磁盘里，才算达到持久性的特征；只更新了内存，不能叫持久性。

持久性说的是：即使出现数据库故障、宕机等等，也不能改变"数据已经被修改"这个事实。你要是只改了内存，一宕机，磁盘里没改，那么一恢复，刚才那个事务做的那些修改就全没了——这个事实就被改变了。

那怎么办？为了保证内存中的数据一定能写入磁盘，我们在内存修改之后，把数据记录到一个叫 `redo log` 的日志当中；这样即使出现宕机，我们重启了 MySQL 服务器之后，也能从这个日志文件里把数据恢复出来。

> **结论**：`redo` 日志最明显的两点就是「恢复」和「保证持久性」。

还有一层不那么显眼的作用：让日志跟着事务一直执行到最后结束，其实在一定程度上也保证了事务一致性的状态。

### undo 日志与事务的两个最终状态

`undo log` 主要就是做回滚，音译过来直接叫回滚日志，这一点大家应该更容易理解。

要把它讲明白，得把上一章讲事务状态时的那张图接上：事务有两个最终状态。

- **提交的状态**：相当于数据整个确定下来了——说白了，这个事务里的那几条 DML 操作都执行成功了。
- **中止的状态**：相当于又回滚到了最初的状态。

这两个归宿分别由谁来保证？

提交的状态是由 `redo` 日志来保证的：既然你已经提交了，那对数据库的修改就是持久性的，这就是持久性这个特征。而如果你执行到一半，发现下面这条语句执行失败了，那就要回滚到最初的状态、回到中止的状态——这一步是由 `undo log` 这个回滚日志来保证的。

> **提示**：把两个最终状态跟两种日志挂上钩，redo 和 undo 的分工就很清楚了——一个负责一直往前走到提交并钉住结果，一个负责在执行不下去时退回去。

### redo 与 undo 的联系与区别

有人会说：`undo` 不就是 `redo` 的逆过程吗？

他这么讲的理由是：一个事务里有几个操作，`redo` 保证的就是你一直往前突、一直往前冲，一直冲到这个事务提交，这是一个往前走的过程；而 `undo` 是执行到一半发现后面执行不了了，然后往后退。一个往前冲、一个往后退，那这不就算是一个逆过程吗？

> **注意**：不要这样简单地去理解，这样理解是不对的。

我们先把联系说清楚，再说区别。

**联系一：二者都被视作一种恢复操作。**

`undo` 理解成恢复比较容易接受——把已经做过的操作再回滚回去，这是一种恢复之前数据的行为。`redo` 为什么也叫恢复？还是回到内存与磁盘那个落差：数据是内存改完、一秒以后才去做刷盘操作的；如果在这一秒之内宕机了，内存中的修改已经记录到 `redo` 日志里了，那么重启服务器以后，我们就能从 `redo` 里把这个数据恢复出来。所以它同样是一种恢复行为。

**联系二：二者都是存储引擎层生成的日志。**

后面要讲的 `binlog`（二进制日志），就不是存储引擎层生成的了。

**区别：`redo log` 是物理级别上的修改，`undo log` 是逻辑上的操作。**

`redo log` 的"物理级别"是什么意思？它真正记录的是：在**哪个页号**上、**偏移量是多少**的那个位置上，写入了一个什么样的数据。也就是说，它针对的是实打实的物理磁盘上的一条记录。

`undo log` 的"逻辑操作"又是什么意思？就是我们写 SQL 语句那种逻辑操作。比如针对一张表的数据做了一次 `insert`，那么这个 insert 操作做完之后，我们在 `undo log` 里就会记录一个与它相反的 `delete` 操作；如果这个事务要回滚，要把这行记录删掉，那我们就执行 undo 里这个 `delete` 就行了。

| 对比项 | `redo log` | `undo log` |
| :--- | :--- | :--- |
| 记录内容 | 物理级别：哪个页号、什么偏移量、写入了什么数据 | 逻辑操作：与已执行操作相反的操作，如 insert 对应 delete |
| 生成层次 | 存储引擎层 | 存储引擎层 |
| 主要作用 | 恢复提交事务修改的页，保证持久性 | 事务回滚，保证原子性与一致性；另有一致性非锁定读 |

`undo log` 的作用除了事务回滚之外，还有一个叫**一致性非锁定读**，这个要等到后面讲 MVCC 的时候结合着说。

### InnoDB 的页、缓冲池与脏页

往下具体看 `redo` 日志之前，先把"数据是怎么被改的"这个前提摆清楚。

讲 InnoDB 的时候我们提到过：数据的存储和访问，都是以**页**为最基本的单位。当我们真正要访问页面的时候，就需要把磁盘中的数据以页为单位加载到内存中，放到 `buffer pool`（缓冲池）里面。而针对数据的增删改行为，我们也都**先改内存层面**的数据，然后再以一定的频率把数据更新到磁盘上。

```text
┌──────────────────────────────┐
│  内存（易失，断电即丢）      │
│  buffer pool 中的数据页      │
│  已改但未刷盘的页 = 脏页     │
└──────────────┬───────────────┘
               │  以固定频率刷盘（Checkpoint 机制）
               ▼
┌──────────────────────────────┐
│  磁盘（持久，写入本身就慢）  │
│  表空间中的数据页            │
└──────────────────────────────┘
```

读图说明：上半部分是内存，事务的增删改先落在 `buffer pool` 的数据页上，改过、但还没刷回磁盘的页就是脏页；下半部分是磁盘，它按固定频率接收刷下来的数据页，这个频率由 Checkpoint 机制控制。

针对内存中的数据做更新，这个操作是很快的——CPU 跟内存打交道，比直接去更新磁盘要快很多。从这个意义上讲，缓冲池其实优化了 CPU 和磁盘之间的那道鸿沟，它在中间做了这样一层优化。

那刷盘这件事为什么必须做？第一，不更新的话，内存中的数据跟磁盘中的数据就不一致了；第二，内存中的数据很不稳定，一旦断电就没有了。我们既然要保证事务的持久性，就要保证内存中的修改在磁盘中一定体现出来，所以一定要做刷盘操作。

> **定义**：在刷盘之前，内存中改了、磁盘中还没改、两边还没同步的那个页，就叫**脏页**。

以一定的频率刷新磁盘，对应的机制叫 `Checkpoint`（检查点）机制，这个后面会讲。至于为什么不干脆刷得更勤、甚至实时刷盘，这笔账我们下面连本带利一起算。

### redo 日志的必要性

现在来看 `redo` 日志在整个过程当中充当了一个什么样的角色，以及我们为什么一定要去使用它。分两种宕机时机来看，结论完全不一样。

#### 未提交时宕机：不涉及刷盘

还是内存与磁盘那张图。我们单独画一个所谓的事务，事务里边有几个 DML 操作，整块构成一个事务。

比如先操作了一条 SQL 语句，对内存中的数据做了一个修改，记一下；接着再操作一条，又做了一次修改。再往下操作的时候，宕机了——MySQL 服务器宕机了。

这时候数据是什么状态？因为你这个事务也没提交，相当于这个事务就相当于没做。MySQL 重启以后，磁盘中的数据其实还是事务执行之前的那个状态。

我们现在的实现实际上就能保证这种状态：这个状态下不会涉及刷盘操作——内存中做了修改之后服务器宕机，内存中的数据就没了；重启以后，磁盘中的数据还是最初的那个数据，相当于我们什么也没做。

从逻辑上也讲得通：你这个事务也没提交，那就是最初的状态，这也是合理的，满足 ACID。这里没有问题。

#### 提交之后、刷盘之前宕机：持久性失守

换一种情形：事务往下走、一直走到最后，做了一个 `commit` 操作。

这个时候就意味着，从逻辑层面上看，这个事务已经结束了，而且提交了。那你这时候是不是也要满足 ACID？

看内存层面：一个、两个、三个、四个——这四个操作全做了，在内存里这个事务确实是完成了。但我们前面讲过，内存里完成并不意味着数据真正意义上完成了；我们需要把这个事务的数据在磁盘中真正做出修改，才能叫持久性。这时候就涉及刷盘行为，而刷盘是以一定的频率进行的。

问题就出在"一定的频率"上。假设刷盘行为一秒执行一次，恰好内存里执行完了、也 `commit` 了，内存中的数据要在一秒以后才刷到磁盘。而在不到一秒的这个时间之内，MySQL 服务器宕机了——这是完全有可能的。

```text
时间轴 ──────────────────────────────────────────────▶

  t0 ── 事务开始
       │
       ├── 逐条 DML：改的全是内存中的数据页
       │
  t1 ── 最后一条 DML 执行完，内存里的操作全改好了
       │
  t2 ── commit：逻辑上事务已经结束并提交
       │
       │      ┌────────────────────────────────────────┐
       ├────▶│  在这不到一秒的窗口里宕机：            │
       │      │  - 内存中的修改全部丢失                │
       │      │  - 磁盘中仍是最初的数据                │
       │      │  - 事务却已提交，持久性失守            │
       │      └────────────────────────────────────────┘
       │
  t3 ── 本应在这里刷盘（刷盘频率：一秒一次）
```

读图说明：`commit` 完成之后到下一次刷盘之间有一段不到一秒的窗口，宕机恰好落在这个窗口里——内存中的修改随内存一起消失，磁盘里仍然是最初的数据，而这个事务在逻辑上已经提交，持久性保证不了了。

一宕机会怎样？内存里的数据就全没了；重启服务器以后，内存中的数据没了，磁盘中的数据还是以前的，而我们这个事务已经说了提交了，这就不能保证持久性。

另一方面，既然叫持久性，那么你对数据库的修改，**不管系统有没有发生崩溃，都应该是改变了的**。现在这一点保证不了了。

> **结论**：问题不在于要不要刷盘，而在于刷盘是在提交之后按频率做的——提交完成与刷盘完成之间存在一段空档。

#### 实时刷盘方案的两笔代价

怎么解决？一个比较简单粗暴的办法是：既然要保证内存和磁盘尽可能一致，那就别"以一定的频率"了，也别一秒一次了——内存中的数据一旦修改，马上就去更新磁盘中的数据。

也就是说：事务里执行一条 `update` 语句，这条语句本身就是更新内存里的数据；这一更新，磁盘马上也跟着更新。再来一条数据，内存中一改，磁盘也马上跟着改。这样一来，尽可能保证了持久性——比如这块已经提交了，那边肯定也结束了，相当于马上就把它确定地保存下来。

这样行不行？可以。但有问题。

**代价一：修改量与刷新磁盘的工作量严重不成比例。**

假设我们只想改某张表里某一条记录中的某一个字段，一个极细微小的改变，可能只影响到一个字节。但前面讲过，数据从磁盘读到内存中都是以页为单位的，即使你只改这一个字节，也要把这一页加载到内存中。好，通过事务当中的一个 `update` 语句，只改了页当中的一个字节——然后因为"内存中一改，磁盘中也要改"，接下来你要把这个页的数据**完整地**刷新到磁盘上，默认一页是 16 KB。

> **易错点**：只改了 1 个字节，却要付出 16 KB 的刷盘代价。一方面是 1 字节对 16 KB 的数量差距，另一方面这是跨介质的修改，本身更慢。这个成本差距太大了。

**代价二：随机 I/O。**

写一条 `update` 语句，比如想修改员工表当中工资是 5,000 的员工，把他们的工资都改成 6,000。这些工资为 5,000 的员工在表当中**有可能存储在不同的页里**。你把它们都加载到内存中做了修改之后，接着往磁盘刷新的时候，这些页可能并不是连续的——那就意味着随机 I/O，我们得一个页一个页地去找。而随机 I/O 本身的成本也很高。

> **结论**：这两笔代价叠加，导致我们实际上没有选择实时刷盘这种做法。

#### redo 日志的引入

成本实在太高了。那我们应该怎么做、怎么做会更好？

我们想实现的事情其实挺简单：希望事务提交以后，内存中改了，磁盘中也一定确定地能改；但不想实时去更新。那就把内存中的这个修改**先保存到一个文件里**——这个文件其实就是日志了。根据它的作用给它起个名字，就叫 `redo` 日志。相当于把内存中的修改直接记录到这个日志文件里了。注意，**这是物理磁盘上真实存在的一个文件**。

后面的刷盘呢？你不是一秒刷一次吗？那就继续一秒刷一次，这都正常，都没事。区别在于：在刷盘这个行为之前，内存中的数据我们都要先往 `redo` 日志里记录一份。

那这一秒中的数据要是没赶上刷盘、服务器就宕机了呢？服务器重启以后，由于这个事务已经提交了、内存中改了、日志文件里也记录了，只是磁盘中还没改——我们启动之后就把 `redo` 日志中的这些数据重新做一次恢复，对磁盘做出修改。这就保证了之前 `commit` 的数据在磁盘中体现出来，持久性也就有了。

```text
┌────────────────────────────────────────┐
│  内存：buffer pool 中的数据页          │
│  第一步：事务里的 DML 逐条改这里       │
└───────────────────┬────────────────────┘
                    │
                    │  第二步：修改同时按顺序记入 redo 日志
                    ▼
┌────────────────────────────────────────┐
│  磁盘：redo 日志文件（真实存在的文件） │
└───────────────────┬────────────────────┘
                    │
                    │  第三步：服务器重启后，用日志里的记录重做一遍
                    ▼
┌────────────────────────────────────────┐
│  磁盘：表空间中的数据页                │
│  第四步：平时仍按一秒一次的频率刷盘    │
└────────────────────────────────────────┘
```

读图说明：事务的 DML 先改内存中的数据页，同一个修改同时按顺序记入磁盘上的 redo 日志文件；服务器重启后用日志里的记录重做一遍，落到表空间的数据页上；平时的刷盘频率保持一秒一次不变。

而且我们仍然可以考虑一秒做一次刷盘操作——刷盘频率可以不变，实时刷盘的那些弊端也就没有呈现出来。

### WAL：日志优先写

上面这种做法，这个技术叫 `WAL`，全称 `Write-Ahead Logging`，叫日志优先写，或者叫优先写日志的技术。

意思就是：我们对内存中的数据做了更改之后，先不要想着刷新到磁盘文件当中，先把它保存到日志里；然后再考虑后续——需要刷盘的时候、或者需要恢复的时候，再去使用这个日志。

> **结论**：一定要先把这件事往日志里放。因为这个速度是比较快的。

### redo 日志的好处与特点

顺下来，`redo` 日志的好处就是自然而然的事了。

**好处一：降低了刷盘的频率。** 相较于一开始那种实时刷盘的做法，我们这里仍然可以维持一秒刷一次，这就要更好一些。

**好处二：占用的空间比较小。** 有人会担心：内存中的数据先保存在 `redo log` 当中，那磁盘空间占用是不是会比较大？要说的是，它占用的空间其实很小，这也算是个优点。

它的特点有两条。

**特点一：`redo` 日志是顺序写入磁盘的。** 事务当中每执行一条语句产生的具体操作，我们是按照这个顺序记录在 `redo` 日志里的；它对应在磁盘文件上，也就是顺序写入磁盘文件。顺序 I/O 比随机 I/O 要快一些。

**特点二：事务的执行过程中，`redo log` 是不断记录的。** 这个特点相较于后面要讲的 `binlog`，是有区别的。

### redo log 与 binlog 的区别

先泛泛说一下 `binlog`。前面提到过主从复制：如果单台主机的性能达到极限了，我们就可以使用多台服务器——简单来讲，一台当主机、一台当从机；主机负责写的操作，从机负责读的操作。这时候肯定要保证主从数据的一致性：你在主机上写入一条数据，从机上是不是也应该有这条数据？

靠什么保证？就靠 `binlog` 日志。主机当中写入一条记录，我们就在 `binlog` 里做一条记录；然后从机从 `binlog` 日志当中把这个数据恢复过来，相当于它也加了一条记录。

这时候大家就会发现一个问题：`redo log` 怎么感觉跟 `binlog` 作用好像一样呢？都是"你这边做了什么事，我这边记一下"。`redo log` 是为了便于我们去做事务的持久化，你做了什么，我也记录了一下。但要注意，二者还是有区别的。

**第一，是不同的日志，没有用一套日志去做。**

**第二，产生的层次不一样。** `redo log` 是在**存储引擎层**产生的，而 `binlog` 是在**数据库层（Server 层）**产生的。

**第三，记录的时机不一样。** 假设一个事务有 10 万行的插入行为，在这个过程当中，我们是**不断**地往 `redo log` 中写——事务执行的过程中就开始往 `redo log` 里做记录了；`binlog` 不记录。当我们这个事务**提交**的时候，才会**一次性**写入到 `binlog` 文件当中。

| 对比项 | `redo log` | `binlog` |
| :--- | :--- | :--- |
| 是否同一套日志 | 独立的一套 | 与 redo log 不是同一套 |
| 产生层次 | 存储引擎层 | 数据库层（Server 层） |
| 记录时机 | 事务执行过程中不断记录 | 事务提交时一次性写入 |
| 主要用途 | 崩溃恢复、保证持久性 | 主从复制的数据同步 |

至于 `binlog` 具体如何去使用，等到后面讲其他日志的时候再说。

行，那这样的话，我们就把 `redo log` 的作用、还有它的好处是什么，先明确出来了。

## 170-Redo日志的刷盘策略与过程剖析
> 对应分集：P170 | 原始标题：《170-Redo日志的刷盘策略与过程剖析》

上一讲讲完，大家脑子里大概形成了一个很直观的印象：磁盘上有一个 `redo` 文件，服务器崩了，我们靠它恢复数据，事务的持久性就靠它兜底。这个印象没错，但只对了一半——真正意义上，redo 日志的构成比我们想的要稍微复杂一点，它涉及两部分结构：一部分在内存层面，另一部分才是我们持久化层面那个 redo log file。

所以这一讲我们先把这两部分认全，再把一个更新事务在它们之间怎么流转讲清楚，最后落到那个大家最关心的参数上：内存里的 redo 日志，到底什么时候刷到磁盘里去。

### redo 日志的两层结构

#### 内存层：重做日志缓冲

内存层面的这一块叫重做日志缓冲（redo log buffer）。一看 `buffer` 这个词就知道，它是内存层面的结构，是容易丢失的。

服务器启动的时候，就会向操作系统申请一片空间，这片空间就叫 `redo log buffer`，专门用来存重做日志。它默认大小是 16 兆，可以通过一个变量来查看和修改：

```sql
-- 查看重做日志缓冲的大小
show variables like 'innodb_log_buffer_size';
```

- 这个值换算一下就是 16 兆；
- 它可以调，最大值很大，最小可以是 1 兆；
- 换句话说，这个变量咱们是可以修改的。

在这片空间内部，它又被一块一块地分割开，每一个小块叫 `redo log block`，也就是 redo log 的块。一个块占 512 个字节。块内部还有更细的结构，这里先不展开，我们先从宏观上把它认下来：一个个 redo log block 拼起来，整个构成 redo log buffer。

#### 持久化层：重做日志文件

另一个就是重做日志文件，这才是真正磁盘意义上的文件。服务器崩溃以后，为了体现事务的持久性，我们要靠日志文件来恢复。

这里要把一个容易含糊的地方说死：我们所说的恢复，不是内存层面的恢复。服务器一崩，内存里的数据就没了，所谓恢复指的是从磁盘中的文件里恢复。

这个文件有它自己的存储位置，默认就在当前的数据目录当中。我们到机器上看一眼，进到数据目录：

```bash
cd /var/lib/mysql
```

在这个路径下，默认情况下会有两个文件，一个叫 `ib_logfile0`，一个叫 `ib_logfile1`。默认就是两个。而且你会发现这两个文件的大小一模一样。

这里有个容易被误会的点：看到两个一样大的文件，是不是以为我们的日志已经写满了？

> **提示**：并没有。它是先把空间开辟出来，后续事务一条条执行时，把修改的相关信息一条条记录进去。也就是说文件大小先占好，之后它不会再变大——空间预留式占用，不是写满了。

这两个文件，就是磁盘当中真正存在的 redo log file。**我们恢复数据，就是从这两个文件里恢复**，这一点要记牢。

#### 读图：两层结构与数据落点

```text
                内存（易失）                          磁盘（持久）
        ┌──────────────────────────┐        ┌──────────────────────────┐
        │      redo log buffer     │        │      redo log file       │
        │   默认 16M，可 1M 起调    │        │  ib_logfile0             │
        │  ┌────────┬────────┬───┐ │        │  ib_logfile1             │
        │  │ block  │ block  │...│ │        │  （大小固定、预先占好）    │
        │  │ 512B   │ 512B   │   │ │        │                          │
        │  └────────┴────────┴───┘ │        │                          │
        └──────────────────────────┘        └──────────────────────────┘
                    │                                   ▲
                    │            ┌──────────────┐       │
                    └───────────►│  page cache  │───────┘
                                 │（操作系统管） │
                                 └──────────────┘
```

读图说明：左半部分是内存里的 redo log buffer，由 512 字节的 redo log block 拼成；右半部分是磁盘里的 redo log file，默认两个文件、大小预留；两者之间并不是直连的，中间隔了一层由操作系统管理的文件系统缓存 `page cache`，这一层正是本讲刷盘策略的关键所在。

### 一个更新事务的完整流转过程

知道了内存层面有 redo log buffer、磁盘层面有 redo log file 之后，我们先讲清 redo log 的整体流程。这个流程**一定要清楚**。至于文件里的结构是什么、redo log block 的头尾又有什么东西，那些你可以了解，但整体流程是必须掌握的。

为什么这个流程跟我们后面的优化有关？因为接下来就涉及到参数设置了。前面讲数据库调优的时候，我们提到过服务器层面可以调的参数，还通过一个案例用到过其中一个参数——那个参数，正好在这里能讲清楚。

我们就以一个更新的事务为例，看 redo log 的一整个流转过程。

**第一步：把要改的数据页加载进内存。**

我们要做一个更新操作的事务，首先得从磁盘中把你更新的这个事务对应的那张表里的数据，先加载到内存当中，放到缓冲池（buffer pool）里。

**第二步：在内存里改数据，并实时写 redo log buffer。**

事务对应的语句一操作，内存中的数据就被修改了。改完以后，按照 write-ahead logging 的要求，你得先去写日志。所以内存中改完，第二步就是在内存层面这个 redo log buffer 当中做一条记录。

> **易错点**：这一步不是等事务 `commit` 之后才做的。假设一个事务有多个语句，那么在事务的执行过程当中，它就已经开始记录了——**实时记录，与事务提交无关，也与后面要讲的刷盘参数无关**。

**第三步：把 redo log buffer 的内容刷到 redo log file。**

记录完之后，下一步就是把内存层面 redo log buffer 中的数据写入到磁盘中的 redo log file 里。先写到这儿。

**第四步：以一定频率把内存中数据页的修改刷盘到磁盘。**

再往后，你以一定的频率，把内存中数据页的修改刷到磁盘当中去。

所谓 write-ahead logging，说的就是**他优先、他其次**：日志先落，数据页后落。

```text
  磁盘                          内存                        磁盘
┌────────────┐  ①加载数据页  ┌────────────────────┐
│  数据表     │─────────────►│    buffer pool     │
│ （数据页）  │              │  ②语句在内存中修改  │
└────────────┘              └─────────┬──────────┘
      ▲                               │
      │                               │ ③write ahead：先记日志
      │                     ┌─────────▼──────────┐
      │                     │   redo log buffer  │
      │                     └─────────┬──────────┘
      │                               │
      │  ④按频率刷脏页                │ ③刷盘（本讲核心）
      │                               ▼
┌─────┴──────┐              ┌────────────────────┐
│  数据文件   │              │   redo log file    │
└────────────┘              │ ib_logfile0 / 1    │
                            └────────────────────┘
```

读图说明：① 数据页先从磁盘加载进 buffer pool；② 事务语句在内存里改数据；③ 因为 write-ahead logging，修改一发生就先记进 redo log buffer（实时），再刷到 redo log file（这一步就是大家说的刷盘）；④ 数据页本身按频率从 buffer pool 刷回磁盘。刷盘策略管的是 ③，不是 ④。

### 刷盘策略关注的是哪一步

下面专门讲 redo log 的刷盘策略。有同学会问，这个刷盘策略主要指的是谁？

> **结论**：主要指的就是上面第三步——**从内存的 redo log buffer 刷到 redo log file**。不是第四步数据页的刷盘。

为什么核心关注的是它？你想：只要把内存层面这个数据的修改（也就是你这个事务涉及到的修改）记录到了 redo log file 当中，这时候你就可以放 100 个心了。既然都写到文件里了，不管你的 MySQL 服务挂了，还是整个操作系统挂了，我们都不担心——修改的数据已经持久化了。MySQL 服务启动以后，我们只需要拿这个文件做一次恢复就行。

那现在的关键问题就是：内存中这块一修改，redo log buffer 就跟着改了，我们特别担心的点在于——**你什么时候会把 redo log buffer 中的数据刷新到 redo log file 里**。这个过程是让我们提心吊胆的：你别出事儿，你只要不出事儿，后面就不会有事儿，就能够保证事务的持久性。

#### 中间还有一层 page cache

先指明一件事：redo log buffer 刷新到文件里这个过程，**其实不是真正意义上直接刷新到磁盘**。

为什么？因为中间要经过文件系统缓存（page cache）。这是现代操作系统为了提高文件写入效率做的一个优化。

也就是说，我们要往磁盘刷的时候，先得过一下 page cache，然后由操作系统来决定怎么、什么时候把文件系统缓存里的数据再刷到磁盘中的 redo 文件里。这是操作系统做的一个优化行为。

所以这个刷盘操作，原来以为是一个过程，现在其实是两个过程：**buffer → page cache**，**page cache → redo log file**。两件事。

### 参数 innodb_flush_log_at_trx_commit 的三种取值

针对刷盘策略，MySQL 给了一个参数：`innodb_flush_log_at_trx_commit`。它管的是——**事务提交的时候，我们该如何刷新这个日志**。它针对的就是 redo log 日志。

这个参数有三种取值：1、0、2。先看默认行为。

```sql
-- 查看该参数的默认值
show variables like 'innodb_flush_log_at_trx_commit';
```

> **提示**：这个变量必须按 `global` 级别来设置，直接 `set` 一个不带作用域的写法会报错。

```sql
-- 正确写法：必须带 global
set global innodb_flush_log_at_trx_commit = 1;
```

#### 取值为 1：每次提交都同步刷盘

默认值是 1，它在调优那一讲里我们已经提过一次，当时是泛泛一说，包括 `innodb_log_buffer_size` 也是一样；现在我们正式讲这两个参数应该怎么用。

值为 1，表示**每次事务提交时都进行同步刷盘**。也就是说，从 buffer 到 page cache，再到 file，这两步都在提交时做掉：

- 事务执行过程当中，redo log buffer 那边一直在实时记录；
- 只要 `commit` 完成，内容就提交到 page cache；
- page cache 随即刷新到 redo 文件当中。

那就相当于，这个操作是随着事务提交来进行的。整体感受得到，它的保障是比较好的：一提交马上就做这件事，文件当中的数据还是比较有保障的。

> **结论**：值为 1 时，只要事务提交成功，数据就已经落到文件里，之后谁挂都不怕。持久性保证最好、安全性最好，代价是性能稍微差一点。

这里还要补一个细节：刷盘频率跟事务本身的持续时间有关。比如一个事务持续了 2 秒钟，那在这 2 秒里，其实后台线程每隔一秒就已经刷了一次；如果事务只执行了 0.5 秒，那还没等到那 1 秒钟的点，提交时的刷盘动作就已经做完了。

再看事务没提交的情况：我们往 buffer 里咔咔一顿写，然后服务器挂了。挂了就挂了——内存中的数据没有了，不要了。因为你也没提交，数据回到事务之前的最初状态，也是合情合理的。所以值为 1 的时候，完全能够保证事务的持久化。

#### 取值为 0：提交时什么都不做

值为 0，表示**每次事务提交时不进行刷盘操作**。

具体说：事务在提交的时候，它也不主动做 buffer → page cache 这件事，也不主动做 page cache → file 这件事，就相当于啥也没做。

那到底什么时候刷新？这里就提到一个关键点，稍微有点绕：**InnoDB 存储引擎有一个后台线程，它每隔一秒就会把 redo log buffer 中的内容写入文件系统缓存，然后调用刷盘操作。**

也就是说，redo log buffer 每隔一秒钟刷新到 page cache，然后同步到 redo log file 当中。如果参数设置为 0，事务提交时没有任何操作行为，那实际上执行的就是这个默认的一秒一次的行为。

变成什么叫法？**我不管你事务提交了还是没提交，因为提交这块你没有任何作为了，我就是每隔一秒往 page cache 刷一下，随后把后面那一半也做掉。** 纯粹的一秒一次。

#### 取值为 2：提交时只写到 page cache

值为 2 时，**每次事务提交都会把 redo log buffer 中的内容写入 page cache，但后边就不管了**。

即：只要一提交事务，马上把 redo log buffer 直接更新到 page cache 当中；之后 page cache → redo file 这件事我就不做了。你不做，就交给操作系统——操作系统大约每隔一秒钟，把 page cache 中的数据刷到 redo file 里。

所以三者的差别可以这样对照：

| 取值 | 事务提交时做什么 | 谁来决定落盘 | 持久性风险 |
| --- | --- | --- | --- |
| `1` | 同步刷盘：buffer → page cache → file 一次做完 | 提交动作本身 | 提交成功即安全；效率稍差 |
| `2` | 只做 buffer → page cache，后边不管 | 操作系统，约每秒一次 | MySQL 挂了没事，操作系统挂了丢 |
| `0` | 提交时什么都不做 | InnoDB 后台线程，每秒一次 | MySQL 挂、操作系统挂都丢；事务没提交也会被刷 |

> **注意**：取值为 0 时会出现一个特别的情况——**一个没有提交事务的 redo log，也会出现刷盘**。原因就是后台线程那个每秒一次的动作，它不看你提交没提交。

### 三种取值的持久化保证边界

#### 值为 0：不可靠的一秒窗口

参数为 0 时，事务提交的那一刻什么都不做，全靠后台线程每秒一次。既然提交这个动作不再提供任何保障，我们就不能保证数据的安全性，会有丢失数据的风险。这是三种取值里最"放飞"的一种。

#### 值为 2：MySQL 挂了没事，操作系统挂了就没了

值为 2 的时候，我们要考虑的核心场景还是"事务提交了没有"。一提交，它马上把这件事做到 page cache 这一层。

但是做到这儿其实是不保险的。假设事务 0.5 秒做完，那么后面还有约 0.5 秒的时间，才会去做 page cache → redo file 的那次刷盘。在这 0.5 秒之内，如果 MySQL 数据库服务器挂了会受影响吗？

- **MySQL 服务器挂了，不受影响。** 因为提交事务的时候数据已经更新到文件系统缓存了，这块已经归操作系统管了。换句话讲，MySQL 服务器挂了没关系，数据还在这儿。
- **操作系统挂了，就受影响了。** page cache 一挂，当前这个事务就相当于没有保存到 redo log file 当中。

> **结论**：参数取值 2 的时候，只要操作系统别挂就行。操作系统不挂、MySQL 服务器挂了，我们仍然保证持久化。而操作系统挂掉的概率还是比较低的——但毕竟算是有一定的风险。

注意，MySQL 服务挂了以后，redo log buffer 这块是不靠谱的（内存数据没了），但 page cache 里的内容还在，这就是值为 2 相对值为 0 的关键差别。

#### 在时序上把它们摆在一起

```text
时间轴 ──────────────────────────────────────────────────────────────►
        执行事务（redo log buffer 实时记录，与参数无关）
                                     │
                                  提交事务
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
     值为 1                       值为 2                       值为 0
        │                            │                            │
   buffer→page cache          buffer→page cache            提交时无任何动作
        │                            │                            │
   page cache→file             （等待操作系统）                （等待后台线程）
   （同步，立即）                    │                            │
        │                      约每秒一次刷 file              每秒一次 buffer→
        │                            │                       page cache→file
        ▼                            ▼                            ▼
  提交即持久化              0.5s 窗口内 OS 挂则丢       未提交的事务也会被刷盘
```

读图说明：三种取值在"提交事务"这一点上分岔——值为 1 当场把两步都做完，值为 2 只做到 page cache、后半程交给操作系统按秒推进，值为 0 提交时完全不动手、全部交给 InnoDB 后台线程。它们的差别不在"要不要记日志"，而在"提交这一刻谁负责把日志推过 page cache 这道关"。

### 三种取值的实测耗时对比

理论上说清楚了，我们再动手做一个例子，体现参数设置不同时，事务行为的耗时差别大概有多少，让大家宏观上有个概念。

测试环境是这样搭的：先 `use` 一下 `atguigudb3` 这个库，库里建一张 `test_log` 表，表结构很简单——一个自增主键列，外加一个定长字符串列，用来演示插入数据的行为。

然后提供一个存储过程，用于向 `test_log` 中添加数据。它的插入行为有两个关键设计：

- 插入时主键位置写成 `null`，交给自增列去生成；
- 字符列写入一段较长的字符串——让字符（比如 c）重复 80 次，构成一个 80 字符的定长值。

> **提示**：这两处的用意都在"让单个事务有点分量"。字符串够长，每行的写入量就不小；而真正决定耗时结构的，是下面的提交频率。

```sql
-- 创建存储过程：向 test_log 中循环插入数据
delimiter $$
create procedure p_insert_test_log()
begin
    declare i int default 1;
    while i <= 30000 do
        insert into test_log values(null, repeat('c', 80));
        commit;
        set i = i + 1;
    end while;
end $$
delimiter ;
```

这个存储过程里最要紧的一行是那个 `commit`：**每 `insert` 一下，就做一次 `commit`**。所以如果插入了 3 万条数据，那就相当于有 **3 万个事务**在执行。

下面依次跑三种取值，每次跑之前都清空表，保证每次都从空表、新事务开始。

```sql
-- 每次测试前清空表并确认
truncate table test_log;
select count(*) from test_log;

-- 设置并查看当前刷盘策略
set global innodb_flush_log_at_trx_commit = 1;   -- 依次改成 1、0、2
show variables like 'innodb_flush_log_at_trx_commit';

-- 调用存储过程，观察耗时
call p_insert_test_log();
```

`truncate` 这个清空操作本身相当于做过一次事务提交，所以我们再去测试的时候不会有什么影响，表里的数据每一次都是完全空的、一个新事务开始的。

#### 三次实测结果

| 测试 | `innodb_flush_log_at_trx_commit` | 执行 3 万条插入的耗时 | 说明 |
| --- | --- | --- | --- |
| 测试 1 | `1`（默认） | 1 分 28 秒 | 耗时最长，持久性最有保障 |
| 测试 2 | `0` | 37.945 秒 | 耗时最短，安全性最差 |
| 测试 3 | `2` | 45 秒多 | 介于两者之间，与 0 比较接近 |

三次对比下来，差别是能明显看出来的：

- 耗时关系大约在 **一比三** 这样的量级（3 万条数据，说实话还不算特别多，差别已经这么明显）；
- 取值为 `0` 和 `2` 时两者耗时比较接近，**都比取值为 `1` 时更少**；
- 取值为 `1` 是默认行为，它一定比 `0` 和 `2` 花的时间更多，但它保证的是真正意义上的数据安全性，也就是我们所说的事务持久性。

> **结论**：从实际情况看，虽然取值为 1 耗时最多，但还是建议大家相对 0 和 2 选择 1。唯一的例外，是面对上一章讲的那个案例那种场景——服务器宕机的场景毕竟比较少出现，那时可以考虑降低 CPU 的使用频率，把这个值做一次修改。当时讲数据库调优案例的时候，我们就是把 1 改成了 2。

### 实测数据带来的两个判断

#### 这 3 万条数据本身应该怎么插

刚才演示的时候，我说过 3 万条数据其实不算多，但从另一个角度讲，这里边执行的时间花到哪了？**因为我们每做一个操作就做了一次 `commit`，相当于这里有 3 万个事务。**

单纯针对这个题目来讲：如果我们要插入 3 万条数据，其实应该把它们**整体看成一个事务**来操作——不要每次执行完一个 `insert` 就 `commit` 一下，那样花的时间肯定要多；3 万条都插完了以后，再去提交一次，这样更靠谱。

那为什么测试还要这么写？因为这个题目要测的就是"想让事务多一点"——**把每个事务多花的那一点时间累积起来，一共 3 万个，来看参数不同造成的差别有多大**。这一点懂就行。

#### 参数值到底看什么

把耗时和安全性两件事合起来看，判断标准就两条：

1. **要不要接受"提交后仍可能丢"的窗口**——取值为 1 没有这个窗口，取值为 2 有一个约一秒（取决于提交时刻与刷盘时刻的相对位置）的窗口，取值为 0 连未提交的事务都可能被刷，谈不上保证。
2. **能不能接受"每次提交都同步刷盘"的开销**——如果你的场景是高频小事务，比如这里每次 `insert` 一个事务，那么取值为 1 的开销会被放大 3 万倍地累积出来；这时候要么按 7.1 把多个操作合并成一个事务，要么才去考虑把参数降到 2。

整体上，针对这三种取值的效率和安全性问题，到这里已经讲完了，大家心里应该有个直观印象：自己机器上测出来的数据，跟这里的实测结果差不太大，极其接近。

### 基本概念：mini-transaction（MTR）

#### 原子访问与 MTR 的定义

要把 redo log buffer 的写入过程讲明白，先得引入一个概念：迷你事务（mini-transaction，MTR）。

> **定义**：MySQL 把对底层页面的一次原子访问的过程，称为一个迷你事务（mini-transaction，MTR）。一个 MTR 可以包含一组 redo 日志记录。

这句话里有两个词是绑在一起的：**原子访问**和**一组日志**。原子访问是说这次访问不可再分，中间不会插进别的访问；一组日志是说这一个不可再分的动作，落到 redo 日志上不一定是**一条**。

#### 一个 MTR 对应多条 redo 日志的原因

拿往索引对应的 B+ 树里插一条记录来说。这就是一次原子操作，我们把它称为一个 MTR。可这一个 MTR 里，会包含一组 redo 日志，为什么？

设想往 B+ 树的某个数据页里插一条记录，位置落在已有两条记录中间。位置一插进去，原来在后头的那条记录就得往后移；更麻烦的是，这一页有可能本来就是满的，那还得牵扯到往下一页移——移到哪儿，中间这一块又怎么空出来。这一连串动作，每一下都要记日志。而 redo 日志记录的是物理磁盘上你做的那个具体操作：哪一个页、页内哪个位置、偏移量是多少、做什么样的移动和修改。所以一个 MTR 里**一定**是有多条 redo 记录，这一点没有疑问。

#### 事务、语句、MTR 与 redo 日志的包含关系

再往上看一层：一个事务可能包含多个语句，而每一个语句是由若干个 MTR 构成的。这条关系线必须先立住，后面讲 redo log buffer 的写入过程才接得上。

```text
事务（transaction）
 |
 +-- 语句 1
 |    |
 |    +-- MTR-1 --+   redo #1
 |    |           +   redo #2
 |    |           +   ...（一组，必须连着）
 |    |
 |    +-- MTR-2 --+   redo #1
 |                 +   ...
 |
 +-- 语句 2
 |    +-- MTR-1 ...
 |
 +-- 语句 3 ...
```

读图：包含关系自上而下收窄——一个事务拆成若干语句，每条语句拆成若干 MTR，每个 MTR 再拆成一组 redo 日志记录。

拿一条语句来验证这条链。我们写一个 `update`，把某张表里工资是 5000 的改成 6000：

```sql
update 表名 set salary = 6000 where salary = 5000;
```

这一条语句底下要改的位置可能不止一处，因为 `salary` 是 5000 的记录可能有多个位置都得改。**每改一个位置，就相当于一次原子化的访问，也就是一个 MTR**；而刚才说了，一个 MTR 又可能对应多条 redo 日志记录。语句、MTR、redo 日志这三层的关系，到这里就清楚了。

### redo log buffer 的写入过程

#### 日志块的组成与 `buf_free` 指针

redo log buffer 在内存中是**一片区域**，这片区域由一个一个的 redo log block（日志块）构成。一个块多大？512 字节。每个块又由三部分构成——日志头（log block header）、日志体（log body）、日志尾（log block trailer）。

其中头和尾不存数据，真正放数据的是日志体。日志体里放的，就是一条一条的 redo 记录：redo-1、redo-2 …… redo-n。

我们要做的，就是把上面那些 redo 日志往这片内存里填。填满一个块就依次往后走，走到哪儿算哪儿；再来新的 redo 日志就接着往下挤，前一个块满了就挤到下一个块。

```text
redo log buffer（内存中的一片区域）

+--------+--------+--------+--------+--------+--------+--------+
| block1 | block2 | block3 | block4 | block5 |        |        |
| 已填满 | 已填满 | 已填满 | 已填满 | 未填满 |  空闲  |  空闲  |
+--------+--------+--------+--------+--------+--------+--------+
                                          ^
                                          |
                                       buf_free
                                 （记录当前用到了哪里）
```

读图：日志按块顺序向右填充，`buf_free` 这个变量始终指着已经用到的那条边界，左边的块已经写满，右边还是空闲。

那"现在写到哪儿了"这件事得有个变量记着，这个变量叫 `buf_free`。它记录当前使用到哪个位置，之后新来的 redo 日志就从它指的位置继续往后放。

#### MTR 内部连续与 MTR 之间的交错

一个 MTR 执行过程中会产生若干条 redo 日志，这已经说过了。关键在于：**这个 MTR 是满足原子性的，不能分割**。既然不能分割，那它这一组日志往 redo log buffer 里放的时候就必须**挨着**，中间不能被别人的日志插进来。

那把事务的层级先跨过去，直接看 MTR。假设事务 1 由两个 MTR 构成，记为 `MTR-T1` 的第一和第二个；事务 2 同理。于是我们手上有 4 个 MTR，每个 MTR 各自带着一组必须连成整体的 redo 日志。

> **结论**：**一个 MTR 内部的 redo 日志必须完全挨着；不同 MTR 之间可以不挨着。**

为什么可以不挨着？因为事务本身是并发执行的。既然可能并发，两个事务的 MTR 就可能交替地落在 redo log buffer 里。

假设当前已经写到了某个位置，此刻"同时"（加引号的"同时"）执行事务 1 和事务 2，各自带两个 MTR。一种可能的落法是：先把事务 1 的 MTR-1 写进去——它是个整体，内部日志必须连着；紧接着进来的不是事务 1 的东西，而是另一个事务里的一个 MTR；随后又轮回事务 1 的第二个 MTR，而这个 MTR 在当前块里放不下了，那就另起一个块，还放不下就接着再往后——用多少算多少；等它落定，再下一个是事务 2 的第二个 MTR，接着往后放就行。

```text
redo log buffer 中的实际排布（两个事务共 4 个 MTR 交替落入）

|<- block ->|<- block ->|<- block ->|<- block ->|<- block ->|
+-----------+-----------+-----------+-----------+-----------+
| T1-MTR1   | T1-MTR1   | T2-MTR1   | T1-MTR2   | T1-MTR2   | ...
| redo #1   | redo #2   | redo #1   | redo #1   | redo #2   |
+-----------+-----------+-----------+-----------+-----------+
                                                        ^
                                                     buf_free

  T2-MTR2 随后接在这里
```

读图：同一个 MTR 的 redo 记录是连成一片的（如 `T1-MTR1` 的两条紧挨着），而 `T2-MTR1` 可以切在 `T1-MTR1` 和 `T1-MTR2` 中间——MTR 之间允许被打断，MTR 内部不允许。当一个 MTR 在当前块里放不下时，它会跨到下一个块继续写。

一句话收束这一节：**MTR 内部的这些 record 必须完全挨着**，这就是我们要强调的问题。

#### 日志块的字节划分与 512 字节的来源

还是由整体到部分。整体是 redo log buffer 这片区域，部分是其中的一个块。这个块由日志头、日志体、日志尾三部分构成，它们的字节数是：头占 12 个字节，尾占 8 个字节。

$$512 - 12 - 8 = 492$$

也就是说，一个 512 字节的块里，真正能存 redo 记录的是 **492 字节**。

```text
                     一个 redo log block（512 字节）

+------------------+----------------------------------+------------------+
| 日志头（header） |          日志体（body）          | 日志尾（trailer）|
|     12 字节      |            492 字节              |      8 字节      |
+------------------+----------------------------------+------------------+
                     redo #1 | redo #2 | ... | redo #n
                     头尾都不存数据，日志记录只放 body 里
```

读图：日志头和日志尾是固定开销，各占 12 字节与 8 字节，夹在中间的 492 字节日志体才是装 redo 记录的地方。

至于日志头、日志尾内部又包含哪些字段、每个字段什么意思，这里不再解释。有兴趣的同学可以在这里停一下，稍微暂停，自己看看里边的意思。再往下讲就有点过深了；包括在里边再去测试等等，也不做，没必要，适可而止。

那**为什么这个块设计成 512 字节**？这算一个常识：跟我们磁盘的扇区有关。机械磁盘默认一个扇区是 512 个字节，我们跟它正好完全匹配。

匹配的意义有两个：

- 如果你要写入的数据大于 512 字节，就相当于要占**两个扇区**，那就得转动磁盘去找下一个扇区，这首先是要花时间的；
- 其次，假如 A 扇区写成功、B 扇区写失败（磁盘扇区坏了等等这类问题），就会出现**非原子性**的操作。

所以我们干脆让它完全匹配：**一个磁盘扇区对应一个日志块**。这样一次块的写入就落在一个扇区的原子粒度上。

到这里，redo log buffer 就说完了。

### redo log file 的存储位置与容量参数

接下来看 redo log file。这块有什么可说的？实际里边还是有一些问题可以揪的。

#### 日志文件位置参数 `innodb_log_group_home_dir`

第一个参数是 `innodb_log_group_home_dir`，它管的是 redo log 文件**到底存在哪儿**。

默认情况下就在当前的数据目录下，也就是我们看到的这两个文件。为什么在那儿？主要就是由这个变量记录的。可以 `SHOW` 一下：

```sql
-- 在 MySQL 里查看与 redo log 相关的系统变量
SHOW variables LIKE '%innodb_log%';
```

你会看到 `innodb_log_group_home_dir` 这个值是一个 `.\`。它相当于一个根目录，而这个根目录指的就是当前的数据目录——作为我们所谓的根目录，实际就是刚才看到的那条路径，意思是把日志文件放在这儿。

#### 日志文件个数与单个文件大小

放在这里边的文件，默认情况下有**两个**。为什么是两个？由另一个系统变量控制，`SHOW` 出来你会看到它的值是 `2`，这个 2 正好对得上：第一个文件、第二个文件。

再往下一步，就是每个文件的大小。单个文件的大小由再下面一个变量控制，这个直接 `SHOW` 一下就能看到取值，一换算就是 **48 MB**。

（放在这几个变量上面那个参数，就是上一讲已经讲过的刷盘策略。）

把这些参数对照着列出来：

| 参数 / 变量 | 作用 | 本讲看到的取值 |
| --- | --- | --- |
| `innodb_log_group_home_dir` | redo log 文件的存放目录 | `.\`（即当前数据目录） |
| 控制日志文件个数的系统变量 | 一个日志文件组里有几个文件 | `2` |
| 控制单个文件大小的系统变量 | 每个日志文件多大 | 换算后为 48 MB |
| 刷盘策略参数 | redo log buffer 何时刷到 redo log file | 上一讲已讲 |

`innodb_log_group_home_dir` 只负责**位置**，文件**个数**与单个文件**大小**分别由另外两个变量控制，三者分工不同，别混在一起记。

#### 组的容量上限与扩容判断

关于大小，有一个上限要注意：**日志文件（组）的大小最大可以是 512 GB**。

这里最容易搞错的是"512 G"到底指谁。

> **易错点**：512 GB 不是**每个文件**能到 512 GB，而是整个**组**的上限。你有几个文件、每个文件多大，乘起来不能超过 512 GB。

对比一下默认值就更清楚了：默认两个文件，每个 48 MB，那么当前占用的空间是

$$48 \times 2 = 96\ \text{MB}$$

整个组的容量上限是 512 GB，而当前只有 96 MB——这已经足够大了。

单个文件的大小也可以通过修改配置文件的方式来设置。

那什么时候要去动它？如果我们这个数据库实例更新得比较频繁，就可以把 group 增大，同时把每个文件的大小也设大一些。

还有一点要留意：整个文件显示为 48 MB，**并不意味着当前已经把这个文件完全占满了**，它里边其实是有一部分是空的；随着事务的增加，它才会逐渐把这块空间占起来。48 MB 是文件的容量，不是当前的使用量。

### 日志文件组的循环写入机制

#### 容量不足时的复用前提

先把问题问出来。有同学会想：万一提交以后这个事务还没刷盘呢？这里要分清两个地方——一个是内存，一个是磁盘。

内存中的数据只要被更新了，就都要记录到 redo log file 里。反过来说，如果内存中的数据已经更新到磁盘上了，那么它在 redo log file 里按说就没有必要再存了，这是其中一部分。

可问题在于：如果内存到磁盘的刷盘操作**积累得太多**，超过了 96 MB（48 MB × 2），文件就存不下了。存不下怎么办？

当然是要扩容。但这里边涉及一些机制，其中一条就是**重复利用**：前面说了，有些数据已经刷到磁盘上了，还在这儿记着就没有必要了。把这个前提用起来，就可以做覆盖。

做一道算术题。假设当前待刷盘的数据是 **90 MB**，这 90 MB 都要往日志文件里放；而文件里现在有 **10 MB** 是之前记录的、现在已经从内存刷盘到磁盘上的数据。

按 90 + 10 = 100 MB 算，显然是存不下的。可你要把这 10 MB 干掉——也就是把之前那些没用的数据覆盖掉——剩下的空间是 96 MB，90 MB 就放得下了。

> **结论**：redo log file 之所以能被循环覆盖，前提是**被覆盖的那段数据已经刷盘到磁盘**，它的日志使命已经完成。

那么这个过程具体是怎么实现的？这就是 redo log file 下面要讲的机制：**日志文件组**（log file group）。

刚才提到一个 group 有两个文件，你也可以设置成多个。假设这里有 n 个文件——一个、两个、一直数到 n。注意数法：如果编号从 0 起，0、1、2、3 这样数到 n，实际上是 **n + 1 个**文件。这么多日志文件合在一起，就构成了一个日志文件组。组里每个文件的大小都一样，通过前面那个参数来设置。

宏观上写入过程是这样的：数据从**头部**开始写，一路写下去；写到第 n 个文件写完了，就翻回来，再从头部接着写。

总共能写多少？最多就是**文件个数 × 单个文件大小**这个乘积。之所以敢回过头去覆盖之前的数据，是因为按定义，之前那段数据已经从内存刷盘到磁盘里了，前面的数据就不要了。

#### `write pos` 与 `checkpoint` 的推进

具体算法涉及两个变量：

- `write pos`：记录当前**写到**的位置，一边写一边往后移；
- `checkpoint`：当前要**擦除**的位置，同样往后推移。

整个过程用一个环来看最清楚。这里画 4 个日志文件，编号 0、1、2、3。

最初的时候，这两个变量都停在同一个位置上。只要往日志文件里写数据，`write pos` 就一直往后移——先动的就是它。假设写着写着到了某个位置，接下来再写，就顺着这个指针继续往后就行。

```text
初始状态：两个指针重合在一起

  file0    file1    file2    file3
    |        |        |        |
    v        v        v        v
 +--------+--------+--------+--------+
 |        |        |        |        |
 +--------+--------+--------+--------+
 ^
 write pos = checkpoint（起点）


写入一段、并且发生了一些刷盘之后

 +--------+--------+--------+--------+
 | 已刷盘 | 已刷盘 |   已记录、未刷盘  |
 +--------+--------+--------+--------+
      ^                   ^
      |                   |
  checkpoint           write pos

 checkpoint  ->  write pos ：已写入日志、还没刷盘，不可覆盖
 write pos   ->  checkpoint（绕回一圈）：空闲，可以继续写
```

读图：`write pos` 随写入前进，`checkpoint` 随刷盘前进；两个指针在环上把空间分成"可写"与"已记录未刷盘"两段。

那 `checkpoint` 这个变量为什么要往后移？因为随着你把内存中的数据刷新到磁盘，相应地，redo log file 里对应的那部分记录就没有必要了。于是从它这个位置开始往后移——移到某个位置之后，**`checkpoint` 和 `write pos` 中间的数据，就是目前已经在 redo log file 里做了记录、但还没有刷新到磁盘上的数据**。后面再刷盘，这个指针就继续往后赶。

接下来是本讲最要紧的一句话。**`write pos` 当前位置到 `checkpoint` 那个位置之间的空间，其实都是可以再写入的**——不只是写到 `checkpoint` 就停了。因为我们虽然写到了这里、算是写满了，但这一段数据已经都刷新到磁盘上了，当然可以再去覆盖它。

> **结论**：环上从 `write pos` 绕行到 `checkpoint` 的整段，都是可以再次写入的空间。

#### 覆盖边界：`write pos` 追上 `checkpoint`

按上面那条规则继续写。写着写着，`write pos` 也来到了 `checkpoint` 所在的位置，两个指针**重合**了。

这时的含义是：`write pos` 相当于绕着 `checkpoint` 走了整整一圈。

- 如果下一刻 `checkpoint` 接着往后移动了，那就没问题——两个指针之间又腾出的这段差距，仍然是可以再次写入的空间大小。
- 如果下一刻 `write pos` 要去**超过** `checkpoint`，那就麻烦了。

为什么麻烦？因为 `checkpoint` 后边的那部分数据**还没有进行刷盘操作**，你是不能去覆盖它的。再想往后写 `write pos`，就意味着这个日志文件**真的是已经满了**。

```text
write pos 与 checkpoint 的三种相对位置

 情形一：正常推进（中间是未刷盘数据，后方是空闲）
 +--------+--------+--------+--------+
 | 空闲   | 空闲   | 已记录未刷盘      |
 +--------+--------+--------+--------+
      ^                   ^
  checkpoint           write pos

 情形二：write pos 绕行一圈，与 checkpoint 重合
 +--------+--------+--------+--------+
 | 已记录、未刷盘（占满整圈）        |
 +--------+--------+--------+--------+
                     ^
          write pos = checkpoint
          （下一刻 checkpoint 后移即可继续写）

 情形三：write pos 将要超过 checkpoint —— 文件真的满了
 +--------+--------+--------+--------+
 | 未刷盘（不可覆盖）| 未刷盘（不可覆盖）|
 +--------+--------+--------+--------+
                ^              ^
          write pos        checkpoint
          （再往后写就无路可走，需要扩容）
```

读图：三种情形的差别只在两个指针的相对位置——中间隔着的是空闲区，指针重合是走了整整一圈，`write pos` 要越过 `checkpoint` 就是撞上了未刷盘的数据，此时文件才真正算满。

到这里，redo log file 的写入过程就说清楚了。

### Write-Ahead Log 策略的整体把控

整个 redo log 部分讲完，需要大家整体把控的是一条策略：**预写式日志（Write-Ahead Log，WAL）**。

它说的是一件很朴素的事：**一定要先把数据写入日志文件，然后才考虑把内存中的数据进行刷盘**。

这一讲讲的 `write pos` 与 `checkpoint` 机制，正好是这条策略的另一面。环上从 `checkpoint` 到 `write pos` 的那一段，是"已经写了日志、但还没刷盘"的数据，它必须被保护起来、不能被覆盖；只有在数据真正刷到磁盘之后，`checkpoint` 才能往前推，那一段空间才被释放出来供回卷覆盖。换句话说，**日志文件的循环复用，本身就是被 WAL 的顺序约束住的**——不能提前覆盖，是因为它所保护的那份数据还没落盘。

```text
  ① 修改内存中的数据页
        |
        |   必须先把对应的 redo 日志写下来（Write-Ahead）
        v
  ② redo log buffer（内存）── 按刷盘策略 ──> ③ redo log file（磁盘）
                                                    |
                    ④ 之后才考虑把内存中的数据刷盘   |
                                                    v
                                          ⑤ 表空间数据文件（磁盘）

  回卷覆盖的许可条件：redo log file 中"已经刷盘"的那一段
                      （checkpoint 之后才允许被 write pos 覆盖）
```

读图：写入顺序自上而下是"先日志、后数据"，而右侧标注的回卷覆盖条件说明，日志文件能循环利用正是因为它的旧数据已经落盘。

redo log 到这里讲完。接下来要讲的是 undo 日志。

## 172-Undo日志的概述与写入过程
> 对应分集：P172 | 原始标题：《172-Undo日志的概述与写入过程》

上一讲我们拆事务执行过程中那张图的时候，undo 日志其实已经在图里露过脸了——它处在什么位置、卡在执行流程的哪一个环节，你们当时就看到了。当时没展开，这一讲我们就具体来看它：undo 日志到底是怎么保证事务的原子性的。

这一讲的内容我们分成几块来说。先把泛泛意义上 undo 日志的基本情况说清楚；再讲它的"生命周期"——从一开始的生成，到需要回滚时怎么操作，直到最后怎么删除；然后是它的存储结构，以及真正写入时那条版本链是怎么长出来的。这一讲整体难度不大，你们熟悉这样一个过程就可以了。

### Undo 日志的基本概念与写入位置

事务中更新数据的前置操作，是先写入一条 undo log。这句话就回答了刚才留下的那个问题——更新数据不是第一步。

> **定义**：为了支持回滚而记录下来的内容，就叫撤销日志，也叫回滚日志（undo log）。

这里有三个关键点。

第一，所谓"更新数据"不简单指 `update` 这一条语句，`insert` 和 `delete` 同样算。说白了，凡是针对数据表里的数据做了修改的操作，我们都泛泛地称之为更新。但 `select` 不包括在内，查询操作是不会写入 undo 日志的。

第二，它的写入时机在更新数据之前。把更新之前的数据记录到 undo 日志里，这一点其实很好理解：要是等更新完了才记，回滚的时候你手里拿的是什么？回滚要回滚到更新之前的状态，所以记录的必然是更改之前的数据。

第三，正因为它记录的是旧值、写的是逻辑信息，undo 日志整体上比 redo 日志要简单，难度不是特别大。

> **提示**：这里说的"更新"是个泛指概念——`insert`、`delete`、`update` 都算更新，唯独 `select` 不算。它不是语句层面的分类，而是"有没有改动数据表里的数据"这个层面的分类。

还有一点要单独留意：undo log 本身也会产生 redo log。undo 日志自己也需要持久化保护，所以它同样伴随着 redo log 的生成，这个大家注意一下。

### Undo 日志在事务原子性中的作用

事务要保证原子性，这个前面都讲过：要么全部完成，要么什么也不做。那我们就得考虑，事务在执行过程当中可能出现的意外情况到底是什么。一方面来自服务器本身——MySQL 数据库服务器也好，操作系统也好，甚至物理层面的断电也好，都可能出意外；另一方面是我们主动执行 `rollback` 去做数据回滚。

这些情况一旦发生，一个事务里的多个操作有可能只执行了一半，那就得让已经执行的那部分再退回去。退回去之后造成的效果是：看起来这个事务之前做的事等于什么也没做。

> **结论**：undo 日志要解决的就是这个"看起来什么也没做"——用"退回去"的记录，把执行到一半的事务抹平。

### Undo 日志的两大作用

#### 回滚数据

回滚数据是 undo 日志最直观的作用，上面说的那些就是它。但这里有一个容易产生的误解，我要专门提一下：**undo 日志不可能把我们这个数据物理性地恢复到之前。**

举个例子。现在有一个数据页，我们在事务当中执行一个插入数据的操作。或者假设这个数据页已经满了，你要插的这条数据一看页满了，那就得开辟一个新的数据页，在新页里把数据插进去。紧接着，我在这个事务里执行了一个 `rollback`。这时候它会对我插入的这条数据做一个删除操作。

那是不是说，我们把整个新开辟的数据页也一起干掉了、什么都退回去了？不是的。数据页已经开辟，那个空间就真的开辟了；`rollback` 只是相当于又做了一次 `delete`，把刚添加的那条数据删掉。而物理层面上的这个数据页不会跟着消失。

为什么不能收回这个页？你想想，一个数据库里实际上可以同时执行几百个甚至上千个并发事务。有可能你这个事务往表里加了一条记录，另外还有好几个事务也在往表里加记录，它们用的可能就是同一个新数据页。你要是回滚时把这个页收回去，那这些事务怎么办？这不就懵了。所以肯定不行。

需要明确的是：我们只是**从逻辑上**把数据恢复成原来的样子，物理层面上如果已经发生了一些变化，这个变化是改不了的。

说得再直白一点，我们做的这个事只能是一直往前推，不能真正意义上说"回滚了"。用生活里的例子说：A 给了 B 100 块钱，现在你要做回滚，这个回滚不是说让这件事退回到没发生过的状态，那不可能；只能是 B 又把这 100 块钱还给 A，最后达到的效果相当于没转成、没给钱。之前是个 `insert`，现在就做个 `delete`，让你看到的是之前的效果，这是逻辑上的，不是物理意义上的。

再换个说法，就像两个人相处，你恶言恶语已经伤害到对方了；你后面再怎么把她哄好，可能回到吵架之前的状态，但那种伤害有可能是持续性的。你只能是说了些不好的话、又加了些好的话，达到一个平衡——但那也只是**最终效果上的平衡**而已。

> **易错点**：undo 的"恢复"是逻辑恢复，不是物理恢复。物理上已经发生的页分配、空间占用等变化收不回去，所以 undo 与 redo 也绝不是互为逆过程。

#### MVCC

第二个作用是并发多版本并发控制（MVCC，Multi-Version Concurrency Control），这个我们在专门讲 MVCC 的时候再重点展开，现在先泛泛理解一下：InnoDB 存储引擎的 MVCC 实现，是通过 undo 来完成的。

当用户读取一行记录时，如果该记录已经被其他事务占用，当前事务可以通过 undo 读取这行记录之前的行版本信息，从而实现非锁定读取。这就是 undo 日志的第二个作用。

### Undo 日志的存储结构

undo 日志采用**段**的方式来组织，这个段我们称之为回滚段（rollback segment）。

段下面是 undo log segment：每个 rollback segment 里记录了 1024 个 undo log segment，这个数字要记住。而在每一个 undo log segment 当中，进行 undo 页的申请——undo 页里才是你真正去写的那些回滚记录，也就是前面讲的那些具体内容。

```text
表空间（undo 表空间 / ibdata 共享表空间）
  └─ 回滚段 rollback segment            × 1（InnoDB 1.1 之前）
     └─ undo log segment               × 1024（每个回滚段内）
        └─ undo 页（申请自 undo log segment）
           └─ 回滚记录（insert / update 类型）
```

读图说明：从表空间往下逐层收敛，回滚段是顶层容器，undo log segment 是它内部固定 1024 个的槽位，真正的回滚记录最终落在 undo 页里。

回滚段到底有多少个？在 InnoDB 1.1 版本之前（不包括 1.1），我们只有一个回滚段。那就意味着同时可以有 1024 个事务并发执行，每个事务相当于使用一个 undo log segment。到了 1.1 这个版本之后，InnoDB 最大支持 128 个回滚段，这时候 128 × 1024，就能同时支持这么多在线并发事务了，你们体会一下这个量级。

回滚段虽然支持到 128 个，但这些回滚段的数据都存在 `ibdata` 里。`ibdata` 我们在讲架构、讲目录结构的时候提到过，它是一个共享表空间；以前表数据都可以设置成存储在这里边。

这里有三个参数了解一下：

| 参数 | 含义 | 说明 |
| --- | --- | --- |
| `innodb_undo_directory` | undo log 的存储位置 | 默认值是一个点，也就是 `./`，实际就是存在当前的数据目录下，即 `var/lib/mysql` 目录下 |
| `innodb_undo_logs` | 回滚段的个数 | 默认回滚段数量 |
| `innodb_undo_tablespaces` | 构成回滚段的文件数量 | 可以设置多个，**至少得有两个** |

用 `show variables like` 加上参数名就能查看这些值，比如 `innodb_undo_directory` 查出来就是 `./` 这样一个点斜杠的值，`innodb_undo_tablespaces` 默认查出来就是 2。这些参数一般我们很少去改动，了解一下就可以。

那为什么 undo 表空间**至少要有两个**？比如这一个文件正在使用，另一个文件就可以拿去做一些清理操作，这样才有腾挪的余地——下面讲重用时还会提到这件事。

### 回滚段结构与 undo 页重用

#### undo 页重用

undo 页也是要考虑重用的。这里要解决什么问题呢？每开启一个事务，都要把执行增删改之前的数据记录到 undo log 当中；如果每个事务都去申请一个独立的页，而我们一个页的大小是 16 KB，这样分配其实是非常浪费的。

算一笔账：`TPS`（每秒处理事务的数量）如果是 1000，那就意味着 1 秒钟一个事务对应一个页，相当于要操作 1000 个页，大概就是 16 MB；一分钟下来就相当于 1 GB 了。这样下去，如果清理不及时，整个空间占用会非常快。空间被占满倒还好说，关键在于**一个事务对应一个页本身就是对页空间的极大浪费**，因为页里面大部分都是空的。

> **结论**：解决办法就是 undo 页可以被重用。一个 undo 页当中可能混杂着好几个事务的记录；事务提交以后，这个 undo 页会被放到一个链表当中，如果这个 undo 页的使用空间小于 3/4，它就可以被重用。

#### 回滚段与事务

回滚段和具体事务之间有几个点，直接说就明白：

- 每个事务都会使用一个回滚段，而一个回滚段在同一个时刻可能会服务于多个事务。
- 一个事务开始的时候，会指定一个回滚段。
- 在事务进行的过程中，数据被修改时，原始数据会被复制到这个回滚段里边。
- 在回滚段中，事务会不断地填充盘区，直到事务结束、或者所有空间被用完。
- 当盘区不够用的时候，事务会在段当中请求下一个盘区——段里边放的本来就是区。
- 如果所有的盘区都用完了，事务会覆盖最初的盘区；或者在回滚段允许的情况下，去扩展新的盘区。

回滚段存储于 undo 表的表空间当中，数据库中可以存在多个 undo 表的表空间。前面我们查过的那两个参数，至少得是 2，说的就是这件事。

#### 提交时的两个判断

事务提交的时候，InnoDB 存储引擎会判断两件事。

第一，是不是要提交了。因为一旦提交，我们就不会去回滚数据了，这时候就可以考虑把 undo log 放到列表当中，供之后的清除线程去做清除操作。

第二，判断 undo log 所在的页是不是可以被重用。就是刚才说的那个比例——使用率低于 3/4 的页可以考虑重用。

### 回滚段中数据与 undo 的类型

#### 数据的三种状态

回滚段中记录的都是 undo log，这些数据分成三种情况。

**第一种，未提交的回滚数据。** 比如一个事务里做了好几个增删改操作，每做一次操作之前，都要把原始数据记录到相应回滚段的 undo log 里，每一次执行之前都要这样记一笔。当事务还没有提交的时候，随时有可能回滚，这时这些数据就处于第一种状态。

**第二种，已经提交但未过期的回滚数据。** 事务最后做了 `commit`，但 commit 完之后数据还没有过期。有同学可能会想：事务一提交不就不能回滚了吗？既然不能回滚，这些数据不就完全失效了吗？其实不然。事务提交之后不能马上删除 undo log 和 undo log 所在的页，这是因为可能还有其他的事务要通过 undo log 取得行记录之前的版本。

**第三种，已经提交并且已经过期的回滚数据。** 到了这一步，purge 线程才会最终去判断这个 log 和它所在的页是不是要删掉，以及是不是可以重用。

也就是说，数据先被放进链表当中，由 purge 线程来最终判断。

#### undo 的两种类型

回滚段中数据分类的第二、第三种情况，从 undo 的类型上也能体会到。undo 分成两种类型：一种是 `insert` 类型，一种是 `update` 类型。有同学会问，怎么没有 `delete` 类型？因为 `delete` 跟 `update` 合在一起了。

`insert` 操作产生的 undo log 属于 `insert` 类型。这类记录对事务本身是可见的，其他事务看不到它——这是隔离性的要求。正因为其他事务不会用到它，所以事务提交以后，这个 undo log 就可以直接进行删除操作。这就是我们直观上理解的"我提交了，undo log 就该清除了"。

`update` 类型则是 `delete` 和 `update` 产生的 undo log。这类 undo log 需要提供多版本并发的机制，所以当前事务提交完之后，其他事务仍然有可能要查看你这次操作之前的数据。因此我们不能急着删除它，而是要把它放到 undo log 链表当中，由清除的线程来决定最后的清除行为。

| undo 类型 | 来源操作 | 对其他事务可见性 | 事务结束后的处理 |
| --- | --- | --- | --- |
| `insert` 类型 | `insert` | 不可见（隔离性要求） | 事务结束即可直接删除 |
| `update` 类型 | `update`、`delete` | 可能被其他事务读取旧版本 | 放入 undo log 链表，交由 purge 线程判断 |

读表说明：两类 undo 的差别只在"别人还需不需要它"，`insert` 记录别人用不上，所以能立即删；`update` 记录要支撑 MVCC，所以必须留待判断。

### Undo 与 Redo 的写入过程

#### 只有 Buffer Pool 时的流程

先看没有 redo、没有 undo 的情况下，只有 Buffer Pool 参与时，查询操作和增删改操作是怎么走的。

```text
客户端请求
   │
   ▼
Buffer Pool（内存）
   │ 没有要查询/更新的数据 → 从磁盘加载
   ▼
磁盘数据页
   │ 更新完成后，按刷盘策略定期回写
   └──────────────► 磁盘数据页
```

读图说明：内存里没有目标数据就从磁盘加载，更新完的数据靠定期刷盘策略回写磁盘——这条链路上没有任何日志保护，宕机就会丢数据。

#### 加入 redo 与 undo 之后的写入顺序

有了 redo log 和 undo log 之后，以更新数据为例，`Buffer Pool` 里找不到目标数据，还是先从磁盘加载。区别在于接下来这几步。

```text
        ┌──────────────┐
        │  Buffer Pool │（内存中的数据页，含更新后的最新值）
        └──────┬───────┘
   更新前记录旧值│            │更新后写入新值
        ▼                    ▼
   undo log（回滚段文件）   redo log buffer（内存）
        │                    │ 按参数控制的策略刷盘
        │                    ▼
        │              redo log file（磁盘日志文件）
        │                    │
        └────────► 后续再把内存中的数据页刷盘到磁盘数据页
```

读图说明：更新之前先把旧值写进回滚段的 undo 文件，更新之后把新值写进内存的 redo log buffer，再由 redo log buffer 落到磁盘的 redo log 文件，最后才是把内存数据页刷到磁盘数据页——日志始终走在数据前面，这就是日志文件优先原则（write-ahead logging）。

执行器帮我们完成更新操作。更新完以后，要把更新后的数据记录到内存层面的 `redo log buffer` 里面；`redo log buffer` 有对应参数控制的策略，需要把内存中的数据更新到 `redo log` 的 file 当中，也就是磁盘中的文件里。这么安排的道理就是日志文件优先——先写它，然后才把内存中的数据刷盘到真正磁盘中的数据页。

这个过程中还要处理一个文件：`binlog` 日志文件，也就是二进制文件。它是为后面讲主从复制准备的——主机把数据记录到 binlog 之后，从机拿到这个文件，就能知道主机到底做了哪些操作，从而实现主从数据的同步。

#### undo 版本链的构建

详细过程我们拿具体例子来说，这里要用到前面讲数据页结构时提到的行格式。行格式里有三个隐藏的列——当时讲 InnoDB 数据存储结构、讲行格式的时候说过，一条真实的记录其实还会带三个隐藏列，当时说放到后面讲事务日志时再展开，其实就是现在要讲的内容，前后就搭到一起了。

这三个隐藏列分别是 `row_id`、`transaction_id` 和 `roll_pointer`，也就是回滚指针。

`row_id` 前面提过：如果表里没有显式定义主键，系统会自动选择一个非空的唯一索引；如果这个也没有，InnoDB 会自动添加一个叫 `row_id` 的隐藏列作为主键。因为索引即数据，底层要存储数据就一定要有主键这个角色。

`transaction_id` 是事务 ID，相当于记录这条记录目前是哪一个事务正在操作它。事务提交了，数据就更新完成；事务没有提交、发生了回滚，那针对这条数据、针对这个事务 ID，我们就要对它进行修改。

`roll_pointer` 是回滚指针。行记录里记的是当前内存中修改以后的数据，那是真实的；可你要回滚的话，就得拿着这条数据去跟 update 之前的行为对照，看原来旧的是多少，这时候就要关联到 undo log。这个变量记录的就是关联到 undo log 的位置。

现在看例子。在 `begin` 里启动一个事务，添加一条记录。

```text
行记录（最新状态永远在行里）
┌──────────────────────────────────────────────┐
│ delete mark = 0                              │
│ 事务 ID                     = 当前事务        │
│ roll_pointer ────────────────────────┐       │
│ id = 1                               │       │
│ name = Tom                            │       │
└──────────────────────────────────────┼───────┘
                                       ▼
                            undo log 编号 0（插入之前的行为）
```

读图说明：插入一条 Tom 记录时 `delete mark` 是 0（当前没有被删除），事务 ID 记的是当前事务，回滚指针指向这条记录添加之前的那个行为。

在这个基础上再执行一个 `update`，把 `id=1` 这条记录的名字从 Tom 改成 Rose。这时候注意看：刚才生成的 undo log 编号是 0；现在新生成的 undo log 被这条记录的回滚指针所指，而这个新生成的 undo log 又去指向旧的 undo log。

```text
行记录（name = Rose）
   │ roll_pointer
   ▼
undo log 编号 1  ──►  undo log 编号 0
```

读图说明：行记录里永远保存最新的数据，回滚指针指向最近生成的那条 undo log，而新的 undo log 再指向更旧的 undo log，如此串成一条链。

> **提示**：行记录本身永远记录最新的数据，这一点不会变；历史值一律留在 undo 日志里，靠回滚指针一层层串起来。

再看一个 `update`：把 `id=1` 这条数据改成 `id=2`。底层操作并不是简单把数据里的 1 改成 2，而是把原来的那条记录标记为一个已删除的状态，然后重新生成一条记录，`id` 是 2、名字还是 Rose。

同时在原有记录上也会产生一条 undo log，编号就是 2（它是最新的，所以指向关系是这样的）。它里边记录的是什么？相当于 `delete mark` 从 0 变成了 1 这个过程，另外还记录了一条新记录的相关信息——相当于你之前 `id` 是 1，现在改成 2 了。整个几个操作的过程当中生成的 undo log 就是这样一条链。

#### 回滚的执行顺序

接下来看 undo log 是如何回滚的。假设我们执行了三条 DML 操作，然后做了一个 `rollback`。

回滚是从最近的一条开始，沿着版本链往回走：

```text
rollback
   │ ① 执行 undo log 编号 3：删除 id = 2 那条记录
   │ ② 执行 undo log 编号 2：delete mark 由 1 改回 0，让 id = 1 的记录回来
   │ ③ 执行 undo log 编号 1：把 Rose 改回 Tom
   │ ④ 再往前：insert 对应的两个行为也一并没了
   ▼
回到事务开始之前的状态
```

读图说明：回滚按 undo 版本链由新到旧逐条反向执行，先撤销最近的一次修改，再依次向前，直到把事务里的所有修改都抹平。

具体来说：首先通过编号为 3 的这条 undo log，把 `id=2` 的数据删掉，删掉以后就回滚到上一个场景；在这个场景当中执行编号为 2 的 undo log，把 `delete mark` 从 1 改成 0，这条记录不就又回来了——相当于把最近的那个 `update` 回滚了回去；再接下来执行的就是把 Rose 改成 Tom；然后再往前，相当于 `insert` 那两个行为也没有了。

#### undo log 的删除时机

生成的 undo log 怎么删除，其实前面已经讲过了，这里把两类合起来再说一遍。

针对 `insert` 行为：因为对其他事务不可见，所以只要数据回滚了或者提交了，事务本身就已经结束了——事务要么是已提交状态（`commit`），要么是终止状态（相当于 `rollback`）。总之只要事务结束，记录的这些 `insert` undo log 就没有用了，可以直接删除。

针对 `update`：因为它涉及多版本并发的访问，所以还需要留一下，先放到 undo log 链表当中，等事后的 purge 清除线程来决定要不要删。

purge 线程的作用有两个，算是补充，了解一下就行：一是负责清理 undo 页，刚才提到了；二是清除数据页里带有 `deleted bit` 标识的数据行。这是什么意思？真正要删除一条数据时，其实只是把那个 0 标记成 1，并没有真正删掉；如果你真想把这个空间腾出来，就要用到 purge 线程。

### 小结

最后的收束还是用讲 redo log 时用的那张图，通过这张图把 redo 和 undo 各自的角色看清楚就可以了。有一个点必须明确：**undo 和 redo 不是一对逆过程**，二者的联系与区别一开始就强调过，你们再去熟悉一下。
