## 49-数据库的创建、修改与删除
> 对应分集：P49 | 原始标题：《49-数据库的创建、修改与删除》

从基本的查询操作到对数据本身的结构化管理，是数据库学习过程中的一道重要分水岭。在前面的学习中，我们针对现成的 `employees`、`departments` 等经典官方样本数据，完成了包括单表查询、多表连接、分组聚合以及复杂子查询在内的全套 DML 查询逻辑。很多同学学到这里会觉得查询的套路千变万化，确实有一定难度；但无论查询多么复杂，它都建立在一个前提之上：这些表和数据早就躺在数据库里了。

巧妇难为无米之炊。如果在实际生产开发中，系统连一张数据表都没有，甚至连承载业务的数据库容器都尚未建立，任何查询逻辑都无从谈起。从本讲开始，我们将正式进入 SQL 体系中负责“立骨架”的核心领域——数据定义语言（DDL，Data Definition Language），全面系统地掌握数据库与数据表的创建、运维、修改与生命周期管理。

---

### 结构生命周期与数据存储层次

#### SQL 核心语法分类与 DDL 的工程定位

在建立数据库之前，必须对 SQL 语句的整体分类框架有全局认知。在关系型数据库规范中，SQL 语言根据其功能定位被划分为三大核心类别：

```text
+-----------------------------------------------------------------------+
|                              SQL 语言分类                              |
+-----------------------------------------------------------------------+
        |                                   |                       |
        v                                   v                       v
+-------------------+             +-------------------+   +-------------------+
| DDL (数据定义语言)  |             | DML (数据操作语言)  |   | DCL (数据控制语言)  |
+-------------------+             +-------------------+   +-------------------+
| * CREATE (创建)   |             | * INSERT (插入)   |   | * COMMIT (提交)   |
| * ALTER  (修改)   |             | * DELETE (删除)   |   | * ROLLBACK(回滚)  |
| * DROP   (删除)   |             | * UPDATE (修改)   |   | * SAVEPOINT(保存点)|
| * RENAME (重命名) |             | * SELECT (查询)   |   | * GRANT  (赋权)   |
| * TRUNCATE(清空)  |             +-------------------+   | * REVOKE (撤权)   |
+-------------------+                                     +-------------------+
```

*图 1.1：SQL 语句核心分类及关键指令分布拓扑图*

- **DML（Data Manipulation Language，数据操作语言）**：负责表中数据的读写与流转，包含增（`INSERT`）、删（`DELETE`）、改（`UPDATE`）、查（`SELECT`）。此前我们完成的查询操作就是 DML 中最庞大、最灵活的分支；而增删改操作，必须等到表结构建立完成后才能施展。
- **DDL（Data Definition Language，数据定义语言）**：负责数据库内部逻辑对象（包括数据库、数据表、视图、索引等）的定义与属性变更。核心关键字涵盖 `CREATE`、`ALTER`、`DROP`、`RENAME` 以及用于高速清空表数据的 `TRUNCATE`。
- **DCL（Data Control Language，数据控制语言）**：负责事务保障与权限安全管控。其中 `COMMIT`（事务提交）与 `ROLLBACK`（事务回滚）负责划定事务边界；而 `GRANT`（赋予权限）与 `REVOKE`（回收权限）则由 DBA 或运维人员用于严格限制各系统账号的操作边界。

在工程推进的逻辑链条上，必须严格遵循“先骨架后内容”的因果时序：先执行 DDL 创建库和表结构，再执行 DML 写入业务数据，最后结合业务需求执行精细化查询与维护。

#### 数据存储全流程与系统分层架构

所谓“皮之不存，毛将焉附”。在关系型数据库中，数据记录是“毛”，而数据表与数据库就是那张“皮”。如果在物理机或云端实例上要落地一条业务数据，它在系统逻辑架构中由外而内的穿透路径如下：

```text
+-----------------------------------------------------------------+
| 数据库服务器 (Database Server，底层主机或容器实例，负责端口监听)   |
|  +-----------------------------------------------------------+  |
|  | 数据库管理系统 (DBMS，如 MySQL 8.0 服务进程 mysqld)          |  |
|  |  +-----------------------------------------------------+  |  |
|  |  | 数据库 (Database / Schema，逻辑业务容器，如 mytest1)     |  |  |
|  |  |  +-----------------------------------------------+  |  |  |
|  |  |  | 数据表 (Table，由行记录与列字段构成的二维关系矩阵)   |  |  |  |
|  |  |  |  +-----------------------------------------+  |  |  |  |
|  |  |  |  | 字段/列 (Column) 与 业务记录行 (Row)       |  |  |  |  |
|  |  |  |  +-----------------------------------------+  |  |  |  |
|  |  |  +-----------------------------------------------+  |  |  |
|  |  +-----------------------------------------------------+  |  |
|  +-----------------------------------------------------------+  |
+-----------------------------------------------------------------+
```

*图 1.2：MySQL 系统架构从底层服务到业务记录的分层包含关系*

一条业务数据的物理存储必须严格经历以下阶段：
1. **启动并连接数据库服务器**：通过客户端（命令行、Navicat、DataGrip 等）建立与运行中的 DBMS 进程的长连接；
2. **创建独立的业务数据库**：确定业务边界，为新系统划分独立的 Schema 逻辑隔离区；
3. **确认实体字段并创建数据表**：分析业务实体需求，定义列名、数据类型、长度规格与约束机制，固化数据表结构；
4. **写入持久化数据**：通过 DML 的 `INSERT` 语句将真实的数据行写入底层数据页。

### 数据库的创建（CREATE DATABASE）

在 MySQL 中创建数据库，表面上看只是一条指令，但若深入到字符集编码、系统默认继承以及多脚本幂等性执行场景，其中有许多必须严格遵循的工程规范。

#### 默认字符集创建方式

创建数据库最简练的语法形式如下：

```sql
CREATE DATABASE mytest1;
```

> **提示**：创建数据库属于实例级别的管理操作，执行账号必须具备相应的权限。在本地开发与教学演示中，我们通常使用具有超级管理员身份的 `root` 用户登录。`root` 是 MySQL 的根用户，拥有最高的全局权限；若在企业生产环境中由普通业务账号执行此命令，且该账号未被授予 `CREATE` 权限，系统将直接拒绝并抛出 `Access denied` 错误。

当使用这种极简形式创建数据库时，数据库的字符集编码（Character Set）和校对规则（Collation）并没有在语句中显式声明。此时，该数据库会自动继承当前 MySQL 数据库服务器层级所配置的默认字符集。

#### 显式指定字符集的创建方式

在多语言交互或对汉字存储有特殊要求的场景下，强烈反对依赖系统隐式默认值，而应当在建库时显式指明字符集：

```sql
CREATE DATABASE mytest2 
CHARACTER SET 'gbk';
```

这里的关键字为 `CHARACTER SET`（或缩写为 `CHARSET`），紧随其后指定合法的字符编码方案，例如支持简体中文早期编码规范的 `gbk`，或是具备全球全字符集支持能力的通用编码。

要探究字符集继承机制的根源，可以通过系统变量查询指令，查看当前服务端各层级的默认配置：

```sql
SHOW VARIABLES LIKE 'character_%';
```

在执行输出中，重点关注以下两个核心变量：
- `character_set_server`：数据库服务器级别的默认字符集。
- `character_set_database`：当前默认数据库使用的字符集。

在 MySQL 8.0 及其后续版本中，官方默认的字符集已经统一升级为 `utf8mb4`，校对规则对应为 `utf8mb4_0900_ai_ci`；而在企业级存量系统依然大量服役的 MySQL 5.7 环境中，官方默认字符集却是西欧语言的 `latin1`（ISO-8859-1）。如果在 5.7 环境中建库不显式指明字符集，且管理员没有预先修改 `my.cnf` 配置文件，该数据库就会继承 `latin1`，后续插入中文时将直接引发乱码或报字符集越界错误。

#### 幂等性创建（IF NOT EXISTS）与版本陷阱

如果在一个已经存在 `mytest2` 数据库的实例上，再次执行相同的创建语句：

```sql
-- 若 mytest2 已经存在，重复执行将触发硬性报错：
-- ERROR 1007 (HY000): Can't create database 'mytest2'; database exists
CREATE DATABASE mytest2;
```

在自动化脚本运行、CI/CD 持续集成发布或数据库初始化 SQL 批量刷库时，一旦遇到这种抛错，整段批处理脚本会被迫中断退出。为了保障脚本执行的“幂等性”（即多次执行与一次执行产生相同的结果且不引发系统异常），DDL 提供了安全判断分支语法：

```sql
CREATE DATABASE IF NOT EXISTS mytest2 
CHARACTER SET 'utf8';
```

为了彻底厘清 `IF NOT EXISTS` 的内部判定逻辑，我们进行一组严格的对照实验：
假定 `mytest2` 在最初创建时已经被显式指定为 `gbk` 编码。此时执行上述带有 `IF NOT EXISTS` 且将字符集声明为 `utf8` 的语句，控制台会返回 `Query OK, 1 warning`，脚本顺利通过且不报错。那么，`mytest2` 的字符集会被这次执行强行覆盖改写成 `utf8` 吗？

> **结论**：**不会被覆盖**。`IF NOT EXISTS` 的逻辑是：当 DBMS 检测到底层已经存在名为 `mytest2` 的 Schema 实体时，将完全跳过该数据库的创建逻辑，也不会对其现有的属性做任何更新，仅仅是抑制住了本该抛出的 1007 错误，静默结束执行。

由此可总结出生产环境中最推荐采用的建库黄金模板：

```sql
-- 工程推荐规范：兼顾防重报错与跨版本编码统一
CREATE DATABASE IF NOT EXISTS mytest3 
CHARACTER SET 'utf8mb4';
```

> **注意**：由于企业更换底层数据库版本的动力极其缓慢（数据迁移和存储引擎升级成本远高于业务代码重构），当前很多企业的核心生产库依然运行在 MySQL 5.7 上。因此，无论开发环境使用的是 8.0 还是 5.7，在编写建库 DDL 时务必养成显式指定 `IF NOT EXISTS` 以及明确指定 `CHARACTER SET 'utf8mb4'` 的严谨习惯。

#### 查看数据库创建结构定义

要验证一个数据库在物理层面上最终生效的字符集与建库配置，可以使用元数据检视命令：

```sql
SHOW CREATE DATABASE mytest1;
SHOW CREATE DATABASE mytest2;
```

如果在标准的终端命令行中执行，由于输出的列宽度限制，文本可能会被折叠断行，影响阅读体验。此时可以利用 MySQL 终端专用的 `\G` 行列转置结束符替代分号：

```sql
SHOW CREATE DATABASE mytest1\G
```

输出示例结果如下：

```text
*************************** 1. row ***************************
       Database: mytest1
Create Database: CREATE DATABASE `mytest1` /*!40100 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci */ /*!80016 DEFAULT ENCRYPTION='N' */
1 row in set (0.00 sec)
```

通过这一检视方式，可以准确地观察到底层所赋予的默认字符集（`DEFAULT CHARACTER SET`）、校对规则（`COLLATE`）以及加密属性。

### 数据库的日常管理与状态查询

在复杂的企业级实例中，通常会存在成百上千个数据库容器。精准掌握实例中的库状态、作用域切换与表结构检视，是日常运维与数据操作的基本功。

#### 库列表与连接状态查看

查看当前 MySQL 连接实例中所有可访问的数据库列表：

```sql
SHOW DATABASES;
```

执行后将输出一张包含当前用户具有访问权限的所有数据库清单。新装系统通常自带 `information_schema`、`performance_schema`、`sys` 和核心系统库 `mysql`。

#### 作用域切换与当前所属库查询

如果我们在没有明确选定任何数据库的前提下，直接执行针对数据表的查询操作：

```sql
SELECT * FROM employees;
-- 若当前处于未选库状态或处在没有 employees 表的库中，将抛出：
-- ERROR 1046 (3D000): No database selected
-- 或 ERROR 1146 (42S02): Table 'mytest1.employees' doesn't exist
```

要让后续所有的表级 DDL 和 DML 指令在特定的业务库上下文中运行，必须通过 `USE` 指令完成工作空间的切换：

```sql
-- 切换当前会话上下文到指定的数据库
USE mytest2;
```

切换完成后，如果后续在长脚本中需要动态校验当前会话到底驻留在哪个数据库环境中，可以调用 MySQL 内置系统函数 `DATABASE()` 进行求值：

```sql
SELECT DATABASE();
-- 或者使用遵循通用 SQL 规范的形式引入 DUAL 伪表：
SELECT DATABASE() FROM DUAL;
```

若当前会话尚未执行过任何 `USE` 指令，该函数将返回 `NULL`；若已切换，则返回当前活跃的数据库名称。

#### 数据表跨库检视与 GUI 工具本质

查看当前已激活数据库中包含的所有数据表：

```sql
SHOW TABLES;
```

如果我们需要快速检视其他数据库中有哪些表，但**又不想打断或改变当前会话所驻留的上下文**，无需反复来回执行 `USE`，可以直接使用带 `FROM` 从句的高阶语法：

```sql
-- 查看系统核心库 mysql 中包含的数据表，同时保持当前会话所在库不变
SHOW TABLES FROM mysql;
```

> **提示**：我们在使用 Navicat、SQLyog 或 DataGrip 这类可视化客户端工具时，鼠标在左侧对象树中点击展开某一个数据库节点，或者在右侧主界面刷新列表，图形界面的底层本质上并没有任何黑魔法，全是在后台自动向服务端投递了 `SHOW DATABASES`、`USE 数据库名`、`SHOW TABLES` 以及 `SHOW CREATE DATABASE` 等标准的 SQL 交互指令，最终将返回的结果集格式化渲染成树状图和图标而已。

### 数据库的修改与命名边界（ALTER DATABASE）

#### 字符集的变更语法与适用阶段

很多同学会问：数据库已经创建好了，后续还能修改吗？
语法上，MySQL 提供了 `ALTER DATABASE` 指令。但必须明确建立一个工程安全意识：**在真实的生产开发环境中，数据库层面的修改极为罕见**。因为一旦一个库投入运行，其下挂载着几十上百张表，表中沉淀了千万级甚至过亿的数据量，贸然改动库级配置往往会引发级联风险。

通常允许执行修改的唯一安全窗口期，是在**数据库刚刚通过脚本创建完成，表尚未建立，且突然发现字符集或校对规则声明错误**的初期极短时间内。

修改数据库字符集的标准语法如下：

```sql
-- 将 mytest2 的字符集变更为 utf8mb4
ALTER DATABASE mytest2 
CHARACTER SET 'utf8mb4';
```

注意在此语法中，严禁添加 `IF NOT EXISTS` 逻辑（因为 `ALTER` 的对象必须是一个已经存在的实体）。修改完成后，再次通过 `SHOW CREATE DATABASE mytest2;` 验证，可以看到该库的字符集已成功被更新。

#### 数据库重命名的底层真相与生产禁区

在日常管理中，经常会有初学者提出疑问：“既然可以 `ALTER DATABASE` 改字符集，那我能不能直接给数据库改一个名字？”

> **易错点**：**在 MySQL 中，绝对不要尝试直接修改数据库的名称**。
> 
> 在 MySQL 的早期历史中（5.1.7 版本），官方曾尝试引入过 `RENAME DATABASE 旧库名 TO 新库名;` 的指令。但由于数据库在物理磁盘上对应着整个存储目录，且内部紧密交织着存储引擎文件（.ibd）、表定义元数据、外键依赖、触发器及权限表的级联映射，直接物理改名在测试阶段频繁导致严重的数据损坏与丢失。仅仅过了几个补丁版本（5.1.23），官方就紧急且永久地废弃了该指令。

有时大家会发现，某些第三方可视化管理工具上似乎右键点击数据库就有一个“重命名”菜单。必须看清其底层的残酷真相：这类工具并非执行了原子级的改名操作，而是由程序在后台自动执行了一组非常繁重的高危流程：
1. `CREATE DATABASE` 创建一个全新的目标数据库；
2. 逐一提取原数据库中所有表的 DDL 结构并在新库中重建；
3. 将原数据库中所有表的数据批量导出并导入新库；
4. 数据全部迁移校验无误后，执行 `DROP DATABASE` 将旧数据库彻底销毁。

这种操作在数据量极大的生产环境中，不仅耗时漫长、严重锁表，而且一旦网络中断或发生异常，将造成毁灭性的灾难。

因此在现代软件工程规范中，所有数据库和数据表的命名、字符集选型、主从同步规则，必须在项目前期的**架构需求分析与数据库设计说明书**中白纸黑字严格敲定并组织评审。严禁在生产运行时产生“改个库名”的不切实际想法。

### 数据库的删除与容灾红线（DROP DATABASE）

#### 基础删除与防错语法（IF EXISTS）

当某套测试系统废弃或需要重置初始化环境时，可以使用 DDL 的 `DROP` 指令销毁数据库对象。

直接删除语法：

```sql
DROP DATABASE mytest1;
```

如果该数据库在实例中存在，底层对应的目录及内部所有的数据表、视图、存储过程将被物理销毁。然而，如果此时再次执行相同的命令，系统会因找不到该库而抛出硬性错误：

```sql
-- 库不存在时继续执行直接删除，抛出错误：
-- ERROR 1008 (HY000): Can't drop database 'mytest1'; database doesn't exist
DROP DATABASE mytest1;
```

为了确保清理脚本能够平滑无阻地反复重跑，同样必须引入条件判定子句：

```sql
-- 工程推荐写法：如果存在则删除，不存在则安全跳过（静默结束不报错）
DROP DATABASE IF EXISTS mytest1;
DROP DATABASE IF EXISTS mytest2;
```

加入 `IF EXISTS` 后，若目标数据库存在则成功执行删除；若目标数据库本身不存在，系统仅会给出一个静默的警告（Warning），SQL 会话判定为 `Query OK`，整体批处理链路不会因此崩塌。

#### DDL 事务不可逆性与系统库保护红线

在执行数据库或数据表的删除操作时，必须在内心深处刻下两条生死红线：

第一条红线：**DDL 操作默认不参与事务回滚，一旦执行即刻生效，无法通过 `ROLLBACK` 撤销**。
在后续讲解事务控制语言（DCL）时我们会进一步剖析，DML 操作（如 `DELETE FROM`）在未提交前是可以通过执行 `ROLLBACK` 追回数据的；而包括 `DROP DATABASE`、`DROP TABLE`、`TRUNCATE TABLE` 在内的所有 DDL 操作，在 MySQL 引擎内部都会隐式触发一次事务的强制提交（Implicit Commit）。这意味着执行删除的那一刻，元数据和底层数据结构就已经完成了物理抹除。网络上广为流传的“从删库到跑路”的调侃，绝非空穴来风，没有外部专业且完备的物理冷热备份，任何线上删库都是无法逆转的灾难事故。

第二条红线：**严禁触碰任何 MySQL 实例自带的核心系统库**。

```text
+-----------------------------------------------------------------+
|                        MySQL 核心内置系统库                      |
+-----------------------------------------------------------------+
| 1. mysql                 | 存储核心元数据、用户账号、权限表、密码与审计   |
| 2. information_schema    | ANSI 标准的数据字典视图，存放表、列、索引定义  |
| 3. performance_schema    | 实例底层运行时资源监控、锁、内存与性能监控统计 |
| 4. sys                   | 将 performance_schema 复杂度封装的高级诊断视图 |
+-----------------------------------------------------------------+
```

绝不能因为在命令行打出 `SHOW DATABASES;` 后，看到 `mysql` 或 `sys` 库名觉得碍眼，就随手敲上一句 `DROP DATABASE mysql;`。一旦核心系统库被销毁，MySQL 进程将直接丧失身份校验机制与元数据寻址能力，轻则报错拒绝服务，重则无法重启直接瘫痪。所有的建库、改库、删库练习与测试，必须且只能限制在自己亲手建立的业务测试库（如 `mytest_db`）范围内进行。

## 50-常见的数据类型_创建表的两种方式
> 对应分集：P50 | 原始标题：《50-常见的数据类型_创建表的两种方式》

在完成数据库这一层级容器的搭建与管理之后，我们顺理成章地迈入整个数据存储链路的核心阵地——数据表的创建与管理。在前面几章中，我们反复针对现成的数据表做各式各样的复杂查询，但真正的业务落地开发，第一步永远是亲手将数据表建立起来。

创建数据表的 SQL 关键字同样是 `CREATE`，即 `CREATE TABLE`。但与创建数据库时只需给出一个库名不同，数据表是一个由行和列构成的严格二维矩阵。要建表，就必须明确这张表里到底包含哪些列（在数据库领域我们统称为“字段”，类比于高级编程语言中的变量），而每一个字段都必须被赋予一个确定的数据类型。如果脱离了数据类型，表结构就像失去了物理骨架，根本无法在磁盘上分配存储空间。

#### 字段类型选型对业务的两大决定性影响

在实际企业级开发中，字段类型的敲定绝非随性而为，它直接关乎以下两大核心生命线：
1. **数据存储的物理精度与业务合规**：
   特别是涉及到资金、财务或高精度计量的场景，不同类型的底层表示机制截然不同。例如 `FLOAT` 和 `DOUBLE` 属于遵循 IEEE 754 标准的二进制浮点数，在进行四则运算时存在天然的浮点舍入误差。像阿里巴巴《Java开发手册》等国内一线大厂的数据库开发规范中，有硬性强制规定：**任何涉及金钱、价格、账户余额的字段，严禁使用 FLOAT 和 DOUBLE，必须强制使用 DECIMAL 定点数类型**。
2. **磁盘占用空间与内存查询 I/O 吞吐效率**：
   如果某个字段存储的业务数据数值极小（例如用户状态仅有 0、1、2），却草率地选用了 8 字节的 `BIGINT`；或者原本仅有 10 个字符的编号，却随意分配了冗长的大字段空间，单行记录的物理体积就会被无意义地撑大。当单表数据量突破几十万甚至上百万级别时，数据页能容纳的行数大幅减少。在执行检索时，MySQL 必须从磁盘向内存中加载远超实际需求的数据页，导致磁盘 I/O 次数急剧攀升，查询性能成倍恶化。

#### 现阶段建表必备的四大基石类型

为了在不陷入细枝末节的前提下快速掌握建表技术，我们圈定并锁定以下四种最常用的代表性数据类型：

- **整数类型：`INT`**
  占用 4 个字节（32 位二进制）。在未显式声明 `UNSIGNED`（无符号）属性时，默认属于有符号整数，取值范围为：
  $$-2^{31} \sim 2^{31} - 1 \quad (-2,147,483,648 \sim 2,147,483,647)$$
  日常业务主键 ID、计数器、部门编号等无特殊大数值要求的场景，直接使用 `INT` 即可满足。
- **小数/数值类型：`DOUBLE` 与 `DECIMAL`**
  对于带小数点的浮点数值（如员工薪资 `salary`），为了贴合大家在通用编程语言中的直观认知，本讲实操中暂时采用 `DOUBLE`。但在工程架构意识上必须牢记：定点数 `DECIMAL(M, D)` 拥有绝对精确的十进制计算能力，是资金财务核算场景的唯一工业标准。
- **日期时间类型：`DATE`**
  专用于记录纯粹的“年-月-日”（格式如 `2026-09-14`），不携带时分秒细节。若需要记录包含时分秒的完整日志或打卡流水，后续可拓展为 `DATETIME` 或 `TIMESTAMP`。
- **变长字符串类型：`VARCHAR(M)`**
  用于存储可变长度的文本字符串。

> **易错点**：使用 `VARCHAR` 时，**必须显式在括号中声明其最大字符长度 $M$**（例如 `VARCHAR(15)`）。这里的 15 在 MySQL 中代表该字段最多容纳 15 个字符（无论中文字符还是英文字母）。如果不传长度参数，SQL 解析器将直接报语法错误而拒绝执行。

### 方式一：“白手起家”从零构建数据表

创建数据表从方法论上可以分为截然不同的两大流派。第一种方式，是从空白状态开始，逐行定义每一个字段名、数据类型及其规格。在教学理解中，这种方式就像是“富一代”或者“创一代”通过白手起家，一点一滴构筑起整张数据表的结构。

#### 基础建表语法与幂等性保障

标准的基础建表语法结构如下：

```sql
CREATE TABLE [IF NOT EXISTS] 表名 (
    字段名1 数据类型,
    字段名2 数据类型,
    ...
    字段名n 数据类型
);
```

我们切换至工作数据库 `atguigudb`，并在建表前检视该数据库本身的编码属性：

```sql
USE atguigudb;

-- 检视当前数据库创建语句及字符集
SHOW CREATE DATABASE atguigudb;
```

接下来，我们构建一张名为 `myemp1` 的新员工数据表。为了防止在自动化脚本重跑时因同名表已存在而报 `Table 'myemp1' already exists` 的硬性异常，同样应养成使用 `IF NOT EXISTS` 的防御性编程习惯：

```sql
CREATE TABLE IF NOT EXISTS myemp1 (
    id INT,
    emp_name VARCHAR(15),
    hire_date DATE
);
```

> **提示**：执行 `CREATE TABLE` 操作同样需要当前数据库账号具备相应的 DDL 操作权限。在当前实验环境中，我们统一使用拥有全局最高特权的 `root` 超级管理员账号，因此天然具备建表权限。在企业级运维体系中，非 DBA 开发账号的建表权限通常会被严格审查与收拢。

执行完毕后，执行查询验证表内数据：

```sql
SELECT * FROM myemp1;
-- 输出结果：Empty set (0.00 sec)
```

因为这是纯粹白手起家定义出来的一张全新空表，底层仅建立了元数据框架，并未灌入任何业务记录。

#### 表结构的两种检视方法

新建数据表后，必须对其字段规格与物理定义进行反向核验。MySQL 提供了两种维度的检视方式：

##### 方法一：二维矩阵视图（DESCRIBE / DESC）

```sql
DESC myemp1;
```

输出示例表格如下：

| Field | Type | Null | Key | Default | Extra |
| :--- | :--- | :--- | :--- | :--- | :--- |
| id | int | YES | | NULL | |
| emp_name | varchar(15) | YES | | NULL | |
| hire_date | date | YES | | NULL | |

通过该矩阵，可以清晰看到各列名、已生效的数据类型与长度限制、是否允许为空（`YES`）、是否包含主键或外键索引（`Key`）以及默认值（`Default`）。

##### 方法二：完整 DDL 源码视图（SHOW CREATE TABLE）

```sql
SHOW CREATE TABLE myemp1\G
```

输出元数据如下：

```text
*************************** 1. row ***************************
       Table: myemp1
Create Table: CREATE TABLE `myemp1` (
  `id` int DEFAULT NULL,
  `emp_name` varchar(15) DEFAULT NULL,
  `hire_date` date DEFAULT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb3
1 row in set (0.00 sec)
```

通过这一源码级视图，可以挖掘出许多隐式生效的底层事实：
1. **默认值补全**：在未声明 `NOT NULL` 的情况下，系统自动为每个列追加了 `DEFAULT NULL`；
2. **存储引擎指定**：当前数据表默认搭载了 MySQL 核心的事务型存储引擎 `ENGINE=InnoDB`；
3. **字符集继承机制**：该表末尾标注了 `DEFAULT CHARSET=utf8mb3`。为什么是 `utf8mb3` 而不是 MySQL 8.0 默认的 `utf8mb4` 呢？

> **原理剖析**：如果我们在创建数据表时没有使用 `CHARACTER SET` 显式声明表级字符集，**数据表将强制继承其所在数据库的字符集配置**。我们的示例数据库 `atguigudb` 最早是从 MySQL 5.7 环境下导出的备份脚本，在 5.7 中通用汉字编码为使用 3 字节表示一个字符的 `utf8`（在 8.0 内部被规范命名为 `utf8mb3`）。因此，当前数据库的底层编码为 `utf8mb3`，新创建的 `myemp1` 自然顺理成章地继承了该配置。

### 方式二：基于现有表查询结果快速派生建表（CTAS）

与从零定义字段的“白手起家”相对，第二种方式被称为“富二代式”建表（官方技术规范称为 CTAS，即 `CREATE TABLE ... AS SELECT`）。在这种模式下，系统依托于已经存在的数据表资产，将一条 `SELECT` 查询语句的二维结果集直接固化为一张全新的物理数据表。

这也是为什么在整体课程体系中，必须先花大量篇幅把 `SELECT` 查询讲透的原因。一旦吃透了查询，派生建表的能力就会呈指数级放大。

```text
+-----------------------+           +-----------------------+
|  源数据表 (employees)  |           |   目标新表 (myemp2)   |
| +-------------------+ |           | +-------------------+ |
| | employee_id (int) | |           | | employee_id (int) | |
| | last_name (v25)   | | =========>| | last_name (v25)   | |
| | salary (d8,2)     | |   CTAS    | | salary (d8,2)     | |
| | ... (其他字段)     | |           +---------------------+ |
| +-------------------+ |           | 物理灌入 107 条数据  | |
| | 107 条原始数据行  | |           +-----------------------+
+-----------------------+
```

*图 3.1：CTAS 模式下表结构推导与数据物理镜像复制示意图*

#### 结构与数据的同步固化

我们编写一条基础的派生建表语句：

```sql
CREATE TABLE myemp2
AS
SELECT employee_id, last_name, salary
FROM employees;
```

执行后检视新表结构：

```sql
DESC myemp2;
```

输出对比可以发现：`myemp2` 中的 `employee_id` 自动推导为 `int`，`last_name` 自动继承了源表的 `varchar(25)`，而 `salary` 自动继承为 `double(8,2)`。
更关键的是，当我们执行全表检索时：

```sql
SELECT * FROM myemp2;
```

控制台完整输出了 107 条记录！这表明 CTAS 语法完成了一次**原子操作：根据查询输出的列投影自动推导新表的数据类型与长度，并将结果集中每一行数据物理插入到新表中**。

> **结论**：**CTAS 是纯粹的物理副本拷贝**。新表 `myemp2` 生成之后，与源表 `employees` 在物理存储上彻底解耦。后续无论对 `myemp2` 执行任何增、删、改操作，源表中的数据都不会受到丝毫波及。

#### 列别名重命名机制与多表复杂查询融入

在利用查询构建新表时，新表的字段名并不强制与源表保持一致。**在 `SELECT` 子句中赋予列的别名（Alias），将直接作为新数据表的持久化物理字段名**。

此外，查询子句完全支持复杂的连接查询与聚合分析。如下例所示，我们通过内连接（`JOIN`）抽取员工工号、员工姓名及所属部门名称，并在建表时重命名列：

```sql
CREATE TABLE myemp3
AS
SELECT 
    e.employee_id AS emp_id,
    e.last_name AS emp_name,
    d.department_name
FROM employees e 
JOIN departments d
  ON e.department_id = d.department_id;
```

执行后检视 `myemp3` 的表结构：

```sql
DESC myemp3;
```

输出结果显示，新表的字段名精确呈现为 `emp_id`、`emp_name` 和 `department_name`，完美继承了别名定义。

### 表结构深度复制与空表模板提取实战

为了检验对 CTAS 机制的综合运用能力，我们来剖析两组具有极高工程实用价值的对比案例。

#### 案例一：完全复制目标表的结构与全部数据

要求创建一张名为 `employees_copy` 的新表，完全复刻 `employees` 表的所有列定义，并导入全部 107 条在职数据：

```sql
CREATE TABLE employees_copy
AS
SELECT * FROM employees;
```

此时执行 `SELECT * FROM employees_copy;`，整张表的字段矩阵与 107 行数据均被完整克隆。

#### 案例二：仅提取表结构定义，严禁带入任何数据（空表模板）

在生产运维中，经常需要为历史归档、分库分表或压测准备一张与核心业务表结构完全一致、但内部空空如也的“白板表”。

既然 CTAS 的数据导入行为完全取决于 `SELECT` 查询返回的结果集行数，那么只要让查询结果集的记录数变为 0，新表创建出来自然就是一张纯粹的空表。

初学者可能会尝试使用业务边界值进行过滤，例如：

```sql
-- 尝试写法：寻找一个业务上不存在的部门编号
CREATE TABLE employees_blank
AS
SELECT * FROM employees
WHERE department_id > 10000;
```

这种写法虽然在当前数据集下能够碰巧达成目标，但在严谨的工程标准中存在巨大隐患：开发人员无法在理论上保证未来业务不会新增大于 10000 的部门编号；一旦源数据发生偏移，该脚本就会漏进脏数据。

最顶级且规范的解法，是向 SQL 解析器提供一个**在逻辑上恒为假（False）的断言条件**：

```sql
-- 工业标准写法：利用恒假逻辑实现零数据行穿透
CREATE TABLE employees_blank
AS
SELECT * FROM employees
WHERE 1 = 2;
```

##### 恒假条件 `WHERE 1 = 2` 的运行机理

很多同学第一次见到 `WHERE 1 = 2` 会感到非常新奇。这里可以用一个生动的文化典故做类比：在古典诗歌（如《还珠格格》歌词所引用的《乐府诗集·上邪》）中有句经典名句：“山无棱，天地合，乃敢与君绝”。夏天落雪、山峦化为平地、天与地合并，这些自然规律在现实中是绝不可能发生的物理现象；古人正是借助这种永不可能成立的前提，委婉含蓄地表达“我永不与你分离”的坚决誓言。

在 SQL 引擎的执行管道中，`WHERE 1 = 2` 扮演了完全相同的角色。当存储引擎扫描记录时，每一行数据在计算 `1 = 2` 这个布尔表达式时，得到的永远都是数值 0（即 `FALSE`）。因此，所有行记录在第一道过滤网处被全部拦截并丢弃。最终，查询引擎向 DDL 管道输送了一个“具备完整的二维字段元数据头，但数据行为 0”的结果集。

```sql
-- 验证查询
SELECT * FROM employees_blank;
-- 输出结果：Empty set (0.00 sec)
```

验证表明，`employees_blank` 成功具备了 `employees` 的全部字段定义，而内部数据记录为 0，成功提炼出了纯净的物理空表模板。

### 两种建表范式的工程辨析与面试防坑告诫

最后，我们将两种建表方式的核心特性整理为标准工程对比：

| 比较维度 | 方式一：直接声明定义（白手起家） | 方式二：基于查询派生（CTAS 模式） |
| :--- | :--- | :--- |
| **语法核心** | `CREATE TABLE 表名 (列名 类型, ...)` | `CREATE TABLE 表名 AS SELECT ...` |
| **数据源依赖** | 无需依赖任何现成表，从物理底层独立构建 | 必须依赖至少一张已存在的基表或复杂视图 |
| **数据填充** | 仅生成空表结构，后续需配合 DML 灌入数据 | 表结构创建与历史数据导入一次性原子完成 |
| **列名定义** | 显式手工书写，精细可控 | 直接继承查询结果列名（可利用 `AS 别名` 映射） |
| **适用场景** | 全新模块研发、核心业务实体架构首次落地 | 报表中间表落盘、历史数据归档、零数据模板克隆 |

> **提示**：关于“白手起家”和“富二代式”的说法，是我们在深入剖析两种建表机制时，为了方便大家生动理解而自造的形象化比喻。大家在参加技术面试或编写企业架构设计文档时，若被问及“MySQL 中创建数据表有哪几种常见范式”，切记不要脱口而出“一种叫白手起家，一种叫富二代”——面试官会完全无法理解这种内部行话。应当给出规范严谨的技术回答：“**第一种是使用标准 DDL 显式定义列名、数据类型与完整约束的原生建表法；第二种是利用 CTAS 语法（`CREATE TABLE ... AS SELECT`），基于已有结果集快速派生结构并按需同步数据的查询衍生建表法**。”

## 51-修改表_重命名表_删除表_清空表
> 对应分集：P51 | 原始标题：《51-修改表_重命名表_删除表_清空表》

很多初学数据库的同学在学完建表后，常常会有一种心理压力：“要是我入职之后把表结构建错了，或者后续业务变更需要加字段改类型，把线上搞崩了怎么办？”

在实际的软件开发团队中，刚入职的新人通常不需要从零负责整个核心数据库与表结构的搭建。项目经理、系统架构师或资深开发人员往往在项目立项初期，就已经根据数据库设计文档把底层的库和核心表建好了。新手在相当长一段时间内，主要任务是基于现有的表结构完成业务逻辑的查询（`SELECT`）以及数据的增删改（`INSERT`/`DELETE`/`UPDATE`）。

但随着业务功能的持续迭代与个人能力的成长，你必然会面对表结构的演进维护。比如业务增加了一个新特性需要补字段，或者某个字段初期预留的字符长度不够需要扩容，甚至旧业务废弃需要归档或清空。这就涉及数据定义语言（DDL）中针对数据表生命周期的一整套管理指令。

学习这一整套指令时，如果母语是英语，会发现 SQL 语法就像日常说话一样自然：
- “如何创建数据库”：`CREATE DATABASE`
- “如何创建数据表”：`CREATE TABLE`
- “如何修改数据表”：`ALTER TABLE`
- “如何重命名表”：`RENAME TABLE`
- “如何删除数据表”：`DROP TABLE`

### 业务演进下的表结构变更管理（ALTER TABLE）

在数据表的整个生命周期中，变更需求无处不在。修改表结构的核心动词是 `ALTER`，标准句式均以 `ALTER TABLE 表名` 开头。我们以上一讲中白手起家创建的 `myemp1` 表为基准操作对象，目前该表包含三个基础字段：`id`（INT）、`emp_name`（VARCHAR(15)）、`hire_date`（DATE）。

```text
+-----------------------------------------------------------------+
|                       ALTER TABLE 四大核心操作                   |
+-----------------------------------------------------------------+
        |                 |                 |                 |
        v                 v                 v                 v
+---------------+ +---------------+ +---------------+ +---------------+
|  ADD (新增)   | |MODIFY (改属性)| |CHANGE (改名+性)| | DROP COLUMN   |
|               | |               | |               | |    (删除列)   |
| * 默认追加尾部 | | * 扩容/缩容长度| | * 列名彻底重命名| | * 物理剔除字段|
| * FIRST 首列   | | * 调整默认值  | | * 同步修改规格 | | * 级联清除数据|
| * AFTER 指定列 | | (严禁滥改类型)| | (旧列名 新列名)| | (不可逆操作)  |
+---------------+ +---------------+ +---------------+ +---------------+
```

*图 1.1：ALTER TABLE 语法分支与列级操作定位示意图*

#### 新增字段的默认追加与绝对定位（ADD ... FIRST / AFTER）

##### 默认行为：追加至表结构末尾

当业务需要记录员工的薪资时，可以使用 `ADD` 子句新增一列：

```sql
ALTER TABLE myemp1
ADD salary DOUBLE(10, 2);
```

> **提示**：这里的 `DOUBLE(10, 2)` 是典型的浮点数声明方式。数值中的 10 代表该数字的“总显示位数（有效数字长度）”，逗号后面的 2 代表“小数部分保留 2 位”。这意味着整数部分最多可以容纳 $10 - 2 = 8$ 位数字。尽管在涉及金融资金核算时生产规范强制要求使用 `DECIMAL`，但在当前 DDL 结构演练中，我们暂时使用大家熟悉的 `DOUBLE` 进行规格定义。

执行后通过 `DESC myemp1;` 检视，新增的 `salary` 列默认排在全表的最后一行。

##### 绝对定位：插入至首列（FIRST）与指定列后（AFTER）

如果业务需要对字段的排列顺序进行规范化整理，MySQL 提供了位置修饰关键字：
- **`FIRST`**：将新字段强制置于整张数据表的第一列；
- **`AFTER 列名`**：将新字段紧随插入到指定列的后面。

```sql
-- 案例一：将联系电话 phone_number 作为首字段插入
ALTER TABLE myemp1
ADD phone_number VARCHAR(20) FIRST;

-- 案例二：将电子邮箱 email 插入到员工姓名 emp_name 之后、入职日期之前
ALTER TABLE myemp1
ADD email VARCHAR(45) AFTER emp_name;
```

> **注意**：存储电话号码时，**切忌使用整型（INT）**。国内手机号通常为 11 位，早期的 4 字节标准 INT 最大只能表示到 21 亿，不仅面临溢出风险，而且电话号码中可能包含前导 0（例如固定电话区号 `010-`）或国际区号符号（`+86`），这些都属于纯字符文本语义，必须使用 `VARCHAR` 存储。

再次执行 `DESC myemp1;`，可以看到整张表的列顺序已被严格重构：`phone_number` 跃居第一位，而 `email` 精准嵌入到了 `emp_name` 之后。

#### 字段属性与长度修正（MODIFY）

当字段已经存在，但需要调整其存储规格（如长度容量、默认值）时，使用 `MODIFY` 子句。

##### 生产红线：严禁在生产运行时随意修改字段的核心数据类型

在日常开发中，我们**几乎从不修改一个字段的核心数据类型**：
1. **设计严肃性**：如果将一个显然用于存文本的 `email` 列误定义为 `INT`，这属于不可原谅的严重设计失误，应当在需求与代码评审阶段就被彻底拦截；
2. **数据兼容性与截断灾难**：如果表中已经沉淀了真实业务数据，将数值型强行改为字符型可能尚能兼容，但若试图将包含字符的列改为数值或日期，或者缩小存储容量，底层无法转换的数据行会直接触发硬性报错并中断事务，甚至造成静默截断与数据损坏。

##### 常规场景：长度扩容与默认值配置

最符合工程规范的 `MODIFY` 场景是因业务发展导致的**长度扩容**以及**业务默认值的变更**。例如，初期预估员工姓名最多 15 个字符，后来发现少数民族同胞或外籍员工全名较长，必须扩容至 25 或 35 个字符，并设定缺省默认值：

```sql
-- 将 emp_name 长度由 15 扩容为 25
ALTER TABLE myemp1
MODIFY emp_name VARCHAR(25);

-- 进一步扩容至 35 并追加默认缺省值 'aaa'
ALTER TABLE myemp1
MODIFY emp_name VARCHAR(35) DEFAULT 'aaa';
```

执行后通过 `DESC myemp1;` 观察，`emp_name` 的 `Type` 变为 `varchar(35)`，且 `Default` 属性列中清晰标注了 `'aaa'`。未来若向该表插入数据且未显式指定姓名时，系统将自动填充该默认值。

#### 字段重命名与规格联调（CHANGE）

如果业务需要对字段名本身进行重命名，必须使用 `CHANGE` 子句。

##### 语法结构与核心要求

```sql
ALTER TABLE 表名 CHANGE 旧列名 新列名 数据类型 [约束条件];
```

> **易错点**：使用 `CHANGE` 语法重命名列时，**必须在给出新列名之后，再次完整提供该列的数据类型**！即使你不打算改动任何类型和长度，也必须把原有类型完整写上，否则 SQL 解析器将因缺少列规格定义而抛出语法错误。

```sql
-- 将薪资字段 salary 重命名为更具业务辨识度的 monthly_salary
ALTER TABLE myemp1
CHANGE salary monthly_salary DOUBLE(10, 2);
```

##### 复合操作：改名与扩容一体化

正因为 `CHANGE` 强制要求输入数据类型，它天然支持在**重命名列的同时，一并完成数据类型或长度的调整**：

```sql
-- 将 email 改名为 my_email，并顺带将其长度从 45 扩充至 50
ALTER TABLE myemp1
CHANGE email my_email VARCHAR(50);
```

执行 `DESC myemp1;` 后验证，原 `email` 字段已成功更名为 `my_email`，且类型无缝变更为 `varchar(50)`。

#### 物理列的彻底移除（DROP COLUMN）

当业务线废弃、某个特性下线且元数据彻底失效时，需要将特定字段从物理表中剥离：

```sql
ALTER TABLE 表名 DROP COLUMN 列名;
```

关键字 `COLUMN` 可以写出以增加语义可读性，也可简写为 `DROP 列名`。

```sql
-- 尝试删除旧列名 email（由于此前已被重命名为 my_email，此时将引发报错）
-- ERROR 1091 (42000): Can't DROP 'email'; check that column/key exists
ALTER TABLE myemp1 DROP COLUMN email;

-- 正确执行：物理删除已存在的 my_email 列
ALTER TABLE myemp1 DROP COLUMN my_email;
```

> **警告**：执行 `DROP COLUMN` 操作会将整张表中该列存储的所有历史数据物理抹除，且 DDL 操作不提供事务回滚保障。一旦执行，原字段中的全部数据将彻底蒸发，在生产环境必须经过严格评估与脱敏备份后方可实施。

### 数据表的重命名范式（RENAME TABLE 与 ALTER TABLE）

随着系统架构重构或模块归属变更，有时需要对整张数据表进行重命名。MySQL 支持两种不同风格的重命名语法。

#### 独立动词命名法（RENAME TABLE ... TO ...）

这是讲师**强烈推荐大家掌握的标准范式**。它的动词结构与 `CREATE TABLE`、`DROP TABLE` 高度对称，语义清晰明了：

```sql
RENAME TABLE myemp1 TO myemp11;
```

执行后，原表 `myemp1` 的元数据被更新为 `myemp11`。此时执行：

```sql
DESC myemp1;
-- 报错：ERROR 1146 (42S02): Table 'atguigudb.myemp1' doesn't exist

DESC myemp11;
-- 正常输出二维表结构矩阵
```

#### ALTER 衍生语法与工程记忆准则

第二种方式是将重命名作为 `ALTER TABLE` 的一个子功能来实现：

```sql
ALTER TABLE myemp2 RENAME TO myemp12;
-- 这里的 TO 关键字可以省略，写成 ALTER TABLE myemp2 RENAME myemp12 同样合法
```

尽管两种写法底层效果完全等价，但在日常代码规范与脚本编写中，推荐统一收敛到第一种 `RENAME TABLE 旧表名 TO 新表名;`，以降低记忆负荷与维护成本。

### 数据表的物理销毁与容灾边界（DROP TABLE）

#### 幂等性删除保障（IF EXISTS）

删除数据表的关键字是 `DROP TABLE`。它与删除数据库的语法逻辑完全一致：

```sql
DROP TABLE [IF EXISTS] 表名;
```

如果直接执行 `DROP TABLE 表名;`，当目标表在当前数据库中根本不存在时，控制台会抛出硬性错误：

```sql
-- 尝试删除已被改名的 myemp2 表：
-- ERROR 1051 (42S02): Unknown table 'atguigudb.myemp2'
DROP TABLE myemp2;
```

为了保障自动化部署与清库脚本的平稳执行，必须始终追加条件判断：

```sql
-- 生产推荐规范：存在则物理删除，不存在则默默跳过且不报错
DROP TABLE IF EXISTS myemp2;
DROP TABLE IF EXISTS myemp12;
```

在 MySQL 终端或命令行执行带 `IF EXISTS` 的删除语句，即使表不存在，控制台也会输出 `Query OK, 0 rows affected, 1 warning`，脚本整体链路顺畅通过。

#### 存储空间回收与不可回滚性告诫

彻底删除一张表意味着什么？
在物理存储层面上，执行 `DROP TABLE` 会引发连锁销毁：
1. **表元数据结构抹除**：数据字典中关于该表的列定义、主外键关系、触发器等全部销毁；
2. **表数据物理销毁**：数据页上沉淀的全部记录被标为废弃并抹除；
3. **物理空间回收**：该表在磁盘上占用的表空间（例如独立表空间文件 `.ibd`）被操作系统回收并释放。

很多习惯了桌面办公软件的同学会问：“在 Word 或开发工具里写错东西，按下 `Ctrl+Z` 就能撤销；那我敲错了 `DROP TABLE`，能不能在数据库里也撤销回滚？”

> **易错点**：**绝对撤销不了**！
> 
> 在 MySQL 中，所有 DDL 语句（包括 `CREATE`、`ALTER`、`DROP`、`TRUNCATE`）都会在执行时**强制隐式提交当前事务**。这意味着它们完全独立于事务安全体系之外，无法通过 `ROLLBACK` 追回。除非运维团队预先部署了严格的 Binlog 二进制增量归档、全量物理冷备或专门的防灾镜像，否则在无备份状态下一旦执行 `DROP TABLE`，唯一的结局就只能是“从删表到跑路或自首”。

### 数据的高速截断与清空机制（TRUNCATE TABLE）

在日常管理中，经常会出现这样一种业务诉求：某张日志流水表或报表临时表已经存满了旧数据，我们需要**把里面的数据全部清空，但这张表的二维骨架（字段名、数据类型、索引定义）必须原封不动地保留**，以便后续新业务继续写入。

#### 截断语义与表结构留存机制

此时使用的核心指令是 `TRUNCATE TABLE`。这里的单词 `TRUNCATE` 与我们前面学习单行数学函数时的截断函数 `TRUNCATE(X, D)` 拼写完全一致，其核心语义就是“拦腰斩断、全部抹除”。

我们以上一讲中完整克隆了 107 条数据的 `employees_copy` 表进行验证实操：

```sql
-- 确认清空前的数据状态
SELECT COUNT(*) FROM employees_copy;
-- 输出 107 行

-- 执行截断清空操作
TRUNCATE TABLE employees_copy;
```

执行后，客户端控制台通常会返回 `Query OK, 0 rows affected`。很多初学者会被这个 `0 rows affected` 蛊惑，误以为没有清空成功。

此时分别执行查询与表结构检视：

```sql
-- 检视数据
SELECT * FROM employees_copy;
-- 输出结果：Empty set (0.00 sec)

-- 检视表结构
DESC employees_copy;
-- 输出结果：原有的所有列名、类型与属性毫发无损！
```

这充分证明：**`TRUNCATE TABLE` 专注于抹杀表内的数据行，而对表的元数据骨架完好保留**。

```text
+-----------------------------------------------------------------+
|               DROP TABLE 与 TRUNCATE TABLE 的底层效果对比        |
+-----------------------------------------------------------------+
| 操作指令        | 表中数据记录 (Rows) | 表物理骨架结构 (Structure) | 磁盘表空间 |
+----------------+--------------------+-------------------------+-----------+
| DROP TABLE     | 全部彻底销毁       | 物理彻底抹除 (表不存在)   | 完全释放   |
| TRUNCATE TABLE | 全部清空重置       | 完好保留 (空表状态)       | 重建重置   |
+-----------------------------------------------------------------+
```

#### TRUNCATE 与 DELETE 的初探与事务引申

有提前预习或有开发经验的同学此时会敏锐地提出一个深层疑问：
“在后面的 DML 章节中，我们要专门学习 `DELETE FROM 表名;` 指令。`DELETE` 语句如果不加 `WHERE` 过滤条件，同样可以把全表数据删得干干净净，同时保留表结构。既然已经有了 `DELETE`，MySQL 为什么还要大费周章地单独设计一个属于 DDL 范畴的 `TRUNCATE TABLE`？”

这看似重复的功能背后，其实隐藏着关系型数据库底层机制的巨鸿沟：
- `DELETE` 属于数据操作语言（DML），底层是逐行删除记录，会触发事务日志（Undo Log / Redo Log）的详尽记录；在事务未提交前，完全可以通过 `ROLLBACK` 完美撤销！
- `TRUNCATE` 属于数据定义语言（DDL），底层采用物理截断与数据页重建机制，执行速度远超 `DELETE`，但它会**隐式提交事务，彻底无法回滚**！

这两者的深度机理差异，以及数据库事务控制语言（DCL）中 `COMMIT` 与 `ROLLBACK` 的真正运行逻辑，我们将在下一讲中展开专题对决实验。

## 52-DCL中COMMIT与ROLLBACK的使用
> 对应分集：P52 | 原始标题：《52-DCL中COMMIT与ROLLBACK的使用》

在上一讲介绍数据表的生命周期管理时，我们演示了通过 `TRUNCATE TABLE` 可以在保留表结构的前提下，快速将一张大表的数据彻底抹去。但很多对 SQL 有一定了解的同学立刻就会产生疑问：在后续的 DML 操作中，我们同样会学习到一条用于删除数据的标准语句——`DELETE FROM 表名;`。如果不加 `WHERE` 条件，`DELETE` 同样能够把全表数据删得一干二净，而且表结构同样完好保留。

为什么两个看起来功能几乎重合的语法能够并存？它们到底有什么本质区别？

这看似只是两个 SQL 语句的语法之争，其背后其实代表了关系型数据库底层两大阵营的正面交锋：`TRUNCATE` 代表的是负责结构定义的数据定义语言（DDL），而 `DELETE` 代表的是负责行级记录操作的数据操作语言（DML）。为了彻底讲透两者的分水岭，我们必须引入数据控制语言（DCL，在事务细分领域也被称为 TCL，Transaction Control Language 事务控制语言）中最为核心的两大基石指令——`COMMIT` 与 `ROLLBACK`。

---

### 事务控制语言（DCL/TCL）的核心基石

在深入对比表清空机制之前，我们首先需要将 `COMMIT`（提交）与 `ROLLBACK`（回滚）这两个关键字的底层语义和时序边界彻底厘清。

```text
+-----------------------------------------------------------------------+
|                    事务控制的两大状态分支 (COMMIT 与 ROLLBACK)           |
+-----------------------------------------------------------------------+
                                    |
                                    v
                            执行数据变更操作 (DML)
                                    |
               +--------------------+--------------------+
               |                                         |
               v                                         v
       执行 COMMIT 指令                          执行 ROLLBACK 指令
+-------------------------------+         +-------------------------------+
| * 数据永久持久化写入磁盘数据页 |         | * 撤销变更，恢复历史镜像状态  |
| * 无法再次撤销，不可回滚      |         | * 严格回滚至最近一次 COMMIT点 |
+-------------------------------+         +-------------------------------+
```

*图 1.1：数据变更提交与回滚的状态分支机理示意图*

#### COMMIT 的持久化语义与现实映射

`COMMIT` 翻译成中文就是“提交”。在数据库执行引擎中，一旦执行了 `COMMIT` 操作，意味着**当前事务内所发生的所有数据增、删、改操作被永久性、物理性地固化写入到了数据库磁盘中**。

> **结论**：**数据一旦执行 COMMIT 提交，就彻底丧失了在事务层面上撤销与回滚的可能性**。

在日常生活中有非常贴切的现实映射：
- **同行转账场景**：你将 1000 元借款转账给了同学。当银行交易系统提示“转账已成功”的那一刻，底层数据库就已经完成了 `COMMIT`。此时你如果突然反悔，是绝对不可能在手机银行上点击一个类似“撤销/回滚”的按钮把钱直接撤回来的。你唯一的途径是私下跟同学协商，让他再主动发起一笔新的逆向转账把钱打还给你。这在数据库中属于一条全新的 DML 变更操作，而不是事务层面的数据回滚。
- **电信诈骗与银行风控拦截**：在防范电信网络诈骗的资金风控中，银行通常会设置“延迟两小时到账”的保护机制。在这两小时的冻结窗口期内，资金尚未完成最终清算（类比于尚未 COMMIT），一旦受害人醒悟报警，银行有权限在系统中实施拦截终止；但如果两小时过去、资金已经全额划拨到了境外骗子的账户（类比于已经 COMMIT），银行工作人员也无权强行单方面把资金从对方账户中抽回。此时只能立案侦查，等待司法机关追赃挽损。

#### ROLLBACK 的撤销边界与“最近一次提交”推导模型

与 `COMMIT` 相对的指令是 `ROLLBACK`，即“回滚”。它的核心功能就是我们常说的“撤销”。
当我们在数据库中误操作删改了一批数据时，执行 `ROLLBACK` 可以将脏写撤回，将数据恢复到操作前的状态。

但是，`ROLLBACK` 的撤销能力绝非无限穿越的时光机。它在执行时遵循一个绝对严密的时间线边界：

> **定义**：**`ROLLBACK` 只能将数据回滚到当前会话中“最近的一次 COMMIT 操作之后”的状态**。

为了直观理解这一推导链条，我们构建一个状态迁移时序模型：

```text
[时间线推进] ==========================================================>
  |
  +--> 步骤 1: 执行 DML 操作 A (写入新记录)
  |
  +--> 步骤 2: 执行 COMMIT (提交点 C1) =======> [操作 A 被永久物理固化]
  |
  +--> 步骤 3: 执行 DML 操作 B (修改记录)
  |
  +--> 步骤 4: 执行 COMMIT (提交点 C2) =======> [操作 B 被永久物理固化]
  |
  +--> 步骤 5: 执行 DML 操作 C (删除数据)
  |
  +--> 步骤 6: 执行 ROLLBACK (回滚指令)
           |
           +---> 寻址回退到【最近一次提交点 C2】
                 结果：仅撤销步骤 5 的操作 C；操作 A 与 B 坚如磐石，不受影响！
```

*图 1.2：多提交点时序下 ROLLBACK 回滚边界寻址模型图*

从上述模型可以清晰看到：当第 6 步触发 `ROLLBACK` 时，数据库引擎只会逆向撤销步骤 5 中未提交的操作 C；而步骤 1 和步骤 3 的变更，早在遭遇 C1 和 C2 提交点时就已经脱离了回滚日志的保护区，永久沉淀在存储引擎中。

### 表数据清除的双雄对决：TRUNCATE TABLE 与 DELETE FROM

搞清楚了 `COMMIT` 与 `ROLLBACK` 的基石概念后，我们回到核心命题：`TRUNCATE TABLE` 与 `DELETE FROM` 的区别。

#### 功能交集与表结构保留特性

首先明确两者的相同点：
- **目标一致**：两者都可以用于将数据表中的记录清空；
- **骨架留存**：两者在抹去记录的同时，都会**完整保留数据表的二维结构元数据**（包括列名、数据类型、主键索引、存储引擎与编码定义）。清空之后，表依然存在，后续业务随时可以重新写入数据。

#### 语法灵活性与删除粒度对比

两者的关键差异首先体现在语法的精细度上：
- **`TRUNCATE TABLE`**：属于一刀切的截断语法。它**不支持任何 `WHERE` 过滤条件**，只要执行，就必须对整张表的所有数据进行全量清除，没有任何筛选余地。
- **`DELETE FROM`**：属于标准的 DML 数据操作语言。它**天然支持 `WHERE` 条件从句**。开发人员既可以通过 `DELETE FROM 表名 WHERE id = 10;` 精确删除单行记录，也可以通过范围条件删除一个区间的记录；只有在显式省略 `WHERE` 条件时，才会执行全表删除。

而最深刻的本质区别在于：**`DELETE FROM` 操作的数据可以实现事务回滚，而 `TRUNCATE TABLE` 清空的数据绝对不可回滚**！

---

### 事务回滚能力的对照实验与运行机理

很多同学看到这里会产生疑惑：“既然说 `DELETE` 能够回滚，为什么平时我们在图形化界面里敲一句 `DELETE FROM 表名;`，再敲 `ROLLBACK;`，数据依然找不回来呢？”

这是因为在默认情况下，MySQL 会开启一种隐式的运行模式。

#### 自动提交机制（autocommit）与回滚前置条件

在 MySQL 默认配置下，会话级别的系统变量 `autocommit` 的默认值是 `TRUE`（或者表示为 1）：

```sql
SHOW VARIABLES LIKE 'autocommit';
-- 输出 Value 为 ON
```

`autocommit = TRUE` 意味着**自动提交**：你每在客户端敲下一条独立的 DML 语句（无论是一条 `INSERT` 还是一条 `DELETE FROM`），MySQL 内部都会在执行完毕的瞬间，默认替你自动在后台执行一次 `COMMIT`。

既然每条语句都被系统强制自动提交了，后续你再敲 `ROLLBACK`，它回滚到“最近一次提交之后”，面对的自然就是刚刚那次自动提交，结果自然无法挽回。

> **结论**：**要想让 DML 的数据变更支持回滚撤销，必须在执行 DML 操作之前，显式将自动提交机制关闭**：
> ```sql
> SET autocommit = FALSE;
> ```

为了验证 `DELETE` 与 `TRUNCATE` 在回滚机制上的巨大差异，我们使用包含 106 条数据的 `myemp3` 表，进行一组严格控制变量的对照实验。

#### 实验组 A：DELETE FROM 的回滚验证全流程

我们严格按照以下步骤顺序执行：

```sql
-- 步骤 1：显式提交一次，把此前的一切历史操作归零固化，锁定基准线
COMMIT;

-- 步骤 2：核验数据，确保当前表内真实包含 106 条记录
SELECT * FROM myemp3;

-- 步骤 3：核心前置条件——关闭当前会话的自动提交机制
SET autocommit = FALSE;

-- 步骤 4：执行 DML 全表删除操作（不带 WHERE 条件）
DELETE FROM myemp3;

-- 步骤 5：再次核验表数据，确认全表已空
SELECT * FROM myemp3;
-- 输出结果：Empty set (0.00 sec)

-- 步骤 6：执行 DCL 核心撤销指令——数据回滚
ROLLBACK;

-- 步骤 7：见证历史状态复原
SELECT * FROM myemp3;
-- 输出结果：106 条数据全部奇迹般复原！
```

##### 实验 A 结果剖析
在执行 `DELETE FROM` 时，由于我们预先设置了 `SET autocommit = FALSE`，存储引擎没有自动固化该操作，而是将这 106 行记录的删除动作写入了事务回滚日志（Undo Log）。当执行 `ROLLBACK` 时，引擎根据回滚日志成功寻址到了步骤 1 的基准提交点，将整个删除动作完全撤销，数据完整归位。

#### 实验组 B：TRUNCATE TABLE 的回滚失效现象

在相同的环境下，保持所有外部操作完全一致，仅将删除语句替换为 `TRUNCATE TABLE`：

```sql
-- 步骤 1：显式提交一次，确立物理基准线
COMMIT;

-- 步骤 2：确认当前表内依然拥有完好的 106 条记录
SELECT * FROM myemp3;

-- 步骤 3：同样执行关闭自动提交机制
SET autocommit = FALSE;

-- 步骤 4：执行 DDL 截断清空指令
TRUNCATE TABLE myemp3;

-- 步骤 5：核验表状态
SELECT * FROM myemp3;
-- 输出结果：Empty set (0.00 sec)

-- 步骤 6：尝试执行回滚撤销
ROLLBACK;

-- 步骤 7：再次查询数据
SELECT * FROM myemp3;
-- 输出结果：依然为 Empty set (0.00 sec)！数据彻底消失，无法找回！
```

---

### DDL 隐式提交机制的底层真相

#### 认知冲突：为什么没有回滚到清空之前？

实验 B 的结果常常会颠覆很多初学者的逻辑直觉。有同学会提出强烈的质疑：
“宋老师，你前面刚讲过，`ROLLBACK` 是回滚到最近的一次 `COMMIT` 之后。我们在实验 B 的步骤 1 中，明明亲手执行了一次 `COMMIT`；接着我们关闭了自动提交，执行了 `TRUNCATE`，中途并没有手动敲过任何 `COMMIT` 指令。那么按照规则，步骤 6 的 `ROLLBACK` 难道不应该直接回滚到步骤 1 的提交点之后，把表里的 106 条数据复原吗？为什么回滚会彻底失效？”

这是一个极具含金量的高水平疑问。

#### DDL 强制隐式提交与 autocommit 的作用域穿透

这个现象背后隐藏着关系型数据库底层极其关键的一条铁律：

> **核心原理**：**以 TRUNCATE TABLE、CREATE TABLE、ALTER TABLE、DROP TABLE 为代表的所有 DDL 操作，在执行完毕后，内部必然且无条件地自动触发一次强制的隐式提交（Implicit Commit）！且该隐式提交彻底免疫 `SET autocommit = FALSE` 的约束！**

```text
用户脚本执行时序：
COMMIT; (步骤 1，显式提交点 C1)
SET autocommit = FALSE; (仅对 DML 生效)
TRUNCATE TABLE myemp3;
   |
   +---> [底层物理执行]: 释放数据页，重新分配根节点
   |
   +---> [引擎内部暴击]: 强行执行隐式提交 (Implicit Commit 点 C_hidden)！
ROLLBACK;
   |
   +---> 寻址最近一次提交点：找到的是刚刚发生的 C_hidden！
         此时数据早已在 C_hidden 中永久固化为“空表”，回滚动作实质变为空操作！
```

*图 4.1：DDL 隐式提交机制阻断 ROLLBACK 路径分析图*

真相水落石出：
1. `SET autocommit = FALSE;` 仅仅能够约束 `INSERT`、`UPDATE`、`DELETE` 这类 DML 语句的自动提交行为；
2. 只要碰上 DDL 指令，MySQL 认为这属于系统结构元数据层面的重大变更。为了保障底层数据字典与物理文件的一致性，存储引擎必须强制将元数据与数据页状态即刻落盘。
3. 因此在 `TRUNCATE TABLE` 执行结束的那一毫秒，系统在后台悄悄完成了一次提交。后续你的 `ROLLBACK` 寻址到的“最近一次提交点”，根本不是步骤 1 的 C1，而是这个隐式提交点！数据早就被固化为空表了。

#### 生产运维的容灾红线与后续高阶演进

总结本讲的对决，我们将核心技术特征沉淀为以下对比矩阵：

| 评估维度 | TRUNCATE TABLE | DELETE FROM |
| :--- | :--- | :--- |
| **语言归属** | DDL（数据定义语言） | DML（数据操作语言） |
| **过滤条件** | 不支持 `WHERE`，只能清空全表 | 灵活支持 `WHERE`，可删全表亦可删子集 |
| **执行效率** | 极快（直接重置数据页指针与高水位线） | 较慢（逐行扫描、加锁并产生 Undo 日志） |
| **回滚能力** | **绝对不可回滚**（触发强制隐式提交） | **支持事务回滚**（受 autocommit 与事务控制） |
| **自增主键处理**| 强制将 `AUTO_INCREMENT` 计数器重置回初始值 1 | 保留当前最大自增断点，新插入继续递增 |

> **生产安全告诫**：
> 在日常数据库开发与运维管理中，千万不要将图形化软件中的 `Ctrl+Z` 撤销思维带入到数据库 DDL 操作中。在面对 `DROP`、`TRUNCATE`、`ALTER` 语句时，必须时刻警惕其**不可逆性**与**隐式提交特性**。只要涉及结构销毁与物理截断，没有任何后悔药可吃；任何缺少冷热备份支撑的粗暴清表，最终换来的只能是无可挽回的线上灾难。

关于事务更为庞大的核心体系——包括 ACID 四大特性、事务并发引发的脏读、不可重复读与幻读，以及通过锁机制（Locking）与多版本并发控制（MVCC）实现事务隔离级别的高阶原理，我们将在下篇高级进阶中为大家彻底解密。

在实际开发中，当我们面对一张不再需要的表时，往往会面临一个经典的选择：到底该用 `TRUNCATE TABLE` 还是 `DELETE FROM`？这个看似简单的操作选择，背后不仅关乎底层日志、事务资源与执行效率的较量，更直接牵扯到生产环境的数据安全底线。与此同时，建表时的字段命名是否规范、字段长度是否合理，会直接决定数据库底层的 I/O 检索性能；而数据库版本升级带来的底层架构革新（如 MySQL 8.0 的 DDL 原子化），更是彻底改变了多表级元数据操作的容错机制。

### 全表数据清理的工程选型与权衡

#### TRUNCATE TABLE 与 DELETE FROM 的核心差异

如果在技术面试或架构评审中被问到：“现在有一张表，里面的所有数据都不要了，你究竟该用 `TRUNCATE TABLE` 还是 `DELETE FROM`？为什么？”

这道题目表面上考察的是两条 SQL 的语法区别，实际上检验的是对底层运行机理的理解以及真实生产环境下的工程经验。

从语法功能上看，两条命令都能把一张表里的记录全部清空。然而从底层实现与资源消耗的角度来看，两者存在本质区别。阿里巴巴《Java开发手册》在涉及数据库操作的章节中明确指出了这两种操作的性能特征：

> **结论**：`TRUNCATE TABLE` 比 `DELETE` 的运行速度要快得多，并且使用的系统资源和事务日志资源要少得多。

造成这一性能差距的核心原因主要包含以下三点：

1. **事务与日志机制**：`DELETE FROM` 属于数据操作语言（DML，Data Manipulation Language），它默认运行在事务环境中。在执行逐行删除时，MySQL 必须将每一行被删除的数据记录到回滚日志（Undo Log）中。这相当于一边执行删除，一边在后台默默为被删数据做全套副本备份，以便用户一旦发出 `ROLLBACK` 命令时能够完整回滚恢复。而 `TRUNCATE TABLE` 属于数据定义语言（DDL，Data Definition Language），它采用的是立即隐式提交机制。它不需要在事务中为回滚保留数据镜像，执行完毕后也不会提供回滚支持。
2. **触发器（Trigger）开销**：`DELETE` 在逐行清理数据时，会逐条触发该表上绑定的 `BEFORE DELETE` 和 `AFTER DELETE` 触发器，如果触发器内部还包含数据同步或审计逻辑，性能开销将成倍放大；而 `TRUNCATE TABLE` 属于整表物理重置，根本不会触发任何删除触发器。
3. **空间释放方式**：`DELETE` 只是给数据行打上删除标记，表空间的高水位线（High Water Mark）通常不会立即释放，碎片依然存在；而 `TRUNCATE TABLE` 会使数据字典中的表结构被重新初始化，重置自增列计数器，并直接回收数据页空间。

```text
+--------------------------------------------------------------------+
|                       全表数据清理机制对比                         |
+-------------------+--------------------+---------------------------+
| 对比维度          | DELETE FROM 表名   | TRUNCATE TABLE 表名       |
+-------------------+--------------------+---------------------------+
| 语言类别          | DML（数据操作语言）| DDL（数据定义语言）       |
| 事务支持          | 支持事务，可回滚   | 自动隐式提交，不可回滚    |
| 日志与备份        | 逐行写入 Undo Log  | 不记录行数据备份，资源极少|
| 触发器            | 正常逐行激活       | 不激活任何触发器          |
| 自增计数器        | 保持不变           | 重置为初始值（通常为 1）  |
| 资源消耗与速度    | 耗时长，资源开销大 | 瞬时完成，资源消耗极低    |
+-------------------+--------------------+---------------------------+
```
> *读图说明：DML 机制为了保证事务一致性付出大量日志与备份代价；DDL 机制以直接重置表物理结构换取极高的执行速度。*

#### 生产事故防范与选型底线

单纯从性能和系统资源的角度考量，`TRUNCATE TABLE` 显然全面胜出。但在真实的生产开发场景中，工程决策绝不能只看理论层面的性能数字。

> **易错点**：在实际项目开发中，极度不推荐频繁使用 `TRUNCATE TABLE`，应当尽可能使用带明确条件的或受事务保护的操作。

在企业级系统中，无论是系统的运行审计日志，还是业务核心的用户资产数据，一旦在未做冷备或异地容灾的前提下执行了 `TRUNCATE TABLE`，整张表的数据瞬间归零，且无法通过事务日志直接回滚恢复。

在日常高强度的工作中，开发人员如果精神疲劳、注意力不集中，失误把生产环境当作测试环境执行了一条 `TRUNCATE TABLE`，造成的后果往往是灾难性的。在生产环境里，多消耗一点 CPU、多占用一点磁盘 I/O 和回滚日志空间，完全在系统的承载范围之内；但一次无法逆转的数据丢失，足以直接击穿业务系统的可用性，甚至引发法律层面的刑事追责。在业内曾经出现过因为误删生产数据库核心数据而被依法追究刑事责任的真实判例。

因此，面对清空数据的需求，规范的做法是：
- 严格评估数据备份状态；
- 如果必须清空大表，优先走合规的变更评审与数据归档流程；
- 生产环境的交互式终端中，严禁随意敲下 `TRUNCATE TABLE`。

### 阿里巴巴 MySQL 库表与字段设计规范

阿里巴巴《Java开发手册》在业界具备极高的通用性和参考价值。对于中小公司而言，直接借鉴大厂历经海量业务打磨出的建表规范，是避免后续踩坑的最有效途径。

#### 基础命名规范与禁用规则

在定义表名和字段名时，必须遵循以下强制要求：

1. **统一小写与数字**：表名、字段名必须使用小写字母或数字，严禁出现大写字母。
   - 正例：`user_id`、`order_item`、`config_version`
   - 反例：`UserId`、`OrderItem`、`CONFIG_VERSION`
   - *原因说明*：Windows 环境下 MySQL 默认对大小写不敏感，但在 Linux 生产环境下，底层文件系统默认对文件名严格区分大小写。使用大写字母极易在跨平台部署和迁移时引发找不到表或字段的隐蔽 Bug。
2. **禁止数字开头**：表名和字段名禁止以数字开头。
   - 正例：`level3_name`、`type1_status`
   - 反例：`1st_name`、`3_level`
3. **禁止两个下划线中间仅有数字**：
   - 正例：`level_1_category`（不合规，应优化为 `level1_category` 或 `category_l1`）
   - 反例：`level__1__name`、`status__2__code`
4. **命名单词分隔符**：字段名由多个单词组成时，统一采用下划线（snake_case）进行连接。Java 代码中推崇小驼峰命名（如 `userId`），但在关系型数据库中，必须规整为小写加下划线（如 `user_id`）。
5. **禁用保留字与关键字**：严禁使用 SQL 保留字作为表名或字段名，例如 `desc`、`range`、`match`、`delayed`、`key` 等。如果非要使用这些单词，在编写 SQL 时必须强制使用反引号（\`）进行转义，这极大增加了 SQL 维护成本与语法解析出错的概率。
6. **修改代价与谨慎原则**：数据库中的字段一旦落库并上线，其修改代价极大。与 Java 应用不同，数据库字段无法通过“预发布环境平滑热切”来完全屏蔽风险。一个核心字段的重命名，不仅涉及底层存储的重构，还会直接导致线上几十甚至上百处 SQL 映射、缓存系统、索引定义与离线报表任务全面报废。因此在项目初期的 DDL 阶段，就必须把字段名称与业务含义推敲清楚，上线后禁止随意重构。

#### 数据表必须具备的三大基础字段

阿里巴巴规范要求，业务系统中的每一张表，都应当尽量标配以下三个核心字段：

```sql
CREATE TABLE table_name (
    id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    gmt_create   DATETIME NOT NULL COMMENT '创建时间',
    gmt_modified DATETIME NOT NULL COMMENT '修改时间',
    ...
    PRIMARY KEY (id)
);
```

各字段的工程考量如下：

- **`id`（主键）**：
  - 类型推荐为 `BIGINT UNSIGNED`（无符号 64 位大整数）。现代互联网业务的数据体量增长迅速，普通 32 位整型（`INT`）的最大上限仅为 21 亿左右（有符号）或 42 亿（无符号），在大型分布式分表或海量流水场景下极易发生主键耗尽溢出。
  - 声明为 `UNSIGNED` 是因为自增主键没有取负数的业务意义，无符号可以将正数范围扩大一倍。
  - 步长默认为 1，保持单调递增，这对于 InnoDB 底层 B+ 树索引的顺序写入非常友好，能最大程度减少聚簇索引分裂。
- **`gmt_create`（创建时间）**：记录数据行首次写入数据库的时间（精确到年月日时分秒）。为业务审计、数据对账、冷热数据分离提供了可靠的基准时间戳。
- **`gmt_modified`（修改时间）**：记录数据行最近一次发生变更的时间。无论是排查数据一致性问题，还是依靠 Canal、Flink 等工具做增量数据同步（CDC），该字段都是核心筛选依据。

#### 库表命名的业务语义映射

在表名与库名的设计上，规范推荐以下模式：

- **表名**：最好遵循 `业务名称_表的作用` 的组合结构。
  - 例如交易模块的订单表：`trade_order`；
  - 支付宝支付任务调度表：`alipay_task`。
  - 这种命名让人一眼就能看清该表所属的子系统及其承载的核心实体。
- **库名与应用名称一致**：微服务架构下应用通常被拆分为多个独立工程。推荐将微服务的应用名与对应的物理/逻辑数据库名保持一致，方便运维人员和开发人员建立清晰的微服务与数据资产对应拓扑。

#### 字段存储长度对查询 I/O 性能的深层影响

在定义字段类型和长度时，手册中给出了如下指导原则：

> **核心原则**：选择合适的字符存储长度，不仅能节约数据库的表空间和索引存储开销，更关键的是能够显著提升数据的检索速度。

节约存储空间很好理解，但为什么“字段长度合理”能够直接提升查询速度？这需要深入到 MySQL InnoDB 存储引擎的底层 I/O 调度机制去理解。

InnoDB 引擎管理磁盘与内存数据交换的基本单位是**数据页（Page）**，默认大小为 **16KB**。

```text
+--------------------------------------------------------------------+
|                InnoDB 16KB 数据页内存装载机制对比                  |
+--------------------------------------------------------------------+

 场景 A：字段类型冗余偏大（如过度使用 BIGINT / VARCHAR(255)）
 +------------------------------------------------------------------+
 | 16KB 数据页 1: [ Row 1 ][ Row 2 ] ... [ Row 1000 ]               | -> 容纳 1000 行记录
 +------------------------------------------------------------------+
 查询 10,000 条记录：需要从磁盘执行 10 次 I/O，载入 10 个数据页到 Buffer Pool。

 场景 B：字段类型精准克制（按实际业务合理分配 TINYINT / VARCHAR(20)）
 +------------------------------------------------------------------+
 | 16KB 数据页 1: [ Row 1 ][ Row 2 ] ... [ Row 10000 ]              | -> 容纳 10000 行记录
 +------------------------------------------------------------------+
 查询 10,000 条记录：仅需从磁盘执行 1 次 I/O，载入 1 个数据页即可完成命中。
+--------------------------------------------------------------------+
```
> *读图说明：单个记录占用的物理字节越少，单页容纳的数据行越多，获取同等量级数据所需的磁盘物理 I/O 次数越少。*

计算机系统中最昂贵的性能开销就是磁盘 I/O。如果字段类型设定得过分冗余，一个 16KB 的数据页所能容纳的行记录数量就会大幅缩水；在执行全表扫描或大范围索引查询时，原本载入 1 个数据页就能解决的查询，系统被迫需要执行 10 次甚至更多次磁盘 I/O。因此，压缩字段长度的本质，是为了提高内存命中率，降低磁盘读写频次。

为了建立字段类型选型的直观感知，可以参考一套现实标尺：

- **人类年龄**：通常在 0 到 150 岁之间，推荐选用 `TINYINT UNSIGNED`（取值范围 0~255，仅占 1 字节），绝对没有必要使用占用 4 字节的 `INT`；
- **乌龟寿命**：数百岁，超过 255 但在数万以内，可使用 `SMALLINT UNSIGNED`（0~65535，占 2 字节）；
- **恐龙化石与宇宙年龄**：数亿年至上百亿年，则需要上升到 `INT`（约 42 亿）或 `BIGINT`。

在实际业务建模时，应当以这一标尺为参照，审慎评估业务字段在未来 3~5 年内的最大极限范围，选择满足需求的最小数据类型。

### 高危 DDL 操作的权限边界与管理防线

#### 字段删除与表删除的不可逆性

在日常维护中，不仅仅是 `DROP TABLE` 具备毁灭性，`ALTER TABLE` 的子操作同样属于高危动作。

使用 `ALTER TABLE ... DROP COLUMN` 删除某一个已存在的大表字段时，该操作同样是直接生效且不进入普通 DML 事务回滚队列的 DDL 语句。如果该字段中积攒了数年高价值的业务元数据，一旦误删，如果没有实时有效的冷热备份镜像，后果等同于全表被毁。

#### 权限最小化与 DBA 连带责任

企业中通常实行严格的权限隔离制度：

- **普通开发人员账号**：在新员工入职或常规应用连接配置中，账号默认只具备 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 等 DML 操作权限，严禁直接对生产库赋予 `DROP`、`TRUNCATE`、`ALTER` 等 DDL 级别的结构变更权限。
- **DBA 连带责任机制**：若业务代码中不需要执行 DDL，但在初始授权时 DBA 疏忽授予了 `DROP` 权限，一旦发生手抖误删事故，不仅误操作人员难逃其责，当初负责配置权限的 DBA 同样要承担严重的连带过失责任。权限管控的黄金法则是：**权限最小化，能不给的坚决不给，按需临时审批开通**。

### MySQL 8.0 新特性：DDL 的原子化

在 MySQL 5.7 及之前版本中，DDL 语句一直处于“事务之外”。一旦一条语句中涉及多个元数据操作，中途只要发生错误，系统往往会处于一种不可名状的“中间半完成状态”。MySQL 8.0 正式引入了 **DDL 的原子化（Atomic DDL）** 特性，彻底改变了这一局面。

#### 什么是 DDL 的原子化

> **定义**：DDL 原子化是指将数据定义语言操作封装为具有原子性（Atomicity）的操作单元。一个包含多个子步骤的 DDL 语句，要么全部成功执行并持久化提交（Commit），要么在中间任一步骤发生故障时整体回滚（Rollback）到执行前的状态，绝对不会留下只执行了一半的残留状态。

在 MySQL 8.0 之前，元数据信息分散存储在各种 `.frm` 文件、MyISAM 系统表或内存结构中，引擎层与 Server 层元数据脱节，无法统一进行事务化日志追踪。

MySQL 8.0 重新设计了架构，引入了由 InnoDB 统一管理的**集成数据字典（Data Dictionary）**。在执行原子 DDL 时，系统会在后台的 `innodb_ddl_log` 表中记录所有相关的元数据操作记录。如果 DDL 执行顺利结束，该日志被清除；如果执行过程中抛出异常（例如后续依赖的表不存在、发生命名冲突或硬件故障），系统会自动读取这部分 DDL 日志，执行反向补偿操作进行回滚，确保数据字典的一致性。

#### MySQL 5.7 与 MySQL 8.0 的对照实操

为了清晰验证 DDL 原子化的实际效果，设计一个多表复合删除的实验场景：在同一个 `DROP TABLE` 语句中，同时指定删除存在的表和不存在的表。

##### 步骤一：创建测试库与数据表

在 MySQL 5.7 与 MySQL 8.0 环境中分别执行相同的初始化脚本：

```sql
-- 创建测试数据库
CREATE DATABASE mytest;

-- 切换并使用测试数据库
USE mytest;

-- 创建测试表 book1
CREATE TABLE book1 (
    book_id   INT,
    book_name VARCHAR(20)
);

-- 查看当前数据库中的表
SHOW TABLES;
```

此时，两个版本的 `mytest` 数据库中都只有一张数据表 `book1`，而表 `book2` 并不存在。

```text
+------------------+
| Tables_in_mytest |
+------------------+
| book1            |
+------------------+
1 row in set (0.00 sec)
```

##### 步骤二：执行复合删除语句

现在通过一条包含逗号连接的 `DROP TABLE` 语句，尝试同时删除 `book1` 与 `book2`：

```sql
DROP TABLE book1, book2;
```

由于 `book2` 本身并不存在，无论在 MySQL 5.7 还是 MySQL 8.0 中，控制台都会抛出同样的错误信息：

```text
ERROR 1051 (42S02): Unknown table 'mytest.book2'
```

这一报错合情合理。但核心分歧在于：**在报错发生之前已经执行了删除逻辑的 `book1`，到底还在不在？**

##### 步骤三：验证执行结果

再次执行查看表命令：

```sql
SHOW TABLES;
```

- **在 MySQL 5.7 下的执行结果**：
  ```text
  Empty set (0.00 sec)
  ```
  `book1` 已经被彻底删除了。
  在 5.7 中，该语句被顺序解析为“先执行 `DROP TABLE book1`，成功后再执行 `DROP TABLE book2`”。当执行到第二阶段报错崩溃时，整个语句立刻中断退出，但第一阶段对 `book1` 的物理删除已经无法追回。

- **在 MySQL 8.0 下的执行结果**：
  ```text
  +------------------+
  | Tables_in_mytest |
  +------------------+
  | book1            |
  +------------------+
  1 row in set (0.00 sec)
  ```
  `book1` 完好无损地保留在数据库中！
  由于 MySQL 8.0 支持 DDL 原子化，当系统在删除 `book2` 抛出 `ERROR 1051` 异常时，检测到该复合操作未完全成功，系统立即通过 DDL 日志启动内部回滚机制，将前面已经执行的 `DROP TABLE book1` 完整回滚，恢复了原状。

```text
+--------------------------------------------------------------------+
|            DROP TABLE book1, book2; 容错机制对比                    |
+--------------------------------------------------------------------+

 MySQL 5.7 执行时序（非原子化）：
  [DROP book1] -------> 成功 (元数据直接抹除，不可逆)
                            |
  [DROP book2] -------> 失败 (报错 Unknown table 'book2')
                            |
                         程序终止
                 (最终结果：book1 永久丢失，数据字典处于割裂状态)

 MySQL 8.0 执行时序（原子化支持）：
  开启原子 DDL 事务
      |
  [DROP book1] -------> 写入 DDL Log 并执行阶段操作
      |
  [DROP book2] -------> 失败 (报错 Unknown table 'book2')
      |
  触发异常捕获 --------> 依据 DDL Log 执行反向补偿回滚 (ROLLBACK)
      |
  原子 DDL 退出
                 (最终结果：book1 完整恢复，保持操作前的系统一致性)
+--------------------------------------------------------------------+
```
> *读图说明：5.7 遇到中途错误直接截断并留下半成品破坏；8.0 依托数据字典与 DDL Log 实现整体事务性回滚。*

#### 原子性机理与后续事务机制预告

理解了 DDL 的原子化，也就掌握了事务（Transaction）最关键的特质——**原子性（Atomicity）**。

在物理学的发展历程中，原子曾被视作不可再分的最小物质微粒。在数据库领域，借用“原子”这一概念，就是为了形象地表达：**一个操作单元是一个不可分割的整体**。

日常生活中也存在类似的逻辑：比如家长给孩子提出一组考核条件，要求完成背诵、整理房间、完成作业三件事，全做完了才能奖励吃糖。如果孩子只完成了前两件，第三件没做甚至还搞砸了，那么整个奖励机制就会失效，之前谈定的条件全盘重置。

在数据库事务（Transaction）中，典型的业务逻辑通常由多个 DML 语句组合而成：
- **全部成功**：调用 `COMMIT`（提交），修改被永久写入磁盘，持久化固定下来；
- **中途报错**：调用 `ROLLBACK`（回滚），已经改动的数据必须全部撤销还原，就像什么都没发生过一样。

MySQL 8.0 的突破性革新，正是将原本仅属于 DML 领域的事务原子性机制，全面下沉并覆盖到了包括表结构定义在内的 DDL 层面。

有关事务处理的核心原则、ACID 四大特性（原子性、一致性、隔离性、持久性）、底层行级锁与表级锁的竞争机制，以及多版本并发控制（MVCC）的高并发读写调度，构成了数据库性能优化与架构设计的核心命脉，这些深度进阶内容将在后续的事务与存储引擎专题中全面拆解。

### 本讲提到的题目

#### 题目：全表删除操作选型辨析题

**题干描述**：
在实际项目开发中，如果有一张表的所有业务数据均已失效不再需要，现有两种清理方式：`TRUNCATE TABLE` 和 `DELETE FROM 表名`。请从底层性能、系统资源消耗以及生产安全三个维度，说明在面试中应如何正确回答选型依据。

**解析依据**：
1. **性能与资源维度**：依据阿里巴巴开发规范，`TRUNCATE TABLE` 执行速度远快于 `DELETE FROM`，且使用的系统日志和事务资源极少。因为 `TRUNCATE TABLE` 属于 DDL 操作，会自动隐式提交，不走事务 Undo Log 备份，也不激活任何触发器；而 `DELETE FROM` 属于 DML 操作，必须为每一行数据记录回滚日志并触发相关触发器，消耗庞大的 CPU 与磁盘 I/O 资源。
2. **生产安全与工程决策维度**：尽管理论上 `TRUNCATE TABLE` 效率极高，但在真实生产环境中必须保持高度克制与谨慎。由于 `TRUNCATE TABLE` 无法通过事务回滚恢复，一旦在缺乏备份的情况下误操作，将造成不可逆的数据丢失与重大生产事故。因此在实际工程实践中，宁可容忍多消耗一定的系统资源，也应严格控制 `TRUNCATE TABLE` 的使用，优先确保数据资产的安全与容灾可撤销性。

**参考结论**：
回答应当分为“理论与机制”和“生产与工程”两层：首先讲清 `TRUNCATE TABLE` 凭借无事务备份、不走触发器的底层机制在日志开销与执行速度上显著优于 `DELETE FROM`；紧接着结合工程经验强调生产环境安全第一，指出其不可逆的致命风险，表明在无备份和未受严格管控的场景下宁用受控 DML 也不轻易执行 `TRUNCATE TABLE` 的避坑原则。

### 办公管理系统表结构实战（练习一：test01_office）

本练习围绕 `test01_office` 数据库展开，覆盖了从“白手起家”建表、基于现有表复制建表、跨库访问权限，到字段修改、不可逆删除与表重命名的全套标准操作。

#### 数据库与基础部门表的构建

首先创建独立的业务数据库并完成作用域切换：

```sql
-- 1. 创建数据库 test01_office 并指明字符集为 utf8
CREATE DATABASE IF NOT EXISTS test01_office CHARACTER SET 'utf8';

-- 切换到该数据库
USE test01_office;
```

在新建的数据库下，采用“白手起家”的方式从零搭建部门表 `dept01`：

```sql
-- 2. 创建表 dept01
CREATE TABLE IF NOT EXISTS dept01 (
    id   INT(7),
    `name` VARCHAR(25)
);
```

> **注意**：
> 1. `name` 在某些数据库客户端中可能会被高亮显示为保留字或关键字，为避免语法解析产生歧义，工程上建议用一对反引号（着重号 \`）将其包裹。
> 2. `id INT(7)` 中的数字 `7` 并不代表该整型占用 7 个字节（`INT` 无论括号内写几，在底层物理存储中永远固定占用 4 个字节），它仅代表在配置了 `ZEROFILL`（零填充）属性时的**显示宽度**。例如数值 `123` 在 `INT(7) ZEROFILL` 下展示为 `0000123`。

#### 跨数据库查询与复制建表

接下来需要根据已有表 `departments` 的数据和结构，快速生成一张新表 `dept02`。

在执行 `CREATE TABLE ... AS SELECT` 语句时，若直接编写 `FROM departments`，系统会抛出报错：

```text
ERROR 1146 (42S02): Table 'test01_office.departments' doesn't exist
```

这是因为当前会话处于 `test01_office` 命名空间下，系统默认只在该库内检索数据表。若要跨库引用源数据，必须显式指明其所属的数据库前缀 `库名.表名`：

```sql
-- 3. 将 atguigudb 库中 departments 表的数据完整导入到新表 dept02 中
CREATE TABLE dept02
AS
SELECT * 
FROM atguigudb.departments;
```

> **提示**：跨库建表能够顺利执行，是因为当前使用的是权限极高的 `root` 超级管理员账号。在生产环境中，普通业务开发账号通常受到严格的数据库实例隔离限制，如果没有跨库查询授权，该操作将被权限拦截。

#### 员工表创建与字段扩容操作

继续采用从零定义的方式创建员工表 `emp01`：

```sql
-- 4. 创建员工表 emp01
CREATE TABLE IF NOT EXISTS emp01 (
    id         INT(7),
    first_name VARCHAR(25),
    last_name  VARCHAR(25),
    dept_id    INT(7)
);
```

当业务系统发展，原有字段长度无法容纳更长的数据时，需要进行字段长度扩容。将 `last_name` 的长度由 25 字符扩增至 50 字符：

```sql
-- 5. 将列 last_name 的长度增加到 50
ALTER TABLE emp01 
MODIFY last_name VARCHAR(50);

-- 查看表结构确认修改生效
DESC emp01;
```

> **机理说明**：单纯修改字段的长度、默认值或数据类型，使用的是 `MODIFY` 关键字，语法格式为 `ALTER TABLE 表名 MODIFY 字段名 新类型 [新约束];`。

#### 全量复制、DDL 不可逆性与表重命名

使用复制机制创建 `emp02` 表，全量同步源库中的员工信息：

```sql
-- 6. 根据 atguigudb.employees 创建新表 emp02
CREATE TABLE emp02
AS
SELECT * 
FROM atguigudb.employees;
```

此时数据库中存在两张员工表。执行删除旧表 `emp01`：

```sql
-- 7. 删除表 emp01
DROP TABLE IF EXISTS emp01;
```

> **易错点**：`DROP TABLE` 属于 DDL 操作，执行时会隐式自动提交。即使在客户端手动执行 `ROLLBACK;` 命令，被删除的 `emp01` 也绝不可能回滚恢复。这就是所谓的“没有后悔药”。

随后将 `emp02` 重命名为 `emp01`。在 MySQL 中有两种实现语法：

```sql
-- 方式一：ALTER TABLE 语法
-- ALTER TABLE emp02 RENAME TO emp01;

-- 方式二：推荐语法（层级对齐，直观独立）
RENAME TABLE emp02 TO emp01;
```

推荐使用 `RENAME TABLE`，因为它与 `CREATE TABLE`、`DROP TABLE` 保持了同等语法的对称性。

#### 新增字段与删除字段的容错处理

在表结构中动态追加列，默认会被放置在整张表的最后一个位置：

```sql
-- 9. 在表 dept02 和 emp01 中分别添加新的列 test_column
ALTER TABLE emp01 
ADD test_column VARCHAR(10);

ALTER TABLE dept02 
ADD test_column VARCHAR(10);
```

若需要删除表中某个字段，必须确保该字段在当前表中确实存在。例如尝试直接执行：

```sql
ALTER TABLE emp01 DROP COLUMN dept_id;
```

如果表结构中的实际列名为 `department_id` 而非 `dept_id`，MySQL 会立刻拦截并报错：

```text
ERROR 1091 (42000): Can't DROP 'dept_id'; check that column/key exists
```

这提醒我们在执行字段级物理删除时，必须先通过 `DESC 表名;` 核实列名的准确性：

```sql
-- 10. 核实并正确删除 emp01 中的部门编号列
ALTER TABLE emp01 
DROP COLUMN department_id;

-- 验证列已被彻底移除
DESC emp01;
```

### 客户管理系统表结构实战（练习二：test02_market）

本练习依托 `test02_market` 数据库，重点强化字段相对位置的调动（`AFTER`）、字段重命名（`CHANGE`）以及定长与变长字符类型的选型思考。

#### 数据库初始化与客户表结构设计

```sql
-- 1. 创建数据库 test02_market 并设置字符集
CREATE DATABASE IF NOT EXISTS test02_market CHARACTER SET 'utf8';

-- 切换当前数据库
USE test02_market;

-- 验证数据库创建元数据
SHOW CREATE DATABASE test02_market;
```

创建基础客户表 `customers`：

```sql
-- 2. 创建 customers 表
CREATE TABLE IF NOT EXISTS customers (
    c_num     INT,
    c_name    VARCHAR(50),
    c_contact VARCHAR(50),
    c_city    VARCHAR(50),
    c_birth   DATE
);
```

> **提示**：声明日期类型时务必拼写为 `DATE`，切勿笔误写成 `DATA`。

#### 字段顺序调整与长度变更

在实际业务维护中，常有调整字段物理展示顺序的需求。将 `c_contact` 字段位置迁移到 `c_birth` 之后：

```sql
-- 3. 将 c_contact 字段移动到 c_birth 字段的后面
ALTER TABLE customers 
MODIFY c_contact VARCHAR(50) AFTER c_birth;
```

紧接着，将客户姓名 `c_name` 的存储上限拓宽到 70 字符：

```sql
-- 4. 将 c_name 字段的长度修改为 70
ALTER TABLE customers 
MODIFY c_name VARCHAR(70);
```

#### 字段重命名与定长性别字段设计

当需要修改字段名称时，必须使用 `CHANGE` 关键字，且必须完整声明新字段的数据类型：

```sql
-- 5. 将 c_contact 字段改名为 c_phone
ALTER TABLE customers 
CHANGE c_contact c_phone VARCHAR(50);
```

> **语法对比**：
> - `MODIFY`：只改类型、长度、约束或相对顺序，**不改列名**；
> - `CHANGE`：既能**修改列名**，也能同时修改列类型与约束，但**必须附带写出数据类型**。

在 `c_name` 后面新增性别字段 `c_gender`：

```sql
-- 6. 增加 c_gender 字段到 c_name 后面，类型为 CHAR(1)
ALTER TABLE customers 
ADD c_gender CHAR(1) AFTER c_name;
```

> **类型选型**：性别通常仅取“男”或“女”，只需占用单个字符空间。选用定长字符类型 `CHAR(1)` 比动态变长类型 `VARCHAR` 更加紧凑高效，无需额外记录长度偏置字节。

最后执行表重命名与冗余字段清理：

```sql
-- 7. 将表名修改为 customers_info
RENAME TABLE customers TO customers_info;

-- 8. 删除字段 c_city
ALTER TABLE customers_info 
DROP COLUMN c_city;

-- 验证最终表结构
DESC customers_info;
```

重命名之后，若继续使用旧表名 `customers` 进行查询或描述，系统将直接提示 `Table 'test02_market.customers' doesn't exist`。

### 企业组织架构表结构实战（练习三：test03_company）

本练习模拟大型企业组织架构建模，包含分支机构表 `office` 与雇员表 `employees` 的结构定制，重点分析关键字冲突规避与缩减字段长度的底层风险。

#### 机构表构建与字段命名规范反思

```sql
-- 1. 创建数据库 test03_company
CREATE DATABASE IF NOT EXISTS test03_company CHARACTER SET 'utf8';

USE test03_company;

-- 2. 创建机构表 office
CREATE TABLE IF NOT EXISTS office (
    officeCode INT,
    city       VARCHAR(30),
    address    VARCHAR(50),
    country    VARCHAR(50),
    postalCode VARCHAR(25)
);
```

> **规范提示**：题目中出现的 `officeCode`、`postalCode` 采用了 Java 中的小驼峰命名法。按照阿里巴巴 MySQL 规约，数据库字段应严格采用全小写加下划线风格（如 `office_code`、`postal_code`）。工程实战中如遇到历史包袱或特定接口要求驼峰命名，编写 SQL 时需格外注意大小写敏感性问题。

#### 员工表创建与关键字转义保护

在构建 `employees` 表时，字段包含岗位代码 `code`：

```sql
-- 3. 创建 employees 表
CREATE TABLE IF NOT EXISTS employees (
    emp_id     INT,
    last_name  VARCHAR(50),
    first_name VARCHAR(50),
    mobile     VARCHAR(25),
    `code`     INT,
    job_title  VARCHAR(50),
    birth      DATE,
    note       VARCHAR(255),
    sex        VARCHAR(5)
);
```

> **易错点**：`code` 在 SQL 语法高亮中往往会变为特殊色彩，属于潜在的关键字或预留标识。在表定义与后续 DML 中，必须用一对反引号包裹（\`code\`），彻底消除词法解析阶段的歧义。

#### 字段调序、缩短长度的边界陷阱与改名

将 `mobile` 字段调整到 `code` 后面，同时将其声明长度缩短为 20 字符：

```sql
-- 4. 将 mobile 字段修改到 code 字段后面，长度设为 20
ALTER TABLE employees 
MODIFY mobile VARCHAR(20) AFTER `code`;
```

> **深度机制与边界陷阱**：
> 假设在执行该 `MODIFY` 语句前，表中已经插入了真实业务数据，且某些员工的手机号码加上国际区号达到了 22 或 23 位字符长度。此时强行执行缩短长度为 20 的 DDL 语句，**MySQL 会直接拒绝执行并报错终止**！
> 这是数据库的自我数据保护机制。系统绝不允许因为表结构的变更而悄无声息地截断丢失用户现存的合法数据。

将出生日期字段 `birth` 重命名为更规范的 `birthday`：

```sql
-- 5. 将 birth 字段改名为 birthday
ALTER TABLE employees 
CHANGE birth birthday DATE;
```

#### 定长改造、字段裁剪与最终重命名

针对原有定义为 `VARCHAR(5)` 的性别字段 `sex` 进行定长化重构：

```sql
-- 6. 修改 sex 字段类型为 CHAR(1)
ALTER TABLE employees 
MODIFY sex CHAR(1);
```

```text
+--------------------------------------------------------------------+
|                   CHAR(M) 与 VARCHAR(M) 存储机理对比               |
+--------------------------------------------------------------------+

 场景：存储单个字符 '男' (UTF-8 编码下占 3 字节)

 CHAR(1) 定长存储：
 +-----------------------------------+
 | 数据内容: [ '男' ]                | -> 严格分配定长空间，无需长度前缀
 +-----------------------------------+

 VARCHAR(5) 变长存储：
 +-----------------------------------+
 | 长度偏置: [ 0x03 ] | 数据: [ '男' ]| -> 必须额外耗费 1~2 字节维护长度列表
 +-----------------------------------+
+--------------------------------------------------------------------+
```
> *读图说明：定长类型直接通过固定物理偏移定位数据，消除了长度头信息的解析与维护开销；在值长度完全固定的枚举类字段（如性别、状态码、MD5 哈希等）场景下，优先选用 CHAR。*

完成剩余的字段清理、特长列追加与表重命名：

```sql
-- 7. 删除字段 note
ALTER TABLE employees 
DROP COLUMN note;

-- 8. 增加特长/爱好字段 favourite_activity
ALTER TABLE employees 
ADD favourite_activity VARCHAR(100);

-- 9. 将表名重命名为 employees_info
RENAME TABLE employees TO employees_info;

-- 验证最终结构
DESC employees_info;
```

### DDL 核心语法归纳与速查指南

通过上述三大综合案例的实操演练，可以将日常使用频率最高的数据定义语言（DDL）语法骨架归纳为如下拓扑体系：

```text
+--------------------------------------------------------------------+
|                         DDL 常用操作指令体系                       |
+--------------------------------------------------------------------+
 [ 数据库级别 ]
   CREATE DATABASE [IF NOT EXISTS] 库名 [CHARACTER SET '字符集'];
   DROP DATABASE [IF EXISTS] 库名;

 [ 数据表级别 ]
   创建：CREATE TABLE [IF NOT EXISTS] 表名 ( 字段名 类型 [约束], ... );
   复制：CREATE TABLE 表名 AS SELECT ... FROM 源表;
   删除：DROP TABLE [IF EXISTS] 表名;
   重名：RENAME TABLE 旧表名 TO 新表名;

 [ 字段修改级别 (ALTER TABLE 表名 ...) ]
   新增列：ADD 字段名 类型 [FIRST | AFTER 参照列];
   改属性：MODIFY 字段名 新类型 [FIRST | AFTER 参照列];
   改列名：CHANGE 旧列名 新列名 新类型 [FIRST | AFTER 参照列];
   删除列：DROP COLUMN 字段名;
+--------------------------------------------------------------------+
```
> *读图说明：对表本身的变更统一优先使用独立的动词命令；对表内部字段结构的改动，统一以 ALTER TABLE 作为入口驱动。*

## 55-DML之添加数据
> 对应分集：P55 | 原始标题：《55-DML之添加数据》

在完成了数据库与数据表结构的定义（DDL）之后，接下来的核心任务就是对表中的数据进行流动管理。数据操作语言（DML，Data Manipulation Language）涵盖了数据的增加（INSERT）、删除（DELETE）和修改（UPDATE）。

广义上讲，增、删、改本质上都是对表中存储的数据行进行物理或逻辑层面的“变更”（Update）。相比于语法层层嵌套、涉及复杂多表关联与聚合筛选的查询语言（DQL），DML 的基本语法相对规整直观。但在实际开发与高并发生产环境下，数据插入操作不仅涉及字段与值的映射对齐，更关乎隐式类型转换、批量网络 I/O 吞吐性能，以及字段长度缩窄时潜藏的数据截断风险。

---

### 数据插入机制的前置准备与实验表设计

为了深入拆解不同的数据插入方式及其边界条件，首先在 `atguigudb` 数据库下构建一张纯净的测试表 `emp1`。在真实企业开发中，尽量不要直接在核心生产业务表上做语法验证，避免脏数据污染现有业务。

```sql
-- 切换到测试数据库
USE atguigudb;

-- 创建数据插入测试表 emp1
CREATE TABLE IF NOT EXISTS emp1 (
    id        INT,
    `name`    VARCHAR(15),
    hire_date DATE,
    salary    DOUBLE(10, 2)
);

-- 查看表结构与列声明顺序
DESC emp1;
```

此时通过 `DESC emp1;` 可以确认字段的物理声明顺序为：`id` -> `name` -> `hire_date` -> `salary`。

> **提示**：
> 1. 在薪资、交易金额等敏感金融类字段的定义上，阿里巴巴等大厂规范通常强制要求声明为定点数类型 `DECIMAL(M, D)`，以杜绝浮点数在底层二进制存储时产生的精度丢失问题。此处由于尚未正式展开数据类型高级精讲，先使用浮点类型 `DOUBLE(10, 2)` 进行语法教学。
> 2. 数据在执行插入时，其值列表的填充逻辑与表结构在元数据中的声明顺序有着强烈的制约关系。

此时执行全表查询确认初始状态为空：

```sql
SELECT * FROM emp1;
-- 结果为 Empty set
```

### 方式一：基于 VALUES 关键字的行记录插入

基于 `VALUES` 关键字的插入是开发中最常用的模式，根据字段声明的精细程度与批量程度，可细分为四种工程实践形式。

#### 隐式全字段插入（不指明字段列表）

最精简的插入写法是省略表名后面的字段声明括号，直接跟上 `VALUES` 关键字并传入数据元组：

```sql
-- 方式 1.1：不指明插入字段
INSERT INTO emp1
VALUES (1, 'Tom', '2000-12-21', 3400);
```

执行后查询表数据，整行记录被正确写入。其中浮点型字段 `salary` 传入整数 `3400`，数据库引擎内部会自动进行隐式类型转换，转化为 `3400.00` 存入。

但是，这种省去字段名的语法存在极其严苛的物理限制：

> **易错点**：未指明插入字段时，`VALUES` 小括号中传入的值，**其个数、先后顺序、数据类型必须与数据表中定义字段的物理顺序百分之百严格一致**。

假设在录入数据时，开发者混淆了字段顺序，写成了如下代码：

```sql
-- 错误示范：顺序错位导致类型不匹配
INSERT INTO emp1
VALUES (2, 3400, '2000-12-21', 'Jerry');
```

执行该语句后，MySQL 将直接拒绝写入并抛出异常：

```text
ERROR 1265 (01000): Data truncated for column 'salary' at row 1
```

**错误机理剖析**：
- 第二个位置期望是 `name VARCHAR(15)`，传入整数 `3400` 时，系统尚且能将其隐式转换为字符串 `'3400'` 容忍处理；
- 但第四个位置在表结构中严格限定为浮点型 `salary DOUBLE(10, 2)`，传入字符串 `'Jerry'` 根本无法解析为合法的数值，类型校验彻底击穿，导致整条语句被拦截。

在实际业务中，系统的数据表结构往往拥有数十个字段（如系统核心员工表往往包含 11 个甚至更多字段），单纯依靠记忆物理列顺序去组装 SQL，极易出现错位风险，代码可维护性极差。因此在工程开发中**强烈不推荐这种写法**。

#### 显式指定字段插入（推荐的标准写法）

为了彻底解耦表物理结构的顺序制约，工业级 SQL 普遍采用显式声明字段列表的模式：

```sql
-- 方式 1.2：显式指明插入字段（字段顺序可完全自定义）
INSERT INTO emp1 (id, hire_date, salary, `name`)
VALUES (2, '1999-09-09', 4000.00, 'Jerry');
```

在表名后面显式罗列需要插入的目标字段，`VALUES` 列表中的数据项只需要与前面小括号中定义的列名保持**一对一的位置绑定**即可，完全不需要理会底层数据表中 `name` 和 `hire_date` 谁先谁后。这种写法语法语义极其清晰，后期即使表结构通过 `ALTER TABLE` 调整了字段的物理顺序，现有的应用层持久化 SQL 也不会受到任何干扰。

#### 部分字段缺省插入与默认值约束机理

在很多业务场景中，某些字段在新建记录时并不具备初始值，此时可以在字段列表中仅指明部分列：

```sql
-- 方式 1.3：仅插入部分字段
INSERT INTO emp1 (id, salary, `name`)
VALUES (3, 4500.00, 'shk');
```

执行后查看数据结果：

```text
+------+------+------------+---------+
| id   | name | hire_date  | salary  |
+------+------+------------+---------+
|    1 | Tom  | 2000-12-21 | 3400.00 |
|    2 | Jerry| 1999-09-09 | 4000.00 |
|    3 | shk  | NULL       | 4500.00 |
+------+------+------------+---------+
```

可以看到，未被显式指明赋值的字段 `hire_date` 被数据库自动赋予了默认值 `NULL`。

> **约束机制预告**：
> 当前表之所以允许这样插入，是因为 `hire_date` 字段并没有显式声明 `NOT NULL`（非空）约束。
> 在后续的约束设计中，如果某个字段被声明为 `NOT NULL` 且没有预置 `DEFAULT` 默认值，在执行 `INSERT` 时一旦遗漏该字段，MySQL 将直接抛出 `Field 'xxx' doesn't have a default value` 错误中断插入。

#### 单语句批量多行插入（性能最优实践）

如果需要向表中同时插入多行记录，初学者往往会采用编写多条独立 `INSERT INTO` 语句的方式逐行执行：

```sql
-- 低效方式：多条独立语句重复提交
INSERT INTO emp1(id, `name`, salary) VALUES (4, '油胜男', 5000);
INSERT INTO emp1(id, `name`, salary) VALUES (5, '张俊杰', 5500);
```

这种逐条调用的方式在底层会引发多次网络往返传输（Round-Trip）、多次 SQL 解析与权限校验，并且每条语句都需要单独经历一次事务提交与日志持久化过程。

优化的解决方案是使用一条 `INSERT` 语句，通过逗号分隔拼接多个值元组：

```sql
-- 方式 1.4：单条 INSERT 语句批量插入多行记录
INSERT INTO emp1 (id, `name`, salary)
VALUES 
    (4, '油胜男', 5000.00),
    (5, '张俊杰', 5500.00);
```

执行后，客户端控制台明确提示：`Query OK, 2 rows affected`。

```text
+--------------------------------------------------------------------+
|               逐条插入 与 批量单语句插入 执行性能对比               |
+--------------------------------------------------------------------+

 模式 A：独立逐条执行 (N 次循环)
 Client                   MySQL Server
   | --- INSERT Row 1 ---> | (语法解析 -> 事务开销 -> 写入 Redo/Undo)
   | <------ OK ---------  |
   | --- INSERT Row 2 ---> | (语法解析 -> 事务开销 -> 写入 Redo/Undo)
   | <------ OK ---------  |
   开销：N 次网络 I/O，N 次上下文切换，N 次事务日志开销。

 模式 B：单语句批量 VALUES (推荐)
 Client                   MySQL Server
   | - INSERT (Row1,Row2)- | (单次网络传输 -> 一次性批量写入 -> 统一提交)
   | <------ OK ---------  |
   开销：1 次网络 I/O，单次批量合并写入，吞吐量成倍提升。
+--------------------------------------------------------------------+
```
> *读图说明：当系统已获取到多条待持久化记录时，合并为一个 VALUES 列表批量写入，能大幅减轻数据库服务器的连接与日志压力。*

> **规范细节**：在关键字书写上，标准关键字是 `VALUES`。尽管在 MySQL 某些版本中写单数形式的 `VALUE` 也能够执行通过，但它属于非标准扩展语法，生产环境中应坚决遵循规范统一书写 `VALUES`。

### 方式二：基于查询结果集导入数据（INSERT INTO ... SELECT）

第一种方式适用于用户前端注册、生成单笔订单等实时单点录入的业务场景。但在数据仓库抽取、历史数据归档或大批量跨表迁移时，数据往往已经存在于系统的某张表内。此时可以通过 `INSERT INTO ... SELECT` 语法，实现数据的高效批量转储。

#### 语法结构与字段匹配规则

该语法类似于通过查询结果建表的 `CREATE TABLE ... AS SELECT`，但存在一个决定性前提：**目标表必须在物理上已经存在**。

```sql
-- 语法格式：将 employees 表中特定部门的数据导入到 emp1 中
INSERT INTO emp1 (id, `name`, salary, hire_date)
SELECT employee_id, last_name, salary, hire_date
FROM employees
WHERE department_id IN (60, 70);
```

> **核心原则**：
> 1. `INSERT INTO` 后面声明的目标字段数量，必须与 `SELECT` 子句中查询投影出的列数量严格对齐；
> 2. 两者之间按**从左到右的位置顺序进行物理映射**，而非根据列名的命名文本匹配；
> 3. 对应位置上的数据类型必须兼容，支持合法的类型隐式转换。

#### 字段长度不对称时的底层行为与“搬家”机理

在执行上述跨表抽取时，如果将目标表 `emp1` 与源表 `employees` 的底层字段元数据进行对比，会发现一个极度耐人寻味的现象：

```sql
DESC emp1;
DESC employees;
```

```text
+--------------------------------------------------------------------+
|                emp1 与 employees 关键字段元数据对比                |
+-------------------+-----------------------+------------------------+
| 字段含义          | 目标表 emp1           | 源表 employees         |
+-------------------+-----------------------+------------------------+
| 员工编号          | id INT                | employee_id INT(6)     |
| 姓名存储          | name VARCHAR(15)      | last_name VARCHAR(25)  |
| 入职日期          | hire_date DATE        | hire_date DATE         |
| 薪资设定          | salary DOUBLE(10, 2)  | salary DOUBLE(8, 2)    |
+-------------------+-----------------------+------------------------+
```

分析对比可以发现：
- 薪资字段 `salary`：目标表是 `(10, 2)`，源表是 `(8, 2)`，目标表的容量大于源表；
- 姓名存储 `name`：**目标表的长度仅有 15 字符，而源表的定义长度高达 25 字符！**

然而在实际执行上述 `INSERT INTO ... SELECT` 时，语句却没有任何报错，顺利完成了 6 条记录的插入。

这是为什么？

> **底层机理解析**：
> 数据能够成功插入，并不是因为数据库对字段长度的限制失效了，而是**完全取决于源表中被选中的那 6 行记录的实际内容**。
> 在 `department_id IN (60, 70)` 的这批员工中，所有人的 `last_name` 字符串长度恰好都没有超过 15 个字符。因为物理数据长度在 15 字符的安全阈值以内，所以写入顺利通过。
> 
> 但如果源表中存在一个员工的名字长度为 18 字符（介于 15 与 25 之间），在执行这条 SQL 时，系统会立刻判定数据超宽，直接触发报错阻止写入！

这里可以借用生动的**搬家比喻**来理解数据类型的容纳机制：
- **小范围向大范围迁移（如 salary 从 8 位搬到 10 位）**：类似于一个人原本住在一间 15 平米的紧凑单间里，现在搬进了一套宽敞的大别墅，原先的所有家具和家当搬进去绰绰有余，不会造成任何空间冲突或损失；
- **大范围向小范围迁移（如 name 从 25 位压缩到 15 位）**：类似于原本住在大别墅里、家当堆得满满当当，现在家道中落必须搬进一间狭窄的小单间。如果原先的家当刚好很少，侥幸还能塞进去；但只要大件家具稍微多一点，小单间就根本放不下，强行塞入必然面临抛弃家具（精度损失/数据截断）或者直接被房东拒之门外（报错崩溃）。

```text
+--------------------------------------------------------------------+
|               字段长度不对称时的“空间搬家”风险模型                 |
+--------------------------------------------------------------------+

 场景 1：源表范围较小 -> 目标表范围较大 (小单间 -> 大别墅)
 源数据: [ 123456.78 ]  (DOUBLE 8,2)
            |
            v
 目标槽: [ 000123456.78 ] (DOUBLE 10,2)  -> 绝对安全，天然包容

 场景 2：源表声明偏大 -> 目标表声明偏小 (大别墅 -> 小单间)
 临界数据 A: 'King' (4 字符)       -> 能塞进 VARCHAR(15)，侥幸成功
 临界数据 B: 'Alexander-Hunold' (16字符)
            |
            v
 目标槽: [ VARCHAR(15) 限制 ]    -> 空间溢出！直接拦截报错！
+--------------------------------------------------------------------+
```
> *读图说明：目标字段绝不能仅仅依靠“当前数据碰巧未超长”的侥幸去运行，架构设计上必须保持目标字段容量大于或等于源字段。*

> **工程准则**：
> 在利用查询结果向现有表注入数据时，必须提前校验两表的元数据字典。**目标表中接收字段的定义长度与取值范围，严禁低于源表对应查询字段的声明范围**。如果发现目标表字段范围偏小，必须先通过 `ALTER TABLE ... MODIFY` 将字段扩容，确保生产数据管道的绝对稳定性。

### 本讲提到的题目

#### 题目一：不指明字段列表时的插入异常排查题

**题干描述**：
某系统有一张表 `emp1`，其字段顺序为 `(id INT, name VARCHAR(15), hire_date DATE, salary DOUBLE(10, 2))`。执行如下 SQL 时系统报错：
```sql
INSERT INTO emp1 VALUES (2, 3400, '2000-12-21', 'Jerry');
```
请指出该语句的具体报错原因及规范的修改方案。

**解析依据**：
1. **原因分析**：未显式指明字段列表时，`VALUES` 后面的值必须按表物理声明顺序严格匹配。第四个位置为浮点型 `salary`，而传入的值为字符型 `'Jerry'`，类型无法隐式转换，触发 `Data truncated for column 'salary'` 错误。
2. **修改方案**：显式声明插入字段列表，解除物理位置顺序绑定：
   ```sql
   INSERT INTO emp1 (id, salary, hire_date, `name`)
   VALUES (2, 3400, '2000-12-21', 'Jerry');
   ```

#### 题目二：基于查询结果导入数据时的字段长度安全辨析题

**题干描述**：
目标表 `emp1` 中的 `name` 字段类型为 `VARCHAR(15)`，源表 `employees` 中的 `last_name` 字段类型为 `VARCHAR(25)`。通过如下语句导入数据成功且未发生报错：
```sql
INSERT INTO emp1 (id, `name`, salary, hire_date)
SELECT employee_id, last_name, salary, hire_date
FROM employees
WHERE department_id = 60;
```
1. 为什么源字段定义长度大于目标字段定义长度时，仍然能够成功执行？
2. 这种操作在生产环境中存在什么隐患？工程上应如何防范？

**解析依据**：
1. **成功机理**：SQL 执行期只校验实际写入数据的真实字符长度。在 `department_id = 60` 的筛选结果中，所有员工姓名的实际字符长度均小于或等于 15，因此未触发超长校验。
2. **生产隐患与防范措施**：一旦源表中后续存在实际长度介于 16 至 25 之间的记录，导入逻辑将直接中断报错（或在特定 SQL 模式下被截断）。在工程上，目标表的存储字段长度原则上必须大于或等于源表定义，应在导入前执行 `ALTER TABLE emp1 MODIFY name VARCHAR(25);` 完成扩容。

## 56-DML之更新删除操作_MySQL8新特性之计算列
> 对应分集：P56 | 原始标题：《56-DML之更新删除操作_MySQL8新特性之计算列》

在完成了数据的插入操作之后，数据在数据库中的生命周期便进入了频繁的流转与维护阶段。在业务系统的日常运转中，修改现有记录的状态、清理过期或无效的行数据是极高频的操作。数据操作语言（DML）中的 `UPDATE` 与 `DELETE` 承担了这一核心职责。

然而，修改与删除并非孤立的语法执行：不带过滤条件的更新与删除极易造成全表灾难性覆盖；表与表之间建立的完整性约束（如外键约束）会随时拦截破坏参照关系的非法变更；而在数据读取端，为了规避反复临时进行字段运算所带来的巨大 CPU 开销，MySQL 8.0 推出了全新的**计算列（Generated Column）**特性。

---

### 数据更新操作（UPDATE）的语法与工程防线

更新数据，顾名思义就是对表中已经存在的某行或多行记录的字段值进行修改。例如将 60 号部门的员工调整到 30 号部门，或者将离职员工的在职状态修改为禁用。

#### 基础语法与核心防线（WHERE 子句）

数据更新的标准语法格式如下：

```sql
UPDATE 表名
SET 字段名1 = 值1, 字段名2 = 值2, ...
[WHERE 过滤条件];
```

在日常执行 `UPDATE` 操作时，最核心的工程铁律就是：**通常必须显式指定 `WHERE` 过滤条件**。

> **易错点**：如果在执行 `UPDATE` 时漏掉了 `WHERE` 子句，SQL 语法本身并不会报错，但它会以**全表批量修改**的方式，将整张表中所有记录的对应字段瞬间刷新为同一个值！

以测试表 `emp1` 中的数据为例，为编号 `id = 5`（张俊杰）补全入职日期：

```sql
-- 针对特定记录补全入职日期
UPDATE emp1
SET hire_date = CURDATE()
WHERE id = 5;

-- 查询验证修改结果
SELECT * FROM emp1 WHERE id = 5;
```

如果上述语句不小心写成了 `UPDATE emp1 SET hire_date = CURDATE();`，全表所有员工的入职时间将被全部抹平为今天，在生产环境中往往直接导致历史工龄与薪资核算体系瘫痪。

#### 多字段协同修改与动态表达式更新

在实际场景中，一次更新往往涉及多个维度的变更。多个字段的赋值在 `SET` 子句中通过**逗号**进行连接：

```sql
-- 同时修改特定员工的多个字段（更新入职日期并上调薪资）
UPDATE emp1
SET hire_date = CURDATE(), salary = 6000.00
WHERE id = 4;
```

此外，更新的值不仅可以是固定常数，还可以是基于原有字段值的数学运算表达式，并结合高级模糊匹配实现特定群体的批量调薪：

```sql
-- 将表中姓名包含字母 'a' 的所有员工薪资上调 20%
UPDATE emp1
SET salary = salary * 1.2
WHERE `name` LIKE '%a%';
```

这种写法展示了 `UPDATE` 天然支持批量运算的特质。只要 `WHERE` 命中的结果集包含多行，MySQL 就会自动对所有命中行统一执行表达式重算。

#### 外键约束对更新操作的物理拦截

在执行更新时，并非所有的语法合规语句都能成功执行。很多时候，数据库底层的**完整性约束（Constraints）**会直接阻断更新。

在真实的 HR 数据库中，员工表 `employees` 与部门表 `departments` 存在主外键关联。尝试将 `employee_id = 102` 的员工的部门编号修改为一个不存在的部门（如 10000 号部门）：

```sql
UPDATE employees
SET department_id = 10000
WHERE employee_id = 102;
```

执行该语句后，系统会立即拦截并抛出错误：

```text
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`atguigudb`.`employees`, CONSTRAINT `emp_dept_fk` FOREIGN KEY (`department_id`) REFERENCES `departments` (`department_id`))
```

```text
+--------------------------------------------------------------------+
|               外键约束拦截非法 UPDATE 操作机理                      |
+--------------------------------------------------------------------+

 主表 (Parent Table): departments
 +---------------+----------------------+
 | department_id | department_name      |
 +---------------+----------------------+
 | 10, 20, ..., 110 (最大编号仅为 110)   |
 +---------------+----------------------+
         ^
         | 参照完整性校验：主表中根本不存在 department_id = 10000 的记录！
         |
 子表 (Child Table): employees
 +---------------+----------------------+
 | employee_id   | department_id        |
 +---------------+----------------------+
 | 102           | 试图变更为 [ 10000 ] |  -> 校验失败！触发 ERROR 1452 拦截！
 +---------------+----------------------+
+--------------------------------------------------------------------+
```
> *读图说明：外键约束强制要求子表中外键列的值必须在主表的主键范围内真实存在；试图将子表字段修改为主表中没有的非法值，属于破坏参照完整性，会被数据库直接拒止。*

### 数据删除操作（DELETE）与级联风险控制

数据删除属于不可逆的高危物理操作，它将满足条件的数据行从存储引擎的数据页中剔除。

#### DELETE 基础语法与逐行删除

删除数据的语法结构为：

```sql
DELETE FROM 表名 [WHERE 过滤条件];
```

针对 `emp1` 表执行定点删除：

```sql
-- 删除编号为 1 的记录
DELETE FROM emp1
WHERE id = 1;

-- 验证删除效果
SELECT * FROM emp1;
```

与 `UPDATE` 类似，若遗漏 `WHERE` 条件，`DELETE FROM 表名;` 将直接清空整张表的所有数据。虽然在未提交事务前可以通过日志回滚，但其高昂的日志与系统资源消耗依然不可忽视。

#### 外键级联拦截与“父项引用保护”

修改子表受外键制约，反过来，**删除主表记录同样受到严密的外键级联保护**。

例如，在部门表 `departments` 中，50 号部门（Shipping 部门）下挂载了大量的真实在职员工。此时尝试在主表中直接抹去 50 号部门：

```sql
DELETE FROM departments
WHERE department_id = 50;
```

此时控制台会抛出经典的父表外键冲突错误：

```text
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`atguigudb`.`employees`, CONSTRAINT `emp_dept_fk` FOREIGN KEY (`department_id`) REFERENCES `departments` (`department_id`))
```

**底层机制剖析**：
- `departments` 是被依赖的父表（Parent row），`employees` 是依赖它的子表（Child row）；
- 如果数据库允许直接删除主表中的 50 号部门，那么子表中隶属于 50 号部门的几十名员工，其 `department_id` 字段将在业务系统上彻底失去挂靠实体，沦为“悬空孤儿数据”（Orphan Data）；
- 因此，数据库外键保护机制严格禁止直接删除正在被子表引用的父行记录。若要强制删除，必须预先将子表中所有关联员工的部门置空或迁移，或者在建表时显式配置级联删除（`ON DELETE CASCADE`）。

### MySQL 8.0 新特性：计算列（Generated Column）

为了在高并发查询场景下彻底榨干系统性能，避免在大数据量检索时重复进行耗费 CPU 的动态行计算，MySQL 8.0 正式引入了**计算列（Generated Column，又称虚拟列 Virtual Column）**。

#### 传统动态计算的性能瓶颈

在传统数据库设计中，如果数据表中存在列 $A$ 与列 $B$，而业务系统经常需要获取 $A + B$ 的结果（例如商品单价乘以购买数量得出订单总金额），通常有两种处理途径：
1. **查询时动态计算**：在 SQL 中编写 `SELECT a, b, (a + b) AS c FROM 表名;`。
   - *弊端*：当单表数据量达到数十万乃至数百万行时，每一行数据都必须被载入 CPU 执行一次加法运算。几百万次数学计算会产生巨大的 CPU 算力开销，显著拉长查询响应时间。
2. **应用层预计算并持久化额外字段**：在表中额外设计一个物理字段 `c`，每次插入或更新时由应用层算好存入。
   - *弊端*：一旦业务代码遗漏或并发更新不同步，极易引发字段 $A, B$ 与字段 $C$ 之间的数据不一致。

#### 计算列的定义与核心语法

MySQL 8.0 的计算列完美化解了这一矛盾。

> **定义**：计算列是指表中某一列的值无需人工或应用层显式赋值，而是由该表中其他物理列通过预先定义的计算表达式自动推导并维护的特殊列。

在定义表结构时，使用 `GENERATED ALWAYS AS (表达式) VIRTUAL` 进行声明：

```sql
-- 切换到测试数据库
USE atguigudb;

-- 创建包含计算列的数据表 test1
CREATE TABLE IF NOT EXISTS test1 (
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b) VIRTUAL
);

-- 验证表元数据
DESC test1;
```

关键技术关键字解析：
- `GENERATED ALWAYS AS (...)`：强制声明该列由后续小括号内的表达式生成；
- `VIRTUAL`：表示该列为**虚拟计算列**。该列的值不会作为物理数据落盘存储到磁盘数据页中，而是仅将表达式记录在数据字典中；读取该列时由存储引擎在内存中高效解算；
- *单词记忆*：`VIRTUAL` 意为“虚拟的”，在计算机专业词汇中极为常见，如 **Virtual Machine（虚拟机）**、**Virtual Reality（虚拟现实，VR）**。

#### 自动化协同联动实操验证

为了检验计算列的实际表现，执行数据插入与动态更新验证：

##### 步骤一：插入基础数据（省略计算列）

在向 `test1` 表插入数据时，明确只向基础字段 `a` 和 `b` 传值，完全忽略计算列 `c`：

```sql
INSERT INTO test1 (a, b)
VALUES (10, 20);

-- 查看全表数据
SELECT * FROM test1;
```

查询输出结果如下：

```text
+------+------+------+
| a    | b    | c    |
+------+------+------+
|   10 |   20 |   30 |
+------+------+------+
```

在完全没有显式对 `c` 赋值的情况下，字段 `c` 自动呈现为 `10 + 20 = 30` 的计算结果。

##### 步骤二：更新底层物理列观察联动效应

现在通过 `UPDATE` 语句调整基础字段 `a` 的数值：

```sql
UPDATE test1
SET a = 100;

-- 再次查询表数据
SELECT * FROM test1;
```

查询输出结果如下：

```text
+------+------+------+
| a    | b    | c    |
+------+------+------+
|  100 |   20 |  120 |
+------+------+------+
```

可以看到，随着物理列 `a` 的变更，计算列 `c` 的值立即同步且原子性地重算为 `100 + 20 = 120`。应用层无需编写任何冗余维护代码，彻底消除了数据不一致的隐患。在大型报表、复合统计、哈希索引生成等场景下，合理使用计算列能极大精简业务逻辑并提升数据库检索性能。

### 三种数据插入模式的工程实践（DML 写入）

向表中灌入数据时，根据业务场景的不同，通常有三种写入策略：省略字段列表的全列插入、指明字段名称的精细插入，以及一条语句批量录入多条元组。

```text
+--------------------------------------------------------------------------+
| 写入方式对比                                                             |
|                                                                          |
| 1. 不指定列名: INSERT INTO books VALUES (...)                             |
|    -> 强依赖表结构物理声明顺序，结构微调即破坏脚本兼容性                  |
|                                                                          |
| 2. 指定列名:   INSERT INTO books(col1, col2, ...) VALUES (...)          |
|    -> 字段与值一一显式映射，具名安全，解耦物理定义顺序（推荐）            |
|                                                                          |
| 3. 批量插入:   INSERT INTO books(cols...) VALUES (...), (...), (...)     |
|    -> 减少网络往返与事务提交开销，批量录入效率最高                        |
+--------------------------------------------------------------------------+
```
上图总结了单行全列写入、单行具名写入以及批量多值写入的核心机制与工程取舍。

#### 隐式依赖全字段顺序的插入

不显式指明字段名时，`VALUES` 列表中的数据项数量、数据类型与物理位置必须与建表时元数据的声明顺序绝对一致。

```sql
-- 方式一：不指定字段名称插入第 1 条记录
INSERT INTO books
VALUES (1, 'Tal of two cities', 'Charles Dickens', 23, '1995', 'novel', 11);
```

> **注意**：年份类型 `YEAR` 既可以传入四位纯数字，也可以传入单引号包裹的合规年份字符串。

#### 显式指定字段名称的单行插入

显式罗列目标列名是商业级代码与生产脚本的首选方案。哪怕后续表结构执行了 `ALTER TABLE` 增加了非空默认值列，也不会破坏已有的插入逻辑。

```sql
-- 方式二：显式指定字段列表插入第 2 条记录（强烈推荐）
INSERT INTO books (id, `name`, `authors`, price, pubdate, note, num)
VALUES (2, 'Emma', 'Jane Austen', 35, '1993', 'joke', 22);
```

#### 多元组复合批量插入

当面临大量基础数据初始灌库时，一条一条发送 `INSERT` 会引发频繁的网络 I/O 与日志落盘开销。利用多值元组一次性提交能够极大提升写入吞吐量。

```sql
-- 方式三：单条语句批量插入第 3 至第 7 条记录
INSERT INTO books (id, `name`, `authors`, price, pubdate, note, num)
VALUES 
(3, 'Story of Success', 'Malcolm Gladwell', 271, '2008', 'novel', 0),
(4, 'Jane Eyre', 'Charlotte Bronte', 65, '1964', 'novel', 0),
(5, 'Love Talk', 'Bonnie Smith', 285, '2005', 'drama', 10),
(6, 'Legend of Sleepy Hollow', 'Washington Irving', 100, '2008', 'novel', 55),
(7, 'The Battle of the Books', 'Jonathan Swift', 12, '1995', 'joke', 45);
```

写入完成后，执行全表检索核验 7 条初始基准数据：

```sql
SELECT * FROM books;
```

### 数据更新与物理清理规范（DML 变更）

在执行修改与删除操作前，必须养成前置防护意识。未加 `WHERE` 条件的更新或删除会导致整张表的灾难性覆写或清空。

> **提示**：在实际生产运维中，执行 `UPDATE` 或 `DELETE` 之前，务必先用相同的筛选条件执行一次 `SELECT * FROM ... WHERE ...`，看清楚受影响的行到底是不是目标记录；操作完成后，再查一次核验变更结果。

#### 基于分类条件的批量价格上调

将说明字段 `note` 为小说（`'novel'`）的书籍价格统一上浮 5 元：

```sql
-- 将小说类图书价格增加 5 元
UPDATE books 
SET price = price + 5 
WHERE note = 'novel';
```

该操作会同时命中 `id` 为 1、3、4、6 的书籍。例如 `id=1` 的原价格 23 元将调整为 28 元。

#### 基于唯一标识的多字段联动更新

将书名为 `'Emma'` 的图书价格修正为 40 元，同时将其分类分类修改为 `'drama'`：

```sql
-- 多字段同时修改，字段之间以逗号分隔
UPDATE books 
SET price = 40, note = 'drama' 
WHERE `name` = 'Emma';
```

#### 零库存数据的物理删除与数据环境复原

清理库存量 `num` 为 0 的售罄或失效记录：

```sql
-- 删除库存为 0 的图书记录
DELETE FROM books 
WHERE num = 0;
```

此操作将物理清除 Malcolm Gladwell 的《Story of Success》（`id=3`）与 Charlotte Bronte 的《Jane Eyre》（`id=4`）。为了不影响后续 17 道统计分析题目对全量图书特征的验证，演练现场需将因测试删除而被剔除的数据补回表内，保持全表 7 本书的初始基线。

### 业务数据多维统计与检索进阶（17 道典型需求）

数据只有被高维度、多视角地挖掘与重组，才能支撑业务决策。从模糊字符定位到多级聚合分析，以下题目涵盖了企业日常报表查询的核心模式。

#### 模糊匹配与字符包含判断

**需求 7：统计书名中包含字母 'a' 的所有图书。**

```sql
SELECT * 
FROM books 
WHERE `name` LIKE '%a%';
```
> **解析**：标准 SQL 中通配符 `%` 代表匹配零个、一个或多个任意字符。在当前 7 本书中，除《Jane Eyre》外的其余 6 本书名均包含字母 `'a'`。

**需求 8：统计书名中包含 'a' 字母的图书总数量与其库存总量。**

```sql
SELECT COUNT(*) AS book_count, SUM(num) AS total_num 
FROM books 
WHERE `name` LIKE '%a%';
```
> **解析**：`COUNT(*)` 负责统计符合过滤条件的有效行数（返回 6），而 `SUM(num)` 则汇总这 6 本书对应的库存数值列，合计得出总库存量 103 本。

#### 条件筛选与多列层级排序

**需求 9：找出分类为小说（'novel'）的图书，并按照价格从高到低降序排列。**

```sql
SELECT `name`, note, price 
FROM books 
WHERE note = 'novel' 
ORDER BY price DESC;
```
> **解析**：`WHERE` 负责筛选行集，`ORDER BY` 负责在结果集返回前执行排序。降序必须显式指定 `DESC` 关键字。

**需求 10：查询所有图书信息，按库存量降序排列；若库存量相同，则按分类（note）升序排列。**

```sql
SELECT * 
FROM books 
ORDER BY num DESC, note ASC;
```
> **解析**：二级复合排序机制。当排在第一优先级的 `num` 出现并列相同值时，引擎才会启用逗号后第二优先级的 `note` 字段执行升序（`ASC`）对比。

#### 基础分组与聚合过滤（HAVING 子句）

**需求 11：按照分类（note）统计各分类下的图书总数量。**

```sql
SELECT note, COUNT(*) 
FROM books 
GROUP BY note;
```
> **易错点**：当 `SELECT` 列表中同时出现非聚合字段与聚合函数（如 `COUNT`、`SUM`、`AVG`）时，该非聚合字段必须显式声明在 `GROUP BY` 子句中，否则将破坏逻辑分组语义，甚至在启用 `ONLY_FULL_GROUP_BY` 模式下直接报错中断。

**需求 12：按照分类统计图书库存量，且仅展示累计库存超过 30 本的分类。**

```sql
SELECT note, SUM(num) 
FROM books 
GROUP BY note 
HAVING SUM(num) > 30;
```
> **核心辨析**：`WHERE` 用于在物理扫描与分组发生前过滤底层记录行，里面严禁出现聚合函数；而 `HAVING` 则是在数据完成 `GROUP BY` 分组归约之后，对分组聚合计算出的结果集进行二次筛选。

#### 游标分页与极限极值检索

**需求 13：查询所有图书，每页展示 5 本，提取第 2 页的数据。**

```sql
SELECT * 
FROM books 
LIMIT 5, 5;
```
> **解析**：MySQL 标准分页公式为 `LIMIT (page_no - 1) * page_size, page_size`。第 2 页（`page_no=2`）且每页 5 条时，起始偏移量 `offset = (2 - 1) * 5 = 5`，获取条数 `page_size = 5`。

**需求 14：按照分类统计库存量，找出总库存量最高的一类图书。**

```sql
SELECT note, SUM(num) 
FROM books 
GROUP BY note 
ORDER BY SUM(num) DESC 
LIMIT 0, 1;
```
> **解析**：先按类别聚合库存总量，随后对聚合值执行降序排列，最后利用 `LIMIT 0, 1` 截取榜首记录。

#### 字符串剔除与字符长度计算

**需求 15：查询书名长度达到 10 个字符的图书，计算字符数时不计入书名中的任何空格。**

如果直接使用内置的 `TRIM()` 函数，往往只能剥离文本首部和尾部的空白占位符，无法清除单词中间夹杂的空格。此时需借助 `REPLACE()` 函数将空格统一置换为空字符，再套用 `CHAR_LENGTH()` 获取纯净字符数：

```sql
SELECT `name` 
FROM books 
WHERE CHAR_LENGTH(REPLACE(`name`, ' ', '')) >= 10;
```
> **解析**：`CHAR_LENGTH()` 统计的是物理字符个数（无论汉字还是英文字符均记为 1 个单位），不同于按底层物理字节计算的 `LENGTH()`。通过 `REPLACE(name, ' ', '')` 彻底清洗掉内嵌空格后，满足长度大于等于 10 的只有《Legend of Sleepy Hollow》等书籍。

#### 流程控制与标签转义（CASE WHEN 结构）

**需求 16：查询书名及其分类，若 note 为 novel 显示“小说”，law 显示“法律”，medicine 显示“医药”，cartoon 显示“卡通”，joke 显示“笑话”，其余情况统一标注“其他”。**

```sql
SELECT `name` AS 书名, note,
    CASE note
        WHEN 'novel' THEN '小说'
        WHEN 'law' THEN '法律'
        WHEN 'medicine' THEN '医药'
        WHEN 'cartoon' THEN '卡通'
        WHEN 'joke' THEN '笑话'
        ELSE '其他'
    END AS 类型
FROM books;
```
> **解析**：此结构为“简单 CASE 表达式”，适用于针对单一变量的离散等值多路分支比对。末尾补充 `ELSE '其他'` 能够有效兜底未显式枚举的分类，避免输出为 `NULL`。

**需求 17：查询书名与库存，按库存区间打标：库存量 >30 显示“滞销”，0<num<10 显示“畅销”，等于 0 显示“无货”，其余区间显示“正常”。**

```sql
SELECT `name` AS 书名, num AS 库存,
    CASE 
        WHEN num > 30 THEN '滞销'
        WHEN num > 0 AND num < 10 THEN '畅销'
        WHEN num = 0 THEN '无货'
        ELSE '正常'
    END AS 显示状态
FROM books;
```
> **解析**：此结构为“搜索型 CASE 表达式”，`CASE` 后不带变量名，每个 `WHEN` 后面承接布尔条件表达式，非常适合范围区间的连续值研判。

#### 汇总增强与报表空值美化（WITH ROLLUP）

**需求 18：统计每一种分类（note）的库存量，并在结果集末尾追加一行输出合计总库存。**

```sql
SELECT IFNULL(note, '合计库存总量') AS note, SUM(num) AS total_num 
FROM books 
GROUP BY note WITH ROLLUP;
```

```text
+--------------------+-----------+
| note               | total_num |
+--------------------+-----------+
| drama              |        50 |
| joke               |        67 |
| novel              |        14 |
| 合计库存总量        |       131 |
+--------------------+-----------+
```
> **解析**：在 `GROUP BY` 结尾附加 `WITH ROLLUP` 关键字，数据库会在常规分组统计的基表上方，自动增加一条汇总所有分组指标的超级聚合行。由于汇总行原本的分组列会默认填充为 `NULL`，直接呈现给终端用户极不友好。利用 `IFNULL(note, '合计库存总量')` 进行动态置换，能直接产出工业级可读报表。

**需求 19：统计每一种分类下的图书数量，并合计全库图书总本数。**

```sql
SELECT IFNULL(note, '合计总本数') AS note, COUNT(*) AS book_count 
FROM books 
GROUP BY note WITH ROLLUP;
```
> **解析**：逻辑与需求 18 完全同构，将累加指标从数值求和 `SUM(num)` 切换为行数计数 `COUNT(*)`，末尾超级聚合行直观体现库内图书总计 7 本。

#### 综合极值与边界定位技巧

**需求 20：提取库存量位列全馆前三名的图书明细。**

```sql
SELECT * 
FROM books 
ORDER BY num DESC 
LIMIT 0, 3;
```

**需求 21：检索全馆出版年份最早的一部图书作品。**

```sql
SELECT * 
FROM books 
ORDER BY pubdate ASC 
LIMIT 0, 1;
```
> **解析**：由于 `pubdate` 字段采用标准 `YEAR` 类型存储，数字小的年份代表时间线更早。直接对其进行升序排序并截取首条记录，即可定位到出版年份为 1964 年的图书。

**需求 22：检索小说（note='novel'）品类中单价最高的一部书籍。**

```sql
SELECT * 
FROM books 
WHERE note = 'novel' 
ORDER BY price DESC 
LIMIT 0, 1;
```

**需求 23：检索全表图书中，书名纯字符长度最多（不包含任何空格）的一本书。**

```sql
SELECT * 
FROM books 
ORDER BY CHAR_LENGTH(REPLACE(`name`, ' ', '')) DESC 
LIMIT 0, 1;
```
> **解析**：本题不依赖 `WHERE` 进行行过滤，而是将“清洗中间空格并计算字符数”的复杂函数逻辑直接写入 `ORDER BY` 子句。数据库会对每一行记录动态计算其纯文本字符数并执行倒序排列，最终配合 `LIMIT 0, 1` 输出长度之最的书籍记录。

### 员工与用户多表联动操纵（练习 1 实战）

在这个场景中，我们需要在一个数据库下维护具有关联关系的员工信息表与系统用户表，演练从单列精细操作到跨表联动删除的完整生命周期。

```text
+-------------------------------------------------------------------------+
|                          dbtest11 数据库                                 |
|                                                                         |
|  +---------------------------+           +---------------------------+  |
|  |     my_employees 表       |           |         users 表          |  |
|  |---------------------------|           |---------------------------|  |
|  | id (int)                  |           | id (int)                  |  |
|  | first_name (varchar(10))  |           | userid (varchar(10)) <----+--+  |
|  | last_name (varchar(10))   |           | department_id (int)       |  |
|  | userid (varchar(10)) -----+-----------+                           |  |
|  | salary (double(10,2))     |                                       |  |
|  +---------------------------+                                       |  |
+-------------------------------------------------------------------------+
```
上图描绘了 `dbtest11` 数据库中两张关联表的物理布局，二者通过逻辑键 `userid` 维系数据对应关系。

#### 基础表结构与字段元数据创建

首先在实例中开辟独立的数据库命名空间 `dbtest11`，并显式指定字符编码为 `utf8`，随后创建两张核心数据表。

```sql
-- 1. 创建并切换至 dbtest11 数据库
CREATE DATABASE IF NOT EXISTS dbtest11 CHARACTER SET utf8;
USE dbtest11;

-- 2. 创建员工信息表 my_employees
CREATE TABLE IF NOT EXISTS my_employees (
    id INT(10),
    first_name VARCHAR(10),
    last_name VARCHAR(10),
    userid VARCHAR(10),
    salary DOUBLE(10, 2)
);

-- 3. 创建系统用户表 users
CREATE TABLE IF NOT EXISTS users (
    id INT,
    userid VARCHAR(10),
    department_id INT
);

-- 4. 检查两张表的元数据结构
DESC my_employees;
DESC users;
```

> **提示**：在 SQL 规范中，字段命名若由多个英文单词构成，强烈推荐使用下划线蛇形命名法（如 `user_id`）。如果业务设计中已经定型为连写的 `userid`，在后续编写 SQL 时必须严格贴合元数据定义，杜绝手滑混用。

#### 数据批量灌入的高级技巧：VALUES 与 SELECT UNION ALL

向 `my_employees` 表中插入基准数据时，常规做法是使用单条或复合多值的 `INSERT INTO ... VALUES (...)`：

```sql
-- 方式一：复合多值批量插入（常规推荐做法）
INSERT INTO my_employees 
VALUES 
(1, 'patel', 'Ralph', 'rpatel', 895),
(2, 'Dancs', 'Betty', 'bdancs', 860),
(3, 'Biri', 'Ben', 'bbiri', 1100),
(4, 'Newman', 'Chad', 'cnewman', 750),
(5, 'Ropeburn', 'Audrey', 'aropebur', 1550);

-- 向 users 表灌入关联基准数据
INSERT INTO users 
VALUES 
(1, 'rpatel', 10),
(2, 'bdancs', 10),
(3, 'bbiri', 20),
(4, 'cnewman', 30),
(5, 'aropebur', 40);
```

除了上述写法，还有一种极具工程启发意义的拓展思路：**利用 `SELECT` 常量配合 `UNION ALL` 组装内存虚拟表直接灌库**。很多初学者以为 `INSERT INTO ... SELECT` 必须后接 `FROM` 真实存在的物理表，实际上直接通过联合查询生成的结果集同样可以作为数据源：

```sql
-- 方式二（高级技巧）：基于 SELECT 常量与 UNION ALL 构造虚拟数据集灌库
INSERT INTO my_employees
SELECT 1, 'patel', 'Ralph', 'rpatel', 895
UNION ALL
SELECT 2, 'Dancs', 'Betty', 'bdancs', 860
UNION ALL
SELECT 3, 'Biri', 'Ben', 'bbiri', 1100
UNION ALL
SELECT 4, 'Newman', 'Chad', 'cnewman', 750
UNION ALL
SELECT 5, 'Ropeburn', 'Audrey', 'aropebur', 1550;
```

> **深度对比**：`UNION ALL` 在内存中将多行独立常量的投影直接合并为一个流式结果集，由于不执行去重排序（相比 `UNION` 省略了哈希与临时表去重开销），其执行速度非常快，在自动化生成测试桩数据、数据迁移转换及离线脚本构造中极为好用。

#### 字段更新与批量条件调薪

在完成数据灌入后，执行业务变更需求：

```sql
-- 需求 6：将 3 号员工的 last_name 修改为 'drelxer'
UPDATE my_employees 
SET last_name = 'drelxer' 
WHERE id = 3;

-- 需求 7：将所有薪资低于 900 的员工薪资统一提升调整至 1000
UPDATE my_employees 
SET salary = 1000 
WHERE salary < 900;
```

> **易错点**：更新需求 7 命中多条记录（原薪资为 895 与 860 的员工）。在执行这类批量 `UPDATE` 前，必须牢记“改前先查”的防御规范：先通过 `SELECT * FROM my_employees WHERE salary < 900;` 确认命中范围与行数无误，再行执行更新，避免误伤其他薪资梯队的数据。

#### 多表关联级联删除与单语句执行方案

**需求 8：将 `userid` 为 `'bbiri'` 的用户在 `users` 表与 `my_employees` 表中的全部关联记录一次性删除。**

面对跨表关联清理，大部分开发者的第一反应是分步执行两条物理删除语句：

```sql
-- 方式一：常规分步删除（需向数据库发起两次网络往返与事务确认）
DELETE FROM my_employees WHERE userid = 'bbiri';
DELETE FROM users WHERE userid = 'bbiri';
```

而在 MySQL 中，完全支持一种更优雅、效率更高的进阶写法：**多表连接联合删除（Multi-table DELETE）**：

```sql
-- 方式二（推荐高阶写法）：单条语句实现跨表关联删除
DELETE m, u
FROM my_employees m
JOIN users u ON m.userid = u.userid
WHERE m.userid = 'bbiri';
```

```text
+--------------------------------------------------------------------------+
| 多表联合删除执行原理                                                     |
|                                                                          |
|       my_employees (m)                     users (u)                     |
|     +-------------------+              +-------------------+             |
|     | userid = 'bbiri'  |              | userid = 'bbiri'  |             |
|     +---------+---------+              +---------+---------+             |
|               |                                  |                       |
|               +----------------+-----------------+                       |
|                                |                                         |
|                                v                                         |
|                 INNER JOIN (m.userid = u.userid)                         |
|                                |                                         |
|                                v                                         |
|           DELETE m, u (同时从两张表中擦除匹配行，单次事务闭环)           |
+--------------------------------------------------------------------------+
```
上图清晰展示了多表关联删除的执行路径：通过在 `DELETE` 关键字后显式列出待删除的目标表别名 `m, u`，引擎会沿着内连接匹配到的结果集，同时将两张物理表中的目标行精准抹去，既保证了操作的原子性，又免除了多次网络往返的开销。

#### DELETE 全表删除与 TRUNCATE 截断的底层辨析

针对练习 1 末尾要求清空整张表数据的场景，系统演示了两种不同的清除指令：

```sql
-- 方式一：逐行删除数据（DML 操作）
DELETE FROM my_employees;
DELETE FROM users;

-- 方式二：直接物理截断数据表（DDL 操作）
TRUNCATE TABLE my_employees;
```

这两者在表面上看都让表数据变空，但其底层机制有着天壤之别：

| 维度对比 | `DELETE FROM 表名` | `TRUNCATE TABLE 表名` |
| :--- | :--- | :--- |
| **语言范畴** | 数据操作语言（DML） | 数据定义语言（DDL） |
| **事务支持** | 支持事务。在 `SET autocommit = FALSE;` 下可通过 `ROLLBACK` 完整撤销恢复 | 不支持事务回滚。执行瞬间自动隐式提交，一旦执行物理数据永久灭失 |
| **日志与开销** | 逐行扫描并逐行记录 Redo/Undo 事务日志，大数据量时耗时极长、占用巨量日志空间 | 绕过行级记录，直接销毁并重新分配物理数据页（高水位线复位），速度近乎瞬间完成 |
| **自增计数器** | 不会重置 `AUTO_INCREMENT` 计数器，后续插入将在历史最大值基础上继续递增 | 彻底重置自增主键计数器，自增计数从初始基准值（通常为 1）重新开始计算 |

### 宠物档案系统的空值处理与结构变更（练习 2 实战）

现实生活中的很多业务实体（如动物领养、流浪动物救助）天然存在大量信息缺失。例如刚被收容的动物可能没有明确的主人，健康的宠物尚未记录死亡年份。本节以宠物档案 `pet` 为载体，演练包含大量 `NULL` 值的表设计与数据维护。

#### 宠物实体表设计与空值字段的显式插入

创建 `pet` 表，包含名称、主人、物种、性别、出生年份及死亡年份：

```sql
-- 创建宠物信息表 pet
CREATE TABLE IF NOT EXISTS pet (
    `name` VARCHAR(20),
    `owner` VARCHAR(20),
    species VARCHAR(20),
    sex CHAR(1),
    birth YEAR,
    death YEAR
);
```

录入基准数据时，面对未确定的字段（如流浪犬无主人、存活宠物无死亡时间），必须显式书写 `NULL` 占位符，保持元组列数与表结构严格契合：

```sql
-- 录入初始宠物档案，未确定的属性显式填充 NULL
INSERT INTO pet 
VALUES 
('Fluffy', 'Harold', 'cat', 'f', '2003', '2010'),
('Claws', 'Gwen', 'cat', 'm', '2004', NULL),
('Buffy', NULL, 'dog', 'f', '2009', NULL),
('Fang', 'Benny', 'dog', 'm', '2000', NULL),
('Bowser', 'Diane', 'dog', 'm', '2003', '2009'),
('Chirpy', 'Gwen', 'bird', 'f', '2008', NULL);
```

> **生活轶事与设计映射**：很多时候设计这类实体关系表，就如同给生命建立清晰可溯的“家谱”。这就像我读小学时特别喜欢养鸽子，巅峰期家里养了整整 43 只。当时我给每一对种鸽建立档案，第几窝孵出的小鸽子叫什么、后来又与谁配对，谱系记得一清二楚。在关系型数据库中，字段设计的严谨度直接决定了你后续能否准确追溯每一笔业务状态。

#### 表结构变更（ALTER TABLE）与 DDL 事务特性

**需求：在现有 `pet` 表中追加一个字段 `owner_birth`，用于记录宠物主人的出生年月日。**

```sql
-- 动态为 pet 表追加新列
ALTER TABLE pet ADD COLUMN owner_birth DATE;
```

> **注意**：关键字 `COLUMN` 可以省略。执行 `ALTER TABLE` 属于典型的 DDL 操作，具备**不可回滚性**。该列一旦增加到数据字典中，无法通过事务 `ROLLBACK` 撤回；若想撤销，只能再次发起 DDL 语句 `ALTER TABLE pet DROP COLUMN owner_birth;`。初始追加的新字段，在所有已有历史记录中默认自动赋为 `NULL`。

#### 状态驱动的数据更新与复合空值过滤

**需求：将名称为 `'Claws'` 的猫的主人修改为 `'Kevin'`。**

```sql
-- 联合名称与物种双重条件，锁定特定猫进行主人更正
UPDATE pet 
SET `owner` = 'Kevin' 
WHERE `name` = 'Claws' AND species = 'cat';
```

**需求：将所有尚未死亡的狗的主人统一变更指定为 `'Duck'`。**

```sql
-- 筛选活体犬只进行批量主人更新
UPDATE pet 
SET `owner` = 'Duck' 
WHERE death IS NULL AND species = 'dog';
```

> **易错点**：在 SQL 规范中，判定字段是否为空**绝对不能写成 `death = NULL`**！因为在 SQL 三值逻辑中，任何值与 `NULL` 进行等值判断（`=`）得出的布尔结果都是 `UNKNOWN`，永远无法返回 `TRUE`。必须严格使用 `IS NULL` 或 `IS NOT NULL`。

#### 空值匹配与实体物理清理

```sql
-- 1. 查询当前没有主人的宠物名称（收容救助场景）
SELECT `name` 
FROM pet 
WHERE `owner` IS NULL;

-- 2. 查询所有已经死亡的猫的名称、原主人及离世年份
SELECT `name`, `owner`, death 
FROM pet 
WHERE death IS NOT NULL AND species = 'cat';

-- 3. 清理已死亡狗的历史档案记录
DELETE FROM pet 
WHERE death IS NOT NULL AND species = 'dog';

-- 4. 核验全表剩余宠物档案
SELECT * FROM pet;
```

### 员工信息表自主建模与业务查询（练习 3 实战）

在练习 3 中，系统给出了样例数据，要求我们自主反推并推导字段的数据类型，构建 `employee` 表并完成日常检索与修改。

```text
+--------------------------------------------------------------------------+
| 字段类型选型推导矩阵                                                     |
|                                                                          |
| 字段名   | 业务含义 | 推荐类型       | 选型依据与性能考量                    |
|---------+---------+---------------+--------------------------------------|
| id      | 员工工号 | INT           | 整数标识，满足常规企业自增主键容量   |
| name    | 员工姓名 | VARCHAR(15)   | 变长中文姓名，通常不超过 15 个字符   |
| sex     | 性别     | CHAR(1)       | 离散固定单字符（'男'/'女'），定长最优|
| tel     | 联系电话 | VARCHAR(25)   | 包含连字符、固话或国际区号的变长串   |
| addr    | 家庭住址 | VARCHAR(35)   | 变长地址文本，按需动态分配存储空间   |
| salary  | 薪资待遇 | DOUBLE(10,2)  | 浮点金额，总长 10 位保留 2 位小数    |
+--------------------------------------------------------------------------+
```
上表展示了依据业务输入逆向推演表结构时各列的选型推导依据。

#### 业务驱动的字段类型选型：CHAR 与 VARCHAR 的权衡

```sql
-- 自主设计并创建员工信息表 employee
CREATE TABLE IF NOT EXISTS employee (
    id INT,
    `name` VARCHAR(15),
    sex CHAR(1),
    tel VARCHAR(25),
    addr VARCHAR(35),
    salary DOUBLE(10, 2)
);

-- 灌入基础员工数据
INSERT INTO employee 
VALUES 
(1001, '张翠山', '男', '13855551234', '湖北武当山', 1250.00),
(1002, '殷素素', '女', '13966662345', '浙江天鹰教', 1350.00),
(1003, '张无忌', '男', '13777773456', '西域明教光明顶', 2000.00),
(1004, '刘伯温', '男', '13688884567', '浙江青田县', 1100.00),
(1005, '刘全',   '男', '13599995678', '北京和府', 980.00),
(1006, '李四',   '男', '13400006789', '广东佛山', 1200.00);
```

> **设计前瞻**：在定义 `sex` 字段时，使用 `CHAR(1)` 要远优于 `VARCHAR(1)`。`CHAR` 是定长存储，无需额外分配 1 到 2 字节的长度前缀指针，内存对其和寻址效率更高。什么样的字段该用 `CHAR`？什么样的字段该用 `VARCHAR`？包括浮点数高精度计算到底该选 `FLOAT`、`DOUBLE` 还是定点数 `DECIMAL`？这正是数据库调优与表结构设计的核心基石，后续数据类型专门章节将对其底层存储机理展开全面精讲。

#### 薪资区间筛选与字符串模糊匹配的边界控制

在基础表上执行条件提取与文本修正：

```sql
-- 需求：查询薪资在 1200 至 1300 区间内的员工信息
SELECT * 
FROM employee 
WHERE salary BETWEEN 1200 AND 1300;

-- 需求：查询姓“刘”的员工工号、姓名及家庭住址
SELECT id, `name`, addr 
FROM employee 
WHERE `name` LIKE '刘%';
```

> **易错点**：匹配中文姓氏“刘”时，必须书写为 `'刘%'`，绝对不能两端均加上通配符写成 `'%刘%'`！如果写成 `'%刘%'`，语义就退化成了“姓名中包含字符‘刘’”，一旦出现诸如“张刘三”这样的名字就会发生严重的业务误命中。

```sql
-- 需求：将李四的家庭住址修正为广东韶关
UPDATE employee 
SET addr = '广东韶关' 
WHERE `name` = '李四';

-- 需求：查询姓名中包含“小”字的员工信息
SELECT * 
FROM employee 
WHERE `name` LIKE '%小%';
```

在执行修改李四住址时，先通过 `SELECT * FROM employee WHERE name = '李四';` 查看其原籍贯为 `'广东佛山'`，执行更新后再查一次确认其变更为 `'广东韶关'`，始终保持良好的防范与验证直觉。
