## 66-数据完整性与约束的分类
> 对应分集：P66 | 原始标题：《66-数据完整性与约束的分类》

在前面的章节中，我们把 MySQL 的各类字段数据类型做了一次大起底，知道了数字该选什么、字符串该怎么存、时间怎么配。但如果仅仅给字段指定了类型，数据库是不是就能高枕无忧地支撑业务运行了？

显然不是。即使把年龄定义为 `INT`，如果客户端不小心写入了一个 `-5` 或者 `300`，从纯类型角度看它完全合法；如果把员工所属的部门编号定义为 `INT`，写入了一个部门表中压根不存在的 `9999`，底层存储也绝不会报错；如果在注册系统中不加节制，让两个人用一模一样的用户名完成注册，甚至整张表里出现了两条物理上完全一模一样的用户记录，你想修改其中一个人的密码，写 `WHERE` 条件时就会发现根本无法单独命中他。

这就引出了数据库设计中一个极其核心的技术主题——**数据完整性（Data Integrity）**与**约束（Constraint）**。

---

### 为什么数据库必须引入约束

我们在数据库层面设立的所有规则，用一句话概括其终极目标：**为了保证数据完整性**。

> **定义**：数据完整性是指数据库中数据的**精确性（Accuracy）**与**可靠性（Reliability）**。它的本质是通过数据库底层的机制，防止数据库中存在不符合业务语义规定的垃圾数据，防止因为客户端输入错误、并发异常或异常事务导致脏数据入库。

在关系型数据库理论中，数据完整性具体落地为四大维度。这四个维度不是书本上的空洞口号，而是每一位工程师在建表时必须用约束去筑起的四道防线：

```text
                             数据完整性四大维度
                                     │
       ┌──────────────────┬──────────┴──────────┬──────────────────┐
       ▼                  ▼                     ▼                  ▼
【实体完整性】     【域完整性】           【引用完整性】     【用户自定义完整性】
行与行必须可区分   列取值必须合规         跨表关联必须合法   特定业务规则约束
(主键 / 唯一键)   (类型 / CHECK / 默认)  (外键约束)         (业务防重 / 金额限制)
```

#### 实体完整性（Entity Integrity）
实体完整性要求表中的每一行记录都代表一个唯一的客观实体，**同一个表中绝不允许存在两条完全相同、无法区分的记录**。
设想一下，如果一张表中没有定义任何能区分个体的机制，存入了两个同名同姓、所有属性值丝毫不差的用户记录。此时业务系统想要给其中某一个特定用户充值 100 元，当执行 `UPDATE users SET balance = balance + 100 WHERE name = '张三' AND ...` 时，无论条件怎么拼，都会同时修改这两条记录，没有任何手段把它们物理隔离开。
为了保证实体完整性，我们必须借助**主键约束（PRIMARY KEY）**或**唯一约束（UNIQUE）**为每一行数据确立唯一标识。

#### 域完整性（Domain Integrity）
“域”在数据库语境中指的就是字段或列（Attribute / Column）。域完整性要求**指定列的输入值必须落在合法有效的值域范围之内**。
例如：人的年龄字段通常限定在 `0 ~ 120` 岁之间；用户性别限定在特定的枚举选项之内；考试成绩必须在 `0 ~ 100` 分之间。
实现域完整性的手段既包括前一章精讲的基础数据类型（如用 `TINYINT UNSIGNED` 规避负数）、枚举（`ENUM`），也包括本章重点展开的**非空约束（NOT NULL）**、**默认值（DEFAULT）**以及**检查约束（CHECK）**。

#### 引用完整性（Referential Integrity）
引用完整性解决的是**多表关联时的数据合法性与一致性**。
在经典的关系模型中，我们有员工表（`employees`）和部门表（`departments`）。员工表中有一个字段叫 `department_id`，记录该员工归属哪一个部门：

```text
    [ employees 员工表 ]                       [ departments 部门表 ]
+---------+----------+---------------+        +---------------+------------------+
| emp_id  | name     | department_id |        | department_id | dept_name        |
+---------+----------+---------------+        +---------------+------------------+
| 101     | Alice    | 12            | -----> | 12            | 研发中心         |
| 102     | Bob      | 100 (非法?)   | --X    | 13            | 运营中心         |
+---------+----------+---------------+        +---------------+------------------+
```

如果 101 号员工关联的是 12 号部门，我们在部门表中能够准确检索到该部门；但如果向员工表插入 102 号员工时，随手写了一个 `department_id = 100`，而部门表中压根就没有 100 号部门，这名员工在物理架构上就失去了“立锥之地”——他在名义上属于一个不存在的组织。
如果没有底层规则防护，这种脏数据就会大行其道。而通过建立**外键约束（FOREIGN KEY）**，数据库引擎会在写入或更新时自动校验：被引用的主表记录不存在时，从表的数据坚决不予写入。

#### 用户自定义完整性（User-defined Integrity）
用户自定义完整性是针对**特定业务逻辑与规则**设立的定制约束。它来源于应用层特定的业务契约：
- 用户注册时，用户名必须全平台唯一。当用户在网页或 App 输入框填完账号、光标一失去焦点（`blur`），前端就会发送一个异步请求校验唯一性；在数据库底层，该字段必须具备唯一性约束，防止并发绕过造成同名注册。
- 登录密码、支付密码列必须强制非空（`NOT NULL`）。
- 进阶业务规则，例如“本部门经理的薪资不得高于本部门职工平均工资的 5 倍”、“订单总金额必须等于各商品明细金额之和”。
这些规则都可以通过数据库约束、触发器或应用层业务校验来实现。

### 约束的核心概念与技术定位

搞清楚了数据完整性，约束的概念就水到渠成了。

> **定义**：狭义上的约束（Constraint），是指**在数据库表级别设立的、直接作用在字段上的强制性限制规则**。

约束是关系型数据库与普通文件存储系统之间最本质的技术分水岭之一。普通的文本文件或 NoSQL 文档存储通常把数据校验完全推给应用层代码，一旦应用层出现 Bug 或有人直接连库执行 SQL，脏数据就会直接渗透。而 MySQL 约束是直接固化在存储引擎元数据之中的“硬规则”，任何试图破坏约束的 DML 操作（`INSERT`、`UPDATE`、`DELETE`），都会被数据库引擎无情拦截并回滚。

### 约束的多维分类体系

在实际开发和 SQL 语法规范中，我们可以从三个完全不同的视角对约束进行全景分类。

```text
                             MySQL 约束三维分类视图
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
  【按作用列数划分】              【按定义位置划分】              【按业务功能划分】
  · 单列约束                      · 列级约束 (紧随列后)           · NOT NULL (非空)
  · 多列联合约束                  · 表级约束 (列末独立)           · UNIQUE (唯一)
                                                                  · PRIMARY KEY (主键)
                                                                  · FOREIGN KEY (外键)
                                                                  · CHECK (检查)
                                                                  · DEFAULT (默认值)
```

#### 角度一：按约束作用的字段个数分类

从约束所绑定的物理列数量来看，分为单列约束与多列约束：

##### 单列约束
约束仅仅独立作用在表中的**某一个单独字段**上。
例如：单独要求 `id` 字段为主键，或者单独要求 `email` 字段必须具有唯一性。该约束的生效与否，只取决于这单一列的取值。

##### 多列约束（复合/联合约束）
约束同时作用在**两个或两个以上字段的联合组合**之上。
例如：在选课系统或权限系统中，我们允许同一个学生选不同的课，也允许同一门课有不同的学生，但绝对不允许“同一个学生重复选同一门课”。此时不能单独给 `student_id` 或 `course_id` 加唯一约束，而是将 `(student_id, course_id)` 两个字段绑定为一个联合唯一约束（Composite Unique Constraint）。只有当这两个字段的取值同时出现重复时，才会触发约束拦截。

#### 角度二：按约束的声明定义位置与作用范围分类

在编写 DDL 建表语句时，约束写在什么位置，决定了它是列级约束还是表级约束：

```sql
-- 列级约束与表级约束的语法分布示意
CREATE TABLE tb_example (
    -- 1. 列级约束：声明在字段类型之后
    id INT PRIMARY KEY,
    name VARCHAR(20) NOT NULL UNIQUE,
    dept_id INT,
    
    -- 2. 表级约束：所有字段定义完毕后，在末尾独立声明
    CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES tb_department(id)
);
```

##### 列级约束（Column-level Constraint）
在声明某个字段时，直接将约束关键字紧跟在该字段的数据类型之后。
- 特点：声明语法紧凑、直观，一眼就能看出该列受什么保护。
- 局限：单列约束大部分支持列级写法，但**涉及多列联合的约束（如联合主键、联合唯一键、外键）在 MySQL 中无法通过列级语法声明**。

##### 表级约束（Table-level Constraint）
在表中所有的字段均已定义完毕之后，在建表语句的末尾，使用独立的语法子句单独声明约束。
- 特点：能够灵活地给多列组合赋予联合约束，能够为外键、联合主键等命名规范的约束对象提供精确控制。
- 注意：并非所有功能约束都支持表级声明（例如在 MySQL 标准语法中，`NOT NULL` 和 `DEFAULT` 只能以列级方式声明在列属性中）。

#### 角度三：按约束的具体功能作用分类（核心六大族群）

这是日常工程实践中使用频率最高、也是本章后续将逐一精讲的核心体系。MySQL 支持的六大功能约束如下：

| 约束关键字 | 约束名称 | 核心作用与完整性维度 |
| :--- | :--- | :--- |
| `NOT NULL` | 非空约束 | 强制字段必须有确定值，不允许存储 `NULL`（域完整性） |
| `UNIQUE` | 唯一性约束 | 保证该列（或列组合）中的数据全局唯一，不可重复，但允许 `NULL`（实体/用户自定义完整性） |
| `PRIMARY KEY` | 主键约束 | `NOT NULL` 与 `UNIQUE` 的物理结合体，作为数据行的唯一身份凭据（实体完整性） |
| `FOREIGN KEY` | 外键约束 | 建立两表之间的参照联动，限定从表数据必须对应主表合法数据（引用完整性） |
| `CHECK` | 检查约束 | 通过布尔表达式限制列的取值范围（MySQL 8.0 开始正式生效强制校验）（域完整性） |
| `DEFAULT` | 默认值约束 | 当插入记录未显式传值时，自动赋予预设的默认静态值（域完整性） |

在这六大约束中，像非空（`NOT NULL`）、唯一（`UNIQUE`）、默认值（`DEFAULT`）和检查（`CHECK`），通过字面名称就能直接领会其核心意图；而主键（`PRIMARY KEY`）和外键（`FOREIGN KEY`）由于牵扯到底层聚簇索引组织、级联更新删除等深层机制，在认知上需要重点攻克。

### 约束的生命周期管理与添加时机

从工程生命周期的角度来看，我们操作与维护约束主要有两条物理路径：

```text
                           约束的生命周期管理途径
                                     │
           ┌─────────────────────────┴─────────────────────────┐
           ▼                                                   ▼
【创建表时声明 (CREATE TABLE)】                   【创建表后维护 (ALTER TABLE)】
· 最佳实践与首选路径                               · 线上补漏或架构迭代
· 一次性确立物理模型                               · 需面临全表存量数据清洗检验
· 避免后期 DDL 锁表与数据冲突                      · 涉及约束的追加与物理删除
```

#### 建表时声明约束（CREATE TABLE）
这是在绝大多数正规软件工程开发中的**标准范式与推荐做法**。
在设计数据库表结构、书写建表 DDL 语句的初始阶段，架构师与开发人员就必须结合业务用例，想清楚每一个字段的业务边界：哪些字段必填、哪些字段不可重复、关联关系如何锚定。在 `CREATE TABLE` 时直接将约束固化下来，既能杜绝任何脏数据趁虚而入，也不会产生后期的结构改造包袱。

#### 运行期追加或删除约束（ALTER TABLE）
如果项目在初期设计时存在疏漏，或者随着业务迭代出现了新的约束诉求，我们可以通过 `ALTER TABLE` 语句对已有数据表进行结构调整：
- **追加约束**：使用 `ALTER TABLE ... ADD CONSTRAINT ...` 或 `ALTER TABLE ... MODIFY ...`。
- **删除约束**：使用 `ALTER TABLE ... DROP ...`。

> **易错点**：在已存有大量线上业务数据的表中通过 `ALTER TABLE` 追加约束，具有极高的故障风险。
> 1. **存量脏数据冲突**：如果现存数据中已经存在重复值或 `NULL`，直接追加 `UNIQUE` 或 `NOT NULL` 会导致整个 DDL 语句报错中止，必须先人工清洗脏数据；
> 2. **DDL 锁表与性能开销**：在千万级大表上修改列属性或重构索引，即使有 Online DDL 支持，也可能消耗巨大的 I/O 与元数据锁（MDL）资源。因此，**能在一开始建表时规划好的约束，坚决不要留到后期上线后再去改**。

### 本讲提到的题目与认知复盘

本讲在引导大家进入第十三章约束精讲时，虽然没有穿插复杂的代码题，但提出了几个直接贯穿全章核心原理的本质问题。把这几个问题想透，后续学习每一个具体约束的语法时才能做到心中有数。

#### 题目 1：在数据库中，什么是“数据完整性”？它具体包含哪四个维度，分别通过什么约束机制来实现？
- **解析**：
  数据完整性指的是数据库中数据的精确性与可靠性，防止不符合语义规则的错误数据存入库中。具体四大维度为：
  1. **实体完整性**：保证表中的行记录唯一可分，不允许完全重复的行。通过 `PRIMARY KEY`（主键约束）或 `UNIQUE`（唯一约束）实现。
  2. **域完整性**：保证某一列的取值在合法的取值范围之内。通过数据类型、`NOT NULL`（非空）、`DEFAULT`（默认值）、`CHECK`（检查约束）实现。
  3. **引用完整性**：保证主从表之间引用的合法性，不允许从表引用主表中不存在的实体。通过 `FOREIGN KEY`（外键约束）实现。
  4. **用户自定义完整性**：满足特定具体业务的规则限制。通过自定义的 `CHECK` 条件、`UNIQUE` 防重、触发器或存储过程实现。

#### 题目 2：试述约束从“作用列数”、“定义位置”、“业务功能”三个角度的具体划分方式。
- **解析**：
  1. **按作用列数**：划分为**单列约束**（约束作用于单一字段）和**多列约束/复合约束**（约束同时作用于多个字段的联合组合）。
  2. **按定义位置**：划分为**列级约束**（声明在列定义之后，语法紧凑但不支持多列组合）和**表级约束**（在所有列声明完毕后在表尾独立声明，支持联合键及外键的高级定义）。
  3. **按业务功能**：划分为六大核心约束，即 `NOT NULL`（非空）、`UNIQUE`（唯一）、`PRIMARY KEY`（主键）、`FOREIGN KEY`（外键）、`CHECK`（检查）、`DEFAULT`（默认值）。

#### 题目 3：从工程实践角度，为什么强烈建议在建表阶段就将约束定义完整，而不是等上线后通过 ALTER TABLE 补充？
- **解析**：
  1. **数据一致性防护前置**：在建表阶段即确立约束，能够从系统上线的第一行数据开始就百分之百杜绝脏数据入库。
  2. **避免存量数据清洗死锁**：若系统上线并写入数据后再通过 `ALTER TABLE` 追加约束（如 `UNIQUE` 或 `NOT NULL`），一旦已有数据中存在违背新约束的历史脏数据，DDL 执行将直接失败并抛出异常，此时必须在不停服的前提下对海量脏数据进行甄别与清洗，代价极其高昂。
  3. **降低线上元数据锁（MDL）与性能开销**：对已有业务大表执行 `ALTER TABLE` 操作，可能引发元数据锁等待，甚至导致表级阻塞和主从延迟风险。

## 67-非空约束的使用
> 对应分集：P67 | 原始标题：《67-非空约束的使用》

在正式切入每一个具体约束的语法细节之前，我们需要先搞清楚一个之前被很多同学忽略的事实：在前面的章节中，我们反反复复地对员工表（`employees`）和部门表（`departments`）执行各种复杂的 `SELECT` 过滤、多表连接与分组统计，大家在写查询时感觉这些表就是一堆平铺直叙的数据行，但实际上，这些生产级范式表中早已密密麻麻地布满了各种底层的约束规则。

约束不仅在执行 `INSERT`、`UPDATE`、`DELETE` 等写操作时构筑校验关卡，在执行读操作（`SELECT`）时同样深度参与。例如主键约束和唯一约束在底层会自动伴生聚簇索引和唯一二级索引，MySQL 优化器在解析执行计划时，正是依赖这些由约束派生出的索引结构来实现毫秒级的 B+ 树快速寻址。

要感知和探查这些数据表自带的约束，除了在图形化客户端（如 Navicat、DataGrip）的索引设计器中查看之外，在 SQL 命令行中可以通过系统自带的元数据字典表进行精准检索：

```sql
SELECT * 
FROM information_schema.TABLE_CONSTRAINTS 
WHERE TABLE_NAME = 'employees';
```

通过查询 `information_schema.TABLE_CONSTRAINTS` 字典，可以看到约束所属的库表名称、约束对象名称（`CONSTRAINT_NAME`）以及约束的类型（`CONSTRAINT_TYPE`，如 `PRIMARY KEY`、`UNIQUE`、`FOREIGN KEY` 等）。

掌握了查看约束的方法之后，我们正式进入六大约束中最基础、最直观、但在生产环境中出现频率极高的第一位成员——**非空约束（NOT NULL）**。

---

### 非空约束的核心语义与语法边界

非空约束，顾名思义，就是**强制限定表中某个字段（列）的值绝不允许为 `NULL`**。

在 MySQL 的默认行为中，如果不加任何特殊修饰，所有的基础数据类型（整数、浮点、字符、时间等）默认都是允许存储 `NULL` 值的。只有通过显式声明 `NOT NULL` 关键字，数据库引擎才会对该列开启强校验保护。

```text
                             非空约束核心特性图谱
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        ▼                             ▼                             ▼
【仅限列级声明】               【零与空串不等于 NULL】        【拒绝多列联合定义】
必须直接跟在字段类型之后       '' 与 0 属于合法物理值        不能将多个字段打包声明
不支持在表末以表级声明定义     NOT NULL 仅拦截 NULL 标记     只能逐个字段单独附加
```

#### 语法位置与不可联合性
非空约束在定义上具有极其鲜明的语法边界：
1. **仅支持列级约束声明**：在 MySQL 规范中，`NOT NULL` 必须且只能声明在对应字段的类型定义之后，**MySQL 不支持在表末尾使用独立的 `CONSTRAINT ... NOT NULL` 表级语法**。
2. **不支持多列联合约束**：正因为它只能依附于具体的单个字段声明，所以数据库不存在所谓的“联合非空约束”。如果一张表中有 5 个字段都要求必填，就必须在每一个字段后面独立书写 `NOT NULL`。

#### 概念辨析：NULL 与空字符串、数字 0 的本质区别
在日常开发中，初学者极易混淆 `NULL` 与空串的概念：
- **空字符串 `''`**：长度为 0 的字符常量，它占用实际的存储空间，具有明确的字符串类型语义；
- **数字 `0`**：数值系统中的具体整数，具有明确的代数意义；
- **`NULL`**：代表“未知（Unknown）”、“未定义”或“不存在”。在物理底层，InnoDB 引擎需要通过每行记录头信息中的“NULL 值列表（NULL Value Bitmap）”用位标记来专门标识该字段是否为 NULL。
当字段被 `NOT NULL` 约束修饰时，写入 `0` 或空字符串 `''` 是完全合法且能正常通过校验的，约束拦截的仅仅是裸的 `NULL` 标识。

---

### 在 CREATE TABLE 时定义非空约束

在新建表结构时添加非空约束是工程实践中最标准、最规范的途径。开发人员必须根据业务实体的刚性属性，审慎决定哪些列必须保证绝对存在。

我们以搭建一个基础的测试库 `dbtest13` 和测试表 `test1` 为例展开全流程演示：

```sql
-- 1. 创建并切换至测试数据库
CREATE DATABASE dbtest13;
USE dbtest13;

-- 2. 创建带有非空约束的员工测试表
CREATE TABLE test1 (
    id INT NOT NULL,
    last_name VARCHAR(15) NOT NULL,
    email VARCHAR(25),
    salary DECIMAL(10, 2)
);
```

在上述建表语句中，我们将员工的编号 `id` 和员工姓氏 `last_name` 声明为 `NOT NULL`，而将邮箱 `email` 和工资 `salary` 保持默认（允许为 NULL）。因为新员工入职时可能尚未分配企业邮箱，薪资定级也可能尚在审批流中，允许为空符合业务弹性；但一名员工没有 ID 和姓名，在业务逻辑上是绝对无法成立的。

建表完成后，查看表结构元数据：

```sql
DESC test1;
```

执行后输出的元数据结构如下：

| Field | Type | Null | Key | Default | Extra |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | int | **NO** | | NULL | |
| `last_name` | varchar(15) | **NO** | | NULL | |
| `email` | varchar(25) | **YES** | | NULL | |
| `salary` | decimal(10,2) | **YES** | | NULL | |

在返回结果中，`Null` 列清晰地标明了各字段的受控状态：`id` 与 `last_name` 标记为 `NO`，代表非空防线已经成功筑牢；而未加约束的列则显示为 `YES`。

### DML 操作下非空约束的触发与拦截验证

非空约束一旦建立，将时刻监控对该表发生的所有数据写入与更新操作。

#### 正常数据的合法写入
当为所有字段（包括非空字段）赋予明确的合规数值时，数据顺利写入：

```sql
INSERT INTO test1(id, last_name, email, salary)
VALUES (1, 'Tom', 'tom@126.com', 3400.00);
```
此语句执行成功，数据行被安全写入底层数据页。

#### 显式赋值 NULL 时的约束拦截
当客户端试图显式将 `NULL` 传入受保护的字段时，数据库引擎会立即阻断该操作：

```sql
-- 试图将 last_name 显式置为 NULL
INSERT INTO test1(id, last_name, email, salary)
VALUES (2, NULL, 'jerry@126.com', 4500.00);
```
MySQL 立即抛出错误信息：
```text
ERROR 1048 (23000): Column 'last_name' cannot be null
```
同理，如果试图将主键标识 `id` 设为 `NULL`，也会引发相同的阻断。

#### 隐式省略字段引发的“默认值缺失”报错深层解析
在实际生产中，更隐蔽的报错往往发生在**省略列清单**的插入语句中：

```sql
-- 插入时只给 id 和 email 赋值，显式省略了 last_name
INSERT INTO test1(id, email)
VALUES (2, 'abc@126.com');
```

执行该语句时，控制台并没有报 `Column cannot be null`，而是输出了如下提示：
```text
ERROR 1364 (HY000): Field 'last_name' doesn't have a default value
```

很多同学看到这个错误信息会感到十分困惑：明明我违反的是非空约束，为什么报错信息却咬定“该字段没有默认值”？

这里的内部推导链条非常严密，体现了 MySQL 在处理缺失列时的底层逻辑：

```text
               客户端执行 INSERT (省略字段 last_name)
                                │
                                ▼
               检查字段定义是否包含 DEFAULT 显式默认值?
                               /          \
                             是            否
                             /              \
                    自动填入预设默认值      寻找系统隐式回退机制: 尝试填入 NULL
                                                    │
                                                    ▼
                                          检测该字段的 Null 属性
                                                    │
                                       ┌────────────┴────────────┐
                                       ▼                         ▼
                                 若允许 NULL               若为 NOT NULL
                               (成功存入 NULL)             (无法使用 NULL 垫底)
                                                                 │
                                                                 ▼
                                                  触发抛错: 既无默认值又不能为NULL!
                                                  (Field doesn't have a default value)
```

当一条插入语句未指定某列的值时，MySQL 的第一动作不是报错，而是去检索该列是否配置了 `DEFAULT`（默认值约束）。如果配置了默认值，就自动填充默认值；如果未显式配置默认值，MySQL 会尝试采用系统的标准回退值——即 `NULL`。然而该列又被声明了 `NOT NULL`，导致回退机制彻底失效，系统处于“既没有合法值填充、又不允许用 NULL 垫底”的死锁状态，因此最终报出“该字段没有默认值”。

#### UPDATE 场景下的约束防护
非空约束不仅管“生”（`INSERT`），同样管“改”（`UPDATE`）：

```sql
-- 尝试将已有记录的非空列修改为 NULL
UPDATE test1 
SET last_name = NULL 
WHERE id = 1;
```
该操作同样会被无情拦截，报出 `Column 'last_name' cannot be null`。而将允许为空的 `email` 字段重置为 `NULL` 时，则能够顺利执行更新：

```sql
-- 合法更新：未受非空约束的列允许回退为 NULL
UPDATE test1 
SET email = NULL 
WHERE id = 1;
```

### 运行期维护：通过 ALTER TABLE 追加与删除非空约束

在表已经上线运行之后，有时需要调整某些字段的非空控制。在 MySQL 中，非空约束的增加与移除不是通过 `ADD CONSTRAINT` 或 `DROP CONSTRAINT`，而是通过**修改列定义（`MODIFY`）**来实现的。

#### 在已有表中追加非空约束（避坑指南）

追加非空约束的标准语法如下：

```sql
ALTER TABLE 表名 MODIFY 字段名 字段类型 NOT NULL;
```

##### 生产环境致命陷阱：存量脏数据冲突
假设当前 `test1` 表中已经存在如下数据记录：

```sql
SELECT * FROM test1;
```
| id | last_name | email | salary |
| :--- | :--- | :--- | :--- |
| 1 | Tom | **NULL** | 3400.00 |

由于在前面的测试中，我们把 1 号员工的 `email` 更新成了 `NULL`。此时如果直接执行追加非空约束的操作：

```sql
ALTER TABLE test1 MODIFY email VARCHAR(25) NOT NULL;
```

MySQL 会立刻拒绝执行，并抛出严重警告与错误：
```text
ERROR 1138 (22004): Invalid use of NULL value
```

> **易错点**：当向一个已经存在数据的列追加 `NOT NULL` 约束时，**只要表中存在哪怕一条记录的该字段值为 `NULL`，整个 DDL 语句就会直接失败**。因为一旦允许加上约束，表中原本合法的旧数据就会瞬间变成“违法”的脏数据，关系型数据库绝不允许这种状态存在。

##### 标准修复与追加步骤
在生产中必须遵循“先清洗、后约束”的两步走策略：

```sql
-- 第一步：执行数据清洗，消除所有已存在的 NULL 记录
UPDATE test1 
SET email = 'tom@126.com' 
WHERE id = 1;

-- 第二步：在确认全量数据合规后，重新追加非空约束
ALTER TABLE test1 MODIFY email VARCHAR(25) NOT NULL;
```
清洗完成后再次执行，DDL 语句便能顺利通过。此时通过 `DESC test1;` 查看，`email` 的 `Null` 属性已经变更为 `NO`。

#### 在已有表中删除非空约束

删除非空约束的逻辑非常朴素：重新调用 `MODIFY`，重写该字段的完整类型定义，并显式指定 `NULL` 或直接省略 `NOT NULL`：

```sql
-- 移除 email 字段上的非空约束
ALTER TABLE test1 MODIFY email VARCHAR(25) NULL;
```

执行后，再次查看表结构：
```sql
DESC test1;
```
`email` 列的 `Null` 属性重新变回 `YES`。此时再次执行将该字段置为 `NULL` 的更新操作，数据库将完全放行。

### 本讲提到的题目与认知复盘

#### 题目 1：在向某表中执行 INSERT 时，如果省略了一个带有 NOT NULL 约束的字段，MySQL 为何经常抛出 “Field 'xxx' doesn't have a default value” 而非 “Column cannot be null”？
- **解析**：
  在 MySQL 处理缺少赋值的列时，解析流程首先会判断该字段是否存在显式默认值声明（`DEFAULT`）。若未指定显式默认值，系统会尝试自动调用默认回退值 `NULL` 进行占位填充；此时若该字段同时受 `NOT NULL` 约束修饰，则 `NULL` 占位填充动作被彻底阻断。由于既无法获取预设默认值，又被禁止使用默认的 `NULL` 填充，因此 MySQL 的底层错误调度器抛出的是“该字段缺少默认值”这一根本诱因。

#### 题目 2：在维护已运行的业务表时，如果需要将一个历史存量的可空字段调整为 NOT NULL，直接执行 ALTER TABLE ... MODIFY 可能面临什么问题？标准工程处理流程是什么？
- **解析**：
  - **核心问题**：若表中的存量数据已经包含了 `NULL` 记录，执行 `ALTER TABLE ... MODIFY ... NOT NULL` 会触发 `ERROR 1138: Invalid use of NULL value`，导致 DDL 修改被整体回滚。
  - **标准工程处理流程**：
    1. **数据探查**：执行 `SELECT COUNT(*) FROM table WHERE col IS NULL;` 确认存量空数据的规模与受影响记录；
    2. **存量数据清洗**：通过 `UPDATE` 语句为存量 `NULL` 记录补充有意义的业务初值或通用占位符；
    3. **结构变更（DDL）**：在确认字段已全量非空后，执行 `ALTER TABLE ... MODIFY col TYPE NOT NULL;` 正式启用约束；
    4. **元数据复核**：通过 `DESC table;` 确认约束生效无误。

## 68-唯一性约束的使用
> 对应分集：P68 | 原始标题：《68-唯一性约束的使用》

在上一讲中，我们解决了数据“必须有值”的非空要求。但在实际业务场景中，光有值是远远不够的。比如用户的手机号、身份证号、员工的工号、企业邮箱，系统不仅要求它们非空，更核心的诉求是：**全表之中绝不能出现两份完全相同的值**。

这就是本讲的主角——**唯一性约束（UNIQUE Constraint）**。

在英文里，`unique` 这个词的拼写稍不留神容易写错，但它的语义极富感染力——代表“唯一的、独一无二的”。就像大家跟自己的伴侣表白时说“*You are my unique lover*”，或者珠宝界那句家喻户晓的广告语“*钻石恒久远，一颗永流传*”，唯一性约束在关系型数据库中的使命，就是让特定的数据列在整张表中保持独一无二的排他性。

---

### 唯一性约束的业务语义与选型考量

唯一性约束的核心作用，是**强制限定表中某个字段（或多个字段的组合）的值不得重复**。

但在建表时，到底哪些字段该加唯一约束、哪些字段坚决不能加，必须建立在深刻的真实业务场景与人情世故的洞察之上，绝不能拍脑袋乱加。

```text
                           字段唯一性选型考量矩阵
                                     │
       ┌─────────────────────────────┴─────────────────────────────┐
       ▼                                                           ▼
【适合建立唯一约束的字段】                                 【坚决不能建立唯一约束的字段】
· id / 工号：全局排他标识                                  · last_name (姓名)：重名现象极其普遍
· email (邮箱)：通信私密性要求                             · salary (工资)：密薪制与同岗同酬
· 身份证号 / 手机号：自然人真实唯一映射                     · 状态码 / 性别 / 年龄：天然有限值域
```

#### 为什么员工姓名（last_name）绝不能加 UNIQUE
如果给用户或员工的姓名加上了 `UNIQUE` 约束，系统上线之日就是灾难的开端。
在现实生活中，同名同姓的现象普遍得超乎想象。像全国叫“张伟”、“李伟”、“王伟”的人，一拉能拉出来一个排。我上高中的时候，班里就有两个叫“张超”的同学，一个是男生一个是女生。每次任课老师在讲台上点名提问，都必须特别指定“男张超”还是“女张超”。如果在员工表中把姓名列设为 `UNIQUE`，当公司录用了第二个叫“张超”的员工时，人事在录入系统时会直接被数据库报主键重复打回，这在业务逻辑上是极其荒谬的。

#### 为什么企业邮箱（email）必须加 UNIQUE
与姓名相反，员工的企业邮箱必须加 `UNIQUE`。
如果邮箱不设唯一性约束，由于录入失误导致两名员工拥有完全相同的系统邮箱，一旦管理层或财务向该邮箱发送年终奖明细、人事变动或涉及商业机密的私信，邮件会被同时抄送给无关人员，直接酿成严重的管理事故和泄密风险。

#### 为什么薪资待遇（salary）绝不能加 UNIQUE
在大多数正规企业中，薪资体系遵循“背靠背”的密薪制。
如果在数据库中把 `salary` 定义为 `UNIQUE`，就意味着整个公司所有员工的工资数字都必须两两不同。现实中同一职级、同一年资的员工拿一模一样的底薪是极其正常的。更重要的是，一旦工资要求全员唯一，员工私下一打听：“你一个月多少钱？”“一万五。”“你呢？”“一万二。”两个人做着一模一样的工作，薪资偏低的员工必然心态失衡，引发团队极大的内部动荡与离职风险。

---

### 在 CREATE TABLE 时声明唯一约束

在建表阶段添加唯一约束，MySQL 提供了**列级约束**与**表级约束**两种声明语法。

```sql
-- 创建测试数据库与数据表
CREATE TABLE test2 (
    id INT UNIQUE,                           -- 方式一：列级约束声明
    last_name VARCHAR(15),
    email VARCHAR(25),
    salary DECIMAL(10, 2),
    
    CONSTRAINT uk_test2_email UNIQUE(email)  -- 方式二：表级约束声明
);
```

#### 列级约束与表级约束的语法差异

在上面的建表语句中，我们同时使用了两种声明方式：
1. **列级约束**（在 `id INT UNIQUE` 中体现）：
   直接将 `UNIQUE` 关键字紧跟在字段类型定义之后。此方式书写极其精炼，但缺点是**无法为该约束显式指定一个业务友好的名称**，MySQL 会在底层默认采用该列的字段名作为约束名。
2. **表级约束**（在表尾独立声明）：
   语法格式为：`CONSTRAINT 约束名 UNIQUE(字段名)`。
   - `CONSTRAINT`：关键字，声明这是一个约束实体；
   - `uk_test2_email`：开发人员自定义的约束名称（工程规范中，通常以 `uk_` 代表 Unique Key，后接 `表名_列名`，也可以使用 `uni_` 前缀）；
   - `UNIQUE(email)`：指定约束类型为唯一约束，并用小括号圈定作用的字段。

> **提示**：如果在表级约束中省略了 `CONSTRAINT 约束名`，直接书写 `UNIQUE(email)`，建表依然能够成功，此时 MySQL 同样会默认以该字段名作为约束名。

#### 约束状态探查
建表完成后，我们可以通过两种方式查看约束的生效情况：

##### 查看表结构
```sql
DESC test2;
```
输出中，`id` 和 `email` 字段的 `Key` 列均显示为 **`UNI`**，表明唯一性防线已正确就位。

##### 查询系统字典表
```sql
SELECT * 
FROM information_schema.TABLE_CONSTRAINTS 
WHERE TABLE_NAME = 'test2';
```
在系统元数据中，能够清晰地检索出两条 `CONSTRAINT_TYPE = 'UNIQUE'` 的记录，其中一条的名字是默认的 `id`，另一条是自定义的 `uk_test2_email`。

### DML 校验与核心特例：NULL 值的多重并存机制

唯一性约束建立之后，对于常规的数值写入，如果出现重复，MySQL 会立即予以拦截：

```sql
-- 1. 成功插入合规基准记录
INSERT INTO test2(id, last_name, email, salary)
VALUES (1, 'Tom', 'tom@126.com', 4500.00);

-- 2. 尝试插入重复的 id (已存在 1)
INSERT INTO test2(id, last_name, email, salary)
VALUES (1, 'Jerry', 'jerry@126.com', 5000.00);
-- 触发报错: ERROR 1062 (23000): Duplicate entry '1' for key 'test2.id'

-- 3. 尝试插入重复的 email (已存在 tom@126.com)
INSERT INTO test2(id, last_name, email, salary)
VALUES (2, 'Tom2', 'tom@126.com', 6000.00);
-- 触发报错: ERROR 1062 (23000): Duplicate entry 'tom@126.com' for key 'test2.uk_test2_email'
```

#### 核心特例：向 UNIQUE 字段插入 NULL 值
现在考虑一个在面试与开发中极具迷惑性的问题：
**如果某个字段被声明为了 UNIQUE，那么这个字段是否允许被存入 NULL？如果允许，是否只能存入一个 NULL？**

我们直接用代码进行验证：

```sql
-- 第一次向 UNIQUE 字段 email 写入 NULL
INSERT INTO test2(id, last_name, email, salary)
VALUES (2, 'Tom2', NULL, 6000.00);
-- 执行结果: 成功插入!

-- 第二次继续向 UNIQUE 字段 email 写入 NULL
INSERT INTO test2(id, last_name, email, salary)
VALUES (3, 'Tom3', NULL, 7000.00);
-- 执行结果: 依然成功插入!
```

事实证明：**向声明为 UNIQUE 的列中，不仅可以存入 NULL，而且可以写入任意多个 NULL 值！**

```text
                           UNIQUE 字段的 NULL 值并存逻辑
                                        │
           ┌────────────────────────────┴────────────────────────────┐
           ▼                                                         ▼
【业务人情味视角】                                         【关系代数底层原理】
新员工入职人事填表:                                        SQL 三值逻辑体系:
· 第一个员工: "我刚入职还没邮箱" -> 人事: "先空着(NULL)"   · NULL 代表 "未知 / 不存在"
· 第二个员工: "我也还没邮箱"                               · NULL = NULL 的比较结果不是 TRUE
· 人事绝不会说: "不行! 前面已经有人 NULL 过了,              · 比较结果为 UNKNOWN
  你必须有邮箱, 不能再 NULL 了!"                           · 既然不相等, 就不构成重复!
```

在现实生活中，新员工入职办理手续，张三说自己还没申请公司邮箱，人事说先空着（存为 NULL）；接着李四入职，也说自己还没邮箱，人事绝不可能刁难说：“不行，刚才张三已经空过了，你不能再空了，全公司只能有一个人没有邮箱！”在业务逻辑上，空值代表的是“缺失”，缺失并不等同于冲突。

从数据库底层的关系代数与三值逻辑（Three-Valued Logic）来看，`NULL` 代表的是未知（Unknown）。在 SQL 标准中，执行 `NULL = NULL` 得到的布尔值并不是 `TRUE`，而是 `UNKNOWN`。既然任何一个 `NULL` 与另一个 `NULL` 在逻辑比对中都无法判定为相等，那么在唯一性检验算法看来，它们就互不冲突，因而可以无限次存入。

> **提示**：如果业务上既要求字段唯一，又坚决不让存入空值，必须将两个约束组合使用：`email VARCHAR(25) NOT NULL UNIQUE`。

### 运行期维护：通过 ALTER TABLE 追加唯一约束

在数据表已经建立之后，可以通过 `ALTER TABLE` 补充添加唯一约束。MySQL 支持两种等价的追加语法：

#### 语法形式一：ADD 语法（表级追加）
```sql
-- 语法：ALTER TABLE 表名 ADD [CONSTRAINT 约束名] UNIQUE(字段名);
ALTER TABLE test2 ADD CONSTRAINT uk_test2_sal UNIQUE(salary);
```
该语法与建表时的表级约束完全一脉相承，推荐使用，并显式给约束起一个规范的名称。

#### 语法形式二：MODIFY 语法（列级追加）
```sql
-- 语法：ALTER TABLE 表名 MODIFY 字段名 字段类型 UNIQUE;
ALTER TABLE test2 MODIFY salary DECIMAL(10, 2) UNIQUE;
```
通过重写列定义的列级语法追加约束。

> **易错点**：执行追加唯一约束前，**表中现存的历史数据中如果已经包含了重复值，DDL 语句将直接报错崩溃**！例如表中已经存在两条工资同为 4500.00 的记录，执行 `ADD UNIQUE(salary)` 时会立刻报 `ERROR 1062: Duplicate entry '4500.00'`。必须先排查并去重存量数据，方可执行变更。

### 复合唯一约束（多列联合唯一约束）

在复杂的业务建模中，很多时候单一字段都不适合作为唯一标识，但**几个字段结合在一起的联合凭证必须保持全局唯一**。

```text
                               复合唯一约束机理
                         UNIQUE ( col_A, col_B )
                                    │
       ┌────────────────────────────┴────────────────────────────┐
       ▼                                                         ▼
【单列相同允许并存】                                       【组合全同坚决拦截】
· 行 1: (A=1, B=100)                                       · 若表中已有: (A=1, B=100)
· 行 2: (A=1, B=200) -> 允许写入!                          · 试图写入:   (A=1, B=100)
· 行 3: (A=2, B=100) -> 允许写入!                          · 结果: 立即触发 Duplicate entry 阻断
```

#### 语法规范：强制要求表级声明
由于列级约束只能紧随单列之后，无法将多列同时打包，因此**复合唯一约束必须使用表级约束语法声明**：

```sql
CREATE TABLE tb_user (
    id INT,
    name VARCHAR(15),
    password VARCHAR(25),
    
    -- 复合唯一约束声明
    CONSTRAINT uk_user_name_pwd UNIQUE(name, password)
);
```

#### 经典业务场景：高校多对多选课模型

在高校教务系统中，学生、课程与选课成绩之间的实体关系是复合唯一约束的教科书级实战案例：

```sql
-- 1. 创建学生表
CREATE TABLE student (
    sid INT PRIMARY KEY,
    sname VARCHAR(20),
    tel VARCHAR(11),
    card_id VARCHAR(18)
);

-- 2. 创建课程表
CREATE TABLE course (
    cid INT PRIMARY KEY,
    cname VARCHAR(20)
);

-- 3. 创建学生选课成绩表
CREATE TABLE student_course (
    id INT PRIMARY KEY,
    sid INT,
    cid INT,
    score DECIMAL(4, 1),
    
    -- 核心：学生学号与课程编号的复合唯一约束
    UNIQUE KEY (sid, cid)
);
```

##### 业务模型推导
- 一个学生可以选修多门不同的课（`sid` 相同，但 `cid` 不同）：合法；
- 同一门课可以被多名不同的学生选修（`cid` 相同，但 `sid` 不同）：合法；
- **同一个学生在同一门课程上，只能产生一份唯一的最终考试成绩**！如果表中已经存在 `sid=2, cid=1002` 的成绩记录，试图再次插入 `(2, 1002)` 时，复合唯一约束将触发硬性拦截：
```text
ERROR 1062 (23000): Duplicate entry '2-1002' for key 'student_course.sid'
```

### 唯一约束的删除机制与底层唯一索引绑定

在学习删除唯一约束时，很多习惯了标准 SQL 思维的同学会想当然地去写 `ALTER TABLE 表名 DROP CONSTRAINT 约束名;`，但在 MySQL 中，这会牵扯出一段极其严密底层的底层实现机理。

```text
                           唯一约束与索引的底层绑定闭环
                                        │
           ┌────────────────────────────┼────────────────────────────┐
           ▼                            ▼                            ▼
【自动伴生机制】                 【删除路径唯一性】            【索引命名推导规则】
创建唯一约束时,                 删除唯一约束,                 · 显式命名: 索引名 = 约束名
MySQL 底层必须且自动            只能通过删除底层对应          · 单列未命名: 索引名 = 列名
创建同名的 "唯一索引"           唯一索引来实现!               · 复合未命名: 索引名 = 第一列列名
```

#### 核心事实链条
1. **自动伴生唯一索引**：当在某个列（或列组合）上声明了唯一约束时，MySQL 底层存储引擎会**自动且无条件地在背后为该列创建一个唯一索引（Unique Index）**。因为要快速判断新插入的值是否重复，必须依赖 B+ 树索引结构实现 $O(\log N)$ 级的检索，否则每次插入都要进行全表扫描。
2. **删除约束即删除索引**：MySQL 官方并没有提供独立的物理约束删除指令，**删除唯一约束的唯一法定途径，就是将底层伴生的唯一索引删除**！
3. **删除语法规范**：
   ```sql
   ALTER TABLE 表名 DROP INDEX 索引名;
   ```
4. **索引名称定位规则**：既然删除索引必须指定索引名，那么这个索引的名字到底叫什么？
   - **规则一**：如果创建约束时显式指定了约束名（如 `CONSTRAINT uk_test2_email`），则**唯一索引名完全等于该约束名**（即 `uk_test2_email`）。
   - **规则二**：如果创建单列唯一约束时未指定名称，则**唯一索引名默认等于该字段列名**（如 `last_name`）。
   - **规则三**：如果创建多列复合唯一约束时未指定名称（如前面选课表的 `UNIQUE KEY (sid, cid)`），则**唯一索引名默认等于小括号内排在第一位的字段列名**（即 `sid`）。可以通过 `information_schema.TABLE_CONSTRAINTS` 验证，其 `CONSTRAINT_NAME` 正是 `sid`。

#### 删除实操演示
针对我们测试表 `test2` 中现存的唯一约束，执行删除动作：

```sql
-- 1. 删除通过列级约束声明、未显式命名的单列唯一约束（索引名即列名 last_name）
ALTER TABLE test2 DROP INDEX last_name;

-- 2. 删除显式指定了约束名的唯一约束（索引名即约束名 uk_test2_sal）
ALTER TABLE test2 DROP INDEX uk_test2_sal;
```

执行后，再次运行 `DESC test2;`，可以看到 `last_name` 和 `salary` 字段对应的 `UNI` 索引标记已经彻底消失，约束解除。此时再次向对应字段写入完全重复的值，数据库将顺利放行。

### 本讲提到的题目与认知复盘

#### 题目 1：在 MySQL 中，为一个字段添加了 UNIQUE 唯一约束后，能否向该字段多次插入 NULL 值？为什么？
- **解析**：
  可以多次插入 `NULL`。
  其根本原因在于 SQL 体系中的三值逻辑规范：`NULL` 代表“未知”或“未定义”。在关系代数运算中，任何两个 `NULL` 之间进行等值比较（`NULL = NULL`）其返回结果都是 `UNKNOWN`，而非 `TRUE`。因此，数据库判定各个 `NULL` 记录彼此互不冲突，故唯一约束默认放行多个 `NULL` 记录。若要强制杜绝 `NULL`，需配合 `NOT NULL` 一并使用。

#### 题目 2：在系统建模中，为什么用户的姓名（last_name）和员工的工资（salary）被视为绝对不可建立 UNIQUE 约束的典型反例？
- **解析**：
  - 姓名不可加 `UNIQUE`：由于自然人重名现象极其普遍，一旦将姓名设为唯一键，会导致同名同姓的合法用户根本无法完成注册或入职建档；
  - 薪资不可加 `UNIQUE`：在企业经营与密薪制管理下，相同岗位、相同年资的员工拿相同数值的薪资是完全正常的物理事实，给薪资加唯一键会导致正常的同岗位薪资无法录入，严重脱离现实业务逻辑。

#### 题目 3：简述 MySQL 中删除唯一约束的标准 SQL 语法及其底层实现原理。如果一个复合唯一约束在创建时没有显式起名（例如 UNIQUE KEY(col1, col2)），如何知道其删除时应指定的名称？
- **解析**：
  - **语法**：`ALTER TABLE 表名 DROP INDEX 索引名;`。
  - **原理**：MySQL 中唯一约束是直接依附并绑定在底层的“唯一索引”之上实现的。引擎没有独立的物理约束销毁逻辑，消除唯一约束的唯一手段就是销毁其对应的唯一索引。
  - **未起名的复合约束定名法则**：当省略显式约束命名时，MySQL 会自动抓取括号内定义的**第一个列的列名**作为该复合唯一索引的名称。因此针对 `UNIQUE KEY(col1, col2)`，其删除指令为 `ALTER TABLE 表名 DROP INDEX col1;`。

## 69-主键约束的使用
> 对应分集：P69 | 原始标题：《69-主键约束的使用》

数据表里存了成千上万条记录，怎么确保能准确揪出某一条特定的行，而不是抓出一把分不清谁是谁的数据？

我们在最开始探讨数据库约束时，反复强调过一个核心维度——数据的完整性。在完整性体系中，首当其冲的就是“实体完整性（Entity Integrity）”。实体完整性要求在同一个数据表内，绝不能存在两条完全相同、无法相互区分的记录。如果在业务执行过程中，系统查出两行数据所有字段一模一样，业务端根本无法判断该扣谁的钱、该发谁的货，整张表的数据可用性就彻底崩溃了。

在关系型数据库中，解决实体完整性最高效、最根本的武器就是主键约束（`PRIMARY KEY`）。

---

### 主键约束的核心语义与底层约束特征

#### 实体完整性与行的唯一标识

主键（Primary Key）的核心职能，就是用来唯一地标识表中的某一行记录。

有同学可能会问：前面我们不是学过唯一性约束（`UNIQUE`）吗？如果把员工的邮箱 `email` 字段加上唯一约束，每个员工邮箱都不一样，不就已经实现唯一性了吗？

答案是：不一定。唯一约束虽然要求值不能重复，但它允许字段多次插入 `NULL`。假设业务代码执行 `WHERE email IS NULL` 查询，屏幕上可能瞬间弹出来十几条甚至成百上千条记录。只要存在空值，这一行记录就失去了精准定位的基准。为了让一条记录在任何时间、任何条件下都能被锁定，我们必须在“唯一”的基础之上，强制要求该字段“非空”。

```text
+-------------------+      +-------------------+      +----------------------------+
| 唯一约束 (UNIQUE)  |  +   | 非空约束(NOT NULL)|  =   |  主键约束 (PRIMARY KEY)    |
| 允许出现多次 NULL  |      | 拒绝 NULL 写入    |      |  绝对非空 + 全局绝对唯一    |
+-------------------+      +-------------------+      +----------------------------+
```

> **定义**：主键约束（`PRIMARY KEY`）在语义上等价于“唯一约束 + 非空约束”的严格组合。声明为主键的列，既不允许多次重复，也不允许存放任何 `NULL` 值。

一个极其关键的物理规则是：**一个表中最多只能有一个主键约束**。无论你在该表中声明的是单列主键还是由多个列组合而成的复合主键，整张表的主键定义有且仅有一套。为什么不能设两个主键？这与 MySQL 底层存储引擎在磁盘上组织数据的数据结构密切相关。

#### 主键索引与 B+ 树的映射关系

在 MySQL 默认的 InnoDB 存储引擎中，数据表中的行数据并不是散乱地堆在磁盘文件里的，它的底层物理存储结构是一棵 B+ 树（B+ Tree）。

整个数据表所有行记录的物理排布与存储叶子节点，全都是依照主键索引构建起来的。这棵树也被称作聚簇索引（Clustered Index）。如果允许一张表并存两个互不干涉的主键，底层物理引擎就会彻底陷入混乱——整张表的数据到底依照哪一个字段的顺序去落盘？树的分裂与节点寻址到底听谁的？

```text
                  +-----------------------+
                  |  根节点 (B+ Tree Root) |
                  |  [PK: 10]   [PK: 50]  |
                  +-----------+-----------+
                              |
            +-----------------+-----------------+
            |                                   |
  +---------v---------+               +---------v---------+
  |  分支节点 (Branch)|               |  分支节点 (Branch)|
  |  [PK: 1]  [PK: 5] |               |  [PK: 20] [PK: 35]|
  +----+---------+----+               +----+---------+----+
       |         |                         |         |
+------v---+ +---v------+           +------v---+ +---v------+
| 叶子节点 | | 叶子节点 |           | 叶子节点 | | 叶子节点 |
| [PK:1,行]| | [PK:5,行]| <=======> | [PK:20,行]| | [PK:35,行]|
+----------+ +----------+           +----------+ +----------+
       叶子节点双向链表有序贯通，叶子节点内部直接存放整行真实数据
```

如上图所示，B+ 树的根节点与分支节点只负责维护主键索引键值的路由，而底层的叶子节点直接存放着整行的数据内容。由于整张表物理上只有一套数据存储体系，因此主键只能有一个。

基于主键检索时，查询引擎可以直接顺着主键 B+ 树在 $O(\log N)$ 的时间复杂度内精确定位到叶子节点，读取整行数据，效率极高。而如果使用普通辅助索引（比如普通 `UNIQUE` 索引），辅助索引树的叶子节点存放的仅仅是对应记录的主键值，引擎查到主键值后，还必须拿着该主键值到主键 B+ 树中再走一次完整的寻址过程，这个过程在工程上被称为**回表**。这也从底层原理上解释了主键在表结构设计中的绝对统治地位。

---

### 建表阶段定义主键约束的两种语法形式

#### 列级约束语法与系统默认命名

在 `CREATE TABLE` 语句中，最直接的方式是在定义字段类型之后，紧跟 `PRIMARY KEY` 关键字。这种直接依附在特定列定义后面的语法被称为列级约束。

在设计员工信息表时，部门编号 `department_id` 或员工编号 `id` 这类天然具备唯一编号性质的列，最适合作为主键：

```sql
CREATE TABLE test4 (
    id INT PRIMARY KEY,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2),
    email VARCHAR(25)
);
```

执行创建后，通过查看表约束的元数据视图，检验系统为该主键赋予的标识：

```sql
SELECT * 
FROM information_schema.TABLE_CONSTRAINTS 
WHERE table_name = 'test4';
```

查询结果中，该表的约束类型（`CONSTRAINT_TYPE`）显示为 `PRIMARY KEY`，而约束名称（`CONSTRAINT_NAME`）则固定为 `PRIMARY`。在列级约束语法下，SQL 不允许用户显式指定约束名称。

#### 表级约束语法与自定义名称失效现象

除在列后直接声明外，还可以在所有列声明完毕后，在语句末尾以独立的子句形式声明主键，这就是表级约束。

很多开发者在编写外键或唯一约束时习惯使用 `CONSTRAINT constraint_name` 给约束显式命名。但如果在主键约束上尝试显式命名，会发生什么？

```sql
CREATE TABLE test5 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2),
    email VARCHAR(25),
    -- 尝试使用表级约束语法显式命名主键约束
    CONSTRAINT pk_test5_id PRIMARY KEY (id)
);
```

上述 SQL 执行完全正常，没有任何语法报错。但当我们再次去元数据字典或图形化工具中检查索引与约束名称时：

```sql
SELECT 
    CONSTRAINT_NAME, 
    CONSTRAINT_TYPE 
FROM information_schema.TABLE_CONSTRAINTS 
WHERE table_name = 'test5';
```

查询返回的结果中，`CONSTRAINT_NAME` 依然是冷冰冰的 `PRIMARY`，而不是我们写的 `pk_test5_id`。

> **结论**：在 MySQL 中，主键约束与底层对应的主键索引名称**永远是 `PRIMARY`**。即使在建表或修改表时使用 `CONSTRAINT 名字` 进行了自定义命名，MySQL 也会无条件忽略该名字，强制重置为 `PRIMARY`。因此，在表级主键定义中编写 `CONSTRAINT 自定义名称` 没有任何实际意义，直接书写 `PRIMARY KEY (列名)` 即可。

#### 插入操作的数据校验与报错拦截

通过对建好的 `test4` 表执行真实的插入测试，可以直观观察主键约束对脏数据的防御机制。

写入首条标准数据：

```sql
INSERT INTO test4(id, last_name, salary, email) 
VALUES (1, 'Tom', 4500.00, 'tom@qq.com');

SELECT * FROM test4;
```

控制台成功查询到该记录。紧接着，我们执行两次违规插入，分别测试其对“重复值”和“空值”的拦截表现。

**测试场景 A：主键值重复**

```sql
-- 试图再次插入主键 id 为 1 的数据
INSERT INTO test4(id, last_name, salary, email) 
VALUES (1, 'Jerry', 5500.00, 'jerry@126.com');
```

执行后直接报错，拦截信息明确指向主键唯一性：
`ERROR 1062 (23000): Duplicate entry '1' for key 'test4.PRIMARY'`

**测试场景 B：主键值显式或隐式赋予 NULL**

```sql
-- 显式将主键赋值为 NULL
INSERT INTO test4(id, last_name, salary, email) 
VALUES (NULL, 'Jerry', 5500.00, 'jerry@126.com');
```

或者在指定插入列时直接省略 `id` 且该列未配置默认生成规则：

```sql
INSERT INTO test4(last_name, salary, email) 
VALUES ('Jerry', 5500.00, 'jerry@126.com');
```

执行均会直接中断并抛出错误：
`ERROR 1048 (23000): Column 'id' cannot be null`

这两处报错在底层直接印证了主键的核心语义：非空且绝对唯一。

### 多列复合主键机制与业务场景

在实际业务建模中，很多实体并非由单一的自增数字标识，而是由多个维度的属性共同锁定。此时，需要使用多个列联合在一起充当主键，这就是复合主键（Composite Primary Key）。

#### 复合主键的建表语法

由于涉及多列联合，**复合主键绝不能使用列级约束语法定义，必须使用表级约束语法**。

假设存在一个测试用户表 `user1`，需要将用户名与密码联合作为主键：

```sql
CREATE TABLE user1 (
    id INT,
    name VARCHAR(15),
    password VARCHAR(25),
    -- 表级约束：name 与 password 联合构成复合主键
    PRIMARY KEY (name, password)
);
```

#### 复合键值判定规则与严格非空校验

复合主键的校验逻辑在工程上有两项硬性指标：
1. **联合唯一**：只有参与复合主键的所有列的值全部同时相同，才判定为重复；只要其中任何一列不同，即视为不同记录。
2. **绝对非空**：组成复合主键的每一个列，都必须具备非空属性，**绝不允许任何一列出现 `NULL`**。

写入初始合法记录：

```sql
INSERT INTO user1(id, name, password) 
VALUES (1, 'Tom', 'abc');
```

接下来测试联合唯一性判断。修改用户名，保持密码相同：

```sql
-- 复合键为 ('Tom1', 'abc')，组合值未重复，允许写入
INSERT INTO user1(id, name, password) 
VALUES (1, 'Tom1', 'abc');
```

此时执行 `SELECT * FROM user1`，两条数据共存无误。

但如果测试空值情况，往往容易出现认知偏差。有的开发者会下意识认为：“既然是联合主键，是不是只要两列不同时为空就可以？”

我们通过实验验证这一设想：

```sql
-- 尝试将其中一列设为 NULL
INSERT INTO user1(id, name, password) 
VALUES (1, NULL, '123');
```

SQL 执行后立即报错：
`ERROR 1048 (23000): Column 'name' cannot be null`

> **易错点**：复合主键中的“非空”是对每一个构成列的绝对约束。任何一列传入 `NULL`，无论其余列的值多么唯一，都会直接触发 `Column cannot be null` 异常。必须每一列均有实际值，且各列联合后的元组值在全表中唯一。

#### 复合主键经典应用：选课关联模型

在关系数据库设计中，多对多关联表的建模是复合主键的经典应用场景。例如高校选课系统中的“学生表（Student）”、“课程表（Course）”以及连接两者的“选课记录表（Student_Course）”。

```text
+-----------------------+              +-----------------------+
|    学生表 (Student)   |              |    课程表 (Course)    |
|    student_id (PK)    |              |    course_id (PK)     |
+-----------+-----------+              +-----------+-----------+
            |                                      |
            +------------------+-------------------+
                               |
                   +-----------v-----------+
                   |  选课表 (Student_Course)|
                   |  student_id (FK)      |
                   |  course_id  (FK)      |
                   |  PRIMARY KEY(sid, cid)|
                   +-----------------------+
```

在选课表内部，如果业务上不额外设立自增流水号 `id`，那么一个学生选择一门课程这一业务实体，就是由 `student_id`（学号）与 `course_id`（课程编号）联合决定的。一名学生对同一门课程只能选一次，同时学号与课程编号都必须实打实存在，二者联合设为主键天然契合实体完整性要求。

### 表结构修改中的主键维护操作

在项目迭代过程中，有时建表初期遗漏了主键，或者需要调整主键结构，必须通过 `ALTER TABLE` 语句进行表级结构的动态更迭。

#### 使用 ALTER TABLE 追补主键

假设有一张建表时未设置主键的初始表：

```sql
CREATE TABLE test6 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2),
    email VARCHAR(25)
);
```

此时执行 `DESC test6;`，`id` 字段的 `Key` 列为空，`Null` 列显示为 `YES`，允许为空且无主键索引。

为该表追加主键约束的语法如下：

```sql
ALTER TABLE test6 
ADD PRIMARY KEY (id);
```

追加完成后，再次执行 `DESC test6;` 观察字段元数据变化：
- `Key` 列出现了 `PRI`（Primary Key 标记）；
- `Null` 列自动从 `YES` 翻转为 `NO`。

> **注意**：如果表中已经存在存量数据，执行 `ADD PRIMARY KEY` 的前提是：目标列中已有的数据行必须既没有重复值，也没有任何 `NULL`。如果存量数据中存在脏数据，ALTER 操作会直接中断并抛出异常。

#### 语法层面的主键删除与 NOT NULL 遗留

删除主键约束的语法非常精炼：

```sql
ALTER TABLE test6 
DROP PRIMARY KEY;
```

因为一张表无论怎么折腾，最多只有一个主键，且主键的名字在引擎中固定就叫 `PRIMARY`，所以语法中完全不需要像删除外键那样指定约束名字，直接 `DROP PRIMARY KEY` 即可。

执行删除后，运行 `DESC test6;` 查看表结构细节：
- `Key` 列原本的 `PRI` 标识彻底消失；
- 但此时仔细观察 `Null` 列，`id` 字段的 `Null` 属性**仍然保留为 `NO`**。

很多初学者看到这里，会习惯性地掏出笔记本把这个技术细节记下来，准备当作面试八股文背诵：“在 MySQL 中删除主键约束后，字段原有的非空约束依然保留”。

**千万不要花精力去背这个细节。** 为什么？因为在真实的工程生产环境里，**去删除一个表的主键约束，纯粹是没事找事**。

### 生产环境严禁删除主键与变更主键值的架构深度解析

为什么在实际开发中绝对不允许去删除表中的主键约束？这必须回到第一节讲到的 InnoDB 存储组织架构来解答。

#### 数据物理重构的灾难性代价

前文已经讲明，InnoDB 数据表的全部记录，其底层文件组织形式就是一棵以主键为聚集键的 B+ 树。如果你脑子一热，在生产库上执行了 `ALTER TABLE ... DROP PRIMARY KEY`，底层会发生什么？

1. 表中的聚簇索引树瞬间被判定失效；
2. InnoDB 必须维持表的物理存储组织，它只能退而求其次，在表中搜索是否存在非空的唯一索引（`UNIQUE NOT NULL`）。如果找到了，就用那个列重构整张表的 B+ 树；
3. 如果连非空的唯一索引都没有，InnoDB 的优化器与存储管理模块就必须在后台为每一行记录自动生成一个隐藏的 6 字节 `DB_ROW_ID`，并依据这个隐藏列去强行把整张表重构为一颗新的 B+ 树。

如果这是一张只有几行数据的小玩具表，重构可能耗时几毫秒。但如果这是一张线上运行的千万级核心业务表，删除主键意味着底层几千万条数据行必须在磁盘上全部重新挪动、重新物理排序、重新分裂与分配数据页！这不仅会引发长时间的严重锁表与磁盘 I/O 暴涨，直接导致线上服务雪崩，而且没有任何业务收益。

这就像当年秦朝修建阿房宫，耗费了无数人力物力搭建起了极其庞大的建筑群，虽然还没完全落成，结果你一把大火直接给全烧光了，然后通知所有人推平废墟重新打地基再建一遍。这是极其荒谬、极具毁灭性的操作。

#### 严禁频繁变更主键字段值的性能开销

除了不能删主键，**在日常的 UPDATE 业务操作中，也严禁随意修改主键字段的值**。

在业务数据流转中，员工改名字、调薪资、换部门都很常见，执行对应的 `UPDATE test4 SET salary = ...` 只会修改叶子节点中行记录对应列的物理存储数据。

但如果执行 `UPDATE test4 SET id = 9999 WHERE id = 1`：
- 因为主键决定了该记录在整个 B+ 树中的物理排序位置；
- 将 `id` 从 1 改为 9999，意味着原本位于第一个叶子数据页的行记录必须被物理删除；
- 存储引擎必须在 B+ 树最末端的叶子页中重新开辟空间，将整行数据迁徙过去；
- 这一过程会极其高频地引发 B+ 树的**页分裂（Page Split）**与**页合并（Page Merge）**，导致严重的物理碎片和 I/O 阻塞。

主键自被写入的那一刻起，就应当具备永久不变的唯一标识属性。选定合理的主键策略（如自增整数、业务流水号或雪花 ID），并在数据生命周期内保持其不可变更性，是关系型数据库物理设计中必须死守的底线规范。

## 70-AUTO_INCREMENT
> 对应分集：P70 | 原始标题：《70-AUTO_INCREMENT》

在关系型数据库的日常操作中，主键约束保证了每一行记录的绝对唯一与非空。但在实际业务开发中，由谁来为主键列填入具体的数值？

如果完全依赖业务代码在应用层计算下一个 ID 并显式插入，在高并发插入的场景下，极容易发生并发主键冲突；而如果让用户或者操作员手工输入编号，遗漏与重复更是不可避免。面对这一痛点，数据库引擎提供了开箱即用的自动递增机制——自增约束（`AUTO_INCREMENT`）。

---

### 自增约束的核心概念与语法规范

#### 自动增长的产生背景与业务价值

`AUTO_INCREMENT` 的核心职能是为某个特定列的值提供由数据库内核驱动的自增服务。在执行数据插入（`INSERT`）操作时，如果该列没有被显式赋值，存储引擎会自动在当前已记录的最大数值基础上累加步长（默认步长为 1），生成一个全新的唯一整数。

自增约束通常与主键约束深度绑定使用。它将主键唯一标识的生成逻辑下沉到数据库引擎内部，不仅极大简化了业务层的持久化代码，更借助数据库底层的自增锁与并发控制机制，保证了主键流水号在高并发下的严格单调递增与并发安全。

#### 自增约束的建立语法与三大前置条件

在建表阶段声明自增字段非常简单，只需在列定义末尾添加 `AUTO_INCREMENT` 关键字：

```sql
CREATE TABLE test7 (
    id INT PRIMARY KEY AUTO_INCREMENT,
    last_name VARCHAR(15)
);
```

但在使用 `AUTO_INCREMENT` 时，MySQL 规定了三条必须严格遵守的物理硬性规则：

1. **唯一性（单表限制）**：一个数据表中有且**只能拥有一个**自增列。数据库不允许在一张表中同时为两列配置自动增长。
2. **类型限制（必须为整数）**：被声明为 `AUTO_INCREMENT` 的列，其数据类型必须是整数族类型（如 `TINYINT`、`SMALLINT`、`INT`、`BIGINT` 等）。浮点型或字符串类型严禁配置自增。
3. **索引限制（必须为键）**：自增列**必须是键（Key）的一部分**，通常为主键（`PRIMARY KEY`）或者唯一键（`UNIQUE`）。

如果在建表时试图在一个没有建立任何键索引的普通列上添加自增属性：

```sql
-- 错误示范：未将 id 设为主键或唯一键
CREATE TABLE test_error (
    id INT AUTO_INCREMENT,
    name VARCHAR(15)
);
```

MySQL 执行器会直接中断并抛出语法错误：
`ERROR 1075 (42000): Incorrect table definition; there can be only one auto column and it must be defined as a key`

这一底线限制确保了自增生成的序列值在表中必然具备唯一性寻址与索引支撑。

---

### 数据插入行为与自增计数器推进规则

#### 缺省值与占位符（NULL/0）的递增行为

创建好包含自增主键的表结构后，针对自增字段的数据写入有几种不同的传参方式：

```sql
-- 方式一：在 INSERT 列表中完全省略自增列
INSERT INTO test7(last_name) VALUES ('Tom');

-- 方式二：显式传入 0 作为占位符
INSERT INTO test7(id, last_name) VALUES (0, 'Jerry');

-- 方式三：显式传入 NULL 作为占位符
INSERT INTO test7(id, last_name) VALUES (NULL, 'Bob');
```

执行上述三条插入后，通过 `SELECT * FROM test7;` 查看全表数据：

```text
+----+-----------+
| id | last_name |
+----+-----------+
|  1 | Tom       |
|  2 | Jerry     |
|  3 | Bob       |
+----+-----------+
```

数据呈现出严格的连续累加特征：
- 当省略该字段时，系统自动从 1 开始赋值；
- 当显式向自增列写入 `0` 或 `NULL` 时，MySQL 并没有报错，也没有将 `id` 置为 0 或空，而是将其识别为“请求系统自增”，同样在上一条最大记录值的基础上顺延累加。

#### 人工指定数值、跳跃增长与负数边界

如果我们在插入时既不省略，也不传 0 或 NULL，而是非要强行人工指定一个特定的正数，系统会作何反应？

```sql
-- 人工强行指定一个跳跃数值 10
INSERT INTO test7(id, last_name) VALUES (10, 'Rose');
```

执行完全成功，表中成功新增一条 `id = 10` 的数据。紧接着，如果我们再次使用缺省方式插入新行：

```sql
INSERT INTO test7(last_name) VALUES ('Jack');
```

此时再次查询该表，会发现新记录的 `id` 变成了 **11**。

> **规律**：当人工显式指定一个大于当前自增序列的数值时，自增计数器会被强行拔高至该数值；后续缺省插入的数据，将从这个人为拔高的新最大值开始继续向上累加。

进一步发散思考：如果人工向自增列写入一个负数呢？

```sql
-- 写入一个负数
INSERT INTO test7(id, last_name) VALUES (-10, 'David');
```

SQL 同样执行成功。执行 `SELECT * FROM test7;` 查看结果时，会发现 `-10` 被排在了整张表的最前面。这是因为作为主键索引，底层 B+ 树会按照键值的真实物理大小进行升序组织，负数自然排在正数 1 之前。

但需要明确的是：后续如果不传自增列继续插入数据，引擎依然只会依据全表最大的正数值（此时是 11）继续累加生成 12，而绝不会在负数的基础上向 0 递增。

#### 生产环境中的自增字段使用规范

上述关于显式赋值 10、显式插入负数的操作，纯属用来探索数据库内核边界条件的验证性测试。

在真实的生产开发环境中，必须确立一条死规范：
> **结论**：一旦数据表的主键列配置了 `AUTO_INCREMENT`，在编写任何应用层业务代码的 `INSERT` 语句时，**绝不要将该自增列纳入 INSERT 字段列表**。所有的流水号生成全部交由数据库内核托管，坚决杜绝任何人工干预或跳号传值，避免主键序列产生不可控的碎片空隙与业务歧义。

### 表结构变更中的自增属性管理

在项目迭代中，偶尔会遇到建表初期漏掉了自增属性，或者需要将自增属性解除的表结构维护任务。这可以通过 `ALTER TABLE` 配合 `MODIFY` 子句实现。

#### 使用 ALTER TABLE 为既有字段追加自增

假设建表时仅声明了主键，但未添加自增：

```sql
CREATE TABLE test8 (
    id INT PRIMARY KEY,
    last_name VARCHAR(15)
);
```

通过 `DESC test8;` 查看表结构，`Extra` 列为空，无自增标记。为其追加自增属性的语法如下：

```sql
ALTER TABLE test8 
MODIFY id INT AUTO_INCREMENT;
```

执行后再次查看 `DESC test8;`，`id` 对应的 `Extra` 列成功刷新为 `auto_increment`。

> **注意**：使用 `MODIFY` 追加自增属性的前提，是该列必须已经在表内具备了主键约束或唯一性约束。如果是普通无索引字段直接执行上述语句，同样会触发 `Incorrect table definition` 错误。

#### 使用 MODIFY 语法剥离自增属性

如果需要将自增属性剥离，只需使用 `MODIFY` 重新定义该列的数据类型与约束，且**在语句中不写 `AUTO_INCREMENT` 关键字**即可：

```sql
ALTER TABLE test8 
MODIFY id INT;
```

执行完成后，`DESC test8;` 中 `Extra` 列的 `auto_increment` 标记彻底移除，主键退化为纯手工填值的普通主键。

在工程实践中，由于数据库建模规范在概要设计与详细设计阶段就必须敲定，自增主键绝大多数都是在 `CREATE TABLE` 阶段一次性成型，极少在存量业务表上进行追加或剥除。

### MySQL 5.7 与 8.0 自增计数器底层机理对比

在 MySQL 的版本演进史中，自增计数器在系统重启后的持久化表现，是 5.7 与 8.0 之间极具标志性的底层架构重构之一。

#### 删除末尾数据与重启服务的对比实验

为了彻底观察这一差异，我们设计一组严格受控的测试流程，分别在 MySQL 5.7 与 MySQL 8.0 两个独立实例上执行完全相同的操作。

**第一阶段：创建表并写入初始数据**

```sql
CREATE TABLE test9 (
    id INT PRIMARY KEY AUTO_INCREMENT
);

-- 连续插入 4 条数据
INSERT INTO test9 VALUES (0), (0), (0), (0);
SELECT * FROM test9;
```
此时两版本表中均存在四条记录：`1, 2, 3, 4`。

**第二阶段：删除尾部记录并产生裂缝**

```sql
-- 删除末尾的 4
DELETE FROM test9 WHERE id = 4;

-- 再次插入一条自增记录
INSERT INTO test9 VALUES (0);
SELECT * FROM test9;
```
此时表中数据为 `1, 2, 3, 5`。因为曾经插入过 4，即使被删除，自增计数器依然推进到了 5。这种中间缺失了 4 的序列现象被称为自增裂缝。

**第三阶段：删除最新的 5 并重启服务**

```sql
-- 删除最新的 5，此时表中仅剩 1, 2, 3
DELETE FROM test9 WHERE id = 5;
SELECT * FROM test9;
```
现在两个版本的数据表中，都实实在在只保留着 `1, 2, 3` 三条数据。

此时，我们通过命令行以管理员身份分别重启两个版本的数据库服务：

```cmd
-- 重启 MySQL 5.7
net stop mysql57
net start mysql57

-- 重启 MySQL 8.0
net stop mysql80
net start mysql80
```

**第四阶段：重启后执行首次插入**

服务重启成功后，重新连入数据库，在两边同时执行一条无参自增插入：

```sql
INSERT INTO test9 VALUES (0);
SELECT * FROM test9;
```

此时查看查询结果，戏剧性的分歧出现了：
- **在 MySQL 5.7 中**：新插入的记录 `id` 赫然显示为 **4**！
- **在 MySQL 8.0 中**：新插入的记录 `id` 坚定地显示为 **6**！

#### MySQL 5.7 内存计数器与重启回退缺陷

为什么 MySQL 5.7 会退回到 4？

在 MySQL 5.7 及更早的 InnoDB 引擎实现中，**表的自增计数器（Auto-increment Counter）仅仅保存在操作系统的内存中，从来不向磁盘文件持久化**。

```text
======================= MySQL 5.7 自增机制 =======================

[ 运行中 ]
  内存计数器: 1 -> 2 -> 3 -> 4 -> 5
  磁盘数据表: [id: 1, 2, 3] (4 与 5 已被 DELETE)

             |
             v 服务器重启 (Crash / Restart)
               内存被清空，计数器彻底丢失！
             |
             v
[ 重启后首次访问 ]
  InnoDB 执行内部查询: SELECT MAX(id) FROM test9 FOR UPDATE;
  取得当前磁盘存量最大值: MAX(id) = 3
  重新初始化内存计数器: Counter = 3 + 1 = 4
  新插入记录分配 id: 4  (发生自增序列历史回退！)
==================================================================
```

由于内存易失，当 MySQL 5.7 服务重启后，内存中的计数器归零。当该表接收到重启后的第一次查询或插入请求时，InnoDB 会在底层被动触发一次全表扫描寻址：
`SELECT MAX(id) FROM test9 FOR UPDATE;`

在存量数据只剩下 `1, 2, 3` 的情况下，引擎检索出当前磁盘上的最大值是 3，于是强行把内存计数器初始化为 `3 + 1 = 4`。

这一设计在特定业务场景下会引发灾难性后果：如果外部系统（如支付流水、第三方发票系统）已经引述并缓存了曾经生成过的 `id = 4` 和 `id = 5`，服务器意外重启后，数据库竟然重新复用了这两个旧编号，直接打破了主键的业务不可篡改性与全局时序性。

#### MySQL 8.0 Redo Log 持久化机制与崩溃恢复

为了彻底终结这一历史包袱，MySQL 8.0 对自增计数器的生命周期进行了底层物理重构。

```text
======================= MySQL 8.0 自增持久化机制 =======================

[ 每次自增递增 ]
  Counter = 5 -> 写入 Redo Log (重做日志) -> 内存计数器同步更新
  检查点 (Checkpoint) -> 计数器最新值刷新到系统元数据字典

             |
             v 服务器重启 (Crash / Restart)
               内存清空，但 Redo Log 与系统表数据完好无损！
             |
             v
[ 重启阶段恢复 ]
  引擎直接从 Redo Log 和元数据字典读取自增计数器最新峰值:
  读取到历史峰值: Counter = 5
  无需执行 SELECT MAX(id)！
  新插入记录直接分配: 5 + 1 = 6  (序列严格保持单调递增)
========================================================================
```

在 MySQL 8.0 的 InnoDB 体系中：
1. **Redo Log 协同写盘**：每一次计数器的自增变动，都会作为重做事件被同步写入 `Redo Log`（重做日志）中。
2. **元数据字典持久化**：在发生系统检查点（Checkpoint）时，最新的计数器数值会被精确落盘到 InnoDB 内置的元数据字典（Metadata Dictionary）系统表中。
3. **崩溃恢复无缝衔接**：数据库服务重启时，存储引擎在 Crash Recovery 流程中，直接从重做日志与元数据字典中还原崩溃前的最大计数器峰值，根本不需要向数据表发起 `MAX(id)` 查询。

即使历史上的 4 和 5 已经被彻底物理删除，8.0 依然清清楚楚地记得“这个序列曾经走到了 5”，因此重启后能够平滑衔接到 6。这项改进彻底消除了主键序列回退的风险，为现代分布式事务与微服务架构下的主键审计提供了强一致性的底层保障。

## 71-外键约束的使用
> 对应分集：P71 | 原始标题：《71-外键约束的使用》

在多表关联的业务场景中，例如员工表与部门表，如果员工表里的某位新员工被随手分配到了一个根本不存在的“999 号部门”，或者人事部门随手注销了“财务部”，导致该部门原有的几十名员工在系统里变成了归属不明的“孤魂野鬼”，整个系统的数据一致性将彻底沦陷。

在数据库理论中，实体之间的这种依附与引用关系被称为“引用完整性（Referential Integrity）”。关系型数据库用来在物理存储层面强制捍卫引用完整性的核心工具，就是外键约束（`FOREIGN KEY`）。

---

### 引用完整性与外键约束的核心规范

#### 引用完整性与主从表拓扑结构

外键约束（`FOREIGN KEY`）专门用于限定两张表之间某个字段的引用关联。它建立起两个实体表之间的“父子”或“主从”层级：

```text
+----------------------------+             +----------------------------+
|       主表 (父表 Parent)   |             |       从表 (子表 Child)    |
|   dept (部门表)            |             |   emp (员工表)             |
+----------------------------+             +----------------------------+
| * did: 10                  | <---------- |   eid: 1001                |
|   dname: 'IT部'            |   引用关系  |   ename: 'Tom'             |
+----------------------------+  (Foreign)  | * dept_id: 10 (外键列)     |
                                           +----------------------------+
```

打个形象的比方：主表和从表好比两个互相独立的国家，从表中的外键列就相当于从表派驻到主表中的“外交官”。两张表之间能否建立合法建交，必须依凭这位“外交官”与主表特定凭证之间的精确比对。

#### 外键列的三大物理硬性约束

在 MySQL 中创建外键，绝不是随意拉扯两个列就能连起来的。内核在解析外键定义时，有三条不可逾越的物理红线：

1. **主表被引用列的索引限制**：从表外键列所引用的**主表那一列，必须是主表的主键（`PRIMARY KEY`）或者唯一键（`UNIQUE`）**。如果主表被引用的字段仅仅是一个没有任何唯一性保障的普通列，建表必抛异常。
2. **数据类型与逻辑意义一致**：从表的外键列与主表被引用的主键/唯一键列，在数据类型上必须完全一致（或严格兼容），两者的业务逻辑语义必须完全对齐。
3. **命名空间与多外键支持**：一个数据表中可以声明**多个外键约束**。例如经典的员工表 `employees`，其内部既可以通过 `department_id` 外键关联部门表，也可以通过 `job_id` 外键关联岗位表，还可以通过 `manager_id` 自身外键关联上级管理者。

#### 建表与删表的物理时序法则

由于外键建立起了严格的物理依赖拓扑，表的生命周期维护顺序必须严格倒序对齐：

> **结论**：
> - **建表时序**：必须**先创建主表**（父表），**再创建从表**（子表）。因为从表在解析外键时需要立即校验主表及其被引用字段的存在性；
> - **删表时序**：必须**先删除从表**（子表），**再删除主表**（父表）。如果在从表尚存且维持引用时强行删除主表，数据库会直接拒绝执行并报错拦截。

### 外键约束的创建语法与元数据索引

#### 表级约束定义与命名规范

外键约束必须在建表语句的末尾使用表级约束语法显式定义。

我们先构建一个未设立主键的主表 `dept1`：

```sql
CREATE TABLE dept1 (
    dept_id INT,
    dept_name VARCHAR(15)
);
```

紧接着，我们尝试直接创建从表 `emp1` 并建立外键关联：

```sql
CREATE TABLE emp1 (
    emp_id INT PRIMARY KEY AUTO_INCREMENT,
    emp_name VARCHAR(15),
    department_id INT,
    -- 尝试定义外键约束
    CONSTRAINT fk_emp1_dept_id FOREIGN KEY (department_id) REFERENCES dept1(dept_id)
);
```

执行后系统直接抛出致命错误：
`ERROR 1822 (HY000): Failed to add the foreign key constraint. Missing index for constraint 'fk_emp1_dept_id' in the referenced table 'dept1'`

报错信息明确指出：主表 `dept1` 的被引用列缺少索引支撑！这直接证实了前述第 1 条硬性规则。

我们通过 `ALTER TABLE` 补齐主表的主键约束：

```sql
ALTER TABLE dept1 
ADD PRIMARY KEY (dept_id);
```

此时再次执行从表 `emp1` 的建表语句，控制台顺利通过。

```sql
SELECT 
    CONSTRAINT_NAME, 
    CONSTRAINT_TYPE 
FROM information_schema.TABLE_CONSTRAINTS 
WHERE table_name = 'emp1';
```

查询结果中清晰地列出了两条记录：`PRIMARY KEY`（主键约束）与 `fk_emp1_dept_id`（外键约束）。

#### 自动生成的外键普通索引及其机制

细心的开发者在执行 `DESC emp1;` 时会注意到，外键列 `department_id` 对应的 `Key` 字段显示为 `MUL`（Multiple）。

这是因为在 MySQL 中，**一旦给某个字段添加了外键约束，存储引擎会自动在该从表的外键字段上建立一个普通的 B+ 树索引**。这一底层机制非常精妙：它确保了未来每次向子表写入数据、或者父表发生更新删除时，引擎不必进行代价极高的子表全表扫描，而是借助该普通索引以 $O(\log N)$ 的极速定位子表记录，进行引用合法性验证。

### 外键拦截机制与数据写入行为测试

有了外键这道铁闸，数据库在面对日常增删改（`DML`）时，究竟如何进行安全拦截？

#### 从表插入非法引用的拦截表现

当前主表 `dept1` 尚未录入任何部门。此时我们直接向从表 `emp1` 写入一条关联 10 号部门的员工记录：

```sql
-- 试图插入归属 10 号部门的员工
INSERT INTO emp1(emp_id, emp_name, department_id) 
VALUES (1001, 'Tom', 10);
```

系统立即抛出拦截报错：
`ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails ('dbtest13'.'emp1', CONSTRAINT 'fk_emp1_dept_id' FOREIGN KEY ('department_id') REFERENCES 'dept1' ('dept_id'))`

错误非常精确：“无法添加或更新子表行，外键约束校验失败”。这迫使开发人员必须先向主表添加合法的部门，才能录入员工：

```sql
-- 先在主表中添加 10 号 IT 部门
INSERT INTO dept1(dept_id, dept_name) VALUES (10, 'IT');

-- 再次向从表插入员工，执行成功！
INSERT INTO emp1(emp_id, emp_name, department_id) VALUES (1001, 'Tom', 10);
```

#### 主表非法删除与更新的阻断机制

如果主表中已经有员工依附于 10 号部门，此时有人试图直接在主表中删除或修改 10 号部门：

**测试 A：强行删除被引用的主表记录**

```sql
DELETE FROM dept1 WHERE dept_id = 10;
```

执行立刻被内核阻止：
`ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails`

**测试 B：强行修改被引用的主表键值**

```sql
UPDATE dept1 SET dept_id = 20 WHERE dept_id = 10;
```

同样被直接阻止，抛出完全相同的错误代码 1451。

在日常业务操作中，语法完全合规的 `DELETE` 或 `UPDATE` 竟然会莫名其妙执行失败，这往往就是外键在底层严防死守、阻止数据孤岛产生的直接体现。

### 表结构维护与外键约束的管理

#### 使用 ALTER TABLE 追加外键约束

如果系统初期两张表已经独立建好，后期需要建立物理关联：

```sql
CREATE TABLE dept2 (
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(15)
);

CREATE TABLE emp2 (
    emp_id INT PRIMARY KEY AUTO_INCREMENT,
    emp_name VARCHAR(15),
    dept_id INT
);
```

使用 `ALTER TABLE` 为 `emp2` 追加外键约束：

```sql
ALTER TABLE emp2 
ADD CONSTRAINT fk_emp2_dept_id FOREIGN KEY (dept_id) REFERENCES dept2(dept_id);
```

#### 外键约束与对应普通索引的双重清理

当业务调整需要废弃外键时，必须使用指定外键约束名的方式执行删除（因为一张表可能存在多个外键）：

```sql
ALTER TABLE emp1 
DROP FOREIGN KEY fk_emp1_dept_id;
```

运行元数据查询，外键约束确实消失了。但如果此时执行 `SHOW INDEX FROM emp1;` 查看索引列表，会发现原本由外键附带生成的普通索引 `fk_emp1_dept_id` **依然顽固地残留在表中**！

> **易错点**：删除外键约束（`DROP FOREIGN KEY`）仅仅移除了外键的校验机制，但当初自动创建的底层索引不会被联动删除。如果需要彻底净化表结构，必须显式调用索引清理语句：
> ```sql
> ALTER TABLE emp1 DROP INDEX fk_emp1_dept_id;
> ```

### 外键约束等级与级联操作机制

在很多真实业务场景中，父表发生变动时，直接抛出异常阻止用户并不是最佳体验。例如：总公司调整了部门编码，难道不能让旗下员工的部门编码自动跟着修改吗？总公司撤销了某个部门，难道不能把员工的部门字段暂时置为待分配（`NULL`）吗？

为了支持这种灵活的联动，外键约束引入了级联操作等级。

#### 级联模式核心语义对比

在定义外键时，可以通过 `ON UPDATE` 和 `ON DELETE` 分别指定联动策略：

| 约束等级关键字 | 核心处理逻辑 | 适用场景与业务效果 |
| :--- | :--- | :--- |
| **CASCADE** | **级联联动**：父表记录更新或删除时，子表对应记录自动同步更新或同步物理删除 | 适合强生命周期绑定的主从结构（如订单主表与订单明细表） |
| **SET NULL** | **置空兜底**：父表记录更新或删除时，子表对应列自动置为 `NULL` | 适合弱依附关系（如部门撤销，员工暂留公司待转岗） |
| **RESTRICT / NO ACTION** | **严格阻止**：子表若存在关联记录，绝对拒绝父表的更新或删除操作（默认行为） | 核心资产、关键业务维度，必须人工逐级确认 |
| **SET DEFAULT** | **默认值回退**：父表变动时子表回退至列默认值（MySQL InnoDB 引擎暂不支持） | 规范定义，但在 MySQL 中实际不可用 |

#### ON UPDATE CASCADE 与 ON DELETE SET NULL 实测验证

我们设计一组生产中最常用的级联组合实验：更新时同步变更，删除时置空保护。

```sql
-- 1. 创建部门主表
CREATE TABLE dept (
    did INT PRIMARY KEY,
    dname VARCHAR(15)
);

-- 2. 创建员工从表，配置复合级联规则
CREATE TABLE emp (
    eid INT PRIMARY KEY,
    ename VARCHAR(15),
    did INT,
    CONSTRAINT fk_emp_did FOREIGN KEY (did) REFERENCES dept(did)
        ON UPDATE CASCADE 
        ON DELETE SET NULL
);

-- 3. 填充主表部门数据 (1001, 1002, 1003)
INSERT INTO dept VALUES (1001, '教学部'), (1002, '财务部'), (1003, '咨询部');

-- 4. 填充员工数据：张三李四归属 1001，王五归属 1002
INSERT INTO emp VALUES (1, '张三', 1001), (2, '李四', 1001), (3, '王五', 1002);
```

**实验 A：验证级联更新（ON UPDATE CASCADE）**

将主表中的财务部编号由 1002 变更为 1004：

```sql
UPDATE dept SET did = 1004 WHERE did = 1002;
```

执行后立即查询员工从表：

```sql
SELECT * FROM emp WHERE ename = '王五';
```

结果显示，王五的 `did` 字段已经被数据库内核**全自动同步刷新为 1004**！级联更新生效。

**实验 B：验证级联置空（ON DELETE SET NULL）**

将主表中的 1004 部门物理删除：

```sql
DELETE FROM dept WHERE did = 1004;
```

语句执行成功，并没有像以前一样报错。再次查询员工表：
王五依然健在，但他所属的 `did` 已经全自动被安全重置为 `NULL`。

> **提示**：若要在外键上配置 `ON DELETE SET NULL`，从表的外键字段本身绝对不能有 `NOT NULL` 约束，否则引擎在置空时会因列属性冲突而报错。

#### 生产环境推荐的级联策略组合

在涉及物理外键的传统系统中，最成熟的配置组合通常是：
`ON UPDATE CASCADE ON DELETE RESTRICT`

即：主表的编码更新允许自动同步到底层从表，避免主从编码失序；但如果试图删除父实体，必须严防死守拒绝执行，杜绝因一次手抖误删主表而导致下游成千上万条明细数据被连环“火烧连营”式物理抹杀。

---

### 生产架构深度剖析：物理外键与应用层逻辑外键的取舍

讲到这里，外键约束的功能已经完备无缺。但在当今主流的互联网架构与中大型企业开发中，一个最具颠覆性的行业现实是：**大部分系统在数据库物理建模时，严禁建立物理外键！**

#### 高并发下物理外键的锁开销与性能损耗

在单机、低并发的管理信息系统（MIS）中，物理外键是保证数据干净的好帮手。但在大并发、高负载的互联网系统中，物理外键直接构成了吞吐量的致命杀手：

```text
               +-------------------------------------------+
               |  业务并发写入: INSERT INTO emp (员工表)    |
               +---------------------+---------------------+
                                     |
                                     v
               +-------------------------------------------+
               |  MySQL 内核自动发起跨表校验:             |
               |  必须持有 dept (部门表) 共享锁 (S锁)      |
               |  若有多级外键，将引发锁链路连环蔓延       |
               +---------------------+---------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
| 并发写冲突严重: 导致主表并发阻塞、锁等待甚至死锁 (Deadlock)             |
| 级联操作更容易引发灾难性的"更新风暴 (Update Storm)", 拖垮整机 I/O         |
+-------------------------------------------------------------------------+
```

1. **频繁跨表校验与锁升级**：每次向子表插入或修改数据，数据库都必须在内部向父表申请行锁或表锁进行校验。当写入并发达到数千甚至数万 QPS 时，大量的数据库连接被阻塞在跨表行锁的等待上，系统吞吐量呈断崖式下跌。
2. **级联风暴**：一旦触发生命周期较长的主表级联删除或更新，数据库后台会瞬间裂变出数十万次关联子表修改，产生严重的“更新风暴（Update Storm）”，将整个数据库服务器的 I/O 和 CPU 瞬间打满。

#### 阿里巴巴开发手册【强制】禁用外键与级联的架构成因

国内工业界广泛遵循的《阿里巴巴 Java 开发手册》中明确立项了一条军规级规范：

> **【强制】不得使用外键与级联，一切外键概念必须在应用层解决。**
> 
> *说明：学生表中的 student_id 是主键，那么成绩表中的 student_id 为外键。如果更新学生表中的 student_id，同时触发成绩表中的 student_id 更新，即为级联更新。外键与级联引用的结构适合于单机低并发，不适合分布式、高并发集群；级联更新是强阻塞，存在数据库更新风暴的风险；外键还会极大地影响数据库的插入速度。*

这一规范的本质，就是把原本压在数据库引擎单点上的强计算与校验开销，卸载出来并分摊到横向扩展能力极强的应用服务器集群上。

#### 分布式、微服务与分库分表下的逻辑外键治理

进入微服务与分布式数据库架构时代后，物理外键在物理拓扑上直接失去了生存土壤：

```text
[ 用户服务 / 用户微服务 ]                [ 订单服务 / 订单微服务 ]
           |                                       |
           v                                       v
+----------------------+               +----------------------+
| 用户中心数据库 (DB-A) |               | 交易订单数据库 (DB-B) |
| 表: user (user_id PK)|               | 表: orders           |
| (物理节点 192.168.1.10)|               | (物理节点 192.168.1.20) |
+----------------------+               +----------------------+
           \                                       /
            \--- 物理外键彻底失效！无法跨网络建立物理约束 ---/
```

- **物理边界隔离**：在微服务体系下，“用户表”归属用户中心服务，存放在物理节点 A；“订单表”归属交易服务，存放在物理节点 B。单机数据库引擎根本无法跨越网络和跨物理实例去建立底层外键。
- **分库分表断链**：当单表数据破千万、通过 Sharding-JDBC 或 MyCat 按用户 ID 哈希分片到多个子库后，父表与子表往往被拆分到完全不同的物理分片中，物理外键机制彻底报废。

现代工程的最佳实践是：**保留“逻辑外键”概念，但坚决剥离“物理外键”约束**。

即在从表的设计中，依然保留 `department_id` 这个语义字段，但是在 `CREATE TABLE` 时绝不写 `FOREIGN KEY` 语句。引用的合法性校验下沉至业务逻辑层：在执行插入前，通过 Spring Boot / Java 代码先从 Redis 缓存中校验部门是否存在；多表之间的数据生命周期同步，通过分布式事务（如 Seata）或异步消息队列（MQ）进行最终一致性保障。

## 72-检查约束与默认值约束
> 对应分集：P72 | 原始标题：《72-检查约束与默认值约束》

在企业数据治理中，仅仅保证数据非空或唯一往往远远不够。例如员工的薪资，如果人事录入时手抖输了一个负数或者几百块钱，或者系统默认把状态置为了空值，都会直接把脏数据带入财务流水中。

数据表中的字段需要有明确的业务取值范围，以及在未传参时的兜底预设。这就是关系型数据库中的检查约束（`CHECK`）与默认值约束（`DEFAULT`）。

---

### 检查约束 CHECK 的语义、语法与跨数据库支持

#### 业务数据边界与检查约束的定义语法

检查约束（`CHECK`）的核心职能是验证表中某个字段录入的数据是否满足特定的布尔逻辑表达式或数值范围要求。

以企业员工薪资为例：在各大一线城市，人社部门通常会出台法定最低工资标准，用工单位给员工开出的薪资绝不能低于这个红线。在大城市生活，吃穿等日常消费实际上与很多二三线城市相差不大甚至打折更频繁，但最大的刚性开销在居住租房上。刚毕业的年轻人如果想在公司周边步行通勤，一个普通套间每月租金动辄六七千元。如果系统允许给员工录入一千多块钱的月薪，在现实中是无法维持基本生存的。

在数据库物理建表阶段，我们可以使用 `CHECK` 约束直接将这道业务防线固化在字段属性上：

```sql
CREATE TABLE test10 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2) CHECK (salary > 2000)
);
```

我们在 MySQL 8.0 环境下执行合法与非法数据的写入对比：

```sql
-- 写入满足薪资下限的数据：执行成功
INSERT INTO test10 VALUES (1, 'Tom', 2500.00);

-- 写入低于 2000 元下限的数据：触发拦截报错
INSERT INTO test10 VALUES (2, 'Tom1', 1500.00);
```

在 8.0 中，第二条写入立即被数据库内核拦截，控制台抛出标准异常：
`ERROR 3819 (HY000): Check constraint 'test10_chk_1' is violated.`

数据表底层的真实有效性得到了坚固的物理守护。

#### MySQL 5.7 与 MySQL 8.0 的支持差异

尽管 ANSI（美国国家标准局）制定的 SQL 标准很早就确立了 `CHECK` 约束，但在 MySQL 的发展历程中，对该特性的实现存在显著的版本断层。

我们把上述建表与插入语句原封不动地搬到 **MySQL 5.7** 实例中执行：

```sql
-- 在 MySQL 5.7 中创建包含 CHECK 的表，语句成功执行，没有任何语法警告
CREATE TABLE test10 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2) CHECK (salary > 2000)
);

-- 在 MySQL 5.7 中强行写入 1500 元
INSERT INTO test10 VALUES (2, 'Tom1', 1500.00);

-- 查询表记录
SELECT * FROM test10;
```

查询结果显示：**1500 元被顺顺利利地写入了数据表！**

> **定义**：在 MySQL 5.7 及更早版本中，引擎为了兼容 SQL 语法，允许用户书写 `CHECK` 关键字建表且不报语法错误，但在底层物理执行时**彻底忽略该约束（完全不起作用）**。直到 **MySQL 8.0.16** 开始，MySQL 才真正由内核引擎落地支持了 `CHECK` 约束的物理校验。

目前国内外仍有大量企业在生产环境中使用 MySQL 5.7，如果在 5.7 实例上声明了 `CHECK` 约束，纯属“形同虚设”的心理安慰。

#### 工业级数据库对 ANSI SQL 标准的支持对比

相比 MySQL 长期以来的滞后支持，商业数据库如 Oracle 以及开源学院派标杆 PostgreSQL，对 ANSI SQL 标准的贯彻则严谨得多。

我们在 Oracle 10g 实例中进行平行测试：

```sql
-- Oracle 语法测试 (使用 VARCHAR2)
CREATE TABLE test10 (
    id INT,
    last_name VARCHAR2(15),
    salary NUMBER(10, 2) CHECK (salary > 2000)
);

INSERT INTO test10 VALUES (1, 'Tom', 2500.00);

-- 尝试在 Oracle 中写入 1500
INSERT INTO test10 VALUES (2, 'Tom1', 1500.00);
```

Oracle 立即抛出经典约束违规异常：
`ORA-02290: check constraint (SCOTT.SYS_C005921) violated`

不同数据库厂商在 ANSI 标准的实现完备度上存在梯次差异，这也促使开发团队在跨数据库迁移和架构设计时必须保持清醒认知。

### 默认值约束 DEFAULT 的应用与生命周期管理

#### 默认值约束的建表语法与赋值回退逻辑

默认值约束（`DEFAULT`）用于给某个列指定兜底默认值。当执行 `INSERT` 操作而未显式指定该列的值时，存储引擎会自动提取该默认值填充。

在建表阶段，直接在字段定义后追加 `DEFAULT 默认值`：

```sql
CREATE TABLE test11 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2) DEFAULT 2000.00
);
```

执行 `DESC test11;`，可以观察到 `Default` 列准确显示为 `2000.00`。

进行数据插入测试：

```sql
-- 场景 A：显式指定薪资为 3000，使用显式传入值
INSERT INTO test11(id, last_name, salary) VALUES (1, 'Tom', 3000.00);

-- 场景 B：INSERT 列列表中完全省略 salary 字段
INSERT INTO test11(id, last_name) VALUES (2, 'Tom1');

SELECT * FROM test11;
```

查询结果中，第二行数据的 `salary` 自动回退为配置的默认值 `2000.00`。

#### 使用 ALTER TABLE 修改与剥离默认值约束

在数据表创建之后，可以使用 `ALTER TABLE ... MODIFY` 语法对默认值进行动态变更或清理。

假设存量表 `test12` 初始未设置默认值：

```sql
CREATE TABLE test12 (
    id INT,
    last_name VARCHAR(15),
    salary DECIMAL(10, 2)
);
```

**追加或修改默认值**：

```sql
ALTER TABLE test12 
MODIFY salary DECIMAL(8, 2) DEFAULT 2500.00;
```

执行后查看 `DESC test12;`，字段精度成功变更为 `DECIMAL(8,2)` 且 `Default` 刷新为 `2500.00`。

**剥除默认值约束**：
只需再次使用 `MODIFY` 重新声明列类型，**且不追加 DEFAULT 关键字**即可：

```sql
ALTER TABLE test12 
MODIFY salary DECIMAL(8, 2);
```

再次执行 `DESC test12;`，`Default` 列恢复为 `NULL`，默认值约束被干净剥除。

### 数据库字段约束设计原则与最佳实践

#### 避免 NULL 值污染的表结构设计准则

在互联网企业开发中，阅读成熟的建表 DDL 时，经常会看到形如以下的字段定义：

```sql
`user_name` VARCHAR(32) NOT NULL DEFAULT '',
`status`    TINYINT     NOT NULL DEFAULT 0,
`amount`    DECIMAL(10,2) NOT NULL DEFAULT 0.00
```

为什么工程师宁愿在建表时多敲几个单词，也非要给字段组合加上 `NOT NULL` 与 `DEFAULT ''` / `DEFAULT 0`？

根本原因在于**在关系型数据库中，空值（NULL）是极具杀伤力的“毒药”**：

1. **运算具有传染性毒性**：在 SQL 中，任何数值与 `NULL` 进行算术运算（`NULL + 1`、`NULL * 10`），其返回值统统退化为 `NULL`。业务逻辑一旦出现意外的 NULL 渗透，会导致财务或积分计算全线清零。
2. **三值逻辑破坏判断意图**：`NULL` 参与条件比对时，既不是真（TRUE）也不是假（FALSE），而是未知（UNKNOWN）。这会导致简单的 `WHERE status != 1` 漏掉所有 `status IS NULL` 的记录。
3. **底层索引检索效率低下**：在 InnoDB 的 B+ 树物理存储中，`NULL` 列需要专门的 Null Flag 标记位进行特殊维护。在复合索引与范围过滤时，针对允许为 NULL 的列做寻址和排序，开销显著高于具有明确字面值的非空字段。
4. **防范应用层空指针异常（NPE）**：从数据库映射到 Java 等强类型语言的对象实体时，空值极易在下游引发 `NullPointerException`。通过赋予默认空串或零值，系统健壮性得到了极大保障。

#### 数据库核心约束全景选型与建表期落地建议

至此，关系型数据库中的六大约束（`NOT NULL`、`UNIQUE`、`PRIMARY KEY`、`AUTO_INCREMENT`、`FOREIGN KEY`、`CHECK`、`DEFAULT`）已全部解析完毕。

在实际项目工程中，必须建立以下落地共识：
- **建表期定型，运行期不动**：关于非空、唯一、主键和默认值的规划，必须在详细设计阶段敲定，在 `CREATE TABLE` 时一次性建立到位。生产环境运行期间，严禁通过 `ALTER TABLE` 随意添加或卸载约束。
- **物理约束精简化**：主键不可或缺，非空与默认值强力推行；但对于外键与检查约束，由于跨版本兼容性（如 5.7）与高并发锁竞争瓶颈，主流方案坚决采用**业务应用层校验方案**替代数据库物理外键与物理检查。

### 本讲提到的题目

#### 题目一：建表字段为何常配置 NOT NULL DEFAULT '' 或 DEFAULT 0？

- **题干**：在很多互联网大厂的建表规范中，要求字段尽量定义为 `NOT NULL`，且根据数据类型补充 `DEFAULT ''`（针对字符串）或 `DEFAULT 0`（针对数值）。这样设计的深层技术原因是什么？
- **解析**：
  1. 避免 `NULL` 参与算术运算产生的逻辑吞没（任何数与 `NULL` 计算均为 `NULL`）；
  2. 消除 SQL 中由于三值逻辑（TRUE / FALSE / UNKNOWN）导致的查询筛选漏判；
  3. 优化 InnoDB B+ 树索引的存储与寻址效率，避免为了维护 NULL 标志位产生额外存储与比较开销；
  4. 规避应用层数据反序列化时产生的空指针异常（NPE）。
- **答案**：通过联合使用 `NOT NULL` 与确定性的默认值，消除了空值的逻辑毒性与索引劣势，提升了数据库底层检索性能与上游业务系统的容错性。

#### 题目二：带有 AUTO_INCREMENT 的自增列必然从 1 开始吗？

- **题干**：在 MySQL 数据表中，如果某列配置了 `AUTO_INCREMENT` 自增约束，该字段生成的数据值是否一定是从 1 开始严格单调递增？
- **解析**：
  不一定。自增列生成的起始基准取决于自增计数器的初始状态：
  1. 如果建表后插入首条数据时，开发者显式指定了初始主键值（例如 `INSERT INTO tbl(id, name) VALUES (10, 'Tom');`），那么自增计数器会被强行推高至该数值；
  2. 随后在缺省自增列的情况下插入第二条记录时，系统将从该人为指定的基准值递增，分配为 `10 + 1 = 11`；
  3. 此外，在建表语句末尾显式指定 `AUTO_INCREMENT = 100` 也会导致序列从 100 起步。
- **答案**：不必然从 1 开始。若用户在首次插入时显式指定了起始值，或建表时预设了自增起始点，引擎后续将以该基准值作为新的自增起点继续累加。

#### 题目三：数据表能否随意指定存储引擎？外键约束对存储引擎有何限制？

- **题干**：在 MySQL 建表语句中，可以通过 `ENGINE = ...` 子句任意指定数据表的存储引擎吗？在涉及外键约束（FOREIGN KEY）时，对主从表的存储引擎有何严格限制？
- **解析**：
  1. 在单表独立场景下，用户可以根据业务读写特征在语法上自由指定存储引擎（如高并发事务使用 `InnoDB`，纯归档高压缩使用 `Archive`，内存高频读写使用 `Memory` 等）；
  2. 但一旦两张表之间需要建立物理外键约束，**外键绝对不允许跨存储引擎建立**。
  3. 主表与从表必须使用完全相同的存储引擎，且该引擎本身必须具备外键支撑能力。由于 `MyISAM` 等轻量级引擎在底层根本不支持事务与外键机制，因此在建立外键关联时，主从两表必须同时选用 `InnoDB` 引擎。
- **答案**：单表通常可自由指定存储引擎，但外键约束严禁跨引擎构建。包含外键约束的主从两表必须采用完全相同的存储引擎，且必须选用支持外键与事务特性的存储引擎（如 InnoDB）。

## 73-第13章约束课后练习
> 对应分集：P73 | 原始标题：《73-第13章约束课后练习》

前面几讲我们把主键、唯一、非空、外键、检查和默认值等各种约束的原理规则翻了个底朝天。很多同学听完之后觉得约束的概念并不复杂，无非是在表上加一道道规则卡扣，在增删改数据时让数据库引擎自动帮我们把关拦截。但到了工程实操中，表结构往往不是一成不变的真空环境：有的是建表初期漏掉了约束需要后期通过 `ALTER TABLE` 亡羊补牢；有的是主从表建立外键关联时因为字段类型或无符号属性细微不一致而频频报错；还有的是字段迁移改名后导致原有约束形态生变。

这一讲我们通过三套递进的综合实战案例，把约束的添加、修改、字段调整与底层机理完整串联起来。不仅要掌握语法怎么写，更要搞明白为什么要这么定，以及生产环境中避开那些容易让人翻车的隐蔽深坑。

### 现有表的约束追加入门：主键与外键的动态挂载

在企业现有业务中，经常会遇到初始建表非常简陋、任何约束都没声明的“裸表”。此时必须在不破坏现有表定义的前提下，通过修改表结构把完整性约束补齐。

我们首先在专用的测试数据库中准备两张基准表：员工表 `emp2` 与部门表 `dept2`。

```sql
CREATE DATABASE test04_emp;
USE test04_emp;

-- 初始部门表（未声明约束）
CREATE TABLE dept2 (
    id INT,
    name VARCHAR(20)
);

-- 初始员工表（未声明约束）
CREATE TABLE emp2 (
    id INT,
    name VARCHAR(20)
);
```

#### 主键约束的补全与底层聚簇索引机理

对于 `emp2` 表，我们首先要给 `id` 字段追加主键约束。在造表实践中，有一条必须坚守的底线：**任何一张业务数据表，都必须提供主键。**

很多初学者理解加主键的原因仅仅停留在表层——为了实体完整性，能够通过主键唯一区分表里的每一条记录，不至于两条记录完全长得一模一样分不清。但仅靠这个理由，工程说服力其实还不够充分。真正核心的底层原因在于 MySQL 的存储引擎实现。

以最核心的 InnoDB 存储引擎为例，底层数据是以 B+ 树的结构组织在一起的，整张表的数据本身就是一颗按主键组织排序的聚集索引（Clustered Index）树。每一个叶子节点上完整保存着整行数据：

```text
               +-----------------------+
               |      [ 根节点 ]        |
               |   Key: 10   Key: 20   |
               +-----------+-----------+
                           |
             +-------------+-------------+
             |                           |
    +--------v--------+         +--------v--------+
    |    [ 分支页 ]    |         |    [ 分支页 ]    |
    |  Key: 5  Key: 8 |         | Key: 25  Key: 30|
    +--------+--------+         +--------+--------+
             |                           |
  +----------+----------+     +----------+----------+
  |                     |     |                     |
+-v--------+  +---------v-+ +-v---------+  +--------v--+
| 叶子节点 |  | 叶子节点  | | 叶子节点  |  | 叶子节点  |
| Id=1(行) |  | Id=8(行)  | | Id=21(行) |  | Id=30(行) |
+----------+  +-----------+ +-----------+  +-----------+
```
> 图 1：InnoDB 引擎基于主键构建的 B+ 树聚集索引示意图。所有行记录均挂载在主键聚簇树的叶子节点上。

如果我们在建表时没有显式声明主键，InnoDB 就会在表内寻找第一个不允许为 NULL 的唯一索引（Unique Not Null）作为聚簇索引；如果连这样的唯一索引都没有，系统底层就会被迫自动生成一个长度为 6 字节的隐式自增行指针（`ROW_ID`）来搭建 B+ 树。这种由系统隐式生成的机制不仅无法在业务层面直接检索，还会因为全局共享并发分配计数器而带来隐患。因此，绝不要把选择权留给数据库自行猜测，开发中必须主动声明主键。

追加主键的标准语法如下：

```sql
-- 方式一：标准语法（不显式起约束名）
ALTER TABLE emp2 ADD PRIMARY KEY (id);

-- 方式二：尝试指定约束名（不推荐）
-- ALTER TABLE emp2 ADD CONSTRAINT pk_emp2_id PRIMARY KEY (id);
```

> **易错点**：虽然在写 `ADD CONSTRAINT pk_emp2_id PRIMARY KEY (id)` 时语法不会报错，但这属于无用功。因为在关系数据库实现中，一张表的主键是唯一的，系统底层统一强制将其命名为 `PRIMARY`，即使在 SQL 语句中写了自定义名字，刷新查看系统结构时约束名依然显示为 `PRIMARY`。

同时必须明确追加主键的前提条件：若表中已经存有历史数据，则被声明为主键的列中所有现有数据必须已经提前满足 `NOT NULL` 与全局唯一性。如果已有数据存在重复的 `id = 1` 或者包含 `NULL`，该 DDL 语句必定报错回滚。

同理，我们为部门表 `dept2` 补全主键约束：

```sql
ALTER TABLE dept2 ADD PRIMARY KEY (id);
```

#### 外键列的追加与引用完整性关联

现在我们要让员工属于某个具体部门，需要将员工表与部门表关联。此时 `emp2` 表中尚无关联字段，需要两步操作：先新增字段，再建立外键关系。

```sql
-- 第一步：为从表 emp2 增加外键列
ALTER TABLE emp2 ADD dept_id INT;
```

> **注意**：从表（子表）中外键字段的名称（`dept_id`）与主表（父表）被引用的主键名称（`id`）可以完全不同，并不要求同名；但是，**两者的字段数据类型必须严格完全一致**（此处主从两表均为 `INT`）。

字段就位后，我们为 `dept_id` 建立指向 `dept2(id)` 的外键约束：

```sql
ALTER TABLE emp2 
ADD CONSTRAINT fk_emp2_deptid 
FOREIGN KEY (dept_id) REFERENCES dept2(id);
```

执行后刷新表结构，会发现在从表的索引列表里自动多出了一个对应的普通索引。这是因为关系数据库为了保证外键校验与关联查询的性能，在建立外键约束的同时会自动在外键列上创建二级普通索引。

外键声明生效的硬性前置条件是：**被引用的主表字段必须已经具备主键约束（PRIMARY KEY）或唯一性约束（UNIQUE）**。由于我们在此前已经将 `dept2` 的 `id` 设为主键，此处外键关联顺畅通过。

### 现有综合表的约束重构：自增主键与批量非空约束

在实际项目迭代中，常常会接手前人遗留下来的旧系统表。例如此前处理过的图书数据表 `books`，起初仅定义了字段名和基本类型，缺失业务层面的严谨校验。

我们切换到现有的图书数据库并检查表结构：

```sql
USE test01_library;
DESC books;
```

原始表包含 `id`、`name`、`authors`、`price`、`pubdate`、`note`、`num` 等字段。根据业务规范，需要将 `id` 改为主键自增，并将大部分字段严格设为非空。

#### 主键与 AUTO_INCREMENT 的一步到位修改法

通常如果要修改现有字段为主键且自增，往往会想到拆分成两步：先 `ADD PRIMARY KEY` 追加主键约束，再通过 `MODIFY` 修改字段属性增加 `AUTO_INCREMENT`。

但在实践中，完全可以使用一条 `MODIFY` 语句直接一步到位完成：

```sql
-- 推荐：一条语句同时完成主键约束追加与自增属性挂载
ALTER TABLE books MODIFY id INT PRIMARY KEY AUTO_INCREMENT;
```

执行后通过 `DESC books;` 可以看到，`id` 字段的 `Key` 列成功变为 `PRI`，且 `Extra` 属性中明确标注了 `auto_increment`。合并写法的可读性与执行效率在工程上显著优于多次 DDL 分步执行。

#### NOT NULL 非空约束的批量修正规范

非空约束不同于外键或独立索引，它是直接依附于字段类型的列级修饰属性。给现有字段添加或取消非空约束，必须使用 `MODIFY` 语法重新声明该列的完整类型定义。

```sql
-- 为书名添加非空约束
ALTER TABLE books MODIFY name VARCHAR(50) NOT NULL;

-- 为其余字段批量添加非空约束（按语句逐个指定）
ALTER TABLE books MODIFY authors VARCHAR(100) NOT NULL;
ALTER TABLE books MODIFY price FLOAT NOT NULL;
ALTER TABLE books MODIFY pubdate YEAR NOT NULL;
ALTER TABLE books MODIFY num INT NOT NULL;
```

> **提示**：在书写数值与金额字段时，有两个细节值得特别留意：
> 1. **关于金额类型的选用**：本例历史代码中价格使用了 `FLOAT`。在真实商业项目与电商系统中，**严禁使用 `FLOAT` 或 `DOUBLE` 存储涉及金钱的字段**。浮点数在底层存在固有的精度舍入偏差，生产环境中应一律采用高精度的定点数类型 `DECIMAL(M, D)`。
> 2. **关于整数显示宽度**：定义 `num INT` 时，不需要习惯性写成 `INT(11)`。因为在未开启零填充的情况下括号内的数字仅代表显示宽度，且在 MySQL 8.0 中整数显示宽度属性已明确废弃，直接写 `INT` 即可。

执行上述修改后执行 `DESC books;` 校验，除了允许留空的备注字段 `note` 依然保持 `Null = YES` 之外，其余核心字段的 `Null` 标识全部变为 `NO`，保证了图书元数据的完整性。

### 建表初期内嵌约束设计与 DDL 架构重构演进

在软件正规研发流程中，最正统、最推荐的作法是在执行 `CREATE TABLE` 初始化表结构的瞬间，就将所有列级约束与表级约束全盘规范好，而不是等数据进来后再去被动填坑。

我们以搭建一套公司内部的职场办公与员工归属系统（`test04_company`）为例，演示从初始化规范建表到后续字段调整的完整演化链路。

```sql
CREATE DATABASE IF NOT EXISTS test04_company CHARACTER SET 'utf8';
USE test04_company;
```

> **提示**：在 MySQL 5.7 环境中，默认字符集为 `latin1`，建库时必须显式声明 `CHARACTER SET 'utf8'`（或 `utf8mb4`）；而在 MySQL 8.0 之后，默认字符集已天然升级为 `utf8mb4`，省去了手工声明字符集的琐碎步骤。

#### 职场表 offices 的内嵌约束设计

职场表作为组织架构中的基准主表，结构定义如下：

```sql
CREATE TABLE IF NOT EXISTS offices (
    officeCode INT PRIMARY KEY,
    city VARCHAR(50) NOT NULL,
    address VARCHAR(50),
    country VARCHAR(50) NOT NULL,
    postalCode VARCHAR(15),
    CONSTRAINT uk_office_postalcode UNIQUE (postalCode)
);
```

##### 命名风格与设计考量
- **字段命名规范**：表中字段采用了小驼峰命名（如 `officeCode`、`postalCode`）。在 SQL 传统工程习惯中，通常更推荐全小写配合下划线的蛇形命名（Snake Case，如 `office_code`）。虽然在 Windows 平台下底层不区分字段大小写，但为了杜绝在 Linux 生产环境中由于大小写敏感策略引发的突发故障，团队必须选定一种规范并保持一致。
- **列级约束与表级约束**：`postalCode`（邮政编码）要求全局唯一。虽然可以直接在字段后紧跟 `UNIQUE` 作为列级约束，但此处采用表级约束写法，显式赋予约束名 `uk_office_postalcode`。这样做的好处是，后续若需针对该唯一约束进行维护或通过 `ALTER TABLE ... DROP INDEX` 删除时，能够精准通过命名的索引进行操作。

#### 员工表 employees 的全量约束与外键避坑

员工表作为从表，不仅包含主键、自增、非空与唯一约束，还包含指向职场表的外键。

```sql
CREATE TABLE employees (
    employeeNumber INT PRIMARY KEY AUTO_INCREMENT,
    last_name VARCHAR(50) NOT NULL,
    first_name VARCHAR(50) NOT NULL,
    mobile VARCHAR(25) UNIQUE,
    officeCode INT NOT NULL,
    jobTitle VARCHAR(50) NOT NULL,
    birth DATETIME NOT NULL,
    note VARCHAR(255),
    sex VARCHAR(5),
    CONSTRAINT fk_emp_officecode FOREIGN KEY (officeCode) REFERENCES offices(officeCode)
);
```

##### 关键避坑：ZEROFILL、UNSIGNED 与外键类型失配
在设计 `officeCode` 外键关联时，很多同学在定义字段长度时容易踩进严重的技术误区：
1. **显示宽度与物理存储**：如果在定义整型时写了 `officeCode INT(10)`，必须清醒认识到括号内的 `10` 仅仅代表展示宽度，并没有对底层存储空间做任何压缩，它依然独占 4 个字节的物理磁盘空间。
2. **ZEROFILL 导致的类型畸变**：单纯写 `INT(10)` 没有任何实质意义。若为了实现补零效果而加上了 `ZEROFILL`（即 `INT(10) ZEROFILL`），MySQL 会在底层自动为该字段追加 `UNSIGNED`（无符号）属性。此时若主表 `offices` 中的 `officeCode` 只是普通的有符号 `INT`，两者类型就会产生冲突，外键创建语句会直接因数据类型定义不匹配而硬性报错退出！

> **结论**：**外键字段与主表被引用字段的数据类型必须完全匹配**。若主表字段未声明 `UNSIGNED`，从表外键字段绝对不可附带 `UNSIGNED` 或带有潜在副作用的 `ZEROFILL`。

对于外键约束的命名，通常遵循 `fk_从表名_字段名` 的前缀命名法（如 `fk_emp_officecode`），一眼即可辨析其约束属性。

### 表结构的后续演进与生产维护防线

表建好之后，随着业务需求的演化变更，我们经常需要对表内字段的位置、命名、类型及存在性做二次调整。

#### 字段物理顺序调整与列重命名

##### 需求一：将手机号字段 mobile 调整到职场编号 officeCode 之后
在现有表结构中若希望移动列的物理存储排布，需要借助 `MODIFY ... AFTER` 语法：

```sql
ALTER TABLE employees MODIFY mobile VARCHAR(25) AFTER officeCode;
```
调整后通过 `DESC employees;` 检查，`mobile` 成功迁移至 `officeCode` 后方，且原有的 `UNIQUE` 唯一性约束完整保留，不受物理顺序变动的影响。

##### 需求二：将出生日期字段 birth 改名为 employee_birth
字段更名使用 `CHANGE` 语法，注意改名时必须完整补写其原始数据类型：

```sql
ALTER TABLE employees CHANGE birth employee_birth DATETIME NOT NULL;
```

> **提示**：在此处，原有表的字段风格大多是驼峰式（如 `jobTitle`），但题目要求改成 `employee_birth` 下划线风格。在实际工程项目中，严禁在同一个表中混合使用两种命名法则。字段命名混搭不仅造成调用层 ORM 映射困难，还会显得底层表结构设计极其不规范。

##### 需求三：将性别字段 sex 优化为 CHAR(1) 且非空
初始建表时将 `sex` 定义为 `VARCHAR(5)` 存在空间浪费与长度冗余，由于性别通常仅需存储单一字符（如 'M'/'F' 或 '男'/'女'），我们将其收紧：

```sql
ALTER TABLE employees MODIFY sex CHAR(1) NOT NULL;
```

#### 字段废弃、新增与整表重命名的生产规范

##### 需求四：删除备注字段 note
```sql
ALTER TABLE employees DROP COLUMN note;
```

> **易错点**：**在生产环境中，执行 `DROP COLUMN` 必须极其慎重！**
> 1. DDL 操作属于原子级隐式提交，执行后**无法通过事务回滚（ROLLBACK）撤回**。
> 2. 如果事前未执行完备的物理冷备或逻辑备份，一旦字段被物理剔除，该列包含的历史生产数据将彻底永久丢失。在企业生产规范中，废弃字段通常先在应用层停止读写、在数据库保留或软下线，确需清理时必须先执行全量备份。

##### 需求五：新增爱好字段 favorite_activity
```sql
ALTER TABLE employees ADD favorite_activity VARCHAR(100);
```
默认情况下，新追加的字段会自动追加至表的末尾列。

##### 需求六：重命名表结构
当业务模块重构时，需要将整张表修改为更表意的名称：

```sql
RENAME TABLE employees TO employees_info;
```

重命名执行完毕后，原表名 `employees` 即刻失效。若此时继续执行 `DESC employees;`，系统会明确抛出 `Error 1146 (42S02): Table 'test04_company.employees' doesn't exist` 异常，必须使用全新的表名 `DESC employees_info;` 才能正常访问。
