## 59-MySQL数据类型概述_字符集设置
> 对应分集：P59 | 原始标题：《59-MySQL数据类型概述_字符集设置》

在关系型数据库的设计与建模中，很多初学者在掌握了基本的建表语句（DDL）和增删改查（DML）之后，往往容易忽视数据类型的选型细节。在日常写小 Demo 或做课后练习时，大家可能习惯了整数一律无脑写 `INT`，带小数的一律写 `DOUBLE`，字符串一律写 `VARCHAR(20)`。然而在真实的工业级生产环境中，字段类型一旦选型不当，轻则白白浪费几倍甚至几十倍的物理磁盘与内存缓冲空间，严重拖慢查询与索引效率；重则引发不可逆的灾难——比如在金融、清算、电商等涉及资金核算的业务中，如果盲目选用浮点数 `FLOAT` 或 `DOUBLE`，其固有的二进制精度截断问题在海量交易累积下，就会造成账目对不上的重大生产事故。

本文梳理了 SQL 知识体系中 DDL、DML 与 DCL 的整体演进脉络，深入剖析了在表设计阶段专门攻坚数据类型的底层必要性，并全景拆解 MySQL 数值、日期时间、文本与二进制、JSON 及空间数据等五大核心类型家族，最后层层推导字符集在“库-表-列”三级作用域中的继承与覆盖机制。

### SQL 演进脉络与数据类型精讲的技术定位

回顾整个 SQL 课程的学习主线，我们始终是沿着三条脉络纵深推进的：

```text
+-------------------------------------------------------------------------+
|                           SQL 核心知识结构                              |
|                                                                         |
|  1. DDL (数据定义语言): CREATE / ALTER / DROP TABLE (元数据结构与生命周期) |
|                                                                         |
|  2. DML (数据操作语言):                                                 |
|     +- DQL (查询): SELECT 单表/多表/子查询/聚合 (重中之重，使用最频繁)  |
|     +- 增删改:    INSERT / UPDATE / DELETE / TRUNCATE (业务状态持久化)  |
|                                                                         |
|  3. DCL (数据控制语言):                                                 |
|     +- TCL (事务控制): COMMIT / ROLLBACK (ACID 特性保障)                |
|     +- 安全与权限:     GRANT / REVOKE / 用户与角色体系 (生产安全边界)    |
+-------------------------------------------------------------------------+
```
上图总结了 SQL 语言三大支柱的功能边界与技术分工。

在学完增删改查与基础建表之后，按照常规教材的目录，通常紧接着会进入第 13 章的约束（Constraint，如主键、外键、唯一、非空等）以及第 14 章的视图、存储过程、触发器等高级对象。但在正式约束表结构之前，必须前置设立专门的章节对“数据类型”进行底层精讲。之所以花大力气把这块细碎的内容彻底掰开揉碎讲透，核心在于两个极其严苛的工程约束：

1. **精度约束（业务正确性底线）**：
   浮点数（`FLOAT`/`DOUBLE`）由于底层 IEEE 754 标准的限制，存在无法被精确表示的二进制无限循环小数，极易在运算时发生四舍五入的精度丢失。一旦涉及电商订单、充值、流水清算等场景，必须使用能够绝对精确存储的定点数（`DECIMAL`），否则累积误差会直接造成账务事故。
2. **性能与微观设计规范（高并发与系统调优前提）**：
   在系统调优层面，性能优化从来不是单一维度的。线上系统的瓶颈可能来自于业务代码逻辑、服务器硬件网络吞吐、JVM 堆内存垃圾回收，但最终高频交互的瓶颈几乎全部收敛在数据库层。在数据库设计规范（如阿里巴巴 Java 与 MySQL 开发规约）中，范式理论（1NF、2NF、3NF、BCNF）决定了表与实体关系的宏观骨架，而字段类型的选型则是决定微观 I/O 效率与索引吞吐的最底层原子单元。能用 1 字节搞定的绝不用 4 字节，字段越窄，B+ 树一个数据页能容纳的索引项就越多，系统吞吐量就越高。

### MySQL 数据类型全景分类与选型矩阵

MySQL 提供了极为丰富的数据类型以适配不同维度的现实业务数据。在逻辑上，我们可以将所有的原生类型归纳为五大分类：

```text
+-------------------------------------------------------------------------+
|                        MySQL 原生数据类型全景分类                        |
|                                                                         |
|  +--------------------+  +--------------------+  +--------------------+  |
|  |     数值类型       |  |    日期时间类型    |  |  文本/二进制/富媒体 |  |
|  |--------------------|  |--------------------|  |--------------------|  |
|  | * 整数:            |  | * YEAR             |  | * 纯文本字符:      |  |
|  |   TINYINT (1B)     |  | * DATE             |  |   CHAR / VARCHAR   |  |
|  |   SMALLINT (2B)    |  | * TIME             |  |   TEXT 系列        |  |
|  |   MEDIUMINT (3B)   |  | * DATETIME         |  | * 离散与集合:      |  |
|  |   INT / INTEGER(4B)|  | * TIMESTAMP        |  |   ENUM / SET       |  |
|  |   BIGINT (8B)      |  +--------------------+  | * 二进制字节流:    |  |
|  | * 浮点:            |                          |   BLOB / BINARY    |  |
|  |   FLOAT / DOUBLE   |                          +--------------------+  |
|  | * 定点 (高精度):   |  +--------------------+  +--------------------+  |
|  |   DECIMAL          |  |     JSON 类型      |  |    空间数据类型    |  |
|  | * 位类型: BIT      |  | JSON 对象/JSON 数组|  | Geometry, Point 等 |  |
|  +--------------------+  +--------------------+  +--------------------+  |
+-------------------------------------------------------------------------+
```
上图描绘了 MySQL 丰富数据类型生态的宏观分类树状层级。

#### 数值类型族（Numeric Types）

数值类型涵盖整数、非精确浮点数、精确小数以及底层二进制位：

- **整数系列**：
  分为 `TINYINT`（1 字节）、`SMALLINT`（2 字节）、`MEDIUMINT`（3 字节）、`INT`/`INTEGER`（4 字节）、`BIGINT`（8 字节）。空间开销从小到大线性翻倍，取值区间随字节数指数级扩展。
- **浮点系列与定点系列对比**：
  `FLOAT`（单精度，4 字节）与 `DOUBLE`（双精度，8 字节）适用于科学计算等对微量截断不敏感的统计场景。而在商业开发中，只要涉及金钱和严谨计数，结论非常明确：**必须统一选用定点数 `DECIMAL`**，通过内部紧凑字符串编码杜绝任何浮点截断。
- **位类型 `BIT`**：
  用于以二进制位形式存储 0 和 1 的开关状态或掩码位。虽然在通用业务中占用比例较小，但在底层系统架构中不可或缺。这就像联合国大会上的各个主权国家，有的国家体量庞大，有的国家（如摩洛哥）领土虽小，但在法律地位上同样平起平坐。位类型虽然日常用得少，但在底层数据类型体系中也是完全独立的标准成员。

#### 日期与时间类型族（Date and Time Types）

在 Java、C++ 或 Python 等高级语言中，日期类型往往只是标准库中的一个 `Date` 或 `LocalDateTime` 类，但在持久化数据库中，日期时间被赋予了极其繁复的细分类型（`YEAR`、`DATE`、`TIME`、`DATETIME`、`TIMESTAMP`）。

之所以在数据库层面高度强调时间类型，核心原因在于关系型数据库是系统状态流转的最终见证者。业务实体何时创建、何时审核、何时支付、哪一条记录在什么时间点发生了变更，都需要精确到秒乃至毫秒级的时间戳作为防篡改审计与日志流水的关键凭据。如果只记录年份，则选用极致紧凑的 `YEAR`（仅需 1 字节）；若需追踪完整操作流水，则需在 `DATETIME` 与支持时区自动换算的 `TIMESTAMP` 之间进行精细权衡。

#### 文本、集合与二进制富媒体类型族

- **纯文本字符流**：
  `CHAR` 代表固定长度字符串，空间利用换时间，读取速度最快；`VARCHAR` 代表可变长度字符串，节省物理磁盘，按需分配；海量非格式化大文本（如论坛长篇评论、文章详情）则交由 `TEXT` 系列存储。
- **离散枚举与组合集合**：
  `ENUM` 适用于“固定多选一”（例如季节：春夏秋冬选其一；性别：男、女、未知选其一）；`SET` 适用于“多选多”（例如用户画像标签、兴趣爱好勾选），底层以紧凑的整型位图映射存储。
- **二进制数据块（BLOB 与 BINARY）**：
  类比编程语言中的“字节流”，专门用于接纳非纯文本的原始字节流。虽然生产环境中极少推荐将几十兆的原始图片、MP3 音频或 MP4 视频直接塞进关系型数据库（通常交由外部对象存储 OSS/S3 处理，表内仅存 URL 字符串），但诸如签名私钥、加密证书、小图标等特殊二进制切片，必须借助 `BLOB` 家族容纳，绝不可用 `TEXT` 存储，否则在字符编码解码转换时会直接破坏底层二进制序列。

#### JSON 原生类型与空间数据类型

- **原生 JSON 支持**：
  随着微服务与前后端分离架构普及，轻量级的 JSON 格式成为跨进程通信的事实标准。MySQL 原生提供了 JSON 数据类型，内部支持校验 JSON 格式合法性，并具备高效的路径表达式定位与就地更新能力。
- **空间几何类型（Spatial Types）**：
  涵盖 `GEOMETRY`、`POINT`、`LINESTRING`、`POLYGON` 等，专门支撑地图定位、LBS 距离计算与地理信息系统（GIS）。对于通用业务系统开发者而言，该部分只需理解其存在场景，作为知识储备即可。

### 字段修饰属性：无符号标识与多层级字符集配置

在字段定义语法中，除指定核心类型外，还可以追加特定属性修饰符（如 `UNSIGNED`、`ZEROFILL` 及 `CHARACTER SET`）。

```sql
-- 字段修饰符语法结构
字段名 数据类型 [UNSIGNED] [CHARACTER SET 字符集名] [约束条件]
```

#### 无符号修饰符（UNSIGNED）的业务语义

`UNSIGNED` 专门用于修饰整型数值类型。默认情况下，整型是有符号的（最高位作为符号位，正负各半）。一旦追加 `UNSIGNED`，该整型将剥离负数表示能力，其正数取值上限将整整翻倍。

> **提示**：业务语义中具有天然非负特征的属性（如人类年龄、城市常住人口数、商品库存、自增物理主键 ID 等），非常适合追加 `UNSIGNED` 修饰，在相同字节开销下获得翻倍的正向容纳上限。

#### 字符集的层级继承与列级覆盖机制

字符编码决定了文本在磁盘物理字节与人类字符之间的转换规则。MySQL 架构中设计了一套层层下推、逐级覆盖的字符集继承树：

```text
+--------------------------------------------------------------------------+
| 字符集层级继承与覆盖机制                                                 |
|                                                                          |
|   服务器级 (Server Default)                                              |
|      |                                                                   |
|      v (若未显式指定，则继承上一级)                                      |
|   数据库级 (Database Level)  -> CREATE DATABASE ... CHARACTER SET utf8    |
|      |                                                                   |
|      v (若未显式指定，则继承上一级)                                      |
|   数据表级 (Table Level)     -> CREATE TABLE ... CHARACTER SET utf8       |
|      |                                                                   |
|      v (若未显式指定，则继承上一级)                                      |
|   字段列级 (Column Level)    -> 列名 VARCHAR(15) CHARACTER SET gbk        |
+--------------------------------------------------------------------------+
```
上图直观展现了字符集在 MySQL 实例各个结构单元中由上至下的流转规律。

##### 数据库级字符集（Database Level）

在创建数据库阶段，通过 `CHARACTER SET` 显式圈定本库的默认字符编码环境：

```sql
-- 创建第 12 章演练数据库并指明默认编码为 utf8
CREATE DATABASE IF NOT EXISTS dbtest12 CHARACTER SET utf8;
USE dbtest12;

-- 查看数据库底层真实的 DDL 创建元数据
SHOW CREATE DATABASE dbtest12;
```

控制台返回的定义语句中会显式包含 `DEFAULT CHARACTER SET utf8`。

##### 数据表级字符集（Table Level）

在已有数据库上下文内创建数据表时，若不显式指定字符集，新建的表将无缝继承所属数据库的编码：

```sql
-- 创建测试表 temp，未显式声明编码
CREATE TABLE IF NOT EXISTS temp (
    id INT
);

-- 查看表创建元数据
SHOW CREATE TABLE temp;
```

此时查看 `SHOW CREATE TABLE temp;`，其尾部会默认标记 `DEFAULT CHARSET=utf8`。当然，若该表有特殊国际化诉求，亦可在建表语句末尾显式指定专属字符集进行覆盖。

##### 字段列级字符集（Column Level）

最细粒度的控制可以精确到单个字符串列。即使整张表采用 `utf8` 编码，个别字段依然可以显式指定其他字符集（例如遗留老旧系统对接时使用的 `gbk`）：

```sql
-- 创建测试表 temp1，在列级显式指定覆盖编码
CREATE TABLE IF NOT EXISTS temp1 (
    id INT,
    `name` VARCHAR(15) CHARACTER SET gbk
);

-- 查看字段级元数据
SHOW CREATE TABLE temp1;
```

> **结论**：在 MySQL 体系中，下级对象始终以继承上级对象的字符集为默认基准；只要在当前层级显式声明了 `CHARACTER SET`，当前配置便会立即生效并覆盖上级继承下来的默认值。这种设计兼具了全局统一性与局部场景的灵活性。

## 60-整型数据类型讲解
> 对应分集：P60 | 原始标题：《60-整型数据类型讲解》

在数据库表结构设计中，整型（Integer）几乎是出镜率最高的数据类型。从自增主键、用户 ID、状态位、访问计数值到库存数量，整型的身影无处不在。然而很多开发者在面对 `TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT` 和 `BIGINT` 这五种类型时，往往缺乏底层的边界概念与架构考量。有人觉得“反正硬盘便宜，所有整型一律给 `BIGINT`”，结果导致 B+ 树索引严重膨胀、内存缓存命中率暴跌；也有人走向另一个极端，教条地奉行“能省 1 个字节就省 1 个字节”，为了所谓的紧凑设计在主键上抠搜地选用 `MEDIUMINT`，结果在业务上线一两年后遭遇静默溢出报错，导致线上核心交易系统瘫痪数小时。

更令人困惑的是 MySQL 中类似 `INT(11)`、`INT(5)` 这种带括号的古老语法——到底括号里的数字代表存储字节、数值长度还是显示位数？为什么在 MySQL 5.7 中建表会自动补齐括号，而到了 MySQL 8.0 之后官方却强烈建议废弃？

本文将从底层的二进制位权推导出发，全面解构 MySQL 五大整数类型的物理存储结构、数值边界与越界机制；深入剖析“显示宽度 M”与 `ZEROFILL` 零填充的联动原理；最后结合 1997 年香港金融保卫战的天量交易场景，剖析存储空间与系统可靠性之间的架构权衡法则。

### 五大整数类型的物理存储与数值边界推导

在 MySQL 中，整数类型严格遵循标准的二进制物理存储规范。不同的整数类型占据不同数量的字节（Byte），每个字节由 8 个二进制位（bit）构成。根据最高位是否被用作“符号位”（Sign Bit），整型被划分为“有符号（Signed）”与“无符号（Unsigned）”两种形态。

```text
+---------------------------------------------------------------------------------------------------------+
|                                    MySQL 五大整数类型取值范围全景矩阵                                    |
|                                                                                                         |
| 类型名        | 存储空间 | 有符号取值范围 (默认)                          | 无符号取值范围 (UNSIGNED)            |
|--------------+---------+----------------------------------------------+----------------------------------|
| TINYINT      | 1 字节  | -128 ~ 127                                   | 0 ~ 255                          |
| SMALLINT     | 2 字节  | -32,768 ~ 32,767                             | 0 ~ 65,535                       |
| MEDIUMINT    | 3 字节  | -8,388,608 ~ 8,388,607                       | 0 ~ 16,777,215 (约 1677 万)       |
| INT / INTEGER| 4 字节  | -2,147,483,648 ~ 2,147,483,647 (约 -21.47 亿)| 0 ~ 4,294,967,295 (约 42.94 亿)  |
| BIGINT       | 8 字节  | -2^63 ~ 2^63 - 1 (约 -9.22 x 10^18)          | 0 ~ 2^64 - 1 (约 1.84 x 10^19)   |
+---------------------------------------------------------------------------------------------------------+
```
上表展示了 MySQL 原生支持的五种整数类型在存储开销与数值范围上的精确对应关系。

#### 二进制位权与上下限数学推导

每一个整数类型所能表达的状态总数，本质上就是 2 的对应位次方：

- **TINYINT（1 字节 = 8 bit）**：
  状态总数为 $2^8 = 256$ 种。若为有符号数，最高位为符号位（0 代表正数，1 代表负数），负数通过补码存储，表示范围为 $-2^7 \sim 2^7 - 1$，即 $-128 \sim 127$；若声明为无符号（`UNSIGNED`），则 8 位全用于表示数值，表示范围为 $0 \sim 2^8 - 1$，即 $0 \sim 255$。
- **SMALLINT（2 字节 = 16 bit）**：
  状态总数为 $2^{16} = 65,536$ 种。有符号范围为 $-2^{15} \sim 2^{15} - 1$（$-32,768 \sim 32,767$）；无符号范围为 $0 \sim 65,535$。
- **MEDIUMINT（3 字节 = 24 bit）**：
  状态总数为 $2^{24} = 16,777,216$ 种。有符号范围为 $-8,388,608 \sim 8,388,607$；无符号范围为 $0 \sim 16,777,215$。
- **INT / INTEGER（4 字节 = 32 bit）**：
  状态总数为 $2^{32} \approx 42.9$ 亿种。有符号范围为 $-2,147,483,648 \sim 2,147,483,647$；无符号范围为 $0 \sim 4,294,967,295$。
- **BIGINT（8 字节 = 64 bit）**：
  状态总数为 $2^{64}$ 种，上限可达 1800 亿亿级别，能够满足人类目前已知绝大多数天量规模的计数诉求。

#### 越界截断与严格模式异常验证

为了验证各整型在越界时的引擎行为，我们在测试数据库 `dbtest12` 中构建包含 5 种整型字段的测试表：

```sql
-- 切换至测试数据库
USE dbtest12;

-- 创建包含 5 类整型的基准测试表
CREATE TABLE IF NOT EXISTS test_int1 (
    f1 TINYINT,
    f2 SMALLINT,
    f3 MEDIUMINT,
    f4 INT,
    f5 BIGINT
);

-- 验证有符号 TINYINT 的极限合法插入
INSERT INTO test_int1 (f1) VALUES (12), (-12), (-128), (127);

-- 查看写入结果
SELECT f1 FROM test_int1;
```

当向 `f1` 尝试写入超出其物理边界的数值（如 `128`）时：

```sql
-- 越界插入触发报错
INSERT INTO test_int1 (f1) VALUES (128);
```

> **结论**：在 MySQL 默认的严格 SQL 模式（`STRICT_TRANS_TABLES`）下，引擎绝不允许静默截断，而是立即拦截并抛出 `ERROR 1264 (22003): Out of range value for column 'f1'` 错误，强行中断事务以保障底层数据完整性。

### 显示宽度 M 与零填充 ZEROFILL 机制解密

在 MySQL 的历史版本中，最让人产生误解的语法莫过于 `INT(M)` 中的 `M`。许多人望文生义，误以为 `INT(5)` 只能存储 5 位数，或者误以为它只占 5 个字节。这是必须纠正的经典谬误。

#### 与 8.0 版本元数据呈现差异

在 MySQL 5.7 实例中执行 `DESC test_int1;`，控制台返回的类型定义会自带括号与数字：

```text
+-------+---------------+------+-----+---------+-------+
| Field | Type          | Null | Key | Default | Extra |
+-------+---------------+------+-----+---------+-------+
| f1    | tinyint(4)    | YES  |     | NULL    |       |
| f2    | smallint(6)   | YES  |     | NULL    |       |
| f3    | mediumint(9)  | YES  |     | NULL    |       |
| f4    | int(11)       | YES  |     | NULL    |       |
| f5    | bigint(20)    | YES  |     | NULL    |       |
+-------+---------------+------+-----+---------+-------+
```

而在 MySQL 8.0 实例中执行相同的指令，括号内的数字消失了，干净利落地呈现为 `tinyint`、`smallint`、`int` 等纯净类型名。之所以在学习时以 5.7 为主对照演练，是因为目前大量企业级存量系统依然运行在 5.7 架构上，只有搞懂了 5.7 的设计由头，才能彻底明白 8.0 废弃它的技术必然。

#### 默认显示宽度的计算来源

为什么在 5.7 默认不写括号时，系统会自动分别分配 4、6、9、11、20 的宽度？其推导法则与最高负数的字符长度直接绑定：

- `TINYINT` 的最小负数是 `-128`：包含 3 个数字字符与 1 个负号字符，总共需要 **4 个字符宽度** 完整展示，故默认为 `tinyint(4)`。
- `SMALLINT` 的最小负数是 `-32768`：包含 5 个数字字符加 1 个负号，总计 **6 个字符宽度**，故默认为 `smallint(6)`。
- `INT` 的最小负数是 `-2147483648`：包含 10 个数字字符加 1 个负号，总计 **11 个字符宽度**，故默认为 `int(11)`。
- `BIGINT` 的最小负数长达 19 个数字字符加 1 个负号，总计 **20 个字符宽度**，故默认为 `bigint(20)`。

> **核心定义**：括号中的 `M` 严格代表**显示宽度（Display Width）**，其合法取值范围为 0 到 255。**显示宽度绝对不限制该类型底层的存储字节（INT 永远固定为 4 字节），也绝对不限制其实际能存入的数值区间**。哪怕定义为 `INT(5)`，只要存入的数据未超出 INT 的 -21.47 亿到 +21.47 亿边界，无论 6 位数、7 位数还是 10 位数，都能正常存储，绝不报错。

#### ZEROFILL 零填充的联动生效机理

既然 `M` 不影响存储和计算范围，那它存在的意义是什么？答案是：**单独声明 `M` 没有任何实际意义，它必须且只能与 `ZEROFILL` 属性配合时才会生效**。

```sql
-- 创建测试表演练 ZEROFILL 与显示宽度
CREATE TABLE IF NOT EXISTS test_int2 (
    f1 INT,
    f2 INT(5),
    f3 INT(5) ZEROFILL
);

-- 插入数值并比对展示格式
INSERT INTO test_int2 (f1, f2, f3) 
VALUES 
(123, 123, 123),
(123456, 123456, 123456);

-- 检索结果
SELECT * FROM test_int2;
```

```text
+--------+--------+--------+
| f1     | f2     | f3     |
+--------+--------+--------+
|    123 |    123 |  00123 |
| 123456 | 123456 | 123456 |
+--------+--------+--------+
```

```text
+--------------------------------------------------------------------------+
| 显示宽度与 ZEROFILL 联动渲染机制                                         |
|                                                                          |
|   插入值 123:                                                            |
|     INT(5)          -> [1][2][3]           (无前导补齐，正常展示)        |
|     INT(5) ZEROFILL -> [0][0][1][2][3]     (不足 5 位，左侧前置填 0 补齐)|
|                                                                          |
|   插入值 123456:                                                         |
|     INT(5) ZEROFILL -> [1][2][3][4][5][6]  (已超 5 位，无缝原样完整输出) |
+--------------------------------------------------------------------------+
```
上图直观展现了 `ZEROFILL` 在数据位数不足时补零、超出显示宽度时原样输出的渲染行为。

通过 `SHOW CREATE TABLE test_int2;` 查看表定义，还会发现一个极为关键的底层连锁反应：

```sql
SHOW CREATE TABLE test_int2;
```

返回的定义中，`f3` 字段被系统自动转化为了 `int(5) unsigned zerofill`。这是因为**一旦指定了零填充，该字段在逻辑上已被假定为绝对非负数（负数不可能在负号前补零），因此引擎会自动为其隐式附加上 `UNSIGNED` 约束**。

#### 无符号对显示宽度的动态重算

当字段显式指定为 `UNSIGNED` 时，负数空间被消除，数字上限扩张。此时默认显示宽度也会动态微调：

```sql
-- 创建无符号整数表
CREATE TABLE IF NOT EXISTS test_int3 = (
    f1 INT UNSIGNED
);

-- 查看表结构
DESC test_int3;
```

此时控制台呈现的类型是 `int(10) unsigned`。因为无符号 `INT` 的最大值是 `4294967295`，总共有 10 位数字，且不再需要负号，因此其最大显示宽度由 11 缩减为 10。向其中插入最大值 `4294967295` 顺利执行，插入 `4294967296` 则立即越界报错。

> **规范演进**：从 MySQL 8.0.17 开始，官方已正式废弃对整型指定显示宽度 `M` 的语法（Deprecated）。现代软件工程建议将数据显示格式的格式化（如银行流水补前导 0）下放到上层业务应用（如 Java、Go、Python 或前端）完成，数据库底层回归纯粹的数据存储，建表时直接声明 `INT` 即可。

### 业务场景适配与架构权衡法则

在明确了各类型的理论边界后，摆在架构师和开发者面前的现实问题是：如何在具体的业务建模中精准拍板？

```text
+-------------------------------------------------------------------------+
| 五大整数类型的典型工业级选型适配                                         |
|                                                                         |
| TINYINT   -> 状态开关 (0/1)、审核标识、百分比 (0~100%)                  |
| SMALLINT  -> 中小固定资产设备统计、仓库库位编号 (0~65535)               |
| MEDIUMINT -> 城市客运站日运力、公共交通日刷卡量 (~1600 万)              |
| INT       -> 通用自增主键、用户 UID、商品 SKU、订单流水 (~21 亿/42 亿)  |
| BIGINT    -> 全网海量交易订单号、巨量日志埋点、全网金融衍生品持仓总额   |
+-------------------------------------------------------------------------+
```
上图总结了五种整型在工业级不同吞吐维度下的典型业务适配映射。

#### 典型业务场景映射

1. **`TINYINT`**：
   专用于小范围离散值或系统阈值配置。例如表示进度百分比（0 到 100 绝不可能超过 100）、逻辑删除标记（0 未删除、1 已删除）、用户性别或审批状态。
2. **`SMALLINT`**：
   适用于体量可控的局部统计场景。如企业固定资产台账、中小学校学生编号、高校各学院学科分类等。
3. **`MEDIUMINT`**：
   用于百到千万级别的大型指标。例如大型交通枢纽的每日客流量、某地级市机动车保有量等。
4. **`INT`**：
   通用业务的核心主力。取值区间达 21.47 亿（无符号 42.94 亿），在常规中大型企业系统、电商商品库、用户基础表中，只要生命周期内数据条目不会爆发式突破数十亿，`INT` 是兼顾性能与空间的平衡之选。
5. **`BIGINT`**：
   应对天文数字级别的超大规模并发与累积数据。
   - **典型场景**：电商全网“双十一”并发交易总额、全网分布式日志 TraceID、社交平台亿级用户的点赞与高频行为流。
   - **金融巨浪中的天量吞吐**：这就像 1997 至 1998 年著名的“香港金融保卫战”。当时国际金融炒家索罗斯携对冲基金对港币与恒生指数发动了前所未有的立体化恶意做空。香港特区政府在中央政府的全力支持下，动用庞大外汇储备在股市和期市硬接抛盘，决战当天恒生指数单日成交额高达数百亿港元，涉及的金融衍生品持仓合约与资金清算流水规模极其庞大。面对这类关乎国家金融安全、日交易流水与持仓市值达数千亿乃至上万亿元的场景，底层清算系统必须采用 `BIGINT` 甚至高精度定点数作为承载，绝对不允许有任何溢出风险。

#### 存储空间 vs 系统可靠性的终极权衡

在许多数据库优化教科书中，常常告诫大家“字段越小越好”。从底层的 InnoDB 存储引擎机制看，确实如此：数据以 16KB 数据页（Page）为单位驻留内存缓冲区并持久化至磁盘，主键和字段占用的字节数越少，单个数据页内能容纳的行记录和 B+ 树索引节点就越多，这能直接降低树高、减少磁盘 I/O 寻道次数。

然而，优秀的软件工程从来不是刻舟求剑，而是多维利益的博弈与权衡：

> **架构核心结论**：**在实际工业生产中，系统崩溃停机所造成的业务损失与故障成本，远远高于在磁盘上多增加几个字节所产生的存储开销！**

试想一个真实的教训：架构设计之初，开发者为了追求所谓的“极致空间优化”，将某个业务的核心主键设定为 `MEDIUMINT UNSIGNED`（上限约 1677 万）。在系统上线的前两年，数据增长缓慢，系统运转一切良好。然而随着业务裂变与时间累积，在某一天的业务高峰期，主键值悄然突破了 16777215。底层引擎瞬间全线抛出 `Out of range` 异常，核心下单接口大面积超时，整条业务链路彻底停摆。

面对生产事故，团队紧急排查、拉取高危变更、执行线上 `ALTER TABLE` 修改上千万行记录的字段类型，停机维护长达数小时。期间损失的商业利润数以百万计，更伴随着严重的品牌声誉降级与团队复盘问责。而造成这一切灾难的源头，仅仅是当初建表时为了省下微不足道的 1 个字节！

因此，在字段选型时必须具备前瞻性的容量规划意识：
- **评估生命周期**：不仅要看当前存量，更要按照未来 3 到 5 年的业务翻倍速度测算峰值上限；
- **核心主键留有余量**：业务核心实体的主键 ID，宁可直接使用 `BIGINT`，也绝不要把空间卡得严丝合缝；
- **局部紧凑精打细算**：只有在取值范围受数学法则或物理规律严格受限的字段（如月份 1~12、星期 1~7、百分比 0~100），才果断采用 `TINYINT` 压榨空间。这种收放自如的平衡，才是工业级数据库设计的精髓所在。

## 61-浮点数、定点数与位类型讲解
> 对应分集：P61 | 原始标题：《61-浮点数、定点数与位类型讲解》

在数据库表结构设计中，只要涉及到带小数点的数值，很多初学者往往不假思索地直接选择 `FLOAT` 或 `DOUBLE`。然而在真实的业务系统（尤其是电商交易、财务核算与零售计费）中，一个看似微不足道的小数点误差，足以引发灾难性的账目混乱。我们在设计字段时，不仅要清楚如何存下数据，更要明白底层到底是近似值还是精确值，以及当数据超出精度限制时数据库会发生何种行为。

从本质上看，整数完全可以视作小数的特例。如果在一个声明为浮点类型的字段中写入整数 `123`，MySQL 会执行隐式类型转换，在底层补齐小数位以 `123.00` 的形式存储。但是在面对小数时，MySQL 提供了两套截然不同的数据类型分支：浮点数（`FLOAT`、`DOUBLE`、`REAL`）与定点数（`DECIMAL` / `NUMERIC`）。此外，针对底层位操作与二进制状态标记，MySQL 还提供了位类型（`BIT`）。本文将系统剖析这几类数值类型的存储结构、精度控制、四舍五入边界、浮点累加误差，并给出生产环境下的选型法则。

---

### 浮点数类型（FLOAT、DOUBLE、REAL）

#### 浮点数规格与 REAL 的模式切换

MySQL 中的浮点数类型主要包含单精度浮点数 `FLOAT` 与双精度浮点数 `DOUBLE`。在语法定义中还会看到一个 `REAL` 类型：

```text
+--------------+----------+------------------------------------------------+
| 类型名称     | 存储字节 | 默认精度说明                                   |
+--------------+----------+------------------------------------------------+
| FLOAT        | 4 字节   | 单精度浮点数，32位，约 7 位有效数字            |
| DOUBLE       | 8 字节   | 双精度浮点数，64位，约 15~17 位有效数字        |
| REAL         | 8 字节   | 默认等价于 DOUBLE；受 sql_mode 影响可变为 FLOAT |
+--------------+----------+------------------------------------------------+
```

很多初学者看到文档里列出 `REAL` 会产生疑问：既然有了 `FLOAT` 和 `DOUBLE`，为什么还需要 `REAL`？`REAL` 在标准 SQL 中是一个通用概念。在 MySQL 默认环境下，`REAL` 就是 `DOUBLE` 的同义词，占用 8 个字节。但 MySQL 允许通过修改 `sql_mode` 改变这一行为：

```sql
SET sql_mode = 'REAL_AS_FLOAT';
```

一旦将 `sql_mode` 设置为 `REAL_AS_FLOAT`，后续再在建表时声明 `REAL`，MySQL 就会将其自动解析为 4 字节的 `FLOAT`。虽然在生产环境中极少会特意去修改这个模式，但了解这一点有助于理解历史遗留 SQL 脚本在不同模式下的兼容性表现。

#### 浮点数的底层存储格式与 UNSIGNED 的特殊表现

在整型数据中，如果声明为 `UNSIGNED`（无符号），其表示范围会把负数空间整个平移到正数区，例如 `TINYINT` 的有符号范围是 `-128 ~ 127`，无符号范围则是 `0 ~ 255`，正数范围直接扩大了一倍。

然而，如果在浮点数 `FLOAT` 或 `DOUBLE` 后面加上 `UNSIGNED`，其取值范围却发生了反直觉的变化：它**并没有**扩大正数范围，仅仅是生硬地把负数那一段区间直接切除丢弃，只留下从 `0` 到正数最大值的区间。

这一现象的根本原因在于浮点数遵循 IEEE 754 标准的底层二进制存储格式。浮点数在物理存储上由三部分拼装而成：

```text
+-------------------+---------------------+-------------------------+
| 符号位 (Sign)     | 阶码位 (Exponent)   | 尾数位 (Mantissa)       |
| 1 bit             | FLOAT: 8 bit        | FLOAT: 23 bit           |
|                   | DOUBLE: 11 bit      | DOUBLE: 52 bit          |
+-------------------+---------------------+-------------------------+
浮点数值计算逻辑：V = (-1)^Sign * (1 + Mantissa) * 2^(Exponent - Bias)
```

不论你是否声明 `UNSIGNED`，数据库在物理底层都必须分配固定的符号位空间。声明无符号并不能将符号位挪去给阶码或尾数扩容，它只是在应用层和写入校验层做了一个规则拦截：不允许写入负数。占用的磁盘与内存字节数（4 字节或 8 字节）完全不变，可表示的最大正数值也丝毫没有增加。

> **提示**：正因如此，在 MySQL 8.0 中，官方已经明确将 `FLOAT(M, D)`、`DOUBLE(M, D)` 以及浮点数的 `UNSIGNED` 属性列为废弃特性（Deprecated），在未来的主版本中将会被彻底移除。在现代开发中，切忌对浮点数刻意声明 `UNSIGNED`。

#### 浮点数的精度与标度定义（M, D）

在 MySQL 中，浮点数支持一种非标准的扩展语法：`FLOAT(M, D)` 或 `DOUBLE(M, D)`。

- **M（Precision，精度）**：指该数值的总位数，即整数位位数与小数位位数之和。M 的有效取值范围为 `1 ~ 255`。
- **D（Scale，标度）**：单指小数位的位数。D 的有效取值范围为 `0 ~ 30`，且必须满足 $M \ge D$。
- **整数位最大容量**：等于 $M - D$。

例如声明 `FLOAT(5, 2)`：
- 总位数为 5 位；
- 小数位占 2 位；
- 整数位最多只能容纳 $5 - 2 = 3$ 位；
- 允许的有符号存储范围为 `-999.99 ~ 999.99`。若带 `UNSIGNED`，则为 `0 ~ 999.99`。

如果在建表时不指定 `(M, D)`，MySQL 将遵循底层硬件与操作系统的标准浮点表示方式，按实际精度进行存取和显示。

#### 溢出截断、四舍五入与进位溢出实测

我们通过建表实测验证浮点数在数据写入时的四舍五入机制与溢出边界。

创建测试表：

```sql
CREATE TABLE test_double1 (
    f1 FLOAT,
    f2 DOUBLE,
    f3 FLOAT(5, 2),
    f4 DOUBLE(5, 2)
);
```

查看表结构（在 MySQL 5.7 环境中）：

```sql
DESC test_double1;
```

向表中写入规范数据：

```sql
INSERT INTO test_double1 (f1, f2) VALUES (123.45, 123.45);
INSERT INTO test_double1 (f3, f4) VALUES (123.45, 123.45);
```

此时 `123.45` 整数位 3 位、小数位 2 位，完全落在 `(5, 2)` 的容纳范围内，写入成功。

##### 现象一：小数位超出引发的四舍五入

向 `(5, 2)` 字段写入小数位超出 2 位的值：

```sql
INSERT INTO test_double1 (f4) VALUES (123.456);
```

执行后并不报错，查询结果显示该字段的值变为了 `123.46`。

> **结论**：当写入数据的小数位数超过声明的标度 $D$ 时，MySQL 会对超出的低位小数执行**四舍五入**，截断至设定的标度保存。

##### 现象二：整数位超出直接触发溢出报错

向 `(5, 2)` 字段写入整数位超出 3 位的值：

```sql
INSERT INTO test_double1 (f4) VALUES (1234.456);
```

执行后控制台直接报错：
`ERROR 1264 (22003): Out of range value for column 'f4' at row 1`

四舍五入只能平抑小数位的超长，根本无法压缩整数位。一千多的数值无论如何舍入仍然是一千多，必须要占 4 位整数位，超出了 $5 - 2 = 3$ 位的硬性限制，系统直接判定数据溢出。

##### 现象三：小数四舍五入进位导致的整数位连锁溢出

考察以下看似符合“3 位整数”限制的极端边界值：

```sql
INSERT INTO test_double1 (f4) VALUES (999.995);
```

在写入前，整数部分是 `999`（恰好 3 位），小数部分是 `.995`（3 位）。按规则小数位需保留 2 位，对末位数字 `5` 进行四舍五入向高位进位：
- `.995` 进位变为 `1.00`；
- 产生的进位加到整数部分，导致 `999 + 1 = 1000`；
- 最终结果变成了 `1000.00`，整数位从 3 位变成了 4 位！

执行该语句，控制台同样抛出异常：
`ERROR 1264 (22003): Out of range value for column 'f4' at row 1`

> **易错点**：边界值的四舍五入不是局部的，进位若穿越了小数点，可能导致原本合法的整数位数被撑破，从而触发 `Out of range` 错误。

### 浮点数的精度缺陷与误差陷阱

浮点数最大的软肋在于**不够精准**。计算机使用二进制补码与阶码来近似模拟十进制连续小数，而大多数十进制小数（例如 `0.1`、`0.2`）转化为二进制后都是无限循环小数。在有限的尾数位长度下，必须在末位执行截断与舍入，这在底层埋下了微小却客观存在的精度误差。

#### 累加误差实证

创建精度测试表：

```sql
CREATE TABLE test_double2 (
    f1 DOUBLE
);

INSERT INTO test_double2 VALUES (0.4), (0.4), (0.3);
```

这三个数值在人类的数学直觉中相加极为简单：
$$0.4 + 0.4 + 0.3 = 1.1$$

但当我们使用聚合函数 `SUM()` 对其进行累加查询时：

```sql
SELECT SUM(f1) FROM test_double2;
```

控制台返回的真实结果为：
`1.0999999999999999`

该数值无限趋近于 `1.1`，但它在二进制底层就不是 `1.1`。

#### 条件比较陷阱

如果业务代码中存在基于浮点数字段的相等性过滤，隐患会立即爆发：

```sql
SELECT SUM(f1) = 1.1 FROM test_double2;
```

在 MySQL 中，比较表达式成立返回 `1`（True），不成立返回 `0`（False）。上面这条查询的返回结果确凿无疑是 `0`！

如果换成单精度的 `FLOAT` 类型，由于其尾数位仅有 23 位，有效数字比 `DOUBLE` 更少，所产生的相对误差会更加夸张。

> **核心告诫**：
> 绝不能在业务 SQL 中直接使用等号 `=` 判断浮点类型字段是否等于某个给定的浮点数值！这种条件过滤往往由于微小的尾数截断导致逻辑判断落空，产生难以排查的幽灵 Bug。

### 定点数类型（DECIMAL）

面对财务结算、电商支付与银行账目等“一分钱都不能差”的业务场景，浮点数的近似存储是完全不可接受的。为此，MySQL 引入了高精度的定点数类型：`DECIMAL`（其别名包括 `DEC`、`NUMERIC`）。

#### DECIMAL 的底层存储原理与语法

`DECIMAL(M, D)` 的参数含义与浮点数一致：
- $M$ 为精度（总位数），最大值为 65；
- $D$ 为标度（小数位），最大值为 30，且 $M \ge D$。

`DECIMAL` 之所以能够保证绝对精准，其底层机制在于：**它不再依赖 CPU 硬件层面的二进制浮点寄存器进行编解码，而是在底层以类似定长字符/压缩十进制字节数组的方式进行精确存储**。存储格式将整数部分和小数部分分别拆开，按每 9 位十进制数字占用 4 个字节进行紧凑打包。

其占用的存储空间大致可以用公式 $M + 2$ 字节作粗略估算。由于每个十进制数位都是精准确定的，因此不存在任何进制转换截断误差，支持任意精度的绝对无损存储。这与 Java 语言中的 `BigDecimal` 思想异曲同工。

#### 默认参数缺省行为与 MySQL 8.0 规范

与 `FLOAT` / `DOUBLE` 允许省略 `(M, D)` 由系统自适应不同，`DECIMAL` 在省略参数时具有严格且危险的默认值：

```sql
CREATE TABLE test_decimal1 (
    f1 DECIMAL,
    f2 DECIMAL(5, 2)
);

DESC test_decimal1;
```

查看表结构可以发现：
- `f2` 显示为 `decimal(5, 2)`；
- 未指定精度的 `f1`，被 MySQL 赋予了默认值 **`decimal(10, 0)`**。

> **注意**：`decimal(10, 0)` 意味着标度 $D = 0$，即**完全不保留任何小数位**！

验证缺省情况下的写入：

```sql
INSERT INTO test_decimal1 (f1) VALUES (123), (123.45);
SELECT f1 FROM test_decimal1;
```

查询结果：两条记录的 `f1` 均显示为 `123`。写入 `123.45` 时，由于标度为 0，`.45` 按照四舍五入规则被直接舍弃。如果在定义 `DECIMAL` 字段时遗漏了参数，就会导致小数位在不知不觉中被全部截断抹平。因此在开发中声明 `DECIMAL` 时，必须显式指明 `(M, D)`。

此外，在 MySQL 8.0 中，整型和浮点数后面的显示宽度及 `(M, D)` 已被废弃，但在执行建表时，系统依然对 `DECIMAL(M, D)` 给予特许保留并严格要求。原因正在于 `DECIMAL` 占用的实际存储空间和物理编解码规则与 $M$ 和 $D$ 紧密绑定，必须强制明确。

#### 精度对比实证：用 DECIMAL 彻底根治误差

将之前包含浮点累加误差的 `test_double2` 表字段改造为 `DECIMAL`：

```sql
ALTER TABLE test_double2 MODIFY f1 DECIMAL(5, 2);
```

修改字段类型后，再次执行相同的聚合求和与相等性校验：

```sql
SELECT SUM(f1) FROM test_double2;
SELECT SUM(f1) = 1.1 FROM test_double2;
```

查询结果：
- `SUM(f1)` 干净利落地输出了 `1.10`，尾部不再有任何冗余的浮点尾巴；
- 相等性判断 `SUM(f1) = 1.1` 的返回值直接变为了 `1`（True）。

浮点数与定点数的核心特性对比总结如下：

```text
+--------------+--------------------+----------------------+--------------------+--------------------+
| 数据类型     | 存储占用           | 数值取值范围         | 计算性能           | 精度可靠性         |
+--------------+--------------------+----------------------+--------------------+--------------------+
| FLOAT        | 4 字节（固定）     | 极大（约 10^38）     | 极高（CPU硬件直算）| 存在舍入误差       |
| DOUBLE       | 8 字节（固定）     | 极其巨大（约 10^308）| 极高（CPU硬件直算）| 存在舍入误差       |
| DECIMAL(M,D) | 约 M+2 字节（可变）| 受 M 限制（最大 65位）| 较低（软件模拟计算）| 绝对精准，无误差   |
+--------------+--------------------+----------------------+--------------------+--------------------+
```

### 浮点数与定点数的选型原则与开发权衡

在工程架构中，技术的选择永远是一场空间、性能与可靠性之间的博弈。没有绝对完美的数据类型，只有最贴合业务场景的权衡决策。

#### 权衡维度：空间与性能 vs 可靠性

1. **浮点数的优势领域**：
   在固定的 4 字节或 8 字节空间内，浮点数凭借科学计数法（阶码机制）能够表达天文数字或微观极小的数值。同时，浮点运算能够直接被现代 CPU 的 FPU（浮点运算单元）硬件加速，吞吐量极高。在计算化学、分子建模、流体力学、天气预报、游戏物理引擎、3D 渲染等科学计算或图形图像领域，微小的尾数误差完全可以容忍，而对计算吞吐率和数值跨度要求极高，此时应当坚定选择 `FLOAT` 或 `DOUBLE`。
2. **定点数的不可替代性**：
   定点数占用空间大，运算需要数据库引擎在内存中逐位模拟算法，计算开销显著高于硬件浮点。但它带来了 100% 的准确率。正如老式功能手机（飞利浦、诺基亚）充电一次能待机一个月，而现代智能手机功能极其强大却必须一天一充、随身携带充电宝；纯电动汽车环保安静但补能耗时，燃油车加油五分钟即可上路——任何技术换取了高级特性的同时，必然要背负相应的资源代价。

在数据库领域，硬件存储介质与算力成本正在逐年下降，而由账目差错引发的法律风险、业务审计阻力与客户投诉损失则是不可承受之重。**我们宁可用稍微多一点的存储空间和 CPU 算力，去换取数据 100% 的可靠性与准确性**。

#### 行业真实工程规范

某大型连锁零售企业的核心技术规范中，有这样一条具有代表性的系统架构铁律：

> “在交易中台与结算中心的所有数据表设计中，除主键 ID、商品编码、条形码以及状态位等明确属于无小数的离散标识必须使用整型（`BIGINT` / `INT`）外，**凡是涉及金额、单价、折扣、费率、佣金、税率等一切带有小数点的字段，一律强制使用 `DECIMAL` 类型，严禁出现 `FLOAT` 或 `DOUBLE`。**”

该规范切中行业要害：在零售、外卖、电商平台中，即便一笔订单只差 0.0001 元，在亿级并发的流水日终对账中，就会汇聚成数以万计的账实不符，导致财务报表无法平账。因此，涉及资金资产的场景，`DECIMAL` 是唯一正确的选择。

### 位类型（BIT）的原理与实操

除了整型、浮点数与定点数之外，MySQL 还提供了一种专门存储二进制位串的数值类型：`BIT`。

#### BIT 类型的语法与容量限制

语法格式为：`BIT(M)`。
- $M$ 表示该字段包含的二进制位个数，取值范围为 `1 ~ 64`。
- 如果省略参数 $M$，默认值为 `1`，即 `BIT(1)`，此时只能存储 1 个二进制位（值只能是 `0` 或 `1`）。
- 物理存储占用空间为 $\lceil M / 8 \rceil$ 个字节（即 $(M + 7) / 8$ 字节向下取整）。

创建位类型测试表：

```sql
CREATE TABLE test_bit1 (
    f1 BIT,
    f2 BIT(5),
    f3 BIT(64)
);
```

若尝试指定超出范围的长度，例如 `f4 BIT(65)`，MySQL 会直接拒绝执行并提示超出最大边界值 64。

执行表结构查看：

```sql
DESC test_bit1;
```

结果显示 `f1` 为 `bit(1)`，`f2` 为 `bit(5)`。

#### 写入限制与进制解析

向 `test_bit1` 写入基础数据：

```sql
INSERT INTO test_bit1 (f1) VALUES (0), (1);
```

`f1` 作为 `BIT(1)`，写入 `0` 和 `1` 均成功。如果尝试写入十进制数字 `2`：

```sql
INSERT INTO test_bit1 (f1) VALUES (2);
```

执行直接报错：
`ERROR 1406 (22001): Data too long for column 'f1' at row 1`

这是因为十进制的 `2` 转换为二进制是 `10`，需要占用 2 个二进制位，超出了 `BIT(1)` 仅能容纳 1 位的上限。

针对 `f2 BIT(5)`，其最大容量为 5 个全 1 的二进制数：
$$\text{Bin: } 11111_2 = \text{Dec: } 16 + 8 + 4 + 2 + 1 = 31$$

测试极限边界写入：

```sql
-- 写入最大合法值 31
INSERT INTO test_bit1 (f2) VALUES (31);

-- 尝试写入 32（二进制为 100000，占 6 位）
INSERT INTO test_bit1 (f2) VALUES (32);
```

测试结果表明：`31` 顺利存入，而 `32` 立即触发 `Data too long for column 'f2'` 错误，确凿证明了位类型的容量是由其二进制位数而非十进制数值决定的。

#### 查询呈现与转换技巧（BIN、HEX 与隐式转换）

在终端或客户端（如 SQLyog、Navicat）中直接执行 `SELECT * FROM test_bit1;` 时，读者经常会看到奇怪的显示效果：

```text
+------+------+
| f1   | f2   |
+------+------+
| b'0' | NULL |
| b'1' | NULL |
| NULL | 0x1F |
+------+------+
```

这是因为 `BIT` 字段内部存储的是原生二进制比特流，数据库控制台和可视化工具会尝试按照 ASCII 字符或十六进制字面量进行渲染输出，导致直观上无法直接看清具体的二进制数值。

为了在查询中清晰地检视和分析位数据，可以使用以下三种手段：

##### 方式一：使用内置函数 BIN() 显示原生二进制

```sql
SELECT BIN(f1), BIN(f2) FROM test_bit1;
```

返回结果直接还原位串的二进制真实面貌，例如写入的 `31` 会直接显示为文本 `'11111'`。

##### 方式二：使用内置函数 HEX() 显示十六进制

```sql
SELECT HEX(f1), HEX(f2) FROM test_bit1;
```

数值 `31` 将被转换为十六进制形式的 `'1F'`。

##### 方式三：讲师常用技巧——算术运算隐式转十进制

```sql
SELECT f1 + 0, f2 + 0 FROM test_bit1;
```

在 SQL 查询中，只要对 `BIT` 字段进行数学加减运算（最便捷的是加 `0`），MySQL 的类型推导引擎就会自动将底层的位串提升为十进制整数参与算术运算并输出。此时 `f2` 会直接以人类最易读的十进制数值 `31` 呈现。

#### BIT 类型在日常开发中的实用评价

虽然 `BIT` 类型在存储上非常精简，但在日常 Web 业务开发中，其使用频率其实远低于整型：
1. 大多数仅表示二值状态（如“是否删除”、“是否激活”、“性别”）的字段，在工程习惯上通常优先使用 `TINYINT`（或 `TINYINT(1)`）。`TINYINT` 占 1 个字节，语义明确，各语言 ORM 框架（MyBatis、Hibernate、JPA）对其适配与反序列化极为丝滑成熟，不易引发乱码或类型映射异常。
2. 当需要存储大容量二进制流（如加密盐值、哈希校验码、文件流）时，MySQL 提供了更为强大的 `BINARY`、`VARBINARY` 以及 `BLOB` 家族，后者的容量和处理灵活性远胜 `BIT`。

因此，对 `BIT` 类型，开发者应当理解其底层按位截断的限制及 `+ 0` 的查询技巧，在设计极度节约存储空间的硬件通信、权限掩码（Permission Mask）等特殊位运算系统时按需选用。

### 本讲提到的题目

#### 题目：浮点数累加结果判定

**题干**：
在 MySQL 数据库中执行以下 SQL 脚本：

```sql
CREATE TABLE test_double2 (
    f1 DOUBLE
);

INSERT INTO test_double2 VALUES (0.4), (0.4), (0.3);

SELECT SUM(f1) = 1.1 FROM test_double2;
```

请问该查询语句输出的最终数值是什么？背后的底层机制是什么？如果要彻底解决该问题，表结构应当如何重构？

**解析**：
1. **执行结果**：输出值为 `0`。
2. **底层机制**：
   - 字段 `f1` 声明为双精度浮点数 `DOUBLE`，遵循 IEEE 754 标准，由符号位、11 位阶码位和 52 位尾数位组成。
   - 十进制小数 `0.4` 和 `0.3` 转换为二进制时均为无限循环小数，受限于有限尾数位长度，存储时会产生不可避免的截断舍入误差。
   - 对三条记录求和执行 `SUM(f1)` 时，累计计算结果为 `1.0999999999999999`，与字面量 `1.1` 进行相等性比较不成立。MySQL 中布尔逻辑假返回数值 `0`。
3. **重构方案**：
   将字段改为定点数类型 `DECIMAL`：
   ```sql
   ALTER TABLE test_double2 MODIFY f1 DECIMAL(5, 2);
   ```
   `DECIMAL` 底层以紧凑十进制格式精准存储，不产生进制截断误差，执行 `SELECT SUM(f1) = 1.1` 将精准返回 `1`。

## 62-日期时间类型讲解
> 对应分集：P62 | 原始标题：《62-日期时间类型讲解》

在业务系统的数据库设计中，日期和时间是使用频次最高、也是最容易出现隐性故障的字段类型之一。从电商订单的创建与支付时效、用户的注册与登录审计，到商品的限时秒杀与促销排期，无一不高度依赖精确的时间记录。

对于存储日期与时间，初学者往往只知道 `DATETIME`，对其他类型的存在意义与底层机制缺乏深究：为什么只记录时间的 `TIME` 类型取值范围能远超 24 小时甚至为负？为什么 `TIMESTAMP` 和 `DATETIME` 都能存年月日时分秒，字节数却差了一倍？为什么有些系统跨国部署后订单时间会凭空多出一小时？

MySQL 针对不同的时间精度与业务场景，提供了五种原生日期时间类型。本文将逐一拆解它们的存储结构、取值范围、解析歧义、时区敏感机理，并总结生产环境下的字段选型铁律。

---

### 日期时间类型概览与存储规格

在 MySQL（无论是 5.7 还是 8.0）中，核心的日期与时间类型共有五种：

```text
+---------------+----------+------------------------------------------------------+---------------------------------+
| 数据类型      | 存储空间 | 取值范围                                             | 标准展示格式                    |
+---------------+----------+------------------------------------------------------+---------------------------------+
| YEAR          | 1 字节   | 1901 ~ 2155 (以及 0000)                              | YYYY                            |
| DATE          | 3 字节   | 1000-01-01 ~ 9999-12-31                              | YYYY-MM-DD                      |
| TIME          | 3 字节   | -838:59:59 ~ 838:59:59                               | HH:MM:SS (或 D HH:MM:SS)        |
| DATETIME      | 8 字节   | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59           | YYYY-MM-DD HH:MM:SS             |
| TIMESTAMP     | 4 字节   | 1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC   | YYYY-MM-DD HH:MM:SS             |
+---------------+----------+------------------------------------------------------+---------------------------------+
```

从宏观维度观察这组类型：
1. **单一维度**：`YEAR` 仅仅存储年份，存储极其紧凑；`DATE` 专门记录年月日（无时刻）；`TIME` 专门记录时分秒（无日期）。
2. **复合维度**：`DATETIME` 与 `TIMESTAMP` 均同时记录年月日与时分秒，但二者的字节数、有效时间范围、时区关联性存在本质区别。

---

### 单一维度类型详解与解析规则

#### YEAR 类型：极端紧凑与历史遗留规则

`YEAR` 类型仅占用 1 个字节（8 个 bit）。一个字节最多只能表示 $2^8 = 256$ 种离散状态，因此它的年份跨度注定是有限的，设计区间为 `1901 ~ 2155` 年，加上一个特殊的 `0000` 年。

##### 语法声明演进
在早期的 MySQL 语法中，允许显式指定显示宽度，如 `YEAR(4)` 或 `YEAR(2)`。从 MySQL 5.5.27 起，两位格式的 `YEAR(2)` 已被废弃；从 MySQL 8.0.19 开始，显式声明宽度 `YEAR(4)` 同样不再推荐使用，未来版本将直接废弃显示宽度。在现代建表语句中，直接声明 `YEAR` 即可，默认均为 4 位。

```sql
CREATE TABLE test_year (
    f1 YEAR
);
```

##### 数据写入与边界校验
标准的写入方式是使用四位格式的字符串或数字：

```sql
-- 正常写入合法年份
INSERT INTO test_year VALUES ('2021'), (2022), (2155);

-- 尝试写入越界年份 2156
INSERT INTO test_year VALUES (2156);
```

执行越界写入时，MySQL 会直接报错：
`ERROR 1264 (22003): Out of range value for column 'f1' at row 1`

##### 两位年份的解析“黑洞”
尽管工程上严禁使用两位年份，但 MySQL 底层为了兼容旧系统，仍然保留了一套极易混淆的两位字符与数值转换映射：

```text
写入两位值              解析目标年份                底层逻辑依据
'01' ~ '69'   -->      2001 ~ 2069 年              假定为 21 世纪早期
'70' ~ '99'   -->      1970 ~ 1999 年              对应 UNIX 时间戳起点时代
数字 0        -->      0000 年                     视为绝对零值
字符 '0'/'00' -->      2000 年                     视为千禧年
```

验证该映射行为：

```sql
INSERT INTO test_year VALUES ('69'), ('70'), (0), ('00');
SELECT * FROM test_year;
```

查询结果依次为 `2069`、`1970`、`0000`、`2000`。

> **易错点**：数字 `0` 和带引号的字符串 `'00'` 在 `YEAR` 字段中解析出的年份完全不同！在开发中务必始终使用标准的四位数字或字符串（如 `'2024'`），杜绝任何两位简写。

#### DATE 类型：纯日期存储

`DATE` 占用 3 个字节，专门用于存储没有时间分量的纯日期（如出生日期、合同生效日、账单日），范围涵盖 `1000-01-01` 至 `9999-12-31`。

##### 语法与标准格式
标准格式为字符串 `'YYYY-MM-DD'`，如 `'2023-10-01'`。

```sql
CREATE TABLE test_date1 (
    f1 DATE
);

-- 标准写入
INSERT INTO test_date1 VALUES ('2021-03-01');

-- 紧凑字符串格式（自动识别）
INSERT INTO test_date1 VALUES ('20210301');

-- 纯数字隐式转换（不推荐）
INSERT INTO test_date1 VALUES (20210301);
```

上述三种方式均能成功存入 `2021-03-01`。无分隔符和纯数值写法依赖 MySQL 的内部推导机制，可读性极差，生产环境下必须强制统一为带短横线的 `'YYYY-MM-DD'` 格式。

##### 当前系统日期获取
向 `DATE` 字段插入当前系统日期时，可以使用以下内置函数：

```sql
-- 推荐使用 CURDATE() 或 CURRENT_DATE()
INSERT INTO test_date1 VALUES (CURDATE()), (CURRENT_DATE());

-- 使用 NOW() 同样可以写入
INSERT INTO test_date1 VALUES (NOW());
```

> **提示**：函数 `NOW()` 本身返回的是包含“年月日+时分秒”的完整时间戳，但在向 `DATE` 类型的字段插入时，MySQL 会自动截除时分秒分量，仅保留年月日入库。

#### TIME 类型：不仅是时刻，更是“时间间隔”

`TIME` 类型占用 3 个字节，标准表示为 `'HH:MM:SS'`。

初学者往往有一个巨大的认知误区：既然一天只有 24 小时，为什么 `TIME` 的官方取值范围是 `-838:59:59 ~ 838:59:59`，不仅有高达 800 多小时的跨度，居然还允许为负数？

> **定义**：
> `TIME` 类型在 MySQL 中承载了双重语义：
> 1. **时刻（Time of Day）**：表示一天之内的具体几点几分几秒（`00:00:00 ~ 23:59:59`）；
> 2. **时间间隔 / 耗时（Elapsed Time / Interval）**：表示两个事件之间流逝的工时、时长差值或倒计时。

由于它能充当跨天累计耗时（例如长跑比赛计时、服务器持续运行时间、机器累计工作台时），因此它支持带有天数（Day）的输入格式，最大支持约 34 天（$34 \times 24 \approx 816$ 小时，上限为 838 小时 59 分 59 秒）。负数则用于表示倒计时或相减产生的负时间差。

##### 语法与格式解析陷阱
创建测试表：

```sql
CREATE TABLE test_time1 (
    f1 TIME
);
```

`TIME` 类型支持多种复合字符串语法，但其解析规则存在极为隐蔽的歧义：

```sql
-- 包含天数的格式：'D HH:MM:SS'
-- 2 天 12 小时 30 分 29 秒，转换为：2 * 24 + 12 = 60 小时
INSERT INTO test_time1 VALUES ('2 12:30:29');

-- 标准时分秒格式
INSERT INTO test_time1 VALUES ('12:35:20');

-- 两位带冒号格式：'HH:MM'
-- 重点：'12:10' 被解析为 12 小时 10 分钟 00 秒，绝不是 12 分钟 10 秒！
INSERT INTO test_time1 VALUES ('12:10');

-- 单个数字格式：'SS'
-- '45' 将被直接视为 45 秒，解析为 00:00:45
INSERT INTO test_time1 VALUES ('45');

-- 纯数字无冒号格式：1210
-- 重点：数值 1210 被解析为 MMSS，即 12 分钟 10 秒！
INSERT INTO test_time1 VALUES (1210);
```

执行查询校验：

```sql
SELECT * FROM test_time1;
```

结果输出：
- `'2 12:30:29'` $\rightarrow$ `60:30:29`
- `'12:35:20'` $\rightarrow$ `12:35:20`
- `'12:10'` $\rightarrow$ `12:10:00`
- `'45'` $\rightarrow$ `00:00:45`
- `1210` $\rightarrow$ `00:12:10`

> **易错点**：
> 字符串 `'12:10'` 带冒号时，MySQL 遵循“从高位小时开始截取”的规则，被视作 **12 小时 10 分**；而纯数值 `1210` 不带冒号时，MySQL 遵循“低位补齐”规则，将其视作 **12 分 10 秒**！这种解析极易引发业务数据错位。在编写 SQL 时，必须始终使用完整的 `'HH:MM:SS'` 格式。

获取当前时间可以使用 `CURTIME()` 或 `CURRENT_TIME()`：

```sql
INSERT INTO test_time1 VALUES (CURTIME());
```

### 复合维度类型对比：DATETIME 与 TIMESTAMP

当业务需要精确锁定到某年某月某日某时某分某秒时，开发者必须在 `DATETIME` 与 `TIMESTAMP` 之间做出选择。这两者在底层实现上有着本质的鸿沟。

```text
DATETIME 架构：所见即所得（客观面值存储）
+------------------------+      存储      +------------------------+      读取      +------------------------+
| 应用写入：             |  ---------->  | 磁盘存储：             |  ---------->  | 应用读取：             |
| 2024-03-15 14:00:00    | (不转时区)    | 2024-03-15 14:00:00    | (不转时区)    | 2024-03-15 14:00:00    |
+------------------------+               +------------------------+               +------------------------+
                                                                                  (无论数据库时区如何切换，永不改变)

TIMESTAMP 架构：时区自适应（UTC 毫秒时间戳存储）
+------------------------+      存储      +------------------------+      读取      +------------------------+
| 东八区 (+08:00) 写入： |  ---------->  | 磁盘存储：             |  ---------->  | 东九区 (+09:00) 读取： |
| 2024-03-15 14:00:00    | (减去 8 小时) | 2024-03-15 06:00:00    | (加上 9 小时) | 2024-03-15 15:00:00    |
+------------------------+               | (UTC 纪元毫秒数)       |               +------------------------+
                                         +------------------------+               (跨时区查询自动增减时间差)
```

#### 核心差异对比

```text
+----------------------+------------------------------------------+------------------------------------------+
| 比较维度             | DATETIME                                 | TIMESTAMP                                |
+----------------------+------------------------------------------+------------------------------------------+
| 存储占用             | 8 字节（MySQL 5.6.4+ 优化为 5 字节）      | 4 字节                                   |
| 时间范围             | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59| 1970-01-01 00:00:01 ~ 2038-01-19 03:14:07|
| 时区相关性           | 无关（所见即所得，原样存取）             | 强相关（内部转为 UTC 存储，按时区渲染）  |
| 默认零值             | '0000-00-00 00:00:00'                    | '0000-00-00 00:00:00'                    |
| 排序与比对速度       | 字符串/解包数值比较                      | 整数毫秒数比较（性能略优）               |
+----------------------+------------------------------------------+------------------------------------------+
```

#### TIMESTAMP 的 2038 年灾难边界

`TIMESTAMP` 仅占用 4 个字节（32 位有符号整数），其存储的是从世界标准时间（UTC）`1970-01-01 00:00:00` 开始计算的秒数偏移量。
32 位有符号整型的最大正整数为：
$$2^{31} - 1 = 2147483647$$

将 2147483647 秒累加到 1970 年元旦，其极限时间点即为：
**2038 年 01 月 19 日 03:14:07（UTC）**。

测试越界写入：

```sql
CREATE TABLE test_timestamp1 (
    f1 TIMESTAMP
);

-- 写入合法上限边缘
INSERT INTO test_timestamp1 VALUES ('2038-01-19 03:14:07');

-- 尝试写入越界时间（例如 2038-01-20）
INSERT INTO test_timestamp1 VALUES ('2038-01-20 00:00:00');
```

执行后立即触发异常：
`ERROR 1292 (22007): Incorrect datetime value: '2038-01-20 00:00:00' for column 'f1' at row 1`

> **提示**：如果系统设计生命周期超过 2038 年，或者需要存储未来的长期契约（如 30 年房贷合同、百年品牌规划），绝不能使用 `TIMESTAMP`。

#### 时区动态联动实证测试

为了直观见证时区对两者的实际影响，我们构建双字段比对表：

```sql
CREATE TABLE test_tz_compare (
    d1 DATETIME,
    d2 TIMESTAMP
);
```

##### 步骤一：在默认东八区（+08:00）写入数据

```sql
INSERT INTO test_tz_compare VALUES 
('2024-03-15 14:00:00', '2024-03-15 14:00:00'),
(NOW(), NOW());

SELECT * FROM test_tz_compare;
```

此时两列显示的内容完全相同，肉眼看不到任何差异。

##### 步骤二：动态修改当前会话的时区至东九区（+09:00）

```sql
-- 将当前会话时区设置为东九区（如东京时间）
SET time_zone = '+09:00';

-- 再次查询完全相同的数据表
SELECT * FROM test_tz_compare;
```

控制台返回的真实结果：
- `d1`（`DATETIME`）：依然保持 `'2024-03-15 14:00:00'`，丝毫未变。
- `d2`（`TIMESTAMP`）：自动变为了 `'2024-03-15 15:00:00'`，整整增加了一小时！

##### 步骤三：底层机理解密
- 当我们在东八区向 `TIMESTAMP` 写入 `14:00:00` 时，MySQL 底层推算出对应的 UTC 国际标准时间为 `06:00:00`（$14 - 8 = 6$），并将 `06:00:00` 的毫秒/秒数写进磁盘。
- 当会话时区切换至东九区后，MySQL 读取出底层的 UTC `06:00:00`，自动累加 9 个小时的时差偏移量，动态渲染出 `15:00:00` 输出给客户端。
- 反观 `DATETIME`，它在磁盘上直接记录了字面字符数值，既不扣除 8 小时，也不累加 9 小时，完全与时区脱钩。

### 生产环境下的时间选型决策与架构法则

在实际工程落地中，面对丰富的数据类型，团队应当遵循怎样的技术规范？

#### 伪优化陷阱：拆分 DATE 与 TIME 的误区

有些开发者在审视存储空间时提出设想：`DATE` 占 3 字节，`TIME` 占 3 字节，两者合起来才占 6 字节；而早期的 `DATETIME` 占 8 字节。为了省下这 2 个字节，能否在表中设立两列——一列存年月日、一列存时分秒？

> **结论**：**严禁采用这种拆分设计！**
> 1. **心智负担与编码复杂度**：业务查询绝大多数要求跨天、跨周期的精确时间范围检索（如 `WHERE create_time BETWEEN t1 AND t2`）。若拆为两列，SQL 必须编写为复合比对逻辑，不仅可读性极差，而且极其容易在跨天边界出现逻辑 Bug。
> 2. **索引与性能损耗**：对单一 `DATETIME` 建立单列索引，B+ 树能完美维持全局时间有序；如果拆成两列，只能建立 `(date_col, time_col)` 复合索引，树节点更大，查询条件中的范围检索会立即阻断后续列的索引下推与使用，性能反受其害。
> 3. **空间收益微乎其微**：在 MySQL 5.6.4 之后，官方对 `DATETIME` 的底层存储结构进行了优化（不带微秒时仅占用 5 个字节），拆分方案在存储上甚至毫无优势。

#### DATETIME 的统治地位

在当代 Web 架构中，**`DATETIME` 是绝大多数业务实体的绝对首选**：
- **直观性与确定性**：研发人员、运维人员和 DBA 在排查问题或手动执行 SQL 变更时，`DATETIME` 所见即所得，绝不会因客户端时区设置混乱而产生错觉。
- **超长生命周期**：覆盖到 9999 年，彻底免疫 2038 年时间戳溢出漏洞。
- **现代化国际化解耦**：现代大型系统通常在应用层（Application Layer）统一处理时区转换逻辑（服务端统一切为 UTC，前端根据用户的浏览器地理位置进行本地化时间格式化展示），无需依赖数据库引擎在底层频繁转换。

#### 整数时间戳（BIGINT）的高并发场景

在超高并发流水日志、分布式链路追踪、秒级高频排序等极致性能场景中，业界常采用 `BIGINT` 存储 13 位毫秒级 UNIX 时间戳：
- 占用 8 字节；
- 能够直接利用 CPU 原生整数寄存器进行瞬时比对与范围排序；
- 与 Java、Go、Python 等后端语言原生的时间戳数据流完美映射，避免了字符串解析开销。在不需要直接以 SQL 肉眼直查可读日期的核心底层链路中，这是一种成熟高效的备选方案。

## 63-文本字符串类型（含ENUM、SET）讲解
> 对应分集：P63 | 原始标题：《63-文本字符串类型（含ENUM、SET）讲解》

在关系型数据库的设计中，文本字符串是业务数据中使用占比最高、变化最为丰富的一类数据。从用户的姓名、手机号、家庭住址，到商品的图文详情、文章长帖、新闻评论，全都以字符串形态驻留在数据表中。

然而，面对字符串字段，许多开发者的习惯极为单一——无论什么字段，随手就是一个 `VARCHAR(255)`。实际上，MySQL 针对不同长度、不同业务语义的文本，设计了一套细致入微的类型体系：从定长的 `CHAR` 到变长的 `VARCHAR`，从长文本的 `TEXT` 家族，再到具有强选项约束的 `ENUM`（枚举）与 `SET`（集合）。更为关键的是，选择 `CHAR` 还是 `VARCHAR`，不仅关乎字节数的节省，更直接受制于底层**存储引擎（InnoDB vs MyISAM）**的行格式机制。

本文将深入文本字符串类型的底层存储结构、空格截断与填充陷阱、最大长度物理限制，并剖析为何在 InnoDB 存储引擎下 `VARCHAR` 能够颠覆传统的“定长优先”经验。

### 文本字符串类型体系总览

MySQL 中的文本字符串类型可以划分为三大分支：

```text
+-----------------------+-------------------+----------------------------------------------------------+
| 类别                  | 具体数据类型      | 核心特征与场景                                           |
+-----------------------+-------------------+----------------------------------------------------------+
| 短字符串（通用业务）  | CHAR(M)           | 固定长度字符，不足右侧补空格；检索时自动截断空格         |
|                       | VARCHAR(M)        | 可变长度字符，按实际内容+长度前缀存储，需显式声明 M      |
+-----------------------+-------------------+----------------------------------------------------------+
| 长文本（非定长文本）  | TINYTEXT          | 最大 255 字节（约 0.25 KB）                              |
|                       | TEXT              | 最大 65,535 字节（约 64 KB），最常用文本类型             |
|                       | MEDIUMTEXT        | 最大 16,777,215 字节（约 16 MB）                         |
|                       | LONGTEXT          | 最大 4,294,967,295 字节（约 4 GB）                       |
+-----------------------+-------------------+----------------------------------------------------------+
| 预定义选项（受限枚举）| ENUM              | 单选枚举，1~2 字节，底层映射为数字索引，最多 65,535 项   |
|                       | SET               | 多选集合，1~8 字节，底层以位图存储，最多 64 项           |
+-----------------------+-------------------+----------------------------------------------------------+
```

### 定长字符 CHAR 与变长字符 VARCHAR 的底层机制

#### CHAR 类型的定长特性与空格填充陷阱

`CHAR(M)` 中的 $M$ 代表**字符数**（注意不是字节数），取值范围为 `0 ~ 255`。如果不指定 $M$，默认值为 `1`，即 `CHAR(1)`。

##### 物理存储与空格填充行为
当向 `CHAR(M)` 写入字符时，如果字符数不足 $M$ 个，MySQL 会在物理存储阶段在字符串的**右侧用半角空格自动填充**，补齐至 $M$ 个字符的长度。

然而，更为特殊的是它的读取逻辑：**当从数据库中执行 `SELECT` 检索 `CHAR` 字段时，MySQL 会自动将字符串尾部所有填充的空格全部截断剔除！**

验证测试：

```sql
CREATE TABLE test_char1 (
    c1 CHAR,
    c2 CHAR(5)
);

DESC test_char1;
```

结果显示 `c1` 默认宽度为 `char(1)`，`c2` 为 `char(5)`。

向 `c2` 写入长度不足 5 个字符的数据：

```sql
INSERT INTO test_char1 (c2) VALUES ('ab');
INSERT INTO test_char1 (c2) VALUES ('尚硅谷');
```

使用 `CONCAT()` 拼接星号测试是否存在末尾空格：

```sql
SELECT CONCAT(c2, '*') FROM test_char1;
```

控制台返回的结果为 `'ab*'` 和 `'尚硅谷*'`，原本用于填充占位的空格消失得无影无踪。

##### 极为致命的空格抹除陷阱
由于 MySQL 认为 `CHAR` 尾部的空格纯粹是系统为了凑齐定长而填充的“填充物”，因此当你主动写入带有末尾有效空格的数据时，系统会产生误伤：

```sql
-- 主动写入 'ab  '（后面带两个空格，共 4 个字符）
INSERT INTO test_char1 (c2) VALUES ('ab  ');

-- 测量其字符长度
SELECT CHAR_LENGTH(c2) FROM test_char1 WHERE c2 LIKE 'ab%';
```

执行后，`CHAR_LENGTH(c2)` 查出的结果竟然是 **`2`**！
你辛辛苦苦存进去的两个业务空格，被 MySQL 在检索阶段当作无用填充强行裁掉了。

> **易错点**：如果业务数据本身在字符串末尾具有严格的空格语义（例如特定报文格式、对齐协议），绝对不能选用 `CHAR` 类型，否则末尾空格会在出库时被全量抹去。

#### VARCHAR 类型的变长机制与长度前缀

`VARCHAR(M)` 同样表示字符数，但其参数 $M$ **必须显式声明**，不能缺省（缺省会直接抛出语法错误）。

##### 版本演进与字符定义
- **MySQL 4.0 及以前**：`VARCHAR(20)` 代表 20 个**字节**。如果存放 UTF-8 编码的汉字（一个汉字占 3 字节），最多只能存放 6 个汉字。
- **MySQL 5.0 及以后**：`VARCHAR(20)` 代表 20 个**字符**。无论是数字、英文字母还是汉字，都能完整存放 20 个。

##### 物理存储开销：实际数据 + 长度前缀
`VARCHAR` 的物理占用空间不是固定的，而是遵循公式：
$$\text{存储空间} = \text{实际字符占用字节数} + L$$
其中 $L$ 为记录实际字符长度的前缀字节：
- 当定义的列最大可能字节数 $\le 255$ 时，$L = 1$ 字节；
- 当定义的列最大可能字节数 $> 255$ 时，$L = 2$ 字节。

#### VARCHAR 的物理极限：为什么不能定义 VARCHAR(65535)？

很多官方手册标注 `VARCHAR` 的最大长度是 65,535 字节。如果在建表时尝试声明 `VARCHAR(65535)`：

```sql
CREATE TABLE test_varchar_limit (
    name VARCHAR(65535)
);
```

MySQL 会立刻抛出错误：
`ERROR 1074 (42000): Column length too big for column 'name' (max = 21845); use BLOB or TEXT instead`

系统明确提示最大长度只能写 `21845`。这是为什么？

底层计算推导如下：
1. MySQL 规定**整张数据表中所有列的物理总长度不能超过 65,535 字节**（行长度限制，Row Size Limit）。
2. 在当前默认字符集为 UTF-8（准确说是 `utf8mb3`）的环境下，每个字符最多占用 3 个字节：
   $$\frac{65535}{3} = 21845$$
3. 如果字符集是更完善的 `utf8mb4`（每个字符最多占 4 字节），那么 $65535 / 4 = 16383$ 字符。
4. 此外，一行数据中还需要额外扣除：
   - 变长列长度列表（`VARCHAR` 自身需要 2 个字节记录长度）；
   - NULL 标志位（若允许为 NULL，需要 1 个字节做位图记录）。
   因此在真实建表中，即便是单个列，极限值往往还要比 21845 再少几个字符。

### CHAR 与 VARCHAR 的工程选型与存储引擎内幕

在日常面试与架构评审中，“`CHAR` 与 `VARCHAR` 如何选择”是一道高频考题。回答这道题不能只停留在“定长与变长”的表面，必须上升到存储引擎与磁盘 I/O 的高度。

#### 空间与时间的经典博弈

```text
+----------+--------------------------+--------------------------+
| 比较维度 | CHAR                     | VARCHAR                  |
+----------+--------------------------+--------------------------+
| 空间占用 | 固定分配，存在尾部空间浪费| 按需分配，额外占 1~2 字节 |
| 访问速度 | 极快（偏移量固定，免计算）| 略慢（需解析前缀长度偏移）|
| 数据碎片 | 几乎不产生碎片，就地更新  | 频繁更新长串易引发页分裂  |
+----------+--------------------------+--------------------------+
```

#### 适用 CHAR 的三大经典场景

尽管 `VARCHAR` 节省空间，但在以下三种场景中，`CHAR` 具有绝对优势：

##### 场景一：存储极短的文本（如门牌号、状态码、性别标识）
如果存储的内容本身只有 1~2 个字符，使用 `VARCHAR` 不仅无法省空间，反而会更浪费！
例如存储单字符 `'A'`，`CHAR(1)` 占 1 字节；而 `VARCHAR(1)` 既要存字符 `'A'`（1 字节），还要额外拿 1 个字节记录其长度为 1，总共占用 2 字节，空间开销直接翻倍！

> **生活比喻（买车与买自行车的对比）**：
> 去 4S 店买一辆 10 万元的汽车，缴纳 100 元手续费，你会觉得手续费极低可以忽略；但如果给孩子买一辆 200 元的小自行车，商家同样强收 100 元手续费（占售价的 50%），任何人都会觉得这是不可理喻的浪费。极短字符串使用 `VARCHAR` 的长度前缀，就是那笔不成比例的沉重手续费。

##### 场景二：天然严格固定长度的业务数据
- MD5 哈希校验码（固定 32 位字符）；
- UUID / GUID（去掉横杠后固定 32 位字符）；
- 居民身份证号（固定 18 位字符）；
- 手机号码（固定 11 位字符）。
此类数据每条记录的长度完全相同，不存在变长节省空间的可能，使用 `CHAR` 能够免除长度计算。

##### 场景三：更新极其频繁且长度变动剧烈的字段
如果某列数据不仅更新频率极高，而且每次更新长度剧烈变化：
- 使用 `VARCHAR` 时，旧空间容纳不下变长后的新字符串，InnoDB 必须在数据页内部进行碎片整理、甚至将记录迁移至新页面（引发行溢出与页分裂），产生沉重的磁盘 I/O；
- 使用 `CHAR` 时，其物理空间从建表起便严格锁死，更新永远是**就地覆盖（In-place Update）**，执行效率极高。

#### 存储引擎维度的重大认知反转：InnoDB 为什么推荐 VARCHAR？

在 MySQL 早期或面试题库中，常有“`CHAR` 比 `VARCHAR` 快，尽量用 `CHAR`”的说法。但这一结论在现代 MySQL（默认 `InnoDB`）环境下被彻底颠覆！

```text
MyISAM 引擎的数据行架构（静态表优势）：
+---------+------------------+------------------+------------------+
| Row 1   | CHAR(10) [固定]  | CHAR(20) [固定]  | INT [固定]       | ---> 行长度恒定，寻址可直接按公式：
+---------+------------------+------------------+------------------+      Offset = Row_Index * Row_Size
| Row 2   | CHAR(10) [固定]  | CHAR(20) [固定]  | INT [固定]       |      硬件级别瞬间跳转定位！
+---------+------------------+------------------+------------------+

InnoDB 引擎的数据行架构（紧凑型/动态型）：
+------------------------------------------------------------------+
| 变长字段长度列表 | NULL 值列表 | 记录头信息 | 列1 | 列2 | ...     |
+------------------------------------------------------------------+
(底层在存储 Compact / Dynamic 行格式时，变长字符集下的 CHAR 同样按变长处理！
 核心性能瓶颈是：整行体积越小，16KB 数据页装下的行越多，磁盘 I/O 越少！)
```

1. **MyISAM 引擎**：
   MyISAM 的存储结构中有一种特有的“静态表（Static Format）”。如果表中所有列全是定长（例如全用 `CHAR`、`INT`），MyISAM 每行记录所占的字节数完全相同。此时通过物理指针寻址可以直接计算偏移量：
   $$\text{Offset} = \text{RowID} \times \text{RowLength}$$
   寻址速度极快。因此在 MyISAM 时代，空间换时间首选 `CHAR`。
2. **Memory 引擎**：
   在内存引擎中，即使声明为 `VARCHAR`，内部也是一律按照定长 `CHAR` 进行内存分配。
3. **InnoDB 引擎（现代核心基准）**：
   InnoDB 内部的行格式（`Compact`、`Dynamic`）并没有为定长列单独开辟类似 MyISAM 的静态寻址通道。特别是在使用变长字符集（如 `utf8mb4`）时，`CHAR(10)` 在底层根本就不是固定 10 字节，而是根据具体字符在 10~40 字节之间浮动，InnoDB 同样要用变长机制来管理它！
   因此，在 InnoDB 中，**决定性能的关键指标是整行数据的总物理字节数**：
   - 使用 `VARCHAR` 能够最大限度剔除空格浪费，压低单行体积；
   - 单行体积越小，一个标准 16 KB 的 InnoDB 数据页就能容纳更多的数据行；
   - 内存缓冲池（Buffer Pool）命中率更高，执行表扫描或索引遍历时的**磁盘 I/O 次数大幅减少**！

> **结论**：在当前绝大多数以 InnoDB 为引擎的业务系统中，除了上述明确固长或极短的场景外，**首选推荐使用 `VARCHAR`**。

### 长文本类型（TEXT 家族）与存储空洞陷阱

当单列文本长度可能突破几千甚至上万字符时，`VARCHAR` 不仅无法胜任，而且会受限于单行 65,535 字节的硬限制。此时必须接入 `TEXT` 家族：

- `TINYTEXT`（255 字节）
- `TEXT`（64 KB，最常用）
- `MEDIUMTEXT`（16 MB）
- `LONGTEXT`（4 GB）

#### TEXT 与 CHAR 的读取差异

创建 TEXT 测试表：

```sql
CREATE TABLE test_text1 (
    tx TEXT
);

INSERT INTO test_text1 VALUES ('尚硅谷   ');
SELECT CHAR_LENGTH(tx) FROM test_text1;
```

查询结果：返回 `6`（3 个汉字 + 3 个空格）。
与 `CHAR` 会自动抹平尾部空格不同，`TEXT` **完整保留所有输入的尾部空格与格式符**，存多少就是多少。

#### 生产红线：存储空洞与垂直分表规范

由于 `TEXT` 字段体积庞大，在工程架构中存在两项严格红线：

1. **严禁用 TEXT 字段充当主键**：主键要求唯一且具备紧凑的高效索引，`TEXT` 长度不固定且体积臃肿，无法直接高效构建 B+ 树主键索引。
2. **警惕频繁更新与删除引发的“存储空洞”**：
   如果在核心业务表中存放了上万字的大文本，后续对该记录进行大范围修改或 `DELETE` 删除，操作系统和数据库引擎无法立即把这块庞大的物理磁盘空间无缝回收，数据页内部会撕裂出巨大的**存储空洞（Holes）**，产生大量的磁盘碎片（Fragmentation）。
   随着碎片堆积，整张表的全表扫描和普通字段查询性能将发生断崖式下跌。

> **架构规范**：
> **严禁在核心事务主表（如用户表、订单表）中直接嵌入大容量 `TEXT` 字段！**
> 必须实施**垂直分表**策略：将 `TEXT` 大字段剥离至独立的扩展子表中（例如 `article_content` 表），通过主键与主表（`article_info`）关联。主表只保留标题、作者、发布时间等高频检索轻量字段，仅在用户需要查看正文详情时才通过单条主键点查子表，从而捍卫核心数据流的高速缓存命中率。

### 选项约束类型：ENUM 与 SET

MySQL 还提供了两种专门用于收敛输入范围的特殊字符串类型：`ENUM` 与 `SET`。它们的本质是**将预定义的字符串映射为底层的整型数字存储**。

#### ENUM（枚举类型）：严格单选

`ENUM` 又称枚举类型，适用于互斥的单选场景（如性别、季节、审批状态）。

##### 定义与使用

```sql
CREATE TABLE test_enum (
    season ENUM('春', '夏', '秋', '冬', 'UNKNOWN')
);

-- 正确写入单选值
INSERT INTO test_enum VALUES ('春'), ('秋');

-- 写入未定义的值（报错）
INSERT INTO test_enum VALUES ('人');
-- ERROR 1265 (01000): Data truncated for column 'season' at row 1

-- 尝试同时写入两个值（报错）
INSERT INTO test_enum VALUES ('春,秋');
-- 同样被判定为非法枚举值而报错
```

##### 关键特性
1. **忽略大小写**：如果枚举定义为 `'UNKNOWN'`，写入小写 `'unknown'` 能够被正常解析入库。
2. **底层索引数字映射**：`ENUM` 在底层是按照定义时的先后顺序编为从 `1` 开始的整数索引：
   - `'春'` $\rightarrow$ `1`
   - `'夏'` $\rightarrow$ `2`
   - `'秋'` $\rightarrow$ `3`
   - `'冬'` $\rightarrow$ `4`
   - `'UNKNOWN'` $\rightarrow$ `5`
   
   因此，可以直接向字段写入整数索引：
   ```sql
   INSERT INTO test_enum VALUES (1), (3);
   SELECT * FROM test_enum;
   ```
   查询结果直接显示为 `'春'` 和 `'秋'`。
3. **NULL 值规则**：如果字段未设置 `NOT NULL`，允许显式存入 `NULL`。

#### SET（集合类型）：多选排列

`SET` 适用于多选场景（如用户标签、兴趣爱好、权限位）。它的上限是 64 个成员。

```sql
CREATE TABLE test_set (
    s SET('A', 'B', 'C')
);

-- 写入单选或多选（以半角逗号分隔）
INSERT INTO test_set VALUES ('A'), ('A,B'), ('A,B,C');

-- 写入重复选项：底层自动去重
INSERT INTO test_set VALUES ('A,B,C,A');
SELECT * FROM test_set WHERE s LIKE '%A%';
```

查询结果：写入 `'A,B,C,A'` 不仅不会报错，而且系统会自动完成去重，最终入库的依然是 `'A,B,C'`。如果写入集合中不存在的项（如 `'A,B,D'`），则会直接拦截报错。

#### 综合实战演练

构建包含枚举与集合的复合业务表：

```sql
CREATE TABLE temp_multi (
    gender ENUM('男', '女'),
    hobbies SET('睡觉', '打豆豆', '看书', '写代码')
);

-- 合法写入：性别单选，爱好选两项
INSERT INTO temp_multi VALUES ('男', '睡觉,打豆豆');

-- 校验非法写入：试图在单选字段塞入两个值
INSERT INTO temp_multi VALUES ('男,女', '看书');
-- ERROR 1265: Data truncated for column 'gender'
```

尽管 `ENUM` 和 `SET` 能够提供数据库级别的取值校验并节约空间，但在现代化微服务架构中，过度依赖数据库的枚举类型会导致后续增删枚举项时需要执行昂贵的 `ALTER TABLE` DDL 操作。因此，现代企业级开发更倾向于使用 `TINYINT` 配合应用层 Java/Go 代码中的枚举类进行状态管理；而在小型单体应用或强一致性静态归档表中，`ENUM` 与 `SET` 依然是高效的选择。

## 64-二进制类型与JSON类型讲解
> 对应分集：P64 | 原始标题：《64-二进制类型与JSON类型讲解》

在关系型数据库的设计演进中，数据形态早已超越了单纯的数值与文字。随着移动互联网与多媒体应用的发展，系统不仅需要存储纯文本，还需要处理图像、加密哈希、序列化对象，以及前后端高频交互的半结构化数据（JSON）和地理空间信息。

本文将全面拆解二进制字符串类型、BLOB 对象的存储缺陷与架构替代方案，并详解现代 Web 开发中不可或缺的 JSON 数据类型及其查询提取技巧。

### 二进制字符串类型（BINARY 与 VARBINARY）

#### 二进制类型与字符类型的本质鸿沟

在前面学习的 `CHAR`、`VARCHAR`、`TEXT` 体系中，数据被称为“文本字符串”。文本字符串的核心特征在于：**它们是面向字符（Character）的，其存储与检索必须深度绑定字符集（Character Set，如 UTF-8、GBK）和校对规则（Collation）**。数据库在比较 `'a'` 和 `'A'` 时是否区分大小写，完全取决于 Collation 的定义。

而 `BINARY` 与 `VARBINARY` 被称为“二进制字符串”：
- 它们存储的是未经任何字符集编码转义的**原始二进制字节（Byte）流**；
- 排序与比较操作完全基于**字节的数值（0~255）**逐字节比对，天然区分大小写，且不受任何数据库字符集配置的影响；
- 常用于存储二进制散列值（如 MD5、SHA256 生成的原始 16 字节/32 字节 Hash）、AES 加密密文、UUID 二进制压缩、序列化协议数据等。

```text
文本类型 vs 二进制类型对比：
+-----------------------+-----------------------+----------------------------------+----------------------------------+
| 类型分支              | 核心代表              | 计量单位                         | 比较规则                         |
+-----------------------+-----------------------+----------------------------------+----------------------------------+
| 文本字符串            | CHAR, VARCHAR         | 字符数（Character）              | 依赖字符集 Collation (通常忽略大小写) |
| 二进制字符串          | BINARY, VARBINARY     | 字节数（Byte）                   | 逐字节二进制比对 (严格区分大小写) |
+-----------------------+-----------------------+----------------------------------+----------------------------------+
```

#### 定长 BINARY 与变长 VARBINARY 的机制差异

`BINARY(M)` 与 `VARBINARY(M)` 的关系，完全等价于 `CHAR(M)` 与 `VARCHAR(M)`：

- **BINARY(M)**：定长二进制，参数 $M$ 表示字节数。如果不指明 $M$，默认值为 `1`（只能存 1 个字节）。如果写入的数据不足 $M$ 个字节，**MySQL 会在右侧用十六进制的零值 `\0`（即 `0x00`）填充补齐**，以满足定长要求。
- **VARBINARY(M)**：变长二进制，参数 $M$ 表示允许存储的最大字节数。**必须显式指明 $M$**，不可缺省。物理存储空间等于实际字节数加上 1 或 2 个字节的长度前缀。

##### 语法声明与建表实测

```sql
CREATE TABLE test_binary1 (
    f1 BINARY,          -- 默认宽度为 1 个字节
    f2 BINARY(3),       -- 固定 3 个字节
    f3 VARBINARY(10),   -- 必须指明长度
    f4 VARBINARY(10)
);

DESC test_binary1;
```

向单字节字段 `f1` 写入字符数据：

```sql
-- 写入单个 ASCII 字符 'a'（占 1 字节），成功
INSERT INTO test_binary1 (f1) VALUES ('a');

-- 尝试写入 'ab'（占 2 字节）
INSERT INTO test_binary1 (f1) VALUES ('ab');
-- ERROR 1406 (22001): Data too long for column 'f1' at row 1
```

##### 长度补齐与检索对比验证
向 `f2 BINARY(3)` 和 `f4 VARBINARY(10)` 均写入两个字符 `'ab'`：

```sql
INSERT INTO test_binary1 (f2, f4) VALUES ('ab', 'ab');

SELECT LENGTH(f2), LENGTH(f4) FROM test_binary1 WHERE f2 IS NOT NULL;
```

查询结果：
- `LENGTH(f2)` 输出 **`3`**（实际内容为 `'ab\0'`，底层自动补全了 1 个零字节）；
- `LENGTH(f4)` 输出 **`2`**（变长记录，实际存了 2 个字节就只记录 2 个字节）。

### 二进制大对象（BLOB 家族）与多媒体存储

当需要保存的二进制数据体积突破普通字段限制时，MySQL 提供了 `BLOB`（Binary Large Object，二进制大对象）家族。

#### BLOB 四大规格定义

`BLOB` 家族同样根据存储上限划分为四个梯度，与 `TEXT` 家族形成镜像对应：

```text
+----------------+--------------------+----------------------------+-------------------------------------+
| BLOB 类型      | 最大物理存储容量   | 换算常用容量单位           | 典型应用场景                        |
+----------------+--------------------+----------------------------+-------------------------------------+
| TINYBLOB       | 255 字节           | 约 0.25 KB                 | 极小加密盐值、认证凭证              |
| BLOB           | 65,535 字节        | 约 64 KB                   | 紧凑证书、小配置二进制包            |
| MEDIUMBLOB     | 16,777,215 字节    | 约 16 MB                   | 标准图片、短语音切片                |
| LONGBLOB       | 4,294,967,295 字节 | 约 4 GB                    | 高清长视频、大型可执行文件、ISO 镜像|
+----------------+--------------------+----------------------------+-------------------------------------+
```

#### BLOB 存储实操测试

创建包含 `MEDIUMBLOB` 字段的测试表：

```sql
CREATE TABLE test_blob1 (
    id INT,
    image MEDIUMBLOB
);
```

在数据库层面，可以通过 GUI 客户端（如 SQLyog、Navicat）或者后端代码（Java 使用 JDBC 的 `PreparedStatement.setBinaryStream()`）将本地磁盘上的图片（如 JPG、PNG）以输入流的方式直接灌入 `image` 字段。

然而在客户端执行常规查询时：

```sql
SELECT * FROM test_blob1;
```

控制台只能返回一长串乱码或十六进制符号。数据库本质上无法直接理解该多媒体资源，只能被动充当字节搬运工。

### 架构铁律：为什么生产环境中严禁在数据库中存文件？

虽然 MySQL 在功能上完全支持通过 `LONGBLOB` 存储高达 4GB 的多媒体文件，但在真实的工业级后端架构中，**将图片、音视频等大文件直接存储在数据库中是绝对禁止的反模式（Anti-Pattern）**。

```text
反模式架构：文件全量存入数据库（灾难级性能与运维）
+------------+       上传 10MB 图片       +---------------------------------------------+
| Web 客户端 | ------------------------> | MySQL 数据库                                |
+------------+                            | [用户表]                                    |
                                          | id: 1001                                    |
                                          | avatar: 0xFFD8FFE0... (10MB 二进制流占据磁盘) |
                                          +---------------------------------------------+
                                          (主从复制延迟暴增、Binlog 撑爆、备份耗时数天、缓存极速失效)

现代标准架构：对象存储 + 数据库轻量级 URL 关联（高性能、解耦）
+------------+       1. 直传图片          +---------------------------------------------+
| Web 客户端 | ------------------------> | 分布式文件系统 / 对象存储 (FastDFS / OSS)   |
|            | <------------------------ | 存储完毕，返回访问 URL: /images/user_1001.jpg |
|            |       2. 返回图片 URL     +---------------------------------------------+
|            |
|            |       3. 仅存 URL 字符串   +---------------------------------------------+
|            | ------------------------> | MySQL 数据库                                |
+------------+                            | [用户表]                                    |
                                          | id: 1001                                    |
                                          | avatar_url: 'https://cdn.site.com/u1001.jpg'|
                                          +---------------------------------------------+
                                          (数据库单行仅数十字节，B+ 树极度紧凑，吞吐量极高)
```

#### 致命弊端分析

1. **磁盘空洞（Holes）与严重的碎片化（Fragmentation）**：
   在频繁更新或删除包含大容量 `BLOB` / `TEXT` 的记录时，数据库无法在底层数据页内平滑复用释放出的庞大连续空间，从而产生大量物理存储碎片与空洞。日积月累，整张表的数据页离散度急剧上升，全表扫描和普通索引范围检索的 I/O 效率将出现灾难性下跌。
2. **主从同步（Replication）严重延迟**：
   MySQL 的主从复制严重依赖 Binlog 日志传输。一个数兆或数十兆的 `BLOB` 字段被写入时，产生的 Row 格式 Binlog 体积巨大。从库在拉取日志并重放时，会引发漫长的主从复制延迟，甚至导致从库直接发生读写超时崩溃。
3. **备份与灾难恢复耗时失控**：
   数据库的逻辑备份（如 `mysqldump`）和物理备份（如 XtraBackup）必须对所有数据页进行快照扫描。若表中堆积了几百 GB 的多媒体二进制流，日常备份不仅会耗尽磁盘 I/O 导致线上业务卡顿，更会导致灾难恢复时间（RTO）被拉长到无法容忍的数天。
4. **内存缓冲池（Buffer Pool）污染**：
   InnoDB 依赖内存中的 Buffer Pool 缓存高频热点数据。当某条查询意外读取了 `BLOB` 字段时，庞大的数据块会瞬间将原本缓存的热点索引和高频业务行踢出内存，导致缓存命中率暴跌。

#### 行业标准解决方案

现代化工业系统的标准做法是**动静分离与资源解耦**：
- **静态资源存入专业存储**：将图片、音视频、PDF 附件直接上传至分布式文件系统（如开源的 FastDFS、MinIO）或公有云对象存储（如阿里云 OSS、腾讯云 COS、AWS S3），并结合 CDN 进行边缘节点加速。
- **数据库仅存元数据与访问路径**：数据库表中仅保留一个普通的 `VARCHAR(255)` 类型的 `file_url` 字段，存储资源文件的 CDN 访问链接。数据库回归结构化事务处理的核心职责，系统吞吐量与扩展性获得几何级提升。

### 大对象（TEXT 与 BLOB）的优化原则

如果在极少数特殊场景下（如敏感合规数据要求随库物理隔离保护），必须在 MySQL 中保存长文本或大二进制对象，必须贯彻以下三项优化规范：

#### 垂直拆表规范（核心）
**严禁将大字段混杂在核心事务主表中！**
必须实施垂直拆表策略：
- **主表**（如 `user_info`）：仅存放 ID、账号、状态等轻量高频检索字段；
- **扩展子表**（如 `user_profile_detail`）：仅存放 `user_id` 与大容量 `BLOB` / `TEXT` 字段。
绝大多数业务查询只读主表，享受小行体积带来的高速内存命中；只有在真正需要查看完整大字段详情时，才通过主键精准点查关联子表。

#### 前缀索引（Prefix Index）
由于大字段内容动辄几千字符，直接对其建立全量索引在物理上是不可行的（超出单个索引键的最大字节数限制）。如果必须对大文本进行搜索，必须采用**前缀索引**：

```sql
-- 仅对文章正文的前 20 个字符建立索引
ALTER TABLE article_content ADD INDEX idx_content_prefix (content(20));
```

通过截取前 $N$ 个字符构建 B+ 树索引，既能满足前缀模糊匹配与等值检索，又大幅压低了索引体积。

#### 绝不滥用 SELECT *
大字段对于网络传输带宽是极大的负担。业务 SQL 必须养成严格禁止 `SELECT *` 的纪律，按需声明字段名，避免非必要的全量大字段随网络传输拉取。

### JSON 数据类型的机制与实操

在互联网业务架构中，客户端（Web、iOS、Android、微信小程序）与服务端之间交换数据的主流标准格式是 JSON（JavaScript Object Notation）。相比早期的 XML，JSON 凭借轻量、结构紧凑、高解析效率的优势统治了 Web 交互。

从 MySQL 5.7 开始，官方正式引入了原生的 `JSON` 数据类型，并在 MySQL 8.0 中进行了深度优化。

#### 原生 JSON 类型 vs 存储为普通 TEXT/VARCHAR

很多初学者认为：JSON 本质上不就是一段用花括号括起来的文本字符串吗？为什么不能直接存进 `VARCHAR` 或 `TEXT` 里？

```text
VARCHAR 存储 JSON 字符串：
+--------------------------------------------------------------+
| '{"name":"宋红康","age":18,"address":{"province":"北京"}}'   |
+--------------------------------------------------------------+
(对于数据库而言完全是一堆无序死文字；读取时必须全量取回应用层，
 由 Java/Python 的 Fastjson/Gson 框架全量解析反序列化才能读取其中一个属性)

MySQL 原生 JSON 类型（内部二进制 BSON 优化存储）：
+--------------------+-----------------------------------------+
| 内部解析好的 Key 表 | 指向各个 Value 的物理存储绝对偏移量指针  |
+--------------------+-----------------------------------------+
(具备格式合法性语法强校验；数据库引擎可在磁盘/内存中根据键名
 瞬间跳转到指定字段的物理偏移量直接提取，无需全量解包反序列化！)
```

原生 `JSON` 类型的核心价值在于：
1. **自动格式校验**：写入数据时，MySQL 会在底层严格校验 JSON 语法的合法性，格式不符合 JSON 规范直接拒绝入库；
2. **优化的二进制存储格式**：内部使用紧凑二进制树状结构存储，键名建立了内部索引查找表，支持以 $O(1)$ 或二分查找的效率直接定位特定键的数值，极大地提升了局部的读写性能。

#### JSON 表结构定义与数据写入

创建 JSON 测试表：

```sql
CREATE TABLE test_json (
    id INT PRIMARY KEY AUTO_INCREMENT,
    js JSON
);
```

向字段写入复合嵌套的 JSON 数据：

```sql
INSERT INTO test_json (js) VALUES (
    '{
        "name": "宋红康",
        "age": 18,
        "address": {
            "province": "北京",
            "city": "北京"
        }
    }'
);
```

执行全表查询：

```sql
SELECT * FROM test_json;
```

控制台能够正常以标准 JSON 结构输出。如果尝试存入不闭合括号或非法 JSON 串，MySQL 会立即报错拦截。

#### 数据提取技巧：箭头操作符与 JSON Path 表达式

在 MySQL 中，开发者无需编写繁杂的字符串截取函数，可以直接使用**箭头操作符 `->`** 配合以 `$` 开头的 **JSON Path** 表达式进行层级下钻查询。

##### 语法规则
- `$` 代表 JSON 数据的根节点；
- `$.key` 用于定位顶层对象中的键；
- `$.object.sub_key` 用于对嵌套子对象进行深层递归点查。

##### 实操演练：单层与深层属性提取

```sql
SELECT 
    js->'$.name' AS full_name,
    js->'$.age' AS user_age,
    js->'$.address.province' AS province,
    js->'$.address.city' AS city
FROM test_json;
```

控制台返回的查询结果清晰有序：

```text
+--------------+----------+----------+--------+
| full_name    | user_age | province | city   |
+--------------+----------+----------+--------+
| "宋红康"     | 18       | "北京"   | "北京" |
+--------------+----------+----------+--------+
```

> **提示**：使用 `->` 提取出的字符串值外围默认保留双引号（保留 JSON 原生字面量类型）。若需要获取不带引号的纯文本展示值，可以使用双箭头操作符 `->>`（等价于 `JSON_UNQUOTE(js->'$.name')`），直接产出人类友好的洁净文本。

### 空间数据类型（GIS）简述

除了常规的标量与复合数据类型外，MySQL 还内建了一整套符合开放地理空间联盟（OGC）标准的地形与空间数据类型（Spatial Data Types），主要用于支持 LBS（基于位置的服务）、地图导航、打车路线追踪以及“查找附近的商家”等业务场景。

空间数据类型宏观上分为两类：
1. **单值几何对象**：
   - `GEOMETRY`：可以容纳任何类型的几何对象基类；
   - `POINT`：点（坐标，如经度与纬度 `(X, Y)`）；
   - `LINESTRING`：线（由两点或多点连接而成的线段或轨迹）；
   - `POLYGON`：多边形（由多条线闭合构成的区域，如配送范围、行政区划）。
2. **复合几何集合对象**：
   - `MULTIPOINT`：多点集合；
   - `MULTILINESTRING`：多线集合；
   - `MULTIPOLYGON`：多个多边形集合（如群岛地貌）；
   - `GEOMETRYCOLLECTION`：任意几何对象的混合容器。

日常开发中，空间类型通常配合 MySQL 的空间分析函数（如 `ST_Distance` 计算经纬度球面距离）与空间 R 树索引协同使用。对于非地理信息强相关的常规业务研发，只需理解其存在与适用场景即可。

## 65-小结及类型使用建议
> 对应分集：P65 | 原始标题：《65-小结及类型使用建议》

在把 MySQL 所有的字段数据类型——从整型、浮点型、定点数，到日期时间、字符串、文本、二进制、JSON 以及枚举集合——完整剖析完一遍之后，很多同学的脑子大概已经开始“嗡嗡”响了。面对 MySQL 提供的几十种具体类型，原本建表时还清楚该用什么，学完一大堆底层细节和边界规则之后，反而不知道在实际项目中该怎么落笔了。

读书和掌握技术的路径，往往要经历两个阶段：**先由薄读厚，再由厚读薄**。

在最初学习 DDL 建表语句时，是一个“读薄”的阶段：我们告诉大家遇到整数就写 `INT`，遇到小数就写 `DOUBLE`，遇到日期就写个 `DATE`，三两句话带过，先跑起来再说。而在前面的章节中，我们把这些类型一层层剥开，看存储占用的字节数、看有符号与无符号的补码机制、看定点数的底层十进制编码、看时区与时间戳转换，这是一个“读厚”的过程。现在到了收官时刻，我们必须重新把它“读薄”——把这些繁复的底层参数，淬炼成一套在实际开发、生产环境和技术面试中可以直接套用的**默认选型底线与工程实践准则**。

### 业务开发中的默认选型基线与底线思维

面对具体的业务字段，如果既没有极端的性能瓶颈，也没有严苛的特殊物理约束，我们应当确立一套标准化的“默认选项”。这套默认基线的第一目标，是**确保系统在长期演进中绝不因为数据类型的定义失误而产生线上故障**。

```text
+-------------------+--------------------+------------------------------------------+
|    数据类别       |    默认推荐类型    |               核心选型考量               |
+-------------------+--------------------+------------------------------------------+
| 整数类型          | INT (或 BIGINT)    | 兜底容量风险，防止数值溢出导致写入崩溃   |
| 小数与金额        | DECIMAL(M, D)      | 强精度保证，彻底杜绝浮点数二进制舍入误差 |
| 日期与时间        | DATETIME           | 跨度大（至9999年），无2038年溢出风险     |
+-------------------+--------------------+------------------------------------------+
```

#### 整数类型的兜底原则与语法变迁

在定义整型字段时，只要没有极度明确的节省空间诉求，**不出意外一律使用 `INT` 类型**。

在初学者或过度优化的设计中，经常有人试图去锱铢必较：看到一个状态码或类型编码，就去定义成 `TINYINT`；看到一个可能几千上万的数据，就自作聪明地定义成 `SMALLINT`（最大仅支持 32767 或无符号 65535）。结果业务上线后数据增长超出预期，一旦数值超过 `SMALLINT` 的上限，在 MySQL 开启严格模式（Strict SQL Mode）时，后续的 `INSERT` 操作会直接报错中断；在非严格模式下则会被截断写入上限值，导致严重的业务数据错乱。

选择 `INT`（占用 4 个字节，带符号可达 21 亿，无符号可达 42 亿）作为默认值，本质上是用微不足道的存储成本，买下整个存储系统的可靠性保障。对于全局唯一流水号、自增主键、超大流水日志，则直接一步到位升级为 `BIGINT`（8 个字节）。

同时必须牢记 MySQL 8.0 的语法规范变化：
在 MySQL 8.0 之前，我们经常在建表语句中看到 `INT(11)` 或 `INT(4)` 这样的写法。我们在前面反复强调过，括号内的数字 `M` 并不代表能够存储的最大数值大小或数据存储位数，它仅仅是在配合 `ZEROFILL` 属性时指定的显示宽度（Display Width）。到了 MySQL 8.0 版本中，官方已经正式不推荐（Deprecated）在整数类型后附加显示宽度括号，未来的版本将彻底移除该语法。因此，现代建表语句中应直接书写 `INT`，不再附加任何多余的小括号参数。

#### 高精度计算对定点数 DECIMAL 的刚性要求

在涉及小数存储时，特别是价格、金额、费率、核算分摊等与资金相关的场景，**一律推荐使用定点数类型 `DECIMAL`**。

使用 `DECIMAL` 时必须严格遵守语法规范：**必须显式指定精度 `M`（总位数）与标度 `D`（小数位数）**。
如果在建表语句中仅仅写了一个裸的 `DECIMAL`，MySQL 会采用默认规则处理：

```sql
-- 错误/不推荐的省略写法
CREATE TABLE tb_demo (
    amount DECIMAL
);

-- MySQL 底层等价于：
CREATE TABLE tb_demo (
    amount DECIMAL(10, 0)
);
```

当省略 `(M, D)` 时，默认标度 `D` 为 0，这意味着该字段将彻底失去小数位，任何写入的小数部分都会被四舍五入抹掉。必须根据业务明确写成形如 `DECIMAL(10, 2)`（总共 10 位，其中包含 2 位小数）的形式。

#### 日期时间类型的稳定性优先

在日期时间类型的选择上，实际开发中推荐默认采用 `DATETIME`。

虽然 `TIMESTAMP` 占用 4 字节，相比占用 5 字节（MySQL 5.6.4 及以后优化版本）或 8 字节（老版本）的 `DATETIME` 略省空间，并且具备时区自动转换特性，但 `TIMESTAMP` 存在致命的硬伤——其最大有效时间仅到 `2038-01-19 03:14:07`（受 32 位有符号整型上限限制）。在企业级架构中，许多合同到期日、按揭贷款期、会员长期权限等时间数据早已规划到了几十年之后，使用 `TIMESTAMP` 极易引发 2038 年溢出灾难。

`DATETIME` 的时间范围覆盖 `1000-01-01 00:00:00` 到 `9999-12-31 23:59:59`，能够彻底屏蔽系统运行的时间跨度边界风险。虽然它需要业务应用层自行统一处理时区，但从底层持久化可靠性的角度来看，它是最具容错能力的默认选项。

### 阿里开发手册规约与核心选型规则

在互联网高并发与海量数据架构中，各大技术团队通过踩坑沉淀出了一系列工业级规范。其中《阿里巴巴 Java 开发手册》针对 MySQL 字段类型的定义，给出了几条极其严谨的强制与推荐标准。

```text
                             阿里巴巴 MySQL 字段规范矩阵
                                          │
       ┌──────────────────┬───────────────┴───────────────┬──────────────────┐
       ▼                  ▼                               ▼                  ▼
【无符号规约】     【小数类型禁止浮点】             【超限处理方案】    【字符串长度分级】
非负字段必须      强制使用 DECIMAL                 拆分整数与小数      ≤5000: VARCHAR
加 unsigned        禁止 FLOAT / DOUBLE              独立存储            >5000: 独立表 TEXT
```

#### 非负数值字段强制使用 unsigned

> **规约**：任何字段如果存储的数值在业务语义上是非负的，必须为其加上 `unsigned` 属性。

在整型数据存储中，计算机底层使用最高位作为符号位（0 表示正数，1 表示负数），其数值表示遵循二进制补码规则：

```text
标准有符号 INT (32 位):
[ 符号位 1 bit ] [ 数值位 31 bits ]  => 范围: -2,147,483,648 到 2,147,483,647

无符号 INT UNSIGNED (32 位):
[ 全数值位 32 bits ]               => 范围: 0 到 4,294,967,295
```

如果某个业务实体（例如自增主键 ID、商品库存量、用户年龄、访问 PV、点赞数）在业务逻辑上绝对不可能为负数，那么保留左侧的负数区间是完全无意义的资源浪费。通过附加 `unsigned` 约束，符号位转化为有效数值位，在不增加任何物理存储字节数的前提下，正数上限直接扩大了一整倍。对于处于业务爆发期、主键消耗极快的数据表，这相当于将主键用尽的风险向后推迟了一倍的时间。

对于浮点类型，语法上也支持指定 `unsigned`，但由于其底层采用 IEEE 754 浮点编码格式，且浮点类型在现代数据库规范中被高度边缘化，故无符号修饰符在浮点上收益有限，主要战场集中于整型家族。

#### 小数类型强制使用 DECIMAL 并严禁浮点数

> **规约**：小数类型必须使用 `DECIMAL`，禁止使用 `FLOAT` 和 `DOUBLE`。

手册在这里使用了极严厉的词汇——**“禁止”**。之所以如此坚决地把 `FLOAT` 和 `DOUBLE` 排除在商业生产系统之外，核心根源在于其底层的二进制浮点表示法具有不可逆的精度缺失。

计算机内存采用二进制位存储数据，而十进制的小数部分在转换为二进制时，通常会产生无限循环的小数位。例如十进制的 `0.1`，转化为二进制浮点表示为：

$$0.1_{10} = 0.00011001100110011..._2$$

受限于 `FLOAT`（32 位，23 位尾数）和 `DOUBLE`（64 位，52 位尾数）的存储位宽，超出尾数长度的部分只能被硬件强制截断或舍入。这会导致看似简单的数值计算在数据库层产生幽灵误差：两个在业务逻辑上完全相等的浮点数，使用 `=` 条件查询时可能永远返回 false；在执行累加求和（`SUM()`）时，账目总额会多出一分或少出一分钱。

定点数 `DECIMAL` 在底层并不是采用 IEEE 754 浮点编码，而是将数字转换成特定的紧凑十进制格式（由每 9 个十进制数字打包为 4 字节的整型序列）进行存储与运算，每一位数字都是物理上绝对精确的。商业系统中账务核算、资产划转、结算分账对数据精准度是零容忍的，因此必须全线杜绝浮点数。

#### 超出 DECIMAL 上限的高阶架构设计：拆分存储

在面试或超高精度金融交易系统设计中，经常会出现一个追问：
**如果需要存储的数值精度或数值范围，超出了 MySQL `DECIMAL` 所能支持的最大范围，应当如何处理？**

MySQL 的 `DECIMAL(M, D)` 中，`M` 的最大限制是 65，`D` 的最大限制是 30。尽管这已经足以支撑绝大多数日常业务，但在某些天体物理模拟、区块链高位加密货币单位（如以太坊的最小单位 Wei，1 ETH = $10^{18}$ Wei）、外汇微秒级高频微点差计算中，依然可能面临溢出。

处理该问题的标准工程方案为：**拆分存储法**。
将原本的一个数值，在逻辑上人工拆解为两个独立的字段：
1. **整数部分字段**：使用 `BIGINT` 或独立的 `DECIMAL` 存储该数值的整数位。
2. **小数部分字段**：使用独立的 `BIGINT` 或 `DECIMAL` 存储该数值的小数部分，记录其放大 $10^N$ 倍后的实际基数与有效精度指数。

在数据库物理层面，两个字段各自承担一部分存储，彼此不会发生精度溢出；在应用层（如 Java 服务的底层计算框架中），读取这两个字段后组装成 `BigDecimal` 或自研的大数运算库进行高精度运算。在面试中遇到此类追问，必须能够清晰说明这种“空间换精度、化整为零”的架构设计。

### 字符串与大文本类型的存储选型与物理性能

字符串类型的选择，核心在于权衡**物理连续性、长度开销与检索性能**。

```text
                              字符串选型决策流
                                     │
                     [字符串长度是否基本固定?]
                            /          \
                          是            否
                          /              \
                   选用 CHAR(N)        [最大长度是否 ≤ 5000?]
                                             /          \
                                           是            否
                                           /              \
                                  选用 VARCHAR(N)      选用 TEXT
                                                      且独立拆分子表
```

#### CHAR 与 VARCHAR 的选型边界

在短文本存储场景中，我们需要在定长类型 `CHAR` 与变长类型 `VARCHAR` 之间做抉择：

| 类型对比维度 | 定长类型 CHAR(N) | 变长类型 VARCHAR(N) |
| :--- | :--- | :--- |
| **存储空间** | 固定占用 $N$ 个字符对应的物理字节空间，不足时右补空格填充 | 实际字符占用空间 + 变长长度列表（1~2 字节） |
| **修改开销** | 极小，行长度固定，就地原地更新，绝不发生行迁移（Row Migration） | 增大字符时可能导致行长度超出原位置，引发页分裂与重构 |
| **检索性能** | 内存偏移量计算极快，直接按固定步长寻址 | 需先解析前置长度字节，计算实际数据边界 |
| **典型应用** | 手机号（11位）、MD5密文（32位）、UUID、身份证号、状态定长代码 | 用户住址、商品标题、个人简介、动态评论 |

如果字符串的物理长度在业务上完全一致，或者极度接近（例如中国大陆手机号码固定为 11 位数字），必须果断使用 `CHAR`。虽然 `VARCHAR` 理论上能省下极少量空间，但为了节省这几个字节，需要额外付出维护 1~2 字节长度前缀的代价，并在 CPU 解析数据行时增加寻址运算负担。

而对于长度不可预估、长短差异极大的文本（如收货地址，短的可能十几个字，长的包含省市区街道门牌号上百字），则选用 `VARCHAR`。

#### 大文本超过 5000 字符的隔离原则与空间空洞防护

> **规约**：当变长字段长度超过 5000 时，不再适宜使用 `VARCHAR`，应升级为 `TEXT` 类型；并且建议将 `TEXT` 字段从主表中剥离，单独建立一张附加表进行一对一关联存储。

该规约背后隐藏着 InnoDB 存储引擎底层的两大核心痛点：

##### 避免主表行记录膨胀引发的聚簇索引利用率暴跌
InnoDB 的数据是以“数据页（Page）”为单位加载进 Buffer Pool（内存缓冲池）的，每个数据页的标准大小为 16KB。
如果一张表中包含大量长文本字段，导致单行记录的数据体积急剧膨胀，那么一个 16KB 的数据页中能够容纳的数据行数就会暴跌。在进行全表扫描、范围查询或非覆盖索引回表时，数据库必须加载成倍的磁盘数据页才能检索出目标数据，极大地消耗了磁盘 I/O 和内存带宽。
把超过 5000 字符的大文本剥离至扩展表中，主表只保留轻量级的核心检索字段，能够让主表的聚簇索引树变得极度紧凑，大幅提升内存命中率。

##### 规避高频变更产生的存储碎片与“空间空洞（Table Holes / Fragmentation）”
在前面剖析 TEXT 和 BLOB 溢出页存储时曾讲过，大文本字段在物理底层往往被存放在独立于聚簇索引页之外的“溢出页（Off-page）”中。
当对这些长文本字段进行高频的更新（`UPDATE`）或删除（`DELETE`）操作时，由于文本长度变动剧烈，被释放出来的溢出页和数据块无法直接被其他固定长度的行记录复用。长期运行后，数据文件中会充斥着大量无法合并的离散空白碎片，也就是通常所说的**空间空洞**。
如果把这类字段隔离在独立子表中，未来即使产生了严重的存储碎片，也可以单独针对该子表执行 `OPTIMIZE TABLE` 操作进行空间回收与表重构，而完全不会阻塞或影响主核心业务表的正常读写。

搞清楚字段类型后方附加的各类属性：
- `UNSIGNED`：无符号标识，仅用于非负数值，扩大正数存储区间。
- `CHARACTER SET & COLLATE`：为字符列显式或隐式绑定的字符编码集（如 `utf8mb4`）与排序校对规则。
- `DECIMAL(M, D)` 的精度定义：严格指定总位数与小数位，杜绝使用裸 `DECIMAL`。
- 8.0 语法演进：明确废弃了整型显示宽度参数的误导性使用。

#### 生产环境的业务场景选型权衡
1. **可靠性优先于过度优化**：在容量预估不明确时，优先选用大一级别的标准类型（如用 `INT` 代替 `SMALLINT`），确保数据永不溢出挂死。
2. **精度绝对优先于计算性能**：涉及金钱、结算必须强制 `DECIMAL`，彻底远离浮点陷阱。
3. **空间开销与 I/O 效率的动态平衡**：对于大字段，通过垂直分表（拆分 `TEXT`）保护主表行宽，从物理层面规避碎片空洞与全表扫描性能恶化。

### 本讲提到的题目

在这一讲的总结与课后练习安排中，我们没有布置偏怪的冷门算法题，而是梳理了在实际开发与技术面试中最容易被考察的三个核心复盘问题。

#### 题目 1：在 MySQL 规范中，核心数据类型的分类有哪些？在定义字段时应建立怎样的默认基线？
- **解析**：
  核心分类涵盖数值型（整型、定点数、浮点数）、字符与文本型（CHAR、VARCHAR、TEXT）、日期时间型（YEAR、DATE、TIME、DATETIME、TIMESTAMP）、二进制型（BINARY、VARBINARY、BLOB）、以及高级复合类型（JSON、ENUM、SET）。
- **基线标准**：
  在通用业务中，整型不出意外默认使用 `INT`（超大表用 `BIGINT`）；小数与金额强制使用定点数 `DECIMAL(M, D)` 并显式指明参数；日期时间默认推荐使用 `DATETIME` 规避 2038 年溢出问题。

#### 题目 2：如果在金融系统中需要记录超高精度的数值，但数值大小已经超出了 MySQL 定点数 DECIMAL(65, 30) 的物理上限，工程上有何标准的解决思路？
- **解析**：
  此题为典型的高级架构与面试考点。标准解决方案为**拆分存储法**。在数据库表中将该数值拆分为两个独立字段：一个字段用来存储整数部分（使用 `BIGINT` 或 `DECIMAL`），另一个字段用来存储经过放大换算的小数部分；在应用层（如使用 Java 的 `BigDecimal`）对数据进行拼装与高精度数学计算，从而绕过单字段存储宽度的物理上限。

#### 题目 3：简述 CHAR、VARCHAR 与 TEXT 的选型界限，并解释为什么阿里巴巴规范要求当字段长度超过 5000 时需转为 TEXT 并建议单独拆表？
- **解析**：
  - `CHAR` 用于长度严格固定或高度一致的短文本（如手机号、MD5哈希），无需额外维护长度列表，检索寻址速度最快；
  - `VARCHAR` 适用于长度波动较大的变长文本，但在长度超过 5000 时，若继续留在主表中，会导致主表行记录（Row Format）过宽，使得单个 16KB 数据页容纳的行数大幅减少，降低 Buffer Pool 的缓存效率并严重恶化 I/O 性能；
  - 将超过 5000 字符的文本升级为 `TEXT` 并隔离至独立的扩展子表中，主表仅保留外键或关联 ID，一方面保证了主表聚簇索引树的高度紧凑，另一方面隔离了长文本高频修改产生的磁盘碎片与“空间空洞”，避免主表性能劣化。
